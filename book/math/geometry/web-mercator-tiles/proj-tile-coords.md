# ⚙️ Тайлова арифметика: обернений хід, видима область і п'ять пасток

Перетворення «градуси → номер тайла» пишуть першим, і воно ж єдине, яке зазвичай працює з першого разу. Робочий код карти живе з іншого боку: треба вміти повернутися від пікселя до градусів, зібрати список тайлів під видимий прямокутник, обійти гілку квадродерева для офлайн-кешу й намалювати масштабну лінійку. Тут зібрано всі чотири операції — робочим кодом на TypeScript (клієнт у браузері) і C++ (наземна станція, гаряча дорога рендера) — і п'ять місць, де ця арифметика ламається мовчки.

## Обернений хід: від пікселя до градусів

Пряме перетворення робило два кроки: нормалізувало точку в квадрат зі стороною одиниця, потім множило на 2ᶻ. Обернене йде тими самими кроками навспак — ділимо на 2ᶻ, розгортаємо нормалізацію. Лінійна горизонталь повертається тривіально, а от вертикаль вимагає обернути інтеграл секанса.

Обернена до `y = ln tan(π/4 + φ/2)` має три рівносильні записи:

```text
φ(y) = 2·arctan(eʸ) − π/2 = arcsin(tanh y) = arctan(sinh y)
```

Математично це одна функція (у неї є ім'я — **ґудерманіан**), але для обчислень вони не рівноцінні. Перша форма біля екватора віднімає два майже однакові числа: при малому `y` вираз `2·arctan(eʸ)` дорівнює приблизно `π/2 + y`, і віднімання `π/2` з'їдає саме ту дрібну частину, заради якої все рахувалося. Втрата вимірна:

```text
y = 10⁻¹²      2·arctan(eʸ) − π/2   →  1.000088900582e−12     відносна похибка 8.9·10⁻⁵
               arctan(sinh y)       →  9.999999999999e−13     точно
```

Тобто за метр від екватора перша форма бреше в п'ятому знаку. Тому в коді стоїть `arctan(sinh y)` — одна бібліотечна функція, монотонна, без віднімань. З тієї ж причини й пряме перетворення краще писати як `asinh(tan φ)`, а не `ln tan(π/4 + φ/2)`: на широті 10⁻⁷ градуса логарифмічна форма вже розходиться з правильною відповіддю в дев'ятому знаку. Обидві форми спираються на [гіперболічні функції](book:math/hyperbolic-functions) — синус і його обернену, і саме їхня бібліотечна реалізація рятує точність біля нуля.

Далі — код. Функція бере **дробові** тайлові координати: ціла частина — номер тайла, дробова — позиція всередині нього. Так одна функція покриває і «кут тайла», і «піксель під курсором». Чотири фрагменти C++ нижче йдуть підряд і складають один файл: перший відкриває простір імен, останній його закриває.

```ts
export const MAX_LAT = 85.0511287798;   // широта зрізу: там висота карти = ширині
export const TILE = 256;                // сторона тайла в пікселях

export interface LatLon { lat: number; lon: number; }
export interface BBox { north: number; south: number; west: number; east: number; }

/** Дробові тайлові координати рівня z -> широта/довгота. */
export function tileToLatLon(fx: number, fy: number, z: number): LatLon {
  const n = 2 ** z;
  const lon = (fx / n) * 360 - 180;              // горизонталь лінійна
  const ym = (0.5 - fy / n) * 2 * Math.PI;       // назад у меркаторові одиниці
  return { lat: (Math.atan(Math.sinh(ym)) * 180) / Math.PI, lon };
}

/** Тайл (z,x,y) плюс піксель усередині нього -> градуси. */
export function pixelToLatLon(x: number, y: number, px: number, py: number, z: number): LatLon {
  return tileToLatLon(x + px / TILE, y + py / TILE, z);
}

/** Географічні межі тайла: NW-кут і SE-кут. */
export function tileBounds(x: number, y: number, z: number): BBox {
  const nw = tileToLatLon(x, y, z);
  const se = tileToLatLon(x + 1, y + 1, z);
  return { north: nw.lat, west: nw.lon, south: se.lat, east: se.lon };
}
```

#include <cmath>
#include <cstdint>
#include <cstddef>
#include <algorithm>
#include <initializer_list>
#include <string>
#include <vector>

namespace tiles {

inline constexpr double PI      = 3.14159265358979323846;
inline constexpr double MAX_LAT = 85.0511287798;   // широта зрізу: висота = ширині
inline constexpr int    TILE    = 256;             // сторона тайла в пікселях

struct LatLon { double lat, lon; };
struct BBox   { double north, south, west, east; };
struct TileId { int z; std::int64_t x, y; };

// 2^z точно й дешево — без pow()
inline double pow2(int z) { return std::ldexp(1.0, z); }

// Дробові тайлові координати рівня z -> широта/довгота.
LatLon tile_to_lat_lon(double fx, double fy, int z) {
    const double n   = pow2(z);
    const double lon = fx / n * 360.0 - 180.0;          // горизонталь лінійна
    const double ym  = (0.5 - fy / n) * 2.0 * PI;       // назад у меркаторові одиниці
    return { std::atan(std::sinh(ym)) * 180.0 / PI, lon };
}

// Тайл (z,x,y) плюс піксель усередині нього -> градуси.
LatLon pixel_to_lat_lon(std::int64_t x, std::int64_t y, double px, double py, int z) {
    return tile_to_lat_lon(static_cast<double>(x) + px / TILE,
                           static_cast<double>(y) + py / TILE, z);
}

// Географічні межі тайла: NW-кут і SE-кут.
BBox tile_bounds(std::int64_t x, std::int64_t y, int z) {
    const LatLon nw = tile_to_lat_lon(static_cast<double>(x),     static_cast<double>(y),     z);
    const LatLon se = tile_to_lat_lon(static_cast<double>(x + 1), static_cast<double>(y + 1), z);
    return { nw.lat, se.lat, nw.lon, se.lon };
}

## Тайли під видиму область

Клієнт має прямокутник видимої області в градусах і рівень `z`; треба список адрес. Здається, що досить прогнати два кути крізь пряме перетворення й пробігти діапазон номерів — і саме тут ховається найдорожча помилка тайлового коду.

Причина в тому, що карта по горизонталі **циклічна**. Схід і захід — той самий 180-й меридіан, і тайл із номером `n−1` сусідить із тайлом `0`. Коли видима область перетинає цей шов, лівий край дає більший номер, ніж правий, і наївне `min`/`max` розвертає діапазон навиворіт: замість двох стовпців ви просите весь світ.

**Видима область через 180-й меридіан, рівень z = 3 (n = 8 стовпців).**
```text
захід λ = 170°    fx = (170 + 180)/360 · 8 = 7.778   → стовпець 7
схід  λ = −170°   fx = (−170 + 180)/360 · 8 = 0.222  → стовпець 0

наївно:      min = 0, max = 7  →  стовпці 0…7  →  8 з 8  →  ВЕСЬ СВІТ
правильно:   0.222 < 7.778 → додаємо n: 8.222
             стовпці 7…8, тобто 7 і 8 mod 8 = 0  →  2 тайли
```

Ліки — рахувати ширину діапазону **до** взяття цілої частини: якщо права дробова координата виявилася меншою за ліву, прямокутник перетнув шов, і до неї треба додати `n`. Далі номери беруться за модулем `n` — це звичайна [арифметика лишків](book:math/modular-arithmetic), тільки модуль тут степінь двійки.

По вертикалі все навпаки: карта **розрізана**. Полюсів на ній немає взагалі, верхній край — це 85.0511°, і за ним нічого немає. Тому `y` не загортається, а **обрізається** до `[0, n−1]`. Плутати ці дві осі не можна: загорнути `y` означає намалювати Антарктиду над Арктикою, обрізати `x` — розірвати карту посеред Тихого океану.

*По горизонталі карта — циліндр: стовпець 7 сусідить зі стовпцем 0, і перехід між ними є взяттям лишку за модулем 2ᶻ. По вертикалі карта — смуга з обрізаними краями: за верхнім рядком нічого немає, тому номер рядка притискається до діапазону, а не загортається. Наївні min/max на циклічній осі перетворюють два тайли на всі вісім.*

:::tabs
```ts
export interface TileId { z: number; x: number; y: number; }

/** Довгота -> дробова тайлова X. НЕ обрізається: значення може вийти за [0,n). */
function lonToX(lonDeg: number, z: number): number {
  return ((lonDeg + 180) / 360) * 2 ** z;
}

/** Широта -> дробова тайлова Y. Зріз до ±MAX_LAT ОБОВ'ЯЗКОВИЙ перед asinh/log. */
function latToY(latDeg: number, z: number): number {
  const lat = Math.min(MAX_LAT, Math.max(-MAX_LAT, latDeg));
  const ym = Math.asinh(Math.tan((lat * Math.PI) / 180));   // = ln tan(π/4 + φ/2)
  return (0.5 - ym / (2 * Math.PI)) * 2 ** z;
}

/** Усі тайли рівня z, що накривають прямокутник. Коректно через 180-й меридіан. */
export function tilesForBBox(b: BBox, z: number): TileId[] {
  const n = 2 ** z;

  // y: обрізаємо — полюсів на карті немає, склеювати нема чого
  const yTop = Math.max(0, Math.floor(latToY(b.north, z)));
  const yBot = Math.min(n - 1, Math.floor(latToY(b.south, z)));

  // x: ширину рахуємо в ДРОБОВИХ координатах, до floor
  const fLeft = lonToX(b.west, z);
  let fRight = lonToX(b.east, z);
  if (fRight < fLeft) fRight += n;                 // прямокутник перетнув шов
  const xLeft = Math.floor(fLeft);
  const spanX = Math.min(n, Math.floor(fRight) - xLeft + 1);

  const out: TileId[] = [];
  for (let y = yTop; y <= yBot; y++) {
    for (let i = 0; i < spanX; i++) {
      out.push({ z, x: (((xLeft + i) % n) + n) % n, y });   // циклічність по x
    }
  }
  return out;
}
```
```cpp
// Довгота -> дробова тайлова X. НЕ обрізається: значення може вийти за [0,n).
double lon_to_x(double lon_deg, int z) {
    return (lon_deg + 180.0) / 360.0 * pow2(z);
}

// Широта -> дробова тайлова Y. Зріз до ±MAX_LAT ОБОВ'ЯЗКОВИЙ перед asinh/log.
double lat_to_y(double lat_deg, int z) {
    const double lat = std::clamp(lat_deg, -MAX_LAT, MAX_LAT);
    const double ym  = std::asinh(std::tan(lat * PI / 180.0));   // = ln tan(π/4 + φ/2)
    return (0.5 - ym / (2.0 * PI)) * pow2(z);
}

// Усі тайли рівня z, що накривають прямокутник. Коректно через 180-й меридіан.
std::vector<TileId> tiles_for_bbox(const BBox& b, int z) {
    const std::int64_t n = std::int64_t{1} << z;    // z ≤ 62, інакше UB

    // y: обрізаємо — полюсів на карті немає, склеювати нема чого
    const std::int64_t y_top = std::max<std::int64_t>(
        0, static_cast<std::int64_t>(std::floor(lat_to_y(b.north, z))));
    const std::int64_t y_bot = std::min<std::int64_t>(
        n - 1, static_cast<std::int64_t>(std::floor(lat_to_y(b.south, z))));

    // x: ширину рахуємо в ДРОБОВИХ координатах, до floor
    const double f_left = lon_to_x(b.west, z);
    double f_right      = lon_to_x(b.east, z);
    if (f_right < f_left) f_right += static_cast<double>(n);   // перетнули шов

    const std::int64_t x_left = static_cast<std::int64_t>(std::floor(f_left));
    const std::int64_t span_x = std::min<std::int64_t>(
        n, static_cast<std::int64_t>(std::floor(f_right)) - x_left + 1);

    std::vector<TileId> out;
    if (y_bot < y_top || span_x <= 0) return out;
    out.reserve(static_cast<std::size_t>((y_bot - y_top + 1) * span_x));
    for (std::int64_t y = y_top; y <= y_bot; ++y)
        for (std::int64_t i = 0; i < span_x; ++i)
            out.push_back({ z, ((x_left + i) % n + n) % n, y });   // циклічність по x
    return out;
}

Рахувати кількість треба **до** циклу, а не всередині нього.

## Обхід гілки квадродерева

Предзавантаження офлайн-карти ставить іншу задачу: є район на грубому рівні, потрібні всі тайли під ним аж до робочого рівня. Оскільки тайл `(z, x, y)` розпадається рівно на чотирьох дітей `(z+1, 2x+i, 2y+j)` при `i, j ∈ {0, 1}`, це обхід гілки чотиридольного дерева вглиб.

Головне тут не сам обхід, а **число**. Кожен рівень множить кількість на чотири, тож глибина `d` дає геометричну суму:

```text
1 + 4 + 16 + … + 4ᵈ = (4ᵈ⁺¹ − 1) / 3
```

**Один тайл рівня 10, викачаний до рівня 16.**
```text
d = 16 − 10 = 6
всього = (4⁷ − 1)/3 = (16384 − 1)/3 = 5461 тайлів
при ~15 КБ на тайл                  ≈ 80 МБ
на один рівень глибше (до 17)       ≈ 21845 тайлів ≈ 320 МБ
```

Один зайвий рівень учетверяє і трафік, і час. Тому функція підрахунку існує окремо від функції обходу й викликається першою — спитати користувача «качаємо 320 МБ?» можна лише до того, як почав качати. Практичну механіку зберігання й витіснення розібрано в [кеші тайлів](book:programming/offline-tile-cache); якщо ж адреси треба ще й компактно індексувати, трійка `(z, x, y)` згортається в один ключ переплітанням бітів — [крива Мортона](book:algorithms/z-order-curve), у тайловому світі відома як quadkey.

Обхід пишемо явним стеком, без рекурсії: глибина відома наперед, а рекурсивний виклик на гарячій дорозі рендера дає лише зайвий кадр стека на кожен тайл.

:::tabs
```ts
/** Усі нащадки тайла — від нього самого до рівня maxZ включно. */
export function* descendants(root: TileId, maxZ: number): Generator<TileId> {
  const stack: TileId[] = [root];
  while (stack.length > 0) {
    const cur = stack.pop()!;
    yield cur;
    if (cur.z >= maxZ) continue;
    const z = cur.z + 1, x = cur.x * 2, y = cur.y * 2;
    stack.push({ z, x, y }, { z, x: x + 1, y }, { z, x, y: y + 1 }, { z, x: x + 1, y: y + 1 });
  }
}

/** Скільки тайлів це буде. Викликати ПЕРЕД завантаженням. */
export function descendantCount(fromZ: number, toZ: number, seeds: number): number {
  if (toZ < fromZ) return 0;
  const d = toZ - fromZ;
  return seeds * ((4 ** (d + 1) - 1) / 3);       // 1 + 4 + … + 4ᵈ
}
```
```cpp
// Усі нащадки тайла — від нього самого до рівня max_z включно.
// Явний стек, не рекурсія: глибина відома, зайві кадри на гарячій дорозі ні до чого.
template <class F>
void for_each_descendant(TileId root, int max_z, F&& visit) {
    std::vector<TileId> stack{ root };
    while (!stack.empty()) {
        const TileId cur = stack.back();
        stack.pop_back();
        visit(cur);
        if (cur.z >= max_z) continue;
        const int z = cur.z + 1;
        const std::int64_t x = cur.x * 2, y = cur.y * 2;
        stack.push_back({ z, x,     y     });
        stack.push_back({ z, x + 1, y     });
        stack.push_back({ z, x,     y + 1 });
        stack.push_back({ z, x + 1, y + 1 });
    }
}

// Скільки тайлів це буде. Викликати ПЕРЕД завантаженням.
std::int64_t descendant_count(int from_z, int to_z, std::int64_t seeds) {
    if (to_z < from_z) return 0;
    const int d = to_z - from_z;
    if (d > 30) return -1;                       // 4^31 уже не влазить — сигналимо
    const std::int64_t total = ((std::int64_t{1} << (2 * (d + 1))) - 1) / 3;
    return seeds * total;                        // ділимо ПЕРЕД множенням
}
```

## Масштабна лінійка

Роздільність — це скільки метрів землі припадає на піксель екрана. Оскільки карта розтягнула все в `sec φ` разів, дійсність треба стиснути назад тим самим множником, тобто помножити на `cos φ`:

```text
роздільність(φ, z) = 40 075 016.686 · cos φ / (256 · 2ᶻ)   метрів на піксель
```

Але лінійка малюється не з цього числа. Ніхто не показує смужку з підписом «365 метрів» — показують круглу величину, а під неї підганяють довжину смужки. Тобто рахунок іде навпаки: беремо бюджет у пікселях, переводимо в метри, округлюємо **вниз** до найближчого зручного числа з ряду 1-2-5, і вже з нього отримуємо справжню ширину смужки.

**Київ, рівень 15, бюджет 120 пікселів.**
```text
роздільність = 40 075 016.686 · cos 50.4501° / (256 · 32768) = 3.0420 м/піксель
120 пікселів = 3.0420 · 120 = 365.03 м
округлення вниз по ряду 1-2-5:            365.03 → 200 м
ширина смужки = 200 / 3.0420               = 65.7 пікселя
```

Смужка вийшла коротшою за бюджет майже вдвічі — така плата за круглий підпис, і саме тому бюджет беруть із запасом. Важливіше інше: лінійка чесна лише на тій широті, для якої порахована, і лише на коротких відстанях. Розтягувати її на пів екрана не можна — `cos φ` встигне помітно змінитися. Для справжніх вимірів беруть [відстань по великому колу](book:math/great-circle-distance) або геодезичні розв'язки на еліпсоїді.

:::tabs
```ts
const EQUATOR = 2 * Math.PI * 6378137;          // 40 075 016.686 м

/** Метрів землі в одному пікселі екрана на цій широті й цьому рівні. */
export function resolution(latDeg: number, z: number): number {
  return (EQUATOR * Math.cos((latDeg * Math.PI) / 180)) / (TILE * 2 ** z);
}

export interface ScaleBar { metres: number; pixels: number; label: string; }

/** Найбільша «кругла» відстань (ряд 1-2-5), що вміщується в maxPx пікселів. */
export function scaleBar(latDeg: number, z: number, maxPx = 120): ScaleBar {
  const mPerPx = resolution(latDeg, z);
  const raw = mPerPx * maxPx;
  const pow = 10 ** Math.floor(Math.log10(raw));
  const nice = [5, 2, 1].find((c) => raw >= c * pow)! * pow;
  return {
    metres: nice,
    pixels: nice / mPerPx,
    label: nice >= 1000 ? `${nice / 1000} км` : `${nice} м`,
  };
}
```
```cpp
inline constexpr double EQUATOR = 40075016.685578488;   // 2π·6378137 м

// Метрів землі в одному пікселі екрана на цій широті й цьому рівні.
double resolution(double lat_deg, int z) {
    return EQUATOR * std::cos(lat_deg * PI / 180.0) / (TILE * pow2(z));
}

struct ScaleBar { double metres, pixels; std::string label; };

// Найбільша «кругла» відстань (ряд 1-2-5), що вміщується в max_px пікселів.
ScaleBar scale_bar(double lat_deg, int z, double max_px = 120.0) {
    const double m_per_px = resolution(lat_deg, z);
    const double raw      = m_per_px * max_px;
    const double p        = std::pow(10.0, std::floor(std::log10(raw)));

    double nice = p;
    for (double c : { 5.0, 2.0, 1.0 })
        if (raw >= c * p) { nice = c * p; break; }

    const std::string label =
        nice >= 1000.0 ? std::to_string(static_cast<long long>(nice / 1000.0)) + " км"
                       : std::to_string(static_cast<long long>(nice)) + " м";
    return { nice, nice / m_per_px, label };
}

## П'ять пасток

### Зріз широти мусить стояти перед логарифмом

Це найпідступніше місце, бо жодна з трьох аварій не схожа на аварію. Функція `tan(π/4 + φ/2)` на полюсі мала б дати нескінченність, але в числах із рухомою комою `π/2` не подається точно, тож замість вибуху виходить велике **скінченне** число — і далі все «працює»:

```text
φ = 90°      tan(π/4 + φ/2) = 1.633·10¹⁶   y = 37.33    yn = −5.44   Y при z=15 = −178 308
φ = 90.5°    tan(…) від'ємний              y = NaN      yn = NaN     Y = NaN
φ = −90°     tan(…) = 0 точно              y = −∞       yn = +∞      Y = +∞
```

Три різні поломки з однієї причини. Рівно на полюсі номер тайла стає великим від'ємним цілим — запит іде на неіснуючу адресу або, гірше, індексує масив кеша за від'ємним зсувом. За полюсом (а туди легко потрапити з битого NMEA-речення чи з повзунка, який дозволив 90.0000001) тангенс міняє знак, логарифм від'ємного дає `NaN`, і той `NaN` тихо розповзається по всій геометрії: будь-яке порівняння з ним хибне, тож перевірка меж його не спіймає. На південному полюсі тангенс — точний нуль, логарифм нуля за IEEE-754 дорівнює мінус нескінченності, і номер тайла стає плюс нескінченністю.

Тому `clamp` до ±85.0511287798° стоїть **першим рядком** функції, до будь-якої тригонометрії. Не після, не в місці виклику — саме там, бо це єдина точка, крізь яку проходять усі широти. Природа `NaN` і причина, чому «нескінченність» тут виявляється скінченним сміттям, — у [числах із рухомою комою](book:math/floating-point).

### x циклічний, y — ні

Розібрано вище на прикладі 180-го меридіана. Правило коротке: `x` завжди береться `mod 2ᶻ`, `y` завжди притискається до `[0, 2ᶻ−1]`. Симетрична обробка обох осей — помилка в будь-який бік.

### Переповнення 2ᶻ

`2ᶻ` в 32-бітному цілому переповнюється на `z = 31`, і зсув `1 << 31` для знакового типу — це навіть не переповнення, а невизначена поведінка. Але біда приходить набагато раніше, бо реально рахують не тайли, а **світові пікселі**: їх `2ᶻ⁺⁸`.

```text
z = 22    світових пікселів 2³⁰ = 1 073 741 824    ще влазить у int32
z = 23    світових пікселів 2³¹ = 2 147 483 648    переповнення (максимум 2 147 483 647)
```

Тобто знаковий 32-бітний лічильник помирає вже на 23-му рівні — а такі рівні цілком трапляються в аерознімках і власних ортофотопланах, де тайли ріжуть глибше за звичайну оглядову карту. Симптом характерний: карта працює до якогось зуму, а далі стрибає в протилежний кут світу, бо номер став від'ємним. Ліки — `int64` для номерів і зсув із правильним типом літерала (`std::int64_t{1} << z`, а не `1 << z`); механізм самої аварії — у [переповненні й загортанні](book:programming/overflow-wraparound).

### float32 не доживає до 20-го рівня

Ця пастка окрема, бо тут переповнення немає — числа цілком у діапазоні, просто перестають розрізнятися. У 32-бітному числі з рухомою комою 24 значущі двійкові розряди. Світ на рівні `z` має `2ᶻ⁺⁸` пікселів завширшки, і щойно це перевищить `2²⁴`, сусідні пікселі отримують одне й те саме подання.

Наслідок красиво не залежить від зуму. Крок `float32` на землі дорівнює довжині екватора, поділеній на `2²⁴`, — і це те саме число на будь-якому рівні:

```text
крок float32 на землі = 40 075 016.686 / 2²⁴ ≈ 2.39 м        (незалежно від z)

z = 16    піксель на землі 2.39 м    крок float32 = 1 піксель    ще рівно
z = 18    піксель 0.60 м             крок = 4 пікселі
z = 20    піксель 0.15 м             крок = 16 пікселів
z = 22    піксель 0.037 м            крок = 64 пікселі
```

Тобто світові координати у `float32` дають близько двох з половиною метрів точності назавжди, скільки не наближай. На 16-му рівні це ще збігається з розміром пікселя, а далі кожен рівень подвоює помилку: на 22-му позначка стрибає на шістдесят чотири пікселі — майже чверть тайла.

![Два графіки в логарифмічному масштабі проти рівня зуму: спадна пряма — розмір пікселя на землі, горизонтальна пряма на рівні 2.39 метра — крок float32; вони перетинаються рівно на z=16, і праворуч від перетину відмічено похибку 16 пікселів на z=20 і 64 пікселі на z=22](/book/math/geometry/web-mercator-tiles/img/float32-floor.svg)
*Розмір пікселя на землі падає вдвічі з кожним рівнем, а крок float32 у світових координатах на землі стоїть на місці — близько 2.39 метра. Перетин припадає рівно на 16-й рівень: там одне значення float32 дорівнює одному пікселю. Глибше float32 уже не розрізняє сусідні пікселі, і розрив подвоюється щорівня.*

Виправляється це не переходом на `double` в шейдері (там його часто просто немає), а зміною початку відліку: координати тримають **відносно тайла або відносно локального центру**, а не від краю світу. Тоді величини малі, а `float32` на малих величинах точний — уся його біда була в тому, що 24 розряди витрачалися на адресу в гігантському світі замість позиції всередині маленького тайла.

### TMS проти XYZ: `y` рахується з іншого краю

Схем адресації дві, і вони відрізняються лише напрямком вертикального номера. У схемі XYZ (її вживають OpenStreetMap, Google і майже всі тайлові сервіси) початок — у **північно-західному** куті, `y` росте на південь. У схемі TMS, описаній специфікацією OSGeo, початок — у **південно-західному** куті, і `y` росте на північ; специфікація прямо визначає `<Origin>` як нижній лівий кут тайла 0/0. Вікі OpenStreetMap попереджає про цю розбіжність окремим рядком.

Переведення між ними — віддзеркалення номера рядка:

```text
y_TMS = 2ᶻ − 1 − y_XYZ
```

:::tabs
```ts
/** XYZ (початок угорі) <-> TMS (початок унизу). Саме собі обернене. */
export const flipY = (y: number, z: number): number => 2 ** z - 1 - y;
```
```cpp
// XYZ (початок угорі) <-> TMS (початок унизу). Саме собі обернене.
std::int64_t flip_y(std::int64_t y, int z) { return (std::int64_t{1} << z) - 1 - y; }

}   // namespace tiles
```
:::

Перетворення збігається зі своєю оберненою, тож окремої функції «назад» не треба. А підступність його в тому, **де** воно себе не виявляє: на нульовому рівні тайл один, `2⁰ − 1 − 0 = 0`, і обидві схеми дають ту саму адресу. Отже, карта на найгрубішому зумі виглядає правильно, і помилка спливає лише на першому наближенні — коли півкулі раптом міняються місцями. Яка схема в конкретного сервісу, видно з шаблона адреси; розбір самих шаблонів — в [адресних схемах тайлових сервісів](book:programming/tile-url-schemes).

## Скільки це коштує

Обчислювальна вартість тут ніде не є вузьким місцем, і це варто проговорити, бо оптимізують зазвичай не те:

```text
обернене перетворення      O(1)          пара викликів atan/sinh
список тайлів під екран    O(W·H / 256²) стільки, скільки тайлів на екрані
обхід гілки дерева         O(4ᵈ)         сама відповідь такого розміру
масштабна лінійка          O(1)          один log10 і одне ділення
```

Єдина функція з небезпечним зростанням — обхід дерева, і в неї воно закладене в саму задачу: результат справді містить `4ᵈ` тайлів. Решта лінійна щодо того, що й так доведеться намалювати. Тобто на кадр припадають десятки викликів тригонометрії — ніщо на тлі однієї мережевої затримки.

Звідси й практичний висновок про те, що насправді треба стерегти. Не швидкість арифметики, а **кількість адрес**, які ця арифметика породжує: помилка в рівні, розвернутий через шов діапазон або зайвий рівень предзавантаження коштують не мікросекунд, а сотень мегабайтів і десятків хвилин. Тому в усіх чотирьох функціях підрахунок відокремлено від виконання — щоб було де спинитися.
