# ⚙️ Числа Пеано в коді: тип, зроблений з двох конструкторів

Є твердження, яке звучить майже надто гарно: набір аксіом і тип даних — це одне й те саме, просто сказане двома мовами. Легко кивнути й піти далі. Але кивати не варто, поки не побачив на власні очі, — тож зберімо натуральні числа з нічого прямо в коді, маючи в руках рівно дві цеглинки: «нуль» і «наступний». Не намалюймо схему, а напишімо **робочий** тип, навчімо його додавати й множити, переводити в машинне число й назад, — і подивімось, у якій саме точці ця бездоганна на папері конструкція врізається в залізо й перестає бути практичною. Та точка сама по собі виявиться уроком.

## Задача: число, у якого немає нічого, крім будови

Умова навмисно сувора. Потрібен тип `Nat`, що вміє зобразити будь-яке натуральне число, підтримує додавання й множення і переводиться туди-сюди з машинним цілим, — але збудований **виключно** з двох конструкторів: «нуль» і «наступник». Жодних вбудованих чисел процесора, жодних `int` усередині. Якщо десь прослизне машинне число — ми змахлювали, бо саме його існування й треба пояснити з нуля.

Навіщо така аскеза? Бо вона робить абстрактне твердження перевірним. «Аксіоми — це тип даних» — гарна фраза, поки не спитаєш, що конкретно чому відповідає і де межа. Коли ж число зібране руками з двох конструкторів, кожна аксіома Пеано отримує адресу в коді, кожне арифметичне правило стає рядком функції, а місце, де математична чистота ламається об пам'ять і стек, — стає видимим і вимірним. Ми не ілюструємо теорію; ми беремо її на дотик.

## Ідея: «або-або» — це і є перші дві аксіоми

Уся конструкція тримається на одному прийомі з теорії типів — **тип-сумі** (англ. *sum type*, він же алгебричний тип даних або розмічене об'єднання). Тип-сума каже: значення буває одного з кількох різновидів, і кожне значення точно знає, якого воно різновиду. Для натурального числа різновидів рівно два:

```
Nat = Zero               — або нуль,
    | Succ Nat           — або наступник іншого Nat.
```

Прочитайте цей рядок як означення й порівняйте з аксіомами. «Значення `Nat` буває нулем» — це аксіома «0 є натуральне число». «Значення `Nat` буває наступником іншого `Nat`» — це аксіома «у кожного числа є наступник, і він теж число». Дві цеглинки означення — дві перші аксіоми, слово в слово.

Найкраще те, що дві **інші** аксіоми додаються самі, без жодного рядка. Конструктори `Zero` і `Succ` — різні, і жодне значення не може бути водночас обома: значення, зроблене через `Zero`, ніколи не дорівнює значенню, зробленому через `Succ`. Це буквально «нуль не є наступником жодного числа». А `Succ x` дорівнює `Succ y` тоді й лише тоді, коли `x` дорівнює `y`, — бо порівняння тип-суми зіставляє вміст. Це буквально «якщо наступники рівні, то рівні й самі числа». Чотири аксіоми з п'яти вже вшиті в тип, і жодну з них ми не програмували — вони випали з самого «або-або». П'ята, індукція, теж тут, тільки проявиться пізніше, коли ми почнемо цей тип обходити.

## Робочий код: той самий тип трьома мовами

Ось `Nat` разом із чотирма операціями — `toInt`, `fromInt`, `add`, `mul` — у трьох мовах, які по-різному розповідають одну історію. Haskell показує ідею в найчистішому вигляді. Rust змушує проговорити те, що інші ховають: рекурсивний тип не влазить сам у себе без непрямості. TypeScript робить ту саму суму типів у мові, де немає ні того, ні того, — самими лише розміченими об'єктами.

:::tabs
```haskell
data Nat = Z | S Nat            -- число — це нуль або наступник числа

toInt :: Nat -> Integer
toInt Z     = 0                 -- база: нуль → 0
toInt (S n) = 1 + toInt n       -- крок: зняли один S, додали 1

fromInt :: Integer -> Nat
fromInt 0 = Z
fromInt n = S (fromInt (n - 1)) -- n > 0: накрутити S стільки ж разів

add :: Nat -> Nat -> Nat
add a Z     = a                 -- a + 0 = a
add a (S b) = S (add a b)       -- a + S(b) = S(a + b)

mul :: Nat -> Nat -> Nat
mul _ Z     = Z                 -- a · 0 = 0
mul a (S b) = add (mul a b) a   -- a · S(b) = a·b + a
```
```rust
#[derive(Clone)]
enum Nat {
    Zero,
    Succ(Box<Nat>),             // Box: без непрямості тип мав би нескінченний розмір
}
use Nat::{Zero, Succ};

fn to_int(n: &Nat) -> u64 {
    match n {
        Zero => 0,
        Succ(pred) => 1 + to_int(pred),
    }
}

fn from_int(n: u64) -> Nat {
    match n {
        0 => Zero,
        _ => Succ(Box::new(from_int(n - 1))),
    }
}

fn add(a: &Nat, b: &Nat) -> Nat {
    match b {
        Zero => a.clone(),                       // a + 0 = a
        Succ(pred) => Succ(Box::new(add(a, pred))),
    }
}

fn mul(a: &Nat, b: &Nat) -> Nat {
    match b {
        Zero => Zero,                            // a · 0 = 0
        Succ(pred) => add(&mul(a, pred), a),     // a·S(b) = a·b + a
    }
}
```
```typescript
type Nat =
  | { tag: "zero" }
  | { tag: "succ"; pred: Nat };          // розмічене об'єднання за полем tag

const zero: Nat = { tag: "zero" };
const succ = (n: Nat): Nat => ({ tag: "succ", pred: n });

function toInt(n: Nat): number {
  return n.tag === "zero" ? 0 : 1 + toInt(n.pred);
}

function fromInt(n: number): Nat {
  return n === 0 ? zero : succ(fromInt(n - 1));
}

function add(a: Nat, b: Nat): Nat {
  return b.tag === "zero" ? a : succ(add(a, b.pred));   // a + S(b) = S(a + b)
}

function mul(a: Nat, b: Nat): Nat {
  return b.tag === "zero" ? zero : add(mul(a, b.pred), a);
}
```
:::

Придивімося, як кожна мова несе той самий кістяк і чим виказує свою природу.

`add` і `mul` — це не «реалізація арифметики», а буквально ті два рядки означення додавання й множення, які виводяться з аксіом. `a + 0 = a` і `a + S(b) = S(a + b)` перетворюються на дві гілки функції `add` без жодної зміни; так само `a · 0 = 0` і `a · S(b) = a·b + a` дають дві гілки `mul`. Ми нічого не «придумали» — ми переписали означення синтаксисом мови. Тому в усіх трьох вкладках `add` і `mul` виглядають майже однаково: спільне в них — математика, а не мова.

Haskell договорює ідею до кінця й замовкає. `data Nat = Z | S Nat` — це майже дослівно аксіоми; зіставлення зі зразком (`add a Z`, `add a (S b)`) розбирає значення точно по конструкторах, якими його зібрали. Ніякого шуму.

Rust не дає збрехати про пам'ять. Спробуйте написати `enum Nat { Zero, Succ(Nat) }` — і компілятор відмовить: тип, що містить сам себе, мав би нескінченний розмір, бо `Succ` мусив би вмістити цілий `Nat`, той — ще один, і так без дна. Тому всередину йде `Box` — покажчик на купу. Це не примха Rust, а правда, яку Haskell і TypeScript просто ховають: їхні значення й так завжди за покажчиком, тож ланцюг `Succ` насправді і там, і там — це низка комірок у пам'яті, з'єднаних посиланнями. Rust лише змушує це вимовити вголос. Через ту саму непрямість `add` бере й повертає значення за посиланням, а на базі `a + 0` доводиться зробити `a.clone()` — глибоку копію всього ланцюга; тримайте це в думці, воно нам ще знадобиться.

TypeScript робить суму типів там, де мова про неї начебто не знає. Поле `tag` зі значеннями `"zero"` чи `"succ"` — це розмітка різновиду; перевірка `n.tag === "zero"` не просто читає поле, а звужує тип: у гілці «інакше» компілятор уже знає, що `n` — це `succ`, тож `n.pred` дозволено. Виходить та сама двоконструкторна будова, зібрана з простих об'єктів.

## Обхід типу — це індукція, яку перевіряє компілятор

Тепер прокинеться п'ята аксіома. Погляньте, як влаштована кожна функція: вона розбирає число на два випадки — `Zero` і `Succ(...)`, — у першому дає готову відповідь, а в другому знімає рівно один `Succ` і кличе себе на тому, що лишилось. Це **структурна рекурсія**: спуск строго по будові значення, з базою на конструкторі без вкладення. І це та сама фігура, що й індукція, просто прочитана з іншого боку.

> 🔧 **Навіщо це.** Структурна рекурсія тут не просто «зупиняється» — вона зупиняється **гарантовано**, і гарантію дає аксіома. Кожен рекурсивний виклик іде на менший `Nat` — на попередника поточного числа. Ланцюг попередників не може спускатися вічно, бо `Zero` ні за ким не стоїть (аксіома 3), тож будь-який спуск за скінченне число кроків уперся в базу. Це і є [математична індукція](book:math/mathematical-induction), обернена в бік коду: індукція каже, що кожне число досяжне від нуля за скінченну кількість кроків наступника, — отже, знімаючи наступники, ми за скінченну кількість кроків неминуче дійдемо до нуля. *(Індукція: властивість, що є в базі й переходить з кожного кроку на наступний, накриває всі елементи; тут вона гарантує, що рекурсія по `Nat` завжди завершується.)*

Ба більше, компілятор мовчки перевіряє за вас, що «доведення» повне. Індуктивне міркування має рівно два обов'язки — база й крок; функція на `Nat` має рівно дві гілки — `Zero` і `Succ`. Зіставлення зі зразком, у якому ви забули випадок `Zero`, — це індукція без бази; добрий компілятор попередить про невичерпний розбір, як логік про діру в доведенні. Ця глибока відповідність «програма — це доведення, а її тип — це твердження» має ім'я: **співвідношення Каррі–Говарда** (Гаскелл Каррі помітив кістяк 1934 року, Вільям Говард виписав його 1969-го, опубліковано 1980-го) — усталений місток між логікою й програмуванням. Тип `Nat` показує його в мініатюрі: обхід структури й доведення індукцією — не «схожі», а буквально те саме, записане в двох нотаціях.

Прокрутімо `mul` руками, щоб побачити, як з двох рядків народжується відповідь. Нехай 2 — це `S(S(Z))`.

**Умова: обчислити 2 · 2 самими лише рядками означення множення й додавання.**
```
розкручуємо  a · S(b) = add (a · b) a  згори вниз:
2 · 2 = 2 · S(1) = add (2 · 1) 2
2 · 1 = 2 · S(0) = add (2 · 0) 2
2 · 0 = 0                                 [база множення]

збираємо знизу вгору:
2 · 0 = 0
2 · 1 = add 0 2 = 2                        [0 + 2 = 2]
2 · 2 = add 2 2 = 4                        [2 + 2 = 4]
```
Ми ніде не «знали», що двічі два — чотири. Ми це **обчислили**, крутячи означення, поки другий множник не спав до нуля, — а тоді зібрали відповідь назад. Точно так само, як індукція будує висновок від бази вгору.

## Складність і пастки: чому це прекрасно, але непрактично

Тепер найважливіше — межа. Цей тип бездоганний як математичний об'єкт і як матеріал для доведень у системах на кшталт Coq чи Agda. А як число для реальних обчислень він майже непридатний, і варто точно розуміти, чому.

**Унарність: O(n) пам'яті на число n.** Число 5 — це п'ять комірок `Succ`, нанизаних одна на одну, і остання показує на `Zero`. Число мільйон — це мільйон комірок у купі. Запис, де величина дорівнює **кількості** знаків, звуть унарним, і він найрозточливіший з можливих. Порівняйте з позиційним: у двійковому те саме число займає лише ⌈log₂n⌉ бітів, бо кожен наступний розряд подвоює місткість. Розрив не лінійний, а **експоненційний**.

![Унарний запис числа як ланцюг комірок Succ проти того самого числа кількома бітами; збоку — розрив у пам'яті між O(n) і O(log n)](/book/math/logic-foundations/natural-numbers/img/unary-cost.svg)
*Те саме число двома записами. Унарно (тип Пеано) число n — це n комірок Succ у купі, з'єднаних посиланнями: O(n) пам'яті. Двійково те саме n — це ⌈log₂n⌉ бітів: O(log n). Щоб зберегти мільйон, унарному запису треба мільйон комірок, а двійковому — двадцять бітів. Розрив експоненційний, і саме він робить числа Пеано непрактичними в залізі.*

Цей унарний ланцюг — не курйоз, а стара й поважна ідея: рівно так натуральні числа кодував Алонзо Чорч у λ-численні наприкінці 1933 року (**числа Чорча**), де n — це «застосувати дію n разів». «Наступник, застосований n разів до нуля» і «функція, застосована n разів до аргументу» — той самий унарний рахунок. Красиво для теорії обчислюваності; згубно для лічби великих величин. Порівняння записів «унарний проти позиційного» — окрема тема: [позиційні системи](book:math/positional-systems) (звична причина, чому «123» — це сто двадцять три: кожен розряд важить у стільки разів більше, скільки основа системи; саме звідси береться логарифмічна, а не лінійна довжина запису).

**Час теж унарний.** `add a b` робить стільки кроків, яка довжина `b`, тобто O(b); `mul` — добуток довжин, O(a·b). Двійковий суматор у процесорі складає ті самі числа за O(log n) — за кількість розрядів, а не за саму величину. Тобто тип Пеано програє не лише в пам'яті, а й у кожній операції, і теж експоненційно. Що таке O-нотація й чому «за величину» і «за кількість розрядів» — це прірва, а не дрібниця: [асимптотична складність](book:algorithms/asymptotic-complexity) (спосіб порівнювати зростання вартості з розміром входу, відкидаючи сталі; тут вирішальне те, що величина n і довжина її запису log n — різні осі).

**Глибина стека.** Структурна рекурсія спускається на глибину, що дорівнює числу: `toInt` на числі 100 000 вкладає сто тисяч викликів. Це прямий шлях у [переповнення стека](book:programming/stack-overflow) (стек викликів має скінченний розмір; надто глибока рекурсія його вичерпує, і програма падає) — уже на числах, які машинний `int` тримає, навіть не змигнувши. Лінива природа Haskell не рятує: `toInt (S n) = 1 + toInt n` не є хвостовим викликом, тож замість глибокого стека він накопичує довгий ланцюг відкладених додавань — та сама O(n), тільки в іншій купі. Частину бід знімає хвостова рекурсія з накопичувачем, але коренева біда — унарність — залишається.

**Немає від'ємних.** Тип `Nat` за будовою не вміє зобразити −1: у нього немає конструктора для «менше нуля», і це не хиба, а точний портрет ℕ, де від'ємних теж немає. Розплата практична. `fromInt (-1)` у коді вище не поверне помилку — він зациклиться, бо ніколи не вцілить у базу `0`, вічно віднімаючи одиницю. А віднімання доводиться робити «зрізаним» (монус): нижче нуля не спускаємось, а впираємось у нуль.

```haskell
-- зрізане віднімання (монус): результат не буває від'ємним
sub :: Nat -> Nat -> Nat
sub a     Z     = a            -- a − 0 = a
sub Z     _     = Z            -- 0 − будь-що = 0, а не від'ємне
sub (S a) (S b) = sub a b      -- знімаємо по одному з обох боків
```

Тут `2 − 5` дасть не −3, а `0`: обидва наступники знімаються синхронно, доки не вичерпається зменшуване, — і воно вичерпується першим. Щоб дістати справжні від'ємні, тип треба **добудувати** до цілих чисел — зазвичай як пару натуральних або як окрему суму «знак плюс величина». Але це вже інша конструкція; чисті числа Пеано за означенням живуть від нуля й тільки вгору.

## Висновок: одна річ, дві мови

Зберімо все докупи. Два конструктори `Zero` і `Succ` — це перші дві аксіоми Пеано; їхня різність — третя й четверта; обхід типу структурною рекурсією — п'ята, індукція; а вичерпний розбір випадків, якого вимагає компілятор, — це перевірка, що ваше індуктивне «доведення» має і базу, і крок. Аксіоми не «схожі» на тип даних і не «моделюються» ним — вони **є** ним; математик і програміст записали ту саму думку двома нотаціями, і на межі ці нотації змикаються в одну.

І та сама вправа показує, чому природне для доведень майже нікуди не годиться для лічби. Унарний запис, у якому число дорівнює довжині ланцюга, робить кожен байт і кожен крок пропорційними самій величині — там, де позиційний запис обходиться логарифмом від неї. Тому натуральне число має ніби два тіла: індуктивне, унарне — ідеальне, щоб про нього **міркувати** й доводити теореми, і позиційне, двійкове — ідеальне, щоб на ньому **рахувати** в залізі. Це те саме число в різному вбранні. Числа Пеано в коді — не спосіб рахувати; це спосіб побачити на дотик, що аксіома й тип даних — одне й те саме, і що за найпростішим `1, 2, 3` ховається вибір форми, який вирішує все.
