# ⚙️ Чому пошук нічого не доводить: тісні промахи й самозванці

Комп'ютер — блискучий мисливець на контрприклади й безпорадний свідок їхньої відсутності, і теорема Ферма показує цю різницю як під мікроскопом. Тут ми напишемо перебірник, що чесно прочісує рівняння `aⁿ + bⁿ = cⁿ`, подивимося, як він раз по раз повертає «нічого немає», — і зрозуміємо, чому цей вирок, хоч як далеко його гнати, доказом не робиться. А заразом зустрінемо промахи, скроєні так, щоб такий перебір обвести круг пальця.

## Порахувати чесно можна тільки цілими

Уся робота перебірника зводиться до одного порівняння: чи дорівнює `aⁿ + bⁿ` якомусь точному `cⁿ`? Виглядає як дрібниця. Пастка — у тому, ЯК порівнювати. Візьми числа з рухомою комою — і машина збреше саме там, де найцікавіше.

На малих числах брехати нема як. Найтісніший промах серед невеликих кубів видно голим оком:

```
6³ + 8³ = 728
9³      = 729
```

Одиниці бракує — і жоден калькулятор тут не помиляється, числа куці. Але підніми показник і добери числа з розумом — і щілина стане невидимою для рухомої коми. Саме таку пастку двічі підкидали глядачам сценаристи «Сімпсонів»: у кадрі майнало готове «спростування» теореми Ферма — для тих, хто кинеться перевіряти його на калькуляторі.

```
(«Treehouse of Horror VI», 1995)             1782¹² + 1841¹² =? 1922¹²
(«The Wizard of Evergreen Terrace», 1998)    3987¹² + 4365¹² =? 4472¹²
```

Забий друге в десятизначний калькулятор — обидві сторони покажуть `6.397665635·10⁴³`, тобто однакове. Витягни корінь дванадцятого степеня з лівої частини — `4472.000000`. Комар носа не підточить. І все ж рівність хибна: у точних цілих ліва частина більша за праву на

```
3987¹² + 4365¹² − 4472¹² = 1211886809373872630985912112862690
```

— 34-значний промах, схований під 44-значним числом.

Чому око (і калькулятор) обдурені? Річ у [скінченній точності рухомої коми](topic:programming/floating-point). Число `4472¹²` має 44 десяткові цифри, а `double` тримає лише близько шістнадцяти значущих, екран же калькулятора — ще менше, десяток. Обидві сторони збігаються у відносній точності `1.9·10⁻¹¹` — тобто в перших десятьох-одинадцятьох цифрах, — і розходяться аж далі, куди екран не сягає. Гірше: корінь дванадцятого степеня ділить відносну похибку на дванадцять, тож `¹²√(лівої частини)` відрізняється від `4472` лише на `1.6·10⁻¹²` — на порядки менше, ніж здатен показати десяток цифр. Звідси `4472.000000` на екрані — брехня, сказана з цілковитою певністю.

![Дві «сімпсонівські» рівності, у кожній ліву й праву частини виписано повністю в цифрах: перші дев'ять-десять цифр обох частин однакові й підсвічені зеленим, далі числа розходяться (перша розбіжна цифра червона, решта сіра), і саме цей зелений початок — усе, що показує десятизначний екран](img/near-miss.svg)
*Чому калькулятор бреше: обидві частини кожної фальшивки збігаються в перших дев'ятьох-десятьох цифрах (зелене) і розходяться лише далі (червоне й сіре), куди десятизначний екран не сягає.*

Другий самозванець б'є в інший бік: `1782¹² + 1841¹²` не перевищує, а НЕ ДОТЯГУЄ до `1922¹²` — на одну частку з `10¹⁰`, збігаючись у перших дев'ятьох цифрах. Той самий трюк, дзеркально.

Висновок для коду категоричний: порівнюй точні цілі — інакше ти перевіряєш не рівняння Ферма, а ширину власної мантиси.

## Перебірник

Тепер сам пошук. Для фіксованого показника `n` і межі `N` пробіжімо всі пари `a ≤ b < N`, складімо `s = aⁿ + bⁿ` і спитаймо: чи `s` — точний `n`-й степінь? Єдиний чесний спосіб — цілий корінь `n`-го степеня: найбільше ціле `c`, для якого `cⁿ ≤ s`, знайдене бінарним пошуком, а не через `round(s**(1/n))`, чия рухома кома збреше рівно на промахах. Якщо `cⁿ = s` — маємо розв'язок; ні — занотуймо, наскільки близько підійшли.

:::tabs
```python
def iroot(s, n):
    """Ціла частина кореня n-го степеня з s — точно, лише на цілих."""
    if s < 2:
        return s
    hi = 1 << (-(-s.bit_length() // n))   # 2^⌈біти/n⌉ — завідомо не менше кореня
    lo = hi >> 1
    while lo < hi:                        # бінарний пошук найбільшого r: rⁿ ≤ s
        mid = (lo + hi + 1) >> 1
        if mid ** n <= s:
            lo = mid
        else:
            hi = mid - 1
    return lo

def search(n, N):
    """Прочесати 1 ≤ a ≤ b < N: розв'язок або найтісніший промах."""
    best = None                           # (відносний промах, a, b, cc, delta)
    for a in range(1, N):
        an = a ** n
        for b in range(a, N):
            s = an + b ** n
            c = iroot(s, n)               # cⁿ ≤ s < (c+1)ⁿ
            if c ** n == s:
                return f"РОЗВ'ЯЗОК: {a}^{n} + {b}^{n} = {c}^{n}"
            lo, hi = s - c ** n, (c + 1) ** n - s
            cc = c if lo < hi else c + 1   # найближчий n-й степінь
            delta = cc ** n - s            # >0: сума нижча за ccⁿ
            rel = abs(delta) / s
            if best is None or rel < best[0]:
                best = (rel, a, b, cc, delta)
    rel, a, b, cc, delta = best
    sign = "−" if delta > 0 else "+"
    return (f"немає розв'язку при a, b < {N};  найтісніше:  "
            f"{a}^{n} + {b}^{n} = {cc}^{n} {sign} {abs(delta)}")

print(search(3, 1000))
# немає розв'язку при a, b < 1000;  найтісніше:  791^3 + 812^3 = 1010^3 − 1
```
```cpp
#include <cstdio>
#include <cstdint>
using u128 = unsigned __int128;

u128 ipow(uint64_t x, int n) { u128 p = 1; while (n--) p *= x; return p; }

uint64_t iroot(u128 s, int n) {               // ⌊ⁿ√s⌋ — бінарний пошук, лише цілими
    uint64_t lo = 1, hi = 2'000'000'000ull;   // верхня межа з запасом для діапазону
    while (lo < hi) {
        uint64_t mid = lo + (hi - lo + 1) / 2;
        if (ipow(mid, n) <= s) lo = mid; else hi = mid - 1;
    }
    return lo;
}

int main() {
    const int n = 3, N = 1000;
    long double bestRel = 2.0L;
    uint64_t bA = 0, bB = 0, bC = 0; long long bDelta = 0;
    for (uint64_t a = 1; a < (uint64_t)N; ++a)
        for (uint64_t b = a; b < (uint64_t)N; ++b) {
            u128 s = ipow(a, n) + ipow(b, n);
            uint64_t c = iroot(s, n);                    // cⁿ ≤ s < (c+1)ⁿ
            u128 below = ipow(c, n), above = ipow(c + 1, n);
            if (below == s) { printf("РОЗВ'ЯЗОК\n"); return 0; }
            uint64_t cc = (s - below < above - s) ? c : c + 1;
            long long delta = (long long)((__int128)ipow(cc, n) - (__int128)s);
            long double rel = (delta < 0 ? -delta : delta) / (long double)s;
            if (rel < bestRel) { bestRel = rel; bA = a; bB = b; bC = cc; bDelta = delta; }
        }
    printf("немає розв'язку при a, b < %d;  найтісніше:  "
           "%llu^%d + %llu^%d = %llu^%d %c %lld\n", N,
           (unsigned long long)bA, n, (unsigned long long)bB, n,
           (unsigned long long)bC, n, bDelta > 0 ? '-' : '+',
           bDelta > 0 ? bDelta : -bDelta);
    // немає розв'язку при a, b < 1000;  найтісніше:  791^3 + 812^3 = 1010^3 - 1
    return 0;
}
```
:::

Перебір при `a, b < 1000` не знаходить жодного розв'язку — зате знаходить промахи, і найтісніший із них теж схибив рівно на одиницю: `791³ + 812³ = 1010³ − 1`. Ось де серце справи: щілина буває `1`, `2`, скільки завгодно мала — але ніколи не нуль. Промахів «на одиницю» безліч; влучань «на нуль» — жодного.

## Дешеве сито: самозванця можна викрити, не тримаючи його в руках

Щоб зловити підробку, велетенські числа рахувати взагалі не обов'язково. Якби рівність `aⁿ + bⁿ = cⁿ` була справжня, вона трималася б за будь-яким модулем. Отже, досить узяти кілька малих `m`, порахувати остачі (це копійки) — і один-єдиний незбіг остач стає довічним свідоцтвом брехні. Мова [модульної арифметики](topic:math/modular-arithmetic) тут і швидка, і безпечна: остачі малі, переповнення нема.

:::tabs
```python
def refuted_by(a, b, c, n, mods=(2, 9, 7, 13)):
    """Дешево спростувати aⁿ+bⁿ=cⁿ: знайти модуль, за яким рівність не тримається.
    Повертає такий модуль або 0, якщо жоден із проби підробки не викрив."""
    for m in mods:
        if (pow(a, n, m) + pow(b, n, m) - pow(c, n, m)) % m != 0:
            return m
    return 0

print(refuted_by(1782, 1841, 1922, 12))   # 2 — гине вже на парності
print(refuted_by(3987, 4365, 4472, 12))   # 9 — переживає парність, гине за модулем 9
```
```cpp
#include <cstdio>
#include <cstdint>

uint64_t modpow(uint64_t x, uint64_t n, uint64_t m) {   // xⁿ mod m — швидке піднесення
    uint64_t r = 1 % m; x %= m;
    while (n) { if (n & 1) r = r * x % m; x = x * x % m; n >>= 1; }
    return r;
}

// Модуль, за яким aⁿ+bⁿ=cⁿ не тримається (0 — жоден із проби не викрив).
uint64_t refuted_by(uint64_t a, uint64_t b, uint64_t c, uint64_t n) {
    for (uint64_t m : {2ull, 9ull, 7ull, 13ull})
        if ((modpow(a, n, m) + modpow(b, n, m) + m - modpow(c, n, m)) % m) return m;
    return 0;
}

int main() {
    printf("%llu\n", (unsigned long long)refuted_by(1782, 1841, 1922, 12)); // 2
    printf("%llu\n", (unsigned long long)refuted_by(3987, 4365, 4472, 12)); // 9
}
```
:::

Перший самозванець гине миттєво на парності: `1782` парне, `1841` непарне, їхня сума в дванадцятому степені непарна, а `1922¹²` парне — парне не дорівнює непарному, і ніякі 40 цифр рахувати не треба. Другий хитріший: він переживає і парність, і останню цифру, — та ламається за модулем `9`, бо `3987` і `4365` обидва діляться на `9`, тож ліва частина кратна дев'яти, а `4472¹² ≡ 1`. Найголовніше: `modpow` не виходить за 64 біти й ніде не тримає 44-значного числа — а проте певно засвідчує, що `4472¹²` не є тією сумою. Щоб упіймати брехню, самого велетня будувати не конче.

> 🔧 **Навіщо це.** Сито за остачами — не фокус лише проти жартів «Сімпсонів», а робочий кінь усякого справжнього пошуку. Точна перевірка `aⁿ + bⁿ = cⁿ` коштує множення велетенських чисел; перевірка за `2·9·7·13·…` — це жменька дій над крихітними остачами, що відкидає майже кожного кандидата. Дорогу цілочислову арифметику ти платиш лише за того одного вцілілого з мільярда. Пошук, що знехтував би цим ситом і довірився рухомій комі, і проґавив би справжнє влучання, і потонув би в самозванцях.

## Складність і пастки

- Прохід — `Θ(N²)` пар; кожна перевірка — цілий корінь, а це `O(log N)` піднесень велетенських чисел. Подвоїш межу — вчетверо більше роботи, а накрита ділянка так і лишиться скінченним квадратом у нескінченній площині.
- Дійсний (float) корінь бреше саме там, де важить. `round(s**(1/12))` для першого самозванця дає `1922`, тимчасом як чесний цілий корінь — `1921` з ненульовою остачею. Завжди звіряй `cⁿ == s` у точних цілих, ніколи — через кому.
- Числа фіксованої ширини переповнюються блискавично: `__int128` упирається в стелю близько `3.4·10³⁸` (39 цифр), тож тримає пошук для `n = 3`, але не `4472¹²` (44 цифри). Тоді — рідні великі цілі (Python) чи бібліотека довгих чисел; а ще краще — обійти велике число зовсім тим самим ситом остач, що не виходить за 64 біти.
- Жодна межа не буває «достатньою». Чесне значення, яке повертає пошук, — завжди «нема при `a, b < N`», ніколи «нема ніде».

## Чому скінченний пошук — не доказ

Наш перебір закрив `a, b < 1000` для куба; пусти його ширше, для більших показників — закриє більше. Неможливість справді перевіряли обчислювально до астрономічних меж: усі показники до багатьох мільйонів, числа далеко за все написане вище. Щоразу відповідь та сама: нічого. І це нічого не доводить.

Причина — у самій формі твердження. «Для кожного `n > 2` розв'язку немає» — це універсальна заява над нескінченною областю. Таку заяву валить один-єдиний контрприклад і не стверджує жодна скінченна купа підтверджень: скільки б кандидатів не відкинути, попереду завжди лишається нескінченний хвіст неперевіреного, і самотня трійка могла б сидіти будь-де в ньому. Пошук — машина спростування: він здатен крикнути «ось воно!» тієї ж миті, щойно натрапить на влучання, але його мовчання означає лише «не в тій коробці, яку я відкрив».

Ця асиметрія — не занудство. Наступний розділ — її живий доказ.

## Сусідка, що впала: здогадка Ойлера

Ще у XVIII столітті Ойлер узагальнив мораль рівняння Ферма. Ферма каже: двох `n`-х степенів на `n`-й степінь ніколи не стане. Ойлер припустив, що правило тягнеться далі — щоб скласти `n`-й степінь, треба щонайменше `n` доданків-степенів, тож суми лише `(n−1)` з них ніколи не досить. Для `n = 3` це той самий випадок Ферма; для `n = 4` це забороняє трьом четвертим степеням дати четвертий; для `n = 5` — чотирьом п'ятим дати п'ятий. Звучало природно, і два століття кожне число, яке брали до рук, слухняно корилося.

`1966` — Леон Ландер і Томас Паркін прямим машинним перебором знайшли чотири п'ятих степені, що дають п'ятий:

```
27⁵ + 84⁵ + 110⁵ + 133⁵ = 144⁵ = 61 917 364 224
```

Їхнє оголошення ввійшло в історію як одна з найкоротших наукових публікацій — по суті кілька рядків. Двохсотрічний взірець, «перевірений» на всьому, що трапляється під руку, виявився просто хибним: він лише ховав свої контрприклади далі, ніж хтось зазирав.

Випадок четвертих степенів тримався довше й упав ефектніше. `1988` — Ноам Елкіс уже не сліпим перебором, а через арифметику еліптичних кривих здобув цілу нескінченну родину контрприкладів, найперший з яких

```
2682440⁴ + 15365639⁴ + 18796760⁴ = 20615673⁴
```

а вже знаючи, що розв'язки існують, Роджер Фрай прицільним пошуком дотиснув найменший:

```
95800⁴ + 217519⁴ + 414560⁴ = 422481⁴
```

Кожне з цих рівнянь — звичайнісінька, перевірна тотожність у цілих числах: усі три вище я звірив точним обчисленням, забий і сам.

Ось і вся осторога в одній сусідці. Здогадка може пережити двісті років «перевіряли й перевіряли» — і все одно бути хибною, бо «багато» — не «всі», а «майже» — не «дорівнює». Для рівняння Ферма це ріже в обидва боки: саме тому йому був потрібен доказ, а не пошук, — і саме тому, якби перебір бодай раз натрапив на одну-єдину `aⁿ + bⁿ = cⁿ`, три століття скінчилися б того ж пополудня. Машина здатна закрити цю історію, лише зламавши її; щоб знати, що рівняння тримається довіку, комусь довелося міркувати про всю нескінченну область заразом.
