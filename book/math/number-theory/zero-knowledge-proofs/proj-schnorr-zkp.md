# ⚙️ Реалізація протоколу Шнорра: від інтерактивного діалогу до NIZK

Практична реалізація доведення знання дискретного логарифма за допомогою протоколу Шнорра вимагає виконання модульного піднесення до степеня над великими цілими числами та використання стійких криптографічних хеш-функцій.

У даній праці продемонстровано повну робочу реалізацію неінтерактивного доказу з нульовим розголошенням (англ. *Non-Interactive Zero-Knowledge*, NIZK) на основі евристики Фіата — Шаміра. Алгоритм створює secret key `x`, обчислює відповідний public key `y = g^x mod p`, формує неінтерактивний доказ у вигляді пари `π = (r, s)` та здійснює незалежну перевірку на боці верифікатора без розкриття секрету `x`.

Для наочності математичної структури в прикладах використано зменшені 64-бітні параметри простого поля, що дозволяє легко простежити хід обчислень без підключення громіздких бібліотек довгої арифметики. У реальних криптографічних застосунках (наприклад, Bitcoin, Ethereum або Zcash) використовують 256-бітні еліптичні криві (secp256k1, ed25519) або 2048-бітні поля `ℤ_p^*`.

## Детальний розбір математичних функцій реалізації

Реалізація протоколу Шнорра спирається на три фундаментальні обчислювальні процедури:

1. **Модульне множення без переповнення (`mul_mod`)**: При множенні двох 64-бітних цілих чисел `a · b` результат може досягати 128 біт, що спричиняє переповнення стандартних регістрів цілих чисел `uint64_t`. Для запобігання переповненню застосовується алгоритм двоічного додавання зі зсувом (англ. *binary multiplication by shift-and-add*). Функція розкладає множник `b` на двійкові розряди і на кожному кроці виконує модульне додавання: `res = (res + a) % m`.
2. **Швидке модульне піднесення до степеня (`power_mod`)**: Для обчислення `g^k mod p` та `g^s mod p` використовується двоічний алгоритм піднесення до степеня справа наліво (англ. *right-to-left binary exponentiation*). Алгоритм зменшує обчислювальну складність від `O(k)` операцій до `O(log k)` модульних множень.
3. **Хешування Фіата — Шаміра (`fiat_shamir_hash`)**: У приклада C++ використано алгоритм FNV-1a для детермінованого перетворення трійки `(g, y, r)` на виклик `c ∈ [1, q-1]`. У навчальній версії це ілюструє контракт хешування. Проте у продакшн-коді обов'язково застосовують криптографічно стійкі хеш-функції, такі як SHA-256, SHA3-256 або BLAKE2b, щоб унеможливити знаходження прообразу чи колізій.

## Опис кроків програмного алгоритму

Процес побудови та перевірки неінтерактивного доказу у коді складається з послідовних етапів. Кожен етап гарантує математичну цілісність системи та відсутність витоку секретних змінних:

1. **Ініціалізація групи**: Створюються параметри `GroupParams`, де задається модуль `p`, порядок підгрупи `q` та твірний елемент `g`. Значення `p` та `q` обираються так, щоб `q` ділило `p - 1`.
2. **Генерація ключів**: Алгоритм обирає випадкове число `x ∈ [1, q-1]`, яке слугує приватним ключем доводжувача, та обчислює значення відкритого публічного ключа `y = g^x mod p`.
3. **Створення зобов'язання (Prover)**: Доводжувач обирає тимчасовий випадковий nonce `k ∈ [1, q-1]` і розраховує `r = g^k mod p`.
4. **Обчислення хеш-виклику**: Замість запиту до перевіряльника доводжувач обчислює детермінований хеш `c = H(g, y, r) mod q`. Це перетворює інтерактивний діалог на неінтерактивний аргумент знання.
5. **Формування відповіді**: Доводжувач обчислює підсумкову відповідь `s = (k + c · x) mod q`.
6. **Верифікація (Verifier)**: Верифікатор отримує публічний ключ `y` та доказ `(r, s)`. Він самостійно обчислює `c' = H(g, y, r)` і перевіряє тотожність `g^s ≡ r · y^{c'} (mod p)`.

## Простеження виконання на конкретних числах

Розглянемо числовий приклад з маленькими параметрами поля `p = 467`, `q = 233`, `g = 4`:

- Припустимо, доводжувач обрав секретний ключ `x = 100`.
- Публічний ключ обчислюється як `y = 4^{100} mod 467 = 229`.
- При генерації доказу доводжувач обирає випадковий nonce `k = 50`.
- Зобов'язання доводжувача дорівнює `r = 4^{50} mod 467 = 189`.
- Оракул Фіата — Шаміра обчислює хеш `c = H(4, 229, 189) mod 233 = 42`.
- Доводжувач формує відповідь `s = (50 + 42 · 100) mod 233 = (50 + 4200) mod 233 = 4250 mod 233 = 56`.
- Пакетований доказ передається перевіряльнику у вигляді `π = (r=189, s=56)`.
- Перевіряльник обчислює ліву частину: `left = 4^{56} mod 467 = 325`.
- Перевіряльник обчислює праву частину: `right = (189 · 229^{42}) mod 467 = 325`.
- Оскільки `left == right`, верифікація проходить успішно.

#include <iostream>
#include <vector>
#include <string>
#include <random>
#include <cstdint>
#include <stdexcept>

// Спрощена математична модель для 64-бітних цілих чисел
// У реальних системах використовуються 256-бітні поля (наприклад, secp256k1)
struct GroupParams {
    uint64_t p; // Великий модуль простого поля
    uint64_t q; // Порядок циклічної підгрупи (q ділить p - 1)
    uint64_t g; // Твірний елемент підгрупи
};

struct Proof {
    uint64_t r; // Зобов'язання (Commitment)
    uint64_t s; // Підтверджувальна відповідь (Response)
};

// Безпечне модульне множення для запобігання переповненню
uint64_t mul_mod(uint64_t a, uint64_t b, uint64_t m) {
    uint64_t res = 0;
    a %= m;
    while (b > 0) {
        if (b % 2 == 1) res = (res + a) % m;
        a = (a * 2) % m;
        b /= 2;
    }
    return res;
}

// Швидке модульне піднесення до степеня: (base^exp) % mod
uint64_t power_mod(uint64_t base, uint64_t exp, uint64_t mod) {
    uint64_t res = 1;
    base %= mod;
    while (exp > 0) {
        if (exp % 2 == 1) res = mul_mod(res, base, mod);
        base = mul_mod(base, base, mod);
        exp /= 2;
    }
    return res;
}

// Проста імітація криптографічного хешування для евристики Фіата — Шаміра: H(g, y, r) mod q
uint64_t fiat_shamir_hash(uint64_t g, uint64_t y, uint64_t r, uint64_t q) {
    uint64_t h = 14695981039346656037ULL; // FNV-1a basis
    auto mix = [&h](uint64_t val) {
        for (int i = 0; i < 8; ++i) {
            h ^= (val & 0xFF);
            h *= 1099511628211ULL;
            val >>= 8;
        }
    };
    mix(g);
    mix(y);
    mix(r);
    return (h % (q - 1)) + 1; // повертає значення у діапазоні [1, q - 1]
}

class SchnorrZKP {
public:
    explicit SchnorrZKP(GroupParams params) : params_(params), gen_(std::random_device{}()) {}

    // Генерація ключової пари
    std::pair<uint64_t, uint64_t> generate_keypair() {
        std::uniform_int_distribution<uint64_t> dist(1, params_.q - 1);
        uint64_t secret_x = dist(gen_);
        uint64_t public_y = power_mod(params_.g, secret_x, params_.p);
        return {secret_x, public_y};
    }

    // Створення неінтерактивного доказу (Prover)
    Proof prove(uint64_t secret_x, uint64_t public_y) {
        std::uniform_int_distribution<uint64_t> dist(1, params_.q - 1);
        uint64_t k = dist(gen_); // Тимчасовий випадковий nonce
        
        uint64_t r = power_mod(params_.g, k, params_.p); // r = g^k mod p
        uint64_t c = fiat_shamir_hash(params_.g, public_y, r, params_.q); // c = H(g, y, r)
        
        uint64_t cx = mul_mod(c, secret_x, params_.q);
        uint64_t s = (k + cx) % params_.q; // s = (k + c * x) mod q
        
        return Proof{r, s};
    }

    // Перевірка неінтерактивного доказу (Verifier)
    bool verify(uint64_t public_y, const Proof& proof) const {
        if (proof.r == 0 || proof.r >= params_.p || proof.s >= params_.q) {
            return false; // Захист від граничних значень
        }
        
        // Обчислення хеш-виклику на боці верифікатора: c = H(g, y, r)
        uint64_t c = fiat_shamir_hash(params_.g, public_y, proof.r, params_.q);
        
        // Ліва частина: g^s mod p
        uint64_t left = power_mod(params_.g, proof.s, params_.p);
        
        // Права частина: (r * y^c) mod p
        uint64_t y_c = power_mod(public_y, c, params_.p);
        uint64_t right = mul_mod(proof.r, y_c, params_.p);
        
        return left == right;
    }

private:
    GroupParams params_;
    mutable std::mt19937_64 gen_;
};

int main() {
    // Параметри групи ℤ_p^* з p = 467, q = 233, g = 4 (де q ділить p - 1)
    GroupParams params{467, 233, 4};
    SchnorrZKP zkp(params);

    // 1. Prover генерує ключі
    auto [secret_x, public_y] = zkp.generate_keypair();
    std::cout << "[+] Публічний ключ y = " << public_y << " (Секретний ключ x приховано)\n";

    // 2. Prover створює неінтерактивний доказ
    Proof proof = zkp.prove(secret_x, public_y);
    std::cout << "[+] Сформовано доказ: r = " << proof.r << ", s = " << proof.s << "\n";

    // 3. Verifier перевіряє доказ без знання x
    bool is_valid = zkp.verify(public_y, proof);
    std::cout << "[+] Результат верифікації доказу: " << (is_valid ? "УСПІШНО (ACCEPTED)" : "ВІДХИЛЕНО (REJECTED)") << "\n";

    // 4. Спроба фальсифікації зі зміненим s
    Proof fake_proof = proof;
    fake_proof.s = (fake_proof.s + 1) % params.q;
    bool fake_valid = zkp.verify(public_y, fake_proof);
    std::cout << "[+] Перевірка підробленого доказу: " << (fake_valid ? "УСПІШНО" : "ВІДХИЛЕНО (УСПІШНО ВИЯВЛЕНО ФАЛЬСИФІКАЦІЮ)") << "\n";

    return 0;
}

import hashlib
import secrets

class GroupParams:
    def __init__(self, p: int, q: int, g: int):
        self.p = p  # Модуль поля
        self.q = q  # Порядок підгрупи
        self.g = g  # Твірний елемент

class SchnorrNIZK:
    def __init__(self, params: GroupParams):
        self.params = params

    def generate_keypair(self) -> tuple[int, int]:
        """Генерація приватної та публічної пари ключів."""
        secret_x = secrets.randbelow(self.params.q - 1) + 1
        public_y = pow(self.params.g, secret_x, self.params.p)
        return secret_x, public_y

    def _fiat_shamir_hash(self, g: int, y: int, r: int) -> int:
        """Детерміноване хешування даних для отримання виклику c."""
        data = f"{g}:{y}:{r}".encode('utf-8')
        digest = hashlib.sha256(data).digest()
        c = int.from_bytes(digest, byteorder='big') % self.params.q
        return c if c != 0 else 1

    def prove(self, secret_x: int, public_y: int) -> tuple[int, int]:
        """Створення неінтерактивного доказу знання дискретного логарифма."""
        k = secrets.randbelow(self.params.q - 1) + 1
        r = pow(self.params.g, k, self.params.p)
        c = self._fiat_shamir_hash(self.params.g, public_y, r)
        s = (k + c * secret_x) % self.params.q
        return r, s

    def verify(self, public_y: int, proof: tuple[int, int]) -> bool:
        """Верифікація неінтерактивного доказу без розкриття secret_x."""
        r, s = proof
        if not (0 < r < self.params.p and 0 <= s < self.params.q):
            return False

        c = self._fiat_shamir_hash(self.params.g, public_y, r)
        
        # Перевірка тотожності g^s ≡ r * y^c (mod p)
        left = pow(self.params.g, s, self.params.p)
        right = (r * pow(public_y, c, self.params.p)) % self.params.p
        
        return left == right

if __name__ == "__main__":
    # Безпечні криптографічні параметри (p = 467, q = 233, g = 4)
    params = GroupParams(p=467, q=233, g=4)
    zkp = SchnorrNIZK(params)

    # 1. Prover генерує ключі
    secret_x, public_y = zkp.generate_keypair()
    print(f"[+] Публічний ключ y: {public_y}")

    # 2. Prover будує довідкову трійку
    r, s = zkp.prove(secret_x, public_y)
    print(f"[+] Згенеровано NIZK доказ: (r={r}, s={s})")

    # 3. Verifier перевіряє доказ
    is_valid = zkp.verify(public_y, (r, s))
    print(f"[+] Результат верифікації: {'ПРИЙНЯТО' if is_valid else 'ВІДХИЛЕНО'}")

## Ключові пастки реалізації та критичні вразливості

Під час перенесення даного алгоритму у продакшн-системи розробники найчастіше припускаються трьох критичних помилок:

1. **Повторне використання значення `k` (Nonce Reuse)**: Якщо розробник використає одне й те саме тимчасове `k` для двох різних доведень із викликами `c₁` та `c₂`, будь-який спостерігач зможе обчислити секретний ключ `x`. Для двох доказів маємо систему:
   ```
   s₁ = k + c₁ · x mod q
   s₂ = k + c₂ · x mod q
   ```
   Віднявши перше рівняння від другого, отримуємо `s₁ - s₂ = (c₁ - c₂) · x mod q`, звідки приватний ключ відновлюється абсолютно легко:
   ```
   x = (s₁ - s₂) · (c₁ - c₂)^{-1} mod q
   ```
   У реальних проєктах тимчасовий `k` мусить бути унікальним та криптографічно випадковим для кожного прогону, або генеруватися детерміновано за специфікацією RFC 6979.

2. **Атака слабкої трансформації Фіата — Шаміра (Weak Fiat-Shamir Attack)**: Якщо хеш-функція `H` при обчисленні виклику `c` приймає лише зобов'язання `r`, але не хешує публічний ключ `y` та генератор `g`, зловмисник може створити підроблений доказ для довільного чужого публічного ключа `y'`. Строго обов'язково включати усі публічні вхідні дані до контексту хешування: `c = H(g, y, r)`.

3. **Відсутність санітарних перевірок межі входу**: Якщо верифікатор приймає значення `r = 0` або `r ≥ p`, зловмисник може передати спеціально підготовлені граничні значення і обійти перевірку тотожності. Перевірка `0 < r < p` та `0 ≤ s < q` є криптографічно обов'язковою до початку виконання модульного піднесення до степеня.

4. **Вразливості до атак по бічних каналах (Side-Channel Vulnerabilities)**: Стандартне виконання модульного піднесення до степеня за допомогою умовних розгалужень `if (bit == 1)` дозволяє зловмиснику відновити секретний ключ `x` або nonce `k` шляхом заміру часу виконання процесорних інструкцій (англ. *timing attack*) або аналізу споживання електроенергії (DPA). Продакшн-реалізації повинні використовувати обчислення з постійним часом (англ. *constant-time execution*).

Розглянута програмна реалізація демонструє практичний зв'язок абстрактної числово-теоретичної моделі з безпечним програмуванням криптографічних протоколів у реальних системах.
