# ⚙️ НСД у коді

Сам цикл поліпшити не вдалося нікому: пара чисел, залишок, обмін — і так доки друге не стане нулем. Але між цим циклом і функцією, що справді стоїть у бібліотеці, лежать чотири питання, на які математика відповіді не дає. Не тому, що складні, — тому, що це не її питання.

Придивімося, як вони виникають. Рівність НСД(a, b) = НСД(b, a mod b) **рекурентна** — вона просить рекурсії, а машина бере за рекурсію плату стеком. Рівність каже «a mod b» — а ділення на машині коштує в рази дорожче за все інше. Рівність **бінарна**, два аргументи, — а дані приходять масивами. Рівність каже НСК = a·b / НСД — і на цьому добутку код переповнюється.

Щоразу та сама вилка: математика радить одне, машина — інше. Розберімо всі чотири.

### Рекурсія: форма, яку диктує сама формула

НСД(a, b) = НСД(b, a mod b) — це не опис послідовності дій, а рівність, що зводить задачу до себе ж, тільки меншої. Такі рівності лягають у код одним рухом — переписуванням:

:::tabs
```cpp
#include <cstdint>

std::int64_t gcd_rec(std::int64_t a, std::int64_t b) {
    return b == 0 ? a : gcd_rec(b, a % b);
}
```
```py
def gcd_rec(a: int, b: int) -> int:
    return a if b == 0 else gcd_rec(b, a % b)
```
```ts
function gcdRec(a: number, b: number): number {
  return b === 0 ? a : gcdRec(b, a % b);
}
```
:::

Вигадувати тут нема чого: код — це формула, записана синтаксисом мови. База рекурсії (b = 0) — це та сама умова зупинки, і вона в коді стоїть буквально там, де в математиці.

Ба більше, виклик стоїть **останньою дією** функції. Коли внутрішній `gcd_rec` поверне число, робити з ним уже нічого — воно і є відповідь. Такий виклик звуть **хвостовим** (tail call), і кадр стека йому теоретично не потрібен: замість «викликати й чекати на повернення» можна підмінити аргументи й стрибнути на початок функції. Тобто хвостова [рекурсія](book:algorithms/recursion) — це цикл, записаний іншими словами.

Теоретично. Чи станеться перетворення насправді — вирішує не математика, а реалізація мови.

**C++.** gcc і clang на `-O2` хвостовий виклик справді згортають у стрибок, і глибина стека лишається сталою. Але стандарт цього **не гарантує**: складання з `-O0` дасть чесну рекурсію з кадром на кожен крок. Оптимізація, на яку не можна покластися, — не гарантія, а везіння.

**Python.** Не згортає — і не згортатиме. Це не прогалина, а рішення: Ґвідо ван Россум розібрав його у квітні 2009 року двома дописами в блозі Neopythonic, назвавши усунення хвостової рекурсії «непайтонічним». Аргументи були не про швидкодію: згорнутий кадр зникає зі стека, а разом із ним — і рядок у трасуванні винятку; до того ж, щойно оптимізація з'явиться, люди почнуть писати код, що на неї спирається, і той код перестане працювати на інших реалізаціях Python. Глибина натомість обмежена явно: `sys.getrecursionlimit()` за замовчуванням — **1000**.

І ось тут ховається пастка, варта того, щоб її роздивитися. Скільки кроків робить алгоритм Евкліда на випадковій парі? Дж. Д. Діксон і Ганс Гайльбронн незалежно один від одного показали, що середня кількість ділень для пари чисел, обмежених n, асимптотично дорівнює (12·ln 2 / π²)·ln n (пізніше Дж. В. Портер уточнив доданок похибки — звідси стала Портера). Переведімо це в біти:

```
середньо кроків ≈ (12 · ln 2 / π²) · ln(2^b)
                = 0.8428 · b · ln 2
                = 0.5842 · b            де b — довжина числа в бітах

межа рекурсії Python = 1000  →  b ≈ 1000 / 0.5842 ≈ 1712 біт
```

Тобто десь на 1712 бітах середня глибина рекурсії впирається в стелю. Перевіримо на живих числах — по 300 випадкових пар на кожну довжину:

```
1024 біт:  середньо  599 кроків  →  валить рекурсію   0.0 % пар
1408 біт:  середньо  824 кроки   →  валить рекурсію   0.0 % пар
1536 біт:  середньо  896 кроків  →  валить рекурсію   0.0 % пар
1712 біт:  середньо  999 кроків  →  валить рекурсію  54.0 % пар   ← передбачений поріг
1792 біт:  середньо 1050 кроків  →  валить рекурсію  98.3 % пар
2048 біт:  середньо 1199 кроків  →  валить рекурсію 100.0 % пар
```

Теорія й вимір збіглися розряд у розряд: рівно там, де формула обіцяла перетин, половина пар справді падає. А тепер подивіться на крайні рядки. На 1024-бітних числах рекурсивна версія не падає **ніколи**. На 2048-бітних — падає **завжди**. Це не хиткий баг, що зрідка вистрілює: це урвище. Функція проходить усі тести, працює на ключах старого розміру, а на модулі RSA-2048 — а це сьогодні звичайний розмір у [криптографії з відкритим ключем](book:communications/public-key-crypto) — гарантовано кидає `RecursionError`. Ітеративна версія на тій самій парі відповідає миттєво.

> 🔧 **Навіщо це.** Підняти `sys.setrecursionlimit(5000)` — спокуса, і саме її треба обійти. Ліміт Python стереже не власну примху, а справжній стек C-рівня під інтерпретатором; піднявши число, ви міняєте зрозумілий `RecursionError` на [переповнення стека](book:programming/stack-overflow) — тобто на аварію процесу без трасування. Мова каже вам «тут глибоко» рівно тоді, коли варто взяти цикл.

**TypeScript.** Хвостові виклики (proper tail calls) є в специфікації ES6 від 2015 року — і досі це один із небагатьох пунктів стандарту, який великі рушії просто не реалізували. JavaScriptCore (Safari) зробив це 2016 року й відтоді має; V8 і SpiderMonkey — ні. Отже в Node й Chrome урвище те саме, що в Python, лише поріг інший.

Підсумок простий: рекурсивна форма — чесний переклад **формули**, цикл — чесний переклад **машини**. Формула гарна, але виконуватимуть таки машину.

### Двійковий НСД: коли ділення задороге

`a % b` — один символ у тексті програми й найдорожча ціла операція в процесорі. Додавання, віднімання, зсув, порівняння коштують такт-два; ділення — десятки тактів, бо його, на відміну від решти, толком не розкладеш на конвеєр. У циклі Евкліда ділення стоїть на кожному кроці.

Звідси думка, від якої й починається інший алгоритм: **а що, як обійтися лише тими операціями, які машина робить задарма?**

У двійковому запису дві дії безкоштовні. Поділити на 2 — зсунути розряди праворуч (`n >> 1`): рівно те саме, що в десятковій системі викреслити нуль у кінці числа 1230. Перевірити парність — глянути на останній розряд (`n & 1`). Обидві вміє будь-яка [позиційна система](book:math/positional-systems) для своєї основи, і двійкова тут просто збіглася з тим, як влаштоване залізо.

Двійка — не будь-який дільник, а той єдиний, з яким машина працює безплатно. Тож збудуймо весь алгоритм навколо неї.

![Чотири правила двійкового НСД: нульова база, спільна двійка виноситься, несумісна відкидається, різниця двох непарних завжди парна](/book/math/number-theory/gcd-euclidean/img/binrules.svg)
*Кожне правило перевіряється тим самим міркуванням про множину спільних дільників. Найцікавіше — останнє: різниця двох непарних чисел завжди парна, тож одразу після віднімання спрацьовує правило зі зсувом. Саме тому кроки не тупцюють на місці: щоразу з пари йде щонайменше один біт.*

Придивімося до третього правила, бо в ньому вся економія. Якщо u непарне, а v парне, то двійка, що сидить у v, спільною бути **не може** — в u її просто немає. Отже викинути її можна задарма, відповідь не зміниться. А спільні двійки збираються лише в другому правилі — і кількість їх ми просто лічимо.

Вийшло те саме, що робить Евклід, тільки іншою валютою: жодне правило **не шукає дільників**, кожне лише або знімає двійку, або зменшує пару. Різниця в тому, що всі дії тепер — зсуви, порівняння й віднімання:

```cpp
#include <bit>        // std::countr_zero — C++20
#include <cstdint>
#include <utility>    // std::swap

std::uint64_t binary_gcd(std::uint64_t u, std::uint64_t v) {
    if (u == 0) return v;
    if (v == 0) return u;

    // Спільні двійки — єдине місце, де НСД їх набирає. Знімаємо і запам'ятовуємо.
    const int k = std::countr_zero(u | v);
    u >>= std::countr_zero(u);           // далі u завжди непарне

    do {
        v >>= std::countr_zero(v);       // робимо непарним і v
        if (u > v) std::swap(u, v);      // тримаємо u ≤ v
        v -= u;                          // різниця двох непарних — парна
    } while (v != 0);

    return u << k;                       // повертаємо спільні двійки на місце
}
```

Код тут написано на C++ не з примхи: уся його суть — у вартості машинних операцій, а `std::countr_zero` (заголовок `<bit>`, C++20) лягає в одну інструкцію — `TZCNT` на x86, пара `RBIT`+`CLZ` на ARM. Вона лічить нулі в хвості числа, тобто одразу знімає всі двійки замість того, щоб зсувати їх по одній у циклі. Старіші компілятори мають `__builtin_ctz`, але з ним варто бути обачним: апаратний `BSF` на нулі не визначений, тож `__builtin_ctz(0)` — це UB. `std::countr_zero(0)` натомість визначений (поверне розрядність типу), і саме тому в бойовому коді беруть його. Утім, у нашому циклі нуль на вхід `countr_zero` не потрапляє ніколи: `u | v` ненульове після перевірок, а `v` перевіряється умовою `while`.

Тепер найцікавіше — чи воно того варте. Порахуймо кроки на знайомій парі.

![Та сама пара 1071 і 462: Евклід витрачає три ділення, двійковий алгоритм — п'ять ітерацій без жодного ділення](/book/math/number-theory/gcd-euclidean/img/bintrace.svg)
*Обидва доходять до 21, але різними грішми. Ліворуч три кроки, і кожен — ділення. Праворуч п'ять кроків, і жоден із них не ділення: тільки зсуви, обмін і віднімання. Спільних двійок тут немає (1071 непарне), тож k = 0 і наприкінці зсувати нема чого.*

Кроків **більше** — і так буде майже завжди. На двадцяти тисячах випадкових пар:

```
 32 біти:  Евклід  18.8 ділень  |  двійковий  22.1 ітерації   (×1.18)
 64 біти:  Евклід  37.5 ділень  |  двійковий  44.7 ітерації   (×1.19)
256 бітів: Евклід 149.7 ділень  |  двійковий 180.2 ітерації   (×1.20)
```

Стабільні двадцять відсотків зайвих кроків — і це не поразка, а ціна. Обмін свідомий: на п'яту частину більше кроків, зате з них зникла найдорожча інструкція. Ахаві й Валле, розібравши алгоритм докладно, оцінили виграш приблизно в **60 % менше бітових операцій** проти класичного Евкліда.

А ось несподіванка. Пара сусідніх чисел Фібоначчі — найгірший вхід для Евкліда, той самий, де всі частки дорівнюють одиниці:

```
Fib #10  (144, 89):              Евклід 10 кроків  |  двійковий  4
Fib #20  (17711, 10946):         Евклід 20 кроків  |  двійковий 12
Fib #40  (267914296, 165580141): Евклід 40 кроків  |  двійковий 21
```

На своєму найгіршому вході Евклід програє двійковому алгоритму **вдвічі**. Причина не в тому, що двійковий кращий, а в тому, що **найгірші входи в них різні**. Фібоначчі мучить Евкліда тим, що кожне ділення зрізає мінімум — рівно одне *b*. Двійковому це байдуже: він не ділить, а дивиться на біти, і послідовність Фібоначчі жодної особливої біди для бітів не створює. Найгірший випадок — властивість пари «алгоритм + вхід», а не самого входу.

**Пастки.** Перша — найприкріша: на сучасних x86 подільники стали значно швидшими, і `binary_gcd` цілком може програти трирядковому циклу з `%`, який компілятор ще й розгорне. Виграш двійкового алгоритму реальний **там, де ділення справді дороге** — на довгих числах у bignum-бібліотеках, на мікроконтролерах без апаратного подільника. Тож міряйте, а не вірте.

Друга серйозніша. Погляньте ще раз на цикл: скільки разів він крутиться і які гілки бере — залежить від **самих чисел**. Якщо цими числами є секретний ключ, час роботи функції розповідає про нього стороннім. Саме тому Даніель Бернстайн і Бо-Їн Янґ на CHES 2019 запропонували `safegcd` — переписали Евкліда через «divsteps», однакові й безумовні кроки, де ні кількість ітерацій, ні гілки від даних не залежать. Цей код сьогодні стоїть у libsecp256k1 — бібліотеці, якою користується Bitcoin. Іронія в тому, що заради сталого часу довелося відмовитися саме від того, чим цікавий двійковий НСД: від уміння вискочити раніше.

### НСД масиву: згортка, що вміє здатися рано

Формула знає два аргументи. Життя приносить масив: звести вектор дробів, знайти крок сітки, обчислити спільний період кількох таймерів.

Рятує те, що операція **асоціативна**: НСД(НСД(a, b), c) = НСД(a, b, c). Причину видно, якщо не думати про числа, а думати про множини. Спільні дільники трійки {a, b, c} — це перетин трьох множин дільників. Перетин можна брати в будь-якому порядку й будь-якими дужками: спершу перші дві, потім третю — результат той самий. А НСД щоразу лише називає найбільший елемент того, що вийшло.

Асоціативність означає, що НСД масиву — це **згортка** (fold). Лишається питання, з чого починати. Відповідь підказує сама рівність НСД(0, x) = x: нуль ділиться на будь-що, тож нічого не обмежує. Отже **нуль — нейтральний елемент**, і згортку природно починати з нього. Заразом це дає безплатну відповідь на межовий випадок: НСД порожнього масиву — 0.

:::tabs
```cpp
#include <numeric>    // std::gcd
#include <cstdint>
#include <span>

std::int64_t gcd_all(std::span<const std::int64_t> xs) {
    std::int64_t g = 0;                  // нейтральний елемент: НСД(0, x) = x
    for (std::int64_t x : xs) {
        g = std::gcd(g, x);
        if (g == 1) return 1;            // одиницю вже ніщо не зрушить
    }
    return g;
}
```
```py
from math import gcd

def gcd_all(xs: list[int]) -> int:
    g = 0                                # нейтральний елемент: НСД(0, x) = x
    for x in xs:
        g = gcd(g, x)
        if g == 1:
            return 1                     # одиницю вже ніщо не зрушить
    return g

# Від Python 3.9 math.gcd бере скільки завгодно аргументів: gcd(*xs).
# Зручно, але дострокового виходу ви вже не контролюєте.
```
```ts
function gcdAll(xs: number[]): number {
  let g = 0;                             // нейтральний елемент: gcd(0, x) = x
  for (const x of xs) {
    g = gcd(g, Math.abs(x));             // gcd — звичайна двоаргументна версія
    if (g === 1) return 1;               // одиницю вже ніщо не зрушить
  }
  return g;
}
```
:::

Рядок із достроковим виходом виглядає як дрібна оптимізація «про всяк випадок». Насправді він майже завжди й спрацьовує — і ось чому.

Імовірність того, що два навмання взяті цілі числа взаємно прості, дорівнює 6/π² ≈ **0.6079**. Число це не з повітря: воно є 1/ζ(2), а ζ(2) = π²/6 — знаменита базельська задача, яку 1735 року розв'язав Ойлер. Міркування коротке: просте *p* ділить випадкове число з імовірністю 1/p, отже ділить обидва — з імовірністю 1/p², а не ділить обох одразу — з імовірністю (1 − 1/p²). Перемноживши по всіх простих, дістаємо ∏(1 − 1/p²) = 1/ζ(2).

Для *k* чисел міркування те саме, лише степінь інший: імовірність, що НСД усіх *k* дорівнює 1, є 1/ζ(k). А ζ(k) стрімко котиться до одиниці: ζ(2) ≈ 1.645, ζ(3) ≈ 1.202, ζ(4) ≈ 1.082. Тобто вже трьох випадкових чисел вистачає, щоб НСД став одиницею з імовірністю 83 %. Перевірка на двадцяти тисячах масивів по 30 випадкових чисел:

```
НСД сягає 1 у середньому після 2.70 елементів
масивів, де 1 досягнуто за ≤ 3 елементи:  83.1 %
```

Отже на мільйоні випадкових чисел цикл майже напевно обірветься на третьому елементі — і саме тому один цей рядок перетворює O(n) на практичне O(1).

**Пастки.** Не сортуйте масив «щоб швидше» — сортування коштує O(n log n), а сама згортка з виходом на одиниці майже завжди закінчується за три кроки. Пам'ятайте й про виродження: якщо всі елементи нулі, НСД = 0 — саме цього й вимагає домовленість, але код, що потім ділить на цей НСД, розсиплеться.

### НСК: переповнюється не відповідь, а дорога до неї

Зв'язок НСД·НСК = a·b перекладається в код сам собою — і саме тому так небезпечний. Запишімо буквально й підставмо a = 2³¹, b = 2³².

![Дві дороги до одного НСК: наївне a·b перевищує стелю int64 рівно на одиницю й дає від'ємну відповідь, тоді як a/НСД·b лишається крихітним](/book/math/number-theory/gcd-euclidean/img/lcmtrap.svg)
*НСД(2³¹, 2³²) = 2³¹, тож НСК = 2³² — чотири мільярди з гаком, дрібниця для 64-бітного типу. Але наївний шлях спершу множить: a·b = 2⁶³, а це рівно на одиницю більше за INT64_MAX. Число [загортається](book:programming/overflow-wraparound) у від'ємне, ділення чесно доводить його до кінця — і функція повертає НСК −4 294 967 296.*

Вдумайтеся в те, що сталося. Відповідь — 2³² — влазить у int64 із запасом у два мільярди разів. Переповнилася не вона, а **дорога до неї**: проміжний добуток. Причому наслідок гірший за просто велике число: у [доповняльному коді](book:math/twos-complement) 2⁶³ читається як −2⁶³, і на виході маємо від'ємне «найменше спільне кратне» — величину, від'ємною бути не здатну за означенням.

Ліки — переставити дії:

```
НСК(a, b) = a / НСД(a, b) · b        ✓  ділимо ПЕРШИМ
НСК(a, b) = a · b / НСД(a, b)        ✗  добуток може не влізти
```

Переставляти можна тому, що НСД(a, b) ділить *a* **націло** — заокруглення тут нема звідки взятися, ділення точне. А число після нього меншає, тож множення стартує з меншого. Максимум, що побачить машина, — саме значення НСК, а не добуток, що вдвічі довший.

:::tabs
```cpp
#include <numeric>
#include <cstdint>

std::int64_t lcm_safe(std::int64_t a, std::int64_t b) {
    if (a == 0 || b == 0) return 0;      // інакше нижче — ділення на нуль
    return a / std::gcd(a, b) * b;       // ділимо ПЕРШИМ
}
// std::lcm із <numeric> робить те саме (реалізації ділять першими),
// але межу має ту саму: якщо сам НСК не влазить у тип — це UB, а не помилка.
```
```py
from math import gcd

def lcm_safe(a: int, b: int) -> int:
    if a == 0 or b == 0:
        return 0
    return a // gcd(a, b) * b            # порядок тут — питання не безпеки, а швидкості

# Від Python 3.9 є math.lcm (і теж багатоаргументний).
# Переповнення в Python не буває взагалі: цілі ростуть, доки є пам'ять.
```
```ts
function lcmSafe(a: bigint, b: bigint): bigint {
  if (a === 0n || b === 0n) return 0n;
  return (a / gcdBig(a, b)) * b;         // gcdBig — версія циклу на BigInt
}
// number тут не годиться: понад 2⁵³ він перестає бути точним цілим.
```
:::

Три мови — три різні стелі, і кожна бреше по-своєму.

**C++** переповнюється мовчки. Гірше того, знакове переповнення — це UB, тож компілятор має право вважати, що його не буває, і оптимізувати відповідно.

**Python** не переповнюється ніколи. Ціле росте, доки вистачає пам'яті, тож `lcm_safe` тут — питання швидкодії (менші числа множаться швидше), а не правильності.

**TypeScript** найковарніший. Числа тут — float64, і понад 2⁵³ вони просто перестають бути точними цілими:

```
2⁵³     = 9007199254740992
2⁵³ + 1 = 9007199254740993   →  у float64 не відрізняється від 2⁵³
```

Це не переповнення: нічого не загортається, помилки не буде, знак не зміниться. [Рухома кома](book:programming/floating-point) просто тихо округлить — і `a % b` почне давати правильні на вигляд, але хибні залишки. Переповнення бодай кричить; float64 бреше пошепки. Єдиний вихід — `BigInt`.

**Пастка з мінімальним числом.** Стандарт C++ каже про `std::gcd` прямо: якщо |m| або |n| не подається в спільному типі, це UB. За цим сухим формулюванням — конкретний випадок: `std::abs(INT64_MIN)` не існує, бо додатного двійника в мінімального числа нема. Тобто `std::gcd(INT64_MIN, x)` — уже UB. Той самий ґандж має й саморобний цикл, що закінчується рядком `return a < 0 ? -a : a`: на `INT64_MIN` заперечення переповнюється. Хочете надійності — беріть беззнакові типи або перевіряйте вхід.

**Пастка з масивом.** НСК масиву — теж згортка, тільки нейтральний елемент тут 1 (а не 0). Але дострокового виходу в неї нема, а рости вона вміє страшно:

```
НСК(1..42) =    219 060 189 739 591 200     ← ще влазить у int64
НСК(1..43) =  9 419 588 158 802 421 600     ← INT64_MAX = 9 223 372 036 854 775 807
```

Сорок два числа — і запас іще сорокакратний. Сорок три — і виліт. Річ у тім, що 43 просте, тож НСК просто помножився на 43 цілком. НСК не підповзає до стелі поступово, даючи час помітити, — він перестрибує її одним множенням на чергове просте. Тому для НСК масиву або беруть довгу арифметику, або перевіряють переповнення на **кожному** кроці.

### Що з цього лишається

Чотири питання — і жодне з них не про математику. Цикл справді не змінився: він так і лишається обміном пари чисел на меншу пару з тією самою відповіддю.

Змінилося те, що навколо. Рекурсія падає не тому, що формула хибна, а тому, що в машини скінченний стек. Двійковий алгоритм виграє не кращою математикою, а дешевшими інструкціями — і програє там, де подільник швидкий. Згортка масиву тримається на асоціативності, але живе з імовірності 6/π². НСК переповнюється не у відповіді, а на шляху до неї.

Спільне в них одне: у машини й математики різні уявлення про те, що таке число. Для математики воно просто є — без розрядності, без стека, без ціни за ділення. Код доводиться писати на межі двох цих світів, і майже всі помилки трапляються саме там, а не в самому алгоритмі, якому дві з половиною тисячі років.
