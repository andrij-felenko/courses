# 📋 Специфікація кадрів ISO/IEC 14443 та криптографічних APDU

У довіднику наведено розширену структуризацію низькорівневих кадрів фізичного та канального рівнів ISO/IEC 14443-3 (Type A та Type B), транспортного протоколу ISO/IEC 14443-4 (T=CL), а також структуру кадрів прикладного рівня APDU (ISO/IEC 7816-4) з підтримкою захищених сесій (*Secure Messaging*).

---

### 1. Канальний шар та таймінги кадрів (ISO/IEC 14443-3)

На фізичному рівні підключення Type A використовує модифіковану модуляцію Міллера з паузою в несучій (з боку зчитувача) та манчестерське кодування на піднесучій 847 кГц (з боку тега). Для Type B використовується модуляція NRZ з 10% АМ (зчитувач) та BPSK модуляція піднесучої 847 кГц (тег).

Параметри швидкостей передачі узгоджуються на етапі ініціалізації за допомогою кадру **PPS** (*Protocol and Parameter Selection*).

#### Таблиця часових інтервалів та параметрів швидкості

| Параметр | Позначення | Стандартне значення | Інженерний зміст та залежність |
| :--- | :--- | :--- | :--- |
| **Базова швидкість** | f_c / 128 | 105.9375 кбіт/с | Початкова швидкість каскаду антиколізії (f_c = 13.56 МГц) |
| **Високі швидкості** | 2x, 4x, 8x | 212, 424, 848 кбіт/с | Швидкості обміну після узгодження кадру PPS |
| **Час затримки кадру** | FDT (Frame Delay Time) | 1172 / f_c (86.3 мкс) | Мінімальний інтервал між кінцем кадру зчитувача й початком кадру тега |
| **Найбільший час очікування** | FWT (Frame Waiting Time) | (256 × 16 / f_c) × 2^FWI | Максимальний інтервал до відповіді тега (FWI = 0...14) |
| **Час Guard Time** | GT (Guard Time) | 16 / f_c (1.18 мкс) | Мінімальна пауза між двома послідовними кадрами зчитувача |

#### Каскад ідентифікації ISO/IEC 14443-3 Type A

Процедура антиколізії дозволяє зчитувачу виділити один пристрій серед кількох карт, що знаходяться в магнітному полі. Якщо картка має 7-байтний UID, процедура повторюється два рази (Cascade Level 1 та Cascade Level 2).

| Команда / Поле | Код кадру | Розмір | Опис інженерної функції |
| :--- | :--- | :--- | :--- |
| **REQA** | `0x26` | 7 бітів | Опитування пристроїв у стані IDLE (Short Frame) |
| **WUPA** | `0x52` | 7 бітів | Опитування всіх пристроїв у полі, включаючи стан HALT |
| **ATQA** | `0x0004` / `0x0002` | 2 байти | Код відповіді: формат ідентифікатора (1, 2 або 3 рівні UID) |
| **ANTICOLLISION CL1** | `0x93 0x20` | 2 байти | Запит перших 4 байтів UID |
| **SELECT CL1** | `0x93 0x70 [4B UID] [BCC]` | 9 байтів | Фіксація вибору тега 1-го рівня (BCC — контрольний байт XOR) |
| **ANTICOLLISION CL2** | `0x95 0x20` | 2 байти | Запит наступних 4 байтів UID (якщо UID 7-байтний) |
| **SELECT CL2** | `0x95 0x70 [4B UID2] [BCC]`| 9 байтів | Фіксація вибору 2-го рівня (перший байт є прапором `0x88 CT`) |
| **SAK** | Select Acknowledge | 1 байт | Байт відповіді: Bit 3 вказує на наявність ISO 14443-4 |

#### Поліном контрольної суми CRC16 (ISO/IEC 14443-3)
Для перевірки цілісності кожного кадру додається 2 байти CRC16. Початкове значення регістра для Type A становить `0x6363`, для Type B — `0xFFFF`.

Поліном обчислюється за формулою:

```
Поліном: x¹⁶ + x¹² + x⁵ + 1  (Гексадецимальне подання: 0x1021)
Тип А початковий стан: 0x6363
Тип B початковий стан: 0xFFFF
```

### 2. Формат кадрів протоколу ISO/IEC 14443-4 (Block Format T=CL)

Після вибору картки процедура повертає байт SAK із встановленим бітом ISO 14443-4. Зчитувач надсилає кадр **RATS** (*Request for Answer to Select*), у відповідь на який тег повертає структуру **ATS** (*Answer to Select*), де вказуються максимальний розмір кадру (FSC), параметри FWI та підтримка високих швидкостей.

#### Структура кадру T=CL

Кадр T=CL загортає прикладні дані APDU у транспортний блок із перевіркою парності та цілісності:

```
+---------+---------+---------+------------------------+---------------+
| PCB     | CID     | NAD     | INF (Application APDU) | CRC16 (2 B)   |
| (1 B)   | (0-1 B) | (0-1 B) | (0–253 B)              | (LSB, MSB)    |
+---------+---------+---------+------------------------+---------------+
```

#### Декодування байте контролю протоколу PCB (Protocol Control Byte)

Байт PCB визначає тип блоку й керує потоком даних та повторною передачею кадрів:

1. **I-Block (Інформаційний блок, PCB = `000x b`):** Несе прикладні дані APDU. Біт `b` є номером кадру (Block Number 0/1) для контролю втрат.
2. **R-Block (Блок підтвердження, PCB = `101x b`):** Передає сигнатури ACK/NAK. Використовується для запиту повторної передачі при виявленні помилки CRC16.
3. **S-Block (Керувальний блок, PCB = `11xx b`):** 
   - `0xC2` (DESELECT): М'яке відключення тега й переведення в режим сну.
   - `0xF2` (WTX — Frame Waiting Extension): Запит тега на розширення часу очікування відповіді. Тег повертає байт `WTXM` (коєфіцієнт множення часу), щоб запобігти таймауту зчитувача під час складних криптографічних обчислень.

### 3. Формат прикладних команд APDU (ISO/IEC 7816-4)

Для обміну криптографічними командами використовується формат APDU (*Application Protocol Data Unit*).

#### Структура Command APDU (Команда зчитувача)

Команда може передаватися в короткій формі (до 256 байтів data) або розширеній формі Extended APDU (до 65535 байтів data).

```
+-----+-----+-----+-----+---------+---------------------+---------+
| CLA | INS | P1  | P2  | Lc      | Data Payload        | Le      |
| 1 B | 1 B | 1 B | 1 B | 1/3 B   | 0–255 (або 65535) B | 1/3 B   |
+-----+-----+-----+-----+---------+---------------------+---------+
```

| Поле | Позначення | Розмір | Інженерне призначення |
| :--- | :--- | :--- | :--- |
| **CLA** | Class Byte | 1 байт | Клас команди: `0x00` (стандартний), `0x80` (пропрієтарний), `0x0C` (шифрований з MAC) |
| **INS** | Instruction | 1 байт | Код інструкції (`0xA4` SELECT, `0x20` VERIFY, `0x82` EXTERNAL AUTH, `0x84` GET CHALLENGE) |
| **P1-P2**| Parameters | 2 байти | Специфічні параметри (наприклад, селектор AID, номер ключа, зміщення в файлі) |
| **Lc** | Length Cmd | 1 або 3 B | Довжина даних у полі Data Payload |
| **Data** | Data Payload | `Lc` байтів| Криптографічний запит (генерація Random Nonce, зашифрований токен) |
| **Le** | Length Exp | 1 або 3 B | Максимальна кількість байтів, яку зчитувач очікує у відповіді |

#### Структура Response APDU (Відповідь тега)

Відповідь повертає дані й двобайтний код статусу SW1-SW2:

```
+------------------------------------+---------+---------+
| Data Payload (0–256 B / 65535 B)   | SW1     | SW2     |
| (Криптографічний підпис / Сертифікат)| (1 B) | (1 B)   |
+------------------------------------+---------+---------+
```

#### Довідник кодів статусу SW1-SW2

Таймінги й помилки обробки відображаються у двох останніх байтах відповіді:

| SW1-SW2 | Категорія | Інженерний опис та стан безпеки |
| :--- | :--- | :--- |
| `0x9000` | Success | Операція виконана успішно, автентифікацію підтверджено |
| `0x6300` | Warning | Помилка перевірки ключа або PIN-коду (без вказування кількості спроб) |
| `0x63CX` | Warning | Невірний PIN-код, залишилося `X` спроб до повного блокування чипа |
| `0x6982` | Security Error | Доступ заборонено: не виконано умову безпеки (відсутня попередня автентифікація) |
| `0x6984` | Data Invalidated | Заблокований криптографічний ключ або пошкоджена чексума EEPROM |
| `0x6985` | Conditions Not Met| Команда відхилена: недопустимий стан (наприклад, сесія вже закрита) |
| `0x6A82` | File Not Found | Відсутній обраний застосунок (AID) на смарт-картці |
| `0x6C XX` | Wrong Length | Невірна довжина `Le`: тег повідомляє точний розмір відповіді `XX` байтів |

### 4. Кадри захищеного сеансу Secure Messaging (ISO/IEC 7816-4 SM)

При виконанні захищених транзакцій (EMV банківські картки, паспорти eMRTD) звичайний APDU-кадр загортається в захисний контейнер **Secure Messaging (SM)** на основі сесійних ключів AES-128 / AES-256 (`K_ENC` та `K_MAC`).

#### Структура BER-TLV обгортки Secure Messaging

Вміст кадру APDU шифрується та доповнюється кодом автентифікації повідомлення (MAC):

```
+---------+--------------------+---------+-------------------+---------+-------------------+
| Header  | Tag 0x87 (Cipher)  | Tag 0x97| Tag 0x97 (Le)     | Tag 0x8E| Tag 0x8E (MAC)    |
| CLA P1P2| Len + 0x01 + Data  | 0x01    | Очікувана довжина | 0x08    | 8 байтів AES-MAC  |
+---------+--------------------+---------+-------------------+---------+-------------------+
```

1. **Tag `0x87` (Cryptogram):** Вміщує зашифрований корисний вміст оригінального Data Payload. Перед шифруванням до даних додається вирівнювальний падінг (Padding Content Indicator `0x01` + ISO 9797 Method 2 padding).
2. **Tag `0x97` (Le Encapsulation):** Зашифроване або захешоване значення оригінального поля `Le`.
3. **Tag `0x8E` (Cryptographic Checksum):** Обчислюється як CMAC (Cipher-based MAC) або CBC-MAC по всьому кадру, включаючи маскований заголовок CLA/INS/P1/P2 та лічильник послідовності сесії (SSC — *Send Sequence Counter*).

Збільшення лічильника SSC на +1 для кожного нового кадру унеможливлює повторне підставляння зашифрованих кадрів атакуючим (*Anti-Replay Protection*). Якщо лічильник SSC не збігається з очікуваним значенням на тезі, кадр відхиляється з кодом SW1-SW2 `0x6988`.
