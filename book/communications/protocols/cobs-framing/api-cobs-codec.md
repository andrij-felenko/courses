# 📋 Специфікація форматів COBS, COBS/R та кодових станів

Специфікація протоколу кадрування COBS визначає точні правила кодування байтів, формати структур у пам'яті, карти кодових значень для варіантів COBS/R і COBS/ZPE та контракти обробки помилок канального рівня.

---

## Загальна структура кадру в лінії зв'язку

Кадр COBS передається каналом зв'язку як послідовність октетних значень, що завершується єдиним недвозначним байтом-розділювачем `0x00`:

```
┌──────────┬──────────────┬──────────┬──────────────┬───┬──────────┬──────────────┬──────────┐
│  Code 1  │ Data Block 1 │  Code 2  │ Data Block 2 │...│  Code k  │ Data Block k │ Delimiter│
│ (1 байт) │ (0..254 байт)│ (1 байт) │ (0..254 байт)│   │ (1 байт) │ (0..254 байт)│  (0x00)  │
└──────────┴──────────────┴──────────┴──────────────┴───┴──────────┴──────────────┴──────────┘
▲                                                                                 ▲
└─────────────────────────── Тіло кадру (жодного 0x00!) ──────────────────────────┴─ Межа кадру
```

### Формальні інваріанти структури кадру

Будь-яка сумісна з каноном реалізація алгоритму COBS зобов'язана гарантувати дотримання трьох фундаментальних інваріантів канального рівня:

1. **Інваріант виключення розділювача (Zero-Exclusion Invariant):**
   Усередині тіла кадру (починаючи від першого октету `Code 1` і закінчуючи завершальним байтом `Data Block k` включно) жоден байт не може набувати числового значення `0x00`. Поява октету `0x00` у будь-якій позиції вхідного потоку трактується приймачем як безумовна межа між двома сусідніми повідомленнями. Якщо нуль виявлено в момент, коли лічильник поточного блоку ще не вичерпано, це вважається критичною помилкою кадрування, яка вимагає негайного скидання буфера прийому.

2. **Інваріант обмеження довжини (Length Boundedness Invariant):**
   Для вихідного масиву корисного навантаження довжиною `N` октетних позицій (`N ≥ 0`) повна довжина сформованого кадру в лінії зв'язку (включно з кінцевим маркером `0x00`) суворо затиснута в діапазоні:
   ```
   N + 2 ≤ L_total ≤ N + ⌈N / 254⌉ + 1
   ```
   Нижній край діапазону (`N + 2`) досягається для масивів, які не містять нулів або містять поодинокі нулі при довжині повідомлення менше `254` байтів. Верхній край діапазону досягається для масивів, що складаються з довгих послідовностей ненульових байтів, де кожні `254` байти породжують додатковий байт службового покажчика `0xFF`.

3. **Інваріант ланцюжка зміщень (Pointer Chaining Invariant):**
   Якщо абсолютна позиція поточного службового покажчика в закодованому потоці дорівнює `p`, то позиція наступного службового покажчика (або кінцевого розділювача кадру `0x00`) обчислюється строго за формулою:
   ```
   p_next = p + Code
   ```
   Якщо за адресою `p_next` не виявлено наступного байта покажчика або кінцевого маркера `0x00`, приймач фіксує фатальну помилку порушення структури кадру (англ. *offset out of bounds*).

## Таблиця кодових значень базового алгоритму COBS

Покажчик зміщення `Code` займає рівно 1 октет і набуває значень у діапазоні від `0x01` до `0xFF` (`1..255`). Семантика кожного значення визначена наступною специфікацією:

| Значення коду (Hex) | Значення коду (Dec) | Довжина даних у блоці | Дія декодера під час обробки блоку |
|---|---|---|---|
| `0x00` | 0 | — | **Заборонено в тілі кадру.** Інтерпретується як маркер межі або помилка. |
| `0x01` | 1 | 0 байтів | Прочитати 0 байтів даних; записати відновлений `0x00` у буфер призначення. |
| `0x02` | 2 | 1 байт | Прочитати 1 байт даних; записати відновлений `0x00` у буфер призначення. |
| `0x03` | 3 | 2 байти | Прочитати 2 байти даних; записати відновлений `0x00` у буфер призначення. |
| `0x04` | 4 | 3 байти | Прочитати 3 байти даних; записати відновлений `0x00` у буфер призначення. |
| `...` | ... | ... | Прочитати `Code - 1` байтів; записати відновлений `0x00` у буфер призначення. |
| `0xFE` | 254 | 253 байти | Прочитати 253 байти даних; записати відновлений `0x00` у буфер призначення. |
| `0xFF` | 255 | 254 байти | Прочитати 254 байти даних; **НЕ записувати 0x00** (максимальний блок). |

### Детальні правила інтерпретації кодів

Кодове значення `0x01` є особливим випадком нульової довжини: воно сигналізує декодеру, що між двома нулями у вихідному повідомленні не було жодного корисного байта даних (наприклад, при зустрічі послідовності `0x00 0x00`). Декодер не зчитує байти з потоку, а відразу записує `0x00` у відновлений масив і переходить до наступного кодового октету.

Кодові значення від `0x02` до `0xFE` позначають стандартні блоки корисних даних. Числове значення покажчика дорівнює кількості наступних ненульових байтів плюс одиниця. Після зчитування цих байтів декодер зобов'язаний автоматично вставити в кінець блоку один нульовий байт `0x00`, оскільки саме цей нуль завершив поточний блок під час кодування на стороні передавача.

Кодове значення `0xFF` позначає граничний блок максимального розміру. Оскільки один октет може адресувати зміщення не більше ніж на `255` позицій уперед, блок містить рівно `254` ненульових байти даних. Оскільки блок завершився не через появу нуля у вихідних даних, а через переповнення розрядності покажчика, **після зчитування 254 байтів нуль у вихідний буфер не вставляється**.

*Спеціальне правило кінця пакета:* Якщо блок є останнім у кадрі (тобто покажчик зміщення вказує безпосередньо на кінцевий розділювач `0x00`), завершальний нуль `0x00` у буфер корисного навантаження не вставляється, оскільки корисне повідомлення повністю розпаковано.

## Специфікація модифікації COBS/R (Reduced Overhead)

Формат COBS/R є зворотно-сумісною оптимізацією базового алгоритму COBS, покликаною усунути фінальний накладний байт оверхеду в пакетах, де останній байт корисного навантаження має велике числове значення.

### Алгоритм кодування COBS/R

Нехай довжина фінального блоку пакета становить `L` ненульових байтів (`1 ≤ L ≤ 254`), а числове значення останнього байта в цьому блоці дорівнює `d_last`.

1. **Умова заміщення (Спрацювання оптимізації):**
   Якщо `d_last ≥ L + 1`:
   * На місце кодового покажчика записується саме значення `Code = d_last`.
   * У потік записуються перші `L - 1` байтів фінального блоку.
   * Сам останній байт `d_last` окремо в кінець блоку не записується.
   * *Результат:* Загальна довжина кадру скорочується рівно на 1 октет, забезпечуючи нульові накладні витрати на рівні кадрування.

2. **Умова стандартного збереження:**
   Якщо `d_last < L + 1`:
   * На місце кодового покажчика записується стандартне значення `Code = L + 1`.
   * У потік записуються всі `L` байтів фінального блоку (включно з `d_last`).

### Алгоритм декодування COBS/R

Декодер обчислює реальну кількість байтів `R`, що залишилися між позицією поточного покажчика `Code` та кінцевим нулем `0x00` у прийнятому кадрі:

1. Якщо `Code > R`:
   * Декодер розпізнає спрацювання оптимізації COBS/R.
   * Копіює `R - 1` байтів із вхідного потоку у вихідний буфер.
   * Записує у вихідний буфер значення самого покажчика `Code` як останній відновлений байт даних `d_last`.
2. Якщо `Code == R`:
   * Декодер виконує стандартну обробку блоку COBS, копіюючи `Code - 1` байтів даних.

## Специфікація кодового простору COBS/ZPE (Zero Pair Elimination)

Модифікація COBS/ZPE оптимізована для стиснення потоків розріджених даних (наприклад, 16-бітних та 32-бітних нульових цілих чисел або дробових нулів у телеметрії). Алгоритм резервує невикористаний діапазон кодових значень для маркування подвійних нулів `0x00 0x00`.

| Діапазон коду (Hex) | Довжина блоку даних | Дія декодера після блоку | Семантичний тип блоку |
|---|---|---|---|
| `0x01` | 0 байтів | Вставити `0x00` | Одиночний нуль |
| `0x02 .. 0xDF` | `1 .. 222` байти | Вставити `0x00` | Звичайний блок COBS |
| `0xE0` | 0 байтів | Вставити `0x00 0x00` | **Пара нулів без даних** |
| `0xE1 .. 0xFD` | `1 .. 29` байтів | Вставити `0x00 0x00` | **Блок даних + пара нулів** |
| `0xFE` | 253 байти | Вставити `0x00` | Довгий стандартний блок |
| `0xFF` | 254 байти | Не вставляти нуль | Максимальний блок (продовження) |

Код `0xE0` позначає наявність двох послідовних нулів без корисних даних перед ними. Коди від `0xE1` до `0xFD` містять від 1 до 29 байтів даних, після яких автоматично вставляється пара нулів `0x00 0x00`. Це дозволяє суттєво стискати типові структури телеметрії датчиків польотних контролерів, у яких нульові поля становлять значну частку обсягу пакета.

## Матриця переходів потокового автомата (FSM Matrix)

Потоковий декодер функціонує за детермінованою матрицею станів, що гарантує захист від зависання автомата:

| Поточний стан | Вхідна подія / Байт | Наступний стан | Виконувана дія | Статус операції |
|---|---|---|---|---|
| `HUNT_DELIM` | `0x00` | `READ_CODE` | Скинути довжину прийому (`len = 0`) | `COBS_OK` |
| `HUNT_DELIM` | `0x01 .. 0xFF` | `HUNT_DELIM` | Пропустити байт (пошук синхронізації) | `COBS_OK` |
| `READ_CODE` | `0x00` | `READ_CODE` | Якщо `len > 0` → пакет зібрано; скинути `len = 0` | `COBS_OK` |
| `READ_CODE` | `0x01` | `READ_CODE` | Записати `0x00` у вихідний буфер | `COBS_OK` (з перевіркою overflow) |
| `READ_CODE` | `0x02 .. 0xFE` | `READ_DATA` | Встановити лічильник `rem = code - 1` | `COBS_OK` |
| `READ_CODE` | `0xFF` | `READ_DATA` | Встановити лічильник `rem = 254` | `COBS_OK` |
| `READ_DATA` | `0x00` | `HUNT_DELIM` | **Помилка кадрування:** скинути буфер | `COBS_ERR_UNEXPECTED_DELIMITER` |
| `READ_DATA` | `0x01 .. 0xFF` (`rem > 1`) | `READ_DATA` | Записати байт у буфер; декремент `--rem` | `COBS_OK` (з перевіркою overflow) |
| `READ_DATA` | `0x01 .. 0xFF` (`rem == 1`, `code < 0xFF`) | `READ_CODE` | Записати байт; записати `0x00` | `COBS_OK` (з перевіркою overflow) |
| `READ_DATA` | `0x01 .. 0xFF` (`rem == 1`, `code == 0xFF`) | `READ_CODE` | Записати байт; (без відновлення нуля) | `COBS_OK` (з перевіркою overflow) |

### Опис критичних переходів та обробки аварійних ситуацій

Стан `HUNT_DELIM` є захисним фільтром, який запобігає передачі пошкодженого або неповного пакета на вищі рівні мережевого стека. Будь-який збій кадрування (наприклад, отримання байта `0x00` у момент, коли лічильник `rem` усередині стану `READ_DATA` був більшим за нуль) негайно переводить автомат у стан `HUNT_DELIM`. Усі наступні байти відкидаються до моменту отримання наступного справжнього розділювача `0x00`.

Стан `READ_CODE` відповідає за розпізнавання структури поточного блоку. Якщо в цьому стані надходить байт `0x00`, автомат перевіряє, чи було накопичено корисні дані в буфері (`len > 0`). Якщо дані є, це свідчить про успішне завершення прийому кадру: автомат формує подію готовності пакета, сповіщає прикладний рівень і готується до прийому наступного повідомлення. Якщо ж `len == 0`, нуль вважається порожнім інтервалом спокою між повідомленнями (англ. *inter-frame gap*).

## Стандартизовані коди помилок та обчислення ємності буферів

Для забезпечення інтероперабельності всі реалізації драйверів COBS повертають уніфіковані статус-коди:

| Символічний код | Число | Категорія помилки | Рекомендована реакція драйвера |
|---|---|---|---|
| `COBS_OK` | 0 | Успіх | Передати пакет наступному рівню стека (CRC / розбір команд) |
| `COBS_ERR_NULL_PTR` | 1 | Помилка API | Перевірити вхідні покажчики у виклику функції |
| `COBS_ERR_BUFFER_OVERFLOW` | 2 | Критична | Відкинути кадр, скинути парсер у `HUNT_DELIM` |
| `COBS_ERR_ZERO_IN_PAYLOAD` | 3 | Помилка каналу | Зустрінуто заборонений `0x00` у тілі під час блокового декодування |
| `COBS_ERR_UNEXPECTED_DELIMITER` | 4 | Збій кадру | Розділювач `0x00` надійшов до вичерпання лічильника блоку |
| `COBS_ERR_INVALID_OFFSET` | 5 | Пошкодження заголовка | Покажчик зміщення виходить за межі вхідного масиву |

### Деталізація категорій помилок та механізми діагностики

Помилка `COBS_ERR_NULL_PTR` є програмною винятковою ситуацією, яка свідчить про передачу некоректного нульового покажчика в інтерфейсні функції `cobs_encode` або `cobs_decode`. Ця помилка виявляється на етапі вхідної валідації аргументів до початку будь-яких маніпуляцій із пам'яттю.

Помилка `COBS_ERR_BUFFER_OVERFLOW` виникає, коли виділений вихідний буфер має недостатній розмір для збереження результату операції. Для функції кодування це означає, що розмір `dst_capacity` є меншим за величину `N + ⌈N / 254⌉ + 1`. Для функції декодування це свідчить про те, що розмір відновлених даних перевищує виділену місткість масиву призначення. У потоковому режимі ця помилка призводить до аварійного скидання накопичувального буфера та переходу FSM у стан `HUNT_DELIM`.

Помилка `COBS_ERR_ZERO_IN_PAYLOAD` сигналізує про виявлення октету `0x00` всередині закодованого масиву під час блокової обробки до досягнення заявленого кінця повідомлення. Це однозначно вказує на пошкодження даних у каналі зв'язку (наприклад, через апаратну заваду, яка інвертувала біти переданого покажчика зміщення).

Помилка `COBS_ERR_UNEXPECTED_DELIMITER` виникає в потоковому автоматі, коли байт-розділювач `0x00` надходить у момент, коли лічильник байтів поточного блоку `rem` не дорівнює нулю. Приймач фіксує передчасне завершення блоку, відкидає частково прийнятий пакет і повертається в початковий стан синхронізації.

Помилка `COBS_ERR_INVALID_OFFSET` фіксується блоковим декодером, якщо значення зчитаного покажчика зміщення `Code` перевищує кількість байтів, що залишилися до кінця переданого вхідного масиву (`src + (Code - 1) > src_end`). Це свідчить про пошкодження кодового байта завадою під час транспортування лінією зв'язку.

## Розрахунок статичної пам'яті для вбудованих систем

Для коректного виділення пам'яті на етапі компіляції та уникнення помилок переповнення буферів використовуються наступні математичні вирази:

:::tabs
```c
#include <stddef.h>

/**
 * Обчислення максимального розміру буфера передавача (включно з кінцевим 0x00).
 */
#define COBS_ENCODED_MAX_SIZE(payload_size) \
    ((payload_size) + ((payload_size) / 254) + 1 + 1)

/**
 * Обчислення максимального розміру буфера корисного навантаження після розпакування.
 */
#define COBS_DECODED_MAX_SIZE(encoded_size) \
    ((encoded_size) > 1 ? ((encoded_size) - 1) : 0)
```
```cpp
#include <cstddef>

namespace cobs {

/**
 * Константний вираз часу компіляції для максимального розміру закодованого буфера.
 */
[[nodiscard]] constexpr size_t encoded_max_size(size_t payload_size) noexcept {
    return payload_size + (payload_size / 254) + 1 + 1;
}

/**
 * Константний вираз для максимального розміру відновленого корисного навантаження.
 */
[[nodiscard]] constexpr size_t decoded_max_size(size_t encoded_size) noexcept {
    return (encoded_size > 1) ? (encoded_size - 1) : 0;
}

} // namespace cobs
```
:::

## Часова та просторова складність операцій кодека

Алгоритм COBS спроектовано для забезпечення граничної обчислювальної ефективності на мікроконтролерах із низькою тактовою частотою:

* **Часова складність кодування `O(N)`:** Алгоритм кодування виконує рівно один послідовний прохід по вхідному масиву даних. Для кожного байта виконується лише одна перевірка на рівність нулю, один інкремент лічильника та один прямий запис у пам'ять. Відсутність вкладених циклів та рекурсії гарантує лінійний час виконання без сплесків затримки.
* **Часова складність декодування `O(N)`:** Декодер послідовно читає вхідний масив від початку до кінця, копіюючи фрагменти пам'яті за допомогою швидких інструкцій блокового пересилання. Кожен вхідний байт обробляється рівно один раз.
* **Просторова складність `O(1)`:** Алгоритм не потребує виділення динамічної пам'яті, створення таблиць пошуку чи збереження дерева станів. Усі проміжні змінні розміщуються в кількох регістрах процесора загального призначення (на стеку функції використовується менше ніж 32 байти пам'яті).

## Контракти функцій API (Preconditions та Postconditions)

Для забезпечення надійності в критичних системах авіоніки та медицини інтерфейсні функції кодека підпорядковуються суворим формальним контрактам:

### Контракт блокового кодування `cobs_encode`
* **Передмови (Preconditions):**
  * Вказівники `src`, `dst` та `out_len` не повинні бути рівними `NULL`.
  * Буфер `dst` повинен мати місткість щонайменше `src_len + ⌈src_len / 254⌉ + 1` октетів.
  * Області пам'яті `src` та `dst` не повинні перекриватися (англ. *restrict semantics*).
* **Післямови (Postconditions):**
  * У масив `dst` записано рівно `*out_len` октетів, жоден із яких не дорівнює `0x00`.
  * Значення `*out_len` задовольняє нерівність `src_len + 1 ≤ *out_len ≤ src_len + ⌈src_len / 254⌉ + 1`.
  * Повернено статус `COBS_OK`.

### Контракт блокового декодування `cobs_decode`
* **Передмови (Preconditions):**
  * Вказівники `src`, `dst` та `out_len` не повинні бути рівними `NULL`.
  * Дозволяється тотожність адрес `src == dst` для виконання in-place декодування.
* **Післямови (Postconditions):**
  * При поверненні `COBS_OK` у буфер `dst` записано відновлені корисні дані довжиною `*out_len ≤ src_len - 1`.
  * У разі помилки структури кадру стан буфера `dst` вважається невизначеним, а функція повертає відповідний статус помилки.

### Контракт потокового парсера `cobs_parser_feed_byte`
* **Передмови (Preconditions):**
  * Вказівник `parser` не дорівнює `NULL`, а внутрішній буфер `parser->rx_buf` коректно ініціалізовано.
* **Інваріанти структури парсера:**
  * На кожному виклику виконується нерівність `parser->rx_len ≤ parser->rx_capacity`.
  * Поточний стан `parser->state` є коректним значенням перечислення `cobs_parser_state_t`.
  * Лічильник залишку байтів `parser->block_rem` суворо не перевищує `254`.
* **Повернене значення:**
  * Функція повертає `true` тоді й тільки тоді, коли отриманий байт `0x00` успішно завершив валідний кадр корисних даних ненульової довжини.
* **Потокобезпека (Thread Safety):**
  * Екземпляр `cobs_parser_t` є реентерабельним між різними екземплярами, але одночасний доступ до одного й того самого об'єкта з кількох потоків або контексту переривання вимагає зовнішньої синхронізації через м'ютекс або критичну секцію.

## Інтеграційні рекомендації для проектувальників протоколів

Під час розробки власного протоколу прикладного рівня на базі кадрування COBS рекомендується дотримуватися наступних інженерних правил:
1. **Інкапсуляція контрольної суми:** Контрольна сума кадру (CRC-16-CCITT або CRC-32) завжди обчислюється від сирого корисного навантаження і дописується в кінець повідомлення **до** виклику функції `cobs_encode`. Кадрування COBS має огортати весь сформований пакет (заголовок + навантаження + CRC).
2. **Єдиний розділювач між пакетами:** Для економії пропускної здатності між двома послідовними пакетами достатньо передавати рівно один байт `0x00`. Цей октет одночасно слугує маркером кінця попереднього пакета та стартовим сигналом синхронізації для наступного.
3. **Обробка пауз у лінії (Inter-byte timeouts):** У разі тривалої паузи між байтами всередині одного кадру (таймаут перевищує час передачі кількох символів) потоковий декодер повинен додатково контролюватися програмним таймером скидання, який переводить FSM у стан `HUNT_DELIM` для запобігання склеюванню залишків завислого кадру з новим пакетом.
4. **Кросплатформна інтероперабельність:** Оскільки кадрування COBS оперує суто на рівні окремих 8-бітних октетів і не залежить від порядку байтів у багатобайтових числах (Endianness), двійкові пакети COBS можуть безпосередньо транслюватися між процесорами з різною архітектурою (наприклад, Little-Endian ARM Cortex-M та Big-Endian DSP/RISC-V) без додаткової конвертації на канальному рівні.
5. **Діагностика апаратного рівня UART:** У разі виникнення апаратного сигналу BREAK на лінії послідовного порту (тривалий низький рівень понад 1 кадр, який апаратно формує нульовий байт із помилкою кадрування Framing Error), драйвер нижнього рівня повинен переводити парсер COBS у стан `HUNT_DELIM`, забезпечуючи негайне узгодження з передавачем після відновлення сигналу.
