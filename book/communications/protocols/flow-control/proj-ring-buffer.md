# ⚙️ Кільцевий буфер у C: безпечний для переривань

[Керування потоком](book:communications/flow-control) тримається на одному непомітному вузлі — **кільцевому буфері** (англ. *ring / circular buffer* — «кільцевий буфер»), куди переривання складає прийняті байти, а головний код їх звідти забирає. Ідея проста до краю: масив, у якому після останньої комірки знову йде перша. Та щойно доходить до коду, проста ідея ставить підступне запитання: **як писати й читати одночасно** — із переривання і з основного циклу — так, щоб байт ніколи не «розірвало» навпіл і жоден не зник без сліду? Відповідь — у тому, **хто** торкається кожного покажчика і в **якому порядку**.

**Задача буденна, але всюдисуща.** Будь-який драйвер UART, що не блокує процесор, влаштований так: апаратне переривання спрацьовує на кожен прийнятий байт (або на заповнення апаратного FIFO), коротко перекладає байт у буфер у пам'яті — і виходить. Застосунок же читає з того ж буфера, коли йому зручно, через `Serial.read()` чи подібне. Виходить **один писач і один читач**, що працюють асинхронно: переривання може врізатися в головний код будь-якої миті, навіть посеред рядка. Якщо структуру буфера зроблено наївно, цей збіг тихо псує дані — і налагоджувати таке пекельно, бо збій плаває й залежить від таймінгу.

## Чому звичайна черга тут не годиться

Найочевидніша черга — масив плюс лічильник `count`, скільки байтів усередині: писач робить `count++`, читач `count--`. На одному потоці це бездоганно. Але `count++` — **не одна** машинна операція, а три: прочитати, додати одиницю, записати назад. Якщо переривання-писач врветься між «прочитати» і «записати» головного коду-читача (який саме робив `count--`), одне з оновлень загубиться — і `count` поступово розійдеться з реальністю. Це **гонитва даних** (англ. *race condition* — «стан гонитви»): результат залежить від того, хто кого випередив на такт.

Рятунок елегантний: **не ділити жодної змінної між писачем і читачем для запису**. Замість спільного `count` беремо два окремі покажчики — `head` (його **пише лише** переривання) і `tail` (його **пише лише** читач). Кожен бік володіє своїм покажчиком одноосібно й лише **читає** чужий. Тоді оновлення нікому не треба захищати: писач рухає `head`, читач рухає `tail`, і їхні записи ніколи не накладаються на ту саму комірку пам'яті. Стан буфера випливає з порівняння двох покажчиків, а не з третьої спільної змінної.

## Ідея: head пише, tail читає, ціною однієї комірки

Домовляємось так: `head` показує, **куди писати наступний** байт; `tail` — **звідки читати наступний**. Буфер **порожній**, коли `head == tail` (нема непрочитаного). Буфер **повний**, коли наступний крок `head` уперся б у `tail`.

І тут вилазить класична двозначність: стан «порожньо» (`head == tail`) і стан «повно» виглядали б **однаково**, якби ми дозволили `head` дійти впритул до `tail` ззаду. Розрізнити їх можна двома способами — або тримати окремий лічильник (а ми щойно від нього відмовилися заради безпеки), або **жертвувати однією коміркою**: вважати буфер повним на крок раніше, коли між `head` і `tail` лишається один порожній проміжок. Друге — стандартний і безпечний для нашої схеми вибір: ціна — один невикористаний байт із, скажімо, 256, а виграш — жодних спільних змінних. Тому корисна місткість буфера на `N` комірок — `N − 1` байт.

Залишок при діленні на `N` робить кільце кільцем: після `N − 1` покажчик повертається на 0. Якщо `N` — **степінь двійки** (64, 128, 256), цей залишок дешевший за саме ділення — його роблять побітовим «і» з маскою `N − 1`, що для мікроконтролера помітно швидше. Тому місткість майже завжди беруть степенем двійки.

## Робочий код

Спершу структура й операції. `volatile` тут обов'язковий: він каже компілятору, що покажчики змінюються «ззовні» (з переривання), тож їх не можна кешувати в регістрі й треба щоразу перечитувати з пам'яті.

:::tabs
```cpp
#include <stdint.h>
#include <stdbool.h>

#define RB_SIZE 256                 // степінь двійки → маска замість ділення
#define RB_MASK (RB_SIZE - 1)

typedef struct {
    volatile uint8_t  buf[RB_SIZE];
    volatile uint16_t head;         // пише ЛИШЕ переривання
    volatile uint16_t tail;         // пише ЛИШЕ читач
} RingBuf;

static inline bool rb_empty(const RingBuf* r) {
    return r->head == r->tail;
}

static inline bool rb_full(const RingBuf* r) {
    return ((r->head + 1) & RB_MASK) == r->tail;   // наступний head упреться в tail
}
```
```python
RB_SIZE = 256                       # степінь двійки → маска замість ділення
RB_MASK = RB_SIZE - 1


class RingBuf:
    def __init__(self):
        self.buf = bytearray(RB_SIZE)
        self.head = 0               # пише ЛИШЕ переривання
        self.tail = 0               # пише ЛИШЕ читач

    def empty(self):
        return self.head == self.tail

    def full(self):
        # наступний head упреться в tail
        return ((self.head + 1) & RB_MASK) == self.tail
```
:::

Бік писача — його викликає **лише переривання**. Він рухає `head` **останнім**, уже після того, як байт ліг у комірку:

:::tabs
```cpp
// Викликається з ISR прийому UART. Повертає false, якщо буфер повний (байт відкинуто).
bool rb_push(RingBuf* r, uint8_t b) {
    if (rb_full(r)) return false;            // нема місця — чесно відмовляємо
    r->buf[r->head] = b;                     // 1) спершу кладемо байт
    r->head = (r->head + 1) & RB_MASK;       // 2) і ЛИШЕ ПОТІМ відкриваємо його читачеві
    return true;
}
```
```python
# Викликається з ISR прийому UART. Повертає False, якщо буфер повний (байт відкинуто).
def rb_push(r, b):
    if r.full():
        return False                         # нема місця — чесно відмовляємо
    r.buf[r.head] = b                        # 1) спершу кладемо байт
    r.head = (r.head + 1) & RB_MASK          # 2) і ЛИШЕ ПОТІМ відкриваємо його читачеві
    return True
```
:::

Бік читача — його викликає **лише головний код**. Він рухає `tail` **останнім**, уже забравши байт:

:::tabs
```cpp
// Викликається з головного циклу. Повертає false, якщо читати нема чого.
bool rb_pop(RingBuf* r, uint8_t* out) {
    if (rb_empty(r)) return false;           // порожньо
    *out = r->buf[r->tail];                  // 1) спершу забираємо байт
    r->tail = (r->tail + 1) & RB_MASK;       // 2) і ЛИШЕ ПОТІМ звільняємо комірку писачеві
    return true;
}
```
```python
# Викликається з головного циклу. Повертає (False, None), якщо читати нема чого.
def rb_pop(r):
    if r.empty():
        return False, None                   # порожньо
    out = r.buf[r.tail]                      # 1) спершу забираємо байт
    r.tail = (r.tail + 1) & RB_MASK          # 2) і ЛИШЕ ПОТІМ звільняємо комірку писачеві
    return True, out
```
:::

Уся безпека сидить у **порядку двох рядків** усередині кожної функції. Писач спершу записує комірку й **аж потім** просуває `head` — тож читач, який бачить новий `head`, гарантовано бачить і вже записаний байт під ним, а не сміття. Читач спершу забирає байт і **аж потім** відсуває `tail` — тож писач не затре комірку, яку читач саме копіює. Поки кожен покажчик рухає рівно один бік і рухає його останньою дією, жодних блокувань чи вимикання переривань не треба.

## Worked-приклад: переривання влетіло посеред читання

Найкраще видно безпеку схеми на найгіршому збігу — коли переривання спрацьовує **просто посеред** `rb_pop`.

**Умова.** Буфер `RB_SIZE = 256`. У ньому два непрочитані байти: `tail = 10`, `head = 12`. Головний код викликав `rb_pop` і саме виконав рядок 1 (`*out = buf[10]`), але **ще не** оновив `tail`. У цю мить приходить байт по UART і спрацьовує переривання з `rb_push`.

```text
стан до:        tail=10, head=12   (непрочитані: комірки 10, 11)

головний код:   rb_pop, рядок 1 → *out = buf[10]   (tail ЩЕ 10)
   ⚡ сюди влітає переривання:
ISR:            rb_push(0x41)
                rb_full? (12+1=13) == 10? ні → є місце
                buf[12] = 0x41                      (пише в 12 — далеко від 10)
                head = 13                           (рухає СВІЙ покажчик)
   ⚡ переривання вийшло, головний код продовжує:
головний код:   rb_pop, рядок 2 → tail = 11         (рухає СВІЙ покажчик)

стан після:     tail=11, head=13   (непрочитані: комірки 11, 12)
```

Жодного зіпсутого байта. Переривання писало в комірку 12 і чіпало лише `head`; читач читав комірку 10 і чіпав лише `tail`. Вони **фізично не перетнулися** ні на комірці пам'яті, ні на покажчику. Прочитаний байт (`buf[10]`) коректний, новий байт (`0x41`) ліг на місце, обидва покажчики зрушили правильно. Саме тому «один писач рухає head останнім, один читач рухає tail останнім» працює **без** вимикання переривань — а вимикати їх у драйвері лінії якраз і не хочеться, бо це додає затримок усьому іншому.

## Скільки пам'яті брати й де схема ламається

Розмір буфера — не «чим більше, тим краще», а **порахована** величина: він має пережити найдовшу паузу, на яку головний код може застрягнути, не вичитуючи лінію. Прикидка проста — швидкість лінії в байтах за секунду, помножена на найгіршу затримку. На 115200 8N1 це ≈ 11520 байт/с; якщо запис у flash раз у раз блокує цикл на 10 мс, за цей час прилетить близько 115 байтів — отже, 256-байтовий буфер (степінь двійки, найближча зверху) має комфортний запас. Якщо ж застосунок читає лінію щотакту й ніколи не блокується надовго, вистачить і 64 байтів: великий буфер тоді просто марнує дефіцитну на мікроконтролері пам'ять.

Чесно про межу схеми: уся ця безблокувальність спирається на **один процесор з одним ядром** (точніше — на те, що писач і читач бачать пам'ять у єдиному, узгодженому порядку). На однокристальному МК з одним ядром, де переривання просто витісняє головний код на тому ж процесорі, `volatile` і «рухай свій покажчик останнім» — цього досить. Але на **двоядерному** чипі (як ESP32), коли переривання обслуговує одне ядро, а читач крутиться на іншому, самого `volatile` вже **замало**: ядра можуть побачити записи в різному порядку, і потрібен бар'єр пам'яті (англ. *memory barrier* — «бар'єр упорядкування доступів до пам'яті») або готовий потокобезпечний примітив із бібліотеки. Для класичного «одне переривання UART → головний цикл» однопроцесорна модель тримається; щойно з'являється друге ядро чи друга задача — берись за атомарні засоби, а не за саморобне кільце.

## Граблі

Помилки тут тихі: код проходить тести на столі, а в полі під навантаженням починає зрідка губити чи плутати байти.

- **Спільний `count`.** Лічильник, який інкрементує писач і декрементує читач, — класичне джерело гонитви: `count±±` не атомарний. Два окремі покажчики, кожен під одним господарем, прибирають проблему в корені.
- **Просунути покажчик ПЕРШИМ.** Якщо `rb_push` зрушить `head` до запису комірки (або `rb_pop` зрушить `tail` до читання), протилежний бік на мить побачить «готовий» байт, якого ще нема, — і прочитає сміття. Покажчик рухають **останньою** дією.
- **Забути `volatile`.** Без нього компілятор має право закешувати `head`/`tail` у регістрі й не помітити змін із переривання — цикл очікування байта зависне назавжди, хоч дані вже надійшли. Покажчики, які змінює ISR, **завжди** `volatile`.
- **Плутати «повно» і «порожньо».** Якщо дозволити `head` зійтися з `tail` упритул, обидва стани зіллються. Або жертвуй одною коміркою (`rb_full` дивиться на крок наперед), або тримай окремий безпечний лічильник — але не лишай двозначності.
- **Місткість не степінь двійки.** Тоді замість дешевої маски `& (N−1)` доведеться рахувати справжній залишок `% N` — ділення, яке на дрібному МК коштує десятки тактів **у кожному** перериванні. Бери 64, 128, 256.
- **Два писачі або два читачі.** Уся схема тримається на «один писач, один читач». Якщо в буфер пишуть два переривання (або читають дві задачі), безблокувальна гарантія зникає — тут уже потрібні атомарні операції чи коротке вимикання переривань навколо зміни покажчика.
