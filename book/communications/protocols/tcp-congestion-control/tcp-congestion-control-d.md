# Керування заторами TCP

<preknowlist>
- [Протокол TCP](book:communications/tcp-vs-udp) — надійне потокове з'єднання, послідовності байтів, підтвердження ACK та ковзне вікно.
- [Керування потоком](book:communications/flow-control) — обмеження швидкості передавача розміром буфера приймача (rwnd).
</preknowlist>

Жовтневого дня 1986 року мережева магістраль між Національною лабораторією імені Лоуренса в Берклі та Університетом Каліфорнії раптово зазнала катастрофічного падіння пропускної здатності. Лінія зв'язку зі швидкістю 400 кбіт/с провалилася до реальної швидкості у 40 біт на секунду. Корисний потік даних зменшився у 10 000 разів: мережа фактично зупинилася, хоча фізичні лінії, приймачі й передавачі залишалися повністю справними. Ця подія увійшла в історію комп'ютерних мереж під назвою колапсу заторів (Congestion Collapse). Вона викрила фундаментальну прогалину у початковому проектуванні протоколу TCP: наявний механізм керування потоком захищав буфер приймача, але абсолютно нічого не знав про спроможність проміжних маршрутизаторів пропустити згенерований трафік.

Контроль заторів (англ. *congestion control*) — це комплекс алгоритмів, за допомогою яких передавач TCP динамічно з'ясовує доступну ємність усієї транзитної мережі й адаптує свою швидкість так, щоб максимально завантажити канал, не викликаючи переповнення буферів у маршрутизаторах.

## Фізика заторів: теорія масового обслуговування та виникаюча нелінійність

Щоб зрозуміти, чому мережа під навантаженням раптово втрачає продуктивність, слід звернутися до теорії масового обслуговування. Маршрутизатор у мережі Інтернет моделюється як система масового обслуговування з скінченною чергою (модель M/M/1/K). Пакети надходять з інтенсивністю `λ` (пакетів на секунду), а вихідний канал обробляє їх із максимальною швидкістю `μ` пакетів/с.

Коефіцієнт завантаження каналу `ρ` визначається як:

```
ρ = λ / μ
```

Згідно із Законом Літтла (Little's Law), середня затримка пакета в буфері маршрутизатора `D` залежить від коефіцієнта `ρ` нелінійно:

```
D = 1 / (μ - λ) = (1 / μ) · (1 / (1 - ρ))
```

Коли навантаження каналу `ρ` є малим (`ρ < 0.7`), затримка `D` практично дорівнює чистому часу передачі кадру по фізичному кабелю. Проте коли інтенсивність вхідного трафіку `λ` наближається до максимальної ємності `μ` (`ρ → 1`), заменник `(1 - ρ)` прямує до нуля, і затримка в буфері **зростає експоненціально до нескінченності**.

```
Затримка D (мс)
  ▲
  │                                     / (Експоненціальний вибух)
  │                                    /
  │                                   /
  │                                 .'
  │                              .-'
  │                     _ . -  '
  ┼────────────────────┴───────────────┴────► Завантаження ρ = λ / μ
  0                   0.7             1.0
```

Якщо буфер маршрутизатора є скінченним (ємністю `K` пакетів), то при `ρ > 1` черга заповнюється на 100%, і кожен наступний пакет мовчки скидається. Якщо відправники у відповідь на втрати починають агресивно відправляти повторні пакети, інтенсивність `λ` зростає ще більше, створюючи неконтрольовану самопосилювану петлю затору.

## Двовимірне обмеження: rwnd проти cwnd

Для забезпечення надійної та плавної передачі даних передавач TCP мусить враховувати два принципово різних обмеження:

1. **Керування потоком (Flow Control):** Захищає **приймач**. Приймач повідомляє передавачеві розмір свого вільного приймального буфера через поле `rwnd` (англ. *Receiver Window*) у заголовку кожного пакета ACK. Це явна, пряма команда: «у мене лишилося місце лише на 64 кілобайти».
2. **Керування заторами (Congestion Control):** Захищає **проміжну мережу**. Оскільки маршрутизатори в Інтернеті не надсилають кожному передавачу явних повідомлень про свій стан, передавач змушений самостійно обчислювати динамічну змінну — вікно заторів `cwnd` (англ. *Congestion Window*).

Реальний обсяг даних, який передавач має право відправити в мережу без отримання підтвердження (так зване ефективне вікно передачі `W`), визначається як мінімум із цих двох величин:

```
W = min(cwnd, rwnd)
```

Якщо приймач має гігабайтний буфер (`rwnd = 1 GB`), але вузьке місце десь на маршрутизаторі в Інтернеті здатно пропустити лише 10 мегабіт на секунду, підсумкове вікно `W` буде повністю обмежене змінною `cwnd`. І навпаки: якщо мережа вільна, але мобільний телефон-приймач не встигає вичитати дані з сокета, передачу стримуватиме `rwnd`.

```
Передавач TCP                    Проміжна мережа                 Приймач TCP
  (Sender)                    (Маршрутизатори)                  (Receiver)
      │                              │                               │
      │──── Вікно заторів cwnd ─────►│                               │
      │     (Оцінка пропускної       │                               │
      │      здатності каналу)       │                               │
      │                              │──── Вікно приймача rwnd ─────►│
      │                              │     (Явний розмір буфера)     │
      │                              │                               │
      ▼                              ▼                               ▼
                       Ефективне вікно: W = min(cwnd, rwnd)
```

Головна складність керування заторами полягає в тому, що Інтернет для передавача є «чорною скринькою». Передавач бачить лише свій сокет і надходження підтверджень ACK від адресата. З цього скупого потоку зворотного зв'язку він мусить неперервно оцінювати стан сотень проміжних комутаторів та маршрутизаторів.

## Принцип збереження пакетів та чотири класичні алгоритми (RFC 5681)

У 1988 році Ван Якобсон сформулював **Принцип збереження пакетів** (англ. *Packet Conservation Principle*): стабільне з'єднання перебуває в стані рівноваги, коли новий пакет вводиться в мережу лише тоді, коли старий пакет залишає її.

Підтвердження ACK, що повертається від приймача, є не просто сигналом про успішне отримання байтів, а й «годинниковим імпульсом» (англ. *self-clocking*), який показує, що з мережі вийшов один пакет, отже, звільнилося місце для нового.

Для підтримки цієї рівноваги специфікація RFC 5681 визначає чотири класичні алгоритми, які працюють як єдиний кінцевий автомат: **Повільний старт**, **Уникання заторів**, **Швидка повторна передача** та **Швидке відновлення**.

![Пилоподібна динаміка вікна заторів](/book/communications/protocols/tcp-congestion-control/img/cwnd-sawtooth.svg)
*Пилоподібна динаміка розміру вікна заторів (cwnd) під час повільного старту, лінійного уникання заторів AIMD та швидкого відновлення.*

### 1. Повільний старт (Slow Start)

Коли TCP-з'єднання тільки відкривається, передавач не знає пропускної здатності каналу. Починати одразу з великої швидкості небезпечно — це миттєво переповнить буфери маршрутизаторів.

Передавач ініціалізує `cwnd` малим значенням (історично `1 MSS`, у сучасних системах `10 MSS`, де `MSS` — Maximum Segment Size, зазвичай 1460 байтів) і встановлює початковий поріг повільного старту `ssthresh` у максимально можливе значення (наприклад, 65 535 байтів).

На етапі повільного старту за кожне отримане підтвердження ACK розмір `cwnd` збільшується на 1 MSS:

```
[при отриманні нового ACK у режимі Slow Start]
cwnd = cwnd + 1 MSS
```

Оскільки за один RTT передавач надсилає `cwnd` пакетів і отримує на них `cwnd` підтверджень ACK, розмір вікна **подвоюється з кожним кругом RTT**:

```
RTT 1: cwnd = 1 MSS   ──► передано 1 пакет  ──► отримано 1 ACK  ──► cwnd = 2 MSS
RTT 2: cwnd = 2 MSS   ──► передано 2 пакети ──► отримано 2 ACK  ──► cwnd = 4 MSS
RTT 3: cwnd = 4 MSS   ──► передано 4 пакети ──► отримано 4 ACK  ──► cwnd = 8 MSS
```

Попри назву «повільний», зростання тут є експоненціальним. Повільним він називається лише тому, що починає з одного сегмента. Експоненціальний розгін триває доти, доки `cwnd` не досягне порогу `ssthresh` або в мережі не станеться втрата пакета.

### 2. Уникання заторів (Congestion Avoidance / AIMD)

Коли `cwnd >= ssthresh`, передавач вважає, що він наблизився до безпечної межі ємності каналу. Подальше експоненціальне зростання спричинить затор. Передавач перемикається в режим **Уникання заторів**.

У цьому режимі експоненціальний розгін змінюється на помірне **лінійне зростання**. Мета — збільшувати вікно приблизно на `1 MSS` за один повний круг RTT, незалежно від того, на скільки окремих ACK було розбито підтвердження:

```
[при отриманні нового ACK у режимі Congestion Avoidance]
cwnd = cwnd + MSS · (MSS / cwnd)
```

При отриманні `cwnd / MSS` підтверджень сумарне приростання складає рівно `1 MSS`. Ця стратегія відповідає принципу **аддитивного збільшення** (англ. *Additive Increase*).

Якщо ж у мережі відбувається втрата пакета, передавач застосовує **мультиплікативне зменшення** (англ. *Multiplicative Decrease*): встановлює поріг `ssthresh` в половину поточного розміру `cwnd` (але не менше ніж `2 MSS`):

```
ssthresh = max(cwnd / 2, 2 · MSS)
```

Комбінація цих двох правил утворює класичну модель **AIMD** (Additive Increase Multiplicative Decrease), яка формує характерний пилоподібний графік швидкості TCP.

### 3. Швидка повторна передача (Fast Retransmit)

У перших реалізаціях TCP єдиним сигналом втрати пакета був тайм-аут повторної передачі (RTO). Якщо пакет втрачався, передавач мовчки чекав завершення таймера (який часто становив від 500 мс до кількох секунд), що призводило до тривалих простоїв.

Алгоритм Fast Retransmit (RFC 5681) використовує властивість приймача надсилати дубльовані ACK (англ. *duplicate ACK*, або `dupACK`). Якщо пакети №1, №2, №3, №4 надсилаються підряд, але пакет №2 втрачається, приймач отримує №1, а потім №3. Оскільки №3 прийшов із порушенням порядку, приймач не може підтвердити його новим номером — він знову надсилає `ACK 2`, сигналізуючи: «я все ще чекаю на пакет №2». При надходженні пакета №4 приймач знову надсилає `ACK 2`.

Отримання **трьох однакових дубльованих ACK** підпільним чином вказує передавачеві: пакет №2 точно втрачено, але наступні пакети (№3 та №4) успішно пройшли через мережу. Передавач негайно повторно надсилає втрачений пакет №2, не чекаючи спрацьовування таймера RTO.

```
Передавач                                                        Приймач
    │ ── Пакет 1 ───────────────────────────────────────────────► │ (ОК, ACK 2)
    │ ── Пакет 2 (ВТРАЧЕНО У МЕРЕЖІ) ──X                         │
    │ ── Пакет 3 ───────────────────────────────────────────────► │ (Поза порядком! dupACK 2)
    │ ── Пакет 4 ───────────────────────────────────────────────► │ (Поза порядком! dupACK 2)
    │ ── Пакет 5 ───────────────────────────────────────────────► │ (Поза порядком! dupACK 2)
    │                                                             │
    │ (Отримано 3x dupACK 2! Швидка повторна передача)            │
    │ ── Повтор Пакета 2 ───────────────────────────────────────► │ (ОК, розблоковано! ACK 6)
```

### 4. Швидке відновлення (Fast Recovery)

Після того, як 3 dupACK спричинили швидку повторну передачу, передавачеві недоцільно скидати `cwnd` до 1 MSS і знову проходити Slow Start, адже факт приходу трьох dupACK доводить, що мережа все ще здатна пропускати пакети.

Алгоритм Fast Recovery регулює `cwnd` так:
1. `ssthresh = max(cwnd / 2, 2 * MSS)`
2. `cwnd = ssthresh + 3 * MSS` (враховуємо 3 пакети, які залишили мережу й згенерували 3 dupACK)
3. Кожен наступний `dupACK` збільшує `cwnd` ще на `1 MSS`, дозволяючи відправляти нові пакети.
4. Як тільки надходить **новий ACK**, який підтверджує повторно надіслані дані, передавач встановлює `cwnd = ssthresh` і повертається в режим лінійного уникання заторів (Congestion Avoidance).

## Математична стійкість AIMD та модель Матіса

Чому саме комбінація аддитивного збільшення та мультиплікативного зменшення (AIMD) стала основою протоколу TCP, а не, наприклад, мультиплікативне збільшення чи аддитивне зменшення?

У 1989 році Дхамака Чіу та Радж Джейн провели математичний аналіз збіжності розподілу ресурсів у мережі. На фазовій площині для двох потоків із швидкостями `x₁` та `x₂` лінія ефективності задається як `x₁ + x₂ = C`, а лінія справедливості — як `x₁ = x₂`.

![Фазова діаграма Чіу-Джейна](/book/communications/protocols/tcp-congestion-control/img/aimd-phase-plane.svg)
*Векторна фазова діаграма Чіу-Джейна: доведення збіжності двох потоків під впливом AIMD до лінії справедливості та лінії ємності.*

Як видно з фазової діаграми:
- **Аддитивне збільшення (+1, +1)** зсуває стан системи паралельно лінії 45°, що зменшує відносний розрив між потоками.
- **Мультиплікативне зменшення (×0.5, ×0.5)** спрямовує вектор строго в початок координат `(0,0)`, зберігаючи кут відношення швидкостей, але зменшуючи абсолютну відстань до лінії справедливості вдвічі.

Будь-які інші комбінації (AIAD, MIMD, MIAD) або не збігаються до лінії справедливості, або роблять систему нестабільною.

На основі властивостей AIMD Метт Матіс у 1997 році вивів математичну формулу граничної пропускної здатності TCP залежно від ймовірності втрати пакетів `p` та часу зворотного шляху `RTT`:

```
BW ≤ (1.22 · MSS) / (RTT · √p)
```

Ця формула показує фундаментальне обмеження класичного TCP: якщо в каналі з RTT 50 мс ймовірність втрати пакетів складає `p = 0.01` (1%), то швидкість з'єднання фізично не зможе перевищити ~28.5 Мбіт/с, навіть якщо фізичний канал є гігабітним.

> Повний математичний доказ збіжності Чіу-Джейна та виведення формули Матіса наведено у вставці [🧮 Аналіз стійкості AIMD та модель продуктивності Матіса](book:communications/tcp-congestion-control/math-aimd-stability.md).

## Еволюція Loss-based алгоритмів: Tahoe, Reno, NewReno, CUBIC

Зі зростанням швидкостей мереж та появою оптичних ліній зв'язку класичні алгоритми зазнавали постійної модифікації.

### Порівняльне сімейство Loss-based алгоритмів

| Алгоритм | Рік | Реакція на 3x dupACK | Реакція на RTO (Тайм-аут) | Головний профіль застосування |
|---|---|---|---|---|
| **TCP Tahoe** | 1988 | `ssthresh = cwnd/2`, `cwnd = 1 MSS` (Slow Start) | `ssthresh = cwnd/2`, `cwnd = 1 MSS` | Історичний перший алгоритм |
| **TCP Reno** | 1990 | `ssthresh = cwnd/2`, Fast Recovery (`cwnd = ssthresh + 3 MSS`) | `ssthresh = cwnd/2`, `cwnd = 1 MSS` | Стандарт RFC 5681, класичний Інтернет |
| **TCP NewReno** | 1999 | Уточнений Fast Recovery для обробки кількох втрат за один RTT | `ssthresh = cwnd/2`, `cwnd = 1 MSS` | RFC 6582, усунення провалів Reno |
| **TCP CUBIC** | 2006 | Збереження `W_max`, кубічна функція відновлення `W(t)` | `ssthresh = cwnd/2`, `cwnd = 1 MSS` | Стандарт ядра Linux (RFC 8312), мережі з високим BDP |

### Проблема високошвидкісних каналів (High BDP)

Добуток пропускної здатності на затримку (англ. *Bandwidth-Delay Product*, BDP) визначає обсяг даних, який «знаходиться в польоті» в мережевому трубопроводі:

```
BDP = Bandwidth · RTT
```

На сучасних міжконтинентальних оптичних каналах (наприклад, 10 Gbit/s із RTT 200 мс) значення BDP становить:

```
BDP = 10 000 000 000 біт/с · 0.2 с = 2 000 000 000 біт = 250 Мегабайтів
```

Для заповнення такого каналу вікно `cwnd` має становити близько 170 000 сегментів. Якщо на такому каналі алгоритм TCP Reno втрачає один пакет, вікно зменшується вдвічі (до 85 000 сегментів). При лінійному збільшенні на 1 MSS за RTT алгоритму Reno знадобиться 85 000 RTT для відновлення колишньої швидкості:

```
Час відновлення Reno = 85 000 · 0.2 с = 17 000 секунд ≈ 4.7 години!
```

Це робить AIMD абсолютно непридатним для сучасних високошвидкісних мереж.

### TCP CUBIC: кубічна функція вікна

Щоб розв'язати проблему довгого відновлення у мережах із високим BDP, у 2006 році було розроблено алгоритм **CUBIC** (RFC 8312).

Замість того, щоб прив'язувати зростання вікна до надходження ACK та часу RTT, CUBIC розраховує розмір вікна як **кубічну функцію часу `t`**, що минув із моменту останньої втрати пакетів:

```
W_cubic(t) = C · (t - K)³ + W_max
```

де:
- `W_max` — розмір вікна заторів безпосередньо перед останньою втратою;
- `C` — постійний коефіцієнт масштабування;
- `K` — часовий інтервал, необхідний для збільшення вікна від початкового після скорочення до `W_max`:
  ```
  K = ∛(W_max · β / C)
  ```

Графік кубічної функції має характерну **S-подібну форму**:

```
Вікно cwnd
  ▲
  │                                      / (Швидке зондування)
  │                                     /
W_max ├───────────────.───────────────'  (Плато безпеки)
  │                  / \
  │                 /   \
  │                /     (Втрата!)
  │  _.-'        /
  ┼─────────────┼───────────────────────► Час t
  0             K
```

1. **Фаза швидкого зростання:** Одразу після втрати вікно стрімко зростає, швидко наближаючись до попереднього стабільного значення `W_max`.
2. **Фаза плато (Plateau):** Наближаючись до `W_max`, зростання сповільнюється до майже нуля. Система обережно випробовує мережу навколо попередньої точки затору, не викликаючи повторного сплеску втрат.
3. **Фаза дослідження (Probing):** Якщо за період перебування на плато втрат не сталося, кубічна функція починає стрімко вигинатися вгору, зондуючи наявність нової вільної смуги в мережі.

Завдяки тому, що функція `W(t)` залежить від фізичного часу `t`, а не від кількості RTT, CUBIC є абсолютно **іваріантним до RTT** і забезпечує чесну конкуренцію між короткими та довгими потоками. З 2006 року CUBIC є алгоритмом за замовчуванням у ядрі Linux.

## Буферне роздування (Bufferbloat) та Model-based контролери (BBR)

Усі розглянуті вище алгоритми (Tahoe, Reno, NewReno, CUBIC) належать до класу **Loss-based** — вони вважають єдиним сигналом затору втрату пакета. Проте цей підхід містить приховану фундаментальну ваду.

### Криза Bufferbloat

Зі здешевленням оперативної пам'яті виробники маршрутизаторів почали вбудовувати в пристрої величезні буфери кадрів (від мегабайтів до гігабайтів).

Коли Loss-based алгоритм (CUBIC чи Reno) збільшує `cwnd`, він продовжує нарощувати швидкість навіть тоді, коли вузький канал уже працює на 100% своєї фізичної ємності. Усі «зайві» пакети не втрачаються, а осідають у гігантському буфері маршрутизатора.

![Заповнення буферів у Loss-based та BBR](/book/communications/protocols/tcp-congestion-control/img/bufferbloat-bbr.svg)
*Порівняння заповнення буферів маршрутизаторів у Loss-based алгоритмах (Reno/CUBIC) та Model-based (BBR).*

В результаті виникає явище **Bufferbloat** (буферне роздування):
- Пропускна здатність не зростає (вона вперлася в стелю каналу).
- Затримка RTT катастрофічно зростає (від 20 мс до 2000 мс), оскільки пакети годинами просідають у довжелезній черзі буфера.
- Втрата пакета стається лише тоді, коли гігантський буфер нарешті переповнюється (англ. *tail drop*).

Loss-based алгоритми працюють у найгіршій точці — у точці **максимальної затримки та переповненого буфера**.

### BBR: Модельний контроль заторів (Bottleneck Bandwidth and RTT)

У 2016 році інженери Google (Ніл Кардвелл, Ван Якобсон та ін.) представили новий алгоритм — **BBR** (Bottleneck Bandwidth and Round-trip propagation time).

BBR повністю відмовляється від використання втрат пакетів або заповнення буферів як первинного сигналу затору. Натомість BBR неперервно будує **фізичну модель мережевого каналу**, вимірюючи дві фундаментальні величини:

1. **`BtlBw` (Bottleneck Bandwidth):** Максимальна виміряна швидкість доставки пакетів за останні кілька RTT.
2. **`RTprop` (Round-Trip Propagation Time):** Мінімальна виміряна затримка фізичного каналу без урахування черг у буферах.

Оптимальний обсяг даних у польоті (BDP) для мінімальної затримки та максимальної швидкості розраховується як:

```
BDP_opt = BtlBw · RTprop
```

### Стан кінцевого автомата BBR

BBR регулює не лише розмір вікна `cwnd`, а й **швидкість пейсингу** (англ. *pacing rate*) — інтервал часу між відправкою окремих пакетів на рівні мережевої карти:

```
pacing_rate = pacing_gain · BtlBw
cwnd = cwnd_gain · BDP_opt
```

Автомат BBR циклічно проходить чотири стани:

```
  ┌──────────────┐
  │   STARTUP    │  ──► Експоненціальний розгін (pacing_gain = 2.89)
  └──────┬───────┘
         │ (до виявлення плато пропускної здатності)
         ▼
  ┌──────────────┐
  │    DRAIN     │  ──► Скидання накопиченої черги в буфері (pacing_gain = 0.35)
  └──────┬───────┘
         │ (до очищення черги RTT -> RTprop)
         ▼
  ┌──────────────┐      ┌──────────────┐
  │   PROBE_BW   │ ◄──► │  PROBE_RTT   │
  └──────────────┘      └──────────────┘
  Циклічне випробовування  Периодичне очищення буфера
  смуги (8-кроковий фазовий  до 4 пакетів для вимірювання
  цикл pacing_gain)        чистого RTprop (раз на 10 с)
```

BBR забезпечує високу швидкість передачі при мінімальній затримці, що робить його ідеальним для відеострімінгу (YouTube), сервісів Google та хмарних систем.

## Активне керування чергами (AQM) та Explicit Congestion Notification (ECN)

Боротьба із заторами вимагає сприяння не лише від кінцевих хостів, а й від самих маршрутизаторів.

### Алгоритми AQM (Active Queue Management)

Замість пасивного чекання переповнення буфера (`Tail Drop`), сучасні маршрутизатори застосовують алгоритми активного керування чергами:

- **RED (Random Early Detection):** Маршрутизатор починає випадковим чином скидати невеликий відсоток пакетів ще до повного заповнення буфера, коли середня довжина черги перевищує перший поріг.Це змушує передавачі TCP завчасно зменшити вікно `cwnd`.
- **CoDel (Controlled Delay):** Оцінює не кількість пакетів у буфері, а **час перебування** пакета в черзі. Якщо мінімальна затримка пакета в черзі перевищує 5 мс протягом 100 мс, CoDel скидає пакет на виході з черги.
- **FQ-CoDel:** Комбінує справедливу черговість (Fair Queueing) для окремих потоків із алгоритмом CoDel, захищаючи інтерактивний трафік (DNS, VoIP, SSH) від монополізації місткими файловими завантаженнями.

### Явне повідомлення про затор ECN (RFC 3168)

Механізм **ECN** (Explicit Congestion Notification) дозволяє маршрутизатору попереджати хости про виникнення затору **без скидання пакетів**.

ECN використовує 2 біти в полі DiffServ/TOS заголовка IPv4/IPv6 та прапорці в заголовку TCP:

```
Заголовок IP (поле ECN - 2 біти):
  00: ECN не підтримується (Not-ECT)
  01 або 10: Хости підтримують ECN (ECT - ECN-Capable Transport)
  11: Маршрутизатор зафіксував затор (CE - Congestion Encountered)

Заголовок TCP (прапорці ECE та CWR):
  ECE (ECN-Echo): Приймач повідомляє передавача про отримання IP-пакета з маркуванням CE (11).
  CWR (Congestion Window Reduced): Передавач підтверджує зменшення вікна cwnd у відповідь на ECE.
```

```
Передавач TCP                   Маршрутизатор (AQM/ECN)              Приймач TCP
    │                                     │                               │
    ├────── IP: ECT (01), TCP ───────────►│                               │
    │                                     │ (Виявлено затор! Маркує CE)   │
    │                                     ├────── IP: CE (11), TCP ──────►│
    │                                     │                               │ (Бачить CE = 11!)
    │◄───── IP, TCP: ECE = 1 ─────────────┴───────────────────────────────┤ (Надсилає ECE в ACK)
    │
    │ (Реагує: зменшує cwnd як при втраті!)
    ├────── IP: ECT (01), TCP: CWR = 1 ──────────────────────────────────►│ (Підтверджує реакцію)
```

Завдяки ECN мережа позбавляється потреби втрачати пакети для регулювання швидкості, що повністю усуває затримки на повторне надсилання.
