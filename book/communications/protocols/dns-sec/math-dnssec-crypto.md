# 🧮 Криптографічне підґрунтя DNSSEC: підписи, хеші та канонічне сортування

Ця математична вставка містить формалізацію алгоритмів цифрового підпису, функцій криптографічного хешування, алгебри еліптичних кривих, матричних операцій у решітках та лексикографічного порядкового сортування, що складають криптографічну основу підтвердження цілісності у DNSSEC.

## 1. Математична модель набору записів RRset та канонічного перед-зображення

У протоколі DNSSEC криптографічний підпис створюється не над окремим записом, а над усім набором записів одного типу та одного імені власника — `RRset`.

Нехай `S` — набір із `k` записів ресурсу одного типу `T` для доменного імені `N`:

```text
S = { R₁, R₂, ..., Rₖ }
```

Кожен запис `R_i` визначається трійкою `(N, T, RDATA_i)`, де `N` — ім'я власника, `T` — числовий тип запису (наприклад, `T = 1` для типу A), а `RDATA_i` — сирий масив байтів даних `i`-го запису.

### Канонічна трансформація запису C(R_i)

Для усунення неоднозначностей у двійковому представленні кожен запис `R_i` піддається канонічній трансформації `C(R_i)`:
1. Ім'я власника `N` перетворюється на канонічну форму `N_canon`, де всі ASCII-символи у верхньому регістрі замінюються на нижній регістр (`A-Z` → `a-z`).
2. Значення часу життя `TTL` замінюється на фіксоване поле `TTL_orig` із заголовка підпису `RRSIG`.

### Лексикографічне сортування записів

Масив канонізованих записів `C(S) = (C(R_π(1)), C(R_π(2)), ..., C(R_π(k)))` впорядковується за допомогою бінарного порівняльного оператора `≺`:

```text
C(R_i) ≺ C(R_j)  ⇔  RDATA_i < RDATA_j  [побайтове порівняння беззнакових uint8_t зліва направо]
```

Якщо `RDATA_i` є початковим префіксом `RDATA_j` (тобто довжина `L_i < L_j` при побайтовому збігу перших `L_i` байтів), то `C(R_i) ≺ C(R_j)`.

### Доведення детермінованості сортування RRset

Теорема: для будь-якої перестановки `π` записів у наборі `S`, канонічна трансформація та сортування оператором `≺` продукують єдиний детермінований масив `C(S)_sorted`.

Доведення: Оскільки оператор побайтового порівняння `≺` над скінченними послідовностями байтів беззнакових цілих чисел `uint8_t` задовольняє три властивості строгого часткового порядку (антисиметричність, транзитивність, антирефлексивність), а всі `RDATA` у межах одного запису є унікальними (RFC 2181 вимагає вилучення точних дублікатів з RRset), порядок сортування є строгим лінійним порядком. Отже, вихідний буфер є єдиним для всіх сертифікованих реалізацій DNSSEC.

### Побудова підписуваного перед-зображення (Preimage M)

Підписуваний бінарний буфер `M` формується шляхом конкатенації (послідовного додавання байтів, позначеного символом `∥`):

```text
M = RRSIG_RDATA_Header ∥ N_canon ∥ RDATA_1 ∥ RDATA_2 ∥ ... ∥ RDATA_k
```

де `RRSIG_RDATA_Header` складається з 18 фіксованих байтів заголовка `RRSIG`:

```text
RRSIG_RDATA_Header = TypeCovered (2B) ∥ Algorithm (1B) ∥ Labels (1B) ∥ 
                     OriginalTTL (4B) ∥ Expiration (4B) ∥ Inception (4B) ∥ 
                     KeyTag (2B) ∥ SignerName_canon
```

## 2. Математичний розрахунок відповідності групи символів (Wildcard Synthesis)

Якщо запис у зоні згенеровано за допомогою шаблону `*.example.com.`, а запит надійшов до імені `a.b.example.com.`, кількість міток у підписуваному перед-зображенні визначається полем `Labels` запису `RRSIG`.

Формально, якщо початкове ім'я має `L_real` міток (наприклад, `a.b.example.com.` має 3 мітки, не враховуючи корінь), а поле `Labels` дорівнює `L_sig = 2`, валідатор зрізає найлівіші `L_real - L_sig` міток і замінює ліву мітку на `*`.

Формула трансформації імені для перед-зображення:

```text
N_preimage = "*" ∥ Labels_from_right(N_canon, L_sig)
```

У нашому прикладі `L_real - L_sig = 3 - 2 = 1` мітка (`a`) видаляється, і замість неї у перед-зображення підставляється `*.example.com.`. Це забезпечує суворий доказовий збіг хешу для всіх груп символів.

## 3. Ймовірнісна модель атак отруєння кешу та парадокс днів народження

Оцінимо криптографічну стійкість класичного DNS без DNSSEC проти атак отруєння кешу за моделлю Камінські.

Нехай `N_tx = 2¹⁶ = 65536` — кількість можливих ідентифікаторів транзакцій, а `N_port = 2¹⁶ = 65536` — кількість можливих вихідних портів UDP.

1. **Без рандомізації портів (класичний DNS):**
   При фіксованому порту атакуючий надсилає `B` підроблених відповідей на 1 запит резолвера. Імовірність `P_poison` успішного отруєння кешу з першої спроби:
   ```text
   P_poison = B / N_tx = B / 65536
   ```
   Якщо `B = 500`, імовірність становить ≈ 0.76%. При повторенні `m` запитів до неіснуючих субдоменів імовірність успіху за `m` спроб наближається до одиниці:
   ```text
   P_total = 1 - (1 - B / N_tx)ᵐ
   ```
   При `m = 1000` спробах `P_total = 1 - (1 - 500/65536)¹⁰⁰⁰ ≈ 99.97%`. Атака здійснюється за пару секунд.

2. **Із рандомізацією портів (RFC 5452):**
   Ентропія зростає до `N_total = N_tx · N_port = 2³² ≈ 4.29 × 10⁹`. Для досягнення 50% імовірності за парадоксом днів народження потрібно:
   ```text
   m_50% ≈ √(2 · N_total · ln(2)) ≈ √(2 · 2³² · 0.693) ≈ 77160 запитів
   ```

3. **DNSSEC захист:**
   З DNSSEC імовірність успішної підробки визначається стійкістю криптографічного підпису. Для ECDSA P-256 імовірність вгадування становить `2⁻²⁵⁶ ≈ 8.6 × 10⁻⁷⁸`, що робить фізичний замах неможливим за законами термодинаміки Всесвіту.

## 4. Математика RSA-підписів (алгоритм 8 RSASHA256)

Історичним та розповсюдженим криптографічним алгоритмом у DNSSEC є RSA з хешуванням SHA-256 (RFC 5702).

### Генерація ключів RSA

1. Вибираються два великі випадкові прості числа `p_rsa` та `q_rsa` рівної розрядності (наприклад, по 1024 біти для 2048-бітного ключа).
2. Обчислюється модуль `N_rsa = p_rsa · q_rsa`.
3. Обчислюється функція Ейлера `φ(N_rsa) = (p_rsa - 1) · (q_rsa - 1)`.
4. Вибирається публічна експонента `e`, взаємно проста з `φ(N_rsa)` (типово `e = 65537 = 2¹⁶ + 1`).
5. Обчислюється приватна експонента `d_rsa` як мультиплікативна інверсія `e (mod φ(N_rsa))`:
   ```text
   d_rsa · e ≡ 1  (mod φ(N_rsa))
   ```

### Створення та перевірка підпису RSA PKCS#1 v1.5

Для підписання перед-зображення `M`:
1. Обчислюється хеш `H = SHA-256(M)`.
2. Формується набивка PKCS#1 v1.5 (DigestInfo structure):
   ```text
   EM = 0x00 ∥ 0x01 ∥ 0xFF ∥ ... ∥ 0xFF ∥ 0x00 ∥ AlgorithmIdentifier ∥ H
   ```
3. Обчислюється цифровий підпис `S_rsa` через зведення у степінь за модулем `N_rsa`:
   ```text
   S_rsa = (EM)^d_rsa mod N_rsa
   ```

Перевірка підпису валідатором здійснюється зворотним зведенням у степінь публічною експонентою `e`:
```text
EM' = (S_rsa)^e mod N_rsa
```
Підпис є дійсним, якщо розпакований масив `EM'` побайтово відповідає структурі DigestInfo для хешу SHA-256 від перед-зображення `M`.

## 5. Криптографія еліптичних кривих: ECDSA P-256 та P-384 (алгоритми 13 та 14)

Для створення цифрового підпису у сучасному DNSSEC застосовується алгоритм ECDSA над поверненою кривою secp256r1 (NIST P-256) або secp384r1 (NIST P-384).

### Алгебра кривої над скінченним полем F_p

Крива визначена канонічним рівнянням Вейєрштрасса над простим полем `F_p`:

```text
y² ≡ x³ + a·x + b  (mod p)
```

де для P-256 параметри кривої задано як:
- Модуль поля `p = 2²⁵⁶ - 2²²⁴ + 2¹⁹² + 2⁹⁶ - 1` (просте число Доппельта-Мерсенна).
- Коефіцієнт `a = -3 ≡ p - 3 (mod p)`.
- Коефіцієнт `b = 0x5AC635D8AA3A93E7B3EBBD55769886BC651D06B0CC53B0F63BCE3C3E27D2604B`.
- Базова точка-генератор `G = (x_G, y_G)` порядку `n`, де `n` — просте число розміром 256 біт.

Для кривої P-384 (алгоритм 14) використовується хеш-функція SHA-384 та модуль поля `p_384 = 2³⁸⁴ - 2²⁸³ - 2⁹⁶ + 2³² - 1`. Збільшення розміру поля до 384 бітів підвищує математичну криптостійкість із 128 біт безпеки до 192 біт.

### Скалярне множення точок на кривій

Обчислення `k · G` виконується за допомогою ефективного алгоритму «Double-and-Add» або двійкового віконного методу (wNAF — Windowed Non-Adjacent Form).

Алгоритм Double-and-Add для скаляра `k = (k_{m-1} k_{m-2} ... k_0)_2`:

```text
R = O (Точка на нескінченності)
Для i від m-1 до 0:
  R = 2 · R  (Подвоєння точки: Point Doubling)
  Якщо k_i == 1:
    R = R + G  (Додавання точок: Point Addition)
Повернути R
```

Математичні формули подвоєння точки `P = (x_1, y_1)` у координатах Афінного простору:
```text
λ = (3·x₁² + a) / (2·y₁)  mod p
x₃ = λ² - 2·x₁  mod p
y₃ = λ·(x₁ - x₃) - y₁  mod p
```

### Схема генерації підпису (Signing Algorithm)

Для підписання повідомлення `M` за допомогою приватного ключа `d ∈ [1, n-1]`:
1. Обчислюється криптографічний хеш `h = SHA-256(M)`, який інтерпретується як ціле число `z`.
2. Вибирається випадкове криптографічно стійке число `k ∈ [1, n-1]` (одноразовий nonce).
3. Обчислюється точка кривої `P = (x_1, y_1) = k · G` через скалярне множення.
4. Обчислюється перша компонента підпису `r`:
   ```text
   r = x₁ mod n
   ```
   Якщо `r = 0`, вибирається нове випадкове `k`.
5. Обчислюється друга компонента підпису `s`:
   ```text
   s = k⁻¹ · (z + r · d) mod n
   ```
   Якщо `s = 0`, вибирається нове випадкове `k`.
6. Підпис DNSSEC RRSIG формується як конкатенація 32-байтових чисел `r` та `s`: `Signature = r ∥ s` (довжина 64 байти).

### Схема перевірки підпису (Verification Algorithm)

Для перевірки підпису `(r, s)` над повідомленням `M` за допомогою публічного ключа `Q = d · G`:
1. Перевіряється, що `r, s ∈ [1, n-1]`. Якщо ні — підпис недійсний.
2. Обчислюється хеш `z = SHA-256(M)`.
3. Обчислюється мультиплікативна інверсія `w = s⁻¹ (mod n)`.
4. Обчислюються допоміжні скаляри `u_1` та `u_2`:
   ```text
   u₁ = z · w mod n
   u₂ = r · w mod n
   ```
5. Обчислюється точка кривої `R = (x_2, y_2)` за формулою лінійної комбінації точок:
   ```text
   R = u₁ · G + u₂ · Q
   ```
6. Підпис вважається дійсним тоді й лише тоді, коли `R ≠ O` (не є точкою на нескінченності) та:
   ```text
   x₂ mod n ≡ r
   ```

## 6. Математичне розшифрування алгоритму Ed25519 (алгоритм 15)

Алгоритм Ed25519 (RFC 8080) базується на скрученій кривій Едвардса (Twisted Edwards Curve):

```text
-x² + y² ≡ 1 + d_ed · x² · y²  (mod p_ed)
```

де `p_ed = 2²⁵⁵ - 19`, а параметр `d_ed = -121665 / 121666 (mod p_ed)`.

Перевагою кривих Едвардса є наявність повної формули додавання точок (Full Addition Law), що виключає крайові випадки `P = Q` або `P = -Q` і захищає реалізацію від атак по побічних каналах (Side-Channel Attacks) без уповільнення обчислень.

Формула додавання точок `P_1(x_1, y_1)` та `P_2(x_2, y_2)`:

```text
x₃ = (x₁·y₂ + y₁·x₂) / (1 + d_ed·x₁·x₂·y₁·y₂)  mod p_ed
y₃ = (y₁·y₂ + x₁·x₂) / (1 - d_ed·x₁·x₂·y₁·y₂)  mod p_ed
```

## 7. Перспектива постквантової криптографії (Falcon / ML-DSA)

Існуючі алгоритми RSA та ECDSA є вразливими до алгоритму Шора (Shor's Algorithm) на квантових обчислювачах достатньої потужності. Для захисту DNSSEC IETF досліджує перехід на решіткову криптографію (Lattice-based Cryptography), зокрема алгоритм Falcon (NIST PQC Standard).

Falcon базується на складній задачі пошуку найкоротшого вектора у решітці (Shortest Vector Problem, SVP) у решітках NTRU:

```text
f · y - g · x = q  (у кільці решіток R = Z[X] / (Xⁿ + 1))
```

Основною математичною перевагою Falcon для DNSSEC є надзвичайно компактні розміри підписів (≈ 666 байт для Falcon-512) порівняно з іншими постквантовими схемами (наприклад, ML-DSA / Dilithium має підпис розміром 2420 байт, що перевищує стандартний ліміт UDP-пакета EDNS0 у 1232 байти та призводить до масової фрагментації IP-пакетів).

## 8. Обчислення контрольної суми Key Tag

Запис `Key Tag` є 16-бітною контрольною сумою RDATA запису `DNSKEY`. Математичний алгоритм обчислення виражається циклічною сумою:

```text
KeyTag = ( Sum(A_i) + ( Sum(A_i) >> 16 ) ) mod 65536  [для i від 0 до L-1]
```

де для кожного байта `RDATA[i]` (`i = 0 ... L-1`):

```text
A_i = RDATA[i] << 8   (якщо i — парний індекс)
A_i = RDATA[i]        (якщо i — непарний індекс)
```

### Числовий приклад обчислення Key Tag

Нехай RDATA запису `DNSKEY` складається з 4 байтів: `0x01, 0x00, 0x03, 0x0D` (Flags = 256, Protocol = 3, Alg = 13):

```text
i = 0: RDATA[0] = 0x01  ->  A₀ = 0x0100 = 256
i = 1: RDATA[1] = 0x00  ->  A₁ = 0x0000 = 0
i = 2: RDATA[2] = 0x03  ->  A₂ = 0x0300 = 768
i = 3: RDATA[3] = 0x0D  ->  A₃ = 0x000D = 13

Сума ac = 256 + 0 + 768 + 13 = 1037 (0x040D)
ac >> 16 = 0
KeyTag = 1037 (0x040D)
```

## 9. Обчислення дайджесту DS та перевірка еквівалентності

Запис делегованого підписувача `DS` містить дайджест публічного ключа `KSK`. Обчислення дайджесту для алгоритму `Digest Type = 2` (SHA-256) здійснюється за формулою:

```text
H_DS = SHA-256( N_child_canon ∥ Flags (2B) ∥ Protocol (1B) ∥ Algorithm (1B) ∥ Public_Key_Bytes )
```

Покроковий приклад обчислення SHA-256 для 32-байтового хешу:

```text
Хешувальні блоки B_i розміром 512 біт (64 байти)
Вхідний масив паддується: M_padded = M ∥ 0x80 ∥ 0x00...00 ∥ Length_in_bits (64-bit uint)

Для кожного 512-бітного блоку B:
  1. Розгортання 16 слів W₀..W₁₅ у 64 слова W₀..W₆₃:
     W_t = σ₁(W_{t-2}) + W_{t-7} + σ₀(W_{t-15}) + W_{t-16}

  2. Змішування змінних станів (a, b, c, d, e, f, g, h) протягом 64 раундів:
     T₁ = h + Σ₁(e) + Ch(e, f, g) + K_t + W_t
     T₂ = Σ₀(a) + Maj(a, b, c)
     h = g;  g = f;  f = e;  e = d + T₁;  d = c;  c = b;  b = a;  a = T₁ + T₂

  3. Додавання стану до проміжного вектора H = (H₀+a, H₁+b, ..., H₇+h)
```

Математичний результат `H_DS` побайтово порівнюється з полем `Digest` у записі `DS`. Збіг дайджесту із ймовірністю помилки `< 2⁻²⁵⁶` доводить, що публічний ключ `KSK` дочірньої зони згенеровано власником батьківської зони.

## 10. Записи NSEC3 та математична стійкість до перебору імен

Для захисту від сканування зони (Zone Walking) NSEC3 застосовує до імен зони однонапрямлену хеш-функцію з додаванням солі (Salt) та повторним хешуванням (Iterations):

```text
H₀ = SHA-1( N_canon ∥ Salt )
H₁ = SHA-1( H₀ ∥ Salt )
...
H_k = SHA-1( H_{k-1} ∥ Salt )
```

Формально NSEC3 доводить неіснування імені `Q`, обчислюючи його хеш `h_Q = H_k(Q_canon)`. Запис NSEC3 надає підписаний інтервал `[h_A, h_B]`, де:

```text
h_A < h_Q < h_B  (у циклічному Base32-просторі)
```

Оскільки хеш-функція SHA-1 є незворотною, обчислення `Q` за відомим `h_Q` вимагає повного перебору (Brute-Force). Додавання солі `Salt` унеможливлює використання заздалегідь обчислених таблиць (Rainbow Tables) для всієї доменної зони.

## 11. Математичне розшифрування прискорення обчислень за допомогою редукції Монтгомері

Під час перевірки цифрових підписів RSA (алгоритми 8 та 10) основною обчислювальною операцією є зведення у великий степінь за модулем `N_rsa`:

```text
EM = S^e mod N_rsa
```

Класичне ділення у стовпчик для 2048-бітних чисел є надзвичайно повільним. Для прискорення застосовується редукція Монтгомері (Montgomery Reduction), яка замінює важке ділення на модульні зсуви та множення.

Вибирається вспоміжне число `R_mont > N_rsa`, таке що `gcd(R_mont, N_rsa) = 1` (зазвичай `R_mont = 2²⁰⁴⁸`).

Кожне число `A` переводиться у форму Монтгомері:

```text
A' = A · R_mont mod N_rsa
```

Операція множення двох чисел у формі Монтгомері `REDC(A', B')` обчислюється за формулою:

```text
REDC(A', B') = (A' · B' + m · N_rsa) / R_mont
```

де `m = ((A' · B' mod R_mont) · N') mod R_mont`, а `N' = -N_rsa⁻¹ mod R_mont`.

Оскільки ділення виконується на `R_mont = 2²⁰⁴⁸`, воно зводиться до простого побітового зсуву вправо на 2048 бітів, що прискорює валідацію RSA-підписів у десятки разів.

## 12. Теорема про повноту охоплення простору NSEC3

Теорема: Множина інтервалів `[h_A, h_B]`, надана записами NSEC3 підписаної зони, формує повне зациклене покриття простору `[0, 2¹⁶⁰ - 1]`.

Доведення: Нехай зона містить `M` унікальних імен. Хеш-функція SHA-1 відображає кожне канонізоване ім'я `N_i` у 160-бітне значення `h_i = H(N_i) ∈ [0, 2¹⁶⁰ - 1]`. Оскільки множина хешів `H = {h_1, h_2, ..., h_M}` є скінченною підмножиною впорядкованого циклічного кільця, сортування за зростанням утворює унікальний ланцюг `h_1 < h_2 < ... < h_M`. Запис NSEC3 для `h_i` вказує на `h_{i+1}` (а для `h_M` — на `h_1`). Отже, для будь-якого елемента `h_Q ∉ H` існує єдиний інтервал `h_k < h_Q < h_{k+1}`, що й доводить неіснування імені `Q`.

## 13. Складність атаки словникового перебору на хеші NSEC3

Розглянемо криптоаналіз незворотності записів NSEC3 при використанні солі `Salt` довжиною `L_salt` байтів та кількості ітерацій `K`.

Нехай словник найвживаніших субдоменів містить `V` елементів (наприклад, `V = 10⁷` слів).

1. **Без солі (`L_salt = 0`):** Атакуючий може заздалегідь обчислити таблицю хешів `T` для всіх `V` субдоменів за час `O(V · K)`. Після отримання файлу NSEC3 для будь-якої зони перевірка наявності субдомену виконується за `O(1)` операцій пошуку в хеш-таблиці `T`.
2. **З використанням солі (`L_salt > 0`):** Соління модифікує вхідний масив хеш-функції `SHA-1(N ∥ Salt)`. Для кожної нової зони з унікальною сіллю `Salt_zone` атакуючий змушений заново обчислювати словник з `V` хешів. Часова складність атаки на одну зону становить:

```text
Complexity = O( V · (K + 1) · Hash_Time(SHA1) )
```

При `K = 10` та `V = 10⁷` обчислення вимагає `10⁸` викликів SHA-1 на одну зону. Оскільки для 100 000 доменних зон використано 100 000 унікальних солей, сукупні обчислення розростаються до `10¹³` операцій хешування, що робить масове автоматичне вивантаження доменів мережі недоцільним.

## 14. Математика постквантових підписів Falcon у решітках NTRU

Для постквантового захисту DNSSEC в алгоритмі Falcon розглядаються алгебраїчні кільця многочленів `R = Z[X] / (Xⁿ + 1)`, де `n = 512` або `n = 1024`.

Криптографічний ключ є парою малих многочленів `(f, g, F, G) ∈ R⁴`, що задовольняють рівняння Накахара-Клопфенштейна-NTRU:

```text
f · G - g · F = q  mod (Xⁿ + 1)
```

де `q = 12289` — просте число модуля решітки.

Створення підпису зводиться до обчислення вектора `(s₁, s₂)` у n-вимірній решітці `Λ`, розташованого поблизу вхідного повідомлення-хешу `h = HashToPoint(M)` за допомогою швидкого дискретного Гаусового семплінгу (Fast Fourier Sampling):

```text
s₁ = c - ⌊ c ⌉_g  (де c залежить від h та публічного h_pub = g · f⁻¹ mod q)
s₂ = h - s₁ · h_pub mod q
```

Перевірка підпису валідатором перевіряє сувору норму квадрата довжини вектора:

```text
||s₁||² + ||s₂||² ≤ ⌊ σ_bound ⌉²
```

Якщо Евклідова норма вектора `(s₁, s₂)` перебільшує поріг `σ_bound = 1.17 · σ_gaussian · √n`, підпис відхиляється. Це гарантує математичний захист від підробки як на класичних, так і на квантових комп'ютерах.
