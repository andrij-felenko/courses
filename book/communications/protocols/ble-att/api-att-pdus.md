# 📋 Довідник кадрів ATT PDU, кодів операцій та помилок

Кожен байт, що передається між BLE-пристроями у фіксованому каналі L2CAP з ідентифікатором каналу `0x0004`, підпорядковується бінарному формату протоколу атрибутів (англ. *Attribute Protocol*, ATT). Цей документ є структурним довідником двійкового інтерфейсу ATT: він визначає кодування байта операції, точну розкладку полів кожного кадру PDU (англ. *Protocol Data Unit*), правила байтового пакування, інваріанти валідації, розбір шістнадцяткових дампів реальних пакетів, розширення Enhanced ATT (EATT) та повний реєстр стандартних кодів помилок із семантикою їхньої обробки.

### 1. Анатомія байта коду операції (Opcode)

Байт коду операції `Opcode` є першим обов'язковим октетом будь-якого кадру ATT PDU. Він визначає метод операції, наявність криптографічного підпису та категорію взаємодії (запит/відповідь чи одностороння команда).

```
Біти:    [ 7 ]          [ 6 ]          [ 5 .. 0 ]
Поле:    Command Flag   AuthSignature  Attribute Opcode Method
Розмір:  1 біт          1 біт          6 бітів
```

#### Бітові прапорці заголовка
* **Біт 7 (Command Flag — прапорець команди)**: встановлюється в `1` виключно для операцій типу «Команда» (наприклад, `Write Command` з кодом `0x52`), які надсилаються клієнтом без очікування протокольного підтвердження від сервера. Для всіх класичних запитів (Requests), відповідей (Responses), сповіщень (Notifications) та індикацій (Indications) цей біт дорівнює `0`.
* **Біт 6 (Authentication Signature Flag — прапорець підпису автентифікації)**: встановлюється в `1`, якщо кадр містить завершальний 12-байтний блок автентифікації (`Signed Write Command` з кодом `0xD2`). Цей блок складається з 4-байтного лічильника підписів (Sign Counter) та 8 байтів коду автентифікації повідомлення (MAC), згенерованого за алгоритмом AES-128 CMAC за допомогою спільного ключа зв'язку (CSRK — Connection Signature Resolving Key).
* **Біти 5..0 (Method — номер базового методу)**: 6-бітне беззнакове ціле число в діапазоні `0x00`–`0x3F`, яке кодує функціональну сутність операції.

### 2. Загальні правила серіалізації та інваріанти валідації

При обробці та генерації будь-якого кадру ATT PDU програмний стек зобов'язаний дотримуватися фундаментальних правил форматування:

1. **Порядок байтів (Endianness)**: усі числові поля розміром 16 бітів (дескриптори `Handle`, зміщення `Offset`, розміри буферів `MTU`, 16-бітні коди `UUID`) та 128-бітні значення передаються в порядку від молодшого байта до старшого (**Little-Endian**, LSB first). Наприклад, дескриптор `0x0012` передається в кадрі як байти `0x12, 0x00`.
2. **Заборона дескриптора 0x0000**: значення `0x0000` зарезервоване в стандарті як недійсний дескриптор. Будь-який запит, у якому поле `Starting Handle` або `Attribute Handle` дорівнює `0x0000`, повинен негайно відхилятися сервером генерацією `ATT_ERROR_RSP` із кодом помилки `0x01` (`Invalid Handle`).
3. **Умова валідності діапазонів**: у всіх операціях сканування та виявлення (`Find Info`, `Read By Type`, `Read By Group Type`, `Find By Type Value`) початковий дескриптор діапазону не може перевищувати кінцевий: обов'язково має виконуватися співвідношення `1 <= StartingHandle <= EndingHandle <= 0xFFFF`. Якщо `StartingHandle > EndingHandle`, сервер генерує `ATT_ERROR_RSP` з кодом `0x01`.
4. **Максимальний розмір кадру**: загальний розмір будь-якого сформованого PDU разом із байтом Opcode не може перевищувати поточний узгоджений розмір `ATT_MTU` для даного з'єднання (за замовчуванням 23 байти, максимум 517 байтів). Спроба відправити PDU більшого розміру спричиняє скидання з'єднання на канальному рівні L2CAP.
5. **Граничні розміри корисного навантаження**: оскільки заголовок ATT забирає частину простору кадру (1 байт Opcode для `Read Response`, 3 байти `Opcode + Handle` для `Write Request`, `Notification` та `Indication`, 5 байтів `Opcode + Handle + Offset` для `Prepare Write Request`), розмір корисних даних у кожному PDU строго обмежений формулами:
   * Для `ATT_READ_RSP`: `Payload = ATT_MTU - 1`;
   * Для `ATT_WRITE_REQ`, `ATT_WRITE_CMD`, `ATT_HANDLE_VALUE_NTF`, `ATT_HANDLE_VALUE_IND`: `Payload = ATT_MTU - 3`;
   * Для `ATT_PREPARE_WRITE_REQ`: `Payload = ATT_MTU - 5`.
   Якщо довжина даних, що записуються або сповіщаються, перевищує відповідний ліміт, стек зобов'язаний застосувати фрагментацію або процедуру черги підготовки.

### 3. Детальна специфікація структури кадрів PDU

Нижче наведено побайтову структуру та правила поведінки сторін для кожного протокольного кадру.

#### 3.1. Відповідь про помилку (`ATT_ERROR_RSP`, `0x01`)
Генерується сервером щоразу, коли клієнт надсилає запит (Request), який не може бути успішно виконаний через відсутність атрибута, порушення прав доступу, невірний формат або стан безпеки.

```
Зміщення:  [ 0 ]      [ 1 ]           [ 2 .. 3 ]         [ 4 ]
Поле:      Opcode     RequestOpcode   AttributeHandle    ErrorCode
Тип:       uint8_t    uint8_t         uint16_t (LE)      uint8_t
Значення:  0x01       0x02 .. 0x18    0x0001 .. 0xFFFF   0x01 .. 0xFF
```

* `RequestOpcode`: код операції запиту клієнта, під час обробки якого виник збій.
* `AttributeHandle`: дескриптор атрибута, на якому сталася помилка. Якщо помилка виникла на операції, що не оперує конкретним атрибутом (наприклад, непідтримуваний `ATT_EXCHANGE_MTU_REQ`), це поле заповнюється значенням `0x0000`.
* `ErrorCode`: однобайтний код помилки з таблиці стандартних кодів.

#### 3.2. Узгодження MTU (`ATT_EXCHANGE_MTU_REQ`, `0x02` / `ATT_EXCHANGE_MTU_RSP`, `0x03`)
Процедура узгодження виконується лише один раз за час існування з'єднання, зазвичай одразу після встановлення каналу зв'язку.

```
ATT_EXCHANGE_MTU_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]
Поле:      Opcode     ClientRxMTU
Тип:       uint8_t    uint16_t (LE)
Розмір:    3 байти

ATT_EXCHANGE_MTU_RSP:
Зміщення:  [ 0 ]      [ 1 .. 2 ]
Поле:      Opcode     ServerRxMTU
Тип:       uint8_t    uint16_t (LE)
Розмір:    3 байти
```

* `ClientRxMTU` та `ServerRxMTU` вказують максимальний розмір буфера приймача відповідної сторони.
* Значення не можуть бути меншими за `23` байти.
* Після успішного обміну обидва пристрої встановлюють робочий MTU як `MTU = min(ClientRxMTU, ServerRxMTU)`. Повторний запит узгодження MTU в межах того самого з'єднання заборонений специфікацією і викликає помилку `ATT_ERR_REQUEST_NOT_SUPPORTED`.

#### 3.3. Пошук інформації про типи атрибутів (`ATT_FIND_INFO_REQ`, `0x04` / `ATT_FIND_INFO_RSP`, `0x05`)
Використовується для послідовного опитування бази атрибутів з метою побудови повної карти дескрипторів та їхніх типів (UUID).

```
ATT_FIND_INFO_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 4 ]
Поле:      Opcode     StartingHandle     EndingHandle
Тип:       uint8_t    uint16_t (LE)      uint16_t (LE)
Розмір:    5 байтів
```

```
ATT_FIND_INFO_RSP:
Зміщення:  [ 0 ]      [ 1 ]              [ 2 .. N-1 ]
Поле:      Opcode     Format             InformationData
Тип:       uint8_t    uint8_t            Масив байтів
Розмір:    від 6 до MTU байтів
```

* `Format`:
  * `0x01` — список 16-бітних Bluetooth UUID. Поле `InformationData` містить послідовність записів по 4 байти кожен: `[ Handle (2 B) ] [ 16-bit UUID (2 B) ]`.
  * `0x02` — список 128-бітних вендорних UUID. Поле `InformationData` містить послідовність записів по 18 байтів кожен: `[ Handle (2 B) ] [ 128-bit UUID (16 B) ]`.
* В одній відповіді суворо заборонено змішувати 16-бітні та 128-бітні записи. Якщо сервер під час формування відповіді доходить до дескриптора з іншим розміром UUID, він зобов'язаний зупинити формування пакету і відправити лише ті елементи, які мають однаковий розмір. Клієнт, отримавши відповідь, продовжує пошук із наступного дескриптора.

#### 3.4. Пошук за типом і значенням (`ATT_FIND_BY_TYPE_VALUE_REQ`, `0x06` / `0x07`)
Дозволяє швидко локалізувати межі сервісу за його відомим 16-бітним UUID (наприклад, знайти дескриптори первинного сервісу `0x2800` зі значенням `0x180D`).

```
ATT_FIND_BY_TYPE_VALUE_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 4 ]       [ 5 .. 6 ]       [ 7 .. N-1 ]
Поле:      Opcode     StartingHandle     EndingHandle     AttributeType    AttributeValue
Тип:       uint8_t    uint16_t (LE)      uint16_t (LE)    uint16_t (LE)    Масив байтів
Розмір:    від 7 до MTU байтів
```

```
ATT_FIND_BY_TYPE_VALUE_RSP:
Зміщення:  [ 0 ]      [ 1 .. N-1 ]
Поле:      Opcode     HandlesInformationList
Тип:       uint8_t    Масив записів по 4 байти
Розмір:    від 5 до MTU байтів (1 + 4 * K)
```

* Кожен запис у `HandlesInformationList` має довжину 4 байти: `[ FoundAttributeHandle (2 B) ] [ GroupEndHandle (2 B) ]`.
* `FoundAttributeHandle` вказує на початок знайденої групи, а `GroupEndHandle` — на останній дескриптор, що належить цій групі. Якщо відповідних атрибутів не знайдено, сервер відповідає `ATT_ERROR_RSP` із кодом `0x0A` (`Attribute Not Found`).

#### 3.5. Читання за типом (`ATT_READ_BY_TYPE_REQ`, `0x08` / `ATT_READ_BY_TYPE_RSP`, `0x09`)
Основний робочий PDU для процедури виявлення характеристик усередині знайденого сервісу. Клієнт передає діапазон дескрипторів та UUID декларації характеристики (`0x2803`).

```
ATT_READ_BY_TYPE_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 4 ]       [ 5 .. N-1 ]
Поле:      Opcode     StartingHandle     EndingHandle     AttributeType (2 B або 16 B UUID)
Тип:       uint8_t    uint16_t (LE)      uint16_t (LE)    UUID (LE)
Розмір:    7 байтів (для 16-біт UUID) або 21 байт (для 128-біт UUID)
```

```
ATT_READ_BY_TYPE_RSP:
Зміщення:  [ 0 ]      [ 1 ]              [ 2 .. N-1 ]
Поле:      Opcode     Length             AttributeDataList
Тип:       uint8_t    uint8_t            Масив записів фіксованої довжини
Розмір:    від 4 до MTU байтів
```

* Поле `Length` вказує точний розмір одного запису в списку `AttributeDataList` (включно з 2 байтами Handle на початку кожного запису).
* Кожен елемент списку має структуру: `[ Handle (2 B) ] [ Value ((Length - 2) B) ]`.
* Якщо значення наступного знайденого атрибута має іншу довжину, ніж попередній, сервер зупиняє формування списку, щоб зберегти фіксовану довжину кроку `Length` для всього кадру.

#### 3.6. Читання за дескриптором (`ATT_READ_REQ`, `0x0A` / `ATT_READ_RSP`, `0x0B`)
Читання повного значення атрибута за його точним 16-бітним дескриптором.

```
ATT_READ_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]
Поле:      Opcode     AttributeHandle
Тип:       uint8_t    uint16_t (LE)
Розмір:    3 байти
```

```
ATT_READ_RSP:
Зміщення:  [ 0 ]      [ 1 .. N-1 ]
Поле:      Opcode     AttributeValue
Тип:       uint8_t    Масив байтів (0 .. MTU-1 байтів)
Розмір:    від 1 до MTU байтів
```

* Якщо фактична довжина атрибута більша за `(MTU - 1)` байтів, сервер відсікає значення і відправляє рівно перші `(MTU - 1)` байтів. Клієнт розпізнає це за розміром пакету: якщо повернуто рівно `MTU - 1` байтів корисного навантаження, залишок значення необхідно дочитати за допомогою `ATT_READ_BLOB_REQ`.

#### 3.7. Читання довгого атрибута (`ATT_READ_BLOB_REQ`, `0x0C` / `ATT_READ_BLOB_RSP`, `0x0D`)
Використовується для послідовного вичитування довгих масивів даних (наприклад, імені пристрою, дескрипторів звітів HID чи прошивки OTA) частинами з вказаного зміщення.

```
ATT_READ_BLOB_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 4 ]
Поле:      Opcode     AttributeHandle    ValueOffset
Тип:       uint8_t    uint16_t (LE)      uint16_t (LE)
Розмір:    5 байтів
```

```
ATT_READ_BLOB_RSP:
Зміщення:  [ 0 ]      [ 1 .. N-1 ]
Поле:      Opcode     PartAttributeValue
Тип:       uint8_t    Масив байтів (0 .. MTU-1 байтів)
Розмір:    від 1 до MTU байтів
```

* `ValueOffset`: байтове зміщення всередині значення атрибута, з якого слід розпочати читання.
* Якщо зміщення `ValueOffset` перевищує або дорівнює повній довжині значення атрибута на сервері, операція завершується помилкою `ATT_ERROR_RSP` із кодом `0x07` (`Invalid Offset`).
* Повернення значення, довжина якого менша за `(MTU - 1)` байтів, однозначно свідчить про успішне прочитання останнього фрагмента довгого атрибута.

#### 3.8. Запис із підтвердженням (`ATT_WRITE_REQ`, `0x12` / `ATT_WRITE_RSP`, `0x13`)
Класичний запис значення в характеристику чи дескриптор. Клієнт блокує чергу відправлення до отримання підтвердження від сервера.

```
ATT_WRITE_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. N-1 ]
Поле:      Opcode     AttributeHandle    AttributeValue
Тип:       uint8_t    uint16_t (LE)      Масив байтів (0 .. MTU-3 байтів)
Розмір:    від 3 до MTU байтів
```

```
ATT_WRITE_RSP:
Зміщення:  [ 0 ]
Поле:      Opcode
Тип:       uint8_t
Розмір:    рівно 1 байт (значення 0x13)
```

* Відповідь `ATT_WRITE_RSP` містить виключно байт свого коду операції і не несе корисного навантаження. Її прибуття свідчить про те, що сервер успішно записав значення у свою локальну базу даних і перевірив усі права доступу.

#### 3.9. Запис без підтвердження (`ATT_WRITE_CMD`, `0x52`)
Команда запису, яка не викликає формування відповіді `ATT_WRITE_RSP`.

```
ATT_WRITE_CMD:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. N-1 ]
Поле:      Opcode     AttributeHandle    AttributeValue
Тип:       uint8_t    uint16_t (LE)      Масив байтів (0 .. MTU-3 байтів)
Розмір:    від 3 до MTU байтів (Opcode = 0x52)
```

* Оскільки відповіді немає, клієнт не блокує чергу запитів і може надсилати команди `ATT_WRITE_CMD` у кожному інтервалі з'єднання підряд.
* Якщо дескриптор не існує або в нього заборонено запис, сервер мовчки ігнорує пакет без відправки повідомлення про помилку.

#### 3.10. Підписаний запис без підтвердження (`ATT_SIGNED_WRITE_CMD`, `0xD2`)
Дозволяє передавати команди запису з криптографічною автентифікацією джерела навіть через незашифроване радіоз'єднання.

```
ATT_SIGNED_WRITE_CMD:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. N-13 ]      [ N-12 .. N-9 ]   [ N-8 .. N-1 ]
Поле:      Opcode     AttributeHandle    AttributeValue     SignCounter       MessageAuthCode (MAC)
Тип:       uint8_t    uint16_t (LE)      Масив байтів       uint32_t (LE)     8 байтів (AES-CMAC)
Розмір:    від 15 до MTU байтів (Opcode = 0xD2)
```

* `SignCounter`: 32-бітний монотонно зростаючий лічильник транзакцій, що унеможливлює атаки повторного відтворення (Replay Attack). Сервер відкидає пакет, якщо прийнятий лічильник менший або дорівнює останньому зафіксованому значенню.
* `MessageAuthCode (MAC)`: молодші 64 біти результату хешування вмісту всього кадру (Opcode + Handle + Value + SignCounter) за алгоритмом AES-128 CMAC за допомогою спільного ключа CSRK (Connection Signature Resolving Key).

#### 3.11. Підготовка та виконання черги запису (`0x16`, `0x17`, `0x18`, `0x19`)
Механізм надійного запису довгих значень (> MTU - 3) або атомарного запису в кілька різних характеристик одночасно.

```
ATT_PREPARE_WRITE_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 4 ]       [ 5 .. N-1 ]
Поле:      Opcode     AttributeHandle    ValueOffset      PartAttributeValue
Тип:       uint8_t    uint16_t (LE)      uint16_t (LE)    Масив байтів (0 .. MTU-5 B)
Розмір:    від 5 до MTU байтів
```

```
ATT_PREPARE_WRITE_RSP:
Повна точна копія (echo) запиту ATT_PREPARE_WRITE_REQ з Opcode = 0x17.
```

```
ATT_EXECUTE_WRITE_REQ:
Зміщення:  [ 0 ]      [ 1 ]
Поле:      Opcode     Flags
Тип:       uint8_t    uint8_t (0x00 = Cancel, 0x01 = Write)
Розмір:    рівно 2 байти
```

```
ATT_EXECUTE_WRITE_RSP:
Зміщення:  [ 0 ]
Поле:      Opcode
Тип:       uint8_t (0x19)
Розмір:    рівно 1 байт
```

* Клієнт надсилає послідовність кадрів `ATT_PREPARE_WRITE_REQ`, передаючи фрагменти даних із відповідними зміщеннями `ValueOffset`. Сервер зберігає їх у тимчасовому буфері підготовки і повертає `ATT_PREPARE_WRITE_RSP` як відлуння.
* Після завантаження всіх частин клієнт відправляє `ATT_EXECUTE_WRITE_REQ` із прапорцем `Flags = 0x01` для атомарної фіксації всіх змін або `Flags = 0x00` для повного скасування та очищення буфера сервера.

#### 3.12. Сповіщення та індикації (`0x1B`, `0x1D`, `0x1E`)
Серверні процедури відправки даних клієнту за його попередньою підпискою через дескриптор конфігурації клієнта (CCCD, UUID `0x2902`).

```
ATT_HANDLE_VALUE_NTF (Сповіщення):
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. N-1 ]
Поле:      Opcode     AttributeHandle    AttributeValue
Тип:       uint8_t    uint16_t (LE)      Масив байтів (0 .. MTU-3 байтів)
Розмір:    від 3 до MTU байтів (Opcode = 0x1B)
```

```
ATT_HANDLE_VALUE_IND (Індикація):
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. N-1 ]
Поле:      Opcode     AttributeHandle    AttributeValue
Тип:       uint8_t    uint16_t (LE)      Масив байтів (0 .. MTU-3 байтів)
Розмір:    від 3 до MTU байтів (Opcode = 0x1D)
```

```
ATT_HANDLE_VALUE_CFM (Підтвердження індикації):
Зміщення:  [ 0 ]
Поле:      Opcode
Тип:       uint8_t (значення 0x1E)
Розмір:    рівно 1 байт
```

* `Handle Value Notification` надсилається без підтвердження. Сервер не очікує жодної реакції від клієнта на рівні ATT і може негайно відправляти наступні дані.
* `Handle Value Indication` вимагає від клієнта обов'язкового відправлення `ATT_HANDLE_VALUE_CFM`. Доки підтвердження не надійде, сервер блокує відправку будь-яких наступних індикацій для даного з'єднання.

### 4. Розширення Enhanced ATT (EATT) у Bluetooth 5.2

У специфікації Bluetooth 5.2 введено розширений протокол Enhanced ATT (EATT), який працює поверх динамічних каналів L2CAP з кредитним керуванням потоком (L2CAP Enhanced Credit-Based Flow Control). Це усуває проблему блокування початку черги (Head-of-Line Blocking) класичного ATT і додає оптимізовані типи PDU:

#### 4.1. Читання атрибутів змінної довжини (`ATT_READ_MULTIPLE_VAR_REQ`, `0x20` / `0x21`)
Класичний PDU `Read Multiple Request` (`0x0E`) вимагав, щоб клієнт заздалегідь знав розміри всіх запитуваних атрибутів, оскільки сервер повертав їх склеєними в єдиний масив без роздільників. Новий PDU `Read Multiple Variable Length` додає префікс довжини до кожного значення:

```
ATT_READ_MULTIPLE_VAR_REQ:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 4 ]       [ ... ]
Поле:      Opcode     SetOfHandles (Список дескрипторів uint16_t LE)
Розмір:    від 5 байтів (мінімум два дескриптори)

ATT_READ_MULTIPLE_VAR_RSP:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 3+L1-1 ]  [ ... ]
Поле:      Opcode     Length_1 (uint16)  Value_1          Length_2 ...
Розмір:    від 3 до MTU байтів
```

#### 4.2. Множинні сповіщення в одному кадрі (`ATT_MULTIPLE_HANDLE_VALUE_NTF`, `0x23`)
Дозволяє серверу об'єднати сповіщення від кількох різних характеристик в один пакет PDU:

```
ATT_MULTIPLE_HANDLE_VALUE_NTF:
Зміщення:  [ 0 ]      [ 1 .. 2 ]         [ 3 .. 4 ]       [ 5 .. 5+L1-1 ]
Поле:      Opcode     Handle_1 (uint16)  Length_1 (uint16) Value_1 (L1 байтів) ...
Розмір:    від 5 до MTU байтів
```

### 5. Розбір типових трас обміну на рівні байтів

Для ілюстрації реального протокольного обміну розглянемо шістнадцяткові дампи типових транзакцій, перехоплених на рівні L2CAP (CID `0x0004`).

#### Приклад 1. Узгодження MTU між смартфоном та датчиком
Клієнт (телефон) пропонує буфер розміром 512 байтів (`0x0200`). Сервер (ESP32) підтримує буфер 247 байтів (`0x00F7`).

```
Клієнт -> Сервер:  02 00 02
  02       : Opcode (ATT_EXCHANGE_MTU_REQ)
  00 02    : ClientRxMTU = 0x0200 = 512 байтів (Little-Endian)

Сервер -> Клієнт:  03 F7 00
  03       : Opcode (ATT_EXCHANGE_MTU_RSP)
  F7 00    : ServerRxMTU = 0x00F7 = 247 байтів (Little-Endian)
```
Результат: робочий розмір `ATT_MTU` для обох пристроїв стає рівним `247` байтів.

#### Приклад 2. Виявлення сервісів (Read By Group Type)
Клієнт шукає всі первинні сервіси (UUID `0x2800`) у повному просторі дескрипторів від `0x0001` до `0xFFFF`.

```
Клієнт -> Сервер:  10 01 00 FF FF 00 28
  10       : Opcode (ATT_READ_BY_GROUP_TYPE_REQ)
  01 00    : StartingHandle = 0x0001
  FF FF    : EndingHandle   = 0xFFFF
  00 28    : AttributeType  = 0x2800 (GATT Primary Service Declaration)

Сервер -> Клієнт:  11 06 01 00 05 00 0D 18 06 00 09 00 0F 18
  11       : Opcode (ATT_READ_BY_GROUP_TYPE_RSP)
  06       : Length одного елемента = 6 байтів
  Елемент 1 (6 B):
    01 00  : Found Handle = 0x0001 (дескриптор сервісу)
    05 00  : Group End Handle = 0x0005 (останній дескриптор сервісу)
    0D 18  : Service UUID = 0x180D (Heart Rate Service)
  Елемент 2 (6 B):
    06 00  : Found Handle = 0x0006
    09 00  : Group End Handle = 0x0009
    0F 18  : Service UUID = 0x180F (Battery Service)
```

#### Приклад 3. Підписка на сповіщення через запис у дескриптор CCCD
Клієнт вмикає сповіщення (Notifications), записуючи значення `0x0001` у дескриптор конфігурації клієнта за дескриптором `0x0004`.

```
Клієнт -> Сервер:  12 04 00 01 00
  12       : Opcode (ATT_WRITE_REQ)
  04 00    : AttributeHandle = 0x0004 (дескриптор CCCD)
  01 00    : AttributeValue  = 0x0001 (Біт 0 = 1: Notifications Enabled)

Сервер -> Клієнт:  13
  13       : Opcode (ATT_WRITE_RSP, запис успішно підтверджено)
```

#### Приклад 4. Відправка асинхронного сповіщення пульсометра
Сервер надсилає сповіщення вимірювання пульсу з дескриптора `0x0003`.

```
Сервер -> Клієнт:  1B 03 00 00 48
  1B       : Opcode (ATT_HANDLE_VALUE_NTF)
  03 00    : AttributeHandle = 0x0003 (дескриптор Heart Rate Measurement)
  00 48    : Value (Байт прапорців 0x00 + Значення пульсу 0x48 = 72 уд/хв)
```

### 6. Реєстр стандартних кодів помилок ATT

Якщо запит клієнта не може бути успішно виконаний або порушує правила доступу, сервер генерує `ATT_ERROR_RSP` із відповідним кодом помилки:

| Код (Hex) | Символічна константа | Опис причини збою | Інтерпретація та відновлення |
|:---|:---|:---|:---|
| `0x01` | `ATT_ERR_INVALID_HANDLE` | Дескриптор `Attribute Handle` дорівнює `0x0000` або виходить за межі діапазону бази даних сервера. | Помилка адресації; клієнт повинен перевірити межі дескрипторів або повторити виявлення сервісів. |
| `0x02` | `ATT_ERR_READ_NOT_PERMITTED` | Атрибут не має дозволу на операцію читання (Permissions). | Спроба прочитати суто записуваний атрибут (наприклад, команду скидання); операція неприпустима. |
| `0x03` | `ATT_ERR_WRITE_NOT_PERMITTED` | Атрибут захищений від запису або є константою тільки для читання. | Спроба записати значення в незмінну характеристику (наприклад, версію апаратного забезпечення). |
| `0x04` | `ATT_ERR_INVALID_PDU` | Довжина PDU або внутрішній формат полів не відповідає специфікації для даного коду операції. | Збій серіалізації; перевірити коректність довжини буфера перед відправленням. |
| `0x05` | `ATT_ERR_INSUFFICIENT_AUTHENTICATION` | Для доступу до атрибута потрібне автентифіковане спарювання (автентифікація з захистом від MITM). | Клієнт повинен ініціювати процедуру спарювання SMP з введенням PIN-коду чи Passkey. |
| `0x06` | `ATT_ERR_REQUEST_NOT_SUPPORTED` | Сервер не підтримує запитану процедуру (наприклад, сервер не реалізує буферизацію `Prepare Write`). | Використовувати базові операції запису або перевірити версію стека сервера. |
| `0x07` | `ATT_ERR_INVALID_OFFSET` | Зміщення `ValueOffset` у `Read Blob` або `Prepare Write` виходить за межі поточної довжини значення атрибута. | Нормальний сигнал закінчення вичитування довгого значення або помилка позиціювання в буфері. |
| `0x08` | `ATT_ERR_INSUFFICIENT_AUTHORIZATION` | Спарювання виконано, але клієнт не має явного дозволу користувача (User Authorization) на доступ. | Застосунок вимагає підтвердження на екрані пристрою користувача для надання прав. |
| `0x09` | `ATT_ERR_PREPARE_QUEUE_FULL` | Вичерпано ліміт пам'яті сервера для збереження підготовлених фрагментів довгого запису. | Зменшити розмір блоку транзакції або виконати скасування черги через `Execute Write (Cancel)`. |
| `0x0A` | `ATT_ERR_ATTRIBUTE_NOT_FOUND` | У вказаному числовому діапазоні не знайдено жодного атрибута із запитаним UUID. | Штатний сигнал завершення процедури пошуку сервісів чи характеристик у діапазоні. |
| `0x0B` | `ATT_ERR_ATTRIBUTE_NOT_LONG` | Спроба читання через `ATT_READ_BLOB_REQ` атрибута, розмір якого не перевищує `(MTU - 1)`. | Атрибут повністю вміщується в один кадр; читати звичайним запитом `ATT_READ_REQ`. |
| `0x0C` | `ATT_ERR_INSUFFICIENT_ENC_KEY_SIZE` | Розмір ключа шифрування каналу зв'язку менший за мінімально вимаганий для цього атрибута (наприклад, < 16 B). | Необхідно переузгодити шифрування з повною 128-бітною довжиною ключа безпеки. |
| `0x0D` | `ATT_ERR_INVALID_ATTR_VALUE_LEN` | Розмір даних у запиті на запис не відповідає фіксованій довжині поля характеристики на сервері. | Перевірити структуру переданого об'єкта; розмір корисного навантаження має бути точним. |
| `0x0E` | `ATT_ERR_UNLIKELY_ERROR` | Внутрішня непередбачувана помилка обробника атрибута на стороні прошивки сервера. | Тимчасовий збій ресурсу; клієнт може повторити запит через певний проміжок часу. |
| `0x0F` | `ATT_ERR_INSUFFICIENT_ENCRYPTION` | Канал зв'язку не зашифрований, тоді як права доступу атрибута вимагають обов'язкового шифрування. | Клієнт повинен увімкнути шифрування з'єднання Link Layer через протокол SMP. |
| `0x10` | `ATT_ERR_UNSUPPORTED_GROUP_TYPE` | Тип групи у запиті `Read By Group Type` не є валідним груповим UUID (наприклад, відмінний від `0x2800`/`0x2802`). | Перевірити правильність переданого групового UUID. |
| `0x11` | `ATT_ERR_INSUFFICIENT_RESOURCES` | Сервер не має вільних апаратних або системних ресурсів для обробки запиту в поточний момент. | Клієнт повинен сповільнити частоту звернень і повторити запит пізніше. |
| `0x12` | `ATT_ERR_DATABASE_OUT_OF_SYNC` | База атрибутів сервера змінилася під час з'єднання, а клієнт намагається використати застарілий кеш (BT 5.1). | Клієнт зобов'язаний скинути кешовані дескриптори та виконати повторне виявлення сервісів. |
| `0x13` | `ATT_ERR_VALUE_NOT_ALLOWED` | Значення параметра виходить за межі допустимого діапазону валідності для цієї характеристики (BT 5.2). | Перевірити передане числове значення на відповідність діапазону значень характеристики. |
| `0x80 .. 0x9F` | `Application Error Codes` | Специфічні коди помилок користувацьких профілів або прошивок пристроїв. | Інтерпретуються згідно з документацією розробника конкретної периферії. |
| `0xFD` | `CCC_IMPROPERLY_CONFIGURED` | Клієнт намагається виконати операцію над характеристикою, дескриптор CCCD якої не налаштований належним чином. | Записати біти дозволу `0x0001` (Notify) або `0x0002` (Indicate) у відповідний дескриптор CCCD (`0x2902`). |
| `0xFE` | `PROCEDURE_ALREADY_IN_PROGRESS` | Сервер уже виконує тривалу операцію для цього дескриптора (наприклад, оновлення чи самокалібрування). | Дочекатися завершення поточної процедури перед відправленням наступного запиту. |
| `0xFF` | `OUT_OF_RANGE` | Записане числове значення виходить за межі діапазону, визначеного дескриптором формату характеристики. | Відкоригувати значення згідно з дескриптором валідного діапазону характеристик. |

### 7. Логіка обробки помилок безпеки клієнтом

Отримання кодів помилок безпеки `0x05` (`Insufficient Authentication`), `0x0C` (`Insufficient Encryption Key Size`) та `0x0F` (`Insufficient Encryption`) є нормальним етапом протокольного узгодження захисту. Стандарт Bluetooth Low Energy передбачає модель «лінивого підвищення безпеки» (англ. *Lazy Security Elevation*): пристрої підключаються без шифрування на базовому рівні GAP, а запит на шифрування або спарювання надсилається лише тоді, коли клієнт намагається отримати доступ до захищеного атрибута:

1. **Отримання `0x0F` (Insufficient Encryption)**: клієнт зобов'язаний негайно надіслати запит канального рівня `LL_ENC_REQ` (якщо пристрої вже спарені й мають збережений довгостроковий ключ LTK) або ініціювати фазу спарювання SMP Security Request. Після активації шифрування каналу клієнт зобов'язаний автоматично повторити попередній перерваний запит ATT.
2. **Отримання `0x05` (Insufficient Authentication)**: свідчить про те, що поточне шифрування каналу зв'язку було встановлено за допомогою неавтентифікованого методу Just Works, який не захищає від атак перехоплення трафіку (Man-in-the-Middle, MITM). Клієнт зобов'язаний ініціювати процедуру повторного спарювання з обов'язковою автентифікацією користувача (введення 6-значного Passkey або підтвердження числовим порівнянням Numeric Comparison).
3. **Отримання `0x12` (Database Out of Sync)**: введено у специфікації Bluetooth 5.1 для підтримки кешування бази атрибутів. Якщо клієнт звертається за старими дескрипторами після того, як на сервері відбулася зміна прошивки або динамічне додавання сервісів, сервер блокує запит цим кодом. Клієнт зобов'язаний прочитати системний дескриптор Database Hash (`0x2B2A`), перевірити збіг хешів та за потреби виконати повторне повне сканування бази даних.
