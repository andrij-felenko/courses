# 🧮 Математика бітового пакування: діапазони, ентропія та вирівнювання

Правила упакованого кодування PER (ITU-T X.691) оптимізують використання смуги пропускання, спираючись на точну математичну модель множин можливих значень. Якщо тип даних має скінченну множину допустимих станів, кодування зводиться до відображення цієї множини на двійковий простір мінімальної розмірності.

### Обмежені цілі числа: модель мінімального поля

Нехай задано цілочислову величину `v`, обмежену нижньою межею `lb` (англ. *lower bound*) та верхньою межею `ub` (англ. *upper bound*):

```
lb ≤ v ≤ ub
```

Кількість можливих різних значень, які може приймати змінна, визначається розміром діапазону `R`:

```
R = ub - lb + 1
```

Перший крок кодування полягає у зміщенні значення до невід'ємного базису від нуля:

```
v' = v - lb,    де 0 ≤ v' ≤ R - 1
```

Кількість бітів `b`, необхідна для однозначного кодування будь-якого значення з множини потужністю `R` у рівномірному двійковому коді, дорівнює найменшому цілому числу, не меншому за двійковий логарифм `R`:

```
b = 0,               якщо R = 1     [єдине константне значення не потребує бітів]
b = ceil(log₂(R)),   якщо R > 1     [мінімальна кількість двійкових розрядів]
```

Тут `log₂(R) = ln(R) / ln(2)`.

**Розрахунок кількості бітів для типових діапазонів ASN.1**

Розглянемо покроковий розрахунок для трьох характерних випадків:

**Випадок 1: Вибір із 8 варіантів (наприклад, `ENUMERATED` з 8 елементів або `INTEGER (0..7)`)**
```
R = 7 - 0 + 1                                     [розрахунок потужності множини]
  = 8
b = ceil(log₂(8))                                 [логарифм степеня двійки]
  = ceil(3.0)                                     [2³ = 8, точний збіг]
  = 3 біти
```

**Випадок 2: Діапазон кута азимута `INTEGER (0..359)`**
```
R = 359 - 0 + 1                                   [потужність діапазону]
  = 360
b = ceil(log₂(360))                               [обчислення ентропійного порогу]
  = ceil(ln(360) / ln(2))                         [перехід до натуральних логарифмів]
  = ceil(5.8861 / 0.6931)                         [чисельне ділення]
  = ceil(8.492)                                   [округлення вгору до цілого]
  = 9 бітів
```
Закодоване поле займе рівно 9 бітів. Максимальне значення, яке можна записати в 9 бітах, дорівнює `2⁹ - 1 = 511`. Простір від 360 до 511 залишається невикористаним (надлишковість через дискретність біта).

**Випадок 3: Константне поле `INTEGER (5..5)`**
```
R = 5 - 5 + 1                                     [єдине фіксоване значення]
  = 1
b = 0 бітів                                       [значення відоме зі схеми, 0 бітів на дроті]
```

### Ентропійний аналіз: PER проти оптимального коду Шеннона

Згідно з фундаментальною теоремою Шеннона про кодування для дискретного джерела без пам'яті, теоретична нижня межа середньої довжини повідомлення визначається інформаційною ентропією `H(X)`:

```
H(X) = - ∑ [pᵢ · log₂(pᵢ)]    для всіх i від 1 до R
```
де `pᵢ` — ймовірність появи `i`-го значення.

Якщо всі значення в діапазоні `R` є рівноймовірними (`pᵢ = 1 / R` для всіх `i`), ентропія досягає свого абсолютного максимуму:

```
H_max(X) = - ∑ [(1 / R) · log₂(1 / R)]           [підстановка рівномірного розподілу]
         = - R · (1 / R) · (-log₂(R))             [спрощення суми однакових доданків]
         = log₂(R)                                [ентропія рівномірного джерела]
```

У цьому випадку надлишковість (англ. *redundancy*) упакованого коду PER на одне значення дорівнює:

```
η = b - H_max(X) = ceil(log₂(R)) - log₂(R)
```

Оскільки `0 ≤ ceil(x) - x < 1`, надлишковість PER для рівномірно розподілених величин строго обмежена:

```
0 ≤ η < 1 біт на значення
```

Це означає, що для рівномірного розподілу фіксований бітовий код PER відстає від теоретично ідеального ентропійного кодування (арифметичного або коду Гаффмана) менше ніж на 1 біт на кожне поле, не вимагаючи при цьому складних обчислень і динамічних імовірнісних таблиць.

**Ціна нерівномірного розподілу**

Якщо ж розподіл значень є сильно нерівномірним, виникає надлишковість. Розглянемо приклад виклику в стільниковій мережі з 4 причинами (`EstablishmentCause`):
* `mo-Data` (звичайне передавання даних): ймовірність `p₁ = 0.80`
* `mo-Signalling` (сигналізація): ймовірність `p₂ = 0.15`
* `emergency` (терміновий виклик): ймовірність `p₃ = 0.04`
* `highPriorityAccess`: ймовірність `p₄ = 0.01`

Обчислимо ентропію Шеннона:
```
H(X) = - [0.80·log₂(0.80) + 0.15·log₂(0.15) + 0.04·log₂(0.04) + 0.01·log₂(0.01)]
     = - [0.80·(-0.3219) + 0.15·(-2.7370) + 0.04·(-4.6439) + 0.01·(-6.6439)]
     = - [-0.2575 - 0.4105 - 0.1858 - 0.0664]
     = 0.9202 біта
```

Кодування PER для `R = 4` призначає фіксовану довжину `b = ceil(log₂(4)) = 2` біти.
Надлишковість фіксованого коду становить:
```
Δ = b - H(X) = 2.0 - 0.9202 = 1.0798 біта на повідомлення
```

У радіопротоколах цією різницею свідомо нехтують: детермінований розбір за фіксованими бітовими зсувами є набагато швидшим і стійкішим до збоїв, ніж побітове розкодування префіксних дерев змінної довжини.

### Напівобмежені цілі числа: логарифмічне шкалювання байтів

Коли нижня межа задана, а верхня формально відсутня (`INTEGER (lb..MAX)`), множина значень є нескінченною. Для таких чисел застосовується логарифмічне представлення: спочатку передається кількість байтів `k`, необхідна для запису зміщення `v' = v - lb`, а потім самі `k` байтів значення у беззнаковому двійковому форматі.

Кількість байтів `k` визначається нерівністю:

```
0 ≤ v' < 256ᵏ,    звідки k = 1, якщо v' = 0; інакше k = ceil(log₂₅₆(v' + 1))
```

Оскільки `log₂₅₆(x) = log₂(x) / 8`:

```
k = ceil(ceil(log₂(v' + 1)) / 8)    [розрахунок мінімальної кількості октетних байтів]
```

Загальна кількість бітів для запису напівобмеженого цілого складається з префікса довжини (1 октет для малих чисел) та `k` октетних байтів:

```
L_semi = 8 + 8 · k бітів
```

**Приклад розрахунку для лічильника пакетів `v = 70000` (при `lb = 0`):**
```
v' = 70000
log₂(70001) = 16.095
k = ceil(16.095 / 8) = ceil(2.012) = 3 байти
```
Число 70 000 буде записано 1 байтом довжини (`0x03`) та 3 байтами значення `0x01 0x11 0x70` (разом 4 байти = 32 біти).

### Звуження алфавіту рядкових типів: компресія символів

Однією з найпотужніших математичних оптимізацій у PER є стиснення текстових рядків на основі обмеженого алфавіту (англ. *Permitted Alphabet Constraint*).

У класичних протоколах кожен символ рядка `IA5String`, `VisibleString` або `PrintableString` займає рівно 1 октет (8 бітів або 7 бітів ASCII). Проте якщо схема накладає обмеження `FROM (...)`, PER будує впорядковану множину тільки дозволених символів `A = {c₀, c₁, ..., c_{K-1}}`, де потужність алфавіту дорівнює `K = |A|`.

Кожен символ у невирівняному режимі UPER кодується індексом у цьому локальному алфавіті й займає:

```
b_char = ceil(log₂(K)) бітів
```

**Приклад 1: Шістнадцятковий рядок (Hex string)**

Нехай визначено тип для передачі MAC-адреси або криптографічного хешу:
```asn1
HexString ::= VisibleString (FROM ("0".."9" | "A".."F")) (SIZE(16))
```

Розрахунок бітів:
```
K = 10 + 6                                        [10 цифр від 0 до 9 + 6 літер від A до F]
  = 16
b_char = ceil(log₂(16))                           [кількість бітів на один символ]
       = 4 біти
Довжина 16 символів · 4 біти                      = 64 біти (8 байтів)
```
У стандартному представленні ASCII такий рядок зайняв би `16 · 8 = 128` бітів (16 байтів). PER автоматично досягає рівно двократного стиснення (стискає до 4 бітів на символ) без застосування алгоритмів LZW або gzip.

**Приклад 2: Телефонний номер абонента (E.164)**

```asn1
PhoneNumber ::= NumericString (FROM ("0".."9" | "#" | "*" | ",")) (SIZE(1..15))
```

Розрахунок бітів:
```
K = 10 + 3 = 13 символів
b_char = ceil(log₂(13))                           [ceil(3.7004)]
       = 4 біти на символ
```
Номер довжиною 12 цифр займе: `12 · 4 = 48` бітів (6 байтів) замість 12 байтів у незахищеному вигляді.

### Зазвичай малі невід'ємні цілі (NSNNI)

У протоколах сигналізації часто зустрічаються величини, які теоретично можуть приймати великі значення, але на практиці у 99% випадків не перевищують кількох одиниць (наприклад, індекси додаткових розширень протоколу, номери рідкісних помилок). Для таких величин PER використовує концепцію **Normally Small Non-Negative Integer** (NSNNI).

Математичне правило кодування NSNNI значення `k ≥ 0`:

```
f_NSNNI(k) = 0 || bin₆(k),              якщо 0 ≤ k ≤ 63   [1 біт префікса 0 + 6 бітів значення]
f_NSNNI(k) = 1 || f_SemiConstrained(k),  якщо k ≥ 64       [1 біт префікса 1 + довжина + октети]
```

Якщо `k ≤ 63`, поле займає рівно `1 + 6 = 7` бітів.
Якщо `k ≥ 64`, записується біт `1`, за яким іде напівобмежене ціле (лічильник октетних байтів + мінімальна кількість байтів для запису `k`).

**Математичне сподівання довжини NSNNI**

Нехай розподіл значень `k` задається дискретним геометричним законом із параметром успіху `p` (ймовірність того, що `k < 64` становить `P(k < 64) = 1 - (1 - p)⁶⁴`):

Якщо `P(k < 64) = 0.99`, а у випадку `k ≥ 64` середня довжина напівобмеженого запису становить 2 байти (16 бітів + 8 бітів довжини = 24 біти):

```
E[L_NSNNI] = 0.99 · 7 + 0.01 · (1 + 24)           [зважена сума короткої та довгої форм]
           = 6.93 + 0.25
           = 7.18 біта
```

Для порівняння, фіксоване 16-бітове ціле витрачало б 16 бітів постійно, а формат varint Protobuf витрачав би 8 або 16 бітів. Схема NSNNI досягає математичного оптимуму близько 7.2 бітів.

### Кодування бітових масок (BIT STRING) зі змінним розміром

Для типу `BIT STRING (SIZE(min..max))` довжина маски є випадковою величиною `L ∈ [min .. max]`.

PER оптимізує передачу довжини залежно від потужності діапазону `S = max - min + 1`:

1. **Фіксована довжина (`min = max = N`):**
   Довжина `L` не передається взагалі (`b_len = 0`). Передаються рівно `N` бітів значення.
2. **Малий діапазон (`max ≤ 16` або `S ≤ 65536` у UPER):**
   Довжина `L` кодується як обмежене ціле число в діапазоні `[min .. max]`, що займає:
   ```
   b_len = ceil(log₂(max - min + 1)) бітів
   ```
   За цим префіксом слідують рівно `L` бітів даних.
3. **Необмежена довжина (`max > 65536` або розмір без обмежень):**
   Довжина кодується за загальним правилом детермінанта довжини (1 октет для 0..127, 2 октети для 128..16K або фрагментація).

**Розрахунок для `BIT STRING (SIZE(1..8))`**

```
S = 8 - 1 + 1 = 8
b_len = ceil(log₂(8)) = 3 біти
```
Якщо передається 5 бітів даних `10110₂`:
* Префікс довжини: `5 - 1 = 4 = 100₂` (3 біти).
* Біти значення: `10110₂` (5 бітів).
* Разом у потоці: `100 10110₂` = рівно 8 бітів (1 октет).

У BER такий бітовий рядок зайняв би: тег `0x03` (1 байт) + довжина `0x02` (1 байт) + лічильник невикористаних бітів `0x03` (1 байт) + 1 байт даних = 4 байти (32 біти). Стиснення PER становить `32 / 8 = 4.0x`.

### Математична модель вибору гілок (CHOICE)

Тип `CHOICE` представляє диз'юнктне об'єднання множин (варіантний тип). Нехай кореневий список вибору містить `C` альтернатив, пронумерованих від 0 до `C - 1`.

1. **Якщо маркер розширення відсутній (`...` немає):**
   Індекс обраної гілки `c ∈ {0, ..., C - 1}` кодується рівно у:
   ```
   b_choice = ceil(log₂(C)) бітів
   ```
   Після індексу безпосередньо слідують біти значення обраного типу.

2. **Якщо присутній маркер розширення (`...`):**
   Першим передається **біт розширення** (англ. *extension addition flag*):
   * Якщо обрано кореневу гілку (`c < C`): передається біт `0`, за яким слідує індекс гілки у `ceil(log₂(C))` бітах і значення поля.
   * Якщо обрано додану в новій версії гілку (`c ≥ C`): передається біт `1`, за яким індекс розширення `e = c - C` записується як NSNNI `f_NSNNI(e)`. Значення поля упаковується як **відкритий тип** (англ. *Open Type*): спочатку лічильник довжини в байтах, потім самі байти значення.

**Розрахунок середніх витрат бітів для розширюваного CHOICE:**

Нехай ймовірність вибору базових гілок становить `P_root = 0.98`, а нових розширень — `P_ext = 0.02`. Кількість базових альтернатив `C = 4` (`ceil(log₂(4)) = 2` біти):

```
E[L_tag] = P_root · (1 + 2) + P_ext · (1 + 7 + 8) [базові 3 біти проти розширення з байтом довжини]
         = 0.98 · 3 + 0.02 · 16
         = 2.94 + 0.32
         = 3.26 біта
```
Накладні витрати на підтримку нескінченного простору майбутніх розширень становлять лише 0.26 біта на повідомлення.

### Канонічне сортування множин (SET OF) у CPER

У канонічних правилах CPER (Canonical PER) для гарантії єдиного бітового представлення елементи конструкції `SET OF Type` повинні передаватися у строго визначеному лексикографічному порядку.

Нехай множина містить `M` елементів `S = {e₁, e₂, ..., e_M}`. Кожен елемент `eᵢ` спочатку кодується за стандартними правилами PER в окремий бітовий рядок `b(eᵢ)` довжиною `lᵢ` бітів.

Правило канонічного впорядкування елементів у вихідному потоці:

```
e_j ≺ e_k  ⟺  b_pad(e_j) <_lex b_pad(e_k)
```
де `b_pad(e)` — це бітовий рядок `b(e)`, доповнений нульовими бітами праворуч до найближчої межі октету, а `<_lex` — строгий лексикографічний порядок порівняння масивів октетів зліва направо:

1. Байти порівнюються як беззнакові цілі числа `uint8_t` від 0 до 255.
2. Якщо перші `min(len_j, len_k)` байтів збігаються, коротший рядок вважається меншим за довший.

Оскільки відображення значення типу на його закодований двійковий вектор `e ↦ b(e)` є строгою ін'єкцією, лексикографічний порядок на множині двійкових рядків є повним строгим порядком. Це гарантує існування єдиної бієкції між довільною математичною множиною значень і вихідним бітовим потоком CPER, що забезпечує абсолютну відтворюваність криптографічних гешів і цифрових підписів.

### Дійсні числа (REAL): логарифмічне нормування експоненти

Тип `REAL` у PER кодується за правилами двійкового представлення з плаваючою комою:

```
v = M · Bᴱ
```
де `M` — мантиса (ціле число), `B ∈ {2, 8, 16}` — основа степеня (зазвичай `B = 2`), а `E` — експонента (ціле число зі знаком).

Кодування дійсного числа у PER виконується за алгоритмом:
1. Якщо `v = 0`, записується 1 октет довжини `0x00` (значення займає 0 октетних байтів).
2. Якщо `v = +∞` або `-∞`, записується спеціальний заголовок особливих значень.
3. У загальному випадку першим записується октет конфігурації (біт знака мантиси, біти основи `B`, 2 біти формату довжини експоненти).
4. За ним передається експонента `E` (1, 2, 3 або `n` байтів у доповняльному двійковому коді) та беззнакова мантиса `M`.

Завдяки цьому дійсні числа записуються точно з потрібною точністю, без зайвих байтів розширення до стандартного IEEE 754, якщо мантиса поміщається у меншу кількість розрядів.

### Математичне сподівання паддінгу: UPER проти APER

У невирівняному режимі UPER усі бітові поля слідують безпосередньо одне за одним. Загальна довжина повідомлення з `K` полів із довжинами `b₁, b₂, ..., b_K` бітів становить:

```
L_UPER = ∑ b_k    (бітів)
```

Загальна кількість байтів у каналі після фінального доповнення до кінця кадру:

```
N_UPER = ceil(L_UPER / 8)    (байтів)
```

Кількість втрачених бітів паддінгу наприкінці всього UPER-повідомлення дорівнює:

```
W_UPER = (8 - (L_UPER mod 8)) mod 8
```
Середні втрати на все повідомлення становлять рівно `3.5` біта (якщо значення `L_UPER mod 8` розподілені рівномірно на множині `{0, 1, ..., 7}`).

У вирівняному режимі APER правила ITU-T X.691 вимагають вирівнювання на межу октету перед:
1. Полями довжиною понад 2 байти (`R > 65536`).
2. Рядками `OCTET STRING` та `BIT STRING` довжиною понад 2 байти.
3. Префіксами довжини у відкритих типах `Open Type`.

Нехай у повідомленні зустрічається `M` точок вирівнювання. У кожній точці поточна бітова позиція `pos` доповнюється нулями до найближчого кратного 8:

```
pad_m = (8 - (pos_m mod 8)) mod 8
```

Якщо припустити, що перед кожною точкою вирівнювання значення зміщення `pos_m mod 8` є незалежною випадковою величиною, рівномірно розподіленою на `{0, 1, ..., 7}`:

```
E[pad_m] = (1 / 8) · ∑ i   для i від 0 до 7
         = (0 + 1 + 2 + 3 + 4 + 5 + 6 + 7) / 8
         = 28 / 8
         = 3.5 біта
```

Сумарне математичне сподівання кількості бітів паддінгу в повідомленні APER з `M` точками вирівнювання становить:

```
E[W_APER] = 3.5 · M + 3.5 = 3.5 · (M + 1) бітів
```

**Порівняння втрат на прикладі 10 полів**

Нехай повідомлення містить 10 полів великих цілих або рядків (`M = 10`):
* У UPER середні втрати на паддінг: `E[W_UPER] = 3.5` біта (менше половини байта).
* У APER середні втрати на паддінг: `E[W_APER] = 3.5 · 11 = 38.5` бітів (майже 5 байтів надлишкового службового сміття).

Цей розрахунок чітко демонструє, чому для вузьких стільникових каналів LTE/5G RRC було обрано саме UPER, тоді як для дротових інтерфейсів базових станцій (S1AP/NGAP) обрано APER заради високої швидкості обробки.

### Довжини та нелінійна кускова фрагментація

Для полів змінної довжини (масивів `SEQUENCE OF`, рядків `OCTET STRING`, невідомих розширень) правила PER використовують кускову функцію кодування лічильника довжини `n`.

Довжина `n` кодується за таким правилом:

```
f(n) = 0 || bin₇(n),                          якщо 0 ≤ n ≤ 127        [1 октет, 7 бітів значення]
f(n) = 10 || bin₁₄(n),                        якщо 128 ≤ n ≤ 16383    [2 октети, 14 бітів значення]
f(n) = Фрагмент(m, 16384) + f(n - m·16384),   якщо n ≥ 16384          [кускова фрагментація]
```
де `||` позначає конкатенацію бітових рядків, а `bin_k(n)` — запис числа `n` у `k` бітах.

У режимі фрагментації обирається найбільший цілий множник `m ∈ {1, 2, 3, 4}`, такий що `m · 16384 ≤ n`:

```
m = min(4, floor(n / 16384))
```

Префікс фрагмента записується як `11 || bin₆(m)`, де `bin₆(m)` приймає значення:
* `m = 1` (16 384 елементи): префікс `11000001₂` (`0xC1`)
* `m = 2` (32 768 елементів): префікс `11000010₂` (`0xC2`)
* `m = 3` (49 152 елементи): префікс `11000011₂` (`0xC3`)
* `m = 4` (65 536 елементів): префікс `11000100₂` (`0xC4`)

Після запису `m · 16384` елементів алгоритм рекурсивно застосовується до залишку:

```
n_new = n - m · 16384
```

Процес повторюється доти, доки залишок `n_new` не стане меншим за 16 384, після чого записується фінальний 1- або 2-байтовий заголовок довжини.

**Покроковий приклад фрагментації масиву з 150 000 елементів**

```
Крок 1: n = 150000
m₁ = min(4, floor(150000 / 16384)) = min(4, 9) = 4
Розмір блоку = 4 · 16384 = 65536 елементів
Заголовок = 11000100₂ (0xC4)
Залишок n₁ = 150000 - 65536 = 84464

Крок 2: n = 84464
m₂ = min(4, floor(84464 / 16384)) = min(4, 5) = 4
Розмір блоку = 4 · 16384 = 65536 елементів
Заголовок = 11000100₂ (0xC4)
Залишок n₂ = 84464 - 65536 = 18928

Крок 3: n = 18928
m₃ = min(4, floor(18928 / 16384)) = min(4, 1) = 1
Розмір блоку = 1 · 16384 = 16384 елементи
Заголовок = 11000001₂ (0xC1)
Залишок n₃ = 18928 - 16384 = 2544

Крок 4: n = 2544
2544 < 16384, але 2544 ≥ 128 → застосовуємо 2-байтову форму:
Заголовок = 10₂ || bin₁₄(2544)
2544 у 14 бітах = 00100111110000₂
Заголовок у байтах = 10001001 11110000₂ (0x89 0xF0)
Передаються фінальні 2544 елементи.
```

Сумарна перевірка довжини розпакованих блоків:

```
65536 + 65536 + 16384 + 2544 = 150000 елементів.
```

Ця кускова схема гарантує, що приймачу не потрібно виділяти нескінченно великі динамічні масиви пам'яті під невідомі повідомлення: декодер може обробляти потік фіксованими порціями по 16–64 КБ без ризику переповнення буфера.
