# ⚙️ CRC за таблицею: як зробити перевірку майже безкоштовною

Поле [CRC у пакеті](book:communications/packet-design) рахується бітовою арифметикою: для кожного байта прокручуємо вісім кроків зсуву й умовного XOR із поліномом. Це чесно й коротко, але на потоці в десятки кілобайтів за секунду вісім ітерацій **на кожен байт** — відчутна ціна для скромного мікроконтролера. Хороша новина: усю цю внутрішню вісімку можна порахувати **наперед**, по разу для кожного з 256 можливих байтів, і скласти в таблицю. Тоді в гарячому циклі лишається **одна** дія на байт — звернення до таблиці. Саме так CRC рахують у реальній прошивці.

Прикинемо ціну на числах. Хай телеметрія йде на 115200 бод — це приблизно 11520 байтів за секунду. Бітовий CRC робить вісім ітерацій внутрішнього циклу на кожен байт, тобто близько 92 тисяч прокруток зсуву-XOR щосекунди — і це лише на прийомі, стільки ж на передачі. Для процесора на десятки мегагерц, що паралельно веде регулювання, читає давачі й крутить логіку керування, така стала фонова витрата зовсім не дрібниця. Тому внутрішню вісімку прибирають зовсім.

**Звідки береться таблиця.** Придивімося, що робить бітовий CRC-8 (поліном `0x07`) з одним байтом. Він бере поточне значення CRC, XOR-ить його з байтом і вісім разів зсуває з умовним XOR. Ключове спостереження: результат після цих восьми кроків залежить **лише** від одного восьмибітного числа — від `crc ^ byte`. А таких чисел усього 256. Отже, можна раз порахувати, у що перетворюється кожне з них, і запам'ятати:

:::tabs
```cpp
#include <stdint.h>
#include <stddef.h>

uint8_t crc8_table[256];

// Заповнити таблицю один раз на старті (поліном 0x07)
void crc8_init(void) {
    for (int i = 0; i < 256; i++) {
        uint8_t crc = (uint8_t)i;
        for (int b = 0; b < 8; b++)
            crc = (crc & 0x80) ? (uint8_t)((crc << 1) ^ 0x07)
                               : (uint8_t)(crc << 1);
        crc8_table[i] = crc;
    }
}
```
```python
# Порахувати таблицю один раз (поліном 0x07)
def crc8_init():
    table = []
    for i in range(256):
        crc = i
        for _ in range(8):
            crc = ((crc << 1) ^ 0x07) & 0xFF if crc & 0x80 else (crc << 1) & 0xFF
        table.append(crc)
    return table

crc8_table = crc8_init()
```
:::

Кілька значень для самоперевірки: `crc8_table[0x00]` = `0x00`, `crc8_table[0x01]` = `0x07` (це сам поліном — логічно, бо одиничний старший біт зсувається й XOR-иться рівно раз), `crc8_table[0x02]` = `0x0E`, `crc8_table[0x03]` = `0x09`. Таблиця займає 256 байтів флешу — копійки навіть для найдрібнішого чипа.

**Гарячий цикл.** Маючи таблицю, обхід даних згортається до одного рядка на байт:

:::tabs
```cpp
uint8_t crc8_fast(const uint8_t *p, size_t n) {
    uint8_t crc = 0x00;
    for (size_t i = 0; i < n; i++)
        crc = crc8_table[crc ^ p[i]];   // одна вибірка замість восьми зсувів
    return crc;
}
```
```python
def crc8_fast(data):
    crc = 0x00
    for byte in data:
        crc = crc8_table[crc ^ byte]   # одна вибірка замість восьми зсувів
    return crc
```
:::

Вираз `crc8_table[crc ^ p[i]]` робить те саме, що й уся внутрішня вісімка бітового варіанта, але за одне звернення до пам'яті. На тих самих даних обидва дають однаковий результат: для байтів `03 12 41 42` (LEN, ID і двоє даних із прикладу пакета) і таблична, і бітова версія повертають `0xC9`. Виграш у швидкості — приблизно у вісім разів, бо внутрішній цикл зник зовсім.

> 🔧 **Навіщо це.** Коли по UART ллється суцільний потік телеметрії, CRC рахується **на кожному** прийнятому й відправленому байті. Бітовий варіант на такій швидкості легко з'їдає помітну частку процесорного часу; таблиця знімає це питання начисто й коштує лише 256 байтів пам'яті. Тому в робочому коді CRC майже завжди табличний — бітовий лишають хіба для демонстрації або там, де пам'ять рахують поштучно.

**Де живе таблиця.** Заповнювати її на старті `crc8_init()` — не єдиний шлях, і часто не найкращий. Якщо таблицю порахувати наперед (хоч тим самим скриптом на комп'ютері) і вписати як готовий масив із `const`, компілятор покладе її у **флеш**, а не в дорогоцінну оперативну пам'ять, і не витратить жодного такту на ініціалізацію:

```c
static const uint8_t crc8_table[256] = {
    0x00, 0x07, 0x0E, 0x09, 0x1C, 0x1B, 0x12, 0x15,
    /* …решта 248 значень для полінома 0x07… */
};
```

На дрібних мікроконтролерах, де оперативної пам'яті лічені кілобайти, це відчутна різниця: 256 байтів сталих у флеші не шкода, а ті самі 256 байтів у ОЗП могли б знадобитися під буфери. Розрахунок таблиці на старті лишають хіба тоді, коли поліном обирається вже під час роботи.

**А якщо CRC рахує залізо.** Багато сучасних мікроконтролерів мають **апаратний** блок CRC: завантажуєш у регістр байти, читаєш готовий результат — без жодної таблиці й без процесорних тактів на сам обхід. Ціна за швидкість — менша гнучкість: апаратний блок жорстко зашитий під певний поліном (часто CRC-32 чи фіксований CRC-16), і його параметри — той самий поліном, старт, відображення — треба **точно** звірити з тим, що рахує другий бік протоколу. Якщо інша прошивка рахує CRC програмно з іншим набором параметрів, числа не зійдуться, дарма що формула «та сама». Тому навіть з апаратним блоком знати чотири параметри CRC обов'язково.

**Один поліном на обидва кінці.** Таблиця нерозривно зв'язана з поліномом: передавач і приймач мусять користуватися **тим самим** генератором, інакше їхні CRC ніколи не зійдуться, і кожен цілий пакет виглядатиме побитим. Тому поліном — частина «контракту» протоколу нарівні з форматом полів. Для CRC-8 поширений `0x07`, для CRC-16 — `0x1021` чи `0x8005`; бери усталений, а не вигаданий, бо в усталених добре відомі гарантії виявлення помилок. Для ширших CRC принцип той самий, лише таблиця має 256 записів по 16 чи 32 біти — і обхід так само лишається одним зверненням на байт.

**Поліном — це ще не вся домовленість.** Тут ховається пастка, на якій сходяться нанівець багато вечорів: один поліном можуть реалізувати **по-різному**, і два коректні CRC із тим самим `0x1021` дадуть **різні** числа. Повний опис будь-якого стандартного CRC — це чотири параметри, не один:

- **поліном** — який генератор (наприклад, `0x1021`);
- **початкове значення** (*init*) — чим заповнити `crc` перед обходом: `0x0000` чи `0xFFFF`. Ненульовий старт потрібен, щоб CRC ловив **додані спереду нулі** (інакше пакет, що починається з нулів, дає той самий CRC, що й коротший);
- **відображення** (*reflection*) — чи обробляти біти в кожному байті від молодшого до старшого (LSB-first) чи навпаки (MSB-first). Код вище — MSB-first; «віддзеркалена» реалізація зсуває в інший бік і дає інше число;
- **кінцевий XOR** (*xorout*) — чи XOR-ити готовий результат із маскою наприкінці.

Звідси й те, що той самий `0x1021` живе у двох різних усталених варіантах: **CRC-16/XMODEM** (init `0x0000`, без відображення) і «справжній CCITT» у віддзеркаленій формі з іншим стартом. Тому, домовляючись про CRC між двома прошивками, фіксуй **усі чотири** параметри, а не лише поліном — і найкраще бери готовий профіль із каталогу CRC, а до нього звіряйся за відомим тестовим вектором. Кожен профіль має свій: для CRC-16/CCITT-FALSE (`0x1021`, init `0xFFFF`, без відображення) CRC рядка `"123456789"` дорівнює `0x29B1`, тоді як XMODEM на тому самому поліномі дає `0x31C3`. Збіглося твоє число з еталонним — профіль точно той самий на обох кінцях.

**Чого CRC не вміє.** Корисно тверезо знати межу: CRC захищає від **випадкового** псування — шуму на лінії, наведень, поодиноких збитих бітів. Він **не** захищає від навмисної підміни. Зловмисник, що хоче змінити вміст пакета, легко перерахує й правильний CRC для свого підробленого вмісту — адже алгоритм і поліном відкриті. CRC — це детектор помилок, а не підпис: для захисту від підробки потрібні криптографічні засоби (наприклад, код автентифікації повідомлення на секретному ключі), і це зовсім інша задача. У звичайному дротовому чи радіообміні між своїми пристроями підміни зазвичай не бояться, тож CRC цілком на місці; але плутати «цілий» із «справжній» не можна. І ще одне практичне: CRC ловить ушкодження лише в тих байтах, які ним **накриті**. Якщо лишити поле поза розрахунком (скажімо, забути ID), то збій саме в ньому пройде непоміченим. Тому межі покриття — від першого службового поля до останнього байта даних — варто задати свідомо й однаково на обох кінцях.

Підсумок простий. Бітовий CRC добрий, щоб **зрозуміти**, що відбувається; табличний — щоб **це працювало** на реальній швидкості за ціну в кілька сотень байтів пам'яті. Але хай реалізація буде хоч бітова, хоч таблична, хоч апаратна — головне лишається тим самим: поліном і всі чотири параметри мусять бути однакові на обох кінцях. CRC — це частина того ж «контракту», що й розкладка полів пакета: щойно обидві сторони рахують його однаково, контроль цілості стає тим тихим вартовим, який мовчки відсіює побите й пропускає лише ціле.
