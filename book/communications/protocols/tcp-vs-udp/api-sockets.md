# 📋 Сокет-API: як вибрати TCP чи UDP у коді

Увесь вибір між надійним потоком і швидкою датаграмою робиться одним аргументом функції `socket()` — а далі два протоколи вимагають різної послідовності викликів. Тут зібрано ці послідовності, підписи функцій POSIX (той самий C-інтерфейс, який обгортають усі мови й фреймворки) і пастки, що найчастіше кусають.

## Один перемикач

```c
int socket(int domain, int type, int protocol);
```

Аргумент `type` і є розвилкою:

- `SOCK_STREAM` → **TCP**: надійний потік байтів зі з'єднанням.
- `SOCK_DGRAM` → **UDP**: окремі датаграми без з'єднання.

`domain` — сімейство адрес (`AF_INET` для IPv4, `AF_INET6` для IPv6); `protocol` зазвичай `0` (типовий для цього типу).

## Послідовність викликів

Різниця тут не лише в іменах функцій, а в самій моделі роботи. TCP **орієнтований на з'єднання**: спершу встановлюєш канал, далі ллєш у нього байти, наче в трубу, а адресу більше не згадуєш — вона зафіксована. UDP **орієнтований на повідомлення**: жодного каналу немає, і кожне відправлення — самостійний лист з адресою просто на конверті. Звідси й уся відмінність послідовностей нижче.

**TCP-клієнт** — з'єднайся, потім лий потік:

```c
int fd = socket(AF_INET, SOCK_STREAM, 0);
connect(fd, (struct sockaddr*)&server, sizeof server);
send(fd, buf, len, 0);        // адреса вже відома — з connect()
recv(fd, rbuf, sizeof rbuf, 0);
close(fd);
```

**TCP-сервер** — прив'яжись до порту, слухай, приймай кожне з'єднання окремо:

```c
int s = socket(AF_INET, SOCK_STREAM, 0);
bind(s, (struct sockaddr*)&addr, sizeof addr);
listen(s, backlog);                       // черга очікування
int c = accept(s, NULL, NULL);            // НОВИЙ сокет на це з'єднання
recv(c, rbuf, sizeof rbuf, 0);
```

`accept()` повертає **окремий** дескриптор на кожен клієнт; вихідний `s` лише слухає далі.

**UDP** — жодного з'єднання, адреса їде з кожним пакетом:

```c
int fd = socket(AF_INET, SOCK_DGRAM, 0);
bind(fd, (struct sockaddr*)&addr, sizeof addr);   // потрібно, лише щоб ПРИЙМАТИ
sendto(fd, buf, len, 0, (struct sockaddr*)&dst, sizeof dst);

struct sockaddr_in from; socklen_t flen = sizeof from;
recvfrom(fd, rbuf, sizeof rbuf, 0, (struct sockaddr*)&from, &flen);
```

Немає ні `connect()`, ні `listen()`, ні `accept()`. Хто відправник — дізнаєшся з `from`, який заповнює `recvfrom()`.

## Підписи

```c
int  bind(int fd, const struct sockaddr *addr, socklen_t len);
int  listen(int fd, int backlog);
int  accept(int fd, struct sockaddr *addr, socklen_t *len);
int  connect(int fd, const struct sockaddr *addr, socklen_t len);

ssize_t send(int fd, const void *buf, size_t n, int flags);
ssize_t recv(int fd, void *buf, size_t n, int flags);
ssize_t sendto(int fd, const void *buf, size_t n, int flags,
               const struct sockaddr *dst, socklen_t dstlen);
ssize_t recvfrom(int fd, void *buf, size_t n, int flags,
                 struct sockaddr *src, socklen_t *srclen);
```

Різниця видна вже з підписів: `send`/`recv` адреси **не несуть** (вона зафіксована з'єднанням), а `sendto`/`recvfrom` тягнуть її **щоразу** — бо в UDP кожна датаграма самостійна.

## Пастки

- **TCP-`send()` може відправити менше, ніж просили.** Повернене число — скільки байтів реально прийнято в буфер; решту треба досилати в циклі:

```c
size_t off = 0;
while (off < len) {
    ssize_t k = send(fd, buf + off, len - off, 0);
    if (k < 0) { /* помилка */ break; }
    off += k;
}
```

- **TCP-`recv()` повертає `0` — це кінець потоку** (інший бік закрив з'єднання), а не «нема даних». `>0` — стільки байтів прийшло, `-1` — помилка.
- **У TCP немає меж повідомлень.** Один `recv()` може віддати півповідомлення або два злиплих. Де кінчається твій «кадр» — розмічай сам (довжиною спереду чи роздільником).
- **UDP-`recvfrom()` віддає рівно одну датаграму** — цілу або нічого. Якщо буфер менший за неї, **надлишок мовчки відкидається**: бери буфер із запасом.
- **UDP нічого не повідомляє про долю пакета.** Немає ні кінця потоку, ні звістки про втрату — надіслав і не знаєш, чи дійшло.
- **Велика UDP-датаграма крихка.** Стеля — близько 65 кілобайтів, але на практиці варто триматися нижче розміру кадру мережі (приблизно 1472 байти у звичайному Ethernet). Більшу датаграму рівень IP ріже на фрагменти, і втрата бодай **одного** фрагмента губить **усю** датаграму цілком — тому дрібніші пакети доходять надійніше.
- **«Приєднаний» UDP.** Виклик `connect()` на `SOCK_DGRAM` не встановлює з'єднання, а лише **фіксує співрозмовника**: далі можна слати простим `send()`/`recv()`, і ядро повертатиме помилки (наприклад, ICMP «порт недосяжний») від цього одного адресата.

## Блокування, помилки, закриття

За замовчуванням ці виклики **блокують**: `recv()` чекає на дані, `accept()` — на клієнта, `connect()` — на рукостискання. Щоб обслуговувати багато з'єднань водночас, сокети переводять у неблокувальний режим і чекають на всі разом (`poll`/`epoll`/`select`) — один потік тягне тисячі з'єднань. Клієнтові, до речі, `bind()` не потрібен: ядро само призначить йому вільний тимчасовий порт джерела при першому ж `connect()` чи `sendto()`.

Помилки два протоколи повертають по-різному. TCP-`connect()` на закритий порт **швидко падає** з `ECONNREFUSED` (у відповідь прийшов RST). UDP-`sendto()` на закритий порт локально **вдається** (з'єднувати нема чого), і про недосяжний порт дізнаєшся хіба згодом — та й то лише на «приєднаному» сокеті, через ICMP-повідомлення в `errno`.

Закриття теж різне за можливостями. `close()` просто звільняє дескриптор; а `shutdown()` уміє закрити **половину** TCP-потоку — перестати слати (пославши FIN), але й далі **дочитувати** те, що шле інший бік, поки й він не завершить.

## Тільки UDP: широкомовлення й група

Одну датаграму UDP можна адресувати **багатьом** одержувачам одразу — `sendto()` на широкомовну (broadcast) чи групову (multicast) адресу, увімкнувши відповідний параметр сокета. TCP так не вміє **в принципі**: з'єднання має рівно два кінці, тож розіслати щось «усім у сегменті» через нього неможливо. Це різниця не швидкості, а **можливостей** — тому виявлення пристроїв у локальній мережі й одночасну роздачу стану роблять саме на UDP. Щоб, скажімо, знайти всі камери в підмережі, застосунок шле один широкомовний запит — і кожна, що його почула, озивається; через TCP довелося б по черзі стукати в кожну можливу адресу окремо.

## Те саме мовою високого рівня

Обгортки лише перейменовують ці виклики. У Python той самий вибір — константа в конструкторі:

```python
import socket
tcp = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # потік
udp = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # датаграми
```

А в ESP32 (Arduino) `WiFiClient` — це `SOCK_STREAM`, `WiFiUDP` — `SOCK_DGRAM`; під капотом ті самі `connect`/`send` проти `sendto`/`recvfrom`.
