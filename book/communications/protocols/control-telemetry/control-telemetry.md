# Керування й телеметрія

Коли кажуть «апарат на радіокеруванні», легко уявити **одну** радіолінію: пульт зв'язується з апаратом, і все. У реальній системі працює **кілька** радіоліній із **різними ролями**, і плутати їх — типова помилка новачка. Розкласти ці ролі по поличках — найпростіший спосіб зрозуміти весь радіозв'язок апарата.

### Дві (а часто три) радіолінії

![Радіозв'язок апарата — це не одна лінія, а кілька ролей](/book/communications/protocols/control-telemetry/img/two-links.svg)
*Угору йде керування — команди пілота чи автопілота (потребують низької затримки). Униз і вгору йде телеметрія: стан апарата вниз (висота, GPS, заряд), налаштування вгору. Часто є й третя лінія — відео (FPV) для картинки з камери. Кожна лінія має свої вимоги, тому їх зазвичай розділяють.*

Ролей, по суті, дві головні плюс одна допоміжна. **Керування** (від лат. *contrarotulus* — «звірочний список», звідки англ. *control*) — команди йдуть **угору**, від пілота до апарата: куди летіти, який режим. Це **висхідний канал** (англ. *uplink*). **Телеметрія** (від грец. *tēle* — «далеко» + *metron* — «міра») — дані йдуть переважно **вниз**, від апарата до землі: висота, координати, заряд, попередження; а налаштування й команди — угору. Це переважно **низхідний канал** (англ. *downlink*) із зворотним підканалом. Часто є й третя — **відео** (англ. *FPV, first-person view* — «огляд від першої особи»): картинка з бортової камери вниз. Кожна з цих ліній — наче окрема розмова з власними правилами, і саме тому їх зазвичай **розділяють**.

### Лінія керування: «віжки» апарата

Найкритичніша лінія — **керування**, бо від неї залежить, чи слухається апарат узагалі.

![Лінія керування несе мало даних, але миттєво й безвідмовно](/book/communications/protocols/control-telemetry/img/control-link.svg)
*Лінія керування несе команди — положення стіків пульта, розкладені на «канали», або команди автопілота. Вимоги: низька затримка (запізнена команда = аварія), висока надійність (втрата → безпечний режим), мало даних (лише положення стіків і режим). Якщо лінія падає — спрацьовує failsafe.*

Лінія керування — це **віжки**. Вона несе **мало** даних: по суті, лише положення стіків пульта, розкладені на окремі **канали** (від лат. *canalis* — «жолоб, русло»): газ, крен, тангаж, нишпорення, перемикачі режимів. Але ці крихти мусять долітати **блискавично** й **безвідмовно**. Запізнена на півсекунди команда «вирівнятися» — і апарат уже впав; загублена команда — і він не послухався. Тому головні вимоги — **мінімальна затримка** й **максимальна надійність**, навіть ціною низької швидкості даних.

Наскільки блискавично? У сучасних системах радіокерування на кшталт ExpressLRS затримка лінії прямо випливає з **частоти пакетів**: 1000 пакетів за секунду дають близько 1 мс, 500 — близько 2 мс, 250 — близько 4 мс, а на дальніх 50 пакетах за секунду це вже близько 20 мс. Вища частота — менша затримка, але коротша дальність, тож пілот свідомо обирає компроміс. Це **висхідний потік команд** із частотою оновлення в **сотні разів за секунду** — на порядки частіше, ніж низхідна телеметрія.

Лінія керування **«священна»**: якщо вона зникає (вийшов за межу дальності, заглушили, сіла батарея пульта), вмикається **failsafe** (англ. *fail-safe* — «безпечний за відмови»). Апарат сам повертається додому — режим **RTL** (англ. *return to launch* — «повернення до точки зльоту») — або сідає. Як саме [пульт прив'язується до приймача й кодує команди](book:communications/rc-link) — окрема велика тема.

🔧 **Навіщо це.** Failsafe тримається на одній простій ідеї: борт мусить **сам** помітити, що команди перестали надходити, і не чекати, поки впаде. На практиці це лічильник часу від останнього валідного кадру керування — щотакту прошивка перевіряє, чи не перевищив він поріг.

:::tabs
```cpp
// викликається з основного циклу польотного контролера (~раз на такт)
void rc_failsafe_tick(uint32_t now_ms) {
    const uint32_t RC_TIMEOUT_MS = 500;   // 0.5 с без валідного кадру = втрата
    if (now_ms - g_last_rc_frame_ms > RC_TIMEOUT_MS) {
        enter_failsafe(FS_RTL);           // повернення додому (RTL)
    }
}
// приймач: щойно прийшов валідний кадр керування — оновлюємо мітку часу
void on_rc_frame_valid(uint32_t now_ms) { g_last_rc_frame_ms = now_ms; }
```
```py
RC_TIMEOUT_MS = 500   # 0.5 с без валідного кадру = втрата

# викликається з основного циклу польотного контролера (~раз на такт)
def rc_failsafe_tick(now_ms):
    if now_ms - g_last_rc_frame_ms > RC_TIMEOUT_MS:
        enter_failsafe(FS_RTL)            # повернення додому (RTL)

# приймач: щойно прийшов валідний кадр керування — оновлюємо мітку часу
def on_rc_frame_valid(now_ms):
    global g_last_rc_frame_ms
    g_last_rc_frame_ms = now_ms
```
```js
const RC_TIMEOUT_MS = 500;   // 0.5 с без валідного кадру = втрата

// викликається з основного циклу польотного контролера (~раз на такт)
function rcFailsafeTick(nowMs) {
    if (nowMs - gLastRcFrameMs > RC_TIMEOUT_MS) {
        enterFailsafe(FS_RTL);            // повернення додому (RTL)
    }
}
// приймач: щойно прийшов валідний кадр керування — оновлюємо мітку часу
function onRcFrameValid(nowMs) { gLastRcFrameMs = nowMs; }
```
:::

Поріг беруть із запасом над періодом кадрів: за 50 пакетів/с кадр приходить кожні 20 мс, тож 500 мс — це десятки пропущених кадрів поспіль, справжня втрата, а не одна завада. Зробиш поріг надто малим — апарат сахатиметься в failsafe від кожного шуму; надто великим — пізно помітить реальну втрату.

### Лінія телеметрії: «панель приладів» і розмова

Друга роль — **телеметрія**. Це вже не «віжки», а радше **панель приладів** плюс двостороння розмова.

![Лінія телеметрії: багато даних, двосторонньо, терпить затримку](/book/communications/protocols/control-telemetry/img/telemetry-link.svg)
*Униз ідуть дані стану: висота, кути, GPS, заряд, режим польоту. Угору — налаштування, завантаження місії, окремі команди. Це двостороння розмова з багатьма даними, що терпить сотні мілісекунд затримки. Саме тут живе MAVLink — спільна мова цієї розмови, часто через QGroundControl.*

Лінія телеметрії несе **багато** різнорідних даних, але вже **не в реальному часі керування**. Униз тече **стан** апарата — висота, кути нахилу, координати GPS, заряд батареї, режим, попередження; це наповнює «панель приладів» наземної станції (карту, індикатори). Угору йдуть **налаштування** — завантаження маршруту-місії, зміна параметрів, окремі команди. Ключова відмінність від керування: телеметрія **терпить затримку** в сотні мілісекунд, бо це інформація й конфігурація, а не миттєві «віжки». Загубився пакет — нічого страшного, прийде наступний.

І частота тут зовсім інша. Борт шле телеметрію не сотні разів за секунду, а **одиниці**. У відкритому автопілоті ArduPilot службове повідомлення «я живий» (heartbeat) іде рівно **1 раз за секунду**, а групи даних стану наземна станція зазвичай просить слати **близько 4 разів за секунду**; окреме повідомлення можна прискорити чи сповільнити параметрами потоку. Те, [що саме й як часто борт шле вниз цим потоком телеметрії](book:communications/telemetry-stream), — серцевина окремої теми. На цій лінії й живе **MAVLink** — стандартна мова, якою борт і станція (наприклад, QGroundControl) ведуть розмову.

### Третя лінія: відео (FPV)

![Відеолінія шле картинку вниз і з'їдає найширшу смугу](/book/communications/protocols/control-telemetry/img/video-link.svg)
*Відеолінія шле одну річ — картинку з бортової камери вниз, на екран чи окуляри пілота. Це найширша смуга з усіх, тому відео майже завжди дають окремий діапазон (часто 5.8 ГГц), щоб воно не «забивало» вузькі, але критичні лінії керування й телеметрії.*

Відеолінія має одну задачу — передати **картинку** з бортової камери вниз, пілотові на екран чи в окуляри. Вона **одностороння** й **найненажерливіша до смуги**: відео — це багато даних щосекунди. Тому її майже завжди виносять в **окремий діапазон**, найчастіше 5.8 ГГц, щоб широкий відеопотік не заважав вузьким, але життєво важливим лініям керування й телеметрії. Тут стає у пригоді [колова поляризація антени](book:communications/antenna-polarization) — її застосовують саме для FPV-відео, щоб картинка не пропадала, коли апарат перекидається в маневрах.

### Навіщо розділяти ролі

Чому не звести все в одну лінію — простіше було б? Бо вимоги ролей **майже протилежні**.

![Три причини розділяти лінії: різні вимоги, різні діапазони, безпека](/book/communications/protocols/control-telemetry/img/why-separate.svg)
*Три причини. Різні вимоги: керуванню потрібна затримка, телеметрії — обсяг даних, відео — смуга; один канал усе не потягне оптимально. Різні діапазони: керування на 2.4/868/433 МГц, телеметрія на 433/915 МГц, відео на 5.8 ГГц — не глушать одне одного. Безпека: критичну лінію керування ізолюють, щоб збій відео чи телеметрії її не зачепив.*

Причин три. **Перша — несумісні вимоги:** одна лінія не може бути водночас наднизьколатентною (керування), ємною за даними (телеметрія) і широкосмуговою (відео); компроміс задовольнив би всіх погано. **Друга — різні діапазони:** розвівши ролі по різних частотах (керування часто 2.4 ГГц чи 868/915/433 МГц, телеметрія — 433/915 МГц, відео — 5.8 ГГц), ми уникаємо взаємних завад, та ще й обираємо для кожної оптимальний діапазон за дальністю й проникністю, як того вимагає [поведінка різних частотних діапазонів](book:communications/frequency-bands). **Третя — безпека:** ізолювавши критичну лінію керування, ми гарантуємо, що збій у відео чи телеметрії її **не зачепить** — апарат лишиться керованим.

### Три ролі — три набори вимог

![Таблиця: затримка, надійність, обсяг, частота оновлення й напрям для трьох ролей](/book/communications/protocols/control-telemetry/img/requirements.svg)
*Керування: затримка критична, надійність найвища, даних мало, оновлення сотні разів за секунду, напрям угору. Телеметрія: затримку терпить, даних середньо, оновлення одиниці разів за секунду, у два боки. Відео: затримка помірна, даних багато, десятки кадрів за секунду, вниз. Вимоги настільки різні, що зливати їх в одне неоптимально.*

Контраст по кожному рядку наочний. По **затримці** керування на іншому полюсі від телеметрії: мілісекунди проти сотень мілісекунд. По **частоті оновлення** так само: керування — сотні разів за секунду, телеметрія — одиниці. По **обсягу даних** усе навпаки: керування — крихти, відео — потоки. **Напрям** теж різний: керування переважно вгору, відео вниз, телеметрія — у два боки. Ці протилежні профілі й пояснюють, чому в серйозній системі радіоліній **кілька**, а не одна. А заодно вони підказують, **на що тиснути**, проєктуючи зв'язок: для керування борися за [затримку й надійність лінії](book:communications/latency-reliability), для телеметрії — за обсяг і двосторонність, для відео — за смугу.

### Сучасний поворот: лінії зливаються, ролі — ні

![Класично — двоє радіо; сучасно — одне радіо несе керування й телеметрію](/book/communications/protocols/control-telemetry/img/convergence.svg)
*Класично керування й телеметрія йшли окремими радіомодулями. Сучасні системи (ExpressLRS, TBS Crossfire) шлють телеметрію назад тим самим лінком керування — одне радіо, двосторонній обмін. Технології зливаються, але дві ролі — «віжки» й «панель приладів» — лишаються концептуально різними.*

Раніше керування й телеметрія майже завжди були **окремими** радіомодулями з окремими антенами. Нові системи радіокерування — як-от **ExpressLRS** чи **TBS Crossfire** — уміють слати телеметрію назад **тим самим** лінком, що несе керування: одне радіо, двосторонній обмін, ще й MAVLink може йти прямо там. Це зручно й економить вагу. Але тут видно ту саму протилежність вимог зблизька. У такій лінії є **бюджет пакетів**, і телеметрія забирає частку в керування: налаштування «співвідношення телеметрії» (наприклад, 1:8 чи 1:2) означає, скільки пакетів із кожних восьми чи двох іде на зворотні дані. Хочеш більше телеметрії — менше лишається керуванню. Сам поділ на ролі від цього нікуди не дівається: навіть коли керування й телеметрія фізично йдуть одним радіо, це досі **дві різні розмови** — миттєві «віжки» й неспішна «панель приладів». Поділ концептуальний, і він лишається, хоч би скільки ліній фізично було.

Так радіозв'язок апарата розкладається на три ролі: керування, телеметрія, відео. Найкритичніша — [лінія керування](book:communications/rc-link), що тримає апарат у покорі: пульт перетворює рух стіків на канали, прив'язується до приймача, а за цим стоять протоколи на кшталт PPM, SBUS чи ELRS. Серцем телеметричної лінії є [MAVLink](book:communications/mavlink-packet) — мова, якою борт і наземна станція ведуть свою неспішну розмову.
