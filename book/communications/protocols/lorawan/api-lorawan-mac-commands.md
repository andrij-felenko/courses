# 📋 Специфікація MAC-команд та форматів кадрів LoRaWAN

Координація роботи радіомережі LoRaWAN — динамічна зміна частотних каналів, адаптація швидкості передачі, налаштування часових затримок вікон прийому, періодичності синхронізації Class B, керування груповими розсилками Multicast та діагностика стану батареї — здійснюється виключно за допомогою службових команд канального рівня (англ. *MAC Commands*). Ці команди передаються непомітно для прикладного програмного забезпечення: вони або вбудовуються безпосередньо в заголовок кадру в поле додаткових опцій `FOpts`, або передаються окремим кадром як корисне навантаження на зарезервованому порту `FPort = 0`.

У цій довідковій специфікації зведено точну структуру бітових полів заголовків кадру LoRaWAN MAC, вичерпний реєстр усіх команд стандарту LoRaWAN Link Layer v1.0.4 / v1.1 (включаючи розширення Class B, Class C та Multicast), правила їх квитування, формати відповідей, регіональні таблиці швидкостей та діаграми кінцевих автоматів обробки.

---

### 1. Бітова структура заголовків кадру LoRaWAN MAC

Кожен радіопакет LoRaWAN канального рівня (`PHYPayload`) має таку загальну структуру:

```
+---------------+------------------------------------------------+---------------+
|   MHDR (1 Б)  |         MACPayload (7 .. 250 байтів)           |   MIC (4 Б)   |
+---------------+------------------------------------------------+---------------+
```

#### Заголовок типу кадру MHDR (1 байт)

Поле `MHDR` (англ. *MAC Header*) визначає тип повідомлення та версію протоколу:

| Біти | Назва поля | Опис та значення |
| :--- | :--- | :--- |
| **7 .. 5** | `MType` | **Тип повідомлення:**<br>`000` (0) — `Join-Request` (Запит активації OTAA)<br>`001` (1) — `Join-Accept` (Відповідь активації OTAA)<br>`010` (2) — `Unconfirmed Data Up` (Непідтверджені дані від вузла)<br>`011` (3) — `Unconfirmed Data Down` (Непідтверджені дані від сервера)<br>`100` (4) — `Confirmed Data Up` (Підтверджені дані від вузла, вимагають ACK)<br>`101` (5) — `Confirmed Data Down` (Підтверджені дані від сервера, вимагають ACK)<br>`110` (6) — `Rejoin-Request` (Повторна активація у LoRaWAN 1.1)<br>`111` (7) — `Proprietary` (Пропрієтарний формат) |
| **4 .. 2** | `RFU` | Зарезервовано для майбутніх розширень (встановлюється в `000`). |
| **1 .. 0** | `Major` | **Версія формату кадру:**<br>`00` (0) — LoRaWAN R1 (застосовується для всіх версій 1.0.x та 1.1.x) |

#### Структура MACPayload

```
+--------------------------+-----------------+---------------------------+
|      FHDR (7..23 Б)      |   FPort (0..1 Б)|    FRMPayload (0..N Б)    |
+--------------------------+-----------------+---------------------------+
```

1. `FHDR` (Frame Header):
   - `DevAddr` (4 байти, Little-Endian): мережева адреса пристрою;
   - `FCtrl` (1 байт): керуючі прапорці каналу;
   - `FCnt` (2 байти у радіоефірі, Little-Endian): молодші 16 бітів монотонного лічильника кадру;
   - `FOpts` (0 .. 15 байтів): поле для розміщення одного або кількох об'єднаних MAC-команд.
2. `FPort` (0 або 1 байт): номер порту (присутній, якщо довжина `FRMPayload > 0`):
   - `FPort = 0`: корисне навантаження містить виключно MAC-команди, зашифровані ключем `NwkSKey`;
   - `FPort = 1 .. 223`: прикладні дані додатка, зашифровані ключем `AppSKey`;
   - `FPort = 224`: зарезервовано для сертифікаційного протоколу тестування на відповідність (англ. *MAC Compliance Test Protocol*);
   - `FPort = 225 .. 255`: зарезервовано для майбутніх стандартизованих служб.

#### Байт керування FCtrl

Структура байта `FCtrl` відрізняється залежно від напрямку передачі:

**Висхідний канал (Uplink):**
| Біти | Поле | Призначення |
| :--- | :--- | :--- |
| **7** | `ADR` | `1` — пристрій дозволяє мережевому серверу керувати швидкістю й потужністю через ADR. |
| **6** | `ADRACKReq` | `1` — пристрій запитує підтвердження наявності зв'язку від сервера (захист ADR від випадання з мережі). |
| **5** | `ACK` | `1` — підтвердження отримання попереднього кадру типу `Confirmed Data Down`. |
| **4** | `ClassB` | `1` — пристрій перейшов у режим Class B і готовий приймати пакети у слотах Ping Slots. |
| **3 .. 0** | `FOptsLen` | Довжина поля `FOpts` у байтах (від 0 до 15). Якщо `FOptsLen > 0`, поле `FPort` не може дорівнювати 0. |

**Низхідний канал (Downlink):**
| Біти | Поле | Призначення |
| :--- | :--- | :--- |
| **7** | `ADR` | `1` — сервер підтверджує керування ADR. |
| **6** | `RFU` | Зарезервовано. |
| **5** | `ACK` | `1` — підтвердження отримання попереднього кадру `Confirmed Data Up`. |
| **4** | `FPending` | `1` — у сервера є додаткові дані в черзі; пристрій Class A повинен якомога швидше надіслати наступний Uplink для відкриття нових вікон прийому. |
| **3 .. 0** | `FOptsLen` | Довжина поля `FOpts` у байтах (від 0 до 15). |

### 2. Повний реєстр команд канального рівня (MAC Commands)

MAC-команда ідентифікується 1-байтним кодом команди (англ. *Command Identifier*, CID), за яким слідують фіксовані аргументи:

| CID | Назва команди | Напрямок | Опис функції |
| :--- | :--- | :--- | :--- |
| `0x02` | `LinkCheckReq` | Вузол → Сервер | Запит перевірки якості радіозв'язку з мережею. |
| `0x02` | `LinkCheckAns` | Сервер → Вузол | Відповідь із демодуляційним запасом (Margin) та кількістю шлюзів. |
| `0x03` | `LinkADRReq` | Сервер → Вузол | Запит на зміну Data Rate, потужності TX Power, маски каналів та кількості повторів. |
| `0x03` | `LinkADRAns` | Вузол → Сервер | Підтвердження або відхилення параметрів ADR. |
| `0x04` | `DutyCycleReq` | Сервер → Вузол | Тимчасове обмеження максимального робочого циклу передавача. |
| `0x04` | `DutyCycleAns` | Вузол → Сервер | Підтвердження встановлення обмеження робочого циклу. |
| `0x05` | `RxParamSetupReq` | Сервер → Вузол | Налаштування зсуву швидкості для RX1 та частоти/швидкості для другого вікна RX2. |
| `0x05` | `RxParamSetupAns` | Вузол → Сервер | Статус застосування параметрів прийому RX1/RX2. |
| `0x06` | `DevStatusReq` | Сервер → Вузол | Запит діагностичного статусу: рівня заряду батареї та запасу демодуляції. |
| `0x06` | `DevStatusAns` | Вузол → Сервер | Відповідь із рівнем заряду батареї та виміряним SNR останнього прийому. |
| `0x07` | `NewChannelReq` | Сервер → Вузол | Динамічне додавання нового радіоканалу або модифікація наявного. |
| `0x07` | `NewChannelAns` | Вузол → Сервер | Статус налаштування нового частотного каналу. |
| `0x08` | `RxTimingSetupReq` | Сервер → Вузол | Зміна базової затримки відкриття вікна прийому `RECEIVE_DELAY1` (1 .. 15 с). |
| `0x08` | `RxTimingSetupAns` | Вузол → Сервер | Підтвердження зміни таймінгу вікон прийому. |
| `0x09` | `TxParamSetupReq` | Сервер → Вузол | Налаштування максимального EIRP та лімітів Dwell Time (US915, AS923, AU915). |
| `0x09` | `TxParamSetupAns` | Вузол → Сервер | Підтвердження встановлення обмежень випромінювання. |
| `0x0A` | `DlChannelReq` | Сервер → Вузол | Встановлення окремої частоти для низхідного зв'язку (Downlink) на заданому каналі. |
| `0x0A` | `DlChannelAns` | Вузол → Сервер | Статус встановлення частоти Downlink. |
| `0x0B` | `RekeyInd` | Вузол → Сервер | Підтвердження успішного оновлення ключів безпеки (LoRaWAN 1.1). |
| `0x0B` | `RekeyConf` | Сервер → Вузол | Квитанція підтвердження версії протоколу від сервера безпеки (LoRaWAN 1.1). |
| `0x0C` | `ADRParamSetupReq` | Сервер → Вузол | Налаштування лімітів лічильників `ADR_ACK_LIMIT` та `ADR_ACK_DELAY` (LoRaWAN 1.1). |
| `0x0C` | `ADRParamSetupAns` | Вузол → Сервер | Підтвердження параметрів лічильників ADR. |
| `0x0D` | `DeviceTimeReq` | Вузол → Сервер | Запит точного всесвітнього часу (UTC / GPS Time). |
| `0x0D` | `DeviceTimeAns` | Сервер → Вузол | Відповідь із 32-бітним часом в епосі GPS та дробовою частиною секунди. |
| `0x0E` | `ForceRejoinReq` | Сервер → Вузол | Примусова вимога до пристрою виконати процедуру Rejoin (LoRaWAN 1.1). |
| `0x0F` | `RejoinParamSetupReq`| Сервер → Вузол | Періодичність надсилання запитів Rejoin-Request (LoRaWAN 1.1). |
| `0x0F` | `RejoinParamSetupAns`| Вузол → Сервер | Підтвердження налаштування періодичності Rejoin. |
| `0x10` | `PingSlotInfoReq` | Вузол → Сервер | Повідомлення періодичності відкриття вікон Ping Slots у Class B. |
| `0x10` | `PingSlotInfoAns` | Сервер → Вузол | Підтвердження реєстрації параметрів слотів Class B. |
| `0x11` | `PingSlotChannelReq`| Сервер → Вузол | Встановлення частоти та швидкості передачі для слотів прийому Class B. |
| `0x11` | `PingSlotChannelAns`| Вузол → Сервер | Підтвердження налаштування каналу Ping Slot. |
| `0x12` | `BeaconTimingReq` | Вузол → Сервер | Запит точного часу до наступного маячка Beacon (застаріла у LoRaWAN 1.0.3+). |
| `0x12` | `BeaconTimingAns` | Сервер → Вузол | Часове зміщення та номер каналу наступного маячка. |
| `0x13` | `BeaconFreqReq` | Сервер → Вузол | Встановлення фіксованої частоти прийому маячків Beacon. |
| `0x13` | `BeaconFreqAns` | Вузол → Сервер | Підтвердження налаштування частоти маячка. |
| `0x20` | `DeviceModeInd` | Вузол → Сервер | Повідомлення про зміну робочого режиму між Class A та Class C (LoRaWAN 1.1). |
| `0x20` | `DeviceModeConf` | Сервер → Вузол | Підтвердження перемикання класу пристрою. |

### 3. Деталізація форматів полів та аргументів основних MAC-команд

#### 0x02: LinkCheckReq / LinkCheckAns
Команда дозволяє пристрою перевірити цілісність радіолінії без надсилання підтверджених прикладних даних:
- `LinkCheckReq`: корисне навантаження відсутнє (довжина 0 байтів).
- `LinkCheckAns` (довжина 2 байти):
  - Байт 0 (`Margin`, 1 байт): запас демодуляції в децибелах (від 0 до 254 дБ, де `Margin = 0` означає прийом на граничній межі чутливості демодулятора, значення `255` зарезервовано);
  - Байт 1 (`GwCnt`, 1 байт): кількість шлюзів, які успішно прийняли останній запит `LinkCheckReq`.

#### 0x03: LinkADRReq / LinkADRAns
Найважливіша команда адаптації каналу.
- `LinkADRReq` (довжина 4 байти):
  - Байт 0 (`DataRate_TXPower`):
    - Біти `7 .. 4`: новий `DataRate` (0 .. 15);
    - Біти `3 .. 0`: новий рівень потужності `TXPower` (0 .. 15).
  - Байти 1 .. 2 (`ChMask`, 16 бітів, Little-Endian): бітова маска увімкнених каналів (біт `i = 1` дозволяє канал `i`, біт `i = 0` вимикає).
  - Байт 3 (`Redundancy`):
    - Біт `7`: зарезервовано;
    - Біти `6 .. 4` (`ChMaskCntl`): керування банком маски каналів (для розширення маски понад 16 каналів або глобального увімкнення всіх каналів);
    - Біти `3 .. 0` (`NbTrans`): кількість передач одного пакета (від 1 до 15) для непідтверджених повідомлень (захист від втрат без ACK).
- `LinkADRAns` (довжина 1 байт):
  - Біти `7 .. 3`: зарезервовано (`00000`);
  - Біт `2` (`PowerACK`): `1` — пристрій підтримує запитану потужність `TXPower`;
  - Біт `1` (`DataRateACK`): `1` — пристрій підтримує запитаний `DataRate` для поточного частотного плану;
  - Біт `0` (`ChannelMaskACK`): `1` — пристрій успішно застосував маску каналів `ChMask`.

*Правило атомарності:* Усі три прапорці повинні дорівнювати `1` для успішного застосування команди; якщо хоча б один біт дорівнює `0`, пристрій відхиляє всю команду атомарно і зберігає попередні налаштування радіотракту.

#### 0x04: DutyCycleReq / DutyCycleAns
Команда тимчасового адміністративного обмеження випромінювання передавача:
- `DutyCycleReq` (довжина 1 байт):
  - Байт 0 (`DutyCyclePL`):
    - Біти `7 .. 4`: зарезервовано;
    - Біти `3 .. 0` (`MaxDCycle`): показник максимального робочого циклу. Максимально дозволений агрегований робочий цикл обчислюється за формулою:
      `Max_Duty_Cycle = 1 / (2^MaxDCycle)`.
      Значення `MaxDCycle = 0` вимикає додаткові обмеження, залишаючи лише стандартні регіональні ліміти.
- `DutyCycleAns`: підтвердження без параметрів (довжина 0 байтів, передається сам байт CID `0x04`).

#### 0x05: RxParamSetupReq / RxParamSetupAns
- `RxParamSetupReq` (довжина 4 байти):
  - Байт 0 (`DLsettings`):
    - Біт `7`: зарезервовано;
    - Біти `6 .. 4` (`RX1DROffset`): зсув швидкості для вікна RX1 відносно швидкості висхідного Uplink (значення 0 .. 7);
    - Біти `3 .. 0` (`RX2DataRate`): фіксована швидкість передачі для вікна RX2 (0 .. 15).
  - Байти 1 .. 3 (`Frequency`, 24 біти, Little-Endian): центральна частота вікна RX2, закодована як ціле число з кроком 100 Гц (наприклад, 869.525 МГц = `8695250` = `0x84AE12`).
- `RxParamSetupAns` (довжина 1 байт):
  - Біт `2` (`Rx1DROffsetACK`): `1` — зсув швидкості RX1 прийнято;
  - Біт `1` (`Rx2DataRateACK`): `1` — швидкість RX2 підтримується апаратно;
  - Біт `0` (`ChannelACK`): `1` — частота RX2 підтримується синтезатором частоти.

#### 0x06: DevStatusReq / DevStatusAns
Команда періодичного моніторингу працездатності та заряду елементів живлення.
- `DevStatusReq`: аргументи відсутні (0 байтів).
- `DevStatusAns` (довжина 2 байти):
  - Байт 0 (`Battery`):
    - `0` — пристрій живиться від зовнішнього джерела (мережа 220 В / сонячна панель);
    - `1 .. 254` — лінійне відображення рівня заряду батареї (`1` — мінімальний робочий рівень напруги, `254` — повний 100% заряд);
    - `255` — пристрій не має апаратної можливості виміряти напругу або рівень заряду.
  - Байт 1 (`Margin`): 6-бітне знакове число в доповняльному коді (біти `5 .. 0`), що відображає SNR останнього успішно прийнятого пакета `DevStatusReq` (діапазон від −32 дБ до +31 дБ).

#### 0x07: NewChannelReq / NewChannelAns
- `NewChannelReq` (довжина 5 байтів):
  - Байт 0 (`ChIndex`): індекс каналу, що конфігурується (від 0 до 15 для EU868);
  - Байти 1 .. 3 (`Frequency`): частота в одиницях 100 Гц (значення `0` вимикає та видаляє канал);
  - Байт 4 (`DrRange`):
    - Біти `7 .. 4` (`MaxDR`): максимальний дозволений Data Rate на цьому каналі;
    - Біти `3 .. 0` (`MinDR`): мінімальний дозволений Data Rate на цьому каналі.
- `NewChannelAns` (довжина 1 байт):
  - Біт `1` (`DataRateRangeOK`): `1` — діапазон швидкостей коректний;
  - Біт `0` (`ChannelFrequencyOK`): `1` — частота підтримується радіотрактом.

#### 0x08: RxTimingSetupReq / RxTimingSetupAns
- `RxTimingSetupReq` (довжина 1 байт):
  - Біти `7 .. 4`: зарезервовано;
  - Біти `3 .. 0` (`Del`): час затримки до вікна RX1 у секундах: значення від `0` до `15`, де `0` трактується як 1 секунда, а значення `1 .. 15` задають затримку від 1 до 15 секунд. Затримка до вікна RX2 автоматично становить `Del + 1` секунду.
- `RxTimingSetupAns`: підтвердження без параметрів (довжина 0 байтів, передається сам байт CID `0x08`).

#### 0x0D: DeviceTimeReq / DeviceTimeAns
- `DeviceTimeReq`: порожній запит (0 байтів).
- `DeviceTimeAns` (довжина 5 байтів):
  - Байти 0 .. 3 (`Seconds`, 32 біти, Little-Endian): кількість цілих секунд, що минули з початку епохи GPS (00:00:00 UTC, 6 січня 1980 року);
  - Байт 4 (`Fractional-seconds`, 1 байт): дробова частина секунди з дискретністю `1 / 2^8 = 1 / 256` секунди (близько 3.90625 мс).

#### 0x10: PingSlotInfoReq / PingSlotInfoAns (Розширення Class B)
Команда узгодження розкладу періодичних слотів прийому в режимі Class B:
- `PingSlotInfoReq` (довжина 1 байт):
  - Байт 0 (`PingSlotParam`):
    - Біти `7 .. 3`: зарезервовано;
    - Біти `2 .. 0` (`Periodicity`): період відкриття слотів прийому. Інтервал між слотами обчислюється як:
      `T_ping = 2^(12 − Periodicity) · 30 мс`.
      При `Periodicity = 0` слоти відкриваються щосекунди (128 слотів за період маячка 128 с); при `Periodicity = 7` слот відкривається 1 раз на 128 секунд.
- `PingSlotInfoAns`: підтвердження без параметрів (довжина 0 байтів, CID `0x10`).

#### 0x11: PingSlotChannelReq / PingSlotChannelAns (Розширення Class B)
- `PingSlotChannelReq` (довжина 4 байти):
  - Байти 0 .. 2 (`Frequency`, 24 біти, Little-Endian): фіксована частота слотів прийому з кроком 100 Гц (значення `0` перемикає пристрій на псевдовипадковий стрибок частоти за стандартизованою схемою);
  - Байт 3 (`DrRange`): діапазон швидкостей `MaxDR` (біти `7..4`) та `MinDR` (біти `3..0`).
- `PingSlotChannelAns` (довжина 1 байт):
  - Біт `1` (`DataRateRangeOK`): `1` — швидкість підтримується;
  - Біт `0` (`ChannelFrequencyOK`): `1` — частота підтримується радіотрактом.

### 4. Список частотних каналів CFList у повідомленні Join-Accept

Поле `CFList` (англ. *Channel Frequency List*) є опційним 16-байтним блоком у складі кадру `Join-Accept`. Воно дозволяє серверу автоматично сконфігурувати повний частотний план пристрою безпосередньо під час процедури підключення OTAA:

1. **Тип 0 (CFList для динамічних каналів, EU868, AS923):**
   Блок містить рівно 5 додаткових частот каналів (по 3 байти на канал у кодуванні з дискретністю 100 Гц) та 1 байт типу списку (`0x00`).
   - Канал 3: Байти `0 .. 2` (наприклад, `867.100 МГц`);
   - Канал 4: Байти `3 .. 5` (`867.300 МГц`);
   - Канал 5: Байти `6 .. 8` (`867.500 МГц`);
   - Канал 6: Байти `9 .. 11` (`867.700 МГц`);
   - Канал 7: Байти `12 .. 14` (`867.900 МГц`);
   - Байт 15: Тип списку `CFListType = 0x00`.
   Після обробки цього блоку кінцевий пристрій отримує повний набір із 8 робочих каналів (3 канали за замовчуванням + 5 додаткових).

2. **Тип 1 (CFList як маска каналів для фіксованих сіток, US915, AU915):**
   У мережах US915 та AU915, що мають фіксовану сітку з 64 або 72 каналів, `CFList` містить 16-бітні маски увімкнених банків каналів (`ChMask0 .. ChMask4`), що дозволяє серверу вказати пристрою конкретний 8-канальний піддіапазон (Sub-band) оператора:
   - Байти `0 .. 9`: п'ять 16-бітних масок каналів `ChMask0` .. `ChMask4`;
   - Байти `10 .. 14`: зарезервовано нулями;
   - Байт 15: Тип списку `CFListType = 0x01`.

### 6. Керування багатоадресними групами (Multicast) у Class B та Class C

Для оновлення вбудованого програмного забезпечення повітрям (FUOTA) та масової передачі команд телеметрії стандарт LoRaWAN визначає протокол керування групами `Multicast Control Package`.

Кінцевий пристрій може бути членом до чотирьох незалежних багатоадресних груп. Кожна група має власну віртуальну адресу `McDevAddr` та окремий набір сесійних ключів:
- `McNwkSKey`: для верифікації коду цілісності групових повідомлень;
- `McAppSKey`: для розшифрування групового корисного навантаження.

Управління групами здійснюється за допомогою стандартизованих команд:
- `McGroupSetupReq` (налаштування ідентифікатора групи, адреси `McDevAddr` та зашифрованого ключа групи `McKeyEncryption`);
- `McClassBSessionReq` (встановлення часу початку багатоадресної сесії в епосі GPS, періодичності слотів та робочої частоти);
- `McClassCSessionReq` (встановлення точного часу початку та тривалості безперервного прийому в режимі Class C).

Оскільки багатоадресний зв'язок є строго одностороннім (Downlink), кінцеві пристрої ніколи не надсилають квитанцій ACK на групові пакети, щоб запобігти колапсу радіоефіру через одночасну відповідь тисяч вузлів.

### 7. Сертифікаційний тестовий протокол на порті FPort = 224

Для проходження офіційного тестування на відповідність вимогам LoRa Alliance у лабораторіях (LoRaWAN Certification Testing) пристрій зобов'язаний підтримувати тестовий режим на порті `FPort = 224`.

Коли сервер надсилає команду активації тесту `0x01` на порт 224:
1. Кінцевий пристрій блокує генерацію звичайних прикладних пакетів датчиків;
2. Пристрій перемикає лічильник `FCntUp` у тестовий режим;
3. Всі отримані тестові пакети автоматично віддзеркалюються назад сервери зі збільшенням лічильника кадру (режим Echo);
4. Пристрій дозволяє віддалену перевірку всіх діапазонів `LinkADRReq`, `DutyCycleReq` та `RxParamSetupReq` без обмежень локального коду додатка.

### 8. Правила мультиплексування, чергування та квитування MAC-команд

1. **Конкатенація команд у полі FOpts:**
   У полі `FOpts` (максимум 15 байтів) дозволяється об'єднувати декілька MAC-команд поспіль. Наприклад, відповідь на запит статусу (`DevStatusAns`, CID `0x06` + 2 байти) та підтвердження ADR (`LinkADRAns`, CID `0x03` + 1 байт) формують єдину послідовність із 5 байтів:
   `06 [Battery] [Margin] 03 [Status]`.
2. **Атомарність виконання:**
   Якщо пакет містить декілька команд `LinkADRReq` або `NewChannelReq`, кінцевий пристрій зобов'язаний обробити їх усі в порядку надходження і надіслати підтвердження `LinkADRAns` для кожного запиту окремо. Усі зміни каналів набувають чинності одночасно після обробки повного списку.
3. **Пріоритет передачі (FOpts проти FPort = 0):**
   - Якщо сумарна довжина MAC-команд не перевищує 15 байтів, вони завжди передаються у полі `FOpts` разом із прикладними даними (`FPort ≥ 1`), що заощаджує час перебування в ефірі;
   - Якщо довжина відповідей перевищує 15 байтів, або якщо у пристрою немає прикладних даних для відправлення, MAC-команди розміщуються у полі `FRMPayload` на порту `FPort = 0`. Одночасне розміщення MAC-команд у `FOpts` та на `FPort = 0` суворо заборонено стандартом.
4. **Повторна передача відповідей на команди сервера:**
   Коли кінцевий пристрій генерує відповідь на команду сервера (наприклад, `LinkADRAns` або `RxParamSetupAns`), він зобов'язаний повторювати цю відповідь у полі `FOpts` усіх наступних висхідних повідомлень доти, доки від сервера не буде отримано новий низхідний пакет Downlink (що свідчить про успішний прийом сервером квитанції). Це гарантує надійність керування навіть в умовах односторонньої втрати радіопакетів.
