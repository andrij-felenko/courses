# 🧮 Градієнт затримки та фільтрація джиттера в алгоритмі TWCC

Алгоритми керування заторами на основі втрат пакетів (Loss-Based Congestion Control, як у класичних протоколах TCP Reno чи CUBIC) виявляються непридатними для інтерактивного відеозв'язку реального часу. Коли проміжний мережевий маршрутизатор перевантажується, він спочатку накопичує надлишкові пакети у своєму внутрішньому буфері пам'яті (явище Bufferbloat). Лише після повного заповнення буфера нові пакети починають відкидатися (Drop-Tail).

Для файлового завантаження через TCP затримка буфера у 300–800 мілісекунд є прийнятною, проте для відеоконференцій або дистанційного керування безпілотниками така затримка означає повну втрату інтерактивності задовго до того, як кодер отримає сигнал про втрату пакета.

Алгоритм TWCC (Transport-Wide Congestion Control, RFC 8888) у поєднанні з оцінювачем GCC (Google Congestion Control) реалізує керування на основі **градієнта затримки** (Delay-Based Congestion Control). Він детектує зростання черг у маршрутизаторах за зміною часу міжприбуття пакетів задовго до виникнення реальних втрат.

## Математична модель варіації односторонньої затримки

Нехай відправник транслює послідовність RTP-пакетів. Для кожного пакета з індексом `i` фіксуються два часові параметри:
- `T[i]`: точний час відправлення пакета з локального сокета відправника (монотонний таймер відправника).
- `t[i]`: точний час надходження пакета на мережевий інтерфейс приймача (монотонний таймер приймача).

Оскільки таймери двох незалежних комп'ютерів не синхронізовані і можуть мати довільний початковий зсув та різну швидкість ходу годинників, абсолютна затримка `t[i] - T[i]` не може використовуватися безпосередньо. Замість цього розглядається **міжпакетна дельта (Inter-Packet Delta)**:

```text
ΔT[i] = T[i] - T[i-1]   [інтервал між відправкою двох послідовних пакетів]
Δt[i] = t[i] - t[i-1]   [інтервал між прибуттям цих самих пакетів на приймач]
```

Варіація односторонньої затримки `d[i]` (One-Way Delay Variation) визначається як різниця інтервалів прийому та відправлення:

```
d[i]
= Δt[i] - ΔT[i]
= (t[i] - t[i-1]) - (T[i] - T[i-1])
```

Фізичний зміст величини `d[i]`:
1. `d[i] = 0`: час передачі стабільний, черга в маршрутизаторах не змінюється.
2. `d[i] > 0`: інтервал між прибуттям пакетів більший за інтервал відправлення (`Δt[i] > ΔT[i]`). Це означає, що пакет `i` затримався в мережевій черзі довше, ніж пакет `i-1`. Черга на проміжному комутаторі зростає — ознака **перевантаження каналу**.
3. `d[i] < 0`: пакет `i` наздогнав попередній пакет (`Δt[i] < ΔT[i]`). Черга в маршрутизаторі розвантажується — ознака **недовикористання каналу**.

## Групування пакетів у кадри та фільтрація

Окремий відеокадр H.264 чи VP8 зазвичай розбивається на кілька RTP-пакетів (наприклад, 5–20 пакетів на один великий I-кадр). Оскільки всі пакети одного кадру надсилаються майже одночасно (із затримкою менше ніж 1 мс завдяки пейсеру), вимірювання дельти для кожного окремого пакета містить високий рівень випадкового шуму (джиттера мікроконтролера та Wi-Fi MAC-рівня).

Тому алгоритм групує пакети у пачки (Bursts / Frames) з індексом `k`.

Пачка вважається завершеною, якщо виконується одна з умов:
- Інтервал відправки між пакетами перевищує поріг міжпакетної паузи: `T[i] - T[i-1] > 5 мс`.
- Сумарна тривалість пачки перевищує вікно групування: `T[i] - T[first] > 5 мс`.

Для пачки `k` обчислюються зведені часові мітки:
- Час відправлення пачки: `T_send[k] = max(T[i])` для всіх пакетів у пачці.
- Час прибуття пачки: `t_recv[k] = max(t[i])` для всіх пакетів у пачці.
- Дельта відправлення: `ΔT[k] = T_send[k] - T_send[k-1]`.
- Дельта прибуття: `Δt[k] = t_recv[k] - t_recv[k-1]`.
- Сумарна затримка пачки: `d[k] = Δt[k] - ΔT[k]`.

## Оцінка градієнта затримки через лінійну регресію (Trendline Filter)

У сучасній кодовій базі WebRTC фільтр Калмана замінено на стійкіший до фазових стрибків алгоритм лінійної регресії Trendline.

Алгоритм накопичує історію вимірювань у ковзному вікні розміром `W = 20` пачок. Для кожної пачки `k` обчислюється накопичена варіація затримки `z[k]`:

```
z[k]
= z[k-1] + d[k]        [накопичення відносного зміщення затримки]
```

Для усунення випадкових викидів накопичена затримка згладжується експоненційним фільтром:

```
z_smooth[k]
= (1 - χ) · z_smooth[k-1] + χ · z[k]   [де χ = 0.9 — коефіцієнт згладжування]
```

Градієнт затримки `m[k]` (Slope) визначається як кутовий коефіцієнт прямої лінії, що найкраще апроксимує вибірку точок `(T_send[j], z_smooth[j])` у поточному вікні за методом найменших квадратів (OLS — Ordinary Least Squares):

```
m[k]
= Cov(T_send, z_smooth) ÷ Var(T_send)
= (∑ (T_send[j] - T̄) · (z_smooth[j] - z̄)) ÷ (∑ (T_send[j] - T̄)²)
```

де `T̄` та `z̄` — середні арифметичні значення часу та згладженої затримки у вікні.

Отриманий градієнт `m[k]` масштабується на сумарну кількість переданих пакетів для отримання безрозмірної величини оцінки зростання затримки:

```
m_scaled[k]
= m[k] · N_packets_in_window
```

## Адаптивний динамічний поріг перевантаження

Оцінений градієнт `m_scaled[k]` порівнюється з порогом детектування перевантаження `γ[k]` (гамма).

Фіксований статичний поріг не підходить:
- Якщо поріг занадто малий, природний джиттер бездротової мережі Wi-Fi/LTE призведе до постійних помилкових спрацьовувань і безпідставного заниження бітрейту відео (ефект голодування).
- Якщо поріг занадто великий, алгоритм пропустить реальне утворення черги і відреагує лише тоді, коли затримка вже перевищить допустиму норму.

Тому WebRTC застосовує **адаптивний поріг**, який підлаштовується під поточний рівень мережевого шуму за наступним диференційним правилом:

```
Якщо |m_scaled[k]| > γ[k-1]:
γ[k] = γ[k-1] + Δt_k · k_u · (|m_scaled[k]| - γ[k-1])   [збільшення порогу під час сплесків]

Якщо |m_scaled[k]| ≤ γ[k-1]:
γ[k] = γ[k-1] + Δt_k · k_d · (|m_scaled[k]| - γ[k-1])   [повільне зниження порогу у стабільному стані]
```

Параметри адаптації порогу:
- `k_u = 0.01` (коефіцієнт збільшення).
- `k_d = 0.00018` (коефіцієнт зменшення).
- Асиметрія `k_u > k_d`: поріг швидко зростає при появі шумів (запобігаючи хибному детектуванню перевантаження), але повільно зменшується назад.
- Обмеження діапазону: `γ[k] ∈ [6.0, 600.0]`.

## Автомат станів детектора перевантаження (Overuse Detector)

На основі порівняння градієнта `m_scaled[k]` з порогом `γ[k]` детектор переходить між трьома станами:

```text
          m_scaled > γ (і триває > 10 мс)
       ┌───────────────────────────────────┐
       │                                   v
+──────────────+                    +──────────────+
|    Normal    |                    |   Overuse    |
+──────────────+                    +──────────────+
       ^                                   │
       │       m_scaled < -γ               │
       └───────────────────────────────────┘
```

1. **Стан `Overuse` (Перевантаження)**:
   - Умова: `m_scaled[k] > γ[k]` і цей стан спостерігається неперервно протягом щонайменше `t_overuse_hold = 10` мс.
   - Фізичний зміст: черга в буфері маршрутизатора монотонно зростає. Необхідно негайно знизити бітрейт кодера.
2. **Стан `Underuse` (Недовикористання)**:
   - Умова: `m_scaled[k] < -γ[k]`.
   - Фізичний зміст: буфер маршрутизатора спорожнюється, пропускна здатність каналу звільнилася.
3. **Стан `Normal` (Нормальний стан)**:
   - Умова: `-γ[k] ≤ m_scaled[k] ≤ γ[k]`.
   - Фізичний зміст: затримка стабільна, швидкість генерації трафіку відповідає реальній пропускній здатності каналу.

## Адаптація бітрейту (Rate Control State Machine)

Модуль керування бітрейтом (AIMD — Additive Increase Multiplicative Decrease) обчислює цільовий бітрейт кодера `A[k]` на основі поточного стану детектора та виміряної швидкості прийому `R_recv[k]`:

### 1. Реакція на стан `Overuse` (Мультиплікативне зниження)
Коли зафіксовано перевантаження, бітрейт негайно знижується пропорційно до поточної швидкості прийому:

```
A[k]
= β · R_recv[k]       [де β = 0.85 — коефіцієнт зниження на 15%]
```

Зниження на 15% дозволяє маршрутизатору швидко спорожнити накопичену чергу пакетів і повернути затримку до базового фізичного RTT.

### 2. Реакція на стан `Normal` (Адитивне збільшення або зондування)
Якщо система знаходиться у стані `Normal`, вона обережно збільшує бітрейт для зондування доступної смуги:

```
A[k]
= A[k-1] + α · Δt_k   [адитивний приріст]
```

де `α` обчислюється на основі поточного бітрейту (приблизно 8% на секунду), забезпечуючи плавний вихід на максимальну якість відео.

## Альтернативна математична модель: адаптивний фільтр Калмана

У перших версіях рушія Google Congestion Control (специфікація `draft-alvestrand-rmcat-congestion-03`) для оцінки градієнта затримки використовувався 2-вимірний адаптивний фільтр Калмана. Хоча сучасні версії WebRTC використовують стійкіший Trendline-фільтр, математичний апарат фільтра Калмана залишається еталоном для аналізу динамічних систем у реальному часі.

### Вектор стану та модель спостереження

Стан системи в момент часу `k` описується 2-вимірним вектором стану:

```text
x[k] = [ m[k], v[k] ]ᵀ
```
де:
- `m[k]` — поточний градієнт затримки (зростання черги на одиницю часу відправлення).
- `v[k]` — зміщення нульового рівня та високочастотний шум каналу.

Рівняння зміни стану припускає, що градієнт затримки є випадковим блуканням із білим шумом процесу `w[k]`:

```
x[k]
= x[k-1] + w[k]        [матриця переходу F є одиничною матрицею I]
```

Коваріаційна матриця шуму процесу `Q` моделює швидкість можливої зміни умов у каналі зв'язку:

```text
Q[k] = [ q₁  0  ]
       [ 0   q₂ ]
```
де `q₁ = 10⁻³`, `q₂ = 10⁻²`.

Рівняння вимірювання пов'язує спостережувану міжпакетну затримку `d[k]` з вектором стану через інтервал відправки `ΔT[k]`:

```
d[k]
= H[k] · x[k] + n[k]
= m[k] · ΔT[k] + v[k] + n[k]
```
де матриця вимірювання має вигляд `H[k] = [ ΔT[k], 1 ]`, а `n[k]` — випадковий шум вимірювання з дисперсією `R_noise[k]`.

### Покрокові рівняння оновлення фільтра Калмана

На кожному кроці `k` надходження нової пачки пакетів фільтр виконує два етапи обчислень:

#### 1. Етап прогнозу (Time Update / Predict):
Апріорна оцінка стану та коваріаційної матриці помилок `P`:

```
x̂_prior[k] = x̂[k-1]
P_prior[k] = P[k-1] + Q[k]
```

#### 2. Етап корекції (Measurement Update / Correct):
Обчислення нев'язки вимірювання (Innovation Residual) `e[k]`:

```
e[k]
= d[k] - H[k] · x̂_prior[k]
= d[k] - (m̂_prior[k] · ΔT[k] + v̂_prior[k])
```

Дисперсія нев'язки `S[k]` та коефіцієнт підсилення Калмана `K[k]`:

```
S[k]
= H[k] · P_prior[k] · H[k]ᵀ + R_noise[k]
= P₁₁ · (ΔT[k])² + 2 · P₁₂ · ΔT[k] + P₂₂ + R_noise[k]

K[k]
= P_prior[k] · H[k]ᵀ · S[k]⁻¹
```

Апостеріорне оновлення вектора стану та коваріації:

```
x̂[k]
= x̂_prior[k] + K[k] · e[k]

P[k]
= (I - K[k] · H[k]) · P_prior[k]
```

Оцінене значення першої компоненти `m̂[k] = x̂[1][k]` передається до детектора перевантаження для порівняння з адаптивним порогом `γ[k]`.

## Комбінований контур: поєднання градієнта затримки та втрат пакетів

Повний контролер швидкості GCC поєднує в собі два паралельні контури: **Delay-Based Controller** (оцінювач на основі градієнта затримки) та **Loss-Based Controller** (оцінювач на основі частки втрачених пакетів).

Остаточний бітрейт кодера `A_target[k]` обирається як мінімум між цими двома оцінками:

```
A_target[k]
= min(A_delay[k], A_loss[k])
```

### Математика контуру на основі втрат (Loss-Based Controller)

Приймач періодично надсилає звіти RTCP Receiver Report (RFC 3550), які містять 8-бітове значення частки втрачених пакетів `Fraction Lost` у діапазоні від `0` (0%) до `255` (100%).

Поточний коефіцієнт втрат `p_loss = Fraction_Lost / 256.0` аналізується за тризонною схемою:

```text
               p_loss < 2%                2% <= p_loss <= 10%              p_loss > 10%
        ┌─────────────────────────┬─────────────────────────────────┬─────────────────────────┐
        │  Адитивне збільшення    │        Утримання бітрейту       │ Мультиплікативне спадання│
        │   A[k] = A[k-1] · 1.08  │          A[k] = A[k-1]          │  A[k] = A[k-1]·(1-0.5·p)│
        └─────────────────────────┴─────────────────────────────────┴─────────────────────────┘
```

1. **Зона низьких втрат (`p_loss < 0.02`, втрати менше 2%)**:
   Вважається, що втрати спричинені одиничними випадковими завадами в радіоефірі, а не переповненням черги. Контролер дозволяє плавне збільшення бітрейту:
   ```
   A_loss[k] = A_loss[k-1] · (1.0 + 0.08 · Δt_k)
   ```
2. **Зона помірних втрат (`0.02 ≤ p_loss ≤ 0.10`, втрати від 2% до 10%)**:
   Канал знаходиться на межі насичення. Контролер заморожує поточну швидкість:
   ```
   A_loss[k] = A_loss[k-1]
   ```
3. **Зона високих втрат (`p_loss > 0.10`, втрати понад 10%)**:
   Високі втрати свідчать про переповнення буферів комутаторів. Бітрейт агресивно знижується:
   ```
   A_loss[k] = A_loss[k-1] · (1.0 - 0.5 · p_loss)
   ```

## Математика згладжування сплесків трафіку (Pacer Leaky Bucket)

Коли відеокодер генерує ключовий IDR/I-кадр, його розмір (наприклад, 80 КіБ) у 10–20 разів перевищує розмір звичайного P-кадру (4 КіБ). Якщо відправити всі 60 RTP-пакетів цього кадру миттєво в мережу на канальній швидкості мережевої карти (1 Гбіт/с), це викличе мікросплеск (Micro-Burst) і штучний стрибок затримки в буфері першого ж маршрутизатора.

Щоб запобігти цьому, WebRTC використовує модуль **Pacer** (формувач трафіку за моделлю дірявого відра Leaky Bucket):

- Швидкість виштовхування пакетів із пейсера встановлюється з коефіцієнтом перекриття `k_pacing = 2.5`:
  ```
  Pacing_Rate
  = 2.5 · A_target[k]
  ```
- Пакети розміщуються у пріоритетній черзі відправника і випускаються рівномірними інтервалами `Δt_pacer = 5` мс.
- Якщо відеокодер згенерував менше трафіку, ніж цільова швидкість зондування каналу, Pacer генерує фіктивні пакети заповнення (Padding Packets) для підтримки безперервного потоку вимірювань TWCC.

## Зондування пропускної здатності пачками (Probing Clusters)

Коли канал зв'язку раптово покращується (наприклад, безпілотник наблизився до базової станції або мобільний телефон перемкнувся з 3G на 5G), адитивне збільшення бітрейту `A[k] = A[k-1] + α` піднімає якість відео занадто повільно (підйом із 1 Мбіт/с до 10 Мбіт/с може тривати 15–20 секунд).

Для миттєвого виявлення вільної смуги WebRTC використовує механізм **зондувальних кластерів** (Probing Clusters):

- Відправник генерує короткий кластер із `N = 5` пакетів (сумарним обсягом близько 6 КіБ), які виштовхуються з пейсера з надзвичайно високою миттєвою швидкістю `R_probe = 2.0 · A_target`.
- Пакети надсилаються з мінімальним інтервалом `ΔT_probe = 1` мс.
- На приймачі вимірюється інтервал прийому всього кластера `Δt_cluster = t_recv[last] - t_recv[first]`.

Оцінка пропускної здатності вузького місця (Bottleneck Capacity) обчислюється як:

```
R_bottleneck
= (Bytes_in_cluster · 8) ÷ Δt_cluster
```

Якщо `R_bottleneck > A_target` і при цьому градієнт затримки кластера `d_cluster ≈ 0`, контролер робить миттєвий стрибок бітрейту до виміряного значення `R_bottleneck`, скорочуючи час адаптації до 1 RTT (50–100 мс).

## Порівняння архітектур: чому застарів REMB (RFC draft-alvestrand-rmcat-remb)

До стандартизації TWCC у 2020 році основним протоколом зворотного зв'язку був **REMB (Receiver Estimated Maximum Bitrate)**.

У схемі REMB:
1. Приймач самостійно виконував оцінку градієнта затримки через фільтр Калмана.
2. Приймач обчислював кінцеве число бітрейту (наприклад, `2.4 Мбіт/с`) і надсилав його раз на 1000 мс у спеціальному RTCP-повідомленні з кодом корисного вантажу `a=rtcp-fb:* goog-remb`.

Математичні недоліки схеми REMB:
- **Асиметрія обчислень**: Мобільний пристрій приймача зі слабким процесором мусив витрачати ресурси батареї на розрахунок фільтрів Калмана для десятків вхідних відеотреків.
- **Втрата дрібнозернистої інформації**: Відправник отримував лише одне підсумкове число `R_max` і не мав жодного уявлення про те, які саме пакети затрималися, чи був джиттер спричинений конкретним I-кадром, чи є втрати рівномірними.
- **Неможливість спільного пейсингу**: Кожен відеотрек оцінювався окремо, що унеможливлювало глобальне керування заторами для мультиплексованого сокета BUNDLE.

У TWCC вся аналітична та математична робота перенесена на потужний передавач. Приймач залишається «тупим рефлектором»: він лише записує точний час надходження `t_recv` для кожного номера `Transport Sequence Number` і пакує ці часові дельти у компактні повідомлення RTCP Feedback (RFC 8888) розміром менше ніж 80 байтів.

## Покроковий числовий приклад розрахунку

Розглянемо числовий приклад обробки 4 послідовних пачок відеопакетів, що проходять через маршрутизатор, де починає утворюватися черга.

### Вхідні вимірювання міток часу (у мілісекундах)

| Пачка `k` | Час відправки `T_send` (мс) | Час прийому `t_recv` (мс) | `ΔT = T_k - T_{k-1}` | `Δt = t_k - t_{k-1}` | Варіація `d_k = Δt - ΔT` |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | 100.0 | 140.0 | — | — | — |
| 2 | 120.0 | 160.0 | 20.0 | 20.0 | **0.0 мс** |
| 3 | 140.0 | 185.0 | 20.0 | 25.0 | **+5.0 мс** |
| 4 | 160.0 | 212.0 | 20.0 | 27.0 | **+7.0 мс** |

### Розрахунок накопиченої затримки та градієнта

Початковий поріг: `γ = 12.0`.
Початковий бітрейт прийому: `R_recv = 2.0 Мбіт/с`.

```
z[1] = 0.0 мс
z[2] = z[1] + d[2] = 0.0 + 0.0 = 0.0 мс
z[3] = z[2] + d[3] = 0.0 + 5.0 = 5.0 мс
z[4] = z[3] + d[4] = 5.0 + 7.0 = 12.0 мс
```

Кутовий коефіцієнт лінії регресії за точками `(120, 0)`, `(140, 5)`, `(160, 12)`:

```
m = Δz / ΔT ≈ (12.0 - 0.0) / (160.0 - 120.0) = 12.0 / 40.0 = 0.30 мс/мс
m_scaled = m · N_packets = 0.30 · 50 = 15.0
```

Порівняння з порогом:
```
m_scaled = 15.0 > γ = 12.0
```

Висновок автомата станів:
Детектор переходить у стан **`Overuse`**.
Модуль керування бітрейтом виконує мультиплікативне зниження:

```
A_new
= β · R_recv          [правило мультиплікативного зниження GCC]
= 0.85 · 2.0 Мбіт/с   [підстановка коефіцієнта β = 0.85 та поточної швидкості R_recv]
= 1.70 Мбіт/с         [новий ліміт бітрейту для відеокодера]
```

Кодер H.264 миттєво отримує команду зменшити квантування та знизити швидкість генерації кадрів до 1.70 Мбіт/с, що дозволяє усунути перевантаження черги буфера за один RTT.
