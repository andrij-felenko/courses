# 🧮 Математика HKDF та ефемерного обміну ключів ECDHE у TLS 1.3

Абсолютна безпека та математична стійкість рукостискання TLS 1.3 базуються на поєднанні двох криптографічних концепцій: **еліптичної криптографії (ECDHE)** для безконтактного узгодження спільного секрету та **ієрархічної функції деривації ключів (HKDF на основі HMAC)** для розгортання шифрувальних ключів.

---

## 1. Узгодження секрету на еліптичних кривих (ECDHE)

Математичний фундамент еліптичної криптографії базується на геометрії алгебраїчних кривих над скінченними полями. Нехай `E` — еліптична крива над скінченним полем Galois `F_p`, задана канонічним рівнянням Вайєрштрассе:

```text
y² = x³ + a·x + b   (mod p)
```

Або крива Монтгомері (наприклад, Curve25519, що описується рівнянням `v² = u³ + 486662·u² + u (mod 2²⁵⁵ - 19)`). Базова генераторна точка кривої `G` має фіксований простий порядок `n`.

Множина точок еліптичної кривої разом із нескінченно віддаленою точкою `O` утворюють абелеву групу щодо операції додавання точок. Для двох точок `P_1 = (x_1, y_1)` та `P_2 = (x_2, y_2)` точка суми `P_3 = P_1 + P_2 = (x_3, y_3)` обчислюється через кутовий коефіцієнт січної або дотичної прямої `λ`:

```text
λ = (y_2 - y_1) / (x_2 - x_1)  (mod p)    [для P_1 ≠ P_2]
λ = (3·x_1² + a) / (2·y_1)      (mod p)    [для P_1 = P_2]

x_3 = λ² - x_1 - x_2            (mod p)
y_3 = λ·(x_1 - x_3) - y_1        (mod p)
```

### Процедура математичного обміну ключів за схемою Ефемерного Діффі-Геллмана (ECDHE)

1. **Генерація пари ключів клієнта**: Клієнт обирає криптографічно стійке випадкове число `d_c ∈ [1, n-1]` у якості свого приватного ключа. Потім він обчислює свій публічний ключ (точку на кривій):
   ```text
   Q_c = d_c · G      [скалярне множення точки G на d_c]
   ```
2. **Генерація пари ключів сервера**: Сервер незалежно обирає випадковий приватний ключ `d_s ∈ [1, n-1]` та обчислює свій публічний ключ:
   ```text
   Q_s = d_s · G      [скалярне множення точки G на d_s]
   ```
3. **Обмін публічними точками**: Клієнт передає `Q_c` у розширенні `key_share` повідомлення `ClientHello`. Сервер відповідає своєю точкою `Q_s` у розширенні `key_share` повідомлення `ServerHello`.
4. **Обчислення спільного секрету**:
   - Клієнт множить свій приватний ключ `d_c` на публічну точку сервера `Q_s`:
     ```text
     Z_client = d_c · Q_s = d_c · (d_s · G) = (d_c · d_s) · G
     ```
   - Сервер множить свій приватний ключ `d_s` на публічну точку клієнта `Q_c`:
     ```text
     Z_server = d_s · Q_c = d_s · (d_c · G) = (d_s · d_c) · G
     ```
   Завдяки асоціативності та абелевій груповій структурі точок еліптичної кривої отримуємо точну рівність:
   ```text
   Z_client = Z_server = Z
   ```

Як спільний вхідний секрет `IKM` (Input Keying Material) береться лише `x`-координата точки `Z`, зведена до вектора байтів фіксованої довжини:
```text
IKM = bytes(x_Z)
```

### Алгоритм драбини Монтгомері (Montgomery Ladder) для захисту від side-channel атак

Під час обчислення скалярного добутку `d · G` на еліптичних кривих звичайний алгоритм «double-and-add» піддається атакам по побічних каналах (Side-Channel Attacks, зокрема розгалуження часу виконання чи енергоспоживання). У залежності від того, чи дорівнює поточний біт ключа `0` чи `1`, виконання гілки `if` займає різний час.

Для усунення цієї вразливості в Curve25519 застосовується **драбина Монтгомері**, яка виконує однакову кількість операцій додавання й подвоєння точок на кожен біт ключа незалежно від його значення:

```text
R_0 = G
R_1 = 2 · G

for i from (k-1) down to 0:
    if bit_i(d) == 0:
        R_1 = R_0 + R_1
        R_0 = 2 · R_0
    else:
        R_0 = R_0 + R_1
        R_1 = 2 · R_1

return R_0
```

Завдяки строго константному часу виконання драбина Монтгомері робить неможливим відновлення ефемерного приватного ключа `d` шляхом вимірювання мікросекундних затримок процесора (атаки типу Flush+Reload чи Prime+Probe).

## 2. Ієрархія розгортання ключів HKDF (RFC 5869 / RFC 8446)

HKDF (HMAC-based Extract-and-Expand Key Derivation Function) будується на псевдовипадковій геш-функції HMAC (наприклад, HMAC-SHA256) і складається з двох послідовних математичних операцій: `HKDF-Extract` та `HKDF-Expand`.

### 2.1. Операція Extract (Конденсація ентропії)

Операція `Extract` бере вхідний секрет `IKM`, який може мати нерівномірний розподіл ентропії, і стискає його у псевдовипадковий ключ `PRK` (Pseudorandom Key) фіксованої довжини `HashLen` (32 байти для SHA-256):

```text
PRK = HMAC-Hash(Salt, IKM)
```
Якщо аргумент `Salt` відсутній або порожній, замість нього береться рядок із нульових байтів довжиною `HashLen`.

Математичне обґрунтування безпеки `HKDF-Extract` спирається на **лемму про залишок ентропії (Leftover Hash Lemma)**. Навіть якщо координата `x_Z` точок еліптичної кривої не є повністю рівномірним псевдовипадковим вектором, застосування універсального сімейства геш-функцій HMAC концентрує фізичну ентропію джерела у рівномірно розподілений ключ `PRK`.

### 2.2. Операція Expand (Розгортання ключів)

Операція `Expand` бере псевдовипадковий ключ `PRK` та контекстну мітку `Info` і розгортає їх у вихідний псевдовипадковий потік `OKM` (Output Keying Material) необхідної довжини `L` байтів за допомогою послідовної ітерації HMAC:

```text
T(0) = порожній рядок
T(1) = HMAC-Hash(PRK, T(0) + Info + 0x01)
T(2) = HMAC-Hash(PRK, T(1) + Info + 0x02)
T(3) = HMAC-Hash(PRK, T(2) + Info + 0x03)
...
OKM = T(1) + T(2) + T(3) + ... [обрізано до перших L байтів]
```

### 2.3. Помічник HKDF-Expand-Label у TLS 1.3

Для уникнення колізій між різними ключами у TLS 1.3 специфікація RFC 8446 визначає спеціальну функцію-обгортку `HKDF-Expand-Label`, яка автоматично додає префікс `"tls13 "` та прив'язує ключ до транскрипту рукостискання:

```text
HKDF-Expand-Label(Secret, Label, Context, Length) = 
    HKDF-Expand(Secret, HkdfLabel, Length)

де HkdfLabel є бінарною структурою:
  struct {
      uint16 length = Length;
      opaque label<7..255> = "tls13 " + Label;
      opaque context<0..255> = Context; // Зазвичай Transcript-Hash
  };
```

## 3. Математичний граф деривації ключів у TLS 1.3

Нехай `H(Messages)` — це результат гешування SHA-256 від конкатенації послідовних повідомлень рукостискання.

```text
                  00...00 (HashLen zeroes)
                     |
                     v
   IKM = 0  --->  HKDF-Extract  --->  Early Secret
                     |
                     +---> Derive-Secret(..., "derived", "")
                     |
                     v  (Використовується як Salt)
   IKM = ECDHE ---> HKDF-Extract  --->  Handshake Secret
   Shared Secret     |
   (bytes(x_Z))      +---> HKDF-Expand-Label(..., "c hs traffic", H(ClientHello..ServerHello))
                     |      = Client Handshake Traffic Key
                     |
                     +---> HKDF-Expand-Label(..., "s hs traffic", H(ClientHello..ServerHello))
                     |      = Server Handshake Traffic Key
                     |
                     +---> Derive-Secret(..., "derived", "")
                     |
                     v  (Використовується як Salt)
   IKM = 0  --->  HKDF-Extract  --->  Master Secret
                     |
                     +---> HKDF-Expand-Label(..., "c ap traffic", H(ClientHello..Finished))
                     |      = Client Application Traffic Key
                     |
                     +---> HKDF-Expand-Label(..., "s ap traffic", H(ClientHello..Finished))
                            = Server Application Traffic Key
```

### Математичний захист цілісності рукостискання (Transcript Binding)

Кожен секрет трафіку створюється за допомогою `HKDF-Expand-Label` з явним включенням `Transcript-Hash` — гешу від усіх переданих раніше повідомлень. Якщо нападник посередині (MITM) змінить хоча б один біт у повідомленні `ClientHello` (наприклад, виріже розширення або змінить список шифрокомплектів), це призведе до зміни значення `Transcript-Hash`.

У результаті Клієнт і Сервер згенерують **абсолютно різні симетричні ключі шифрування**. Перша ж спроба сервера розшифрувати повідомлення або спроба клієнта перевірити HMAC у кадрі `Finished` завершиться фатальною помилкою `decrypt_error`.

## 4. Формування маски IV для AEAD-шифрування (Nonce XOR Masking)

Для захисту від атак повторного використання вектору ініціалізації (IV Reuse) у симетричному AEAD-шифруванні (AES-GCM чи ChaCha20-Poly1305) TLS 1.3 усунув відкриту передачу IV в заголовку кадру.

Замість цього 96-бітовий вектор ініціалізації `Nonce` для кожного кадру обчислюється як результативна операція XOR між статичним вектором `write_iv` та 64-бітовим порядковим номером кадру `seq_num`:

```text
Nonce_i = write_iv XOR (seq_num_i padded to 96 bits)
```

Де `seq_num` починається з `0` для першого зашифрованого кадру й монотонно інкрементується на `1` з кожним наступним кадром.

Оскільки монотонний лічильник `seq_num` гарантує 100% унікальність для кожного кадру в межах одного ключа, колізія значень `Nonce` стає математично неможливою. Це унеможливлює катастрофічні криптографічні атаки на режим AES-GCM, при яких повторне використання одного й того самого IV призводить до миттєвої компрометації аутентифікаційного ключа GHASH.
