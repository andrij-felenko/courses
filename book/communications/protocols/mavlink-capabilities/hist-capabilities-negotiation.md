# 📜 Еволюція узгодження можливостей у MAVLink: від жорстких припущень до динамічного рукостискання

На світанку розвитку відкритої безпілотної авіації у 2009–2013 роках кожна наземна станція керування (англ. *Ground Control Station*, GCS) працювала з польотним контролером за принципом жорстких припущень. Щойно оператор підключав дрон через модем телеметрії, станція зчитувала перший пакет `HEARTBEAT` і намагалася вгадати логіку подальшої взаємодії лише за двома числовими полями: типом автопілота (`MAV_AUTOPILOT_ARDUPILOTMEGA` чи `MAV_AUTOPILOT_PX4`) та типом апарата (`MAV_TYPE_QUADROTOR` чи `MAV_TYPE_FIXED_WING`). Якщо користувач завантажував експериментальну прошивку, використовував кастомний мікроконтролер або оновлював автопілот до нової версії з іншим набором команд, зв'язок розвалювався: станція надсилала пакети нового формату, які стара прошивка мовчки відкидала через невідповідність довжини або невідомий номер повідомлення. Потреба у динамічному протоколі узгодження можливостей (англ. *capability negotiation*) стала питанням фізичної безпеки польотів.

### Криза точності шляхових точок: чому одинарної точності виявилося замало

Найгостріший технічний конфлікт, який змусив розробників протоколу переглянути фундаментальні принципи кадрування, виник навколо передачі географічних координат у протоколі польотних місій.

У першій версії стандарту MAVLink для передачі координат шляхових точок (повідомлення `MISSION_ITEM`, `#39`) використовувалися числа з рухомою комою одинарної точності за стандартом IEEE 754 (`float32`). Це рішення здавалося логічним для 8-бітних мікроконтролерів AVR (плата APM 2.0/2.5/2.6), оскільки 4-байтні числа займали мінімум місця в оперативній пам'яті та швидко пакувалися в радіоканал.

Проте формат `float32` має всього 24 біти двійкової мантиси (23 біти зберігаються явно, один біт нормалізації прихований), що еквівалентно приблизно `7.22` десяткових знаків точності:

```
2²⁴ = 16 777 216 ≈ 10⁷·²²  [роздільна здатність мантиси float32]
```

Довжина екватора Землі становить приблизно 40 075 кілометрів, що відповідає розмаху географічної широти у 180 градусів та довготи у 360 градусів. Отже, один градус широти дорівнює:

```
40 075 000 м ÷ 360° ≈ 111 319.4 м/градус
```

Якщо географічна координата має значення `50.4501234` градусів (типова точка в межах Києва), вона містить дев'ять десяткових цифр. Формат `float32` фізично не здатний зберегти дев'ять значущих цифр: він зберігає лише перші сім цифр, а решта обнуляється або округлюється до найближчого двійкового представлення:

```
50.4501234  [бажана координата з сантиметровою точністю]
50.4501228  [найближче представлення у float32]
Δ = 0.0000006° ≈ 0.067 м = 6.7 см похибки на рівному місці
```

У міру віддалення від нульового меридіана та наближення довготи до 180 градусів (де ціла частина займає вже три десяткових розряди, наприклад `179.1234567`) кількість доступних знаків після коми у `float32` зменшується до чотирьох. Ціна одного квота дискретизації досягає:

```
0.0001° · 111 319 м ≈ 11.13 м
```

Коли у 2013–2014 роках з'явилися приймачі RTK-GPS із сантиметровою точністю та автоматичні системи зльоту й посадки на базу, похибка у кілька метрів через округлення чисел із рухомою комою стала неприпустимою.

Для вирішення проблеми було розроблено повідомлення `MISSION_ITEM_INT` (`#73`), у якому широта й довгота передаються як 32-бітні цілі числа зі знаком (`int32_t`), масштабовані на коефіцієнт `1e7` (десять мільйонів). Діапазон `int32_t` від `-2 147 483 648` до `+2 147 483 647` ідеально покриває діапазон від `-180.0000000°` до `+180.0000000°` із фіксованою роздільною здатністю:

```
1° ÷ 10 000 000 = 0.0000001° ≈ 1.11 см
```

Але виникла інша проблема: якщо сучасна наземна станція надішле повідомлення `MISSION_ITEM_INT` старій прошивці, старий парсер, який не знає `ID 73`, скине повідомлення з помилкою контрольної суми `CRC_EXTRA`. Дрон залишиться без місії. Якщо ж станція з переляку надішле старий `MISSION_ITEM`, новий контролер прийме його, але втратить сантиметрову точність.

Єдиним виходом стало введення бітового прапорця можливостей: автопілот зобов'язаний явно повідомити станції: «Я вмію приймати `MISSION_ITEM_INT`», виставивши біт `MAV_PROTOCOL_CAPABILITY_MISSION_INT` (значення `0x04`).

### Пастка конфігураційних параметрів: спотворення бітових масок у float

Паралельно розгорталася ще одна криза, пов'язана з протоколом конфігурації параметрів.

У класичному MAVLink усі параметри передавалися у повідомленні `PARAM_VALUE` (`#22`), де значення зберігалося в єдиному 32-бітному полі `float param_value`. Для дійсних чисел (коефіцієнти PID-регуляторів, ліміти швидкості) це працювало ідеально. Але для системних конфігурацій потрібні були інші типи даних: 32-бітні бітові маски прапорців калібрування, цілі числа конфігурації портів, рядкові ідентифікатори.

Розробники прошивок пішли на небезпечний компроміс: вони виконували пряме побайтове копіювання пам'яті (англ. *type punning* або `memcpy`) з `int32_t` у `float` перед відправкою, а на приймачі робили зворотну операцію.

Але стандарти компіляторів C/C++ та апаратні блоки FPU процесорів містять пастку: не всі комбінації 32 бітів є допустимими числами з рухомою комою. Певні бітові комбінації інтерпретуються як нечислові значення (англ. *Not-a-Number*, NaN) або ненормалізовані числа (англ. *denormalized numbers*).

Коли апаратний співпроцесор FPU бачить бітову маску, схожу на сигнальне значення NaN (наприклад `0x7FC00001`), він може автоматично замінити її на канонічний тихий NaN (`0x7FC00000`), безповоротно стираючи молодші біти конфігурації!

```
0x7FC00001  [початкова бітова маска конфігурації сенсорів]
     │
     ▼  (проходження через FPU регістр або компіляторну оптимізацію)
0x7FC00000  [спотворене значення після нормалізації NaN]
```

Це призводило до катастрофічних наслідків: користувач вмикав прапорець резервного компаса, а після передачі через MAVLink біт зникав, або навпаки — вмикав небажані функції.

Для подолання цієї кризи було розроблено протокол розширених параметрів `PARAM_EXT_VALUE` (прапорець `MAV_PROTOCOL_CAPABILITY_PARAM_UNION`) та швидкісний протокол передачі параметрів через бінарні файли MAVLink FTP (прапорець `MAV_PROTOCOL_CAPABILITY_FTP`). Завдяки цьому параметри передаються без участі FPU, у вигляді сирих типізованих байтів.

### Еволюція калібрування сенсорів та зовнішнього керування

Ще одним болісним кроком розвитку була процедура калібрування компаса (магнітометра).

У ранніх версіях ArduPilot та QGroundControl для усунення спотворень магнітного поля (англ. *hard iron* та *soft iron distortions*) застосовувався незграбний підхід: користувач вручну обертав дрон навколо всіх осей, у той час як автопілот неперервно транслював сирі вектори напруженості магнітного поля через повільний радіолінк (57600 бод). Наземна станція збирала тисячі точок, розраховувала матрицю еліпсоїдного наближення методом найменших квадратів на процесорі ноутбука, а потім по черзі записувала дев'ять обчислених коефіцієнтів назад у пам'ять автопілота через протокол параметрів.

Якщо радіозв'язок переривався посеред запису коефіцієнтів, у контролері залишалася наполовину оновлена матриця корекції, що гарантувало втрату орієнтації та зрив у штопор (англ. *toilet-bowling*) при першому зльоті.

Поява прапорця `MAV_PROTOCOL_CAPABILITY_COMPASS_CALIBRATION` (`0x0800`) кардинально змінила цей процес: потужні 32-бітні процесори ARM Cortex-M4/M7 отримали змогу самостійно виконувати факторизацію та розрахунок матриці корекції безпосередньо у прошивці. Станція тепер лише ініціює команду старту калібрування і відображає прогрес у відсотках, усуваючи ризик спотворення коефіцієнтів через радіошум.

Схожа революція відбулася у сфері зовнішнього комп'ютерного зору та бортових комп'ютерів (Raspberry Pi, Nvidia Jetson). Замість підміни сигналів апаратури радіокерування через небезпечний `RC_CHANNELS_OVERRIDE`, введення прапорців `MAV_PROTOCOL_CAPABILITY_SET_ATTITUDE_TARGET` та `MAV_PROTOCOL_CAPABILITY_SET_POSITION_TARGET_LOCAL_NED` стандартизувало пряму передачу просторових векторів швидкості та кватерніонів орієнтації для систем автономного огинання перешкод.

### Перехід до MAVLink 2.0: прапорець PROTOCOL_V2

У 2016–2017 роках відбувся масштабний перехід протоколу на версію MAVLink 2.0. Новий стандарт приніс 24-бітні ідентифікатори повідомлень (замість 8-бітних), нульове стискання корисного навантаження, поля розширень та криптографічний підпис пакетів для захисту від підміни команд в ефірі.

Проте виникла проблема сумісності: радіоканал не міг миттєво переключитися на v2, доки обидві сторони не переконаються у взаємній підтримці нового кадрування. Наземні станції використовували гібридний режим: перші запити надсилалися у форматі v1, а щойно автопілот повертав `AUTOPILOT_VERSION` із встановленим бітом `MAV_PROTOCOL_CAPABILITY_MAVLINK2` (`0x1000`), станція негайно перемикала весь вихідний потік на кадрування зі стартовим байтом `0xFD` (MAVLink v2).

### Народження AUTOPILOT_VERSION (#148) та стандартизація MAV_CMD_REQUEST_MESSAGE

У 2014 році провідні архітектори екосистеми MAVLink — Лоренц Маєр (творець PX4 та MAVLink) та Ендрю Тріджелл (ведучий розробник ArduPilot) — домовилися стандартизувати єдине двійкове повідомлення, яке б описувало всі характеристики автопілота в одному пакеті.

Так народилося повідомлення `AUTOPILOT_VERSION` (`#148`). Воно об'єднало:
1. 64-бітну маску можливостей `capabilities`;
2. Версії трьох рівнів програмного стека: польотна прошивка (`flight_sw_version`), проміжний рівень (`middleware_sw_version`) та операційна система (`os_sw_version`);
3. Апаратну версію друкованої плати (`board_version`);
4. Коміти вихідного коду Git (`flight_custom_version`), що дозволило GCS точно ідентифікувати тестові збірки розробників.

Спочатку для виклику цього повідомлення було створено спеціалізовану команду `MAV_CMD_AUTOPILOT_VERSION_REQUEST` (`#183`). Але дуже швидко стало очевидно, що плодити окрему команду для кожного інформаційного повідомлення — це глухий кут архітектури: кожне нове повідомлення вимагало б розширення таблиці обробників команд у прошивці.

Тому команду `#183` було оголошено застарілою, а замість неї було введено універсальну команду `MAV_CMD_REQUEST_MESSAGE` (`#512`). Її перший параметр `param1` просто приймає числовий номер потрібного повідомлення (наприклад, `148.0f` для `AUTOPILOT_VERSION`, `264.0f` для `FLIGHT_INFORMATION` або `300.0f` для інформації про протокол).

### Від 64-бітного UID до 128-бітного UID2: вимога криптографії та Remote ID

Останнім етапом еволюції повідомлення стало поле апаратного ідентифікатора.

Спочатку повідомлення містило 64-бітне числове поле `uid` (`uint64_t`). Для ранніх контролерів цього вистачало. Проте зі стандартизацією архітектури Pixhawk та переходом на мікроконтролери STM32F4/F7/H7 виявилося, що апаратний заводський номер процесора (Electronic Signature / Unique Device ID), який вшивається на фабриці STMicroelectronics у захищені регістри пам'яті, має розмір 96 бітів (12 байтів, 3 слова по 32 біти). Спроба втиснути 96-бітне число у 64-бітне поле `uid` призводила до того, що прошивки або брали `CRC64` від серійного номера, або відкидали 32 біти, що створювало ризик колізій ідентифікаторів у великих флотах дронів.

Більше того, ухвалення стандартів дистанційної ідентифікації безпілотників (FAA Remote ID у США та EASA Open Category в ЄС) вимагало наявності глобально унікального 128-бітного ідентифікатора апарата (UUIDv4 або серійного номера стандарту ANSI/CTA-2063-A).

Щоб вирішити цю проблему без порушення зворотної сумісності, до блоку розширень повідомлення `AUTOPILOT_VERSION` було додано масив `uid2` розміром 18 байтів. Перший байт задає тип та довжину ідентифікатора, а решта байтів зберігають повний серійний номер чіпа.

Сьогодні процедура узгодження можливостей є обов'язковим першим кроком під час підключення будь-якого безпілотного апарата: вона унеможливлює збої через несумісність форматів, гарантує сантиметрову точність навігації та забезпечує повний захист каналу зв'язку.
