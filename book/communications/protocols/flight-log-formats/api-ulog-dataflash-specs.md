# 📋 Побайтова специфікація двійкових форматів ULog та DataFlash (BIN)

Цей технічний довідник визначає побайтову двійкову структуру заголовків, опкодів повідомлень, форматних дескрипторів, масок прапорців та правил вирівнювання даних для двох промислових стандартів високочастотного бортового логування безпілотних апаратів: PX4 ULog та ArduPilot DataFlash (.BIN). Специфікація призначена для системних інженерів, розробників низькорівневого вбудованого програмного забезпечення польотних контролерів та авторів діагностичного інструментарію аналізу польотів для автономного створення сумісних бінарних кодеків, парсерів та валідаторів без звернення до вихідного коду автопілотів.

---

## 1. Загальні конвенції серіалізації та пам'яті

Обидва формати проектувалися з розрахунку на пряме копіювання даних з оперативної пам'яті мікроконтролерів із 32-бітною та 64-бітною архітектурою (ARM Cortex-M4/M7, RISC-V, POSIX SITL), де пам'ять організована з прямим порядком розташування байтів.

### 1.1. Порядок байтів (Endianness)
Усі числові значення довжиною понад один байт — беззнакові цілі (`uint16_t`, `uint32_t`, `uint64_t`), цілі зі знаком (`int8_t`, `int16_t`, `int32_t`, `int64_t`) та числа з рухомою комою стандартів IEEE 754 (`float` 32 біти, `double` 64 біти) — завжди записуються у файл у порядку **Little-Endian** (молодший байт розміщується за найменшою адресою пам'яті). Декодери на платформах Big-Endian (наприклад, деяких мережевих процесорах MIPS) зобов'язані здійснювати побайтову реверсію при розпакуванні.

### 1.2. Щільне пакування (Structure Packing)
У двійкових потоках обох форматів поля повідомлень розміщуються підряд без компіляторного вирівнювання за 4- чи 8-байтними межами адресації пам'яті (англ. *packed structures*, директива `__attribute__((packed))` у компіляторах GCC/Clang). Це мінімізує обсяг запису на повільні накопичувачі, але вимагає особливої обережності при прямому розіменуванні вказівників на непарних адресах пам'яті на апаратних архітектурах без підтримки невирівняного доступу (англ. *unaligned memory access fault*).

### 1.3. Кодування символьних рядків
Текстові назви топіків, параметрів, системних ключів та журналів кодуються в ASCII або базовому діапазоні UTF-8:
* У форматі ULog рядки змінної довжини передаються без термінального нульового байта `\0`, а їхній розмір обчислюється з різниці між загальною довжиною повідомлення та довжиною його фіксованих полів або визначається окремим однобайтним префіксом довжини `key_len`.
* У форматі DataFlash більшість рядків мають жорстко зафіксовану довжину масиву (`char[4]`, `char[16]`, `char[50]`, `char[64]`). Якщо довжина тексту менша за місткість поля, залишок масиву обов'язково заповнюється нульовими байтами `0x00`.

## 2. Повна специфікація формату PX4 ULog

Двійковий файл ULog являє собою структурований потік, що відкривається 16-байтним заголовком ідентифікації версії, за яким слідує послідовність самоописних секційних контейнерів.

### 2.1. Заголовок файлу (File Header Layout)

Файл розпочинається строго з 16 фіксованих байтів:

| Зміщення (байти) | Розмір | Назва поля | Тип | Опис та фіксовані значення |
| :--- | :--- | :--- | :--- | :--- |
| `0x00..0x06` | 7 | `magic` | `uint8_t[7]` | Магічна сигнатура: `0x55 0x4C 0x6F 0x67 0x01 0x12 0x35` («ULog» + v1) |
| `0x07..0x0E` | 8 | `timestamp` | `uint64_t` | Системний час старту логування (мікросекунди від завантаження системи або UTC) |
| `0x0F` | 1 | `reserved` | `uint8_t` | Зарезервовано під майбутні розширення (значення `0x00`) |

### 2.2. Загальний контейнер повідомлення ULog

Кожне повідомлення в потоці логу після 16-байтного заголовка файлу загортається в стандартний 3-байтний транспортний фрейм:

```
+---------------------+--------------------+------------------------------------------+
| msg_size (uint16_t) | msg_type (uint8_t) | msg_payload (довжина: msg_size байтів)   |
+---------------------+--------------------+------------------------------------------+
  0                  1 2                  3  4 ... (msg_size + 3)
```

Поле `msg_size` (2 байти Little-Endian) визначає точну довжину тіла повідомлення в байтах і не включає самі 3 байти заголовка (`msg_size` + `msg_type`). Поле `msg_type` (1 байт) визначає семантику корисної інформації.

### 2.3. Реєстр типів повідомлень ULog

| Код типу | ASCII | Назва секції | Фаза запису | Призначення |
| :--- | :--- | :--- | :--- | :--- |
| `0x48` | `'H'` | Flag / Header Bits | Початок файлу | Сумісність та прапорці формату |
| `0x46` | `'F'` | Format Definition | Початок / Динамічно | Опис схеми структури uORB |
| `0x49` | `'I'` | Information (Meta) | Початок / Динамічно | Текстові або числові метадані системи |
| `0x4D` | `'M'` | Multi Information | Початок / Динамічно | Багатосекційні метадані довжиною > 255 B |
| `0x50` | `'P'` | Parameter | Початок / Динамічно | Початкові та змінені системні параметри |
| `0x51` | `'Q'` | Parameter Default | Початок файлу | Заводські значення параметрів за замовчуванням |
| `0x41` | `'A'` | Add Logged Msg | Динамічно | Підписка: прив'язка `msg_id` до імені схеми |
| `0x52` | `'R'` | Remove Logged Msg | Динамічно | Скасування реєстрації `msg_id` |
| `0x44` | `'D'` | Data | Тіло польоту | Сирий бінарний семпл даних uORB |
| `0x4C` | `'L'` | Logged String | Тіло польоту | Текстовий журнал (syslog) |
| `0x43` | `'C'` | Tagged Logged String| Тіло польоту | Текстовий журнал із тегом підсистеми |
| `0x53` | `'S'` | Sync / Dropout | Тіло польоту | Фіксація втрати кадрів через переповнення |

### 2.4. Побайтовий аналіз секцій метаданих та схем

#### Секція прапорців та сумісності `'H'` (0x48)
Секція `'H'` передається одразу після заголовка файлу. Вона інформує парсер про наявність спеціальних режимів запису:

```
Побайтова структура Payload 'H' (фіксовано 40 байтів):
  +0x00: uint8_t incompat_flags[8]   [Маска несумісних прапорців]
  +0x08: uint8_t compat_flags[8]     [Маска сумісних прапорців]
  +0x10: uint64_t appended_offsets[3] [Зміщення блоків дозапису у файлі]
```

Значення бітових масок `incompat_flags`:
* **Біт 0 (`0x01`): `ULOG_INCOMPAT_FLAG_APPENDED_DATA`** — вказує, що файл містить додаткові сегменти дозапису, зафіксовані у масиві `appended_offsets`. Якщо парсер не підтримує обробку розривів дозапису, аналіз файлу зупиняється з помилкою несумісності.
* **Біт 1 (`0x02`): `ULOG_INCOMPAT_FLAG_EXTENDED_TYPES`** — сигналізує про використання розширеного набору системних типів uORB.
* **Решта бітів (2..63):** Зарезервовано. Якщо встановлено невідомий біт у `incompat_flags`, сторонній парсер зобов'язаний відхилити файл.

#### Секція опису структури `'F'` (0x46)
Секція `'F'` містить повний декларативний опис топіка шини uORB. Формат запису є повністю текстовим і складається з імені структури, двокрапки та списку полів, розділених крапкою з комою:

```
Payload 'F': "format_name:type1 field1;type2[N] field2;type3 field3;"
```

Приклад реального пакету `'F'` для повідомлення `sensor_combined`:
`sensor_combined:uint64_t timestamp;float[3] gyro_rad;uint32_t gyro_integral_dt;int32_t accelerometer_timestamp_relative;float[3] accelerometer_m_s2;uint32_t accelerometer_integral_dt;`

Правила розбору форматного рядка:
1. Символ `:` відокремлює назву структури від списку її внутрішніх полів.
2. Поля відокремлюються символом `;`. Останнє поле також обов'язково завершується крапкою з комою.
3. Оголошення поля складається з типу та імені, розділених рівно одним пробілом (`"uint64_t timestamp"`).
4. Якщо після типу стоять квадратні дужки `[N]`, це означає фіксований масив із `N` однотипних елементів (`"float[3] gyro_rad"`).
5. Дозволяються вкладені типи. Якщо поле містить нестандартний базовий тип (наприклад `"quaternion q"`), парсер очікує знайти окреме визначення `'F'` для структури `quaternion` раніше в потоці логу або розпаковує його рекурсивно.

#### Секція системних метаданих `'I'` (0x49) та `'M'` (0x4D)
Використовується для запису ідентифікаторів прошивки, конфігурації плати, версії протоколів та серійних номерів апаратури:

```
Побайтова структура Payload 'I':
  +0x00: uint8_t key_len          [Довжина рядка ключа, N байтів]
  +0x01: char    key[key_len]     [Текстовий опис типу та імені: "type key_name"]
  +1+N : uint8_t value[]          [Двійкове значення або рядок, довжина = msg_size - 1 - key_len]
```

Для довгих текстових рядків (довжиною понад 255 байтів), таких як повний дамп параметрів або текстові звіти про ініціалізацію, застосовується секція `'M'` (Multi-part Info). Її першим байтом після `key_len` є однобайтний індекс фрагмента `is_continued`, що вказує на продовження попереднього метаблоку.

Типові стандартні ключі метаданих:
* `char[28] sys_name` — ідентифікатор системи, наприклад `"PX4 Autopilot"`.
* `char[16] ver_sw` — символьна назва версії прошивки (`"v1.14.0"`).
* `char[16] ver_hw` — апаратна платформа контролера (`"PX4_FMU_V5X"`).
* `char[40] ver_sw_release` — повний 40-символьний Git SHA комміту складання.
* `uint32_t boot_time_utc` — час завантаження системи за шкалою UTC в секундах.
* `int32_t replay` — бінарний прапорець (`1`), якщо лог записано в режимі симулятора або апаратного відтворення.

#### Секція параметрів `'P'` (0x50) та дефолтних параметрів `'Q'` (0x51)
Фіксує стан системи на момент зльоту, а також динамічні зміни налаштувань у процесі польоту:

```
Побайтова структура Payload 'P':
  +0x00: uint8_t key_len          [Довжина рядка ключа, N байтів]
  +0x01: char    key[key_len]     [Текстовий опис: "float MC_ROLL_P" або "int32_t SYS_AUTOSTART"]
  +1+N : uint8_t value[]          [Значення параметра: 4 байти для float/int32 або 8 байтів для double]
```

#### Секція реєстрації підписки на дані `'A'` (0x41) та зняття підписки `'R'` (0x52)
Секція `'A'` виконує прив'язку компактного числового ідентифікатора `msg_id` (2 байти) до раніше зареєстрованого типу структури uORB:

```
Побайтова структура Payload 'A':
  +0x00: uint8_t  multi_id        [Індекс екземпляра: 0 = перший сенсор, 1 = дублюючий сенсор]
  +0x01: uint16_t msg_id          [Числовий ID топіка в бінарному потоці: 0..65535]
  +0x03: char     message_name[]  [Назва структури uORB, довжина = msg_size - 3]
```

Секція `'R'` (Remove) скасовує дію підписки й має довжину payload рівно 2 байти, що містять `uint16_t msg_id`. Після появи повідомлення `'R'` парсер припиняє обробку кадрів `'D'` із цим ідентифікатором, доки не надійде нове повідомлення `'A'`.

### 2.5. Побайтовий аналіз секцій даних та подій

#### Секція сирих бінарних вибірок `'D'` (0x44)
Найбільш високочастотне повідомлення, на частку якого припадає до 98% загального обсягу файлу:

```
Побайтова структура Payload 'D':
  +0x00: uint16_t msg_id          [Ідентифікатор підписки, оголошений у секції 'A']
  +0x02: uint8_t  data[]          [Сирі байти структури, довжина = msg_size - 2]
```
Байти поля `data` безпосередньо відповідають полям структури, оголошеним у відповідному форматі `'F'`, включаючи часову мітку `timestamp` (uint64_t), значення датчиків, кути орієнтації чи сигнали керування.

#### Секція текстового журналу `'L'` (0x4C) та тегованого журналу `'C'` (0x43)
Використовується для запису діагностичних текстових повідомлень компонентів системи:

```
Побайтова структура Payload 'L':
  +0x00: uint8_t  log_level       [Рівень важливості повідомлення: 0..7]
  +0x01: uint64_t timestamp       [Час генерації повідомлення в мікросекундах]
  +0x09: char     message[]       [Текст повідомлення UTF-8, довжина = msg_size - 9]
```

Рівні важливості `log_level`:
* `0` — `EMERGENCY` (негайне падіння, критична відмова ядра)
* `1` — `ALERT` (відмова основного джерела живлення, аварійна посадка)
* `2` — `CRITICAL` (відмова головного навігаційного фільтра)
* `3` — `ERROR` (помилка драйвера датчика або втрата зв'язку)
* `4` — `WARNING` (перевищення порогу вібрацій або температури)
* `5` — `NOTICE` (зміна режиму керування або фіксація Arm/Disarm)
* `6` — `INFO` (інформаційне повідомлення планувальника)
* `7` — `DEBUG` (глибока інженерна діагностика розробників)

У повідомленні `'C'` після мітки часу додається 2-байтний дескриптор `tag` (`uint16_t`), що ідентифікує модуль чи потік операційної системи.

#### Секція втрати даних `'S'` (0x53)
Повідомлення дропу генерується підсистемою логування, коли швидкість надходження повідомлень у кільцевий буфер SRAM перевищує пропускну здатність запису на SD-карту:

```
Побайтова структура Payload 'S':
  +0x00: uint16_t duration        [Тривалість випадання даних у мілісекундах]
```
Отримавши пакет `'S'`, парсер коригує графіки часових рядів, розриваючи неперервні лінії інтерполяції сигналів на відповідний часовий інтервал `duration`.

## 3. Повна специфікація формату ArduPilot DataFlash (.BIN)

Двійковий формат ArduPilot DataFlash є суворо покадровим. Кожен двійковий пакет у файлі починається з унікальної 2-байтної преамбули кадрування.

```
Загальна структура пакету DataFlash:
+--------------+--------------+------------------+------------------------------------+
| HEAD1 (0xA3) | HEAD2 (0x95) | Type ID (uint8)  | Payload (довжина = FMT.Length - 3) |
+--------------+--------------+------------------+------------------------------------+
  0              1              2                  3 ... FMT.Length
```

* `HEAD1 = 0xA3` (десяткове `163`): перший синхронізуючий байт кадру.
* `HEAD2 = 0x95` (десяткове `149`): другий синхронізуючий байт кадру.
* `Type ID` (1 байт, `0x00..0xFF`): числовий тип повідомлення.
* `Payload`: масив даних фіксованої довжини, визначеної у схемі `FMT` для цього `Type ID`.

---

### 3.1. Символьні специфікатори типів полів DataFlash

Кожне поле структури кодується одним ASCII-символом у форматній масці:

| Символ | Тип у C/C++ | Байт | Опис та правила масштабування |
| :---: | :--- | :---: | :--- |
| `b` | `int8_t` | 1 | 8-бітне ціле зі знаком |
| `B` | `uint8_t` | 1 | 8-бітне ціле без знака |
| `h` | `int16_t` | 2 | 16-бітне ціле зі знаком |
| `H` | `uint16_t` | 2 | 16-бітне ціле без знака |
| `i` | `int32_t` | 4 | 32-бітне ціле зі знаком |
| `I` | `uint32_t` | 4 | 32-бітне ціле без знака |
| `q` | `int64_t` | 8 | 64-бітне ціле зі знаком |
| `Q` | `uint64_t` | 8 | 64-бітне без знака (зазвичай системний час `TimeUS` у мкс) |
| `f` | `float` | 4 | Число з рухомою комою одинарної точності IEEE 754 |
| `d` | `double` | 8 | Число з рухомою комою подвійної точності IEEE 754 |
| `n` | `char[4]` | 4 | Текстовий рядок фіксованої довжини 4 байти |
| `N` | `char[16]` | 16 | Текстовий рядок фіксованої довжини 16 байтів |
| `Z` | `char[64]` | 64 | Текстовий рядок фіксованої довжини 64 байти |
| `c` | `int16_t` | 2 | Фіксована кома: `значення = int16 / 100.0` (наприклад кут × 100) |
| `C` | `uint16_t` | 2 | Фіксована кома: `значення = uint16 / 100.0` |
| `e` | `int32_t` | 4 | Фіксована кома: `значення = int32 / 100.0` |
| `E` | `uint32_t` | 4 | Фіксована кома: `значення = uint32 / 100.0` |
| `L` | `int32_t` | 4 | Географічні координати: `градуси = int32 / 10000000.0` (масштаб `1e-7`) |
| `M` | `uint8_t` | 1 | Числовий код польотного режиму автопілота |

### 3.2. Керівні структури опису схеми DataFlash

#### Повідомлення опису схеми `FMT` (Type `0x80` = 128)
Повідомлення `FMT` має строго фіксовану довжину 89 байтів (86 байтів payload + 3 байти заголовка):

:::tabs
```c
// C99 / C11
struct __attribute__((packed)) DataFlash_FMT_Payload {
    uint8_t  type;          // Числовий ідентифікатор типу повідомлення (1..255)
    uint8_t  length;        // Повна довжина пакета в байтах (включно з заголовком 0xA3 0x95 Type)
    char     name[4];       // 4-байтова назва типу повідомлення з доповненням нулями ("ATT\0", "GPS\0")
    char     format[16];    // Рядок специфікаторів типів полів (наприклад "Qffff", доповнений нулями)
    char     columns[64];   // Назви полів через кому ("TimeUS,Roll,Pitch,Yaw,ErrRP", доповнений нулями)
};
```
```cpp
// C++20
#include <cstdint>
#include <array>

#pragma pack(push, 1)
struct DataFlash_FMT_Payload {
    uint8_t  type{0};
    uint8_t  length{0};
    std::array<char, 4>  name{};
    std::array<char, 16> format{};
    std::array<char, 64> columns{};
};
#pragma pack(pop)
```
:::

#### Повідомлення одиниць вимірювання `FMTU` (Type `0x2A` = 42)
Описує фізичні одиниці та множники для полів зареєстрованого типу:

:::tabs
```c
// C99 / C11
struct __attribute__((packed)) DataFlash_FMTU_Payload {
    uint64_t time_us;       // Час реєстрації схеми в мікросекундах
    uint8_t  type;          // Числовий Type ID повідомлення, до якого застосовуються одиниці
    char     units[16];     // Масив символьних кодів фізичних одиниць для кожного поля
    char     mults[16];     // Масив символьних кодів множників для кожного поля
};
```
```cpp
// C++20
#include <cstdint>
#include <array>

#pragma pack(push, 1)
struct DataFlash_FMTU_Payload {
    uint64_t time_us{0};
    uint8_t  type{0};
    std::array<char, 16> units{};
    std::array<char, 16> mults{};
};
#pragma pack(pop)
```
:::

Символьні коди одиниць вимірювання `units`:
* `'d'` — градуси (`deg`)
* `'r'` — радіани (`rad`)
* `'s'` — метри за секунду (`m/s`)
* `'m'` — метри відстані (`m`)
* `'h'` — метри висоти над рівнем моря (`m ASL`)
* `'G'` — напруженість магнітного поля в Гаусах (`Gauss`)
* `'A'` — сила електричного струму в Амперах (`A`)
* `'v'` — електрична напруга у Вольтах (`V`)
* `'a'` — лінійне прискорення (`m/s²`)
* `'z'` — кутова швидкість (`rad/s` або `deg/s`)
* `'%'` — відсоткові частки (`0..100%`)

Символьні коди масштабних множників `mults`:
* `'1'` — множник відсутній (`× 1.0`)
* `'2'` — множення на сто (`× 100.0`)
* `'3'` — множення на тисячу (`× 1000.0`)
* `'e'` — ділення на сто (`× 0.01`)
* `'d'` — ділення на десять (`× 0.1`)
* `'m'` — мілі-множник (`× 0.001`)
* `'u'` — мікро-множник (`× 0.000001`)

### 3.3. Стандартний каталог системних повідомлень DataFlash

#### Повідомлення просторової орієнтації `ATT` (Типовий Type `0x05`)
Специфікація `format`: `"Qcccc"`, довжина 19 байтів (разом із 3-байтним заголовком):
* `TimeUS` (`uint64_t`, 8 байтів): системний час у мікросекундах.
* `DesRoll` (`int16_t`, 2 байти): цільовий кут крену (`значення = int16 / 100.0` град).
* `Roll` (`int16_t`, 2 байти): фактичний кут крену (`значення = int16 / 100.0` град).
* `DesPitch` (`int16_t`, 2 байти): цільовий кут тангажу (`значення = int16 / 100.0` град).
* `Pitch` (`int16_t`, 2 байти): фактичний кут тангажу (`значення = int16 / 100.0` град).
* `DesYaw` (`uint16_t`, 2 байти): цільовий кут рискання (`значення = uint16 / 100.0` град).
* `Yaw` (`uint16_t`, 2 байти): фактичний кут рискання (`значення = uint16 / 100.0` град).

#### Повідомлення супутникової навігації `GPS` (Типовий Type `0x01`)
Специфікація `format`: `"QBIHBIIfffff"`, довжина 47 байтів (разом із заголовком):
* `TimeUS` (`uint64_t`): мікросекунди.
* `Status` (`uint8_t`): статус фіксації супутників (`0` = No GPS, `3` = 3D Fix, `4` = DGPS, `6` = RTK Fixed).
* `GMS` (`uint32_t`): мілісекунди GPS-тижня.
* `GWk` (`uint16_t`): номер GPS-тижня.
* `NSats` (`uint8_t`): кількість видимих навігаційних супутників.
* `HDop` (`float`): горизонтальний фактор зниження точності (Horizontal Dilution of Precision).
* `Lat` (`int32_t`): географічна широта, помножена на `1e7` (масштаб `L`).
* `Lng` (`int32_t`): географічна довгота, помножена на `1e7` (масштаб `L`).
* `Alt` (`float`): висота над еліпсоїдом у метрах.
* `Spd` (`float`): швидкість руху відносно землі в метрах за секунду.
* `GCrs` (`float`): курс руху над землею в градусах (`0..360°`).
* `VZ` (`float`): вертикальна швидкість підйому/спуску в м/с.

#### Повідомлення інерційних датчиків `IMU` (Типовий Type `0x02`)
Специфікація `format`: `"QffffffI"`, довжина 35 байтів:
* `TimeUS` (`uint64_t`): мікросекунди.
* `GyrX`, `GyrY`, `GyrZ` (`float`, `float`, `float`): кутові швидкості по трьох осях у рад/с.
* `AccX`, `AccY`, `AccZ` (`float`, `float`, `float`): лінійні прискорення по трьох осях у м/с².
* `ErrCount` (`uint32_t`): апаратний лічильник збоїв зв'язку SPI/I2C із чіпом акселерометра/гіроскопа.

#### Повідомлення барометричного висотоміра `BARO` (Типовий Type `0x04`)
Специфікація `format`: `"Qffcf"`, довжина 22 байти:
* `TimeUS` (`uint64_t`): системний час у мікросекундах.
* `Alt` (`float`): розрахована барометрична висота в метрах.
* `Press` (`float`): статичний атмосферний тиск у Паскалях.
* `Temp` (`int16_t`): температура датчика (`значення = int16 / 100.0` °C).
* `CRate` (`float`): швидкість вертикального набору висоти (Climb Rate) у м/с.

#### Повідомлення контролю акумулятора та живлення `BAT` (Типовий Type `0x10`)
Специфікація `format`: `"Qfffff"`, довжина 27 байтів:
* `TimeUS` (`uint64_t`): мікросекунди.
* `Volt` (`float`): загальна напруга силової батареї у Вольтах.
* `VoltR` (`float`): розрахункова напруга з урахуванням внутрішнього опору комірок.
* `Curr` (`float`): миттєвий струм споживання в Амперах.
* `CurrTot` (`float`): витрачена ємність батареї в міліампер-годинах (мА·год).
* `Temp` (`float`): температура акумуляторного блоку в °C.

#### Повідомлення контуру налаштування та стабілізації `CTUN` (Типовий Type `0x15`)
Специфікація `format`: `"Qfffffeeff"`, довжина 43 байти:
* `TimeUS` (`uint64_t`): мікросекунди.
* `DesAlt` (`float`): цільова висота автопілота в метрах.
* `Alt` (`float`): поточна висота за оцінкою EKF у метрах.
* `AngBst` (`float`): коефіцієнт компенсації тяги при нахилах апарата (Angle Boost).
* `CRt` (`float`): поточна вертикальна швидкість у м/с.
* `DesCRt` (`float`): цільова вертикальна швидкість у м/с.
* `ThrOut` (`int32_t`): вихідне значення газу регулятора (`значення = int32 / 100.0` %).
* `DesThr` (`int32_t`): цільовий рівень газу пілота (`значення = int32 / 100.0` %).
* `DAlt` (`float`): похибка утримання висоти в метрах.
* `DCRt` (`float`): похибка регулятора вертикальної швидкості в м/с.

#### Повідомлення вихідних каналів сервоприводів та моторів `RCOU` (Типовий Type `0x1D`)
Специфікація `format`: `"QHHHHHHHHHHHHHHHH"`, довжина 41 байт:
* `TimeUS` (`uint64_t`): системний час у мікросекундах.
* `C1..C16` (`uint16_t[16]`): тривалість керівних ШІМ-імпульсів (PWM) або команд протоколів DShot/CAN на виходах контролера (1000..2000 мкс).

#### Повідомлення вхідних сигналів апаратури радіокерування `RCIN` (Типовий Type `0x1C`)
Специфікація `format`: `"QHHHHHHHHHHHH"`, довжина 33 байти:
* `TimeUS` (`uint64_t`): системний час у мікросекундах.
* `C1..C12` (`uint16_t[12]`): сигнали каналів приймача радіокерування (Roll, Pitch, Throttle, Yaw, режими, тумблери аварійного перемикання).

#### Повідомлення системних параметрів `PARM` (Type `0x81` = 129)
Фіксує калібрувальні налаштування системи:

:::tabs
```c

    float    value;         // Значення параметра (IEEE 754 float32)
};
```
```cpp

#include <array>

    float    value{0.0f};

#pragma pack(pop)
```

## 4. Алгоритми відновлення потоку та обробка крайових випадків

Розробка надійних бінарних декодерів для бортових логів вимагає обробки аварійних станів файлової системи, що виникають при раптовому вимкненні живлення в польоті або деградації флеш-носія.

### 4.1. Обробка аварійного відсікання файлу (Incomplete EOF)
Оскільки запис на SD-карту здійснюється блоками по 512 байтів (або секторами по 4096 байтів), раптове знеструмлення польотного контролера при зіткненні майже завжди призводить до появи «обірваного» пакета в кінці файлу:
* **У форматі ULog:** якщо розмір залишкового хвоста файлу менший за 3 байти або менший за `msg_size + 3`, парсер зобов'язаний відкинути незавершений блок без генерації фатальної помилки, завершивши формування часових рядів на останньому валідному пакеті.
* **У форматі DataFlash:** якщо після маркера `0xA3 0x95` та байта `type_id` довжина доступних даних менша за `FMT.Length - 3`, залишок байтів ігнорується.

### 4.2. Алгоритм відновлення синхронізації DataFlash при випаданні байтів
Якщо в потоці DataFlash зустрічається пошкоджений блок (наприклад, через збій блоку флеш-пам'яті), декодер переходить у режим побайтового ковзання:
1. Поточний покажчик зсувається вперед на 1 байт.
2. Виконується перевірка умови `buffer[i] == 0xA3 && buffer[i+1] == 0x95`.
3. Зчитується кандидат на `Type ID = buffer[i+2]`.
4. Якщо для цього `Type ID` зареєстровано дійсне повідомлення у таблиці `FMT`, а наступні байти за зміщенням `i + FMT.Length` знову утворюють маркер `0xA3 0x95`, синхронізацію вважається успішно відновленою.
