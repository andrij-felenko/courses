# 🧮 Математична модель пріоритетів кандидатів і пар у фреймворку ICE

Фреймворк ICE (RFC 8445) установлює строгий детермінований порядок тестування маршрутів між двома вузлами мережі. Для мінімізації часу встановлення сесії найшвидші та найменш затратні канали (пряме з'єднання Host-to-Host) повинні перевірятися першими, а повільні й фінансово затратні (TURN Relay) — останніми.

Для цього стандарт визначає строгі алгебраїчні формули обчислення 32-бітного пріоритету окремого кандидата, 64-бітного пріоритету пари кандидатів, оцінки ймовірностей підбору портів у разі асиметричної трансляції, а також математичні обмеження на темпування перевірок та оптимізацію очікуваного часу з'єднання.

---

### 1. Формула пріоритету локального кандидата (32 біти)

Згідно зі специфікацією RFC 8445 (розділ 5.1.2), числовий пріоритет кандидата розраховується за формулою лінійної зваженої комбінації трьох параметрів:

```
Priority
= (2²⁴) · Type_Pref + (2⁸) · Local_Pref + (2⁰) · (256 - Component_ID)
```

де:
* **`Type_Pref`** (8 бітів, діапазон `0..126`): тип транспортного кандидата. Стандартні рекомендовані константи:
  * `Host` (локальний фізичний адаптер): `126` (`0x7E`);
  * `Peer Reflexive (prflx)` (виявлений під час перевірок): `110` (`0x6E`);
  * `Server Reflexive (srflx)` (отриманий через STUN): `100` (`0x64`);
  * `Relayed (relay)` (виділений на TURN): `0` (`0x00`).
* **`Local_Pref`** (16 бітів, діапазон `0..65535`): коефіцієнт локальної переваги мережевого інтерфейсу. Використовується для градації фізичних підключень (наприклад, перевага прямого оптоволоконного Ethernet над бездротовим Wi-Fi або Wi-Fi над стільниковим модемом 4G/5G). Якщо вузол має лише один мережевий адаптер, значення встановлюється в максимальне: `65535` (`0xFFFF`).
* **`Component_ID`** (8 бітів, діапазон `1..256`): числовий ідентифікатор медіапотоку (`1` для медіапотоку RTP, `2` для контрольного потоку RTCP). Вираз `256 - Component_ID` гарантує, що основний потік даних завжди має вищий числовий ранг, ніж допоміжний.

#### Бітове пакування 32-бітного слова

Множники `2²⁴`, `2⁸` та `2⁰` відповідають зміщенням бітових полів у 32-бітному цілому числі без знаку:

```
 31            24 23                            8 7             0
+----------------+-------------------------------+---------------+
| Type_Pref (8)  |        Local_Pref (16)        | 256-CompID(8) |
+----------------+-------------------------------+---------------+
```

Завдяки неперетинним бітовим маскам побітове порівняння двох 32-бітних чисел строго еквівалентне лексикографічному порівнянню кортежу:

```
(Type_Pref, Local_Pref, 256 - Component_ID)
```

Це доводить, що тип кандидата (`Type_Pref`) має абсолютну перевагу над локальними налаштуваннями інтерфейсу (`Local_Pref`), а локальні налаштування інтерфейсу — над ідентифікатором медіакомпонента. Наприклад, навіть найбільш пріоритетний інтерфейс Ethernet із релеєм TURN (`Type_Pref = 0`) матиме сумарний пріоритет значно нижчий, ніж повільний стільниковий зв'язок 4G із прямим кандидатом Host (`Type_Pref = 126`).

### 2. Формула пріоритету пари кандидатів (64 біти)

Після обміну SDP-офертами кожен ICE-агент формує повний декартовий добуток локальних і віддалених адрес. Нехай `G` — 32-бітний пріоритет кандидата, наданого **керівним агентом (Controlling Agent)**, а `D` — 32-бітний пріоритет кандидата, наданого **керованим агентом (Controlled Agent)**.

Згідно з RFC 8445 (розділ 6.1.2.3), 64-бітний пріоритет пари обчислюється за формулою:

```
Pair_Priority
= 2³² · min(G, D) + 2 · max(G, D) + (G > D ? 1 : 0)
```

#### Бітова розмітка 64-бітного значення

```
 63                            32 31                            1 0
+--------------------------------+-------------------------------+---+
|          min(G, D)             |          max(G, D)            | T |
|          (32 біти)             |          (31 біт)             |   |
+--------------------------------+-------------------------------+---+
```

де `T = (G > D ? 1 : 0)` — молодший біт вирішення симетрії.

### 3. Математичні теореми та властивості формули пар

#### Теорема 1 (Принцип «найслабшої ланки»)
*Твердження*: Пріоритет пари кандидатів асимптотично визначається гіршим із двох кандидатів у парі.

*Доведення*: Значення `min(G, D)` займає старші 32 біти 64-бітного числа (помножене на `2³²`). Нехай маємо дві пари:
* Пару 1 із кандидатами `(Host, Relay)`, де `G = 2.13 · 10⁹`, `D = 1.67 · 10⁷` (`min = 1.67 · 10⁷`).
* Пару 2 із кандидатами `(Srflx, Srflx)`, де `G = 1.69 · 10⁹`, `D = 1.69 · 10⁹` (`min = 1.69 · 10⁹`).

Оскільки `1.69 · 10⁹ > 1.67 · 10⁷`, старші 32 біти Пари 2 перевищують старші 32 біти Пари 1 на два порядки. Отже, `Pair_Priority(Пара 2) > Pair_Priority(Пара 1)`. Прямий рефлексивний зв'язок завжди тестується раніше, ніж з'єднання, у якому хоча б один учасник використовує ретранслятор TURN.

#### Теорема 2 (Комутативна узгодженість контрольного списку)
*Твердження*: Обидва агенти (Controlling і Controlled) генерують ідентично впорядковані контрольні списки перевірок зв'язності (Checklists).

*Доведення*: Функції `min(G, D)` та `max(G, D)` є симетричними відносно множини аргументів `{G, D}`. Оскільки позначення `G` завжди закріплене за кандидатом керівного агента, а `D` — за кандидатом керованого агента, обидві сторони підставляють у формулу однакові числові значення в однакових ролях. Отже, обчислені 64-бітні числа збігаються біт-у-біт, і списки перевірок сортуються в ідентичному порядку без додаткових раундів узгодження через мережу.

#### Теорема 3 (Бієктивність та відсутність колізій)
*Твердження*: Для будь-яких двох різних пар кандидатів `(G₁, D₁)` та `(G₂, D₂)` значення `Pair_Priority` є строго різними.

*Доведення*:
1. Якщо `min(G₁, D₁) ≠ min(G₂, D₂)`, старші 32 біти чисел не збігаються, тому значення різні.
2. Якщо `min(G₁, D₁) = min(G₂, D₂) = m`, але `max(G₁, D₁) ≠ max(G₂, D₂) = M₁ ≠ M₂`, різниця середніх бітів становить:
   ```
   Δ = |(2 · M₁ + T₁) - (2 · M₂ + T₂)|
     ≥ 2 · |M₁ - M₂| - |T₁ - T₂|
     ≥ 2 · 1 - 1
     ≥ 1
   ```
   Значення не можуть бути рівними.
3. Якщо і `min`, і `max` збігаються, множини кандидатів ідентичні: `{G₁, D₁} = {G₂, D₂}`. Якщо самі пари не рівні (`G₁ = D₂` та `D₁ = G₂`, де `G₁ ≠ D₁`), то для однієї пари `G₁ > D₁` (отже, `T₁ = 1`), а для іншої `G₂ < D₂` (отже, `T₂ = 0`). Їхні значення відрізняються рівно на `1`. Рівність результатів можлива лише за повної тотожності вхідних пріоритетів `G₁ = G₂` та `D₁ = D₂`.

### 4. Розрахунковий приклад: пріоритети для типової WebRTC-сесії

Розглянемо встановлення аудіозв'язку RTP (`Component_ID = 1`, `256 - Component_ID = 255`) між клієнтом A (Controlling) та клієнтом B (Controlled). Обидва клієнти мають один інтерфейс (`Local_Pref = 65535 = 0xFFFF`).

#### Розрахунок пріоритетів кандидатів

1. **Кандидат Host (`Type_Pref = 126`)**:
```
Priority_Host
= 126 · 2²⁴ + 65535 · 2⁸ + (256 - 1)    [формула пріоритету кандидата]
= 126 · 16777216 + 65535 · 256 + 255   [обчислення степенів двійки]
= 2113929216 + 16776960 + 255           [покомпонентне множення]
= 2130706431                            [шістнадцяткове: 0x7EFFFF]
```

2. **Кандидат Server Reflexive (`Type_Pref = 100`)**:
```
Priority_Srflx
= 100 · 2²⁴ + 65535 · 2⁸ + 255          [формула пріоритету кандидата]
= 100 · 16777216 + 16776960 + 255       [обчислення степенів двійки]
= 1677721600 + 16776960 + 255           [покомпонентне множення]
= 1694501815                            [шістнадцяткове: 0x64FFFF]
```

3. **Кандидат Relayed (`Type_Pref = 0`)**:
```
Priority_Relay
= 0 · 2²⁴ + 65535 · 2⁸ + 255            [формула пріоритету кандидата]
= 0 + 16776960 + 255                    [обчислення компонентів]
= 16777215                              [шістнадцяткове: 0x00FFFF]
```

#### Розрахунок пріоритетів пар кандидатів

* **Пара 1: `Host A ⇄ Host B`**:
  * `G = 2130706431`, `D = 2130706431`
  * `min = 2130706431`, `max = 2130706431`, `G > D = 0`
  ```
  Pair_Priority
  = 2³² · 2130706431 + 2 · 2130706431 + 0 [підстановка у формулу]
  = 9151043085521747966                    [десяткове 64-бітне значення]
  ```

* **Пара 2: `Host A ⇄ Srflx B`**:
  * `G = 2130706431`, `D = 1694501815`
  * `min = 1694501815`, `max = 2130706431`, `G > D = 1`
  ```
  Pair_Priority
  = 2³² · 1694501815 + 2 · 2130706431 + 1 [підстановка у формулу]
  = 7277864380183183359                    [десяткове 64-бітне значення]
  ```

* **Пара 3: `Relay A ⇄ Relay B`**:
  * `G = 16777215`, `D = 16777215`
  * `min = 16777215`, `max = 16777215`, `G > D = 0`
  ```
  Pair_Priority
  = 2³² · 16777215 + 2 · 16777215 + 0     [підстановка у формулу]
  = 72057598332895230                      [десяткове 64-бітне значення]
  ```

### 5. Ймовірнісна модель симетричного NAT та парадокс днів народження

Коли один із клієнтів перебуває за симетричним транслятором (Symmetric NAT), що виділяє випадковий порт для кожного нового адресата, виникає математична задача оцінки ймовірності випадкового пробивання порту (Port Guessing).

Нехай транслятор виділяє порт випадково й рівномірно з діапазону розміром `M` портів (наприклад, динамічний діапазон `1024..65535`, де `M = 64512`). Клієнт-ініціатор надсилає `N` пробних пакетів на випадково обрані порти.

Ймовірність `P` того, що хоча б один із `N` надісланих пакетів влучить у порт, виділений симетричним транслятором, описується класичною формулою парадоксу днів народження:

```
P(hit)
= 1 - ∏ (1 - k / M)                     [добуток за k від 0 до N-1]
≈ 1 - e^(-N² / (2 · M))                 [експоненційне наближення Тейлора]
```

Для досягнення ймовірності успішного з'єднання `P = 0.5` (50% шанс) необхідна кількість пакетів `N` розраховується з рівняння:

```
1 - e^(-N² / (2 · M)) = 0.5
e^(-N² / (2 · M))     = 0.5             [перенесення константи]
-N² / (2 · M)         = ln(0.5)         [логарифмування обох частин]
N²                    = 2 · M · ln(2)   [множення на -2M]
N                     = √(2 · M · ln(2)) [вилучення квадратного кореня]
```

Підставивши розмір пулу `M = 64512`:
```
N
= √(2 · 64512 · 0.69315)                [обчислення підкореневого виразу]
= √(89422)                              [результат множення]
≈ 299                                   [пакетів для 50% успіху]
```

Для досягнення надійності `P = 0.99` (99% успіху):
```
N_99
= √(2 · 64512 · ln(100))                [формула для 99% надійності]
= √(2 · 64512 · 4.60517)                [обчислення логарифма]
= √(594168)                             [результат множення]
≈ 771                                   [пакетів для 99% успіху]
```

#### Висновок щодо застосовності підбору портів
Хоча теоретично надіслати 800 UDP-пакетів за 100 мілісекунд технічно можливо, на практиці міжмережеві екрани розцінюють такий сплеск як сканування портів (Port Scan) і блокують IP-адресу клієнта. Саме тому стандарт WebRTC та IETF повністю відмовилися від сліпого підбору портів симетричного NAT, закріпивши обов'язкове використання протоколу ретрансляції TURN.

### 6. Часова складність та збіжність перевірок зв'язності ICE

Нехай агент A має `k` кандидатів, а агент B має `m` кандидатів. Загальна кількість сформованих пар у контрольному списку дорівнює `N_pairs = k · m`.

Щоб не перевантажувати канал зв'язку масивним сплеском трафіку (STUN Storm), стандарт RFC 8445 вводить таймер темпування (Pacing Timer) `Ta` (за замовчуванням `Ta = 20` мс або `50` мс для бездротових мереж).

Теоретичний максимальний час збіжності повного контрольного списку `T_max` до знаходження робочої пари обчислюється як:

```
T_convergence = (N_pairs - 1) · Ta + RTT
```

де `RTT` — час кругового обігу пакетів між вузлами.

| Топологія кандидатів | Кількість пар (`N_pairs`) | Час старту останньої перевірки (`Ta = 20` мс) | Оцінка затримки (`RTT = 50` мс) |
| :---: | :---: | :---: | :---: |
| 1x1 (Host ⇄ Host) | 1 | 0 мс | 50 мс |
| 2x2 (Host, Srflx) | 4 | 60 мс | 110 мс |
| 4x4 (Host, 2 Srflx, Relay) | 16 | 300 мс | 350 мс |
| 6x6 (Dual-Stack IPv4/IPv6 + VPN) | 36 | 700 мс | 750 мс |

### 7. Математичні обмеження на смугу пропускання під час темпування перевірок

Під час активної фази перевірок зв'язності (Connectivity Checks) клієнт генерує потік пакетів STUN Binding Request. Середній розмір такого пакета з атрибутами автентифікації та контрольної суми становить `S ≈ 100` байтів (800 бітів).

Швидкість споживання смуги пропускання на вихідному каналі (Uplink) під час опитування визначається як:

```
R_STUN = (S · 8) / Ta
```

де `Ta` — інтервал темпування між послідовними запитами.

* При `Ta = 20` мс (`0.02` с):
  ```
  R_STUN = 800 / 0.02 = 40000 біт/с = 40 кбіт/с
  ```
* При `Ta = 5` мс (`0.005` с):
  ```
  R_STUN = 800 / 0.005 = 160000 біт/с = 160 кбіт/с
  ```

Для мобільних або супутникових каналів із низькою вихідною пропускною здатністю `C_up` (наприклад, канал телеметрії дрона зі швидкістю `C_up = 256` кбіт/с) неконтрольований потік STUN-перевірок на швидкості 160 кбіт/с спожив би понад 60% пропускної здатності, спричинивши втрату пакетів відеопотоку або затримку команд керування.

З цієї причини стандарт RFC 8445 накладає фундаментальне математичне обмеження: трафік перевірок зв'язності STUN не повинен перевищувати **5% від загальної вихідної пропускної здатності каналу**:

```
R_STUN ≤ 0.05 · C_up
```

Звідси мінімальний допустимий інтервал темпування `Ta_min` обчислюється як:

```
Ta_min = (S · 8) / (0.05 · C_up) = (800) / (0.05 · C_up) = 16000 / C_up
```

Якщо швидкість вихідного каналу `C_up = 256000` біт/с (256 кбіт/с), мінімальний інтервал між STUN-перевірками становить:

```
Ta_min = 16000 / 256000 = 0.0625 с = 62.5 мс
```

Адаптивне регулювання таймера темпування `Ta` гарантує, що конвеєр ICE не деградує якість паралельного медіапотоку та не створює буферного колапсу (Bufferbloat) на вузьких радіолініях зв'язку.

### 8. Оптимізація контрольного списку: факторизація через Foundation

У складних багатоінтерфейсних мережах (наприклад, одночасне підключення через Wi-Fi, Ethernet, 4G-модем та два VPN-тунелі) кількість кандидатів на кожному вузлі може досягати `k = 8..12`, породжуючи понад 100 пар у контрольному списку. Тестування такої кількості пар за таймером `Ta = 20` мс зайняло б понад 2 секунди.

Для радикального скорочення кількості надлишкових перевірок стандарт RFC 8445 вводить концепцію **Foundation (базису кандидата)**.

Foundation — це текстовий ідентифікатор (хеш), що присвоюється кандидату залежно від:
1. Типу кандидата (`Host`, `Srflx`, `Relay`, `Prflx`).
2. Базової IP-адреси локального мережевого адаптера (Base IP).
3. Протоколу транспорту (UDP або TCP).
4. IP-адреси STUN/TURN сервера (для рефлексивних та релейних кандидатів).

#### Математичне відношення еквівалентності

Кандидати, що мають однаковий Foundation, вважаються топологічно еквівалентними відносно маршрутизації в глобальній мережі.

Нехай множина пар кандидатів розбивається на класи еквівалентності за парою базисів:

```
(Foundation_Local, Foundation_Remote)
```

Правило динамічного блокування (Freezing Rule) в ICE стверджує:
* Для кожного унікального класу `(Foundation_Local, Foundation_Remote)` у стан `Waiting` переводиться **рівно одна пара з найвищим пріоритетом**.
* Усі інші пари цього класу переводяться у стан `Frozen` (Заблоковано).
* Якщо перша перевірена пара класу успішно відповідає (`Succeeded`), усі заблоковані пари цього класу розморожуються і можуть бути використані за потреби, проте повторні дорогі перевірки не виконуються.

Це знижує практичну кількість активних перевірок зв'язку з `O(k · m)` до `O(f_A · f_B)`, де `f_A` та `f_B` — кількість реальних фізичних інтерфейсів (зазвичай не більше 2–3), скорочуючи фазу встановлення WebRTC-з'єднання до 50–120 мілісекунд.

### 9. Статистична модель очікуваного часу з'єднання при випадкових затримках RTT

У реальних IP-мережах час кругового обігу пакетів (RTT) є випадковою величиною, що задовільно апроксимується логнормальним розподілом:

```
ln(RTT) ~ N(μ, σ²)
```

Нехай маємо впорядкований список із `K` пар кандидатів, для яких імовірності успішного встановлення зв'язку дорівнюють `p₁, p₂, ..., p_K`.

Очікуваний час встановлення з'єднання `E[T_conn]` при жадібному послідовному опитуванні з інтервалом темпування `Ta` обчислюється як математичне сподівання:

```
E[T_conn] = ∑ P(Пара i є першою успішною) · E[T_i]
```

де час успіху для пари з номером `i` становить:

```
T_i = (i - 1) · Ta + RTT_i
```

Ймовірність того, що саме `i`-та пара стане першою успішною (за умови незалежності перевірок):

```
P(успіх_i) = p_i · ∏ (1 - p_j)           [добуток за j від 1 до i-1]
```

#### Доведення оптимальності спадного впорядкування за пріоритетом

Нехай маємо дві незалежні пари кандидатів X та Y із ймовірностями успіху `p_X > p_Y` та однаковим математичним сподіванням затримки `E[RTT]`.

1. **Якщо спочатку тестувати X, а потім Y**:
   ```
   E[T_XY]
   = p_X · E[RTT] + (1 - p_X) · p_Y · (Ta + E[RTT])
   = (p_X + p_Y - p_X · p_Y) · E[RTT] + (1 - p_X) · p_Y · Ta
   ```
2. **Якщо спочатку тестувати Y, а потім X**:
   ```
   E[T_YX]
   = p_Y · E[RTT] + (1 - p_Y) · p_X · (Ta + E[RTT])
   = (p_Y + p_X - p_Y · p_X) · E[RTT] + (1 - p_Y) · p_X · Ta
   ```

Різниця математичних сподівань становить:

```
E[T_YX] - E[T_XY]
= (1 - p_Y) · p_X · Ta - (1 - p_X) · p_Y · Ta [віднімання виразів]
= (p_X - p_X · p_Y - p_Y + p_X · p_Y) · Ta   [розкриття дужок]
= (p_X - p_Y) · Ta                           [скорочення добутків]
> 0                                          [оскільки p_X > p_Y та Ta > 0]
```

*Висновок*: Оскільки `E[T_YX] > E[T_XY]`, тестування більш імовірної та швидкої пари (Host або Srflx) **суворо мінімізує середній час встановлення з'єднання**. Формула обчислення пріоритетів ICE, що призначає найвищі коефіцієнти кандидатам Host (`126`) та Srflx (`100`), є математично строгою реалізацією оптимального розкладу обслуговування черги за критерієм мінімізації середнього часу затримки сесії.

### 10. Модель Happy Eyeballs для Dual-Stack IPv4 / IPv6 (RFC 8421)

У сучасних гетерогенних мережах вузли часто підтримують одночасно протоколи IPv4 та IPv6 (Dual-Stack). Згідно з рекомендаціями IETF, стек ICE повинен віддавати перевагу новішому протоколу IPv6, проте за наявності проблем із маршрутизацією IPv6 (наприклад, тунелі 6to4 з великими втратами) клієнт не повинен чекати повного тайм-ауту.

Стандарт **RFC 8421 (*Happy Eyeballs for ICE*)** формулює це правило у вигляді часового зсуву (Pacing Delay) `T_delay`:
* Якщо в контрольному списку верхню позицію займає пара IPv6, перевірка для неї запускається негайно (`t = 0`).
* Наступна за пріоритетом пара IPv4 **штучно затримується на інтервал `T_delay = 25..50` мс**, даючи перевагу IPv6.
* Якщо відповідь від пари IPv6 надходить протягом `T_delay`, пара IPv4 взагалі не тестується.
* Якщо за `T_delay` відповіді немає, агент паралельно вистрілює перевірку IPv4.

Нехай `RTT_6` та `RTT_4` — випадкові величини затримок IPv6 та IPv4. Ймовірність того, що зв'язок буде встановлено через IPv6, виражається формулою:

```
P(IPv6_обрано) = P(RTT_6 < RTT_4 + T_delay)
```

Завдяки зсуву `T_delay = 25` мс протокол IPv6 успішно обирається у понад 90% сесій, де маршрутизація IPv6 працює стабільно, а у разі повної деградації IPv6 перемикання на робочий IPv4 відбувається з мінімальною додатковою затримкою лише у 25 мілісекунд.
