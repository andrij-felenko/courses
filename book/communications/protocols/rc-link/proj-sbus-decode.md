# ⚙️ Кадр SBUS у коді: розпаковка 16 каналів по 11 бітів

Приймач віддає канали по [SBUS](book:communications/rc-link), а той — інвертований UART на 100 000 бод із кадром у 25 байтів. Прийняти ці 25 байтів — півсправи; усередині них 16 каналів **запаковано по 11 бітів**, і вони **не вирівняні на байт**. Розпакувати їх правильно — типова, але підступна задача прошивки: помилишся на біт чи на порядок — і всі канали «попливуть».

**Задача звучить буденно**, та з'являється в кожному польотному контролері: приймач щонайменше раз на 14 мс кидає в порт свіжий кадр, прошивка має витягти з нього 16 чисел і віддати їх у цикл стабілізації. Зробити це треба швидко, без купи окремих масок на канал і так, щоб жодна наводка чи зсув у потоці не перетворили газ на крен. Чому 11 бітів, а не зручні 8 чи 16? Бо канал має давати помітно більше за 256 рівнів (256 кроків на повний хід стіка — це грубо), а 16 бітів на кожен — марнотратство в кадрі, що летить десятки разів на секунду; 11 бітів (2048 рівнів) — компроміс між роздільністю й розміром. Платимо за нього тим, що канали не лягають на байти, і саме це робить розпаковку нетривіальною. Розберімо задачу від будови кадру до робочого коду, його місця в прошивці й граблів.

## Будова кадру

Кадр завжди 25 байтів і має жорстку рамку:

```
байт 0      — старт, завжди 0x0F
байти 1..22 — 22 байти даних каналів: 16 каналів × 11 бітів = 176 бітів
байт 23     — прапорці: [ - - - - failsafe frame_lost ch18 ch17 ]
байт 24     — кінець, завжди 0x00
```

22 байти — це рівно 176 бітів, а 16 × 11 = 176: канали лягають **впритул**, без проміжків. Два службові канали (ch17, ch18) — однобітні, лежать у байті прапорців. Там само два прапорці, які не можна ігнорувати: `frame_lost` (кадр прийнято з помилкою, значенням не можна вірити цей раз) і `failsafe` (передавач пропав, приймач уже у failsafe — це **не** валідні канали, а сигнал «рятуйся»).

Ключова тонкість — **порядок бітів**. SBUS пакує канали від молодшого біта (англ. *least significant bit first*). Перший канал займає всі 8 бітів байта 1 і ще 3 молодші біти байта 2; другий канал продовжує зі старших бітів байта 2 — і так далі. Тобто біти течуть суцільним потоком молодшими вперед, а межі каналів ріжуть цей потік кожні 11 бітів незалежно від меж байтів.

## Ідея: рухоме бітове вікно

Перша спокуса — розпакувати кожен канал власною формулою з масок і зсувів: `ch1 = b1 | ((b2 & 0x07) << 8)`, `ch2 = (b2 >> 3) | ((b3 & 0x3F) << 5)` і так шістнадцять разів. Це працює, але кожен рядок свій, зсуви різні, і досить переплутати один — як канал тихо зіпсується. Шукати таку помилку потім дуже неприємно.

Краще побачити дані такими, якими вони є: **суцільним потоком бітів**, що тече молодшими вперед, а канали — просто вікна по 11 бітів уздовж нього. Тоді й код стає одним циклом замість шістнадцяти формул. Прийом зветься **бітовий акумулятор**: тримаємо широку змінну-накопичувач і лічильник «скільки бітів у ній зараз». Ідемо по байтах даних і досипаємо кожен у накопичувач **зверху** (зсувом на поточну кількість бітів); щойно там назбиралося 11 — знімаємо молодші 11 як готовий канал і викидаємо їх зсувом. Накопичувач завжди тримає лише «хвіст», що ще не склався в канал. Один цикл, жодних поканальних формул, і порядок «молодшими вперед» лягає сам собою — бо саме так біти й досипаються, і так само знімаються.

## Робочий код

:::tabs
```cpp
#include <stdint.h>

struct SbusData {
    uint16_t ch[16];   // 16 каналів, сирі значення 192..1792
    bool failsafe;     // приймач у failsafe — каналам не вірити
    bool frame_lost;   // цей кадр прийнято з помилкою
};

// Розпарсити 25-байтовий кадр SBUS. Повертає false, якщо рамка кадру не та.
bool sbus_parse(const uint8_t frame[25], SbusData* out) {
    if (frame[0] != 0x0F || frame[24] != 0x00)
        return false;                       // не наш кадр / зсув по байтах

    uint32_t bits = 0;                      // акумулятор бітів
    int nbits = 0;                          // скільки бітів у ньому зараз
    int ch = 0;                             // який канал заповнюємо

    for (int i = 1; i <= 22 && ch < 16; i++) {
        bits |= (uint32_t)frame[i] << nbits;   // досипати байт молодшими вперед
        nbits += 8;
        while (nbits >= 11 && ch < 16) {       // назбиралося на канал?
            out->ch[ch++] = bits & 0x07FF;     // зняти молодші 11 бітів
            bits >>= 11;
            nbits -= 11;
        }
    }

    out->frame_lost = frame[23] & 0x04;     // біт 2 байта прапорців
    out->failsafe   = frame[23] & 0x08;     // біт 3
    return true;
}
```
```python
from dataclasses import dataclass, field


@dataclass
class SbusData:
    ch: list[int] = field(default_factory=lambda: [0] * 16)  # 16 каналів, сирі значення 192..1792
    failsafe: bool = False   # приймач у failsafe — каналам не вірити
    frame_lost: bool = False  # цей кадр прийнято з помилкою


# Розпарсити 25-байтовий кадр SBUS. Повертає None, якщо рамка кадру не та.
def sbus_parse(frame: bytes) -> SbusData | None:
    if frame[0] != 0x0F or frame[24] != 0x00:
        return None                          # не наш кадр / зсув по байтах

    out = SbusData()
    bits = 0                                 # акумулятор бітів
    nbits = 0                                # скільки бітів у ньому зараз
    ch = 0                                   # який канал заповнюємо

    for i in range(1, 23):                   # байти даних 1..22
        if ch >= 16:
            break
        bits |= frame[i] << nbits            # досипати байт молодшими вперед
        nbits += 8
        while nbits >= 11 and ch < 16:       # назбиралося на канал?
            out.ch[ch] = bits & 0x07FF       # зняти молодші 11 бітів
            ch += 1
            bits >>= 11
            nbits -= 11

    out.frame_lost = bool(frame[23] & 0x04)  # біт 2 байта прапорців
    out.failsafe   = bool(frame[23] & 0x08)  # біт 3
    return out
```
:::

Чому акумулятор саме `uint32_t`. У найгіршу мить у ньому до 10 «хвостових» бітів від попереднього кроку плюс свіжі 8 — це 18 бітів, що вільно влазить у 32. Брати `uint16_t` не можна: `frame[i] << nbits` при `nbits = 8` і більше зрушить біти за межу 16-бітного типу, і вони пропадуть.

## Worked-приклад

Перевіримо на нейтралі. Хай байт 1 = `0xE0`, байт 2 = `0x03`, решта даних нулі — це означає, що перший канал стоїть посередині.

```text
крок i=1: bits = 0x0000_00E0,  nbits = 8   → 8 < 11, каналу ще нема
крок i=2: bits |= 0x03 << 8 = 0x0000_03E0,  nbits = 16
          16 ≥ 11 → ch[0] = 0x03E0 & 0x7FF = 0x3E0 = 992
          bits >>= 11 → 0,  nbits = 5
```

Канал 0 вийшов **992** — рівно середина діапазону SBUS (192…1792), тобто відпущений стік. Перетворення 992 у звичні 1500 мкс — уже робота прошивки поверх цього парсера (лінійне відображення 192→1000, 1792→2000).

## Де парсер живе у прошивці

Сам `sbus_parse` — чиста функція без побічних ефектів: дай 25 байтів, забери канали. Та щоб ці 25 байтів зібрати, навколо неї треба ще трохи механіки, і саме вона на практиці частіше підводить, ніж розпаковка бітів.

Байти приходять по UART по одному, з частотою кадру близько 14 мс (а в швидкому режимі — 7 мс). Чекати їх у головному циклі не можна: він зайнятий стабілізацією й не сміє блокуватися. Тому кадр зазвичай збирають **у перериванні приймання** або через **DMA** у кільцевий буфер, а вже головний цикл бере зібрані 25 байтів і викликає парсер. Межу кадру шукають за тим самим стартовим `0x0F` плюс паузою в потоці перед ним: SBUS лишає між кадрами тишу в кілька мілісекунд, і саме вона надійно відділяє один кадр від іншого, коли байти течуть без явних роздільників.

Звідси випливає ще одне правило, про яке легко забути: **стеж за свіжістю каналів**. Якщо новий кадр не прийшов за розумний час (скажімо, кілька періодів поспіль), це той самий обрив зв'язку — і реагувати на нього має прошивка, навіть якщо приймач сам ще шле старі значення. Тримати лічильник «коли востаннє був валідний кадр» і вмикати свій failsafe за його простроченням — частина тієї самої задачі, а не окрема розкіш.

Окрема пастка — **ресинхронізація** після збою. UART не має поняття «межа кадру»: він просто віддає байти. Загубив приймач один байт або ти ввімкнув порт посеред кадру — і байти посунулися, а парсер, що сліпо бере 25 підряд, читатиме сміття **постійно**, бо стартом наступного кадру він вважатиме випадковий байт. Рятує саме пара «початок `0x0F` + кінець `0x00`» разом із паузою між кадрами: побачив не-`0x0F` там, де чекав старт, — відкидай байт і чекай тиші, тоді лови `0x0F` наново. Без цього один збій ламає лінк назавжди, а не на один кадр.

## Сусід CRSF: та сама ідея, інша рамка

Той самий код-кістяк лягає й на [CRSF](book:communications/rc-link), лише з двома відмінностями, і їх корисно бачити поруч. По-перше, CRSF — **не інвертований** UART і на 420 000 бод, тож шар нижче інший. По-друге, його кадр **не фіксованої довжини**: після стартового байта йде поле «довжина», а наприкінці — контрольна сума CRC. Тому ловити межу кадру там простіше (довжину прочитав — знаєш, де кінець), зате з'являється обов'язок **перевірити CRC** й відкинути кадр, що не зійшовся. Канали в пакеті каналів CRSF теж по 11 бітів і теж пакуються молодшими вперед — отже, наш бітовий акумулятор працює без змін, міняється лише обгортка навколо нього.

## Граблі

Помилки тут типові й тихі — код «майже працює», а канали поводяться дивно:

- **Порядок бітів навпаки.** Якщо досипати байти старшими вперед або знімати зі старшого боку — канали будуть змішані й стрибатимуть від чужих бітів. SBUS — строго молодшими вперед.
- **Вузький акумулятор.** `uint16_t bits` мовчки губить біти на зсуві ≥ 8 — частина каналів поповзе. Тримай 32 біти.
- **Інверсія на залізі.** UART має бути **інвертований**; на звичайному порту без апаратної інверсії (або без зовнішнього інвертора-транзистора) ти або взагалі не зловиш `0x0F`, або зловиш сміття. Це не вина парсера — це шар нижче.
- **8E2, а не 8N1.** SBUS — 8 бітів даних, **парність even, 2 стоп-біти**. Налаштуєш порт як звичайний 8N1 — кадри читатимуться з помилками парності.
- **Ігнорувати прапорці.** Кадр із піднятим `failsafe` несе не команди пілота, а сигнал «передавача нема»; узяти ці значення за справжні канали — пряма дорога до аварії. Завжди перевіряй `failsafe` й `frame_lost`, перш ніж вірити каналам.
- **Не ловити рамку.** Перевірка `frame[0]==0x0F && frame[24]==0x00` рятує від зсуву на байт у потоці: без неї один загублений байт зсуває всі канали, і вони лишаються «кривими» назавжди.
