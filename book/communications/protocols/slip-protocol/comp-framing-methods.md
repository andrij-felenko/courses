# 🔌 Порівняння методів кадрування: SLIP, COBS, HDLC/PPP та довжинний префікс

Передавання структурованих повідомлень, телеметрії або мережевих пакетів через послідовні канали зв'язку (UART, RS-485, радіомодеми, точкові шини) вимагає надійного виділення меж окремих блоків даних у безперервному потоці байтів. Якщо фізичний рівень передає байти без апаратної прив'язки до кадрів, приймач повинен мати однозначний математичний або синтаксичний критерій: де пакет починається, де закінчується і чи не порушено цілісність переданої інформації.

В інженерній практиці сформувалися чотири класичні парадигми кадрування. Кожна з них висуває власні вимоги до обчислювальних ресурсів процесора, пропускної здатності каналу, обсягу буферної пам'яті (RAM) та стійкості до апаратних завад у лінії.

```
+-------------------+-------------------+-------------------+-------------------+-------------------+
| Параметр          | SLIP (RFC 1055)   | COBS              | HDLC / PPP        | Довжинний префікс |
+-------------------+-------------------+-------------------+-------------------+-------------------+
| Роздільник меж    | END (0xC0)        | Нульовий (0x00)   | Прапорець (0x7E)  | Сталий SYNC-байт  |
| Метод усунення    | Байт-стаффінг     | Зсувні покажчики  | Байт- або біт-    | Не потрібен       |
| колізій           | (0xDB 0xDC/0xDD)  | нульових байтів   | стаффінг (0x7D)   | (довжина LEN)     |
| Оверхед (типовий) | 2 байти + ~0.8%   | 1 байт + 1 B/254  | 6–8 байтів        | 3–5 байтів        |
| Оверхед (найгірш.)| +100% (подвоєння) | 1 байт + N/254    | +100% (байт-стаф.)| Фіксований        |

| Відновлення збою  | Миттєво (за END)  | Миттєво (за 0x00) | Миттєво (за 0x7E) | Пошук наступного  |
|                   |                   |                   |                   | SYNC + валідність |
+-------------------+-------------------+-------------------+-------------------+-------------------+
```

### 1. SLIP: граничний мінімалізм і побайтовий розбір

Протокол SLIP розв'язує задачу кадрування з найменшими можливими витратами пам'яті та коду. Його головна перевага — повна придатність до потокового кодування й декодування «на льоту» (англійською *streaming / on-the-fly*).

Передавачу не потрібно зберігати весь вихідний пакет у пам'яті перед початком відправки: щойно черговий байт надходить від вищого рівня, функція кодування миттєво вирішує, чи відправити його безпосередньо в регістр UART, чи замінити парою байтів екранування. Приймач обходиться найпростішим двостановим кінцевим автоматом (FSM), який витрачає буквально десяток процесорних інструкцій на байт і може виконуватися прямо всередині обробника переривань від послідовного порту.

Головним недоліком SLIP є недетермінований і нерівномірний оверхед. Якщо корисне навантаження складається з випадкових бінарних даних, оверхед становить скромні 0.78% (приблизно 2 заміни на кожні 256 байтів). Проте якщо пакет містить структури, де часто повторюються значення `0xC0` або `0xDB` (наприклад, стиснені графічні зображення, упаковані архіви або масиви чисел із плаваючою комою певних діапазонів), розмір повідомлення може збільшитися на величину до 100%. Подвоєння довжини кадру в найгіршому випадку неприпустиме для каналів зв'язку з жорсткими часовими рамками доставки (*hard real-time deadlines*) або на радіолініях із високою вартістю передачі кожного байта.

### 2. COBS: детермінований оверхед для критичних систем

Алгоритм COBS (*Consistent Overhead Byte Stuffing*, запропонований Стюартом Чеширом та Мері Бейкер у 1997 році) створювався спеціально для усунення головної вади SLIP — випадкового роздування розміру кадру.

Ідея COBS полягає в повному усуненні байта `0x00` із закодованого повідомлення. Байт `0x00` стає абсолютно унікальним, гарантованим маркером межі пакета. Щоб видалити нулі, кодер розбиває масив даних на фрагменти довжиною до 254 байтів, записуючи на початку кожного фрагмента байт зсуву (*overhead code byte*), який вказує точну відстань до наступного нульового байта у вихідних даних.

Завдяки такій схемі оверхед кодування COBS суворо детермінований і обмежений математичною формулою:

```
Оверхед = 1 + ceil(Довжина_даних / 254) байтів
```

Для кадру довжиною 1000 байтів максимальний оверхед становить рівно `1 + 4 = 5` байтів (0.5%), незалежно від того, якими саме байтами заповнений пакет. Навіть якщо весь пакет складатиметься виключно з нулів, оверхед не перевищить гарантованої величини 0.4%.

Ціною детермінованості є підвищені вимоги до буферизації: щоб записати перший байт зсуву на початку кадру, кодер повинен просканувати дані вперед до першого нульового байта. Це унеможливлює побайтове передавання без проміжного буфера на передавальному боці.

### 3. HDLC / PPP: промисловий стандарт канального рівня

Протокол PPP (*Point-to-Point Protocol*, RFC 1661), заснований на міжнародному стандарті HDLC (*High-Level Data Link Control*), являє собою завершений, повнофункціональний канальний протокол для складних телекомунікаційних систем.

Кадр PPP обрамляється прапорцем `0x7E` (`01111110` у двійковому коді). У послідовних асинхронних лініях використовується байт-стаффінг: символ `0x7E` замінюється послідовністю `0x7D 0x5E`, а символ керування `0x7D` — послідовністю `0x7D 0x5D`. На додаток, у синхронних каналах зв'язку HDLC підтримує біт-стаффінг (*bit stuffing*): передавач автоматично вставляє нульовий біт після кожних п'яти послідовних одиниць, щоб уникнути появи прапорця `01111110` всередині даних.

На відміну від мінімалістичних SLIP та COBS, заголовок PPP обов'язково включає:
- Сталі поля адреси (`0xFF`) та керування (`0x03`);
- 16-бітне поле типу протоколу (наприклад, `0x0021` для IPv4, `0x0057` для IPv6, `0xC021` для службового протоколу керування лінією LCP);
- Обов'язкову контрольну суму FCS (*Frame Check Sequence*) на основі полінома CRC-16 або CRC-32.

PPP забезпечує повноцінне мультиплексування різних протоколів через один фізичний провід, автоматичний контроль якості лінії та динамічну конфігурацію адрес. Проте його службовий оверхед становить від 6 до 8 байтів на кожен кадр, а повна програмна реалізація стека PPP вимагає значного обсягу пам'яті Flash та RAM, що робить його занадто важким для простих 8-бітних та 32-бітних мікроконтролерів (Cortex-M0/M3).

### 4. Кадрування з довжинним префіксом (Length-Prefix Framing)

Альтернативою методам побайтового стаффінгу є кадрування на основі явного зазначення довжини в заголовку (класичний приклад — протокол MAVLink для безпілотних апаратів або власні бінарні протоколи мікроконтролерного обміну).

У цій архітектурі кадр завжди починається з фіксованого маркера синхронізації SYNC (наприклад, `0xAA 0x55` або `0xFE` / `0xFD` у MAVLink), за яким передається байт або двобайтове слово довжини `LEN`, ідентифікатор типу повідомлення та корисні дані, а завершується кадр контрольною сумою CRC.

Головна перевага довжинного методу — повна відсутність оверхеду на екранування даних. Корисне навантаження передається абсолютно прозоро і без змін, навіть якщо в ньому містяться байти, ідентичні маркеру SYNC. Приймач зчитує заголовок, дізнається точну довжину повідомлення і забирає з буфера рівно вказану кількість байтів.

Слабким місцем довжинного кадрування є поведінка при помилках передачі: якщо електромагнітна завада в лінії спотворить поле довжини `LEN`, приймач відрахує неправильну кількість байтів, втратить межу кадру і змушений буде відкинути дані, шукаючи наступний маркер SYNC та звіряючи контрольну суму CRC.

### Вимоги до пам'яті та апаратне прискорення

Порівняймо обчислювальні ресурси та пам'ять, необхідні для роботи кожного з підходів на 32-бітному мікроконтролері ARM Cortex-M:

1. **SLIP**:
   - **Flash (код)**: менше 300 байтів коду (дві функції на базі простих `switch`).
   - **RAM (оперативна пам'ять)**: виключно буфер для одного пакета MTU (наприклад, 512 або 1500 байтів) плюс 16 байтів контексту FSM.
   - **Апаратна сумісність**: пряма побайтова обробка в перериваннях UART без необхідності очікування кінця кадру.

2. **COBS**:
   - **Flash (код)**: близько 500–800 байтів коду.
   - **RAM (оперативна пам'ять)**: вимагає буфера розміром `MTU + ceil(MTU / 254) + 1` байтів на прийом і окремого буфера на передачу для обчислення покажчиків блоків.
   - **Апаратна сумісність**: чудово поєднується з контролерами DMA в режимі прийому за детектуванням нульового байта (*character match interrupt*).

3. **HDLC / PPP**:
   - **Flash (код)**: від 8 до 30 кілобайтів (включаючи таблиці CRC-16/32, стан LCP/IPCP та парсер кадрів).
   - **RAM (оперативна пам'ять)**: від 2 до 8 кілобайтів для структур черг пакетів і контекстів з'єднань.

4. **Довжинне кадрування (Length-Prefix + CRC)**:
   - **Flash (код)**: близько 600–1200 байтів (включаючи табличну перевірку CRC-16 або CRC-32).
   - **RAM (оперативна пам'ять)**: буфер одного повідомлення фіксованого розміру (зазвичай 64–280 байтів).

### Порівняльний аналіз для прикладних сценаріїв

Вибір оптимального методу кадрування визначається специфікою апаратної платформи та вимогами до надійності:

1. **Мікроконтролерні шлюзи IP та легковажні стеки (lwIP over UART / Bluetooth SPP)**:
   - Найкращий вибір — **SLIP**. Він потребує мінімуму пам'яті (лише буфер на один кадр MTU), не вимагає обчислення складних таблиць і розгортається кількома рядками коду.
2. **Бортова телеметрія дронів і систем керування (Flight Controller to Companion Computer)**:
   - Найкращий вибір — **COBS** або **Кадрування з префіксом довжини + CRC**. Вони гарантують сталий час передачі кадру без ризику несподіваного роздування трафіку та забезпечують миттєву перевірку цілісності керівних команд.
3. **Міжмашинний зв'язок операційних систем (Linux/RTOS over RS-232/RS-485)**:
   - Найкращий вибір — **HDLC / PPP**. Він надає готові механізми виявлення апаратних розривів, контролю помилок через CRC та автоматичного призначення мережевих адрес.
4. **Промислові мережі збору даних датчиків (RS-485 Modbus / Custom Sensors)**:
   - Найкращий вибір — **Кадрування з довжинним префіксом або часовими інтервалами (Modbus RTU)**, де фіксований формат спрощує парсинг на гранично простих 8-бітних чипах.
5. **Радіоканали з високим рівнем завад (LoRa / FSK / ISM-модеми)**:
   - Найкращий вибір — **Довжинне кадрування з обов'язковим CRC-16/32 та прямим виправленням помилок (FEC)**, оскільки будь-яке пошкодження маркера роздільника в потокових протоколах без лічильника байтів може призвести до склеювання кількох пакетів поспіль.
