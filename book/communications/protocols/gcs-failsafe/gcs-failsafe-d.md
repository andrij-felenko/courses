# Failsafe на стороні GCS: виявлення втрати зв'язку та поведінка

<preknowlist>
- [Пакет MAVLink](book:communications/mavlink-packet) — структура бінарного кадру, контроль цілісності та лічильники послідовності.
- [Потік телеметрії](book:communications/telemetry-stream) — періодичність повідомлень `HEARTBEAT`, частоти потоків і затримки доставки.
- [Режими failsafe RC](book:communications/rc-failsafe-modes) — реакція автопілота на втрату апаратурного радіоканалу пульта.
</preknowlist>

Безпілотник виконує політ на відстані кількох кілометрів, передаючи на екран наземної станції керування (Ground Control Station, GCS — наприклад, QGroundControl або Mission Planner) координати, швидкість 22 м/с і заряд батареї. Раптом лічильник секунд у кутку інтерфейсу зупиняється, штучний горизонт застигає в правому крені 15°, а значок літака на супутниковій мапі припиняє рух. Оператор не знає, що відбувається в повітрі: чи апарат продовжує маневр, чи вирівнявся, чи зірвався в некероване падіння. Радіоканал телеметрії обірвався через перешкоду рельєфу або інтерференцію.

У такій ситуації відлік іде на секунди. Без чіткого системного алгоритму наземна станція продовжувала б відображати застарілі дані, заколисуючи оператора ілюзією контролю, або дозволила б надсилати команди наосліп у порожнечу. Аварійний механізм захисту (англ. *fail-safe* — «безпечний за відмови») на стороні наземної станції та відповідний йому бортовий контур каналу даних (DataLink Failsafe) вирішують цю задачу: вони забезпечують своєчасне виявлення тиші в ефірі, сповіщення пілота, блокування небезпечних дій на землі та виконання наперед узгодженого польотного алгоритму на борту.

> 🔧 **Навіщо це.** Втрата телеметричного каналу — штатний крайовий випадок для будь-яких місій поза прямою видимістю (BVLOS). Невірно сконфігурований захист призводить до двох типових катастроф: або дрон перериває корисну місію за найменшої тіні від пагорба й повертається завчасно, або станція накопичує команди ручного керування та вистрілює ними в апарат у мить відновлення зв'язку, провокуючи миттєве звалювання.

### Радіофізика розриву каналу телеметрії

Радіозв'язок між наземною антеною та безпілотником у повітрі підпорядковується фундаментальним законам електродинаміки. Розуміння фізичних причин втрати сигналу дозволяє відрізнити тимчасове глибоке завмирання від остаточного виходу за радіогоризонт.

Головним чинником затухання на робочих частотах телеметрії (433 МГц, 868/915 МГц або 2.4 ГГц) є перекриття першої зони Френеля — тривимірного еліпсоїда обертання між антенами передавача та приймача. Радіус поперечного перерізу цієї зони в середині траси обчислюється за формулою:

```
r = 0.5 · √(λ · D)
```

де `λ` — довжина хвилі (наприклад, 0.34 м для частоти 868 МГц), а `D` — дистанція між станцією та безпілотником.

```
+-------------------------------------------------------------------------------+
|                            ПЕРША ЗОНА ФРЕНЕЛЯ                                 |
|                                                                               |
|                   .........................................                   |
|              ..'''                                         '''..              |
|          ..''                     Промінь прямої видимості      ''..          |
|  [GCS] *============================================================* [UAV]   |
|          ''..                                                   ..''          |
|              ''..         /\                               ..''               |
|                  ''''''' /  \ '''''''''''''''''''''''''''''                   |
|      Земля              /    \  Пагорб (перешкода перекриває                  |
|     ===================/      \=============================                  |
|                                 понад 40 % радіуса зони)                      |
+-------------------------------------------------------------------------------+
```

Якщо верхівка пагорба, крони лісу або споруди перекривають понад 20–40 % радіуса зони Френеля, рівень сигналу на вході приймача падає на 15–30 дБ навіть за збереження оптичної видимості між антенами.

Другим критичним фактором є багатопроменеве розповсюдження (Multipath Fading). Радіохвиля доходить до антени двома шляхами: прямим променем і відбитим від водної гладіні або бетонного покриття злітної смуги. Якщо різниця фаз між цими променями становить 180° (протифаза), вони взаємно гасять один одного. Це явище спричиняє раптові глибокі провали сигналу на кілька сотень мілісекунд під час зміни висоти або прольоту над водоймами.

Третім фактором є крос-поляризаційне згасання при маневруванні. Штирьові антени наземної станції та безпілотника мають вертикальну поляризацію. Коли літак виконує глибокий віраж із креном 45–60°, бортова антена нахиляється, і взаємне узгодження поляризацій порушується, що спричиняє додаткове падіння потужності сигналу на 10–20 дБ у найвідповідальніший момент маневру.

### Два боки одного обриву: GCS Loss проти RC Loss

Для побудови надійної архітектури безпеки необхідно чітко розмежовувати два незалежні канали керування: апаратурний радіоканал ручного пульта (RC Link) та цифровий двосторонній канал телеметрії й команд (DataLink / GCS Link).

```
+-----------------------------------------------------------------------------------+
|                                  БОРТ АПАРАТА                                     |
|                                                                                   |
|  +--------------------+        SBUS / CRSF (50-200 Гц)     +-------------------+  |
|  | RC-приймач (RX)    | ---------------------------------> |                   |  |
|  +--------------------+        Прямі кути/тяга (стикові)   |                   |  |
|                                                            | Польотний         |  |
|  +--------------------+        MAVLink UART (1-10 Гц)      | контролер (FC)    |  |
|  | Радіомодем / Модуль| <--------------------------------> | (PX4 / ArduPilot) |  |
|  +--------------------+        Телеметрія + Команди місії  |                   |  |
+-----------------------------------------------------------------------------------+
           ^                                                           ^
           | RC-радіоефір                                              | Двосторонній лінк
           v                                                           v (SiK, Wi-Fi, LTE)
+-----------------------+                                   +-----------------------+
| Апаратурний пульт     |                                   | Наземна станція (GCS) |
| пілота (RC TX)        |                                   | (QGroundControl / MP) |
+-----------------------+                                   +-----------------------+
```

Канал ручного пульта (RC) проектується як високошвидкісний односторонній потік (частота 50–200 Гц) із мінімальною латентністю (5–20 мс). Його призначення — пряме утримання рівноваги та маневрування апаратом у реальному часі. Якщо цей потік зникає довше ніж на 0.5–1.0 с, польотний контролер фіксує `RC Loss Failsafe` і перебирає керування на себе.

Канал наземної станції (DataLink) функціонує за протоколом MAVLink через радіомодеми (SiK 433/915 МГц, RFD900), бездротові мережі Wi-Fi або стільниковий зв'язок LTE. Це інтелектуальний канал: ним передаються не сирі положення потенціометрів, а структурований стан систем, навігаційні завдання та високорівневі накази («почати місію», «змінити висоту», «активувати корисне навантаження»). Частота оновлення телеметрії складає 1–10 Гц.

Через меншу частоту оновлення та вищу ймовірність короткочасних мережевих затримок поріг спрацьовування DataLink Failsafe встановлюється значно більшим: типово від 3.5 до 10 секунд.

Головна відмінність полягає в розподілі відповідальності:
1. **Бортовий контролер** стежить за тишею з боку станції. Якщо земля не шле запитів або підтверджень понад ліміт часу, борт активує власну аварійну програму.
2. **Наземна станція** стежить за тишею з боку безпілотника. Якщо борт перестав транслювати телеметрію, станція маркує дрон як втрачений, вмикає звукову й візуальну сигналізацію оператору та блокує інтерфейс відправки нових директив.

### Анатомія виявлення: сторож пульсу (Heartbeat Watchdog)

Основним інструментом перевірки життєздатності каналу між станцією та бортом є періодичне повідомлення `HEARTBEAT` (ідентифікатор MAVLink `#0`). Кожен учасник мережі — польотний контролер, бортовий комп'ютер і наземна станція — зобов'язаний транслювати власний кадр пульсу з фіксованою частотою 1 Гц (один раз на секунду).

![Хронологія детектора пульсу (Heartbeat Watchdog) при розриві каналу](/book/communications/protocols/gcs-failsafe/img/watchdog-timeline.svg)
*Часова шкала переходу стану каналу зв'язку від активного прийому через деградацію до аварійного стану Failsafe.*

На стороні GCS працює програмний сторожовий таймер (Watchdog). При отриманні кожного кадру `HEARTBEAT` від конкретного системного ідентифікатора апарата (`System ID`) таймер скидається в поточне монотонне значення системного часу: `last_heartbeat_time = monotonic_now()`.

Поточний стан зв'язку розраховується в головному циклі програми за різницею `Δt = monotonic_now() - last_heartbeat_time`:

1. **Нормальний стан (`CONNECTED`): `Δt < 1.5 с`.**
   Пакети надходять штатно. Інтерфейс GCS відображає активний зелений індикатор, рівень сигналу RSSI та актуальні показники швидкості, висоти й орієнтації.

2. **Стан деградації (`DEGRADED` / `WARNING`): `1.5 с ≤ Δt < 3.5 с`.**
   Пропущено 1–2 послідовні кадри пульсу. Причиною може бути локальне радіозавмирання або перевантаження буфера модема. Індикатор зв'язку забарвлюється в жовтий колір. GCS утримує останні отримані навігаційні координати, але забороняє виконання критичних операцій (наприклад, калібрування сенсорів чи завантаження нових польотних планів).

3. **Аварійний обрив (`LINK LOST` / `FAILSAFE`): `Δt ≥ 3.5–5.0 с`.**
   Станція констатує повну втрату зв'язку з повітряним судном. Вмикається голосове оповіщення («Telemetry lost»), віджет позиції дрона на мапі стає напівпрозорим або позначається знаком питання, а всі елементи керування блокуються.

У програмній реалізації простий таймер обов'язково доповнюється аналізом лічильника послідовності пакетів (`Sequence Number`). Це дозволяє фіксувати деградацію зв'язку за відсотком втрат ще до того, як спливе повний таймаут тиші; повний вихідний код сторожа наведено у вставці [алгоритм детектора розриву та сковзного вікна втрат у коді](book:communications/gcs-failsafe/proj-heartbeat-watchdog.md).

### Ієрархія аварійних контурів у польотному контролері

Бортовий автопілот одночасно відстежує десятки потенційних загроз: падіння напруги живлення, вихід за межі польотної геозони, відмову сенсорів EKF, втрату пульта RC та обрив телеметрії GCS.

Коли одночасно виникає декілька аварійних подій, автопілот керується суворою матрицею пріоритетів безпеки (Failsafe Priority Hierarchy):

```
[Пріоритет 1: Найвищий]  Аварійний вимикач двигунів (Emergency Kill Switch / Crash Check)
           |
[Пріоритет 2]            Критичний розряд батареї (Critical Low Battery Failsafe)
           |
[Пріоритет 3]            Порушення меж геозони (Geofence Breach Failsafe)
           |
[Пріоритет 4]            Втрата апаратурного пульта RC (RC Loss Failsafe)
           |
[Пріоритет 5]            Втрата каналу телеметрії GCS (DataLink Loss Failsafe)
           |
[Пріоритет 6: Найнижчий]  Втрата каналу зв'язку з компаньйоном (Offboard Loss)
```

Фундаментальне правило безпеки польотних систем стверджує: **подія нижчого пріоритету ніколи не може скасувати або послабити дію, викликану подією вищого пріоритету**.

Розглянемо практичний приклад. Апарат виконує місію, і в нього обривається телеметричний зв'язок із GCS. Автопілот переходить у режим зависання (Loiter) на 30 секунд. Під час зависання напруга акумулятора падає нижче критичного порогу 3.3 В на банку (`Battery Critical Failsafe`, пріоритет 2). Автопілот негайно перериває зависання і починає примусову посадку (`Emergency Land`). Якщо в цей момент зв'язок із наземною станцією відновлюється, GCS не зможе скасувати посадку, оскільки загроза повного знеструмлення має вищий пріоритет над відновленням каналу зв'язку.

### Аварійні режими польотного контролера при DataLink Loss

Коли бортовий контролер фіксує перевищення таймауту відсутності телеметрії від GCS (параметр `COM_DL_LOSS_T` у PX4 або `FS_GCS_TIMEOUT` в ArduPilot), він переходить до виконання наперед запрограмованого аварійного режиму.

![Логіка дій польотного контролера при DataLink Loss](/book/communications/protocols/gcs-failsafe/img/failsafe-decision-tree.svg)
*Дерево прийняття рішень автопілотом при втраті телеметрії: залежність від польотного режиму, наявності GPS та конфігураційних прапорців.*

Поведінка апарата залежить від обраної стратегії безпеки, поточного режиму польоту та наявності супутникової навігації:

#### 1. Повернення додому (RTL / Return-to-Launch)
Найпоширеніша дія для напівавтономних польотів у зоні прямої видимості. Отримавши сигнал про втрату телеметрії, контролер:
- Фіксує поточні координати.
- Піднімається на попередньо налаштовану безпечну висоту повернення (`RTL_ALT`, наприклад, 50–100 м над рельєфом), щоб уникнути зіткнення з деревами чи будівлями.
- Прямує за прямою траєкторією або зворотним треком до збереженої точки старту (`Home Position`).
- Зависає над точкою зльоту або виконує автоматичну посадку після завершення таймауту очікування.

Сучасні автопілоти підтримують функцію слідування за рельєфом (Terrain Following RTL): спираючись на завантажену у внутрішню пам'ять цифрову модель висот SRTM, контролер автоматично підтримує безпечний кліренс над вершинами пагорбів на всьому зворотному шляху.

#### 2. Інтелектуальне повернення за збереженим треком (SmartRTL)
Прямолінійне повернення RTL несе загрозу в складних умовах: наприклад, якщо безпілотник залетів за висотну будівлю або маневрував у вузькому гірському каньйоні. Повернення по прямій призведе до зіткнення зі схилом.

Алгоритм SmartRTL усуває цю небезпеку: під час польоту контролер безперервно записує безпечні пройдені навігаційні точки у внутрішній кільцевий буфер. Для економії пам'яті траєкторія в реальному часі спрощується за допомогою геометричного алгоритму Рамера-Дугласа-Пекера (Ramer-Douglas-Peucker), відкидаючи дрібні флуктуації.

При виникненні аварії безпілотник розвертається і рухається у зворотному напрямку строго по своєму вхідному коридору, гарантовано оминаючи всі перешкоди.

#### 3. Зависання та кружляння (Loiter / Hold)
Апарат припиняє рух за маршрутом і переходить у режим стабілізації позиції: мультикоптер зависає в поточній точці, а літак фіксованого крила починає описувати коло радіусом `NAV_LOITER_RAD`.

Цей режим застосовується як проміжна ланка: автопілот очікує відновлення зв'язку протягом заданого проміжку часу (наприклад, 20–30 секунд). Якщо оператор змінить позицію антени або дрон вийде із зони радіотіні, зв'язок відновлюється без зриву місії. Якщо ж після закінчення таймауту зв'язок не з'явився, автопілот ескалує аварію до рівня RTL або аварійної посадки.

#### 4. Аварійна посадка на місці (Land)
Вертикальне зниження з контрольованою швидкістю (типово 0.5–1.5 м/с) безпосередньо в точці виникнення аварії. Цей алгоритм активується як безальтернативний у двох критичних випадках:
- Відсутній або деградований сигнал супутникової навігації GNSS (апарат не здатний визначити вектор на точку старту).
- Залишковий заряд акумуляторної батареї недостатній для подолання дистанції повернення проти вітру.

#### 5. Продовження виконання місії (Continue Mission)
Спеціалізований режим для далеких автономних польотів (BVLOS), моніторингу протяжних об'єктів або картографування.

Якщо апарат виконує заздалегідь завантажений і валідований польотний план (`AUTO` mode), втрата радіомодема вважається штатною подією. Дрон не перериває завдання, проходить усі заплановані навігаційні точки, скидає корисне навантаження або виконує зйомку, і повертається на точку посадки виключно за маршрутом. Детальний опис конфігураційних прапорців та параметрів PX4 і ArduPilot для цього режиму систематизовано у вставці [структури повідомлень MAVLink та системні параметри автопілота](book:communications/gcs-failsafe/api-mavlink-failsafe.md).

### Керування через джойстик GCS та Joystick Failsafe

Сучасні станції керування дозволяють оператору пілотувати дрон не апаратурним RC-пультом, а USB-джойстиком чи геймпадом, підключеним безпосередньо до комп'ютера GCS. Станція зчитує положення осей геймпада й транслює їх на борт за допомогою повідомлення `MANUAL_CONTROL` (#69).

Така схема несе приховану загрозу: ланцюжок проходження сигналу стає довшим і піддається впливу затримок операційної системи (USB polling, планувальник потоків ОС, мережевий стек UDP/IP, буферизація в радіомодемі).

```
[Геймпад USB] ---> [Драйвер ОС / GCS] ---> [UDP/UART Модем] ~~~ Радіоефір ~~~> [FC Борт]
   (100 Гц)          (Обробка QGC)             (Буфер черги)                   (Обчислення)
```

Якщо в момент енергійного віражу (наприклад, затиснутий правий стик крену та максимальний газ) радіоканал обривається, бортовий контролер без належного захисту продовжував би отримувати останній зафіксований стан або утримував би його у внутрішніх змінних.

Для усунення цієї небезпеки в автопілотах реалізовано незалежний контур **Joystick Failsafe (Manual Control Timeout)**:
- Бортовий стек контролює інтервал надходження пакетів `MANUAL_CONTROL`.
- Поріг спрацьовування встановлюється жорстким: **0.5–1.0 секунди** (параметр `COM_RC_LOSS_T` у PX4).
- Якщо протягом 1 секунди не надійшло жодного нового пакета джойстика, автопілот негайно нейтралізує віртуальні стики (встановлює нульові кути крену, тангажу та рискання) і автоматично переводить дрон у режим стабілізації висоти (`Altitude Hold`) або зависання за GPS (`Position Hold / Loiter`).

Розгляньмо, як виглядає програмна перевірка таймауту джойстика на стороні контролера:

```c
#include <stdint.h>
#include <stdbool.h>

#define JOYSTICK_TIMEOUT_MS 1000u

typedef struct {
    int16_t pitch;    // -1000 .. +1000
    int16_t roll;     // -1000 .. +1000
    int16_t throttle; // 0 .. 1000
    int16_t yaw;      // -1000 .. +1000
} manual_axes_t;

typedef struct {
    manual_axes_t target_axes;
    uint32_t last_manual_packet_ms;
    bool is_joystick_active;
    bool failsafe_engaged;
} joystick_failsafe_t;

void joystick_failsafe_init(joystick_failsafe_t *fs) {
    fs->target_axes = (manual_axes_t){0, 0, 0, 0};
    fs->last_manual_packet_ms = 0;
    fs->is_joystick_active = false;
    fs->failsafe_engaged = false;
}

// Викликається при отриманні MAVLink повідомлення MANUAL_CONTROL (#69)
void joystick_failsafe_on_packet(joystick_failsafe_t *fs, int16_t p, int16_t r, int16_t t, int16_t y, uint32_t now_ms) {
    fs->target_axes.pitch = p;
    fs->target_axes.roll = r;
    fs->target_axes.throttle = t;
    fs->target_axes.yaw = y;
    fs->last_manual_packet_ms = now_ms;
    fs->is_joystick_active = true;
    fs->failsafe_engaged = false;
}

// Викликається у високочастотному циклі регулятора (наприклад, 100 Гц)
void joystick_failsafe_update(joystick_failsafe_t *fs, uint32_t now_ms) {
    if (!fs->is_joystick_active) {
        return;
    }

    uint32_t elapsed = now_ms - fs->last_manual_packet_ms;
    if (elapsed >= JOYSTICK_TIMEOUT_MS) {
        // Таймаут перевищено: скидаємо стики в безпечну нейтраль
        fs->target_axes.pitch = 0;
        fs->target_axes.roll = 0;
        fs->target_axes.yaw = 0;
        // Газ утримується на рівні зависання (Hover Throttle) або передається регулятору висоти
        fs->target_axes.throttle = 500;
        fs->failsafe_engaged = true;
    }
}
```

```cpp
#include <cstdint>
#include <chrono>

struct ManualAxes {
    int16_t pitch{0};    // -1000 .. +1000
    int16_t roll{0};     // -1000 .. +1000
    int16_t throttle{0}; // 0 .. 1000
    int16_t yaw{0};      // -1000 .. +1000
};

class JoystickFailsafe {
public:
    using Milliseconds = std::chrono::milliseconds;
    using TimePoint = std::chrono::steady_clock::time_point;

    explicit JoystickFailsafe(Milliseconds timeout = Milliseconds{1000})
        : timeoutThreshold_(timeout) {}

    void onManualControlPacket(const ManualAxes& axes, TimePoint now = std::chrono::steady_clock::now()) noexcept {
        currentAxes_ = axes;
        lastPacketTime_ = now;
        isActive_ = true;
        isFailsafeEngaged_ = false;
    }

    void update(TimePoint now = std::chrono::steady_clock::now()) noexcept {
        if (!isActive_) {
            return;
        }

        auto elapsed = std::chrono::duration_cast<Milliseconds>(now - lastPacketTime_);
        if (elapsed >= timeoutThreshold_) {
            // Примусове центрування осей керування
            currentAxes_.pitch = 0;
            currentAxes_.roll = 0;
            currentAxes_.yaw = 0;
            currentAxes_.throttle = 500; // Нейтральна тяга утримання висоти
            isFailsafeEngaged_ = true;
        }
    }

    [[nodiscard]] const ManualAxes& axes() const noexcept { return currentAxes_; }
    [[nodiscard]] bool isFailsafeEngaged() const noexcept { return isFailsafeEngaged_; }
    [[nodiscard]] bool isActive() const noexcept { return isActive_; }

private:
    Milliseconds timeoutThreshold_;
    ManualAxes currentAxes_{};
    TimePoint lastPacketTime_{};
    bool isActive_{false};
    bool isFailsafeEngaged_{false};
};
```

### Буферизація, відновлення зв'язку та пастка відкладених команд

Під час польоту обрив телеметрії часто буває короткочасним: дрон пролітає за високою будівлею, потрапляє в зону локальної радіоінтерференції або зазнає багатопроменевого завмирання. За кілька секунд канал зв'язку відновлюється (подія `Reconnect`).

![Відновлення зв'язку та очищення черг керування](/book/communications/protocols/gcs-failsafe/img/reconnect-resync.svg)
*Процедура безпечного повернення телеметрії: скидання застарілих команд джойстика та ресинхронізація поточного стану місії.*

Процедура відновлення лінку приховує критичну архітектурну вразливість — **виконання застарілих команд (Stale Commands Execution)**.

Коли радіозв'язок зникає, оператор у стані стресу може багаторазово натискати клавіші зміни висоти, перемикання режимів або рухати стики геймпада. Якщо мережевий стек GCS або буфер передавача радіомодема використовує чергу з блокуванням без контролю часу життя пакетів (TTL), усі ці команди накопичуються.

У момент відновлення зв'язку черга миттєво вистрілює десятками застарілих пакетів у бік безпілотника. Борт, який щойно успішно стабілізувався в режимі RTL, раптово отримує шквал суперечливих наказів секундної давнини.

Для усунення цієї проблеми в архітектурі GCS застосовуються суворі правила очищення:
1. **Знищення черги при обриві (Flush on Loss):** Усі буферизовані непідтверджені команди ручного пілотування та разові директиви негайно видаляються з пам'яті GCS у момент фіксації стану `LINK_STATE_LOST`.
2. **Маркування часу життя (Timestamp & Expiration):** Кожне критичне повідомлення супроводжується міткою часу. Контролер ігнорує будь-яку команду керування, якщо затримка її доставки перевищує 500 мс.
3. **Ресинхронізація стану (State Resync):** Першим кроком після відновлення прийому кадру `HEARTBEAT` станція надсилає запит на отримання поточного польотного режиму (`custom_mode`), номера поточної навігаційної точки (`MISSION_CURRENT`) та журналу текстових сповіщень `STATUSTEXT`. Станція повинна синхронізувати свій екран із фактичним станом дрона, а не нав'язувати йому свої старі очікування.

Паралельно ведеться буферизація даних на обох кінцях лінку. На борту пишеться суцільний бінарний лог високої деталізації (ULog у PX4 або DataFlash `.bin` в ArduPilot на microSD-карту), який фіксує всі показання сенсорів навіть під час повної тиші в ефірі. На землі станція безперервно пише лог телеметрії (`.tlog`). При відновленні лінку GCS аналізує прогалини в телеметрії та заповнює службові звіти про інцидент.

### Специфіка роботи через стільникові та супутникові канали

Сучасні безпілотні комплекси все частіше відмовляються від прямих радіомодемів прямої видимості на користь глобальних стільникових мереж LTE/5G та супутникових терміналів.

#### Стільниковий зв'язок LTE/5G
Перевагою стільникових мереж є необмежена дальність польоту в зоні покриття оператора. Проте робота в повітрі має суттєву специфіку:
- **Діаграма спрямованості базових станцій:** Антени стільникових операторів нахилені вниз (down-tilt) для покриття наземних абонентів. На висотах понад 100–150 метрів безпілотник потрапляє у зону слабких бічних пелюсток діаграми спрямованості, через що зв'язок може раптово зникати навіть у густонаселених районах.
- **Хендовери між вишками:** При високій швидкості польоту (20–30 м/с) дрон постійно перемикається між базовими станціями (Cell Handover). У момент перемикання виникає затримка доставки пакетів до 1.5–2.5 секунд. Сторожовий таймер GCS повинен враховувати ці затримки, щоб не генерувати хибні тривоги Failsafe при кожній зміні стільникової вишки.

#### Супутниковий зв'язок (Iridium SBD / Inmarsat)
Для морських та трансконтинентальних апаратів єдиним каналом телеметрії є супутникові модеми коротких повідомлень (Iridium Short Burst Data, SBD).

Характеристики супутникового каналу вимагають спеціальної адаптації Failsafe:
- Час доставки одного повідомлення складає від 5 до 25 секунд.
- Вартість кожного байта трафіку є високою.
- Частота передачі пульсу `HEARTBEAT` знижується з 1 Гц до 0.05–0.1 Гц (один пакет на 20–60 секунд).
- Поріг DataLink Failsafe на борту збільшується до 120–300 секунд, а замість повних кадрів передаються стиснуті бінарні дайджести стану безпілотника.

### Протокол дій оператора в польотній зоні при виникненні аварії

Спрацьовування сигналізації `LINK LOST` на наземній станції є початком чіткого регламенту дій льотного екіпажу на землі. Оператор діє за затвердженим чек-листом для максимізації шансів безпечного повернення повітряного судна:

1. **Фіксація параметрів польоту:** Оператор запам'ятовує останній зафіксований азимут, дистанцію, висоту та залишок заряду акумулятора, відображені на екрані GCS перед замерзанням телеметрії.
2. **Апаратна перевірка наземного сегмента:** Перевіряється надійність кабельного з'єднання між ноутбуком і радіомодемом, індикатори живлення та статус USB-порту станції.
3. **Юстування та переміщення антен:** Якщо використовується спрямована антена (Patch / Yagi) або автоматичний антенний трекер, оператор вручну направляє антену в розрахунковий сектор знаходження апарата з урахуванням напрямку вітру. За необхідності оператор піднімає антенну щоглу або переміщується на найближчу висоту рельєфу.
4. **Розрахунок часу повернення:** Знаючи крейсерську швидкість літака (наприклад, 20 м/с) та відстань у момент обриву (4000 м), оператор обчислює очікуваний час прибуття в зону посадки (близько 200 секунд) з поправкою на зустрічний вітер.
5. **Підготовка посадкового майданчика:** Візуальний спостерігач (Visual Observer) займає позицію для кругового огляду повітряного простору над точкою зльоту. Злітно-посадкова смуга очищається від сторонніх предметів та персоналу.
6. **Готовність резервного пульта RC:** Оператор вмикає апаратурний пульт ручного керування. Коли безпілотник наближається до точки старту та входить у зону дії високочастотного лінку RC, пілот перехоплює керування для виконання точної ручної посадки.

### Кібербезпека каналу зв'язку: глушіння, супутні атаки та криптографічний підпис

Обрив телеметричного зв'язку може бути наслідком не лише природних радіозавад, а й навмисного ворожого впливу або спроби захоплення керування.

#### Радіопридушення (Jamming)
Широкосмуговий або прицільний загороджувальний шум на частотах 433/868/915 МГц повністю блокує вхідні каскади приймача радіомодема (знижує SNR нижче критичного рівня -5 дБ). У таких умовах автопілот беззастережно фіксує DataLink Loss Failsafe. Правильно налаштований режим SmartRTL або Continue Mission дозволяє апарату автоматично вийти із зони дії глушилки та відновити зв'язок на безпечній відстані.

#### Підміна станції (Spoofing) та атаки повтору (Replay Attacks)
Небезпечнішим сценарієм є активне втручання зловмисника: трансляція фальшивих повідомлень `HEARTBEAT` з тим самим System ID або передача підроблених команд посадки `MAV_CMD_NAV_LAND`. Якщо канал зв'язку не захищений, автопілот сприйме чужі пакети за валідний лінк станції, що заблокує активацію штатного Failsafe.

Для запобігання цим загрозам у стандарті MAVLink версії 2.0 впроваджено обов'язковий механізм криптографічного підпису пакетів (Message Signing):
- Кожен пакет супроводжується 13-байтним блоком підпису, що містить ідентифікатор ключа (`link_id`), 48-бітний монотонний мікросекундний таймстемп і 48-бітний зріз хешу HMAC-SHA-256.
- Спільний симетричний секретний ключ (Secret Passphrase) записується в енергонезалежну пам'ять станції та польотного контролера перед вильотом.
- Будь-який пакет із невірним HMAC або застарілим таймстемпом миттєво відкидається на рівні парсера MAVLink. Бортовий контролер продовжує фіксувати тишу і своєчасно активує Failsafe, повністю ігноруючи ворожі спроби зірвати захист.

### Передполітна валідація Failsafe (Pre-flight Checklist)

Жоден виліт не повинен розпочинатися без інструментальної перевірки готовності аварійних систем на землі. Комплексний передполітний чек-лист включає:
1. **Перевірка точки Home:** Переконатися, що координати `Home Position` зафіксовані з високою точністю (3D GPS Fix, кількість супутників > 12, HDOP < 1.0) на вільному від перешкод майданчику.
2. **Верифікація висоти повернення:** Зіставити параметр `RTL_ALT` із картою висот та наявністю високовольтних ліній передач уздовж польотного маршруту.
3. **Імітація обриву DataLink на землі:** Тимчасово знеструмити наземний радіомодем на 10 секунд і переконатися, що автопілот коректно виставляє статус тривоги в бортовому лозі, а станція відтворює голосове сповіщення «Telemetry Lost».
4. **Тест кнопки аварійного переривання:** Перевірити готовність фізичного перемикача ручного перехоплення на апаратурному пульті RC.

### Логування інцидентів, взаємодія з UTM та авіаційний моніторинг

Втрата зв'язку з повітряним судном — це авіаційний інцидент, що фіксується на системному та міжсистемному рівнях.

#### 1. Бортова діагностика та журнал статусів
У момент виявлення розриву зв'язку польотний контролер формує діагностичне повідомлення `STATUSTEXT` із рівнем критичності `MAV_SEVERITY_CRITICAL` (код `2`):
`"Failsafe: DataLink loss detected, entering RTL"`.
Цей запис потрапляє в енергонезалежний бортовий журнал із точною міткою GPS-часу та координатами місця події.

#### 2. Інтеграція з системами керування повітряним рухом безпілотників (UTM)
Під час виконання комерційних операцій наземна станція керування з'єднана через інтернет-шлюз із хмарною системою моніторингу повітряного простору (Unmanned Traffic Management, UTM). За протоколами UTM або стандартами дистанційної ідентифікації (Direct Remote ID / Network Remote ID):
- GCS зобов'язана негайно передати диспетчерській службі UTM статус `CONTINGENCY: C2_LINK_LOST` (втрата каналу Command and Control).
- Повідомлення містить останню відому тривимірну позицію апарата, розрахункову траєкторію повернення RTL та прогнозований час знаходження в повітрі до вичерпання батареї.
- Сусідні пілотовані та безпілотні судна отримують автоматичне попередження про апарат, що виконує аварійний маневр без прямого контролю оператора.

#### 3. Моніторинг повітряної обстановки (ADS-B / FLARM)
Якщо безпілотник виконує аварійне повернення додому за відсутності телеметрії, він перетворюється на потенційну загрозу для іншої авіації. Сучасні бортові комплекси оснащуються приймачами ADS-B (Automatic Dependent Surveillance-Broadcast). Навіть перебуваючи в режимі автономного RTL без зв'язку з землею, автопілот продовжує сканувати повітряний простір: при виявленні транспондера літака, що наближається, алгоритм Failsafe тимчасово змінює висоту або перериває курс повернення для запобігання зіткненню.

### Підсумкова матриця рішень GCS та автопілота

| :--- | :--- | :--- | :--- | :--- |
| **Короткий пропуск кадру** (Δt = 1.5 с) | Жовтий статус `DEGRADED`, зростання % втрат. | Відсутня (таймаут не вичерпано). | Блокування відправки конфігураційних змін. | Продовження поточного режиму без змін. |
