# 📋 Інтерфейси налаштування MTU та фрагментації в Linux

Керування поведінкою фрагментації дейтаграм та виявлення MTU шляху (PMTUD) у Linux здійснюється на трьох взаємопов'язаних рівнях: через системні виклики сокетів (`setsockopt` / `getsockopt`), глобальні параметри ядра через віртуальну файлову систему `sysctl` (`/proc/sys/net/ipv4/` та `/proc/sys/net/ipv6/`) та правила фільтрації пакетів у підсистемах `iptables` і `nftables`.

У цьому довіднику зібрано повний опис програмних інтерфейсів, структур даних ядра, формул розрахунку сегментів для тунельних протоколів та інструментів діагностики мережевого стека.

---

### Сокетні опції керування PMTUD та фрагментацією

Налаштування здійснюються через виклики `setsockopt()` та `getsockopt()` на рівні протоколу `IPPROTO_IP` (для IPv4) або `IPPROTO_IPV6` (для IPv6).

#### 1. Опція `IP_MTU_DISCOVER` (рівень `IPPROTO_IP`)

Задає стратегію обробки прапорця `DF` (Don't Fragment) та взаємодії зі стеком PMTUD ядра для вихідних дейтаграм. Опція приймає цілочисельний аргумент (`int`), що відповідає одному з шести режимів:

| Значення константи | Числовий код | Режим роботи та поведінка ядра |
| :--- | :--- | :--- |
| **`IP_PMTUDISC_DONT`** | `0` | **Фрагментувати завжди.** Прапорець `DF` ніколи не встановлюється у вихідних пакетах. Якщо дейтаграма перевищує MTU вихідного інтерфейсу, ядро автоматично фрагментує її на локальному вузлі. Віддалені маршрутизатори також мають право фрагментувати пакет. |
| **`IP_PMTUDISC_WANT`** | `1` | **Використовувати за наявності маршруту.** Встановлює `DF = 1`, якщо маршрут підтримує PMTUD. Якщо розмір перевищує відомий PMTU, пакет фрагментується локально замість повернення помилки, не блокуючи виклик відправки. |
| **`IP_PMTUDISC_DO`** | `2` | **Суворий PMTUD (стандарт для TCP та з'єднаних сокетів).** Завжди встановлює `DF = 1`. Якщо розмір дейтаграми перевищує PMTU, виклик `sendto()` / `send()` негайно повертає помилку `-1` із `errno = EMSGSIZE`. Застосунок зобов'язаний сам зменшити розмір буфера. |
| **`IP_PMTUDISC_PROBE`** | `3` | **Зондування шляху (PLPMTUD).** Завжди встановлює `DF = 1`, але **ігнорує** кешований у ядрі PMTU. Дозволяє застосунку надсилати великі пакети для активного вимірювання пропускного вікна без блокування виклику `sendto()`. |
| **`IP_PMTUDISC_INTERFACE`** | `4` | **Прив'язка до MTU інтерфейсу.** Встановлює `DF = 1`, але обмежує розмір пакетів виключно фізичним MTU локального мережевого адаптера, ігноруючи віддалені ICMP-повідомлення. Застосовується для локального широкомовлення або зв'язку в межах одного L2-сегмента. |
| **`IP_PMTUDISC_OMIT`** | `5` | **Виключення з обліку PMTU.** Встановлює `DF = 0` і не оновлює запис у кеші маршрутизації при отриманні помилок. |

#### 2. Опція `IP_MTU` (рівень `IPPROTO_IP`, тільки читання)

Повертає поточне цілочисельне значення Path MTU (у байтах), кешоване ядром для даного сокета (з урахуванням останніх отриманих повідомлень `ICMP Type 3 Code 4`). Сокет мусить бути попередньо з'єднаний через виклик `connect()` або відправити хоча б один пакет на адресу призначення, інакше виклик поверне помилку `ENOTCONN`.

:::tabs
```c
/* Отримання поточного кешованого PMTU мовою C */
#include <stdio.h>
#include <sys/socket.h>
#include <netinet/in.h>

int get_socket_pmtu(int sock_fd) {
    int current_pmtu = 0;
    socklen_t len = sizeof(current_pmtu);
    if (getsockopt(sock_fd, IPPROTO_IP, IP_MTU, &current_pmtu, &len) < 0) {
        perror("getsockopt IP_MTU");
        return -1;
    }
    return current_pmtu;
}
```
```cpp
// Отримання поточного кешованого PMTU мовою C++
#include <sys/socket.h>
#include <netinet/in.h>
#include <system_error>
#include <expected>

[[nodiscard]] std::expected<int, std::error_code> get_socket_pmtu(int sock_fd) noexcept {
    int current_pmtu = 0;
    socklen_t len = sizeof(current_pmtu);
    if (::getsockopt(sock_fd, IPPROTO_IP, IP_MTU, &current_pmtu, &len) < 0) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    return current_pmtu;
}
```
:::

#### 3. Опція `IP_RECVERR` та асинхронна черга помилок (`MSG_ERRQUEUE`)

Опція `IP_RECVERR` вмикає збереження розширених мережевих помилок у черзі помилок сокета. Коли маршрутизатор надсилає `ICMP Type 3 Code 4` (*Fragmentation Needed*), ядро Linux зберігає структуру `struct sock_extended_err` у черзі допоміжних повідомлень (`msg_control`).

Поля структури `struct sock_extended_err` (із заголовка `<linux/errqueue.h>`):
- `ee_errno`: містить код помилки (наприклад, `EMSGSIZE`);
- `ee_origin`: походження помилки (`SO_EE_ORIGIN_ICMP`);
- `ee_type`: тип ICMP-повідомлення (значення `3` для Destination Unreachable);
- `ee_code`: код ICMP-повідомлення (значення `4` для Fragmentation Needed);
- `ee_info`: **актуальне значення Next-Hop MTU**, передане проміжним роутером.

#### 4. Опції сокета `SO_RCVBUF` та пам'ять черг збирання

Розмір буфера прийому сокета `SO_RCVBUF` впливає на максимальний обсяг даних, який застосунок може одночасно утримувати в черзі дефрагментації:
- Якщо `SO_RCVBUF` встановлено у значення менше за розмір зібраної дейтаграми (наприклад, 32 КБ для дейтаграми розміром 64 КБ), ядро відкидає дейтаграму на етапі фінального збирання через брак буферного простору сокета, навіть якщо всі фрагменти надійшли без помилок.
- Для прийому великих фрагментованих дейтаграм системний адміністратор повинен переконатися, що `net.core.rmem_max` дозволяє виділення щонайменше 128–256 КБ на сокет.

#### 5. Опції IPv6 (`IPPROTO_IPV6`)

- **`IPV6_MTU_DISCOVER`**: Аналог `IP_MTU_DISCOVER` для сокетів IPv6. Приймає значення `IPV6_PMTUDISC_DONT` (0), `IPV6_PMTUDISC_WANT` (1), `IPV6_PMTUDISC_DO` (2), `IPV6_PMTUDISC_PROBE` (3), `IPV6_PMTUDISC_INTERFACE` (4), `IPV6_PMTUDISC_OMIT` (5).
- **`IPV6_DONTFRAG`**: Булевий прапорець (0 або 1). При встановленні в `1` забороняє локальну фрагментацію дейтаграм IPv6 вузлом-джерелом, змушуючи ядро повертати `EMSGSIZE`, якщо пакет більший за MTU інтерфейсу.
- **`IPV6_PATHMTU`**: Отримання структури `struct ip6_mtuinfo`, яка містить поточний MTU шляху (`ip6m_mtu`) та сокетну адресу призначення (`ip6m_addr`).

### Параметри ядра `sysctl` для підсистеми фрагментації

Глобальні налаштування пам'яті, черг та алгоритмів PMTUD доступні в ієрархії `/proc/sys/net/`:

#### 1. Керування пам'яттю та чергами IPv4 (`/proc/sys/net/ipv4/`)

Критичні параметри керування ресурсами дефрагментації:

- **`net.ipv4.ipfrag_high_thresh` (типово 4 194 304 байти / 4 МБ):**
  Верхня межа оперативної пам'яті під усі активні черги фрагментації. Щойно сумарний обсяг виділених під фрагменти буферів `sk_buff` досягає цього значення, підсистема `inet_frags` переходить у режим екстреного вилучення застарілих черг за алгоритмом LRU (Least Recently Used), доки обсяг пам'яті не знизиться до `ipfrag_low_thresh`. На високонавантажених шлюзах (10+ Гбіт/с) цей параметр збільшують до 64–128 МБ (`67108864` – `134217728`), щоб запобігти втратам пакетів під час сплесків трафіку.

- **`net.ipv4.ipfrag_low_thresh` (типово 3 145 728 байтів / 3 МБ):**
  Нижня межа пам'яті дефрагментації. Ядро продовжує скидати незавершені черги, доки лічильник зайнятої пам'яті не впаде нижче цього порогу.

- **`net.ipv4.ipfrag_time` (типово 30 секунд):**
  Максимальний час життя черги збирання дейтаграми (*Reassembly Timer*). Якщо за 30 секунд хост не отримав усі фрагменти, черга знищується, а виділена пам'ять повертається операційній системі. Якщо хост встиг отримати фрагмент із нульовим зміщенням (`Offset = 0`), відправнику надсилається повідомлення `ICMP Type 11 Code 1` (*Time Exceeded: Fragment Reassembly Time Exceeded*).

- **`net.ipv4.ipfrag_max_dist` (типово 64):**
  Максимальна дозволена розбіжність ідентифікаторів (`Identification`) для фрагментів від одного джерела перед підозрою на колізію ID. Допомагає боротися зі змішуванням фрагментів при отриманні пакетів із порушеним порядком доставки (Out-of-Order Delivery) на багатопотокових каналах.

- **`net.ipv4.ip_no_pmtu_disc` (типово 0):**
  Глобальний перемикач механізму PMTUD:
  - `0` — PMTUD увімкнено (стандартна поведінка RFC 1191);
  - `1` — глобальне вимкнення PMTUD для всієї системи (усі вихідні пакети надсилаються з `DF = 0`, що дозволяє проміжну фрагментацію, але створює ризик втрати продуктивності);
  - `2` — режим вимкнення з фіксацією розміру сегмента за мінімальним MTU.

#### 2. Керування PLPMTUD та TCP MSS (`/proc/sys/net/ipv4/`)

- **`net.ipv4.tcp_mtu_probing` (типово 0):**
  Керування механізмом виявлення MTU транспортного рівня (Packetization Layer PMTUD, RFC 4821):
  - `0` — вимкнено (система покладається виключно на класичні ICMP-повідомлення);
  - `1` — адаптивний режим (вмикає активне зондування чорних дір лише тоді, коли стек TCP фіксує багаторазові таймаути ретрансмісії без відповіді ICMP);
  - `2` — постійно увімкнено (TCP завжди зондує шлях великими сегментами для пошуку максимального пропускного MTU).

- **`net.ipv4.tcp_base_mss` (типово 1024 байти):**
  Базовий розмір MSS, до якого TCP тимчасово скидає розмір сегмента при виявленні чорної діри PMTUD, після чого починає поступовий двійковий пошук безпечного розміру сегмента вгору.

- **`net.ipv4.tcp_min_snd_mss` (типово 48 байтів):**
  Абсолютний мінімальний розмір TCP MSS, нижче якого ядро ніколи не зменшуватиме сегмент при відкиданнях пакетів.

#### 3. Параметри IPv6 (`/proc/sys/net/ipv6/`)

- **`net.ipv6.ip6frag_high_thresh`** (типово 4 МБ) — верхній поріг пам'яті для черг IPv6;
- **`net.ipv6.ip6frag_low_thresh`** (типово 3 МБ) — нижній поріг пам'яті для черг IPv6;
- **`net.ipv6.ip6frag_time`** (типово 60 секунд за RFC 2460/8200) — час життя черги збирання IPv6 (у стандартизації IPv6 час життя черги збільшено вдвічі порівняно з IPv4 для компенсації міжконтинентальних затримок).

### Налаштування TCP MSS Clamping на маршрутизаторах

TCP MSS Clamping (примусове затискання розміру сегмента) застосовується на шлюзах та маршрутизаторах для усунення проблем із тунелями PPPoE (MTU 1492), IPsec (MTU 1420), GRE (MTU 1476) та VXLAN (MTU 1450).

#### Формула розрахунку максимального розміру TCP MSS

Для коректного проходження пакетів без фрагментації розмір TCP MSS розраховується за формулою:
```
MSS = Interface_MTU - IP_Header_Size - TCP_Header_Size - Tunnel_Overhead
```

Типові значення накладних витрат популярних протоколів інкапсуляції:
- **PPPoE:** 8 байтів overhead → `MTU = 1492` → `MSS = 1452` (IPv4) або `1432` (IPv6);
- **GRE:** 24 байти overhead (20 B IPv4 + 4 B GRE) → `MTU = 1476` → `MSS = 1436`;
- **IPsec ESP (тунельний режим, AES-GCM-128 + SHA256):** 56–72 байти overhead → `MTU = 1420` → `MSS = 1380`;
- **VXLAN (UDP порт 4789):** 50 байтів overhead (14 B Ethernet + 20 B IP + 8 B UDP + 8 B VXLAN) → `MTU = 1450` → `MSS = 1410`;
- **WireGuard (UDP):** 60 байтів для IPv4 (20 B IP + 8 B UDP + 32 B WireGuard) або 80 байтів для IPv6 → `MTU = 1420` (IPv4) або `1280` (IPv6).

#### 1. Синтаксис `iptables` (таблиця `mangle`)

Автоматичне підлаштування MSS під MTU інтерфейсу виходу:
```bash
# Автоматичне затискання MSS для всіх прохідних пакетів SYN/RST у ланцюжку FORWARD
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu

# Примусове встановлення фіксованого значення MSS (наприклад, 1452 байти для PPPoE)
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --set-mss 1452
```

Для транзитного трафіку IPv6:
```bash
ip6tables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

#### 2. Синтаксис `nftables`

Сучасна еквівалентна конфігурація у правилах `nftables`:
```
table inet filter {
    chain forward {
        type filter hook forward priority mangle; policy accept;
        
        # Автоматичне затискання MSS до PMTU маршруту
        tcp flags syn tcp option maxseg size set rt mtu
        
        # Або фіксоване обмеження значенням 1452 байти для вихідного PPPoE-інтерфейсу
        # oifname "ppp0" tcp flags syn tcp option maxseg size set 1452
    }
}
```

### Команди діагностики MTU та перевірки фрагментації

#### 1. Перевірка та зміна MTU інтерфейсу (`iproute2`)

```bash
# Перегляд поточного MTU на всіх мережевих інтерфейсах
ip link show

# Зміна MTU для інтерфейсу eth0 (наприклад, увімкнення Jumbo Frames 9000 B)
sudo ip link set dev eth0 mtu 9000

# Перегляд кешу маршрутизації та виявленого PMTU для конкретної цілі
ip route get 1.1.1.1
# Вивід: 1.1.1.1 via 192.168.1.1 dev eth0 src 192.168.1.50 pmtu 1492
```

#### 2. Ручне тестування PMTU за допомогою `ping`

Для точного виявлення вузького місця надсилають ICMP Echo Request із примусовим прапорцем `DF` та варіюванням розміру корисного навантаження:

```bash
# Утиліта ping у Linux (розмір -s задає розмір навантаження ICMP без 28 B заголовків IP+ICMP)
# Для перевірки MTU 1500: payload = 1500 - 20 (IP) - 8 (ICMP) = 1472 байти
ping -M do -s 1472 -c 1 8.8.8.8

# Якщо MTU лінку менший за 1500 (наприклад, PPPoE MTU 1492), ядро поверне:
# From 192.168.1.1 icmp_seq=1 Frag needed and DF set (mtu = 1492)
```

Пояснення прапорців `-M`:
- `-M do` — заборонити фрагментацію (встановити `DF = 1`);
- `-M dont` — дозволити локальну та проміжну фрагментацію (`DF = 0`);
- `-M probe` — встановити `DF = 1`, ігноруючи кеш PMTU ядра (для виявлення нових значень).

#### 3. Трасування MTU шляху через `tracepath`

Утиліта `tracepath` автоматично надсилає UDP-дейтаграми різного розміру та визначає MTU кожного транзитного стрибка (Hop):

```bash
tracepath 8.8.8.8
# 1?: [LOCALHOST]     pmtu 1500
# 1:  192.168.1.1     0.842ms
# 2:  10.200.0.1      3.124ms pmtu 1492
# 3:  8.8.8.8         14.210ms reached
#     Resume: pmtu 1492 hops 3 back 3
```

#### 4. Інспекція стану активних сокетів (`ss`)

```bash
# Перегляд внутрішніх метрик активних TCP-з'єднань (зокрема pmtu та mss)
ss -ti '( dport = :https )'
# Вивід: ESTAB 0 0 192.168.1.50:48212 104.21.48.1:443
#        cubic wscale:7,7 rto:200 rtt:14.2/2.1 ato:40 mss:1452 pmtu:1492 rcvspace:14600
```

### Фільтри `tcpdump` та Wireshark для перехоплення фрагментації

Аналіз трафіку на рівні сирих байтів є основним методом локалізації аномалій фрагментації та виявлення прихованих ICMP-блокувань:

#### 1. Фільтри Berkeley Packet Filter (BPF) для `tcpdump`

- **Перехоплення всіх фрагментованих пакетів (проміжних або фінальних):**
  ```bash
  # Перевіряє, чи встановлено прапорець MF (0x2000) або Fragment Offset > 0 (0x1fff)
  sudo tcpdump -ni any 'ip[6:2] & 0x3fff != 0'
  ```

- **Перехоплення ТІЛЬКИ неперших фрагментів (Offset > 0):**
  ```bash
  # Виділяє фрагменти, які не містять транспортних заголовків L4
  sudo tcpdump -ni any 'ip[6:2] & 0x1fff != 0'
  ```

- **Перехоплення повідомлень ICMP Fragmentation Needed:**
  ```bash
  # Фільтрує ICMP Type 3 (Destination Unreachable) та Code 4 (Fragmentation Needed)
  sudo tcpdump -ni any 'icmp and (icmp[0] == 3 and icmp[1] == 4)'
  ```

- **Перехоплення пакетів із забороною фрагментації (`DF = 1`):**
  ```bash
  # Перевіряє біт DF у 6-му байті заголовка IP (маска 0x40)
  sudo tcpdump -ni any 'ip[6] & 0x40 != 0'
  ```

#### 2. Фільтри відображення Wireshark (Display Filters)

- `ip.flags.mf == 1` — показати пакети з ознакою наявності наступних фрагментів;
- `ip.flags.df == 1` — показати пакети з прапорцем Don't Fragment;
- `ip.frag_offset > 0` — показати фрагменти, зміщені відносно початку;
- `icmp.type == 3 and icmp.code == 4` — показати повідомлення про необхідність фрагментації та Next-Hop MTU;
- `ipv6.nxt == 44` — перехоплення пакетів IPv6 із заголовком розширення Fragment Extension Header.

### Специфіка MTU в хмарних середовищах та контейнерних мережах (Kubernetes CNI)

У віртуалізованих дата-центрах та контейнерних кластерах невідповідність MTU між фізичним інтерфейсом вузла та віртуальним оверлейним інтерфейсом (Overlay Interface) є найпоширенішою причиною деградації з'єднань.

#### 1. Вплив оверлейних плагінів CNI (Calico, Cilium, Flannel)

Плагіни контейнерних мереж CNI загортають трафік контейнерів у додаткові тунельні заголовки (Geneve, VXLAN, WireGuard або IP-in-IP):

- Якщо фізичний інтерфейс вузла має стандартний `MTU = 1500`, а плагін CNI налаштовує VXLAN із накладними витратами 50 байтів, інтерфейс поду (`eth0` усередині контейнера) **зобов'язаний мати `MTU = 1450`**.
- Якщо CNI-плагін помилково виділяє поду `MTU = 1500`, будь-який повнорозмірний TCP-пакет після додавання VXLAN-заголовка матиме розмір 1550 байтів. Фізичний мережевий адаптер вузла не зможе передати такий кадр без оверлейної фрагментації, що спричиняє падіння продуктивності в рази та порушує роботу апаратного розвантаження (Offloading).

#### 2. Матриця базових значень MTU популярних хмарних провайдерів

| Провайдер / Середовище | Стандартний MTU інтерфейсу | Підтримка Jumbo Frames | Примітки щодо PMTUD та налаштування |
| :--- | :--- | :--- | :--- |
| **AWS EC2 (VPC)** | `1500` або `9001` (Jumbo) | До `9001` байтів (всередині одного VPC / Placement Group) | Трафік через Internet Gateway (IGW) суворо обмежений `1500` байтами. При спілкуванні через інтернет пакети понад 1500 B відкидаються. |
| **Google Cloud (GCP VPC)** | `1460` (типово) або `1500` | До `8896` байтів | Стандартні віртуальні мережі GCP історично використовують `MTU = 1460` через внутрішнє капсулювання Andromeda SDN. Потрібен обов'язковий MSS Clamping або відповідне налаштування CNI. |
| **Microsoft Azure (VNet)** | `1500` | Не підтримуються (фіксовано 1500) | Пакети понад 1500 байтів безумовно фрагментуються віртуальним комутатором Azure Virtual Filtering Platform (VFP). |
| **Cloudflare WARP / Tunnel** | `1280` (IPv6 мінімум) | Ні | Використовує суворий мінімальний MTU 1280 байтів для гарантованого проходження через будь-які мобільні та транзитні мережі без фрагментації. |

### Особливості виявлення MTU у протоколах QUIC (RFC 9000) та DTLS 1.3 (RFC 9147)

Сучасні протоколи транспортного рівня, що функціонують поверх UDP, реалізують власні незалежні рушії PMTUD на рівні простору користувача:

#### 1. Механіка PMTUD у протоколі QUIC (RFC 9000 §14 та RFC 8899)

Оскільки QUIC шифрує всі заголовки пакетів (включно з номерами послідовності Packet Number), проміжні маршрутизатори не можуть відстежувати стан з'єднання. Керування розміром дейтаграм здійснюється за такими правилами:
- **Початковий розмір (Initial Datagram Size):** Клієнт зобов'язаний доповнювати початкові пакети `Initial` нульовими байтами (Padding) до мінімального розміру **1200 байтів** (мінімальний розмір дейтаграми IPv6 мінус заголовки). Це захищає від атак ампліфікації (Amplification Attack) та перевіряє базову здатність шляху пропускати пакети понад 1 КБ.
- **DPLPMTUD-зондування:** Клієнт або сервер надсилає спеціальні пробні пакети `PING` з прапорцем `PADDING` збільшеного розміру (наприклад, 1350, 1400, 1472 байти). Якщо на пакет надходить підтвердження `ACK`, розмір визнається безпечним. Якщо пакет губиться, QUIC повертається до базового MTU 1200 байтів без розриву сесії.

#### 2. Таймінги та обмеження у DTLS 1.3

Протокол DTLS 1.3 розбиває записи рукостискання (Handshake Messages, такі як великі сертифікати X.509 або ланцюжки відкритих ключів) на власні фрагменти транспортного рівня ще до передачі в системний виклик `send()`. Це повністю усуває необхідність у мережевій фрагментації IP: кожен запис DTLS вміщується у відомий розмір PMTU сокета, запобігаючи скиданню пакетів проміжними вузлами.

### Ізоляція MTU у віртуальних середовищах: VRF та мережеві простори імен (Network Namespaces)

У середовищах із багатьма орендарями (Multi-Tenant Environments) та маршрутизацією на основі VRF (Virtual Routing and Forwarding):

1. **Мережеві простори імен (`ip netns`):**
   Кожен простір імен має власні незалежні значення `sysctl` для підсистеми `net.ipv4.ipfrag_*`. Зміна `ipfrag_high_thresh` у кореневому просторі імен не впливає автоматично на ізольовані контейнери, що дозволяє виділяти окремі квоти пам'яті під дефрагментацію для критичних сервісів.

2. **Віртуальні пари `veth`:**
   При створенні віртуального інтерфейсу `veth` ядро встановлює для нього типовий `MTU = 1500`. Якщо хост використовує Jumbo Frames (MTU 9000), MTU обох кінців пари `veth` необхідно явно синхронізувати:
   ```bash
   sudo ip link set dev veth-host mtu 9000
   sudo ip netns exec container-ns ip link set dev veth-guest mtu 9000
   ```

3. **Корекція MTU на рівні eBPF TC (`clsact` qdisc):**
   Сучасні SDN-рішення (Cilium) можуть модифікувати значення MTU пакета під час проходження черги трафіку Traffic Control за допомогою функції `bpf_skb_change_tail()` та коригувати прапорець `DF` за допомогою `bpf_skb_store_bytes()`. Це дозволяє усувати розбіжності MTU на рівні ядра без втручання в налаштування фізичного мережевого адаптера.

### Рекомендований чек-лист для усунення проблем із PMTUD у продакшені

1. **Перевірте дозвіл ICMP на фаєрволах:** Переконайтеся, що правила міжмережевого екрана (iptables, AWS Security Groups, Cloud Firewalls) явно дозволяють транзит пакетів `ICMP Type 3 Code 4` (IPv4) та `ICMPv6 Type 2` (Packet Too Big).
2. **Увімкніть TCP MSS Clamping на граничних роутерах:** Якщо шлюз обслуговує тунелі VPN, PPPoE або SD-WAN, додайте правило `--clamp-mss-to-pmtu` в таблицю mangle.
3. **Активуйте TCP MTU Probing на серверах:** Для захисту від непідконтрольних проміжних чорних дір в інтернеті встановіть `net.ipv4.tcp_mtu_probing = 1` через `sysctl`.
4. **Синхронізуйте MTU у кластерах Kubernetes:** Перевірте, щоб значення MTU у конфігурації CNI-плагіна (наприклад, `calico-config` або `cilium-config`) було щонайменше на 50 байтів меншим за MTU фізичних інтерфейсів хостів.
