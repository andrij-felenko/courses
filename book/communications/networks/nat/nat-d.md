Коли офісна мережа на п'ятдесят комп'ютерів із приватними адресами `192.168.1.0/24` надсилає запити до вебсерверів у глобальній мережі через один-єдиний маршрутизатор із публічною IP-адресою `203.0.113.5`, жоден із віддалених серверів в Інтернеті не має зворотного маршруту до локального пулу `192.168.1.0/24`. Без спеціального перетворення адрес маршрутизатор просто не зміг би повернути відповіді клієнтам: протокол IPv4 резервує приватні діапазони за стандартом RFC 1918 виключно для локального використання, а магістральні маршрутизатори Інтернету беззастережно відкидають будь-які пакети з такими адресами.

Механізм, що розв'язує цю проблему, має назву **трансляція мережевих адрес (англ. *Network Address Translation, NAT*)**. Він перехоплює мережеві пакети на межі між локальною та глобальною мережами, підміняє внутрішні немаршрутизовані адреси на зовнішню публічну адресу маршрутизатора, зберігає стан кожного активного з'єднання у спеціальній таблиці сесій і здійснює зворотну підміну, коли віддалений сервер повертає відповідь.

### 1. Архітектура та основні види трансляції адрес

Залежно від кількості доступних публічних IP-адрес та завдань мережі трансляція реалізується за однією з трьох базових моделей: статичною, динамічною або портовою.

#### Статичний NAT (Static NAT 1:1)
Статичний NAT встановлює фіксовану взаємно однозначну відповідність (бієкцію) між однією внутрішньою приватною адресою та однією зовнішньою публічною адресою:

```
192.168.1.10  ⇄  203.0.113.10
192.168.1.11  ⇄  203.0.113.11
```

У цій схемі кожен внутрішній комп'ютер вимагає власної виділеної публічної IP-адреси. Статичний NAT не економить адресний простір IPv4. Його застосовують для розміщення публічних серверів (веб, пошта, VPN) у так званій демілітаризованій зоні (DMZ): внутрішній сервер має приватну адресу для зручності адміністрування, але ззовні завжди доступний за стабільною глобальною адресою без обмежень на ініціацію з'єднань.

#### Динамічний NAT (Dynamic NAT — пул адрес)
Динамічний NAT використовує пул із кількох публічних адрес (`M` публічних адрес для `N` внутрішніх хостів, де `N > M`):

```
Пул WAN: [203.0.113.10, 203.0.113.11, 203.0.113.12]
Клієнт 192.168.1.50 надсилає пакет ➔ отримує 203.0.113.10 на час сесії
Клієнт 192.168.1.51 надсилає пакет ➔ отримує 203.0.113.11 на час сесії
```

Коли внутрішній комп'ютер відкриває сесію назовні, маршрутизатор тимчасово виділяє йому першу вільну публічну адресу з пулу. Ця адреса закріплюється за клієнтом до завершення сесії або вичерпання тайм-ауту неактивності. Якщо всі публічні адреси з пулу вже зайняті активними клієнтами, наступний внутрішній хост отримує відмову у відкритті з'єднання, доки хтось із попередніх користувачів не звільнить адресу.

#### Трансляція адрес і портів (NAPT / PAT — Port Address Translation)
Найпоширенішим різновидом трансляції, що використовується в кожному домашньому роутері, офісі та мобільному телефоні, є **NAPT (англ. *Network Address and Port Translation*)**, часто скорочено званий **PAT** або маскарадингом (англ. *Masquerade*).

NAPT дозволяє сотням і тисячам внутрішніх пристроїв одночасно виходити в Інтернет через **одну-єдину публічну IP-адресу**. Для розрізнення потоків маршрутизатор використовує номери портів транспортного рівня (TCP та UDP), виділяючи кожній вихідній сесії унікальний зовнішній порт із діапазону `1024..65535`:

```
Внутрішній сокет      ➔  NAT-шлюз (203.0.113.5)  ➔  Цільовий вебсервер
192.168.1.50:51234    ➔  203.0.113.5:40001       ➔  93.184.216.34:80
192.168.1.51:51234    ➔  203.0.113.5:40002       ➔  93.184.216.34:80
```

Зверніть увагу: обидва внутрішні комп'ютери згенерували однаковий локальний порт `51234`. Маршрутизатор NAPT підмінив порт першого на `40001`, а другого — на `40002`. Коли від сервера `93.184.216.34` приходить відповідь на порт `40001`, роутер перевіряє свою таблицю з'єднань, бачить, що порт `40001` належить хосту `192.168.1.50`, і пересилає пакет йому.

![Архітектура трансляції: вихідний SNAT та вхідний DNAT](/book/communications/networks/nat/img/nat-topology-snat-dnat.svg)
*Топологія NAT: приватна мережа LAN підміняється на публічну IP маршрутизатора для вихідних сесій (SNAT/Masquerade), а вхідні запити до сервісів перенаправляються за фіксованими правилами (DNAT/Port Forwarding).*

#### Напрямки трансляції: SNAT проти DNAT
У практичній конфігурації мереж операції трансляції чітко поділяють за напрямком підміни заголовків:
1. **SNAT (Source Network Address Translation)**: підміна адреси **джерела**. Застосовується на етапі виходу пакета з маршрутизатора (ланцюжок `POSTROUTING`). Використовується, коли ініціатором з'єднання є внутрішній клієнт. Спеціальний випадок SNAT на динамічних інтерфейсах (де публічна IP призначається провайдером через DHCP чи PPPoE) зветься **Masquerade**.
2. **DNAT (Destination Network Address Translation)**: підміна адреси **призначення**. Застосовується на етапі входу пакета в маршрутизатор (ланцюжок `PREROUTING`). Відомий під побутовою назвою **прокидання портів (англ. *Port Forwarding*)**: зовнішні клієнти надсилають запити на публічний сокет роутера `203.0.113.5:8080`, а роутер перенаправляє їх на внутрішній вебсервер `192.168.1.10:80`.

#### Операторський NAT: CGNAT (Carrier-Grade NAT) та виділений префікс RFC 6598
Коли вичерпання IPv4 досягло масштабів інтернет-провайдерів, виникла потреба групувати тисячі абонентів за масивними шлюзами провайдера. Для цього було стандартизовано технологію **Carrier-Grade NAT (CGNAT)** (або NAT444). 

Щоб приватні адреси користувачів за RFC 1918 не конфліктували з внутрішньою мережею провайдера, стандарт **RFC 6598** зарезервував спеціальний блок адрес **`100.64.0.0/10`** (від 100.64.0.0 до 100.127.255.255, понад 4 мільйони адрес). 

Для оптимізації пам'яті CGNAT застосовує **блоковий розподіл портів (англ. *Port Block Allocation, PBA*)**: кожному користувачеві виділяється фіксований блок із 256 або 512 портів (наприклад, порти `4000..4255`), що зменшує обсяг записів у системних журналах білінгу в сотні разів.

Історичні передумови створення стандарту та дискусії навколо порушення базових архітектурних принципів мережі викладено у вставці [Історія створення NAT](book:communications/nat/hist-nat-evolution.md).

### 2. Класифікація типів NAT: конуси, фільтрація та симетрія

Коли клієнт за NAT відкриває вихідне UDP-з'єднання на віддалений сервер, транслятор створює відображення (мапінг) внутрішнього сокета `(IP_in, Port_in)` на зовнішній сокет `(IP_ext, Port_ext)`. Проте різні моделі маршрутизаторів та операційних систем по-різному обробляють вхідні пакети від сторонніх вузлів на цей відкритий порт.

Класичний стандарт **RFC 3489** розділив поведінку NAT на чотири фундаментальні класи.

![Класифікація типів NAT за правилами фільтрації та мапінгу](/book/communications/networks/nat/img/nat-types-cone-symmetric.svg)
*Чотири типи поведінки трансляції та фільтрації: Full Cone, Restricted Cone, Port Restricted Cone та Symmetric NAT.*

#### 1. Full Cone NAT (Повний конус)
У системі Full Cone NAT відображення сокета є повністю незалежним від адресата: щойно внутрішній клієнт `192.168.1.50:5000` надіслав перший пакет назовні, маршрутизатор відкриває порт `203.0.113.5:45000`. 

**Правило фільтрації**: **будь-який** зовнішній хост в Інтернеті може надіслати UDP-пакет на адресу `203.0.113.5:45000`, і маршрутизатор безумовно перешле його внутрішньому клієнту `192.168.1.50:5000`, навіть якщо клієнт ніколи раніше не спілкувався з цим відправником. Це найбільш відкритий тип NAT, що ідеально підходить для P2P-зв'язку та ігор.

#### 2. Address-Restricted Cone NAT (Обмежений за адресою конус)
Як і у повному конусі, внутрішній сокет завжди відображається на той самий зовнішній порт `45000` для всіх вихідних напрямків.

**Правило фільтрації**: зовнішній вузол `IP_remote` може надіслати пакет на відкритий порт `45000` **лише за умови**, що внутрішній клієнт раніше надіслав хоча б один пакет на цю конкретну адресу `IP_remote`. Порт відправника ролі не грає: якщо клієнт надіслав пакет на `93.184.216.34:80`, сервер `93.184.216.34` може відповісти зі свого порту `80`, `53` або будь-якого іншого. Пакети з інших IP-адрес роутер відкидає.

#### 3. Port-Restricted Cone NAT (Обмежений за портом конус)
Найпоширеніший тип транслятора в сучасних домашніх Wi-Fi маршрутизаторах. Зовнішній мапінг порту залишається стабільним для всіх вихідних сесій клієнта.

**Правило фільтрації**: зовнішній вузол може надіслати відповідь на порт `45000` **виключно з тієї самої IP-адреси та того самого номера порту**, на які внутрішній клієнт раніше відправив вихідне повідомлення. Якщо клієнт звертався до `93.184.216.34:80`, то пакет від `93.184.216.34:8080` або з іншої IP буде заблоковано вбудованим фільтром.

#### 4. Symmetric NAT (Симетричний NAT)
Принципово відмінна архітектура, характерна для корпоративних міжмережевих екранів, мобільних операторів 4G/5G (CGNAT) та симетричних шлюзів безпеки.

У симетричному NAT **не існує єдиного зовнішнього порту** для внутрішнього сокета. Для **кожного нового зовнішнього адресата `(IP_dest, Port_dest)`** транслятор виділяє **новий, унікальний зовнішній порт**:

```
192.168.1.50:5000  ➔  Сервер A (93.184.216.34:80)   виділяє  203.0.113.5:45001
192.168.1.50:5000  ➔  Сервер B (198.51.100.20:80)  виділяє  203.0.113.5:45002
```

Оскільки зовнішній порт змінюється для кожного нового співрозмовника, пряме встановлення з'єднання між двома клієнтами за симетричним NAT (P2P Hole Punching) математично неможливе без проміжного сервера-ретранслятора.

#### Сучасна стандартизація: RFC 4787 та RFC 5389
Оскільки термінологія «конусів» із RFC 3489 змішувала логіку виділення портів із правилами фільтрації безпеки, стандарт **RFC 4787** замінив її роздільним описом двох незалежних параметрів:

1. **Поведінка відображення (Mapping Behavior)**:
   - *Endpoint-Independent Mapping (EIM)*: однаковий зовнішній порт для всіх цілей (відповідає всім трьом Cone NAT).
   - *Address-Dependent Mapping (ADM)*: новий порт для кожної нової IP-адреси призначення.
   - *Address and Port-Dependent Mapping (APDM)*: новий порт для кожної нової пари IP:порт (Symmetric NAT).
2. **Поведінка фільтрації (Filtering Behavior)**:
   - *Endpoint-Independent Filtering (EIF)*: пакети приймаються від будь-кого (Full Cone).
   - *Address-Dependent Filtering (ADF)*: перевіряється лише IP відправника (Restricted Cone).
   - *Address and Port-Dependent Filtering (APDF)*: перевіряються і IP, і порт відправника (Port-Restricted Cone та Symmetric NAT).

#### Петля трансляції (Hairpinning / NAT Loopback)
Важливою характеристикою коректного NAT-шлюзу є підтримка механізму **Hairpinning (NAT Loopback)**. Якщо клієнт всередині локальної мережі `192.168.1.50` намагається звернутися до сусіднього локального сервера `192.168.1.10` за його публічною адресою `203.0.113.5:8080`, пакет надходить на внутрішній інтерфейс роутера. 

Розгляньмо, чому без спеціальної обробки це з'єднання руйнується:
1. Якщо роутер застосує лише DNAT (перепише адресу призначення `203.0.113.5 ➔ 192.168.1.10`), пакет прийде до локального сервера з оригінальною адресою джерела `192.168.1.50`.
2. Локальний сервер побачить, що адреса відправника `192.168.1.50` належить до його власної підмережі `192.168.1.0/24`. Він сформує відповідь і надішле її **напряму через локальний Ethernet-комутатор L2 в обхід роутера**.
3. Клієнт `192.168.1.50` отримає пакет-відповідь від IP `192.168.1.10`, тоді як його вихідний TCP-сокет очікував відповідь від публічної адреси `203.0.113.5`. Стек TCP клієнта негайно відкине цей пакет і надішле у відповідь прапорець `RST`, розірвавши з'єднання.

Маршрутизатор із підтримкою Hairpinning усуває цей збій за допомогою **подвійної трансляції (Double NAT)**:
- **DNAT**: змінює адресу призначення `203.0.113.5 ➔ 192.168.1.10`;
- **SNAT**: одночасно змінює адресу джерела `192.168.1.50 ➔ 192.168.1.1` (власну LAN-адресу роутера).

Отримавши такий пакет, сервер змушений відповісти роутеру, а роутер розгортає обидві трансляції у зворотному напрямку і передасть відповідь клієнту з очікуваної публічної адреси `203.0.113.5`.

### 3. Технології подолання NAT (NAT Traversal)

Оскільки NAT забороняє прямі вхідні з'єднання ззовні, виникає фундаментальна проблема для однорангових мереж (P2P), голосового та відеозв'язку (VoIP/SIP, WebRTC), онлайн-ігор та месенджерів. Для встановлення прямого зв'язку між клієнтами було розроблено стек протоколів **подолання NAT (англ. *NAT Traversal*)**.

![Механізми подолання NAT: архітектура STUN, TURN та ICE](/book/communications/networks/nat/img/nat-traversal-stun-turn-ice.svg)
*Протоколи подолання NAT: рефлексивне визначення адреси (STUN), релей трафіку при симетричному NAT (TURN) та координація кандидатів (ICE).*

#### STUN (Session Traversal Utilities for NAT — RFC 5389 / RFC 8489)
Протокол STUN є клієнт-серверним протоколом полегшеного опитування. Сервер STUN розміщується у публічному Інтернеті на відомій IP-адресі:
1. Клієнт за NAT надсилає UDP-запит `Binding Request` на STUN-сервер.
2. Пакет проходить крізь локальний NAT, який підміняє внутрішній сокет клієнта на публічний `(IP_wan, Port_wan)`.
3. STUN-сервер читає заголовок отриманого UDP-пакета, витягує реальну публічну адресу відправника і пакує її у тіло відповіді `Binding Response` у спеціальному атрибуті **`XOR-MAPPED-ADDRESS`**.
4. Клієнт отримує відповідь і дізнається свою публічну «рефлексивну» адресу (англ. *Server Reflexive Address*), а також поточний тип поведінки NAT.

Дізнавшись свої публічні сокети через STUN, два клієнти обмінюються ними через зовнішній сервер сигналізації та одночасно надсилають UDP-пакети назустріч один одному. Цей прийом називається **пробиванням отворів у NAT (англ. *UDP Hole Punching*)**: вихідний пакет клієнта A відкриває стан у його роутері для прийому пакетів від клієнта B, і навпаки.

#### Утримання трансляції: тайм-аути та UDP Keep-Alive
Оскільки UDP є протоколом без збереження з'єднання, маршрутизатори NAT використовують агресивні таймери скидання: запис у таблиці закривається вже через 30–60 секунд відсутності активності. 

Щоб вхідний канал дзвінка або P2P-потоку не закрився, додатки (WebRTC, SIP-телефони) реалізують механізм **UDP Keep-Alive**: клієнт надсилає порожні STUN Binding Indication або пусті пакети кожні 15–20 секунд, підтримуючи активність порту в таблиці conntrack.

#### TURN (Traversal Using Relays around NAT — RFC 5766 / RFC 8656)
Коли пряме P2P-з'єднання неможливе через симетричний NAT або жорсткі корпоративні фаєрволи, застосовується протокол **TURN**.

Сервер TURN діє як гарантований ретранслятор (релей) трафіку:
- Клієнт A встановлює вихідне з'єднання з TURN-сервером і резервує публічний порт на ньому (англ. *Relayed Transport Address*).
- Клієнт B також під'єднується до TURN-сервера.
- Увесь медіа-трафік (аудіо, відео, дані) пересилається через TURN-сервер як через посередника.

TURN забезпечує 100% гарантію встановлення зв'язку в будь-яких мережевих умовах, проте створює додаткову затримку (RTT) та вимагає великої пропускної здатності серверної інфраструктури.

#### ICE (Interactive Connectivity Establishment — RFC 5245 / RFC 8445)
Фреймворк **ICE** об'єднує протоколи STUN і TURN у єдиний адаптивний механізм пошуку найшвидшого доступного шляху між двома вузлами (активно використовується у стандарті WebRTC):
1. **Збір кандидатів (Candidate Gathering)**: кожен клієнт збирає список усіх своїх можливих адрес:
   - *Host Candidates*: прямі IP-адреси фізичних мережевих адаптерів (LAN, Wi-Fi, VPN);
   - *Server Reflexive Candidates (srflx)*: публічні IP та порти, отримані через STUN;
   - *Relayed Candidates (relay)*: адреси ретрансляторів, отримані через TURN.
2. **Обмін кандидатами**: клієнти передають свої списки кандидатів співрозмовнику через протокол сигналізації (SDP-оферта/відповідь).
3. **Перевірка зв'язності (Connectivity Checks)**: клієнти формують пари кандидатів і паралельно надсилають контрольні STUN-пакети за всіма можливими маршрутами.
4. **Вибір маршруту**: якщо прямий зв'язок `Host ⇄ Host` або `srflx ⇄ srflx` працює, ICE обирає його з нульовими витратами на релеї. Якщо всі прямі канали заблоковані, ICE плавно перемикається на резервний канал TURN `relay ⇄ relay`.

#### Протоколи локального контролю: UPnP IGD та PCP
Для усунення потреби в STUN/TURN на домашніх роутерах використовують протоколи прямого керування:
- **UPnP IGD (Universal Plug and Play Internet Gateway Device)**: дозволяє додатку на комп'ютері (наприклад, торрент-клієнту або ігровій консолі) автоматично надіслати роутеру XML/SOAP-команду на відкриття порту.
- **PCP (Port Control Protocol — RFC 6887)** та **NAT-PMP**: сучасні бінарні протоколи керування правилами трансляції, що підтримують як IPv4 NAT, так і IPv6 фаєрволи.

### 4. Проблема перерахунку контрольних сум IP, TCP та UDP

Заміна IP-адрес та портів у мережевому заголовку призводить до порушення цілісності контрольних сум на мережевому (L3) та транспортному (L4) рівнях.

#### Чому зміна L3 ламає контрольну суму L4
Контрольна сума IPv4 захищає лише 20 байтів власного IP-заголовка. Проте транспортні протоколи TCP і UDP під час обчислення своєї контрольної суми підсумовують не лише корисні дані, а й так званий **псевдозаголовок IPv4 (англ. *IPv4 Pseudo-Header*)**:

```
┌────────────────────────────────────────────────────────┐
│               IPv4 Source Address (32 біти)            │
├────────────────────────────────────────────────────────┤
│            IPv4 Destination Address (32 біти)          │
├───────────────┬───────────────┬────────────────────────┤
│   Zero (8)    │  Protocol (8) │    TCP/UDP Length (16) │
└───────────────┴───────────────┴────────────────────────┘
```

Оскільки адреси джерела та призначення входять до складу псевдозаголовка, заміна IP-адреси на мережевому рівні L3 **автоматично робить недійсною контрольну суму TCP або UDP на транспортному рівні L4**, навіть якщо сам сегмент даних не змінювався.

#### Інкрементний перерахунок за стандартом RFC 1624
Повний перерахунок контрольної суми по всьому пакету вимагає часу `O(N)`, де `N` — довжина пакета. На маршрутизаторі з потоком у десятки гігабітів за секунду це створило б колосальне навантаження на пам'ять.

Завдяки властивостям арифметики зворотного коду (1's complement) стандарт **RFC 1624** дозволяє оновити контрольну суму за константний час `O(1)` за формулою:

```
~C' = ~C + ~m + m'
C'  = ~(~C')
```

де:
- `C` — початкова контрольна сума;
- `m` — старе 16-бітне значення змінюваного поля;
- `m'` — нове 16-бітне значення;
- `C'` — результуюча скоригована контрольна сума.

Для 32-бітної IP-адреси операція повторюється для старших і молодших 16 бітів. Алгебраїчне виведення, доведення властивостей 1's complement та обробку граничних нулів наведено у вставці [Арифметика зворотного коду та інкрементний перерахунок контрольних сум](book:communications/nat/math-checksum-update.md).

#### Специфіка повідомлень про помилки ICMP
Особливу складність для NAT становлять повідомлення про помилки ICMP (Destination Unreachable, Time Exceeded):
1. За стандартом RFC 792 тіло такого повідомлення містить **копію IP-заголовка та перші 8 байтів корисного навантаження вихідного пакета**, що викликав помилку.
2. Маршрутизатор NAT повинен знайти сесію за цим вкладеним заголовком, розгорнути трансляцію вкладеного IP-заголовка та інкрементно скоригувати як внутрішню контрольну суму вкладеного пакета, так і зовнішню контрольну суму самого ICMP-повідомлення.
3. Без такої подвійної трансляції комп'ютер у локальній мережі не зможе отримати інформацію про розмір MTU каналу, що повністю зламає механізм **Path MTU Discovery (PMTUD)**.

### 5. Збереження сесій у ядрі: підсистема Netfilter conntrack

Для забезпечення надійної трансляції маршрутизатор повинен зберігати повний стан кожного відкритого з'єднання. В операційній системі Linux за це відповідає підсистема **`nf_conntrack` (Netfilter Connection Tracking)**.

![Структура сесії conntrack: двонаправлені кортежі (5-tuple)](/book/communications/networks/nat/img/conntrack-tuple-table.svg)
*Архітектура збереження сесій у підсистемі nf_conntrack ядра Linux: структура кортежу (5-tuple) у напрямках ORIGINAL та REPLY.*

#### Проходження пакетів крізь хуки Netfilter
Підсистема Netfilter вбудована безпосередньо в конвеєр обробки пакетів ядра Linux. Обробка пакетів відбувається на п'яти послідовних етапах (хуках):

```
       [ Мережевий інтерфейс Rx ]
                  │
                  ▼
         ┌─────────────────┐
         │   PREROUTING    │  ← Тут виконується DNAT (Port Forwarding)
         └────────┬────────┘
                  │
                  ▼
         ┌─────────────────┐       [ Локальний процес ]
         │ Routing Decision│             ▲      │
         └────┬───────┬────┘             │      ▼
     (forward)│       │(to local) ┌──────┴──┐┌──┴────────┐
              │       └──────────►│  INPUT  ││  OUTPUT   │
              │                   └─────────┘└──┬────────┘
              ▼                                 │
         ┌─────────┐                            │
         │ FORWARD │◄───────────────────────────┘
         └────┬────┘
              │
              ▼
         ┌─────────────────┐
         │   POSTROUTING   │  ← Тут виконується SNAT / Masquerade
         └────────┬────────┘
                  │
                  ▼
       [ Мережевий інтерфейс Tx ]
```

1. **`PREROUTING`**: викликається одразу після прийому пакета драйвером мережевої карти. Саме тут виконується **DNAT**: перевіряється порт призначення, і адреса підміняється до того, як ядро прийме рішення про маршрутизацію (Routing Decision).
2. **`POSTROUTING`**: викликається безпосередньо перед відправкою пакета у фізичний або віртуальний мережевий інтерфейс після завершення всіх маршрутних обчислень. Саме тут застосовується **SNAT** або **Masquerade**, підміняючи локальну адресу джерела на зовнішню IP-адресу інтерфейсу відправки.

#### Структура запису з'єднання: nf_conntrack_tuple
У пам'яті ядра кожна сесія представлена двома напрямками в структурі `struct nf_conn`:
1. **`IP_CT_DIR_ORIGINAL`**: прямий 5-компонентний кортеж вихідного пакета `(src_ip, dst_ip, src_port, dst_port, protocol)`.
2. **`IP_CT_DIR_REPLY`**: очікуваний зворотний кортеж `(dst_ip, wan_ip, dst_port, nat_port, protocol)`.

Обидва кортежі додаються до єдиної глобальної хеш-таблиці з'єднань ядра (`nf_conntrack_hash`). Коли надходить будь-який пакет, ядро обчислює швидкий хеш Дженкінса (`jhash`) від його 5-tuple і знаходить потрібну сесію за один крок `O(1)`.

#### Стани з'єднань conntrack
У правилах міжмережевого екрана (iptables/nftables) пакети класифікуються за станами conntrack:
- **`NEW`**: перший пакет сесії (наприклад, TCP SYN), що створює новий запис у таблиці;
- **`ESTABLISHED`**: пакет належить до вже встановленого з'єднання, для якого було отримано двонаправлений трафік;
- **`RELATED`**: пакет відкриває нове самостійне з'єднання, логічно пов'язане з наявним (наприклад, потік даних FTP або повідомлення про помилку ICMP Destination Unreachable);
- **`INVALID`**: пакет не відповідає жодному відомому стану протоколу (наприклад, TCP ACK для неіснуючого з'єднання) і зазвичай відкидається;
- **`UNTRACKED`**: пакети, для яких відстеження стану було примусово вимкнено правилом `NOTRACK`.

#### Таймери життя сесій та вичерпання ресурсів
Кожен запис у таблиці conntrack має таймер зворотного відліку (timeout). За замовчуванням у ядрі Linux встановлено такі значення:
- Встановлене TCP-з'єднання (`ESTABLISHED`): **432 000 секунд (5 діб)**;
- TCP після закриття (`TIME_WAIT`): **120 секунд**;
- Потік UDP з одностороннім трафіком (`UNREPLIED`): **30 секунд**;
- Потік UDP із двостороннім трафіком (`ASSURED`): **180 секунд**;
- Трафік ICMP: **30 секунд**.

Кількість одночасних сесій обмежена параметром ядра **`net.netfilter.nf_conntrack_max`**. Якщо таблиця заповнюється повністю (`nf_conntrack_count == nf_conntrack_max`), ядро починає відкидати всі нові пакети, виводячи в системний журнал системне повідомлення `nf_conntrack: table full, dropping packet`.

Повну програмну реалізацію транслятора NAPT із власною хеш-таблицею та оновленням контрольних сум мовами C та C++ розібрано у вставці [Програмний NAPT-транслятор із таблицею сесій та оновленням контрольних сум](book:communications/nat/proj-conntrack-nat.md).

#### Шлюзи прикладного рівня (ALG — Application Layer Gateway)
Деякі протоколи (FTP, SIP, H.323, TFTP) передають IP-адреси та номери портів усередині власного прикладного корисного навантаження (L7). Для їхньої підтримки в ядрі Linux використовуються спеціальні допоміжні модулі (helpers), такі як `nf_nat_ftp` та `nf_nat_sip`:
1. Модуль ALG перехоплює прикладні команди (наприклад, `PORT 192,168,1,50,15,23` в FTP);
2. Замінює текстову адресу на публічну `wan_ip:nat_port`;
3. Якщо довжина рядка змінилася, модуль **коригує номери послідовностей TCP (Sequence Numbers)** для всіх наступних пакетів цього сеансу.

### 6. NAT у перехідних механізмах між IPv4 та IPv6

У процесі глобального переходу на протокол нового покоління IPv6 технології трансляції отримали друге життя як шлюзи взаємодії між різними адресними світами:

1. **NAT64 / DNS64 (RFC 6146 / RFC 6147)**: дозволяє клієнтам у чистій IPv6-мережі безперешкодно звертатися до застарілих серверів в Інтернеті, що мають лише IPv4-адреси.
   - Сервер DNS64 перехоплює DNS-запит клієнта на запис `AAAA`. Якщо домен має лише IPv4-запис `A` (наприклад, `93.184.216.34`), DNS64 синтезує фіктивний IPv6-запис, додаючи префікс транслятора `64:ff9b::/96` ➔ `64:ff9b::5db8:d822`.
   - Шлюз NAT64 перехоплює IPv6-пакети з цим префіксом, конвертує заголовок IPv6 в IPv4 і транслює джерело в пул публічних IPv4-адрес.
2. **464XLAT (RFC 6877)**: стандарт мобільних мереж 4G/5G, де смартфон працює на чистому IPv6-стеку, але додатки, що використовують застарілі IPv4 сокетні API (наприклад, старі ігри чи месенджери), транслюються внутрішнім транслятором CLAT (Customer-side translator) у формат IPv6 і передаються крізь операторський шлюз PLAT (Provider-side translator / NAT64).
3. **Dual-Stack Lite (DS-Lite — RFC 6333)** та **MAP-T / MAP-E**: протоколи інкапсуляції або безстанової трансляції IPv4-трафіку користувачів у тунелі IPv6 для проходження крізь ядро мережі оператора зв'язку без підтримки подвійного стека на маршрутизаторах.

### 7. Системне адміністрування та діагностика

> 🔧 **Навіщо це.** На високонавантажених серверах, у кластерах Kubernetes (де сервіси NodePort та Kube-Proxy активно використовують SNAT/DNAT), а також на прикордонних шлюзах вичерпання таблиці conntrack є однією з найчастіших причин раптової втрати пакетів.

#### Моніторинг активних сесій
Для інспекції поточної таблиці трансляцій утилітою `conntrack` (пакет `conntrack-tools`):

```bash
# Перегляд списку всіх активних сесій із параметрами трансляції
conntrack -L -n

# Моніторинг створення та закриття сесій у реальному часі
conntrack -E
```

Типовий рядок виводу сесії:
```text
tcp 6 431998 ESTABLISHED src=192.168.1.50 dst=93.184.216.34 sport=51234 dport=80 \
    src=93.184.216.34 dst=203.0.113.5 sport=80 dport=40001 [ASSURED] mark=0 use=1
```

#### Налаштування правил трансляції
У сучасних дистрибутивах Linux правила NAT задаються через підсистему `nftables` або застарілий `iptables`:

```bash
# Вихідний маскарадинг (SNAT) для інтерфейсу eth0
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE

# Прокидання вхідного порту (DNAT) на внутрішній сервер
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.10:80
```

Аналогічні правила мовою сучасної підсистеми `nftables`:

```text
table ip nat {
    chain prerouting {
        type nat hook prerouting priority dstnat; policy accept;
        tcp dport 8080 dnat to 192.168.1.10:80
    }
    chain postrouting {
        type nat hook postrouting priority srcnat; policy accept;
        oifname "eth0" masquerade
    }
}
```

#### Оптимізація та тюнінг ядра (sysctl)
Для запобігання переповненню conntrack на шлюзах із високим навантаженням оптимізують такі параметри у файлі `/etc/sysctl.conf`:

```ini
# Збільшення максимального розміру таблиці з'єднань до 1 мільйона сесій
net.netfilter.nf_conntrack_max = 1048576

# Зменшення часу утримання неактивних TCP-сесій з 5 днів до 1 години
net.netfilter.nf_conntrack_tcp_timeout_established = 3600

# Скорочення очікування закриття FIN_WAIT
net.netfilter.nf_conntrack_tcp_timeout_fin_wait = 30

# Розширення діапазону локальних портів
net.ipv4.ip_local_port_range = 1024 65535
```

### Підсумок

Трансляція мережевих адрес NAT стала критичним компромісом комп'ютерної інженерії, який врятував протокол IPv4 від передчасного вичерпання адресного простору та забезпечив функціонування сучасного глобального Інтернету. Поєднуючи швидку інкрементну корекцію контрольних сум на швидкості каналу, двонаправлене хешування сесій у ядрі та протоколи подолання бар'єрів (STUN, TURN, ICE), NAT продовжує залишатися фундаментальним інструментом побудови корпоративних, операторських та хмарних мереж.
