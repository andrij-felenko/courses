# ⚙️ Розбір команд у потоці SPP: де закінчується «дріт»

[Bluetooth SPP](book:communications/bluetooth-spp) дарує приємну ілюзію: пристрій бачить рівний потік байтів, наче під'єднаний дротом. Та щойно ти хочеш керувати ним **командами** з телефонного терміналу — `LED ON`, `SPEED 120`, `STOP`, — ілюзія показує свою межу. SPP передає **байти**, а не **повідомлення**: він не знає, де закінчується одна команда й починається інша. Цю межу мусиш провести ти сам. Саме тут спотикається більшість перших прошивок із бездротовим керуванням — і поведінка виглядає примхливою, хоча причина проста й завжди та сама.

Підступність саме SPP у тім, що він заколисує. Поки ти тестуєш одну команду за раз на столі, за метр від телефона, кожна долітає цілою — і код, що читає «прийняте за один раз» як готову команду, виглядає робочим. Ілюзія дроту тримається рівно доти, доки канал ідеальний. А далі пристрій їде на той кінець кімнати, між ним і телефоном проходить людина, ефір засмічує сусідній Wi-Fi — і той самий код раптом «недочуває» команди або злютовує їх докупи. Шукати причину починають у радіо чи в живленні, хоча вона була закладена з першого рядка розбору: припущення, що **потік сам нарізає повідомлення**. Він не нарізає — ніколи й ніде.

### Чому байт-потік ≠ команди

Уяви, що телефон шле рядок `SPEED 120\n`. Здавалося б, на тому боці він і прийде цілим рядком. Насправді ні. Радіо ріже дані на пакети так, як йому зручно, а не так, як їх набрав користувач. Один виклик `SerialBT.read()` віддає **рівно один байт**; навіть `readBytes` чи `readString` повертають лише те, що **встигло накопичитися** в буфері на цю мить. Тому ті самі десять символів можуть прийти як завгодно:

```
надіслано:  S P E E D _ 1 2 0 \n
прийшло за такт 1:  S P E E D _ 1        ← половина
прийшло за такт 2:  2 0 \n               ← решта, наступним разом
```

А бувають і навпаки: дві швидкі команди злипаються в один прийом — `LED ON\nLED OFF\n` приходить однією грудкою. Висновок невблаганний: **не можна вважати, що один прийом = одна команда**. Потік не має меж повідомлень, і код, написаний у припущенні «прочитав — отримав цілу команду», працюватиме лише доти, доки команди короткі, а зв'язок ідеальний. Варто додати завад чи довшої команди — і він почне губити та плутати ввід.

### Роздільник проводить межу

Раз потік меж не має, домовся про них сам. Класичний прийом — **роздільник** (англ. *delimiter*, «розмежувач»): символ, який ніколи не трапляється всередині команди й тому надійно позначає її кінець. Майже завжди беруть `\n` (новий рядок), бо його автоматично шле будь-який термінал, коли ти тиснеш Enter. Правило стає простим: **накопичуй байти, доки не зустрінеш `\n`; усе до нього — одна готова команда**.

Спокуса зробити це в один рядок велика — і веде прямо в наступну пастку:

```cpp
String cmd = SerialBT.readStringUntil('\n');   // ⚠ блокує цикл!
```

`readStringUntil` **зупиняє весь цикл** (англ. *blocking call*, «блокувальний виклик»), доки не прийде `\n` або не спливе таймаут (за домовчанням цілу секунду). На вигляд працює — поки команди йдуть рівно. Та в реальному пристрої цей рядок з'їдає головний цикл: поки він чекає на `\n`, мотори не оновлюються, давачі не читаються, [failsafe](book:communications/reliable-link) не спрацьовує. Загубився останній `\n` (а в радіо це **звична** річ) — і пристрій застигає на секунду на кожному прийомі. Для регулятора чи дрона це неприпустимо.

### Неблокувальний збирач рядка

Правильний шлях — забирати з буфера лише те, що **вже є**, по байту, і складати рядок між викликами циклу. Цикл ніколи не зупиняється: нема байтів — пролетів далі; прийшов `\n` — маємо цілу команду:

```cpp
#include "BluetoothSerial.h"
BluetoothSerial SerialBT;

char    line[64];        // буфер для одного рядка-команди
uint8_t len = 0;         // скільки символів уже зібрано

void setup() {
  SerialBT.begin("ESP32-robot");
}

void loop() {
  // 1. Забрати все, що ВЖЕ прийшло, не чекаючи решти
  while (SerialBT.available()) {
    char c = SerialBT.read();

    if (c == '\n' || c == '\r') {        // кінець рядка → команда готова
      if (len > 0) {
        line[len] = '\0';                // завершити С-рядок
        handleCommand(line);             // розібрати її
        len = 0;                         // і почати збирати наступну
      }
    } else if (len < sizeof(line) - 1) { // звичайний символ — у буфер
      line[len++] = c;
    } else {
      len = 0;                           // переповнення: скинути сміття, не зависнути
    }
  }

  // 2. Решта циклу біжить ЩОтакту, бо ми ніде не блокувалися
  updateMotors();
  checkFailsafe();
}
```

Серце тут — `while (SerialBT.available())`: він вичерпує буфер до дна (тож злиплі команди розберуться обидві за один прохід циклу), але **не чекає** на те, чого ще нема. Половина команди просто лишається в `line` до наступного такту, коли долетить решта. Жодного блокування: якщо вхідних байтів нема, `available()` одразу повертає нуль і цикл біжить далі — мотори й failsafe працюють безперебійно. Зверни увагу й на захист `len < sizeof(line) - 1`: без нього команда, довша за буфер (через шум чи зловмисника), затерла б пам'ять за межами масиву — класичне переповнення буфера. Ми ж просто скидаємо зіпсований рядок і чекаємо наступного `\n`.

### Розбір самої команди

Коли цілий рядок зібрано, лишається витягти з нього дієслово й аргумент. Для дрібного набору команд вистачає простого порівняння й `sscanf` — без зайвих бібліотек:

```cpp
void handleCommand(const char* cmd) {
  int value;

  if      (strcmp(cmd, "LED ON")  == 0) digitalWrite(LED, HIGH);
  else if (strcmp(cmd, "LED OFF") == 0) digitalWrite(LED, LOW);
  else if (strcmp(cmd, "STOP")    == 0) setSpeed(0);
  else if (sscanf(cmd, "SPEED %d", &value) == 1) setSpeed(value);   // "SPEED 120" → value=120
  else    SerialBT.printf("? невідома команда: %s\n", cmd);          // відповідь у той самий потік

  SerialBT.println("OK");        // підтвердження — зворотний зв'язок користувачу
}
```

Тонкість тут у `sscanf(cmd, "SPEED %d", &value)`: він повертає **кількість успішно зчитаних полів**, тож перевірка `== 1` водночас і впізнає команду `SPEED`, і витягає число, і відкидає сміття на кшталт `SPEED abc` (де поле не зчиталося). Це безкоштовна валідація: команда з кривим аргументом просто не пройде далі й отримає відповідь «невідома», замість того щоб передати в `setSpeed()` випадкове значення зі стека. Для пристрою, що рухається, така дрібниця рятує від ривка на непередбачувану швидкість через один зіпсований радіопакет — тож аргументи з потоку варто перевіряти завжди, а не довіряти їм наосліп.

Така відповідь у той самий потік (`OK` чи `? невідома команда`) — не дрібниця: вона перетворює сліпе «шлю в порожнечу» на діалог, де ти бачиш у терміналі, що пристрій тебе зрозумів. Це той самий рівний потік байтів SPP, лише тепер у ньому в обидва боки течуть **рядки зі змістом**, а не сирі символи.

### Ті самі граблі — і поза Bluetooth

Найкорисніше тут те, що **жодна стрічка цього коду не залежить від Bluetooth**. Заміни `SerialBT` на звичайний `Serial` — і той самий збирач розбиратиме команди з [дротового UART](book:communications/async-serial), з USB-терміналу, із будь-якого байт-потоку. Бо проблема не в Bluetooth, а в самій природі **потоку без меж повідомлень**: він однаковий усюди, де байти течуть суцільно. Опанувавши цей шаблон раз, ти закриваєш цілий клас «примхливих» багів розбору вводу — у термінала, у GPS-модуля, у будь-якого послідовного давача. А якщо команди стають складнішими за «дієслово + число» (бінарні поля, контрольна сума), час від саморобного роздільника переходити до [справжнього проєктування пакета](book:communications/packet-design) з рамкою, довжиною й [CRC](book:communications/crc).

### Чого ще стерегтися

Лишилося кілька дрібниць, на яких легко обпектися саме в радіоканалі. Перша — **обірваний рядок**. Якщо зв'язок упав посеред команди, у буфері `line` назавжди застрягне її початок без `\n`, і він мовчки приклеїться до першої ж команди після відновлення: набереш `STOP`, а пристрій побачить `SPEED 12STOP`. Надійні прошивки тримають **таймер тиші**: якщо від останнього байта минуло, скажімо, кілька сотень мілісекунд, а `\n` так і не прийшов, недозібраний рядок викидають (`len = 0`) як зіпсований. Це той самий принцип, що рятує дротовий UART від пів-кадру, лише поріг тут добираєш під свій темп команд.

Друга — **луна терміналу**. Чимало Bluetooth-терміналів шлють після Enter не один символ, а пару `\r\n` (повернення каретки + новий рядок). Якби збирач реагував лише на `\n`, символ `\r` затесався б у кінець команди — і `strcmp(cmd, "STOP")` тихо не спрацював би, бо насправді в буфері лежить `STOP\r`. Саме тому в умові вище стоїть `c == '\n' || c == '\r'`: будь-який із роздільників завершує рядок, а порожні рядки (коли `len == 0`) ми просто пропускаємо. Дрібниця на один символ — а без неї половина команд «не розуміється» без видимої причини.

Третя — **темп відповідей**. Спокусливо на кожну команду слати назад довгий звіт, але SPP, хоч і виглядає як рівний дріт, поділяє [спільний ефір](book:communications/on-chip-radio) з усім довкола. Завалиш канал зустрічним потоком — і команди в інший бік почнуть запізнюватися. Тримай відповіді короткими (`OK`, код помилки), а об'ємну телеметрію шли окремим, рідшим темпом. Тоді керування лишається жвавим навіть тоді, коли пристрій водночас звітує про свій стан.
