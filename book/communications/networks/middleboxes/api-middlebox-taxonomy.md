# 📋 Класифікація та поведінкові пастки проміжних пристроїв: довідник структур і модифікацій

Для проектування надійних мережевих протоколів, діагностики аномалій доставки та оптимізації затримок у глобальних мережах інженеру необхідний точний довідник функціональних класів проміжних пристроїв (Middlebox), структур даних підсистеми відстеження з'єднань (*Connection Tracking / Conntrack*), матриць таймерів трансляції та системних параметрів ядра ОС, що керують взаємодією з транзитними вузлами.

Усі проміжні пристрої класифікуються за глибиною аналізу пакетів у моделі OSI, наявністю та масштабом збереження стану (Stateful / Stateless), а також характером втручання в семантику потоку даних:

### Структури даних та конвеєр обробки Conntrack у ядрі Linux

У ядрі Linux та більшості мережевих операційних систем базовим механізмом обліку сесій для фаєрволів та NAT є підсистема **Netfilter Connection Tracking (conntrack)**.

#### 1. Розташування conntrack у конвеєрі Netfilter

Пакет, що проходить через ядро Linux, потрапляє у послідовність гачків (*Netfilter Hooks*):
1. `NF_INET_PRE_ROUTING`: первинна дефрагментація IP та створення початкового стану conntrack; тут же виконується трансляція адреси призначення (DNAT);
2. `NF_INET_LOCAL_IN`: фільтрація пакетів, призначених локальним сокетам хоста;
3. `NF_INET_FORWARD`: перевірка дозволів міжмережевого екрана для транзитного трафіку;
4. `NF_INET_LOCAL_OUT`: реєстрація вихідних з'єднань, згенерованих локальними процесами;
5. `NF_INET_POST_ROUTING`: виконання трансляції адреси відправника (SNAT / Masquerade) безпосередньо перед виходом у мережевий драйвер.

#### 2. Структура кортежу conntrack (`struct nf_conntrack_tuple`)

Кожне двостороннє з'єднання ідентифікується парою симетричних кортежів: оригінального напрямку (`ORIGINAL`, від клієнта до сервера) та напрямку відповіді (`REPLY`, від сервера до клієнта). Цитата структури з вихідного коду ядра Linux:

```text
/* Структура кортежу з'єднання в ядрі Linux (include/net/netfilter/nf_conntrack_tuple.h) */
struct nf_conntrack_tuple {
    struct {
        union nf_inet_addr u3; /* Source IP (IPv4 або IPv6) */
        union {
            __be16 all;
            struct { __be16 port; } tcp;
            struct { __be16 port; } udp;
            struct { __be16 id; }   icmp;
        } u;                   /* Source Port / ICMP ID */
    } src;

    struct {
        union nf_inet_addr u3; /* Destination IP */
        union {
            __be16 all;
            struct { __be16 port; } tcp;
            struct { __be16 port; } udp;
        } u;                   /* Destination Port */
        u_int8_t protonum;     /* Номер протоколу L4 (IPPROTO_TCP = 6, IPPROTO_UDP = 17) */
        u_int8_t dir;          /* Напрямок: IP_CT_DIR_ORIGINAL або IP_CT_DIR_REPLY */
    } dst;
};
```

Коли транслятор NAT змінює адресу чи порт клієнта, він модифікує кортеж `REPLY`, зберігаючи кортеж `ORIGINAL` без змін. Пошук запису в пам'яті виконується за геш-сумою, яка обчислюється швидким гешуванням `jhash2` над полями кортежу.

#### 3. Формат запису в `/proc/net/nf_conntrack`

Поточний стан активних таблиць ядра можна проінспектувати через віртуальну файлову систему:

```text
ipv4     2 tcp      6 431998 ESTABLISHED src=192.168.1.50 dst=93.184.216.34 sport=52140 dport=443 \
    src=93.184.216.34 dst=198.51.100.1 sport=443 dport=38421 [ASSURED] mark=0 use=1
```

* `ipv4` — родина адрес мережевого рівня;
* `tcp 6` — транспортний протокол та його номер в IP;
* `431998` — залишковий час життя запису в секундах до примусового видалення;
* `ESTABLISHED` — поточний стан кінцевого автомата TCP;
* `src=192.168.1.50 dst=93.184.216.34 sport=52140 dport=443` — оригінальний кортеж пакета;
* `src=93.184.216.34 dst=198.51.100.1 sport=443 dport=38421` — очікуваний кортеж відповіді з урахуванням NAT;
* `[ASSURED]` — прапорець, що підтверджує успішний двосторонній обмін трафіком (запис не буде видалено при першому наближенні до ліміту пам'яті).

### Розрахунок пам'яті та матриця таймаутів conntrack

Пам'ять таблиці conntrack обмежена параметром `net.netfilter.nf_conntrack_max`. Кожен запис сесії (`struct nf_conn`) займає у пам'яті ядра приблизно 320 байтів.

Для високонавантаженого сервера з `nf_conntrack_max = 1048576` (1 мільйон з'єднань) базова потреба в оперативній пам'яті складає:
```text
RAM = 1048576 * 320 байтів ≈ 335 МБ оперативної пам'яті незмінного пулу ядра (SLAB).
```

### Поведінкові моделі відображення та фільтрації NAT (RFC 4787 / RFC 5382)

Характер поведінки трансляторів NAT визначає, чи зможуть два клієнти встановити пряме однорангове з'єднання (P2P / WebRTC). Стандарти RFC 4787 (для UDP) та RFC 5382 (для TCP) класифікують NAT за двома незалежними осями:

#### 1. Поведінка відображення портів (NAT Mapping Behavior)

* **Endpoint-Independent Mapping (EIM / Full Cone)**: Всі пакети з локального сокета `192.168.1.50:5000`, незалежно від IP-адреси та порту призначення, транслюються в один і той самий публічний сокет `198.51.100.1:40000`. Найбільш сприятливий режим для встановлення прямих з'єднань.
* **Address-Dependent Mapping (ADM / Restricted Cone)**: Локальний сокет транслюється в `198.51.100.1:40000` лише під час зв'язку з конкретною цільовою IP-адресою `X`. Якщо клієнт звертається до IP `Y`, NAT виділяє новий зовнішній порт `40001`.
* **Address-and-Port-Dependent Mapping (APDM / Symmetric NAT)**: Новий зовнішній порт виділяється для кожної унікальної комбінації `(Destination IP, Destination Port)`. Пряме пробивання NAT (*NAT Hole Punching*) між двома клієнтами за симетричними NAT є математично неможливим без ретранслятора TURN.

#### 2. Поведінка фільтрації вхідного трафіку (NAT Filtering Behavior)

* **Endpoint-Independent Filtering (EIF)**: Будь-який вузол Інтернету може надіслати пакет на виділений публічний порт `198.51.100.1:40000`, і NAT перешле його локальному хосту.
* **Address-Dependent Filtering (ADF)**: Вхідний пакет пропускається лише тоді, коли локальний клієнт раніше надсилав хоча б один пакет на цю конкретну IP-адресу.
* **Address-and-Port-Dependent Filtering (APDF)**: Вхідний пакет пропускається лише тоді, коли клієнт попередньо відправляв пакет саме на цей `IP:Port`.

#### 3. Підтримка закольцьовування трафіку (NAT Hairpinning / Loopback)

Якщо клієнт `A` (`192.168.1.50`) намагається звернутися до сервера `B` (`192.168.1.60`), розташованого в тій самій локальній мережі, використовуючи його публічну IP-адресу `198.51.100.1:443`, пристрій із підтримкою **Hairpinning** розпізнає власну публічну адресу, коректно виконує подвійну трансляцію (DNAT + SNAT) і повертає пакети назад у внутрішній сегмент без виходу у зовнішню мережу провайдера. Якщо підтримка Hairpinning відсутня, з'єднання зависає з таймаутом.

### Механіка L7-проксі, CDN та систем фільтрації DPI

На рівні L7 проміжні пристрої повністю розбирають прикладні протоколи, реалізуючи складну бізнес-логіку:

#### 1. Зворотні проксі та CDN-вузли (Reverse Proxies & CDNs)

Зворотний проксі-сервер (Nginx, Envoy, HAProxy) повністю розриває клієнтське TCP/TLS-з'єднання:
* Здійснює узгодження версій HTTP через розширення TLS ALPN (*Application-Layer Protocol Negotiation*): вибирає `h2` (HTTP/2), `http/1.1` або `h3` (HTTP/3);
* Виконує перевірку та нормалізацію HTTP-заголовків: додає заголовки трасування `X-Forwarded-For`, `X-Forwarded-Proto`, `Forwarded` (RFC 7239) та `Via`. За відсутності належної фільтрації на першому граничному проксі зловмисник може інжектувати підроблені значення `X-Forwarded-For`, обходячи обмеження доступу за IP;
* Керує повторним використанням з'єднань до внутрішніх серверів (*Connection Pooling*): сотні клієнтських запитів передаються через єдиний постійно відкритий пул TCP-з'єднань до бекенду, мінімізуючи накладні витрати на повторні рукостискання;
* Кешує статичний контент на основі директив `Cache-Control` (`public`, `max-age`, `s-maxage`, `stale-while-revalidate`), валідуючи свіжість через заголовки `If-None-Match` (звірка хешу ETag) та `If-Modified-Since`.

#### 2. Міжмережеві екрани веб-застосунків (WAF) та сигнатурний аналіз DPI

Фаєрволи веб-застосунків (WAF) працюють як модулі всередині або перед L7-проксі:
* Токенізують тіло запиту (JSON, XML, Multipart form-data);
* Застосовують дерева регулярних виразів (наприклад, правила OWASP ModSecurity Core Rule Set) для виявлення SQL-ін'єкцій, міжсайтового скриптингу (XSS) та аномалій кодування символів;
* Використовують **відбитки TLS (TLS Fingerprinting / JA3 / JA4)**: аналізують точний порядок підтримуваних шифрів, розширень та еліптичних кривих у початковому пакеті `ClientHello`. Це дозволяє ідентифікувати автоматизовані боти та шкідливі утиліти навіть тоді, коли вони підробляють заголовок `User-Agent`.

#### 3. Обробка ранніх даних TLS 1.3 (0-RTT Early Data) та захист від атак повторення

При повторному встановленні сесії TLS 1.3 клієнт може надіслати корисні дані першого HTTP-запиту разом із повідомленням `ClientHello` ще до отримання відповіді від сервера (0-RTT). Оскільки зловмисник у мережі може перехопити цей перший зашифрований пакет і надіслати його повторно, проміжний L7-проксі зобов'язаний реалізувати механізм захисту від атак повторення (*Anti-Replay Single-Use Tickets*), кешувати унікальні ідентифікатори квитків або передавати бекенду заголовок `Early-Data: 1` (RFC 8470), забороняючи виконання неідempotентних запитів (таких як платіжні POST-транзакції) через 0-RTT.

### Системні параметри та сокетні опції для роботи в умовах Middlebox

Для запобігання деградації з'єднань через втручання проміжних пристроїв розробники системного програмного забезпечення налаштовують параметри сокетів через інтерфейс `setsockopt`. Порівняємо реалізацію мовами C та C++:

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

int configure_resilient_socket(int fd) {
    /* 1. Активація TCP Keepalive для утримання сесій у таблицях NAT */
    int keepalive = 1;
    if (setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &keepalive, sizeof(keepalive)) < 0) {
        return -1;
    }

    /* Час бездіяльності до першого зонду (25 с для запобігання скидання CGNAT) */
    int keepidle = 25;
    if (setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE, &keepidle, sizeof(keepidle)) < 0) {
        return -1;
    }

    /* Інтервал між повторними зондами */
    int keepintvl = 5;
    if (setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL, &keepintvl, sizeof(keepintvl)) < 0) {
        return -1;
    }

    /* Кількість невдалих зондів до розриву сокета */
    int keepcnt = 3;
    if (setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT, &keepcnt, sizeof(keepcnt)) < 0) {
        return -1;
    }

    /* 2. Увімкнення TCP Fast Open на клієнті (RFC 7413) */
    int fastopen = 1;
    setsockopt(fd, IPPROTO_TCP, TCP_FASTOPEN_CONNECT, &fastopen, sizeof(fastopen));

    /* 3. Вимкнення алгоритму Нейгла для мінімізації затримок на проміжних проксі */
    int nodelay = 1;
    if (setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &nodelay, sizeof(nodelay)) < 0) {
        return -1;
    }

    return 0;
}
```
```cpp
#include <iostream>
#include <expected>
#include <system_error>
#include <unistd.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

namespace netbox {

class SocketConfigurator {
public:
    enum class ErrorCode {
        KeepaliveFailed,
        IdleTimeoutFailed,
        IntervalFailed,
        CountFailed,
        NodelayFailed
    };

    static std::expected<void, ErrorCode> configure_resilient_socket(int fd) noexcept {
        // 1. Активація TCP Keepalive для утримання сесій у таблицях NAT
        int keepalive = 1;
        if (::setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &keepalive, sizeof(keepalive)) < 0) {
            return std::unexpected(ErrorCode::KeepaliveFailed);
        }

        // Час бездіяльності до першого зонду (25 с для запобігання скидання CGNAT)
        int keepidle = 25;
        if (::setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE, &keepidle, sizeof(keepidle)) < 0) {
            return std::unexpected(ErrorCode::IdleTimeoutFailed);
        }

        // Інтервал між повторними зондами
        int keepintvl = 5;
        if (::setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL, &keepintvl, sizeof(keepintvl)) < 0) {
            return std::unexpected(ErrorCode::IntervalFailed);
        }

        // Кількість невдалих зондів до розриву сокета
        int keepcnt = 3;
        if (::setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT, &keepcnt, sizeof(keepcnt)) < 0) {
            return std::unexpected(ErrorCode::CountFailed);
        }

        // 2. Увімкнення TCP Fast Open на клієнті (RFC 7413, опціонально)
        int fastopen = 1;
        ::setsockopt(fd, IPPROTO_TCP, TCP_FASTOPEN_CONNECT, &fastopen, sizeof(fastopen));

        // 3. Вимкнення алгоритму Нейгла для мінімізації затримок на проміжних проксі
        int nodelay = 1;
        if (::setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &nodelay, sizeof(nodelay)) < 0) {
            return std::unexpected(ErrorCode::NodelayFailed);
        }

        return {};
    }
};

} // namespace netbox
```

### Керування поведінкою стека ядра Linux через sysctl

Для системних адміністраторів та DevOps-інженерів підсистема `sysctl` надає низькорівневі важелі адаптації стека до умов агресивного фільтрування провайдерів:

```bash
# Увімкнення виявлення MTU без використання ICMP (PLPMTUD, RFC 4821)
# 0 = вимкнено, 1 = вмикається автоматично при виявленні чорної діри, 2 = увімкнено постійно
sudo sysctl -w net.ipv4.tcp_mtu_probing=1

# Базовий розмір MSS при пошуку чорних дір MTU (рекомендовано 1024 або 536 байтів)
sudo sysctl -w net.ipv4.tcp_base_mss=1024

# Дозвіл безпечного повторного використання сокетів у стані TIME_WAIT для вихідних з'єднань NAT
sudo sysctl -w net.ipv4.tcp_tw_reuse=1

# Контроль генерації часових міток TCP (RFC 7323)
# Деякі застарілі фаєрволи блокують пакети зі зміщеними timestamps
sudo sysctl -w net.ipv4.tcp_timestamps=1

# Збільшення максимального розміру таблиці conntrack для уникнення переповнення при SYN-flood
sudo sysctl -w net.netfilter.nf_conntrack_max=1048576

# Зменшення часу утримання стану TCP ESTABLISHED на навантажених шлюзах (замість 5 діб)
sudo sysctl -w net.netfilter.nf_conntrack_tcp_timeout_established=3600
```
