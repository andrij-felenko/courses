# 📋 Довідник двійкових структур кадру Ethernet

Довідник містить точні двійкові зміщення, бітові маски, числові константи, інваріанти пам'яті та сигнатури структур даних мовами C і C++ для розбору заголовків кадру Ethernet II (DIX), розширень IEEE 802.3 LLC/SNAP, тегів віртуальних локальних мереж IEEE 802.1Q і IEEE 802.1ad (QinQ). Окремі розділи розбирають системне вирівнювання структур у пам'яті, правила фільтрації в сокетах Linux, взаємодію з апаратними механізмами розвантаження мережевих карт (Hardware Offloading) та крайові аномалії обробки канальних заголовків.

### 1. Двійкова розкладка заголовка Ethernet II (DIX)

Заголовок Ethernet II є базовою одиницею канального рівня для переважної більшості протоколів сучасного інтернету. Він займає рівно 14 байтів у пам'яті та складається з трьох обов'язкових полів: 6-байтової адреси призначення, 6-байтової адреси джерела та 2-байтового коду протоколу вищого рівня EtherType.

Усі багатобайтові числові значення в заголовках Ethernet передаються фізичним каналом у порядку від старшого байта до молодшого (Big-Endian, або Network Byte Order). Це означає, що при отриманні сирого буфера на процесорах архітектури x86 або ARM (у режимі Little-Endian) 16-бітні поля потребують явного перетворення порядку байтів за допомогою системних функцій `ntohs()` або компіляторних вбудованих функцій розвороту байтів.

| Зміщення (Hex) | Зміщення (Dec) | Розмір (байти) | Поле структури | Тип даних C/C++ | Призначення та діапазон значень |
|---|---|---|---|---|---|
| `0x00` – `0x05` | 0 – 5 | 6 | `dst_mac` | `uint8_t[6]` | MAC-адреса отримувача (Unicast, Multicast або Broadcast) |
| `0x06` – `0x0B` | 6 – 11 | 6 | `src_mac` | `uint8_t[6]` | MAC-адреса відправника (завжди індивідуальна Unicast-адреса) |
| `0x0C` – `0x0D` | 12 – 13 | 2 | `ethertype` | `uint16_t` | Код протоколу вищого рівня (`>= 0x0600`) у Big-Endian порядку |
| `0x0E` – `...` | 14 – `...` | 46 – 1500 | `payload` | `uint8_t[]` | Корисні дані (IP-пакет, кадр ARP тощо) разом із заповненням |
| `Кінець - 4` | Залежить | 4 | `fcs` | `uint32_t` | Контрольна сума кадру CRC-32 (накриває поля `0x00` ... `payload`) |

Перший переданий байт кадру (`dst_mac[0]`) містить два критично важливі апаратні біти конфігурації адресації:
* **Біт 0 (молодший біт першого байта, I/G — Individual/Group):** визначає тип доставки кадру. Значення `0` позначає індивідуальну адресу (Unicast), яку обробляє лише один конкретний мережевий інтерфейс. Значення `1` вказує на групову або широкомовну адресу (Multicast/Broadcast), яку мають прийняти всі зацікавлені вузли сегмента.
* **Біт 1 (другий біт першого байта, U/L — Universal/Local):** визначає статус адміністрування адреси. Значення `0` позначає глобально унікальну адресу, вшиту виробником за ліцензією IEEE OUI. Значення `1` позначає локально адміністровану адресу, призначену системним адміністратором, гіпервізором віртуалізації чи емулятором (наприклад, віртуальними машинами KVM або контейнерами Docker).

### 2. Заголовок IEEE 802.3 з підрівнями LLC та SNAP

Якщо 16-бітне поле на зміщенні 12 містить значення, що не перевищує 1500 (`0x05DC`), кадр інтерпретується як формат IEEE 802.3. У цьому разі поле позначає точну кількість байтів, що містяться в полі даних кадру (включаючи заголовки підрівня LLC).

Для передачі довільних мережевих протоколів поверх IEEE 802.3 застосовується стек із 3-байтового заголовка логічного зв'язку IEEE 802.2 LLC та 5-байтового заголовка протоколу доступу до підмережі SNAP.

| Зміщення (Hex) | Розмір (байти) | Поле | Стандартне значення | Призначення |
|---|---|---|---|---|
| `0x00` – `0x0B` | 12 | `mac_addrs` | 6 Б + 6 Б | MAC-адреси отримувача та відправника |
| `0x0C` – `0x0D` | 2 | `length` | `<= 1500` (`0x05DC`) | Довжина наступних полів у байтах |
| `0x0E` | 1 | `dsap` | `0xAA` | Destination Service Access Point (SNAP Header) |
| `0x0F` | 1 | `ssap` | `0xAA` | Source Service Access Point (SNAP Header) |
| `0x10` | 1 | `control` | `0x03` | Unnumbered Information (UI) — непідтверджена передача |
| `0x11` – `0x13` | 3 | `oui` | `0x000000` | Organizationally Unique Identifier (0x000000 для протоколів Ethernet) |
| `0x14` – `0x15` | 2 | `protocol_id` | `0x0800`, `0x86DD`... | 16-бітний код EtherType вкладеного протоколу (ідентичний до DIX) |
| `0x16` – `...` | 38 – 1492 | `payload` | Байтовий потік | Корисне навантаження (максимальний MTU 1492 байти) |
| `Кінець - 4` | 4 | `fcs` | `uint32_t` | Контрольна послідовність кадру CRC-32 |

Через додавання 8 байтів заголовків LLC/SNAP максимальний розмір корисних даних для мережевого рівня скорочується з 1500 до 1492 байтів. Якщо кінцевий вузол формує IP-пакет розміром 1500 байтів, він не зможе поміститися в такий кадр без канальної або мережевої фрагментації.

### 3. Теги віртуальних мереж: IEEE 802.1Q та IEEE 802.1ad (QinQ)

Тегування віртуальних локальних мереж здійснюється шляхом вставки 4-байтового блоку даних між адресою джерела `src_mac` та оригінальним полем `ethertype`.

Прийомний пристрій розпізнає наявність тега за константою `0x8100` у перших двох байтах вставки. Для комутатора або операційної системи ця константа сигналізує, що наступні два байти містять службову інформацію керування тегом (TCI), а справжній код протоколу вищого рівня зміщений на 4 байти вперед (на зміщення `0x10`).

```
Зміщення:  0x00      0x06      0x0C      0x0E      0x10           Кінець - 4
Кадр:     [Dst MAC] [Src MAC] [  TPID ] [  TCI  ] [EtherType] ... [   FCS   ]
Розмір:     6 Б       6 Б       2 Б       2 Б       2 Б             4 Б
                               \_______________/
                                802.1Q Tag (4 Б)
```

Детальна бітова структура 16-бітного поля TCI (Tag Control Information) складається з трьох незалежних компонентів:

| Компонент TCI | Біти поля | Маска (Hex) | Зсув бітів | Опис та діапазон значень |
|---|---|---|---|---|
| **PCP** (*Priority Code Point*) | 3 біти (`15..13`) | `0xE000` | `>> 13` | Рівень пріоритету трафіку IEEE 802.1p від `0` (найнижчий) до `7` (найвищий). |
| **DEI / CFI** (*Drop Eligible*) | 1 біт (`12`) | `0x1000` | `>> 12` | Drop Eligible Indicator. При значенні `1` комутатор за умов перевантаження черг дропає цей кадр першим. |
| **VID** (*VLAN Identifier*) | 12 бітів (`11..0`) | `0x0FFF` | `& 0x0FFF` | Номер віртуальної мережі. Діапазон значень: від `0` до `4095`. |

Спеціальні значення ідентифікатора VLAN (VID):
* `0x000` (0) — кадр пріоритету (Priority Tagged Frame). Кадр не належить до жодного конкретного VLAN, але несе інформацію про пріоритет QoS у полі PCP.
* `0x001` (1) — типова віртуальна мережа за замовчуванням (Default VLAN), до якої належать усі неналаштовані порти комутаторів.
* `0x002` – `0xFFE` (2 – 4094) — діапазон стандартних користувацьких VLAN для розділення широкомовних доменів.
* `0xFFF` (4095) — зарезервоване значення стандарту IEEE 802.1Q, не використовується для передачі користувацького трафіку (часто використовується для внутрішніх потреб комутаційних матриць або списків контролю доступу).

У провайдерських мережах використовується розширення IEEE 802.1ad (подвійне тегування, або QinQ). У такий кадр послідовно вкладаються два теги:
1. **Зовнішній тег провайдера (Service Tag, S-Tag):** має TPID = `0x88A8` та власний S-VID для маршрутизації всередині магістральної мережі оператора.
2. **Внутрішній тег клієнта (Customer Tag, C-Tag):** має TPID = `0x8100` та клієнтський C-VID, що залишається прозорим для провайдера.
Сумарний оверхед заголовків збільшується до 22 байтів, а максимальний кадр на магістральних транках досягає щонайменше 1526 байтів.

### 4. Реєстр кодів протоколів EtherType

Коди EtherType реєструються організацією IEEE Standards Association. Значення в діапазоні від `0x0600` (1536) до `0xFFFF` однозначно ідентифікують вкладений протокол.

| EtherType (Hex) | EtherType (Dec) | Офіційна назва протоколу | Опис та сфера застосування |
|---|---|---|---|
| `0x0800` | 2048 | **IPv4** | Протокол Internet Protocol версії 4 (RFC 791, RFC 894) |
| `0x0806` | 2054 | **ARP** | Протокол перетворення IP-адрес на MAC-адреси (RFC 826) |
| `0x8035` | 32821 | **RARP** | Зворотний ARP для завантаження бездискових станцій (RFC 903) |
| `0x8100` | 33024 | **IEEE 802.1Q** | Тегування VLAN та класів пріоритету IEEE 802.1p |
| `0x86DD` | 34525 | **IPv6** | Протокол Internet Protocol версії 6 (RFC 2464) |
| `0x8808` | 34824 | **Flow Control** | Кадри керування паузою передачі (PAUSE frames, IEEE 802.3x) |
| `0x8847` | 34887 | **MPLS Unicast** | Мультипротокольна комутація міток для одноадресного трафіку (RFC 3032) |
| `0x8848` | 34888 | **MPLS Multicast** | Мультипротокольна комутація міток для групового трафіку |
| `0x8863` | 34915 | **PPPoE Discovery** | Етап виявлення тунелів PPP over Ethernet (RFC 2516) |
| `0x8864` | 34916 | **PPPoE Session** | Передача корисних даних у встановленій сесії PPPoE |
| `0x888E` | 34958 | **EAPOL (802.1X)** | Автентифікація користувачів та портів на канальному рівні |
| `0x88A8` | 34984 | **IEEE 802.1ad** | Провайдерські теги VLAN (QinQ Service Tag) |
| `0x88CC` | 35020 | **LLDP** | Протокол виявлення сусідніх пристроїв (Link Layer Discovery Protocol, 802.1AB) |
| `0x88E5` | 35045 | **MACsec (802.1AE)** | Апаратне шифрування та автентифікація канального рівня |
| `0x88F7` | 35063 | **PTP (IEEE 1588)** | Протокол точної синхронізації часу на апаратному рівні (Precision Time Protocol) |

### 5. Зарезервовані та групові MAC-адреси

Групові MAC-адреси (Multicast) відрізняються одиничним значенням молодшого біта першого байта (`01:xx:xx:...`). Прийом таких кадрів вимагає налаштування апаратних фільтрів хеш-таблиці мережевої карти.

| Діапазон / Адреса | Призначення | Механізм формування та використання |
|---|---|---|
| `FF:FF:FF:FF:FF:FF` | **Broadcast** | Широкомовний кадр для всіх вузлів локального домену колізій/VLAN. Обробляється центральним процесором кожного підключеного вузла. |
| `01:00:5E:00:00:00` – `01:00:5E:7F:FF:FF` | **IPv4 Multicast** | Адреси стандарту IANA (RFC 1112). Старші 25 бітів фіксовані (`01:00:5E` + нульовий біт), молодші 23 біти копіюються з молодших 23 бітів IP-адреси групи. Через згортання 28 бітів IPv4 у 23 біти MAC виникає 32-кратна неоднозначність (32 різні IP-групи ділять один MAC). |
| `33:33:00:00:00:00` – `33:33:FF:FF:FF:FF` | **IPv6 Multicast** | Стандарт RFC 2464. Старші два байти завжди `33:33`, молодші 4 байти (32 біти) точно відповідають молодшим 32 бітам адреси IPv6 Multicast (зокрема Solicited-Node Multicast). |
| `01:80:C2:00:00:00` | **STP / RSTP BPDU** | Мостові кадри Spanning Tree Protocol (IEEE 802.1D). Згідно зі стандартом, керовані комутатори ніколи не повинні ретранслювати цей кадр на інші порти — він обробляється локально процесором комутатора. |
| `01:80:C2:00:00:01` | **802.3x Flow Control** | Кадри призупинення передачі (PAUSE frames). Зупиняють передавач протилежного боку лінка на вказану кількість квантів часу. |
| `01:80:C2:00:00:02` | **LACP (802.3ad)** | Link Aggregation Control Protocol та повільні службові протоколи (Slow Protocols) для об'єднання фізичних портів у логічний транк. |
| `01:80:C2:00:00:0E` | **LLDP (802.1AB)** | Кадри топологічного виявлення сусідніх пристроїв. Не ретранслюються стандартними комутаторами. |
| `01:1B:19:00:00:00` | **PTPv2 over L2** | Повідомлення Precision Time Protocol (IEEE 1588) під час роботи безпосередньо поверх Ethernet без обгортки UDP/IP. |

### 6. Системні структури даних ядра Linux та вирівнювання пам'яті

В операційних системах сімейства POSIX/Linux структури кадру Ethernet визначені в системних заголовках `<linux/if_ether.h>` (рівень ядра та UAPI) та `<net/ethernet.h>` (простір користувача C-бібліотеки glibc/musl).

Головна архітектурна проблема розбору канальних кадрів у пам'яті — **непарне вирівнювання (Unaligned Memory Access)**.
Заголовок Ethernet займає рівно 14 байтів. Якщо базовий буфер у пам'яті починається з адреси, кратної 4 або 8 байтам (наприклад, зміщення `0x00`), то початок вкладеного IP-заголовка припадає на зміщення `14` (`0x0E`). Число 14 не ділиться на 4.

У результаті всі 32-бітні поля заголовка IP (IP-адреса джерела, IP-адреса отримувача) опиняються зміщеними на 2 байти відносно природних 4-байтових меж пам'яті.
* На апаратних платформах із суворою перевіркою вирівнювання (старі процесори ARMv5/ARMv6, MIPS, SPARC) пряме розіменування вказівника `uint32_t*` на адресу `buffer + 14` породжувало апаратне переривання вирівнювання (`Alignment Fault`) або аварійне завершення процесу сигналом `SIGBUS`.
* На сучасних процесорах x86-64 та ARM64 непарний доступ підтримується апаратно, але призводить до додаткових мікрооперацій кешу, знижуючи швидкість потокової обробки пакетів на швидкостях 10G/40G/100G.

Для подолання цієї аномалії драйвери мережевих карт ядра Linux під час виділення сокетного буфера `sk_buff` викликають спеціальну процедуру зміщення: `skb_reserve(skb, NET_IP_ALIGN);` (де макрос `NET_IP_ALIGN` дорівнює 2 на більшості архітектур).
Мережевий адаптер записує L2-кадр через DMA починаючи з адреси `buffer + 2`. Тоді 14 байтів заголовка Ethernet займають інтервал від 2 до 16 байтів, а наступний IP-заголовок починається точно з 16-го байта — адреси, ідеально вирівняної за межею 4, 8 та 16 байтів. Це забезпечує максимальну продуктивність векторних інструкцій SIMD під час парсингу IP та TCP.

### 7. Фільтрація канальних кадрів та BPF у сокетах Linux

Прийом і фільтрація сирих Ethernet-кадрів у просторі користувача здійснюються через сирі сокети родини `AF_PACKET`: виклик `socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL))` відкриває прямий доступ до каналу. Параметр `SOCK_RAW` передає користувачеві кадр разом із канальним заголовком Ethernet, тоді як режим `SOCK_DGRAM` автоматично зрізає 14 байтів заголовка й залишає лише IP-навантаження.

Для фільтрації трафіку без перемикання контексту ядра використовується класичний фільтр BPF (Berkeley Packet Filter), що підключається системним викликом `setsockopt(fd, SOL_SOCKET, SO_ATTACH_FILTER, ...)`. Фільтр BPF компілюється в компактний набір інструкцій віртуальної машини ядра:
* `BPF_LD + BPF_H + BPF_ABS` на зміщенні 12: завантажує 2 байти поля EtherType в акумулятор.
* `BPF_JMP + BPF_JEQ`: порівнює завантажене значення з кодом протоколу (наприклад, `0x0800` для IPv4).
* Якщо умова виконується, фільтр повертає кількість байтів для збереження (`BPF_RET`); якщо ні — повертає `0`, і ядро миттєво відкидає кадр без копіювання в простір користувача.

Крім того, мережевий інтерфейс може працювати в трьох різних апаратних режимах прийому адрес:
1. **Звичайний режим (Normal/Directed):** NIC приймає лише кадри зі своїм власним MAC, широкомовні кадри `FF:FF:FF:FF:FF:FF` та зареєстровані Multicast-групи.
2. **All-Multicast (`IFF_ALLMULTI`):** NIC вимикає фільтрацію групових адрес і передає в драйвер усі Multicast-кадри сегмента.
3. **Нерозбірливий режим (Promiscuous Mode, `IFF_PROMISC`):** апаратний фільтр MAC-адрес повністю вимикається. Мережева карта пересилає в ОС абсолютно всі кадри, зафіксовані на фізичному кабелі, незалежно від адреси отримувача (режим роботи утиліт `tcpdump` та Wireshark).

### 8. Апаратні механізми розвантаження (Hardware Offloading)

Сучасні високошвидкісні мережеві адаптери перебирають на себе значну частину функцій обробки кадру для звільнення центрального процесора:
* **RX Checksum Offload (FCS / L3 / L4 Checksum):** апаратний блок обчислює контрольну суму CRC-32 на льоту під час зчитування бітів із середовища. Якщо контрольна сума зіпсована, кадр скидається на рівні кремнію контролера й навіть не потрапляє в пам'ять хоста. При успішній перевірці адаптер встановлює прапор у RX-дескрипторі DMA і за потреби відкидає 4 байти FCS перед записом кадру в системну RAM.
* **VLAN Hardware Stripping / Insertion:** під час прийому тегованого кадру 802.1Q мережева карта апаратно видаляє 4 байти тега з потоку даних і записує значення VID та PCP в окреме метадане поле дескриптора пакета (`skb->vlan_tci`). При передачі карта навпаки апаратно вставляє тег перед відправкою в кабель. Це створює важливий підводний камінь для діагностичних утиліт: при увімкненому розвантаженні сирий сокет може бачити кадри без тега 802.1Q, оскільки тег знято залізом до того, як кадр дійшов до підсистеми `AF_PACKET`.
* **TSO (TCP Segmentation Offload) та LRO (Large Receive Offload):** стек ОС формує один великий буфер розміром до 64 КБ (Superpacket), а мережевий чип самостійно нарізає його на стандартні кадри Ethernet з MTU 1500 байтів, реплікуючи MAC- та IP-заголовки й обчислюючи окрему CRC-32 для кожного згенерованого кадру.

### 9. Крайові аномалії та безпека канального рівня

Під час практичного аналізу мережевих дампів розробники стикаються з нестандартними категоріями кадрів:
* **Runt Frames:** кадри, довжина яких менша за мінімальні 64 байти (зазвичай внаслідок колізій CSMA/CD у напівдуплексних мережах або апаратних збоїв кабелю). Стандартні контролери відкидають їх як биті пакети (`rx_length_errors`).
* **Giants / Jabbers:** кадри, довжина яких перевищує максимально допустимий розмір MTU (понад 1518/1522 байти у стандартних мережах без підтримки Jumbo Frames). Кадри, що передаються неперервно через заклинювання передавача (Jabber), блокуються апаратним таймером фізичного рівня PHY.
* **VLAN Hopping (Double Tagging Attack):** вектор атаки на безпеку комутаторів, що використовує особливості обробки подвійних тегів. Якщо зловмисник надсилає кадр із двома тегами (зовнішній — свій рідний Native VLAN, внутрішній — цільовий ізольований VLAN), комутатор на транковому порті знімає перший тег відповідно до стандарту 802.1Q і пересилає кадр далі. Наступний комутатор читає другий тег і доставляє кадр у чужий VLAN, порушуючи ізоляцію мереж. Захист полягає в обов'язковому тегуванні Native VLAN на всіх магістральних транках або призначенні невикористовуваного фіктивного VID для рідного VLAN.

### 10. Високопродуктивна обробка кадру в eBPF XDP

У сучасній архітектурі Linux ядра найшвидша обробка Ethernet-кадрів відбувається на рівні **XDP (eXpress Data Path)** безпосередньо в кільці дескрипторів драйвера мережевої карти до виділення сокетного буфера `sk_buff` і до виклику підсистеми пам'яті ядра.

Програма XDP отримує контекст `struct xdp_md`, що містить два прямі вказівники на пам'ять DMA: `data` (початок кадру Ethernet) та `data_end` (кінець отриманого кадру). Оскільки верифікатор ядра Linux (eBPF Verifier) суворо гарантує безпеку доступу до пам'яті, розробник зобов'язаний перед кожним зверненням до полів кадру явно довести компілятору виконання умови `data + sizeof(struct eth_hdr) <= data_end`. Якщо розмір недостатній, повертається `XDP_DROP`.

На рівні XDP програма може миттєво прийняти одне з рішень:
1. `XDP_DROP` — миттєве відкидання кадру в кремнії/драйвері (наприклад, для захисту від DDoS-атак зі швидкістю до 24 мільйонів пакетів на секунду на одне процесорне ядро).
2. `XDP_TX` — зворотне відправлення кадру в той самий порт (L2-відбивач або балансувальник навантаження із заміною MAC-адрес).
3. `XDP_REDIRECT` — перенаправлення в інший фізичний інтерфейс або в сокет простору користувача AF_XDP (Zero-Copy Packet Processing).
4. `XDP_PASS` — передача кадру стандартному мережевому стеку ядра Linux для повноцінної маршрутизації та обробки TCP/IP.

#include <cstdint>
#include <array>
#include <span>
#include <bit>
#include <string>
#include <format>

namespace net {

inline constexpr std::size_t mac_address_len = 6;
inline constexpr std::size_t ethernet_header_len = 14;
inline constexpr std::size_t vlan_tag_len = 4;
inline constexpr std::size_t min_frame_len = 64;
inline constexpr std::size_t max_standard_frame_len = 1518;
inline constexpr std::size_t fcs_len = 4;

enum class ether_type : uint16_t {
    ipv4  = 0x0800,
    arp   = 0x0806,
    vlan  = 0x8100,
    ipv6  = 0x86DD,
    qinq  = 0x88A8,
    lldp  = 0x88CC,
    ptp   = 0x88F7
};

using mac_address = std::array<uint8_t, mac_address_len>;

#pragma pack(push, 1)
struct eth_header {
    mac_address dst_mac;
    mac_address src_mac;
    uint16_t    ethertype_be;

    [[nodiscard]] ether_type type() const noexcept {
        uint16_t host_val = (std::endian::native == std::endian::big)
            ? ethertype_be
            : std::byteswap(ethertype_be);
        return static_cast<ether_type>(host_val);
    }

    [[nodiscard]] bool is_multicast() const noexcept {
        return (dst_mac[0] & 0x01) != 0;
    }

    [[nodiscard]] bool is_broadcast() const noexcept {
        return dst_mac == mac_address{0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF};
    }

    [[nodiscard]] bool is_local_admin() const noexcept {
        return (dst_mac[0] & 0x02) != 0;
    }

    [[nodiscard]] std::string format_dst() const {
        return std::format("{:02X}:{:02X}:{:02X}:{:02X}:{:02X}:{:02X}",
            dst_mac[0], dst_mac[1], dst_mac[2], dst_mac[3], dst_mac[4], dst_mac[5]);
    }
};

struct vlan_header {
    uint16_t tpid_be;
    uint16_t tci_be;

    [[nodiscard]] uint16_t tci() const noexcept {
        return (std::endian::native == std::endian::big)
            ? tci_be
            : std::byteswap(tci_be);
    }

    [[nodiscard]] uint8_t pcp() const noexcept  { return static_cast<uint8_t>((tci() >> 13) & 0x07); }
    [[nodiscard]] bool dei() const noexcept     { return ((tci() >> 12) & 0x01) != 0; }
    [[nodiscard]] uint16_t vid() const noexcept { return tci() & 0x0FFF; }
};
#pragma pack(pop)

} // namespace net
