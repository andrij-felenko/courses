Коли електричний сигнал надходить у приймальний тракт мережевої карти, трансивер бачить лише неперервний потік змін напруги або оптичних імпульсів. У цьому фізичному потоці немає вбудованих пауз між байтами, немає позначок початку повідомлення і немає гарантії, що біти дійшли без спотворень. Якщо один комп'ютер почне передавати байти даних без попередньої домовленості про структуру, приймач не зможе визначити, де закінчується фоновий шум лінії, з якого саме біта починається адреса отримувача і чи належить переданий фрагмент поточному пакету. Щоб перетворити хаотичний потік сигналів на надійний канал обміну даними, фізичний потік бітів структурують у фіксовані порції — **кадри** (англ. *frames*). Кадр канального рівня Ethernet є тим базовим «конвертом», у який пакуються всі пакети глобального інтернету.

### Проблема неперервного сигналу: як виділити межі передачі

Будь-яка передача даних кабелем [витої пари](book:communications/utp-cable) або оптоволокном починається з фундаментальної фізичної проблеми: тактові генератори передавача й приймача ніколи не збігаються ідеально. Навіть високоточні кварцові резонатори мають похибку частоти в кілька десятків часток на мільйон (ppm). Якщо передавати мільйони бітів підряд без підстроювання, приймач неминуче зсунеться по фазі й прочитає один біт двічі або пропустить його. Крім того, лінія зв'язку в моменти спокою перебуває під впливом теплових шумів та наведених завад.

Щоб приймач міг «захопити» тактову частоту сигналу й точно визначити момент початку першого байта адреси, кожен кадр Ethernet відкривається службовим блоком фізичного рівня з 8 байтів:

1. **Преамбула (Preamble, 7 байтів):** послідовність із 56 бітів, у якій чергуються одиниці та нулі — `10101010` (шістнадцяткове значення `0xAA`). На фізичному рівні цей шаблон формує ідеальний прямокутний меандр із максимальною частотою перемикання. Проходячи крізь приймач, цей сигнал змушує схему фазового автопідстроювання частоти (англ. *Phase-Locked Loop*, PLL) миттєво підлаштувати внутрішній тактовий генератор під частоту й фазу передавача. До кінця сьомого байта приймач повністю синхронізований із потоком бітів.
2. **Розділювач початку кадру (Start Frame Delimiter, SFD, 1 байт):** байт зі значенням `10101011` (`0xAB`). Перші шість бітів продовжують чергування `101010`, а останні два біти — дві одиниці підряд `11` — різко ламають періодичний шаблон. Цей перепад є апаратним тригером: він сигналізує приймачу, що фазове підстроювання завершено, преамбула закінчилася, і наступний біт є найпершим бітом адреси призначення кадру канального рівня.

```
Фізичний дріт: [ 0xAA 0xAA 0xAA 0xAA 0xAA 0xAA 0xAA ] [ 0xAB ] [ Початок кадру L2 ... ]
Біти на дроті:   10101010 ... (56 бітів меандру)       10101011
Призначення:   Синхронізація генератора PLL         Маркер SFD
```

Усі байти кадру передаються фізичним каналом **молодшим бітом уперед (LSB-first)** у межах кожного окремого байта. Тобто байт `0xAB` (`10101011` у двійковому записі від старшого біта до молодшого) передається на дріт як послідовність: `1`, потім `1`, потім `0`, `1`, `0`, `1`, `0`, `1`. Щойно логіка контролера фіксує послідовність двох одиниць, апаратний серіалізатор/десеріалізатор (SerDes) перемикається в режим накопичення байтів і починає записувати байти заголовка в приймальний буфер.

Преамбула та SFD генеруються передавальним чипом фізичного рівня (PHY) і поглинаються приймальним чипом PHY. Вони не зберігаються в пам'яті комп'ютера, не враховуються під час обчислення довжини кадру в операційній системі й не доступні користувацьким програмам через сокети.

![Анатомія кадру Ethernet II на фізичному дроті](/book/communications/networks/ethernet-frame/img/ethernet-frame-anatomy.svg)
*Повна структура передачі Ethernet II: фізична преамбула (7 Б) та SFD (1 Б) відкривають передачу, канальний заголовок (14 Б) несе MAC-адреси та EtherType, корисне навантаження (46–1500 Б) містить L3-пакет, а FCS (4 Б) замикає кадр. Між сусідніми передачами витримується обов'язковий інтервал IFG (12 байт-часів).*

### Анатомія кадру Ethernet II: поля, зміщення та адресація

Кадр канального рівня (L2 Frame) починається безпосередньо після байта SFD. У загальноприйнятому стандарті **Ethernet II** (відомому також як стандарт консорціуму DIX — Digital, Intel, Xerox) заголовок має довжину рівно 14 байтів і складається з трьох полів.

**1. MAC-адреса отримувача (Destination MAC, 6 байтів).**
Адреса призначення завжди стоїть на першому місці в кадрі. Таке розташування — фундаментальне інженерне рішення для високошвидкісної комутації. Коли кадр надходить у порт комутатора, процесор комутаційної матриці зчитує перші 6 байтів і миттєво шукає вихідний порт у своїй таблиці MAC-адрес (CAM-таблиці).

Завдяки тому, що адреса стоїть на самому початку, комутатор може застосовувати різні режими пересилання:
* **Наскрізна комутація (Cut-Through Switching):** комутатор зчитує лише перші 6 байтів MAC призначення й негайно починає передавати байти кадру у вихідний порт ще до того, як решта кадру фізично добіжить по кабелю. Затримка передачі становить менше 1 мікросекунди незалежно від розміру пакета. Головний недолік — комутатор ретранслює пошкоджені кадри, оскільки перевірити контрольну суму FCS у хвості кадру він ще не може.
* **Комутація з проміжним зберіганням (Store-and-Forward):** комутатор повністю зчитує весь кадр у внутрішній буфер, обчислює CRC-32, звіряє з полем FCS і лише в разі повної цілісності пересилає його далі. Це повністю очищає мережу від сміття та помилок, але додає затримку, пропорційну довжині кадру (близько 12 мікросекунд для 1500 байтів на гігабітному лінку).
* **Безфрагментна комутація (Fragment-Free):** компромісний режим, за якого комутатор витримує паузу рівно до зчитування перших 64 байтів (кванту часу Slot Time). Якщо за перші 64 байти не сталося колізії, кадр гарантовано не є уламком зіткнення, і комутатор починає передачу у вихідний порт, не чекаючи завантаження всього корисного навантаження.

Перший переданий байт адреси призначення (`dst_mac[0]`) містить два апаратні біти-прапорці:
* **Молодший біт (біт 0, I/G — Individual/Group):** визначає тип адресації. Якщо біт дорівнює `0`, це індивідуальна адреса (Unicast). Якщо біт дорівнює `1`, це групова адреса (Multicast) або широкомовна адреса (`FF:FF:FF:FF:FF:FF`). Мережева карта перевіряє цей біт найпершим: якщо кадр одноадресний і MAC не збігається з власною адресою карти, залізо скидає прийом решти кадру, не турбуючи центральний процесор перериваннями.
* **Другий біт (біт 1, U/L — Universal/Local):** визначає статус унікальності. `0` — глобально унікальна адреса, зашита виробником на заводі за ліцензією IEEE. `1` — локально адміністрована адреса, призначена адміністратором вручну або згенерована віртуальною машиною.

**2. MAC-адреса джерела (Source MAC, 6 байтів).**
Містить апаратну адресу вузла, який відправив цей кадр. Комутатори використовують це поле для автоматичного навчання топології (*MAC Learning*): фіксують, з якого саме фізичного порту надійшов кадр із цією адресою, і вносять запис у таблицю комутації. Адреса джерела завжди має бути індивідуальною (Unicast, біт I/G = `0`).

**3. Поле EtherType / Довжина (2 байти).**
Розташоване на зміщенні `0x0C` (12-й байт від початку L2-кадру). У форматі Ethernet II це поле позначає числовий код протоколу вищого (мережевого) рівня, чий пакет упаковано всередині кадру.
Найпоширеніші значення поля `EtherType`:
* `0x0800` — протокол **IPv4**;
* `0x0806` — протокол розпізнавання адрес **ARP**;
* `0x86DD` — протокол **IPv6**;
* `0x8100` — наявність тега віртуальної мережі **IEEE 802.1Q (VLAN)**;
* `0x88A8` — провайдерський тег **IEEE 802.1ad (QinQ)**.

Повний перелік бінарних зміщень, масок та кодів зафіксовано в [довіднику двійкових структур кадру](book:communications/ethernet-frame/api-frame-headers.md).

> 🔧 **Навіщо це.** Поле `EtherType` забезпечує демультиплексування протоколів усередині операційної системи. Мережева карта не повинна вгадувати, що лежить усередині кадру: драйвер ядра читає два байти на зміщенні 12 і викликає відповідний обробник — `ip_rcv()` для `0x0800` або `arp_rcv()` для `0x0806`. Якщо надійде невідомий протокол, ядро миттєво відкине кадр без розбору даних.

![Ethernet II проти IEEE 802.3 LLC/SNAP](/book/communications/networks/ethernet-frame/img/dix-vs-8023.svg)
*Порівняння форматів: Ethernet II вкладає IP-пакет напряму після 2 байтів EtherType. Формат IEEE 802.3 замість типу несе довжину, вимагаючи 8 додаткових байтів LLC/SNAP. Демаркаційна межа 1536 (0x0600) дозволяє розрізняти обидва формати на льоту.*

### Межа 1536: співіснування Ethernet II та IEEE 802.3

На початку 1980-х років між розробниками промислового стандарту Ethernet II (консорціумом DIX) та комітетом стандартизації IEEE 802 виник конфлікт архітектурних філософій. Комітет IEEE намагався уніфікувати локальні мережі під еталонну модель OSI й замінив поле `EtherType` на поле **довжини (Length)**, яке вказувало кількість байтів у полі даних. Інформація про сам протокол виносилася в додатковий 8-байтовий заголовок підрівнів LLC (IEEE 802.2) та SNAP.

Детально історію цього протистояння та причини перемоги формату DIX розкрито у вставці [Від коаксіального кабелю до стандарту: як DIX переміг комітет IEEE](book:communications/ethernet-frame/hist-dix-to-ieee.md).

Щоб сучасне мережеве обладнання могло приймати обидва типи кадрів без ручного налаштування, діє єдине математичне правило демаркації, затверджене стандартом IEEE 802.3x-1997:

```
Значення 2 байтів на зміщенні 12:
  <= 1500 (0x05DC) ──> Інтерпретується як ДОВЖИНА (IEEE 802.3 з заголовком LLC/SNAP)
  >= 1536 (0x0600) ──> Інтерпретується як ETHERTYPE (Ethernet II / DIX)
```

Оскільки максимальний розмір стандартного поля даних становить 1500 байтів, значення поля Length ніколи не перевищує 1500. А всі коди `EtherType` починаються від 1536 (`0x0600`). Діапазон значень від 1501 до 1535 оголошено зарезервованим і забороненим для передачі.

### Корисне навантаження, паддінг та контрольна сума FCS

За заголовком слідує поле даних — **корисне навантаження (Payload)**. У стандартному кадрі його розмір становить від 46 до 1500 байтів.

**Проблема заповнення (Padding).**
Якщо вищий протокол генерує пакет, менший за 46 байтів (наприклад, стандартний ARP-запит має розмір лише 28 байтів), канальний рівень не може надіслати такий кадр як є, оскільки мінімальний розмір кадру Ethernet без контрольної суми становить 60 байтів (14 байтів заголовка + 46 байтів даних).

У цьому разі мережевий чип автоматично дописує в кінець даних нульові байти доповнення — **паддінг (Padding)**.
Це створює важливу інженерну особливість: приймач на канальному рівні отримує буфер розміром 46 байтів і не знає, де закінчуються справжні дані й починається паддінг. Цю задачу розв'язує мережевий рівень: IP-заголовок містить власне поле `Total Length`, за яким ядро операційної системи відтинає зайві нулі.

**Контрольна послідовність кадру (Frame Check Sequence, FCS).**
Кадр завершується 4-байтовим полем FCS, що містить циклічний надлишковий код **CRC-32**.
Контрольна сума обчислюється над усіма полями кадру: починаючи з найпершого байта `dst_mac` і закінчуючи останнім байтом корисного навантаження або паддінгу (преамбула, SFD та сам FCS у розрахунок не входять).

В Ethernet використовується стандартизований поліном IEEE 802.3:
`x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹ + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x + 1`

Апаратний передавач обчислює залишок від ділення полінома на льоту й записує його в кінець кадру. Приймач паралельно обчислює CRC над вхідним потоком. Якщо після проходження всього кадру (разом із полем FCS) залишок у регістрі збігається з константою `0x2144DF1C` (магічний залишок CRC-32), кадр вважається цілісним. Якщо хоча б один біт спотворено електромагнітною завадою, контрольна сума не зійдеться, і мережева карта миттєво відкине пошкоджений кадр без передачі в операційну систему (лічильник `rx_crc_errors` в утиліті `ethtool`).

![Чому мінімальний кадр рівно 64 байти](/book/communications/networks/ethernet-frame/img/min-frame-slot-time.svg)
*Фізика колізійного вікна: час поширення сигналу в максимальному колізійному домені (2.5 км) туди й назад становить 51.2 мкс (512 біт-часів на 10 Мбіт/с). Кадр має тривати щонайменше 64 байти, щоб передавач не завершив передачу до приходу відлуння колізії.*

### Фізика колізійного вікна: чому мінімум 64 байти

Мінімальний розмір кадру Ethernet зафіксовано на рівні рівно **64 байтів** (512 бітів):
`6 байтів (Dst MAC) + 6 байтів (Src MAC) + 2 байти (EtherType) + 46 байтів (Payload/Pad) + 4 байти (FCS) = 64 байти`

Кадр, розмір якого менший за 64 байти, в термінології Ethernet називається **Runt-кадром** (англ. *runt* — недоросток) і вважається апаратним дефектом.

Ця цифра — не випадковий вибір, а жорсткий наслідок законів електродинаміки в первинному напівдуплексному Ethernet на коаксіальному кабелі з методом доступу [CSMA/CD](book:communications/csma-cd) (Carrier Sense Multiple Access with Collision Detection).

У спільному кабелі електромагнітний сигнал поширюється зі швидкістю приблизно `200 000 км/с` (близько `5 нс` на кожен метр мідного дроту). Максимальна довжина мережі 10BASE5 з урахуванням чотирьох повторювачів (репітерів) становила `2500 метрів`.
1. Час поширення сигналу від вузла A на одному кінці кабелю до найвіддаленішого вузла B на іншому кінці становив приблизно `T_prop ≈ 25.6 мкс`.
2. Припустімо, вузол A почав передавати кадр у момент часу `t = 0`. Сигнал дійшов до вузла B у момент `t = 25.5 мкс` — за мить до того, як вузол B сам вирішив почати передачу, вважаючи лінію вільною.
3. Сигнали накладаються біля вузла B — виникає колізія. Вузол B фіксує аномальну напругу й починає генерувати шумовий сигнал глушіння (Jam-сигнал).
4. Хвиля зіткнення повинна пройти весь кабель у зворотному напрямку, щоб дійти до початкового передавача A. Вузол A дізнається про колізію лише через час подвійного пробігу (Round Trip Time, RTT):
   `2 · T_prop ≈ 51.2 мкс`

На швидкості 10 Мбіт/с передача одного біта триває рівно `100 нс` (1 біт-час). За час подвійного пробігу `51.2 мкс` передавач встигає відправити в лінію:
`51.2 мкс ÷ 100 нс = 512 бітів = 64 байти`

Цей проміжок часу називається **квантом часу (Slot Time)**.

Якщо кадр триває щонайменше 64 байти, передавач A гарантовано все ще продовжує передавати дані в момент, коли хвиля колізії повертається назад. Вузол A фіксує перевантаження за струмом, розуміє, що сталася колізія, припиняє передачу й планує повторну спробу за алгоритмом двійкового експоненційного відкату.

Якби кадр був коротшим (наприклад, 30 байтів), вузол A повністю завершив би передачу, очистив буфер і вважав би доставку успішною ще до того, як відлуння аварії докотиться назад. Виникла б **пізня колізія (Late Collision)** — катастрофічний стан, за якого дані втрачено на канальному рівні без відома передавача.

У сучасному повнодуплексному комутованому Ethernet колізій більше не існує, оскільки кожен порт комутатора утворює ізольований домен колізій із виділеними лініями прийому (RX) та передачі (TX). Проте ліміт у 64 байти залишили незмінним у стандартах Fast Ethernet, Gigabit Ethernet та 100G Ethernet. Це гарантує зворотну сумісність протоколів, незмінність логіки контролерів і стабільність конвеєрів пам'яті в комутаційних чипах ASIC.

### Міжкадровий інтервал (IFG)

Між завершенням передачі попереднього кадру (останнього біта FCS) та початком преамбули наступного кадру передавач зобов'язаний витримати паузу тиші на фізичній лінії — **міжкадровий інтервал (Interframe Gap, IFG)**, який також називають міжкадровим проміжком (Interpacket Gap, IPG).

Стандарт IEEE 802.3 жорстко фіксує тривалість IFG на рівні **96 біт-часів** (що еквівалентно часу передачі 12 байтів):
* **10 Мбіт/с (Ethernet):** `9.6 мкс`
* **100 Мбіт/с (Fast Ethernet):** `960 нс`
* **1 Гбіт/с (Gigabit Ethernet):** `96 нс`
* **10 Гбіт/с (10GbE):** `9.6 нс`
* **100 Гбіт/с (100GbE):** `0.96 нс`

Фізична необхідність міжкадрового інтервалу зумовлена кількома факторами:
1. **Релаксація фізичного середовища:** на витій парі та оптоволокні після передачі кадру повинні згаснути паразитні перехідні процеси, електричні заряди ємності кабелю та відлуння сигналів.
2. **Відновлення приймального тракту:** за час паузи схема PLL приймача готується до прийому нової преамбули, скидаються внутрішні регістри зрушення десеріалізатора та лічильники бітів.
3. **Обробка переривань і перемикання буферів DMA:** контролеру потрібен час, щоб записати дескриптор завершеного кадру в оперативну пам'ять хоста й підготувати наступний вільний дескриптор кільця прийому.
4. **Компенсація дрейфу генераторів (Clock PPM compensation):** якщо передавач працює на гранично допустимій швидкості (+100 ppm), а комутатор-ретранслятор має трохи повільніший генератор (-100 ppm), комутатор змушений злегка скорочувати міжкадровий інтервал (наприклад, з 96 до 92 або 88 біт-часів), щоб внутрішня черга FIFO не переповнювалася. Інтервал у 96 бітів створює пружний запас для такого вирівнювання.

Сумарна мінімальна «фізична вага» стандартного кадру Ethernet на кабелі складається з канального кадру та службових накладних витрат фізичного рівня:
`8 байтів (Преамбула + SFD) + 14 байтів (Заголовок L2) + 1500 байтів (MTU) + 4 байти (FCS) + 12 байтів (IFG) = 1538 байтів на дроті`

![Вставка та структура тега IEEE 802.1Q](/book/communications/networks/ethernet-frame/img/vlan-8021q-tag.svg)
*Структура тегованого кадру IEEE 802.1Q: 4-байтовий тег містить TPID (0x8100) та 16 бітів керування TCI (3 біти пріоритету PCP, 1 біт DEI та 12 бітів ідентифікатора VLAN ID від 1 до 4094).*

### Тегування IEEE 802.1Q: ізоляція VLAN та пріоритети QoS

У великих корпоративних мережах та центрах обробки даних виникає потреба розділити одну спільну фізичну інфраструктуру кабелів і комутаторів на сотні ізольованих логічних мереж ([віртуальні локальні мережі, VLAN](book:communications/vlan-and-trunking)).

Для передачі трафіку багатьох VLAN одним фізичним кабелем (на транкових магістралях між комутаторами) стандарт **IEEE 802.1Q** вводить механізм тегування.

Тег 802.1Q має фіксований розмір **4 байти** і вставляється безпосередньо в середину заголовка Ethernet — між полем `src_mac` та початковим полем `ethertype`.

Структура 4 байтів тега 802.1Q:
1. **TPID (Tag Protocol Identifier, 2 байти):** завжди містить константу `0x8100`. Для мережевого обладнання це значення вказує, що звичний заголовок зміщено, і наступні два байти несуть інформацію про тег.
2. **TCI (Tag Control Information, 2 байти / 16 бітів):**
   * **PCP (Priority Code Point, 3 біти):** рівень пріоритету кадру за стандартом IEEE 802.1p. Вісім рівнів (від `0` — фоновий трафік до `7` — критичні пакети керування мережею). Комутатори використовують PCP для розкладання кадрів за апаратними чергами QoS (наприклад, щоб передавати голосові пакети VoIP раніше за завантаження файлів).
   * **DEI (Drop Eligible Indicator, 1 біт, раніше CFI):** прапор дозволу на скидання. Якщо канал перевантажено, комутатор у першу чергу знищує кадри з `DEI = 1`.
   * **VID (VLAN Identifier, 12 бітів):** числовий номер віртуальної мережі. 12 бітів дозволяють закодувати `2¹² = 4096` значень:
     * `0` — пріоритетний кадр (Priority Tagged, не належить жодному конкретному VLAN);
     * `1` — стандартний VLAN за замовчуванням (Default Native VLAN);
     * `2 – 4094` — дійсні номери призначених користувацьких VLAN;
     * `4095` — зарезервовано стандартом.

Вставка 4 байтів тега збільшує максимальний розмір стандартного кадру Ethernet з 1518 до **1522 байтів** (при збереженні незмінного IP MTU 1500 байтів). Старі комутатори, що не підтримували 802.1Q, відкидали такі кадри як аномальні (Baby Giant Frames).

У провайдерських мережах використовується розширення **IEEE 802.1ad (QinQ)**: у кадр вставляється два теги послідовно — зовнішній тег оператора (Service Tag, `TPID = 0x88A8`) та внутрішній тег клієнта (Customer Tag, `TPID = 0x8100`). Розмір кадру на магістралях оператора зростає до 1526 байтів.

![Ефективність Jumbo Frames](/book/communications/networks/ethernet-frame/img/jumbo-frame-efficiency.svg)
*Порівняння оверхеду: передача 9000 байтів даних через стандартний MTU 1500 вимагає 6 кадрів (сумарно 468 байтів службових заголовків L1–L4 та 6 переривань CPU). Один Jumbo Frame з MTU 9000 передає той самий обсяг з оверхедом лише 78 байтів і 1 перериванням.*

### Високі швидкості та Jumbo Frames

Стандартне обмеження корисного навантаження в 1500 байтів виникло на початку 1980-х років, коли швидкість мережі становила 10 Мбіт/с, а оперативна пам'ять комп'ютерів вимірювалася мегабайтами.

На сучасних швидкостях 10G, 40G та 100G Ethernet ліміт 1500 байтів перетворюється на серйозне гальмо продуктивності:
* Щоб завантажити лінк 10 Гбіт/с стандартними кадрами по 1500 байтів, мережева підсистема повинна обробляти приблизно **812 000 кадрів щосекунди**.
* Для кожного кадру центральний процесор змушений обробляти апаратні переривання драйвера, виділяти дескриптори кільця DMA, перевіряти заголовки й оновлювати стан сокетів. Навіть на потужних серверах це призводить до значних накладних витрат процесорного часу.

Для подолання цієї проблеми виробники мережевого обладнання впровадили **Jumbo Frames (гігантські кадри)** — кадри канального рівня, розмір корисного навантаження яких перевищує стандартні 1500 байтів і зазвичай становить **9000 байтів** (MTU 9000).

Переваги Jumbo Frames:
1. **Зменшення кількості пакетів у 6 разів:** передача 9000 байтів блоку даних дискового масиву SAN (iSCSI, NFS) замість шести окремих кадрів по 1500 байтів виконується одним-єдиним кадром.
2. **Зниження оверхеду протоколів:** на 9000 байтів корисного навантаження замість 6 заголовків L2/L3/L4 (сумарно `6 × 78 = 468` байтів разом з IFG) витрачається лише один набір заголовків (`1 × 78 = 78` байтів).
3. **Розвантаження CPU:** кількість переривань та оновлень дескрипторів кілець DMA падає пропорційно, звільняючи ядра процесора для роботи прикладних задач.

Підводні камені та інженерні обмеження Jumbo Frames:
* **Відсутність офіційного стандарту IEEE:** розмір Jumbo Frames не зафіксовано в офіційних специфікаціях IEEE 802.3 (робоча група відмовилася стандартизувати їх, щоб не порушувати сумісність базових алгоритмів). Тому різні виробники підтримують різні максимальні межі (9000, 9216 або 9600 байтів).
* **Несумісність MTU та ефект «чорної діри»:** якщо хоча б один комутатор або маршрутизатор усередині локального L2-сегмента налаштований на стандартний MTU 1500, він мовчки відкине Jumbo-кадр розміром 9000 байтів через перевищення буфера (`rx_oversize_errors`). При цьому комутатор канального рівня не вміє генерувати повідомлення ICMP «Fragmentation Needed» (оскільки він не розбирає IP). Зв'язок між вузлами раптово зникає на великих пакетах, хоча дрібні утиліти на кшталт `ping` продовжують працювати.
* **Зростання затримки черг (Head-of-Line Blocking):** передача одного 9000-байтового кадру на повільному 1-гігабітному лінку триває `72 мкс`. Увесь цей час чутливий голосовий (VoIP) або ігровий трафік змушений чекати в черзі, що збільшує джиттер ([затримку й варіацію затримки](book:communications/latency-reliability)).
* **Деградація надійності CRC-32:** циклічний код CRC-32 гарантовано виявляє будь-які спотворення до 3 перекинутих бітів включно на довжинах блоків до 11 455 байтів (відстань Геммінга `d = 4`). При перевищенні цієї довжини математична стійкість полінома різко падає, і ймовірність пропустити комбіновану помилку кабелю зростає на кілька порядків.

### Розбір та обробка кадру в коді

Для роботи з сирими Ethernet-кадрами в операційній системі Linux використовується сімейство сокетів `AF_PACKET` у режимі `SOCK_RAW`. Системний виклик повертає повноцінний масив байтів кадру разом із заголовком Ethernet II.

Програмний парсер зчитує 14 байтів базового заголовка, перевіряє значення поля на зміщенні 12 і рекурсивно розгортає всі присутні теги VLAN 802.1Q:

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define ETH_ALEN       6
#define ETH_HLEN       14
#define ETHERTYPE_IPV4 0x0800
#define ETHERTYPE_VLAN 0x8100

struct eth_header {
    uint8_t  dst[ETH_ALEN];
    uint8_t  src[ETH_ALEN];
    uint16_t type; /* У Big-Endian порядку */
};

/* Базова перевірка та виділення EtherType */
bool parse_ethernet_header(const uint8_t *buffer, size_t len,
                           uint16_t *out_ethertype, size_t *out_payload_offset) {
    if (len < ETH_HLEN)
        return false;

    size_t offset = 12;
    uint16_t proto = (uint16_t)((buffer[offset] << 8) | buffer[offset + 1]);
    offset += 2;

    /* Обробка тега 802.1Q */
    if (proto == ETHERTYPE_VLAN) {
        if (len < offset + 4)
            return false;
        /* Пропускаємо TCI (2 байти) і читаємо справжній EtherType */
        offset += 2;
        proto = (uint16_t)((buffer[offset] << 8) | buffer[offset + 1]);
        offset += 2;
    }

    *out_ethertype = proto;
    *out_payload_offset = offset;
    return true;
}
```
```cpp
#include <cstdint>
#include <array>
#include <span>
#include <optional>
#include <bit>

namespace net {

inline constexpr std::size_t mac_size = 6;
inline constexpr std::size_t eth_header_size = 14;
inline constexpr uint16_t ethertype_vlan = 0x8100;

struct parsed_eth_info {
    std::array<uint8_t, mac_size> dst_mac{};
    std::array<uint8_t, mac_size> src_mac{};
    uint16_t ethertype{0};
    std::span<const uint8_t> payload{};
};

[[nodiscard]] std::optional<parsed_eth_info>
parse_ethernet(std::span<const uint8_t> frame_bytes) noexcept {
    if (frame_bytes.size() < eth_header_size)
        return std::nullopt;

    parsed_eth_info info;
    std::copy_n(frame_bytes.data(), mac_size, info.dst_mac.begin());
    std::copy_n(frame_bytes.data() + mac_size, mac_size, info.src_mac.begin());

    std::size_t offset = 12;
    uint16_t proto = static_cast<uint16_t>((frame_bytes[offset] << 8) | frame_bytes[offset + 1]);
    offset += 2;

    /* Розгортання тега 802.1Q */
    if (proto == ethertype_vlan) {
        if (frame_bytes.size() < offset + 4)
            return std::nullopt;
        offset += 2; // Пропускаємо TCI
        proto = static_cast<uint16_t>((frame_bytes[offset] << 8) | frame_bytes[offset + 1]);
        offset += 2;
    }

    info.ethertype = proto;
    info.payload = frame_bytes.subspan(offset);
    return info;
}

} // namespace net
```

Кадр Ethernet залишається головним будівельним блоком комп'ютерних мереж уже понад чотири десятиліття. Від коаксіального кабелю 10BASE5 до 800-гігабітних оптичних магістралей структура з преамбулою, 48-бітними MAC-адресами, полем EtherType та захистом CRC-32 довела свою абсолютну масштабованість і стабільність, пов'язуючи фізичне середовище кремнію та оптики з глобальним мережевим простором IP.
