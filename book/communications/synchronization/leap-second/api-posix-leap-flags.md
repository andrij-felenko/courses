# 📋 Системні прапорці та структури керування високосною секундою в POSIX та ядрі Linux

Цей довідник містить вичерпний опис інтерфейсів програмування додатків (API), системних структур даних ядра Linux, бітових прапорців підсистеми обліку часу (timekeeping), а також протокольних заголовків NTPv4 (RFC 5905) та PTP (IEEE 1588-2019). Довідник призначений для системних інженерів, розробників високонавантажених сервісів та авторів мережевих протоколів, які взаємодіють із механізмами синхронізації та обробки високосних секунд на рівні ядра операційної системи та мережевих сокетів.

---

### Архітектура підсистеми обліку часу ядра Linux

Підсистема обліку часу ядра Linux (розташована у вихідних файлах `kernel/time/timekeeping.c` та `kernel/time/ntp.c`) забезпечує функціонування кількох базових годинників системи: монотонного годинника `CLOCK_MONOTONIC`, сирого апаратного годинника `CLOCK_MONOTONIC_RAW`, годинника часу завантаження `CLOCK_BOOTTIME` та цивільного настінного часу `CLOCK_REALTIME`. Серед них саме годинник `CLOCK_REALTIME` безпосередньо підпорядковується правилам цивільного часу UTC і зазнає коригувань під час настання високосних секунд.

Ядро операційної системи моделює системний годинник як прецизійний інтегратор фази, що підраховує такти апаратного джерела переривань або високоточного лічильника процесора (TSC у сучасних системах x86_64, HPET або лічильника архітектури ARM Generic Timer). Оскільки жоден фізичний кварцовий резонатор не має абсолютно стабільної частоти генерації, ядро реалізує алгоритм зворотного зв'язку фазового та частотного автопідстроювання (PLL/FLL), запозичений із праць Девіда Міллса та стандарту RFC 5905.

Для взаємодії з цим внутрішнім регулятором призначено спеціалізовані системні виклики `adjtimex()` та `ntp_adjtime()`, які дозволяють користувацьким процесам (за наявності відповідних адміністративних привілеїв) отримувати поточну метрологічну телеметрію ядра та передавати директиви щодо зміни частоти генератора або планування вставки високосної секунди.

### Системна структура `struct timex` та її поля

Заголовні файли `<sys/timex.h>` (простір користувача) та `<linux/timex.h>` (внутрішній інтерфейс ядра) визначають головну структуру керування параметрами годинника. Нижче наведено детальний опис призначення кожного з її полів:

Поле `modes` є вхідною бітовою маскою, яка вказує ядру, які саме поля структури містять нові конфігураційні параметри для запису. Якщо процес викликає `adjtimex()` із нульовим значенням `modes == 0`, ядро не вносить жодних змін у налаштування генератора, а лише заповнює поля структури поточними виміряними значеннями та повертає статус автомата станів.

Поле `offset` визначає величину фазової похибки системного часу відносно еталону. За замовчуванням це поле вимірюється в мікросекундах, однак за умови встановлення прапорця `STA_NANO` в полі `status` ядро починає інтерпретувати це значення з наносекундною роздільною здатністю. Коли користувацький демон записує нове значення зсуву з прапорцем `ADJ_OFFSET`, ядро не виконує миттєвий стрибок годинника, а передає це значення до пропорційно-інтегрального регулятора PLL, який поступово ліквідує накопичену похибку шляхом тимчасового прискорення або уповільнення ходу годинника.

Поле `freq` задає постійне відносне зміщення частоти тактового генератора. У ядрі Linux це поле масштабується в одиницях з фіксованою комою: одиниця молодшого розряду відповідає `1 / 65 536` частці на мільйон (`2⁻¹⁶ ppm`). Таке високе розділення необхідне для того, щоб підсистема обліку часу могла виконувати ультраточне підлаштування частоти без накопичення похибок округлення під час кожного тіка таймера. Максимальне значення відхилення частоти жорстко обмежене ядром на рівні `±500 ppm` (константа `MAXFREQ`), що запобігає випадковому або зловмисному розбалансуванню системи.

Поле `maxerror` містить максимальну гарантовану похибку часу в мікросекундах. Це значення розраховується демоном синхронізації на основі оцінки затримок передачі пакетів у мережі та дрейфу локального кварцу. Якщо сервер втрачає зв'язок із джерелами точного часу, ядро починає щосекунди збільшувати `maxerror` на величину максимального паспортного дрейфу кварцу (`tolerance`), відображаючи деградацію точності.

Поле `esterror` визначає очікувану статистичну середньоквадратичну похибку часу за результатами серії останніх мережевих вимірювань алгоритму Марзулло.

Поле `status` є бітовою маскою прапорців стану годинника. Саме через це поле передаються команди планування високосної секунди (`STA_INS` для додавання або `STA_DEL` для вилучення), вмикаються режими роботи з наносекундною точністю (`STA_NANO`) та сигналізується про втрату синхронізації (`STA_UNSYNC`).

Поле `constant` задає логарифмічну постійну часу фільтра PLL. Цей параметр визначає баланс між швидкістю реакції регулятора на зміну часу та його стійкістю до випадкового джитеру мережевих пакетів.

Поле `precision` показує мінімальну дискретність вимірювання часу, яку забезпечує поточне апаратне джерело (доступне тільки для читання).

Поле `tolerance` вказує максимальну величину нестабільності частоти апаратного генератора, що закладається в математичну модель ядра (за замовчуванням `500 ppm`, тільки для читання).

Поле `time` представляє поточний час системи у форматі структури `struct timeval`. За звичайних умов це поле заповнюється ядром при читанні, але при використанні прапорця `ADJ_SETOFFSET` значення з цього поля миттєво записується як новий системний час.

Поле `tick` задає тривалість одного тіка таймера ядра в мікросекундах. Воно дозволяє виконувати грубе коригування базової частоти переривань системного таймера (зазвичай значення становить `10 000 мкс` для систем із базовою частотою `100 Гц` або `1000 мкс` для `1000 Гц`).

Група полів `ppsfreq`, `jitter`, `shift`, `stabil`, `jitcnt`, `calcnt`, `errcnt`, `stbcnt` забезпечує роботу підсистеми апаратного стробування імпульсами секунди (PPS). Вони надають діагностичну інформацію про стабільність зовнішнього сигналу, кількість відкинутих імпульсів та якість калібрування локального генератора.

Поле `tai` містить цілочисельний зсув між Міжнародним атомним часом TAI та цивільним часом UTC у секундах (станом на поточну епоху це значення становить `37 секунд`). Завдяки цьому полю програми можуть отримувати атомний час без додаткових таблиць перерахунку.

### Бітові прапорці модифікації (`modes`)

Під час виклику системної функції `adjtimex(&tx)` значення поля `modes` інформує ядро про те, які саме поля структури слід обробити:

* `ADJ_OFFSET` (`0x0001`): активує зміну фазового зсуву `tx.offset`. Ядро передає вказане значення у фільтр фази для плавного вирівнювання часу.
* `ADJ_FREQUENCY` (`0x0002`): вмикає оновлення базової частоти генератора `tx.freq`.
* `ADJ_MAXERROR` (`0x0004`): наказує ядру оновити поле максимальної оціненої похибки `tx.maxerror`.
* `ADJ_ESTERROR` (`0x0008`): оновлює очікувану похибку `tx.esterror`.
* `ADJ_STATUS` (`0x0010`): вказує ядру застосувати нові бітові прапорці стану з поля `tx.status`, зокрема директиви вставки високосної секунди.
* `ADJ_TIMECONST` (`0x0020`): встановлює новий коефіцієнт згладжування фільтра `tx.constant`.
* `ADJ_TAI` (`0x0080`): оновлює системний зсув атомного часу TAI `tx.tai`.
* `ADJ_SETOFFSET` (`0x0100`): виконує миттєвий примусовий стрибок системного часу на значення, вказане в `tx.time`.
* `ADJ_MICRO` (`0x1000`): вказує ядру повернутися до класичного мікросекундного подання похибок.
* `ADJ_NANO` (`0x2000`): вмикає наносекундну точність інтерфейсу `timex`.

### Бітові прапорці стану (`status`)

Поле `status` є головним реєстром конфігурації автомата станів високосної секунди:

* `STA_INS` (`0x0010`): прапорець планування додатної високосної секунди (+1 с). Демон синхронізації встановлює цей біт за 24 години до настання кінця доби. Отримавши цей прапорець, ядро переходить у стан очікування `TIME_INS`. Рівно о 23:59:59 UTC ядро активує стан `TIME_OOP` і повторює секунду `23:59:59` двічі, запобігаючи стрибку часу вперед.
* `STA_DEL` (`0x0020`): прапорець планування від'ємної високосної секунди (−1 с). Сигналізує ядру про необхідність вилучити секунду `23:59:59` наприкінці доби (перехід від `23:59:58` безпосередньо до `00:00:00`).
* `STA_UNSYNC` (`0x0040`): прапорець розсинхронізації. Встановлюється автоматично при старті системи або демоном синхронізації при втраті зв'язку з еталонами часу. Переводить ядро в аварійний стан `TIME_ERROR`.
* `STA_FREQCNT` (`0x0020`): дозвіл автоматичного калібрування частоти генератора за сигналами PPS.
* `STA_PPSSIGNAL` (`0x0100`): прапорець, що підтверджує фіксацію апаратного імпульсу PPS на вході відповідного драйвера.
* `STA_PPSJITTER` (`0x0200`): індикатор перевищення допустимого джитеру сигналу PPS.
* `STA_PPSWANDER` (`0x0400`): індикатор надмірного дрейфу фази сигналу PPS.
* `STA_PPSERROR` (`0x0800`): загальний статус помилки підсистеми обробки імпульсів PPS.
* `STA_CLOCKERR` (`0x1000`): повідомлення про апаратну несправність тактового генератора.
* `STA_NANO` (`0x2000`): підтвердження роботи підсистеми timekeeping з наносекундною роздільною здатністю.
* `STA_MODE` (`0x4000`): перемикання алгоритму підстроювання на режим FLL (Frequency-Locked Loop).
* `STA_CLK` (`0x8000`): активний режим використання резервного годинника.

### Внутрішній автомат станів високосної секунди ядра Linux

Обробка прапорців високосної секунди в ядрі Linux здійснюється спеціальним автоматом станів, який перевіряється під час кожного виклику функції `second_overflow()` у контексті переривання системного таймера.

Коли демон синхронізації (`chronyd` або `ntpd`) отримує сповіщення про майбутню високосну секунду, він викликає `adjtimex()` зі встановленим бітом `STA_INS` у полі `tx.status` та маскою `ADJ_STATUS`. Ядро перевіряє валідність параметрів і змінює свій стан із нормального `TIME_OK` (код 0) на стан `TIME_INS` (код 1).

У стані `TIME_INS` ядро продовжує штатний відлік часу, очікуючи моменту настання кінця доби. Коли лічильник часу досягає значення `23:59:59.999... UTC`, функція `second_overflow()` виявляє, що наступна секунда є високосною:
1. Ядро переводить внутрішній стан у `TIME_OOP` (код 3, Out of Order).
2. Замість інкременту лічильника секунд `xtime.tv_sec` ядро повертає лічильник на одну секунду назад або тимчасово призупиняє його нарощування, через що системний час повторює секунду `23:59:59`.
3. Після завершення високосної секунди (коли минає рівно 1.000 секунда фізичного часу) ядро переходить у стан `TIME_WAIT` (код 4).
4. У стані `TIME_WAIT` ядро очікує, поки користувацький демон синхронізації знову викличе `adjtimex()` і явно скине прапорець `STA_INS` у полі `status`.
5. Після скидання прапорця автомат повертається у вихідний стан `TIME_OK` (код 0).

Якщо в будь-який момент часу годинник втрачає синхронізацію або демон встановлює біт `STA_UNSYNC`, ядро негайно переходить у стан `TIME_ERROR` (код 5), інформуючи всі зацікавлені процеси про недостовірність системного часу.

### Прапорці мережевого протоколу NTPv4 (RFC 5905)

У протоколі NTP версії 4 кожне повідомлення містить 2-бітне поле **Leap Indicator (LI)** у першому байті заголовка пакета (біти 7 та 6):

1. **`LI = 00` (`0b00`, `LI_NOWARNING`):** нормальний стан. Сповіщає клієнта про те, що наприкінці поточної доби жодних високосних коригувань не відбудеться.
2. **`LI = 01` (`0b01`, `LI_PLUSSEC`):** попередження про вставку додатної секунди. Вказує на те, що остання хвилина поточної доби UTC міститиме 61 секунду (`23:59:60`).
3. **`LI = 10` (`0b10`, `LI_MINUSSEC`):** попередження про вилучення секунди. Вказує на те, що остання хвилина доби міститиме лише 59 секунд (`23:59:58 -> 00:00:00`).
4. **`LI = 11` (`0b11`, `LI_ALARM`):** стан тривоги. Вказує на те, що сервер розсинхронізований із первинним джерелом і його покази не повинні використовуватися для налаштування клієнтського часу.

Поширення прапорця LI відбувається за ієрархією Stratum: первинні сервери Stratum 1 встановлюють `LI = 01` рівно за 24 години до настання події, після чого вторинні сервери Stratum 2 та клієнти підхоплюють цей статус під час чергового опитування.

Важливо відзначити поведінку серверів у режимі **Leap Smearing (розмазування)**: такі сервери (наприклад, Google Public NTP або Cloudflare) **завжди передають `LI = 00`**. Вони приховують факт високосної секунди від клієнтів і транслюють плавно спотворену частоту, щоб запобігти активації механізму стрибка в клієнтських операційних системах.

### Прапорці протоколу точного часу PTP (IEEE 1588-2019)

У прецизійному протоколі PTP інформація про високосну секунду транслюється генератором Grandmaster Clock у спеціалізованих повідомленнях типу `Announce`. Повідомлення містить 16-бітне поле `flagField` (байти 6 та 7 заголовка PTP) та інформаційні поля стану шкали:

1. **`leap61` (біт 0 першого октету):** встановлюється в одиницю, якщо наприкінці поточної доби UTC буде додана високосна секунда.
2. **`leap59` (біт 1 першого октету):** встановлюється в одиницю у разі вилучення високосної секунди.
3. **`currentUtcOffsetValid` (біт 2 першого октету):** підтверджує, що поле `currentUtcOffset` містить валідне значення поточного зсуву між TAI та UTC.
4. **`ptpTimescale` (біт 3 першого октету):** визначає тип шкали. Якщо біт дорівнює `1`, протокол використовує неперервну атомну шкалу PTP/TAI, де високосні секунди не призводять до розривів монотонності. Якщо біт дорівнює `0`, використовується довільна шкала ARB.
5. **`timeTraceable` (біт 4 першого октету):** підтверджує метрологічну простежуваність часу джерела Grandmaster до національних еталонів UTC.
6. **`frequencyTraceable` (біт 5 першого октету):** підтверджує простежуваність частоти генератора до стандартів SI.
7. **`currentUtcOffset` (16-бітне ціле зі знаком у тілі повідомлення):** містить точну поточну різницю в секундах між шкалами TAI та UTC (`37 секунд` на поточний момент).

### Програмні приклади взаємодії з інтерфейсом ядра

Нижче наведено практичні приклади коду на мовах C та ідіоматичному C++20 для керування автоматом станів високосної секунди та декодування мережевих прапорців.

#### Приклад 1: Планування додатної високосної секунди через `adjtimex`
Програма зчитує поточний стан підсистеми timekeeping ядра, встановлює прапорець `STA_INS` та перевіряє новий статус автомата станів.

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <sys/timex.h>

int schedule_leap_insertion(void) {
    struct timex tx;
    memset(&tx, 0, sizeof(tx));

    // Зчитуємо поточні параметри ядра
    if (adjtimex(&tx) < 0) {
        perror("Помилка зчитування параметрів через adjtimex");
        return -1;
    }

    // Додаємо прапорець вставки та знімаємо прапорець видалення
    tx.modes = ADJ_STATUS;
    tx.status |= STA_INS;
    tx.status &= ~STA_DEL;

    int state = adjtimex(&tx);
    if (state < 0) {
        if (errno == EPERM) {
            fprintf(stderr, "Помилка: потрібні права CAP_SYS_TIME для керування годинником!\n");
        } else {
            perror("Помилка запису нового статусу в adjtimex");
        }
        return -1;
    }

    printf("Прапорець STA_INS успішно встановлено. Поточний стан ядра: %d (TIME_INS)\n", state);
    return 0;
}
```

### Діагностика та налагодження підсистеми часу через sysfs та ftrace

Для оперативного контролю стану годинника та налагодження поведінки системи під час настання високосної секунди в операційній системі Linux використовуються такі системні інструменти:

По-перше, системна псевдофайлова система `/sys` дозволяє перевірити, яке саме апаратне джерело часу використовується ядром для генерації міток:
```bash
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
# Повертає назву активного таймера: tsc, kvm-clock, hpet або acpi_pm
```

По-друге, системна утиліта командного рядка `adjtimex` дозволяє безпосередньо зчитати поточний стан усіх полів структури `timex` ядра:
```bash
adjtimex --print
# Виводить параметри: modes, offset, frequency, maxerror, esterror, status, time_state
```

По-третє, механізм динамічного трасування ядра `ftrace` надає можливість перехоплювати події спрацьовування високосної секунди в реальному часі без зупинки системи:
```bash
# Увімкнення трасування подій підсистеми timekeeping
echo 1 > /sys/kernel/debug/tracing/events/timekeeping/enable

# Перегляд журналу подій під час настання 23:59:59 UTC
cat /sys/kernel/debug/tracing/trace_pipe | grep -E "timekeeping|leap"
```
Цей механізм фіксує внутрішні виклики функцій `timekeeping_leap_insert()` та переходи автомата станів, дозволяючи системним адміністраторам переконатися у коректній роботі ядра під час астрономічних корекцій.
