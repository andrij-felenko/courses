# ⚙️ Драйвер керування напрямком RS-485 у коді

Цей практичний розбір розкриває алгоритми та програмні реалізації керування сигналом напрямку `DE/RE` (*Driver Enable*) у напівдуплексних мережах RS-485. Тут детально проаналізовано гонки сигналів, часові інтервали кадру UART, пастки передчасного відпускання лінії та наведено робочі приклади коду мовами C та C++.

### Проблема точного часового перемикання DE

У напівдуплексному режимі RS-485 одна вита пара використовується і для передачі, і для приймання. Передавач вузла повинен умикатися в шину (`DE = 1`) строго перед відправкою першого старт-біта та від'єднуватися у третій стан (`DE = 0`) одразу після завершення останнього стоп-біта кадру.

Головна практична пастка програмування драйверів RS-485 полягає в некоректному виборі події завершення передачі:

1. **Передчасне відпускання (обрізання стоп-біта):** Початківці часто опускають `DE = 0` одразу після того, як функція запису віддасть останній байт у буфер периферії UART. Проте прапорець «буфер порожній» (`TXE` у STM32 або `TXFNF` у NXP) означає лише те, що байт перемістився з програмного регістру в апаратний зсувний регістр (*Shift Register*). Сам байт ще фізично випромінюється у дріт! Якщо опустити `DE` у цей момент, останній символ або його стоп-біт буде обрізано напівдорозі, і віддалений приймач отримає помилку кадрування (*Framing Error*).
2. **Запізніле відпускання (блокування шини):** Якщо після передачі зробити завелику затримку у прошивці (наприклад, викликати програмний `delay`), передавач лишатиметься активним, коли віддалений відповідач уже почне передавати відповідь. Відбудеться колізія шини, і перші байти відповіді будуть незворотно спотворені.

Правильне програмне рішення: опускати `DE = 0` **строго за прапорцем повного спорожнення зсувного регістра** — `TC` (*Transmission Complete*), або використовувати апаратний режим автокерування `DE` у мікроконтролерах.

### Математичний розрахунок байтового таймінгу та затримок

Для налаштування програмних таймаутів та оцінки часових вікон розробник мусить чітко розраховувати час передачі одного кадру UART. Для найпоширенішого формату `8N1` (1 старт-біт, 8 бітів даних, без парності, 1 стоп-біт) один кадр містить рівно 10 бітових інтервалів.

Формули розрахунку часових інтервалів:

```
Час 1 біта (t_bit)     = 1 / BaudRate
Час 1 кадру (t_frame)   = 10 · t_bit
Час кадру з парністю   = 11 · t_bit  (для формату 8E1 або 8O1)
```

Приклади точного розрахунку для типових швидкостей обміну:

1. **Швидкість 9600 бод:**
   - Час 1 біта `t_bit = 1 / 9600 ≈ 104.17 мкс`.
   - Час 1 кадру `t_frame = 10 · 104.17 мкс ≈ 1.042 мс`.
   - Затримка у півтора символу (типова межа кадру в Modbus RTU): `1.5 · 1.042 мс ≈ 1.56 мс`.
   - Інтервал тиші між кадрами в Modbus RTU (3.5 символи): `3.5 · 1.042 мс ≈ 3.65 мс`.

2. **Швидкість 115200 бод:**
   - Час 1 біта `t_bit = 1 / 115200 ≈ 8.68 мкс`.
   - Час 1 кадру `t_frame = 10 · 8.68 мкс ≈ 86.8 мкс`.
   - Затримка між кадрами (3.5 символи): `3.5 · 86.8 мкс ≈ 304 мкс`.

Ці цифри показують, що на високих швидкостях (115200 бод і вище) програмне перемикання піна `DE` в операційних системах реального часу (FreeRTOS, Zephyr) або за допомогою затримок стає ненадійним через джиттер переривань та квантування часу ОС. Якщо переривання запізниться бодай на 100 мікросекунд, шина лишиться заблокованою на цілий байтовий інтервал.

### Апаратне автоматичне керування DE (Hardware Auto-Direction)

Сучасні мікроконтролери (STM32 родини F4/F7/H7/G4, ESP32-S3, NXP LPC, Microchip SAM) містять вбудовану підтримку режиму RS-485 безпосередньо у периферичному модулі USART/UART.

У цьому режимі один із виводів мікроконтролера (наприклад, `USART1_RTS`) переводиться в альтернативну функцію апаратного сигналу `DE`. Модуль UART самостійно відповідає за часові інтервали:

```
                  ┌─ Старт-біт        ┌─ Стоп-біт
                  ▼                   ▼
Лінія DE: ────────┐───────────────────┌──────── High-Z
                  │   Кадр даних      │
Лінія TX: ────────┴──┴──┴──┴──┴──┴──┴─┴────────
                  ▲                   ▲
                  │                   │
            Driver Enable       Driver Disable
            Assertion Time      De-assertion Time
```

Налаштування апаратного режиму забезпечує дві фундаментальні переваги:
1. **Захист від затримок ОС:** Перемикання виконується апаратними автоматами стану на рівні тактової частоти периферії без участі ядра процесора та без виклику обробників переривань.
2. **Програмовані затримки до й після кадру:** У регістрах `CR1/CR3` можна задати точну кількість тактів (*Assertion / De-assertion Time*), протягом яких пін `DE` піднімається до першого старт-біта та опускається після стоп-біта. Це гарантує стабільну роботу на швидкостях до 10 Мбіт/с.

### Робочий приклад реалізації (C та C++)

Нижче наведено робочі реалізації драйвера керування напрямком RS-485 для систем без апаратного авто-DE.

- У вкладці **C** показано низькорівневий асинхронний драйвер із використанням переривань UART та строгим контролем прапорця `TC` (*Transmission Complete*).
- У вкладці **C++** показано об'єктно-орієнтований драйвер із застосуванням концепції RAII (*Resource Acquisition Is Initialization*) для гарантованого відпускання лінії та безпечної роботи з буферами пам'яті через `std::span`.

```c
// ============================================================================
// Мова C: Низькорівневий драйвер RS-485 з перериванням Transmission Complete
// ============================================================================
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>

// Абстракція низькорівневого HAL мікроконтролера
extern void gpio_set_de_high(void);
extern void gpio_set_de_low(void);
extern void uart_hardware_send_byte(uint8_t byte);
extern bool uart_is_tx_complete(void);

typedef struct {
    const uint8_t *tx_buffer;
    size_t         tx_size;
    volatile size_t tx_index;
    volatile bool   is_busy;
} rs485_driver_t;

static rs485_driver_t g_rs485 = {0};

// Запуск асинхронної відправки блоку даних по RS-485
bool rs485_send_async(rs485_driver_t *drv, const uint8_t *data, size_t len) {
    if (drv->is_busy || len == 0 || data == NULL) {
        return false; // Передача вже триває або невірні параметри
    }

    drv->tx_buffer = data;
    drv->tx_size   = len;
    drv->tx_index  = 0;
    drv->is_busy   = true;

    // Крок 1: Захоплюємо шину — піднімаємо пін DE у HIGH
    gpio_set_de_high();

    // Крок 2: Відправляємо перший байт у зсувний регістр UART
    uart_hardware_send_byte(drv->tx_buffer[drv->tx_index++]);

    // Подальша передача продовжується у функціях переривання UART
    return true;
}

// Обробник переривання спорожнення буфера передачі та повного кадру (TC)
void USART_IRQHandler(void) {
    // Якщо буфер вільний і є ще байти у черзі
    if (g_rs485.is_busy && (g_rs485.tx_index < g_rs485.tx_size)) {
        uart_hardware_send_byte(g_rs485.tx_buffer[g_rs485.tx_index++]);
    } 
    // Якщо всі байти записані й апаратура підтвердила прапорець TC
    else if (g_rs485.is_busy && uart_is_tx_complete()) {
        // Крок 3: Останній стоп-біт вийшов у дріт — відпускаємо шину
        gpio_set_de_low();
        g_rs485.is_busy = false;
    }
}
```
```cpp
// ============================================================================
// Мова C++: Ідіоматичний RAII-драйвер RS-485 із підтримкою std::span
// ============================================================================
#include <cstdint>
#include <cstddef>
#include <span>
#include <system_error>

class Rs485Bus {
public:
    enum class Direction {
        Receive,
        Transmit
    };

    // Конструктор приймає функціональний вказівник на керування піном DE
    explicit Rs485Bus(void (*set_dir_fn)(Direction)) 
        : set_direction_cb_(set_dir_fn) {
        setDirection(Direction::Receive); // За замовчуванням слухаємо шину
    }

    // RAII-клас для гарантованого автоматичного відпускання шини
    class ScopedTransmitter {
    public:
        explicit ScopedTransmitter(Rs485Bus& bus) : bus_(bus) {
            bus_.setDirection(Direction::Transmit);
        }
        
        ~ScopedTransmitter() {
            bus_.flushHardwareTx(); // Дочекатися прапорця TC перед відпусканням
            bus_.setDirection(Direction::Receive); // Гарантовано відпустити шину
        }

        ScopedTransmitter(const ScopedTransmitter&) = delete;
        ScopedTransmitter& operator=(const ScopedTransmitter&) = delete;

    private:
        Rs485Bus& bus_;
    };

    // Синхронна передача блоку даних через безпечний константний span
    std::error_code send(std::span<const std::uint8_t> data) {
        if (data.empty()) {
            return std::make_error_code(std::errc::invalid_argument);
        }

        // RAII-об'єкт автоматично захоплює шину і опускає DE при виході з зони видимості
        ScopedTransmitter tx_guard(*this);

        for (std::uint8_t byte : data) {
            sendHardwareByte(byte);
        }

        return {}; // Передачу виконано успішно
    }

private:
    void setDirection(Direction dir) {
        if (set_direction_cb_) {
            set_direction_cb_(dir);
        }
    }

    void sendHardwareByte(std::uint8_t byte) {
        extern void platform_uart_write(std::uint8_t);
        platform_uart_write(byte);
    }

    void flushHardwareTx() {
        // Очікування прапорця TC (Transmission Complete) на рівні периферії
        extern void platform_uart_wait_tc(void);
        platform_uart_wait_tc();
    }

    void (*set_direction_cb_)(Direction);
};
```

### Діагностика граблей і типових помилок

При налагодженні драйвера RS-485 осцилографом або логічним аналізатором слід звертати увагу на такі поширені дефекти:

1. **Зсув першого старт-біта:** Якщо пін `DE` піднімається одночасно з записом у регістр `DR/TDR`, на деяких повільних мікросхемах трансиверів перші наносекунди старт-біта можуть просісти, бо трансивер не встиг вийти з High-Z. Ліки: додавати невелику паузу в 1..2 мікросекунди між підйомом `DE` та записом байта.
2. **Низька швидкість зсуву сигналу DE у програмі:** Якщо перемикання піна `DE` виконується через повільні операційні виклики (наприклад, виклики через системний шар шини або розширювач портів I²C), затримка вимкнення становитиме декілька мілісекунд, що унеможливить роботу напівдуплексних протоколів типу Modbus RTU.
