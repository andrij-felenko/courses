# ⚙️ Пачковий канал у симуляції: перемішування на власні очі

Розмови про те, що перемішування перетворює пачку на розсіяні помилки, звучать переконливо — та переконливість дешева. Справжня перевірка одна: зібрати весь ланцюг у коді, пропустити крізь нього мільйони бітів і подивитися на числа. Тому зберемо повний пачковий канал у Python — від джерела бітів до підрахунку залишкових помилок — і покрутимо єдину ручку, глибину перемішування, доки на власні очі не побачимо, де воно рятує день, а де безсило.

Python тут обраний не випадково. Уся винагорода цієї вправи — статистика: розподіли, залишкові частоти, криві. Мова, де за три рядки збираєш гістограму й одразу читаєш форму, важить більше за швидкодію — потік ми і так проганяємо офлайн, а не в реальному ефірі. Це не той випадок, де кожна наносекунда на бит вирішує; це той випадок, де вирішує ясність цифри.

## Що будуємо і що міряємо

Ланцюг простий і чесний, рівно як у справжній лінії:

```
джерело даних → блоковий код → перемішувач → КАНАЛ (з пам'яттю) → розперемішувач → декодер → лічильник помилок
```

Питання, на які має відповісти симуляція, теж прості:

- як залежить **залишкова частота помилок** у даних від глибини перемішування;
- як виглядає **розподіл помилок на кодове слово** без перемішування й із ним — та сама пачка, дві різні картини;
- скільки коштує глибина в **затримці** — той вічний компроміс;
- і де саме **замала глибина** ламається об довгу пачку.

Останнє — не дрібниця, а головна пастка всієї теми, і ми виведемо її не з міркувань, а з виміру.

## Ідея: конвеєр із чотирьох чесних дрібниць

Уся симуляція — це чотири маленькі частини, кожна на кілька рядків, з'єднані в конвеєр:

1. **Канал із пам'яттю**, що зумисне робить пачки, — модель Гілберта–Елліота.
2. **Простий блоковий код** із бюджетом рівно одна помилка на слово — Геммінг(7,4).
3. **Блоковий перемішувач** — запис у рядки, читання стовпцями.
4. **Вимірювач** — прогнати, розперемішати, декодувати, порахувати.

А тоді крутимо одну-єдину ручку — глибину — і дивимося, як конвеєр оживає. Розберімо частини по черзі.

## Канал, що робить пачки

Пачки беруться не з окремих незалежних невдач, а з того, що канал застрягає в поганому стані на низку бітів поспіль. Найпростіше змалювати це [моделлю Гілберта–Елліота](book:communications/gilbert-elliott-model): два стани — добрий і поганий, — між якими канал перескакує, і поганий стан **липкий**.

Замість того щоб щоразу гнати біти крізь автомат, зробимо ефективніше: один раз згенеруємо **маску помилок** уздовж позицій ефіру — де саме канал перевернув біт. Дві ймовірності керують переходами: `p` — шанс зіскочити з доброго стану в поганий, `r` — шанс вибратися назад. У поганому стані біт псується з ймовірністю `e_bad`, у доброму — майже ніколи.

```py
import random

def ge_mask(n, p=0.0003, r=0.03, e_good=0.0, e_bad=0.4, seed=7):
    """Маска помилок каналу Гілберта–Елліота вздовж n позицій ефіру.
    p: G→B (рідко), r: B→G (вихід із пачки), e_bad: густота помилок у поганому стані."""
    rng = random.Random(seed)
    bad = False
    mask = [0] * n
    runs = []                          # довжини поганих епізодів — для статистики
    run = 0
    for i in range(n):
        e = e_bad if bad else e_good
        if rng.random() < e:
            mask[i] = 1                 # канал перевернув цей біт
        if bad:
            run += 1
            if rng.random() < r:        # вибираємось із поганого стану
                bad = False; runs.append(run); run = 0
        else:
            if rng.random() < p:        # провалюємось у поганий стан
                bad = True
    if run:
        runs.append(run)
    return mask, runs
```

Двох параметрів досить, щоб керувати «пачковістю». Середня довжина поганого епізоду — це очікування геометричного розподілу:

```
середній поганий пробіг ≈ 1 / r          # r = 0.03  →  ≈ 33 біти
частка часу в поганому стані = p / (p + r)  # ≈ 0.0099, тобто ~1 %
```

Прогін на потоці в 64 000 слів по 7 бітів (448 000 бітів ефіру) дає рівно те, що обіцяє теорія:

```
air bits: 448000 | raw channel BER: 0.00381 | bad episodes: 126
mean bad run: 33.4 | max bad run: 169
```

Середня пачка — 33 біти, але хвіст розподілу тягнеться аж до **169 бітів** в одному епізоді. Запам'ятаймо це число: саме воно, а не середнє, вирішить долю нашого перемішування.

> 🔧 **Навіщо це.** Маску ми генеруємо **раз** і застосовуємо однаково до всіх глибин. Це не оптимізація заради швидкості — це умова чесності досліду. Канал не знає й не мусить знати, як ми перемішали біти всередині; він псує фізичні позиції ефіру за своєю пам'яттю. Змінюючи глибину, ми змінюємо лише те, який біт якого слова сидить на кожній позиції, а сам візерунок пачок лишаємо незмінним. Інакше кожна глибина міряла б свій, інший канал — і порівняння нічого не варте б було.

Це рівно протилежність [двійковому симетричному каналу](book:communications/binary-symmetric-channel) з його незалежними помилками: там сусідні біти псуються нарізно, тут — юрбою.

## Простий код із бюджетом «одна на слово»

Тепер код, що ремонтує. Візьмемо [код Геммінга](book:communications/hamming-code) (7,4): чотири біти даних загортаються в семибітове слово, і код гарантовано виправляє **одну** перевернуту помилку в слові. Це і є той «бюджет одна на слово», навколо якого крутиться вся вправа: одна помилка — код мовчки лагодить; дві й більше — губиться й нерідко «виправляє» не туди, псуючи дані ще дужче.

```py
def h74_encode(d):                     # d: 4 біти даних → 7 бітів слова
    d1, d2, d3, d4 = d
    p1 = d1 ^ d2 ^ d4
    p2 = d1 ^ d3 ^ d4
    p3 = d2 ^ d3 ^ d4
    return [p1, p2, d1, p3, d2, d3, d4]

def h74_decode(c):                     # 7 бітів (можливо з помилкою) → 4 біти даних
    p1, p2, d1, p3, d2, d3, d4 = c
    s1 = p1 ^ d1 ^ d2 ^ d4
    s2 = p2 ^ d1 ^ d3 ^ d4
    s3 = p3 ^ d2 ^ d3 ^ d4
    syn = s1 + (s2 << 1) + (s3 << 2)   # 0 — чисто; інакше синдром = позиція помилки (1..7)
    if syn:
        c = c[:]                       # не псуємо вхід
        c[syn - 1] ^= 1                # перевертаємо підозрілий біт назад
    return [c[2], c[4], c[5], c[6]]    # d1, d2, d3, d4
```

Синдром — це трибітове число, що прямо вказує позицію єдиної помилки: якщо він не нуль, перевертаємо той біт, і слово знову чисте. Проста, дешева, класична машинка з бюджетом рівно на одну помилку. Далі побачимо, як пачка легко перевищує цей бюджет — і як перемішування повертає його в гру.

## Блоковий перемішувач

Ось серце вправи. Беремо `D` кодових слів, пишемо їх у **рядки** матриці `D × W` (де `W = 7`), а в ефір відсилаємо **стовпцями**. На приймачі складаємо стовпці назад у матрицю й читаємо рядки — і кожне слово знову ціле.

```py
def interleave(words, D):
    """Пише D слів у рядки, читає стовпцями → плаский потік бітів ефіру."""
    W = len(words[0]); air = []
    for base in range(0, len(words), D):
        block = words[base:base + D]
        for col in range(W):
            for row in range(D):
                air.append(block[row][col])
    return air

def deinterleave(air, D, W, nwords):
    """Зворотна дія: складає стовпці назад у D×W і повертає слова."""
    words = []; per = D * W
    for base in range(0, len(air), per):
        chunk = air[base:base + per]
        block = [[0] * W for _ in range(D)]
        k = 0
        for col in range(W):
            for row in range(D):
                block[row][col] = chunk[k]; k += 1
        words.extend(block)
    return words[:nwords]
```

Чому саме `D` і є та максимальна пачка, яку перемішувач знешкоджує? Погляньмо на порядок в ефірі. Сусідні позиції ефіру йдуть **вниз по рядках** одного стовпця: позиція 0 — рядок 0, позиція 1 — рядок 1, і так `D` разів, аж поки не почнеться наступний стовпець. Отже, два біти ефіру потраплять в **одне** слово (той самий рядок) лише тоді, коли їхні позиції різняться рівно на `D`. Пачка завдовжки `b ≤ D` займає `b` сусідніх позицій — усі різні рядки, по одній помилці на слово, точно в межах бюджету. А пачка `b = D + 1` вперше зачепить якийсь рядок **двічі** — і те слово мертве.

Один рядок кода — і маємо точну межу: **перемішувач глибини `D` перетворює будь-яку пачку завдовжки до `D` бітів на щонайбільше одну помилку на слово.** Незалежно від `W`. Саме цю обіцянку ми зараз і перевіримо числом. Докладніше про самі схеми — у [перемішуванні](book:communications/interleaving).

(Одна тонкість, до якої повернемось у пастках: потік слів доповнюють нулями до кратного `D`, інакше останній, неповний блок зсуне лік стовпців — і розперемішувач розсинхронізується.)

## Крутимо ручку глибини

Зберемо конвеєр докупи. Джерело — псевдовипадкові дані; кожне слово кодуємо, весь потік перемішуємо, накладаємо **ту саму** маску каналу, розперемішуємо, декодуємо й рахуємо, скільки бітів **даних** лишилося зіпсованими.

```py
from collections import Counter

NW, W = 64000, 7
rng = random.Random(1)
data = [[rng.randint(0, 1) for _ in range(4)] for _ in range(NW)]
codewords = [h74_encode(d) for d in data]
mask, runs = ge_mask(NW * W)           # маска каналу — одна на всі глибини

def run(D):
    air = interleave(codewords, D)
    air = [b ^ m for b, m in zip(air, mask)]     # канал псує біти
    recv = deinterleave(air, D, W, NW)
    bit_err = 0
    hist = Counter()
    for i in range(NW):
        chan = sum(a ^ b for a, b in zip(codewords[i], recv[i]))  # помилок каналу у слові
        hist[chan] += 1
        dec = h74_decode(recv[i])
        bit_err += sum(a ^ b for a, b in zip(data[i], dec))       # залишок у даних
    return bit_err / (NW * 4), hist

for D in [1, 2, 4, 8, 16, 32, 64, 128, 256]:
    ber, _ = run(D)
    print("D=%-4d  залишковий BER даних = %.6f" % (D, ber))
```

Ось що друкує прогін:

```
D=1     залишковий BER даних = 0.003973
D=2     залишковий BER даних = 0.004031
D=4     залишковий BER даних = 0.003457
D=8     залишковий BER даних = 0.003277
D=16    залишковий BER даних = 0.002625
D=32    залишковий BER даних = 0.001500
D=64    залишковий BER даних = 0.000629
D=128   залишковий BER даних = 0.000145
D=256   залишковий BER даних = 0.000145
```

Прочитаймо цю драбину. Без перемішування (`D = 1`) залишок — **0.40 %**, майже тотожний сирій частоті помилок каналу (0.38 %). Код не дав нічого — ба навіть ледь нашкодив: пачка вкидає в поодинокі слова по три-сім помилок, декодер губиться й «виправляє» не туди, а сім бітів слова замість чотирьох даних лише збільшують поверхню, яку канал може вжалити. Уся надлишковість Геммінга змарнована, бо пачка витратила бюджет в одній точці.

Далі, поки глибина мала (`D = 2…8`), майже нічого не змінюється: пачка на 33 біти й досі накриває кілька рядків матриці по кілька разів. І лише коли глибина підповзає до довжини пачки, драбина обвалюється: `D = 32` дає покращення в 2.6 раза, `D = 64` — уже в 6, `D = 128` — у 27 разів. А тоді все завмирає: `D = 256` не кращий за `D = 128`. Ми вперлися в **підлогу** — залишок, який глибиною вже не збити.

## Розподіл помилок на слово: до і після

Драбина каже *скільки*, але не показує *чому*. Аби побачити механізм, порахуймо гістограму: скільки помилок каналу випало на кодове слово — до декодування — без перемішування й із ним.

![Дві панелі стовпчиків на спільній шкалі 0–100 %: скільки з уражених слів дістали рівно k помилок каналу. Ліворуч (D=1) стовпчики розповзлися від 1 до 7, більшість слів має 2–4 помилки — далеко за бюджетом. Праворуч (D=64) майже все зібралося в одному зеленому стовпчику на k=1, крихітні червоні залишки на k=2,3.](/book/communications/coding-theory/burst-error/img/proj-per-word.svg)

*Зліва від пунктирної межі бюджету код лагодить; справа — мертві слова. Без перемішування уражені слова розсипані по 1–7 помилок, більшість — за межею. З глибоким перемішуванням майже кожне уражене слово має рівно одну помилку — усередині бюджету.*

Числа під картинкою промовисті:

```
D=1  : {0: 63348, 1: 136, 2: 181, 3: 179, 4: 117, 5: 31, 6: 6, 7: 2}   мертвих слів (≥2): 516
D=64 : {0: 62396, 1: 1503, 2: 98, 3: 3}                                 мертвих слів (≥2): 101
```

Ось уся суть в одному рядку. Без перемішування слів із **однією** помилкою — усього 136, зате аж 516 слів дістали по дві-сім і полягли; пачка воліє бити купно. З перемішуванням картина перевертається: слів з однією помилкою — 1503 (усі виправні!), а «мертвих» лишилося вп'ятеро менше, 101. Перемішування **не прибрало жодної помилки** — сумарна їх кількість та сама. Воно лише **пересунуло** їх із купи в бюджет коду: розтягнуло щільний згусток у тонку низку, де кожне слово зачеплене найбільше раз.

## Крива залишку і ціна глибини

Складімо всю драбину в одну криву — і одразу видно її форму: пласке плато, обрив, підлога.

![Напівлогарифмічна крива: залишковий BER даних (вісь 10⁻² … 10⁻⁴) проти глибини перемішування 1…256. Крива тримається біля 4·10⁻³ до глибини ~16, потім круто падає між 32 і 128 і виходить на пласку підлогу ≈1.4·10⁻⁴. Дві червоні вертикалі позначають середню пачку (≈33 біти) і найдовшу (≈169) — обрив кривої лягає саме між ними.](/book/communications/coding-theory/burst-error/img/proj-residual-depth.svg)

*Обрив збігається не з середньою пачкою, а тягнеться аж за найдовшу. Підлога ≈1.4·10⁻⁴ — це те, чого самою глибиною вже не позбутися.*

Крива каже дві речі, і обидві коштовні. Перша: **обрив лягає за довжиною пачки, а не за глибиною наосліп.** Середня пачка — 33 біти; на `D = 32` (тобто рівно на середню!) залишок упав лише в 2.6 раза — сміховинно мало. Аби по-справжньому приборкати канал, глибина мусить перекрити **хвіст** розподілу: найдовшу пачку в 169 бітів, а не типову. Тому `D = 256` і виходить на підлогу — воно нарешті ширше за найдовший провал.

> 🔧 **Навіщо це.** Проєктувати перемішування за середньою пачкою — класична й дорога помилка. Канал вбиває вас не типовим провалом, а рідкісним довгим — тим самим хвостом, який середнє ховає. Правило просте: **бери глибину з добрячим запасом над найгіршою очікуваною пачкою, а не над середньою.** У нашому досліді різниця між «за середньою» (`D = 32`, залишок 1.5·10⁻³) і «за хвостом» (`D = 128`, залишок 1.4·10⁻⁴) — цілий порядок надійності.

Друга річ — ціна. Глибина не безкоштовна, і платимо ми затримкою: щоб відіслати перший стовпець, треба спершу назбирати всі `D` слів у буфер, і те саме повторюється на приймачі. Груба оцінка наскрізної затримки:

```
затримка ≈ 2 · D · W бітів    (буфер на передавачі + буфер на приймачі)
```

Для нашої підлоги `D = 128` це буфер на 128 слів по 7 бітів із кожного боку — сотні бітів чекання. Для потокового відео чи файлу — дрібниця; для голосу чи керма, де кожна зайва мілісекунда відчутна, — уже боляче. Ось він, вічний компроміс: глибина проти латентності, надійність проти живості.

## Згортковий перемішувач: та сама сила, вдвічі дешевше

Блоковий перемішувач мусить назбирати цілий блок `D × W`, перш ніж хоч щось відіслати. А що, як розтягувати потік **безперервно**, без пауз на цілі блоки? Це і робить **згортковий перемішувач** — розкладка з набору ліній затримки різної довжини (Дж. Л. Ремзі, 1970; Ґ. Д. Форні, 1971; це доведено **оптимальні** схеми за пам'яттю й затримкою).

Ідея така: `N` гілок, гілка `j` має чергу-затримку на `j·M` символів; комутатор по черзі кидає символи в гілки `0, 1, …, N−1` і одразу знімає з них те, що виповзло. Розперемішувач дзеркальний — гілка `j` затримує на `(N−1−j)·M`, щоб сумарна затримка кожної гілки була однакова й потік вирівнявся.

```py
def conv_interleave(stream, N, M):
    fifos = [[0] * (j * M) for j in range(N)]      # гілка j: черга на j·M символів
    out = []
    for i, s in enumerate(stream):
        j = i % N
        if j == 0:
            out.append(s)                          # гілка 0 без затримки — наскрізь
        else:
            fifos[j].append(s); out.append(fifos[j].pop(0))
    return out

def conv_deinterleave(stream, N, M):
    fifos = [[0] * ((N - 1 - j) * M) for j in range(N)]   # дзеркальні затримки
    out = []
    for i, s in enumerate(stream):
        j = i % N
        if (N - 1 - j) * M == 0:
            out.append(s)
        else:
            fifos[j].append(s); out.append(fifos[j].pop(0))
    return out
```

Прогін підтверджує, що це точна пара (потік відновлюється після сталої затримки), і дає формули пам'яті та латентності:

```
N=8, M=4 : наскрізна затримка = 224 символи,  пам'ять = 112 комірок
загалом:   затримка = N·(N−1)·M символів,     пам'ять = M·N·(N−1)/2 на бік
```

А тепер порівняння, заради якого все й затівалося. Щоб перекрити пачку розмаху `B`, блоковий перемішувач буферизує близько `B²` символів і додає затримку близько `2B²`; згортковий за ту саму захисну спроможність обходиться приблизно **вдвічі меншою** пам'яттю й затримкою. Саме тому глибокі стандарти — DVB, ADSL — беруть згортковий, а не блоковий: та сама стійкість до пачок за половину ціни в буферах і в очікуванні.

## Складність і пастки

Обчислювально симуляція тривіальна — `O(біти)` за часом, `O(D·W)` за пам'яттю для блокового перемішувача. Уся глибина ховається не в алгоритмі, а в пастках, і кожну ми щойно бачили на числах.

**Замала глибина проти довгих пачок — головна пастка.** Драбина `D` показала: глибина, підігнана під **середню** пачку, майже не допомагає (2.6 раза на `D = 32`). Захист вмикається, лише коли `D` перекриває **найдовшу** очікувану пачку. Проєктуйте за хвостом розподілу, не за його серединою.

**Крайові ефекти буфера.** Потік слів ми доповнили нулями до кратного `D`. Це не косметика: якщо останній блок неповний, розперемішувач порахує не ту кількість стовпців і зсунеться — а зсув у перемішувачі не псує один біт, він **розвалює цілі чисті слова**, бо кладе їх вміст не на свої місця. У згортковому перемішувачі та сама пастка вбрана інакше: перші `N·(N−1)·M` символів на виході — це прогрів затримок (нулі), і їх треба відкинути, інакше приймач прийме сміття за дані. Межі буфера — там, де тихо гинуть симуляції, що «майже працюють».

**Латентність — справжня ціна.** Затримка росте лінійно з глибиною (`≈ 2·D·W`), і для інтерактивних ліній вона стеля значно раніша за пам'ять. Найнадійніша у світі глибина марна, якщо канал возить голос і не терпить буфера на сотні бітів.

**Перемішування не додає жодного надлишку — тому саме воно не рятує.** Це, мабуть, найважливіше. Перемішувач лише **пересуває** помилки; ремонтує їх код. Тому лишається підлога: `D = 256` дало 14 слів із двома помилками не тому, що пачка довша за глибину, а тому, що **два незалежні погані епізоди** випадково влучили в одне слово — збіг, який жодна глибина не прибере. А в реальному каналі до цього додається ще й рідкий шум доброго стану (спробуйте `e_good > 0`): він уже розсіяний, перемішувати його нікуди, і витягує його **тільки код**. Ось чому справжні системи ставлять і те, і те разом: глибоке перемішування плюс сильний символьний код — як [конкатенація](book:communications/concatenated-codes) Ріда–Соломона з перемішуванням у компакт-диску. Перемішування готує поле; код збирає врожай.

Головний висновок вправи не в жодній окремій цифрі, а в тому, що ми жодної з них не приймали на віру. Ми зібрали канал, який справді має пам'ять, пропустили крізь нього справжній код і справжнє перемішування — і драбина глибин, гістограма слів та крива залишку самі, без умовлянь, показали і силу перемішування, і точну межу цієї сили.
