# ⚙️ Монте-Карло симулятор BER: виміряти криву, а не повірити формулі

Формула `BER = Q(√(2·Eb/N₀))` обіцяє точну криву надійності. Але формула — це модель, а модель варта рівно стільки, скільки її припущення. Реальний приймач має скінченну арифметику, неідеальний поріг, можливо ще й код виправлення помилок зверху — а для згорткового коду чи LDPC замкненої формули BER **узагалі немає**, її нічим порахувати на папері. Тож рано чи пізно інженер ставить пряме питання: чи справді **мій** канал лягає на теоретичну криву — і де саме він від неї відхиляється?

Чесна відповідь одна: прогнати крізь модель каналу мільйони випадкових бітів і полічити, скільки зламалося. Це і є **метод Монте-Карло** — замінити інтеграл, який важко (або неможливо) взяти аналітично, підрахунком частоти у великій випадковій вибірці. Завдання цього проєкту: побудувати такий симулятор для BPSK, дістати з нього криву окремими точками, накласти їх на теоретичну `Q` — і, що найважливіше, навчитися бачити, **коли точці можна вірити, а коли вона тихо бреше**.

## Ідея: канал у п'ять рядків

Уся модель каналу — п'ять кроків, і кожен відповідає одному фізичному явищу:

```
1. біти:    b ∈ {0, 1}              джерело даних
2. BPSK:    s = 2b − 1 ∈ {−1, +1}   0 → −1,  1 → +1  (енергія біта Eb = 1)
3. канал:   r = s + n,  n ~ N(0, σ²)  додаємо гаусів шум
4. рішення: b̂ = [ r > 0 ]           поріг у нулі: дивимось на знак
5. лік:     помилка ⟺ b̂ ≠ b         рахуємо розбіжності
```

Другий рядок — це модуляція [BPSK](book:communications/fsk-psk), де нуль і одиниця — та сама несуча з протилежною фазою, тож на числовій осі вони стають просто `−1` і `+1`. Третій рядок — це [канал AWGN](book:communications/awgn-channel): він додає до символа гаусів шумовий поштовх, і на одну дійсну координату сигналу припадає дисперсія `σ² = N₀/2` (половина, бо `N₀` — двобічна спектральна густина потужності шуму). Четвертий рядок — оптимальне рішення для рівноймовірних символів: поріг стоїть точно посередині між `−1` і `+1`, тобто в нулі, і приймач лише дивиться на знак прийнятого числа.

Чотири з п'яти рядків очевидні. Уся тонкість — у третьому: **яким має бути σ**, щоб симуляція відтворювала саме заданий `Eb/N₀`, а не якийсь інший? Це та єдина точка, де ламається більшість саморобних симуляторів, тож виведімо σ повільно й до кінця.

Домовмося брати одиничну енергію біта: `s = ±1`, отже `Eb = s² = 1`. Тоді відношення `Eb/N₀ = γ` (у разах) однозначно задає густину шуму, а з неї — потрібне відхилення:

```
γ    = 10^( Eb/N₀[дБ] / 10 )      переклад децибел у рази
N₀   = Eb / γ = 1/γ                бо Eb = 1
σ²   = N₀ / 2 = 1/(2γ)             дисперсія шуму на дійсну координату
σ    = 1 / √(2γ)                   оце й підставляємо в код
```

Перевірмо, що ця σ справді відтворює теорію, — інакше симулятор «підтверджуватиме» неправильну криву. Помилка стається, коли слали `+1`, а шум збив прийняте число за поріг, тобто `n < −1`. Для гаусіани з відхиленням σ ця площа хвоста дорівнює `Q(1/σ)`:

```
P(помилка) = P(n < −1),  n ~ N(0, σ²)
           = Q( 1/σ ) = Q( √(2γ) ) = Q( √(2·Eb/N₀) )
```

Рівно та формула, проти якої ми зіставлятимемо точки. Отже нормування правильне **за побудовою** — не бо «так у книжці», а бо ми його щойно вивели з тих самих означень, що й теорію.

> 🔧 **Навіщо це.** Монте-Карло — це не «недороблена теорія для лінивих», а єдиний інструмент там, де теорії немає: закодований канал, нелінійний підсилювач, завмирання з пам'яттю, самопальний декодер. Симулятор не питає, чи існує формула, — він просто рахує помилки. Ціна цієї універсальності — статистика: кожна точка тепер випадкова, і половина роботи інженера полягає в тому, щоб відрізнити справжній результат від шуму власного експерименту.

## Робочий код: точка, потім уся крива

Ключове рішення в конструкції — **не фіксувати кількість бітів**. Замість «прогнати рівно 10⁶ біт» симулятор крутить блоки доти, доки не назбирає задане число помилок (скажімо, 200). Це саме собою робить дві потрібні речі: на кожну точку припадає **достатньо** помилок, щоб їй вірити, а робота автоматично росте там, де BER мала, і не витрачається дарма там, де помилок і так купа.

Серце — симулятор однієї точки за фіксованого `Eb/N₀`. Python із `numpy` векторизує весь блок в одну операцію, і це ідіоматично для аналізу; C++ той самий крок робить у тісному циклі з пам'яттю `O(1)` — і саме він потрібен, коли `BER` западає так низько, що жоден масив у пам'ять уже не влазить. Обидві мови лягають, тож ось той самий симулятор у двох:

:::tabs
```python
import numpy as np
import math

def simulate_ber(ebn0_db, target_errors=200, block=200_000,
                 max_bits=10**10, rng=None):
    """Емпірична BER для BPSK за одного Eb/N0.
    Крутить блоки бітів, доки не збере target_errors помилок
    (або не впреться в max_bits — щоб не зависнути на дні кривої)."""
    rng = rng or np.random.default_rng()
    g = 10 ** (ebn0_db / 10)           # Eb/N0 у рази
    sigma = 1.0 / math.sqrt(2 * g)     # σ² = N0/2 = 1/(2γ),  Eb = 1

    errors = total = 0
    while errors < target_errors and total < max_bits:
        bits = rng.integers(0, 2, block)                  # 1. джерело
        symb = 2 * bits - 1                                # 2. BPSK: 0→−1, 1→+1
        recv = symb + sigma * rng.standard_normal(block)   # 3. + шум AWGN
        decided = (recv > 0).astype(np.int8)               # 4. поріг у нулі
        errors += int(np.count_nonzero(decided != bits))   # 5. лічимо
        total += block
    return errors / total, errors, total
```
```cpp
#include <cstdint>
#include <cmath>
#include <random>

// Емпірична BER для BPSK за одного Eb/N0 — тісний цикл, пам'ять O(1).
// Крутить біти по одному, доки не збере target_errors помилок.
struct Result { double ber; uint64_t errors, total; };

Result simulate_ber(double ebn0_db,
                    uint64_t target_errors = 200,
                    uint64_t max_bits = 100'000'000'000ULL,
                    uint64_t seed = 2024) {
    const double g     = std::pow(10.0, ebn0_db / 10.0);  // Eb/N0 у рази
    const double sigma = 1.0 / std::sqrt(2.0 * g);        // σ² = N0/2 = 1/(2γ)

    std::mt19937_64 gen(seed);
    std::bernoulli_distribution src(0.5);                 // джерело бітів
    std::normal_distribution<double> noise(0.0, sigma);   // шум AWGN

    uint64_t errors = 0, total = 0;
    while (errors < target_errors && total < max_bits) {
        int    bit = src(gen);              // 0 або 1
        double s   = 2 * bit - 1;           // BPSK: 0→−1, 1→+1
        double r   = s + noise(gen);        // + шум
        int    dec = (r > 0.0) ? 1 : 0;     // поріг у нулі
        errors += (dec != bit);             // лічимо розбіжність
        ++total;
    }
    return { double(errors) / total, errors, total };
}
```
:::

Різниця не косметична. Python тримає в пам'яті цілий блок (`200 000` чисел `float64` ≈ 1.6 МБ) і обробляє його однією векторною командою — швидко й читко для звичайних `BER`. C++ не тримає **нічого**: кожен біт живе наносекунду в регістрі й забувається. Саме це дає йому змогу дійти туди, куди Python уже фізично не може, — про що нижче.

Тепер обгортка: пробіг по діапазону `Eb/N₀` і накладання на теорію. Це чистий аналіз, домівка Python, тож без вкладок:

```python
def q_bpsk(ebn0_db):                       # теорія, проти якої зіставляємо
    g = 10 ** (ebn0_db / 10)
    return 0.5 * math.erfc(math.sqrt(g))   # = Q(√(2·Eb/N0))

rng = np.random.default_rng(2024)          # одне зерно на весь пробіг
print(f"{'Eb/N0':>6} {'симуляція':>12} {'теорія':>11} {'помилок':>9} {'бітів':>10}")
for db in range(0, 11):
    ber, K, N = simulate_ber(db, target_errors=200, rng=rng)
    print(f"{db:>4} дБ {ber:>12.2e} {q_bpsk(db):>11.2e} {K:>9} {N:>10.1e}")
```

Два стовпці цифр збігаються до частки децибела на всьому діапазоні — симулятор працює, теорія підтверджена емпірично. Але найцікавіше сховане у стовпці «бітів». На `0 дБ` симулятор набрав шістнадцять тисяч помилок за жалюгідні `200 000` біт. На `10 дБ`, щоб набрати ті самі дві сотні помилок, довелося прогнати **51 мільйон** біт — у двісті п'ятдесят разів більше. Ось вона, ціна руху вниз по водоспаду: кожні кілька децибелів вглиб множать роботу на порядок. Накладімо ці точки на криву й позначмо, котрим із них можна вірити:

*Надійні точки (сотні помилок) лягають просто на теорію, і їхні «вуса» довірчого інтервалу крихітні. «Голодні» точки з кількома помилками розсипаються навколо кривої, а точка, де за весь прогін не трапилось жодної помилки, взагалі провалюється на фальшиве «дно» `1/N` — артефакт скінченної вибірки, а не властивість каналу.*

Ця картинка — уся мораль проєкту в одному кадрі. Симулятор легко написати; важко — **не обманутися його виходом**. Розберімо чотири пастки, кожна з яких псує саме цю картинку.

## Пастка 1 — нормування шуму

Найпідступніша помилка живе в одному рядку: `sigma`. Забути поділити `N₀` на два, переплутати дисперсію з відхиленням, узяти амплітуду `√Eb` за неодиничного `Eb` — і симулятор працюватиме **бездоганно на вигляд**: гладкий водоспад, гарні точки. Просто не той. Порахуймо, чого коштує один такий недогляд — забути горезвісну двійку:

```
правильно:  σ = 1/√(2γ)  →  виміряна BER = Q(1/σ) = Q(√(2γ))
забули /2:  σ = 1/√γ      →  виміряна BER = Q(1/σ) = Q(√γ) = Q(√(2γ)/√2)
```

`Q(√γ)` — це крива для `Eb/N₀`, меншого рівно вдвічі. У децибелах уся крива тихо поповзла праворуч на `10·log₁₀2 ≈ 3.01 дБ`. Три децибели помилки, і жодного попередження: канал просто «виявився» на три децибели гіршим, ніж він є. Для бюджету лінка це катастрофа — саме стільки часом становить увесь запас на завмирання.

Захист єдиний і дешевий: **завжди накладай теорію**. Якщо точки лягають на `Q(√(2·Eb/N₀))` по всьому діапазону — σ правильна. Якщо вони йдуть гарною кривою, але паралельно зсунуті вбік на сталу кількість децибелів — σ неправильна рівно на цей зсув, і його видно з першого графіка. Симулятор без накладеної теорії — це прилад без повірки: показує впевнено, а що саме — невідомо.

## Пастка 2 — замало помилок: правило сотні

Оцінка `p̂ = K/N` — не число, а **випадкова величина**: заново запусти з іншим зерном — дістанеш інше `p̂`. Наскільки інше, диктує число зібраних помилок `K`, а не число прогнаних бітів `N`. Розкладімо чому. Кількість помилок `K` — це [біноміальна випадкова величина](book:math/binomial-distribution): `N` незалежних спроб, кожна псує біт з імовірністю `p`, тож дисперсія лічильника — `N·p·(1−p)`. За малих `p` (а на дні кривої `p` крихітна) це майже `N·p = K̄` — біном стискається в розподіл Пуассона, де відхилення дорівнює корінню із середнього:

```
K̄ = N·p         очікуване число помилок
σ_K ≈ √(N·p) = √K̄   відхилення лічильника (пуассонівська межа)

відносна похибка оцінки:   σ_K / K̄  =  √K̄ / K̄  =  1/√K̄  ≈  1/√K
```

Ось і весь секрет «правила сотні». Точність залежить **тільки** від числа зібраних помилок:

```
K = 4    →  1/√4   = ±50 %      точка майже нічого не значить
K = 25   →  1/√25  = ±20 %
K = 100  →  1/√100 = ±10 %      прийнятно для інженерної кривої
K = 1000 →  1/√1000 = ±3.2 %    вже гладко
```

![Лійка точності Монте-Карло: горизонтальна вісь — число зібраних помилок K у логарифмічній шкалі від 10 до 1000, вертикальна — відношення оцінки до істинної BER, дзвіноподібна лійка ±1/√K звужується з ростом K; підписи ±32 % при K=10, ±18 % при K=30, ±10 % при K=100, ±5.8 % при K=300, ±3.2 % при K=1000.](/book/communications/coding-theory/ber-snr-curve/img/mc-precision.svg)

*Відносна похибка оцінки тісніє як `1/√K` — з числом **помилок**, а не бітів. Прогнати вдесятеро більше бітів на «легкому» кінці кривої не додасть точності жодній точці на «важкому» кінці: там усе вирішує тільки те, скільки помилок ти встиг зловити.*

Найгірша форма цієї пастки — фіксувати `N` наперед. Візьміть `N = 10⁶` на кожну точку. На високому `Eb/N₀` істинна `BER` западає нижче за `1/N = 10⁻⁶`, симулятор ловить **нуль** помилок, `p̂ = 0`, і точка або зникає (логарифм нуля), або сідає на фальшиве «дно» `1/N`. Крива на графіку ніби «впирається в поличку» — а полички тієї не існує, це просто ваша вибірка вичерпалась. Саме цей провал показує точка на `11 дБ` на картинці вище. Адаптивний цикл «крути, доки не набереш `K` помилок» розчиняє всю проблему одним рухом: він просто не спиняється, поки точці не можна вірити.

## Пастка 3 — точка без похибки бреше про свою точність

Одне голе число `3.6·10⁻⁵` прикидається точним. Воно не точне — це оцінка з довірчим інтервалом, і чесний симулятор мусить той інтервал повідомляти. За нормального наближення біному (воно чинне, щойно `K` не зовсім крихітне) 95-відсотковий інтервал такий:

```
p̂ ± 1.96·√( p̂·(1−p̂) / N )   ≈   p̂ · ( 1 ± 1.96/√K )
```

Тобто для `K = 100` точка відома з точністю близько `±20 %` у сенсі 95 %, для `K = 200` — близько `±14 %`. Один рядок коду — і кожна точка носить свій «вус»:

```python
def ci95(errors, total):
    """95 % довірчий інтервал для BER за нормальним наближенням біному."""
    p = errors / total
    half = 1.96 * math.sqrt(p * (1 - p) / total)   # ≈ p · 1.96/√errors
    return max(0.0, p - half), p + half
```

Вус — це не прикраса, а інструмент рішення. Точка, чий вус накриває теоретичну криву, її **підтверджує**. Точка, чий вус сидить осторонь від кривої, — це вже **справжня** розбіжність, варта розслідування: або баг у симуляторі, або реальний ефект, якого проста формула не бачить (насичення підсилювача, помилка синхронізації, кореляція шуму). Без вуса ці два випадки нерозрізненні — ви не знаєте, дивитесь на сигнал чи на власний статистичний шум. Оце й перетворює «намалював точки» на «виміряв криву».

## Пастка 4 — вартість на самому дні

Рідкісні події дорогі, і дорожчають вони нещадно. Щоб зловити сто помилок за `BER = 10⁻⁹`, треба прогнати:

```
N ≈ 100 / 10⁻⁹ = 10¹¹ біт
```

Сто мільярдів біт на **одну** точку — і звідси два наслідки, обидва з таблиці вище видно наперед. Перший — пам'ять: масив `float64` на `10¹¹` елементів — це `8·10¹¹` байт, **800 гігабайтів**. Жоден `numpy`-масив такого не витримає, тож Python **зобов'язаний** обробляти блоками (як у коді вище), а не одним махом; C++ узагалі не тримає масиву — і саме тому на дні кривої він єдиний виживає. Другий наслідок — час: навіть на `10⁸ біт/с` одна точка `10⁻⁹` — це `≈ 1000 с`, чверть години чекання заради однієї цятки.

Ось де тісний цикл на C/C++ остаточно виправдовує себе: без масиву, зі швидким генератором — і точка, яка в Python рахувалася б годинами, дається за хвилини. А нижче `≈ 10⁻⁹` здається вже й він, і інженери переходять на **вибірку за значущістю** (importance sampling): навмисно підкручують шум, щоб помилки стали частими, ловлять їх дешево, а тоді переважують результат назад — але це вже окремий проєкт. Чесна межа проста: прямий Монте-Карло — це мікроскоп для `BER` десь до `10⁻⁷…10⁻⁸`; глибше треба міняти прилад.

І остання, тиха пастка на все це згори — **генератор випадкових чисел**. Засій його один раз і протягни те саме зерно крізь увесь пробіг (як `rng` у коді), — тоді прогін відтворюваний, а точки статистично незалежні одна від одної. Створиш натомість свіжий генератор із тим самим сталим зерном **усередині** кожної точки — і всі точки поділять один і той самий потік шуму, крива стане підозріло гладкою, а насправді корельованою й брехливою. Випадковість у Монте-Карло має бути справжньою рівно там, де треба, і відтворюваною рівно там, де зручно, — і плутати ці дві вимоги не можна.

Отак симулятор із іграшки перетворюється на прилад. Він не просто малює водоспад — він дає змогу **повірити** будь-який канал, для якого немає формули, і водночас чесно сказати, наскільки можна вірити кожній намальованій точці. Уся хитрість не в тому, щоб нагенерувати біти й полічити помилки: це п'ять рядків. Хитрість — у правильному σ, у сотні помилок на точку, у вусах довіри й у тверезому розумінні, де закінчується сила простого підрахунку.
