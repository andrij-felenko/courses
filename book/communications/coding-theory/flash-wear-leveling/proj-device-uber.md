# ⚙️ Оцінка UBER пристрою за гістограмою зносу

Контролер накопичувача змушений вести лічильник стирань на кожен блок: без нього неможливо покласти черговий запис у найменш зношений блок. Отже, у прошивці вже лежить готовий масив на кілька тисяч чисел — знімок здоров'я всієї пам'яті. З нього можна витягти те єдине число, заради якого затіяно все: **який рівень невиправних помилок має пристрій просто зараз**.

Зберімо модель, що це рахує. Вона маленька — сотня рядків, — але показує річ, яку словами переказати важко: чому долю накопичувача з тисяч блоків вирішують одиниці.

## Задача

Дано:

- `wear[]` — лічильник стирань (циклів P/E) кожного з N блоків;
- код: довжина кодового слова **n** бітів, гарантовано виправляє **t** помилок.

Знайти: **UBER пристрою** — частку невиправних бітів на всьому носії. І, окремо, **хто його визначає**: скільки в це число вніс кожен блок.

Мова — Python: задача суто числова (біноміальні хвости, статистика, робота в логарифмах), гарячого шляху тут немає, а все потрібне лежить у стандартній бібліотеці — `math.lgamma`, `statistics.NormalDist`, `functools.lru_cache`. Це офлайн-аудит телеметрії, а не код прошивки.

```python
from dataclasses import dataclass
from functools import lru_cache
from math import lgamma, log, log1p, exp, log10, fsum
from statistics import NormalDist
```

## Ідея: три ланки, і вся драма — у середній

```
знос блока  →  RBER блока  →  P(слово невиправне)  →  UBER пристрою
    eᵢ             pᵢ               P_uw(pᵢ)          середнє по блоках
 ціле число    монотонна          хвіст біноміала        лінійне
                й помірна            ∝ p^(t+1)          усереднення
```

Перша ланка помірна: удвічі більший знос піднімає рівень помилок у рази, не на порядки. Третя взагалі лінійна — усереднили по блоках, та й по всьому. А от середня ланка **опукла до жорстокості**: ймовірність, що слово не вилікується, іде як p у степені t+1, тобто для коду з t = 40 — як p⁴¹.

Звідси весь фокус. Ми усереднюємо по блоках **не знос, а ризик**. Усереднення — операція лінійна, і якби ризик був лінійною функцією зносу, то середній ризик визначався б середнім зносом, а гістограма нікого б не обходила. Але ризик — функція зносу опукла, до того ж скажено опукла, а середнє від такої функції притягується до **найбільших** її значень. Воно живе не в центрі гістограми зносу, а в її правому хвості. Пристрій, у якого «в середньому все гаразд», може бути вже мертвий.

Це твердження перевіряється числом. Зберімо модель по ланці.

## Канал: знос → сирий рівень помилок

```python
P_FRESH, P_RATED, E_RATED = 1e-5, 1e-3, 3000


def rber(pe_cycles: int) -> float:
    """RBER росте експоненційно зі зносом: ×100 за паспортні 3000 циклів."""
    p = P_FRESH * (P_RATED / P_FRESH) ** (pe_cycles / E_RATED)
    return min(p, 0.5)
```

Калібрування — на двох якорях. Свіжий блок має RBER близько 10⁻⁵. Наприкінці паспортного ресурсу (3000 циклів) — близько 10⁻³: саме такий сирий рівень помилок ще тримає під межею специфікації BCH-код зі швидкістю 0.935 (числа з доповіді Еріха Гарача на Flash Memory Summit 2015, наведені в дисертації Їсіня Ло про надійність NAND). Між якорями — експонента: лабораторна характеризація реальних MLC-чипів (Юй Цай зі співавторами, DATE 2012) дає прямим текстом, що зі зростанням числа циклів P/E рівень помилок росте експоненційно, бо кожне стирання жене заряд крізь тонкий окисел і залишає в ньому пастки для електронів. У цих числах RBER подвоюється кожні ~451 цикл:

```
p(e) = 10⁻⁵ · 100^(e/3000)

подвоєння:  100^(Δe/3000) = 2
            Δe = 3000 · log₁₀2 / log₁₀100 = 3000 · 0.30103 / 2 = 451.5 циклу
```

`min(p, 0.5)` — стеля: канал, гірший за підкидання монети, не має змісту, та й далеко за паспортним ресурсом модель усе одно вийшла з діапазону, у якому її калібрували.

## Код: RBER → ймовірність відмови слова

Слово гине, коли в ньому набереться більше ніж t перевернутих бітів. Якщо биті трапляються незалежно з імовірністю p, це хвіст біноміального розподілу:

```
P_uw(p) = Σ (k від t+1 до n)  C(n,k) · pᵏ · (1−p)ⁿ⁻ᵏ
```

Виведення цього хвоста, вибір t під задану межу UBER і те, чому в робочому діапазоні його майже цілком задає перший доданок, — [окремий розбір](book:communications/flash-wear-leveling/math-uber-rber.md): там показано, що доданки спадають майже геометрично, тож сума лише на чверть більша за провідний член. Нам тут потрібне інше: **порахувати цю суму, не збрехавши**.

Найпряміший запис не працює:

```python
from math import comb

P_uw = sum(comb(n, k) * p**k * (1 - p)**(n - k) for k in range(t + 1, n + 1))
```

Цей рядок не «дає неточність» — він падає:

```
OverflowError: int too large to convert to float
```

Бо C(8752, 4376) — ціле число на **2633 десяткові цифри**. Python порахує його точно (цілі в нього безмежні), а от помножити на float уже не зможе: у double стеля ~1.8·10³⁰⁸. І хоча сам добуток C·pᵏ мізерний і чудово вліз би у float, до нього не дійти — проміжний множник не існує в тих числах, якими рахує машина.

Ліки — рахувати **логарифми доданків** і не матеріалізувати самі числа:

```python
def _log_term(n: int, k: int, p: float) -> float:
    """ln[C(n,k)·pᵏ·(1−p)ⁿ⁻ᵏ] — самі числа поза межами float, логарифми — ні."""
    return (lgamma(n + 1) - lgamma(k + 1) - lgamma(n - k + 1)
            + k * log(p) + (n - k) * log1p(-p))
```

`lgamma` — це логарифм факторіала (Γ(m+1) = m!), тож ln C(n,k) виходить трьома відніманнями, і «число на 2633 цифри» ніде не народжується.

Далі суму треба зібрати назад із логарифмів. Стандартний хід — винести за дужку найбільший доданок:

```
Σ Tₖ = T_max · Σ exp(ln Tₖ − ln T_max)
```

Кожен `exp()` тепер бере недодатне число, віддає щось із проміжку (0, 1] — і нічого не переповнюється.

І тут пастка, на якій я спіймався сам. Спокусливо взяти за опору **перший** доданок хвоста (k = t+1): у робочому діапазоні він і є найбільший, код працює, числа сходяться. Але найбільший він лише поки середнє число помилок у слові n·p менше за t+1. Щойно блок зношується так, що n·p переростає t (для n = 8752, t = 40 це p ≈ 4.7·10⁻³), максимум хвоста заповзає вправо, різниця ln Tₖ − ln T₄₁ стає **додатною** — і `exp()` переповнюється, тобто модель падає рівно на найцікавіших, найзношеніших блоках. Опорою мусить бути саме **максимум**, а не перший-ліпший доданок:

```python
@dataclass(frozen=True)
class Code:
    n: int          # довжина кодового слова, бітів
    t: int          # скільки помилок гарантовано виправляє


BCH_1KIB = Code(n=8752, t=40)      # 1 КіБ даних + 40·14 = 560 бітів парності; рейт 0.936


def word_failure_prob(code: Code, p: float) -> float:
    """P(у слові більше ніж t перевернутих бітів) — точний біноміальний хвіст."""
    if p <= 0.0:
        return 0.0
    n, t = code.n, code.t
    # опора — НАЙБІЛЬШИЙ доданок хвоста (мода біноміала, підтягнута в межі хвоста),
    # інакше exp() від додатної різниці переповниться
    k_peak = min(n, max(t + 1, int((n + 1) * p)))
    ref = _log_term(n, k_peak, p)
    total, k = 0.0, t + 1
    while k <= n:
        rel = _log_term(n, k, p) - ref          # завжди ≤ 0 ⇒ exp() безпечний
        total += exp(rel) if rel > -700.0 else 0.0
        if k >= n * p and rel < -40.0:          # обрив ЛИШЕ за піком, де доданки спадають
            break
        k += 1
    return min(exp(ref + log(total)), 1.0)
```

Про обрив циклу окремо. Сумувати всі 8712 доданків не треба — вони спадають геометрично, і вистачає кількох десятків. Але обривати можна не будь-де: спершу доданки можуть **рости**, і зупинка на малому доданку до піку викинула б усю масу хвоста. Де саме пік — видно з відношення сусідніх доданків:

```
Tₖ₊₁ / Tₖ = (n−k)/(k+1) · p/(1−p)

< 1   ⟺   (n−k)·p < (k+1)·(1−p)   ⟺   k > n·p + p − 1
```

Тобто **від k ≥ n·p доданки строго спадають** — лише за цією межею обрив безпечний. Звідси й умова `k >= n * p and rel < -40.0`, а не просте «доданок став малим». Коштує це дрібницю: для зношеного до 3000 циклів блока (p = 10⁻³) хвіст обривається за **24 доданки** з 8712 можливих, для найгіршого блока в прогонах нижче (p = 2.33·10⁻³) — за 39. Точний хвіст такий дешевий, що наближати його провідним членом просто нема сенсу; для довідки, провідний член занижує хвіст у 1.3 раза при p = 10⁻³ і в 2.4 раза при p = 2.9·10⁻³ — дрібниця проти порядків, якими ми оперуємо.

Що модель рахує саме те, що обіцяє, варто перевірити незалежно. На малих n хвіст можна просумувати чесно, цілими числами, без жодних логарифмів — і звірити:

```
n=40   t=3 p=0.02 : точно=8.2409281004e-03  модель=8.2409281004e-03  відн. похибка 2.1e-14
n=200  t=5 p=0.01 : точно=1.6022906909e-02  модель=1.6022906909e-02  відн. похибка 2.3e-14
n=500  t=8 p=0.005: точно=1.0979656125e-03  модель=1.0979656125e-03  відн. похибка 4.7e-13
```

## Від блока до пристрою

```python
@lru_cache(maxsize=None)
def block_uber(code: Code, pe_cycles: int) -> float:
    """UBER блока = частота відмов слова, поділена на довжину слова (JESD218)."""
    return word_failure_prob(code, rber(pe_cycles)) / code.n


def device_uber(code: Code, wear: list[int]) -> float:
    """UBER пристрою = середнє по блоках (читання розкладені рівномірно)."""
    return fsum(block_uber(code, e) for e in wear) / len(wear)


def risk_profile(code: Code, wear: list[int]) -> list[float]:
    """Внесок кожного блока в UBER пристрою, від найбільшого."""
    return sorted((block_uber(code, e) / len(wear) for e in wear), reverse=True)
```

Ділення на `code.n` — не вигадка задля зручності: так UBER визначено стандартом. JEDEC JESD218 (той самий, що задає межі 10⁻¹⁵ для клієнтських носіїв і 10⁻¹⁶ для серверних) називає UBER числом помилок даних на прочитаний біт після виправлення, а рахують його як **частоту відмов кодового слова, поділену на довжину слова**. Ділення на N у `device_uber` — це вага читань: якщо хост читає блоки рівномірно, кожен входить у підсумок з вагою 1/N.

`lru_cache` на цілому лічильнику — не косметика. Лічильник стирань фізично **ціле число**, тож різних його значень у популяції набагато менше, ніж блоків: для перекошеної популяції нижче — 773 на 4096 блоків, для вирівняної — 101. Кеш обертає 4096 обчислень хвоста на 773, і повний прогін пристрою займає 0.026 с.

## Популяція зносу

```python
def wear_population(n_blocks: int, mean_pe: float, sigma: float) -> list[int]:
    """Детермінована квантильна сітка: блок i сидить у квантилі (i+0.5)/N."""
    nd = NormalDist(mean_pe, sigma)
    return [max(0, round(nd.inv_cdf((i + 0.5) / n_blocks))) for i in range(n_blocks)]
```

Тут навмисно немає генератора випадкових чисел. Якби ми насипали 4096 випадкових значень, відповідь стрибала б від прогону до прогону — і саме тому, що її вирішує **максимум** вибірки, а максимум гуляє найдужче з усього, що можна взяти з вибірки. Досліджувати вплив хвоста інструментом, чий власний хвіст шумить, — кепська ідея. Квантильна сітка садить блок i рівно в квантиль (i+0.5)/N: розподіл відтворено точно, найзношеніший блок сидить у квантилі 4095.5/4096, тобто на z = 3.67 сигми, і результат однаковий щоразу.

**σ — це і є ручка вирівнювання.** Wear leveling не змінює, скільки всього стирань зробив хост: сумарний знос Σe задано навантаженням, і політика вирішує лише, як він **розкладений** — тобто ширину гістограми. Через симетрію квантильної сітки Σe зберігається точно: у всіх прогонах нижче він однаковий до одиниці — 12 288 000 стирань.

Усі вісім рядків — **той самий пристрій із тим самим сумарним зносом**: 4096 блоків, 12 288 000 стирань, у середньому рівно 3000 циклів на блок, тобто паспортний ресурс вироблено цілком. Змінюється сама лише **ширина** гістограми.

Читаємо. Середній блок скрізь однаковий: e = 3000, p = 10⁻³, його власний UBER — 2.7·10⁻¹⁹, з запасом у три з половиною порядки під межею. Але UBER **пристрою** гуляє на тринадцять порядків — від 3.6·10⁻¹⁹ до 9.0·10⁻⁷. Межу специфікації перетинають між σ = 100 і σ = 60: **розкид лічильників у 3.3% — уже смерть, у 2.0% — іще життя.** Три відсотки.

Візьмімо два рядки впритул. Перекошена популяція (σ = 150, розкид 5%) дає UBER 1.7·10⁻¹² — пристрій провалює специфікацію в 1660 разів. Вирівняна (σ = 15) — 3.6·10⁻¹⁹, тримає з запасом. Між ними **6.7 порядку**: UBER падає у 4.6 мільйона разів. Сумарний знос при цьому не зменшився ні на одне стирання — ми лише переклали ті самі стирання рівніше.

І тепер найголовніше — хто платить. У перекошеній популяції **один-єдиний блок із 4096 несе 61.3% усього ризику пристрою**. Його «чесна» частка — 1/4096, тобто 0.024%; він нагрібає у 2512 разів більше. Десять найгірших блоків — 94.2%. Решта 4086 блоків, разом узяті, — менше за шість відсотків.

> 🔧 **Навіщо це.** Порахувати середній знос уміє кожна прошивка, і він майже нічого не каже: у таблиці вище середній блок в усіх восьми рядках однаковісінький, а пристрій у п'яти з них уже мертвий. Показник здоров'я пам'яті, вартий місця в телеметрії, — не `mean(wear)`, а **розкид** лічильників стирань, тобто правий хвіст гістограми. Якщо логувати один-єдиний скаляр, логуйте `max(wear) − mean(wear)`, а не середнє.

Одна деталь у таблиці варта окремої уваги, бо ламає щойно проголошене гасло. Внесок найгіршого блока росте від 0.3% до 64%… а тоді **падає** — до 24.5% при σ = 300 і до 3.1% при σ = 400. Диктатура найгіршого — явище **схилу**, а не дна. Щойно блок остаточно звалюється з обриву, його ймовірність відмови слова впирається в одиницю, а UBER блока — у стелю 1/n = 1.14·10⁻⁴: гірше вже просто не буває. При σ = 400 за край звалилася не одна штука, а кількадесят, усі вперлися в ту саму стелю — і ризик знову «демократичний», просто пристрій уже безнадійний. Найгірший блок вирішує долю рівно доти, доки він **один стоїть на краю**.

## Ціна вирівнювання

Досі виглядало, ніби рівність безкоштовна. Не так. Статичне вирівнювання переселяє холодні дані з малозношених блоків, а переселення — це стирання, яких хост не просив ([підсилення запису](book:algorithms/write-amplification)): платимо **зайвим сумарним зносом** за вужчу гістограму. Модель дозволяє звести дебет із кредитом — вирівняймо ідеально (σ = 15), але накиньмо зверху зайвих стирань:

```
+  0% зносу:  Σe = 12 288 000   UBER = 3.6·10⁻¹⁹   тримає
+  2% зносу:  Σe = 12 533 760   UBER = 6.8·10⁻¹⁸   тримає
+  5% зносу:  Σe = 12 902 400   UBER = 4.9·10⁻¹⁶   тримає ледве
+ 10% зносу:  Σe = 13 516 800   UBER = 3.8·10⁻¹³   ПАДАЄ
```

Обмін виходить крутий в обидва боки. П'ять відсотків зайвих стирань коштують майже три порядки UBER — бо зайвий знос зсуває **всю** гістограму вправо, ближче до обриву. Але й прибуток від звуження гістограми величезний. Беззбитковість рахується прямо: вирівнювання з σ = 150 до σ = 15 дає той самий UBER, що й перекошена популяція, коли коштує **+11.2%** зайвого зносу. Тобто до 11% зайвих стирань — вигідно, за 11% — ви робите гірше, ніж якби не чіпали нічого взагалі. Ось точний зміст поради «вирівнювати рівно настільки, щоб жоден блок не наблизився до обриву, і ні на крок більше»: бюджет тут не метафора, а число, і його можна перевитратити.

## Складність

Наївна оцінка — O(N·n): для кожного з N блоків просумувати до n доданків, тобто 4096 · 8712 ≈ 36 мільйонів кроків. Насправді працює O(D·L):

- **D** — число **різних** лічильників стирань, а не блоків (773 з 4096 у перекошеній популяції, 101 у вирівняній): це дає `lru_cache` на цілому e;
- **L** — довжина хвоста до обриву: 24–39 доданків замість 8712, бо доданки спадають геометрично.

Разом ≈ 773 · 30 ≈ 23 тисячі викликів `_log_term` — 0.026 с на цілий пристрій. Вузьке місце тут не блоки, а **різноманіття** зносу: на реальній телеметрії з мільйоном блоків D усе одно впирається в діапазон лічильників (кілька тисяч), тож час майже не росте.

## Пастки

**Канал без пам'яті — найбільше спрощення моделі.** Біноміальний хвіст стоїть на припущенні, що біти перевертаються **незалежно** один від одного, а у флеші помилки збиваються в купки: втрата заряду залежить від записаного значення, програмування комірки збурює сусідні. Купчастість завжди робить хвіст важчим за біноміальний, тож `word_failure_prob` радше **занижує** ризик. Для висновків важить, у який бік це зміщує картину. Купчастість домножує P_uw усіх блоків заразом, тобто рухає **поріг** — ту σ, на якій пристрій перестає тримати специфікацію, — але не чіпає ні опуклості ланки p → p^(t+1), ні того, що середнє від опуклої функції притягується до свого максимуму. Іншими словами, під сумнівом тут число «розкид 3.3% — уже смерть», а не сам факт, що долю пристрою вирішує вузький хвіст гістограми.

**Залежність RBER(e) — модель, і в полі вона інша.** Експоненційний ріст — це лабораторія: чипи, які циклюють прискорено й контрольовано. Польове дослідження Б. Шредер, Р. Лагісетті й А. Мерчанта на парку накопичувачів Google (FAST 2016, шість років, мільйони диско-днів) дало інше: RBER росте з циклами P/E радше **лінійно**, ніж експоненційно, і — важливіше — RBER **погано передбачає** невиправні помилки; ба більше, автори не знайшли кореляції між числом прочитаних бітів і числом невиправних помилок, тобто засумнівалися в самій осмисленості UBER як міри надійності накопичувача. Обидва результати добре задокументовані й не суперечать один одному: лабораторія міряє голий чип, поле — цілий носій разом із контролером, який усіляко бореться з помилками. Практичний висновок: абсолютні числа цієї моделі — **не прогноз** для реального диска. Але порівняльний висновок (розкид важить, найгірший блок домінує) тримається не на показнику експоненти, а лише на **опуклості** ланки p → p^(t+1) — і вціліє за будь-якої монотонної rber(e), хоч лінійної.

**Однаковий знос ≠ однаковий RBER.** У моделі rber — чиста функція лічильника, тож ідеальне вирівнювання дає ідеально однакові блоки. Насправді є розкид виготовлення: у 3D NAND, за вимірами Ло, найгірша сторінка має RBER більш ніж **удвічі** вищий за середній по блоку — через різницю між шарами кристала. А що ризик іде як p⁴¹, залишкова двійка перетворюється на 2⁴¹ ≈ 2·10¹² різниці в ризику. Отже, у гістограмі ризику є **непереборне дно**, якого вирівнюванням не досягти: рядок σ = 15 у таблиці — ідеалізація, бо навіть за однакових лічильників блоки не однакові.

**Стеля 1/n.** За домовленістю JESD218 відмова слова рахується як одна помилка даних, тож дощенту мертвий блок звітує UBER = 1/n = 1.14·10⁻⁴, а не ~p. Метрика не відрізняє «загубилося одне слово» від «блок згорів дотла» — і це саме той ґандж, через який польове дослідження радить дивитися на частоту невиправних помилок, а не на UBER.

**Рівномірні читання — оптимістичне припущення.** Вага 1/N означає, що хост читає всі блоки однаково. У житті гарячі дані і пишуть, і читають частіше, тож блоки з найвищим p часто ще й читаються найбільше — кореляція додатна, і справжній UBER гірший за оцінку. (Втішає лише те, що вирівнювання, ганяючи дані по пам'яті, цю кореляцію частково розриває.)

**Лише коди з жорсткою межею t.** Модель припускає декодер із межею: до t помилок — вилікує напевно, від t+1 — здасться напевно. BCH саме такий, тому числа тут чесні. А от [LDPC](book:communications/ldpc) із м'яким декодуванням ніякого чіткого t не має — у нього ймовірнісний спад, і його відмова взагалі не є біноміальним хвостом. Для сучасного накопичувача на LDPC ця модель дає **форму** міркування, але не число.
