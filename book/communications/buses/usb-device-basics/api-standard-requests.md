# 📋 Стандартні керівні запити USB: побайтова довідка

Кожна команда енумерації — `SET_ADDRESS`, `GET_DESCRIPTOR`, `SET_CONFIGURATION` і решта — це керівна передача, чия перша стадія завжди складається з тих самих **восьми байтів** у єдиному форматі; тут цей формат і всі стандартні запити зведено до чисел: коди, напрями, поля.

Ці вісім байтів займають Setup-стадію керівної передачі. За нею йде необовʼязкова стадія даних (у той бік, що названий у першому ж байті) і коротка стадія статусу-підтвердження. Розкладка байтів однакова для будь-якого запиту — змінюється лише вміст полів, і саме він перетворює однаковий каркас то на «прийми адресу», то на «віддай дескриптор».

## Setup-пакет: вісім байтів

Порядок і розміри полів фіксовані. Два перші поля — однобайтові, три наступні — 16-бітові, і на дротах вони лежать **молодшим байтом уперед** (little-endian).

| Зсув | Поле | Розмір | Призначення |
|:----:|------|:------:|-------------|
| 0 | `bmRequestType` | 1 | Біт-мапа: напрям, тип і отримувач запиту |
| 1 | `bRequest` | 1 | Код запиту (число з таблиці нижче) |
| 2 | `wValue` | 2 | Головний аргумент; сенс залежить від `bRequest` |
| 4 | `wIndex` | 2 | Індекс/зсув: інтерфейс, точка або мова |
| 6 | `wLength` | 2 | Скільки байтів піде в стадії даних |

![Восьмибайтовий Setup-пакет: bmRequestType, bRequest, далі 16-бітові wValue, wIndex, wLength; байт bmRequestType розкладено на біти — напрям D7, тип D6–D5, отримувач D4–D0](/book/communications/buses/usb-device-basics/img/setup-packet.svg)

*Розкладка Setup-пакета незмінна: два однобайтові поля, потім три двобайтові. Нульовий байт `bmRequestType` сам поділений на три бітові поля — напрям передачі, тип запиту й отримувача, — і саме вони кажуть хостові й пристрою, як витлумачити решту сімох байтів.*

## bmRequestType: три бітові поля

Нульовий байт — не число, а біт-мапа. Його старший біт D7 разом із полем `wLength` визначає, чи буде взагалі стадія даних і в який бік вона піде.

| Біти | Поле | Значення |
|:----:|------|----------|
| D7 | Напрям даних | `0` = OUT (хост → пристрій) · `1` = IN (пристрій → хост) |
| D6–D5 | Тип запиту | `0` стандартний · `1` класовий · `2` вендорний · `3` резерв |
| D4–D0 | Отримувач | `0` пристрій · `1` інтерфейс · `2` кінцева точка · `3` інше · 4…31 резерв |

Складені разом, ці поля дають кілька готових значень байта, що трапляються найчастіше:

| `bmRequestType` | Розшифровка |
|:---------------:|-------------|
| `0x00` | OUT · стандартний · пристрій |
| `0x80` | IN · стандартний · пристрій |
| `0x01` / `0x81` | OUT / IN · стандартний · інтерфейс |
| `0x02` / `0x82` | OUT / IN · стандартний · кінцева точка |

Ця довідка охоплює лише **стандартний** тип (D6–D5 = `0`). Класові й вендорні запити мають ті самі вісім байтів, але власний набір кодів `bRequest`, який визначає відповідний клас пристрою чи його виробник.

## Коди стандартних запитів

Для стандартного типу поле `bRequest` — число з цієї таблиці. Наведено повний набір; шість запитів, якими фактично йде енумерація, розписано детальніше нижче.

| Запит | `bRequest` | `bmRequestType` | `wValue` | `wIndex` | `wLength` | Стадія даних |
|-------|:----------:|:---------------:|----------|----------|:---------:|--------------|
| `GET_STATUS` | 0 · `0x00` | `0x80`/`0x81`/`0x82` | 0 | 0 / інтерфейс / точка | 2 | статус (2 Б) → хост |
| `CLEAR_FEATURE` | 1 · `0x01` | `0x00`/`0x01`/`0x02` | селектор | 0 / інтерфейс / точка | 0 | — |
| `SET_FEATURE` | 3 · `0x03` | `0x00`/`0x01`/`0x02` | селектор | 0 / інтерфейс / точка | 0 | — |
| `SET_ADDRESS` | 5 · `0x05` | `0x00` | адреса 0…127 | 0 | 0 | — |
| `GET_DESCRIPTOR` | 6 · `0x06` | `0x80` | тип ≪8 ∣ індекс | 0 або LangID | довжина | дескриптор → хост |
| `SET_DESCRIPTOR` | 7 · `0x07` | `0x00` | тип ≪8 ∣ індекс | 0 або LangID | довжина | дескриптор ← хост |
| `GET_CONFIGURATION` | 8 · `0x08` | `0x80` | 0 | 0 | 1 | номер конфіг. (1 Б) → хост |
| `SET_CONFIGURATION` | 9 · `0x09` | `0x00` | номер конфіг. | 0 | 0 | — |
| `GET_INTERFACE` | 10 · `0x0A` | `0x81` | 0 | інтерфейс | 1 | альт. (1 Б) → хост |
| `SET_INTERFACE` | 11 · `0x0B` | `0x01` | альт-налашт. | інтерфейс | 0 | — |
| `SYNCH_FRAME` | 12 · `0x0C` | `0x82` | 0 | кінцева точка | 2 | номер кадру (2 Б) → хост |

Коди `2` і `4` зарезервовані й не використовуються. Зверніть увагу, що напрям у `bmRequestType` завжди узгоджений зі стадією даних: усі `GET_*` та `GET_STATUS` читають (IN, D7 = 1), а `SET_*` і `CLEAR_FEATURE` або пишуть, або взагалі не мають даних (OUT, D7 = 0).

## Шість запитів енумерації — по полях

### `GET_DESCRIPTOR` — прочитати дескриптор

Цим запитом хост витягує з пристрою весь його самоопис. Дескриптор, який треба віддати, названо в `wValue`.

- `bmRequestType` = `0x80` — IN, стандартний, отримувач пристрій.
- `wValue` — старший байт задає **тип** дескриптора (числа нижче), молодший — його **індекс** (номер рядка чи конфігурації; для дескриптора пристрою — `0`).
- `wIndex` — зазвичай `0`; для рядкового дескриптора сюди кладуть **Language ID** (наприклад, `0x0409` — англійська США).
- `wLength` — скільки байтів хост готовий прийняти. Тут живе типовий прийом: спершу просять лише перші вісім байтів, читають із них повну довжину дескриптора, а тоді повторюють запит уже на всю довжину.
- Стадія даних: сам дескриптор іде до хоста.

Тип дескриптора (старший байт `wValue`):

| Тип | Код | Що описує |
|-----|:---:|-----------|
| `DEVICE` | 1 · `0x01` | пристрій — «титульна сторінка», 18 байтів |
| `CONFIGURATION` | 2 · `0x02` | конфігурацію разом з усіма вкладеними |
| `STRING` | 3 · `0x03` | рядок у UTF-16LE (назва, серійник) |
| `INTERFACE` | 4 · `0x04` | інтерфейс (лише вкладений у конфігурацію) |
| `ENDPOINT` | 5 · `0x05` | кінцеву точку (лише вкладену в конфігурацію) |
| `DEVICE_QUALIFIER` | 6 · `0x06` | параметри пристрою на іншій швидкості (High-Speed) |
| `OTHER_SPEED_CONFIGURATION` | 7 · `0x07` | конфігурацію на іншій швидкості |
| `INTERFACE_ASSOCIATION` | 11 · `0x0B` | групу інтерфейсів однієї функції (композит) |

На практиці окремими запитами просять лише `DEVICE`, `CONFIGURATION` та `STRING` (а на High-Speed ще `DEVICE_QUALIFIER` й `OTHER_SPEED_CONFIGURATION`). Типи `INTERFACE` та `ENDPOINT` окремо не запитують — вони приходять вкладеними всередині відповіді на `CONFIGURATION`, одним суцільним блоком. Побайтову розкладку самих дескрипторів розібрано в [статті про енумерацію](book:programming/usb-enumeration).

### `SET_ADDRESS` — видати пристрою адресу

Команда, якою хост дає щойно скинутому пристрою його постійний номер на шині.

- `bmRequestType` = `0x00` — OUT, отримувач пристрій.
- `wValue` — нова адреса, число `1…127` (сім бітів; `0` — службова стартова адреса).
- `wIndex` = `0`, `wLength` = `0` — стадії даних немає.

> 🔧 **Навіщо це.** Тонкість, на якій ловляться прошивки: пристрій **не** застосовує нову адресу відразу, отримавши Setup-пакет. Він мусить відпрацювати цим запитом усі три стадії (включно зі стадією статусу) ще на **старій** адресі `0` — і лише після завершення передачі перемкнутися на новий номер. Перемкнетеся на байт раніше, до стадії статусу, — і хост не отримає підтвердження, а енумерація зірветься на першому ж кроці.

### `SET_CONFIGURATION` — увімкнути конфігурацію

Завершальний крок енумерації: команда, що оживляє всі кінцеві точки пристрою.

- `bmRequestType` = `0x00` — OUT, отримувач пристрій.
- `wValue` — молодший байт містить номер конфігурації з її дескриптора; старший байт `0`. Значення `0` не вмикає, а **розконфігуровує** пристрій.
- `wIndex` = `0`, `wLength` = `0`, даних немає.

### `GET_CONFIGURATION` — дізнатися поточну

Дзеркальний запит: хост питає, яка конфігурація зараз активна.

- `bmRequestType` = `0x80` — IN, отримувач пристрій.
- `wValue` = `0`, `wIndex` = `0`, `wLength` = `1`.
- Стадія даних: один байт — номер активної конфігурації (`0`, якщо пристрій ще не сконфігуровано).

### `GET_STATUS` — прочитати стан

Два байти стану того отримувача, що названий у `bmRequestType` і `wIndex`.

- `bmRequestType` = `0x80` / `0x81` / `0x82` — IN; отримувач пристрій / інтерфейс / кінцева точка.
- `wValue` = `0`; `wIndex` = `0`, номер інтерфейсу або адреса точки; `wLength` = `2`.
- Стадія даних: два байти статусу (little-endian), значення бітів залежить від отримувача:

| Отримувач | Біти статусу (2 байти) |
|-----------|------------------------|
| Пристрій | D0 = живиться сам (Self-Powered) · D1 = ввімкнено віддалене пробудження · решта `0` |
| Інтерфейс | усі біти `0` (зарезервовано) |
| Кінцева точка | D0 = Halt (точку зупинено, стан `STALL`) |

### `SET_FEATURE` / `CLEAR_FEATURE` — увімкнути чи скинути ознаку

Пара запитів, що вмикає й вимикає булеві ознаки отримувача. Яку саме ознаку — задає `wValue`.

- `bmRequestType` = `0x00` / `0x01` / `0x02` — OUT; отримувач за селектором.
- `wValue` — селектор ознаки (числа нижче); `wIndex` — `0`, номер інтерфейсу або адреса точки; `wLength` = `0`, без даних.

| Селектор | Код | Отримувач | Дія |
|----------|:---:|-----------|-----|
| `ENDPOINT_HALT` | 0 | кінцева точка | зупинити точку або зняти зупинку |
| `DEVICE_REMOTE_WAKEUP` | 1 | пристрій | дозволити пристрою будити хост |
| `TEST_MODE` | 2 | пристрій | тестовий режим (High-Speed; номер тесту — у старшому байті `wIndex`) |

Найчастіше з цієї пари в живому коді трапляється `CLEAR_FEATURE(ENDPOINT_HALT)` — ним хост «розстопорює» кінцеву точку після того, як вона відповіла `STALL` і застрягла в зупиненому стані.

## Мінімальний виклик

Setup-стадію зручно тримати структурою рівно на вісім байтів. Заповнити її потрібними числами — і є весь «виклик» стандартного запиту; далі хост-контролер сам проганяє три стадії передачі. Код домену — реєстри й побайтовий протокол, тож мовою тут природно взяти C.

```c
#include <stdint.h>

/* Setup-пакет — рівно 8 байтів; 16-бітові поля little-endian */
typedef struct __attribute__((packed)) {
    uint8_t  bmRequestType;   /* D7 напрям · D6-5 тип · D4-0 отримувач */
    uint8_t  bRequest;        /* код запиту */
    uint16_t wValue;
    uint16_t wIndex;
    uint16_t wLength;         /* байтів у стадії даних */
} usb_setup;                  /* sizeof(usb_setup) == 8 */
```

Три типові запити енумерації в заповненому вигляді — і байти, що реально лягають на дроти:

```c
/* «Дай 18 байтів дескриптора пристрою» */
usb_setup get_dev_desc = {
    .bmRequestType = 0x80,    /* IN · стандартний · пристрій          */
    .bRequest      = 0x06,    /* GET_DESCRIPTOR                        */
    .wValue        = 0x0100,  /* тип 0x01 (DEVICE) << 8  |  індекс 0   */
    .wIndex        = 0x0000,  /* мова не потрібна                      */
    .wLength       = 18,      /* повний device-дескриптор = 18 байтів  */
};
/* на дротах:  80 06 00 01 00 00 12 00   (wValue, wLength — LSB перший) */

/* «Прийми адресу 7» — стадії даних немає */
usb_setup set_addr = {
    .bmRequestType = 0x00,    /* OUT · стандартний · пристрій */
    .bRequest      = 0x05,    /* SET_ADDRESS                  */
    .wValue        = 7,       /* нова адреса                  */
    .wIndex        = 0,
    .wLength       = 0,
};
/* на дротах:  00 05 07 00 00 00 00 00 */

/* «Увімкни конфігурацію 1» — завершення енумерації */
usb_setup set_config = {
    .bmRequestType = 0x00,
    .bRequest      = 0x09,    /* SET_CONFIGURATION  */
    .wValue        = 1,       /* номер конфігурації */
    .wIndex        = 0,
    .wLength       = 0,
};
/* на дротах:  00 09 01 00 00 00 00 00 */
```

Простежте переклад полів у байти на першому прикладі: `wValue = 0x0100` лягає як `00 01`, а `wLength = 18 = 0x0012` — як `12 00`. Це і є та сама умова «молодший байт уперед», якої вимагає формат Setup-пакета, і саме через неї сирий дамп на дротах виглядає «навиворіт» проти звичного запису числа.
