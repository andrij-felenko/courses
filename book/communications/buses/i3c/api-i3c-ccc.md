# Довідкова специфікація командних кодів CCC та структури протоколу MIPI I3C

Специфікація MIPI I3C (версій v1.0 та v1.1.1 Basic) формалізує взаємодію між активним головним контролером (*Main Controller*) та цільовими пристроями (*Targets*) через систему стандартизованих командних кодів — **CCC** (*Common Command Codes*). Команди CCC дозволяють конфігурувати адресний простір шини, керувати станами енергозбереження, опитувати апаратні дескриптори, призначати ліміти пакетної передачі та обробляти події без використання нестандартних регістрових карт виробників.

---

### 1. Класифікація та адресація команд CCC

Командний код CCC передається безпосередньо після сигналу старту (*START*) та зарезервованої 7-бітної адреси загального виклику I3C:

```
I3C_BROADCAST_ADDR = 7'h7E (0b1111110)
```

Усі команди CCC поділяються на два функціональні діапазони:

1. **Широкомовні команди (*Broadcast CCC*, коди `0x00`–`0x7F`):** адресовані одночасно всім підімкненим до магістралі I3C-пристроям. Передача не вимагає повторної адресації окремого веденого. Усі пристрої одночасно приймають командний байт та параметри конфігурації.
2. **Адресні команди (*Direct CCC*, коди `0x80`–`0xFE`):** після коду команди контролер генерує повторний старт (*Repeated START*) та вказує 7-бітну динамічну адресу конкретного цільового пристрою, якому призначені дані або запит. Тільки ціль зі збігом динамічної адреси обробляє подальші байти корисного навантаження.

| Код CCC (Hex) | Назва команди | Тип | Напрямок | Призначення |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | `ENEC` | Broadcast | Запис | Широкомовне увімкнення подій (IBI, Hot-Join) |
| `0x01` | `DISEC` | Broadcast | Запис | Широкомовне вимкнення подій (IBI, Hot-Join) |

| `0x04` | `ENTAS2` | Broadcast | Запис | Перехід у стан активності 2 (затримка пробудження до 100 мкс) |
| `0x05` | `ENTAS3` | Broadcast | Запис | Перехід у стан активності 3 (глибокий сон, пробудження до 10 мс) |

### 2. Детальний опис базових керуючих команд CCC

Кожна команда CCC має фіксований протокольний контракт щодо передачі параметрів та очікуваних відповідей:

#### Команди увімкнення та вимкнення подій (`ENEC` та `DISEC`)

Команди `ENEC` (коди `0x00`/`0x80`) та `DISEC` (коди `0x01`/`0x81`) керують генерацією асинхронних подій цільовими пристроями. Після коду команди контролер передає один байт маски подій (*Event Mask*):

* **Біт 0 (`ENINT` / `DISINT`):** увімкнення або вимкнення внутрішньосмугових переривань IBI для звичайних сенсорних подій.
* **Біт 1 (`ENCR` / `DISCR`):** увімкнення або вимкнення запитів передачі ролі контролера (*Controller Role Request*) від вторинних контролерів.
* **Біт 3 (`ENHJ` / `DISHJ`):** увімкнення або вимкнення запитів гарячого підключення (*Hot-Join Requests*) на адресі `0x02`.

Якщо біт маски встановлено в `1`, відповідна подія дозволяється (для `ENEC`) або забороняється (для `DISEC`). Це дозволяє контролеру ізолювати шумні давачі з надмірною частотою переривань без блокування всієї шини.

#### Команди станів активності (`ENTAS0`–`ENTAS3`)

Широкомовні команди `ENTASx` (коди `0x02`..`0x05`) встановлюють глобальний профіль енергоспоживання шини:

* `ENTAS0` (Activity State 0): активний робочий режим. Усі внутрішні генератори, підсилювачі та цифрові фільтри сенсорів увімкнені. Час готовності до зчитування даних — нульовий.
* `ENTAS1` (Activity State 1): режим легкої паузи. Аналогові блоки залишаються заживленими, тактування цифрових автоматів знижується. Максимальний гарантований час пробудження — до 1 мікросекунди.
* `ENTAS2` (Activity State 2): стан помірного сну. Основна частина аналогових трактів вимикається, працює лише черговий компаратор пробудження. Гарантований час відновлення повної точності — до 100 мікросекунд.
* `ENTAS3` (Activity State 3): режим ультраглибокого сну (*Deep Sleep*). Сенсори споживають струм у діапазоні десятків наноампер. Для виходу з режиму та повторного калібрування АЦП контролер зобов'язаний витримати паузу тривалістю до 10 мілісекунд перед виконанням першої транзакції зчитування.

#### Команди лімітів довжини транзакцій (`SETMWL` та `SETMRL`)

Команди `SETMWL` (коди `0x09`/`0x89`) та `SETMRL` (коди `0x0A`/`0x8A`) захищають внутрішні апаратні буфери FIFO малопотужних мікроконтролерів і сенсорів від переповнення при довгих потокових передачах:

* `SETMWL` передає два байти: старший байт `MWL[15:8]` та молодший байт `MWL[7:0]`, які визначають максимальну кількість байтів корисних даних, що контролер має право записати у пристрій за одну SDR-транзакцію.
* `SETMRL` передає два байти ліміту читання `MRL[15:8]`, `MRL[7:0]`, а також необов'язковий третій байт `IBI_Payload_Size`, що жорстко обмежує максимальну кількість додаткових байтів даних, які сенсор може додати до свого переривання IBI.

### 3. Структура 48-бітного Provisional ID

Кожен I3C-пристрій має обов'язковий апаратний 48-бітний ідентифікатор (*Provisional ID*, PID), що однозначно визначає його виробника, модельне сімейство та екземпляр кристала:

```
+------------------------------------+---+------------------+---------------+---------------+
| 47                              33 | 32| 31            16 | 15         12 | 11          0 |
+------------------------------------+---+------------------+---------------+---------------+
|       MIPI Manufacturer ID         | T |     Part ID      |  Instance ID  | Extra / Rand  |
|             (15 бітів)             |   |    (16 бітів)    |   (4 біти)    |   (12 бітів)  |
+------------------------------------+---+------------------+---------------+---------------+
```

Детальний опис полів ідентифікатора:

* **MIPI Manufacturer ID (біти 47..33, 15 бітів):** унікальний ідентифікатор виробника кремнію, призначений альянсом MIPI Alliance. Старший 15-бітний префікс гарантує, що чипи різних постачальників ніколи не збігатимуться за першими розрядами під час арбітражу DAA.
* **Provisioned ID Type Selector (біт 32, 1 біт):**
  * `0` — довільний вендорний формат молодших 32 бітів ідентифікатора.
  * `1` — стандартизована структура з фіксованими полями *Part ID*, *Instance ID* та *Extra Information*.
* **Part ID (біти 31..16, 16 бітів):** внутрішній код сімейства та моделі сенсора виробника (наприклад, конкретна ревізія IMU-акселерометра або модуля ToF).
* **Instance ID (біти 15..12, 4 біти):** апаратний номер примірника чипа на друкованій платі (формується фізичним підключенням адресних ніжок до землі або живлення).
* **Extra / Random Data (біти 11..0, 12 бітів):** номер кремнієвої пластини, молодші розряди серійного номера кристала або псевдовипадкова послідовність, що гарантує відсутність колізій між однаковими чипами під час процедури DAA.

### 4. Регістри характеристик BCR та DCR

Під час процедури динамічного призначення адрес цільовий пристрій передає контролеру два 8-бітних байти характеристик: **BCR** (*Bus Characteristics Register*) та **DCR** (*Device Characteristics Register*).

#### Регістр характеристик шини (BCR)

Регістр BCR повідомляє контролеру про апаратні обмеження та протокольні можливості цільового вузла:

| Біти BCR | Назва поля | Значення | Опис |
| :--- | :--- | :--- | :--- |
| `[7:6]` | `DEVICE_ROLE` | `00` | I3C Target (звичайний цільовий вузол) |
| | | `01` | I3C Secondary Controller (вторинний контролер) |
| | | `10` | Зарезервовано |
| | | `11` | Зарезервовано |
| `[5]` | `HDR_CAPABLE` | `1` | Підтримує режими високої швидкості HDR |
| | | `0` | Працює виключно в базовому режимі SDR |
| `[4]` | `BRIDGE_ID` | `1` | Пристрій є шинним мостом або комутатором |
| | | `0` | Звичайний кінцевий пристрій |
| `[3]` | `OFFLINE_CAP` | `1` | Підтримує тимчасове відімкнення від шини |
| | | `0` | Постійно активний інтерфейс |
| `[2]` | `IBI_PAYLOAD` | `1` | Переривання IBI містить один або кілька байтів даних |
| | | `0` | Переривання IBI не містить корисного навантаження |
| `[1]` | `IBI_REQUEST` | `1` | Здатний генерувати внутрішньосмугові переривання IBI |
| | | `0` | Не підтримує генерацію IBI |
| `[0]` | `MAX_SPEED_LIMIT`| `1` | Має жорстке обмеження максимальної тактової частоти |
| | | `0` | Працює на повній базовій частоті SDR 12.5 МГц |

#### Регістр характеристик пристрою (DCR)

Регістр DCR класифікує тип підімкненого датчика чи периферійного вузла, дозволяючи системному стеку операційної системи автоматично завантажувати відповідний драйвер класу пристрою:

| Код DCR (Hex) | Клас пристрою | Приклади сенсорів та вузлів |
| :--- | :--- | :--- |
| `0x00` | Generic Device | Універсальний вузол введення/виведення |
| `0x01` | Accelerometer | 3-осьові акселерометри |
| `0x02` | Gyroscope | 3-осьові гіроскопи |
| `0x03` | Magnetometer | 3-осьові електронні компаси |
| `0x04` | Combination IMU | 6-осьові та 9-осьові інерційні модулі |
| `0x05` | Barometer | Барометричні датчики тиску та висоти |
| `0x06` | Temperature Sensor | Цифрові термометри високої точності |
| `0x07` | Ambient Light Sensor | Давачі освітленості та наближення (ALS/Proximity) |
| `0x08` | Heart Rate / Bio | Біометричні датчики пульсу та SpO2 |
| `0x09` | Time-of-Flight (ToF) | Оптичні далекоміри та лазерні сканери |
| `0x0A` | Touch Controller | Ємнісні контролери сенсорних екранів та кнопок |
| `0x0B` | Power Management IC | Контролери живлення PMIC та вимірювачі струму |
| `0x0C` | Bridge / Expander | Мости I3C-to-SPI, I3C-to-UART та розширювачі GPIO |

### 5. Структура внутрішньосмугового переривання IBI та Mandatory Data Byte

Коли цільовий пристрій виграє арбітраж переривання IBI, контролер надсилає підтвердження *ACK*, після чого ціль може передати один обов'язковий байт даних — **MDB** (*Mandatory Data Byte*), а також додаткові байти корисного навантаження (*Payload*), якщо це дозволено бітом `BCR[2]`.

```
+---+----------------------------+---+-----+-------------------+---+-----+------+---+
| S | Dynamic Address (7 бітів) | 1 | ACK |  MDB Byte (8 біт) | T | ... | Data | T |
+---+----------------------------+---+-----+-------------------+---+-----+------+---+
  ^                ^               ^    ^            ^           ^          ^     ^
  |                |               |    |            |           |          |     |
START         Адреса цілі         RnW Контролер  Причина IBI   T-біт   Корисні  T-біт
                                   =1            (статус події) (парність) байти
```

Формат байта MDB за стандартом MIPI I3C визначає контекст переривання:

* **MDB діапазон `0x00`–`0x1F`:** переривання готовності даних датчиків (*Sensor Data Ready*). Молодші 5 бітів вказують номер суб-каналу сенсора (наприклад, `0x01` — перевищення порогу по осі X, `0x02` — по осі Y, `0x04` — FIFO заповнено наполовину).
* **MDB діапазон `0x20`–`0x7F`:** помилки та апаратні події периферійного пристрою (*Error / Event Notification*).
* **MDB діапазон `0x80`–`0xEF`:** призначені вендором коди переривань (*Vendor Specific*).
* **MDB діапазон `0xF0`–`0xFF`:** системні службові коди (переповнення черги, збій калібрування, скидання за живленням).

#### Структура статусного регістра (GETSTATUS)

Команда прямого опитування статусу `GETSTATUS` (код `0x90`) повертає два байти діагностики:
* **Байт 0 (молодший):**
  * `Біт 0`: прапорець очікування переривання (*Pending Interrupt*).
  * `Біт 1`: прапорець наявності помилки протоколу (*Protocol Error*).
  * `Біти [3:2]`: стан внутрішнього буфера FIFO (порожній, частково заповнений, переповнений).
  * `Біти [7:4]`: зарезервовано.
* **Байт 1 (старший):** код останньої зафіксованої апаратної помилки виконання команди.

### 6. Структура та часові параметри кадру SDR

У базовому режимі SDR (*Single Data Rate*) дані передаються байтами по 8 бітів, де замість біта підтвердження *ACK/NACK* використовується дев'ятий біт переходу — **T-біт** (*Transition / Parity bit*).

#### Функція T-біта при записі (Master Write)

Контролер формує T-біт як біт парності для контролю цілісності:

```
T_bit = ¬ (D7 ⊕ D6 ⊕ D5 ⊕ D4 ⊕ D3 ⊕ D2 ⊕ D1 ⊕ D0)   [непарна парність: odd parity]
```

Якщо сума одиниць у байті даних парна, T-біт виставляється в `1`, забезпечуючи непарну загальну кількість одиниць у 9-бітному слові.

#### Функція T-біта при читанні (Master Read)

Цільовий пристрій використовує T-біт для індикації завершення потоку:

* `T = 1` (End of Data): ціль сигналізує контролеру, що переданий байт є останнім у буфері, і вона не має більше даних для читання.
* `T = 0` (Data Continues): ціль має наступні байти даних і готова продовжувати читання на наступному тактовому імпульсі SCL.

#### Основні електричні та часові межі шини I3C SDR (12.5 МГц)

| Параметр | Позначення | Мінімум | Типове | Максимум | Одиниця |
| :--- | :--- | :--- | :--- | :--- | :--- |

#### Обробка протокольних винятків та скидання завислих вузлів

Якщо цільовий пристрій зависає або втрачає синхронізацію посеред транзакції (наприклад, через електростатичну заваду або перепад напруги), контролер виконує стандартизовану послідовність аварійного відновлення:

1. **Генерація 9 імпульсів відновлення SCL:** Контролер у режимі відкритого стоку видає 9 послідовних тактових імпульсів з утриманням SDA у високому стані. Завислий автомат веденого пристрою завершує поточний байтовий цикл і відпускає лінію SDA.
2. **Формування стану STOP:** Контролер формує валідний сигнал зупинки.
3. **Широкомовне скидання адрес (`RSTDAA`, CCC `0x06`):** Контролер скидає всю адресну таблицю шини та повторно запускає цикл `ENTDAA`, повертаючи периферію до штатного стану без повного вимкнення живлення плати.
