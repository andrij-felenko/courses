# ⚙️ Проріджувач на C: цілочисловий КІХ, що рахує лише виживші виходи

Ось робочий, компільований проріджувач на C — той самий ощадний, про який каже теорія: [КІХ](book:algorithms/fir-filter)-фільтр низьких частот у цілочисловій арифметиці [фіксованої коми](book:programming/fixed-point) Q15, зі зрізом на новій межі Найквіста fs/(2M), який обчислює **лише ті виходи, що переживуть проріджування** ↓M. Він показує виграш ×M проти наївного шляху й одразу три пастки, що перетворюють бездоганний на папері фільтр на тихий брухт у залізі: переповнення акумулятора, латентність групової затримки та розігрів потоку.

---

## Задача

Потік цілочислових відліків летить на частоті fs; треба звести його до fs/M, не впустивши аліасу. Правильний шлях — спершу зняти фільтром усе вище за fs/(2M), тоді лишити кожен M-й відлік. Наївна реалізація робить це буквально: жене **кожен** вхідний відлік крізь КІХ на повній частоті, а тоді з готового потоку викидає M−1 із кожних M. Кожен викинутий вихід коштував повного скалярного добутку на N відводів — і всі ці добутки, крім кожного M-го, пропали намарно.

Ще дві обставини роблять задачу «залізною», а не навчальною. По-перше, цільова платформа — мікроконтролер без апаратного дійсного числа: рахувати доведеться в **цілих**, у форматі Q15, де множення й насичення поводяться інакше, ніж звичне `float`. По-друге, дані йдуть **потоком**: відліки прибувають по одному, коли їх віддає давач чи АЦП, тож проріджувач мусить приймати їх один за одним і сам вирішувати, коли народився вихід, а коли ще ні.

Отже, ціль потрійна: (1) фільтрувати правильно, (2) зробити рівно 1/M роботи наївного шляху, (3) вижити в цілочисловій арифметиці — без переповнень, без глюків на межах, з чесно врахованою затримкою.

## Ідея: рахувати вихід лише на кожній M-й подачі

Ключ — не обчислювати того, що однаково викинемо. Вихід потрібен кожен M-й, тож і скалярний добуток фільтра рахуємо лише там, де він виживе; проміжні M−1 не рахуємо взагалі.

Щоб це стало потоковим, потрібні дві прості речі:

- **[Кільцевий буфер](book:algorithms/ring-buffer)** останніх N входів. Кожна нова подача перезаписує найстаріший відлік і зсуває позицію запису — так фільтр завжди має під рукою своє вікно з N сусідів, не рухаючи масив.
- **Лічильник фази** 0…M−1. Кожна подача його збільшує; щойно він дійшов M — настав час одного виходу: беремо скалярний добуток вікна з коефіцієнтами, віддаємо результат, скидаємо лічильник. Між цими моментами подача лише кладе відлік у буфер і мовчить.

![Потоковий проріджувач: лічильник фази вирішує, коли feed() народжує вихід](/book/communications/signal-processing/decimation/img/stream-timeline.svg)
*Кожна подача `feed()` кладе вхідний відлік у кільцевий буфер і крутить лічильник фази 1→2→3→M. Тільки на M-й подачі народжується один вихідний відлік (`ready`), решту разів функція повертає «нічого». Перші виходи, поки буфер ще не наповнився й у вікні стоять стартові нулі, — розігрів: їх відкидають. Для N = 64 відводів і M = 4 це перші 15 виходів.*

Це і є вся економія: дорогий N-відводний добуток біжить **раз на M входів**, а не раз на вхід. Гострішу версію тієї самої думки — [поліфазний розклад](book:algorithms/polyphase-fir), де фільтр розбивають на M підфільтрів і жоден вхідний відлік навіть не читається двічі, — лишаємо на потім; базовий прийом «рахуй тільки виживших» уже забирає головну частку зайвих множень.

> 🔧 **Навіщо це.** Виграш тут не «трохи швидше», а рівно в M разів менше множень — а на мікроконтролері, де кожен такт на рахунку, це різниця між «встигає в реальному часі» і «захлинається». Той самий фільтр, переставлений із входу на вихід, коштує стільки, скільки він коштує на **низькій** частоті fs/M, а не на високій fs.

## Коефіцієнти: віконний sinc зі зрізом fs/(2M)

Перш ніж рахувати, треба самі коефіцієнти ФНЧ. Ідеальний фільтр низьких частот у часовій області — це `sinc`, нескінченний в обидва боки; реальний КІХ обрізає його вікном скінченної довжини й згладжує краї, щоб не наробити брижів. Зріз ставимо рівно на нову межу Найквіста: у частках fs це `fc = (fs/2M)/fs = 1/(2M)`. Далі — унормувати суму коефіцієнтів до одиниці (щоб фільтр не змінював підсилення на 0 Гц) і перевести кожен коефіцієнт у Q15.

```c
#include <stdint.h>
#include <stdio.h>
#include <math.h>

#ifndef M_PI
#define M_PI 3.14159265358979323846
#endif

#define TAPS 64                 /* довжина КІХ: 64 відводи */

typedef int16_t q15_t;          /* Q1.15: ціле v ↔ дійсне v / 2¹⁵, діапазон [−1, +1) */

typedef struct {
    q15_t h[TAPS];              /* коефіцієнти ФНЧ у Q15 */
    q15_t buf[TAPS];            /* кільцевий буфер останніх TAPS входів */
    int   widx;                 /* куди писати наступний вхід */
    int   phase;                /* лічильник фази: 0 … M−1 */
    int   M;                    /* коефіцієнт проріджування */
} decim_t;

static q15_t to_q15(double v)   /* дійсне [−1, +1) → ціле Q15 із насиченням */
{
    long r = lround(v * 32768.0);          /* 2¹⁵ = 32768 */
    if (r >  32767) r =  32767;             /* +1.0 у 16 бітах не подати */
    if (r < -32768) r = -32768;
    return (q15_t)r;
}

/* Скласти проріджувач: коефіцієнти ФНЧ зі зрізом fs/(2M) — віконний sinc
   із вікном Геммінга, унормований до одиничного підсилення на 0 Гц. */
void decim_init(decim_t *d, int M)
{
    const int    N  = TAPS;
    const double fc = 0.5 / (double)M;      /* зріз, нормований до fs: 1/(2M) */
    double taps[TAPS], sum = 0.0;
    int k;

    for (k = 0; k < N; k++) {
        double m    = (double)k - (N - 1) / 2.0;                     /* центр вікна */
        double sinc = (fabs(m) < 1e-9) ? 2.0 * fc
                                       : sin(2.0 * M_PI * fc * m) / (M_PI * m);
        double win  = 0.54 - 0.46 * cos(2.0 * M_PI * k / (N - 1));   /* Геммінг */
        taps[k] = sinc * win;
        sum += taps[k];
    }
    for (k = 0; k < N; k++)
        d->h[k] = to_q15(taps[k] / sum);    /* Σh = 1 → підсилення 1 на 0 Гц */

    for (k = 0; k < N; k++) d->buf[k] = 0;  /* розігрів: буфер стартує з нулів */
    d->widx  = 0;
    d->phase = 0;
    d->M     = M;
}
```

Пік коефіцієнта тут — приблизно `2·fc = 1/M`, тобто для M = 4 близько 0.25, у Q15 це ~8192: жоден окремий відвід не виходить за 16 біт. А ось їхня **сума** дорівнює одиниці (32768 у Q15) — і саме вона визначить, наскільки широким має бути акумулятор. Про це — далі.

## Робочий код: гарячий шлях

Серце проріджувача — одна функція. Вона приймає один вхідний відлік, кладе його в кільце й вирішує: чи це та сама M-та подача, на якій народжується вихід. Якщо ні — мовчки повертає 0. Якщо так — рахує скалярний добуток вікна з коефіцієнтами й повертає 1, поклавши вихід у `*y`. Це і є злитий інтерфейс `feed()`/`ready()`: подаєш відлік — і одразу дізнаєшся, чи вийшло щось на виході.

```c
/* Подати один вхідний відлік x. Якщо він завершив групу з M входів —
   обчислити вихідний відлік, покласти в *y і повернути 1; інакше 0. */
int decim_put(decim_t *d, q15_t x, q15_t *y)
{
    int64_t acc;
    int idx, k;

    d->buf[d->widx] = x;                        /* записали найновіший відлік */
    if (++d->widx == TAPS) d->widx = 0;         /* обгортання кільця */

    if (++d->phase < d->M) return 0;            /* ще не M-та подача — виходу нема */
    d->phase = 0;                               /* почали нову групу */

    acc = 0;
    idx = (d->widx == 0) ? TAPS - 1 : d->widx - 1;      /* найновіший відлік */
    for (k = 0; k < TAPS; k++) {
        acc += (int64_t)d->h[k] * d->buf[idx];  /* Q15·Q15 = Q30, розширено ДО множення */
        idx = (idx == 0) ? TAPS - 1 : idx - 1;  /* крок назад у часі, з обгортанням */
    }
    acc = (acc + (1 << 14)) >> 15;              /* Q30 → Q15 з округленням (2¹⁴ = ½ LSB) */
    if (acc >  32767) acc =  32767;             /* насичення, а не обгортання */
    if (acc < -32768) acc = -32768;
    *y = (q15_t)acc;
    return 1;
}
```

Розкладемо, що тут відбувається. Найновіший відлік лежить на позиції `widx−1` (з обгортанням), і цикл іде від нього назад у часі, парує `h[0]` з найновішим, `h[1]` — із попереднім, і так далі: це буквально `y = Σ h[k]·x[n−k]`, звичайна згортка КІХ. Обгортання індексу — той самий трюк кільцевого буфера, тільки в зворотний бік. Кожне множення двох Q15-чисел дає Q30, сума йде в широкий акумулятор, а тоді один зсув повертає результат у Q15 і насичення тримає його в 16 бітах. Про три позначені рядки — `int64_t`, `>> 15` і насичення — окрема розмова нижче: у них ховаються всі пастки цілочислової арифметики.

Тепер демонстрація. Вона робить дві речі: рахує, скільки множень коштує наївний і ощадний шляхи (виграш ×M), і перевіряє, що фільтр справді глушить тон вище за нову межу Найквіста, а нижчий пропускає.

```c
int main(void)
{
    const int    M  = 4;
    const double fs = 48000.0;          /* Гц */
    const int    K  = 4096;             /* вхідних відліків на прогін */
    decim_t d;
    q15_t   y;
    int     n, t;

    /* (1) робота: множень на вихід */
    long outs       = K / M;
    long muls_smart = outs * (long)TAPS;        /* лише виживші виходи */
    long muls_naive = (long)K * TAPS;           /* КІХ на кожному вході */
    printf("вхід %d відліків, M=%d, відводів=%d\n", K, M, TAPS);
    printf("наївно:  %ld множень\n", muls_naive);
    printf("розумно: %ld множень  (×%.1f менше)\n",
           muls_smart, (double)muls_naive / muls_smart);

    /* (2) чи глушиться високий тон? 2 кГц має пройти, 9 кГц (> 6 кГц) — згаснути */
    double freqs[2] = { 2000.0, 9000.0 };
    for (t = 0; t < 2; t++) {
        decim_init(&d, M);
        int peak = 0;
        for (n = 0; n < K; n++) {
            double s = 0.7 * sin(2.0 * M_PI * freqs[t] * n / fs);
            if (decim_put(&d, to_q15(s), &y)) {
                int a = (y < 0) ? -y : y;
                if (n > K / 2 && a > peak) peak = a;    /* заміряємо після розігріву */
            }
        }
        printf("тон %.0f Гц: пік виходу %.3f\n", freqs[t], peak / 32768.0);
    }
    return 0;
}
```

Збірка: `cc -std=c11 decimator.c -lm`. На виході — щось таке:

```
вхід 4096 відліків, M=4, відводів=64
наївно:  262144 множень
розумно: 65536 множень  (×4.0 менше)
тон 2000 Гц: пік виходу 0.695
тон 9000 Гц: пік виходу 0.004
```

Обидва твердження підтверджено числом: ощадний шлях зробив рівно вчетверо менше множень, а тон 9 кГц, який при наївному викиданні відліків склався б у фальшиві 3 кГц, фільтр приглушив у ~170 разів — до майже нуля. Пастка аліасингу закрита ще **до** проріджування, як і має бути.

## Пастка 1: переповнення акумулятора й масштаб

Q15 подає дійсне число `r` цілим `v = round(r·2¹⁵)`: одиниця стає 32768, діапазон — [−1, +1). Добуток двох Q15-чисел — уже Q30 (два дробові множники по 15 біт складають 30), і його величина сягає 2³⁰ ≈ 1.07 млрд — це на **один** біт не дотягує до стелі 32-бітного цілого (2³¹−1 ≈ 2.15 млрд). Звідси й спокуса: «добуток влазить у int32 → накопичуватиму в int32». Це і є пастка.

![Розрядність у цілочисловій згортці: добуток влазить у int32, а сума — не конче](/book/communications/signal-processing/decimation/img/q15-accum.svg)
*Один добуток Q15·Q15 = Q30 сягає 2³⁰ і ще влазить у int32 (стеля 2³¹). Але сума N = 64 таких доданків у найгіршому разі сягає N·2³⁰ = 2³⁶ — це в 32 рази за стелю int32. Реальна сума для унормованого ФНЧ менша, ≈ Σ|h|·2³⁰ (трохи вище за 2³⁰), тож у int32 вона ще ледве влазить — саме тому наївний int32-код «працює», аж поки не зміниш фільтр. int64-акумулятор зі стелею 2⁶³ знімає питання назавжди.*

Різниця — між **одним** добутком і **сумою** N добутків. Верхня межа суми — N·2³⁰; для 64 відводів це 2³⁶, у 32 рази за 32-бітну стелю. Реальна сума менша, бо коефіцієнти малі й різнознакові: для унормованого ФНЧ вона ≈ Σ|h|·2³⁰, а Σ|h| у доброго фільтра лише трохи більша за 1. Тому наївний int32-код часто **навіть працює** — на цьому конкретному фільтрі. А тоді ти піднімаєш M, чи береш фільтр із підсиленням, чи довше вікно — Σ|h| росте, сума перестрибує 2³¹, і 32-бітне ціле тихо **обгортається**: гучний додатний відлік вискакує гучним від'ємним. Ніякого попередження — просто тріск у даних.

Ліки прості: акумулятор **ширший за добуток**. На ПК це `int64_t` — стеля 2⁶³ так далеко, що сума N Q30-доданків до неї не дістане за жодного мислимого N. На DSP-ядрі ту саму роль грає апаратний 40-бітний акумулятор із кількома «сторожовими» бітами саме під такі суми. Дешево, і цілий клас помилок зникає.

Лишилося повернути Q30-суму в Q15 — зсувом на 15 біт праворуч. Просте `acc >> 15` округлює донизу; щоб округлити до найближчого, додаємо перед зсувом пів-одиниці молодшого розряду, `(acc + (1 << 14)) >> 15`. (Зсув від'ємного цілого праворуч формально визначає стандарт «як реалізація хоче», та всі реальні компілятори роблять арифметичний зсув — тобто те, що нам і треба.) І останнє: результат теж треба **наситити** до 16 біт, а не дати йому обгорнутися. Насичення притискає перебір до 32767 чи −32768 — чутно як м'яке кліпування; обгортання ж перекидає знак — чутно як гучний глюк. Тому в DSP арифметика насичувальна.

## Пастка 2: групова затримка — це латентність

Наш КІХ **симетричний** (вікно й sinc симетричні відносно центру), а симетричний КІХ має лінійну фазу: всі частоти він затримує **однаково**, рівно на (N−1)/2 відліків. Це водночас велика чеснота й неминуча ціна.

Чеснота — що затримка **однакова для всіх частот**: форма сигналу не спотворюється, бо ніяка складова не «випереджає» іншу. Саме за це лінійнофазові КІХ цінують там, де важлива форма — в аудіо, у вимірюваннях.

Ціна — що ця затримка **є**, і вона реальна. Для N = 64 це (64−1)/2 = 31.5 вхідного відліку. При fs = 48 кГц — 31.5/48000 ≈ 0.66 мс чистої латентності: вихід, що відповідає «теперішньому» входу, з'явиться на 0.66 мс пізніше. У переліку частот це дрібниця, а от у **контурі керування** — ні: 0.66 мс запізнення у зворотному зв'язку з'їдають запас стійкості, і що агресивніший регулятор, то помітніше. Тому в конвеєрі давача довжину фільтра беруть не «якомога більшу для гострішого зрізу», а найкоротшу, що дає потрібне придушення, — бо кожен зайвий відвід додає затримки. Глибше про те, як [груповий час затримки](book:electronics/group-delay) міряють і чим за нього платять, — окремо.

## Пастка 3: розігрів і перші відліки

Потоковий інтерфейс має дві межові тонкощі, і обидві кусають початківця.

Перша: `decim_put()` віддає вихід **не щоразу**. З кожних M подач лише одна повертає 1; решта M−1 повертають 0 і нічого не кладуть у `*y`. Хто викликає проріджувач, мусить **перевіряти повернене значення**, а не думати, ніби на кожен вхід є вихід. Звідси й фраза «що робити з першими M−1 відліками»: перші M−1 подач виходу не дають зовсім — і це нормально, це сама природа зниження частоти.

Друга, тонша: буфер стартує з нулів, тож найперші виходи фільтр рахує, домішуючи в вікно **стартові нулі**, яких у сигналі не було. Це перехідний сплеск, поки вікно не наповнилося справжніми відліками. Вихід стає «чистим» лише тоді, коли в буфері не лишилося жодного стартового нуля — тобто після N подач. Усе, що вилетіло раніше, — розігрів; для чистого старту ці виходи відкидають. Скільки саме? Стільки, скільки виходів народилося за перші N входів: ⌊(N−1)/M⌋. Для N = 64, M = 4 це ⌊63/4⌋ = 15 виходів. Хто цього не знає — бачить на початку кожного потоку загадковий короткий тріск і довго шукає його в математиці фільтра, хоч це просто незігнорований розігрів.

## Складність і виграш

Порахуймо ціну одного вихідного відліку. Скалярний добуток — N множень і N−1 додавань; пам'ять — кільцевий буфер на N відліків плюс N коефіцієнтів, тобто O(N) сталого місця, без жодних виділень у гарячому шляху. Найголовніше — робота міряється **на вихід**, а виходів у M разів менше, ніж входів. Тому за секунду:

```
N=64 відводів, fs=48 кГц, M=4 → вихід 12 кГц

наївно (КІХ на кожному вході):   64 × 48000 = 3 072 000 множень/с
розумно (лише виживші виходи):   64 × 12000 =   768 000 множень/с

виграш = 3 072 000 / 768 000 = 4 = M
```

Правило чисте: правильний проріджувач коштує рівно стільки, скільки фільтр на **вихідній** частоті, — і що більше M, то дорожчою була б наївна лічба й то більший виграш. Дрібне вдосконалення, яке варто знати: внутрішній цикл робить по одній перевірці обгортання на кожен відвід. Її прибирають, розбивши цикл на два суцільні пробіги (від позиції запису до кінця масиву й від початку до неї) або тримаючи буфер [подвоєної довжини](book:algorithms/ring-buffer) — тоді індекс біжить без розгалуження, і компілятор векторизує тіло. А коли M справді велике — десятки, сотні, — навіть ця ощадна лічба задорога на найвищій частоті, і перший шар віддають безмножниковому CIC, лишаючи КІХ на комфортну низьку частоту. Але це вже надбудова; серце ощадного проріджувача — та сама думка «рахуй лише виживших», прошита у лічильник фази.
