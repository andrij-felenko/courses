# 🧮 Математика HKDF та дерево ключів TLS 1.3

Дерево ключів TLS 1.3 (Key Schedule) базується на двофазній конструкції виведення ключів на базі HMAC — стандартизованій функції HKDF (HMAC-based Extract-and-Expand Key Derivation Function, RFC 5869).

Замість монолітної псевдовипадкової функції (PRF), що застосовувалася в TLS 1.2, стандарт TLS 1.3 розділяє процес генерації криптографічних матеріалів на суворо детерміновані фази з чітким розділенням криптографічних контекстів: раннього секрету (Early Secret), секрету рукостискання (Handshake Secret) та головного секрету додатку (Master Secret).

## Математичні основи екстракції ентропії та лема про залишковий хеш

У криптографічних протоколах спільний секрет, отриманий у результаті асиметричного обміну Діффі — Геллмана, є точкою на еліптичній кривій або елементом скінченного поля. Хоча такий секрет має високу ентропію (його неможливо вгадати за поліноміальний час), його двійкове подання розподілене нерівномірно: біти координат задовольняють алгебраїчне рівняння кривої і не є незалежними псевдовипадковими величинами.

Використання такого сирого значення безпосередньо як симетричного ключа для шифру AES є небезпечним, оскільки алгоритми симетричного шифрування доводять свою стійкість лише за умови, що ключ обрано зі строго рівномірного розподілу на множині двійкових рядків довжини `k`.

Задача перетворення нерівномірного джерела високої мін-ентропії у криптографічно стійкий псевдовипадковий бітовий рядок розв'язується за допомогою екстракторів випадковості (Randomness Extractors). Математичним обґрунтуванням цього процесу є **лема про залишковий хеш (Leftover Hash Lemma)**: 

Нехай `X` — випадкова величина над множиною `{0, 1}^n` з мін-ентропією `H_min(X) = -log₂ (max_x Pr[X = x]) ≥ k`. Нехай `H = {h_s : {0, 1}^n → {0, 1}^m}` — 2-універсальне сімейство хеш-функцій. Тоді для випадково обраного індексу `S` та незалежного `X`:

```
Статистична відстань розподілу від ідеального:
SD( (S, h_S(X)), (S, U_m) ) ≤ (1 / 2) · √( 2^( -(k - m) ) )
```

де `U_m` — ідеальний рівномірний розподіл над `{0, 1}^m`.

Щоб статистична відстань `ε` була зневажливо малою (наприклад, `ε ≤ 2⁻⁶⁴`), достатньо встановити розмір вихідного блоку `m ≤ k - 2·log₂(1/ε) = k - 128`.

У функції HKDF роль 2-універсального екстрактора виконує конструкція HMAC, де роль випадкового вибору `S` відіграє сіль (`Salt`), а нерівномірним джерелом `X` є вхідний ключовий матеріал (`IKM`). Для кривої X25519 мін-ентропія `k ≈ 252` біти, а вихід `m = 256` бітів, що в моделі псевдовипадкових оракулів (PRF) гарантує практичну нерозрізненість згенерованого псевдовипадкового ключа `PRK` від ідеальної випадковості.

## Конструкція HKDF: Extract та Expand

Функція HKDF складається з двох фундаментальних математичних операторів: екстракції ентропії (Extract) та її подальшого псевдовипадкового розширення (Expand).

```
Вхідні параметри функції HKDF:
IKM    : вхідний ключовий матеріал (Input Keying Material)
Salt   : сіль — псевдовипадкова послідовність (якщо відсутня, береться рядок із Hash.len нулів)
Info   : контекстний рядок застосування (Application-Specific Context)
L      : бажана довжина вихідного ключа в байтах
Hash   : криптографічна хеш-функція (наприклад, SHA-256 з довжиною блоку Hash.len = 32 байти)
```

### 1. Фаза екстракції: HKDF-Extract

Мета екстракції — перетворити сирий вхідний матеріал `IKM` у псевдовипадковий псевдорівномірний ключ фіксованої довжини `PRK` (Pseudorandom Key):

```
PRK
= HMAC-Hash(Salt, IKM)      [стиснення нерівномірної ентропії у криптографічний псевдовипадковий ключ]
```

Властивості оператора екстракції:
- Довжина вектора `PRK` завжди точно дорівнює вихідній довжині хеш-функції `Hash.len` (32 байти для SHA-256, 48 байтів для SHA-384).
- Якщо сіль `Salt` не передана, вона ініціалізується як масив із `Hash.len` нульових байтів.
- Під припущенням, що HMAC є функцією псевдовипадкового стиснення (Dual-PRF), вектор `PRK` є нерозрізнимим від випадкового оракула для будь-якого поліноміального супротивника.

### 2. Фаза розширення: HKDF-Expand

Маючи псевдовипадковий ключ `PRK`, фаза розширення генерує псевдовипадковий потік довільної довжини `L ≤ 255 · Hash.len`, обчислюючи послідовність криптографічних блоків `T(i)`:

```
T(0) = порожній рядок (довжина 0)
T(1) = HMAC-Hash(PRK, T(0) || Info || 0x01)
T(2) = HMAC-Hash(PRK, T(1) || Info || 0x02)
T(3) = HMAC-Hash(PRK, T(2) || Info || 0x03)
...
T(N) = HMAC-Hash(PRK, T(N-1) || Info || N)

OKM
= T(1) || T(2) || ... || T(N)   [конкатенація з подальшим відсіканням перших L байтів]
```

де `N = ⌈L / Hash.len⌉`, а символ `||` позначає конкатенацію байтових масивів. Однобайтовий лічильник у кінці кожного блоку унеможливлює виникнення циклічних повторень у вихідному потоці.

### 3. Спеціалізоване розширення: HKDF-Expand-Label

Протокол TLS 1.3 інкапсулює виклик `HKDF-Expand` у стандартизовану функцію `HKDF-Expand-Label`, яка формує строго типізовану структуру `Info`, унеможливлюючи міжпротокольні колізії:

```
struct {
    uint16 length = L;
    opaque label<7..255> = "tls13 " + Label;
    opaque context<0..255> = Context;
} HkdfLabel;

HKDF-Expand-Label(Secret, Label, Context, Length)
= HKDF-Expand(Secret, HkdfLabel, Length)    [детерміноване формування цільового ключа]
```

Префікс `"tls13 "` довжиною 6 байтів гарантує, що ключі, виведені в TLS 1.3, ніколи не збіжаться з ключами інших криптографічних протоколів, навіть якщо в них випадково використано однакові значення `Secret` та `Label`.

## Математична структура дерева ключів TLS 1.3

Дерево ключів TLS 1.3 розгортається у три послідовні фази. На кожному етапі задіюється поняття хешу транскрипту повідомлень (Transcript Hash).

Хеш транскрипту для стану `k` визначається як хеш від конкатенації всіх надісланих і прийнятих повідомлень рукостискання від початку з'єднання:

```
Transcript-Hash(k)
= Hash(M₁ || M₂ || ... || Mₖ)   [криптографічна фіксація повної історії обміну]
```

Завдяки властивості стійкості хеш-функції до пошуку других прообразів (Second Preimage Resistance), неможливо модифікувати жодне поле в `ClientHello` чи `ServerHello` без повної зміни `Transcript-Hash`.

### Етап 1: Ранній секрет (Early Secret)

Якщо клієнт та сервер використовують спільний попередньо узгоджений ключ `PSK`, він подається як `IKM`. Якщо `PSK` не використовується, береться нульовий вектор довжини `Hash.len`:

```
Early Secret
= HKDF-Extract(0, PSK)                                  [ініціалізація дерева ентропії]

Client Early Traffic Secret
= HKDF-Expand-Label(Early Secret, "c e traffic", Transcript-Hash(ClientHello), Hash.len)

Early Exporter Master Secret
= HKDF-Expand-Label(Early Secret, "e exp master", Transcript-Hash(ClientHello), Hash.len)
```

З вектора `Client Early Traffic Secret` генеруються симетричний ключ `Key` та вектор ініціалізації `IV` для захисту ранніх даних 0-RTT.

### Етап 2: Секрет рукостискання (Handshake Secret)

Для переходу до наступного рівня генерується проміжний виведений секрет:

```
Derived-Early-Secret
= HKDF-Expand-Label(Early Secret, "derived", Hash(""), Hash.len)
```

Клієнт і сервер виконують обмін ефемерними ключами на еліптичній кривій (наприклад, X25519). Нехай клієнт має приватний скаляр `x_A` та публічну точку `Y_A = x_A · G`, а сервер — приватний скаляр `x_B` та публічну точку `Y_B = x_B · G`. Спільний скалярний добуток:

```
Z
= x_A · Y_B                                             [обчислення клієнтом]
= x_B · Y_A                                             [обчислення сервером]
= x_A · x_B · G                                         [спільний секрет ECDHE]
```

Отриманий вектор координат `Z` подається як `IKM` для другої фази екстракції:

```
Handshake Secret
= HKDF-Extract(Derived-Early-Secret, Z)                 [змішування асиметричного секрету]

Client Handshake Traffic Secret
= HKDF-Expand-Label(Handshake Secret, "c hs traffic", Transcript-Hash(ClientHello..ServerHello), Hash.len)

Server Handshake Traffic Secret
= HKDF-Expand-Label(Handshake Secret, "s hs traffic", Transcript-Hash(ClientHello..ServerHello), Hash.len)
```

Ключі, виведені з `Client Handshake Traffic Secret` та `Server Handshake Traffic Secret`, захищають решту повідомлень рукостискання (`EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`).

### Етап 3: Головний секрет додатку (Master Secret)

Після завершення обміну ефемерними ключами дерево переходить у фінальну фазу без додавання нових зовнішніх секретів (`IKM = 0`):

```
Derived-Handshake-Secret
= HKDF-Expand-Label(Handshake Secret, "derived", Hash(""), Hash.len)

Master Secret
= HKDF-Extract(Derived-Handshake-Secret, 0)             [консолідація головного сесійного секрету]

Client Application Traffic Secret 0
= HKDF-Expand-Label(Master Secret, "c ap traffic", Transcript-Hash(ClientHello..ServerFinished), Hash.len)

Server Application Traffic Secret 0
= HKDF-Expand-Label(Master Secret, "s ap traffic", Transcript-Hash(ClientHello..ServerFinished), Hash.len)

Resumption Master Secret
= HKDF-Expand-Label(Master Secret, "res master", Transcript-Hash(ClientHello..ClientFinished), Hash.len)
```

## Алгебраїчні основи обміну ключами на кривій Curve25519

У сучасному протоколі TLS 1.3 домінуючою групою для обміну ключами є `X25519` (RFC 7748), побудована на кривій Монтгомері над простим полем `GF(2²⁵⁵ - 19)`. Рівняння кривої задається у вигляді:

```
y² = x³ + 486662·x² + x   [над скінченним полем GF(2²⁵⁵ - 19)]
```

Ключовою математичною особливістю функції X25519 є те, що обчислення спільного секрету використовує **виключно x-координату точки** (Куммерове розшарування), що повністю усуває потребу в обчисленні y-координати та спрощує скалярне множення.

Скалярне множення виконується за алгоритмом драбини Монтгомері (Montgomery Ladder):
1. Для приватного скаляра `k` довжиною 256 бітів спочатку виконується операція «очищення бітів» (Bit Clamping): скидаються три молодші біти `k[0] &= 248` (для усунення впливу малої підгрупи порядку 8) та встановлюється старший біт `k[31] |= 64` і скидається найвищий `k[31] &= 127`.
2. Драбина Монтгомері виконує фіксовану кількість із 255 ітерацій додавання та подвоєння точок у проективних координатах `(X:Z)`.
3. Час виконання кожної ітерації є строго незалежним від бітів скаляра `k`, що надає математичний захист від атак сторонніми каналами за часом (Timing Attacks) та споживанням потужності (DPA).

Отриманий у результаті скалярного добутку вектор `Z = X25519(x_A, Y_B)` є 32-байтною послідовністю, яка містить нерівномірну x-координату точки та подається як вхідний матеріал `IKM` для фази `HKDF-Extract`.

## Теоретико-ігрова модель безпеки та Dual-PRF властивість HMAC

Безпека функції HKDF доведена у стандартній моделі криптографії на базі двох припущень щодо конструкції HMAC:
1. **Властивість PRF (Pseudorandom Function):** Якщо перший аргумент (ключ) є рівномірно випадковим, а другий (повідомлення) контролюється атакуючим, вихід HMAC є нерозрізнимим від випадкового оракула з перевагою супротивника `Adv_PRF ≤ O(q² / 2^b)`, де `q` — кількість запитів, а `b` — довжина блоку хешу.
2. **Властивість Dual-PRF (Екстрактор випадковості):** Якщо перший аргумент є фіксованою публічною сіллю `Salt`, а другий аргумент є джерелом високої мін-ентропії `IKM` (з ентропією `H_min ≥ k`), вихід `HKDF-Extract` є статистично близьким до рівномірного з відстанню `Dist ≤ 2^{-(H_min - Hash.len)/2}`.

Це математично гарантує, що дерево ключів TLS 1.3 забезпечує криптографічну стійкість навіть у випадку, коли відкриті ключі Діффі — Геллмана піддаються активному впливу зловмисника в каналі зв'язку.

## Виведення сесійних ключів та векторів ініціалізації (Key & IV Derivation)

Для будь-якого секрету трафіку `TrafficSecret` (раннього, рукостискання чи додатку) остаточні симетричні параметри для алгоритму AEAD обчислюються за єдиними формулами:

```
AEAD Write Key
= HKDF-Expand-Label(TrafficSecret, "key", "", Key.length)   [16 байтів для AES-128, 32 байти для AES-256]

AEAD Write IV
= HKDF-Expand-Label(TrafficSecret, "iv", "", IV.length)     [завжди 12 байтів (96 біт) для TLS 1.3 AEAD]
```

## Математичне доведення безпеки транскрипту та автентифікація Finished

Повідомлення `Finished` виконує роль фінального криптографічного замка в протоколі TLS 1.3: воно математично доводить, що обидві сторони спостерігали абсолютно ідентичну послідовність бітів протягом усього процесу рукостискання.

### Теорема про непідроблюваність транскрипту (Transcript Binding)

Нехай `H` — криптографічна хеш-функція, стійка до колізій із безпекою `b` бітів, а `HMAC` — безпечний псевдовипадковий код автентифікації повідомлень. Нехай активний зловмисник посередині (MitM) намагається підмінити будь-яке поле у повідомленні `ClientHello` (наприклад, видалити запропоноване розширення чи підмінити шифрокомплект на слабший):

```
Справжній транскрипт клієнта :  T_C = M₁ || M₂ || ... || Mₖ
Підроблений транскрипт сервера:  T_S = M₁' || M₂ || ... || Mₖ   (де M₁' ≠ M₁)
```

Для успішного завершення атаки зловмисник повинен змусити сервер прийняти повідомлення `Finished` від клієнта. Це вимагає виконання однієї з двох математичних умов:
1. **Колізія хеш-функції:** `H(T_C) = H(T_S)` при `T_C ≠ T_S`. За припущенням стійкості SHA-256 / SHA-384 до колізій, імовірність знаходження такої пари за поліноміальний час обмежена величиною `Pr[Collision] ≤ O(q² / 2^b) ≈ 2⁻¹²⁸`, що є практично неможливим.
2. **Підробка коду автентифікації:** знаходження валідного значення `verify_data = HMAC(Finished_Key, H(T_S))` без знання секрету `Finished_Key`. Оскільки `Finished_Key` виводиться з `Handshake Secret` (який залежить від невідомого атакуючому асиметричного секрету `Z`), імовірність підробки `verify_data` обмежена стійкістю HMAC: `Pr[Forgery] ≤ 2^{-Hash.len} = 2⁻²⁵⁶`.

Таким чином, будь-яка спроба активного втручання в незахищені перші повідомлення рукостискання неминуче виявляється на етапі перевірки `Finished`, що призводить до негайного розриву з'єднання з фатальною помилкою `decrypt_error`.

## Математичне виведення зв'язок PSK (Binder Key Derivation)

У режимі відновлення сесії через PSK клієнт зобов'язаний криптографічно довести серверу, що він володіє відповідним ключем `PSK`, не розкриваючи його у відкритому `ClientHello`. Для цього використовується механізм зв'язок `binders`:

1. З поточного `Early Secret = HKDF-Extract(0, PSK)` обчислюється спеціальний проміжний ключ зв'язки:
```
Binder-Key
= HKDF-Expand-Label(Early Secret, "res binder", Hash(""), Hash.len)
```

2. Клієнт формує повідомлення `ClientHello` включно з усіма розширеннями, крім списку самих зв'язок `binders` (так званий скорочений транскрипт `Truncated-ClientHello`).
3. Обчислюється HMAC-код підтвердження:
```
Finished-Binder
= HMAC-Hash(Binder-Key, Transcript-Hash(Truncated-ClientHello))
```

Сервер, отримавши `ClientHello`, паралельно обчислює `Binder-Key` зі свого кешу PSK та перевіряє `Finished-Binder`. Будь-яка невідповідність означає, що квиток підроблено або транскрипт `ClientHello` був змінений посередником, що призводить до відхилення режиму PSK та переходу до повного асиметричного рукостискання 1-RTT.

## Математичні гарантії зв'язування сесій (Session Binding Invariants)

Конструкція дерева ключів TLS 1.3 надає формальні доказові гарантії криптографічної ізоляції контекстів:

1. **Некорельованість міжсесійних ключів (Inter-Session Independence):**
   Нехай дві різні сесії `S₁` та `S₂` використовують ідентичний попередньо узгоджений ключ `PSK`. Завдяки обов'язковому включенню випадкових чисел `ClientHello.random` та `ServerHello.random` у транскрипт рукостискання, значення хешів транскрипту задовольняють умову:
   `Pr[ Transcript-Hash(S₁) = Transcript-Hash(S₂) ] ≤ 2^{-Hash.len}`.
   Оскільки вихід `HKDF-Expand-Label` строго залежить від `Transcript-Hash`, сесійні ключі обох сесій є статистично незалежними: компрометація сесійного ключа першої сесії не дає жодної аналітичної переваги для атаки на другу сесію.

2. **Односпрямованість та незворотність станів (State Irreversibility):**
   Функція переходу між фазами `Derive-Secret(Secret, "derived")` є незворотною псевдовипадковою функцією на базі HMAC. Знання `Handshake Secret` не дозволяє обчислити `Early Secret`, а знання `Master Secret` не дозволяє відновити `Handshake Secret`. Це забезпечує пошарову криптографічну ізоляцію протокольних фаз.

## Експортери ключів для зовнішніх протоколів (Key Exporters)

Протокол TLS 1.3 дозволяє прикладним протоколам безпечно отримувати криптографічні ключі для зовнішніх потреб (наприклад, для захисту каналів WebRTC, автентифікації сесій SSH чи підпису токенів OAuth) без розкриття основних ключів шифрування:

```
Exported-Key-Material
= HKDF-Expand-Label(Exporter Master Secret, Label, Hash(Context), DesiredLength)
```

Завдяки властивостям псевдовипадкового розширення HKDF, експортовані ключі є криптографічно незалежними: навіть повний злам або компрометація зовнішнього сервісу WebRTC не дає зловмиснику жодної інформації про сесійні ключі трафіку TLS.

## Оновлення ключів (KeyUpdate Ratchet)

Якщо з'єднання залишається активним протягом тривалого часу або передає гігабайти даних, стандарт передбачає механізм оновлення сесійних ключів без виконання повторного асиметричного рукостискання (Forward Secrecy Ratcheting):

```
Application Traffic Secret (N + 1)
= HKDF-Expand-Label(Application Traffic Secret (N), "traffic upd", "", Hash.len)
```

Одразу після обчислення нового секрету старий секрет `Application Traffic Secret (N)` безповоротно стирається з оперативної пам'яті. Завдяки односторонньому характеру HMAC, навіть якщо поточний сесійний ключ буде скомпрометовано внаслідок експлуатації вразливості пам'яті (наприклад, переповнення буфера), зловмисник не зможе обчислити попередній ключ і розшифрувати пакети, передані до моменту компрометації.

## Математична верифікація повідомлення Finished

Повідомлення `Finished` автентифікує всю історію переговорів. Для його створення обчислюється спеціальний ключ підтвердження:

```
Finished-Key
= HKDF-Expand-Label(BaseTrafficSecret, "finished", "", Hash.len)

Verify-Data
= HMAC-Hash(Finished-Key, Transcript-Hash)              [автентифікаційний тег підсумкового стану]
```

Клієнт і сервер перевіряють, що обчислене значення `Verify-Data` збігається біт-у-біт із переданим у кадрі. Оскільки `Transcript-Hash` містить повну послідовність повідомлень, будь-яка спроба підміни параметрів шифрування, сертифікатів чи розширень активним зловмисником призведе до невідповідності `Verify-Data` і миттєвого завершення з'єднання з фатальною помилкою `decrypt_error`.

## Покроковий розрахунковий приклад

**Вхідні параметри сесії:**
- Хеш-функція: `SHA-256` (`Hash.len = 32` байти);
- Алгоритм обміну: `X25519` (`Key.len = 32` байти);
- Шифрокомплект: `TLS_AES_128_GCM_SHA256` (довжина симетричного ключа `16` байтів, довжина `IV = 12` байтів);
- Відсутній `PSK` (чистий старт з'єднання).

```
1. Обчислення Early Secret:
IKM = 0x00 [32 нульові байти]
Salt = 0x00 [32 нульові байти]
Early Secret
= HMAC-SHA256(Salt, IKM)
= 0x33ad0a1c607ec03b09e6cd9893680ce210adf300aa1f2660e1b22e10f170f92a [32 байти]

2. Обчислення Derived-Early-Secret:
EmptyHash = SHA256("")
HkdfLabel = 0x0020 || 0x07 || "tls13 derived" || 0x20 || EmptyHash
Derived-Early-Secret
= HKDF-Expand(Early Secret, HkdfLabel, 32)
= 0x6f2615a108c702c5678f54fc9dbab69716c076189c48250cebeac3576c3611ba [32 байти]

3. Обчислення Handshake Secret з ECDHE Z:
Нехай Z = 0x8b54... [32 байти координат точки X25519]
Handshake Secret
= HMAC-SHA256(Derived-Early-Secret, Z)
= 0x1dc8... [32 байти Handshake Secret]

4. Виведення ключів клієнта для рукостискання:
Transcript = SHA256(ClientHello || ServerHello)
Client Handshake Traffic Secret
= HKDF-Expand-Label(Handshake Secret, "c hs traffic", Transcript, 32)

5. Виведення Write Key (16 байтів) та Write IV (12 байтів):
Write Key
= HKDF-Expand-Label(Client Handshake Traffic Secret, "key", "", 16)
Write IV
= HKDF-Expand-Label(Client Handshake Traffic Secret, "iv", "", 12)
```

Завдяки незворотності операцій HMAC, навіть якщо ключ трафіку додатку `Client Application Traffic Secret` буде скомпрометовано внаслідок витоку пам'яті процесу, зловмисник не зможе обчислити назад ні `Handshake Secret`, ні `Early Secret`, забезпечуючи повну ізоляцію рівнів безпеки.
