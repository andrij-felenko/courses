# 📋 Реєстр, формати повідомлень та протокольні профілі SASL

Цей довідник містить вичерпну технічну специфікацію реєстру IANA, ABNF-граматики повідомлень, двійкові формати кадрів, правила нормалізації SASLprep та детальні протокольні профілі впровадження каркаса SASL (RFC 4422) у прикладні системи зв'язку (IMAP, SMTP, LDAP, Apache Kafka, PostgreSQL, AMQP 1.0). У ньому зведено точні синтаксичні контракти, бінарні зміщення та матриці відповідності помилок, необхідні інженеру для створення клієнтських драйверів, серверних обробників та шлюзів безпеки.

## Реєстр механізмів IANA SASL

Офіційний реєстр механізмів адмініструється організацією IANA (*Internet Assigned Numbers Authority*). Назва механізму є рядком із суворими синтаксичними обмеженнями:

```
sasl-mech-name = 1*20mech-char
mech-char      = UPPER-ALPHA / DIGIT / "-" / "_"
UPPER-ALPHA    = %x41-5A   ; Символи 'A'-'Z' (ASCII)
DIGIT          = %x30-39   ; Символи '0'-'9' (ASCII)
```

1. **Довжина:** Від 1 до 20 символів включно.
2. **Алфавіт:** Лише великі літери латиниці `A-Z`, цифри `0-9`, дефіс `-` та підкреслення `_`. Будь-які малі літери, пробіли, крапки або спецсимволи суворо заборонені.
3. **Префікси вендорів:** Механізми, розроблені окремими компаніями без відкритого стандарту IETF, повинні починатися з префікса `X-` (наприклад, `X-OAUTH2`, `X-AMZN-TOKEN`).
4. **Суфікс прив'язки до каналу:** Механізми, що підтримують обов'язкову криптографічну прив'язку до захищеного транспорту TLS (*Channel Binding*), отримують стандартизований суфікс `-PLUS` (наприклад, `SCRAM-SHA-256-PLUS`, `GS2-KRB5-PLUS`).

| Назва механізму | Стандарт RFC | Схема автентифікації | Взаємна перевірка | Рівень безпеки (QOP) | Підтримка Channel Binding |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `PLAIN` | RFC 4616 | Простий відкритий пароль | Ні | Ні | Ні |
| `EXTERNAL` | RFC 4422 | Неявні облікові дані транспорту | Залежить від TLS | Ні | Зовнішній TLS |
| `SCRAM-SHA-1` | RFC 5802 | Солений виклик-відповідь (SHA-1) | Так | Ні | Лише в `-PLUS` |
| `SCRAM-SHA-256` | RFC 7677 | Солений виклик-відповідь (SHA-256) | Так | Ні | Лише в `-PLUS` |
| `GSSAPI` | RFC 4752 | Квитки Kerberos v5 (GSS-API) | Так | Так (`auth-int`, `auth-conf`) | Через GS2 |
| `OAUTHBEARER` | RFC 7628 | Токен доступу OAuth 2.0 Bearer (JWT) | Ні | Ні | Так (GS2 header) |
| `ANONYMOUS` | RFC 4505 | Неавтентифікований гостьовий доступ | Ні | Ні | Ні |
| `DIGEST-MD5` | RFC 2831 (Historic) | Дайджест-виклик (MD5) | Так | Так (застарілий RC4/DES) | Ні |

## Специфікація нормалізації рядків SASLprep (RFC 4013)

Для запобігання ситуаціям, коли візуально ідентичні імена користувачів або паролі відхиляються сервером через різні двійкові коди символів Unicode (наприклад, форми NFC проти NFD), стандарт RFC 4013 визначає профіль нормалізації **SASLprep** на базі алгоритму Stringprep (RFC 3454).

Алгоритм SASLprep обробляє вхідний рядок у чотири послідовні фази:

1. **Відображення (Mapping):**
   - Нерозривні пробіли (`U+00A0`), ідеографічні пробіли (`U+3000`) та інші символи простору відображаються у звичайний ASCII-пробіл `U+0020` (таблиця C.1.2).
   - «М'які переноси» (`U+00AD`) та невидимі символи нульової ширини (`U+200B`) видаляються (відображаються в порожній рядок, таблиця B.1).
2. **Нормалізація (Normalization):**
   - Рядок канонізується за алгоритмом Unicode **NFKC** (*Compatibility Decomposition, followed by Canonical Composition*).
3. **Перевірка заборонених символів (Prohibited Output):**
   - Керуючі символи ASCII (`U+0000-001F`, `U+007F`) та non-ASCII (`U+0080-009F`, `U+06DD`, `U+200E-200F`, таблиця C.2.1/C.2.2).
   - Символи приватного використання (*Private Use*, `U+E000-F8FF`, `U+F0000-FFFFD`, таблиця C.3).
   - Непризначені кодові пункти (*Unassigned code points*, таблиця A.1).
   - Суррогатні кодові пункти (`U+D800-DFFF`, таблиця C.4).
   - Несимвольні кодові пункти (`U+FDD0-FDEF`, `U+FFFE-FFFF`, таблиця C.5).
   - Неприпустимі теги та символи зміни порядку (`U+FFF9-FFFC`, `U+E0001`, `U+E0020-E007F`, таблиця C.6/C.7/C.8).
   - Якщо знайдено будь-який заборонений символ, обробка завершується аварійною помилкою валідації.
4. **Двонаправлена перевірка (Bidirectional Characters / Bidi):**
   - Якщо рядок містить хоча б один символ із властивістю R або AL (символи правостороннього письма арабиці чи івриту, таблиця D.1), перший і останній символи рядка обов'язково повинні мати властивість R або AL.
   - Рядок, що містить символи R/AL, категорично не може одночасно містити символи лівостороннього письма L (таблиця D.2).

## Специфікація форматів повідомлень механізмів

### 1. Механізм PLAIN (RFC 4616)

Механізм `PLAIN` передає облікові дані у вигляді єдиного двійкового масиву, де елементи розділено нульовими байтами:

```
plain-message = [ authzid ] UTF8NUL authcid UTF8NUL passwd
authzid       = 1*UTF8-char   ; Ідентифікатор авторизації (права доступу)
authcid       = 1*UTF8-char   ; Ідентифікатор автентифікації (логін)
passwd        = 1*UTF8-char   ; Пароль користувача (UTF-8)
UTF8NUL       = %x00          ; Нульовий октет '\0'
```

- **Структура корисного навантаження:** Послідовність байтів `authzid \0 authcid \0 passwd`.
- **Семантика полів:**
  - Якщо `authzid` порожній, рядок починається безпосередньо з нульового байта `\0`. Права доступу надаються суб'єкту `authcid`. Приклад: `\0alice\0SecretPass_42!` (Base64: `AGFsaWNlAFNlY3JldFBhc3NfNDIh`).
  - Якщо `authzid` вказано (наприклад, `admin\0alice\0SecretPass_42!`), сервер перевіряє пароль користувача `alice`, але після успішної перевірки призначає права облікового запису `admin` (делегування або маскування). У Base64: `YWRtaW4AYWxpY2UAU2VjcmV0UGFzc180MiE=`.
- **Вимога безпеки:** Механізм `PLAIN` категорично заборонено використовувати через відкриті незашифровані канали зв'язку. Сервер зобов'язаний оголошувати `AUTH=PLAIN` лише після успішного встановлення сесії TLS (або через локальний UNIX-сокет).

### 2. Механізм EXTERNAL (RFC 4422)

Механізм `EXTERNAL` використовується, коли клієнт уже був однозначно ідентифікований на нижчому рівні зв'язку (за допомогою клієнтського сертифіката X.509 у протоколі TLS mTLS, безпечної асоціації IPsec або облікових даних процесу UNIX-сокета через системний виклик `getsockopt(..., SO_PEERCRED)`).

```
external-message = [ authzid ]
```

- Клієнт надсилає порожній рядок (якщо бажає авторизуватися як суб'єкт, закладений у клієнтському сертифікаті / сокеті), або вказує явний `authzid` для зміни контексту прав.
- Сервер витягує ідентичність клієнта безпосередньо з дескриптора з'єднання і завершує автентифікацію без обміну паролями.

### 3. Каркас GS2 та механізми родини SCRAM (RFC 5801, RFC 5802, RFC 7677)

Механізми `SCRAM-SHA-256` та `SCRAM-SHA-256-PLUS` використовують стандартизований заголовок GS2 (*Generic Security Services v2*), що розташовується на початку першого повідомлення клієнта:

```
gs2-header   = gs2-cb-flag "," [ gs2-authzid ] ","
gs2-cb-flag  = ("p=" cb-name) / "n" / "y"
cb-name      = 1*(ALPHA / DIGIT / "-" / ".")
gs2-authzid  = "a=" saslprep-authzid
```

1. **Прапорець зв'язування з каналом (`gs2-cb-flag`):**
   - `n`: Клієнт стверджує, що він **не підтримує** прив'язку до каналу (наприклад, у незашифрованому каналі або механізмі без суфікса `-PLUS`).
   - `y`: Клієнт підтримує прив'язку до каналу, але вважає, що сервер її не оголосив (використовується для виявлення MITM-атак пониження можливостей).
   - `p=tls-server-end-point` або `p=tls-unique`: Клієнт явно застосовує вказаний тип криптографічної прив'язки до поточного TLS-з'єднання.
2. **Атрибути повідомлень SCRAM (пари `ключ=значення` через кому):**
   - `n=username`: Ім'я користувача (пройдене через алгоритм SASLprep).
   - `r=nonce`: Рядок випадкового виклику клієнта або об'єднаний виклик `client_nonce || server_nonce`.
   - `s=salt`: Індивідуальна криптографічна сіль користувача у форматі Base64.
   - `i=iterations`: Кількість ітерацій алгоритму PBKDF2 (ціле додатне число, зазвичай не менше 4096).
   - `c=channel-binding`: Закодований у Base64 заголовок GS2 разом із бінарними даними прив'язки до каналу (наприклад, SHA-256 відбиток сертифіката сервера).
   - `p=proof`: Маскований доказ клієнта `ClientProof = ClientKey ⊕ ClientSignature` у Base64.
   - `v=signature`: Цифровий підпис сервера `ServerSignature` у Base64.
   - `e=error`: Код помилки від сервера (`invalid-encoding`, `bad-channel-binding`, `unknown-user`, `invalid-proof`).

### 4. Механізм GSSAPI (RFC 4752)

Механізм `GSSAPI` забезпечує прозору інтеграцію протоколу Kerberos v5 у SASL.

- **Початковий токен клієнта:** Клієнт звертається до Kerberos KDC, отримує службовий квиток для SPN (*Service Principal Name*, наприклад `imap/mail.example.com@REALM`) і передає токен `GSS_Init_sec_context()` (структура `KRB_AP_REQ`).
- **Відповідь сервера:** Сервер перевіряє квиток через `GSS_Accept_sec_context()` і повертає токен `KRB_AP_REP`.
- **Узгодження рівня безпеки:** Після встановлення контексту Kerberos сервер надсилає 4-байтове повідомлення:
  - Байт 0: Бітова маска підтримуваних режимів захисту QOP: `0x01` (`auth`), `0x02` (`auth-int`), `0x04` (`auth-conf`).
  - Байти 1..3: Максимальний розмір буфера прикладних даних (24-бітне число Big-Endian), який сервер здатний прийняти після завершення автентифікації.
- Клієнт повертає свій вибір режиму QOP, максимальний розмір власного буфера та ідентифікатор авторизації `authzid`, підписані за допомогою `GSS_Wrap()`.

### 5. Механізм OAUTHBEARER (RFC 7628)

Механізм `OAUTHBEARER` стандартизує передачу токенів доступу OAuth 2.0 (Bearer JWT) через єдиний кадр GS2.

```
oauthbearer-message = gs2-header oauth-payload
oauth-payload       = "host=" host %x01 "port=" port %x01 "auth=Bearer " access-token %x01 %x01
```

Символ `%x01` (`Ctrl+A` / ASCII 1) використовується як суворий внутрішній розділювач параметрів:

```
n,a=user@example.com,\x01host=mail.example.com\x01port=993\x01auth=Bearer eyJhbGciOiJSUzI1Ni...
```

Сервер перевіряє криптографічний підпис токена JWT за відкритим ключем провайдера ідентифікації (IdP / OpenID Connect), строк його дії (`exp`), цільову аудиторію (`aud`) та надані права (`scope`). Якщо токен протерміновано, сервер повертає JSON-структуру з деталями помилки: `{"status":"invalid_token", "scope":"mail", "schemes":"Bearer"}`.

## Специфікація обрамлення рівня безпеки (Security Layer Framing)

Якщо під час автентифікації було узгоджено рівень безпеки `auth-int` або `auth-conf`, усі подальші байти прикладного з'єднання інкапсулюються у спеціальні кадри безпеки SASL:

```
+-----------------------------------+-----------------------------------+
|  4 байти довжини (Big-Endian)     |  Захищений блок даних (N байтів) |
|  uint32 length = N                |  Шифротекст або відкритий + HMAC  |
+-----------------------------------+-----------------------------------+
```

1. **Префікс довжини:** Рівно 4 октети у мережевому порядку байтів (*Network Byte Order / Big-Endian*), що позначають довжину наступного криптографічного блоку `N` у байтах.
2. **Обмеження розміру:** Значення `N` не повинно перевищувати максимальний розмір буфера, узгоджений сторонами на етапі автентифікації.
3. **Обробка потоку:** Приймач зобов'язаний спочатку вичитати з сокета рівно 4 байти, декодувати довжину `N`, після чого вичитати `N` байтів і передати їх у функцію розгортання `sasl_decode()` (або `GSS_Unwrap()`). Отриманий відкритий потік передається парсеру прикладного протоколу.

## Протокольні профілі впровадження SASL

### 1. Протокол IMAP4rev1 (RFC 3501 / RFC 4959)

- **Оголошення:** Сервер повертає можливості у відповіді на команду `CAPABILITY`: `AUTH=PLAIN AUTH=SCRAM-SHA-256 AUTH=GSSAPI`. Підтримка початкової відповіді клієнта позначається прапорцем `SASL-IR`.
- **Запуск:** Клієнт надсилає команду: `a001 AUTHENTICATE SCRAM-SHA-256 [initial-response-base64]`.
- **Виклики:** Сервер повертає проміжні виклики у рядках зі знаком плюс: `+ <base64-challenge>`. Клієнт відповідає рядком `<base64-response>`.
- **Скасування:** Клієнт надсилає рядок з єдиним символом `*`. Сервер відхиляє команду: `a001 BAD Authentication aborted`.
- **Завершення:** Успіх позначається тегованим рядком: `a001 OK [CAPABILITY ...] Success`, помилка: `a001 NO Authentication failed`.

### 2. Протокол SMTP (RFC 4954)

- **Оголошення:** У відповіді на привітання `EHLO` сервер повертає рядок: `250-AUTH SCRAM-SHA-256 PLAIN GSSAPI`.
- **Запуск:** Клієнт надсилає команду: `AUTH SCRAM-SHA-256 [initial-response]`.
- **Виклики:** Сервер використовує тризначний числовий код стану `334`: `334 <base64-challenge>`.
- **Скасування:** Клієнт надсилає `*`, сервер відповідає `501 Authentication canceled`.
- **Завершення:** Успіх повертає код `235 2.7.0 Authentication successful`, помилка — `535 5.7.8 Authentication credentials invalid`.

### 3. Протокол LDAPv3 (RFC 4511 / RFC 4513)

У бінарному протоколі LDAP повідомлення кодуються за правилами ASN.1 BER (*Basic Encoding Rules*):

```
BindRequest ::= [APPLICATION 0] SEQUENCE {
    version        INTEGER (1..127),
    name           LDAPDN,
    authentication AuthenticationChoice
}

AuthenticationChoice ::= CHOICE {
    simple         [0] OCTET STRING,
    sasl           [3] SaslCredentials
}

SaslCredentials ::= SEQUENCE {
    mechanism      LDAPString,
    credentials    OCTET STRING OPTIONAL
}
```

Двійковий кадр `BindRequest` для вибору `SCRAM-SHA-256` розгортається у таку послідовність октетів:
- Байт `0x30` (SEQUENCE) + довжина всього повідомлення.
- Байт `0x02 0x01 0x03` (INTEGER: MessageID = 3).
- Байт `0x60` (APPLICATION 0: BindRequest) + довжина тіла запиту.
- Байт `0x02 0x01 0x03` (INTEGER: LDAP Version = 3).
- Байт `0x04 0x00` (OCTET STRING: Name = порожній DN для SASL).
- Байт `0xa3` (CONTEXT-SPECIFIC 3: SaslCredentials) + довжина структури.
  - Байт `0x04 0x0d` (OCTET STRING: mechanism = "SCRAM-SHA-256").
  - Байт `0x04` + довжина + бінарні байти `client-first-message`.

Сервер відповідає структурою `BindResponse` (тег `0x61` / APPLICATION 1) із кодом результату `resultCode = 14` (`saslBindInProgress`) та контекстним полем `serverSaslCreds` (тег `0x87` / CONTEXT-SPECIFIC 7), що містить байти серверного виклику. Завершення позначається кодом `resultCode = 0` (`success`) або `resultCode = 49` (`invalidCredentials`).

### 4. Розподілений брокер Apache Kafka (Kafka SASL Protocol)

У двійковому протоколі Kafka автентифікація виконується на самому початку TCP-сесії за допомогою двох послідовних бінарних запитів:

1. **`SaslHandshakeRequest` (API Key 17, Version 1):**
   - Двійкова структура запиту:
     - `int16 api_key` = 17
     - `int16 api_version` = 1
     - `int32 correlation_id` = 1
     - `string client_id` = "producer-node-1"
     - `string mechanism` = "SCRAM-SHA-256" (рядок із 2-байтовим префіксом довжини)
   - Відповідь брокера `SaslHandshakeResponse`:
     - `int16 error_code`: 0 (успіх), 33 (`UNSUPPORTED_SASL_MECHANISM`), 34 (`ILLEGAL_SASL_STATE`).
     - `array[string] enabled_mechanisms`: масив механізмів, підтримуваних брокером.
2. **`SaslAuthenticateRequest` (API Key 36, Version 1):**
   - Двійкова структура запиту:
     - `int16 api_key` = 36
     - `int16 api_version` = 1
     - `int32 correlation_id` = 2
     - `bytes auth_bytes`: сирий масив байтів SASL-виклику/відповіді (без текстового перекодування в Base64).
   - Відповідь брокера `SaslAuthenticateResponse`:
     - `int16 error_code`: 0 (успіх), 58 (`SASL_AUTHENTICATION_FAILED`).
     - `nullable_string error_message`: детальний текст діагностики від брокера.
     - `bytes auth_bytes`: байти серверного виклику або фінального підпису.
     - `int64 session_lifetime_ms`: залишковий час дії сесійного токена у мілісекундах.

### 5. Реляційна СКБД PostgreSQL (Frontend/Backend Protocol v3.0)

Протокол PostgreSQL оперує 1-байтовими символьними ідентифікаторами пакетів та 4-байтовими довжинами:

- **Пакет `AuthenticationSASL` від сервера:**
  - Байт `0x52` (символ `'R'`).
  - `Int32 length` = розмір усього пакета.
  - `Int32 code` = `10` (код `AUTH_REQ_SASL`).
  - Послідовність нуль-термінованих рядків підтримуваних механізмів, що завершується додатковим нульовим байтом: `"SCRAM-SHA-256\0\0"`.
- **Пакет `SASLInitialResponse` від клієнта:**
  - Байт `0x70` (символ `'p'`).
  - `Int32 length` = розмір пакета.
  - Нуль-термінований рядок механізму: `"SCRAM-SHA-256\0"`.
  - `Int32 data_len` = довжина початкових даних клієнта (або `-1`, якщо дані відсутні).
  - Масив байтів `client-first-message`.
- **Пакет `AuthenticationSASLContinue` від сервера:**
  - Байт `0x52` (`'R'`), `Int32 code` = `11` (`AUTH_REQ_SASL_CONT`), байти `server-first-message`.
- **Пакет `SASLResponse` від клієнта:**
  - Байт `0x70` (`'p'`), `Int32 length`, байти `client-final-message`.
- **Пакет `AuthenticationSASLFinal` від сервера:**
  - Байт `0x52` (`'R'`), `Int32 code` = `12` (`AUTH_REQ_SASL_FIN`), байти `server-final-message` (`v=...`).
- **Підтвердження:** Сервер надсилає пакет `AuthenticationOk` (код `Int32(0)`), після чого надсилає параметри сесії (`ReadyForQuery`).

### 6. Промисловий протокол AMQP 1.0 (ISO/IEC 19464)

У протоколі AMQP 1.0 процедура автентифікації виконується до відкриття основного транспортного сеансу:

1. **Заголовок протоколу SASL:** Клієнт надсилає 8-байтовий заголовок `AMQP\x03\x01\x00\x00` (де байт `0x03` означає SASL Security Profile). Сервер відповідає аналогічним 8-байтовим заголовком.
2. **Кадр `sasl-mechanisms` (дескриптор `0x00000000:0x00000040`):** Сервер надсилає масив символьних назв механізмів: `["ANONYMOUS", "PLAIN", "SCRAM-SHA-256"]`.
3. **Кадр `sasl-init` (дескриптор `0x00000000:0x00000041`):** Клієнт передає обраний механізм, початковий блок даних та ідентифікатор `hostname`.
4. **Кадри `sasl-challenge` (`0x42`) та `sasl-response` (`0x43`):** Здійснюють транспортування бінарних блоків виклику та відповіді.
5. **Кадр `sasl-outcome` (дескриптор `0x00000000:0x00000044`):** Сервер повідомляє результат:
   - `0`: `OK` — успішна автентифікація.
   - `1`: `AUTH` — помилка автентифікації (невірні облікові дані).
   - `2`: `SYS` — внутрішня системна помилка сервера.
   - `3`: `SYS_PERM` — постійна відмова в доступі для даного облікового запису.
   - `4`: `SYS_TEMP` — тимчасова відмова (перевантаження служби, спробуйте пізніше).

Після отримання статусу `0` (`OK`) обидві сторони скидають стан парсерів і відкривають основне з'єднання стандартним заголовком `AMQP\x00\x01\x00\x00`.

## Правила кодування Base64 та розбиття рядків

У текстових прикладних протоколах (IMAP, SMTP, POP3, XMPP) бінарні байти викликів та відповідей передаються через алфавіт Base64 (RFC 4648):

1. **Алфавіт кодування:** Символи `A-Z`, `a-z`, `0-9`, `+`, `/` із символом доповнення `=`.
2. **Заборона розриву рядків:** На відміну від MIME-передачі файлів (RFC 2045), де рядки Base64 розбиваються кожні 76 символів парою `CRLF`, у командах SASL протоколів IMAP та SMTP виклик або відповідь передається як **єдиний нерозривний рядок** без внутрішніх пробілів та переносів.
3. **Порожні виклики та відповіді:** Якщо механізм видає порожній блок даних (0 байтів), у командному рядку передається символ `=`, або порожній рядок залежно від синтаксису прикладного протоколу (наприклад, `+ ` в IMAP або `334 ` в SMTP).
4. **Максимальна довжина рядка:** Протокол SMTP (RFC 5321) обмежує максимальну довжину командного рядка 512 символами, але для команд `AUTH` з великими токенами Kerberos або OAuth 2.0 сервер зобов'язаний підтримувати рядки довжиною не менше 12288 байтів.
