# 📋 Специфікація протоколу SCRAM: повідомлення, атрибути та прив'язка до каналу

Цей довідник містить повну технічну специфікацію протоколу SCRAM (*Salted Challenge Response Authentication Mechanism*) відповідно до стандартів RFC 5802, RFC 7677 та RFC 5929. У ньому наведено синтаксичні правила форматування повідомлень, опис усіх атрибутів, граматику заголовка GS2, механізм прив'язки до каналу TLS, перелік стандартних помилок сервера, вимоги до нормалізації рядків, структуру зберігання в базах даних, правила обробки крайових випадків та особливості інтеграції в протоколи прикладного рівня.

Довідник призначений для розробників клієнтських і серверних бібліотек, системних інженерів та аудиторів безпеки, які реалізують або інтегрують механізм SCRAM у протоколи прикладного рівня (SASL, GSS-API, PostgreSQL, MongoDB, XMPP, Kafka).

## 1. Реєстр механізмів SASL

Протокол SCRAM зареєстровано в реєстрі IANA SASL Mechanisms під кількома офіційними назвами залежно від базової криптографічної геш-функції та підтримки прив'язки до каналу TLS:

| Назва механізму SASL | Базова геш-функція `H` | Довжина виходу гешу (байти) | Прив'язка до каналу (*Channel Binding*) | Стандарт RFC |
| :--- | :--- | :--- | :--- | :--- |
| `SCRAM-SHA-1` | SHA-1 | 20 | Ні | RFC 5802 |
| `SCRAM-SHA-1-PLUS` | SHA-1 | 20 | Так (обов'язково) | RFC 5802 |
| `SCRAM-SHA-256` | SHA-256 | 32 | Ні | RFC 7677 |
| `SCRAM-SHA-256-PLUS` | SHA-256 | 32 | Так (обов'язково) | RFC 7677 |
| `SCRAM-SHA-512-PLUS` | SHA-512 | 64 | Так (обов'язково) | RFC 5802 / Draft |

Механізми з суфіксом `-PLUS` вимагають обов'язкового передавання даних прив'язки до каналу TLS у заголовку GS2. Якщо сервер або клієнт підтримують прив'язку до каналу, але обмін відбувається без суфікса `-PLUS`, протокол передбачає механізм виявлення спроб примусового зниження безпеки (*downgrade attack*).

## 2. Формат та граматика повідомлень

Повідомлення SCRAM передаються у вигляді текстових рядків у кодуванні UTF-8, що складаються з пар `атрибут=значення`, розділених комами `,`. На відміну від протоколів на зразок HTTP Digest або SIP, у SCRAM відсутні подвійні лапки навколо значень та пробіли між елементами.

### Правила екранування символів

У полях, де дозволено довільний текст (зокрема ім'я користувача `n=` та ідентифікатор авторизації `a=`), символи коми та знака рівності підлягають обов'язковому екрануванню:

- Символ коми `,` кодується послідовністю `=2C` (або `=2c`);
- Символ рівності `=` кодується послідовністю `=3D` (або `=3d`).

Будь-яка інша поява знака `=` безпосередньо після знака `=` (наприклад, `=XX`, де `XX` не є `2C` чи `3D`) вважається синтаксичною помилкою кодування `invalid-encoding`. Символ відкритого знака `=` використовується виключно як роздільник між ім'ям атрибута та його значенням або у фінальному вирівнюванні Base64.

### Формальна ABNF-граматика

Синтаксис повідомлень описується розширеною формою Бекуса-Наура (ABNF, RFC 5234):

```
scram-message       = (client-first-message /
                       server-first-message /
                       client-final-message /
                       server-final-message)

client-first-message = gs2-header client-first-message-bare

client-first-message-bare = [reserved-mext ","]
                            username "," nonce ["," extensions]

server-first-message = [reserved-mext ","]
                       nonce "," salt "," iteration-count ["," extensions]

client-final-message = channel-binding "," nonce ["," extensions]
                       "," proof

server-final-message = (server-error / server-verifier) ["," extensions]

gs2-header          = gs2-cb-flag "," [authzid] ","
gs2-cb-flag         = "p=" cb-name / "n" / "y"
authzid             = "a=" saslname
username            = "n=" saslname
nonce               = "r=" printable-ascii-string
salt                = "s=" base64-string
iteration-count     = "i=" 1*DIGIT
channel-binding     = "c=" base64-string
proof               = "p=" base64-string
server-verifier     = "v=" base64-string
server-error        = "e=" error-code
reserved-mext       = "m=" 1*(ALPHA / DIGIT / "." / "-")
```

## 3. Чотири повідомлення обміну

Повний цикл автентифікації SCRAM складається з двох послідовних обертів (чотирьох повідомлень).

### 3.1. Перше повідомлення клієнта: `client-first-message`

Повідомлення формується клієнтом для ініціалізації сесії автентифікації:

```
n,,n=user,r=fyko+d2lwyECACBYghMXFGW3
```

Складові частини повідомлення:
1. `gs2-header` (заголовок GS2): префікс `n,,`, де `n` позначає відсутність прив'язки до каналу, а порожнє поле між комами означає відсутність окремого `authzid`.
2. `client-first-message-bare`: тіло повідомлення, що містить ім'я користувача `n=user` та клієнтський одноразовий рядок `r=fyko+d2lwyECACBYghMXFGW3`.

Якщо клієнт використовує авторизацію від імені іншого облікового запису (проксі-авторизація `authzid`), заголовок набуває вигляду:
`n,a=admin,n=user,r=fyko+d2lwyECACBYghMXFGW3`.

### 3.2. Перше повідомлення сервера: `server-first-message`

Сервер видобуває зі своєї бази даних обліковий запис користувача, генерує випадкове доповнення до одноразового рядка і надсилає параметри обчислення:

```
r=fyko+d2lwyECACBYghMXFGW3B96duGRZSbNHH3ftuGJqtryh,s=QSXCR+Q6sek8bf92,i=4096
```

Складові частини повідомлення:
1. `r=...` (об'єднаний `nonce`): повний рядок, який починається з клієнтського одноразового числа і доповнюється випадковими даними сервера.
2. `s=...` (сіль `salt`): випадкова криптографічна сіль користувача, закодована в Base64.
3. `i=...` (лічильник ітерацій `iteration-count`): десяткове ціле число (мінімум 4096 для SHA-256), що визначає складність розтягування ключа в алгоритмі PBKDF2.

### 3.3. Фінальне повідомлення клієнта: `client-final-message`

Клієнт обчислює криптографічні ключі через `PBKDF2`, формує рядок авторизаційного повідомлення `AuthMessage` і надсилає доказ знання секрету:

```
c=biws,r=fyko+d2lwyECACBYghMXFGW3B96duGRZSbNHH3ftuGJqtryh,p=v0X8v3Bz2T0CJGbJQII0GeKPxjw=
```

Складові частини повідомлення:
1. `c=...` (дані прив'язки до каналу `channel-binding`): закодований у Base64 заголовок `gs2-header` разом із криптографічним матеріалом TLS (для `n,,` кодується базовий рядок `n,,`, що в Base64 дає `biws`).
2. `r=...` (об'єднаний `nonce`): той самий повний рядок, отриманий від сервера.
3. `p=...` (клієнтський доказ `proof`): результат бітового виключного АБО `ClientKey ⊕ ClientSignature`, закодований у Base64.

### 3.4. Фінальне повідомлення сервера: `server-final-message`

Сервер знімає маску з отриманого доказу `p=...`, перевіряє справжність клієнта і у разі успіху надсилає власний підпис для взаємної автентифікації:

```
v=rmF9pqV8S7suAoZWja4TGst0VaE=
```

Поле `v=...` містить `ServerSignature = HMAC(ServerKey, AuthMessage)`, закодований у Base64. Якщо перевірка клієнта провалилася, сервер повертає повідомлення про помилку:

```
e=invalid-proof
```

## 4. Словник атрибутів протоколу

Усі атрибути протоколу ідентифікуються однією латинською літерою:

| Атрибут | Назва | Де з'являється | Опис та формат значення |
| :--- | :--- | :--- | :--- |
| `n` | `username` | `client-first` | Ім'я користувача (UTF-8 рядок після нормалізації SASLprep). Символи `,` та `=` екрануються як `=2C` та `=3D`. |
| `a` | `authzid` | `gs2-header` | Необов'язковий ідентифікатор авторизації (для виконання дій від імені іншого акаунта). |
| `r` | `nonce` | `client-first`, `server-first`, `client-final` | Одноразовий псевдовипадковий рядок із символів ASCII (за винятком коми). |
| `s` | `salt` | `server-first` | Сіль користувача у форматі Base64. Рекомендована довжина — не менше 16 байтів випадкових даних. |
| `i` | `iteration-count` | `server-first` | Позитивне десяткове ціле число — кількість раундів у PBKDF2 (наприклад, `4096`). |
| `c` | `channel-binding` | `client-final` | Base64-представлення заголовка GS2 та даних прив'язки до каналу TLS. |
| `p` | `proof` | `client-final` | Клієнтський доказ `ClientProof = ClientKey ⊕ ClientSignature` у форматі Base64. |
| `v` | `verifier` | `server-final` | Підпис сервера `ServerSignature` у форматі Base64 для взаємної автентифікації. |
| `e` | `error` | `server-final` | Текстовий код помилки автентифікації (якщо автентифікація зазнала невдачі). |
| `m` | `mandatory-extension`| будь-яке повідомлення | Обов'язкове розширення протоколу. Якщо сторона не знає розширення, з'єднання скидається. |

## 5. Заголовок GS2 та прив'язка до каналу (Channel Binding)

Специфікація GS2 (RFC 5801) стандартизує спосіб підключення механізмів SASL до захищеного транспорту. Заголовок `gs2-header` визначає статус прив'язки до каналу TLS за допомогою прапорця `gs2-cb-flag`:

| Прапорець | Значення | Опис |
| :--- | :--- | :--- |
| `n` | Клієнт не підтримує прив'язку | Клієнт підключається без прив'язки до каналу і знає, що сервер не вимагає суфікса `-PLUS`. |
| `y` | Клієнт підтримує, але сервер не вміє | Клієнт підтримує прив'язку до каналу, але вибрав механізм без `-PLUS`, бо сервер не оголосив підтримку. Сервер перевіряє цей прапорець: якщо сервер насправді підтримує `-PLUS`, він скидає з'єднання з помилкою `server-does-support-channel-binding` (захист від MitM-downgrade). |
| `p=cb-name` | Клієнт використовує прив'язку | Клієнт використовує механізм `-PLUS` і вказує тип прив'язки `cb-name` (наприклад, `p=tls-server-end-point`). |

### Формування значення атрибута `c=`

Атрибут `c=` у повідомленні `client-final-message` містить Base64-код рядка, який складається з повного `gs2-header` та бінарних даних прив'язки каналу:

```
c-value = Base64( gs2-header [ ‖ channel-binding-data ] )
```

Типи прив'язок до каналу (RFC 5929):
- `tls-server-end-point`: даними прив'язки є криптографічний геш SHA-256 сертифіката сервера TLS у бінарному форматі DER. Якщо сертифікат використовує геш-функцію з сімейства SHA-2 з довжиною виходу більше 256 біт (наприклад, SHA-384 чи SHA-512), використовується відповідна геш-функція сертифіката.
- `tls-unique`: даними прив'язки є байти поля *TLS Finished* першого успішного рукостискання TLS з'єднання.

## 6. Стандартні коди помилок сервера

Якщо автентифікація не може бути завершена, сервер повертає `server-final-message` з атрибутом `e=код-помилки`. Стандарт RFC 5802 визначає такий фіксований набір кодів помилок:

| Код помилки | Семантичне значення |
| :--- | :--- |
| `invalid-encoding` | Повідомлення містить неприпустимі символи, некоректні послідовності UTF-8 або помилкове екранування знаків `=` чи `,`. |
| `extensions-not-supported` | Повідомлення містить обов'язковий атрибут розширення `m=...`, який не підтримується даною реалізацією сервера. |
| `invalid-proof` | Наданий клієнтом `ClientProof` є недійсним: після зняття маски перевірка `H(ClientKey') == StoredKey` не пройшла (невірний пароль користувача). |
| `channel-bindings-dont-match` | Дані прив'язки до каналу TLS, обчислені сервером, не збігаються зі значенням, переданим клієнтом у полі `c=...` (виявлено перехоплення або MitM-проксі). |
| `server-does-support-channel-binding` | Клієнт надіслав прапорець `y` (вважаючи, що сервер не вміє channel binding), але сервер насправді підтримує механізм `-PLUS` (виявлено атаку примусового зниження безпеки). |
| `channel-binding-not-supported` | Клієнт запросив тип прив'язки `p=cb-name`, який не підтримується сервером. |
| `unknown-user` | Користувача з вказаним ім'ям `n=...` не знайдено в базі даних сервера. Сервери можуть імітувати випадкову сіль для запобігання витоку інформації про існування користувачів. |
| `invalid-username-encoding` | Рядок імені користувача не пройшов валідацію або нормалізацію за алгоритмом SASLprep. |
| `no-resources` | Сервер не має достатніх обчислювальних ресурсів для виконання операцій гешування або обслуговування сесії. |
| `other-error` | Будь-яка інша внутрішня помилка виконання сервера. |

## 7. Нормалізація рядків: SASLprep

Для запобігання ситуаціям, коли пароль або ім'я користувача, введені на різних операційних системах, дають різні байти в UTF-8 через різницю у представленні символів Юнікоду, стандарт вимагає застосування профілю **SASLprep** (RFC 4013 на основі Stringprep RFC 3454).

Алгоритм обробки рядка:
1. **Відображення (*Mapping*):** 
   - Нерозривні пробіли (U+00A0, U+2000..U+200B) замінюються на стандартний пробіл ASCII (U+0020).
   - «М'які» дефіси та невидимі символи відкидаються (відображаються у порожній рядок).
2. **Нормалізація (*Normalization*):**
   - Застосовується канонічна сумісна нормалізація Юнікоду **NFKC** (*Normalization Form KC*). Це об'єднує композиційні символи з діакритичними знаками в єдині кодові позиції.
3. **Перевірка заборонених символів (*Prohibited Output*):**
   - Перевіряється відсутність символів керування ASCII (U+0000..U+001F, U+007F..U+009F), приватних областей користувача (*Private Use* U+E000..U+F8FF) та неприпустимих сурогатних пар.
4. **Перевірка бідирекційного тексту (*Bidirectional Characters*):**
   - Якщо рядок містить символи з напрямком письма справа наліво (RTL, наприклад арабські або іврит), перший і останній символи рядка обов'язково повинні мати категорію RTL.

## 8. Вимоги безпеки до одноразових чисел (Nonce)

Клієнтський і серверний одноразові рядки `nonce` повинні відповідати жорстким критеріям криптографічної безпеки:
- Генерація має здійснюватися виключно за допомогою криптографічно стійкого генератора псевдовипадкових чисел (CSPRNG).
- Мінімальна довжина клієнтського одноразового числа повинна складати не менше 64 бітів ентропії (рекомендовано від 16 до 32 друкованих символів Base64 або шістнадцяткових значень).
- Сервер зобов'язаний згенерувати власне доповнення до рядка довжиною не менше 64 бітів і повернути об'єднане значення `r_client + r_server`.
- Клієнт зобов'язаний перевірити, що значення `r=...` у повідомленні `server-first-message` починається з точного префікса, згенерованого ним у `client-first-message`. Якщо префікс не збігається, клієнт повинен негайно перервати з'єднання без виконання обчислень PBKDF2.

## 9. Формат зберігання облікових записів у базах даних

Сервер SCRAM не зберігає ані відкритого пароля, ані значення `SaltedPassword`, ані `ClientKey`. У базі даних користувачів зберігаються виключно такі поля:

| Поле бази даних | Тип даних | Призначення | Приклад значення у PostgreSQL `pg_authid` |
| :--- | :--- | :--- | :--- |
| `username` | Текстовий рядок | Ім'я облікового запису користувача | `alice` |
| `salt` | Двійковий масив / Base64 | Унікальна псевдовипадкова сіль (16+ байтів) | `QSXCR+Q6sek8bf92` |
| `iterations` | Ціле число | Кількість раундів PBKDF2 | `4096` |
| `stored_key` | Двійковий масив / Base64 | Геш `StoredKey = SHA256(ClientKey)` | `L57e937e...` |
| `server_key` | Двійковий масив / Base64 | Ключ `ServerKey = HMAC(SaltedPassword, "Server Key")` | `m9F4...` |

У системному каталозі PostgreSQL (`pg_authid.rolpassword`) цей запис формується у вигляді єдиного компактного рядка:

```
SCRAM-SHA-256$4096:QSXCR+Q6sek8bf92$L57e...=$m9F4...=
```

Такий формат дозволяє серверу миттєво зчитати всі параметри виклику при отриманні `client-first-message` без жодної необхідності зворотного дешифрування чи доступу до відкритих секретів.

## 10. Інтеграція SCRAM у прикладні протоколи

SCRAM інтегрується у фреймворк SASL як універсальний механізм. Нижче наведено приклади пакування повідомлень у конкретних протоколах.

### Інтеграція у PostgreSQL (Frontend/Backend Protocol v3.0)

У протоколі PostgreSQL обмін SCRAM вбудовується у фазу встановлення сесії:

```
Клієнт -> Сервер: StartupMessage (user="alice", database="production")
Сервер -> Клієнт: AuthenticationSASL ('SCRAM-SHA-256', '\0')
Клієнт -> Сервер: SASLInitialResponse ('SCRAM-SHA-256', n,,n=alice,r=fyko+...)
Сервер -> Клієнт: AuthenticationSASLContinue (r=fyko+...B96d...,s=QSXC...,i=4096)
Клієнт -> Сервер: SASLResponse (c=biws,r=fyko+...B96d...,p=v0X8...)
Сервер -> Клієнт: AuthenticationSASLFinal (v=rmF9pqV8S7suAoZWja4TGst0VaE=)
Сервер -> Клієнт: AuthenticationOk
```

### Інтеграція у XMPP (RFC 6120)

У протоколі XMPP повідомлення SCRAM пакуються в XML-елементи простору імен `urn:ietf:params:xml:ns:xmpp-sasl`:

```xml
<!-- 1. Клієнт ініціює автентифікацію -->
<auth xmlns='urn:ietf:params:xml:ns:xmpp-sasl' mechanism='SCRAM-SHA-256'>
  biwsbj1hbGljZSxyPWZ5a28rZDJsd3lFQ0FDQllnaE1YRkdXMw==
</auth>

<!-- 2. Сервер повертає виклик, сіль та ітерації (Base64) -->
<challenge xmlns='urn:ietf:params:xml:ns:xmpp-sasl'>
  cj1meWtvK2QybHd5RUNBQ0JZZ2hNWEZHVzNCOTZkdUdSWlNiTkhIM2Z0dUdKcXRyeWgscz1RU1hDUitRNnNlazhiZjkyLGk9NDA5Ng==
</challenge>

<!-- 3. Клієнт надсилає доказ ClientProof (Base64) -->
<response xmlns='urn:ietf:params:xml:ns:xmpp-sasl'>
  Yz1iaXdzLHI9ZnlrbytkMmx3eUVDQUNCWWdoTVhGR1czQjk2ZHVHUlpTYk5ISDNmdHVHSnF0cnloLHA9djBYOHYzQnoyVDBDSkdiSlFJSTBHZUtQeGp3PQ==
</response>

<!-- 4. Сервер підтверджує взаємну автентифікацію -->
<success xmlns='urn:ietf:params:xml:ns:xmpp-sasl'>
  dj1ybUY5cHFWOFM3c3VBb1pXamE0VEdzdDBWYUU9
</success>
```

### Інтеграція в SMTP та IMAP (SASL Command Flow)

У поштових протоколах SMTP (RFC 4954) та IMAP (RFC 3501) повідомлення передаються у командах `AUTH` та `AUTHENTICATE`:

```
C: AUTH SCRAM-SHA-256
S: 334 (готовий прийняти перший кадр)
C: biwsbj1hbGljZSxyPWZ5a28r... (Base64 client-first)
S: 334 cj1meWtvK2QybHd5... (Base64 server-first)
C: Yz1iaXdzLHI9Znlrbytk... (Base64 client-final)
S: 235 2.7.0 dj1ybUY5cHFWO... (Base64 server-final / успіх)
```

## 11. Модель станів (State Machine) клієнта і сервера

Для запобігання атакам із повторенням повідомлень та збоям синхронізації обидві сторони реалізують суворі скінченні автомати станів.

### Стани клієнта:
1. `INITIAL`: згенерувати клієнтський `nonce`, створити `client-first-message-bare`, надіслати `client-first-message`, перейти в `WAIT_SERVER_FIRST`.
2. `WAIT_SERVER_FIRST`: отримати `server-first-message`, перевірити префікс `nonce`, видобути `s` та `i`. Обчислити `PBKDF2`, `ClientKey`, `StoredKey`, `ServerKey`, зібрати `AuthMessage`, обчислити `ClientProof`, надіслати `client-final-message`, перейти в `WAIT_SERVER_FINAL`.
3. `WAIT_SERVER_FINAL`: отримати `server-final-message`. Якщо містить `e=`, скинути автентифікацію з помилкою. Якщо містить `v=`, перевірити `v == HMAC(ServerKey, AuthMessage)`. Якщо збіглося — перейти в стан `AUTHENTICATED`, інакше — зафіксувати спробу зламу та негайно скинути з'єднання.

### Стани сервера:
1. `WAIT_CLIENT_FIRST`: отримати `client-first-message`. Розібрати заголовок GS2, видобути ім'я користувача та клієнтський `nonce`. Знайти обліковий запис у базі даних. Згенерувати серверне доповнення `nonce`, сформувати `server-first-message`, перейти в `WAIT_CLIENT_FINAL`.
2. `WAIT_CLIENT_FINAL`: отримати `client-final-message`. Перевірити збіг `nonce` та даних прив'язки до каналу в `c=`. Зібрати `AuthMessage`, зняти XOR-маску з доказу `p=`: `ClientKey' = ClientProof ⊕ HMAC(StoredKey, AuthMessage)`. Перевірити рівність `H(ClientKey') == StoredKey`. У разі успіху надіслати `v=HMAC(ServerKey, AuthMessage)` і перейти в стан `AUTHENTICATED`. У разі невдачі надіслати `e=invalid-proof` і скинути сесію.

## 12. Безпека реалізації та захист пам'яті

Розробники бібліотек SCRAM зобов'язані дотримуватися таких практик захисту:

1. **Порівняння за сталий час (*Constant-Time Comparison*):**
   Порівняння обчисленого `StoredKey` з еталоном бази даних, а також перевірка підпису `ServerSignature` на клієнті повинні виконуватися виключно функціями зі сталим часом виконання (наприклад, `CRYPTO_memcmp()` в OpenSSL або `timingsafe_bcmp()`). Звичайний `memcmp()` перериває порівняння на першому неспівпалому байті, що створює канал витоку інформації через вимірювання затримок відповіді (*timing side-channel attack*).

2. **Очищення конфіденційної пам'яті (*Secure Memory Erasing*):**
   Буфери, які містили `Password`, `SaltedPassword` та `ClientKey`, повинні затиратися нулями одразу після завершення криптографічних перетворень за допомогою функцій `explicit_bzero()` або `OPENSSL_cleanse()`. Звичайний `memset()` може бути оптимізований і видалений компілятором як «мертвий код» (*dead store elimination*).

3. **Захист від переліку користувачів (*User Enumeration Mitigation*):**
   Якщо клієнт запитує неіснуюче ім'я користувача `n=unknown`, сервер не повинен миттєво повертати помилку `e=unknown-user` або скидати з'єднання. Натомість сервер генерує фіктивну сіль `fake_salt = HMAC(server_secret, username)` і повертає коректний `server-first-message`. Після отримання `client-final-message` сервер повертає `e=invalid-proof`. Це зрівнює час обробки запитів для існуючих і неіснуючих акаунтів, унеможливлюючи сканування бази логінів нападником.

## 13. Еталонний тестовий вектор (RFC 7677)

Для перевірки коректності реалізації парсерів та криптографічного конвеєра стандарт RFC 7677 наводить такі еталонні значення для механізму `SCRAM-SHA-256`:

- **Ім'я користувача (`username`):** `user`
- **Пароль (`password`):** `pencil`
- **Клієнтський `nonce`:** `r=fyko+d2lwyECACBYghMXFGW3`
- **Серверний `nonce`:** `r=fyko+d2lwyECACBYghMXFGW3B96duGRZSbNHH3ftuGJqtryh`
- **Сіль (`salt` Base64):** `s=QSXCR+Q6sek8bf92` (бінарно 12 байтів: `4125c247e43ab1e93c6dfd76`)
- **Ітерації (`i`):** `4096`

Проміжні криптографічні значення:
- `SaltedPassword` (32 байти): `2455853b0...`
- `ClientKey` (32 байти): `HMAC(SaltedPassword, "Client Key")`
- `StoredKey` (32 байти): `SHA256(ClientKey)`
- `ServerKey` (32 байти): `HMAC(SaltedPassword, "Server Key")`
- `AuthMessage`:
  `n=user,r=fyko+d2lwyECACBYghMXFGW3,r=fyko+d2lwyECACBYghMXFGW3B96duGRZSbNHH3ftuGJqtryh,s=QSXCR+Q6sek8bf92,i=4096,c=biws,r=fyko+d2lwyECACBYghMXFGW3B96duGRZSbNHH3ftuGJqtryh`
- `ClientSignature`: `HMAC(StoredKey, AuthMessage)`
- `ClientProof` (Base64): `p=v0X8v3Bz2T0CJGbJQII0GeKPxjw=`
- `ServerSignature` (Base64): `v=rmF9pqV8S7suAoZWja4TGst0VaE=`

## 14. Обробка крайових випадків у парсерах

Надійна реалізація парсера повідомлень SCRAM повинна враховувати такі крайові сценарії:

1. **Невідомі атрибути розширення:** Якщо повідомлення містить атрибут, не описаний у стандарті (наприклад, `x=value`), і перед ним немає обов'язкового прапорця `m=x`, парсер зобов'язаний проігнорувати цей атрибут без помилки. Це забезпечує зворотну сумісність при розширенні протоколу в майбутньому.
2. **Обов'язкові розширення `m=`:** Якщо в повідомленні присутній атрибут `m=name`, а реалізація не підтримує розширення з іменем `name`, обмін негайно скидається з помилкою `extensions-not-supported`.
3. **Порядок атрибутів:** Атрибути у повідомленнях мають суворий позиційний порядок згідно з ABNF-граматикою. Повідомлення, у якому порядок порушено (наприклад, `r=...,n=...` замість `n=...,r=...` у `client-first`), має відхилятися з помилкою `invalid-encoding`.
4. **Зайві пробіли та порожні поля:** Поява неіменованих пробілів навколо ком чи знаків `=` є порушенням граматики. Додаткові коми без атрибутів (окрім передбачених структурою `gs2-header` `n,,`) також спричиняють помилку парсингу.

## 15. Продуктивність та оптимізація обчислень

Основним обчислювальним навантаженням у протоколі SCRAM є виконання функції розтягування ключів `PBKDF2`. Оскільки `PBKDF2` виконується виключно на стороні клієнта (сервер отримує вже розраховані значення `StoredKey` та `ServerKey` з бази даних), архітектура SCRAM має високу масштабованість.

Серверне навантаження на один сеанс автентифікації обмежується лише трьома швидкими криптографічними операціями:
1. `ClientSignature = HMAC-SHA-256(StoredKey, AuthMessage)`
2. `H(ClientKey') = SHA-256(ClientProof ⊕ ClientSignature)`
3. `ServerSignature = HMAC-SHA-256(ServerKey, AuthMessage)`

Ці операції не містять важких циклів і можуть виконуватися десятками тисяч разів на секунду на одному ядрі сучасного процесора з апаратною підтримкою інструкцій Intel SHA Extensions або ARMv8 Crypto. Клієнтські ж додатки можуть використовувати векторизацію SIMD (AVX2/AVX-512) для прискорення обчислень `PBKDF2` при багаторазовому встановленні паралельних з'єднань.
