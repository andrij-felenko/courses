Цей довідник містить точні специфікації двох фундаментальних стиків у системі доставки DRM-ключів: стандартизованого JavaScript-інтерфейсу W3C Encrypted Media Extensions (EME) та двійкової структури контейнерного боксу `pssh` (Protection System Specific Header) за стандартом ISO/IEC 23001-7. Без знання цих структур неможливо реалізувати власний медіаплеєр або сервер пакування й ліцензування.

## 1. Специфікація контейнерного боксу `pssh`

Бокс `pssh` розміщується в ініціалізаційному сегменті ISO BMFF (всередині боксу `moov`) або безпосередньо перед фрагментом медіа (всередині боксу `moof`). Він передає модулю розшифрування (CDM) параметри, необхідні для формування запиту ліцензії.

Коли пакувальник мультимедіа шифрує аудіо- або відеопотік, він генерує 128-бітний ідентифікатор ключа контенту (`KID`). Цей ідентифікатор записується в заголовок `tenc` (Track Encryption Box). Проте сам по собі `KID` не містить інформації про те, до якого саме сервера ліцензій має звернутися пристрій, які криптографічні протоколи підтримуються та які внутрішні службові дані потрібні серверу ліцензій для ідентифікації контенту. Саме для передачі цієї специфічної інформації стандарт ISO/IEC 23001-7 визначає бокс `pssh`.

### Двійкова структура заголовка (ISO/IEC 23001-7 §8.1)

```
+-----------------------------------+-----------------------------------+
| Поле                              | Розмір і тип                      |
+-----------------------------------+-----------------------------------+
| Size                              | 32-бітний uint (розмір боксу)     |
| Type                              | 4 байти FourCC: 'pssh' (0x70737368)|
| Version                           | 8-бітний uint (0x00 або 0x01)     |
| Flags                             | 24-бітний uint (завжди 0x000000)  |
| SystemID                          | 16 байтів (UUID системи захисту)  |
| [Тільки Version 1] KID_count      | 32-бітний uint (кількість KID)    |
| [Тільки Version 1] KID[KID_count] | 16 байтів * KID_count (список KID)|
| DataSize                          | 32-бітний uint (розмір Data)      |
| Data                              | DataSize байтів (opaque payload)  |
+-----------------------------------+-----------------------------------+
```

### Призначення полів та відмінності версій

1. **`Size` (32 біти, big-endian)**: Загальний розмір боксу в байтах, включно із заголовком. Якщо бокс пошкоджено або розмір не відповідає фактичній довжині корисного навантаження, демультиплексор ігнорує весь блок.
2. **`Type` (4 байти)**: Чотирисимвольний код FourCC, що дорівнює `0x70737368` (ASCII-символи `'pssh'`).
3. **`Version` (8 бітів)**:
   - `0x00` (Версія 0): Застаріла версія стандарту 2012 року. У ній список `KID` не винесено в окремий стандартизований заголовок; ідентифікатори ключів заховані всередині непрозорого поля `Data`. Через це клієнтський демультиплексор не може дізнатися, які саме ключі описані в цьому боксі, не розпарсивши пропрієтарний формат виробника DRM.
   - `0x01` (Версія 1): Сучасна версія стандарту (з 2016 року). Додає явний 32-бітний лічильник `KID_count` та фіксований масив 16-байтових ідентифікаторів `KID`. Це дозволяє браузеру або програвачу зіставити вміст боксу `pssh` із записами в заголовку `tenc` без залучення модуля CDM.
4. **`Flags` (24 біти)**: Зарезервовано стандартом. Мусить дорівнювати нулю (`0x000000`).
5. **`SystemID` (16 байтів / 128 бітів)**: Унікальний двійковий ідентифікатор (UUID) DRM-системи, якій адресовано цей блок. Демультиплексор порівнює `SystemID` із переліком систем, підтримуваних браузером. Якщо у файлі присутні кілька боксів `pssh` для різних систем, клієнт відфільтровує лише той, який відповідає активованому CDM.
6. **`DataSize` (32 біти)**: Довжина поля `Data` у байтах.
7. **`Data` (`DataSize` байтів)**: Довільне двійкове корисне навантаження, структуру якого розуміє лише цільовий модуль CDM та відповідний сервер ліцензій.

Кожна система захисту реєструє власний 128-бітний UUID. Демультиплексор порівнює `SystemID` із боксу з підтримуваними модулями CDM:

| **Microsoft PlayReady** | `9a04f079-9840-4286-ab92-e65be0885f95` | `urn:uuid:9a04f079-9840-4286-ab92-e65be0885f95` |

## 2. Формати корисного навантаження (`Data`) у PSSH

Поле `Data` є непрозорим для стандарту ISO/IEC 23001-7, але має чітку внутрішню структуру для кожної конкретної DRM-системи.

### 2.1. Widevine PSSH Data (Protocol Buffers)

Google Widevine пакує корисне навантаження боксу у форматі Protocol Buffers v2:

```protobuf
message WidevineCencHeader {
  enum Algorithm {
    UNENCRYPTED = 0;
    AESCTR = 1;
  }
  optional Algorithm algorithm = 1;
  repeated bytes key_id = 2;              // 16-байтові ідентифікатори ключів
  optional string provider = 3;            // Ідентифікатор контент-провайдера
  optional bytes content_id = 4;           // Унікальний ID фільму / епізоду
  optional string policy = 5;              // Назва бізнес-політики (опціонально)
  optional uint32 crypto_period_index = 6; // Номер періоду ротації ключів
  optional bytes grouped_license = 7;      // Контейнер групової ліцензії
  optional uint32 protection_scheme = 8;   // FourCC схеми: 'cenc' або 'cbcs'
}
```

У разі використання Widevine поле `provider` дозволяє серверу ліцензій визначити клієнта або дистриб'ютора контенту в системі Multi-Tenant (коли один DRM-сервер обслуговує кілька різних онлайн-кінотеатрів). Поле `content_id` пов'язує потік із внутрішнім каталогом фільмів, а `crypto_period_index` використовується під час трансляцій наживо для синхронізації періодів зміни ключів (Key Rotation).

### 2.2. PlayReady PSSH Data (WRMHEADER XML)

Microsoft PlayReady записує в поле `Data` структуру `PlayReady Header Object` (PRO), яка містить один або кілька записів заголовка `WRMHEADER` у кодуванні UTF-16LE:

```xml
<WRMHEADER xmlns="http://schemas.microsoft.com/DRM/2007/03/PlayReadyHeader" version="4.3.0.0">
  <DATA>
    <PROTECTINFO>
      <KID ALGID="AESCTR" CHECKSUM="base64==" VALUE="base64-guid=="></KID>
    </PROTECTINFO>
    <LA_URL>https://license.example.com/playready/rightsmanager.asmx</LA_URL>
    <LUI_URL>https://license.example.com/playready/ui.html</LUI_URL>
    <DS_ID>base64-domain-service-id==</DS_ID>
    <DECRYPTORSETUP>ONDEMAND</DECRYPTORSETUP>
  </DATA>
</WRMHEADER>
```

Особливістю PlayReady є наявність тегу `LA_URL` (License Acquisition URL) безпосередньо всередині PSSH-метаданих. Якщо вебзастосунок не перевизначає адресу сервера ліцензій у JavaScript, модуль PlayReady CDM може автоматично використати URL, зашитий у медіаконтейнер. Поле `CHECKSUM` використовується для швидкої валідації правильності згенерованого ключа перед початком повноцінного декодування потоку.

### 2.3. FairPlay PSSH Data

У специфікаціях HLS та fMP4 Apple FairPlay Streaming (FPS) передає ініціалізаційні дані або у формі тегу `#EXT-X-KEY` у маніфесті, або через бокс `pssh`. Структура `Data` містить:
1. `ContentID` (UTF-8 рядок або двійковий ідентифікатор активу, що починається з префіксу `skd://`).
2. `KeySystemID` (ідентифікатор провайдера ключів).
3. Сертифікат застосунку (Application Secret Key / Application Certificate), який використовується клієнтом для зашифрування початкового запиту SPC (Server Playback Context).

## 3. Об'єктна модель W3C EME API

EME розширює стандартні можливості HTML5-елемента `<video>` (`HTMLMediaElement`) та надає низькорівневий асинхронний інтерфейс для управління сесіями дешифрування. EME не виконує дешифрування самостійно; інтерфейс є стандартизованим конвеєром обміну повідомленнями між прикладним кодом мовою JavaScript та модулем Content Decryption Module (CDM).

```
+-------------------------------------------------------------------------+
| navigator.requestMediaKeySystemAccess(keySystem, supportedConfigurations)|
+-------------------------------------------------------------------------+
                                     |
                                     v
                  +--------------------------------------+
                  | MediaKeySystemAccess                 |
                  | - keySystem: string                  |
                  | - getConfiguration(): MediaKeySystemConfig |
                  | - createMediaKeys(): Promise<MediaKeys> |
                  +--------------------------------------+
                                     |
                                     v
                  +--------------------------------------+
                  | MediaKeys                            |
                  | - createSession(sessionType): MediaKeySession |
                  | - setServerCertificate(cert): Promise<void>   |
                  +--------------------------------------+
                                     |
                                     v
                  +--------------------------------------+
                  | HTMLMediaElement                     |
                  | - setMediaKeys(mediaKeys): Promise   |
                  | - onencrypted: EventHandler          |
                  +--------------------------------------+
```

### 3.1. Метод `navigator.requestMediaKeySystemAccess()`

Запитує в браузера доступ до вказаної системи ключів із заданими вимогами до апаратного та програмного середовища.

**Сигнатура:**
```typescript
navigator.requestMediaKeySystemAccess(
  keySystem: string,
  supportedConfigurations: MediaKeySystemConfiguration[]
): Promise<MediaKeySystemAccess>
```

Якщо браузер або операційна система не підтримують зазначену систему захисту чи передану комбінацію параметрів (наприклад, запитано апаратний рівень L1, але пристрій підтримує лише програмний L3), проміс відхиляється з помилкою `NotSupportedError`.

**Параметри `keySystem`:**
- `com.widevine.alpha` — Google Widevine (Modular).
- `com.microsoft.playready` або `com.microsoft.playready.recommendation` — Microsoft PlayReady.
- `com.apple.fps` або `com.apple.fps.1_0` — Apple FairPlay Streaming.
- `org.w3.clearkey` — еталонна тестова система ClearKey (без шифрування ліцензійного каналу).

### Структура `MediaKeySystemConfiguration`

Об'єкт конфігурації дозволяє детально визначити вимоги плеєра до криптографічних можливостей платформи:

```typescript
interface MediaKeySystemConfiguration {
  label?: string;
  initDataTypes?: string[];              // ['cenc', 'keyids', 'webm']
  audioCapabilities?: MediaKeySystemMediaCapability[];
  videoCapabilities?: MediaKeySystemMediaCapability[];
  distinctiveIdentifier?: "required" | "optional" | "not-allowed";
  persistentState?: "required" | "optional" | "not-allowed";
  sessionTypes?: string[];               // ['temporary', 'persistent-license']
}

interface MediaKeySystemMediaCapability {
  contentType: string;                   // MIME-тип із кодеками: 'video/mp4; codecs="avc1.640028"'
  robustness?: string;                   // Рівень стійкості: 'SW_SECURE_CRYPTO', 'HW_SECURE_ALL' тощо
  encryptionScheme?: "cenc" | "cbcs" | "cbcs-1-9" | null;
}
```

### Семантика прапорців конфіденційності та стану

1. **`distinctiveIdentifier`**:
   - `"required"`: Вимагає від системи наявності унікального апаратного ідентифікатора пристрою (використовується в апаратних сертифікатах Widevine L1 та PlayReady SL3000). Браузер може запитати дозвіл у користувача на надання доступу до такого ідентифікатора.
   - `"not-allowed"`: Забороняє використання апаратних ідентифікаторів задля захисту приватності. У такому разі можливе лише програмне емулювання або сертифікація пулом тимчасових ключів.
   - `"optional"`: Дозволяє системі вибрати найкращий доступний варіант.
2. **`persistentState`**:
   - `"required"`: Вимагає від CDM здатності зберігати криптографічний стан (ліцензії, ключі, лічильники відтворень) в енергонезалежній пам'яті для подальшого автономного відтворення без доступу до інтернету.
   - `"not-allowed"`: Забороняє збереження будь-яких ключів на диску. Усі ключі знищуються в момент закриття сесії або вкладки браузера.

### Значення `robustness` для різних DRM

Рядок `robustness` визначає, який рівень апаратної ізоляції вимагає застосунок. Якщо браузер не може забезпечити вказаний рівень, конфігурація відхиляється:

| DRM-система | Значення robustness | Опис вимог до апаратури |
| :--- | :--- | :--- |
| **Widevine** | `""` або `"SW_SECURE_CRYPTO"` | Widevine L3: програмне розшифрування в пам'яті хоста |
| **Widevine** | `"HW_SECURE_CRYPTO"` | Widevine L2: апаратне розшифрування, вивід через звичайну пам'ять |
| **Widevine** | `"HW_SECURE_ALL"` | Widevine L1: повний Secure Video Path (розшифрування й декодування в TEE) |
| **PlayReady**| `"2000"` | PlayReady SL2000: програмне розшифрування або частковий захист |
| **PlayReady**| `"3000"` | PlayReady SL3000: повний апаратний захист TEE + апаратний шлях відео |
| **FairPlay** | `"1"` або `"2"` | Апаратний захист через Secure Enclave на пристроях Apple |

## 4. Об'єкт `MediaKeys` та налаштування сертифіката сервера

Об'єкт `MediaKeys` представляє екземпляр криптографічного контексту для конкретного елемента медіа. Він створюється викликом `mediaKeySystemAccess.createMediaKeys()`.

### Метод `setServerCertificate()`

Деякі DRM-системи (зокрема Google Widevine та Apple FairPlay) вимагають попереднього завантаження публічного сертифіката сервера ліцензій перед генерацією будь-яких запитів:

```typescript
mediaKeys.setServerCertificate(serverCertificate: BufferSource): Promise<void>
```

**Чому це критично:**
Коли модуль CDM формує повідомлення запиту ліцензії (License Challenge), він записує всередину чутливі дані клієнта: унікальний ідентифікатор пристрою, внутрішні криптографічні нонси та версію прошивки. Якщо публічний сертифікат сервера передано в `setServerCertificate()`, CDM зашифровує клієнтський челендж відкритим ключем сервера ліцензій безпосередньо всередині захищеного контуру. Завдяки цьому прикладний код JavaScript та проміжні мережеві вузли бачать лише зашифрований шифротекст і не можуть відстежити чи підробити параметри пристрою.

## 5. Інтерфейс `MediaKeySession` та життєвий цикл сесії

`MediaKeySession` представляє контекст обміну повідомленнями між вебзастосунком та модулем CDM.

### Сигнатура та властивості

```typescript
interface MediaKeySession extends EventTarget {
  readonly sessionId: string;
  readonly expiration: number;           // Час закінчення ліцензії в епосі Unix (мс) або NaN
  readonly keyStatuses: MediaKeyStatusMap;
  readonly closed: Promise<MediaKeySessionClosedReason>;

  generateRequest(initDataType: string, initData: BufferSource): Promise<void>;
  load(sessionId: string): Promise<boolean>;
  update(response: BufferSource): Promise<void>;
  close(): Promise<void>;
  remove(): Promise<void>;

  onmessage: ((this: MediaKeySession, ev: MediaKeyMessageEvent) => any) | null;
  onkeystatuseschange: ((this: MediaKeySession, ev: Event) => any) | null;
}
```

### Стан та переходи життєвого циклу сесії

Сесія проходить кілька послідовних станів:
1. **Створення**: Виклик `mediaKeys.createSession("temporary")` повертає сесію в початковому стані. Значення `sessionId` є порожнім рядком, а `keyStatuses` порожній.
2. **Генерація запиту**: Виклик `generateRequest(initDataType, initData)` переводить сесію в стан обробки. CDM розбирає `initData`, перевіряє сертифікат пристрою та генерує License Challenge. Після завершення властивість `sessionId` отримує унікальний рядок, і генерується подія `message`.
3. **Очікування відповіді**: Плеєр надсилає бінарне навантаження `ev.message` на сервер ліцензій через мережевий запит HTTPS POST.
4. **Оновлення (Update)**: Отримавши ліцензійну відповідь від сервера, плеєр викликає `session.update(response)`. CDM розгортає криптографічний конверт, завантажує ключ у захищені регістри та змінює стан ключів у мапі `keyStatuses`.
5. **Активне відтворення**: Якщо ключі перейшли в статус `"usable"`, елемент `<video>` починає безперервне дешифрування та показ кадрів.
6. **Закриття або видалення**: Після завершення перегляду викликається `session.close()` (звільнення оперативної пам'яті) або `session.remove()` (якщо сесія була `persistent-license`, це видаляє ліцензію зі сховища пристрою та відправляє запит вивільнення на сервер).

### Типи подій сесії

#### 1. `MediaKeyMessageEvent` (`message`)
Виникає, коли CDM формує запит ліцензії або сертифіката, який необхідно передати через мережу на сервер.

```typescript
interface MediaKeyMessageEvent extends Event {
  readonly messageType: MediaKeyMessageType;
  readonly message: ArrayBuffer;        // Бінарний челендж ліцензії (Challenge)
}

type MediaKeyMessageType = 
  | "license-request"                   // Первинний запит ліцензії
  | "license-renewal"                   // Запит на оновлення ліцензії, термін якої збігає
  | "license-release"                   // Повідомлення про звільнення офлайн-ліцензії
  | "individualization-request";        // Запит на персоналізацію/сертифікацію CDM
```

- `"license-request"`: Стандартний початковий запит для отримання ключів контенту.
- `"license-renewal"`: Запит періодичного оновлення ліцензії (наприклад, під час трансляції спортивних подій кожні 15 хвилин або під час оренди фільму).
- `"license-release"`: Повідомлення, що формується під час виклику `session.remove()`. Воно передається на сервер ліцензій для підтвердження того, що офлайн-копію дійсно видалено з пристрою (необхідно для систем оренди з обмеженою кількістю завантажень).
- `"individualization-request"`: Виникає, коли CDM не має власного дійсного сертифіката пристрою (наприклад, після першого встановлення браузера). Запит надсилається на сервер індивідуалізації вендора (Google або Microsoft) для генерації та підпису унікального сертифіката.

#### 2. `keystatuseschange`
Виникає щоразу, коли статус хоча б одного ключа в сесії змінюється (ключ успішно завантажено, термін дії минув, або виявлено невідповідність HDCP).

```typescript
interface MediaKeyStatusMap {
  readonly size: number;
  has(keyId: BufferSource): boolean;
  get(keyId: BufferSource): MediaKeyStatus | undefined;
  entries(): IterableIterator<[ArrayBuffer, MediaKeyStatus]>;
  keys(): IterableIterator<ArrayBuffer>;
  values(): IterableIterator<MediaKeyStatus>;
}

type MediaKeyStatus = 
  | "usable"                            // Ключ активний, розшифрування працює
  | "expired"                           // Термін дії ліцензії вичерпано
  | "released"                          // Ліцензію вивільнено клієнтом
  | "output-restricted"                 // Заборонено політикою виводу (наприклад, потрібен HDCP 2.2)
  | "output-downscaled"                 // Дозволено лише зі штучним зниженням роздільної здатності
  | "status-pending"                    // Статус обробляється CDM
  | "internal-error";                   // Збій у криптографічному модулі
```

### Поведінка плеєра при зміні статусів

- `"usable"`: Потік відтворюється у штатному режимі.
- `"output-restricted"`: Користувач під'єднав зовнішній дисплей через кабель або перехідник, який не підтримує зазначену в ліцензії версію HDCP (наприклад, підключено старий монітор VGA або телевізор із HDCP 1.4 під час перегляду 4K-відео, яке вимагає HDCP 2.2). У такому разі плеєр зобов'язаний зупинити відтворення або перемкнутися на потік нижчої якості (1080p або 720p), для якого обмеження HDCP відсутні.
- `"output-downscaled"`: Відеокарта або операційна система автоматично зменшує роздільну здатність кадру до безпечного рівня перед виведенням на несертифікований екран.
- `"expired"`: Плеєр мусить або припинити відтворення та показати повідомлення про необхідність поновлення підписки, або ініціювати новий запит ліцензії.

### 5.1. Причини закриття сесії (`MediaKeySessionClosedReason`)

Властивість `session.closed` повертає проміс, який переходить у стан виконання, коли сесію остаточно завершено. Починаючи з оновленої специфікації W3C EME, проміс повертає перелічуване значення причини закриття:

- `"internal-error"`: Апаратний збій у криптографічному чипі, перезавантаження захищеної операційної системи анклаву (TEE) або вичерпання апаратної пам'яті.
- `"closed-by-application"`: Програмний код JavaScript явно викликав метод `session.close()`.
- `"release-acknowledged"`: Сервер ліцензій успішно підтвердив видалення ліцензії після запиту вивільнення.
- `"hardware-context-reset"`: Зміна режиму живлення пристрою (вихід зі сну) або перемикання графічного драйвера призвели до скидання сесійних ключів у кремнії.

## 6. Робота з багатьма ключами (Multi-Key PSSH)

У сучасних трансляціях високої чіткості аудіодоріжка, стандартне відео (SD) та відео надвисокої чіткості (4K UHD) шифруються різними симетричними ключами:
1. `KID_audio` — ключ зі спрощеними вимогами до безпеки (дозволено відтворення на будь-якому обладнанні).
2. `KID_sd` — ключ для відео 480p/720p (дозволено для програмного модуля Widevine L3).
3. `KID_uhd` — ключ для відео 4K HDR (вимагає апаратного захисту Widevine L1 та підтримки HDCP 2.2).

### Обробка багатоключового боксу версії 1

Коли бокс `pssh` версії 1 містить одразу кілька ідентифікаторів `KID`, модуль CDM формує єдиний груповий запит ліцензії. У відповідь сервер повертає один контейнер, який містить усі три ключі, але з різними прапорцями обмежень.

Мапа `session.keyStatuses` після виклику `session.update()` містить три окремі записи:
- Для `KID_audio` статус `"usable"`.
- Для `KID_sd` статус `"usable"`.
- Для `KID_uhd` статус `"output-restricted"`, якщо пристрій підключено до монітора без підтримки HDCP 2.2.

Завдяки цьому плеєр може продовжувати безперервне відтворення аудіо та відео якості 1080p, заблокувавши лише перемикання на доріжку 4K, замість повного аварійного збою сесії.

## 7. Зіставлення форматів ініціалізаційних даних (`initDataType`)

Метод `generateRequest(initDataType, initData)` приймає тип пакування контейнерних метаданих:

1. **`"cenc"`**:
   - Двійковий масив, що містить один або кілька повних боксів `pssh` (разом із 8-байтовим заголовком `size` + `pssh`). Застосовується в контейнерах ISO BMFF / fMP4 та специфікаціях DASH і CMAF.
2. **`"keyids"`**:
   - JSON-документ формату `{"kids": ["base64url-kid-1", "base64url-kid-2"]}`. Використовується в W3C ClearKey для тестування без прив'язки до бінарних медіаконтейнерів.
3. **`"webm"`**:
   - 16-байтове значення `ContentEncKeyID` безпосередньо з елемента `ContentEncryption` контейнера Matroska/WebM.

## 8. Типові коди помилок та винятки EME

Операції EME повертають відхилені проміси з об'єктами `DOMException`. Перелік стандартизованих помилок:

| Виняток (`DOMException.name`) | Причина виникнення |
| :--- | :--- |
| `NotSupportedError` | Запитувана комбінація `keySystem`, кодеків чи `robustness` не підтримується платформою. |
| `InvalidStateError` | Виклик методу у невідповідному стані сесії (наприклад, `generateRequest()` для вже ініціалізованої сесії). |
| `QuotaExceededError` | Вичерпано ліміт пам'яті для зберігання офлайн-ліцензій (`persistent-license`). |
| `TypeError` | Некоректні параметри або невалідний `initData` / `response`. |
