# 📋 Інтерфейси зняття метрик рівнів сигналу

Програмні інтерфейси взаємодії з мобільними модемами та бездротовими адаптерами надають різнорівневі методи читання метрик RSSI, RSRP, RSRQ та SINR. Від текстових AT-команд стандарту 3GPP до низькорівневих системних шин DBus, бінарних протоколів QMI/MBIM, сокетів підсистеми mac80211/nl80211 ядра Linux та високорівневих системних API мобільних операційних систем Android — кожен інтерфейс має власний механізм опитування, кодування та обробки подій.

## Текстовий протокол AT-команд (3GPP TS 27.007)

Текстовий інтерфейс AT-команд (Attention Commands) є фундаментальним стандартом взаємодії з сотовими модемами через послідовні інтерфейси UART або віртуальні USB-порти CDC-ACM. Запит надсилається у формі ASCII-рядка, а відповідь повертається у визначеному форматі з підсумковим статусом `OK` або `ERROR`.

### 1. Базова команда AT+CSQ (Signal Quality)

Команда `AT+CSQ` була розроблена у часи 2G (GSM) і залишається найпростішим методом оцінки сигналу для сумісності з застарілими пристроями.

**Синтаксис запиту:**
```text
AT+CSQ
```

**Формат відповіді:**
```text
+CSQ: <rssi>,<ber>
OK
```

Параметр `<rssi>` надає умовне значення індикатора сили прийнятого сигналу у діапазоні від 0 до 31, а `<ber>` показує коефіцієнт помилок бітів у каналах голосу (Bit Error Rate, від 0 до 7 за шкалою 3GPP TS 45.008).

Таблиця декодування параметра `<rssi>` у фізичну потужність дБм:

| Значення `<rssi>` | Еквівалентна потужність RSSI | Рівень якості та стан каналу |
|---|---|---|
| `0` | `-113 dBm` або менше | Граничний рівень чутливості, втрата зв'язку |
| `1` | `-111 dBm` | Дуже слабкий сигнал |
| `2 ... 30` | від `-109 dBm` до `-53 dBm` | Рівномірний крок 2 дБ (`RSSI = -113 + 2 · rssi`) |
| `31` | `-51 dBm` або більше | Максимально потужний сигнал поблизу вежі |
| `99` | Не визначено / немає мережі | Модем у стані пошуку соти або відключений |

**Формула розрахунку RSSI у дБм:**
```text
RSSI_dBm = -113 + (2 · rssi_val)    [для 0 ≤ rssi_val ≤ 31]
```

Основне обмеження `AT+CSQ` — відсутність відомостей про RSRP, RSRQ та завади у мережах LTE/5G. Команда повертає лише розрахований модемом широкосмуговий RSSI.

### 2. Розширена команда AT+CESQ (Extended Signal Quality)

У стандарті 3GPP TS 27.007 впроваджено команду `AT+CESQ`, яка розщеплює вимірювання за специфічними метриками для 2G, 3G (RSCP/EcNo), LTE та 5G (RSRQ/RSRP).

**Синтаксис запиту:**
```text
AT+CESQ
```

**Формат відповіді:**
```text
+CESQ: <rxlev>,<ber>,<rscp>,<ecno>,<rsrq>,<rsrp>
OK
```

У мережах LTE та 5G параметри `<rxlev>`, `<rscp>` та `<ecno>` приймають значення `255` (не застосовується), а модем повертає актуальні поля `<rsrq>` та `<rsrp>`.

Декодування значення `<rsrq>` (Reference Signal Received Quality):
- `0`: менше `-19.5 dB`;
- `1 ... 33`: діапазон від `-19.5 dB` до `-3.5 dB` з кроком `0.5 dB`;
- `34`: `-3.0 dB` або більше;
- `255`: не визначено.

**Формула декодування RSRQ:**
```text
RSRQ_dB = -20.0 + (rsrq_val · 0.5)
```

Декодування значення `<rsrp>` (Reference Signal Received Power):
- `0`: менше `-140 dBm`;
- `1 ... 96`: діапазон від `-140 dBm` до `-45 dBm` з кроком `1 dBm`;
- `97`: `-44 dBm` або більше;
- `255`: не визначено.

**Формула декодування RSRP:**
```text
RSRP_dBm = -141 + rsrp_val
```

### 3. Проперитарні команди вендорів для NB-IoT та 5G (Quectel / SIMCom / Nordic / Telit)

Виробники мікросхем реалізують власні розширені команди для доступу до розширеної розкладки метрик (включаючи SINR та індекси активних променів 5G NR).

Приклад команди Quectel `AT+QENG="servingcell"`:
```text
+QENG: "servingcell","NOCONN","LTE","FDD",255,01,1A2B3,350,1300,3,5,5,"4321",-95,-11,-65,15
```
де в кінці віддаються значення `RSRP=-95 dBm`, `RSRQ=-11 dB`, `RSSI=-65 dBm` та `SINR=15 dB`.

У спеціалізованих узкосмугових модулях NB-IoT (Quectel BC66, SIMCom SIM7020) застосовують команду `AT+NUESTATS="CELL"`, яка відображає додатково рівень шуму та зміщення частоти (Frequency Offset).

У системі на кристалі Nordic Semiconductor nRF9160 (LTE-M/NB-IoT) використовується AT-команда `AT%XSIGNAL`:
```text
%XSIGNAL: 85, -95, -11, 14
```
де повертаються значення відносного індексу якості (0–100%), RSRP у дБм, RSRQ у дБ та SINR у дБ.

У модемах Telit (серії LE910 / FN980) використовують проперитарну команду `AT$QCRSRP`:
```text
$QCRSRP: -94, 0
```
де повертається виміряний RSRP у дБм та номер антенного порту.

### 4. Асинхронні сповіщення (Unsolicited Result Codes, URC)

Опитування модема через `AT+CESQ` у циклі створює зайве навантаження на послідовний порт і процесор. Більшість сучасних модемів (Quectel EC25/EG25, SIMCom SIM7600) підтримують налаштування періодичних сповіщень URC під час зміни параметрів сигналу на задану величину.

Приклад конфігурації URC на модемах Quectel:
```text
AT+QCFG="urc/ri/ring",1
AT+QINDCFG="csq",1,1
```

Після активації модем самостійно надсилає в порт асинхронний рядок при зміні рівня:
```text
+QIND: "csq",-75,-105,-11,18
```
де параметри відповідають `RSSI=-75 dBm`, `RSRP=-105 dBm`, `RSRQ=-11 dB`, `SINR=18 dB`.

### 5. Обробка відповідей та парсинг рядків у коді

Під час взаємодії з модемом через послідовний порт прикладне ПЗ мусить враховувати особливості таймінгів та форматування:
- **Затримка відповіді:** Деякі AT-команді (наприклад, сканування операторів `AT+COPS=?`) потребують до 60 секунд, тоді як `AT+CESQ` виконується за 10–50 мс.
- **Ехо-символи:** За замовчуванням модем може повертати в порт вхідний рядок команди (якщо не вимкнено командою `ATE0`).
- **Символи переведення рядка:** Відповіді стандартизовано завершуються послідовністю `\r\nOK\r\n` або `\r\nERROR\r\n`.

Приклад парсингу відповіді `+CESQ` на C:
```c
int rsrq_val = 255, rsrp_val = 255;
if (sscanf(response, "\r\n+CESQ: %*d,%*d,%*d,%*d,%d,%d\r\n", &rsrq_val, &rsrp_val) == 2) {
    if (rsrp_val != 255) {
        double rsrp_dbm = -141.0 + rsrp_val;
        printf("RSRP: %.1f dBm\n", rsrp_dbm);
    }
}
```

### 6. Робота з модемами у вбудованих Linux-системах (OpenWrt / Yocto)

У спеціалізованих маршрутизаторах та проміжних вбудованих вузлах на базі OpenWrt чи Yocto Linux прямий виклик команд виконується через системну утиліту `chat` або демони `comgt` / `uqmi` / `mbimcli`.

Конфігураційний скрипт `netifd` у OpenWrt створює інтерфейс мобільного зв'язку через протокол `3g` або `qmi`:
```bash
config interface 'wan'
	option proto 'qmi'
	option device '/dev/cdc-wdm0'
	option apn 'internet'
	option auth 'none'
```

Демон автоматично опитує вимірювальні служби `QMI_NAS` і передає значення потужності в системний стек `ubus`, звідки статус зчитується веб-інтерфейсом LuCI.

Обробка можливих помилок зв'язку при роботі з послідовним портом передбачає перевірку відповідей `+CME ERROR`. Якщо модем повертає `+CME ERROR: 10` (SIM not inserted) або `+CME ERROR: 30` (No network service), прикладний демон зупиняє опитування `AT+CESQ` та переводить пристрій у стан повторної енумерації через перезапуск USB-порту (USB Bus Reset).

## Бінарні протоколи високої швидкості: Qualcomm QMI та MBIM

Текстові AT-команди мають високу затримку парсингу і не можуть використовуватися в високошвидкісних маршрутизаторах та системних демонах. У сучасних LTE/5G модулях застосовують бінарні протоколи керування через шар драйверів `qmi_wwan` або `cdc_mbim`.

### 1. Qualcomm QMI (Qualcomm MSM Interface)

Протокол QMI базується на обміні бінарними пакетами поверху символьного пристрою `/dev/cdc-wdm0`. Служба **NAS (Network Access Service)** відповідає за стан радіомережі.

Для отримання розширених метрик клієнт надсилає запит `QMI_NAS_GET_SIGNAL_INFO` (ID повідомлення `0x004F`).

Структура відповіді містить бінарні блоки TLV (Type-Length-Value):
- **TLV 0x11 (LTE Signal Info):**
  - `rssi`: 2 байти (знакове `int16`, крок `0.1 dBm`);
  - `rsrp`: 2 байти (знакове `int16`, крок `0.1 dBm`);
  - `rsrq`: 2 байти (знакове `int16`, крок `0.1 dB`);
  - `snr`:  2 байти (знакове `int16`, крок `0.1 dB`).
- **TLV 0x14 (5G Signal Info / NR5G):**
  - `rsrp`: 2 байти (знакове `int16`, крок `0.1 dBm`);
  - `rsrq`: 2 байти (знакове `int16`, крок `0.1 dB`);
  - `sinr`: 2 байти (знакове `int16`, крок `0.1 dB`).

Приклад використання консольної утиліти `uqmi`:
```bash
uqmi -d /dev/cdc-wdm0 --get-signal-info
```

Результат виконання у форматі JSON:
```json
{
	"type": "lte",
	"rssi": -67,
	"rsrp": -96,
	"rsrq": -11,
	"snr": 15
}
```

### 2. MBIM (Mobile Broadband Interface Model)

Стандарт USB-IF для мобільних адаптерів у Windows та Linux. Обмін здійснюється керуючими структурами MBIM Control Messages. Служба `MBIM_UUID_BASIC_CONNECT` надає CID `MBIM_CID_SIGNAL_STATE`.

Відповідь містить структуру `MBIM_SIGNAL_STATE_INFO`, яка повертає значення `RSRP` та `RSRQ` у стандартних кодованих одиницях 3GPP, а також порогові інтервали для генерації системних подій переривання.

Приклад виклику через CLI-утиліту `mbimcli`:
```bash
mbimcli -d /dev/cdc-wdm0 --query-signal-state
```

Вивід консолі:
```text
[/dev/cdc-wdm0] Signal state retrieved:
	Signal strength: '85'
	RSRP:            '-95 dBm'
	RSRQ:            '-11 dB'
	RSSI:            '-65 dBm'
```

### 3. Специфіка підсистеми Windows WWAN Service (WMBCLASS)

У системному середовищі Microsoft Windows керування сотовими модемами виконується через службу **WWAN Service (WwanSvc)** та архітектуру драйверів NDIS 6.x / MBIM.

Розробники системного ПЗ на C++ взаємодіють з модемом через Windows API `WwanOpenHandle` та `WwanQueryInterface`:

```cpp
DWORD result = WwanQueryInterface(
    hClient,
    &pInterfaceList->InterfaceInfo[0].InterfaceGuid,
    wwan_intf_opcode_radio_state,
    NULL,
    &dataSize,
    (PVOID*)&pData
);
```

Служба Windows самостійно трансляціює значення RSRP у системний індикатор «паличок» (Signal Bars) у треї Windows taskbar:
- 5 паличок: `RSRP >= -85 dBm`;
- 4 палички: `-95 dBm <= RSRP < -85 dBm`;
- 3 палички: `-105 dBm <= RSRP < -95 dBm`;
- 2 палички: `-115 dBm <= RSRP < -105 dBm`;
- 1 паличка: `RSRP < -115 dBm`.

## Linux NetworkManager (libnm) та ModemManager

У сучасних дистрибутивах Linux керування мережами автоматизоване через демон NetworkManager та його бібліотеку `libnm`.

Диспетчер NetworkManager отримує дані від `ModemManager` через DBus та конвертує різнорідні показники RSRP/RSSI у нормований відсоток сили сигналу `0 ... 100%` за внутрішньою поліноміальною шкалою:
- `0%`: RSRP нижче `-115 dBm`;
- `20%`: RSRP близько `-105 dBm`;
- `50%`: RSRP близько `-95 dBm`;
- `80%`: RSRP близько `-85 dBm`;
- `100%`: RSRP перевищує `-75 dBm`.

Приклад консольного запиту стану сигналу через `nmcli`:
```bash
nmcli dev wifi list
nmcli -f IN-USE,SIGNAL,SSID dev wifi
```

У прикладних програмах мовою C/C++ використовують C-бібліотеку `libnm`:
```c
NMClient *client = nm_client_new(NULL, NULL);
const GPtrArray *devices = nm_client_get_devices(client);
for (guint i = 0; i < devices->len; i++) {
    NMDevice *dev = g_ptr_array_index(devices, i);
    if (NM_IS_DEVICE_MODEM(dev)) {
        guint quality = nm_device_modem_get_active_network_signal_quality(NM_DEVICE_MODEM(dev));
        printf("Якість сигналу модема: %u%%\n", quality);
    }
}
```

## Linux Subsystem nl80211 (Wi-Fi 802.11)

Для Wi-Fi бездротових адаптерів (драйвери `ath9k`, `iwlwifi`, `mt76`) підсистема ядра Linux `cfg80211` надає доступ до метрик через мережеві сокети Netlink протоколу `nl80211`.

### Структура Netlink повідомлення NL80211_CMD_GET_STATION

Запит інформації про стан підключення повертає вкладений атрибут `NL80211_ATTR_STA_INFO`.

Основні атрибути сигналу у структурі `nl80211`:
- `NL80211_STA_INFO_SIGNAL`: Знакове 8-бітне ціле число (`s8`), що показує рівень RSSI останнього прийнятого кадру у дБм.
- `NL80211_STA_INFO_SIGNAL_AVG`: Знакове 8-бітне ціле число (`s8`), що показує експоненційно згладжений рівень RSSI (EMA), який розраховується безпосередньо у драйвері ядра Linux.
- `NL80211_STA_INFO_CHAIN_SIGNAL`: Масив значень RSSI окремо для кожної антени в конфігураціях MIMO (наприклад, `[-54, -58] dBm` для 2x2 MIMO).
- `NL80211_SURVEY_INFO_NOISE`: Рівень фонового теплового шуму ефіру, виміряний під час сканування (типово `-95 dBm`).

Приклад швидкого опитування Wi-Fi сигналу в консолі через `wpa_cli`:
```bash
wpa_cli -i wlan0 signal_poll
```

Вивід:
```text
RSSI=-55
LINKSPEED=866
NOISE=-95
FREQUENCY=5180
```

Програмне обчислення співвідношення сигнал/шум (SNR) для Wi-Fi у прикладній програмі:
```text
SNR_dB = RSSI_dBm - Noise_dBm
```
Наприклад, при `RSSI = -60 dBm` та `Noise = -95 dBm`, `SNR = -60 - (-95) = 35 dB`, що забезпечує максимальну швидкість кадру під час використання модуляції 256QAM чи 1024QAM.

## Мобільні ОС: Android TelephonyManager API

В операційній системі Android додатки зчитують стан мережі через Java/Kotlin API класу `android.telephony.TelephonyManager` та `SignalStrength`.

З версії Android 10 (API Level 29) доступні прямо розпаковані екземпляри класів `CellSignalStrengthLte` та `CellSignalStrengthNr`:

```java
CellSignalStrengthLte lteSignal = cellInfoLte.getCellSignalStrength();
int rsrpDbm = lteSignal.getRsrp();   // Значення у dBm (наприклад, -98)
int rsrqDb  = lteSignal.getRsrq();   // Значення у dB (наприклад, -11)
int rssiDbm = lteSignal.getRssi();   // Значення у dBm
int sinrDb  = lteSignal.getRssnr();  // SNR у dB
```

Для 5G NR використовується клас `CellSignalStrengthNr`:
```java
CellSignalStrengthNr nrSignal = (CellSignalStrengthNr) cellInfoNr.getCellSignalStrength();
int ssRsrp = nrSignal.getSsRsrp();   // SS-RSRP у dBm
int ssRsrq = nrSignal.getSsRsrq();   // SS-RSRQ у dB
int ssSinr = nrSignal.getSsSinr();   // SS-SINR у dB
```

Ці виклики дозволяють розробникам мобільних додатків створювати карти покриття ефіру (Speedtest, NetMonster) без прямого доступу до root-прав чи AT-порту модема.

## Градація якості зв'язку для IoT-пристроїв

Для прийняття автоматичних рішень у промислових контролерах (наприклад, вибір активної SIM-карти у двосимочному модемі або вибір типу трафіку) використовують єдину метрологічну матрицю:

| Стан зв'язку | RSRP (дБм) | RSRQ (дБ) | SINR (дБ) | Рекомендована поведінка системи |
|---|---|---|---|---|
| **Excellent (Відмінно)** | `>= -80` | `>= -10` | `>= 20` | Дозволено максимальний трафік, передачу потокового відео, оновлення ПЗ. |
| **Good (Добре)** | `-81 ... -90` | `-11 ... -15` | `13 ... 19` | Стабільна робота всіх телеметричних додатків, висока швидкість. |
| **Fair (Задовільно)** | `-91 ... -100` | `-16 ... -18` | `0 ... 12` | Базовий режим передачі датчиків, можливі затримки, заборона важких завантажень. |
| **Poor (Погано)** | `< -100` | `< -18` | `< 0` | Критичний стан, високий BLER, підготовка до перемикання SIM-карти чи рестарту модема. |
