# ⚙️ Переривання по фронту чи по рівню: код і пастки

Поділ «фронт проти рівня» живе не лише в кремнії тригерів — він зринає щоразу, коли мікроконтролер ловить зовнішню подію через **переривання** (англ. *interrupt* — «переривати»). Лінію переривання майже завжди можна налаштувати або на **фронт** (зреагувати на сам перехід сигналу), або на **рівень** (реагувати, поки вхід тримає активне значення). І вибір тягне за собою цілком різну поведінку — рівно ту саму різницю, що між тригером по фронту й прозорим латчем.

## Задача

Кнопка, давач, мікросхема-сусід смикають ніжку мікроконтролера. Треба, щоб процесор кинув поточну роботу й виконав короткий **оброблювач** (*handler*) — але рівно стільки разів, скільки сталося подій, без зайвих повторів і без пропусків. Конкретне рішення, яке доведеться ухвалити в кожному драйвері: спрацьовувати на **перехід** лінії чи на її **стан**? І як після цього правильно «закрити» подію, щоб переривання не зациклилося й не загубилося. Помилка тут не ловиться компілятором — вона тихо проявляється як «оброблювач крутиться без кінця» або «натиснув, а нічого не сталося».

## Ідея

Розрізнення просте, якщо тримати в голові аналогію з тригером і латчем.

**Фронт** — це «вистрелив і забув»: контролер фіксує **одну** подію на кожен перехід (наприклад, 0→1) і виставляє прапорець. Доки не станеться **новий** перехід, нового переривання не буде, хоч би скільки трималася лінія. Це поведінка тригера: реакція на мить, не на стан.

**Рівень** — це «поки тримається»: переривання активне весь час, **поки на вході активний рівень**. Якщо джерело не «погасити» в самому пристрої, то щойно оброблювач вийде — переривання спрацює **негайно знову**, бо рівень нікуди не подівся. Це поведінка прозорого латча: реакція на стан, не на мить.

Звідси два практичні наслідки. Рівневі лінії можна чесно **ділити** між кількома джерелами: усі вони підтягують спільну лінію, а оброблювач опитує по черзі, хто саме її підняв, і гасить винуватця. Зате гасити в джерелі — **обов'язково**. Фронтові лінії ділити так не можна (два майже одночасні фронти зіллються в один — і одну подію проґавиш), зате й клопоту менше: прапорець знімаєш — і чекаєш наступного переходу.

Чому рівень дозволяє спільну лінію, а фронт — ні, видно, якщо подумати про **накладання** подій. Уявіть, що на одну лінію повісили три давачі. Якщо лінія **рівнева** й активна, поки бодай один давач має дані, то навіть коли всі три заговорять одночасно, лінія просто лишиться активною, доки оброблювач не обійде й не погасить **усіх трьох** по черзі — жодну подію не втрачено, бо рівень терпляче «чекає», поки його приберуть. А якщо лінія **фронтова**, то два майже одночасні переходи зіллються в **один** фронт: апаратура побачить лише один край і викличе оброблювач один раз, а друга подія тихо зникне. Тому загальне правило драйверів таке: спільна лінія переривань — **рівнева**; виділена лінія одного джерела — частіше **фронтова**. Це прямий відповідник того, чому рівневий латч «бачить стан», а тригер «бачить мить»: стан можна додати ще одним джерелом, мить — ні.

Є й зворотний бік. Рівень вимагає **двостороннього діалогу**: пристрій тримає сигнал, поки процесор не зробить щось конкретне (прочитає регістр, скине прапорець), — і лише тоді сигнал знімається. Фронт же — **однобічне повідомлення без підтвердження**: пристрій «крикнув» переходом і більше нічого не чекає. Однобічність робить фронт швидшим і простішим, але саме через відсутність підтвердження він і здатний загубити подію, якщо та злилася з іншою або потонула в брязкоті.

## Робочий C: фронт на STM32 (EXTI)

На STM32 зовнішніми перериваннями керує блок EXTI. Який фронт ловити, задають **два окремі** регістри: `EXTI->RTSR` — дозвіл наростання (*rising trigger*), `EXTI->FTSR` — дозвіл спаду (*falling trigger*). Налаштуємо лінію 0 на фронт наростання:

**Умова: спіймати натискання кнопки на лінії EXTI0 лише по фронту наростання (0→1).**

```c
#include <stdint.h>

void exti0_rising_setup(void) {
    EXTI->RTSR |=  (1u << 0);   // дозволити фронт наростання на лінії 0
    EXTI->FTSR &= ~(1u << 0);   // спад вимкнути — ловимо лише 0->1
    EXTI->IMR  |=  (1u << 0);   // зняти маску: переривання дозволено
    // (тактування SYSCFG і вибір порту для EXTI0 — поза цим прикладом)
}

void EXTI0_IRQHandler(void) {
    if (EXTI->PR & (1u << 0)) {   // це справді наша лінія?
        EXTI->PR = (1u << 0);     // зняти прапорець: запис 1 у PR його СКИДАЄ
        on_button_press();        // корисна робота — коротко!
    }
}
```

Дві деталі тут вирішальні. По-перше, прапорець `EXTI->PR` для лінії скидається **записом одиниці** в цей самий біт (не нуля — це поширена плутанина). По-друге, для фронту скинути прапорець треба **вручну** в оброблювачі; не скинеш — апаратура вважатиме, що подія ще не оброблена, і викличе оброблювач знову.

## Те саме, але по рівню — і чому без скидання в джерелі буде цикл

У багатьох контролерів (наприклад, в ядрах із контролером NVIC/GIC, або в зовнішніх розширювачах портів) лінію можна налаштувати **рівневою**. Тоді логіка інша: поки на вході активний рівень, переривання «висить». Уявімо мікросхему-давач, яка тримає лінію INT низькою, **доки** в неї є непрочитані дані:

**Умова: давач тримає INT=0, поки є дані; обробити всі дані й відпустити лінію.**

```c
// рівневе переривання (активне, поки INT тримається низьким)
void sensor_irq_level_handler(void) {
    // ОБОВ'ЯЗКОВО гасимо джерело: читаємо дані, аж поки давач не відпустить INT.
    while (sensor_data_ready()) {     // поки давач сигналить
        uint8_t v = sensor_read();    // читання знімає його внутрішній прапорець
        consume(v);
    }
    // тепер давач відпустив INT (рівень знявся) — переривання більше не активне.
    // Якби ми вийшли, не дочитавши, рівень лишився б — і оброблювач
    // спрацював би НЕГАЙНО знову. Це і є "залипання" на рівні.
}
```

Суть пастки: у рівневому режимі **апаратура не запам'ятовує подію — вона дивиться на стан**. Якщо стан активний, переривання повториться одразу після виходу. Тому рівневий оброблювач мусить довести джерело до неактивного стану (дочитати буфер, скинути прапорець у давачі), інакше процесор застрягне в нескінченному вході-виході з оброблювача.

## Дрібний фронт, або чому кнопці потрібне «придушення брязкоту»

Є ще одна пастка, що б'є саме по **фронтових** перериваннях, і вона прямо випливає з вимоги «фронт мусить бути чистим». Механічна кнопка під час натискання **брязкає** контактами — за кілька мілісекунд дає десятки швидких переходів 0↔1. Для тригера це були б кілька фронтів; для фронтового переривання — **десятки викликів** оброблювача на одне натискання.

Лік — **придушення брязкоту** (*debounce*): прийняти перший фронт, а далі на короткий час ігнорувати нові, поки контакти не заспокояться.

```c
#include <stdint.h>
#include <stdbool.h>

static volatile uint32_t last_tick = 0;   // мітка часу останньої прийнятої події
extern uint32_t millis(void);             // системний лічильник мілісекунд

void EXTI0_IRQHandler(void) {
    if (EXTI->PR & (1u << 0)) {
        EXTI->PR = (1u << 0);              // зняти апаратний прапорець завжди
        uint32_t now = millis();
        if (now - last_tick >= 20) {      // 20 мс тиші між справжніми натисками
            last_tick = now;
            on_button_press();            // одне натискання -> один виклик
        }
        // інакше це брязкіт того самого натиску — мовчки ігноруємо
    }
}
```

Тут `last_tick` оголошено `volatile`, бо його змінює оброблювач переривання, а читати можуть і інші частини коду — компілятор не має права «кешувати» це значення в регістрі. Двадцять мілісекунд — типовий поріг для кнопки; точна цифра залежить від механіки. Сенс той самий, що й на тактових лініях: фронт має бути **один і чистий**, інакше система зробить зайві кроки.

## Складність і пастки

Самі операції тривіальні — кілька записів у регістри, **O(1)**. Уся складність — у пастках, кожна з яких компілюється без жодного попередження:

- **Не скинув прапорець фронту** → оброблювач крутиться без кінця. Скидати `EXTI->PR` (записом 1) на початку обробки.
- **Не погасив джерело рівневого переривання** → те саме залипання, але причина зовні: дочитуй буфер / скидай прапорець у самому пристрої, поки рівень не знявся.
- **Сплутав рівень і фронт** на лінії, що ділиться між пристроями: ділити можна **лише рівневі** (оброблювач опитує всіх); фронтова спільна лінія губить події, коли два фронти зливаються.
- **Брязкіт кнопки на фронтовому вході** → десятки хибних спрацювань: придушення брязкоту (часом або апаратним [тригером Шмітта](topic:electronics/threshold-schmitt) на вході).
- **Забув `volatile`** на змінних, що їх чіпає оброблювач: компілятор оптимізує читання — і код «не бачить» оновлення з переривання.
- **Довгий оброблювач**: робота в перериванні має бути короткою. Велику справу відкладай у головний цикл, з переривання лише виставляй прапорець.

## Підсумок

Переривання по **фронту** фіксує одну подію на кожен перехід («вистрелив і забув»): прапорець треба зняти вручну, спільну лінію так ділити не можна, а механічну кнопку доводиться [очищати від брязкоту](topic:electronics/threshold-schmitt). Переривання по **рівню** активне, поки тримається сигнал («поки висить»): його можна ділити між джерелами, зате джерело **обов'язково** гасити в самому пристрої, інакше оброблювач зациклиться. Це той самий поділ, що між [тригером по фронту й прозорим латчем](topic:electronics/edge-vs-level): фронт — реакція на мить, рівень — на стан. Обираючи режим лінії, ви фактично обираєте, чи ваша подія — це «перехід», чи «стан», і весь подальший код драйвера випливає з цього вибору.
