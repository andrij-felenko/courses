# 📋 Формат пакетів та типів даних MIPI CSI-2

Специфікація інтерфейсу MIPI CSI-2 (Camera Serial Interface 2) стандартизує синтаксис та семантику пакетного рівня, що зв'язує фізичний рівень приймально-передавальних ліній (D-PHY або C-PHY) з логічними конвеєрами оброблення зображень (ISP). На рівні протоколу потік даних організовано в пакети двох фундаментальних категорій: короткі пакети (Short Packets) фіксованого розміру 4 байти для синхронізації та передавання керувальних команд, і довгі пакети (Long Packets) змінної довжини для транспортування піксельних масивів та службових метаданих сенсора.

Нижче наведено детальний технічний опис структури пакетів, класифікації типів даних, схем бітового пакування відліків АЦП, математичних матриць розрахунку контрольних сум ECC та CRC-16, а також карти регістрів типового апаратного контролера CSI-2 RX.

---

### 1. Структура ідентифікатора даних (Data Identifier, DI)

Кожен пакет MIPI CSI-2 відкривається однобайтним полем Data Identifier (DI), яке визначає адресацію потоку та внутрішню структуру корисного навантаження:

```
БІТОВА СТРУКТУРА БАЙТА DATA IDENTIFIER (DI):
┌───────────┬───────────┬───────────────────────────────────────────┐
│   DI[7]   │   DI[6]   │  DI[5]   DI[4]   DI[3]   DI[2]   DI[1]   DI[0]  │
├───────────┴───────────┼───────────────────────────────────────────┤
│  Virtual Channel (VC) │              Data Type (DT)               │
└───────────────────────┴───────────────────────────────────────────┘
```

#### Віртуальні канали (Virtual Channels, VC)
Поле `DI[7:6]` містить 2-бітний номер віртуального каналу (від 0 до 3 у специфікації CSI-2 версії v1.x). Віртуальні канали дозволяють розділити один фізичний лінк на чотири незалежних логічних потоки. Це вирішує три критичні архітектурні задачі сучасних систем технічного зору:

1. **Мультисенсорні модулі з єдиним інтерфейсом:** Мобільний або бортовий модуль може містити основну оглядову камеру високої роздільної здатності (потік передається з тегом `VC = 0`) та сенсор вимірювання глибини сцени Time-of-Flight (потік із тегом `VC = 1`). Обидва потоки надходять на один апаратний порт процесора, де демультиплексор автоматично розкладає їх у різні кільцеві буфери оперативної пам'яті.
2. **Апаратний розширений динамічний діапазон (HDR):** Матриця сенсора під час знімання висококонтрастної сцени експонує пікселі кількома різними витримками одночасно. Рядки, зчитані з короткою витримкою (для запобігання пересвічуванню відблисків), маркуються як `VC = 0`, а рядки довгої витримки (для витягування деталей із глибоких тіней) — як `VC = 1`. Процесор ISP отримує обидва експозиційні шари синхронно і виконує їхнє попіксельне злиття без затримок.
3. **Автомобільні концентратори відеокамер:** У системах кругового огляду автомобіля чотири окремі відеокамери підключаються коаксіальними кабелями до центрального десеріалізатора (наприклад, мікросхем сімейств TI FPD-Link або Analog Devices GMSL). Десеріалізатор об'єднує чотири незалежні відеопотоки в один вихідний 4-лінійний інтерфейс MIPI CSI-2, маркуючи камери каналами `VC0`, `VC1`, `VC2` та `VC3`.

У специфікаціях MIPI CSI-2 версії v2.0 та вище простір віртуальних каналів розширено з 4 до 32 (`VC0..VC31`). Старші розряди номера каналу `VC[4:2]` кодуються за допомогою спеціальних службових байтів розширення або модифікованих коротких пакетів, що зберігає повну зворотну сумісність із приймачами попередніх поколінь.

#### Тип даних (Data Type, DT)
Поле `DI[5:0]` є 6-бітним селектором формату корисного навантаження (значення від `0x00` до `0x3F`). Діапазон `0x00..0x0F` закріплено за короткими пакетами синхронізації та загальних команд; діапазон `0x10..0x3F` відведено для довгих пакетів пікселів та службових метаданих сенсора.

### 2. Повна таблиця типів даних (Data Types, DT)

Кожен числовий код типу даних суворо регламентує внутрішню структуру корисного навантаження та поведінку апаратного депакетизатора приймача:

#### 2.1. Короткі пакети синхронізації та сигналізації (`0x00..0x0F`)

Короткі пакети мають фіксовану довжину рівно 4 байти і не містять поля корисного навантаження (Payload). Поле `Data Field` (2 байти) переносить службові лічильники або системні параметри:

| Код DT (Hex) | Бінарний код | Назва типу | Призначення та формат поля Data Field (16 біт) |
| :--- | :--- | :--- | :--- |
| `0x00` | `000000` | **Frame Start (FS)** | Маркер початку нового відеокадру. Поле `Data Field` містить 16-бітний беззнаковий номер кадру (Frame Number), який інкрементується сенсором на 1 для кожного наступного кадру (діапазон від 1 до 65535, нульове значення означає, що апаратний лічильник кадрів у сенсорі вимкнено). |
| `0x01` | `000001` | **Frame End (FE)** | Маркер завершення передавання відеокадру. Поле `Data Field` містить той самий номер кадру, що й відповідний відкриваючий пакет `Frame Start`. Дозволяє системному драйверу контролювати втрату пакетів усередині кадру. |
| `0x02` | `000010` | **Line Start (LS)** | Опційний маркер початку рядка пікселів. Поле `Data Field` містить 16-бітний номер фізичного рядка в кадрі. |
| `0x03` | `000011` | **Line End (LE)** | Опційний маркер завершення рядка пікселів. Поле `Data Field` дублює номер завершеного рядка. |
| `0x04..0x07` | `000100..000111` | **Зарезервовано** | Зарезервовано стандартом для майбутніх розширень синхронізації кадрової структури. |
| `0x08..0x0F` | `001000..001111` | **Generic Short 1..8** | Універсальні короткі пакети для передавання команд реального часу, міток точного часу експозиції (Timestamp) або тригерів апаратної синхронізації спалаху чи лазерного підсвічування. Поле `Data Field` несе довільні 16 бітів інформації користувацького рівня. |

#### 2.2. Довгі пакети службових даних (`0x10..0x17`)

Довгі пакети службових даних використовуються для калібрування ліній зв'язку та передавання допоміжних метаданих камери:

| Код DT (Hex) | Бінарний код | Назва типу | Структура та призначення корисного навантаження (Payload) |
| :--- | :--- | :--- | :--- |
| `0x10` | `010000` | **Null Data** | Фіктивні байти довільного змісту. Використовуються передавачем для підтримки активності швидкісного каналу або заповнення часових пауз без перемикання ліній у режим низького споживання LP. |
| `0x11` | `010001` | **Blanking Data** | Дані інтервалів горизонтального та вертикального гасіння (H-Blank / V-Blank). Передаються для емуляції стандартних часових розгорток аналогових відеоінтерфейсів. |
| `0x12` | `010010` | **Embedded 8-bit Data** | Вбудовані метадані сенсора. Передаються на початку кадру (перед першим піксельним рядком) або наприкінці. Містять точні знімки конфігураційних регістрів матриці, значення поточної експозиції, аналогового підсилення (Gain), температури кристала та параметрів зони фокусування. |
| `0x13..0x17` | `010011..010111` | **Generic Long 1..5** | Довгі пакети спеціального призначення, структура яких визначається виробником конкретного сенсора або модуля стиснення. |

#### 2.3. Довгі пакети форматів колірності YUV (`0x18..0x1F`)

Формати із роздільним представленням яскравості (Y) та двох різницевих колірних складових (U/V, або Cb/Cr). Вони використовують фізіологічну властивість людського зору, який має значно вищу роздільну здатність до яскравості, ніж до кольору, що дозволяє суттєво зменшити обсяг передаваних даних:

| Код DT (Hex) | Бінарний код | Формат | Бітів / піксель | Порядок байтів у корисній частині (Payload) |
| :--- | :--- | :--- | :--- | :--- |
| `0x18` | `011000` | **YUV420 8-bit** | 12 | Парні рядки містять чергування відліків `Y0, U0, Y1, V0...`, непарні рядки містять виключно відліки яскравості `Y2, Y3, Y4, Y5...`. Колірні складові спільні для чотирьох сусідніх пікселів (квадрат 2×2). |
| `0x19` | `011001` | **YUV420 10-bit** | 15 | 10-бітне квантування яскравості та колірності з пакуванням по 5 байтів на кожні 4 відліки. |
| `0x1A` | `011010` | **YUV420 8-bit Legacy** | 12 | Застарілий стандарт черезрядкового чергування U/V, присутній для сумісності з ранніми мобільними чипсетами. |
| `0x1C` | `011100` | **YUV420 8-bit (CS)** | 12 | Формат зі зсунутою просторовою вибіркою колірності (Chroma Shifted) для точного збігу з сіткою кодеків H.264/HEVC. |
| `0x1D` | `011101` | **YUV420 10-bit (CS)** | 15 | 10-бітний варіант зі зсунутою колірністю. |
| `0x1E` | `011110` | **YUV422 8-bit** | 16 | Найпоширеніший стандарт для готового відео: горизонтальна субдискретизація колірності у 2 рази. Послідовність байтів: `U0, Y0, V0, Y1, U2, Y2, V2, Y3...` (рівно 2 байти на піксель). |
| `0x1F` | `011111` | **YUV422 10-bit** | 20 | Професійний 10-бітний потік: кожні 4 компоненти `U0, Y0, V0, Y1` займають рівно 5 байтів у лінії. |

#### 2.4. Довгі пакети форматів прямого кольору RGB (`0x20..0x27`)

Формати прямого передавання складових червоного, зеленого та синього каналів для сенсорів із внутрішнім блоком оброблення або дисплейних інтерфейсів:

| Код DT (Hex) | Бінарний код | Формат | Бітів / піксель | Порядок розміщення каналів у пам'яті |
| :--- | :--- | :--- | :--- | :--- |
| `0x20` | `100000` | **RGB444** | 16 (12 корисних) | Два байти на піксель: `[B3:B0, G3:G0], [R3:R0, 0000]`. Чотири молодші біти другого байта заповнюються нулями. |
| `0x21` | `100001` | **RGB555** | 16 (15 корисних) | Два байти на піксель: `[G2:G0, B4:B0], [0, R4:R0, G4:G3]`. Найстарший біт другого байта є нульовим. |
| `0x22` | `100010` | **RGB565** | 16 | Два байти на піксель: `[G2:G0, B4:B0], [R4:R0, G5:G3]`. Популярний формат для вбудованих дисплеїв із 6 бітами зеленого каналу. |
| `0x23` | `100011` | **RGB666** | 18 | 18 бітів на піксель: блок із 4 пікселів упаковується в 9 послідовних байтів. |
| `0x24` | `100100` | **RGB888** | 24 | Повноколірний 24-бітний потік: послідовність трьох байтів `B0, G0, R0, B1, G1, R1...` (синій канал передається першим). |

#### 2.5. Довгі пакети сирих даних сенсора RAW (`0x28..0x2F`)

Формати сирих відліків напруги з піксельних фотодіодів матриці Баєра, знятих безпосередньо з виходів внутрішніх аналого-цифрових перетворювачів (АЦП) сенсора. Це основний тип даних для сучасних високоякісних цифрових камер:

| Код DT (Hex) | Бінарний код | Формат | Розрядність АЦП | Коефіцієнт та схема пакування |
| :--- | :--- | :--- | :--- | :--- |
| `0x28` | `101000` | **RAW6** | 6 бітів | 4 пікселі упаковуються у 3 байти (24 біти). |
| `0x29` | `101001` | **RAW7** | 7 бітів | 8 пікселів упаковуються у 7 байтів (56 бітів). |
| `0x2A` | `101010` | **RAW8** | 8 бітів | 1 піксель = 1 байт (пряме побайтове відображення без змішування розрядів). |
| `0x2B` | `101011` | **RAW10** | 10 бітів | 4 пікселі упаковуються у 5 байтів (40 бітів). Головний мобільний формат сенсорів. |
| `0x2C` | `101100` | **RAW12** | 12 бітів | 2 пікселі упаковуються у 3 байти (24 біти). Стандарт для камер машинного зору та дронів. |
| `0x2D` | `101101` | **RAW14** | 14 бітів | 4 пікселі упаковуються у 7 байтів (56 бітів). Застосовується в професійній фототехніці. |
| `0x2E` | `101110` | **RAW16** | 16 бітів | 1 піксель = 2 байти (Little-Endian: молодший байт першим). |
| `0x2F` | `101111` | **RAW20** | 20 бітів | 2 пікселі упаковуються у 5 байтів (специфікація CSI-2 v2.0+ для наукових сенсорів). |

### 3. Бітові схеми розпакування даних (Pixel Unpacking Layouts)

Для досягнення 100% корисної завантаженості шини формати з розрядністю, некратною 8 бітам, упаковуються без порожніх бітів заповнення. Розглянемо точну побітову розкладку основних форматів.

#### 3.1. Пакування та розпакування RAW10 (`DT = 0x2B`)
Кожна четвірка сусідніх пікселів `P0, P1, P2, P3` (кожен розрядністю 10 бітів, разом 40 бітів) передається рівно за 5 послідовних байтів `B0..B4`:

```
БІТОВА РОЗКЛАДКА 5-БАЙТНОГО БЛОКУ RAW10:
Байт 0 (B0): [ P0[9] P0[8] P0[7] P0[6] P0[5] P0[4] P0[3] P0[2] ] -> Старші 8 бітів P0
Байт 1 (B1): [ P1[9] P1[8] P1[7] P1[6] P1[5] P1[4] P1[3] P1[2] ] -> Старші 8 бітів P1
Байт 2 (B2): [ P2[9] P2[8] P2[7] P2[6] P2[5] P2[4] P2[3] P2[2] ] -> Старші 8 бітів P2
Байт 3 (B3): [ P3[9] P3[8] P3[7] P3[6] P3[5] P3[4] P3[3] P3[2] ] -> Старші 8 бітів P3
Байт 4 (B4): [ P3[1:0] (біти 7:6) | P2[1:0] (біти 5:4) | P1[1:0] (біти 3:2) | P0[1:0] (біти 1:0) ]
```

Математичні рівняння попіксельного відновлення повних 10-бітних значень у конвеєрі приймача:
```
P0 = (B0 << 2) | ((B4 >> 0) & 0x03)
P1 = (B1 << 2) | ((B4 >> 2) & 0x03)
P2 = (B2 << 2) | ((B4 >> 4) & 0x03)
P3 = (B3 << 2) | ((B4 >> 6) & 0x03)
```

#### 3.2. Пакування та розпакування RAW12 (`DT = 0x2C`)
Кожна пара сусідніх пікселів `P0, P1` (по 12 бітів, разом 24 біти) передається 3 байтами `B0..B2`:

```
БІТОВА РОЗКЛАДКА 3-БАЙТНОГО БЛОКУ RAW12:
Байт 0 (B0): [ P0[11] P0[10] P0[9] P0[8] P0[7] P0[6] P0[5] P0[4] ] -> Старші 8 бітів P0
Байт 1 (B1): [ P1[11] P1[10] P1[9] P1[8] P1[7] P1[6] P1[5] P1[4] ] -> Старші 8 бітів P1
Байт 2 (B2): [ P1[3:0] (біти 7:4) | P0[3:0] (біти 3:0) ]            -> Молодші 4 біти P1 та P0
```

Математичні рівняння відновлення відліків:
```
P0 = (B0 << 4) | ((B2 >> 0) & 0x0F)
P1 = (B1 << 4) | ((B2 >> 4) & 0x0F)
```

#### 3.3. Розрахунок поля Word Count (WC)
Поле `Word Count` (2 байти) у заголовку довгого пакета задає точну кількість байтів корисного навантаження (Payload) в одному рядку. Для кадру з активною шириною `W` пікселів значення `WC` розраховується за формулами:

- **RAW8:** `WC = W` (ширина може бути довільною).
- **RAW10:** `WC = (W × 5) / 4` (ширина `W` обов'язково повинна бути кратною 4).
- **RAW12:** `WC = (W × 3) / 2` (ширина `W` обов'язково кратна 2).
- **RAW14:** `WC = (W × 7) / 4` (ширина `W` кратна 4).
- **RAW16 / YUV422 8-bit:** `WC = W × 2` (два байти на кожен піксель).
- **RGB888:** `WC = W × 3` (три байти на кожен піксель).

Наприклад, для стандартного сенсора з роздільною здатністю 1920 × 1080 у форматі RAW10 значення `Word Count` для кожного довгого пакета рядка складатиме:
```
WC = (1920 × 5) / 4 = 2400 байтів.
```

### 4. Алгоритм розрахунку та корекції ECC заголовка (Header ECC)

Поле ECC (байт 3 у заголовку Packet Header) формується за модифікованим кодом Хеммінга на основі 24 бітів даних заголовка: `D[7:0]` (байт DI), `D[15:8]` (молодший байт WC_L) та `D[23:16]` (старший байт WC_H).

Поле містить 6 бітів паритету `P[5:0]` та два фіксованих нульових біти: `ECC[7:0] = [0, 0, P5, P4, P3, P2, P1, P0]`.

Кожен біт парності обчислюється передавачем як сума за модулем 2 (XOR) від строго визначеної комбінації бітів даних заголовка:

```
МАТРИЦЯ РОЗРАХУНКУ БІТІВ ПАРИТЕТУ ХЕММІНГА:
P0 = D0 ⊕ D1 ⊕ D2 ⊕ D4 ⊕ D5 ⊕ D7 ⊕ D8 ⊕ D10 ⊕ D11 ⊕ D13 ⊕ D14 ⊕ D16 ⊕ D20 ⊕ D21 ⊕ D23
P1 = D0 ⊕ D1 ⊕ D3 ⊕ D4 ⊕ D6 ⊕ D7 ⊕ D9 ⊕ D10 ⊕ D12 ⊕ D13 ⊕ D15 ⊕ D17 ⊕ D20 ⊕ D22 ⊕ D23
P2 = D0 ⊕ D2 ⊕ D3 ⊕ D5 ⊕ D6 ⊕ D7 ⊕ D11 ⊕ D12 ⊕ D13 ⊕ D18 ⊕ D19 ⊕ D20 ⊕ D22 ⊕ D23
P3 = D1 ⊕ D2 ⊕ D3 ⊕ D8 ⊕ D9 ⊕ D10 ⊕ D11 ⊕ D12 ⊕ D13 ⊕ D14 ⊕ D15 ⊕ D18 ⊕ D19 ⊕ D21 ⊕ D22 ⊕ D23
P4 = D4 ⊕ D5 ⊕ D6 ⊕ D7 ⊕ D8 ⊕ D9 ⊕ D10 ⊕ D11 ⊕ D12 ⊕ D13 ⊕ D14 ⊕ D15 ⊕ D16 ⊕ D17 ⊕ D21 ⊕ D22 ⊕ D23
P5 = D16 ⊕ D17 ⊕ D18 ⊕ D19 ⊕ D20 ⊕ D21 ⊕ D22 ⊕ D23
```

#### Синдромний декодер та виправлення помилок приймачем
Приймач після десеріалізації заголовка заново обчислює контрольні біти `P_calc[5:0]` над прийнятими 24 бітами даних і знаходить вектор синдрому:

```
Syndrome[5:0] = P_received[5:0] ⊕ P_calc[5:0]
```

Логіка прийняття рішень апаратним блоком декодера:
1. **`Syndrome == 0x00`:** Заголовок прийнято без спотворень. Дані передаються в конвеєр оброблення.
2. **`Syndrome` відповідає одному з 24 унікальних кодів Хеммінга:** Зафіксовано 1-бітову помилку в полі даних `D[23:0]`. Таблиця відповідності однозначно визначає номер пошкодженого біта:
   - `0x07 → D0`, `0x0B → D1`, `0x0D → D2`, `0x0E → D3`, `0x13 → D4`, `0x15 → D5`, `0x16 → D6`, `0x19 → D7`
   - `0x1A → D8`, `0x1C → D9`, `0x23 → D10`, `0x25 → D11`, `0x26 → D12`, `0x29 → D13`, `0x2A → D14`, `0x2C → D15`
   - `0x31 → D16`, `0x32 → D17`, `0x34 → D18`, `0x38 → D19`, `0x1F → D20`, `0x2F → D21`, `0x37 → D22`, `0x3B → D23`
   Апаратний інвертор миттєво інвертує вказаний біт, виправляючи заголовок «на льоту», а лічильник виправлених помилок `ERR_ECC_CORRECTED` інкрементується.
3. **`Syndrome` дорівнює степеню двійки (`0x01, 0x02, 0x04, 0x08, 0x10, 0x20`):** Помилка виникла в самому перевірному біті `P[5:0]`. Дані заголовка не постраждали.
4. **Будь-яке інше ненульове значення синдрому:** Зафіксовано фатальну 2-бітову помилку (2-bit uncorrectable error). Пакет відкидається, а контролер генерує переривання.

### 5. Поліном і розрахунок CRC-16 для кінцевика (Packet Footer)

Контрольна сума кінцевика пакета розраховується над усіма `WC` байтами поля Payload за стандартом CRC-16-CCITT:

- **Генераторний поліном:** `P(x) = x¹⁶ + x¹² + x⁵ + 1` (шістнадцятковий двійковий коефіцієнт `0x1021`).
- **Початкове значення регістра (Init):** `0xFFFF`.
- **Порядок обробки бітів:** старший біт першим (MSB first) у кожному байті.
- **Порядок передавання на лінії:** молодший байт `CRC[7:0]` передається першим, старший байт `CRC[15:8]` — другим.

:::tabs
```c
#include <stdint.h>
#include <stddef.h>

// Побайтовий розрахунок CRC-16-CCITT для перевірки кінцевика CSI-2
uint16_t csi2_crc16_update(uint16_t crc, uint8_t byte) {
    crc ^= (uint16_t)((uint16_t)byte << 8);
    for (int i = 0; i < 8; i++) {
        if (crc & 0x8000) {
            crc = (uint16_t)((crc << 1) ^ 0x1021);
        } else {
            crc = (uint16_t)(crc << 1);
        }
    }
    return crc;
}

// Пакетний розрахунок контрольної суми над усім масивом Payload
uint16_t csi2_calc_payload_crc(const uint8_t *payload, size_t word_count) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < word_count; i++) {
        crc = csi2_crc16_update(crc, payload[i]);
    }
    return crc;
}
```
```cpp
#include <cstdint>
#include <cstddef>
#include <span>

namespace mipi::csi2 {

// Побайтовий розрахунок CRC-16-CCITT для перевірки кінцевика CSI-2
constexpr uint16_t crc16_update(uint16_t crc, uint8_t byte) noexcept {
    crc ^= static_cast<uint16_t>(static_cast<uint16_t>(byte) << 8);
    for (int i = 0; i < 8; ++i) {
        if (crc & 0x8000) {
            crc = static_cast<uint16_t>((crc << 1) ^ 0x1021);
        } else {
            crc = static_cast<uint16_t>(crc << 1);
        }
    }
    return crc;
}

// Пакетний розрахунок контрольної суми над усім масивом Payload
constexpr uint16_t calculate_payload_crc(std::span<const uint8_t> payload) noexcept {
    uint16_t crc = 0xFFFF;
    for (uint8_t byte : payload) {
        crc = crc16_update(crc, byte);
    }
    return crc;
}

} // namespace mipi::csi2
```

### 6. Карта регістрів апаратного контролера MIPI CSI-2 RX

Апаратний блок прийому MIPI CSI-2 у складі сучасних систем на кристалі (SoC) надає програмному драйверу інтерфейс конфігурації, діагностики та оброблення переривань через наступний базовий набір регістрів:

| Зсув (Offset) | Назва регістру | Доступ | Призначення та бітові поля |
| :--- | :--- | :--- | :--- |
| `0x00` | **CSI2_CTRL** | R/W | Керування ядром контролера: `bit[0]` — Enable (увімкнення конвеєра прийому); `bit[1]` — Soft Reset (програмне скидання автоматів станів); `bit[3:2]` — Кількість активних ліній даних (00: 1 lane, 01: 2 lanes, 11: 4 lanes); `bit[4]` — Автоматичне маскування пошкоджених рядків із помилкою CRC. |
| `0x04` | **CSI2_STATUS** | RO | Фізичний стан ліній D-PHY: `bit[3:0]` — Прапорці зупинки ліній даних `Data0..Data3` у пасивному стані Stop State (`LP-11`); `bit[4]` — Прапорець тактової лінії `Clock Lane` у стані `LP-11`; `bit[5]` — Режим ультранизького споживання (ULPS active). |
| `0x08` | **CSI2_INT_STATUS** | W1C | Регістр переривань (скидається записом одиниці): `bit[0]` — Прийнято пакет Frame Start; `bit[1]` — Прийнято пакет Frame End; `bit[8]` — Виправлено 1-бітову помилку ECC в заголовку; `bit[9]` — Зафіксовано фатальну 2-бітову помилку ECC; `bit[16]` — Помилка контрольної суми CRC-16; `bit[20]` — Переповнення внутрішньої черги асинхронного переходу тактових доменів (CDC FIFO Overflow). |
| `0x0C` | **CSI2_INT_MASK** | R/W | Маска дозволу генерації системних переривань для процесора. Бітове відображення відповідає структурі `CSI2_INT_STATUS`. |
| `0x10` | **CSI2_VC_FILTER** | R/W | Фільтрація віртуальних каналів: біти `[3:0]` дозволяють проходження пакетів із відповідними номерами `VC0..VC3` у системну пам'ять або конвеєр ISP. Пакети інших каналів автоматично відкидаються без переривань. |
| `0x14` | **CSI2_FRAME_NUM** | RO | Поточний номер кадру, зчитаний із поля `Data Field` останнього прийнятого короткого пакета Frame Start. |
| `0x18` | **CSI2_LINE_NUM** | RO | Номер поточного рядка кадру. |
| `0x1C` | **CSI2_ERR_ECC_CNT** | RO | 16-бітний апаратний лічильник відновлених однобітових помилок ECC. Дозволяє оцінити рівень завад на шині. |
| `0x20` | **CSI2_ERR_CRC_CNT** | RO | 16-бітний лічильник відкинутих довгих пакетів із помилкою CRC-16. |
