# ⚙️ Ядро тренування як пошук: розгортка, карта P/F і посадка в центр

Уся фізика калібрування DDR — лінії затримки, строби, пороги, відбиття — зводиться, коли доходить до прошивки, до напрочуд скромного шматка коду. Скінченний автомат тренування не «розуміє» ока сигналу й не міряє наносекунд. Він крутить одну ручку — код затримки чи код порога, — щоразу питає канал одне-єдине «збіглося?», складає відповіді в масив і шукає в цьому масиві найширшу суцільну смугу успіхів, щоб сісти в її середину. Оце і все ядро. Решта — обгортка навколо нього: команди DRAM, регістри режиму, тонкощі конкретного PHY.

Тут ми напишемо це ядро цілком — робочим C, який можна перенести в прошивку майже без змін, — і, що важливіше, розберемо, **де воно ламається**. Бо наївна версія «знайди першу одиницю, знайди останню, візьми середину» пише сама собою за п'ять хвилин і працює на ідеальній платі в лабораторії. А на реальній вона тихо ставить робочу точку не туди — і система, що бездоганно бігала на столі, розсипається в нагрітому корпусі. Різниця між цими двома версіями — рівно три граничні випадки й дві пастки, і кожен коштував комусь дня за осцилографом.

## Задача: перетворити «крути й міряй» на код, що не бреше

Сформулюймо контракт. Нам дано дві речі, і обидві — від конкретного заліза.

Перша — **актуатор**: спосіб виставити ручку в задане ціле значення. Для затримки строба це запис коду в регістр лінії затримки PHY; діапазон — від 0 до якогось `range_max` (типово кілька десятків або сотень кроків, кожен по кілька пікосекунд). Для порога VREF — запис коду в регістр MR6 самого чіпа. Нас не обходить, що там усередині: ми лише кажемо «стань на код `k`».

Друга — **пробник** (англ. *probe*): спосіб дізнатися, чи працює канал за поточної ручки. Він робить одне — жене крізь канал наперед відомий взірець і повертає `true`, якщо прочитане збіглося з еталоном, `false`, якщо ні. Як саме — залежить від кроку: під час центрування читання це «читай із регістрів MPR і порівняй», під час запису — «запиши взірець, перечитай, порівняй», під час вирівнювання запису — «поглянь на біт, що чіп повернув на DQ». Ядро пошуку про це не знає й знати не повинно.

Тобто інтерфейс до заліза — рівно дві функції, і на них тримається все:

:::tabs
```cpp
#include <cstdint>

// Виставити ручку (код затримки / порога) у ціле значення code.
// Реалізація — запис у регістр конкретного PHY чи чіпа.
void knob_set(int code);

// Прогнати відомий взірець крізь канал за поточної ручки й порівняти.
// true  = прочитане == еталон (pass),
// false = хоч один біт розійшовся (fail).
bool probe_once();
```
```python
# Виставити ручку (код затримки / порога) у ціле значення code.
# Реалізація — запис у регістр конкретного PHY чи чіпа.
def knob_set(code: int) -> None: ...

# Прогнати відомий взірець крізь канал за поточної ручки й порівняти.
# True  = прочитане == еталон (pass),
# False = хоч один біт розійшовся (fail).
def probe_once() -> bool: ...
```
:::

Усе, що нижче, спирається **тільки** на ці дві функції. Це не випадковість, а сама суть підходу з [материнської теми](book:electronics/memory-training): невимірний аналоговий тракт логіка бачить лише крізь вузьку щілину `probe_once()` — один біт за раз, — а далі працює зі здобутими бітами як зі звичайним масивом. Відділивши пошук від заліза, ми дістаємо код, який однаковий для DDR3, DDR4 і LPDDR: міняється реалізація двох функцій, ядро лишається те саме.

> 🔧 **Навіщо це.** Ця пара `knob_set` / `probe_once` — не навчальне спрощення, а те, як пишуть справжні тренувальні бібліотеки в завантажувачах (U-Boot, coreboot, вендорські BLOB). Пошук центру ока не залежить від того, ЩО за ручка й ЯК влаштований пробник, тож його виносять у спільну процедуру, а під кожен крок підставляють свою пару функцій-заглушок до заліза. Наплутаєте тут — і замість одного ядра, вивіреного раз, матимете десяток копій «знайди середину», кожну зі своїм набором власних багів у граничних випадках.

## Крок нуль: розгортка — зібрати карту P/F

Найперше — обійти весь діапазон ручки й для кожного значення записати `true`/`false`. Це буквальний переклад слова «розгортка» (англ. *sweep*) у код: цикл від 0 до `range_max`, на кожному кроці поставити ручку, дати каналу заспокоїтися, опитати пробник.

:::tabs
```cpp
constexpr int RANGE_MAX = 64;    // скільки кодів у ручки (0 .. RANGE_MAX-1)

// Заповнює map[i] результатом пробника за коду затримки i.
// Повертає кількість зібраних точок (== RANGE_MAX).
int sweep(bool map[], int range_max)
{
    for (int code = 0; code < range_max; code++) {
        knob_set(code);          // виставили ручку
        settle();                // пауза на встановлення лінії затримки
        map[code] = probe_once();
    }
    return range_max;
}
```
```python
RANGE_MAX = 64                   # скільки кодів у ручки (0 .. RANGE_MAX-1)

# Заповнює map[i] результатом пробника за коду затримки i.
# Повертає зібрану карту (довжиною range_max).
def sweep(range_max: int) -> list[bool]:
    pf_map = [False] * range_max
    for code in range(range_max):
        knob_set(code)           # виставили ручку
        settle()                 # пауза на встановлення лінії затримки
        pf_map[code] = probe_once()
    return pf_map
```
:::

Дрібниця, яку легко проґавити й яка коштує найдовше: **`settle()`**. Лінія затримки перемикається не миттєво — усередині PHY це ланцюжок керованих елементів, і після зміни коду сигнал якийсь час «дзвенить», поки не влаштується на новій затримці. Опитаєте пробник, поки триває цей перехід, — дістанете `false` там, де насправді вже `true`, і карта збрешеться саме на межах вікна, де кожна точка на вагу золота. Тому між `knob_set` і `probe_once` завжди мусить бути коротка витримка (від одиниць до десятків тактів, залежно від PHY). У наївній версії її забувають першою.

Друга дрібниця — **надійність одного вимірювання**. `probe_once()` гоняє скінченний взірець (скажімо, 8 чи 64 біти). Якщо канал на межі, одна помилка на мільйон бітів може й не трапитися за цей один прогін — і точка, що насправді на самому краю ока, покажеться `true`. Тому серйозний пробник жене **довший або повторюваний** взірець: не один раз, а кілька, і зараховує `pass`, лише якщо збіглося **щоразу**. Це прямо розширює або звужує знайдене вікно, тож довжину взірця беруть не наздогад, а з бюджету надійності. Але для ядра пошуку це вже всередині `probe_once` — воно бачить лише підсумковий біт.

Після розгортки в `map[]` лежить те, заради чого все й затівалося: рядок `P` і `F`, розмічена вісь ручки. Далі — чиста робота з масивом, заліза більше не торкаємось.

## Наївне ядро — і чому воно бреше

Спокуса написати так:

:::tabs
```cpp
// НАЇВНО, НЕ ВЖИВАТИ: перша й остання одиниця, середина між ними.
int center_naive(const bool map[], int n)
{
    int lo = 0;
    while (lo < n && !map[lo]) lo++;      // перша P
    int hi = n - 1;
    while (hi >= 0 && !map[hi]) hi--;     // остання P
    return (lo + hi) / 2;                 // «центр»
}
```
```python
# НАЇВНО, НЕ ВЖИВАТИ: перша й остання одиниця, середина між ними.
def center_naive(pf_map: list[bool]) -> int:
    n = len(pf_map)
    lo = 0
    while lo < n and not pf_map[lo]:      # перша P
        lo += 1
    hi = n - 1
    while hi >= 0 and not pf_map[hi]:     # остання P
        hi -= 1
    return (lo + hi) // 2                 # «центр»
```
:::

На ідеальній карті `FFFPPPPPPPFF` це дає правильну відповідь. І саме тому воно небезпечне: працює рівно доти, доки карта ідеальна. А реальна карта майже ніколи не буває ідеальною. Ось три способи, якими вона підкладає свиню, і кожен розберемо з кодом.

![Три рядки карти P/F, кожен з яких ламає наївний пошук: A — вікно впирається в лівий край діапазону, тож істинного центру за межею не видно; B — два окремі вікна, треба брати ширше, а не перше; C — одиничний F усередині вікна від шуму на межі, не сплутати зі справжнім краєм](img/pf-map-cases.svg)
*Чому «перша й остання одиниця» не годиться. Рядок A: смуга P притиснута до краю діапазону — наївний центр з'їжджає до стінки, бо справжня середина ока лежить за межею, куди ручка не дотягується. Рядок B: два розділені вікна; беручи «першу P … останню P», наївний код обрахує центр між ними — у мертвій зоні F. Рядок C: одна помилка-провал усередині суцільного вікна (шум на самій межі); наївний «останню P» це не зачепить, але будь-який пошук найширшої смуги спіткнеться об цей F і розколе одне широке вікно на два вузькі. Справжнє ядро мусить пережити всі три.*

Наївна версія падає на кожному з трьох рядків по-своєму. На рядку B вона обрахує `(lo+hi)/2` між двома вікнами — і посадить строб у зону `F`, де канал гарантовано не працює: гірше годі й вигадати. На рядку C, якщо додати наївний захист «шукаю найдовшу смугу», одиничний `F` розколе широке вікно на два вузькі, і код обере вужче, ніж мусив. На рядку A навіть правильний пошук чесно повідомить центр, не знаючи, що справжня середина ока — за стінкою діапазону. Полагодьмо по черзі.

## Правильне ядро: найширше суцільне вікно й межа-край

Правильна ідея — не «перша й остання одиниця», а **найширша суцільна смуга одиниць**. Пройдімо масив одним проходом, ведучи поточну смугу `P` і запам'ятовуючи найкращу. Це класичний прохід «поточний відрізок проти найкращого», рідня [пошуку максимума одним проходом](book:algorithms/binary-search) — лінійний, без жодного зайвого перебору.

:::tabs
```cpp
struct Window {
    int lo;        // індекс першої P у вікні
    int hi;        // індекс останньої P у вікні
    int width;     // hi - lo + 1; 0 = вікна нема (усе F)
};

// Знаходить НАЙШИРШЕ суцільне вікно P у map[0..n-1].
Window widest_window(const bool map[], int n)
{
    Window best = { -1, -1, 0 };
    int cur_lo = -1;                       // початок поточної смуги, -1 = поза смугою

    for (int i = 0; i < n; i++) {
        if (map[i]) {
            if (cur_lo < 0) cur_lo = i;    // смуга щойно почалась
            int w = i - cur_lo + 1;
            if (w > best.width) {          // поточна побила рекорд — зберігаємо
                best.lo = cur_lo;
                best.hi = i;
                best.width = w;
            }
        } else {
            cur_lo = -1;                   // смуга обірвалась
        }
    }
    return best;                           // best.width == 0, якщо жодної P
}
```
```python
from dataclasses import dataclass

@dataclass
class Window:
    lo: int        # індекс першої P у вікні
    hi: int        # індекс останньої P у вікні
    width: int     # hi - lo + 1; 0 = вікна нема (усе F)

# Знаходить НАЙШИРШЕ суцільне вікно P у pf_map[0..n-1].
def widest_window(pf_map: list[bool]) -> Window:
    best = Window(-1, -1, 0)
    cur_lo = -1                            # початок поточної смуги, -1 = поза смугою

    for i, cell in enumerate(pf_map):
        if cell:
            if cur_lo < 0:
                cur_lo = i                 # смуга щойно почалась
            w = i - cur_lo + 1
            if w > best.width:             # поточна побила рекорд — зберігаємо
                best.lo = cur_lo
                best.hi = i
                best.width = w
        else:
            cur_lo = -1                    # смуга обірвалась
    return best                            # best.width == 0, якщо жодної P
```
:::

Це вже переживає рядок B: два вікна виявляються обидва, і `best` лишається на ширшому — саме тому порівняння `w > best.width` бере **строго** ширше й не перескакує на пізніше вікно тієї самої ширини (перше з рівних стабільніше). Тепер центр беремо **тільки всередині знайденого вікна**:

:::tabs
```cpp
// Головна процедура: розгорнути, знайти вікно, повернути його центр.
// Повертає код ручки для посадки, або -1, якщо робочого вікна нема взагалі.
int find_center()
{
    bool map[RANGE_MAX];
    int n = sweep(map, RANGE_MAX);

    Window w = widest_window(map, n);
    if (w.width == 0) {
        return -1;                         // жодної робочої точки — канал мертвий
    }
    return (w.lo + w.hi) / 2;              // центр САМЕ цього вікна
}
```
```python
# Головна процедура: розгорнути, знайти вікно, повернути його центр.
# Повертає код ручки для посадки, або -1, якщо робочого вікна нема взагалі.
def find_center() -> int:
    pf_map = sweep(RANGE_MAX)

    w = widest_window(pf_map)
    if w.width == 0:
        return -1                          # жодної робочої точки — канал мертвий
    return (w.lo + w.hi) // 2              # центр САМЕ цього вікна
```
:::

Ось перша по-справжньому важлива різниця з наївним кодом: центр рахується від `w.lo` і `w.hi` **одного** вікна, а не від першої й останньої одиниці на всій осі. На рядку B це вже дає точку в серці широкого вікна, а не в мертвій зоні між двома.

І окремо — повернення `-1`. Наївний код цього випадку взагалі не мав: якщо жодної `P`, `while` добіжить до кінця, `lo` стане `n`, `hi` стане `-1`, і `(lo+hi)/2` видасть якесь безглузде число, яке автомат мовчки запише в затримку. Правильне ядро **мусить** відрізняти «знайшов вузьке вікно» від «не знайшов нічого»: порожнє вікно — це не робоча точка на краю, а сигнал «стоп, тренування провалилось, канал не заведеться». Пропустиш цю перевірку — і замість чесної помилки дістанеш систему, що стартувала з випадковою затримкою й падає незрозуміло де.

### Край діапазону: коли око не влазить у ручку

Рядок A — тонший. Уявімо, що справжнє око широке, а діапазон ручки короткий: вікно `P` доходить до самого краю масиву й обривається не тому, що там край ока, а тому, що там **кінець діапазону затримки**. Наш `widest_window` чесно знайде смугу `PPPPP` від індексу 0, порахує центр десь усередині неї — але це **не** центр ока. Справжня середина лежить за стінкою, куди ручка фізично не дотягується.

Так само буває, коли смуга впирається у **правий** край (`i == n-1`). Це не помилка коду — це фізичний факт про плату: діапазону затримки не вистачає, щоб охопити все око, тож ми бачимо лише його шматок. Небезпека в тому, що центр обрізаного шматка ближчий до однієї стінки, ніж треба, — запас із того боку менший, і саме туди першою поповзе робоча точка на спеці.

Правильна поведінка — **не мовчати про це**. Ядро має розрізняти вікно, обидва краї якого — справжні межі ока (усередині діапазону), і вікно, що торкається стінки:

:::tabs
```cpp
enum WinKind {
    WIN_OK,          // обидва краї вікна — справжні межі ока
    WIN_CLIP_LO,     // вікно впирається у код 0 — око тягнеться нижче діапазону
    WIN_CLIP_HI,     // вікно впирається у range_max-1 — око тягнеться вище
    WIN_NONE         // вікна нема (усе F)
};

WinKind classify(Window w, int n)
{
    if (w.width == 0)          return WIN_NONE;
    if (w.lo == 0)             return WIN_CLIP_LO;   // почалось на самому краю
    if (w.hi == n - 1)         return WIN_CLIP_HI;   // дійшло до самого краю
    return WIN_OK;
}
```
```python
from enum import Enum, auto

class WinKind(Enum):
    WIN_OK = auto()       # обидва краї вікна — справжні межі ока
    WIN_CLIP_LO = auto()  # вікно впирається у код 0 — око тягнеться нижче діапазону
    WIN_CLIP_HI = auto()  # вікно впирається у range_max-1 — око тягнеться вище
    WIN_NONE = auto()     # вікна нема (усе F)

def classify(w: Window, n: int) -> WinKind:
    if w.width == 0:       return WinKind.WIN_NONE
    if w.lo == 0:          return WinKind.WIN_CLIP_LO   # почалось на самому краю
    if w.hi == n - 1:      return WinKind.WIN_CLIP_HI   # дійшло до самого краю
    return WinKind.WIN_OK
```
:::

Що робити з `WIN_CLIP_*` — рішення рівня системи, не ядра. Іноді край терпимий: діапазон ручки в цьому PHY просто ширший за потрібне рідко, і клип на кілька кодів означає, що запас усе одно величезний. Іноді це симптом грубої помилки — не та довжина доріжки, не той код грубого зсуву, — і тренування має зупинитись із діагностикою «око не вміщується, перевір розводку». Але щоб **ухвалити** це рішення, автомат мусить спершу **знати** про клип — а наївна «середина між першою й останньою» його ховає. Отут різниця між кодом, що бреше тихо, і кодом, що каже правду.

> 🔧 **Навіщо це.** Клип вікна об край діапазону — улюблена причина «плата працює через раз». PHY має скінченний діапазон затримки; якщо доріжка розведена так, що потрібний зсув близький до стінки, око опиняється напівза межею, видимий шматок вузький, центр обрізаний — і на температурі точка з'їжджає за край. Симптом підступний: холодна плата стартує, гаряча падає; одна планка з партії ловить, сусідня — ні. Код, що повертає `WIN_CLIP_HI` замість тихого числа, дає інженерові зачіпку одразу, а не після тижня з термофеном.

## Шумова межа: одиничний F усередині вікна

Найпідступніший — рядок C. У ньому серед суцільного вікна сидить один-єдиний `F`: `PPPPP F PPPPPPP`. Звідки він? З того, що око не має різкої стінки — воно **розмивається** до країв. Ближче до межі надійність падає плавно, і там, де `pass` уже не стовідсотковий, окрема точка може випадково провалитись, поки сусідні тримаються. Це не справжній край ока — це **шум на межі**, статистичне тремтіння одного вимірювання.

Для `widest_window` цей одинокий `F` — катастрофа: він обриває смугу, і замість одного широкого вікна код бачить два вужчі. Центр обраного стає зсунутим, запас — заниженим. А іноді гірше: якщо шумовий `F` рівно посередині, обидві половинки виходять однакові й вузькі, і код обирає геть не ту точку.

Лікують це **згладжуванням** карти перед пошуком вікна. Ідея проста: справжній край ока — це коли `F` йдуть **підряд**, а не поодинці. Тому дірку в одну (чи задану кількість) клітинку, оточену з обох боків одиницями, вважаємо шумом і затираємо назад у `P`. Тільки суцільна смуга `F` завдовжки більш ніж `gap` рахується справжнім краєм.

:::tabs
```cpp
// Замазує «діри» з F завдовжки <= max_gap, оточені P з обох боків:
// такі короткі провали — шум на межі ока, а не справжній край.
// map правиться на місці.
void despeckle(bool map[], int n, int max_gap)
{
    int i = 0;
    while (i < n) {
        if (map[i]) { i++; continue; }

        int j = i;                         // початок смуги F
        while (j < n && !map[j]) j++;      // j — перша P після смуги (або n)
        int gap = j - i;                   // довжина смуги F

        bool bounded = (i > 0) && (j < n); // P ліворуч І P праворуч
        if (bounded && gap <= max_gap) {
            for (int k = i; k < j; k++)    // коротка внутрішня діра — затерти
                map[k] = true;
        }
        i = j;                             // йдемо далі від кінця смуги
    }
}
```
```python
# Замазує «діри» з F завдовжки <= max_gap, оточені P з обох боків:
# такі короткі провали — шум на межі ока, а не справжній край.
# pf_map правиться на місці.
def despeckle(pf_map: list[bool], max_gap: int) -> None:
    n = len(pf_map)
    i = 0
    while i < n:
        if pf_map[i]:
            i += 1
            continue

        j = i                              # початок смуги F
        while j < n and not pf_map[j]:     # j — перша P після смуги (або n)
            j += 1
        gap = j - i                        # довжина смуги F

        bounded = (i > 0) and (j < n)      # P ліворуч І P праворуч
        if bounded and gap <= max_gap:
            for k in range(i, j):          # коротка внутрішня діра — затерти
                pf_map[k] = True
        i = j                              # йдемо далі від кінця смуги
```
:::

Тепер конвеєр повний:

:::tabs
```cpp
int find_center_robust(int max_gap)
{
    bool map[RANGE_MAX];
    int n = sweep(map, RANGE_MAX);

    despeckle(map, n, max_gap);            // прибрати шумові провали
    Window w = widest_window(map, n);

    switch (classify(w, n)) {
    case WIN_NONE:
        return -1;                         // канал не заводиться
    case WIN_CLIP_LO:
    case WIN_CLIP_HI:
        report_clip();                     // діагностика: око за межею діапазону
        break;                             // (рішення — далі; тут беремо що є)
    case WIN_OK:
        break;
    }
    return (w.lo + w.hi) / 2;
}
```
```python
def find_center_robust(max_gap: int) -> int:

    if kind is WinKind.WIN_NONE:
        return -1                          # канал не заводиться

                                           # (рішення — далі; тут беремо що є)
    # WIN_OK — нічого додатково не робимо
    return (w.lo + w.hi) // 2
```
:::

Але тут причаїлась зворотна пастка, і про неї треба сказати прямо. `despeckle` замазує діри — а що, як діра **справжня**? Що, як вікно й правда розколоте фізично (два окремі просвіти від якогось резонансу в тракті), і `F` посередині — не шум, а реальна межа? Тоді агресивне згладжування **зліпить** два вікна в одне фальшиве й посадить строб у мертву зону між ними — рівно та біда, від якої ми тікали на рядку B, тільки тепер ми її самі й створили.

Тому `max_gap` — не декоративний параметр, а **тонке налаштування під конкретне залізо**. Ставлять його малим — 1, зрідка 2, — рівно щоб покрити поодиноке тремтіння межі, і **ніколи** настільки великим, щоб перекрити реальну мертву зону. А ще краще — не гадати про поодинокі точки взагалі, а зробити пробник надійнішим (довший взірець, повтори), щоб шумових `F` просто не було в карті. Згладжування — це латка на недосконале вимірювання; де можна зміряти чесніше, там воно й не потрібне.

> 🔧 **Навіщо це.** Це та межа, де «зроби код терплячішим до шуму» перетворюється на «код бреше по-новому». Замазав `max_gap=3` — і одиничні провали зникли, карта гарна, тренування завжди «успішне»… аж поки на якійсь платі два вікна справді розійшлись, згладжування їх зліпило, строб сів у діру, і система падає з ідеально «пройденим» калібруванням. Правило залізне: `max_gap` тримати мінімальним і радше вкладатись у надійніший пробник, ніж у ширшу гумку. Латка на вимірювання не повинна ставати джерелом нового мовчазного багу.

## Монотонний випадок: вирівнювання запису без розгортки всього

Досі ручка давала **вікно** — смугу `P` між двома краями. Але один крок тренування влаштований інакше, і на ньому все ядро вище — надлишкове. Це **вирівнювання запису** (англ. *write leveling*), докладно описане в [материнській темі](book:electronics/memory-training): PHY суне затримку строба DQS, а чіп у спеціальному режимі щоразу защіпає рівень такту CK у мить фронту строба й вертає його на DQ. Поки строб клацає раніше за фронт CK — відповідь `0`; щойно наздогнав — `1`. Відповідь **монотонна**: спершу суцільні `0`, потім суцільні `1`, і між ними один-єдиний стрибок. Це усталений механізм DDR3/DDR4: DRAM у режимі write leveling видає на DQ рівень CK, спійманий фронтом DQS, а контролер малими кроками рухає DQS, доки не побачить перехід `0 → 1`.

Тут немає вікна й немає центру — є **єдина точка переходу**. І перебирати заради неї весь діапазон марнотратно: коли функція монотонна (спершу все `0`, потім усе `1`), точку зламу знаходять **навпіл**, [бінарним пошуком](book:algorithms/binary-search). Дивимось на середину діапазону: якщо там `0`, злам правіше — відкидаємо ліву половину; якщо `1`, злам не правіше — відкидаємо праву. За кілька кроків замість десятків локалізуємо перехід із точністю до одного коду.

:::tabs
```cpp
// Пробник для монотонного випадку: true, якщо за коду затримки
// чіп повернув рівень CK == 1 (строб уже наздогнав фронт).
bool probe_ck_is_high(int code)
{
    knob_set(code);
    settle();
    return probe_once();     // тут probe_once читає біт, повернений чіпом на DQ
}

// Бінарний пошук першого коду, за якого відповідь стала 1
// (перехід 0 -> 1) на монотонній осі 0 .. range_max-1.
// Повертає цей код, або range_max, якщо 1 не з'явилась узагалі.
int find_transition(int range_max)
{
    int lo = 0, hi = range_max;           // шукаємо в [lo, hi): перший code з '1'
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;     // так безпечніше від переповнення
        if (probe_ck_is_high(mid))
            hi = mid;                      // '1' тут — межа не правіше mid
        else
            lo = mid + 1;                  // '0' тут — межа строго правіше
    }
    return lo;                             // перший код з '1'; == range_max, якщо '1' нема
}
```
```python

# (перехід 0 -> 1) на монотонній осі 0 .. range_max-1.
# Повертає цей код, або range_max, якщо 1 не з'явилась узагалі.
def find_transition(range_max: int) -> int:
    lo, hi = 0, range_max                 # шукаємо в [lo, hi): перший code з '1'
    while lo < hi:
        mid = lo + (hi - lo) // 2         # так безпечніше від переповнення
        if probe_ck_is_high(mid):
            hi = mid                       # '1' тут — межа не правіше mid
        else:
            lo = mid + 1                   # '0' тут — межа строго правіше
    return lo                             # перший код з '1'; == range_max, якщо '1' нема
```
:::

Це той самий інваріант, що й у будь-якому чесному бінарному пошуку межі: у напіввідкритому проміжку `[lo, hi)` завжди тримаємо `lo` на території `0`, `hi` — на території `1` (або за краєм). `mid = lo + (hi-lo)/2` замість `(lo+hi)/2` — не педантизм: на широких діапазонах і 32-бітних лічильниках `lo+hi` може переповнитись, а цей запис — ніколи. І умова циклу `lo < hi` (не `<=`) із напіввідкритим `[lo, hi)` не дає ні зациклитись, ні промахнутись повз останній код.

Але два застереження, без яких бінарний пошук тут **зламається мовчки**, і обидва — про припущення монотонності.

Перше: він **вимагає** справжньої монотонності. Якби на осі write leveling трапився шумовий `1` серед `0` (тремтіння межі, як на рядку C), бінарний пошук міг би застрибнути на нього й повернути хибний перехід — і жодного натяку, що щось не так, бо він не бачить усієї карти, лише окремі точки. Тому саме тут пробник має бути особливо надійним (кілька фронтів, зараховуємо `1`, лише коли стабільно `1`), або перехід **підтверджують** контрольним зчитуванням сусідніх кодів після знахідки. Швидкість бінарного пошуку — плата за довіру до монотонності; де довіри нема, повертаються до повної розгортки, яка бачить усю картину й переживає одиничний збій.

Друге: якщо `1` не з'явилась **зовсім** (строб не наздогнав фронт навіть на максимальній затримці), код чесно поверне `range_max` — сигнал «переходу в діапазоні нема». Це, як і порожнє вікно вище, треба ловити окремо: це не «межа скраю», а «тренування не зійшлося, дивись розводку CK/DQS». Не перевіриш — і автомат візьме `range_max` за валідну затримку.

## Складність і бюджет: скільки це коштує на старті

Тепер порахуймо ціну, бо тренування — частина ввімкнення живлення, і кожен крок множиться на кількість ліній та рангів пам'яті.

**Час.** Повна розгортка — це `range_max` викликів пробника, тобто **O(range_max)** прогонів взірця. Кожен прогін — не безкоштовний: це запис і читання цілого взірця через фізичну шину плюс `settle()`. Для `range_max = 64` і взірця в кілька сотень нанос­екунд один крок тренування на одній лінії — десятки мікросекунд. Помножте на 8–16 ліній DQ, на кілька типів тренування (захоплення строба, читання, запис, VREF) і на кілька рангів — і набігають **мілісекунди**, ті самі, через які машина «думає» після ввімкнення. Ось чому монотонні кроки віддають бінарному пошуку: **O(log range_max)** замість O(range_max) — для 64 кодів це 6 прогонів замість 64, і на масштабі всієї шини економія відчутна. Правило просте: **є вікно — повна розгортка** (треба бачити обидва краї); **є монотонний перехід — бінарний пошук** (досить однієї точки).

**Пам'ять.** Карта — це `range_max` булевих значень. Наївно `bool[64]` — 64 байти на лінію; хочете тісніше — пакуйте в бітову маску (`uint64_t` на всю вісь, якщо `range_max ≤ 64`), і тоді пошук найширшого вікна стає грою з бітами. Для завантажувача, де ОЗП іще толком нема (пам'ять же саме калібрують!), ця економія не абстрактна: карту часто тримають у крихітному вбудованому SRAM чи навіть у регістрах, і зайвий кілобайт має значення.

**Двовимірний випадок.** Центрування VREF розгортає **дві** ручки — затримку й поріг, — і карта стає площиною (шму-графік із [материнської теми](book:electronics/memory-training)). Наївно це `range_delay × range_vref` прогонів — квадрат, найдорожчий крок усього тренування. Тому його не женуть тупим суцільним переліком: спершу центрують затримку при одному VREF, тоді VREF при знайденій затримці, і лише навколо цієї точки уточнюють дрібну ділянку площини. «Найглибша точка острова» шукається не обходом кожної клітинки, а розумним звуженням — але базова цеглинка та сама `probe_once`, лише викликана в двовимірному циклі.

## Пастки, зібрані докупи

Наприкінці — чек-лист, кожен пункт якого вже коштував комусь дня в лабораторії. Це різниця між «написав center за п'ять хвилин» і «написав center, що працює на реальному залізі».

- **Забув `settle()`.** Опитав пробник, поки лінія затримки ще перемикається, — карта збрехала на межах вікна, центр з'їхав. Пауза між `knob_set` і `probe_once` — обов'язкова, і саме її викидають першою «для швидкості».

- **Надто грубий крок розгортки.** Якщо ручка має тонкі кроки, а ви розгортаєте через один (щоб було швидше), вузьке око можна **перестрибнути цілком**: між двома вашими пробами воно відкрилось і закрилось, обидві точки лягли `F`, і код вирішив, що вікна нема — або знайшов сусіднє, ширше й гірше. Швидка розгортка приховує саме ті марґінальні канали, заради яких тренування й потрібне. Крок беруть не за зручністю, а достатньо дрібним, щоб найвужче очікуване око дало хоч кілька `P`.

- **Шумова межа злиплась із рішенням.** Одиничні `F` від тремтіння краю або замазують надто агресивним `despeckle` (і зліплюють реальні окремі вікна), або лишають як є (і розколюють одне вікно на два вузькі). Правильно — тримати `max_gap` мінімальним і вкладатись у надійніший пробник (довший взірець, повтори), а не в ширшу гумку.

- **Центр від усієї осі, а не від вікна.** Наївне «перша P … остання P … середина» садить строб у мертву зону між двома вікнами. Центр рахують **лише всередині обраного** найширшого вікна.

- **Проігнорований край діапазону.** Вікно, що впирається у стінку ручки, має обрізаний центр і фальшиво малий запас з одного боку. Ядро мусить це **позначати** (`WIN_CLIP_*`), а не ховати за тихим числом, — інакше «гаряча плата падає, холодна ні» шукатимуть тижнями.

- **Порожнє вікно й відсутній перехід — не оброблені.** Якщо жодної `P` (чи `1` так і не з'явилась у монотонному пошуку), код мусить повернути явну помилку, а не безглузде число, яке автомат мовчки запише в затримку. Різниця між чесним «тренування провалилось» і системою, що стартувала навмання.

- **Бінарний пошук на немонотонній осі.** Пошук навпіл законний **тільки** там, де відповідь монотонна (write leveling). Пусти його на вісь із вікном — і він застрибне на випадкову `1` посеред `F` і поверне сміття без жодного попередження. Форму відповіді визначає крок тренування, і метод пошуку добирають під неї, а не навпаки.

Складімо докупи. Ядро тренування — це не хитра електроніка, а маленький, але вимогливий алгоритм: розгорни ручку, зчисти шум із карти, знайди найширшу суцільну смугу успіхів, перевір, чи не впирається вона в стінку й чи існує взагалі, сядь у її середину — або, коли відповідь монотонна, злови точку переходу навпіл. Кожен рядок захисту в цьому коді відповідає конкретній фізичній ваді реального тракту, і саме ці рядки, а не сама формула центру, відрізняють прошивку, що заводить пам'ять на будь-якій платі з партії, від тієї, що бездоганно бігає на столі й сиплеться в нагрітому корпусі.
