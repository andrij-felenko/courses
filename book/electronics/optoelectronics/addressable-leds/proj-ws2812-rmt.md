# ⚙️ Кодуємо буфер кадру в RMT-символи й женемо на ESP32

Задача практична: у пам'яті лежить масив кольорів пікселів, а на дроті даних має з'явитися потік імпульсів із точністю до сотень наносекунд — і при цьому Wi-Fi раз у раз краде процесор перериванням. Як зібрати цей потік, не покладаючись на програмний цикл, що збивається від першого ж переривання? Ідея — доручити таймінг апаратному блокові RMT, а процесором лише **скласти** масив символів. Тут — робочий драйвер: кодувальник байта, складання кадру GRB і відправлення. Точні тривалості біта й відповідність «біт ↔ RMT-символ» беремо з [протоколу WS2812](topic:electronics/addressable-leds/api-ws2812-protocol.md); саму науку адресних світлодіодів — з [теми](topic:electronics/addressable-leds).

---

## Ідея: процесор складає масив, RMT відмірює наносекунди

RMT відтворює символи (`rmt_data_t`) з точністю до тактів власного джерела, незалежно від CPU і переривань — рівно те, чого вимагає WS2812. Один біт кодуємо одним символом (рівень + тривалість, потім рівень + тривалість), байт — вісьмома, кадр N пікселів — N × 24 символами. Процесор заповнює цей масив у RAM звичайним циклом, без жодних наносекундних затримок у коді, а тоді одним викликом віддає масив апаратурі — і та жене імпульси сама, поки ядро вільне робити інше.

## Кодувальник байта в RMT-символи

Нижче — Arduino-ESP32 на новому RMT-API (core 3.x), де стиль `rmtInit`/`rmtWrite` узгоджений із `ledcAttach`-підходом [апаратного ШІМ](topic:programming/hardware-pwm). Тривалості — у тіках, tick = 0.1 мкс (джерело RMT на 10 МГц):

```cpp
#include <driver/rmt.h>          // Arduino ESP32 core 3.x
// rmtInit(pin, RMT_TX_MODE, RMT_MEM_NUM_BLOCKS_1, 10000000)
// → tick = 1/10MHz = 100 нс = 0.1 мкс

// Тривалості у тіках (tick = 0.1 мкс) — за специфікацією WS2812B
#define T0H  4    // 0.4 мкс HIGH для «0»
#define T0L  9    // 0.85 мкс LOW  для «0» (9 × 0.1 ≈ 0.9, у допуску)
#define T1H  8    // 0.8 мкс HIGH для «1»
#define T1L  5    // 0.45 мкс LOW  для «1» (5 × 0.1 = 0.5, у допуску)

// Кодує один байт у 8 RMT-символів; out — масив на 8 елементів
void encodeByte(uint8_t b, rmt_data_t* out) {
    for (int i = 0; i < 8; i++) {
        int bit = (b >> (7 - i)) & 1;   // старший біт першим (MSB-first)
        if (bit) {
            out[i].level0    = 1;
            out[i].duration0 = T1H;
            out[i].level1    = 0;
            out[i].duration1 = T1L;
        } else {
            out[i].level0    = 1;
            out[i].duration0 = T0H;
            out[i].level1    = 0;
            out[i].duration1 = T0L;
        }
    }
}
```

CPU тут лише заповнює масив у RAM — жодних наносекундно-точних затримок у циклі. Після `rmtWrite` апаратура сама веде потік за власним таймером.

## Складання кадру GRB і відправлення

```cpp
#define N_PIXELS  60
#define DATA_PIN  5       // ніжка даних стрічки

struct RGB { uint8_t r, g, b; };   // буфер кольорів у логіці програми
RGB pix[N_PIXELS];

rmt_data_t sym[N_PIXELS * 24];     // 24 символи на піксель

void ws2812_setup() {
    // tick = 1/10_000_000 = 0.1 мкс
    rmtInit(DATA_PIN, RMT_TX_MODE, RMT_MEM_NUM_BLOCKS_1, 10000000);
}

void ws2812_show() {
    for (int i = 0; i < N_PIXELS; i++) {
        // GRB — НЕ RGB! (типова пастка WS2812)
        encodeByte(pix[i].g, &sym[i * 24 + 0]);   // G першим
        encodeByte(pix[i].r, &sym[i * 24 + 8]);   // R другим
        encodeByte(pix[i].b, &sym[i * 24 + 16]);  // B третім
    }
    // RMT жене всі N*24 символи; CPU вільний одразу після виклику
    rmtWrite(DATA_PIN, sym, N_PIXELS * 24, RMT_WAIT_TX_DONE);
    // Скидання ≥50 мкс — зазвичай вистачає паузи між двома викликами ws2812_show();
    // якщо треба явно — delayMicroseconds(60)
}
```

Поділ праці чіткий: CPU складає масив чисел (ціна — O(N) простих операцій), а RMT відмірює наносекунди апаратно — навіть коли Wi-Fi-[переривання](topic:programming/interrupts) займає ядро.

## Складність і пастки на МК

**Пам'ять.** Кожен `rmt_data_t` — 4 байти; масив символів для 300 пікселів = 300 × 24 × 4 = 28 800 байт (≈ 28 КБ) лише під RMT-символи, плюс 3 байти на піксель під буфер кольорів. На ESP32 це реально, але не безкоштовно. Для довгих стрічок кодують і шлють порціями через callback RMT, тримаючи в пам'яті лише 24–48 символів одночасно.

**Час складання.** Заповнення N × 24 символів — O(N), і воно дешевше за саму передачу (кожен піксель летить ≈ 30 мкс). Вузьке місце — фізика дроту, не CPU. Це принципова відмінність від bit-bang через [GPIO-регістри](topic:programming/gpio-registers), де CPU зайнятий безперервно впродовж усієї передачі.

**Джерело такту RMT.** Тіки прив'язані до тактового джерела блоку. Зміниться джерело (конфігурація APB) — масштаб тіків «попливе» і тривалості зрушаться: той самий принцип, що й у [роздільності ШІМ](topic:programming/pwm-resolution), де тактова частота таймера визначає всі похідні. На новому API джерело фіксують при `rmtInit` явно, тому ризик нижчий — але знати про нього варто.

**Клони.** T0H/T0L/T1H/T1L — саме для WS2812B; SK6812 і WS2813 схожі, але не ідентичні, WS2811 удвічі повільніший. Документуй, для якого чипа розраховано константи, — не вважай їх вічними.

**Чому не bit-bang.** RMT утримує наносекундну точність апаратно навіть під Wi-Fi-[перериваннями](topic:programming/interrupts). Програмний цикл `digitalWrite` спрацює хіба з вимкненими на весь час передачі перериваннями — а це блокує систему на десятки мілісекунд і руйнує решту логіки.

Від числа в буфері до мікросекундного фронту на дроті шлях тепер увесь під контролем: процесор склав масив, апаратура витримала таймінг, а ядро тим часом лишилося вільним.
