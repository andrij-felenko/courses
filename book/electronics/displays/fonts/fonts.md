Текст на екрані — це гліфи, які беруть зі шрифту й блітають у [кадровий буфер](book:electronics/framebuffer). Але що таке цей гліф і як узагалі зберігають шрифт? Тут стикаються два протилежні підходи з геть різною ціною: **бітмапний** (наперед намальовані пікселі) і **векторний** (контури, які растеризують). А поверх них — згладжування, кернінг, охоплення символів, і та сама турбота, що переслідує embedded скрізь: скільки **Flash** з'їдає гарний шрифт. На дрібному залізі вибір шрифту — майже завжди битва за пам'ять, і кожне рішення в ній має ціну, яку варто бачити наперед.

## Гліф: дві філософії зберігання

**Гліф** (від грец. *glyphē* — «різьблення, викарбуване») — це накреслення одного символу, його форма. Зберегти цю форму можна двома принципово різними способами. Перший — **як пікселі**: намалювати літеру на маленькій сітці й запам'ятати, які клітинки чорні. Другий — **як контур**: описати геометрію форми лініями й кривими, не прив'язуючись до жодного розміру.

![Ліворуч бітмап — готова сітка пікселів одного конкретного розміру; праворуч вектор — контур із точок і кривих, з якого літеру малюють будь-якого кегля.](/book/electronics/displays/fonts/img/glyph.svg)
*Бітмап читати швидко, але він негнучкий і прив'язаний до розміру; вектор компактний і гнучкий, та його щоразу треба «готувати» — растеризувати.*

Перший підхід зберігає **результат**, другий — **рецепт**. Готовий результат читати швидко, зате він негнучкий і об'ємний, коли результатів багато (тут — багато розмірів). Рецепт компактний і гнучкий, зате його щоразу треба готувати. Ця відмінність між збереженим результатом і збереженим рецептом і визначає всі їхні переваги та вади. Історично першими були бітмапні шрифти: на ранніх екранах контури не було чим обчислювати. Векторні прийшли з процесорами, здатними растеризувати на льоту; а в embedded, де процесор знову скромний, бітмап нерідко вертається — коло замикається.

## Бітмапні шрифти: піксель готовий наперед

У бітмапному шрифті кожен гліф — це **фіксований візерунок пікселів** одного розміру, що лежить у Flash як масив бітів. Намалювати літеру — означає просто **блітнути** цей візерунок [готовою операцією копіювання прямокутника пікселів](book:electronics/primitives-raster); жодних обчислень, жодної математики.

![Три кеглі однієї літери, кожен — окремий збережений набір пікселів; спроба масштабувати дрібний гліф дає блочну літеру.](/book/electronics/displays/fonts/img/bitmap-sizes.svg)
*Один збережений розмір не перетворити гладко на інший, тож кожен кегль зберігають окремо — і Flash множиться на число розмірів.*

Звідси чіткий баланс. Плюси — простота, швидкість і передбачуваність: блітнути готові пікселі вміє найскромніший мікроконтролер, без жодної RAM під обчислення. Мінуси прямо випливають із того, що збережено пікселі саме **одного** розміру: гладко масштабувати їх не вийде (збільшений гліф блочний, зменшений — каша), тож кожен потрібний кегль доводиться зберігати окремо, а великі розміри з'їдають багато Flash. Тому бітмапні шрифти панують на дрібних МК, і часто їх наперед готують із векторного шрифту під час збирання — рівно на ті розміри, що знадобляться. Разом із пікселями інструмент пакує кілька **мірок**: базову лінію, на якій «стоять» літери, і **крок** (*advance* — «просування») — на скільки зсунути курсор після літери, щоб рядок був рівний, а не стрибучий.

Як саме виглядає те «блітнути й зсунути курсор», варто побачити — весь рендеринг бітмапного тексту тримається на цих двох діях.

**Малювання рядка бітмапним гліфом 8×8, 1 біт/піксель.** Гліф лежить як 8 байтів — по байту на рядок, біт = піксель. Малюємо кожну виставлену точку в кадровий буфер і після літери зсуваємо курсор на її крок:

:::tabs
```cpp
// Кадровий буфер RGB565: WIDTH×HEIGHT, рядок за рядком
uint16_t fb[WIDTH * HEIGHT];

// Один гліф 8×8: 8 байтів, старший біт — лівий піксель рядка
void blit_glyph(int x, int y, const uint8_t glyph[8], uint16_t color) {
    for (int row = 0; row < 8; row++) {
        uint8_t bits = glyph[row];          // рядок гліфа
        for (int col = 0; col < 8; col++) {
            if (bits & (0x80 >> col))       // біт виставлено → піксель чорний
                fb[(y + row) * WIDTH + (x + col)] = color;
        }
    }
}

// Рядок тексту: блітнути гліф і зсунути курсор на крок (тут моноширинний — 8)
void draw_text(int x, int y, const char *s, uint16_t color) {
    int cursor = x;
    for (; *s; s++) {
        const uint8_t *g = font8x8[(uint8_t)*s];  // код символу → 8 байтів гліфа
        blit_glyph(cursor, y, g, color);
        cursor += 8;                              // advance: наступна літера праворуч
    }
}
```
```python
# Кадровий буфер RGB565: WIDTH×HEIGHT, рядок за рядком
fb = [0] * (WIDTH * HEIGHT)

# Один гліф 8×8: 8 байтів, старший біт — лівий піксель рядка
def blit_glyph(x, y, glyph, color):
    for row in range(8):
        bits = glyph[row]                   # рядок гліфа
        for col in range(8):
            if bits & (0x80 >> col):        # біт виставлено → піксель чорний
                fb[(y + row) * WIDTH + (x + col)] = color

# Рядок тексту: блітнути гліф і зсунути курсор на крок (тут моноширинний — 8)
def draw_text(x, y, s, color):
    cursor = x
    for ch in s:
        g = font8x8[ord(ch)]                # код символу → 8 байтів гліфа
        blit_glyph(cursor, y, g, color)
        cursor += 8                         # advance: наступна літера праворуч
```
:::

Тут видно всю суть бітмапного шрифту: жодної математики, лише вибірка байтів і запис у пам'ять. Для пропорційного шрифту, де в кожної літери свій крок, змінився б лише один рядок — `cursor += advance[(uint8_t)*s]` замість сталої вісімки.

## Векторні шрифти: форма, яку растеризують

Векторний (контурний) шрифт зберігає не пікселі, а **контури** літери — її обриси, задані кривими (зазвичай Безьє), незалежно від розміру. Щоб намалювати гліф, його **растеризують** на льоту: беруть контур, масштабують під потрібний кегль і заливають — тим самим [перетворенням форми на пікселі сітки](book:electronics/primitives-raster).

![Один опис контуру растеризують у літери 16, 24 й 32 пікселі — і всі виходять гладкими.](/book/electronics/displays/fonts/img/vector-scale.svg)
*Ціна цієї гнучкості — потрібен растеризатор: код, процесорний час і трохи RAM на кожен гліф.*

Переваги дзеркальні до бітмапних: **будь-який** розмір з одного опису, завжди гладкий, а один файл шрифту покриває всі кеглі й навіть дозволяє вивести жирне чи похиле накреслення з тієї ж геометрії. Розплата — потрібен **растеризатор** (рушій на кшталт відомого FreeType), а це і код, і процесорний час, і RAM під проміжний гліф. Тому повноцінний векторний рендеринг тримають для потужніших мікроконтролерів, а на скромних задовольняються бітмапом. Формати, які ви бачите щодня, — це **TrueType** і **OpenType**: гліф у них описано кривими плюс підказки, що на дрібних розмірах притягують штрихи до сітки пікселів, і таблиці кернінгу.

## Гладкі літери: 1 біт проти згладжування

Окремий вимір — **наскільки гладкі** краї літер. Якщо піксель гліфа зберігати одним **бітом** (чорний або білий), малі літери виходять різкими й ступінчастими — ті самі сходинки, що псують будь-яку [намальовану похилу лінію чи криву](book:electronics/primitives-raster). Якщо ж відвести пікселю кілька **бітів** (скажімо, 4 біти = 16 рівнів сірого), краї можна **згладити**: проміжні пікселі роблять сірими пропорційно тому, як форма накриває клітинку, і око зливає їх у плавну лінію (саме для цього й потрібні [проміжні рівні сірого у форматі пікселя](book:electronics/color-formats)). Цей прийом і зветься **згладжуванням** (англ. *anti-aliasing* — буквально «проти сходинок»).

![Той самий косий штрих: ліворуч один біт — видно сходинки; праворуч чотири біти — сірі краєві пікселі зливаються в плавність.](/book/electronics/displays/fonts/img/aa.svg)
*Згладжування коштує більше байтів на гліф (кілька бітів замість одного), зате робить дрібний текст читабельним.*

Це прямий компроміс: згладжування коштує **в кілька разів** більше пам'яті на гліф (бо піксель тепер не біт, а 2–4 біти), зате дрібний текст із ним читається легко, а без нього розсипається. На кольорових екранах воно майже обов'язкове; на грубому монохромному від нього відмовляються, бо проміжного сірого там немає взагалі — на чисто чорно-білому e-ink чи символьному дисплеї гладкого тексту не буде, хоч як старайся, тож лишається добирати чіткий, спеціально мальований під цей розмір бітмапний шрифт.

## Кернінг: відстань між парами літер

Просте «зсунь курсор на крок» після кожної літери дає прийнятний, але не ідеальний текст. Деякі пари за рівних проміжків виглядають розхристано: класичний приклад — «AV» чи «To», де похилі форми лишають між собою завелику дірку. **Кернінг** (англ. *kerning*, від *kern* — виступ літери за межі її площадки) — це підгін відстані для конкретних **пар**: окрема таблиця поправок, що каже «після A перед V підсунь ближче».

![Без кернінгу між A і V зяє дірка; з кернінгом V підсувають під навислий край A, і пара виглядає рівно.](/book/electronics/displays/fonts/img/kerning.svg)
*Це окрема таблиця пар — додаткова пам'ять, тож у дрібних embedded-шрифтах кернінг часто пропускають.*

Кернінг робить текст професійним на вигляд, але коштує тієї самої валюти — пам'яті під таблицю пар і трохи коду. На великому гарному інтерфейсі він доречний; на крихітному екранчику з парою рядків ним зазвичай нехтують.

## Юнікод: які символи взагалі є у шрифті

Легко мовчки припустити, що потрібна літера у шрифті є. Та шрифт містить рівно стільки гліфів, скільки в нього **поклали**, і кожен символ, що ви покажете, мусить мати свій гліф. Латиниця — це близько сотні знаків; додайте кирилицю — вже за дві сотні; а повний **юнікод** (*Unicode* — «єдиний код» для всіх писемностей світу), включно з десятками тисяч ієрогліфів, — це гігантський набір, якому в дрібному МК просто немає місця. Тому в embedded майже завжди роблять **підмножину** (англ. *subset*): кладуть у шрифт лише ті символи, що реально знадобляться — вашу мову, цифри, потрібні знаки, — і викидають решту.

Окремий клопіт — **кодування** тексту, який ви виводите. Сучасний стандарт — **UTF-8**: латинські символи він пише одним байтом, а кирилицю, акценти й решту — двома й більше. Тобто українська «ї» в рядку — це не один байт, а два, і код малювання має спершу **розібрати** ці байти назад у код символу, перш ніж шукати гліф. Наївний цикл «байт = символ» на UTF-8 покаже замість «ї» дві кракозябри, тож рендер тексту на МК завжди починається з простенького декодера UTF-8.

## Вага у Flash: головна турбота embedded

Усі ці вибори — бітмап чи вектор, 1 біт чи згладжування, який кегль, чи з кернінгом, скільки символів — зрештою сходяться в одне число: **скільки Flash з'їсть шрифт**. І воно вражає.

![Таблиця ваги: дрібний 1-бітний латинський шрифт — лічені кілобайти; великий згладжений з кирилицею — сотні кілобайтів.](/book/electronics/displays/fonts/img/flash.svg)
*Кожен множник — більший кегль, згладжування, ширший набір, ще одне накреслення — накладається на інші.*

**Вага шрифту 16×16 пікселів для латиниці з кирилицею (~200 символів).** Порахуймо два варіанти глибини пікселя:

```
1 біт/піксель:       16 × 16 = 256 біт = 32 байти/гліф
                     200 × 32  = 6 400 байтів    ≈ 6.4 КБ

4 біти/піксель (АА): 16 × 16 × 4 = 1024 біти = 128 байтів/гліф
                     200 × 128 = 25 600 байтів  ≈ 25.6 КБ
```

Одне лише згладжування вчетверо роздуло шрифт; великий кегль роздув би його ще на порядок (48-піксельний — це вже ~9× площі), а окреме жирне накреслення — подвоїло б. Звідси наскрізне правило економії: бери **лише потрібні** символи (субсет), **лише потрібні** розміри й накреслення, а згладжування додавай там, де воно справді треба для читабельності, а не всюди.

> 🔧 **Навіщо це.** Шрифт у вбудованому виробі — часто один із найбільших споживачів Flash, і легко непомітно з'їсти ним сотні кілобайтів. Перш ніж додати ще один кегль, накреслення чи згладжування, прикиньте їхню ціну за формулою «символів × байтів на гліф». Найдешевший шрифт — субсет лише вашої мови, у потрібному розмірі, без зайвого; найдорожчий — повний юнікод великим згладженим кеглем «про всяк випадок».

Отже, текст — не «безкоштовний» елемент інтерфейсу, як його іноді сприймають: за кожним рядком стоїть і пам'ять під гліфи, і робота з їх малювання, і десятки дрібних рішень — розмір, накреслення, згладжування, охоплення мов. Підійшовши до шрифту як до повноцінного компонента з власним бюджетом, ви уникнете і роздутого Flash, і блідого нечитабельного тексту, який псує навіть найкращий виріб. А коли картинка з гліфами вже зібрана в кадровому буфері, лишається окреме питання — як **показати** її глядачеві так, щоб вона не рвалася й не мерехтіла під час оновлення; це розв'язує [подвійна буферизація з синхронізацією кадру](book:electronics/double-buffering).
