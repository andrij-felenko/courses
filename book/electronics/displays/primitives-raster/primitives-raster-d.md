# Растеризація: глибше

[Базова стаття](book:electronics/primitives-raster) показала картину згори: форму вкладають у сітку, лінію й коло веде ціла похибка, прямокутник заливають спанами, текст переносять блоками. Тут ми спускаємось на рівень нижче — туди, де ці прийоми **виводяться з нуля**: чому в Брезенхема саме така похибка й чому вона ціла, як та сама ідея згинає коло, як залити **довільний** многокутник, як погасити сходинки півтонами й як відсікти лінію до вікна, не малюючи зайвого. Усе — реальним C для прошивки, бо саме на дрібному залізі ці деталі вирішують, чи буде графіка живою.

### Лінія: звідки береться ціла похибка

Почнімо чесно — зі шкільного рівняння й подивімось, як воно само проситься стати цілочисловим. Хай лінія йде від (x₀, y₀) до (x₁, y₁), і поки що вона **полога** та йде вправо-вгору: 0 ≤ нахил ≤ 1, тобто `dx = x₁−x₀ ≥ dy = y₁−y₀ ≥ 0`. Полога — означає, що довша вісь — це X, тож саме по X ми й крокуємо на кожен піксель.

На кроці від x до x+1 ідеальна координата y зростає на нахил `m = dy/dx`. Наївно:

```c
// НАЇВНО: дробовий y, множення й округлення на кожен піксель
float m = (float)dy / dx;
float y = y0;
for (int x = x0; x <= x1; x++) {
    set_pixel(x, lroundf(y), color);   // округлення до клітинки
    y += m;                            // float-додавання щокроку
}
```

Працює, але `float` на мікроконтролері без апаратної коми — це десятки тактів на крок. Прибираймо дроби думкою. Ключ — питати не «де зараз y», а «**наскільки** поточний рядок розійшовся з ідеальною лінією». Назвемо цей розрив похибкою. Поставивши піксель у рядку y, ми робимо помилку проти ідеального y; на наступному кроці лінія підніметься ще на `m`. Коли накопичена помилка переростає **півклітинки**, рядок y вже далі від лінії, ніж рядок y+1, — час зсунути y на одиницю.

Запишемо це через дробову помилку `err` (відстань від центру поточної клітинки до лінії, у частках клітинки):

```c
// ПРОМІЖНО: ще float, але вже «накопичена похибка проти півклітинки»
float err = 0.0f;
int y = y0;
for (int x = x0; x <= x1; x++) {
    set_pixel(x, y, color);
    err += m;                 // лінія піднялась на нахил
    if (err > 0.5f) {         // переросла півклітинки — рядок треба підняти
        y++;
        err -= 1.0f;          // і відняти цілу клітинку назад
    }
}
```

Тепер найкрасивіший крок — позбутися дробів зовсім. `m = dy/dx`, тож помножмо **всю** логіку на `2·dx` (на два — щоб поріг «півклітинки» 0.5 став цілим dx). Підстановки: `err·2dx` стає цілою змінною `e`; крок `+= m` стає `+= 2·dy`; поріг `> 0.5` стає `> dx`; віднімання `−1` стає `−2·dx`. Жодного дробу не лишилось:

```c
// ЦІЛОЧИСЛОВО (полога лінія вправо-вгору): самі int, без множень у циклі
int e = 0;                    // = 2·dx·(дробова похибка)
int y = y0;
for (int x = x0; x <= x1; x++) {
    set_pixel(x, y, color);
    e += 2 * dy;              // 2·dy — константа, обчислена один раз
    if (e > dx) {            // поріг «півклітинки», помножений на 2·dx
        y++;
        e -= 2 * dx;
    }
}
```

`2*dy` і `2*dx` — константи, пораховані до циклу; всередині лишаються лише додавання й порівняння цілих. Це і є серце Брезенхема: дробова геометрія, чесно домножена на знаменник, аж поки не зникли дроби.

Варто побачити, що `e` має й геометричний сенс — це, з точністю до сталого множника, **знакова відстань** від центру поточної клітинки до ідеальної лінії. Додатна — клітинка нижче лінії, від'ємна — вище. Алгоритм тримає цю відстань у вузькому коридорі шириною в клітинку: щойно вона виходить за половину, ми робимо вертикальний крок, і відстань знову падає всередину коридору. Саме тому Брезенхем кладе пікселі **найближче** до лінії — він буквально мінімізує цю відстань, крок за кроком. І саме тому той самий шаблон — вести цілу знакову функцію й кроком повертати її в коридор — повторюється скрізь у растеризації: у колі, в еліпсі, у заливці. Хто впізнає цей шаблон, той далі читає всі ці алгоритми як варіації однієї думки, а не як окремі рецепти.

Лишилось зняти обмеження «полога, вправо-вгору». Круту лінію (`dy > dx`) обертають: крокують по Y, а зсувають X — симетрично. Напрями вліво чи вниз додають знаки кроку `sx`, `sy`. Усі чотири випадки злити в одну петлю дозволяє трюк зі знаком `dy`: беремо `dx = abs(...)`, `dy = -abs(...)` і ведемо одну похибку `err = dx + dy`, перевіряючи її проти обох порогів. Саме ця форма стоїть у [базовій статті](book:electronics/primitives-raster) як `draw_line` — тепер видно, що то не магія, а згорнуті в одну гілку чотири окремі симетрії.

> 🔧 **Навіщо це.** Розуміти вивід, а не лише копіювати код, треба тоді, коли Брезенхема доводиться **гнути під задачу**: вести разом із лінією градієнт кольору (та сама похибка інтерполює і яскравість), малювати товсту лінію без щілин, чи покласти на лінію пунктир із правильним кроком. Хто бачить, що `err` — це просто домножена відстань до лінії, той робить ці варіації за хвилини; хто визубрив петлю — застрягає.

### Коло: та сама похибка, зігнута по колу

Коло растеризують **midpoint**-алгоритмом — прямим родичем Брезенхема. Ідея та сама: вести цілу вирішальну змінну, що каже, з якого боку кривої ми опинились, і нею вибирати наступний піксель без жодного кореня й тригонометрії.

Рівняння кола радіуса r у початку координат: `x² + y² = r²`. Визначмо функцію `F(x, y) = x² + y² − r²`. Вона нульова **на** колі, від'ємна **всередині**, додатна **зовні** — зручний компас.

Чому досить **одного** октанта — видно з нахилу. Біля верхівки кола (0, r) дотична горизонтальна: на одиницю вправо крива опускається менше ніж на одиницю, тобто X тут — довша вісь, і крокувати треба по X. Так триває рівно до діагоналі `x = y` (нахил −45°); далі крива стає крутішою за діагональ, довшою віссю стає Y, і логіка дзеркалиться. Тому межа октанта — саме `x ≤ y`: поки ця умова тримається, ми в зоні, де крок по X дає рівно один піксель без дір, як і в пологій лінії. Решту кола добудовує симетрія, тож рахувати круту половину октанта окремо не треба зовсім.

Працюємо у цьому октанті — від верхньої точки (0, r) праворуч-донизу. На кожен крок x зростає на 1, а y або лишається, або падає на 1. Стоячи в пікселі (x, y), наступний — або «схід» E = (x+1, y), або «південний схід» SE = (x+1, y−1). Вибирає **середина** між ними, точка (x+1, y−½): підставляємо її в наш компас F і дивимось знак. Якщо середина **всередині** кола (`F < 0`), справжня крива проходить **вище** середини — нижній піксель SE був би зайвим, беремо E; якщо середина зовні (`F ≥ 0`) — крива нижча, беремо SE. Тобто знак однієї цілої величини на кожному кроці й вирішує весь вибір.

Підставмо середину у F — отримаємо вирішальну змінну `d = F(x+1, y−½) = (x+1)² + (y−½)² − r²`. Рахувати її щоразу заново — знову множення; натомість ведемо її **приростом**. Якщо обрали E, наступна середина зсунеться по x: різниця `d` дорівнює `2x + 3`. Якщо обрали SE — `2x − 2y + 5`. Це чисті цілі прирости. Початкове значення в точці (0, r): `d₀ = 1 − r` (півклітинку `¼` відкидають — округлення цілого старту нічого не псує). Усе разом:

```c
// Коло радіуса r з центром (cx,cy): один октант + вісім дзеркал, самі int.
void draw_circle(uint16_t *fb, int W, int H,
                 int cx, int cy, int r, uint16_t color)
{
    int x = 0, y = r;
    int d = 1 - r;                 // вирішальна змінна, старт F(1, r-½)≈1-r
    while (x <= y) {
        plot8(fb, W, H, cx, cy, x, y, color);   // вісім симетричних точок
        if (d < 0) {               // середина всередині кола → крок E
            d += 2 * x + 3;
        } else {                   // середина зовні → крок SE
            d += 2 * (x - y) + 5;
            y--;
        }
        x++;
    }
}
```

`plot8` — і є та economiя симетрією: одна обчислена пара (x, y) лягає у вісім точок, по дзеркалу на кожну вісь і діагональ.

```c
static inline void plot8(uint16_t *fb, int W, int H,
                         int cx, int cy, int x, int y, uint16_t color)
{
    set_clip(fb, W, H, cx + x, cy + y, color);   // кожна точка ще й
    set_clip(fb, W, H, cx - x, cy + y, color);   // відсікається до екрана
    set_clip(fb, W, H, cx + x, cy - y, color);
    set_clip(fb, W, H, cx - x, cy - y, color);
    set_clip(fb, W, H, cx + y, cy + x, color);
    set_clip(fb, W, H, cx - y, cy + x, color);
    set_clip(fb, W, H, cx + y, cy - x, color);
    set_clip(fb, W, H, cx - y, cy - x, color);
}
```

З цього кістяка ростуть усі круглі форми. **Залите** коло: замість восьми точок проводимо горизонтальні **спани** між симетричними парами (від `cx−x` до `cx+x` на рядках `cy±y`, і від `cx−y` до `cx+y` на рядках `cy±x`) — знову найдешевший інструмент. **Дуга**: малюємо лише ті октанти (чи діапазон кутів), що потрапляють у потрібний сектор. **Еліпс**: те саме F, але з різними півосями `a`, `b` — `F(x,y) = b²x² + a²y² − a²b²`; октант доводиться розбити на дві зони (де крутіша похідна — крокуємо по іншій осі), та принцип незмінний.

### Заливка довільної фігури: scanline й парність

Прямокутник і коло заливаються легко, бо їхні межі прості. А як залити **довільний** многокутник — трикутник, зірку, опуклу чи навіть самоперетинну фігуру? Тут працює **алгоритм по рядках** (scanline) з **правилом парності**.

Ідея спирається на просте спостереження: проведіть уявний горизонтальний промінь крізь фігуру зліва направо й рахуйте, скільки разів він перетнув її межу. Поза фігурою лічильник парний (нуль перетинів), усередині — непарний. Кожен перетин **перемикає** стан «всередині ↔ зовні». Отже, для кожного рядка екрана достатньо знайти всі x, де він перетинає ребра фігури, посортувати їх і **залити спани між парами**: від 1-го перетину до 2-го, від 3-го до 4-го, і так далі.

:::tabs
```c
// Заливка многокутника по рядках. poly[] — N вершин (x,y) за обходом.
void fill_polygon(uint16_t *fb, int W, int H,
                  const Point *poly, int N, uint16_t color)
{
    // межі по Y — лише рядки, які фігура справді накриває
    int ymin = INT_MAX, ymax = INT_MIN;
    for (int i = 0; i < N; i++) {
        if (poly[i].y < ymin) ymin = poly[i].y;
        if (poly[i].y > ymax) ymax = poly[i].y;
    }
    if (ymin < 0) ymin = 0;
    if (ymax > H - 1) ymax = H - 1;

    int xs[MAX_X];                         // перетини поточного рядка
    for (int y = ymin; y <= ymax; y++) {
        int n = 0;
        // зібрати x-перетини ребер із серединою рядка (y + 0.5)
        for (int i = 0, j = N - 1; i < N; j = i++) {
            int yi = poly[i].y, yj = poly[j].y;
            // ребро перетинає рядок, якщо y між його кінцями (півінтервал!)
            if ((yi <= y && yj > y) || (yj <= y && yi > y)) {
                // лінійна інтерполяція x у точці перетину
                int xi = poly[i].x + (long)(y - yi) * (poly[j].x - poly[i].x)
                                     / (yj - yi);
                xs[n++] = xi;
            }
        }
        // посортувати перетини зліва направо (n мале — досить вставками)
        for (int a = 1; a < n; a++) {
            int v = xs[a], b = a - 1;
            while (b >= 0 && xs[b] > v) { xs[b + 1] = xs[b]; b--; }
            xs[b + 1] = v;
        }
        // залити спани між парами 0-1, 2-3, ...
        for (int a = 0; a + 1 < n; a += 2)
            hspan(fb, W, H, xs[a], xs[a + 1], y, color);
    }
}
```
```python
# Заливка многокутника по рядках. poly — список вершин (x, y) за обходом.
def fill_polygon(fb, W, H, poly, color):
    N = len(poly)
    # межі по Y — лише рядки, які фігура справді накриває
    ymin = max(0,     min(p[1] for p in poly))
    ymax = min(H - 1, max(p[1] for p in poly))

    for y in range(ymin, ymax + 1):
        xs = []
        # зібрати x-перетини ребер із серединою рядка (y + 0.5)
        for i in range(N):
            (xi, yi), (xj, yj) = poly[i], poly[i - 1]   # i-1 замикає на останню вершину
            # ребро перетинає рядок, якщо y між його кінцями (півінтервал!)
            if (yi <= y < yj) or (yj <= y < yi):
                # лінійна інтерполяція x у точці перетину
                xs.append(xi + (y - yi) * (xj - xi) // (yj - yi))
        xs.sort()                                       # перетини зліва направо
        # залити спани між парами 0-1, 2-3, ...
        for a in range(0, len(xs) - 1, 2):
            hspan(fb, W, H, xs[a], xs[a + 1], y, color)
```
:::

Два місця тут несуть усю коректність. Перше — **півінтервал** у перевірці ребра (`yi <= y && yj > y`): кінець-вершину рахуємо рівно один раз. Чому це критично, видно на простому збої. Уявімо вершину трикутника, у якій сходяться два ребра, і рядок проходить рівно через неї. Якби обидва ребра рахували цю спільну точку як перетин, рядок дістав би **два** перетини в одному x — парність перемкнулась би двічі й лишилась незмінною, тобто половина фігури від цієї вершини й далі залилась би навиворіт. Півінтервал розриває цю двозначність: ребро «володіє» лише своїм нижнім кінцем, верхній віддає сусідові, тож спільна вершина рахується точно один раз. Це не причепа, а саме той випадок, на якому наївна заливка трикутників розсипається на діагональні щілини. Друге місце — **сортування** перетинів: спани кладемо строго зліва направо, тож межі мають іти в порядку зростання x; без сортування пари «вхід-вихід» переплутаються, і замість суцільної заливки вийде смугаста.

На великих фігурах список ребер тримають заздалегідь посортованим за y (edge table) і ведуть **активний список** (active edge list) лише тих ребер, що перетинають поточний рядок, доточуючи x інкрементом, як у Брезенхема, — це прибирає повторний перебір усіх ребер на кожен рядок. Для невеликих UI-фігур на мікроконтролері й простіший варіант вище цілком швидкий: рядків мало, ребер одиниці, і весь перебір губиться на тлі самих записів у буфер.

> 🔧 **Навіщо це.** Кнопка зі скошеними кутами, стрілка, сектор кругової шкали, заливка під графіком — усе це довільні многокутники. Маючи один `fill_polygon`, ви замикаєте всю заливку UI на нього й не плодите окремий код під кожну форму. А розуміння парності рятує, коли фігура раптом самоперетинна (зірка): тоді замість «парного» правила беруть **ненульове** (nonzero winding), що рахує напрям перетину, — але каркас по рядках той самий.

### Згладжування: піксель напівсвітиться

Сходинки на косих лініях і колах — **аліасинг**: гладка форма прикидається грубою драбинкою, бо кожен піксель може бути лише цілком засвічений або цілком ні. Назва не випадкова й веде до глибшої причини. Растеризуючи, ми **дискретизуємо** неперервну форму — беремо її значення лише в центрах клітинок, тобто у вузлах сітки з кроком один піксель. А в сигналів є залізне правило: коли в зображенні є деталі дрібніші за крок дискретизації (а гострий край косої лінії — це нескінченно дрібна деталь), вони не зникають, а **підмінюються** грубшими, яких в оригіналі не було. Ця підміна частот і зветься аліасингом; сходинки — її зорове обличчя. Тому радикально позбутися їх простим вибором «цей піксель чи той» неможливо: проблема не в поганому виборі, а в надто рідкій сітці проти нескінченно різкого краю.

Вихід — не різкіший край, а **м'якший**: дати пікселю **проміжну** яскравість, пропорційну тому, яку частку його площі накриває ідеальна форма. Це згладжування (anti-aliasing). Замість питати «центр клітинки всередині форми чи ні?» — питаємо «яку частку клітинки форма накрила?» і світимо піксель рівно на цю частку. Око інтегрує ці півтони назад у гладку межу, бо сприймає не окремий піксель, а їх локальне середнє. Фактично ми згладжуємо нескінченно різкий край перед тим, як його дискретизувати, — і підміни вже немає чим живитись.

Найпрямолінійніший підхід — **покриття** (coverage): для кожного крайового пікселя оцінити частку накриття від 0 до 1 і змішати колір форми з тлом у цій пропорції. Для лінії Сяолінь Ву (Xiaolin Wu, 1991) помітив гарне: на кожному кроці по довшій осі ідеальна лінія проходить між **двома** сусідніми пікселями, і дробова частина її координати прямо дає вагу — ближчий світиться сильніше, дальший слабше, а їхні ваги в сумі дають одиницю. Звідси гладка лінія за майже ту саму ціну, що й Брезенхем:

:::tabs
```c
// Один крок згладженої лінії Ву по осі X: два пікселі з вагами c і 1-c.
// fy — точна (дробова) y-координата лінії в стовпці x.
static inline void plot_aa(uint16_t *fb, int W, int H,
                           int x, float fy, uint16_t fg, uint16_t bg)
{
    int    yi = (int)floorf(fy);
    float  c  = fy - yi;                 // частка над нижнім пікселем
    set_pixel(x, yi,     blend(fg, bg, 1.0f - c));  // ближчий — яскравіший
    set_pixel(x, yi + 1, blend(fg, bg, c));         // дальший — тьмяніший
}
```
```python
import math

# Один крок згладженої лінії Ву по осі X: два пікселі з вагами c і 1-c.
# fy — точна (дробова) y-координата лінії в стовпці x.
def plot_aa(fb, W, H, x, fy, fg, bg):
    yi = math.floor(fy)
    c  = fy - yi                                    # частка над нижнім пікселем
    set_pixel(x, yi,     blend(fg, bg, 1.0 - c))    # ближчий — яскравіший
    set_pixel(x, yi + 1, blend(fg, bg, c))          # дальший — тьмяніший
```
:::

`blend(fg, bg, a)` — змішування кольорів: `a` частки переднього плану й `1−a` тла, поканально (для [RGB565](book:electronics/color-formats) кожен канал змішують окремо). Якщо тло не однотонне, його колір під пікселем спершу читають із [кадрового буфера](book:electronics/framebuffer).

Тут чигає тонка, але реальна пастка — **гама**. Числа в буфері — це не яскравість, а її стиснений код: значення зберігають у гама-кодуванні, де серединний код 128 відповідає десь п'ятій частині фізичного світла, а не половині. Тому наївне усереднення кодів дає не те накриття, яке око бачить: чорний текст на білому тлі при простому лінійному `blend` виходить **затонким**, бо «50% коду» темніше за «50% світла». Правильно — переводити обидва кольори в лінійне світло, змішувати там, тоді кодувати назад; на мікроконтролері це роблять маленькою таблицею-вибіркою (код → лінійне → код), бо рахувати степеневу функцію щоразу задорого. Можна цим знехтувати — багато простих рушіїв так і роблять, — але саме звідси беруться скарги «згладжений шрифт виглядає блідим і кволим»; тепер ви знаєте причину й де її лагодити.

Згладжування коштує **читання тла + множення на канал** — дешевше, ніж здається, але не безплатне, тож його тримають там, де воно справді важить. А важить воно понад усе [для тексту](book:electronics/fonts): літери — це маса дрібних косих і круглих штрихів, і без півтонів на малому кеглі вони розсипаються на нечитабельні сходинки. На монохромному екранчику, де проміжного сірого фізично немає, від згладжування відмовляються зовсім; натомість іноді застосовують **дизер** — імітують сірий рідким візерунком чорних точок.

### Відсікання: не писати за межі

Кожна операція малювання мусить лишатися в межах екрана чи поточного вікна — інакше запис за край [кадрового буфера](book:electronics/framebuffer) затирає чужу пам'ять (у кращому разі — сусідній рядок, у гіршому — змінні програми). Захиститись можна двома рівнями.

Найпростіший — **поточкове** відсікання: перед кожним записом перевіряти координати. Один прийом робить це двома порівняннями замість чотирьох — приведенням до беззнакового: від'ємний x як `unsigned` стає величезним і відсікається тим самим верхнім порогом.

```c
static inline void set_clip(uint16_t *fb, int W, int H,
                            int x, int y, uint16_t color)
{
    if ((unsigned)x < (unsigned)W && (unsigned)y < (unsigned)H)
        fb[y * W + x] = color;            // лише видимі пікселі
}
```

Це просто, але марнує роботу: для лінії, що на 90% за екраном, ми все одно проганяємо весь Брезенхем, лише викидаючи більшість пікселів. Тому довгі примітиви відсікають **геометрично заздалегідь** — обрізають відрізок до прямокутника вікна ще до растеризації. Класика тут — **Cohen–Sutherland**: кожному кінцю лінії приписують 4-бітний код (**outcode**) — по біту на «лівіше / правіше / нижче / вище» вікна.

```c
#define OUT_LEFT   1
#define OUT_RIGHT  2
#define OUT_BOTTOM 4
#define OUT_TOP    8

static int outcode(int x, int y, int xmin, int ymin, int xmax, int ymax)
{
    int c = 0;
    if (x < xmin) c |= OUT_LEFT;  else if (x > xmax) c |= OUT_RIGHT;
    if (y < ymin) c |= OUT_BOTTOM; else if (y > ymax) c |= OUT_TOP;
    return c;
}
```

Далі — дві миттєві перевірки. Якщо `code0 | code1 == 0`, **обидва** кінці у вікні — лінію беремо як є (trivial accept). Якщо `code0 & code1 != 0`, обидва кінці по один бік **однієї** межі — лінія цілком зовні, відкидаємо без обчислень (trivial reject). Інакше відрізаємо лінію по тій межі, де один із кінців вийшов, замінюємо цей кінець точкою перетину й повторюємо, аж доки лінія не звузиться до trivial accept чи reject:

```c
// Cohen–Sutherland: обрізати лінію до вікна [xmin..xmax]×[ymin..ymax].
// Повертає 1, якщо лишився видимий відрізок (кінці оновлено), інакше 0.
int clip_line(int *x0, int *y0, int *x1, int *y1,
              int xmin, int ymin, int xmax, int ymax)
{
    int c0 = outcode(*x0, *y0, xmin, ymin, xmax, ymax);
    int c1 = outcode(*x1, *y1, xmin, ymin, xmax, ymax);
    for (;;) {
        if ((c0 | c1) == 0) return 1;           // обидва у вікні — приймаємо
        if ((c0 & c1) != 0) return 0;           // обидва за межею — відкидаємо
        int c = c0 ? c0 : c1;                    // кінець, що зовні
        int x = 0, y = 0;
        if (c & OUT_TOP) {                       // перетин з верхньою межею
            x = *x0 + (*x1 - *x0) * (ymax - *y0) / (*y1 - *y0); y = ymax;
        } else if (c & OUT_BOTTOM) {
            x = *x0 + (*x1 - *x0) * (ymin - *y0) / (*y1 - *y0); y = ymin;
        } else if (c & OUT_RIGHT) {
            y = *y0 + (*y1 - *y0) * (xmax - *x0) / (*x1 - *x0); x = xmax;
        } else { /* OUT_LEFT */
            y = *y0 + (*y1 - *y0) * (xmin - *x0) / (*x1 - *x0); x = xmin;
        }
        if (c == c0) { *x0 = x; *y0 = y; c0 = outcode(x, y, xmin, ymin, xmax, ymax); }
        else         { *x1 = x; *y1 = y; c1 = outcode(x, y, xmin, ymin, xmax, ymax); }
    }
}
```

На практиці поєднують обидва рівні: довгі лінії й многокутники відсікають геометрично (швидко й мало пікселів), а одиночні точки й дрібні форми лишають на дешеву поточкову перевірку `set_clip`. Вікно відсікання при цьому — не конче весь екран: задавши його меншим, дістають **обрізання за областю** — основу віджетів, що малюють лише у своєму прямокутнику й не лізуть на сусідів.

### Товсті лінії й кінці

Лінія в один піксель — ідеал; реальні рамки, стрілки й графіки потребують **товщини**. Простих шляхів три, кожен зі своїм компромісом.

Перший — вести **кілька паралельних** тонких ліній Брезенхема, зсунутих перпендикулярно до напряму. Дешево, але на стиках і поворотах лишаються щілини, а кінці виходять косими. Другий — на кожному кроці лінії ставити не піксель, а маленький **диск** (залите коло) радіуса півтовщини: стик і кінці виходять круглими й без щілин, ціна — те коло на кожен крок. Третій, найчистіший, — звести товсту лінію до **многокутника**: чотири кути прямокутника завширшки з товщину, повернутого під кутом лінії, і залити його `fill_polygon`. Так виходять рівні прямі краї й передбачувані кінці; саме цей шлях беруть, коли товщина велика або важливий точний вигляд кінця (зрізаний, круглий, квадратний).

Пунктир лягає поверх будь-якого з трьох: ведемо лічильник довжини вздовж лінії й вмикаємо пікселі лише на «повних» ділянках візерунка, лишаючи «порожні» темними. Важливо рахувати довжину **вздовж** лінії (по числу кроків Брезенхема), а не по одній осі, — інакше на косих лініях штрихи виходять різної довжини.

### Рух між пікселями: дробова позиція без float

Окрема глибина відкривається, щойно картинка має **рухатись** плавно — стрілка приладу, повзунок, анімований графік. Якщо позицію тримати цілими пікселями, повільний рух іде ривками: об'єкт стоїть кілька кадрів, тоді стрибає на цілий піксель. Око це бачить як сіпання. Лік — **субпіксельна** позиція: тримати координату дрібніше за піксель і на цьому дробі або вибирати, з якого боку поставити край, або (зі згладжуванням) ділити яскравість крайнього пікселя між двома сусідами пропорційно дробовій частині. Тоді стрілка, посуваючись на чверть пікселя за кадр, плавно «перетікає» сусідню межу замість стрибати.

Робити це знову треба **без float**. Беруть **числа з фіксованою комою**: ціле трактують так, ніби кілька молодших бітів — дробова частина. Скажімо, формат 26.6 (шість бітів на дріб) дає крок 1/64 пікселя; координата `x_fixed` зберігає `x · 64`, ціла позиція — це `x_fixed >> 6`, а дробова для ваги згладжування — `x_fixed & 63`. Уся арифметика лишається цілою: додати чверть пікселя — це `+= 16`. Цей самий формат 26.6, до речі, використовують і всередині [шрифтових рушіїв](book:electronics/fonts) для гладкого розташування гліфів. Так плавність руху дістається тією ж монетою, що й усе інше в растеризації, — цілим числом, у яке заховано дріб.

### Власні фігури: усе зводиться до трьох рухів

Маючи лінію, коло, заливку по рядках і бліт, ви вже вмієте намалювати майже будь-що — складніша форма є їхньою комбінацією. **Заокруглений прямокутник**: чотири прямі сторони спанами плюс чотири чверті кола в кутах (той самий midpoint, обмежений одним октантом на кут). **Трикутник, стрілка, зірка**: `fill_polygon` по вершинах. **Графік-крива**: ламана з відрізків Брезенхема, а під нею — заливка спанами до осі. **Іконка чи спрайт**: бітмап, перенесений блітом, як гліф.

Це і є та сама наскрізна думка, лише доведена до дна: будь-яка форма зрештою розпадається на **спани** (рівні ділянки — цілим рядком), **цілочислові криві** (лінія й коло — похибкою без дробів) і **бліти** (готові блоки — копією). Хто бачить за кнопкою ці три рухи, той пише графічний рушій під мікроконтролер невеликим і швидким; решта тоне в окремому коді під кожну дрібницю. А коли заліза стане більше, ті самі три рухи нікуди не зникнуть — їх просто почне виконувати апаратний 2D-прискорювач, лишивши вам ту саму модель у голові.
