# ⚙️ Розгортання шини в поіменні ланцюги

> Креслячи схему, ви пишете `D[7..0]` один раз — і вважаєте, що вісім ліній даних заведено. Але плата не знає слова «шина»: на ній є вісім окремих доріжок, кожна зі своїм іменем і своїм списком пінів. Хтось мусить перетворити **один компактний запис** на **вісім поіменних скалярних ланцюгів** — і зробити це так, щоб жоден член не загубився й не лишився висіти. Цей хтось — редактор схем, а точніше невеликий шматок його коду, що зветься **розгортанням шини** (англ. *bus expansion*). Розберімо його зсередини: як парситься діапазон `[a..b]` в обидва боки, як народжуються імена членів, як на склеюванні й стику шин звіряється розрядність — і як та сама перевірка ловить висячий член ще до того, як він поїде у фотошаблон.

### Задача

Дано запис шини — рядок на кшталт `D[7..0]`, `A[15..8]`, `{CTRL, D[6..0]}`. Треба:

1. **Розібрати** його — виокремити префікс (`D`), межі діапазону (`7` і `0`) і напрям;
2. **Породити** список імен членів — `D7, D6, … D0` — у правильному порядку й правильній кількості;
3. **Звести** кожен член зі своїм піном приймача й **зібрати мапу** «ім'я члена → піни», бо саме вона, а не намальована товста лінія, описує плату;
4. **Перевірити** дві речі, які мовчки псують плати: чи при склеюванні й стику шин **збігається розрядність** (скільки ліній віддано — стільки й прийнято) і чи не лишилось **висячих членів** (лінія, яку оголосили, але нікуди не завели).

Усе це робиться **до** розведення плати — на тому ж проході, що будує нетлист зі схеми. І вся хитрість не в самому розгортанні (воно тривіальне), а в крайових випадках: діапазон, що йде вниз; ширини, що розійшлися на одиницю; і — найпідступніше — ім'я, яке для ока збігається, а для коду ні.

> 🔧 **Навіщо це.** Розгортання — це **точка, де вектор перестає існувати**. До неї `D[7..0]` — зручна абстракція для людини; після неї лишаються самі скаляри, і вся подальша машинерія плати (розведення, фотошаблон, складальний файл) бачить тільки їх. Тому будь-яка помилка тут — переплутана ширина, загублений член, кирилична літера в імені — проходить далі **без жодного опору**: вектора вже немає, нема чому й спіткнутися. Розуміти цей крок означає розуміти, де саме народжуються плати, що «зібрані точно за схемою, а не працюють».

### Ідея: один раз розгорнути, далі — звичайні скаляри

Ключова думка, від якої все спрощується: шина — це [скорочення запису, а не новий тип з'єднання](book:electronics/net-bus-notation). `D[7..0]` означає рівно ті самі вісім дротів, що й вісім окремо накреслених `D0…D7`. Тому розгортанню не потрібен жоден особливий «механізм шин» — досить **один раз** перетворити діапазон на список імен, а далі поводитися з кожним членом як зі звичайною [міткою ланцюга](book:electronics/schematic-line-conventions): `D3` на шині та `D3` на піні деталі зливаються за збігом імені, як зливаються дві мітки `+5В`.

![Конвеєр: запис шини → парсер діапазону → члени-скаляри → мапа ім'я→піни](/book/electronics/analog/net-bus-notation/img/expand-pipeline.svg)
*Чотири кроки розгортання. Парсер вихоплює з `D[7..0]` префікс і межі; генератор породжує вісім імен членів і прив'язує кожне до номера біта; нарешті кожен член осідає в мапі «ім'я → піни». На виході вектора немає — лише вісім звичайних ланцюгів, готових лягти на плату.*

Тобто конвеєр такий: **рядок шини → (парсер) → межі → (генератор) → список імен → (злиття за іменем) → мапа ім'я→піни**. Перші дві ланки — суто текстова робота, і саме в них ховаються всі пастки напряму й ширини. Третя ланка — той самий union-find за іменами, що зводить докупи весь [нетлист](book:electronics/nodes-connections/proj-netlist-erc.md); тут на ньому не спинятимемось, бо для шини він нічим не особливий — їй досить дати йому вже розгорнуті імена.

### Крок 1: розбір діапазону в обидва боки

Почнемо з парсера, бо саме він задає все інше. Запис шини має сталу форму: `<префікс>[<a>..<b>]`. Префікс — це звичайне ім'я ланцюга (`D`, `ADDR`, `SPI_MISO`). У дужках — два цілих через `..`. І перша ж тонкість: **`a` не зобов'язане бути більшим за `b`**. На схемах живуть обидва записи — `D[7..0]` (старший перший, звичний для шин даних) і `D[0..7]` (молодший перший). Парсер мусить прийняти обидва, не плутаючи напрям.

Заведемо для розібраної шини окрему структуру — вона тримає префікс, обидві межі й позначку, чи це взагалі вектор (бо `CLK` без дужок — теж легітимний вхід, просто скаляр):

```cpp
#include <string>
#include <vector>
#include <cstdio>

// Розібрана шина: префікс, нижня й верхня межі ЯК НАПИСАНО, і чи це вектор.
// Увага: lo/hi тут — це ліве/праве число запису, НЕ «менше/більше».
struct BusName {
    std::string prefix;   // "D" для "D[7..0]"
    int left, right;      // ліва й права межі: 7 і 0 для "D[7..0]"
    bool is_vector;       // false для скаляра "CLK"
};
```

Тепер сам розбір. Він простий, але мусить **відмовлятися** від кривого запису, а не тихо вгадувати: бракує закритої дужки, у дужках не число, дужка є — а `..` немає. Кожен такий випадок — це або одрук, або не-шина, і парсер чесно повертає невдачу, щоб редактор показав попередження, а не сплів нісенітницю.

```cpp
// Розібрати "D[7..0]" → BusName{"D", 7, 0, true}.
// Запис без дужок ("CLK") — це скаляр: BusName{"CLK", 0, 0, false}.
// Кривий запис ("D[7..]", "D[a..b]") — повертаємо false, хай редактор лається.
static bool parse_bus(const std::string& s, BusName& out) {
    size_t lb = s.find('[');
    if (lb == std::string::npos) {           // дужок нема — звичайний скаляр
        out = { s, 0, 0, false };
        return true;
    }
    size_t dd = s.find("..", lb + 1);        // роздільник діапазону
    size_t rb = s.find(']', lb + 1);         // закрита дужка
    if (dd == std::string::npos || rb == std::string::npos || !(lb < dd && dd < rb))
        return false;                        // нема "..", нема "]", або переплутаний порядок

    out.prefix = s.substr(0, lb);
    std::string a = s.substr(lb + 1, dd - lb - 1);   // між '[' і '..'
    std::string b = s.substr(dd + 2, rb - dd - 2);   // між '..' і ']'
    try {
        out.left  = std::stoi(a);            // кине виняток, якщо не число
        out.right = std::stoi(b);
    } catch (...) {
        return false;                        // "[a..b]" — не діапазон
    }
    out.is_vector = true;
    return true;
}
```

Зверніть увагу на дрібницю, що рятує від тихих бід: межі звуться `left`/`right`, **не** `lo`/`hi`. Спокуса назвати їх «нижня» й «верхня» й одразу впорядкувати — пряма дорога до помилки, бо тоді з `D[7..0]` і `D[0..7]` вийде однаковий внутрішній стан, і редактор втратить інформацію про напрям перелічення, яку інженер навмисне заклав у схему. Парсер зберігає запис **як написано**; розв'язувати, де старший біт, — це вже не його справа.

### Крок 2: генерація імен членів і ширина

Маючи `left` і `right`, породжуємо імена. Тут і виявляється сенс «обох боків»: крок ітерації — `+1`, коли діапазон зростає, і `−1`, коли спадає. Інакше цикл або проскочить повз кінець (для `D[7..0]` з кроком `+1` ми б рушили від 7 угору й ніколи не дійшли до 0), або взагалі не виконається.

```cpp
// Розгорнути BusName у список імен членів.
// "D[7..0]" → {"D7","D6",...,"D0"};  "D[0..7]" → {"D0","D1",...,"D7"}.
// Скаляр "CLK" → {"CLK"} (один член — він сам).
static std::vector<std::string> expand(const BusName& bn) {
    std::vector<std::string> members;
    if (!bn.is_vector) {
        members.push_back(bn.prefix);        // скаляр — сам собі єдиний член
        return members;
    }
    int step = (bn.left <= bn.right) ? +1 : -1;   // напрям перелічення
    for (int i = bn.left; ; i += step) {
        members.push_back(bn.prefix + std::to_string(i));   // "D" + "7" = "D7"
        if (i == bn.right) break;            // дійшли до другого кінця — стоп
    }
    return members;
}
```

Цикл навмисне з виходом **усередині**, а не в умові `for`: так він правильно відпрацьовує й вироджений випадок `D[3..3]` — один член `D3`. Якби умова стояла зверху (`i != right`), для рівних меж тіло не виконалося б жодного разу, і член зник би.

Окремо порахуймо **ширину** — скільки членів у шині. Вона знадобиться для звірки розрядності, і рахувати її треба незалежно від напряму: ширина `D[7..0]` і `D[0..7]` однакова — вісім.

```cpp
// Розрядність шини: скільки в ній членів. Не залежить від напряму запису.
static int bus_width(const BusName& bn) {
    if (!bn.is_vector) return 1;                       // скаляр — ширина 1
    int span = (bn.left <= bn.right) ? bn.right - bn.left
                                     : bn.left - bn.right;
    return span + 1;                                   // +1, бо обидва кінці включно
}
```

`+1` тут — типове джерело помилки на одиницю: `D[7..0]` — це **вісім** ліній, не сім, бо включені обидва кінці (і 7, і 0). Хто рахує «7 − 0 = 7», той недолічить одну лінію — і саме вона потім висітиме.

### Крок 3: мапа «ім'я члена → піни»

Тепер з'єднаймо членів із залізом. Кожен пін приймача підписаний іменем члена (`D3` на піні мікросхеми), і з'єднання народжується зі **збігу імен**: член `D3`, розгорнутий із шини, і пін `D3` деталі — це один ланцюг. Тому розгортання шини не потребує власного механізму злиття: воно лише годує загальний збирач нетлиста готовими іменами, а той зливає однойменне.

Зберемо результат у мапу «ім'я ланцюга → перелік пінів». Це і є та структура, яку далі бачить плата:

```cpp
#include <map>

struct Pin { std::string part; int pad; };   // напр. {"U3", 12}

// Ланцюг = ім'я + усі піни, що мусять стати однією міддю.
// Мапа ім'я→піни — це РЕАЛЬНИЙ опис плати; вектор у ній уже не фігурує.
using Netlist = std::map<std::string, std::vector<Pin>>;

// Завести шину у нетлист: розгорнути й приписати кожному членові його пін.
// pins — піни приймача в ТОМУ Ж порядку, що й члени шини.
static void attach_bus(Netlist& net, const BusName& bn,
                       const std::vector<Pin>& pins) {
    std::vector<std::string> members = expand(bn);
    for (size_t i = 0; i < members.size() && i < pins.size(); ++i)
        net[members[i]].push_back(pins[i]);   // D3 → {U3.pad}, D2 → {…}, …
}
```

Маленька, але важлива деталь у заголовку: піни передаються **в тому ж порядку, що й члени**. Член `i` лягає на пін `i`. Якщо порядок переплутати — наприклад, завести члени `D[7..0]` (старший перший) на піни, підписані `D[0..7]` (молодший перший), — кожна лінія сполучиться, ширина збіжиться, ERC змовчить, а дані поїдуть **дзеркально перевернуті**: те, що мало бути старшим бітом, стане молодшим. Це найгидкіший різновид помилки шини, бо він не рве з'єднань — він тихо плутає їхній сенс. Verilog-спільнота наступає на ці граблі рівно так само: оголосити вектор `[0:7]`, а звертатися як до `[7:0]` — і дані «перевертаються», хоч компілятор не скаже й слова. *(Верилогівську конвенцію `[MSB:LSB]` з MSB>LSB і пастку змішування `[7:0]`/`[0:7]` підтверджено мовним стандартом і навчальними матеріалами.)*

### Крок 4: звірка розрядності при склеюванні й стику шин

Найцінніше, що дає розгортання, — це **рання перевірка**. Дві операції над шинами тримаються на одному правилі: скільки ліній зліва, стільки й справа.

**Стик шини з шиною.** Коли `D[7..0]` виходить з одного блоку, а в інший входить однойменна шина, вони — той самий жмут, але лише **за умови однакової ширини**. Заведете восьмирозрядну шину на семирозрядний вхід — один член лишиться без пари.

**Склеювання (конкатенація).** Запис `{CTRL, D[6..0]}` зводить окремий сигнал і семирозрядну шину в один восьмирозрядний жмут; його сумарна ширина (1 + 7 = 8) мусить дорівнювати ширині приймача. Помилитесь у складанні — знову висячий член.

Перевірка проста: розгорнути обидві сторони, порівняти довжини списків. Ось вона для стику двох шин і для склеювання довільного списку частин:

```cpp
// Чи можна стикувати дві шини? Лише якщо однакова розрядність.
static bool widths_match(const BusName& a, const BusName& b) {
    return bus_width(a) == bus_width(b);
}

// Сумарна ширина склеювання {частина, частина, ...}.
// {CTRL, D[6..0]} → 1 + 7 = 8.
static int concat_width(const std::vector<BusName>& parts) {
    int total = 0;
    for (const auto& p : parts) total += bus_width(p);
    return total;
}

// Звірити склеювання з приймачем заданої ширини; інакше — попередити.
static bool check_concat(const std::vector<BusName>& parts, int sink_width) {
    int w = concat_width(parts);
    if (w != sink_width) {
        printf("ПОМИЛКА розрядності: склеювання дає %d ліній, приймач чекає %d\n",
               w, sink_width);
        return false;
    }
    return true;
}
```

![Збіг ширин — усе зчеплено; неспівпадіння — член висить](/book/electronics/analog/net-bus-notation/img/width-check.svg)
*Ліворуч ширини збіглися (8 = 8): кожен член `D0…D7` знайшов свій вхід `Q0…Q7`. Праворуч віддали лише сім ліній на восьмирозрядний вхід — і верхній `Q7` лишився без пари. Редактор бачить це **на розгортанні**, до плати: розрядності не зійшлися — отже, є висячий член.*

Уся сіль у тому, що ця перевірка можлива **тільки після розгортання**, бо порівнюються довжини списків членів, а не самі рядки записів. Тому-то редактори й розгортають шину так рано: розгорнувши, вони задарма отримують ширину, а з нею — і ранній сигнал про неспівпадіння.

### Крок 5: ловля висячих членів (ERC) ще до плати

Звірка ширин ловить неспівпадіння на **відомому** стику. Але буває й тихіший випадок: член оголосили в шині, а **нікуди не завели** — забули провести зрив, не поставили мітку на піні. Ширина приймача тут ні до чого: лінія просто нікуди не йде. Це класичний **висячий ланцюг** (англ. *dangling net*), і розгортання дає матеріал, щоб його викрити: кожен член, що з'явився з шини, мусить осісти в нетлисті щонайменше у **двох** точках (звідки виходить і куди входить). Член, що має лише одну, — підозра на недогляд.

```cpp
// Кожен член шини мусить мати ≥2 пінів (джерело + приймач).
// Член з одним піном — оголошено, але нікуди не заведено: висячий.
static void warn_dangling(const Netlist& net, const BusName& bn) {
    for (const std::string& m : expand(bn)) {
        auto it = net.find(m);
        size_t n = (it == net.end()) ? 0 : it->second.size();
        if (n < 2)
            printf("ПОПЕРЕДЖЕННЯ: член %s шини %s[...] висить (пінів: %zu)\n",
                   m.c_str(), bn.prefix.c_str(), n);
    }
}
```

Поріг «менше двох» навмисне грубий — він свідомо ловить і той випадок, коли члена не згадано в нетлисті взагалі (нуль пінів, бо мітку забули геть). Справжні редактори додають винятки (член, навмисне лишений вільним, можна позначити спеціальним прапорцем «не під'єднано», щоб перевірка змовкла) — але кістяк саме такий: **розгорнути шину й перевірити, що кожен її член кудись веде**.

Складімо всі кроки в один прохід — від рядка шини до перевіреного нетлиста:

```cpp
// Повний конвеєр для однієї шини, заведеної на приймач.
static void process_bus(Netlist& net,
                        const std::string& bus_text,        // "D[7..0]"
                        const std::vector<Pin>& sink_pins)  // піни приймача по порядку
{
    BusName bn;
    if (!parse_bus(bus_text, bn)) {                 // 1) розбір
        printf("ПОМИЛКА: не розібрати запис шини '%s'\n", bus_text.c_str());
        return;
    }
    if (bn.is_vector && bus_width(bn) != (int)sink_pins.size())  // 2) звірка ширин
        printf("ПОМИЛКА розрядності: шина %s — %d ліній, приймач — %zu пінів\n",
               bus_text.c_str(), bus_width(bn), sink_pins.size());

    attach_bus(net, bn, sink_pins);                 // 3) розгорнути й завести
    warn_dangling(net, bn);                         // 4) перевірити висячі члени
}
```

Це повний кістяк розгортання: розбір діапазону в обидва боки, генерація імен, мапа на піни, звірка розрядності й ловля висячих членів — усе **до** того, як проєкт поїде в розведення. І все це лінійне за числом членів: розгортання — один прохід, звірка — одне порівняння довжин, перевірка висячих — прохід по членах.

### Шина ↔ регістр порту мікроконтролера

Розгортання живе в редакторі схем, на настільному комп'ютері. Та сама шина має **дзеркальне** життя у прошивці — і розуміти зв'язок між ними варто, бо саме тут схема стуляється з кодом. Коли вісім ліній даних заведено на один порт мікроконтролера, шина `D[7..0]` у залізі є **регістром порту**: одне багатобітне число, де кожен біт сидить на своєму піні. Розгортання шини зі схеми й «розгортання» регістра в коді — це одна й та сама ідея зв'язки «індекс ↔ окрема лінія», тільки в редакторі вона текстова, а в МСU — апаратна.

Те, що редактор робить парсером, мікроконтролер робить **дротами кристала**: біт 7 регістра фізично припаяний до того піна, на який ви завели `D7`. Тому індекс члена зі схеми стає **номером біта** в регістрі один в один — за умови, що ви завели лінії на піни порту по порядку. Виставити всю шину — один запис; апаратура розкладе біти по пінах сама:

```c
// На STM32 порт — це структура регістрів; шину D[7..0] заведено на молодший байт.
#define DATA_PORT   GPIOB

void bus_write(uint8_t value) {
    // Зберегти старші 8 ліній порту, замінити лише молодші 8 — нашу шину.
    DATA_PORT->ODR = (DATA_PORT->ODR & 0xFF00) | value;   // D7..D0 за одну дію
}

uint8_t bus_read(void) {
    return (uint8_t)(DATA_PORT->IDR & 0x00FF);            // прочитати весь вектор
}
```

А «дістати член `D[3]`» у коді — це **вибрати біт 3** маскою. Тут і видно, як зв'язка «індекс ↔ лінія» з редактора оживає в прошивці: член `D[3]` — це біт 3, тобто `1 << 3`.

```c
#define D3_MASK   (1u << 3)        // член D[3] шини = біт 3 регістра порту

int read_d3(void) {
    return (DATA_PORT->IDR & D3_MASK) ? 1 : 0;   // витягти один скаляр зі жмута
}
```

Є й тонший спосіб виставляти окремі лінії — регістр **атомарного встановлення/скидання** (англ. *bit set/reset register*, BSRR). У ньому молодші 16 бітів **вмикають** відповідні піни, старші 16 — **вимикають**; запис туди міняє лише названі біти, не чіпаючи решти й не потребуючи читання-модифікації-запису. Для шини це зручно, коли треба смикнути один-два члени, не зачепивши сусідів:

```c
// Виставити член D[5] у 1, член D[2] у 0 — однією атомарною дією, без R-M-W.
void set_d5_clear_d2(void) {
    DATA_PORT->BSRR = (1u << 5)          // молодші 16 бітів: ВСТАНОВИТИ біт 5
                    | (1u << (2 + 16));  // старші 16 бітів: СКИНУТИ біт 2
}
```

Так замикається коло від креслення до коду: вектор на схемі ↔ регістр у пам'яті, член шини ↔ окремий біт, індекс зі схеми ↔ номер біта, а напрям `[7..0]` ↔ те, який біт ми домовились вважати старшим. Розгортання в редакторі лише гарантує, що ця відповідність нічого не загубила по дорозі від наміру до плати.

### Складність і пастки

**Складність.** Усі ланки лінійні. Парсер проходить рядок раз; генерація імен — один прохід по членах (їх стільки, скільки ліній у шині); звірка ширин — одне віднімання; ловля висячих — прохід по членах із пошуком у мапі (логарифмічним для `std::map`, сталим для хеш-мапи). Шин на схемі небагато, а членів у кожній — десятки, тож на тлі всього складання нетлиста розгортання нічого не коштує.

А ось пастки — і саме вони псують реальні плати:

- **Інверсний діапазон, що мовчки перевертає дані.** `D[7..0]` і `D[0..7]` оголошують **той самий** набір ліній, але задають **протилежний** порядок перелічення. Якщо джерело й приймач написані по-різному, а піни заведено «як лежать», ширина збіжиться, ERC змовчить — а старший біт стане молодшим. Це не обрив, це **тиха перестановка сенсу**, найгидкіший різновид помилки шини. Запобіжник один: тримати в проєкті **єдину** домовленість про напрям (звично `[N-1..0]`, старший перший) і ніколи не змішувати її з `[0..N-1]` у тій самій лінії даних. Саме тому парсер вище зберігає `left`/`right` **як написано**, а не впорядковує їх: інакше він **стер** би різницю напряму ще до того, як її можна перевірити. *(Та сама пастка в HDL: змішування `[7:0]` і `[0:7]` у Verilog «перевертає» дані без попередження компілятора — підтверджено стандартом мови.)*

- **Неспівпадіння ширин на одиницю.** Класична помилка «±1»: порахували `7 − 0 = 7` і завели сім ліній замість восьми, бо забули, що **обидва** кінці діапазону включні. Або склали `{CTRL, D[7..0]}` (1 + 8 = 9) на восьмирозрядний вхід. Один член лишається без пари; у кращому разі редактор попередить, у гіршому — мовчки лишить лінію висіти. Рятує єдине: рахувати ширину формулою `|left − right| + 1` і звіряти її при **кожному** склеюванні й стику, а не «на око».

- **Кирилична плутанина в іменах.** Найпідступніше. Префікс шини `ADDR` латинськими й `АDDR`, де перша літера — кирилична **А** (Unicode U+0410), для ока **однакові**, а для коду це два різні рядки байтів і дві різні шини. Розгорнуться вони в `ADDR0…` і `АDDR0…` — однаково на вигляд, по-різному в пам'яті, — і члени **не** зіллються за іменем: половина адресних ліній лишиться ні з чим, а схема виглядатиме бездоганно. Це той самий механізм, що й у фішингових доменах-двійниках; Консорціум Unicode веде окремий перелік таких «плутаників» (`confusables.txt`, де латинську A прямо позначено візуально рівною кириличній А — близько 6,5 тисяч таких пар). На рівні розгортання рятує лише звірка **байтів** імен (порівняння рядків нічого не пробачає) і звичка не змішувати розкладки клавіатури в іменах ланцюгів. *(Кодпойнти U+0410/U+0041 і їхній запис у `confusables.txt` підтверджено документацією Unicode.)*

- **Запис, що не схожий на шину.** Парсер мусить чесно **відмовитися** від `D[7..]` чи `D[a..b]`, а не вгадувати. Тиха підстановка («мабуть, мали на увазі…») гірша за відмову: вона породжує ланцюг, якого інженер не малював. Тому всі три перевірки в `parse_bus` — є дужка, є `..`, у межах число — обов'язкові, і будь-яка осічка веде до видимого попередження, а не до здогаду.

Отже, розгортання шини — це чотири прості ланки: розбір діапазону в обидва боки, генерація імен членів, мапа на піни й перевірка (розрядність + висячі члени). Сам алгоритм тривіальний; уся вага — у крайових випадках, бо саме після розгортання вектор зникає, і виправляти стає нíчого. Хто бачить за товстою лінією вісім звичайних ланцюгів і знає, де розгортання мовчить — інверсний напрям, ширина на одиницю, кирилична літера, — той ловить ці тихі помилки на схемі, де їх іще видно, а не на платі, де вже пізно.
