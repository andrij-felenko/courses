# 📋 Специфікація та формати пам'яті піксельних даних YUV і YCbCr

Апаратні відеопроцесори (VPU), блоки захоплення камери (Image Signal Processor — ISP), графічні прискорювачі (GPU) та підсистеми мультимедійного ядра операційної системи (Linux V4L2, DRM/KMS, Android Gralloc) здійснюють обмін нестисненими піксельними даними через строго стандартизовані формати компоновки пам'яті. У цифровому відео просторове розділення компонентів яскравості `Y` та колірності `Cb, Cr` (або `U, V`) реалізується не лише як математична абстракція, а й як фізичне групування байтів у системній пам'яті DRAM.

Цей довідник надає повну технічну специфікацію площинних (planar), напівплощинних (semi-planar) та упакованих (packed) форматів кодування кольору, формули розрахунку вирівнювання рядків (stride/pitch), структурацію буферів у ядрах V4L2 та DRM/KMS, а також особливості 10-бітних форматів для відео з розширеним динамічним діапазоном (HDR).

## Класифікація апаратних розкладок пам'яті

Кожен піксельний формат визначає порядок розміщення компонентів колірного простору у лінійній адресації оперативної пам'яті. Вибір конкретної апаратної розкладки зумовлений архітектурою крізних шин DMA (Direct Memory Access), шинами даних графічного прискорювача та способом організації кеш-пам'яті відеокодеків.

За принципом фізичного структурування байтів усі формати поділяються на три великі категорії:

### 1. Площинні формати (Planar Formats)

У площинних форматах кожна з трьох колірних компонентів (`Y`, `U` та `V`) виділяється у власний суцільний безперервний масив пам'яті, який називається площиною (plane). Кадр складається з трьох послідовних площин, розташованих одна за одною.

Площинна організація є оптимальною для програмних алгоритмів фільтрації та стиснення зображень, оскільки дозволяє процесору обробляти матрицю яскравості `Y` як монохромне зображення через векторайзер SIMD (NEON, AVX-512) без необхідності деінтерлівінгу (пропускання байтів колірності).

Найважливішими представниками площинних форматів є:
- `I420 (YUV420p)`: Послідовно розміщує площину яскравості `Y`, потім площину синьої колірності `U (Cb)`, а за нею — площину червоної колірності `V (Cr)`.
- `YV12`: Повністю аналогічний `I420`, але порядок колірних площин інвертовано: за площиною `Y` йде площина `V (Cr)`, а в кінці — площина `U (Cb)`.
- `YUV444p`: Площинний формат без субдискретизації, де кожна з трьох площин (`Y`, `U`, `V`) має повний розмір `W × H`.

### 2. Напівплощинні формати (Semi-Planar Formats)

У напівплощинних форматах кадр розділяється строго на дві окремі площини:
1. Перша площина містить усі значення яскравості `Y` для кожного пікселя кадру (розмір `W × H` байтів).
2. Друга площина містить об'єднані колірнорізницеві компоненти `U` та `V`, які записуються з чергуванням продуктів у кожній парі байтів (`U, V, U, V...` або `V, U, V, U...`).

Напівплощинна структура є золотим стандартом для апаратних відеодекодерів (NVDEC у NVIDIA, QuickSync у Intel, VPU у ARM SoC), оскільки дозволяє графічному прискорювачу викликом одного API передавати колірну площину `UV` як двоканальну 2D-текстуру (формат `RG88` у OpenGL / Vulkan).

Найважливіші напівплощинні формати:
- `NV12`: Перша площина `Y`, друга площина — `U` і `V` із чергуванням, де `U` передує `V` (`U0, V0, U1, V1...`). Основний формат для Linux VA-API, DirectX Video Acceleration (DXVA) та GStreamer.
- `NV21`: Аналогічний `NV12`, але у другій площині `V` передує `U` (`V0, U0, V1, U1...`). Використовується за замовчуванням у стекі Android Camera NDK та підсистемі MediaCodec.

### 3. Упаковані формати (Packed / Interleaved Formats)

У впорядкованих упакованих форматах усі компоненти `Y`, `U` та `V` об'єднуються в єдиний безперервний потік байтів без поділу на окремі площини. Усі значення для сусідніх пікселів розміщуються в пам'яті пліч-о-пліч.

Упаковані формати є стандартними для простих цифрових відеокамер (USB Video Class — UVC), оскільки аналого-цифрові перетворювачі (АЦП) відеосенсорів видають байти по мірі зчитування рядків матриці.

Основні упаковані формати:
- `YUY2 (YUYV)`: Послідовність байтів `Y0, U01, Y1, V01`.
- `UYVY`: Послідовність байтів `U01, Y0, V01, Y1`.
- `RGB24`: Три байти на піксель у порядку `R, G, B`.
- `BGR24`: Три байти на піксель у зворотному порядку `B, G, R` (стандарт Windows DIB та OpenCV).

## Детальний топографічний опис пам'яті для 4:2:0 форматів

### 1. Топологія пам'яті формату I420 (Planar YUV 4:2:0)

Для кадру розміром `W × H` (де `W` та `H` — парні числа):

```
Адреса 0:
+-------------------------------------------------------+
| Площина Y (Luminance)                                 |
| Ширина: W байтів, Висота: H рядків                    |
| Обсяг: W * H байтів                                   |
+-------------------------------------------------------+
Адреса 0 + (W * H):
+-------------------------------------------------------+
| Площина U / Cb (Chroma Blue)                          |
| Ширина: W/2 байтів, Висота: H/2 рядків                |
| Обсяг: (W * H) / 4 байтів                             |
+-------------------------------------------------------+
Адреса 0 + (W * H) + (W * H / 4):
+-------------------------------------------------------+
| Площина V / Cr (Chroma Red)                           |
| Ширина: W/2 байтів, Висота: H/2 рядків                |
| Обсяг: (W * H) / 4 байтів                             |
+-------------------------------------------------------+
```

Розрахунок покажчиків у пам'яті:

:::tabs
```c
const uint8_t *y_plane = base_ptr;
const uint8_t *u_plane = base_ptr + (width * height);
const uint8_t *v_plane = base_ptr + (width * height) + (width * height / 4);
```
```cpp
const auto* y_plane = base_ptr;
const auto* u_plane = base_ptr + (width * height);
const auto* v_plane = base_ptr + (width * height) + (width * height / 4);
```
:::

### 2. Топологія пам'яті формату NV12 (Semi-Planar YUV 4:2:0)

```
Адреса 0:
+-------------------------------------------------------+
| Площина Y (Luminance)                                 |
| Розмір: W * H байтів                                  |
+-------------------------------------------------------+
Адреса 0 + (W * H):
+-------------------------------------------------------+
| Сумісна площина UV (Interleaved Chroma)              |
| Байтовий порядок: U0, V0, U1, V1, U2, V2 ...           |
| Ширина: W байтів, Висота: H/2 рядків                  |
| Обсяг: (W * H) / 2 байтів                             |
+-------------------------------------------------------+
```

Розрахунок покажчиків:

:::tabs
```c
const uint8_t *y_plane  = base_ptr;
const uint8_t *uv_plane = base_ptr + (width * height);
```
```cpp
const auto* y_plane  = base_ptr;
const auto* uv_plane = base_ptr + (width * height);
```
:::

Адресація конкретної компоненти колірності для пікселя з координатами `(x, y)`:

:::tabs
```c
size_t y_offset  = y * stride_y + x;
size_t uv_offset = (y / 2) * stride_uv + (x / 2) * 2;

uint8_t y_val  = y_plane[y_offset];
uint8_t cb_val = uv_plane[uv_offset];     /* Компонента U */
uint8_t cr_val = uv_plane[uv_offset + 1]; /* Компонента V */
```
```cpp
const size_t y_offset  = y * stride_y + x;
const size_t uv_offset = (y / 2) * stride_uv + (x / 2) * 2;

const uint8_t y_val  = y_plane[y_offset];
const uint8_t cb_val = uv_plane[uv_offset];     // Компонента U
const uint8_t cr_val = uv_plane[uv_offset + 1]; // Компонента V
```
:::

## Фізика кроку рядка (Stride / Pitch) та вирівнювання пам'яті

У реальними системами обробки зображень довжина рядка кадру у пам'яті практично ніколи не дорівнює його точній графічній ширині `width`. Сучасні прямі масиви пам'яті DMA вимагають, щоб кожен рядок починався з адреси, кратної розміру шини даних процесора або кеш-ліній (16, 32, 64 або 128 байтів).

Параметр **Stride** (або **Pitch**) визначає повний фізичний крок рядка в байтах, включаючи вирівнювальні порожні байти (padding) наприкінці кожного рядка.

```
+------------------------------------------+---------+
| Корисні піксельні дані рядка (W байтів)  | Padding |
+------------------------------------------+---------+
|<----------------- Stride (P байтів) -------------->|
```

Формула розрахунку вирівняного значення Stride:

:::tabs
```c
size_t align_up(size_t val, size_t alignment) {
    return (val + alignment - 1) & ~(alignment - 1);
}

size_t stride_y  = align_up(width, 64); /* Вирівнювання на 64 байти */
size_t stride_uv = align_up(width, 64);
```
```cpp
constexpr size_t align_up(size_t val, size_t alignment) noexcept {
    return (val + alignment - 1) & ~(alignment - 1);
}

size_t stride_y  = align_up(width, 64); // Вирівнювання на 64 байти
size_t stride_uv = align_up(width, 64);
```
:::

### Наслідки ігнорування Stride

Якщо програма обчислює адресу пікселя за спрощеною формулою `ptr[y * width + x]` замість `ptr[y * stride + x]`, кожна наступна лінія кадру буде зсуватися на `(stride - width)` байтів. На екрані це призведе до важкого геометричного спотворення — зображення «попливе» по діагоналі з викривленням кольорів та аварійним збоєм читання пам'яті на останніх рядках.

## Апаратні інтерфейси ядра Linux: V4L2 та DRM/KMS

У системному програмуванні для Linux робота з піксельними форматами реалізується через дві головні підсистеми ядра:

### 1. Підсистема Video4Linux2 (V4L2)

Драйвери відеозахоплення камери виділяють буфери у пам'яті через структуру `v4l2_format`. Для форматів YUV використовується два методи опису:
- **Single-Planar API (`V4L2_BUF_TYPE_VIDEO_CAPTURE`):** Кадр з усіма його площинами описується єдиним неперервним масивом пам'яті (`struct v4l2_pix_format`). Використовується для форматів `YUYV`, `NV12`, `I420`, якщо драйвер гарантує суцільність кадру.
- **Multi-Planar API (`V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`):** Кожна площина кадру описується окремим незалежним покажчиком та власним розміром у структурі `v4l2_pix_format_mplane`. Це необхідно для складних ISP-контролерів, які записують площину `Y` та площину `UV` у різні фізичні банки оперативної пам'яті.

Коди FourCC у V4L2 задаються макросом `v4l2_fourcc('N', 'V', '1', '2')`.

### 2. Підсистема Direct Rendering Manager (DRM / KMS)

У графічному ядрі Linux для виведення відео на дисплей через сканер кадру (display engine) використовується драйвер DRM/KMS. Буфери описуються структурами `drm_mode_fb_cmd2`.

Приклад конфігурації DRM-фреймбуфера для формату `DRM_FORMAT_NV12`:

:::tabs
```c
struct drm_mode_fb_cmd2 fb_cmd = {0};
fb_cmd.width = 1920;
fb_cmd.height = 1080;
fb_cmd.pixel_format = DRM_FORMAT_NV12; /* FourCC NV12 */
fb_cmd.handles[0] = gem_handle_y;       /* Диспетчер GEM для площини Y */
fb_cmd.pitches[0] = 1920;              /* Stride площини Y */
fb_cmd.offsets[0] = 0;

fb_cmd.handles[1] = gem_handle_uv;      /* Диспетчер GEM для площини UV */
fb_cmd.pitches[1] = 1920;              /* Stride площини UV */
fb_cmd.offsets[1] = 1920 * 1080;       /* Зсув до площини UV */
```
```cpp
drm_mode_fb_cmd2 fb_cmd{};
fb_cmd.width = 1920;
fb_cmd.height = 1080;
fb_cmd.pixel_format = DRM_FORMAT_NV12; // FourCC NV12
fb_cmd.handles[0] = gem_handle_y;       // Диспетчер GEM для площини Y
fb_cmd.pitches[0] = 1920;              // Stride площини Y
fb_cmd.offsets[0] = 0;

fb_cmd.handles[1] = gem_handle_uv;      // Диспетчер GEM для площини UV
fb_cmd.pitches[1] = 1920;              // Stride площини UV
fb_cmd.offsets[1] = 1920 * 1080;       // Зсув до площини UV
```
:::

Завдяки розділенню покажчиків `handles` та зсувів `offsets` підсистема DRM/KMS дозволяє показувати відео безпосередньо з буферів апаратного декодера без проміжного копіювання даних у пам'яті (Zero-Copy Video Pipeline).

## 10-бітні формати відео з розширеним динамічним діапазоном (HDR)

Із впровадженням стандартів HDR10 та BT.2020 класичне 8-бітне подання пікселів (`256` рівнів на канал) виявилося недостатнім: на плавних градієнтах яскравості виникав ступеневий артефакт (banding). Сучасне відео використовує 10-бітне або 12-бітне подання (`1024` рівні на канал).

Оскільки процесори обробляють байти, 10-бітні значення упаковуються у 16-бітні слова (uint16_t). Найпоширенішим апаратним 10-бітним форматом є **P010**:

- **P010 (Semi-Planar 4:2:0 10-bit):**
  Будова повністю аналогічна `NV12`, але кожен елемент `Y`, `U` та `V` зберігається у 16-бітному числі (2 байти). 10 біт корисних даних вирівнюються за старшим бітом (MSB-aligned), а 6 молодших бітів заповнюються нулями:

```
Біти 16-бітного слова: [ D9 D8 D7 D6 D5 D4 D3 D2 D1 D0 | 0  0  0  0  0  0 ]
Значення:              |<------- 10 біт даних ------->|<-- 6 біт нулів -->|
```

Таке вирівнювання за старшим бітом дозволяє графічним прискорювачам зчитувати 10-бітові формати P010 через ззвичайні 16-бітні текстурні блоки без виконання додаткових побітових зсувів у шейдерах.

Розуміння специфіки розкладок пам'яті `YUV` та `YCbCr` дозволяє розробникам будувати високоефективні мультимедійні системи з прямим апаратним проходженням даних (Zero-Copy) від сенсора камери до джерела відображення на дисплеї.
