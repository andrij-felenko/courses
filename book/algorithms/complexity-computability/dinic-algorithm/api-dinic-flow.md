# 📋 Специфікація інтерфейсу обчислення максимального потоку (DinicFlow)

Цей нормативний документ визначає повний інтерфейсний контракт, сигнатури методів, структури даних, перед- та післяумови, гарантії часової і просторової складності, модель потокобезпечності, динамічне оновлення місткостей, схеми REST/JSON-сервісів, інтерфейси телеметрії, а також формати серіалізації для бібліотечного модуля знаходження максимального потоку та мінімального розрізу на базі алгоритму Дініца (`DinicFlow`).

## 1. Архітектурний огляд та життєвий цикл компонента

Модуль `DinicFlow` є високопродуктивним детермінованим компонентом комбінаторної оптимізації. Він інкапсулює алгоритм Дініца за фасадною абстракцією, розділяючи життєвий цикл на три суворо розмежовані фази:
1. **Фаза побудови топології (Graph Construction Phase):** динамічне або пакетне додавання вершин та орієнтованих дуг з відповідними пропускними спроможностями.
2. **Фаза обчислень (Execution / Solving Phase):** фазовий запуск пошуку в ширину (BFS) для побудови рівневих підграфів та пошуку в глибину (DFS) зі збереженням вказівників `ptr` для проштовхування блокуючих потоків.
3. **Фаза запитів та інспекції (Query & Inspection Phase):** зчитування обчислених значень максимального потоку, отримання завантаженості окремих фізичних ребер, виділення мінімального `s-t` розрізу та експорт результатів у стандартні формати.

```
       ┌─────────────────┐
       │  Uninitialized  │
       └────────┬────────┘
                │  DinicFlow(V) / dinic_create(V)
                ▼
       ┌─────────────────┐
       │   Configured    │ ◄──────────────────────┐
       └────────┬────────┘                        │
                │  add_edge(u, v, cap)            │
                ▼                                 │
       ┌─────────────────┐                        │
       │ Graph Built     │ ◄──────────┐           │ reset_flow()
       └────────┬────────┘            │           │
                │  solve(s, t)        │ update()  │
                ▼                     │           │
       ┌─────────────────┐            │           │
       │     Solved      ├────────────┴───────────┘
       └────────┬────────┘
                │  min_cut(s) / get_flow(e)
                ▼
       ┌─────────────────┐
       │ Extracted Data  │
       └─────────────────┘
```

### Модель скінченного автомата станів (FSM):
- **Uninitialized:** пам'ять під системні масиви не виділена; будь-які виклики обчислень повертають помилку ініціалізації.
- **Configured:** виділено базові масиви для заданої кількості вершин `|V|`. Об'єкт готовий до прийому ребер.
- **Graph Built:** ребра додано в списки суміжності. Можливе динамічне доповнення або зміна місткостей.
- **Solved:** виконано метод `solve(s, t)`. Кожне ребро містить розрахований потік `flow`, а залишкова мережа не містить шляхів між джерелом і стоком (`dist_f(s, t) = ∞`).
- **Extracted Data:** виконано аналіз мінімального розрізу; об'єкт може бути скинутий у стан `Configured` через метод `reset_flow()`.

## 2. Структури даних та дескриптори

Інтерфейс параметризується числовим типом потоку `FlowType` (за замовчуванням 64-бітне знакове ціле `int64_t`, що запобігає переповненню розрядної сітки при великих сумарних значеннях).

### 2.1. Структура `FlowEdge<FlowType>`
Містить повну інформацію про конкретне орієнтоване ребро мережі:

| Поле | Тип | Опис та обмеження |
|---|---|---|
| `from` | `int32_t` | Індекс початкової вершини дуги (`0 ≤ from < |V|`). |
| `to` | `int32_t` | Індекс кінцевої вершини дуги (`0 ≤ to < |V|`). |
| `capacity` | `FlowType` | Початкова фізична пропускна спроможність (`capacity ≥ 0`). |
| `flow` | `FlowType` | Розрахований спрямований потік через дугу (`0 ≤ flow ≤ capacity`). |
| `id` | `uint32_t` | Унікальний монотонно зростаючий числовий дескриптор ребра. |

Методи-помічники структури:
- `residual_capacity()`: повертає невикористаний залишок пропускної спроможності `capacity - flow`.
- `is_saturated()`: повертає булевий прапорець повного насичення дуги (`flow == capacity`).

### 2.2. Структура `CutResult<FlowType>`
Інкапсулює результат декомпозиції графа на дві неперетинні підмножини мінімального розрізу:

| Поле | Тип | Опис |
|---|---|---|
| `in_source_set` | `std::vector<bool>` | Булевий масив розмірності `|V|`. Значення `true` відповідає множині `S` (досяжні з `s` у залишковій мережі), значення `false` — множині `T`. |
| `cut_capacity` | `FlowType` | Сумарна пропускна спроможність ребер, що перетинають розріз від `S` до `T`. Суворо дорівнює значенню `max_flow`. |
| `cut_edge_ids` | `std::vector<uint32_t>` | Перелік числових ідентифікаторів насичених ребер, які перетинають границю розрізу від множини `S` до `T`. |

## 3. Програмний інтерфейс (C++ та C API)

Нижче наведено нормативні декларації публічного API модуля `DinicFlow` мовами C++ та C.

```cpp
#ifndef DINIC_FLOW_HPP
#define DINIC_FLOW_HPP

#include <cstdint>
#include <vector>
#include <limits>
#include <string>
#include <stdexcept>

namespace flow {

enum class Status {
    Success = 0,
    InvalidVertex = 1,
    NegativeCapacity = 2,
    SameSourceSink = 3,
    UnconnectedGraph = 4,
    OverflowDetected = 5
};

template <typename FlowType = int64_t>
struct FlowEdge {
    int32_t from;
    int32_t to;
    FlowType capacity;
    FlowType flow;
    uint32_t id;

    FlowType residual_capacity() const { return capacity - flow; }
    bool is_saturated() const { return flow >= capacity; }
};

template <typename FlowType = int64_t>
struct CutResult {
    std::vector<bool> in_source_set;
    FlowType cut_capacity;
    std::vector<uint32_t> cut_edge_ids;
};

template <typename FlowType = int64_t>
class IDinicFlow {
public:
    virtual ~IDinicFlow() = default;

    // Додавання орієнтованого ребра from -> to.
    // Повертає унікальний ідентифікатор доданого ребра.
    virtual uint32_t add_edge(int32_t from, int32_t to, FlowType cap, FlowType rev_cap = 0) = 0;

    // Обчислення максимального потоку від source до sink
    virtual FlowType solve(int32_t source, int32_t sink) = 0;

    // Обчислення максимального потоку з масштабуванням місткостей
    virtual FlowType solve_scaled(int32_t source, int32_t sink, FlowType min_delta = 1) = 0;

    // Отримання поточного потоку через ребро за його ідентифікатором
    virtual FlowType get_flow(uint32_t edge_id) const = 0;

    // Отримання повної інформації про ребро
    virtual FlowEdge<FlowType> get_edge_info(uint32_t edge_id) const = 0;

    // Виділення мінімального розрізу
    virtual CutResult<FlowType> extract_min_cut(int32_t source) const = 0;

    // Зміна місткості ребра без повної перебудови графа
    virtual void update_capacity(uint32_t edge_id, FlowType new_capacity) = 0;

    // Скидання всіх потоків до нуля для повторного обчислення
    virtual void reset_flow() = 0;

    // Повне очищення графа
    virtual void clear() = 0;

    // Експорт графа у формат DIMACS
    virtual std::string export_dimacs(int32_t source, int32_t sink) const = 0;
};

} // namespace flow

#endif // DINIC_FLOW_HPP
```

## 4. Детальна специфікація контрактів методів

### 4.1. `add_edge(from, to, cap, rev_cap = 0)`
- **Призначення:** створення орієнтованого ребра від вершини `from` до вершини `to` з пропускною спроможністю `cap` та відповідного зворотного залишкового ребра від `to` до `from` з місткістю `rev_cap`.
- **Семантика аргументів:**
  - `from`: цілочисельний індекс вихідної вершини.
  - `to`: цілочисельний індекс кінцевої вершини.
  - `cap`: допустима пряма пропускна спроможність.
  - `rev_cap`: допустима зворотна пропускна спроможність (для неорієнтованих мереж передається `rev_cap = cap`).
- **Передмови (Preconditions):**
  - `0 ≤ from < num_vertices` та `0 ≤ to < num_vertices`.
  - `cap ≥ 0` та `rev_cap ≥ 0`.
- **Післяумови (Postconditions):**
  - У списки суміжності графа додаються два внутрішні реберні записи.
  - Присвоюється числовий дескриптор `edge_id`.
  - Поточний потік обох доданих дуг встановлюється в `0`.
- **Повернене значення:** унікальний дескриптор `edge_id` типу `uint32_t`.

### 4.2. `solve(source, sink)`
- **Призначення:** ініціалізація та виконання повного циклу алгоритму Дініца для знаходження максимального потоку між виділеними полюсами.
- **Внутрішній алгоритмічний протокол:**
  1. Ініціалізується акумулятор сумарного потоку `total_flow = 0`.
  2. Запускається підпрограма `bfs(source, sink)`, яка будує рівневий підграф `level[]`. Якщо `level[sink] == -1`, алгоритм негайно переходить до кроку 6.
  3. Масив вказівників `ptr[]` ініціалізується початковими індексами вихідних ребер для кожної вершини.
  4. У циклі викликається підпрограма `dfs(source, sink, INF)`. Кожен успішний виклик знаходить розширювальний шлях у рівневому графі, оновлює прямий і зворотний потоки на величину пляшкового горла `Δ` та збільшує `total_flow += Δ`.
  5. Коли `dfs` повертає 0 (досягнуто блокуючого потоку поточної довжини), керування повертається до кроку 2.
  6. Повертається накопичене значення `total_flow`.
- **Передмови (Preconditions):**
  - `0 ≤ source < num_vertices` та `0 ≤ sink < num_vertices`.
  - `source ≠ sink`.
- **Післяумови (Postconditions):**
  - Усі ребра мережі задовольняють умовам допустимості: `0 ≤ flow ≤ capacity`.
  - Для всіх проміжних вершин `u ∉ {source, sink}` виконується закон збереження потоку: `∑ f_{in}(u) = ∑ f_{out}(u)`.
  - Залишкова мережа не містить жодного шляху з ненульовою місткістю від `source` до `sink`.
- **Асимптотичні часові гарантії:**
  - Загальні довільні графічні мережі: `O(V² · E)`.
  - Мережі з одиничними пропускними спроможностями ребер (`c(e) = 1`): `O(E · min(V^(2/3), E^(1/2)))`.
  - Одиничні мережі (двочасткове паросполучення, де кожна вершина має `deg_in ≤ 1` або `deg_out ≤ 1`): `O(E · √V)`.

### 4.3. `solve_scaled(source, sink, min_delta = 1)`
- **Призначення:** оптимізоване обчислення максимального потоку на мережах з великими цілими пропускними спроможностями за допомогою техніки бітового масштабування місткостей (Capacity Scaling).
- **Механізм функціонування:**
  - Алгоритм визначає максимальну місткість ребра в мережі `U = max c(e)` і обчислює початковий масштаб як максимальний ступінь двійки `Δ = 2^⌊log₂ U⌋`.
  - На кожній ітерації алгоритм Дініца запускається виключно на підграфі `Δ`-залишкової мережі, що містить ребра із залишковою місткістю `c_f(e) ≥ Δ`.
  - Після досягнення блокуючого потоку для поточного `Δ`, параметр ділиться навпіл: `Δ = Δ / 2`.
  - Процес завершується, коли `Δ < min_delta`.
- **Переваги:** на розріджених графах з великими числовими вагами забезпечує строгу оцінку `O(V · E · log U)` незалежно від найгірших патологічних топологій.

### 4.4. `extract_min_cut(source)`
- **Призначення:** визначення мінімального `s-t` розрізу на базі фінального стану залишкової мережі після завершення методу `solve()`.
- **Алгоритм вилучення:**
  1. Виконується один обхід у ширину (BFS) від вершини `source`, переходячи виключно через ребра з додатною залишковою місткістю `c_f(u, v) > 0`.
  2. Усі досяжні вершини позначаються прапорцем `true` у масиві `in_source_set` (множина `S`). Усі недосяжні вершини отримують `false` (множина `T`).
  3. Проходиться повний список ребер. Ребро `u → v` включається до списку `cut_edge_ids`, якщо `in_source_set[u] == true`, а `in_source_set[v] == false`.
- **Гарантії:** сумарна пропускна спроможність виділених дуг розрізу точно дорівнює максимальному потоку `val(f) = cap(S, T)`.
- **Часова складність:** лінійна відносно розміру графа `O(V + E)`.

### 4.5. Динамічне оновлення місткостей (`update_capacity`)
У багатьох реальних сценаріях (динамічна маршрутизація пакетів у телекомунікаціях, перепланування логістичних маршрутів) пропускні спроможності окремих ребер змінюються в часі. Повний перезапуск алгоритму з нуля («холодний старт») вимагав би зайвих обчислень.

Метод `update_capacity(edge_id, new_capacity)` реалізує стратегію «гарячого рестарту» (Warm Restart):
1. **Збільшення місткості (`new_capacity > capacity`):** оскільки початковий знайдений потік залишається повністю допустимим, збільшення місткості дуги лише додає нові можливості для проштовхування додаткового потоку. Алгоритм не скидає раніше знайдений потік, а просто продовжує виконання фаз Дініца в оновленій залишковій мережі. Це дозволяє дорахувати дельту потоку за частки мілісекунди.
2. **Зменшення місткості без порушення балансу (`new_capacity ≥ flow`):** значення `capacity` просто оновлюється в структурі ребра, а залишок `c_f` перераховується. Поточний максимальний потік зберігається.
3. **Зменшення місткості нижче поточного потоку (`new_capacity < flow`):** виникає надлишок потоку `excess = flow - new_capacity`. У такому разі модуль виконує процедуру локального скасування потоку (Flow Cancellation) через пошук компенсуючого шляху від кінця дуги назад до джерела, або виконує скидання методом `reset_flow()`.

## 5. Обробка помилок та виняткові ситуації

Інтерфейс забезпечує детерміновану діагностику помилок без виникнення невизначеної поведінки:

1. **`Status::InvalidVertex` (`DINIC_ERR_INVALID_VERTEX`):** виникає при спробі передати номер вершини, який не належить інтервалу `[0, num_vertices - 1]`.
2. **`Status::NegativeCapacity` (`DINIC_ERR_NEGATIVE_CAPACITY`):** виникає при спробі додати ребро з від'ємною місткістю.
3. **`Status::SameSourceSink` (`DINIC_ERR_SAME_SOURCE_SINK`):** фіксується при спробі знайти потік між тотожними вершинами (`source == sink`).
4. **`Status::OverflowDetected` (`DINIC_ERR_OVERFLOW`):** генерується, якщо сумарний потік або проміжна сума перевищує максимальну місткість числового типу `FlowType`.

## 6. Ресурсоємність та оптимізація звернень до пам'яті

Для планування системних ресурсів наведено точні витрати оперативної пам'яті:

| Структура даних | Розмірність C++ (std::vector) | Розмірність C (Forward Star) | Обсяг пам'яті (V=10⁵, E=10⁶) |
|---|---|---|---|
| Списки ребер | `|E_total| · sizeof(Edge) + |V| · 24` | `|E_total| · sizeof(Edge)` | ~48 МБ (64-біт потік) |
| Масиви `head`, `level`, `ptr` | `|V| · (sizeof(int) + sizeof(size_t))` | `|V| · 3 · sizeof(int)` | ~2.4 МБ |
| Черга обходу BFS | `|V| · sizeof(int)` | `|V| · sizeof(int)` | ~0.4 МБ |
| **Разом** | **O(V + E)** | **O(V + E)** | **~51 МБ** |

### Аналіз локальності кешу:
Під час виконання фази BFS процесор послідовно зчитує елементи черги та ітерує по суміжних ребрах. У представленні Forward Star ребра однієї вершини розташовані в пам'яті у вигляді зв'язного списку індексів. 

Для графів з великим коефіцієнтом розгалуження застосовується сортування ребер у пам'яті за початковою вершиною під час ініціалізації (Compact Forward Star), що забезпечує послідовне зчитування цілих блоків кеш-ліній (64 байти) процесора без випадкових стрибків за покажчиками.

## 7. Модель потокобезпечності (Thread-Safety Contract)

1. **Конкурентний доступ:** модифікація структури графа (`add_edge`, `update_capacity`, `clear`) не є потокобезпечною і вимагає зовнішньої синхронізації або ексклюзивного блокування (Unique Lock).
2. **Паралельні запити:** після завершення фази обчислень `solve()` довільна кількість потоків може паралельно викликати методи зчитування `get_flow()`, `get_edge_info()` та `extract_min_cut()` без блокувань (Read-Only Concurrent Safety).
3. **Паралельна декомпозиція рівнів:** на багатоядерних серверах обхід BFS у великих графах розпаралелюється по рівнях. Усі вершини рівня `d` обробляються паралельними потоками пулу задач (Task Thread Pool), оскільки їхні списки суміжності оновлюють рівні вершин строго рівня `d + 1` без стану гонитви за даними (Data Race).

## 8. Мережевий сервіс та JSON Schema (Flow as a Service)

У хмарних мікросервісних архітектурах модуль `DinicFlow` розгортається як високопродуктивний gRPC або REST-сервіс. Нижче наведено специфікацію схеми JSON для міжсервісної взаємодії:

### 8.1. Схема вхідного запиту (`FlowRequest.json`):
- `vertices_count` (int): кількість вершин у графі.
- `source` (int): індекс вузла-джерела.
- `sink` (int): індекс вузла-стоку.
- `scaling` (bool): прапорець активації бітового масштабування місткостей.
- `edges` (масив об'єктів): кожен елемент містить `from`, `to`, `capacity`, та опціональний `rev_capacity`.

### 8.2. Схема вихідної відповіді (`FlowResponse.json`):
- `status` (string): текстовий статус виконання (`SUCCESS`, `INVALID_GRAPH`, `DISCONNECTED`).
- `max_flow` (int64): розрахована величина максимального потоку.
- `phase_count` (int): кількість виконаних рівневих фаз алгоритму.
- `computation_time_microseconds` (int64): час роботи алгоритмічного ядра в мікросекундах.
- `cut_edges` (масив індексів): список ідентифікаторів ребер мінімального розрізу.
- `partition_s` (масив int): перелік вершин, що залишилися в множині джерела.
- `partition_t` (масив int): перелік вершин, що відійшли до множини стоку.

## 9. Патерни інтеграції в інженерні системи

1. **Патерн виявлення пляшкових шийок (Bottleneck Discovery Pattern):** після виконання методу `solve()` система зчитує всі ребра, повернені `extract_min_cut()`. Ці дуги є критичними магістралями: збільшення пропускної спроможності будь-якого ребра поза розрізом не змінить загальну пропускну здатність мережі, тоді як розширення ребер мінімального розрізу безпосередньо збільшує максимальний потік.
2. **Патерн балансування циркуляції з вимогами у вузлах (Circulation with Demands):** якщо кожна вершина `v` має виробництво або споживання `d(v)`, задача зводиться до `DinicFlow` додаванням фіктивного супер-джерела `S*` та супер-стоку `T*`. Джерело `S*` з'єднується з вузлами виробництва (`d(v) < 0`), а вузли споживання (`d(v) > 0`) з'єднуються зі стоком `T*`. Якщо максимальний потік насичує всі вихідні ребра `S*`, циркуляція є допустимою.
3. **Патерн розв'язання задачі відновлення контуру зображення:** у медичній діагностиці та автономному керуванні розріз мінімальної місткості в решітчастому графі пікселів точно відокремлює контури внутрішніх органів або перешкод на дорозі з субпіксельною точністю.

## 10. Інтерфейс спостереження подій та телеметрії (Telemetry & Observers)

Для профілювання та візуалізації роботи алгоритму в навчальних або моніторингових системах модуль підтримує зворотні виклики через абстракцію слухача подій (Observer Pattern):

- `on_phase_started(phase_id, bfs_distance)`: сигналізує про початок нової фази BFS та мінімальну знайдену відстань до стоку. Дозволяє фіксувати монотонне зростання відстані між фазами.
- `on_path_augmented(path_vertices, pushed_flow)`: викликається при кожному успішному знаходженні розширювального шляху під час DFS. Передає послідовність ідентифікаторів вершин та обсяг проштовхнутого потоку.
- `on_edge_saturated(edge_id)`: фіксує момент повного вичерпання залишкової місткості дуги та її виключення з допустимого підграфа поточної фази.
- `on_phase_finished(phase_id, total_phase_flow)`: підбиває підсумки обсягу проштовхнутого потоку в поточній фазі та кількість перевірених дуг.

### Рівні деталізації телеметрії (Logging Levels):
1. **Production Mode (За замовчуванням):** обробники подій відключені на етапі компіляції (`constexpr if`), що усуває будь-який накладний оверхед на виклики функцій.
2. **Debug Mode:** фіксуються лише межі фаз та фінальний обсяг максимального потоку.
3. **Trace Mode:** повне логування кожного розширювального шляху та насичення ребер для покрокової візуалізації у графічних інтерфейсах або генерації анімацій.

## 12. Формати серіалізації та експорту

Модуль підтримує експорт та імпорт мереж у міжнародних форматах:

### 12.1. Формат DIMACS Max-Flow
Міжнародний текстовий формат для стандартизованого бенчмаркінгу алгоритмів на графах:

```
c Файл конфігурації мережі DIMACS
p max 6 8
n 1 s
n 6 t
a 1 2 10
a 1 3 10
a 2 4 4
a 2 5 8
a 3 5 9
a 4 6 10
a 5 6 10
a 4 3 3
```

- Рядок `p max NODES ARCS` задає загальну кількість вершин та дуг.
- Рядки `n ID s` та `n ID t` визначають ідентифікатори джерела та стоку.
- Рядки `a FROM TO CAPACITY` описують орієнтовані дуги з пропускними спроможностями.

### 12.2. Формат Graphviz DOT для візуалізації розрізів
Модуль генерує скрипти візуалізації DOT, де автоматично підсвічуються насичені ребра мінімального розрізу:
- Вершини множини `S` фарбуються у світло-синій колір (`fillcolor="#eaf0fd"`).
- Вершини множини `T` фарбуються у світло-червоний колір (`fillcolor="#fdecea"`).
- Ребра розрізу відображаються жирними червоними лініями з підписами потоку та місткості `flow / cap`.
- Ребра з нульовим потоком позначаються сірими пунктирними стрілками.
