# ⚙️ Від варіанта до оцінки: скільки кроків насправді

Варіант обіцяє не лише зупинку. Він одразу вручає число: проходів не буде більше, ніж його стартове значення. В алгоритмі Евкліда варіант — це `b`, тож для `b₀ = 1000000` обіцянка звучить так: «не більш ніж мільйон проходів». Обіцянка чесна. А тепер порахуймо, скільки проходів цикл робить насправді в найгіршому випадку серед усіх пар з `b ≤ 10⁶`:

```
найгірша пара при b ≤ 10⁶:      (1346269, 832040)
проходів насправді:              29
обіцяла обмежувальна функція:    1000000
розрив:                          у 34 483 рази
```

Двадцять дев'ять проти мільйона. Варіант не збрехав — просто його стартове значення виявилося оцінкою, від якої користі, як від «вода закипить не пізніше, ніж за тиждень».

Тут і ховається непорозуміння, через яке варіант часто вважають придатним лише для доведення зупинки. Оцінку дає **не варіант**. Оцінку дає **закон, за яким варіант спадає**. Варіант відповідає на питання «чи спиниться». Закон спуску відповідає на питання «коли». Це різні питання, і друге доводиться ставити окремо — а щоб поставити його вдало, спершу треба зрозуміти, чому навпростець воно не ставиться.

## Питання, на яке немає відповіді

Спитаймо навпростець: як швидко падає варіант? Для лічильника відповідь очевидна — на одиницю щокроку. Поставмо те саме питання Евклідові. Нехай `b = 100`; яким буде `b` після проходу?

```
b = 100  →  наступне b = a mod 100  —  будь-що з проміжку [0, 99]

   a = 200  →  b′ = 0     обвал просто до дна
   a = 199  →  b′ = 99    спад аж на одиницю
```

Відповіді немає. Спад залежить не від `b`, а від пари `(a, b)` цілком — від того, скільки разів `b` вкладається в `a`. Рекурентність «наступне значення варіанта через попереднє» тут не пишеться взагалі: варіант не знає власного майбутнього. Питання поставлено невдало — і жодна кмітливість не витягне відповідь, якої в самій величині немає.

Тож перевернімо його.

**Замість «як швидко падає `v`» питаймо: яким мусить бути `v₀`, щоб вистачило на `k` кроків.**

Позначмо `W(k)` — найменше значення варіанта, з якого ще можливо зробити `k` кроків. Це найдешевший, найощадливіший прогін: цикл ледве-ледве шкребе, віддає щокроку рівно стільки, скільки мусить, і ні крихти більше. Тоді твердження, заради якого все й затівалось, читається саме собою:

```
v₀ < W(k)   ⟹   кроків буде менше за k
```

Бо якби з `v₀` вдалося зробити `k` кроків, то `v₀` було б одним зі стартів, що на `k` кроків спроможні, — а `W(k)` за означенням найменший з них. Отже, число кроків обмежене згори тим найбільшим `k`, для якого `W(k)` ще влазить у `v₀`. **Межа на кроки — це просто обернена функція до `W`.**

Виграш у тому, що `W` будується **назад**, від дна: `W(0)` — це дно, а щоб дістати `W(k+1)`, питаємо «який найдешевший стан уміє ступити в щось вартістю `W(k)`». Назад питання має відповідь завжди, бо крок обираємо ми самі — і обираємо найощадливіший. Уперед доводилось вгадувати чужий вибір; назад ми його диктуємо.

![Ліворуч — драбина, яку будуємо назад від дна: кожна сходинка W(k) це найменший старт, з якого ще можливо k кроків. Праворуч — три закони спуску й три межі, що з них виходять](/book/algorithms/complexity-computability/loop-variant/img/inverted-question.svg)

*Той самий механізм на три алгоритми. Питання «як швидко падає `v`» відповіді часто не має — спад залежить від усього стану. Питання «на скільки вистачить `v₀`» має відповідь завжди: будуємо найдешевший прогін назад від дна. `W` росте, і межа на кроки — обернена до неї: лінійна `W` дає лінійну межу, подвоєння дає логарифм, Фібоначчі дає логарифм за основою φ.*

> 🔧 **Навіщо це.** Зворотна побудова віддає не лише число. Найдешевший прогін, який ти виписав, — це **конкретний найгірший вхід**, готовий лягти в тест. Для двійкового пошуку це буде `n = 2ᵏ⁻¹`, для Евкліда — пара сусідніх чисел Фібоначчі. Оцінка, здобута наосліп із рекурентності, дає число й мовчить; оцінка, здобута назад, дає число **і пред'явника**. Коли профайлер потім показує сплеск, у тебе вже є вхід, на якому цей сплеск відтворюється щоразу.

Найпростіший випадок перевіряє механізм на міцність. Лічильник `while n > 0: n -= 1`: дно `W(0) = 0`, і щоб дозволити ще один крок, треба рівно на одиницю більше, тож `W(k) = k`. Обернена до тотожності — тотожність: `k ≤ v₀`. Тут наївна межа «стільки, скільки стартове значення» і є правильна. Саме тому вона так переконливо збиває з пантелику деінде: на лічильнику вона точна, і рука сама тягнеться перенести її на решту.

## Двійковий пошук: драбина, що подвоюється

Візьмімо [двійковий пошук](book:algorithms/binary-search) — він тримає вікно, у якому ще може бути ціль, і щопроходу відкидає половину; варіант — ширина цього вікна. Ось код, який рахує і водночас стежить за власним варіантом:

```python
def bsearch(a, target):
    """Пошук у відсортованому масиві. Вікно — напіввідкрите [lo, hi)."""
    lo, hi = 0, len(a)
    while lo < hi:
        v = hi - lo                     # варіант — ширина вікна
        mid = lo + (hi - lo) // 2       # так, а не (lo + hi) // 2: різниці нема з чого переповнитись
        if a[mid] == target:
            return mid
        if a[mid] < target:
            lo = mid + 1                # ціль правіше: відкидаємо ліву половину РАЗОМ з mid
        else:
            hi = mid                    # ціль лівіше: відкидаємо праву половину разом з mid
        assert hi - lo <= v // 2        # закон спуску, а не просто «впало»
    return -1
```

Придивімось до `assert`. Він стежить не за тим, що варіант «якось» упав, — він стежить за **законом**: `v′ ≤ ⌊v/2⌋`. Ось звідки цей закон береться. У циклі `v ≥ 1`, а `mid = lo + ⌊v/2⌋`, тож `lo ≤ mid < hi`. Дві гілки:

```
гілка a[mid] < target:  lo′ = mid + 1
    v′ = hi − mid − 1 = v − ⌊v/2⌋ − 1 = ⌈v/2⌉ − 1

гілка a[mid] > target:  hi′ = mid
    v′ = mid − lo = ⌊v/2⌋

перевірка при v = 4:  ⌈4/2⌉ − 1 = 1   і   ⌊4/2⌋ = 2   —  обидві ≤ ⌊4/2⌋ = 2
перевірка при v = 5:  ⌈5/2⌉ − 1 = 2   і   ⌊5/2⌋ = 2   —  обидві ≤ ⌊5/2⌋ = 2
перевірка при v = 1:  ⌈1/2⌉ − 1 = 0   і   ⌊1/2⌋ = 0   —  вікно спорожніло, цикл вийшов
```

Обидві гілки вкладаються в `v′ ≤ ⌊v/2⌋`. Тепер будуймо драбину назад. Дно: `W(0) = 0` — порожнє вікно, цикл не заходить. Найменше вікно, з якого можливий бодай один крок, — це `W(1) = 1`. А далі: щоб дозволити ще один крок понад `k`, після проходу мусить лишитися щонайменше `W(k)`, тобто `⌊v/2⌋ ≥ W(k)`. Найменше таке `v` — це `2·W(k)`:

```
W(1) = 1
W(k+1) = 2·W(k)
⟹  W(k) = 2ᵏ⁻¹
```

Драбина подвоюється — отже, обернена до неї логарифмічна. Щоб дозволити `k` кроків, треба `n ≥ 2ᵏ⁻¹`, звідки `k ≤ log₂ n + 1`, тобто `k ≤ ⌊log₂ n⌋ + 1`. Перевірмо на `n = 1000` повним перебором усіх цілей, включно з відсутніми:

```
n = 1000
межа:            ⌊log₂ 1000⌋ + 1 = 9 + 1 = 10
найгірше насправді (перебір усіх 1002 цілей): 10 проходів
```

Межа не просто правильна — вона **досяжна**: знайшовся вхід, що вибирає її до останнього кроку. Це і є ознака того, що драбину побудовано без марнотратства. А `W(k) = 2ᵏ⁻¹` каже й те, який саме вхід треба взяти для найгіршого випадку: розмір, що дорівнює степеню двійки.

## Евклід: чому саме Фібоначчі

Тепер той самий прийом на задачі, де вперед не пройти. [Алгоритм Евкліда](book:math/gcd-euclidean) замінює пару `(a, b)` на `(b, a mod b)`, аж доки `b` не стане нулем; варіант — це `b`, а закону спуску «через саме `b`» тут немає.

Зате назад питання ставиться чудово. Ми хочемо найдешевший крок — такий, що з'їдає якнайменше. Крок Евкліда — це `a mod b`, тобто віднімання `b` від `a` стільки разів, скільки влізе. Кожне таке віднімання обвалює числа. Отже, найощадливіший крок — той, де віднімання відбулося **рівно один раз**:

```
частка 1  ⟺  b ≤ a < 2b  ⟺  a mod b = a − b
```

Будь-яка більша частка збиває `b` швидше — а нам треба повільно. Записуймо цей найдешевший крок навпаки. Якщо після кроку маємо `(b, r)`, то попереду стояло `(a, b)` з `a = b + r`:

```
pred(a, b) = (a + b, a)
```

Запустімо це з дна — з пари `(1, 0)`, на якій цикл спиняється:

```
(1, 0) ← (1, 1) ← (2, 1) ← (3, 2) ← (5, 3) ← (8, 5) ← (13, 8) ← (21, 13) ← …

менше число кожної пари:  0, 1, 1, 2, 3, 5, 8, 13, …   —   це рівно Fₖ
```

Числа Фібоначчі. І вони тут не збіг і не курйоз: `pred` каже «нове `a` = сума двох попередніх», а це **буквально** рекурентність `Fₖ₊₂ = Fₖ₊₁ + Fₖ`. Фібоначчі — це і є найповільніший спуск Евкліда, виписаний навспак. Питати «чому тут вигулькнули числа Фібоначчі» — те саме, що питати, чому в дзеркалі та сама людина.

![Ланцюг пар від дна назад: pred(a, b) = (a + b, a) — і це рівно рекурентність Фібоначчі, тож пари виявляються сусідніми числами Фібоначчі](/book/algorithms/complexity-computability/loop-variant/img/euclid-backwards.svg)

*Найдешевший крок Евкліда — частка 1, тобто `a mod b = a − b`. Обернений до нього крок — це `a = b + r`, сума двох попередніх. Тому, будуючи найощадливіший прогін назад від дна, алгоритм сам виписує числа Фібоначчі: `k` кроків вимагають `b ≥ Fₖ₊₁`, а найменша пара, що вимагає рівно `k` кроків, — це `(Fₖ₊₂, Fₖ₊₁)`.*

Це твердження легко перевірити не вірою, а перебором — просто спитавши в машини найменшу пару для кожного `k`:

```python
def gcd_steps(a, b):
    k = 0
    while b:
        a, b = b, a % b
        k += 1
    return k

# найменша пара a > b > 0, що вимагає k кроків
def min_pair(k, cap=400):
    for b in range(1, cap):
        for a in range(b + 1, 2 * cap):
            if gcd_steps(a, b) >= k:
                return a, b
```

```
k = 1  → (2, 1)     = (F₃, F₂)
k = 2  → (3, 2)     = (F₄, F₃)
k = 3  → (5, 3)     = (F₅, F₄)
k = 4  → (8, 5)     = (F₆, F₅)
k = 5  → (13, 8)    = (F₇, F₆)
…
k = 11 → (233, 144) = (F₁₃, F₁₂)
```

Далі — чиста арифметика. Щоб вистачило на `k` кроків, треба `b ≥ Fₖ₊₁`. Числа Фібоначчі ростуть як степінь золотого перетину, `Fₘ ≈ φᵐ/√5`, де `φ = (1 + √5)/2 ≈ 1.618034`. Обертаємо:

```
b ≥ Fₖ₊₁ ≈ φ⁽ᵏ⁺¹⁾/√5
φ⁽ᵏ⁺¹⁾ ≲ √5 · b
k ≤ log_φ(√5 · b) − 1
```

**Скільки проходів для `b₀ = 10⁶`:**

```
√5 · 10⁶        = 2236068
ln(2236068)     = 14.6202
ln(φ)           = 0.4812118
log_φ(2236068)  = 14.6202 / 0.4812118 = 30.382
k ≤ 30.382 − 1  = 29.382     →     k ≤ 29

найгірша пара при b ≤ 10⁶:  (1346269, 832040) = (F₃₁, F₃₀)   →   29 проходів
```

Двадцять дев'ять — і саме двадцять дев'ять. Оцінка збіглася з дійсністю копійка в копійку, бо будувалася від найдешевшого прогону, а не від переляку.

Ця арифметика має ім'я. Француз Ґабріель Ламе (Gabriel Lamé, 1795–1870) — той самий, чиї параметри пружності носять його прізвище, — 1844 року оприлюднив у *Comptes rendus* Паризької академії наук доведення: число ділень в алгоритмі Евкліда не перевищує **вп'ятеро числа десяткових цифр меншого з чисел**. Звідки та п'ятірка, видно з одного рядка:

```
log_φ(10) = ln(10)/ln(φ) = 2.302585 / 0.4812118 = 4.785
```

Кожна десяткова цифра купує не більш ніж 4.785 кроку — округлили вгору, дістали 5. Оцінка Ламе тримається, і тримається туго: на парі `(13, 8)` виходить рівно 5 кроків при одній цифрі в `b`, тобто множник 5 таки досягається, а не береться про запас. Рік і формулювання — усталений факт, що перевіряється за публікацією. А ось поширене твердження, ніби це перший аналіз складності алгоритму й перше практичне застосування чисел Фібоначчі, — вже оцінка з літератури, а не теорема.

Три оцінки для `b₀ = 10⁶` варто побачити поруч:

```
наївно, «стільки, скільки стартове b»:            1000000
Ламе, по 5 на кожну з 7 цифр:  5 · 7        =          35
через φ:       log_φ(√5·10⁶) − 1            =          29     ← досягається
```

## Коли одного лічильника мало

Досі варіант був одним числом. Тепер — цикл, де жодне окреме число не годиться, і то не в іграшці, а в алгоритмі, що його пишуть постійно: **сортувальна станція** (англ. *shunting yard* — за подібністю до залізничної сортувальної гірки, де вагони розтягують на тимчасові колії й збирають наново). Едсгер Дейкстра опублікував її 1961 року у звіті MR 34/61 амстердамського Математичного центру; вона перетворює звичний інфіксний запис `3 + 4 * 2` на постфіксний `3 4 2 * +`, який рахується стеком без жодних дужок.

Головний цикл робить за прохід рівно одну дію — або **читає** токен, або **знімає** оператор зі стека:

:::tabs
```python
PREC = {"+": 1, "-": 1, "*": 2, "/": 2}

def to_rpn(tokens):
    """Інфікс → постфікс. Один прохід = одна дія."""
    out, ops, i = [], [], 0
    while i < len(tokens) or ops:
        v = (len(tokens) - i, len(ops))          # варіант — ПАРА
        t = tokens[i] if i < len(tokens) else None

        if t is not None and t not in PREC and t not in ("(", ")"):
            out.append(t); i += 1                            # число — одразу у вихід
        elif t == "(":
            ops.append(t); i += 1
        elif t == ")" and ops and ops[-1] == "(":
            ops.pop(); i += 1                                # дужка закрилася
        elif t is not None and t in PREC and (
                not ops or ops[-1] == "(" or PREC[ops[-1]] < PREC[t]):
            ops.append(t); i += 1                            # оператор іде вгору
        else:
            out.append(ops.pop())                            # старший оператор — у вихід

        assert (len(tokens) - i, len(ops)) < v    # кортежі порівнюються словниково
    return out
```
```rust
fn prec(c: char) -> u8 {
    match c { '+' | '-' => 1, '*' | '/' => 2, _ => 0 }
}

fn tok_prec(t: Tok) -> u8 {
    match t { Tok::Op(c) => prec(c), _ => 0 }
}

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
enum Tok { Num(i64), Op(char), LPar, RPar }

/// Інфікс → постфікс. Один прохід = одна дія.
fn to_rpn(tokens: &[Tok]) -> Vec<Tok> {
    let mut out: Vec<Tok> = Vec::new();
    let mut ops: Vec<Tok> = Vec::new();
    let mut i = 0usize;

    while i < tokens.len() || !ops.is_empty() {
        // варіант — ПАРА; кортежі в Rust порівнюються словниково «з коробки»
        let v = (tokens.len() - i, ops.len());

        let t = tokens.get(i).copied();
        let top = ops.last().copied();

        if let Some(n @ Tok::Num(_)) = t {
            out.push(n); i += 1;                             // число — одразу у вихід
        } else if t == Some(Tok::LPar) {
            ops.push(Tok::LPar); i += 1;
        } else if t == Some(Tok::RPar) && top == Some(Tok::LPar) {
            ops.pop(); i += 1;                               // дужка закрилася
        } else if let Some(Tok::Op(c)) = t {
            if top.map_or(true, |x| x == Tok::LPar || tok_prec(x) < prec(c)) {
                ops.push(Tok::Op(c)); i += 1;                // оператор іде вгору
            } else {
                out.push(ops.pop().unwrap());                // старший оператор — у вихід
            }
        } else {
            out.push(ops.pop().expect("незбалансовані дужки"));
        }

        debug_assert!((tokens.len() - i, ops.len()) < v);    // пара впала словниково
    }
    out
}
```
:::

Простежмо `3 + 4 * 2` і подивімось, що взагалі тут спадає:

```
дія                  (лишок, стек)          лишок    стек
число 3 → вихід      (5, 0) → (4, 0)         −1       =
+ → стек             (4, 0) → (3, 1)         −1      +1
число 4 → вихід      (3, 1) → (2, 1)         −1       =
* → стек             (2, 1) → (1, 2)         −1      +1
число 2 → вихід      (1, 2) → (0, 2)         −1       =
*: стек → вихід      (0, 2) → (0, 1)          =      −1
+: стек → вихід      (0, 1) → (0, 0)          =      −1
```

Лишок входу стоїть на двох кроках із семи. Стек не падає на п'ятьох із семи, ба навіть росте. Жодна колонка окремо не є варіантом. А **пара** спадає щокроку — за словниковим порядком: читання зменшує першу координату (і байдуже, що стек при цьому підріс, — менша перша координата робить меншою всю пару), а зняття зі стека лишає першу координату й зменшує другу. Обидві мови це вміють задарма: і Python, і Rust порівнюють кортежі саме словниково, тож перевірка спуску — це буквально `<` між парами, без жодного рядка нового коду.

Зупинку доведено. А **межа**?

Ось де пара підводить: вона не число, оберненої функції з неї не візьмеш. Треба **згорнути пару в одне число** — і саме тут вирішується, буде оцінка гострою чи ганебною.

Згортка робиться одометром. Якщо відомо, що за крок, який з'їдає одиницю першої координати, друга підскакує щонайбільше на `r`, — беремо

```
N = (r + 1)·x + y
```

і перевіряємо обидві гілки:

```
y падає, x стоїть:                    ΔN ≤ −1
x падає на 1, y підскакує на ≤ r:     ΔN ≤ −(r + 1) + r = −1
```

Обидві гілки — крок униз щонайменше на одиницю. Отже, `N` — звичайнісінький цілочисловий варіант із дном, і межа на кроки просто дорівнює `N₀`. Вага `r + 1` тут не з примхи: візьми на одиницю менше, і все розсиплеться —

```
вага r (при r = 1):   (3, 0) → (2, 1)   дає   1·3 + 0 = 3   →   1·2 + 1 = 3   — не впало
```

![Пара згортається в одне число N = (r+1)·x + y; обидві гілки дають крок униз щонайменше на одиницю, а вся якість межі вирішується вагою](/book/algorithms/complexity-computability/loop-variant/img/odometer-collapse.svg)

*Згортка одометра. Словниковий варіант доводить зупинку, але межі не дає — пара не число. Якщо ж відомо, на скільки щонайбільше доливається друга координата за крок, що з'їдає першу, пара згортається в одне число, і межа читається просто як `N₀`. Уся якість оцінки сидить у вазі: не знаєш доливу — припускаєш найгірший і дістаєш квадрат; знаєш, що читання кладе на стек не більш ніж один оператор, — дістаєш лінію.*

Тепер підставмо станцію, `n` токенів. Не знаючи нічого про долив, довелось би припустити найгірше: стек здатен дорости до `n`, тобто `r = n`, і межа виходить `N₀ = (n + 1)·n` — **квадрат**. Але ми знаємо більше: одне читання кладе на стек **не більш ніж один** оператор. Тобто `r = 1`, і

```
N = 2·(лишок входу) + (розмір стека)
N₀ = 2n + 0 = 2n
```

**Лінійно.** Той самий цикл, той самий спуск — а межа впала з `n²` до `2n` тільки тому, що вагу взяли за фактом, а не за переляком. Перебір 20 000 випадкових виразів згоден: межа `2n` не порушується жодного разу, найгірше відношення проходів до токенів — 1.481.

Варто назвати те, що ми щойно зробили, справжнім ім'ям. `2·лишок + стек` — це рівно **потенціал** з амортизаційного аналізу, той самий «кожен токен наперед оплачує дві монети: одну за читання, одну за майбутнє зняття зі стека». Обмежувальна функція циклу й потенціал амортизаційного аналізу — не родичі й не аналогія, а **один і той самий предмет**, названий двічі різними школами. Словниковий варіант дає зупинку; вага, підібрана за фактом, дає межу.

## Варіант як рантайм-перевірка

Усе, що ми виписували, — закон спуску, дно, передбачену межу, — можна не лишати на папері, а вкласти в код, щоб воно перевіряло себе саме. Ось [перевірка припущення](book:programming/assert-panic) на всі три обіцянки одразу:

:::tabs
```python
class Variant:
    """Строгий спад + дно + збіг із передбаченою межею."""

    def __init__(self, floor=0, budget=None):
        self.floor, self.budget = floor, budget
        self.prev, self.steps = None, 0

    def step(self, now):
        """Викликати ПЕРШИМ рядком тіла циклу — жодна гілка не прослизне."""
        self.steps += 1
        assert now >= self.floor, "варіант пробив дно: %r < %r" % (now, self.floor)
        if self.prev is not None:
            assert now < self.prev, "варіант не впав: %r → %r" % (self.prev, now)
        if self.budget is not None:
            assert self.steps <= self.budget, \
                "перевищено передбачену межу: %d > %d" % (self.steps, self.budget)
        self.prev = now
```
```rust
use std::fmt::Debug;

/// Строгий спад + дно + збіг із передбаченою межею.
struct Variant<V: Ord + Debug> {
    floor: V,
    budget: Option<usize>,
    prev: Option<V>,
    steps: usize,
}

impl<V: Ord + Debug> Variant<V> {
    fn new(floor: V, budget: Option<usize>) -> Self {
        Variant { floor, budget, prev: None, steps: 0 }
    }

    /// Викликати ПЕРШИМ рядком тіла циклу — жодна гілка не прослизне.
    fn step(&mut self, now: V) {
        self.steps += 1;
        assert!(now >= self.floor, "варіант пробив дно: {:?} < {:?}", now, self.floor);
        if let Some(prev) = &self.prev {
            assert!(now < *prev, "варіант не впав: {:?} → {:?}", prev, now);
        }
        if let Some(b) = self.budget {
            assert!(self.steps <= b, "перевищено передбачену межу: {} > {}", self.steps, b);
        }
        self.prev = Some(now);
    }
}
```
:::

Місце виклику вибране не для краси. Перевірка стоїть **першим рядком тіла**, а не останнім, — і тому її не обійде жодна гілка. Останній рядок обходиться тривіально: досить `continue` десь усередині, і контроль пролітає повз. А до першого рядка потрапляє все, що заходить на новий прохід, — байдуже, звідки воно прийшло:

```
цикл із гілкою `continue`, що забула зрушити лічильник:
    AssertionError: варіант не впав: 7 → 7        ← спіймано на першому ж витку
```

Третя обіцянка — найцікавіша. `budget` перетворює твою **оцінку складності на рантайм-перевірку**. Ти вирахував для двійкового пошуку `⌊log₂ n⌋ + 1`; передай це число в `budget` — і відтепер кожен запуск мовчки звіряє теорію з дійсністю:

```
n = 1000, budget = ⌊log₂ 1000⌋ + 1 = 10  →  найгірше 10 проходів, assert мовчав
n = 1000, budget = 3 (свідомо занижений) →  AssertionError: перевищено передбачену межу: 4 > 3
```

Хибна оцінка складності перестає бути хибним рядком у коментарі й стає **падінням тесту**. І ця сама сторожа без єдиної правки бере кортеж: у Python кортежі порівнюються словниково, у Rust `V: Ord` покриває `(usize, usize)` так само.

```
сторожа на парі:  (2, 5) → (2, 3) → (1, 99) — проходить (словниковий спад)
                  (1, 99) → (1, 99)          — AssertionError: варіант не впав
```

## Пастки

**Нестрогість біля самого дна.** Класичне зависання двійкового пошуку — це `lo = mid` замість `lo = mid + 1`. Помилка на одиницю, і закон спуску ламається **рівно в одній точці** — при `v = 1`:

```
a = [10, 20], ціль 15:

   lo=0, hi=2, v=2 → mid=1, a[1]=20 > 15 → hi = mid = 1     v: 2 → 1   впало
   lo=0, hi=1, v=1 → mid=0, a[0]=10 < 15 → lo = mid = 0     v: 1 → 1   СТОП
   lo=0, hi=1, v=1 → mid=0, a[0]=10 < 15 → lo = mid = 0     v: 1 → 1   СТОП
   … і так довіку
```

При `v ≥ 2` варіант падає (`v′ = ⌈v/2⌉ < v`) і помилки не видно; а на вікні шириною 1 `mid` збігається з `lo`, і прохід не змінює геть нічого. Пастка чекає в найвужчому місці — тому й переживає тести, які ганяють масиви «нормального» розміру. `assert` на закон спуску ловить її на першому ж такому вході.

**Машинні цілі — не ℕ, а кільце.** Доведення велося над натуральними, а код виконується над `ℤ/2ⁿ`. Це не педантизм: кільце лишків **не має дна взагалі** — воно циклічне, і спуск `0 → 2ⁿ−1 → 2ⁿ−2 → …` триває вічно. [Фундованість](book:algorithms/loop-variant/math-well-founded.md), на якій тримається все доведення, просто не виконується:

```c
#include <stddef.h>

/* Здається, рахує вниз від n−1 до 0. Насправді — не спиняється ніколи. */
void walk_backwards(const int *a, size_t n)
{
    for (size_t i = n - 1; i >= 0; i--)   /* i БЕЗЗНАКОВЕ: умова тотожно істинна */
        use(a[i]);                        /* при i = 0 крок i-- дає SIZE_MAX */
}

/* Так правильно: перевірка й крок в одному, дно недосяжне знизу. */
void walk_backwards_ok(const int *a, size_t n)
{
    for (size_t i = n; i-- > 0; )
        use(a[i]);
}
```

Умова `i >= 0` для беззнакового типу — не дно, а тавтологія: кожне беззнакове число `≥ 0` (gcc так і каже: *comparison of unsigned expression >= 0 is always true*). Варіант мусить жити у множині без нескінченного спуску — а [переповнення](book:programming/overflow-wraparound) робить із такої множини карусель.

**Переповнення в арифметиці самого варіанта.** Тут ламається не спуск, а обчислення варіанта. 2006 року Джошуа Блох показав у блозі Google Research, що `int mid = (low + high) / 2` переповнюється на масивах від 2³⁰ елементів: сума стає від'ємною, ділення лишає її від'ємною, індекс вилітає за межі. Баг прожив у `java.util.Arrays.binarySearch` близько дев'яти років, а родовід веде ще від «Programming Pearls» Джона Бентлі — там він просидів десятиліття. Саме тому вище стоїть `mid = lo + (hi - lo) // 2`: різниця невід'ємна й не більша за `v`, тож переповнитись їй нема з чого.

**Дійснозначний варіант нічого не доводить.** Множина `ℝ≥0` не фундована: ланцюг `1 > 1/2 > 1/4 > …` строго спадний, обмежений нулем — і нескінченний. Тому «строго спадає й не менше нуля» для дійсних величин не є доведенням зупинки взагалі:

```
x = 1.0
while x > 0.0:
    x = x / 2      # у ℝ це НЕСКІНЧЕННИЙ спуск, нуля не досягає ніколи
```

Цей цикл таки спиняється — за 1075 проходів. Але спиняє його не математика, а вичерпання денормалів [плаваючої коми](book:programming/floating-point): `x` провалюється в рівний нуль. Покладатися на такий збіг не варто, бо сусідній випадок збігу не подарує: у `y -= 1e-20` при `y = 1.0` округлення повертає те саме `y`, спад **перестає бути строгим уже на першому проході**, і цикл висить назавжди. Щоб дійсна величина стала варіантом, потрібен гарантований мінімальний крок `ε` — тоді варіантом є ціле `⌈v/ε⌉`, і воно вже живе в ℕ.

**Межа рахує проходи, а не час.** Обмежувальна функція каже, скільки разів виконається тіло, — і ні слова про те, скільки коштує саме тіло. Якщо всередині ховається лінійний прохід, `⌊log₂ n⌋ + 1` ітерацій дають `O(n log n)` часу, а не `O(log n)`. Час — це добуток межі на ціну проходу; варіант чесно віддає лише перший множник. І окремо варто пильнувати ціну самого обчислення варіанта: величина, що сама коштує лінійного проходу, у робочому коді має лишатися під `assert`-ом, який вимикається в релізі, — інакше сторожа стане дорожчою за те, що вона стереже.

---

Уся ця робота зводиться до одного питання, поставленого правильним боком. «Як швидко воно падає» — питання, на яке цикл здебільшого не відповідає. «На скільки його вистачить, якщо воно падатиме якнайощадливіше» — питання, на яке відповідь є завжди, бо найощадливіший спуск ти будуєш власноруч, назад від дна. Драбина, яку при цьому виписуєш, і є оцінкою: подвоюється — маєш логарифм, росте за Фібоначчі — маєш логарифм за золотим перетином, росте на одиницю — маєш лінію. А найдешевший прогін, що лишається в руках наприкінці, — це найгірший вхід, готовий до тесту.
