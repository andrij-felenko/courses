# ⚙️ Робочий динамічний масив: виміряти амортизацію на живих числах

Довести на папері, що додаток у масив коштує амортизований O(1), — одне. Побачити це на власні очі — інше. Папір легко обдурити себе: пропустив множник, недорахував ряд — і висновок наче правильний, а насправді хиткий. Тож зробимо інакше. Візьмемо справжній масив, що росте, **вмонтуємо в нього лічильник реальних копіювань** і проженемо мільйон додатків. Хай не формула, а сам код скаже, скільки насправді роботи. А тоді покрутимо один-єдиний параметр — коефіцієнт росту — і подивимось, як та сама структура з O(1) провалюється в O(n).

## Задача: не рахувати, а зміряти

Динамічний масив тримає елементи в суцільному блоці пам'яті фіксованого розміру. Коли блок повний, а додати треба ще, доводиться взяти більший блок, **скопіювати туди все старе** й лише потім дописати новий елемент. Копіювання — і є та рідкісна дорога робота, яку амортизація розмазує по дешевих сусідах. Питання, на яке ми хочемо тверду числову відповідь: **скільки всього елементів фізично переміститься за n додатків** — і як ця сума залежить від того, наскільки агресивно масив росте.

Щоб відповісти чесно, лічильник має рахувати не додатки, не перевиділення, а саме **переміщення елементів** — кожне присвоєння `bigger[i] = data[i]`. Це і є одиниця реальної вартості. Проженемо три політики росту:

- **× 2** — подвоєння місткості (так росте `std::vector` у GCC та Clang);
- **× 1.5** — множення на півтора (так росте `std::vector` у MSVC і `fbvector` у Facebook/Folly);
- **+ 1** — щоразу рівно на один елемент більше (навмисне зле, щоб побачити катастрофу).

## Робочий код: масив із лічильником копіювань

Це системний код: ручне виділення й звільнення пам'яті, копіювання блоку, арифметика вказівників. Тут доречна мова, у якій усе це видно без завіси, — C. Уся хитрість в одному рядку `v->copies += v->len` усередині гілки росту: він накопичує саме ту роботу, яку ми хочемо зміряти.

```c
#include <stdio.h>
#include <stdlib.h>

typedef struct {
    int    *data;               // блок пам'яті під елементи
    size_t  len, cap;           // зайнято / вміщає
    double  factor;             // коефіцієнт росту: 2.0, 1.5 або 1.0 (=«+1»)
    unsigned long long copies;  // скільки елементів скопійовано за весь пробіг
    unsigned           reallocs;// скільки разів росли
    size_t             peak;    // найбільша місткість, яку тримали
} Vec;

// Наступна місткість за коефіцієнтом. Ключова тонкість — гарантований приріст:
// коли cap мале, cap*1.5 може округлитись донизу до cap, і масив завис би навіки.
static size_t grow(size_t cap, double f) {
    if (cap == 0) return 1;                 // перший блок
    size_t nc = (size_t)(cap * f);
    if (nc <= cap) nc = cap + 1;            // приріст хоч на один — інакше глухий кут
    return nc;
}

void push(Vec *v, int x) {
    if (v->len == v->cap) {                     // місця немає — треба рости
        size_t nc = grow(v->cap, v->factor);
        int *bigger = malloc(nc * sizeof(int));
        for (size_t i = 0; i < v->len; i++)     // копіюємо ВСЕ старе: O(len)
            bigger[i] = v->data[i];
        v->copies += v->len;                     // ← ось де лічимо реальну роботу
        v->reallocs++;
        free(v->data);
        v->data = bigger;
        v->cap  = nc;
        if (nc > v->peak) v->peak = nc;
    }
    v->data[v->len++] = x;                        // дешевий запис: O(1)
}

int main(void) {
    const size_t N = 1000000;                     // мільйон додатків
    double      factor[] = {2.0, 1.5, 1.0};
    const char *name[]   = {"× 2", "× 1.5", "+ 1"};

    printf("коеф.   копіювань          росли    пік. місткість   копій/додаток\n");
    for (int f = 0; f < 3; f++) {
        Vec v = {0};                              // усе в нулі: data=NULL, len=cap=0
        v.factor = factor[f];
        for (size_t i = 0; i < N; i++)
            push(&v, (int)i);
        printf("%-6s %14llu %8u %16zu %13.3f\n",
               name[f], v.copies, v.reallocs, v.peak,
               (double)v.copies / N);
        free(v.data);
    }
    return 0;
}
```

Тип лічильника — `unsigned long long`, і це не педантизм: для політики «+1» сума копіювань переросте чотири мільярди, і 32-розрядного `unsigned long` (яким він буває, зокрема, на Windows) не вистачило б — число тихо переповнилося б і збрехало.

## Що друкує лічильник

Проганяємо на `N = 1 000 000`. Ось таблиця (для «+1» це, до речі, справжня мука — півтрильйона копіювань і мільйон викликів `malloc`/`free`; сам цей факт — половина висновку):

```
коеф.   копіювань          росли    пік. місткість   копій/додаток
× 2           1048575       21          1048576         1.049
× 1.5         2099753       35          1049869         2.100
+ 1      499999500000  1000000          1000000    499999.500
```

Прочитаймо останній стовпчик — **копій на один додаток**. Це і є амортизована вартість, зважена й поділена самим прогоном, без жодної формули.

Для подвоєння вона — **1.049**. Округлено: один додаток тягне за собою одне копіювання. Мільйон додатків — трохи більше за мільйон копіювань. Не мільйон у квадраті, а мільйон. Сумарна робота **лінійна**, тож на операцію припадає **стала** — це і є O(1) амортизовано, впіймане в лічильник.

Для «× 1.5» — **2.1** копії на додаток. Теж стала, теж O(1), просто вдвічі більша: півтора-масив копіює частіше (35 перевиділень проти 21), бо росте меншими кроками. Тримай це число в голові — за хвилину воно виявиться не вадою, а платою за важливу перевагу.

А тепер «+ 1»: **499 999.5** копій на додаток. Half a million. І це не стала — це рівно **n/2**. Прожени на вдесятеро довшій послідовності — і стовпчик стане п'ять мільйонів. Вартість однієї операції **росте разом із входом**: чистий O(n) на додаток, а на всю послідовність — O(n²). Той самий код, той самий масив, змінили одне число `factor` — і структура з лінійної стала квадратичною.

![Логарифмічний графік: копій на один додаток для коефіцієнтів росту 2, 1.5 і +1 при кількості додатків n від 10² до 10⁶. Лінії ×2 (≈1) і ×1.5 (≈2) лишаються плоскими — не залежать від n, це амортизований O(1); лінія +1 прямо росте як n/2 — це O(n) на операцію](img/growth-copies.svg)

*Копій на додаток проти розміру входу, обидві осі логарифмічні. Геометричні коефіцієнти (×2 і ×1.5) — плоскі горизонталі: скільки не додавай, вартість одного додатка тримається сталою (жменя копіювань). Це амортизований O(1) на власні очі. «+1» — пряма, що лізе вгору під кутом: копій на додаток дорівнює n/2, тобто O(n). Різниця між геометричним і лінійним ростом — це різниця між горизонталлю й похилою.*

Чому геометричні коефіцієнти дають саме сталу — видно з простого міркування. При коефіцієнті k масив, дорісши до місткості C, наступного разу перевиділяється аж коли заповниться знову, тобто після ще (kC − C) = (k−1)C додатків. За ці додатки він скопіює C елементів. Отже, копій на додаток у цьому циклі ≈ C / ((k−1)C) = **1/(k−1)** — стала, що від C (а отже, і від n) не залежить. Підставмо: для k = 2 це 1/(2−1) = 1 копія на додаток; для k = 1.5 це 1/(1.5−1) = 2 копії. Рівно те, що надрукував лічильник (1.05 і 2.1). А для «+1», де k → 1, знаменник → 0 і вартість вибухає. Уся прірва між O(1) і O(n) сидить у тому, чи є в знаменнику стала (k−1), чи вона тане до нуля.

> 🔧 **Навіщо це.** Число 1/(k−1) — це важіль, яким проєктувальник контейнера торгує швидкість за пам'ять. Хочеш менше копіювань — бери коефіцієнт більший (k = 4 дасть 1/3 копії на додаток), але тоді масив тримає до вчетверо більше зайвої місткості. Хочеш ощадніше до пам'яті — тисни k до одиниці, та копіювань стане більше. Обидва краї — та сама амортизована O(1); змінюється лише стала. Розуміння цієї формули — різниця між «взяв 2, бо всі беруть» і свідомим вибором під свій профіль навантаження.

## Чому 1.5, коли 2 копіює вдвічі менше?

Тут напрошується питання. Подвоєння копіює менше (1.05 проти 2.1 на додаток) і перевиділяється рідше (21 раз проти 35). За швидкістю воно виграє. Чому ж поважні реалізації — MSVC, Folly — свідомо беруть повільніший півтора-масив? Відповідь — у пам'яті, і вона тонша, ніж здається.

**Перше: менше змарнованої місткості.** Масив майже завжди тримає більше місця, ніж зайнято, — запас під ріст. Скільки саме змарновано? Одразу після перевиділення зайнято C, а місткість — kC, тобто корисно використано 1/k. Для подвоєння це 1/2 — **половина блоку простоює**. Для «× 1.5» це 1/1.5 ≈ 2/3 — простоює лише третина. Усереднімо по циклу заповнення: середнє використання виходить (1+k)/(2k) — для подвоєння 75 % (чверть намарно), для півтора-масиву 83 % (намарно лише шоста). Півтора-масив тісніший: він тримає менше повітря.

**Друге, головне: перевикористання звільнених блоків.** Коли масив росте, старий блок звільняється й повертається аллокаторові. Логічно спитати: а чи не можна наступного разу **лягти назад у звільнене** — узяти під новий блок ту саму пам'ять, що вже колись відпустили? Якби так — купа (heap) не росла б угору без потреби, а перевикористовувала б старі діри. І ось тут коефіцієнт росту вирішує все.

Простежмо подвоєння. Блоки, які масив по черзі виділяв і звільняв, — це 1, 2, 4, 8, … Коли настав час просити блок на 16, які діри вже вільні? Це 1, 2, 4 (а восьмірка ще жива — з неї саме копіюємо). Їхня сума — **7. А треба 16.** Замало. Складімо навіть усі коли-небудь звільнені, разом із вісімкою: 1 + 2 + 4 + 8 = 15. Однаково менше за 16 — рівно **на одиницю**. І це не збіг цього кроку: сума геометричного ряду, що подвоюється, завжди на один менша за наступний член. Тож при подвоєнні звільнене **ніколи** не доганяє наступний запит — новий блок щоразу мусить лягати у свіжу пам'ять поза старими дірами, і верхня межа купи невпинно повзе вгору.

Тепер «× 1.5». Блоки ростуть як 1, 2, 3, 4, 6, 9, 13, 19, 28, … Коли треба блок на 28, звільнені діри — це 1, 2, 3, 4, 6, 9, 13 (дев'ятнадцятка ще жива). Їхня сума — **38. Треба 28. Влазить**, ще й із запасом. Аллокатор, що зливає сусідні вільні блоки, кладе новий масив у стару діру — і купа не росте. Менші кроки означають, що звільнене встигає накопичитись і наздогнати наступний запит.

![Два ряди пам'яті: для коефіцієнта ×2 звільнені блоки 1+2+4=7 менші за наступний запит 16, тож новий блок не влазить у стару діру і купа росте; для коефіцієнта ×1.5 звільнені блоки 1+2+3+4+6+9+13=38 більші за наступний запит 28, тож новий блок лягає у стару діру і пам'ять перевикористовується. Поріг — золотий переріз φ≈1.618](img/block-reuse.svg)

*Чи влазить наступний блок у суму вже звільнених дір. Угорі (× 2) звільнене — 7, запит — 16: не влазить, і так щоразу, тож купа тільки росте, а стара пам'ять марнується. Унизу (× 1.5) звільнене — 38, запит — 28: влазить, аллокатор кладе блок у стару діру, купа не росте. Живий блок, з якого саме копіюємо, у діру не рахується — тому точний поріг перевикористання не 2, а золотий переріз φ = (1+√5)/2 ≈ 1.618.*

Звідки береться саме **золотий переріз** φ ≈ 1.618? Умова перевикористання проста: сума раніше звільнених блоків має дорости до наступного запиту. Якщо коефіцієнт k, а поточна місткість C, то звільнені блоки — це C/k, C/k², C/k³, … Ключова тонкість: блок, який ми **щойно** звільняємо (той, з якого копіюємо), у цю мить іще живий — його рахувати не можна. Сума решти в границі дорівнює C/(k(k−1)) від наступного запиту kC, тобто відношення 1/(k(k−1)). Воно ≥ 1 (звільнене доганяє запит) саме коли k(k−1) ≤ 1, тобто k² − k − 1 ≤ 0, тобто **k ≤ (1+√5)/2 = φ**. Подвоєння (k = 2) поза межею — не перевикористовує ніколи; півтора (k = 1.5) під межею — перевикористовує. Ось чому 1.5 не випадкове число, а дешевий раціональний наближенець до φ, який ще й легко лічити (C + C/2). Це поріг, за яким аллокатор перестає марнувати пам'ять.

Чесна засторога: усе це — про аллокатор, що вміє **зливати** сусідні вільні блоки в суцільну діру. Не кожен так робить, і фрагментація реальної купи буває примхливою. Тому «× 1.5 завжди ощадніше» — не залізний закон, а сильна тенденція, підтверджена практикою: саме заради неї Folly у `fbvector` явно взяв 1.5 і навчив контейнер співпрацювати з аллокатором jemalloc, просячи блоки рівно такого розміру, щоб не лишалося зазору.

> 🔧 **Навіщо це.** Вибір коефіцієнта росту — жива інженерна розвилка, і різні команди вирішили її по-різному: GCC та Clang тримають подвоєння (менше копіювань, більше пам'яті), MSVC і Folly — півтора (більше копіювань, менше пам'яті й перевикористання дір). Жодна не «правильна» — вони оптимізують різне. Знаючи формулу 1/(k−1) для копіювань і поріг φ для пам'яті, ти вже не мусиш вірити на слово: ти бачиш, чим саме одна бібліотека відрізняється від іншої й котра пасує твоєму навантаженню.

## Пастка перша: ріст робить вказівники недійсними

Тепер про підступ, на якому спотикаються всі, хто пише свій контейнер, — і чимало тих, хто просто ним користується. Подивись іще раз на `push`: коли масив росте, `malloc` дає **новий** блок, старий `free` віддає системі, і `v->data` починає вказувати в інше місце. Це означає, що **будь-який вказівник у масив, узятий до росту, після росту показує в звільнену пам'ять** — і розіменувати його вже не можна.

```c
Vec v = {0}; v.factor = 2.0;
push(&v, 10);
int *p = &v.data[0];    // вказівник на нульовий елемент
push(&v, 20);           // ← тут масив виріс: data перевиділено, старий блок звільнено
printf("%d\n", *p);     // ☠️ p показує у ЗВІЛЬНЕНУ пам'ять — невизначена поведінка
```

Помилка підступна тим, що часто «ніби працює»: доки масив не переріс місткість, `data` не рухається, і `p` лишається дійсним — код проходить тести на малих даних. А тоді на продакшені масив доростає до межі, `push` перевиділяє блок — і збережений раніше вказівник тихо стає бомбою. Те саме стосується ітераторів у C++: стандарт прямо каже, що будь-яке `push_back`, яке спричинило ріст, **інвалідизує всі ітератори, вказівники й посилання** на елементи вектора.

Ліки прості, коли знаєш причину. Не тримай **вказівник** через дію, що може викликати ріст, — тримай **індекс**. Індекс переживає перевиділення, бо він не адреса, а зсув; його завжди можна перетворити на свіжу адресу після росту:

```c
Vec v = {0}; v.factor = 2.0;
push(&v, 10);
size_t i = 0;           // зберігаємо ІНДЕКС, а не адресу
push(&v, 20);           // масив виріс — байдуже
printf("%d\n", v.data[i]);   // ✓ адресу беремо ЗАНОВО від актуального data
```

Це не дрібниця стилю, а прямий наслідок того, як улаштований амортизований ріст: сама його механіка — «інколи переселити весь масив» — і робить старі адреси недійсними. Хочеш дешевих додатків у середньому — плати уважністю до вказівників.

## Пастка друга: reserve наперед — це відмова від амортизації на користь гарантії

Амортизована O(1) чудова, доки тебе цікавить **сумарна** пропускність. Але вона нічого не обіцяє про **окрему** операцію: той єдиний `push`, що влучив у переповнення й копіює пів мільйона елементів, коштує чесних O(n) — просто розмазаних по сусідах. Для звукового зворотного виклику з дедлайном 5 мс чи контуру керування, що мусить укластися в такт, ця одна довга операція — зірваний дедлайн, дарма що «в середньому все чудово». Про це — окрема розмова в [системах реального часу](topic:algorithms/real-time-systems), де важлива не середня, а найгірша поодинока затримка.

Коли розмір відомий наперед, є прямий вихід — **зарезервувати місткість заздалегідь**:

```c
void reserve(Vec *v, size_t want) {
    if (want <= v->cap) return;
    int *bigger = malloc(want * sizeof(int));
    for (size_t i = 0; i < v->len; i++)
        bigger[i] = v->data[i];
    v->copies += v->len;
    free(v->data);
    v->data = bigger;
    v->cap  = want;
}

// далі — мільйон додатків БЕЗ жодного росту:
Vec v = {0}; v.factor = 2.0;
reserve(&v, 1000000);         // одне-єдине виділення наперед
for (int i = 0; i < 1000000; i++)
    push(&v, i);              // v->len ніколи не дорівнює v->cap → гілка росту мовчить
```

Тепер `push` **жодного разу** не заходить у гілку росту: лічильник `copies` лишиться на нулі, `reallocs` — теж. Кожен додаток — рівно один запис, тверда O(1) на **кожну** операцію, без сплесків. Ми проміняли амортизовану межу (дешево в середньому, зрідка дорого) на **гарантію** (дешево завжди).

Але задурно нічого не буває, і ціна `reserve` двобічна. Недооціниш `want` — і масив однаково дорощуватиметься амортизовано, резерв лише відсунув перший сплеск. Переоціниш — і триматимеш велику незаповнену місткість, марнуючи пам'ять точно так, як зловживання великим коефіцієнтом росту. Головне ж — `reserve` вимагає **знати n наперед**, а амортизація саме тим і цінна, що працює, **коли не знаєш**: структура сама доростає під будь-який обсяг без твого втручання. Тож це не «reserve завжди кращий», а свідомий розмін: є надійна оцінка розміру й важлива стеля затримки — резервуй; немає — довірся амортизації.

## Другий приклад: стек із multipop і той самий агрегатний трюк

Масив, що росте, — не єдина структура, чия чесна вартість ховається в сумі по пробігу. Візьмімо стек із незвичною операцією `multipop(k)` — «зняти зверху відразу k елементів (або скільки є, коли менше)». Один її виклик може коштувати O(n): якщо в стеку мільйон елементів, `multipop(1000000)` зніме їх усі. Наївно множимо цей сплеск на кількість операцій — і лякаємось квадрата. Але й тут переляк оманливий.

```c
#include <stdio.h>
#include <stdlib.h>

typedef struct {
    int   *data;
    size_t len, cap;
    unsigned long long moves;   // реальні переміщення: кожен запис і кожен зняток
} Stack;

void st_push(Stack *s, int x) {
    if (s->len == s->cap) {
        size_t nc = s->cap ? s->cap * 2 : 1;
        s->data = realloc(s->data, nc * sizeof(int));
        s->cap  = nc;
    }
    s->data[s->len++] = x;
    s->moves++;                                  // один запис
}

size_t st_multipop(Stack *s, size_t k) {
    size_t popped = 0;
    while (k-- && s->len) {                       // знімаємо min(k, len)
        s->len--;
        s->moves++;                               // один зняток
        popped++;
    }
    return popped;
}

int main(void) {
    Stack s = {0};
    unsigned ops = 0, pushes = 0;

    for (int i = 0; i < 20; i++) { st_push(&s, i); ops++; pushes++; }
    st_multipop(&s, 100); ops++;                  // ДОРОГИЙ виклик: зняв усі 20
    for (int i = 0; i < 5; i++)  { st_push(&s, i); ops++; pushes++; }
    st_multipop(&s, 3);   ops++;                  // зняв 3
    st_push(&s, 99);      ops++; pushes++;
    st_multipop(&s, 100); ops++;                  // зняв рештку 3

    printf("операцій: %u,  штовхань: %u,  переміщень: %llu\n", ops, pushes, s.moves);
    printf("межа 2·штовхань = %u  ≥  переміщень %llu\n", 2 * pushes, s.moves);
    free(s.data);
    return 0;
}
```

Друкує:

```
операцій: 29,  штовхань: 26,  переміщень: 52
межа 2·штовхань = 52  ≥  переміщень 52
```

Двадцять дев'ять операцій, серед них один `multipop`, що зняв аж 20 елементів, — а всього переміщень лише **52**. Не 29 × 20, а 52. Секрет — одне залізне спостереження: **кожен елемент можна зняти щонайбільше один раз, і лише після того, як його один раз поклали**. Тож скільки б не було `multipop` і хоч які дорогі поодинокі, сумарна кількість знятків за весь пробіг не перевищить кількості штовхань. Отже, вся робота (штовхання + зняття) ≤ 2 × штовхань ≤ 2n. Сумарно — O(n), амортизовано — O(1) на операцію, попри те що окремий `multipop` буває O(n).

Це той самий **агрегатний метод**, що й для масиву: не множ найдорожчу поодиноку операцію на кількість, а спитай, скільки роботи можлива вся послідовність **разом**. Для масиву стелю дав геометричний ряд копіювань; для стека — те, що знято не більше, ніж покладено. Різні структури, той самий хід думки: дорога операція мусить спершу «накопичити собі умови» (набити стек, наповнити масив), і саме дешеві сусіди те накопичення й оплатили.

## Складність: підсумок

| структура / політика | одна операція (найгірша) | амортизовано на операцію |
|---|---|---|
| масив, ріст × 2 | O(n) на перевиділенні | **O(1)** (≈1.05 копії/додаток) |
| масив, ріст × 1.5 | O(n) на перевиділенні | **O(1)** (≈2.1 копії/додаток) |
| масив, ріст + 1 | O(n) щоразу | **O(n)** (n/2 копій/додаток) |
| масив із `reserve(n)` | O(1) завжди | **O(1)**, тверда, без сплесків |
| стек: push | O(n) на перевиділенні | **O(1)** |
| стек: multipop(k) | O(k) ≤ O(n) | **O(1)** (знято ≤ покладено) |

Уся суть проєкту — в одному рядку `v->copies += v->len`. Він перетворив паперове твердження «амортизований O(1)» на число, яке можна побачити, недовіритись і перевірити самому. Виміряне: геометричний ріст тримає копіювання на сталій жмені (1/(k−1) на додаток), лінійний — вибухає квадратом; півтора виграє пам'ять ціною частіших копіювань; резерв міняє м'яку середню межу на тверду поопераційну; а зухвалий `multipop` виявляється дешевим у пробігу, бо знімає лише те, що хтось раніше поклав. Три сегменти нотації O ховають різну поведінку — і найпевніший спосіб не сплутати їх — вмонтувати лічильник і подивитись.

Основа для читання формул O(1), O(n), O(n²) — [асимптотична складність](topic:algorithms/asymptotic-complexity).
