# 📋 Інтерфейс аналізу та побудови ейлерових шляхів

Специфікація програмного інтерфейсу (API) аналізу та обходу ейлерових структур регламентує типи даних, контракти функцій, структури результатів, коди помилок та інваріанти пам'яті для обчислення ейлерових шляхів і циклів у орієнтованих і неорієнтованих графах.

Програмний інтерфейс розроблено з урахуванням системних вимог до високопродуктивних обчислень у базах даних, біоінформатичних пайплайнах та низькорівневих модулях маршрутизації. Інтерфейс надає як C-сумісний процедурний контракт без динамічних винятків для вбудованих систем та C-ABI зв'язок, так і об'єктно-орієнтований C++ контракт на основі RAII, шаблонів та семантики переміщення.

---

## Концептуальна архітектура та вибір структур даних

При проектуванні API для роботи з ейлеровими графами ключовою інженерною вимогою є забезпечення лінійного часу обробки `O(|V| + |E|)` при мінімальному накладній витраті пам'яті. Вибір внутрішньої структури даних визначає швидкість обходу та ефективність використання кеш-пам'яті процесора.

### 1. Порівняння моделей представлення графа

Для виконання алгоритму Гіргольцера потрібен швидкий доступ до невідвіданих ребер кожної вершини та можливість маркування або вилучення ребер за О(1). Розглянемо два основних варіанти структури:

- **Матриця суміжності (`V × V`)**: Дозволяє перевіряти наявність ребра за `O(1)`, проте обхід усіх суміжних ребер вершини вимагає сканування всього рядка довжиною `V`. Загальна складність алгоритму Гіргольцера на матриці суміжності зростає до `O(V²)`, що є неприйнятним для розріджених графів великої розмірності (`V = 10⁶`, `E = 10⁶`). Крім того, матриця вимагає `O(V²)` пам'яті та не підтримує мультиграфи з паралельними ребрами без складних додаткових лічильників.
- **Списки суміжності (`Adjacency Lists`)**: Зберігають для кожної вершини лише реально існуючі вихідні ребра. Обхід вихідних ребер виконується за час, пропорційний `deg⁺(v)`, що забезпечує підсумкову складність `O(|V| + |E|)`. Пам'ять становить `O(|V| + |E|)`.

У даному API обрано модель списків суміжності з унікальною ідентифікацією кожного ребра (`edge_id`), що дозволяє підтримувати мультиграфи з паралельними ребрами та петлями без втрати продуктивності.

### 2. Стратегія управління ребрами та кеш-локальність

Під час обходу ейлерового циклу кожне ребро має бути відвідане й позначене як використане рівно один раз. Фізичне вилучення елементів зі зв'язаного списку супроводжується викликами `free()` або перебудовою масивів, що катастрофічно знижує швидкодію через промахи кешу (cache misses) та фрагментацію купи.

Для досягнення максимальної продуктивності у бібліотеці застосовано схему **двопокажчикової навігації з масивом відвіданих ребер**:
1. Усі ребра графа зберігаються у суцільному масиві або зв'язаних блоках списків.
2. Для кожного ребра виділяється унікальний цілочисельний індекс `id ∈ [0, E - 1]`.
3. Стан відвіданості зберігається у компактному бітовому або булевому масиві `visited_edges` розміром `E` байт.
4. Кожна вершина підтримує зміщення `head_cursor`, яке вказує на поточне неперевірене ребро в її списку суміжності. Це дозволяє уникнути повторного перегляду вже відвіданих ребер і гарантує амортизовану складність `O(1)` на кожне ребро.

### 3. Архітектура приховування реалізації (Pimpl Pattern)
У C++ API застосовано паттерн **Pimpl (Pointer to Implementation)** через `std::unique_ptr<Impl>`. Це дає наступні системні переваги:
- **ABI Stability**: Внутрішні зміни структур даних списків суміжності чи алгоритмів обходу не вимагають перекомпіляції клієнтського коду, оскільки розмір класу `EulerianGraph` залишається постійним (дорівнює розміру одного покажчика `sizeof(void*)`).
- **Ізоляція залежностей**: Заголовковий файл `euler_api.hpp` не включає важких системних залежностей або приватних внутрішніх типів, що прискорює час компіляції проєктів великої розмірності.

## Базові структури даних та типізація (C та C++)

### 1. Перелічення статусів та кодів помилок

Всі функції бібліотечного інтерфейсу повертають деталізований системний статус. Це дозволяє клієнтському коду точно діагностувати причину відмови та вживати відповідних заходів відновлення.

:::tabs
```c
typedef enum {
    EULER_SUCCESS                 =  0, /* Операція успішно виконана */
    EULER_ERR_NULL_POINTER        = -1, /* Передано нульовий покажчик (NULL) */
    EULER_ERR_INVALID_VERTEX      = -2, /* Індекс вершини виходить за межі [0, V-1] */
    EULER_ERR_OUT_OF_MEMORY       = -3, /* Помилка виділення динамічної пам'яті */
    EULER_ERR_NOT_EULERIAN        = -4, /* Граф не задовольняє умові парності степеней */
    EULER_ERR_DISCONNECTED        = -5, /* Ребра належать кільком компонентам */
    EULER_ERR_NO_PATH_EXISTS      = -6, /* Ейлерів шлях/цикл не існує */
    EULER_ERR_EMPTY_GRAPH         = -7, /* Граф не містить жодного ребра */
    EULER_ERR_FROZEN_GRAPH        = -8  /* Спроба модифікації заклиненого графа */
} euler_status_t;
```
```cpp
enum class Status : int32_t {
    Success             =  0,
    NullPointer         = -1,
    InvalidVertex       = -2,
    OutOfMemory         = -3,
    NotEulerian         = -4,
    Disconnected        = -5,
    NoPathExists        = -6,
    EmptyGraph          = -7,
    FrozenGraph         = -8
};
```
:::

#### Деталізація семантики помилок:
- `EULER_ERR_NULL_POINTER`: Виникає, якщо у функцію передано `NULL` замість вхідного графа або вихідного покажчика на результат. Свідчить про помилку в логіці клієнтського коду.
- `EULER_ERR_INVALID_VERTEX`: Сигналізує про передачу індексу вершини `u < 0` або `u >= num_vertices`. Перевірка здійснюється на самому початку операції.
- `EULER_ERR_NOT_EULERIAN`: Помилка валідації. Для неорієнтованого графа означає наявність вершин із непарним степенем (і їх кількість відмінна від 2 для шляху). Для орієнтованого графа означає наявність хоча б однієї вершини, у якої `in_degree != out_degree`.
- `EULER_ERR_DISCONNECTED`: Помилка зв'язності. Виникає, якщо степені вершин є парними або збалансованими, проте ребра розбиті на дві або більше ізольованих компонент, не з'єднаних між собою.
- `EULER_ERR_FROZEN_GRAPH`: Помилка модифікації. Після виклику аналітичних функцій граф може переходити у стан "Read-Only" для забезпечення потокобезпечності.

### 5. Структура результату обходу

Структура призначена для повернення згенерованого ейлерового циклу або шляху.

:::tabs
```c
typedef struct {
    int* path_vertices;          /* Масив послідовності вершин [length] */
    int* path_edges;             /* Масив послідовності ребер [length - 1] */
    int length;                  /* Кількість вершин у шляху */
    euler_status_t status;       /* Підсумковий статус */
    bool is_circuit;             /* true якщо замкнений цикл */
} euler_result_t;
```
```cpp
struct EulerianPathResult {
    std::vector<int> vertices;   // Послідовність вершин обходу [E + 1]
    std::vector<int> edge_ids;   // Послідовність ID ребер [E]
    bool is_circuit{false};     // Прапорець замкненого циклу

    [[nodiscard]] std::size_t num_edges() const noexcept {
        return edge_ids.size();
    }
};
```
:::

#### Правила володіння пам'яттю для `euler_result_t`:
1. Структура `euler_result_t` ініціалізується всередині функцій пошуку `euler_graph_find_circuit` або `euler_graph_find_path`.
2. Буфери `path_vertices` та `path_edges` виділяються в системній купі за допомогою `malloc()`.
3. Клієнтський код **зобов'язаний** звільнити пам'ять викликом спеціалізованої функції `euler_result_free()` після завершення використання результату.

## Матриця статусів та обробки помилок

При роботі з API клієнтський код повинен дотримуватися регламентованого сценарію обробки помилок:

| Код помилки | Умова виникнення | Рекомендована дія клієнта |
| :--- | :--- | :--- |
| `EULER_SUCCESS` | Алгоритм успішно побудував цикл чи шлях | Використовувати масив `path_vertices` та звільнити через `euler_result_free` |
| `EULER_ERR_NOT_EULERIAN` | Існують вершини з `deg⁻(v) != deg⁺(v)` або непарним степенем | Провести попередню модифікацію графа (додати повторні ребра через `Chinese Postman Matching`) |
| `EULER_ERR_DISCONNECTED` | Ребра розбиті на декілька ізольованих компонент | Перевірити компонентний склад графа алгоритмом Tarjan / Kosaraju |
| `EULER_ERR_EMPTY_GRAPH` | У графі відсутні ребра (`E = 0`) | Перевірити коректність зчитування вхідних даних |
| `EULER_ERR_INVALID_VERTEX` | Передано `u >= V` або `u < 0` | Перевірити індексацію вершин (повинна бути `0`-based) |
| `EULER_ERR_OUT_OF_MEMORY` | Не вдалося виділити пам'ять під буфери стека | Зменшити розмір графа або збільшити системні ліміти пам'яті |
| `EULER_ERR_FROZEN_GRAPH` | Спроба додавання ребра у заклинений граф | Створити новий екземпляр графа для додавання нових ребер |

## Приклад використання API (C та C++)

Нижче наведено повноцінні приклади створення графа, додавання ребер, перевірки властивостей та знаходження ейлерового циклу.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include "euler_api.h"

int main(void) {
    euler_graph_t* graph = NULL;
    euler_status_t status;

    /* 1. Створення орієнтованого графа з 4 вершинами */
    status = euler_graph_create(4, EULER_GRAPH_DIRECTED, &graph);
    if (status != EULER_SUCCESS) {
        fprintf(stderr, "Помилка створення графа: %d\n", status);
        return EXIT_FAILURE;
    }

    /* 2. Додавання ребер: 0->1->2->3->0 та 1->3->1 */
    euler_graph_add_edge(graph, 0, 1, 1, NULL);
    euler_graph_add_edge(graph, 1, 2, 1, NULL);
    euler_graph_add_edge(graph, 2, 3, 1, NULL);
    euler_graph_add_edge(graph, 3, 0, 1, NULL);
    euler_graph_add_edge(graph, 1, 3, 1, NULL);
    euler_graph_add_edge(graph, 3, 1, 1, NULL);

    /* 3. Пошук ейлерового циклу */
    euler_result_t result;
    status = euler_graph_find_circuit(graph, 0, &result);

    if (status == EULER_SUCCESS) {
        printf("Ейлерів цикл успішно знайдено (довжина %d вершин):\n", result.length);
        for (int i = 0; i < result.length; i++) {
            printf("%d%s", result.path_vertices[i], (i == result.length - 1) ? "\n" : " -> ");
        }
        euler_result_free(&result);
    } else {
        printf("Не вдалося побудувати ейлерів цикл, код помилки: %d\n", status);
    }

    /* 4. Звільнення ресурсів */
    euler_graph_free(graph);
    return EXIT_SUCCESS;
}
```
```cpp
#include <iostream>
#include "euler_api.hpp"

int main() {
    try {
        // 1. Створення орієнтованого графа з 4 вершинами (RAII)
        euler::EulerianGraph graph(4, euler::GraphType::Directed);

        // 2. Додавання ребер: 0->1->2->3->0 та 1->3->1
        graph.add_edge(0, 1);
        graph.add_edge(1, 2);
        graph.add_edge(2, 3);
        graph.add_edge(3, 0);
        graph.add_edge(1, 3);
        graph.add_edge(3, 1);

        // 3. Пошук ейлерового циклу через std::optional
        if (auto result = graph.find_circuit(0)) {
            std::cout << "Ейлерів цикл успішно знайдено (довжина " 
                      << result->vertices.size() << " вершин):\n";
            for (std::size_t i = 0; i < result->vertices.size(); ++i) {
                std::cout << result->vertices[i] 
                          << (i == result->vertices.size() - 1 ? "\n" : " -> ");
            }
        } else {
            std::cout << "Граф не містить ейлерового циклу.\n";
        }
    } catch (const std::exception& ex) {
        std::cerr << "Системна помилка: " << ex.what() << "\n";
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

## Інваріанти та гарантії безпеки

1. **Гарантія неруйнівного читання**: Виклик функцій `euler_graph_find_circuit` або `euler_graph_find_path` не змінює початкову структуру графа. Усі тимчасові масиви відвіданих ребер виділяються в окремих робочих буферах.
2. **Потокобезпечність (Thread-Safety)**: Константні методи `EulerianGraph::find_circuit` є потокобезпечними та можуть викликатися паралельно з кількох потоків над одним і тим самим екземпляром графа після завершення його формування.
3. **Лінійні гарантії пам'яті**: Загальний обсяг додаткової пам'яті, необхідної для побудови ейлерового циклу, не перевищує `O(V + E)` слів, що робить алгоритм придатною для застосування на вбудованих системах з обмеженим обсягом RAM.
