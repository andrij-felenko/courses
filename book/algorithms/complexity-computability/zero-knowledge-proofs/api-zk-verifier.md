# 📋 Інтерфейс специфікації та верифікатора ZK-протоколів

Цей документ визначає уніфікований контракт програмного інтерфейсу (API) та машинний специфікат для системи верифікації протоколів нульового розголошення. Специфікація охоплює як інтерактивні 3-крокові Sigma-протоколи, так і неінтерактивні лаконічні аргументи знань (NIZK / ZK-SNARK). Інтерфейс призначений для інтеграції верифікуючих ядер у високозавантажені серверні системи, криптографічні модулі та смарт-контракти.

## 1. Архітектурні вимоги та специфікація типів даних

Для забезпечення міжплатформенної сумісності між різними мовами програмування (C, C++, Rust, Go, TypeScript) та апаратними архітектурами (x86_64, ARM64, RISC-V) усі криптографічні елементи подаються у фіксованій біг-ендіан (англ. *big-endian*) або літл-ендіан байтовій формі з вирівнюванням за межами 64 бітів.

Елементи скінченного поля `F_p` представляються у вигляді масивів байтів без знаку фіксованої довжини, що відповідають розміру модуля поля. Точки еліптичних кривих у групах `G1` та `G2` можуть передаватися як у стисненій формі (тільки координата `X` та один біт знаку координати `Y`), так і у повній афінній або проективній координаційній сітці.

При розробці верифікуючого модуля висуваються суворі вимоги до пам'яті: верифікатор не повинен виконувати динамічний розподіл пам'яті на купі (англ. *heap allocation*) під час перевірки доказу після ініціалізації сесії. Це забезпечує передбачуваний час виконання та захист від атак відмови в обслуговуванні (DoS).

### Основні типи та константи

Нижче наведено таблицю базових криптографічних типів даних, які використовуються для представлення вхідних сигналів, точок еліптичних кривих та ідентифікаторів сесій у середовищі виконання.

| Назва типу / Константи | Розмір (байт) | Опис та призначення |
| :--- | :--- | :--- |
| `zk_field_element_t` | 32 або 64 | Елемент скінченного поля `F_p` (до 512 бітів). |
| `zk_curve_point_g1_t` | 64 або 128 | Точка еліптичної кривої у групі `G1` (стисла або розгорнута форма). |
| `zk_curve_point_g2_t` | 128 або 256 | Точка еліптичної кривої у розширенні поля `G2` (для кривих зі спарюванням). |
| `zk_transcript_hash_t` | 32 | Криптографічний хеш стенограми (SHA-256 / Blake2b / Poseidon). |
| `zk_protocol_id_t` | 4 | Унікальний ідентифікатор протоколу (Schnorr, GMW, Groth16, PLONK, STARK). |

### Структура стану інтерактивного верифікатора

Для керування станом інтерактивного спілкування між доводжувачем та верифікатором використовується сесійна структура `zk_interactive_session_t`. Вона фіксує поточний етап обміну повідомленнями, збережені публічні входи `x`, зобов'язання `R`, згенерований виклик `e` та отриману відповідь `s`.

Переходи між станами автомата є строго монотонними. Будь-яке порушення послідовності викликів функцій переводить сесію у термінальний стан помилки `ZK_STATE_ERROR`.

```c
typedef enum {
    ZK_STATE_UNINITIALIZED = 0,
    ZK_STATE_WAITING_COMMITMENT = 1,
    ZK_STATE_CHALLENGE_GENERATED = 2,
    ZK_STATE_VERIFIED_ACCEPTED = 3,
    ZK_STATE_VERIFIED_REJECTED = 4,
    ZK_STATE_ERROR = 5
} zk_verifier_state_t;

typedef struct {
    zk_protocol_id_t     protocol_id;     /* Ідентифікатор типу протоколу */
    zk_verifier_state_t  state;           /* Поточний стан автомата */
    uint64_t             session_id;      /* Унікальний ID сесії взаємодії */
    uint32_t             security_bits;   /* Рівень безпеки (наприклад, 128 або 256 біт) */
    
    zk_field_element_t   public_input[8];  /* Загальнодоступний вхід x */
    uint32_t             public_input_len;
    
    zk_field_element_t   commitment_R;    /* Зобов'язання R від доводжувача */
    zk_field_element_t   challenge_e;     /* Випадковий виклик верифікатора */
    zk_field_element_t   response_s;      /* Відповідь s від доводжувача */
} zk_interactive_session_t;
```

### Структура SNARK-доказу та CRS параметрів

Для неінтерактивних лаконічних доказів ZK-SNARK (зокрема у формі Groth16 над кривою BN254 або BLS12-381) доказ передається у вигляді компактної трійки точок еліптичної кривої `pi_a ∈ G1`, `pi_b ∈ G2` та `pi_c ∈ G1`. Ключ верифікації `zk_verification_key_t` містить елементи спільного рядка параметрів (CRS), необхідні для однокрокової перевірки тотожності спарювання.

Точка `alpha_g1` та `beta_g2` закодовані під час фази довіреної установки (англ. *trusted setup*). Масив `ic_query` містить комбінацію точок для лінійної комбінації публічних сигналів входу.

```c
typedef struct {
    zk_curve_point_g1_t  pi_a;            /* Елемент A у групі G1 */
    zk_curve_point_g2_t  pi_b;            /* Елемент B у групі G2 */
    zk_curve_point_g1_t  pi_c;            /* Елемент C у групі G1 */
} zk_snark_groth16_proof_t;

typedef struct {
    zk_curve_point_g1_t  alpha_g1;
    zk_curve_point_g2_t  beta_g2;
    zk_curve_point_g2_t  gamma_g2;
    zk_curve_point_g2_t  delta_g2;
    zk_curve_point_g1_t *ic_query;       /* Масив точок публічного входу */
    uint32_t             ic_query_len;
} zk_verification_key_t;
```

## 2. Коди помилок та детальний аналіз виключних ситуацій

Усі функції програмного інтерфейсу повертають 32-бітне ціле число зі знаком (`zk_status_t`). Значення `0` відповідає успішному виконанню операції (`ZK_SUCCESS`). Будь-яке від'ємне значення позначає конкретний клас помилок, що виникли під час розбору, валідації або алгебраїчної перевірки доказу.

Правильна обробка кодів помилок є критичною для криптографічної стійкості: верифікатор ніколи не повинен ігнорувати проміжні помилки парсингу точок або виходу чисел за межі поля.

| Код помилки (Enum) | Числове значення | Опис причини та рекомендована дія |
| :--- | :--- | :--- |
| `ZK_SUCCESS` | `0` | Операцію виконано успішно; доказ або крок прийнято. |
| `ZK_ERR_INVALID_PARAMETER` | `-1` | Передано `NULL`-вказівник або некоректні розміри буферів. |
| `ZK_ERR_INVALID_STATE` | `-2` | Виклик функції у невідповідному стані сесійного автомата. |
| `ZK_ERR_FIELD_OVERFLOW` | `-3` | Числове значення перевищує порядок модуля `p` скінченного поля. |
| `ZK_ERR_POINT_NOT_ON_CURVE` | `-4` | Точка `(X, Y)` не належить еліптичній кривій або не лежить у групі `G1/G2`. |
| `ZK_ERR_COMMITMENT_REJECTED` | `-5` | Зобов'язання `R` є тривіальним (нуль або одиниця групи). |
| `ZK_ERR_CHALLENGE_MISMATCH` | `-6` | Помилка генерації виклику або невідповідність Fiat-Shamir хешу. |
| `ZK_ERR_VERIFICATION_FAILED` | `-7` | Доказ алгебраїчно невірний: перевірка рівняння чи спарювання не пройдена. |
| `ZK_ERR_SETUP_CORRUPTED` | `-8` | Пошкоджено або несвіжий ключ верифікації (Common Reference String). |

Детальний аналіз типових виключних ситуацій:

1. **Переповнення поля (`ZK_ERR_FIELD_OVERFLOW`):** Виникає, коли передане байтове значення числа перевищує модуль поля `p`. Верифікатор повинен перевіряти нерівність `v < p` до виконання будь-яких арифметичних операцій.
2. **Точка поза кривою (`ZK_ERR_POINT_NOT_ON_CURVE`):** Перевірка тотожності `Y² = X³ + aX + b mod p` для точок `G1` та відповідального рівняння для `G2`. Передача точки, що не належить кривій, може дозволити нападнику реалізувати атаку на слабку підгрупу.
3. **Невірне спарювання (`ZK_ERR_VERIFICATION_FAILED`):** Повертається, коли підсумкове рівняння дуального оператора спарювання `e(A, B) ≠ e(alpha, beta) · e(x, gamma) · e(C, delta)` не справджується. Це є нормальним результатом перевірки фальшивого доказу.

## 3. Опис функціонального API C-інтерфейсу

### Сквозний потік інтерактивної верифікації

Інтерактивний потік верифікатора реалізує послідовність переходів станів. Спочатку сесія ініціалізується функцією `zk_verifier_init`, яка приймає публічні вхідні дані `x` та налаштовує параметри безпеки. Далі прийом зобов'язання `R` від доводжувача виконується через `zk_verifier_process_commitment`. Функція `zk_verifier_generate_challenge` обирає криптографічно стійкий випадковий виклик `e`, після чого очікується відповідь `s` у функції `zk_verifier_process_response`.

Кожна функція перевіряє поточний стан структури `session` перед виконанням операцій.

```c
/**
 * @brief Ініціалізація нової верифікаційної сесії.
 * @param session Вказівник на структуру сесії.
 * @param protocol Ідентифікатор криптографічного протоколу.
 * @param public_inputs Масив публічних даних x.
 * @param inputs_len Кількість елементів публічного входу.
 * @return ZK_SUCCESS або код помилки.
 */
int32_t zk_verifier_init(
    zk_interactive_session_t *session,
    zk_protocol_id_t          protocol,
    const zk_field_element_t *public_inputs,
    uint32_t                  inputs_len
);

/**
 * @brief Прийом зобов'язання R від доводжувача та перехід у стан WAITING_COMMITMENT.
 * @param session Вказівник на активну сесію.
 * @param commitment_R Байт-масив зобов'язання R.
 * @return ZK_SUCCESS у разі коректності елемента.
 */
int32_t zk_verifier_process_commitment(
    zk_interactive_session_t *session,
    const zk_field_element_t *commitment_R
);

/**
 * @brief Генерація криптографічно стійкого виклику e (Challenge).
 * @param session Вказівник на активну сесію.
 * @param out_challenge Буфер для запису згенерованого числа e.
 * @return ZK_SUCCESS при успішній генерації з системного джерела CSPRNG.
 */
int32_t zk_verifier_generate_challenge(
    zk_interactive_session_t *session,
    zk_field_element_t       *out_challenge
);

/**
 * @brief Отримання відповіді s, перевірка алгебраїчного рівняння та фіналізація.
 * @param session Вказівник на активну сесію.
 * @param response_s Байт-масив відповіді s.
 * @return ZK_SUCCESS якщо доказ прийнято, або ZK_ERR_VERIFICATION_FAILED при відхиленні.
 */
int32_t zk_verifier_process_response(
    zk_interactive_session_t *session,
    const zk_field_element_t *response_s
);
```

### Неінтерактивний API (NIZK / ZK-SNARK Verifier)

Для неінтерактивних доказів мережева взаємодія відсутня: верифікатор виконує атомарну перевірку доказу за допомогою функції `zk_nizk_groth16_verify`. Функція перевіряє рівняння спарювання `e(A, B) = e(alpha, beta) · e(x_IC, gamma) · e(C, delta)` над кривою BN254.

Обчислювальний порядок функції дорівнює `O(1)` відносно розміру доказу, та `O(|x|)` відносно кількості публічних сигналів входу.

```c
/**
 * @brief Однокрокова перевірка стислого неінтерактивного доказу ZK-SNARK (Groth16).
 * @param vk Вказівник на перевірочний ключ (Verification Key).
 * @param proof Вказівник на структуру доказу (pi_a, pi_b, pi_c).
 * @param public_inputs Вектор публічних вхідних сигналів.
 * @param inputs_len Кількість публічних сигналів.
 * @return ZK_SUCCESS якщо спарювання e(A,B) == e(alpha,beta) * e(x, gamma) * e(C, delta).
 */
int32_t zk_nizk_groth16_verify(
    const zk_verification_key_t   *vk,
    const zk_snark_groth16_proof_t *proof,
    const zk_field_element_t      *public_inputs,
    uint32_t                       inputs_len
);
```

## 4. Схема переходів станів автомата верифікатора

Автомат верифікатора функціонує строго відповідно до скінченно-автоматної моделі (FSM). Будь-яка спроба виконати виклик поза чергою призводить до скидання сесії у стан `ZK_STATE_ERROR` та повернення `ZK_ERR_INVALID_STATE`.

```
[ UNINITIALIZED ]
       │
       ▼  (zk_verifier_init)
[ WAITING_COMMITMENT ]
       │
       ▼  (zk_verifier_process_commitment)
[ CHALLENGE_GENERATED ]
       │
       ▼  (zk_verifier_generate_challenge & zk_verifier_process_response)
 ┌─────┴────────────────────────┐
 │                              │
 ▼ (Алгебра задоволена)         ▼ (Алгебра хибна)
[ VERIFIED_ACCEPTED ]        [ VERIFIED_REJECTED ]
```

Правила обробки переходів станів:

- Перехід з `UNINITIALIZED` у `WAITING_COMMITMENT` відбувається виключно після перевірки налідності публічних вхідних даних `x`.
- Перехід з `WAITING_COMMITMENT` у `CHALLENGE_GENERATED` вимагає успішної перевірки того, що зобов'язання `R` є некоректним або нетривіальним елементом групи.
- Перехід у термінальні стани `VERIFIED_ACCEPTED` або `VERIFIED_REJECTED` є остаточним. Після досягнення цих станів структура `session` не може бути використана повторно без нового виклику `zk_verifier_init`.

## 5. Формат серіалізації транскрипту та сумісність

Для передачі доказів через мережеві REST/gRPC API та зберігання в розподілених базах даних використовується канонічний JSON-формат або упакований шістнадцятковий канонічний бінарний формат (Hex-string):

```json
{
  "protocol": "SCHNORR_SECP256K1_V1",
  "security_level": 256,
  "public_key": "0x0279be667ef9dcbbac55a06295ce870b07029bfcdb2dce28d959f2815b16f81798",
  "transcript": {
    "commitment_R": "0x032cbe667ef9dcbbac55a06295ce870b07029bfcdb2dce28d959f2815b16f81799",
    "challenge_e": "0x5a3f1208a1b2c3d4e5f60718293a4b5c",
    "response_s": "0x8f14b29a102456789abcde0123456789"
  }
}
```

Для ZK-SNARK (Groth16 над кривою BN254) використовується бінарна упаковка розміром рівно 128 байтів:
- `pi_a`: 32 байти `X` + 32 байти `Y` (група `G1`, 64 байти);
- `pi_b`: 64 байти `X` + 64 байти `Y` (група `G2`, 128 байтів у стисненій формі 64 байти);
- `pi_c`: 32 байти `X` + 32 байти `Y` (група `G1`, 64 байти).

## 6. Рекомендації з безпеки реалізації верифікатора

1. **Захист від атак бічного каналу (Side-Channel Attacks):** Усі алгоритми порівняння великих чисел та перевірки точок на кривій повинні виконуватися за сталий час (англ. *constant-time execution*) для запобігання атакам за часом (англ. *timing attacks*).
2. **Стійкість до нульових точок:** Модуль верифікації зобов'язаний відхиляти нейтральні елементи (нескінченно віддалені точки), якщо вони передаються як зобов'язання `R` або елементи `pi_a, pi_b`, щоб заблокувати атаки заперечення (англ. *subgroup containment attacks*).
3. **Захист від підробки виклику:** При переході до Fiat-Shamir неінтерактивної форми криптографічний хеш **мусить** включати в себе як зобов'язання `R`, так і всі елементи публічного входу `x`. Втрата входу `x` з контексту хешування створює уразливість підробки доказу (англ. *weak Fiat-Shamir vulnerability*).
4. **Потокобезпечність (Thread Safety):** Структура `zk_verification_key_t` є константною та може бути використана кількома потоками верифікації одночасно. Об'єкти сесій `zk_interactive_session_t` не є потокобезпечними і повинні бути локальними для кожного окремого з'єднання.
