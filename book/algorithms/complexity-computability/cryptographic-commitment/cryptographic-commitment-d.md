Розподілені обчислювальні системи, криптографічні аукціони, протоколи голосування та децентралізовані фінансові мережі вимагають фіксації вибору або даних суб'єкта до того, як стануть відомі рішення інших учасників чи настане фаза виконання. Якщо аукціоніст у закритому аукціоні дізнається ставки учасників раніше часу, він може передати цю інформацію афілійованій особі. Якщо у грі «підкидання монети по телефону» один із гравців першим назве свою сторону монети, інший гравець миттєво оголосить вигідний для себе результат. З іншого боку, якщо учасник залишає свої дані нефіксованими, він отримає можливість підмінити свою ставку або відповідь після того, як дізнається результати суперників.

Розв'язанням цієї фундаментальної проблеми стало **криптографічне зобов'язання** (Commitment Scheme) — двофазний криптографічний протокол, який дозволяє одній стороні (доводжувачу або Alice) зафіксувати вибране значення або повідомлення в зашифрованому вигляді («покласти в сейф»), передати зафіксоване значення іншій стороні (верифікатору або Bob), а пізніше розкрити вміст («передати ключ від сейфа»). При цьому криптографічна схема гарантує дві фундаментальні властивості: Боб не може дізнатися зміст повідомлення до фази відкриття (**приховування / Hiding**), а Аліса не може відкрити зобов'язання як інше повідомлення, відмінне від початково зафіксованого (**зв'язування / Binding**).

Історичний процес виникнення цього криптографічного конверта з протоколів підкидання монети Мануеля Блума та його подальший розвиток детально описано у нарисі [Родоводи та суперечки довкола схеми криптографічного зобов'язання](book:algorithms/complexity-computability/cryptographic-commitment/hist-cryptographic-commitment.md).

## 1. Двофазна архітектура та формальне означення

Формально схема криптографічного зобов'язання над множиною повідомлень `M` являє собою пару алгоритмів `(Commit, Open)`, які працюють у двох послідовних фазах:

1. **Фаза зобов'язання (Commit Phase):**
   Доводжувач обирає повідомлення `m ∈ M` та випадкове значення (blinding factor / random salt) `r` з множини випадковості `R`.
   Доводжувач обчислює значення зобов'язання:
   ```
   c = Commit(m, r)
   ```
   Доводжувач надсилає `c` верифікатору, залишаючи значення `m` та `r` у таємниці.

2. **Фаза відкриття (Reveal / Open Phase):**
   Доводжувач передає верифікатору вихідні значення `(m, r)`.
   Верифікатор локально обчислює предикат верифікації:
   ```
   Open(c, m, r) = 1  <=>  Commit(m, r) =?= c
   ```
   Якщо рівність виконується, верифікатор приймає відкрите повідомлення `m` як дійсно зафіксоване у фазі 1.

Використання випадкового фактора `r` є суворо обов'язковим. Якщо обчислювати зобов'язання як детерміновану функцію `c = Commit(m)`, то у випадку малого простору повідомлень `M = {0, 1}` (наприклад, голосування «ТАК» або «НІ») верифікатор зможе миттєво розкрити `m`, обчисливши `Commit(0)` та `Commit(1)` і порівнявши їх з отриманим `c`. Додавання високоелементарної випадковості `r` перетворює процес на імовірнісне шифрування, роблячи `c` непередбачуваним.

## 2. Фундаментальні властивості стійкості: Hiding та Binding

Безпека будь-якої схеми зобов'язання тримається на двох стовпах, які математично протистоять зловживанням двох різних учасників протоколу:

```
                  ┌─────────────────────────────────────────┐
                  │ Криптографічне зобов'язання c           │
                  └────────────────────┬────────────────────┘
                                       │
            ┌──────────────────────────┴──────────────────────────┐
            ▼                                                     ▼
┌─────────────────────────┐                             ┌───────────────────┐
│  Приховування (Hiding)  │                             │Зв'язування(Binding│
├─────────────────────────┤                             ├───────────────────┤
│Захищає ДОВОДЖУВАЧА      │                             │Захищає ВЕРИФІКАТОР│
│від дострокового витоку  │                             │від підміни m      │
│значення повідомлення m. │                             │на інше m' Алісою. │
└─────────────────────────┘                             └───────────────────┘
```

### 2.1 Приховування (Hiding)

Властивість приховування захищає доводжувача від верифікатора. Вона означає, що зобов'язання `c` не розголошує жодного біта інформації про зафіксоване повідомлення `m` до фази відкриття.

Існують два класи цієї властивості:
- **Обчислювальне приховування (Computational Hiding):** Жоден імовірнісний алгоритм поліноміального часу (PPT-супротивник) не здатний розрізнити зобов'язання для двох різних повідомлень `m₀` та `m₁` з ймовірністю, істотно більшою за випадкове вгадування `1/2 + ε(k)`.
- **Безумовне / Досконале приховування (Perfect / Information-Theoretic Hiding):** Навіть супротивник із необмеженою обчислювальною потужністю математично не може визначити `m` за значенням `c`, оскільки розподіли імовірностей випадкової величини `Commit(m₀, R)` та `Commit(m₁, R)` є ідентичними.

### 2.2 Зв'язування (Binding)

Властивість зв'язування захищає верифікатора від доводжувача. Вона означає, що доводжувач не може змінити свою думку після передачі `c` і відкрити зобов'язання для іншого повідомлення `m' ≠ m`.

Аналогічно, виділяють два класи:
- **Обчислювальне зв'язування (Computational Binding):** Для будь-якого поліноміального доводжувача ймовірність знайти колізію — дві такі пари `(m, r)` та `(m', r')`, що `m ≠ m'`, але `Commit(m, r) = Commit(m', r')`, є нехтовно малою функцією `ε(k)`.
- **Безумовне / Досконале зв'язування (Perfect / Information-Theoretic Binding):** Для кожного `c` існує **не більше одного** повідомлення `m`, для якого існує `r` таке, що `Commit(m, r) = c`. Неіснування альтернативних коренів є абсолютним математичним фактом.

### 2.3 Неможливість одночасного безумовного приховування та зв'язування

В теорії складності та криптографії доведено фундаментальну теорему про неможливість (Impossibility Theorem): **жодна схема криптографічного зобов'язання не може володіти одночасно безумовним приховуванням та безумовним зв'язуванням у класичній обчислювальній моделі**.

Якщо схема володіє безумовним приховуванням, то для кожного зобов'язання `c` та для будь-якого повідомлення `m'` існує фактор випадковості `r'` такий, що `Commit(m', r') = c`. Супротивник з нескінченною обчислювальною потужністю може просто перебрати всі можливі `r'` і знайти паралельне відкриття для `m'`, порушивши безумовне зв'язування. І навпаки, якщо існує єдине `m` під `c` (безумовне зв'язування), необмежений верифікатор може перебрати всі пара `(m, r)` і однозначно вирахувати `m`, порушивши безумовне приховування.

Тому криптографи завжди обирають компроміс:
1. **Обчислювальне приховування + Безумовне зв'язування** (наприклад, зобов'язання на основі класичних хеш-функцій чи RSA).
2. **Безумовне приховування + Обчислювальне зв'язування** (наприклад, схема Педерсена).

Формальні алгебраїчні доведення цих критеріїв стійкості викладено у вставці [Математичні доведення стійкості зобов'язань Педерсена та KZG](book:algorithms/complexity-computability/cryptographic-commitment/math-cryptographic-commitment.md).

## 3. Практичні схеми зобов'язання

### 3.1 Проста хеш-схема (Hash-based Commitment)

Найпростіший спосіб побудувати схему зобов'язання полягає у використанні криптографічної хеш-функції `H` (наприклад, SHA-256):

```
c = H(m || r)
```

де `m` — повідомлення, `r` — криптографічно стійкий випадковий бітовий рядок (довжиною не менше 256 біт), `||` — операція конкатенації.

- **Фаза відкриття:** Доводжувач передає `(m, r)`. Верифікатор обчислює `H(m || r)` і перевіряє збіг із `c`.
- **Стійкість:** Приховування базується на властивості стійкості хеш-функції до пошуку прообразу (Preimage Resistance) та оракулі випадковості. Зв'язування базується на стійкості `H` до колізій (Collision Resistance). Якщо доводжувач знаходить колізію `H(m || r) = H(m' || r')`, він порушує зв'язування.

### 3.2 Гомоморфна схема Педерсена (Pedersen Commitment)

Схема Педерсена спирається на важкість обчислення дискретного логарифма у мультиплікативній групі скінченного поля або групі еліптичної кривої.

Нехай `G` — циклічна група простого порядку `q` з генератором `g`. Нехай `h = g^x ∈ G` — другий генератор групи такий, що ніхто не знає дискретного логарифма `x = log_g(h)` (значення `h` згенеровано через процес Nothing-Up-My-Sleeve).

Для обчислення зобов'язання для значення `v ∈ Z_q` з випадковим фактором приховування `r ∈ Z_q`:

```
c = g^v · h^r mod p
```

Схема Педерсена володіє унікальною властивістю **адитивного гомоморфізму**. Помноживши два зобов'язання `c₁` та `c₂`, верифікатор отримує коректне зобов'язання для суми значень `v₁ + v₂`:

```
c₁ · c₂ = (g^v₁ · h^r₁) · (g^v₂ · h^r₂)       [підстановка означень зобов'язань c₁ та c₂]
        = (g^v₁ · g^v₂) · (h^r₁ · h^r₂)       [комутативність множення в групі]
        = g^(v₁ + v₂) · h^(r₁ + r₂) mod p     [властивість степеня: a^x · a^y = a^(x+y)]
        = Commit(v₁ + v₂, r₁ + r₂)            [означення зобов'язання для суми]
```

Це дозволяє перевіряти математичні рівності та баланси над зашифрованими даними без розкриття самих даних.

### 3.3 Векторні та поліноміальні зобов'язання (Vector & Polynomial Commitments)

Для сучасних розподілених систем зобов'язання щодо одного скаляра є недостатнім. Потрібні схеми, які дозволяють зафіксувати цілий вектор `V = (v₁, v₂, ..., v_N)` або поліном `f(X)` і відкривати лише окремі елементи або точки оцінювання:

1. **Дерева Меркла (Merkle Tree Commitments):** Векторне зобов'язання, де значення зафіксовано в листі дерева, а зобов'язанням виступає корінь `Root`. Відкриття `i`-го елемента вимагає доказу Меркла (Merkle Audit Path) розміру `O(log N)`.
2. **Поліноміальна схема KZG (Kate-Zaverucha-Goldberg):** Дозволяє зафіксувати поліном `f(X)` ступеня `d` у єдиній точці групи `C = [f(τ)]₁ ∈ G₁` за допомогою публічних параметрів SRS (Structured Reference String). KZG дозволяє надати доказ того, що `f(z) = y` для будь-якої точки `z`, причому розмір доказу `π` становить всього один елемент групи `O(1)`, а верифікація виконується за один виклик білінійного спарювання.

## 4. Спектр застосування в сучасних розподілених системах

Криптографічні зобов'язання є універсальними будівельними блоками (cryptographic primitives), на яких базується безпека більшості сучасних протоколів:

- **Конфіденційні транзакції (Confidential Transactions / Monero / Liquid):** Суми переказу грошей зашифровано через зобов'язання Педерсена. Мережа перевіряє, що `∑ C_inputs = ∑ C_outputs + Fee`, що гарантує відсутність емісії монет з повітря без відкриття балансів користувачів.
- **Доведення з нульовим розголошенням (ZK-SNARKs & ZK-STARKs):** Використовують зобов'язання KZG, IPA або FRI для фіксації векторів виконань обчислювальних схем (Execution Trace) та коефіцієнтів поліноміальних рівнянь.
- **Масштабування блокчейнів (Stateless Clients & EIP-4844):** Використовують KZG-зобов'язання для завірення великих блоків даних (Blobs) у мережі Ethereum, забезпечуючи перевірку доступності даних (Data Availability) без завантаження повного блоку.
- **Аукціони із закритими ставками (Vickrey Auctions) та Електронне голосування:** Забезпечують неможливість спотворення результатів чи підглядання голосів до моменту офіційного підрахунку.

## 5. Системний аналіз обчислювальної складності та компромісів

При виборі конкретної схеми зобов'язання архітектори розподілених систем змушені балансувати між обчислювальними ресурсами доводжувача, верифікатора та розміром доказу, який передається мережею.

Нижче наведено порівняльну характеристику основних класів зобов'язань за критеріями обчислювальної складності:

```
┌────────────────────┬────────────────────┬────────────────────┬────────────────────┐
│ Схема зобов'язання │ Складність Commit  │ Розмір доказу Open │ Складність Verify  │
├────────────────────┼────────────────────┼────────────────────┼────────────────────┤
│ Хеш-конверт        │ O(1)               │ O(1) [m + r]       │ O(1)               │
│ Педерсен           │ O(1) [експонента]  │ O(1) [v + r]       │ O(1) [експонента]  │
│ Дерево Меркла      │ O(N)               │ O(log N)           │ O(log N)           │
│ KZG Поліноміальне  │ O(d)               │ O(1) [1 елемент G₁]│ O(1) [1 спарювання]│
└────────────────────┴────────────────────┴────────────────────┴────────────────────┘
```

Розглянемо детальніше кожен з цих параметрів:

1. **Хеш-конверти:** Забезпечують максимально швидке обчислення `Commit` та `Verify` на процесорах загального призначення через наявність апаратних інструкцій SHA-256. Проте вони не володіють гомоморфними властивостями.
2. **Зобов'язання Педерсена:** Вимагають скалярного множення на еліптичній кривій, що в 100–1000 разів повільніше за обчислення хешу, але надають адитивний гомоморфізм.
3. **Поліноміальні зобов'язання KZG:** Вимагають попереднього проведення процедури довереного налаштування (Trusted Setup ceremony) для генерації SRS. Проте можливість перевірити оцінку полінома ступеня `d = 1 000 000` за один виклик білінійного спарювання `O(1)` робить KZG незамінним для рівнів масштабування L2 в блокчейнах.

## 6. Детальний аналіз крайових випадків та вразливостей

Робота криптографічних зобов'язань у реальних умовах супроводжується низкою крайових випадків (edge cases) та потенційних атак, які вимагають додаткових засобів захисту:

### 6.1 Атака розширюваності довжини у хеш-конвертах (Length Extension Attack)
При використанні застарілих хеш-функцій сімейства MD5 або SHA-1/SHA-256 у простій конструкції `c = H(r || m)` супротивник може скористатися властивістю побудови Меркла — Дамґорда (Merkle-Damgård construction) і обчислити `c' = H(r || m || m_added)` без знання `r`. Для запобігання цій атаці обов'язково використовують порядок `c = H(m || r)` або конструкцію HMAC.

### 6.2 Захист від атак виходу за межі діапазону (Range Proof Integration)
У фінансових протоколах на основі зобов'язань Педерсена доводжувач може зафіксувати від'ємне значення `v = -100 ≡ p - 100 mod p`. При додаванні з іншими зобов'язаннями баланс буде математично збережено (`50 + (-100) + 50 = 0`), але користувач отримає змогу згенерувати додатні монети з нічого. Для вирішення цієї проблеми зобов'язання Педерсена завжди супроводжуються доказом діапазону (Bulletproofs / Range Proofs), який гарантує, що `v ∈ [0, 2^64)`.

Криптографічне зобов'язання пройшло шлях від елегантного теоретичного вирішення математичної гри до фундаментального наріжного каменя децентралізованих обчислень XXI століття.
