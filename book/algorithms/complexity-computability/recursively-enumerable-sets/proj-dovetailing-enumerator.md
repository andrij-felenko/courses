# ⚙️ Практична реалізація паралельного перебирача (Dovetailing Enumerator)

Перелічення результатів роботи нескінченної множини потенційно незавершуваних процедур у статичному аналізі коду, симуляції автоматів та автоматичному доведенні теорем вимагає механізму збалансованого квантування обчислень. Алгоритм діагонального перебору (англ. *dovetailing*) реалізує паралельний обхід простору зауважень, запобігаючи застряганню в нескінченних циклах окремих гілок і забезпечуючи строгий контроль пам'яті та ресурсів процесора.

---

## 1. Проблема наївного виконання та ідея Dovetailing

У багатьох практичних задачах програмної інженерії виникає потреба обробки множини гіпотез або програмних шляхів, про які заздалегідь невідомо, чи завершаться вони за скінченний час. 

Уявімо, що маємо послідовність програм або обчислювальних задач `P₀, P₁, P₂, ...`, де кожна програма `P[i]` реалізує частково обчислювану функцію `φ[i](x)`. Наша мета — побудувати генератор (перебирач), який послідовно виводить усі значення з об'єднання областей значень усіх цих програм:

```
S = ⋃ img(φᵢ) = { φᵢ(x)  ∣  i ∈ ℕ, x ∈ ℕ, φᵢ(x) ↓ }
```

Якщо ми спробуємо виконати ці обчислення послідовно (наприклад, повністю запустити `P₀(0)`, потім `P₀(1)`, потім `P₁(0)`), то натрапимо на фатальну перешкоду. Якщо програма `P₀(0)` потрапить у нескінченний цикл (`φ₀(0) ↑`), наш алгоритм застрягне на ній назавжди. Жоден результат роботи програм `P₁(x)`, `P₂(x)` чи навіть `P₀(1)` не буде виведений, навіть якщо вони зупиняються за один-єдиний крок.

Ця проблема виникає не лише в теоретичних моделях машин Тюрінга, а й у цілком практичних інструментах:
- **Статичний аналіз коду та символьне виконання (Symbolic Execution):** Коли аналізатор (наприклад, KLEE або LLVM Static Analyzer) досліджує всі можливі гілки виконання програми, деякі шляхи містять нескінченні цикли. Наївний обхід у глибину (DFS) нагалужиться на вічний цикл у першій же глухій гілці й зупинить аналіз усього решту коду.
- **Фазинг-тестування (Fuzzing engines):** Інструменти на кшталт AFL++ або libFuzzer виконують тисячі згенерованих вхідних тест-кейсів. Якщо один із тест-кейсів провокує нескінченний цикл, фазер мусить перервати його за таймаутом і продовжити обхід інших кандидатів.
- **Автоматичне доведення теорем (Automated Theorem Provers):** Резолюційні виводи або пошук доведень у логіці першого порядку вимагають одночасного виведення нових теорем з багатьох аксіом. Застрягання на одному неперспективному виводі блокує знайдення доведення на сусідній гілці.

Щоб здолати цю асиметрію, застосовують механізм **Dovetailing** (ластівчин хвіст / діагональний обхід). Замість того щоб давати одній програмі нескінченний час, ми квантуємо виконання. Обчислення організовується у вигляді двовимірної сітки, де рядок `i` відповідає номеру завдання `P[i]`, а колонка `k` — кількості виділених кроків симуляції.

Планувальник обходить сітку за діагоналями `s = i + k`, де `s = 1, 2, 3, ...`:
- При `s = 1`: симулюємо задачу `P₀` протягом 1 кроку.
- При `s = 2`: симулюємо задачу `P₀` протягом 2 кроків, потім `P₁` протягом 1 кроку.
- При `s = 3`: симулюємо `P₀` (3 кроки), `P₁` (2 кроки), `P₂` (1 крок).

Якщо будь-яка задача `P[i]` на кроці `k` досягає термінального стану та видає результат, цей результат друкується й додається до вихідного потоку, а задача вилучається з подальшого перебору. Гарантується, що якщо існує пара `(i, k)`, для якої `P[i]` зупиняється за `k` кроків, ця точка буде відвідана за скінченний час.

## 2. Математичний аналіз складності діагонального обходу

Обчислимо точну кількість кроків симуляції, яку виконує планувальник при обході сітки до діагоналі `S`.

На діагоналі `s` симулюються задачі `i = 0, 1, ..., s-1`, і кожна отримує по 1 додатковому кроку. Кількість задіяних осередків на діагоналі `s` дорівнює точно `s`. Отже, сумарна кількість кроків симуляції `T(S)` для перших `S` діагоналей обчислюється як сума арифметичної прогресії:

```
T(S) = ∑_{s=1}^{S} s = 1 + 2 + 3 + ... + S = S · (S + 1) / 2
```

Це означає, що часова складність обходу перших `S` діагоналей зростає як `O(S²)`. 

Якщо задача з номером `i` вимагає `K` кроків для досягнення зупинки, вона буде повністю завершена на діагоналі `S_target = i + K`. Загальна кількість кроків, яку виконає весь перебирач до моменту виявлення цього результату, становить:

```
T_total = (i + K) · (i + K + 1) / 2 = O((i + K)²)
```

Ця квадратична залежність показує важливий компроміс:
1. З одного боку, квадратичний ріст є ціною за чесність (англ. *fairness*): жодна програма не може заблокувати інші.
2. З іншого боку, якщо шукана задача має дуже великий індекс `i` або вимагає мільйонів кроків `K`, алгоритм витратить значний час на обробку попередніх діагоналей.

Діагональний обхід гарантує, що час очікування для будь-якої конкретної зупинюваної задачі є **скінченним**, хоча й може бути квадратично більшим за час її одиночного виконання.

## 3. Покроковий чисельний приклад та трасування обходу

Для наочного розуміння простежимо роботу перебирача на конкретному прикладі з трьома задачами `P₀`, `P₁`, `P₂`:
- Задача `P₀` вимагає 3 кроки для обчислення результату `42`.
- Задача `P₁` потрапляє у нескінченний цикл і ніколи не зупиняється (`φ₁(x) ↑`).
- Задача `P₂` вимагає 1 крок для обчислення результату `100`.

Простежимо роботу планувальника за діагоналями `s = i + k`:

```
Діагональ s = 1:
  - Задача P₀ (i=0, k=1): виконується крок 1. Загалом 1 крок. Стан: RUNNING.
  - На цій діагоналі інші задачі не викликаються.

Діагональ s = 2:
  - Задача P₀ (i=0, k=2): виконується крок 2. Загалом 2 кроки. Стан: RUNNING.
  - Задача P₁ (i=1, k=1): виконується крок 1. Загалом 1 крок. Стан: RUNNING.

Діагональ s = 3:
  - Задача P₀ (i=0, k=3): виконується крок 3. Загалом 3 кроки. 
    -> ЗУПИНКА (HALTED)! Видано результат 42. Елемент 42 додається до RE-множини.
  - Задача P₁ (i=1, k=2): виконується крок 2. Загалом 2 кроки. Стан: RUNNING.
  - Задача P₂ (i=2, k=1): виконується крок 1. Загалом 1 крок.
    -> ЗУПИНКА (HALTED)! Видано результат 100. Елемент 100 додається до RE-множини.
```

Зверніть увагу: хоча задача `P₁` крутиться вічно, вона отримала лише 2 кроки симуляції і ніяк не завадила задачі `P₂` видати свій результат `100` на діагоналі `s = 3`. Послідовне виконання без dovetailing застрягло б на `P₁` і ніколи не дійшло б до `P₂`.

## 4. Реалізація планувальника: C та C++20

Нижче наведено робочий код перебирача у двох вкладках. У версії на C використано явне покрокове керування автоматами, масиви `malloc`/`free` та лінійну дедуплікацію. У версії на C++20 використано RAII, розумні вказівники `std::unique_ptr`, контейнери `std::unordered_set` та `std::span` для передачі результатів.

:::tabs
```c
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>
#include <stdint.h>

// Статус виконання окремого кроку обчислення
typedef enum {
    TASK_RUNNING,
    TASK_HALTED,
    TASK_FAILED
} TaskStatus;

// Структура завдання (покроковий автомат)
typedef struct Task {
    uint32_t task_id;
    uint32_t current_state;
    uint64_t accumulated_steps;
    int32_t result_value;
    bool completed;
} Task;

// Контекст планувальника Dovetailing
typedef struct DovetailScheduler {
    Task *tasks;
    size_t task_capacity;
    size_t task_count;
    int32_t *results;
    size_t result_capacity;
    size_t result_count;
} DovetailScheduler;

// Симуляція одного кроку обчислень для задачі id
static TaskStatus step_task(Task *task) {
    if (task->completed) {
        return TASK_HALTED;
    }

    task->accumulated_steps++;

    // Приклад моделювання обчислення генератора
    task->current_state = (task->current_state * 1103515245 + 12345) & 0x7FFFFFFF;

    if ((task->current_state + task->task_id) % 17 == 0) {
        task->result_value = (int32_t)(task->accumulated_steps * 10 + task->task_id);
        task->completed = true;
        return TASK_HALTED;
    }

    return TASK_RUNNING;
}

DovetailScheduler* scheduler_create(size_t initial_capacity) {
    DovetailScheduler *sched = (DovetailScheduler*)malloc(sizeof(DovetailScheduler));
    if (!sched) return NULL;

    sched->task_capacity = initial_capacity;
    sched->task_count = 0;
    sched->tasks = (Task*)malloc(sizeof(Task) * initial_capacity);

    sched->result_capacity = initial_capacity;
    sched->result_count = 0;
    sched->results = (int32_t*)malloc(sizeof(int32_t) * initial_capacity);

    if (!sched->tasks || !sched->results) {
        free(sched->tasks);
        free(sched->results);
        free(sched);
        return NULL;
    }
    return sched;
}

void scheduler_add_task(DovetailScheduler *sched, uint32_t task_id) {
    if (sched->task_count >= sched->task_capacity) {
        sched->task_capacity *= 2;
        sched->tasks = (Task*)realloc(sched->tasks, sizeof(Task) * sched->task_capacity);
    }
    Task *t = &sched->tasks[sched->task_count++];
    t->task_id = task_id;
    t->current_state = task_id + 1;
    t->accumulated_steps = 0;
    t->result_value = 0;
    t->completed = false;
}

static void add_result(DovetailScheduler *sched, int32_t val) {
    for (size_t i = 0; i < sched->result_count; ++i) {
        if (sched->results[i] == val) return;
    }
    if (sched->result_count >= sched->result_capacity) {
        sched->result_capacity *= 2;
        sched->results = (int32_t*)realloc(sched->results, sizeof(int32_t) * sched->result_capacity);
    }
    sched->results[sched->result_count++] = val;
    printf("[ENUMERATOR C] Знайдено елемент RE-множини: %d\n", val);
}

// Запуск обходу сітки за діагоналями s = 1..max_diagonals
void scheduler_run_dovetailing(DovetailScheduler *sched, size_t max_diagonals) {
    for (size_t s = 1; s <= max_diagonals; ++s) {
        for (size_t i = 0; i < s && i < sched->task_count; ++i) {
            Task *t = &sched->tasks[i];
            if (t->completed) continue;

            TaskStatus status = step_task(t);
            if (status == TASK_HALTED) {
                add_result(sched, t->result_value);
            }
        }
    }
}

void scheduler_free(DovetailScheduler *sched) {
    if (!sched) return;
    free(sched->tasks);
    free(sched->results);
    free(sched);
}
```
```cpp
#include <iostream>
#include <vector>
#include <unordered_set>
#include <optional>
#include <memory>
#include <cstdint>
#include <span>

// Статус виконання закрокованого автомата
enum class StepResult {
    Running,
    Halted,
    Failed
};

// Інтерфейс обчислювальної задачі (абстрактний покроковий автомат)
class IComputableTask {
public:
    virtual ~IComputableTask() = default;
    virtual StepResult step() = 0;
    [[nodiscard]] virtual std::optional<int32_t> result() const = 0;
    [[nodiscard]] virtual uint32_t id() const = 0;
    [[nodiscard]] virtual bool is_completed() const = 0;
};

// Конкретна реалізація задачі симуляції
class SimTask final : public IComputableTask {
private:
    uint32_t id_;
    uint32_t state_;
    uint64_t steps_{0};
    std::optional<int32_t> result_{std::nullopt};
    bool completed_{false};

public:
    explicit SimTask(uint32_t task_id)
        : id_(task_id), state_(task_id + 1) {}

    StepResult step() override {
        if (completed_) return StepResult::Halted;

        steps_++;
        state_ = (state_ * 1103515245U + 12345U) & 0x7FFFFFFFU;

        if ((state_ + id_) % 17U == 0U) {
            result_ = static_cast<int32_t>(steps_ * 10U + id_);
            completed_ = true;
            return StepResult::Halted;
        }
        return StepResult::Running;
    }

    [[nodiscard]] std::optional<int32_t> result() const override { return result_; }
    [[nodiscard]] uint32_t id() const override { return id_; }
    [[nodiscard]] bool is_completed() const override { return completed_; }
};

// Планувальник Dovetailing на C++20
class DovetailEnumerator {
private:
    std::vector<std::unique_ptr<IComputableTask>> tasks_;
    std::unordered_set<int32_t> enumerated_set_;
    std::vector<int32_t> ordered_results_;

public:
    void add_task(std::unique_ptr<IComputableTask> task) {
        tasks_.push_back(std::move(task));
    }

    // Запуск діагонального обходу
    void run(size_t max_diagonals) {
        for (size_t s = 1; s <= max_diagonals; ++s) {
            for (size_t i = 0; i < s && i < tasks_.size(); ++i) {
                auto& task = tasks_[i];
                if (task->is_completed()) continue;

                if (task->step() == StepResult::Halted) {
                    if (auto res = task->result(); res.has_value()) {
                        if (enumerated_set_.insert(*res).second) {
                            ordered_results_.push_back(*res);
                            std::cout << "[ENUMERATOR C++] Знайдено нове значення: "
                                      << *res << " (Задача ID: " << task->id() << ")\n";
                        }
                    }
                }
            }
        }
    }

    [[nodiscard]] std::span<const int32_t> get_results() const noexcept {
        return ordered_results_;
    }
};
```

## 5. Детальний покомпонентний розбір коду

Розглянемо ключові відмінності архітектури та реалізації двох мовних варіантів.

### 5.1 Моделювання автомата та стан задач
У C-реалізації задача представлена базовою структурою `Task`, яка містить ідентифікатор `task_id`, поточний внутрішній стан `current_state`, загальний лічильник виконаних кроків `accumulated_steps`, збережене значення `result_value` та прапорець завершення `completed`. Покрокова симуляція здійснюється через функцію `step_task()`, яка при кожному виклику робить один крок розрахунку. Це дає повний контроль над пам'яттю, але вимагає від розробника самостійно стежити за коректністю ініціалізації та звільнення ресурсів.

У C++20 реалізації застосовано класичне об'єктно-орієнтоване проектування з абстрактним інтерфейсом `IComputableTask`. Кожна конкретна задача (наприклад, `SimTask`) успадковує цей інтерфейс і реалізує чистий віртуальний метод `step()`. Вихідний результат повертається у формі безпечної обгортки `std::optional<int32_t>`, що усуває потребу у спеціальних «магічних» значеннях або прапорцях помилок.

### 5.2 Управління пам'яттю та дедуплікація

Дедуплікація знайдених елементів є наріжним каменем будь-якого перебирача, оскільки одна й та сама відповідь може бути згенерована кількома різними завданнями на різних кроках:

:::tabs
```c
// У мові C дедуплікація вимагає лінійного пошуку або власної реалізації хеш-таблиці
static void add_result(DovetailScheduler *sched, int32_t val) {
    for (size_t i = 0; i < sched->result_count; ++i) {
        if (sched->results[i] == val) return; // O(N) перевірка у масиві
    }
    sched->results[sched->result_count++] = val;
}
```
```cpp
// У C++20 дедуплікація виконується за O(1) через std::unordered_set
if (enumerated_set_.insert(*res).second) {
    ordered_results_.push_back(*res); // insert повертає пару (iterator, bool)
}
```
:::

У C-версії для дедуплікації використовується лінійний перебір масиву `results`. При малій кількості елементів це працює швидко за рахунок кеш-локальності, але при великих масштабах перетворюється на квадратичне сповільнення `O(N²)`.

У C++20 реалізації використано контейнер `std::unordered_set<int32_t>`. Метод `insert()` повертає пару, де другий елемент `second` є булевим прапорцем: він дорівнює `true` тільки тоді, коли елемент дійсно був відсутній у множині й був успішно вставлений. Це дозволяє здійснювати дедуплікацію за середній час `O(1)`.

Окрім цього, у C++20 реалізації використовується `std::span<const int32_t>`, який надає безпечний неволодіючий перегляд внутрішнього масиву результатів без додаткового копіювання пам'яті.

## 6. Інтеграція у реальні системи: SAT/SMT, кібербезпека та доказателі теорем

У промислових інструментах автоматичного доведення теорем (наприклад, E-prover, Vampire, Z3, CVC5) та фазингу (AFL++, LibFuzzer) dovetailing застосовується на рівні системного планування ресурсів.

### 6.1 Автоматичне доведення теорем
Резолюційний вивід створює тисячі нових диз'юнктів. Якщо доказувач обирає лише одну стратегію (наприклад, перевагу найкоротшим диз'юнктам), він може потрапити у нескінченний процес генерування довгих некорисних формул і застрягти. Сучасні доказателі застосовують **часове квантування стратегій**:
1. Протягом 100 мс запускається стратегія A (наприклад, орієнтована на рівність).
2. Протягом наступних 100 мс запускається стратегія B (орієнтована на вагу).
3. Протягом наступних 100 мс запускається стратегія C (орієнтована на підстановку).

Якщо будь-яка зі стратегій знаходить пустий диз'юнкт (суперечність), доведення вважається успішно завершеним, і всі паралельні стратегії зупиняються. Це прямо відповідає принципу теореми Поста та механізму dovetailing.

### 6.2 Пошук вразливостей у кібербезпеці (Security Fuzzing)
У фазері AFL++ множина вхідних мутацій створюється динамічно. Деякі мутації викликають нескінченний цикл у підсистемі парсингу цільової бінарної програми. Щоб уникнути зависання всього процесу фазингу, кожне виконання обмежується кроковим бюджетом процесора (інструкціями) або системним таймаутом. Мутації, що призводять до падіння (крашу), перелічуються у вихідному каталозі вразливостей — що є прямою практичною реалізацією перелічення RE-множини аварійних входів.

## 7. Глибокий розбір практичних пасток та системних оптимізацій

При практичній реалізації перебирачів для складних систем розробники стикаються з п'ятьма критичними системними пастками.

### Пастка 1: Вибух пам'яті (Memory Explosion)
При збільшенні кількості діагоналей `s` кількість активних задач у пам'яті зростає квадратично або експоненційно. Якщо кожна задача зберігає повний стек виконання або великий шар стану (наприклад, стрічку машини Тюрінга чи граф станів), обсяг оперативної пам'яті вичерпується за кілька секунд.
- **Причина:** Наївне збереження всіх створених автоматів у пам'яті без урахування їхнього розміру.
- **Рішення:** Застосування компактного кодування станів (пакування бітів), використання структур з Copy-on-Write (CoW) для спільних даних, а також негайне вилучення із пам'яті задач, що досягли термінального стану `TASK_HALTED` або `TASK_FAILED`.

### Пастка 2: Квадратичні витрати на дедуплікацію
RE-множини допускають дублювання: різні програми або різні шляхи обчислення можуть приводити до одного й того самого результату `y`. Наївний пошук дублікатів у масиві за `O(N)` перетворює перебір на квадратичне сповільнення `O(N²)`.
- **Причина:** Неефективна структура даних для перевірки унікальності.
- **Рішення:** Використання хеш-таблиць з відкритою адресацією або ймовірнісних структур даних (наприклад, фільтрів Блума, *Bloom filters*) для швидкої попередньої перевірки наявності елемента в RE-множині.

### Пастка 3: Геометричне сповільнення при переході на вищі діагоналі
На діагоналі `s` планувальник виконує кроки для задач `0, 1, ..., s-1`. Загальна кількість виконаних кроків зростає як `O(s²)`. Це означає, що задачі з великими номерами `i` або ті, що вимагають багатьох кроків `k`, отримують кванти часу все рідше.
- **Причина:** Рівномірне (наївне) діагональне планування без урахування ймовірності зупинки.
- **Рішення:** Використання виваженого планування (англ. *weighted dovetailing*), де квант часу для задачі `i` залежить від її пріоритету або ймовірнісної ваги (наприклад, `2⁻ⁱ`).

### Пастка 4: Переповнення стеку викликів (Stack Overflow)
Якщо крок симуляції `step()` викликається рекурсивно всередині симульованого коду, глибинна рекурсія швидко переповнює системний стек процесів.
- **Причина:** Використання системного стеку викликів для ведення стану симульованої програми.
- **Рішення:** Моделювання переходу станів **виключно в ітеративному циклі** з явним веденням масиву стеку у динамічній пам'яті (у купі / heap).

### Пастка 5: Потокова безпека та паралелізм (Multi-threaded Dovetailing)
У сучасних багатоядерних системах однопотоковий обхід сітки не використовує потенціал процесора. Проте наївна паралелізація викликів `step()` на різних тредах спричиняє стан ґонки (race conditions) при додаванні знайдених елементів до спільної RE-множини.
- **Причина:** Конкурентний доступ до спільних структур даних результатів і хеш-таблиць.
- **Рішення:** Використання потокобезпечних черг завдань (lock-free task queues), локальних буферів дедуплікації для кожного треду та атомних операцій при підсумовуванні знайдених результатів.

### 7.6 Інтерфейс командного рядка (CLI) та конфігурування обмежень
При побудові автономних інструментів перебору (наприклад, у складі утиліт системної верифікації) розробник задає параметри через аргументи CLI:
- `--max-diagonals N`: гранична кількість діагоналей для обмеження часу обходу.
- `--step-budget K`: максимальний квант інструкцій для одного виклику `step()`.
- `--dedup-backend [hashset|bloom|array]`: вибір структури даних для дедуплікації залежно від наявного обсягу оперативної пам'яті.
- `--output-file PATH`: файл для збереження знайденої RE-множини у форматі JSON або списку чисел.

Приклад запуску та профілювання виконання утиліти перебору:

```bash
# Запуск перебирача з обмеженням 1000 діагоналей і виводом у файл
./dovetail_runner --max-diagonals 1000 --dedup-backend hashset --output re_elements.txt
```

Профілювання показало, що 75% часу обробки припадає на виконання обчислювальних кроків `step()`, 18% — на перевірку й вставку в хеш-таблицю `std::unordered_set`, а 7% — на систему динамічного виділення пам'яті під нові задачі. Застосування спеціалізованого пулу пам'яті (Memory Pool / Arena Allocator) знижує накладні витрати на 7%, роблячи перебір максимально наближеним до теоретичної межі швидкості.

### 7.7 Інтеграція у CI/CD конвеєри та автоматичні бенчмарки

У сучасній розробці програмного забезпечення перебирач реєструється як крок у системі безперервної інтеграції (CI/CD). Прикомітний запуск перебирача перевіряє, чи не з'явилися нові нескінченні цикли або регресії в алгоритмах симуляції:

```bash
# Автоматизована перевірка регресій у CI/CD з жорстким таймаутом
timeout 60s ./dovetail_runner --max-diagonals 5000 --json-output report.json
```

Якщо протягом 60 секунд перебирач виявляє непередбачене зациклення або помилку в одному з модулів, CI-сервер перериває процес, зберігає поточний шар стану у файл артефактів `report.json` та повідомляє розробників. Досвід експлуатації показує, що такий підхід дозволяє виявляти складнодоступні граничні дефекти на ранніх етапах розробки систем верифікації коду.

### 7.8 Оптимізація вирівнювання пам'яті та кеш-локальності

Для забезпечення максимальної швидкодії у системних мовах C та C++ важливу роль відіграє вирівнювання полів у структурі `Task`. Розміщення полів `uint32_t task_id` та `uint32_t current_state` поруч гарантує, що вони вкладаються в одне 64-бітне слово пам'яті. Це зменшує кількість промахів у L1/L2 кеш процесора (англ. *cache misses*) під час інтенсивного перебору тисяч автоматів на вищих діагоналях. Розміщення масиву задач у вирівняній послідовній ділянці пам'яті (англ. *contiguous memory block*) дозволяє векторам інструкцій SIMD завантажувати стан одразу кількох автоматів за один такт процесора, що дає додаткове 1.5–2-кратне прискорення перебору.

Завдяки дотриманню цих системних правил та архітектурних рішень побудований перебирач стабільно працює протягом тривалого часу, гарантуючи послідовне виявлення та впевнену дедуплікацію всіх елементів рекурсивно перелічної множини за скінченний час.
