# 📋 Інтерфейс та специфікація двигуна перелічення (Enumerator API)

Ця вставка містить відкриту специфікацію системного програмного інтерфейсу (API) та контракти взаємодії для двигуна перелічення рекурсивно перелічних множин (англ. *Dovetailing Enumeration Engine*). Документ визначає структури даних, коди помилок, функції керування життєвим циклом, параметри конфігурації, механізми зворотності викликів (callbacks) та профілювання обчислювальних ресурсів.

---

## 1. Загальна архітектура та публічний контракт

Двигун перелічення надає низькорівневий C-сумісний ABI-інтерфейс та ідіоматичні обгортки для C++20. Двигун керує впорядкованим виконанням абстрактних покрокових задач, здійснює дедуплікацію згенерованих результатів та підтримує строгий контроль пам'яті й квантів часу процесора.

### Основні концепції та принципи проекту
- **Task (Завдання):** Ізольований покроковий автомат, який виконує частково рекурсивне обчислення. На кожному кроці автомат повертає статус виконання та (у разі зупинки) вихідне значення. Автомат зобов'язаний бути ітеративним і не спиратися на системний стек викликів.
- **Enumerator Context (Контекст перебирача):** Непрозорий об'єкт керування (`EnumeratorHandle`), що утримує реєстр усіх активних задач, масив результатів, хеш-таблицю дедуплікації та метрики виконання. Контекст є власником усього виділеного ресурсу пам'яті.
- **Diagonal Step (Діагональний крок):** Базовий квант планування, протягом якого двигун виконує по одному кроку для задач з номерами `0, 1, ..., s-1`.

---

## 2. Типи даних та структури конфігурації

### 2.1 Коди статусів та помилок (`EnumeratorStatus`)

Усі функції API повертають код статусу типу `EnumeratorStatus`. Значення `ENUM_OK` (0) позначає успішне виконання операції. Від'ємні значення відповідають помилкам.

| Код статусу | Числове значення | Опис та семантика помилки |
| :--- | :--- | :--- |
| `ENUM_OK` | `0` | Операція успішно завершена. |
| `ENUM_ERR_NULL_POINTER` | `-1` | Передано нульовий вказівник у якості аргументу. |
| `ENUM_ERR_INVALID_CONFIG` | `-2` | Помилка конфігурації (наприклад, від'ємний лиміт пам'яті або відсутність покрокової функції). |
| `ENUM_ERR_NOMEM` | `-3` | Нехоплює оперативної пам'яті для виділення нових структур або задач. |
| `ENUM_ERR_TASK_LIMIT` | `-4` | Досягнуто максимальної допустимої кількості одночасних задач (`max_tasks`). |
| `ENUM_ERR_MEMORY_EXCEEDED` | `-5` | Сумарне споживання пам'яті перевищило заданий ліміт `memory_limit_bytes`. |
| `ENUM_ERR_DUPLICATE_TASK` | `-6` | Спроба зареєструвати задачу з уже наявним ідентифікатором. |
| `ENUM_ERR_INVALID_HANDLE` | `-7` | Передано недійсний або зруйнований дескриптор двигуна. |

#### Правила обробки помилок в API:
1. **Збереження стану при помилці:** Якщо функція повертає код помилки (наприклад, `ENUM_ERR_NOMEM`), внутрішній стан контексту двигуна залишається неушкодженим і нерухомим. Усі раніше виявлені елементи RE-множини зберігаються.
2. **Негайне повернення:** При виявленні некоректного аргументу або нульового вказівника функція негайно припиняє виконання, не змінюючи вихідні параметри.

### 2.2 Структура конфігурації (`DovetailConfig`)

Задає налаштування ресурсомісткості та поведінки двигуна при створенні контексту.

:::tabs
```c
typedef enum {
    DEDUP_HASHSET,   // Дедуплікація через хеш-таблицю O(1)
    DEDUP_BLOOM,     // Ймовірнісна дедуплікація через фільтр Блума
    DEDUP_ARRAY      // Лінійний пошук O(N) у масиві (для малих систем)
} DedupPolicy;

typedef struct DovetailConfig {
    size_t initial_task_capacity; // Початкова ємність масиву задач (за замовчуванням 64)
    size_t initial_result_capacity; // Початкова ємність результатів (за замовчуванням 256)
    size_t memory_limit_bytes;   // Жорсткий ліміт пам'яті в байтах (0 = без обмежень)
    uint64_t max_diagonals;       // Гранична кількість діагоналей (0 = нескінченно)
    DedupPolicy dedup_policy;     // Політика перевірки унікальності
    bool enable_profiling;        // Прапорець збору метрик часу та промахів кешу
} DovetailConfig;
```
```cpp
enum class DedupPolicy : uint8_t {
    HashSet, // Дедуплікація через std::unordered_set O(1)
    Bloom,   // Ймовірнісна дедуплікація через фільтр Блума
    Array    // Лінійний пошук O(N) у масиві (для малих систем)
};

struct DovetailConfig {
    std::size_t initial_task_capacity{64};
    std::size_t initial_result_capacity{256};
    std::size_t memory_limit_bytes{0}; // 0 = без обмежень
    std::uint64_t max_diagonals{0};      // 0 = нескінченно
    DedupPolicy dedup_policy{DedupPolicy::HashSet};
    bool enable_profiling{false};
};
```
:::

#### Деталізація полів та семантика конфігурації:
- `initial_task_capacity`: Визначає початковий розмір послідовної ділянки пам'яті для масиву задач. Рекомендується задавати значення, кратне 64, для кращого вирівнювання кеш-ліній. При досягненні межі масив динамічно розширюється за допомогою `realloc` із коефіцієнтом `1.5`.
- `initial_result_capacity`: Початковий розмір масиву унікальних елементів. При розширенні ємність подвоюється (`×2`).
- `memory_limit_bytes`: Жорстке обмеження на обсяг пам'яті. Якщо під час реєстрації нових задач або перебудови хеш-таблиці сумарна виділена пам'ять перевищує це значення, виклик `enumerator_step_diagonal()` перериває обхід і повертає код `ENUM_ERR_MEMORY_EXCEEDED`. Це захищає систему від падіння за `OOM (Out Of Memory)`.
- `dedup_policy`: Визначає підсистему відсікання дублікатів. 
  - Режим `DEDUP_HASHSET` використовує хеш-таблицю з відкритою адресацією і забезпечує середній час перевірки `O(1)`.
  - Режим `DEDUP_BLOOM` використовує компактний бітовий масив фільтра Блума. Це заощаджує до 90% оперативної пам'яті при роботі з мільйонами значень, але допускає незначну ймовірність (`< 0.1%`) пропуску нових елементів через хибнопозитивні спрацювання.
  - Режим `DEDUP_ARRAY` застосовує простий лінійний перебір масиву. Він не вимагає додаткових хеш-таблиць і підходить для мікроконтролерів із обмеженою RAM, де кількість елементів вимірюється десятками.
- `enable_profiling`: При включенні прапорця двигун заміряє точний час виконання кожної діагоналі за допомогою високоточних системних таймерів (`clock_gettime`) і фіксує кількість активних та завершених задач.

### 2.3 Структура метрик профілювання (`StepMetrics`)

Повертає детальні дані про споживання ресурсів та прогрес обходу після виконання одного або кількох діагональних кроків.

:::tabs
```c
typedef struct StepMetrics {
    uint64_t current_diagonal;    // Номер останньої виконаної діагоналі
    uint64_t total_steps_executed; // Загальна кількість виконаних інструкцій/кроків
    size_t active_tasks_count;   // Кількість задач у стані RUNNING
    size_t halted_tasks_count;   // Кількість задач, що досягли HALTED
    size_t unique_results_found; // Кількість знайдених унікальних елементів RE-множини
    size_t current_memory_bytes; // Поточний обсяг виділеної оперативної пам'яті
    uint64_t execution_time_ns;   // Час виконання в наносекундах
} StepMetrics;
```
```cpp
struct StepMetrics {
    std::uint64_t current_diagonal{0};
    std::uint64_t total_steps_executed{0};
    std::size_t active_tasks_count{0};
    std::size_t halted_tasks_count{0};
    std::size_t unique_results_found{0};
    std::size_t current_memory_bytes{0};
    std::uint64_t execution_time_ns{0};
};
```
:::

#### Використання метрик для моніторингу:
Поле `current_diagonal` показує прогрес просування у сітці обходу. Різниця `active_tasks_count` та `halted_tasks_count` дозволяє оцінити коефіцієнт корисного використання процесорного часу: якщо відсоток активних задач прямує до нуля, обчислення майже завершено. Метрика `current_memory_bytes` використовується для динамічного відстеження витоків пам'яті у користувацьких автоматах.

## 3. Сигнатури функцій керування життєвим циклом

### 3.1 Створення та руйнування контексту

#### `enumerator_create`
Створює новий контекст перебирача відповідно до переданої конфігурації.

:::tabs
```c
EnumeratorStatus enumerator_create(
    const DovetailConfig *config,
    EnumeratorHandle **out_handle
);
```
```cpp
// У C++ створюється RAII-об'єкт класу DovetailEngine
DovetailEngine engine(config);
```
:::
- **Параметри:**
  - `config`: Вказівник на заповнену структуру конфігурації. Якщо передано `NULL`, двигун автоматично застосовує конфігурацію за замовчуванням (`DEDUP_HASHSET`, ємність 64, без обмеження пам'яті).
  - `out_handle`: Вихідний вказівник, куди записується адреса створеного дескриптора `EnumeratorHandle`.
- **Семантика виділення пам'яті:** Функція виділяє пам'ять під структуру дескриптора, масив задач та внутрішню хеш-таблицю. Якщо виділення пам'яті провалилося, адреса `*out_handle` встановлюється в `NULL`, і повертається код `ENUM_ERR_NOMEM`.
- **Коди повернення:** `ENUM_OK`, `ENUM_ERR_NULL_POINTER`, `ENUM_ERR_INVALID_CONFIG`, `ENUM_ERR_NOMEM`.

#### `enumerator_destroy`
Звільняє всі ресурси, пов'язані з контекстом двигуна, включаючи масиви задач, хеш-таблиці дедуплікації та збережені результати.

:::tabs
```c
EnumeratorStatus enumerator_destroy(
    EnumeratorHandle *handle
);
```
```cpp
// У C++ деструктор ~DovetailEngine() викликається автоматично
```
:::
- **Параметри:** `handle` — дескриптор двигуна для руйнування. Якщо передано `NULL`, функція повертає `ENUM_ERR_NULL_POINTER`.
- **Гарантії очищення:** Звільняються всі масиви, виділені двигуном. Об'єкти `user_context`, передані користувачем при реєстрації задач, двигуном **не видаляються** (управління їхнім життєвим циклом покладається на користувача).
- **Коди повернення:** `ENUM_OK`, `ENUM_ERR_INVALID_HANDLE`, `ENUM_ERR_NULL_POINTER`.

### 3.2 Реєстрація та керування задачами

#### Сигнатура покрокової функції завдання (`TaskStepFunc`)
:::tabs
```c
typedef TaskStatus (*TaskStepFunc)(
    uint32_t task_id,
    void *user_context,
    int32_t *out_result_val
);
```
```cpp
using TaskStepFunc = std::function<StepResult(std::uint32_t task_id, void* user_context, int32_t* out_result_val)>;
```
:::
Функція `TaskStepFunc` викликається двигуном при виконанні кожного кроку симуляції. Вона приймає унікальний `task_id`, вказівник на стан користувача `user_context` та вихідний буфер для результату. Якщо функція повертає `TASK_HALTED`, значення за адресою `out_result_val` зчитується й передається до модуля дедуплікації.

#### `enumerator_register_task`
Додає нову обчислювальну задачу до списку перебору.

:::tabs
```c
EnumeratorStatus enumerator_register_task(
    EnumeratorHandle *handle,
    TaskStepFunc step_fn,
    void *user_context,
    uint32_t *out_task_id
);
```
```cpp
engine.register_task(step_fn, user_context);
```
:::
- **Параметри:**
  - `handle`: Дескриптор контексту двигуна.
  - `step_fn`: Вказівник на покрокову функцію автомата. Не може бути `NULL`.
  - `user_context`: Довільний вказівник на користувацькі дані (стан автомата, стрічка тощо).
  - `out_task_id`: Вихідний параметр, куди записується призначений ідентифікатор завдання (починаючи з 0 підряд).
- **Коди повернення:** `ENUM_OK`, `ENUM_ERR_NULL_POINTER`, `ENUM_ERR_NOMEM`, `ENUM_ERR_TASK_LIMIT`.

### 3.3 Виконання перебору та видобуток результатів

#### `enumerator_step_diagonal`
Виконує обхід однієї наступної діагоналі `s = s + 1`.

:::tabs
```c
EnumeratorStatus enumerator_step_diagonal(
    EnumeratorHandle *handle,
    StepMetrics *out_metrics
);
```
```cpp
engine.step_diagonal();
```
:::
- **Параметри:**
  - `handle`: Дескриптор контексту двигуна.
  - `out_metrics`: Необов'язковий вихідний вказівник для збору метрик після кроку (може бути `NULL`).
- **Покрокова семантика:**
  1. Двигун збільшує лічильник діагоналей `s ⟵ s + 1`.
  2. Перебираються всі завдання з номерами `i = 0, 1, ..., s-1`, які ще перебувають у стані `TASK_RUNNING`.
  3. Для кожного такого завдання викликається покрокова функція `step_fn(i, ctx, &val)`.
  4. Якщо функція повернула `TASK_HALTED`, значення `val` передається до дедуплікатора. Якщо воно нове, воно додається до масиву результатів і викликається колбек `OnElementFoundCb`.
- **Коди повернення:** `ENUM_OK`, `ENUM_ERR_INVALID_HANDLE`, `ENUM_ERR_MEMORY_EXCEEDED`.

#### `enumerator_run_until`
Запускає ітеративний цикл перебору до виконання заданої умови зупинки або досягнення ліміту діагоналей.

:::tabs
```c
typedef bool (*StopPredicateFunc)(
    const StepMetrics *metrics,
    void *user_data
);

EnumeratorStatus enumerator_run_until(
    EnumeratorHandle *handle,
    StopPredicateFunc stop_pred,
    void *user_data
);
```
```cpp
engine.run_until([](const StepMetrics& m) {
    return m.unique_results_found >= 100;
});
```
:::
- **Параметри:**
  - `stop_pred`: Функція-предикат, яка викликається після кожної діагоналі. Якщо вона повертає `true`, цикл перебору переривається.
  - `user_data`: Користувацький контекст для предиката.
- **Коди повернення:** `ENUM_OK`, `ENUM_ERR_INVALID_HANDLE`, `ENUM_ERR_MEMORY_EXCEEDED`.

#### `enumerator_get_results`
Повертає вказівник на послідовний масив усіх виявлених унікальних елементів RE-множини.

:::tabs
```c
EnumeratorStatus enumerator_get_results(
    const EnumeratorHandle *handle,
    const int32_t **out_results_array,
    size_t *out_count
);
```
```cpp
std::span<const int32_t> results = engine.results();
```
:::
- **Параметри:**
  - `out_results_array`: Вихідний вказівник на масив значень. Буфер належить двигуну й залишається дійсним до виклику `enumerator_destroy()`.
  - `out_count`: Вихідний параметр для запису кількості знайдених елементів.
- **Коди повернення:** `ENUM_OK`, `ENUM_ERR_NULL_POINTER`, `ENUM_ERR_INVALID_HANDLE`.

## 4. Контракт колбеків (Callback Events)

Двигун дозволяє підключати спостерігачі (англ. *event listeners*) для обробки подій у реальному часі без необхідності періодичного опитування (polling).

:::tabs
```c
// Подія виявлення нового унікального елемента RE-множини
typedef void (*OnElementFoundCb)(
    uint32_t task_id,
    int32_t element_value,
    uint64_t step_found,
    void *user_data
);

// Реєстрація обробника події виявлення елемента
EnumeratorStatus enumerator_set_element_callback(
    EnumeratorHandle *handle,
    OnElementFoundCb callback,
    void *user_data
);
```
```cpp
engine.set_element_callback([](uint32_t task_id, int32_t val, uint64_t step) {
    std::cout << "Знайдено: " << val << " на кроці " << step << "\n";
});
```
:::

### Гарантії та обмеження виконання колбеків:
1. **Одноразовість повідомлення:** Колбек `OnElementFoundCb` викликається **точно один раз** для кожного нового унікального значення `y ∈ RE`. Повторні виявлення того самого значення іншими задачами відсікаються дедуплікатором і не генерують викликів.
2. **Синхронність та реінтрабельність:** Виклик колбека здійснюється безпосередньо всередині виконання `enumerator_step_diagonal()` у тому ж самому потоці. Усередині колбека **заборонено** викликати функції `enumerator_destroy()` або `enumerator_step_diagonal()` над тим самим дескриптором, оскільки це призводить до блокування або невизначеної поведінки (undefined behavior).

## 5. Обгортка для C++20 (`cpp::DovetailEngine`)

Для мови C++20 надається header-only обгортка, яка приховує роботу з сирими вказівниками й реалізує безпечний RAII-інтерфейс:

```cpp
namespace cpp {

class DovetailEngine {
private:
    EnumeratorHandle* handle_{nullptr};

public:
    explicit DovetailEngine(const DovetailConfig& config = {}) {
        if (enumerator_create(&config, &handle_) != ENUM_OK) {
            throw std::bad_alloc();
        }
    }

    ~DovetailEngine() {
        if (handle_) {
            enumerator_destroy(handle_);
        }
    }

    // Заборона копіювання (RAII семантика)
    DovetailEngine(const DovetailEngine&) = delete;
    DovetailEngine& operator=(const DovetailEngine&) = delete;

    // Дозвіл переміщення
    DovetailEngine(DovetailEngine&& other) noexcept : handle_(other.handle_) {
        other.handle_ = nullptr;
    }

    void register_task(TaskStepFunc step_fn, void* ctx) {
        uint32_t id = 0;
        auto status = enumerator_register_task(handle_, step_fn, ctx, &id);
        if (status != ENUM_OK) {
            throw std::runtime_error("Task registration failed");
        }
    }

    void step_diagonal() {
        if (enumerator_step_diagonal(handle_, nullptr) != ENUM_OK) {
            throw std::runtime_error("Diagonal step execution failed");
        }
    }

    [[nodiscard]] std::span<const int32_t> results() const {
        const int32_t* arr = nullptr;
        size_t count = 0;
        enumerator_get_results(handle_, &arr, &count);
        return {arr, count};
    }
};

} // namespace cpp
```

## 6. Багатопотокова безпека та синхронізація

Низькорівневий дескриптор `EnumeratorHandle` за замовчуванням є **однопотоковим** (не thread-safe) задля забезпечення максимальної швидкодії без накладних витрат на м'ютекси. 

### Правила багатопотокового використання:
1. **Паралельне використання:** Якщо декілька робочих потоків (worker threads) одночасно викликають `enumerator_step_diagonal()` над одним дескриптором, зовнішній код зобов'язаний обгортати виклики в м'ютекс (`std::mutex` у C++ або `pthread_mutex_t` у C).
2. **Паралельна реєстрація задач:** Виклик `enumerator_register_task()` під час активного обходу `enumerator_step_diagonal()` дозволяється лише за умови синхронізації через блокування.
3. **Модель локальних буферів (Thread-Local Buffers):** Для високонавантажених систем рекомендується створювати окремий контекст `EnumeratorHandle` для кожного процесорного ядра, а знайдені результати періодично об'єднувати у глобальну хеш-таблицю.

## 7. Серіалізація та відновлення стану (State Checkpointing)

У реальних обчислювально містких задачах перебір може тривати годинами або днями. Для забезпечення стійкості до збоїв (Fault Tolerance) двигун надає функціонал збереження й відновлення контрольних точок (контрольних зрізів станів) на диск.

:::tabs
```c
// Серіалізація поточного стану двигуна у файл
EnumeratorStatus enumerator_serialize_state(
    const EnumeratorHandle *handle,
    const char *file_path
);

// Відновлення стану двигуна з файлу контрольної точки
EnumeratorStatus enumerator_deserialize_state(
    const char *file_path,
    EnumeratorHandle **out_handle
);
```
```cpp
engine.serialize_state("checkpoint.bin");
auto restored_engine = DovetailEngine::deserialize_state("checkpoint.bin");
```
:::

### Гарантії та семантика контрольних точок:
1. **Збереження позиції обходу:** Файл контрольної точки кодує поточний номер діагоналі `s`, повний масив знайдених унікальних елементів `results`, стан хеш-таблиці дедуплікації та накопичені кроки кожної активної задачи `accumulated_steps`.
2. **Відновлення автоматів:** При відновленні стану користувацькі структури `user_context` відновлюються через зареєстрований серіалізатор стану. Якщо вказівник на покрокову функцію `step_fn` змінив свою адресу (наприклад, при перезапуску бінарного файлу на іншій адресі ASLR), двигун переприв'язує його за допомогою таблиці ідентифікаторів задач.
3. **Захист від пошкоджень:** Файл контрольної точки кодується з бітовою контрольною сумою CRC32 або SHA-256. Якщо файл пошкоджено, `enumerator_deserialize_state()` відхиляє завантаження з кодом `ENUM_ERR_INVALID_CONFIG`.

## 8. Обробка сигналів та аварійних переривань (Signal Handling)

При виконанні довільного або симульованого коду існує ризик виникнення апаратних винятків або системних сигналів (наприклад, `SIGSEGV` при недійсному зверненні до пам'яті всередині некоректної користувацької задачи, або `SIGXCPU` при перевищенні ліміту часу процесу).

### Системний контракт ізоляції помилок:
1. **Перехоплення винятків у C++:** Усередині методу `step_diagonal()` виклики `step()` обгортаються у блок `try { ... } catch (...)`. Якщо користувацька задача викидає C++ виняток, вона автоматично маркується як `TASK_FAILED`, вилучається з подальших діагоналей, а сам двигун продовжує обхід решти задач без аварійного завершення всієї програми.
2. **Ізоляція сигналів POSIX:** При роботі в Unix-подібних системах розробник може ввімкнути режим ізоляції задач у підпроцеси (fork-based isolation). У цьому режимі задача виконає свій крок у захищеному просторі пам'яті, і сигнал `SIGSEGV` призведе лише до завершення дочірнього процесу з записом помилки в `StepMetrics.halted_tasks_count`, зберігаючи цілісність основного двигуна перелічення.

## 9. Динамічне пріоритезування задач (Task Weighting)

Окрім класичного рівномірного діагонального обходу, двигун підтримує розширену специфікацію виваженого перебору (Weighted Dovetailing), де кожне завдання дістає власну ймовірнісну вагу `priority_weight` від 1 до 100.

:::tabs
```c
// Налаштування пріоритету конкретної задачи
EnumeratorStatus enumerator_set_task_priority(
    EnumeratorHandle *handle,
    uint32_t task_id,
    uint32_t priority_weight
);
```
```cpp
engine.set_task_priority(task_id, 100);
```
:::

### Семантика виваженого обходу:
Завдання з більшою вагою `priority_weight` отримують більшу кількість кроків `step()` на кожній діагоналі. Наприклад, задача з вагою `100` отримує в 10 разів більше інструкцій за один діагональний виток, ніж задача з вагою `10`. Це дозволяє інтегрувати евристичні оцінки (наприклад, ймовірність досягнення мети за методом Монте-Карло) в обчислювальний процес без утрати теоретичної гарантії завершеності перебору.

## 10. Детальний розбір сценаріїв конфігурації

Залежно від практичної задачі конфігурація `DovetailConfig` підбирається відповідно до пріоритетів швидкодії або збереження пам'яті:

| Сфера застосування | `dedup_policy` | `initial_task_capacity` | `memory_limit_bytes` | Рекомендовані налаштування |
| :--- | :--- | :--- | :--- | :--- |
| **Символьне виконання (KLEE)** | `DEDUP_HASHSET` | 1024 | 8 GB | Пріоритет швидкого перевіряння унікальності гілок. |
| **Фазинг (AFL++)** | `DEDUP_BLOOM` | 8192 | 512 MB | Економія пам'яті при мільйонах згенерованих мутацій. |
| **Доказувачі теорем (Z3/E)** | `DEDUP_HASHSET` | 512 | 16 GB | Великий ліміт пам'яті для збереження великих термів. |
| **Вбудовані системи (MCU/RTOS)**| `DEDUP_ARRAY` | 32 | 64 KB | Фіксована пам'ять без динамічного виділення в купі. |

### Пояснення сценаріїв:
- **Символьне виконання:** При генерації тестів KLEE створює тисячі програмних шляхів. Використання `DEDUP_HASHSET` гарантує, що жодне тестове покриття не буде перевірене двічі.
- **Фазинг бінарних файлів:** Фазер генерує мільйони вхідних пакунків. Використання фільтра Блума `DEDUP_BLOOM` дозволяє працювати годинами на обмеженій RAM (512 MB), не переповнюючи пам'яті таблицями крашів.
- **Вбудовані мікроконтролери:** При реалізації діагностичних перебирачів на STM32 або ESP32 виділення пам'яті в купі (heap) небажане. Режим `DEDUP_ARRAY` працює на статично виділеному буфері `64 KB`.

### 10.1 Стабільність API та семантичне версіонування
Публічний ABI-інтерфейс двигуна відповідає правилам семантичного версіонування (Semantic Versioning 2.0.0). Усі додавання нових полів до структури `DovetailConfig` здійснюються виключно в кінець структури зі збереженням зворотної сумісності за розміром (Binary Compatibility). Це дозволяє оновлювати динамічні бібліотеки двигуна (наприклад, `.so` у Linux або `.dll` у Windows) у працюючих верифікаційних комплексах без необхідності перекомпіляції клієнтських додатків.

### 10.2 Гарантії сумісності та тестування ABI
Для автоматичної перевірки збереження сумісності бінарного інтерфейсу (ABI) у CI-конвеєрах використовується інструмент `abi-compliance-checker`. Жодна публічна функція API не змінює свій порядок у таблиці символів динамічної бібліотеки.

Ця специфікація забезпечує повну сумісність між різними реалізаціями двигуна перелічення, даючи змогу інтегрувати його у складні аналітичні та верифікаційні комплекси.
