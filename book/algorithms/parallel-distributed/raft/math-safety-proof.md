# 🧮 Формальні інваріанти та індуктивне доведення безпеки Raft

Коректність алгоритму консенсусу спирається не на емпіричні спостереження, а на строгі математичні інваріанти. У цій вставці наведено формальні визначення п'яти фундаментальних властивостей безпеки Raft та строге індуктивне доведення ключової теореми — **повноти логу лідера (Leader Completeness)**.

## 1. П'ять фундаментальних інваріантів безпеки

Нехай `S` — множина всіх серверів кластера розміром `N = |S|`, а час дискретизовано термами `T ∈ ℕ`.

```
1. Election Safety (Безпека виборів):
   Для будь-якого терму T існує щонайбільше один лідер:
   |{s ∈ S : role(s, T) = Leader}| ≤ 1

2. Leader Append-Only (Лог лідера тільки дописується):
   Лідер ніколи не перезаписує і не обрізає свій власний лог;
   він лише додає нові записи в кінець:
   ∀ s, T : role(s, T) = Leader ⇒ log(s, t₁) ⊑ log(s, t₂) при t₁ ≤ t₂

3. Log Matching (Відповідність логів):
   Якщо два логи на різних серверах містять запис із однаковим індексом i
   та однаковим термом t, то:
   a) Ці записи містять однакову команду;
   b) Логи повністю ідентичні на всіх попередніх позиціях від 1 до i-1.

4. Leader Completeness (Повнота логу лідера):
   Якщо запис логу зафіксовано (committed) у термі T, то цей запис обов'язково
   буде присутній у логах лідерів для всіх вищих термів U > T:
   committed(entry, T) ∧ role(L, U) = Leader ∧ U > T ⇒ entry ∈ log(L)

5. State Machine Safety (Безпека скінченного автомата):
   Якщо сервер s застосував запис логу з індексом i до свого автомата,
   жоден інший сервер ніколи не застосує інший запис для індексу i:
   applied(s₁, i, cmd₁) ∧ applied(s₂, i, cmd₂) ⇒ cmd₁ = cmd₂
```

---

## 2. Доведення властивості 1: Безпека виборів (Election Safety)

**Твердження:** У будь-якому термі `T` обирається не більше одного лідера.

**Доведення:**
1. Нехай розмір кластера дорівнює `N`. За протоколом, для перемоги на виборах у термі `T` кандидат зобов'язаний зібрати кворум голосів більшості `Q ⊂ S`, де:
   ```
   |Q| ≥ ⌊N / 2⌋ + 1
   ```
2. Припустимо від супротивного, що в термі `T` обрано двох різних лідерів `L₁ ≠ L₂`.
3. Для обрання `L₁` потрібен кворум `Q₁`, а для `L₂` — кворум `Q₂`.
4. За принципом Діріхле (кворумний перетин):
   ```
   |Q₁ ∩ Q₂| = |Q₁| + |Q₂| - |Q₁ ∪ Q₂|
             ≥ (⌊N / 2⌋ + 1) + (⌊N / 2⌋ + 1) - N
             ≥ N + 2 - N = 2   [для парного N]
             ≥ N + 1 - N = 1   [для непарного N]
             ≥ 1               [завжди]
   ```
5. Отже, існує щонайменше один спільний сервер `v ∈ Q₁ ∩ Q₂`.
6. За правилом протоколу Raft, кожен сервер має право віддати **не більше одного голосу** в межах одного терму `T` (`votedFor` скидається лише при зміні терму).
7. Сервер `v` не міг проголосувати одночасно і за `L₁`, і за `L₂` у термі `T`.
8. Отримали суперечність. Отже, `|{Leader у термі T}| ≤ 1`. ∎

## 3. Доведення властивості 3: Відповідність логів (Log Matching)

**Твердження:** Якщо `log₁(k) = log₂(k)` за термом і індексом, то `log₁[1..k] = log₂[1..k]`.

**Доведення (математична індукція за індексом k):**

**База індукції (`k = 1`):**
- Якщо записи мають `index = 1` та однаковий терм `T`, вони створені лідером терму `T`.
- Оскільки лідер у термі `T` єдиний (Властивість 1), і лідер створює не більше одного запису на даній позиції, команди в цих записах ідентичні. Попередніх записів немає. База доведена.

**Індукційний перехід (`k → k + 1`):**
1. Припустимо, що твердження істинне для всіх індексів `≤ k`.
2. Розглянемо два сервери, які мають однаковий запис на позиції `k + 1` з термом `T`.
3. Запис на позиції `k + 1` міг додати лише лідер терму `T`.
4. Коли лідер терму `T` розсилає `AppendEntries`, він передає параметри `prevLogIndex = k` та `prevLogTerm = log_leader[k].term`.
5. Фоловер приймає запис `k + 1` **лише якщо** його локальний запис на позиції `prevLogIndex = k` має терм, ідентичний `prevLogTerm`.
6. Отже, обидва сервери мали однаковий запис на позиції `k`.
7. За індукційним припущенням, рівність записів на індексі `k` тягне за собою повну ідентичність логів на всьому відрізку `1..k`.
8. Разом із рівністю на позиції `k + 1` отримуємо повну ідентичність `log₁[1..k+1] = log₂[1..k+1]`. ∎

## 4. Головна теорема: Повнота логу лідера (Leader Completeness)

**Теорема:** Якщо запис `e` зафіксовано лідером у термі `T`, то `e` буде присутній у логах лідерів усіх наступних термів `U > T`.

**Доведення (індукція за номером терму U > T):**

**База індукції (`U = T + 1`):**
1. Нехай запис `e` було зафіксовано лідером `L_T` у термі `T` на індексі `k`.
2. За визначенням коміту, запис `e` успішно репліковано на кворум більшості `Q_commit ⊂ S`.
3. Нехай у термі `T + 1` обрано лідера `L_{T+1}`. Для обрання він зібрав кворум голосів `Q_vote ⊂ S`.
4. Оскільки `|Q_commit| + |Q_vote| > N`, кворуми обов'язково перетинаються:
   ```
   ∃ v ∈ (Q_commit ∩ Q_vote)
   ```
5. Сервер `v` містить запис `e` у своєму лозі (бо `v ∈ Q_commit`).
6. Сервер `v` віддав голос за `L_{T+1}` (бо `v ∈ Q_vote`).
7. За правилом виборів (Election Restriction), `v` віддає голос кандидату `L_{T+1}` лише за умови, що лог кандидата є *не менш свіжим*, ніж лог `v`:
   ```
   lastTerm(L_{T+1}) > lastTerm(v) ∨
   (lastTerm(L_{T+1}) = lastTerm(v) ∧ lastIndex(L_{T+1}) ≥ lastIndex(v))
   ```
8. Оскільки `v` бачив терм `T` (містить `e`), `lastTerm(v) ≥ T`.
9. Оскільки `L_{T+1}` балотується в термі `T + 1`, його `lastTerm(L_{T+1}) ≤ T` (записів із термом `T + 1` ще не існує під час виборів).
10. Отже, єдиний можливий випадок — `lastTerm(L_{T+1}) = lastTerm(v) = T`.
11. Тоді за правилом довжини логу:
    ```
    lastIndex(L_{T+1}) ≥ lastIndex(v) ≥ k
    ```
12. Оскільки останній запис кандидата має терм `T` і довжину `≥ k`, за властивістю Log Matching лог кандидата `L_{T+1}` містить усі записи логу `v` до індексу `k`, включно із записом `e`.
13. База для `U = T + 1` доведена.

**Індукційний перехід (`U > T + 1`):**
1. Припустимо, що твердження істинне для всіх термів від `T + 1` до `U - 1`: лідери всіх цих термів містять запис `e`.
2. Припустимо від супротивного, що лідер `L_U` терму `U` **не містить** запису `e` на позиції `k`.
3. Лідер `L_U` зібрав кворум виборів `Q_vote`.
4. Знову розглянемо сервер перетину `v ∈ (Q_commit ∩ Q_vote)`.
5. Сервер `v` містить `e` у своєму лозі з термом `T`.
6. Оскільки `v` проголосував за `L_U`, лог `L_U` був не менш свіжим за лог `v`:
   - Якщо останній запис `v` належав терму `T`, то аналогічно базі `L_U` повинен містити `e` (суперечність).
   - Якщо останній запис `v` належав деякому терму `T' ∈ (T, U)`, то сервер `v` отримав цей запис від законного лідера `L_{T'}`.
7. За індукційним припущенням, лідер `L_{T'}` містив запис `e` у своєму лозі на позиції `k`.
8. За властивістю Log Matching, оскільки `v` містить запис терму `T'`, він також обов'язково містить усі попередні записи лідера `L_{T'}`, включно з `e`.
9. Оскільки `lastTerm(L_U) ≥ lastTerm(v) = T'`, лог `L_U` містить усі записи до `lastIndex(v)` або належить ще вищому терму, який також успадкував `e`.
10. В усіх випадках отримуємо, що `L_U` зобов'язаний містити запис `e`.
11. Суперечність доводить, що `e ∈ log(L_U)` для будь-якого `U > T`. ∎

## 5. Доведення безпеки скінченного автомата (State Machine Safety)

**Теорема:** Якщо будь-який сервер застосував запис логу `log[i]` до свого автомата, жоден інший сервер ніколи не застосує інший запис для індексу `i`.

**Доведення:**
1. Сервер застосовує запис `log[i]` до скінченного автомата лише тоді, коли цей запис зафіксовано (`i ≤ commitIndex`).
2. Фіксація означає, що запис репліковано на більшість вузлів у деякому термі `T`.
3. За теоремою Leader Completeness, лідери всіх наступних термів `U > T` міститимуть цей самий запис на позиції `i`.
4. За властивістю Leader Append-Only, лідери ніколи не перезаписують і не видаляють свої записи.
5. Отже, у будь-якому майбутньому термі всі лідери надсилатимуть фоловерам виключно цей самий запис для індексу `i`.
6. Відповідно, будь-який сервер, який досягне `commitIndex ≥ i`, матиме на позиції `i` ідентичний запис і застосує до автомата ту саму команду.
7. Розходження станів реплікованих автоматів є математично неможливим. ∎
