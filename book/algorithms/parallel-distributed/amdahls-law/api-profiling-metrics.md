# 📋 Довідник метрик паралельного масштабування та профілювання

Цей довідник містить формальні специфікації аналітичних метрик масштабованості, апаратні події підсистеми Performance Monitoring Unit (PMU) ядра Linux, інтерфейси керування топологією виконання та структуровані методи інженерного усунення патологій паралелізму.

---

## 1. Специфікація метрик масштабованості

Кількісна оцінка якості розпаралелювання спирається на систему взаємопов'язаних аналітичних показників. Кожна метрика висвітлює окремий аспект поведінки системи: від чистого часового виграшу до ступеня деградації апаратних ресурсів.

| Метрика | Формула | Область значень | Фізичний зміст та діагностичний критерій |
| :--- | :--- | :--- | :--- |
| **Прискорення (Speedup, `S(N)`)** | `T₁ / T(N)` | `[1, N]` (ідеально `N`) | Відношення часу виконання на одному ядрі до часу на `N` ядрах. Оцінює реальний виграш у швидкості. |
| **Ефективність (Efficiency, `E(N)`)** | `S(N) / N` | `[0.0, 1.0]` (або `0–100%`) | Частка обчислювальної потужності системи, задіяна для корисної роботи. `E(N) < 0.5` свідчить про неефективне нарощування ядер. |
| **Метрика Карпа — Флатта (`e`)** | `(1/S(N) - 1/N) / (1 - 1/N)` | `[0.0, 1.0]` | Експериментально виміряна послідовна частка. Якщо `e = const` — вузьке місце в алгоритмі; якщо `e` росте з `N` — затримки комунікації/блокувань. |
| **Масштабоване прискорення Густафсона (`S_G(N)`)** | `N - s'·(N - 1)` | `[1, N]` | Прискорення в умовах слабкого масштабування (обсяг задачі збільшується пропорційно до `N`). |
| **Універсальна масштабованість Ґюнтера (`C(N)`)** | `N / (1 + σ(N-1) + κN(N-1))` | `[0, N]` | Модель реальної пропускної здатності з урахуванням черг блокувань (`σ`) та взаємодії когерентності кешів (`κ`). |
| **Пікова ємність USL (`N*`)** | `√((1 - σ) / κ)` | `N ≥ 1` | Оптимальна кількість ядер/потоків, після якої починається ретроградне падіння продуктивності. |

Метрика прискорення `S(N)` показує лише фінальний результат виконання, але сама по собі не пояснює причин втрати продуктивності. Ефективність `E(N)` дозволяє оцінити економічну доцільність виділення додаткових серверних потужностей: коли `E(N)` опускається нижче 50%, вартість експлуатації нових ядер перевищує отриманий виграш у часі.

Метрика Карпа — Флатта `e` слугує головним математичним індикатором природи деградації. Якщо розраховане значення `e` залишається незмінним при переході від 2 до 16 чи 64 ядер, причина обмеження криється виключно в алгоритмічній структурі коду (нерозпаралелений цикл, послідовна агрегація). Якщо ж значення `e` монотонно зростає зі збільшенням кількості потоків, програма страждає від динамічних накладних витрат: конкуренції за м'ютекси, очікування на шині оперативної пам'яті або частих перемикань контексту.

## 2. Апаратні події Linux `perf` для діагностики

Для виявлення прихованих послідовних ділянок та апаратних затримок використовуються апаратні лічильники продуктивності процесора (Performance Monitoring Unit, PMU), доступні через системний виклик `perf_event_open`. Сучасні процесори містять спеціалізовані апаратні регістри MSR (Model-Specific Registers), які підраховують мікроархітектурні події безпосередньо в кремнії без сповільнення виконання програми.

Ядро Linux зчитує ці регістри через кільцевий буфер у спільній пам'яті (`mmap`) і генерує переривання при переповненні лічильника (механізм вибірки подій, англ. *sampling*).

| Назва події `perf` | Рівень аналізу | Пороговий орієнтир | Діагноз при відхиленні |
| :--- | :--- | :--- | :--- |
| **`cycles`** | Ядро CPU | — | Загальна кількість процесорних тактів, витрачених на виконання програми. |
| **`instructions`** | Ядро CPU | — | Кількість виконаних інструкцій. Співвідношення `instructions / cycles` (IPC) вказує на ефективність конвеєра (норма IPC `> 1.8`). |
| **`cache-misses`** | Кеш L3 / LLC | `> 5%` від `cache-references` | Масивний вихід за межі кешу останнього рівня; насичення шини оперативної пам'яті (Memory Bandwidth Wall). |
| **`LLC-load-misses`** | Кеш L3 / LLC | `> 10 000` на секунду | Потоки активно конкурують за доступ до оперативної пам'яті або читають дані з віддалених вузлів NUMA. |
| **`L1-dcache-load-misses`** | Кеш L1 Data | `> 15%` від звернень | Неоптимальний шаблон доступу до пам'яті (відсутність просторової чи часової локальності). |
| **`context-switches`** | Ядро ОС | `> 1000` на секунду на потік | Висока конкуренція за м'ютекси (Lock Contention); потоки переходять у стан сну через системні виклики `futex`. |
| **`cpu-migrations`** | Планувальник ОС | `> 50` на секунду | Планувальник перекидає потоки між різними фізичними ядрами, що призводить до повного скидання L1/L2 кешів. |
| **`page-faults`** | Віртуальна пам'ять | Високі сплески під час роботи | Динамічне виділення пам'яті в робочих потоках; конкуренція за блокування таблиць сторінок процесу (`mmap_lock`). |

Ключовим показником стану конвеєра є індекс `IPC` (`instructions per cycle`). Якщо під час виконання паралельного регіону `IPC` опускається нижче одиниці (`IPC < 1.0`), ядра більшість часу простоюють в очікуванні надходження даних з оперативної пам'яті або блокуються на лініях когерентності кешу.

Висока частота подій `context-switches` однозначно вказує на те, що замість виконання корисної роботи процесор витрачає ресурс на збереження регістрів, перемикання стеків і виклики диспетчера задач операційної системи.

## 3. Керування топологією та прив'язкою потоків (Affinity)

За замовчуванням планувальник задач операційної системи Linux намагається динамічно розподіляти навантаження між ядрами. Проте міграція потоку з одного ядра на інше призводить до повної втрати гарячих даних у локальних кешах L1 і L2. Щоб зафіксувати потік на конкретному фізичному ядрі та усунути накладні витрати міграції, застосовують афінність (Thread Affinity).

Фіксація потоку гарантує, що його стек, локальні змінні та кешовані структури залишаються в L1/L2 кеші того самого фізичного ядра. Це знижує латентність звернень до пам'яті й стабілізує результати бенчмаркінгу.

:::tabs
```c
#define _GNU_SOURCE
#include <pthread.h>
#include <sched.h>
#include <stdio.h>

/* Прив'язка потоку thread до логічного ядра core_id через POSIX API */
int pin_thread_to_core(pthread_t thread, int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);
    int res = pthread_setaffinity_np(thread, sizeof(cpu_set_t), &cpuset);
    if (res != 0) {
        perror("Помилка встановлення афінності потоку");
        return -1;
    }
    return 0;
}
```
```cpp
#include <thread>
#include <pthread.h>
#include <sched.h>
#include <system_error>
#include <iostream>

// Прив'язка потоку std::thread до конкретного логічного ядра core_id
void pin_thread_to_core(std::thread& th, int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);
    
    int rc = pthread_setaffinity_np(th.native_handle(), sizeof(cpu_set_t), &cpuset);
    if (rc != 0) {
        throw std::system_error(rc, std::generic_category(), "Не вдалося прив'язати потік до ядра");
    }
}
```
:::

### Конфігураційні змінні середовища OpenMP

Для програм, що використовують паралельні директиви OpenMP, керування топологією розміщення потоків здійснюється без зміни вихідного коду за допомогою змінних середовища. Середовище виконання OpenMP самостійно зчитує топологію процесора через інтерфейс `/sys/devices/system/cpu` і прив'язує нитки до ядер згідно із заданими правилами.

| Змінна середовища | Можливі значення | Поведінка середовища виконання |
| :--- | :--- | :--- |
| **`OMP_NUM_THREADS`** | `N` (наприклад `8`, `16`) | Задає фіксовану кількість робочих потоків у паралельних секціях `#pragma omp parallel`. |
| **`OMP_PROC_BIND`** | `true`, `false`, `close`, `spread`, `master` | Стратегія прив'язки. `close` саджає потоки на сусідні ядра (спільний L3-кеш); `spread` розподіляє по різних сокетах для максимізації пропускної здатності RAM. |
| **`OMP_PLACES`** | `threads`, `cores`, `sockets`, `{0,1,2,3}` | Визначає апаратні одиниці для розміщення. Значення `cores` розміщує кожен потік на окремому фізичному ядрі, уникаючи колізій на SMT. |
| **`OMP_SCHEDULE`** | `static`, `dynamic[,chunk]`, `guided` | Стратегія диспетчеризації ітерацій. `static` має нульові накладні витрати, але чутливий до перекосу навантаження; `dynamic` балансує потік задач через чергу. |

## 4. Матриця діагностики патологій паралельного масштабування

У таблиці зведено класичні архітектурні патерни, через які паралельні програми втрачають лінійне прискорення та впираються в апаратні обмеження.

| Патологія масштабування | Фізичний механізм деградації | Симптоми в метриках та `perf` | Інженерне рішення |
| :--- | :--- | :--- | :--- |
| **Алгоритмічний послідовний поріг (Amdahl Serial Bottleneck)** | Код містить ділянки однопотокової редукції або вводу-виводу. | Метрика Карпа — Флатта `e` стабільна (`e ≈ const`); `E(N)` монотонно спадає за кривою `1/(sN + 1-s)`. | Перехід на паралельні дерева редукції (`O(log N)` замість `O(N)`), асинхронне фонове завантаження даних (Double Buffering). |
| **Хибне розділення кеш-ліній (False Sharing)** | Різні ядра пишуть у сусідні байти однієї 64-байтової лінії кешу L1/L2. | Метрика `e` стрімко зростає вже на 2–4 ядрах; прискорення `S(N) < 1.0`; високі показники `L1-dcache-load-misses` та HITM у `perf c2c`. | Вирівнювання структур результатів потоків на межу 64 байти (`alignas(64)`), використання локальних змінних у стеку замість спільного масиву. |
| **Конкуренція за блокування (Lock Contention)** | Потоки очікують доступу до критичної секції під спільним м'ютексом. | `context-switches` зростає в тисячі разів; високий час `kernel time` (виклики `futex`); зростання параметра `σ` в моделі USL. | Дрібнозернисті блокування (Fine-grained locking), шардинг структур даних, lock-free структури на атоміках (`std::atomic`), патерн RCU. |
| **Насичення шини пам'яті (Memory Bandwidth Wall)** | Усі ядра одночасно вимагають потокового читання/запису з RAM. | `LLC-load-misses` сягає максимуму; прискорення виходить на плато при заповненні пропускної здатності каналів пам'яті (DDR4/DDR5). | Оптимізація локальності даних (Loop Tiling / Blocking), стиснення структур даних, перехід до кеш-обізнаних алгоритмів (Cache-Oblivious). |
| **Міжвузловий трафік NUMA (Cross-NUMA Traffic)** | Потоки на сокеті 1 звертаються до сторінок пам'яті, виділених на сокеті 0. | IPC падає на 30–50%; висока латентність доступу до пам'яті; асиметрія часу виконання окремих потоків. | Прив'язка пам'яті до локального NUMA-вузла (`numactl --membind` або виклик `mbind()`), реплікація даних тільки для читання між вузлами. |

Аналіз кожної патології починається з перевірки двох базових гіпотез: чи пов'язане падіння швидкості з алгоритмічною структурою обчислень (послідовна частина за Амдалом), чи воно викликане конфліктами апаратного рівня (кеш, пам'ять, шина).

При профілюванні протоколів когерентності (MESI/MOESI) особливу увагу звертають на стан лінії кешу Modified (M): якщо лінія модифікується одним ядром, усі інші ядра при читанні змушені запитувати оновлені дані через між'ядерну кільцеву шину (Ring Bus / Mesh), що призводить до сплеску затримок у сотні процесорних тактів.

## 5. Метод обчислення параметрів моделі USL

Щоб застосувати модель Ґюнтера USL для практичного прогнозування масштабування виробничої системи, параметри конкуренції `σ` та когерентності `κ` знаходять шляхом нелінійної регресії за методом найменших квадратів на основі виміряних точок `(N_i, X(N_i))`, де `X(N_i)` — виміряна пропускна здатність системи (запитів на секунду).

Рівняння приводять до лінійного вигляду відносно невідомих коефіцієнтів:

```
N / X(N) - 1 / X(1) = σ · (N - 1) / X(1) + κ · N · (N - 1) / X(1)
```

Ввівши змінні `Y = N/X(N) - 1/X(1)`, `x₁ = (N - 1)/X(1)` та `x₂ = N·(N - 1)/X(1)`, задачу зводять до класичної множинної лінійної регресії `Y = σ·x₁ + κ·x₂`. Отримані коефіцієнти дозволяють точно обчислити точку зламу системи `N*` ще до закупівлі додаткових фізичних серверів.

При практичному розрахунку регресії для виключення викидів вимірів рекомендується проводити щонайменше п'ять повторних прогонів на кожній конфігурації потоків `N` та брати медіанне значення часу виконання. Якщо коефіцієнт детермінації `R²` отриманої регресії перевищує `0.98`, модель вважається адекватною і може використовуватися для планування потужностей хмарних кластерів.

## 6. Типові сценарії команд профілювання

Для локалізації проблем паралелізму в середовищі Linux застосовують стандартизовані сценарії виклику системних утиліт:

### 1. Зняття апаратного профілю продуктивності

```bash
# Базовий збір лічильників прискорення та ефективності
perf stat -e task-clock,cycles,instructions,cache-misses,LLC-load-misses,context-switches,cpu-migrations ./app_parallel

# Детальний аналіз промахів кеш-пам'яті всіх рівнів
perf stat -e L1-dcache-loads,L1-dcache-load-misses,LLC-loads,LLC-load-misses ./app_parallel
```

### 2. Пошук гарячих точок коду (Profiling & Flamegraph)

Генерація полум'яних графіків (Flamegraphs) дозволяє наочно побачити частку часу, яку програма проводить усередині послідовних функцій або системних викликів очікування блокувань:

```bash
# Запис профілю стеків викликів із частотою 99 Гц
perf record -F 99 -g -- ./app_parallel

# Текстовий звіт про найбільш ресурсомісткі функції
perf report --stdio --no-children

# Експорт даних для візуалізації у Flamegraph
perf script | stackcollapse-perf.pl | flamegraph.pl > parallel_profile.svg
```

### 3. Діагностика конфліктів ліній кешу (Cache-to-Cache / False Sharing)

Утиліта `perf c2c` спеціально розроблена для виявлення випадків, коли кілька ядер конкурують за одну лінію кешу (подія HITM — Hit Modified Cache Line):

```bash
# Запис подій міжядерних звернень до модифікованих кеш-ліній
perf c2c record -F 60000 -- ./app_parallel

# Формування підсумкового звіту про рядки структури з false sharing
perf c2c report --stdio
```

Завдяки цим командам розробник отримує точні координати структур даних у вихідному коді, які спричиняють взаємне блокування процесорних ядер.
