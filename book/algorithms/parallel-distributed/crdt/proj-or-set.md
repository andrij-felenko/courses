# ⚙️ Станові CRDT у коді: лічильник і OR-Set

Тут ми зберемо повний, компільований C++-файл двох станових CRDT — і запустимо його, щоб **побачити** абстрактну гарантію на очах: дві репліки приймають конфліктні записи, зливаються в будь-якому порядку — і опиняються в **однаковому** стані. Не «мають зійтися за теоремою», а виводять на екран `identical: 1`.

Беремо два типи. Перший — **лічильник, що лише зростає** (G-Counter): найпростіше, на чому видно весь прийом. Другий — **множина зі спостереженим видаленням** (OR-Set): справжня школа, де наївний проєкт розбивається об паралельність, а правильний — ні. І перевіряємо на кожному рівно одне: злий будь-як, хоч двічі, хоч у зворотному порядку — стан один; а коли одна репліка видаляє елемент, а друга в ту саму мить його знову додає, **додавання перемагає**.

Чому C++, а не скриптова мова. Станові CRDT — це структури даних плюс чисті функції над ними: стан — це просто множини й мапи, а злиття — функція без побічних ефектів, що бере два стани й повертає третій. Тут немає мережі, потоків, вводу-виводу — лише алгебра над контейнерами, де кожен `std::set` **буквально є** тією множиною, що утворює напіврешітку. Систематична робота зі структурами даних без зайвого шару абстракцій — рідна стихія C++, і весь приклад влазить в один файл без жодної залежності.

## Розігрів: лічильник, що лише додає

Спокуса — тримати одне спільне число й на злитті брати більше з двох. Вона тихо втрачає записи: дві репліки, кожна незалежно додавши одиницю до 5, обидві матимуть 6, і `max(6, 6) = 6` — одна одиниця зникла. Причина проста: злиття не може відрізнити «ми обидва бачимо 6, бо це те саме 6» від «ми обидва дійшли до 6 різними шляхами».

Ліки — не змішувати внески різних реплік. Стан лічильника — це **мапа** «репліка → скільки нарахувала **саме вона**». Збільшити лічильник — збільшити **свою** комірку. Значення — сума всіх комірок. А злиття бере **поелементний максимум**: у кожній комірці лишає більше з двох. Тепер `max` порівнює лише два погляди на внесок **однієї** репліки — а він монотонно росте, тож більше з двох і є актуальне.

```cpp
#include <cstdint>
#include <string>
#include <map>
#include <set>
#include <iostream>

// Лічильник, що лише зростає (G-Counter).
struct GCounter {
    std::map<uint32_t, uint64_t> cell;   // id репліки -> скільки нарахувала САМЕ вона

    void inc(uint32_t self, uint64_t by = 1) { cell[self] += by; }   // росте лише СВОЯ комірка

    uint64_t value() const {
        uint64_t s = 0;
        for (const auto& [id, c] : cell) s += c;   // значення = сума всіх комірок
        return s;
    }

    void merge(const GCounter& other) {
        for (const auto& [id, c] : other.cell)
            if (c > cell[id]) cell[id] = c;         // злиття = поелементний максимум
    }
};
```

Максимум комутативний (`max(x,y) = max(y,x)`), асоціативний і ідемпотентний (`max(x,x) = x`) — тобто мапа під поелементним максимумом є напіврешітка, і лічильник збігається за будь-якого перемішування доставки. Складність тривіальна: при `R` репліках `inc` — O(log R), `value` і `merge` — O(R). Перевіримо збіжність:

```cpp
GCounter c1, c2;                // лічильники на репліці 1 і на репліці 2
c1.inc(1); c1.inc(1);           // репліка 1 нарахувала двічі  -> cell{1:2}
c2.inc(2);                      // репліка 2 нарахувала раз    -> cell{2:1}
c1.merge(c2); c2.merge(c1);     // обмінялися станами (порядок і кратність байдужі)
std::cout << "G-Counter = " << c1.value()
          << " (згода: " << (c1.value() == c2.value()) << ")\n";   // 3 (згода: 1)
```

Той самий прийом — «розділи внески по комірках, зливай максимумом» — далі підіймає значно складніший тип.

## Унікальний тег: свідок одного додавання

Множина ламає інтуїцію там, де лічильник її пестив. Спробуйте наївно: тримати одну множину елементів, злиття — об'єднання. Додавання зіллється чудово. Але видалення нема куди подіти: якщо на злитті брати об'єднання, видалений на одній репліці елемент **воскресне** з другої, яка його ще має; а якщо тримати окрему «цвинтарну» множину видалених елементів, то раз потрапивши в неї, елемент **не додати знову** — його надгробок навіки блокує повторне додавання. Обидва наївні ходи ламаються на тому, що вони оперують **елементом як таким**, а елемент не має особистості: два різні додавання того самого `x` для них — те саме `x`.

Розрив кола — дати кожному **додаванню** особистість. Кожен `add` народжує **унікальний тег**: пару «id репліки + її локальний лічильник». Пара глобально унікальна, бо простір тегів поділений між репліками за id — репліка 2 ніколи не викарбує тег репліки 1, а свій локальний лічильник лише росте, тож і в межах репліки тег не повториться. У літературі про CRDT такий тег звуть **крапкою** (dot).

```cpp
// Тег ("крапка"): глобально унікальний свідок ОДНОГО додавання.
struct Tag {
    uint32_t replica;   // хто викарбував
    uint64_t seq;       // локальний лічильник цієї репліки на момент карбування
    bool operator<(const Tag& o) const {                       // щоб клали в std::set
        return replica != o.replica ? replica < o.replica : seq < o.seq;
    }
};
```

Тепер «елемент присутній» означає не «його колись додали», а «серед його додавань є хоч одне, чий тег ще не видалено». Особистість додавання — це те, за що можна вхопитися при видаленні: прибирати не абстрактний елемент, а **конкретні бачені теги**.

## OR-Set: додавання перемагає

Стан OR-Set — це дві множини, що **лише ростуть**. Перша, `addTags`, — мапа «елемент → множина тегів, що його додавали». Друга, `tombstones`, — множина надгробків, тобто тегів, які якесь видалення вже прибрало. Живі теги елемента — це `додані \ видалені`: теги з `addTags[e]`, яких нема в `tombstones`. Елемент присутній, якщо живий тег є хоч один.

```cpp
// Множина зі спостереженим видаленням (OR-Set): додавання перемагає видалення.
struct ORSet {
    uint32_t self;                                  // id цієї репліки
    uint64_t clock = 0;                             // локальний лічильник для карбування тегів
    std::map<std::string, std::set<Tag>> addTags;   // елемент -> теги, що його додавали
    std::set<Tag> tombstones;                        // теги, які видалення вже прибрало

    explicit ORSet(uint32_t id) : self(id) {}

    void add(const std::string& e) {
        addTags[e].insert(Tag{ self, ++clock });    // кожен add карбує НОВИЙ, ніде не бачений тег
    }

    void remove(const std::string& e) {
        auto it = addTags.find(e);
        if (it == addTags.end()) return;
        for (const Tag& t : it->second)              // спостережене видалення:
            tombstones.insert(t);                    // надгробимо РІВНО ті теги e, що бачимо зараз
    }

    bool contains(const std::string& e) const {
        auto it = addTags.find(e);
        if (it == addTags.end()) return false;
        for (const Tag& t : it->second)
            if (!tombstones.count(t)) return true;   // живий тег (доданий, не надгроблений) => присутній
        return false;
    }

    void merge(const ORSet& o) {
        for (const auto& [e, tags] : o.addTags)
            addTags[e].insert(tags.begin(), tags.end());          // об'єднання множин тегів, поелементно
        tombstones.insert(o.tombstones.begin(), o.tombstones.end());  // об'єднання надгробків
    }
};
```

Уся хитрість — у двох рядках `remove`: воно надгробить **лише ті теги, які бачить у цю мить**. Ось звідки береться «додавання перемагає». Уявіть: елемент `x` живе на обох репліках із тегом `{1,1}`. Мережа рветься. Репліка A виконує `remove(x)` — надгробить бачений тег `{1,1}`. Репліка B у ту саму мить виконує `add(x)` — карбує **свіжий** тег `{2,1}`, якого видалення на A **не могло бачити**, бо його ще не існувало на A. Після злиття `addTags[x] = {{1,1}, {2,1}}`, `tombstones = {{1,1}}`: тег `{1,1}` мертвий, а `{2,1}` живий — тож `x` лишається. Повторне додавання після повного видалення теж працює само собою: це щоразу новий тег, якого старі надгробки не покривають.

Обидві множини — `addTags` і `tombstones` — тільки ростуть, а злиття їх **об'єднує**. Об'єднання множин ідемпотентне, комутативне й асоціативне — отже, кожна з них є напіврешітка, і весь OR-Set збігається за будь-якого перемішування, дублювання й перестановки доставки.

## Демонстрація: паралельні add/remove сходяться

Складемо це в програму й перевіримо саме те, заради чого все й затівалось: конфліктні паралельні правки, злиті **в обох порядках**, дають ідентичний стан. Додайте цей `main` до типів вище (разом це один файл) — і запустіть.

```cpp
int main() {
    ORSet A(1), B(2);        // дві репліки з різними id

    A.add("x");              // A карбує тег {1,1} для x
    B.merge(A);              // B дізнається про x через тег {1,1}; тепер обидві згодні

    // --- мережа рветься; A і B діють ОДНОЧАСНО ---
    A.remove("x");           // A надгробить бачений тег x: {1,1}
    B.add("x");              // B карбує СВІЖИЙ тег {2,1} для x

    // Зливаємо два розбіжні стани — пробуємо ОБИДВА порядки:
    ORSet ab = A; ab.merge(B);   // (видалив) а потім (додав)
    ORSet ba = B; ba.merge(A);   // (додав) а потім (видалив)

    std::cout << "A|B contains x: " << ab.contains("x") << "\n";   // 1 — додавання перемогло
    std::cout << "B|A contains x: " << ba.contains("x") << "\n";   // 1 — та сама відповідь
    std::cout << "identical: "
              << (ab.addTags == ba.addTags && ab.tombstones == ba.tombstones) << "\n";  // 1
}
```

Вивід:

```
A|B contains x: 1
B|A contains x: 1
identical: 1
```

Розберемо, чому так. Ось стани перед злиттям і після нього в кожному порядку:

```
перед злиттям:
  A: addTags{ x:{ {1,1} } }          tombstones{ {1,1} }        (видалила бачений тег)
  B: addTags{ x:{ {1,1},{2,1} } }    tombstones{ }              (додала свіжий тег)

A ⊔ B:  addTags{ x:{ {1,1},{2,1} } }  tombstones{ {1,1} }
B ⊔ A:  addTags{ x:{ {1,1},{2,1} } }  tombstones{ {1,1} }        ← той самий стан
        живі теги x = { {1,1},{2,1} } \ { {1,1} } = { {2,1} } ≠ ∅  → x присутній
```

Два порядки дали побайтово однаковий стан, бо `merge` — це об'єднання множин, а об'єднання **комутативне**: `A ∪ B = B ∪ A`. Додавання перемогло не тому, що ми його якось привілеювали, а тому, що його тег `{2,1}` фізично відсутній у `tombstones` — видалення на A прибрало лише те, що бачило, а `{2,1}` тоді ще не народився. Конфлікт не розв'язано постфактум — його **сконструйовано неможливим**.

## Складність і пастки

Хай `N` — число елементів, `Tₑ` — скільки тегів записано для елемента `e` (включно з надгробленими, поки їх не прибрано), `T = ΣTₑ` — усього тегів, `K` — число надгробків. Для контейнерів на збалансованих деревах (`std::map`/`std::set`):

```
add(e)       O(log N + log Tₑ)        знайти кошик елемента + вставити тег
contains(e)  O(log N + Tₑ·log K)      перебрати теги e, кожен звірити з надгробками
remove(e)    O(log N + Tₑ·log K)      надгробити всі бачені теги e
merge(o)     O(T′·log T + K′·log K)    доводиться пройти ВЕСЬ чужий стан (T′,K′ — його розміри)
пам'ять      O(T + K)                 росте на КОЖНОМУ add і КОЖНОМУ remove
```

Замінивши дерева на геш-таблиці (`unordered_map`/`unordered_set`), логарифмічні множники стають амортизованим O(1): `contains`/`remove` — O(Tₑ), `merge` — O(T′+K′). Я взяв упорядковані контейнери навмисне: вони дають детермінований порядок обходу, зручний для друку й порівняння станів у демо.

Головна пастка ховається в рядку «пам'ять — O(T + K)»: структура **тільки росте**. Кожне видалення не звільняє тег, а **додає** надгробок; сам тег теж лишається в `addTags`. Множина, яку мільйон разів додавали й видаляли, тримає мільйон мертвих тегів, `contains` дедалі повільніший, а `merge` тягне весь цей баласт мережею. Це не деталь реалізації, а плата за те, що злиття вміє лише **об'єднувати** — воно принципово не може нічого викинути самотужки, бо «викинути» означало б рух униз напіврешіткою, а туди їй ходу нема.

> 🔧 **Навіщо це.** Складання сміття (garbage collection) надгробків — не бонус, а умова придатності OR-Set для довгоживучих множин. Без нього кошик, який щодня наповнюють і спорожняють, за рік стане мегабайтами мертвих тегів під одним видимим елементом.

Прибрати надгробок **насправді небезпечно**. Викинути тег `t` з обох множин можна лише тоді, коли **кожна** репліка вже точно бачила і його додавання, і його видалення. Інакше — воскресіння. Уявіть: репліка C так і не отримала видалення `x`, тож у неї досі `addTags[x] ⊇ {{1,1}}`. Якщо A, «прибираючи сміття», викине `{1,1}` і з `addTags`, і з `tombstones`, то наступне `A.merge(C)` знову внесе `{1,1}` в `addTags` — а надгробка на нього вже нема, і мертвий `x` оживе. Тому прибирати можна лише **причинно стабільні** теги: ті, що їх спостерігали всі. А щоб знати, хто що спостерігав, потрібні [векторні годинники](book:algorithms/vector-clocks) — по лічильнику на репліку, що фіксують, які оновлення кожна вже точно бачила; коли тег стабільний і надгроблений усюди, його безпечно викинути з обох множин. Це легша монета, ніж консенсус (лічильники їдуть попутно з плітками, нікого не блокуючи), але це все ж **дрібка тієї самої координації**, від якої CRDT тікав, — безкоштовного прибирання не буває.

Ще дві пастки, менші, але кусючі:

- **Не переви́користати тег.** Уся правильність спирається на те, що тег унікальний. Якщо репліка перезапуститься й скине `clock` у нуль, вона знову викарбує `{self,1}` для іншого додавання — і надгробок на старий `{self,1}` мовчки вб'є новий. Локальний лічильник треба **зберігати між запусками** або відновлювати вищим за будь-який уже викарбуваний тег.
- **«Додавання перемагає» — це вибір, а не закон.** OR-Set add-wins бо `remove` чіпає лише бачені теги. Дзеркальний тип, де за паралельного конфлікту перемагає видалення (remove-wins), будують іншим карбуванням — під семантику, а не навпаки. Питання не «як правильно», а «що має статися, коли двоє одночасно чіпають те саме», — і відповідь закладають у конструкцію типу.
