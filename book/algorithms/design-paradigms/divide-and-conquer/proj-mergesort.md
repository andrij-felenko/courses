# ⚙️ Сортування злиттям: від трьох рухів до робочого коду

Три рухи поділу — розрубати масив навпіл, підкорити кожну половину тим самим методом, поєднати дві впорядковані половини злиттям — на папері вміщаються в п'ять рядків. Але між елегантним начерком і кодом, який не соромно покласти в бібліотеку, лежить прірва, і саме в ній ховаються всі уроки. Начерк, де `merge` ріже списки навпіл і зшиває їх новими списками, **правильний** — і водночас марнотратний: він виділяє свіжу пам'ять на кожному злитті, жене [рекурсію](topic:algorithms/recursion) аж до одинаків і перекопіює більше, ніж треба. Робоча версія коштує ті самі `n·log n` порівнянь, але обходиться **одним** буфером на весь сорт, зупиняє поділ на дрібних шматках і не плодить жодного зайвого списку. Зберімо її по-справжньому — крок за кроком, і на кожному видно, яку саме пастку затуляє чергове уточнення.

Одразу домовмося про мови. Пітон тут — для **ясності**: у ньому злиття читається майже як псевдокод, і на ньому найлегше побачити механіку. C++ — для **швидкодії**: сортування живе на гарячому шляху, буфери й покажчики важать, і саме там видно, чого варте кожне зайве копіювання. Тож кожен шматок коду подано в обох — перемикайте вкладки.

## Уся вага — на злитті

Поділ навпіл тривіальний: узяв середину — і маєш дві половини. Уся праця сорту сидить у **злитті** двох уже впорядкованих частин в одну впорядковану. Зроби злиття правильним і швидким — і решта прикладеться сама. А злиття — це рівно те місце, де живуть майже всі помилки на одиницю, бо тут бігають три покажчики нараз.

Наївне злиття зшиває **новий** список і повертає його. Робоче — пише результат у наперед заведений **буфер** через покажчики-індекси, а тоді переносить назад. Різниця не косметична: замість `log n` окремих виділень пам'яті на кожен виклик — один буфер на весь сорт. Ось воно, з індексами:

:::tabs
```python
def merge(a, buf, lo, mid, hi):
    """Зливає дві відсортовані частини a[lo:mid] і a[mid:hi] через buf,
       тоді переносить злите назад у a[lo:hi].
       Півінтервали: ліва [lo, mid), права [mid, hi) — межа mid належить ПРАВІЙ."""
    i, j, k = lo, mid, lo               # i — по лівій, j — по правій, k — по buf
    while i < mid and j < hi:
        if a[i] <= a[j]:                # ≤, а не < — на рівних беремо з ЛІВОЇ (стійкість)
            buf[k] = a[i]; i += 1
        else:
            buf[k] = a[j]; j += 1
        k += 1
    while i < mid:                      # долити лівий хвіст (правий уже вичерпано)
        buf[k] = a[i]; i += 1; k += 1
    while j < hi:                       # або правий хвіст (вичерпано лівий)
        buf[k] = a[j]; j += 1; k += 1
    a[lo:hi] = buf[lo:hi]              # перенести злите на місце
```
```cpp
#include <vector>
using std::vector;

// Зливає a[lo,mid) і a[mid,hi) через buf, переносить назад у a[lo,hi).
static void merge(vector<int>& a, vector<int>& buf, int lo, int mid, int hi) {
    int i = lo, j = mid, k = lo;        // i — по лівій, j — по правій, k — по buf
    while (i < mid && j < hi)
        buf[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];   // ≤ → з лівої на рівних
    while (i < mid) buf[k++] = a[i++];  // лівий хвіст
    while (j < hi)  buf[k++] = a[j++];  // правий хвіст
    for (int t = lo; t < hi; ++t) a[t] = buf[t];       // перенести назад
}
```
:::

Придивімося до трьох тонких місць, бо кожне — окрема пастка. Перше — **півінтервали**. Ліва частина це `[lo, mid)`, права `[mid, hi)`: межа `mid` належить правій і **не** входить у ліву. Тримайся цієї домовленості скрізь — і ніколи не спитаєш себе, чи не загубив/не подвоїв елемент на стику. Друге — **два хвости**. Коли один із покажчиків добіг до краю своєї частини, у другій ще щось лишилось, і це «щось» уже відсортоване — його треба просто **долити**. Забути долити хвіст — класична половина злиття, що мовчки губить елементи. Третє — та сама `≤`, до якої ми ще повернемось окремо: вона вирішує долю однакових ключів.

Простежмо один прохід руками. Зливаємо ліву `[2, 5, 8]` і праву `[1, 4, 9]`:

```
i→2 j→1   2 ≤ 1? ні  → беремо з правої: buf=[1]           i→2 j→4
i→2 j→4   2 ≤ 4? так → беремо з лівої:  buf=[1,2]         i→5 j→4
i→5 j→4   5 ≤ 4? ні  → беремо з правої: buf=[1,2,4]       i→5 j→9
i→5 j→9   5 ≤ 9? так → беремо з лівої:  buf=[1,2,4,5]     i→8 j→9
i→8 j→9   8 ≤ 9? так → беремо з лівої:  buf=[1,2,4,5,8]   ліва вичерпана
права ще має 9 → доливаємо хвіст:       buf=[1,2,4,5,8,9]
```

![Один крок злиття зблизька: два ряди-джерела — ліва частина a[lo:mid) і права a[mid:hi), кожна з покажчиком (i над лівою, j над правою) на поточну верхівку, спожиті клітини притемнені; знизу ряд-буфер buf із покажчиком k на наступну вільну клітину; підписи півінтервалів [lo,mid) та [mid,hi); нижче нагадування, що на рівних ключах беремо з лівої (умова ≤)](img/merge-indices.svg)
*Механіка одного злиття. Три покажчики: `i` по лівій частині, `j` по правій, `k` по буферу. Щокроку порівнюємо дві верхівки `a[i]` та `a[j]`, меншу переписуємо в `buf[k]` і зсуваємо відповідний покажчик. Коли одна частина вичерпалась, хвіст другої доливаємо без порівнянь. Межа `mid` належить правій частині — це і є та домовленість про півінтервали, що прибирає помилки на одиницю.*

Порівнянь тут рівно стільки, скільки елементів разом, — злиття **лінійне**, один прохід по обох частинах. Це той наріжний факт, з якого виросте вся вартість сорту.

## Рекурсія згори вниз: один буфер, поріг, швидкий шлях

Тепер обгорнімо злиття рекурсією — але одразу так, як пишуть насправді. Три уточнення проти наївного начерку. **Буфер виділяємо раз** — на початку, розміром з увесь масив, і передаємо крізь усі виклики; жодних свіжих списків усередині. **Поділ спиняємо не на одинаку, а на порозі** `CUTOFF`: дрібний шматок дешевше добити простим сортуванням вставками, ніж дробити далі. І **швидкий шлях**: якщо після сортування половин виявилось, що вони вже й так стоять у правильному порядку на стику (`a[mid-1] ≤ a[mid]`), злиття взагалі зайве.

:::tabs
```python
CUTOFF = 32                            # шматки ≤ 32 добиваємо вставками

def insertion_sort(a, lo, hi):
    for i in range(lo + 1, hi):
        key = a[i]
        j = i - 1
        while j >= lo and a[j] > key:  # > (не ≥) — рівні не переставляємо (стійкість)
            a[j + 1] = a[j]; j -= 1
        a[j + 1] = key

def _sort(a, buf, lo, hi):
    if hi - lo <= CUTOFF:              # дрібний шматок — простим сортуванням
        insertion_sort(a, lo, hi)
        return
    mid = lo + (hi - lo) // 2          # НЕ (lo+hi)//2 — про це нижче
    _sort(a, buf, lo, mid)             # підкорити ліву
    _sort(a, buf, mid, hi)             # підкорити праву
    if a[mid - 1] <= a[mid]:           # уже впорядковано на стику → злиття зайве
        return
    merge(a, buf, lo, mid, hi)         # поєднати

def merge_sort(a):
    buf = list(a)                      # буфер розміру n, виділений ОДИН раз
    _sort(a, buf, 0, len(a))
    return a
```
```cpp
#include <vector>
using std::vector;
static const int CUTOFF = 32;          // шматки ≤ 32 добиваємо вставками

static void insertion_sort(vector<int>& a, int lo, int hi) {
    for (int i = lo + 1; i < hi; ++i) {
        int key = a[i], j = i - 1;
        while (j >= lo && a[j] > key)  // > (не ≥) — стійкість
            a[j + 1] = a[j--];
        a[j + 1] = key;
    }
}

static void sort_rec(vector<int>& a, vector<int>& buf, int lo, int hi) {
    if (hi - lo <= CUTOFF) { insertion_sort(a, lo, hi); return; }
    int mid = lo + (hi - lo) / 2;      // НЕ (lo+hi)/2 — переповнення (про це нижче)
    sort_rec(a, buf, lo, mid);         // підкорити ліву
    sort_rec(a, buf, mid, hi);         // підкорити праву
    if (a[mid - 1] <= a[mid]) return;  // уже впорядковано → злиття зайве
    merge(a, buf, lo, mid, hi);        // поєднати
}

void merge_sort(vector<int>& a) {
    vector<int> buf(a.size());         // буфер розміру n, ОДИН раз
    sort_rec(a, buf, 0, (int)a.size());
}
```
:::

Три рухи видно просто в тілі: `mid` — розділити, два виклики `sort_rec` — підкорити, `merge` — поєднати. Порогова гілка не міняє асимптотики — вона зрізає **сталу**: на найдрібніших шматках рекурсія з її викликами й буферами дорожча за тісний цикл вставок, і поріг просто вимикає поділ там, де він уже не окупається. Глибина рекурсії тут — рівно [двійковий логарифм](topic:math/binary-logarithm) від `n`: щоразу ділимо навпіл, тож рівнів `log₂n` і не більше (для мільярда елементів — близько тридцяти). Це важлива обставина, до якої повернемось у пастках.

Швидкий шлях `a[mid-1] ≤ a[mid]` вартий окремого слова. На вже впорядкованому вході кожне таке порівняння істинне, отже **жодне** злиття не виконується — і весь сорт вироджується в один прохід порогових вставок, тобто в лінійний час. Це маленька, майже безкоштовна крихта тієї адаптивності, на якій цілком стоїть промисловий Timsort: реальні дані часто вже частково впорядковані, і не платити за це — чесний виграш.

## Знизу вгору: те саме без рекурсії

У рекурсії згори вниз є прихована ціна — стек викликів. Її можна прибрати повністю, перевернувши поділ **навиворіт**. Замість «ділити, доки не впадемо до одинаків, і зливати на зворотному шляху» — почати з одинаків одразу й зливати сусідні купки, подвоюючи їхню ширину: спершу зливаємо сусідів по одному в купки по двоє, тоді купки по двоє в купки по четверо, і так, доки одна купка не проковтне весь масив. Жодної рекурсії — два вкладені цикли: зовнішній подвоює ширину, внутрішній проходить масив зліва направо й зливає пари сусідніх купок цієї ширини.

:::tabs
```python
def merge_sort_bottomup(a):
    n = len(a)
    buf = list(a)                          # буфер розміру n, один раз
    width = 1
    while width < n:                       # ширина купок: 1, 2, 4, 8, …
        lo = 0
        while lo < n:
            mid = min(lo + width, n)       # кінець лівої купки
            hi  = min(lo + 2 * width, n)   # кінець правої купки
            if mid < hi:                   # права купка непорожня — є що зливати
                merge(a, buf, lo, mid, hi)
            lo += 2 * width
        width *= 2
    return a
```
```cpp
#include <algorithm>
#include <vector>
using std::vector;

void merge_sort_bottomup(vector<int>& a) {
    int n = (int)a.size();
    vector<int> buf(n);                              // один раз
    for (int width = 1; width < n; width *= 2)       // ширина купок: 1, 2, 4, …
        for (int lo = 0; lo < n; lo += 2 * width) {
            int mid = std::min(lo + width, n);       // кінець лівої купки
            int hi  = std::min(lo + 2 * width, n);   // кінець правої купки
            if (mid < hi)                            // права непорожня
                merge(a, buf, lo, mid, hi);
        }
}
```
:::

![Сортування знизу вгору на масиві [5,2,8,1,9,4,7,3]: чотири рядки згори вниз, ліворуч мітка ширини; ширина 1 — вісім одинаків; ширина 1→2 — чотири впорядковані пари [2 5][1 8][4 9][3 7]; ширина 2→4 — дві четвірки [1 2 5 8][3 4 7 9]; ширина 4→8 — один упорядкований масив; кожен рядок дужками позначає купки, що зливаються в наступному проході](/book/algorithms/design-paradigms/divide-and-conquer/img/bottomup.svg)
*Той самий поділ, перевернутий. Починаємо з одинаків (ширина 1 — уже впорядковані самі собою) і щопрохід зливаємо сусідні купки, подвоюючи ширину: 1 → 2 → 4 → 8. Проходів рівно `log₂n`, на кожному зливається в сумі `n` елементів — та сама вартість `n·log n`, але циклом, без стека рекурсії.*

Чому це не просто інший спосіб написати те саме. По-перше, **нема стека** — глибина викликів нульова, тож переповнення стека на велетенському вході неможливе в принципі. По-друге, доступ до пам'яті йде рівними проходами зліва направо, а це дружніше до [кешу](topic:programming/cache), ніж стрибки рекурсії вгору-вниз деревом. Саме тому зливне сортування у справжніх бібліотеках — по суті бото́м-ап: `std::stable_sort` у C++ зливає знизу вгору, а Timsort (стандартний сорт у Python і для об'єктів у Java) — це «природний» бото́м-ап, що бере вже наявні впорядковані відрізки замість купок фіксованої ширини.

### Пінг-понг: прибрати копіювання назад

У нашому `merge` останній рядок — перенесення злитого з буфера назад у масив. На кожному з `log₂n` рівнів це ще один повний прохід копіювання: зайвий трафік пам'яті, який нічого не сортує. Його можна прибрати геть трюком **пінг-понг**: хай злиття читає з одного масиву й пише в інший, а наступний прохід міняє джерело й приймач місцями. Тоді копіювати назад не треба — результат проходу вже лежить там, де його читатиме наступний.

```cpp
#include <algorithm>
#include <vector>
using std::vector;

// Злиття БЕЗ переносу назад: читає зі src, пише в dst.
static void merge_into(const vector<int>& src, vector<int>& dst,
                       int lo, int mid, int hi) {
    int i = lo, j = mid, k = lo;
    while (i < mid && j < hi)
        dst[k++] = (src[i] <= src[j]) ? src[i++] : src[j++];
    while (i < mid) dst[k++] = src[i++];      // хвіст (сюди ж і поодинока купка,
    while (j < hi)  dst[k++] = src[j++];      // коли правої нема, — просто переносимо)
}

void merge_sort_pingpong(vector<int>& a) {
    int n = (int)a.size();
    vector<int> buf(a);                       // старт: копія масиву
    vector<int>* src = &buf;                  // читаємо з buf
    vector<int>* dst = &a;                    // пишемо в a
    for (int width = 1; width < n; width *= 2) {
        for (int lo = 0; lo < n; lo += 2 * width) {
            int mid = std::min(lo + width, n);
            int hi  = std::min(lo + 2 * width, n);
            merge_into(*src, *dst, lo, mid, hi);   // навіть поодиноку купку переносимо
        }
        std::swap(src, dst);                  // ролі міняються — жодного copy-back
    }
    if (src != &a) a = *src;                   // якщо результат осів у буфері — один перенос
}
```

![Пінг-понг двома буферами: зверху прямокутник «масив a», знизу «буфер buf»; між ними стрілки проходів, що чергують напрям — прохід 1 (ширина 1) з buf у a, прохід 2 (ширина 2) з a в buf, прохід 3 (ширина 4) з buf у a; збоку підпис, що копіювання назад зникає, бо приймач попереднього проходу стає джерелом наступного; унизу нагадування про один фінальний перенос, якщо результат осів у буфері](img/pingpong.svg)
*Пінг-понг прибирає перенос назад. Кожен прохід зливає з одного масиву в інший; наступний прохід просто міняє їх ролями. За `log₂n` проходів даних не копіюють «додому» жодного разу — лишається щонайбільше один фінальний перенос, якщо після останнього проходу результат опинився в буфері, а не в самому масиві.*

Зверни увагу на єдину тонкість: коли купка на краю масиву поодинока (правої пари для неї нема), `merge_into` все одно мусить **перенести** її зі `src` у `dst` — інакше в приймачі на цьому місці лишиться старе сміття з минулого проходу. Наші два `while`-хвости роблять це самі: коли `mid ≥ hi`, перший хвіст просто скопіює `[lo, mid)`. Тому тут, на відміну від звичайного бото́м-ап, гілку `if (mid < hi)` **не** ставимо — переносити треба завжди.

## Що ми за це маємо: складність, пам'ять, стійкість

Тепер тверезо порахуймо, що дає ця машина й чим за неї платимо.

**Час — завжди `n·log n`, без винятків.** І в цьому головна чеснота злиття перед його швидшим на позір родичем — швидким сортуванням (quicksort). Вартість описує рекурентність `T(n) = 2·T(n/2) + n`: два підсорти по пів масиву плюс лінійне злиття. На кожному з `log₂n` рівнів дерева поділу зливається в сумі `n` елементів, разом `n·log n` — і так для **будь-якого** входу. Немає «поганих» даних, що заганяють злиття в квадрат: ані вже відсортований масив, ані відсортований навспак, ані зловмисно підібраний. Швидке сортування в середньому теж `n·log n`, але на невдалому виборі опори падає до `n²`; злиття цієї ями не має зовсім. Ось як рівно тримається відношення сусідніх часів при подвоєнні `n` (випадкові цілі, `merge_sort` вище, одна машина — важливі не секунди, а стовпчик відношень):

```
       n     час (с)   T(2n)/T(n)
  100000       0.061           —
  200000       0.131        2.15
  400000       0.281        2.15
  800000       0.601        2.14
 1600000       1.284        2.14
```

Відношення тримається трохи вище двійки — саме там, де й має бути `n·log n`: чиста лінія дала б рівно 2, а логарифмічний множник підіймає до ≈ 2.1. (Чому `log n` проступає в цьому вимірі так кволо й чому подвоєння взагалі так читає клас — окрема розмова про [асимптотику й метод подвоєння](topic:algorithms/asymptotic-complexity).)

**Пам'ять — `O(n)` понад вхід.** Це друга сторона монети: за гарантований `n·log n` без ям платимо буфером розміром з увесь масив. Швидке сортування працює **на місці**, обходячись лише `O(log n)` стека, — і в цьому його козир на тісній пам'яті. Злиття без буфера теж можливе, але дорого: справжнє злиття «на місці» або сповзає в `n²`, або вимагає хитрої блокової техніки, що псує сталу. Саме тому `std::stable_sort` у C++ **пристосовується до пам'яті**: якщо тимчасовий буфер удалося виділити — він робить `n·log n`; якщо ні — відступає на злиття на місці й гарантує вже `n·log²n`. Швидший поріг не безкоштовний — за нього платять пам'яттю.

**Стійкість — дарунок тієї єдиної `≤`.** Сортування **стійке** (stable), якщо однакові ключі лишаються в тому ж взаємному порядку, що й на вході. Злиття стійке — але тільки завдяки одній деталі: на рівних верхівках (`a[i] == a[j]`) ми беремо з **лівої** частини (умова `≤`, а не `<`). Ліва частина — це елементи, що стояли раніше у вихідному масиві; беручи їх першими, ми зберігаємо їхнє старшинство. Заміни `≤` на `<` — і однакові ключі почнуть мінятися місцями, стійкість зламано. Той самий інваріант тримає й `insertion_sort`: цикл зсуву йде, доки `a[j] > key` (строго), тож рівний елемент ніколи не перестрибне через свого двійника. Дрібниця в одному символі — а несе всю властивість.

> 🔧 **Навіщо це.** Стійкість — не академічна забаганка, вона робить можливим сортування за кількома ключами через простий прийом. Хочеш упорядкувати список людей за прізвищем, а всередині однакових прізвищ — за ім'ям? Відсортуй **спершу за ім'ям**, тоді **за прізвищем** — і якщо другий сорт стійкий, він не поруйнує вже наведений порядок за ім'ям усередині кожного прізвища. Так з простих однопрохідних сортувань складають складні багаторівневі, не пишучи жодного мудрого компаратора. Саме тому стандартні сорти для об'єктів свідомо стійкі: `sorted` у Python, `Arrays.sort` для об'єктів у Java (обидва — Timsort), `std::stable_sort` у C++. А `std::sort` стійкості не обіцяє — і тому для такого ланцюжка не годиться.

Порогова гілка теж окупається на реальному часі. На тому самому вході `n = 1 600 000` чиста рекурсія до одинаків (`CUTOFF = 1`) проти порога `CUTOFF = 32`:

```
CUTOFF =  1  (поділ до одинаків):     1.68 с
CUTOFF = 32  (дрібні — вставками):    1.28 с   ≈ на 24 % швидше
```

Асимптотика та сама — зрізали лише сталу, але на гарячому шляху чверть часу це чверть часу.

## Пастки, на яких ламаються

Каркас простий, і саме тому оманливий: кожна з цих пасток трапляється в живому коді знову й знову.

**Помилка на одиницю у злитті.** Три покажчики, дві межі, два хвости — простір для збоїв багатий. Найтиповіші: сплутати, кому належить `mid` (тримайся півінтервалів — `mid` завжди в правій частині), забути долити хвіст непорожньої частини (елементи тихо зникають), переписати не той діапазон при переносі. Ліки — не героїзм, а дисципліна: єдина домовленість про півінтервали `[lo, mid)` та `[mid, hi)` наскрізь по всьому коду, і жодного «а тут я на одиницю посуну».

Окремий, підступний різновид цієї ж пастки — **переповнення при обчисленні середини**. Здається природним написати `mid = (lo + hi) / 2`. І це працює роками — аж поки масив не переросте мільярд елементів: сума `lo + hi` вискакує за межу 32-бітного знакового цілого, стає від'ємною, і `mid` показує чортзна-куди. Правильно — `mid = lo + (hi - lo) / 2`: різниця `hi - lo` завжди вміщається, бо не більша за сам масив. Це не вигаданий страх: Джошуа Блох 2006 року показав, що ця вада десятиліттями сиділа в перевіреному [двійковому пошуку](topic:algorithms/binary-search) з «Programming Pearls» Джона Бентлі — і в тому самому вигляді в реалізації, яку він сам написав для стандартної бібліотеки Java (доказовий статус: задокументована, широковідома вада, стаття «Nearly All Binary Searches and Mergesorts are Broken»). У мовах з необмеженими цілими (Python) переповнення нема, але звичка писати `lo + (hi - lo) // 2` не завадить — код часто переносять на мову, де межа є.

**Поріг переходу на просте сортування.** Ми його вже поставили, але варто знати, звідки береться число. На дрібному шматку рекурсія програє: виклики, перевірки, буфер — усе це стала, яку простий `O(m²)` сорт вставок на маленькому `m` легко перебиває, бо в нього ця стала крихітна, а на майже впорядкованих або коротких даних він ще й дуже прудкий. Де саме проходить межа — питання емпіричне, і справжні бібліотеки вибрали її вимірами: інтросорт у libstdc++ (`std::sort`) добиває вставками шматки менші за **16**; Timsort бере мінімальну довжину відрізка (minrun) у діапазоні від **32** до 64 і короткі відрізки нарощує двійковою вставкою до цієї довжини. Тому наш `CUTOFF = 32` — не з голови, а з тієї ж вилки, що її намацали промислові реалізації. Замалий поріг (як `1`) лишає всю рекурсійну сталу на столі; завеликий — віддає забагато роботи квадратичному сорту.

**Глибина стека.** Рекурсія згори вниз їсть стек, і тут ховається питання: чи не переповнить вона його на великому вході? Для злиття — ні, і саме тому, що ми ділимо **навпіл**: глибина це `log₂n`, тобто близько 30 навіть для мільярда елементів, — стек такого й не помітить. Небезпека виникла б, якби поділ був **нерівним** (як у невдалого швидкого сортування, де одна частина майже порожня, а друга майже ціла): тоді глибина сповзає до `O(n)` і стек справді [переповнюється](topic:programming/stack-overflow). Захисний прийом на такий випадок — рекурсувати в **меншу** половину, а більшу доганяти циклом у тому ж кадрі (обмежує глибину до `log n` навіть при кривому поділі). Але злиття ділить рівно завжди, тож йому це не потрібне зовсім; а хто боїться стека принципово — бере бото́м-ап, де рекурсії нема.

**Копіювання проти роботи на місці.** Наївне злиття плодить нові списки — `O(n)` виділень пам'яті на рівень, тиск на збирач сміття, кепська стала. Один спільний буфер прибирає виділення, але лишає перенос назад на кожному рівні. Пінг-понг прибирає й перенос, лишаючи щонайбільше один фінальний. А повний відказ від буфера (`O(1)` понад вхід) коштує або гіршої сталої, або зростання до `n·log²n` — тим самим відступом, що його робить `std::stable_sort`, коли буфер виділити не вдалося. Це чесний компроміс без безкоштовного обіду: менше пам'яті — повільніша стала, і навпаки. Обирай усвідомлено, а не за звичкою різати списки навпіл.

## Той самий каркас, інший поділ: множення Карацуби

Щоб побачити, що поділ — це **форма**, а не один алгоритм, прикладімо ту саму трійку рухів до зовсім іншої задачі: перемножити два велетенські числа. Стовпчиком це коштує `n²` цифрових множень — кожна цифра одного числа на кожну цифру другого. Поділ валить цю вартість, і зроблено це геть інакше, ніж у сорті: інший **поділ** і, головне, значно хитріше **зліплювання**.

Розділяй тут — це розрізати кожне число навпіл за розрядами на старшу й молодшу частину. Якщо `x = xₐ·B + x_b` і `y = yₐ·B + y_b` (де `B` — степінь основи, зсув на пів числа), то

```
x·y = xₐ·yₐ · B²  +  (xₐ·y_b + x_b·yₐ) · B  +  x_b·y_b
```

Наївно тут **чотири** множення половинок. Уся кмітливість Карацуби — помітити, що середню суму `xₐ·y_b + x_b·yₐ` можна дістати **без** окремого множення: одне зайве множення `(xₐ+x_b)·(yₐ+y_b)` дає всі три доданки суми разом, і, віднявши від нього вже пораховані `xₐ·yₐ` та `x_b·y_b`, лишаємось саме з серединою. **Три** множення замість чотирьох — і решта дешеві додавання й зсуви:

```python
def karatsuba(x, y):
    # БАЗОВИЙ ВИПАДОК: дрібні числа множимо прямо
    if x < 10 or y < 10:
        return x * y
    # РОЗДІЛИТИ: ріжемо кожне число навпіл за розрядами
    m = min(len(str(x)), len(str(y))) // 2
    base = 10 ** m
    xa, xb = divmod(x, base)                 # старша й молодша половини x
    ya, yb = divmod(y, base)                 # старша й молодша половини y
    # ПІДКОРИТИ: три множення замість чотирьох (тим самим методом, рекурсивно)
    hi    = karatsuba(xa, ya)                # старша·старша
    lo    = karatsuba(xb, yb)                # молодша·молодша
    mid   = karatsuba(xa + xb, ya + yb)      # (сума)·(сума) — одне зайве множення
    cross = mid - hi - lo                    # = xa·yb + xb·ya, БЕЗ окремого множення
    # ПОЄДНАТИ: зсуви за розрядами й додавання
    return hi * base * base + cross * base + lo
```

Тут поділ показовий саме своєю несхожістю на сорт. **Обидві** половини потрібні й жодну не викидають (на відміну від двійкового пошуку). А зліплювання не лінійна злиття, а алгебраїчний фокус: замість чотирьох добутків — три, ціною жмені додавань. Рекурентність через це інша — `T(n) = 3·T(n/2) + n`, і три підзадачі замість двох зсувають показник з `log₂4 = 2` (тобто `n²`) на `log₂3 ≈ 1.585`:

```
стовпчиком:   n²
Карацуба:     n^log₂3  ≈  n^1.585
```

На числах у тисячі цифр `n^1.585` проти `n²` — уже інший світ. (Цей результат двадцятитрирічний Анатолій Карацуба здобув 1960 року, за тиждень спростувавши здогад Андрія Колмогорова, що швидше за `n²` множити не можна; доказовий статус — усталений факт, опубліковано 1962.) Каркас той самий, що й у сорту, — розділити на менші копії, підкорити кожну тим самим методом, поєднати; змінилася лише **начинка** двох гачків, `split` і `combine`. Опануєш форму — і впізнаєш її там, де на позір нема нічого спільного між упорядкуванням карток і множенням чисел.

## Підсумок

Три рухи поділу пишуться в п'ять рядків, але робочий сорт — це те, що навколо них. Уся вага сидить у **лінійному злитті** двох упорядкованих частин, і робоче злиття пише через покажчики в **один буфер**, заведений раз на весь сорт, а не плодить списки; там же, в трьох покажчиках і двох межах, живуть майже всі помилки на одиницю — їх приборкує єдина домовленість про півінтервали `[lo, mid)` та `[mid, hi)`. Рекурсія згори вниз додає **поріг** переходу на вставки для дрібних шматків (зрізає сталу, як у справжніх бібліотек — 16 у libstdc++, 32 у Timsort) і **швидкий шлях**, що робить уже впорядкований вхід лінійним. Бото́м-ап робить те саме без рекурсії — без стека й дружніше до кешу, — а пінг-понг ще й прибирає перенос назад. За все це маємо `n·log n` **завжди**, без квадратичних ям будь-якого входу, ціною `O(n)` пам'яті та однієї `≤`, що дарує **стійкість** (а з нею — багаторівневе сортування задарма). Пастки збираються в короткий список: півінтервали й переповнення `(lo+hi)/2`, вибір порога, глибина стека при нерівному поділі, компроміс копіювання проти роботи на місці. А що це не один алгоритм, а форма, доводить множення Карацуби: той самий каркас, але поділ ріже число за розрядами й не викидає жодної половини, а зліплювання замінює чотири добутки трьома — і `n²` осідає до `n^1.585`.
