# ⚙️ Проєкт: heapsort у півсотні рядків C

Ідея heapsort вміщається в один абзац — побудуй купу, а тоді (n−1) разів зніми корінь-максимум у хвіст, — але робочий код спотикається не на ідеї, а на жмені арифметики індексів і двох межах, які майже кожен переставляє неправильно з першого разу. Зберімо повну, коректну реалізацію мовою C від першого рядка до останнього — і поряд назвемо саме ті пастки, у які провалюються, коли пишуть купу по пам'яті.

Уся конструкція стоїть на одній операції — **просіюванні вниз**, тому спершу вона. Це той самий примітив, яким [купа](book:algorithms/priority-queue) лагодить свій порядок: після того як у корінь потрапив «завеликий» для цього місця елемент, просіювання спускає його вниз доти, доки він не сяде на своє. Купа — повне двійкове дерево, складене в масив підряд, з властивістю «батько не менший за обох дітей» (це max-купа); просіювання відновлює цю властивість уздовж однієї гілки за O(log n).

## sift_down — функція, на якій тримається все

Просіювання вниз бере індекс `i` і розмір купи `n`, і занурює `a[i]` до його рівня. Уся логіка — знайти найбільшого серед трьох (батько й дві дитини), і якщо ним виявився не батько — обмінятися та спуститися:

```c
/* Просіяти a[i] вниз по max-купі, що займає a[0 .. n-1].
   Після виходу піддерево з коренем i — знову коректна купа. */
static void sift_down(int a[], int i, int n) {
    for (;;) {
        int l   = 2 * i + 1;         /* ліва дитина  */
        int r   = 2 * i + 2;         /* права дитина */
        int max = i;                 /* поки що найбільший — сам батько */

        if (l < n && a[l] > a[max]) max = l;
        if (r < n && a[r] > a[max]) max = r;   /* r < n: правої дитини може й не бути */

        if (max == i) return;        /* батько не менший за обох — тут купа ціла */

        int t = a[i]; a[i] = a[max]; a[max] = t;   /* міняємось із БІЛЬШОЮ дитиною */
        i = max;                     /* спускаємось на її місце — і по колу знову */
    }
}
```

Прочитаймо її повільно, бо кожен рядок затуляє свою помилку. Два `if` разом означають «візьми максимум із трьох»: спершу порівнюємо батька з лівою дитиною, тоді переможця — з правою. Тому `max` наприкінці вказує саме на найбільший із трьох, а обмін відбувається **з більшою дитиною**, а не з першою-ліпшою. Це не дрібниця: якби ми обміняли батька з меншою дитиною, вона стала б батьком свого більшого брата — і властивість купи зламалася б на рівень нижче, тихо й непомітно, аж поки сортування не видасть неправильний результат.

Умова `max == i` — це момент зупинки: якщо найбільший серед трьох і є батько, елемент уже на місці, нижче спускати нема куди. Інакше міняємось і присвоюємо `i = max` — тобто продовжуємо стежити за тим самим елементом, який щойно з'їхав на рівень униз. Цикл `for(;;)` крутиться, поки елемент не впреться в лист (`l >= n`, `r >= n` — дітей нема) або не стане не меншим за обох дітей.

> 🔧 **Навіщо це цикл, а не рекурсія.** Просіювання природно пишеться рекурсивно: «обміняйся з більшою дитиною й виклич себе на її позиції». Але цей рекурсивний виклик — **останній** у функції (хвостова рекурсія), тож він тривіально розгортається в цикл. Різниця не косметична. Рекурсивна версія росте в стек на глибину до ⌊log₂ n⌋; компілятор *може* оптимізувати хвостовий виклик у цикл, але стандарт C цього не гарантує, і в збірці без оптимізацій (`-O0`, налагодження) стек таки росте. Цикл робить глибину стека **O(1) гарантовано, а не з надією** — а саме нульова зайва пам'ять і відсутність рекурсії були одними з причин обрати heapsort. Тож писати просіювання циклом — не стиль, а виконання обіцянки.

## Дві фази поверх sift_down

Маючи `sift_down`, весь heapsort — це два цикли. Зверни увагу, що `sift_down` бере розмір купи `n` окремим параметром: саме він дозволить тому самому просіюванню служити в обох фазах, де межа купи щоразу інша.

```c
void heapsort(int a[], int n) {
    /* Фаза 1 — побудова купи знизу-вгору. Останній батько — індекс n/2-1. */
    for (int i = n / 2 - 1; i >= 0; i--)
        sift_down(a, i, n);

    /* Фаза 2 — (n-1) разів зняти корінь-максимум у хвіст і полагодити купу. */
    for (int end = n - 1; end > 0; end--) {
        int t = a[0]; a[0] = a[end]; a[end] = t;   /* максимум → на лівий край хвоста */
        sift_down(a, 0, end);                       /* купа тепер коротша: розмір = end */
    }
}
```

**Фаза перша — побудова.** Ми проходимо просіюванням кожен внутрішній вузол, з кінця масиву до кореня. Звідки взявся стартовий індекс `n/2 - 1`? Це найпряміша арифметика купи. Дитина з індексом `c` має батька `(c-1)/2` (ціле ділення) — це дзеркало до правила `діти(i) = 2i+1, 2i+2`. Останній елемент масиву стоїть на індексі `n-1`; його батько — це `(n-1-1)/2 = (n-2)/2`, що в цілому діленні дорівнює `n/2 - 1` і для парного, і для непарного `n`. Отже, `n/2 - 1` — індекс **останнього вузла, у якого взагалі є дитина**. Усе, що правіше (індекси `n/2 … n-1`), — листки: їм просіюватися нема куди, і чіпати їх — марна робота.

*Індекс вузла однозначно задає індекси його дітей: 2i+1 і 2i+2. Права половина масиву (індекси n/2…n−1) — самі листки, тому побудова купи стартує з останнього батька n/2−1 і йде до кореня. У вузла 4 права дитина була б під індексом 10 — а його в масиві нема, тому в коді й стоїть перевірка `r < n`.*

**Фаза друга — сортування.** `end` — це індекс останньої комірки купи, і водночас межа відсортованого хвоста. Кожен оберт: обмінюємо корінь `a[0]` (максимум) з `a[end]` — максимум фіксується на лівому краї хвоста, назавжди на своєму місці, — а колишній `a[end]` сідає в корінь. Потім `sift_down(a, 0, end)` лагодить купу, **але вже коротшу**: третій аргумент — `end`, а не `n`. Це найважливіший рядок у всьому проєкті, і саме тут ховається найпоширеніша помилка heapsort. Якби ми передали `n`, просіювання вважало б відсортований хвіст частиною купи й затягло б назад уже поставлені максимуми — сортування б розвалилося. Купа має **скорочуватися** на кожному кроці, і `end` — це її поточний розмір.

Цикл іде `end = n-1, n-2, …, 1`. На `end == 0` лишається один елемент; він і так найменший і вже на місці, окремого кроку не потребує — тому умова `end > 0`, а не `end >= 0`. Приємний наслідок роботи зі знаковим `int`: для `n = 0` чи `n = 1` перший цикл із `n/2 - 1` дає від'ємний старт і просто не виконується, другий — теж; порожній чи одноелементний масив коректно проходить наскрізь без жодної окремої перевірки.

## Повний код, який компілюється

Три шматки вище — `#include`, `sift_down`, `heapsort` — плюс маленький драйвер складаються в готовий файл. Драйвер бере ту саму max-купу, що й покроковий прогін у статті, щоб результат можна було звірити очима:

```c
#include <stdio.h>

/* ... сюди sift_down і heapsort з попередніх блоків ... */

int main(void) {
    int a[] = {9, 7, 8, 3, 6, 2};
    int n = sizeof a / sizeof a[0];

    heapsort(a, n);

    for (int i = 0; i < n; i++)
        printf("%d ", a[i]);        /* друкує: 2 3 6 7 8 9 */
    putchar('\n');
    return 0;
}
```

Прокрути другу фазу в голові на цьому вході — і побачиш ту саму послідовність зон, що й у ручному прогоні: `[8,7,2,3,6|9]`, `[7,6,2,3|8,9]`, `[6,3,2|7,8,9]`, `[3,2|6,7,8,9]`, `[2|3,6,7,8,9]`. Код відтворює її крок у крок, бо він і є той прогін, записаний двома циклами.

## У C++ ці дві фази вже лежать у стандартній бібліотеці

Писати heapsort від руки в C++ майже ніколи не треба — обидві його фази вже є в `<algorithm>` як дві окремі функції, і це найкраще підтверджує, що ми зібрали саме те, що треба:

```cpp
#include <algorithm>
#include <vector>

std::vector<int> a = {9, 7, 8, 3, 6, 2};

std::make_heap(a.begin(), a.end());   // Фаза 1: побудова max-купи за O(n)
std::sort_heap(a.begin(), a.end());   // Фаза 2: (n-1) вибірок, O(n log n)
// a == {2, 3, 6, 7, 8, 9}
```

`std::make_heap` — це рівно наша фаза 1 (стандарт вимагає щонайбільше 3·(last−first) порівнянь, тобто O(n)), а `std::sort_heap` — рівно фаза 2 (щонайбільше 2·N·log N порівнянь). Разом ці два виклики **і є** heapsort, розкладений на свої природні половини; за замовчуванням `operator<` дає max-купу зверху, тому `sort_heap` упорядковує за зростанням.

Але в реальному коді навіть цих двох викликів зазвичай не роблять — беруть `std::sort`. І тут heapsort ховається вдруге: `std::sort` реалізовано **інтроспективним сортуванням** — воно починає зі швидкого сортування заради типової швидкості, стежить за глибиною рекурсії, і щойно та перевищить поріг близько 2·log n (ознака, що розбиття вироджуються в O(n²)), перемикає цей піддіапазон на heapsort. Саме тому стандарт гарантує `std::sort` найгірший випадок O(N log N), а не O(N²): heapsort стоїть усередині запобіжником, що ловить найгірший сценарій швидкого сортування. Та сама тверда межа, яку ми щойно зібрали руками, — це те, заради чого його туди й поклали.

## Складність по фазах і зайва пам'ять

```
sift_down (одне просіювання)      O(h) ≤ O(log n)   — уздовж однієї гілки
Фаза 1: heapify                   O(n)              — НЕ O(n log n)
Фаза 2: (n−1) × sift_down         O(n log n)        — уся вага тут
──────────────────────────────────────────────────
разом                             O(n log n)        — за будь-якого входу
зайва пам'ять                     O(1)              — сортуємо в тому ж масиві
глибина стека                     O(1)              — цикл, не рекурсія
```

Один рядок тут контрінтуїтивний. Фаза 1 викликає `sift_down` приблизно `n/2` разів, кожен — до O(log n), тож наївна оцінка дає O(n log n). Але тісна межа — **O(n)**: майже всі вузли сидять біля дна дерева, де просіювати майже нікуди, і сума їхніх висот збігається до лінійної. Тому побудова, попри `n/2` викликів, коштує менше, ніж одна-єдина фаза 2, і не впливає на підсумок; повне виведення цієї суми — в [аналізі купи](book:algorithms/priority-queue). Разом весь heapsort — O(n log n), у тих самих байтах, що зайняті даними, і без жодного кадру рекурсії.

## Граблі, на яких спотикаються всі

Кожна з цих помилок дає код, що компілюється й навіть «майже сортує» — тому їх і важко ловити.

**0-індексація дітей.** Багато підручників малюють купу з індексами від 1: діти вузла `i` там `2i` і `2i+1`, батько `i/2`. Скопіювати таку формулу в масив від 0 — тиха катастрофа: за 0-індексації `2·0 = 0`, тобто вузол 0 став би власною дитиною, і просіювання зациклилося б на місці. У масиві від нуля правильно `діти(i) = 2i+1, 2i+2`, `батько(c) = (c-1)/2`. Це найчастіша помилка при перенесенні псевдокоду.

**Обмін із меншою дитиною.** Якщо порівнювати батька лише з лівою дитиною (чи міняти з першою, що більша за батька, не глянувши на другу), можна підняти менший елемент над більшим братом. Купа ламається на рівень нижче, максимум у корені все одно опиняється правильний, і на коротких тестах усе «працює» — а на довших сортування збоїть. Два послідовні `if`, кожен оновлює `max`, — це і є захист: вони гарантовано лишають у `max` найбільший із трьох.

**Права дитина, якої нема.** Перевірку `r < n` треба ставити **перед** доступом до `a[r]`. Забудеш — і на вузлі з єдиною (лівою) дитиною читаєш за межею купи: у фазі 2 це елемент уже відсортованого хвоста, і його можна помилково затягти назад. Пастка підступна тим, що кусає лише вузли-одинаки на «шві» дерева, яких мало.

**Межа розміру купи у фазі 2.** `sift_down(a, 0, end)` — саме `end`, поточний розмір купи, що тане, а не сталий `n`. Передаси `n` — і кожен уже поставлений максимум просіється назад у купу; результат перестане бути відсортованим. Власне заради цієї межі `sift_down` і приймає розмір окремим аргументом: щоб на кожному виклику вона була явною.

**Беззнакова петля побудови.** Спокусливо оголосити лічильник як `size_t` (адже індекси невід'ємні). Але тоді `for (size_t i = n/2 - 1; i >= 0; i--)` — нескінченний цикл: умова `i >= 0` для беззнакового типу **завжди істинна**, а коли `i` доходить до 0, декремент обертає його на `SIZE_MAX`, і наступний `sift_down` лізе далеко за межі масиву. До того ж `n/2 - 1` при `n == 0` теж підкручується вниз. Тому в навчальному коді вище лічильник — знаковий `int` (умова `i >= 0` працює як задумано); у продакшені з великими масивами беруть `size_t` і пишуть цикл інакше — наприклад, `for (size_t i = n/2; i-- > 0; )`, де перевірка й декремент влаштовані так, що нуля не проґавиш.

**Рекурсія замість циклу.** Не помилка коректності, а зламана обіцянка: рекурсивне просіювання може непомітно вирости в стек на O(log n) і забрати ту саму «нульову зайву пам'ять», заради якої heapsort і брали. Цикл лишає глибину стека O(1) без застережень.

Жодна з цих пасток не стосується ідеї — усі до одної живуть у трьох рядках арифметики й двох межах. Саме тому heapsort варто раз зібрати руками: доки не напишеш `sift_down` сам, «обмінятися з більшою дитиною» звучить очевидно — а в коді це два `if` поспіль, кожен з яких хтось колись забув.
