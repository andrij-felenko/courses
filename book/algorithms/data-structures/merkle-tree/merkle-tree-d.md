Коли однорангова мережа передає гігабайтний файл або 100 000 транзакцій між тисячами незнайомих комп'ютерів, будь-який бітовий збій на магнітному диску чи навмисна підміна фрагмента даних зловмисником невідворотно руйнує цілісність усього масиву. Перевірка цілісності лише одним загальним криптографічним хешем файлу вимагає повністю завантажити всі дані перед тим, як вдасться виявити помилку: якщо бодай один біт у 4-гігабайтному архіві пошкоджено, доводиться відкидати весь завантажений архів і починати передачу заново. Передача окремого 32-байтного хешу для кожного дрібного 16-кілобайтного блока утворює 8 мегабайтів додаткових метаданих на кожен файл, створюючи лінійні накладні витрати `O(N)`. Дерево Меркла повністю усуває цей компроміс: воно дозволяє підтвердити цілісність та факт наявності будь-якого одного блока з `N` елементів за логарифмічний час `O(log N)` та передачу всього `⌈log₂ N⌉` хешів, маючи на руках лише один 32-байтний корінь.

## 1. Проблема цілісності у розподілених системах

Розглянемо фундаментальну суперечність між надійністю точкової перевірки даних та обсягом супровідних метаданих у будь-якій системі обробки даних.

Уявімо послідовність із `N` впорядкованих блоків даних `D = (d₀, d₁, d₂, ..., d_{N-1})`. Це можуть бути сектори диска у файловій системі, шматки файла у торент-клієнті або транзакції у блоці криптовалюти.

Існує три базові інженерні підходи до перевірки цілісності цього масиву:

```
Підхід 1: Один монолітний хеш
[d₀, d₁, d₂, ..., d_{N-1}]  ───>  Hash(d₀ || d₁ || ... || d_{N-1}) = H_total
Плюси: метадані мають сталий розмір O(1) (32 байти для SHA-256).
Мінуси: точкова перевірка неможлива. Для виявлення пошкодження d₁ треба завантажити всі N блоків.

Підхід 2: Масив хешів кожного блока
d₀ ───> Hash(d₀)
d₁ ───> Hash(d₁)
...
d_{N-1} ───> Hash(d_{N-1})
Плюси: миттєва точкова перевірка будь-якого блока d_k за сталий час O(1).
Мінуси: обсяг метаданих зростає строго лінійно як O(N). Для мільйона блоків треба передати 32 МБ хешів.

Підхід 3: Ієрархічне Дерево Меркла
Листки = Hash(d_i)
Внутрішні вузли = Hash(Left || Right)
Вершина = Merkle Root
Плюси: метадані для фіксації всього стану мають сталий розмір O(1) (Merkle Root), 
а доказ наявності будь-якого одного блока вимагає передачі лише O(log N) хешів.
```

Дерево Меркла (англ. *Merkle Tree*, також відоме як криптографічне хеш-дерево) — це двійкове дерево, у якому кожен листок містить хеш відповідного блока даних, а кожен внутрішній вузол містить криптографічний хеш від зчеплення (конкатенації) своїх дочірніх вузлів.

Про те, як ця концепція народилася у 1979 році під час створення цифрових підписів Лампорта і як вона еволюціонувала до BitTorrent, Git та Bitcoin, детально описано в [історичному нарисі про Дерево Меркла](book:algorithms/merkle-tree/hist-merkle.md).

## 2. Анатомія та покроковий порядок побудови дерева

Побудова Дерева Меркла відбувається знизу вгору (bottom-up) за детермінованим алгоритмом.

![Анатомія Дерева Меркла](/book/algorithms/data-structures/merkle-tree/img/merkle-tree-structure.svg)
*Анатомія Дерева Меркла: хешування листків із префіксом 0x00, рекурсивна конкатенація внутрішніх вузлів із префіксом 0x01 та отримання єдиного кореня Merkle Root.*

### Ланка 1: Хешування листків та розділення доменів (Domain Separation)
Кожен бінарний блок даних `d_i` перетворюється на листовий вузол дерева. Щоб захистити структуру від криптографічних атак маніпуляцій глибиною (атаки другого прообразу), перед даними обов'язково додається однобайтний префікс домену `0x00`:

```
L_i = Hash(0x00 || d_i)
```

Завдяки цьому листок дерева принципово відрізняється від внутрішнього вузла ще на рівні байтового префікса, унеможливлюючи підробку типів даних.

### Ланка 2: Формування внутрішніх вузлів
Пари сусідніх листків `(L₀, L₁), (L₂, L₃)` зчіплюються у байтовий вектор, і від отриманої послідовності обчислюється хеш із префіксом внутрішнього домену `0x01`:

```
N₀₁ = Hash(0x01 || L₀ || L₁)
N₂₃ = Hash(0x01 || L₂ || L₃)
```

Цей процес рекурсивного сходження об'єднує вузли рівень за рівнем. На кожному вищому рівні кількість вузлів зменшується вдвічі:

```
Рівень 0 (Листки):          L₀         L₁         L₂         L₃
                             \        /            \        /
Рівень 1 (Внутрішній):         N₀₁                    N₂₃
                                 \                    /
Рівень 2 (Корінь):                      Merkle Root
```

### Ланка 3: Обчислення кореня (Merkle Root)
На самій вершині дерева залишається єдиний підсумковий вузол. Його хеш називається **коренем Меркла** (*Merkle Root*).

Корінь Меркла має криптографічну властивість **лавинного ефекту** (avalanche effect): якщо змінити бодай один біт у будь-якому вхідному блоці `d_i`, хеш відповідного листка `L_i` повністю змінюється. Це викликає ланцюгову реакцію перебудови всіх батьківських хешів уздовж гілки аж до самісінької вершини. Звідси випливає важливий інваріант: **Merkle Root повністю й однозначно закриває (фіксує) весь стан вхідного масиву даних**.

## 3. Механізм доказу включення (Merkle Inclusion Proof)

Головне практичне призначення Дерева Меркла — це формування та перевірка компактного **доказу включення** (*inclusion proof* або *audit path*).

Уявімо клієнта (наприклад, мобільний криптогаманець або торент-клієнт), який знає лише один 32-байтний Merkle Root `R`. Клієнт завантажив з мережі один блок `d₁` і хоче переконатися, що цей блок є справжнім і дійсно входить до складу загального масиву з коренем `R`.

Серверу не потрібно надсилати клієнту всі інші блоки даних чи повне дерево. Сервер надсилає лише сам блок `d₁` та логарифмічний список так званих **сестринських хешів** (*sibling hashes*) — вузлів, які лежать поруч на шляху від `d₁` до кореня.

![Шлях аудиторського доказу](/book/algorithms/data-structures/merkle-tree/img/merkle-proof-path.svg)
*Шлях аудиторського доказу (Merkle Proof) для блоку d₁: для перевірки потрібні лише сестринські хеші L₀ та N₂₃.*

### Покрокова процедура перевірки доказу на боці клієнта
Нехай клієнт перевіряє блок `d₁` у дереві з 4 елементів. Доказ складається з масиву пар `(сестринський_хеш, напрямок)`:

1. **Крок 0 (Листок)**: Клієнт обчислює хеш самого завантаженого блока: `V₀ = Hash(0x00 || d₁)`.
2. **Крок 1 (Внутрішній вузол)**: Клієнт бере перший сестринський хеш `L₀` (напрямок `LEFT`) і обчислює батьківський вузол:
   ```
   V₁ = Hash(0x01 || L₀ || V₀)   // Отримали обчислений вузол N₀₁
   ```
3. **Крок 2 (Підняття до кореня)**: Клієнт бере другий сестринський хеш `N₂₃` (напрямок `RIGHT`) і обчислює наступний рівень:
   ```
   V₂ = Hash(0x01 || V₁ || N₂₃)  // Отримали кандидат кореня R'
   ```
4. **Звірка коренів**: Клієнт порівнює `V₂` з відомим коренем `R`. Якщо `V₂ == R`, факт наявності та незмінності блока `d₁` математично доведено зі 100% впевненістю.

Для масиву з `N = 1 000 000` елементів висота дерева дорівнює `⌈log₂ 1000000⌉ = 20`. Замість завантаження 1 мільйона елементів клієнту достатньо отримати й обчислити всього **20 хешів** (640 байтів даних).

Детальний математичний аналіз складності операцій, формальне визначення та доказ стійкості до підробки подано у [математичному аналізі Дерева Меркла](book:algorithms/merkle-tree/math-merkle-proof.md).

## 4. Крайові випадки та криптографічні атаки

Попри елегантність структури, наївна реалізація Дерева Меркла містить кілька небезпечних підводних каменів, які в історії криптографії призводили до реальних вразливостей.

### Крайовий випадок 1: Непарна кількість листків
Якщо кількість вхідних блоків `N` не є степенем двійки, на деякому рівні виникає «самотній» вузол без пари.

Існує дві основні стратегії обробки таких вузлів у стандартних протоколах:
1. **Дублювання останнього вузла**: Непарний вузол `X` конкатенується сам із собою: `Parent = Hash(0x01 || X || X)`.
2. **Перенесення на вищий рівень**: Вузол `X` піднімається на наступний рівень без хешування, доки не знайде собі пару.

> ⚠️ **Історична вразливість Bitcoin (CVE-2012-2459)**:
> У протоколі Bitcoin для непарних рівнів було обрано дублювання останньої транзакції `Hash(X || X)`. Зловмисники виявили, що якщо блок містить транзакції `[A, B, C]`, його корінь обчислюється як для `[A, B, C, C]`. Це дозволяло створювати дубльовані транзакції з однаковим Merkle Root, мутуючи вміст блоків і спричиняючи відмову в обслуговуванні (DoS) у вузлах мережі.

### Крайовий випадок 2: Атака другого прообразу (Second Pre-image Attack)
Якщо в реалізації відсутнє розділення доменів (тобто хеш обчислюється просто як `Hash(A || B)` і для листків, і для внутрішніх вузлів), виникає критична вразливість для дерев нефіксованої глибини.

![Захист від атак другого прообразу](/book/algorithms/data-structures/merkle-tree/img/merkle-domain-separation.svg)
*Атака другого прообразу: підміна внутрішнього вузла N₁₂ на листовий блок без префіксів доменів та її блокування префіксами 0x00 і 0x01.*

Якщо префікси відсутні, зловмисник може взяти внутрішній вузол `N₁₂ = Hash(L₁ || L₂)` і видати рядок `d* = L₁ || L₂` за справжній листовий блок даних. Оскільки `Hash(d*) = N₁₂`, система сприйме внутрішній гілковий хеш за листок, що дозволяє підробляти докази для склеєних даних.

Використання строго відмінних префіксів `0x00` (для даних) та `0x01` (для хеш-вузлів) унеможливлює цю атаку, оскільки `Hash(0x00 || (L₁ || L₂)) ≠ Hash(0x01 || L₁ || L₂)`.

## 5. Варіації та сучасні розширення

Класичне Дерево Меркла є статичним: воно будується один раз для фіксованого масиву даних. Для динамічних систем із мільйонами оновлень розроблено спеціалізовані модифікації.

### 5.1. Sparse Merkle Tree (SMT / Розріджене Дерево Меркла)
SMT — це дерево фіксованої глибини (наприклад, 256 рівнів, під ключ SHA-256), у якому **абсолютно всі можливі ключі** мають своє наперед визначене місце у листках. Оскільки більшість із `2²⁵⁶` листків є порожніми (містять хеш нуля `Hash(0)`), їхні піддерева обчислюються заздалегідь і кешуються.

Головна перевага SMT: воно дозволяє формувати **доказ відсутності** (*non-membership proof*). Щоб довести, що ключа `K` немає у базі даних, достатньо надати Merkle Proof для відповідного листка і показати, що він містить нуль.

### 5.2. Merkle-Patricia Trie (State Trie в Ethereum)
У блокчейні Ethereum необхідно миттєво оновлювати баланси мільйонів акаунтів після кожного блоку. Класичне дерево вимагало б повного перебудування за `O(N)`.

Ethereum поєднує префіксне дерево (Patricia Trie) та Дерево Меркла. Ключем є хеш адреси акаунта, а значенням — його баланс та стан. Якщо змінюється баланс одного акаунта, модифікується лише один промінь дерева завдовжки `O(log N)`, а новий Merkle Root обчислюється за кілька мікросекунд.

### 5.3. Verkle Trees (Векторні криптографічні дерева)
Verkle Trees (скорочення від *Vector Commitment + Merkle Tree*) замінюють криптографічні хеш-функції у внутрішніх вузлах на векторні зобов'язання (Vector Commitments, зокрема на еліптичних кривих Bandersnatch).

Завдяки цьому внутрішній вузол може мати не 2 нащадки, а **256 або 1024 нащадки**, що робить дерево надзвичайно широким і низьким. Розмір доказу включення зменшується від `O(log₂ N)` до сталого розміру `O(1)` (близько 150 байтів замість кілобайтів), що є критичним для масштабування розподілених мереж.

## 6. Простеження через файлові системи та системні виклики (sysfs / procfs / git)

Щоб побачити Дерево Меркла в дії на практиці, розглянемо його простеження у розподілених та системних інструментах Linux.

### Простеження у Git через низькорівневі plumbing-команди
У Git кожен каталог є деревом Меркла. Ми можемо дослідити його структуру безпосередньо через системний інструментарій:

```bash
# Отримаємо хеш поточного комміта
$ git rev-parse HEAD
4a8d9b1c2e3f4a5b6c7d8e9f0a1b2c3d4e5f6a7b

# Отримаємо вказівник на дерево файлів (Merkle Tree Root) у комміті
$ git cat-file -p HEAD
tree 8f2b3a4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a
author Author Name <author@example.com> 1723632000 +0300
committer Author Name <author@example.com> 1723632000 +0300

# Розгорнемо корінь дерева: він містить хеші піддерев і blobs
$ git cat-file -p 8f2b3a4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a
100644 blob 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b    README.md
040000 tree 9b8a7f6e5d4c3b2a1f0e9d8c7b6a5f4e3d2c1b0a    src
```

Кожен запис `tree` і `blob` — це адресація за вмістом SHA-1/SHA-256. Будь-яке редагування файла `README.md` змінює його `blob`, що автоматично перераховує хеш дерева `8f2b...` та комміта `4a8d...`.

## 7. Порівняльний аналіз із суміжними структурами даних

Щоб чітко розуміти місце Дерева Меркла у кодовій базі, порівняємо його з альтернативними структурами організованого доступу та фіксації стану:

```
+------------------------+-------------------+-------------------+-------------------+-------------------+
| Властивість            | Хеш-таблиця       | B-дерево          | Дерево Меркла     | Merkle-Patricia   |
+------------------------+-------------------+-------------------+-------------------+-------------------+
| Головне призначення    | Точковий доступ   | Дисковий індекс   | Криптографія      | Стан смарт-контр. |
| Пошук елемента         | O(1)              | O(log N)          | O(log N)          | O(log N)          |
| Доказ включення Proof  | Неможливий        | Неможливий        | O(log N)          | O(log N)          |
| Перевірка цілісності   | Ні                | Ні                | Так (Merkle Root) | Так (State Root)  |
| Обсяг доказу           | O(N)              | O(N)              | O(log N)          | O(log N)          |
+------------------------+-------------------+-------------------+-------------------+-------------------+
```

## 8. Практичне застосування у реальних системах

> 🔧 **Навіщо це.** Дерево Меркла — це універсальний клема-фіксатор для будь-якої розподіленої архітектури. Воно перетворює довільний обсяг даних на один 32-байтний інваріант і дозволяє перевіряти будь-які фрагменти без довіри до джерела.

### 1. BitTorrent та IPFS
У однорангових мережах завантаження файлів відбувається від багатьох незахищених пірів. Торрент-файл або IPFS CID містить корінь Дерева Меркла. Під час завантаження кожного шматка (chunk) розміром 16 КБ клієнт верифікує його за допомогою Merkle proof. Це захищає систему від шкідливих пірів, які надсилають зіпсований вміст.

### 2. Git (Розподілений контроль версій)
Уся файлова система проєкту у Git подається як граф об'єктів. Каталоги є хеш-деревами, що вказують на файли (blobs). Завдяки цьому будь-яка зміна у коді автоматично змінює хеш комміта, унеможливлюючи незапобіжну фальсифікацію історії розробки.

### 3. Блокчейн (Bitcoin, Ethereum)
У Bitcoin корінь Меркла вміщується у 80-байтний заголовок блоку. Це дозволяє легковажним гаманцям (SPV) верифікувати надходження грошей за `O(log N)` кроків без завантаження повного блокчейну. В Ethereum розширені дерева фіксують увесь стан балансів та пам'яті смарт-контрактів.

### 4. Файлові системи ZFS та Btrfs
У ZFS кожна блок-вказівка містить хеш адресованого дискового блока. Усе дерево файлів зводиться до єдиного кореня `ubercore`, що усуває проблему «тихого псування даних» (*bit rot*).

### 5. Certificate Transparency (RFC 6962)
Усі випущені SSL/TLS сертифікати записуються у публічні додаванські (append-only) логи на базі Дерева Меркла. Це дозволяє браузерам перевіряти, що Центр Сертифікації (CA) не випустив фальшивий сертифікат для чужого домену.
