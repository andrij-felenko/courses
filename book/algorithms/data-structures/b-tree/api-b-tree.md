# 📋 Фізичний формат сторінки та інтерфейс B-дерева

Фізичне представлення сторінки B-дерева у зовнішній пам'яті спирається на побайтове двовимірне розміщення даних (Slotted Page Architecture), яке визначає формат заголовків, масиви зсувів комірок, структуру зберігання ключів та вказівників, а також програмний C/C++ інтерфейс буферного пулу (Buffer Pool Manager) і дискового сторінкового менеджера (Page Manager).

## Архітектура сторінки з вибірковими комірками (Slotted Page Architecture)

У реальних базах даних (зокрема PostgreSQL, SQLite, MySQL InnoDB) та дискових файлових системах вузол B-дерева серіалізується у фіксований дисковий блок (найчастіше 4096 або 8192 байти). Оскільки ключі та значення можуть мати змінну довжину (наприклад, текстові рядки або бінарні дамп-об'єкти), використання масиву фіксованого розміру призвело б до високої фрагментації пам'яті.

Щоб розв'язати цю проблему, застосовують архітектуру **Slotted Page** (сторінка з покажчиками комірок). Сторінка ділиться на чотири основні зони:

1. **Заголовок сторінки (Page Header)**: Фіксована структура у початку сторінки (зазвичай 24–64 байти), яка містить метадані сторінки, лічильники ключів, покажчик вільного простору, журнальний номер LSN та прапорець типу вузла.
2. **Масив покажчиків комірок (Slot Array / Cell Pointer Array)**: Росте від кінця заголовка **зліва направо**. Кожен слот займає 2 байти i містить зміщення (offset) від початку сторінки до відповідної комірки з даними. Слоти завжди впорядковані за ключем.
3. **Область нерозподіленої пам'яті (Unallocated Free Space)**: Вільний простір між масивом слотів та комірками даних.
4. **Область комірок даних (Cell Data Area)**: Росте від самого кінця сторінки **справа наліво** (від адреси 4095 до початку). Комірка містить дисковий вказівник на дочірню сторінку, довжину ключа, самий ключ та корисне навантаження (payload/значення).

```
+-----------------------------------------------------------------------+
| Page Header | Slot 0 | Slot 1 | Slot 2 | ... |                        |
| (24 bytes)  | (2B)   | (2B)   | (2B)   |     |                        |
+----------------------------------------------+                        |
|                                              v                        |
|                     Вільний простір (Unallocated)                     |
|                                                                       |
|                                 +-------------------------------------+
|                                 | Cell 2       | Cell 1   | Cell 0    |
|                                 | (Data)       | (Data)   | (Data)    |
+-----------------------------------------------------------------------+
0                                                                     4095
```

## Механізм дефрагментації та впорядкування усередині сторінки

Архітектура Slotted Page забезпечує два видатні інженерні здобутки:

- **O(1) впорядкування слотів без фізичного переміщення даних**: Коли новий ключ вставляється посередині сторінки, самі дані ключа просто копіюються в кінець області даних (`cells_start_offset`), а зсуваються лише 2-байтові покажчики у масиві слотів. Це скорочує обсяг переміщуваної пам'яті у десятки разів.
- **Усунення зовнішньої фрагментації через локальну дефрагментацію (Page Compaction)**: Вилучення ключа зі сторінки залишає «діру» в області комірок даних (dead space). Замість складної процедури збирання сміття, коли сумарна величина dead space перевищує поріг, сторінка дефрагментується за один прохід: всі активні комірки зсуваються строго до правого краю сторінки (до адреси 4095), а `cells_start_offset` оновлюється.

Окремого розгляду заслуговує операція вилучення комірки з Slotted Page. Коли комірка видаляється, її слот у масиві покажчиків помічається як вільний (зсув встановлюється у значення `0xFFFF`), а лічильник `num_cells` регулюється. Область даних вилученої комірки залишається непорушеною до найближчого виклику процедури дефрагментації сторінки, що мінімізує кількість операцій зсуву пам'яті у RAM.

## Префіксне стиснення ключів (Prefix Compression & Key Truncation)

Для текстових ключів (наприклад, поштові адреси або URL-посилання) багато сусідніх ключів у сторінці мають спільний префікс (наприклад, `"https://example.com/page1"` та `"https://example.com/page2"`).

Щоб зекономити дисковий простір сторінки, застосовують **префіксне стиснення**:

1. **Спільний префікс сторінки (Page Prefix)**: На початку області даних записується спільний префікс для всіх ключів сторінки.
2. **Зберігання суфіксів (Suffix Storage)**: Кожна окрема комірка зберігає лише довжину спільного префікса `prefix_len` та унікальний суфікс `suffix_bytes`.
3. **Усікання ключів у внутрішніх вузлах (Key Truncation)**: Оскільки внутрішні вузли B-дерева використовуються лише для направлення пошуку, ключ розмежовування не обов'язково має бути повним ключем з листка. Достатньо зберегти найкоротший унікальний префікс, який розділяє ліве і праве піддерево. Наприклад, якщо макс-ключ лівого дитини — `"Alexandria"`, а мін-ключ правого — `"Alexander"`, у внутрішній вузол піднімається найкоротший роздільник `"Alexandr"`. Це підвищує ступінь розгалуження `m` на 20–40%.

## Двійкова структура заголовка сторінки (Byte-level Layout)

Розглянемо точну побайтову декомпозицію 24-байтового заголовка сторінки B-дерева у форматі C-структури:

| Зсув (Байт) | Поле | Тип | Опис |
| :--- | :--- | :--- | :--- |
| `0x00 - 0x07` | `lsn` | `uint64_t` | Log Sequence Number (LSN) для транзакційного журналу WAL |
| `0x08 - 0x0B` | `page_id` | `uint32_t` | Унікальний номер сторінки в файлі бази даних (Page Block ID) |
| `0x0C - 0x0D` | `flags` | `uint16_t` | Бітові прапорці: `0x01` = Leaf, `0x02` = Root, `0x04` = Overflow |
| `0x0E - 0x0F` | `num_cells` | `uint16_t` | Кількість активних слотів/ключів у сторінці |
| `0x10 - 0x11` | `free_space_offset` | `uint16_t` | Зсув кінця масиву слотів (росте зліва направо) |
| `0x12 - 0x13` | `cells_start_offset`| `uint16_t` | Зсув початку останньої виділеної комірки (росте справа наліво) |
| `0x14 - 0x17` | `right_sibling_id`  | `uint32_t` | Номер правої сусідньої сторінки (для швидкодії B+ Tree) |

Детальний аналіз кожного призначення полів заголовка:

- `lsn`: 64-бітне значення Log Sequence Number. Використовується для синхронізації з журналом транзакцій (Write-Ahead Logging). Своєю наявністю гарантує, що невідновлена сторінка не буде записана на диск без відповідних журнальних записів.
- `page_id`: 32-бітний унікальний ідентифікатор сторінки у файлі бази даних. Фізичний зсув сторінки у файлі обчислюється як `Offset = page_id * PAGE_SIZE`.
- `flags`: Бітова маска прапорців. `PAGE_FLAG_LEAF` описує, чи є сторінка листком, `PAGE_FLAG_ROOT` позначає корінь індексу, а `PAGE_FLAG_OVERFLOW` інформує про наявність переповнених сторінок даних (OVERFLOW pages) для надвеликих ключів або значень.
- `num_cells`: Кількість активних ключів, збережених у цій сторінці. Визначає розмір масиву слотів `Slot Array`.
- `free_space_offset`: Байтовий зсув від початку сторінки до першого вільного байта після масиву слотів. Збільшується на 2 байти при додаванні кожного нового елемента.
- `cells_start_offset`: Байтовий зсув початку найбільш лівої комірки даних. Зменшується на розмір розміщеної комірки при додаванні нових елементів.
- `right_sibling_id`: Вказівник на праву сусідню сторінку того самого рівня. Використовується у B+ деревах для виконання лінійного діапазонного сканування (Range Scan) без повернення до батьківського вузла.

#include <stdint.h>
#include <stdbool.h>

#define PAGE_SIZE 4096
#define PAGE_FLAG_LEAF     0x01
#define PAGE_FLAG_ROOT     0x02
#define PAGE_FLAG_OVERFLOW 0x04

#pragma pack(push, 1)

/* Заголовок сторінки B-дерева (24 байти) */

    uint64_t lsn;                 /* WAL Log Sequence Number */
    uint32_t page_id;             /* Номер сторінки в файлі */
    uint16_t flags;               /* Прапорці сторінки */
    uint16_t num_cells;           /* Кількість елементів */
    uint16_t free_space_offset;   /* Верхня межа слотів */
    uint16_t cells_start_offset;  /* Нижня межа комірок даних */
    uint32_t right_sibling_id;    /* Вказівник на праву сусідню сторінку */
} PageHeader;

/* Покажчик комірки (2 байти) */
typedef uint16_t CellOffset;

/* Структура комірки внутрішнього вузла */
typedef struct InternalCell {
    uint32_t child_page_id;       /* Вказівник на дочірній блок */
    uint16_t key_len;             /* Довжина ключа у байтах */
    uint8_t  key_data[];          /* Гнучкий масив даних ключа */
} InternalCell;

/* Структура комірки листка */
typedef struct LeafCell {
    uint16_t key_len;             /* Довжина ключа у байтах */
    uint16_t val_len;             /* Довжина значення/payload у байтах */
    uint8_t  payload[];           /* Спочатку ключ, потім значення */
} LeafCell;

## Зберігання відсутніх і порожніх значень (NULL Value Representation)

При кодуванні ключів баз даних у B-дереві виникає вимога коректного збереження необов'язкових полів (`NULL` у реляційних таблицях):

- **Бітова карта відсутності значень (Null Bitmap)**: У кожній комірці листка `LeafCell` перед корисним навантаженням розміщується 1-байтова маска `null_flags`. Якщо біт `0x01` встановлено, значення розглядається як `NULL`.
- **Нульова довжина корисного навантаження (`val_len = 0`)**: Для `NULL` значення поле `val_len` дорівнює 0, і простір під `payload` не виділяється.
- **Спеціальне сортувальне значення**: У B-деревах значень `NULL` впорядковуються або як найменше можливе значення (`NULLS FIRST`), або як найбільше можливе значення (`NULLS LAST`). Це гарантує, що всі `NULL`-ключі згруповані на одному краї листка, що прискорює запити видалення та сканування `WHERE column IS NULL`.

## Контрольні суми та виявлення спотворень пам'яті (Page Checksums / CRC-32C)

Для виявлення мовчазного спотворення даних на диску (англ. *silent data corruption* або *bit rot*), яке викликане збоями дискового контролера чи апаратними дефектами накопичувача, кожен заголовок сторінки доповнюється полем `checksum`:

- **Обчислення при зберіганні**: Перед записом сторінки на диск менеджер буферного пулу обчислює 32-бітну контрольну суму за алгоритмом CRC-32C від 4096 байтів сторінки (із зануленим полем `checksum`).
- **Перевірка при зчитуванні**: При виклику `fetch_page()` зчитується 4 КБ блок, обчислюється його поточний CRC-32C і порівнюється з записаним у заголовку. Якщо контрольні суми не збігаються, викидається виняток `BTreeErrorCode::PageCorrupted`, запобігаючи виконанню аварійного коду над пошкодженою структурою дерева.

## Управління надвеликими ключами: Сторінки переповнення (Overflow Pages)

Коли розмір ключа або значення становить значну частку від розміру сторінки (наприклад, текстове поле `VARCHAR(2000)` у 4-кілобайтовій сторінці), розміщення такого елемента безпосередньо у сторінці B-дерева порушило б інваріант високого розгалуження: у сторінці вмістився б лише один або два ключі, перетворивши B-дерево на звичайне бінарне дерево.

Для розв'язання цієї проблеми СУБД застосовують механізм **Overflow Pages** (у PostgreSQL відомий як TOAST, у SQLite — overflow pages):

- **Поріг винесення (Overflow Threshold)**: Якщо розмір комірки перевищує поріг (наприклад, `PAGE_SIZE / 4 = 1024` байти), комірка ділиться.
- **Внутрішній посилання-замінник**: У самій сторінці B-дерева зберігаються лише перші `N` байтів ключа (префікс для швидкого порівняння) та 8-байтовий вказівник на першу сторінку переповнення `overflow_page_id`.
- **Ланцюжок сторінок переповнення**: Самі дані записуються у послідовний зв'язаний список однорангових дискових блоків. Це дозволяє зберігати ключі довільного обсягу (мегабайти) без деградації висоти та ефективності B-дерева.

## Інтерфейс менеджера сторінок та буферного пулу (Buffer Pool API)

У системі збереження даних B-дерево не працює з файлом безпосередньо. Замість цього всі операції читання та запису проходять через **Buffer Pool Manager**, який утримує фіксовану кількість сторінок у оперативній пам'яті (Page Frame Buffer), виконує витіснення за алгоритмами LRU/CLOCK та керує синхронізацією з диском.

Принцип роботи буферного пулу спирається на два поняття:

1. **Закріплення сторінки (Pinning / Unpinning)**: Коли B-дерево звертається до сторінки `page_id`, викликається `fetch_page(page_id)`. Буферний пул підвантажує сторінку з диска (якщо її немає в кеші) і збільшує `pin_count` на 1. Доки `pin_count > 0`, фоновий потік витіснення сторінок (Eviction Thread) не має права вивантажувати цю сторінку з оперативної пам'яті. Після закінчення роботи зі сторінкою викликом `unpin_page(page_id, is_dirty)` лічильник `pin_count` зменшується.
2. **Маркування брудної сторінки (Dirty Flag)**: Якщо сторінка була модифікована (наприклад, вставлено або видалено ключ), вона позначається прапорцем `is_dirty = true`. При вивантаженні з кешу або при виконанні контрольної точки (Checkpoint) брудні сторінки примусово скидаються на диск.

C++ контракт інтерфейсу `BufferPoolManager`:

```cpp
#include <cstdint>
#include <memory>
#include <system_error>
#include <span>

using PageId = uint32_t;

enum class BTreeErrorCode {
    Success = 0,
    PageNotFound,
    BufferPoolFull,
    DiskReadError,
    DiskWriteError,
    PageCorrupted,
    KeyAlreadyExists,
    KeyNotFound
};

class BTreeException : public std::runtime_error {
public:
    explicit BTreeException(BTreeErrorCode code, const std::string& msg)
        : std::runtime_error(msg), code_(code) {}
    [[nodiscard]] BTreeErrorCode code() const noexcept { return code_; }
private:
    BTreeErrorCode code_;
};

/* Інтерфейс утримання сторінки у пам'яті (RAII Page Handle) */
class PageHandle {
public:
    virtual ~PageHandle() = default;

    /* Отримати прямий вказівник на 4KB байтовий буфер */
    [[nodiscard]] virtual std::span<uint8_t, PAGE_SIZE> data() noexcept = 0;
    [[nodiscard]] virtual std::span<const uint8_t, PAGE_SIZE> data() const noexcept = 0;

    /* Позначити сторінку як брудну (підлягає запису на диск) */
    virtual void mark_dirty() noexcept = 0;

    /* Отримати ідентифікатор сторінки */
    [[nodiscard]] virtual PageId page_id() const noexcept = 0;
};

/* Головний контракт інтерфейсу BufferPoolManager */
class IBufferPoolManager {
public:
    virtual ~IBufferPoolManager() = default;

    /* Завантажити сторінку з диска або отримати з клейму кешу */
    [[nodiscard]] virtual std::unique_ptr<PageHandle> fetch_page(PageId page_id) = 0;

    /* Створити нову дискову сторінку */
    [[nodiscard]] virtual std::unique_ptr<PageHandle> new_page(PageId* out_page_id) = 0;

    /* Вивільнити сторінку (зменшити лічильник pin_count) */
    virtual void unpin_page(PageId page_id, bool is_dirty) = 0;

    /* Примусово скинути сторінку на диск (FSYNC) */
    virtual void flush_page(PageId page_id) = 0;

    /* Скинути всі брудні сторінки індексу */
    virtual void flush_all_pages() = 0;
};
```

## Інтерфейс низькорівневих операцій зі сторінкою

Для маніпулювання елементами всередині однієї сторінки без розпакування всього вузла використовується низькорівневий клас-обгортка `BTreePageDecoder`:

```cpp
#include <cstdint>
#include <span>
#include <optional>
#include <cstring>

class BTreePageDecoder {
    std::span<uint8_t, PAGE_SIZE> buffer_;
    PageHeader* header_;

public:
    explicit BTreePageDecoder(std::span<uint8_t, PAGE_SIZE> buffer)
        : buffer_(buffer), header_(reinterpret_cast<PageHeader*>(buffer.data())) {}

    [[nodiscard]] bool is_leaf() const noexcept {
        return (header_->flags & PAGE_FLAG_LEAF) != 0;
    }

    [[nodiscard]] uint16_t cell_count() const noexcept {
        return header_->num_cells;
    }

    /* Отримати зсув i-ї комірки з масиву слотів */
    [[nodiscard]] uint16_t get_cell_offset(uint16_t index) const {
        if (index >= header_->num_cells) {
            throw std::out_of_range("Індекс слота виходить за межі num_cells");
        }
        const auto* slot_array = reinterpret_cast<const CellOffset*>(
            buffer_.data() + sizeof(PageHeader)
        );
        return slot_array[index];
    }

    /* Обчислити обсяг вільного простору у сторінці */
    [[nodiscard]] uint16_t free_space() const noexcept {
        if (header_->cells_start_offset < header_->free_space_offset) {
            return 0;
        }
        return header_->cells_start_offset - header_->free_space_offset;
    }

    /* Додати комірку у сторінку з дефрагментацією за потреби */
    bool insert_cell(uint16_t index, std::span<const uint8_t> key, std::span<const uint8_t> payload) {
        uint16_t required_bytes = sizeof(CellOffset) + sizeof(LeafCell) + key.size() + payload.size();
        if (free_space() < required_bytes) {
            return false; /* Сторінка переповнена, вимагається split */
        }

        // Виділяємо простір для комірки з кінця сторінки
        header_->cells_start_offset -= (sizeof(LeafCell) + key.size() + payload.size());
        uint16_t new_cell_offset = header_->cells_start_offset;

        auto* leaf_cell = reinterpret_cast<LeafCell*>(buffer_.data() + new_cell_offset);
        leaf_cell->key_len = static_cast<uint16_t>(key.size());
        leaf_cell->val_len = static_cast<uint16_t>(payload.size());
        std::memcpy(leaf_cell->payload, key.data(), key.size());
        std::memcpy(leaf_cell->payload + key.size(), payload.data(), payload.size());

        // Вставляємо новий слот у масив слотів зі зсувом елементів
        auto* slot_array = reinterpret_cast<CellOffset*>(buffer_.data() + sizeof(PageHeader));
        for (int i = header_->num_cells; i > index; --i) {
            slot_array[i] = slot_array[i - 1];
        }
        slot_array[index] = new_cell_offset;

        header_->num_cells++;
        header_->free_space_offset += sizeof(CellOffset);
        return true;
    }
};
```

## Синхронізація сторінок у пам'яті: Менеджер блокувальників (Page Latch Manager)

Для підтримки паралельного доступу багатьох потоків до однієї сторінки у буферному пулі кожна сторінка у пам'яті (Page Frame) містить власний читацько-письменницький м'ютекс (Read/Write Latch):

- **Shared Latch (S-Latch)**: Захоплюється потоками, що виконують операції читання (пошук чи сканування). Двоє або більше потоків можуть одночасно утримувати S-Latch на одній сторінці.
- **Exclusive Latch (X-Latch)**: Захоплюється потоком при виконанні операцій модифікації (вставка, видалення, розщеплення чи дефрагментація). Жоден інший потік не може читати чи писати у сторінку, доки X-Latch не буде вивільно.

Співвідношення між транзакційними блокуваннями (Locks) та блокуваннями сторінок (Latches):
- **Locks (Транзакційні блокування)**: Захищають логічні дані (рядки чи таблиці) протягом всієї транзакції (`BEGIN ... COMMIT`). Зберігаються у глобальній таблиці Lock Manager.
- **Latches (Фізичні блокування сторінок)**: Захищають фізичні двійкові структури сторінки в оперативній пам'яті на дуже короткий час (мікросекунди), необхідний для читання чи запису декількох байтів.

## Управління вільними дисковими сторінками (Free Page Map / Freelist)

Коли у B-дереві відбувається вилучення елементів або злиття вузлів, деякі дискові сторінки стають повністю порожніми і вилучаються з дерева. Щоб не повертати ці блоки операційній системі (що вимагає дорогої обрізки файлу `ftruncate`), менеджер дискового простору підтримує структуру **Freelist** (список вільних сторінок):

- **Заголовок Freelist**: Зберігається у фіксованій мета-сторінці файлу бази даних (`Page 0`).
- **Стек вільних блоків**: Порожні сторінки зв'язуються у односпрямований список через поле `right_sibling_id`.
- **Перевикористання блоків**: При розщепленні вузлів виклик `new_page()` спочатку перевіряє Freelist. Якщо у списку є вільні сторінки, повертається існуюча дискова сторінка замість збільшення фізичного розміру файлу на диску.

## Порівняльний аналіз форматів сторінок у промислових СУБД

Різні промислові СУБД адаптують структуру сторінки B-дерева під власні цілі:

- **PostgreSQL (`nbtree`)**: Використовує розмір сторінки 8 КБ. Заголовок `PageHeaderData` займає 24 байти. Комірка внутрішньої сторінки містить структуру `IndexTupleData`. Для переповнених полів використовується механізм TOAST.
- **SQLite**: Використовує розмір сторінки за замовчуванням 4096 байтів. Заголовок сторінки B-дерева має змінний розмір: 8 байтів для внутрішніх сторінок і 12 байтів для листків. Слоти містять 2-байтові зсуви.
- **MySQL InnoDB**: Використовує розмір сторінки 16 КБ. Заголовок `FIL Header` займає 38 байтів. Вузли містять двоспрямовані списки сторінок `FIL_PAGE_PREV` та `FIL_PAGE_NEXT` для прискорення зворотного індексного сканування.

## Журналювання транзакцій та відновлення (WAL & LSN)

Кожна дискова сторінка B-дерева містить у заголовку 64-бітне поле `lsn` (Log Sequence Number). Це поле є фундаментальним інструментом гарантії збоєстійкості (ACID/Durability) за алгоритмом ARIES (Algorithm for Recovery and Isolation Exploiting Semantics):

1. **Правило WAL (Write-Ahead Logging)**: Перед тим як модифікована сторінка B-дерева буде записана з буферного пулу на диск, журнальний запис WAL про відповідну операцію (вставка, розщеплення чи злиття) **повинен** бути фізично скинутий на диск (`fsync`).
2. **Перевірка відновлення**: Під час стабілізації системи після аварійного вимкнення живлення менеджер відновлення порівнює `LSN` журнального запису з `LSN` у заголовку сторінки:
   - Якщо `Page.LSN >= LogRecord.LSN`, зміни вже фізично присутні у сторінці — повторне застосування (REDO) пропускається.
   - Якщо `Page.LSN < LogRecord.LSN`, операція повторно накочується (REDO) на сторінку, після чого `Page.LSN` оновлюється.

Така структура заголовків та інтерфейсу гарантує, що B-дерево залишається цілісним та відновлюваним навіть при раптових відмовах дискової підсистеми або вимкненні живлення.
