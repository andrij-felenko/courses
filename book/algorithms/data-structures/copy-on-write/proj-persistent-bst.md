# ⚙️ Персистентне дерево пошуку копіюванням шляху

<preknowlist>
- [Двійкове дерево пошуку (BST)](book:algorithms/binary-search-tree) — вузли з ключем і двома дітьми, впорядковані так, що пошук іде згори вниз одним шляхом від кореня до листка.
- [Рекурсія](book:algorithms/recursion) — функція, що викликає себе на меншій частині задачі; тут це спуск деревом від кореня до місця вставки.
- [Незмінність](book:programming/immutability) — прийом, коли створений об'єкт уже ніколи не міняють на місці, а «зміна» означає новий об'єкт поряд зі старим.
- [Підрахунок посилань](book:programming/reference-counting) — лічильник власників блока; поділити структуру — це не копіювати її, а лише додати ще один покажчик і збільшити лічильник.
</preknowlist>

**Задача.** Побудувати [дерево пошуку](book:algorithms/binary-search-tree), у якому кожна вставка чи оновлення **повертає новий корінь**, а старий корінь лишається повноцінним деревом, яким досі можна користуватись. Жодна версія не затирає попередню: маючи корінь версії, будь-коли читаємо саме її стан. І все, що лежить **осторонь** зміненого місця, дві сусідні версії мусять **ділити**, а не копіювати, — інакше кожна дрібна правка коштувала б цілого дерева. Рушій має вміти три речі: віддати новий корінь на вставку; лишити старий корінь запитуваним; і показати на числах, як мало вузлів насправді додає кожна версія.

Навіщо це в житті: історія редагувань із необмеженим відкотом, знімки стану, багатоверсійні читання в базах даних, «подорож у часі» запитом до того, як усе виглядало на певний момент, незмінні словники у функційних мовах. Скрізь там треба тримати багато майже однакових версій однієї структури — і не платити за кожну повним копіюванням.

**Ідея.** Найдивовижніше тут те, що персистентність (лат. *persistere* — залишатися) не **додає** механізму, а **прибирає** його. Якщо вузли [незмінні](book:programming/immutability) — створений вузол уже ніколи не міняється, — то звичайна [рекурсивна](book:algorithms/recursion) вставка **сама собою** копіює лише шлях. Придивімося, чому.

Рекурсія вставки спускається деревом рівно там, де пройшов би пошук: від кореня до порожнього місця, куди ляже новий ключ. Це один-єдиний шлях завдовжки з висоту дерева. На кожному кроці цього спуску ми **не пишемо** в наявний вузол (він незмінний), а будуємо **новий**: кладемо в нього той самий ключ і значення, що були, одну дитину беремо з результату рекурсивного виклику (туди, куди спускаємось), а другу дитину — **старим покажчиком** на незаймане піддерево збоку. І все. Убік від шляху не копіюється нічого: новий вузол просто дивиться туди ж, куди дивився старий. А старий корінь навіть не дізнався, що поряд виросла нова версія, — жоден його вузол не змінили.

Отже, немає окремого кроку «а тепер скопіюймо шлях». Копіювання шляху — це просто **форма звичайної рекурсії над незмінними вузлами**. Пишеш знайому вставку в дерево, тільки замість «поправити дитину на місці» щоразу «повернути новий вузол із новою дитиною» — і персистентність виходить задарма.

![Масив versions[] тримає корені всіх версій; база v0 — велике спільне ядро, а кожна наступна версія додає лише тонкий свіжий шлях O(log n) вузлів над тим самим ядром](/book/algorithms/data-structures/copy-on-write/img/version-chain.svg)
*Масив `versions[]` тримає корені всіх версій. База `v0` — велике спільне ядро, у якому живе майже все дерево в одному екземплярі. Кожна наступна версія — той самий поділений кістяк плюс тонкий свіжий шлях завдовжки O(log n), що покажчиками дивиться назад у ядро. Тому k версій коштують O(k·log n) пам'яті понад базу, а не O(k·n): у реальному замірі 20 версій над деревом на 1000 вузлів додали разом 261 вузол, а не 20 000.*

## Осердя: вставка, що повертає новий корінь

Вузол тримає ключ, значення й двох дітей — і після народження вже ніколи не міняється. Вставка приймає старий корінь і повертає новий; старий лишається на місці неторканий.

:::tabs
```python
from dataclasses import dataclass
from typing import Optional, Any

@dataclass(frozen=True)            # frozen — поля вузла вже не переприсвоїш: він незмінний
class Node:
    key:   Any
    val:   Any
    left:  Optional["Node"]
    right: Optional["Node"]

def insert(node: Optional[Node], key, val) -> Node:
    if node is None:                                       # дійшли до порожнього місця —
        return Node(key, val, None, None)                 #   новий листок

    if key < node.key:                                    # ліворуч: новий вузол,
        return Node(node.key, node.val,                   #   той самий ключ і значення,
                    insert(node.left, key, val),          #   НОВЕ ліве (рекурсія),
                    node.right)                           #   СПІЛЬНЕ праве (той самий об'єкт)

    if key > node.key:                                    # праворуч: дзеркально
        return Node(node.key, node.val,
                    node.left,                            #   СПІЛЬНЕ ліве
                    insert(node.right, key, val))         #   НОВЕ праве

    return Node(key, val, node.left, node.right)          # ключ уже є — нове значення,
                                                          #   обидві дитини спільні (оновлення)
```
```cpp
#include <memory>

// Дерево — це або порожньо (nullptr), або спільний незмінний вузол
// під підрахунком посилань. `const` усередині shared_ptr робить вузол
// недоторканним: у поділений вузол не можна записати.
template <class K, class V>
struct Node {
    K key;
    V val;
    std::shared_ptr<const Node> left;
    std::shared_ptr<const Node> right;
};

template <class K, class V>
using Tree = std::shared_ptr<const Node<K, V>>;

template <class K, class V>
Tree<K, V> insert(const Tree<K, V>& node, K key, V val) {
    if (!node)                                             // дійшли до порожнього місця —
        return std::make_shared<const Node<K, V>>(         //   новий листок
            Node<K, V>{key, val, nullptr, nullptr});

    if (key < node->key)                                   // ліворуч: новий вузол,
        return std::make_shared<const Node<K, V>>(Node<K, V>{
            node->key, node->val,                          //   той самий ключ і значення,
            insert(node->left, key, val),                  //   НОВЕ ліве (рекурсія),
            node->right});                                 //   СПІЛЬНЕ праве: копія shared_ptr = +1 до лічильника

    if (key > node->key)                                   // праворуч: дзеркально
        return std::make_shared<const Node<K, V>>(Node<K, V>{
            node->key, node->val,
            node->left,                                    //   СПІЛЬНЕ ліве
            insert(node->right, key, val)});               //   НОВЕ праве

    return std::make_shared<const Node<K, V>>(Node<K, V>{  // ключ уже є — нове значення,
        key, val, node->left, node->right});               //   обидві дитини спільні (оновлення)
}
```
:::

Серце — це три однотипні гілки. Пішли ліворуч — повертаємо новий вузол, у якого ліва дитина взялася з рекурсії (там сталася зміна), а права **лишилась старою**: у Python ми просто передали `node.right`, у C++ — скопіювали `node->right`. Пішли праворуч — усе дзеркально. Натрапили на порожнє місце — народили листок. Ключова дисципліна: у жодній гілці ми **не чіпаємо** старий вузол `node`; ми тільки читаємо його поля й будуємо з них новий. Тому старе дерево лишається точно таким, яким було.

Особливо повчальна гілка «спільне» у версії на C++. Копія `node->right` **не копіює піддерева**: `right` — це `std::shared_ptr` (англ. *shared pointer* — спільний покажчик із [підрахунком посилань](book:programming/reference-counting)), і скопіювати такий покажчик означає лише додати одиницю до лічильника власників, віддавши **той самий** вузол. Поділити піддерево коштує один приросток лічильника — байдуже, три в ньому вузли чи три мільйони. У Python те саме виходить само собою: `node.right` — це посилання, і передати його в новий вузол означає поділити той самий об'єкт, нічого не копіюючи.

А гілка «ключ уже є» — це наше **оновлення**: ключ той самий, тож ідемо не ліворуч і не праворуч, а будуємо новий вузол із новим значенням і **обома** старими дітьми (їх ділимо). Виходить, `insert` і `update` — та сама функція; різниця лише в тому, чи ми дійшли до порожнього місця, чи натрапили на наявний ключ.

## Стара версія жива: зберігаємо й питаємо

Пошук у персистентному дереві — звичайнісінький: він **тільки читає**, тож нічого не копіює й працює однаково в будь-якій версії. Різні версії — це просто різні корені, з яких стартує той самий спуск.

```python
def lookup(node, key):
    while node is not None:
        if   key < node.key: node = node.left
        elif key > node.key: node = node.right
        else:                return node.val
    return None
```

Тепер видно, як версії співіснують. Тримаємо їхні корені у звичайному списку й питаємо будь-яку:

```python
v0 = None
for k in [8, 4, 12, 2, 6, 10, 14]:          # база: збалансоване дерево на 7 вузлів
    v0 = insert(v0, k, str(k))

versions = [v0]
versions.append(insert(versions[-1], 15, "15"))   # v1 = v0 + ключ 15
versions.append(insert(versions[-1],  5,  "5"))   # v2 = v1 + ключ 5

print(lookup(versions[0], 15))   # None  — у нульовій версії п'ятнадцяти ще немає
print(lookup(versions[1], 15))   # '15'  — у першій уже є
print(lookup(versions[0],  6))   # '6'   — спільний вузол, читається з обох версій
print(lookup(versions[2],  5))   # '5'
print(lookup(versions[1],  5))   # None  — а у v1 п'ятірки ще не було
```

Вивід (реальний):
```
None
15
6
5
None
```

Найважливіший рядок — перший: у `v0` ключа 15 **немає**, хоч `v1` виросла саме з `v0`. Стара версія не «відчула» вставки, бо її коренем ніхто не писав. Це і є персистентність: минуле лишається точним, і кожен старий корінь назавжди описує рівно той стан, який був у мить, коли його зберегли.

## Спільність — на очах

Що «ділити» означає **ту саму комірку пам'яті**, а не однакову копію, легко показати прямо. Візьмімо ліве піддерево нульової та першої версій і спитаймо, чи це той самий об'єкт. Кожна мова відповідає на це своїм рідним способом — Python звіряє тотожність через `is`, C++ порівнює адреси вузлів (`get()`) і читає лічильник власників через `use_count`:

:::tabs
```python
# versions[0] і versions[1] з попереднього прикладу
print(versions[0] is versions[1])              # False — корені різні (шлях скопійовано)
print(versions[0].left is versions[1].left)    # True  — ЛІВЕ піддерево (вузол 4) СПІЛЬНЕ
print(versions[0].right is versions[1].right)  # False — праве перебудовано (там був шлях)
```
```cpp
// v0 і v1 — корені двох версій (Tree<int, std::string>)
std::cout << std::boolalpha;
std::cout << (v0.get()        == v1.get())        << '\n';  // false — корені різні (шлях скопійовано)
std::cout << (v0->left.get()  == v1->left.get())  << '\n';  // true  — ЛІВЕ піддерево (вузол 4) СПІЛЬНЕ
std::cout << (v0->right.get() == v1->right.get()) << '\n';  // false — праве перебудовано (там був шлях)

std::cout << v0->left.use_count() << '\n';                  // 2 — на вузол 4 дивляться ОБИДВА корені
```
:::

Обидві мови кажуть одне: корені `v0` і `v1` — різні об'єкти (шлях справді скопіювався), а от ліве піддерево — **той самий вузол**, на який тепер указують обидві версії. У C++ це видно навіть кількісно: `use_count` на цьому вузлі дорівнює `2`, бо на нього посилаються і старий корінь `8`, і новий `8′`. А кожен свіжий вузол шляху має лічильник `1` — його дістає лише новий корінь. Лічильник на «шві» між новим і старим — точний вимірювач того, де закінчилося копіювання й почалося спільне.

## Скільки коштує версія

Порахуймо додані вузли на конкретному дереві. База — збалансована сімка, яку ми будували вище:

```
            8
          /   \
         4     12
        / \   /  \
       2   6 10   14

insert(v0, 15):   15 > 8  → праворуч, у 12
                  15 > 12 → праворуч, у 14
                  15 > 14 → праворуч, порожньо → новий листок 15

скопійовано (свіжі):   8′, 12′, 14′  +  новий листок 15   =  4 вузли
поділено (не копіюємо): усе ліве піддерево 8′ — вузли 4, 2, 6  +  листок 10
```

Порахуймо баланс. Старе дерево — 7 вузлів, лишилось цілим. Нове — 8 вузлів, з яких **4 свіжі** (шлях `8′→12′→14′` і листок), а решта 4 (піддерево `4` та листок `10`) — спільні зі старим. Дві версії разом коштують 7 + 4 = 11 вузлів, а не 14: три вузли лівого піддерева ми поділили. Кількість свіжих вузлів дорівнює довжині шляху — приблизно висоті дерева плюс новий листок, тобто **O(log n)** у збалансованому дереві.

Щоб побачити, що це справді логарифм, а не прихований лінійний ріст, зробимо просте: обгорнемо народження вузла в лічильник і поставимо тисячі випадкових вставок. Виходить така картина (усе виміряно, `avg_fresh` — середнє число свіжих вузлів на одну вставку):

```
      n     свіжих/версію     log₂ n     повна копія (=n)
    100          6.96          6.64            100
  1 000         11.96          9.97          1 000
 10 000         16.67         13.29         10 000
100 000         20.51         16.61        100 000
```

Свіжих вузлів — це невелика стала, помножена на log₂n (тут близько 1.2·log₂n): збільшуємо дерево в тисячу разів — плата за версію росте всього втричі-вчетверо. Тим часом повне копіювання (правий стовпчик) росте прямо пропорційно n. На дереві в сто тисяч вузлів персистентна версія коштує ~20 вузлів проти 100 000 — у п'ять тисяч разів дешевше.

І накопичення так само дешеве. Двадцять послідовних вставок у дерево на 1000 вузлів дали разом лише **261 новий вузол** — усі двадцять версій живі й запитувані, а коштували вони стільки, скільки чверть одного дерева. Наївне «щоразу копіюй усе» витратило б 20 × 1000 = 20 000 вузлів. Ось звідки береться формула O(k·log n) на k версій: кожна додає лише свій тонкий шлях, а величезне спільне ядро всі ділять.

## Складність

Складемо все докупи. Позначмо висоту дерева h, кількість вузлів n, число збережених версій k:

```
одна вставка / оновлення :  O(h) нових вузлів,  O(h) часу
запит у будь-якій версії :  O(h) часу,  0 нових вузлів (лише читання)
k збережених версій      :  O(k · h) пам'яті понад базове дерево
```

Усе тримається на висоті h. У **збалансованому** дереві h = O(log n), тож вставка й запит — [O(log n)](book:algorithms/asymptotic-complexity), а k версій коштують O(k·log n). Але сам по собі наш код дерево **не балансує**, і тут криється пастка: якщо ключі приходять уже відсортованими, дерево вироджується в довгий ланцюг заввишки h = n, і кожна «версія» копіює половину дерева. Виміряно на відсортованому вході:

```
n =   100 :  свіжих/версію = 50.5
n = 1 000 :  свіжих/версію = 500.5     ← ~n/2, тобто O(n) на версію!
```

Логарифм зник, лишилась лінія. Тому по-справжньому персистентні словники будують не на голому BST, а на самобалансівному [дереві пошуку](book:algorithms/binary-search-tree) — червоно-чорному чи балансованому за вагою, — де обертання теж роблять копіюванням шляху. Балансування гарантує h = O(log n) на будь-якому вході; принцип копіювання шляху при цьому не міняється ані на йоту — просто шлях, який копіюють, лишається коротким.

## Пастки

**Спільний вузол — недоторканний.** Уся коректність тримається на одному правилі: якщо вузол ділять кілька версій, у нього не можна писати на місці, бо запис протече в чужу версію. Наш код цього уникає не перевіркою, а конструкцією — вставка **ніколи** не пише в наявний вузол, а лише будує нові. `frozen=True` у Python і `const` усередині `shared_ptr<const Node>` у C++ перетворюють це правило на інваріант, за яким стежить сама мова: спробуєш записати в поділений вузол — не скомпілюється (C++) чи впаде виняток (Python). Свідомо лишити вузол мутабельним заради «оптимізації» — найпряміший шлях зіпсувати минуле.

**Копіюється й значення, не лише вузол.** У версії на C++ кожен новий вузол на шляху копіює старе значення (`node->val`), хоч воно й не змінилось. Для чисел це дрібниця, а для великого значення — зайва робота на кожному з O(log n) вузлів шляху. Лік — той самий прийом, що й для піддерев: тримати значення за спільним покажчиком (`shared_ptr<const V>`), і тоді копія знову стає лише приростком лічильника, а не копією полів. У Python ця проблема не виникає: `node.val` і так посилання, ділиться безкоштовно.

**Старе не звільняється само.** Поки живий бодай один корінь, що дістає вузол, цей вузол не звільнити. Тримати геть усі версії вічно — означає тримати всі їхні вузли: пам'ять росте як O(k·log n) і не спадає. Щойно версія більше не потрібна, її корінь треба **відпустити** — тоді лічильники посилань на її ексклюзивні вузли впадуть до нуля і пам'ять звільниться (у C++ — коли останній `shared_ptr` на вузол зникає; у Python — [збиранням сміття](book:programming/garbage-collection)). Персистентність не скасовує плати за пам'ять, лише розтягує її в часі.

**Глибина рекурсії.** Наша вставка рекурсивна, тож глибина стека дорівнює висоті дерева. У збалансованому дереві це O(log n) — байдуже. У виродженому дереві на мільйон вузлів рекурсія в мільйон рівнів переповнить стек. Ще один доказ, що на реальних обсягах під персистентність беруть балансоване дерево, а не голе BST.

**Видалення — так само, лише хитріше.** Ми показали вставку й оновлення; видалення підкоряється тому самому принципу — скопіювати шлях до вузла й перечепити покажчики, — але має зайвий клопіт: коли видаляють вузол із двома дітьми, його заміняють наступним за порядком ключем, а це другий шлях, який теж доводиться копіювати. Принцип не змінюється: старе дерево лишається цілим, нове ділить із ним усе, крім O(log n) свіжих вузлів на обох шляхах.

За всіма цими деталями — одна проста думка. Незмінний вузол не можна зіпсувати, тож його безпечно ділити скільки завгодно; а «змінити» дерево означає лише збудувати короткий новий шлях до місця правки й дозволити йому дивитися на старе, спільне все інше. Минуле не копіюють, щоб зберегти, — його просто ніколи не затирають.
