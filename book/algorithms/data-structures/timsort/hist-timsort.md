# 📜 Історія народження Timsort: від патчу до CPython до стандарту мов програмування

Коли програміст викликає стандартну функцію сортування у високорівневій мові, він очікує передбачуваної поведінки: збереження порядку еквівалентних записів, лінійної швидкості на вже впорядкованих масивах і відсутності несподіваних падінь через вичерпання пам'яті. У класичних підручниках з алгоритмів сортування розглядалося переважно як математична абстракція над масивом випадкових чисел. Проте в інженерній практиці більшість даних надходить із систем уже частково впорядкованими: логи за часовими мітками, таблиці баз даних після багаторівневих фільтрацій, конкатеновані списки чи черги подій. Ця вставка розкриває історію створення адаптивного алгоритму Timsort Тімом Пітерсом у 2002 році, його тріумфальну інтеграцію у фундаментальні платформи Java, Rust та Android, а також драматичне виявлення прихованого дефекту в інваріантах стека через тринадцять років за допомогою формальної верифікації.

## Проблема мови Python: криза samplesort у 2002 році

На початку 2000-х років інтерпретатор CPython версії 2.2 використовував для впорядкування списків алгоритм `samplesort` — варіацію швидкого сортування (Quicksort), яка намагалася обирати якісні опорні елементи через попереднє семплювання. Для випадкових масивів чисел цей підхід демонстрував прийнятні результати. Проте мова Python дедалі ширше застосовувалася для обробки реальних бізнес-даних, вебсерверів та аналізу структурованих записів, де виявилися дві критичні вади `samplesort`:

1. **Відсутність стійкості (stability):** У мовах загального призначення розробники постійно застосовують сортування за кількома ключами (наприклад, спершу впорядкувати таблицю за містом, а потім за прізвищем клієнта). Алгоритм `samplesort` не гарантував збереження відносного порядку записів з однаковими ключами. Розробникам доводилося або конструювати складні складені ключі (tuple sorting), або писати власні повільні обгортки на чистому Python.
2. **Сліпота до природної впорядкованості:** Якщо користувач передавав у `list.sort()` масив із мільйона записів, який уже був відсортований або складався з двох склеєних відсортованих списків, `samplesort` виконував повний обсяг порівнянь порядку `O(N log N)` та генерував масу зайвих перестановок у пам'яті.

Американський інженер і ключовий розробник CPython Тім Пітерс (Tim Peters) поставив за мету створити сортувальний механізм, оптимізований саме під реальні патерни інженерних даних.

## Інтелектуальні корені: ідея природних серій Пітера Макілроя

Створюючи новий алгоритм, Тім Пітерс не винаходив абсолютно всі концепції з нуля. Він спирався на фундаментальну наукову працю Пітера Макілроя (Peter McIlroy) 1993 року під назвою *«Optimistic Sorting and Information Theoretic Complexity»* («Оптимістичне сортування та інформаційно-теоретична складність»).

Макілрой досліджував поведінку алгоритмів сортування злиттям, які не дробили масив штучно навпіл на кожному кроці, а шукали в ньому вже наявні відсортовані послідовності — так звані «природні серії» (natural runs). Макілрой довів, що якщо масив містить серії різної довжини, алгоритм може досягати теоретичної нижньої межі ентропії впорядкування, якщо зливатиме серії за принципом побудови дерева Гаффмана або підтримуватиме строгий баланс розмірів серій.

Пітерс узяв математичну концепцію природних серій Макілроя та трансформував її у високоефективний інженерний алгоритм. Він додав кілька вирішальних практичних інновацій:
- **Інверсія спадних відрізків:** Розпізнавання не лише неспадних, а й строго спадних послідовностей із миттєвим розвертанням на місці через два вказівники.
- **Підлога довжини через `minrun`:** Досортовування занадто коротких природних серій за допомогою швидкого бінарного сортування вставками (Binary Insertion Sort), що радикально зменшило накладні витрати на малих масштабах.
- **Режим галопу (Galloping mode):** Механіка експоненційного стрибкового пошуку для миттєвого пропуску великих блоків елементів, коли одна серія домінує над іншою.

У липні 2002 року Тім Пітерс представив свою реалізацію у вихідному коді CPython 2.3. Алгоритм отримав неофіційну назву **Timsort** і продемонстрував безпрецедентну продуктивність: на частково впорядкованих списках час роботи скоротився у 5–10 разів, а на випадкових даних алгоритм не поступався швидкому сортуванню, забезпечуючи при цьому абсолютну стійкість.

## Тріумфальна експансія: Java, Android, Rust та вебрушії

Упродовж наступних кількох років Timsort залишався внутрішнім надбанням спільноти Python. Проте у 2009 році відомий архітектор мови Java та автор бестселера *Effective Java* Джошуа Блох (Joshua Bloch) звернув увагу на виняткову ефективність алгоритму Пітерса.

До версії Java 6 включно метод `Arrays.sort(Object[])` для масивів посилальних типів у стандартній бібліотеці Java використовував класичне сортування злиттям (клас `java.util.Arrays`). Ця стара реалізація завжди виділяла повний допоміжний масив розміром `N` і не вміла адаптуватися до наявного порядку елементів. Джошуа Блох здійснив портування алгоритму Тіма Пітерса мовою Java та інтегрував класи `java.util.TimSort` і `java.util.ComparableTimSort` у репозиторій OpenJDK 7. Одночасно Timsort став стандартним алгоритмом сортування об'єктів у фреймворку Android (Android Open Source Project).

Успіх у Java викликав ланцюгову реакцію в індустрії. Timsort було стандартизовано або адаптовано у таких системах:
- **Rust:** Стандартна бібліотека Rust у модулі `core::slice` реалізувала функцію `slice::sort()` (та `sort_by()`) на основі модифікованого Timsort, що вимагав стабільного сортування елементів.
- **V8 (Google Chrome / Node.js):** Довгий час рушій V8 використовував Timsort для методу `Array.prototype.sort()` для стабілізації сортування великих масивів.
- **Swift:** Мова від Apple інтегрувала принципи Timsort для реалізації стандартного методу `sort()` для колекцій із довільним доступом.

## Тринадцять років прихованої бомби: викриття 2015 року

У 2015 році дослідницька група з Європи — Стейн де Хау (Stijn de Gouw, Лейденський університет), Юрріан Рот (Jurriaan Rot), Франк де Бур (Frank S. de Boer), Річард Бубель (Richard Bubel) та Райнер Хенле (Reiner Hähnle, Технічний університет Дармштадта) — проводила дослідження з формальної верифікації коду стандартної бібліотеки Java.

Метою науковців була математична перевірка коректності класу `java.util.TimSort.java` за допомогою інструмента автоматизованого доведення теорем **KeY** (формальний верифікатор для мови Java). Верифікатор KeY перевіряє, чи кожен метод задовольняє свої формальні перед- та післяумови для будь-яких можливих вхідних даних.

Під час аналізу процедури підтримання інваріантів стека серій система KeY несподівано відмовилася довести відсутність виходу за межі масиву (Array Out Of Bounds).

### Суть дефекту в інваріантах

Для збереження висоти стека логарифмічною та запобігання переповненню Тім Пітерс у 2002 році заклав правило, яке перевірялося для трьох верхніх серій на стеку `A`, `B`, `C` (де `A` — верхівка стека, `B` — під нею, `C` — під `B`):

```
1. len(C) > len(B) + len(A)
2. len(B) > len(A)
```

Джошуа Блох у коді Java виділив під стек фіксований масив розміром у 40 елементів. Виходячи з властивості зростання Фібоначчі, сорока елементів стека мало з надлишком вистачити для впорядкування будь-якого масиву розміром до `2^31 - 1` елементів (максимальний розмір масиву в Java), оскільки сорокове число Фібоначчі перевищує `1.6 × 10^8`.

Проте дослідники з Лейдена математично довели, що правила Пітерса розглядають **лише три верхні серії**, ігноруючи четверту серію `D` (`stack[top-3]`). За певної штучно сформованої послідовності довжин серій порушення інваріанта на четвертому рівні не запускало вчасне злиття на верхівці стека. У результаті стек починав розростатися швидше, ніж передбачала формула Фібоначчі.

Науковці згенерували спеціальний вхідний масив із 67 108 864 елементів, який під час виконання `Arrays.sort()` у Java 7 та 8 неминуче викликав фатальний збій:

```
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: 40
    at java.util.TimSort.pushRun(TimSort.java:725)
    at java.util.TimSort.doSort(TimSort.java:234)
    at java.util.Arrays.sort(Arrays.java:792)
```

Дефект існував непоміченим у коді CPython упродовж 13 років, а в коді Java — упродовж 6 років, оскільки для випадкових або типових даних глибина стека рідко досягала навіть 20–25 рівнів.

### Виправлення дефекту у глобальних екосистемах

Після публікації звіту де Хау та колег у лютому 2015 року спільноти розробників негайно розробили та впровадили виправлення:
1. **Розширення інваріанта стека (4-run invariant):** Алгоритм перевірки злиття `mergeCollapse` було модифіковано так, щоб перевіряти стан не трьох, а чотирьох верхніх елементів стека:
   - `len(D) > len(C) + len(B)`
   - `len(C) > len(B) + len(A)`
   - `len(B) > len(A)`
2. **Оновлення CPython:** Дефект було зареєстровано як Python Issue #23515 і виправлено у вихідному файлі `Objects/listobject.c` у версіях CPython 2.7.10, 3.4.4 та 3.5. Тім Пітерс особисто брав участь в обговоренні патчу в розсилці python-dev, підтвердивши точність висновків європейських математиків.
3. **Оновлення OpenJDK:** Корпорація Oracle випустила офіційний патч JDK-8072924 для Java 8u60 та Java 9, переглянувши таблицю максимальних розмірів стека для 32-бітних і 64-бітних діапазонів індексів.
4. **Оновлення Android та Rust:** Аналогічні виправлення було інтегровано у кодові бази Android Open Source Project та стандартну бібліотеку Rust (`alloc::slice::merge_sort`).

## Вплив на сучасний дизайн алгоритмів

Спадщина Timsort справила фундаментальний вплив на проектування стандартних бібліотек наступних поколінь мов програмування:

- **Поява Powersort:** У 2018 році німецький дослідник Себастьян Вільд (Sebastian Wild) разом із колегами запропонував алгоритм Powersort, який замість евристичних інваріантів стека Пітерса використовує метод майже оптимальних двійкових дерев пошуку (node powers). Powersort гарантує мінімальну кількість порівнянь для довільних комбінацій серій і був офіційно прийнятий у CPython 3.11 у 2022 році як прямий спадкоємець оригінального Timsort.
- **Дискусії в мовах Go та C++:** Розробники стандартної бібліотеки Go тривалий час обирали між Timsort та швидким сортуванням із захистом від найгіршого випадку (Pattern-Defeating Quicksort / pdqsort). Якщо для задач із вимогою абсолютної стійкості Timsort залишається еталоном, то для нестійкого сортування примітивних типів сучасні мови надають перевагу алгоритмам, що не потребують виділення додаткової динамічної пам'яті під буфер злиття.

Цей історичний шлях — від локального патчу для інтерпретатора скриптової мови до світового стандарту обробки даних та об'єкта формальної верифікації — став класичним прецедентом в історії комп'ютерних наук. Він продемонстрував, що перемога алгоритму в реальному світі визначається не лише теоретичною оцінкою у найгіршому випадку, а насамперед глибоким розумінням природи даних, з якими щодня працюють інженерні системи.
