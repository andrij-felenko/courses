# 📋 Специфікація інтерфейсу та контракти некриптографічних хеш-функцій

Некриптографічна хеш-функція надає чітко визначений програмний контракт для обчислення фіксованого хеш-значення (32, 64 або 128 бітів) з довільної послідовності байтів у пам'яті. На відміну від криптографічних алгоритмів, де інтерфейс передбачає підтримку потокового оновлення стану (`init`, `update`, `final`) для обробки гігабайтних файлів за допомогою невеликого фіксованого буфера, некриптографічні хеш-функції оптимізуються під точкову обробку блоку пам’яті за один виклик (zero-allocation single-shot call). 

Ця специфікація визначає канонічний C та C++ API для некриптографічних хеш-функцій, розбирає параметри випробувань у тестових сюїтах SMHasher та SMHasher3, деталізує вимоги до порядку байтів (endianness), аналізує вирівнювання пам'яті на різних системних архітектурах та дає правила інтеграції хешів у високонавантажені структури даних.

## Сигнатура контракту та типи даних

Стандартний C та C++ API для некриптографічного хешування задовольняє вимоги точкового виклику без виконання системних викликів або виділення динамічної пам'яті в купі (heap allocation).

### Канонічні сигнатури інтерфейсу

:::tabs
```c
/* 32-бітний C-інтерфейс хешування */
uint32_t hash32_fn(const void *input, size_t len, uint32_t seed);

/* 64-бітний C-інтерфейс хешування */
uint64_t hash64_fn(const void *input, size_t len, uint64_t seed);
```
```cpp
// Ідіоматичний C++20 інтерфейс хешування
[[nodiscard]] std::uint32_t hash32_fn(std::span<const std::uint8_t> input, std::uint32_t seed = 0) noexcept;

[[nodiscard]] std::uint64_t hash64_fn(std::span<const std::uint8_t> input, std::uint64_t seed = 0) noexcept;
```
:::

| Параметр | Тип C / C++ | Опис та семантика контракту |
| :--- | :--- | :--- |
| `input` / `data` | `const void*` або `std::span<const uint8_t>` | Вказівник на перший байт вхідного масиву пам'яті. Не може бути `NULL` (якщо `len > 0`). При `len == 0` може бути вказівником на порожній буфер. |
| `len` / `length` | `size_t` | Довжина вхідного блоку в байтах. Значення `0` є абсолютно допустимим і повертає хеш-код порожнього стану на основі `seed`. |
| `seed` | `uint32_t` або `uint64_t` | Початкове значення акумулятора. Використовується для рандомізації хеш-таблиць та захисту від колізійних атак. |
| `return` | `uint32_t`, `uint64_t` або `Hash128Value` | Обчислене значення хешу. Виконання має бути строго детермінованим для того самого вводу та `seed`. |

### Структура 128-бітного хеш-значення

Для 128-бітних алгоритмів (наприклад, MurmurHash3_x64_128, CityHash128 або XXH128) вихідне значення повертається у вигляді структури, складеної з двох 64-бітних беззнакових цілих чисел:

:::tabs
```c
typedef struct {
    uint64_t low64;  /* Молодші 64 біти хешу */
    uint64_t high64; /* Старші 64 біти хешу */
} Hash128Value;

/* 128-бітний C-інтерфейс хешування */
Hash128Value hash128_fn(const void *input, size_t len, uint64_t seed);
```
```cpp
namespace core::hash {

struct alignas(16) Hash128 {
    std::uint64_t low{0};
    std::uint64_t high{0};

    [[nodiscard]] constexpr auto operator<=>(const Hash128&) const noexcept = default;
};

[[nodiscard]] Hash128 hash128_fn(std::span<const std::uint8_t> input, std::uint64_t seed = 0) noexcept;

} // namespace core::hash
```
:::

## Вимоги до вирівнювання пам'яті (Alignment Preconditions)

Поведінка невирівняного читання пам'яті (unaligned memory access) суттєво відрізняється залежно від архітектури процесора:

1. **Архітектура x86 / x86-64 (Intel / AMD):** Підтримує апаратне невирівняне читання без виключень. Сучасні микроархітектури (Intel Raptor Lake, AMD Zen 4) виконують читання 64-бітних цілих чисел за невирівняною адресою фактично без покарання за швидкістю, якщо межа читання не перетинає межу кеш-лінії 64 байти. Якщо читання перетинає межу кеш-лінії, виникає невелике падіння продуктивності (1-2 такти).
2. **Архітектура ARM64 (AArch64):** Підтримує невирівняне читання на рівні більшості інструкцій `LDR`/`STR`, проте вимагає включення підтримки на рівні операційної системи (прапор `SCTLR_EL1.A`). За замовчуванням Linux на ARM64 обробляє невирівняний доступ прозоро.
3. **Архітектура ARMv7 / RISC-V / MIPS:** Багато мікроконтролерів (наприклад, ARM Cortex-M0/M3) та строгих процесорів не підтримують невирівняний доступ на апаратному рівні. Спроба прочитати 64-бітне число з адреси, не кратної 8 байтам, викликає апаратний збій вирівнювання (`BUS_ERROR` / `HardFault`).

Реалізація некриптографічного хешу повинна абстрагувати невирівняний доступ через системну функцію `memcpy` або через умовну компіляцію для платформ із підтримкою `UNALIGNED_READ`. Виклик `memcpy` є повністю портативним, не порушує strict aliasing та інлайниться компілятором у скалярні інструкції читання.

## Порядок байтів (Endianness sensitivity)

Некриптографічні хеш-функції, що обробляють дані 64-бітними блоками (`uint64_t`), інтерпретують послідовність байтів у пам'яті згідно з порядком байтів архітектури ЦПУ:

* **Little-Endian (LE):** Байт за адресою `p` стає молодшим байтом `(p[0] << 0)`, байт за адресою `p+7` стає старшим байтом `(p[7] << 56)`. За замовчуванням x86-64 та ARM64 працюють у режимі Little-Endian.
* **Big-Endian (BE):** Байт за адресою `p` стає старшим байтом `(p[0] << 56)`. Використовується на мейнфреймах (IBM z/Architecture) та деяких мережевих процесорах.

Якщо обчислити хеш від байтового масиву `"HELLO_WORLD"` на Little-Endian системі, а потім на Big-Endian системі без спеціальної корекції порядку байтів, отримані хеш-коди будуть **різними**.

Для забезпечення крос-платформеної сумісності (наприклад, у розподілених базах даних чи мережевих протоколах) специфікація контракту вимагає використання функції байтового розвертання (`bswap64`) на Big-Endian системах:

:::tabs
```c
#if defined(__BYTE_ORDER__) && __BYTE_ORDER__ == __ORDER_BIG_ENDIAN__
#  define SWAP64(x) __builtin_bswap64(x)
#else
#  define SWAP64(x) (x)
#endif
```
```cpp
#include <bit>

template<typename T>
[[nodiscard]] constexpr T normalize_endian(T val) noexcept {
    if constexpr (std::endian::native == std::endian::big) {
        return std::byteswap(val);
    }
    return val;
}
```
:::

## Тестова сюїта SMHasher / SMHasher3

Сюїта SMHasher (розроблена Остіном Епплбі) та її сучасний форк SMHasher3 є розширеним набором випробувань для перевірки некриптографічних хеш-функцій. Для визнання хеш-функції придатною до використання вона повинна пройти 14 категорій тестів із нульовою кількістю дефектів (0 failures).

### Опис випробувань SMHasher

1. **Sanity Test:** Обчислює контрольні хеш-суми для набору визначених послідовностей різної довжини й порівнює їх із еталоном. Перевіряє сумісність та детермінованість на різних компіляторах та платформах.
2. **Avalanche Test (Лавинний тест):** Почергово інвертує кожен з `N` бітів вхідного масиву і вимірює ймовірність зміни кожного з `M` бітів вихідного хешу. Відхилення ймовірності `P` від значення 0.5 більше ніж на `0.1%` є дефектом.
3. **BIC (Bit Independence Criterion):** Перевіряє, чи є зміни у парах вихідних бітів `(j, l)` незалежними при зміні вхідного біта `i`. Вимірює p-значення статистичної кореляції.
4. **Differential Test:** Згенеровує мільярди пар ключів із малим значенням дифференціала `X1 ^ X2` та перевіряє, чи не утворюються колізійні хеш-різниці `H(X1) ^ H(X2) == 0`.
5. **Sparse Keys / Low-bit Keys:** Подає на вхід ключі, у яких більшість бітів є нульовими або одиничними (наприклад, бітові маски, прапорці, адреси пам'яті).
6. **Cyclic & Permutation Tests:** Подає послідовності анаграм та циклічних зсувів байтів (наприклад, `"abcde"`, `"bcdea"`, `"cdeab"`), перевіряючи чутливість алгоритму до порядку символів.
7. **Window / High-Bit Tests:** Подає ковзні вікна бітів через буфер великого розміру.
8. **Alignment Test:** Перевіряє, чи змінюється результат обчислення хешу при зміщенні вказівника на вхідні дані на 1, 2, 3... 7 байтів відносно межі вирівнювання.
9. **Speed / Throughput Benchmark:** Вимірює пропускну здатність алгоритму у такт/байт (cycles per byte, cpb) та Гбайт/с на ключах розміром від 1 байта до 256 кілобайтів.

## Гарантії контракту та безпека у промислових системах

1. **Нестабільність між версіями (Cross-version instability):** Некриптографічні хеш-функції створюються для максимальної швидкості в пам'яті, а не для стійкого збереження на диску. Автори бібліотек (xxHash, FarmHash, Abseil) залишають за собою право змінювати внутрішній алгоритм та вихідні значення між мажорними релізами. Зберігати некриптографічний хеш у базах даних чи файлових індексах між оновленнями ПЗ суворо заборонено.
2. **Рандомізація за допомогою Seed:** У некриптографічних сервісах передача `seed = 0` є стандартним значенням за замовчуванням. Проте для запобігання атакам класу HashDoS у веб-додатках `seed` повинен ініціалізуватися випадковим числом із системного джерела ентропії (`/dev/urandom` або `getrandom()`) під час запуску кожного нового процесу.
3. **Обробка порожніх вхідних масивів (`len == 0`):** Передача `len = 0` є легальним викликом. Функція повинна повернути обчислений хеш початкового акумулятора стану (включаючи `seed` та фіналізатор `fmix`) без спроби розіменування вказівника `input`.
