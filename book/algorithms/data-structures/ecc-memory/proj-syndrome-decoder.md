# ⚙️ Синдромний декодер: робочий SEC/SECDED-кодек для 64-бітового слова

Уявімо, що ми пишемо шар пам'яті, якому не можна тихо збрехати. Назовні він дає дві прості операції: `encode` перетворює 64 біти даних на ширше кодове слово, готове лягти в комірки; `decode` бере прочитане слово назад і повертає **дані плюс вирок** — «ціле», «був один биток, я його полагодив» або «зіпсовано двома, лагодити не берусь». Уся цінність — у третьому рядку: сховище, яке відмовляється видати правдоподібне, але хибне число, коштує безмежно більше за те, що мовчки віддає сміття.

Це і є задача синдромного декодера. Теорію — чому контрольні біти сидять на степенях двійки й чому [код Геммінга](book:communications/hamming-code) знаходить биток за один крок — приймемо як відому й зосередимося на іншому: як перетворити її на **робочий C**, який ганяється на кожному читанні пам'яті, тримається на бітових операціях і ніде не бреше. C тут не примха: це системний гарячий шлях, де слово — це регістр, а «порахувати парність» — це XOR, тож будь-яка вища мова лише сховала б від нас саме те, що ми хочемо бачити.

## Ідея: слово, що саме називає свій биток

Один прийом робить увесь кодек коротким. **Синдром — це XOR номерів усіх позицій, де в слові стоїть одиниця.** Порахуймо цю суму для цілого кодового слова — вона дорівнює нулю (ми навмисне так виставимо контрольні біти). Тепер нехай перекинеться біт на позиції p. У сумі рівно на цю одну позицію змінюється склад доданків — число p то з'являється, то зникає, — і синдром стає точно **p**. Слово буквально вимовляє номер свого битка.

Чому XOR номерів тотожний тим самим k контрольним парностям, про які зазвичай говорять? Гляньмо на розряд j цієї суми. Він дорівнює XOR-у молодшого внеску кожного доданка в розряд j — тобто XOR-у бітів на всіх позиціях, у чиєму **двійковому номері стоїть розряд j**. А це рівно той набір позицій, за яким стежить контрольний біт на позиції 2ʲ. Отже «XOR номерів» і «k окремих контрольних парностей» — те саме число, записане двома способами. Перший запис коротший у коді; другий — той, що лягає в залізо XOR-деревами. Ми скористаємося першим, а наприкінці побачимо, чому кремній обирає другий.

> 🔧 **Навіщо це.** Тотожність «синдром = XOR номерів одиниць» — не фокус для краси, а те, що робить локалізацію битка операцією **сталого часу без пошуку**. Наївний декодер мусив би питати «на яке з 2⁶⁴ законних слів це найбільше схоже?» — таблиця, якої не існує. Синдром відповідає одним числом, і це число *вже є* адресою біта, який треба перекинути.

## Розкладка: 72 біти й де що лежить

Порахуймо розміри чесно. Щоб синдром міг назвати кожну позицію серед n = 64 бітів даних, потрібно k контрольних бітів, де 2ᵏ ≥ n + k + 1; для 64 це дає k = 7. Сім контролів плюс 64 дані — 71 позиція, і цей код виправляє **один** биток. Щоб іще й **виявляти два** — розрізняти виправну одиничну помилку й невиправну подвійну, — додамо один біт **загальної парності** над усім словом. Разом 72 біти: саме та дев'ята мікросхема на серверному модулі й шина 72 замість 64.

![Мапа 72-бітового слова: позиція 0 — загальна парність, степені двійки 1,2,4,8,16,32,64 — контрольні, решта 64 — дані](/book/algorithms/data-structures/ecc-memory/img/layout.svg)
*Де що лежить у 72-бітовому слові. Позиції нумеруємо з нуля. Позиція 0 (зелена) — біт загальної парності над усім словом, той, що додає до SEC ще й DED. Позиції — степені двійки 1, 2, 4, 8, 16, 32, 64 (сині) — сім контрольних бітів коду Геммінга: кожен відповідає за свій розряд синдрому. Решта 64 клітинки (білі) — біти даних 0…63, розкладені по позиціях за зростанням. Саме через це чергування «контроль на степенях двійки, дані поміж» кодування не просто дописує контроль збоку, а **вплітає** його в слово — і код мусить розкладати й збирати дані по несуміжних позиціях.*

Тримати 72-бітове слово будемо в `__uint128_t`: біт i контейнера — це позиція i. Це розширення GCC/Clang, звичне на 64-бітних цілях; де його немає, слово розкладають на дві `uint64_t`-половини (до цієї деталі повернемося серед пасток — вона не косметична).

## Код: кодування, синдром, виправлення

Почнімо з розкладки в коді. Контрольна позиція — це степінь двійки; одна перевірка ловить усі сім:

```c
#include <stdint.h>
#include <stdio.h>

typedef __uint128_t word72;         /* 72-бітове кодове слово: біт i = позиція i */

enum { N = 72, HAM = 71 };          /* N — уся ширина; 1..HAM — код Геммінга */

/* Позиція контрольна ⟺ це степінь двійки (1,2,4,8,16,32,64). */
static int is_check(unsigned p) {
    return p != 0 && (p & (p - 1)) == 0;   /* рівно один біт у номері */
}
```

Тепер два примітиви, на яких тримається все. Перший — синдром як XOR номерів одиниць; другий — загальна парність усього слова. Обидва навмисно написані «в лоб», циклом: так видно, *що саме* рахується. У реальному коді ці два рядки замінює `__builtin_parityll` або, у залізі, XOR-дерево — про це наприкінці.

```c
/* Синдром: XOR номерів усіх позицій, де стоїть 1.
   Для цілого слова = 0; для одного битка = номер битої позиції. */
static unsigned syndrome(word72 cw) {
    unsigned s = 0;
    for (unsigned p = 1; p < N; ++p)        /* позиція 0 (=0) у XOR нічого не додає */
        if ((cw >> p) & 1) s ^= p;
    return s;
}

/* Загальна парність: XOR усіх 72 бітів (0 = парна кількість одиниць). */
static unsigned parity(word72 cw) {
    unsigned g = 0;
    for (unsigned p = 0; p < N; ++p)
        g ^= (unsigned)((cw >> p) & 1);
    return g;
}
```

Кодування робить три речі за чергою: розкладає 64 біти даних по не-контрольних позиціях, виставляє контрольні біти так, щоб синдром став нулем, і накриває все загальною парністю.

```c
word72 ecc_encode(uint64_t data) {
    word72 cw = 0;

    /* 1. Розкласти дані: біти 0..63 → не-контрольні позиції 1..71 за зростанням. */
    unsigned b = 0;
    for (unsigned p = 1; p <= HAM; ++p)
        if (!is_check(p)) {
            cw |= (word72)((data >> b) & 1) << p;
            ++b;                            /* рівно 64 таких позиції */
        }

    /* 2. Контрольні біти. Синдром слова з самих даних — це число t;
       його розряди — це рівно контрольні біти, кожен на своїй позиції 2^j.
       Виставивши їх, робимо синдром цілого слова нулем: t ⊕ t = 0. */
    unsigned t = syndrome(cw);
    for (unsigned j = 0; j < 7; ++j)
        if ((t >> j) & 1) cw |= (word72)1 << (1u << j);   /* позиція 2^j */

    /* 3. Біт загальної парності на позицію 0 — робить вагу всього слова парною. */
    cw |= (word72)parity(cw) << 0;
    return cw;
}
```

Крок 2 — уся хитрість кодування в двох рядках, тож варто спинитися. `t` — це синдром слова, у якому лежать самі дані, а всі контрольні позиції ще нульові. Ми хочемо, щоб у **готовому** слові синдром був нуль. Кожен контрольний біт сидить на позиції 2ʲ, тож увімкнути його — це додати в XOR номерів рівно число 2ʲ. Виставмо контрольні біти так, щоб їхнє спільне «число» дорівнювало t: тоді синдром стане t ⊕ t = 0. А оскільки розряд j числа t каже, ставити біт 2ʲ чи ні, — увесь крок і є той цикл на сім ітерацій. Жодних матриць, жодних таблиць кодування.

Тепер декодування — серце теми. Дивимося на дві величини й розводимо три випадки.

![Рішення декодера за синдромом s і загальною парністю g: ціле, виправити позицію s, або подвійна помилка — тривога](/book/algorithms/data-structures/ecc-memory/img/decode.svg)
*Уся логіка SECDED — у трьох рядках. Синдром s каже, ЯКИЙ біт битий; загальна парність g каже, СКІЛЬКИ бітів перекинуто (за парністю). s = 0 і g = 0 — слово ціле. g = 1 (непарна вага) — рівно одна помилка, і s указує на неї: перекинути й віддати. g = 0, але s ≠ 0 — парна кількість збоїв, тобто щонайменше два: локалізувати вже не можна, тож єдина чесна дія — тривога, а не сліпе виправлення. Саме останній рядок відрізняє SECDED від голого Геммінга.*

```c
typedef enum { ECC_OK, ECC_CORRECTED, ECC_DOUBLE } ecc_status;
typedef struct { uint64_t data; ecc_status status; unsigned pos; } ecc_result;

/* Зібрати 64 біти даних із не-контрольних позицій 1..71 назад у uint64_t. */
static uint64_t gather(word72 cw) {
    uint64_t data = 0;
    unsigned b = 0;
    for (unsigned p = 1; p <= HAM; ++p)
        if (!is_check(p)) {
            data |= (uint64_t)((cw >> p) & 1) << b;
            ++b;
        }
    return data;
}

ecc_result ecc_decode(word72 cw) {
    ecc_result r = { 0, ECC_OK, 0 };
    unsigned s = syndrome(cw);      /* 0 або номер битої позиції */
    unsigned g = parity(cw);        /* 0 = парна вага, 1 = непарна */

    if (s == 0 && g == 0) {         /* ── ціле ── */
        r.status = ECC_OK;
    } else if (g == 1) {            /* ── непарна вага → рахуємо як одну помилку ── */
        if (s == 0) {               /* перекинувся сам біт загальної парності */
            r.status = ECC_CORRECTED; r.pos = 0;
        } else if (s <= HAM) {      /* биток на позиції s — виправляємо */
            cw ^= (word72)1 << s;
            r.status = ECC_CORRECTED; r.pos = s;
        } else {                    /* s поза словом → збій за межами коду */
            r.status = ECC_DOUBLE;  /* чесно: не виправляємо наосліп */
        }
    } else {                        /* ── g == 0, s != 0 → парна вага (≥2) ── */
        r.status = ECC_DOUBLE;      /* виявили, виправити не можна */
    }

    r.data = gather(cw);            /* на ECC_DOUBLE ці дані НЕ довіряти */
    return r;
}
```

Зверніть увагу на дисципліну останнього рядка: `gather` викликається завжди, але на `ECC_DOUBLE` слово ми **не чіпали**, і повернені дані свідомо лишаються зіпсованими. Контракт простий і суворий: значення `data` дійсне лише тоді, коли `status` не `ECC_DOUBLE`. Виправлення слова наосліп, «щоб хоч щось повернути», було б рівно тією тихою брехнею, проти якої весь кодек і будувався.

## Перевірка на живому слові

Маленька збірка, що вкидає 0, 1 і 2 битки й дивиться на вирок:

```c
static word72 flip(word72 cw, unsigned p) { return cw ^ ((word72)1 << p); }

int main(void) {
    uint64_t data = 0xDEADBEEF12345678ULL;
    word72   code = ecc_encode(data);

    ecc_result a = ecc_decode(code);                       /* 0 помилок */
    ecc_result b = ecc_decode(flip(code, 40));             /* 1 биток: позиція 40 */
    ecc_result c = ecc_decode(flip(flip(code, 40), 9));    /* 2 битки: 40 і 9 */

    printf("ціле  : status=%d  data=%016llx  (%s)\n", a.status,
           (unsigned long long)a.data, a.data == data ? "збіг" : "РОЗБІЖНІСТЬ");
    printf("1 биток: status=%d  pos=%u  data=%016llx  (%s)\n", b.status, b.pos,
           (unsigned long long)b.data, b.data == data ? "збіг" : "РОЗБІЖНІСТЬ");
    printf("2 битки: status=%d  (виявлено подвійну — дані не довіряти)\n", c.status);
    return 0;
}
```

Простежмо два цікаві рядки в голові, без запуску. Одиничний биток на позиції 40 змінює синдром з 0 на 40 і робить загальну парність непарною (g = 1). Гілка `g == 1, s ≤ 71` перекидає біт 40 назад — слово знову ціле, `gather` віддає вихідні дані, статус `ECC_CORRECTED`, `pos = 40`. Два битки на позиціях 40 і 9 дають синдром 40 ⊕ 9 = 33 (адже 101000 ⊕ 001001 = 100001), а парність від двох перекидань повертається до парної (g = 0). Гілка `g == 0, s ≠ 0` каже `ECC_DOUBLE` — і не чіпає слова. Саме так і має бути: код побачив подвійну помилку й чесно спасував, замість вигадати неіснуючий «биток на позиції 33».

## Складність

Порахуймо роботу на слово. Кодування й обчислення синдрому — це фіксована кількість проходів по 72 бітах: скільки б даних не текло крізь пам'ять, ширина слова стала, тож на **кожне** слово припадає **O(1)** роботи. Формально цикли — O(n) за шириною слова n, але n тут — константа заліза (72), а не розмір входу, тож на слово це стала.

Тонше з локалізацією. Зібрати k-бітовий синдром — це k контрольних парностей, **O(k)** (тут k = 7). А от знайти за синдромом, який біт перекинути, — **O(1)**: синдром *уже є* номером біта, тож виправлення — одна індексована дія `cw ^= 1 << s`, без жодного пошуку. Варто відчути масштаб виграшу: наївне «звірити з усіма законними словами» коштувало б O(2⁶⁴) на слово — стільки кодових слів у 64-бітному коді. Синдром зводить це до семи XOR-ів і одного зсуву.

Пам'ять — **O(1)**: жодних структур, що ростуть із даними, лише сталі маски й розкладка. Саме тому ECC живе на гарячому шляху пам'яті, де будь-яка залежність від обсягу була б смертю.

## Пастки

**Хибне «виправлення» подвійної помилки — без DED-біта.** Це найпідступніше. Приберімо з коду загальну парність і лишімо голий Геммінг: на двох битках синдром усе одно ненульовий. У прикладі вище дві помилки на позиціях 40 і 9 дали синдром 40 ⊕ 9 = 33 — номер **здорової** позиції 33. Наївний декодер слухняно перекине біт 33, перетворить дві помилки на три й **відрапортує успіх**. Система впевнено віддасть спотворене число. Рятує саме той один біт загальної парності: одне перекидання робить вагу слова непарною (g = 1), два — знову парною (g = 0). Тому правило залізне: **ненульовий синдром за парної загальної ваги — це `ECC_DOUBLE`, і біт чіпати не можна**. Гілки `else if (g == 1)` й `else` в коді — не стилістика, а межа між «полагодив» і «зламав ще дужче». Один зайвий біт піднімає мінімальну відстань коду з 3 до 4 — рівно настільки, щоб відрізнити один биток від двох; це і є [SECDED](book:communications/secded).

**Вирівнювання слова.** Одиниця захисту тут — **усе слово цілком**, 64 біти даних разом зі своїми контрольними, а не окремий байт. Звідси три наслідки, об які легко перечепитися. Перший: контрольні біти пораховані над **усім** словом, тож змінити в пам'яті один байт «на місці» неможливо — доведеться прочитати ціле слово, перевірити й виправити його, вставити нові байти й **перерахувати** контроль, аж тоді записати. Це читання-зміна-запис (read-modify-write), і саме тому вузькі чи невирівняні записи в ECC-пам'ять коштують дорожче за широкі. Другий: слово мусить бути природно вирівняне, щоб контролер прочитав його разом із бічними контрольними бітами **неподільно**; рваний доступ, що вхопить половину старого й половину нового значення, виглядає для коду як багатобітова помилка, якої той не подужає. Третій, уже в нашій моделі: 72-бітове слово лежить у `__uint128_t`, а на платформі без нього — у двох `uint64_t`; тоді половини треба тримати вкупі, бо загубити одну — це загубити контрольні біти. Сюди ж лягає й гонка з фоновим [очищенням пам'яті](book:communications/memory-scrubbing): якщо scrubbing читає-виправляє-записує слово, а програма тим часом пише в той самий гранул без взаємного виключення, один запис затре інший. Вирівнювання тут — не про естетику адрес, а про те, що дає коду право поводитися зі словом як із неподільним цілим.

**Чому в залізі синдром рахують не циклом.** Наш `for` по 72 бітах чудовий для розуміння й безнадійний для контролера пам'яті: синдром мусить з'явитися **в межах затримки читання, на кожному читанні**. Тож кремній реалізує кожен розряд синдрому як фіксоване **XOR-дерево** над тими бітами, що їх вибирає відповідний рядок перевірної матриці — усі сім розрядів **паралельно**, за одну (логарифмічну за глибиною) затримку воріт, без жодної ітерації. Перехід «синдром → який біт перекинути» — це дешифратор чи невелика **таблиця**, що звіряє синдром зі стовпцями перевірної матриці. Ба більше: справжні контролери не беруть наш переплетений розклад Геммінга (де синдром дорівнює позиції), а **відокремлений** систематичний — дані лишаються чистим 64-бітним словом, контроль лягає збоку — з матрицею, підібраною під мінімальну й збалансовану глибину XOR-дерев. Це код Гсяо (M. Y. Hsiao, IBM, 1970), чиї стовпці — різні вектори непарної ваги; там «синдром = позиція» заступає «синдром = стовпець H для цього біта», і декодер розрізняє їх звірянням. Наша елегантна тотожність — навчальна зручність; залізо оптимізує затримку воріт і площу й рахує **той самий** синдром стіною XOR-ворит. Це заодно й пояснює, чому контрольні біти сидять на окремих мікросхемах збоку від даних, а не вперемішку з ними.

Разом ці три пастки окреслюють ту саму думку з різних боків: кодек цінний рівно доти, доки чесний. Він мусить розрізняти виправне від невиправного (перший біт загальної парності), поводитися зі словом як із неподільним цілим (вирівнювання) і встигати з вироком у такт пам'яті (комбінаційна логіка замість циклу). Прибери будь-що з трьох — і замість сховища, якому можна довіряти, дістанеш машину, що бреше, не знаючи про це ні сама, ні ти.
