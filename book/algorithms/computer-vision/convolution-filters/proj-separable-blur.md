# ⚙️ Розділюване гаусове розмиття на мікроконтролері

Гаусове розмиття 2D-ядром `k×k` коштує `k²` множень на кожен піксель. Для кадру 320×240 і ядра 5×5 це понад **1.9 мільйона** множень на кадр — і це лише розмиття, до пошуку меж справа ще не дійшла. На ARM Cortex-M4 без кешу й без апаратного паралелізму такий цикл легко з'їдає весь бюджет кадру. Та гаус розділюваний, тож ту саму роботу можна зробити за `2k` множень на піксель — для 5×5 це 10 проти 25, у два з половиною рази менше. Зберемо таку реалізацію від задачі до робочого коду й порахуємо, скільки вона коштує насправді.

## Ідея: два одновимірні проходи замість одного двовимірного

Гаусове ядро розпадається на добуток рядка й стовпця. Тому замість того, щоб для кожного пікселя обходити квадрат `k×k`, робимо два прості проходи:

```
прохід 1 (горизонтальний): кожен рядок згортаємо з 1D-ядром → проміжний кадр
прохід 2 (вертикальний):   кожен стовпець проміжного кадру згортаємо з тим самим 1D-ядром → результат
```

Перший прохід розмиває зображення лише по горизонталі, другий домазує по вертикалі — і разом вони дають точнісінько те саме, що повний 2D-гаус, але за `k + k` множень на піксель. Це найдешевша велика економія в усій просторовій обробці, і нічого, крім розділюваності ядра, для неї не потрібно.

Для розмиру 5 візьмемо класичні цілі ваги `(1, 4, 6, 4, 1)` — це біноміальні коефіцієнти, дискретне наближення гаусу. Їхня сума — 16, тож після згортки результат треба поділити на 16 (а оскільки проходів два, повний дільник — 16×16 = 256, але ділити зручніше після кожного проходу, по 16).

## Фіксована точка: ваги в цілих, ділення зсувом

На Cortex-M4 (ядро з апаратним множенням цілих, але без апаратного поділу — `SDIV`/`UDIV` є, проте повільніші за зсув) арифметику з комою тримати ні до чого: ваги цілі, а ділення на 16 — це зсув на 4 біти. Це і є **фіксована точка**: дробові коефіцієнти подаємо цілими, а масштаб тримаємо в голові. Сума ваг 16 = 2⁴ означає, що нормування — рівно `>> 4`, без жодного `MUL` чи `DIV`.

Одна тонкість зі зсувом: щоб результат округлювався, а не лише відкидав дробову частину (це зсувало б яскравість донизу на кожному проході), додаємо перед зсувом половину дільника — 8:

```c
out = (acc + 8) >> 4;   // округлення до найближчого, а не вниз
```

Накопичувач `acc` має бути достатньо широким, щоб не переповнитися. Максимум на один піксель: 255 × (1+4+6+4+1) = 255 × 16 = 4080 — спокійно влазить у `int16_t` (до 32767), а тим паче в `int32_t`. Беремо `int32_t` для запасу й швидкості (Cortex-M4 рідний для 32-біт).

## Чому саме ваги (1,4,6,4,1)

Ваги взяті не зі стелі — це **біноміальні коефіцієнти** п'ятого порядку (рядок трикутника Паскаля: 1, 4, 6, 4, 1). Біноміальні коефіцієнти — найкраще ціле наближення гаусу, яке взагалі можна дістати: повторна згортка коробкового ядра `(1,1)` саме сама з собою щоразу дає наступний рядок Паскаля, а за центральною граничною теоремою багаторазове усереднення сходиться до гаусу. Тому `(1,4,6,4,1)` — це фактично гаус, але цілими числами й із сумою рівно 16 = 2⁴, тобто нормування безплатне (зсув). Якби ми взяли «справжній» гаус із якоюсь сигмою, ваги вийшли б дробові, сума — не степінь двійки, і довелося б або ділити (повільно), або масштабувати у фіксовану точку з похибкою заокруглення. Біноміальні ваги обходять усе це: точне ціле наближення з даровим нормуванням. За це платимо лише фіксованою «силою» розмиття — щоб розмити сильніше, ядро `(1,4,6,4,1)` проганяють **кілька разів** поспіль (кожен прохід додає розмиття), а не розширюють до 7×7 чи 9×9.

Перш ніж довіряти такій реалізації, її варто **звірити з еталоном** — повним 2D-гаусом, порахованим «у лоб». Напиши коротку перевірку: проганяє той самий кадр і двома 1D-проходами, і одним 2D-ядром 5×5 (зовнішнім добутком `(1,4,6,4,1)` на себе, сума 256, зсув `>> 8`), тоді порівнює результати піксель у піксель. Вони мусять збігатися всюди, крім, можливо, ±1 на крайніх пікселях через різний порядок округлення (двічі по `>> 4` проти одного `>> 8`). Якщо розбіжність більша за 1 або є в середині кадру — десь помилка: переплутані осі проходів, не той дільник або зіпсована адресна арифметика. Така звірка ловить найпідступніші баги розділюваної реалізації, бо очі на готовому розмитому кадрі різниці в один-два рівні яскравості не побачать.

## Граничні умови: повтор краю (edge-clamp)

Біля краю кадру ядро звисає за межу — частина його ваг лягає на неіснуючі пікселі. Найпростіша й найбезпечніша відповідь — **повтор краю** (англ. *edge-clamp* «затиск до краю»): піксель за межею вважаємо рівним найближчому крайньому. Це не плодить ні темної рамки (як доповнення нулями), ні дивних кольорів з протилежного боку (як загортання) — лише трохи «розмазує» сам край, що для розмиття природно. Реалізуємо clamp простим обрізанням індексу:

```c
static inline int clampi(int v, int lo, int hi) {
    if (v < lo) return lo;
    if (v > hi) return hi;
    return v;
}
```

## Робочий код: один прохід ядром (1,4,6,4,1)

Обидва проходи — горизонтальний і вертикальний — це той самий 1D-гаус, лише вздовж різних осей. Напишемо одну функцію проходу по рядку й одну по стовпцю; буфер для проміжного кадру виділяє той, хто викликає (на мікроконтролері статично, не з купи).

:::tabs
```cpp
#include <stdint.h>

#define KR 2   /* радіус ядра: 5 = 2*KR+1 */
static const int32_t W[5] = {1, 4, 6, 4, 1};   /* сума = 16 = 2^4 */

static inline int clampi(int v, int lo, int hi) {
    return v < lo ? lo : (v > hi ? hi : v);
}

/* Горизонтальний прохід: src -> dst, кожен рядок згортається з W. */
static void blur_h(const uint8_t *src, uint8_t *dst, int w, int h) {
    for (int y = 0; y < h; ++y) {
        const uint8_t *row = src + (size_t)y * w;
        uint8_t       *out = dst + (size_t)y * w;
        for (int x = 0; x < w; ++x) {
            int32_t acc = 0;
            for (int t = -KR; t <= KR; ++t) {
                int xi = clampi(x + t, 0, w - 1);   /* edge-clamp по краю рядка */
                acc += W[t + KR] * row[xi];
            }
            out[x] = (uint8_t)((acc + 8) >> 4);     /* /16 з округленням */
        }
    }
}

/* Вертикальний прохід: src -> dst, кожен стовпець згортається з W. */
static void blur_v(const uint8_t *src, uint8_t *dst, int w, int h) {
    for (int y = 0; y < h; ++y) {
        uint8_t *out = dst + (size_t)y * w;
        for (int x = 0; x < w; ++x) {
            int32_t acc = 0;
            for (int t = -KR; t <= KR; ++t) {
                int yi = clampi(y + t, 0, h - 1);   /* edge-clamp по краю стовпця */
                acc += W[t + KR] * src[(size_t)yi * w + x];
            }
            out[x] = (uint8_t)((acc + 8) >> 4);
        }
    }
}

/* Повне гаусове розмиття 5x5 двома проходами.
   tmp — проміжний буфер тих самих розмірів, що й кадр (виділяє викликач). */
void gauss5_separable(const uint8_t *src, uint8_t *dst,
                      uint8_t *tmp, int w, int h) {
    blur_h(src, tmp, w, h);   /* спершу рядки  */
    blur_v(tmp, dst, w, h);   /* тоді стовпці  */
}
```
```python
KR = 2                      # радіус ядра: 5 = 2*KR+1
W = (1, 4, 6, 4, 1)         # сума = 16 = 2^4


def clampi(v, lo, hi):
    return lo if v < lo else (hi if v > hi else v)


def blur_h(src, dst, w, h):
    """Горизонтальний прохід: src -> dst, кожен рядок згортається з W."""
    for y in range(h):
        row = y * w
        for x in range(w):
            acc = 0
            for t in range(-KR, KR + 1):
                xi = clampi(x + t, 0, w - 1)   # edge-clamp по краю рядка
                acc += W[t + KR] * src[row + xi]
            dst[row + x] = (acc + 8) >> 4      # /16 з округленням


def blur_v(src, dst, w, h):
    """Вертикальний прохід: src -> dst, кожен стовпець згортається з W."""
    for y in range(h):
        row = y * w
        for x in range(w):
            acc = 0
            for t in range(-KR, KR + 1):
                yi = clampi(y + t, 0, h - 1)   # edge-clamp по краю стовпця
                acc += W[t + KR] * src[yi * w + x]
            dst[row + x] = (acc + 8) >> 4


def gauss5_separable(src, dst, tmp, w, h):
    """Повне гаусове розмиття 5x5 двома проходами.
    tmp — проміжний буфер тих самих розмірів, що й кадр (виділяє викликач)."""
    blur_h(src, tmp, w, h)    # спершу рядки
    blur_v(tmp, dst, w, h)    # тоді стовпці
```
:::

Виклик для кадру 320×240 у відтінках сірого:

```c
static uint8_t frame[320 * 240];
static uint8_t blurred[320 * 240];
static uint8_t scratch[320 * 240];   /* проміжний буфер */

gauss5_separable(frame, blurred, scratch, 320, 240);
```

Зверни увагу на дві деталі реалізації. По-перше, проміжний буфер `tmp` потрібен **окремий** — писати назад у `src` під час горизонтального проходу не можна, бо сусідні пікселі того ж рядка ще читаються. По-друге, вертикальний прохід читає `src[(yi)*w + x]` — стрибками по `w` байтів між рядками; це найгірший шаблон доступу до пам'яті (кожне читання — нова лінія кешу, якщо кеш є). На дрібних кадрах це дрібниця, на великих — привід тримати кадр у швидкій внутрішній пам'яті, а не в зовнішньому SDRAM.

> 🔧 **Навіщо це.** Окремий проміжний буфер `tmp` — це зайвий кадр у пам'яті (для 320×240 — 76.8 КБ). На МК із тісною RAM це може бути більше, ніж є вільного. Тоді розмивають **смугами**: тримають у пам'яті лише `2·KR+1` рядків, проганяють обидва проходи по смузі й видають готові рядки, зсуваючи вікно. Код складніший, зате пам'ять — кілька рядків замість цілого кадру. Архітектурне рішення «цілий буфер чи смуга» диктує не швидкість, а скільки в тебе RAM.

## Скільки це коштує: рахунок тактів на Cortex-M4

Порахуймо роботу на один піксель. Кожен прохід — це цикл по 5 вагах, у кожній ітерації: обчислити індекс із clamp (пара порівнянь), множення `W[..] * піксель` (на Cortex-M4 `MUL` — 1 такт), додавання до накопичувача. Грубо — близько 5–6 тактів на одну вагу з урахуванням адресної арифметики й читання, тобто ~30 тактів на піксель на прохід, ~60 на обидва. Це **оцінка**, не виміряний результат: точне число залежить від того, як компілятор розгорне цикл, де лежить кадр (внутрішня SRAM чи зовнішній SDRAM) і чи ввімкнено кеш на M7. Виміряти треба лічильником циклів `DWT->CYCCNT`:

```c
/* увімкнути лічильник тактів ядра (один раз при старті) */
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0;
DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;

uint32_t t0 = DWT->CYCCNT;
gauss5_separable(frame, blurred, scratch, 320, 240);
uint32_t cycles = DWT->CYCCNT - t0;
/* cycles / 168e6 = час у секундах на 168 МГц */
```

Прикинемо порядок. Кадр 320×240 = 76 800 пікселів. За ~60 тактів на піксель — близько **4.6 млн тактів** на розмиття. На Cortex-M4 @ 168 МГц це ≈ 27 мс. Для 30 кадрів/с бюджет на кадр — 33 мс, тож саме лише розмиття з'їдає більшу його частину, на решту конвеєра майже нічого не лишається. Порівняймо з нерозділюваним 5×5: там `k² = 25` множень проти `2k = 10`, тобто десь у 2.5 раза довше — близько 67 мс, що **не влазить** у кадр узагалі. Ось ціна розділюваності в живих мілісекундах: вона і є та межа, за якою фільтр або встигає в реальному часі, або ні.

Якщо й розділюваного замало — далі є куди тиснути: розгорнути внутрішній цикл по 5 вагах вручну (прибрати накладні витрати циклу), скористатися інструкціями SIMD Cortex-M4 (`SMLAD` множить-додає дві пари 16-бітних чисел за такт — два пікселі заразом), або взяти ширші ваги в `int16` і паковані операції. Та перший і найбільший крок — це сам перехід від `k²` до `2k`; усе інше лише шліфує вже зменшене число.
