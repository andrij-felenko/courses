# ⚙️ Цілочисельне RGB ↔ HSV для бортового MCU

## Задача

На дроні треба знайти в кадрі помаранчевий маркер. Найстійкіший до освітлення шлях — перевести піксель у HSV і ловити по тону. Але класичні формули HSV рясніють діленнями й значеннями в [0,1], тобто **плаваючою комою**. А бортовий мікроконтролер (скажімо, Cortex-M0 чи M3) часто **не має блоку плаваючої коми** (FPU — *floating-point unit*): кожна операція з `float` емулюється бібліотекою в десятки тактів. Помножити це на сотні тисяч пікселів кадру, та ще й на 30 кадрів за секунду, — і процесор захлинеться, не встигаючи за відеопотоком.

Полічімо на пальцях, чому це справді біль. Кадр навіть скромних 320×240 — це 76 800 пікселів. На MCU без FPU одне програмне ділення `float` коштує близько сотні тактів, а в наївній формулі HSV їх кілька на піксель. Це вже понад двадцять мільйонів тактів **лише на ділення** — і це на один кадр; на 30 кадрів за секунду треба під мільярд тактів, тоді як у Cortex-M3 на 72 МГц їх усього сімдесят два мільйони за секунду. Розрив у десятки разів: наївний код фізично не встигне. Цілі числа з діленням, заміненим на зсув, дають саме той порядок прискорення, якого бракує.

Потрібна конвертація RGB↔HSV **на цілих числах**, без жодного `float`, достатньо точна, щоб поріг по тону працював, і достатньо швидка, щоб устигати за камерою. І зворотний бік — HSV→RGB — теж: ним малюють підсвітку чи рамку навколо знайденого маркера.

## Ідея

Три прийоми роблять цілочисельний HSV можливим і точним.

**Перший — шкала 0…255 замість часток і градусів.** Тримаємо H, S, V кожне в одному байті (0…255). Для S і V це природно. Для тону H замість 0…360° беремо 0…255 — увесь круг у байт; домноження на 360/255 (якщо комусь треба градуси) — справа викликача.

**Другий — масштабувати чисельник ПЕРЕД діленням.** Серце точності. Наївне цілочисельне `Δ / Cmax` дасть майже завжди 0 (бо Δ < Cmax). Тож домножуємо чисельник на 255 **до** ділення: `(Δ · 255) / Cmax` — і результат одразу в потрібній шкалі 0…255, з нормальною точністю. Той самий прийом для тону.

**Третій — обхід ділення там, де можна.** На MCU без апаратного ділення (`UDIV`) операція `/` теж бібліотечна й повільна. Зовсім без ділення HSV не вивести (S і H — це по суті відношення), але кількість ділень тримаємо мінімальною: одне на S, одне на H, і обираємо знаменники так, щоб не ділити двічі тим самим. Зворотне HSV→RGB виходить **зовсім без ділення** на гарячому шляху — лише множення й зсуви.

Тримаємо всі проміжні в `int32_t`: масштабування `Δ·255` сягає 65025, а в обчисленні тону трапляються більші добутки й від'ємні різниці — `int16_t` тут мовчки переповниться й видасть зіпсований колір.

## Робочий код

### RGB → HSV

```c
#include <stdint.h>

// RGB888 -> HSV, кожен канал 0..255. Тон закодовано як 0..255 (увесь круг у байт).
// Без float. Усі проміжні int32_t — проти переповнення масштабування.
void rgb_to_hsv_u8(uint8_t r, uint8_t g, uint8_t b,
                   uint8_t *h, uint8_t *s, uint8_t *v) {
    int32_t cmax = r > g ? (r > b ? r : b) : (g > b ? g : b);
    int32_t cmin = r < g ? (r < b ? r : b) : (g < b ? g : b);
    int32_t delta = cmax - cmin;

    *v = (uint8_t)cmax;                       // V = Cmax

    if (cmax == 0) { *s = 0; *h = 0; return; } // чорне: S,H не визначені
    *s = (uint8_t)((delta * 255) / cmax);      // S = Δ/Cmax, масштаб ×255

    if (delta == 0) { *h = 0; return; }        // сіре: тон не визначений

    // тон рахуємо у проміжній шкалі 0..1530 (6 секторів по 255), тоді /6 у 0..255
    int32_t hue;
    if (cmax == r)      hue = 0    + (255 * (g - b)) / delta;  // червоний сектор
    else if (cmax == g) hue = 510  + (255 * (b - r)) / delta;  // зелений  (+2·255)
    else                hue = 1020 + (255 * (r - g)) / delta;  // синій    (+4·255)

    if (hue < 0) hue += 1530;                  // загорнути від'ємний бік (≡ mod 6)
    *h = (uint8_t)(hue / 6);                   // 1530 → 255
}
```

Перевіримо на помаранчевому R=240, G=140, B=20:

```text
cmax=240(R)  cmin=20(B)  delta=220
V = 240
S = (220·255)/240 = 56100/240 = 233          (≈ 91%)
cmax==r → hue = (255·(140−20))/220 = 30600/220 = 139
hue ≥ 0 → без загортання
H = 139/6 = 23                               (23/255 круга ≈ 32° — помаранчевий!)
```

Виходить H=23, S=233, V=240 — жодного `float`. Проміжна шкала 1530 потрібна, щоб `/6` наприкінці не зжерло точність; `delta*255 = 56100` саме тому тримаємо в `int32_t`.

### HSV → RGB

Зворотне перетворення виходить **без ділення** на гарячому шляху — самі множення й зсуви.

```c
#include <stdint.h>

// HSV (кожен 0..255, тон — увесь круг у байт) -> RGB888. Без float, без ділення в циклі.
void hsv_to_rgb_u8(uint8_t h, uint8_t s, uint8_t v,
                   uint8_t *r, uint8_t *g, uint8_t *b) {
    if (s == 0) { *r = *g = *b = v; return; }   // сіре: усі канали = V

    int32_t region = h / 43;            // 256/6 ≈ 43 → номер сектора 0..5
    int32_t rem    = (h - region * 43) * 6;     // залишок у 0..255 усередині сектора

    int32_t p = (v * (255 - s)) >> 8;                       // нижній рівень
    int32_t q = (v * (255 - ((s * rem) >> 8))) >> 8;        // спадна складова
    int32_t t = (v * (255 - ((s * (255 - rem)) >> 8))) >> 8; // висхідна складова

    switch (region) {
        case 0:  *r = v; *g = t; *b = p; break;
        case 1:  *r = q; *g = v; *b = p; break;
        case 2:  *r = p; *g = v; *b = t; break;
        case 3:  *r = p; *g = q; *b = v; break;
        case 4:  *r = t; *g = p; *b = v; break;
        default: *r = v; *g = p; *b = q; break;   // case 5
    }
}
```

Тут `region` — сектор (один поділ на 43, дешево), а `p, q, t` — три рівні каналу, пораховані самими множеннями зі зсувом `>> 8` (ділення на 256). У гарячому циклі жодного бібліотечного ділення немає.

Прокрутимо назад наш помаранчевий H=23, S=233, V=240, щоб переконатися, що цикл туди-назад замикається:

```text
s ≠ 0 → рахуємо
region = 23/43 = 0          rem = (23 − 0)·6 = 138
p = (240·(255−233)) >> 8 = (240·22) >> 8 = 5280 >> 8 = 20
q = (240·(255 − ((233·138)>>8))) >> 8 = (240·(255 − 125)) >> 8 = (240·130) >> 8 = 121
t = (240·(255 − ((233·(255−138))>>8))) >> 8 = (240·(255 − 106)) >> 8 = (240·149) >> 8 = 139
region 0 → R=v=240, G=t=139, B=p=20
```

Дістали (240, 139, 20) — практично вихідний (240, 140, 20); розбіжність в одиницю на зеленому — це законне округлення цілочисельних зсувів, не помилка. Туди-назад зійшлося.

Один поділ на 43 у HSV→RGB можна прибрати й зовсім, якщо тримати тон одразу як «сектор + залишок» або взяти зсув замість ділення (256 на 6 ділиться неточно, тож 43 — компроміс). Для малювання рамок це не критично — викликів небагато; для масового перетворення цілого кадру назад у RGB варто переписати на зсуви.

### Як це викликають у конвеєрі

```c
// маска «помаранчевий маркер» по тону, стійка до освітлення
static inline int is_orange(uint8_t r, uint8_t g, uint8_t b) {
    uint8_t h, s, v;
    rgb_to_hsv_u8(r, g, b, &h, &s, &v);
    return (h >= 16 && h <= 30)   // тон ≈ 22…42° (у шкалі 0..255)
        && (s >= 90)              // ВІДСІЯТИ сірі (інакше їхній тон = артефакт)
        && (v >= 50);             // ВІДСІЯТИ темні (тінь, де тон ненадійний)
}
```

Зверни увагу, що смуга тону тут задана в шкалі 0…255 (16…30), а не в градусах — бо саме так повертає `rgb_to_hsv_u8`. Перерахунок простий: 16/255 круга ≈ 22°, 30/255 ≈ 42°, тобто це класична помаранчева смуга 20–40°. Тримати поріг у тій самій шкалі, що й функція, — окрема дрібна дисципліна: змішаєш градуси зі шкалою 0…255, і маска «з'їде» на чужий колір, навіть коли сама конвертація бездоганна.

## Пастки

**Undefined hue при S=0.** Найголовніша. Коли піксель сірий (R=G=B, отже delta=0) або чорний (cmax=0), тон **не існує** — у коді ми кладемо H=0. Але 0 — це «червоний»! Якщо потім фільтрувати по тону без відсіву, кожен сірий і чорний піксель прикинеться насиченим червоним і засипле «червону» маску хибними спрацюваннями. **Правило: поріг по тону завжди йде в парі з порогом по S (відсіяти сірі) і по V (відсіяти темні)** — як у `is_orange` вище. Це не косметика, а різниця між робочим детектором і суцільним шумом.

**Переповнення проміжку при масштабуванні.** `delta * 255` сягає 65025 — це впритул до стелі `uint16_t` (65535), а в обчисленні тону `255 * (g - b)` дає і більші, і **від'ємні** значення. Поклади все проміжне в `int32_t`; `int16_t` чи `uint16_t` тут мовчки обріжуться, і кольори «попливуть» там, де проміжок переповнився. Звужуй до `uint8_t` лише наприкінці, коли результат гарантовано в 0…255.

**Втрата точності при ранньому діленні.** Якщо написати `delta / cmax` без домноження на 255, отримаєш майже завжди 0 (бо delta < cmax). Масштаб **перед** діленням — обов'язковий; тон рахуй у проміжній шкалі 1530, а не одразу в 0…255, інакше фінальне `/6` зжере молодші розряди.

**Загортання від'ємного тону.** У червоному секторі при B > G різниця `(g − b)` від'ємна, і тон «заходить» за нуль на пурпуровий бік. Додавання 1530 (`if (hue < 0)`) — цілочисельний відповідник `mod 6`; забути його — дістати від'ємний H і сміття після звуження до `uint8_t`.

**Округлення вниз.** Цілочисельне ділення відкидає дробову частину (округлює до нуля). Для тонкого тону це інколи помітно. Якщо точність критична, додавай половину дільника перед діленням (`(x + d/2) / d`) — округлення до найближчого; для маски по тону зазвичай не потрібно, та варто знати.

**Червоний на стику кола.** Сам червоний лежить навколо H=0, тобто **по обидва боки** від нуля (і трохи нижче 255, і трохи вище 0). Якщо ловиш саме червоний, одна умова `h >= a && h <= b` його не покриє — поріг доведеться розбити на два діапазони (`h >= 245 || h <= 10`) або тимчасово зсунути тон. Для помаранчевого, що цілком в одному секторі, цієї біди немає, але про неї треба пам'ятати, коли ціль — червона.

## Як перевірити

Найдешевший тест цілочисельної конвертації — **прокрутка туди-назад**: узяти набір RGB, перевести в HSV і назад, і впевнитися, що результат відрізняється від вихідного **не більш ніж на одиницю-дві** на канал (саме стільки з'їдають законні округлення зсувів). Більша розбіжність — ознака або переповнення проміжку, або забутого загортання тону. Окремо варто прогнати **граничні точки**: чисте чорне (0,0,0), чисте біле (255,255,255), кілька сірих (R=G=B) — усі вони мусять дати S=0 і не зламати ділення. І нарешті — кілька чистих кольорів (червоний, зелений, синій, жовтий), щоб переконатися, що тон падає рівно в очікувані сектори (0, ≈85, ≈170 у шкалі 0…255). Цей десяток перевірок ловить майже всі помилки, перш ніж код потрапить у гарячий цикл обробки кадру.
