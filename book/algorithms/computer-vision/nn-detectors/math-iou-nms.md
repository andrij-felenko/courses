# 🧮 Математика детекції: IoU, NMS і вибір порогів

Детектор оперує прямокутниками, а прямокутники треба **порівнювати** — наскільки два збігаються, який із кількох двійників лишити, де провести межу між «знайшов» і «вигадав». Усе це тримається на одній простій величині — IoU — і на одному жадібному алгоритмі — NMS. Розберімо їх не як рецепт, а від першопричин: чому саме така формула, чому алгоритм коректний і як два пороги (IoU та впевненості) крутять баланс точності й повноти.

## IoU від перших принципів

Питання, на яке відповідає IoU, звучить наївно: наскільки два прямокутники — це «той самий» прямокутник? Спершу спробуймо очевидні відповіді й подивімося, де вони ламаються.

**Спроба перша — відстань між центрами.** Здавалося б, ближчі центри — ближчі рамки. Та відстань центрів сліпа до розміру й форми: крихітна рамка й величезна можуть мати **спільний** центр (відстань нуль!), хоча описують геть різні речі. Відкинули.

**Спроба друга — площа перетину.** Більший спільний шматок — кращий збіг? Теж ні: велика рамка перетинається з усім підряд великою площею просто тому, що вона велика. Перетин не нормований — його не порівняти між парами різного розміру. Відкинули.

Чого бракує обом — **спільної шкали**. Перетин треба з чимось **поділити**, щоб дістати частку від 0 до 1, незалежну від абсолютних розмірів. Природний знаменник — площа всього, що дві рамки разом укривають, тобто їх **об'єднання**. Так народжується IoU:

```
IoU = площа(A ∩ B) / площа(A ∪ B)
```

Чому об'єднання — правильний вибір знаменника, а не, скажімо, площа меншої рамки? Бо об'єднання карає **обидва** види розбіжності одразу. Якщо A набагато більша за B і ледь її накриває — об'єднання велике (майже вся A), перетин малий (уся B), частка мала: IoU справедливо низький. Якщо A і B однакові й збігаються — перетин дорівнює об'єднанню, IoU = 1. Якщо не торкаються — перетин 0, IoU = 0. Одна величина ловить **і положення, і розмір, і форму** разом і завжди лежить у [0, 1].

### Площа об'єднання без подвійного рахунку

Тонкість, на якій часто спотикаються: площу об'єднання **не** рахують прямо. Її виводять із принципу включення-виключення:

```
площа(A ∪ B) = площа(A) + площа(B) − площа(A ∩ B)
```

Чому віднімаємо перетин? Бо спільний шматок входить і в площу A, і в площу B — якщо просто додати дві площі, його порахуємо **двічі**. Віднявши перетин один раз, прибираємо зайвий рахунок. Ця формула й зручна: площі прямокутників і перетин ми вже вміємо рахувати, а об'єднання не доводиться будувати геометрично.

### Площа перетину двох вирівняних прямокутників

Лишається перетин. Для прямокутників, вирівняних по осях (а рамки детектора саме такі), перетин — теж прямокутник, і його межі знаходяться елементарно. Задамо рамку кутами `[x1, y1, x2, y2]`. Тоді перетин по горизонталі тягнеться від **правішого з лівих** країв до **лівішого з правих**:

```
ix1 = max(A.x1, B.x1)        // лівий край перетину
ix2 = min(A.x2, B.x2)        // правий край перетину
iw  = ix2 − ix1              // ширина; якщо ≤ 0 — рамки не перетинаються по x
```

І так само по вертикалі (`iy1 = max(A.y1,B.y1)`, `iy2 = min(A.y2,B.y2)`, `ih = iy2 − iy1`). Логіка `max` для лівого й `min` для правого — це і є геометрія перекриття: спільна смуга починається там, де **обидві** рамки вже почалися, і кінчається там, де **перша** з них скінчилася.

Критична деталь — знак ширини. Якщо рамки **не** перетинаються по x, то `ix2 < ix1`, і `iw` виходить **від'ємна**. Якщо тут не зупинитися, а перемножити від'ємні `iw` й `ih`, дістанемо **додатний** фальшивий перетин — типова тиха помилка. Тому перед множенням ширину й висоту обрізають нулем:

:::tabs
```cpp
float iou(box_t a, box_t b) {
    float ix1 = fmaxf(a.x1, b.x1), iy1 = fmaxf(a.y1, b.y1);
    float ix2 = fminf(a.x2, b.x2), iy2 = fminf(a.y2, b.y2);
    float iw = ix2 - ix1, ih = iy2 - iy1;
    if (iw <= 0.0f || ih <= 0.0f) return 0.0f;     // не торкаються — перетин 0
    float inter = iw * ih;
    float areaA = (a.x2 - a.x1) * (a.y2 - a.y1);
    float areaB = (b.x2 - b.x1) * (b.y2 - b.y1);
    return inter / (areaA + areaB - inter);         // ∩ / ∪
}
```
```python
def iou(a, b):                                     # рамка — (x1, y1, x2, y2)
    ix1, iy1 = max(a[0], b[0]), max(a[1], b[1])
    ix2, iy2 = min(a[2], b[2]), min(a[3], b[3])
    iw, ih = ix2 - ix1, iy2 - iy1
    if iw <= 0 or ih <= 0:                          # не торкаються — перетин 0
        return 0.0
    inter = iw * ih
    area_a = (a[2] - a[0]) * (a[3] - a[1])
    area_b = (b[2] - b[0]) * (b[3] - b[1])
    return inter / (area_a + area_b - inter)        # ∩ / ∪
```
:::

🧮 **Worked-приклад: IoU рамок A = [0, 0, 100, 100] і B = [50, 50, 150, 150].**

```
перетин x: max(0,50)=50 ... min(100,150)=100 → iw = 50
перетин y: max(0,50)=50 ... min(100,150)=100 → ih = 50
inter = 50 × 50 = 2500

areaA = 100 × 100 = 10000
areaB = 100 × 100 = 10000
union = 10000 + 10000 − 2500 = 17500

IoU = 2500 / 17500 ≈ 0.143
```

Дві однакові рамки, зсунуті на пів-сторони, дають IoU лише ≈ 0.14 — менше, ніж підказує око. Це корисна каліброка інтуїції: IoU зростає різко, лише коли рамки справді **тісно** лягають одна на одну. Збіг «на око непоганий» — це часто IoU усього 0.3–0.4.

## NMS: алгоритм і доведення коректності

Сирий детектор кидає на одну ціль по кілька рамок. Придушення немаксимумів (*Non-Maximum Suppression*) лишає одну. Сформулюймо точно й доведімо, що воно робить саме те, що треба.

**Алгоритм.**
1. Згрупувати кандидатів за класом (рамки різних класів не конкурують).
2. У межах класу відсортувати рамки за **спаданням** упевненості.
3. Узяти найвпевненішу ще не оброблену рамку — оголосити її **лишеною**.
4. Викинути всі ще не оброблені рамки, чий IoU із нею **більший за поріг** `τ`.
5. Повторювати крок 3, доки лишаються необроблені рамки.

:::tabs
```cpp
int nms(det_t *d, int n, float tau, int *keep) {
    sort_desc_by_score(d, n);                 // крок 2
    for (int i = 0; i < n; i++) keep[i] = 1;
    for (int i = 0; i < n; i++) {
        if (!keep[i]) continue;               // вже придушена — пропустити
        for (int j = i + 1; j < n; j++) {     // лише дальші (вони слабші)
            if (!keep[j] || d[j].cls != d[i].cls) continue;
            if (iou(d[i].box, d[j].box) > tau) keep[j] = 0;   // крок 4
        }
    }
    int kept = 0; for (int i = 0; i < n; i++) kept += keep[i];
    return kept;
}
```
```python
def nms(dets, tau):
    dets.sort(key=lambda d: d.score, reverse=True)   # крок 2
    keep = [True] * len(dets)
    for i, di in enumerate(dets):
        if not keep[i]:                              # вже придушена — пропустити
            continue
        for j in range(i + 1, len(dets)):            # лише дальші (вони слабші)
            dj = dets[j]
            if not keep[j] or dj.cls != di.cls:
                continue
            if iou(di.box, dj.box) > tau:            # крок 4
                keep[j] = False
    return [d for d, k in zip(dets, keep) if k]      # лишені рамки
```
:::

**Чому достатньо дивитися тільки вперед (`j > i`).** Масив відсортований за спаданням упевненості, тож будь-яка рамка `j > i` **не впевненіша** за `i`. Якщо `j` сильно перекриває `i`, то `i` — впевненіший представник того самого об'єкта, і саме `j` має поступитися. Рамку `i` ніколи не доведеться душити кимось із дальших — вони всі слабші. Тому однобічного проходу досить, і окремий пошук максимуму не потрібен: перша незаймана рамка завжди вже найсильніша.

**Коректність — два твердження.**

*Твердження 1 (жодних двійників на виході).* Хай дві рамки лишені (`keep = 1`) і мають IoU понад `τ`. Та сама, що йде раніше в сортуванні, на своєму кроці `i` перевірила б другу й погасила б її (`keep[j] = 0`) — суперечність. Отже серед лишених жодна пара не перевищує `τ`: двійники неможливі.

*Твердження 2 (жоден об'єкт не зник дарма).* Рамку гасять **лише** тоді, коли є впевненіша рамка, що перекриває її понад `τ`. За означенням великого IoU обидві описують **той самий** об'єкт. Отже разом із погашеною рамкою об'єкт **не втрачається** — його представляє впевненіший двійник, який лишився. Жадібність безпечна саме тут: найвпевненіша рамка майже завжди й найточніша, тож лишати першою варто її.

Складність — `O(n²)` у найгіршому разі (кожна з кожною), але `n` після порога впевненості зазвичай мала (десятки рамок), тож на борту це дешево. Якщо кандидатів тисячі — спершу ріжуть порогом упевненості, і аж тоді NMS.

### М'якший варіант: чому різке викидання іноді шкодить

Жорсткий NMS приймає бінарне рішення: IoU понад поріг — рамку **геть**. У щільній сцені це підступно. Дві людини стоять упритул, їхні справжні рамки перекриваються на IoU ≈ 0.6, поріг `τ = 0.5` — і друга людина гине як «двійник» першої, хоча це окрема ціль. Звідси **Soft-NMS**: замість викидати рамку, її впевненість **знижують** тим сильніше, чим більший IoU:

```
score_j ← score_j · (1 − IoU(i, j))        // лінійний варіант
```

Слабко перекрита рамка майже не втрачає впевненості й виживає; сильно перекритий двійник просесідає під поріг сам. Жодного різкого «геть» — і сусідні цілі не приносяться в жертву. Ціна — рамки доводиться переоцінювати, а не просто позначати, але в щільних сценах це повертає проґавлені цілі.

## Два пороги: як IoU і впевненість крутять баланс

У детекції живуть **два різні** пороги, і їх постійно плутають. Розведімо їх остаточно й подивімося, як кожен зсуває точність і повноту.

**Поріг упевненості** `c` — нижня межа оцінки рамки, щоб її взагалі розглядати. Це **головний** регулятор обміну точність-повнота. Точність — частка справжніх серед названих: `precision = TP / (TP + FP)`. Повнота — частка знайдених серед справжніх: `recall = TP / (TP + FN)`.

```
поріг c ↑  →  лишаються тільки найнадійніші рамки
              FP ↓ (менше хибних тривог)  →  precision ↑
              TP ↓ (гинуть і слабкі правдиві)  →  recall ↓

поріг c ↓  →  проходить більше рамок
              TP ↑ (ловимо й слабкі правдиві)  →  recall ↑
              FP ↑ (та й хибних більше)  →  precision ↓
```

Ось чому **одне** число не описує детектор: пересунув поріг — і точність із повнотою помінялися місцями. Тому якість міряють кривою точність-повнота (точки при всіх порогах `c`), а її площу згортають у **AP** (*Average Precision*); середнє AP по класах — **mAP**.

**Поріг IoU** `τ` — окрема річ, і він з'являється у **двох** ролях, які теж не можна мішати:

*У NMS* (`τ` придушення) `τ` вирішує, що вважати двійником. Високий `τ` (0.7) — душимо лише майже-копії, двійники просочуються; низький `τ` (0.3) — душимо й сусідів, щільні сцени злипаються. Це баланс «двійники проти злиплих цілей».

*В оцінці якості* (`τ` зарахування) `τ` вирішує, наскільки точно рамка має лягти на ціль, щоб її зарахувати як TP. Звідси запис **mAP@0.5**: рамку зараховують, якщо IoU з ground-truth ≥ 0.5. Піднімеш цей поріг до 0.75 — вимога до точності рамок зросте, і та сама модель покаже нижчий mAP (звідси й строгіша метрика mAP@[0.5:0.95], усереднена по порогах від 0.5 до 0.95). Тут `τ` не торкається NMS — він лише визначає планку «достатньо точного» збігу при підрахунку.

🧮 **Worked-приклад: як поріг упевненості рухає точність і повноту.**

```
Кадр: 4 справжні цілі. Після NMS лишилось 5 рамок (відсортовані за впевненістю),
для кожної відомо, чи вона лягає на справжню ціль (IoU ≥ 0.5):
  conf 0.95 → правдива (TP)
  conf 0.88 → правдива (TP)
  conf 0.60 → хибна    (FP)
  conf 0.55 → правдива (TP)
  conf 0.40 → правдива (TP)

Поріг c = 0.50  (беремо все ≥ 0.50): TP=3, FP=1, FN=1 (ціль conf 0.40 відсіяна)
   precision = 3/4 = 0.75      recall = 3/4 = 0.75

Поріг c = 0.30  (беремо все ≥ 0.30): TP=4, FP=1, FN=0
   precision = 4/5 = 0.80      recall = 4/4 = 1.00

Поріг c = 0.70  (беремо все ≥ 0.70): TP=2, FP=0, FN=2
   precision = 2/2 = 1.00      recall = 2/4 = 0.50
```

Та сама модель, ті самі рамки — три різні «якості» залежно від одного порога. При `c = 0.70` детектор не бреше зовсім (точність 1.0), зате сліпне на половину цілей (повнота 0.5). При `c = 0.30` бачить усіх (повнота 1.0) ціною однієї хибної тривоги. Жодна точка не «правильна» сама по собі — правильну вибирає **задача**: для детектора перешкод тягнемо повноту вгору (краще зайва тривога, ніж пропущений стовп), для детектора, що витрачає дорогий ресурс, — точність (хибна тривога коштує надто дорого). Саме тому поріг крутять під борт, а не лишають заводський, і саме тому в бенчмарку дивляться на криву та mAP, а не на одне ефектне число.
