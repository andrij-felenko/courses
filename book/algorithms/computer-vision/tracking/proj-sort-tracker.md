# ⚙️ Мінімальний SORT-трекер на C

## Задача

Маємо потік детекцій: щокадру детектор дає список габаритних рамок, але **без номерів** — він не знає, чи ця рамка та сама, що секунду тому, чи нова. Треба перетворити цей рій безіменних рамок на **треки**: стійкі об'єкти зі сталими номерами, що переживають короткі пропуски (ціль на кадр сховалась) і не плодяться від хибних спрацювань детектора. Це і є **SORT** (англ. *Simple Online and Realtime Tracking*) — і вся його краса в тім, що він робить це **без** єдиного погляду на пікселі, самими лише рамками, у пару сотень рядків.

Мета — один самодостатній файл на C, без зовнішніх залежностей, який можна вкласти в бортову прошивку: подаєш масив рамок кадру — отримуєш оновлений список треків із номерами.

## Ідея

SORT складають рівно чотири деталі, кожну з яких ми реалізуємо:

1. **Фільтр Калмана** на кожен трек — веде стан [центр, розмір, швидкості] і дає **прогноз** рамки на цей кадр. Щоб код лишився коротким і дешевим, скористаємося тим, що в моделі сталої швидкості координати **незалежні**: замість однієї матриці 8×8 — чотири крихітні фільтри 2×2 (пара «координата + її швидкість»). Апарат цих фільтрів — у [математичній вставці про стан бокс-трекера](book:algorithms/tracking/math-kf-tracking-state.md).
2. **Матриця вартості** 1 − IoU між прогнозами треків і свіжими детекціями.
3. **Прив'язка** — добір пар трек↔детекція. Класичний SORT бере вінгерський алгоритм; ми візьмемо **жадібний** добір за найменшою вартістю — для типових десятків цілей різниця в якості мала, а коду на порядок менше (повноцінний вінгерський з обробкою прямокутних матриць сам тягне на сотню рядків). Де щільність висока — зноску на вінгерський лишаємо в коментарі.
4. **Життєвий цикл** — народження пробних треків із непов'язаних детекцій, підвищення їх до підтверджених після min_hits збігів, убивання після max_missed пропусків.

Складаємо це знизу вгору: спершу скалярний фільтр 2×2, тоді IoU, тоді один кадр трекера.

## Код

### Скалярний фільтр Калмана 2×2

Кожна координата рамки веде власний фільтр зі станом [значення, швидкість]. Це прямий код рівнянь predict/update для моделі сталої швидкості; усі матричні добутки для 2×2 розписано в скаляри, тож ні циклів, ні обернень матриць:

:::tabs
```cpp
#include <stdint.h>
#include <stdbool.h>
#include <math.h>
#include <string.h>

/* Один канал: стан [v, vel], коваріація P (2x2 симетрична: p00,p01,p11). */
typedef struct {
    float v, vel;            /* значення та його швидкість */
    float p00, p01, p11;     /* коваріація стану */
    float q_pos, q_vel, r;   /* шум процесу (поз./швид.) і шум виміру */
} KF1;

static void kf1_init(KF1 *k, float v0, float q_pos, float q_vel, float r) {
    k->v = v0;  k->vel = 0.0f;
    k->p00 = 10.0f;  k->p01 = 0.0f;  k->p11 = 1000.0f;  /* P широка по швидкості */
    k->q_pos = q_pos;  k->q_vel = q_vel;  k->r = r;
}

/* PREDICT: x ← F·x,  P ← F·P·Fᵀ + Q   (Δt = 1 кадр) */
static void kf1_predict(KF1 *k) {
    k->v += k->vel;                                  /* v' = v + vel */
    k->p00 += 2.0f * k->p01 + k->p11 + k->q_pos;     /* розкручений F·P·Fᵀ */
    k->p01 += k->p11;
    k->p11 += k->q_vel;
}

/* UPDATE: стягнути стан до виміру z */
static void kf1_update(KF1 *k, float z) {
    float y = z - k->v;                 /* нев'язка */
    float s = k->p00 + k->r;            /* коваріація нев'язки */
    float k0 = k->p00 / s;              /* підсилення (положення) */
    float k1 = k->p01 / s;              /* підсилення (швидкість) */
    k->v   += k0 * y;
    k->vel += k1 * y;
    float p00 = (1.0f - k0) * k->p00;   /* P ← (I − K·H)·P */
    float p01 = (1.0f - k0) * k->p01;
    float p11 = k->p11 - k1 * k->p01;
    k->p00 = p00;  k->p01 = p01;  k->p11 = p11;
}
```

### Рамка, IoU і трек

Рамку веде по одному фільтру на кожну з чотирьох координат (центр x, центр y, ширина, висота). Структура треку тримає ці чотири фільтри плюс лічильники життєвого циклу:

:::tabs
```cpp
typedef struct { float x, y, w, h; } Rect;   /* центр (x,y) і розмір */

typedef enum { TENTATIVE, CONFIRMED, DELETED } TrackState;

typedef struct {
    int        id;                /* стійкий номер об'єкта */
    KF1        fx, fy, fw, fh;    /* 4 незалежні канали фільтра */
    TrackState state;
    int        hits;              /* збігів поспіль */
    int        misses;           /* кадрів поспіль без детекції */
    int        age;              /* усього кадрів живе */
} Track;

/* перекриття двох рамок: перетин до об'єднання (0..1) */
static float iou(Rect a, Rect b) {
    float ax0 = a.x - a.w*0.5f, ax1 = a.x + a.w*0.5f;
    float ay0 = a.y - a.h*0.5f, ay1 = a.y + a.h*0.5f;
    float bx0 = b.x - b.w*0.5f, bx1 = b.x + b.w*0.5f;
    float by0 = b.y - b.h*0.5f, by1 = b.y + b.h*0.5f;
    float ix = fmaxf(0.0f, fminf(ax1,bx1) - fmaxf(ax0,bx0));
    float iy = fmaxf(0.0f, fminf(ay1,by1) - fmaxf(ay0,by0));
    float inter = ix * iy;
    float uni   = a.w*a.h + b.w*b.h - inter;
    return uni > 0.0f ? inter / uni : 0.0f;
}

static Rect track_predict(Track *t) {            /* predict усіх каналів → прогноз рамки */
    kf1_predict(&t->fx);  kf1_predict(&t->fy);
    kf1_predict(&t->fw);  kf1_predict(&t->fh);
    Rect r = { t->fx.v, t->fy.v, t->fw.v, t->fh.v };
    return r;
}

static void track_update(Track *t, Rect d) {     /* update усіх каналів свіжою детекцією */
    kf1_update(&t->fx, d.x);  kf1_update(&t->fy, d.y);
    kf1_update(&t->fw, d.w);  kf1_update(&t->fh, d.h);
}

static void track_init(Track *t, int id, Rect d) {
    t->id = id;  t->state = TENTATIVE;
    t->hits = 1;  t->misses = 0;  t->age = 1;
    /* шуми: положення точніше за розмір; підбирати під камеру */
    kf1_init(&t->fx, d.x, 1.0f, 10.0f, 1.0f);
    kf1_init(&t->fy, d.y, 1.0f, 10.0f, 1.0f);
    kf1_init(&t->fw, d.w, 1.0f, 10.0f, 4.0f);
    kf1_init(&t->fh, d.h, 1.0f, 10.0f, 4.0f);
}
```
```python
from dataclasses import dataclass
from enum import Enum


@dataclass
class Rect:               # центр (x,y) і розмір
    x: float
    y: float
    w: float
    h: float


class TrackState(Enum):
    TENTATIVE = 0
    CONFIRMED = 1
    DELETED = 2


# перекриття двох рамок: перетин до об'єднання (0..1)
def iou(a, b):
    ax0, ax1 = a.x - a.w * 0.5, a.x + a.w * 0.5
    ay0, ay1 = a.y - a.h * 0.5, a.y + a.h * 0.5
    bx0, bx1 = b.x - b.w * 0.5, b.x + b.w * 0.5
    by0, by1 = b.y - b.h * 0.5, b.y + b.h * 0.5
    ix = max(0.0, min(ax1, bx1) - max(ax0, bx0))
    iy = max(0.0, min(ay1, by1) - max(ay0, by0))
    inter = ix * iy
    uni = a.w * a.h + b.w * b.h - inter
    return inter / uni if uni > 0.0 else 0.0


class Track:
    def __init__(self, id, d):
        self.id = id                       # стійкий номер об'єкта
        self.state = TrackState.TENTATIVE
        self.hits = 1                      # збігів поспіль
        self.misses = 0                    # кадрів поспіль без детекції
        self.age = 1                       # усього кадрів живе
        # шуми: положення точніше за розмір; підбирати під камеру
        self.fx = KF1(d.x, 1.0, 10.0, 1.0)  # 4 незалежні канали фільтра
        self.fy = KF1(d.y, 1.0, 10.0, 1.0)
        self.fw = KF1(d.w, 1.0, 10.0, 4.0)
        self.fh = KF1(d.h, 1.0, 10.0, 4.0)

    def predict(self):                     # predict усіх каналів → прогноз рамки
        self.fx.predict(); self.fy.predict()
        self.fw.predict(); self.fh.predict()
        return Rect(self.fx.v, self.fy.v, self.fw.v, self.fh.v)

    def update(self, d):                   # update усіх каналів свіжою детекцією
        self.fx.update(d.x); self.fy.update(d.y)
        self.fw.update(d.w); self.fh.update(d.h)
```

### Один кадр трекера

Тут зведено всі чотири деталі. Порядок строгий: спершу **прогноз** усіх треків, тоді **прив'язка** до детекцій, тоді **оновлення** пар, **народження** нових треків із непов'язаних детекцій і **вибирання** мертвих:

:::tabs
```cpp
#define MAX_TRACKS 64
#define IOU_GATE   0.30f     /* поріг прив'язки: нижче — не пара */
#define MIN_HITS   3         /* збігів до «підтверджено» */
#define MAX_MISSED 30        /* пропусків до смерті (≈1 с при 30 к/с) */

typedef struct {
    Track tracks[MAX_TRACKS];
    int   n;                 /* активних треків */
    int   next_id;           /* лічильник видачі номерів */
} Sort;

static void sort_init(Sort *s) { s->n = 0; s->next_id = 1; }

/* Один кадр: dets[nd] — рамки від детектора. Після виклику s->tracks оновлено. */
void sort_step(Sort *s, const Rect *dets, int nd) {
    Rect pred[MAX_TRACKS];
    bool det_used[64] = { false };          /* чи вже прив'язана детекція */
    int  matched[MAX_TRACKS];               /* індекс детекції для треку або -1 */

    /* 1. ПРОГНОЗ кожного треку на цей кадр */
    for (int i = 0; i < s->n; i++) {
        pred[i] = track_predict(&s->tracks[i]);
        matched[i] = -1;
    }

    /* 2. ЖАДІБНА ПРИВ'ЯЗКА: повторно беремо глобально найкращу пару (макс. IoU).
          (Класичний SORT бере вінгерський алгоритм — оптимальніше при щільних цілях.) */
    for (;;) {
        float best = IOU_GATE;              /* нижче порога не приймаємо */
        int bi = -1, bj = -1;
        for (int i = 0; i < s->n; i++) {
            if (matched[i] >= 0) continue;
            for (int j = 0; j < nd; j++) {
                if (det_used[j]) continue;
                float v = iou(pred[i], dets[j]);
                if (v > best) { best = v; bi = i; bj = j; }
            }
        }
        if (bi < 0) break;                  /* більше пар над порогом немає */
        matched[bi] = bj;
        det_used[bj] = true;
    }

    /* 3. ОНОВИТИ треки за результатом прив'язки */
    for (int i = 0; i < s->n; i++) {
        Track *t = &s->tracks[i];
        t->age++;
        if (matched[i] >= 0) {
            track_update(t, dets[matched[i]]);
            t->hits++;  t->misses = 0;
            if (t->state == TENTATIVE && t->hits >= MIN_HITS)
                t->state = CONFIRMED;
        } else {
            t->misses++;
            if (t->state == TENTATIVE)        t->state = DELETED;  /* проба зірвалась */
            else if (t->misses > MAX_MISSED)  t->state = DELETED;  /* зник надовго */
        }
    }

    /* 4. НАРОДИТИ нові треки з детекцій, що лишились без пари */
    for (int j = 0; j < nd && s->n < MAX_TRACKS; j++) {
        if (det_used[j]) continue;
        track_init(&s->tracks[s->n], s->next_id++, dets[j]);
        s->n++;
    }

    /* 5. ВИБРАТИ мертві треки (стиснути масив на місці) */
    int k = 0;
    for (int i = 0; i < s->n; i++)
        if (s->tracks[i].state != DELETED) s->tracks[k++] = s->tracks[i];
    s->n = k;
}
```
```python
MAX_TRACKS = 64
IOU_GATE   = 0.30    # поріг прив'язки: нижче — не пара
MIN_HITS   = 3       # збігів до «підтверджено»
MAX_MISSED = 30      # пропусків до смерті (≈1 с при 30 к/с)


class Sort:
    def __init__(self):
        self.tracks = []     # активні треки
        self.next_id = 1     # лічильник видачі номерів

    # Один кадр: dets — рамки від детектора. Після виклику self.tracks оновлено.
    def step(self, dets):
        n = len(self.tracks)
        det_used = [False] * len(dets)      # чи вже прив'язана детекція
        matched = [-1] * n                  # індекс детекції для треку або -1

        # 1. ПРОГНОЗ кожного треку на цей кадр
        pred = [t.predict() for t in self.tracks]

        # 2. ЖАДІБНА ПРИВ'ЯЗКА: повторно беремо глобально найкращу пару (макс. IoU).
        #    (Класичний SORT бере вінгерський алгоритм — оптимальніше при щільних цілях.)
        while True:
            best = IOU_GATE                 # нижче порога не приймаємо
            bi = bj = -1
            for i in range(n):
                if matched[i] >= 0:
                    continue
                for j in range(len(dets)):
                    if det_used[j]:
                        continue
                    v = iou(pred[i], dets[j])
                    if v > best:
                        best, bi, bj = v, i, j
            if bi < 0:                      # більше пар над порогом немає
                break
            matched[bi] = bj
            det_used[bj] = True

        # 3. ОНОВИТИ треки за результатом прив'язки
        for i, t in enumerate(self.tracks):
            t.age += 1
            if matched[i] >= 0:
                t.update(dets[matched[i]])
                t.hits += 1
                t.misses = 0
                if t.state == TrackState.TENTATIVE and t.hits >= MIN_HITS:
                    t.state = TrackState.CONFIRMED
            else:
                t.misses += 1
                if t.state == TrackState.TENTATIVE:      # проба зірвалась
                    t.state = TrackState.DELETED
                elif t.misses > MAX_MISSED:              # зник надовго
                    t.state = TrackState.DELETED

        # 4. НАРОДИТИ нові треки з детекцій, що лишились без пари
        for j in range(len(dets)):
            if len(self.tracks) >= MAX_TRACKS:
                break
            if det_used[j]:
                continue
            self.tracks.append(Track(self.next_id, dets[j]))
            self.next_id += 1

        # 5. ВИБРАТИ мертві треки
        self.tracks = [t for t in self.tracks if t.state != TrackState.DELETED]
```
:::

Усе. Близько ста семидесяти рядків — і це повний робочий трекер: подаєш рамки кадру в `sort_step`, читаєш `s->tracks` (беручи назовні лише `CONFIRMED`), номери `id` тримаються стабільно, короткі пропуски переживаються прогнозом фільтра.

Порядок п'яти кроків у `sort_step` не довільний, і переставити їх не можна без поломки. Прогноз мусить іти **перший** — інакше прив'язка звіряла б детекції зі **вчорашніми** рамками треків, а не з тим, де ціль має бути **сьогодні**, і IoU систематично просідала б на швидких цілях. Народження нових треків мусить іти **після** оновлення наявних, інакше свіжа детекція, що насправді належить наявному треку, могла б помилково завести дубль. А вибирання мертвих — **останнім**, бо доти індекси `matched[i]` указують на треки в їхньому теперішньому порядку; почисти масив раніше — і ці індекси з'їдуть. Це типова риса трекера: він не одна формула, а конвеєр, де кожен крок спирається на стан, залишений попереднім.

Одна тонкість із пам'яттю варта окремої уваги. На кроці 5 ми стискаємо масив `s->tracks` на місці, копіюючи живі треки вперед. Це безпечно саме тому, що `Track` — самодостатня структура **за значенням**: усе, що треку треба (чотири фільтри, лічильники, номер), лежить усередині неї, без указівників назовні. Якби трек тримав, скажімо, указівник на свій буфер ознак вигляду (як у DeepSORT), просте копіювання структури породило б два треки, що ділять один буфер, — і звільнення його при смерті одного зіпсувало б другий. Тут цієї біди немає, тож стиснення масиву — це чисте копіювання без жодного володіння ресурсами.

## Worked-приклад: три кадри одного об'єкта

Прогляньмо, що буде з єдиною ціллю, яка їде вправо й на третьому кадрі **зникає** (детектор її проґавив). Деталі — як міняються лічильники й стан:

```
почат.:  s->n = 0,  next_id = 1

кадр 1:  dets = [ (300,200,40,30) ]
  прогноз: треків нема → нема
  прив'язка: нема пар
  народження: новий трек id=1, стан TENTATIVE, hits=1, misses=0
  → s->n=1; назовні НЕ віддаємо (ще проба)

кадр 2:  dets = [ (312,196,40,30) ]
  прогноз треку 1: фільтр щойно з нуля → ≈(300,200,40,30)
  прив'язка: IoU(прогноз, det) ≈ 0.79 > 0.30 → пара
  оновлення: track_update; hits=2, misses=0; ще TENTATIVE (2 < MIN_HITS=3)
  → s->n=1; ще не віддаємо

кадр 3:  dets = []   (детектор проґавив ціль)
  прогноз треку 1: фільтр веде НАОСЛІП → ≈(324,192,40,30)
  прив'язка: детекцій нема → matched[0] = -1
  оновлення: misses=1; трек ще TENTATIVE → DELETED!  (проба зірвалась)
  → s->n=0
```

Тут видно тонкість, варту уваги: **пробний** трек гине від **першого** ж пропуску, тож короткий збій детектора на кадрі 3 **вбив** ще не дозрілий трек. Якби трек уже був `CONFIRMED` (пережив MIN_HITS збігів), пропуск лише наростив би `misses`, а фільтр вів би ціль наосліп ще до MAX_MISSED кадрів. Саме тому MIN_HITS не роблять завеликим: поки трек «доводить себе», він крихкий до будь-якого блимання детектора.

## Складність і пастки

**Вартість — O(n·m) на кадр** на прив'язці (n треків × m детекцій), плюс O(n) на жадібний добір повторюваний щонайбільше min(n,m) разів — тобто грубо O(n²·m) у найгіршому разі. Для десятків цілей це мікросекунди; фільтри 2×2 ще дешевші. Замінити жадібний добір на вінгерський — це краща якість при щільних цілях ціною O(n³) і сотні рядків коду.

- **Жадібний проти вінгерського.** Жадібний добір бере найкращу пару поспіль і може віддати детекцію не тому треку, коли двоє претендують на одну рамку. На рідких цілях це майже ніколи не спрацьовує, але в щільному натовпі дає зайві підміни номерів. Якщо вони муляють — став вінгерський алгоритм (порядок виклику й структура `sort_step` лишаються ті самі, міняється лише блок 2).
- **Δt = 1 «на кадр».** Код припускає рівні кадри (predict крокує рівно на один кадр). Якщо кадри йдуть нерівномірно (пропуски в захопленні), масштаб швидкості попливе. Лікують передачею справжнього Δt у predict (домноживши швидкісні члени) — як у дискретному [ПІД із виміряним кроком](book:algorithms/discrete-pid).
- **Фіксований масив детекцій.** `det_used[64]` обмежує кадр 64 детекціями; на більше — підняти розмір або винести в параметр. Так само `MAX_TRACKS` обмежує число одночасних треків.
- **Лише геометрія.** Цей SORT прив'язує самими рамками — і тому **плутає номери**, коли дві однакові цілі перетинаються (їхні прогнози перекриваються, IoU не розрізняє). Лікування — додати ознаку зовнішності до вартості, тобто перейти до DeepSORT; чистий SORT із цим зробити нічого не може.
- **Затримка підтвердження.** Назовні віддають лише `CONFIRMED` треки, тож нова ціль з'являється у виході із запізненням на MIN_HITS кадрів. Це свідома плата за відсів хибних спрацювань; зменшити MIN_HITS — швидше показувати, але й більше фантомів.

## Підсумок

Повний SORT — це чотири деталі в строгому порядку: **прогноз** кожного треку фільтром Калмана (чотири дешеві канали 2×2 замість 8×8), **матриця 1 − IoU**, **прив'язка** (жадібна тут, вінгерська в класиці) і **життєвий цикл** — народження пробних, підтвердження після min_hits, смерть після max_missed. Усе на самих рамках, без погляду на пікселі, у пару сотень рядків без залежностей — тому SORT і кладеться на бортове залізо. Його єдина принципова межа — плутанина номерів на перетині однакових цілей, бо гола геометрія не зберігає особистості; усе інше тримається на трьох порогах (IOU_GATE, MIN_HITS, MAX_MISSED), якими й налаштовують характер трекера під задачу.
