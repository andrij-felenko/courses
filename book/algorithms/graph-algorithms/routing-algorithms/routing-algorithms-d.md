# Алгоритми маршрутизації

<preknowlist>
- [Алгоритм Дейкстри](book:algorithms/dijkstra) — обчислення найкоротших шляхів у графі з невід'ємними вагами ребер.
- [Алгоритм Беллмана–Форда](book:algorithms/bellman-ford) — релаксація ребер та обробка графа з можливими від'ємними вагами.
- [Пошук у ширину (BFS)](book:algorithms/breadth-first-search) — обхід неуваженого графа рівень за рівнем для пошуку найкоротшого шляху за кількістю ребер.
</preknowlist>

Коли мережевий пакет із даними прибуває на вхідний інтерфейс маршрутизатора в Токіо із заголовочною IP-адресою призначення в Лондоні, пристрій мусить за частки мікросекунди прийняти локальне рішення: у який саме з десятків вихідних фізичних портів переслати цей пакет. У цей момент маршрутизатор не має ані чарівного центрального оракула, який підказував би правильні кроки згори, ані часу на обхід мільйона можливих комбінацій шляхів. Єдине, чим володіє пристрій, — це локальна таблиця просування (англ. *Forwarding Table*), сформована в результаті постійної, розподіленої та автономної співпраці тисяч незалежних вузлів. Процес обчислення, узгодження та підтримки цих шляхів у динамічному графі мережі становить суть **алгоритмів маршрутизації** (англ. *routing algorithms*, від фр. *route* — шлях, дорога).

Якщо класичні алгоритми пошуку найкоротших шляхів на графі — такі як [алгоритм Дейкстри](book:algorithms/dijkstra) чи [алгоритм Беллмана–Форда](book:algorithms/bellman-ford) — працюють у припущенні, що вся структура графа `G = (V, E)` повністю відома й зберігається в оперативній пам'яті одного процесора, то алгоритми мережевої маршрутизації розв'язують значно складніше завдання. Вони працюють у повністю розподіленому середовищі, де кожен вузол початково знає лише своїх прямих фізичних сусідів, зв'язки між якими можуть у будь-який момент обірватися, затримки змінитись, а сам граф зрости до мільйонів вершин.

### Проблема розподіленого вибору шляху у графі

Щоб зрозуміти, чому простого запуску алгоритму Дейкстри на одному сервері недостатньо для керування мережею, розділимо дві базові функції мережевого обладнання: **просування** (англ. *forwarding*) та **маршрутизацію** (англ. *routing*).

Просування — це дія на рівні каналів передачі даних (англ. *data plane*): пакет входить в один порт, роутер дивиться у швидку апаратну таблицю (CAM/TCAM пам'ять) і комутує пакет у вихідний порт. Ця дія виконується для кожного пакета окремо й забирає наносекунди. 

Маршрутизація — це дія на рівні управління (англ. *control plane*): це обчислювальний процес, під час якого роутери обмінюються службовими повідомленнями, вивчають топологію мережі та будують ту саму таблицю просування.

```
+-------------------------------------------------------------------+
|                        CONTROL PLANE (Управління)                 |
|  [ Протоколи маршрутизації: OSPF / BGP / RIP / IS-IS ]            |
|  Обмін службовими повідомленнями та обчислення графів              |
|                                 │                                 |
|                                 ▼                                 |
|                  Таблиця маршрутизації (RIB)                      |
+--------------------------------─┼---------------------------------+
                                  │ Завантаження кращих шляхів
+--------------------------------─┼---------------------------------+
|                                 ▼                                 |
|                  Таблиця просування (FIB)                         |
|                                 │                                 |
|  Вхідний пакет ──► [ Апаратний пошук TCAM ] ──► Вихідний порт     |
|                        DATA PLANE (Дані)                          |
+-------------------------------------------------------------------+
```

Фундаментальна проблема розподіленої маршрутизації полягає в тому, що жоден вузол не володіє повним знанням про стан усіх лінків у реальному часі. Інформація про зміни топології поширюється мережею зі скінченною швидкістю, обмеженою затримкою поширення сигналу `T_prop` та часом обробки повідомлень. Якщо вузли приймають рішення на основі застарілих або суперечливих даних, у графі виникають **петлі маршрутизації** (англ. *routing loops*) — ситуації, коли пакет безкінечно циркулює між групою роутерів, виснажуючи пропускну здатність каналів.

Окрім блокування петель, алгоритми маршрутизації мусять задовольняти чотирьом жорстким інженерним вимогам:
1. **Швидка збіжність** (англ. *convergence*): після зміни топології (обриву лінії чи включення нового роутера) усі вузли повинні якнайшвидше прийти до єдиної узгодженої оцінки найкоротших шляхів.
2. **Масштабованість** (англ. *scalability*): обсяг пам'яті та службового трафіку не повинен рости експоненційно з ростом кількості вузлів у графі `|V|`.
3. **Стійкість до відмов** (англ. *robustness*): збій одного чи кількох роутерів не повинен паралізувати роботу всієї мережі.
4. **Автономність та локальність дій**: кожен вузол має приймати коректні рішення, спираючись лише на локальний обмін із сусідами.

### Класифікація алгоритмів маршрутизації

Залежно від способу збору інформації про граф та обсягу знань, яким володіє кожен вузол, алгоритми маршрутизації поділяють на три великі класи:

```
                               Алгоритми маршрутизації
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        ▼                                 ▼                                 ▼
Дистанційно-векторні             Стану зв'язків                    Шляхово-векторні
(Distance-Vector)                (Link-State)                      (Path-Vector)
Розподілений Беллман-Форд        Локальний Дейкстра                Політики та AS-Path
Приклад: RIP                     Приклад: OSPF, IS-IS              Приклад: BGP
```

- **Дистанційно-векторні алгоритми (Distance-Vector / DV)**: вузли знають лише віддаленість (дистанцію) та напрямок (вектор/наступний хоп) до інших вершин. Вузли не знають повного вигляду графа й обмінюються з сусідами підсумковими векторами обчислених відстаней.
- **Алгоритми стану зв'язків (Link-State / LS)**: кожен вузол за допомогою затоплення розсилає усім іншим первинну інформацію про свої прямі лінки. Отримавши всі анонси, кожен роутер відновлює у пам'яті *повноцінний граф мережі* `G = (V, E)` і локально запускає [алгоритм Дейкстри](book:algorithms/dijkstra).
- **Шляхово-векторні алгоритми (Path-Vector / PV)**: модифікація дистанційно-векторного підходу для міждоменної маршрутизації у глобальному Інтернеті. Замість чистої числової віддаленості анонс містить повний список Автономних Систем (англ. *Autonomous Systems*), через які пройшов маршрут, що уможливлює миттєве виявлення петель та гнучкий вибір шляху на основі комерційних політик.

Окрім цього, маршрутизацію ділять на **внутрішньодоменну** (IGP, англ. *Interior Gateway Protocol* — OSPF, RIP, IS-IS), яка працює всередині однієї організації з єдиною метрикою якості, та **міждоменну** (EGP, англ. *Exterior Gateway Protocol* — BGP), яка з'єднує незалежні мережі провайдерів у глобальний Інтернет. Детальніше про еволюційні етапи створення цих протоколів див. у 📜 [Історії алгоритмів маршрутизації: від ARPANET до OSPF та BGP](book:algorithms/routing-algorithms/hist-routing-protocols.md).

### Дистанційно-векторні алгоритми (Distance-Vector)

В основу дистанційно-векторних алгоритмів закладено ітеративний розподілений варіант [алгоритму Беллмана–Форда](book:algorithms/bellman-ford). Кожен вузол `x` підтримує вектор відстаней `D_x = [d_x(y) : y in V]`, де `d_x(y)` — поточна оцінка вартості найкоротшого шляху від `x` до `y`.

Окрім власних оцінок, вузол `x` зберігає у пам'яті вектори відстаней всіх своїх прямих сусідів `v in N(x)`. Основна операція оновлення полягає у послідовному застосуванні рекурентного рівняння Беллмана–Форда:

```
d_x(y) = min_{v ∈ N(x)} { c(x, v) + d_v(y) }
```

де `c(x, v)` — вартість прямого зв'язку між вузлом `x` та його сусідом `v`.

Сусід `v*`, на якому досягається цей мінімум, стає наступним хопом (`next_hop`) у таблиці маршрутизації вузла `x` для досягнення цілі `y`.

![Дистанційно-векторне оновлення за рівнянням Беллмана–Форда](/book/algorithms/graph-algorithms/routing-algorithms/img/dv-update.svg)
*Дистанційно-векторне оновлення: вузол B отримує вектор від сусіда C і переобчислює найкоротші відстані до віддалених вершин за рівнянням Беллмана–Форда.*

Алгоритм працює асинхронно і крок за кроком виконує таку циклічну процедуру:
1. **Очікування**: вузол спить, поки не отримає новий вектор від якогось із сусідів або поки не зміниться вартість локального лінка.
2. **Переобчислення**: вузол перераховує свій вектор `D_x` за рівнянням Беллмана–Форда.
3. **Анонсування**: якщо хоча б одна оцінка `d_x(y)` у векторі змінилася, вузол відправляє оновлений вектор усім своїм прямим сусідам.

#### Проблема відліку до нескінченності (Count-to-Infinity)

Головний недолік дистанційно-векторних алгоритмів полягає у реакції на погіршення зв'язку або обрив ребер. У той час як хороші новини (поява нового короткого лінка) розповсюджуються мережею дуже швидко, погані новини (обрив зв'язку) поширюються надзвичайно повільно, спричиняючи феномен **відліку до нескінченності** (англ. *Count-to-Infinity Problem*).

Розглянемо просту мережу з трьох вузлів: `A — B — C`, де ваги ребер дорівнюють 1.
У стабільному стані оцінки відстані до `C` дорівнюють: `d_B(C) = 1`, `d_A(C) = 2` (через `B`).

Припустимо, що лінк `B — C` обривається. Вузол `B` бачить втрату лінка, але в його пам'яті зберігається останнє значення від `A`: `d_A(C) = 2`. Вузол `B` помилково вважає: «я можу дістатися до `C` через `A` за ціною 1 + 2 = 3»!

![Проблема відліку до нескінченності при обриві зв'язку](/book/algorithms/graph-algorithms/routing-algorithms/img/count-to-infinity.svg)
*Механізм зациклення відліку до нескінченності: при обриві лінка B-C вузли A і B почергово нарощують оцінку відстані один через одного, вважаючи сусідній вузол обхідним шляхом.*

Після цього `B` анонсує вузлу `A` нове значення `d_B(C) = 3`. Вузол `A`, чий маршрут до `C` йшов через `B`, бачить нову оцінку від `B` і оновлює свою відстань: `d_A(C) = 1 + 3 = 4`. Далі `B` піднімає свою оцінку до 5, `A` до 6, і так далі. Оцінки монотонно зростають до нескінченності `INF`, а пакети до `C` застрягають у нескінченній петлі між `A` та `B`.

Строге математичне доведення феномену відліку до нескінченності та умов збіжності наведено у 🧮 [Математиці збіжності та проблеми відліку до нескінченності](book:algorithms/routing-algorithms/math-dv-convergence.md).

#### Засоби ліквідації петель: Split Horizon та Poison Reverse

Щоб запобігти двовузловим петлям, у протоколах дистанційно-векторної маршрутизації (таких як RIP) застосовують три інженерні прийоми:

1. **Розщеплення горизонту** (англ. *Split Horizon*): вузол `A` не повинен анонсувати маршрут до вершини `C` тому сусіду (`B`), через якого сам вузол `A` досягає цієї вершини `C`.
2. **Отруйний реверс** (англ. *Poison Reverse*): замість приховування маршруту, вузол `A` явно анонсує вузлу `B` нескінченну відстань `d_A(C) = INF`. Отримавши `d_A(C) = INF`, вузол `B` ніколи не спробує використати `A` як обхідний шлях до `C`.
3. **Таймери утримання** (англ. *Hold-Down Timers*): після отримання повідомлення про обрив маршруту вузол ігнорує будь-які нові анонси про цей маршрут протягом фіксованого інтервалу часу, даючи мережі можливість очиститися від застарілих векторів.

> 🔧 **Навіщо це.** Дистанційно-векторний підхід вимагає мінімум пам'яті `O(|V|)` і є ідеальним для малих вбудованих мереж, роутерів домашнього сегмента або промислових контролерів. Проте через повільну збіжність на великих графах та уразливість до тривузлових петель його замінили алгоритмами стану зв'язків.

Практичний приклад реалізації дистанційно-векторного алгоритму з розщепленням горизонту мовами C та C++ розібрано у ⚙️ [Реалізації дистанційно-векторного алгоритму маршрутизації з отруйним реверсом](book:algorithms/routing-algorithms/proj-distance-vector.md).

### Алгоритми стану зв'язків (Link-State)

Алгоритми стану зв'язків (англ. *Link-State algorithms*) кардинально змінюють філософію обміну інформацією. Замість того щоб передавати сусідам підраховані вектори відстаней («обчислені результати»), кожен вузол передає первинні факти про власне оточення («стан своїх лінків»).

Робота Link-State алгоритму складається з п'яти послідовних фаз:

```
1. Виявлення сусідів (Hello-пакети) ──► 2. Вимірювання вартості лінків (Delay/Cost)
                                                        │
                                                        ▼
4. Обчислення дерева Дейкстри       ◄── 3. Затоплення LSA пакетів (Flooding)
           │
           ▼
5. Формування таблиці просування (FIB)
```

1. **Виявлення сусідів**: при включенні роутер надсилає у свої фізичні інтерфейси коротке повідомлення `Hello` для виявлення прямих сусідів.
2. **Вимірювання вартості лінків**: вузол вимірює затримку, пропускну здатність або вартість кожної лінії зв'язку зі своїми сусідами.
3. **Формування та затоплення LSA**: вузол створює пакет стану зв'язків LSA (англ. *Link-State Advertisement*), який містить список ідентифікаторів сусідів та вагу відповідних ребер. Цей пакет розсилається всім вузлам мережі шляхом надійного **затоплення** (англ. *flooding*).
4. **Побудова картографії графа**: кожен вузол, отримавши LSA від усіх інших роутерів, будує у своїй пам'яті ідентичну точну копію графа мережі `G = (V, E)`.
5. **Локальне обчислення**: кожен вузол запускає [алгоритм Дейкстри](book:algorithms/dijkstra) від самого себе як кореня, обчислюючи дерево найкоротших шляхів (SPT, англ. *Shortest Path Tree*) і будуючи таблицю просування.

![Затоплення LSA та локальне обчислення дерева найкоротших шляхів](/book/algorithms/graph-algorithms/routing-algorithms/img/link-state.svg)
*Двоетапний процес Link-State: ліворуч — надійне затоплення пакетами LSA для побудови карти графа; праворуч — локальний запуск алгоритму Дейкстри на ізольованому роутері.*

#### Надійне затоплення та керування порядковими номерами

Головне завдання фази затоплення — гарантувати, що кожна LSA досягне кожного вузла мережі без утворення нескінченних штормів дублікатів. 

Для цього кожна LSA містить:
- **Ідентифікатор джерела** (`Router ID`).
- **Порядковий номер** (англ. *Sequence Number*): 32-бітне число, що зростає при кожній новій зміні стану лінків.
- **Час життя** (англ. *Age*): таймер, що відраховує час перебування пакета в мережі.

Коли вузол `u` отримує LSA від джерела `s` з порядковим номером `seq`, він порівнює `seq` з уже збереженим значенням у своїй топологічній базі даних (LSDB, англ. *Link-State Database*):
- Якщо новий `seq` є **більшим**, вузол оновлює свою LSDB і пересилає пакет усім іншим своїм сусідам, окрім того, від якого пакет прийшов.
- Якщо `seq` **менший або дорівнює** збереженому, пакет вважається дублікатом і мовчки відкидається.

#### Ієрархічне декомпонування топології: OSPF Areas

Щоб алгоритм Дейкстри не перевантажував процесор у мережах із тисячами роутерів, протокол OSPF вводить ієрархічне розділення графа на **області** (англ. *Areas*).

```
                      +-----------------------------+
                      |   Backbone Area 0 (Магістраль)|
                      |    [ ABR 1 ]     [ ABR 2 ]  |
                      +-------┬─────────────┬-------+
                              │             │
              ┌───────────────┘             └───────────────┐
              ▼                                             ▼
   +--------------------+                        +--------------------+
   |   Area 1 (Звичайна)|                        |   Area 2 (Stub/NSSA)|
   | [ Router A ]       |                        | [ Router B ]       |
   | [ Router C ]       |                        | [ ASBR ] ──► BGP   |
   +--------------------+                        +--------------------+
```

- **Backbone Area 0 (Магістральна область)**: центральна частина мережі, до якої мусять підключатися всі інші області. Вона забезпечує транзит між областями.
- **ABR (Area Border Router, пограничний маршрутизатор області)**: роутер, що належить одночасно до Area 0 та локальної області. ABR агрегує префікси й надсилає у сусідні області лише сумарні анонси (LSA Type 3), приховуючи внутрішню топологію своєї області.
- **ASBR (Autonomous System Boundary Router)**: роутер, що імпортує зовнішні маршрути з інших протоколів (наприклад, BGP) у вигляді LSA Type 5.

Завдяки розділенню на області, при обриві лінка всередині Area 1 запуск алгоритму Дейкстри відбувається **лише у роутерів Area 1**. Решта мережі отримує лише незначне оновлення метрики без перепідрахунку графа, що забезпечує масштабованість Link-State на десятки тисяч вузлів.

### Шляхово-векторні алгоритми (Path-Vector)

Хоча Link-State алгоритми володіють високою швидкістю збіжності та стійкістю до петель, вони абсолютно **не масштабуються** на рівень глобального Інтернету з двох причин:
1. **Вимоги до пам'яті та процесора**: збереження графа з мільйона ребер і постійний перерахунок алгоритму Дейкстри `O(|E| + |V| log |V|)` зажадали б колосальних обчислювальних ресурсів на кожному глобальному роутері.
2. **Комерційні та політики безпеки**: провайдери не бажають розкривати внутрішню топологію своїх мереж конкурентам через LSA-пакети.

Для розв'язання цієї проблеми в міждоменній маршрутизації використовують **шляхово-векторні алгоритми** (англ. *Path-Vector Routing*), яскравим представником яких є протокол BGP (англ. *Border Gateway Protocol*).

Глобальний Інтернет розділено на **Автономні Системи** (AS) — мережі під управлінням єдиної адміністративної організації. У шляхово-векторному алгоритмі вузол анонсує сусідам не просто відстань до мережі призначення, а **повний ланцюжок Автономних Систем** (`AS_PATH`), через які мусить пройти пакет.

```
Префікс: 192.0.2.0/24
Анонс напрямку: AS100 ──► AS200 ──► AS300 ──► AS400
Маршрутний атрибут: AS_PATH = [AS300, AS200, AS100]
```

![Шляхово-векторна маршрутизація (Path-Vector) та запобігання петель](/book/algorithms/graph-algorithms/routing-algorithms/img/path-vector.svg)
*Запобігання петель у Path-Vector (BGP): якщо анонс маршруту повертається до автономної системи, чий номер уже є в списку AS_PATH, анонс негайно відкидається.*

Блокування петель у Path-Vector стає простим і строго гарантованим: **якщо маршрутизатор отримує анонс маршруту, у списку `AS_PATH` якого вже присутній номер його власної Автономної Системи, він негайно відкидає цей анонс.** 

Ця перевірка вимагає лише лінійного перегляду списку `O(k)`, де `k` — довжина шляху, без будь-яких складних графових обчислень.

#### Атрибути BGP та прийняття рішень (Decision Process)

На відміну від внутрішньодоменних протоколів, що шукають шлях із найменшою сумою затримок, BGP вибирає кращий маршрут на основі послідовного алгоритму оцінки векторних атрибутів (англ. *BGP Decision Process*):

```
1. Найвищий WEIGHT (локальний привабливий коефіцієнт роутера)
               │
               ▼
2. Найвищий LOCAL_PREF (пріоритет виходу з Автономної Системи)
               │
               ▼
3. Локально згенерований маршрут (Network / Redistribute)
               │
               ▼
4. Найкоротший список AS_PATH (найменша кількість AS)
               │
               ▼
5. Найнижчий ORIGIN (IGP < EGP < Incomplete)
               │
               ▼
6. Найнижчий MED (Multi-Exit Discriminator — побажання сусіда)
               │
               ▼
7. Перевага eBGP над iBGP (зовнішній маршрут кращий за внутрішній)
               │
               ▼
8. Найнижча IGP-метрика до next-hop (гаряча картопля / Hot-Potato Routing)
```

Завдяки такій базі атрибутів оператор мережі може налаштовувати гнучкі правила: наприклад, спрямовувати весь трафік до Google через дешевий піринговий канал (високий `LOCAL_PREF`), навіть якщо фізичний шлях через платного провайдера має меншу кількість хопів.

#### Економіка міждоменного обміну: Провайдери та IXP

Глобальний граф Автономних Систем будується не на геометричних найкоротших шляхах, а на економічних відносинах між трьома категоріями гравців:
1. **Tier-1 Провайдери** (наприклад, Lumen, Telia, NTT): транзитні гіганти, які володіють міжконтинентальними волоконно-оптичними кабелями й з'єднані між собою повним графом безоплатного пірингу (Bill-Keep-Peer). Вони не купують транзит ні в кого.
2. **Tier-2 та Tier-3 Провайдери**: регіональні оператори, які купують послуги транзиту (Transit) у Tier-1 провайдерів для доступу до решти глобального графа.
3. **Точки обміну трафіком (IXP, Internet Exchange Points)**: фізичні майданчики (наприклад, DE-CIX у Франкфурті або UA-IX у Києві), де сотні автономних систем підключають свої роутери до спільних високошвидкісних комутаторів для обміну локальним трафіком напряму через BGP Route Servers, оминаючи дорогих Tier-1 транзитників.

#### Безпека міждоменної маршрутизації: RPKI та BGPsec

Оскільки класичний BGP довіряв усім анонсам від сусіда, виникла вразливість **перехоплення маршрутів** (англ. *BGP Route Hijacking*): некоректний або шкідливий анонс вузла про чужу IP-мережу міг перенаправити світовий трафік через фальшивий роутер.

Для захисту графа міждоменної маршрутизації розроблено криптографічні стандарти:
- **RPKI (Resource Public Key Infrastructure)**: криптографічна інфраструктура ключів, де власник діапазону IP-адрес підписує документ ROA (англ. *Route Origin Authorization*). Роутер при отриманні BGP-анонсу перевіряє, чи має право дана AS анонсувати цей префікс.
- **BGPsec**: розширення BGP, у якому кожна AS при пересиланні анонсу підписує атрибут `AS_PATH` своїм асиметричним приватним ключем, що унеможливлює модифікацію шляху транзитними вузлами.

### Адаптивне балансування трафіку (ECMP та UCMP)

У реальних мережах між двома вузлами може існувати декілька паралельних шляхів однакової або різної вартості. Проста маршрутизація вибирала б один шлях, залишаючи інші лінії зв'язку бездільними.

- **ECMP (Equal-Cost Multi-Path)**: якщо алгоритм Дейкстри чи Беллмана–Форда знаходить декілька шляхів із **однаковою мінімальною вартістю**, роутер розподіляє пакети між ними. Щоб уникнути порушення порядку пакетів усередині одного TCP-з'єднання (що призвело б до падіння швидкості TCP через хибні повторні передачі), роутер використовує хешування 5 полів заголовка (`Src IP`, `Dst IP`, `Src Port`, `Dst Port`, `Protocol`) для прив'язки сесії до одного лінка.
- **UCMP (Unequal-Cost Multi-Path)**: у протоколі EIGRP (алгоритм DUAL) реалізовано розподіл трафіку пропорційно пропускній здатності шляхів із різною вартістю за допомогою коефіцієнта `variance`.

### Багатоадресна маршрутизація (Multicast Routing)

Окремим важливим класом є алгоритми **багатоадресної маршрутизації** (англ. *Multicast Routing*), де джерело `S` надсилає один пакет, а мережа повинна розмножити його в точки розгалуження графа так, щоб доставити пакет групі отримувачів без створення дублікатів лінками.

Для цього алгоритми будують **дерева покриття** (англ. *Spanning Trees*):
1. **Джерела-специфічні дерева (Source-Based Trees / Shortest Path Trees)**: алгоритми DVMRP та PIM-DM (Dense Mode) використовують зворотне просування (RPF, англ. *Reverse Path Forwarding*). Роутер приймає багатоадресний пакет від джерела `S` тільки якщо він прийшов через інтерфейс, який є наступним хопом для повернення до `S`. Затоплення та відсікання гілок (Pruning) будують оптимальне дерево для кожного джерела.
2. **Спільні дерева (Shared Trees)**: алгоритм PIM-SM (Sparse Mode) обирає у графі центральний вузол — **точку рандеву** (RP, англ. *Rendezvous Point*). Усі отримувачі приєднуються до єдиного спільного дерева з коренем у RP, що зменшує накладні витрати пам'яті `O(|S| * |G|)` до `O(|G|)`.

### Багатокритеріальна маршрутизація (QoS та Segment Routing)

У сучасних високошвидкісних мережах класичний вибір найкоротшого шляху доповнюється вимогами **якості обслуговування** (QoS, англ. *Quality of Service*). Проста мінімізація кількості хопів часто призводить до перевантаження магістральних лінків.

- **CSPF (Constrained Shortest Path First)**: модифікація алгоритму Дейкстри, яка перед розрахунком шляху відфільтровує з графа всі ребра, чия вільна пропускна здатність менша за затребувану смугу (Bandwidth Reservation), а затримка вища за допустимий поріг (Delay Constraint).
- **Segment Routing (SR / SRv6)**: сучасний підхід до джерельної маршрутизації (англ. *Source Routing*). Замість зберігання складних станів у кожному проміжному роутері, стартовий вузол вставляє у заголовок пакета стек міток (Segment IDs). Проміжні роутери просто виконують інструкції зі стеку (Pop/Push), що позбавляє мережу від потреби у важких протоколах сигналізації (RSVP-TE).
- **Швидке перемикання при обриві (Fast Reroute / LFA)**: алгоритм Loop-Free Alternates (LFA) заздалегідь обчислює резервний наступний хоп для кожного напрямку. Якщо основний лінк обривається, апаратний Data Plane переключає трафік на резервний шлях за час до 50 мілісекунд, даючи контрольному протоколу OSPF час на перерозрахунок графа без втрати пакетів.

### Програмно-конфігуровані мережі (SDN) та централізований вибір шляху

З появою концепції **Software-Defined Networking (SDN)** у 2010-х роках маятник мережевої архітектури хитнувся від повністю розподілених алгоритмів назад до централізованого обчислення.

У SDN-архітектурі функція обчислення маршрутів виноситься з роутерів на центральний **SDN-контролер** (наприклад, OpenDaylight або ONOS):

```
                      +-----------------------------+
                      |   Центральний SDN-Контролер |
                      |  (Глобальний алгоритм G)    |
                      +--------------┬--------------+
                                     │ OpenFlow / P4
             ┌───────────────────────┼───────────────────────┐
             ▼                       ▼                       ▼
      +--------------+        +--------------+        +--------------+
      |  Світч 1     |        |  Світч 2     |        |  Світч 3     |
      | (Data Plane) |        | (Data Plane) |        | (Data Plane) |
      +--------------+        +--------------+        +--------------+
```

1. **Глобальна топологічна картина**: контролер отримує інформацію про всі лінки, завантаження та збої через протокол OpenFlow або телеметрію P4.
2. **Централізований розрахунок**: контролер виконує оптимізаційні алгоритми лінійного програмування або алгоритм Дейкстри на потужних серверах, враховуючи глобальні потоки трафіку (Traffic Engineering).
3. **Завантаження правил**: готовий граф просування завантажується безпосередньо в апаратні таблиці комутаторів у вигляді правил `Match-Action`.

Це поєднує переваги точної глобальної оптимізації без локальних петель із миттєвою адаптацією до потреб додатків.

### Особливості маршрутизації в IPv6 (MP-BGP та OSPFv3)

Перехід від IPv4 до IPv6 вніс суттєві вдосконалення в алгоритми маршрутизації:
- **OSPFv3 (RFC 5340)**: запуск алгоритму Дейкстри відв'язано від IP-підмереж. OSPFv3 працює безпосередньо над лінками (per-link routing), використовуючи IPv6 Link-Local адреси (`fe80::/10`) для обміну пакетами `Hello` та LSA. Завдяки цьому один фізичний інтерфейс може підтримувати декілька заізольованих екземплярів маршрутизації.
- **MP-BGP (Multiprotocol BGP, RFC 4760)**: розширення шляхово-векторного алгоритму, яке дозволяє одному BGP-сеансу одночасно транспортувати анонси для декількох родин адрес (AFI/SAFI): IPv4, IPv6, VPNv4 та EVPN. Атрибут `NEXT_HOP` у MP-BGP містить як глобальну IPv6-адресу сусіда, так і його Link-Local адресу, що забезпечує швидке перемикання каналів канального рівня.

Завдяки відокремленню мережевого протоколу від алгоритму транспортування анонсів, MP-BGP став універсальною обчислювальною платформою для побудови віртуальних приватних мереж (IP-VPN, EVPN), де роутери обмінюються інформацією про сегментацію трафіку в хмарах та дата-центрах.

### Дослідження таблиць маршрутизації в Linux (FIB, Netlink, Procfs)

У сучасній операційній системі Linux реалізовано високопродуктивний стек маршрутизації. Слід чітко розрізняти демони маршрутизації рівня користувача (user-space daemons, такі як `bird` чи `frr`) та таблицю просування ядра (kernel FIB).

Коли демон `bird` підключається до сусідніх OSPF чи BGP роутерів, він обчислює граф найкоротших шляхів у пам'яті свого процесу (RIB, англ. *Routing Information Base*). Після цього демон відправляє через сокет `NETLINK_ROUTE` повідомлення `RTM_NEWROUTE` до ядра Linux. Ядро оновлює локальну таблицю просування (FIB, англ. *Forwarding Information Base*).

Для перегляду поточного стану FIB у Linux використовуються утиліти сімейства `iproute2`:

```bash
# Перегляд головної таблиці просування в ядра Linux
ip route show table main

# Перегляд системної таблиці локальних та мультикаст маршрутів
ip route show table local

# Інспекція статистики використання кешу маршрутів через procfs
cat /proc/net/rt_cache
```

Ядро Linux організовує FIB за допомогою високооптимізованого префіксного дерева LC-Trie (англ. *Level-Compressed Trie*), яке забезпечує пошук найдовшого збігу префікса (LPM, англ. *Longest Prefix Match*) за час `O(1)` незалежно від кількості записів у таблиці маршрутизації. При отриманні мережевого пакета мережева карта (NIC) за допомогою драйвера передає сокетний буфер `sk_buff` до підсистеми IP, яка робить швидкий запит до префіксного дерева LC-Trie і негайно комутує пакет у відповідний мережевий інтерфейс. Якщо запис у FIB відсутній, ядро відправляє відправнику ICMP-повідомлення `Destination Host Unreachable` та скидає пакет, звільняючи виділену системну пам'ять сокетного буфера.

### Порівняльний аналіз, складність та компроміси

Вибір алгоритму маршрутизації — це завжди інженерний компроміс між складностями обчислень, обсягом службового трафіку та вимогами до пам'яті. 

Зведемо ключові характеристики п'яти парадигм у порівняльну таблицю:

| Параметр / Властивість | Дистанційно-векторні (RIP) | Стану зв'язків (OSPF, IS-IS) | Шляхово-векторні (BGP) | Багатоадресні (PIM-SM) | Програмні (SDN / SR) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Складність пам'яті на вузол** | `O(|V|)` — лише вектори | `O(|V| + |E|)` — граф | `O(префікси * AS)` | `O(|S| * |G|)` дерева | `O(1)` проміжні вузли |
| **Обчислительна складність** | `O(|E|)` на ітерацію | `O(|E| + |V| log |V|)` Дейкстра | `O(k)` перевірка `AS_PATH` | `O(|E|)` RPF перевірка | `O(1)` апаратний Pop/Push |
| **Обсяг службового трафіку** | Періодичні обміни `O(|V|)` | Затоплення `O(|E|)` при змінах | Анонси при змінах політик | Затоплення та Prune | Телеметрія до контролера |
| **Швидкість збіжності** | Повільна (до `O(|V|)` кроків) | Дуже висока (секунди) | Залежить від політик | Висока | Миттєва (перемикання SR) |
| **Механізм блокування петель** | Split Horizon / Poison Reverse | Ідентичність графа та Дейкстра | Перевірка в `AS_PATH` | RPF перевірка інтерфейсу | Заданий стек інструкцій |
| **Сфера застосування** | Малі локальні мережі | Корпоративні та провайдерські | Глобальний Інтернет (EGP) | Потокове відео/IPTV | ЦОД, хмари, 5G мережі |

Маршрутизація на графах демонструє фундаментальний алгоритмічний принцип: відсутність глобальної інформації компенсується розподіленою співпрацею, а математична строгість перевірки петель гарантує стабільну роботу глобальної мережевої інфраструктури людства.
