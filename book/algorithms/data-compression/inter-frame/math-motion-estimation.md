# 🧮 Оцінка руху: пошук «звідки приїхав блок»

Компенсація руху обіцяла дешевизну: замість цілого блока пікселів — короткий **вектор руху** плюс крихітний залишок. Та обіцянка мовчить про головну роботу — **знайти** той вектор. Звідки кодувальник знає, що блок із нового кадру «приїхав» саме з точки (+5, +5) старого, а не (+4, +6) чи (−1, 0)? Він цього **не знає** — він **шукає**. Ця задача зветься **оцінка руху** (*motion estimation*), і саме вона, а не саме стиснення, з'їдає більшість часу кодувальника.

### Чим міряти схожість

Спершу треба число, яке скаже, наскільки добре блок-кандидат зі старого кадру збігається з тим, що шукаємо. Найпростіша й найуживаніша міра — **сума абсолютних різниць** (*SAD*, *Sum of Absolute Differences*): пройти всі пікселі блока, на кожному взяти різницю яскравостей нового й старого, відкинути знак і додати.

```
        N-1 N-1
SAD =    Σ   Σ  | new(i,j) − ref(i + dx, j + dy) |
        i=0 j=0
```

Тут `new` — блок N×N з поточного кадру, `ref` — блок зі старого (опорного) кадру, зсунутий на кандидат-вектор `(dx, dy)`. Що менший SAD, то краще збіг; **SAD = 0** означав би ідеальне накладання (так буває на нерухомому тлі). Абсолютне значення замість квадрата беруть навмисне: модуль рахується **без множення**, лише віднімання й додавання, — а для апаратного кодувальника це разюче дешевше, тож SAD лягає в кремній майже задарма.

> 🔧 **Навіщо це.** SAD — причина, чому оцінку руху взагалі вдається робити в реальному часі на скромному залізі дрона. Якби міряли схожість через суму квадратів (множення на кожен піксель), кодувальник або не встигав би за кадрами, або жер би значно більше струму. Дешева міра — те, що робить живе відео можливим.

### Чому повний перебір не тягне

Тепер головне: кандидатів **багато**. Хай блок може зрушитися в межах ±16 пікселів у будь-який бік — це **вікно пошуку** 33×33 = 1089 можливих векторів. Для кожного треба порахувати SAD по всьому блоку. Полічімо ціну одного макроблока 16×16 за повного перебору (*full search* — перевірити геть усі позиції вікна):

```c
// Скільки операцій коштує знайти ОДИН вектор повним перебором.
int block = 16 * 16;              // 256 пікселів у блоці
int win   = 33 * 33;             // 1089 позицій-кандидатів у вікні +-16
long ops_per_block = (long)block * win;   // 256 * 1089 = 278 784 ≈ 0.28 млн

// А тепер — на цілий кадр 1280x720.
int mb = (1280 / 16) * (720 / 16);        // 80 * 45 = 3600 макроблоків
long ops_per_frame = ops_per_block * mb;  // 278 784 * 3600 ≈ 1.0 млрд
long ops_per_sec   = ops_per_frame * 30;  // при 30 к/с ≈ 30 млрд оп/с
```

Близько **мільярда** операцій лише на пошук руху для **одного** кадру, і тридцять мільярдів за секунду на потоці 30 к/с — і це **до** власне DCT, квантування й кодування. Ось чому оцінка руху домінує в бюджеті кодувальника: решта конвеєра проти неї майже безкоштовна. І ось чому повний перебір на вбудованому залізі не тягне — він просто не вкладається в такт.

### Як зрізають кути

Рятує те, що поверхня SAD здебільшого **гладка**: близькі вектори дають близькі похибки, а справжній мінімум зазвичай один і виразний. Тому замість обмацувати всі 1089 позицій кодувальник іде **розумним пошуком** (*fast search*) — пробує жменю точок, котиться в бік меншого SAD і так за кілька кроків сходить до мінімуму, минаючи переважну більшість кандидатів.

- **Алмазний / шестикутний пошук** (*diamond / hexagon search*): перевірити кілька точок навколо поточної здогадки, перейти в найкращу, повторити з меншим кроком — так за десяток-другий перевірок замість тисячі сходимо до мінімуму.
- **Передбачення вектора із сусідів**: сусідні блоки зазвичай рухаються разом (та сама панорама, той самий об'єкт), тож вектор сусіда — чудова **початкова здогадка**, біля якої й шукати. Кодувальник стартує не з нуля, а з готового припущення — і доходить швидше.

Платня за швидкість — ризик: розумний пошук може скотитися в **локальний** мінімум і проґавити трохи кращий вектор десь осторонь. Тоді залишок вийде ледь більший, ніж міг би, а отже, кадр — ледь важчий. Це і є та ручка **«пресет якості»** в кодувальнику: повільні пресети шукають ретельніше (ближче до повного перебору) і дають менший файл за ту саму картинку; швидкі — обмацують менше точок, кодують швидше, але трохи марнотратніше. Вибираючи між «fast» і «slow», ти насправді торгуєш машинним часом за кілька зекономлених відсотків бітрейту.

### Чому «найсхожіший» не означає «найдешевший»

Є ще одна тонкість, через яку наївний пошук «знайди мінімум SAD» не зовсім правильний. Уяви два кандидати-вектори: один дає трохи менший залишок, зате сам **вектор** довгий і дивний (скажімо, (+13, −9)), а другий — залишок ледь більший, та вектор **короткий і схожий на сусідів** ((+1, 0)). Що вибрати? Виходить, що **другий** часто вигідніший: адже сам вектор теж треба закодувати й переслати, а вектор, близький до передбаченого із сусідів, коштує майже нічого, тоді як «дикий» вектор з'їсть зайві біти. Тому сучасний кодувальник міряє не голий SAD, а **повну вартість** кандидата:

```
вартість = SAD(залишок) + λ · біти(вектор)
```

Тут `біти(вектор)` — скільки коштуватиме сам вектор після кодування (тим більше, чим далі він від передбаченого із сусідів), а **λ** (лямбда) — множник, що зважує два доданки один проти одного. Цей підхід зветься **оптимізацією за швидкістю й спотворенням** (*rate-distortion optimization*): кодувальник шукає не найточніший прогноз, а найдешевший **разом із вектором**. Лямбда прямо пов'язана з вибраним бітрейтом: тиснеш сильніше (менший бітрейт) — λ більша, і кодувальник дужче карає за дорогі вектори, охочіше беручи трохи гірший, зате дешевший прогноз.

> 🔧 **Навіщо це.** Саме тому два кодувальники з тим самим «найкращим збігом» можуть дати помітно різні за вагою файли: важить не лише точність пошуку, а й те, наскільки розумно кодек зважує вартість самого вектора. І саме тому панорама стискається так гарно — сусідні блоки їдуть однаково, їхні вектори майже збігаються, тож кожен наступний коштує копійки.
