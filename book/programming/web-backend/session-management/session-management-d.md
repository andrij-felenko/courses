# Сесія автентифікації

<preknowlist>
- [Автентифікація](book:programming/authentication) — як користувач доводить, хто він (пароль чи інший фактор); сесія починається рівно там, де автентифікація підтвердила особу.
- [HTTP-cookie](book:programming/http-cookies) — маленький іменований запис, який браузер зберігає й **сам** додає до кожного запиту на той самий сайт; саме він везе номер сесії туди-назад.
</preknowlist>

Ти вводиш пароль, натискаєш «увійти» — і далі ходиш сайтом вільно: відкриваєш профіль, кошик, налаштування, і жодна сторінка більше не питає пароль. Дрібниця, до якої всі звикли. Але за нею ховається справжня загадка, бо **HTTP влаштований так, що сервер тебе не пам'ятає**. Кожен запит приходить до нього голим і самотнім: «дай сторінку профілю» — і ні слова про те, хто просить. Наступний запит сервер бачить так, ніби перший ніколи не існував. Протокол задумали без пам'яті навмисне — так простіше й надійніше масштабувати, — і в цій забудькуватості вся суть проблеми.

То що ж тоді несе крізь десятки окремих, нічого не знаючих один про одного запитів оте «це досі та сама людина, що ввела пароль пів хвилини тому»? Відповідь — **сесія** (лат. *sessio* — «сидіння», відрізок безперервної роботи). Сесія — це пам'ять сервера про те, хто ти **зараз**, розтягнута поверх багатьох безпам'ятних запитів. Уся справа в тім, **де** цю пам'ять тримати й **як** прив'язати її до конкретного відвідувача, щоб він не мусив щоразу доводити особу наново.

## Головна ідея: сервер лишає правду в себе, а тобі дає лише номерок

Найпростіше рішення напрошується саме: хай клієнт носить свою особу з собою. Увійшов — браузер запам'ятав «я користувач Марія, роль адміністратор» і додає це до кожного запиту. Коротко й без сервера. І цілком безнадійно: усе, що тримає клієнт, клієнт може **підробити**. Ніщо не завадить відкрити інструменти браузера й дописати собі роль адміністратора. Довіряти клієнтові власну особу — це віддати ключі від сейфа тому, кого сейф і має стримувати.

Тому справжня схема інша, і вона тримається на одному точному розрізненні: **правду сервер лишає в себе, а клієнтові дає лише беззмістовний номерок-указівник на цю правду**. При вході сервер створює запис — «сесія №a8f3…9c — це Марія, увійшла о 14:03, роль адміністратор» — і кладе його у своє **сховище сесій**. Клієнтові він віддає тільки випадковий номер цієї сесії, більш нічого. Номер сам собою не значить нічого: він не каже, хто ти, не несе жодних прав — це просто вказівник, за яким сервер знайде запис у власній пам'яті.

Точна аналогія — **гардеробний номерок**. Ти віддаєш пальто (при вході — доводиш особу), отримуєш бляшку з числом. Бляшка нічого не розповідає про пальто й ні про які права не свідчить — це голе число. Але хто її пред'явить, тому видадуть пальто. Ось де аналогія ламається, і злам цей важливий: гардеробний номер можна спокійно показувати, а номер сесії — ні, бо зловмисник у мережі здатний перебирати мільйони чисел за секунду, і викрадення бляшки видно (пальта нема), а викрадення номера сесії — невидиме, бо в тебе лишається його копія.

![Ліворуч рамка «клієнт» тримає cookie з написом «sid = a8f3…9c — беззмістовний номер»; від неї стрілка «запит везе cookie» веде праворуч до рамки «сервер», усередині якої таблиця-сховище зіставляє номери сесій з правдою (a8f3…9c → Марія, роль адмін, 14:03); підпис унизу «клієнт тримає лише вказівник — правда живе на сервері»](/book/programming/web-backend/session-management/img/pointer.svg)

*Клієнт носить самий лише номер, у якому немає ні особи, ні прав. Уся правда — хто це і що йому дозволено — лежить у сховищі сесій на сервері; номер із cookie тільки вказує, який саме рядок звідти прочитати.*

> 🔧 **Навіщо це.** Розрізнення «правда на сервері, у клієнта — указівник» — це не педантизм, а лінія оборони. Щойно бачиш, що застосунок вирішує права за даними, які **прийшли від клієнта** (роль у полі форми, «isAdmin» у cookie), — це майже завжди діра: клієнт це підробить. Правильний рефлекс — за номером сесії підняти на сервері свій довірений запис і рішення ухвалювати **тільки** за ним. Клієнт носить номерок; що він означає — вирішує сервер.

## Як це працює: cookie везе номер, сервер піднімає запис

Лишається питання, **чим** возити той номер від запиту до запиту. Тут і вступає [cookie](book:programming/http-cookies) (термін з англійського *magic cookie* — непрозорий шматок даних, що його програма отримує назад незмінним): при вході сервер надсилає заголовок `Set-Cookie: sid=…`, браузер зберігає його й **сам** причіпляє до кожного наступного запиту на цей сайт. Клієнтові не треба нічого робити свідомо — механізм cookie возить номер автоматично. Сервер на кожному запиті читає номер, іде в сховище, піднімає запис — і знає, хто прийшов.

Увесь цикл — три короткі рухи: **вхід створює сесію, cookie возить номер, вихід знищує сесію**.

:::tabs
```ts
import { randomBytes } from "node:crypto";

// Сервер тримає правду в себе; клієнт отримає лише номер
const sessions = new Map<string, { userId: string; createdAt: number }>();

function login(res: Response, userId: string) {
  const sid = randomBytes(16).toString("hex");        // 128 біт із CSPRNG
  sessions.set(sid, { userId, createdAt: Date.now() });
  res.setHeader("Set-Cookie",
    `sid=${sid}; HttpOnly; Secure; SameSite=Lax; Path=/`);
}

function whoAmI(req: Request): string | null {
  const sid = parseCookie(req.headers.cookie).sid;
  const session = sid ? sessions.get(sid) : undefined;
  return session ? session.userId : null;             // немає запису → анонім
}

function logout(sid: string) {
  sessions.delete(sid);        // знищуємо ПРАВДУ на сервері, не лише cookie
}
```
```py
import secrets, time

sessions: dict[str, dict] = {}          # правда живе на сервері

def login(response, user_id: str) -> None:
    sid = secrets.token_hex(16)         # 128 біт із CSPRNG
    sessions[sid] = {"user_id": user_id, "created_at": time.time()}
    response.set_cookie("sid", sid, httponly=True, secure=True, samesite="Lax")

def who_am_i(request) -> str | None:
    sid = request.cookies.get("sid")
    session = sessions.get(sid) if sid else None
    return session["user_id"] if session else None     # немає запису → анонім

def logout(sid: str) -> None:
    sessions.pop(sid, None)       # знищуємо ПРАВДУ на сервері, не лише cookie
```
:::

Зверни увагу на `logout`: він викидає запис зі **сховища**, а не просто просить браузер забути cookie. Це не дрібниця, а осердя всієї моделі. Якщо вихід лише стирає cookie, а серверний запис живий, то будь-хто, хто встиг переписати номер собі, і далі заходить як ти. Правда — на сервері, тож і гасити сесію треба **там**. Саме звідси випливає велика перевага серверних сесій: їх **можна відкликати** будь-якої миті — досить прибрати запис, і номер миттєво стає мертвим. Повний робочий склад сесій — із генерацією номерів, строками, ротацією й відкликанням — [зібрано окремим проєктом](book:programming/session-management/proj-session-store.md).

## Номер сесії — це справжня таємниця

Раз номер відмикає весь обліковий запис, він мусить бути **невгадним**. Тут ховається найпоширеніша й найгрубіша помилка новачка: узяти номер із простого генератора випадковості на кшталт `Math.random()`. Такі генератори роблять числа, що *виглядають* випадковими, але породжуються передбачуваним правилом: побачивши кілька виданих номерів, зловмисник обчислює наступні. Це рівносильно тому, щоб роздавати гардеробні номери по порядку — вкравши один, крадеш і сусідні.

Тому номер сесії беруть **лише** з криптографічного генератора — [CSPRNG](book:algorithms/csprng), чий вихід неможливо передбачити навіть за багатьма попередніми значеннями. У коді вище саме він: `randomBytes` і `secrets.token_hex` — це криптографічні джерела, на відміну від звичайного `Math.random()`. Друга вимога — **довжина**: номер має нести стільки випадковості, щоб перебором його не взяти за розумний час. Практичне правило (OWASP) — щонайменше 128 біт номера й не менш як 64 біти справжньої ентропії. Чому саме стільки й чому 64 біти ентропії перетворюються на сотні років марного перебору навіть для цілого флоту зловмисників — [порахуємо в математиці теми](book:programming/session-management/math-session-entropy.md).

> 🔧 **Навіщо це.** Одне слово — `Math.random()` замість `crypto` — перетворює всю оборону на декорацію: скільки не став прапорців на cookie, передбачуваний номер зловмисник просто **обчислить**, не крадучи нічого. Рефлекс простий: усе, що відмикає доступ, — номери сесій, токени скидання пароля, разові коди — родиться **тільки** з криптографічного генератора. Побачив «випадковий» ідентифікатор із `Math.random()` чи лічильника — це вже вразливість, а не стиль.

## Броня на cookie: три прапорці, що рятують номер

Невгадний номер марний, якщо його легко **вкрасти**. Оскільки номер їде в cookie, головні три способи захисту — це три атрибути того самого cookie, і кожен закриває окремий канал крадіжки.

**`HttpOnly`** забороняє коду сторінки читати cookie. Без нього одна впорснута на сторінку [шкідлива вставка скрипту](book:programming/web-vulnerability-classes) прочитала б `document.cookie` й відіслала номер сесії зловмисникові. З `HttpOnly` номер існує лише в надрах браузера й для JavaScript невидимий — навіть пробитий на сторінку скрипт до нього не дотягнеться.

**`Secure`** велить надсилати cookie тільки шифрованим з'єднанням. Без нього номер поїхав би відкритим текстом через будь-яку відкриту Wi-Fi-точку, де його спокійно прочитають дорогою; `Secure` прив'язує номер до захищеного каналу, тож у мережі його не перехопити.

**`SameSite`** каже браузерові не додавати cookie до запитів, що йдуть із **чужого** сайту. Це прямо б'є по підступному наслідку автоматичності cookie: якщо браузер сам чіпляє твій номер сесії до **кожного** запиту на банк, то й запит, який тихо згенерувала шкідлива стороння сторінка, поїде з твоїм номером — і банк виконає його як твій. Ця атака зветься [міжсайтова підробка запиту (CSRF)](book:programming/csrf), і `SameSite` — її перша й найдешевша перепона.

## Життя сесії: від входу до згасання

Сесія не живе вічно — і не має. Що довше вона відкрита, то ширше вікно, у яке хтось може прослизнути з украденим номером, тож строк сесії — це компроміс між зручністю й ризиком. Керують ним два незалежні лічильники.

**Таймаут простою** гасить сесію, якщо певний час не було жодного запиту: відійшов від чужого ноутбука — за пів години сесія згасла сама. Він **ковзний**: кожна дія зсуває дедлайн уперед, тож поки ти працюєш, тебе не викидає. **Абсолютний строк** — тверда стеля згори: скільки б ти не був активний, через, скажімо, дванадцять годин сесія завершується й вимагає ввійти знову. Перший стереже покинуту сесію, другий обмежує здобич навіть від активно вкраденого номера.

![Горизонтальна вісь часу; подія «вхід» створює запис у сховищі й надсилає Set-Cookie; далі смуга активних запитів, над кожним ковзний таймаут простою зсувається вперед, а знизу тверда лінія абсолютного строку не рухається; праворуч дві розв'язки — «вихід або згасання» — обидві ведуть до «запис знищено на сервері → номер мертвий»](/book/programming/web-backend/session-management/img/lifecycle.svg)

*Два лічильники стережуть сесію з різних боків: ковзний таймаут простою зсувається за кожною дією й ловить покинуту сесію, абсолютний строк стоїть нерухомо й обмежує сумарний час. Хоч так, хоч так кінець один — запис зникає зі сховища, і номер більше нічого не відмикає.*

> 🔧 **Навіщо це.** Строки — не бюрократія, а розмір вікна для зловмисника. Практичний баланс: для звичайного сайту простій — десятки хвилин, абсолют — години; для банку — хвилини й один робочий сеанс. І головне — **вихід і згасання мусять знищувати серверний запис**, а не тільки cookie. Класична помилка: «вийти» лише стирає cookie у браузері, а сесія в сховищі жива — украдений заздалегідь номер працює далі. Гаси правду там, де вона лежить.

## Три атаки, від яких усе й захищають

Три прапорці й строки — це відповіді на конкретні напади. Варто побачити самі напади, бо саме їхній механізм диктує оборону.

**Викрадення сесії** — зловмисник дістає чинний номер (пробитим скриптом, перехопленням у мережі, з-під недбало залишеного в логах cookie) і відмикає ним твій обліковий запис. Проти цього й стоять `HttpOnly`, `Secure` та короткі строки: закрити канали крадіжки й звузити вікно, поки номер ще чинний.

**Фіксація сесії** — тонша й хитріша. Зловмисник спершу сам отримує від сайту номер (ще анонімний, до входу), тоді **підсовує** цей відомий йому номер жертві — посиланням чи скриптом. Жертва з цим номером **входить** — і сервер, наївно лишивши той самий номер, підвищує його до повноправної сесії. Тепер зловмисник, який знає номер від початку, заходить як жертва. Хиба тут у тому, що номер пережив момент входу. Ліки прості й обов'язкові: **на кожній зміні рівня прав — насамперед одразу після входу — сервер видає новий номер**, а старий викидає. Тоді номер, який зловмисник підсунув, після входу вже мертвий, і його копія нічого не варта.

![Два ряди-сценарії. Верхній «без ротації»: зловмисник дістає номер X, підсовує його жертві, жертва входить, сесія X стає повноправною, зловмисник відмикає X — вхід зламано. Нижній «з ротацією на вході»: жертва входить, сервер видає НОВИЙ номер Y і гасить X, копія X у зловмисника мертва — вхід захищено](/book/programming/web-backend/session-management/img/fixation.svg)

*Фіксація живе рівно доти, доки номер переживає вхід. Досить видати при вході свіжий номер і викинути старий — і підсунута зловмисником копія перетворюється на мертве число ще до того, як за ним постане хоч якась правда.*

**Міжсайтова підробка запиту (CSRF)** росте з самої зручності cookie: браузер додає твій номер сесії до кожного запиту на сайт **незалежно від того, хто цей запит почав**. Тож стороння шкідлива сторінка може тихо надіслати запит на твій банк, і він поїде з твоїм номером. Перша перепона — уже згаданий `SameSite`; поверх нього кладуть спеціальні одноразові [токени проти CSRF](book:programming/csrf). Те, що сесія на cookie сама породжує цей клас атак, — не випадковість, а зворотний бік її головної зручності.

Сам термін «фіксація сесії» й перший її розбір належать словенському дослідникові Мітї Колшеку (ACROS Security, грудень 2002) — до того діру не мали за окрему й недооцінювали. Як народилася вся ця конструкція — стан поверх безпам'ятного HTTP, cookie Лу Монтуллі 1994 року в Netscape, серверні сесії, — [зібрано в історії поняття](book:programming/session-management/hist-session-cookie.md).

## Де живе сховище, коли серверів багато

Поки сервер один, сховище сесій — це просто таблиця в його пам'яті, як `Map` у прикладі вище. Але щойно навантаження росте й серверів стає кілька за [балансувальником](book:programming/load-balancing), проста таблиця в пам'яті ламається: перший запит створив сесію в пам'яті сервера №1, а другий балансувальник кинув на сервер №2, який про цю сесію ніколи не чув. Користувача викидає на вхід посеред роботи.

Є два виходи. Перший — **липкі сесії**: балансувальник прив'язує відвідувача до одного сервера, і всі його запити йдуть туди ж. Працює, але крихко: помер той сервер — і всі його сесії згинули разом із ним, а рівномірність навантаження псується. Другий, правильний, — **спільне сховище**: сесії тримають не в пам'яті окремого сервера, а в спільній швидкій базі, доступній усім, — [розподіленому кеші](book:programming/distributed-cache) на кшталт Redis. Тепер будь-який сервер піднімає будь-яку сесію, серпи можна додавати й гасити вільно, і смерть одного нічого не втрачає.

![Балансувальник розкидає запити на три застосункові сервери. Ліворуч «липкі сесії»: користувач прив'язаний до сервера 2, сесія лежить у його пам'яті; сервер 2 гасне — і сесію втрачено. Праворуч «спільне сховище»: усі три сервери читають один спільний Redis, будь-який обслуговує будь-який запит, смерть одного не чіпає сесій](/book/programming/web-backend/session-management/img/scaling.svg)

*Тримати сесію в пам'яті одного сервера — значить прив'язати до нього користувача й утратити все, коли сервер помре. Винести сесії у спільне сховище — і сервери стають взаємозамінні: будь-який піднімає будь-яку сесію, а масштабувати можна вшир без болю.*

Саме тому серверний стан — то не безкоштовна зручність, а те, що доводиться свідомо виносити назовні, щоб система масштабувалася вшир. Ширше про це — у темі про те, [чому «без стану» цінують для горизонталі](book:programming/sessions-state).

## Інша розв'язка: віддати всю особу клієнтові

Дійшовши сюди, помічаєш прикру ціну: щоб знати, хто прийшов, сервер на **кожному** запиті мусить сходити у сховище й підняти запис. Виникає спокуса зрізати цей крок — і є цілком інша модель, що так і робить. Замість тримати правду в себе й давати клієнтові беззмістовний номер, сервер віддає клієнтові **всю особу одразу**, але **криптографічно підписану**, щоб її не можна було підробити: [токен без стану (JWT)](book:programming/jwt-tokens). Тепер клієнт носить не номер-указівник, а сам запис «я Марія, роль адмін», скріплений підписом; сервер на кожному запиті лише перевіряє підпис — і жодного походу у сховище.

За це платять зворотним боком тієї самої монети. Серверну сесію легко **відкликати** — прибрав запис, і все; а підписаний токен сервер не тримає в себе, тож і забрати його назад так само просто не може — токен чинний, доки не збіжить його строк, навіть якщо ти «вийшов». Ось і весь стрижень вибору, до якого зводиться вся тема: **серверна сесія — відклична, але потребує спільного сховища; токен без стану — масштабується задарма, але важко відкликається**. Що взяти — вирішує не мода, а те, що для системи дорожче: миттєве відкликання чи легкість горизонталі.

## Що лишається в руках

HTTP тебе не пам'ятає — і сесія є та пам'ять, яку доклали поверх його безпам'ятності. Уся конструкція тримається на одному розрізненні: **правда живе на сервері, а клієнтові дають лише беззмістовний номер-указівник**, який cookie возить від запиту до запиту. Тому клієнтові немає чого підробляти — усі рішення сервер ухвалює за своїм довіреним записом.

Звідси випливає й решта. Номер відмикає обліковий запис, тож він мусить родитися з криптографічного генератора й бути досить довгим, щоб перебором його не взяти. Оскільки він їде в cookie, його боронять три прапорці — `HttpOnly`, `Secure`, `SameSite`, — кожен проти свого каналу крадіжки. Оскільки правда на сервері, сесію можна вчасно згасити строками й **відкликати** будь-якої миті — і цю правду ж треба знищувати при виході, а не тільки стирати cookie. На кожному вході номер міняють, щоб убити фіксацію. А коли серверів багато, сесії виносять у спільне сховище, щоб будь-який сервер міг підняти будь-яку сесію. І над усім цим стоїть один свідомий вибір — тримати стан у себе заради відкличності чи віддати підписану особу клієнтові заради дешевої горизонталі.
