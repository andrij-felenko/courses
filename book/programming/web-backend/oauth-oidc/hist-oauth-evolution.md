# 📜 Від спільного пароля до OIDC: історія воєн за делегований доступ

Коли в середині 2000-х веб перетворився з набору ізольованих сторінок на екосистему взаємопов'язаних сервісів, індустрія вперлася у глухий кут безпеки: як дозволити сторонньому застосунку взаємодіяти з даними користувача, не змушуючи того віддавати свій головний логін і пароль? Шлях від примітивного збирання облікових даних до сучасного тандему OAuth 2.0 та OpenID Connect тривав понад півтора десятиліття, супроводжувався гучними розколами в робочих групах IETF, відмовами провідних авторів від авторства та фундаментальним переосмисленням криптографії у вебі.

### Епоха «парольного антипатерна»: 2005–2007 роки

У перші роки епохи Web 2.0 популярні сервіси — від фотохостингу Flickr до рекомендаційної мережі Yelp та агрегаторів контактів — пропонували користувачеві «знайти друзів» або «надрукувати фотоальбом». Механізм цієї операції виглядав дико за сучасними мірками: веб-сторінка стороннього сервісу показувала поля «Введіть ваш логін і пароль від Yahoo!, Google або MSN».

Отримавши ці дані, бекенд стороннього сайту підключався до поштового сервера жертви через протоколи POP3, IMAP чи веб-скрапінг, читав адресну книгу, копіював контакти й зберігав чужий пароль у своїй базі даних у відкритому чи слабо зашифрованому вигляді. Цей підхід отримав назву **парольний антипатерн** (англ. *password anti-pattern*).

Наслідки були катастрофічними:
1. **Принцип «усе або нічого»**: віддаючи пароль для імпорту адрес електронної пошти, користувач несвідомо давав сторонньому сервісу повний контроль над усім своїм обліковим записом, включно з можливістю змінити пароль чи видалити пошту.
2. **Неможливість вибіркового відкликання**: аби забрати доступ у підозрілого сервісу, користувач мусив змінити свій пароль, що ламало авторизацію на всіх інших підключених пристроях і застосунках.
3. **Поширення фішингу**: користувачів роками привчали вводити свої головні системні паролі в довільні форми на чужих доменах, що цілковито знищувало базову цифрову гігієну.

Компанії почали шукати альтернативи. Google створив закритий протокол AuthSub, Yahoo! запустив BBAuth, Flickr мав власний Flickr API Auth. Кожен великий провайдер будував власний несумісний «острів» авторизації. Якщо розробник хотів інтегрувати свій віджет із десятьма платформами, йому доводилося писати десять різних клієнтів з абсолютно різною логікою підпису та життєвого циклу сесій.

### Народження OAuth 1.0 та криптографічний глухий кут (2007–2010)

У листопаді 2006 року Блейн Кук (Blaine Cook), тоді головний архітектор сервісу Twitter, працював над впровадженням відкритого протоколу OpenID для входу в систему. Водночас інженер Кевін Маркс (Kevin Marks) шукав спосіб автентифікувати віджети для сервісу Ma.gnolia без передачі паролів. До них приєдналися Кріс Мессіна (Chris Messina) та Ларрі Халфф (Larry Halff).

У квітні 2007 року в Каліфорнії сформувалася невелика група розробників, яка поставила за мету створити єдиний відкритий стандарт делегованого доступу за моделлю API. Проєкт назвали **OAuth** (від англ. *Open Authorization* — «відкрита авторизація»). У грудні 2007 року було опубліковано чернетку OAuth Core 1.0, а в квітні 2010 року Інженерна рада інтернету (IETF) закріпила стандарт як [RFC 5849](https://datatracker.ietf.org/doc/html/rfc5849).

OAuth 1.0 вирішував головне завдання: користувач перенаправлявся на сайт провайдера, підтверджував надання прав, а клієнт отримував пару токенів (`oauth_token` та `oauth_token_secret`). Пароль залишався у таємниці.

Проте за це довелося заплатити надмірною криптографічною складністю. У часи домінування звичайного HTTP без обов'язкового шифрування каналу творці OAuth 1.0 вирішили захищати кожен окремий HTTP-запит цифровим підписом на рівні застосунку.

Щоб надіслати запит, клієнт мусив:
1. Зібрати рядок нормалізації (Base String): вирівняти в алфавітному порядку всі параметри URL, поля тіла запиту та заголовки, застосувати до них суворе процентне кодування (URL-encoding) за правилами RFC 3986.
2. Згенерувати випадковий рядок (nonce) та точну часову мітку (timestamp) для захисту від повтору запитів.
3. Порахувати підпис HMAC-SHA1 або RSA-SHA1 від базового рядка з використанням спільного секрету.
4. Додати підпис у заголовок `Authorization`.

```
Base String = POST&https%3A%2F%2Fapi.example.com%2Fphotos&oauth_consumer_key%3D...
Signature   = HMAC-SHA1(Base String, ConsumerSecret&TokenSecret)
```

На практиці це обернулося кошмаром. Найменша розбіжність у порядку параметрів, кодуванні символів пробілу (`%20` проти `+`) або розходженні системного годинника навіть на секунду призводила до мовчазної помилки `401 Unauthorized`. Особливо страждали мобільні застосунки та код на мові JavaScript у браузері, де в ті роки не було стандартних криптографічних API для швидкого обчислення SHA-1.

У 2009 році дослідник Ерхан Чеврукер (Erhan Çevrüker) виявив критичну вразливість у протоколі OAuth 1.0: зловмисник міг перехопити запит на авторизацію до того, як користувач завершить схвалення, і підмінити зворотну адресу (Session Fixation Attack). Робочій групі довелося терміново випускати виправлену специфікацію OAuth 1.0a, яка додала верифікаційний код для прив'язки підтвердження. Але загальне розчарування складністю підпису спонукало індустрію до радикального перегляду всієї концепції.

### Розкол довкола OAuth 2.0 та демарш Ерана Хаммера (2010–2012)

У 2010 році робоча група IETF розпочала розробку OAuth 2.0. Провідним редактором специфікації став Еран Хаммер (Eran Hammer), який до цього очолював розробку OAuth 1.0a. До процесу приєдналися технічні гіганти: Google, Facebook, Microsoft, Yahoo! та Salesforce.

Головною ідеєю OAuth 2.0 була відмова від обов'язкового підпису кожного HTTP-запиту за рахунок повного переходу на захищений транспортний шар TLS/HTTPS. Якщо весь канал зашифровано надійними шифрами, клієнтові достатньо передавати простий рядок — **Bearer-токен** (англ. *bearer* — «пред'явник»). Будь-хто, хто тримає в руках цей токен, отримує доступ, аналогічно до звичайного готівкового квитка в театр. Це зняло з розробників тягар нормалізації рядків та генерації HMAC на кожен запит.

Проте за стіл переговорів сіли учасники з діаметрально протилежними вимогами:
- **Мобільні розробники** вимагали простих редіректів та роботи без серверного бекенду (так з'явився згодом відкинутий Implicit Grant).
- **Великі корпорації** хотіли підтримки мікросервісів, бекенд-інтеграцій без участі користувача (Client Credentials Grant) та спрощеного входу з корпоративних машин.
- **Корпоративні безпечники** наполягали на гнучкості форматів токенів та можливості вбудовування в наявні корпоративні сховища.

Аби догодити всім, робоча група почала прибирати зі специфікації обов'язкові вимоги щодо криптографічних алгоритмів, форматів збереження токенів і способів їхнього відкликання, перетворюючи точний стандарт на абстрактний «фреймворк» (Framework).

Це призвело до гострого конфлікту. У липні 2012 року, за кілька місяців до фінальної публікації [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749) та [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750), Еран Хаммер публічно подав у відставку з посади редактора, відкликав своє ім'я з титульної сторінки документа й опублікував знамениту статтю «OAuth 2.0 and the Road to Hell».

Хаммер стверджував, що новий документ — це не сумісний протокол, а небезпечний конструктор:
> «OAuth 2.0 створили фахівці з масштабних веб-платформ, які принесли безпеку в жертву простоті інтеграції для своїх сервісів. Замість єдиного суворого протоколу ми отримали незліченну кількість несумісних між собою реалізацій, кожна з яких має власні дірки в безпеці».

Попри скандал, у жовтні 2012 року IETF стандартизував RFC 6749. Пророцтво Хаммера справдилося частково: OAuth 2.0 дійсно став фундаментом сучасної веб-інтеграції завдяки неймовірній зручності для розробників, але розмитість специфікації призвела до десятиліття боротьби з типовими атаками — від витоків токенів через заголовки `Referer` до підміни авторизаційних кодів.

### Війни за ідентичність: чому виник OpenID Connect

Щойно OAuth 2.0 набув широкої популярності, розробники масово почали припускатися концептуальної помилки: використовувати OAuth 2.0 як інструмент входу на сайт («Увійти через Facebook», «Увійти через Google»).

OAuth 2.0 проектувався виключно як протокол **авторизації** (делегування прав доступу до ресурсів), а не **автентифікації** (встановлення особи). Отримавши `access_token`, клієнт робив запит до захищеного API, отримував профіль і вважав: «Якщо токен дійсний, отже, користувач успішно зайшов!».

Ця плутанина породжувала катастрофічні дірки в безпеці. Зловмисник міг згенерувати дійсний `access_token` у власному шкідливому застосунку, перехопити авторизаційну сесію жертви й надіслати свій токен на сайт жертви. Сайт робив запит до провайдера, бачив `200 OK`, витягував ідентифікатор зловмисника і приєднував акаунт жертви до чужого профілю (Confused Deputy Problem).

Паралельно існували окремі протоколи для ідентичності, але вони програвали ринок:
- **SAML 2.0** (Security Assertion Markup Language, 2005) — важкий корпоративний стандарт на базі XML та SOAP. Він містив надзвичайно надійні криптографічні гарантії, проте був практично непридатний для мобільних пристроїв та браузерних SPA-застосунків через величезний розмір XML-повідомлень та складність парсерів XML-підписів (XML Signature Wrapping attacks).
- **OpenID 1.0 / 2.0** (2006–2007) — відкритий стандарт автентифікації на базі URL-ідентифікаторів. Його концепція вимагала від користувача вводити власний URL (наприклад, `alice.myopenid.com`), що спантеличувало звичайних людей. До того ж протокол використовував складні механізми виявлення сервісів (XRDS / Yadis) та застарілий формат обміну парами «ключ-значення».
- **Facebook Connect** (2008) — закрита пропрієтарна система, яка показала ринку, наскільки зручною може бути кнопка «Увійти» в один клік, але прив'язувала всю індустрію до одного комерційного постачальника.

Виникла нагальна потреба об'єднати легкість транспортного механізму OAuth 2.0 із суворою безпекою та стандартизованими даними про особу.

У лютому 2014 року організація OpenID Foundation опублікувала специфікацію **OpenID Connect 1.0 (OIDC)**. Провідними авторами виступили Майкл Джонс (Michael B. Jones, Microsoft), Джон Бредлі (John Bradley, Ping Identity) та Нать Сакамура (Nat Sakimura, NRI).

OIDC елегантно розв'язав проблему ідентичності, надбудувавши над OAuth 2.0 три обов'язкові компоненти:
1. **ID-токен (`id_token`)**: підписаний токен у форматі [JWT](topic:programming/jwt-tokens), створений спеціально для клієнтського застосунку. Він містив гарантії того, хто саме автентифікувався (`sub`), який сервер це підтвердив (`iss`), для якого клієнта призначений токен (`aud`), коли сталася автентифікація (`auth_time`) і випадковий рядок захисту від підміни (`nonce`).
2. **Стандартний набір даних про профіль**: чітко зафіксовані назви прав (scopes `openid`, `profile`, `email`) та формат відповіді ендпоінта `/userinfo`.
3. **Автоматичне виявлення метаданих (Discovery)**: єдиний JSON-документ за фіксованим шляхом `/.well-known/openid-configuration`, з якого будь-який клієнт міг автоматично зчитати адреси точок входу та відкриті ключі шифрування (JWKS) провайдера.

OpenID Connect миттєво став золотим стандартом федеративного входу та Single Sign-On (SSO) для Google, Microsoft, Apple (Sign in with Apple побудований саме на OIDC), AWS та enterprise-систем Okta, Auth0 і Keycloak.

### Еволюція безпеки: PKCE та шлях до OAuth 2.1

З масовим поширенням смартфонів та браузерних односторінкових застосунків (SPA) на базі React та Angular проявилася нова фундаментальна вразливість оригінального OAuth 2.0: **витік авторизаційного коду**.

У мобільних операційних системах Android та iOS застосунки реєстрували власні схеми посилань (Custom URL Schemes, наприклад `myapp://oauth-callback`). Оскільки операційна система дозволяла кільком застосункам заявляти однакові схеми, шкідлива програма могла зареєструвати чужу схему, перехопити редірект із чутливим авторизаційним кодом і використати його для отримання токенів доступу.

Аби закрити цю діру, у вересні 2015 року робоча група IETF опублікувала [RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636) — **PKCE** (Proof Key for Code Exchange, вимовляється як «піксі»). Розробники додали динамічний криптографічний секрет (`code_verifier`) та його односторонній хеш (`code_challenge`), що надійно прив'язало початковий запит на авторизацію до фінального запиту на отримання токена.

Накопичений десятиліттям досвід експлуатації та закриття дір спонукав робочу групу IETF розпочати роботу над **OAuth 2.1**. Цей документ не створює новий протокол, а консолідує найкращі практики захисту (Best Current Practice, RFC 8725 та RFC 8252):
- **Повна заборона Implicit Grant**: видача токенів через фрагмент URL у браузері визнана небезпечною через легкість витоку з історії браузера та логів.
- **Обов'язкове використання PKCE для всіх клієнтів**, включно з серверними бекендами.
- **Повна заборона Resource Owner Password Credentials Grant**: введення логіна й пароля безпосередньо у форму стороннього клієнта остаточно викреслено зі стандарту.
- **Суворе зіставлення адрес редіректу**: точне порівняння рядків без підстановки шаблонів (wildcards) та відкритих перенаправлень.
- **Обов'язкова ротація Refresh-токенів** (Refresh Token Rotation) для публічних клієнтів, що мінімізує шкоду від викрадення довгоживучого секрету.

Сучасна екосистема OAuth 2.0 та OpenID Connect подолала дитячі хвороби фрагментації. Те, що колись починалося як імпровізований скрипт для читання контактів у Twitter, перетворилося на сувору, багаторівневу інженерну систему, яка обслуговує мільярди щоденних входів та захищає API глобального інтернету.
