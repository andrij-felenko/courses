# 🧮 Математичний аналіз джитеру та розподілу навантаження ретраїв

Коли зовнішній сервіс споживача зазнає тимчасової аварії і тисячі паралельних викликів вебхуків одночасно завершуються помилками тайм-ауту або HTTP 503, алгоритм розрахунку затримок між повторними спробами (англ. retry backoff) визначає, чи зможе відновлена система повернутися до нормальної роботи, чи буде миттєво знищена лавиною повторних запитів.

Математична проблема полягає у розподілі випадкової величини часу відправлення запиту `t` на часовій осі так, щоб максимізувати ймовірність успішної доставки за мінімальний сумарний час і водночас обмежити пікову щільність запитів на одиницю часу `λ(t)` нижче пропускної здатності цільового сервера `C`.

## Постановка стохастичної моделі збою та повторів

Припустимо, що провайдер вебхуків обслуговує групу клієнтів, чий приймальний сервер у момент часу `t = 0` зазнає збою (наприклад, перезапуск процесу, втрата з'єднання з базою даних або короткочасний сплеск вхідного трафіку). У системі провайдера знаходиться `N` незалежних повідомлень, адресованих цьому ендпоінту.

Кожен із `N` запитів у момент `t = 0` завершується помилкою. Провайдер переводить кожне повідомлення на крок повторної спроби `n = 1, 2, ..., M`, де `M` — максимальна дозволена кількість спроб перед скиданням у мертву чергу (англ. Dead-Letter Queue).

Для кожного повідомлення `i ∈ {1, 2, ..., N}` на кроці `n` генерується випадкова величина затримки `T[i, n]`. Відповідно, момент часу, коли повідомлення буде повторно надіслано в мережу, дорівнює:

```
t[i, n] = t[i, n-1] + T[i, n]
```

де `t[i, 0] = 0` — момент першого зафіксованого збою.

Нехай тривалість обробки одного HTTP-запиту на боці сервера споживача є випадковою величиною `δ` із середнім значенням `E[δ]` (час виконання обробника плюс мережева затримка round-trip time, типово `δ ∈ [0.02, 0.2]` секунд). Якщо в часовому вікні `[t, t + δ]` на сервер надходить `k` запитів, кількість одночасно відкритих TCP-з'єднань та зайнятих потоків бекенда в цей момент дорівнює `k`.

Якщо пропускна здатність споживача обмежена числом робочих потоків або лімітом пулу з'єднань СУБД `C_max`, то за умови `k > C_max` сервер знову відмовляє з кодом HTTP 503 (Service Unavailable) або скидає TCP-з'єднання через переповнення черги `listen backlog`.

## Детермінований експоненційний відступ і проблема лавини

У класичній детермінованій моделі експоненційного відступу (англ. Deterministic Exponential Backoff) час очікування для кроку `n` обчислюється за формулою:

```
T_det(n) = min(t_max, t_0 · 2ⁿ)
```

де:
- `t_0` — базовий інтервал очікування (наприклад, `t_0 = 1.0` с);
- `t_max` — верхня межа інтервалу відступу (наприклад, `t_max = 3600` с = 1 година);
- `n` — цілочисельний номер поточної спроби (`n ∈ {0, 1, 2, ...}`).

Оскільки функція `T_det(n)` є строго детермінованою і не містить стохастичної складової, випадкова величина затримки для всіх `N` повідомлень має нульову дисперсію:

```
E[T_det(n)] = min(t_max, t_0 · 2ⁿ)
Var(T_det(n)) = 0
```

Це призводить до явища, відомого як лавинний ефект або проблема стада, що біжить (англ. Thundering Herd Problem, від лат. tonitrus — грім). Якщо `N` запитів зазнали невдачі в момент `t = 0`, усі `N` повторних запитів першої спроби (`n = 1`) будуть надіслані точно в момент `t = t_0 · 2¹ = 2` с.

Якщо тривалість обробки запиту становить `δ`, миттєва інтенсивність вхідного потоку запитів `λ(t)` у точці `t = t_0 · 2ⁿ` являє собою дельта-подібний імпульс:

```
λ_peak = N / δ
```

Для системи з `N = 10 000` завислих вебхуків та середнім часом відповіді `δ = 50` мс (`0.05` с) пікова інтенсивність сягає:

```
λ_peak = 10000 / 0.05 = 200 000 запитів / секунду
```

Якщо споживач спроможний обробляти щонайбільше `C_max = 500` запитів на секунду, то 99.75% повторних викликів негайно зазнають повторного колапсу. На кроці `n = 2` вся маса `N` повідомлень знову синхронно вдарить по серверу в момент `t = 4` с, на кроці `n = 3` — у момент `t = 8` с. Детермінований відступ збільшує паузи між ударами, але не зменшує амплітуду самого удару.

## Введення випадковості: класифікація моделей джитеру

Щоб ліквідувати синхронізацію та розсіяти дельта-імпульс `λ_peak` у плавний неперервний потік, до детермінованої бази додають псевдовипадкову величину — джиттер (англ. jitter — «тремтіння, флуктуація»).

Розглянемо три фундаментальні схеми рандомізації: Full Jitter, Equal Jitter та Decorrelated Jitter.

### 1. Повний джиттер (Full Jitter)

У схемі Full Jitter обчислюється детермінована стеля для поточного кроку `V_n = min(t_max, t_0 · 2ⁿ)`, після чого фактична затримка вибирається рівномірно на відрізку від `0` до `V_n`:

```
T_full(n) ~ Uniform(0, min(t_max, t_0 · 2ⁿ))
```

Знайдемо математичне сподівання та дисперсію цієї випадкової величини. Для неперервного рівномірного розподілу на відрізку `[0, V_n]`:

```
E[T_full(n)] = (0 + V_n) / 2 = V_n / 2 = (min(t_max, t_0 · 2ⁿ)) / 2

Var(T_full(n)) = (V_n - 0)² / 12 = V_n² / 12 = (min(t_max, t_0 · 2ⁿ))² / 12
```

Густина ймовірності `f(t)` розподілена рівномірно на інтервалі шириною `V_n`:

```
f(t) = 1 / V_n  для  t ∈ [0, V_n],  і  0 за межами інтервалу.
```

Миттєва очікувана інтенсивність потоку запитів `λ_full(t)` при одночасному збої `N` подій стає неперервною функцією:

```
λ_full(t) = N · f(t) = N / V_n = N / (t_0 · 2ⁿ)
```

Порівняємо пікову інтенсивність детермінованого підходу та Full Jitter:

```
λ_peak_det / λ_full = (N / δ) / (N / V_n) = V_n / δ
```

Для кроку `n = 3`, `t_0 = 1.0` с (`V_3 = 8` с) та тривалості обробки `δ = 0.05` с відношення пікового навантаження становить:

```
V_3 / δ = 8.0 / 0.05 = 160 разів
```

Full Jitter зменшує пікове навантаження на цільовий сервер у 160 разів уже на третьому кроці ретраю, перетворюючи нищівний удар на рівномірне фонове навантаження.

### 2. Рівний (половинний) джиттер (Equal Jitter)

Недоліком Full Jitter є ненульова ймовірність згенерувати значення затримки, близьке до нуля (наприклад, `T ≈ 0.001` с), навіть на високих кроках `n`. Це означає, що невелика частка запитів повторюється майже миттєво після збою, коли сервер гарантовано ще не встиг відновитися.

Схема Equal Jitter усуває цей ефект, фіксуючи половину інтервалу як гарантований детермінований відступ, а другу половину рандомізуючи:

```
V_n = min(t_max, t_0 · 2ⁿ)
T_equal(n) = (V_n / 2) + Uniform(0, V_n / 2)
```

Обчислимо характеристики розподілу для Equal Jitter:

```
E[T_equal(n)] = V_n / 2 + (0 + V_n / 2) / 2
              = V_n / 2 + V_n / 4
              = (3 / 4) · V_n

Var(T_equal(n)) = (V_n / 2 - 0)² / 12
                = (V_n² / 4) / 12
                = V_n² / 48
```

Порівняння з Full Jitter:
1. Гарантована нижня межа: `T_equal(n) ≥ V_n / 2`. Запити на кроці `n = 4` (`V_4 = 16` с) ніколи не почнуть надходити раніше, ніж через 8 секунд.
2. Середній час очікування вищий: `E[T_equal] = 0.75 · V_n` проти `0.5 · V_n` у Full Jitter, що дещо збільшує загальний час доставки.
3. Дисперсія вчетверо менша: `Var(T_equal) = V_n² / 48` проти `V_n² / 12`. Менша дисперсія означає, що трафік розсіюється по інтервалу вдвічі вужчому (`[V_n / 2, V_n]`), тому пікова інтенсивність `λ_equal` буде вдвічі вищою, ніж у Full Jitter (`λ_equal = 2 · N / V_n`), проте все ще в десятки разів нижчою за детермінований сплеск.

### 3. Декорельований джиттер (Decorrelated Jitter)

У схемах Full Jitter та Equal Jitter затримка на кроці `n` залежить виключно від номера кроку `n` та базових констант `t_0`, `t_max`. Декорельований джиттер є рекурентним марковським процесом (від лат. decorrelatio — порушення зв'язку), де кожна наступна затримка обчислюється на основі фактично згенерованого попереднього значення `T[n-1]`:

```
T_decorr(0) = t_0
T_decorr(n) = min(t_max, Uniform(t_0, 3 · T_decorr(n-1)))
```

Для кожного повідомлення послідовність затримок формує випадкове блукання з мультиплікативним зростанням.

Обчислимо умовне математичне сподівання на кроці `n` за умови відомого попереднього значення `T[n-1] = x`:

```
E[T_decorr(n) | T[n-1] = x] = (t_0 + 3x) / 2 = 1.5 · x + 0.5 · t_0  (до досягнення t_max)
```

Коефіцієнт зростання математичного сподівання за крок дорівнює `1.5`, що менше за детермінований множник `2.0`. Проте Decorrelated Jitter повністю руйнує кореляцію між моментами відправлення повідомлень, які мали однаковий номер спроби. Навіть якщо група повідомлень одночасно перейшла на крок `n = 3`, їхні затримки `T[3]` будуть залежати від різних реалізацій `T[2]`, що забезпечує максимальне перемішування трафіку в часі.

## Динаміка сумарного часу доставки та навантаження черги

Розглянемо випадкову величину сумарного часу очікування `S_k` до виконання `k`-ї спроби:

```
S_k = ∑_{i=1}^k T(i)
```

Для незалежних затримок математичне сподівання суми дорівнює сумі математичних сподівань:

```
E[S_k] = ∑_{i=1}^k E[T(i)]
```

А дисперсія сумарного часу дорівнює сумі дисперсій:

```
Var(S_k) = ∑_{i=1}^k Var(T(i))
```

Обчислимо ці характеристики для детермінованого відступу та Full Jitter при сумі перших `k` спроб (вважаючи, що стеля `t_max` ще не досягнута, `t_0 · 2ⁱ < t_max`):

### Детермінований відступ:

```
E[S_k_det] = ∑_{i=1}^k t_0 · 2ⁱ = t_0 · (2¹ + 2² + ... + 2ᵏ) = t_0 · (2^{k+1} - 2)
Var(S_k_det) = 0
```

### Full Jitter:

```
E[S_k_full] = ∑_{i=1}^k (t_0 · 2ⁱ) / 2 = (t_0 / 2) · (2^{k+1} - 2) = t_0 · (2ᵏ - 1)

Var(S_k_full) = ∑_{i=1}^k (t_0 · 2ⁱ)² / 12 = (t_0² / 12) · ∑_{i=1}^k 4ⁱ
              = (t_0² / 12) · (4 · (4ᵏ - 1) / 3)
              = (t_0² / 9) · (4ᵏ - 1)
```

Стандартне відхилення сумарного часу доставки для Full Jitter:

```
σ(S_k_full) = √Var(S_k_full) = (t_0 / 3) · √(4ᵏ - 1) ≈ (t_0 / 3) · 2ᵏ
```

Зауважимо фундаментальну властивість: для Full Jitter стандартне відхилення `σ(S_k_full)` має той самий порядок зростання `O(2ᵏ)`, що й саме математичне сподівання `E[S_k_full] = O(2ᵏ)`.

Це означає, що зі збільшенням кількості спроб `k` інтервал можливих часів прибуття запитів розширюється пропорційно середньому часу очікування. Якщо для `k = 5` і `t_0 = 1.0` с середній сумарний час становить `E[S_5] = 31` с, то стандартне відхилення дорівнює `σ ≈ 10.6` с. Повідомлення, що стартували одночасно, розсіюються по вікну тривалістю понад 40 секунд.

## Ймовірнісна модель колізій і перевантаження пулу споживача

Оцінимо ймовірність виникнення перевантаження цільового сервера в довільний момент часу `t`.

Нехай сервер споживача має `C` паралельних слотів обробки (пул воркерів або з'єднань БД). Кожен запит займає слот на час `δ`. Це відповідає класичній системі масового обслуговування типу `M/G/C/C` (формула Ерланга B), де запити, що перевищують ємність `C`, відхиляються або скидаються.

Якщо `N` повідомлень рівномірно розподілені по інтервалу тривалістю `W = V_n`, інтенсивність потоку надходження становить `λ = N / W`. Кількість запитів `K`, що надходять у вікно тривалості `δ`, підпорядковується розподілу Пуассона з параметром `μ = λ · δ = (N · δ) / W`:

```
P(K = k) = (μᵏ / k!) · e^{-μ}
```

Ймовірність того, що сервер перевищить свою пропускну здатність `C` (переповнення пулу з'єднань), виражається через хвіст пуассонівського розподілу:

```
P(K > C) = 1 - ∑_{k=0}^C (μᵏ / k!) · e^{-μ}
```

Для детермінованого відступу все навантаження `N` зосереджено в точці, тому `W → 0`, `μ → ∞`, і `P(K > C) = 1` для будь-якого скінченного `C < N`.

Для Full Jitter ширина вікна `W_n = t_0 · 2ⁿ` подвоюється на кожному кроці. Відповідно, параметр навантаження спадає:

```
μ_n = (N · δ) / (t_0 · 2ⁿ)
```

Коли `μ_n < C`, за нерівністю Чернова ймовірність перевантаження спадає експоненційно:

```
P(K ≥ C) ≤ e^{-μ_n} · (e · μ_n / C)^C
```

Ця оцінка строго доводить, чому подвоєння вікна затримки експоненційно швидко зводить імовірність повторного колапсу до нуля.

Крім того, розрахунок показує вплив джитеру на утримання сокетів на боці самого провайдера: коли запити відправляються одночасно, провайдер вичерпує власний пул вихідних портів (англ. ephemeral ports exhaustion), оскільки операційна система підтримує щонайбільше ~60 000 одночасних вихідних з'єднань на одну IP-адресу. Розмазування трафіку через Full Jitter утримує кількість активних вихідних TCP-сокетів на рівні `Q_active = N · δ / W_n`, що захищає локальний стек TCP/IP від вичерпання дескрипторів.

## Марковська модель життєвого циклу повідомлення

Розглянемо повну стохастичну динаміку черги вебхуків як дискретний марковський ланцюг зі станами:
- `S_n` (`n = 0, 1, ..., M-1`) — стан повідомлення перед `n`-ю спробою відправки;
- `S_{success}` — поглинальний стан успішної доставки (HTTP 2xx);
- `S_{DLQ}` — поглинальний стан мертвої черги (вичерпання ліміту `M` або фатальна помилка HTTP 4xx).

Нехай `p` — ймовірність того, що сервер споживача відмовить на черговій спробі (ймовірність помилки, `0 ≤ p ≤ 1`), а `q = 1 - p` — ймовірність успіху.

Ймовірність того, що повідомлення буде успішно доставлене рівно на кроці `k` (`1 ≤ k ≤ M`), дорівнює:

```
P(доставка на кроці k) = p^{k-1} · (1 - p)
```

Ймовірність того, що повідомлення потрапить у Dead-Letter Queue після вичерпання всіх `M` спроб:

```
P(DLQ) = p^M
```

Очікувана середня кількість спроб `E[Attempts]`, необхідних для обробки одного повідомлення:

```
E[Attempts] = ∑_{k=1}^M k · p^{k-1} · (1 - p) + M · p^M
            = (1 - p^M) / (1 - p)
```

При малих значеннях ймовірності збою `p ≪ 1` середня кількість спроб `E[Attempts] ≈ 1 + p`, а вартість ретраїв незначна. Проте коли сервіс споживача лежить тривалий час (`p ≈ 1.0`), кожне повідомлення генерує рівно `M` запитів, збільшуючи трафік на інфраструктуру провайдера рівно в `M` разів (коефіцієнт мультиплікації навантаження).

Саме тому провайдер зобов'язаний поєднувати експоненційний backoff з механізмом Circuit Breaker: якщо спостережувана ймовірність помилки `p → 1`, генерація ретраїв тимчасово призупиняється для всієї черги даного споживача, запобігаючи множенню холостого трафіку.

## Розрахунковий приклад: аварія 50 000 вебхуків

Розглянемо практичний сценарій збою великого провайдера вебхуків:
- Кількість завислих подій: `N = 50 000`;
- Базовий інтервал: `t_0 = 2.0` с;
- Максимальна стеля: `t_max = 300` с (5 хвилин);
- Середній час обробки на боці клієнта: `δ = 0.04` с (40 мс);
- Максимальна стійка пропускна здатність споживача: `C_max = 200` RPS.

Зведемо результати розрахунку характеристик для спроб `n = 1..6` у порівняльну таблицю:

| Крок `n` | Стеля `V_n` (с) | Детермінований `E[T]` | Детерм. `RPS_peak` | Full Jitter `E[T]` | Full Jitter `RPS_avg` | Equal Jitter `E[T]` | Equal Jitter `RPS_avg` |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 1 | 4.0 | 4.0 с | 1 250 000 | 2.0 с | 12 500 | 3.0 с | 25 000 |
| 2 | 8.0 | 8.0 с | 1 250 000 | 4.0 с | 6 250 | 6.0 с | 12 500 |
| 3 | 16.0 | 16.0 с | 1 250 000 | 8.0 с | 3 125 | 12.0 с | 6 250 |
| 4 | 32.0 | 32.0 с | 1 250 000 | 16.0 с | 1 562 | 24.0 с | 3 125 |
| 5 | 64.0 | 64.0 с | 1 250 000 | 32.0 с | 781 | 48.0 с | 1 562 |
| 6 | 128.0 | 128.0 с | 1 250 000 | 64.0 с | 390 | 96.0 с | 781 |

У детермінованому варіанті кожна спроба генерує миттєвий пік `50000 / 0.04 = 1 250 000` RPS, що у 6250 разів перевищує ліміт споживача `C_max = 200` RPS.

У схемі Full Jitter навантаження на кожному кроці спадає рівно вдвічі. Вже на кроці `n = 6` середня інтенсивність надходження падає до `390` RPS, наближаючись до зони стабілізації клієнтського сервісу. Якщо частина запитів починає успішно оброблятися, залишкове навантаження `N_{remaining}` падає за експоненційним законом, прискорюючи вихід системи з аварійного стану.

## Критерій вибору оптимального алгоритму

На основі стохастичного аналізу формулюється практичне правило вибору алгоритму повторів для архітектури вебхук-провайдера:

1. **Критерій мінімізації пікового навантаження на споживача (Downstream Work Contention):**
   Full Jitter є строго оптимальним, оскільки забезпечує максимальну дисперсію `Var(T) = V_n² / 12` на відрізку `[0, V_n]` і мінімальне значення математичного сподівання сумарного часу затримки `E[S_k] = t_0 · (2ᵏ - 1)`. Сервер споживача отримує найменшу пікову щільність запитів при найшвидшій середній доставці.

2. **Критерій захисту від передчасних ретраїв на ранніх стадіях аварії:**
   Equal Jitter застосовується тоді, коли відомо, що мінімальний час відновлення стороннього сервісу (наприклад, холодний рестарт бекенда в контейнері) становить десятки секунд. Нижня межа `T_min = V_n / 2` гарантує відсутність холостих викликів у перші миті після фіксації помилки.

3. **Критерій ізоляції клієнтських черг:**
   У багатотенантній системі розрахунок затримок за алгоритмом Full Jitter у поєднанні з обмеженням швидкості на рівні клієнта (Per-Tenant Rate Limiting) усуває як глобальні сплески навантаження на інфраструктуру провайдера, так і локальні перевантаження кінцевих споживачів.
