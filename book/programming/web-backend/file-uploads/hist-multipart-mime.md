# 📜 Як з'явився multipart/form-data: від електронної пошти до RFC 1867

Електронна пошта початку 1980-х років спиралася на протокол SMTP (англ. *Simple Mail Transfer Protocol*, RFC 821, серпень 1982), який створювали винятково для обміну 7-бітним англійським текстом у кодуванні ASCII. Системи поштового реле безжально відкидали або обнуляли восьмий біт кожного байта, якщо хтось намагався передати двійковий файл (наприклад, скомпільовану програму чи оцифроване зображення). Щоби переслати двійкові дані, користувачам доводилося вручну перетворювати їх на текстові рядки за допомогою утиліт `uuencode`, вставляти отриманий текст у тіло листа й сподіватися, що адресат на іншому кінці власноруч викличе `uudecode`.

Цей хаос спонукав робочу групу IETF під керівництвом Натана Боренштейна (*Nathan Borenstein*) та Неда Фріда (*Ned Freed*) розробити стандарт MIME (англ. *Multipurpose Internet Mail Extensions*, RFC 1341, червень 1992, пізніше вдосконалений у RFC 2046, листопад 1996). MIME заклав два фундаментальні принципи: типізацію вмісту через заголовок `Content-Type` із розбиттям на тип і підтип (як-от `image/jpeg` або `application/octet-stream`) та механізм пакування кількох різних за природою сутностей у єдине повідомлення — медіатип `multipart/mixed`.

Щоби відокремити один блок даних від іншого без зміни двійкового вмісту, винайшли текстову межу — рядок-роздільник (англ. *boundary*). Правило було простим: заголовок повідомлення оголошував унікальний рядок символів, а тіло листа ділилося на частини, кожна з яких починалася з двох дефісів і цього рядка (`--boundary`), а завершувалася фінальною міткою (`--boundary--`). Якщо всередині частини передавалися двійкові байти, їх кодували через Base64 (RFC 2045), який пакував три довільні байти у чотири ASCII-символи, додаючи приблизно 33% накладних витрат обсягу.

## Ранній веб і глухий кут передачі форм

У 1993–1994 роках ранній веб стрімко набирав популярності, проте механізм взаємодії користувача із сервером залишався примітивним. Перша специфікація мови HTML описувала форми з єдиним форматом кодування — `application/x-www-form-urlencoded`.

Цей формат перетворював усі пари імен і значень на єдиний суцільний ASCII-рядок, де пробіли замінювалися на знак `+`, а всі неалфавітні символи (зокрема будь-які байти двійкового файлу) записувалися як шістнадцятковий код із префіксом відсотка `%XX` (наприклад, нульовий байт перетворювався на `%00`, а байт зі значенням 255 — на `%FF`).

```
first_name=Ivan&last_name=Franko&avatar=%89PNG%0D%0A%1A%0A%00%00%00%0DIHDR...
```

Коли розробники спробували використати `application/x-www-form-urlencoded` для надсилання файлів, система зайшла у глухий кут із трьох причин:

1. **Трикратне роздування трафіку.** Двійковий файл розміром 10 МБ перетворювався на 30 МБ шістнадцяткового тексту, оскільки майже кожен байт потребував трьох символів замість одного. Для каналів зв'язку з модемами на 14.4 або 28.8 кбіт/с це означало багатогодинне очікування.
2. **Неможливість потокової обробки.** Серверні CGI-скрипти отримували цей монолітний рядок через стандартний потік вводу або змінну середовища `QUERY_STRING`, змушені були зчитувати всі десятки мегабайтів у пам'ять, шукати амперсанди `&` та вручну декодувати кожен `%XX` назад у байт. Оперативна пам'ять серверів того часу (зазвичай від 16 до 64 МБ) переповнювалася на першому ж паралельному запиті.
3. **Втрата метаданих.** Формат не мав засобів передати оригінальне ім'я файлу на диску клієнта, його системний тип чи дату модифікації без окремих додаткових полів у формі.

## Суперечки в IETF: чи потрібен Base64 у HTTP

У середині 1990-х років точилася принципова дискусія між інженерами поштових протоколів та архітекторами раннього вебу. Творець HTTP Тім Бернерс-Лі (*Tim Berners-Lee*) та пізніше Рой Філдінг (*Roy Fielding*) відстоювали позицію, що HTTP із самого початку проєктувався як 8-бітний чистий транспорт (англ. *8-bit clean*). На відміну від застарілих поштових шлюзів, вебсервери не модифікували старший біт байта і не вимагали закінчення рядків лише в стилі телетайпу.

Представники поштового табору стверджували, що для уніфікації слід узяти готовий `multipart/mixed` разом із кодуванням `Base64` або `Quoted-Printable`. Проте веб-інженери наполягали: додавати 33% накладних витрат до кожного завантаженого файлу в умовах повільних мереж — неприпустиме марнотратство обчислювальних ресурсів і каналів передачі.

Компроміс полягав у тому, щоби запозичити сам синтаксис меж MIME, але дозволити передачу сирих двійкових байтів у тілі частин без проміжного текстового кодування.

## Пропозиція RFC 1867: Masinter і Nebel

У листопаді 1995 року Ларрі Масінтер (*Larry Masinter*) із корпорації Xerox та Ернесто Небель (*Ernesto Nebel*) опублікували історичний документ RFC 1867 під назвою *«Form-based File Upload in HTML»*.

Автори запропонували поєднання двох взаємопов'язаних рішень:

* **Новий елемент інтерфейсу користувача в HTML.** Тег `<input type="file">`. Це дозволило браузерам показувати нативне системне діалогове вікно вибору файлу на диску користувача, де користувач міг вибрати один або кілька локальних файлів.
* **Спеціалізований медіатип для HTTP-форм.** Замість загального `multipart/mixed` було введено тип `multipart/form-data`. Він описував повідомлення, що складалося з іменованих частин форми, де кожне текстове поле й кожен переданий файл отримували окремий блок зі своїми метаданими.

Кожна частина форми отримала заголовок `Content-Disposition`, де фіксувалися ім'я поля у формі (`name`) та опціональне початкове ім'я файлу на машині клієнта (`filename`):

```http
POST /upload HTTP/1.0
Content-Type: multipart/form-data; boundary=---------------------------974767299852498929531610575
Content-Length: 1048712

-----------------------------974767299852498929531610575
Content-Disposition: form-data; name="description"

Звіт за третій квартал
-----------------------------974767299852498929531610575
Content-Disposition: form-data; name="document"; filename="report.pdf"
Content-Type: application/pdf

%PDF-1.4 ... [сирі двійкові байти файлу без кодування Base64] ...
-----------------------------974767299852498929531610575--
```

Завдяки цьому рішенню накладні витрати протоколу скоротилися до кількох сотень байтів службових заголовків на все завантаження, незалежно від того, чи важив файл один мегабайт, чи сто.

## Перші бібліотеки: Lincoln Stein, CGI.pm та PHP

Після виходу RFC 1867 у розробників виникла нагальна потреба в готових інструментах парсингу нового формату. У 1995 році Лінкольн Стейн (*Lincoln Stein*) створив для мови Perl модуль `CGI.pm`, який став де-факто стандартом веб-розробки 1990-х років. Стейн реалізував розбір `multipart/form-data` на рівні тимчасових файлів операційної системи: модуль перехоплював вхідний потік вебсервера, створював дескриптор у `/tmp` і скидав туди байти частин, надаючи скрипту зручний файловий дескриптор замість сирого масиву байтів.

Наприкінці 1990-х років Расмус Лердорф (*Rasmus Lerdorf*) та розробники PHP 3 і PHP 4 вбудували автоматичний парсинг `multipart/form-data` безпосередньо в рушій мови через глобальний масив `$_FILES`. Щоразу, коли на PHP-сервер приходив запит із типом `multipart/form-data`, інтерпретатор автоматично парсив усі частини запиту ще до виконання першого рядка коду користувача, зберігаючи завантажені файли у системному каталозі під випадковими іменами виду `/tmp/phpYzdqkD`.

Це рішення зробило завантаження файлів надзвичайно простим для мільйонів веб-майстрів, проте водночас заклало архітектурну бомбу сповільненої дії: сервер повністю блокувався на час прийому важких файлів по повільних каналах зв'язку, а оперативна пам'ять або дисковий простір вичерпувалися задовго до того, як прикладний код встигав перевірити права користувача.

## Перші вразливості та проблеми реалізації в браузерах

Першим браузером, який підтримав RFC 1867, став Netscape Navigator 2.0 наприкінці 1995 року. Майже одночасно підтримку додали автори вебсервера NCSA HTTPd та перших версій Apache HTTP Server. Проте перша хвиля впровадження виявила серйозні проблеми безпеки та сумісності:

### Розкриття структури файлової системи (Path Traversal)
Ранні версії браузера Microsoft Internet Explorer передавали в параметрі `filename` не просто назву файлу, а повний локальний шлях в операційній системі Windows: `filename="C:\Documents and Settings\Admin\Personal\secret.pdf"`.
Це призводило до витоку конфіденційної структури каталогів клієнта, а на стороні серверів викликало помилки: наївні CGI-скрипти намагалися відкрити файл за переданим рядком і створювали файли у непередбачуваних каталогах або перетирали системні файли сервера.

### Хаос кодових сторінок
До повсюдного впровадження стандарту Unicode та UTF-8 на початку 2000-х років кожна операційна система надсилала імена файлів у локальному кодуванні. Якщо користувач у Windows завантажував файл із назвою `звіт.doc`, браузер надсилав байти кодування Windows-1251. Якщо сервер працював під керуванням FreeBSD або Linux з локаллю KOI8-U чи ISO-8859-1, ім'я файлу перетворювалося на нечитабельний набір символів. Протокол RFC 1867 не мав поля для зазначення кодування параметра `filename`.

### Атаки на вичерпання дисків CGI-скриптів
Ранні вебсервери за замовчуванням зберігали всі частини `multipart/form-data` у системний каталог `/tmp`. Зловмисники надсилали гігантські файли у паралельних з'єднаннях, миттєво переповнюючи кореневий розділ диска сервера, що блокувало роботу всієї операційної системи.

## Еволюція: від RFC 2388 до RFC 7578

У серпні 1998 року робоча група IETF опублікувала RFC 2388 (*«Returning Values from Forms: multipart/form-data»*), який деталізував обробку кількох файлів у межах одного поля введення та рекомендував клієнтам надсилати лише базову назву файлу без інформації про каталоги.

Однак справжній консенсус було знайдено лише у травні 2015 року з виходом RFC 7578, авторами якого стали представники вендорів усіх ключових браузерів (Mozilla, Google, Apple):

1. **Суворий UTF-8.** Усі заголовки частин та імена файлів зобов'язані передаватися винятково в кодуванні UTF-8 або через синтаксис процентного кодування RFC 5987 (`filename*=UTF-8''%D0%B7%D0%B2%D1%96%D1%82.pdf`).
2. **Остаточна заборона префіксів шляхів.** Клієнти зобов'язані обрізати будь-які слеші (`/` та `\`) перед відправкою заголовка `filename`.
3. **Видалення застарілих концепцій MIME.** Було офіційно заборонено використання заголовка `Content-Transfer-Encoding` всередині частин HTTP multipart-запиту: веб остаточно відмовився від поштової спадщини 7-бітних систем.

Конструкція, винайдена Боренштейном, Фрідом, Масінтером і Небелем понад три десятиліття тому як спосіб узгодити несумісні світи пошти та вебу, залишається фундаментальним транспортом файлових потоків у сучасному інтернеті.
