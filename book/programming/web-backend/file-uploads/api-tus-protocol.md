# 📋 Протокол відновлюваного завантаження TUS 1.0.0

Протокол TUS (англ. *open protocol for resumable file uploads*, версія 1.0.0) стандартизує механізм надійного відновлюваного завантаження файлів поверх протоколу HTTP/1.1 та HTTP/2. Головна мета специфікації — забезпечити гарантоване відновлення передачі гігабайтних обсягів даних після непередбачуваних обривів зв'язку, збоїв мережевого обладнання або перемикання між Wi-Fi та стільниковою мережею, усуваючи необхідність повторно передавати вже отримані сервером байти.

Специфікація розділена на базовий обов'язковий протокол (англ. *Core Protocol*) та набір офіційних розширень (англ. *Protocol Extensions*), які узгоджуються між клієнтом і сервером під час фази виявлення можливостей через метод `OPTIONS`.

## Базовий протокол (Core Protocol)

Базовий протокол описує механізм виявлення поточного стану завантаження та дописування байтів у кінець незавершеного файлу.

### Обов'язкові заголовки запиту та відповіді

| Заголовок | Тип | Опис та формат |
| :--- | :--- | :--- |
| `Tus-Resumable` | Запит / Відповідь | Версія протоколу. Клієнт і сервер зобов'язані передавати значення `1.0.0` у кожному запиті та відповіді. |
| `Tus-Version` | Відповідь | Список підтримуваних сервером версій протоколу через кому (наприклад, `1.0.0,0.2.2`). |
| `Tus-Max-Size` | Відповідь | Максимально дозволений розмір завантажуваного файлу в байтах (ціле невід'ємне число). |
| `Tus-Extension` | Відповідь | Список підтримуваних сервером розширень (наприклад, `creation,termination,checksum`). |
| `Upload-Offset` | Запит / Відповідь | Поточний зсув файлу в байтах від початку (десяткове ціле число). Визначає точку, з якої сервер очікує наступний байт. |
| `Upload-Length` | Відповідь | Повний остаточний розмір завантажуваного файлу в байтах. |
| `Content-Type` | Запит | Для методу `PATCH` значення зобов'язане бути суворо `application/offset+octet-stream`. |

### Метод HEAD: Опитування стану та зсуву

Клієнт використовує метод `HEAD` для визначення точної кількості байтів, які сервер уже успішно зафіксував на своєму боці. Це дозволяє клієнту дізнатися, з якої саме позиції слід відновити завантаження після раптового обриву мережі або перезавантаження браузера.

#### Приклад запиту:
```http
HEAD /files/24e533e029fc3d441ba7478d HTTP/1.1
Host: upload.example.com
Tus-Resumable: 1.0.0
```

#### Приклад відповіді (успіх — 200 OK):
```http
HTTP/1.1 200 OK
Upload-Offset: 70866960
Upload-Length: 100000000
Tus-Resumable: 1.0.0
Cache-Control: no-store
```

#### Інваріанти методу HEAD:
* **Заборона кешування.** Сервер зобов'язаний повернути заголовок `Cache-Control: no-store`, щоби проміжні проксі-сервери не віддавали застарілий зсув.
* **Відсутність тіла.** Відповідь на `HEAD` ніколи не містить корисного навантаження в тілі.
* **Обробка неіснуючих сесій.** Якщо ресурс не знайдено або термін його придатності минув, сервер повертає `404 Not Found` або `410 Gone`.

### Метод PATCH: Передача порції даних (Чанка)

Метод `PATCH` передає сирі двійкові байти для додавання у кінець файлу, починаючи суворо зі зсуву, вказаного в заголовку `Upload-Offset`.

#### Приклад запиту:
```http
PATCH /files/24e533e029fc3d441ba7478d HTTP/1.1
Host: upload.example.com
Upload-Offset: 70866960
Content-Type: application/offset+octet-stream
Content-Length: 29133040
Tus-Resumable: 1.0.0

[... 29 133 040 двійкових байтів ...]
```

#### Приклад відповіді (успіх — 204 No Content):
```http
HTTP/1.1 204 No Content
Upload-Offset: 100000000
Tus-Resumable: 1.0.0
```

#### Інваріанти методу PATCH:
* **Суворий контроль зсуву (Конфлікт 409):** Якщо заголовок `Upload-Offset` у запиті клієнта не збігається з поточним реальним розміром файлу на сервері, сервер зобов'язаний негайно відхилити запит із кодом `409 Conflict` без збереження переданих байтів. Це запобігає пошкодженню файлу при паралельних або повторних запитах.
* **Перевірка заголовка Content-Type (415):** Якщо значення `Content-Type` відмінне від `application/offset+octet-stream`, сервер повертає `415 Unsupported Media Type`.
* **Оновлення зсуву:** У разі успішного збереження чанка сервер повертає статус `204 No Content` та новий зсув у заголовку `Upload-Offset`, який дорівнює сумі початкового зсуву та кількості прийнятих байтів.

### Метод OPTIONS: Виявлення можливостей сервера

Метод `OPTIONS` дозволяє клієнту наперед дізнатися конфігурацію сервера, максимальний розмір завантаження та список доступних розширень.

#### Приклад запиту:
```http
OPTIONS /files HTTP/1.1
Host: upload.example.com
```

#### Приклад відповіді (204 No Content або 200 OK):
```http
HTTP/1.1 204 No Content
Tus-Resumable: 1.0.0
Tus-Version: 1.0.0
Tus-Max-Size: 10737418240
Tus-Extension: creation,creation-with-upload,termination,checksum,concatenation,expiration
```

## Офіційні розширення протоколу (Extensions)

### 1. Розширення Creation (Створення ресурсу)

Дозволяє клієнту ініціювати нову сесію завантаження через надсилання запиту `POST` на головний ендпойнт створення.

#### Приклад запиту створення:
```http
POST /files HTTP/1.1
Host: upload.example.com
Upload-Length: 100000000
Upload-Metadata: filename dmlkZW8ubXA0,mimetype dmlkZW8vbXA0,is_public dHJ1ZQ==
Tus-Resumable: 1.0.0
Content-Length: 0
```

#### Приклад відповіді (201 Created):
```http
HTTP/1.1 201 Created
Location: https://upload.example.com/files/24e533e029fc3d441ba7478d
Upload-Offset: 0
Tus-Resumable: 1.0.0
```

#### Формат заголовка Upload-Metadata:
Метадані передаються як список пар `ключ значення`, розділених комами. Значення обов'язково кодуються в алгоритмі Base64:
```
Upload-Metadata: key1 Base64(val1), key2 Base64(val2)
```

#### Відкладена довжина (Upload-Defer-Length):
Якщо на момент старту клієнт не знає кінцевого розміру потоку (наприклад, прямий стрім із камери або динамічно стискуваний архів), замість `Upload-Length` передається заголовок `Upload-Defer-Length: 1`. Клієнт передає реальний `Upload-Length` у фінальному `PATCH`-запиті.

### 2. Розширення Creation With Upload

Дозволяє об'єднати створення файлу та передачу першого блоку даних в один мережевий HTTP-запит `POST`, скорочуючи затримку (Round-Trip Time, RTT) для швидких з'єднань.

```http
POST /files HTTP/1.1
Host: upload.example.com
Upload-Length: 100000000
Upload-Metadata: filename dmlkZW8ubXA0
Content-Type: application/offset+octet-stream
Content-Length: 5242880
Tus-Resumable: 1.0.0

[... перші 5 МБ даних ...]
```

Сервер повертає `201 Created` із заголовком `Upload-Offset: 5242880`.

### 3. Розширення Termination (Примусове видалення)

Дозволяє клієнту або серверу скасувати незавершене завантаження та негайно звільнити зарезервоване дискове сховище.

#### Приклад запиту:
```http
DELETE /files/24e533e029fc3d441ba7478d HTTP/1.1
Host: upload.example.com
Tus-Resumable: 1.0.0
```

#### Приклад відповіді:
```http
HTTP/1.1 204 No Content
Tus-Resumable: 1.0.0
```

### 4. Розширення Checksum (Перевірка цілісності чанка)

Запобігає пошкодженню даних при проходженні крізь дефектні роутери та мережеві проксі. Клієнт додає до запиту `PATCH` заголовок `Upload-Checksum`, що містить назву геш-алгоритму та Base64-значення контрольної суми цього конкретного чанка.

```http
PATCH /files/24e533e029fc3d441ba7478d HTTP/1.1
Host: upload.example.com
Upload-Offset: 0
Content-Type: application/offset+octet-stream
Upload-Checksum: sha256 K7gNU3sdo+OL0wNhqoVWhr3g6s1xYv72ol/pe/Unols=
Content-Length: 5242880
Tus-Resumable: 1.0.0

[... 5 МБ даних ...]
```

#### Помилка Checksum Mismatch (460):
Якщо сервер після отримання чанка обчислює інший хеш, він повертає спеціальний статус `460 Checksum Mismatch`, відкидає байти та залишає `Upload-Offset` незмінним. Клієнт повторює передачу того самого чанка.

### 5. Розширення Concatenation (Паралельне завантаження частин)

Дозволяє завантажувати великий файл паралельно у кілька незалежних TCP-потоків (наприклад, 4 частини по 250 МБ для 1 ГБ файлу) з подальшим безшовним об'єднанням на стороні сервера.

1. **Створення частин:** Клієнт створює кілька ресурсів із заголовком `Upload-Concat: partial`.
2. **Паралельне завантаження:** Кожна частина вантажиться незалежними `PATCH`-запитами.
3. **Фінальне зшивання:** Клієнт відправляє фінальний запит `POST` із заголовком `Upload-Concat: final;<url1> <url2> <url3> <url4>`. Сервер склеює файли на рівні блоків файлової системи без додаткового копіювання байтів через мережу.

### 6. Розширення Expiration (Строк життя сесії)

Сервер автоматично видаляє покинуті завантаження після закінчення терміну придатності. Заголовок `Upload-Expires` у форматі RFC 7231 вказує точний момент видалення файлу:

```http
Upload-Expires: Wed, 19 Aug 2026 18:30:00 GMT
```

## Налаштування міждоменного доступу (CORS)

Коли завантаження виконується безпосередньо з веббраузера на окремий домен або порт TUS-сервера, браузерний рушій безпеки блокує доступ до спеціальних заголовків.

Для забезпечення коректної роботи TUS-клієнтів у веббраузерах сервер зобов'язаний додавати такі HTTP-заголовки до всіх відповідей:

### 1. Дозвіл нестандартних заголовків запиту (Access-Control-Allow-Headers)
```http
Access-Control-Allow-Headers: Upload-Offset, Location, Upload-Length, Tus-Version, Tus-Resumable, Tus-Max-Size, Tus-Extension, Upload-Metadata, Upload-Defer-Length, Upload-Concat, Upload-Checksum
```

### 2. Експонування заголовків відповіді для JavaScript (Access-Control-Expose-Headers)
```http
Access-Control-Expose-Headers: Upload-Offset, Location, Upload-Length, Tus-Version, Tus-Resumable, Tus-Max-Size, Tus-Extension, Upload-Metadata, Upload-Defer-Length, Upload-Concat, Upload-Checksum, Upload-Expires
```

### 3. Дозволені методи HTTP (Access-Control-Allow-Methods)
```http
Access-Control-Allow-Methods: POST, GET, HEAD, PATCH, DELETE, OPTIONS
```

Якщо заголовок `Access-Control-Expose-Headers` налаштовано неправильно, клієнтський скрипт JavaScript не зможе прочитати значення заголовка `Upload-Offset` із відповіді сервера, і механізм відновлення завантаження не працюватиме.

## Динамічний підбір розміру чанка для мобільних клієнтів

Вибір розміру порції даних (чанка) для запиту `PATCH` є критичним компромісом між накладними витратами протоколу та вартістю повторної передачі при обриві зв'язку:

* **Завеликий чанк (наприклад, 100 МБ).** Якщо мобільне з'єднання обривається на 99-му мегабайті, клієнт змушений повторно передавати всі 99 МБ, марнуючи заряд батареї смартфона та трафік користувача.
* **Замалий чанк (наприклад, 64 КБ).** На швидкому з'єднанні 100 Мбіт/с клієнт виконує тисячі окремих HTTP-запитів `PATCH`, витрачаючи час на очікування підтверджень TCP і накладні витрати заголовків HTTP.

Клієнтські бібліотеки реалізують алгоритм адаптивного підбору розміру чанка (англ. *adaptive chunk sizing*):

1. Завантаження починається з мінімального базового чанка розміром `1 МБ`.
2. Клієнт заміряє час виконання запиту `PATCH`. Якщо передача триває менше ніж 2 секунди і не супроводжується помилками мережі, розмір наступного чанка подвоюється (`2 МБ -> 4 МБ -> 8 МБ -> 16 МБ`).
3. Максимальний розмір обмежується стелею `20 МБ` для мобільних мереж або `50 МБ` для стаціонарного оптоволокна.
4. Якщо запит `PATCH` завершується таймаутом або обривом TCP, розмір чанка миттєво зменшується вдвічі (до мінімуму `512 КБ`), що дозволяє пробити завантаження навіть крізь критично нестабільні канали зв'язку.

## Архітектура драйверів сховища на стороні сервера

Серверний демон TUS (наприклад, офіційний еталонний сервер `tusd`) не зберігає дані самостійно, а транслює протокольні операції в драйвери сховища (англ. *storage backends*).

### Драйвер локальної файлової системи (Filestore)
Застосовується на одиночних серверах. Для кожного завантаження створюються два файли:
* `upload_id.bin` — сирі збережені байти файлу.
* `upload_id.info` — JSON-структура з поточним станом (`Upload-Offset`, `Upload-Length`, метадані, строк дії).

Операція `PATCH` транслюється у пряме позиціювання файлового дескриптора через системний виклик ядра `lseek(fd, offset, SEEK_SET)` із наступним викликом `write()`. Це гарантує максимальну продуктивність і нульові накладні витрати на перепакування даних.

### Драйвер хмарного об'єктного сховища (S3Store / GCSStore)
Хмарні об'єктні сховища (AWS S3, Google Cloud Storage) не підтримують дописування довільних байтів до існуючого об'єкта. TUS-сервер вирішує цю проблему за допомогою API багаточастинного завантаження (S3 Multipart Upload):

1. При отриманні запиту `POST` (створення) сервер викликає в AWS S3 метод `CreateMultipartUpload`, отримуючи внутрішній `UploadId`.
2. Кожен вхідний запит `PATCH` накопичується у внутрішньому локальному буфері сервера до досягнення мінімального розміру частини S3 (5 МБ).
3. Щойно розмір накопиченого чанка досягає 5 МБ, сервер відправляє його в AWS через метод `UploadPart`.
4. Коли весь файл завантажено, TUS-сервер викликає `CompleteMultipartUpload`, зшиваючи всі завантажені частини в єдиний монолітний об'єкт.

## Розподілене блокування та кластеризація (DLM)

У розподілених інфраструктурах кластер TUS-серверів працює за балансувальником навантаження (англ. *Load Balancer*). Послідовні `PATCH`-запити одного завантаження можуть потрапляти на різні фізичні ноди.

Для запобігання гонкам даних застосовується розподілений менеджер блокувань (англ. *Distributed Lock Manager*, DLM) на базі Redis або Etcd:

```
[Клієнтський запит: PATCH /files/upload_99]
                    │
                    ▼
     [Балансувальник навантаження (HAProxy)]
                    │
         ┌──────────┴──────────┐
         ▼                     ▼
  [TUS Сервер Нода 1]   [TUS Сервер Нода 2]
         │                     │
         └──────────┬──────────┘
                    ▼
   [Redis Distributed Lock (Redlock)]
   Блокування ключа: "lock:upload:upload_99" (TTL 30с)
```

1. Перед обробкою запиту `PATCH` серверний вузол намагається встановити розподілене блокування в Redis із коротким строком життя (TTL 30 секунд).
2. Якщо інший вузол у цей момент уже записує чанк у цей самий файл, поточний вузол негайно повертає клієнту код `409 Conflict`.
3. Під час передачі великого блоку вузол періодично продовжує дію блокування в Redis.
4. Після завершення запису та скидання буферів на диск блокування звільняється.

## Стратегія збереження стану на стороні клієнта

Щоби користувач міг закрити вкладку браузера, вимкнути комп'ютер і наступного дня продовжити завантаження 10-гігабайтного файлу, клієнтська бібліотека (наприклад, `tus-js-client`) зберігає стан сесії у локальному сховищі браузера (IndexedDB або LocalStorage).

Алгоритм відновлення працює за такою схемою:

1. **Генерація відбитка файлу (Fingerprint).**
   Браузер не має доступу до повного шляху файлу на диску через пісочницю безпеки, тому відбиток обчислюється як композитний ключ:
   ```
   fingerprint = ["tus", file.name, file.type, file.size, file.lastModified].join("::")
   ```
2. **Пошук активної сесії.**
   Перед надсиланням `POST`-запиту клієнт перевіряє наявність ключа `fingerprint` у сховищі IndexedDB.
3. **Відновлення за URL.**
   Якщо запис знайдено, клієнт пропускає фазу `POST` і одразу надсилає `HEAD`-запит за збереженою URL-адресою ресурсу.
4. **Звірка прогресу.**
   Сервер повертає актуальний `Upload-Offset` (наприклад, 4 ГБ). Клієнт створює двійковий зріз файлу `file.slice(4294967296)` і продовжує передачу чанків через `PATCH`.
5. **Очищення сховища.**
   Після отримання статусу завершення завантаження запис із IndexedDB видаляється.

## Інтеграція з бекендом через вебхуки та хуки подій

TUS-сервер зазвичай виступає спеціалізованим інфраструктурним шлюзом і не містить бізнес-логіки додатка. Для взаємодії з основним бекендом сервер надає систему хуків (англ. *event hooks / webhooks*):

* **`pre-create`:** Викликається перед створенням файлу. Бекенд перевіряє авторизацію користувача, квоти простору та валідність метаданих. Якщо бекенд повертає статус `403`, TUS-сервер відхиляє створення файлу.
* **`post-receive`:** Викликається після успішного збереження кожного чанка. Дозволяє бекенду транслювати прогрес завантаження через WebSocket або Server-Sent Events (SSE) іншим користувачам.
* **`post-finish`:** Викликається в момент, коли останній байт файлу зафіксовано на диску чи в S3. Бекенд отримує сповіщення із фінальним ідентифікатором файлу та ставить задачу в чергу фонової обробки.
* **`post-terminate`:** Викликається у разі явного скасування завантаження клієнтом або очищення за таймаутом `Upload-Expires`.

## Автентифікація під час багатогодинних завантажень

Окремою проблемою довготривалих завантажень (наприклад, файлу розміром 50 ГБ через нестабільний мобільний зв'язок) є протухання короткоживучих токенів доступу (JWT).

Якщо клієнт використовує стандартний заголовок `Authorization: Bearer <token>` із часом життя 15 хвилин, через 15 хвилин черговий виклик `PATCH` буде відхилено шлюзом API зі статусом `401 Unauthorized`.

Для вирішення цієї проблеми застосовують дві взаємодоповнюючі стратегії:

1. **Токен сесії завантаження (Upload Ticket Token).** Під час фази `POST` (створення ресурсу) бекенд генерує спеціалізований криптографічно підписаний токен для цього конкретного `upload_id`, строк дії якого дорівнює максимальній тривалості сесії (наприклад, 48 годин). Токен дозволяє виконувати винятково операції `PATCH` і `HEAD` над цим файлом.
2. **Перехоплення 401 на клієнті та автооновлення.** Клієнтська бібліотека перехоплює код `401`, оновлює основний OAuth-токен за допомогою `refresh_token`, виконує `HEAD`-запит із новим заголовком `Authorization` та безперервно продовжує завантаження чанка.

## Порівняльний аналіз протоколів відновлюваного завантаження

| Критерій | Відкритий протокол TUS 1.0.0 | AWS S3 Multipart Upload | GCS Resumable Upload |
| :--- | :--- | :--- | :--- |
| **Відкритість стандарту** | Відкритий RFC-сумісний стандарт (Tus.io) | Пропрієтарний API Amazon Web Services | Пропрієтарний API Google Cloud Platform |
| **Методи HTTP** | `POST`, `PATCH`, `HEAD`, `DELETE`, `OPTIONS` | `POST` (Create/Complete), `PUT` (Part), `DELETE` | `POST` (Initiate), `PUT` (Upload range) |
| **Мінімальний розмір чанка** | Довільний (від 1 байта) | Суворо 5 МБ (крім останнього чанка) | Рекомендовано кратний 256 КБ |
| **Паралельне завантаження** | Підтримується (розширення Concatenation) | Нативна паралельність номерів PartNumber (1..10000) | Послідовний потік за замовчуванням |
| **Незалежність від вендора** | Повна (працює на Disk, S3, GCS, MinIO, Ceph) | Прив'язано до S3 API | Прив'язано до Google Cloud Storage |
| **Підтримка контрольних сум** | Окремо для кожного чанка (`Upload-Checksum`) | MD5/SHA256 для кожного Part (`Content-MD5`) | `Content-MD5` або CRC32C |

## Матриця HTTP-кодів станів протоколу TUS

| Код стану | Назва за стандартом | Умови виникнення в TUS |
| :--- | :--- | :--- |
| `200 OK` | Успішний запит | Повертається на виклик `HEAD` із заголовками стану файлу. |
| `201 Created` | Ресурс створено | Повертається на виклик `POST` (Creation extension) з URL у заголовку `Location`. |
| `204 No Content` | Дія виконана | Повертається на виклик `PATCH`, `DELETE` або `OPTIONS`. |
| `400 Bad Request` | Некоректний запит | Помилка парсингу заголовків `Upload-Metadata` або `Upload-Offset`. |
| `403 Forbidden` | Заборонено | Недостатньо прав на модифікацію або видалення ресурсу завантаження. |
| `404 Not Found` | Не знайдено | URL ресурсу завантаження не існує або термін його життя закінчився. |
| `409 Conflict` | Конфлікт зсуву | Переданий клієнтом `Upload-Offset` не збігається з поточним зсувом на сервері. |
| `410 Gone` | Ресурс видалено | Завантаження було примусово видалено або очищено збирачем сміття. |
| `412 Precondition Failed` | Помилка передумови | Заголовок `Tus-Resumable` відсутній або вказує несумісну версію. |
| `413 Payload Too Large` | Завеликий розмір | Розмір файлу перевищує ліміт `Tus-Max-Size` сервера. |
| `415 Unsupported Media` | Непідтримуваний тип | Заголовок `Content-Type` у методі `PATCH` не дорівнює `application/offset+octet-stream`. |
| `460 Checksum Mismatch` | Невідповідність хешу | Обчислена сервером контрольна сума не збіглася з `Upload-Checksum`. |

## Інваріанти узгодженості та блокування гонок

Для забезпечення повної надійності TUS-сервер реалізує такі обов'язкові інваріанти:

1. **Атомарність оновлення зсуву (Offset Mutex).**
   Сервер зобов'язаний блокувати ресурс завантаження (через Redis-lock або рядкове блокування в базі даних) на час виконання операції `PATCH`. Якщо два клієнтські процеси одночасно спробують виконати `PATCH` над одним файлом, лише один отримає блокування, а другий отримає `409 Conflict`.

2. **Ідемпотентність повторних опитувань HEAD.**
   Метод `HEAD` є безпечним і не змінює стан сервера. Клієнт може виконувати `HEAD` необмежену кількість разів для перевірки прогресу.

3. **Стійкість до часткових записів.**
   Якщо TCP-з'єднання обривається посеред виконання `PATCH` (наприклад, із 50 МБ чанка сервер встиг записати на диск лише 32 МБ), сервер оновлює `Upload-Offset` винятково на фактично збережену кількість байтів (32 МБ). Наступний `HEAD`-запит від клієнта поверне зсув `32 МБ`, і клієнт надішле наступний `PATCH`, починаючи саме з 32-го мегабайта.
