# 📜 Історія HTTP Range: від діапазонів RFC 2068 до протистояння з прискорювачами завантажень

У 1995–1997 роках, коли всесвітнє павутиння стрімко еволюціонувало від академічної мережі обміну гіпертекстовими документами до масового комерційного простору, архітектура HTTP стикнулася з фундаментальним фізичним обмеженням. Більшість користувачів підключалися до Інтернету через аналогові телефонні модеми зі швидкістю 14.4, 28.8 або 33.6 кбіт/с. Передача звичайного виконуваного файлу інсталятора або відеоролика розміром 20–50 МБ тривала від трьох до шести годин.

Будь-який випадковий сплеск шумів у телефонній лінії, вхідний дзвінок на паралельний апарат або секундне зависання маршрутизатора провайдера миттєво обривали TCP-з'єднання. Оскільки протокол HTTP/1.0 (RFC 1945) знав лише єдиний спосіб отримання даних — монолітний запит `GET /file.bin` з передачею байтів від нульового до кінцевого, — після обриву на 99% завантаження користувач втрачав усе. Години очікування та гроші за погодинний доступ згорали марно: передачу доводилося розпочинати з першого байта.

Ця криза спонукала робочу групу IETF HTTP (англ. *HTTP Working Group*) розпочати проєктування механізму фрагментарного читання ресурсів, який згодом назавжди змінив архітектуру мережевих клієнтів, мультимедійних плеєрів та вебсерверів.

## Поява RFC 2068 та перша стандартизація байтових діапазонів

У січні 1997 року IETF опублікувала чорновий стандарт HTTP/1.1 у документі RFC 2068, провідними авторами якого виступили Рой Філдінг (Roy Fielding), Джим Геттіс (Jim Gettys), Джеффрі Могул (Jeffrey Mogul), Генрік Фрістік Нільсен (Henrik Frystyk Nielsen) та Тім Бернерс-Лі (Tim Berners-Lee). Одним із ключових нововведень специфікації став розділ про запити діапазонів (англ. *Byte Range Requests*).

Концепція базувалася на чотирьох фундаментальних елементах:

1. **Оголошення можливостей (`Accept-Ranges`).** Сервер отримав можливість явно повідомляти клієнтам, що він підтримує позиціювання за байтами, повертаючи заголовок `Accept-Ranges: bytes`. Якщо ресурс генерувався динамічно без відомої наперед довжини (наприклад, потік даних зі скрипту CGI), сервер міг вказати `Accept-Ranges: none`.
2. **Селектор зміщення (`Range`).** Клієнт отримав стандартизований заголовок `Range: bytes=start-end`, де міг запросити будь-який замкнений, напіввідкритий або суфіксний діапазон.
3. **Статус часткового вмісту (`206 Partial Content`).** Замість класичного статусу `200 OK`, який гарантував передачу повного представлення, було введено код 206, що захищав кеші від помилкового збереження фрагмента замість цілого файлу.
4. **Заголовок охоплення (`Content-Range`).** Відповідь сервера обов'язково супроводжувалася метаданими про точні межі переданого блоку та загальний розмір сутності на момент відповіді (наприклад, `Content-Range: bytes 500-999/5000`).

У червні 1999 року стандарт було доопрацьовано й перезатверджено у фундаментальному документі RFC 2616, де детально описали семантику обробки кількох діапазонів у єдиному запиті через MIME-тип `multipart/byteranges` та ввели статус помилки `416 Requested Range Not Satisfiable`.

## Епоха прискорювачів завантажень: війна за смугу пропускання

Поява стандарту RFC 2068 спричинила вибухову революцію в індустрії клієнтського програмного забезпечення. Наприкінці 1990-х років з'явився абсолютно новий клас утиліт — менеджери та прискорювачі завантажень (англ. *Download Accelerators*). Серед них легендарну популярність здобули програми GetRight (1997, автор Майкл Берфорд), ReGet (1998, Владислав Фірсов), FlashGet (спочатку JetCar, 1999, Хоу Яньчжен) та Download Accelerator Plus (DAP).

Інженери цих програм виявили, що заголовки `Range` можна використовувати не лише для аварійного відновлення після розриву з'єднання, а й для радикального збільшення сумарної швидкості скачування.

```
       ┌─── TCP З'єднання 1: Range: bytes=0-2499999 ───────► Потік 1 (30 КБ/с) ──┐
       │                                                                         │
Клієнт ├─── TCP З'єднання 2: Range: bytes=2500000-4999999 ───► Потік 2 (30 КБ/с) ──┼──► Локальний
       │                                                                         │    файл (10 МБ)
       ├─── TCP З'єднання 3: Range: bytes=5000000-7499999 ───► Потік 3 (30 КБ/с) ──┤
       │                                                                         │
       └─── TCP З'єднання 4: Range: bytes=7500000-9999999 ───► Потік 4 (30 КБ/с) ──┘
```

Принцип роботи базувався на обході обмежень протоколу TCP та політик провайдерів:

* **Подолання алгоритму TCP Slow Start.** Протокол TCP поступово збільшує розмір вікна перевантаження (англ. *congestion window*). Одне TCP-з'єднання на трансатлантичній лінії з високим RTT вимагало десятків секунд для виходу на пікову пропускну здатність. Запуск 8–16 паралельних з'єднань дозволяв агресивно утилізувати весь доступний канал миттєво.
* **Обхід обмежень швидкості на з'єднання.** Багато вебсерверів та хостингів того часу встановлювали ліміти швидкості (наприклад, 50 КБ/с на один сокет). Відкриваючи 10 паралельних запитів `Range`, клієнт отримував 500 КБ/с.
* **Подолання втрат окремих пакетів.** Якщо в одному TCP-потоці губився пакет, протокол знижував вікно передачі вдвічі (`AIMD`). Інші паралельні потоки продовжували передавати дані на максимальній швидкості, згладжуючи просідання.

Програми-прискорювачі демонстрували ефектний графік: файл у пам'яті розбивався на кольорові сегменти, які заповнювалися паралельно. Для користувачів це виглядало як магія: швидкість скачування зростала в 3–5 разів. Проте для адміністраторів серверів та інтернет-провайдерів настав кошмар.

Тисячі користувачів з увімкненими менеджерами завантажень створювали лавину одночасних TCP-сесій. Сервери Apache 1.3, які використовували модель створення окремого процесу операційної системи на кожне TCP-з'єднання (`prefork MPM`), миттєво вичерпували пул процесів (`MaxClients`) і завершували роботу через виснаження оперативної пам'яті. Хостинг-провайдери почали масово вимикати `Accept-Ranges: none` або блокувати клієнтів за специфічними рядками `User-Agent`.

## Загроза цілісності та винайдення If-Range

Масове використання часткових запитів виявило іншу серйозну архітектурну діру. Що відбувалося, коли клієнт завантажував перші 5 МБ файлу розміром 10 МБ, після чого адміністратор оновлював файл на сервері (наприклад, випускав патч версії 2), і клієнт надсилав запит `Range: bytes=5000000-`?

Сервер надсилав другу половину *нового* файлу. Клієнт склеював перші 5 МБ старої версії з 5 МБ нової версії. Отриманий двійковий файл виявлявся незворотно пошкодженим (англ. *silent data corruption*), хоча HTTP-транспорт відпрацьовував без жодної формальної помилки.

Для розв'язання цієї проблеми в RFC 2616 було введено умовний заголовок `If-Range`. Він дозволив об'єднати перевірку валідатора свіжості (сильного ETag або дати `Last-Modified`) та запит діапазону в єдину атомарну транзакцію:

* Якщо ресурс не змінювався, сервер повертає `206 Partial Content` з потрібним фрагментом.
* Якщо ресурс оновився, сервер ігнорує діапазон і одразу повертає `200 OK` з усім тілом нового файлу, не вимагаючи від клієнта додаткових кругових затримок (RTT).

## Катастрофа Apache Killer (CVE-2011-3192)

Найбільша криза в історії механізму Range вибухнула в серпні 2011 року, коли дослідник безпеки під псевдонімом Kingcope опублікував експлойт `killapache.pl`, зареєстрований як вразливість CVE-2011-3192.

Вразливість вражала всі версії вебсервера Apache HTTP Server серій 1.3, 2.0 та 2.2 — на той момент Apache обслуговував понад 65% усіх активних сайтів в Інтернеті.

Суть атаки полягала у створенні штучного комбінаторного перевантаження через заголовок `Range`. Зловмисник формував один простий HTTP-запит, який містив сотні або тисячі перекритих діапазонів для великого статичного файлу (наприклад, фонового зображення або PDF):

```http
HEAD /test.png HTTP/1.1
Host: target.example.com
Range: bytes=0-,5-1,5-2,5-3,5-4,5-5,5-6,5-7,5-8,5-9,... [ще 1300 діапазонів]
Accept-Encoding: gzip
Connection: close
```

Архітектура обробки Range в Apache того часу містила фатальну ваду реалізації:

1. Для кожного зазначеного діапазону сервер виділяв окрему структуру пам'яті (англ. *bucket brigade*) та формував окремий MIME-заголовок частини `multipart/byteranges`.
2. За наявності тисячі діапазонів `0-` сервер тисячу разів клонував покажчики на вміст файлу і збирав гігантську структуру в оперативній пам'яті процесу.
3. Якщо було увімкнено стиснення `mod_deflate`, сервер намагався стиснути кожен згенерований MIME-фрагмент окремо, що навантажувало процесор на 100%.
4. Усього кілька десятків таких запитів, надісланих зі звичайного домашнього комп'ютера через низькошвидкісний канал, повністю вичерпували гігабайти оперативної пам'яті сервера, спричиняли масовий дисковий свопінг (англ. *thrashing*) і примушували ядро операційної системи аварійно зупиняти вебсервер через вичерпання ресурсів.

Розробники Apache випустили екстрені оновлення 2.2.20 та 2.2.21, у яких впровадили алгоритм примусової коалесценції (злиття та дедуплікації) діапазонів, обмежили максимальну кількість частин у запиті (директива `MaxRanges`, за замовчуванням обмежена 200, а пізніше 5–10 діапазонами) та запровадили повернення звичайного `200 OK` замість 206, якщо сумарні накладні витрати заголовків MIME перевищували розмір самого запитаного вмісту.

Ця подія змусила авторів інших вебсерверів (зокрема Ігоря Сисоєва в NGINX) переглянути власну політику. NGINX обрав ще радикальніший та безпечніший шлях: повністю відмовитися від підтримки `multipart/byteranges`, обробляючи виключно одиночні діапазони байтів.

## Сучасна ера: RFC 7233, RFC 9110 та відеострімінг

У червні 2014 року робоча група IETF розбила монолітний стандарт RFC 2616 на серію модульних документів. Механізм діапазонів отримав окрему присвячену специфікацію — RFC 7233 (*Hypertext Transfer Protocol (HTTP/1.1): Range Requests*).

У 2022 році стандарт було оновлено та уніфіковано в RFC 9110 (*HTTP Semantics*), де закріплено сучасні правила:

* Жорстка заборона використання слабких валідаторів (`W/"..."`) у заголовку `If-Range`, оскільки слабкий ETag гарантує лише семантичну еквівалентність сутності, але не гарантує побайтну ідентичність зміщень.
* Чіткі алгоритми нормалізації та об'єднання діапазонів, що запобігають атакам на відмову в обслуговуванні.
* Офіційне закріплення права сервера ігнорувати заголовок `Range` і повертати повний ресурс зі статусом `200 OK`, якщо розбір діапазонів створює надмірне обчислювальне навантаження.

Сьогодні HTTP Range Requests є невидимим, але життєво необхідним фундаментом сучасної цифрової інфраструктури:

* **Прогресивне завантаження медіа.** HTML5-елементи `<video>` та `<audio>` у браузерах використовують Range для миттєвого перемотування (англ. *seeking*) відеопотоку без скачування гігабайтів попередніх кадрів.
* **Читання складних форматів.** Переглядачі PDF (зокрема Mozilla PDF.js) завантажують лише сторінку 50 із 500-сторінкового каталогу завдяки лінеаризованій структурі PDF (англ. *Byte-Serving*).
* **Хмарні сховища та аналітика.** Інструменти обробки великих даних (Apache Spark, Trino, ClickHouse) вичитують метадані та окремі стовпці файлів Apache Parquet та ORC з Amazon S3 за допомогою цільових запитів `Range: bytes=X-Y`, скорочуючи мережевий трафік на порядки.

Історія HTTP Range — це показовий приклад того, як простий заголовок, створений для компенсації нестабільних телефонних ліній 1990-х років, трансформувався у високоефективний архітектурний механізм прямого доступу до довільних двійкових структур у глобальній мережі.
