# 📋 Семантика HTTP: методи, статуси та контракти заголовків

Специфікація RFC 9110 («HTTP Semantics», червень 2022 року) визначає універсальну семантичну модель протоколу HTTP, яка залишається незмінною для будь-якої версії транспорту — HTTP/1.1 (текстовий потік), HTTP/2 (бінарне мультиплексування) чи HTTP/3 (дейтаграми QUIC). Ця довідка містить нормативний опис методів запиту, класифікацію статусів відповідей, контракти заголовків, алгоритм пріоритету умовних запитів та правила взаємодії підсистем (CORS, Range-запити, Cookie, WebSocket Upgrade, Problem Details, Alt-Svc, Trailers), необхідні для проектування надійних розподілених вебсистем і серверних API.

## 1. Методи HTTP та їхні інваріанти

Метод запиту вказує на цільову дію, яку клієнт очікує виконати над ідентифікованим ресурсом. Поведінка методів регламентується трьома ключовими властивостями:
- **Безпечність (Safe):** метод призначений виключно для отримання представлення ресурсу й не повинен викликати значущих змін стану на стороні сервера (наприклад, видалення записів або списання коштів).
- **Ідемпотентність (Idempotent):** багаторазове виконання однакових запитів поспіль дає точно такий самий кінцевий стан ресурсів на сервері, як і один запит: `f(f(x)) = f(x)`.
- **Кешованість (Cacheable):** відповідь на запит цим методом може бути збережена проміжними вузлами для повторного використання згідно з правилами RFC 9111.

| Метод | Специфікація | Безпечний | Ідемпотентний | Кешований за замовчуванням | Тіло запиту | Тіло відповіді | Основне призначення |
| :--- | :--- | :---: | :---: | :---: | :--- | :--- | :--- |
| `GET` | RFC 9110 §9.3.1 | **Так** | **Так** | **Так** | Не використовується | Передається | Отримання представлення цільового ресурсу. |
| `HEAD` | RFC 9110 §9.3.2 | **Так** | **Так** | **Так** | Не використовується | **Заборонено** | Отримання заголовків відповіді без передачі тіла. |
| `POST` | RFC 9110 §9.3.3 | **Ні** | **Ні** | Умовно (з явним `Cache-Control`) | Обов'язкове / типове | Дозволено | Передача даних для цільової обробки або створення ресурсу. |
| `PUT` | RFC 9110 §9.3.4 | **Ні** | **Так** | **Ні** | Обов'язкове (повне представлення) | Залежить від коду (200/201/204) | Повне створення або повна заміна стану цільового ресурсу. |
| `DELETE` | RFC 9110 §9.3.5 | **Ні** | **Так** | **Ні** | Не рекомендується | Дозволено | Знищення зв'язку між URI та ресурсом на сервері. |
| `CONNECT` | RFC 9110 §9.3.6 | **Ні** | **Ні** | **Ні** | Заборонено | Спеціальне (тунель) | Встановлення наскрізного TCP-тунелю (проксі HTTPS). |
| `OPTIONS` | RFC 9110 §9.3.7 | **Так** | **Так** | **Ні** | Рідко | Дозволено | Запит підтримуваних серверних методів і параметрів (CORS preflight). |
| `TRACE` | RFC 9110 §9.3.8 | **Так** | **Так** | **Ні** | Заборонено | Тіло = відлуння запиту | Діагностика маршруту (повернення отриманого запиту клієнту). |
| `PATCH` | RFC 5789 §2 | **Ні** | **Ні** (у заг. вип.) | **Ні** | Обов'язкове (набір інструкцій змін) | Дозволено | Застосування часткових змін до стану існуючого ресурсу. |

### Нормативні інваріанти методів:
1. **`PUT` проти `PATCH`:** `PUT` вимагає передачі повного нового стану документа. Якщо в ресурсі є 10 полів, а клієнт надіслав `PUT` з 3 полями, решта 7 мають бути скинуті у значення за замовчуванням або видалені. Для часткового оновлення полів використовується `PATCH` зі спеціалізованими форматами (наприклад, JSON Patch RFC 6902 або JSON Merge Patch RFC 7396).
2. **Ідемпотентність `DELETE`:** повторний виклик `DELETE /items/42` може повернути статус `404 Not Found` (бо об'єкт уже знищено), але кінцевий стан бази даних залишається ідентичним до стану після першого виклику. Метод лишається ідемпотентним, оскільки властивість стосується стану сервера, а не коду статусу відповіді.
3. **Метод `HEAD`:** сервер зобов'язаний повернути точно такі самі заголовки (`Content-Length`, `ETag`, `Last-Modified`, `Content-Type`), які він згенерував би для аналогічного запиту `GET`, але без відправлення байтів тіла повідомлення. Це дозволяє клієнтам перевіряти наявність оновлень і розмір файлу без витрат мережевого трафіку.

## 2. Коди стану HTTP (Status Codes)

Код стану складається з трьох десяткових цифр. Перша цифра визначає загальний клас відповіді:

```
1xx — Інформаційні (Informational): запит прийнято, обробка триває.
2xx — Успішні (Successful): запит успішно отримано, зрозуміло й виконано.
3xx — Перенаправлення (Redirection): для виконання дії потрібні додаткові кроки.
4xx — Помилки клієнта (Client Error): запит містить синтаксичні помилки або не може бути виконаний.
5xx — Помилки сервера (Server Error): сервер виявив помилку або не зміг обробити коректний запит.
```

### 1xx: Інформаційні коди
- **`100 Continue`:** повідомляє клієнту, що початкові заголовки запиту прийнято, і він може надсилати тіло (використовується за наявності заголовка `Expect: 100-continue`). Клієнт надсилає лише метадані з розміром, сервер перевіряє авторизацію та права, відповідає `100 Continue`, і лише після цього клієнт прокачує важкий бінарний файл.
- **`101 Switching Protocols`:** сервер погоджується змінити протокол згідно із заголовком `Upgrade` (наприклад, перехід на WebSocket поверх існуючого TCP-з'єднання).
- **`103 Early Hints`:** попередні заголовки (наприклад, `Link: </style.css>; rel=preload`), що надсилаються браузеру для раннього прогріву ресурсів до формування основного тіла відповіді.

### 2xx: Успішна обробка
- **`200 OK`:** стандартна успішна відповідь із корисним навантаженням у тілі.
- **`201 Created`:** ресурс успішно створено. Відповідь обов'язково повинна містити заголовок `Location` з адресою новоствореного ресурсу.
- **`202 Accepted`:** запит прийнято на асинхронну обробку, але вона ще не завершена (статус фонового завдання).
- **`204 No Content`:** дія виконана успішно, відповідь свідомо не містить тіла (застосовується після `DELETE` або оновлення через `PUT`/`PATCH`).
- **`206 Partial Content`:** сервер повертає лише запитаний діапазон байтів ресурсу (відповідь на заголовок `Range`, наприклад, при докачуванні відео чи аудіотрансляції).

### 3xx: Перенаправлення та збереження методів

| Код стану | Назва | Мета перенаправлення | Збереження методу та тіла (RFC 9110) |
| :--- | :--- | :--- | :--- |
| **`301`** | Moved Permanently | Постійне переміщення ресурсу на новий URI. | Клієнти історично **змінюють `POST` на `GET`**. |
| **`302`** | Found | Тимчасове переміщення ресурсу. | Клієнти історично **змінюють `POST` на `GET`**. |
| **`303`** | See Other | Перенаправлення після обробки (Post/Redirect/Get). | **Обов'язкова заміна методу на `GET`** без тіла. |
| **`304`** | Not Modified | Валідація кешу: копія в клієнта чинна. | Тіло відповіді **суворо заборонене**. |
| **`307`** | Temporary Redirect | Тимчасове перенаправлення за новим URI. | **Суворо зберігає оригінальний метод і тіло!** |
| **`308`** | Permanent Redirect | Постійне перенаправлення за новим URI. | **Суворо зберігає оригінальний метод і тіло!** |

### 4xx: Помилки клієнта
- **`400 Bad Request`:** синтаксична помилка в запиті (некоректний JSON, битий стартовий рядок, розсинхронізація кадрування).
- **`401 Unauthorized`:** відсутня або недійсна автентифікація. Відповідь обов'язково повинна містити заголовок `WWW-Authenticate` із зазначенням схеми (наприклад, `Bearer realm="api"` або `Basic`).
- **`403 Forbidden`:** клієнт автентифікований, але не має прав доступу до цього ресурсу (авторизація відхилена).
- **`404 Not Found`:** цільовий ресурс за вказаним URI не знайдено.
- **`405 Method Not Allowed`:** метод не підтримується для цього ресурсу. Сервер зобов'язаний повернути заголовок `Allow: GET, POST, OPTIONS` зі списком доступних методів.
- **`406 Not Acceptable`:** сервер не може згенерувати представлення, що задовольняє заголовки `Accept` клієнта.
- **`408 Request Timeout`:** сервер перервав очікування завершення надсилання запиту клієнтом.
- **`409 Conflict`:** запит суперечить поточному стану сервера (наприклад, порушення унікальності ключа чи версії документа при оптимістичному блокуванні).
- **`410 Gone`:** ресурс існував раніше, але був назавжди видалений і не відновлюватиметься.
- **`411 Length Required`:** сервер відмовляється приймати запит без явного заголовка `Content-Length`.
- **`412 Precondition Failed`:** не виконано умову валідації (наприклад, `If-Match` не збігся з поточним `ETag`).
- **`413 Content Too Large`:** розмір тіла запиту перевищує ліміти, встановлені сервером.
- **`415 Unsupported Media Type`:** формат тіла запиту (`Content-Type`) не підтримується сервером.
- **`422 Unprocessable Content`:** синтаксис запиту коректний, але семантичні бізнес-правила порушено (наприклад, від'ємна сума переказу).
- **`429 Too Many Requests`:** перевищено ліміт запитів (Rate Limiting). Рекомендується повертати заголовок `Retry-After: 30` (час у секундах до наступної спроби).

### 5xx: Помилки сервера
- **`500 Internal Server Error`:** непередбачений збій або аварія в коді сервера.
- **`501 Not Implemented`:** сервер не має функціональної можливості для виконання запитаного методу.
- **`502 Bad Gateway`:** проміжний вузол (шлюз, зворотний проксі Nginx/Envoy) отримав некоректну відповідь від висхідного бекенда.
- **`503 Service Unavailable`:** сервер тимчасово не здатний обробити запит через перевантаження або планове технічне обслуговування.
- **`504 Gateway Timeout`:** проміжний проксі не дочекався своєчасної відповіді від висхідного сервера за встановлений таймаут.
- **`505 HTTP Version Not Supported`:** версія протоколу HTTP з запиту не підтримується сервером.

## 3. Таксономія та контракти стандартних заголовків

Заголовки HTTP є парами «ключ-значення» без урахування регістру символів у назві (`Case-Insensitive`). За класифікацією RFC 9110 вони поділяються за функціональним призначенням і зоною дії.

### Наскрізні (End-to-End) проти Повузлових (Hop-by-Hop)
- **Hop-by-Hop заголовки:** діють виключно на поточному транспортному сегменті між двома сусідніми вузлами й **не повинні** пересилатися далі проксі-серверами (`Connection`, `Keep-Alive`, `Transfer-Encoding`, `TE`, `Upgrade`, `Proxy-Authorization`).
- **End-to-End заголовки:** призначені для кінцевого одержувача й мають передаватися через усі проміжні вузли без змін (крім авторизованих модифікацій проксі).

### Основні категорії заголовків:

#### 1. Метадані представлення (Representation Metadata)
- `Content-Type`: MIME-тип даних і кодування (наприклад, `application/json; charset=utf-8`).
- `Content-Length`: розмір тіла в десяткових байтах.
- `Content-Encoding`: алгоритм стиснення корисного навантаження (`gzip`, `br`, `deflate`).
- `Content-Language`: природна мова вмісту (`uk-UA`, `en-US`).

#### 2. Узгодження вмісту (Content Negotiation)
- `Accept`: пріоритетний перелік прийнятних форматів (наприклад, `application/json, text/html;q=0.9`).
- `Accept-Encoding`: підтримувані алгоритми декомпресії (`gzip, deflate, br;q=1.0`).
- `Accept-Language`: мовні вподобання клієнта з коефіцієнтами ваги `q`.

#### 3. Умовні запити та кешування
- `Cache-Control`: прямі директиви кешування (`no-store`, `no-cache`, `public`, `private`, `max-age=300`, `must-revalidate`, `immutable`).
- `ETag`: унікальний ідентифікатор версії сутності (наприклад, `W/"686897696a7c7"`).
- `If-None-Match`: перевірка свіжості за ETag; якщо збігається, повертається `304 Not Modified`.
- `If-Match`: забезпечення оптимістичного блокування перед мутацією (`PUT`/`DELETE`).
- `Last-Modified`: дата та час останньої зміни ресурсу у форматі GMT.
- `If-Modified-Since`: умовний запит за датою.
- `Vary`: перелік заголовків запиту, від яких залежить вигляд відповіді (наприклад, `Vary: Accept-Encoding, User-Agent`).

#### 4. Безпека та контроль доступу
- `Authorization`: облікові дані клієнта (наприклад, `Bearer eyJhbGciOi...`).
- `WWW-Authenticate`: вимога автентифікації від сервера.
- `Origin`: джерело клієнтського запиту (`схема://домен:порт`) для перевірки CORS.
- `Access-Control-Allow-Origin`: дозволені джерела виконання скриптів (`*` або конкретний origin).
- `Strict-Transport-Security`: обов'язкове використання HTTPS (`max-age=31536000; includeSubDomains; preload`).
- `Content-Security-Policy`: обмеження джерел завантаження скриптів, стилів і медіа.

## 4. Алгоритм оцінки умовних запитів (RFC 9110 §13.2.2)

Коли клієнт надсилає запит із кількома умовними заголовками, сервер зобов'язаний обчислювати їх у строго визначеному порядку, щоб запобігти стану гонитви (Race Condition) та некоректному перезапису даних:

```
Крок 1: Чи присутній заголовок `If-Match`?
        ├── ТАК: якщо жоден ETag не збігається з поточним ETag ресурсу
        │        (або ресурс не існує) ──► ПЕРЕРВАТИ: повернути `412 Precondition Failed`.
        │        Якщо збігається ──► перейти до Кроку 3.
        └── НІ:  перейти до Кроку 2.

Крок 2: Чи присутній заголовок `If-Unmodified-Since` (і метод не GET/HEAD)?
        ├── ТАК: якщо дата в заголовку раніша за дату Last-Modified ресурсу
        │        ──► ПЕРЕРВАТИ: повернути `412 Precondition Failed`.
        └── НІ:  перейти до Кроку 3.

Крок 3: Чи присутній заголовок `If-None-Match`?
        ├── ТАК: якщо будь-який ETag збігається з поточним ETag ресурсу
        │        ├── для GET / HEAD ──► повернути `304 Not Modified`.
        │        └── для інших методів ──► повернути `412 Precondition Failed`.
        └── НІ:  перейти до Кроку 4.

Крок 4: Чи присутній заголовок `If-Modified-Since` (для методів GET / HEAD)?
        ├── ТАК: якщо дата Last-Modified ресурсу не пізніша за передану дату
        │        ──► повернути `304 Not Modified`.
        └── НІ:  перейти до Кроку 5.

Крок 5: Чи присутній заголовок `If-Range` (разом із заголовком Range)?
        ├── ТАК: якщо ETag або дата в If-Range не збігається з ресурсом
        │        ──► ігнорувати Range, повернути повний ресурс зі статусом `200 OK`.
        └── НІ:  виконати запит, задовольнити діапазон зі статусом `206 Partial Content`.
```

Цей алгоритм гарантує, що сильні валідатори сутності (`ETag`) мають пріоритет над неточними валідаторами часу (`Last-Modified`), а мутуючі операції захищені від випадкового застосування до застарілої версії ресурсу.

## 5. Механізм спільного використання ресурсів (CORS)

Cross-Origin Resource Sharing (CORS) — це механізм безпеки браузера, що контролює, чи дозволено скрипту, завантаженому з домену `https://app.example.com`, робити запити до API на домені `https://api.service.com`.

### Прості запити (Simple Requests)
Запит вважається простим, якщо він використовує метод `GET`, `HEAD` або `POST`, містить лише безпечні заголовки (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`) і `Content-Type` обмежено типами `application/x-www-form-urlencoded`, `multipart/form-data` або `text/plain`.

1. Браузер автоматично додає заголовок `Origin: https://app.example.com`.
2. Сервер перевіряє `Origin` і повертає заголовок `Access-Control-Allow-Origin: https://app.example.com` (або `*`).
3. Якщо заголовок відсутній або не збігається, браузер блокує доступ до відповіді з коду JavaScript.

### Попередні перевірочні запити (Preflight Requests)
Якщо запит містить нестандартні заголовки (наприклад, `Authorization`, `X-Custom-Header`) або використовує метод `PUT`, `DELETE` чи `PATCH`, браузер спочатку надсилає запит `OPTIONS`:

```
OPTIONS /api/v1/orders/12 HTTP/1.1
Host: api.service.com
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: Authorization, Content-Type
```

Сервер зобов'язаний підтвердити дозвіл відповідними заголовками:

```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 86400
Access-Control-Allow-Credentials: true
```

Директива `Access-Control-Max-Age: 86400` дозволяє браузеру кешувати результат перевірки на добу, уникаючи повторних запитів `OPTIONS` перед кожним наступним викликом API.

## 6. Часткові запити та докачування (Range Requests)

Механізм часткових запитів (RFC 9110 §14) дозволяє клієнту завантажувати файл окремими діапазонами байтів. Це критично для відеоплеєрів (перемотування відео), багатопотокових завантажувачів та відновлення обірваних завантажень.

1. **Опитування можливості:** Сервер сигналізує про підтримку діапазонів заголовком `Accept-Ranges: bytes` (якщо не підтримує — `Accept-Ranges: none`).
2. **Запит діапазону:** Клієнт передає заголовок `Range`:
   - `Range: bytes=0-1023` — перші 1024 байти.
   - `Range: bytes=2048-` — усі байти від 2048 до кінця файлу.
   - `Range: bytes=-500` — останні 500 байтів файлу.
3. **Відповідь сервера:**
   - Якщо діапазон валідний, сервер повертає статус `206 Partial Content`, заголовок `Content-Range: bytes 0-1023/146515` (де 146515 — повний розмір файлу) і лише запитані байти в тілі.
   - Якщо переданий діапазон виходить за межі розміру файлу, сервер повертає статус `416 Range Not Satisfiable` із заголовком `Content-Range: bytes */146515`.

## 7. Управління станом: Cookie та атрибути Set-Cookie (RFC 6265bis)

Заголовок `Set-Cookie` відправляється сервером для збереження фрагмента стану на боці клієнта. Безпека кукі-файлів регулюється набором обов'язкових атрибутів:

```
Set-Cookie: session_id=s%3A849201; Secure; HttpOnly; SameSite=Strict; Path=/; Domain=example.com; Max-Age=3600
```

- **`Secure`:** кукі передається браузером **виключно** через зашифровані канали HTTPS. Будь-яка спроба передати кукі через відкритий HTTP блокується браузером.
- **`HttpOnly`:** забороняє доступ до кукі з боку JavaScript (через `document.cookie`). Це фундаментальний захист сесії від крадіжки через міжсайтовий скриптинг (XSS).
- **`SameSite`:** захист від міжсайтової підробки запитів (CSRF):
  - `SameSite=Strict`: кукі не надсилається за будь-яких переходів із зовнішніх сайтів (навіть за звичайним посиланням).
  - `SameSite=Lax`: кукі надсилається при безпечній навігації верхнього рівня (перехід за `GET`-посиланням), але блокується у формах `POST` та AJAX-запитах зі сторонніх сайтів (поведінка за замовчуванням у сучасних браузерах).
  - `SameSite=None`: кукі надсилається у всіх міжсайтових контекстах (вимагає обов'язкової наявності прапорця `Secure`).
- **Префікси імен кукі:**
  - `__Secure-`: вимагає, щоб кукі встановлювалося виключно через HTTPS із прапорцем `Secure`.
  - `__Host-`: найсуворіший режим. Вимагає `Secure`, відсутності атрибута `Domain` (прив'язка суворо до поточного хоста без піддоменів) та `Path=/`.

## 8. Рукостискання перемикання протоколу (WebSocket Upgrade)

Специфікація RFC 6455 описує механізм переходу зі звичайного HTTP/1.1 на двонаправлений протокол WebSocket через єдиний TCP-сокет.

Клієнт надсилає запит на підвищення протоколу:

```
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

Сервер обчислює відповідь: бере випадковий рядок `Sec-WebSocket-Key`, конкатенує його зі стандартизованим магічним GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`, рахує хеш SHA-1 від отриманого рядка і кодує результат у Base64:

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

Після передачі цього рядка TCP-сокет переходить у бінарний режим WebSocket-фреймів.

## 9. Стандартизований формат помилок: Problem Details (RFC 7807 / RFC 9457)

Для уніфікації машинної обробки помилок у REST API консорціум IETF стандартизував спеціальний MIME-тип `application/problem+json`:

```json
{
  "type": "https://api.example.com/errors/insufficient-funds",
  "title": "Недостатньо коштів на рахунку",
  "status": 422,
  "detail": "Поточний баланс становить 120.00 UAH, запитана сума списання — 500.00 UAH.",
  "instance": "/transactions/tx_891048",
  "balance": 120.00,
  "required": 500.00
}
```

- `type` (URI): унікальний ідентифікатор класу проблеми (документація помилки).
- `title` (рядок): коротке людинозрозуміле резюме помилки.
- `status` (число): HTTP-код стану, що дублює статус стартового рядка.
- `detail` (рядок): детальне пояснення конкретного інциденту.
- `instance` (URI): ідентифікатор конкретного ресурсу чи транзакції, де виникла помилка.

## 10. Виявлення альтернативних протоколів: заголовок Alt-Svc (RFC 7838)

Заголовок `Alt-Svc` (Alternative Services) дозволяє серверу повідомити клієнту, що поточний ресурс доступний через швидший протокол або інший порт на тому самому чи іншому мережевому хості. Це основний механізм автоматичного перемикання з HTTP/1.1 або HTTP/2 на HTTP/3 через QUIC:

```
Alt-Svc: h3=":443"; ma=86400; persist=1
```

- `h3=":443"`: вказує, що протокол HTTP/3 доступний через UDP-порт 443.
- `ma=86400` (Max-Age): час у секундах (1 доба), протягом якого клієнт може надсилати наступні запити одразу через протокол HTTP/3 без попереднього опитування HTTP/1.1/2.
- `persist=1`: вказівка клієнту зберігати знання про альтернативну службу навіть у разі зміни мережевого інтерфейсу (наприклад, перемикання з Wi-Fi на LTE).

## 11. Трейлери повідомлення: передача метаданих після тіла (Trailers)

У стандартному потоці HTTP заголовки надсилаються суворо перед корисним навантаженням. Проте під час потокової генерації або шифрування великих файлів деякі метадані (наприклад, цифрова контрольна сума SHA-256 або підсумковий час обробки на сервері) стають відомими лише після того, як останній байт тіла згенеровано й передано в мережу.

HTTP/1.1 підтримує передачу заголовків-трейлерів у блоковому кодуванні `Transfer-Encoding: chunked`:

1. Клієнт попередньо сигналізує про готовність приймати трейлери: `TE: trailers`.
2. Сервер у початкових заголовках оголошує список майбутніх трейлерів: `Trailer: Content-Digest, Server-Timing`.
3. Після передачі термінального нульового чанка `0\r\n` сервер надсилає фінальні заголовки перед останнім `\r\n`:

```
0\r\n
Content-Digest: sha-256=:X48E9qOokqqrvdts8nOJRJN3OWDUoyWxBf7k8BiMHJA=:\r\n
Server-Timing: db;dur=53, total;dur=142\r\n
\r\n
```

Трейлери дозволяють передавати контрольні суми для перевірки цілісності потоку без накопичення гігабайтів даних у пам'яті сервера перед початком передачі.
