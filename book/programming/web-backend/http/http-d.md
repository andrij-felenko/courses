Уяви дослідницьку лабораторію кінця 1980-х років: на столах стоять десятки комп'ютерів із несумісними операційними системами — мейнфрейми VAX, станції Unix, комп'ютери NeXT, перші Mac та ПК під керуванням DOS. Щоб ознайомитися зі звітом колеги на сусідньому поверсі, дослідник мусив дізнатися мережеву IP-адресу його машини, відкрити термінал Telnet, ввести персональний логін і пароль, знайти шлях у чужому дереві каталогів, вивантажити файл через протокол FTP і запустити локальний текстовий процесор. Якщо в тексті траплялося посилання на результати іншого експерименту на третьому вузлі, увесь ланцюжок ручних дій повторювався спочатку. Зв'язок між документами був не автоматичним переходом, а текстовою інструкцією для людини.

Головна проблема полягала в тому, що мережеві протоколи того часу (FTP, Telnet, SMTP) будувалися навколо концепції постійного з'єднання зі збереженням стану (stateful session). Сервер виділяв окремий процес чи потік пам'яті під кожного активного користувача, вимагав обов'язкової автентифікації на рівні операційної системи та очікував команд. У такій моделі поява мільйонів читачів миттєво паралізувала б будь-який сервер: обчислювальні ресурси вичерпувалися не через передачу даних, а через утримання мільйонів відкритих дескрипторів сесій.

Щоб інформаційні масиви перетворилися на зв'язану Всесвітню павутину, потрібен був протокол із принципово іншою архітектурою: такий, що не вимагає стану на сервері, спирається на єдину глобальну систему адрес (URI), використовує стандартизований непровідний формат представлення (HTML) і працює за простою схемою «запит → відповідь». Цим протоколом став HTTP (англ. *HyperText Transfer Protocol* — протокол передачі гіпертексту).

## 1. Архітектурна модель: запит, відповідь і безстановість

Уся комунікація в HTTP побудована на суворій клієнт-серверній моделі. Розмову завжди ініціює **клієнт** (User Agent: веббраузер, мобільний застосунок або мікросервіс), надсилаючи **запит** (Request). **Сервер** (Origin Server або проміжний проксі) приймає запит, виконує необхідні обчислення та повертає **відповідь** (Response).

Фундаментальною властивістю протоколу є його **безстановість** (англ. *stateless*). Це означає, що протокол HTTP на власному рівні не зберігає жодної інформації про попередні взаємодії між тим самим клієнтом і сервером. Сервер обробляє кожен запит так, ніби він є найпершим і єдиним у всесвіті:

```
Запит #1:  Клієнт ──► [ GET /profile ] ──► Сервер (хто це? потрібні облікові дані)
                                       ◄── Сервер повертає 401 Unauthorized

Запит #2:  Клієнт ──► [ GET /profile + Token ] ──► Сервер (перевірив токен, віддав профіль)
                                               ◄── Сервер повертає 200 OK

Запит #3:  Клієнт ──► [ GET /orders ] ──► Сервер (знову не пам'ятає, хто це: потрібен токен)
```

Безстановість забезпечує колосальну масштабованість. Оскільки сервер не зобов'язаний тримати в оперативній пам'яті стан сесії клієнта, балансувальник навантаження може спрямувати перший запит на один фізичний сервер, а другий запит того ж клієнта через мілісекунду — на інший сервер на іншому континенті. Будь-який вузол у кластері здатний миттєво відповісти на запит, якщо цей запит містить повний контекст.

Ціною безстановості є надмірність метаданих: кожен запит змушений повторно нести в собі ідентифікаційні дані користувача, перелік підтримуваних мов, формати даних і налаштування кешування. Коли застосунку все ж необхідна сесія (наприклад, збереження кошика покупця в інтернет-магазині), стан накладається поверх протоколу прикладним кодом — за допомогою заголовків `Cookie` або токенів `Authorization`.

Детальний аналіз того, як ця модель формувалася історично від експериментів Тіма Бернерса-Лі до глобальних стандартів, викладено в [історичному нарисі про еволюцію HTTP](book:programming/http/hist-http-evolution.md).

## 2. Анатомія текстового повідомлення HTTP/1.1

До появи бінарного кадрування в HTTP/2 повідомлення протоколу HTTP/1.1 передавалися як відкритий текстовий потік символів ASCII через звичайний TCP-сокет. Це зробило протокол прозорим для діагностики: інженер міг підключитися утилітою Telnet чи Netcat до порту 80 і вручну надрукувати запит.

Будь-яке повідомлення HTTP/1.1 (як запит, так і відповідь) складається з чотирьох послідовних частин:
1. **Стартовий рядок:** визначає тип дії або результат її виконання.
2. **Блок заголовків (Headers):** набір пар «ключ-значення» з метаданими.
3. **Порожній рядок-роздільник:** послідовність байтів CRLF (`\r\n`), що сигналізує про завершення блоку метаданих.
4. **Тіло повідомлення (Body / Payload):** довільний бінарний або текстовий масив корисних даних.

![Анатомія текстового повідомлення HTTP/1.1](/book/programming/web-backend/http/img/http-message-anatomy.svg)

*Структура запиту й відповіді HTTP/1.1: стартовий рядок, блок заголовків, обов'язковий роздільник CRLF і корисне навантаження.*

### Стартовий рядок запиту (Request-Line)
Стартовий рядок запиту містить три поля, розділені одинарними пробілами, і завершується символами `\r\n`:

```
GET /api/v2/products/108?format=json HTTP/1.1\r\n
```

1. **Метод (Method):** дієслово англійською мовою у верхньому регістрі (`GET`, `POST`, `PUT`, `DELETE`), що позначає цільову семантичну операцію.
2. **Цільовий ресурс (Request-URI):** абсолютний або відносний шлях до ресурсу разом із необов'язковим рядком параметрів запиту (Query String).
3. **Версія протоколу:** назва та номер стандарту (`HTTP/1.1`, `HTTP/1.0`).

### Стартовий рядок відповіді (Status-Line)
Сервер відповідає стартовим рядком статусу:

```
HTTP/1.1 200 OK\r\n
```

1. **Версія протоколу:** версія, за якою сервер сформував відповідь (`HTTP/1.1`).
2. **Тризначний код стану (Status Code):** десяткове число, призначене для машинної класифікації результату (`200`, `404`, `500`).
3. **Текстове пояснення (Reason Phrase):** коротка фраза людською мовою для зручності читання логів (`OK`, `Not Found`, `Internal Server Error`).

## 3. Проблема меж і кадрування: Content-Length проти Chunked

Оскільки TCP є неперервним байтовим потоком, він не розставляє міток між повідомленнями. Програма-отримувач бачить лише суцільну стрічку байтів. Стартовий рядок і заголовки мають природний кінець — подвійний символ переносу рядка `\r\n\r\n` (0x0D 0x0A 0x0D 0x0A). Але як сервер чи клієнт дізнається, де закінчується **тіло** повідомлення і починається наступний запит у тому самому сокеті?

Протокол HTTP/1.1 пропонує два основні механізми визначення довжини тіла:

### 1. Фіксована довжина через `Content-Length`
Сервер або клієнт заздалегідь підраховує точну кількість байтів у тілі й передає її в заголовку:

```
HTTP/1.1 200 OK\r\n
Content-Type: application/json\r\n
Content-Length: 38\r\n
\r\n
{"status":"success","items_count":12}
```

Отримувач зчитує рівно 38 байтів після порожнього рядка і знає, що повідомлення вичерпане. Якщо тіло не містить даних (наприклад, у запитах `GET` чи відповідях `204 No Content`), заголовок або має значення `Content-Length: 0`, або взагалі опускається.

### 2. Блокове кодування (Chunked Transfer Encoding)
Що робити, якщо розмір відповіді невідомий заздалегідь? Наприклад, сервер генерує величезний PDF-звіт, читає велику таблицю з бази даних частинами або транслює відеопотік. Якщо використовувати `Content-Length`, сервер був би змушений спершу зберегти всі гігабайти в оперативній пам'яті чи тимчасовому файлі, підрахувати розмір і лише потім надіслати перший байт клієнту. Це створює велетенську початкову затримку (Time to First Byte, TTFB).

Для розв'язання цієї проблеми HTTP/1.1 запровадив заголовок `Transfer-Encoding: chunked`. Тіло надсилається послідовністю окремих блоків (чанків). Кожен блок має суворий формат:
- Рядок із розміром блока в шістнадцятковій системі числення (Hexadecimal) + `\r\n`.
- Байти даних відповідного розміру + `\r\n`.
- Фінальний блок нульового розміру `0\r\n\r\n`, що сигналізує про завершення тіла.

```
HTTP/1.1 200 OK\r\n
Content-Type: text/plain\r\n
Transfer-Encoding: chunked\r\n
\r\n
7\r\n
Початок\r\n
A\r\n
 продовження\r\n
0\r\n
\r\n
```

### Пастка розсинхронізації: HTTP Request Smuggling
Коли перед бекенд-сервером стоїть зворотний проксі-сервер (Reverse Proxy: Nginx, AWS ALB, Cloudflare), вони спілкуються через одне спільне TCP-з'єднання, у якому запити різних користувачів ідуть один за одним.

Якщо зловмисник надсилає запит, що **одночасно містить і `Content-Length`, і `Transfer-Encoding: chunked`**, виникає смертельна неоднозначність: який заголовок вважати пріоритетним?

![Розсинхронізація меж повідомлень (HTTP Request Smuggling)](/book/programming/web-backend/http/img/http-smuggling-desync.svg)

*Атака HTTP Request Smuggling (CL.TE): проксі читає Content-Length, а бекенд — Transfer-Encoding. Відрізаний хвіст запиту залишається в сокеті й отруює наступний запит невинного користувача.*

Якщо фронтенд-проксі орієнтується на `Content-Length`, а бекенд — на `Transfer-Encoding`, бекенд вважає перший запит завершеним на нульовому чанку `0\r\n\r\n`. Решта байтів, переданих у межах `Content-Length`, лишається в буфері TCP-сокета. Коли наступний легітимний користувач надсилає запит `GET /index.html`, бекенд зклеює залишений у буфері префікс із новим запитом і виконує шкідливу команду від імені жертви.

> 🔧 **Навіщо це.** Специфікація RFC 9112 §6.3 суворо вимагає: якщо в повідомленні присутній заголовок `Transfer-Encoding`, заголовок `Content-Length` повинен або повністю ігноруватися, або такий запит має негайно відхилятися з кодом помилки `400 Bad Request`. Будь-який промисловий HTTP-парсер повинен перевіряти це правило.

Практичну реалізацію такого безпечного автомата станів наведено у [проєкті низькорівневого парсера HTTP](book:programming/http/proj-http-parser.md).

## 4. Семантика HTTP: безпечність, ідемпотентність і мова статусів

Стандарт RFC 9110 («HTTP Semantics») чітко розмежовує механіку транспорту та семантику дій. Семантичний рівень визначає, що саме означає кожен метод і як клієнти, кеші та сервери повинні інтерпретувати результат.

### Безпечні та ідемпотентні методи
Архітектура вебсервісів і REST API стоїть на двох ключових математичних властивостях методів:

1. **Безпечні методи (Safe):** `GET`, `HEAD`, `OPTIONS`, `TRACE`. Ці методи за своїм призначенням є операціями «тільки для читання». Клієнт може викликати їх автоматично (наприклад, пошуковий робот Googlebot індексує сторінки) без ризику змінити стан ресурсу на сервері.
2. **Ідемпотентні методи (Idempotent):** метод називається ідемпотентним, якщо результат багаторазового виконання ідентичних запитів призводить до точно такого самого стану сервера, як і виконання одного запиту. `GET`, `HEAD`, `PUT`, `DELETE` є ідемпотентними. Якщо мережа обірвалася, клієнт може безпечно повторити запит `PUT /users/42` чи `DELETE /orders/99` — кінцевий стан бази буде однаковим.
3. **Небезпечні та неідемпотентні методи:** `POST`, `PATCH`. `POST` створює новий ресурс або виконує бізнес-транзакцію (списання грошей, відправлення листа). Повторення виклику `POST /payments` призведе до подвійного списання, якщо на сервері не реалізовано спеціальний механізм ключів ідемпотентності.

![Семантичні властивості методів HTTP](/book/programming/web-backend/http/img/http-methods-matrix.svg)

*Класифікація методів HTTP за безпечністю, ідемпотентністю та можливістю кешування.*

### Мова статусів відповідей
Коди станів забезпечують універсальну мову між клієнтом і сервером:
- **`201 Created`:** створення ресурсу з обов'язковим заголовком `Location: /items/123`.
- **`204 No Content`:** успішне виконання дії, коли тіло відповіді непотрібне (наприклад, після `DELETE`).
- **`301` проти `308`:** статус `301 Moved Permanently` через історичну помилку ранніх браузерів дозволяв клієнту змінювати метод `POST` на `GET` при переході за новою адресою. Сучасний статус `308 Permanent Redirect` суворо забороняє змінювати метод і тіло запиту при перенаправленні.
- **`401 Unauthorized` проти `403 Forbidden`:** `401` означає «ми не знаємо, хто ти (надай валідний токен у `Authorization`)», тоді як `403` означає «ми знаємо, хто ти, але в тебе немає прав на цю дію».
- **`502 Bad Gateway` проти `504 Gateway Timeout`:** `502` вказує, що зворотний проксі отримав відмову чи невалідну відповідь від бекенда, а `504` — що бекенд не встиг відповісти за відведений ліміт часу (таймаут).

Повний перелік методів, заголовків і статусів зведено в [довіднику семантики HTTP](book:programming/http/api-http-semantics.md).

## 5. Вузькі місця HTTP/1.1: блокування черги та Keep-Alive

У версії HTTP/1.0 кожна передача ресурсу вимагала нового TCP-з'єднання. Сторінка з 50 зображеннями змушувала браузер 50 разів поспіль виконувати тристороннє рукостискання TCP і витрачати секунди на затримки RTT:

```
Київ → Франкфурт (RTT ≈ 30 мс):
50 запитів × 30 мс (TCP Handshake) = 1500 мс лише на відкриття сокетів!
Плюс затримки фази повільного старту TCP (Slow Start) для кожного нового з'єднання.
```

HTTP/1.1 виправив це за допомогою **постійних з'єднань** (Persistent Connections / `Connection: keep-alive`), увімкнених за замовчуванням: усі ресурси завантажувалися через одне відкрите з'єднання. Проте виникла інша фундаментальна проблема: **блокування початку черги (Head-of-Line Blocking, HoL)** на прикладному рівні.

Спроба HTTP/1.1 вирішити цю проблему через конвеєризацію (Pipelining — надсилання пачки запитів без очікування відповіді) зазнала невдачі. Оскільки в текстовому потоці HTTP/1.1 немає ідентифікаторів повідомлень, сервер зобов'язаний повертати відповіді суворо в тому ж порядку, у якому надійшли запити:

```
Клієнт надсилає: [Req 1: Важкий звіт SQL] -> [Req 2: Стиль main.css] -> [Req 3: Логотип logo.png]

Сервер:
  Req 2 (CSS) пораховано за 2 мс  (чекає в буфері!)
  Req 3 (PNG) пораховано за 1 мс  (чекає в буфері!)
  Req 1 (SQL) рахується 3000 мс...

Результат: клієнт не бачить ані CSS, ані картинок цілих 3 секунди, бо вся черга заблокована першим запитом!
```

Через це браузери були змушені відкривати до 6 паралельних TCP-з'єднань на кожен домен (Domain Sharding), що призводило до марнування пам'яті серверів і неефективного використання пропускної здатності мережі.

![Еволюція транспорту та блокування черги](/book/programming/web-backend/http/img/http-multiplexing-vs-pipelining.svg)

*Еволюція транспорту: блокування черги в HTTP/1.1 Pipelining, мультиплексування бінарних кадрів у HTTP/2 та незалежні потоки QUIC у HTTP/3.*

## 6. HTTP/2: бінарне кадрування та мультиплексування

Стандарт HTTP/2 (RFC 7540 / RFC 9113, 2015 рік) вирішив проблему блокування черги на рівні прикладного протоколу завдяки переходу від текстового формату до **бінарного шару кадрування (Binary Framing Layer)**.

Замість відкритого тексту повідомлення розбиваються на невеликі бінарні кадри фіксованої структури:

```
┌────────────────────────────────────────────────────────┐
│ Length (24 біти) │ Type (8) │ Flags (8) │ R (1)        │
├────────────────────────────────────────────────────────┤
│ Stream Identifier (31 біт)                             │
├────────────────────────────────────────────────────────┤
│ Frame Payload (довільна довжина, згідно з Length)      │
└────────────────────────────────────────────────────────┘
```

Кадр має 9-байтний фіксований заголовок:
- **Length (24 біти):** довжина корисного навантаження кадру (типово до 16 КБ).
- **Type (8 бітів):** тип кадру (`HEADERS`, `DATA`, `SETTINGS`, `RST_STREAM`, `PING`, `GOAWAY`, `WINDOW_UPDATE`).
- **Flags (8 бітів):** бітові прапорці стану (`END_STREAM`, `END_HEADERS`, `ACK`).
- **Stream Identifier (31 біт):** числовий номер логічного потоку, до якого належить цей кадр (0 — потік керування з'єднанням; непарні числа — потоки клієнта; парні — потоки сервера).

Це уможливило справжнє **мультиплексування (Multiplexing)**: через одне-єдине TCP-з'єднання клієнт і сервер можуть одночасно передавати сотні паралельних логічних потоків. Кадри різних потоків вільно чергуються в одному сокеті:

```
[Потік 1: Кадр HEADERS] [Потік 2: Кадр DATA] [Потік 1: Кадр DATA 1] [Потік 3: Кадр DATA] [Потік 1: Кадр DATA 2]
```

Якщо потік #1 (важкий SQL-запит) затримується, потік #2 (стилі CSS) миттєво віддає свої дані клієнту. Блокування початку черги на рівні HTTP було повністю знищено.

### Керування потоком даних (Flow Control)
Оскільки всі потоки ділять єдиний TCP-буфер, швидкий потік міг би монополізувати сокет і переповнити пам'ять отримувача. HTTP/2 реалізує кредитний механізм керування потоком (Credit-Based Flow Control) за допомогою кадрів `WINDOW_UPDATE`. Кожен потік і з'єднання загалом мають вікно прийому в байтах. Отримувач витрачає байти вікна при прийомі `DATA` і надсилає `WINDOW_UPDATE`, коли звільняє свій буфер, дозволяючи відправнику надіслати наступну порцію.

### Стиснення заголовків HPACK
У типовому вебзастосунку заголовки запитів (`Cookie`, `User-Agent`, `Authorization`) займають від 500 байтів до 2 КБ на кожен запит і повторюються на 90 % байт-у-байт. У HTTP/1.1 ці гігабайти надлишкового тексту передавалися у відкритому вигляді.

HTTP/2 запровадив алгоритм стиснення **HPACK (RFC 7541)**:
1. **Статична таблиця:** фіксований список із 61 найпоширенішого заголовка (наприклад, індекс 2 відповідає `:method: GET`, індекс 7 — `:scheme: https`).
2. **Динамічна таблиця:** таблиця, що наповнюється значеннями, які вже передавалися в межах поточної сесії. Якщо довгий токен авторизації передано один раз, у наступних запитах замість 500 символів летить лише короткий числовий індекс.
3. **Кодування Гаффмана:** стиснення рядкових значень оптимальним префіксним кодом.

HPACK зменшує накладні витрати на передачу метаданих на 85–95 %.

## 7. HTTP/3: подолання меж TCP через протокол QUIC

Попри успіх HTTP/2, інженери виявили нове вузьке місце: блокування черги на рівні **самого транспорту TCP**.

TCP гарантує строгу послідовність байтів. Якщо на нестабільному каналі зв'язку (наприклад, мобільна мережа 4G під час руху) губиться один IP-пакет, що містив кадр потоку #1, операційна система блокує видачу даних для всіх інших потоків (#2, #3, #4), доки TCP-стек не надішле повторний запит і не отримає втрачений байт. Усі незалежні потоки HTTP/2 стають заручниками одного втраченого пакета.

Стандарт **HTTP/3 (RFC 9114, 2022 рік)** переніс HTTP на принципово новий транспортний протокол — **QUIC (RFC 9000)**, який працює поверх дейтаграмного протоколу UDP у просторі користувача.

### Ключові переваги HTTP/3 та QUIC:
1. **Справді незалежні транспортні потоки:** QUIC реалізує логіку надійної доставки окремо для кожного потоку. Втрата пакета в потоці A жодним чином не впливає на читання даних із потоків B і C.
2. **Нульова затримка встановлення з'єднання (0-RTT Handshake):** у HTTP/1.1 та HTTP/2 встановлення захищеного з'єднання вимагало окремого рукостискання TCP (1 RTT) і наступного рукостискання TLS (1–2 RTT). У QUIC транспортне підключення та шифрування TLS 1.3 об'єднані в одну операцію (1 RTT для першого з'єднання і 0 RTT для повторного).
3. **Міграція з'єднань (Connection Migration):** TCP-з'єднання жорстко прив'язане до четвірки значень `(IP_клієнта, Порт_клієнта, IP_сервера, Порт_сервера)`. Коли телефон перемикається з домашнього Wi-Fi на стільникову мережу, його IP-адреса змінюється, і всі TCP-сокети примусово розриваються. QUIC ідентифікує сесію за 64-бітним ідентифікатором з'єднання (`Connection ID`), тому зміна IP-адреси відбувається абсолютно непомітно для користувача.
4. **Стиснення заголовків QPACK (RFC 9204):** оскільки пакети QUIC можуть надходити не по порядку, старий алгоритм HPACK призвів би до блокування черги під час оновлення динамічної таблиці. QPACK розв'язує цю проблему, виділяючи окремі двонаправлені службові потоки (Encoder Stream та Decoder Stream) для узгодження динамічних індексів.

## 8. Проксі, посередники та ланцюжки передачі контексту

У реальних мережевих топологіях клієнт майже ніколи не спілкується з бекендом напряму. Між ними знаходиться ланцюжок посередників (Middleboxes): прикордонні шлюзи, балансувальники навантаження, кешуючі сервери CDN, WAF-фаєрволи та проксі виходу в інтернет.

### Прямі (Forward) та Зворотні (Reverse) проксі
- **Forward Proxy (Прямий проксі):** діє від імені клієнта. Клієнт явно налаштовує свій браузер на адресу проксі (наприклад, у корпоративній мережі для контролю виходу в інтернет). Для захищених з'єднань клієнт використовує метод `CONNECT host:443 HTTP/1.1`, просячи проксі відкрити сирий TCP-тунель.
- **Reverse Proxy (Зворотний проксі):** діє від імені сервера. Клієнт вважає, що звертається безпосередньо до сервера (`https://api.example.com`), але насправді потрапляє на балансувальник (Nginx, Envoy, HAProxy), який термінує TLS-з'єднання, перевіряє ліміти швидкості й розподіляє запити між пулом внутрішніх бекендів.

### Передача ідентичності клієнта: заголовки X-Forwarded та Forwarded
Коли зворотний проксі пересилає запит бекенду через внутрішню мережу, початкова IP-адреса клієнта та протокол з'єднання губляться: для бекенда відправником пакета виглядає сам проксі.

Для збереження контексту використовуються спеціальні заголовки:
- `X-Forwarded-For: 203.0.113.195, 198.51.100.1` — список IP-адрес, через які пройшов запит (найлівіша — початковий клієнт).
- `X-Forwarded-Proto: https` — початкова схема з'єднання між клієнтом і прикордонним шлюзом.
- `X-Forwarded-Host: api.example.com` — оригінальний заголовок `Host`, надісланий клієнтом.
- `Forwarded` (RFC 7239): стандартизований заголовок, що об'єднує всі параметри в один рядок: `Forwarded: for=203.0.113.195;proto=https;by=198.51.100.1;host=api.example.com`.

> ⚠️ **Безпека проксі:** Заголовок `X-Forwarded-For` може бути легко підроблений зловмисником, який сам допише в запит фіктивну IP-адресу. Бекенд повинен довіряти лише тим значенням `X-Forwarded-For`, які додав власний перевірений прикордонний проксі, відкидаючи непідтверджені префікси.

## 9. Життєвий цикл з'єднань і пул сокетів у виробничих системах

У високонавантажених мікросервісних бекендах продуктивність визначається не лише швидкістю парсингу повідомлень, а й дисципліною керування пулами з'єднань (Connection Pooling).

### Стани TCP-сокета на сервері
Коли з'єднання HTTP/1.1 закривається стороною сервера, сокет переходить у стан `TIME_WAIT` (триває 60 секунд за стандартом RFC 793). Якщо мікросервіс відкриває нове TCP-з'єднання на кожен вихідний HTTP-запит, за високого навантаження (5000 запитів/с) локальні порти операційної системи (Ephemeral Ports) швидко вичерпуються:

```
netstat -an | grep TIME_WAIT | wc -l
# Результат: 28240 -> ядро Linux блокує створення нових сокетів з помилкою EADDRNOTAVAIL
```

Щоб цього уникнути, бекенд-клієнти використовують пули постійних з'єднань:
- З'єднання тримається відкритим і повертається в пул після вичитування тіла відповіді.
- Задається таймаут простою (`Idle Timeout`, наприклад, 90 с) і максимальна кількість з'єднань на хост (`MaxConnsPerHost`).
- Обов'язково вичитується все тіло відповіді до кінця (навіть при помилці `500`), інакше сокет не може бути перевикористаний і змушено розривається.

## 10. Узгодження вмісту (Content Negotiation) та фактор якості q

Один і той самий логічний ресурс на сервері (наприклад, звіт про продажі за адресою `/reports/sales/2026-Q2`) може мати кілька різних фізичних представлень: документ у форматі HTML для перегляду у браузері, JSON-структура для мобільного застосунку або бінарний PDF-файл для друку.

HTTP надає механізм узгодження вмісту, керований клієнтом (Server-Driven Content Negotiation). Клієнт передає у заголовках запиту свої вподобання разом із коефіцієнтами відносної ваги `q` (Quality Value, число з плаваючою комою від 0.000 до 1.000 за стандартом RFC 9110 §12.4.2):

```
Accept: text/html;q=1.0, application/json;q=0.8, application/xml;q=0.5, */*;q=0.1
Accept-Encoding: zstd;q=1.0, br;q=0.9, gzip;q=0.7
Accept-Language: uk-UA;q=1.0, uk;q=0.9, en-US;q=0.7, en;q=0.5
```

Алгоритм вибору представлення на сервері працює за такими правилами:
1. За замовчуванням вага `q` дорівнює `1.0` (якщо не вказана явно).
2. Сервер зіставляє список доступних форматів із переліком клієнта за спаданням коефіцієнта `q`.
3. Специфічні типи MIME (`text/html`) мають пріоритет над підгрупами (`text/*`) та загальними масками (`*/*`).
4. Якщо сервер обирає представлення на основі заголовків клієнта, він **зобов'язаний** повернути у відповіді заголовок `Vary: Accept, Accept-Encoding, Accept-Language`. Це повідомляє проміжним кешам CDN, що збережена копія відповіді підходить лише тим наступним клієнтам, які мають ідентичний набір цих трьох заголовків.

## 11. Асинхронний ввід-вивід та архітектура HTTP-серверів

Традиційні сервери першого покоління (наприклад, ранні версії Apache HTTP Server у режимі `prefork`) створювали окремий потік операційної системи або окремий процес на кожне активне TCP-з'єднання. Коли клієнт повільно читав відповідь через мобільний інтернет, потік сервера блокувався на виклику `write()`, утримуючи стек пам'яті (типово 2–8 МБ на потік). За 10 000 одночасних з'єднань («проблема C10k») сервер витрачав десятки гігабайтів оперативної пам'яті лише на утримання стеків потоків, а планувальник ядра Linux витрачав процесорний час на перемикання контексту.

Сучасні високонавантажені HTTP-сервери (Nginx, Node.js, Envoy, Netty) використовують архітектуру асинхронного неблокуючого вводу-виводу на основі циклу подій (Event Loop) та системного виклику ядра Linux `epoll` (або `kqueue` у FreeBSD/macOS):

```
1. Сервер створює сокет у неблокуючому режимі: fcntl(fd, F_SETFL, O_NONBLOCK).
2. Сокет реєструється в дескрипторі epoll: epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev).
3. Єдиний потік виконання (Worker Thread) спить у виклику epoll_wait(), очікуючи подій готовності дескрипторів.
4. Щойно в сокет надходять байти або сокет стає готовим до запису, epoll повертає масив готових дескрипторів.
5. Сервер зчитує доступні байти у вхідний буфер, передає їх у потоковий парсер, формує відповідь і негайно переходить до наступного сокета без блокування.
```

Такий підхід дозволяє одному робочому процесу обслуговувати понад 100 000 одночасних відкритих HTTP-з'єднань, витрачаючи лише кілька кілобайтів пам'яті на кожне з'єднання.

## 12. Простеження та діагностика HTTP-трафіку

Для діагностики проблем у промислових вебсистемах інженери використовують поглиблений аналіз часових інтервалів запиту за допомогою утиліти `curl`:

```
curl -w "\nЧас DNS:       %{time_namelookup} s\n\
Час TCP:       %{time_connect} s\n\
Час TLS:       %{time_appconnect} s\n\
Час до TTFB:   %{time_starttransfer} s\n\
Повний час:    %{time_total} s\n" \
-o /dev/null -s "https://api.example.com/health"
```

Ці показники дозволяють миттєво локалізувати вузьке місце:
- Великий `time_namelookup` свідчить про затримки в роботі DNS-резолвера.
- Різниця `time_connect - time_namelookup` показує мережеву затримку RTT до сервера.
- Різниця `time_appconnect - time_connect` відображає тривалість криптографічного рукостискання TLS.
- Інтервал `time_starttransfer - time_appconnect` є чистим часом обробки запиту сервером (TTFB).

## 13. Проби життєздатності та готовності (Health Checks)

У сучасних оркестраторах контейнерів (Kubernetes, Nomad) протокол HTTP є стандартним інтерфейсом контролю життєвого циклу процесів. Оркестратор періодично надсилає легковагові HTTP-запити `GET` на спеціалізовані ендпоінти:

1. **Проба життєздатності (`Liveness Probe` на `/livez`):** перевіряє, чи не завис процес сервера (наприклад, у нескінченному циклі чи взаємному блокуванні Deadlock). Якщо сервер повертає статус із діапазону 200–399, контейнер вважається живим. Отримання статусів 5xx або таймаут змушує оркестратор примусово вбити контейнер (SIGKILL) і перезапустити його наново.
2. **Проба готовності (`Readiness Probe` на `/readyz`):** перевіряє, чи здатний бекенд приймати користувацький трафік (чи прогріто локальні кеші, чи встановлено пул з'єднань із базою даних і брокером повідомлень). Якщо сервіс тимчасово повертає `503 Service Unavailable`, балансувальник навантаження вилучає цей екземпляр із пулу маршрутизації, не перезапускаючи процес, доки стан не нормалізується.
3. **Проба запуску (`Startup Probe` на `/startupz`):** захищає повільні сервіси з тривалим стартом (наприклад, завантаження великих моделей у пам'ять) від передчасного вбивства пробою liveness.

## 14. Незмінність семантики: чому HTTP переміг

Еволюція HTTP демонструє унікальний інженерний тріумф: за три десятиліття протокол кардинально змінив свою фізичну форму — від відкритого однорядкового тексту ASCII в HTTP/0.9 через блоковий текстовий потік HTTP/1.1 і бінарні кадри HTTP/2 до криптографічних UDP-дейтаграм QUIC у HTTP/3.

Але впродовж усієї цієї еволюції **семантичний контракт залишався незмінним**:
- Метод `GET /api/users` завжди означає безпечне читання представлення ресурсу.
- Код `404 Not Found` завжди свідчить про відсутність сутності.
- Заголовок `Authorization: Bearer ...` несе облікові дані доступу.
- Правила взаємодії кешів через `Cache-Control` та `ETag` функціонують однаково на будь-якій швидкості.

Саме чітке розділення семантики ресурсу та механіки транспорту зробило HTTP універсальною операційною системою Всесвітньої мережі, здатною пережити будь-які зміни фізичних каналів зв'язку.
