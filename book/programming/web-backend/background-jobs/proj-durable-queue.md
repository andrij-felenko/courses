# ⚙️ Довговічна черга на таблиці бази

Окремий брокер для черги задач потрібен не завжди: звичайна таблиця в тій самій базі, де вже лежать ваші дані, дає й довговічність, і застовплення задачі за одним виконавцем, і відступання, і мертву чергу — а на додачу вміє те, чого зовнішній брокер не вміє в принципі: записати задачу тією ж транзакцією, що й бізнес-дані. Тут ми складемо таку чергу цілком — схему, запит-застовплення, цикл виконавця, закриття задачі, повтори й мертву чергу — і назвемо місця, де вона тріщить.

Уся конструкція тримається на одному стовпці й одному запиті. Стовпець зветься `run_at` і означає рівно одне: **не раніше цього моменту**. Запит — атомарне застовплення, що одним ходом вибирає задачу, ховає її від інших виконавців і віддає нам у руки. Решта — обв'язка навколо цих двох речей.

## Що черга мусить уміти

Випишімо спершу, за що ми платимо складністю. Шість пунктів, і жодного не можна викинути:

1. **Пережити перезапуск** — прийнята задача лежить на диску, доки її не виконано.
2. **Віддати задачу одному виконавцю** — двоє не беруться за той самий рядок.
3. **Повернути задачу в обіг**, якщо виконавець замовк, — і бажано без окремого наглядача, що ходить і шукає завислі рядки.
4. **Повторювати з наростальною затримкою** — і не всім гуртом в один такт.
5. **Відкласти безнадійне** вбік після N спроб — навіть тоді, коли задача вбиває виконавця раніше, ніж той устигне поскаржитися.
6. **Не заважати основній базі** — не пиляти її холостими опитуваннями й не роздувати таблицю.

Кожен із цих пунктів далі лягає в конкретний стовпець або конкретний рядок SQL. Почнімо зі схеми.

## Схема: один стовпець часу замість трьох станів

```sql
CREATE TABLE jobs (
    id            bigserial   PRIMARY KEY,
    kind          text        NOT NULL,                 -- який обробник виконує
    payload       jsonb       NOT NULL,                 -- аргументи задачі
    status        text        NOT NULL DEFAULT 'ready'
                  CHECK (status IN ('ready', 'dead')),  -- станів лише два
    run_at        timestamptz NOT NULL DEFAULT now(),   -- «не раніше цього моменту»
    attempts      int         NOT NULL DEFAULT 0,       -- скільки разів задачу БРАЛИ
    max_attempts  int         NOT NULL DEFAULT 5,
    locked_by     text,                                 -- хто взяв востаннє
    last_error    text,
    created_at    timestamptz NOT NULL DEFAULT now()
);

-- єдиний індекс, яким ходить застовплення
CREATE INDEX jobs_ready ON jobs (run_at, id) WHERE status = 'ready';
```

Найпомітніше тут — те, чого нема. Нема стану `running`. Спокуса завести його велика: задачу взяли — позначмо «виконується». Але цей стан бреше тієї ж миті, коли виконавець гине: рядок лишається `running` назавжди, бо перевести його назад нікому — той, хто мав це зробити, і є мертвий. Далі доводиться писати наглядача, що ходить по таблиці й шукає рядки, які «виконуються» надто довго, — а наглядач сам потребує наглядача.

Час такої вади не має: він іде далі й тоді, коли всі процеси мертві. Тому стан задачі ми кодуємо не словом, а моментом. **Видима задача** — це `status = 'ready' AND run_at <= now()`. Усе інше — «поки що ні»:

- задачу щойно взяв виконавець: `run_at = now() + 60 с` — це **оренда**;
- задача чекає повтору після невдачі: `run_at = now() + затримка` — це **відступання**;
- задачу поставлено «на дев'яту ранку»: `run_at = завтра 09:00` — це **відкладена постановка**.

Три різні за змістом речі — один механізм, і відрізняються вони лише числом. Стовпець `run_at` не знає, чому час іще не настав; він знає тільки, що не настав. Через це в таблиці немає жодного стану, з якого рядок не вибереться сам.

Стовпець `attempts` рахує **взяття**, а не невдачі — різниця здається дрібною, а рятує від задач, які валять виконавця цілком. `locked_by` для правильності вибору не потрібен: він працює запобіжником на закритті задачі. `dead` — єдиний стан, у який рядок переходить назавжди й лише свідомо.

## Постановка: задача в тій самій транзакції

Задачу ставлять звичайним `INSERT` — і ставлять там-таки, де пишуть бізнес-дані:

```sql
BEGIN;
  INSERT INTO orders (id, user_id, total_cents)
       VALUES ('ord_91', 'u_7', 120000);
  INSERT INTO jobs (kind, payload)
       VALUES ('order.receipt', '{"order_id": "ord_91"}');
COMMIT;
```

Ці два рядки в одній транзакції — не дрібниця оформлення, а головна перевага таблиці-черги, і варто побачити, що ламається без неї. Коли черга живе в зовнішньому брокері, замовлення й задача фіксуються в двох різних системах, і жодна пара «спочатку одне, потім друге» не рятує. Записали замовлення, а надіслати задачу не встигли — клієнт не дістане чека, і сліду про борг ніде нема. Надіслали задачу, а транзакція із замовленням відкотилася — виконавець шукає `ord_91` і не знаходить. Найпідступніше третє: задачу надіслано, транзакція ще не зафіксована, виконавець хапає задачу за мілісекунду й читає базу — замовлення там **ще не видно**, бо чужа транзакція не завершилась. Задача провалюється на порожньому місці.

Саме заради цієї атомарності й вигадали [вихідний ящик](book:programming/outbox-pattern) — коли повідомлення спершу пишуть у таблицю тієї самої бази однією транзакцією з даними, а вже окремий відправник переливає їх у брокер. Черга на таблиці — це вихідний ящик, у якого відпав другий крок: споживач читає ту саму таблицю. Задача або є разом із замовленням, або нема разом із ним; проміжного стану не існує, бо його не існує для [транзакції](book:programming/transactions-acid).

Відкласти задачу на потім — та сама вставка з іншим `run_at`:

```sql
INSERT INTO jobs (kind, payload, run_at)
     VALUES ('report.monthly', '{"month": "2026-07"}', now() + interval '2 hours');
```

## Застовплення: один запит, який вирішує все

Ось те місце, заради якого написано решту. Виконавець мусить забрати задачу так, щоб її не забрав ніхто інший, — і зробити це одним ходом:

```sql
UPDATE jobs
   SET run_at    = now() + make_interval(secs => $2),   -- оренда
       attempts  = attempts + 1,
       locked_by = $3
 WHERE id IN (
       SELECT id FROM jobs
        WHERE status = 'ready'
          AND run_at <= now()
          AND attempts < max_attempts
        ORDER BY run_at, id
        LIMIT $1
        FOR UPDATE SKIP LOCKED
 )
RETURNING id, kind, payload, attempts, max_attempts;
```

Розберімо по шматках — тут майже кожен рядок закриває окрему діру.

**`FOR UPDATE`** ставить на вибрані рядки замок на запис — [песимістичне блокування](book:programming/pessimistic-locking) (рядок оголошують своїм наперед, а не сподіваються, що ніхто не втрутиться). Замок тримається до кінця транзакції, тож жодна інша транзакція не змінить цих рядків, доки ми їх не оновимо.

**`SKIP LOCKED`** — те слово, без якого вся конструкція перетворюється на однорядну чергу. Звичайний `FOR UPDATE`, натрапивши на замкнений рядок, **чекає**, доки замок звільниться. Десять виконавців, що одночасно просять найстарішу задачу, стають у чергу до одного рядка: перший бере, решта дев'ять стоять і дивляться. `SKIP LOCKED` каже базі інше — «замкнений рядок просто пропусти, дай наступний вільний». Тому десять виконавців отримують десять різних задач за один такт, і жоден нікого не чекає. Це і є [конкурентні споживачі](book:programming/competing-consumers) в чистому вигляді, зроблені однією фразою SQL.

**Чому не `SELECT`, а потім `UPDATE`** двома окремими запитами? Бо між ними — проміжок, і в цей проміжок пролізе інший виконавець: обидва прочитали «задача #41 вільна», обидва пішли її оновлювати, обидва отримали задачу. Це класичний розрив «перевір, тоді дій» ([check-then-act](book:programming/atomicity-races) — між перевіркою і дією стан устигає змінитися), і жодна пильність у коді його не закриває, бо він структурний. Один `UPDATE ... RETURNING` не має цього проміжку: вибір, захоплення й читання відбуваються всередині однієї транзакції бази.

**`ORDER BY run_at, id`** дає приблизний порядок надходження. Він мусить стояти саме у вкладеному `SELECT`: в `UPDATE` порядку немає, оновлення не «йде згори вниз». `id` у сортуванні — щоб задачі з однаковим `run_at` мали сталий порядок, а не той, який сьогодні вибрав планувальник.

**`LIMIT $1`** — скільки задач узяти за раз. Одиниця — найчесніший старт; більше число ділить накладні витрати на запит між кількома задачами, і має за це власну ціну.

**`attempts = attempts + 1`** — і ось тонкість, яку легко зробити неправильно. Лічильник росте при **взятті**, а не при невдачі. Бо задача, що валить виконавця цілком — з'їдає всю пам'ять, ділить на нуль у бібліотеці без обробника, — ніколи не дійде до рядка коду, що записує невдачу. Якби ми рахували невдачі, така задача вічно поверталася б у чергу зі значенням `attempts = 0`, валила б наступного виконавця й наступного: [отруйне повідомлення](book:programming/poison-message), від якого черга не має жодного захисту. Лічильник, що росте в момент застовплення, ловить і цей випадок: п'ять взять — п'ять спроб, незалежно від того, чи хтось вижив, аби про них розповісти.

**`AND attempts < max_attempts`** — пара до попереднього рядка: щойно спроби вичерпано, задачу більше не видають. `RETURNING` віддає нам `attempts` уже збільшеним, тож виконавець одразу знає, котра це спроба з якої кількості.

**`locked_by = $3`** для правильності самого вибору не потрібен — але без нього не можна безпечно **закрити** задачу, коли її вже зроблено. Заразом він показує в моніторингу, чиї задачі зараз у роботі.

> 🔧 **Навіщо це.** Спокуса розбити застовплення на кілька запитів («знайти вільну задачу», «позначити своєю», «прочитати тіло») виникає щоразу, коли черга обростає умовами — фільтром за типом, пріоритетами, квотами на клієнта. Кожен такий поділ повертає в код проміжок між перевіркою і дією, і черга починає **зрідка** видавати ту саму задачу двом виконавцям — раз на тисячу, вночі, під навантаженням. Правило просте: усе, що вирішує, чия задача, мусить лишатися всередині одного оператора SQL. Умови до нього дописують; на два запити його не розрізають.

*Дві різні за масштабом часу межі: `run_at > now()` ховає задачу на секунди й хвилини, а `SKIP LOCKED` розводить виконавців у ті мікросекунди, поки триває чуже застовплення.*

На `SKIP LOCKED` можна спиратися не в кожній базі й не в кожній версії. PostgreSQL дістав його у 9.5 (вийшла 7 січня 2016 року, автор реалізації — Томас Манро), MySQL — у 8.0.1 (2017). Oracle уміє це найдовше: механізм роками працював усередині вбудованої черги Advanced Queuing, а в документацію потрапив аж у 11g, тобто офіційно спиратися на нього стало можна з 2007 року. SQLite обходиться без нього з іншої причини: там і так один письменник за раз, тож двох одночасних застовплень просто не буває.

## Цикл виконавця

Тепер обв'язка: вічний цикл «застовпити → зробити → закрити», який і є виконавцем.

:::tabs
```go
package queue

import (
    "context"
    "database/sql"
    "encoding/json"
    "log"
    "math"
    "math/rand"
    "time"
)

const claimSQL = `
UPDATE jobs SET run_at = now() + make_interval(secs => $2),
                attempts = attempts + 1, locked_by = $3
 WHERE id IN (SELECT id FROM jobs
               WHERE status = 'ready' AND run_at <= now()
                 AND attempts < max_attempts
               ORDER BY run_at, id LIMIT $1 FOR UPDATE SKIP LOCKED)
RETURNING id, kind, payload, attempts, max_attempts`

const lease = 60 * time.Second

type Job struct {
    ID          int64
    Kind        string
    Payload     json.RawMessage
    Attempts    int
    MaxAttempts int
}

type Handler func(context.Context, Job) error

// Run крутить одного виконавця, доки не скасують ctx.
func Run(ctx context.Context, db *sql.DB, me string, h Handler) error {
    for ctx.Err() == nil {
        jobs, err := claim(ctx, db, 1, me)
        if err != nil {
            return err
        }
        if len(jobs) == 0 { // черга порожня — почекати з розкидом
            idle := 500 + rand.Intn(500)
            select {
            case <-ctx.Done():
                return nil
            case <-time.After(time.Duration(idle) * time.Millisecond):
            }
            continue
        }
        for _, j := range jobs {
            runOne(ctx, db, me, h, j)
        }
    }
    return nil
}

func claim(ctx context.Context, db *sql.DB, n int, me string) ([]Job, error) {
    rows, err := db.QueryContext(ctx, claimSQL, n, lease.Seconds(), me)
    if err != nil {
        return nil, err
    }
    defer rows.Close()
    var out []Job
    for rows.Next() {
        var j Job
        if err := rows.Scan(&j.ID, &j.Kind, &j.Payload, &j.Attempts, &j.MaxAttempts); err != nil {
            return nil, err
        }
        out = append(out, j)
    }
    return out, rows.Err()
}

func runOne(ctx context.Context, db *sql.DB, me string, h Handler, j Job) {
    // дедлайн задачі коротший за оренду — щоб не працювати після її кінця;
    // зупинка процесу не рве вже початої задачі, тому WithoutCancel
    jctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), lease-5*time.Second)
    defer cancel()

    // якщо закрити рядок не вдалося — задачу поверне оренда, тож просто пишемо в журнал
    closeRow := func(q string, args ...any) {
        if _, err := db.Exec(q, args...); err != nil {
            log.Printf("задача %d: рядок не закрито: %v", j.ID, err)
        }
    }

    switch err := h(jctx, j); {
    case err == nil:
        closeRow(`DELETE FROM jobs WHERE id = $1 AND locked_by = $2`, j.ID, me)
    case j.Attempts >= j.MaxAttempts:
        closeRow(`UPDATE jobs SET status = 'dead', last_error = $2, run_at = now()
                   WHERE id = $1 AND locked_by = $3`, j.ID, err.Error(), me)
    default:
        closeRow(`UPDATE jobs SET run_at = now() + make_interval(secs => $2), last_error = $3
                   WHERE id = $1 AND locked_by = $4`, j.ID, backoff(j.Attempts), err.Error(), me)
    }
}

// backoff повертає затримку в секундах: база·2^(спроба−1), зі стелею й розкидом.
func backoff(attempt int) float64 {
    const base, ceil = 5.0, 3600.0
    d := math.Min(ceil, base*math.Pow(2, float64(attempt-1)))
    return d/2 + rand.Float64()*d/2 // розкид: [d/2 .. d]
}
```
```ts
import { Pool } from "pg";

const CLAIM = `
UPDATE jobs SET run_at = now() + make_interval(secs => $2),
                attempts = attempts + 1, locked_by = $3
 WHERE id IN (SELECT id FROM jobs
               WHERE status = 'ready' AND run_at <= now()
                 AND attempts < max_attempts
               ORDER BY run_at, id LIMIT $1 FOR UPDATE SKIP LOCKED)
RETURNING id, kind, payload, attempts, max_attempts`;

const LEASE_S = 60;

export type Job = {
  id: string;              // bigint приходить рядком — не втрачаємо точності
  kind: string;
  payload: unknown;
  attempts: number;
  max_attempts: number;
};

export type Handler = (job: Job, signal: AbortSignal) => Promise<void>;

export async function runWorker(pool: Pool, me: string, handle: Handler, stop: AbortSignal) {
  while (!stop.aborted) {
    const { rows } = await pool.query<Job>(CLAIM, [1, LEASE_S, me]);
    if (rows.length === 0) {                       // черга порожня — почекати з розкидом
      await sleep(500 + Math.random() * 500);
      continue;
    }
    for (const job of rows) await runOne(pool, me, handle, job);
  }
}

async function runOne(pool: Pool, me: string, handle: Handler, job: Job) {
  // дедлайн задачі коротший за оренду — щоб не працювати після її кінця
  const ctl = new AbortController();
  const timer = setTimeout(() => ctl.abort(), (LEASE_S - 5) * 1000);
  let failure: string | null = null;
  try {
    await handle(job, ctl.signal);
  } catch (e) {
    failure = e instanceof Error ? e.message : String(e);
  } finally {
    clearTimeout(timer);
  }

  try {
    if (failure === null) {
      await pool.query(`DELETE FROM jobs WHERE id = $1 AND locked_by = $2`, [job.id, me]);
    } else if (job.attempts >= job.max_attempts) {
      await pool.query(
        `UPDATE jobs SET status = 'dead', last_error = $2, run_at = now()
          WHERE id = $1 AND locked_by = $3`, [job.id, failure, me]);
    } else {
      await pool.query(
        `UPDATE jobs SET run_at = now() + make_interval(secs => $2), last_error = $3
          WHERE id = $1 AND locked_by = $4`, [job.id, backoff(job.attempts), failure, me]);
    }
  } catch (e) {
    // рядок не закрито — задачу поверне оренда, тож просто пишемо в журнал
    console.error(`задача ${job.id}: рядок не закрито`, e);
  }
}

/** Затримка в секундах: база·2^(спроба−1), зі стелею й розкидом. */
function backoff(attempt: number): number {
  const base = 5, ceil = 3600;
  const d = Math.min(ceil, base * 2 ** (attempt - 1));
  return d / 2 + Math.random() * d / 2;            // розкид: [d/2 .. d]
}

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
```

```py
import logging
import random
import threading
from typing import Any, Callable
from psycopg_pool import ConnectionPool

CLAIM = """
UPDATE jobs SET run_at = now() + make_interval(secs => %s),
                attempts = attempts + 1, locked_by = %s
 WHERE id IN (SELECT id FROM jobs
               WHERE status = 'ready' AND run_at <= now()
                 AND attempts < max_attempts
               ORDER BY run_at, id LIMIT %s FOR UPDATE SKIP LOCKED)
RETURNING id, kind, payload, attempts, max_attempts
"""

LEASE_S = 60
Handler = Callable[[str, Any], None]


def run_worker(pool: ConnectionPool, me: str, handle: Handler, stop: threading.Event) -> None:
    while not stop.is_set():
        with pool.connection() as conn:                       # транзакція на запит
            rows = conn.execute(CLAIM, (LEASE_S, me, 1)).fetchall()
        if not rows:                                          # черга порожня — почекати з розкидом
            stop.wait(0.5 + random.random() * 0.5)
            continue
        for row in rows:
            _run_one(pool, me, handle, *row)


def _run_one(pool: ConnectionPool, me: str, handle: Handler,
             job_id: int, kind: str, payload: Any, attempts: int, max_attempts: int) -> None:
    failure: str | None = None
    try:
        handle(kind, payload)          # дедлайн задачі — таймаути всередині обробника
    except Exception as exc:
        failure = str(exc)

    try:
        with pool.connection() as conn:
            if failure is None:
                conn.execute("DELETE FROM jobs WHERE id = %s AND locked_by = %s", (job_id, me))
            elif attempts >= max_attempts:
                conn.execute("UPDATE jobs SET status = 'dead', last_error = %s, run_at = now()"
                             " WHERE id = %s AND locked_by = %s", (failure, job_id, me))
            else:
                conn.execute("UPDATE jobs SET run_at = now() + make_interval(secs => %s),"
                             " last_error = %s WHERE id = %s AND locked_by = %s",
                             (backoff(attempts), failure, job_id, me))
    except Exception:
        # рядок не закрито — задачу поверне оренда, тож просто пишемо в журнал
        logging.exception("задача %s: рядок не закрито", job_id)


def backoff(attempt: int) -> float:
    """Затримка в секундах: база·2^(спроба−1), зі стелею й розкидом."""
    base, ceil = 5.0, 3600.0
    d = min(ceil, base * 2 ** (attempt - 1))
    return d / 2 + random.random() * d / 2          # розкид: [d/2 .. d]
```

Виконавців запускають по кілька в одному процесі й на кількох машинах одразу — код той самий, а домовлятися між собою їм не треба взагалі: усю координацію взяла на себе база. Аргумент `me` — ім'я виконавця, будь-який стабільний на час життя процесу рядок: ім'я машини, номер процесу, номер потоку.

## Закриття: успіх, повтор, смерть

Три шляхи з обробника — три різні оператори, і всі троє мають той самий хвіст `AND locked_by = $me`.

```sql
-- успіх: рядок просто зникає
DELETE FROM jobs WHERE id = $1 AND locked_by = $2;

-- невдача, спроби ще є: відсунути час і записати причину
UPDATE jobs SET run_at = now() + make_interval(secs => $2), last_error = $3
 WHERE id = $1 AND locked_by = $4;

-- невдача, спроби вичерпано: відкласти вбік
UPDATE jobs SET status = 'dead', last_error = $2, run_at = now()
 WHERE id = $1 AND locked_by = $3;
```

Навіщо `locked_by` в умові — видно з неприємного сценарію. Виконавець узяв задачу з орендою на 60 секунд і завис: складальник сміття став на паузу, мережа кліпнула, віртуалку приморозили. Оренда вичерпалась, задачу взяв інший виконавець і робить її наново. А потім перший **відмерзає** й дописує свій `DELETE` — стираючи рядок, який зараз у роботі в другого. Другий доробить і не знайде рядка, або, гірше, задача зникне на пів дорозі. Умова `locked_by = $me` це блокує: другий виконавець уже переписав `locked_by` на себе, тож `DELETE` застарілого не зачепить жодного рядка. Це те саме [оптимістичне блокування](book:programming/optimistic-locking) — «зміни, лише якщо стан такий, як я бачив», — а `locked_by` виконує роль версії рядка.

Успіх видаляє рядок, а не позначає його. Таблиця-черга має лишатися **маленькою**: це найгарячіша таблиця в базі, і кожен зайвий мільйон виконаних задач сидить у тому самому індексі, яким ходить застовплення. Якщо історія потрібна, її пишуть окремо — рядком в [журнал подій](book:programming/event-log) або в архівну таблицю тією ж транзакцією, що й видалення.

Затримку повтору рахує `backoff`. Число `max_attempts` виглядає безневинним, але саме воно вирішує, яку за тривалістю аварію сусіднього сервісу задача переживе. Порахуймо це вікно:

**Скільки часу вкриють спроби при базі 5 с (стеля 3600 с, розкид поки що відкинемо).**

```
після k-ї невдачі чекаємо  dₖ = 5 · 2^(k−1) секунд
5 спроб → 4 очікування, тож вікно = d₁ + d₂ + d₃ + d₄
        = 5·(2⁰ + 2¹ + 2² + 2³) = 5·(2⁴ − 1) = 75 с

загалом для n очікувань:   вікно = 5·(2ⁿ − 1) с

n = 4  (5 спроб)   → 5·15   =   75 с
n = 9  (10 спроб)  → 5·511  = 2555 с ≈ 43 хв
n = 10 (11 спроб)  → 5·1023 = 5115 с ≈ 1.4 год
```

Отже, стандартні п'ять спроб із базою 5 с розтягуються всього на хвилину з чвертю. Якщо сусідній сервіс лежить типово по пів години, ці налаштування безглузді — задача помре, поки він піднімається. Пережити півгодинну аварію дають або більше спроб (десять спроб укривають ≈ 43 хвилини), або більша база. Розкид укорочує кожне очікування — воно випадає між `d/2` і `d`, — тож справжнє вікно лежить десь між половиною порахованого й повним. Стеля ж потрібна, щоб двадцята спроба не призначалася на наступний місяць: без неї d₂₀ = 5·2¹⁹ ≈ 30 діб.

Сам розкид `[d/2 .. d]` замість рівно `d` — не косметика. Тисяча задач, що провалилися в ту саму секунду через ту саму аварію, з точним відступанням прокинуться теж в одну секунду й ударять по сервісу, який щойно піднявся, — [стадо, що біжить разом](book:programming/thundering-herd). Випадковий розкид розтягує їхнє пробудження по всьому інтервалу й розводить цю хвилю; докладніше про форми відступання — [окремо](book:programming/retries-backoff).

## Оренда: чому падіння лікує само себе

Тепер найкраща властивість цієї схеми. Виконавець узяв задачу і вмер — не «повернув помилку», а зник разом із процесом. Жоден рядок його коду більше не виконається. Що станеться з задачею?

Нічого — рівно 60 секунд. Її `run_at` стоїть у майбутньому, тому інші виконавці її не бачать. А потім час просто настає, умова `run_at <= now()` знову стає істинною, і найближчий виконавець бере задачу вдруге. Ніякого наглядача, ніякого «пошуку завислих», ніякого таймера в пам'яті — задачу повернув в обіг годинник бази.

![Дві часові доріжки: у першій виконавець падає на дванадцятій секунді, задача мовчки лежить під орендою до шістдесятої, а потім знову стає видимою і її бере інший; у другій задача триває довше за оренду, тому на шістдесятій секунді її паралельно бере другий виконавець.](/book/programming/web-backend/background-jobs/img/lease-timeline.svg)

*Оренда — це та сама відсічка `run_at`, тільки коротка. Вона безкоштовно повертає задачу після падіння — і так само безкоштовно віддає її вдруге, якщо задача виявилась довшою за оренду.*

Ціна цієї безкоштовності — на другій доріжці. Оренда 60 секунд, а перекодування відео триває десять хвилин: на шістдесятій секунді задача знову видима, і другий виконавець береться за неї, поки перший ще працює. Два виконавці роблять ту саму роботу одночасно. Три ліки, і застосовують їх разом:

1. **Оренда довша за найдовшу задачу.** Найпростіше й найгрубіше: якщо задачі йдуть до десяти хвилин, оренда — двадцять. Ціна — стільки ж чекатимемо після справжнього падіння.
2. **Серцебиття.** Поки обробник працює, окремий таймер щоразу відсуває оренду: `UPDATE jobs SET run_at = now() + interval '60 seconds' WHERE id = $1 AND locked_by = $2` кожні 20 секунд. Живий виконавець тримає задачу скільки треба; мертвий перестає відсувати, і оренда вичерпується за хвилину. Це дає і швидке повернення, і довгі задачі — ціною одного маленького `UPDATE` на кожні кілька десятків секунд.
3. **Дедлайн у коді, коротший за оренду.** Обробник, що знає свій крайній строк, сам припиняє роботу до кінця оренди — саме це роблять `context.WithTimeout` і `AbortSignal` у коді вище. Без нього виконавець може працювати над задачею, яку в нього вже відібрали.

Але жодне з трьох не робить подвійне виконання неможливим — вони лише роблять його рідкісним. Заморожений на дві хвилини процес не встигне ні відсунути оренду, ні помітити дедлайн, а прокинувшись, продовжить з того місця, де спав, і допише свій результат. Тому черга й дає доставку [щонайменше раз](book:programming/delivery-guarantees), а обробники пишуть [ідемпотентними](book:programming/idempotency) — так, щоб друге виконання не мало другого наслідку. Оренда керує тим, як часто це трапляється; ідемпотентність — тим, чи це шкодить.

## Мертва черга: як туди потрапляють і як звідти виходять

Один шлях у `dead` ми вже написали: обробник повернув помилку на останній спробі. Але є другий, і його легко проґавити — задача, яка вбиває виконавця. Такий рядок ніколи не дійде до `UPDATE ... status = 'dead'`, бо той код нікому виконати. Його `attempts` дійде до `max_attempts` через застовплення, і завдяки умові `attempts < max_attempts` рядок перестане видаватися — але так і залишиться `ready`, тобто невидимим сміттям, про яке ніхто не знає.

Тому переведення в мертву чергу мусить мати шлях, що не залежить від живого виконавця. Це один запит, який ганяють раз на хвилину:

```sql
UPDATE jobs
   SET status = 'dead',
       last_error = coalesce(last_error, 'спроби вичерпано, виконавець не відповів')
 WHERE status = 'ready'
   AND attempts >= max_attempts
   AND run_at <= now();
```

Умова `run_at <= now()` тут не для краси: без неї запит поховав би задачу, яку просто зараз хтось виконує на останній спробі. З нею він чіпає лише те, чия оренда вже вичерпалась, тобто справді нічийне.

Далі мертвою чергою користується людина. Подивитися, на чому все стало:

```sql
SELECT kind,
       count(*)          AS dead,        -- скільки задач цього типу вмерло
       max(created_at)   AS newest,      -- коли поставили найсвіжішу з них
       min(last_error)   AS sample_error -- зразок причини, з чого починати розбір
  FROM jobs WHERE status = 'dead'
 GROUP BY kind ORDER BY dead DESC;
```

І повернути в роботу після того, як причину усунули, — скинувши лічильник спроб:

```sql
UPDATE jobs SET status = 'ready', attempts = 0, run_at = now(), last_error = NULL
 WHERE status = 'dead' AND kind = 'order.receipt' AND created_at > now() - interval '1 day';
```

Оце й уся [мертва черга](book:programming/dead-letter-queue) — не окрема система, а два значення стовпця `status` і два запити, які ви запускаєте руками, коли розібралися.

## Складність і підводні камені

Тепер про те, що болить у виробництві.

**Індекс — не «на всяк випадок», а частина алгоритму.** Частковий [індекс](book:programming/database-indexes) `(run_at, id) WHERE status = 'ready'` збігається з умовою застовплення точно: [планувальник](book:programming/query-planner) бере з нього діапазон `run_at <= now()` уже впорядкованим і зупиняється на `LIMIT`. Без такого індексу застовплення читає всю таблицю й сортує — і що більша черга, то повільніше. Якщо виконавці фільтрують за типом (`AND kind = ANY($4)`), тип має стати першим стовпцем: `(kind, run_at, id) WHERE status = 'ready'`. Форма індексу мусить повторювати форму запиту — інакше індекс є, а користі з нього нема.

**Розпухання таблиці.** Кожне застовплення — це `UPDATE`, а `UPDATE` в базі з багатоверсійністю не переписує рядок, а створює нову версію й лишає стару мертвою ([MVCC](book:programming/mvcc)). Черга — найгарячіша таблиця в базі за кількістю змін на рядок, тож мертві версії накопичуються швидше, ніж деінде, і роздувають індекс. Прибирання під неї треба налаштувати окремо й агресивніше за стандартне:

```sql
ALTER TABLE jobs SET (autovacuum_vacuum_scale_factor = 0.01,
                      autovacuum_vacuum_cost_delay  = 0);
```

**Холосте опитування.** П'ятдесят виконавців, що раз на пів секунди питають порожню чергу, — це сотня запитів на секунду чистого шуму, які ходять цілодобово. Розкид у паузі (як у коді вище) розводить їх у часі; довша пауза здешевлює опитування, зате додає затримки перед стартом задачі. Найкраще — не опитувати взагалі, а прокидатися за сигналом: у PostgreSQL це `LISTEN`/`NOTIFY`, де постановник шле `pg_notify('jobs', '')`, а виконавець спить на з'єднанні. Опитування при цьому лишають як запасний шлях — на випадок, якщо сигнал загубився, і для задач із майбутнім `run_at`, про які жодного сигналу не буде.

**Стеля пропускної здатності.** Кожне застовплення — окрема записувальна транзакція: нова версія рядка, запис у [журнал попереднього запису](book:programming/write-ahead-log), його скидання на диск. Тобто черга змагається за той самий журнал і той самий [пул з'єднань](book:programming/connection-management), що й основне навантаження. Батчування (`LIMIT` більший за одиницю) ділить ці витрати на кілька задач і піднімає стелю в рази. Але точну стелю не вгадують і не беруть із чужих статей — її вимірюють на своїй базі й своєму залізі; коли виміряне не влазить, це і є момент переходити на [окремий брокер](book:programming/message-queue).

**Розмір батчу має тіньову ціну.** Узявши `LIMIT 20`, виконавець накриває всі двадцять задач **однією орендою**, що почалася в момент застовплення. Якщо кожна йде по десять секунд, остання в пачці почнеться на 190-й — задовго після кінця шістдесятисекундної оренди, і хтось устигне забрати її собі. Батч має сенс для коротких задач; довгі беруть по одній.

**Порядок — приблизний, а не гарантований.** `SKIP LOCKED` навмисне пропускає рядки, тому задача #42 цілком може завершитися раніше за #41. Для більшості робіт це байдуже. Коли ж порядок для якогось ключа важливий — скажімо, події одного замовлення мусять оброблятися послідовно, — потрібен додатковий стовпець із ключем групи й умова, що з однієї групи одночасно видається не більш ніж одна задача; це помітно ускладнює запит застовплення й забирає паралельність рівно там, де ви її щойно попросили.

**Пріоритети породжують голодування.** Додати `priority` й сортувати `ORDER BY priority DESC, run_at` — три хвилини роботи. Наслідок: рівний потік високопріоритетних задач може годинами не пускати низькопріоритетні до виконавців. Ліки — не «чесніше сортування», а окремі пули виконавців із власними квотами: частина виконавців бере лише низький пріоритет і тим гарантує йому мінімальний потік.

**Зупинка процесу.** На сигнал зупинки виконавець мусить перестати застовплювати нові задачі, але дати поточній дограти в межах оренди. Якщо не встигає — просто не закриває рядок: оренда вичерпається, і задачу підбере інший. Найгірше, що можна зробити, — обірвати процес між ефектом і `DELETE`; тоді задача виконається вдруге. Про це — [коректне завершення](book:programming/graceful-shutdown).

**Час беруть тільки з бази.** У всіх запитах вище він приходить із `now()`, і жодне рішення не спирається на годинник виконавця. Це навмисно: машини розходяться в часі на секунди, а сплячі віртуалки — на хвилини, тож оренда, порахована на одній машині й перевірена на іншій, була б лотереєю. Один годинник на всю чергу означає, що оренда й відступання міряються однаково для всіх, хоч би скільки машин було в пулі.

**Спостережуваність вимірюють у секундах, а не в рядках.** Кількість задач у черзі майже нічого не каже: тисяча дрібних розлетиться за секунду, а десять важких мулятимуть годину. Показник, за яким видно біду, — **вік найстарішої видимої задачі**:

```sql
SELECT kind,
       count(*) AS waiting,                                 -- скільки видимих задач чекає
       extract(epoch FROM now() - min(run_at)) AS oldest_s  -- вік найстарішої, секунди
  FROM jobs WHERE status = 'ready' AND run_at <= now()
 GROUP BY kind;
```

Якщо цей вік стало росте — виконавці, у середньому, не встигають за припливом, і жодне налаштування черги цього не виправить: треба або більше виконавців, або швидший обробник, або менше задач.
