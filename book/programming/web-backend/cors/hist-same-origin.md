# 📜 Від ізоляції Netscape до стандарту W3C: як веб навчився безпечно ділитися ресурсами

У 1995 році компанія Netscape Communications випустила браузер Netscape Navigator 2.0, у якому вперше з'явилася мова програмування JavaScript (створена Бренданом Айком, англ. *Brendan Eich*) та об'єктна модель документа (DOM). Разом із можливістю динамічно змінювати сторінку виникла критична загроза безпеці: відкриття двох різних сайтів у сусідніх вікнах або фреймах дозволяло сценарію з одного сайту вільно читати вміст, форми та паролі користувача на іншому. Щоб запобігти тотальному витоку конфіденційних даних, інженери Netscape сформулювали фундаментальне обмеження безпеки — **політику однакового походження (Same-Origin Policy, SOP)**.

Первинна реалізація SOP базувалася на простому правилі: скрипт, завантажений з одного сервера, мав повний доступ до DOM лише тих документів, які мали точно такі самі протокол, доменне ім'я та номер порту. У перші роки існування всесвітньої павутини цього було достатньо, оскільки сайти були ізольованими монолітами, що віддавали статичний HTML або генерували сторінки цілком на стороні сервера за протоколом CGI.

## Ера AJAX та криза ізоляції

У лютому 2005 року Джессі Джеймс Ґарретт (англ. *Jesse James Garrett*) опублікував есе «Ajax: A New Approach to Web Applications», описавши революційний підхід до побудови інтерактивних веб-інтерфейсів за допомогою об'єкта `XMLHttpRequest`. Замість повного перезавантаження сторінки браузер отримав здатність надсилати фонові асинхронні запити до сервера та оновлювати лише окремі вузли інтерфейсу.

З вибуховим розвитком концепції Web 2.0 веб-архітектура почала стрімко фрагментуватися. Розробники більше не будували замкнені сайти на одному сервері: виникла гостра потреба розміщувати статичний інтерфейс на розподілених мережах доставки контенту (CDN), звертатися до мікросервісів на сторонніх піддоменах (`api.example.com`), інтегрувати карти, віджети коментарів, платіжні шлюзи та агрегувати публічні API.

Однак сувора політика SOP блокувала будь-яку спробу скрипту з `https://app.com` прочитати відповідь на запит `fetch` чи `XMLHttpRequest` до `https://api.com`. Склалася парадоксальна ситуація: браузер вільно дозволяв вбудовувати зображення через тег `<img>`, завантажувати стилі через `<link>` або виконувати чужі скрипти через `<script src="...">`, проте повністю забороняв читати структуровані текстові дані через JavaScript.

## Обхідні шляхи: JSONP, фрейми та загрози безпеці

Щоб обійти обмеження SOP, індустрія почала застосовувати інженерні трюки та нестандартні хаки. Найпопулярнішим із них став **JSONP (JSON with Padding)**, запропонований Бобом Іпполіто (англ. *Bob Ippolito*) у 2005 році.

Ідея JSONP полягала в експлуатації винятку в SOP для тега `<script>`. Клієнт створював динамічний DOM-елемент `<script src="https://api.example.com/users?callback=parseData">`. Сервер повертав не чистий JSON, а фрагмент JavaScript-коду, що загортав дані у виклик указаної функції: `parseData({"user": "Alice"})`. Браузер завантажував цей файл як повноцінний виконуваний скрипт і запускав обробник у глобальній області видимості.

JSONP мав катастрофічні архітектурні та безпекові недоліки:
1. **Повна відсутність ізоляції:** завантажуваний скрипт виконувався з тими самими правами, що й основний додаток. Якщо сторонній сервер було скомпрометовано або в його відповідь вклинився зловмисник (атака Man-in-the-Middle), він міг виконати будь-який довільний код, викрасти сесійні токени чи перехопити введення клавіатури (XSS).
2. **Обмеження методами HTTP:** тег `<script>` міг виконувати лише операції `GET`. Надіслати методи `POST`, `PUT` чи `DELETE`, передати бінарні дані або кастомні заголовки авторизації було технічно неможливо.
3. **Неможливість обробки помилок:** у разі повернення сервером статусів `404 Not Found` або `500 Internal Server Error` браузер просто мовчки відхиляв виконання синтаксично некоректного скрипту, не даючи застосунку змоги дізнатися про причину збою.

Паралельно компанія Macromedia (згодом поглинута Adobe) розробила власну систему дозволів для плагіна Flash — файл `crossdomain.xml`. Розміщений у корені домену XML-документ описував список доменів, яким дозволялося зчитувати дані через Flash-сокети. Однак адміністратори масово конфігурували його директивою `<allow-access-from domain="*" />`, що регулярно призводило до витоків конфіденційних даних через спеціально скомпільовані SWF-файли.

## Народження стандарту CORS: від VoiceXML до W3C

Потреба в легальному, безпечному та стандартизованому механізмі міжсайтового обміну даними стала очевидною для консорціуму W3C.

У 2004 році Метт Ошрі (англ. *Matt Oshry*) та Бред Портер (англ. *Brad Porter*) із компанії Tellme Networks запропонували концепцію «Cross-Origin Resource Sharing» для VoiceXML. Ця ініціатива була підхоплена робочою групою W3C WebAppSec та браузерними вендорами.

У 2006 році Анне ван Кестерен (англ. *Anne van Kesteren*) з Opera Software почав формалізацію чернетки специфікації, яка спочатку називалася *Cross-Origin Requests*, а згодом отримала офіційну назву **Cross-Origin Resource Sharing (CORS)**. 

Фундаментальна філософія стандарту базувалася на трьох принципах:
- **Контроль на боці сервера:** клієнтський скрипт не може сам собі надати права — сервер повинен явно оголосити дозволи за допомогою спеціальних HTTP-заголовків `Access-Control-Allow-*`.
- **Захист спадщини (Legacy Web):** мільйони серверів, створених у 1990-х роках, розраховували на те, що браузер ніколи не відправить нестандартний метод або заголовок із чужого походження. Щоб не зламати інтернет, було введено концепцію **попередніх перевірочних запитів (Preflight)** через метод `OPTIONS`.
- **Імутабельність заголовка Origin:** браузер бере на себе абсолютну відповідальність за встановлення заголовка `Origin`, забороняючи клієнтському JavaScript модифікувати його значення.

У 2011 році Адам Барт (англ. *Adam Barth*) опублікував **RFC 6454 («The Web Origin Concept»)**, який дав суворе математичне визначення поняття походження як трійки `(scheme, host, port)` та стандартизував правила його серіалізації.

16 січня 2014 року W3C офіційно надала специфікації CORS статус рекомендованого стандарту (Recommendation). Згодом робоча група WHATWG об'єднала правила міжсайтового доступу безпосередньо в єдиний живий стандарт **Fetch Standard**, який сьогодні керує всіма мережевими запитами в сучасній веб-платформі.
