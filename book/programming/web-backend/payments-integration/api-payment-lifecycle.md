# 📋 Контракт життєвого циклу платежу та специфікація вебхуків

Цей довідник містить вичерпну специфікацію структур даних, станів скінченного автомата, протоколів автентифікації підпису вебхуків, каталогів помилок еквайрингу та архітектури подвійного бухгалтерського запису. Контракт стандартизує взаємодію між бекендом торговця та платіжним провайдером (англ. *Payment Service Provider*, PSP) на основі сучасної моделі платіжних намірів (англ. *Payment Intents API*).

Усі грошові операції в розподілених системах спираються на формальні інтерфейсні домовленості: правильний формат числових значень без втрати точності з рухомою комою, ізоляцію прав доступу між клієнтським браузером та бекендом, детермінований граф переходів станів і криптографічно підтверджені асинхронні сповіщення.

## Сутність платіжного наміру (PaymentIntent)

Об'єкт `PaymentIntent` є центральною сутністю платіжного шлюзу, яка супроводжує процес списання коштів від моменту створення кошика покупцем до остаточного фінансового клірингу або скасування.

```json
{
  "id": "pi_3MtwxU2eZvKYlo2C19kdH4yZ",
  "object": "payment_intent",
  "amount": 10990,
  "currency": "usd",
  "status": "requires_action",
  "client_secret": "pi_3MtwxU2eZvKYlo2C19kdH4yZ_secret_4j9kL0mNx",
  "capture_method": "manual",
  "confirmation_method": "automatic",
  "payment_method": "pm_1N4x9k2eZvKYlo2C0pRt5VwQ",
  "payment_method_types": ["card"],
  "setup_future_usage": "off_session",
  "next_action": {
    "type": "use_stripe_sdk",
    "use_stripe_sdk": {
      "type": "three_d_secure_redirect",
      "stripe_js": "https://hooks.stripe.com/redirect/authenticate/src_1N..."
    }
  },
  "metadata": {
    "order_id": "ord_884920",
    "customer_id": "usr_9918"
  },
  "created": 1692489600,
  "canceled_at": null,
  "cancellation_reason": null
}
```

### Детальний опис полів сутності PaymentIntent

- **`id` (string):** Унікальний ідентифікатор об'єкта в системі платіжного провайдера з префіксом `pi_`. Цей рядок є первинним ключем у зовнішній системі й залишається незмінним протягом усього життєвого циклу транзакції.
- **`amount` (integer):** Сума до списання, виражена виключно у найменших неподільних одиницях валюти (цілочисельне значення). Для валют із двома десятковими знаками (USD, EUR, UAH) сума вказується в центах чи копійках: $109.90 записується як `10990`. Для валют без десяткових знаків (наприклад, японська єна JPY, ісландська крона ISK) сума вказується як є: ¥1000 передається як `1000`. Використання дробових чисел (типу `float` або `double`) у фінансових протоколах суворо заборонено через накопичення похибок двійкового округлення за стандартом IEEE 754.
- **`currency` (string):** Трилітерний код валюти за міжнародним стандартом ISO 4217, переданий виключно у нижньому регістрі (`usd`, `eur`, `uah`, `gbp`).
- **`status` (string):** Поточна позиція об'єкта в графі станів скінченного автомата платежу.
- **`client_secret` (string):** Тимчасовий криптографічний токен із суворо обмеженими правами, призначений для передачі на клієнтську сторону (у браузер чи мобільний додаток). Клієнтський SDK використовує його для завершення оплати або проходження челенджу 3D Secure. Цей ключ не дає доступу до балансів торговця, перегляду чужих транзакцій або виконання повернення коштів (Refund).
- **`capture_method` (string):** Стратегія списання коштів. Значення `automatic` активує однофазну модель, коли авторизація та кліринг виконуються в єдиному кроці. Значення `manual` вмикає двофазну модель (авторизація з холдом), де списання заморожує ліміт на картці, але вимагає явного подальшого виклику `capture` для остаточного переказу грошей.
- **`payment_method` (string | null):** Ідентифікатор безпечно токенізованого платіжного засобу (з префіксом `pm_`), збереженого в PCI-сховищі провайдера без розкриття номера картки бекенду.
- **`setup_future_usage` (string | null):** Вказує на намір зберегти платіжний засіб для майбутніх списань: `on_session` (повторні покупки за прямої присутності покупця) або `off_session` (регулярні підписки та автоматичні нарахування за споживання без участі користувача).
- **`next_action` (object | null):** Структурований блок інструкцій для фронтенду торговця. Якщо банк-емітент вимагає суворої автентифікації клієнта (SCA / 3DS 2.0), цей блок містить посилання на фрейм автентифікації або параметри запуску нативного SDK банку.
- **`metadata` (key-value dictionary):** Довільний асоціативний масив ключ-значення торговця (розміром до 50 пар). Служить для зв'язування зовнішньої транзакції з внутрішніми сутностями бекенда (`order_id`, `user_id`, `cart_fingerprint`) і передається у всіх пов'язаних вебхуках.
- **`cancellation_reason` (string | null):** Код причини у разі скасування транзакції: `duplicate` (виявлено дублікат замовлення), `fraudulent` (підозра у шахрайстві), `requested_by_customer` (покупець відмовився від замовлення), `abandoned` (покупець закрив сторінку без завершення).

## Сутність збереження картки для рекурентних списань (SetupIntent)

Для збереження платіжного засобу під регулярні підписки або списання за фактом використання (Usage-based billing) без негайного списання грошей застосовується сутність `SetupIntent`. Вона ініціює процедуру прив'язки картки та проходження 3DS 2.0 для отримання безстрокової банківської згоди (мандата) на майбутні безконтактні списання (Merchant Initiated Transactions, MIT).

```json
{
  "id": "seti_1N4y8k2eZvKYlo2C77aB99qZ",
  "object": "setup_intent",
  "status": "succeeded",
  "customer": "cus_99182312",
  "payment_method": "pm_1N4x9k2eZvKYlo2C0pRt5VwQ",
  "usage": "off_session",
  "mandate_data": {
    "customer_acceptance": {
      "type": "online",
      "online": {
        "ip_address": "195.12.34.56",
        "user_agent": "Mozilla/5.0..."
      }
    }
  },
  "created": 1692489900
}
```

## Таблиця переходів скінченного автомата станів

Стан транзакції змінюється детерміновано за чіткими правилами переходу. Будь-які невалідні переходи (наприклад, спроба перевести списаний статус `succeeded` назад у стан вибору картки) негайно блокуються рушієм шлюзу як порушення контракту.

| Початковий стан | Подія або Виклик API | Наступний стан | Механізм і зміст переходу |
| :--- | :--- | :--- | :--- |
| — (відсутній) | Створення наміру (`POST /v1/payment_intents`) | `requires_payment_method` | Намір ініціалізовано на бекенді, створено `client_secret`. Очікується введення та токенізація реквізитів покупцем. |
| `requires_payment_method` | Прив'язка токена картки (`payment_method`) | `requires_confirmation` | Реквізити токенізовано клієнтським SDK, намір готовий до списання або запуску перевірки антифроду. |
| `requires_confirmation` | Підтвердження списання без потреби SCA | `processing` / `succeeded` | Якщо оцінка ризику низька й банк не вимагає 3DS, платіж переходить у миттєвий кліринг або успіх. |
| `requires_confirmation` | Підтвердження з вимогою банку про SCA | `requires_action` | Банк вимагає проходження 3D Secure 2. Покупцю надсилається виклик автентифікації (SMS / FaceID у додатку банку). |
| `requires_action` | Успішне завершення 3DS челенджу покупцем | `requires_capture` / `succeeded` | Автентифікацію успішно пройдено. Залежно від `capture_method` кошти або блокуються на картці, або списуються. |
| `requires_action` | Відхилення челенджу покупцем або таймаут | `requires_payment_method` | Автентифікація провалилася. Намір не анулюється, а повертається до вибору іншої картки. |
| `requires_confirmation` | Успішна авторизація при `capture_method: manual` | `requires_capture` | Кошти гарантовано заблоковано на балансі покупця (холд діє до 7 днів). Очікується відвантаження товару. |
| `requires_capture` | Виклик захоплення коштів (`POST /capture`) | `succeeded` | Кліринг завершено. Гроші перераховуються на рахунок торговця, замовлення вважається остаточно оплаченим. |
| `requires_capture` | Виклик скасування авторизації (`POST /cancel`) | `canceled` | Холд миттєво знімається банком-емітентом. Торговець не сплачує міжбанківських комісій за списання. |
| Будь-який нефінальний | Фатальна відмова банку або ручне скасування | `canceled` / `failed` | Термінальний стан. Подальші модифікації цього об'єкта неможливі; для нової спроби створюється новий намір. |

## Типи інструкцій наступної дії (next_action)

Коли платіжний намір переходить у стан `requires_action`, поле `next_action.type` визначає точний інтерфейсний сценарій, який фронтенд повинен надати покупцю:

1. **`use_stripe_sdk` (або `three_d_secure_redirect`):** стандартний сценарій 3D Secure 2. Клієнтський SDK створює невидимий або видимий iframe для зв'язку з сервером банку-емітента (ACS) та обробки челенджу.
2. **`redirect_to_url`:** перенаправлення на зовнішню сторінку платіжної системи (наприклад, перехід на сайт банку для авторизації через iDEAL, Sofort або Klarna). Об'єкт містить `return_url`, куди користувача буде повернуто після завершення.
3. **`display_bank_transfer_instructions`:** відображення реквізитів міжнародного банківського переказу (IBAN, BIC/SWIFT, унікальний код призначення платежу). Використовується для безготівкових B2B-рахунків або клірингу через систему SEPA Credit Transfer.
4. **`verify_with_microdeposits`:** верифікація банківського рахунку через мікродепозити (характерно для ACH Direct Debit у США). Провайдер надсилає два випадкові перекази на суму до $1.00, після чого покупець повинен ввести точні суми в інтерфейсі чекауту для підтвердження володіння рахунком.

## Специфікація заголовка підпису вебхуків

Кожне асинхронне сповіщення про зміну стану надсилається провайдером у формі HTTP POST-запиту з криптографічним заголовком підпису `Stripe-Signature` (або `X-Signature`). Цей механізм гарантує автентичність джерела та цілісність переданого тіла повідомлення.

```http
POST /api/webhooks/payments HTTP/1.1
Host: api.merchant.com
Content-Type: application/json; charset=utf-8
Stripe-Signature: t=1692489615,v1=5257a869e7ecebeda32affa62cdca3fa51cad7e77a0e56ff536d0ce8e108d8bd
```

### Алгоритм покрокової валідації підпису:

1. **Розбір елементів заголовка:** Заголовок розбивається за комою на ключ-значення. Виділяються мітка часу `t` (десятковий UNIX timestamp у секундах) та шістнадцятковий геш підпису версії `v1`.
2. **Перевірка часового вікна довіри (Tolerance Window):** Поточний системний час UTC порівнюється з міткою `t`. Якщо різниця перевищує допустимий ліміт (за замовчуванням 300 секунд / 5 хвилин): `|t_current - t| > 300`, запит негайно відхиляється з кодом помилки `400 Bad Request`. Це унеможливлює повторне відтворення перехопленого пакету зловмисником.
3. **Формування підписуваного рядка:** Створюється бінарний рядок шляхом конкатенації мітки часу, крапки та незмінного сирого тіла HTTP-запиту: `${t}.${raw_body}`. Тіло запиту повинно братися у вигляді вихідного буфера байтів до парсингу в JSON-об'єкт, оскільки будь-яка зміна пробілів чи порядку ключів ламає підпис.
4. **Обчислення HMAC-SHA256:** Розраховується криптографічний геш із використанням секретного ключа вебхук-ендпоїнта: `expected_sig = HMAC_SHA256(payload_bytes, webhook_secret)`.
5. **Порівняння за сталий час:** Отриманий підпис `v1` порівнюється з `expected_sig` виключно за допомогою функцій порівняння за сталий час (`crypto.timingSafeEqual`). Звичайне строкове порівняння через `===` заборонено, оскільки воно завершується на першому невідповідному байті й відкриває вразливість до атак за часом виконання (англ. *timing attacks*).

## Каталог критичних подій вебхуків (Webhook Events)

```json
{
  "id": "evt_1N4yABC2eZvKYlo2xyz98765",
  "object": "event",
  "api_version": "2023-10-16",
  "created": 1692489615,
  "type": "payment_intent.succeeded",
  "data": {
    "object": {
      "id": "pi_3MtwxU2eZvKYlo2C19kdH4yZ",
      "object": "payment_intent",
      "amount": 10990,
      "currency": "usd",
      "status": "succeeded"
    }
  },
  "request": {
    "id": "req_1234567890",
    "idempotency_key": "idem_ord_884920_checkout"
  }
}
```

### Реєстр подій та обов'язкові дії обробника

- **`payment_intent.succeeded`:** Платіж успішно авторизовано та списано (або готовий до захоплення). Бекенд зобов'язаний перевести замовлення в статус «Оплачено», ініціювати відвантаження товару чи активацію цифрової ліцензії та створити відповідні бухгалтерські проводки в головній книзі.
- **`payment_intent.payment_failed`:** Спроба списання остаточно відхилена платіжною системою або банком-емітентом. Бекенд фіксує код відмови у журналі та сповіщає покупця через інтерфейс або електронну пошту з пропозицією скористатися іншою карткою.
- **`payment_intent.requires_action`:** Намір перейшов у стан очікування підтвердження 3D Secure. Використовується для моніторингу застряглих сесій або відправки пуш-нагадувань у мобільний додаток.
- **`payment_intent.canceled`:** Намір списання скасовано торговцем через тайм-аут або відмову від покупки. Бекенд повертає зарезервовані одиниці товару на склад.
- **`setup_intent.succeeded`:** Платіжний засіб успішно верифіковано та авторизовано для майбутніх списань без присутності клієнта (off-session). Бекенд зберігає `payment_method_id` у профілі користувача для наступних періодичних білінгових циклів.
- **`charge.refunded`:** Зафіксовано факт повернення коштів покупцю (повного чи часткового). Бекенд зменшує баланс виконаного замовлення, створює зворотні бухгалтерські проводки та за потреби анулює цифрові права доступу.
- **`charge.dispute.created`:** Покупець подав офіційну заяву на чарджбек через свій банк, стверджуючи про шахрайство або неотримання товару. Шлюз автоматично списує оскаржувану суму разом із штрафною комісією за розгляд спору. Бекенд зобов'язаний зафіксувати дедлайн подачі доказів (evidence deadline) та сповістити команду комплаєнсу.
- **`charge.dispute.closed`:** Банк-емітент завершив розгляд чарджбеку. Поле `status` містить результат: `won` (торговець надав переконливі докази, кошти повернено на рахунок) або `lost` (спір програно, кошти остаточно списано на користь власника картки).
- **`payout.paid`:** Платіжний провайдер здійснив регулярний кліринговий переказ накопиченого балансу торговця на його офіційний банківський розрахунковий рахунок (IBAN). Обробник формує бухгалтерську проводку переказу коштів між транзитним та основним рахунками компанії.

## Класифікація помилок API та коди банківських відмов

Помилки інтеграції поділяються на два принципово різні рівні: **системні помилки платформи** (HTTP 4xx/5xx) та **банківські коди відхилення картки** (Decline Codes).

### Системні класи помилок платіжного API

- **`invalid_request_error` (HTTP 400):** синтаксична або логічна помилка в тілі запиту (непідтримувана валюта, від'ємна сума, невалідний формат JSON). Повторення запиту без виправлення коду заборонено (`is_retryable: false`).
- **`authentication_error` (HTTP 401):** секретний API-ключ не передано, відкликано або він не має прав на виконання цієї операції.
- **`rate_limit_error` (HTTP 429):** бекенд перевищив ліміт запитів на секунду (RPS). Запит повинен бути повторений із застосуванням експоненційного відступу з випадковим джитером (exponential backoff with jitter, `is_retryable: true`).
- **`idempotency_error` (HTTP 400 / 409):** ключ ідемпотентності був використаний повторно з іншим тілом запиту (Payload Mismatch) або попередній запит із цим ключем ще знаходиться в процесі виконання.
- **`api_connection_error` (HTTP 502 / 503 / 504):** мережевий таймаут або тимчасова недоступність серверів провайдера. Запит повинен бути автоматично повторений із тим самим заголовком `Idempotency-Key` (`is_retryable: true`).

### Каталог банківських кодів відмови (Decline Codes)

Коли банк-емітент відхиляє спробу авторизації картки, відповідь API повертає HTTP-статус `402 Payment Required`, а внутрішній об'єкт помилки містить машинночитний код відмови (`decline_code`).

| Код відмови | Причина емітента | Стратегія повтору та реакція бекенда |
| :--- | :--- | :--- |
| `insufficient_funds` | На рахунку покупця недостатньо коштів для списання. | Автоматичний повтор бекендом суворо заборонений (це призводить до штрафів від платіжних систем за надлишкові спроби). Покупцю демонструється повідомлення про поповнення рахунку. |
| `card_declined` | Загальна неспецифікована відмова банку (Do Not Honor). | Покупець має звернутися до служби підтримки свого банку для зняття лімітів на інтернет-платежі або скористатися іншою карткою. |
| `expired_card` | Термін дії картки закінчився. | Форма чекауту вимагає від користувача введення актуального платіжного засобу. |
| `incorrect_cvc` | Помилка у тризначному коді безпеки. | Покупцю надається можливість повторного введення CVC/CVV коду без створення нового платіжного наміру. |
| `authentication_required` | Транзакцію заблоковано через відсутність обов'язкової автентифікації 3DS/SCA. | Бекенд повинен повторити підтвердження списання з інструкцією перенаправлення на інтерфейс 3D Secure 2. |
| `stolen_card` / `lost_card` | Картка внесена до стоп-листа як викрадена або загублена. | Транзакція негайно відхиляється. Повторні спроби списання з цієї ж картки блокуються. |
| `fraudulent` | Транзакцію превентивно заблоковано антифрод-системою шлюзу (Stripe Radar, Adyen RevenueProtect). | Запит відхиляється. При частих систематичних спрацьовуваннях бекенд додає IP-адресу або ідентифікатор пристрою до локального чорного списку. |

## Архітектура головної книги та подвійний запис (Double-Entry Ledger)

Управління грошовими балансами через перезапис числового поля в реляційній таблиці (наприклад, `UPDATE accounts SET balance = balance + 100`) є критичною інженерною помилкою, оскільки вона не залишає аудиторського сліду і призводить до невідновлюваних розбіжностей при збоях. Усі фінансові рухи моделюються як незмінний журнал проводок за принципом подвійного запису (англ. *Double-Entry Bookkeeping*), де сума дебетів завжди дорівнює сумі кредитів.

### Стандартний план рахунків (Chart of Accounts):

- `1010` (Активи / Asset): Розрахунковий транзитний рахунок у платіжному провайдері (PSP Clearing).
- `1020` (Активи / Asset): Основний банківський рахунок юридичної особи торговця (Bank Settlement).
- `2010` (Пасиви / Liability): Зобов'язання перед покупцями за невиконаними замовленнями (Customer Escrow).
- `4010` (Доходи / Revenue): Виручка від реалізації товарів і надання послуг (Gross Sales).
- `4020` (Контрарні доходи / Contra-Revenue): Повернення товарів та відшкодування покупцям (Sales Returns).
- `5010` (Витрати / Expense): Витрати на міжбанківські комісії платіжного шлюзу (Processing Fees).
- `5020` (Витрати / Expense): Витрати на штрафні комісії розгляду спорів та чарджбеків (Dispute Penalties).

### Приклад фіксації транзакції на $100.00 з комісією еквайрингу 2.9% + $0.30 ($3.20):

```
1. Фіксація успішного списання з картки покупця ($100.00):
   ДЕБЕТ:   Рахунок 1010 (PSP Clearing)        $100.00
   КРЕДИТ:  Рахунок 4010 (Виручка від продажу) $100.00

2. Утримання транзакційної комісії платіжним провайдером ($3.20):
   ДЕБЕТ:   Рахунок 5010 (Комісії еквайрингу)  $3.20
   КРЕДИТ:  Рахунок 1010 (PSP Clearing)        $3.20

   Поточний залишок у розпорядженні торговця на рахунку 1010 становить $96.80.

3. Регулярна виплата накопичених коштів провайдером на банківський рахунок ($96.80):
   ДЕБЕТ:   Рахунок 1020 (Банківський рахунок) $96.80
   КРЕДИТ:  Рахунок 1010 (PSP Clearing)        $96.80
```
