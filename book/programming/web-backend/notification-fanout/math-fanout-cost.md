# 🧮 Математика навантаження Fanout: посилення запису, латентність і закон Ципфа

Масштабування систем розсилки сповіщень та формування стрічок спирається на точний розрахунок балансу між операціями запису й читання. Коли одна подія розмножується для мільйонів отримувачів, система зазнає ефекту посилення навантаження, який описується апаратом дискретної математики, теорії масового обслуговування, теорії ймовірностей, мережевої динаміки, апаратної продуктивності пам'яті, енергетичної ефективності, теорії ймовірнісних структур даних та важкохвостих розподілів.

## Базові метрики навантаження: коефіцієнти посилення

Позначимо параметри розподіленої системи:
- `N` — загальна кількість зареєстрованих користувачів у системі;
- `N_act` — кількість активних користувачів (активна щоденна аудиторія DAU, `N_act ≤ N`);
- `R_w` — середня частота публікації нових подій або сповіщень (запитів запису на секунду, Write RPS);
- `R_r` — середня частота відкриття стрічки або перевірки сповіщень користувачами (запитів читання на секунду, Read RPS);
- `K_in(u)` — вхідний ступінь графа для користувача `u` (кількість підписок, на скількох авторів підписаний `u`);
- `K_out(u)` — вихідний ступінь графа для користувача `u` (кількість підписників автора `u`).

У замкненому графі зв'язків сума всіх вхідних ребер тотожно дорівнює сумі всіх вихідних ребер, тому середні значення кількості підписок і підписників збігаються:

```
E[K_in] = E[K_out] = K_avg
```

Головними інженерними показниками навантаження архітектури є два безрозмірні коефіцієнти:
1. **Коефіцієнт посилення запису** `A_w` (Write Amplification Factor) — середня кількість операцій запису в сховища та черги, породжена однією вхідною подією:
   `A_w = W_total ÷ R_w`
2. **Коефіцієнт посилення читання** `A_r` (Read Amplification Factor) — середня кількість операцій читання/злиття джерел, необхідна для формування однієї стрічки користувача:
   `A_r = R_total ÷ R_r`

### Аналітичне порівняння чистих моделей

Розглянемо сумарну кількість операцій за секунду `Ops_total` для двох взаємно протилежних моделей обробки.

#### 1. Модель Fanout-on-Write (Eager Push / Матеріалізація)
Під час публікації подія розмножується у персональні поштові скриньки (Inboxes) усіх `K_out` підписників автора. Читання полягає у вибірці вже готового списку:

```
W_push = R_w · E[K_out]
R_push = R_r · 1
Ops_push = R_w · E[K_out] + R_r
A_w(push) = E[K_out]
A_r(push) = 1
```

Потреба в оперативній пам'яті для зберігання матеріалізованих стрічок довжиною `L_inbox` елементів (де розмір одного ідентифікатора події `S_id = 8` байтів):

```
RAM_push = N_act · L_inbox · S_id
```

Для системи з `N_act = 50 000 000` користувачів та глибиною стрічки `L_inbox = 800` елементів:

```
RAM_push = 50 000 000 · 800 · 8 байтів
= 320 000 000 000 байтів               [добуток кількості користувачів на розмір скриньки]
≈ 298 ГБ оперативної пам'яті           [переведення байтів у гігабайти]
```

#### 2. Модель Fanout-on-Read (Lazy Pull / Ліниве злиття)
Подія зберігається лише один раз у персональному сховищі автора (Outbox). Під час читання система опитує всі `K_in` підписок користувача і здійснює злиття:

```
W_pull = R_w · 1
R_pull = R_r · E[K_in]
Ops_pull = R_w + R_r · E[K_in]
A_w(pull) = 1
A_r(pull) = E[K_in]
```

Потреба в дисковому сховищі визначається лише загальною кількістю унікальних опублікованих повідомлень `N_events` та середнім розміром одного повідомлення `S_event`:

```
Disk_pull = N_events · S_event
```

### Точка перетину ефективності (Crossover Point)

Знайдемо співвідношення частот читання й запису, при якому сумарна кількість операцій обох моделей однакова (`Ops_push = Ops_pull`), припускаючи `E[K_in] = E[K_out] = K_avg`:

```
Ops_push - Ops_pull
= (R_w · K_avg + R_r) - (R_w + R_r · K_avg)  [підстановка формул навантаження]
= R_w · (K_avg - 1) - R_r · (K_avg - 1)      [групування за спільним множником]
= (R_w - R_r) · (K_avg - 1)                  [винесення (K_avg - 1)]
```

Прирівнюючи різницю до нуля за умови `K_avg > 1`, отримуємо висновок:

```
Ops_push = Ops_pull ⇔ R_w = R_r
```

- Якщо `R_r > R_w` (читання переважає над записом, типово для соцмереж та новинних порталів, де співвідношення `R_r ÷ R_w ≈ 50...100`), то `Ops_push < Ops_pull` — модель **Fanout-on-Write** виконує значно менше сумарних операцій на секунду.
- Якщо `R_w > R_r` (запис переважає над читанням, наприклад, у системах логування датчиків або телеметрії), то `Ops_pull < Ops_push` — модель **Fanout-on-Read** є ефективнішою.

## Вплив важкохвостих розподілів: закон Ципфа

Реальні графи соціальних взаємодій ніколи не мають нормального чи рівномірного розподілу зв'язків. Розподіл кількості підписників `K_out` підпорядковується степеневому закону Парето або закону Ципфа:

```
P(K_out = k) = C · k^(-γ)
```

де `γ` — показник ступеня (для більшості соціальних графів `2.0 ≤ γ ≤ 2.5`), а `C` — нормувальна константа:

```
C = 1 ÷ (∑ [від k = 1 до k_max] k^(-γ))
```

Нехай мінімальна кількість підписників `k_min = 1`, а максимальна кількість підписників у найпопулярнішого акаунта `k_max = 100 000 000`. При показнику `γ = 2.0` обчислимо математичне сподівання кількості підписників `E[K_out]`:

```
E[K_out]
= ∑ [від k = 1 до k_max] k · P(k)            [означення математичного сподівання]
= C · ∑ [від k = 1 до k_max] k · k^(-2.0)    [підстановка закону Ципфа]
= C · ∑ [від k = 1 до k_max] (1 ÷ k)         [скорочення степеня]
≈ C · ln(k_max)                              [наближення гармонічного ряду]
```

Оскільки сума `∑ (1 ÷ k²)` швидко збігається до константи `π² ÷ 6 ≈ 1.6449`, нормувальна константа `C ≈ 1 ÷ 1.6449 ≈ 0.6079`. Тоді:

```
E[K_out] = 0.6079 · ln(100 000 000)          [підстановка константи С та аргументу]
= 0.6079 · 18.42                             [обчислення натурального логарифма]
= 11.2 підписника                            [фінальний добуток середнього значення]
```

Хоча середнє значення кількості підписників становить лише 11, дисперсія є надзвичайно великою. Порахуємо, яку частку загального обсягу операцій запису у чистому Fanout-on-Write генерує верхній `0.1%` найпопулярніших авторів (автори з кількістю підписників `k ≥ 1000`):

```
Fraction_writes(k ≥ 1000)
= (∫ [від 1000 до k_max] k · k^(-2) dk) ÷ (∫ [від 1 до k_max] k · k^(-2) dk)   [інтегральне наближення]
= [ln(k_max) - ln(1000)] ÷ [ln(k_max) - ln(1)]                                 [первісна ln(k)]
= ln(100 000 000 ÷ 1000) ÷ ln(100 000 000)                                     [властивість логарифма]
= ln(100 000) ÷ ln(100 000 000)                                                 [ділення аргументів]
= 11.513 ÷ 18.421                                                               [числові значення]
≈ 0.625 (тобто 62.5%)                                                           [підсумок частки]
```

**Аналітичний висновок:** у системі з чистим Fanout-on-Write усього `0.1%` публікацій суперзірок генерують понад `62%` усього навантаження на диски, брокери повідомлень та оперативну пам'ять. Це створює раптові сплески та перевантаження черг.

## Оптимізація гібридного порогу k*

У гібридній архітектурі вводиться поріг кількості підписників `k*`:
- якщо автор має `K_out < k*`, публікація обробляється шляхом Fanout-on-Write;
- якщо автор має `K_out ≥ k*`, публікація зберігається в Outbox (Fanout-on-Read).

Нехай `c_w` — відносна вартість одиничної операції запису в пам'ять або чергу, а `c_r` — відносна вартість опитування та злиття одного джерела в оперативній пам'яті при читанні. Сумарна функція вартості системи `Cost(k*)` має вигляд:

```
Cost(k*)
= c_w · R_w · E[K_out | K_out < k*] + c_r · R_r · E[Celebrities_followed(k*)]
```

де `E[Celebrities_followed(k*)]` — середня кількість авторів-знаменитостей серед підписок одного користувача:

```
E[Celebrities_followed(k*)] = K_avg · P(K_out ≥ k*)
```

Використовуючи неперервне наближення розподілу Парето з `γ = 2`:

```
P(K_out ≥ k*) = ∫ [від k* до ∞] k^(-2) dk = 1 ÷ k*
E[K_out | K_out < k*] = ∫ [від 1 до k*] k · k^(-2) dk = ln(k*)
```

Підставимо отримані складові у функцію вартості:

```
Cost(k*) = c_w · R_w · ln(k*) + c_r · R_r · K_avg · (1 ÷ k*)
```

Знайдемо мінімум функції вартості, взявши похідну за `k*` і прирівнявши її до нуля:

```
d(Cost) ÷ d(k*)
= c_w · R_w · (1 ÷ k*) - c_r · R_r · K_avg · (1 ÷ (k*)²)  [диференціювання ln(k*) та 1/k*]
= 0                                                       [умова екстремуму]
```

Розв'яжемо рівняння відносно `k*`:

```
c_w · R_w · (1 ÷ k*) = c_r · R_r · K_avg · (1 ÷ (k*)²)   [перенесення доданка]
c_w · R_w = c_r · R_r · K_avg · (1 ÷ k*)                 [множення на k*]
k* = (c_r ÷ c_w) · (R_r ÷ R_w) · K_avg                   [вираження оптимального порогу]
```

### Практичний розрахунок оптимального порогу

Нехай для високонавантаженої платформи:
- `R_r = 100 000` запитів читання/с;
- `R_w = 2 000` публікацій/с;
- `K_avg = 200` підписок на користувача;
- Опитування джерела в пам'яті приблизно вдвічі дешевше за запис у розподілену чергу: `c_r ÷ c_w = 0.5`.

Обчислимо оптимальний поріг `k*`:

```
k* = 0.5 · (100 000 ÷ 2 000) · 200
= 0.5 · 50 · 200                     [ділення частот читання і запису R_r ÷ R_w]
= 5 000 підписників                  [множення коефіцієнтів вартості та підписок]
```

Усі автори з кількістю підписників понад `5 000` мають переводитися на модель Fanout-on-Read, що мінімізує сукупні витрати апаратних ресурсів кластера.

## Вплив усічення розподілу (Finite-Size Scaling)

У реальних мережах кількість підписників фізично не може перевищувати загальну кількість користувачів `N`. При врахуванні експоненційного зрізання на хвості (Truncated Power Law) з порогом `k_cutoff = 10 000 000`:

```
P(K_out = k) = C_trunc · k^(-γ) · e^(-k ÷ k_cutoff)
```

Дисперсія вихідного ступеня графа залишається скінченною, але чутливість до вибору порогу `k*` зростає: зміщення порогу з 5 000 до 10 000 збільшує навантаження на воркери запису на 40%, водночас скорочуючи кількість об'єднань при читанні лише на 5%.

## Теорія черг і латентність розсилки (Queueing & Latency Bounds)

Розсилку повідомлень можна змоделювати як систему масового обслуговування з чергою та `M` паралельними воркерами (модель `M/M/M` або `M/D/M` за класифікацією Кендалла).

Нехай:
- `λ` — середня швидкість надходження завдань на розсилку (завдань/с);
- `μ` — продуктивність одного воркера (сповіщень/с);
- `M` — кількість незалежних воркерів у пулі.

Коефіцієнт завантаження системи `ρ`:

```
ρ = λ ÷ (M · μ)
```

Система є стабільною лише тоді, коли `ρ < 1`. Якщо `ρ ≥ 1`, черга зростає безмежно, а лаг доставки прагне до нескінченності.

За законом Літтла (Little's Law), середня кількість повідомлень у черзі `L_q` прямо пропорційна інтенсивності вхідного потоку `λ` та середньому часу очікування повідомлення в черзі `W_q`:

```
L_q = λ · W_q
```

Для детермінованого часу обробки батчів (модель `M/D/M`) середній час очікування завдання в черзі описується наближеною формулою Кроммеліна:

```
W_q ≈ (ρ ÷ (2 · M · μ · (1 - ρ))) · (1 + (1 - ρ) · (M - 1) · (√(4 + 5 · M) - 2) ÷ (16 · M · ρ))
```

Коли завантаження системи наближається до критичної межі (`ρ → 1`), час затримки в черзі зростає гіперболічно як `1 ÷ (1 - ρ)`. Наприклад, при зростанні завантаження з `ρ = 0.8` до `ρ = 0.95` середня затримка доставки збільшується у:

```
Ratio_delay = (1 ÷ (1 - 0.95)) ÷ (1 ÷ (1 - 0.8))
= (1 ÷ 0.05) ÷ (1 ÷ 0.20)                        [обчислення різниць знаменників]
= 20 ÷ 5                                         [ділення коефіцієнтів черги]
= 4 рази                                         [підсумкове відношення лагів]
```

## Математичне згладжування піків: Jitter

Якщо подія вимагає сповіщення `N_push` користувачів, миттєве вкидання всіх повідомлень створює піковий сплеск інтенсивності `λ_peak`:

```
λ_peak = N_push ÷ Δt_instant  (де Δt_instant → 0)
```

Це миттєво переводить `ρ >> 1` і призводить до колапсу воркерів. Застосування рівномірного часового розмазування (Jitter) у вікні тривалості `T_window` розбиває відправку на плавний потік:

```
λ_smoothed = N_push ÷ T_window
```

Для збереження стабільності системи (`ρ ≤ ρ_target = 0.8`) мінімально необхідна ширина вікна розмазування `T_window` обчислюється як:

```
T_window ≥ N_push ÷ (ρ_target · M · μ)
```

Для розсилки `N_push = 10 000 000` сповіщень пулом з `M = 50` воркерів продуктивністю `μ = 2 000` сповіщень/с:

```
T_window ≥ 10 000 000 ÷ (0.8 · 50 · 2 000)
= 10 000 000 ÷ 80 000                      [обчислення ефективної пропускної здатності пулу]
= 125 секунд (близько 2 хвилин)            [фінальний розрахунок тривалості вікна]
```

## Апаратна пропускна здатність оперативної пам'яті (Memory Bandwidth Saturation)

Під час масового копіювання ідентифікаторів у персональні стрічки пам'ять сервера стає фізичним обмеженням. Пропускна здатність шини пам'яті сучасного сервера на базі двох процесорів з 8-канальною пам'яттю DDR5 становить близько `BW_ram = 300 ГБ/с` (300 000 000 000 байтів/с).

Якщо стрічки зберігаються у вигляді зв'язних списків у Redis або розрізнених структур у купі, кожен запис ідентифікатора `tweet_id` (8 байтів) призводить до читання й запису повного кеш-рядка процесора розміром `S_cache_line = 64` байти через відсутність просторової локальності:

```
Bytes_per_insert = S_cache_line · 2  [читання старого рядка в кеш L1/L3 + запис назад у RAM]
= 64 · 2                             [підстановка розміру кеш-лінії 64 байти]
= 128 байтів                         [сумарний трафік шини пам'яті на одну вставку]
```

Максимальна теоретична кількість операцій вставки в секунду `Inserts_max_ram`, обмежена лише шиною пам'яті:

```
Inserts_max_ram = BW_ram ÷ Bytes_per_insert
= 300 000 000 000 ÷ 128                     [підстановка пропускної здатності пам'яті]
≈ 2 343 750 000 вставок/с (2.34 млрд/с)     [теоретична межа швидкості запису]
```

Проте при використанні неблокувальних структур або м'ютексів виникає протокол когерентності кешів (MESI/MOESI), де передача ліній між сокетами через шину Ultra Path Interconnect (UPI) знижує реальну пропускну здатність у 5–10 разів до близько `250 000 000` операцій на секунду на фізичний сервер.

## Дедуплікація та фільтри Блума (Bloom Filters)

Під час масової розсилки виникає завдання дедуплікації (перевірки, чи не надсилалося сповіщення користувачу протягом останніх 24 годин). Зберігання 100 мільйонів рядків у реляційній БД або Redis `Set` вимагає гігабайти пам'яті.

Ймовірнісна структура даних **Фільтр Блума** (Bloom Filter) дозволяє перевірити належність елемента множині за час `O(k)` з нульовою ймовірністю хибно-негативної відповіді (False Negative) та контрольованою ймовірністю хибно-позитивної відповіді `p` (False Positive).

Формула ймовірності помилки `p` для бітового масиву розміром `m` бітів, `n` елементів та `k` незалежних хеш-функцій:

```
p ≈ (1 - e^(-(k · n) ÷ m))^k
```

Оптимальна кількість хеш-функцій `k_opt`, що мінімізує помилку `p`:

```
k_opt = (m ÷ n) · ln(2) ≈ 0.693 · (m ÷ n)
```

Мінімально необхідний розмір бітового масиву `m` для заданої кількості елементів `n` та допустимої похибки `p`:

```
m = - (n · ln(p)) ÷ (ln(2))²
```

Для дедуплікації `n = 100 000 000` сповіщень на добу з похибкою `p = 0.001` (0.1%):

```
m = - (100 000 000 · ln(0.001)) ÷ (0.69315)²
= - (100 000 000 · (-6.90775)) ÷ 0.48045     [підстановка логарифма похибки ln(0.001)]
= 690 775 000 ÷ 0.48045                      [множення чисельника]
= 1 437 766 677 бітів                        [розрахунок бітового масиву]
= 179 720 834 байти (близько 171 МБ)         [переведення бітів у мегабайти]
```

Оптимальна кількість хеш-функцій для такого фільтра:

```
k_opt = (1 437 766 677 ÷ 100 000 000) · 0.69315
= 14.377 · 0.69315                           [ділення бітів на кількість ключів m/n]
= 10 хеш-функцій                             [округлення до найближчого цілого]
```

Таким чином, фільтр розміром лише `171 МБ` утримує повну історію дедуплікації 100 мільйонів користувачів у кеші L3 процесора.

## Енергетична ефективність розсилки (Joules per Notification)

Енергетичні витрати мережевого адаптера (NIC) та процесора на передачу одиничного TCP-пакета описуються моделлю питомого споживання `E_net`:

```
E_packet = P_nic_active · (S_packet ÷ BW_nic) + E_cpu_syscall
```

де `P_nic_active ≈ 15 Вт` — споживання мережевої карти під навантаженням, `E_cpu_syscall ≈ 0.5 мкДж` — витрати процесора на обробку системного виклику `sendmsg()`.

При поштучній відправці `B = 1` сумарна енергія на одне сповіщення:

```
E_single = 15 · (550 · 8 ÷ 10^10) + 0.5 · 10^(-6)
= 6.6 · 10^(-7) + 0.5 · 10^(-6)              [підстановка розміру пакета 550 байтів]
= 1.16 мкДж на сповіщення                    [сумарна енергія одного поштучного пакету]
```

При батчингу `B = 500` енергія системного виклику амортизується на 500 елементів:

```
E_batched = (15 · (330.2 · 8 ÷ 10^10)) + (0.5 · 10^(-6) ÷ 500)
= 3.96 · 10^(-7) + 1.0 · 10^(-9)             [розподіл системного виклику на 500]
= 0.397 мкДж на сповіщення                   [сумарна енергія одного батчованого елемента]
```

Батчинг знижує енергоспоживання передачі у `1.16 ÷ 0.397 ≈ 2.9` раза (майже втричі), що є вирішальним фактором зменшення операційних витрат датацентру при розсилці мільярдів сповіщень щомісяця.

## Динаміка мережевого каналу: добуток смуги пропускання на затримку (BDP)

Під час мультиплексування потоків у протоколі HTTP/2 до сервісу Apple APNs продуктивність одного TCP-з'єднання лімітується добутком смуги пропускання на кругову затримку каналу (Bandwidth-Delay Product, BDP):

```
BDP = Bandwidth · RTT
```

де `Bandwidth` — пропускна здатність мережевої карти (наприклад, 10 Гбіт/с = 1.25 ГБ/с), а `RTT` — час проходження пакета до датацентру Apple (зазвичай 40 мс = 0.04 с):

```
BDP = 1 250 000 000 байтів/с · 0.04 с
= 50 000 000 байтів (50 МБ)           [обчислення обсягу даних у польоті]
```

Щоб повністю завантажити мережевий канал, обсяг непідтверджених даних у польоті (in-flight frames) повинен дорівнювати `BDP`. Якщо середній розмір HTTP/2 фрейма з push-сповіщенням становить `S_frame = 500` байтів, оптимальна кількість одночасних мультиплексованих потоків `Streams_opt` на одному TCP-з'єднанні становить:

```
Streams_opt = BDP ÷ S_frame
= 50 000 000 ÷ 500                    [підстановка BDP та розміру одного фрейма]
= 100 000 потоків у польоті           [розрахунок паралельних стрімів на з'єднання]
```

Оскільки протокол APNs обмежує максимальну кількість паралельних стрімів на одному TCP-з'єднанні значенням `Max_concurrent_streams = 1000...1500`, мінімальна кількість паралельних стійких TCP-з'єднань `Connections_min` у пулі воркера обчислюється як:

```
Connections_min = Streams_opt ÷ Max_concurrent_streams
= 100 000 ÷ 1 000                     [підстановка загальної кількості стрімів та ліміту]
= 100 TCP-з'єднань                    [розрахунок мінімального пулу сесій до APNs]
```

Підтримання пулу зі 100 активних TCP/TLS-з'єднань до APNs дозволяє повністю утилізувати мережевий інтерфейс 10 GbE без простоїв процесора.

## Рівномірність шардування: Consistent Hashing та закон великих чисел

Розподіл розсилки між `M` шардами воркерів спирається на консистентне хешування ідентифікаторів користувачів `user_id`.

Нехай `h(user_id)` — рівномірна криптографічна хеш-функція (наприклад, MurmurHash3 або xxHash). Дисперсія кількості призначених користувачів на один шард `Var[N_shard]` при використанні `V` віртуальних вузлів (Virtual Nodes) на кожен фізичний шард зменшується пропорційно `V`:

```
Var[N_shard] ≈ (N ÷ M) · (1 + 1 ÷ V)
```

Стандартне відхилення навантаження (коефіцієнт дисбалансу `σ`):

```
σ = √(Var[N_shard]) ÷ (N ÷ M)
≈ 1 ÷ √(V)
```

При використанні `V = 256` віртуальних точок на кільці консистентного хешування максимальне відхилення навантаження між шардами не перевищує:

```
σ = 1 ÷ √(256)
= 1 ÷ 16                              [добування квадратного кореня з 256]
= 0.0625 (тобто 6.25%)                [розрахунок відносного дисбалансу]
```

Це гарантує, що жоден окремий воркер розсилки не стане вузьким місцем конвеєра через нерівномірний розподіл партицій.

## Математика батчингу при взаємодії з APNs / FCM

Під час розсилки push-сповіщень через мережу до провайдерів доставки (Apple APNs, Google FCM) кожне мережеве з'єднання має накладні витрати службових заголовків TCP, TLS та протоколу прикладного рівня:
- `S_net_hdr` — розмір службових заголовків (IP + TCP + TLS ≈ 100 байтів);
- `S_proto_hdr` — розмір заголовків HTTP/2 або JSON RPC (≈ 150 байтів);
- `S_payload` — корисне навантаження сповіщення (JSON тіло ≈ 300 байтів);
- `B` — розмір пакета (кількість повідомлень в одному батч-запиті).

### 1. Без батчингу (B = 1)
Сумарний обсяг переданих даних для розсилки `M` сповіщень:

```
Bytes_single = M · (S_net_hdr + S_proto_hdr + S_payload)
= M · (100 + 150 + 300)               [підстановка розмірів заголовків та тіла]
= 550 · M байтів                      [сумарний обсяг передачі на M повідомлень]
```

Корисне використання каналу (Efficiency):

```
Efficiency_single = S_payload ÷ (S_net_hdr + S_proto_hdr + S_payload)
= 300 ÷ 550                           [відношення корисного тіла до повного пакета]
≈ 54.5%                               [відсоток корисного навантаження каналу]
```

### 2. З батчингом (B = 500 повідомлень у пакеті FCM або мультиплексування APNs)
Службові заголовки TCP/TLS амортизуються на весь пакет:

```
Bytes_batched = (M ÷ B) · S_net_hdr + M · (S_proto_hdr_per_item + S_payload)
```

При використанні FCM v1 Batch API службовий оверхед на одне повідомлення всередині multipart-пакета падає до `S_proto_hdr_per_item ≈ 30` байтів:

```
Bytes_batched = (M ÷ 500) · 100 + M · (30 + 300)
= M · 0.2 + M · 330                   [розподіл службових заголовків на розмір батча 500]
= 330.2 · M байтів                    [фінальний обсяг переданих даних на M повідомлень]
```

Корисне використання каналу:

```
Efficiency_batched = (M · 300) ÷ (330.2 · M)
= 300 ÷ 330.2                         [скорочення множника M]
≈ 90.8%                               [відсоток корисного навантаження при батчингу]
```

**Ефект:** батчинг зменшує мережевий трафік на `(550 - 330.2) ÷ 550 ≈ 40%` і скорочує кількість системних викликів введення-виведення `sendmsg()` у `500` разів, захищаючи ядро операційної системи від вичерпання дескрипторів сокетів та переповнення черг драйвера мережевої карти.
