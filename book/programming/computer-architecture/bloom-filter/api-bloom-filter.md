# 📋 Інтерфейс та конфігурація системного фільтра Блума

Програмний інтерфейс (API) фільтра Блума на системному рівні повинен задовольняти комплекс жорстких інженерних вимог. Оскільки структура призначена для обслуговування високочастотних запитів у ядрі операційної системи, мережевому стеку чи рушіях зберігання даних (LSM-деревах, таблицях SSTable), її контракт має гарантувати нульові накладні витрати на виклик, стабільність двійкового інтерфейсу (ABI), передбачувану роботу з вирівнюванням пам'яті та потокобезпеку без блокувань.

Будь-яка системна реалізація повинна чітко розмежовувати три рівні взаємодії: конфігурацію масиву під час створення, гарячий шлях запису та перевірки належності ключів, а також протокол серіалізації бітового відбитка на постійні носії інформації для збереження між перезапусками процесів.

---

### Контракт програмного інтерфейсу: C та C++20

Нижче наведено парні специфікації інтерфейсу. Версія на мові C надає стабільний C-сумісний інтерфейс з непрозорим покажчиком (*opaque pointer*) та явними кодами повернення помилок. Версія на мові C++20 використовує сучасні ідіоми: типи безпеки пам'яті `std::span` та `std::string_view`, шаблон повернення результату `std::expected`, RAII-управління ресурсами та строгий контроль вирівнювання типів.

:::tabs
```c
#ifndef SYSTEM_BLOOM_FILTER_H
#define SYSTEM_BLOOM_FILTER_H

#include <stdint.h>
#include <stddef.h>
#include <stdbool.h>

#ifdef __cplusplus
extern "C" {
#endif

// Коди результатів системних операцій
typedef enum {
    BLOOM_OK                = 0,
    BLOOM_ERR_INVALID_ARGS  = -1,
    BLOOM_ERR_OUT_OF_MEMORY = -2,
    BLOOM_ERR_CORRUPT_DATA  = -3,
    BLOOM_ERR_IO            = -4
} bloom_status_t;

// Параметри створення та конфігурації фільтра
typedef struct {
    size_t   expected_entries; // Очікувана кількість унікальних ключів (n)
    double   target_fp_rate;   // Цільова ймовірність хибного спрацьовування (p)
    uint32_t seed;             // Базовий seed для генерації гешів
    bool     cache_aligned;    // Вирівнювання блоків за межею 64 байтів
} bloom_config_t;

// Непрозора структура внутрішнього стану фільтра
typedef struct bloom_filter bloom_filter_t;

// Створення нового екземпляра фільтра у динамічній пам'яті
bloom_status_t bloom_create(const bloom_config_t *config, bloom_filter_t **out_filter);

// Додавання байтового буфера довільної довжини
void bloom_add_bytes(bloom_filter_t *filter, const void *data, size_t len);

// Швидкісний шлях для додавання 64-розрядного цілочисельного ключа
void bloom_add_u64(bloom_filter_t *filter, uint64_t key);

// Перевірка присутності ключа за байтовим буфером (true — ймовірно є, false — 100% немає)
bool bloom_contains_bytes(const bloom_filter_t *filter, const void *data, size_t len);

// Швидкісний шлях для перевірки 64-розрядного цілочисельного ключа
bool bloom_contains_u64(const bloom_filter_t *filter, uint64_t key);

// Скидання всіх розрядів масиву в 0 (очищення фільтра)
void bloom_reset(bloom_filter_t *filter);

// Отримання необхідного розміру буфера для повної бінарної серіалізації
size_t bloom_serialized_size(const bloom_filter_t *filter);

// Серіалізація стану фільтра в байтовий масив
bloom_status_t bloom_serialize(const bloom_filter_t *filter, void *buffer, size_t buf_size);

// Відновлення фільтра з раніше серіалізованого бінарного буфера
bloom_status_t bloom_deserialize(const void *buffer, size_t buf_size, bloom_filter_t **out_filter);

// Звільнення виділених ресурсів та пам'яті фільтра
void bloom_destroy(bloom_filter_t *filter);

#ifdef __cplusplus
}
#endif

#endif // SYSTEM_BLOOM_FILTER_H
```
```cpp
#pragma once

#include <cstdint>
#include <cstddef>
#include <span>
#include <string_view>
#include <memory>
#include <expected>
#include <concepts>

namespace sys::bloom {

// Типізовані коди помилок системного рівня
enum class Error : int32_t {
    InvalidArguments = -1,
    OutOfMemory      = -2,
    CorruptedData    = -3,
    IoError          = -4
};

// Параметри створення фільтра Блума
struct Config {
    size_t expected_entries{1'000'000};
    double target_fp_rate{0.01};
    uint32_t seed{0x9e3779b9};
    bool cache_aligned{true};
};

class BloomFilter {
public:
    // Безпечний фабричний метод створення екземпляра
    static std::expected<BloomFilter, Error> create(const Config& cfg) noexcept;

    // Конструктори переміщення (Move semantics)
    BloomFilter(BloomFilter&&) noexcept = default;
    BloomFilter& operator=(BloomFilter&&) noexcept = default;

    // Заборона копіювання для запобігання дублювання великих масивів пам'яті
    BloomFilter(const BloomFilter&) = delete;
    BloomFilter& operator=(const BloomFilter&) = delete;

    ~BloomFilter() = default;

    // Запис елементів довільних типів даних
    void add(std::span<const std::byte> key) noexcept;
    void add(std::string_view key) noexcept;
    void add(uint64_t key) noexcept;

    // Перевірка належності ключів (константний неблокуючий доступ)
    [[nodiscard]] bool contains(std::span<const std::byte> key) const noexcept;
    [[nodiscard]] bool contains(std::string_view key) const noexcept;
    [[nodiscard]] bool contains(uint64_t key) const noexcept;

    // Очищення вмісту бітового масиву
    void clear() noexcept;

    // Інформаційні методи стану
    [[nodiscard]] size_t memory_bytes() const noexcept;
    [[nodiscard]] size_t bit_capacity() const noexcept;
    [[nodiscard]] uint32_t hash_count() const noexcept;

    // Двійкова серіалізація та відновлення стану
    [[nodiscard]] size_t serialized_size() const noexcept;
    std::expected<void, Error> serialize(std::span<std::byte> destination) const noexcept;
    static std::expected<BloomFilter, Error> deserialize(std::span<const std::byte> source) noexcept;

private:
    struct Impl;
    std::unique_ptr<Impl> impl_;
    explicit BloomFilter(std::unique_ptr<Impl> impl) noexcept;
};

} // namespace sys::bloom
```

### Детальний опис параметрів та поведінки функцій

#### Ініціалізація та конфігурація (`bloom_create` / `BloomFilter::create`)
Функція ініціалізації приймає структуру `Config`, що задає два фундаментальні обмеження:
1. `expected_entries` (`n`) — планова максимальна кількість унікальних ключів, які будуть додані до фільтра. Якщо фактична кількість елементів перевищить це число, фільтр не зламається і не почне давати збої пам'яті, проте його бітовий масив перенасититься одиницями, що призведе до експоненційного зростання ймовірності хибнопозитивних спрацьовувань вище закладеного порогу.
2. `target_fp_rate` (`p`) — бажаний коефіцієнт хибних спрацьовувань (наприклад, `0.01` відповідає 1% помилок). На основі значень `n` та `p` конструктор автоматично обчислює мінімально необхідну кількість бітів `m` за формулою `m = -n · ln(p) / (ln(2))²` та оптимальну кількість геш-функцій `k = (m / n) · ln(2)`.
3. `cache_aligned` — прапорець, який вмикає блочну організацію пам'яті з обов'язковим апаратним вирівнюванням кожного сектора за межею 64 байтів (`alignas(64)` або `posix_memalign`).

#### Операція додавання (`bloom_add_*` / `BloomFilter::add`)
Функція додавання виконує обчислення 64-розрядного базового гешу ключа (наприклад, алгоритмом `xxHash64` чи `MurmurHash3`), після чого формує `k` бітових індексів за допомогою оптимізації Кірша-Мітценмахера: `g_i(x) = (h₁ + i · h₂) mod m`. Для кожного індексу відповідний біт у масиві встановлюється в стан 1 за допомогою побітового `OR`.

Операція додавання є ідемпотентною: повторний запис того самого ключа не змінює стан масиву та не збільшує кількість активованих розрядів.

#### Операція перевірки (`bloom_contains_*` / `BloomFilter::contains`)
Гаряча функція перевірки обчислює ті самі `k` геш-індексів для запитуваного ключа та послідовно зчитує відповідні біти:
- Якщо хоча б один біт дорівнює 0, функція негайно повертає `false` (*True Negative*). Це гарантує на 100%, що ключ ніколи не додавався до фільтра.
- Якщо всі `k` бітів виявилися встановленими в 1, функція повертає `true` (*Possible Positive*). Ключ присутній у множині з імовірністю `1 - p`, або ж виникла колізія гешів із імовірністю `p`.

### Формат бінарної серіалізації на диск (On-Disk Layout)

Для довготривалого збереження фільтра у файлах баз даних (наприклад, у блоках метаданих таблиць SSTable або індексах пошукових систем) використовується суворо структурований бінарний формат із 32-байтовим заголовком, вирівняним за межею 64 байтів.

| Зсув (байти) | Поле заголовка        | Тип даних  | Призначення та інваріанти                                     |
|:-------------|:----------------------|:-----------|:--------------------------------------------------------------|
| `0x00..0x03` | `magic_bytes`         | `uint32_t` | Сигнатура формату: `0x424C4F4D` (ASCII-рядок `"BLOM"`)       |
| `0x04..0x05` | `version`             | `uint16_t` | Номер версії двійкового формату (`0x0002`)                   |
| `0x06..0x07` | `flags`               | `uint16_t` | Бітові прапорці: біт 0 = Blocked 64B, біт 1 = Compressed      |
| `0x08..0x0B` | `num_hashes`          | `uint32_t` | Кількість використаних геш-функцій `k`                        |
| `0x0C..0x0F` | `seed`                | `uint32_t` | Базове випадкове зерно генератора гешів                       |
| `0x10..0x17` | `num_bits`            | `uint64_t` | Повний розмір корисного бітового масиву `m`                   |
| `0x18..0x1F` | `checksum_crc64`      | `uint64_t` | Контрольна сума CRC-64-ECMA для перевірки цілісності          |
| `0x20..`     | `bit_payload[]`       | `uint8_t[]`| Сирий бітовий масив, вирівняний за апаратною межею 64 байтів  |

#### Нульове копіювання при десеріалізації (Zero-Copy mmap)
Якщо файл із серіалізованим фільтром відображається в адресний простір процесу за допомогою системного виклику `mmap()`, бітовий масив не потребує копіювання у виділену динамічну пам'ять. Програма перевіряє сигнатуру `magic_bytes` та контрольну суму, після чого покажчик внутрішнього масиву встановлюється безпосередньо на зміщення `0x20` у пам'яті `mmap`. Завдяки вирівнюванню за межею 64 байтів усі подальші операції `contains()` виконуються безпосередньо над сторінковим кешем ядра ОС без додаткових алокацій.

### Інваріанти багатопотоковості та паралелізму

1. **Паралельне читання (Concurrent Reads):** операція `contains()` не модифікує внутрішній стан фільтра і є абсолютно безпечною для одночасного виконання з довільної кількості потоків без використання м'ютексів чи спінлоків. Усі звернення до пам'яті можуть виконуватися з порядком пам'яті `std::memory_order_relaxed`.
2. **Конкурентний запис (Concurrent Writes):** оскільки встановлення біта модифікує спільне машинне слово (64-розрядне число `uint64_t`), два одночасні записи в різні біти одного й того самого слова створюють стан гонитви (*data race*). Для безпечного багатопотокового заповнення фільтра встановлення бітів має виконуватися через атомарну операцію `fetch_or`:

:::tabs
```c
// Атомарне встановлення біта у мові C
atomic_fetch_or_explicit((_Atomic uint64_t*)&word, mask, memory_order_relaxed);
```
```cpp
// Атомарне встановлення біта у мові C++
reinterpret_cast<std::atomic<uint64_t>*>(&word)->fetch_or(mask, std::memory_order_relaxed);
```
:::

3. **Читання під час запису (Read-While-Write Consistency):** якщо один потік читає фільтр у той час, як інший записує новий ключ, потік, що читає, може побачити або старий стан бітів (до запису), або частково оновлений стан. Оскільки операція запису лише встановлює одиниці й ніколи не скидає їх у нуль, частковий стан може тимчасово дати відповідь `false` (ніби ключ ще не додався), але ніколи не призведе до спотворення пам'яті чи аварійного завершення програми.

### Інженерна таблиця вибору параметрів пам'яті

Наведена таблиця містить точні розрахунки обсягу пам'яті та кількості геш-функцій для типових системних конфігурацій:

| Кількість ключів `n` | Цільовий рівень `p` | Розмір масиву `m` (біт) | Витрати пам'яті (RAM) | Кількість гешів `k` |
|:---------------------|:--------------------|:------------------------|:----------------------|:--------------------|
| **10 тисяч (10K)**   | 1.0% (0.01)         | 95 850 бітів            | ~11.7 КБ              | 7                   |
| **1 мільйон (1M)**   | 5.0% (0.05)         | 6 235 224 біти          | ~761 КБ               | 4                   |
| **1 мільйон (1M)**   | 1.0% (0.01)         | 9 585 058 бітів         | ~1.14 МБ              | 7                   |
| **1 мільйон (1M)**   | 0.1% (0.001)        | 14 377 588 бітів        | ~1.71 МБ              | 10                  |
| **100 мільйонів**    | 1.0% (0.01)         | 958 505 837 бітів       | ~114.2 МБ             | 7                   |
| **1 мільярд (1B)**   | 1.0% (0.01)         | 9.585 × 10⁹ бітів       | ~1.12 ГБ              | 7                   |

Коли система працює під екстремальним навантаженням, вибір між класичною та блочною конфігурацією визначається тим, де знаходиться вузьке місце: якщо критичною є економія кожного байта RAM (наприклад, у мікроконтролерах із 64 КБ пам'яті), використовують класичний масив з непарними розмірами; якщо ж головною метою є максимальна кількість транзакцій за секунду на багатоядерному сервері, перевагу беззастережно віддають кеш-блочному фільтру з апаратним вирівнюванням блоків по 64 байти.
