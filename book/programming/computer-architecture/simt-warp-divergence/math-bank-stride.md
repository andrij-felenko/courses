# 🧮 Математика банківських конфліктів: крок доступу, НСД та циклічне масштабування затримки

Організація спільної пам'яті (англ. *Shared Memory*) на графічних процесорах спирається на циклічний розподіл слів за незалежними фізичними модулями пам'яті — банками. Якщо кілька потоків у межах одного варпу звертаються до пам'яті з певним кроком (англ. *stride*), виникають апаратні колізії.

Розглянемо точний алгебраїчний апарат, що описує розподіл звернень, ступінь серіалізації транзакцій та математичні методи усунення конфліктів.

### Алгебра відображення адрес на банки пам'яті

Нехай варп складається з `W = 32` потоків із локальними індексами `i ∈ {0, 1, 2, ..., 31}`. Кожен потік звертається до 32-бітного слова (4 байти) у спільній пам'яті за адресою:

```
Address(i) = BaseAddress + i · S · 4 байтів
```

де `BaseAddress` — базова адреса масиву (вирівняна на межу 4 байтів), а `S` — цілочисловий крок доступу у 4-байтних словах.

Фізичний масив спільної пам'яті розділено на `M = 32` незалежні банки (від банку 0 до банку 31). Номер банку `B(i)`, до якого надходить запит від потоку `i`, визначається залишком від ділення індексу слова на кількість банків:

```
B(i)
= (Address(i) / 4 байтів) mod 32      [визначення номера банку]
= (BaseWord + i · S) mod 32           [підстановка адреси слова]
```

Оскільки константа `BaseWord` лише зміщує початковий банк циклічно для всіх потоків одночасно і не змінює взаємної відстані між запитами, покладемо для спрощення `BaseWord = 0`. Отримуємо функцію відображення:

```
B(i) = (i · S) mod 32,    де i ∈ {0, 1, ..., 31}
```

### Теорема про кількість унікальних банків та ступінь конфлікту

Функція `B(i)` задає гомоморфізм адитивної циклічної групи `Z₃₂` у саму себе. Множина досяжних банків є циклічною підгрупою, породженою елементом `S mod 32`:

```
Im(B) = { (i · S) mod 32 | i ∈ {0, 1, ..., 31} } ⊆ Z₃₂
```

З теорії циклічних груп розмір образу підгрупи (кількість унікальних банків `U`, що отримають хоча б один запит) дорівнює порядку елемента `S` у групі `Z₃₂`:

```
U = |Im(B)| = 32 / gcd(S, 32)
```

де `gcd(a, b)` — найбільший спільний дільник (англ. *greatest common divisor*, НСД) чисел `a` та `b`.

Оскільки всі 32 потоки варпу рівномірно розподіляються між цими `U` унікальними банками, кількість потоків `k`, які претендують на один і той самий банк (ступінь банківського конфлікту або англ. *k-way bank conflict*), становить:

```
k
= W / U                               [кількість потоків на один банк]
= 32 / (32 / gcd(S, 32))              [підстановка розміру підгрупи]
= gcd(S, 32)                          [скорочення на 32]
```

Таким чином, ступінь банківського конфлікту `k` строго дорівнює найбільшому спільному дільнику кроку доступу `S` та кількості банків 32.

### Таблиця масштабування затримки від кроку доступу

Якщо один такт шини пам'яті обслуговує одне слово на банк, то апаратний контролер спільної пам'яті витрачає на виконання однієї машинної інструкції завантаження/збереження (LDS/STS) рівно `k` послідовних циклів:

```
T(S) = gcd(S, 32) · T_base
```

Розглянемо характерні значення кроку `S`:

```
Крок S    gcd(S, 32)    Унікальні банки    Ступінь конфлікту    Затримка шини
─────────────────────────────────────────────────────────────────────────────
1 (послід.)   1               32                 1-way (немає)     1 такт
2             2               16                 2-way             2 такти
3 (непарний)  1               32                 1-way (немає)     1 такт
4             4                8                 4-way             4 такти
8             8                4                 8-way             8 тактів
16           16                2                16-way            16 тактів
32 (стовпець)32                1                32-way            32 такти
```

Будь-який непарний крок `S` (1, 3, 5, 7, 9, 11...) має `gcd(S, 32) = 1`, завдяки чому генерує повну перестановку всіх 32 банків без жодного конфлікту. Навпаки, степені двійки викликають катастрофічну деградацію, досягаючи піку при `S = 32`, коли всі 32 потоки б'ють у банк 0.

### Математичне обґрунтування паддингу (Padding)

Нехай у спільній пам'яті виділено двовимірний масив розміром `32 × 32` елементи типу float32:

```
float tile[32][32];
```

При транспонуванні матриці запис виконується за рядками (потік `i` пише в `tile[row][i]`, крок `S = 1`, `gcd(1, 32) = 1` — конфліктів немає). Однак зчитування виконується за стовпцями (потік `i` читає `tile[i][col]`).

Адреса елемента `tile[i][col]` у лінійній пам'яті має вигляд:

```
Index(i) = i · 32 + col
B(i) = (i · 32 + col) mod 32 = col mod 32
```

Для фіксованого стовпця `col` значення `B(i)` є сталою величиною для всіх `i ∈ {0, ..., 31}`. Усі 32 потоки звертаються до одного банку `col mod 32`, що дає `k = 32` (повна серіалізація на 32 такти).

Додамо `P` фіктивних елементів паддингу до кожного рядка розміром `TileX`:

```
S_pad = TileX + P
```

Мінімальний паддинг `P_min`, що повністю ліквідує конфлікти для довільної ширини плитки `TileX`, визначається як найменше невід'ємне ціле число, яке задовольняє умову взаємної простоти:

```
P_min = min { P ≥ 0 | gcd(TileX + P, 32) = 1 }
```

Для класичної плитки `TileX = 32` отримуємо:
* При `P = 0`: `gcd(32, 32) = 32` (32-кратний конфлікт);
* При `P = 1`: `gcd(33, 32) = 1` (0 конфліктів, 1 такт).

Перевіримо розподіл для `tile[32][33]` аналітично:

```
Index_pad(i) = i · 33 + col
B_pad(i)
= (i · 33 + col) mod 32               [лінійний індекс з паддингом]
= (i · (32 + 1) + col) mod 32         [розклад 33 = 32 + 1]
= (i · 32 + i · 1 + col) mod 32       [дистрибутивність множення]
= (i · 1 + col) mod 32                [бо (i · 32) mod 32 = 0]
= (i + col) mod 32
```

Оскільки `gcd(1, 32) = 1`, відображення `i ↦ (i + col) mod 32` є бієкцією множини `{0, ..., 31}` на саму себе для будь-якого значення `col`. Кожен потік потрапляє у свій унікальний банк:

```
k_pad = gcd(33, 32) = gcd(32 + 1, 32) = gcd(1, 32) = 1
```

Банківські конфлікти ліквідовано повністю ціною виділення 32 додаткових чисел float (128 байтів пам'яті).

### Аналіз 64-бітних типів (double, int64_t)

Якщо масив містить 64-бітні операнди (8 байтів), фізична адресація залежить від конфігурації банку:

1. **Режим 4-байтних банків (дефолтний на багатьох архітектурах):**
   Одне 64-бітне число займає два послідовні 4-байтні банки: `Банк 2i` та `Банк 2i + 1`. Звернення варпу до 32 64-бітних чисел природно розпадається на дві фази: перша фаза вибирає молодші 32 біти для всіх 32 потоків (використовуючи всі 32 банки), а друга фаза вибирає старші 32 біти.
   Якщо ж доступ виконується з кроком `S = 2`, молодші біти всіх потоків потрапляють лише в парні банки (0, 2, 4, ..., 30), генеруючи 2-кратний конфлікт на кожній фазі.

2. **Режим 8-байтних банків (налаштовується через `cudaDeviceSetSharedMemConfig`):**
   Кожен банк має ширину 8 байтів. Формула номера банку набуває вигляду:
   ```
   B₆₄(i) = (Address(i) / 8 байтів) mod 32 = (i · S₆₄) mod 32
   ```
   У цьому режимі 32 потоки зчитують 32 64-бітні числа за 1 такт, якщо `gcd(S₆₄, 32) = 1`. Проте 32-бітні операнди (float) у цьому режимі ділять кожне 8-байтне слово між двома сусідніми числами, що вимагає вирівнювання на парні/непарні позиції для уникнення внутрішньобанкових конфліктів.

### Доведення коректності XOR-свізлінгу (Swizzling)

Якщо обсяг спільної пам'яті жорстко обмежений і витрачати байти на паддинг неприпустимо, застосовують бітове перемішування адрес — **XOR-свізлінг** (англ. *swizzling*).

Визначимо номер стовпця у двовимірному масиві через операцію побітового виключального АБО (XOR, позначення `⊕`):

```
col_swizzled = col ⊕ (row mod 32)
```

Розглянемо властивості цього відображення над полем Галуа `GF(2)⁵`:
1. **Запис рядка (фіксований `row`, змінний `col = i`):**
   Функція `f_{row}(i) = i ⊕ row` є лінійним бієктивним оператором над 5-бітними векторами. Для будь-яких `i₁ ≠ i₂` маємо `i₁ ⊕ row ≠ i₂ ⊕ row`. Отже, всі 32 потоки записують дані в 32 різні банки за 1 такт.
2. **Зчитування стовпця (фіксований `col`, змінний `row = i`):**
   Функція `g_{col}(i) = col ⊕ i` також є бієкцією над множиною `{0, ..., 31}`. При зміні `i` від 0 до 31 значення `g_{col}(i)` пробігає всі 32 унікальні номери банків без повторень.

Таким чином, XOR-свізлінг математично гарантує відсутність банківських конфліктів як при читанні, так і при записі, зберігаючи розмір масиву строго рівним `32 × 32` без жодного байта зайвої пам'яті.
