# 📋 Інтерфейси керування SMT, планування та топології в Linux

Операційна система Linux та апаратна архітектура x86-64 надають розробникам і системним адміністраторам багаторівневий комплекс програмних інтерфейсів для діагностики топології процесора, динамічного конфігурування апаратної багатопотоковості та забезпечення ізоляції обчислювальних задач:

1. **Інтерфейс системної файлової системи `sysfs`:** глобальний контроль за статусом SMT у системі, динамічне відключення та підключення логічних процесорів без перезавантаження (механізм CPU Hotplug), а також аналіз взаємного розташування ядер на кремнієвому кристалі.
2. **Системні виклики ядра для керування плануванням та безпекою:** механізм Core Scheduling (`prctl`) для створення ізольованих доменів довіри між контейнерами чи віртуальними машинами, а також функції маніпулювання масками спорідненості ниток (`sched_setaffinity` та `sched_getaffinity`).
3. **Апаратна інструкція CPUID:** пряме опитування внутрішніх регістрів мікропроцесора для низькорівневого визначення кількості фізичних ядер, логічних ниток та бітових масок APIC ID.

---

### 1. Системний інтерфейс sysfs для підсистеми SMT

Керування глобальним станом апаратної багатонитковості зосереджено в каталозі `/sys/devices/system/cpu/smt/`. Цей вузол надає уніфікований інтерфейс до внутрішнього стану ядра операційної системи, дозволяючи перевіряти наявність апаратної підтримки технології та оперативно регулювати кількість активних ниток.

| Шлях файлу | Режим доступу | Опис та семантика значень |
| :--- | :--- | :--- |
| `/sys/devices/system/cpu/smt/control` | Читання / Запис | Стан та керування технологією SMT у системі:<br>• `on` — SMT увімкнено для всіх ядер процесора.<br>• `off` — SMT вимкнено (лише перший логічний процесор на кожному ядрі активний, решта переведені у стан offline).<br>• `forceoff` — SMT примусово деактивовано параметром завантаження ядра (`nosmt=force`) без можливості подальшого динамічного увімкнення.<br>• `notsupported` — апаратна підтримка SMT відсутня на цьому процесорі.<br>• `notimplemented` — архітектура платформи не реалізує динамічне керування станом SMT. |
| `/sys/devices/system/cpu/smt/active` | Лише читання | Числовий стан: `1` — SMT наразі активний (наявні фізичні ядра з більш ніж одним активним логічним процесором), `0` — SMT неактивний. |

#### Механізм динамічного відключення логічних процесорів (CPU Hotplug)

Коли записом значення `off` у файл `smt/control` адміністратор вимикає технологію SMT, ядро Linux запускає процедуру CPU Hotplug для кожного вторинного логічного процесора. Процедура виведення нитки з експлуатації включає такі кроки:

1. **Міграція завдань:** планувальник блокує чергу виконання цільового логічного процесора та переносить усі активні користувацькі потоки на активні первинні ядра.
2. **Перенаправлення апаратних переривань (IRQ):** підсистема обробки переривань переписує таблиці маршрутизації контролера переривань IO-APIC або MSI-X, гарантуючи, що апаратні події не надходитимуть до вимкненого процесора.
3. **Зупинка ядра:** цільовий процесор виконує інструкцію глибокого сну (`MWAIT` або `HLT`) з низьким споживанням енергії. Фізичне ядро перемикається в однопотоковий режим, автоматично віддаючи всі 100% буферів вибірки, записів ROB та черг виконання єдиній активній первинній нитці.

#### Інспекція топології через `/sys/devices/system/cpu/cpuX/topology/`

Для кожного логічного процесора `cpuX` у системі створюється каталог з атрибутами розміщення на кристалі:

| Атрибут топології | Формат виводу | Практичне призначення |
| :--- | :--- | :--- |
| `thread_siblings_list` | Рядок діапазонів (напр. `0,4` або `0-1`) | Список усіх логічних процесорів (SMT-ниток), що ділять одне й те саме фізичне ядро з `cpuX`. Використовується для виявлення SMT-двійників. |
| `core_cpus_list` | Рядок діапазонів | Сучасний синонім `thread_siblings_list` у версіях Linux 5.15+. |
| `package_cpus_list` | Рядок діапазонів (напр. `0-15`) | Усі логічні процесори, розташовані в межах одного фізичного сокета (пакета). |
| `core_id` | Ціле десяткове число | Унікальний номер фізичного ядра всередині сокета. Два CPU з однаковим `core_id` та `physical_package_id` є SMT-двійниками. |
| `physical_package_id` | Ціле десяткове число | Ідентифікатор фізичного сокета або процесорного сокета на материнській платі. |

### 2. Системний виклик prctl: Механізм Core Scheduling

Механізм Core Scheduling (впроваджений у ядрі Linux 5.14) розв'язує фундаментальну проблему безпеки SMT у багатокористувацьких та хмарних середовищах. Замість повного відключення SMT (яке веде до втрати 20–30% обчислювальної ємності сервера), Core Scheduling гарантує, що взаємно недовірені завдання ніколи не виконуватимуться одночасно на споріднених логічних процесорах одного фізичного ядра.

Кожен процес або нитка може отримати унікальну мітку довіри — 64-бітне число (англ. *cookie*). Планувальник операційної системи суворо дотримується правила: два завдання можуть одночасно займати SMT-нитки одного ядра лише тоді, коли їхні cookies повністю збігаються. Якщо для зайнятого ядра немає іншої задачі з тим самим cookie, другий логічний процесор примусово зупиняється й виконує фіктивну нитку простою (idle), блокуючи витоки через побічні канали PortSmash, L1TF та MDS.

#### Внутрішні накладні витрати Core Scheduling

Реалізація Core Scheduling змінює алгоритм вибору наступного завдання (`pick_next_task`) у планувальнику Linux. У класичному планувальнику CFS/EEVDF кожне логічне ядро обирає процес зі своєї локальної черги виконання за час `O(1)` або `O(log N)`. У режимі Core Scheduling планувальники двох SMT-ниток одного фізичного ядра змушені координувати свій вибір через міжпроцесорні переривання (IPI) або блокування спільної структури ядра `core_rq`.

Коли Нитка 0 планує запустити процес із міткою `Cookie A`, вона перевіряє стан Нитки 1. Якщо на Нитці 1 крутиться процес із міткою `Cookie B`, ядро надсилає сигнал негайного перепланування. Якщо відповідного процесу з міткою `Cookie A` для Нитки 1 не знайдено, вона примусово переводиться у стан примусового простою (force-idle). Це створює накладні витрати на синхронізацію, які для типових навантажень становлять від 2% до 8% продуктивності, що є прийнятною ціною за повну апаратну ізоляцію без фізичного відключення SMT.

#### Сигнатура та параметри системного виклику

Системний виклик `prctl` використовує константу `PR_SCHED_CORE` (числове значення `62`):

| Параметр виклику | Можливі значення | Опис операції |
| :--- | :--- | :--- |
| `option` | `PR_SCHED_CORE` (`62`) | Вибір підсистеми Core Scheduling ядра Linux. |
| `arg2` (команда операції) | `PR_SCHED_CORE_GET` (`0`) | Отримати 64-бітне значення поточного cookie цільового процесу. |
| | `PR_SCHED_CORE_CREATE` (`1`) | Згенерувати новий унікальний домен довіри (новий cookie) для процесу. |
| | `PR_SCHED_CORE_SHARE_TO` (`2`) | Скопіювати cookie поточного процесу цільовому процесу (`arg3`). |
| | `PR_SCHED_CORE_SHARE_FROM` (`3`)| Отримати й встановити cookie від іншого процесу (`arg3`). |
| `arg3` (ідентифікатор PID) | `pid_t` або `0` | Ідентифікатор цільового процесу або нитки (`0` — викликаючий потік). |
| `arg4` (тип області дії) | `PIDTYPE_PID` (`0`) | Застосувати дію виключно до вказаної нитки. |
| | `PIDTYPE_TGID` (`1`) | Застосувати дію до всієї групи ниток процесу (Thread Group ID). |
| | `PIDTYPE_PGID` (`2`) | Застосувати дію до всієї групи процесів сесії (Process Group ID). |
| `arg5` (буфер виводу) | `uint64_t *` | Покажчик на 64-бітну змінну пам'яті (використовується виключно для команди `PR_SCHED_CORE_GET`). |

#### Коди помилок prctl(PR_SCHED_CORE)

| Код помилки | Причина виникнення |
| :--- | :--- |
| `EINVAL` | Передано невідому команду або ядро Linux зібрано без конфігураційного прапорця `CONFIG_SCHED_CORE=y`. |
| `ENODEV` | На системі відсутня підтримка SMT (Core Scheduling деактивовано, оскільки кожне ядро має лише одну нитку). |
| `EPERM` | Брак привілеїв `PTRACE_MODE_READ_REALCREDS` для читання чи модифікації мітки довіри стороннього процесу. |
| `ESRCH` | Процес або нитку з переданим ідентифікатором PID не знайдено в таблиці процесів ядра. |

### 3. Програмне керування Core Scheduling

Нижче наведено робочий приклад коду, що створює новий ізольований домен довіри для поточної групи процесів.

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdint.h>
#include <errno.h>
#include <string.h>
#include <sys/prctl.h>
#include <unistd.h>

#ifndef PR_SCHED_CORE
#define PR_SCHED_CORE 62
#define PR_SCHED_CORE_GET 0
#define PR_SCHED_CORE_CREATE 1
#define PIDTYPE_PID 0
#define PIDTYPE_TGID 1
#endif

int enable_core_scheduling_isolation(void) {
    /* Створюємо новий унікальний домен довіри для всієї групи ниток */
    int res = prctl(PR_SCHED_CORE, PR_SCHED_CORE_CREATE, 0, PIDTYPE_TGID, 0);
    if (res < 0) {
        if (errno == ENODEV) {
            fprintf(stderr, "SMT неактивний або ядра не підтримують SMT\n");
            return 0;
        }
        fprintf(stderr, "Помилка prctl(PR_SCHED_CORE_CREATE): %s\n", strerror(errno));
        return -1;
    }

    uint64_t cookie = 0;
    res = prctl(PR_SCHED_CORE, PR_SCHED_CORE_GET, 0, PIDTYPE_PID, (unsigned long)&cookie);
    if (res == 0) {
        printf("Core Scheduling активовано успішно. Cookie домену довіри: 0x%lx\n", cookie);
    }
    return 0;
}

int main(void) {
    return enable_core_scheduling_isolation();
}
```
```cpp
#include <iostream>
#include <cstdint>
#include <cstring>
#include <cerrno>
#include <expected>
#include <format>
#include <sys/prctl.h>
#include <unistd.h>

#ifndef PR_SCHED_CORE
#define PR_SCHED_CORE 62
#define PR_SCHED_CORE_GET 0
#define PR_SCHED_CORE_CREATE 1
#define PIDTYPE_PID 0
#define PIDTYPE_TGID 1
#endif

namespace core_sched {

enum class SchedError {
    NoSmtSupport,
    PermissionDenied,
    KernelNotSupported,
    UnknownError
};

std::expected<uint64_t, SchedError> create_trust_domain() {
    int res = prctl(PR_SCHED_CORE, PR_SCHED_CORE_CREATE, 0, PIDTYPE_TGID, 0);
    if (res < 0) {
        if (errno == ENODEV) {
            return std::unexpected(SchedError::NoSmtSupport);
        }
        if (errno == EPERM) {
            return std::unexpected(SchedError::PermissionDenied);
        }
        if (errno == EINVAL) {
            return std::unexpected(SchedError::KernelNotSupported);
        }
        return std::unexpected(SchedError::UnknownError);
    }

    uint64_t cookie{0};
    res = prctl(PR_SCHED_CORE, PR_SCHED_CORE_GET, 0, PIDTYPE_PID, reinterpret_cast<unsigned long>(&cookie));
    if (res < 0) {
        return std::unexpected(SchedError::UnknownError);
    }

    return cookie;
}

} // namespace core_sched

int main() {
    auto result = core_sched::create_trust_domain();
    if (result.has_value()) {
        std::cout << "Core Scheduling активовано успішно. Cookie: 0x"
                  << std::hex << result.value() << std::dec << '\n';
        return 0;
    }

    switch (result.error()) {
        case core_sched::SchedError::NoSmtSupport:
            std::cerr << "SMT не підтримується процесором або вимкнено в BIOS/sysfs\n";
            break;
        case core_sched::SchedError::PermissionDenied:
            std::cerr << "Брак прав для зміни параметрів планування\n";
            break;
        case core_sched::SchedError::KernelNotSupported:
            std::cerr << "Ядро Linux зібрано без CONFIG_SCHED_CORE\n";
            break;
        case core_sched::SchedError::UnknownError:
            std::cerr << "Невідома системна помилка при виклику prctl\n";
            break;
    }
    return 1;
}
```

### 4. Низькорівневе виявлення SMT через інструкцію CPUID

На апаратному рівні архітектури x86-64 операційна система та діагностичні утиліти з'ясовують топологію кристала за допомогою інструкції `CPUID`.

#### Основні листки CPUID для аналізу багатопотоковості:

1. **Листок 0x01 (Базова інформація про можливості процесора):**
   - **Регістр `EDX`, біт 28 (`HTT` — *Hyper-Threading Technology*):** значення `1` вказує, що процесор підтримує роботу кількох логічних ядер на кристал.
   - **Регістр `EBX`, біти [23:16]:** максимальна кількість логічних процесорів у поточному фізичному сокеті.

2. **Листок 0x0B та Листок 0x1F (Extended Topology Enumeration):**
   Сучасний стандарт Intel та AMD для опису складних багаторівневих ієрархій (SMT, Cores, Modules, Tiles, Packages).
   - Вхідний параметр `ECX` визначає рівень топології (англ. *Sub-leaf*):
     - `ECX = 0` — рівень SMT (Hyper-Threading).
     - `ECX = 1` — рівень фізичного ядра (Core Level).
     - `ECX = 2` — рівень модуля або кристала (Die / Tile Level).
   - При `ECX = 0` вихідні регістри містять:
     - `EAX[4:0]` — кількість бітів зсуву x2APIC ID, необхідна для отримання ідентифікатора фізичного ядра. Для SMT2 це значення дорівнює `1` (один біт кодує номер логічної нитки всередині ядра).
     - `EBX[15:0]` — кількість логічних процесорів на цьому рівні (зазвичай `2` для SMT2 або `4` для SMT4).
     - `ECX[15:8]` — тип рівня (значення `1` позначає рівень SMT).
     - `EDX` — повний 32-бітний x2APIC ID поточного логічного процесора.

За допомогою комбінації бітових зсувів `EAX[4:0]` ядра операційної системи миттєво будують карту відповідності між номерами логічних процесорів `cpu0..cpuN` та їхнім фізичним розташуванням на кремнієвому кристалі.
