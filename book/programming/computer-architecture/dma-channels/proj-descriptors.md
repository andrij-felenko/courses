# ⚙️ Дескриптори зв'язаним списком: scatter-gather своїми словами

DMA-каналу передають дескриптор із вказівкою «звідки, куди, скільки». Але реальна передача рідко є одним суцільним шматком пам'яті. Як одним запуском DMA зібрати кадр із розкиданих по RAM частин — і не будити ядро між ними? Відповідь у тому, що дескриптор — не одна структура, а вузол списку, який апаратура обходить сама.

## Задача

DMA народився з ідеї «вивільнити ядро від монотонного копіювання»: окремий [контролер DMA](topic:programming/dma-controller) ганяє байти замість процесора. Але є підступна ситуація: дані, які треба відправити одним потоком, лежать у RAM не підряд. Уявіть типовий кадр: заголовок (header) живе в одному буфері, корисне навантаження — в іншому, контрольний хвіст (CRC або checksum) — у третьому. Три окремі шматки пам'яті; один суцільний потік на виході.

Перше наївне рішення — зібрати все в один великий буфер копіюванням, а потім запустити DMA одним разом. Але ж саме від копіювання DMA нас рятував! Витрачати такти ядра на склейку, щоб потім красиво їх «вивільнити» для передачі — іронія без жодного виграшу.

Друге наївне рішення — запускати DMA тричі: окремо для заголовка, окремо для тіла, окремо для хвоста. Між кожним запуском канал підіймає переривання, ядро прокидається, переналаштовує канал і запускає знову. Три переривання замість одного, тричі зайнятий планувальник — і знову втрачається той спокій, заради якого ми взагалі взяли DMA.

Мета вставки: показати, як один старт каналу змушує апаратуру пройти всі шматки підряд і підняти одне переривання в кінці. Механізм називається «розкидати-зібрати» (*scatter-gather*), а будівельний блок — «дескриптор» (*descriptor*).

## Ідея: дескриптор — це вузол однозв'язного списку

Замість щоразу вказувати DMA-контролеру «ось адреса, ось довжина» вручну, ми описуємо кожен шматок невеликою структурою в RAM — дескриптором. Структура містить: вказівник `buf` (куди або звідки дані), поля `length` і `size` (скільки передати і яка місткість слота), набір бітів-прапорців — і головне — поле `next`, що є адресою наступного дескриптора.

Поле `next` зшиває дескриптори в ланцюг — однозв'язний список у RAM.

![Три дескриптори в RAM, зчеплені полем next у ланцюг: вузол hdr → вузол body → вузол crc. Поле buf кожного вузла дивиться на свій розкиданий буфер у пам'яті; останній вузол має eof=1 і next=0. Контролеру передають лише адресу першого вузла, решту він обходить сам.](img/descriptor-chain.svg)

*Дескриптори як вузли однозв'язного списку в RAM: поле next зшиває їх у ланцюг, поле buf вказує на розкидані шматки даних, останній вузол обриває ланцюг і піднімає одне переривання. Контролеру дають адресу лише першого вузла.*

Ми передаємо контролеру адресу лише першого дескриптора. Закінчивши шматок, апаратура сама читає поле `next`, переходить до наступного вузла й тягне буфер, на який він вказує — і так доти, поки `next` не виявиться NULL або поки не натрапить на прапорець «кінець». Ядро не торкається шини між шматками. Якщо ви писали програмний однозв'язний список із обходом по `next`, то тут та сама ідея — тільки «ітератор» залізний, а не рядок коду.

**Прапорець власника (owner-біт).** Кожен вузол має один біт, що позначає, хто зараз «володіє» дескриптором. Значення «1» означає: цей вузол належить апаратурі, вона зараз обробляє його буфер. Значення «0» — вузол повернуто CPU, можна читати або перезаписувати. CPU виставляє «передаю DMA» перед стартом; апаратура скидає назад після завершення. Це той самий контракт «один господар у момент часу», що й у дисципліні власності при роботі з [перериваннями](topic:programming/interrupts) — лише замість програмних покажчиків тут апаратний біт.

**Прапорець кінця кадру (eof).** Один біт на останньому вузлі каже: «це фінальний шматок — тут підіймай переривання». Завдяки цьому одне переривання надходить після всього кадру, а не після кожного шматка.

## Структура дескриптора в C

```c
// Дескриптор DMA для ESP32-класу (форма апаратного GDMA).
// Лежить у звичайній RAM; апаратура читає його як є — тому
// розкладка полів і вирівнювання фіксовані, не змінюй їх.
typedef struct dma_desc_s {
    uint32_t size    : 12;  // місткість буфера, байтів (кратна, з вирівнюванням)
    uint32_t length  : 12;  // скільки байтів реально передати з цього буфера
    uint32_t rsv     : 6;   // зарезервовано
    uint32_t eof     : 1;   // 1 = останній шматок: підняти переривання
    uint32_t owner   : 1;   // 1 = власник DMA (зайнято), 0 = власник CPU
    uint8_t  *buf;          // адреса даних цього шматка
    struct dma_desc_s *next; // наступний вузол; NULL = кінець ланцюга
} dma_desc_t;
```

Перше 32-бітне слово містить усі прапорці й лічильники у вигляді бітових полів: апаратура читає його цілком за один шинний транзакт, не розбираючи байти окремо. Поля `buf` і `next` — повноцінні машинні слова-покажчики, окремі від заголовка. Структура мусить лежати в RAM, до якої DMA має фізичний доступ — окрема морока з [кешем та вирівнюванням](topic:programming/dma-cache-races); тут лише застереження.

## Збираємо ланцюг і запускаємо

**Приклад (кадр із трьох розкиданих буферів).**
Три буфери (`hdr`, `body`, `crc`) живуть у різних місцях RAM. Завдання: зібрати з них scatter-gather ланцюг і передати одним запуском каналу.

```c
static dma_desc_t desc[3];   // масив вузлів живе доки триває передача

void send_frame(uint8_t *hdr, uint32_t hlen,
                uint8_t *body, uint32_t blen,
                uint8_t *crc,  uint32_t clen)
{
    // 1) описати кожен розкиданий шматок окремим вузлом
    desc[0] = (dma_desc_t){ .buf = hdr,  .length = hlen, .size = hlen,
                            .owner = 1, .eof = 0, .next = &desc[1] };
    desc[1] = (dma_desc_t){ .buf = body, .length = blen, .size = blen,
                            .owner = 1, .eof = 0, .next = &desc[2] };
    // 2) останній вузол: eof=1 (тут переривання), next=NULL — кінець
    desc[2] = (dma_desc_t){ .buf = crc,  .length = clen, .size = clen,
                            .owner = 1, .eof = 1, .next = NULL };

    // 3) один старт: даємо лише адресу ПЕРШОГО вузла; решту апаратура
    //    обійде сама по полю next, доки не зустріне eof
    dma_start(SOME_CHANNEL, &desc[0]);
    // ядро вільне; одне переривання прийде після crc, не між шматками
}
```

Один виклик `dma_start` — і апаратура передає `hdr`, `body`, `crc` підряд без копіювання в спільний буфер і без пробудження ядра між шматками. «Зібрати розкидане» обійшлося CPU лише часом, витраченим на заповнення трьох невеликих структур — а не часом власне копіювання даних.

![Два шляхи зібрати кадр із трьох розкиданих буферів. Ліворуч наївний: ядро спершу копіює hdr, body, crc в один великий буфер, і лише потім запускає DMA одним блоком — такти CPU витрачені на склейку. Праворуч scatter-gather: три дескриптори зчеплені по next, DMA сама обходить їх і виливає один потік без копіювання й без пробудження ядра між шматками.](img/sg-vs-naive.svg)

*Наївний шлях (склеїти все в один буфер копіюванням, потім один DMA) проти scatter-gather (DMA сама збирає розкидане по ланцюгу дескрипторів). Список вузлів позбавляє і від зайвого копіювання, і від пробудження ядра між шматками.*

## Варіація: ланцюг, що замикається в кільце

Якщо в останнього вузла поле `next` вказує не на NULL, а назад на перший вузол, ланцюг стає нескінченним кільцем: апаратура крутить його безперервно, передаючи потік без зупинок. [Подвійна буферизація і ping-pong](topic:programming/double-buffering) — окремий випадок такого замкненого ланцюга рівно з двох вузлів: поки DMA опрацьовує один, CPU заповнює інший. Тут важливо побачити, що однозв'язний список дескрипторів є основою й для цієї схеми.

## Складність і пастки на МК

- **Дескриптор мусить пережити передачу.** Якщо `desc[]` оголошено локально на стеку функції — масив зникне щойно функція поверне керування, а DMA ще читатиме поле `next` із вже неіснуючого стека. Тримайте вузли в `static` або глобальній пам'яті — той самий принцип «час життя», що й у програмних зв'язаних списках.

- **`next` — фізична адреса в RAM, не індекс.** Апаратура нічого не знає про ваш масив; вона читає покажчик і переходить за ним. NULL (або прапорець `eof`) — єдиний сигнал «зупинись»; якщо забули обірвати ланцюг — DMA побіжить по будь-якій пам'яті, на яку вкаже сміттєвий `next`.

- **`length ≤ size`, обидва нерідко мають бути вирівняні або кратні чомусь.** Контролер передає рівно `length` байтів, але сам слот у пам'яті може вимагати кратного розміру для коректного доступу — це частина ширшої мороки з [вирівнюванням під DMA](topic:programming/dma-cache-races). Перевіряйте обмеження конкретного блоку GDMA перед тим, як виставляти довільні розміри.

- **Owner-біт — рукостискання, а не формальність.** Виставили «власник CPU» і одразу читаєте буфер, поки апаратура ще пише туди — гонка. Перевіряйте та очікуйте повернення власності так, як вимагає документація контролера.

- **Рівно один eof на логічний кадр.** Кілька вузлів із `eof=1` — кілька переривань, і обробник не знатиме, яке є справжнім кінцем. Жодного `eof` — ядро не дізнається про завершення передачі взагалі (або канал просто зупиниться без сигналу, залежно від реалізації).

- **Спершу дані, потім `owner=DMA`.** Заповніть буфер і всі поля дескриптора — і лише останнім виставте `owner=1`, передаючи власність апаратурі. Той самий принцип «публікуй останнім», що рятує від [гонок при спільному доступі](topic:programming/atomicity-races): якщо виставити `owner` першим, DMA може схопити недописаний буфер.

## Підсумок

Дескриптор — вузол однозв'язного списку в RAM із полями `buf`, `length`, прапорцями й `next`; scatter-gather — апаратний обхід цього списку по `next`. Один виклик `dma_start` із адресою першого вузла — і апаратура сама збирає розкидані шматки в один потік, будячи ядро лише раз (на `eof`). Та сама ідея «список + обхід next», що в програмуванні, тільки ітератор залізний. Замкнувши `next` назад на перший вузол, дістаємо основу для нескінченних потокових і [ping-pong передач](topic:programming/double-buffering).
