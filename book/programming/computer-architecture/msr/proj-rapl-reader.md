# ⚙️ Читання MSR у Linux: вимірювання енергоспоживання CPU через RAPL

Пряме читання моделе-залежних регістрів MSR у мікропроцесорах архітектури x86 за замовчуванням є строго привілейованою операцією. Апаратна інструкція `RDMSR` заблокована на рівні користувача (Ring 3) і при спробі виконання неминуче генерує виняток загального захисту `#GP(0)`. Проте для діагностичних системних утиліт, високоточних інструментів профілювання продуктивності та моніторингу серверних ферм операційна система Linux надає штатні ворота прямого доступу — символьні файли пристроїв `/dev/cpu/<cpu_id>/msr`, які обслуговуються стандартним модулем ядра `msr.ko`.

Звертання до такого пристрою через системний виклик `pread()` дозволяє зчитувати довільний 64-бітний MSR безпосередньо з коду простору користувача: позиція файлового зсуву (*offset*) при виклику точно відповідає 32-бітному числовому індексу цільового MSR-регістра.

Головна мета цього проєкту — побудувати практичну системну утиліту для вимірювання реального енергоспоживання та миттєвої теплової потужності процесора за допомогою апаратного інтерфейсу Intel/AMD RAPL (англ. *Running Average Power Limit*). Ми детально розберемо структуру апаратних доменів живлення процесора, дослідимо фізичну модель інтегрування енергії кремнієм, розглянемо шлях системного виклику всередині ядра Linux, розберемо числовий приклад розрахунку на реальних даних, дослідимо багатосокетні топології NUMA та порівняємо відмінності між платформами Intel та AMD, покажемо інтеграцію з хмарними системами обліку та eBPF, реалізуємо надійний код мовами C та C++ з використанням сучасних ідіом і розберемо практичні механізми обмеження потужності (Power Capping).

### Апаратні домени RAPL та їхні конфігураційні регістри

Інтерфейс RAPL, уперше представлений у мікроархітектурі Intel Sandy Bridge і згодом підтриманий процесорами AMD (починаючи з сімейства Zen 17h), розділяє енергетичну підсистему сучасного процесора на кілька незалежних апаратних доменів живлення:

1. **Package Domain (`PKG`)**: Охоплює весь процесорний кристал цілком (сокет), включно з усіма обчислювальними ядрами, кеш-пам'яттю третього рівня L3, вбудованим контролером пам'яті, системним агентом та шинами зв'язку. Поточний стан спожитої енергії цього домену фіксується в регістрі `MSR_PKG_ENERGY_STATUS` (індекс `0x00000611` на Intel та `0xC001029B` на AMD Zen).
2. **Power Plane 0 Domain (`PP0` / Cores)**: Включає в себе виключно обчислювальні ядра процесора та їхні локальні кеші L1/L2. Доступний через регістр `MSR_PP0_ENERGY_STATUS` (індекс `0x00000639` на Intel та `0xC001029A` на AMD Zen). Різниця між енергією `PKG` та `PP0` дозволяє точно оцінити енергетичні витрати кешу L3 та контролерів шини (Uncore).
3. **Power Plane 1 Domain (`PP1` / Uncore / Graphics)**: Охоплює інтегроване графічне ядро на клієнтських процесорах. Доступний через MSR `0x00000641`.
4. **DRAM Domain**: Фіксує споживання енергії модулями оперативної пам'яті, підключеними до інтегрованого контролера процесора. Доступний через регістр `MSR_DRAM_ENERGY_STATUS` (індекс `0x00000619`, переважно на серверних платформах Xeon та EPYC).
5. **Platform / PSys Domain**: Дозволяє відстежувати сумарне енергоспоживання всієї материнської плати включно з втратами у колах перетворювачів живлення VRM (MSR `0x0000065D`).

Для коректної інтерпретації сирих цілих чисел із лічильників енергії процесор надає базовий конфігураційний регістр одиниць вимірювання — `MSR_RAPL_POWER_UNIT` (індекс `0x00000606` на Intel та `0xC0010299` на AMD). Цей 64-бітний регістр складається з трьох ключових бітових полів:

- **Power Units (PU, біти [3:0])**: Показник двійкового ступеня для одиниць потужності. Базова одиниця потужності дорівнює `1 / (2^PU)` ватів (зазвичай `PU = 3`, тобто `1/8 = 0.125` Вт).
- **Energy Status Units (ESU, біти [12:8])**: Показник двійкового ступеня для одиниць накопиченої енергії. Базовий квант енергії одного відліку становить `1 / (2^ESU)` джоулів. У більшості сучасних процесорів `ESU = 16`, що відповідає ціні одного кванта `1 / 65536 ≈ 15.258789` мікроджоулів (мкДж).
- **Time Units (TU, біти [19:16])**: Показник двійкового ступеня для часових вікон усереднення лімітів потужності: `1 / (2^TU)` секунд (зазвичай `TU = 10`, тобто `1/1024 ≈ 0.976` мілісекунди).

### Фізична модель накопичення енергії в кремнії

Усередині процесорного кристала кремній не має класичних механічних або теплових ватметрів. Натомість апаратний мікроконтролер керування живленням PCU (англ. *Power Control Unit*) безперервно зчитує телеметрію з вбудованих цифрових датчиків струму, напруги та лічильників активності транзисторних блоків ядра. Апаратний інтегратор накопичує добуток струму на напругу в часі й кожні кілька сотень мікросекунд збільшує 32-бітний регістр `MSR_PKG_ENERGY_STATUS`.

Оскільки лічильник `MSR_PKG_ENERGY_STATUS` використовує лише молодші 32 біти 64-бітного MSR-регістра, максимальне число, яке він здатний зберегти, дорівнює `2^32 − 1 = 4 294 967 295` відліків. За ціни кванта `15.26` мкДж повна енергетична ємність лічильника становить близько `65 536` джоулів. Якщо сучасний серверний процесор працює під інтенсивним обчислювальним навантаженням із потужністю 250 ватів, лічильник повністю заповнюється і скидається в нуль кожні `65536 / 250 ≈ 262` секунди (трохи більше ніж чотири хвилини).

Миттєва середня потужність у ватах за інтервал спостереження розраховується за фізичною формулою:

```
P = ΔE / Δt
  = (E_now − E_prev) · (1 / 2^ESU) / (t_now − t_prev)
```

де `E_now` та `E_prev` — послідовні показники лічильника енергії, `ESU` — константа одиниці енергії з MSR `0x606`, а `t` — мітка часу з монотонного системного годинника.

Завдяки правилам модульної двійкової арифметики стандарту беззнакових цілих чисел `uint32_t`, операція віднімання `cur_energy - prev_energy` дає абсолютно точний математичний результат приросту навіть тоді, коли між двома вимірами лічильник переповнився і перейшов через нуль (за умови, що інтервал між вимірами не перевищує повного періоду переповнення лічильника).

### Числовий приклад розрахунку на реальних даних

Розгляньмо конкретний покроковий числовий приклад, отриманий на 8-ядерному процесорі під час виконання тесту множення матриць:

1. **Читання одиниць вимірювання**:
   - Зчитуємо MSR `0x606`: отримано значення `0x000A1003`.
   - Витягуємо біти [12:8]: `(0x000A1003 >> 8) & 0x1F = 0x10 = 16`.
   - Ціна кванта енергії: `energy_unit = 1 / 2^16 = 1 / 65536 ≈ 0.000015258789` Дж (15.26 мкДж).
2. **Перший замір (час t1 = 100.0000 c)**:
   - Зчитуємо MSR `0x611`: значення лічильника `E1 = 0x8A120000 = 2 316 435 456` квантів.
3. **Другий замір через одну секунду (час t2 = 101.0025 c)**:
   - Зчитуємо MSR `0x611`: значення лічильника `E2 = 0x8A535400 = 2 320 716 800` квантів.
4. **Обчислення енергії та потужності**:
   - Приріст у квантах: `ΔE_ticks = E2 − E1 = 4 281 344` відліки.
   - Витрачена енергія у джоулях: `ΔE = 4 281 344 · (1 / 65536) ≈ 65.3281` Дж.
   - Інтервал часу: `Δt = 101.0025 − 100.0000 = 1.0025` с.
   - Середня потужність процесорного сокета: `P = 65.3281 / 1.0025 ≈ 65.16` Вт.

Якщо процесор переходить у стан глибокого енергозбереження C-state (C6/C7), де більшість ядер знеструмлені, приріст за секунду впаде до `260 000` квантів, що відповідатиме потужності холостого ходу близько `3.9` Вт.

### Багатосокетні сервери та топологія NUMA

На двосокетних або чотирисокетних серверах (наприклад, платформах із двома процесорами Intel Xeon або AMD EPYC) кожен фізичний сокет має власний незалежний контролер живлення PCU та власний лічильник `MSR_PKG_ENERGY_STATUS`. Якщо прочитати `/dev/cpu/0/msr`, ми отримаємо енергію сокета 0; читання ж `/dev/cpu/64/msr` (першого логічного ядра другого сокета) поверне енергію сокета 1.

Аби правильно зібрати загальну енергетичну картину багатосокетної машини, системна утиліта повинна спочатку визначити топологію системи через файлову систему `sysfs`. Шлях `/sys/devices/system/cpu/cpuX/topology/physical_package_id` містить числовий ідентифікатор фізичного сокета для кожного логічного ядра. Програма формує список унікальних сокетів, обирає по одному «лідеру» ядра для кожного сокета (наприклад, ядро 0 для сокета 0 та ядро 32 для сокета 1) і зчитує MSR паралельно, підсумовуючи загальну споживану потужність обчислювального вузла.

### Облік енергії в хмарі: eBPF та cgroups

У сучасних хмарних середовищах Kubernetes та контейнерах Docker показники RAPL MSR є основою для систем точного обліку споживання енергії окремими мікросервісами (проєкти Kepler — Kubernetes Efficient Power Level Exporter та Scaphandre).

Оскільки MSR `MSR_PKG_ENERGY_STATUS` вимірює енергію всього процесора разом, програми розбивають це загальне число між окремими процесами за допомогою технології eBPF (англ. *Extended Berkeley Packet Filter*). Програма eBPF перехоплює перемикання контексту планувальника ядра (`sched_switch`), рахує кількість виконаних інструкцій і процесорних циклів для кожної групи контролю cgroup через лічильники PMC і пропорційно ділить витрачені джоулі RAPL між запущеними контейнерами.

### Відмінності між платформами Intel та AMD

Хоча математична модель розрахунку потужності є ідентичною для обох платформ, архітектурні адреси MSR між Intel та AMD відрізняються. Процесори AMD Zen підтримують стандартний набір лічильників RAPL через інший діапазон MSR:
- `MSR_AMD_RAPL_POWER_UNIT` — адреса `0xC0010299`;
- `MSR_AMD_CORE_ENERGY_STATUS` — адреса `0xC001029A`;
- `MSR_AMD_PKG_ENERGY_STATUS` — адреса `0xC001029B`.

Універсальні системні інструменти (як-от `turbostat` або `powertop`) перед відкриттям файлів `/dev/cpu/*/msr` спочатку викликають інструкцію `CPUID` з листком `0x0`, аналізують рядок виробника (`"GenuineIntel"` або `"AuthenticAMD"`) і динамічно вибирають відповідну таблицю адрес MSR для поточної машини.

### Як ядро Linux обслуговує /dev/cpu/*/msr під капотом

Коли користувацька програма викликає `pread(fd, &val, 8, msr_addr)` для файлу `/dev/cpu/2/msr`, усередині ядра Linux відбувається чітка послідовність низькорівневих операцій:

1. **Диспетчеризація драйвера**: Системний виклик потрапляє у функцію `msr_read()` у файлі ядра `drivers/char/msr.c`. Драйвер витягує номер цільового логічного процесора (`cpu = 2`) із дескриптора відкритого inode.
2. **Міжпроцесорне переривання IPI**: Якщо потік користувача зараз виконується на ядрі 0, а прочитати потрібно MSR ядра 2, ядро не може просто виконати інструкцію `RDMSR` на місці, оскільки багато MSR є локальними для свого ядра (*core-scope*). Ядро надсилає міжпроцесорне переривання IPI (англ. *Inter-Processor Interrupt*) цільовому ядру 2 через функцію `smp_call_function_single()`.
3. **Безпечне виконання `rdmsr_safe`**: На цільовому ядрі 2 виконується асемблерна обгортка `rdmsr_safe()`. Вона перехоплює можливий виняток `#GP(0)` через таблицю виправлення винятків ядра (Fixup Exception Table). Якщо запитаного номера MSR у поточному процесорі не існує, ядро не падає у Kernel Panic, а повертає коду користувача помилку `EIO` (I/O error).
4. **Повернення даних**: Прочитане 64-бітне значення повертається через спільну пам'ять ядра та копіюється у буфер користувача функцією `copy_to_user()`.

Цей механізм гарантує повну безпеку операційної системи, захищаючи її від збоїв при спробі читання неіснуючих або зарезервованих регістрів.

### Чому прямий MSR, а не sysfs

В операційній системі Linux існує альтернативний інтерфейс доступу до RAPL — підсистема Power Capping Framework через віртуальну файлову систему `/sys/class/powercap/intel-rapl/`. Проте для високочастотного моніторингу та інструментів низькорівневого профілювання пряме читання MSR через `/dev/cpu/*/msr` має вирішальні переваги:

1. **Мінімальний оверхед системних викликів**: Читання з `sysfs` вимагає парсингу текстових ASCII-рядків, динамічного виділення пам'яті в ядрі та конвертації тексту у числа функцією `kstrtoul()`. Читання з `/dev/cpu/X/msr` через `pread()` — це пряма передача 8 бінарних байтів із пам'яті ядра без жодного парсингу, що зменшує затримку виклику з кількох мікросекунд до сотень наносекунд.
2. **Точна прив'язка до сокета та ядра**: При роботі з багатосокетними серверами (NUMA) драйвер `/dev/cpu/<cpu_id>/msr` гарантує виконання інструкції `RDMSR` саме на тому фізичному ядрі, яке відповідає переданому дескриптору.
3. **Універсальність між виробниками**: Інтерфейс MSR працює однаково як на чипах Intel, так і на процесорах AMD Zen, тоді як вузли в `/sys/class/powercap` можуть мати різні шляхи та назви залежно від конфігурації ядра.

### Реалізація утиліти: порівняння C та C++

Нижче наведено дві повні, функціональні реалізації програми моніторингу. Обидві версії коректно відкривають пристрій MSR, читають апаратні одиниці вимірювання, вимірюють точний монотонний час і виводять спожиту енергію у джоулях та миттєву потужність у ватах.

:::tabs
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <fcntl.h>
#include <unistd.h>
#include <time.h>
#include <math.h>
#include <errno.h>
#include <string.h>

#define MSR_RAPL_POWER_UNIT     0x00000606
#define MSR_PKG_ENERGY_STATUS   0x00000611

// Зчитування 64-бітного значення MSR через системний виклик pread
static int read_msr(int fd, uint32_t msr_addr, uint64_t *val) {
    if (pread(fd, val, sizeof(*val), (off_t)msr_addr) != sizeof(*val)) {
        return -1;
    }
    return 0;
}

// Отримання поточного монотонного часу з точністю до наносекунд
static double get_time_sec(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec * 1e-9;
}

int main(int argc, char *argv[]) {
    const char *msr_path = "/dev/cpu/0/msr";
    int fd = open(msr_path, O_RDONLY);
    if (fd < 0) {
        fprintf(stderr, "Помилка відкриття %s: %s\n", msr_path, strerror(errno));
        fprintf(stderr, "Переконайтеся, що завантажено модуль 'modprobe msr' та утиліта має права root.\n");
        return 1;
    }

    // 1. Зчитуємо конфігурацію двійкових одиниць вимірювання
    uint64_t unit_raw = 0;
    if (read_msr(fd, MSR_RAPL_POWER_UNIT, &unit_raw) < 0) {
        fprintf(stderr, "Не вдалося прочитати MSR_RAPL_POWER_UNIT: %s\n", strerror(errno));
        close(fd);
        return 1;
    }

    // Біти [12:8] визначають одиниці енергії: 1 / 2^ESU джоулів
    uint32_t esu = (uint32_t)((unit_raw >> 8) & 0x1F);
    double energy_unit_joules = 1.0 / (double)(1ULL << esu);

    printf("RAPL ініціалізовано: ціна кванта енергії = %.8f Дж (1/2^%u)\n", energy_unit_joules, esu);
    printf("Запуск циклу моніторингу сокета CPU (натисніть Ctrl+C для зупинки)...\n");

    uint64_t prev_raw = 0;
    if (read_msr(fd, MSR_PKG_ENERGY_STATUS, &prev_raw) < 0) {
        fprintf(stderr, "Помилка читання MSR_PKG_ENERGY_STATUS: %s\n", strerror(errno));
        close(fd);
        return 1;
    }

    double prev_time = get_time_sec();
    uint32_t prev_energy = (uint32_t)(prev_raw & 0xFFFFFFFF);

    while (1) {
        sleep(1);

        uint64_t cur_raw = 0;
        if (read_msr(fd, MSR_PKG_ENERGY_STATUS, &cur_raw) < 0) {
            fprintf(stderr, "Помилка читання MSR під час заміру: %s\n", strerror(errno));
            break;
        }

        double cur_time = get_time_sec();
        uint32_t cur_energy = (uint32_t)(cur_raw & 0xFFFFFFFF);

        // Беззнакова арифметика uint32_t коректно обробляє переповнення 32-бітного лічильника
        uint32_t delta_ticks = cur_energy - prev_energy;
        double delta_joules = (double)delta_ticks * energy_unit_joules;
        double delta_time = cur_time - prev_time;

        double power_watts = delta_joules / delta_time;

        printf("Інтервал: +%.3f c | Витрачено енергії: +%8.4f Дж | Потужність: %6.2f Вт\n",
               delta_time, delta_joules, power_watts);

        prev_energy = cur_energy;
        prev_time = cur_time;
    }

    close(fd);
    return 0;
}
```

```cpp
constexpr uint32_t MSR_RAPL_POWER_UNIT   = 0x00000606;
constexpr uint32_t MSR_PKG_ENERGY_STATUS = 0x00000611;

// RAII-клас для безпечного володіння файловим дескриптором пристрою MSR
class DeviceHandle {
public:
    explicit DeviceHandle(int cpu_id) {
        auto path = std::format("/dev/cpu/{}/msr", cpu_id);
        fd_ = ::open(path.c_str(), O_RDONLY);
    }

    ~DeviceHandle() {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }

    DeviceHandle(const DeviceHandle&) = delete;
    DeviceHandle& operator=(const DeviceHandle&) = delete;

    DeviceHandle(DeviceHandle&& other) noexcept : fd_(other.fd_) {
        other.fd_ = -1;
    }

    DeviceHandle& operator=(DeviceHandle&& other) noexcept {
        if (this != &other) {
            if (fd_ >= 0) ::close(fd_);
            fd_ = other.fd_;
            other.fd_ = -1;
        }
        return *this;
    }

    [[nodiscard]] bool is_valid() const noexcept { return fd_ >= 0; }

    [[nodiscard]] std::expected<uint64_t, std::string> read(uint32_t msr_addr) const {
        if (fd_ < 0) {
            return std::unexpected("Дескриптор MSR не відкрито");
        }

        uint64_t value = 0;
        if (::pread(fd_, &value, sizeof(value), static_cast<off_t>(msr_addr)) != sizeof(value)) {
            return std::unexpected(std::strerror(errno));
        }
        return value;
    }

private:
    int fd_{-1};
};

class RaplMonitor {
public:
    static std::expected<RaplMonitor, std::string> create(int cpu_id = 0) {
        DeviceHandle handle(cpu_id);
        if (!handle.is_valid()) {
            return std::unexpected(std::format(
                "Не вдалося відкрити /dev/cpu/{}/msr. Потрібні права root та модуль 'msr'.", cpu_id));
        }

        auto unit_val = handle.read(MSR_RAPL_POWER_UNIT);
        if (!unit_val) {
            return std::unexpected("Помилка читання RAPL_POWER_UNIT: " + unit_val.error());
        }

        auto esu = static_cast<uint32_t>((*unit_val >> 8) & 0x1F);
        double joules_per_tick = 1.0 / static_cast<double>(1ULL << esu);

        return RaplMonitor(std::move(handle), joules_per_tick, esu);
    }

    void run_sampling_loop(std::chrono::milliseconds interval = std::chrono::milliseconds(1000)) {
        std::cout << std::format("RAPL ініціалізовано: ціна кванта = {:.8f} Дж (1/2^{})\n",
                                  joules_per_tick_, esu_);
        std::cout << "Запуск циклу моніторингу сокета CPU (Ctrl+C для завершення)...\n";

        auto prev_sample_time = std::chrono::steady_clock::now();
        auto initial_read = dev_.read(MSR_PKG_ENERGY_STATUS);
        if (!initial_read) {
            std::cerr << "Помилка початкового зчитування MSR: " << initial_read.error() << '\n';
            return;
        }

        auto prev_energy = static_cast<uint32_t>(*initial_read & 0xFFFFFFFF);

        while (true) {
            std::this_thread::sleep_for(interval);

            auto cur_sample_time = std::chrono::steady_clock::now();
            auto cur_read = dev_.read(MSR_PKG_ENERGY_STATUS);
            if (!cur_read) {
                std::cerr << "Помилка читання MSR під час заміру: " << cur_read.error() << '\n';
                break;
            }

            auto cur_energy = static_cast<uint32_t>(*cur_read & 0xFFFFFFFF);

            // Обчислюємо приріст лічильника з урахуванням беззнакового переповнення
            uint32_t delta_ticks = cur_energy - prev_energy;
            double delta_joules = static_cast<double>(delta_ticks) * joules_per_tick_;

            std::chrono::duration<double> elapsed = cur_sample_time - prev_sample_time;
            double power_watts = delta_joules / elapsed.count();

            std::cout << std::format("Інтервал: +{:.3f} c | Витрачено енергії: +{:8.4f} Дж | Потужність: {:6.2f} Вт\n",
                                     elapsed.count(), delta_joules, power_watts);

            prev_energy = cur_energy;
            prev_sample_time = cur_sample_time;
        }
    }

private:
    RaplMonitor(DeviceHandle dev, double joules_per_tick, uint32_t esu)
        : dev_(std::move(dev)), joules_per_tick_(joules_per_tick), esu_(esu) {}

    DeviceHandle dev_;
    double joules_per_tick_{0.0};
    uint32_t esu_{0};
};

} // namespace msr

int main() {
    auto monitor_result = msr::RaplMonitor::create(0);
    if (!monitor_result) {
        std::cerr << "Помилка: " << monitor_result.error() << '\n';
        return 1;
    }

    monitor_result->run_sampling_loop();
    return 0;
}
```

### Керування лімітами потужності (Power Capping)

RAPL — це не лише пасивний монітор, а й потужний двосторонній апаратний регулятор. Запис у конфігураційний регістр `MSR_PKG_POWER_LIMIT` (індекс `0x00000610`) дозволяє адміністратору або системному демону примусово обмежити енергоспоживання всього сокета CPU.

Регістр `MSR_PKG_POWER_LIMIT` задає два незалежні ліміти потужності:

1. **Power Limit 1 (PL1 / Long Term)**: Довготривалий середній ліміт потужності, що відповідає базовому тепловому пакету TDP (англ. *Thermal Design Power*). Якщо середнє споживання за задане часове вікно перевищує цей поріг, вбудований контролер живлення PCU починає знижувати тактову частоту та напругу ядер через динамічне регулювання частоти DVFS.
2. **Power Limit 2 (PL2 / Short Term)**: Короткочасний піковий ліміт для турборежиму (Turbo Boost / Precision Boost). Дозволяє процесору споживати значно більше енергії (наприклад, 180 Вт замість базових 65 Вт) протягом коротких сплесків тривалістю від кількох мілісекунд до кількох секунд, поки температура кристала не наблизиться до критичної позначки.

Завдяки прямій зміні бітів у `MSR_PKG_POWER_LIMIT` хмарні провайдери та оператори центрів обробки даних можуть динамічно знижувати енергоспоживання серверних стійок під час пікових навантажень на мережу охолодження без перезавантаження серверів.

### Підводні камені та системні обмеження

1. **Прив'язка потоку опитування до ядра (CPU Affinity)**:
   MSR-регістри поділяються на *package-scope* (однакові для всіх ядер одного фізичного сокета) та *core-scope* (індивідуальні для кожного ядра). Регістр `MSR_PKG_ENERGY_STATUS` є спільним для всього сокета, тому його можна зчитувати через будь-яке логічне ядро цього процесора. Проте якщо ви модифікуєте код для вимірювання локального споживання ядер (`MSR_PP0_ENERGY_STATUS`) або лічильників продуктивності PMC (`IA32_PMC0`), операційна система Linux може в будь-який момент перемістити робочий потік на інше ядро під час системного виклику. Аби уникнути змішування лічильників різних ядер, потік моніторингу необхідно жорстко зафіксувати на потрібному логічному процесорі за допомогою системного виклику `sched_setaffinity()` (або `pthread_setaffinity_np()`).

2. **Вимоги до привілеїв та Kernel Lockdown**:
   Символьні файли `/dev/cpu/*/msr` за замовчуванням мають права доступу `0600` (читання й запис дозволено лише суперкористувачу `root`). Процес без прав `CAP_SYS_RAWIO` отримає системну помилку `EACCES` (Permission denied).
   
   Окрім того, у сучасних дистрибутивах Linux з активованим захистом UEFI Secure Boot ядро автоматично вмикає режим безпеки **Kernel Lockdown**. У режимі цілісності (`lockdown=integrity`) ядро повністю забороняє будь-які операції запису у файли `/dev/cpu/*/msr`, оскільки запис у чутливі MSR (наприклад, підміна вектора системного виклику `IA32_LSTAR`) дозволив би зловмиснику з правами root виконати довільний непідписаний код на рівні Ring 0. У режимі конфіденційності (`lockdown=confidentiality`) ядро додатково блокує навіть читання деяких MSR, аби запобігти витоку криптографічних ключів через побічні канали пам'яті.

3. **Квантування та частота опитування**:
   Апаратний лічильник RAPL оновлюється не безперервно, а дискретними порціями з частотою приблизно 1 кГц (раз на мілісекунду). Якщо робити заміри занадто часто (наприклад, кожні 100 мікросекунд), різниця `ΔE` у більшості вимірів дорівнюватиме нулю, чергуючись із різкими спайками, що створить значний шум квантування. Оптимальний інтервал спостереження для системних моніторів становить від 100 мілісекунд до 1 секунди.
