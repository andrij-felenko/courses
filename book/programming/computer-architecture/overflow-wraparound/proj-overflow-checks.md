# ⚙️ Ловимо переповнення в C: чому signed overflow — UB і як перевіряти ДО операції

Коли результат [переповнює](book:programming/overflow-wraparound) розрядну сітку, він тихо «перевалює» по колу, а в C/C++ знакове переповнення — це ще й **невизначена поведінка** (*undefined behavior*, UB). Звідси суто практичне питання: як цей баг **спіймати в коді** — і чому найочевидніший спосіб («додам, а потім перевірю, чи не зіпсувалося») для знакових чисел просто не працює.

## Задача: перевірити, що сума влізе

Уявімо найбуденнішу річ — складаємо два цілих, `a + b`, і хочемо бути певні, що результат не вилізе за межі типу. Якщо місця забракне, буде інакше: беззнакове тихо обнулиться, знакове перекине знак, і ніхто не попередить. Постає природне бажання поставити вартового: обчислити суму й одразу перевірити, чи вона «правильна». Саме тут на знакових типах ховається пастка, через яку тему й варто розібрати окремо.

## Ідея: на знакових — лише перевірка ДО, бо саме переповнення вже UB

Перша, наївна думка виглядає переконливо: `int y = x + 1; if (y < x) overflow();` — мовляв, якщо сума раптом стала **меншою** за доданок, отже коло «перевалило», і ми це впіймали. На беззнакових такий прийом справді працює. На **знакових** — ні, і причина глибша за просту неуважність.

![Перевірку після знакового переповнення оптимізатор стирає на компіляції](/book/programming/computer-architecture/overflow-wraparound/img/post-check-trap.svg)
*Знакове переповнення — UB, тож оптимізатор має право **припускати, що його не буває**. Звідси ланцюжок: «`x + 1` не може переповнитися → отже `y` завжди більше за `x` → отже умова `y < x` завжди хибна» — і всю перевірку викидають ще на етапі компіляції. Вартовий зникає саме тоді, коли він потрібен. Рятунок — перевіряти межу **до** операції, поки небезпечної суми ще не існує.*

Ось ключ до всієї теми. UB — це не «дасть якесь дивне число»; це дозвіл компілятору **переписати ваш код**, спираючись на припущення, що забороненого не станеться. Найковарніше тут — що на `-O0` (без оптимізації) перевірка `if (y < x)` лишається на місці й навіть «спрацьовує», тож у налагодженні все наче гаразд; а на `-O2` той самий рядок зникає, і реліз поводиться інакше за зневаджену збірку. Спіймати таке постфактум допомагають окремі інструменти — санітайзер невизначеної поведінки (`-fsanitize=undefined` у GCC/Clang) ловить знакове переповнення під час виконання, — але це діагностика, а не захист: у бойовому коді на нього не покладаються. Тому суму, яка переповнить знаковий тип, не можна навіть **обчислювати** — її треба не допустити. А отже, перевірку слід будувати так, щоб ризикованої дії в ній не виникало: переставити нерівність і звірити `a` з межею, з якої вже **відняли** `b`.

![Перевірка переповнення до додавання a + b: переставлена нерівність](/book/programming/computer-architecture/overflow-wraparound/img/pre-check-rules.svg)
*Замість «склади й подивися» питаємо заздалегідь, чи лишилося місце. Беззнаковий випадок один: `a + b` вилізе ⇔ `a > UINT_MAX − b` (різниця безпечна, бо `b ≤ UINT_MAX`). Знаковий — складніший, бо вилазить у **два** боки: додатне `b` може перебити `INT_MAX`, від'ємне — провалитися під `INT_MIN`; знак `b` і підказує, яку саме межу звіряти. Жодна з цих перевірок сама не переповнюється.*

## Готові перевірки на C

Зведімо ідею в готові перевірки. Кожна з них рахує лише **різницю межі й доданка** — дію, що завжди лишається в діапазоні, — і тому безпечна сама собою (`UINT_MAX`, `INT_MAX`, `INT_MIN` — із `<limits.h>`).

:::tabs
```cpp
// беззнакове a + b  (wrap визначений, але все одно небажаний)
if (a > UINT_MAX - b)
    overflow();              // суму НЕ рахуємо
else
    sum = a + b;

// знакове a + b  (переповнення = UB → ловимо обидві межі)
if (b > 0 && a > INT_MAX - b)      overflow();   // переб'є зверху
else if (b < 0 && a < INT_MIN - b) overflow();   // провалиться знизу
else                               sum = a + b;
```
```python
# межі 32-бітних типів (у Python int безмежний — тримаємо їх явно)
UINT_MAX = 0xFFFFFFFF
INT_MAX  = 0x7FFFFFFF
INT_MIN  = -0x80000000

# беззнакове a + b  (wrap визначений, але все одно небажаний)
if a > UINT_MAX - b:
    overflow()              # суму НЕ рахуємо
else:
    sum = a + b

# знакове a + b  (та сама переставлена нерівність → ловимо обидві межі)
if b > 0 and a > INT_MAX - b:      overflow()   # переб'є зверху
elif b < 0 and a < INT_MIN - b:    overflow()   # провалиться знизу
else:                              sum = a + b
```
:::

Той самий принцип «спершу перевір, тоді дій» переноситься й на решту операцій, тільки замість віднімання межа **ділиться** на множник. Множення небезпечніше за додавання — воно вистрілює за діапазон куди швидше, тож на ньому перевірка ДО потрібна ще частіше.

**Множимо два беззнакові `uint32_t a, b` — чи влізе добуток у 32 біти?**

:::tabs
```cpp
#include <stdint.h>
#include <limits.h>

// беззнакове a * b: добуток вилазить ⇔ a > UINT_MAX / b  (при b != 0)
uint32_t mul_checked(uint32_t a, uint32_t b, int *overflowed) {
    if (b != 0 && a > UINT_MAX / b) {   // ділення безпечне: b != 0
        *overflowed = 1;
        return 0;                       // добуток НЕ рахуємо
    }
    *overflowed = 0;
    return a * b;                       // тут уже певно влізе
}
```
```python
UINT_MAX = 0xFFFFFFFF   # стеля 32-бітного беззнакового

# беззнакове a * b: добуток вилазить ⇔ a > UINT_MAX // b  (при b != 0)
def mul_checked(a, b):
    if b != 0 and a > UINT_MAX // b:    # ділення безпечне: b != 0
        return True, 0                  # (overflowed, добуток НЕ рахуємо)
    return False, a * b                 # тут уже певно влізе
```
:::

Логіка та сама, що з додаванням, лише дзеркальна: якщо `a` більше за «скільки разів `b` влазить у стелю» (`UINT_MAX / b`), то `a * b` стелю перебило б. Ділення нічим не ризикує — воно тільки зменшує число; випадок `b == 0` відкидаємо окремо, бо ділити на нуль не можна (а нуль і так нічого не переповнить). Для **знакового** множення та сама ідея розростається в розбір знаків обох множників і окремий нагляд за `−INT_MIN`: у [доповняльному коді](book:math/twos-complement) додатного відповідника найменшому від'ємному (для байта це неіснуючий `+128`) немає, тож просте `a == INT_MIN` перед запереченням рятує від ще одного UB.

Писати це руками щоразу втомливо, тож на практиці спершу тягнуться до готового арсеналу, а ручну перевірку лишають як універсальний запасний варіант.

![Чим ловити переповнення: від найнадійнішого до найручнішого](/book/programming/computer-architecture/overflow-wraparound/img/toolbox.svg)
*Чотири робочі підходи. **Ширший тип** (порахувати в `int64`, тоді звузити з перевіркою) — найдешевший думкою, коли запас по бітах є. **Вбудовані `__builtin_add_overflow` / `__builtin_mul_overflow`** у GCC і Clang — виконують дію й одночасно повертають `bool`, чи вилізло; це найнадійніший і найшвидший спосіб там, де ці компілятори доступні. **Беззнаковий домен** — коли wrap навмисний (лічильники, гешування, різниця часу), і покладатися на нього **можна**, бо стандарт визначає його як модуль 2ᴺ. **Ручна перевірка до** (переставлена нерівність вище) — переносна будь-куди, без розширень компілятора.*

## Складність і пастки на МК

Сама перевірка коштує копійки — одне віднімання й одне-два порівняння на гілці, що добре передбачається процесором; на тлі корисної роботи це майже непомітно. Куди важливіші пастки, специфічні для мікроконтролера, де «голий» C без страхувальних сіток трапляється найчастіше.

Перша — **цілочислове підвищення** (англ. *integer promotion* — «підвищення цілого»): у виразі типи, вужчі за `int`, спершу розширюються до `int`. Тому `uint8_t a = 200, b = 100; a + b` рахується **не** у 8 бітах — проміжна сума 300 чудово вміщається в `int`, і обрізання станеться аж при зворотному присвоєнні у `uint8_t`. Перевіряти треба той тип, у якому реально йде обчислення, а не той, що у вихідній змінній; через це перевірка для `int8_t` і для `int` буває різна, хоч код виглядає однаково.

Друга — **підступність ширшого типу** на 8/16-бітних ядрах: 64-бітна арифметика там не безкоштовна (емуляція в кілька інструкцій), тож «порахую в `int64`» інколи дорожче за акуратну перевірку у штатному слові. На потужному ядрі ширший тип — найпростіший шлях; на дрібному — зважуйте ціну.

Третя — **`size_t` і довжини**: різниця двох беззнакових `len_a − len_b` за `len_a < len_b` не стане від'ємною, а перетвориться на велетенське число, і `malloc` чи цикл `for` від такого зриваються; різницю беззнакових порівнюйте **до** віднімання (`if (len_a < len_b)`), а не після.

Четверта, особливо підступна — **тихе перетворення знакового в беззнакове при порівнянні**. Коли в одному виразі стрічаються знакове й беззнакове число однакової ширини, C мовчки тлумачить знакове як беззнакове — і `-1 < 1u` дає **хибу**, бо `-1` обертається на найбільше беззнакове. Тому `for (int i = 0; i < some_unsigned; i++)` чи `if (x - 1 >= 0u)` поводяться не так, як підказує око. Не змішуйте знаки в одному порівнянні: або обидва беззнакові, або явно зведіть типи.

І останнє — **апаратні [прапорці перенесення й переповнення](book:programming/overflow-wraparound) (C/V) у залізі є, але C їх не віддає**: дістатися до них можна лише асемблерною вставкою чи тими самими `__builtin`-обгортками, тож у переносному коді спираються саме на перевірку до операції.

> 🔧 **Навіщо це.** Винесіть три речі. Перша: **знакове переповнення в C — це UB, а не «wrap по колу»**; компілятор законно викине вашу перевірку `if (y < x)`, тому таку суму не можна навіть обчислювати — лови межу **до** дії або рахуй у ширшому/беззнаковому типі. Друга: не пишіть це щоразу руками — у GCC і Clang є `__builtin_add_overflow`/`__builtin_mul_overflow`, що роблять дію й кажуть, чи вилізло; ручна переставлена нерівність (`a > INT_MAX − b`) — надійний переносний запасний варіант. Третя, найкаверзніша на МК: пам'ятайте про **підвищення до `int`** (`uint8 + uint8` рахується в `int`!), про **різницю беззнакових** (`len_a − len_b` ніколи не від'ємна) і про **змішані знаки в порівнянні** (`-1 < 1u` хибне) — більшість тихих числових багів сидить саме тут. А в налагодженні ввімкніть `-fsanitize=undefined`: він не замінить перевірок ДО, та швидко покаже місця, де знакове переповнення взагалі трапляється.
