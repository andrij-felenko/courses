# Фільтр Блума на бітовому масиві

У сучасних розподілених базах даних, високонавантажених серверах та мережевих маршрутизаторах однією з найгостріших проблем є ціна дискового та мережевого введення-виведення. Коли користувач запитує запис за ключем (наприклад, перевірка чи заблоковано URL-адресу в браузері, чи існує користувач у базі з мільярдами рядків, або чи містить конкретний SSTable-файл на SSD потрібний первинний ключ), традиційна геш-таблиця чи B-дерево вимагають збереження всіх ключів у пам'яті. Якщо зберегти 100 мільйонів рядкових ключів довжиною по 32 байти, лише самі ключі без службових покажчиків заберуть понад 3.2 гігабайти оперативної пам'яті.

**Фільтр Блума** (*Bloom filter*, винайдений Бертоном Говардом Блумом 1970 року) докорінно змінює цей баланс. Він повністю відкидає самі ключі та зберігає лише їхній компактний двійковий відбиток у єдиному бітовому масиві. Завдяки цьому фільтр Блума дозволяє зменшити витрату пам'яті з десятків байтів на ключ до всього 10 бітів на елемент (економія пам'яті у 25–30 разів), надаючи швидку ймовірнісну відповідь про присутність ключа за `O(k)` процесорних тактів без жодного звернення до диска.

### Математичний апарат: від імовірності до розміру масиву

Фільтр Блума гарантує сувору асиметрію відповідей:
- **True Negative (100% точність):** якщо фільтр відповів «ні», ключ **гарантовано відсутній** у множині. Жодних хибнонегативних помилок (False Negatives) математично бути не може. Програма може миттєво повернути відповідь `404 Not Found` або пропустити читання важкого файлу з диска.
- **Possible Positive (контрольована ймовірність помилки):** якщо фільтр відповів «так», ключ **найімовірніше присутній**, проте існує невелика ймовірність `p` хибнопозитивного спрацьовування (*False Positive*), коли всі перевірені розряди випадково виявилися встановленими в 1 іншими раніше доданими ключами.

Виведемо математичну залежність між розміром бітового масиву `m`, кількістю елементів `n`, кількістю геш-функцій `k` та цільовим рівнем помилок `p`.

#### Покрокове виведення формули хибнопозитивного спрацьовування

1. Нехай бітовий масив має довжину `m` розрядів, і всі вони спочатку ініціалізовані нулями.
2. При додаванні елемента одна геш-функція обирає один випадковий біт з `m`. Ймовірність того, що конкретний біт **не буде обраний** цією геш-функцією, дорівнює:
```
P(не обрано 1 гешем) = 1 - 1/m
```
3. Оскільки для кожного елемента обчислюється `k` незалежних геш-функцій, ймовірність того, що конкретний біт залишиться нулем після додавання **одного** елемента, становить:
```
P(не обрано k гешами) = (1 - 1/m)^k
```
4. Після послідовного додавання `n` різних елементів у фільтр буде виконано `k · n` операцій встановлення бітів. Ймовірність того, що певний біт усе ще дорівнює 0, становить:
```
P(біт лишився 0) = (1 - 1/m)^(k · n)
```
Використовуючи чудову границю `lim_{m → ∞} (1 - 1/m)^m = 1/e = e⁻¹`, робимо заміну:
```
(1 - 1/m)^(k · n) = ((1 - 1/m)^m)^((k · n) / m) ≈ e^(-(k · n) / m)
```
5. Відповідно, ймовірність того, що випадково обраний біт виявиться встановленим в 1 (перебуває в активному стані), дорівнює:
```
P(біт дорівнює 1) = 1 - e^(-(k · n) / m)
```
6. Хибнопозитивне спрацьовування виникає тоді, коли для нового ключа, якого ніколи не було в базі, **усі `k` його геш-індексів потрапили на біти, що вже містять 1**. Оскільки вибори гешів вважаються незалежними, ймовірність `p` дорівнює добутку ймовірностей для кожного з `k` бітів:
```
p = (1 - e^(-(k · n) / m))^k
```

#### Оптимізація кількості геш-функцій `k`

Щоб знайти кількість геш-функцій `k`, яка мінімізує ймовірність помилки `p` при фіксованих `m` та `n`, прологарифмуємо вираз і знайдемо точку екстремуму через взяття похідної за `k`:
```
ln(p) = k · ln(1 - e^(-k · n / m))
```
Мінімум досягається при значенні:
```
k_opt = (m / n) · ln(2) ≈ 0.69315 · (m / n)
```
Підставивши оптимальне `k_opt` назад у формулу ймовірності помилки, отримуємо красиве співвідношення:
```
p_opt = (1 - e^(-ln(2)))^k_opt = (1 - 1/2)^k_opt = (1/2)^k_opt = 2^(-k_opt)
```
Кожна додаткова геш-функція за умови пропорційного розширення масиву вдвічі зменшує ймовірність хибнопозитивної помилки.

#### Розрахунок необхідного обсягу пам'яті `m`

Знаючи бажаний рівень помилок `p` (наприклад, `p = 0.01`, тобто 1% помилок) та очікувану кількість ключів `n`, розмір бітового масиву `m` обчислюється як:
```
m = - (n · ln(p)) / (ln(2))^2 ≈ - 1.4427 · n · ln(p)
```

Практичні співвідношення між точністю та пам'яттю:
- Для `p = 1%` (`0.01`): потрібно `m/n ≈ 9.6` бітів на ключ, `k = 7` гешів.
- Для `p = 0.1%` (`0.001`): потрібно `m/n ≈ 14.4` бітів на ключ, `k = 10` гешів.
- Для `p = 0.01%` (`0.0001`): потрібно `m/n ≈ 19.2` бітів на ключ, `k = 14` гешів.

#### Практичний числовий приклад розрахунку бюджету пам'яті

Нехай ми проєктуємо кеш-шар для бази даних із `n = 10 000 000` (10 мільйонів) записів і вимагаємо рівень хибнопозитивних спрацьовувань не більше `p = 0.01` (1%).

Обчислимо необхідні параметри:
1. Загальна кількість бітів:
   `m = - (10 000 000 · ln(0.01)) / (0.693147)² = (10 000 000 · 4.60517) / 0.480453 ≈ 95 850 584 бітів`.
2. У перерахунку на байти та мегабайти:
   `95 850 584 / 8 ≈ 11 981 323 байтів ≈ 11.43 МБ`.
3. Оптимальна кількість геш-функцій:
   `k = (95 850 584 / 10 000 000) · 0.693147 ≈ 9.585 · 0.693147 ≈ 6.64 → 7 геш-функцій`.

Порівняємо це зі збереженням ключів у геш-таблиці: 10 мільйонів ключів навіть по 16 байтів зажадали б 160 МБ пам'яті плюс щонайменше 80 МБ службових структур колізій (разом понад 240 МБ). Фільтр Блума скорочує розмір структури до 11.43 МБ, що дозволяє тримати індекс 10 мільйонів записів повністю у швидкому L3-кеші процесора.

### Подвійне гешування Кірша–Мітценмахера

Прямолінійне обчислення 7 або 10 окремих криптографічних гешів для кожного рядка створило б величезне обчислювальне навантаження на процесорні ядра.

1986 року математики Адам Кірш та Майкл Мітценмахер довели фундаментальну теорему подвійного гешування: для побудови повноцінного фільтра Блума достатньо обчислити всього **два** якісні 64-бітні геші `h₁(x)` та `h₂(x)`, а всі наступні індекси `gᵢ(x)` генерувати за простою формулою лінійної комбінації:
```
gᵢ(x) = (h₁(x) + i · h₂(x)) mod m,    де i = 0, 1, ..., k - 1
```
Математичний розподіл бітів при такій генерації залишається практично невідрізненним від використання `k` повністю незалежних функцій, але кількість звернень до тексту ключа скорочується рівно до двох проходів.

У ролі базових гешів чудово підходять швидкі некриптографічні алгоритми з відмінним лавинним ефектом (*avalanche effect*): FNV-1a, MurmurHash3 або xxHash.

### Повна реалізація мовами C та C++

Нижче наведено виробничу реалізацію фільтра Блума. Вона містить динамічний бітовий масив на 64-бітних машинних словах, 64-бітний алгоритм гешування FNV-1a з різними початковими константами сідів, автоматичний розрахунок параметрів `m` та `k` за формулами, додавання елементів та перевірку їхньої присутності.

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>
#include <math.h>

// Швидкий 64-бітний алгоритм гешування FNV-1a
static uint64_t fnv1a_64(const char *key, size_t len, uint64_t seed) {
    uint64_t hash = 0xcbf29ce484222325ULL ^ seed;
    for (size_t i = 0; i < len; ++i) {
        hash ^= (uint8_t)key[i];
        hash *= 0x100000001b3ULL;
    }
    return hash;
}

// Структура фільтра Блума
typedef struct {
    uint64_t *words;     // Масив 64-бітних машинних слів
    size_t num_bits;     // Загальна кількість бітів у фільтрі (m)
    size_t num_words;    // Кількість слів uint64_t у масиві
    size_t num_hashes;   // Кількість геш-функцій (k)
    size_t count;        // Лічильник доданих елементів (n)
} BloomFilter;

// Створення фільтра з заданою місткістю та рівнем хибнопозитивних помилок
BloomFilter* bloom_create(size_t capacity, double false_positive_rate) {
    if (capacity == 0 || false_positive_rate <= 0.0 || false_positive_rate >= 1.0) {
        return NULL;
    }

    BloomFilter *filter = (BloomFilter*)malloc(sizeof(BloomFilter));
    if (!filter) return NULL;

    // Розрахунок оптимального m: m = - (n * ln(p)) / (ln(2)^2)
    double m_calc = -((double)capacity * log(false_positive_rate)) / (log(2.0) * log(2.0));
    filter->num_bits = (size_t)ceil(m_calc);
    if (filter->num_bits < 64) filter->num_bits = 64;

    // Розрахунок оптимального k: k = (m / n) * ln(2)
    double k_calc = ((double)filter->num_bits / (double)capacity) * log(2.0);
    filter->num_hashes = (size_t)round(k_calc);
    if (filter->num_hashes < 1) filter->num_hashes = 1;

    filter->num_words = (filter->num_bits + 63) / 64;
    filter->words = (uint64_t*)calloc(filter->num_words, sizeof(uint64_t));
    if (!filter->words) {
        free(filter);
        return NULL;
    }

    filter->count = 0;
    return filter;
}

// Додавання рядкового ключа у фільтр
void bloom_add(BloomFilter *filter, const char *key, size_t len) {
    uint64_t h1 = fnv1a_64(key, len, 0);
    uint64_t h2 = fnv1a_64(key, len, 0x9e3779b97f4a7c15ULL);

    for (size_t i = 0; i < filter->num_hashes; ++i) {
        uint64_t combined_hash = h1 + i * h2;
        size_t bit_index = combined_hash % filter->num_bits;

        // Встановлення біта: word_idx = bit_index / 64, bit_offset = bit_index % 64
        size_t word_idx = bit_index >> 6;
        size_t bit_offset = bit_index & 63;
        filter->words[word_idx] |= (1ULL << bit_offset);
    }
    filter->count++;
}

// Перевірка присутності ключа у фільтрі
bool bloom_contains(const BloomFilter *filter, const char *key, size_t len) {
    uint64_t h1 = fnv1a_64(key, len, 0);
    uint64_t h2 = fnv1a_64(key, len, 0x9e3779b97f4a7c15ULL);

    for (size_t i = 0; i < filter->num_hashes; ++i) {
        uint64_t combined_hash = h1 + i * h2;
        size_t bit_index = combined_hash % filter->num_bits;

        size_t word_idx = bit_index >> 6;
        size_t bit_offset = bit_index & 63;

        // Якщо хоча б один біт дорівнює 0 — ключ гарантовано відсутній
        if ((filter->words[word_idx] & (1ULL << bit_offset)) == 0) {
            return false;
        }
    }
    // Усі біти дорівнюють 1 — ключ можливо присутній
    return true;
}

// Звільнення виділеної пам'яті
void bloom_free(BloomFilter *filter) {
    if (filter) {
        free(filter->words);
        free(filter);
    }
}
```

```cpp
#include <iostream>
#include <vector>
#include <string_view>
#include <cstdint>
#include <cstddef>
#include <cmath>
#include <span>
#include <stdexcept>

class BloomFilter {
public:
    BloomFilter(std::size_t capacity, double false_positive_rate) {
        if (capacity == 0 || false_positive_rate <= 0.0 || false_positive_rate >= 1.0) {
            throw std::invalid_argument("Некоректні параметри фільтра Блума");
        }

        const double ln2 = std::log(2.0);
        const double m_calc = - (static_cast<double>(capacity) * std::log(false_positive_rate)) / (ln2 * ln2);
        num_bits_ = std::max<std::size_t>(64, static_cast<std::size_t>(std::ceil(m_calc)));

        const double k_calc = (static_cast<double>(num_bits_) / static_cast<double>(capacity)) * ln2;
        num_hashes_ = std::max<std::size_t>(1, static_cast<std::size_t>(std::round(k_calc)));

        const std::size_t num_words = (num_bits_ + 63) / 64;
        words_.assign(num_words, 0ULL);
    }

    void add(std::string_view key) noexcept {
        const auto [h1, h2] = hash_pair(key);
        for (std::size_t i = 0; i < num_hashes_; ++i) {
            const std::size_t bit_index = (h1 + i * h2) % num_bits_;
            words_[bit_index >> 6] |= (1ULL << (bit_index & 63));
        }
        ++count_;
    }

    [[nodiscard]] bool contains(std::string_view key) const noexcept {
        const auto [h1, h2] = hash_pair(key);
        for (std::size_t i = 0; i < num_hashes_; ++i) {
            const std::size_t bit_index = (h1 + i * h2) % num_bits_;
            if ((words_[bit_index >> 6] & (1ULL << (bit_index & 63))) == 0) {
                return false; // Гарантовано відсутній
            }
        }
        return true; // Можливо присутній
    }

    [[nodiscard]] std::size_t count() const noexcept { return count_; }
    [[nodiscard]] std::size_t bit_size() const noexcept { return num_bits_; }
    [[nodiscard]] std::size_t hash_count() const noexcept { return num_hashes_; }
    [[nodiscard]] std::span<const std::uint64_t> raw_words() const noexcept { return words_; }

private:
    struct HashPair { std::uint64_t h1; std::uint64_t h2; };

    [[nodiscard]] static HashPair hash_pair(std::string_view key) noexcept {
        auto fnv1a = [](std::string_view s, std::uint64_t seed) noexcept -> std::uint64_t {
            std::uint64_t hash = 0xcbf29ce484222325ULL ^ seed;
            for (char ch : s) {
                hash ^= static_cast<std::uint8_t>(ch);
                hash *= 0x100000001b3ULL;
            }
            return hash;
        };

        return { fnv1a(key, 0), fnv1a(key, 0x9e3779b97f4a7c15ULL) };
    }

    std::size_t num_bits_{0};
    std::size_t num_hashes_{0};
    std::size_t count_{0};
    std::vector<std::uint64_t> words_;
};
```

### Операції над множинами: об'єднання та перетин через побітову логіку

Однією з найелегантніших властивостей фільтра Блума є можливість виконувати теоретико-множинні операції об'єднання (Union) та перетину (Intersection) безпосередньо над двійковими масивами без повторного аналізу вихідних елементів.

Якщо два фільтри `A` та `B` мають однакові розміри `m` та однакові параметри гешування `k`:
- **Об'єднання множин (`A ∪ B`):** обчислюється через побітове АБО між відповідними 64-бітними машинними словами:
  `words_union[i] = words_A[i] | words_B[i]`.
  Отриманий фільтр містить усі елементи з обох множин з тим самим рівнем точності, що й початкові фільтри.
- **Перетин множин (`A ∩ B`):** обчислюється через побітове І:
  `words_intersection[i] = words_A[i] & words_B[i]`.
  Рівень хибнопозитивних помилок у перетині навіть знижується, оскільки щільність встановлених одиниць зменшується.

Ця властивість робить фільтри Блума ідеальними для розподілених баз даних: вузли кластера можуть обмінюватися стиснутими бітовими масками по мережі та виконувати паралельні об'єднання запитів за лічені мікросекунди за допомогою векторних SIMD-інструкцій (наприклад, `_mm256_or_si256`).

### Серіалізація та дискове збереження фільтрів Блума

Коли база даних записує SSTable-файл на SSD, фільтр Блума зберігається у хвості файлу або в окремому метаданому блоці. При серіалізації бітового масиву виникає стандартна проблема порядку байтів ([endianness](book:programming/bits-bytes-endianness)).

Якщо фільтр створено на little-endian процесорі (x86-64 або ARM64) шляхом збереження масиву `uint64_t words[]`, на big-endian машині пряме читання масиву байтів переставить байти кожного 64-бітного слова задом наперед, змістивши всі геш-індекси та призвівши до 100% помилок.

Канонічний формат заголовка серіалізованого фільтра Блума включає:
1. Магічні байти ідентифікатора формату (`0x42 0x4C 0x4F 0x4F 0x4D` — "BLOOM");
2. Версію формату (1 байт);
3. 64-бітне беззнакове число `num_bits` (у фіксованому little-endian порядку);
4. 32-бітне беззнакове число `num_hashes` (`k`);
5. 64-бітне число `count` (кількість доданих ключів);
6. Сирий потік байтів бітового масиву довжиною `(num_bits + 7) / 8` байтів.

При завантаженні фільтра з диска система вичитує параметри та за потреби виконує побайтову конвертацію слів через інструкцію `bswap` (або `std::byteswap` у C++23), гарантуючи абсолютну переносність між серверами будь-якої архітектури. Таке двійкове збереження дозволяє миттєво піднімати фільтри в пам'ять через системний виклик `mmap` без накладних витрат на десеріалізацію.

### Векторна SIMD-оптимізація та апаратне прискорення

У критичних до латентності конвеєрах (наприклад, обробка мережевих пакетів зі швидкістю 100 Гбіт/с) послідовне зчитування `k` бітів із розгалуженнями стає вузьким місцем. Сучасні векторні інструкції (Intel AVX2, AVX-512 або ARM NEON) дозволяють перевірити всі `k` бітових індексів паралельно в межах одного векторного регістра.

Замість виконання `k` окремих операцій `test` процесор формує вектор масок і застосовує інструкцію векторного логічного І:
- Векторна інструкція `_mm256_i32gather_epi64` завантажує слова за кількома індексами одночасно;
- Векторна інструкція `_mm256_testz_si256` перевіряє, чи містить результат операції `AND` хоча б один нульовий розряд, за один машинний такт.

Це дозволяє підняти швидкість перевірки запитів до сотень мільйонів операцій на секунду на одне процесорне ядро, усуваючи накладні витрати на рівні мікроархітектури та розвантажуючи конвеєр команд.

### Експериментальна верифікація та вимірювання помилок

Для підтвердження теоретичних розрахунків корисно провести емпіричний тест на синтетичних даних. Нижче наведено приклад верифікаційного коду, який заповнює фільтр Блума 100 000 унікальними ключами, перевіряє їхню наявність (підтверджуючи повну відсутність False Negatives), а потім тестує 100 000 свідомо відсутніх ключів для вимірювання реального рівня False Positive:

:::tabs
```c
#include <stdio.h>

void run_bloom_benchmark(void) {
    size_t n = 100000;
    double target_fp = 0.01; // 1% цільова похибка
    BloomFilter *filter = bloom_create(n, target_fp);
    char key_buf[64];

    // 1. Додавання 100 000 ключів
    for (size_t i = 0; i < n; ++i) {
        snprintf(key_buf, sizeof(key_buf), "user_id_%zu_test_record", i);
        bloom_add(filter, key_buf, strlen(key_buf));
    }

    // 2. Перевірка наявних ключів (False Negative тест)
    size_t false_negatives = 0;
    for (size_t i = 0; i < n; ++i) {
        snprintf(key_buf, sizeof(key_buf), "user_id_%zu_test_record", i);
        if (!bloom_contains(filter, key_buf, strlen(key_buf))) {
            false_negatives++;
        }
    }

    // 3. Перевірка відсутніх ключів (False Positive тест)
    size_t false_positives = 0;
    for (size_t i = 0; i < n; ++i) {
        snprintf(key_buf, sizeof(key_buf), "missing_key_offset_%zu", i + n);
        if (bloom_contains(filter, key_buf, strlen(key_buf))) {
            false_positives++;
        }
    }

    printf("FN (має бути 0): %zu\n", false_negatives);
    printf("Емпіричний FP: %.4f%% (теоретичний: %.2f%%)\n",
           ((double)false_positives / (double)n) * 100.0, target_fp * 100.0);

    bloom_free(filter);
}
```

### Порівняльний аналіз альтернативних імовірнісних структур

Фільтр Блума — не єдина ймовірнісна структура для перевірки належності множині. За півстоліття з'явилися досконаліші альтернативи, кожна з яких пропонує свій інженерний компроміс:

1. **Фільтр зозулі (Cuckoo Filter, 2014):**
   Базується на гешуванні зозулі (*cuckoo hashing*). Замість розкидання одиничних бітів він зберігає короткі 8- чи 16-бітні відбитки (*fingerprints*) ключів у масиві з кількома слотами на кошик.
   - *Переваги:* нативно підтримує **видалення** ключів без збільшення обсягу пам'яті; забезпечує вищу швидкість читання (перевіряються лише 2 фіксовані кошики в пам'яті, що дає максимум 2 промахи повз кеш замість `k`); витрачає менше пам'яті при жорстких вимогах до помилок (`p < 3%`).
   - *Недоліки:* складніша логіка вставки (можливі каскадні виштовхування та збої вставки при високому коефіцієнті заповнення понад 95%).

2. **Частковий фільтр (Quotient Filter, 2011):**
   Зберігає відбитки у відкритій адресованій геш-таблиці, розбиваючи геш на частку (*quotient*) та залишок (*remainder*).
   - *Переваги:* підтримує динамічне масштабування та злиття (merge) двох фільтрів безпосередньо в пам'яті як бітових потоків без повторного гешування початкових ключів.
   - *Недоліки:* чутливий до кластеризації при переповненні таблиці.

3. **Фільтри Блума з лічильниками (Counting Bloom Filters):**
   Класичний варіант із заміною бітів на 4-бітні комірки.
   - *Переваги:* простота реалізації та перевірена стабільність.
   - *Недоліки:* 4-кратна витрата пам'яті порівняно зі звичайним фільтром Блума та фільтром зозулі.

### Інженерні пастки, модифікації та оптимізація кешу

Практичне використання фільтрів Блума в промислових системах стикається з трьома критичними архітектурними викликами:

#### 1. Неможливість видалення та лічильникові фільтри (Counting Bloom Filter)

У класичному бітовому фільтрі Блума операція видалення елемента неможлива в принципі. Якщо обнулити `k` бітів, відповідних видаленому ключу, ми неминуче пошкодимо інші ключі, чиї геші випадково поділяли ті самі бітові позиції. Після цього фільтр почне видавати помилки False Negative для наявних елементів, що порушує фундаментальний інваріант структури.

Для підтримки видалення 1998 року Фан, Цао, Алмейда та Бродер запропонували **лічильниковий фільтр Блума** (*Counting Bloom filter*, CBF). Замість одного біта на комірку виділяється невеликий лічильник (зазвичай 4 біти, значення від 0 до 15):
- При додаванні лічильники за знайденими індексами інкрементуються: `counter[idx]++`;
- При видаленні лічильники декрементуються: `counter[idx]--`;
- При перевірці перевіряється умова `counter[idx] > 0`.

Плата за видалення — збільшення обсягу пам'яті рівно в 4 рази (до 40 бітів на ключ) та ризик переповнення 4-бітного лічильника при появі аномально популярних геш-колізій.

#### 2. Проблема локальності кешу та блоковані фільтри (Blocked Bloom Filters)

У великих фільтрах Блума (наприклад, розміром 100 МБ для сховища RocksDB) `k` геш-індексів одного ключа випадково розкидані по всьому адресному простору масиву. Для перевірки одного ключа процесор змушений звернутися до 7 або 10 випадкових адрес оперативної пам'яті DRAM. Кожне таке звернення майже гарантовано спричиняє промах повз усі рівні процесорного кешу (L1, L2, L3 cache miss), додаючи до 50–100 наносекунд затримки на кожну перевірку.

Щоб подолати цей бар'єр, 2007 року Путце, Зандерс та Зінглер розробили **блоковані фільтри Блума** (*Blocked Bloom Filters* / *Cache-Sector Bloom Filters*):
- Бітовий масив розбивається на незалежні сектори, розмір кожного з яких точно дорівнює розміру однієї кеш-лінії процесора (64 байти = 512 бітів).
- Перший геш `h₁(x)` обирає номер 64-байтового сектора;
- Решта гешів обчислюються за модулем 512 і виставляють біти **виключно всередині цієї єдиної кеш-лінії**.

Завдяки цьому процесор завантажує з пам'яті лише одну кеш-лінію за одне звернення, а всі перевірки бітів виконуються локально в надшвидкому L1-кеші з використанням векторних інструкцій SIMD (AVX2 / AVX-512). Ціною такого підходу є незначне зростання рівня False Positive (на 10–15% порівняно з ідеальним фільтром), що повністю компенсується зростанням пропускної здатності в 3–5 разів.

#### 3. Деградація при переповненні множини

Якщо у фільтр, розрахований на `n = 1 000 000` ключів з рівнем помилок `p = 0.01`, продовжувати записувати дані без зміни розміру, бітовий масив почне насичуватися. Коли частка одиниць у масиві перевищить 50–60%, рівень хибнопозитивних спрацьовувань почне експоненціально зростати. При повному заповненні (всі біти дорівнюють 1) фільтр формально продовжує працювати без аварійних збоїв, але відповідає «так» на 100% запитів, повністю нівелюючи свою захисну функцію.

У виробничих системах для запобігання деградації застосовують **масштабовані фільтри Блума** (*Scalable Bloom Filters*): коли поточний фільтр заповнюється до розрахункового порогу, створюється новий шар більшого розміру з жорсткішим параметром `p`, і фільтри зв'язуються в ланцюжок.
