# ⚙️ Практикум роботи з XSAVE: опитування CPUID, конфігурація XCR0 та збереження регістрів

Цей практикум демонструє, як на системному рівні взаємодіяти з апаратним механізмом XSAVE: перевірити підтримку розширеного стану процесором і ядром операційної системи, обчислити точний розмір буфера з гарантованим вирівнюванням на 64 байти, виконати безпечне збереження регістрового контексту, декодувати бітовий заголовок `XSTATE_BV` та виявити стан окремих векторних розширень. На відміну від звичайних інструкцій процесора, помилка у вирівнюванні пам'яті або масці запиту під час роботи з XSAVE призводить не до повернення коду помилки, а до негайної генерації апаратного виключення загального захисту `#GP` (*General Protection Fault*), що аварійно зупиняє процес.

## Архітектурний задум і кроки виконання

Робота з розширеним станом у просторі користувача або в ядрі операційної системи вимагає суворого дотримання протоколу рукостискання між залізом, операційною системою та виконуваною програмою. Якщо хоча б одну ланку пропущено, виклик інструкцій збереження завершиться аварією.

Послідовність дій складається з п'яти обов'язкових кроків:

1. **Опитування CPUID Leaf 1 (перевірка OSXSAVE)**: Програма повинна переконатися, що не лише кремній процесора підтримує архітектуру XSAVE (біт `CPUID.1:ECX[26]`), але й ядро операційної системи явно активувало її в регістрі керування процесора `CR4` (біт `CPUID.1:ECX[27]`). Без активного біта `CR4.OSXSAVE` будь-яка спроба виконати інструкції `XSAVE`, `XRSTOR` чи `XGETBV` викличе виключення недійсного коду операції `#UD`.
2. **Опитування CPUID Leaf 0xD (визначення геометрії та оптимізацій)**: Визначити наявність апаратних оптимізацій конвеєра (`XSAVEOPT`, `XSAVEC`, `XSAVES`) та отримати точний розмір пам'яті, необхідний для збереження увімкнених компонентів.
3. **Зчитування маски XCR0 інструкцією XGETBV**: Отримати 64-бітну бітову маску компонентів, дозволених операційною системою для використання поточним процесом.
4. **Виділення вирівняної пам'яті (64 байти)**: Виділити блок пам'яті з адресою, кратною 64 байтам (межа кеш-лінії процесора), та повністю очистити його, аби гарантувати нульовий стан зарезервованих байтів заголовка.
5. **Виконання збереження та розбір заголовка**: Викликати асемблерну інструкцію `xsave64`, витягти 64-байтний заголовок кадру та проаналізувати бітову маску `XSTATE_BV`, яка вказує, які саме регістрові блоки (x87, SSE, AVX, AVX-512, AMX) реально містять модифіковані дані.

## Реалізація на C та C++

У наведеному нижче коді реалізовано два повноцінні підходи. У вкладці C продемонстровано класичне низькорівневе системне програмування з використанням функції `aligned_alloc`, прямих асемблерних вставок GCC/Clang та ручної перевірки бітів. У вкладці C++ реалізовано сучасний об'єктно-орієнтований підхід: виділення вирівняної пам'яті інкапсульовано в `std::unique_ptr` із власним видалячем `AlignedDeleter` за концепцією RAII, бітові маски обробляються через `std::bitset`, а помилки конфігурації генерують строго типізовані винятки.

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>
#include <cpuid.h>
#include <immintrin.h>

#define ALIGNMENT_XSAVE 64

/* Структура 64-байтного заголовка кадру XSAVE */
typedef struct {
    uint64_t xstate_bv;      /* Бітова маска збережених компонентів */
    uint64_t xcomp_bv;      /* Бітова маска стисненого формату */
    uint64_t reserved[6];   /* 48 байтів резерву (мусять бути суворо нулями) */
} __attribute__((packed)) xsave_header_t;

/* Отримання регістра XCR0 за допомогою асемблерної інструкції xgetbv */
static inline uint64_t read_xcr0(void) {
    uint32_t eax, edx;
    __asm__ volatile("xgetbv" : "=a"(eax), "=d"(edx) : "c"(0));
    return ((uint64_t)edx << 32) | eax;
}

/* Безпечна обгортка над інструкцією XSAVE64 з бар'єром пам'яті */
static inline void xsave64_state(void *buffer, uint64_t mask) {
    uint32_t eax = (uint32_t)mask;
    uint32_t edx = (uint32_t)(mask >> 32);
    __asm__ volatile(
        "xsave64 %0"
        : "+m"(*(uint8_t *)buffer)
        : "a"(eax), "d"(edx)
        : "memory"
    );
}

/* Безпечна обгортка над інструкцією XRSTOR64 */
static inline void xrstor64_state(const void *buffer, uint64_t mask) {
    uint32_t eax = (uint32_t)mask;
    uint32_t edx = (uint32_t)(mask >> 32);
    __asm__ volatile(
        "xrstor64 %0"
        :
        : "m"(*(const uint8_t *)buffer), "a"(eax), "d"(edx)
        : "memory"
    );
}

/* Перевірка підтримки XSAVE операційною системою та визначення розміру буфера */
bool detect_xsave_support(size_t *required_size, uint64_t *enabled_features) {
    uint32_t eax, ebx, ecx, edx;

    /* 1. Перевірка CPUID Leaf 1 на наявність біта OSXSAVE (ECX біт 27) */
    __cpuid(1, eax, ebx, ecx, edx);
    if (!(ecx & (1u << 27))) {
        fprintf(stderr, "Помилка: ОС або процесор не підтримують XSAVE (OSXSAVE=0)\\n");
        return false;
    }

    /* 2. Запит розміру буфера через CPUID Leaf 0xD, Subleaf 0 */
    __cpuid_count(0xD, 0, eax, ebx, ecx, edx);
    *required_size = (size_t)ebx; /* EBX повертає розмір для активного XCR0 */

    /* 3. Зчитування активної бітової маски компонентів з XCR0 */
    *enabled_features = read_xcr0();
    return true;
}

int main(void) {
    size_t buffer_size = 0;
    uint64_t xcr0_mask = 0;

    if (!detect_xsave_support(&buffer_size, &xcr0_mask)) {
        return EXIT_FAILURE;
    }

    printf("Розширений стан XSAVE успішно виявлено:\\n");
    printf("  Необхідний розмір буфера : %zu байтів\\n", buffer_size);
    printf("  Активна маска регістра XCR0: 0x%016llX\\n", (unsigned long long)xcr0_mask);

    /* Виділення динамічної пам'яті з обов'язковим вирівнюванням на 64 байти */
    uint8_t *xsave_area = (uint8_t *)aligned_alloc(ALIGNMENT_XSAVE, buffer_size);
    if (!xsave_area) {
        perror("Помилка виділення вирівняної пам'яті");
        return EXIT_FAILURE;
    }

    /* Гарантоване занулення буфера, включаючи зарезервовану зону заголовка */
    memset(xsave_area, 0, buffer_size);

    /* Виконання збереження активного контексту процесора */
    xsave64_state(xsave_area, xcr0_mask);

    /* Заголовок XSAVE розташований рівно за зсувом 512 байтів */
    xsave_header_t *hdr = (xsave_header_t *)(xsave_area + 512);
    printf("\\nАналіз збереженого кадру XSAVE:\\n");
    printf("  Маска XSTATE_BV (активні секції): 0x%016llX\\n", (unsigned long long)hdr->xstate_bv);
    printf("  Маска XCOMP_BV (формат кадру)   : 0x%016llX\\n", (unsigned long long)hdr->xcomp_bv);

    if (hdr->xstate_bv & (1ull << 0)) printf("  [+] x87 FPU стан збережено у Legacy області\\n");
    if (hdr->xstate_bv & (1ull << 1)) printf("  [+] SSE стан (XMM0-XMM15) зафіксовано\\n");
    if (hdr->xstate_bv & (1ull << 2)) printf("  [+] AVX стан (верхня половина YMM) збережено\\n");
    if (hdr->xstate_bv & (1ull << 5)) printf("  [+] AVX-512 Opmask (k0-k7) збережено\\n");
    if (hdr->xstate_bv & (1ull << 6)) printf("  [+] AVX-512 ZMM_Hi256 (верхня чверть ZMM0-15) збережено\\n");
    if (hdr->xstate_bv & (1ull << 7)) printf("  [+] AVX-512 Hi16_ZMM (повні регістри ZMM16-31) збережено\\n");
    if (hdr->xstate_bv & (1ull << 9)) printf("  [+] PKRU стан ключів захисту пам'яті збережено\\n");
    if (hdr->xstate_bv & (1ull << 17)) printf("  [+] AMX конфігурація плиток (TILECFG) активна\\n");
    if (hdr->xstate_bv & (1ull << 18)) printf("  [+] AMX дані матричних плиток (TILEDATA, 8 КБ) збережено\\n");

    free(xsave_area);
    return EXIT_SUCCESS;
}
```

```cpp
#include <iostream>
#include <memory>
#include <bitset>
#include <cstdint>
#include <cstdlib>
#include <cstring>
#include <stdexcept>
#include <cpuid.h>
#include <immintrin.h>

namespace xsave {

constexpr std::size_t Alignment = 64;

/* Структура заголовка XSAVE із гарантованим вирівнюванням */
struct alignas(64) Header {
    std::uint64_t state_bv{0};
    std::uint64_t comp_bv{0};
    std::uint64_t reserved[6]{0};
};

/* Спеціальний функтор видалення пам'яті, виділеної через std::aligned_alloc */
struct AlignedDeleter {
    void operator()(std::uint8_t* ptr) const noexcept {
        std::free(ptr);
    }
};

using BufferPtr = std::unique_ptr<std::uint8_t[], AlignedDeleter>;

class ContextManager {
public:
    ContextManager() {
        std::uint32_t eax{0}, ebx{0}, ecx{0}, edx{0};

        /* 1. Перевірка прапорця OSXSAVE у CPUID.(EAX=1):ECX[27] */
        __cpuid(1, eax, ebx, ecx, edx);
        if (!(ecx & (1u << 27))) {
            throw std::runtime_error("Процесор або ОС не підтримують XSAVE (CR4.OSXSAVE=0)");
        }

        /* 2. Запит розміру кадру для активної конфігурації у CPUID.(EAX=0xD, ECX=0) */
        __cpuid_count(0xD, 0, eax, ebx, ecx, edx);
        buffer_size_ = static_cast<std::size_t>(ebx);

        /* 3. Зчитування активної конфігурації компонентів із XCR0 */
        xcr0_mask_ = readXcr0();

        /* 4. Виділення блоку пам'яті з гарантією вирівнювання за межею 64 байти */
        auto* raw_mem = static_cast<std::uint8_t*>(std::aligned_alloc(Alignment, buffer_size_));
        if (!raw_mem) {
            throw std::bad_alloc();
        }
        buffer_.reset(raw_mem);
        std::memset(buffer_.get(), 0, buffer_size_);
    }

    void saveCurrentState() noexcept {
        const auto eax = static_cast<std::uint32_t>(xcr0_mask_);
        const auto edx = static_cast<std::uint32_t>(xcr0_mask_ >> 32);
        auto* ptr = buffer_.get();

        __asm__ volatile(
            "xsave64 %0"
            : "+m"(*ptr)
            : "a"(eax), "d"(edx)
            : "memory"
        );
    }

    void restoreState() const noexcept {
        const auto eax = static_cast<std::uint32_t>(xcr0_mask_);
        const auto edx = static_cast<std::uint32_t>(xcr0_mask_ >> 32);
        const auto* ptr = buffer_.get();

        __asm__ volatile(
            "xrstor64 %0"
            :
            : "m"(*ptr), "a"(eax), "d"(edx)
            : "memory"
        );
    }

    [[nodiscard]] const Header& getHeader() const noexcept {
        return *reinterpret_cast<const Header*>(buffer_.get() + 512);
    }

    [[nodiscard]] std::size_t size() const noexcept { return buffer_size_; }
    [[nodiscard]] std::uint64_t xcr0() const noexcept { return xcr0_mask_; }

private:
    static std::uint64_t readXcr0() noexcept {
        std::uint32_t eax{0}, edx{0};
        __asm__ volatile("xgetbv" : "=a"(eax), "=d"(edx) : "c"(0));
        return (static_cast<std::uint64_t>(edx) << 32) | eax;
    }

    std::size_t buffer_size_{0};
    std::uint64_t xcr0_mask_{0};
    BufferPtr buffer_{nullptr};
};

} // namespace xsave

int main() {
    try {
        xsave::ContextManager ctx;

        std::cout << "Ініціалізовано контекст XSAVE (C++):\\n"
                  << "  Розмір буфера : " << ctx.size() << " байтів\\n"
                  << "  Маска XCR0    : 0x" << std::hex << ctx.xcr0() << std::dec << "\\n";

        ctx.saveCurrentState();

        const auto& hdr = ctx.getHeader();
        const std::bitset<64> mask(hdr.state_bv);

        std::cout << "\\nАналіз бітової карти XSTATE_BV: 0x" << std::hex << hdr.state_bv << std::dec << "\\n";
        if (mask.test(0)) std::cout << "  - x87 FPU стан активний\\n";
        if (mask.test(1)) std::cout << "  - SSE регістри XMM зафіксовано\\n";
        if (mask.test(2)) std::cout << "  - AVX YMM_Hi128 модифіковано\\n";
        if (mask.test(5)) std::cout << "  - AVX-512 Opmask k0-k7 збережено\\n";
        if (mask.test(6)) std::cout << "  - AVX-512 ZMM_Hi256 збережено\\n";
        if (mask.test(7)) std::cout << "  - AVX-512 Hi16_ZMM збережено\\n";
        if (mask.test(9)) std::cout << "  - PKRU ключі захисту збережено\\n";
        if (mask.test(17) || mask.test(18)) std::cout << "  - AMX матричний стан збережено\\n";

    } catch (const std::exception& ex) {
        std::cerr << "Помилка роботи з XSAVE: " << ex.what() << "\\n";
        return EXIT_FAILURE;
    }

    return EXIT_SUCCESS;
}
```

## Глибокий аналіз асемблерних вставок та бар'єрів пам'яті

Під час написання коду збереження розширеного стану критично важливо розуміти семантику кожного рядка вбудованого асемблера GCC/Clang:

1. **Модифікатор операнда пам'яті `"+m"`**: У виклику `xsave64 %0` операнд передається як `"+m"(*(uint8_t *)buffer)`. Знак `+` вказує компілятору, що пам'ять за цим покажчиком одночасно і читається, і записується інструкцією процесора. Без цього компілятор може помилково вважати, що буфер залишається неініціалізованим або що попередня операція `memset` була зайвою (Dead Store Elimination), і викинути очищення пам'яті під час оптимізації `-O2` чи `-O3`.
2. **Клоббер `"memory"` (Compiler Memory Barrier)**: Інструкція `xsave64` неявно зберігає в пам'ять усі векторні регістри процесора, значення яких компілятор міг згенерувати кілька рядків тому. Якщо не вказати `"memory"` у списку зіпсованих ресурсів (*clobber list*), оптимізуючий компілятор має право переставити векторні обчислення **після** виклику `xsave64`, або навпаки — перенести завантаження результатів у регістри **до** виклику `xrstor64`. Бар'єр `"memory"` змушує оптимізатор скинути всі проміжні значення у змінні до виклику асемблерної інструкції та перечитати їх після неї.
3. **Регістри неявних операндів `EAX` та `EDX`**: Інструкції `XSAVE` та `XRSTOR` не приймають маску компонентів безпосереднім операндом у тексті команди. Вони апаратно читають 64-бітну маску `RFBM` із пари регістрів `EDX:EAX`. Конструкція `"a"(eax), "d"(edx)` жорстко прив'язує значення локальних змінних до фізичних регістрів процесора `RAX` та `RDX` на момент виконання інструкції.

## Застосування у користувацьких планувальниках: корутини та файбери

Одним із найцікавіших прикладів використання `XSAVE` у високонавантажених серверах є створення користувацьких багатопотокових бібліотек (файбери, корутини, green threads), де перемикання завдань відбувається у просторі користувача без виконання важкого системного виклику в ядро.

Якщо корутина виконує SIMD-обчислення (наприклад, розбір JSON через AVX-512 або стиснення даних), простий `setjmp`/`longjmp` чи збереження лише загальних регістрів `RSP`, `RBP`, `RBX`, `R12`–`R15` призведе до спотворення векторних векторів іншої корутини.

Правильна архітектура користувацького перемикача контексту будується за такою схемою:

1. Кожен об'єкт файбера виділяє власну структуру стану з вирівнюванням на 64 байти: `struct fiber_context` містить буфер під загальні регістри та вирівняний блок пам'яті для XSAVE.
2. Під час створення нового файбера заголовок XSAVE заповнюється нулями (`XSTATE_BV = 0`), аби перший виклик `XRSTOR` миттєво апаратно занулив векторні регістри без звернення до пам'яті.
3. Під час передачі керування від файбера `A` до файбера `B` функція перемикання виконує:
   - Збереження цілочисельних регістрів у стек файбера `A`;
   - Виклик `XSAVEOPT` над буфером файбера `A` з маскою `XCR0`: процесор збереже лише ті векторні компоненти, які файбер `A` реально змінював;
   - Перемикання покажчика стека `RSP` на стек файбера `B`;
   - Виклик `XRSTOR` над буфером файбера `B`: якщо файбер `B` не використовував AVX-512, процесор скине вектори в нуль за 25 тактів замість читання кілобайтів пам'яті;
   - Відновлення цілочисельних регістрів файбера `B` та виконання інструкції `RET`.

Такий підхід дозволяє перемикати файбери із підтримкою повного розширеного стану AVX-512 всього за 80–120 тактів процесора, що на два порядки швидше за перемикання контексту через ядро операційної системи.

## Взаємодія з обробниками сигналів ядра (Signal Frames)

Іншим важливим практичним застосуванням структури кадру XSAVE у просторі користувача є обробка сигналів POSIX (наприклад, `SIGSEGV`, `SIGFPE`, `SIGILL`). Коли ядро Linux надсилає сигнал потоку, воно призупиняє його виконання, формує у стеку користувача структуру сигнального кадру `struct rt_sigframe` та передає покажчик на неї в обробник сигналу через структуру `ucontext_t`.

Усередині `ucontext_t->uc_mcontext.fpregs` знаходиться покажчик на збережений стан FPU. У сучасних ядрах, якщо процесор підтримує XSAVE, поле `fpregs` насправді вказує на розширену структуру `struct _xstate`, яка містить класичну застарілу область `FXSAVE` та повноцінний заголовок `XSAVE Header` із маскою `XSTATE_BV`.

Це дозволяє зневаджувачам (GDB, LLDB) або системним бібліотекам перехоплення виключень зчитувати та модифікувати значення векторних регістрів безпосередньо в обробнику сигналу:

1. Обробник сигналу отримує `ucontext_t *uc`.
2. Перевіряє магічне число в структурі контексту `fpregs->sw_reserved.magic1 == FP_XSTATE_MAGIC1`.
3. Зчитує `fpregs->sw_reserved.extended_size` для визначення повного розміру буфера.
4. Досліджує маску `XSTATE_BV` у заголовку XSAVE, знаходить зміщення необхідного регістра `YMM` або `ZMM` і може змінити його значення.
5. Після виходу з обробника сигналу ядро виконує інструкцію `XRSTOR` над цим стековим буфером, завантажуючи оновлені дані назад у фізичні векторні регістри процесора перед поверненням до збійного коду.

## Практичні заміри продуктивності: такти конвеєра

Різні інструкції сімейства XSAVE суттєво відрізняються за вартістю виконання у тактах процесора. Розуміння цих чисел дозволяє системному програмісту обирати правильну інструкцію для корутин чи перемикачів контексту:

1. **Стандартний `XSAVE`**: На процесорах мікроархітектур Skylake та Golden Cove виконання `XSAVE` для повного стану AVX-512 вимагає від 120 до 250 тактів процесора, оскільки інструкція генерує мікропрограмний потік (Microcode Assist) і примусово записує всі кеш-лінії буфера в пам'ять.
2. **Оптимізований `XSAVEOPT`**: Якщо векторні регістри не змінювалися потоком з моменту останнього завантаження, `XSAVEOPT` виконує апаратну перевірку внутрішніх тригерів `XINUSE` за 35–50 тактів і повністю пропускає запис байтів розширеної зони в L1-кеш.
3. **Стиснений `XSAVEC`**: Дозволяє скоротити час запису до 60–90 тактів за рахунок виключення порожніх зон пам'яті між неактивними компонентами.
4. **Відновлення `XRSTOR` з оптимізацією нульового стану (Init-Optimization)**: Якщо в заголовку `XSTATE_BV` біти AVX або AVX-512 скинуті в нуль, `XRSTOR` виконується всього за 20–35 тактів: процесор очищує внутрішні векторні файли мікроархітектури без жодного читання з оперативної пам'яті. Повне ж читання неініціалізованого кадру з пам'яті займає від 100 до 180 тактів.

Для точного вимірювання часу виконання на реальному залізі системні програмісти використовують інструкції серіалізації конвеєра `CPUID` разом із лічильником тактів `RDTSC`/`RDTSCP`. Без серіалізації конвеєр позачергового виконання може почати запис пам'яті ще до зчитування лічильника або навпаки — закінчити збереження після виклику `RDTSC`.

## Підводні камені та типові помилки реалізації

Під час практичного використання інструкцій XSAVE розробники найчастіше стикаються з чотирма критичними пастками:

- **Використання звичайного `malloc()`**: Функція `malloc()` у мові C гарантує вирівнювання пам'яті лише на 8 або 16 байтів (залежно від розрядності архітектури). Виклик `xsave64` над буфером, виділеним через звичайний `malloc`, з імовірністю 75% спричинить виключення загального захисту `#GP(0)`. Необхідно використовувати виключно `aligned_alloc(64, size)`, `posix_memalign()` або `_aligned_malloc()` у середовищі Windows.
- **Ненульовий сміттєвий резерв**: Якщо буфер пам'яті створюється вручну (наприклад, для відновлення заздалегідь підготовленого стану в емуляторі або системі збереження чекпоінтів віртуальної машини), байти 528..575 (зарезервована зона заголовка) обов'язково повинні містити суворо нульові значення. Якщо хоча б один біт у цій 48-байтній області буде одиницею, інструкція `XRSTOR` миттєво відмовиться працювати і згенерує `#GP(0)`.
- **Запит непідтримуваних бітів у масці**: Якщо передати в інструкцію `XRSTOR` маску в `EDX:EAX`, яка містить біти, що не активовані в системному регістрі `XCR0` (наприклад, запит на відновлення AVX-512 на комп'ютері, де підтримується лише базовий AVX), процесор визнає це порушенням прав захисту та кине виключення `#GP(0)`. Маска відновлення завжди повинна бути обмежена кон'юнкцією `RFBM & XCR0`.
- **Ігнорування динамічного перехоплення XFD**: На новітніх процесорах із підтримкою розширення AMX спроба виконати першу інструкцію множення матриць без попереднього запиту дозволу в операційної системи генерує виключення `#NM`. Системна програма або бібліотека лінійного розкладу мусить викликати системний виклик `arch_prctl(ARCH_REQ_XCOMP_PERM, XFEATURE_XTILEDATA)`, щоб ядро розширило буфер потоку до 10 КБ та скинуло біт блокування в MSR `IA32_XFD`.
