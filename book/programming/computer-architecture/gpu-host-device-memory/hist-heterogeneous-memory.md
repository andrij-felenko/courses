# 📜 Від текстурних хаків до єдиного адресного простору: історія гетерогенної пам'яті

На початку 2000-х років спроба змусити відеокарту перемножити дві матриці або розрахувати гідродинамічну сітку нагадувала театральну містифікацію. Графічні прискорювачі того часу були спеціалізованими конвеєрами з жорстко зафіксованими функціями, призначеними виключно для рендерингу тривимірних трикутників. У них не існувало поняття довільного покажчика на пам'ять, не було лінійного адресного простору і не існувало жодного системного виклику для виділення масиву чисел. Будь-які наукові обчислення мусили мімікрувати під комп'ютерну гру.

## Епоха шахрайства з пікселями (2001–2006)

Щоб виконати паралельну операцію над масивом чисел з плаваючою комою, інженери перетворювали числові матриці на тривимірні текстури. Чотири компоненти кольору пікселя — червоний, зелений, синій та альфа-канал (`RGBA`) — слугували контейнерами для чотирьох чисел типу `float`. Обчислення оформлювали як процес малювання: програма створювала прямокутник на весь екран (*screen-aligned quad*), натягувала на нього текстуру з вхідними даними й запускала фрагментний шейдер через графічний конвеєр [OpenGL](book:programming/virtual-memory) або Direct3D.

Фрагментний шейдер трактував кожен піксель як окрему задачу, виконував математичні операції над кольорами й записував результат у вихідний буфер кадру (*framebuffer*). Головна драма розгорталася на етапі повернення результатів у центральний процесор. Щоб прочитати обчислені значення, програма викликала функцію `glReadPixels()`. 

Цей виклик був катастрофічно повільним. Графічний драйвер зупиняв конвеєр рендерингу, чекав завершення всіх активних конвеєрних стадій, скидав графічний кеш і починав побайтове копіювання через інтерфейс AGP 4x або 8x (із піковою пропускною здатністю від 1.06 до 2.1 ГБ/с). Затримка такого читання сягала мілісекунд. Програміст не мав контролю над тим, куди саме у відеопам'яті лягають байти: конвеєр міг стискати текстури, переставляти пікселі за Z-кривою Мортона для оптимізації просторової локальності або вирівнювати рядки під специфічні вимоги растрового блока.

```
Текстура RGBA (Host) 
  → glTexImage2D() через AGP/PCIe 
  → Відеопам'ять VRAM (Z-порядок) 
  → Рендеринг прямокутника у Framebuffer 
  → glReadPixels() 
  → Синхронна пауза CPU 
  → Масив результатів у Host RAM
```

Попри жахливі накладні витрати, дослідники зі Стенфордського університету під керівництвом Пета Ханрахана (Pat Hanrahan) побачили у графічних чипах колосальний потенціал. 2003 року аспірант Стенфорда Ян Бак (Ian Buck) створив проєкт BrookGPU — мову програмування та компілятор, що транслював паралельні потокові алгоритми у шейдери OpenGL та DirectX. BrookGPU ховав графічну термінологію (текстури, фреймбуфери, координати вершин) за абстракцією потоків даних (*streams*) та обчислювальних ядер (*kernels*). Це був перший крок до відокремлення обчислень від графічного конвеєра.

## Революція G80 та народження CUDA (2006–2007)

2004 року компанія NVIDIA найняла Яна Бака для розробки принципово нової архітектури. Результатом став випуск восени 2006 року графічного процесора G80 (GeForce 8800 GTX) та програмно-апаратного комплексу CUDA (*Compute Unified Device Architecture*).

G80 відмовився від розділених блоків вершинних і піксельних шейдерів на користь уніфікованих потокових мультипроцесорів (*Streaming Multiprocessors*, SM). Разом із кремнієм народилася перша справжня модель гетерогенної пам'яті. Архітектори розділили адресний простір на дві ізольовані імперії:
- **Пам'ять хоста (Host Memory)** — оперативна пам'ять процесора, підпорядкована операційній системі;
- **Пам'ять пристрою (Device Memory)** — локальна пам'ять відеокарти GDDR3, доступ до якої мали лише обчислювальні ядра GPU.

CUDA 1.0 запровадила базові виклики керування: `cudaMalloc()` для виділення лінійного масиву у VRAM та `cudaMemcpy()` для передачі блоків даних через системну шину PCIe. Уперше в історії програміст отримав прямий покажчик на байтовий масив у відеопам'яті без необхідності створювати фіктивні вікна рендерингу.

Однак перша реалізація породила фундаментальну проблему синхронізації та продуктивності. Коли розробник виділяв пам'ять на боці CPU через звичайний `malloc()`, операційна система створювала звичайні сторінкові ділянки (*pageable memory*). Контролер прямого доступу до пам'яті ([DMA-контролер](book:programming/dma-controller)), розташований на платі розширення GPU, не міг безпечно читати ці адреси. Якби операційна система під час передачі вирішила витіснити фізичну сторінку у файл підкачки або змінити таблицю сторінок, DMA переписав би чужі дані або прочитав би сміття.

Драйверу доводилося діяти в два кроки: виділяти прихований транзитний буфер із заблокованими фізичними сторінками (*pinned staging buffer*), копіювати дані з пам'яті користувача у транзитний буфер силами центрального процесора, і лише потім запускати апаратний трансфер по шині PCIe. Пропускна здатність передачі падала вдвічі, а центральний процесор марнував такти на перекладання байтів.

Відповіддю інженерів стало відкриття прямого інтерфейсу фіксації сторінок — виклику `cudaMallocHost()` (а згодом `cudaHostAlloc()`). Програміст отримав інструмент блокування сторінок хоста від витискання, завдяки чому контролер DMA прискорювача зміг напряму зчитувати дані з оперативної пам'яті без залучення CPU.

## Ера кластерів і GPUDirect (2010–2013)

На початку 2010-х гетерогенні прискорювачі вийшли за межі робочих станцій і стали головною рушійною силою суперкомп'ютерів (зокрема систем Tianhe-1A, Titan та Oakforest-PACS). Тут архітектура пам'яті натрапила на новий бар'єр: необхідність взаємодії між кількома відеокартами в одному сервері та передачі даних через високошвидкісну мережу InfiniBand.

За класичною схемою CUDA обмін даними між двома GPU вимагав тривалого ланцюжка транзакцій:
```
VRAM (GPU 0) 
  → DMA через PCIe 
  → Pinned Buffer у системній пам'яті CPU 
  → Копіювання через шину процесора 
  → DMA через PCIe 
  → VRAM (GPU 1)
```

Цей маршрут не лише подвоював затримку, а й створював колосальне навантаження на кореневий комплекс шини PCIe процесора (*PCIe Root Complex*) та канали пам'яті центрального процесора.

Для вирішення цієї кризи NVIDIA розробила технологію **GPUDirect**:
1. **GPUDirect Shared Memory (2010)**: усунення проміжних копіювань між драйвером мережевої карти та драйвером GPU за рахунок спільного використання заблокованих сторінок пам'яті хоста.
2. **GPUDirect P2P (Peer-to-Peer, 2011)**: передача даних напряму між двома прискорювачами на одній спільній шині PCIe без заїзду в системну пам'ять хоста. Контролер DMA першої відеокарти навчився формувати транзакції запису безпосередньо за адресами Base Address Register (BAR) другої карти.
3. **GPUDirect RDMA (2012)**: прямий доступ мережевого адаптера ([IOMMU](book:programming/iommu) та InfiniBand HCA) до відеопам'яті GPU по шині PCIe без участі ядер центрального процесора.

## Від програмних милиць до апаратних Page Faults (2014–2017)

Попри досягнення в швидкості передачі, ручне керування двома розділеними адресними просторами лишалося головним джерелом помилок. Програмісти були змушені дублювати кожну структуру даних, виділяти подвійні масиви покажчиків і вручну синхронізувати стан після кожного кроку обчислень. Якщо масив даних хоча б на один байт перевищував обсяг фізичної пам'яті відеокарти, програма падала з фатальною помилкою вичерпання пам'яті (*Out of Memory*).

2014 року з виходом архітектури Kepler (CUDA 6.0) компанія представила першу версію **Unified Memory** (керованої пам'яті). Вона надавала розробнику єдиний покажчик, доступний як із CPU, так і з GPU через функцію `cudaMallocManaged()`. 

Однак у поколінні Kepler керована пам'ять була суто програмною ілюзією. Графічний процесор не мав апаратного блоку обробки сторінкових промахів (*Page Faults*). Драйвер виконував грубу пакетну міграцію: перед запуском кожного обчислювального ядра він примусово переносив *весь* виділений масив цілком із Host RAM у VRAM. Якщо розмір масиву перевищував фізичний розмір відеопам'яті, програма аварійно завершувалася.

Справжній апаратний прорив стався 2016 року в архітектурі **Pascal** (чип GP100):
- **Апаратний блок GPU Page Fault**: потокові мультипроцесори навчилися перехоплювати спробу звернення до невідображеної віртуальної адреси, призупиняти виконання конкретного варпу й надсилати сигнал переривання через шину.
- **49-бітний віртуальний адресний простір**: зрівняння адресних просторів CPU та GPU дозволило передавати складні динамічні структури (дерева, зв'язні списки, графи з вказівниками) без перерахунку зміщень.
- **Сторінкова міграція на вимогу (*On-Demand Page Migration*)**: драйвер отримав можливість переносити дані дрібними блоками (сторінками по 4 КБ або 64 КБ) саме тоді, коли до них звертається ядро, витісняючи найменш запитувані сторінки назад в оперативну пам'ять хоста. Це дозволило безшовно запускати задачі, обсяг яких значно перевищував розмір VRAM (*Oversubscription*).

Паралельно у спільноті розробників ядра Linux розгорнулася масштабна інженерна робота. Розробник Жером Ґлісс (Jérôme Glisse) із компанії Red Hat та Джон Губбард (John Hubbard) спроєктували підсистему **HMM (Heterogeneous Memory Management)**. Її включення в основну гілку ядра Linux (починаючи з версії 4.14 у 2017 році) стандартизувало протокол міграції сторінок між операційною системою та сторонніми прискорювачами, інтегрувавши структуру `struct page` з пристроями на шині PCIe через механізм дзеркалювання таблиць сторінок.

## Епоха когерентних інтерконектів і монолітних SoC (2020-ті)

Сьогодні класична шина PCIe перестає бути єдиним містком між обчислювальними доменами. У сучасних архітектурах суперкомп'ютерів та штучного інтелекту межа між Host і Device остаточно розмивається завдяки високошвидкісним когерентним шинам:
- **NVIDIA Grace Hopper (NVLink-C2C)**: об'єднує процесор ARM Grace та графічний чип Hopper каналом зі швидкістю 900 ГБ/с. Процесор і прискорювач використовують спільну апаратну когерентність кешів без потреби в класичному копіюванні.
- **AMD CDNA3 / MI300A**: перший комбінований APU для датацентрів, де кристали CPU (Zen 4) та GPU (CDNA 3) змонтовані на єдиній підкладці й ділять між собою єдиний спільний масив надшвидкої пам'яті HBM3 з пропускною здатністю 5.3 ТБ/с.
- **Стандарт CXL (Compute Express Link)**: відкритий галузевий протокол поверх фізичного рівня PCIe, який реалізує апаратне підтримання когерентності пам'яті (CXL.cache та CXL.mem) між гетерогенними прискорювачами будь-яких виробників.

Пройшовши шлях від піксельних шейдерів і викликів `glReadPixels()` через дискретні копіювання `cudaMemcpy()` та апаратні сторінкові переривання, архітектура пам'яті повернулася до фундаментальної ідеї: єдиного, прозорого та апаратно узгодженого простору адрес, де фізичне розташування байта визначається лише потребами локальності та енергоефективності.
