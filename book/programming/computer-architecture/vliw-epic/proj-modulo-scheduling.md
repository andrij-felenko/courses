# ⚙️ Програмна конвеєризація: алгоритм Modulo Scheduling у компіляторі

Програмна конвеєризація (англ. *Software Pipelining*) — це фундаментальна техніка глобальної оптимізації циклів у компіляторах для архітектур VLIW та EPIC. Її головна мета — подолати затримки довгих інструкцій (читання з пам'яті, множення з плаваючою комою) шляхом перекриття в часі операцій із різних ітерацій циклу.

У той час як класичне розгортання циклу (англ. *Loop Unrolling*) просто дублює тіло програми, збільшуючи розмір двійкового коду та навантаження на регістри, програмна конвеєризація перебудовує сам алгоритм виконання: кожна наступна ітерація циклу стартує з фіксованим зсувом за часом, ще до того, як завершилися попередні ітерації.

Найвідомішим і математично обґрунтованим методом побудови такого конвеєра є **Modulo Scheduling** (планування за модулем), розроблений Бобом Рау та вдосконалений дослідниками оптимізуючих компіляторів. Розгляньмо повний процес роботи цього алгоритму: від аналізу залежностей до таблиці модульного резервування, евристики Iterative Modulo Scheduling, аналізу часу життя змінних, апаратної ротації регістрів і робочої програмної моделі на мовах C та C++.

### 1. Граф залежностей за даними (DDG) та параметри ребер

Робота компілятора розпочинається з побудови графа залежностей за даними (англ. *Data Dependence Graph*, DDG) для тіла циклу. Вершини графа представляють елементарні операції, а орієнтовані ребра — залежності між ними.

Для кожного ребра `u → v` компілятор обчислює два ключові параметри:
1. **Затримка (Latency, `d(u,v)`):** мінімальна кількість тактів між стартом операції `u` та моментом, коли її результат стає доступним для операції `v`. Наприклад, для операції цілочислового додавання затримка становить 1 такт, для множення — 2–3 такти, а для читання з кешу L1 — 2–4 такти.
2. **Дистанція ітерацій (Iteration Distance, `δ(u,v)`):** різниця між номерами ітерацій циклу, у яких беруть участь операції `u` та `v`:
   - Якщо операція `v` використовує дані, вироблені операцією `u` в тій самій ітерації циклу, то `δ = 0` (внутрішньоітераційна залежність).
   - Якщо операція `v` в ітерації `k` потребує результату, який операція `u` виробила в ітерації `k - 1` (наприклад, накопичення суми `sum = sum + a[i]`), то `δ = 1` (міжітераційна або рекурентна залежність). Для залежностей через дві ітерації `δ = 2`.

Розгляньмо типовий обчислювальний цикл векторного масштабування:
:::tabs
```c
for (int i = 0; i < N; ++i) {
    y[i] = x[i] * 2 + 5;
}
```
```cpp
for (size_t i = 0; i < N; ++i) {
    y[i] = x[i] * 2 + 5;
}
```
:::

Тіло цього циклу складається з трьох послідовних операцій:
- **`L` (Load):** `r_val = load(x[i])` (затримка `d = 2` такти).
- **`C` (Compute):** `r_res = r_val * 2 + 5` (затримка `d = 2` такти).
- **`S` (Store):** `store(y[i], r_res)` (затримка `d = 1` такт).

У цьому базовому прикладі ребра залежностей мають вигляд:
- `L → C` із затримкою `d = 2`, дистанцією `δ = 0`.
- `C → S` із затримкою `d = 2`, дистанцією `δ = 0`.

У послідовному виконанні одна ітерація вимагає `2 + 2 + 1 = 5` тактів. Якщо виконати 1000 ітерацій, процесор витратить 5000 тактів.

### 2. Обчислення мінімального інтервалу ініціалізації (MII)

Головною метою Modulo Scheduling є мінімізація **інтервалу ініціалізації** (англ. *Initiation Interval*, **`II`**) — кількості тактів між запусками послідовних ітерацій. Якщо `II = 1`, процесор розпочинає нову ітерацію циклу **щотакту**.

Мінімально можливий інтервал ініціалізації (`MII`) визначається двома незалежними фізичними обмеженнями:

```
MII = max(ResMII, RecMII)
```

#### Ресурсне обмеження (Resource MII, `ResMII`)
Визначається сумарною кількістю операцій кожного типу в тілі циклу та кількістю доступних функціональних блоків у мікроархітектурі процесора.

Для кожного типу ресурсу `r` (блоки пам'яті, цілочислові АЛП, блоки множення):
```
ResMII = max_r ⌈Кількість_операцій(r) / Кількість_блоків(r)⌉
```

Наприклад, якщо тіло циклу містить 3 операції завантаження/збереження, а процесор має лише 2 порти пам'яті, то `ResMII = ⌈3 / 2⌉ = 2`. Меншим за 2 інтервал `II` бути не може, оскільки портам пам'яті фізично не вистачить пропускної здатності.

#### Рекурентне обмеження (Recurrence MII, `RecMII`)
Визначається наявністю замкнених циклів у графі залежностей (зворотних зв'язків між ітераціями). Для кожного орієнтованого контуру `C` у графі DDG обчислюється відношення сумарної затримки до сумарної дистанції:

```
RecMII = max_C ⌈(∑_{u→v ∈ C} d(u,v)) / (∑_{u→v ∈ C} δ(u,v))⌉
```

Розгляньмо приклад із рекурентним зв'язком — цифровий IIR-фільтр:
:::tabs
```c
for (int i = 1; i < N; ++i) {
    y[i] = y[i - 1] * c + x[i];
}
```
```cpp
for (size_t i = 1; i < N; ++i) {
    y[i] = y[i - 1] * c + x[i];
}
```
:::
Тут операція обчислення `C` в ітерації `i` потребує значення `y[i - 1]`, обчисленого тією самою операцією `C` в ітерації `i - 1`. Маємо замкнений цикл із затримкою множення й додавання `d = 3` такти та дистанцією `δ = 1`. Рекурентний бар'єр становить:
```
RecMII = ⌈3 / 1⌉ = 3 такти
```
Це означає, що як би ми не розширювали процесор, розпочинати нову ітерацію частіше ніж раз на 3 такти неможливо через фундаментальний зв'язок за даними.

Для нашого першого прикладу з незалежним масивом (`y[i] = x[i] * 2 + 5`) рекурентних контурів немає (`RecMII = 1`). На 8-канальному VLIW-процесорі (де є окремі блоки пам'яті та АЛП) отримуємо:
- `ResMII = max(1/1, 1/1, 1/1) = 1`
- `RecMII = 1`
- `MII = max(1, 1) = 1`

### 3. Побудова модульної таблиці резервування (MRT) та евристика IMS

Компілятор бере початкове значення `II = MII` і будує **модульну таблицю резервування** (англ. *Modulo Reservation Table*, MRT). Таблиця має розмір `II × Кількість_Ресурсів`. Її рядки відповідають тактам за модулем `II` (від `0` до `II - 1`).

У класичному алгоритмі **Iterative Modulo Scheduling (IMS)** планування відбувається за евристичною схемою:
1. Компілятор призначає кожній операції `u` пріоритет на основі висоти в графі (англ. *Height-based priority*):
   ```
   Height(u) = max_{v} (Height(v) + d(u,v) - δ(u,v) · MII)
   ```
   Операції з найдовшим шляхом до завершення циклу плануються першими.
2. Для вибраної операції `u` обчислюється часовий інтервал раннього старту:
   ```
   EStart(u) = max_{p→u, p заплановано} (Time(p) + d(p,u) - δ(p,u) · II)
   ```
3. Компілятор перевіряє такти `t = EStart(u), EStart(u) + 1, ..., EStart(u) + II - 1`. Якщо на такті `t` необхідний функціональний блок вільний у клітинці `t mod II` таблиці MRT, операція фіксується на часі `Time(u) = t`.
4. Якщо виникає конфлікт ресурсів у всіх спробах, IMS застосовує відкат (Backtracking): він примусово призначає операцію на найраніший такт, але знімає з розкладу ті раніше заплановані операції, з якими вона вступила в конфлікт за ресурсом або залежностями, і повертає їх у чергу пріоритетів.
5. Кожна операція має лічильник спроб (бюджет відкатів). Якщо загальна кількість відкатів перевищує поріг (наприклад, `3 × Кількість_вершин`), компілятор вважає поточний `II` недосяжним, збільшує `II = II + 1`, повністю очищає MRT і повторює планування.

Альтернативою IMS є алгоритм **Swing Modulo Scheduling (SMS)**. На відміну від IMS, який планує тільки зверху вниз, SMS чергує рух зверху вниз (від джерел до споживачів) і знизу вгору (від споживачів до джерел). Це мінімізує час життя проміжних змінних і суттєво зменшує регістровий тиск.

Заплануймо наш приклад для `II = 1`:
- Операція `L` стартує в такт `t = 0`. Вона займає ресурс пам'яті в слоті `0 mod 1 = 0`.
- Операція `C` залежить від `L` із затримкою 2 такти, тому `EStart(C) = 0 + 2 = 2`. Вона займає блок АЛП у слоті `2 mod 1 = 0`.
- Операція `S` залежить від `C` із затримкою 2 такти, тому `EStart(S) = 2 + 2 = 4`. Вона займає ресурс пам'яті в слоті `4 mod 1 = 0`.

Усі три операції мають довжину розкладу `Schedule_Length = 5` тактів (від `t = 0` до `t = 4`).

### 4. Повний приклад: обчислення скалярного добутку (Dot Product)

Щоб наочно простежити заповнення таблиці MRT та переплетення ітерацій, розгляньмо класичне ядро цифрової обробки сигналів — скалярний добуток двох векторів:

:::tabs
```c
for (int i = 0; i < N; ++i) {
    sum += a[i] * b[i];
}
```
```cpp
for (size_t i = 0; i < N; ++i) {
    sum += a[i] * b[i];
}
```
:::

Розбиття на елементарні операції та їхні затримки:
1. `La`: `r_a = load(a[i])` (блок пам'яті `M0`, затримка 2 такти).
2. `Lb`: `r_b = load(b[i])` (блок пам'яті `M1`, затримка 2 такти).
3. `Mul`: `r_prod = r_a * r_b` (блок множення `F0`, затримка 2 такти).
4. `Acc`: `sum = sum + r_prod` (блок додавання `I0`, затримка 1 такт, рекурентний зв'язок `Acc(i) → Acc(i+1)` із дистанцією `δ = 1`).

Аналіз параметрів:
- Ресурси: 2 порти пам'яті (`M0, M1`), 1 помножувач (`F0`), 1 АЛП (`I0`). Усі операції потребують по 1 блоку свого типу, отже `ResMII = 1`.
- Рекурентність: єдиний контур `Acc → Acc` має затримку `d = 1` та дистанцію `δ = 1`. Звідси `RecMII = ⌈1 / 1⌉ = 1`.
- Загальний мінімум: `MII = max(1, 1) = 1`.

Побудова графіка виконання:
- Такт `t = 0`: `La` на `M0`, `Lb` на `M1`.
- Такт `t = 2`: `Mul` на `F0` (обидва операнди `r_a` та `r_b` готові).
- Такт `t = 4`: `Acc` на `I0` (результат множення готовий).

Загальна довжина одного ланцюжка обчислень становить 5 тактів. За `II = 1` стадії конвеєра розподіляються наступним чином:
- Стадія 0 (Такт 0): читання елементів `a[i]` та `b[i]`.
- Стадія 1 (Такт 1): очікування пам'яті (латентність читання).
- Стадія 2 (Такт 2): множення `a[i] * b[i]`.
- Стадія 3 (Такт 3): очікування результату множника.
- Стадія 4 (Такт 4): накопичення суми `sum += prod`.

У стабільному стані (ядро) на кожному такті процесор одночасно:
- Завантажує елементи для ітерації `i + 4`
- Множить елементи для ітерації `i + 2`
- Додає до накопичувача результат для ітерації `i`

Темп видачі готових накопичень становить рівно **одне множення з додаванням щотакту** (IPC = 4 корисні інструкції за такт), що є абсолютним теоретичним максимумом для цього заліза.

### 5. Фази конвеєра та аналіз часу життя змінних (MaxLive)

Кількість стадій конвеєра обчислюється як:
```
Stage_Count = ⌈Schedule_Length / II⌉ = ⌈5 / 1⌉ = 5 стадій
```

Коли цикл конвеєризовано, його виконання природно розділяється на три частини:
1. **Пролог (Prologue):** Триває `(Stage_Count - 1) · II` тактів. Тут стартують перші операції перших ітерацій, поступово наповнюючи конвеєр.
2. **Ядро (Kernel):** Стабільний робочий стан. Триває `(N - Stage_Count + 1) · II` тактів. У кожному такті ядра одночасно виконуються операції з кількох різних ітерацій. Кожен такт ядра видає один готовий результат!
3. **Епілог (Epilogue):** Триває `(Stage_Count - 1) · II` тактів. Нові ітерації більше не запускаються, а конвеєр поступово зливає та дописує результати останніх оброблених елементів.

Паралельно з побудовою розкладу компілятор проводить аналіз часу життя значень (англ. *Live Range Analysis*). Оскільки результат кожної операції живе протягом кількох тактів, а в конвеєрі одночасно перебуває `Stage_Count` ітерацій, кількість одночасно активних значень однієї змінної становить:
```
MaxLive = ⌈Час_життя_змінної / II⌉
```

Для розподілу регістрів у конвеєризованому циклі компілятор використовує спеціальний варіант розфарбовування графів — розфарбовування дуг кола (англ. *Circular Arc Graph Coloring*). Кожна змінна представляється дугою на кільцевій шкалі довжиною `II`. Алгоритм знаходить мінімальну кількість кольорів (фізичних регістрів), необхідних для покриття всіх перекритих дуг без інтерференції. Якщо в циклі використовується апаратний ротаційний банк, кожна дуга довжиною `L` просто резервує `⌈L / II⌉` послідовних адрес у ротаційному вікні, усуваючи необхідність у складних процедурах злиття життєвих інтервалів.

Якщо сумарний `MaxLive` для всіх змінних циклу перевищує кількість доступних фізичних регістрів процесора, згенерований розклад стає недійсним через нестачу регістрів (Register Spill). Компілятор змушений збільшувати `II`, що скорочує перекриття ітерацій та знижує регістровий тиск до прийнятного рівня.

Часто Modulo Scheduling комбінують із попередньою векторизацією SIMD: якщо об'єднати 4 сусідні ітерації в один векторний пакет, кількість ітерацій `N` зменшується вчетверо, а програмний конвеєр перекриває вже векторні операції, досягаючи максимального коефіцієнта використання обчислювальних трактів DSP або VLIW-ядра.

### 6. Апаратні ротаційні регістри в архітектурі IA-64 та DSP

У класичних архітектурах реалізація прологу, ядра та епілогу вимагала потрійного дублювання коду: окремий блок прологу перед циклом, окреме ядро циклу та окремий епілог після нього. Крім того, оскільки значення `r_val` для ітерації `i+1` виробляється до того, як завершилося використання `r_val` для ітерації `i`, компілятор був змушений виділяти унікальні регістри під кожну стадію та виконувати програмне розгортання.

Архітектура Intel Itanium (IA-64) розв'язала цю проблему за допомогою **апаратних ротаційних регістрів** (англ. *Rotating Registers*):
- Файл регістрів ділиться на статичну частину (`r0..r31`) та ротаційну частину (`r32..r127`).
- Аналогічно предикатні регістри діляться на статичні (`p0..p15`) та ротаційні (`p16..p63`).
- Спеціальний регістр стану кадру CFM (англ. *Current Frame Marker*) містить базовий покажчик ротації `RRB.GR` (Rotating Register Base for General Registers) та `RRB.PR` (для предикатів).
- Спеціальна інструкція умовного переходу циклу **`br.ctop`** (Branch Counted Loop to Top) керує апаратними лічильниками:
  - `AR[LC]` (Loop Counter): кількість ітерацій циклу.
  - `AR[EC]` (Epilogue Counter): кількість стадій епілогу (`Stage_Count - 1`).
- Щотакту виконання `br.ctop` здійснює такі мікрооперації:
  1. Якщо `LC > 0`, зменшує `LC = LC - 1`, записує `1` у предикат `p16` і здійснює перехід на початок ядра.
  2. Якщо `LC == 0` і `EC > 1`, зменшує `EC = EC - 1`, записує `0` у предикат `p16` і продовжує перехід на початок ядра (фаза епілогу).
  3. Якщо `LC == 0` і `EC == 1`, цикл завершується, і процесор переходить до наступної інструкції за межами циклу.
  4. Автоматично зменшує базові покажчики: `RRB.GR = (RRB.GR - 1) mod 96`, `RRB.PR = (RRB.PR - 1) mod 48`.

Схожий механізм використовують сучасні сигнальні процесори Qualcomm Hexagon: апаратні буфери циклів (Hardware Loop Buffers) автоматично фіксують інструкції ядра у внутрішньому надшвидкому кеші та здійснюють безперервну подачу VLIW-пакетів без затримок на вибірку переходу.

Завдяки цьому індекс регістра з погляду інструкції зсувається автоматично: те, що в поточному такті записано в `r32`, у наступному такті адресується як `r33`, а ще через такт — як `r34`. Компілятор генерує **єдине компактне тіло циклу без жодного дублювання інструкцій**.

### 7. Робоча модель програмного конвеєра на C та C++

Наведений нижче приклад демонструє роботу програмного конвеєра із симуляцією апаратного банку ротаційних регістрів для обробки масиву чисел `y[i] = x[i] * 2 + 5`.

```c
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>

#define N 8
#define STAGES 3

// Структура, що моделює банк ротаційних регістрів процесора
typedef struct {
    int32_t val[STAGES]; // val[0] - поточна ітерація, val[1] - попередня, val[2] - передпопередня
    bool pred[STAGES];   // предикати стадій p16, p17, p18
} RotatingBank;

// Апаратний зсув регістрів та предикатів (аналог br.ctop в IA-64)
static void rotate_registers(RotatingBank *b, bool next_stage_valid) {
    for (int i = STAGES - 1; i > 0; --i) {
        b->val[i] = b->val[i - 1];
        b->pred[i] = b->pred[i - 1];
    }
    b->pred[0] = next_stage_valid;
    b->val[0] = 0;
}

void software_pipelined_loop(const int32_t *src, int32_t *dst, size_t count) {
    RotatingBank bank = {0};
    
    // Загальна кількість тактів для виконання N ітерацій у конвеєрі:
    // N ітерацій + (STAGES - 1) тактів на наповнення/злиття
    size_t total_cycles = count + (STAGES - 1);
    size_t input_idx = 0;
    size_t output_idx = 0;

    printf("=== Старт програмного конвеєра (II = 1) ===\n");

    for (size_t cycle = 0; cycle < total_cycles; ++cycle) {
        // Логіка керування предикатом входу: дієвий, поки є вхідні дані
        bool push_valid = (input_idx < count);
        rotate_registers(&bank, push_valid);

        printf("Такт %2zu | Предикати: [%d, %d, %d] | ", 
               cycle + 1, bank.pred[0], bank.pred[1], bank.pred[2]);

        // Стадія 1 (Під предикатом p16 / pred[0]): Читання з пам'яті
        if (bank.pred[0] && input_idx < count) {
            bank.val[0] = src[input_idx];
            printf("Read x[%zu]=%2d ", input_idx, bank.val[0]);
            input_idx++;
        } else {
            printf("               ");
        }

        // Стадія 2 (Під предикатом p17 / pred[1]): Обчислення над даними попереднього такту
        if (bank.pred[1]) {
            bank.val[1] = bank.val[1] * 2 + 5;
            printf("| Calc=%3d ", bank.val[1]);
        } else {
            printf("|          ");
        }

        // Стадія 3 (Під предикатом p18 / pred[2]): Запис результату
        if (bank.pred[2] && output_idx < count) {
            dst[output_idx] = bank.val[2];
            printf("| Write y[%zu]=%3d\n", output_idx, dst[output_idx]);
            output_idx++;
        } else {
            printf("| \n");
        }
    }
}

int main(void) {
    int32_t x[N] = {10, 20, 30, 40, 50, 60, 70, 80};
    int32_t y[N] = {0};

    software_pipelined_loop(x, y, N);

    printf("\nПідсумковий масив y: ");
    for (size_t i = 0; i < N; ++i) {
        printf("%d ", y[i]);
    }
    printf("\n");

    return 0;
}
```

```cpp
#include <iostream>
#include <vector>
#include <array>
#include <cstdint>
#include <iomanip>

constexpr size_t N = 8;
constexpr size_t STAGES = 3;

// Клас, що моделює апаратний ротаційний файл регістрів IA-64
class RotatingRegisterFile {
public:
    void rotate(bool next_stage_valid) noexcept {
        for (size_t i = STAGES - 1; i > 0; --i) {
            values_[i] = values_[i - 1];
            predicates_[i] = predicates_[i - 1];
        }
        predicates_[0] = next_stage_valid;
        values_[0] = 0;
    }

    [[nodiscard]] bool predicate(size_t stage) const noexcept { return predicates_[stage]; }
    [[nodiscard]] int32_t& value(size_t stage) noexcept { return values_[stage]; }
    [[nodiscard]] int32_t value(size_t stage) const noexcept { return values_[stage]; }

private:
    std::array<int32_t, STAGES> values_{};
    std::array<bool, STAGES> predicates_{};
};

void softwarePipelinedLoop(const std::vector<int32_t>& src, std::vector<int32_t>& dst) {
    RotatingRegisterFile rf;
    const size_t count = src.size();
    const size_t totalCycles = count + (STAGES - 1);
    
    size_t inputIdx = 0;
    size_t outputIdx = 0;

    std::cout << "=== Старт програмного конвеєра C++ (II = 1) ===\n";

    for (size_t cycle = 0; cycle < totalCycles; ++cycle) {
        const bool pushValid = (inputIdx < count);
        rf.rotate(pushValid);

        std::cout << "Такт " << std::setw(2) << cycle + 1 << " | Предикати: ["
                  << rf.predicate(0) << ", " << rf.predicate(1) << ", " << rf.predicate(2) << "] | ";

        // Стадія 1: Завантаження елемента під предикатом 0
        if (rf.predicate(0) && inputIdx < count) {
            rf.value(0) = src[inputIdx];
            std::cout << "Read x[" << inputIdx << "]=" << std::setw(2) << rf.value(0) << " ";
            ++inputIdx;
        } else {
            std::cout << "               ";
        }

        // Стадія 2: Обчислення над даними під предикатом 1
        if (rf.predicate(1)) {
            rf.value(1) = rf.value(1) * 2 + 5;
            std::cout << "| Calc=" << std::setw(3) << rf.value(1) << " ";
        } else {
            std::cout << "|          ";
        }

        // Стадія 3: Запис результату під предикатом 2
        if (rf.predicate(2) && outputIdx < count) {
            dst[outputIdx] = rf.value(2);
            std::cout << "| Write y[" << outputIdx << "]=" << std::setw(3) << dst[outputIdx] << "\n";
            ++outputIdx;
        } else {
            std::cout << "| \n";
        }
    }
}

int main() {
    const std::vector<int32_t> x = {10, 20, 30, 40, 50, 60, 70, 80};
    std::vector<int32_t> y(x.size(), 0);

    softwarePipelinedLoop(x, y);

    std::cout << "\nПідсумковий масив y: ";
    for (const auto val : y) {
        std::cout << val << " ";
    }
    std::cout << "\n";

    return 0;
}
```

### 8. Практичні виклики та крайові випадки Modulo Scheduling

1. **Регістровий тиск та скидання на стек (Spill):** Оскільки проміжні результати живуть у конвеєрі протягом кількох тактів для кількох паралельних ітерацій, потреба у фізичних регістрах різко зростає (приблизно як `Stage_Count × Кількість_змінних`). Якщо доступних регістрів не вистачає, компілятор змушений вставляти інструкції скидання в пам'ять (spill), що додає нові звернення до пам'яті та руйнує мінімальний `II`.
2. **Короткі цикли (Trip Count < Stage Count):** Якщо кількість ітерацій циклу `N` менша за глибину стадій конвеєра, повноцінне ядро конвеєра взагалі не встигає активуватися. У звичайних VLIW-компіляторах для цього генерується спеціальна скалярна захисна гілка перевірки перед входом у цикл. В архітектурі EPIC завдяки ротаційним предикатам той самий конвеєризований блок коректно відпрацьовує навіть одиничні ітерації.
3. **Розгалуження всередині циклу:** Якщо тіло циклу містить конструкції `if-else`, компілятор зобов'язаний спершу виконати повну предикацію (Hyperblock formation), перетворивши всі умовні гілки на лінійний код під предикатами, і лише після цього будувати матрицю MRT.
4. **Недетерміновані промахи в кеші:** Уся математична елегантність Modulo Scheduling базується на фіксованій тривалості кожної інструкції. Якщо стадія завантаження `L` промахується в кеші L1, конвеєр заморожується, і вся вигода від ретельно розрахованого `II = 1` миттєво зникає на сотні тактів.
5. **Сучасна інфраструктура в компіляторах (LLVM MachinePipeliner):** У сучасному промисловому компіляторі LLVM генератор програмних конвеєрів винесено в загальний бекенд-пакет `MachinePipeliner` та `ModuloScheduleExpander`. Цей модуль будує матрицю MRT над графом низькорівневих машинних інструкцій (MachineInstr), проводить аналіз перекриття псевдонімів пам'яті через аналізатор `AAResults` та генерує апаратні цикли з ротацією для архітектур Qualcomm Hexagon та спеціалізованих VLIW-прискорювачів. Модуль автоматично генерує блоки прологу та епілогу, розраховує час життя регістрів через інтервали LiveIntervals і вставляє захисні перевірки мінімальної кількості ітерацій перед входом у конвеєризоване ядро.
