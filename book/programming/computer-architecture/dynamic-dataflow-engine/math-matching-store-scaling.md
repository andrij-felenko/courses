# 🧮 Математичний аналіз та моделювання пропускної здатності блоку зіставлення токенів

Блок зіставлення операндів (*Matching Store*) є критичним вузлом динамічного потокового рушія. Якщо темп обробки або пошуку операндів-партнерів відстає від темпу емісії результатів обчислювальними блоками (ALU), черга токенів починає неконтрольовано зростати, що призводить або до вичерпання апаратної пам'яті, або до виникнення дедлоку через блокування зворотного тиску (*backpressure deadlock*).

Розглянемо формальний математичний апарат, що описує динаміку наповнення пам'яті операндів, часову та просторову складність різних схем зіставлення, а також строгі критерії обмеження паралелізму циклів.

## 1. Ймовірнісна модель очікування токенів і закон Літтла

Нехай у потокове кільце рушія надходить сумарний потік токенів із середньою інтенсивністю `λ` (токенів за такт). Усі операції в графі поділяються на:
* **Унарні операції** (частка `p₁`): інструкції з одним входом (наприклад, зміна знака, взяття абсолютної величини, логічне заперечення). Вони не потребують другого операнда і проходять крізь Matching Store миттєво з нульовою затримкою очікування.
* **Бінарні операції** (частка `p₂ = 1 − p₁`): інструкції з двома входами (додавання, множення, порівняння). Кожна така операція породжує два токени — лівий і правий.

Інтенсивність надходження бінарних токенів становить:

```
λ_bin = p₂ · λ
```

Коли перший із пари токенів прибуває до блоку зіставлення, його партнер ще не обчислений. Токен осідає в пам'яті очікування на випадковий час `T_wait` (тактів). Коли прибуває другий токен, він утворює пару з першим, і обидва операнди негайно вилучаються з пам'яті зіставлення.

За **теоремою Літтла** (*Little's Law*), середня кількість непарних операндів `N_store`, які одночасно перебувають у Matching Store у стаціонарному режимі, дорівнює добутку інтенсивності прибуття «перших» токенів на середній час очікування «другого» токена `W_match`:

```
N_store = (λ_bin / 2) · W_match
```

де:
* `λ_bin / 2` — інтенсивність прибуття саме перших токенів бінарних пар;
* `W_match = E[T_wait]` — математичне сподівання інтервалу між надходженням першого та другого операндів конкретної інструкції.

### Залежність часу очікування від глибини графа

Якщо вхідні дані для оператора генеруються двома паралельними гілками графа різної довжини `L₁` та `L₂` (тактів), то мінімальний час перебування першого токена в пам'яті становить:

```
W_match ≥ |L₁ − L₂|
```

При значному дисбалансі гілок (`|L₁ − L₂| ≫ 1`) обсяг пам'яті `N_store` стрімко зростає. Якщо середня інтенсивність генерації токенів становить `λ = 4` токени/такт, частка бінарних операцій `p₂ = 0.8`, а середній часовий перекіс між операндами `W_match = 50` тактів:

```
N_store = (0.8 · 4 / 2) · 50 = 1.6 · 50 = 80 токенів очікування
```

## 2. Порівняльний аналіз складності архітектур Matching Store

Порівняємо три фундаментальні підходи до реалізації блоку зіставлення: повністю асоціативну пам'ять (CAM), апаратну хеш-таблицю та Explicit Token Store (ETS).

### Повністю асоціативна пам'ять (CAM)

У CAM кожен запис містить компаратор тега розміром `B_tag` біт.
* **Апаратна площа**: площа комірки CAM у `4–6` разів перевищує площу стандартної комірки SRAM:

```
Area_CAM ≈ N_slots · (Area_SRAM_bit · B_data + Area_CAM_bit · B_tag)
Area_CAM = O(N_slots · (B_data + 6 · B_tag))
```

* **Енергія одного пошуку**: під час кожного запиту активуються всі `N_slots` ліній збігу:

```
E_search = N_slots · C_matchline · V_dd²
E_search = O(N_slots)
```

При зростанні кількості паралельних потоків `N_slots` від `10³` до `10⁶` енергоспоживання CAM масштабується лінійно `O(N)`, що робить великі CAM фізично нереалізовними.

### Апаратна хеш-таблиця (Manchester Model)

Тег відображається у `M` слотів пам'яті за допомогою хеш-функції `h(Tag) = (Tag · K) mod M`. Коефіцієнт завантаження таблиці становить:

```
α = N_store / M
```

При вирішенні колізій методом відкритих ланцюжків (*chaining*) середня кількість звернень до пам'яті для невдалого пошуку (перший токен пари) та вдалого пошуку (другий токен пари) дорівнює:

```
Probes_first  = 1 + α
Probes_second = 1 + α / 2
```

Якщо коефіцієнт завантаження `α = 0.8`, пошук пари вимагає в середньому `1.4` звернень до SRAM. Проте при пікових сплесках (`α → 1`) максимальна довжина ланцюжка колізій `L_max` зростає логарифмічно:

```
E[L_max] = O((ln M) / (ln(ln M)))
```

Це вносить стохастичну варіацію затримки (*latency jitter*), що руйнує ритмічність потокового конвеєра.

### Explicit Token Store (ETS)

В ETS тег операнда містить безпосередній покажчик кадру активації `FP` та статичне зміщення слота `r`:

```
Addr = FP + r
```

* **Апаратна площа**: стандартна статична пам'ять SRAM без додаткових компараторів:

```
Area_ETS = O(N_slots · (B_data + 1))    [1 біт присутності на слот]
```

* **Часова складність**: строго детермінована за 1 такт:

```
Latency_ETS = 1 такт (константа)
E_search_ETS = O(1)
```

| Параметр | Повністю асоціативна CAM | Апаратна хеш-таблиця | Explicit Token Store (ETS) |
| :--- | :--- | :--- | :--- |
| **Час доступу (Latency)** | 1–2 такти (фіксований) | `1 + α/2` тактів (випадковий) | 1 такт (строго детермінований) |
| **Енергія на операцію** | `O(N)` (масштабується з ємністю) | `O(1 + α)` (локальні читання) | `O(1)` (одне звернення до SRAM) |
| **Щільність пам'яті** | Дуже низька (6 транзисторів + компаратор) | Висока (стандартна SRAM) | Максимальна (SRAM + 1 біт присутності) |
| **Поведінка при піках** | Апаратне переповнення / дедлок | Деградація затримки через колізії | Ізольоване виділення нових кадрів |

## 3. Математика `k`-обмежених циклів (k-Bounded Loops)

Розглянемо виконання циклу з `K` ітерацій, тіло якого містить `D` послідовних стадій обчислень.

Якщо в динамічній потоковій системі дозволити ітераціям розгортатися абсолютно вільно, то генеруючі інструкції заголовка циклу (інкремент лічильника, перевірка умов) можуть випередити повільні операції тіла на тисячі кроків.

### Експоненційний вибух пам'яті

Нехай крок інкременту лічильника виконується за `1` такт, а обчислення тіла циклу триває `T_body = 100` тактів. За відсутності штучного обмеження через `100` тактів у системі одночасно співіснуватимуть токени для `100` паралельних ітерацій.

Необхідний обсяг пам'яті для зберігання операндів зростає лінійно з кількістю розгорнутих ітерацій:

```
Mem_unbounded = K · S_frame
```

де `S_frame` — розмір кадру активації однієї ітерації в словах. Якщо `K = 10⁶` і `S_frame = 16` слів, потреба в пам'яті сягне `16 × 10⁶` слів, що спричинить переповнення пам'яті ETS.

### Теорема про пропускну здатність конвеєра та оптимальне `k`

Щоб запобігти вибуху пам'яті, цикл обмежується константою `k`: у кожен момент часу активними можуть бути **не більше ніж `k` одночасних ітерацій**. Це реалізується за допомогою закільцьованих токенів-дозволів (*acknowledgment tokens*).

Пропускна здатність конвеєра циклу `Throughput(k)` як функція параметра `k` визначається співвідношенням:

```
Throughput(k) = min( 1 / T_crit,  k / T_body )
```

де:
* `T_crit` — час найдовшого критичного шляху між послідовними ітераціями (ініціалізація наступного кроку);
* `T_body` — повна затримка проходження всіх стадій тіла циклу від входу до виходу.

Графік залежності має точку насичення:
1. При `k < k_opt` пропускна здатність обмежена нестачею паралелізму (`k / T_body < 1 / T_crit`). Конвеєр недовантажений.
2. При `k ≥ k_opt` досягається максимальна теоретична продуктивність `1 / T_crit`. Подальше збільшення `k` не додає швидкості, а лише лінійно витрачає пам'ять.

Оптимальне значення `k` розраховується як відношення повної затримки тіла до критичного інтервалу:

```
k_opt = ⌈ T_body / T_crit ⌉
```

### Приклад розрахунку

Нехай тіло циклу обробки сигналу містить конвеєр із загальною затримкою `T_body = 24` такти. Крок інкременту лічильника та генерація покажчика на наступний кадр займає `T_crit = 3` такти.

```
k_opt = ⌈ 24 / 3 ⌉ = 8
```

* Якщо встановити `k = 4`: продуктивність становить `4 / 24 = 0.166` ітерацій/такт (недовантаження на 50%).
* Якщо встановити `k = 8`: продуктивність сягає пікового максимуму `1 / 3 = 0.333` ітерацій/такт при фіксованому обсязі пам'яті лише `8 · S_frame`.
* Збільшення `k` до `64` дасть ту саму швидкість `0.333` ітерацій/такт, але витратить у 8 разів більше пам'яті.

## 4. Моделювання затримок черги відкладених читань I-структур

Пам'ять I-структур підтримує нестрогу модель доступу: читачі можуть запитувати комірку до того, як у неї записано значення.

Нехай запити на читання комірки `I[x]` надходять за пуассонівським процесом з інтенсивністю `λ_r`. Запис значення продюсером відбувається у випадковий момент часу `T_write`, розподілений експоненційно з параметром `μ_w`:

```
P(T_write ≤ t) = 1 − e^(−μ_w · t)
```

Кількість читачів `M_def`, які встигають надійти до моменту запису та осідають у списку відкладених запитів (*deferred list*), є дискретною випадковою величиною.

Імовірність того, що в черзі відкладених запитів опиниться рівно `m` читачів, описується геометричним розподілом:

```
P(M_def = m) = (μ_w / (λ_r + μ_w)) · (λ_r / (λ_r + μ_w))^m
```

Математичне сподівання кількості читачів у відкладеній черзі:

```
E[M_def] = λ_r / μ_w
```

### Затримка спорожнення відкладеної черги

Коли продюсер нарешті виконує операцію `WRITE`, контролер I-структури повинен розіслати `m` вихідних токенів усім підписаним споживачам.

Якщо контролер пам'яті здатен генерувати один токен відповіді за `1` такт, сумарна затримка очищення списку очікування становить:

```
T_flush = m · 1 такт
```

Щоб запобігти перевантаженню мережі маршрутизації токенів при пробудженні масових читачів (`m ≫ 1`), апаратний контролер I-структур використовує **ієрархічне копіювання токенів** (бінарне дерево розмноження), що знижує затримку розсилки з лінійної `O(m)` до логарифмічної:

```
T_flush_tree = ⌈log₂ m⌉ · T_branch
```

Це гарантує, що навіть при одночасному читанні одного глобального параметра тисячами паралельних вузлів час розповсюдження результату залишається в межах кількох десятків машинних тактів.
