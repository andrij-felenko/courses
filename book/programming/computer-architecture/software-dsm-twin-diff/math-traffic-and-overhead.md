# 🧮 Математична модель мережного трафіку та накладних витрат Twin-and-Diff

Оцінка ефективності протоколів розподіленої пам'яті вимагає точного кількісного аналізу двох конкуруючих процесів: з одного боку, обчислювальних витрат на обробку апаратних виключень та пословне сканування пам'яті; з іншого боку, затримок передачі пакетів через мережу. Математична модель встановлює точну межу беззбитковості (Break-Even Threshold), показуючи, за якого ступеня модифікації сторінки побайтова генерація різниці перевершує пряму передачу кадрів пам'яті.

## Модель мережного трафіку: коефіцієнт стиснення даних

Нехай розмір віртуальної сторінки дорівнює `S_page` байтів (стандартно `4096` байтів). Під час робочої епохи потік виконує модифікацію `k` неперервних діапазонів пам'яті, сумарний розмір змінених даних у яких становить `B_mod` байтів.

У протоколі з одним записувачем (Single-Writer) будь-яка ненульова зміна вимагає передачі всієї сторінки разом із мережними заголовками протоколу `H_net`:

```
V_single = S_page + H_net
```

У протоколі Twin-and-Diff кожен із `k` змінених діапазонів кодується дескриптором `(offset, length)` розміром `H_chunk` байтів (у компактному вирівнюванні `H_chunk = 4` байти: 2 байти на зсув та 2 байти на довжину). Загальний обсяг переданих корисних даних складає:

```
V_diff = k·H_chunk + B_mod + H_net
```

Коефіцієнт скорочення мережного трафіку `C_traffic` визначається відношенням обсягів:

```
C_traffic
= 1 - (V_diff ÷ V_single)                                          [означення економії каналу]
= 1 - ((k·H_chunk + B_mod + H_net) ÷ (S_page + H_net))             [підстановка виразів обсягу]
```

Для типового випадку розрідженого оновлення (наприклад, зміна двох 8-байтних лічильників у різних кінцях 4 КБ сторінки: `k = 2`, `B_mod = 16`, `H_chunk = 4`, `S_page = 4096`, `H_net = 64` байти TCP/IP):

```
V_single = 4096 + 64 = 4160 байтів
V_diff   = 2·4 + 16 + 64 = 88 байтів

C_traffic
= 1 - (88 ÷ 4160)
= 1 - 0.02115
= 0.97885                                                          [економія 97.88% мережного трафіку]
```

## Часова модель затримок та точка беззбитковості (Break-Even Point)

Порівняємо сумарний час виконання епохи модифікації для обох протоколів.

Нехай:
- `T_fault` — час перехоплення сторінкового збою, копіювання двійника та виконання `mprotect` (приблизно `3.5` мкс).
- `T_scan` — час пословного сканування 4 КБ сторінки процесором (приблизно `0.5` мкс).
- `R_net` — ефективна швидкість передачі даних мережею (наприклад, `1000` Мбіт/с = `125` МБ/с = `0.125` байта/нс).
- `L_net` — базова латентність проходження пакета (RTT через комутатор, приблизно `30` мкс у 1G Ethernet або `2` мкс у мережах InfiniBand).

Сумарний час передачі сторінки у протоколі Single-Writer:

```
T_single = L_net + (S_page ÷ R_net)
```

Сумарний час генерації та передачі у протоколі Twin-and-Diff:

```
T_twin = T_fault + T_scan + L_net + ((k·H_chunk + B_mod) ÷ R_net)
```

Точка беззбитковості досягається за умови `T_twin = T_single`. Знайдемо критичний обсяг модифікацій `B_mod*`, вище якого накладні витрати сканування та дескрипторів зрівнюються з передачею всієї сторінки:

```
T_fault + T_scan + L_net + ((k·H_chunk + B_mod*) ÷ R_net) = L_net + (S_page ÷ R_net)
T_fault + T_scan + ((k·H_chunk + B_mod*) ÷ R_net) = S_page ÷ R_net                       [скорочення L_net]
(k·H_chunk + B_mod*) ÷ R_net = (S_page ÷ R_net) - (T_fault + T_scan)                     [перенесення витрат CPU]
k·H_chunk + B_mod* = S_page - R_net·(T_fault + T_scan)                                   [множення на швидкість мережі]
B_mod* = S_page - k·H_chunk - R_net·(T_fault + T_scan)                                   [критичний обсяг модифікованих байтів]
```

Обчислимо критичну частку сторінки `α* = B_mod* ÷ S_page` для трьох різних поколінь мережного обладнання:

1. **Мережа 1 Gbps Ethernet (`R_net = 125` Б/мкс, `T_fault + T_scan = 4.0` мкс, `k = 4`):**
```
B_mod* = 4096 - 16 - 125·4.0 = 3580 байтів
α* = 3580 ÷ 4096 = 0.874                                           [87.4% площі сторінки]
```

2. **Мережа 10 Gbps Ethernet (`R_net = 1250` Б/мкс, `T_fault + T_scan = 2.5` мкс за рахунок AVX-512, `k = 4`):**
```
B_mod* = 4096 - 16 - 1250·2.5 = 4080 - 3125 = 955 байтів
α* = 955 ÷ 4096 = 0.233                                            [23.3% площі сторінки]
```

3. **Мережа 100 Gbps InfiniBand / RDMA (`R_net = 12500` Б/мкс, `T_fault + T_scan = 0.2` мкс з `userfaultfd`, `k = 2`):**
```
B_mod* = 4096 - 8 - 12500·0.2 = 4088 - 2500 = 1588 байтів
α* = 1588 ÷ 4096 = 0.388                                           [38.8% площі сторінки]
```

**Аналітичний висновок:** На стандартних мережах Gigabit Ethernet побайтове обчислення різниці є ефективнішим за надсилання всієї сторінки, якщо змінено менше ніж 87.4% байтів сторінки. У надшвидкісних мережах 10G/100G з прямим доступом до пам'яті (RDMA) точка переходу зміщується до 23–38%, що мотивує гібридні протоколи автоматично перемикатися на передачу повної сторінки при виявленні щільних масивних записів.

## Ймовірнісна модель хибного спільного використання

Розглянемо кластер із `N` обчислювальних вузлів, які одночасно виконують незалежні випадкові записи у глобальний спільний масив розміром `M` сторінок. Кожен вузол за епоху виконує `w` рівномірно розподілених записів у різні елементи.

Ймовірність того, що конкретний запис одного вузла потрапить у фіксовану сторінку `P`, дорівнює:

```
p = 1 ÷ M
```

Ймовірність того, що вузол зробить принаймні один запис у сторінку `P`:

```
P_write_node = 1 - (1 - p)ʷ ≈ 1 - e^(-w/M)
```

Ймовірність виникнення конфлікту хибного спільного використання `P_conflict` (ситуація, коли два або більше незалежних вузлів одночасно пишуть у ту саму сторінку `P` протягом однієї епохи) описується біноміальним розподілом:

```
P_conflict = 1 - (1 - P_write_node)ᴺ - N·P_write_node·(1 - P_write_node)ᴺ⁻¹
```

Якщо `M = 1000` сторінок, `N = 16` вузлів, а кожен вузол змінює `w = 100` випадкових змінних:

```
P_write_node
= 1 - e^(-100 / 1000)
= 1 - e^(-0.1)
≈ 1 - 0.9048
= 0.0952                                                           [ймовірність торкнутися сторінки = 9.52%]
```

Обчислимо ймовірність конфлікту хибного спільного використання:

```
(1 - P_write_node)ᴺ = (1 - 0.0952)¹⁶ = 0.9048¹⁶ ≈ 0.1986            [нуль вузлів записали в P]
N·P_write_node·(1 - P_write_node)ᴺ⁻¹ = 16·0.0952·0.9048¹⁵ ≈ 0.3340   [рівно один вузол записав у P]

P_conflict
= 1 - 0.1986 - 0.3340
= 0.4674                                                           [46.74% ймовірність конфлікту на сторінку]
```

При зростанні кількості вузлів `N → ∞` при фіксованій кількості сторінок `M` ймовірність конфлікту наближається до одиниці: `lim_{N → ∞} P_conflict = 1.0`. Це математично доводить, що системи з одним записувачем мають фундаментальне обмеження масштабованості: додавання нових серверів у кластер не прискорює, а експоненційно сповільнює виконання через взаємне блокування сторінок.

У системі з одним записувачем (Single-Writer) майже половина (46.7%) активних сторінок зазнає сторінкового пінг-понгу, повністю блокуючи паралельне виконання. У протоколі Twin-and-Diff усі ці 46.7% конфліктних сторінок обробляються абсолютно паралельно без жодного взаємного блокування.

## Оптимізація довжини ланцюжка дельт та поріг консолідації

У моделі лінивої узгодженості (Lazy Release Consistency) відмінності сторінки накопичуються в ланцюжок дельт довжиною `L` (`Δ₁ → Δ₂ → ... → Δ_L`).

Коли віддалений вузол звертається до застарілої сторінки, він повинен завантажити всі `L` пакетів різниць та послідовно застосувати їх. Нехай `D_avg` — середній розмір одного diff-пакета, `T_apply` — час накладання одного пакета в пам'яті.

Сумарний час відновлення сторінки через ланцюжок дельт:

```
T_restore_diff(L) = L_net + (L·D_avg ÷ R_net) + L·T_apply
```

Час повного оновлення через завантаження цілої свіжої сторінки з координатора:

```
T_restore_page = L_net + (S_page ÷ R_net) + T_copy
```

Оптимальний поріг довжини ланцюжка `L*`, після якого середовище зобов'язане виконати консолідацію сторінки (Garbage Collection):

```
T_restore_diff(L*) = T_restore_page
L_net + L*·(D_avg ÷ R_net + T_apply) = L_net + (S_page ÷ R_net) + T_copy
L*·(D_avg ÷ R_net + T_apply) = (S_page ÷ R_net) + T_copy                                  [скорочення L_net]
L* = ((S_page ÷ R_net) + T_copy) ÷ ((D_avg ÷ R_net) + T_apply)                           [формула оптимального порогу довжини ланцюжка]
```

Для типових параметрів 1G Ethernet (`S_page = 4096`, `D_avg = 64`, `R_net = 125`, `T_copy = 0.2` мкс, `T_apply = 0.05` мкс):

```
Чисельник  = (4096 ÷ 125) + 0.2 = 32.768 + 0.2 = 32.968 мкс
Знаменник  = (64 ÷ 125) + 0.05 = 0.512 + 0.05 = 0.562 мкс

L*
= 32.968 ÷ 0.562
≈ 58.6                                                             [поріг консолідації: 58-59 дельт]
```

Додатково слід враховувати накладні витрати пам'яті на зберігання двійників (Memory Space Overhead). Якщо робочий набір запису (Write Working Set) процесу охоплює `W` активних сторінок, сумарний обсяг пам'яті під буфери двійників становить:

```
M_twins = W · S_page
```

Оскільки двійники існують виключно під час активної епохи запису та знищуються під час виклику `lock_release()` або `barrier()`, пікове споживання пам'яті пропорційне не загальному розміру спільного масиву `M`, а лише числу сторінок `W`, змінених між двома точками синхронізації (`W ≪ M`).

**Висновки моделі:** Середовище DSM може безпечно накопичувати до 50–58 послідовних невеликих відмінностей у ланцюжку до того, як витрати на їх передачу та накладання зрівняються з витратами на завантаження повного 4-кілобайтного образу сторінки.
