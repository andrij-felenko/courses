# ⚙️ Niche filling та Non-Zero оптимізація в дії

У традиційній моделі типізованих мов програмування тип-сума (англ. *tagged union*, або варіант) складається з двох обов'язкових компонентів: тегу дискримінанта (англ. *discriminant*), який позначає активний стан, та області пам'яті для збереження корисного навантаження (англ. *payload*).

Через жорсткі вимоги сучасних процесорів до вирівнювання пам'яті (англ. *memory alignment*) наївна реалізація типу-обгортки `Option<T>` дуже часто подвоює споживання оперативної пам'яті.

---

### Анатомія проблеми: роздуття пам'яті через вирівнювання

Розгляньмо типову структуру, що реалізує аналог `Option<uint32_t>` на низькому рівні.

:::tabs
```c
#include <stdint.h>
#include <stdbool.h>

// Наївна структура Option для 32-бітного числа
struct NaiveOptionalU32 {
    uint32_t value;  // 4 байти (корисне навантаження)
    bool has_value;  // 1 байт (тег дискримінанта)
    // Компілятор змушений додати 3 байти невидимого паддінгу!
}; // Загальний sizeof = 8 байтів!
```
```cpp
#include <cstdint>
#include <optional>

// У стандартному C++ std::optional<uint32_t> поводиться так само
struct ManualOptionalU32 {
    uint32_t value{0};
    bool has_value{false};
    // 3 байти сміття (padding) для збереження вирівнювання за 4 байти
};

static_assert(sizeof(ManualOptionalU32) == 8);
static_assert(sizeof(std::optional<uint32_t>) == 8);
```
:::

Щоб зберегти 4 байти корисного числа зі статусом його наявності, компілятор виділяє 8 байтів. Накладні витрати пам'яті становлять рівно **100%**.

Формула розрахунку байтів заповнення (паддінгу) визначається кратністю адреси: якщо поле розміром `S` вимагає вирівнювання `A`, то зміщення наступного поля повинно бути обов'язково кратним `A`. Для структури з полем `bool` (1 байт) та `uint32_t` (4 байти) компілятор вставляє 3 байти порожнечі між полями або наприкінці структури, щоб наступний елемент у масиві також потрапив на 4-байтну межу.

Якщо високонавантажений сервіс або ігровий рушій зберігає вектор із 50 мільйонів таких елементів, програма виділяє 400 мегабайтів оперативної пам'яті, з яких **200 мегабайтів є абсолютно марним сміттям (паддінгом)**. Ба більше, це сміття суттєво погіршує ефективність використання кеш-ліній процесора (L1/L2 data cache), оскільки половина переданих шиною байтів не містить жодної корисної інформації.

### Ідея «ніші» (Type Niche)

**Ніша типу** (англ. *type niche*) — це конкретна бітова комбінація (патерн нулів та одиниць), яка строго заборонена семантикою самого типу даних і гарантовано не може виникнути у валідному об'єкті під час нормального виконання програми.

Компілятор, який підтримує оптимізацію заповнення ніш (англ. *niche-filling optimization*), знаходить такі невикористані бітові комбінації та використовує їх для кодування службових варіантів переліків (зокрема стану `None`), **повністю ліквідуючи окремий байт тегу дискримінанта**.

#### Таблиця природних ніш у популярних типах:

| Тип даних | Розмір у пам'яті | Діапазон валідних значень | Невикористані бітові ніші | Можливість Niche-filling |
| :--- | :--- | :--- | :--- | :--- |
| **Покажчик / Посилання (`&T`, `*const T`)** | 8 байтів | `0x0000000000000001 .. 0xFFFFFFFFFFFFFFFF` | `0x0000000000000000` (нуль) | `Option<&T>` займає рівно 8 байтів! |
| **`NonZeroU32`** | 4 байти | `1 .. 4 294 967 295` | `0x00000000` (нуль) | `Option<NonZeroU32>` займає 4 байти! |
| **`bool`** | 1 байт | `0x00` (`false`), `0x01` (`true`) | `0x02 .. 0xFF` (254 вільні ніші!) | До 254 додаткових варіантів у 1 байті! |
| **`enum Char` (Unicode)** | 4 байти | `0x0000 .. 0xD7FF`, `0xE000 .. 0x10FFFF` | `0xD800..0xDFFF`, `> 0x10FFFF` | Мільйони вільних ніш |

### Практичний аналіз: Rust та C++

Подивімося, як концепція ніш виглядає на практиці в мовах Rust та C++.

:::tabs
```rust
use std::mem::size_of;
use std::num::NonZeroU32;

fn main() {
    // 1. Звичайний Option<u32>: 4 байти payload + 1 байт тег + 3 байти padding = 8 байтів
    println!("sizeof(Option<u32>):          {} байтів", size_of::<Option<u32>>()); // 8

    // 2. Option<NonZeroU32>: 0 кодує None -> рівно 4 байти (0% оверхеду!)
    println!("sizeof(Option<NonZeroU32>):  {} байти",  size_of::<Option<NonZeroU32>>()); // 4

    // 3. Option<&i32>: null вказівник кодує None -> рівно 8 байтів
    println!("sizeof(Option<&i32>):        {} байтів", size_of::<Option<&i32>>()); // 8

    // 4. Багатошарове вкладення в тип bool завдяки 254 вільним нішам:
    // Option<bool> використовує нішу 2 для None -> 1 байт!
    println!("sizeof(Option<bool>):        {} байт",   size_of::<Option<bool>>()); // 1
    // Option<Option<bool>> використовує нішу 3 для зовнішнього None -> все ще 1 байт!
    println!("sizeof(Option<Option<bool>>): {} байт",  size_of::<Option<Option<bool>>>()); // 1
}
```
```cpp
#include <iostream>
#include <optional>
#include <cstdint>
#include <cassert>

// Ручна реалізація Niche-оптимізованого Optional для ненульових ідентифікаторів у C++
template <typename T, T SentinelValue = 0>
class CompactOptional {
    T value_{SentinelValue};

public:
    constexpr CompactOptional() noexcept = default;
    constexpr CompactOptional(T val) noexcept : value_(val) {
        assert(val != SentinelValue && "Значення не може дорівнювати вартовому!");
    }

    [[nodiscard]] constexpr bool has_value() const noexcept {
        return value_ != SentinelValue;
    }

    [[nodiscard]] constexpr T value() const noexcept {
        return value_;
    }
};

int main() {
    // Стандартний std::optional<uint32_t>: займає 8 байтів через паддінг тегу bool
    std::cout << "sizeof(std::optional<uint32_t>): "
              << sizeof(std::optional<uint32_t>) << " байтів\n"; // 8

    // Компактний варіант: використовує 0 як in-band вартовий, займає рівно 4 байти!
    std::cout << "sizeof(CompactOptional<uint32_t>): "
              << sizeof(CompactOptional<uint32_t>) << " байти\n"; // 4

    CompactOptional<uint32_t> opt(42);
    if (opt.has_value()) {
        std::cout << "Отримано значення: " << opt.value() << "\n";
    }

    return 0;
}
```
:::

### Асемблерна вигода: чому Niche-filling швидший за дискримінанти

Окрім драматичної економії пам'яті, використання ніш істотно покращує якість генерованого асемблерного коду.

#### Порівняння асемблера (x86-64) під час перевірки наявності значення:

**А. Звичайний `Option<u32>` з окремим тегом:**
Під час перевірки `if (opt.is_some())` процесор змушений виконати два звернення до оперативної пам'яті або стека:
```nasm
; Пам'ять структури: [rdi + 0] = value (4 байти), [rdi + 4] = tag (1 байт)
cmp     byte ptr [rdi + 4], 0     ; Читання #1: завантажуємо байт тегу
je      .L_is_none                ; Умовний перехід, якщо None
mov     eax, dword ptr [rdi]      ; Читання #2: завантажуємо саме 32-бітне число
```

**Б. Оптимізований `Option<NonZeroU32>` через нішу (вартовий 0):**
Оскільки значення передається безпосередньо в регістрі процесора, а нуль позначає стан відсутності, код стає ультракоротким:
```nasm
; Значення передане безпосередньо в регістрі eax
test    eax, eax                  ; Перевірка регістра на 0 (1 такт CPU)
jz      .L_is_none                ; Перехід, якщо 0 (None)
; Регістр eax ВЖЕ містить готове до використання число! Друге читання непотрібне!
```

Компілятор генерує всього одну регістрову інструкцію замість двох операцій читання з пам'яті. У конвеєрі процесора це прибирає залежності за даними (load-use latency), дозволяючи інструкціям виконуватися позачергово (out-of-order execution) на повній швидкості тактової частоти.

### Ніші вирівнювання покажчиків (Pointer Alignment Niches)

Ще одне потужне джерело ніш з'являється завдяки апаратному вирівнюванню адрес.

Коли об'єкт структури розміром 8 байтів або 16 байтів розміщується в динамічній пам'яті через системний алокатор (`malloc` або оператор `new`), його адреса завжди вирівнюється за 8 або 16 байтів. Це означає, що числове значення адреси завжди кратне 8 (або 16).

У двійковому поданні адреси, кратної 8, **три молодші біти завжди дорівнюють `0b000`**:

```
Вирівняна адреса (0x1000): ...0001 0000 0000 0000
Молодші три біти:                              ^^^ (завжди 000)
```

Компілятори та розробники високоефективних бібліотек (зокрема `PointerIntPair` у проекті LLVM) використовують ці 3 молодші біти як вбудовану нішу: у них можна упакувати ціле число від `0` до `7` або три незалежні булеві прапорці прямо всередині 64-бітного покажчика! Під час звернення до пам'яті маска `ptr & ~0x7` очищує молодші біти за 1 такт, повертаючи чисту адресу об'єкта.

### Що робити, коли тип не має природних ніш

Якщо тип даних використовує всі можливі комбінації бітів (наприклад, сирий байт `uint8_t` або звичайне ціле число `uint32_t`), автоматичне заповнення ніш стає неможливим, і компілятор змушений додавати окремий байт дискримінанта.

У таких сценаріях архітектори систем проектують спеціальні «типи-обгортки» (англ. *newtypes*):
1. **Обмеження фізичного діапазону**: якщо індекс сутності гарантовано не перевищує `1 000 000`, програміст оголошує тип, де значення `0xFFFFFFFF` резервується як вартовий стан на рівні конструктора.
2. **Семантичний зсув**: зміщення числових значень на `+1`, щоб число `0` завжди позначало порожнечу (індексація з одиниці на машинному рівні).

Це дозволяє створювати структури даних максимальної щільності в пам'яті з повним збереженням статичного контролю типів під час компіляції.

### Екстремальне використання ніш: NaN-boxing у віртуальних машинах

Найвідомішим прикладом екстремального використання бітових ніш у динамічних мовах (JavaScript у рушіях V8, SpiderMonkey та JavaScriptCore, Lua в LuaJIT) є архітектурна техніка **NaN-boxing**.

Стандарт чисел з рухомою комою IEEE 754 визначає 64-бітне число подвійної точності `double`:
- 1 біт знаку (`S`).
- 11 бітів експоненти (`E`).
- 52 біти мантиси (`M`).

Коли всі 11 бітів експоненти встановлені в одиниці (`0x7FF`), а старший біт мантиси дорівнює 1 (Quiet NaN), процесор інтерпретує значення як недійсне число. Решта **51 біт мантиси повністю ігноруються апаратним блоком FPU**.

```
Розкладка 64-бітного Quiet NaN:
[ S=0 | E = 11111111111 | Q=1 | 51 вільний біт для корисних даних! ]
```

Оскільки на сучасних 64-бітних архітектурах x86-64 та ARM64 віртуальні адреси вказівників займають лише 48 бітів, розробники віртуальних машин розміщують 48-бітний покажчик на об'єкт прямо всередині цих 51 біта мантиси Quiet NaN!

Усі типи мови JavaScript (числа, рядки, булеві значення, `null`, `undefined` та об'єкти) упаковуються в рівно 8 байтів пам'яті без жодного окремого поля тегу типу. Якщо біти експоненти не дорівнюють `0x7FF`, це звичайне число `double`; якщо дорівнюють — молодші біти мантиси розкривають тип і значення об'єкта.
