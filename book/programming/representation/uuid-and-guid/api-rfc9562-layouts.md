# 📋 Специфікація розкладок та бітових масок UUID (RFC 9562 та GUID)

Цей довідник містить повну технічну специфікацію двійкових розкладок, бітових масок, алгоритмів валідації та структур пам'яті для всіх версій універсальних ідентифікаторів, стандартизованих у специфікації IETF RFC 9562 (яка повністю замінила й скасувала застарілий RFC 4122), а також особливості подання двійкової структури Microsoft GUID.

---

### 1. Канонічний текстовий формат (8-4-4-4-12) та його варіації

Стандарт RFC 9562 закріплює канонічну форму запису 128-бітного ідентифікатора у вигляді 32 шістнадцяткових цифр у нижньому регістрі (`lowercase`), розділених чотирма дефісами на п'ять позиційних блоків:

```
xxxxxxxx-xxxx-Mxxx-Nxxx-xxxxxxxxxxxx
```

| Позиція символів | Довжина у hex | Розмір у байтах | Назва поля за DCE / RFC | Опис бітового вмісту |
|:---|:---|:---|:---|:---|
| `0..7` | 8 знаків | 4 байти (32 біти) | `time_low` | Молодші 32 біти часової мітки або старші 32 біти Unix-часу |
| `9..12` | 4 знаки | 2 байти (16 бітів) | `time_mid` | Середні 16 бітів часової мітки або решта 16 бітів Unix-часу |
| `14..17` | 4 знаки | 2 байти (16 бітів) | `time_hi_and_version` | Старші 12 бітів часу/лічильника з 4-бітним полем версії `M` у старшому ніблі |
| `19..22` | 4 знаки | 2 байти (16 бітів) | `clk_seq_and_variant` | Старші 2–3 біти варіанта `N` + лічильник послідовності або ентропія |
| `24..35` | 12 знаків | 6 байтів (48 бітів) | `node` | 48 бітів фізичної MAC-адреси IEEE 802 або криптографічної ентропії |

Крім канонічного вигляду, у промислових системах зустрічаються чотири поширені текстові варіанти:
1. **URN-формат**: `urn:uuid:f81d4fae-7dec-11d0-a765-00a0c91e6bf6` (використовується в протоколах IETF, SOAP, XML та стандартизованих схемах даних).
2. **Формат фігурних дужок Microsoft**: `{f81d4fae-7dec-11d0-a765-00a0c91e6bf6}` (стандартний запис ідентифікаторів класів CLSID та інтерфейсів IID у системному реєстрі Windows та файлах IDL).
3. **Компактний шістнадцятковий запис (без дефісів)**: `f81d4fae7dec11d0a76500a0c91e6bf6` (32 символи, часто застосовується в URL-шляхах, компактних JSON-структурах і ключах NoSQL баз даних).
4. **Base64 / Base58 кодування**: двійкові 16 байтів кодуються у 22 символи Base64 або Base58 (наприклад, у бібліотеках генерації коротких ідентифікаторів).

### 2. Поле варіанта (Variant): бітова маска та правила декодування

Поле варіанта розташоване у найстарших бітах байта з індексом 8 (`clk_seq_hi_res`). Воно визначає, якій саме специфікації підпорядковується внутрішня структура полів:

| Бітова маска (старші розряди) | Варіант (десятковий) | Діапазон значень `byte[8]` | Hex-символ `N` | Специфікація та призначення |
|:---|:---|:---|:---|:---|
| `0xx` (старший біт `0`) | 0 | `0x00 .. 0x7F` | `0 .. 7` | Зворотна сумісність з Apollo Network Computing System (NCS 1.x) |
| `10x` (старші біти `10`) | 2 | `0x80 .. 0xBF` | `8, 9, a, b` | Стандарт IETF: RFC 4122, RFC 9562, OSF DCE 1.1, Leach-Salz |
| `110` (старші біти `110`) | 6 | `0xC0 .. 0xDF` | `c, d` | Зворотна сумісність з Microsoft Component Object Model (COM / DCOM) |
| `111` (старші біти `111`) | 7 | `0xE0 .. 0xFF` | `e, f` | Зарезервовано для майбутніх розширень стандарту IETF |

#### Побітові операції для поля варіанта

* **Вилучення номера варіанта**:
  Якщо `(byte[8] & 0x80) == 0x00` — варіант 0 (Apollo).
  Якщо `(byte[8] & 0xC0) == 0x80` — варіант 2 (RFC 9562 / IETF).
  Якщо `(byte[8] & 0xE0) == 0xC0` — варіант 6 (Microsoft COM).
  Якщо `(byte[8] & 0xE0) == 0xE0` — варіант 7 (Reserved).

* **Встановлення варіанта RFC 9562**:
  `byte[8] = (byte[8] & 0x3F) | 0x80;` (очищення двох старших бітів та запис бітів `10xxxxxx`).

### 3. Таблиця версій UUID у стандарті RFC 9562

Поле версії займає 4 біти у старшому ніблі байта з індексом 6 (`time_hi_and_version`).

* **Вилучення версії**: `version = (byte[6] >> 4) & 0x0F;`
* **Встановлення версії**: `byte[6] = (byte[6] & 0x0F) | (version << 4);`

| Версія `M` | Офіційна назва стандарту | Базовий алгоритм генерації | Властивість сортування | Статус у RFC 9562 |
|:---|:---|:---|:---|:---|
| `0x1` (1) | Gregorian Time + Node | 60-бітний григоріанський час (100 нс) + 14-біт лічильник + 48-біт MAC | Частково сортований | Застарілий (Legacy) |
| `0x2` (2) | DCE Security | Часова мітка + інтеграція локального POSIX UID/GID | Не сортований | Спеціалізований |
| `0x3` (3) | MD5 Name-Based | Детермінований MD5-геш від `(Namespace_UUID + Name)` | Не сортований | Заборонений (Do Not Use) |
| `0x4` (4) | Cryptographic Random | 122 біти чистої ентропії від генератора CSPRNG | Повністю хаотичний | Загального вжитку |
| `0x5` (5) | SHA-1 Name-Based | Детермінований SHA-1 геш від `(Namespace_UUID + Name)` | Не сортований | Рекомендований для назв |
| `0x6` (6) | Reordered Time + Node | 60-бітний григоріанський час старшими бітами вперед + MAC | Монотонно сортований | Для міграції з v1 |
| `0x7` (7) | Unix Epoch Time + Rand | 48-бітний Unix-час (мс) + 12-біт суб-мс/лічильник + 62 біти ентропії | Монотонно сортований | Основний для БД |
| `0x8` (8) | Custom / Vendor Layout | Користувацькі 128-бітні дані з фіксацією версії та варіанта | Залежить від схеми | Експериментальний |

### 4. Порозрядні схеми бітових полів за версіями

#### UUIDv1 (Gregorian Time + MAC Address)
Схема зворотної сумісності DCE RPC:
- Байти `0..3` (`time_low`): молодші 32 біти 60-бітного числа 100-наносекундних інтервалів від 15 жовтня 1582 року.
- Байти `4..5` (`time_mid`): середні 16 бітів часової мітки.
- Байти `6..7` (`time_hi_and_ver`): старші 4 біти — значення `0x1`, молодші 12 бітів — старша частина 60-бітного часу.
- Байти `8..9` (`clk_seq`): старші 2 біти — варіант `10`, решта 14 бітів — лічильник послідовності годинника.
- Байти `10..15` (`node`): 48 бітів апаратної MAC-адреси мережевого інтерфейсу IEEE 802.

#### UUIDv2 (DCE Security Version)
Спеціалізований формат безпеки OSF DCE:
- Байти `0..3` (`local_domain_id`): 32-бітний числовий ідентифікатор локального користувача (POSIX UID) або групи (POSIX GID).
- Байти `4..5` (`time_mid`): середні 16 бітів григоріанського часу.
- Байти `6..7` (`time_hi_and_ver`): старші 4 біти — версія `0x2`, молодші 12 бітів — старша частина часу.
- Байт `8`: старші 2 біти — варіант `0b10`, молодші 6 бітів — старша частина лічильника.
- Байт `9` (`local_domain`): ідентифікатор домену безпеки (0 = Person/UID, 1 = Group/GID, 2 = Org).
- Байти `10..15` (`node`): 48 бітів MAC-адреси.

#### UUIDv4 (Повністю випадковий)
Схема максимальної ентропії:
- Байти `0..5`: 48 бітів криптографічно стійкої випадкової ентропії.
- Байт `6`: старший нібл — версія `0x4` (`0b0100`), молодший нібл — 4 біти ентропії.
- Байт `7`: 8 бітів ентропії.
- Байт `8`: старші 2 біти — варіант `0b10`, молодші 6 бітів — ентропія.
- Байти `9..15`: 56 бітів випадкової ентропії.
- Разом чистої випадковості: `48 + 4 + 8 + 6 + 56 = 122` біти.

#### UUIDv6 (Перевпорядкований час v1)
Схема прямої міграції з версії 1 для підтримки B-дерев:
- Байти `0..3` (`time_high`): старші 32 біти 60-бітного григоріанського часу.
- Байти `4..5` (`time_mid`): середні 16 бітів григоріанського часу.
- Байти `6..7` (`time_low_and_ver`): старші 4 біти — версія `0x6` (`0b0110`), молодші 12 бітів — молодша частина григоріанського часу.
- Байти `8..15`: повністю ідентичні полям `clk_seq` та `node` версії 1.

#### UUIDv7 (Unix Epoch Time + Monotonic Random)
Сучасний стандарт для розподілених систем і баз даних:
- Байти `0..5` (`unix_ts_ms`): 48-бітне беззнакове ціле число мілісекунд від початку епохи Unix (1970-01-01 00:00:00 UTC) у порядку Big-Endian.
- Байти `6..7`: старші 4 біти байта 6 — версія `0x7` (`0b0111`); наступні 12 бітів (`rand_a`) — субмілісекундна точність або монотонний лічильник послідовності всередині мілісекунди.
- Байт `8`: старші 2 біти — варіант `0b10`; молодші 6 бітів — старша частина випадкової ентропії `rand_b`.
- Байти `9..15`: молодші 56 бітів криптографічної ентропії `rand_b`.
- Разом ентропії та субмілісекундної послідовності: `12 + 6 + 56 = 74` біти.

#### UUIDv8 (Користувацька експериментальна розкладка)
Гнучкий формат для нестандартних або корпоративних протоколів:
- Байти `0..5` (`custom_a`): 48 бітів користувацьких даних (наприклад, 64-бітний Snowflake-ідентифікатор або наносекундний час).
- Байти `6..7`: старші 4 біти байта 6 — версія `0x8` (`0b1000`); решта 12 бітів — користувацьке поле `custom_b`.
- Байт `8`: старші 2 біти — варіант `0b10`; решта 6 бітів — частина `custom_c`.
- Байти `9..15`: 56 бітів користувацького поля `custom_c`.
- Загалом надає 122 вільні користувацькі біти, зберігаючи сумісність із парсерами RFC 9562.

### 5. Спеціальні ідентифікатори (Nil та Max)

Стандарт закріплює два спеціальні граничні значення 128-бітного адресного простору:

* **Nil UUID** (нульовий ідентифікатор):
  Усі 128 бітів встановлено в `0`.
  Канонічний рядок: `00000000-0000-0000-0000-000000000000`.
  Застосовується для позначення відсутності значення, неініціалізованого первинного ключа або порожнього посилання (еквівалент `NULL` чи покажчика `nullptr`).

* **Max UUID** (максимальний ідентифікатор):
  Усі 128 бітів встановлено в `1` (шістнадцяткове `0xFF`).
  Канонічний рядок: `ffffffff-ffff-ffff-ffff-ffffffffffff`.
  Застосовується у розподілених сховищах для позначення верхньої межі діапазонів запитів (Range Scans) або як маркер максимального елемента в алгоритмах фільтрації.

### 6. Константи стандартних просторів імен (Namespace UUIDs)

Для детермінованого перетворення назв у версіях UUIDv3 та UUIDv5 стандарт закріплює чотири глобальні простори імен:

| Назва простору імен | Двійкове значення (канонічний рядок) | Правила формування рядка імені |
|:---|:---|:---|
| **DNS** | `6ba7b810-9dad-11d1-80b4-00c04fd430c8` | Повне доменне ім'я FQDN у нижньому регістрі (наприклад, `example.com`) |
| **URL** | `6ba7b811-9dad-11d1-80b4-00c04fd430c8` | Канонічна адреса ресурсу URI/URL (наприклад, `https://ietf.org/rfc/rfc9562.txt`) |
| **OID** | `6ba7b812-9dad-11d1-80b4-00c04fd430c8` | Текстовий ідентифікатор об'єкта ISO/IEC OID у точковій нотації (наприклад, `2.5.4.3`) |
| **X.500** | `6ba7b814-9dad-11d1-80b4-00c04fd430c8` | Розпізнавальне ім'я Distinguished Name за стандартом LDAP/X.500 у бінарному DER-кодуванні |

### 7. Структура пам'яті Microsoft GUID та матриця перетворення

У середовищі Windows API тип `GUID` оголошено як мовну структуру C:

:::tabs
```c
/* Визначення у файлі <guiddef.h> (Windows SDK) */
typedef struct _GUID {
    unsigned long  Data1;    /* 32-бітне ціле без знаку (байти 0..3) */
    unsigned short Data2;    /* 16-бітне ціле без знаку (байти 4..5) */
    unsigned short Data3;    /* 16-бітне ціле без знаку (байти 6..7) */
    unsigned char  Data4[8]; /* 8 окремих беззнакових байтів (байти 8..15) */
} GUID;
```
```cpp
#include <array>
#include <cstdint>

struct WindowsGuid {
    uint32_t data1;               // 32-бітне ціле (Little-Endian у пам'яті x86/ARM)
    uint16_t data2;               // 16-бітне ціле (Little-Endian)
    uint16_t data3;               // 16-бітне ціле (Little-Endian)
    std::array<uint8_t, 8> data4; // 8 окремих байтів послідовно
};
```
:::

#### Матриця відповідності зміщень байтів у пам'яті

Таблиця нижче показує, який саме байт із канонічного 16-байтового масиву RFC 4122 / 9562 опиняється за кожним зміщенням адреси в оперативній пам'яті комп'ютера архітектури Little-Endian (x86, x64, ARM64) при використанні структури `GUID`:

| Зміщення в пам'яті | Поле `GUID` | Байт у пам'яті Little-Endian | Відповідний байт у масиві RFC 9562 |
|:---|:---|:---|:---|
| `+0` | `Data1` (байт 0) | Молодший байт `Data1` | Байт `3` масиву RFC |
| `+1` | `Data1` (байт 1) | Другий байт `Data1` | Байт `2` масиву RFC |
| `+2` | `Data1` (байт 2) | Третій байт `Data1` | Байт `1` масиву RFC |
| `+3` | `Data1` (байт 3) | Старший байт `Data1` | Байт `0` масиву RFC |
| `+4` | `Data2` (байт 0) | Молодший байт `Data2` | Байт `5` масиву RFC |
| `+5` | `Data2` (байт 1) | Старший байт `Data2` | Байт `4` масиву RFC |
| `+6` | `Data3` (байт 0) | Молодший байт `Data3` | Байт `7` масиву RFC |
| `+7` | `Data3` (байт 1) | Старший байт `Data3` | Байт `6` масиву RFC |
| `+8 .. +15` | `Data4[0..7]` | Байти масиву послідовно | Байти `8 .. 15` масиву RFC |

Ця специфікація вимагає обов'язкового порозрядного перетворення даних під час передачі двійкових ідентифікаторів між компонентами Windows COM та кросплатформними мережевими сервісами.
