# 📋 Довідник ключових слів JSON Schema Draft 2020-12

Специфікація JSON Schema Draft 2020-12 організована у вигляді модульних словників (Vocabularies), кожен із яких визначає замкнену множину ключових слів, їхній синтаксис та семантику обчислення. Мета-схема документа через директиву `$vocabulary` вказує валідатору, які саме модулі є обов'язковими для виконання, а які можуть ігноруватися без переривання процесу валідації. Такий модульний розподіл забезпечує розширюваність системи та дозволяє створювати спеціалізовані діалекти для генерації інтерфейсів, верифікації баз даних або перевірки мережевих контрактів.

Нижче наведено вичерпний опис структури контрактів, правил обчислення та взаємодії ключових слів між різними словниками стандарту.

---

## 1. Словник ядра та керування областю видимості (Core Vocabulary)

Словник ядра (`https://json-schema.org/draft/2020-12/vocab/core`) є обов'язковим для всіх валідаторів і визначає базові механізми ідентифікації документів, зміни простору імен, локалізації фрагментів та зв'язування зовнішніх ресурсів.

| Ключове слово | Допустимий тип | Призначення та семантика виконання |
| :--- | :--- | :--- |
| `$schema` | `string` (URI) | Декларує діалект та мета-схему, згідно з якою інтерпретується документ. Мусить знаходитися в корені схеми. |
| `$id` | `string` (URI) | Задає канонічний базовий URI (Base URI) для поточної схеми або вкладеного ресурсу. Змінює область видимості для відносних `$ref`. |
| `$anchor` | `string` (NCName) | Створює локальний іменований якір (Plain Name Fragment) всередині базового URI, дозволяючи посилання виду `#anchorName`. |
| `$dynamicAnchor` | `string` (NCName) | Оголошує динамічну точку розширення для поліморфного або рекурсивного перевизначення контексту виконання. |
| `$ref` | `string` (URI-reference) | Передає виконання за вказаною адресою (URI або JSON Pointer). У Draft 2020-12 обчислюється одночасно з іншими суміжними ключовими словами. |
| `$dynamicRef` | `string` (URI-reference) | Динамічне посилання, яке розв'язується на найглибший активний `$dynamicAnchor` у поточному ланцюгу викликів валідатора. |
| `$defs` | `object` | Сховище локальних підсхем. Сам по собі об'єкт `$defs` не валідує екземпляр, доки на його поля не посилається `$ref`. |
| `$comment` | `string` | Внутрішній коментар розробника. Повністю ігнорується рушієм валідації та генераторами звітів. |
| `$vocabulary` | `object` | Використовується в мета-схемах для оголошення набору обов'язкових і опціональних словників через пари `URI: boolean`. |

### Механіка нормалізації базового URI
Коли парсер зустрічає ключове слово `$id`, він нормалізує його значення відносно поточного базового URI за правилами RFC 3986. Якщо `$id` є абсолютним URI (наприклад, `https://api.example.com/v1/user.json`), він стає новим базовим URI для всього вкладеного піддерева. Якщо `$id` містить відносний шлях (наприклад, `sub/address.json`), він об'єднується з батьківським URI.

Будь-який фрагмент після символу `#` у значенні `$id` заборонений у Draft 2020-12. Для створення внутрішньодокументних міток використовується виключно ключове слово `$anchor`, значенням якого мусить бути валідний ідентифікатор без спеціальних символів (NCName за стандартом XML/W3C).

Динамічні якорі `$dynamicAnchor` та посилання `$dynamicRef` працюють як віртуальні точки зв'язування. Коли валідатор слідує за `$dynamicRef: "#node"`, він перевіряє поточний динамічний стек викликів від кореня до поточного вузла. Якщо у зовнішній схемі визначено якір з таким самим іменем, валідатор передає керування зовнішньому якорю, що забезпечує перевизначення базових типів у рекурсивних структурах без мутації вихідної схеми.

## 2. Словник валідації типів та значень (Type Assertions)

Словник валідації (`https://json-schema.org/draft/2020-12/vocab/validation`) містить предикати, які безпосередньо перевіряють примітивні типи та скалярні значення екземпляра.

| Ключове слово | Допустимий тип | Застосовується до | Опис валідаційного правила |
| :--- | :--- | :--- | :--- |
| `type` | `string` або `array` з рядків | Будь-який тип | Вимагає відповідності одному або кільком базовим типам JSON: `"null"`, `"boolean"`, `"object"`, `"array"`, `"number"`, `"string"`, `"integer"`. |
| `enum` | `array` | Будь-який тип | Документ вважається валідним, якщо він глибоко еквівалентний (Deep Equality) хоча б одному з елементів масиву `enum`. |
| `const` | Будь-який тип | Будь-який тип | Документ вважається валідним, якщо він суворо дорівнює вказаному фіксованому значенню. |

### Правила зіставлення типів та перевірки на рівність
Псевдотип `integer` є строгою математичною підмножиною типу `number`. Число `42.0` вважається валідним як для `number`, так і для `integer`, оскільки його дробова частина дорівнює нулю. Якщо в полі `type` вказано масив `["string", "null"]`, валідатор успішно приймає або рядкові значення, або літерал `null`, що замінює застаріле ключове слово `nullable` з ранніх діалектів OpenAPI.

Перевірка `enum` та `const` вимагає структурної еквівалентності. Для об'єктів порядок ключів не має значення: об'єкти `{"a": 1, "b": 2}` та `{"b": 2, "a": 1}` вважаються ідентичними. Для масивів порядок елементів є строгим: списки `[1, 2]` та `[2, 1]` вважаються різними сутностями.

## 3. Валідація числових типів (Numbers & Integers)

Числові предикати встановлюють діапазони та кратність значень для типів `number` та `integer`.

| Ключове слово | Допустимий тип | Семантика перевірки |
| :--- | :--- | :--- |
| `multipleOf` | `number` (> 0) | Екземпляр `x` валідний, якщо `x ÷ multipleOf` є цілим числом. |
| `minimum` | `number` | Екземпляр `x` валідний, якщо `x ≥ minimum` (включно). |
| `exclusiveMinimum` | `number` | Екземпляр `x` валідний, якщо `x > exclusiveMinimum` (суворо). |
| `maximum` | `number` | Екземпляр `x` валідний, якщо `x ≤ maximum` (включно). |
| `exclusiveMaximum` | `number` | Екземпляр `x` валідний, якщо `x < exclusiveMaximum` (суворо). |

### Проблема точності дійсних чисел (IEEE 754)
Під час валідації директиви `multipleOf` для чисел з рухомою комою виникає класична проблема неточності двійкового представлення: операція `0.3 % 0.1` у стандарті IEEE 754 повертає `0.09999999999999998` замість `0`. Надійні валідатори використовують алгоритми порівняння з урахуванням машинного епсилона або трансляцію дійсних чисел у дроби довільної точності (BigRational / BigDecimal).

## 4. Валідація рядків та семантичні формати (Strings)

Рядкові предикати контролюють розмір тексту, синтаксичну структуру за регулярними виразами та відповідність стандартизованим мережевим форматам.

| Ключове слово | Допустимий тип | Семантика перевірки |
| :--- | :--- | :--- |
| `minLength` | `integer` (≥ 0) | Кількість символів у рядку (в одиницях Unicode Code Points) мусить бути `≥ minLength`. |
| `maxLength` | `integer` (≥ 0) | Кількість символів у рядку мусить бути `≤ maxLength`. |
| `pattern` | `string` | Регулярний вираз стандарту ECMA-262. Рядок вважається валідним, якщо знайдено хоча б один збіг. |
| `format` | `string` | Семантичний тип рядка (`date-time`, `date`, `time`, `email`, `idn-email`, `hostname`, `ipv4`, `ipv6`, `uri`, `uri-reference`, `uuid`, `regex`, `json-pointer`). |
| `contentMediaType` | `string` | MIME-тип закодованого вмісту (наприклад, `"application/json"`, `"image/png"`). |
| `contentEncoding` | `string` | Схема бінарного кодування рядка (наприклад, `"base64"`). |
| `contentSchema` | `object` / `boolean` | Схема, яка застосовується до вмісту після його розпакування за `contentMediaType`. |

### Семантичні формати та режими валідації
Специфікація Draft 2020-12 розділяє обробку ключового слова `format` на два словники:
- **Format-Annotation (`vocab/format-annotation`):** Режим за замовчуванням. Валідатор лише збирає значення формату як метадані та не відхиляє документ у разі синтаксичної невідповідності.
- **Format-Assertion (`vocab/format-assertion`):** Суворий режим. Будь-яке порушення семантичного формату (наприклад, невалідна дата в `date-time`) призводить до помилки валідації.

Ключові слова `contentMediaType` та `contentSchema` дозволяють перевіряти вкладені дані, передані всередині рядка (наприклад, JSON-документ, закодований у формат Base64). Валідатор спершу декодує байти за `contentEncoding`, потім парсить структуру згідно з `contentMediaType` і передає результат на перевірку підсхемі `contentSchema`.

## 5. Валідація та аплікатори масивів (Arrays)

У Draft 2020-12 масиви валідуються двома взаємодоповнюючими механізмами: позиційною кортежною схемою та загальною схемою залишкових елементів.

| Ключове слово | Допустимий тип | Семантика перевірки та анотацій |
| :--- | :--- | :--- |
| `prefixItems` | `array` зі схем | Кортежна валідація: елемент `i` масиву перевіряється схемою `prefixItems[i]`. Анотує перевірені індекси. |
| `items` | `object` / `boolean` | Застосовується до всіх елементів масиву, індекси яких перевищують довжину списку `prefixItems`. |
| `minItems` | `integer` (≥ 0) | Кількість елементів у масиві екземпляра мусить бути `≥ minItems`. |
| `maxItems` | `integer` (≥ 0) | Кількість елементів у масиві екземпляра мусить бути `≤ maxItems`. |
| `uniqueItems` | `boolean` | Якщо `true`, усі елементи масиву мусять бути попарно унікальними за глибоким порівнянням. |
| `contains` | `object` / `boolean` | Масив валідний, якщо хоча б один його елемент задовольняє вказану підсхему. |
| `minContains` | `integer` (≥ 0) | Задає мінімальну кількість елементів, які мусять задовольнити умову `contains` (за замовчуванням `1`). |
| `maxContains` | `integer` (≥ 0) | Задає максимальну дозволену кількість елементів, що задовольняють умову `contains`. |
| `unevaluatedItems` | `object` / `boolean` | Перевіряє лише ті елементи масиву, які не були оцінені жодним суміжним ключовим словом (`prefixItems`, `items`, `contains`). |

### Алгоритм валідації масивів
Коли валідатор обробляє масив екземпляра, він спершу порівнює довжину з `minItems` та `maxItems`. Якщо оголошено `prefixItems`, кожен елемент з індексом `0 ≤ i < len(prefixItems)` оцінюється підсхемою `prefixItems[i]`, а індекс `i` додається до множини анотованих позицій. Якщо масив довший за `prefixItems`, усі наступні елементи перевіряються схемою `items` (якщо вона задана). Якщо `items` відсутній, але присутній `unevaluatedItems`, залишок елементів перевіряється ним.

## 6. Валідація та аплікатори об'єктів (Objects)

Об'єктні директиви дозволяють контролювати точні назви полів, регулярні вирази ключів, обов'язковість та динамічні залежності між властивостями.

| Ключове слово | Допустимий тип | Семантика перевірки та анотацій |
| :--- | :--- | :--- |
| `properties` | `object` (ключ: схема) | Валідує властивості з точними іменами. Анотує знайдені властивості як оцінені. |
| `patternProperties` | `object` (регулярка: схема) | Валідує властивості, імена яких відповідають регулярному виразу. Анотує їх як оцінені. |
| `additionalProperties`| `object` / `boolean` | Перевіряє властивості, які не збіглися з `properties` та `patternProperties` **локально у поточному об'єкті**. |
| `required` | `array` з рядків | Перелік імен властивостей, які обов'язково мусять бути присутніми в об'єкті екземпляра. |
| `propertyNames` | `object` / `boolean` | Схема, якій мусять відповідати всі рядкові імена ключів об'єкта. |
| `minProperties` | `integer` (≥ 0) | Кількість ключів в об'єкті екземпляра мусить бути `≥ minProperties`. |
| `maxProperties` | `integer` (≥ 0) | Кількість ключів в об'єкті екземпляра мусить бути `≤ maxProperties`. |
| `dependentRequired` | `object` (ключ: масив рядків) | Якщо в об'єкті є властивість `K`, він також зобов'язаний містити всі поля з `dependentRequired[K]`. |
| `dependentSchemas` | `object` (ключ: схема) | Якщо в об'єкті є властивість `K`, до всього об'єкта додатково застосовується схема `dependentSchemas[K]`. |
| `unevaluatedProperties`| `object` / `boolean` | Перевіряє всі властивості об'єкта, які не були оцінені жодним суміжним ключовим словом або вкладеними аплікаторами (`allOf`, `if` тощо). |

### Залежності між полями
Директива `dependentRequired` замінює застаріле ключове слово `dependencies` з Draft-04. Вона встановлює односторонню вимогу присутності суміжних ключів: наприклад, наявність поля `"creditCard"` вимагає обов'язкової наявності поля `"billingAddress"`. Директива `dependentSchemas` діє ширше: вона накладає довільну схему обмежень на весь кореневий об'єкт у разі появи вказаного ключа.

## 7. Логічні аплікатори та умовні конструкції (Composition)

Словник аплікаторів (`https://json-schema.org/draft/2020-12/vocab/applicator`) визначає правила об'єднання підсхем у логічні кон'юнкції, диз'юнкції та умовні розгалуження.

| Ключове слово | Допустимий тип | Семантика обчислення |
| :--- | :--- | :--- |
| `allOf` | `array` зі схем | Логічне «І» (Кон'юнкція). Екземпляр мусить відповідати **всім** підсхемам масиву. |
| `anyOf` | `array` зі схем | Логічне «АБО» (Диз'юнкція). Екземпляр мусить відповідати **хоча б одній** підсхемі масиву. |
| `oneOf` | `array` зі схем | Виключне «АБО» (XOR). Екземпляр мусить відповідати **рівно одній** підсхемі. |
| `not` | `object` / `boolean` | Логічне «НІ» (Заперечення). Екземпляр **не повинен** відповідати вказаній схемі. |
| `if` | `object` / `boolean` | Умовний предикат. Якщо екземпляр валідний за схемою `if`, застосовується `then`, інакше — `else`. |
| `then` | `object` / `boolean` | Схема, що виконується, якщо умова `if` повернула `true`. |
| `else` | `object` / `boolean` | Схема, що виконується, якщо умова `if` повернула `false`. |

## 8. Метадані та анотації для інструментів (Metadata)

Словник метаданих (`https://json-schema.org/draft/2020-12/vocab/meta-data`) не змінює результат валідації, а надає інформацію для кодогенераторів, генераторів документації та систем рендерингу форм.

| Ключове слово | Допустимий тип | Опис призначення |
| :--- | :--- | :--- |
| `title` | `string` | Коротка назва типу сутності для інтерфейсів та згенерованих класів. |
| `description` | `string` | Детальний опис призначення поля чи структури даних. |
| `default` | Будь-який тип | Значення за замовчуванням для ініціалізації порожніх полів клієнтом. |
| `deprecated` | `boolean` | Позначає поле як застаріле, попереджаючи генератори API та розробників. |
| `readOnly` | `boolean` | Позначає поле, яке передається у відповідях сервера, але ігнорується в запитах створення (PUT/POST). |
| `writeOnly` | `boolean` | Позначає конфіденційне поле (наприклад, пароль), яке приймається в запитах, але ніколи не повертається сервером. |
| `examples` | `array` | Масив демонстраційних значень для документації та автотестів. |

## 9. Формати стандартизованих звітів про помилки (Output Formatting)

Специфікація JSON Schema визначає чотири стандартизовані структури вихідних даних для забезпечення сумісності між різними валідаторами та клієнтськими бібліотеками:

1. **Flag Output:** Мінімальний формат, що містить єдиний булевий прапорець `valid`. Застосовується у високонавантажених шлюзах (API Gateways), де потрібна максимальна пропускна здатність без витрат на формування діагностичних повідомлень.
2. **Basic Output:** Плаский масив об'єктів помилок. Кожен запис містить два шляхи JSON Pointer: `instanceLocation` (координати помилки у вхідному документі) та `keywordLocation` (координати порушеного правила у схемі).
3. **Detailed Output:** Ієрархічне дерево результатів, що зберігає топологію логічних аплікаторів (`allOf`, `oneOf`, `if`). Дозволяє точно зрозуміти, яка саме альтернатива диз'юнкції зазнала невдачі і чому.
4. **Verbose Output:** Повне дерево трасування виконання схеми, що фіксує як неуспішні, так і успішно пройдені вузли разом із зібраними анотаціями (використовується для налагодження та аналізу складних схем).
