# 📜 Еволюція специфікацій JSON Schema: від IETF до сучасних стандартів

Потреба в формальному описі структур JSON виникла в середині 2000-х років, коли легковаговий текстовий формат витіснив XML у вебсервісах та розподілених клієнт-серверних системах. XML мав потужні формальні механізми перевірки типу DTD та W3C XML Schema (XSD), тоді як розробники на JSON опинилися перед відсутністю єдиного стандарту верифікації вхідних повідомлень. Спроби перенести важку семантику XSD на динамічну екосистему зазнали невдачі, що спонукало інженерів створити рідний, самоописовий синтаксис на базі самого формату JSON.

## Зародження концепції та перші чернетки (2008–2012)

У 2008 році Кріс Зіп (Kris Zyp), один із ключових контриб'юторів фреймворку Dojo Toolkit, опублікував першу неофіційну пропозицію JSON Schema в межах ініціативи CommonJS. Метою проєкту було створення простої моделі опису типів для серверного середовища JavaScript. На відміну від XML Schema, яка вимагала окремої мови розмітки та складних просторів імен, JSON Schema сама була валідним документом JSON, що дозволяло парсити та обробляти правила верифікації стандартними засобами мови.

У 2009 році автори спробували стандартизувати формат через Інженерну раду Інтернету (IETF, Internet Engineering Task Force), подавши чернетки `draft-zyp-json-schema-00` та наступні ревізії (Draft-01, Draft-02, Draft-03). Ранні специфікації зосереджувалися на визначенні типів даних (`type`), простих числових обмеженнях (`minimum`, `maximum`), регулярних виразах (`pattern`) та спадкуванні (`extends`).

Draft-03 (2011 рік) зафіксував базовий набір ключових слів для верифікації об'єктів і списків. Проте всередині робочих груп IETF виникли суперечки щодо визначення MIME-типу `application/schema+json`, області видимості ідентифікаторів `id` та взаємодії зі специфікацією гіпермедіа JSON Hyper-Schema.

## Епоха Draft-04 та великий розкол з OpenAPI (2013–2017)

У січні 2013 року вийшов Draft-04, який став фундаментальною віхою в історії формату. У цій редакції автори суттєво переглянули дизайн ключових слів:

- Відмовлено від ключового слова `extends` на користь формальних булевих аплікаторів: `allOf`, `anyOf`, `oneOf`, `not`.
- Запроваджено секцію `definitions` для зберігання локальних перевикористовуваних схем, адресованих за допомогою JSON Pointer (RFC 6901) через синтаксис `{"$ref": "#/definitions/Name"}`.
- Розділено синтаксис валідації масивів: `items` міг приймати або єдину схему для всіх елементів, або масив схем (кортежна валідація за позиціями).

Попри широке визнання в індустрії, процес офіційної стандартизації в IETF загальмував. Автори специфікації не дійшли згоди з комітетом щодо остаточного статусу RFC, і робота над чернетками тимчасово зупинилася.

У цей же період бурхливо розвивалася специфікація опису REST API — Swagger (згодом перейменована на OpenAPI Specification). Створюючи Swagger 2.0 (2014 рік) та OpenAPI 3.0 (2017 рік), консорціум OpenAPI Initiative обрав Draft-04 як основу для опису тіл запитів і відповідей. Однак замість повного дотримання специфікації консорціум адаптував її під потреби статично типізованих мов програмування:

1. Заборонено поліморфні масиви типів: `type: ["string", "null"]` замінено на кастомний прапорець `nullable: true` (у OpenAPI 3.0).
2. Виключено ключове слово `not` та обмежено використання `$ref` (у OpenAPI 2.0 `$ref` не міг комбінуватися з іншими ключовими словами на одному рівні).
3. Додано специфічні ключові слова для поліморфізму: `discriminator`.

Ця модифікація призвела до тривалого «розколу» екосистеми: схеми OpenAPI 3.0 виявилися несумісними зі стандартними валідаторами JSON Schema Draft-04, а бібліотекам доводилося реалізовувати спеціальні режими сумісності або створювати окремі транслятори схем.

## Відродження спільноти: Draft-06 та Draft-07 (2017–2018)

У 2016–2017 роках група ентузіастів на чолі з Остіном Райтом (Austin Wright) та Генрі Ендрюсом (Henry Andrews) відродила проєкт JSON Schema як незалежну відкриту ініціативу під егідою спільноти `json-schema.org`.

Draft-06 (квітень 2017) усунув низку застарілих неоднозначностей:
- Дозволено використання простих логічних констант `true` та `false` як повноцінних схем (де `true` дозволяє будь-який документ, а `false` забороняє все).
- Замінено `id` на `$id` для уникнення колізій з користувацькими полями об'єктів.
- Додано ключове слово `const` як скорочення для `enum` з одного елемента.
- Змінено семантику числових меж: `exclusiveMinimum` та `exclusiveMaximum` стали самостійними числовими значеннями, а не булевими модифікаторами для `minimum`/`maximum`.

Draft-07 (листопад 2017) закріпив успіх спільноти та став одним із найпопулярніших діалектів у продакшн-системах. Головними нововведеннями стали:
- Умовні аплікатори: `if`, `then`, `else`, які дозволили описувати залежності між полями без надмірно громіздких конструкцій на базі `oneOf` чи `anyOf`.
- Метадані для генерації інтерфейсів та інструментів: `readOnly`, `writeOnly`, `comment`.
- Покращені ключові слова для перевірки імен ключів: `propertyNames`.

## Модульна архітектура: Draft 2019-09 та перехід на річні версії

Зі зростанням складності специфікації виникла потреба в чіткому розділенні ядра системи (Core) та валідаційних правил (Validation). У вересні 2019 року вийшов Draft 2019-09, який запровадив нову схему нумерації версій за роком і місяцем випуску замість монотонних номерів чернеток.

Архітектура Draft 2019-09 представила концепцію **словників** (Vocabularies):
- Замість монолітної специфікації JSON Schema розділилася на модулі: Core, Applicator, Validation, Format, Content, Metadata.
- Мета-схема `$schema` отримала можливість через `$vocabulary` декларувати, які саме модулі є обов'язковими для реалізації валідатором. Це дозволило створювати предметно-орієнтовані діалекти (наприклад, схеми виключно для генерації UI-форм або математичних обмежень).
- Секцію `definitions` стандартизовано під новим іменем `$defs`.
- Запроваджено механізм динамічного розв'язання рекурсивних посилань: `$recursiveAnchor` та `$recursiveRef`, що вирішило багаторічну проблему розширення мета-схем іншими специфікаціями.

Найважливішим концептуальним зрушенням став перехід від чистої валідації (Assertions) до **динамічного збору анотацій** (Annotations). Це дозволило запровадити ключове слово `unevaluatedProperties`, яке нарешті усунуло дефекти композиції `allOf` у поєднанні з `additionalProperties: false`.

## Draft 2020-12 та злиття з OpenAPI 3.1

У грудні 2020 року було опубліковано Draft 2020-12 — поточний стабільний стандарт сучасної екосистеми JSON Schema.

Ця редакція внесла фінальні корективи до синтаксису:
1. **Уніфікація масивів:** Ключове слово `items` перестало приймати масив схем. Для кортежної позиційної валідації запроваджено окреме ключове слово `prefixItems`. Тепер `items` відповідає виключно за валідацію решти елементів після позиційного префікса, подібно до того, як `additionalProperties` працює для об'єктів.
2. **Динамічні посилання другого покоління:** Вузли `$recursiveAnchor` / `$recursiveRef` замінено на більш загальний та гнучкий механізм `$dynamicAnchor` та `$dynamicRef`, який дозволяє передавати контекст виконання крізь довільні ланцюги посилань.
3. **Повне об'єднання з OpenAPI 3.1:** У лютому 2021 року вийшла специфікація OpenAPI 3.1.0, яка офіційно оголосила 100% сумісність з JSON Schema Draft 2020-12. Багаторічний розкол було подолано: OpenAPI відмовився від власного діалекту на користь стандартного словника JSON Schema, додавши власні розширення як офіційний додатковий словник (Vocabulary).

Сьогодні JSON Schema є зрілим стандартом промислового рівня, який використовується в сучасних протоколах обміну даними, системах оркестрації мікросервісів (Kubernetes CRD, Temporal), генераторах коду та статичних типізаторах (TypeScript, Go, Rust, C++).
