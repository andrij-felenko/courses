# ⚙️ Розумний покажчик із підрахунком посилань

Візьмемо голу ідею «хай об'єкт сам рахує свої посилання» і доведемо її до робочого типу C++ — власного `shared_ptr` з окремим керівним блоком, слабкими посиланнями й потокобезпечним лічильником, — щоб на власні очі побачити, у якому саме рядку ховаються витік, гонка й подвійне звільнення, коли облік ведеш руками. Ідея вміщається в один абзац; правильна реалізація — це десяток місць, де переставлені дві операції означають крах.

## Контракт: що саме будуємо

Нам потрібен тип `Shared<T>`, який поводиться як звичайний покажчик на об'єкт у купі, але з однією надобавкою: **об'єкт живе рівно доти, доки на нього дивиться бодай один `Shared`, і гине точно тоді, коли зникає останній**. Скопіювати `Shared` — і обидві копії володіють тим самим об'єктом; знищити всі копії — і об'єкт звільняється сам, без жодного ручного `delete`.

До цього додається другий тип, `Weak<T>` — посилання, яке **дивиться, але не тримає**. Воно потрібне, щоб розмикати цикли: два об'єкти, що вказують один на одного сильними посиланнями, ніколи не впадуть до нуля й потечуть. `Weak` бачить об'єкт, поки той живий, і чесно повідомляє «мене вже нема», коли останній `Shared` пішов. Дотягтися до об'єкта через `Weak` можна лише через `lock()` — операцію, що безпечно підвищує слабке посилання до сильного, якщо об'єкт іще живий.

Разом контракт такий: копіювання ділить володіння, присвоєння коректне навіть коли зліва й справа той самий об'єкт, деструктор звільняє на нулі, `Weak::lock()` ніколи не повертає покажчик на мертвий об'єкт, і все це — потокобезпечно, коли об'єкт бачать кілька потоків. Кожен із цих пунктів окремо тривіальний. Разом вони й складають усю складність.

## Ідея: лічильник живе не в об'єкті, а поряд

Перша спокуса — покласти лічильник усередину самого об'єкта. Вона хибна з двох причин. По-перше, тоді облік уміли б вести лише «свої» типи, у які ми це поле вшили, — а `Shared<int>` мав би тримати `int`, у якого поля не додаси. По-друге, і головне: слабке посилання мусить пережити смерть об'єкта. Коли останній `Shared` пішов, об'єкт треба знищити негайно — але `Weak`, що на нього ще дивиться, мусить десь прочитати «його вже нема». Якби лічильник жив в об'єкті, він помер би разом з ним, і слабкому не було б куди зазирнути.

Тому лічильники виносять у окрему структуру — **керівний блок** (control block), — яка живе поряд з об'єктом і переживає його. У блоці два числа: скільки **сильних** посилань (вирішує долю об'єкта) і скільки **слабких** (вирішує долю самого блока). Об'єкт знищують, коли сильних стає нуль. Блок звільняють пізніше — коли й сильних, і слабких нуль: доти він мусить існувати, щоб слабкі мали де спитати «ти живий?».

![Ліворуч Shared<T> і Weak<T>, кожен із полями ptr_ і block_; у центрі керівний блок із полями strong = 1, weak = 1 і deleter; праворуч керований об'єкт T. Shared тримає блок суцільним ребром «володіє», Weak — пунктиром «спостерігає», блок володіє об'єктом і знищує його при strong→0. Знизу два правила: strong = 0 звільняє об'єкт, strong і weak = 0 звільняє блок](img/layout.svg)

*`Shared` і `Weak` — це тонкі обгортки над покажчиком на спільний блок; уся механіка життя й смерті зосереджена в блоці. Розведення двох лічильників розводить два незалежні питання: «чи є ще власник» і «чи є ще спостерігач».*

Далі будуємо саме цю трійцю: блок із правилами життя, сильний покажчик над ним і слабкий покажчик збоку.

## Кістяк: керівний блок і сильний покажчик

Почнемо з однопотокової версії, де лічильник — звичайне `long`. Вона правильна, поки об'єкт не ділять між потоками, і в ній видно всю логіку без шуму атомарних операцій. Блок несе покажчик на об'єкт і два лічильники, а правила життя оформимо його ж методами — хай сам об'єкт «носить свій рахунок»:

```cpp
template <class T> class Weak;   // наперед: блок і Shared на нього посилаються

template <class T>
struct ControlBlock {
    T*   obj;        // сам керований об'єкт (nullptr після знищення)
    long strong;     // скільки Shared володіють об'єктом
    long weak;       // скільки Weak спостерігають за блоком

    explicit ControlBlock(T* p) : obj(p), strong(1), weak(0) {}

    void retain() { ++strong; }              // нове сильне посилання

    void release() {                         // сильне посилання зникло
        if (--strong == 0) {                 // пішов останній власник
            delete obj;                      // ← ~T() тут-таки, детерміновано
            obj = nullptr;
            if (weak == 0)                    // і жоден Weak не дивиться на блок
                delete this;                 // → блок теж можна віддати
        }
    }

    void weak_retain() { ++weak; }           // новий спостерігач

    void weak_release() {                    // спостерігач зник
        if (--weak == 0 && strong == 0)      // ні власників, ні спостерігачів
            delete this;                     // → блок нікому не потрібен
    }
};
```

Тут уже видно всю нетривіальність. `release()` на нулі робить **дві** речі: знищує об'єкт (`delete obj` кличе `~T()` негайно, у цьому самому рядку — оце і є детермінований розпад, на якому стоїть [RAII](book:programming/raii)) і, якщо слабких теж нема, звільняє блок. Але якщо слабкі ще є, блок лишається жити з `obj == nullptr` — порожня оболонка, у якій слабкі прочитають, що об'єкт помер. Звільнить її вже `weak_release`, коли піде останній слабкий.

Тепер сам `Shared` — тонка обгортка над покажчиком на блок:

```cpp
template <class T>
class Shared {
    ControlBlock<T>* cb_ = nullptr;

    // приватний ctor: приймає блок ЯК Є (strong уже піднято тим, хто кличе)
    explicit Shared(ControlBlock<T>* cb) : cb_(cb) {}
    friend class Weak<T>;                    // Weak::lock будує Shared із блока

public:
    Shared() = default;                      // порожній покажчик

    // взяти сирий об'єкт під нагляд: створити блок, стати єдиним власником
    explicit Shared(T* raw)
        : cb_(raw ? new ControlBlock<T>(raw) : nullptr) {}

    T* get() const { return cb_ ? cb_->obj : nullptr; }
    T* operator->() const { return cb_->obj; }
    T& operator*()  const { return *cb_->obj; }
    long use_count() const { return cb_ ? cb_->strong : 0; }
    explicit operator bool() const { return cb_ && cb_->obj; }
};
```

Поки що це напівфабрикат: він уміє взяти об'єкт (`Shared<Node> a(new Node)`), але скопіювати чи знищити його правильно ще не вміє. Саме копіювання, присвоєння й знищення й несуть весь облік — додамо їх по одному, бо кожне ховає свою пастку.

## Копіювання: захопити при копії

Найпростіше — копіювальний конструктор. Нова копія починає дивитися на той самий блок, отже, на об'єкт з'явилося ще одне посилання, отже, `retain`:

```cpp
    Shared(const Shared& o) : cb_(o.cb_) {
        if (cb_) cb_->retain();              // +1: з'явилося нове сильне посилання
    }
```

Одна перевірка на порожнечу (`nullptr` не можна захоплювати) і один інкремент. Симетрично до нього деструктор просто відпускає посилання:

```cpp
    ~Shared() { if (cb_) cb_->release(); }   // −1: посилання зникло (можливо, останнє)
```

Ось де вся автоматика: коли `Shared` виходить з області видимості, компілятор сам кличе `~Shared`, той — `release`, а той на нулі — `~T()`. Програміст не пише жодного `delete`; він пише лише фігурну дужку, що закриває блок коду. Пара «`retain` у копії, `release` у деструкторі» — це і є той механізм, що перекладає облік із людини на мову.

## Присвоєння: захопити ДО звільнити

А тепер операція, у якій найлегше все зламати, — присвоєння `p = q`. Тут відбувається водночас дві події: `p` перестає дивитися на свій старий об'єкт (старому треба `release`) і починає дивитися на об'єкт `q` (новому треба `retain`). Здається, порядок байдужий. Він не байдужий, і ціна помилки — звільнення живого об'єкта.

Розгляньмо самоприсвоєння `p = p`. У житті воно приховане: `a[i] = a[j]`, де `i` випадково дорівнює `j`, або два поля, що вказують на один вузол. Уяви, що `p` — єдиний власник, `strong == 1`. Якщо спершу зробити `release` старого об'єкта — лічильник упаде до нуля, об'єкт звільниться, — а тоді `retain` нового підніме лічильник **уже мертвого** об'єкта. Правильний порядок протилежний: **спершу захопити нове, потім звільнити старе**.

![Дві доріжки для p = q, де p і q — той самий об'єкт із strong = 1. Верхня, правильна: strong = 1, потім +1 дає strong = 2, потім −1 повертає strong = 1, об'єкт живий. Нижня, хибна: strong = 1, потім −1 дає strong = 0 і об'єкт звільнено, потім +1 на трупі — крах](img/assign-order.svg)

*Спершу `+1` на новому — і навіть коли новий виявляється тим самим старим, лічильник підскакує до двох і лише потім опускається до одного. Об'єкт переживає операцію, як і мусив. Переставиш дві операції місцями — і самоприсвоєння звільнить об'єкт, на який ти ж і присвоюєш.*

У коді це три рядки, і порядок у них священний:

```cpp
    Shared& operator=(const Shared& o) {
        if (o.cb_) o.cb_->retain();          // 1. захопити нове (рятує від p = p)
        if (cb_)   cb_->release();           // 2. звільнити старе (може впасти до 0)
        cb_ = o.cb_;                          // 3. перецілитися на новий блок
        return *this;
    }
```

Зверни увагу: тут **немає** явної перевірки `if (this != &o)`. Вона й не потрібна — правильний порядок робить самоприсвоєння безпечним сам собою. Це тонше й надійніше за перевірку на рівність адрес: перевірка ловить лише буквальне `p = p`, а `retain`-перед-`release` рятує й від хитрішого випадку, коли `p` і `q` — різні покажчики на **той самий** блок.

Для повноти додамо переміщення. Переміщення `Shared` — це передача володіння без зайвого дотику до лічильника: новий власник краде блок, старий стає порожнім. Жодного `retain`/`release`, бо загальна кількість посилань не змінилася — воно лише переїхало:

```cpp
    Shared(Shared&& o) noexcept : cb_(o.cb_) { o.cb_ = nullptr; }

    Shared& operator=(Shared&& o) noexcept {
        if (this != &o) {
            if (cb_) cb_->release();          // звільнити своє старе
            cb_ = o.cb_;                       // вкрасти чуже
            o.cb_ = nullptr;                   // джерело спорожніти
        }
        return *this;
    }
```

Різниця між копією й переміщенням — це різниця між «нас тепер двоє» (лічильник +1) і «власник переїхав» (лічильник не чіпаємо). Саме тому переміщення дешевше: воно не б'є записом по лічильнику, а це, як побачимо в ціні, найдорожче в усьому механізмі.

## Слабкий покажчик і безпечне підвищення `lock`

Слабкий покажчик влаштований дзеркально до сильного, тільки смикає інший лічильник. Він **не** тримає об'єкт живим — лише спостерігає за блоком:

```cpp
template <class T>
class Weak {
    ControlBlock<T>* cb_ = nullptr;

public:
    Weak() = default;

    Weak(const Shared<T>& s) : cb_(s.cb_) {  // почати спостерігати за тим, чим володіє s
        if (cb_) cb_->weak_retain();          // +1 до СЛАБКОГО лічильника
    }
    Weak(const Weak& o) : cb_(o.cb_) {
        if (cb_) cb_->weak_retain();
    }
    Weak& operator=(const Weak& o) {
        if (o.cb_) o.cb_->weak_retain();      // той самий порядок: захопити до звільнити
        if (cb_)   cb_->weak_release();
        cb_ = o.cb_;
        return *this;
    }
    ~Weak() { if (cb_) cb_->weak_release(); }

    bool expired() const { return !cb_ || cb_->strong == 0; }

    Shared<T> lock() const {
        if (cb_ && cb_->strong != 0) {        // об'єкт іще живий?
            cb_->retain();                     // застовпити ще одне СИЛЬНЕ посилання
            return Shared<T>(cb_);             // приватний ctor: блок уже з піднятим strong
        }
        return Shared<T>();                    // порожньо — об'єкта вже нема
    }
};
```

Уся сіль тут — у `lock()`. Розіменувати слабке посилання напряму не можна: між миттю, коли ти перевірив «живий», і миттю, коли зчитав об'єкт, останній `Shared` міг зникнути, і ти прочитав би звільнену пам'ять. Тому `lock` не віддає сирий покажчик — він **підвищує** слабке до сильного: піднімає `strong`, тим самим гарантуючи, що об'єкт не помре, поки ти тримаєш повернутий `Shared`. Або ти дістаєш живий об'єкт із гарантією на весь час володіння тимчасовим `Shared`, або чесний порожній покажчик. Третього — прочитати труп — конструкція не допускає. Про різновиди й тонкощі таких посилань — окрема тема [слабкі й м'які посилання](book:programming/weak-references).

Зберемо все й переконаймося, що воно живе:

```cpp
#include <cstdio>

struct Node {
    int          value;
    Shared<Node> next;      // сильне ребро (тут причаїться цикл)
    Weak<Node>   parent;    // слабке ребро (навмисно розірваний цикл)
    explicit Node(int v) : value(v) {}
    ~Node() { std::printf("  ~Node(%d)\n", value); }
};

int main() {
    Shared<Node> a(new Node(1));                 // strong = 1
    Shared<Node> b = a;                          // strong = 2  (копія)
    Weak<Node>   w = a;                          // strong = 2, weak = 1
    std::printf("use = %ld\n", a.use_count());   // 2

    if (Shared<Node> s = w.lock())               // підвищення: strong = 3
        std::printf("живий: %d\n", s->value);    // 1
    // s гине тут → strong = 2

    b = Shared<Node>();                          // release → strong = 1
    a = Shared<Node>();                          // release → strong = 0 → ~Node(1)
    std::printf("expired = %d\n", w.expired());  // 1  (true)
    return 0;                                    // w гине → блок звільнено
}
```

Друкує:

```
use = 2
живий: 1
  ~Node(1)
expired = 1
```

Прослідкуй за нитками. Копія `b = a` підняла лічильник до двох; `lock` тимчасово до трьох і назад; два присвоєння порожнього покажчика відпустили `b` і `a` — і на другому з них `strong` дійшов нуля, тут-таки надрукувавши `~Node(1)`. Об'єкт мертвий, але `w` ще тримає слабке посилання, тож блок живий і чесно каже `expired = 1`. Коли `w` помре на виході з `main`, звільниться й блок. Жодного `delete` в коді — і жодного витоку.

## Той самий лічильник, але між потоками

Однопотокова версія бреше, щойно об'єкт бачать два потоки. А бачать вони його часто — саме тому ним і діляться. Проблема в `++strong`: це не одна дія, а три (прочитати, додати, записати), і якщо два потоки виконають їх упереміш, одне захоплення загубиться. Двоє прочитали `2`, обидва додали, обидва записали `3` — а мало бути `4`. Загублене захоплення означає, що об'єкт звільниться, поки на нього ще хтось дивиться. Це класична [гонка даних](book:programming/atomicity-races), і ліки від неї — зробити лічильник **атомарним**, щоб «прочитати-додати-записати» стало однією неподільною апаратною операцією.

Заміна `long` на `std::atomic<long>` — половина справи. Друга половина тонша: яку **впорядкованість пам'яті** (memory order) вимагати від кожної операції. Тут можна або переплатити, або недоплатити, і обидва однаково погано. Правильний рецепт давно відомий і задокументований у Boost; ось він, з поясненням кожного вибору.

Заразом полагодимо ще одну ваду, яка вилазить саме в багатопотоковому коді, — про неї в пастках нижче. Щоб рішення «звільнити блок» ухвалював **один** лічильник, а не двоє наввипередки, застосуємо усталений трюк: сильні власники **гуртом** тримають один слабкий токен. Тобто `weak` рахує справжні слабкі посилання **плюс один**, поки `strong > 0`. Тоді блок звільняє рівно той, хто опустить `weak` до нуля, — і ніхто інший:

```cpp
#include <atomic>

template <class T>
struct ControlBlock {
    T*                obj;
    std::atomic<long> strong;   // скільки Shared
    std::atomic<long> weak;     // скільки Weak + 1, поки strong > 0

    explicit ControlBlock(T* p)
        : obj(p), strong(1), weak(1) {}   // +1 — спільний токен сильних

    void retain() {
        strong.fetch_add(1, std::memory_order_relaxed);
    }

    void release() {
        if (strong.fetch_sub(1, std::memory_order_release) == 1) {
            std::atomic_thread_fence(std::memory_order_acquire);
            delete obj; obj = nullptr;         // об'єкт мертвий
            weak_release();                     // віддати спільний токен сильних
        }
    }

    void weak_retain() {
        weak.fetch_add(1, std::memory_order_relaxed);
    }

    void weak_release() {                       // ЄДИНИЙ власник рішення «звільнити блок»
        if (weak.fetch_sub(1, std::memory_order_release) == 1) {
            std::atomic_thread_fence(std::memory_order_acquire);
            delete this;
        }
    }
};
```

Три різні впорядкованості — і кожна зумовлена причиною, а не осторогою «про всяк випадок». Тема [впорядкованість пам'яті](book:programming/memory-ordering) розбирає їх докладно; ось чому саме такий набір.

**Захоплення — `relaxed`.** Нове посилання на об'єкт народжується завжди з уже наявного: щоб зробити `retain`, ти вже мусиш тримати живий `Shared`. А те, що передало тобі цей наявний `Shared` (інший потік чи попередній код), уже само собою впорядкувало пам'ять. Тож інкремент нічого не мусить синхронізувати — йому досить бути атомарним, і `relaxed` дає рівно це, найдешевше.

**Звільнення — `release`.** Перш ніж відпустити посилання, потік міг щось у об'єкті писати. Ці записи мусять стати видимими тому, хто об'єкт звільнятиме, — інакше деструктор побачить недописаний об'єкт. `memory_order_release` на `fetch_sub` саме це й гарантує: усе, що потік записав до декременту, не «переїде» за нього.

**Знищення — `acquire`-бар'єр на останньому декременті.** Коли `fetch_sub` повернув `1`, ти — останній, і зараз кличеш деструктор. Але деструктор мусить бачити **всі** зміни, які інші потоки внесли перед своїми `release`. Тому перед `delete` ставлять `atomic_thread_fence(acquire)`: він забороняє звалити читання деструктора раніше за декремент. Можна було б вимагати `acq_rel` від кожного `fetch_sub` — але тоді за `acquire` довелося б платити й на тих декрементах, що **не** доводять до нуля, тобто майже завжди дарма. Бар'єр окремим рядком стягує цю плату рівно один раз — на справжньому знищенні. Саме так це роблять у Boost, і саме тому не інакше.

Слабке підвищення теж мусить стати атомарним. Наївна перевірка `if (strong != 0) { retain(); }` тут — гонка: між перевіркою й інкрементом останній `Shared` міг звільнити об'єкт. Правильний `lock` — це цикл **порівняй-і-обміняй** (compare-and-swap), який піднімає `strong` лише якщо той **не нуль**, і повторює спробу, якщо значення змінилося під руками:

```cpp
    Shared<T> lock() const {
        if (!cb_) return {};
        long s = cb_->strong.load(std::memory_order_relaxed);
        while (s != 0) {                          // поки хтось іще володіє
            if (cb_->strong.compare_exchange_weak(
                    s, s + 1, std::memory_order_relaxed))
                return Shared<T>(cb_);            // підняли strong з s до s+1
            // невдача: s оновлено поточним значенням — пробуємо знову
        }
        return {};                                // strong досяг нуля — об'єкт мертвий
    }
```

`compare_exchange_weak` атомарно перевіряє, що `strong` досі дорівнює прочитаному `s`, і лише тоді записує `s + 1`. Якщо між `load` і обміном хтось `strong` змінив — обмін не вдасться, оновить `s` свіжим значенням, і цикл спробує ще раз. Об'єкт не проскочить від «живий» до «мертвий» непоміченим: якщо в мить обміну `strong` уже нуль, ми туди й не зайдемо. Це і є те, чого не дає проста перевірка.

## Складність і ціна кожної операції

Усі операції — сталого часу, і це головна перевага перед обходом пам'яті, вартість якого росте з обсягом живих даних.

- **Копіювання, присвоєння, знищення посилання — O(1).** Один атомарний інкремент або декремент. Присвоєння — два (захопити, звільнити).
- **`lock()` — O(1) амортизовано.** Цикл `compare_exchange` повторюється лише за одночасної зміни лічильника; під навантаженням число спроб обмежене, операція не блокує потік (lock-free).
- **`use_count`, `expired` — O(1).** Одне атомарне читання.

Один виняток псує ідилію, і про нього треба знати. `release`, що опускає лічильник до нуля, — сам по собі O(1), але тягне `~T()`, а деструктор об'єкта звільняє його поля, і якщо об'єкт володіє великою структурою, звільнення **каскадом** прокотиться всією нею. Відпустив корінь дерева з мільйона вузлів — і цей один `release` синхронно звільнить мільйон об'єктів. Час амортизований (кожен вузол звільниться один раз), але сплеск затримки прив'язаний до конкретного рядка коду.

Ціна за місцем: керівний блок — це два лічильники плюс покажчик на об'єкт (плюс, у повній реалізації, deleter), тобто кілька машинних слів на групу спільного володіння. Кожен `Shared` — це один покажчик. Коли блок і об'єкт створюють однією операцією (у стандарті — `make_shared`), їх кладуть в одну ділянку пам'яті: одне виділення замість двох, щільніше й швидше — ціною того, що байти об'єкта не віддати системі, поки живий блок, а блок живий, поки є слабкі посилання.

## Пастки, кожну з яких видно в коді

Тепер найцінніше — місця, де ця конструкція ламається. Усі вони реальні, і кожна колись когось коштувала ночі за налагоджувачем.

**Самоприсвоєння.** Уже знешкоджене порядком «захопити до звільнити». Але варто раз побачити ціну помилки: переставиш два рядки в `operator=` — і `a[i] = a[j]` за `i == j` звільнить об'єкт, на який ти ж присвоюєш. Компілятор змовчить; впаде воно за годину роботи деінде.

**Подвійний облік одного об'єкта.** Найпідступніша пастка з сирими покажчиками:

```cpp
Node* raw = new Node(7);
Shared<Node> p(raw);     // блок №1, strong = 1
Shared<Node> q(raw);     // блок №2, strong = 1  ← ДВА незалежні блоки на один об'єкт!
```

Кожен `Shared(T*)` створює **свій** керівний блок. Дав той самий сирий покажчик двом — маєш два блоки, два незалежні лічильники, і коли обидва впадуть до нуля, `delete raw` виконається **двічі**. Це подвійне звільнення — миттєве псування купи. Правило залізне: сирий покажчик беруть під нагляд **рівно один раз**; щоб поділитися, копіюють `Shared`, а не загортають сирий покажчик удруге. Той самий закон, до речі, стоїть за `std::enable_shared_from_this` у стандарті — способом дістати `shared_ptr` на себе, не роблячи другого блока.

> 🔧 **Навіщо це.** Межа, де плодяться зайві блоки, завжди та сама: **сирий покажчик, що перетинає межу API**. Бачиш функцію, яка приймає або повертає `T*`, а не `Shared<T>`, — зупинись і спитай, хто володіє цим об'єктом. Якщо ним уже хтось керує, загортати його в новий `Shared` не можна: віддавай і приймай `Shared` наскрізь, щоб володіння читалося прямо в типі. Сирий покажчик у сигнатурі — це неписана домовленість «я лише подивлюся, не володію»; щойно ти робиш із нього `Shared`, ти цю домовленість тихо порушив, і другий блок — плата за це.

**Гонка на неатомарному лічильнику.** Однопотокову версію з `long` віддав у два потоки — і загублений інкремент звільнить живий об'єкт. Ліки — атомарний лічильник; ціна — атомарна операція дорожча за звичайне додавання й перетворює лічильник на точку розжарення між ядрами. Тому атомарну версію беруть лише там, де об'єкт справді ділять між потоками, а не завжди.

**Подвійне звільнення блока.** Ось чому в атомарній версії сильні тримають спільний слабкий токен. Уяви наївний блок із **двома незалежними** лічильниками, де і `release`, і `weak_release` окремо перевіряють «а другий уже нуль?» і, якщо так, звільняють блок. Під конкуренцією це подвійне звільнення:

![Дві смуги подій за спільною віссю часу. Потік 1 (останній shared release): --strong стає 0, знищує об'єкт, читає weak і бачить 0, звільняє блок. Потік 2 (останній weak release): --weak стає 0, читає strong і бачить 0, звільняє блок. Обидва бачать нуль сусіда й обидва звільняють блок — подвійне звільнення](img/block-double-free.svg)

*Потік 1 опустив `strong` до нуля, потік 2 — `weak` до нуля, майже одночасно. Тепер кожен читає лічильник сусіда й бачить нуль, якого мить тому ще не було, — і обидва вирішують, що звільнити блок їхній обов'язок. `delete this` виконується двічі.* Трюк зі спільним токеном прибирає гонку в корені: рішення про звільнення блока приймає **лише** той, хто опустить `weak` до нуля, а таких завжди рівно один. `release`, доводячи `strong` до нуля, не звільняє блок сам — він лише віддає токен через `weak_release`, і далі все вирішує єдиний лічильник.

**Цикл.** Два об'єкти, що тримають одне одного сильними посиланнями, не звільняться ніколи:

```cpp
{
    Shared<Node> x(new Node(10));
    Shared<Node> y(new Node(20));
    x->next = y;      // Node10 тримає Node20 сильно → strong(20) = 2
    y->next = x;      // Node20 тримає Node10 сильно → strong(10) = 2  ← цикл!
}   // x, y виходять: strong кожного впав лише до 1 (тримають одне одного)
// жоден ~Node НЕ надрукується → витік
```

На виході зі блока локальні `x` і `y` відпустили по одному посиланню, але `Node10.next` і `Node20.next` тримають решту. Лічильник кожного застряг на одиниці, ззовні до пари не дотягтися — витік, який лічильник принципово не бачить, бо «на мене дивляться» тут правда й водночас нічого не варта. Лік — розімкнути коло навмисно, зробивши одне з двох ребер слабким:

```cpp
    x->next   = y;    // власницьке ребро лишаємо сильним
    y->parent = x;    // зворотне ребро робимо слабким (Weak<Node>)
```

Тепер `strong(10)` тримає лише живий `x`; щойно він піде, `Node10` звільниться попри слабкий погляд `Node20`, за ним каскадом — `Node20`. Ціна — одне свідоме рішення на кожну двобічну структуру: який напрямок тут **власницький**, а який — лише **знайомство**.

**Каскад і переповнення стека.** Найнесподіваніша з усіх. Побудуй довгий однозв'язний список на сильних посиланнях:

```cpp
Shared<Node> head(new Node(0));
Node* cur = head.get();
for (int i = 1; i < 1'000'000; ++i) {
    cur->next = Shared<Node>(new Node(i));
    cur = cur->next.get();
}
// head = Shared<Node>();  ← крах!
```

Відпустиш `head` — і `~Node(0)` знищує своє поле `next`, що кличе `~Node(1)`, що знищує своє `next`… Це не цикл — це **рекурсія завглибшки в мільйон рівнів**, і стек її не витримає: програма впаде переповненням стека рівно на тому нешкідливому присвоєнні. Каскад звільнень, про який зазвичай думають як про сплеск затримки, обертається аварією. Лік — розбирати структуру **ітеративно**, висмикуючи наступний вузол, перш ніж звільнити поточний, щоб жоден деструктор не викликав інший:

```cpp
while (head) {
    Shared<Node> next = std::move(head->next);  // head->next стає порожнім
    head = std::move(next);                      // старий head гине з ПОРОЖНІМ next → без рекурсії
}
```

Тепер кожен `~Node` бачить уже спорожнене `next` і нікого за собою не тягне: глибина рекурсії — одиниця, робота — та сама O(n), але без стосу викликів на мільйон кадрів.

## Одне число, доведене до типу

Ми зібрали `shared_ptr` з трьох частин, і кожна виявилася нетривіальною там, де на око проста. Керівний блок мусить пережити об'єкт — інакше слабким нема куди зазирнути. Оператор присвоєння мусить захоплювати до звільнення — інакше самоприсвоєння вбиває об'єкт. Атомарний лічильник мусить брати `relaxed` на вході й `release` з бар'єром на виході — інакше або переплата, або недописаний об'єкт у деструкторі. Слабке підвищення мусить бути циклом `compare-and-swap` — інакше об'єкт помре між перевіркою й захопленням. А спільний токен сильних мусить зробити звільнення блока рішенням одного лічильника — інакше блок звільниться двічі.

Кожне з цих «мусить» — та сама думка під різними кутами: облік правдивий лише тоді, коли **жодна** пара «захопив-відпустив» не розірвана й не переставлена, а на межі потоків — ще й не побачена наполовину. Розумний покажчик — це не хитрий алгоритм, а дисципліна парності, вшита в конструктори й деструктори так, щоб її дотримувався компілятор, а не пам'ять людини. Там, де ця дисципліна тримається, `delete` зникає з коду зовсім; там, де рветься на один рядок, — вертається звисаючим покажчиком або витоком, тільки вже без жодної підказки, де саме.
