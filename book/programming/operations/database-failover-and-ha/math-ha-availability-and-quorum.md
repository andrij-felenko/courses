# 🧮 Математика доступності, кворумів та таймаутів лізингу

Проектування відмовостійких систем зберігання даних опирається на математичний апарат теорії ймовірностей, булевої алгебри, теорії графів, теорії масового обслуговування та марковських процесів, який дозволяє кількісно розрахувати коефіцієнт готовності, мінімальний розмір кворуму, очікувані втрати даних при асинхронній реплікації, вплив напівсинхронного запису на латентність, умови виникнення каскадних перевантажень та часові межі лізингу лідера.

## 1. Коефіцієнт готовності та вартість «дев'яток»

Готовність системи (англ. *Availability*, `A`) — це ймовірність того, що в довільний момент часу `t` база даних коректно функціонує та здатна обслуговувати клієнтські запити. Вона визначається через дві фундаментальні метрики надійності:
- **MTBF (Mean Time Between Failures)** — середній час безвідмовної роботи між сусідніми аваріями.
- **MTTR (Mean Time To Repair)** — середній час відновлення працездатності системи після збою (для баз даних це час детекції аварії, промоушену репліки та перемикання трафіку, тобто RTO).

Формальне визначення коефіцієнта готовності:

```
A = MTBF / (MTBF + MTTR)   [співвідношення часу корисної роботи до сумарного часу життєвого циклу]
```

Коефіцієнт простою (англ. *Unavailability*, `U`):

```
U = 1 - A
= 1 - MTBF / (MTBF + MTTR)   [підстановка формули готовності]
= MTTR / (MTBF + MTTR)       [зведення до спільного знаменника]
```

Для річного інтервалу часу `T[рік] = 365.25 · 24 · 3600 = 31 557 600` секунд (або 525 960 хвилин) сумарний річний час простою `D[рік]` обчислюється як:

```
D[рік] = T[рік] · (1 - A)   [добуток тривалості року на коефіцієнт простою]
```

Розрахуємо точний річний час простою для стандартних інженерних класів доступності («кількості дев'яток»):

**Клас 99.0% («дві дев'ятки»):**
```
D[рік] = 525 960 хв · (1 - 0.99)
= 525 960 · 0.01                 [множення на частку простою]
= 5 259.6 хвилин                 [підсумок у хвилинах]
= 87 годин 39 хвилин 36 секунд   [переведення в години]
```

**Клас 99.9% («три дев'ятки» — типова поодинока реляційна база даних):**
```
D[рік] = 525 960 хв · (1 - 0.999)
= 525 960 · 0.001                [множення на частку простою]
= 525.96 хвилин                  [підсумок у хвилинах]
= 8 годин 45 хвилин 58 секунд    [переведення в години]
```

**Клас 99.99% («чотири дев'ятки» — високодоступний HA-кластер з Patroni/Orchestrator):**
```
D[рік] = 525 960 хв · (1 - 0.9999)
= 525 960 · 0.0001               [множення на частку простою]
= 52.596 хвилин                  [підсумок у хвилинах]
= 52 хвилини 36 секунд           [переведення в хвилини та секунди]
```

**Клас 99.999% («п'ять дев'яток» — георозподілені Distributed SQL системи: Spanner, CockroachDB):**
```
D[рік] = 525 960 хв · (1 - 0.99999)
= 525 960 · 0.00001              [множення на частку простою]
= 5.2596 хвилин                  [підсумок у хвилинах]
= 5 хвилин 16 секунд             [переведення в секунди]
```

### Послідовне та паралельне з'єднання компонентів

Архітектура бази даних складається з ланцюга компонентів: обчислювальний вузол (`A[node]`), мережевий комутатор (`A[net]`), шар зберігання/диск (`A[disk]`) та проксі-балансувальник (`A[proxy]`).

1. **Послідовна залежність (Single Point of Failure):** якщо для роботи системи необхідні всі `n` компонентів одночасно, загальна готовність є добутком готовностей:

```
A[sys_seq] = ∏_{i=1}^n A[i]   [імовірність одночасної безвідмовної роботи всіх незалежних елементів]
```

Якщо кожен із 4 компонентів має надійність `99.9% (0.999)`:
```
A[sys_seq] = 0.999 · 0.999 · 0.999 · 0.999
= 0.999⁴                     [піднесення до степеня 4]
= 0.996005996                [числове значення]
≈ 99.60%                     [простій зріс із 8.7 годин до 35 годин на рік]
```

2. **Паралельне резервування (Active-Standby Redundancy):** якщо система має `m` дублюючих вузлів, і для збереження працездатності достатньо хоча б одного працюючого:

```
A[sys_par] = 1 - ∏_{i=1}^m (1 - A[i])   [одиниця мінус імовірність одночасної відмови всіх m вузлів]
```

Для кластера з трьох незалежних вузлів, кожен з яких має індивідуальну доступність `99% (0.99)`:
```
A[sys_par] = 1 - (1 - 0.99)³
= 1 - (0.01)³                [імовірність відмови одного вузла у кубі]
= 1 - 0.000001               [обчислення добутку]
= 0.999999                   [результат: 99.9999% — шість дев'яток]
```

## 2. Марковська модель надійності HA-кластера

Для динамічного моделювання переходів між станами кластера з `N = 3` вузлів застосуємо неперервний марковський процес (Continuous-Time Markov Chain, CTMC).

Визначимо дискретні стани системи:
- **Стан S₂ (Повна працездатність):** Працює Primary та 2 Replicas. Інтенсивність відмови окремого вузла дорівнює `λ` (1/MTBF), сумарна інтенсивність переходу в пошкоджений стан: `3λ`.
- **Стан S₁ (Деградований стан):** Працює Primary та 1 Replica (один вузол впав). Сумарна інтенсивність відмови двох вузлів, що залишилися: `2λ`. Інтенсивність відновлення пошкодженого вузла: `μ` (1/MTTR).
- **Стан S₀ (Відмова системи / Втрата кворуму):** Залишився лише 1 вузол або 0. Кластер не може зібрати кворум 2 з 3 для безпечного запису і зупиняє роботу.

Складемо систему рівнянь балансу ймовірностей для стаціонарного режиму (`dP_i/dt = 0`):

```
3λ · P₂ = μ · P₁                                [баланс переходів між станами S₂ та S₁]
(2λ + μ) · P₁ = 3λ · P₂ + 2μ · P₀               [баланс переходів для деградованого стану S₁]
P₀ + P₁ + P₂ = 1                                [умова нормування повної групи подій]
```

Виразимо стаціонарні ймовірності через відношення інтенсивності відмов до інтенсивності відновлення `ρ = λ / μ`:

```
P₁ = (3λ / μ) · P₂
= 3ρ · P₂                                       [підстановка коефіцієнта навантаження ρ = λ/μ]

P₀ = (2λ / (2μ)) · P₁
= ρ · P₁                                        [спрощення коефіцієнтів]
= 3ρ² · P₂                                      [підстановка виразу для P₁]
```

Підставимо у рівняння нормування:

```
P₂ · (1 + 3ρ + 3ρ²) = 1                         [винесення P₂ за дужки]
P₂ = 1 / (1 + 3ρ + 3ρ²)                         [стаціонарна ймовірність повного стану]
P₁ = 3ρ / (1 + 3ρ + 3ρ²)                        [стаціонарна ймовірність деградованого стану]
P₀ = 3ρ² / (1 + 3ρ + 3ρ²)                       [стаціонарна ймовірність аварійного простою]
```

Загальна готовність кластера `A[cluster]` є сумою ймовірностей станів `S₂` та `S₁` (де кворум збережено):

```
A[cluster] = P₂ + P₁
= (1 + 3ρ) / (1 + 3ρ + 3ρ²)                     [додавання ймовірностей робочих станів]
= 1 - 3ρ² / (1 + 3ρ + 3ρ²)                      [вираження через одиницю мінус імовірність простою P₀]
```

**Числовий розрахунок:**
Нехай для типового сервера бази даних `MTBF = 2000` годин (`λ = 1/2000 = 0.0005` год⁻¹), а середній час автоматичного відновлення та допрогравання репліки `MTTR = 0.5` години (`μ = 1/0.5 = 2.0` год⁻¹).
Тоді відношення `ρ = 0.0005 / 2.0 = 0.00025`.

Обчислимо імовірність аварійного простою `P₀`:
```
P₀ ≈ 3 · (0.00025)²
= 3 · 0.0000000625                              [піднесення до квадрата]
= 0.0000001875                                  [ймовірність простою: 1.875 · 10⁻⁷]

A[cluster] = 1 - 0.0000001875
= 0.9999998125                                  [готовність: 99.99998% — майже сім дев'яток]
```

Марковський аналіз доводить, що автоматичне відновлення реплік зводить імовірність одночасного падіння більшості вузлів до часток секунди на десятиліття.

## 3. Кворумна математика та теорема про розрізи графів

Щоб уникнути розщеплення мозку в розподіленій системі, будь-яка зміна лідерства або фіксація транзакції повинна схвалюватися строгою більшістю вузлів — кворумом.

Нехай кластер складається з `N` однакових вузлів. Розмір мінімального кворуму `Q` визначається правилом простої більшості:

```
Q = ⌊N / 2⌋ + 1   [найменше ціле число, строго більше ніж N / 2]
```

### Теорема про неперетин кворумів (Пемптеорема консенсусу)

**Теорема:** Будь-які дві підмножини вузлів `S₁` та `S₂` потужністю `|S₁| ≥ Q` та `|S₂| ≥ Q`, обрані з множини `N` вузлів, мають хоча б один спільний вузол:

```
S₁ ∩ S₂ ≠ ∅
```

**Доведення:**
Припустимо супротивне: множини `S₁` та `S₂` не перетинаються, тобто `S₁ ∩ S₂ = ∅`.
За аксіомою адитивності потужності для неперетинних множин:

```
|S₁ ∪ S₂| = |S₁| + |S₂|   [сума потужностей неперетинних підмножин]
```

Оскільки `|S₁| ≥ ⌊N/2⌋ + 1` та `|S₂| ≥ ⌊N/2⌋ + 1`:

```
|S₁ ∪ S₂| ≥ (⌊N/2⌋ + 1) + (⌊N/2⌋ + 1)
= 2·⌊N/2⌋ + 2             [розкриття дужок]
```

Розглянемо парні та непарні значення `N`:
1. Нехай `N` непарне: `N = 2k + 1`. Тоді `⌊N/2⌋ = k`.
```
|S₁ ∪ S₂| ≥ 2k + 2
= (2k + 1) + 1            [групування складових]
= N + 1                   [підстановка N = 2k + 1]
```
2. Нехай `N` парне: `N = 2k`. Тоді `⌊N/2⌋ = k`.
```
|S₁ ∪ S₂| ≥ 2k + 2
= N + 2                   [підстановка N = 2k]
```

В обох випадках `|S₁ ∪ S₂| ≥ N + 1`. Проте за визначенням `S₁ ⊆ V` та `S₂ ⊆ V`, де `|V| = N`. Об'єднання підмножин універсальної множини не може перевищувати потужність самої множини: `|S₁ ∪ S₂| ≤ N`.
Отримали строге протиріччя: `N + 1 ≤ |S₁ ∪ S₂| ≤ N`.
Отже, припущення `S₁ ∩ S₂ = ∅` хибне. Таким чином:

```
S₁ ∩ S₂ ≠ ∅   [кворуми завжди мають щонайменше один спільний вузол]
```

### Запобігання Split-Brain при довільному розрізі графа топології

Нехай топологія зв'язку між вузлами кластера описується неорієнтованим графом `G = (V, E)`, де `|V| = N`. Аварія мережевої інфраструктури розбиває граф `G` на `k ≥ 2` ізольованих компонент зв'язності `V₁, V₂, ..., V_k`, таких що:

```
V = ⋃_{i=1}^k V_i   та   V_i ∩ V_j = ∅  для всіх i ≠ j   [розбиття множини вузлів на неперетинні підмережі]
```

Оскільки `∑_{i=1}^k |V_i| = N`, а умова існування легітимного лідера вимагає `|V_i| ≥ ⌊N/2⌋ + 1`:

```
Кількість компонент із кворумом ≤ ⌊ N / (⌊N/2⌋ + 1) ⌋
= ⌊ N / (N/2 + 0.5) ⌋                                    [для непарного N]
< 2                                                      [результат ділення строго менше 2]
```

Це доводить, що серед довільної кількості мережевих сегментів існує **максимум один** сегмент, здатний вибрати лідера. Усі інші сегменти гарантовано переходять у режим очікування або блокують запис.

### Ймовірність збереження кворуму кластером

Якщо кожен із `N` вузлів виходить з ладу незалежно з імовірністю `p` (тобто доступний з імовірністю `q = 1 - p`), то ймовірність того, що кластер збереже дієздатний кворум `P[кворум]`, описується біноміальним розподілом:

```
P[кворум] = ∑_{k=Q}^N C(N, k) · (1 - p)^k · p^(N - k)   [сума ймовірностей станів, де доступно k ≥ Q вузлів]
```
де `C(N, k) = N! / (k! · (N - k)!)` — число біноміальних коефіцієнтів.

Порівняємо надійність кворуму для кластерів із `N = 3` та `N = 5` при ймовірності відмови окремого сервера `p = 0.05` (доступність вузла `q = 0.95`):

**Для N = 3 (необхідний кворум Q = 2):**
```
P[3] = C(3, 2) · 0.95² · 0.05¹ + C(3, 3) · 0.95³ · 0.05⁰
= 3 · 0.9025 · 0.05 + 1 · 0.857375 · 1                  [обчислення доданків]
= 0.135375 + 0.857375                                   [додавання ймовірностей]
= 0.99275                                               [доступність кворуму: 99.275%]
```

**Для N = 5 (необхідний кворум Q = 3):**
```
P[5] = C(5, 3)·0.95³·0.05² + C(5, 4)·0.95⁴·0.05¹ + C(5, 5)·0.95⁵·0.05⁰
= 10 · 0.857375 · 0.0025 + 5 · 0.81450625 · 0.05 + 1 · 0.7737809375 · 1
= 0.021434375 + 0.2036265625 + 0.7737809375            [додавання складових]
= 0.998841875                                           [доступність кворуму: 99.884%]
```

Збільшення кількості вузлів з 3 до 5 зменшило ймовірність втрати кворуму з `0.725%` до `0.116%` (у понад 6 разів).

### Чому парна кількість вузлів (N = 4 або N = 6) не додає відмовостійкості

Для `N = 3`: `Q = ⌊3/2⌋ + 1 = 2`. Кластер витримує відмову `3 - 2 = 1` вузла.
Для `N = 4`: `Q = ⌊4/2⌋ + 1 = 3`. Кластер витримує відмову `4 - 3 = 1` вузла.

Кластер із 4 вузлів вимагає для кворуму 3 працюючих сервери. При відмові 2 вузлів кластер із 4 серверів втрачає кворум точно так само, як і кластер із 3 серверів, але має більше компонентів, кожен з яких може зламатися. Математично:

```
P[4_кворум] = C(4, 3)·0.95³·0.05¹ + C(4, 4)·0.95⁴
= 4 · 0.857375 · 0.05 + 0.81450625
= 0.171475 + 0.81450625
= 0.98598125   [готовність нижча, ніж у кластера з 3 вузлів: 98.598% проти 99.275%]
```

Парна кількість вузлів лише підвищує ймовірність відмови без збільшення допустимого числа аварій.

## 4. Ймовірнісна модель втрати даних (RPO) при асинхронній реплікації

При асинхронній реплікації лідер підтверджує фіксацію транзакції клієнту локально, не чекаючи запису на репліки. У разі раптового падіння лідера втрачаються всі транзакції, які містилися в сегменті реплікаційного лагу `τ` (вираженому в секундах).

Нехай потік транзакцій, що модифікують базу даних, є найпростішим пуассонівським процесом з інтенсивністю `λ[tx]` (транзакцій/с).
Кількість втрачених транзакцій `K` за час затримки `τ` описується розподілом Пуассона:

```
P(K = k | τ) = ((λ[tx] · τ)^k / k!) · e^(-λ[tx] · τ)   [ймовірність втрати k транзакцій при лагу τ]
```

Якщо реплікаційний лаг `τ` є випадковою величиною з функцією густини ймовірності `f(τ)` (наприклад, експоненційний розподіл `f(τ) = β · e^(-βτ)` із середнім лагом `E[τ] = 1/β`):

Обчислимо математичне сподівання кількості безповоротно втрачених транзакцій `E[Lost]`:

```
E[Lost] = ∫₀^∞ E[K | τ] · f(τ) dτ
= ∫₀^∞ (λ[tx] · τ) · f(τ) dτ    [підстановка умовного математичного сподівання λ·τ]
= λ[tx] · ∫₀^∞ τ · f(τ) dτ      [винесення константи λ за знак інтеграла]
= λ[tx] · E[τ]                  [добуток інтенсивності транзакцій на середній реплікаційний лаг]
```

Дисперсія втрат даних `Var[Lost]` (за законом повної дисперсії):

```
Var[Lost] = E[Var(K | τ)] + Var(E[K | τ])
= E[λ[tx] · τ] + Var(λ[tx] · τ)
= λ[tx] · E[τ] + λ[tx]² · Var[τ]   [розклад дисперсії на внесок пуассонівського шуму та флуктуацій лагу]
```

**Числовий приклад:**
Високонавантажена платіжна система генерує `λ[tx] = 5000` транзакцій на секунду.
Реплікація працює в асинхронному режимі із середнім лагом `E[τ] = 40` мс (`0.04` с) та стандартним відхиленням `σ[τ] = 20` мс (`0.02` с ⇒ `Var[τ] = 0.0004` с²).

Обчислимо очікувану кількість втрачених транзакцій під час аварійного failover:
```
E[Lost] = 5000 · 0.04
= 200 транзакцій   [середня кількість втрачених клієнтських операцій]

Var[Lost] = 5000 · 0.04 + (5000)² · 0.0004
= 200 + 25 000 000 · 0.0004
= 200 + 10 000
= 10 200           [дисперсія втрат]

σ[Lost] = √10200
≈ 101 транзакція   [стандартне відхилення втрат]
```

З імовірністю `95%` (правило двох сигм `E ± 2σ`) кількість втрачених транзакцій лежатиме в інтервалі від `0` до `200 + 2·101 = 402` операцій. Цей розрахунок доводить необхідність використання напівсинхронної реплікації (Semi-Sync) для фінансових таблиць, де допустимий `RPO = 0`.

## 5. Латентність напівсинхронного запису та закон Літтла

Напівсинхронна реплікація (Semi-Synchronous Replication) гарантує `RPO = 0`, оскільки лідер відправляє підтвердження `COMMIT` клієнту лише після отримання ACK хоча б від однієї репліки.

Розрахуємо додаткову затримку транзакції `W[tx]`.
Нехай базовий локальний час фіксації на диску лідера складає `T[local_fsync]`, а мережевий час кругового обігу між основним вузлом і реплікою становить `RTT[net]`. Час запису реплікою в буфер журналу WAL/relay-log: `T[replica_write]`.

Загальна тривалість обробки транзакції:

```
W[tx_semi] = T[local_fsync] + RTT[net] + T[replica_write]   [сума локального запису та синхронного мережевого раунду]
```

За **законом Літтла (Little's Law)** середня кількість активних конкурентних транзакцій у системі `L` прямо пропорційна інтенсивності вхідного потоку `λ[tx]` та середньому часу перебування в системі `W`:

```
L = λ[tx] · W[tx]   [середній розмір пулу активних з'єднань і блокувань]
```

Якщо при асинхронній реплікації `W[async] = 2` мс (`0.002` с), а при міжзональній напівсинхронній реплікації через `RTT = 8` мс час зростає до `W[semi] = 10` мс (`0.010` с):
Для підтримки пропускної здатності `λ = 10 000` транзакцій/с:

```
L[async] = 10 000 · 0.002
= 20 активних транзакцій   [розмір пулу з'єднань при асинхронному режимі]

L[semi] = 10 000 · 0.010
= 100 активних транзакцій  [п'ятикратне зростання кількості одночасних блокувань]
```

Це доводить, що перехід на синхронний захист від втрати даних вимагає п'ятикратного розширення пулу з'єднань клієнтів і призводить до збільшення конкуренції за рядкові блокування (Row Locks Contention).

## 6. Модель каскадних відмов у пулі читання (Thundering Herd)

Коли в кластері з одного лідера та `M` реплік для читання падає один вузол (або вибирається новим лідером під час failover), його читацьке навантаження миттєво перерозподіляється між рештою `M - 1` реплік.

Нехай сумарний вхідний потік запитів на читання становить `R[total]` (запитів/с), а максимальна пропускна здатність окремого сервера репліки обмежена величиною `C[node]` (запитів/с).

Коефіцієнт утилізації кожної репліки в штатному стані:

```
ρ[штатний] = R[total] / (M · C[node])   [частка завантаження вузла при M репліках]
```

Після аварії або промоушену однієї репліки новий коефіцієнт утилізації становить:

```
ρ[деградований] = R[total] / ((M - 1) · C[node])
= ρ[штатний] · (M / (M - 1))            [зростання навантаження у M / (M - 1) разів]
```

**Критерій стійкості до каскадного збою (Cascade Safety Invariant):**
Кластер не впаде за принципом доміно тоді й тільки тоді, коли `ρ[деградований] < 1`:

```
ρ[штатний] < (M - 1) / M   [максимально допустимий рівень утилізації в штатному режимі]
```

Для кластера з `M = 3` реплік: `(3 - 1) / 3 = 2/3 ≈ 66.7%`. Якщо в штатному стані три репліки завантажені більш ніж на 67%, падіння однієї призведе до перевантаження двох інших (`ρ > 100%`), черги запитів вичерпають пули потоків, і весь кластер читання миттєво відмовить.

## 7. Модель лізингу, таймаути виявлення збоїв та джитер

В архітектурах Patroni / etcd лідер володіє ключем оренди з обмеженим часом життя (Time-To-Live, `TTL`). Лідер зобов'язаний періодично продовжувати оренду з інтервалом `T[loop]` (loop_wait).

Позначимо параметри часової моделі:
- `T[ttl]` — час життя оренди в DCS (наприклад, 10 с).
- `T[loop]` — період між спробами продовження оренди лідером (наприклад, 2 с).
- `T[retry]` — ліміт очікування відповіді на запит продовження оренди (retry_timeout, наприклад, 5 с).
- `J[net]` — випадковий мережевий джитер та затримка передачі пакетів.
- `Δ[clock]` — максимальний апаратний дрейф годинників між серверами.
- `T[gc]` — максимальна тривалість зупинки процесу (Stop-The-World GC пауза або зависання скидання сторінок на диск).

### Умова безпеки лідера (Safety Invariant)

Лідер має право приймати операції запису від клієнтів лише тоді, коли він абсолютно впевнений, що термін дії його лізу в DCS ще не сплив. Якщо лідер втрачає зв'язок із DCS, він зобов'язаний самоізолюватися (демотувати себе в Read-Only або завершити процес) до того, як спливе час `T[ttl]`.

Час гарантованої безпеки лідера `T[safe]`, який залишається після успішного оновлення лізу в момент `t₀`:

```
T[safe] = T[ttl] - (t - t₀) - 2·Δ[clock] - J[net]   [запас часу дії лізу з урахуванням розбіжності годинників і затримок]
```

Якщо за час `T[ttl] - T[retry]` лідер не зміг отримати підтвердження продовження від кворуму DCS:

```
t - t₀ ≥ T[ttl] - T[retry] ⇒ Leader_Demote()   [примусове зняття повноважень лідера для уникнення split-brain]
```

### Оптимізація таймауту детекції через функцію сумарних витрат

Вибір параметра `T[ttl]` є компромісом між двома видами фінансових втрат:
1. Вартість простою під час реальної аварії: `C[downtime] · RTO(T[ttl])`.
2. Вартість помилкового перемикання (False Positive): `C[false] · P[false](T[ttl])`, де `P[false]` — ймовірність того, що мережева пауза або GC-пауза триватиме довше ніж `T[ttl]`.

Якщо тривалість випадкових затримок `X` описується важкохвостим розподілом Парето `P(X > t) = (t_m / t)^α`:

```
C_total(T[ttl]) = C[downtime] · (T[ttl] + T[promote]) + C[false] · (t_m / T[ttl])^α   [функція загальних очікуваних втрат]
```

Прирівнюючи похідну `dC_total / dT[ttl]` до нуля:

```
dC_total / dT[ttl] = C[downtime] - α · C[false] · t_m^α · T[ttl]^(-α - 1) = 0
T[ttl]^(α + 1) = (α · C[false] · t_m^α) / C[downtime]                                [виділення невідомого параметра]
T[ttl_opt] = ( (α · C[false] · t_m^α) / C[downtime] )^(1 / (α + 1))                 [оптимальний аналітичний таймаут лізу]
```

Ця формула математично визначає точне значення таймауту лізингу на основі бізнес-вартості помилкового перемикання та статистики мережевих викидів інфраструктури.

### Формула загального часу відновлення (RTO) при автоматичному Failover

Сумарний RTO складається з послідовності фізичних фаз:

```
RTO = T[detect] + T[fence] + T[elect] + T[catchup] + T[promote] + T[route]   [сума тривалостей усіх фаз перемикання]
```

Розкладемо компоненти формули:
1. `T[detect] = T[ttl] + ε` — час, необхідний DCS для визнання лізу протермінованим після падіння лідера (`ε` — час реакції спостерігача).
2. `T[fence] = T[ipmi] + T[grace]` — час підтвердження ізоляції старого лідера (відключення через PDU/IPMI або вичерпання локального watchdog-таймера).
3. `T[elect] = 2 · RTT[dcs]` — час проведення раунду виборів нового лідера в Raft/etcd серед доступних кандидатів.
4. `T[catchup] = (LSN[leader] - LSN[candidate]) / B[replay]` — час допрогравання реплікою відсталих записів WAL/binlog, де `B[replay]` — швидкість читання та застосування журналу (байт/с).
5. `T[promote] = T[pg_promote]` — внутрішній час переведення рушія СКБД з режиму recovery у режим read-write (створення нової точки таймлайну Timeline ID).
6. `T[route] = T[health_check] + T[proxy_reload]` — час виявлення нового лідера балансувальником HAProxy / PgBouncer та перемикання сокетів.

### Розрахунок RTO на числовому прикладі

Нехай задано типові виробничі параметри високодоступного кластера PostgreSQL:
- `T[ttl] = 10` с, `T[loop] = 2` с, `T[retry] = 5` с.
- `T[fence] = 1.5` с (watchdog timeout або API ізоляції).
- `RTT[dcs] = 5` мс (`0.005` с) ⇒ `T[elect] = 0.01` с.
- Репліка відставала на `ΔLSN = 16` МБ (`16 777 216` байт), швидкість програвання WAL `B[replay] = 64` МБ/с (`67 108 864` байт/с).
- `T[promote] = 0.8` с.
- Інтервал опитування HAProxy: `inter = 1000` мс (`1` с), `fall = 2`, `rise = 1` ⇒ `T[route] = 1.0` с.

Обчислимо час допрогравання журналу `T[catchup]`:
```
T[catchup] = 16 777 216 / 67 108 864
= 0.25 с   [час застосування 16 МБ WAL]
```

Обчислимо повний час детекції та перемикання RTO:
```
RTO = 10.0 + 1.5 + 0.01 + 0.25 + 0.8 + 1.0
= 13.56 с   [підсумковий час недоступності запису для клієнтів]
```

Цей розрахунок демонструє, що понад 73% часу простою припадає на фазу детекції (`T[ttl] = 10` с). Зменшення `T[ttl]` скорочує RTO, але підвищує ризик помилкових спрацьовувань (False Positive Failover) при тимчасових сплесках мережевої затримки `J[net] > T[retry]`. Математичний компроміс вимагає вибору `T[ttl] ≥ 3 · T[loop] + T[retry]`.
