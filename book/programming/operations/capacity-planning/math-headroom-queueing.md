# 🧮 Математика черг, формули Кінгмана та розрахунок запасу міцності (Headroom)

Розрахунок необхідної кількості серверів на основі простого ділення сумарного трафіку на пропускну здатність одного вузла створює ілюзію стабільності, яка руйнується під час першого ж сплеску попиту. Реальний час відповіді розподіленої системи визначається не середньою швидкістю процесора, а стохастичною поведінкою черг очікування, де затримка зростає гіперболічно при наближенні утилізації до 100%. Математичне моделювання черг та інженерного запасу потужності (англ. *headroom*) дозволяє кількісно обчислити поріг безпечного завантаження, за якого система гарантовано виконує вимоги угоди про рівень обслуговування (SLO).

## Модель M/M/1 та закон Літтла

Найпростішою аналітичною моделлю для опису одного обчислювального вузла (або одного робочого потоку) є система масового обслуговування `M/M/1` за класифікацією Кендалла:
- Перша літера `M` (Markov / Memoryless) означає пуассонівський вхідний потік запитів з інтенсивністю `λ` (середня кількість запитів на секунду). Час між послідовними надходженнями запитів має експоненційний розподіл.
- Друга літера `M` означає експоненційний розподіл тривалості обслуговування запиту із середньою інтенсивністю `μ` (середня кількість оброблених запитів на секунду одним процесором). Середній час чистої обробки запиту становить `S = 1 / μ`.
- Цифра `1` позначає один обслуговуючий пристрій (одне процесорне ядро або один робочий потік).

Коефіцієнт завантаження (утилізація) системи `U` визначається відношенням інтенсивності надходження до інтенсивності обслуговування:

```
U = λ / μ
```

Умова стаціонарності (динамічної рівноваги) вимагає виконання суворої нерівності:

```
U < 1  (тобто λ < μ)
```

Якщо `λ ≥ μ`, черга зростає до нескінченності, і система зазнає переповнення пам'яті або відкидання пакетів.

За законом Літтла (`L = λ · W`), середня кількість запитів у системі `L` дорівнює добутку темпу надходження `λ` на повний середній час перебування запиту в системі `W`. Повний час перебування `W` складається із середнього часу очікування в черзі `W_q` та часу безпосередньої обробки на процесорі `S = 1 / μ`:

```
W = W_q + S = W_q + (1 / μ)
```

Для системи `M/M/1` середня кількість запитів у системі `L` виводиться з імовірностей станів марковського процесу народження і загибелі:

```
L = U / (1 - U)
```

Застосовуючи закон Літтла для знаходження повного часу `W`:

```
W
= L / λ                           [закон Літтла: W = L / λ]
= ( U / (1 - U) ) / λ             [підстановка L = U / (1 - U)]
= ( (λ / μ) / (1 - U) ) / λ       [розкриття визначення утилізації: U = λ / μ]
= (1 / μ) / (1 - U)               [скорочення на λ]
= S / (1 - U)                     [підстановка часу обслуговування S = 1 / μ]
```

Відповідно, середній час очікування в черзі `W_q` до початку виконання процесором становить:

```
W_q
= W - S                           [повний час мінус чистий час обробки]
= (S / (1 - U)) - S               [підстановка W = S / (1 - U)]
= S · ( (1 / (1 - U)) - 1 )       [винесення S за дужки]
= S · ( (1 - (1 - U)) / (1 - U) ) [зведення до спільного знаменника]
= S · ( U / (1 - U) )             [спрощення чисельника]
```

Ця формула описує фундаментальне явище: коли завантаження `U` наближається до 1 (100%), знаменник `1 - U` прямує до нуля, а час черги `W_q` прямує до нескінченності.

## Наближення Кінгмана для загальних розподілів (G/G/1 та G/G/c)

У реальних виробничих середовищах вхідний потік і час обробки рідко бувають суворо експоненційними. HTTP-запити надходять пачками (сплесковий трафік), а час виконання бази даних має важкі хвости (Heavy Tails) через складні аналітичні запити. Для систем загального типу `G/G/1` (General arrival, General service, 1 server) застосовують **наближену формулу Джона Кінгмана** (*Kingman's approximation formula*, 1961):

```
W_q ≈ ( (c_a² + c_s²) / 2 ) · ( U / (1 - U) ) · S
```

Де:
- `c_a = σ_a / E[A]` — коефіцієнт варіації інтервалів між надходженнями запитів (`σ_a` — стандартне відхилення, `E[A] = 1 / λ` — середній інтервал).
- `c_s = σ_s / E[S]` — коефіцієнт варіації тривалості обслуговування запиту (`σ_s` — стандартне відхилення часу обробки, `E[S] = S = 1 / μ`).
- `U = λ / μ` — коефіцієнт завантаження процесора.

Формула Кінгмана розкладає час очікування в черзі на три незалежні множники:
1. **Фактор варіативності (Variability Term):** `(c_a² + c_s²) / 2`. Якщо трафік абсолютно регулярний і детермінований (`c_a = 0, c_s = 0`), черга відсутня взагалі (`W_q = 0`). Якщо в системі з'являється висока дисперсія (наприклад, поодинокі «важкі» запити з `c_s = 3`), час очікування зростає у `(1 + 9) / 2 = 5` разів порівняно з пуассонівським випадком (`c_a = 1, c_s = 1`).
2. **Фактор завантаження (Utilization Term):** `U / (1 - U)`. Визначає нелінійне згинання кривої затримки.
3. **Фактор масштабу сервісу (Service Scale Term):** `S = 1 / μ`. Базова швидкість одиничної обробки.

## Швидкість росту черги: похідна за утилізацією

Щоб зрозуміти, чому невелике збільшення навантаження на перевантажений кластер призводить до катастрофи, візьмемо першу похідну від часу очікування `W_q(U)` за коефіцієнтом утилізації `U`:

```
d(W_q) / dU
= d/dU [ K · ( U / (1 - U) ) ]        [де константа K = ( (c_a² + c_s²) / 2 ) · S]
= K · ( ( 1 · (1 - U) - U · (-1) ) / (1 - U)² ) [правило похідної частки]
= K · ( ( 1 - U + U ) / (1 - U)² )    [розкриття дужок у чисельнику]
= K / (1 - U)²                         [спрощення чисельника]
```

Порівняємо чутливість затримки до зростання завантаження на різних ділянках робочої кривої:

1. **При утилізації `U = 0.50` (50%):**
   ```
   d(W_q) / dU = K / (1 - 0.50)² = K / 0.25 = 4 · K
   ```
   Зростання навантаження на 1% збільшує затримку черги пропорційно коефіцієнту `4 · K`.

2. **При утилізації `U = 0.80` (80%):**
   ```
   d(W_q) / dU = K / (1 - 0.80)² = K / 0.04 = 25 · K
   ```
   Чутливість зросла у `25 / 4 = 6.25` раза порівняно з 50% завантаженням.

3. **При утилізації `U = 0.95` (95%):**
   ```
   d(W_q) / dU = K / (1 - 0.95)² = K / 0.0025 = 400 · K
   ```
   Чутливість зросла у `400 / 4 = 100` разів! На цій ділянці коливання трафіку лише на 1–2% призводить до миттєвого стрибка черги на сотні мілісекунд, що викликає масові таймаути клієнтських додатків.

## Визначення та розрахунок запасу міцності (Headroom)

Headroom (`H`) — це частка загальної обчислювальної місткості системи, яка залишається незадіяною під час регулярної роботи для поглинання дисперсії трафіку, збереження затримки в межах SLO та компенсації відмов обладнання:

```
H = 1 - U = 1 - (λ / C_total)
```

Де:
- `C_total` — сумарна пропускна здатність кластера (максимальний RPS, який кластер здатний обробити без виходу в необмежену чергу).
- `λ` — поточний вхідний потік запитів.

Якщо цільове значення затримки згідно з угодою SLO вимагає, щоб середній час очікування в черзі не перевищував `W_{q,max}`, ми можемо аналітично обчислити гранично допустиму утилізацію `U_{max}` та мінімальний обов'язковий запас `H_{min}`:

```
W_q ≤ W_{q,max}
K · ( U / (1 - U) ) ≤ W_{q,max}
U / (1 - U) ≤ W_{q,max} / K
U ≤ ( W_{q,max} / K ) · (1 - U)
U · ( 1 + W_{q,max} / K ) ≤ W_{q,max} / K
U ≤ ( W_{q,max} / K ) / ( 1 + W_{q,max} / K )
U_{max} = W_{q,max} / ( K + W_{q,max} )
```

Звідси мінімальний Headroom для задоволення SLO затримки становить:

```
H_{min} = 1 - U_{max} = K / ( K + W_{q,max} )
```

## Модель розрахунку розміру кластера з резервуванням N+k

Нехай розподілений сервіс складається з пулу однакових серверних вузлів. Кожен вузол має виміряну навантажувальним тестуванням продуктивність `C_node` (RPS на один вузол при дотриманні SLO).

Вхідні параметри моделі планування потужності:
- `Λ_base` — базовий середній потік вхідних запитів (RPS).
- `k_diurnal` — коефіцієнт добового піку (`Λ_peak = Λ_base · k_diurnal`).
- `k_burst` — коефіцієнт короткочасних випадкових спалахів трафіку (Burst Factor).
- `U_target` — безпечна робоча утилізація кожного окремого вузла (зазвичай 0.60–0.70).
- `k_fail` — кількість одночасно відмовляючих вузлів, яку кластер зобов'язаний витримати без деградації (`k_fail = 1` для схеми `N+1`, `k_fail = 2` для `N+2`).

Формула розрахунку мінімальної кількості робочих вузлів `N_work`:

```
N_work = ceil[ (Λ_base · k_diurnal · k_burst) / (C_node · U_target) ]
```

Повна кількість вузлів кластера `N_total` з урахуванням резервування відмов:

```
N_total = N_work + k_fail
```

### Перевірка завантаженості після відмови (Post-Failure Utilization)

Якщо у кластері з `N_total` вузлів раптово виходять з ладу `k_fail` серверів, решта `N_work = N_total - k_fail` вузлів повинна прийняти 100% пікового навантаження. Завантаженість вцілілих серверів `U_post` становитиме:

```
U_post = U_target · ( N_total / (N_total - k_fail) )
```

**Критична вимога надійності:** завантаженість `U_post` у момент аварії не повинна перевищувати критичний поріг насичення `U_crit` (зазвичай 0.85–0.90), інакше кластер впаде внаслідок каскадної деградації затримки.

```
U_post ≤ U_crit
U_target · ( N_total / (N_total - k_fail) ) ≤ U_crit
U_target ≤ U_crit · ( (N_total - k_fail) / N_total )
```

Ця нерівність доводить важливий інженерний принцип: **чим менше вузлів у кластері, тим нижчим має бути цільове завантаження `U_target`**. 
- Для кластера з `N = 3` вузлів при відмові 1 вузла навантаження зростає у `3 / 2 = 1.50` раза (на 50%). Щоб `U_post ≤ 0.85`, базове `U_target` не повинно перевищувати `0.85 / 1.50 = 0.56` (56%).
- Для кластера з `N = 20` вузлів при відмові 1 вузла навантаження зростає лише у `20 / 19 = 1.052` раза (на 5.2%), тому `U_target` можна безпечно підняти до `0.85 / 1.052 = 0.80` (80%).

## Багатосерверна система M/M/c та формула Ерланга C

Коли запити надходять у спільну чергу, яку паралельно обробляють `c` однакових серверних потоків або обчислювальних ядер, поведінка системи моделюється процесом `M/M/c`.

Сумарна інтенсивність обслуговування системи з `c` серверами дорівнює `c · μ`. Загальний коефіцієнт завантаження системи визначається як:

```
U = λ / (c · μ)
```

Умова стаціонарності вимагає `U < 1` (тобто `λ < c · μ`).

Імовірність того, що новоприбулий запит застане всі `c` серверів зайнятими і буде змушений стати в чергу очікування, описується класичною **формулою Ерланга C** (*Erlang C formula*, `C(c, a)`, де `a = λ / μ = c · U` — запропоноване навантаження в ерлангах):

```
P(очікування) = C(c, a) = ( (a^c / c!) · (1 / (1 - U)) ) / ( ∑_{k=0}^{c-1} (a^k / k!) + (a^c / c!) · (1 / (1 - U)) )
```

Середній час очікування в черзі для системи `M/M/c` виводиться як добуток імовірності очікування на середній час звільнення одного із зайнятих серверів:

```
W_q = C(c, a) · ( S / (c · (1 - U)) ) = C(c, a) / ( c · μ · (1 - U) )
```

З формули Ерланга C випливає важливий математичний ефект **ефекту масштабу черги (Pooling Effect / Economy of Scale)**:
- Один великий спільний пул із `c = 16` ядер при сумарному навантаженні `U = 80%` має в рази меншу середню затримку черги `W_q`, ніж 16 ізольованих ядер з окремими чергами по одному ядру (`c = 1`) при тому самому навантаженні `U = 80%`.
- У великому пулі випадкові статистичні флуктуації часу обробки взаємно гасяться, тому ймовірність простою всіх серверів при наявності черги стрімко падає.

## Скінченні буфери та ймовірність відкидання (M/M/c/K та формула Ерланга B)

У реальних операційних системах пам'ять під чергу не є нескінченною. Якщо сокетний буфер або черга задач у пам'яті вміщує максимум `K` запитів (де `K ≥ c`), система моделюється процесом `M/M/c/K`.

Коли в системі вже знаходиться `K` запитів, будь-який новоприбулий запит негайно відкидається (Drop / Rejection).

Для випадку без черги очікування (`K = c`, тобто запит або обслуговується негайно, або скидається з помилкою) імовірність блокування запиту описується першою **формулою втрат Ерланга (Erlang B formula)**:

```
P(відкидання) = B(c, a) = ( a^c / c! ) / ( ∑_{k=0}^c (a^k / k!) )
```

Де `a = λ / μ` — запропоноване навантаження в ерлангах.

У системах зі скінченною чергою (`K > c`) фактичний темп надходження запитів на сервери `λ_eff` зменшується за рахунок відкинутих запитів:

```
λ_eff = λ · (1 - P_{K})
```

Де `P_{K}` — стаціонарна ймовірність того, що буфер повністю заповнений (`K` запитів у системі). Знання `P_{K}` дозволяє точно розрахувати необхідний розмір системного буфера пам'яті (Backlog Size) для гарантування того, що відсоток втрачених транзакцій не перевищить бюджет помилок SLO (наприклад, менше 0.001% відкинутих запитів).

## Математика відмовостійкості у багатозональній архітектурі (Multi-AZ)

У хмарних архітектурах обчислювальні вузли розподіляються між декількома ізольованими зонами доступності (Availability Zones, AZ). Розглянемо математику планування потужності для випадку повної аварійної відмови однієї з зон.

Нехай загальний вхідний трафік `Λ` рівномірно балансується між `M` зонами доступності (`M ≥ 2`). Кожна зона містить `N_zone` вузлів з одиничною корисною продуктивністю `C_node`.

У штатному режимі (Normal State) кожна зона отримує частку трафіку:

```
Λ_zone = Λ / M
```

Завантаження вузлів у кожній зоні в штатному режимі становить:

```
U_steady = (Λ / M) / (N_zone · C_node) = Λ / (M · N_zone · C_node)
```

При раптовій катастрофічній відмові однієї зони доступності (AZ Outage) вцілілі `M - 1` зон повинні прийняти 100% сумарного трафіку `Λ`. Новий потік на одну працюючу зону:

```
Λ_zone,fail = Λ / (M - 1)
```

Завантаження вузлів у вцілілих зонах `U_fail` підскочить до:

```
U_fail
= Λ_zone,fail / (N_zone · C_node)                   [визначення завантаженості однієї зони при аварії]
= ( Λ / (M - 1) ) / (N_zone · C_node)               [підстановка аварійного трафіку зони Λ_zone,fail = Λ / (M - 1)]
= ( Λ / (M · N_zone · C_node) ) · ( M / (M - 1) )   [виділення штатного співвідношення через множення і ділення на M]
= U_steady · ( M / (M - 1) )                        [підстановка штатної утилізації U_steady]
```

Щоб вцілілі зони не перетнули критичний поріг колапсу затримки `U_crit` (наприклад, `U_crit = 0.85`), штатна завантаженість `U_steady` не повинна перевищувати:

```
U_steady ≤ U_crit · ( (M - 1) / M )
```

Порівняємо вимоги до штатного Headroom залежно від кількості зон:

1. **Двозональна схема (`M = 2` AZ):**
   ```
   U_steady ≤ 0.85 · ( (2 - 1) / 2 ) = 0.85 · 0.50 = 0.425  (42.5%)
   ```
   У двозвузовій/двозональній схемі кожна зона повинна бути недовантажена більш ніж на 57.5% (`Headroom ≥ 57.5%`). В іншому разі падіння однієї зони подвоїть навантаження на другу (`2 · 45% = 90%`), що призведе до повного виходу з ладу всього сервісу.

2. **Тризональна схема (`M = 3` AZ):**
   ```
   U_steady ≤ 0.85 · ( (3 - 1) / 3 ) = 0.85 · 0.667 = 0.567  (56.7%)
   ```
   У тризональній схемі кожна зона штатно працює при `U ≈ 55%`, а обов'язковий `Headroom ≈ 45%`. При падінні однієї зони навантаження на решту зростає в `3 / 2 = 1.5` раза, піднімаючи утилізацію до безпечних `55% · 1.5 = 82.5%`.

3. **Чотиризональна схема (`M = 4` AZ):**
   ```
   U_steady ≤ 0.85 · ( (4 - 1) / 4 ) = 0.85 · 0.75 = 0.6375  (63.75%)
   ```
   У чотиризональній схемі штатна утилізація може сягати 63%, оскільки втрата однієї зони додає лише `4 / 3 = 1.333` (33.3%) до навантаження вцілілих вузлів.

## Розрахунок перцентилів затримки (p95 та p99)

Угоди про рівень обслуговування (SLO) майже ніколи не формулюються через середній час відповіді, оскільки середнє арифметичне приховує важкі хвости затримок. SLO зазвичай встановлює межі для 95-го (`p95`) або 99-го (`p99`) перцентилів.

Для експоненційно розподіленого часу очікування в системі `M/M/1` функція розподілу часу очікування в черзі `P(W_q ≤ t)` має вигляд:

```
P(W_q ≤ t) = 1 - U · e^{ -μ · (1 - U) · t }
```

Знайдемо аналітичний вираз для `p`-го перцентиля затримки черги `t_p` (де `p ∈ (0, 1)`, наприклад `p = 0.99` для 99-го перцентиля):

```
1 - U · e^{ -μ · (1 - U) · t_p } = p
U · e^{ -μ · (1 - U) · t_p } = 1 - p
e^{ -μ · (1 - U) · t_p } = (1 - p) / U
-μ · (1 - U) · t_p = ln[ (1 - p) / U ]
t_p = ln[ U / (1 - p) ] / ( μ · (1 - U) ) = S · ( ln[ U / (1 - p) ] / (1 - U) )
```

Аналіз формули показує:
- При `U = 0.50` і чистому часі обробки `S = 2` мс 99-й перцентиль затримки черги становить:
  ```
  t_{0.99} = 2 мс · ( ln[ 0.50 / 0.01 ] / (1 - 0.50) ) = 2 · ( ln(50) / 0.50 ) = 4 · 3.912 = 15.65 мс
  ```
- При `U = 0.85` і тому самому `S = 2` мс:
  ```
  t_{0.99} = 2 мс · ( ln[ 0.85 / 0.01 ] / (1 - 0.85) ) = 2 · ( ln(85) / 0.15 ) = (2 / 0.15) · 4.443 = 59.24 мс
  ```
- При `U = 0.95`:
  ```
  t_{0.99} = 2 мс · ( ln[ 0.95 / 0.01 ] / (1 - 0.95) ) = 2 · ( ln(95) / 0.05 ) = 40 · 4.554 = 182.15 мс
  ```

Зростання завантаження з 50% до 95% збільшило 99-й перцентиль затримки черги у `182.15 / 15.65 = 11.6` раза! Це математично пояснює, чому високоутилізовані сервери неминуче порушують вимоги строгих SLO для «хвостових» користувачів.

## Покроковий числовий приклад комплексного розрахунку

Розглянемо практичний розрахунок необхідної місткості для бекенду електронної комерції:

**Вихідні дані:**
- Середній денний трафік: `Λ_base = 6 000` RPS.
- Коефіцієнт вечірнього піку: `k_diurnal = 1.5` (піковий трафік `9 000` RPS).
- Коефіцієнт випадкових спалахів: `k_burst = 1.2` (максимальний розрахунковий сплеск `10 800` RPS).
- Продуктивність одного контейнера: `C_node = 400` RPS (при чистому часі обробки `S = 2.5` мс).
- Коефіцієнти варіації: `c_a = 1.2`, `c_s = 1.0`.
- Цільова максимальна затримка в черзі: `W_{q,max} = 5.0` мс.
- Топологія розгортання: `M = 3` зони доступності.
- Вимога відмовостійкості: витримати повне падіння 1 зони доступності (`AZ Outage`) + локальне падіння `k_fail = 1` сервера у кожній вцілілій зоні.

**Крок 1. Розрахунок фактора варіативності `K`:**

```
K
= ( (c_a² + c_s²) / 2 ) · S                         [формула фактора варіативності Кінгмана]
= ( (1.2² + 1.0²) / 2 ) · 2.5 мс                    [підстановка c_a = 1.2, c_s = 1.0, S = 2.5 мс]
= ( (1.44 + 1.00) / 2 ) · 2.5 мс                    [піднесення коефіцієнтів варіації до квадрата]
= ( 2.44 / 2 ) · 2.5 мс                             [додавання квадратів дисперсій]
= 1.22 · 2.5 мс                                     [ділення на 2]
= 3.05 мс                                           [множення на чистий час обробки S]
```

**Крок 2. Розрахунок гранично допустимої утилізації `U_max` за критерієм SLO:**

```
U_max
= W_{q,max} / ( K + W_{q,max} )                     [гранична утилізація за критерієм допустимої черги]
= 5.0 мс / ( 3.05 мс + 5.0 мс )                     [підстановка W_{q,max} = 5.0 мс та K = 3.05 мс]
= 5.0 / 8.05                                        [додавання в знаменнику]
≈ 0.621                                             [ділення: результат 62.1%]
```

Для гарантування запасу обираємо граничну аварійну утилізацію `U_crit = 0.62` (62%).

**Крок 3. Розрахунок штатної цільової утилізації `U_steady` для 3-зональної схеми:**

```
U_steady
= U_crit · ( (M - 1) / M )                          [формула штатного завантаження для M зон]
= 0.62 · ( (3 - 1) / 3 )                            [підстановка U_crit = 0.62 та M = 3 зон]
= 0.62 · ( 2 / 3 )                                  [обчислення частки вцілілих зон]
≈ 0.413                                             [множення: результат 41.3%]
```

Обираємо штатне розрахункове завантаження `U_target = 0.40` (40%).

**Крок 4. Розрахунок сумарної кількості робочих вузлів у кластері:**

```
Λ_total_peak = 6 000 · 1.5 · 1.2 = 10 800 RPS
Корисна штатна місткість одного вузла = C_node · U_target = 400 · 0.40 = 160 RPS

N_work_total
= ceil[ 10 800 / 160 ]                              [ділення пікового трафіку на корисну місткість вузла]
= ceil[ 67.5 ]                                      [проміжний результат ділення]
= 68                                                [округлення вгору до цілого вузла]
```

**Крок 5. Розподіл по 3 зонах з урахуванням локального резерву `k_fail = 1` на зону:**

```
Вузлів на зону (робочих) = ceil[ 68 / 3 ] = 23 вузли
Вузлів на зону (з резервом N+1) = 23 + 1 = 24 вузли
Загальна кількість вузлів у 3 зонах = 24 · 3 = 72 вузли
```

**Крок 6. Перевірка стрес-сценарію: повне падіння 1 зони доступності:**

При падінні однієї зони трафік `10 800` RPS розподіляється порівну між двома вцілілими зонами (по `5 400` RPS на зону).
У кожній зоні працює `24` вузли. Сумарна пікова потужність зони: `24 · 400 = 9 600` RPS.

Фактична утилізація вузлів вцілілих зон під час катастрофи становить:

```
U_disaster
= 5 400 / 9 600                                     [ділення аварійного трафіку на сумарну місткість зони]
= 0.5625                                            [результат ділення: 56.25%]
```

Отримане значення `56.25%` не перевищує граничний ліміт `U_crit = 62%`. Система збереже середній час очікування в черзі менше 5 мс навіть у разі повної втрати цілого дата-центру на піку святкових продажів.
