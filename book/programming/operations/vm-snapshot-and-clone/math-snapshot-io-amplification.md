# 🧮 Математика I/O-ампліфікації, глибини ланцюжка та зростання обсягу при CoW і RoW

Математичний аналіз дискових операцій при роботі зі знімками віртуальних машин дозволяє точно розрахувати деградацію пропускної здатності, зростання латентності вводу-виводу при поглибленні ланцюжка шарів, динаміку вичерпання дискового простору, критерії збіжності живої консолідації та оптимальну точку для запуску ребейзу або злиття. Цей документ містить строге аналітичне виведення коефіцієнтів ампліфікації, ймовірнісних моделей пошуку блоків, динаміки ітеративної пам'яті та розрахунків вартості реструктуризації дискового дерева.

## 1. Коефіцієнт ампліфікації запису (Write Amplification Factor)

Коефіцієнт ампліфікації запису (`WAF`) визначається як відношення сумарного фізичного обсягу даних, записаного на постійний накопичувач, до логічного обсягу даних, надісланого гостьовою операційною системою:

```
WAF = Physical_Bytes_Written / Logical_Bytes_Requested
```

### 1.1. Класичний Copy-on-Write (CoW) з `N` знімками

Розглянемо блоковий том, для якого створено `N` активних знімків за класичною схемою CoW (де основний том продовжує модифікуватися на місці, а витіснені старі блоки копіюються в дельта-пули).

Нехай гостьова ОС надсилає запит на модифікацію одного блоку розміром `B` байтів, який ще не змінювався після створення жодного з `N` знімків. Дисковий контролер виконує:
1. Одне зчитування старого блоку з основного тому: `1 · B` (читання).
2. Запис старого блоку в кожен із `N` дельта-пулів: `N · B` (запис).
3. Запис нового блоку даних на початкове місце в основному томі: `1 · B` (запис).

Сумарна кількість фізичних операцій вводу-виводу на один логічний запис:

```
IO_ops_total
= 1 [читання старого блоку з основного тому]
+ N [записи старого блоку в N дельта-пулів знімків]
+ 1 [запис нового блоку в основний том]
= N + 2 [загальна кількість дискових операцій]
```

Сумарний фізичний коефіцієнт ампліфікації запису за обсягом байтів:

```
WAF_cow(N)
= (N·B + 1·B) / B   [враховуємо лише операції запису]
= N + 1             [фізичний обсяг запису на носій]
```

Якщо врахувати повну вартість дискового каналу (читання + запис):

```
WAF_cow_total(N)
= (1·B + N·B + 1·B) / B   [сума операцій читання та записів, поділена на розмір блоку]
= N + 2                   [повний коефіцієнт навантаження на дискову шину]
```

### Покроковий числовий розрахунок падіння пропускної здатності

Нехай фізичний NVMe-накопичувач забезпечує швидкість випадкового запису `T_raw = 300 000` IOPS. Розрахуємо ефективну швидкість запису гостьової ОС `T_eff` за наявності `N = 4` знімків CoW під час модифікації холодних блоків:

```
T_eff
= T_raw / WAF_cow_total(4)
= 300000 / (4 + 2)          [підстановка N = 4]
= 300000 / 6                [обчислення знаменника]
= 50000 IOPS                [результат: деградація у 6 разів (83.3% втрати)]
```

### 1.2. Redirect-on-Write (RoW) та дельта-оверлеї

У схемі Redirect-on-Write старий блок залишається недоторканим у базовому шарі (Read-Only), а новий блок записується безпосередньо у файл оверлею разом з оновленням запису в таблиці трансляції другого рівня (L2 Table у QCOW2):

```
WAF_row
= (B_data + B_metadata) / B_data
= (65536 + 8) / 65536             [для кластера 64 КБ і запису L2 розміром 8 байтів]
= 65544 / 65536
≈ 1.000122                        [ампліфікація практично відсутня]
```

## 2. Ймовірнісна модель латентності читання та глибини ланцюжка

Розглянемо ланцюжок шарів глибиною `L`, де шар `1` — активний оверлей, шари `2, 3, ..., L - 1` — проміжні знімки, а шар `L` — базовий образ.

### 2.1. Ймовірність локалізації сектора

Нехай у кожному знімку гостьова ОС модифікує випадкову частку блоків `p` (`0 < p < 1`), розподілену рівномірно по всьому простору диска.

Ймовірність того, що шуканий сектор буде знайдено на шарі `k`:
- Для активного шару (`k = 1`): `P(K = 1) = p`.
- Для шару `k` (`1 < k < L`): сектор не був змінений у попередніх `k - 1` шарах, але був змінений у шарі `k`:
  `P(K = k) = p · (1 - p)^(k - 1)`.
- Для базового образу (`k = L`): сектор не змінювався в жодному з попередніх `L - 1` оверлеїв і зчитується з бази:
  `P(K = L) = (1 - p)^(L - 1)`.

Перевіримо умову нормування ймовірностей:

```
Sum_{k=1}^{L} P(K = k)
= Sum_{k=1}^{L-1} [p · (1 - p)^(k-1)] + (1 - p)^(L-1)
= p · [1 - (1 - p)^(L-1)] / [1 - (1 - p)] + (1 - p)^(L-1)   [сума геометричної прогресії]
= p · [1 - (1 - p)^(L-1)] / p + (1 - p)^(L-1)               [скорочення на p]
= 1 - (1 - p)^(L-1) + (1 - p)^(L-1)
= 1                                                         [нормування виконується точно]
```

### 2.2. Математичне сподівання кількості перевірених шарів `E[K]`

Математичне сподівання глибини пошуку `E[K]` визначає середню кількість операцій опитування метаданих, необхідну для виконання одного читання:

```
E[K]
= Sum_{k=1}^{L-1} [k · p · (1 - p)^(k-1)] + L · (1 - p)^(L-1)
```

Застосуємо формулу згортування для арифметрико-геометричного ряду `Sum_{k=1}^{n} k · q^(k-1) = [1 - (n+1)·q^n + n·q^(n+1)] / (1 - q)^2`, де `q = 1 - p`:

```
E[K]
= p · [1 - L·(1 - p)^(L-1) + (L - 1)·(1 - p)^L] / p^2 + L · (1 - p)^(L-1)   [підстановка суми арифметрико-геометричного ряду]
= [1 - L·(1 - p)^(L-1) + (L - 1)·(1 - p)^L] / p + L · (1 - p)^(L-1)         [скорочення на p]
= [1 - (1 - p)^L] / p                                                       [зведення подібних доданків]
```

### Виведення граничних станів

1. Якщо `p -> 1` (диск повністю перезаписується в кожному шарі):
   `lim_{p -> 1} E[K] = [1 - 0] / 1 = 1` (усі читання обслуговуються активним шаром).
2. Якщо `p -> 0` (холодний диск, знімки майже не містять змін):
   За правилом Лопіталя або розкладом у ряд Тейлора `(1 - p)^L = 1 - L·p + (L(L-1)/2)·p^2 - ...`:

```
lim_{p -> 0} E[K]
= lim_{p -> 0} [1 - (1 - L·p + (L·(L-1)/2)·p^2)] / p   [розклад Тейлора до другого порядку]
= lim_{p -> 0} [L·p - (L·(L-1)/2)·p^2] / p             [розкриття дужок у чисельнику]
= L - lim_{p -> 0} [(L·(L-1)/2)·p]                     [ділення на p]
= L                                                    [граничний перехід при p -> 0]
```

При малих змінах гостя середня кількість звернень дорівнює повній глибині ланцюжка `L`.

### 2.3. Розрахунок латентності читання

Нехай час звернення до кешованої таблиці L2 становить `t_meta = 5` мкс, а час читання блоку з NVMe становить `t_media = 80` мкс. Загальна очікувана латентність читання `T_read`:

```
T_read(L, p) = E[K] · t_meta + t_media
```

Для ланцюжка з `L = 10` знімків і частки змін `p = 0.05` (5% модифікацій на шар):

```
E[K]
= [1 - (1 - 0.05)^10] / 0.05
= [1 - (0.95)^10] / 0.05
= [1 - 0.598737] / 0.05          [обчислення 0.95^10]
= 0.401263 / 0.05
= 8.025 шарів                    [середня глибина проходу]

T_read
= 8.025 · 5 мкс + 80 мкс         [підстановка математичного сподівання та латентностей]
= 40.125 + 80                    [множення часу доступу до метаданих]
= 120.125 мкс                    [зростання затримки на 50.1% від базової]
```

## 3. Динаміка розростання дельта-шарів та дивергенція простору

Оцінимо зростання фізичного розміру дельта-оверлею `V_snap(t)` у часі при випадковому потоці записів від гостьової ОС.

Нехай диск має загальну кількість секторів `S`, а гостьова ОС виконує рівномірно розподілений випадковий запис з інтенсивністю `w` секторів за секунду.

Задача еквівалентна класичній задачі збирання купонів (Coupon Collector's Problem). Ймовірність того, що конкретний сектор жодного разу не буде обраний за `m = w · t` незалежних операцій запису:

```
P_not_written(t) = (1 - 1/S)^(w · t)
```

Використовуючи границю `lim_{S -> inf} (1 - 1/S)^S = e^(-1)`, отримуємо наближення:

```
P_not_written(t) ≈ e^(- (w · t) / S)
```

Математичне сподівання кількості унікальних модифікованих секторів `U(t)` до моменту часу `t`:

```
U(t) = S · [1 - P_not_written(t)] = S · [1 - e^(- (w · t) / S)]
```

Фізичний розмір файлу оверлею на хості (без урахування фіксованого заголовка):

```
V_snap(t) = U(t) · Sector_Size = S · Sector_Size · [1 - e^(- (w · t) / S)] = V_base · [1 - e^(- (w · t) / S)]
```

```
Графік насичення дельти:
V_snap / V_base
  1.0 ┤                                      ──────────────── (границя: 100% диска)
      │                                ───---
  0.8 ┤                           ───--
      │                      ───--
  0.6 ┤                  ───-
      │              ───-
  0.4 ┤          ───-
      │      ───-
  0.2 ┤  ───-
      └──┬───────────┬───────────┬───────────┬───────────┬───> Час t
         0          S/w        2·S/w       3·S/w       4·S/w
```

### Практичний висновок

Коли час життя знімка сягає `t = 3 · (S / w)`, оверлей заповнюється на `1 - e^(-3) ≈ 95%` обсягу базового диска. У цій точці спільне використання базового образу втрачає сенс, а дельта-файл споживає майже стільки ж місця, скільки повний клон, додаючи при цьому накладні витрати на трансляцію метаданих.

## 4. Математичний критерій вибору вектору консолідації: Commit проти Stream

Під час ліквідації знімка інженер має вибір між двома операціями:
1. **Block Commit:** перенесення модифікованих блоків з оверлеїв униз у базовий образ.
2. **Block Stream (Pull):** підтягування немодифікованих блоків із базового образу вгору в оверлей.

Нехай:
- `V_base` — повний розмір базового диска.
- `V_delta` — сумарний фізичний розмір модифікованих даних у дельта-оверлеях (`V_delta = Sum_{i=1}^{K} Delta_i`).

### 4.1. Обсяг операцій введення-виведення

Для операції **Block Commit**:
Необхідно зчитати всі дельта-блоки та записати їх у базовий образ:

```
IO_commit = 2 · V_delta   [1 читання з оверлею + 1 запис у базу]
```

Для операції **Block Stream**:
Необхідно зчитати з базового образу всі блоки, які **ще не були модифіковані** в оверлеях, і записати їх у верхній оверлей:

```
IO_stream = 2 · (V_base - V_delta)   [1 читання з бази + 1 запис в оверлей]
```

### 4.2. Точка рівноваги та правило прийняття рішень

Знайдемо умову, за якої Block Commit виконує менше дискових операцій, ніж Block Stream:

```
IO_commit < IO_stream
2 · V_delta < 2 · (V_base - V_delta)   [підстановка формул]
V_delta < V_base - V_delta             [скорочення на 2]
2 · V_delta < V_base                   [перенесення V_delta вліво]
V_delta < V_base / 2                   [ділення на 2]
```

### Практичне правило консолідації

```
Якщо V_delta < 0.5 · V_base  ──>  Обирати Block Commit (швидше, менше I/O)
Якщо V_delta > 0.5 · V_base  ──>  Обирати Block Stream (швидше, менше I/O)
```

Якщо накопичена дельта становить менше 50% розміру базового диска (типовий випадок для короткоживучих знімків перед оновленням ПЗ), операція **Block Commit** є строго оптимальнішою за часом виконання та навантаженням на дискову підсистему. Якщо ж знімок існував місяцями і перевершив 50% базового обсягу, операція **Block Stream** вимагає перенесення меншої кількості байтів.

## 5. Моделювання збіжності живої фонової консолідації (Live Block Commit)

Коли злиття активного верхнього шару виконується у фоновому режимі без зупинки віртуальної машини, гостьова ОС продовжує модифікувати блоки накопичувача паралельно з роботою фонового процесу перенесення.

Нехай:
- `R_commit` — швидкість фонового копіювання блоків гіпервізором (МБ/с).
- `R_guest` — середня швидкість генерації нових брудних блоків гостьовою ОС (МБ/с).
- `D_0` — початковий обсяг дельта-оверлею на момент старту консолідації (МБ).

### 5.1. Динаміка обсягу незлитих блоків за ітераціями

Консолідація працює ітеративними раундами:
- Тривалість раунду `0`: `T_0 = D_0 / R_commit`.
- За час `T_0` гостьова ОС генерує новий брудний обсяг `D_1 = R_guest · T_0 = D_0 · (R_guest / R_commit)`.
- Для довільної ітерації `m`:

```
D_m = D_0 · (R_guest / R_commit)^m
```

Позначимо коефіцієнт генерації дельти як `alpha = R_guest / R_commit`.

Сумарний час виконання `M` ітерацій виражається сумою нескінченної геометричної прогресії:

```
T_total
= Sum_{m=0}^{inf} T_m
= Sum_{m=0}^{inf} (D_m / R_commit)
= (D_0 / R_commit) · Sum_{m=0}^{inf} alpha^m
= (D_0 / R_commit) · [1 / (1 - alpha)]     [за умови alpha < 1]
= D_0 / (R_commit - R_guest)
```

### 5.2. Критерій розбіжності та дроротлювання гостя

- **Умова збіжності (`alpha < 1` або `R_commit > R_guest`):** черга брудних блоків експоненціально прямує до нуля, і після досягнення порогового значення `D_threshold` гіпервізор виконує фінальне перемикання (pivot) за мілісекундну паузу.
- **Умова розбіжності (`alpha >= 1` або `R_guest >= R_commit`):** дельта-оверлей росте швидше, ніж гіпервізор устигає зливати блоки. Консолідація ніколи не завершиться самостійно і призведе до вичерпання дискового простору хоста.

Для примусового забезпечення збіжності оркестратор застосовує штучне обмеження інтенсивності вводу-виводу гостя (I/O Throttling):

```
R_guest_max = R_commit · (1 - epsilon),  де epsilon > 0 (зазвичай 0.2..0.3)
```

## 6. Аналіз багатошарових деревоподібних ієрархій та коефіцієнт дедуплікації

У середовищах тестування або VDI (Virtual Desktop Infrastructure) один базовий диск `base.raw` використовується як основа для розгалуженого дерева зв'язаних клонів та знімків.

Розглянемо регулярне дерево клонів із коефіцієнтом розгалуження `b` та глибиною ієрархії `h`.

- Кількість термінальних активних віртуальних машин на листках дерева: `N_vms = b^h`.
- Обсяг базового незмінного диска: `V_base`.
- Середній обсяг дельти на кожному вузлі дерева: `V_delta`.

Загальний фізичний обсяг сховища, який займає вся ієрархія зв'язаних клонів `V_tree`:

```
V_tree
= V_base + Sum_{j=1}^{h} [b^j · V_delta]              [сума базового диска та дельт усіх вузлів]
= V_base + V_delta · b · (b^h - 1) / (b - 1)          [згортка суми геометричної прогресії]
```

Якби кожна з `N_vms` віртуальних машин створювалася як повний автономний клон (Full Clone), потрібний дисковий простір становив би:

```
V_full = N_vms · (V_base + h · V_delta) = b^h · (V_base + h · V_delta)
```

Коефіцієнт економії дискового простору (Deduplication Ratio):

```
R_dedup = V_full / V_tree
```

### Числовий розрахунок для VDI-ферми

Нехай базовий образ Windows 11 має розмір `V_base = 60` ГБ, коефіцієнт розгалуження `b = 8`, глибина дерева `h = 2` (разом `N_vms = 8^2 = 64` віртуальні машини), а середня накопичена дельта на вузол `V_delta = 5` ГБ.

Розрахуємо обсяги:

```
V_full
= 64 · (60 + 2 · 5)   [підстановка значень: 64 ВМ, 60 ГБ база, 2 рівні по 5 ГБ]
= 64 · 70             [обчислення обсягу однієї автономної ВМ]
= 4480 ГБ (4.375 ТБ)  [сумарний простір для 64 повних клонів]

V_tree
= 60 + 5 · 8 · (8^2 - 1) / (8 - 1)   [підстановка параметрів дерева]
= 60 + 40 · 63 / 7                   [обчислення 8^2 - 1 та знаменника]
= 60 + 40 · 9                        [ділення 63 на 7]
= 60 + 360                           [множення 40 на 9]
= 420 ГБ                             [сумарний фізичний розмір дерева]

R_dedup
= 4480 / 420                         [відношення обсягів]
≈ 10.67                              [економія простору у 10.67 разів (зменшення на 90.6%)]
```

Цей результат строго доводить економічну доцільність зв'язаного клонування для динамічних тестових лабораторій та хмарних пулів розробки.

## 7. Математична модель збереження живого знімка оперативної пам'яті (Live RAM Pre-Copy)

Під час створення живого знімка віртуальної машини зі збереженням пам'яті (`savevm` або `virsh snapshot-create --live`) гіпервізор застосовує алгоритм попереднього ітеративного копіювання сторінок RAM (Pre-Copy Algorithm).

Нехай:
- `M_total` — загальний виділений обсяг оперативної пам'яті віртуальної машини (МБ).
- `B_dump` — пропускна здатність дискової підсистеми хоста для запису дампа пам'яті (МБ/с).
- `R_mem_dirty` — інтенсивність генерації брудних сторінок гостьовою ОС (МБ/с).
- `M_threshold` — пороговий залишок брудної пам'яті для переходу у фінальну фазу зупинки vCPU (зазвичай 50–100 МБ).
- `T_max_downtime` — максимально допустимий час повної зупинки vCPU гостя (наприклад, 100 мс = 0.1 с).

### 7.1. Розрахунок часу ітерацій дампування пам'яті

На початковому кроці `j = 0` гіпервізор починає потоковий запис усіх сторінок пам'яті гостя на диск:

```
T_0 = M_total / B_dump
```

Поки триває запис початкового обсягу, гостьові процеси модифікують пам'ять, генеруючи брудний обсяг для першої ітерації:

```
M_1 = R_mem_dirty · T_0 = M_total · (R_mem_dirty / B_dump)
```

Позначимо коефіцієнт пам'яті як `beta = R_mem_dirty / B_dump`. Для довільної ітерації `j`:

```
M_j = M_total · beta^j
T_j = M_j / B_dump = (M_total / B_dump) · beta^j
```

Кількість ітерацій `J`, необхідна для зменшення залишку до порогового рівня `M_threshold`:

```
M_total · beta^J <= M_threshold
beta^J <= M_threshold / M_total
J · ln(beta) <= ln(M_threshold / M_total)
J >= ln(M_total / M_threshold) / ln(1 / beta)   [оскільки beta < 1, ln(beta) < 0]
```

### 7.2. Фінальний час зупинки віртуальної машини (Downtime)

Коли залишок брудної пам'яті досягає `M_threshold`, гіпервізор повністю зупиняє всі vCPU і скидає залишок пам'яті та стан регістрів процесорів на диск:

```
T_downtime = (M_threshold / B_dump) + T_cpu_state
```

Умова успішності виконання вимог SLA:

```
T_downtime <= T_max_downtime
(M_threshold / B_dump) + T_cpu_state <= T_max_downtime
M_threshold <= B_dump · (T_max_downtime - T_cpu_state)
```

### Числовий приклад розрахунку живої фіксації пам'яті

Нехай віртуальна машина має `M_total = 32 768` МБ (32 ГБ RAM), швидкість дискового масиву `B_dump = 800` МБ/с (швидкий NVMe), швидкість модифікації пам'яті гостя `R_mem_dirty = 200` МБ/с, час збереження регістрів vCPU `T_cpu_state = 0.01` с (10 мс), а цільовий даунтайм `T_max_downtime = 0.1` с (100 мс).

1. Обчислюємо коефіцієнт `beta`:
   `beta = 200 / 800 = 0.25`.
2. Обчислюємо допустимий поріг `M_threshold`:
   `M_threshold = 800 · (0.1 - 0.01) = 800 · 0.09 = 72 МБ`.
3. Обчислюємо кількість ітерацій `J`:
   `J = ln(32768 / 72) / ln(1 / 0.25) = ln(455.11) / ln(4) = 6.12 / 1.3863 ≈ 4.41 -> 5 ітерацій`.
4. Обчислюємо сумарний час фонового дампування до зупинки:

```
T_pre_copy
= (M_total / B_dump) · [ (1 - beta^J) / (1 - beta) ]   [сума часу всіх J ітерацій]
= (32768 / 800) · [ (1 - 0.25^5) / (1 - 0.25) ]       [підстановка M = 32768, B = 800, beta = 0.25, J = 5]
= 40.96 · [ (1 - 0.000976) / 0.75 ]                   [обчислення 0.25^5 та 1 - beta]
= 40.96 · [ 0.999024 / 0.75 ]                         [віднімання в чисельнику]
= 40.96 · 1.33203                                     [ділення на 0.75]
≈ 54.56 секунд                                        [фінальний час фонового дампування]
```

Гіпервізор виконує фоновий запис протягом 54.56 секунд, після чого зупиняє гостьові vCPU лише на 100 мілісекунд для збереження фінальних 72 МБ пам'яті.

## 8. Ампліфікація промахів кешу в багаторівневих ієрархіях

Коли віртуальна машина функціонує з глибоким ланцюжком оверлеїв, кешування блоків зазнає деградації через розділення сторінкового кешу хоста між кількома дескрипторами файлів.

Нехай:
- `C_host` — сумарний обсяг сторінкового кешу ядра хоста (Host PageCache).
- `W` — робочий набір активних блоків віртуальної машини (Working Set Size).
- `L` — глибина ланцюжка шарів.

У монолітному диску всі звернення до робочого набору `W` обслуговуються єдиним дескриптором файлу, і ймовірність влучання в кеш `H_flat` визначається класичною моделлю LRU:

```
H_flat = min(1.0, C_host / W)
```

За наявності `L` шарів оверлеїв звернення до одного й того самого логічного блоку в різні моменти часу розмиваються між `L` окремими дескрипторами `inode` у ядрі хоста. Крім того, для кожного шару ядро змушене утримувати в кеші таблиці трансляції другого рівня `L2`.

Додаткові витрати пам'яті на кешування метаданих оверлеїв:

```
M_metadata(L) = L · (W / S_cluster) · Size_L2_Entry
```

Ефективний обсяг кешу, доступний для корисних даних гостя:

```
C_eff(L) = C_host - M_metadata(L)
```

Ефективна ймовірність влучання в кеш у ланцюжку шарів:

```
H_chain(L) = max(0.0, (C_host - L · (W / S_cluster) · Size_L2_Entry) / (W · (1 + (L - 1) · p)))
```

З формули видно, що при збільшенні глибини ланцюжка `L` ймовірність влучання в кеш падає швидше за лінійну залежність, підтверджуючи фундаментальне інженерне правило: **глибина ланцюжка активних знімків у продуктивному середовищі не повинна перевищувати 3–4 рівнів**.

## 9. Розрахунок граничного часу життя знімка за бюджетом сховища

Щоб запобігти аварійній зупинці продуктивних віртуальних машин через переповнення тонкого сховища хоста (`ENOSPC`), системний адміністратор повинен розраховувати максимально допустимий час життя активного знімка `T_lifespan_max`.

Нехай:
- `S_free` — доступний вільний дисковий простір на розділі хоста (ГБ).
- `S_safety_margin` — гарантований аварійний резерв простору (за стандартом не менше 15–20% від загальної ємності сховища).
- `W_daily` — добовий обсяг запису гостьової ОС (ГБ/добу).
- `V_base` — повний віртуальний обсяг базового диска (ГБ).

Формула граничного часу життя знімка до вимушеного запуску консолідації:

```
T_lifespan_max = - (V_base / W_daily) · ln(1 - (S_free - S_safety_margin) / V_base)
```

Якщо `(S_free - S_safety_margin) >= V_base`, знімок може існувати до повного насичення дельти без ризику переповнення носія. Якщо ж вільний простір обмежений, наведений розрахунок визначає точний дедлайн для планувальника автоматизованого злиття шарів.
