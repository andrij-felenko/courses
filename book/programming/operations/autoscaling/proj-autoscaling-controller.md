# ⚙️ Практична реалізація контролера автоскейлу з гістерезисом та згладжуванням

Побудова власного або інтеграційного контролера автоскейлу (наприклад, для нестандартної черги чи спеціалізованого пулу обчислень) вимагає не просто обчислення співвідношення між поточною метрикою та її цільовим значенням. Найпростіша реалізація на кшталт `if (cpu > 70) replicas++` у продакшні неминуче призводить до катастрофічного явища — «флапінгу» (паразитних автоколивань пулу), коли система безперервно запускає та знищує процеси кожні кілька секунд, спалюючи процесорний час на ініціалізацію та спричиняючи шторм помилок 502/504.

Надійний контролер автоматичного масштабування має розв'язувати чотири інженерні задачі:
1. **Згладжування шумів телеметрії:** поодинокий короткий сплеск навантаження тривалістю 200 мілісекунд (наприклад, важкий звіт чи пачка фонових завдань) не повинен викликати панічний запуск десяти нових серверів.
2. **Зона нечутливості (Deadband):** коливання метрики в межах допустимого коридору (наприклад, ±10% від цілі) повинні ігноруватися, зберігаючи поточний стабільний розмір пулу.
3. **Асиметричні часові вікна (Cooldown / Stabilization):** реакція на перевантаження має бути миттєвою (масштабування вгору), тоді як вивільнення ресурсів (масштабування вниз) має бути витриманим і консервативним, вимагаючи тривалого підтвердження стабільного спаду активності.
4. **Захисні бар'єри (Guardrails):** жорсткі межі мінімальної та максимальної кількості екземплярів, а також ліміт на максимальну швидкість скорочення пулу (rate limit), що захищає від раптового знищення потужностей під час тимчасового збою збору метрик.

## Архітектура та математична модель контролера

Контролер працює як періодичний дискретний регулятор (Control Loop), що викликається через фіксований інтервал часу `Δt` (типово раз на 10–15 секунд).

### 1. Експоненційне згладжування метрики (EMA)
Для фільтрації високочастотного шуму застосовується експоненційно зважене ковзне середнє (англ. *Exponential Moving Average*, EMA):

```
EMA[t] = α · M[t] + (1 - α) · EMA[t - 1]
```

де `M[t]` — сире значення метрики на поточному кроці, а `α ∈ (0, 1]` — коефіцієнт згладжування. При `α = 0.3` регулятор надає 30% ваги свіжому виміру і 70% — накопиченій історії, зрізаючи випадкові викиди.

### 2. Оцінка зони нечутливості (Deadband)
Якщо цільове значення метрики дорівнює `Target`, а поточне згладжене значення — `EMA`, обчислюється відносне відхилення:

```
ratio = EMA / Target
```

Якщо `|ratio - 1.0| ≤ tolerance` (де `tolerance` типово становить 0.1, тобто ±10%), поточна кількість реплік вважається оптимальною і зміна пулу блокується.

### 3. Розрахунок цільової кількості реплік
Якщо відхилення виходить за межі deadband, базова кількість реплік обчислюється як:

```
Desired = ceil( CurrentReplicas · ratio )
```

Округлення вгору (`ceil`) є критичним для забезпечення безпеки: якщо розрахунок показує потребу в 4.1 серверах, виділення 4 призведе до перевантаження, тому система обирає 5.

### 4. Асиметрична стабілізація
- **Scale-up (Збільшення пулу):** якщо `Desired > CurrentReplicas`, новий стан застосовується негайно або з мінімальною паузою (cooldown 10–15 с), щоб запобігти деградації затримки відповідей.
- **Scale-down (Скорочення пулу):** якщо `Desired < CurrentReplicas`, зміна не застосовується одразу. Контролер фіксує таймстемп запиту на зменшення і очікує проходження вікна стабілізації (наприклад, 300 секунд). Якщо протягом усього вікна навантаження залишається стабільно низьким, виконується плавне скорочення не більше ніж на `max_scale_down_step` за крок.

## Реалізація на C та C++

Нижче наведено повністю працездатну, самодостатню реалізацію контролера автоскейлу. Код містить симулятор навантаження, який демонструє обробку різкого стрибка трафіку, перебування на плато та безпечне покрокове згортання без коливань.

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>
#include <math.h>
#include <time.h>

/* Конфігураційні параметри контролера автоскейлу */
typedef struct {
    int min_replicas;             /* Жорсткий мінімум реплік */
    int max_replicas;             /* Жорсткий максимум (захист бази даних) */
    double target_metric;         /* Цільове значення (наприклад, 70% CPU або 50 RPS) */
    double tolerance;             /* Зона нечутливості (наприклад, 0.10 = ±10%) */
    double ema_alpha;             /* Коефіцієнт експоненційного згладжування [0..1] */
    int scale_up_cooldown_sec;    /* Пауза між послідовними збільшеннями пулу */
    int scale_down_window_sec;    /* Вікно стабілізації перед зменшенням пулу */
    int max_scale_down_step;      /* Максимальна кількість реплік, що знімаються за 1 крок */
} AutoscalerConfig;

/* Поточний стан контролера */
typedef struct {
    int current_replicas;         /* Фактична кількість працюючих екземплярів */
    double smoothed_metric;       /* Поточне значення EMA */
    bool ema_initialized;         /* Прапорець першого запуску */
    time_t last_scale_up_time;    /* Час останнього масштабування вгору */
    time_t scale_down_candidate_time; /* Час, коли навантаження вперше впало нижче норми */
} AutoscalerState;

/* Результат кроку оцінки */
typedef struct {
    int new_replicas;             /* Нова рекомендована кількість реплік */
    bool action_taken;            /* Чи була виконана зміна розміру пулу */
    const char* reason;           /* Пояснення прийнятого рішення */
} AutoscalerDecision;

/* Ініціалізація стану за замовчуванням */
void autoscaler_init(AutoscalerState* state, int initial_replicas) {
    state->current_replicas = initial_replicas;
    state->smoothed_metric = 0.0;
    state->ema_initialized = false;
    state->last_scale_up_time = 0;
    state->scale_down_candidate_time = 0;
}

/* Обчислення одного кроку циклу автоскейлу */
AutoscalerDecision autoscaler_evaluate(const AutoscalerConfig* cfg,
                                      AutoscalerState* state,
                                      double raw_metric,
                                      time_t now) {
    AutoscalerDecision decision;
    decision.new_replicas = state->current_replicas;
    decision.action_taken = false;
    decision.reason = "Стан стабільний (у межах норми)";

    /* 1. Оновлення експоненційного середнього (EMA) */
    if (!state->ema_initialized) {
        state->smoothed_metric = raw_metric;
        state->ema_initialized = true;
    } else {
        state->smoothed_metric = cfg->ema_alpha * raw_metric + (1.0 - cfg->ema_alpha) * state->smoothed_metric;
    }

    /* 2. Перевірка відносного відхилення */
    double ratio = state->smoothed_metric / cfg->target_metric;
    double deviation = fabs(ratio - 1.0);

    /* Перевірка зони нечутливості (Deadband) */
    if (deviation <= cfg->tolerance) {
        state->scale_down_candidate_time = 0; /* Скидаємо таймер згортання */
        decision.reason = "Метрика всередині зони нечутливості (deadband)";
        return decision;
    }

    /* 3. Розрахунок бажаної кількості за формулою ceil(N * ratio) */
    int desired = (int)ceil((double)state->current_replicas * ratio);

    /* Застосування жорстких меж Guardrails */
    if (desired < cfg->min_replicas) desired = cfg->min_replicas;
    if (desired > cfg->max_replicas) desired = cfg->max_replicas;

    /* 4. Гілка збільшення потужностей (Scale-up) */
    if (desired > state->current_replicas) {
        state->scale_down_candidate_time = 0; /* Скасовуємо плани на скорочення */

        if (now - state->last_scale_up_time < cfg->scale_up_cooldown_sec) {
            decision.reason = "Scale-up заблоковано таймером охолодження (cooldown)";
            return decision;
        }

        decision.new_replicas = desired;
        decision.action_taken = true;
        decision.reason = "Виконано Scale-up (збільшення навантаження)";
        state->current_replicas = desired;
        state->last_scale_up_time = now;
        return decision;
    }

    /* 5. Гілка зменшення потужностей (Scale-down) */
    if (desired < state->current_replicas) {
        if (state->scale_down_candidate_time == 0) {
            /* Перший крок фіксації падіння навантаження */
            state->scale_down_candidate_time = now;
            decision.reason = "Фіксація спаду метрики: запущено вікно стабілізації";
            return decision;
        }

        /* Перевіряємо, чи минуло вікно стабілізації */
        if (now - state->scale_down_candidate_time < cfg->scale_down_window_sec) {
            decision.reason = "Очікування стабілізації перед Scale-down";
            return decision;
        }

        /* Обмеження кроку скорочення (Rate limit на видалення) */
        int allowed_drop = state->current_replicas - desired;
        if (allowed_drop > cfg->max_scale_down_step) {
            desired = state->current_replicas - cfg->max_scale_down_step;
        }

        decision.new_replicas = desired;
        decision.action_taken = true;
        decision.reason = "Виконано безпечний Scale-down після стабілізації";
        state->current_replicas = desired;
        state->scale_down_candidate_time = now; /* Скидаємо для наступного кроку */
        return decision;
    }

    return decision;
}

int main(void) {
    AutoscalerConfig cfg = {
        .min_replicas = 2,
        .max_replicas = 10,
        .target_metric = 70.0,         /* 70% цільове CPU */
        .tolerance = 0.10,            /* ±10% зона спокою [63%..77%] */
        .ema_alpha = 0.40,            /* Коефіцієнт фільтра */
        .scale_up_cooldown_sec = 15,  /* 15 секунд між scale-up */
        .scale_down_window_sec = 60,  /* 60 секунд стабілізації для тесту */
        .max_scale_down_step = 2      /* Не більше 2 екземплярів за раз */
    };

    AutoscalerState state;
    autoscaler_init(&state, 2);

    /* Імітація профілю навантаження: спокій -> стрибок -> спад */
    double load_profile[] = {
        68.0, 72.0, 95.0, 110.0, 85.0, 75.0, 40.0, 35.0, 30.0, 32.0, 30.0, 30.0
    };
    int steps = sizeof(load_profile) / sizeof(load_profile[0]);

    printf("=== Симуляція роботи контролера автоскейлу (C) ===\n");
    printf("%-5s | %-8s | %-8s | %-8s | %-40s\n", "Час", "Сирий CPU", "EMA CPU", "Репліки", "Рішення");
    printf("----------------------------------------------------------------------------------------\n");

    time_t virtual_time = 1000;
    for (int i = 0; i < steps; ++i) {
        double raw = load_profile[i];
        AutoscalerDecision d = autoscaler_evaluate(&cfg, &state, raw, virtual_time);

        printf("%4ds  | %7.1f%% | %7.1f%% | %8d | %s\n",
               (int)(virtual_time - 1000), raw, state.smoothed_metric, state.current_replicas, d.reason);

        virtual_time += 15; /* Крок 15 секунд */
    }

    return 0;
}
```

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <string_view>
#include <chrono>
#include <cmath>
#include <iomanip>
#include <algorithm>

namespace ops {

using namespace std::chrono_literals;

struct AutoscalerConfig {
    int min_replicas{2};
    int max_replicas{10};
    double target_metric{70.0};              // Цільовий CPU % або RPS
    double tolerance{0.10};                  // Deadband ±10% [63% .. 77%]
    double ema_alpha{0.40};                  // Вага свіжого значення в EMA
    std::chrono::seconds scale_up_cooldown{15s};
    std::chrono::seconds scale_down_window{60s};
    int max_scale_down_step{2};
};

struct AutoscalerDecision {
    int new_replicas;
    bool action_taken;
    std::string reason;
};

class AutoscalerController {
public:
    explicit AutoscalerController(AutoscalerConfig config, int initial_replicas = 2)
        : config_(config), current_replicas_(initial_replicas) {}

    AutoscalerDecision evaluate(double raw_metric, std::chrono::steady_clock::time_point now) {
        // 1. Оновлення експоненційного середнього
        if (!ema_initialized_) {
            smoothed_metric_ = raw_metric;
            ema_initialized_ = true;
        } else {
            smoothed_metric_ = config_.ema_alpha * raw_metric + (1.0 - config_.ema_alpha) * smoothed_metric_;
        }

        // 2. Перевірка зони нечутливості (Deadband)
        const double ratio = smoothed_metric_ / config_.target_metric;
        const double deviation = std::abs(ratio - 1.0);

        if (deviation <= config_.tolerance) {
            scale_down_candidate_time_.reset();
            return {current_replicas_, false, "Метрика всередині зони нечутливості (deadband)"};
        }

        // 3. Розрахунок бажаної кількості з округленням угору
        int desired = static_cast<int>(std::ceil(current_replicas_ * ratio));
        desired = std::clamp(desired, config_.min_replicas, config_.max_replicas);

        // 4. Гілка збільшення (Scale-up)
        if (desired > current_replicas_) {
            scale_down_candidate_time_.reset();

            if (last_scale_up_time_ && (now - *last_scale_up_time_ < config_.scale_up_cooldown)) {
                return {current_replicas_, false, "Scale-up заблоковано таймером охолодження (cooldown)"};
            }

            current_replicas_ = desired;
            last_scale_up_time_ = now;
            return {current_replicas_, true, "Виконано Scale-up (збільшення навантаження)"};
        }

        // 5. Гілка зменшення (Scale-down)
        if (desired < current_replicas_) {
            if (!scale_down_candidate_time_) {
                scale_down_candidate_time_ = now;
                return {current_replicas_, false, "Фіксація спаду метрики: запущено вікно стабілізації"};
            }

            if (now - *scale_down_candidate_time_ < config_.scale_down_window) {
                return {current_replicas_, false, "Очікування стабілізації перед Scale-down"};
            }

            const int allowed_drop = current_replicas_ - desired;
            if (allowed_drop > config_.max_scale_down_step) {
                desired = current_replicas_ - config_.max_scale_down_step;
            }

            current_replicas_ = desired;
            scale_down_candidate_time_ = now;
            return {current_replicas_, true, "Виконано безпечний Scale-down після стабілізації"};
        }

        return {current_replicas_, false, "Стан стабільний (у межах норми)"};
    }

    [[nodiscard]] double smoothed_metric() const noexcept { return smoothed_metric_; }
    [[nodiscard]] int current_replicas() const noexcept { return current_replicas_; }

private:
    AutoscalerConfig config_;
    int current_replicas_;
    double smoothed_metric_{0.0};
    bool ema_initialized_{false};
    std::optional<std::chrono::steady_clock::time_point> last_scale_up_time_;
    std::optional<std::chrono::steady_clock::time_point> scale_down_candidate_time_;
};

} // namespace ops

int main() {
    ops::AutoscalerConfig config{
        .min_replicas = 2,
        .max_replicas = 10,
        .target_metric = 70.0,
        .tolerance = 0.10,
        .ema_alpha = 0.40,
        .scale_up_cooldown = 15s,
        .scale_down_window = 60s,
        .max_scale_down_step = 2
    };

    ops::AutoscalerController controller(config, 2);

    const std::vector<double> load_profile{
        68.0, 72.0, 95.0, 110.0, 85.0, 75.0, 40.0, 35.0, 30.0, 32.0, 30.0, 30.0
    };

    std::cout << "=== Симуляція роботи контролера автоскейлу (C++) ===\n";
    std::cout << std::left << std::setw(6) << "Час"
              << " | " << std::setw(9) << "Сирий CPU"
              << " | " << std::setw(9) << "EMA CPU"
              << " | " << std::setw(8) << "Репліки"
              << " | " << "Рішення\n";
    std::cout << std::string(88, '-') << "\n";

    auto virtual_now = std::chrono::steady_clock::now();
    const auto start_time = virtual_now;

    for (double raw : load_profile) {
        auto decision = controller.evaluate(raw, virtual_now);
        auto elapsed = std::chrono::duration_cast<std::chrono::seconds>(virtual_now - start_time).count();

        std::cout << std::right << std::setw(4) << elapsed << "s  | "
                  << std::setw(7) << std::fixed << std::setprecision(1) << raw << "% | "
                  << std::setw(7) << controller.smoothed_metric() << "% | "
                  << std::setw(8) << controller.current_replicas() << " | "
                  << decision.reason << "\n";

        virtual_now += 15s;
    }

    return 0;
}
```

## Інженерні пастки, регулятори вищого порядку та системне простеження

Під час експлуатації такого регулятора у виробничому середовищі розробники стикаються зі складними крайовими випадками динамічних систем, які виходять за межі простої арифметики.

### 1. Вибір коефіцієнта згладжування `α` та запізнення фази

Експоненційне згладжування створює фазовий зсув (затримку реакції) між реальним моментом сплеску навантаження та моментом, коли згладжена крива перетне поріг активації. Якщо `α` обрано занадто малим (наприклад, `0.05`), система набуває надмірної інерційності: стрибок навантаження зі 100 RPS до 1 000 RPS згладжуватиметься контролером протягом 2–3 хвилин, протягом яких наявні сервери встигнуть вичерпати черги з'єднань, піти у глибокий свопінг і впасти під лавиною клієнтських повторів (retry storm).

Якщо ж `α` обрано занадто великим (`0.90`), фільтр майже не пригнічує високочастотний шум: будь-який одиночний «важкий» SQL-запит або тимчасовий збір сміття (GC pause), що підкинув завантаження ядра на 300 мілісекунд, спричинить непотрібний запуск нових інстансів.

Оптимальний діапазон для дискретного циклу з інтервалом опитування `Δt = 15` секунд становить `0.30 ≤ α ≤ 0.50`. Для критичних систем часто комбінують подвійний поріг: плавний згладжений контур для звичайних добових коливань та аварійний обхідний контур (Fast-path bypass), який негайно подвоює кількість реплік, якщо сире миттєве значення перевищує 95% протягом двох вимірів поспіль.

### 2. ПД- та ПІД-регулятори проти простого пропорційного масштабування

Класичний HPA використовує пропорційний контролер із накопиченням історії через вікно. Проте в теорії автоматичного керування класичним інструментом є пропорційно-інтегрально-диференціальний (ПІД, англ. *PID*) регулятор:

```
u(t) = K_p · e(t) + K_i · ∫ e(τ) dτ + K_d · (de(t) / dt)
```

де помилка розгортання `e(t) = M(t) - Target`.

- **Пропорційна складова (`K_p · e(t)`):** забезпечує пряму реакцію на поточну величину перевантаження. Чим вища поточна метрика, тим більше серверів додається.
- **Диференціальна складова (`K_d · (de/dt)`):** оцінює **швидкість наростання** навантаження (першу похідну). Якщо трафік зростає зі швидкістю +500 RPS за секунду, диференціальна частина б'є на сполох і замовляє сервери **наперед**, ще до того, як абсолютна метрика досягне критичної межі. Це компенсує затримку старту нових контейнерів.
- **Інтегральна складова (`K_i · ∫ e(τ) dτ`):** накопичує тривале невелике відхилення (статичну помилку). Якщо система годинами зависає на рівні 74% при цілі 70%, інтеграл повільно накопичує суму і додає ще один екземпляр для повернення в ідеальну точку.

**Небезпека інтегрального насичення (Integral Windup):** головна пастка ПІД-регулятора в автоскейлі полягає в тому, що коли кластер уперся в жорстку стелю `max_replicas`, інтегральна сума продовжує нескінченно рости, поки триває перевантаження. Коли навантаження нарешті спадає, роздутий інтеграл годинами утримує максимальну кількість серверів, відмовляючись згортати пул. Тому в промислових контролерах використовують схеми захисту від насичення (anti-windup clamping), які заморожують інтегратор при досягненні лімітів `min_replicas` / `max_replicas`.

### 3. Простеження через Linux cgroups v2 та ядро

На рівні операційної системи Linux метрики споживання ресурсів контейнерами зчитуються безпосередньо з файлової системи контрольних груп cgroups v2 (змонтованої у `/sys/fs/cgroup`). Контролер або агент збору метрик (node-exporter, cAdvisor) виконує парсинг системних лічильників:

```bash
# Перевірка обмежень процесора для контейнера
$ cat /sys/fs/cgroup/system.slice/docker-xyz.scope/cpu.max
200000 100000    # Дозволено 200 000 мкс (2 vCPU) на кожні 100 000 мкс квоти

# Отримання реального використання та тротлінгу (cgroups v2)
$ cat /sys/fs/cgroup/system.slice/docker-xyz.scope/cpu.stat
usage_usec 4819203912      # Сумарний час виконання в мікросекундах
user_usec 3912840192
system_usec 906363720
nr_periods 48201           # Кількість минулих квантів часу
nr_throttled 3412          # Скільки разів процес було насильно призупинено (throttling)
throttled_usec 89124012    # Сумарний час затримки через вичерпання ліміту CPU
```

Для автоскейлу метрика `nr_throttled / nr_periods` є критичним випереджальним індикатором: якщо відсоток тротлінгу перевищує 5–10%, це означає, що застосунок впирається у виділені ядра й відчуває різке зростання затримки (latency spikes), навіть якщо усереднений за 1 хвилину CPU показує помірні 65%.

Метрика оперативної пам'яті в cgroups v2 зчитується з:

```bash
$ cat /sys/fs/cgroup/system.slice/docker-xyz.scope/memory.current
1847582720                 # Поточне використання пам'яті в байтах (~1.72 ГБ)

$ cat /sys/fs/cgroup/system.slice/docker-xyz.scope/memory.events
low 0
high 14                    # Скільки разів спрацьовував soft-limit пам'яті
max 0                      # Скільки разів викликався OOM-killer (жорстке завершення процесу)
oom 0
oom_kill 0
```

### 4. Робота з нульовими репліками (Scale-to-Zero) та чергами

Коли сервіс обробляє асинхронні повідомлення з Kafka або RabbitMQ, у періоди простою тримати воркери увімкненими безглуздо. Проте масштабування до нуля створює математичну сингулярність у формулі:

```
Desired = ceil( Current · (Metric / Target) )
        = ceil( 0 · (45000 / 100) )
        = 0
```

Якщо `Current = 0`, результат множення завжди дорівнює нулю, і система ніколи не створить перший екземпляр.

Для подолання цієї проблеми рушії масштабування подій (Event-driven scalers, як-от KEDA) розділяють логіку на два незалежні контури:
1. **Контур активації (Activator):** працює у режимі масштабування 0 ↔ 1. Якщо черга порожня (`Lag == 0`), розмір пулу дорівнює `0`. Як тільки у черзі з'являється хоча б одне повідомлення (`Lag > 0`), активатор примусово викликає оркестратор і виставляє `replicas = 1`.
2. **Контур пропорційного розширення (HPA Scaler):** як тільки кількість реплік стає `≥ 1`, вмикається стандартна пропорційна формула контролера, яка розраховує точну кількість воркерів під обсяг нагромаджених повідомлень:
   `Desired = ceil( Lag / TargetMessagesPerWorker )`.

### 5. Поведінка під час відмови підсистем моніторингу

Якщо Prometheus, агент метрик або мережа між оркестратором та базою часових рядів зазнає аварії, контролер автоскейлу опиняється у стані неповноти даних (Failed Scrape). Існує три стратегії поведінки:

1. **Fail-Closed (Песимістична):** вважати втрату метрик нульовим навантаженням і скоротити пул до `min_replicas`. Це найгірший вибір у продакшні: якщо сервер метрик впав саме через перевантаження мережі під час шторму трафіку, автоскейлер доб'є систему, вимкнувши решту працюючих серверів.
2. **Fail-Open (Агресивна):** примусово виставити `max_replicas` під час тривалої відсутності телеметрії. Це гарантує доступність системи ціною тимчасового збільшення фінансових витрат.
3. **Freeze / Last Known Good (Стандарт Kubernetes HPA):** зафіксувати поточну кількість реплік і повністю заблокувати будь-які операції масштабування (як вгору, так і вниз), згенерувавши критичний алерт для чергових інженерів. Це найбільш збалансований інженерний підхід.

### 6. Взаємодія зі штатним вимкненням (Graceful Drain)

Масштабування вниз (Scale-in) вимагає суворої координації між контролером автоскейлу, балансувальником навантаження та сервером застосунку:
1. Контролер вибирає екземпляри-кандидати на видалення (зазвичай найновіші або ті, що виконуються на найменш завантажених вузлах для подальшого вивільнення цілих віртуальних машин).
2. Оркестратор змінює статус readiness-проби екземпляра на `Unhealthy` або надсилає сигнал балансувальнику (Ingress/Envoy) на вилучення IP-адреси з пулу активної маршрутизації.
3. Балансувальник припиняє надсилати нові TCP-з'єднання.
4. Процесу надсилається сигнал `SIGTERM`. Застосунок завершує обробку активних HTTP-запитів (inflight requests), скидає буфери логів, повертає з'єднання до пулу реляційної бази даних і коректно закриває сокети.
5. Лише після завершення встановленого таймауту завершення (graceful termination period, наприклад, 30–60 секунд) контейнер остаточно знищується.

### 7. Теорія масового обслуговування, закон Літтла та крайові розподіли черг

Коли контролер масштабує асинхронні обробники черг (наприклад, воркери обробки відео, генерації PDF чи парсингу платіжних реєстрів), наївне ділення довжини черги на константу є неповним без урахування закону Літтла (Little's Law).

У стаціонарному стані системи масового обслуговування середня кількість заявок у системі `L` дорівнює добутку середньої швидкості надходження нових заявок `λ` (заявок/секунду) на середній час перебування заявки в системі `W` (секунд):

```
L = λ · W
```

Якщо один воркер здатний обробити одну задачу за середній час `t_task` (тобто його індивідуальна продуктивність становить `μ = 1 / t_task` задач/секунду), то для запобігання нескінченному зростанню черги сумарна продуктивність пулу `N · μ` повинна строго перевищувати швидкість вхідного потоку `λ`:

```
N_min > λ · t_task
```

Проте в реальних системах завдання не просто надходять рівномірним потоком, а накопичуються пачками (backlog `L_current`). Якщо бізнес-вимога (SLA) встановлює жорсткий дедлайн на повне спорожнення наявної черги за час `T_deadline` з урахуванням того, що протягом цього часу продовжуватимуть надходити нові повідомлення зі швидкістю `λ`, повна формула розрахунку кількості воркерів набуває вигляду:

```
Загальна робота = L_current + λ · T_deadline
Продуктивність одного воркера за час дедлайну = T_deadline / t_task
N_desired = ceil[ (L_current + λ · T_deadline) · t_task / T_deadline ]
          = ceil[ (L_current · t_task / T_deadline) + λ · t_task ]
```

Перший доданок відповідає за ліквідацію накопиченого відставання (draining the backlog), а другий — за паралельне обслуговування поточного вхідного трафіку (keeping up with real-time arrivals).

**Вплив «важких хвостів» розподілу (Heavy-tailed workloads):** якщо час обробки задачі `t_task` має велику дисперсію (наприклад, 90% задач виконуються за 10 мс, але 10% важких завдань вимагають 30 секунд), просте середнє арифметичне фатально занижує потребу в ресурсах. Декілька важких задач, що потрапили до одного воркера, блокують його потік (Head-of-Line blocking). У таких умовах контролер зобов'язаний використовувати для розрахунку 95-й або 99-й перцентиль часу виконання `t_p95` та коефіцієнт запасу (safety factor `k_tail ≈ 1.25..1.50`):

```
N_safe = ceil[ N_desired · k_tail ]
```

### 8. Запобігання каскадному колапсу залежностей (Thundering Herd on Downstream)

Найнебезпечнішим побічним ефектом некоординованого масштабування є «ефект доміно» на спільні бази даних або кеш-кластери:

1. **Сплеск трафіку на фронтенді:** веб-сервіс відчуває наплив користувачів і контролер автоскейлу швидко збільшує кількість реплік з 10 до 120.
2. **Множення пулів з'єднань:** якщо кожен екземпляр застосунку сконфігуровано з пулом у 30 TCP-з'єднань до PostgreSQL, сумарна кількість активних з'єднань до єдиного Primary-сервера бази даних миттєво зростає з 300 до 3 600.
3. **Деградація бази:** база даних витрачає весь процесорний час на перемикання контексту між 3 600 потоками ядра, синхронізацію блокувань (lock contention) та керування пам'яттю з'єднань. Час виконання найпростішого SQL-запиту зростає з 2 мс до 1 500 мс.
4. **Хибний позитивний зворотний зв'язок:** веб-сервери, очікуючи повільних відповідей від бази даних, накопичують черги викликів. Їхнє власне використання процесора або кількість завислих in-flight з'єднань злітає до максимуму. Контролер автоскейлу веб-сервісу бачить високе навантаження і намагається додати **ще більше** реплік веб-серверів (аж до `max_replicas = 300`).
5. **Повна загибель системи:** додаткові 180 реплік надсилають ще кілька тисяч з'єднань до бази даних, викликаючи вичерпання дескрипторів сокетів (`max_connections limit reached`), аварійне падіння PostgreSQL і повний параліч усіх сервісів компанії.

Щоб розірвати це замкнене порочне коло, контролер автоскейлу повинен обов'язково інтегруватися з архітектурними запобіжниками:
- **Жорсткий глобальний ліміт `max_replicas`:** розрахований на основі максимальної пропускної здатності найвужчого місця в ланцюжку (downstream bottleneck).
- **Спільні пулери з'єднань (Connection Poolers):** використання проміжних сервісів маршрутизації (PgBouncer, ProxySQL), які тримають фіксовану кількість з'єднань до ядра бази (наприклад, 100) і мультиплексують тисячі клієнтських підключень.
### 9. Отруйні повідомлення (Poison Pills) та Dead Letter Queue

Особливою загрозою для чергових автоскейлерів є «отруйні повідомлення» (Poison Pill): некоректно сформовані задачі або баги у бізнес-логіці, які викликають миттєвий краш воркера (SIGSEGV, OutOfMemoryError або неперехоплений виняток).

Коли воркер аварійно падає під час обробки повідомлення, брокер черги (RabbitMQ, SQS, NATS) повертає це повідомлення назад у початок черги (nack / requeue).
1. Інші воркери беруть це ж повідомлення й по черзі падають один за одним.
2. Пропускна здатність пулу падає до нуля, а загальна довжина черги продовжує рости.
3. Контролер автоскейлу, бачачи зростання черги, панічно замовляє нові репліки воркерів аж до `max_replicas`.
4. Кожен новий воркер запускається, хапає отруйне повідомлення і негайно гине (CrashLoopBackOff), марнуючи ресурси кластера.

Щоб запобігти цьому сценарію, брокери конфігурують з обмеженням кількості спроб доставки (max delivery attempts = 3–5) та автоматичним скиданням збійних повідомлень у чергу недоставлених повідомлень (Dead Letter Queue, DLQ). Контролер автоскейлу повинен зчитувати метрику довжини **виключно з основної черги**, ігноруючи DLQ, а на рівні моніторингу налаштовується окремий критичний алерт на будь-яку появу повідомлень у DLQ для негайного втручання інженерів.
