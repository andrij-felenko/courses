# 🧮 Математика вікон, швидкості випалювання і гістерезису

Алертинг на основі цілей рівня обслуговування (SLO) спирається на строгий розрахунок витрачання бюджету помилок. Якщо поріг спрацьовування обрано інтуїтивно («помилок більше ніж 2%»), система або запізнюється з виявленням повної відмови, або надсилає десятки марних повідомлень на тимчасових сплесках. Математичний апарат швидкості випалювання (Burn Rate) та багатовіконного аналізу дає змогу точно узгодити час реакції пейджера з допустимими бізнес-втратами.

## 1. Ймовірнісна модель потоку запитів та бюджет помилок

Розглянемо потік запитів до сервісу як дискретний випадковий процес. Нехай у момент часу `t` надходить `N(t)` запитів, з яких `E(t)` запитів завершуються помилкою. Кожен запит є випадковою подією Бернуллі, де ймовірність успішної обробки позначається як `p(t) = 1 - e(t)`, де `e(t) ∈ [0, 1]` — миттєва частка помилок (Error Rate).

Нехай для сервісу визначено ціль надійності `SLO ∈ (0, 1)` на ковзному розрахунковому періоді часу `T₀` (зазвичай стандартний місячний інтервал `T₀ = 30` днів = `720` годин = `43 200` хвилин = `2 592 000` секунд).

**Бюджет помилок (Error Budget `B`):**
```
B = 1 - SLO      [визначення бюджету як частки допустимих збоїв]
```

Для сервісу з `SLO = 99.9%` (`0.999`):
```
B = 1 - 0.999    [підстановка цільового значення SLO]
= 0.001          [обчислення допустимої частки помилок 0.1%]
```

Якщо сервіс отримує загальну кількість запитів `N_total` за період `T₀`, то максимальна допустима абсолютна кількість невдалих запитів `E_max` становить:
```
E_max = B · N_total    [добуток бюджету помилок на загальний обсяг запитів]
```

У неперервному часі кумулятивне випалювання бюджету помилок `C(t)` від початку періоду визначається інтегралом:
```
C(t) = ∫₀ᵗ e(τ) · r(τ) dτ    [інтеграл від добутку частки помилок на інтенсивність потоку запитів r(t)]
```

Якщо інтенсивність потоку запитів вважати квазістаціонарною (`r(t) ≈ r_avg`), то частка вичерпаного бюджету `BudgetConsumed(t) ∈ [0, 1]` дорівнює:
```
BudgetConsumed(t) = (1 / (B · T₀)) · ∫₀ᵗ e(τ) dτ    [нормована частка згорілого бюджету]
```

## 2. Швидкість випалювання (Burn Rate)

**Швидкість випалювання (`BR`)** — це безрозмірна величина, що показує, у скільки разів поточний темп витрачання бюджету перевищує розрахунковий базовий темп:

```
BR(t) = e(t) / B = e(t) / (1 - SLO)      [відношення поточної частки помилок до бюджету]
```

Фізичний зміст параметра `BR`:
- Якщо `BR = 1`, сервіс витрачає рівно `100%` свого бюджету помилок за весь розрахунковий період `T₀` (30 днів). Підсумкова надійність у кінці місяця точно дорівнюватиме узгодженому `SLO`.
- Якщо `BR = 0`, помилок немає, бюджет залишається недоторканим.
- Якщо `BR = 2`, бюджет вичерпується вдвічі швидше (за 15 днів).
- Якщо `BR > 1`, система прямує до порушення зобов'язань SLO до завершення звітного місяця.

Час повного вичерпання бюджету `T_exhaust` за умови незмінної швидкості `BR` обчислюється як:

```
T_exhaust = T₀ / BR      [загальний час періоду, поділений на кратність витрачання]
```

**Розрахунок часу вичерпання для місячного вікна `T₀ = 30` днів (720 годин):**
- При `BR = 1`: `T_exhaust = 720 / 1 = 720` годин (`30` днів).
- При `BR = 2`: `T_exhaust = 720 / 2 = 360` годин (`15` днів).
- При `BR = 6`: `T_exhaust = 720 / 6 = 120` годин (`5` днів).
- При `BR = 14.4`: `T_exhaust = 720 / 14.4 = 50` годин (`2.083` дня).
- При `BR = 1000` (повний блекаут, 100% помилок при SLO 99.9%): `T_exhaust = 720 / 1000 = 0.72` години (`43.2` хвилини).

## 3. Частка випаленого бюджету та час виявлення інциденту

Припустимо, ми проєктуємо систему алертингу і хочемо викликати інженера на пейджер щоразу, коли гостра аварія спалює частку `f ∈ (0, 1)` від загального місячного бюджету (наприклад, `f = 0.02`, тобто `2%` бюджету).

Зв'язок між часткою згорілого бюджету `f`, швидкістю випалювання `BR` та тривалістю інциденту `t_detect` виражається формулою:

```
f = t_detect / T_exhaust           [частка згорілого бюджету за час виявлення]
= (t_detect · BR) / T₀             [підстановка T_exhaust = T₀ / BR]
```

Звідси час до спрацьовування алерту:
```
t_detect = (f · T₀) / BR           [вираження часу виявлення через частку f та швидкість BR]
```

**Виведення для критичного алерту (випалювання 2% бюджету за 1 годину):**
Нехай `T₀ = 720` годин, `f = 0.02` (2%), `t_detect = 1` година. Знайдемо необхідний поріг `BR`:

```
BR = (f · T₀) / t_detect           [базова формула зв'язку швидкості з часом виявлення]
= (0.02 · 720) / 1                 [підстановка f = 0.02, T₀ = 720 год, t_detect = 1 год]
= 14.4                             [обчислення кратності випалювання бюджету]
```

Тобто при швидкості `BR = 14.4` рівно `2%` місячного бюджету помилок згорає за `1` годину безперервного збою. Якщо аварія триватиме 50 годин, бюджет спорожніє повністю (`100%`).

**Виведення для критичного алерту 2-го рівня (випалювання 5% бюджету за 6 годин):**
Нехай `T₀ = 720` годин, `f = 0.05` (5%), `t_detect = 6` годин.

```
BR = (0.05 · 720) / 6              [підстановка f = 0.05, T₀ = 720 год, t_detect = 6 год]
= 36 / 6                           [спрощення чисельника]
= 6.0                              [обчислення кратності випалювання]
```

## 4. Чому одновіконний алертинг зазнає статистичного фіаско

Розглянемо наївне правило алертингу з єдиним ковзним вікном усереднення тривалістю `W`:

```promql
rate(http_requests_failed[W]) / rate(http_requests_total[W]) > BR · (1 - SLO)
```

Математичний аналіз виявляє нерозв'язний компроміс між шириною вікна `W` та якістю сигналу:

### Проблема А: Занадто мале вікно (наприклад, W = 10 хвилин)
- **Низька статистична чутливість (High False Negative):** Для виявлення повільного випалювання `BR = 2` при `SLO = 99.9%` частка помилок становить `e = 0.2%`. Якщо сервіс отримує 50 запитів на хвилину, за 10 хвилин надійде 500 запитів, з яких у середньому лише 1 буде збійним. Стохастичні коливання призводять до того, що алерт постійно гасне і загоряється, не даючи стабільного спрацьовування.
- **Хибні тривоги на сплесках (High False Positive):** Якщо вночі трафік падає до 10 запитів за 10 хвилин, випадковий збій 2 запитів (наприклад, сканування ботом) дає частку помилок `20%` (`BR = 200`), викликаючи нічну тривогу на пейджер без реального впливу на бізнес.

### Проблема B: Занадто велике вікно та затримка скидання (Reset Lag)
Нехай обрано велике вікно `W = 36` годин для надійного виявлення тривалого повільного витоку.
Припустимо, сталася масштабна аварія тривалістю `D = 1` година з часткою помилок `E = 10%`, після чого о 12:00 інженери повністю відновили сервіс (`e(t) = 0`).

Ковзне середнє значення частки помилок `e_avg(t)` для моменту часу `t > 12:00` становить:
```
e_avg(t) = (E · D) / W             [усереднення спалених помилок за повне вікно W]
= (0.10 · 1) / 36                  [підстановка значень аварії]
= 0.00277                          [середня частка помилок 0.277%]
```

Оскільки `0.277% > 0.1%` (бюджет перевищено), алерт залишатиметься в стані `Firing` протягом:
```
t_reset = W - D                    [час вимивання аварійного вікна]
= 36 - 1                           [підстановка значень]
= 35 годин                         [тривалість хибного горіння алерту після ремонту]
```

Інженери змушені будуть терпіти активне сповіщення про аварію ще півтори доби після її повного подолання.

## 5. Багатовіконна мульти-Burn-Rate стратегія Google SRE

Щоб одночасно отримати високу швидкість виявлення та миттєве скидання після ремонту, застосовують комбінацію **двох вікон одночасно**:
1. **Довге вікно (`W_long`):** контролює факт накопичення достатнього обсягу спаленого бюджету `f`.
2. **Коротке вікно (`W_short`):** підтверджує, що інцидент активний просто зараз.

За стандартом SRE тривалість короткого вікна обирається у співвідношенні `1/12`:
```
W_short = W_long / 12              [канонічне співвідношення вікон]
```

Логічний предикат алерту вимагає одночасного виконання обох умов:
```
AlertCondition = (BR(W_long) > Порог) ∧ (BR(W_short) > Порог)
```

### Динаміка роботи подвійного вікна:
1. **Фаза початку:** Коли починається збій, `BR(W_short)` перевищує поріг за лічені хвилини. Коли накопичується достатня тривалість, `BR(W_long)` також перетинає поріг — алерт активується (`Firing`).
2. **Фаза зняття:** Щойно систему полагоджено, частка помилок падає до нуля. Коротке вікно `W_short` очищується рівно за `W_short` хвилин (наприклад, за 5 хвилин для 1-годинного довгого вікна). Предикат `AND` стає хибним, і алерт негайно переходить у стан `Resolved`, не чекаючи спорожнення 1-годинного довгого вікна.

### Повна 4-рівнева матриця випалювання бюджету

| Рівень | Ціль сповіщення | Бюджет `f` | Довге вікно `W_long` | Коротке вікно `W_short` | Порог `BR` | Час повного краху `T_exhaust` |
|---|---|---|---|---|---|---|
| **P1.1** | Пейджер (терміново) | `2%` | `1 година` | `5 хвилин` | `14.4` | `2 дні` (`50 год`) |
| **P1.2** | Пейджер (терміново) | `5%` | `6 годин` | `30 хвилин` | `6.0` | `5 днів` (`120 год`) |
| **P2.1** | Тікет (робочий день) | `10%` | `24 години` | `2 години` | `3.0` | `10 днів` (`240 год`) |
| **P2.2** | Тікет (плановий спринт) | `10%` | `3 дні` (`72 год`) | `6 годин` | `1.0` | `30 днів` (`720 год`) |

## 6. Математична модель гістерезису та придушення брязкання

Розглянемо часовий ряд метрики як процес Орнштейна-Уленбека або випадкове блукання зі стохастичним шумом:
```
x(t) = μ(t) + ξ(t),    де ξ(t) ~ N(0, σ²)
```

Якщо система використовує єдиний поріг `T`, то поблизу точки `μ(t) ≈ T` частота випадкових перетинів порогу (частота брязкання `f_flap`) визначається формулою Райса для середньої кількості перетинів нуля випадковим процесом:
```
f_flap = (1 / (2·π)) · (σ_v / σ) · exp( - (T - μ)² / (2·σ²) )
```
де `σ_v` — дисперсія швидкості зміни сигналу `dx/dt`.

При `μ ≈ T` експонента дорівнює 1, і система генерує максимальну кількість хибних перемикань.

### Модель тригера Шмітта з роздільними порогами:
Вводиться два пороги: поріг активації `T_fire` та поріг деактивації `T_clear` (`T_fire > T_clear`).
Ширина зони гістерезису:
```
ΔT = T_fire - T_clear              [ширина захисного буфера гістерезису]
```

Ймовірність того, що випадковий шум `ξ(t)` амплітудою `ΔT` викличе зворотне хибне перемикання стану, обмежується нерівністю Чебишова та інтегралом хвоста нормального розподілу:

```
P(хибне перемикання) = 1 - Φ( ΔT / (2·σ) )
```

Асимптотична оцінка частоти брязкання за наявності гістерезису `ΔT`:
```
f_flap(ΔT) ≈ f₀ · exp( - (ΔT)² / (8·σ²) )    [експоненційне затухання частоти брязкання]
```

**Числовий висновок:**
Встановлення ширини зони гістерезису `ΔT = 3·σ` (де `σ` — середньоквадратичне відхилення шуму метрики) зменшує частоту хибного брязкання на **99.73%**, повністю усуваючи спам у каналах чергових інженерів.

## 7. Бюджетування комбінованих збоїв (Multi-Tier Budget Allocation)

При одночасному налаштуванні кількох рівнів сповіщень загальна частка захищеного бюджету повинна задовольняти умові несумісності хибних спрацьовувань:
```
Σ f_i ≤ B_total                    [сума квот на рівні сповіщень не перевищує загальний бюджет]
```

Якщо короткі вікна (`P1.1` та `P1.2`) споживають сумарно `2% + 5% = 7%` бюджету до моменту виклику інженера, інженерна команда гарантовано зберігає понад `93%` бюджету надійності для локалізації та ліквідації аварії до того, як буде порушено зовнішній договір SLA.
