# 🧮 Математичні моделі RPO, RTO та вартості відновлення

Спроба зменшити точку відновлення (RPO) та час повернення сервісу (RTO) до нуля наївним дублюванням усіх компонентів призводить до експоненційного зростання витрат на інфраструктуру, яке швидко перевищує річний прибуток підприємства. З іншого боку, надмірна економія та використання рідкісних холодних бекапів загрожує компанії банкрутством у разі першої масштабної пожежі чи кібератаки. Математичний апарат теорії надійності дозволяє формалізувати зв'язок між затримкою реплікації журналів WAL, інтенсивністю транзакційного потоку та фінансовими втратами, знаходячи точну точку економічного оптимуму сукупної вартості володіння (TCO).

## Модель втрати даних за динамічної інтенсивності транзакцій

У реальних системах потік вхідних мутацій не є константним: він коливається протягом доби відповідно до користувацької активності.

Нехай:
- `λ(t)` — миттєва щільність вхідного потоку транзакцій (транзакцій/секунду);
- `L(t)` — поточний реплікаційний лаг передачі журналу WAL до віддаленого DR-сховища в момент часу `t` (секунд);
- `t_crash` — точний фізичний момент виникнення катастрофи на основному майданчику.

Тоді фактичний обсяг безповоротно втрачених транзакцій `Δ_loss` дорівнює інтегралу щільності потоку за інтервал реплікаційного відставання:

```
Δ_loss = ∫_{t_crash - L(t_crash)}^{t_crash} λ(τ) dτ   [сумарна кількість втрачених операцій]
```

Якщо швидкість надходження транзакцій наближено вважати локально постійною `λ(t) ≈ λ_avg` на короткому проміжку часу лагу, формула спрощується до прямого добутку:

```
Δ_loss = λ_avg · L(t_crash)   [лінійна оцінка втрат транзакцій]
```

### Гарантія обмеження втрат через RPO

Щоб система гарантовано задовольняла задекларований норматив `RPO_target`, максимальний часовий лаг реплікації зобов'язаний задовольняти строгу нерівність у будь-який момент часу:

```
max_{t} L(t) ≤ RPO_target   [інваріант дотримання RPO]
```

Якщо розмір буфера передачі журналу дорівнює `B(t)` байтів, а пропускна здатність міжрегіонального мережевого каналу становить `C` байтів/сек, лаг виражається через відношення обсягу накопичених даних до швидкості передачі:

```
L(t) = B(t) / C   [часова затримка передачі несинхронізованого журналу]
```

Звідси випливає мінімально необхідна ширина мережевого каналу для забезпечення заданого RPO за пікової швидкості генерації журналу `W_peak` (байтів/сек):

```
C_min = W_peak   [умова відсутності нескінченного накопичення черги WAL]
```

## Теорія черг у передачі журналу транзакцій (Queuing Theory & M/M/1 Buffer)

Передачу сегментів журналу WAL від основного сервера до віддаленого сховища можна промоделювати як систему масового обслуговування типу `M/M/1/K`, де:
- Вхідний потік згенерованих байтів надходить з інтенсивністю `λ_bytes` (байтів/сек);
- Мережевий канал обслуговує потік зі швидкістю `μ_bytes = C` (байтів/сек);
- Коефіцієнт завантаження каналу становить `ρ = λ_bytes / μ_bytes`;
- `K` — максимальний розмір локального дискового буфера для тимчасового зберігання сегментів WAL.

За формулою Літтла середній час очікування сегмента в буфері перед відправкою дорівнює:

```
W_queue = ρ / ( μ_bytes · (1 - ρ) )   [середній час перебування в черзі WAL]
```

Якщо мережевий трафік наближається до насичення (`ρ → 1`), час очікування в черзі зростає гіперболічно, що призводить до миттєвого зриву задекларованого ліміту RPO.

Ймовірність переповнення локального буфера розміром `K` сегментів (після чого основна СКБД буде змушена заблокувати нові транзакції або перервати відправку) виражається формулою Ерланга:

```
P_overflow = ( (1 - ρ) · ρ^K ) / ( 1 - ρ^{K+1} )   [ймовірність втрати буфера при перевантаженні]
```

Для запобігання переповненню інженери встановлюють строгий ліміт завантаження міжрегіональних лінків: `ρ ≤ 0.70`, залишаючи 30% запасу пропускної здатності на випадок пікових сплесків навантаження.

## Нелінійна модель вартості простою (Downtime Cost Function)

Збитки організації від простою сервісу не є строго лінійними. Короткочасний збій на дві хвилини зазвичай викликає лише легке невдоволення користувачів і повторні запити, тоді як простій тривалістю в кілька годин спричиняє масовий відтік клієнтів, штрафи за порушення регуляторних угод SLA, витрати на юридичний супровід та руйнування ринкової капіталізації.

Функція фінансових втрат від тривалості простою `t_down` моделюється шматочно-степеневою функцією:

```
C_down(t_down) = c_linear · t_down + c_quad · (t_down)² + C_penalty · θ(t_down - T_SLA)
```

де:
- `c_linear` — прямі операційні втрати за одиницю часу (втрачена виручка від покупок, простий працівників);
- `c_quad` — коефіцієнт репутаційних втрат та відтоку користувачів (зростає квадратично від часу);
- `C_penalty` — одноразовий фіксований штраф за порушення юридичного контракту SLA;
- `T_SLA` — гарантований поріг безперервної доступності;
- `θ(x)` — функція Гевісайда: `θ(x) = 1` при `x ≥ 0` та `θ(x) = 0` при `x < 0`.

## Оптимізація сукупних витрат: вибір точки рівноваги

Зі зменшенням цільових показників `RPO` та `RTO` вартість підтримки інфраструктури зростає експоненційно: досягнення нульового RTO (Active-Active) вимагає подвоєння серверного парку, оплати виділених оптичних каналів Dark Fiber та складного інженерного супроводу.

Нехай:
- `C_infra(RPO, RTO)` — річна вартість утримання резервної інфраструктури;
- `f_disaster` — річна статистична ймовірність виникнення масштабної катастрофи (частота подій за моделлю розподілу Пуассона);
- `C_loss(RPO)` — прямі збитки від втрати даних обсягом RPO: `C_loss = v_data · Δ_loss(RPO)`, де `v_data` — середня бізнес-вартість однієї транзакції.

Сукупна очікувана річна вартість ризику (англ. *Expected Total Cost of Ownership*, TCO) формулюється як сума витрат на інфраструктуру та математичного сподівання збитків від катастрофи:

```
E[TCO] = C_infra(RPO, RTO) + f_disaster · ( C_loss(RPO) + C_down(RTO + WRT) )
```

Апроксимація вартості інфраструктури від цільових показників описується гіперболічною залежністю:

```
C_infra(RPO, RTO) = k_base + k_rpo / (RPO + ε_rpo) + k_rto / (RTO + ε_rto)
```

де `k_base`, `k_rpo`, `k_rto` — емпіричні коефіцієнти вартості обладнання, а `ε` — технологічні константи мінімальних фізичних затримок передачі світла у мережі.

### Знаходження оптимальних параметрів RPO* та RTO*

Оптимальна інженерна стратегія відповідає точці глобального мінімуму цільової функції `E[TCO]`. Для знаходження мінімуму диференціюємо функцію за RPO та RTO і прирівнюємо частинні похідні до нуля:

```
∂E[TCO] / ∂RPO = 0   [умова мінімуму за параметром RPO]
```

```
- k_rpo / (RPO + ε_rpo)² + f_disaster · v_data · λ_avg = 0   [рівновага граничних витрат і граничного ризику]
```

Розв'язуємо відносно `RPO*`:

```
k_rpo / (RPO + ε_rpo)² = f_disaster · v_data · λ_avg   [перенесення доданка]
```

```
(RPO + ε_rpo)² = k_rpo / (f_disaster · v_data · λ_avg)   [ділення на константу збитків]
```

```
RPO* = √( k_rpo / (f_disaster · v_data · λ_avg) ) - ε_rpo   [аналітичний оптимум точки відновлення]
```

Аналогічно для часу відновлення `RTO*` за умови лінійної складової збитків `c_linear`:

```
∂E[TCO] / ∂RTO = 0   [умова мінімуму за параметром RTO]
```

```
- k_rto / (RTO + ε_rto)² + f_disaster · c_linear = 0   [диференціювання за RTO]
```

```
RTO* = √( k_rto / (f_disaster · c_linear) ) - ε_rto   [аналітичний оптимум часу відновлення]
```

Ці формули доводять строгий економічний закон:
1. Чим вища ймовірність катастрофи `f_disaster` або вартість транзакції `v_data`, тим меншими зобов'язані бути `RPO*` та `RTO*`, виправдовуючи дорогі стратегії Warm Standby та Active-Active.
2. Для рідкісних катастроф на дешевих даних оптимум зміщується в зону великих RPO/RTO, роблячи економічно доцільною холодну стратегію Backup and Restore.

## Практичний розрахунок: приклад платіжного шлюзу

Для закріплення математичної інтуїції розглянемо практичний розрахунок для платіжного шлюзу зі статистичними параметрами:
- Інтенсивність транзакцій: `λ = 400` операцій/сек;
- Середня комісійна маржа з однієї операції: `v_data = 3.50` грн;
- Прямі збитки простою: `c_linear = 1400` грн/сек (близько 5 млн грн за годину);
- Ймовірність масштабної відмови ЦОД: `f_disaster = 0.05` на рік (1 аварія на 20 років);
- Коефіцієнти інфраструктури: `k_rto = 50000000`, `ε_rto = 10` сек.

Розрахуємо оптимальний час відновлення `RTO*`:

```
RTO* = √( 50000000 / (0.05 · 1400) ) - 10
     = √( 50000000 / 70 ) - 10
     = √( 714285 ) - 10
     = 845 - 10
     = 835 секунд (близько 14 хвилин)
```

Цей числовий результат однозначно показує, що для заданого профілю бізнесу стратегія холодного відновлення з RTO у 12 годин призведе до колосальних збитків, які у десятки разів перевищують вартість утримання резервного майданчика. Оптимальним вибором для компанії є архітектура **Warm Standby** із часом відновлення 10–15 хвилин.

## Модель корельованих відмов та копули ризику (Correlated Outages)

Класична теорія надійності припускає, що ймовірність одночасної відмови двох незалежних дата-центрів А і Б є добутком їхніх окремих ймовірностей:

```
P(A ∩ B) = P(A) · P(B)   [гіпотеза незалежних збоїв]
```

Якщо кожен дата-центр має річну ймовірність відмови `P = 0.01` (99% надійності), то ймовірність одночасного падіння обох вважалася б рівною `0.0001` (один випадок на 10 000 років). Проте в реальному світі ця гіпотеза виявляється фатально помилковою через наявність спільних причин збоїв (англ. *Common Cause Failures*, CCF): спільні магістральні оператори зв'язку, загальнонаціональні блекаути електромережі, збої в оновленнях BGP-маршрутизаторів глобальних провайдерів або атаки вірусів-вимагачів.

Справжня ймовірність спільного збою моделюється за допомогою параметричного коефіцієнта кореляції `γ(d)`, що експоненційно спадає з географічною відстанню `d` між регіонами:

```
γ(d) = e^{- d / d_0}   [коефіцієнт просторової кореляції катастроф]
```

де `d_0 ≈ 150` км — характерний радіус географічного впливу масштабних природних та техногенних катаклізмів.

Умовна ймовірність відмови резервного регіону Б за умови загибелі основного регіону А дорівнює:

```
P(B | A) = P(B) + γ(d) · ( 1 - P(B) )   [коригування умовної ймовірності]
```

Якщо дата-центри розташовані в одному місті (`d = 10` км), коефіцієнт кореляції складає `γ(10) ≈ e^{-10/150} ≈ 0.935`. Умовна ймовірність падіння другого дата-центру злітає з 1% до `0.01 + 0.935 · 0.99 ≈ 93.6%`. 

Лише при рознесенні майданчиків на відстань `d > 1000` км коефіцієнт спадає до `γ(1000) ≈ e^{-6.66} ≈ 0.0013`, наближаючи поведінку системи до ідеально незалежного резервування.

## Модель споживання дискового простору при синтетичних бекапах

При регулярному резервному копіюванні зберігати щодня повні знімки розміром `S_full` неможливо через вичерпання дискового простору сховища. Натомість використовують ланцюжок із щотижневого повного знімка та щоденних інкрементів із дедуплікацією.

Нехай:
- `S_base` — розмір повного базового знімка;
- `r_daily` — добовий відсоток зміни даних у базі (англ. *Daily Churn Rate*), зазвичай `r_daily ∈ [0.02, 0.10]`;
- `δ_dedup` — коефіцієнт ефективності дедуплікації та стиснення однакових блоків, `δ_dedup ∈ [0.40, 0.85]`;
- `N_days` — період утримання резервних копій (англ. *Retention Window*).

Сумарний обсяг дискового сховища `V_total(N_days)` для ланцюжка з 1 повного знімка та `(N_days - 1)` щоденних інкрементів розраховується як:

```
V_total(N_days) = S_base + ∑_{k=1}^{N_days - 1} ( S_base · r_daily · (1 - δ_dedup) )
```

Оскільки щоденний приріст змін `ΔS = S_base · r_daily · (1 - δ_dedup)` є сталим, вираз згортається у лінійне рівняння:

```
V_total(N_days) = S_base · ( 1 + (N_days - 1) · r_daily · (1 - δ_dedup) )   [обсяг сховища для періоду утримання]
```

Ця формула дозволяє точно розрахувати необхідну ємність об'єктного сховища S3 для дотримання регуляторного періоду утримання (наприклад, 90 днів) без ризику раптового переповнення дискового масиву.

## Чутливість реплікаційного лагу до мережевих втрат (Mathis Formula)

При передачі журналу WAL через трансконтинентальні канали зв'язку пропускна здатність протоколу TCP різко деградує за наявності навіть незначного відсотка втрачених пакетів `p`. За формулою Матіса максимальна швидкість передачі `BW_tcp` обмежується параметрами:

```
BW_tcp ≤ ( MSS / RTT ) · ( C_mathis / √p )   [теоретична межа швидкості TCP]
```

де `MSS` — максимальний розмір сегмента (1460 байтів), `RTT` — час кругового обігу пакетів (наприклад, 80 мс між Європою та США), `p` — імовірність втрати пакета, а `C_mathis ≈ 1.22`.

Якщо на магістральному каналі виникає деградація з втратою пакетів `p = 0.01` (1%), пропускна здатність каналу 10 Гбіт/с може впасти до 15 Мбіт/с. Швидкість генерації журналу базою даних `W_write` перевищує швидкість передачі `BW_tcp`, через що реплікаційний лаг `L(t)` починає зростати лінійно з часом:

```
dL(t)/dt = ( W_write - BW_tcp ) / BW_tcp   [швидкість деградації RPO під час мережевого шторму]
```

Саме тому сучасні системи DR використовують паралельні TCP-потоки або протоколи на базі UDP (QUIC / BBR congestion control), які запобігають колапсу реплікації під час трансконтинентальних коливань якості зв'язку.
