# 📋 Специфікації конфігурації аварійного відновлення та політик незмінності

Коли аварія виводить з ладу основний виробничий контур, чергові інженери не мають часу з'ясовувати формат параметрів архівації WAL чи погоджувати рівні оренди кворуму в ручному режимі: будь-яка затримка безпосередньо збільшує RTO. Ця специфікація визначає обов'язковий декларативний контракт між компонентами системи аварійного відновлення — від конфігураційних прапорців бази даних і політик незмінності об'єктного сховища S3 до точних станів кінцевого автомата автоматичного перемикання трафіку.

## Декларативна схема маніфесту плану аварійного відновлення

Нижче наведено формальну специфікацію YAML, яка описує топологію міжрегіонального резервування, цільові метрики SLA та правила ізоляції вузлів для контролера автоматичного відновлення.

```yaml
apiVersion: disaster-recovery.infrastructure.io/v1alpha1
kind: DisasterRecoveryPlan
metadata:
  name: core-banking-dr-plan
  namespace: operations
spec:
  # ── 1. Цільові метрики та бізнес-обмеження ────────────────────────────────
  sla:
    targetRpoSeconds: 5               # Максимально допустима втрата даних
    targetRtoSeconds: 300             # Максимальний час підйому DR (5 хвилин)
    maxTolerableDowntimeSeconds: 1800 # Граничний ліміт руйнування бізнесу (30 хв)
    tier: Tier1Critical               # Рівень критичності сервісу

  # ── 2. Географічна топологія та ролі регіонів ────────────────────────────
  topology:
    primaryRegion:
      provider: aws
      region: eu-central-1           # Франкфурт (Основний робочий регіон)
      datacenterId: sbg-dc-01
      vpcCidr: "10.100.0.0/16"
    secondaryRegion:
      provider: aws
      region: eu-west-1              # Дублін (DR-регіон, відстань > 1000 км)
      strategy: WarmStandby          # BackupRestore | PilotLight | WarmStandby | ActiveActive
      minCapacityPercent: 25         # Постійний розмір теплого пулу
      targetCapacityPercent: 100     # Автоскейл до 100% при аварії
      vpcCidr: "10.200.0.0/16"
    quorumWitness:
      provider: aws
      region: eu-north-1             # Стокгольм (Третій незалежний арбітр)
      heartbeatIntervalMs: 500
      leaseTtlSeconds: 5

  # ── 3. Політики виявлення збоїв та арбітражу ─────────────────────────────
  detection:
    healthCheckProbes:
      - path: "/healthz/deep-db"
        port: 443
        intervalSeconds: 2
        consecutiveFailures: 3
        timeoutSeconds: 1
    unreachableThresholdSeconds: 10
    autoFailoverEnabled: false        # Вимагати затвердження чергового інженера

  # ── 4. Механізми ізоляції старої ноди (Fencing / STONITH) ────────────────
  fencing:
    mechanism: CloudIamRevokeAndStonith
    stonith:
      pduEndpoints:
        - "pdu-a1.frankfurt.internal"
        - "pdu-a2.frankfurt.internal"
      command: "power_off"
    cloudIam:
      detachRolePolicyArn: "arn:aws:iam::123456789012:policy/DbWriteAccess"
      revokeSecurityGroupIngress: true
```

### Опис полів маніфесту DisasterRecoveryPlan

1. `spec.sla.targetRpoSeconds`: Максимально допустиме відставання журналу транзакцій. Визначає частоту виклику примусового скидання WAL та алертинг при зростанні черги передачі.
2. `spec.sla.targetRtoSeconds`: Граничний ліміт часу на повний цикл перемикання трафіку на вторинний майданчик.
3. `spec.sla.tier`: Класифікатор критичності бізнес-домену. Сервіси класу `Tier1Critical` вимагають постійної наявності репліки Pilot Light або Warm Standby, тоді як другорядні сервіси (`Tier3NonCritical`) можуть задовольнятися стратегією холодного розгортання з бекапу.
4. `spec.topology.secondaryRegion.strategy`: Архітектурна модель DR-сайту (`BackupRestore`, `PilotLight`, `WarmStandby` або `ActiveActive`). Визначає, чи утримуються постійно запущені контейнери у резервному регіоні.
5. `spec.topology.quorumWitness.leaseTtlSeconds`: Час життя оренди лідера. Якщо лідер не подовжив оренду за цей інтервал, він зобов'язаний автоматично перейти в режим `Read-Only`.
6. `spec.fencing.mechanism`: Спосіб гарантованої ізоляції мертвого або відрізаного мережевим розривом вузла для унеможливлення Split-Brain.

## Системні параметри ядра Linux для трансконтинентальної реплікації

При передачі великих потоків WAL через канали з великою затримкою (RTT > 50 мс) стандартні налаштування мережевого стека Linux обмежують швидкість з'єднання. На серверах реплікації встановлюються такі параметри ядра у файлі `/etc/sysctl.d/99-dr-network.conf`:

| Параметр ядра | Значення за замовчуванням | Оптимізоване для DR | Пояснення інженерного ефекту |
| :--- | :--- | :--- | :--- |
| `net.ipv4.tcp_congestion_control` | `cubic` | `bbr` | Алгоритм BBR від Google максимізує пропускну здатність на каналах із затримками, не плутаючи випадкові втрати пакетів із перевантаженням мережі. |
| `net.core.rmem_max` | 212992 (208 КБ) | 67108864 (64 МБ) | Максимальний розмір буфера прийому TCP-сокетів. Необхідний для покриття добутку пропускної здатності на затримку (BDP). |
| `net.core.wmem_max` | 212992 (208 КБ) | 67108864 (64 МБ) | Максимальний розмір буфера відправки TCP-сокетів для усунення блокування запису при відправці сегментів WAL. |
| `net.ipv4.tcp_rmem` | 4096 87380 6291456 | 4096 87380 67108864 | Автоматичне динамічне масштабування буфера читання TCP. |
| `net.ipv4.tcp_wmem` | 4096 65536 6291456 | 4096 65536 67108864 | Автоматичне динамічне масштабування буфера запису TCP. |
| `vm.dirty_ratio` | 20 (%) | 10 (%) | Примушує ядро частіше скидати брудні сторінки на диск, усуваючи гігабайтні сплески I/O блокування при генерації знімків. |

## Конфігураційні контракти бази даних PostgreSQL (WAL & PITR)

Для забезпечення можливості відновлення до точки в часі (PITR) серверне ядро СКБД конфігурується такими параметрами в `postgresql.conf`:

| Параметр | Рекомендоване значення | Призначення в контурі DR |
| :--- | :--- | :--- |
| `wal_level` | `replica` або `logical` | Визначає обсяг метаданих, що записуються у WAL (необхідний рівень `replica` для відновлення). |
| `archive_mode` | `on` | Дозволяє фоновому процесу `archiver` відправляти заповнені сегменти у сховище. |
| `archive_command` | `test ! -f /mnt/s3_wal/%f && cp %p /mnt/s3_wal/%f` | Атомарна команда передачі сегмента розміром 16 МБ у незмінне віддалене сховище. |
| `archive_timeout` | `60s` | Примусова ротація сегмента WAL раз на 60 секунд навіть при низькому навантаженні (обмежує RPO). |
| `restore_command` | `cp /mnt/s3_wal/%f %p` | Команда завантаження архівного сегмента під час відновлення в режимі Standby/REDO. |
| `recovery_target_time` | `'2026-08-20 14:27:03.999 UTC'` | Точна часова мітка зупинки відтворення змін. |
| `recovery_target_action` | `promote` | Дія після досягнення цільової мітки: підвищити інстанс до повноцінного лідера. |
| `recovery_target_inclusive` | `false` | Виключити саму транзакцію, яка збігається з цільовим часом (пропуск аварійної команди). |

### Деталі взаємодії параметрів архівування

- **`archive_timeout = 60s`:** Якщо на сервері немає активних записів, стандартний 16-мегабайтний файл WAL може заповнюватися годинами. У разі раптової аварії транзакції всередині незаповненого сегмента будуть втрачені. Параметр `archive_timeout` примусово закриває і відправляє поточний сегмент у сховище раз на хвилину, гарантуючи виконання нормативу `RPO ≤ 60s`.
- **`recovery_target_inclusive = false`:** Коли інженер виявляє точний час аварійного запису `DROP TABLE` за журналом аудиту (наприклад, `14:27:04.120`), встановлення `inclusive = false` разом із цільовим часом `14:27:04.120` гарантує, що рушій застосує всі транзакції строго ДО цієї мітки, а саму операцію `DROP` відхилить.

## Політика незмінності об'єктного сховища AWS S3 (Object Lock JSON)

Нижче наведено декларативну політику відра S3 для забезпечення регуляторного стандарту незмінності WORM у режимі Compliance Mode.

```json
{
  "ObjectLockConfiguration": {
    "ObjectLockEnabled": "Enabled",
    "Rule": {
      "DefaultRetention": {
        "Mode": "COMPLIANCE",
        "Days": 90
      }
    }
  }
}
```

Політика доступу (Bucket Policy), яка забороняє видалення навіть обліковому запису адміністратора:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyBucketDeletionAndUnsafeAccess",
      "Effect": "Deny",
      "Principal": "*",
      "Action": [
        "s3:DeleteBucket",
        "s3:DeleteBucketPolicy",
        "s3:PutObjectLockConfiguration"
      ],
      "Resource": "arn:aws:s3:::production-immutable-backups-wal"
    }
  ]
}
```

### Порівняння режимів Object Lock: Governance проти Compliance

1. **Governance Mode (Режим внутрішнього контролю):**
   - Захищає файли бекапів від випадкового видалення більшістю користувачів та сервісних акаунтів.
   - Спеціальний користувач із привілеєм `s3:BypassGovernanceRetention` має право примусово видалити заблокований об'єкт або скоротити термін утримання.
   - Використовується для проміжних тестових бекапів, які можуть бути знищені інженерами вручну за потреби оптимізації витрат.
2. **Compliance Mode (Режим суворої відповідності регуляторам):**
   - Блокує операцію видалення та перезапису на абсолютному апаратно-програмному рівні.
   - Жоден обліковий запис у світі, включаючи root-акаунт компанії, компрометованого адміністратора домену чи генерального директора, **не має технічної можливості зняти блокування** до настання дати закінчення терміну.
   - Обов'язковий стандарт для збереження фінансових реєстрів, транзакційних логів WAL та річних аудит-дампів згідно з вимогами SEC Rule 17a-4, FINRA та GDPR.

## Скінченний автомат процедури аварійного перемикання (Failover State Machine)

Процес перемикання трафіку керується строгим детермінованим автоматом станів, де кожен перехід вимагає валідації попереднього інваріанта.

```
[1. NOMINAL] 
      │ (3 невдалі проби здоров'я + недоступність Регіону А > 10с)
      ▼
[2. DEGRADED_DETECTED]
      │ (Арбітр Регіону В підтверджує відсутність лідера та видає кворум)
      ▼
[3. DISASTER_DECLARED]
      │ (Виклик STONITH / відкликання IAM-прав Регіону А)
      ▼
[4. PRIMARY_FENCED]
      │ (Застосування команди pg_promote над реплікою Регіону Б)
      ▼
[5. STANDBY_PROMOTED]
      │ (Оновлення DNS-записів / перемикання BGP Anycast на Регіон Б)
      ▼
[6. TRAFFIC_REROUTED]
      │ (Запуск фонової вивірки даних WRT та прогін черг)
      ▼
[7. NOMINAL_DR_ACTIVE]
```

### Детальний опис переходів станів автомата

1. **`NOMINAL → DEGRADED_DETECTED`:** Система моніторингу фіксує 3 послідовні невдалі проби глибокої перевірки здоров'я `/healthz/deep-db` або повну втрату мережевої доступності Регіону А протягом понад 10 секунд.
2. **`DEGRADED_DETECTED → DISASTER_DECLARED`:** Незалежний арбітр у Регіоні В перевіряє доступність лідера. Якщо лідер недоступний з обох регіонів і Standby у Регіоні Б отримує кворум більшості (2/3), Incident Commander або автоматичний контролер офіційно оголошує стан катастрофи.
3. **`DISASTER_DECLARED → PRIMARY_FENCED`:** Виконується процедура ізоляції: надсилається команда знеструмлення через PDU або викликається AWS API для відкликання ролі `DbWriteAccess`. Лише після підтвердження відкликання прав процес переходить до наступного кроку.
4. **`PRIMARY_FENCED → STANDBY_PROMOTED`:** Репліка бази даних у Регіоні Б виконує команду `pg_promote`, завершує режим відновлення, призначає новий Timeline ID і відкривається для операцій запису.
5. **`STANDBY_PROMOTED → TRAFFIC_REROUTED`:** Глобальний балансувальник GSLB / Route53 оновлює DNS-записи або перенаправляє префікси Anycast BGP на точку входу Регіону Б. Контейнери застосунків масштабуються до 100% потужності.
6. **`TRAFFIC_REROUTED → NOMINAL_DR_ACTIVE`:** Запускаються фонові процедури аудиту та вивірки пропущених черг повідомлень (інтервал WRT). Після завершення звірки система переходить у стабільний робочий стан на резервному майданчику.

### Таблиця дій інженерного сценарію аварійного реагування (Runbook Steps)

| Крок | Назва фази | Інженерна дія / Команда | Очікуваний результат | Дія при помилці |
| :--- | :--- | :--- | :--- | :--- |
| **01** | **Верифікація аварії** | `curl -sSf https://api-a.prod.internal/healthz/deep` | Отримано HTTP 503 або таймаут > 5с протягом 3 спроб. | Зупинити процедуру, повідомити Incident Commander. |
| **02** | **Ізоляція лідера** | `aws iam detach-role-policy --role-name DbRole --policy-arn ...` | Політика відключена, старий лідер позбавлений доступу до дисків. | Запустити апаратний STONITH через PDU. |
| **03** | **Промоушн Standby** | `pg_ctl promote -D /var/lib/postgresql/data` | У лозі БД з'являється запис `database system is ready to accept read-write connections`. | Перевірити статус процесів, повторити через `pg_promote()`. |
| **04** | **Масштабування додатків** | `kubectl scale deployment core-api --replicas=50 -n prod` | 50 подів переходять у стан `Running` та `Ready`. | Перевірити наявність вільних CPU-нод у кластері. |
| **05** | **Перемикання DNS** | `aws route53 change-resource-record-sets --hosted-zone-id ...` | TTL оновлено, клієнтські запити надходять у Регіон Б. | Форсувати оновлення записів на рівні Cloudflare/GSLB. |
| **06** | **Вивірка транзакцій** | `./scripts/audit_reconcile_wal.sh --since "14:20:00"` | Згенеровано звіт про розбіжності для фінансового відділу. | Перевести шлюзи платежів у режим ручного клірингу. |

## Чеклист передпольотної підготовки контуру DR (Pre-Flight Validation Checklist)

Перед введенням резервного майданчика в експлуатацію автоматичний валідатор зобов'язаний перевірити такі інваріанти:
1. **Збіг версій образів контейнерів:** Образи додатків у Регіоні Б ідентичні за хешем SHA-256 до образів у Регіоні А.
2. **Синхронізація секретів та сертифікатів:** Усі TLS-сертифікати, API-ключі платіжних систем та паролі баз даних синхронізовані через HashiCorp Vault або AWS Secrets Manager.
3. **Квоти хмарних ресурсів (Service Quotas):** Ліміти на кількість vCPU, IP-адрес Elastic IP та ємність дисків у Регіоні Б перевірені та здатні прийняти 100% пікового навантаження Регіону А без блокування провайдером.
4. **Тест затримки DNS:** Значення TTL для публічних записів `api.company.com` встановлено на рівні ≤ 60 секунд.
