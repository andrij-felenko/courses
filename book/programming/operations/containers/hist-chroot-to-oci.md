# 📜 Еволюція ізоляції процесів: від chroot до стандартів OCI

У 1979 році під час розробки сьомої редакції Unix (Version 7 Unix) у Bell Labs для комп'ютерів PDP-11 уперше з'явився системний виклик `chroot` (від англ. *change root*). У березні 1982 року Білл Джой (Bill Joy) портував `chroot` до кодової бази BSD (під час розробки 4.2BSD) для розв'язання практичної проблеми тестування збірок та інсталяційних скриптів операційної системи: щоразу, коли запускалася перевірка свіжозібраного дистрибутива, нова версія системних бібліотек та утиліт перетирала робочі системні файли хостової машини. Щоб уникнути пошкодження основної ОС під час білду, процес збірки ізолювали всередині призначеного підкаталогу. Цей виклик змінював кореневий каталог (`/`) для поточного процесу та його нащадків на вказаний підкаталог файлового дерева.

Виклик `chroot` не створювався як засіб безпеки. Він лише змінював початкову точку трансляції абсолютних шляхів у віртуальній файловій системі (VFS). Процес, замкнений у так званій «chroot jail» (в'язниці chroot), продовжував бачити загальну таблицю процесів хоста, міг надсилати сигнали будь-яким процесам операційної системи, користувався спільним мережевим стеком хоста та мав повний доступ до системних пристроїв, якщо каталог `/dev` був змонтований усередині ізольованого дерева. Більше того, процес із правами суперкористувача (`root`) міг легко втекти з chroot за допомогою створення тимчасового каталогу та повторного виклику `chroot` або використання збереженого дескриптора каталогу за межами ізольованого кореня (`fchdir`).

## 1999 рік: FreeBSD Jails і перша системна пісочниця

Наприкінці 1990-х років бурхливий розвиток комерційного інтернету породив індустрію спільного хостингу (shared hosting). Сотні клієнтів хотіли розміщувати свої сайти на одному фізичному сервері, маючи права адміністратора для налаштування власних веб-серверів, але провайдери не могли надати їм реального доступу до `root` через небезпеку взаємного злому або виснаження ресурсів.

Для розв'язання цієї проблеми Поуль-Геннінг Камп (Poul-Henning Kamp) та Деррік Паллас (Derrick Pallas) розробили для FreeBSD 4.0 технологію **FreeBSD Jails** (`jail(2)`).

Jails перетворили концепцію ізольованого файлового дерева на повноцінну системну пісочницю, закріпивши за ізольованим середовищем чотири інваріанти:
1. **Ізольоване файлове дерево:** процес не міг вийти за межі призначеного кореня; доступ до файлів конфігурації хоста та чужих в'язниць блокувався на рівні ядра.
2. **Прив'язка до IP-адреси:** кожній в'язниці виділялася одна або кілька конкретних IP-адрес; процес у тюрмі не міг перехоплювати пакети інших інтерфейсів хоста, слухати сирі сокети (`SOCK_RAW`) чи змінювати таблиці маршрутизації.
3. **Обмеження простору процесів:** процеси всередині jail бачили виключно своїх сусідів по в'язниці. Вони не могли бачити процеси хоста, надсилати їм сигнали або підключатися через `ptrace`.
4. **Урізаний root:** суперкористувач усередині jail був позбавлений можливості завантажувати модулі ядра, створювати вузли блокових пристроїв через `mknod`, змінювати правила мережевого екрана або керувати параметрами безпеки ядра.

FreeBSD Jails стали першою комерційно успішною реалізацією віртуалізації на рівні операційної системи (OS-level virtualization), яка забезпечила високу щільність розміщення клієнтів без накладних витрат на апаратну емуляцію.

## 2004–2005 роки: Solaris Zones та OpenVZ

Паралельно з розвитком BSD компанія Sun Microsystems розробляла архітектуру **Solaris Zones (Solaris Containers)** для операційної системи Solaris 10. Інженери Sun створили багаторівневу модель ізоляції: глобальна зона (Global Zone) керувала всім фізичним сервером, а неглобальні зони (Non-Global Zones) надавали користувачам повністю ізольовані віртуальні екземпляри ОС.

Головним проривом Solaris Zones стала інтеграція з підсистемою керування ресурсами (Resource Pools та Fair Share Scheduler, FSS) і віртуалізацією мережевих інтерфейсів (проєкт Crossbow). Кожній зоні можна було гарантувати фіксовану кількість процесорних ядер, обмежити оперативну пам'ять та призначити віртуальні мережеві карти (VNIC) із власними лімітами пропускної здатності.

У світі Linux у 2005 році компанія SWsoft (пізніше Parallels) випустила проєкт **OpenVZ** — набір патчів до ядра Linux, що реалізовував ізольовані віртуальні оточення (Virtual Environments). Хоча OpenVZ активно використовувався хостинг-провайдерами, його код не був прийнятий до основного дерева ванільного ядра Linux (mainline kernel) через монолітність та надмірну складність архітектури патчів. Стало зрозуміло, що ванільному Linux потрібен модульний, розбитий на незалежні примітиви підхід.

## 2006–2008 роки: Народження cgroups та Namespaces у ванільному Linux

У 2006 році інженери компанії Google Рохіт Сет (Rohit Seth) та Пол Менедж (Paul Menage) опублікували патчі під назвою **Process Containers**. Метою Google була оптимізація утилізації дата-центрів: інженери хотіли запускати пакети пакетної обробки даних (MapReduce) на тих самих машинах, де крутилися чутливі до затримок пошукові сервіси (Google Web Search), гарантуючи, що важкий бекенд не відбере CPU та пам'ять у користувацьких запитів.

Щоб уникнути плутанини зі словом «контейнери», у 2007 році підсистему перейменували на **Control Groups (cgroups)**. У січні 2008 року cgroups v1 було офіційно включено до складу ядра Linux 2.6.24.

Паралельно команда розробників ядра, серед яких були Ерік Бідерман (Eric Biederman), Серж Галлін (Serge Hallyn) та Павло Ємельянов, послідовно впроваджувала у ванільне ядро механізм **просторів назв (Namespaces)**:
- 2002 (Linux 2.4.19): `CLONE_NEWNS` (Mount namespace) — перший простір назв, створений Алом Віро (Al Viro) для ізоляції точок монтування файлової системи VFS.
- 2006 (Linux 2.6.19): `CLONE_NEWUTS` (UTS namespace) — ізоляція імені хоста та домену NIS.
- 2006 (Linux 2.6.19): `CLONE_NEWIPC` (IPC namespace) — ізоляція черг повідомлень POSIX/System V та спільних сегментів пам'яті.
- 2007 (Linux 2.6.24): `CLONE_NEWPID` (PID namespace) — ізоляція дерева процесів і поява віртуального PID 1.
- 2009 (Linux 2.6.29): `CLONE_NEWNET` (Network namespace) — повна віртуалізація мережевого стека, сокетів, таблиць маршрутизації та правил iptables.
- 2013 (Linux 3.8): `CLONE_NEWUSER` (User namespace) — мапінг користувачів, що дозволив звичайному непривілейованому користувачеві бути `root` усередині пісочниці.

У 2008 році з'явився проєкт **LXC (Linux Containers)** — перший набір користувацьких утиліт і бібліотек (`liblxc`), що об'єднав Namespaces та cgroups v1 у єдиний інтерфейс запуску системних контейнерів, схожих на легковагові віртуальні машини.

## 2013 рік: Революція Docker та контейнери як артефакти

Попри наявність LXC, технологія контейнерів залишалася складним інструментом для системних адміністраторів. Налаштування cgroups, підготовка chroot-оточень, створення віртуальних мереж `veth` та розгортання образів вимагали глибоких знань системних викликів ядра.

У березні 2013 року Соломон Хайкс (Solomon Hykes), засновник платформи як послуги dotCloud, представив на конференції PyCon проєкт з відкритим кодом **Docker**.

Docker здійснив концептуальну революцію, змістивши фокус із «ізоляції сервера» на **«упаковку застосунку»**:
1. **Контейнер як атомарний процес:** замість запуску повноцінної ОС з `systemd` та демонами Docker запропонував запускати в контейнері рівно один процес застосунку (Application Container).
2. **Шаруваті незмінні образи (Image Layering):** використання файлових систем із копіюванням під час запису (AUFS, OverlayFS) дозволило збирати образи з повторно використовуваних шарів, які кешувалися та передавалися по мережі з блискавичною швидкістю.
3. **Декларативний білд (Dockerfile):** опис інфраструктури виконання коду став частиною кодової бази проєкту, що назавжди ліквідувало проблему «на моєму комп'ютері все працювало».
4. **Централізований реєстр (Docker Hub):** можливість публікувати та завантажувати готові образи однією командою `docker pull` створила глобальну екосистему поширення ПЗ.

Спочатку Docker працював як надбудова над LXC, але вже в 2014 році команда випустила власну бібліотеку `libcontainer` (написану мовою Go), яка напряму викликала системні виклики ядра Linux без сторонніх залежностей.

## 2015–2017 роки: Війна стандартів та створення OCI

Бурхливий успіх Docker породив напругу в індустрії. Компанія CoreOS, яка створила мінімалістичну ОС для хмарних кластерів, висловила занепокоєння тим, що Docker перетворюється з простого інструменту виконання на монолітну платформу, яка диктує власні комерційні правила. У грудні 2014 року CoreOS анонсувала альтернативний контейнерний рушій **rkt (Rocket)** та відкриту специфікацію **AppC (Application Container Specification)**.

Індустрія опинилася перед загрозою розколу на несумісні формати контейнерів. Щоб запобігти фрагментації ринку, у червні 2015 року під егідою Linux Foundation лідери індустрії (Docker, CoreOS, Google, Red Hat, Microsoft, IBM) заснували **Відкриту ініціативу контейнерів (Open Container Initiative, OCI)**.

Docker передав новоствореному консорціуму свою бібліотеку `libcontainer` та низькорівневий рушій, який було перейменовано на **`runc`**, а також специфікацію формату образів.

OCI формалізувала три фундаментальні відкриті специфікації:
- **OCI Runtime Specification (`runtime-spec`):** визначає життєвий цикл контейнера, структуру каталогу (OCI Bundle) та формат файлу конфігурації `config.json`, що описує всі параметри системних викликів, просторів назв, cgroups та seccomp.
- **OCI Image Format Specification (`image-spec`):** стандартизує структуру бінарного образу контейнера (маніфест, конфігурація, tar-архіви шарів файлової системи, геші SHA256).
- **OCI Distribution Specification (`distribution-spec`):** стандартизує протокол HTTP API для завантаження, вивантаження та аутентифікації під час взаємодії з реєстрами образів (OCI Registries).

## Сучасний ландшафт: Розподіл рівнів (High-Level vs Low-Level Runtimes)

Завдяки стандартам OCI сучасний контейнерний стек розділився на чітко розмежовані рівні:
- **Низькорівневі рантайми (Low-Level OCI Runtimes):** `runc` (еталонна реалізація на Go), `crun` (швидкий низькорівневий рантайм на C), `youki` (на Rust). Їхнє єдине завдання — взяти розпакований OCI bundle, викликати системні виклики ядра Linux (`clone`, `unshare`, `pivot_root`, налаштувати cgroups) і передати керування бінарнику програми.
- **Високорівневі рантайми (High-Level Container Runtimes):** `containerd` та `CRI-O`. Вони реалізують інтерфейс Kubernetes Container Runtime Interface (CRI), завантажують образи з мережі, розпаковують шари файлової системи, керують мережевими плагінами CNI та делегують безпосередній запуск контейнерів низькорівневим рушіям.

Контейнеризація пройшла шлях від простої утиліти тестування `chroot` до стандартизованого глобального фундаменту сучасних хмарних обчислень, оркестрації та інфраструктури постачання коду.
