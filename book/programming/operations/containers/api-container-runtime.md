# 📋 Системні інтерфейси та специфікації контейнерних рантаймів

Контейнеризація в операційних системах сімейства Linux базується на узгодженій композиції стандартизованих інтерфейсів різних рівнів: від декларативних специфікацій Відкритої ініціативи контейнерів (Open Container Initiative, OCI) та мережевого інтерфейсу контейнерів (Container Network Interface, CNI) до низькорівневих системних викликів ядра POSIX, віртуальних файлових систем `cgroupfs`, псевдотерміналів та сокетів Netlink.

У цій довідці зведено точні сигнатури системних викликів, бінарні прапорці, структури конфігурації, файлові дескриптори, протоколи хуків та коди помилок, які використовуються контейнерними рушіями (`runc`, `crun`, `containerd`, `CRI-O`) для створення ізольованих середовищ.

### Деталізація розділів OCI-конфігурації

1. **`process.noNewPrivileges` (bool):** активує системний виклик `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)`. Це критичний інваріант безпеки: ядро Linux блокує будь-яке підвищення привілеїв через запуск бінарних файлів із встановленими бітами `setuid` чи `setgid` (наприклад, `/usr/bin/sudo` або `passwd`), а також забороняє розширення бітових масок привілеїв Capabilities через файлові атрибути Extended Attributes.
2. **`process.oomScoreAdj` (int):** значення від `-1000` до `1000`, що записується у псевдофайл `/proc/[pid]/oom_score_adj`. Визначає пріоритет вибору процесу системним ліквідатором ядра Out-Of-Memory (OOM) Killer. Значення `200` робить контейнер більш імовірною жертвою для знищення під час виснаження оперативної пам'яті хоста, зберігаючи системні демони (`kubelet`, `containerd`, `sshd`) недоторканими.
3. **`root.readonly` (bool):** вимагає від рантайму змонтувати кореневу файлову систему з бітовим прапорцем `MS_RDONLY`. Будь-яка спроба шкідливого або скомпрометованого коду записати шелл-код у системні каталоги `/bin`, `/usr` чи `/lib` завершиться помилкою `EROFS` (Read-only file system).
4. **`linux.maskedPaths` (array of strings):** список абсолютних шляхів усередині простору назв монтування, до яких процес контейнера не повинен мати доступу. Рантайм перекриває кожен із цих файлів або каталогів монтуванням спеціального файлу `/dev/null` або порожньої файлової системи `tmpfs` із правами доступу `000`. Це захищає хостові структури ядра (дамп фізичної пам'яті `/proc/kcore`, налаштування переривань та системні таймери) від читання.
5. **`linux.readonlyPaths` (array of strings):** перелік системних вузлів `/proc` та `/sys`, які монтуються з атрибутом лише для читання. Наприклад, захист каталогу `/proc/sys` запобігає модифікації глобальних параметрів стека TCP хоста або вимиканню механізмів рандомізації адресного простору ASLR.

## 2. Системні виклики ядра Linux для маніпуляції просторами назв

Для розмежування глобальних системних таблиць ядро Linux надає три фундаментальні системні виклики в заголовному файлі `<sched.h>`.

```
#define _GNU_SOURCE
#include <sched.h>

/* Створення нового дочірнього процесу в ізольованих просторах назв */
int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...
          /* pid_t *parent_tid, void *tls, pid_t *child_tid */ );

/* Від'єднання поточного процесу від батьківських просторів назв */
int unshare(int flags);

/* Вхід поточного процесу в уже існуючий простір назв іншого процесу */
int setns(int fd, int nstype);
```

### Повний перелік прапорців системного виклику `clone`

│ Прапорець        │ Числове значення (Hex) │ Простір назв та об'єкти ізоляції                                                                           │ Версія ядра Linux │
│ :--------------- | :--------------------- | :---------------------------------------------------------------------------------------------------------- | :----------------- |
│ `CLONE_NEWNS`    │ `0x00020000`           │ **Mount (MNT):** власна ієрархія точок монтування файлових систем VFS.                                     │ Linux 2.4.19       │
│ `CLONE_NEWUTS`   │ `0x04000000`           │ **UTS:** власні ім'я хоста (`hostname`) та доменне ім'я NIS (`domainname`).                               │ Linux 2.6.19       │
│ `CLONE_NEWIPC`   │ `0x08000000`           │ **IPC:** черги повідомлень POSIX/System V, семафори та сегменти спільної пам'яті.                          │ Linux 2.6.19       │
│ `CLONE_NEWUSER`  │ `0x10000000`           │ **User:** власна таблиця відображення ідентифікаторів користувачів (UID) та груп (GID).                   │ Linux 3.8          │
│ `CLONE_NEWPID`   │ `0x20000000`           │ **PID:** ізольоване дерево процесів. Перший процес отримує віртуальний PID 1.                             │ Linux 2.6.24       │
│ `CLONE_NEWNET`   │ `0x40000000`           │ **Network:** власний мережевий стек (інтерфейси, IP-адреси, таблиці маршрутів, правила iptables/nftables). │ Linux 2.6.29       │
│ `CLONE_NEWCGROUP`│ `0x02000000`           │ **Cgroup:** віртуалізований корінь дерева cgroups у файлі `/proc/self/cgroup`.                           │ Linux 4.6          │
│ `CLONE_NEWTIME`  │ `0x00000080`           │ **Time:** індивідуальне зміщення монотонного (`CLOCK_MONOTONIC`) та системного годинників.                 │ Linux 5.6          │

### Системний виклик `setns` та псевдофайли `/proc/[pid]/ns/`

Для приєднання до існуючого контейнера (механізм команди `docker exec` або відлагоджувальних сайдкарів Kubernetes) процес відкриває спеціальний файловий дескриптор у каталозі `/proc/[pid]/ns/`:

```
/proc/[pid]/ns/
├── cgroup -> cgroup:[4026531835]
├── ipc    -> ipc:[4026532488]
├── mnt    -> mnt:[4026532486]
├── net    -> net:[4026532491]
├── pid    -> pid:[4026532489]
├── pid_for_children -> pid:[4026532489]
├── time   -> time:[4026531834]
├── user   -> user:[4026531837]
└── uts    -> uts:[4026532487]
```

Число у квадратних дужках — це унікальний 64-бітний номер іноди (inode number) простору назв у віртуальній файловій системі `nsfs`. Якщо два процеси на хості мають однаковий номер іноди для вузла `net`, вони використовують один спільний мережевий стек.

Послідовність системних викликів для входу в мережевий простір назв:
```
int net_fd = open("/proc/48291/ns/net", O_RDONLY | O_CLOEXEC);
if (net_fd < 0) {
    /* Обробка помилки: процес 48291 завершився або немає прав доступу */
}

/* Перехід у мережевий простір цільового контейнера */
if (setns(net_fd, CLONE_NEWNET) != 0) {
    /* Обробка помилки переходу */
}
close(net_fd);
```

### Коди помилок системних викликів просторів назв (`errno`)

- `EPERM`: викликаючий процес не має привілею `CAP_SYS_ADMIN` у поточному або цільовому просторі користувачів.
- `EINVAL`: вказано некоректний тип простору назв або неприпустиму комбінацію прапорців у `clone` (наприклад, одночасне встановлення `CLONE_THREAD` та `CLONE_NEWPID`).
- `ENOSPC`: досягнуто системного ліміту на кількість одночасно відкритих просторів назв, заданого в системних параметрах `/proc/sys/user/max_*_namespaces`.
- `EBADF`: переданий файловий дескриптор `fd` не відповідає відкритому файлу з псевдофайлової системи `nsfs`.

## 3. Файловий інтерфейс керування ресурсами cgroups v2

У єдиній ієрархії cgroups v2 (змонтованій за замовчуванням у каталозі `/sys/fs/cgroup`) кожен контейнер представляється окремим підкаталогом.

```
/sys/fs/cgroup/
├── cgroup.controllers          # Доступні системні контролери
├── cgroup.procs                # Список PID процесів поточної групи
├── cgroup.subtree_control      # Контролери, активні для дочірніх груп
├── cgroup.events               # Стан групи (populated, frozen)
├── cgroup.freeze               # 1 — заморозити процеси, 0 — розморозити
├── cgroup.kill                 # 1 — атомарний розсил SIGKILL усім процесам
└── <slice-or-container-id>/     # Каталог ізольованого контейнера
    ├── cpu.max                 # Ліміт використання CPU (квота та період)
    ├── cpu.weight              # Відносна вага під час планування (1–10000)
    ├── cpu.stat                # Статистика використання часу та тротлінгу
    ├── memory.max              # Жорсткий ліміт оперативної пам'яті (виклик OOM)
    ├── memory.high             # М'який поріг активації тротлінгу алокацій
    ├── memory.min              # Жорстко зарезервована пам'ять (не скидається)
    ├── memory.low              # М'який резерв пам'яті
    ├── memory.current          # Поточне фактичне використання пам'яті в байтах
    ├── memory.events           # Лічильники виснаження пам'яті та подій OOM
    ├── io.max                  # Ліміти швидкості читання/запису (Bps та IOPS)
    ├── io.stat                 # Статистика дискових операцій
    └── pids.max                # Максимальна кількість потоків та процесів
```

### Специфікація форматів файлів контролерів cgroups v2

#### Контролер процесора: `cpu.max`, `cpu.weight`, `cpu.stat`

Файл `cpu.max` задає ліміт квоти Completely Fair Scheduler (CFS).
Формат: `$QUOTA $PERIOD` (у мікросекундах).

```
# Виділення контейнеру 2.0 ядер (200 000 мкс за період 100 000 мкс):
200000 100000

# Зняття обмеження (безлімітне використання вільних ресурсів):
max 100000
```

Файл `cpu.stat` містить агреговану телеметрію планувальника:
- `usage_usec`: сумарний процесорний час виконання в мікросекундах.
- `user_usec`: час виконання коду в просторі користувача (Ring 3).
- `system_usec`: час виконання системних викликів у ядрі (Ring 0).
- `nr_periods`: загальна кількість пройдених періодів планувальника CFS.
- `nr_throttled`: кількість періодів, протягом яких процеси контейнера були штучно заблоковані планувальником через вичерпання квоти.
- `throttled_usec`: сумарний час примусового простою процесів через тротлінг.

#### Контролер оперативної пам'яті: `memory.max`, `memory.high`, `memory.events`

Файл `memory.max` приймає розмір у байтах або ключове слово `max`:
```
# Встановлення жорсткої межі 1 ГіБ (1073741824 байти):
1073741824
```

Файл `memory.events` дозволяє супервізорам відстежувати проблеми виснаження пам'яті без опитування ядрових логів:
- `low`: кількість спроб вивільнення пам'яті нижче порогу `memory.low`.
- `high`: кількість разів, коли споживання перевищило `memory.high`, активувавши синхронне витіснення кешів сторінок (Page Cache reclaim).
- `max`: кількість разів, коли алокація вперлася в жорсткий ліміт `memory.max`.
- `oom`: кількість спроб виклику внутрішнього OOM-кілера групи.
- `oom_kill`: кількість реальних процесів контейнера, знищених сигналом `SIGKILL` через брак оперативної пам'яті.

#### Контролер блокових пристроїв: `io.max`

Файл `io.max` встановлює ліміти пропускної здатності для конкретного пристрою за його мажорним та мінорним номерами:
Формат: `$MAJ:$MIN rbps=$R wbps=$W riops=$RI wiops=$WI`

```
# Обмеження читання до 50 МБ/с (52428800 Б/с) та запису до 1000 IOPS для диска /dev/sda (8:0):
8:0 rbps=52428800 wiops=1000
```

#### Контролер процесів: `pids.max`

Запобігає атакам виснаження ресурсів через неконтрольоване розгалуження процесів (fork-бомби):
```
# Дозволити контейнеру створити максимум 500 потоків і процесів:
500
```

## 4. Специфікація OCI Image Format: маніфести та дескриптори

Специфікація OCI Image Format Specification стандартизує структуру бінарних артефактів образів у реєстрах. Образ складається з маніфесту (Manifest), конфігурації (Config) та набору стиснених tar-архівів шарів (Layer Blobs).

Кожен компонент посилається на інші через **Дескриптор вмісту (Descriptor)**, який містить MIME-тип медіа, криптографічний дайджест SHA256 та розмір у байтах:

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:d5930e15264eb786a3479a96e95c4794e7737d2f9797203b53f650742f1f6c40",
    "size": 7023
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:4f4fb700ef54461cfa02571ae0db9a0dc1e0cdb55774843d52d829b6471f643b",
      "size": 32451202
    },
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:8a5f36e8979339e1a90d402fa6a6f62b87d84879208034d6cb2ae59e2b17a1a4",
      "size": 1823901
    }
  ],
  "annotations": {
    "org.opencontainers.image.created": "2026-08-15T12:00:00Z",
    "org.opencontainers.image.authors": "platform-team@example.com",
    "org.opencontainers.image.title": "backend-service"
  }
}
```

## 5. Специфікація хуків життєвого циклу OCI Hooks

Контейнерні рантайми підтримують синхронне виконання зовнішніх утиліт (хуків) на різних фазах життєвого циклу контейнера.

## 6. Мережевий інтерфейс CNI: контракт плагінів мережі

Специфікація **Container Network Interface (CNI)** визначає контракт взаємодії між високорівневими контейнерними рушіями (`containerd`, `CRI-O`, `kubelet`) та мережевими плагінами (Calico, Flannel, Cilium, Bridge).

Плагін CNI є виконуваним бінарним файлом, який отримує параметри виконання через змінні оточення та потік `stdin`.

### Змінні оточення середовища виконання CNI

│ Змінна оточення      │ Призначення та тип значення                                                                                        │
│ :------------------- | :------------------------------------------------------------------------------------------------------------------ |
│ `CNI_COMMAND`        │ Виконувана дія: `ADD` (налаштувати мережу), `DEL` (демонтувати інтерфейс), `CHECK` (перевірити стан), `VERSION`.     │
│ `CNI_CONTAINERID`    │ Унікальний текстовий ідентифікатор цільового контейнера або Pod'а.                                                  │
│ `CNI_NETNS`          │ Абсолютний шлях до файлу мережевого простору назв на хості (наприклад, `/proc/48291/ns/net` або `/var/run/netns/c1`).│
│ `CNI_IFNAME`         │ Назва мережевого інтерфейсу всередині контейнера (за стандартом завжди `eth0`).                                    │
│ `CNI_PATH`           │ Список каталогів пошуку виконуваних бінарників плагінів (наприклад, `/opt/cni/bin`).                                │
│ `CNI_ARGS`           │ Додаткові користувацькі параметри у форматі `ключ=значення;ключ2=значення2`.                                        │

### Мережева сантехніка ядра: Netlink та veth-пари

Під час обробки команди `ADD` плагін CNI взаємодіє з ядром Linux через сокети сімейства `AF_NETLINK` (підсистема `NETLINK_ROUTE`), виконуючи послідовність операцій:

1. **Створення віртуального кабелю (veth pair):** ядро створює два пов'язані мережеві інтерфейси (`veth0_host` та `veth0_cont`). Будь-який Ethernet-фрейм, надісланий в один інтерфейс, миттєво з'являється на виході іншого.
2. **Переміщення інтерфейсу в простір контейнера:** через повідомлення Netlink `RTM_NEWLINK` із атрибутом `IFLA_NET_NS_FD` інтерфейс `veth0_cont` вилучається з таблиці хоста й додається до мережевого простору контейнера, де перейменовується на `eth0`.
3. **Прив'язка хостового інтерфейсу:** інтерфейс `veth0_host` додається до хостового віртуального комутатора (Linux Bridge `cbr0` або Open vSwitch) або обробляється програмами eBPF (tc-bpf у Cilium).
4. **Конфігурація адрес та маршрутів:** через повідомлення `RTM_NEWADDR` та `RTM_NEWROUTE` інтерфейсу `eth0` присвоюється IP-адреса, маска підмережі та маршрут за замовчуванням через хостовий міст.

## 7. Системний виклик `pivot_root` та ізоляція кореня VFS

Системний виклик `pivot_root(2)` виконує атомарну зміну кореневої точки монтування VFS:

```
#include <sys/syscall.h>
#include <unistd.h>

int pivot_root(const char *new_root, const char *put_old);
```

### Системні вимоги та обмеження `pivot_root`

1. `new_root` та `put_old` зобов'язані бути окремими точками монтування в поточній таблиці VFS (вирішується попереднім викликом `mount(new_root, new_root, "bind", MS_BIND | MS_REC, NULL)`).
2. Поточний простір назв монтування (Mount namespace) повинен мати прапорець поширення `MS_PRIVATE` (активується через `mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL)`), інакше операція викличе помилку `EINVAL`.
3. `put_old` повинен бути підкаталогом усередині `new_root`.
4. Жодна інша файлова система не може бути змонтована поверх `put_old`.

Після успішного виконання `pivot_root` стара хостова файлова система залишається змонтованою в каталозі `put_old`. Рантайм викликає `umount2(put_old, MNT_DETACH)`, що остаточно від'єднує хостовий корінь і робить неможливим будь-який доступ до файлів хоста зсередини контейнера.

## 8. Бінарні структури та макроси Seccomp-BPF

Фільтрація системних викликів у Linux використовує віртуальну машину Berkeley Packet Filter (cBPF).

```
#include <linux/seccomp.h>
#include <linux/filter.h>
#include <linux/audit.h>
#include <sys/ptrace.h>
#include <sys/prctl.h>

/* Структура одного бінарного інструкційного блоку cBPF */
struct sock_filter {
    __u16 code;   /* Код операції віртуальної машини BPF */
    __u8  jt;     /* Зміщення переходу при істинності умови (Jump True) */
    __u8  jf;     /* Зміщення переходу при хибності умови (Jump False) */
    __u32 k;      /* Багатоцільовий аргумент: константа або зміщення даних */
};

struct sock_fprog {
    unsigned short      len;    /* Кількість фільтруючих інструкцій у масиві */
    struct sock_filter *filter; /* Покажчик на масив інструкцій */
};

/* Дані системного виклику, які аналізує програма BPF */
struct seccomp_data {
    int   nr;                   /* Номер системного виклику (наприклад, __NR_read) */
    __u32 arch;                 /* Архітектура процесора (AUDIT_ARCH_X86_64) */
    __u64 instruction_pointer;  /* Значення регістру RIP у момент виклику */
    __u64 args[6];              /* 6 системних аргументів виклику (RDI, RSI, RDX...) */
};
```

### Значення, що повертає фільтр Seccomp (`SECCOMP_RET_*`)

│ Дія Seccomp                │ Числове значення (Hex) │ Поведінка ядра Linux під час обробки системного виклику                                           │
│ :------------------------- | :--------------------- | :------------------------------------------------------------------------------------------------- |
│ `SECCOMP_RET_KILL_PROCESS`  │ `0x80000000`           │ Ядро негайно знищує весь процес сигналом `SIGSYS`.                                                 │
│ `SECCOMP_RET_KILL_THREAD`   │ `0x00000000`           │ Ядро знищує конкретний потік, який здійснив заборонений виклик.                                   │
│ `SECCOMP_RET_TRAP`          │ `0x00030000`           │ Ядро надсилає процесу сигнал `SIGSYS` із заповненою структурою `siginfo_t` для ручної обробки.     │
│ `SECCOMP_RET_ERRNO`        │ `0x00050000`           │ Ядро блокує виконання виклику й повертає вказаний у молодших 16 бітах код `errno` (наприклад `EPERM`). │
│ `SECCOMP_RET_TRACE`        │ `0x7ff00000`           │ Ядро сповіщає процес-відлагоджувач через `ptrace(PTRACE_EVENT_SECCOMP)`.                          │
│ `SECCOMP_RET_LOG`          │ `0x7ffc0000`           │ Системний виклик дозволяється, але запис про нього надсилається в системний аудит `auditd`.        │
│ `SECCOMP_RET_ALLOW`        │ `0x7fff0000`           │ Системний виклик виконується без жодних обмежень чи затримок.                                     │

## 9. Модель привілеїв Linux Capabilities

Усі 41 системний привілей ядра Linux описано в системному заголовному файлі `<linux/capability.h>`.

Для маніпуляції привілеями використовуються системні виклики `capget(2)` та `capset(2)` або високорівнева бібліотека `libcap-ng`.

```
#include <sys/capability.h>
#include <sys/prctl.h>

/* Вилучення привілею з Bounding Set (заборона на отримання в майбутньому) */
int prctl(PR_CAPBSET_DROP, unsigned long cap, 0, 0, 0);

/* Перевірка наявності привілею в Bounding Set */
int prctl(PR_CAPBSET_READ, unsigned long cap, 0, 0, 0);
```

### П'ять наборів привілеїв процесу в ядрі Linux

1. **Effective (`CapEff`):** бітова маска привілеїв, які ядро перевіряє в момент виконання системного виклику (наприклад, право відкрити сокет на порту 80 перевіряє наявність біта `CAP_NET_BIND_SERVICE` у `CapEff`).
2. **Permitted (`CapPrm`):** граничний набір привілеїв, які процес має право увімкнути у своєму наборі `CapEff`.
3. **Inheritable (`CapInh`):** набір привілеїв, які можуть бути успадковані дочірнім процесом під час виклику `execve(2)`.
4. **Bounding (`CapBnd`):** глобальний обмежувач: жоден процес не може отримати привілей, якого немає в його Bounding set, навіть якщо запускається бінарний файл `setuid root`.
5. **Ambient (`CapAmb`):** привілеї, які автоматично передаються непривілейованим програмам під час виклику `execve(2)` без необхідності встановлення бітів файлової системи.

### Перелік критично небезпечних Capabilities, які скидаються за замовчуванням

│ Привілей              │ Номер біта │ Загроза безпеці при збереженні в контейнері                                                                │
│ :-------------------- | :--------- | :--------------------------------------------------------------------------------------------------------- |
│ `CAP_SYS_ADMIN`       │ `21`       │ «Всесильний привілей»: дозволяє монтувати ФС, налаштовувати cgroups, змінювати простори назв та seccomp.   │
│ `CAP_NET_ADMIN`       │ `12`       │ Дозволяє змінювати таблиці маршрутизації хоста, створювати тунелі, модифікувати правила iptables/nftables. │
│ `CAP_SYS_RAWIO`       │ `17`       │ Прямий доступ до фізичної пам'яті хоста (`/dev/mem`, `/dev/kmem`) та портів вводу/виводу процесора (I/O).   │
│ `CAP_SYS_PTRACE`      │ `19`       │ Дозволяє інспектувати пам'ять, змінювати регістри та перехоплювати виклики процесів хоста через `ptrace`.  │
│ `CAP_SYS_MODULE`      │ `16`       │ Дозволяє завантажувати сторонні двійкові модулі ядра (`.ko`), отримуючи повний контроль над Ring 0 хоста. │
│ `CAP_DAC_OVERRIDE`    │ `1`        │ Дозволяє ігнорувати всі перевірки прав доступу файлової системи (читання, запис, виконання будь-яких файлів).│
│ `CAP_MKNOD`           │ `27`       │ Дозволяє створювати спеціальні файли блокових та символьних пристроїв через системний виклик `mknod(2)`.   │
│ `CAP_SYS_BOOT`        │ `22`       │ Дозволяє перезавантажувати або вимикати фізичний хост через системний виклик `reboot(2)`.                  │

## 10. Інтерфейс псевдотерміналів PTY

Якщо в `config.json` параметр `process.terminal` встановлено в `true`, рантайм створює пару псевдотерміналів (Master/Slave PTY) для забезпечення інтерактивного введення/виведення:

:::tabs
```c
#define _XOPEN_SOURCE 600
#include <stdlib.h>
#include <fcntl.h>
#include <termios.h>
#include <sys/ioctl.h>

/* Відкриття ведучого пристрою PTY Master */
int master_fd = posix_openpt(O_RDWR | O_NOCTTY | O_CLOEXEC);

/* Налаштування прав та розблокування Slave PTY */
grantpt(master_fd);
unlockpt(master_fd);

/* Отримання шляху до веденого вузла (наприклад, /dev/pts/3) */
char *slave_path = ptsname(master_fd);
```
```cpp
#include <cstdlib>
#include <fcntl.h>
#include <termios.h>
#include <sys/ioctl.h>
#include <string_view>
#include <system_error>

/* Відкриття ведучого пристрою PTY Master */
int master_fd = ::posix_openpt(O_RDWR | O_NOCTTY | O_CLOEXEC);
if (master_fd < 0) {
    throw std::system_error(errno, std::generic_category(), "posix_openpt failed");
}

/* Налаштування прав та розблокування Slave PTY */
::grantpt(master_fd);
::unlockpt(master_fd);

/* Отримання шляху до веденого вузла */
std::string_view slave_path = ::ptsname(master_fd);
```
:::

Процес контейнера відкриває `slave_path`, дублює його на стандартні дескриптори `0 (stdin)`, `1 (stdout)` та `2 (stderr)` через `dup2(slave_fd, STDIN_FILENO)`, викликає системний виклик `setsid()` для створення нової термінальної сесії та призначає PTY своїм керуючим терміналом через `ioctl(slave_fd, TIOCSCTTY, 0)`.

Зміна розмірів термінального вікна (наприклад, під час ресайзу вікна браузера чи терміналу) передається рантайму через виклик `ioctl`:

:::tabs
```c
struct winsize ws = {
    .ws_row = 24,
    .ws_col = 80,
    .ws_xpixel = 0,
    .ws_ypixel = 0
};
ioctl(master_fd, TIOCSWINSZ, &ws);
```
```cpp
struct winsize ws{};
ws.ws_row = 24;
ws.ws_col = 80;
::ioctl(master_fd, TIOCSWINSZ, &ws);
```
:::

Ядро Linux транслює цей виклик у сигнал `SIGWINCH` процесу контейнера, дозволяючи консольним програмам (`htop`, `vim`, `bash`) автоматично адаптувати свій вивід під розмір екрана.
