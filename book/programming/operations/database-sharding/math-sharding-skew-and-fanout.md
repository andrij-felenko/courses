# 🧮 Математика шардингу: розподіл затримок scatter-gather, дисперсія віртуальних вузлів та закон Ціпфа

Математичний апарат шардингу описує три фундаментальні ймовірнісні процеси в розподілених базах даних: деградацію хвостової затримки під час паралельного опитування вузлів (Scatter-Gather), рівномірність розсіювання ключів на консистентному кільці як функцію від кількості віртуальних вузлів та концентрацію навантаження на окремих серверах під дією закону степеневого розподілу популярності (закону Ціпфа). Без математичного розрахунку цих величин інженерні рішення щодо кількості шардів та розміру хеш-кільця перетворюються на вгадування, яке призводить або до раптового перевантаження окремих машин, або до вибуху 99-го перцентиля затримки.

## 1. Імовірнісна модель деградації затримки при Scatter-Gather запитах

Розглянемо шардовану систему, яка складається з `N` незалежних вузлів. Коли клієнт виконує запит, що не містить ключа шардингу (наприклад, повнотекстовий пошук або агрегація за неіндексованим полем), координатор змушений виконати віялове опитування (Fan-Out / Scatter-Gather) усіх `N` вузлів одночасно.

Підсумковий час виконання запиту `T_total` визначається моментом повернення останнього, найповільнішого результату:

```
T_total = max(X₁, X₂, ..., X_N)
```

де `X_i` — випадкова величина, що позначає час виконання запиту на `i`-му шарді.

### Виведення функції розподілу максимуму

Припустимо, що затримки окремих шардів є незалежними та однаково розподіленими випадковими величинами (i.i.d.) із кумулятивною функцією розподілу `F(t) = P(X_i ≤ t)`.

Ймовірність того, що загальний час виконання запиту `T_total` не перевищить значення `t`, дорівнює ймовірності того, що **кожен** з `N` шардів завершить обробку за час, не більший за `t`:

```
P(T_total ≤ t) = P(max(X₁, X₂, ..., X_N) ≤ t)
= P(X₁ ≤ t ∧ X₂ ≤ t ∧ ... ∧ X_N ≤ t)     [за означенням максимуму множини]
= P(X₁ ≤ t) · P(X₂ ≤ t) · ... · P(X_N ≤ t) [внаслідок незалежності вузлів]
= [F(t)]ᴺ                                  [внаслідок ідентичності розподілів]
```

Таким чином, функція розподілу підсумкової затримки `F_scatter(t)` має вигляд:

```
F_scatter(t) = [F(t)]ᴺ
```

### Розрахунок перцентилів системи

Нехай `t_p` — це `p`-й перцентиль затримки окремого вузла, тобто `F(t_p) = p`. Для 99-го перцентиля (`p = 0.99`) окремий вузол відповідає швидше за `t₀.₉₉` у 99% випадків, а у 1% випадків зазнає затримки через збирання сміття (GC pause), конкуренцію за блокування сторінок або збійні дискові операції введення-виведення.

Обчислимо ймовірність `P_ok(N)` того, що паралельний запит до `N` шардів укладеться в нормальний час `t₀.₉₉` окремої машини:

```
P_ok(N) = [F(t₀.₉₉)]ᴺ = (0.99)ᴺ
```

Відповідно, ймовірність того, що клієнт отримає «хвостову затримку» (тобто запит триватиме довше за нормальний 99-й перцентиль одного вузла):

```
P_tail(N) = 1 - (0.99)ᴺ
```

Порахуємо значення для різної кількості шардів `N`:

Для `N = 1` шард:
```
P_ok(1)   = (0.99)¹ = 0.9900  (99.0% запитів у нормі)
P_tail(1) = 1 - 0.9900 = 0.0100 (1.0% повільних запитів)
```

Для `N = 10` шардів:
```
P_ok(10)   = (0.99)¹⁰ ≈ 0.9044 (90.4% запитів у нормі)
P_tail(10) = 1 - 0.9044 ≈ 0.0956 (9.6% повільних запитів)
```

Для `N = 50` шардів:
```
P_ok(50)   = (0.99)⁵⁰ ≈ 0.6050 (60.5% запитів у нормі)
P_tail(50) = 1 - 0.6050 ≈ 0.3950 (39.5% повільних запитів)
```

Для `N = 100` шардів:
```
P_ok(100)   = (0.99)¹⁰⁰ ≈ 0.3660 (36.6% запитів у нормі)
P_tail(100) = 1 - 0.3660 ≈ 0.6340 (63.4% повільних запитів)
```

Для `N = 500` шардів:
```
P_ok(500)   = (0.99)⁵⁰⁰ ≈ 0.00657 (0.66% запитів у нормі)
P_tail(500) = 1 - 0.00657 ≈ 0.9934 (99.3% повільних запитів)
```

Цей результат викриває головну небезпеку Scatter-Gather: у кластері зі 100 шардів **майже дві третини (63.4%) усіх багатошардових запитів натрапляють на хвостову деградацію одного з вузлів**, навіть якщо кожен окремий сервер працює ідеально в 99% випадків.

## 2. Дисперсія розподілу ключів у консистентному хешуванні

У класичному консистентному хешуванні хеш-простір утворює одиничне кільце `[0, 1)`. Фізичні сервери та ключі відображаються на кільце за допомогою псевдовипадкової хеш-функції з рівномірним розподілом (наприклад, MurmurHash3 або xxHash).

Якщо `S` фізичних серверів розміщуються на кільці як одиничні точки, відстані між сусідніми точками (довжини сегментів дуги `L_i`) мають експоненційний розподіл.

### Математичне сподівання та дисперсія довжини дуги для одиночних вузлів

Для `S` точок, рівномірно кинутих на одиничне коло:

```
E[L] = 1 / S                 [середня довжина сегмента]
Var(L) = (S - 1) / (S² · (S + 1)) ≈ 1 / S²  [дисперсія довжини сегмента]
```

Стандартне відхилення довжини сегмента `σ_L`:

```
σ_L = √Var(L) ≈ 1 / S = E[L]
```

Оскільки стандартне відхилення дорівнює самому середньому значенню (`σ_L / E[L] ≈ 1`), коефіцієнт варіації становить 100%. Це означає, що при наївному розміщенні вузлів на кільці один сервер може отримати в 3–5 разів більше ключів і трафіку, ніж сусідній, що призводить до виникнення гарячих шардів.

### Згладжування через віртуальні вузли (Virtual Nodes)

Щоб усунути перекіс, кожен із `S` фізичних серверів представляється на кільці у вигляді `V` віртуальних вузлів (vnodes). Загальна кількість точок на кільці становить `M = S · V`.

Частка ключів `W_k`, які припадають на `k`-й фізичний сервер, дорівнює сумі довжин `V` випадкових сегментів, що належать його віртуальним вузлам:

```
W_k = ∑_{j=1}^{V} L_{k,j}
```

Згідно з центральною граничною теоремою (ЦГТ), при великому `V` розподіл сумарної частки навантаження фізичного сервера `W_k` прямує до нормального розподілу `N(μ_W, σ_W²)`:

```
μ_W = E[W_k] = V · E[L] = V · (1 / (S · V)) = 1 / S
```

Дисперсія суми `V` слабозалежних випадкових величин:

```
Var(W_k) ≈ V · Var(L) ≈ V · (1 / (S · V)²) = 1 / (S² · V)
```

Звідси відносне стандартне відхилення навантаження сервера (коефіцієнт дисперсії шардингу `CV`):

```
CV = σ_W / μ_W
= √(1 / (S² · V)) / (1 / S)   [підстановка стандартного відхилення та середнього]
= (1 / (S · √V)) / (1 / S)    [винесення кореня зі знаменника]
= 1 / √V                      [скорочення спільного множника 1/S]
```

Точніший теоретичний розрахунок із врахуванням кореляції сусідніх дуг дає асимптотичну оцінку:

```
CV ≈ 1 / √(2 · V)
```

Порахуємо необхідну кількість віртуальних вузлів `V` для досягнення цільової рівномірності кластера:

Для `V = 10` віртуальних вузлів:
```
CV ≈ 1 / √(2 · 10) = 1 / √20 ≈ 0.2236  (похибка розподілу ±22.4%)
```

Для `V = 50` віртуальних вузлів:
```
CV ≈ 1 / √(2 · 50) = 1 / √100 = 0.1000  (похибка розподілу ±10.0%)
```

Для `V = 128` віртуальних вузлів:
```
CV ≈ 1 / √(2 · 128) = 1 / √256 = 0.0625  (похибка розподілу ±6.25%)
```

Для `V = 256` віртуальних вузлів:
```
CV ≈ 1 / √(2 · 256) = 1 / √512 ≈ 0.0442  (похибка розподілу ±4.42%)
```

Для `V = 1024` віртуальних вузлів:
```
CV ≈ 1 / √(2 · 1024) = 1 / √2048 ≈ 0.0221 (похибка розподілу ±2.21%)
```

Ця формула пояснює галузевий стандарт конфігурації розподілених сховищ (Amazon Dynamo, Cassandra, Couchbase): вибір `V = 128..256` гарантує, що перекіс обсягу даних між фізичними шардами не перевищить 5% при мінімальних витратах оперативної пам'яті маршрутизаторів на збереження мапи хеш-кільця.

## 3. Ймовірність колізій блокувань у розподілених транзакціях (Birthday Problem)

Коли в системі виконуються розподілені транзакції, що одночасно модифікують кілька сутностей, виникає ризик зіткнення за блокуваннями (Lock Collisions) між незалежними транзакціями на одному шарді.

Нехай у кластері працює `S` шардів. Дві незалежні паралельні транзакції `T_A` та `T_B` модифікують по `k` випадкових ключів кожна.

Ймовірність того, що транзакція `T_A` торкнеться певної підмножини з `k` шардів без колізій із транзакцією `T_B`, моделюється через узагальнену задачу днів народження.

Ймовірність `P_no_collision` відсутності спільних шардів між двома транзакціями розміру `k`:

```
P_no_collision = ∏_{i=0}^{k-1} ((S - k - i) / (S - i))
```

При малих значеннях `k` відносно `S` (`k ≪ S`) застосовується експоненційна апроксимація:

```
P_collision ≈ 1 - exp(- (k²) / S)
```

Розрахуємо ймовірність колізії для кластера з `S = 16` шардів:
- Якщо транзакції торкаються `k = 2` шардів: `P_collision ≈ 1 - exp(-4 / 16) = 1 - exp(-0.25) ≈ 22.1%`;
- Якщо транзакції торкаються `k = 4` шардів: `P_collision ≈ 1 - exp(-16 / 16) = 1 - exp(-1) ≈ 63.2%`;
- Якщо транзакції торкаються `k = 6` шардів: `P_collision ≈ 1 - exp(-36 / 16) = 1 - exp(-2.25) ≈ 89.5%`.

Цей розрахунок доводить фундаментальний закон проектування розподілених даних: **зростання кількості шардів, задіяних в одній транзакції (`k`), лавиноподібно збільшує ймовірність взаимоблокувань (Deadlocks) та черг очікування на шардах**. Розподілена транзакція повинна проектуватися так, щоб `k ≤ 2`, а операції на більшій кількості вузлів мають переводитися в асинхронні Саги.

## 4. Модель нерівномірності запитів за законом Ціпфа (Zipfian Skew)

Рівномірний розподіл обсягу байтів на диску не гарантує рівномірного розподілу навантаження на процесори. Якщо частота звернень до ключів підпорядковується степеневому закону (Power-Law / Zipf's Law), наявність навіть кількох надпопулярних сутностей («гарячих ключів» або «знаменитостей») призводить до насичення одного шарду.

Закон Ціпфа стверджує, що ймовірність звернення до `k`-го за популярністю ключа в системі з `K` унікальних ключів описується формулою:

```
P(k) = (1 / kˢ) / H_{K,s}
```

де `s` — показник крутизни розподілу (зазвичай `s ∈ [0.7, 1.2]` для соціальних мереж та e-commerce), а `H_{K,s}` — узагальнене гармонічне число порядку `s`:

```
H_{K,s} = ∑_{i=1}^{K} (1 / iˢ)
```

### Концентрація трафіку на топ-ключах

Оцінимо частку трафіку `Q_top(M)`, яка припадає на `M` найпопулярніших ключів системи:

```
Q_top(M) = (∑_{k=1}^{M} (1 / kˢ)) / (∑_{k=1}^{K} (1 / kˢ))
```

Для класичного закону Ціпфа з параметром `s = 1.0` при великому `K` сума гармонічного ряду апроксимується інтегралом:

```
H_{K,1} = ∑_{i=1}^{K} (1 / i) ≈ ln(K) + γ
```

де `γ ≈ 0.5772` — стала Ейлера-Маскероні.

Тоді частка навантаження перших `M` ключів:

```
Q_top(M) ≈ ln(M) / ln(K)
```

Якщо система зберігає `K = 10 000 000` (10 мільйонів) користувачів:
```
ln(K) = ln(10 000 000) ≈ 16.118
```

Частка запитів до топ-100 користувачів (`M = 100`):
```
Q_top(100) ≈ ln(100) / 16.118 = 4.605 / 16.118 ≈ 0.2857 (28.6% усього трафіку системи!)
```

Частка запитів до топ-1000 користувачів (`M = 1000`):
```
Q_top(1000) ≈ ln(1000) / 16.118 = 6.908 / 16.118 ≈ 0.4286 (42.9% усього трафіку системи!)
```

### Вплив на шардинг

Якщо в системі використовується `N = 10` шардів, то за ідеального рівномірного розподілу кожен шард мав би отримувати `1 / 10 = 10%` загального потоку запитів.

Проте якщо топ-10 найпопулярніших акаунтів (наприклад, блогери-мільйонники в соціальній мережі або супермаркети на маркетплейсі) випадково потрапляють за своїм хешем на Шард 3, цей єдиний вузол поглинає:

```
Load(Shard₃) = Baseline(10%) + Zipf_Top10_Traffic(≈ 15–20%) = 25–30% сумарного трафіку кластера
```

У результаті Шард 3 вичерпує ліміти процесора й черги вводу-виводу при середній завантаженості кластера всього у 35%. 

## 5. Модель часу та пропускної здатності мережі при міграції шардів

Під час онлайн-розщеплення або ребалансування шардованого кластера критично важливим є розрахунок часу передачі даних по мережі та оцінка впливу фонового копіювання на користувацький трафік.

### Обсяг даних, що мігрують при зміні топології

Нехай кластер містить `D_total` байтів даних, рівномірно розподілених між `N` фізичними шардами. Обсяг даних одного шарду:

```
D_shard = D_total / N
```

1. **При наївному хешуванні (`hash(k) mod N` → `hash(k) mod (N+1)`):**
Частка ключів, що залишаються на своїх місцях, дорівнює `1 / (N + 1)`.
Обсяг даних, які необхідно перемістити по мережі:

```
D_move_modulo = D_total · (N / (N + 1))
```

Для кластера з `N = 10` шардів та `D_total = 20` ТБ:
```
D_move_modulo = 20 · (10 / 11) ≈ 18.18 ТБ (90.9% усіх даних кластера!)
```

2. **При консистентному хешуванні (Ring) або діапазонному розщепленні:**
При додаванні одного нового шарду до кластера з `N` машин переміщується лише частка даних, яка відходить новому вузлу:

```
D_move_ring = D_total / (N + 1)
```

Для того самого кластера з `N = 10` шардів та `D_total = 20` ТБ:
```
D_move_ring = 20 / 11 ≈ 1.82 ТБ (лише 9.1% даних!)
```

### Розрахунок тривалості бекфілу та смуги пропускання

Тривалість фази фонового копіювання (Bulk Backfill Duration) `T_backfill` визначається виділеною пропускною здатністю мережі `B_alloc`:

```
T_backfill = D_move / B_alloc
```

Якщо мережевий інтерфейс вузла має пропускну здатність `B_phys = 10` Гбіт/с (1.25 ГБ/с), а інженерний ліміт тротлінгу для захисту користувацьких запитів становить `α = 0.20` (не більше 20% мережі під бекфіл, тобто `B_alloc = 250` МБ/с = 0.25 ГБ/с):

Час копіювання `D_move = 1.82` ТБ (1820 ГБ) для консистентного шарду:

```
T_backfill = 1820 ГБ / 0.25 ГБ/с = 7280 секунд ≈ 2.02 години
```

Час копіювання для модульного шардингу (`18.18` ТБ = 18180 ГБ):

```
T_backfill = 18180 ГБ / 0.25 ГБ/с = 72720 секунд ≈ 20.2 години
```

Цей математичний розрахунок наочно демонструє, чому модульний шардинг є неприйнятним для високонавантажених промислових баз даних: 20-годинне перевантаження мережі та дисків під час додавання кожного нового сервера несе неприпустимі ризики деградації SLO. Консистентне кільцеве та діапазонне розщеплення скорочують обсяг та час міграції рівно в `N` разів.

## 6. Теорія екстремальних значень та логнормальний розподіл затримок

У реальних виробничих кластерах затримка обробки запиту одним вузлом не є рівномірною чи експоненційною: вона підпорядковується логнормальному розподілу (Log-Normal Distribution), для якого характерний важкий довгий хвіст рідкісних, але катастрофічно повільних відповідей.

Нехай затримка одного шарду описується випадковою величиною `X_i = exp(μ + σ · Z)`, де `Z ~ N(0, 1)` — стандартний нормальний розподіл.

### Асимптотична оцінка максимуму згідно з теорією екстремальних значень (EVT)

Згідно з граничною теоремою Фішера–Тіппетта–Гнеденка, максимум `N` логнормальних випадкових величин асимптотично прямує до розподілу Гумбеля (Gumbel Distribution).

Математичне сподівання максимальної затримки `E[T_scatter]` при зростанні кількості шардів `N` апроксимується виразом:

```
E[T_scatter] = E[max(X₁, ..., X_N)]
≈ exp(μ + σ · √(2 · ln(N)) - σ · (ln(ln(N)) + ln(4π)) / (2 · √(2 · ln(N))))
```

Для першого наближення при великих `N`:

```
ln(E[T_scatter]) ≈ μ + σ · √(2 · ln(N))
```

### Практичний інженерний приклад:
Нехай базовий час виконання простого читання на шарді має параметри `μ = 1.0` (тобто медіанний час `exp(1.0) ≈ 2.71` мс) та `σ = 0.8` (важкий хвіст через дискові затримки).

Порахуємо очікувану затримку для різного масштабу кластера `N`:

Для `N = 1` шард:
```
E[T₁] ≈ exp(1.0) ≈ 2.71 мс
```

Для `N = 10` шардів:
```
ln(E[T₁₀]) ≈ 1.0 + 0.8 · √(2 · ln(10)) = 1.0 + 0.8 · √(2 · 2.302) = 1.0 + 0.8 · 2.146 = 2.717
E[T₁₀] ≈ exp(2.717) ≈ 15.13 мс (зростання затримки у 5.6 раза!)
```

Для `N = 64` шардів:
```
ln(E[T₆₄]) ≈ 1.0 + 0.8 · √(2 · ln(64)) = 1.0 + 0.8 · √(2 · 4.159) = 1.0 + 0.8 · 2.884 = 3.307
E[T₆₄] ≈ exp(3.307) ≈ 27.31 мс (зростання затримки у 10.1 раза!)
```

Для `N = 256` шардів:
```
ln(E[T₂₅₆]) ≈ 1.0 + 0.8 · √(2 · ln(256)) = 1.0 + 0.8 · √(2 · 5.545) = 1.0 + 0.8 · 3.330 = 3.664
E[T₂₅₆] ≈ exp(3.664) ≈ 39.02 мс (зростання затримки у 14.4 раза!)
```

## 7. Фільтри Блума для мінімізації Scatter-Gather запитів

Для усунення віялових запитів за вторинними нешардованими індексами маршрутизатор або локальні вузли можуть утримувати фільтри Блума (Bloom Filters), що дозволяють перевірити наявність ключа на шарді перед надсиланням важкого SQL-запиту.

### Ймовірність хибнопозитивного спрацювання (False Positive Probability)

Для фільтра Блума розміром `m` біт, що містить `n` збережених елементів і використовує `k` незалежних хеш-функцій, імовірність хибнопозитивного спрацювання `p_fp` (коли фільтр каже «можливо є», але ключа на шарді немає) описується виразом:

```
p_fp ≈ (1 - exp(- (k · n) / m))ᵏ
```

Оптимальна кількість хеш-функцій `k_opt`, яка мінімізує `p_fp` для заданого співвідношення біт на елемент `b = m / n`:

```
k_opt = (m / n) · ln(2) ≈ 0.693 · (m / n)
```

При підстановці `k_opt` у формулу ймовірності:

```
p_fp = (1/2)^{k_opt} = 2^{- (m / n) · ln(2)} = exp(- (m / n) · (ln(2))²)
```

### Розрахунок скорочення віялового трафіку

Якщо в кластері з `N = 100` шардів клієнт виконує точковий пошук за вторинним ключем, який фізично розташований лише на одному шарді:
- Без фільтрів Блума маршрутизатор надсилає `N = 100` паралельних мережевих запитів (1 корисний + 99 холостих);
- Із фільтрами Блума кількість запитів `Q_fanout` становить:

```
Q_fanout = 1 + (N - 1) · p_fp
```

Порахуємо для різних значень виділеної пам'яті `b = m / n`:

1. При `b = 10` біт на ключ (`k = 7` хеш-функцій):
```
p_fp ≈ (0.5)⁷ ≈ 0.00781 (0.78% хибних спрацювань)
Q_fanout = 1 + 99 · 0.00781 ≈ 1 + 0.773 ≈ 1.77 запити на операцію (скорочення трафіку на 98.2%!)
```

2. При `b = 14.4` біт на ключ (`k = 10` хеш-функцій):
```
p_fp ≈ (0.5)¹⁰ ≈ 0.000976 (0.098% хибних спрацювань)
Q_fanout = 1 + 99 · 0.000976 ≈ 1 + 0.097 ≈ 1.10 запитів на операцію (скорочення трафіку на 98.9%!)
```

### Оптимальний поріг тротлінгу бекфілу за теорією черг

Під час фонового копіювання даних утилізація мережевого каналу зростає від базового значення `U_base` до `U_total = U_base + U_backfill`.

Згідно з формулою затримки в системі масового обслуговування M/M/1:

```
W(U) = S / (1 - U)
```

де `S` — час передачі пакету при нульовій черзі.

Щоб збільшення затримки клієнтських запитів `W(U_total) / W(U_base)` не перевищило заданий коефіцієнт деградації `γ` (наприклад, не більше ніж у `γ = 1.25` раза, тобто зростання затримки на 25%), максимально допустима частка смуги під бекфіл `U_backfill_max` обчислюється аналітично:

```
(1 - U_base) / (1 - U_base - U_backfill_max) ≤ γ
1 - U_base - U_backfill_max ≥ (1 - U_base) / γ
U_backfill_max ≤ (1 - U_base) · (1 - 1 / γ)
```

Для базового завантаження каналу `U_base = 0.50` (50%) та допустимої деградації `γ = 1.25`:

```
U_backfill_max ≤ (1 - 0.50) · (1 - 1 / 1.25) = 0.50 · (1 - 0.80) = 0.50 · 0.20 = 0.10 (10% каналу)
```

Цей результат задає точний математичний ліміт: при 50% утилізації мережі фоновий бекфіл не сміє займати більше 10% пропускної здатності, інакше мережеві черги спричинять сплеск затримок клієнтських транзакцій понад 25%.

Таким чином, математичний аналіз шардингу встановлює три непорушні інженерні межі: кількість віртуальних вузлів `V` повинна бути не меншою за 128 для контролю дисперсії в межах 5%, паралельні Scatter-Gather запити не повинні перевищувати 5% від загального трафіку для захисту 99-го перцентиля затримки, а фонові міграції зобов'язані динамічно обмежуватися формулою допустимого розширення черги.
