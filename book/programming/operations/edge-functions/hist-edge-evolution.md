# 📜 Еволюція крайових обчислень: від статичного кешування й ESI до V8 Isolates і WebAssembly

Розподіл статичного вмісту через мережі доставки контенту (англ. *Content Delivery Network*, CDN) наприкінці 1990-х років розв'язав проблему віддачі незмінних файлів — зображень, скриптів і медіа. Проте щойно користувач надсилав динамічний запит із персоналізованими даними, cookies або заголовками автентифікації, весь трафік мусив долати тисячі кілометрів до єдиного центрального сервера бази даних. Ця вставка простежує інженерну еволюцію, що перетворила пасивні сервери кешування на повноцінні розподілені обчислювальні вузли.

```
Еволюція логіки на краю мережі:
[1998: Статичний CDN] → [2001: ESI / Шаблонізація] → [2006: Varnish VCL] → [2017: V8 Isolates] → [2019: WebAssembly]
```

## Пасивний край: народження CDN та обмеження кешування (1998–2000)

У 1998 році професор математики Массачусетського технологічного інституту Том Лейтон (Tom Leighton) та його аспірант Денні Левін (Danny Lewin) заснували компанію Akamai Technologies. Вони створили першу глобальну мережу розподілених проксі-серверів, що використовувала алгоритми узгодженого хешування (англ. *Consistent Hashing*) для балансування запитів між сотнями точок присутності (англ. *Point of Presence*, PoP).

Архітектура перших CDN базувалася на суворому припущенні:
1. Контент або повністю статичний і кешується за URL-адресою;
2. Або динамічний і повністю пропускається наскрізь до центрального вебсервера (англ. *Origin Server*).

```
Клієнт ──(HTTP GET /style.css)──► [Edge PoP (Cache HIT: 5 мс)]
Клієнт ──(HTTP GET /profile)───► [Edge PoP (Cache Bypass)] ──(Транзит 240 мс)──► [Origin Server]
```

Із розвитком динамічного вебу частка статичних сторінок стрімко скорочувалася. Інтернет-магазини, персоналізовані портали та новинні стрічки формували унікальний HTML для кожного зареєстрованого користувача. У результаті пропускна здатність та ефективність кешування на CDN впали до критичного рівня: понад 85% запитів проходили крізь крайові сервери без кешування, стикаючись із повною затримкою трансокеанського оптоволокна.

## Перші спроби динамічного коду: Edge Side Includes (ESI, 2001)

Щоб подолати дилему персоналізації, у 2001 році консорціум компаній на чолі з Akamai, BEA Systems, Dynamo та Oracle розробив стандарт **ESI** (англ. *Edge Side Includes* — крайові включення).

Ідея ESI полягала в декларативній фрагментарній збірці HTML-сторінки безпосередньо на кешуючому сервері. Замість того, щоб генерувати всю сторінку на центральному бекенді, сервер повертав статичний каркас із XML-подібними тегами включення:

```html
<!-- Відповідь бекенду з тегами ESI -->
<!DOCTYPE html>
<html>
<head><title>Магазин</title></head>
<body>
  <header>
    <!-- Персоналізований блок користувача (TTL = 0) -->
    <esi:include src="/api/user-fragment" onerror="continue" />
  </header>
  <main>
    <!-- Загальний каталог товарів (TTL = 1 година) -->
    <esi:include src="/static/catalog-fragment" />
  </main>
</body>
</html>
```

Коли крайовий проксі-сервер отримував такий документ, він аналізував дерево тегів і робив паралельні підзапити до різних ресурсів:
- Каталог товарів віддавався миттєво з локального кешу PoP;
- Персоналізований заголовок завантажувався з бекенду або кешувався з коротким строком життя за `Cookie`.

```
          ┌──(Кеш PoP: /static/catalog-fragment)──► [Каркас сторінки]
[Клієнт] ◄┤
          └──(Запит до Origin: /api/user-fragment)─► [Збирання ESI на краю]
```

Стандарт ESI продемонстрував важливий принцип: **розділення життєвого циклу статичних та динамічних фрагментів**. Проте ESI мав фатальні обмеження:
- Жорсткий декларативний синтаксис без повноцінного розгалуження, обчислень чи довільної логіки;
- Неможливість перехоплювати HTTP-заголовки до звернення в кеш;
- Відсутність підтримки криптографії, генерації токенів та валідації запитів;
- Необхідність повністю розбирати HTML-текст регулярними виразами або XML-парсерами на боці проксі, що суттєво навантажувало процесори серверів.

## Програмований проксі: Varnish та VCL (2006)

У 2006 році данський архітектор Пол-Геннінг Камп (Poul-Henning Kamp) представив високопродуктивний кешуючий прискорювач **Varnish**. Головною інновацією Varnish стала спеціалізована мова конфігурації **VCL** (англ. *Varnish Configuration Language*).

```
Шлях запиту у Varnish VCL:
vcl_recv ──(Пошук у кеші)──► vcl_hit ──► vcl_deliver
    │
    └──(Промах / Bypass)──► vcl_backend_fetch ──► vcl_backend_response
```

На відміну від статичних файлів конфігурації Apache або NGINX, файл VCL перед запуском компілювався у нативний C-код, а потім завантажувався у пам'ять процесу як спільна бібліотека `.so`. Це дозволяло виконувати індивідуальні перевірки заголовків, перезаписувати URL, керувати ключами кешування за регулярними виразами та модифікувати відповіді на швидкості сотень тисяч операцій на секунду.

Мова VCL заклала концепцію кінцевого автомата обробки запиту:
- `vcl_recv`: перехоплення вхідного запиту клієнта;
- `vcl_hash`: обчислення хеш-ключа для таблиці кешу;
- `vcl_backend_fetch`: модифікація запиту перед відправленням на Origin;
- `vcl_backend_response`: обробка відповіді бекенду перед збереженням;
- `vcl_deliver`: фінальна зміна заголовків перед відправленням клієнту.

Компанія Fastly побудувала свою глобальну CDN-інфраструктуру на базі модифікованого ядра Varnish, надавши розробникам можливість розгортати власний VCL-код на всіх точках присутності. Але VCL залишався мовою керування кешем: у ньому було вкрай складно виконувати JSON-парсинг, взаємодіяти зі сторонніми API через підзапити, керувати станом чи писати повноцінну бізнес-логіку додатків.

## Важкі контейнери на краю: AWS Lambda@Edge (2016–2017)

З появою безсерверної парадигми FaaS у центральних хмарах виникла ідея перенести функції на крайові локації. Наприкінці 2016 року Amazon Web Services анонсувала сервіс **AWS Lambda@Edge**, інтегрований із CDN CloudFront.

Lambda@Edge дозволяла виконувати код на JavaScript (Node.js) або Python у чотирьох точках конвеєра CloudFront:
1. *Viewer Request* — одразу після надходження запиту від клієнта;
2. *Origin Request* — перед зверненням до бекенду при промаху кешу;
3. *Origin Response* — після отримання відповіді від бекенду;
4. *Viewer Response* — перед відправленням відповіді клієнту.

Однак архітектура Lambda@Edge успадкувала традиційну контейнерну модель централізованої AWS Lambda. Кожен виклик потребував виділення контейнера або MicroVM, завантаження повного середовища виконання Node.js та ініціалізації модулів.

```
Традиційний FaaS на краю (AWS Lambda@Edge):
[Edge PoP] ──(Холодний старт)──► [Запуск MicroVM / Node.js (150–350 мс)] ──► handler()
```

Це спричинило нездоланний інженерний конфлікт:
- Мета крайових обчислень — зменшити затримку до 5–15 мс;
- Холодний запуск контейнера з повним Node.js займав від 150 до 500 мс;
- Розмазування сотень тисяч функцій користувачів по сотнях PoP призводило до того, що більшість викликів на окремому сервері потрапляли на холодний старт через рідкісність звернень на конкретній локації.

Крім того, через високі вимоги до оперативної пам'яті (від 128 МБ на контейнер) AWS була змушена запускати важкі функції лише на обмеженій кількості регіональних кешів (англ. *Regional Edge Caches*), а не на всіх без винятку крайових точках останньої милі.

## Прорив V8 Isolates: Cloudflare Workers (2017)

У 2017 році команда інженерів Cloudflare під керівництвом Кентона Варди (Kenton Varda, автора протоколу Cap'n Proto та колишнього інженера Google) запропонувала фундаментально іншу модель ізоляції.

Замість того, щоб створювати віртуальні машини або процеси операційної системи для кожного користувача, було вирішено запускати код усередині єдиного системного процесу за допомогою **V8 Isolates** — технології ізоляції пам'яті, розробленої командою Google Chromium для браузера Chrome.

```
Порівняння підходів ізоляції:
Контейнери / MicroVM (2016):  [Ядро Linux] ──► [Процес VM 1 (35 МБ)] + [Процес VM 2 (35 МБ)]
V8 Isolates (2017):           [Один процес] ──► [Isolate A (1.5 МБ)] + [Isolate B (1.5 МБ)]
```

Переваги моделі Isolates змінили правила гри:
- **Час запуску менше 5 мілісекунд**: створення ізоляту V8 полягає у виділенні нового адресного простору купи (англ. *Heap*) всередині вже працюючого рушія, що не потребує системних викликів `fork()` чи завантаження ядра Linux;
- **Мінімальний обсяг пам'яті**: один ізолят споживає лише 1–3 МБ оперативної пам'яті;
- **Справжня багатоорендність (Multi-tenancy)**: на одному стандартному сервері PoP стало можливим одночасно утримувати десятки тисяч активних ізолятів різних клієнтів без ризику вичерпання RAM.

Ключовим викликом для моделі Isolates стали апаратні атаки побічними каналами (Spectre та Meltdown у 2018 році). Оскільки код різних клієнтів виконувався в одному процесі ОС, теоретично зловмисник міг через спекулятивне виконання процесора зчитати байти сусіднього ізоляту. Інженери Cloudflare розв'язали цю проблему комплексом заходів:
1. Вимкненням таймерів високої точності (`performance.now()` отримав штучний шум і округлення), що позбавило атакуючих можливості вимірювати мікросекундні затримки кешу CPU;
2. Апаратним стисненням вказівників (англ. *Pointer Compression*) у 32-розрядному вікні всередині 64-розрядного простору, що апаратно блокувало вихід за межі виділеної 4-гігабайтної зони пам'яті ізоляту;
3. Розподілом функцій неперевірених клієнтів по окремих ізольованих процесах пулу.

Cloudflare Workers обрали стандартизоване API Service Worker (`FetchEvent`, `Request`, `Response`, `Streams`), яке веб-розробники вже добре знали з браузерного середовища.

## Епоха WebAssembly: Fastly Lucet та Wasmtime (2019)

Незважаючи на успіх V8, JavaScript залишався мовою з динамічною типізацією та накладними витратами на інтерпретацію, JIT-компіляцію та збирання сміття (англ. *Garbage Collection*, GC). У 2019 році компанія Fastly представила платформу **Compute@Edge**, засновану на власному відкритому компіляторі та середовищі виконання **Lucet**, яке згодом об'єдналося з проєктом **Wasmtime** під парасолькою альянсу Bytecode Alliance (за участі Mozilla, Fastly, Intel та Red Hat).

```
Складання та запуск WebAssembly на краю:
[Код на Rust / C / Go] ──(wasm32-wasi)──► [Байткод .wasm] ──(AOT/JIT на PoP)──► [Запуск за 35 мікросекунд]
```

WebAssembly (Wasm) надав крайовим функціям нові властивості:
- **Ініціалізація за десятки мікросекунд**: завдяки випереджальній компіляції Ahead-of-Time (AOT) модуль Wasm завантажується та запускається швидше, ніж надходить наступний мережевий пакет TCP;
- **Багатомовність**: розробники отримали змогу писати високопродуктивні крайові сервіси на системних мовах (Rust, C, C++, Go, Zig);
- **Сувора ізоляція пам'яті на рівні байткоду**: кожен модуль Wasm має доступ виключно до свого лінійного масиву байтів (англ. *Linear Memory Sandbox*). Звернення за межі цього масиву апаратно перехоплюються за допомогою захисних сторінок пам'яті (Guard Pages), що унеможливлює атаки на переповнення буфера та витоки чужих даних;
- **Модель можливостей WASI**: системний інтерфейс WebAssembly (WASI) реалізує безпеку на основі мандатів (англ. *Capability-based Security*), де програма не має доступу до жодних системних ресурсів, якщо вони явно не передані хостовим середовищем.

## Стандартизація: створення WinterCG (2022)

Бурхливий розвиток ізольованих середовищ від Cloudflare, Fastly, Deno Deploy, Vercel та Netlify спричинив фрагментацію API: кожен постачальник реалізовував власні специфічні розширення для роботи з мережею та заголовками.

У 2022 році під егідою W3C була сформована робоча група **WinterCG** (англ. *Web-interoperable Runtimes Community Group*), куди увійшли представники Cloudflare, Fastly, Deno, Node.js, Vercel та Shopify. 

```
Єдиний стандарт середовищ виконання WinterCG:
┌──────────────────────────────────────────────────────────┐
│              Спільні стандарти Web API                   │
│  Fetch API (Request/Response) · Web Crypto · Streams     │
│  URL · EventTarget · TextEncoder/Decoder · Web Standards │
├────────────┬─────────────┬─────────────┬─────────────────┤
│ Cloudflare │ Deno Deploy │   Fastly    │  Vercel Edge /  │
│  Workers   │   Runtime   │ Compute@Edge│  Node.js (Core) │
└────────────┴─────────────┴─────────────┴─────────────────┘
```

WinterCG зафіксувала перелік обов'язкових Web API, які повинні підтримуватися будь-яким серверним середовищем виконання без прив'язки до застарілих інтерфейсів POSIX чи прив'язаних до ОС Node.js API (`fs`, `net`, `child_process`). Крайові функції остаточно стали уніфікованим стандартом сучасної розподіленої архітектури.
