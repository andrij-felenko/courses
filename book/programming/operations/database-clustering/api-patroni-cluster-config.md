# 📋 Специфікація координації Patroni: конфігурація DCS, стан вузла та маршрутизація проксі

Для побудови надійного відмовостійкого кластера на базі реляційної СУБД (зокрема PostgreSQL) необхідний зовнішній супервізор, який бере на себе автоматичне управління життєвим циклом інстансів: вибори лідера, конфігурацію потокової реплікації, моніторинг стану та взаємодію з розподіленим сховищем консенсусу (DCS). Стандартом де-факто в інженерній практиці є **Patroni** — керуючий демон кластера, що забезпечує консенсус на базі `etcd` або `Consul`.

Нижче наведено машинну специфікацію конфігураційного контракту Patroni, структуру ключів і значень у DCS, специфікацію HTTP REST API для перевірки здоров'я, детальні протоколи зміни станів та еталонну конфігурацію балансувальника HAProxy для розділення потоків читання і запису.

## 1. Декларативна схема конфігурації `patroni.yml`

Конфігураційний файл `patroni.yml` визначає параметри інтеграції з DCS, налаштування самого рушія бази даних, таймери ліз та правила поведінки вузла в кластері. Кожен параметр конфігурації має суворе призначення та безпосередньо впливає на час виявлення аварій (RTO) та гарантії збереження транзакцій (RPO).

```yaml
# ==============================================================================
# ДЕКЛАРАТИВНА СПЕЦИФІКАЦІЯ ВУЗЛА КЛАСТЕРА PATRONI v3.x
# ==============================================================================
scope: postgres-ha-cluster          # Унікальний префікс кластера в просторі ключів DCS
namespace: /service                 # Кореневий простір імен у DCS
name: pg-node-01                    # Унікальне ім'я поточного вузла в кластері

# ── 1.1. Інтеграція з розподіленим сховищем консенсусу (DCS) ─────────────────
etcd3:
  hosts:
    - 10.0.1.11:2379
    - 10.0.1.12:2379
    - 10.0.1.13:2379
  cacert: /etc/patroni/certs/etcd-ca.crt
  cert: /etc/patroni/certs/patroni-client.crt
  key: /etc/patroni/certs/patroni-client.key

# ── 1.2. Динамічна конфігурація кластера (зберігається в DCS) ────────────────
dcs:
  ttl: 10                           # Час життя лізи лідера в секундах
  loop_wait: 2                      # Інтервал циклу опитування та оновлення серцебиття (сек)
  retry_timeout: 4                  # Таймаут на повторні спроби запису в DCS перед панікою (сек)
  maximum_lag_on_failover: 1048576  # Максимально дозволене відставання репліки для виборів (1 МБ)
  synchronous_mode: true            # Увімкнення синхронної реплікації (Strict Sync)
  synchronous_mode_strict: false    # Чи блокувати запис, якщо всі репліки впали
  synchronous_node_count: 1         # Кількість синхронних реплік, необхідних для підтвердження

  # Шаблон ініціалізації первинного кластера
  bootstrap:
    dcs:
      postgresql:
        use_pg_rewind: true         # Автоматичне вирівнювання розбіжних форків WAL
        use_slots: true             # Використання фізичних слотів реплікації
        parameters:
          wal_level: replica
          max_wal_senders: 10
          max_replication_slots: 10
          hot_standby: "on"
          hot_standby_feedback: "on"
          wal_log_hints: "on"
          archive_mode: "on"
          archive_command: "pgbackrest --stanza=main archive-push %p"
          shared_preload_libraries: "pg_stat_statements"

    initdb:
      - encoding: UTF8
      - data-checksums              # Контрольні суми сторінок для виявлення пошкоджень диска

    pg_hba:
      - host replication replicator 10.0.1.0/24 md5
      - host all all 10.0.1.0/24 md5
      - local all all trust

# ── 1.3. Специфікація локального рушія PostgreSQL ─────────────────────────────
postgresql:
  listen: 10.0.1.21:5432
  connect_address: 10.0.1.21:5432
  data_dir: /var/lib/postgresql/16/main
  bin_dir: /usr/lib/postgresql/16/bin
  pgpass: /var/lib/postgresql/.pgpass

  authentication:
    replication:
      username: replicator
      password: "StrongReplicationSecretPassword123"
    superuser:
      username: postgres
      password: "StrongSuperuserSecretPassword123"

# ── 1.4. Апаратне та програмне огородження (Watchdog) ────────────────────────
watchdog:
  mode: automatic                   # Використання ядра Linux /dev/watchdog
  device: /dev/watchdog
  safety_margin: 5                  # Запас часу до спрацювання апаратного ресету (сек)

# ── 1.5. REST API інтерфейс для перевірок здоров'я ───────────────────────────
restapi:
  listen: 10.0.1.21:8008
  connect_address: 10.0.1.21:8008
  authentication:
    username: patroni_monitor
    password: "MonitorSecretPassword123"

# ── 1.6. Теги та поведінкові прапорці вузла ──────────────────────────────────
tags:
  nofailover: false                 # Чи заборонено вузлу ставати лідером (Primary)
  noloadbalance: false              # Чи виключати вузол із пулу балансування читання
  nosync: false                     # Чи заборонено бути синхронною реплікою
  clonefrom: false                  # Чи заборонено іншим вузлам клонуватися з цього
```

### 1.7. Детальний аналіз ключових параметрів конфігурації

Кожен блок конфігурації відповідає за ізольовану підсистему життєдіяльності кластера. Неправильне розуміння взаємозв'язку між цими параметрами призводить до нестабільності кластера під навантаженням:

1. **Параметр `scope` та простір імен `namespace`:**
   Визначають ізоляцію кластера в спільному сховищі консенсусу. Якщо кілька незалежних кластерів (наприклад, кластер білінгу та кластер аналітики) використовують один ансамбль `etcd`, значення `scope` слугує кореневим роздільником ключів. Будь-яка помилка в назві `scope` призведе до того, що вузол спробує ініціалізувати новий незалежний кластер або приєднатися до чужого дерева ключів.

2. **Інтервал циклу `loop_wait` та час життя лізи `ttl`:**
   Параметр `loop_wait` задає періодичність, з якою керуючий демон прокидається для виконання трьох обов'язкових операцій: перевірки локального процесу СУБД через сокет, запису актуального LSN у ключ вузла та продовження терміну дії оренди ключа лідера (`heartbeat`). Параметр `ttl` визначає максимальний час, протягом якого ліза залишається валідною в `etcd` за відсутності оновлень. Якщо `loop_wait` становить 2 секунди, а `ttl` — 10 секунд, це означає, що лідер має 5 спроб оновити запис до того, як DCS оголосить його мертвим.

3. **Таймаут повторних спроб `retry_timeout`:**
   Визначає ліміт часу, що виділяється демону на виконання транзакцій зв'язку з `etcd`. Якщо мережева затримка між вузлом СУБД та серверами консенсусу перевищує `retry_timeout`, операція вважається проваленою. Це запобігає нескінченному блокуванню керуючого потоку при часткових мережевих збоях.

4. **Поріг відставання `maximum_lag_on_failover`:**
   Задає максимально допустиму різницю в байтах журналу WAL між останнім зафіксованим LSN лідера та позицією репліки. Якщо лідер зазнав аварії, репліка, чиє відставання перевищує це порогове значення (за замовчуванням 1 МБ), добровільно відмовляється від участі у виборах нового лідера. Це гарантує, що вузол із суттєвим відставанням не буде випадково обраний лідером, що мінімізує обсяг потенційно втрачених даних при асинхронній реплікації.

5. **Режими синхронної реплікації (`synchronous_mode` та `synchronous_mode_strict`):**
   У режимі `synchronous_mode: true` Patroni автоматично формує та динамічно оновлює параметр PostgreSQL `synchronous_standby_names`. Коли активна репліка виходить із ладу, супервізор обирає наступну доступну репліку та перезаписує конфігурацію без перезавантаження СУБД. Прапорець `synchronous_mode_strict` контролює поведінку кластера, коли в строю не залишилося жодної живої репліки: якщо він вимкнений (`false`), кластер тимчасово деградує до асинхронного режиму, зберігаючи доступність на запис; якщо увімкнений (`true`), первинний вузол блокує всі операції запису, доки не з'явиться підтверджена репліка, надаючи абсолютний пріоритет збереженню консистентності даних.

## 2. Ієрархія та контракт структури ключів у DCS (`etcd`)

Усі вузли кластера постійно синхронізують свій стан через ієрархічне дерево ключів у просторі `/service/<scope>/`. Механізм консенсусу `etcd` використовує операції порівняння зі збереженням (Compare-And-Swap, CAS), що гарантує атомарність зміни стану навіть за одночасних спроб кількох кандидатів перехопити лідерство.

```
/service/postgres-ha-cluster/
├── leader                  [Ключ лізи лідера: містить ім'я поточного Primary, прив'язаний до Lease ID]
├── initialize              [Маркер первинної ініціалізації: створюється першим вузлом initdb]
├── config                  [Глобальна динамічна конфігурація кластера в форматі JSON]
├── optime/
│   └── leader              [Останній підтверджений LSN лідера для верифікації реплік]
├── sync                    [Список синхронних вузлів, сформований лідером]
├── history                 [Історія змін ліній часу (Timelines) після процедур промоції]
├── failover                [Тимчасовий ключ для ініціації планового або аварійного перемикання]
└── members/
    ├── pg-node-01          [JSON-стан вузла 1: роль, адреси, стан процесу, поточний LSN]
    ├── pg-node-02          [JSON-стан вузла 2: роль, адреси, стан процесу, поточний LSN]
    └── pg-node-03          [JSON-стан вузла 3: роль, адреси, стан процесу, поточний LSN]
```

### 2.1. Контракт і семантика ключів

| Шлях ключа в `etcd` | Тип операції | TTL | Опис і семантичний зміст |
|---|---|---|---|
| `/service/<scope>/leader` | CAS (Compare-And-Swap) | `ttl` (10s) | Ім'я поточного лідера (Primary). Оновлюється тільки власником лізи кожні `loop_wait` секунд через транзакцію продовження оренди. |
| `/service/<scope>/members/<name>` | PUT (Heartbeat) | `ttl` (10s) | Метадані та стан конкретного вузла (роль, LSN, адреса підключення, версія). Зникає автоматично при зупинці вузла. |
| `/service/<scope>/optime/leader` | PUT | Немає | Останній записаний LSN (Log Sequence Number) лідера для обчислення відставання кандидатами. |
| `/service/<scope>/sync` | PUT | Немає | Список призначених синхронних реплік, зафіксований лідером для координації кворуму. |
| `/service/<scope>/failover` | WATCH / DELETE | Немає | Команда на ручне перемикання (Switchover/Failover), створена утилітою `patronictl`. |
| `/service/<scope>/history` | APPEND | Немає | Журнал змін ліній часу (Timelines) PostgreSQL після промоцій нових лідерів. |

### 2.2. Формат документа члена кластера (`/members/<name>`)

Кожен вузол кластера кожні `loop_wait` секунд оновлює свій документ у директорії `/members/`. Документ містить вичерпні дані, необхідні іншим учасникам для маршрутизації та обрання лідера:

```json
{
  "conn_url": "postgres://10.0.1.21:5432/postgres",
  "api_url": "http://10.0.1.21:8008/patroni",
  "state": "running",
  "role": "primary",
  "version": "3.2.0",
  "timeline": 3,
  "xlog_location": 28521267200,
  "tags": {
    "nofailover": false,
    "noloadbalance": false,
    "nosync": false,
    "clonefrom": false
  }
}
```

Поле `xlog_location` (або `lsn`) представляє 64-бітне ціле число — десятковий еквівалент шістнадцяткового LSN (наприклад, `6/A34B2000`). Під час виборів кандидати зчитують це значення: кандидат, у якого `xlog_location` менший за останню відому позицію лідера більше ніж на `maximum_lag_on_failover` байтів, автоматично дискваліфікується.

Поле `state` сигналізує про поточну фазу життєвого циклу рушія бази даних. Воно може приймати такі дискретні значення:
- `running`: база даних повністю функціональна, відкрита для з'єднань і виконує свою роль.
- `stopped`: процес СУБД зупинено штатно (наприклад, для технічного обслуговування).
- `starting`: триває процес запуску рушія, відтворення контрольної точки або завантаження спільних буферів.
- `crashed`: процес СУБД завершився аварійно, супервізор виконує діагностику та спробу перезапуску.
- `creating_replica`: вузол виконує первинне клонування бази даних за допомогою утиліти `pg_basebackup` або `pgbackrest`.

## 3. Специфікація HTTP REST API ендпоінтів

Демон Patroni публікує локальний HTTP REST API на порті `:8008`. Цей інтерфейс виконує подвійну роль: він є точкою входу для системних адміністраторів (управління через CLI `patronictl`) та машинним контрактом для балансувальників навантаження (HAProxy, Envoy, ProxySQL, Keepalived).

```
       ┌────────────────────────┐
       │   HAProxy Health Check │
       └───────────┬────────────┘
                   │
         HTTP GET  │ /primary (порт :8008)
                   ▼
       ┌────────────────────────┐
       │   Patroni REST API     │
       │   HTTP 200 -> Primary  │
       │   HTTP 503 -> Standby  │
       └────────────────────────┘
```

Балансувальники використовують прості GET-запити: якщо вузол відповідає HTTP-кодом `200 OK`, балансувальник направляє клієнтський трафік на відповідний PostgreSQL-порт (`5432`). Якщо ендпоінт повертає `503 Service Unavailable`, балансувальник негайно виключає вузол із пулу маршрутизації.

### 3.1. Таблиця ендпоінтів моніторингу та маршрутизації

| HTTP Ендпоінт | Очікувана роль інстансу | Код 200 OK | Код 503 Service Unavailable |
|---|---|---|---|
| `GET /primary` | Primary (Master) | Вузол є активним лідером, володіє чинною лізою в DCS і відкритий для читання та запису. | Вузол є реплікою (Standby), перебуває в стані ініціалізації або демон зупинено. |
| `GET /replica` | Standby (Replica) | Вузол є реплікою, перебуває в стані відтворення потоку WAL і готовий обслуговувати read-only запити. | Вузол є лідером (Primary), має відставання більше ніж `max_lag`, або сервіс не працює. |
| `GET /replica?lag=10MB` | Репліка з обмеженням лагу | Репліка відстає від лідера не більше ніж на 10 МБ. | Відставання перевищує поріг або вузол не є реплікою. |
| `GET /read-only` | Будь-який читабельний вузол | Вузол здатний виконувати операції читання (і Primary, і здорові Replicas). | База даних недоступна або перебуває в стані екстреного відновлення. |
| `GET /health` | Працездатність процесу | Процес PostgreSQL запущений і відповідає на сигнальні запити. | Процес СУБД впав або завис. |
| `GET /patroni` | Інформаційний статус | Завжди повертає повний JSON-звіт про поточний стан інстансу, лінійку часу та LSN. | Повертається лише при критичному збої самого демона Patroni. |

### 3.2. Ендпоінти адміністративного управління кластером

Крім моніторингу, REST API підтримує виконання керуючих операцій через POST-запити. Ці виклики захищаються HTTP Basic Authentication і дозволяють змінювати конфігурацію або запускати процедури передачі лідерства:

1. **`POST /switchover` — Планове перемикання лідера:**
   Ініціює керовану передачу ролі Primary без втрати транзакцій. Тіло запиту передає імена старого та нового лідера:
   ```json
   {
     "leader": "pg-node-01",
     "candidate": "pg-node-02",
     "scheduled_at": "2026-08-20T03:00:00+00:00"
   }
   ```
   Якщо поле `scheduled_at` не вказане, перемикання виконується негайно. Демон на старому лідері переводить PostgreSQL у режим `read-only`, скидає залишки WAL у реплікаційний потік, передає ключ лідера в DCS і чекає завершення промоції кандидата.

2. **`POST /failover` — Аварійна промоція вузла:**
   Використовується для примусового призначення лідера у випадках, коли старий лідер фізично знищений і не може відповісти на команду `switchover`.

3. **`POST /restart` та `POST /reload`:**
   Виконують перезапуск процесу PostgreSQL або перечитування параметрів конфігурації без переривання роботи керуючого демона Patroni. Підтримують параметр `role`, що дозволяє перезапустити виключно всі репліки або тільки поточного лідера.

4. **`POST /reinit` — Повна повторна ініціалізація пошкодженої репліки:**
   Зупиняє локальну СУБД, повністю очищає каталог даних `data_dir` та запускає клонування свіжої копії бази даних із діючого лідера за допомогою `pg_basebackup`.

## 4. Еталонна конфігурація маршрутизатора HAProxy (`haproxy.cfg`)

Для забезпечення безперервної доступності та коректного розподілу з'єднань між сервісом запису (Write Pool) та масштабованим пулом читання (Read Pool) застосовується HAProxy. Балансувальник налаштовується на два незалежні фронтенди, які періодично опитують REST API Patroni через механізм `http-check`.

```haproxy
# ==============================================================================
# HAPROXY CONFIGURATION FOR POSTGRESQL + PATRONI HA CLUSTER
# ==============================================================================
global
    log /dev/log local0 info
    maxconn 10000
    user haproxy
    group haproxy

defaults
    log global
    mode tcp
    option tcplog
    option dontlognull
    retries 3
    timeout connect 5000ms
    timeout client 50000ms
    timeout server 50000ms

# ── 4.1. Фронтенд та бекенд для ЗАПИСУ (Primary / RW Pool, Порт 5000) ────────
frontend pg_cluster_write_front
    bind *:5000
    default_backend pg_cluster_write_back

backend pg_cluster_write_back
    mode tcp
    option httpchk GET /primary
    http-check expect status 200
    default-server inter 2s fall 3 rise 2 on-marked-down shutdown-sessions
    
    server pg-node-01 10.0.1.21:5432 maxconn 200 check port 8008
    server pg-node-02 10.0.1.22:5432 maxconn 200 check port 8008
    server pg-node-03 10.0.1.23:5432 maxconn 200 check port 8008

# ── 4.2. Фронтенд та бекенд для ЧИТАННЯ (Replicas / RO Pool, Порт 5001) ───────
frontend pg_cluster_read_front
    bind *:5001
    default_backend pg_cluster_read_back

backend pg_cluster_read_back
    mode tcp
    balance roundrobin
    option httpchk GET /replica
    http-check expect status 200
    default-server inter 2s fall 3 rise 2
    
    server pg-node-01 10.0.1.21:5432 maxconn 500 check port 8008
    server pg-node-02 10.0.1.22:5432 maxconn 500 check port 8008
    server pg-node-03 10.0.1.23:5432 maxconn 500 check port 8008
```

### 4.3. Механізм розриву сесій (`on-marked-down shutdown-sessions`)

Директива `on-marked-down shutdown-sessions` є критично важливим елементом захисту від прихованого розщеплення сесій. Розглянемо сценарій її дії:

1. Застосунок відкрив довготривалу транзакцію на запис на порті `5000` (через який трафік ішов на Вузол 1).
2. На Вузлі 1 виникає необхідність планового обслуговування, і адміністратор запускає switchover.
3. Демон Patroni на Вузлі 1 переводить PostgreSQL у режим `read-only` і змінює відповідь ендпоінта `/primary` з `200 OK` на `503 Service Unavailable`.
4. HAProxy під час чергової перевірки (через 2 секунди) фіксує статус `503` і позначає сервер Вузла 1 як недієздатний (`marked DOWN`).
5. За відсутності директиви `shutdown-sessions` HAProxy просто припинив би надсилати *нові* з'єднання на Вузол 1, але залишив би відкритими *старі* TCP-сокети. Клієнтська програма спробувала б виконати наступний SQL-запит `UPDATE` у межах відкритої сесії й отримала б помилку `ERROR: cannot execute UPDATE in a read-only transaction`.
6. За наявності директиви `on-marked-down shutdown-sessions` HAProxy негайно надсилає пакет `TCP RST` усім клієнтам, підключеним до старого сервера. Клієнтський пул з'єднань отримує сигнал про розрив сокета, негайно перепідключається до порту `5000` і прозоро потрапляє на щойно обраний новий Primary-сервер (Вузол 2).

## 5. Таблиця станів і часових лімітів огородження (Watchdog)

Для запобігання розщепленню мозку (Split-Brain) при виникненні тривалих пауз збирача сміття (GC) або зависанні операційної системи, Patroni реалізує жорстку математичну залежність між таймерами DCS та апаратним сторожовим таймером Linux Watchdog.

```
       T_loop = 2s          T_retry = 4s           T_ttl = 10s
    ├─────────────────┼──────────────────────┼───────────────────────┤
    Heartbeat OK      DCS повільний / збій   Ліза втрачена           Watchdog Panic
                                             Вузол знімає статус     Hard Reboot
```

| Параметр конфігурації | Рекомендоване значення | Призначення та фізичний зміст |
|---|---|---|
| `dcs.loop_wait` | `2s` | Базовий інтервал циклу. Кожні 2 секунди демон надсилає серцебиття в `etcd` для продовження лізи. |
| `dcs.retry_timeout` | `4s` | Ліміт очікування відповіді від DCS. Якщо мережа дала збій, демон робить повторні спроби протягом 4 секунд. |
| `dcs.ttl` | `10s` | Загальний час оренди лідерства. Якщо за 10 секунд лідер не оновив ключ, він вважається мертвим. |
| `watchdog.safety_margin`| `5s` | Запас безпеки: `watchdog_timeout = loop_wait + safety_margin = 7s`. Якщо демон завис і не оновив `/dev/watchdog` за 7 секунд, ядро ініціює апаратний перезапуск хоста ДО того, як закінчиться `ttl` (10s) і кластер обере нового лідера. |

### 5.1. Математичне обґрунтування часової формули безпеки

Формула розрахунку інтервалів сторожового таймера будується на суворій нерівності:

```
T_loop + T_safety_margin < T_ttl
```

де:
- `T_loop` (2 секунди) — нормальний час оновлення сторожового таймера;
- `T_safety_margin` (5 секунд) — час, протягом якого система намагається відновити зв'язок або виконати коректне зняття повноважень лідера;
- `T_watchdog_timeout = T_loop + T_safety_margin = 7 секунд` — апаратний таймаут драйвера `/dev/watchdog`;
- `T_ttl` (10 секунд) — момент, коли `etcd` оголошує лізу вільною і дозволяє реплікам обрати нового лідера.

Якщо операційна система старого лідера зависає на рівні ядра (Kernel Hang) на 0-й секунді:
1. На 7-й секунді спрацьовує апаратний сторожовий таймер материнської плати або віртуального пристрою гіпервізора, і старий сервер зазнає примусового холодного перезапуску (Hard Reset / STONITH).
2. На 10-й секунді в `etcd` закінчується термін оренди ключа `/service/postgres-ha-cluster/leader`.
3. На 11-й секунді репліка (Вузол 2) фіксує відсутність лізи, перевіряє свій LSN і успішно просувається до ролі Primary.

Оскільки `7 < 10`, новий лідер ні за яких умов не зможе почати приймати транзакції до того, як старий лідер буде гарантовано знеструмлений або перезавантажений. Це математично унеможливлює виникнення паралельних гілок запису в розподіленій системі.

## 6. Алгоритм виборів лідера та верифікація LSN

Коли ключ `/service/<scope>/leader` у DCS стає вільним (унаслідок штатного зняття повноважень або спливання TTL), усі діючі репліки одночасно переходять у стан змагання за лідерство (Leader Election State). Процедура виборів є суворо детермінованою і запобігає промоції вузлів із застарілими даними:

```
[ Ліза вільна в DCS ]
         │
         ▼
[ Кандидат зчитує /optime/leader ]
         │
         ├──► LSN_candidate >= LSN_leader - max_lag? ──► [НІ] ──► Дискваліфікація
         │
        [ТАК]
         │
         ▼
[ Спроба атомарного CAS-запису в etcd ]
         │
         ├──► Успіх (Key Created)? ──► [ТАК] ──► [ Промоція: pg_ctl promote ]
         │
        [НІ: інший вузол встиг першим]
         │
         ▼
[ Перехід у режим реплікації від нового лідера ]
```

### 6.1. Покроковий протокол перевірки кандидата

1. **Фаза зчитування позиції:**
   Кандидат зчитує значення ключа `/service/<scope>/optime/leader`, у якому зафіксовано останній відомий LSN попереднього лідера. Одночасно кандидат визначає власний локальний LSN через системний виклик PostgreSQL `pg_last_wal_replay_lsn()`.

2. **Фаза валідації безпеки (Safety Check):**
   Кандидат обчислює різницю `delta = LSN_leader - LSN_local`. Якщо `delta > maximum_lag_on_failover` (наприклад, більше 1 МБ), кандидат вибуває з перегонів, щоб не спричинити відкату підтверджених бізнес-транзакцій.

3. **Фаза атомарного захоплення (Atomic CAS):**
   Якщо кандидат відповідає критеріям свіжості, він надсилає в `etcd` запит створення ключа `/service/<scope>/leader` із власним ім'ям та умовою `CreateRevision == 0` (або `version == 0`). Лише один вузол у кластері отримає успішну відповідь від консенсусного кворуму `etcd`.

4. **Фаза промоції (Local Promotion):**
   Вузол-переможець створює файл-тригер або викликає команду `pg_ctl promote`. PostgreSQL перемикає лінію часу (створює новий Timeline ID, наприклад, перехід із `00000003.history` на `00000004.history`), відкриває локальні файли даних на запис і починає приймати клієнтські транзакції.

5. **Фаза адаптації переможених (Follower Realignment):**
   Усі інші репліки бачать новий запис у `/service/<scope>/leader`, формують оновлений рядок підключення `primary_conninfo` із новою адресою лідера та надсилають команду `pg_reload_conf()`. Реплікаційний процес `walreceiver` встановлює TCP-з'єднання з новим лідером і починає викачувати новий потік WAL.

## 7. Архітектура інтеграції з пулерами з'єднань PgBouncer

У високонавантажених виробничих середовищах застосунки рідко підключаються безпосередньо до портів PostgreSQL. Оскільки кожен процес-обробник PostgreSQL споживає від 5 до 20 МБ оперативної пам'яті на сесію, пряме створення тисяч з'єднань швидко призводить до виснаження пам'яті хоста та деградації контекстних перемикань процесора.

Для оптимізації застосовується проміжний шар **PgBouncer**, що розгортається локально на кожному вузлі кластера або як окремий рівень сервісу.

```
[ Застосунки ] ──► [ HAProxy :5000 ] ──► [ PgBouncer :6432 ] ──► [ PostgreSQL :5432 (Primary) ]
```

### 7.1. Конфігурація пулера для роботи в кластері

У файлі `pgbouncer.ini` налаштовується транзакційний пул (`pool_mode = transaction`), який дозволяє тисячам клієнтських веб-потоків ділити невеликий пул (наприклад, 50-100) постійних відкритих з'єднань до рушія СУБД:

```ini
[databases]
* = host=127.0.0.1 port=5432 auth_user=postgres

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 5000
default_pool_size = 50
min_pool_size = 10
reserve_pool_size = 5
reserve_pool_timeout = 5
server_reset_query = DISCARD ALL
server_check_delay = 10
server_check_query = SELECT 1
```

Директива `server_reset_query = DISCARD ALL` гарантує, що після завершення транзакції тимчасові таблиці, підготовлені вирази (Prepared Statements) та змінні сесії скидаються, перш ніж серверне з'єднання буде передане наступному клієнтському запиту.

Коли Patroni змінює роль локального вузла з Primary на Standby, він автоматично викликає системний хук `on_demote`, який виконує команду `PAUSE` або зупиняє локальний PgBouncer, запобігаючи виконанню помилкових записів через застарілі пул-з'єднання.
