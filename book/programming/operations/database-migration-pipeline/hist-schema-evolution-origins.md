# 📜 Від ручних SQL-скриптів DBA до gh-ost та протоколу F1: історія еволюції схем даних

Еволюція структури реляційних баз даних пройшла шлях від регламентних нічних вікон обслуговування із зупинкою підприємств до повністю автоматизованих розподілених конвеєрів, здатних модифікувати петабайтні таблиці під піковим навантаженням без жодної мілісекунди простою.

## Епоха монолітних СУБД та нічних регламентних робіт (1970–1990-ті)

У перші десятиліття розвитку реляційних баз даних після публікації фундаментальної праці Едгара Кодда (англ. *Edgar F. Codd*, 1970) модифікація схеми (Data Definition Language, DDL) вважалася виключною прерогативою адміністратора баз даних (DBA). Організаційна структура підприємств базувалася на суворому розподілі обов'язків: розробники передавали текстові файли з SQL-інструкціями команді системної експлуатації, яка виконувала їх вручну через системні термінали.

```text
1980–1990-ті:
  Розробник (SQL-файл) ──> DBA (Ручна перевірка) ──> Нічне вікно (Зупинка бізнесу: 02:00–06:00)
```

Архітектура ранніх версій комерційних СУБД (IBM System R, Oracle v3–v7, IBM DB2, Informix) не передбачала можливості паралельного виконання DDL і DML-запитів. Будь-яка команда `ALTER TABLE` вимагала ексклюзивного блокування всієї таблиці, створення нової фізичної структури на диску, покрокового перекопіювання кожного рядка та повної перебудови всіх залежних B-дерев індексів.

Через це в індустрії закріпилася практика так званих «вікон технічного обслуговування» (англ. *maintenance windows*). Корпоративні додатки повністю вимикалися для користувачів щосуботи о другій годині ночі. Якщо під час застосування чергового SQL-скрипту виникала помилка або вичерпувався дисковий простір для тимчасових сегментів відкату (rollback segments), адміністратор запускав багаточасове відновлення всієї бази з магнітної стрічки, а ранковий запуск системи відкладався, завдаючи бізнесу прямих фінансових збитків.

## Поява версіонування у коді: революція Rails Active Record (2004)

Корінний злам парадигми відбувся у липні 2004 року, коли данський інженер Девід Гайнемаєр Ганссон (дан. *David Heinemeier Hansson*, відомий у спільноті як DHH) випустив веб-фреймворк Ruby on Rails. Ганссон інтегрував механізм міграцій безпосередньо в об'єктно-реляційне відображення Active Record.

```ruby
class AddStatusToOrders < ActiveRecord::Migration[1.0]
  def up
    add_column :orders, :status, :string, default: "pending", null: false
  end

  def down
    remove_column :orders, :status
  end
end
```

Rails увів три фундаментальні принципи, які згодом стали галузевим стандартом для всіх мов програмування:

1. **Міграція як вихідний код у системі контролю версій.** Зміни схеми бази даних перестали бути зовнішніми артефактами і стали повноправними файлами у репозиторії проекту поруч із бізнес-логікою.
2. **Службовий реєстр виконаних змін.** У базу даних впровадили системну таблицю `schema_migrations`, що фіксувала версії застосованих файлів. Фреймворк автоматично визначав різницю між станом репозиторію та станом таблиці й виконував лише відсутні кроки.
3. **Двонаправленість операцій (`up` / `down`).** Кожна міграція описувала як пряму дію (додавання стовпця, створення індексу), так і зворотну операцію відкату (drop column, drop index).

Перші версії міграцій Rails використовували послідовну цілочисельну нумерацію файлів (`001_create_users.rb`, `002_add_email.rb`). Однак зі зростанням команд розробників виникла проблема колізій: двоє інженерів одночасно створювали файли з однаковим префіксом `003` у різних гілках Git. Під час злиття гілок порядок виконання порушувався, що призводило до невідтворюваного стану бази. Для вирішення цього конфлікту в Rails 2.1 (2008 рік) послідовні лічильники замінили на часові мітки UTC формату `YYYYMMDDHHMMSS` (наприклад, `20080906120000_add_email.rb`).

## Індустріальні та платформонезалежні рушії: Liquibase та Flyway (2006–2010)

Успіх підходу Rails спричинив появу спеціалізованих інструментів для корпоративного Java-середовища та гетерогенних корпоративних баз даних, де один додаток міг підтримувати одночасно Oracle, DB2 та PostgreSQL.

У 2006 році американський розробник Натан Воксленд (англ. *Nathan Voxland*) розпочав проект **Liquibase**. На відміну від Rails, орієнтованого на Ruby DSL, Liquibase запропонував декларативний опис змін (Changelogs) у форматах XML, YAML та JSON, що автоматично транслювалися у діалект цільової СУБД. 

Liquibase запровадив концепцію контрольних сум (MD5/SHA-256 хешів) для кожного блоку змін (`changeSet`): якщо розробник змінював тіло вже застосованого файлу міграції у Git, рушій фіксував розбіжність контрольної суми та аварійно зупиняв конвеєр, запобігаючи неконтрольованому розходженню схем між середовищами розробки та продакшном. Крім того, Liquibase запровадив механізм `DATABASECHANGELOGLOCK` — розподілений замок у вигляді системної таблиці, що виключав одночасний запуск міграцій кількома екземплярами додатку.

У 2010 році німецький інженер Аксель Фонтен (фр. *Axel Fontaine*) представив проект **Flyway**. Фонтен зробив ставку на мінімалізм: замість складних абстракцій XML він повернувся до чистого нативного SQL-синтаксису з суворими правилами іменування файлів (`V1__initial_schema.sql`, `U1__undo_initial_schema.sql`, `R__repeatable_view.sql`). Flyway став де-факто стандартом для мікросервісних архітектур на базі JVM та Go завдяки легкості інтеграції в CI/CD та мінімальному споживанню ресурсів.

## Криза блокувань під навантаженням та народження pt-online-schema-change (2009–2012)

З переходом веб-сервісів до масштабу Web 2.0 (Facebook, Twitter, Flickr, YouTube, SoundCloud) обсяги окремих таблиць MySQL сягнули сотень мільйонів та мільярдів рядків. У рушії зберігання MySQL InnoDB виконання звичайної інструкції `ALTER TABLE` вимагало створення тимчасової копії таблиці на диску під ексклюзивним блокуванням таблиці на запис (`TL_WRITE_ALLOW_WRITE` або блокування метаданих MDL).

Для таблиці розміром 500 ГБ операція тривала понад 6 годин. Протягом цього часу всі клієнтські операції `INSERT` та `UPDATE` накопичувалися в черзі очікування, пул з'єднань додатку вичерпувався за 5–10 секунд, і весь сервіс зазнавав глобального каскадного збою.

У 2009 році інженери компанії Shlomi Noach та фахівці Percona під керівництвом Петра Зайцева (англ. *Peter Zaitsev*) і Вадима Ткаченка (англ. *Vadim Tkachenko*) розробили інструмент `pt-online-schema-change`, що увійшов до пакета Percona Toolkit. Майже одночасно інженери SoundCloud випустили власну бібліотеку `Large Hadron Migrator` (LHM) для середовища Ruby. Обидва інструменти базувалися на механізмі асинхронної тіньової копії за допомогою тригерів:

```text
pt-online-schema-change / LHM:
  1. Створення порожньої таблиці _users_new з новою схемою
  2. Встановлення 3 синхронних тригерів на users (AFTER INSERT, AFTER UPDATE, AFTER DELETE)
  3. Чанкове копіювання рядків з users у _users_new (пакетами по 1 000 рядків)
  4. Атомарний RENAME TABLE users TO _users_old, _users_new TO users
  5. Видалення тригерів та фізичне видалення _users_old
```

Цей підхід уперше дозволив виконувати DDL на живій системі без зупинки читання і запису. Проте тригери створювали значні приховані накладні витрати: кожен запис у вихідну таблицю викликав додаткові транзакційні блокування, створюючи ризик взаємних блокувань (deadlocks) та викликаючи небезпечний стрибок навантаження на процесор під час піків трафіку.

## Безтригерна революція: створення gh-ost у надрах GitHub (2016)

У серпні 2016 року інженер інфраструктури баз даних GitHub Шломі Ноах (івр. שלוми נх‎, англ. *Shlomi Noach*) опублікував інструмент **gh-ost** (GitHub Online Schema Transformations).

Працюючи з базами даних GitHub, які обслуговували мільйони git-операцій за секунду, команда зіткнулася з тим, що тригери `pt-online-schema-change` не витримували екстремального навантаження: під час сплесків активності тригери блокували транзакції, що призводило до переповнення пулів підключень та аварійної деградації кластера.

Ноах запропонував принципово нову безтригерну архітектуру (triggerless architecture):

```text
Архітектура gh-ost:
  Primary MySQL ──(Async Replication)──> Replica MySQL
                                              │
                                       (Binlog Streamer)
                                              ▼
  Primary MySQL <──(Batch Insert/DML)── gh-ost Controller
```

Замість впровадження важких тригерів у простір виконання клієнтських транзакцій, `gh-ost` підключався до репліки MySQL як звичайний реплікаційний клієнт, зчитував бінарний журнал подій (binlog) у форматі рядків (`ROW-based replication`) і самостійно перетворював події створення та оновлення записів у відповідні операції над тіньовою таблицею на основному сервері.

Головними інноваціями `gh-ost` стали:
* **Абсолютна безпека основного сервера:** відсутність тригерів виключила ризик взаємних блокувань клієнтських транзакцій.
* **Динамічний тротлінг (Throttling):** контролер щосекунди опитував затримку реплікації (replication lag), кількість потоків InnoDB та використання процесора. Якщо репліки відставали більше ніж на одну секунду, копіювання даних автоматично ставилося на паузу.
* **Можливість інспекції та тестування на репліці:** міграцію можна було повністю прогнати на пасивній репліці зі збереженням зрізу даних для перевірки перед запуском на основній базі.

## Розподілені СУБД та протокол еволюції схем Google F1 (2013–2020-ті)

Паралельно з розвитком реляційних утиліт виник новий виклик: як оновлювати схеми в георозподілених базах даних без єдиного координатора. 

У 2013 році команда Google під керівництвом Ребекки Тафт (англ. *Rebecca Taft*) та Майка Корбетта (англ. *Mike Corbett*) опублікувала протокол *Online, Asynchronous Schema Change in F1*. У розподіленій системі неможливо миттєво оновити схему на всіх вузлах: через затримки мережі частина вузлів обов'язково працює зі схемою версії `v1`, а інша частина вже перейшла на `v2`. Якщо `v1` та `v2` взаємно несумісні, система отримує пошкодження даних (наприклад, вузол `v2` створює унікальний індекс, а вузол `v1` записує дублікат ключа).

Протокол F1 довів, що безпечна зміна схеми в розподіленому середовищі можлива лише за умови введення двох проміжних станів:

```text
Протокол Google F1:
  absent ──> delete-only ──> write-only ──> public
```

1. **Delete-only:** вузли на цьому етапі видаляють записи з нового індексу при операціях `DELETE`, але ще не додають нові ключі при `INSERT`. Це гарантує, що видалені рядки не залишаться «зомбі-записами».
2. **Write-only:** вузли додають нові записи в новий індекс при `INSERT` та оновлюють їх при `UPDATE`, але запити `SELECT` ще не використовують цей індекс для планування запитів.
3. **Public:** після фонового перенесення всіх історичних даних індекс стає загальнодоступним для читання.

Цей математично доведений протокол став основою для рушіїв сучасних NewSQL-систем, зокрема CockroachDB та TiDB.

## Сучасний етап: декларативні конвеєри, статичний лінтинг та тіньові бази

У 2020-х роках фокус інженерної думки змістився з окремих утиліт виконання на побудову наскрізних конвеєрів доставки (Database DevOps / GitOps).

З'явилися спеціалізовані статичні лінтери (наприклад, **Squawk** для PostgreSQL та **Atlas** від компанії Ariga), які парсять абстрактне синтаксичне дерево (AST) SQL-файлів у CI-конвеєрі та блокують Pull Request розробника при виявленні небезпечних операцій:
* додавання стовпця `NOT NULL` без константного значення `DEFAULT` у старих версіях СУБД;
* створення індексу без директиви `CONCURRENTLY` (у PostgreSQL), що захоплює блокування `ShareLock`;
* зміна типу даних стовпця, що викликає повне фізичне перезаписування таблиці на диску.

Розвиток технологій копіювання при записі (Copy-on-Write) та безсерверних хмарних СУБД (Neon, PlanetScale, AWS Aurora) дав змогу інтегрувати в CI/CD конвеєри створення миттєвих ефемерних клонів продакшн-баз даних. Кожен Pull Request розробника автоматично отримує ізольовану копію бази даних, на якій проганяється міграція з вимірюванням реального часу виконання та перевіркою блокувань до потрапляння коду в основну гілку.
