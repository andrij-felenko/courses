# 🧮 Математичні основи узгодженого гешування та ймовірнісної інвалідації

Розподіл ключів між незалежними вузлами кешування та запобігання синхронному вичерпанню терміну дії записів спираються на строгий математичний апарат: теорію узгодженого гешування на дискретному кільці, аналіз порядкових статистик для віртуальних вузлів, поліноміальне ділення CRC16 та ймовірнісну модель завчасного оновлення (алгоритм XFetch).

## 1. Проблема наївного гешування за модулем

У класичній схемі розподілу ключ `k` прив'язується до вузла з індексом `i` за допомогою операції взяття залишку від ділення:

```
i = hash(k) mod N
```

де `N` — поточна кількість активних серверів у кластері, а `hash(k)` — рівномірна геш-функція з простором значень `[0, M - 1]`.

Розглянемо випадок зміни розміру кластера: додавання нового вузла (`N ➔ N + 1`) або відмова наявного (`N ➔ N - 1`). Нехай `P(rehash)` — ймовірність того, що довільно обраний ключ `k` змінить свій цільовий вузол при переході від `N` до `N + 1`.

Припускаючи, що `hash(k)` розподілена рівномірно і незалежно на множині цілих чисел, індекс залишається незмінним лише за умови:

```
hash(k) mod N = hash(k) mod (N + 1)
```

За китайською теоремою про залишки ця рівність виконується для цілих чисел у діапазоні `[0, N · (N + 1) - 1]` лише тоді, коли `hash(k) mod (N · (N + 1)) < N`. Отже, частка ключів, що зберігають свою прив'язку, дорівнює:

```
P(same)
= N / (N · (N + 1))     [підрахунок сприятливих залишків у періоді N·(N+1)]
= 1 / (N + 1)           [скорочення на спільний множник N]
```

Частка ключів, що змінюють своє положення (фактор міграції):

```
P(rehash)
= 1 - P(same)          [ймовірність протилежної події для повної групи]
= 1 - 1 / (N + 1)      [підстановка виведеного значення P(same)]
= N / (N + 1)          [зведення дробів до спільного знаменника N+1]
```

Для кластера з `N = 9` вузлів при додаванні десятого сервера частка переміщених ключів становить `9 / 10 = 90%`. Це означає, що 90% усього обсягу кешу стає миттєво невалідним (Cold Cache Drop), а відповідні запити транслюються на базу даних, викликаючи її падіння.

## 2. Узгоджене гешування на дискретному кільці

Алгоритм узгодженого гешування Каргера (англ. *Consistent Hashing*, Karger et al., 1997) відображає як множину серверів `S = {s₁, s₂, ..., sₙ}`, так і множину ключів `K` на спільний замкнений числовий інтервал — дискретне кільце `C`:

```
C = [0, 2ᵇ - 1]
```

де `b` — розрядність геш-функції (типово `b = 32` для простору `2³² - 1 ≈ 4.29 · 10⁹` точок або `b = 64`).

Геш-функція `h: {S ∪ K} ➔ C` розміщує вузли на кільці:

```
p(sᵢ) = h(sᵢ)
```

Ключ `k` закріплюється за найближчим за годинниковою стрілкою вузлом `s*`:

```
s*(k) = argmin_{s ∈ S} { (h(s) - h(k)) mod 2ᵇ }
```

### Доведення мінімальної міграції при зміні конфігурації

Нехай на кільці розташовано `N` вузлів, які розбивають простір `C` на `N` дуг `(I₁, I₂, ..., Iₙ)`. При додаванні нового вузла `s_{N+1}` його позиція `h(s_{N+1})` випадковим чином потрапляє на одну з наявних дуг `Iⱼ`.

Новий вузол забирає собі лише підінтервал дуги `Iⱼ` від точки свого гешу назад проти годинникової стрілки до попереднього вузла. Усі інші `N - 1` інтервалів залишаються незмінними.

Оскільки геш-функція `h` розподілена рівномірно, математичне сподівання довжини інтервалу, який перехоплює новий вузол, становить:

```
E[ΔI]
= |C| / (N + 1)         [середня довжина інтервалу між N+1 точками на кільці]
```

Відповідно, математичне сподівання частки ключів, що змінюють своє призначення, дорівнює:

```
E[частка міграції]
= E[ΔI] / |C|                           [відношення довжини перехопленого інтервалу до довжини кільця]
= (|C| / (N + 1)) / |C|                 [підстановка математичного сподівання довжини дуги]
= 1 / (N + 1)                           [скорочення константи розміру кільця C]
```

Для кластера з `N = 9` вузлів при додаванні десятого сервера мігрує лише `1 / 10 = 10%` ключів (замість 90% у схемі за модулем). Решта 90% ключів гарантовано продовжують зчитуватися зі своїх попередніх серверів без жодних промахів.

## 3. Дисперсія навантаження та віртуальні вузли

Якщо на кільце помістити лише `N` фізичних точок, дуги між сусідніми серверами будуть суттєво відрізнятися за довжиною через випадковість гешування.

Розглянемо розподіл довжини випадкової дуги на одиничному колі. Нехай `N` точок розміщуються незалежно та рівномірно на інтервалі `[0, 1)`. Вони розбивають коло на `N` інтервалів `L₁, L₂, ..., Lₙ`. Довжина довільного інтервалу `Lᵢ` підпорядковується бета-розподілу `Beta(1, N - 1)` з густиною ймовірності:

```
f(x) = (N - 1) · (1 - x)^{N - 2}
```

Математичне сподівання та дисперсія довжини інтервалу становлять:

```
E[Lᵢ] = 1 / N
Var(Lᵢ) = (N - 1) / (N² · (N + 1)) ≈ 1 / N²
```

Класичний результат теорії ймовірностей для максимуму з `N` експоненційно розподілених інтервалів показує, що відношення максимального навантаження до середнього без віртуальних вузлів прямує до:

```
E[max Lᵢ] / E[Lᵢ] = O(ln N)
```

Це означає, що при `N = 50` фізичних серверах найбільш навантажений вузол отримуватиме в `ln(50) ≈ 3.9` раза більше ключів, ніж середній сервер кластера, що створює критичні гарячі точки перевантаження пам'яті.

### Зменшення дисперсії через віртуальні вузли (Vnodes)

Щоб збалансувати навантаження, кожен фізичний сервер `sᵢ` проєктується на кільце у вигляді множини з `V` **віртуальних вузлів** (англ. *virtual nodes / vnodes*):

```
vnodes(sᵢ) = { h(sᵢ || "#1"), h(sᵢ || "#2"), ..., h(sᵢ || "#V") }
```

Загальна кількість точок на кільці стає рівною `M = N · V`. Частка ключів, що закріплюються за фізичним сервером `sᵢ`, є сумою довжин `V` випадкових некорельованих інтервалів:

```
W(sᵢ) = ∑_{j=1}^{V} L_{i, j}
```

Математичне сподівання сумарного навантаження на фізичний сервер лишається незмінним:

```
E[W(sᵢ)]
= V · (1 / M)           [сума сподівань V однакових випадкових дуг довжиною 1/M]
= V / (N · V)           [підстановка загальної кількості точок M = N·V]
= 1 / N                 [скорочення множника V]
```

Проте дисперсія сумарного навантаження фізичного сервера стрімко зменшується завдяки усередненню `V` незалежних випадкових величин:

```
Var(W(sᵢ))
= ∑_{j=1}^{V} Var(L_{i, j})             [властивість дисперсії суми незалежних випадкових величин]
= V · (1 / M²)                          [підстановка дисперсії довжини однієї дуги простору M]
= V / (N² · V²)                         [підстановка кількості віртуальних точок M = N·V]
= 1 / (N² · V)                          [скорочення множника V у чисельнику й знаменнику]
```

Стандартне відхилення навантаження (середньоквадратична похибка):

```
σ(W)
= √(Var(W(sᵢ)))                         [означення стандартного відхилення через корінь із дисперсії]
= √(1 / (N² · V))                       [підстановка отриманого значення дисперсії]
= 1 / (N · √V)                          [винесення квадрата N з-під знака кореня]
```

Коефіцієнт варіації навантаження (відношення стандартного відхилення до середнього сподіваного навантаження):

```
CV
= σ(W) / E[W(sᵢ)]                       [означення відносного коефіцієнта варіації]
= (1 / (N · √V)) / (1 / N)              [підстановка стандартного відхилення та сподівання]
= 1 / √V                                [скорочення множника N]
```

Застосовуючи нерівність Чернова для суми випадкових величин, отримуємо оцінку ймовірності того, що навантаження на будь-який фізичний сервер відхилиться від середнього більше ніж на частку `ε`:

```
P(|W(sᵢ) - 1/N| ≥ ε · (1/N)) ≤ 2 · exp(- (V · ε²) / 3)
```

Для того щоб гарантувати, що з ймовірністю `1 - δ` жоден із `N` серверів не буде перевантажений більше ніж на `ε = 5%` (`ε = 0.05`), кількість віртуальних вузлів на сервер повинна задовольняти нерівність:

```
V ≥ (3 / ε²) · ln(2 · N / δ)
```

Підставивши типові значення `ε = 0.05`, `N = 20`, `δ = 0.01`:

```
V ≥ (3 / 0.0025) · ln(40 / 0.01) = 1200 · ln(4000) ≈ 1200 · 8.29 ≈ 9950  [консервативна оцінка Чернова]
```

На практиці для некриптографічних геш-функцій (типу MurmurHash3 або FNV-1a) емпірично встановлено, що значення `V ∈ [150, 256]` забезпечує відхилення навантаження менше 3–4% для 99.9% реальних ключів.

## 4. Математика геш-слотів Redis: поліном CRC16

У Redis Cluster замість кільця дійсних чисел використовується дискретний простір із `16 384 = 2¹⁴` слотів. Відображення довільного байтового масиву ключа на цей простір здійснюється через циклічний надлишковий код CRC16.

CRC16 розглядає байти ключа як бітовий поліном `M(x)` над скінченним полем `GF(2)` (де додавання є операцією XOR). Генераторний поліном стандарту CRC-16-CCITT / XMODEM визначається як:

```
G(x) = x¹⁶ + x¹² + x⁵ + 1
```

Шістнадцяткове представлення коефіцієнтів полінома `G(x)` дорівнює `0x1021`. Контрольна сума `R(x)` є залишком від поліноміального ділення вхідного повідомлення, зсунутого на 16 бітів, на генераторний поліном:

```
M(x) · x¹⁶ = Q(x) · G(x) ⊕ R(x)
```

Номер слота `S` обчислюється як побітове «І» між значенням 16-бітного залишку `R(x)` та маскою `0x3FFF` (16383):

```
S = R(x) & 0x3FFF
```

Математичні властивості CRC16 гарантують:
1. Повний лавинний ефект: зміна навіть одного біта в ключі (`user:1` ➔ `user:2`) змінює в середньому 50% бітів у результаті `R(x)`.
2. Рівномірний розподіл: для будь-якої множини послідовних або структурованих ключів залишки `R(x) mod 16384` розподіляються строго рівномірно по всіх 16 384 слотах без утворення кластерів і колізійних ям.

## 5. Ймовірнісна інвалідація: стохастичний аналіз алгоритму XFetch

Для повного усунення проблеми навали запитів (Cache Stampede) без блокування м'ютексів застосовують алгоритм раннього ймовірнісного оновлення **XFetch** (Vattani, Chierichetti, Lowenstein, 2015).

Традиційна перевірка актуальності ключа є детермінованою:

```
is_expired = (now() > expiry)
```

В алгоритмі XFetch функція перевірки перетворюється на стохастичну. Разом зі значенням у кеші зберігається час його обчислення `δ` (затримка виконання запиту в СУБД, в секундах) та час завершення дії `expiry`.

При зчитуванні значення клієнт обчислює ймовірнісну умову завчасного оновлення:

```
now() - β · δ · ln(U) > expiry
```

де:
- `now()` — поточний час у системі (timestamp у секундах);
- `expiry` — запланований час інвалідації ключа (`TTL`);
- `δ` — час, витрачений базою даних на первинне обчислення цього значення (delta time);
- `β > 0` — конфігураційний коефіцієнт агресивності оновлення (типово `β = 1.0`);
- `U ∼ Uniform(0, 1)` — випадкова величина, рівномірно розподілена на відкритому інтервалі `(0, 1)`.

### Математичний механізм поведінки XFetch

Оскільки `U ∈ (0, 1)`, натуральний логарифм `ln(U)` завжди набуває від'ємних значень:

```
ln(U) ∈ (-∞, 0)
```

Отже, доданок `-β · δ · ln(U)` завжди є додатним:

```
-β · δ · ln(U) > 0
```

Ймовірність того, що клієнт ініціює асинхронне оновлення кешу за `t` секунд до настання `expiry` (де `t = expiry - now() > 0`), дорівнює:

```
P(оновлення | t)
= P(now() - β · δ · ln(U) > expiry)     [початкова стохастична умова алгоритму XFetch]
= P(-β · δ · ln(U) > expiry - now())   [перенесення now() у праву частину нерівності]
= P(-β · δ · ln(U) > t)                [підстановка залишкового часу t = expiry - now]
= P(ln(U) < -t / (β · δ))             [ділення на від'ємне число -β·δ з розворотом знака нерівності]
= P(U < exp(-t / (β · δ)))            [експоненціювання обох монотонних частин]
= exp(-t / (β · δ))                   [інтеграл щільності рівномірного розподілу U на відрізку від 0 до exp]
```

### Інтегральна оцінка кількості оновлень при інтенсивності запитів Q

Нехай запити до ключа надходять як пуассонівський процес з інтенсивністю `Q` запитів на секунду. Знайдемо очікувану кількість оновлень `E[N_refresh]`, які будуть ініційовані клієнтами протягом усього періоду наближення до вичерпання `TTL`.

Ймовірність того, що перше оновлення відбудеться в момент часу `t` до завершення `TTL`, визначається інтенсивністю відмов у теорії надійності:

```
λ(t)
= Q · P(оновлення | t)                  [множення інтенсивності вхідного потоку на ймовірність спрацювання]
= Q · exp(-t / (β · δ))                 [підстановка експоненційного закону ймовірності XFetch]
```

Ймовірність того, що до моменту `t` не відбулося жодного оновлення (функція виживання):

```
S(t)
= exp( - ∫_{t}^{∞} λ(u) du )            [інтеграл інтенсивності від поточного моменту t до нескінченності]
= exp( - Q · β · δ · exp(-t / (β · δ)) ) [первісна від експоненти зі збереженням коефіцієнтів]
```

Очікувана кількість повторних обчислень за час `δ` (поки триває перший асинхронний запит до СУБД) становить:

```
E[дублюючих викликів]
= ∫_{0}^{δ} Q · exp(-t / (β · δ)) · S(t) dt [інтегрування добутку потоку на ймовірність виживання]
≤ 1 + O(1 / (Q · β · δ))                    [асимптотична верхня межа інтеграла Пуассона]
```

Це доводить фундаментальну теорему Ваттані:
1. Математичне сподівання кількості оновлень ключа строго прямує до **1** при будь-якій інтенсивності вхідного потоку `Q ➔ ∞`.
2. База даних отримує рівно один виклик на оновлення замість `Q · δ` паралельних запитів.
3. Ймовірність того, що ключ повністю експайриться без попереднього прогріву (`t ≤ 0`), спадає експоненційно як `exp(-Q · β · δ)`. При `Q = 1000 req/s`, `β = 1.0`, `δ = 0.1 s` ця ймовірність становить `exp(-100) ≈ 3.7 · 10⁻⁴⁴`, що гарантує абсолютну відсутність промахів кешу в продакшні.
