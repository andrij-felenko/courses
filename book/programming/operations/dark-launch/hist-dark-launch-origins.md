# 📜 Народження темного запуску: від чату Facebook до Scientist у GitHub

У березні 2008 року інженерна команда соціальної мережі Facebook стояла перед інфраструктурним викликом, який за тодішніми мірками вебтехнологій вважався майже нездійсненним. Мережа налічувала понад 70 мільйонів активних користувачів, а вся її архітектура була побудована навколо класичної безстатусної моделі (англ. *stateless model*): користувач надсилав запит, вебсервер на базі PHP генерував HTML-сторінку, скидав байти у відповідь і негайно закривав з'єднання. Наступним стратегічним релізом компанії мав стати Facebook Chat — вбудована у вебсторінку панель обміну миттєвими повідомленнями.

Для роботи чату вебсервер більше не міг залишатися пасивним генератором розмітки. Клієнтські браузери мали тримати відкритими постійні двосторонні канали зв'язку через тривале HTTP-опитування (технологія Comet / Long Polling), а бекенд мусив щосекунди синхронізувати статус присутності (англ. *presence*) десятків мільйонів людей і миттєво доставляти повідомлення між співрозмовниками. Інженери Facebook спроєктували новий кластер на базі розподіленої функціональної платформи Erlang та низькорівневих C++ проксі-серверів каналів, здатних утримувати сотні тисяч одночасних сокетних підключень.

Головна небезпека полягала в непередбачуваності навантаження та поведінки підключень. Якби чат увімкнули для всіх 70 мільйонів користувачів одним натисканням перемикача вранці, лавиноподібне встановлення сокетів і хвиля запитів присутності знесли б новий бекенд за лічені секунди. Симуляція такого навантаження на синтетичних тестових стендах була принципово неповною: штучні генератори трафіку надсилають рівномірні синтетичні пакети й не здатні відтворити хаотичну поведінку мільйонів реальних браузерів із різними затримками мережі, раптовими обривами Wi-Fi, повторними підключеннями та специфікою рендерингу сторінок.

Тоді інженери на чолі з Аділом Валі (англ. *Adil Wali*) та командою інфраструктури розробили техніку, яку вперше назвали **темним запуском** (англ. *dark launch*).

## Таємний трафік у браузерах мільйонів людей

За кілька місяців до офіційного відкриття чату команда впровадила в стандартний рушій генерації сторінок Facebook невеликий прихований фрагмент коду JavaScript. Коли звичайний користувач переглядав стрічку новин, фотографії чи профілі друзів, цей скрипт у фоновому режимі без жодного візуального інтерфейсу відкривав постійне з'єднання з новими серверами чату.

Фоновий скрипт надсилав на новий бекенд реальний потік метаданих: фіксував оновлення присутності, імітував надсилання службових пакетів і слухав відповіді сервера. Отримані від сервера відповіді браузер негайно знищував — інтерфейс чату для користувача був повністю відсутній, і жодна людина не підозрювала, що її браузер бере участь у масштабних випробуваннях інфраструктури.

```
Браузер користувача ──[ 1. Звичайний перегляд сторінки ]──> PHP Web Tier
        │
        └──[ 2. Фоновий JavaScript (без UI) ]─────────────> Erlang / C++ Chat Cluster
                                                                   │
                                                      (Збір метрик, сокети,
                                                       профіль пам'яті під 70M)
```

Це дало інженерній команді безпрецедентну можливість для глибокого дослідження системи в реальних умовах:
1. **Профілювання розподілу пам'яті:** інженери побачили поведінку збирача сміття Erlang (англ. *garbage collection*) під час утримання мільйонів живих сокетів. Виявилося, що часті короткоживучі процеси створювали суттєву фрагментацію пам'яті, що вимагало тонкого налаштування аллокатора `malloc` та розмірів стеків процесів Erlang.
2. **Виявлення витоків файлових дескрипторів:** було оптимізовано системні виклики `epoll` у ядрі Linux та налаштовано розміри черг очікування TCP-з'єднань (`tcp_max_syn_backlog` і `somaxconn`), які за умовчанням скидали підключення під час сплесків.
3. **Плавне масштабування:** частку користувачів, які надсилали фоновий трафік, поступово збільшували від 1% до 5%, 25%, 50% і зрештою 100%, виявляючи вузькі місця на кожному кроці без жодного ризику зламати основний функціонал сайту.

Коли навесні 2008 року Facebook нарешті розгорнув користувацький інтерфейс чату, бекенд уже місяцями працював під повним продакшен-навантаженням. Запуск відбувся без жодної аварії чи сповільнення основного сервісу. Цей успіх довів індустрії: перевірка навантаження й надійності повинна відбуватися на реальному продакшен-трафіку задовго до того, як функція стане видимою користувачеві.

## Flickr, Etsy та революція безперервної доставки

Паралельно з експериментами Facebook відбувався тектонічний зсув у методології розгортання програмного забезпечення. До кінця 2000-х років панував підхід «великих релізів»: код накопичувався місяцями в окремих гілках репозиторіїв, проходив тривалий ручний етап «заморожування коду» (англ. *code freeze*) і розгортався вночі з багатогодинним простоєм усієї системи.

У 2009 році на конференції Velocity Джон Олспоу (англ. *John Allspaw*) та Пол Геммонд (англ. *Paul Hammond*) представили доповідь «10+ Deploys Per Day: Dev and Ops Cooperation at Flickr», яка заклала фундамент сучасної культури DevOps. Головним інструментом, що уможливив часті розгортання у Flickr, став конфігураційний файл `feature_flags.php`.

Замість того щоб тримати нову функціональність у довгих ізольованих гілках, розробники Flickr вливали код безпосередньо в головну гілку `main` щодня по кілька разів. Але цей код був загорнутий в умовні конструкції:

```php
if (feature_is_enabled('new_photo_uploader', $current_user)) {
    render_html5_uploader();
} else {
    render_legacy_flash_uploader();
}
```

Прапорці функцій (англ. *feature flags*, або *feature toggles*) радикально розділили два поняття, які раніше вважалися нероздільними:
* **Розгортання (англ. *deployment*):** фізична доставка скомпільованого бінарного файлу або скрипту на сервери продакшену.
* **Реліз (англ. *release*):** відкриття доступу до нової поведінки для кінцевих користувачів.

Невдовзі інженерна команда інтернет-ринку Etsy розвинула цей підхід у системі `Feature.php`, додавши динамічне керування прапорцями через вебінтерфейс без потреби повторного деплою. Це дозволило вмикати нові модулі для 1% користувачів, тестувати поведінку в продакшені та миттєво вимикати функцію в разі виявлення помилок за мілісекунди.

У 2010 році Мартін Фаулер (англ. *Martin Fowler*) та Тімоті Фіц (англ. *Timothy Fitz*) систематизували цей досвід у своїх статтях про неперервне розгортання. Фаулер класифікував прапорці на чотири окремі категорії: релізні (англ. *release toggles* для приховування недописаного коду), експериментальні (англ. *experiment toggles* для A/B-тестування), експлуатаційні (англ. *ops toggles* для вимкнення важких функцій під час перевантаження) та міграційні (англ. *migration toggles* для поступової заміни старих підсистем).

## GitHub та народження патерну Scientist

Якщо темні запуски у Facebook вирішували проблему навантаження й пропускної здатності мережі, то у 2014 році інженери GitHub зіткнулися з іншим фундаментальним викликом: **як гарантувати побітну функціональну коректність при рефакторингу критичних підсистем**.

Моноліт GitHub на базі Ruby on Rails обслуговував мільйони операцій злиття гілок (англ. *git merge*), розрахунку прав доступу та генерації сторінок відмінностей (англ. *diff*). Цей код писався роками, обріс сотнями неявних крайових випадків і взаємодіяв із низькорівневим Git через виклики процесів оболонки. Команда вирішила замінити повільні виклики процесів на швидку нативну бібліотеку `libgit2` та оптимізовані SQL-запити.

Проблема полягала в тому, що навіть найповніший набір модульних тестів не міг покрити всі варіації реальних Git-репозиторіїв: нестандартні кодування символів у комітах, екзотичні дерева каталогів, бінарні конфлікти та пошкоджені об'єкти. Помилка в новому алгоритмі злиття могла непомітно пошкодити код користувача або призвести до витоку приватного репозиторію.

Інженери GitHub Джессі Тот (англ. *Jesse Toth*), Рік Олсон (англ. *Rick Olson*) та їхні колеги створили бібліотеку **Scientist**. Вона реалізувала патерн диференційного тіньового тестування прямо в коді застосунку:

```ruby
def merge_branches(base, head)
  science "git-merge-refactor" do |e|
    e.use { legacy_shell_git_merge(base, head) }  # Контрольна гілка (стара)
    e.try { libgit2_native_merge(base, head) }     # Експериментальна гілка (нова)
    e.compare { |old, new| old.tree_sha == new.tree_sha }
  end
end
```

Механіка Scientist працювала за залізними правилами наукового експерименту:
1. Контрольний варіант (`use`) завжди виконувався надійним шляхом і повертав результат користувачеві.
2. Експериментальний варіант (`try`) запускався в захищеному блоці перехоплення помилок: якщо новий код викидав виняток, зависав чи падав із помилкою, користувач цього не помічав — збій фіксувався в телеметрії.
3. Компаратор звіряв результуючі хеші дерев і вихідні структури. Будь-яка розбіжність фіксувалася в метриках StatsD та базі звітів із повним дампом вхідних аргументів.
4. Порядок запуску `use` і `try` рандомізувався, щоб уникнути викривлення затримок через прогрів процесорного кешу чи кешу бази даних.

GitHub крутив експерименти Scientist місяцями, обробивши мільярди реальних операцій. Було знайдено десятки тонких розбіжностей у поведінці `libgit2` порівняно зі стандартним Git, про які розробники навіть не підозрювали. Лише тоді, коли частка розбіжностей досягла абсолютного 0.0000% на сотнях мільйонів викликів, перемикач перевели на новий рушій, а старий код видалили.

## Від коду застосунку до сервісної сітки

Успіх Scientist спричинив появу відкритих портів практично для всіх провідних мов програмування: Scientist4J для Java, Scientist.NET для C#, галузеві бібліотеки для Go, C++, Python та Rust.

З розвитком розподілених мікросервісів у 2016–2018 роках компанія Lyft розробила високопродуктивний проксі-сервер Envoy, який згодом ліг в основу сервісних сіток Istio та Linkerd. Інженери перенесли концепцію темного запуску з рівня коду функцій на рівень інфраструктурного проксі за допомогою директиви `request_mirror_policy`.

Це дозволило мережевим шлюзам прозоро дублювати вхідний HTTP- або gRPC-трафік на нові версії сервісів асинхронно та без блокування основного потоку. Відповіді тіньових сервісів скидаються на рівні мережевого сокета, забезпечуючи нульовий вплив на користувача навіть у разі повного падіння нового бекенду.

Сьогодні темний запуск, прапорці функцій і диференційне порівняння складають єдиний індустріальний стандарт розгортання критичних систем. Вони перетворили введення нових підсистем у продакшен із небезпечної лотереї на передбачуваний, керований і цілком вимірний інженерний експеримент.
