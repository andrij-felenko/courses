# 📋 Специфікація схеми маніфесту модельного артефакту та API реєстру

Цей документ визначає повну технічну та структурну специфікацію незмінного пакета модельного артефакту, схеми його декларативних метаданих, контракту тензорного інтерфейсу, а також прикладного інтерфейсу (API) централізованого реєстру моделей. У розподілених системах машинного навчання відсутність формального машиночитаного контракту артефакту призводить до аварійних зупинок інференс-процесів під час оновлення версій, непомітного спотворення типів числових ознак та повної втрати відтворюваності бізнес-рішень.

Нижче наведено детальний опис файлової структури артефакту, правила валідації полів маніфесту, специфікацію тензорних сигнатур, схему метрик еталонного рівня, формальний протокол gRPC та повний опис кінцевих точок REST для керування життєвим циклом моделі.

## Файлова архітектура та пакування пакета артефакту

Модельний артефакт пакується у вигляді єдиного незмінного запечатаного архіву або шару OCI-образу з використанням алгоритму стиснення Zstandard (`.tar.zst`). Використання архівного контейнера гарантує, що конфігурація, метадані та бінарні тензори передаються між вузлами кластера як неподільна атомарна сутність.

```text
model-package-v2.4.1/
├── manifest.json          # Кореневий паспорт: ідентифікація, родовід, залежності, SHA-256
├── signature.json         # Формальний контракт вхідних/вихідних тензорів і правил валідації
├── metrics.json           # Еталонний рівень якості, розподіл за зрізами та затримки
├── environment.lock       # Зафіксований знімок середовища, версій бібліотек і прапорців CPU
└── weights.safetensors    # Бінарні масиви числових параметрів із підтримкою mmap
```

Кожен файл усередині пакета має строго визначену функцію:
* `manifest.json`: фіксує криптографічний родовід артефакту (Lineage), пов'язуючи скомпільовані ваги з конкретним комітом у Git, знімком навчального датасету та цифровим підписом агента збирання.
* `signature.json`: декларує очікувані форми тензорів, типи даних, допустимі діапазони значень і правила обробки пропущених полів для захисту інференс-рушія від некоректних запитів.
* `metrics.json`: зберігає базові показники точності та затримок, отримані під час валідації в конвеєрі CI/CD, що слугують точкою відліку для виявлення деградації в режимі реального часу.
* `environment.lock`: містить хеші залежностей, версії компіляторів, драйверів і прапорці мікроархітектури процесора, необхідні для детермінованого відтворення обчислень.
* `weights.safetensors`: містить сирі масиви вагових коефіцієнтів у безпечному форматі без виконуваного коду, оптимізованому для прямого відображення у віртуальну пам'ять (`mmap`).

### Детальний опис та правила валідації полів маніфесту

1. **Секція метаданих (`model_metadata`):**
   * `schema_version` (рядок): версія синтаксичної схеми маніфесту відповідно до специфікації SemVer. Дозволяє парсеру підтримувати зворотну сумісність при зміні структури документа.
   * `name` (рядок): унікальний ідентифікатор моделі в межах організації. Повинен складатися виключно з малих латинських літер, цифр та дефісів (регулярний вираз `^[a-z0-9-]+$`).
   * `version` (рядок): незмінна версія артефакту. Повторне використання номера версії для іншого бінарного вмісту в реєстрі категорично заборонено.
   * `format` (рядок): формат збереження числових ваг (`safetensors`, `onnx`, `tensorrt_engine`).
   * `target_runtime` (рядок): цільове середовище виконання, під яке скомпільовано або оптимізовано артефакт.
   * `build_timestamp` (рядок): час генерації пакета в стандарті ISO-8601 UTC.

2. **Секція родоводу коду (`lineage.code`):**
   * `repository_url` (рядок): канонічна адреса репозиторію системи контролю версій Git.
   * `commit_sha` (рядок): повний 40-символьний SHA-1 або 64-символьний SHA-256 хеш коміту, з якого було запущено навчання.
   * `pipeline_file` (рядок): відносний шлях до виконуваного скрипта або конфігурації конвеєра навчання всередині репозиторію.
   * `feature_engineering_sha` (рядок): контрольна сума коду виділення та нормалізації ознак. Якщо логіка генерації ознак змінюється незалежно від архітектури моделі, цей хеш запобігає розсинхронізації онлайн- та офлайн-обчислень.

3. **Секція родоводу даних (`lineage.data`):**
   * `training_dataset_id` (рядок): унікальне найменування набору даних у корпоративному каталозі даних.
   * `dataset_digest` (рядок): криптографічний хеш контенту датасету (DVC-хеш або знімок версії в сховищі Iceberg/Delta Lake). Будь-яка зміна хоча б одного рядка у вибірці змінює цей хеш.
   * `record_count` (ціле число): точна кількість записів, використаних під час навчання.
   * `train_val_test_split` (масив дійсних чисел): пропорції розбиття вибірки на навчальну, валідаційну та тестову частини.
   * `feature_store_view` (рядок): версійоване представлення вітрини ознак, з якої вичитувалися параметри в момент тренування.

4. **Секція середовища виконання (`lineage.environment`):**
   * `python_version` (рядок): точна версія інтерпретатора, під яким проходила серіалізація.
   * `cuda_driver_version` та `cuda_runtime_version` (рядки): версії драйвера та бібліотек CUDA, критичні для бінарної сумісності скомпільованих ядер GPU.
   * `cpu_isa_flags` (масив рядків): перелік векторних інструкцій процесора (AVX2, AVX-512, NEON), які вимагаються для запуску скомпільованих бібліотек математичного прискорення (MKL, oneDNN, OpenBLAS). Запуск на вузлі без підтримки відповідних інструкцій спричинить аварійне завершення процесу із сигналом `SIGILL` (Illegal Instruction).
   * `random_seed` (ціле число): фіксоване початкове значення генератора псевдовипадкових чисел для перевірки детермінованості навчання.

5. **Секція цілісності та безпеки (`security`):**
   * `signer_identity` (рядок): ідентифікатор автоматизованого сервісного облікового запису або публічного ключа конвеєра збирання.
   * `signature_algorithm` (рядок): криптографічний алгоритм підпису (наприклад, `Ed25519` або `ECDSA-P256`).
   * `signature_value` (рядок): цифровий підпис тіла маніфесту в кодуванні Base64, що виключає можливість непомітної модифікації метаданих зловмисником.

## Специфікація тензорного контракту (signature.json)

Файл `signature.json` визначає суворий типізований інтерфейс взаємодії між зовнішнім клієнтським кодом та внутрішнім графом обчислень моделі. Інференс-сервер використовує цю специфікацію як фільтр вхідного трафіку: якщо вхідний запит не відповідає типам або порушує розмірності, запит відхиляється на рівні шлюзу з кодом `HTTP 400 Bad Request` або gRPC-статусом `INVALID_ARGUMENT` без навантаження обчислювальних ядер GPU.

```json
{
  "$schema": "https://mlops.spec.internal/schemas/v1/signature.json",
  "inputs": [
    {
      "name": "transaction_amount",
      "data_type": "FLOAT32",
      "shape": [-1, 1],
      "nullable": false,
      "constraints": {
        "min_value": 0.01,
        "max_value": 1000000.00
      },
      "description": "Сума фінансової транзакції в еквіваленті USD"
    },
    {
      "name": "user_embedding",
      "data_type": "FLOAT32",
      "shape": [-1, 64],
      "nullable": false,
      "constraints": {
        "norm": "L2_NORMALIZED"
      },
      "description": "Нормалізований вектор поведінкового профілю користувача"
    },
    {
      "name": "channel_type_id",
      "data_type": "INT64",
      "shape": [-1, 1],
      "nullable": false,
      "constraints": {
        "allowed_values": [1, 2, 3, 4, 5]
      },
      "description": "Ідентифікатор платіжного каналу (1=Web, 2=Mobile, 3=POS, 4=ATM, 5=API)"
    }
  ],
  "outputs": [
    {
      "name": "fraud_probability",
      "data_type": "FLOAT32",
      "shape": [-1, 1],
      "constraints": {
        "min_value": 0.0,
        "max_value": 1.0
      },
      "description": "Калібрована ймовірність шахрайства за транзакцією"
    },
    {
      "name": "risk_tier",
      "data_type": "STRING",
      "shape": [-1, 1],
      "constraints": {
        "allowed_values": ["LOW", "MEDIUM", "HIGH", "CRITICAL"]
      },
      "description": "Категорія ризику для автоматизованого ухвалення рішення"
    }
  ]

```

### Семантика опису тензорів та правила нормалізації

* **Форма тензора (`shape`):** описується масивом цілих чисел. Значення `-1` позначає динамічний розмір батчу (англ. *batch dimension*), що дозволяє серверу обробляти як одиничні запити в реальному часі (розмір 1), так і динамічно сформовані пачки запитів (наприклад, 32 або 64) для ефективної утилізації паралельних обчислювальних блоків. Додатні числа задають фіксовані розмірності простору ознак.
* **Підтримувані типи даних (`data_type`):**
  * `FLOAT32` (IEEE 754 одинарної точності) — базовий тип для більшості нейромереж.
  * `FLOAT16` та `BFLOAT16` — формати напівточності для оптимізованого інференсу на сучасних GPU/NPU.
  * `INT8` та `UINT8` — цілочисельні квантовані типи для мікроконтролерів та мобільних пристроїв.
  * `INT64` — цілі числа для ідентифікаторів категорій та дискретних ознак.
  * `STRING` — текстові мітки та категорії.
* **Обмеження та валідація (`constraints`):**
  * `min_value` / `max_value`: порогові межі для числових полів. Значення за межами діапазону сприймаються як аномалія сенсора або збій клієнтського застосунку.
  * `allowed_values`: явний перелік допустимих категоріальних ключів. Захищає модель від некоректних індексів ембеддингів, які могли б спричинити вихід за межі масиву (Out of Bounds).
  * `norm`: математичні вимоги до векторів (наприклад, одинична L2-норма для векторних просторів семантичного пошуку).

### Значення метрик для експлуатації системи

* **Офлайн-метрики якості (`offline_quality`):** визначають початкову математичну здатність алгоритму відокремлювати класи. Оптимальний поріг класифікації (`optimal_threshold`) фіксується всередині артефакту, що гарантує однакову інтерпретацію вихідних імовірностей усіма репліками інференс-сервісу.
* **Бенчмарки затримок (`runtime_benchmarks`):** визначають очікувані часові показники виконання на конкретному апаратному обладнанні. Значення перцентилів p50, p95 та p99 слугують основою для налаштування таймаутів у розподіленій системі та визначення бюджету помилок (Error Budget). Якщо в бойових умовах реальна затримка p99 перевищує еталонну вдвічі, моніторинг сигналізує про деградацію ресурсів процесора або конфлікт пам'яті.
* **Оцінка за зрізами даних (`slice_evaluations`):** розбиває загальну метрику точності на критичні бізнес-сегменти. Це запобігає маскуванню катастрофічних помилок на рідкісних, але фінансово важливих операціях (наприклад, великі корпоративні перекази або міжнародні платежі) за рахунок високої середньої точності на масовому простому трафіку.

## Специфікація бінарного протоколу gRPC (model_service.proto)

Для взаємодії з високонавантаженими серверами інференсу використовується двійковий протокол gRPC/Protobuf, який мінімізує затримки серіалізації в порівнянні з текстовим форматом JSON:

```protobuf
syntax = "proto3";

package mlops.serving.v1;

service ModelServing {
  rpc Predict (PredictRequest) returns (PredictResponse);
  rpc StreamPredict (stream PredictRequest) returns (stream PredictResponse);
  rpc GetModelMetadata (ModelMetadataRequest) returns (ModelMetadataResponse);
}

message PredictRequest {
  string model_name = 1;
  string model_version = 2;
  map<string, TensorProto> inputs = 3;
}

message PredictResponse {
  string model_name = 1;
  string model_version = 2;
  map<string, TensorProto> outputs = 3;
  int64 inference_duration_us = 4;
}

message TensorProto {
  enum DataType {
    TYPE_UNSPECIFIED = 0;
    FLOAT32 = 1;
    FLOAT16 = 2;
    INT64 = 3;
    INT8 = 4;
    STRING = 5;
  }
  DataType data_type = 1;
  repeated int64 shape = 2;
  bytes raw_data = 3;
}

message ModelMetadataRequest {
  string model_name = 1;
}

message ModelMetadataResponse {
  string active_version = 1;
  string target_stage = 2;
  int64 loaded_timestamp = 3;
  int64 total_inferences_served = 4;
}
```

## Протокол взаємодії з реєстром моделей (Model Registry REST API)

Реєстр моделей виступає єдиним джерелом правди в інфраструктурі MLOps. Він надає уніфікований REST API для публікації нових версій, контролю за просуванням стадій, безпечного завантаження та збору телеметрії.

```text
                               ┌─────────────────────────────────────────┐
                               │         Центральний реєстр моделей      │
                               │                                         │
                               │  Стадії версій:                         │
                               │  [ Draft ] ──> [ Staging ] ──> [ Prod ] │
                               │                                   │     │
                               │                                   ▼     │
                               │                              [ Archived]│
                               └─────────────────────────────────────────┘
                                     ▲                         │
           1. Реєстрація артефакту   │                         │  3. Завантаження пакету
              (POST /versions)       │                         │     (GET /active)
                                     │                         ▼
                              ┌───────────────┐        ┌───────────────┐
                              │ CI/CD Конвеєр │        │ Інференс-вузол│
                              └───────────────┘        └───────────────┘
```

Нижче наведено формальну специфікацію основних кінцевих точок інтерфейсу.

### 1. Реєстрація нової версії артефакту
* **Метод і шлях:** `POST /api/v1/models/{model_name}/versions`
* **Призначення:** Створення нового запису в реєстрі та ініціалізація початкового стану артефакту.
* **Заголовки запиту:**
  * `Content-Type: application/json`
  * `Authorization: Bearer <ci_cd_service_token>`
* **Тіло запиту:**
```json
{
  "version": "2.4.1",
  "manifest_payload": "...",
  "signature_payload": "...",
  "metrics_payload": "...",
  "storage_uri": "s3://ml-models-registry/fraud-detection/v2.4.1/package.tar.zst",
  "sha256_checksum": "d8a2bc4190ef2b890123ef451928374102938475610293847561029384756102"
}
```
* **Коди відповідей:**
  * `HTTP 201 Created` — версію успішно зареєстровано, поточний статус `stage: "Draft"`.
  * `HTTP 409 Conflict` — версія з таким номером уже існує в реєстрі. Повторний запис заборонено.
  * `HTTP 422 Unprocessable Entity` — маніфест не пройшов перевірку схеми або криптографічний підпис недійсний.

### 2. Отримання дескриптора активної бойової моделі
* **Метод і шлях:** `GET /api/v1/models/{model_name}/stages/production`
* **Призначення:** Опитування поточного стану бойової моделі інференс-вузлами для автоматичного виявлення релізів або перевірки конфігурації.
* **Заголовки запиту:**
  * `Authorization: Bearer <node_agent_token>`
* **Коди відповідей:**
  * `HTTP 200 OK` — повертає метадані активної версії та тимчасовий підписаний URL для безпечного завантаження архіву:
```json
{
  "model_name": "fraud-detection-engine",
  "version": "2.4.1",
  "stage": "Production",
  "storage_uri": "https://vault.internal/packages/fraud-v2.4.1.tar.zst?token=exp1724128800_sig9a8f",
  "sha256_checksum": "d8a2bc4190ef2b890123ef451928374102938475610293847561029384756102",
  "deployed_at": "2026-08-20T00:30:00Z"
}
```
  * `HTTP 404 Not Found` — для цієї моделі відсутня активна версія в стадії `Production`.

### 3. Атомарне просування стадії життєвого циклу
* **Метод і шлях:** `POST /api/v1/models/{model_name}/versions/{version}/promote`
* **Призначення:** Переведення моделі на наступний етап життєвого циклу (`Draft` → `Staging` → `Production` → `Archived`). При переведенні нової версії в стан `Production` попередня активна версія атомарно переводиться в стан `Archived` зі збереженням повної готовності до миттєвого відкочування.
* **Тіло запиту:**
```json
{
  "target_stage": "Production",
  "reason": "Успішне проходження канаркового тестування: затримка p99 менше 10 мс, помилок 0%",
  "approvals": [
    {
      "gate": "automated_canary_verifier",
      "status": "PASSED",
      "evaluated_at": "2026-08-20T00:25:00Z"
    }
  ]
}
```
* **Коди відповідей:**
  * `HTTP 200 OK` — статус успішно змінено.
  * `HTTP 412 Precondition Failed` — обов'язкові автоматичні гейти перевірки якості не пройдені (наприклад, відсутній результат навантажувального тесту або виявлено критичну деградацію точності).

### 4. Надсилання агрегованої телеметрії для розрахунку дрейфу
* **Метод і шлях:** `POST /api/v1/models/{model_name}/telemetry/drift`
* **Призначення:** Періодичне надсилання фоновими воркерами спостережуваності агрегованих гістограм вхідних ознак для розрахунку статистичного дрейфу відносно еталона з `metrics.json`.
* **Тіло запиту:**
```json
{
  "model_version": "2.4.1",
  "time_window_start": "2026-08-20T01:00:00Z",
  "time_window_end": "2026-08-20T02:00:00Z",
  "total_inferences": 250000,
  "feature_distributions": {
    "transaction_amount": {
      "bin_edges": [0.0, 50.0, 100.0, 250.0, 500.0, 1000.0, 5000.0, 10000.0, 1000000.0],
      "observed_counts": [55000, 92000, 51000, 29000, 14000, 6800, 1900, 300]
    }
  }
}
```
* **Коди відповідей:**
  * `HTTP 202 Accepted` — телеметрію прийнято в чергу аналізу дрейфу.
  * `HTTP 400 Bad Request` — структура бакетів гістограми не збігається зі схемою еталонного розподілу.

## Каталог кодів помилок реєстру

У разі виникнення помилок сервіс реєстру повертає структуровану відповідь із числовим внутрішнім кодом помилки, детальним описом причини та рекомендацією щодо виправлення:

| Код помилки | Статус HTTP / gRPC | Опис та причина виникнення | Необхідна дія клієнта |
| :--- | :--- | :--- | :--- |
| `ERR_CHECKSUM_MISMATCH` | `422 Unprocessable` / `DATA_LOSS` | Обчислений SHA-256 хеш завантаженого файлу не збігається з маніфестом. | Перевірити мережевий канал та повторити завантаження артефакту. |
| `ERR_INVALID_SIGNATURE` | `401 Unauthorized` / `UNAUTHENTICATED` | Цифровий підпис маніфесту не відповідає відкритому ключу довіреного центру. | Перепідписати артефакт дійсним ключем конвеєра збирання. |
| `ERR_SCHEMA_VIOLATION` | `400 Bad Request` / `INVALID_ARGUMENT` | Структура JSON-файлу порушує обов'язкові поля специфікації маніфесту. | Виправити формат документа відповідно до JSON Schema. |
| `ERR_STAGE_GATE_FAILED` | `412 Precondition` / `FAILED_PRECONDITION` | Спроба просування версії в `Production` без проходження автоматичних тестів. | Запустити валідаційний конвеєр та отримати підтвердження гейтів якості. |
| `ERR_VERSION_EXISTS` | `409 Conflict` / `ALREADY_EXISTS` | Спроба зареєструвати пакет під уже зайнятим номером версії. | Збільшити номер версії згідно з правилами семантичного версіювання SemVer. |
| `ERR_MODEL_NOT_FOUND` | `404 Not Found` / `NOT_FOUND` | Запитуване ім'я моделі або вказаний номер версії відсутні в реєстрі. | Перевірити правильність ідентифікатора моделі в запиті. |

## Матриця переходів станів життєвого циклу (State Machine Rules)

Просування моделі між стадіями контролюється детермінованим скінченним автоматом. Нижче наведено перелік допустимих переходів, обов'язкових передумов та автоматичних побічних дій:

1. **`Draft` → `Staging`:**
   * *Вимоги:* Успішне проходження юніт-тестів на сумісність тензорних типів даних, валідація схеми `signature.json`, перевірка цілісності SHA-256.
   * *Дія реєстру:* Надання доступу для контурів інтеграційного тестування та запуску тіньового інференсу (Shadow Mode).
2. **`Staging` → `Production`:**
   * *Вимоги:* Успішне проходження навантажувального тесту на відповідність бюджету затримок p99, відсутність критичного дрейфу під час канаркового випуску, наявність цифрового підпису відповідального інженера.
   * *Дія реєстру:* Атомарне оновлення вказівника активної моделі. Попередня версія зі статусу `Production` автоматично переводиться в статус `Archived`.
3. **`Production` → `Archived`:**
   * *Вимоги:* Ініціюється автоматично при активації новішого релізу, або вручну черговим інженером у разі виявлення критичного інциденту.
   * *Дія реєстру:* Видалення з активного маршруту балансування, збереження всіх бінарних файлів у стані готовності до миттєвого відновлення.
4. **`Archived` → `Production` (Екстрений відкіт):**
   * *Вимоги:* Наявність сигналу аварійного відкочування від чергової зміни або автоматичного контролера SLO.
   * *Дія реєстру:* Миттєве повернення попередньої стабільної версії на бойові інференс-вузли за час `O(1)`.

## Правила сумісності та еволюція схем (Schema Evolution)

Під час оновлення моделей у бойовому середовищі критично дотримуватися правил еволюції схем, щоб не порушити роботу активних клієнтів:

1. **Зворотна сумісність (Backward Compatibility):**
   * Нова версія моделі v2.5 не має права видаляти існуючі обов'язкові вхідні поля зі структури `signature.json`.
   * Додавання нових вхідних ознак дозволяється лише за умови, що для них визначено значення за замовчуванням (Default Value) або вони позначені прапорцем `nullable: true`.
   * Зміна розмірності вихідних тензорів заборонена без створення нового сімейства моделі або мажорного оновлення API.

2. **Інтеграція з вітринами ознак (Feature Store Integration):**
   * Поле `feature_store_view` у маніфесті пов'язує артефакт із конкретною версією сховища ознак (наприклад, Feast або Tecton).
   * Інференс-сервер використовує цей ідентифікатор для автоматичного вичитування низьколатентних векторів із кешу Redis у реальному часі за ключем користувача (`user_id`), гарантуючи математичну ідентичність ознак тим, що використовувалися під час офлайн-навчання.

## Політика збереження та очищення артефактів (Retention & Garbage Collection)

Для запобігання неконтрольованому зростанню витрат на зберігання терабайтних архівів моделей в об'єктних сховищах реєстр реалізує автоматизовану політику життєвого циклу даних:

* Версії в стані `Production` та `Staging` мають статус незмінного вічного збереження (Permanent Hold) і не підлягають автоматичному видаленню за жодних умов.
* Версії в стані `Archived` зберігаються в повному обсязі щонайменше 180 днів для забезпечення фінансового та юридичного аудиту рішень моделі. Після закінчення цього терміну важкі файли ваг (`weights.safetensors`) можуть переміщуватися в архівне холодне сховище (AWS S3 Glacier), тоді як легковажні маніфести (`manifest.json`, `signature.json`, `metrics.json`) залишаються доступними в реєстрі назавжди.
* Невдалі збірки в стані `Draft`, які не пройшли автоматичні тести протягом 14 днів, автоматично видаляються з реєстру фоновим процесом збирача сміття (Garbage Collector).
