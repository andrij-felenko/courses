# 📋 Специфікація декларативних примітивів та інтерфейсів оркестратора

Взаємодія між компонентами кластерного оркестратора, користувацькими маніфестами, контролерами та низькорівневими плагінами ядра Linux базується на строго типізованих декларативних контрактах. Кожен об'єкт у системі є версійованим ресурсом, стан якого описується схемою полів JSON/YAML та валідується API-шлюзом перед збереженням у транзакційному журналі.

Нижче наведено нормативну специфікацію ключових структур даних, поведінкових параметрів проб здоров'я, класів якості обслуговування (QoS), моделі мережевої безпеки, контрактів сховищ та системних плагінних інтерфейсів рантайму, мережі та дисків.

## 1. Схема базового конверта об'єкта (Object Envelope)

Будь-який ресурс кластера містить обов'язкові метадані ідентифікації, контролю паралелізму та життєвого циклу.

```yaml
apiVersion: string         # Версія схеми API (наприклад, "apps/v1" або "v1")
kind: string               # Тип ресурсу ("Pod", "Deployment", "Service")
metadata:
  name: string             # Унікальне ім'я ресурсу в межах простору імен (до 253 символів, RFC 1123)
  namespace: string        # Простір імен для ізоляції ("default", "kube-system", "production")
  uid: string              # Унікальний UUID об'єкта, що генерується API Server при створенні
  resourceVersion: string  # Монотонний рядок версії в etcd; використовується для оптимістичного блокування CAS
  generation: integer      # Монотонний лічильник змін специфікації (.spec), що збільшується контролером мутацій
  creationTimestamp: string# Час створення об'єкта у форматі ISO 8601 (UTC)
  labels:                  # Словник міток для динамічної селекції та маршрутизації (key: value)
    app: string
    tier: string
    environment: string
  annotations:             # Неіндексовані службові метадані (конфігурація інструментів, SHA256 хеші)
    kubectl.kubernetes.io/restartedAt: string
  ownerReferences:         # Зв'язки підпорядкування для каскадного видалення (Garbage Collection)
    - apiVersion: string
      kind: string
      name: string
      uid: string
      controller: boolean  # Чи є цей батьківський об'єкт прямим керуючим контролером
      blockOwnerDeletion: boolean
  finalizers:              # Масив ключів блокування видалення до виконання очищення зовнішніх ресурсів
    - string
```

### Поля метаданих та їхні інваріанти

Метадані об'єкта виконують критичну роль у забезпеченні консистентності розподіленої системи:

1. **Ідентифікація (`name`, `namespace`, `uid`):**
   Комбінація `(namespace, kind, name)` є унікальним первинним ключем для адресації об'єкта через REST API. Поле `uid` формується у форматі UUID v4 під час збереження першої версії в сховищі і гарантує, що новий об'єкт, створений із тим самим ім'ям після видалення попереднього, не успадкує застарілі зв'язки або незавершені операції.

2. **Оптимістичний паралелізм (`resourceVersion`, `generation`):**
   Поле `resourceVersion` містить глобальний номер транзакції etcd. Будь-який клієнт, що надсилає зміни через методи `PUT` або `PATCH`, зобов'язаний передавати останній відомий йому `resourceVersion`. Якщо версія не збігається з поточною версією в базі даних, API Server повертає код помилки `409 Conflict`. Поле `generation` відображає кількість прямих редагувань бажаного стану (`.spec`): воно збільшується на 1 щоразу, коли користувач змінює конфігурацію, і дозволяє контролерам відстежувати, чи встиг цикл узгодження застосувати найсвіжіші правки (`status.observedGeneration == metadata.generation`).

3. **Селекція та маршрутизація (`labels`, `annotations`):**
   Мітки (`labels`) індексуються базою даних і використовуються планувальниками, сервісами та контролерами для динамічного групування (`LabelSelector`). Анотації (`annotations`) призначені для збереження довільних неіндексованих метаданих обсягом до 256 КБ (наприклад, конфігурація плагінів Ingress, декларації політик безпеки або повні дампи маніфестів інструментів CI/CD).

4. **Дерево залежностей (`ownerReferences`, `finalizers`):**
   Масив `ownerReferences` зв'язує дочірній ресурс (наприклад, `Pod`) із батьківським (`ReplicaSet`). При видаленні батька системний збирач сміття (Garbage Collector) автоматично каскадно видаляє всіх нащадків. Фіналізатори (`finalizers`) зупиняють фізичне видалення запису з etcd: встановлення часу видалення `deletionTimestamp` переводить об'єкт у режим блокування, даючи контролерам можливість коректно відключити хмарні диски, звільнити зовнішні статичні IP-адреси та оновити таблиці маршрутизації.

## 2. Специфікація контейнерного пода (`PodSpec`)

`PodSpec` описує контракт виконання одного або групи взаємопов'язаних контейнерів, що мають спільні простори імен ядра (Network, IPC, UTS) та спільні томи сховища.

```yaml
spec:
  restartPolicy: string    # "Always" (за замовчуванням), "OnFailure", "Never"
  terminationGracePeriodSeconds: integer # Час на штатне вимкнення перед SIGKILL (за замовчуванням 30s)
  nodeSelector:            # Простий фільтр вузлів за точним збігом міток
    topology.kubernetes.io/zone: "eu-west-1a"
    disktype: "nvme"
  nodeName: string         # Ім'я вузла; якщо заповнене — планувальник пропускає етап фільтрації/оцінки
  serviceAccountName: string # Ім'я облікового запису для отримання JWT-токенів автентифікації
  hostNetwork: boolean     # Чи використовувати мережевий простір імен хоста (NetNS хоста)
  dnsPolicy: string        # "ClusterFirst", "Default", "ClusterFirstWithHostNet", "None"
  
  initContainers:          # Масив допоміжних контейнерів, що виконуються послідовно ДО запуску основних
    - name: string
      image: string
      command: ["/bin/sh", "-c"]
      args: ["migrate-db --dry-run=false"]
      
  containers:              # Масив основних довгоживучих контейнерів, що виконуються паралельно
    - name: string         # Ім'я контейнера (унікальне всередині пода)
      image: string        # Повний шлях до OCI-образу ("registry.example.com/app:v2.4.1")
      imagePullPolicy: string # "Always", "IfNotPresent", "Never"
      command: ["/app/server"]
      args: ["--port=8080", "--config=/etc/app/config.json"]
      env:                 # Змінні оточення
        - name: DB_HOST
          value: "postgres.internal"
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-secrets
              key: db-pass
      ports:
        - name: http
          containerPort: 8080
          protocol: TCP
      resources:           # Вимоги та обмеження обчислювальних ресурсів
        requests:
          cpu: "500m"      # 500 міліядер = 0.5 CPU
          memory: "256Mi"  # 256 мебібайтів
        limits:
          cpu: "2000m"     # Жорсткий ліміт CFS quota = 2.0 ядер
          memory: "1Gi"    # Жорсткий ліміт cgroup memory.max; перевищення викликає OOM
      volumeMounts:
        - name: app-config
          mountPath: /etc/app
          readOnly: true
```

### Семантика виконання контейнерів у поді

1. **Ініціалізаційні контейнери (`initContainers`):**
   Виконуються строго по черзі. Якщо будь-який ініціалізаційний контейнер завершується з ненульовим кодом помилки, весь под перезапускається згідно з правилом `restartPolicy`. Основні контейнери ніколи не запускаються доти, доки останній ініціалізаційний контейнер не завершить свою роботу з кодом `0`. Це гарантує безпечне виконання міграцій схем БД та попереднє завантаження важких конфігурацій.

2. **Паралельні контейнери (`containers`):**
   Усі контейнери основного блоку стартують паралельно в межах єдиного мережевого простору імен (`Network Namespace`). Вони можуть звертатися один до одного через локальний інтерфейс зворотного зв'язку (`localhost`), але не мають права слухати однакові мережеві порти.

3. **Керування ресурсами (`requests` проти `limits`):**
   - **`requests` (Гарантована бронь):** Значення, які враховуються планувальником (kube-scheduler) для пошуку вільного місця на вузлах. Для CPU значення транслюється в параметр ядерного планувальника CFS `cpu.weight` (або `cpu.shares`), забезпечуючи пропорційний поділ часу процесора при конкуренції.
   - **`limits` (Жорсткі обмеження):** Значення, які накладаються на рівні підсистем cgroups ядра Linux. Для CPU ліміт встановлює параметри `cpu.max` (CFS bandwidth quota): процес примусово пригальмовується (CPU throttling) при вичерпанні кванту часу в межах періоду 100 мс. Для пам'яті ліміт встановлює `memory.max`: якщо сумарне споживання анонімної пам'яті контейнера перевищує ліміт, ядро Linux негайно надсилає сигнали аварійної зупинки `SIGKILL` (Out-Of-Memory Killer).

## 3. Специфікація перевірок здоров'я (Health Probes)

Оркестратор підтримує три взаємодоповнюючі проби життєвого циклу контейнера. Кожна проба налаштовується однаковим блоком обробників та часових параметрів.

```yaml
startupProbe:   # Блокує liveness та readiness перевірки до моменту успішного персивного старту
  httpGet:
    path: /healthz/startup
    port: 8080
    scheme: HTTP
    httpHeaders:
      - name: X-Probe-Agent
        value: Orchestrator-Kubelet
  initialDelaySeconds: 0  # Затримка перед першою спробою після старту контейнера
  periodSeconds: 5        # Інтервал між періодичними опитуваннями
  timeoutSeconds: 2       # Таймаут очікування відповіді від сокета
  failureThreshold: 30    # Кількість невдач до визнання збою (30 * 5s = 150s на старт важких застосунків)
  successThreshold: 1     # Кількість успішних відповідей для переходу в стан Success

livenessProbe:  # Виявляє стан зависання (deadlock/panic); при невдачі перезапускає контейнер через CRI
  tcpSocket:
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 1
  failureThreshold: 3

readinessProbe: # Визначає готовність приймати мережевий трафік; при невдачі вилучає IP з EndpointSlice
  exec:
    command:
      - /bin/sh
      - -c
      - "pg_isready -h 127.0.0.1 -p 5432"
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
  successThreshold: 1
```

### Порівняльна матриця дій при збої проб

| Тип проби | Призначення | Дія оркестратора при статусі Failure | Вплив на мережеву маршрутизацію |
| :--- | :--- | :--- | :--- |
| **Startup** | Контроль повільної ініціалізації | Вбивство контейнера `SIGKILL`, перезапуск за `restartPolicy` | Трафік не надсилається (Readiness не активна) |
| **Liveness** | Контроль фатальних зависань | Вбивство контейнера `SIGKILL`, рестарт у тій самій підмережі | Трафік тимчасово припиняється на час перезапуску |
| **Readiness** | Контроль готовності до навантаження | Контейнер **НЕ перезапускається**; процес залишається живим | IP-адреса вилучається з балансувальників та Ingress |

## 4. Класи якості обслуговування (QoS Classes)

На основі заповнення блоків `requests` та `limits` оркестратор автоматично присвоює поду один із трьох класів якості обслуговування (**QoS** — Quality of Service), який визначає значення ядерного параметра пріоритету витіснення пам'яті (`/proc/[pid]/oom_score_adj` в Linux).

```
                             ┌───────────────────────────────┐
                             │ Чи вказані ресурси для ВСІХ  │
                             │    контейнерів у PodSpec?     │
                             └──────────────┬────────────────┘
                                            │
                     ┌──────────────────────┴──────────────────────┐
                     │ ТАК                                         │ НІ
                     ▼                                             ▼
       ┌───────────────────────────┐                         ┌───────────┐
       │ requests == limits для    │                         │  Якщо НЕ  │
       │ CPU та RAM у кожному?     │                         │ вказано   │
       └─────────────┬─────────────┘                         │  жодного  │
                     │                                       └─────┬─────┘
        ┌────────────┴────────────┐                                │
        │ ТАК                     │ НІ                             ▼
        ▼                         ▼                         ┌─────────────┐
 ┌──────────────┐          ┌─────────────┐                  │ BestEffort  │
 │  Guaranteed  │          │  Burstable  │                  └─────────────┘
 └──────────────┘          └─────────────┘
```

### Механізм витіснення пам'яті ядра Linux

Коли на сервері виникає дефіцит фізичної оперативної пам'яті, підсистема ядра Linux OOM Killer обирає процес-жертву на основі розрахунку підсумкового балу `oom_score`:

```
oom_score = (фактично_використана_пам'ять / загальна_пам'ять_системи) · 1000 + oom_score_adj
```

Оркестратор динамічно конфігурує системний файл `/proc/[pid]/oom_score_adj` для кожного контейнера:
1. **Guaranteed (`oom_score_adj = -997`):** Бали процесу штучно зменшуються на 997 одиниць. Ядро ніколи не вб'є контейнер Guaranteed, доки в системі залишається хоча б один процес інших класів.
2. **Burstable:** Значення розраховується пропорційно відношенню зарезервованої пам'яті до місткості ноди:
   ```
   oom_score_adj = 1000 - (1000 · memory_request) / node_capacity
   ```
   Якщо контейнер споживає менше задекларованого `requests.memory`, його `oom_score` залишається низьким. Якщо процес починає перевищувати бронь, наближаючись до `limits.memory`, його ймовірність бути знищеним різко зростає.
3. **BestEffort (`oom_score_adj = 1000`):** Максимально можливий бал ризику. Такі процеси витісняються ядром першими при найменшому наближенні до вичерпання пулу вільних сторінок RAM хоста.

## 5. Специфікація мережевої безпеки: NetworkPolicy

За замовчуванням мережева модель оркестратора є відкритою (**flat non-isolated network**): будь-який под у кластері може надсилати TCP/UDP пакети на IP-адресу будь-якого іншого пода. Для обмеження зв'язності використовується декларативний ресурс `NetworkPolicy`, який транслюється CNI-плагіном у правила ядра (eBPF tail calls або iptables `FORWARD`).

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: payment-isolation
  namespace: production
spec:
  podSelector:             # Цільова група подів, на які накладаються обмеження
    matchLabels:
      app: payment-db
  policyTypes:
    - Ingress
    - Egress
  ingress:                 # Правила для вхідного трафіку
    - from:
        - namespaceSelector:
            matchLabels:
              environment: production
          podSelector:
            matchLabels:
              app: payment-backend
      ports:
        - protocol: TCP
          port: 5432
  egress:                  # Правила для вихідного трафіку
    - to:
        - ipBlock:
            cidr: 10.0.0.0/8
            except:
              - 10.0.1.0/24
      ports:
        - protocol: TCP
          port: 443
```

Якщо для пода активовано `NetworkPolicy`, усі вхідні пакети від неавторизованих джерел блокуються ядром на етапі перевірки Netfilter/eBPF, повертаючи клієнту таймаут з'єднання або скидання `RST`.

## 6. Контракт інтерфейсу контролера (Reconciler API)

Усі контролери платформи реалізують єдиний декларативний інтерфейс циклу узгодження. Нижче наведено сигнатуру контракту мовою Go (стандарт контролерів Kubernetes / controller-runtime):

```go
// Request містить лише ключ ідентифікації об'єкта
type Request struct {
    types.NamespacedName
}

// Result керує наступною дією планувальника черги
type Result struct {
    // Requeue вказує негайно повернути ключ у чергу
    Requeue bool
    // RequeueAfter вказує поставити ключ у чергу з фіксованою затримкою
    RequeueAfter time.Duration
}

// Reconciler — фундаментальний інтерфейс обробника узгодження
type Reconciler interface {
    // Reconcile виконує читання стану, розрахунок різниці та коригувальні дії
    Reconcile(ctx context.Context, req Request) (Result, error)
}
```

### Семантика повернення значень методу `Reconcile`

1. `return Result{}, nil` — Узгодження успішне. Бажаний стан досягнуто, повторна постановка в чергу не потрібна до наступної зміни в etcd.
2. `return Result{RequeueAfter: 30 * time.Second}, nil` — Стан у процесі сходження (наприклад, очікування прогріву кешу або зовнішнього API). Ключ буде повторно оброблено через 30 секунд.
3. `return Result{}, err` — Сталася помилка виконання (таймаут мережі, конфлікт версій). Каркас контролера автоматично відправляє ключ у чергу з **експоненційним уповільненням (Exponential Backoff)**.

## 7. Коди стану та обробка помилок API Server

Взаємодія клієнтів із шлюзом API підпорядковується стандартним кодам HTTP REST із розширеною семантикою об'єкта `Status`:

| HTTP Код | Причина помилки (Reason) | Опис та рекомендована реакція клієнта |
| :--- | :--- | :--- |
| **`200 OK / 201 Created`** | `Success` | Запит успішно валідовано, мутовано та зафіксовано в etcd. |
| **`400 Bad Request`** | `Invalid` | Помилка синтаксису JSON/YAML або невідповідність OpenAPI-схемі. Повтор без виправлення маніфесту безглуздий. |
| **`401 Unauthorized`** | `Unauthorized` | Відсутній або прострочений TLS-сертифікат / JWT токен автентифікації. |
| **`403 Forbidden`** | `Forbidden` | Автентифікація успішна, але правила RBAC забороняють дію (Verb) над ресурсом. |
| **`404 Not Found`** | `NotFound` | Запитуваний ресурс або простір імен не існує в сховищі. |
| **`409 Conflict`** | `Conflict` | Конфлікт версії CAS (`resourceVersion` застарів). Клієнт зобов'язаний перечитати свіжий стан і повторити спробу. |
| **`422 Unprocessable`** | `InvalidValue` | Синтаксис вірний, але порушено бізнес-правило (наприклад, спроба змінити незмінне поле `spec.clusterIP`). |
| **`429 Too Many Requests`** | `TooManyRequests` | Спрацював лімітер частоти (API Priority and Fairness). Клієнт повинен застосувати Exponential Backoff із Jitter. |
| **`500 Internal Error`** | `InternalError` | Внутрішній збій API Server або падіння бази etcd. |
| **`503 Service Unavailable`** | `ServiceUnavailable` | Кворум etcd втрачено (впала більшість майстрів), запис заблоковано. |

## 8. Низькорівневі системні інтерфейси: CRI, CNI та CSI

Оркестратор делегує фізичні операції з операційною системою трьом стандартизованим плагінним інтерфейсам gRPC та JSON-CLI.

```
                    ┌─────────────────────────────────────────┐
                    │          Kubelet (Node Agent)           │
                    └────┬─────────────────┬────────────────┬─┘
                         │ gRPC            │ JSON/CLI       │ gRPC
                         ▼                 ▼                ▼
                  ┌─────────────┐   ┌─────────────┐  ┌─────────────┐
                  │     CRI     │   │     CNI     │  │     CSI     │
                  │ containerd  │   │  Cilium/BGP │  │ NVMe/Ceph   │
                  │   CRI-O     │   │   Calico    │  │ AWS EBS     │
                  └─────────────┘   └─────────────┘  └─────────────┘
```

### 1. CRI (Container Runtime Interface) — gRPC Proto специфікація

Керує життєвим циклом пісочниць (Pod Sandbox) та контейнерів:
```protobuf
service RuntimeService {
    rpc RunPodSandbox(RunPodSandboxRequest) returns (RunPodSandboxResponse);
    rpc StopPodSandbox(StopPodSandboxRequest) returns (StopPodSandboxResponse);
    rpc CreateContainer(CreateContainerRequest) returns (CreateContainerResponse);
    rpc StartContainer(StartContainerRequest) returns (StartContainerResponse);
    rpc StopContainer(StopContainerRequest) returns (StopContainerResponse);
    rpc ContainerStatus(ContainerStatusRequest) returns (ContainerStatusResponse);
}
```

### 2. CNI (Container Network Interface) — Потоковий JSON контракт

Плагін викликається локально як бінарний виконуваний файл з передачею параметрів через змінні середовища (`CNI_COMMAND=ADD`) та стандартний вхідний потік (stdin JSON):

```json
{
  "cniVersion": "1.0.0",
  "name": "cbr0-net",
  "type": "bridge",
  "bridge": "cbr0",
  "isGateway": true,
  "ipMasq": true,
  "ipam": {
    "type": "host-local",
    "subnet": "10.244.1.0/24",
    "routes": [{ "dst": "0.0.0.0/0" }]
  }
}
```

### 3. CSI (Container Storage Interface) — Двофазний контракт монтування дисків

Керує блочними сховищами у розподіленому середовищі:
- `ControllerPublishVolume` (Attach): Прив'язує хмарний диск (LUN / EBS) до конкретної віртуальної або фізичної машини хоста.
- `NodeStageVolume` (Format): Створює файлову систему (ext4, xfs) на щойно підключеному блочному пристрої `/dev/disk/by-id/...`.
- `NodePublishVolume` (Mount): Виконує системний виклик `mount --bind` змонтованого каталогу безпосередньо у файлову систему контейнера всередині `/var/lib/kubelet/pods/<pod-uid>/volumes/...`.
