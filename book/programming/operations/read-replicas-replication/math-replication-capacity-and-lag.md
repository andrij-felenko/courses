# 🧮 Математична модель пропускної здатності, лагу черги реплікації та ймовірності застарілого читання

Експлуатація кластера реплік вимагає точного кількісного аналізу фізичних процесів, що відбуваються в системі: за якої інтенсивності запису реплікаційний лаг починає нескінченно зростати, як розрахувати час відновлення після раптового спалаху навантаження, якою є математична ймовірність натрапити на застарілий стан під час читання та скільки реплік первинний вузол здатний живити напряму до вичерпання фізичної смуги пропускання мережевого інтерфейсу.

У цьому розділі виведено строгі аналітичні моделі теорії масового обслуговування, динаміку нестаціонарних перехідних процесів, теорію ймовірності сесійних збоїв та оптимізацію мережевого розгалуження.

---

## 1. Модель черги накатування журналу: СМО M/M/1 та M/D/1

Процес реплікації можна розглядати як класичну систему масового обслуговування (СМО), у якій генерація транзакцій на первинному вузлі утворює вхідний потік вимог, а процес відновлення на репліці (`apply process` у PostgreSQL або `SQL_THREAD` у MySQL) виступає в ролі обслуговуючого пристрою.

### Параметри системи та коефіцієнт утилізації

Нехай:
- `λ` — середня інтенсивність надходження транзакцій запису з первинного вузла (транзакцій на секунду, tx/s).
- `μ` — середня швидкість застосування транзакцій процесом відновлення на репліці (транзакцій на секунду, tx/s).
- `T_s = 1 / μ` — середній час, необхідний репліці для застосування однієї транзакції до локального сховища.

Коефіцієнт завантаження обслуговуючого пристрою (утилізація рушія реплікації) позначається грецькою літерою `ρ`:

```
ρ = λ ÷ μ = λ · T_s   [коефіцієнт утилізації рушія застосування змін]
```

### Умова стаціонарності системи

Для того щоб черга не застосованих транзакцій не зростала до нескінченності, обов'язковою є фундаментальна умова ергодичності:

```
ρ < 1   ⇔   λ < μ   [швидкість накатування обов'язково перевищує швидкість генерації запису]
```

Якщо `ρ = 1` або `ρ > 1`, система входить у нестаціонарний режим: репліка не встигає обробляти транзакції, розмір черги зростає монотонно, а реплікаційний лаг збільшується з кожною секундою.

---

### Стаціонарний стан: Довжина черги та час відставання

Залежно від характеру навантаження та структури журналу транзакцій застосовують дві різні аналітичні моделі:

#### А. Модель M/M/1 (Пуассонівський вхідний потік, експоненційний час обробки)
Ця модель застосовується у випадках, коли транзакції мають суттєво різний розмір (наприклад, прості оновлення одного рядка чергуються з важкими транзакціями на сотні рядків). Час обробки `T_s` є випадковою величиною з високою дисперсією `σ² = (1 / μ)²`.

Середня кількість транзакцій, що очікують у черзі реплікації `L_q`, та середній час очікування транзакції в черзі `W_q` (що є математичним очікуванням реплікаційного лагу у секундах) становлять:

```
L_q = ρ² ÷ (1 − ρ)          [середня довжина черги транзакцій у моделі M/M/1]
W_q = L_q ÷ λ = ρ ÷ (μ·(1 − ρ))   [формула Літтла: середній лаг реплікації у секундах]
```

#### Б. Модель M/D/1 (Пуассонівський вхідний потік, детермінований час обробки)
Ця модель описує оптимізовану рядкову логічну реплікацію (Row-Based Replication), де кожна операція являє собою стандартизовану бінарну дельту фіксованого розміру. У цьому випадку дисперсія часу обслуговування дорівнює нулю (`σ² = 0`).

Згідно з універсальною формулою Поллачека — Хінчина для черг типу M/G/1:

```
L_q = ρ² ÷ (2·(1 − ρ))      [середня довжина черги при нульовій дисперсії]
W_q = ρ ÷ (2·μ·(1 − ρ))     [середній лаг реплікації у моделі M/D/1]
```

*Математичний висновок:* Перехід від довільних нерівномірних транзакцій до детермінованих рядкових блоків скорочує середній реплікаційний лаг та довжину черги рівно вдвічі при тому самому коефіцієнті завантаження `ρ`.

### Числовий приклад розрахунку стаціонарного лагу

Розглянемо високостійку базу даних, у якій:
- Первинний вузол генерує `λ = 4000` операцій запису на секунду.
- Репліка читання має пропускну здатність процесу відновлення `μ = 5000` операцій на секунду.

Розрахуємо коефіцієнт утилізації:

```
ρ = 4000 ÷ 5000 = 0.80   [завантаження становить 80%]
```

Обчислимо середній лаг реплікації для обох моделей:

```
W_q (M/M/1) = 0.80 ÷ (5000 · (1 − 0.80))
= 0.80 ÷ (5000 · 0.20)
= 0.80 ÷ 1000
= 0.0008 секунди = 0.80 мілісекунди

W_q (M/D/1) = 0.80 ÷ (2 · 5000 · (1 − 0.80))
= 0.80 ÷ (10000 · 0.20)
= 0.80 ÷ 2000
= 0.0004 секунди = 0.40 мілісекунди
```

Якщо інтенсивність транзакцій зростає на 20% і досягає `λ = 4800` tx/s (`ρ = 0.96`):

```
W_q (M/D/1) = 0.96 ÷ (2 · 5000 · (1 − 0.96))
= 0.96 ÷ (10000 · 0.04)
= 0.96 ÷ 400
= 0.0024 секунди = 2.40 мілісекунди
```

При наближенні коефіцієнта завантаження до критичної одиниці лаг зростає нелінійно за гіперболічним законом `1 / (1 − ρ)`.

## 2. Динаміка нестаціонарного спалаху (Transient Burst Dynamics)

У моменти запуску важких міграцій схеми, нічних пакетних оновлень (Batch Updates) або пікових промо-кампаній інтенсивність генерації журналу на лідері тимчасово перевищує пропускну здатність репліки: `λ_burst > μ`. У цьому випадку стаціонарний стан руйнується, а утилізація `ρ > 1`.

Нехай спалах навантаження триває фіксований час `T_burst` (у секундах).

```
Інтенсивність
    ▲
    │        ┌────────────────────────┐  λ_burst (наприклад, 10 000 tx/s)
    │        │                        │
    │ ───────┼────────────────────────┼─────── μ (швидкість apply = 5 000 tx/s)
    │        │  Накопичення черги     │
    │ ───────┘                        └─────── λ_base (базовий рівень = 2 000 tx/s)
    └────────┬────────────────────────┬─────────► Час (t)
            t_0                    t_0 + T_burst
```

### Диференціальне рівняння приросту черги

Протягом інтервалу `0 ≤ t ≤ T_burst` швидкість накопичення не застосованих транзакцій у буфері репліки описується диференціальним рівнянням:

```
dQ(t)/dt = λ_burst − μ   [швидкість лінійного росту черги]
```

Інтегруючи це рівняння від `0` до `T_burst`, отримуємо піковий розмір черги `Q_max` на момент завершення спалаху:

```
Q_max = (λ_burst − μ) · T_burst   [максимальна кількість транзакцій у черзі]
```

Піковий часовий лаг реплікації `Lag_max` (у секундах відставання) на момент завершення спалаху дорівнює:

```
Lag_max = Q_max ÷ μ = ((λ_burst − μ) ÷ μ) · T_burst   [піковий лаг у секундах]
```

### Фаза розсмоктування черги (Drain Phase)

Після моменту `t = T_burst` інтенсивність вхідного потоку спадає до нормального базового рівня `λ_base < μ`. Швидкість, з якою репліка скорочує накопичену чергу, визначається різницею продуктивності:

```
dQ_drain(t)/dt = −(μ − λ_base)   [швидкість ліквідації накопиченого відставання]
```

Повний час, необхідний репліці для повної ліквідації лагу та повернення до стаціонарного стану `T_drain`, обчислюється як:

```
T_drain = Q_max ÷ (μ − λ_base)
= T_burst · (λ_burst − μ) ÷ (μ − λ_base)   [час відновлення актуальності репліки]
```

Загальна тривалість періоду деградації системи (протягом якого репліка має підвищений лаг) становить `T_total = T_burst + T_drain`.

---

### Практичний розрахунок наслідків спалаху

Нехай кластер бази даних має такі експлуатаційні характеристики:
- Пропускна здатність репліки: `μ = 5000` tx/s.
- Базове навантаження: `λ_base = 2000` tx/s.
- Спалах запису: `λ_burst = 10000` tx/s (подвоєне навантаження) тривалістю `T_burst = 60` секунд (1 хвилина).

Обчислимо ключові метрики інциденту:

1. Пікова черга транзакцій:
```
Q_max = (10000 − 5000) · 60 = 5000 · 60 = 300 000 транзакцій
```

2. Максимальний лаг реплікації:
```
Lag_max = 300 000 ÷ 5000 = 60 секунд відставання
```

3. Час ліквідації черги після закінчення спалаху:
```
T_drain = 300 000 ÷ (5000 − 2000) = 300 000 ÷ 3000 = 100 секунд (1 хвилина 40 секунд)
```

4. Загальний час аварійного стану:
```
T_total = 60 + 100 = 160 секунд (2 хвилини 40 секунд)
```

*Інженерний висновок:* Хвилинний спалах активності генерує затримку у 60 секунд і виводить репліку з ладу майже на три хвилини. Протягом усього цього часу будь-який запит клієнта повертатиме застарілий стан, якщо в системі відсутня LSN-маршрутизація.

## 3. Математична ймовірність застарілого читання (Stale Read Probability)

Оцінимо ймовірність виникнення аномалії *Read-Your-Own-Writes*, коли клієнт після мутації стану звертається до випадкової асинхронної репліки через часовий інтервал `Δt` (наприклад, час виконання HTTP-редиректу).

Нехай `X_lag` — випадкова величина поточного реплікаційного лагу в секундах. Клієнт отримає застарілий стан тоді і тільки тоді, коли фактичний лаг репліки в момент запиту перевищує інтервал між записом і читанням:

```
P(Stale | Δt) = P(X_lag > Δt)   [ймовірність читання застарілого знімка даних]
```

У стаціонарному режимі системи M/M/1 щільність розподілу часу очікування підпорядковується показниковому (експоненційному) закону з параметром згасання `γ = μ · (1 − ρ)`:

```
P(X_lag > Δt) = e^(−μ·(1 − ρ)·Δt)   [функція ймовірності застарілого читання]
```

### Аналіз впливу утилізації на ймовірність помилки

Візьмемо типовий інтервал редиректу браузера `Δt = 50 мс = 0.050 с` та продуктивність репліки `μ = 5000` tx/s:

1. **Низька утилізація (`ρ = 0.50`):**
```
γ = 5000 · (1 − 0.50) = 2500
P(Stale) = e^(−2500 · 0.050) = e^(−125) ≈ 5 · 10⁻⁵⁵ ≈ 0%
```

2. **Середня утилізація (`ρ = 0.80`):**
```
γ = 5000 · (1 − 0.80) = 1000
P(Stale) = e^(−1000 · 0.050) = e^(−50) ≈ 1.9 · 10⁻²² ≈ 0%
```

3. **Висока утилізація (`ρ = 0.98` — передкритичний стан):**
```
γ = 5000 · (1 − 0.98) = 100
P(Stale) = e^(−100 · 0.050) = e^(−5.0) ≈ 0.006737 (0.67% клієнтів побачать старі дані)
```

4. **Критична утилізація (`ρ = 0.995`):**
```
γ = 5000 · (1 − 0.995) = 25
P(Stale) = e^(−25 · 0.050) = e^(−1.25) ≈ 0.2865 (28.6% клієнтів отримають помилку)
```

*Висновок:* Поки коефіцієнт утилізації репліки утримується нижче `0.90`, ймовірність застарілого читання при типових веб-інтервалах прямує до нуля. Проте щойно навантаження досягає `98–99%`, кожен сотий користувач стикається з аномалією, що вимагає обов'язкового застосування сесійного закріплення (Session Pinning).

## 4. Обмеження мережевого розгалуження лідера (Fan-out Scaling)

Первинний вузол зобов'язаний транслювати кожен згенерований байт журналу WAL кожній підключеній фізичній репліці.

### Баланс мережевого трафіку

Нехай:
- `B_wal` — швидкість генерації журналу на лідері під час активного запису (МБ/с).
- `C_nic` — фізична пропускна здатність мережевої карти сервера лідера (МБ/с).
- `η` — коефіцієнт корисного використання каналу з урахуванням службових заголовків TCP/IP, кадрів Ethernet та накладних витрат TLS-шифрування (`η ≈ 0.80–0.85`).
- `N` — кількість одночасно підключених реплік.

Сумарний вихідний мережевий трафік лідера `B_egress` зростає строго лінійно:

```
B_egress = N · B_wal   [пряма лінійна залежність вихідного трафіку від кількості реплік]
```

### Фізична межа кількості реплік

Умова безаварійної роботи мережевого інтерфейсу вимагає:

```
N · B_wal ≤ C_nic · η
N_max = ⌊(C_nic · η) ÷ B_wal⌋   [максимально допустима кількість реплік для прямого підключення]
```

#### Розрахунок граничного розгалуження:
- Сервер має мережевий інтерфейс `10 Gbps Ethernet` (`C_nic ≈ 1190 МБ/с`).
- Інтенсивний транзакційний запис генерує `B_wal = 120 МБ/с` потоку WAL.
- Коефіцієнт каналу: `η = 0.85`.

```
N_max = ⌊(1190 · 0.85) ÷ 120⌋ = ⌊1011.5 ÷ 120⌋ = 8 реплік
```

Підключення 9-ї репліки викличе 100% насичення вихідного мережевого буфера лідера. Пакети почнуть відкидатися, спрацює механізм TCP Congestion Control, швидкість відправки WAL впаде для всіх реплік одночасно, і весь кластер увійде в стан неконтрольованого зростання лагу.

## 5. Оптимізація каскадного дерева реплікації (Cascading Tree Optimization)

Для подолання обмеження `N_max` будують дворівневу каскадну топологію:
- Первинний вузол передає потік WAL лише на `k` проміжних вузлів (Relay Nodes / Standby Masters).
- Кожен Relay-вузол роздає потік на `m` листових реплік читання (Leaf Replicas).

Загальна кількість реплік читання, які обслуговують клієнтські запити:

```
N = k · m   [загальна ємність дворівневого кластера]
```

Вихідний мережевий трафік на первинному вузлі становить лише `k · B_wal` замість `(k · m) · B_wal`.

```
                  Primary (Лідер)
                  ┌─────────────┐
                  │ Egress: k·B │
                  └──────┬──────┘
            ┌────────────┴────────────┐
            ▼                         ▼
      Relay Node 1              Relay Node 2
      ┌─────────────┐           ┌─────────────┐
      │ Egress: m·B │           │ Egress: m·B │
      └──────┬──────┘           └──────┬──────┘
        ┌────┴────┐               ┌────┴────┐
        ▼         ▼               ▼         ▼
     Leaf 1    Leaf 2          Leaf 3    Leaf 4
```

При симетричному дереві (`k = m = √N`) трафік на первинному вузлі зменшується з `O(N)` до `O(√N)`:

```
B_primary_cascade = √N · B_wal   [сублінійне навантаження на мережу лідера]
```

Для кластера з `N = 64` реплік читання симетричне дерево з `k = 8` проміжними вузлами вимагає від первинного вузла смуги лише на 8 з'єднань (`960 МБ/с`), що повністю вкладається в ліміт карти 10 Gbps, забезпечуючи стабільну роботу кластера будь-якого масштабу.
