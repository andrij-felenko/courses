# 📜 Еволюція управління з'єднаннями: від CGI-скриптів до HikariCP та PgBouncer

Коли на початку 1990-х років Всесвітнє павутиння робило перші кроки, веб-сервери працювали за простою моделлю: кожен HTTP-запит викликав запуск окремого процесу через загальний шлюзовий інтерфейс (англ. *Common Gateway Interface, CGI*). Скрипт мовою Perl або C запускався операційною системою, зчитував змінні оточення, відкривав мережевий TCP-сокет до сервера бази даних, проходив процедуру автентифікації, виконував один SQL-запит, генерував HTML-сторінку й негайно завершував роботу, викликаючи `exit(0)`. Операційна система знищувала процес, а мережевий стек закривав з'єднання.

Поки відвідуваність сайтів вимірювалася кількома десятками запитів на годину, ця схема функціонувала бездоганно. Проте з появою комерційного інтернету та перших систем електронної комерції навантаження стрімко зросло. Веб-сервери почали приймати сотні запитів на секунду. Кожен такий запит змушував сервер баз даних створювати новий робочий процес, виділяти віртуальну пам'ять для буферів сесії та проводити важку криптографічну перевірку паролів.

## Перші спроби: постійні процеси та з'єднання mod_php

Першим кроком подолання накладних витрат CGI стала відмова від перезапуску самого веб-сервера. У 1995 році з'явився веб-сервер Apache HTTP Server із моделлю попереднього створення процесів (англ. *prefork MPM*). Замість одноразових скриптів інтерпретатори мов програмування вбудовували безпосередньо в процес веб-сервера через модулі розширення — найвідомішим із яких став `mod_php`.

У цій архітектурі народилася ідея «постійних з'єднань» (англ. *persistent connections*), реалізована функцією `mysql_pconnect()` у PHP та аналогами в Perl DBI (`Apache::DBI`). Замість закриття сокета після генерації сторінки інтерпретатор зберігав файловий дескриптор у глобальній хеш-таблиці процесу за ключем `хост:порт:користувач`. Наступний HTTP-запит, який потрапляв у той самий процес Apache, миттєво використовував уже відкритий сокет без повторного мережевого рукостискання.

Однак постійні з'єднання `mod_php` швидко породили нову системну кризу:
- **Жорстка прив'язка до кількості веб-воркерів:** Якщо веб-сервер Apache налаштовували на обробку 500 одночасних клієнтів (`MaxRequestWorkers 500`), він утримував рівно 500 відкритих TCP-з'єднань до СУБД. Навіть коли клієнт повільно завантажував картинку або тримав відкриту сторінку через HTTP Keep-Alive, виділене процесу з'єднання з базою даних простоювало, заблоковане для інших клієнтів.
- **Забруднення стану сесії:** Якщо скрипт змінював локальну часову зону (`SET TIME ZONE`), створював тимчасову таблицю (`CREATE TEMP TABLE`) або не закривав відкриту транзакцію через фатальну помилку виконання, наступний випадковий користувач отримував «брудне» з'єднання з чужим контекстом виконання та незафіксованими замками.
- **Вичерпання лімітів СУБД:** Кілька серверів веб-додатків із вбудованими пулами Apache миттєво доводили кількість відкритих сокетів до тисяч, паралізуючи ядро бази даних.

Стало зрозуміло: пул з'єднань не може бути простим побічним ефектом кешування змінних у процесі веб-сервера. Він мав стати самостійним архітектурним компонентом із суворим контролем життєвого циклу.

## Епоха багатопотокових пулів Java та JDBC

Наприкінці 1990-х і на початку 2000-х років розвиток платформи Java Enterprise Edition (J2EE) сформував класичну парадигму клієнтського пулу з'єднань. Багатопотокові сервери застосунків (BEA WebLogic, IBM WebSphere, Apache Tomcat) обслуговували запити спільним пулом потоків, де кожна транзакція вимагала оренди об'єкта `java.sql.Connection` через стандартний інтерфейс `DataSource`.

Перше покоління відкритих пулів з'єднань — Apache Commons DBCP (2001 рік) та C3P0 (2001 рік) — базувалося на важких колекціях із грубим синхронним блокуванням (англ. *coarse-grained locking*). Кожна спроба взяти з'єднання з пулу або повернути його назад вимагала захоплення єдиного глобального монітора (`synchronized`).

Коли кількість процесорних ядер у серверах зросла з 2 до 8 і 16, грубе блокування стало головним вузьким місцем багатопотокових систем:
1. **Конкуренція за блокування (Lock Contention):** Десятки робочих потоків одночасно намагалися викликати `getConnection()`, проводячи більше часу в очікуванні звільнення системного м'ютекса, ніж на виконанні самого SQL-запиту.
2. **Перевірка живості через важкі запити:** Для захисту від обірваних з'єднань пули виконували валідаційний запит `SELECT 1` на кожну оренду сокета. На корисний запит застосунку припадав один фіктивний службовий запит, що подвоювало навантаження на аналізатор запитів і транзакційний лог СУБД.
3. **Витоки пам'яті через відстеження стейтментів:** Спроби пулів кешувати підготовлені вирази (Prepared Statements) усередині обгорток з'єднань часто призводили до вичерпання купи Java (OutOfMemoryError) через надмірну глибину об'єктних графів.

У 2009 році з'явився пул BoneCP, автори якого вперше розділили пул на кілька паралельних сегментів (англ. *partitioning*), щоб зменшити конкуренцію потоків. Проте сегментація була лише частковим паліативом: за нерівномірного навантаження потоки голодували в одному сегменті, поки з'єднання бездіяльно очікували в іншому.

## Революція нульових накладних витрат: поява HikariCP

У 2013 році інженер Бретт Вулдрідж (Brett Wooldridge) представив проєкт HikariCP (від японського *hikari* — світло, блискавка), який кардинально змінив інженерні підходи до побудови високонавантажених пулів ресурсів. Вулдрідж поставив перед собою завдання усунути всі джерела накладних витрат процесора між застосунком та драйвером бази даних.

Прорив HikariCP базувався на чотирьох фундаментальних оптимізаціях:
- **Відмова від синхронізації на користь безблокових черг:** Замість традиційних блокувальних черг `LinkedBlockingQueue` було створено спеціалізовану колекцію `FastList`, оптимізовану під доступ за принципом LIFO, та безблокову структуру на базі `Lock-Free ArrayList` з атомарними порівняннями й перестановками (CAS).
- **Пряма генерація байт-коду замість динамічних проксі:** Традиційні пули огортали кожен JDBC-інтерфейс через важкий рефлексивний механізм `java.lang.reflect.Proxy`. HikariCP перейшов на пряму компіляцію байт-коду обгорток за допомогою Javassist на етапі ініціалізації, завдяки чому виклики методів з'єднання стали інлайнитися JIT-компілятором без жодного оверхеду.
- **Оптимізація роботи з кешами процесора:** Усі поля структур даних були вирівняні під розміри рядків кешу L1/L2 процесора для повного усунення ефекту хибного спільного використання пам'яті (False Sharing).
- **Використання драйверного методу isValid():** Замість важкого синтаксичного розбору запитів `SELECT 1` HikariCP перейшов на виклик нативного методу JDBC 4.0 `Connection.isValid()`, який надсилає низькорівневий мережевий ping-пакет безпосередньо у протокол СУБД.

Бенчмарки показали, що HikariCP виконував операції взяття й повернення з'єднання за лічені наносекунди — у 10–50 разів швидше за DBCP та C3P0. Завдяки цьому HikariCP став де-факто стандартом індустрії та був інтегрований як типовий пул за замовчуванням у Spring Boot та більшість сучасних фреймворків.

## Вихід на рівень інфраструктури: PgBouncer, Odyssey та ProxySQL

Паралельно з розвитком клієнтських пулів виникла потреба в централізованому управлінні з'єднаннями на рівні серверної інфраструктури. Особливо гостро ця проблема постала перед користувачами СУБД PostgreSQL, архітектура якої побудована на моделі окремих процесів операційної системи (`fork()`).

Кожне відкрите з'єднання в PostgreSQL споживає від 5 до 20 МБ оперативної пам'яті під робочі структури процесу (`relcache`, `syscache`, кеші планів запитів). Коли кількість мікросервісів у компаніях досягла сотень, а кожен екземпляр сервісу тримав свій локальний клієнтський пул на 20 з'єднань, база даних опинялася під тиском 5 000–10 000 одночасних процесів. Операційна система витрачала до 80% ресурсів процесора лише на перемикання контексту ядра та конкуренцію за загальні буфери пам'яті.

Для вирішення цієї проблеми у 2007 році компанія Skype розробила спеціалізований проміжний проксі-пулер **PgBouncer**. Головною інновацією PgBouncer стала підтримка трьох режимів пулінгу:
1. **Сесійний пулінг (Session Pooling):** Сокет виділяється клієнту на весь час сесії.
2. **Транзакційний пулінг (Transaction Pooling):** Найефективніший режим, за якого фізичне серверне з'єднання надається клієнту лише на час виконання транзакції (`BEGIN ... COMMIT`). Щойно транзакція зафіксована, з'єднання повертається в загальний пул проксі і в ту саму мілісекунду передається іншому клієнтському запиту.
3. **Пулінг операторів (Statement Pooling):** З'єднання звільняється після кожного окремого SQL-виразу (не підтримує багаторядкові транзакції).

Транзакційний пулінг дав змогу утримувати 10 000 активних клієнтських з'єднань застосунків усього на 30–50 фізичних процесах ядра PostgreSQL. Згодом з'явилися багатопотоковий пул **Odyssey** від Yandex (із підтримкою легкої асинхронної обробки на корутинах) та **pgcat** (із вбудованим шардингом і балансуванням реплік), а для екосистеми MySQL — **ProxySQL**.

## Хмарна трансформація: Serverless, лямбда-функції та AWS RDS Proxy

Новий виток архітектурного протистояння розпочався у другій половині 2010-х років із масовим поширенням безсерверних обчислень (англ. *Serverless / FaaS*, Function-as-a-Service). У моделі AWS Lambda чи Google Cloud Functions кожен виклик функції виконується в ізольованому мікроконтейнері, який живе від кількох секунд до кількох хвилин.

Коли спалах трафіку ініціював одночасний запуск 3 000 екземплярів безсерверних функцій, кожна лямбда намагалася відкрити власне незалежне TCP-з'єднання до реляційної СУБД. Виникав ефект «шторму підключень» (англ. *connection storm*), який за кілька секунд повністю вичерпував ліміт `max_connections` і клав кластер бази даних. Ба більше, короткоживучі функції не могли підтримувати локальний клієнтський пул, оскільки кожна функція заморожувалася операційною системою між викликами.

Для вирішення цієї кризи у 2020 році хмарні провайдери випустили керовані балансувальники з'єднань, такі як **AWS RDS Proxy**. Архітектура RDS Proxy побудована на винесенні проксі-шару в окремий високонадійний кластер із автоматичним збереженням пулу теплих з'єднань до бази даних і підтримкою автентифікації через IAM-ролі та протокол Secrets Manager.

Одночасно виникла запекла інженерна дискусія щодо так званого «прив'язування сесії» (англ. *connection pinning*). Якщо застосунок у транзакційному режимі виконує команду встановлення параметрів сесії (`SET application_name` або `SET search_path`), створює підготовлений вираз без іменування або використовує консультативні замки (`pg_advisory_lock`), проксі-сервер не може безпечно повернути сокет в загальний пул після `COMMIT`. У такому разі проксі змушений «прив'язувати» фізичне з'єднання до конкретної лямбда-функції аж до її повного знищення, що частково нівелює вигоду від пулінгу.

Сучасні протоколи баз даних (зокрема розширення протоколу PostgreSQL 14+ та драйвери з підтримкою `DISCARD TEMP`) цілеспрямовано адаптують ядро СУБД під вимоги зовнішніх проксі, доводячи, що управління з'єднаннями стало спільним завданням як прикладного софту, так і хмарної мережевої інфраструктури.

Еволюція довела: пул з'єднань пройшов шлях від примітивного кешування файлових дескрипторів у скриптах до багаторівневої системи управління ресурсами, де швидкий внутрішньопроцесний клієнтський пул співпрацює з високоефективним інфраструктурним проксі для забезпечення стабільності всієї розподіленої системи.
