# 🧮 Математика швидкості вигорання та мульти-віконних алертів

Формалізація надійності розподілених систем вимагає переходу від інтуїтивних оцінок до точного математичного апарату теорії ймовірностей, математичної статистики та аналізу часових рядів. Будь-який рівень обслуговування описується набором числових метрик, над якими будуються контури оцінки, прогнозування вичерпання ресурсів та автоматичного сповіщення.

## Дискретна та неперервна подійні моделі SLI

Індикатор рівня обслуговування (SLI) описує фактичну якість функціонування системи на часовому проміжку `T = [t_start, t_end]`.

У дискретній подійній моделі (Request-based SLI) робота сервісу розглядається як потік окремих атомарних подій (запитів, повідомлень у черзі, фінансових транзакцій) `E = {e_1, e_2, ..., e_N}`. Для кожної події `e_i` визначаються дві бінарні характеристичні функції:

1. **Функція валідності події `V(e_i) ∈ {0, 1}`:**
   Визначає, чи належить подія до сфери відповідальності сервісу. Наприклад, HTTP-запит із синтаксичною помилкою клієнта (код `400 Bad Request`) або неіснуючим URL (`404 Not Found`) не є відмовою сервера, тому `V(e_i) = 0`. Запит до дійсного ендпойнта з коректними параметрами має `V(e_i) = 1`.

2. **Функція задоволеності (успішності) події `G(e_i) ∈ {0, 1}`:**
   Визначає, чи був запит оброблений відповідно до критеріїв якості. Запит вважається хорошим (`G(e_i) = 1`), якщо сервер повернув успішний статус (`2xx` або `3xx`), а повний час очікування відповіді клієнтом `Latency(e_i)` не перевищив граничного порогу `L_max` (наприклад, 200 мс).

Фактичний рівень індикатора обчислюється як відношення кількості успішних валідних подій до загальної кількості валідних подій:

```
SLI = ( ∑_{i=1}^N G(e_i)·V(e_i) ) / ( ∑_{i=1}^N V(e_i) )
```

У неперервній часовій моделі (Window-based або Uptime-based SLI) проміжок спостереження `T` розбивається на `M` рівних інтервалів тривалістю `Δt` (наприклад, `Δt = 1 хвилина`). Інтервал `k` позначається як працездатний (`U_k = 1`), якщо частка помилок усередині цієї хвилини була меншою за допустимий поріг `θ` (наприклад, `θ = 0.01`):

```
SLI_time = ( ∑_{k=1}^M U_k ) / M,    де M = T / Δt
```

### Чому подійна модель переважає часову

Часова модель має істотну ваду: вона розглядає кожну хвилину як рівноцінну незалежно від інтенсивності навантаження. Збій тривалістю 5 хвилин о 03:00 ночі (коли сервіс обробляє 10 запитів на секунду) і збій тривалістю 5 хвилин о 14:00 під час пікового навантаження (коли надходить 50 000 запитів на секунду) в часовій моделі мають однаковий негативний внесок у показник доступності.

Подійна модель автоматично зважує вплив аварії за обсягом реального трафіку: у нічному випадку буде втрачено лише 3 000 запитів, тоді як у денному — 15 000 000 запитів. Відповідно, подійна модель набагато точніше відображає реальний сукупний біль користувачів.

## Математичне визначення цілі (SLO) та бюджету помилок

Нехай цільовий рівень надійності зафіксовано в SLO на ковзному часовому інтервалі `T_SLO` (типово 30 календарних днів = 720 годин = 43 200 хвилин = 2 592 000 секунд) як дійсне число `S ∈ (0, 1)`.

**Бюджет помилок (Error Budget, `B`)** визначається як математичне доповнення цілі до одиниці:

```
B = 1 - S
```

Для цілі `S = 0.999` (99.9%) бюджет помилок становить `B = 0.001` (0.1%).

Місткість бюджету помилок може бути виражена у двох взаємозамінних вимірах:

1. **У допустимій кількості збійних подій:**
   ```
   Bad_allowed = B · N_valid = (1 - S) · N_valid
   ```
   Якщо за обліковий період надійшло `N_valid = 100 000 000` запитів при цілі `S = 0.999`, сервіс має право завершити з помилкою не більше `100 000` запитів.

2. **У часі допустимого сумарного простою:**
   ```
   Downtime_allowed = B · T_SLO = (1 - S) · T_SLO
   ```

Для стандартного 30-денного періоду (`43 200 хвилин`) допустимий час простою становить:
* При `SLO = 99.0%` (`B = 0.01`): `432 хвилини` (7 годин 12 хвилин);
* При `SLO = 99.9%` (`B = 0.001`): `43.2 хвилини` (43 хвилини 12 секунд);
* При `SLO = 99.95%` (`B = 0.0005`): `21.6 хвилини` (21 хвилина 36 секунд);
* При `SLO = 99.99%` (`B = 0.0001`): `4.32 хвилини` (4 хвилини 19.2 секунди);
* При `SLO = 99.999%` (`B = 0.00001`): `0.432 хвилини` (25.92 секунди).

## Коефіцієнт швидкості вигорання (Burn Rate)

Під час стабільної роботи системи помилки виникають рідко, і бюджет споживається повільно. Під час збоїв частка відмов різко зростає, що призводить до прискореного вичерпання запасу надійності.

**Коефіцієнт швидкості вигорання (Burn Rate, `b`)** визначається як відношення поточної фактичної частки помилок `ErrorRate_curr` до гранично допустимої частки помилок, обумовленої бюджетом:

```
b = (1 - SLI_curr) / (1 - S) = ErrorRate_curr / B
```

Розглянемо фізичний зміст значень коефіцієнта `b`:
* **`b = 0.0`:** Повна відсутність помилок (`SLI = 1.0`). Бюджет взагалі не витрачається.
* **`b = 1.0`:** Фактична частота помилок точно дорівнює плановій (`ErrorRate = 1 - S`). При постійному збереженні цієї швидкості весь бюджет буде вичерпано рівно наприкінці періоду `T_SLO` (за 30 днів).
* **`b > 1.0`:** Бюджет вигорає швидше, ніж дозволяє план. Система рухається до передчасного вичерпання запасу надійності.
* **`b = 14.4`:** Швидкість, за якої 100% місячного бюджету згорає за `720 / 14.4 = 50 годин` (трохи більше 2 діб).

Час до повного вичерпання бюджету `T_exhaust` при сталій швидкості `b` виражається формулою:

```
T_exhaust = T_SLO / b
```

Частка бюджету `F_consumed`, яка витрачається за довільне часове вікно тривалістю `w`:

```
F_consumed = b · (w / T_SLO)
```

**Приклад розрахунку частки витрати:**
Нехай тривалість облікового періоду `T_SLO = 30 днів = 720 годин`, вікно оцінки становить `w = 1 година`, а поточний коефіцієнт швидкості вигорання дорівнює `b = 14.4`.

```
F_consumed
= 14.4 · (1 / 720)       [підстановка значень параметрів]
= 14.4 / 720             [виконання множення]
= 0.02                   [результат: 0.02, або 2.0% бюджету]
```

Отже, швидкість вигорання `b = 14.4` протягом однієї години призводить до втрати рівно `2%` від усього місячного ліміту помилок.

## Чому одновіконний алертинг створює нерозв'язну дилему

Першим інженерним підходом до сповіщень на базі SLO був простий поріг над єдиним часовим вікном `w`:
`Сповіщення активується, якщо BurnRate(w) > b_threshold`.

Ця схема страждає від фундаментального статистичного компромісу між чутливістю та хибними спрацюваннями:

1. **Коротке вікно (`w = 5 хвилин`):**
   * *Перевага:* Швидка реакція. Якщо сервіс повністю впав, алерт спрацює максимум через 5 хвилин.
   * *Недолік:* Висока частота хибних тривог через мікросплески. Якщо під час планового рестарту одного вузла виникло 10 збійних запитів, короткочасний `BurnRate(5m)` підскочить до `30×`–`50×`, викликавши тривогу серед ночі, хоча сумарна втрата бюджету становила нікчемні `0.002%`.

2. **Довге вікно (`w = 1 година` або `w = 6 годин`):**
   * *Перевага:* Надійна фільтрація мікросплесків. Короткий сплеск розчиняється у великому знаменнику тривалого вікна.
   * *Недолік — затримка очищення (Reset Lag):* Якщо тяжка аварія тривала 10 хвилин і була повністю ліквідована інженером шляхом відкочування збірки, середнє значення помилок за 1-годинне вікно залишатиметься вище порогу ще впродовж наступних 50 хвилин. Система продовжуватиме генерувати тривожні сповіщення щодо інциденту, який уже вирішено.

## Алгоритм Multi-Window Multi-Burn-Rate (MWMBR)

Для повного усунення дилеми Google SRE розробили алгоритм **мульти-віконного оцінювання за кількома швидкостями вигорання**.

### Логічна структура перевірки

Алерт активується тоді й лише тоді, коли поріг швидкості вигорання перевищено **одночасно** у двох узгоджених вікнах: довгому (`w_long`) та короткому (`w_short`):

```
ALERT_STATE = ( BurnRate(w_long) > b_threshold ) ∧ ( BurnRate(w_short) > b_threshold )
```

Оптимальне геометричне співвідношення тривалості вікон доведено емпірично та математично:

```
w_short = w_long / 12
```

Для стандартних інтервалів моніторингу це дає пари:
* Довге вікно `w_long = 1 година` (60 хв) → Коротке вікно `w_short = 5 хвилин`;
* Довге вікно `w_long = 6 годин` (360 хв) → Коротке вікно `w_short = 30 хвилин`;
* Довге вікно `w_long = 24 години` → Коротке вікно `w_short = 2 години`;
* Довге вікно `w_long = 3 доби` (72 години) → Коротке вікно `w_short = 6 годин`.

### Доведення математичних властивостей MWMBR

1. **Мінімальний час виявлення (Fast Time to Detect):**
   Якщо виникає масштабна системна аварія зі швидкістю `b ≥ b_threshold`, значення `BurnRate` у короткому вікні `w_short` перевищує поріг уже за час `t = w_short`. Оскільки довге вікно також наповнюється з тією самою інтенсивністю, обидві умови кон'юнкції виконуються за час `w_short` (наприклад, 5 хвилин для критичного рівня).

2. **Стійкість до одиничних мікросплесків (Noise Immunity):**
   Нехай виник одиничний сплеск помилок тривалістю `t_spike = 1 хвилина` зі швидкістю `b_spike = 50`.
   У короткому вікні `w_short = 5 хв` середнє значення складе `(50 · 1) / 5 = 10`, що перевищує поріг `b_threshold = 14.4` лише на мить.
   У довгому вікні `w_long = 60 хв` середній внесок складе `(50 · 1) / 60 = 0.83`, що набагато менше за `14.4`.
   Умова `(0.83 > 14.4) ∧ (10 > 14.4)` повертає `0 ∧ 0 = 0`, і хибне спрацювання повністю блокується.

3. **Швидке автоматичне скидання (Fast Auto-Reset):**
   Щойно інженер ліквідує несправність, потік помилок припиняється. Упродовж наступних `w_short` хвилин (наприклад, 5 хвилин) у коротке вікно надходять виключно успішні запити, і `BurnRate(w_short)` миттєво падає до 0.
   Логічна кон'юнкція набуває значення `1 ∧ 0 = 0`, і тривога автоматично деактивується без очікування завершення годинного інтервалу.

## Композиція SLO в розподілених графах викликів

Сучасні системи складаються з багатьох мікросервісів, організованих у направлений ациклічний граф (DAG). Надійність наскрізного бізнес-сценарію залежить від топології взаємодії компонентів.

### Послідовна залежність компонентів (Serial Dependency)

Якщо виконання клієнтського запиту вимагає послідовного виклику `K` незалежних сервісів, кожен із яких має власний рівень надійності `SLO_i`, сукупна надійність ланцюжка дорівнює добутку надійностей:

```
SLO_chain = ∏_{i=1}^K SLO_i
```

**Приклад деградації надійності:**
Якщо ланцюжок складається з 10 мікросервісів, кожен із яких має цільове `SLO = 99.9%` (`0.999`):

```
SLO_chain
= (0.999)¹⁰              [піднесення до степеня за кількістю вузлів]
≈ 0.990045               [обчислення добутку]
≈ 99.0%                  [результат: деградація на цілий порядок]
```

Замість трьох дев'яток наскрізний ланцюжок забезпечує лише дві дев'ятки: сумарний допустимий простій зріс із 43 хвилин до більш ніж 7 годин на місяць.

### Паралельне надлишкове резервування (Parallel Redundancy)

Якщо критичний компонент має резервну копію або альтернативний провайдер (наприклад, два незалежні платіжні шлюзи), і запит вважається успішним, якщо спрацював хоча б один із них, сукупна надійність обчислюється через імовірність одночасної відмови:

```
SLO_parallel = 1 - ∏_{j=1}^M (1 - SLO_j)
```

Якщо сервіс використовує два незалежні шлюзи з посередньою надійністю `SLO = 99.0%` (`1 - S = 0.01`):

```
SLO_parallel
= 1 - (0.01 · 0.01)      [добуток імовірностей відмов]
= 1 - 0.0001             [віднімання від одиниці]
= 0.9999                 [результат: чотири дев'ятки, 99.99%]
```

Паралельне резервування перетворює два ненадійні компоненти на надзвичайно стабільну підсистему, підвищуючи сукупну надійність на два порядки.

## Математична некоректність усереднення затримок

Поширеною помилкою інженерів є спроба формулювати SLI затримок через середнє арифметичне часу обробки або через пряме усереднення квантилів `P99` між серверами.

Математична статистика вказує на дві грубі помилки в таких операціях:

1. **Асиметрія розподілів затримок (Heavy-Tailed Distributions):**
   Час обробки мережевих запитів ніколи не підпорядковується нормальному розподілу Ґауса. Він має виражений довгий хвіст через паузи збирача сміття (GC), дискові блокування та черги в операційній системі. Середнє арифметичне значення маскує критичні аномалії: 999 запитів із затримкою 10 мс і 1 запит із затримкою 10 000 мс дають середнє `~20 мс`, хоча один користувач чекав цілих 10 секунд.

2. **Неадитивність квантилів:**
   Квантилі та процентилі не є лінійними операторами. Якщо сервер A має `P99 = 100 мс`, а сервер B має `P99 = 200 мс`, 99-й процентиль кластера з двох серверів **не дорівнює** середньому `150 мс`:

   ```
   P99(A ∪ B) ≠ ( P99(A) + P99(B) ) / 2
   ```

З цієї причини стандартом побудови SLI затримок є **подійна оцінка за фіксованим порогом**:
`SLI_latency = (Кількість запитів із часом обробки ≤ L_target) / (Загальна кількість валідних запитів)`.

Ця величина є чистою часткою (пропорцією), підпорядковується біноміальному розподілу, є строго адитивною і дозволяє безпомилково агрегувати показники між довільною кількістю серверів, дата-центрів і географічних регіонів.

## Дискретизація часових рядів та кільцеві буфери

Для обчислення SLI у рантаймі неможливо зберігати повний масив усіх мільярдів запитів за 30 днів. Застосовується чисельна дискретизація за часовими інтервалами (бакетами) тривалістю `Δt` (зазвичай `Δt = 10 секунд` або `Δt = 1 хвилина`).

Кожен бакет зберігає вектор цілочисельних лічильників `{N_total, N_good, N_bad}`. Загальне ковзне вікно тривалістю `W` формується як кільцевий буфер (Ring Buffer) із `K = W / Δt` комірок.

### Похибка квантування та ковзний накопичувач

Чисельне наближення вносить максимальну теоретичну похибку дискретизації часових меж вікна:

```
Error_quantization ≤ Δt / W
```

Для короткого вікна `W = 5 хвилин` при кроці бакета `Δt = 10 секунд` відносна похибка меж становить `10 / 300 = 3.33%`, що цілком допустимо для оперативних алертів. Для годинного вікна `W = 60 хвилин` при тому самому кроці похибка спадає до `10 / 3600 = 0.27%`.

Для досягнення обчислювальної складності `O(1)` на кожен доданий бакет замість постійного перепідсумовування масиву використовується алгоритм ковзного накопичувача (Sliding Accumulator):

```
Sum_good(t + Δt) = Sum_good(t) + Bucket_new.good - Bucket_expired.good
Sum_total(t + Δt) = Sum_total(t) + Bucket_new.total - Bucket_expired.total
```

Це дозволяє обчислювати точні значення SLI та швидкостей вигорання для тисяч метрик одночасно з фіксованими мікросекундними витратами процесорного часу.

## Прямокутне ковзне вікно проти експоненційного зважування

У практиці аналізу часових рядів постає вибір математичної вагової функції вікна:

1. **Прямокутне вікно (Rectangular Sliding Window):**
   Кожна подія у вікні `[t - W, t]` має вагу `w(τ) = 1`, а за межами вікна — `w(τ) = 0`.
   * *Властивість:* Ідеальна відповідність суті SLO як відсотку успішних запитів за точний період.
   * *Математична особливість:* Має ступінчасту функцію впливу (Step Response). Подія, що сталася 29 днів 23 години тому, має таку ж вагу, як подія, що сталася секунду тому, а рівно через 1 годину її вага стрибкоподібно обнуляється.

2. **Експоненційне згладжування (Exponential Moving Average, EMA):**
   Вага подій плавно згасає за експоненційним законом `w(τ) = e^{-λ(t - τ)}`.
   * *Властивість:* Не потребує збереження кільцевого буфера історії — достатньо оновлювати одне число в пам'яті: `EMA(t) = α · Metric(t) + (1 - α) · EMA(t - Δt)`.
   * *Обмеження для SLO:* Не має фіксованого терміну життя подій і спотворює абсолютні розрахунки бюджету помилок, оскільки «хвіст» експоненти теоретично триває до нескінченності. Тому для юридичних SLA та строгих інженерних SLO застосовують виключно прямокутні ковзні вікна.

## Статистичні довірчі інтервали при низькому трафіку

Коли сервіс обробляє невелику кількість запитів (наприклад, внутрішній адміністративний API або сервіс у нічні години з `N_valid < 100`), виникає проблема статистичної значущості вибірки. Один випадковий збій при `N = 10` дає миттєве падіння `SLI = 90%`, що призводить до хибного вичерпання бюджету.

Класичний довірчий інтервал Вальда `p ± z · √(p(1-p)/n)` стає непридатним, оскільки при `p ≈ 1.0` його нижня дисперсія прямує до нуля, створюючи ілюзію надвисокої точності.

Для коректної оцінки застосовують **інтервал Вільсона (Wilson Score Interval)** для біноміальної пропорції:

```
p_lower = ( p + z²/(2n) - z·√( (p(1-p)/n) + z²/(4n²) ) ) / ( 1 + z²/n )
```

де `p = N_good / N_total`, `n = N_total`, а `z` — квантиль стандартного нормального розподілу (наприклад, `z = 1.96` для довірчого рівня 95%).

Інтервал Вільсона гарантує, що при малому обсязі запитів система розширює довірчі межі й не здійснює передчасного блокування CI/CD-конвеєрів через одиничні випадкові флуктуації, зберігаючи суворість контролю при зростанні вибірки.
