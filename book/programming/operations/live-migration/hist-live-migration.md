# 📜 Від міграції процесів до безшовних хмар: історія живої міграції

Ідея перенесення працюючої програми з одного фізичного комп'ютера на інший без переривання її виконання виникла задовго до появи сучасних хмарних дата-центрів. У 1980-х роках дослідники розподілених операційних систем намагалися реалізувати автоматичне балансування обчислювального навантаження між робочими станціями локальної мережі, щоб невикористані процесорні цикли на столах колег виконували важкі компіляції чи наукові розрахунки.

Проте всі ранні спроби вирішити це завдання на рівні окремих процесів операційної системи вперлися у фундаментальну проблему розподіленого стану, і лише зміна межі абстракції — перехід від ізольованого процесу до повної віртуальної машини — перетворила експериментальну ідею на стандарт хмарної індустрії.

## Глухий кут міграції процесів: пастка залишкових залежностей

У період з 1983 по 1995 рік провідні університетські лабораторії світу створили кілька амбітних розподілених операційних систем:
- **V-System** (Стенфордський університет, 1983–1988, під керівництвом Девіда Черітона / David Cheriton);
- **Sprite OS** (Каліфорнійський університет у Берклі, 1988–1991, Джон Оустерхаут / John Ousterhout та Фред Дугліс / Fred Douglis);
- **MOSIX** (Єврейський університет у Єрусалимі, 1986–1999, Амнон Барак / Amnon Barak);
- **Mach** (Університет Карнегі–Меллона, Річард Рашид / Richard Rashid).

Ключовим механізмом цих систем була **міграція процесів (англ. *process migration*)**: спеціальний системний виклик або планувальник ядра заморожував виконання потоку, зчитував його адресний простір, передавав байти пам'яті по локальній мережі на інший вузол і створював там ідентичний процес.

Саме в системі V-System Девід Черітон та Віллі Цванепул (Willy Zwaenepoel) 1985 року вперше сформулювали концепцію **попереднього копіювання (англ. *pre-copy*)**: замість повної зупинки процесу на весь час перекачування мегабайтів пам'яті, система копіювала сторінки пам'яті у фоновому режимі, поки процес продовжував виконуватися на вихідному вузлі, а повторному надсиланню підлягали лише ті сторінки, які процес встиг змінити.

Однак міграція процесів у загальному випадку виявилася нежиттєздатною через **проблему залишкових залежностей (англ. *residual dependency trap*)**:
1. **Зв'язаність з ядром:** Процес володіє не лише оперативною пам'яттю, а й сотнями неявних структур усередині монолітного ядра ОС — відкритими файловими дескрипторами, віртуальними сокетами TCP, орендованими семафорами SysV IPC, ідентифікаторами PID та зв'язками батьківсько-дочірніх процесів.
2. **Мережевий проксі-шлейф:** Якщо процес мігрував на вузол B, але мав відкритий файл на вузлі A, вузол B мусив проксіювати кожен системний виклик `read()` або `ioctl()` назад на вузол A через мережевий RPC.
3. **Крихкість відмов:** Якщо вихідний вузол A перезавантажувався або виходив з ладу, мігрований процес на вузлі B негайно падав, оскільки його стан залишався розмазаним між двома машинами.

Розробники усвідомили: щоб перенесення було по-справжньому автономним, процес має мігрувати разом з усіма своїми залежностями. Проте перенести шматок ядра для одного процесу, не порушивши роботу сусідніх процесів на тому ж ядрі, було практично неможливо.

## Зміна парадигми: перенесення цілої віртуальної машини

Наприкінці 1990-х років відродження віртуалізації на архітектурі x86 відкрило принципово інший підхід. Замість спроб розплутати складні зв'язки окремого процесу з ядром хоста інженери вирішили переносити **всю операційну систему цілком**.

Віртуальна машина інкапсулює усередині свого віртуального апаратного простору:
- Власне гостьове ядро з усіма його таблицями сторінок, дескрипторами та сокетами;
- Весь масив фізичної пам'яті (Guest Physical Memory);
- Віртуальні пристрої (контролери дисків, таймери, мережеві карти) із фіксованим станом регістрів.

Єдиними зовнішніми зв'язками віртуальної машини залишалися мережевий інтерфейс (Ethernet MAC/IP) та віртуальний диск. Якщо віртуальний диск розміщувався на спільному мережевому сховищі (SAN / NAS / Fibre Channel), вся задача перенесення зводилася до копіювання пам'яті та передачі стану віртуальних пристроїв між двома гіпервізорами.

```
Міграція процесу (1980-ті):
  [Процес] ➔ переноситься
  [Ядро ОС, сокети, дескриптори, драйвери] ➔ лишаються на старому хості (розрив зв'язку)

Жива міграція ВМ (2000-ні):
  ┌──────────────────────────────────────────────┐
  │ [Процеси + Ядро ОС + Сокети + Віртуальне залізо] │ ➔ переносяться як єдиний контейнер
  └──────────────────────────────────────────────┘
```

## 2003: VMware vMotion — комерційний прорив

У 2003 році компанія VMware під керівництвом Діани Грін (Diane Greene) та Менделя Розенблюма (Mendel Rosenblum) представила технологію **VMware vMotion** у складі платформи ESX Server 2.0 (провідні інженери: Майкл Нельсон / Michael Nelson, Бенг-Хонг Лім / Beng-Hong Lim та Ґреґ Гатчінс / Greg Hutchins).

vMotion вперше продемонстрував практичну живу міграцію без зупинки роботи операційних систем Windows та Linux на серверах x86. Робота спиралася на спільне сховище SAN та апаратні пастки гіпервізора VMware для відстеження змін у пам'яті гостя за допомогою тіньових таблиць сторінок (Shadow Page Tables).

Незважаючи на комерційний тріумф, VMware vMotion була закритою пропрієтарною технологією. Інженерна спільнота потребувала відкритого академічного опису математичних моделей, алгоритмів та граничних умов живої міграції.

## 2005: Маніфест Xen — народження відкритого стандарту

У травні 2005 року на конференції USENIX NSDI (Networked Systems Design and Implementation) дослідницька група Кембриджського університету та творці гіпервізора Xen опублікували фундаментальну статтю, яка визначила розвиток технології на десятиліття вперед:

> *Christopher Clark, Keir Fraser, Steven Hand, Jacob Gorm Hansen, Eric Jul, Christian Limpach, Ian Pratt, Keir A. Fraser — "Live Migration of Virtual Machines" (NSDI 2005).*

Автори Xen детально описали шестифазний алгоритм ітеративного попереднього копіювання (Pre-Copy):
1. **Ініціалізація (Initialization):** Резервування пам'яті та структур на цільовому хості.
2. **Резервування (Reservation):** Створення порожнього контейнера домену на цілі.
3. **Ітеративне копіювання (Iterative Pre-Copy):** Передача всіх сторінок RAM у першому раунді, увімкнення режиму відстеження брудних сторінок (*dirty page logging*), циклічне надсилання сторінок, змінених за час попередньої ітерації.
4. **Зупинка та копіювання (Stop-and-Copy):** Коли обсяг брудної пам'яті стабілізується нижче порогу або кількість раундів перевищує ліміт, гіпервізор призупиняє виконання vCPU, надсилає останній невеликий залишок сторінок пам'яті та передає стан регістрів процесора.
5. **Фіксація (Commit):** Цільовий гіпервізор стає основним володарем стану машини.
6. **Активація (Activation):** Запуск vCPU на цільовому хості та відправка пакету Gratuitous ARP у мережу для миттєвого переналаштування комутаторів.

Авторам вдалося досягти часу простою (downtime) менше 60 мілісекунд для веб-серверів під навантаженням, що було менше за стандартний таймаут повторної передачі пакетів TCP, завдяки чому користувачі взагалі не помічали факту переїзду сервера.

## 2009–2015: Стіна збіжності та винайдення Post-Copy

Зі зростанням обсягів пам'яті серверів до сотень гігабайтів та появою високонавантажених баз даних у пам'яті (Redis, Memcached, SAP HANA, кластери СУБД) підхід Pre-Copy натрапив на фундаментальне обмеження.

Якщо гостьова ОС записує в пам'ять зі швидкістю 2 ГБ/с, а пропускна здатність мережі становить 1 ГБ/с (10 GbE), обсяг брудної пам'яті на кожній ітерації не зменшується, а зростає. Міграція входить у нескінченний цикл і ніколи не може перейти до фази Stop-and-Copy без примусової зупинки гостя на десятки секунд.

У 2009 році дослідники Майкл Гайнс (Michael R. Hines), Умеш Дешпанде (Umesh Deshpande) та Картік Гопалан (Kartik Gopalan) з Університету Бінгемтона опублікували революційну статтю:
> *"Post-Copy Live Migration of Virtual Machines" (ACM SIGPLAN/SIGOPS VEE 2009).*

Ідея Post-Copy перевернула процес з ніг на голову:
1. Замість тривалого перекачування гігабайтів пам'яті на працюючому гості, віртуальна машина призупиняється на вихідному вузлі на 20–30 мілісекунд.
2. Її регістри vCPU та стан пристроїв негайно передаються на цільовий вузол.
3. Цільовий вузол **відразу запускає виконання гостя з порожньою пам'яттю**.
4. Коли гість звертається до сторінки пам'яті, якої ще немає на новому місці, апаратний сторінковий збій перехоплюється гіпервізором, сторінка миттєво запитується по мережі з вихідного вузла на вимогу (*on-demand paging*), а фоновий потік паралельно докачує решту пам'яті.

Реалізація Post-Copy вимагала глибокої підтримки на рівні ядра операційної системи. 1 листопада 2015 року Андреа Арканджелі (Andrea Arcangeli) включив до ядра Linux 4.3 механізм **`userfaultfd`**, який дозволив простору користувача (зокрема QEMU) перехоплювати сторінкові збої пам'яті без участі сигналів. Уже в грудні 2015 року Девід Алан Ґілберт (Dr. David Alan Gilbert, Red Hat) інтегрував повноцінну підтримку Post-Copy у QEMU 2.5.

## 2015–2026: Ера апаратного прискорення та гетерогенних пристроїв

В останнє десятиліття розвиток живої міграції зосередився на усуненні накладних витрат процесора та підтримці складного фізичного заліза:

1. **Intel PML (Page Modification Logging, 2015):** Починаючи з мікроархітектури Broadwell Server, компанія Intel додала апаратне логування адрес модифікованих сторінок безпосередньо мікрокодом процесора у виділений 4-кілобайтний буфер. Це позбавило гіпервізор потреби генерувати сотні тисяч важких виходів VM-Exit для кожної зміненої сторінки під час Pre-Copy.
2. **KVM Dirty Ring (2020):** Пітер Сюй (Peter Xu) та Паоло Бонзіні (Paolo Bonzini) реалізували в ядрі Linux 5.11 та QEMU 6.0 кільцевий буфер брудних сторінок на кожен vCPU (`KVM_DIRTY_LOG_RING`), усунувши глобальне блокування структур пам'яті VM та суттєво підвищивши масштабованість міграції на машинах із сотнями ядер.
3. **Multifd та паралельна міграція (2018–2022):** Впровадження багатопотокової передачі даних через десятки паралельних TCP або RDMA з'єднань дозволило насичувати сучасні мережеві карти зі швидкістю 100–400 Гбіт/с.
4. **VFIO Live Migration (2020–2024):** Найскладніший сучасний виклик — міграція віртуальних машин із прямим прокиданням обладнання (PCIe Passthrough, GPU, DPU, SmartNIC). Завдяки стандартизації інтерфейсу VFIO Migration v2 в ядрі Linux 5.18+ апаратні драйвери постачальників (NVIDIA, Intel, AMD) отримали уніфікований скінченний автомат для зчитування внутрішнього стану апаратних прискорювачів під час міграції.

Жива міграція перетворилася зі сміливого експерименту над окремими процесами на фундамент сучасної безперервної експлуатації хмарних дата-центрів, що дозволяє виконувати оновлення ядер хостів, ремонт материнських плат та динамічне перебалансування навантаження абсолютно непомітно для користувачів.
