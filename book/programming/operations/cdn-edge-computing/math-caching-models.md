# 🧮 Математичні моделі кешування, закони розподілу Zipf та оптимізація затримок на краю

Розподілені мережі доставки вмісту оперують обмеженими обсягами дорогої оперативної та енергонезалежної пам'яті на крайових серверах. Щоб мінімізувати навантаження на центральні бази даних і досягти передбачуваного часу відгуку системи, інженер повинен кількісно розраховувати ймовірність влучання в кеш, швидкість вимивання застарілих даних та сумарний виграш у затримці передачі даних. Математичний апарат кешування спирається на емпіричний розподіл популярності контенту Ципфа, наближення Че для алгоритмів витіснення LRU та ймовірнісні моделі часу до першого байта (TTFB).

## Розподіл популярності контенту за законом Ципфа

У реальних мережевих додатках поведінка користувачів демонструє виражену асиметрію: невелика частка популярних ресурсів (хітів) генерує переважну більшість усіх переглядів і завантажень. Якщо впорядкувати всі `N` доступних об'єктів каталогу (файлів, вебсторінок, відеороликів) за спаданням частоти звернень, де ранг `r = 1` відповідає найпопулярнішому об'єкту, а `r = N` — найменш популярному, ймовірність запиту до об'єкта рангу `r` підпорядковується дискретному закону розподілу Ципфа:

```
P(r) = (1 / r^α) / H(N, α)
```

У цій формулі:
- `r` — порядковий ранг об'єкта у відсортованому каталозі (`1 ≤ r ≤ N`);
- `α` — параметр форми або показник експоненційного спадання популярності;
- `H(N, α)` — узагальнене гармонійне число порядку `α`, що виконує роль нормувального коефіцієнта, гарантуючи, що сума ймовірностей для всіх об'єктів каталогу дорівнює одиниці:

```
H(N, α) = ∑_{i=1}^N (1 / i^α)
```

### Фізичний зміст параметра форми `α`
Значення параметра `α` визначає ступінь концентрації користувацького попиту в різних прикладних доменах:
- **`α ≈ 0.6–0.7` (Помірний розподіл)**: Характерний для онлайн-кінотеатрів та каталогів художніх фільмів (Video on Demand). Каталог має «довгий хвіст» (Long Tail), і користувачі дивляться багато рідкісних спеціалізованих фільмів;
- **`α ≈ 0.8–0.9` (Типовий вебтрафік)**: Загальні вебпортали, інтернет-магазини, сайти новин. Основна увага зосереджена на свіжих публікаціях та головній сторінці;
- **`α ≥ 1.1–1.3` (Висока концентрація)**: Дзеркала оновлення операційних систем, дистрибутиви пакетів (npm, pip, apt) та вірусний контент у соціальних мережах, де 95% трафіку припадає на кілька найновіших релізів.

### Кумулятивна частка запитів і теоретичний коефіцієнт влучання (Cache Hit Ratio)

Якщо крайовий сервер має ємність пам'яті, достатню для зберігання `C` найпопулярніших об'єктів (`C ≤ N`), теоретичний коефіцієнт влучання в кеш (Cache Hit Ratio, `CHR(C)`) визначається як сума ймовірностей перших `C` рангів:

```
CHR(C) = ∑_{r=1}^C P(r)
       = (∑_{r=1}^C (1 / r^α)) / (∑_{i=1}^N (1 / i^α))
```

Для великих каталогів (`N ≫ 10^5`) дискретну суму можна замінити інтегралом від неперервної степеневої функції `f(x) = x^(-α)`:

```
∑_{r=1}^C (1 / r^α) ≈ ∫_1^C x^(-α) dx = (C^(1 - α) - 1) / (1 - α)      [при α ≠ 1]
```

Підставляючи інтегральні вирази для чисельника та знаменника:

```
CHR(C)
= ((C^(1 - α) - 1) / (1 - α)) / ((N^(1 - α) - 1) / (1 - α))   [підстановка інтегральних наближень]
= (C^(1 - α) - 1) / (N^(1 - α) - 1)                          [скорочення спільного множника (1 - α)]
≈ (C / N)^(1 - α)                                            [наближення при C ≫ 1 та N ≫ 1]
```

Для окремого випадку `α = 1` первісна функції `1 / x` дорівнює натуральному логарифму `ln(x)`:

```
CHR(C)
= (∫_1^C (1 / x) dx) / (∫_1^N (1 / x) dx)    [інтегрування оберненої функції при α = 1]
= ln(C) / ln(N)                              [відношення натуральних логарифмів ємності]
```

### Покроковий розрахунковий приклад: Вплив ємності кешу на розвантаження сервера

Розглянемо практичний випадок розгортання крайового сховища для каталогу медіафайлів розміром `N = 1 000 000` унікальних об'єктів із параметром спадання популярності `α = 0.85`.

Розрахуємо нормувальну суму для всього каталогу та для крайового кешу ємністю `C = 10 000` об'єктів (що становить лише 1% від загального розміру каталогу):

```
H(1000000, 0.85) = ∑_{i=1}^{1000000} (1 / i^0.85) ≈ 42.14       [сума для повного каталогу]
H(10000, 0.85)   = ∑_{r=1}^{10000} (1 / r^0.85)   ≈ 34.02       [сума для топ-1% об'єктів]

CHR(10000)
= 34.02 / 42.14                                         [відношення часткової суми до повної]
= 0.8073                                                [теоретичний коефіцієнт влучання 80.73%]
```

Цей розрахунок доводить, що виділення відносно невеликого обсягу оперативної пам'яті (1% каталогу) дозволяє обслужити понад 80% усіх запитів користувачів без звернення до центрального сервера.

## Оцінка параметра $\alpha$ за методом найменших квадратів

Для практичного налаштування розміру пам'яті інженери CDN збирають статистику реальних логів доступу. Прологарифмувавши закон Ципфа, отримуємо лінійне рівняння:

```
ln(P(r)) = -α · ln(r) - ln(H(N, α))
```

Якщо побудувати графік залежності натурального логарифма частоти звернень від логарифма рангу об'єкта `ln(r)`, емпіричні точки утворюють пряму лінію. Тангенс кута нахилу цієї прямої, знайдений методом лінійної регресії, дорівнює показнику `-α`. Знаючи `α`, архітектор може розрахувати мінімальний обсяг пам'яті, необхідний для досягнення цільового SLA (наприклад, Cache Hit Ratio ≥ 95%).

## Динаміка витіснення за алгоритмом LRU: Наближення Че

У реальних виробничих умовах склад популярного контенту постійно змінюється, тому сервери CDN використовують динамічні алгоритми витіснення, найпоширенішим з яких є алгоритм найменш нещодавно використаних об'єктів (Least Recently Used, LRU).

Класичний точний марковський аналіз черги LRU для мільйона об'єктів є обчислювально нездійсненним, оскільки простір станів вимагає аналізу `N!` перестановок.

У 2002 році Хао Че (Hao Che) та його колеги запропонували потужне аналітичне наближення (Che's Approximation), яке розглядає динаміку кешу через поняття **характерного часу життя** (Characteristic Time, `t_C`).

### Математична суть наближення Че
Припустимо, що запити до кожного об'єкта `i` надходять як незалежний пуассонівський процес з інтенсивністю `λ[i]` (запитів на секунду). Об'єкт `i` потрапляє у вершину LRU-списку в момент звернення і поступово зміщується до кінця черги. Він залишається в кеші ємністю `C` об'єктів доти, доки між двома послідовними запитами до нього проходить менше ніж `t_C` секунд.

Ймовірність того, що протягом інтервалу `t_C` надійде хоча б один новий запит до об'єкта `i` (що поверне його у вершину списку), описується показниковим розподілом:

```
P_hit(i) = 1 - e^(-λ[i] · t_C)
```

Значення характерного часу `t_C` є глобальною константою для всього кешу даної ємності `C` і знаходиться як єдиний корінь нелінійного рівняння балансу ресурсів:

```
∑_{i=1}^N (1 - e^(-λ[i] · t_C)) = C
```

Сумарний середньозважений коефіцієнт влучання LRU-кешу для загального потоку запитів `Λ = ∑_{i=1}^N λ[i]`:

```
CHR_LRU = (1 / Λ) · ∑_{i=1}^N λ[i] · (1 - e^(-λ[i] · t_C))
```

Похибка наближення Че порівняно з прямим комп'ютерним моделюванням поведінки LRU не перевищує 1.5–2%, що робить його основним інструментом інженерного проектування ємності CDN.

## Модель деградації популярності в часі (Temporal Locality & Aging Decay)

У реальних інформаційних системах популярність контенту не є постійною в часі. Новинні матеріали, вірусні відео та оновлення додатків переживають пік популярності в перші години після публікації, після чого частота звернень згасає за експоненційним законом:

```
λ_i(t) = λ_i(0) · e^(-γ · t)
```

Де `γ` — коефіцієнт старіння контенту (`γ > 0`), а `t` — час, що минув з моменту появи об'єкта.

Враховуючи часову деградацію, динамічний коефіцієнт влучання для об'єкта віком `t` набуває вигляду:

```
P_hit(i, t) = 1 - e^(-λ_i(0) · e^(-γ · t) · t_C)
```

Це рівняння показує, чому статичні алгоритми кешування з фіксованим TTL вимагають динамічної адаптації: об'єкти з високим темпом старіння `γ` повинні мати коротший TTL, щоб звільняти пам'ять крайових вузлів для нових висхідних трендів.

## Зважені за розміром та ціною алгоритми витіснення: GreedyDual-Size

Класичний LRU оптимізує виключно кількість звернень, не враховуючи розмір файлу та вартість його завантаження з центрального сервера. Для максимізації байтового влучання (BHR) та мінімізації вартості трафіку застосовується алгоритм **GreedyDual-Size with Frequency (GDSF)**.

Кожен збережений об'єкт `p` отримує динамічний індекс корисності `H(p)`:

```
H(p) = L + F(p) · (Cost(p) / Size(p))
```

Де:
- `Cost(p)` — ціна промаху (затримка отримання від Origin або вартість завантаження в доларах);
- `Size(p)` — розмір файлу в байтах;
- `F(p)` — лічильник кількості звернень до об'єкта за час його перебування в пам'яті;
- `L` — глобальний лічильник старіння (Aging Clock), який оновлюється при кожному витісненні: `L = H(витіснений_об'єкт)`.

При вичерпанні пам'яті кеш витісняє об'єкт із найменшим значенням `H(p)`. Це забезпечує пріоритетне збереження невеликих, часто запитуваних і дорогих у генерації файлів, максимізуючи загальну ефективність вузла.

## Співвідношення коефіцієнта влучання об'єктів (OHR) та байтів (BHR)

У вебсистемах об'єкти мають суттєво різний розмір: текстовий HTML-документ важить 25 КБ, а відеофрагмент — 4 МБ.

Тому інженери вимірюють дві незалежні метрики:
1. **Object Hit Ratio (OHR)**: частка успішно оброблених HTTP-запитів без звернення до Origin;
2. **Byte Hit Ratio (BHR)**: частка переданого клієнтам обсягу трафіку (у байтах), відданого безпосередньо з пам'яті кешу:

```
BHR = (∑_{i=1}^N S[i] · Запити_Hit[i]) / (∑_{i=1}^N S[i] · Запити_Всього[i])
```

Де `S[i]` — розмір `i`-го файлу в байтах. Якщо невеликі файли (картинки, іконки, CSS) мають високий коефіцієнт влучання (OHR = 90%), але важкі відеоролики промахуються повз кеш через брак дискового простору, сумарний BHR може впасти до 40%, що призведе до значних фінансових витрат на оплату вихідного трафіку (Egress) з центральної хмари.

## Багаторівнева ієрархія: Коефіцієнт розвантаження джерела (Origin Offload)

У багаторівневих мережах CDN запити, що промахнулися повз перший крайовий рівень (L1 Edge PoP з коефіцієнтом влучання `H[1]`), спрямовуються на другий рівень регіонального кешу (L2 Origin Shield з коефіцієнтом влучання `H[2]`).

Імовірність того, що запит досягне центрального сервера (Origin):

```
P_origin_miss = (1 - H[1]) · (1 - H[2])
```

Сумарний коефіцієнт розвантаження центрального сервера (Origin Offload Ratio, `O`):

```
O = 1 - P_origin_miss
  = 1 - (1 - H[1]) · (1 - H[2])
  = H[1] + H[2] - H[1] · H[2]
```

### Покроковий розрахунок розвантаження при двох рівнях

При типових промислових показниках крайового рівня `H[1] = 0.88` (88%) та регіонального захисного шару `H[2] = 0.75` (75% від тих промахів, що надійшли з L1):

```
P_origin_miss
= (1 - 0.88) · (1 - 0.75)     [добуток імовірностей промаху на L1 та L2]
= 0.12 · 0.25                  [розрахунок залишку]
= 0.03                         [3% запитів доходять до Origin]

O
= 1 - 0.03                     [інверсія ймовірності]
= 0.97                         [97% сумарного розвантаження]
```

Завдяки регіональному захисному екрану (Origin Shield) навантаження на центральну базу даних і бекенд знижується в 33.3 раза (з 100% до 3%).

## Теорія масового обслуговування: Скорочення черг за законом Літтла

Вплив кешування на затримку обробки черг на бекенді описується законом Літтла (Little's Law):

```
L = λ · W
```

Де:
- `L` — середня кількість запитів, що очікують у черзі сервера;
- `λ` — інтенсивність вхідного потоку (запитів/с);
- `W` — середній час перебування запиту в системі.

Для односерверної черги бекенду моделі `M/M/1` з інтенсивністю обслуговування `μ` середній час відповіді дорівнює:

```
W = 1 / (μ - λ)
```

Коли CDN відсікає 95% трафіку, ефективна інтенсивність навантаження на бекенд падає з `λ` до `λ_eff = 0.05 · λ`. Це відсуває систему від точки насичення `λ → μ`, запобігаючи експоненційному зростанню черг та падінню процесорів у тротлінг.

## Оптимальне розміщення реплік: Задача $k$-медіани на графі

Розподіл дата-центрів CDN по поверхні земної кулі формулюється як класична комбінаторна задача оптимізації $k$-медіани (k-Median Problem).

Нехай `V` — множина міст із користувачами, де кожне місто `i ∈ V` генерує потік трафіку вагою `w[i]`. Нехай `F ⊆ V` — множина потенційних локацій для розміщення точок присутності (PoP). Необхідно вибрати підмножину `S ⊆ F` розміром `|S| = k`, яка мінімізує сумарну затримку доставки:

```
min ∑_{i ∈ V} w[i] · min_{j ∈ S} d(i, j)
```

Де `d(i, j)` — мережева затримка RTT між клієнтським вузлом `i` та сервером `j`. Задача належить до класу NP-важких, тому провайдери вирішують її за допомогою генетичних алгоритмів та жадібних евристик розміщення (Greedy Facility Location), розміщуючи сервери в точках максимальної щільності інтернет-обміну (IXP).

## Енергетична ефективність та вуглецевий слід кешування

Передача даних через трансконтинентальні підводні кабелі та сотні проміжних маршрутизаторів споживає значну кількість електроенергії:
- Пряма передача 1 ГБ трафіку між континентами вимагає приблизно `0.06–0.08` кВт·год електроенергії для живлення лазерних підсилювачів EDFA, регенераторів оптичних сигналів та комутаторів ядра;
- Зчитування того самого гігабайта з локального NVMe SSD чи RAM на крайовому PoP-вузлі споживає менше ніж `0.00015` кВт·год.

Коефіцієнт енергетичної ефективності кешування (Energy Efficiency Gain, `EEG`):

```
EEG = E_transatlantic / E_edge_local ≈ 0.07 / 0.00015 ≈ 466
```

Локалізація контенту на краю скорочує споживання електроенергії телекомунікаційною інфраструктурою майже в 500 разів, що знижує вуглецевий слід цифрових сервісів та зменшує навантаження на глобальні магістральні канали.

## Зв'язок наближення Че з геометрією простору станів марковського процесу

Для глибокого розуміння природи наближення Че важливо підкреслити, що воно проектує гіперкуб станів марковського ланцюга розмірністю $N!$ на одновимірний інтервал характерного часу $t_C$. Завдяки закону великих чисел для $N \ge 10^4$ флуктуації кількості об'єктів у черзі між повторними зверненнями прямують до нуля. Це робить детерміністичний розрахунок точки рівноваги через рівняння суми ймовірностей абсолютно строгим з інженерної точки зору.

## Аналітична модель затримки та часу до першого байта (TTFB)

Час до отримання першого байта відповіді (Time to First Byte, TTFB) клієнтом визначається сумою мережевого кругового часу обігу (RTT), часу криптографічного рукостискання TLS, часу пошуку в локальному індексі кешу та тривалості генерації відповіді бекендом у разі промаху:

```
E[TTFB] = H[1] · TTFB_hit + (1 - H[1]) · H[2] · TTFB_shield + (1 - O) · TTFB_origin
```

Де:
- `TTFB_hit = RTT_client_edge + T_lookup` — час віддачі безпосередньо з RAM/NVMe крайового вузла L1;
- `TTFB_shield = RTT_client_edge + RTT_edge_shield + T_shield_lookup` — час віддачі з регіонального вузла L2 через швидкісну магістраль;
- `TTFB_origin = RTT_client_edge + RTT_edge_origin + T_backend_compute` — повний час запиту до центрального сервера з обробкою запиту базою даних.

### Порівняльний розрахунок середньої затримки

Розглянемо реальні параметри зв'язку між користувачем у Сіднеї та центральним сервером у Франкфурті:
- Прямий RTT до центрального сервера: `RTT_origin = 280 мс`;
- RTT до локального Anycast Edge PoP у Сіднеї: `RTT_client_edge = 8 мс`;
- RTT від Edge до Origin Shield у Сингапурі: `RTT_edge_shield = 90 мс`;
- RTT від Edge до Origin через оптимізовану приватну мережу: `RTT_edge_origin = 210 мс`;
- Час пошуку в індексі кешу: `T_lookup = 2 мс`;
- Час генерації динамічної відповіді на бекенді: `T_backend_compute = 120 мс`.

Розрахуємо середній TTFB без CDN та з дворівневим CDN (`H[1] = 0.88`, `H[2] = 0.75`):

```
TTFB_прямий (без CDN)
= RTT_origin + T_backend_compute       [пряме звернення до сервера]
= 280 + 120
= 400 мс

TTFB_L1_hit
= RTT_client_edge + T_lookup           [миттєва віддача з краю]
= 8 + 2
= 10 мс

TTFB_L2_shield_hit
= RTT_client_edge + RTT_edge_shield + T_lookup  [віддача з регіонального екрана]
= 8 + 90 + 2
= 100 мс

TTFB_origin_miss
= RTT_client_edge + RTT_edge_origin + T_backend_compute  [повний промах через магістраль]
= 8 + 210 + 120
= 338 мс

E[TTFB_CDN]
= 0.88 · 10 + 0.12 · 0.75 · 100 + 0.03 · 338   [математичне сподівання затримки]
= 8.8 + 9.0 + 10.14
= 27.94 мс
```

Середня затримка відповіді знижується з 400 мс до 27.94 мс — прискорення становить понад 14 разів, при цьому 88% клієнтів відчувають майже миттєву реакцію системи (10 мс).
