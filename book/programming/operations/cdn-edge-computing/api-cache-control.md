# 📋 Протокол кешування та інтерфейси крайового керування: заголовки, директиви й Purge API

Протокол передачі гіпертексту HTTP визначає розподілений договір між вебклієнтом, проміжними проксі-серверами та сервером-джерелом (Origin). Без чітко специфікованих заголовків керування кешем проміжні вузли CDN або некоректно повертають користувачам застарілі конфіденційні дані інших облікових записів, або надсилають кожен повторний запит безпосередньо на центральний бекенд, перевантажуючи базу даних. Нижче наведено детальний опис директив стандарту RFC 9111, розширень RFC 5861 та RFC 9213, а також специфікацію REST API для програмної інвалідації розподіленого стану.

## Специфікація заголовка `Cache-Control` у відповідях (RFC 9111)

Заголовок `Cache-Control` у відповіді сервера визначає, хто, де і протягом якого часу має право зберігати та повторно використовувати згенерований HTTP-ресурс.

Кожна директива керує станом внутрішнього автомата кешування (HTTP Caching State Machine):

```
Стани ресурсу в кеші:
[Генерація на Origin] ──► [Свіжий (Fresh): age < max-age]
                             ↓ (age >= max-age)
                          [Застарілий (Stale): очікує валідації]
                             ↓ (виклик Purge або витіснення)
                          [Вилучено (Evicted / Expired)]
```

### Детальний розбір базових директив відповіді

#### 1. Директива `public`
Позначає, що відповідь може бути збережена будь-яким проміжним кешем у ланцюгу передачі даних: браузером користувача, корпоративним проксі-сервером організації, провайдерським кешем інтернет-провайдера та публічними вузлами CDN. Директива `public` є критично важливою для ресурсів, які повертаються на запити з заголовком `Authorization`: за замовчуванням стандарт HTTP забороняє спільним кешам зберігати автентифіковані відповіді, і лише явна присутність директиви `public` дозволяє CDN кешувати такий контент.

#### 2. Директива `private`
Вказує, що сформований ресурс містить персональні дані, специфічні для одного конкретного користувача (наприклад, стан кошика покупок, профіль користувача, виписку з банку). Проміжним спільним кешам (CDN, проксі) суворо заборонено зберігати таку відповідь. Браузер кінцевого користувача має право зберегти копію у своєму локальному дисковому кеші для прискорення навігації кнопками «Назад / Вперед».

#### 3. Директива `no-cache`
Всупереч інтуїтивній назві, директива `no-cache` **не забороняє** зберігати ресурс у пам'яті чи на диску кеш-сервера. Вона наказує кешу обов'язково виконати умовний запит валідації до центрального сервера (Origin) перед кожною віддачею збереженої копії клієнту. Якщо Origin підтверджує валідність (`304 Not Modified`), кеш повертає збережене тіло без повторного завантаження даних через мережу.

#### 4. Директива `no-store`
Найсуворіша директива безпеки. Забороняє кешу зберігати будь-яку частину запиту чи відповіді на будь-якому постійному або тимчасовому носії інформації (ні в оперативній пам'яті RAM, ні на SSD/HDD). Об'єкт передається клієнту транзитом і негайно затирається з буферів пам'яті процесу. Використовується для платіжних даних, одноразових паролів (OTP) та конфіденційних медичних карт.

#### 5. Директива `max-age=<секунди>`
Встановлює максимальний час (у секундах) від моменту генерації відповіді на Origin, протягом якого ресурс вважається «свіжим» (Fresh). Поки поточний вік об'єкта (`Age`) менший за `max-age`, кеш має право віддавати ресурс клієнтам без будь-яких звернень до центрального сервера. Застосовується однаково як до приватних браузерів, так і до публічних вузлів CDN.

#### 6. Директива `s-maxage=<секунди>`
Спеціалізована директива для спільних кешів (Shared Caches), таких як CDN. Вона повністю перевизначає значення `max-age` та заголовка `Expires` для проміжних вузлів мережі. Браузер користувача повністю ігнорує `s-maxage` і продовжує орієнтуватися на `max-age`. Це дозволяє налаштовувати тривале зберігання на крайових вузлах CDN (наприклад, `s-maxage=86400` — 24 години) за умови короткого кешування в браузері клієнта (`max-age=60` — 1 хвилина).

#### 7. Директива `must-revalidate`
Наказує кешу суворо дотримуватися терміну свіжості. Якщо ресурс застарів (`Age >= max-age`), кеш **не має права** повертати застарілу копію за жодних обставин (наприклад, при тимчасовому обриві зв'язку з бекендом), а зобов'язаний повернути клієнту помилку `504 Gateway Timeout`, якщо повторна валідація не вдалася.

#### 8. Директива `proxy-revalidate`
Виконує ту саму функцію, що й `must-revalidate`, але обмежує свою дію виключно спільними проміжними кешами (CDN та проксі-серверами). Клієнтські браузери ігнорують цю директиву, що дозволяє користувачеві в автономному режимі переглядати кешовані сторінки, водночас гарантуючи, що публічні крайові сервери ніколи не віддадуть застарілі спільні дані.

#### 9. Директива `immutable`
Повідомляє кешу, що тіло ресурсу ніколи не зміниться протягом усього періоду дії `max-age`. Зазвичай використовується для статичних асетів з унікальним хешем вмісту в URL (`bundle.8f92a1c.js`, `logo.v2.png`). Браузер при оновленні сторінки (F5) не надсилає жодних умовних запитів валідації `If-None-Match`, віддаючи файл миттєво з локальної пам'яті.

## Асинхронні розширення керування застарілим кешем (RFC 5861)

Директиви стандарту RFC 5861 вводять концепцію багаторівневого життєвого циклу застарілих даних, дозволяючи поєднувати мілісекундну швидкість віддачі з гарантією актуальності контенту.

```http
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=86400, stale-if-error=604800
```

### Директива `stale-while-revalidate=<секунди>`
Визначає додаткове часове вікно після вичерпання основного ліміту `s-maxage`, протягом якого крайовий вузол негайно повертає клієнту збережену копію за 2 мс, і паралельно запускає фоновий асинхронний запит до Origin для завантаження свіжої версії.

Якщо `s-maxage=300` і `stale-while-revalidate=86400`:
- Протягом перших 300 секунд ресурс вважається повністю свіжим (Fresh HIT, 2 мс);
- Від 300-ї секунди до 86700-ї секунди перший клієнт, що надійшов, миттєво отримує відповідь із кешу зі статусом `X-Cache: STALE`, а вузол у фоновому потоці зв'язується з Origin;
- Наступний клієнт, який звернеться після завершення фонового запиту, отримає вже нову свіжу версію без жодної затримки.

### Директива `stale-if-error=<секунди>`
Визначає період часу, протягом якого крайовий вузол CDN має право віддавати застарілу версію ресурсу в разі, якщо спроба зв'язатися з центральним Origin-сервером завершилася мережевим таймаутом або HTTP-помилкою класу `5xx` (`500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`). Це захищає користувачів від спостереження повідомлень про збої сервісу під час падіння бази даних.

## Точний алгоритм розрахунку віку об'єкта (Заголовок Age за RFC 9111)

Протокол HTTP не вимагає абсолютно синхронізованих годинників між сервером, проміжними проксі та клієнтом. Стандарт RFC 9111 визначає точну формулу розрахунку віку ресурсу, яка нівелює розсинхронізацію системного часу:

```
apparent_age = max(0, response_time - date_value)
response_delay = response_time - request_time
corrected_age_value = age_value + response_delay
corrected_initial_age = max(apparent_age, corrected_age_value)
resident_time = now - response_time
current_age = corrected_initial_age + resident_time
```

Крайовий вузол CDN збільшує значення `Age` на величину `resident_time` (час перебування в пам'яті PoP-вузла) перед передачею заголовка клієнту:

```http
HTTP/1.1 200 OK
Date: Wed, 20 Aug 2026 01:50:00 GMT
Age: 240
Cache-Control: public, max-age=300
```
*Клієнт бачить, що ресурс пробув у розподіленому кеші 240 секунд, і вважатиме його свіжим ще протягом 60 секунд (`300 - 240`).*

## Обробка куків та сесій на краю (Cookie Stripping)

Присутність заголовка `Set-Cookie` у відповіді центрального сервера за замовчуванням змушує кеш CDN вважати ресурс приватним і відмовлятися від його збереження. Якщо ж неконфігурований проксі помилково закешує відповідь із заголовком `Set-Cookie: session_id=abc123xyz`, сесійний ідентифікатор одного користувача буде відданий тисячам наступних відвідувачів, що призведе до критичної вразливості захоплення облікових записів (Account Takeover).

Правила крайового обробника:
1. **Видалення вхідних Cookie для статичних асетів (Cookie Stripping on Request)**: Крайовий воркер перед формуванням ключа кешування видаляє заголовок `Cookie` для файлів зображень, CSS та JS, щоб уникнути фрагментації кешу;
2. **Видалення Set-Cookie у відповідях (Set-Cookie Stripping on Response)**: Якщо статичний контент помилково повертає `Set-Cookie`, крайовий вузол видаляє цей заголовок перед збереженням ресурсу в кеш, гарантуючи безпеку сесій.

## Протокол попередньої доставки Early Hints (HTTP 103)

Стандарт RFC 8297 впроваджує інформаційний статус `103 Early Hints`, який дозволяє крайовому вузлу CDN значно скоротити час критичного шляху рендерингу (Critical Rendering Path).

Коли запит вимагає тривалої генерації HTML на бекенді (наприклад, 300 мс для складного SQL-запиту):
1. Крайовий вузол негайно надсилає клієнту попередню відповідь зі статусом `103 Early Hints`:
   ```http
   HTTP/1.1 103 Early Hints
   Link: </css/main.css>; rel=preload; as=style
   Link: </js/app.js>; rel=preload; as=script
   ```
2. Браузер клієнта, не чекаючи основного HTML-документа, починає паралельне завантаження та парсинг критичних файлів CSS та JS з локального кешу CDN;
3. Коли бекенд завершує генерацію і повертає `200 OK` з основним тілом HTML, всі залежності вже завантажені в пам'ять браузера, що усуває затримку візуального відмальовування сторінки.

## Правила вирішення конфліктів директив кешування

Коли відповідь Origin-сервера містить комбінацію директив, що суперечать одна одній, крайовий вузол керується формальними правилами пріоритету стандарту RFC 9111:

1. **`no-store` має абсолютний пріоритет**: Якщо у заголовку присутні одночасно `public, max-age=3600, no-store`, директива `no-store` перекриває всі інші. Ресурс не зберігається в пам'яті ні на мілісекунду;
2. **`private` перекриває `public` та `s-maxage`**: Якщо вказано `public, private, s-maxage=3600`, CDN зобов'язаний вважати ресурс приватним і відмовитися від його збереження на крайовому вузлі;
3. **`must-revalidate` скасовує дію `stale-while-revalidate`**: Якщо ресурс містить обидві директиви, крайовий сервер блокує асинхронну фонову віддачу після вичерпання TTL і переходить у режим обов'язкової синхронної перевірки на Origin;
4. **`s-maxage` перевизначає `max-age` для спільних кешів**: Значення `max-age` повністю ігнорується вузлом CDN, якщо присутнє коректне значення `s-maxage`.

## Специфікація таргетованих заголовків крайових мереж

У складних архітектурах виникає потреба розділити директиви кешування для різних рівнів проксі-серверів. Для цього використовуються спеціалізовані заголовки пріоритету:

```
Пріоритет обробки крайовим вузлом (від найвищого до найнижчого):
[Вендорний заголовок: Cloudflare-CDN-Cache-Control / Fastly-Cache-Control]
  ↓ (якщо відсутній)
[Стандартний крайовий: CDN-Cache-Control (RFC 9213)]
  ↓ (якщо відсутній)
[Заголовок сурогатів: Surrogate-Control]
  ↓ (якщо відсутній)
[Базовий заголовок: Cache-Control]
```

### Специфікація `CDN-Cache-Control` (RFC 9213)
Стандарт RFC 9213 впроваджує універсальний заголовок, призначений виключно для кеш-серверів CDN, який ігнорується клієнтськими браузерами:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=0, must-revalidate
CDN-Cache-Control: public, max-age=3600, stale-while-revalidate=600
```

У цьому прикладі браузер кінцевого користувача вважає ресурс застарілим одразу після завантаження (`max-age=0`) і завжди перевіряє його валідність, тоді як розподілена мережа CDN надійно утримує копію в оперативній пам'яті протягом однієї години (`max-age=3600`), розвантажуючи центральний Origin.

## Заголовки умовної валідації та протокол злиття заголовків

Умовна валідація дозволяє перевірити, чи змінився ресурс на сервері, передаючи мінімальний обсяг мережевого трафіку:

### 1. Заголовок `ETag` (Entity Tag)
Унікальний рядок-ідентифікатор версії ресурсу, що генерується сервером:
- **Сильний ETag** (наприклад, `ETag: "686897696a7c-gzip"`): гарантує побайтову ідентичність тіла відповіді;
- **Слабкий ETag** (наприклад, `ETag: W/"582-xyz"`): гарантує семантичну еквівалентність контенту (наприклад, дві сторінки містять однаковий текст, але відрізняються часовою міткою у коментарі HTML).

### 2. Механіка обробки відповіді `304 Not Modified`
Коли крайовий вузол надсилає умовний запит з `If-None-Match: "686897696a7c-gzip"`, і центральний сервер підтверджує незмінність ресурсу статусом `304 Not Modified`:
- Сервер не передає тіло відповіді, заощаджуючи 99% пропускної здатності;
- Крайовий вузол виконує процедуру злиття заголовків (Header Merging): оновлює службові заголовки `Date`, `Expires` та `Cache-Control` з отриманої відповіді 304, залишаючи тіло відповіді та заголовки `Content-Type` і `Content-Length` зі збереженого кешу;
- Внутрішній лічильник `Age` скидається в 0, а ресурс переходить у стан Fresh.

### 3. Заголовок `Vary`
Вказує, які саме заголовки вхідного HTTP-запиту повинні враховуватися під час формування унікального ключа кешування (Cache Key). Наприклад, `Vary: Accept-Encoding, X-Device-Type` зобов'язує CDN зберігати окремі версії файлу для стиснення Gzip, Brotli та для мобільних/десктопних клієнтів.

## Обробка діапазонних запитів (Range Requests та 206 Partial Content)

Для оптимізації відтворення відеофайлів та докачування великих бінарних файлів застосовується заголовок `Range`:

```http
GET /video/sample.mp4 HTTP/1.1
Host: cdn.example.com
Range: bytes=1048576-2097151
```

Крайовий вузол CDN обробляє діапазонний запит за однією з двох стратегій:
1. **Повний кеш (Full-Object Cache)**: Якщо файл уже повністю збережений у локальному кеші PoP-вузла, крайовий сервер виділяє запитаний фрагмент із пам'яті та повертає статус `206 Partial Content` із заголовком `Content-Range: bytes 1048576-2097151/52428800` без звернення до Origin;
2. **Пофрагментний кеш (Byte-Range Slice Caching)**: Якщо файл має розмір десятки гігабайтів, CDN розбиває його на фіксовані блоки (наприклад, по 2 МБ) і кешує лише ті чанки, які реально переглянув користувач.

## Групова інвалідація: Сурогатні ключі (Surrogate-Keys / Cache-Tags)

Сурогатні ключі (Cache-Tags) дозволяють здійснювати зв'язане керування кешем для складних вебпорталів.

Центральний сервер при генерації сторінки позначає її відповідними тегами сутностей:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Cache-Control: public, max-age=86400
Surrogate-Key: product-4829 category-electronics brand-sony in-stock
```

Крайовий вузол зберігає сторінку в кеші, додає посилання на неї у внутрішні списки зворотного індексу для кожного зі зазначених ключів (`product-4829`, `category-electronics`, `brand-sony`, `in-stock`), і автоматично вирізає заголовок `Surrogate-Key` перед відправкою відповіді клієнту.

Коли ціна товару змінюється, бекенд надсилає один Purge-запит на тег `product-4829`. Крайова мережа знаходить усі сторінки, що містять цей тег (сторінку товару, сторінку категорії, результати пошуку та блок знижок), і миттєво інвалідує їх по всьому світу.

## Специфікація REST API для програмного очищення кешу (Purge API)

Програмне очищення здійснюється через захищений HTTPS REST API крайового провайдера.

### 1. Очищення за списком URL (Purge by URL)
Дозволяє видалити конкретні файли за їхньою точною абсолютною адресою:

```http
POST /v1/zones/8a92b3c4d5e6/purge_cache HTTP/1.1
Host: api.cdn-provider.com
Authorization: Bearer cdn_api_token_live_9f83a2c1
Content-Type: application/json

{
  "files": [
    "https://example.com/assets/bundle.js",
    "https://example.com/api/products/4829"
  ]
}
```

### 2. Очищення за Cache-Tags / Surrogate-Keys
Дозволяє миттєво скинути тисячі зв'язаних сторінок за спільним ідентифікатором:

```http
POST /v1/zones/8a92b3c4d5e6/purge_cache HTTP/1.1
Host: api.cdn-provider.com
Authorization: Bearer cdn_api_token_live_9f83a2c1
Content-Type: application/json

{
  "tags": [
    "product-4829",
    "category-electronics"
  ]
}
```

### 3. Очищення за префіксом (Prefix Purge)
Дозволяє інвалідувати всі файли, шлях яких починається з певного префікса (наприклад, при оновленні версії всього каталогу статичних ресурсів):

```http
POST /v1/zones/8a92b3c4d5e6/purge_cache HTTP/1.1
Host: api.cdn-provider.com
Authorization: Bearer cdn_api_token_live_9f83a2c1
Content-Type: application/json

{
  "prefixes": [
    "example.com/static/v2/",
    "example.com/images/thumbnails/"
  ]
}
```

### Схема успішної відповіді сервера (`200 OK`):
```json
{
  "success": true,
  "errors": [],
  "messages": [],
  "result": {
    "id": "purge_req_98127391823",
    "timestamp": "2026-08-20T01:54:19Z",
    "purged_count": 142
  }
}
```

### Коди помилок та обробка виняткових ситуацій:
- `400 Bad Request`: некоректний синтаксис JSON або заборонені символи в назвах тегів;
- `401 Unauthorized`: відсутній або прострочений Bearer-токен автентифікації;
- `403 Forbidden`: токен не має дозволів на запис у зону `zone_id`;
- `429 Too Many Requests`: перевищено ліміт запитів до API очищення (стандартне обмеження: 2000 викликів на 5 хвилин);
- `503 Service Unavailable`: переповнення черги реплікації інвалідацій на магістральних брокерах CDN.
