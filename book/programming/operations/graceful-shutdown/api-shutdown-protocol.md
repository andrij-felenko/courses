# 📋 Протоколи та системні контракти штатного вимкнення

Штатне вимкнення та дренаж у розподілених системах спираються на багаторівневий набір інтерфейсів: від низькорівневих сигналів ядра POSIX до бінарних фреймів протоколів прикладного рівня (HTTP/2, HTTP/3, WebSocket, GraphQL-WS, gRPC), протоколів брокерів повідомлень (Kafka, AMQP), контрактів баз даних, пулів з'єднань, алгоритмів консенсусу (Raft, etcd), контролерів контрольних груп cgroups v2, криптографічного стирання секретів, інтерфейсів Windows Service Control Manager (SCM), сервісних сіток (Service Mesh) та декларативних директив супервізорів (systemd, Kubernetes, containerd, AWS ALB, Envoy). У цій довідці зведено точні специфікації, сигнатури, бінарні структури, числові константи та часові контракти, необхідні для коректної реалізації процедур завершення роботи.

## 1. Сигнали POSIX та асинхронна безпека

У стандарті POSIX.1-2017 керування життєвим циклом процесу реалізується за допомогою сигналів. Кожен сигнал має фіксований номер, типову дію ядра та специфіковане призначення під час вимкнення.

### Таблиця сигналів життєвого циклу

| Сигнал | Номер | Типова дія | Перехоплення | Призначення під час згортання |
| :--- | :--- | :--- | :--- | :--- |
| `SIGHUP` | 1 | Завершення | Так | Історично — обрив термінала; у демонах — перечитування конфігурації без зупинки або перезапуск воркерів. |
| `SIGINT` | 2 | Завершення | Так | Переривання з термінала (`Ctrl+C`); ініціація інтерактивного штатного вимкнення. |
| `SIGQUIT` | 3 | Дамп пам'яті | Так | Завершення з генерацією core dump (`Ctrl+\`); часто використовується для екстреного згортання без очікування дренажу. |
| `SIGKILL` | 9 | Негайне знищення | **Ні** | Безумовне примусове вбивство процесу ядром; перехоплення та блокування неможливі. |
| `SIGUSR1` | 10 | Завершення | Так | Користувацький сигнал 1; в Apache/NGINX — ротація логів або плавний перезапуск воркерів. |
| `SIGUSR2` | 12 | Завершення | Так | Користувацький сигнал 2; в NGINX — безшовне оновлення виконуваного бінарного файлу на льоту. |
| `SIGTERM` | 15 | Завершення | Так | Головний сигнал штатного завершення від супервізорів (systemd, Kubernetes, Docker). |
| `SIGWINCH` | 28 | Ігнорування | Так | Зміна розміру вікна; в NGINX — зупинка запуску нових воркерів під час оновлення бінарника. |

### Контракт асинхронно-сигнальної безпеки (Async-Signal-Safe)

Згідно з POSIX.1 (розділ 2.4.3), усередині обробника сигналу дозволено викликати лише вузький перелік функцій. Будь-який виклик функцій, що не входять до безпечного списку, спричиняє невизначену поведінку (Undefined Behavior) та ризик мертвого блокування (deadlock).

```
┌───────────────────────────────────────────────┬───────────────────────────────────────────────┐
│     ДОЗВОЛЕНІ (Async-Signal-Safe)             │       ЗАБОРОНЕНІ (Небезпечні в обробнику)     │
├───────────────────────────────────────────────┼───────────────────────────────────────────────┤
│ _exit(), _Exit()                              │ exit(), quick_exit(), atexit()                │
│ write(), read(), open(), close()              │ printf(), sprintf(), snprintf(), puts()       │
│ signalfd(), eventfd(), timerfd_create()       │ malloc(), free(), realloc(), calloc()         │
│ kill(), raise(), sigaction(), sigprocmask()   │ pthread_mutex_lock(), pthread_cond_signal()   │
│ clock_gettime(), time(), getpid()             │ syslog(), getaddrinfo(), gethostbyname()      │
│ strlen(), memcpy(), memset() (чисті)          │ operator new, operator delete, std::string    │
│ sig_atomic_t (читання/запис)                  │ C++ iostream (std::cout, std::cerr)           │
└───────────────────────────────────────────────┴───────────────────────────────────────────────┘
```

## 2. Мережеві протоколи прикладного рівня

Для запобігання втраті клієнтських запитів під час дренажу протоколи прикладного рівня надають спеціальні сигнальні заголовки та бінарні керуючі фрейми.

### HTTP/1.1 (RFC 9112): Заголовок `Connection: close`

У протоколі HTTP/1.1 за замовчуванням діє режим постійного з'єднання (Persistent Connection / Keep-Alive). Щоб сповістити клієнта про намір закрити TCP-з'єднання після поточної відповіді, сервер додає заголовок:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 42
Connection: close

{"status":"success","message":"processed"}
```

Контракт поведінки:
- Сервер зобов'язаний повністю передати тіло поточної відповіді.
- Після передачі останнього байта сервер виконує активне закриття сокета через `shutdown(fd, SHUT_WR)` або `close(fd)`.
- Клієнт, отримавши заголовок `Connection: close`, не має права надсилати нові запити у цей сокет і зобов'язаний закрити своє з'єднання.

### HTTP/2 (RFC 7540): Керуючий фрейм `GOAWAY`

У мультиплексованому протоколі HTTP/2 для закриття з'єднання використовується фрейм типу `0x7` (`GOAWAY`).

#### Бінарна структура фрейму GOAWAY

```
+---------------------------------------------------------------+
|                        Length (24 bits)                       |
+---------------+---------------+---------------+---------------+
|   Type (0x7)  |   Flags (0x0) |           R (1 bit)           |
+---------------+---------------+---------------+---------------+
|                     Last-Stream-ID (31 bits)                  |
+---------------------------------------------------------------+
|                      Error Code (32 bits)                     |
+---------------------------------------------------------------+
|                  Additional Debug Data (0...N)               |
+---------------------------------------------------------------+
```

#### Поля структури

- **`Length` (24 біти):** Довжина корисного навантаження (мінімум 8 байтів: 4 байти `Last-Stream-ID` + 4 байти `Error Code`).
- **`Type` (8 бітів):** Константа `0x07` (тип `GOAWAY`).
- **`Flags` (8 бітів):** Для `GOAWAY` прапорці не визначені (значення `0x00`).
- **`Last-Stream-ID` (31 біт):** Найвищий числовий ідентифікатор потоку (Stream ID), який відправник прийняв в обробку. Будь-які потоки з номерами, вищими за це значення, відправник проігнорував.
- **`Error Code` (32 біти):** 32-бітний числовий код причини закриття:
  - `0x00` (`NO_ERROR` / `GRACEFUL_SHUTDOWN`): Штатне планове закриття з'єднання.
  - `0x01` (`PROTOCOL_ERROR`): Порушення специфікації протоколу.
  - `0x02` (`INTERNAL_ERROR`): Внутрішня помилка сервера.
  - `0x0b` (`ENHANCE_YOUR_CALM`): Перевищення лімітів навантаження.
- **`Additional Debug Data`:** Довільні бінарні або текстові діагностичні дані (наприклад, рядок `"server draining for rolling update"`).

#### Двокроковий протокол дренажу (Graceful GOAWAY Dance)

```
Клієнт                                             Сервер
  │                                                   │ [Отримано SIGTERM]
  │ ─── Stream 5: GET /api/v1/users ────────────────> │
  │ ─── Stream 7: POST /api/v1/payments ────────────> │
  │                                                   │
  │ <── GOAWAY (Last-Stream-ID: 2^31-1, NO_ERROR) ─── │ [Крок 1: заборона нових]
  │                                                   │
  │ [Клієнт припиняє створення Stream 9+]             │
  │                                                   │ [Чекаємо 1 RTT]
  │ <── GOAWAY (Last-Stream-ID: 7, NO_ERROR) ──────── │ [Крок 2: точна фіксація]
  │                                                   │
  │ <── Stream 5 Response (200 OK) ────────────────── │ [Обробка активних]
  │ <── Stream 7 Response (200 OK) ────────────────── │
  │                                                   │
  │ ─── TCP FIN / Close ────────────────────────────> │ [Чисте закриття]
```

### HTTP/3 та QUIC (RFC 9000 / RFC 9114)

У протоколі HTTP/3 поверх транспорту QUIC використовуються два рівні сигналізації:
1. **HTTP/3 `GOAWAY` Frame (Тип `0x07`):** Передається у керуючому потоці (Control Stream). Містить поле `Stream ID` у форматі змінної довжини QUIC VarInt.
2. **QUIC `CONNECTION_CLOSE` Frame (Типи `0x1c` та `0x1d`):** 
   - Тип `0x1c`: Помилка транспортного рівня QUIC.
   - Тип `0x1d`: Помилка рівня застосунку (Application Close).
   - Під час штатного закриття сервер переходить у стан `DRAINING` на період `3 * PTO` (Probe Timeout), вичитуючи залишки пакетів від клієнта без генерації повторних ACK.

### WebSocket (RFC 6455): Закриваючий фрейм (Opcode 0x8)

Для двостороннього закриття WebSocket-з'єднання відправляється керуючий фрейм із кодом операції `0x8`.

#### Стандартні коди стану WebSocket Close

| Код стану | Константа RFC 6455 | Семантика |
| :--- | :--- | :--- |
| `1000` | `Normal Closure` | Мета з'єднання успішно досягнута (штатний вихід). |
| `1001` | `Going Away` | Сервер вимикається на оновлення або клієнт залишає сторінку. |
| `1002` | `Protocol Error` | Помилка протоколу. |
| `1003` | `Unsupported Data` | Непідтримуваний тип даних (наприклад, бінарний замість тексту). |
| `1008` | `Policy Violation` | Порушення політики безпеки сервісу. |
| `1011` | `Internal Error` | Неопрацьоване виключення на сервері під час обробки. |

### GraphQL Subscriptions поверх WebSocket (RFC GraphQL-WS)

У протоколі `graphql-transport-ws` для штатної зупинки довгоживучих підписок сервер виконує двокрокове сповіщення:
1. Для кожної активної підписки сервер надсилає повідомлення типу `complete` з ідентифікатором операції (`id`):
   ```json
   {"id":"sub-42","type":"complete"}
   ```
2. Після відправки всіх повідомлень `complete` сервер закриває транспортний WebSocket-сокет із кодом `1001` (`Going Away`), спонукаючи клієнтську бібліотеку (Apollo Client, Relay, Urql) перепідключитися до іншого інстанса бекенду та відновити підписку.

### gRPC та HTTP/2 Metadata

У системі RPC від Google (gRPC) штатне вимкнення реалізується через метод `Server::Shutdown(deadline)`:
- Сервер надсилає HTTP/2 `GOAWAY` з `NO_ERROR`.
- Для нових RPC, які потрапляють у зазор між надсиланням фрейму та оновленням клієнтського каналу, сервер повертає статус `UNAVAILABLE` (код `14`) із метаданими `grpc-retry-pushback-ms: 100`, сигналізуючи клієнту про необхідність негайного повтору на сусідньому вузлі.
- Активні унарні та стрімінгові RPC продовжують виконання до завершення або вичерпання дедлайну.

## 3. Протоколи черг та брокерів повідомлень

Під час зупинки обробників черг ключовим контрактом є повернення невиконаних завдань і фіксація оброблених зміщень.

### Apache Kafka: Протокол споживачів (Consumer Group Protocol)

1. **Кооперативне перебалансування (Cooperative Sticky Assignor):** Споживач викликає `KafkaConsumer.close(Duration timeout)`.
2. **Надсилання запиту `LeaveGroupRequest`:** Споживач інформує координатора групи (Group Coordinator) про плановий вихід через явне повідомлення з кодом причини `REASON_SHUTDOWN`. Це усуває затримку очікування `session.timeout.ms` (за замовчуванням 45 секунд).
3. **Фіксація зміщень (Offset Commit):** Перед виходом виконується синхронний виклик `commitSync()` для всіх оброблених повідомлень. Якщо повідомлення взято в обробку, але не доведено до кінця, його зміщення не фіксується, і сусідній споживач підхоплює його негайно після оновлення генерації групи.

### RabbitMQ та AMQP 0-9-1

1. **Відкликання споживача (`basic.cancel`):** Воркер надсилає брокеру команду `basic.cancel(consumer_tag)`. Брокер перестає надсилати нові повідомлення у цей канал.
2. **Обробка наявних повідомлень:** Воркер докручує повідомлення, які вже потрапили у внутрішній буфер `prefetch_count`.
3. **Негативне підтвердження (`basic.nack`):** Якщо воркер не встигає завершити задачу до дедлайну, він надсилає `basic.nack(delivery_tag, multiple=false, requeue=true)`, повертаючи задачу в початок черги.
4. **Закриття каналу та сокета:** `Channel.Close` (reply-code 200) → `Connection.Close`.

## 4. Контракти пулів з'єднань баз даних

Закриття пулів підключень до реляційних і NoSQL баз даних (HikariCP, pgx, psycopg, node-postgres) підпорядковується суворим часовим інваріантам:

```
┌───────────────────────────────────┬───────────────────────────────────────────────────────────────────┐
│ Параметр пулу / Метод             │ Контракт під час дренажу                                          │
├───────────────────────────────────┼───────────────────────────────────────────────────────────────────┤
│ HikariDataSource.close()          │ Переводить пул у стан `SUSPENDED`, забороняє нові `getConnection()`│
│                                   │ Негайно закриває всі вільні (idle) з'єднання.                     │
│                                   │ Очікує завершення активних з'єднань до вичерпання таймауту.       │
│ pgxpool.Close() (Go)              │ Закриває слухач пулу, очікує повернення зайнятих дескрипторів.    │
│ maxLifetime                       │ Максимальний вік сокета; запобігає зависанню з'єднань на проксі.  │
│ connectionTimeout                 │ Таймаут очікування вільного з'єднання клієнтським потоком.        │
│ leakDetectionThreshold            │ Поріг виявлення витоку з'єднань (попередження в лог при зависанні).│
└───────────────────────────────────┴───────────────────────────────────────────────────────────────────┘
```

Якщо під час вимкнення сесія бази даних утримує незавершену транзакцію (`BEGIN` без `COMMIT`), клієнтський драйвер при закритті сокета надсилає команду `ROLLBACK` або ядро СУБД (PostgreSQL, MySQL) автоматично відкочує транзакцію при отриманні `TCP FIN/RST`, звільняючи рядкові блокування (Row-Level Locks).

## 5. Розподілений консенсус та передача лідерства (Raft, etcd, Consul)

У кластерних сховищах та системах координації раптове вимкнення лідера спричиняє вибори нового лідера через вичерпання таймауту виборів (Election Timeout, зазвичай 1–3 секунди), протягом якого кластер не приймає операції запису.

### Протокол передачі лідерства (Leadership Transfer)
1. **Ініціація передачі (`StepDown` / `TransferLeadership`):** Перед вимкненням лідер вузла обирає найбільш актуального послідовника (Follower з найвищим `matchIndex`) і надсилає йому RPC `TimeoutNow`.
2. **Миттєві вибори:** Послідовник негайно починає новий термін (Term) і надсилає запити `RequestVote`, стаючи новим лідером без очікування таймауту виборів.
3. **Звільнення сесій блокувань (Consul / etcd Lease Revocation):** Вузол явно відкликає свої ключі блокування (Distributed Locks / Leases), дозволяючи іншим інстансам негайно захопити роль обробника черги.

## 6. Контейнерні рушії та передача сигналів (PID 1 Subreaper)

Усередині контейнерів Linux (Docker, containerd, Podman) процес із PID 1 має особливий статус ядра: за замовчуванням ядро ігнорує будь-які сигнали, надіслані процесу PID 1, якщо той явно не встановив власний обробник сигналу через `sigaction`.

### Проблема запуску через оболонку
Якщо контейнер запущено як:
```dockerfile
ENTRYPOINT ./start.sh
```
Оболонка `/bin/sh` стає PID 1, але вона не пересилає сигнал `SIGTERM` своїм дочірнім процесам. Як наслідок, контейнер чекає 30 секунд до приходу `SIGKILL`.

Для вирішення проблеми застосовують:
- Виклик через заміну образу: `exec ./server` у скрипті запуску.
- Використання супервізора-ініціалізатора (наприклад, `tini` або `dumb-init`), який реєструється через системний виклик `prctl(PR_SET_CHILD_SUBREAPER, 1)` і коректно транслює `SIGTERM` усій групі процесів, а також збирає процеси-зомбі (`waitpid`).

## 7. Контрольні групи Linux cgroups v2: Інтерфейси `freeze` та `kill`

У сучасних версіях ядра Linux керування групами процесів у cgroups v2 надає атомарні файлові інтерфейси в псевдофайловій системі `/sys/fs/cgroup`:

```
┌───────────────────────────────────┬───────────────────────────────────────────────────────────────────┐
│ Файловий інтерфейс cgroups v2     │ Специфікація дії ядра                                             │
├───────────────────────────────────┼───────────────────────────────────────────────────────────────────┤
│ cgroup.freeze (значення 1)        │ Атомарно заморожує всі процеси групи у стані D/TASK_UNINTERRUPTIBLE│
│                                   │ Планувальник вилучає їх з черги виконання без надсилання сигналів.│
│ cgroup.freeze (значення 0)        │ Розморожує всі процеси групи для відновлення роботи.              │
│ cgroup.kill (значення 1)          │ Ядро надсилає сигнал SIGKILL усім процесам групи одночасно.       │
│                                   │ Повністю усуває проблему процесів-сиріт, які уникали SIGTERM.     │
└───────────────────────────────────┴───────────────────────────────────────────────────────────────────┘
```

## 8. Криптографічна гігієна та стирання ключів у пам'яті

Під час завершення роботи процесів, що оперують конфіденційними даними (TLS-сертифікати, приватні ключі автентифікації, сесійні токени), стандартний виклик `free()` не очищає байти оперативної пам'яті. Сторонні процеси або дампи пам'яті можуть вичитати залишки секретів.

Координатор штатного вимкнення зобов'язаний виконати гарантоване занулення буферів пам'яті:

:::tabs
```c
/* Безпечне занулення в C без оптимізацій компілятора */
explicit_bzero(secret_key_buffer, key_size);
OPENSSL_cleanse(private_key, key_length);
```
```cpp
// Безпечне занулення в C++ (через std::span та OpenSSL)
#include <span>
#include <openssl/crypto.h>

void wipe_memory(std::span<std::byte> secret_buffer) noexcept {
    OPENSSL_cleanse(secret_buffer.data(), secret_buffer.size());
}
```
:::

Якщо пам'ять була заблокована від вивантаження у файл підкачки через системний виклик `mlock(ptr, size)`, координатор перед завершенням викликає `munlock(ptr, size)`.


## 9. Служби Windows: Контракти Service Control Manager (SCM)

У середовищі Windows NT/Server керування службами здійснюється системним процесом `services.exe` через інтерфейс Service Control Handler:

```
┌───────────────────────────────────┬───────────────────────────────────────────────────────────────────┐
│ Керуючий код SCM                  │ Контракт обробки службою                                          │
├───────────────────────────────────┼───────────────────────────────────────────────────────────────────┤
│ SERVICE_CONTROL_STOP              │ Системний наказ зупинити службу (аналог SIGTERM).                 │
│ SERVICE_CONTROL_PRESHUTDOWN       │ Сповіщення про вимикання ОС до зупинки звичайних служб.           │
│                                   │ Служба має право запросити розширений таймаут (до кількох хвилин).│
│ SERVICE_CONTROL_SHUTDOWN          │ Фінальне сповіщення перед перезавантаженням комп'ютера.           │
└───────────────────────────────────┴───────────────────────────────────────────────────────────────────┘
```

Під час дренажу служба повідомляє диспетчер SCM про прогрес за допомогою виклику `SetServiceStatus`:
- Статус встановлюється у `SERVICE_STOP_PENDING`.
- Поле `dwWaitHint` передає SCM очікуваний час дренажу в мілісекундах (наприклад, 15000 мс).
- Поле `dwCheckPoint` регулярно інкрементується; якщо служба не оновить чекпоінт протягом `dwWaitHint`, SCM вважає процес завислим і примусово знищує його (`TerminateProcess`).

## 10. Сервісні сітки та Sidecar-синхронізація (Istio, Envoy)

У сервісних сітках (Service Mesh) усередині одного Pod одночасно функціонують два контейнери: основний застосунок та проксі-sidecar (Envoy).

### Порядок згортання у Service Mesh
1. **Захист від передчасної смерті Sidecar:** Якщо контейнер Envoy зупиниться раніше за основний застосунок, усі вихідні HTTP/gRPC-запити застосунку до бази даних та зовнішніх сервісів будуть миттєво обірвані.
2. **Налаштування затримки Envoy:**
   ```yaml
   apiVersion: networking.istio.io/v1alpha3
   kind: Sidecar
   metadata:
     name: default
   spec:
     lifecycle:
       preStop:
         exec:
           command: ["/usr/local/bin/pilot-agent", "request", "POST", "/drain_listeners?graceful"]
   ```
3. **Прапорець `EXIT_ON_ZERO_ACTIVE_CONNECTIONS`:** Проксі-агент очікує, поки лічильник активних клієнтських з'єднань застосунку опуститься до нуля, і лише після цього завершує свій власний процес.

## 11. Специфікація життєвого циклу Kubernetes Pod

В оркестраторі Kubernetes процес вимкнення контейнера регламентується специфікацією `PodSpec` та узгоджується з мережевими контролерами `EndpointSlice`.

### Конфігураційні параметри `PodSpec`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: api-service
spec:
  terminationGracePeriodSeconds: 30
  containers:
  - name: server
    image: app:v2.4.0
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 10"]
    readinessProbe:
      httpGet:
        path: /healthz/ready
        port: 8080
      periodSeconds: 2
      failureThreshold: 1
```

## 12. Директиви конфігурації systemd Service

Для сервісів, що керуються системним менеджером Linux systemd, директиви зупинки налаштовуються у секції `[Service]` юніт-файлу (наприклад, `/etc/systemd/system/api-service.service`).

### Параметри секції `[Service]`

```ini
[Unit]
Description=High-Performance API Service
After=network.target remote-fs.target

[Service]
Type=notify
ExecStart=/usr/local/bin/api-server
ExecStop=/usr/local/bin/api-server --drain-command
TimeoutStopSec=30s
KillMode=control-group
KillSignal=SIGTERM
SendSIGKILL=yes
FinalKillSignal=SIGKILL
SuccessExitStatus=0 143
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

### Специфікація директив зупинки systemd

- **`TimeoutStopSec=`:** Час очікування завершення сервісу після надсилання `ExecStop=` або `KillSignal=`. Типове значення в systemd — `90s`. Якщо сервіс не завершився, надсилається `SIGKILL`.
- **`KillMode=`:** Стратегія надсилання сигналів процесам у cgroup сервісу:
  - `control-group` (за замовчуванням): Сигнал надсилається головному процесу та всім дочірнім процесам у цій контрольній групі.
  - `process`: Сигнал надсилається **тільки** головному процесу (PID 1 сервісу). Дочірні процеси повинні згортатися самостійно.
  - `mixed`: Спочатку `SIGTERM` надсилається тільки головному процесу, а після вичерпання `TimeoutStopSec` сигнал `SIGKILL` надсилається всій cgroup.
  - `none`: systemd не надсилає жодних сигналів автоматично (використовується лише `ExecStop=`).
- **`KillSignal=`:** Сигнал, який надсилається для початку зупинки (за замовчуванням `SIGTERM`).
- **`SendSIGKILL=`:** Чи надсилати `SIGKILL` після завершення `TimeoutStopSec` (значення `yes` або `no`).
- **`FinalKillSignal=`:** Сигнал фінального знищення (за замовчуванням `SIGKILL`).
- **`SuccessExitStatus=`:** Список додаткових кодів виходу, які systemd вважає успішним завершенням (наприклад, код `143` для `SIGTERM`).

## 13. Хмарні балансувальники та проксі (AWS ALB, Envoy)

На рівні граничних шлюзів та проксі-серверів діють власні контракти дренажу:

### AWS Application Load Balancer (ALB) Target Group
- **`deregistration_delay.timeout_seconds`:** Час, протягом якого ALB дозволяє існуючим з'єднанням завершити роботу після вилучення інстанса з Target Group (за замовчуванням 300 секунд, для мікросервісів зазвичай зменшується до 15–30 секунд). Протягом цього вікна ALB не скеровує на вузол нові запити, але не розриває існуючі сесії.

### Envoy Proxy Drain Manager
- **`/drain_listeners?graceful`:** Адміністративний ендпоінт Envoy для початку плавної зупинки слухачів.
- **`drain_strategy: DRAIN_ALL`:** Envoy надсилає HTTP/1.1 `Connection: close` та HTTP/2 `GOAWAY` усім підключеним клієнтам і очікує завершення конфігурованого інтервалу `drain_time` (за замовчуванням 600 секунд).

## 15. Стандартні коди завершення процесу (Exit Codes)

Згідно зі стандартом POSIX та угодами системних оболонок (Unix Shell Exit Status Conventions), код завершення процесу є 8-бітним цілим числом без знаку (діапазон `0..255`).

```
┌───────────────┬───────────────────────────────────────────────────────────────────────────────┐
│  Код виходу   │ Значення за стандартом POSIX / Linux                                         │
├───────────────┼───────────────────────────────────────────────────────────────────────────────┤
│ 0             │ Успішне штатне завершення (Success / Graceful Exit).                          │
│ 1             │ Загальна помилка виконання (General Catchall Error).                          │
│ 2             │ Некоректне використання вбудованих команд оболонки або помилка парсингу CLI. │
│ 126           │ Команда знайдена, але файл не є виконуваним (Permission Denied).             │
│ 127           │ Команду не знайдено в таблиці $PATH.                                         │
│ 128           │ Некоректний аргумент команди exit (вихід за межі 8 біт).                     │
│ 128 + N       │ Процес завершено зовнішнім сигналом з номером N (Фатальний сигнал).           │
│ 130 (128 + 2) │ Процес примусово перервано сигналом SIGINT (Ctrl+C).                         │
│ 137 (128 + 9) │ Процес примусово знищено ядром через SIGKILL (або OOM Killer).                │
│ 143 (128 + 15)│ Процес зупинено сигналом SIGTERM (стандартний вихід за наказом оркестратора). │
└───────────────┴───────────────────────────────────────────────────────────────────────────────┘
```

Контракт для контейнерів: якщо застосунок самостійно обробив `SIGTERM`, повністю виконав дренаж і викликав `exit(0)`, оркестратор фіксує статус `Completed` з кодом `0`. Якщо ж застосунок не встановлював обробник `SIGTERM` і був завершений стандартною дією сигналу за замовчуванням, операційна система поверне статус `143`, що також інтерпретується оркестратором як планова зупинка, але свідчить про відсутність штатного внутрішнього дренажу.
