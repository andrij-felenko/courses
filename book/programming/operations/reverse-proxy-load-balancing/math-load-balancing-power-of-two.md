# 🧮 Математика розподілу навантаження: степеневі вибори, дисперсія черг та узгоджене хешування

Розподіл потоку незалежних запитів між пулом паралельних обчислювальних серверів є класичною задачею теорії ймовірностей, відомою в комбінаториці як «задача про розміщення куль у комірках» (англ. *balls-into-bins problem*). Коли `N` однакових куль (клієнтських HTTP-запитів) незалежно й рівномірно розподіляються між `N` комірками (серверами бекенда), виникає фундаментальне питання: наскільки нерівномірним буде завантаження найповільнішого або найбільш перевантаженого вузла, і як прості математичні евристики здатні експоненційно зменшити довжину черг очікування.

## Класична випадкова схема (d = 1) та логарифмічна висота піку

Розглянемо базовий випадок, коли кожен вхідний запит направляється на один випадково обраний сервер із пулу розміром `N` з однаковою ймовірністю `p = 1 / N`.

Кількість запитів `X[j]`, які потрапляють на фіксований сервер `j` при загальній кількості запитів `M = N`, описується біноміальним розподілом `Binomial(N, 1/N)`. При великих значеннях `N` цей розподіл апроксимується розподілом Пуассона з параметром `λ = N · (1/N) = 1`:

```
P(X[j] = k)
= (N! / (k! · (N - k)!)) · (1 / N)ᵏ · (1 - 1 / N)ᴺ⁻ᵏ   [біноміальний розподіл]
≈ (e⁻¹ · 1ᵏ) / k!                                        [наближення Пуассона при N → ∞]
= 1 / (e · k!)                                           [спрощення: 1ᵏ = 1]
```

Нас цікавить математичне сподівання максимального завантаження серед усіх `N` серверів:

```
L_max(1) = max_{1 ≤ j ≤ N} (X[j])
```

Використовуючи формулу Стірлінґа для факторіала `k! ≈ √(2·π·k) · (k / e)ᵏ`, оцінимо ймовірність того, що окремий сервер отримає щонайменше `k` запитів:

```
P(X[j] ≥ k)
≈ 1 / (e · k!)                                           [хвіст розподілу Пуассона]
≈ 1 / (e · √(2·π·k) · (k / e)ᵏ)                          [апроксимація Стірлінґа]
```

Застосовуючи нерівність об'єднання (Union Bound) для всіх `N` серверів:

```
P(L_max(1) ≥ k)
≤ ∑_{j=1}^{N} P(X[j] ≥ k)                                [нерівність об'єднання]
= N · P(X[1] ≥ k)                                        [симетрія однакових серверів]
≈ N / (√(2·π·k) · (k / e)ᵏ)                              [підстановка оцінки Пуассона]
```

Покладемо цю ймовірність рівною малій константі та розв'яжемо рівняння відносно `k`:

```
N ≈ (k / e)ᵏ
ln(N) ≈ k · (ln(k) - 1)                                  [логарифмування обох частин]
ln(N) ≈ k · ln(k)                                        [головний асимптотичний член]
k ≈ ln(N) / ln(ln(N))                                    [ітераційне наближення]
```

Теорема про максимальне завантаження при чисто випадковому виборі стверджує: при розподілі `N` куль по `N` комірках максимальна кількість куль у найбільш завантаженій комірці з високою ймовірністю (With High Probability, `1 - o(1)`) становить:

```
L_max(1)
= (ln(N) / ln(ln(N))) · (1 + o(1))                       [асимптотична межа при d = 1]
```

Це означає, що при чисто випадковому виборі серверів пікове навантаження на один сервер зростає як сублогарифмічна функція від розміру кластера. Для кластера з 1 000 000 серверів найнещасніший сервер отримає приблизно у 8–9 разів більше навантаження, ніж середньостатистичний, що неминуче спричинить спалах затримок (Latency Spike) і вичерпання черг сокетів.

## Сила двох випадкових виборів (Power of Two Choices, d = 2)

У 1999 році дослідники Йосі Азар, Андрій Бродер, Анна Карлін та Елі Упфал (Yossi Azar, Andrei Broder, Anna Karlin, Eli Upfal) довели дивовижний математичний результат, відомий як теорема «Power of Two Random Choices» (P2C).

Модифікуємо алгоритм: замість сліпого призначення на один випадковий сервер, балансувальник незалежно і рівномірно обирає `d = 2` випадкових сервери (кандидати `A` та `B`), порівнює їхню поточну кількість запитів і призначає новий запит тому серверу, який містить менше запитів (при рівності — будь-якому з двох).

```
ДВА ВИБОРІВ (d = 2):
1. Обираємо вузли i, j ∈ {1..N} рівномірно й незалежно
2. q[i] — поточна черга вузла i; q[j] — поточна черга вузла j
3. Якщо q[i] ≤ q[j] → призначити вузлу i; інакше → призначити вузлу j
```

### Доведення експоненційного скорочення черги

Введемо випадкову величину `ν[i]`, яка позначає частку серверів, що мають чергу висотою не менше `i` (тобто щонайменше `i` запитів) у системі з `N` серверами після розміщення `N` куль:

```
ν[i] = (Кількість серверів із чергою ≥ i) / N
```

За побудовою алгоритму, новий запит потрапляє на рівень `i + 1` (тобто збільшує висоту черги деякого сервера з `i` до `i + 1`) тоді й лише тоді, коли **обидва** обраних сервери `A` та `B` вже мають висоту черги щонайменше `i`:

```
P(Запит збільшує чергу до i + 1)
= P(Черга(A) ≥ i AND Черга(B) ≥ i)                       [умова вибору P2C]
= P(Черга(A) ≥ i) · P(Черга(B) ≥ i)                      [незалежність вибору A і B]
= (ν[i]) · (ν[i])                                        [частка вузлів із чергою ≥ i]
= (ν[i])²                                                [квадратичне згасання]
```

Оскільки сумарно надходить `N` запитів, очікувана зміна загальної кількості вузлів із чергою висотою `≥ i + 1` задовольняє рекурентну верхню оцінку:

```
ν[i + 1]
≤ (ν[i])²                                                [рекурентне квадратичне співвідношення]
```

Початкова умова: частка вузлів із чергою висотою `≥ 1` не може перевищувати середнє навантаження, тобто `ν[1] ≤ 1`. Якщо розглянути базовий рівень `ν[6] ≤ 1/2` (константа, що строго доводиться через експоненційні мартингали Азуми-Хьофдінга), рекурентна послідовність породжує ланцюг подвійних степенів:

```
ν[6 + 1] ≤ (1/2)² = (1/2)²¹
ν[6 + 2] ≤ ((1/2)²)² = (1/2)²² = (1/2)⁴
ν[6 + 3] ≤ (1/2)²³ = (1/2)⁸
...
ν[6 + k] ≤ (1/2)²ᵏ                                       [експонента у показнику степеня]
```

Знайдемо критичну висоту `k`, за якої очікувана кількість серверів із такою довжиною черги стає меншою за одиницю (`N · ν[6 + k] < 1`), тобто таких серверів у системі не залишиться зовсім:

```
N · (1/2)²ᵏ < 1
N < 2²ᵏ                                                  [множення на 2²ᵏ]
ln(N) < 2ᵏ · ln(2)                                       [логарифмування]
2ᵏ > ln(N) / ln(2)                                       [ділення на ln(2)]
k > log₂[ ln(N) / ln(2) ]                                [повторне логарифмування за основою 2]
k ≈ (ln(ln(N)) / ln(2))                                  [перехід до натурального логарифма]
```

Отже, максимальна довжина черги `L_max(2)` для схеми з вибором із двох кандидатів становить:

```
L_max(2)
= (ln(ln(N)) / ln(2)) + O(1)                             [теорема Азара-Бродера-Карлін-Упфала]
```

### Порівняння швидкості росту при d = 1, d = 2 та d = 3

Складемо порівняльну таблицю максимальної черги для кластерів різного масштабу:

| Кількість серверів `N` | `d = 1` (Випадково, `ln N / ln ln N`) | `d = 2` (P2C, `ln ln N / ln 2`) | `d = 3` (`ln ln N / ln 3`) |
| :--- | :--- | :--- | :--- |
| `100` | 3.5 | 2.2 | 1.4 |
| `10 000` | 5.3 | 3.2 | 2.0 |
| `1 000 000` (1 млн) | 8.8 | 3.8 | 2.4 |
| `1 000 000 000` (1 млрд) | 12.4 | 4.4 | 2.8 |

Математичний висновок фундаментальний: перехід від `d = 1` до `d = 2` перетворює логарифмічний ріст пікового навантаження на практично константний (подвійний логарифм `ln(ln(N))` зростає надзвичайно повільно: для 1 мільярда вузлів максимальна черга складає лише 4–5 одиниць).

Водночас перехід від `d = 2` до `d = 3` дає лише незначне покращення (зменшення дільника з `ln(2) ≈ 0.693` до `ln(3) ≈ 1.098`), але збільшує накладні витрати на вимірювання телеметрії на 50%. Тому вибір `d = 2` є точкою оптимуму за критерієм витрати-якість і використовується в усіх сучасних балансувальниках (Envoy, Finagle, gRPC).

### Зважений P2C (Weighted Power of Two Choices)

Коли бекенди мають різну обчислювальну потужність, кожному вузлу `i` призначається статична вага `w[i] > 0`. Загальна сума ваг:

```
W_total = ∑_{i=1}^{N} w[i]
```

Імовірність вибору вузла `i` як першого або другого кандидата робиться пропорційною його вазі:

```
P(Вибір кандидата = i) = w[i] / W_total
```

Порівняння двох обраних кандидатів `A` та `B` виконується не за абсолютною кількістю активних з'єднань, а за нормованим навантаженням:

```
Навантаження(i) = Активні_з'єднання[i] / w[i]
```

Запит направляється вузлу з меншим нормованим навантаженням. Теорема про зважений P2C гарантує, що частка часу, яку кожен сервер проводить під навантаженням, пропорційна його вазі, а максимальне відхилення від середньозваженої затримки залишається обмеженим константою `O(ln(ln(N)))`.

## Динамічна модель супермаркету (Supermarket Model) та марковські ланцюги

Розглянемо безперервну динамічну систему, де запити не просто прибувають, а й завершуються з певною швидкістю. Модель супермаркету (запропонована Майклом Мітценмахером, Michael Mitzenmacher) моделює `N` черг, на які надходить пуассонівський потік запитів сумарної інтенсивності `λ · N` (`λ < 1`), а час обробки кожного запиту розподілений експоненційно з одиничним параметром `μ = 1`.

Нехай `s[k](t)` — частка серверів, які в момент часу `t` мають довжину черги щонайменше `k` (де `s[0](t) = 1` для всіх `t`).

Усталений стан системи (Stationary State) при `N → ∞` описується нескінченною системою звичайних диференціальних рівнянь:

```
d s[k] / dt
= λ · (s[k - 1])ᵈ - μ · (s[k] - s[k + 1])                 [динамічний баланс притоку й відтоку]
```

Прирівнюючи похідну до нуля (`d s[k] / dt = 0`) для пошуку стаціонарного розподілу при `d = 2` та `μ = 1`:

```
λ · (s[k - 1])² = s[k] - s[k + 1]                         [стаціонарне рівняння рівноваги]
```

Розв'язок цього рівняння має вигляд подвійної експоненти:

```
s[k]
= λ^{(2ᵏ - 1)}                                            [експоненційне згасання хвоста черги]
```

Для порівняння, у класичній незалежній системі черг M/M/1 (`d = 1`) стаціонарний розподіл хвостової частки черг згасає лінійно у показнику:

```
s[k](d = 1)
= λᵏ                                                     [проста геометрична прогресія]
```

Якщо коефіцієнт навантаження системи складає `λ = 0.9` (сервери завантажені на 90%):
- При `d = 1`: частка серверів із чергою `≥ 10` становить `0.9¹⁰ ≈ 0.348` (35% усіх серверів перевантажені довгими чергами);
- При `d = 2`: частка серверів із чергою `≥ 4` становить `0.9^{(2⁴ - 1)} = 0.9¹⁵ ≈ 0.205`, а з чергою `≥ 5` становить `0.9³¹ ≈ 0.038` (менше 4%), а черга `≥ 7` зникає до нуля (`0.9¹²⁷ ≈ 0.000001`).

Це строго доводить, чому алгоритм P2C майже повністю знищує черги довжиною понад 4–5 елементів навіть при високому коефіцієнті завантаження системи.

## Моделі черг M/M/1 та затримка у хвості (Tail Latency)

У реальних системах запити різняться часом обробки. Розглянемо кожен сервер як систему масового обслуговування `M/M/1` (пуассонівський вхідний потік з інтенсивністю `λ` запитів/с та експоненційний час обслуговування з інтенсивністю `μ` запитів/с).

Середній час перебування запиту в системі (час очікування в черзі плюс час виконання) визначається формулою Хінчина-Поллачека:

```
W
= 1 / (μ - λ)                                            [середній час відгуку в M/M/1]
= (1 / μ) · (1 / (1 - ρ))                                [через коефіцієнт завантаження ρ = λ / μ]
```

Дисперсія часу відгуку:

```
Var(W)
= 1 / (μ - λ)²                                           [квадрат стандартного відхилення]
```

Коли коефіцієнт завантаження вузла `ρ` наближається до 1 (`ρ → 1`), як середній час затримки, так і його дисперсія вибухають асимптотично до нескінченності:

```
lim_{ρ → 1} W = ∞
lim_{ρ → 1} Var(W) = ∞
```

Якщо балансувальник розподіляє трафік наївно за циклічним Round Robin, випадкові «важкі» запити накопичуються на окремих вузлах. Вузол із коефіцієнтом `ρ = 0.95` демонструє затримку у 20 разів вищу, ніж вузол із `ρ = 0.50` (`1 / (1 - 0.95) = 20` проти `1 / (1 - 0.50) = 2`).

Використання алгоритму **Peak EWMA (Exponentially Weighted Moving Average)**, де завантаження оцінюється як добуток активних з'єднань на згладжену затримку:

```
EWMA[t]
= α · Latency_sample + (1 - α) · EWMA[t - 1]             [експоненційне згладжування затримки]
Вага(вузла)
= Активні_з'єднання · EWMA[t]                            [комбінована метрика навантаження]
```

дозволяє алгоритму P2C оперативно відхиляти трафік від серверів, які входять у зону насичення `ρ → 1`, ліквідуючи довгі хвости затримок 99-го та 99.9-го перцентилів (P99 / P99.9).

## Математика узгодженого хешування (Consistent Hashing)

Коли запити повинні маршрутизуватися детерміновано (наприклад, для утримання сесій або підвищення попадання в кеш), застосовують хешування.

Класичне наївне хешування за модулем `Сервер = Hash(Key) mod N` володіє катастрофічною нестабільністю: при зміні кількості серверів з `N` на `N + 1` частка ключів, які змінюють своє призначення, дорівнює:

```
P(Hash(Key) mod N ≠ Hash(Key) mod (N + 1))
= N / (N + 1)                                            [частка переміщених ключів]
≈ 1 - 1 / N                                              [при великих N прямує до 100%]
```

Зміна пулу з 100 до 101 сервера призводить до скидання 99% кешу та колапсу бекендів від шторму повторних обчислень (Cache Stampede).

У 1997 році Девід Каргер, Ерік Леман, Том Лейтон та ін. (David Karger et al.) запропонували концепцію **узгодженого хешування** (Consistent Hashing).

### Хеш-кільце та властивість мінімального збурення

Простір значень хеш-функції розглядається як неперервне кільце в інтервалі `[0, 2³² - 1]`. Кожен фізичний сервер відображається на одну або кілька точок на кільці за допомогою рівномірної хеш-функції `h(server_id)`. Ключ запиту (наприклад, `user_id`) також відображається на це кільце: `h(key)`. Запит направляється на перший сервер, чия точка на кільці розташована за годинниковою стрілкою після точки ключа:

```
Server(key) = argmin_{s ∈ Servers} { (h(s) - h(key)) mod 2³² }
```

При додаванні нового `(N + 1)`-го сервера на кільце він забирає лише той сегмент кільця, який раніше належав його сусіду за годинниковою стрілкою. Математичне сподівання частки ключів, що змінюють сервер, строго дорівнює теоретичному мінімуму:

```
Частка_переміщених_ключів
= 1 / (N + 1)                                            [мінімально можливе переміщення]
```

### Дисперсія довжини сегментів і віртуальні вузли (vnodes)

Якщо кожен фізичний сервер розміщує на кільці лише **одну** точку, довжини сегментів між сусідніми серверами розподілені нерівномірно. Точки випадково розбивають відрізок одиничної довжини на `N` частин. Згідно з теорією порядкових статистик експоненційного розподілу, довжина максимального сегмента складає:

```
E[L_max_segment]
= (ln(N) / N) · (1 + o(1))                               [максимальний інтервал між N точками]
```

Оскільки середній сегмент має довжину `1 / N`, найбільш завантажений сервер отримує у `ln(N)` разів більше трафіку, ніж середній (для 100 серверів — у 4.6 рази більше, для 1 000 — у 6.9 рази більше).

Для подолання цієї дисперсії вводять **віртуальні вузли** (Virtual Nodes, або vnodes): кожен фізичний сервер `S[i]` хешується `V` разів під різними іменами `h("S[i]-vnode-1")`, `h("S[i]-vnode-2")`, ..., `h("S[i]-vnode-V")`.

**Теорема про рівномірність із віртуальними вузлами:** для будь-якого фіксованого коефіцієнта дисперсії `ε > 0`, якщо кожен із `N` фізичних серверів має кількість віртуальних точок:

```
V ≥ (c · ln(N)) / ε²                                     [де c — універсальна константа]
```

тоді з імовірністю щонайменше `1 - 1/N` кожен фізичний сервер отримає частку ключів `P(S[i])`, обмежену вузьким діапазоном:

```
(1 - ε) / N ≤ P(S[i]) ≤ (1 + ε) / N                      [рівномірний розподіл навантаження]
```

На практиці для досягнення нерівномірності завантаження менше 5–10% (`ε = 0.05..0.10`) використовують значення `V = 100..256` віртуальних вузлів на один фізичний сервер. Це гарантує ідеальний баланс між пам'яттю індексу бінарного пошуку в масиві точок (`O(N · V)`) та захистом бекендів від утворення гарячих точок.

### Узгоджене хешування з обмеженим навантаженням (Consistent Hashing with Bounded Loads)

Класичне кільцеве хешування передбачає, що всі ключі мають однакову частоту звернень. Однак у реальних вебсервісах розподіл популярності ключів підпорядковується закону Ціпфа: один популярний ключ (наприклад, вірусне відео або товар на головній сторінці) може генерувати 30% усього світового трафіку.

У 2017 році дослідники Вахід Міррокні, Міккель Торуп та Мортеза Задімокаддам (Vahdid Mirrokni, Mikkel Thorup, Morteza Zadimoghaddam) запропонували алгоритм **Consistent Hashing with Bounded Loads**.

Кожному серверу задається жорстка максимальна місткість:

```
C = ceil[ (1 + ε) · (M / N) ]                             [де M — поточна кількість активних запитів]
```

Коли надходить ключ `k`, алгоритм знаходить первинний вузол `s = Server(k)` на кільці. Якщо поточне навантаження вузла `s` менше за поріг `C`, запит призначається йому. Якщо ж вузол `s` уже заповнений до межі `C`, балансувальник продовжує рух за годинниковою стрілкою по кільцю vnodes, доки не знайде перший вузол, чиє навантаження строго менше `C`.

Математично доведено, що цей алгоритм зберігає властивість мінімального переміщення ключів при зміні складу кластера, але одночасно гарантує, що жоден сервер за жодних обставин (навіть при катастрофічному сплеску запитів до одного гарячого ключа) не отримає навантаження більше ніж `(1 + ε)` від середнього по системі.

## Порівняння з табличним узгодженим хешуванням: Алгоритм Maglev

У кільцевому хешуванні Каргера пошук цільового сервера для ключа вимагає бінарного пошуку в масиві з `N · V` відсортованих точок, що має часову складність `O(log(N · V))`. При 1 000 серверах і 256 vnodes це становить близько 18 порівнянь цілих чисел у пам'яті на кожен запит.

У 2016 році компанія Google розробила алгоритм **Maglev Hashing**, який досягає константного часу вибору сервера `O(1)` за рахунок фіксованої таблиці розміром `M`, де `M` — велике просте число (типово `M = 65537` або `M = 655373`).

Кожен бекенд `i` генерує псевдовипадкову перестановку позицій у таблиці за двома незалежними хеш-функціями `offset` та `skip`:

```
offset[i] = Hash1(backend[i]) mod M
skip[i] = (Hash2(backend[i]) mod (M - 1)) + 1
Позиція[i, j] = (offset[i] + j · skip[i]) mod M
```

Всі `N` серверів по черзі (раунд за раундом `j = 0, 1, 2, ...`) заповнюють вільні клітинки таблиці `LookupTable[0 .. M - 1]`. Коли таблиця повністю заповнена, пошук вузла для клієнтського пакету зводиться до єдиного виклику:

```
Цільовий_сервер = LookupTable[ Hash(Packet_5tuple) mod M ]
```

Алгоритм Maglev забезпечує:
1. **Час пошуку O(1):** прямий доступ за індексом у масиві пам'яті без бінарного пошуку.
2. **Ідеальну рівномірність:** кожен вузол отримує рівно `M / N ± 1` слотів у таблиці (дисперсія менше `0.01%`).
3. **Мінімальне збурення:** при відмові одного сервера перерозподіляються лише його слоти (частка `1 / N`), а з'єднання до здорових серверів не порушуються.

Цей математичний апарат лежить в основі найшвидших сучасних мережевих балансувальників у ядрах Linux (eBPF Katran від Meta, Google Maglev, Cilium).
