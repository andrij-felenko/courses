# ⚙️ Розчепити запит із побічним ефектом: рефакторинг брудного коду в чесну пару команда+запит

Правило легко переказати одним реченням, а от відчути його на пальцях можна лише над справжнім кодом, який хтось уже зіпсував. Тому візьмемо не вигаданий приклад «для показу», а типовий модуль, який росте роками в будь-якому застосунку, — невеличкий сервіс сесій із аналітикою, — знайдемо в ньому три запити, що потайки міняють стан, і **власноруч** розчепимо кожен на чисту пару: команду, що змінює, і запит, що лише відповідає. Дорогою навчимося відрізняти справжній баг від того ефекту, який зовні непомітний і його можна лишити, а наприкінці впремося в найтонше — коли **гонитва** (англ. *race condition*) не просто дозволяє, а **вимагає** злити команду й запит в один атомарний виняток на кшталт `pop()` чи `incrementAndGet()`.

Весь код нижче — робочий TypeScript і Python, той самий приклад двома мовами вкладками. Дві версії — до й після — стоятимуть поряд, щоб зміну було видно не на словах, а в самих підписах методів.

## Пацієнт: сервіс сесій, який обріс ефектами

Уяви клас, що видає й обслуговує сесії користувачів. Народився він чистим — пара полів, кілька очевидних методів. Але за півроку в нього дописали лічильник звернень «для метрик», лінивий кеш конфігурації «щоб не читати з диска щоразу», журнал «щоб бачити, хто що питає». Кожен допис здавався дрібним і робився **всередині наявного get-методу**, бо навіщо плодити нові — ось же зручне місце. Ось цей клас, чесно доведений до стану, у якому такий код зазвичай і потрапляє на очі:

:::tabs
```ts
class SessionService {
  private hits = 0;                       // лічильник звернень «для метрик»
  private config: Config | null = null;   // лінивий кеш конфігурації
  private sessions = new Map<string, Session>();
  private readonly log: Logger;
  private readonly store: ConfigStore;

  constructor(log: Logger, store: ConfigStore) {
    this.log = log;
    this.store = store;
  }

  // «get» у назві — а всередині МІНЯЄ лічильник і ще й пише в журнал
  getSession(id: string): Session | undefined {
    this.hits += 1;                                  // ← прихована зміна
    this.log.info(`session lookup #${this.hits}: ${id}`); // ← ще ефект
    return this.sessions.get(id);
  }

  // теж «get» — а при першому виклику ЧИТАЄ з диска й КЕШУЄ
  getConfig(): Config {
    if (this.config === null) {
      this.config = this.store.load();               // ← прихована зміна
    }
    return this.config;
  }
}
```
```python
class SessionService:
    def __init__(self, log: Logger, store: ConfigStore) -> None:
        self._hits = 0                     # лічильник звернень «для метрик»
        self._config: Config | None = None # лінивий кеш конфігурації
        self._sessions: dict[str, Session] = {}
        self._log = log
        self._store = store

    # «get» у назві — а всередині МІНЯЄ лічильник і ще й пише в журнал
    def get_session(self, id: str) -> Session | None:
        self._hits += 1                                   # ← прихована зміна
        self._log.info(f"session lookup #{self._hits}: {id}")  # ← ще ефект
        return self._sessions.get(id)

    # теж «get» — а при першому виклику ЧИТАЄ з диска й КЕШУЄ
    def get_config(self) -> Config:
        if self._config is None:
            self._config = self._store.load()             # ← прихована зміна
        return self._config
```
:::

Два методи, обидва починаються на `get`, обидва обіцяють назвою «я лише питаю» — і обидва щось міняють. Але міняють вони по-різному, і в цій різниці вся сіль цієї вставки. `getSession` зсуває **спостережуваний** стан: лічильник `hits` — це число, яке хтось читає, тож кожен зайвий виклик псує метрику. `getConfig` теж міняє поле, але його ефект зовні **непомітний**: скільки не клич, віддається та сама конфігурація. Перший — справжній баг, що чекає на розчеплення. Другий — прийнятний виняток, і треба вміти довести, чому. Розберімо їх окремо, у порядку зростання підступності.

## Випадок 1: get-метод, що тихо лічить і логує

Почнемо з найяснішого — `getSession`. Назва каже «дай мені сесію за ідентифікатором»; це чистий запит за наміром. Але тіло робить три речі: інкрементує `hits`, пише рядок у журнал і лише потім повертає значення. Дві з них — зміна стану, замаскована під читання.

Щоб побачити, чому це кусається, не треба вигадувати екзотику — досить звичайного коду навколо, написаного людиною, яка **вірить назві**. Вона ж бачить `getSession` і резонно вважає його безпечним читанням, яке можна кликати вільно:

:::tabs
```ts
// Хтось перевіряє наявність, а потім бере значення — двічі «прочитав»:
if (service.getSession(id) !== undefined) {   // виклик №1
  const s = service.getSession(id);           // виклик №2 — те саме питання
  render(s);
}
// Наслідок: hits виріс на 2 за один логічний перегляд однієї сесії,
// а в журналі два рядки «lookup» там, де відбувся один перегляд.
```
```python
# Хтось перевіряє наявність, а потім бере значення — двічі «прочитав»:
if service.get_session(id) is not None:   # виклик №1
    s = service.get_session(id)           # виклик №2 — те саме питання
    render(s)
# Наслідок: hits виріс на 2 за один логічний перегляд однієї сесії,
# а в журналі два рядки «lookup» там, де відбувся один перегляд.
```
:::

Ось воно. Людина написала цілком розумний код — спершу спитала «чи є?», потім «дай» — і кожне з цих нешкідливих на вигляд читань тихо зсунуло метрику. `hits` тепер міряє не «скільки сесій переглянули», а «скільки разів десь у коді хтось торкнувся `getSession`», що взагалі не те число, яке хотіли. І ніхто не помітить: код не падає, тести на рендер зелені, метрика просто **бреше**, а причину шукатимуть місяцями. Це рівно та пастка з касиром і гривнею, тільки замість гаманця страждає дашборд.

**Ліки — механічні, і в цьому їхня краса.** Розчеплення такого методу не потребує кмітливості, лише дисципліни: витягни кожну зміну в окрему **команду**, а в запиті лиши тільки повернення. Крок за кроком це виглядає так.

Крок перший — назви ефекти поіменно. Усередині `getSession` живуть дві зміни (`hits += 1`, запис у журнал) і одне читання (`sessions.get`). Читання лишається в запиті; кожна зміна їде у свій метод.

Крок другий — витягни зміни у явні команди. Інкремент лічильника стає командою `recordSessionView` (назва каже, що вона робить: реєструє перегляд). Журналювання, якщо воно взагалі потрібне саме тут, теж стає окремою відповідальністю, а не безбілетником у запиті.

Крок третій — очисти запит. Тепер `getSession` робить рівно те, що обіцяє назвою: повертає сесію й нічого більше.

:::tabs
```ts
class SessionService {
  private hits = 0;
  private sessions = new Map<string, Session>();

  // ЗАПИТ: лише повертає, стан не чіпає. Клич скільки хоч.
  getSession(id: string): Session | undefined {
    return this.sessions.get(id);
  }

  // КОМАНДА: явно реєструє перегляд. Нічого не повертає.
  recordSessionView(id: string): void {
    this.hits += 1;
  }

  // ЗАПИТ на саму метрику — теж чистий.
  viewCount(): number {
    return this.hits;
  }
}
```
```python
class SessionService:
    def __init__(self) -> None:
        self._hits = 0
        self._sessions: dict[str, Session] = {}

    # ЗАПИТ: лише повертає, стан не чіпає. Клич скільки хоч.
    def get_session(self, id: str) -> Session | None:
        return self._sessions.get(id)

    # КОМАНДА: явно реєструє перегляд. Нічого не повертає.
    def record_session_view(self, id: str) -> None:
        self._hits += 1

    # ЗАПИТ на саму метрику — теж чистий.
    def view_count(self) -> int:
        return self._hits
```
:::

Тепер відповідальність за метрику переїхала туди, де їй місце, — до **викликача**, який єдиний знає, що саме є «переглядом». Той самий фрагмент, що раніше тихо накручував лічильник удвічі, тепер чесний: читання скільки завгодно безкоштовне, а зміна відбувається рівно там і рівно стільки разів, скільки поставив автор:

:::tabs
```ts
if (service.getSession(id) !== undefined) {  // читання — безкоштовне
  const s = service.getSession(id);          // ще читання — теж
  service.recordSessionView(id);             // ← зміна: свідомо, один раз
  render(s);
}
```
```python
if service.get_session(id) is not None:   # читання — безкоштовне
    s = service.get_session(id)           # ще читання — теж
    service.record_session_view(id)       # ← зміна: свідомо, один раз
    render(s)
```
:::

Дивись, що ми виграли. Раніше «скільки разів рахувати перегляд» вирішувало те, скільки разів код випадково торкнувся запиту, — тобто число визначалося формою чужого коду, а не наміром. Тепер його визначає рівно один явний виклик команди. Метрика знову означає те, що обіцяє. І ключове: запит `getSession` став тим, чим прикидався від початку, — його можна перевіряти в `if`, брати в тернарному операторі, обгортати логом на час діагностики, повторювати в циклі, — і жодна з цих дій більше нічого не ламає. Це та сама свобода читати спокійно, заради якої правило й існує.

> 🔧 **Навіщо це.** Найдешевший детектор цього класу помилок працює прямо в редакторі, без запуску: збіг очима **назви й тіла**. Метод зветься `get…`, `is…`, `find…`, `count…`, `calculate…` — тобто обіцяє відповідь без наслідків, — а всередині є присвоєння полю, `push`/`add` у колекцію, виклик `save`, `log`, `emit`, `++`? Це майже завжди прихована команда під маскою запиту, і майже завжди її треба розчепити тим самим механічним рухом: зміну — в окремий метод-команду, у запиті лишити голе повернення. Не треба чекати бага — його ще немає, поки метод кличуть рівно раз; але він **неминучий** тієї миті, коли хтось резонно повірить назві й покличе двічі.

## Випадок 2: лінивий кеш — коли ефект є, а бага немає

Тепер хитріше. `getConfig` теж міняє поле — при першому виклику присвоює `config` результат читання з диска. За буквою CQS це порушення: команда (записати поле) зрослася із запитом (повернути конфіг). Механічний детектор із попереднього випадку спрацював би й тут: назва `get`, а всередині присвоєння. То чи треба його розчіплювати так само?

**Ні. І вміти пояснити, чому саме ні, — важливіше за саме вміння розчіплювати.** Бо якщо сліпо розганяти кожне присвоєння в команду, код обросте безглуздими `initializeConfig()`, які нічого не дають, а лише перекладають на викликача турботу, що його не стосується.

Ключ — у різниці між **зміною стану** і **зміною спостережуваної відповіді**. Придивімося, що насправді бачить викликач `getConfig`:

:::tabs
```ts
const a = service.getConfig();   // перший виклик: читає з диска, кешує
const b = service.getConfig();   // другий: віддає кеш
const c = service.getConfig();   // третій: віддає кеш
// a, b, c — та сама конфігурація. Один і той самий об'єкт.
// Викликач НЕ БАЧИТЬ, що перший виклик щось робив, а решта — ні.
```
```python
a = service.get_config()   # перший виклик: читає з диска, кешує
b = service.get_config()   # другий: віддає кеш
c = service.get_config()   # третій: віддає кеш
# a, b, c — та сама конфігурація. Той самий об'єкт.
# Викликач НЕ БАЧИТЬ, що перший виклик щось робив, а решта — ні.
```
:::

Порівняй це з `getSession` до розчеплення. Там три виклики поспіль давали **різні** видимі наслідки: `hits` ставав 1, 2, 3, і хтось, хто читає цю метрику, бачив, як вона повзе. Тут три виклики дають **однакову** відповідь; ефект (заповнення кешу) стався один раз і сховався всередині так, що назовні його не намацати жодним читанням. Викликач не може відрізнити «сервіс, що кешує лінь» від «сервісу, що тримає конфіг у полі від народження». Різниця є в бітах пам'яті, але її **немає у спостережуваній поведінці**.

Ось де проходить справжня межа CQS — не «чи є присвоєння всередині», а «**чи зсуває виклик відповідь на наступний виклик**». Правило існує заради однієї практичної цінності: свободи переставляти, повторювати й кешувати запити, не боячись зіпсувати результат. Лінивий кеш цієї свободи **не забирає** — переставляй виклики `getConfig` як хоч, повторюй скільки хоч, результат той самий. Тому такий ефект прийнятний: він порушує букву правила, але шанує його дух.

Праворуч зіпсований getConfig(), що при кожному виклику домішує мітку часу: три виклики дають різні A1, A2, A3 — відповідь зсувається, це вже баг](/book/programming/software-design/command-query-separation/img/lazy-vs-buggy.svg)

*Той самий на вигляд «get», а різниця вирішальна. Ліворуч лінивий кеш: зміна сталася раз і сховалася — усі виклики бачать одне, свобода повторювати ціла, ефект прийнятний. Праворуч кеш, що підмішує стан у саму відповідь: кожен виклик зсуває результат — і це вже та прихована команда, яку треба розчепити.*

Щоб відчути межу на дотик, зіпсуймо `getConfig` навмисне — так, щоб він з прийнятного став справжнім багом. Досить, аби ефект **проступив** у відповідь. Хай метод при кожному виклику домішує в конфіг свіжу мітку часу «останнього доступу»:

:::tabs
```ts
// ЗІПСОВАНО: тепер кеш підмішує стан у саму відповідь.
getConfig(): Config {
  if (this.config === null) {
    this.config = this.store.load();
  }
  // ← ефект тепер ВИДИМИЙ: кожен виклик міняє те, що повертається
  this.config.lastAccess = Date.now();
  return this.config;
}
```
```python
# ЗІПСОВАНО: тепер кеш підмішує стан у саму відповідь.
def get_config(self) -> Config:
    if self._config is None:
        self._config = self._store.load()
    # ← ефект тепер ВИДИМИЙ: кожен виклик міняє те, що повертається
    self._config.last_access = now_ms()
    return self._config
```
:::

Одним рядком метод перескочив межу. Тепер три виклики поспіль дають конфіги з **різними** `lastAccess`, і код навколо, що порівнював дві «прочитані» конфігурації або кешував першу, раптом бачить, що вони не рівні. Ефект перестав ховатися — він тече в саму відповідь, — і ось тут детектор має кричати: це вже не лінива ініціалізація, це запит, що зсуває власний результат. Його треба розчепити рівно як `getSession`: читання доступу — окрема команда `touch()`, `getConfig` повертає незмінний конфіг.

Різниця між прийнятним і неприйнятним, отже, не в наявності зміни, а в її **видимості назовні**. Той самий критерій зустрічається під іншим ім'ям у понятті [ідемпотентності](book:programming/api-idempotency): виклик ідемпотентний, коли повторити його — те саме, що викликати раз, з погляду спостережуваного результату. Чистий запит — гранично ідемпотентний: скільки не повторюй, і стан, і відповідь ті самі. Лінивий кеш **не** ідемпотентний за станом (перший виклик міняє поле, решта — ні), але ідемпотентний за **відповіддю** (усі виклики повертають одне), і саме ця друга ідемпотентність — те, що CQS насправді обороняє.

> 🔧 **Навіщо це.** Перш ніж розчіплювати черговий «get» із присвоєнням усередині, постав методу одне питання: **чи побачить викликач різницю, якщо покличе його двічі поспіль?** Якщо друга відповідь відрізняється від першої — це прихована команда, розчіплюй. Якщо обидві відповіді однакові, а змінився лише невидимий кеш чи лінива ініціалізація — лиши як є, ти нічого не виграєш розчепленням, лише накинеш викликачеві турботу вручну ініціалізувати те, що чудово ініціалізується саме. Буква правила каже «жодних змін у запиті»; дух правила каже «жодних змін, які викликач **помітить**», — і в цьому конкретному місці слухайся духу.

## Випадок 3: коли гонитва вимагає злити назад — чесний атомарний виняток

Дотепер ми **розділяли** команду й запит, і це майже завжди правильно. Але є вузький клас випадків, де сумлінне розділення не просто зайве, а **шкідливе** — і диктує це не лінь, а найсуворіший із можливих суддів: одночасність. Розберімо його до дна, бо саме тут проходить остання, найтонша межа.

Вернімося до лічильника переглядів. Ми зробили `recordSessionView()` командою, `viewCount()` — запитом, і поодинці це бездоганно. Тепер уяви цілком реальну потребу: видати кожному переглядові свій **послідовний номер** — перший перегляд №1, другий №2, — щоб, скажімо, показувати «ви N-й відвідувач». Наївно це збирається з нашої чистої пари: спитати поточне число, потім збільшити.

:::tabs
```ts
// Наче чисто за CQS: спершу ЗАПИТ, потім КОМАНДА. Але…
const myNumber = service.viewCount();   // запит: читаю поточне
service.recordSessionView(id);          // команда: збільшую
// myNumber — «мій» номер відвідувача?
```
```python
# Наче чисто за CQS: спершу ЗАПИТ, потім КОМАНДА. Але…
my_number = service.view_count()    # запит: читаю поточне
service.record_session_view(id)     # команда: збільшую
# my_number — «мій» номер відвідувача?
```
:::

Однопотоково це працює бездоганно. А тепер пусти два запити одночасно — два перегляди, що прийшли в ту саму мілісекунду, у двох потоках сервера. Розгорнімо, що може статися між рядками:

```
hits = 5 на старті

потік A: viewCount() → читає 5
потік B: viewCount() → читає 5        ← обидва прочитали ОДНЕ число
потік A: recordSessionView() → hits = 6
потік B: recordSessionView() → hits = 7

Наслідок: A і B обидва вважають себе «5-м відвідувачем».
Номер 6 не дістався НІКОМУ. hits дійшов до 7 — а виданих
унікальних номерів лише два, і вони однакові.
```

Ось вона, **гонитва**: два потоки читають те саме значення до того, як бодай один устиг його змінити, і зміни затирають одна одну. Проблема не в тому, що ми порушили CQS, — навпаки, ми його **бездоганно дотримали**, розділивши читання й зміну на два окремі виклики. І саме цей чесний поділ **відкрив шпарину** між ними, у яку й прослизнув другий потік. Розділення тут працює **проти** нас.

Причина глибша за конкретний код: між двома окремими викликами — запитом і командою — завжди є мить, коли інший потік може втрутитися, бо це **два різні кроки**, а не один. Хоч як щільно ти їх постав у сусідніх рядках, між ними лишається щілина. Прибрати щілину можна лише одним способом: зробити «прочитати поточне **і** збільшити» **одним неподільним кроком**, який ніхто не може розірвати посередині, — тобто свідомо злити команду й запит назад в атомарний метод.

Саме для цього існують атомарні операції «прочитати-змінити-повернути». У Java це `AtomicInteger.incrementAndGet()` — він атомарно збільшує лічильник і повертає нове значення однією неподільною дією; усередині це цикл на апаратній операції **порівняти-і-замінити** (англ. *compare-and-swap*, CAS): прочитати поточне, обчислити наступне, спробувати записати за умови «якщо значення досі те, що я прочитав», а якщо хтось устиг вклинитися — повторити (це задокументована поведінка `incrementAndGet`, підтверджена специфікацією класу від Oracle). Ключове тут те, що читання й зміна **неподільні**: другий потік не може прочитати число посеред операції першого, бо серединки просто немає.

Ось той самий лічильник, переписаний чесним атомарним винятком. Зверни увагу: метод **навмисне** і повертає, і міняє — і це не недбалість, а єдиний спосіб закрити щілину:

:::tabs
```ts
// TS: атомарність будуємо на індивідуальному замку навколо
// неподільної секції (у Node немає вбудованого атомарного лічильника
// для звичайного числа — але ідея та сама: read-modify-write як ОДНЕ ціле).
class ViewCounter {
  private hits = 0;
  private readonly lock = new Mutex();

  // Чесний виняток: І міняє, І повертає — але НЕПОДІЛЬНО.
  async nextViewNumber(): Promise<number> {
    return this.lock.runExclusive(() => {
      this.hits += 1;      // зміна
      return this.hits;    // і повернення — між ними ніхто не влізе
    });
  }
}
```
```python
import threading

class ViewCounter:
    def __init__(self) -> None:
        self._hits = 0
        self._lock = threading.Lock()

    # Чесний виняток: І міняє, І повертає — але НЕПОДІЛЬНО.
    def next_view_number(self) -> int:
        with self._lock:        # секцію не розірве інший потік
            self._hits += 1     # зміна
            return self._hits   # і повернення разом — атомарно
```
:::

Тепер два одночасні перегляди дістануть **різні** номери — 6 і 7, — і жоден номер не пропаде, бо неможливо прослизнути між читанням і зміною: вони склеєні в одну операцію. Ми свідомо порушили CQS — але порушили **чесно**: назва `nextViewNumber` не бреше, вона прямо каже «дай наступний номер», тобто відкрито обіцяє й зміну (наступний — значить, лічильник посунувся), і повернення. Ніхто не сплутає її з безневинним `viewCount()`, який лише дивиться.

Той самий візерунок — усюди, де читання й зняття мусять бути неподільні. Класичний `pop()` у стека чи черги: він знімає верхній елемент (команда) **і** повертає його (запит) однією дією саме тому, що розділена пара `top()` + `pop()` відкрила б гонитву — між «подивитися верхній» і «зняти» інший потік устиг би зняти те, що ти щойно бачив, і ти зняв би не те. У Python, до речі, `list.pop()` на кінці списку атомарний уже завдяки глобальному блокуванню інтерпретатора (GIL) — а от складена перевірка «якщо не порожньо — зняти» вже **не** атомарна й потребує явного замка (це підтверджено документацією Python щодо потокобезпеки: одинична `pop()` безпечна, а `if lst: lst.pop()` — ні):

:::tabs
```ts
// pop() чесно поєднує: знімає (команда) І віддає знятий (запит) —
// одним рухом, щоб між «подивитися» і «зняти» ніхто не вклинився.
class Stack<T> {
  private items: T[] = [];
  push(x: T): void { this.items.push(x); }   // чиста команда
  // порушує CQS СВІДОМО і ЧЕСНО — назва не прикидається читанням
  pop(): T | undefined { return this.items.pop(); }
}
```
```python
# Одинична pop() атомарна під GIL — знімає І віддає неподільно.
# Але складена «перевір-і-зніми» вже НЕ атомарна: потрібен замок.
lock = threading.Lock()

def safe_pop(lst: list) -> object | None:
    with lock:                    # інакше два потоки пройдуть перевірку
        if lst:                   # і обидва спробують pop() з порожнього
            return lst.pop()
        return None
```
:::

Як же відрізнити цей чесний виняток від прихованого бага з випадку 1? Тим самим питанням про **чесність підпису**, тільки тепер із додатковим «навіщо». `nextViewNumber`, `pop`, `incrementAndGet` поєднують команду й запит — але поєднання **видно з назви** й воно потрібне для **неподільності**: розділиш — відкриєш гонитву. `getSession`, що тихо лічить, теж поєднував команду й запит — але поєднання було **сховане** за назвою-запитом, а неподільність нікому не була потрібна; там розділення шпарини не відкривало, лише прибирало брехню. Ось повний критерій межі:

```
Поєднувати команду й запит в один метод ЧЕСНО, коли:
  1) поєднання ВИДНО з назви (pop, next, incrementAndGet, take)
  2) воно потрібне для АТОМАРНОСТІ — розділення відкрило б гонитву
Розділяти ОБОВ'ЯЗКОВО, коли:
  • назва обіцяє запит (get, is, find, count), а тіло тихо міняє
  • атомарність тут ні до чого — зміна просто прокралася в читання
```

Ось чому наївне «завжди розділяй команду й запит» — напівправда. Розділення — стандарт, правильний у переважній більшості місць, і саме його ми застосували у випадках 1 і 2. Але там, де читання й зміна мусять статися неподільно під тиском одночасності, чесніше й безпечніше злити їх у видимий з назви атомарний метод, ніж дотримати букву правила ціною гонитви. Глибше про сам механізм — чому «прочитати-змінити-записати» без атомарності рветься й що таке та неподільна секція — розібрано в темі про [атомарність і гонки](book:programming/atomicity-races); апаратний бік compare-and-swap і порядок пам'яті, на яких стоять `incrementAndGet` та подібні, — у темі про [std::atomic і порядок пам'яті](book:programming/std-atomic).

## Складність і пастки: що легко зробити не так

Три випадки пройдено; лишається зібрати граблі, на які найлегше наступити під час такого рефакторингу, бо кожен із них перетворює правильну ідею на нову проблему.

**Пастка перша: розчепити те, що чіпати не варто.** Найчастіша помилка новонаверненого — побачити присвоєння в кожному `get` і кинутися розганяти всі підряд у команди, зокрема ліниві кеші з випадку 2. Результат — рій порожніх `initializeX()`, `ensureLoaded()`, які викликач мусить пам'ятати кликати вручну, хоча ефект їхній зовні непомітний. Критерій один і його варто вивчити напам'ять: розчіпляй, лише коли **другий виклик поспіль дає іншу відповідь**. Невидима зміна — не твоя ціль.

**Пастка друга: команда, що потайки повертає «заодно».** Розчепивши запит, легко за інерцією зробити команду, яка **теж** повертає щось «корисне» — новий стан, старе значення, прапорець успіху. І ось ти знову збудував гібрид, тільки з іншого боку: тепер уже команда спокушає читати стан через дію. `recordSessionView` має повертати `void`, а не «новий лічильник»; хто хоче число — хай окремо спитає `viewCount()`. Виняток — лише той самий чесний атомарний випадок 3, де повернення з команди свідоме й видиме з назви.

**Пастка третя: сплутати «непомітно зараз» із «непомітно завжди».** Лінивий кеш прийнятний, поки його ефект справді невидимий. Але варто комусь дописати в конфіг мітку часу доступу, лічильник читань чи будь-що, що тече у відповідь, — і вчорашній прийнятний виняток стає сьогоднішнім багом, як ми бачили в зіпсованій версії `getConfig`. Тому лишаючи лінивий ефект, лишай і **коментар-застереження**: цей кеш дозволений рівно доти, доки нічого спостережуваного в нього не домішано. Наступний, хто торкнеться методу, має знати, яку саме межу не можна переступати.

**Пастка четверта: замок не там, де щілина.** У випадку 3 легко поставити атомарність не навколо тієї ділянки. Обгорнути замком окремо `viewCount()` і окремо `recordSessionView()` — марно: кожен виклик стане атомарним сам по собі, а **щілина між ними** лишиться відкритою, бо це два різні входи в замок. Неподільним має бути саме «прочитати **і** збільшити» як **одне ціле** — один вхід у замок на обидві дії, — інакше гонитва повертається тихцем, і виглядатиме код при цьому «захищеним».

**Пастка п'ята: атомарність там, де її не просили.** Дзеркальна крайність — обвішати замками й атомарними лічильниками код, який зроду однопотоковий. Атомарний виняток із випадку 3 виправданий **лише** під реальним тиском одночасності; у суто послідовному коді проста чиста пара команда+запит краща в усьому — простіша, швидша, чесніша, — і городити навколо неї неподільні секції означає платити за захист від загрози, якої немає. Спершу переконайся, що гонитва справді можлива, а вже потім злютовуй атомарний виняток; інакше це просто зайва складність, а не гнучкість. Не вгадуй, чи є в тебе одночасність, — знай напевно.

Спосіб тримати все це в голові один-єдиний. Дивлячись на метод із назвою-запитом, постав дві короткі перевірки поспіль. Перша: **чи побачить викликач різницю від повторного виклику?** Якщо ні — це або чистий запит, або прийнятний невидимий кеш, не чіпай. Якщо так — усередині ховається команда, і за замовчуванням її треба **витягти** в окремий явний метод, лишивши запит голим. І лише одна причина скасовує це «витягти» — друга перевірка: **чи вимагає одночасність, щоб читання і зміна були неподільні?** Якщо так — не розділяй, а навпаки, злютуй їх у видимий з назви атомарний виняток на кшталт `pop()` чи `incrementAndGet()`. Розділення — стандарт; чесне злиття під гонитву — рідкісний, але законний виняток; а прихована зміна під маскою запиту — завжди помилка. Уся дисципліна CQS на щодень уміщається в ці три речення.
