# ⚙️ Чотири запахи в прошивці й точний рух проти кожного

Драбини зв'язності й зчеплення дають імена — але імена лежать мертвим вантажем, поки ти не побачив, як конкретний запах виглядає в живому коді й **який саме рух** його прибирає. Тут ми беремо шматок цілком реальної прошивки — драйвер давача температури на I²C, логер на SD-картку, обробник кадрів телеметрії — і проходимо чотирма запахами по черзі. Для кожного: код **до**, крок правки, код **після** — і головний замір, заради якого все й затіяне: **скільки місць чіпає типова зміна** до й після. Цей замір я називатиму **хвилею правки** — скільки файлів, функцій, рядків доведеться торкнути, щоб провести одну звичайну вимогу крізь код.

Хвиля — не метафора для краси. Це те єдине, що зчеплення й зв'язність насправді міряють: коли зміна локальна, ти чіпаєш одне місце й спиш спокійно; коли зміна розповзається, ти чіпаєш сім, забуваєш восьме, і воно стріляє в польових умовах через місяць. У Фаулера цей самий симптом — «одна зміна б'є по багатьох класах» — має власне ім'я, **дробовик по хірургії (англ. *shotgun surgery*)**: одне влучення, картеч розлітається, і латати доводиться скрізь. Мета кожного руху нижче — звести хвилю з багатьох до одного. *(Це усталений термін із «Refactoring» Фаулера, 1999; статус — канон дисципліни.)*

Одразу застереження, яке проведемо наскрізь: **рефакторинг не завжди окупається**. У самому кінці — розділ про те, де хвиля вже мала (один-два дотики), і тоді введений заради «чистоти» інтерфейс лише додає коду, не прибравши болю. Прошивка це загострює: тут абстракція коштує не лише читабельності, а й тактів та байтів флешу, яких на мікроконтролері рахована кількість.

## Запах 1: клас-звалище `Utils` — випадкова зв'язність

**Задача.** У проєкті завівся `SensorUtils` — тека, куди пів року складали все, що «дотичне до давачів і не мало іншого дому». Спершу дві функції, тепер одинадцять. Кожен програміст, якому не було куди подіти хелпер, доклав свій. Тепер це виглядає так:

:::tabs
```cpp
// SensorUtils: звалище. Що спільного? Слово "sensor" у назві файлу — і все.
class SensorUtils {
public:
    static float   celsiusFromRaw(uint16_t raw);      // математика перетворення
    static uint8_t crc8(const uint8_t* d, size_t n);  // контрольна сума I²C
    static void    logReading(float t);               // запис у кільцевий буфер
    static bool    isPlausible(float t);              // перевірка діапазону
    static uint32_t millisSinceBoot();                // обгортка над таймером
    static void    blinkError(uint8_t code);          // блимання світлодіодом
    // …ще п'ять таких самих різнорідних
};
```
```python
# SensorUtils: звалище. Що спільного? Слово "sensor" у назві файлу — і все.
class SensorUtils:
    @staticmethod
    def celsius_from_raw(raw: int) -> float: ...      # математика перетворення
    @staticmethod
    def crc8(data: bytes) -> int: ...                 # контрольна сума I²C
    @staticmethod
    def log_reading(t: float) -> None: ...            # запис у кільцевий буфер
    @staticmethod
    def is_plausible(t: float) -> bool: ...           # перевірка діапазону
    @staticmethod
    def millis_since_boot() -> int: ...               # обгортка над таймером
    @staticmethod
    def blink_error(code: int) -> None: ...           # блимання світлодіодом
    # …ще п'ять таких самих різнорідних
```
:::

**Ідея.** Випадкова зв'язність (найнижчий щабель) означає, що речі складено докупи **без причини** — назва файлу не причина. Рух проти неї один: **розкласти за причиною зміни**. Не «за темою», не «за схожістю» — саме за тим, **що змусить це поле правити**. Функції, що змінюються з однієї причини, ідуть в один дім; що з різних — у різні. Ось де живе справжня причина кожного шматка:

- `celsiusFromRaw`, `isPlausible` — правляться, коли **міняється давач** (нова модель, інша формула, інший діапазон). Це знання про конкретний давач.
- `crc8` — правиться, коли **міняється протокол шини**. Це знання про I²C-обмін, не про температуру.
- `logReading` — правиться, коли **міняється формат чи місце логу**.
- `blinkError`, `millisSinceBoot` — це платформа, спільна для всієї прошивки.

**Крок правки.** Розтягуємо звалище за цими причинами. Кожна купка стає класом із власним іменем, що каже, **чому** він існує:

:::tabs
```cpp
// Дім для знання про конкретний давач — правиться при зміні давача
class Tmp117 {
public:
    static float celsius(uint16_t raw) { return raw * 0.0078125f; }  // 7.8125 м°C/LSB
    static bool  plausible(float c)    { return c > -40.0f && c < 125.0f; }
};

// Дім для знання про шину — правиться при зміні протоколу
class I2cFrame {
public:
    static uint8_t crc8(const uint8_t* d, size_t n);  // поліном 0x07, як у SMBus
};

// Дім для логу — правиться при зміні формату/носія
class ReadingLog {
public:
    void append(float celsius);
};
```
```python
# Дім для знання про конкретний давач — правиться при зміні давача
class Tmp117:
    @staticmethod
    def celsius(raw: int) -> float:
        return raw * 0.0078125          # 7.8125 м°C/LSB
    @staticmethod
    def plausible(c: float) -> bool:
        return -40.0 < c < 125.0

# Дім для знання про шину — правиться при зміні протоколу
class I2cFrame:
    @staticmethod
    def crc8(data: bytes) -> int: ...   # поліном 0x07, як у SMBus

# Дім для логу — правиться при зміні формату/носія
class ReadingLog:
    def append(self, celsius: float) -> None: ...
```
:::

`blinkError`/`millisSinceBoot` переїжджають у платформний `Board` — вони не про давач узагалі.

**Код після — точка виклику.** Тепер драйвер читає давач через ясні імена, і кожен виклик каже, з якого світу дані:

```cpp
void SensorTask::poll() {
    uint8_t raw[2];
    if (!i2c_.read(TMP117_ADDR, TMP117_REG_TEMP, raw, 2)) return;
    if (I2cFrame::crc8(raw, 2) != expectedCrc_) { crcErrors_++; return; }

    float t = Tmp117::celsius((raw[0] << 8) | raw[1]);
    if (Tmp117::plausible(t)) log_.append(t);
}
```

**Хвиля правки.** Порахуймо на конкретній вимозі: **«переходимо з давача TMP117 на SHT30» (інша формула, інший діапазон, інша адреса).**

```
ДО (звалище SensorUtils):
  правити celsiusFromRaw       — так, це давач
  правити isPlausible          — так, це давач
  перечитати crc8              — а це чіпати? (ні, але треба переконатися)
  перечитати logReading        — а це? (ні)
  …прочитати весь клас, бо не видно, що давач, а що ні
  хвиля: 2 правки + ревізія 9 чужих методів у пошуку «чи не зачепив»

ПІСЛЯ (розкладено за причиною):
  замінити Tmp117 на Sht30     — один файл, дім давача
  хвиля: 1 файл, і жоден чужий метод перечитувати не треба
```

Виграш тут не в двох правках проти двох — він у тому, що в «після» **очевидно, куди дивитися й де зупинитися**. Звалище краде час не стільки правками, скільки страхом: ти не знаєш, що з одинадцяти методів зачепить твоя зміна, тож читаєш усі. Дім із чесною назвою відповідає на це питання самою назвою.

> 🔧 **Навіщо це.** У прошивці зміна давача — не рідкість, а норма: постачальник зняв чип із виробництва, закупівля знайшла дешевший, ревізія плати поставила інший. Якщо знання про давач розмазане по `Utils`, кожна така заміна — археологія. Якщо воно в класі `Tmp117`, заміна — це новий клас `Sht30` поруч і один рядок у точці створення. Різниця між тижнем і годиною.

Один нюанс, щоб не перегнути. Розкладати треба **за реальними, а не уявними** причинами. Якщо `crc8` у твоєму проєкті ніколи не житиме окремо від цього єдиного давача й іншої шини не передбачається — витягати його в окремий `I2cFrame` передчасно (див. останній розділ). Причина зміни має бути **правдоподібною**, а не теоретично можливою.

## Запах 2: передача цілого об'єкта заради двох полів — зчеплення за зліпком

**Задача.** Функція калібрування бере поправку й пише її в лог. Хтось колись передав їй увесь об'єкт `Reading` — «щоб було під рукою», — і відтоді вона знає про всю його форму:

:::tabs
```cpp
struct Reading {
    float    celsius;
    uint16_t raw;
    uint32_t timestamp;
    uint8_t  sensorId;
    uint8_t  crc;
    int8_t   rssi;       // сила сигналу, якщо давач бездротовий
    // …структура росте, її чіпають з десятка причин
};

// Зчеплення за зліпком: бере всю структуру, використовує ДВА поля
float applyCalibration(const Reading& r, const CalTable& tbl) {
    float offset = tbl.lookup(r.sensorId);   // потрібне поле 1
    return r.celsius + offset;               // потрібне поле 2
    // решта Reading тут не використана — але функція від неї залежить
}
```
```python
@dataclass
class Reading:
    celsius: float
    raw: int
    timestamp: int
    sensor_id: int
    crc: int
    rssi: int           # сила сигналу, якщо давач бездротовий
    # …структура росте, її чіпають з десятка причин

# Зчеплення за зліпком: бере всю структуру, використовує ДВА поля
def apply_calibration(r: Reading, tbl: CalTable) -> float:
    offset = tbl.lookup(r.sensor_id)         # потрібне поле 1
    return r.celsius + offset                # потрібне поле 2
    # решта Reading тут не використана — але функція від неї залежить
```
:::

**Ідея.** Зчеплення за зліпком (**stamp**) означає: модулю передали **цілу складену структуру**, а йому потрібні лічені поля. Тепер він зайво знає про всю форму `Reading` — і кожна зміна цієї форми потенційно тягнеться до нього, хоч по суті не стосується. Рух проти: **передавати рівно потрібне** — ті два скалярні параметри, і нічого більше. Функція перестає залежати від структури, від якої не залежить її логіка.

**Крок правки.** Звужуємо сигнатуру до справжніх потреб:

:::tabs
```cpp
// За даними: рівно те, що використано. Про Reading функція більше не знає.
float applyCalibration(float celsius, uint8_t sensorId, const CalTable& tbl) {
    return celsius + tbl.lookup(sensorId);
}
```
```python
# За даними: рівно те, що використано. Про Reading функція більше не знає.
def apply_calibration(celsius: float, sensor_id: int, tbl: CalTable) -> float:
    return celsius + tbl.lookup(sensor_id)
```
:::

Точка виклику розпаковує потрібне сама — і робить це видимим:

:::tabs
```cpp
r.celsius = applyCalibration(r.celsius, r.sensorId, calTable_);
```
```python
r.celsius = apply_calibration(r.celsius, r.sensor_id, cal_table)
```
:::

**Хвиля правки.** Вимога: **«додаємо в `Reading` поле `humidity` й прибираємо застаріле `rssi`».**

```
ДО (передавали весь Reading):
  applyCalibration бере const Reading&  → перекомпілювати, перевірити,
      чи зміна форми структури нічого їй не зламала
  так само кожна з ~8 функцій, яким «про всяк випадок» дали весь Reading
  хвиля: ревізія 8 сигнатур на дотик до полів, що змінилися

ПІСЛЯ (передаємо два скаляри):
  applyCalibration(float, uint8_t, …)   → форма Reading їй байдужа,
      її не треба ні чіпати, ні перечитувати
  хвиля: 0 дотиків до функцій, що беруть лише скаляри
```

Тут виграш прямий: функція, що бере `float` і `uint8_t`, **фізично не може** постраждати від додавання поля `humidity` — вона його не бачить. Зчеплення за зліпком робить структуру `Reading` **центром тяжіння**: усе, кому її передали, стає її заручником. Звузивши параметри, ти розриваєш цей зв'язок у корені.

Є й тонша користь, невидима в хвилі, але важлива: **сигнатура тепер каже правду**. `applyCalibration(float, uint8_t, …)` чесно оголошує «мені треба температура й id» — читач бачить залежність, не відкриваючи тіло. `applyCalibration(const Reading&, …)` бреше, що їй потрібен увесь `Reading`, і читач мусить лізти всередину, щоб дізнатися, що насправді — два поля.

**Де межа.** Якщо функції потрібні **п'ять** полів із семи — тягнути п'ять скалярів гірше, ніж один об'єкт: сигнатура роздувається, порядок аргументів стає пасткою (`float, uint8_t, uint32_t, uint8_t, int8_t` — переплутати легко). Тоді правильний рух інший: або лишити структуру, або **виділити меншу** структуру, що є справжнім зліпком саме цих даних (напр., `CalInput{celsius, sensorId}`). Правило не «ніколи не передавай структур», а «не передавай **більшої**, ніж треба».

## Запах 3: параметр-прапорець `mode` — керівне зчеплення

**Задача.** Функція запису на SD-картку вміє два режими: швидкий (буферизований, для звичайного логу) і надійний (з негайним `flush` і перевіркою, для критичних подій). Обидва впхнули в одну функцію, а вибір — булевим прапорцем:

```cpp
// Керівне зчеплення: bool керує тим, ЯКОЮ функція буде всередині
bool writeRecord(const uint8_t* data, size_t len, bool durable) {
    file_.write(data, len);
    if (durable) {
        file_.sync();                    // змусити контролер картки скинути кеш
        return verifyLastWrite(data, len);   // перечитати й звірити
    }
    return true;                         // швидкий шлях: довіряємо буферу
}
```

**Ідея.** Керівне зчеплення (**control**) — це коли клієнт передає не дані, а **команду**, що керує гілкою чужої поведінки. `durable` не описує запис — він **наказує** функції бути іншою. Виклик `writeRecord(buf, n, true)` у місці виклику нічого не пояснює: щоб зрозуміти, що станеться, треба піти в тіло й вивчити, що вмикає `true`. Рух проти: **розділити на дві функції**, кожна з ясним іменем, і хай точка виклику сама каже, чого хоче.

**Крок правки.** Розчеплюємо гілки. Спільний шматок (сам `write`) лишається приватним, дві публічні функції беруть кожна свій шлях:

```cpp
private:
    bool rawWrite(const uint8_t* data, size_t len) {   // спільне ядро
        return file_.write(data, len) == len;
    }
public:
    // Швидкий шлях — ім'я каже саме за себе
    bool logRecord(const uint8_t* data, size_t len) {
        return rawWrite(data, len);
    }
    // Надійний шлях — окрема функція, окрема гарантія
    bool commitRecord(const uint8_t* data, size_t len) {
        if (!rawWrite(data, len)) return false;
        file_.sync();
        return verifyLastWrite(data, len);
    }
```

**Код після — точка виклику.** Тепер намір видно без стрибка в реалізацію:

```cpp
logRecord(telemetry, tlen);      // рутинна телеметрія — швидко
commitRecord(alarm, alen);       // подія тривоги — надійно, звірено
```

**Хвиля правки.** Вимога: **«додаємо третій режим — запис зі стисненням для довгого архіву».**

```
ДО (прапорець durable):
  bool уже не вистачає — треба enum Mode{Fast, Durable, Compressed}
  правити сигнатуру writeRecord у КОЖНІЙ із ~15 точок виклику
      (bool→enum: старі виклики writeRecord(…, true) не компілюються)
  додати третю гілку в тіло, стежачи, щоб не зламати дві наявні
  хвиля: 1 тіло + 15 точок виклику + ризик у двох старих гілках

ПІСЛЯ (дві окремі функції):
  додати третю функцію archiveRecord() поруч — нову, самостійну
  наявні logRecord/commitRecord не чіпати
  хвиля: +1 нова функція, 0 правок у наявних викликах
```

Ось де керівне зчеплення показує зуби: прапорець **не масштабується**. Один `bool` вроді безневинний, але щойно режимів стає три, він мутує в `enum`, і кожна стара точка виклику ламається на зміні типу. Дві (чи три) окремі функції ростуть **додаванням**, а не переписуванням: нова поведінка — новий дім, старі стоять недоторкані. Це та сама відкритість до розширення, яку в принципах формулюють окремо — код відкритий для нового, закритий для правок наявного.

> 🔧 **Навіщо це.** Прапорець-режим підступний тим, що видно його лише в сигнатурі, і на код-рев'ю легко пропустити. Правило-детектор просте: **якщо всередині функції прапорець розгалужується на два несумісні шляхи, де майже нема спільного коду, — це дві функції, склеєні в одну**. Якщо ж гілки ділять 90% тіла й різняться одним рядком — можливо, прапорець доречний (див. нижче). Ріж там, де шляхи справді розходяться.

**Де НЕ різати.** Якщо `durable` вмикав би не окрему поведінку, а один рядок у спільному потоці — скажімо, просто додатковий `sync()` наприкінці того самого коду, — розділення на дві майже однакові функції породило б **дублювання**: 95% тіла скопійовано двічі. Тоді прапорець чесніший за дві копії. Керівне зчеплення шкідливе, коли гілки **несумісні**; коли вони — та сама робота з дрібною відмінністю, прапорець (або окремий крихітний метод `sync()`, який клієнт кличе сам) кращий за клонування.

## Запах 4: спільна глобальна змінна — спільне зчеплення

**Задача.** Стан радіоканалу тримають у глобальній змінній, бо «до неї треба з багатьох місць»: обробник переривань пише туди RSSI, задача телеметрії читає, веб-конфіг скидає лічильники.

```cpp
// Спільне зчеплення: глобал, у який пише і читає будь-хто, будь-коли
volatile int  g_rssi        = 0;
volatile bool g_linkUp      = false;
uint32_t      g_packetsLost = 0;

// у перериванні радіо:
void radio_isr() { g_rssi = readRssi(); g_linkUp = (g_rssi > -90); }
// у задачі телеметрії:
void telemetryTask() { if (g_linkUp) send(g_rssi); }
// у веб-конфізі:
void onReset() { g_packetsLost = 0; g_linkUp = false; }  // хто ще це бачить?
```

**Ідея.** Спільне зчеплення (**common**) — модулі спілкуються через **спільну змінну, яку кожен може мовчки змінити**. Проблем тут дві, і обидві злі. Перша: **ніхто не володіє інваріантом**. `g_linkUp` мав би означати `g_rssi > -90`, але `onReset` виставляє `g_linkUp = false`, не чіпаючи `g_rssi`, — і тепер вони суперечать одне одному. Друга, специфічна для прошивки: **гонитва**. `radio_isr` пише `g_rssi` посеред того, як `telemetryTask` його читає; на 8/16-бітному ядрі 32-бітне читання неатомарне, і задача може вхопити половину старого, половину нового значення.

Рух проти: **інкапсулювати за аксесором** — сховати змінні за об'єктом, що єдиний ними володіє, а доступ дати через методи. Тоді інваріант тримається в одному місці, а критичну секцію можна закрити там само, де живуть дані.

**Крок правки.** Обгортаємо стан у клас `LinkStatus`. Пряме поле стає приватним; читання й запис — через методи, де інваріант і захист зібрані докупи:

```cpp
class LinkStatus {
public:
    // Запис — лише звідси; інваріант linkUp ⟺ rssi>поріг тримається тут
    void updateRssi(int rssi) {
        CriticalSection cs;           // закрили переривання на час запису
        rssi_   = rssi;
        linkUp_ = (rssi > RSSI_THRESHOLD);
    }
    void reset() {
        CriticalSection cs;
        packetsLost_ = 0;
        linkUp_      = false;
        rssi_        = RSSI_FLOOR;    // і rssi узгоджуємо — не лишаємо брехати
    }
    // Читання — атомарний зліпок, щоб не вхопити півзначення
    struct Snapshot { int rssi; bool up; uint32_t lost; };
    Snapshot read() const {
        CriticalSection cs;
        return { rssi_, linkUp_, packetsLost_ };
    }
private:
    static constexpr int RSSI_THRESHOLD = -90;
    static constexpr int RSSI_FLOOR     = -128;
    volatile int      rssi_        = RSSI_FLOOR;
    volatile bool     linkUp_      = false;
    volatile uint32_t packetsLost_ = 0;
};

LinkStatus g_link;   // один екземпляр — але доступ лише через його методи
```

Тепер клієнти не торкаються полів:

```cpp
void radio_isr()      { g_link.updateRssi(readRssi()); }
void telemetryTask()  { auto s = g_link.read(); if (s.up) send(s.rssi); }
void onReset()        { g_link.reset(); }
```

**Хвиля правки.** Вимога: **«поріг зв'язку залежить від режиму — у дальньому режимі опустити з −90 до −100 dBm».**

```
ДО (голі глобали):
  знайти КОЖНЕ місце, де рахують g_linkUp = (g_rssi > -90)
      — а це радіо-ISR, ще й дубль у діагностиці, ще й у тесті зв'язку
  правити поріг у кожному (легко забути один → лінк «стрибає»)
  а гонитву як була, так і лишили — окрема прихована біда
  хвиля: 3 місця з магічним -90, і одне точно забудеш

ПІСЛЯ (інкапсульовано):
  поріг живе в одному updateRssi (одна константа/параметр)
  правиш одну функцію — інваріант перерахується скрізь однаково
  хвиля: 1 місце; гонитва вже закрита CriticalSection
```

Спільне зчеплення тим і підступне, що **правило розмазане по всіх, хто чіпав змінну**. Поки `g_linkUp` рахували в трьох місцях, «що таке живий лінк» не мало єдиного визначення — воно існувало в трьох копіях, які легко розходяться. Аксесор стягує правило в **одну** функцію: тепер «живий лінк» означає рівно те, що каже `updateRssi`, і ніхто інший цього не перевизначає. А critical-section, який раніше нікуди було приткнути (глобал не має «свого» місця для захисту), тепер природно лягає туди, де живуть дані.

> 🔧 **Навіщо це.** Глобальний стан у прошивці — не просто «поганий стиль», це **джерело плаваючих багів**, які не ловляться в лабораторії й вилазять у полі: гонитва ISR із задачею, розсинхрон інваріанта після скидання, неможливість написати тест (глобал тягне за собою півсистеми). Інкапсуляція за аксесором лікує всі три разом — володіння, атомарність, тестованість — коштом одного класу-обгортки.

## Ціна: де рефакторинг НЕ окупається

Тепер чесно про зворотний бік, бо без нього все вище перетворюється на догму «завжди розчіплюй». **Кожен із цих рухів має ціну, і буває, що ціна більша за виграш.** Три випадки, де правильна відповідь — **не чіпати**.

**Хвиля вже дорівнює одиниці.** Уся арифметика вище тримається на тому, що зміна **розповзається**. Якщо `celsiusFromRaw` викликають з **одного** місця й давач у цьому пристрої **ніколи не зміниться** (він упаяний, ревізій плати не планують), то виносити його в клас `Tmp117` — робота без віддачі: хвиля була 1 і лишилась 1, а коду побільшало. Рефакторинг проти запаху окупається рівно тоді, коли запах **справді болить хвилею**; на коді, який чіпають раз на рік в одному місці, «чистота» — це витрачені години, яких ніхто не поверне. Спитай не «чи це запах за підручником», а «**скільки місць чіпає реальна зміна тут**» — якщо одне, лиши як є.

**Абстракція наперед — це YAGNI навпаки.** Витягти `I2cFrame::crc8` заради «а раптом буде друга шина» — заплатити зчепленням-послабленням за майбутнє, яке може не настати. Поки шина одна, окремий клас `I2cFrame` — це зайвий файл, зайвий рівень непрямості й ілюзія гнучкості, якою ніхто не скористається. Абстракцію став тоді, коли **друга** реалізація вже стукає у двері, а не «про всяк випадок». Передчасне узагальнення дорожче за дублювання, яке ти прибереш, коли (і якщо) воно справді заболить. Це прямо [YAGNI](book:programming/dry-kiss-yagni): не абстрагуй наперед того, чого ще не потребуєш.

**Непрямість коштує тактів і байтів — а на МК їх рахують.** Це специфічно для прошивки й часто вирішальне. Розділення на дві функції зазвичай безкоштовне (компілятор вбудує). Але коли «послаблення зчеплення» веде до **віртуального виклику** — інтерфейс давача з `virtual float celsius() = 0`, щоб «підставляти будь-який давач», — ти платиш непрямим стрибком через таблицю віртуальних методів на **кожному** зчитуванні, плюс vtable у флеші, плюс втрачений inline. У гарячому циклі опитування на 8 МГц ядрі це може бути різниця між «встигаємо» і «ні». Якщо давач у продукті рівно один, віртуальний інтерфейс — заплачена ціна за поліморфізм, якого нема. Тут правильний рух — **статичне** розділення (окремі класи, шаблон, тег-тип), а не віртуальний інтерфейс; абстракцію піднімай до віртуальної лише там, де реалізацію справді **підставляють у рантаймі**.

Спільна нитка всіх трьох винятків одна: **запах — це гіпотеза, а не вирок**. Драбина каже «тут пахне зчепленням за зліпком» — але рішення різати ухвалює не драбина, а хвиля правки, помножена на ймовірність, що ця зміна колись прийде, мінус ціна абстракції в тактах і рядках. Порахуй хвилю — реальну, на цьому коді, а не з підручника. Велика хвиля й правдоподібна зміна — рухайся щаблем, як показано вище. Хвиля в одиницю або зміна, що ніколи не прийде, — лиши запах жити: він дешевший за ліки.
