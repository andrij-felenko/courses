# ⚙️ Життя випуску: money від v1.0.0 до діамантового конфлікту

Ти ведеш компонент `money` — тип грошей, валюта, округлення, обмін. За рік він неминуче міняється: тут помилка, там нова можливість, а десь одна болюча перебудова. І кожна така зміна падає не в порожнечу, а на людей, яких ти ніколи не бачив, — на тих, хто написав у себе `import money` й пішов далі своїми справами. Ось у чому задача, і вона одразу двобока, дзеркальна.

З боку автора: різати кожен випуск так, щоб його **номер казав правду** — щоб три числа наперед попереджали, боляче буде оновлення чи ні. З боку споживача: оголосити залежність так, щоб **оновлення ніколи не заскочило зненацька** — щоб чужий поступ приходив, коли ти готовий, а не тієї миті, коли автор натиснув «запушити». Пройдімо обидва боки на одному живому компоненті, тоді приберімо випуск і подивімось, як усе валиться, а насамкінець знайдімо місце, де ламаються навіть чесні версії, — «діамант».

## Ідея: три числа — це машиночитана обіцянка

Уся хитрість семантичного версіонування (англ. *Semantic Versioning*, SemVer; специфікацію 2.0.0 склав Том Престон-Вернер, співзасновник GitHub) — в одному питанні, яке автор ставить до кожної своєї зміни: **що вона робить із кодом, який мене вже викликає?**

- Ламає його — компілятор захлинеться, тести почервоніють — це **MAJOR** (перше число).
- Додає щось нове, не чіпаючи старого, — старий код працює як був — це **MINOR** (середнє).
- Тихо виправляє поведінку, не міняючи жодного підпису, — це **PATCH** (останнє).

Зверни увагу, чого номер **не** описує: ні розміру правки, ні тижнів праці, ні того, пишався ти нею чи ні. Він описує рівно одне — **ризик для того, хто залежить**. Величезний внутрішній рефакторинг, невидимий зовні, — це PATCH. Один перейменований метод, дрібниця на п'ять хвилин, — це MAJOR. Номер міряє не тебе, а їхню збірку.

## money крок за кроком

Почнімо з першого випуску. Гроші зберігаємо як число з рухомою комою в основних одиницях, конструктор відкритий:

```ts
// money v1.0.0
export class Money {
  constructor(public amount: number, public currency: string) {}
  add(other: Money): Money { /* ... */ }
  format(): string { return `${this.amount} ${this.currency}`; }
}
// new Money(10.5, "USD")
```

Щойно ти опублікував `1.0.0`, ця форма — уже обіцянка. `amount` — число з комою, конструктор кличуть напряму, метод зветься `format`. Тисячі рядків чужого коду тепер спираються саме на це написання.

І тут вилазить давня біда грошей із рухомою комою: `0.1 + 0.2` не дорівнює `0.3`, копійки течуть крізь пальці. Правильний лік вимагає зберігати гроші **цілими** мінімальними одиницями — центами — і сховати конструктор за фабрикою, щоб ніхто не створив зіпсованого значення. Але це **прибирає** старе `new Money(10.5, ...)`: кожен виклик ламається. Це вже не латка й не сумісне доповнення — це ламка зміна:

```ts
// money v2.0.0 — ЛАМКЕ
export class Money {
  private constructor(private cents: number, readonly currency: string) {}
  static of(cents: number, currency: string): Money { return new Money(cents, currency); }
  add(other: Money): Money { /* ... */ }
  toString(): string { /* колишній format() */ }
}
// Money.of(1050, "USD")   // 10.50 USD
```

Тут аж два розломи одразу: конструктор став приватним, а `format` перетворився на `toString`. Обидва невидимі, доки споживач не оновиться й не побачить, як його збірка падає. Число `2.0.0` — це і є попередження, яке ти йому винен: «спершу прочитай, що змінилось, і лише тоді переходь».

Далі хтось просить переведення в іншу валюту. Ти **додаєш** метод, не чіпаючи нічого старого:

```ts
// money v2.1.0
convert(rate: number, target: string): Money { /* нове — старе недоторкане */ }
```

Нічого не прибрано, нічого не переписано. Той, хто сидів на `2.0.0`, оновлюється до `2.1.0` й не помічає нічого, крім нового методу під рукою. Це MINOR: середнє число росте, останнє — скидається в нуль, `2.1.0`.

А тоді виявляється, що `convert` обрізає дробову копійку замість чесного округлення й дає похибку в цент. Ти виправляєш округлення — той самий підпис, та сама поведінка ззовні, просто тепер правильно. Це PATCH: `2.1.1`.

Найтонше місце тут — **скидання молодших розрядів**. Із `2.1.1` наступний MINOR — це `2.2.0`, а не `2.1.2`; наступний MAJOR — `3.0.0`, а не `2.2.0`. Молодші числа — як лічильник пробігу: коли обертається старше колесо, усі молодші відкочуються в нуль. Ось це рішення «яке число рухати» цілком у коді — той самий вибір для трьох різних екосистем:

:::tabs
```ts
type Bump = "major" | "minor" | "patch";
function bump(v: string, kind: Bump): string {
  const [maj, min, pat] = v.split(".").map(Number);
  if (kind === "major") return `${maj + 1}.0.0`;   // скидає min і pat
  if (kind === "minor") return `${maj}.${min + 1}.0`; // скидає pat
  return `${maj}.${min}.${pat + 1}`;
}
// bump("2.1.1", "minor") === "2.2.0"
// bump("2.1.1", "major") === "3.0.0"
```
```python
def bump(v: str, kind: str) -> str:
    maj, min_, pat = (int(x) for x in v.split("."))
    if kind == "major":
        return f"{maj + 1}.0.0"        # скидає min і pat
    if kind == "minor":
        return f"{maj}.{min_ + 1}.0"   # скидає pat
    return f"{maj}.{min_}.{pat + 1}"
# bump("2.1.1", "major") -> "3.0.0"
```
```go
func Bump(v, kind string) string {
    var maj, min, pat int
    fmt.Sscanf(v, "%d.%d.%d", &maj, &min, &pat)
    switch kind {
    case "major":
        return fmt.Sprintf("%d.0.0", maj+1)      // скидає min і pat
    case "minor":
        return fmt.Sprintf("%d.%d.0", maj, min+1) // скидає pat
    default:
        return fmt.Sprintf("%d.%d.%d", maj, min, pat+1)
    }
}
```
:::

Арифметика тут — найлегша частина. Важке — чесно вибрати сам `kind`. Підняти число вміє й машина; а от розпізнати, ламає ця зміна когось чи ні, здатна лише людина (або інструмент, що звіряє підписи API). Помилишся в класифікації — і жоден із цих рядків тебе не врятує.

![Горизонтальна вісь чотирьох випусків money: v1.0.0, далі ламка зміна піднімає перше число до v2.0.0, сумісна можливість — середнє до v2.1.0, латка — останнє до v2.1.1; під віссю смуга показує, що залежність ^2.1.0 приймає версії від 2.1.0 включно до, але не включно, 3.0.0](/book/programming/software-design/reuse-release-equivalence/img/semver-lifecycle.svg)

*Який розряд рухає яка зміна. Ламка (центи замість рухомої коми, `format`→`toString`) підіймає MAJOR і скидає молодші в нуль; нова можливість (`convert`) — MINOR; виправлення округлення — PATCH. Смуга внизу — вікно `^2.1.0`: усе, що споживач тягне сам, і межа `3.0.0`, яку він перетне лише навмисне.*

## CHANGELOG: журнал, без якого номер німий

Номер каже «щось зламалось», але не каже **що** і **як перейти**. Це робить журнал змін. За домовленістю, яку 2014 року запропонував Олів'є Лакан (Olivier Lacan) під назвою «Keep a Changelog», записи йдуть найновішим угору й групуються за родом зміни — додано, змінено, виправлено, прибрано:

```markdown
# Changelog

## [2.1.1] — 2026-05-04
### Виправлено
- `convert()` округляв обрізанням — тепер банкове округлення (до парного).

## [2.1.0] — 2026-04-12
### Додано
- `convert(rate, target)` — переведення в іншу валюту.

## [2.0.0] — 2026-02-20
### Змінено
- **ЛАМКЕ:** гроші тепер зберігаються цілими мінімальними одиницями (центами):
  `new Money(10.5, "USD")` → `Money.of(1050, "USD")`.
- **ЛАМКЕ:** `format()` перейменовано на `toString()`.

## [1.0.0] — 2026-01-08
### Додано
- Тип `Money`, `add()`, `format()`.
```

Запис `2.0.0` — це, власне, карта переходу: два рядки, що перетворюють глухий стрибок номера на дорогу, якою можна пройти. Без нього `2.0.0` — замкнені двері без ключа: споживач бачить, що щось зламалось, але не знає, куди подіти свій старий виклик.

## Як споживач оголошує залежність

Тепер дзеркальний бік. REP універсальний — та сама обіцянка живе в кожній екосистемі, просто пишеться трьома різними написаннями. Ось наш `checkout`, який залежить від `money 2.1.0`:

:::tabs
```json
{
  "name": "checkout-service",
  "dependencies": {
    "money": "^2.1.0"
  }
}
```
```toml
# Cargo.toml — Rust
[dependencies]
money = "2.1.0"      # каре — типове; це вже й означає "^2.1.0"
```
```go
// go.mod — Go
module example.com/checkout

go 1.22

require example.com/money/v2 v2.1.0
```
:::

Читаються вони по-різному, і різниця тут не косметична.

**npm** розуміє `^2.1.0` як «від `2.1.0` включно, доки не зміниться перше ненульове число» — тобто `>=2.1.0 <3.0.0`. Отже `2.1.1` і навіть `2.9.9` приходять самі; `3.0.0` не прийде ніколи без твого відома.

**Cargo** ставить каре **типово**: рядок `money = "2.1.0"` уже означає те саме `^2.1.0` (`>=2.1.0 <3.0.0`). Растовець рідко пише сам символ `^` — він мається на увазі.

**Go** узагалі не знає діапазонів. `require ... v2.1.0` називає **одну** версію — і це **підлога, а не стеля**. І придивись до `/v2` у шляху: починаючи з мажора 2, головне число живе прямо в шляху імпорту (це зветься семантичним версіонуванням імпорту), тож `money` версії 1 і версії 2 — буквально **різні пакети**, а не два стани одного.

> 🔧 **Навіщо це.** Оцей один рядок у маніфесті — і є та точка, де REP перестає бути гарною думкою й починає керувати твоєю збіркою. `^2.1.0` каже менеджеру пакетів: «довіряю обіцянці автора в межах другого мажора — підхоплюй усе, що там з'явиться, але за поріг `3.0.0` не переступай без мене». Ти залежиш не від файлу й не від функції, а від **випущеної, пойменованої версії**, і саме діапазон робить оновлення керованим: усе безпечне тече само, усе небезпечне чекає твого рішення.

## Як менеджер пакетів це розв'язує

Робота менеджера пакетів — зібрати **всі** діапазони з усього дерева залежностей (не лише твої прямі, а й ті, що їх вимагають твої залежності) і знайти версію, яка вдовольняє кожен. Тут екосистеми знову розходяться: npm і Cargo беруть **найвищу** версію, що влазить у діапазон; Go зі своїм мінімальним добором версій (англ. *minimal version selection*, MVS) — навпаки, **найнижчу**, що вдовольняє всіх (найвищу з-поміж підлог). Обране число менеджер записує у файл-замок (lockfile), щоб наступна збірка була до байта такою самою.

Ось те саме розв'язання коротко — розкладка каре у вікно й вибір із того, що є на полиці:

```python
def caret_window(v):
    maj, min_, pat = (int(x) for x in v.split("."))
    if maj > 0:
        return (maj, min_, pat), (maj + 1, 0, 0)      # >=v, <(maj+1).0.0
    if min_ > 0:
        return (maj, min_, pat), (maj, min_ + 1, 0)   # 0.x: стеля — наступний мінор
    return (maj, min_, pat), (maj, min_, pat + 1)     # 0.0.x: кожна латка ламка

def resolve(available, lo, hi):
    ok = [v for v in available if lo <= v < hi]
    return max(ok) if ok else None   # npm/Cargo: найвища; Go MVS узяв би min(ok)

lo, hi = caret_window("2.1.0")
print(resolve([(2, 1, 0), (2, 1, 1), (2, 2, 0), (3, 0, 0)], lo, hi))  # (2, 2, 0)
```

Кортежі в Python порівнюються порозрядно, тож `(2,1,0) <= v < (3,0,0)` — це рівно семантика каре. `3.0.0` відпадає як завелике, а з решти береться найбільше — `2.2.0`.

Тут же видно й тонкість нульового мажора: доки версія `0.y.z`, ламким колесом стає **мінор**, і `caret_window` це враховує окремою гілкою. І варто затямити: файл-замок і маніфест — не одне й те саме. Маніфест — це **дозволений діапазон**, замок — **обрана точка**. Для застосунку замок комітять (щоб збірка відтворювалась), для бібліотеки — ні (хай останнє слово буде за застосунком, що її вбирає).

## Світ без випуску проти світу з випуском

Тепер прибери випуск — і подивись, що лишиться. Замість діапазону вкажи прямо на вихідники, на живу гілку:

```json
{
  "dependencies": {
    "money": "github:acme/money#main"
  }
}
```

`#main` — це не версія. Це «те, що на цій гілці **просто зараз**». Автор запушив у `main` перехід із рухомої коми на центи — і твоє найближче встановлення залежностей затягує цей злам; збірка падає, а ти його **не обирав**. Немає числа, щоб закріпитись, немає журналу, щоб стати воротами, немає способу лишитися на старому. Це та сама фотокопія знімка чужих вихідників, лише перевдягнена в залежність: ти успадковуєш кожен їхній пуш, хотів ти його чи ні.

Поверни `#main` назад на `^2.1.0` — і той самий пуш автора стає просто числом `3.0.0`, що лежить у сховищі, не чіпаючи твоєї збірки, і чекає, доки ти прочитаєш журнал і сам вирішиш. Оце і весь виграш REP, стиснутий в один рядок маніфесту: оновлення з засідки перетворюється на рішення.

## Діамантовий конфлікт

Але навіть із чесними версіями діапазони вміють зіштовхнутись. Твій `checkout` тягне дві залежності: `report` (звіти) і `ledger` (журнал операцій). `report` давніший і сидить іще на старому API грошей — вимагає `money ^1.0.0`. `ledger` уже перейшов на центи — вимагає `money ^2.0.0`. Менеджер шукає одну версію `money`, що вдовольнить обох:

- `^1.0.0` — це `>=1.0.0 <2.0.0`;
- `^2.0.0` — це `>=2.0.0 <3.0.0`.

Вікна не перетинаються. Спільної версії просто **не існує** — не тому, що хтось помилився з номером, а тому, що шляхи `checkout → report → money` і `checkout → ledger → money` замикаються на несумісних вимогах до одного й того самого. Це і є діамантовий конфлікт (термін і схема — загальновживані в інженерії залежностей).

```python
def intersects(a_lo, a_hi, b_lo, b_hi):
    return max(a_lo, b_lo) < min(a_hi, b_hi)

# report: ^1.0.0    ledger: ^2.0.0
intersects((1, 0, 0), (2, 0, 0),  (2, 0, 0), (3, 0, 0))   # False → діамант
```

Що робить кожна екосистема, коли впирається в таке:

- **npm** ставить **обидві** копії: `money@1` вкладеною під `report`, `money@2` — під `ledger`. Часто це минається: кожен тримає свою копію й не заважає сусідові. Кусає тоді, коли значення `Money` **перетинає межу** між `report` і `ledger` — бо це вже два різні класи `Money` із двох копій: `x instanceof Money` дає хибу, `a.add(b)` кидає помилку. Те саме ім'я, дві різні особи.
- **Cargo** теж компілює обидва мажори поряд (`1.x` і `2.x` — для нього різні крейти) — і та сама пастка подвійних типів, щойно `money` виринає в спільному прилюдному API.
- **Go** уже зробив із `/v2` окремий шлях імпорту, тож версії 1 і 2 співіснують за задумом; а всередині одного мажора MVS однаково добирає єдину версію.

Справжній вихід тут не механічний, а соціальний: звести `report` і `ledger` на **один** мажор `money` — зазвичай піднявши `report` за ламку зміну до другої версії. Дві копії по-справжньому працюють лише там, де ці два світи **ніколи не обмінюються** значенням `Money`.

*Дві незалежні гілки вимагають несумісних мажорів одного `money` — вікна `^1.0.0` і `^2.0.0` не перетинаються, і жодна версія не влаштує обох. Механічний «вихід» через дві копії мовчить лише доти, доки типи `Money` не зустрінуться на межі; надійний вихід — звести обидві залежності на спільний мажор.*

## Складність і пастки

- **Відкочуй лічильник.** MINOR обнуляє PATCH, MAJOR обнуляє і MINOR, і PATCH. Забудеш — і випустиш `2.1.2` там, де мав бути `2.2.0`, збивши весь дальший відлік.
- **Нульовий мажор — інший звір.** Доки версія `0.y.z`, ламким колесом є **мінор**: `^0.2.3` означає `>=0.2.3 <0.3.0`. Випуск `1.0.0` — це окрема обіцянка: «відсьогодні я перестаю ламати легковажно».
- **SemVer — обіцянка, яку тримає людина.** Піднімеш MINOR, а насправді тихо зміниш поведінку — і збрешеш так, що інструмент цього не зловить, доки в когось не почервоніють тести. Звіряння підписів API звужує щілину для сигнатур; за поведінку відповідає лише дисципліна.
- **Передрелізи стоять нижче за реліз.** `2.0.0-rc.1` менший за `2.0.0`, і каре `^2.1.0` не втягне передреліз, доки його не попросиш явно.
- **Несподіванка MVS.** Розробник, звиклий, що менеджер хапає найновіше, дивується, що Go тримається найнижчої версії, яка вдовольняє вимоги: новизна тут — річ навмисна, а не типова. Плата за це — відтворюваність без окремого файла-замка.
- **Діаманти з типами на межі.** Подвійне встановлення глушить менеджер, але закладає міни під `instanceof`. Замість тішитись, що «зібралось», краще звести залежності на спільний мажор.

Номер, діапазон, журнал і файл-замок — це чотири деталі однієї машини, що перетворює «схопи вихідники й молись» на «залеж і оновлюйся навмисне». А REP — причина, чому цій машині взагалі є на чому стояти: усі ці обіцянки можна дати лише про те, що ти справді **випускаєш**.
