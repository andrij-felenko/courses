# Принцип інверсії залежностей (DIP)

<preknowlist>
- [Інтерфейс проти реалізації](book:programming/interface-vs-implementation) — поділ на те, ЩО модуль обіцяє зовні, і ЯК він це робить усередині; без цього поділу інверсію нема куди вставити.
- [Принцип абстракції в програмуванні](book:programming/abstraction-principle) — чому одну ідею ховають за назвою, а деталі лишають усередині; абстракція — те, на що обидва боки почнуть спиратися.
- [Поліморфізм і динамічне зв'язування](book:programming/polymorphism) — як виклик через спільний інтерфейс за реальним типом об'єкта потрапляє в потрібну реалізацію; механізм, яким підставлена ззовні деталь оживає.
- [Зчеплення і зв'язність](book:programming/coupling-cohesion) — дві мірки залежності модулів; інверсія залежностей — прийом послаблення зчеплення, доведений до архітектурного рівня.
</preknowlist>

Коли пишеш код, залежності виникають самі собою, і майже завжди дивляться в один бік. Верхній модуль — той, що втілює задум, заради якого програму й писали, — гукає нижчі, щоб ті зробили чорну роботу. Розрахунок замовлення гукає базу даних, щоб зберегти результат. Логіка гри гукає бібліотеку рендеру, щоб намалювати кадр. Обробник платежу гукає HTTP-клієнт, щоб постукати до банку. Стрілка залежності скрізь одна: **важливе спирається на дрібне**. Так підказує сам порядок думки — спершу ми уявляємо, ЩО робимо, а тоді хапаємо перший-ліпший інструмент, що вміє це виконати, і вписуємо його ім'я просто в код.

І тут закладено тиху біду, яку [Роберт Мартін](book:programming/dependency-inversion/hist-dip-birth.md) 1996 року назвав однією з головних причин, чому системи «гниють». Придивись, що насправді сталося, коли розрахунок замовлення вписав усередину себе рядок із `MySqlConnection`. Цінна, довговічна річ — бізнес-правило, яке переживе десяток технологій, — виявилася **прибитою цвяхом до скороминущої деталі**. База даних зміниться. Провайдер платежів зміниться. Бібліотека рендеру застаріє за три роки. А правило рахувати суму замовлення — ні. Але через один рядок із чужим іменем воно тепер не компілюється без тієї бібліотеки, не тестується без живої бази, і будь-яка заміна нижнього шару лізе вгору, туди, де їй не місце. Напрямок стрілки зробив крихке ядром, а тривке — заручником.

## Стрілку можна розвернути

Ядро принципу вміщається в одну картинку: **між двома модулями поставити абстракцію — і змусити спиратися на неї обидва, а не один на одного**. Верхній більше не називає нижній на ім'я. Він називає лише інтерфейс — обіцянку «хтось уміє зберегти замовлення», байдуже хто. Нижній модуль цю обіцянку **виконує**, тобто реалізує інтерфейс. І ось що змінилося: тепер стрілка від нижнього йде **вгору, до абстракції** — він мусить підлаштуватися під чужу обіцянку. Обидва дивляться в одну точку посередині, і жоден не залежить від нутрощів іншого.

Звідси й слово **інверсія (лат. *inversio* — перевертання)**: перевертається саме той природний напрямок, у якому залежність тягнеться сама. Була стрілка «важливе → дрібне»; стало дві стрілки, що сходяться до абстракції, а деталь опинилася **на кінці, куди вона й належить** — залежною, замінною, необов'язковою для розуміння задуму.

Мартін стиснув це у два рядки, і варто прочитати їх повільно:

```
A. Модулі високого рівня не мають залежати від модулів низького рівня.
   Обидва мають залежати від абстракцій.
B. Абстракції не мають залежати від деталей.
   Деталі мають залежати від абстракцій.
```

Друга половина — не повтор першої, у ній окрема думка, і саме її найлегше проґавити. Мало розвернути стрілку — важливо ще, **чиєю мовою написана абстракція**. Інтерфейс має говорити поняттями верхнього, змістовного шару — «зберегти замовлення», «списати кошти», — а не протікати деталями нижнього: жодних `commitTransaction`, `rowId`, `httpStatus` у назвах методів. Бо якщо абстракція повторює форму конкретної бази, вона лише перефарбована деталь: підмінити базу все одно не вдасться, інтерфейс уже просякнутий її звичками. Абстракція, що залежить від деталі, — інверсія лише на папері.

> 🔧 **Навіщо це.** Найдорожче в цьому принципі — не «чистота», а **тестовність і замінність**, які він дає майже задарма. Поки розрахунок гукає інтерфейс `OrderStore`, у тесті на його місце стає крихітна підробка в пам'яті — і правило перевіряється за мілісекунди, без бази, мережі й прихованого стану. У проді туди ж стає справжня реалізація. Той самий шов пускає систему рости: додати другого провайдера платежів — це нова реалізація інтерфейсу, а ядро не чіпаємо. Один розворот стрілки одразу купує і швидкі тести, і свободу міняти інфраструктуру, не тривожачи бізнес-логіку.

## Як це виглядає в коді

Візьмімо той самий обробник платежу. Спершу — «як пишеться саме собою», з прямою залежністю ядра від деталі:

:::tabs
```cpp
// Ядро прибите до конкретного HTTP-клієнта: стрілка «важливе → дрібне»
#include "StripeHttpClient.h"          // деталь протекла у файл із логікою

class PaymentService {
    StripeHttpClient http_;            // ядро ТРИМАЄ конкретну деталь
public:
    void charge(const Order& o) {
        auto body = buildStripeJson(o); // логіка знає формат саме Stripe
        http_.post("https://api.stripe.com/charges", body);
    }
};
```
```python
# Ядро прибите до конкретного HTTP-клієнта: стрілка «важливе → дрібне»
from stripe_http_client import StripeHttpClient  # деталь протекла у модуль із логікою

class PaymentService:
    def __init__(self):
        self._http = StripeHttpClient()           # ядро ТРИМАЄ конкретну деталь

    def charge(self, order):
        body = build_stripe_json(order)           # логіка знає формат саме Stripe
        self._http.post("https://api.stripe.com/charges", body)
```
```go
// Ядро прибите до конкретного HTTP-клієнта: стрілка «важливе → дрібне»
import "example.com/stripe" // деталь протекла у пакет із логікою

type PaymentService struct {
    http stripe.HttpClient // ядро ТРИМАЄ конкретну деталь
}

func (s *PaymentService) Charge(o Order) {
    body := buildStripeJSON(o) // логіка знає формат саме Stripe
    s.http.Post("https://api.stripe.com/charges", body)
}
```
:::

Тут `PaymentService` неможливо ні зібрати без бібліотеки Stripe, ні перевірити без справжнього мережевого виклику, ні перевести на іншого провайдера без правки самого класу. Деталь оселилася в ядрі. Тепер поставимо між ними абстракцію мовою верхнього шару:

:::tabs
```cpp
// Абстракція говорить БІЗНЕС-мовою: «списати кошти», а не «зробити POST»
struct PaymentGateway {
    virtual ~PaymentGateway() = default;
    virtual ChargeResult charge(const Money& amount, const Card& card) = 0;
};

// Ядро залежить ЛИШЕ від обіцянки — і не знає, хто її виконає
class PaymentService {
    PaymentGateway& gateway_;           // посилання на абстракцію
public:
    explicit PaymentService(PaymentGateway& g) : gateway_(g) {}

    void charge(const Order& o) {
        auto r = gateway_.charge(o.total(), o.card());
        if (!r.ok) throw PaymentFailed(r.reason);
    }
};
```
```python
from abc import ABC, abstractmethod

# Абстракція говорить БІЗНЕС-мовою: «списати кошти», а не «зробити POST»
class PaymentGateway(ABC):
    @abstractmethod
    def charge(self, amount: Money, card: Card) -> ChargeResult: ...

# Ядро залежить ЛИШЕ від обіцянки — і не знає, хто її виконає
class PaymentService:
    def __init__(self, gateway: PaymentGateway):
        self._gateway = gateway         # посилання на абстракцію

    def charge(self, order):
        r = self._gateway.charge(order.total(), order.card())
        if not r.ok:
            raise PaymentFailed(r.reason)
```
```go
// Абстракція говорить БІЗНЕС-мовою: «списати кошти», а не «зробити POST»
type PaymentGateway interface {
    Charge(amount Money, card Card) ChargeResult
}

// Ядро залежить ЛИШЕ від обіцянки — і не знає, хто її виконає
type PaymentService struct {
    gateway PaymentGateway // посилання на абстракцію
}

func NewPaymentService(g PaymentGateway) *PaymentService {
    return &PaymentService{gateway: g}
}

func (s *PaymentService) Charge(o Order) error {
    r := s.gateway.Charge(o.Total(), o.Card())
    if !r.OK {
        return PaymentFailed{r.Reason}
    }
    return nil
}
```
:::

Конкретний Stripe тепер живе **збоку** й реалізує обіцянку — стрілка від нього йде вгору, до `PaymentGateway`:

:::tabs
```cpp
// Деталь ПІДЛАШТОВУЄТЬСЯ під абстракцію верхнього шару
class StripeGateway : public PaymentGateway {
    StripeHttpClient http_;
public:
    ChargeResult charge(const Money& amount, const Card& card) override {
        auto body = toStripeJson(amount, card);
        auto resp = http_.post("https://api.stripe.com/charges", body);
        return { resp.status == 200, resp.errorMessage() };
    }
};
```
```python
# Деталь ПІДЛАШТОВУЄТЬСЯ під абстракцію верхнього шару
class StripeGateway(PaymentGateway):
    def __init__(self):
        self._http = StripeHttpClient()

    def charge(self, amount: Money, card: Card) -> ChargeResult:
        body = to_stripe_json(amount, card)
        resp = self._http.post("https://api.stripe.com/charges", body)
        return ChargeResult(ok=resp.status == 200, reason=resp.error_message())
```
```go
// Деталь ПІДЛАШТОВУЄТЬСЯ під абстракцію верхнього шару
type StripeGateway struct {
    http stripe.HttpClient
}

func (g *StripeGateway) Charge(amount Money, card Card) ChargeResult {
    body := toStripeJSON(amount, card)
    resp := g.http.Post("https://api.stripe.com/charges", body)
    return ChargeResult{OK: resp.Status == 200, Reason: resp.ErrorMessage()}
}
```
:::

Хто саме зшиває ядро з конкретною реалізацією? Не саме ядро — інакше воно знов би назвало деталь на ім'я. Це робить **зовнішній збирач**, у самій верхівці програми, де вже все дозволено знати:

:::tabs
```cpp
int main() {
    StripeGateway stripe;                 // обрали деталь ТУТ, на краю світу
    PaymentService payments(stripe);      // і подали її ядру ззовні
    // ... ядро працює, не відаючи слова "Stripe"
}
```
```python
def main():
    stripe = StripeGateway()              # обрали деталь ТУТ, на краю світу
    payments = PaymentService(stripe)     # і подали її ядру ззовні
    # ... ядро працює, не відаючи слова "Stripe"
```
```go
func main() {
    stripe := &StripeGateway{}                 // обрали деталь ТУТ, на краю світу
    payments := NewPaymentService(stripe)      // і подали її ядру ззовні
    _ = payments                               // ... ядро працює, не відаючи слова "Stripe"
}
```
:::

Ось і вся механіка. Ядро згадує лише `PaymentGateway`. Слово «Stripe» стоїть рівно в одному місці — у точці збірки, найдальшій від бізнес-правил. Щоб у тесті перевірити логіку, туди ж подають підробку:

:::tabs
```cpp
// Підробка замість мережі: тест ядра БЕЗ Stripe і без інтернету
struct FakeGateway : PaymentGateway {
    Money lastAmount{};
    ChargeResult charge(const Money& a, const Card&) override {
        lastAmount = a;                   // просто запам'ятали, що просили
        return { true, "" };              // і вдали успіх
    }
};

// PaymentService payments(fake); charge(order);
// перевіряємо: fake.lastAmount == order.total()  — за мілісекунди, без мережі
```
```python
# Підробка замість мережі: тест ядра БЕЗ Stripe і без інтернету
class FakeGateway(PaymentGateway):
    def __init__(self):
        self.last_amount = None

    def charge(self, amount: Money, card: Card) -> ChargeResult:
        self.last_amount = amount         # просто запам'ятали, що просили
        return ChargeResult(ok=True, reason="")  # і вдали успіх

# PaymentService(fake).charge(order)
# перевіряємо: fake.last_amount == order.total()  — за мілісекунди, без мережі
```
```go
// Підробка замість мережі: тест ядра БЕЗ Stripe і без інтернету
type FakeGateway struct {
    lastAmount Money
}

func (g *FakeGateway) Charge(a Money, _ Card) ChargeResult {
    g.lastAmount = a                      // просто запам'ятали, що просили
    return ChargeResult{OK: true, Reason: ""} // і вдали успіх
}

// NewPaymentService(fake).Charge(order)
// перевіряємо: fake.lastAmount == order.Total()  — за мілісекунди, без мережі
```
:::

Те, що передавання залежності ззовні через конструктор має власну назву — **впровадження залежності (dependency injection)** — не збіг: це найпоширеніший спосіб *здійснити* інверсію на практиці. Тут легко сплутати два різні поняття, і плутають їх постійно.

## DIP — це не те саме, що DI

Розділимо чітко, бо назви небезпечно схожі. **Принцип інверсії залежностей (DIP)** — це *куди має дивитися стрілка*: правило, що ядро й деталь обоє спираються на абстракцію. **Впровадження залежності (DI)** — це *яким прийомом* готову деталь передають туди, де її вживають: не створюй її всередині, а прийми ззовні — параметром конструктора, аргументом, полем. Одне — мета, друге — техніка, і вони не тотожні.

Побачити різницю найлегше на випадку, коли одне є без іншого. Можна впорснути залежність, порушивши інверсію, — якщо тип аргументу конкретний:

:::tabs
```cpp
// DI Є (передали ззовні), а DIP НЕМА (тип — конкретна деталь)
class ReportBuilder {
    MySqlDatabase& db_;                   // впорснули, але прив'язались до MySQL
public:
    explicit ReportBuilder(MySqlDatabase& db) : db_(db) {}
};
```
```python
# DI Є (передали ззовні), а DIP НЕМА (тип — конкретна деталь)
class ReportBuilder:
    def __init__(self, db: MySqlDatabase):  # впорснули, але прив'язались до MySQL
        self._db = db
```
```go
// DI Є (передали ззовні), а DIP НЕМА (тип — конкретна деталь)
type ReportBuilder struct {
    db *MySqlDatabase // впорснули, але прив'язались до MySQL
}

func NewReportBuilder(db *MySqlDatabase) *ReportBuilder {
    return &ReportBuilder{db: db}
}
```
:::

Тут залежність подано ззовні — і все одно ядро зчеплене з конкретною базою: заміни `MySqlDatabase` на абстрактний `Database`, щоб стрілка нарешті вперлася в обіцянку, а не в продукт. І навпаки — можна тримати інверсію без класичного впорскування, просто ховаючи вибір реалізації за [фабрикою](book:programming/factory-method), яка теж повертає абстракцію. Тож DIP каже, *на що* спиратися; DI — лише один зі способів це влаштувати. Поширений, зручний, але не єдиний і не сам принцип.

## Звідки взялася сама ідея розвороту

Думка «не ти гукаєш готовий код, а він гукає твій» старша за акронім і навіть за об'єктне програмування. Її давно знали автори бібліотек і, зокрема, тих, що переросли в **каркаси (frameworks)**. Різницю між бібліотекою й каркасом ловить крилата фраза, яку інженери [запозичили у Голлівуду](book:programming/dependency-inversion/hist-hollywood-ioc.md): «Не дзвоніть нам — ми подзвонимо вам». Бібліотеку ти гукаєш сам, коли схочеш; каркас натомість тримає керування в себе й гукає **твій** код у потрібну мить. Це і є розворот залежності, піднятий на рівень цілого застосунку, — окрема, ширша ідея, знана як **інверсія керування (inversion of control)**.

Ці двоє — рідня, але не одне й те саме, і мішати їх не варто. Інверсія керування — про те, **хто кого гукає** в часі виконання: чий код головний, а чий вставлений у чужий хід подій. Інверсія залежностей — вужча й статичніша: про те, **у який бік дивиться стрілка залежності** на етапі компіляції, куди спрямоване `#include`, від чого не збереться модуль. Каркас майже завжди спирається на обидва розвороти разом, тож їх і плутають; але керування розвертають у рантаймі, а залежність — у структурі коду. З цих двох саме інверсія залежностей — той щоденний важіль, яким і власний код розплітають на замінні частини, не пишучи жодного каркаса.

*Ліворуч стрілка тече від важливого до дрібного — ядро прибите до деталі. Праворуч між ними стоїть абстракція, і обидві стрілки сходяться до неї: ядро залежить від обіцянки, деталь підлаштовується під ту саму обіцянку. Перевернувся напрямок, у який залежність тягнеться сама.*

## Де тут межа й де пастка

Розворот стрілки не безкоштовний, і саме тому його не роблять усюди підряд. Кожен інтерфейс, вставлений між двома модулями, — це зайвий шар, який хтось пише, читає й супроводжує; читаючи виклик, уже не бачиш одразу, *що* виконається, — треба знати, яку реалізацію підставили ззовні. За гнучкість платять **простотою**. Тому інверсію ставлять там, де межа **справжня**: між тривким ядром і скороминущою деталлю, яку реально колись підмінять, — база, зовнішній сервіс, пристрій, формат. Ставити абстракцію між двома шматками, що завжди житимуть і мінятимуться разом, — це заплатити ціну за замінність, якою ніхто не скористається; те саме застереження, що й у [YAGNI](book:programming/dry-kiss-yagni) — не абстрагуй наперед те, чого ще не потребуєш.

Друга пастка тонша й трапляється частіше за першу: **фальшива інверсія**, коли інтерфейс формально є, але списаний із конкретної реалізації. Ознака проста — методи абстракції пахнуть деталлю. Якщо в «загальному» `OrderStore` стирчать `beginTransaction`, `execSql`, `resultSet`, то це не абстракція над сховищем, а тонка плівка поверх однієї бази: підставити чергу чи файл під такий інтерфейс не вийде, бо він уже говорить мовою SQL. Справжня перевірка одна — **чи існує друга, геть інша реалізація, що чесно виконує ту саму обіцянку**. Якщо жодної, крім тієї, під яку інтерфейс і кроївся, помислити не вдається, інверсії ще нема; є лише зайвий шар, що коштує простоти й нічого не купує натомість.

Тому й тримаймося того, з чого почали: залежності виникають самі й самі дивляться на дрібне. Інверсія залежностей — свідоме зусилля розвернути цю стрілку **там, де на кінці опинилося щось важливіше за інструмент, до якого його прив'язали**. Постав між ними обіцянку мовою важливого, змусь інструмент їй коритися — і ядро твоєї програми перестане залежати від того, що завтра застаріє.
