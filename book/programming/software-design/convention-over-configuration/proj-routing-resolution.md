# ⚙️ Розпізнавання конвенційних маршрутів у файловій системі

Маршрутизація на основі файлової системи (File-system routing) є фундаментальним прикладом втілення парадигми конвенції замість конфігурації у сучасній інженерії програмного забезпечення. Замість ручного ведення масивних маніфестів чи списків маршрутизації, де кожен шлях зв'язується з обробником через імперативний виклик `router.add("/api/users/:id", Handler)`, архітектура перетворює саму структуру каталогів на диску в активне дерево виконання.

Коли HTTP-сервер отримує вхідний мережевий запит, наприклад `GET /api/users/1024/profile`, система не здійснює послідовний лінійний перебір списку регулярних виразів. Вона розбиває URL-шлях на атомарні сегменти й спускається по префіксному дереву вузлів, автоматично зіставляючи назви каталогів зі статичними сегментами, вилучаючи значення динамічних параметрів із папок у квадратних дужках та передаючи керування цільовій дії. Це дозволяє досягти стабільної та передбачуваної обробки запитів на масштабі тисяч маршрутів.

## Математична та алгоритмічна модель префіксного дерева

В основі конвенційної диспетчеризації лежить спеціалізоване префіксне дерево (Prefix Trie / Radix Tree). Кожен рівень цього дерева представляє окремий сегмент мережевого шляху між символами скісної риски `/`.

У файловій системі кожен елемент ієрархії маршрутів належить до одного з чітко визначених типів:

1. **Статичний сегмент (Literal Node):** Звичайний каталог із фіксованим ім'ям (наприклад, `api`, `users`, `settings`, `analytics`). Такий вузол вимагає повного посимвольного збігу зі значенням сегмента у вхідному URL.
2. **Параметричний сегмент (Parameter Node):** Каталог, назва якого за конвенцією огортається у квадратні дужки (наприклад, `[id]`, `[slug]`, `[userId]`). Вузол приймає будь-яке довільне рядкове значення із запиту та зберігає його у словнику динамічних параметрів під ключем, зазначеним усередині дужок.
3. **Жадібний сегмент (Catch-all Node):** Каталог із префіксом трикрапки `[...slug]`. Цей вузол захоплює всі наступні сегменти вхідного шляху до самого кінця, упаковуючи їх у послідовний масив рядків.
4. **Обробник кінцевої дії (Terminal Handler):** Файл зі зарезервованою конвенційною назвою (наприклад, `page`, `route`, `index`), який містить точку входу для обробки запиту.

### Структура вузла в оперативній пам'яті

Кожен вузол дерева у пам'яті процесу містить такі фундаментальні поля:
- `name`: Рядковий ідентифікатор сегмента (або назва параметра без квадратних дужок).
- `type`: Перелічуваний тип вузла (статичний чи параметричний).
- `handler`: Вказівник на функцію-обробник або об'єкт зворотного виклику (null для проміжних каталогів).
- `children`: Список або динамічний масив вказівників на дочірні вузли наступного рівня.

Під час ініціалізації сервера інструмент збирання або модуль завантаження сканує файловий каталог маршрутів один раз, формуючи це компактне дерево в оперативній пам'яті. Подальша обробка всіх мережевих запитів відбувається виключно через обхід сформованого дерева без звернень до фізичного диска.

### Правила вирішення конфліктів та спадання пріоритетів

У структурі реального веб-застосунку на одному рівні каталогу можуть одночасно знаходитися записи різних типів. Наприклад, усередині каталогу `app/routes/users/` можуть одночасно існувати папка `settings/` (для налаштувань профілю) та динамічна папка `[id]/` (для завантаження даних конкретного користувача за ідентифікатором).

Щоб поведінка диспетчера була суворо детермінованою і не залежала від порядку читання файлів із диска операційною системою, діє непорушне правило спадання пріоритетів (Precedence Resolution):

- **Пріоритет 1 (Найвищий — Статичний збіг):** Диспетчер завжди спершу шукає точний збіг серед статичних вузлів. Якщо сегмент запиту дорівнює `settings`, обирається статична гілка `users/settings`.
- **Пріоритет 2 (Середній — Динамічний параметр):** Якщо серед статичних вузлів збігу не знайдено, диспетчер перевіряє наявність параметричного вузла `[id]` і зберігає вилучене значення (`id = "1024"`).
- **Пріоритет 3 (Найнижчий — Жадібний сегмент):** Якщо інші варіанти відсутні, керування передається жадібному сегменту `[...rest]`.

Якщо на сервер надходить запит `/api/users/settings`, маршрутизатор знаходить точний статичний збіг і спрямовує виконання до загальних налаштувань. Якщо надходить запит `/api/users/8472`, де статичний каталог `8472` відсутній, диспетчер переходить у параметричний вузол `[id]`.

## Практична реалізація: C та C++

Нижче наведено самодостатню реалізацію конвенційного маршрутизатора мовами C та C++. Реалізація демонструє повний цикл диспетчеризації: токенізацію вхідного шляху без зайвих алокацій пам'яті, рекурсивний пошук у дереві з урахуванням пріоритетів, вилучення параметрів та безпечний відкат стану при виявленні глухого кута.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdbool.h>

#define MAX_CHILDREN 16
#define MAX_PARAMS 8
#define MAX_STR_LEN 64
#define MAX_SEGMENTS 16

typedef enum {
    NODE_STATIC,
    NODE_PARAM
} NodeType;

typedef void (*RouteHandler)(const char* params[][2], size_t param_count);

typedef struct RouteNode {
    char name[MAX_STR_LEN];
    NodeType type;
    RouteHandler handler;
    struct RouteNode* children[MAX_CHILDREN];
    size_t child_count;
} RouteNode;

RouteNode* create_node(const char* name, NodeType type, RouteHandler handler) {
    RouteNode* node = (RouteNode*)calloc(1, sizeof(RouteNode));
    if (!node) return NULL;
    strncpy(node->name, name, MAX_STR_LEN - 1);
    node->type = type;
    node->handler = handler;
    return node;
}

void add_child(RouteNode* parent, RouteNode* child) {
    if (parent && child && parent->child_count < MAX_CHILDREN) {
        parent->children[parent->child_count++] = child;
    }
}

void free_tree(RouteNode* root) {
    if (!root) return;
    for (size_t i = 0; i < root->child_count; ++i) {
        free_tree(root->children[i]);
    }
    free(root);
}

size_t tokenize_path(const char* path, char segments[MAX_SEGMENTS][MAX_STR_LEN]) {
    size_t count = 0;
    const char* p = path;
    while (*p == '/') p++;

    while (*p && count < MAX_SEGMENTS) {
        const char* start = p;
        while (*p && *p != '/') p++;
        size_t len = (size_t)(p - start);
        if (len > 0 && len < MAX_STR_LEN) {
            strncpy(segments[count], start, len);
            segments[count][len] = '\0';
            count++;
        }
        while (*p == '/') p++;
    }
    return count;
}

bool match_recursive(RouteNode* current, char segments[MAX_SEGMENTS][MAX_STR_LEN],
                     size_t seg_idx, size_t total_segs,
                     const char* params[][2], size_t* param_count) {
    if (seg_idx == total_segs) {
        if (current->handler != NULL) {
            current->handler(params, *param_count);
            return true;
        }
        return false;
    }

    const char* current_seg = segments[seg_idx];

    // 1. Пріоритет: точний статичний збіг
    for (size_t i = 0; i < current->child_count; ++i) {
        RouteNode* child = current->children[i];
        if (child->type == NODE_STATIC && strcmp(child->name, current_seg) == 0) {
            if (match_recursive(child, segments, seg_idx + 1, total_segs, params, param_count)) {
                return true;
            }
        }
    }

    // 2. Пріоритет: динамічний параметр [param]
    for (size_t i = 0; i < current->child_count; ++i) {
        RouteNode* child = current->children[i];
        if (child->type == NODE_PARAM) {
            size_t p_idx = *param_count;
            if (p_idx < MAX_PARAMS) {
                params[p_idx][0] = child->name;
                params[p_idx][1] = current_seg;
                *param_count = p_idx + 1;

                if (match_recursive(child, segments, seg_idx + 1, total_segs, params, param_count)) {
                    return true;
                }
                *param_count = p_idx; // Відкат стану у разі глухого кута
            }
        }
    }

    return false;
}

void handle_system_settings(const char* params[][2], size_t count) {
    printf("-> [Handler] Статичний маршрут: Налаштування системи\n");
    (void)params; (void)count;
}

void handle_user_profile(const char* params[][2], size_t count) {
    printf("-> [Handler] Динамічний маршрут: Профіль користувача\n");
    for (size_t i = 0; i < count; ++i) {
        printf("   Параметр [%s] = %s\n", params[i][0], params[i][1]);
    }
}

void handle_user_post(const char* params[][2], size_t count) {
    printf("-> [Handler] Динамічний маршрут: Пост користувача\n");
    for (size_t i = 0; i < count; ++i) {
        printf("   Параметр [%s] = %s\n", params[i][0], params[i][1]);
    }
}

int main(void) {
    RouteNode* root = create_node("", NODE_STATIC, NULL);
    RouteNode* api = create_node("api", NODE_STATIC, NULL);
    RouteNode* users = create_node("users", NODE_STATIC, NULL);
    RouteNode* settings = create_node("settings", NODE_STATIC, handle_system_settings);
    RouteNode* user_id = create_node("userId", NODE_PARAM, NULL);
    RouteNode* profile = create_node("profile", NODE_STATIC, handle_user_profile);
    RouteNode* posts = create_node("posts", NODE_STATIC, NULL);
    RouteNode* post_id = create_node("postId", NODE_PARAM, handle_user_post);

    add_child(root, api);
    add_child(api, users);
    add_child(users, settings);
    add_child(users, user_id);
    add_child(user_id, profile);
    add_child(user_id, posts);
    add_child(posts, post_id);

    const char* test_urls[] = {
        "/api/users/settings",
        "/api/users/1024/profile",
        "/api/users/42/posts/999",
        "/api/users/unknown/invalid/path"
    };

    char segments[MAX_SEGMENTS][MAX_STR_LEN];
    const char* params[MAX_PARAMS][2];

    for (size_t t = 0; t < 4; ++t) {
        printf("=== Запит: %s ===\n", test_urls[t]);
        size_t seg_count = tokenize_path(test_urls[t], segments);
        size_t param_count = 0;

        if (!match_recursive(root, segments, 0, seg_count, params, &param_count)) {
            printf("-> Помилка 404: Відповідного маршруту не знайдено\n");
        }
        printf("\n");
    }

    free_tree(root);
    return 0;
}
```

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <vector>
#include <unordered_map>
#include <memory>
#include <optional>
#include <functional>

enum class NodeType {
    Static,
    Param
};

using ParamMap = std::unordered_map<std::string, std::string>;
using RouteHandler = std::function<void(const ParamMap&)>;

struct RouteNode {
    std::string name;
    NodeType type;
    std::optional<RouteHandler> handler;
    std::vector<std::unique_ptr<RouteNode>> children;

    RouteNode(std::string node_name, NodeType node_type, std::optional<RouteHandler> h = std::nullopt)
        : name(std::move(node_name)), type(node_type), handler(std::move(h)) {}

    RouteNode* add_child(std::string child_name, NodeType child_type, std::optional<RouteHandler> h = std::nullopt) {
        children.push_back(std::make_unique<RouteNode>(std::move(child_name), child_type, std::move(h)));
        return children.back().get();
    }
};

class FileSystemRouter {
public:
    FileSystemRouter() : root_("", NodeType::Static) {}

    RouteNode* root() { return &root_; }

    bool dispatch(std::string_view url_path) const {
        std::vector<std::string_view> segments = tokenize(url_path);
        ParamMap params;
        return resolve(&root_, segments, 0, params);
    }

private:
    RouteNode root_;

    static std::vector<std::string_view> tokenize(std::string_view path) {
        std::vector<std::string_view> result;
        size_t start = 0;
        while (start < path.size()) {
            start = path.find_first_not_of('/', start);
            if (start == std::string_view::npos) break;
            size_t end = path.find_first_of('/', start);
            if (end == std::string_view::npos) {
                result.push_back(path.substr(start));
                break;
            }
            result.push_back(path.substr(start, end - start));
            start = end;
        }
        return result;
    }

    bool resolve(const RouteNode* current, const std::vector<std::string_view>& segments,
                 size_t index, ParamMap& params) const {
        if (index == segments.size()) {
            if (current->handler.has_value()) {
                (*current->handler)(params);
                return true;
            }
            return false;
        }

        std::string_view current_seg = segments[index];

        // 1. Пріоритет: точний статичний збіг
        for (const auto& child : current->children) {
            if (child->type == NodeType::Static && child->name == current_seg) {
                if (resolve(child.get(), segments, index + 1, params)) {
                    return true;
                }
            }
        }

        // 2. Пріоритет: динамічний параметр [name]
        for (const auto& child : current->children) {
            if (child->type == NodeType::Param) {
                params[child->name] = std::string(current_seg);
                if (resolve(child.get(), segments, index + 1, params)) {
                    return true;
                }
                params.erase(child->name); // Відкат стану
            }
        }

        return false;
    }
};

int main() {
    FileSystemRouter router;

    auto* api = router.root()->add_child("api", NodeType::Static);
    auto* users = api->add_child("users", NodeType::Static);

    // Статичний маршрут: /api/users/settings
    users->add_child("settings", NodeType::Static, [](const ParamMap&) {
        std::cout << "-> [Handler] Статичний маршрут: Налаштування системи\n";
    });

    // Динамічний маршрут: /api/users/[userId]/profile
    auto* user_id = users->add_child("userId", NodeType::Param);
    user_id->add_child("profile", NodeType::Static, [](const ParamMap& params) {
        std::cout << "-> [Handler] Динамічний маршрут: Профіль користувача\n";
        for (const auto& [key, value] : params) {
            std::cout << "   Параметр [" << key << "] = " << value << "\n";
        }
    });

    // Динамічний вкладений маршрут: /api/users/[userId]/posts/[postId]
    auto* posts = user_id->add_child("posts", NodeType::Static);
    posts->add_child("postId", NodeType::Param, [](const ParamMap& params) {
        std::cout << "-> [Handler] Динамічний маршрут: Пост користувача\n";
        for (const auto& [key, value] : params) {
            std::cout << "   Параметр [" << key << "] = " << value << "\n";
        }
    });

    const std::vector<std::string_view> test_urls = {
        "/api/users/settings",
        "/api/users/1024/profile",
        "/api/users/42/posts/999",
        "/api/users/unknown/invalid/path"
    };

    for (const auto& url : test_urls) {
        std::cout << "=== Запит: " << url << " ===\n";
        if (!router.dispatch(url)) {
            std::cout << "-> Помилка 404: Відповідного маршруту не знайдено\n";
        }
        std::cout << "\n";
    }

    return 0;
}
```

## Покроковий розбір виконання та трасування обходу

Розглянемо, як алгоритм обробляє запит `/api/users/42/posts/999` крок за кроком:

1. **Фаза токенізації:** Рядок запиту розбивається на послідовність сегментів: `["api", "users", "42", "posts", "999"]`. Кількість сегментів `N = 5`.
2. **Крок 1 (`seg_idx = 0`, сегмент `"api"`):** Пошук починається від кореня `root`. Серед дочірніх вузлів виявляється статичний вузол `"api"`. Відбувається рекурсивний перехід на наступний рівень.
3. **Крок 2 (`seg_idx = 1`, сегмент `"users"`):** У вузла `"api"` єдиний дочірній статичний вузол `"users"` збігається із запитом. Перехід углиб.
4. **Крок 3 (`seg_idx = 2`, сегмент `"42"`):** У вузла `"users"` перевіряється статичний дочірній вузол `"settings"` — посимвольний збіг відсутній. Диспетчер переходить до другого пріоритету й знаходить параметричний вузол `"userId"`. У словник параметрів записується пара `userId = "42"`.
5. **Крок 4 (`seg_idx = 3`, сегмент `"posts"`):** Усередині вузла `"userId"` алгоритм шукає збіг для `"posts"`. Знайдено статичний вузол `"posts"`. Відбувається перехід.
6. **Крок 5 (`seg_idx = 4`, сегмент `"999"`):** У вузла `"posts"` перевіряються дочірні елементи. Виявлено параметричний вузол `"postId"`. У словник записується пара `postId = "999"`.
7. **Крок 6 (Термінальний стан):** Індекс сегмента досяг довжини масиву (`seg_idx == 5`). Вузол `"postId"` містить зареєстрований обробник `handle_user_post`. Диспетчер викликає функцію, передаючи їй сформований словник параметрів (`userId="42"`, `postId="999"`).

## Диспетчеризація HTTP-методів та ієрархія макетів

У промислових системах конвенційна маршрутизація розв'язує ще два критичні завдання:

### 1. Диспетчеризація методів HTTP (Method Dispatching)
Кожен термінальний вузол може містити карту обробників для різних HTTP-дієслів (`GET`, `POST`, `PUT`, `DELETE`). Якщо шлях запиту успішно зіставлений із вузлом дерева, але відповідного методу не зареєстровано, маршрутизатор не повертає помилку `404 Not Found`. Він формує заголовок `Allow` з переліком доступних методів вузла та повертає код стану `405 Method Not Allowed`.

### 2. Ієрархічна композиція макетів (Nested Layouts)
Під час рекурсивного обходу дерева диспетчер зберігає стек знайдених файлів макетів `layout.tsx` для кожного пройденого каталогу. Під час рендерингу відповіді кінцевий компонент сторінки автоматично огортається всіма макетами від кореня до листка: `RootLayout(UsersLayout(UserPage))`. Це позбавляє розробника потреби вручну імпортувати та компонувати спільні елементи інтерфейсу (навігаційні панелі, бічні меню, підвали сайту).

## Механізм конвеєра проміжного ПЗ (Middleware Onion Pipeline)

У конвенційній файловій системі кожен рівень каталогу може містити власний файл проміжного обробника (наприклад, `_middleware.ts` або `middleware.go`). Під час проходження дерева запит виконується за принципом «цибулинної архітектури» (Onion Model):

1. **Фаза прямого спуску (Downstream):** Перед викликом кінцевого обробника послідовно виконуються функції проміжних шарів від кореня до цільового листка. Кореневий middleware перевіряє глобальні обмеження швидкості (Rate Limiting) та генерує унікальний ідентифікатор трасування запиту (TraceID). Вкладений middleware підкаталогу `app/admin/` перевіряє права адміністратора у JWT-токені.
2. **Фаза термінальної обробки:** Виконується дія цільового контролера або рендеринг компонента сторінки.
3. **Фаза зворотного підйому (Upstream):** Відповідь повертається назад через ланцюжок middleware у зворотному порядку, що дозволяє додавати заголовки безпеки (CORS, CSP, HSTS), вимірювати загальний час виконання та фіксувати метрики продуктивності.

## Поглиблений аналіз: стиснення дерева та локальність кешу

У високонавантажених серверах класичне дерево сегментів піддається процедурі стиснення шляхів (Radix Tree Optimization). Якщо ланцюжок каталогів містить проміжні вузли без альтернативних розгалужень та без параметрів (наприклад, `api/v1/internal/health`), оптимізатор зливає їх в один комбінований вузол зі спільним префіксом `"api/v1/internal/health"`.

Переваги стиснення дерева:
1. **Зменшення глибини рекурсії:** Замість чотирьох послідовних викликів функції пошуку диспетчер виконує один посимвольний виклик `strncmp` або `memcmp`, суттєво заощаджуючи ресурси стека процесора.
2. **Локальність даних у пам'яті:** Складені рядки префіксів зберігаються у суміжних ділянках пам'яті (flat memory buffers). При завантаженні вузла в кеш-лінію процесора L1 (64 байти) всі необхідні символи опиняються в надшвидкій пам'яті, мінімізуючи штрафи на промахи кешу (D-Cache misses).
3. **Економія адресного простору:** Кількість об'єктів вузлів у купі зменшується на 40–60%, що знижує навантаження на підсистему збирання сміття у керованих середовищах (Go, Node.js, JVM).

## Обробка паралельних та перехоплюваних маршрутів

У сучасних веб-архітектурах конвенційна файлова система підтримує складні патерни користувацького досвіду без написання імперативного коду навігації:

1. **Паралельні слоти (`@slot`):** Каталоги з префіксом `@` дозволяють рендерити декілька незалежних сторінок одночасно в межах одного батьківського макета (наприклад, панель керування, що одночасно відображає слоти `@analytics` та `@notifications`). Кожен слот має власну ізольовану обробку станів завантаження `loading.tsx` та помилок `error.tsx`.
2. **Перехоплювані маршрути (`(..)route`):** Конвенція дозволяє перехоплювати клієнтські переходи для відображення контекстних модальних вікон (наприклад, перегляд фотографії у модальному оверлеї над стрічкою новин), зберігаючи при цьому можливість прямого завантаження сторінки за повним URL при оновленні вкладки браузера.

## Механізм попереднього завантаження та префетчингу

Конвенційна структура файлової системи дозволяє браузерному клієнту автоматично виконувати префетчинг (Prefetching) коду та даних:

Коли користувач наводить курсор на гіперпосилання або коли посилання з'являється у зоні видимості екрана (через `IntersectionObserver`), клієнтський маршрутизатор визначає відповідний конвенційний вузол дерева та заздалегідь завантажує бандл коду та дані сторінки у фоновому режимі. Завдяки цьому в момент фізичного кліку перехід на нову сторінку відбувається миттєво з нульовою затримкою рендерингу (Zero Latency Transition).

## Статична генерація параметрів та гібридний рендеринг

Для динамічних параметричних маршрутів сучасні конвенційні каркаси надають механізм випереджальної збірки (Static Site Generation, SSG). Замість виконання пошуку в базі даних на кожен вхідний запит розробник експортує конвенційну функцію генерації параметрів:

1. **Функція генерації параметрів (`generateStaticParams`):** Під час збирання проєкту функція повертає повний масив відомих параметрів (наприклад, ідентифікатори перших ста найпопулярніших товарів `[{ id: "1" }, { id: "2" }]`).
2. **Випереджальний рендеринг сторінок:** Компілятор обходить дерево файлової системи та генерує статичні HTML-файли для кожного значення зі списку.
3. **Інкрементальна регенерація (ISR):** Якщо надходить запит на ідентифікатор, якого не було в попередньому списку, сервер обробляє його динамічно, зберігаючи згенерований результат у кеші для всіх наступних клієнтів.

## Інтернаціоналізація та локалізовані піддерева

Для підтримки багатомовних інтерфейсів конвенційні маршрутизатори використовують параметричні кореневі каталоги локалей: `app/[lang]/about/page.tsx`.

1. **Автоматичне розпізнавання мови:** Кореневий middleware аналізує заголовок `Accept-Language`, кукі користувача або географічну IP-локацію, визначаючи цільову мову (наприклад, `uk` або `en`).
2. **Канонічна переадресація:** Якщо запит надійшов на нелокалізований URL `/about`, сервер автоматично генерує HTTP-переадресацію `307 Temporary Redirect` на відповідний мовний шлях `/uk/about`.
3. **Ізоляція словників перекладу:** Значення параметра `lang` автоматично передається у властивості всіх дочірніх макетів і компонентів сторінки, що усуває потребу в глобальних змінних стану.

## Виконання на периферійних вузлах мережі (Edge Runtime)

Сучасні платформи доставки контенту (Cloudflare Workers, Vercel Edge Network, Fastly Compute) компілюють конвенційне префіксне дерево маршрутизації у компактні модулі WebAssembly (Wasm) або оптимізований байткод двигуна V8.

Оскільки префіксне дерево не містить важких залежностей і не виконує операцій блокуючого введення-виведення, диспетчеризація запитів відбувається безпосередньо на прикордонних PoP-серверах (Points of Presence), розташованих у географічній близькості до користувача. Це скорочує мережеву затримку першого байта (Time To First Byte, TTFB) до 5–15 мілісекунд для користувачів по всьому світу.

## Порівняння продуктивності: Таблиця регулярних виразів проти Префіксного дерева

Традиційні маршрутизатори першого покоління зберігали список маршрутів у вигляді плоского масиву скомпільованих регулярних виразів. Під час надходження запиту система послідовно тестувала кожен регулярний вираз від першого до останнього:

| Архітектурна модель | Складність пошуку | Споживання пам'яті | Вплив на CPU Cache |
| :--- | :--- | :--- | :--- |
| **Лінійний перебір RegExp** | `O(N · L)`, де `N` — кількість маршрутів | Високе (окремі об'єкти DFA/NFA) | Часті промахи кешу команд (I-Cache misses) |
| **Конвенційне дерево Radix Trie** | `O(K · M)`, де `K` — глибина сегментів | Низьке (спільні статичні префікси) | Висока локальність даних у L1/L2 кеші |

У системі з 500 кінцевими точками лінійний перебір вимагає до 500 перевірок регулярних виразів на кожен вхідний пакет, що створює помітну затримку під навантаженням. Префіксне дерево виконує пошук за 3–5 порівнянь сегментів незалежно від загальної кількості маршрутів у системі, демонструючи стабільний час відповіді у кілька мікросекунд.

## Системні гарантії, крайові випадки та безпека

Під час практичного використання конвенційної маршрутизації у виробничих серверах інженери враховують такі критичні аспекти:

1. **Канонізація шляхів та захист від Path Traversal:** До початку синтаксичного розбору маршрутизатор зобов'язаний нормалізувати вхідний URL: видалити зайві слеші (`//`), усунути відносні переходи (`..` та `.`), відсікти нульові байти (`%00`) та відкинути матричні параметри чи параметри запиту (`?query=value`). Це гарантує, що запит не зможе вийти за межі кореневого каталогу маршрутів.
2. **Ізоляція стану під час відкату (Backtracking):** Якщо обхід дерева зайшов у параметричну гілку, яка згодом виявилася глухим кутом на глибшому рівні, алгоритм зобов'язаний повністю видалити тимчасово зафіксований параметр зі словника (`params.erase`), перш ніж переходити до наступного кандидата.
3. **Статична валідація на етапі збирання проєкту:** Наявність двох параметричних каталогів із різними назвами на одному рівні файлової системи (наприклад, `app/[userId]/` та `app/[companyId]/`) є логічною помилкою неоднозначності конвенції. Сучасні збирачі застосунків (Next.js, Remix, Vite) діагностують такі конфлікти ще під час компіляції проєкту, блокуючи розгортання некоректного дерева.
4. **Типізація та коерція динамічних значень:** Отримані з файлового дерева параметри запиту є рядками. Каркас надає конвенційні засоби перетворення рядка `"1024"` на ціле число або тип UUID. Якщо вхідне значення не відповідає очікуваному типовому обмеженню (наприклад, передано рядок `"abc"` у числовий параметр ідентифікатора), система формує відмову з кодом стану `400 Bad Request` ще до запуску бізнес-логіки контролера.
5. **Життєвий цикл пам'яті через блочні арени (Arena Allocators):** У високонавантажених C/C++ серверах виділення пам'яті під словник параметрів кожного окремого HTTP-запиту з глобальної купи (`malloc` / `new`) призводить до блокувань у багатопотоковому середовищі. Застосування локального арена-алокатора на стек потоку дозволяє миттєво виділяти пам'ять під час обходу вузлів та скидати весь виділений блок за одну інструкцію після відправки відповіді клієнтові.\n
