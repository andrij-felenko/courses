# 🧮 Ціна повтору: чому важить площа блоку, а не місце перевірки

Порахуймо для кожного способу розставити повтори на маршруті дві величини — скільки зайвих передавань він з'їдає і скільки зайвого часу — і побачимо, що обидві залежать не від того, **де** стоїть перевірка, а від **площі** шматка, який доводиться слати наново. З цієї однієї величини випадають і поріг, за яким наскрізний рестарт програє на порядки, і формула найдешевшого розміру блоку, і відповідь на питання, за якої частоти помилок повтор на сусідній ділянці взагалі окупається.

## Модель і одиниця вартості

Маршрут — це `k` ділянок поспіль, між ними `k − 1` проміжних вузлів; кожен вузол приймає пакет цілком, а тоді відправляє далі ([збережи-й-перешли](topic:programming/store-and-forward)). Файл — `N` пакетів. Одне передавання одного пакета через одну ділянку не доходить цілим з імовірністю `p`; що саме сталося — перевернувся біт у дроті, черга переповнилася, зіпсувалася комірка пам'яті вузла, — для арифметики байдуже, важить лише, що `p` однакове для всіх передавань і вони [незалежні](topic:math/independent-trials).

Вартість міряємо в **пакето-ділянках**: одна пакето-ділянка — це одне передавання одного пакета однією лінією. Це єдина одиниця, у якій дві стратегії можна чесно порівняти, бо вона однаково рахує і роботу дроту, і роботу проміжного вузла.

Щоб числа не висіли в порожнечі: фізичні рівні гігабітного Ethernet проєктують під частоту бітових помилок не гіршу за 10⁻¹², і для пакета в 1500 байтів (12 000 бітів) це дає `p ≈ 1.2·10⁻⁸`. Реальні втрати на маршруті звичайно на порядки більші, бо їх роблять не биті, а переповнені черги — тож увесь діапазон від 10⁻⁸ до 10⁻² тут не гра уяви, а робочий інтервал.

## Скільки разів доведеться повторювати

Нехай одна спроба вдається з імовірністю `P`. Кількість спроб до першого успіху — випадкове число `K`, і його розподіл видно одразу: щоб перша вдала спроба була `j`-ю, треба, щоб `j − 1` спроба провалилася, а `j`-та вдалася.

```
P(K = j) = (1 − P)^(j−1) · P            j = 1, 2, 3, …
```

Середнє значення `K` можна взяти з таблиці ([геометричний розподіл](topic:math/geometric-distribution)), але його швидше вивести, ніж згадати. Позначмо `E = E[K]`. Одну спробу ми робимо завжди. З імовірністю `P` на цьому все закінчується; з імовірністю `1 − P` ми опиняємося рівно в тій самій ситуації, що й на початку, — попереду знову в середньому `E` спроб. Звідси рівняння на саме себе:

```
E = 1 + (1 − P) · E
E · P = 1
E = 1 / P
```

Середнє — не вся правда, і це важливо для планування. Імовірність, що доведеться зробити більш ніж `m` спроб, — це просто `m` поспіль провалів:

```
P(K > m) = (1 − P)^m
```

Звідси квантиль: щоб укластися з імовірністю 99 %, треба закласти не `1/P` спроб, а

```
m₀.₉₉ = ln(0.01) / ln(1 − P) ≈ 4.61 / P = 4.61 · E[K]
```

Хвіст у геометричного розподілу важкий настільки, що середнє й дев'яносто дев'ятий відсоток різняться майже вп'ятеро. Стандартне відхилення `√(1−P)/P` за малого `P` практично дорівнює самому середньому: розкид тут не поправка до відповіді, а сама відповідь. Хто ставить таймаут на «два середні часи передавання», відрізає `e⁻² ≈ 14 %` цілком нормальних передавань.

## Звідки береться обрив

Тепер підставмо в `P` те, що дає модель. Щоб блок із `n` передавань пройшов без жодної помилки, кожне з `n` має пройти:

```
P = (1 − p)^n
```

Ця степінь і є той обрив, який усі бачили на графіках, але корисно розібрати, звідки він береться алгебраїчно. Візьмімо логарифм і розкладімо його в ряд ([ряд Тейлора](topic:math/taylor-series)):

```
ln(1 − p) = −(p + p²/2 + p³/3 + …)

(1 − p)^n = e^(n·ln(1−p)) = e^(−n·p) · e^(−n·p²/2 − …)
```

Головний множник — `e^(−n·p)`, решта — поправка. Отже

```
E[K] = 1 / (1 − p)^n ≈ e^(n·p)
```

і в показнику стоїть **добуток** `n·p`, а не кожен множник окремо. Довжина блоку і якість лінії тут взаємозамінні: удесятеро довший блок на вдесятеро чистішій лінії дає ту саму кількість спроб. Уся арифметика вибору зводиться до одного безрозмірного числа `n·p` — скільки помилок припадає на один блок.

Поправку варто оцінити, щоб знати, коли наближенням можна користуватися. Множник, який ми відкинули, — це `e^(−n·p²/2)`. Для `n = 10⁴` і `p = 10⁻³` він дорівнює `e^(−0.005) = 0.995`, тобто `e^(−np)` занижує відповідь на пів відсотка: точне `1/(1−p)^n = 22 138`, наближене `e¹⁰ = 22 026`. Наближення тримається доти, доки `n·p² ≪ 1`, а це майже завжди, бо `p` мале.

Умова «повторів практично не буде» тепер читається без графіка. Щоб середня кількість спроб не перевищувала `1 + ε`:

```
e^(n·p) ≤ 1 + ε   ⟺   n·p ≤ ln(1 + ε) ≈ ε
```

Для `ε = 0.01` це `n·p ≤ 0.01`. Загальна форма — знайоме `n·p ≪ 1`; ліворуч від цієї межі повтор нічого не коштує, праворуч ціна росте експоненційно.

## Дві крайні стратегії на маршруті з k переходів

Тепер порівняймо два способи довести файл із `N` пакетів через `k` ділянок.

**Повтор на кожній ділянці.** Кожен вузол перевіряє прийняте й, якщо треба, просить сусіда переслати. Для кожної пари «пакет, ділянка» кількість передавань — геометрична з успіхом `1 − p`, тобто в середньому `1/(1−p)`. Таких пар рівно `k·N`, а середнє суми дорівнює сумі середніх незалежно від того, як вони пов'язані:

```
E_ділянка = k·N / (1 − p)                   (точно, не наближено)
```

**Тільки наскрізний рестарт.** Ніхто по дорозі нічого не перевіряє; кінець звіряє відбиток і, якщо не збігся, просить усе спочатку. Спроба вдається, тільки якщо цілими пройшли всі `k·N` передавань, і кожна спроба, вдала чи ні, коштує рівно `k·N` пакето-ділянок (зіпсований пакет ніхто дорогою не викидає — його ж ніхто не перевіряє):

```
P_спроби = (1 − p)^(k·N)
E_наскрізь = k·N / (1 − p)^(k·N)            (теж точно)
```

Поділивши одне на друге, дістаємо відношення, у якому `k·N` уціліло, а решта скоротилася:

```
R = E_наскрізь / E_ділянка = (1 − p)^(1 − k·N) ≈ e^(k·N·p)
```

Одиниця обліку на `R` не впливає: якщо рахувати не пакето-ділянки, а тільки те, що впорснув у мережу відправник, обидві величини поділяться на `k`, і відношення лишиться те саме. Це добре, бо означає, що висновок не залежить від того, кому ми виставляємо рахунок.

Числа для `k = 3` і `N = 10⁴` (тобто `k·N = 3·10⁴` передавань на одну наскрізну спробу):

```
p        k·N·p     спроб        E_ділянка     E_наскрізь      R
10⁻⁷     0.003     1.003        30 000        30 090          1.003
10⁻⁶     0.03      1.030        30 000        30 914          1.030
10⁻⁵     0.3       1.350        30 000        40 496          1.35
10⁻⁴     3         20.1         30 003        602 657         20.1
10⁻³     30        1.08·10¹³    30 030        3.25·10¹⁷       1.08·10¹³
10⁻²     300       8.8·10¹³⁰    30 303        2.6·10¹³⁵       8.7·10¹³⁰
```

Пороги читаються прямо з `R ≈ e^(kNp)`:

```
R ≥ 10    ⟺  p ≥ ln 10  / (k·N) = 7.7·10⁻⁵
R ≥ 100   ⟺  p ≥ ln 100 / (k·N) = 1.5·10⁻⁴
R ≤ 1.01  ⟺  p ≤ ln 1.01 / (k·N) = 3.3·10⁻⁷
```

Між `3.3·10⁻⁷` і `7.7·10⁻⁵` лежить уся зона, де вибір іще не має значення; вона вужча за два з половиною порядки, і саме тому суперечка «повтор унизу чи вгорі» так часто виявляється суперечкою про різні режими роботи однієї мережі.

## Важить лише площа

Дві стратегії вище — крайні точки одного сімейства, і корисно порахувати все сімейство одразу. Нехай відновлення покриває `s` ділянок поспіль (маршрут ділиться на `k/s` таких відтинків) і працює блоками по `u` пакетів (файл ділиться на `N/u` блоків). Перевірка стоїть у кінці кожного відтинку; не збіглося — увесь блок іде цим відтинком наново.

Блок проходить один відтинок цілим, якщо цілими пройшли всі `s·u` передавань усередині:

```
P(блок пройшов відтинок) = (1 − p)^(s·u)
середня кількість спроб   = (1 − p)^(−s·u)
вартість однієї спроби    = s·u  пакето-ділянок
пар «блок × відтинок»     = (N/u) · (k/s)
```

Перемножмо — і `s` з `u` скорочуються всюди, крім показника:

```
E(s, u) = (N/u)·(k/s) · s·u · (1 − p)^(−s·u) = k·N · (1 − p)^(−s·u)
```

Позначмо `A = s·u` — **площа блоку відновлення** в клітинках «пакет × ділянка». Тоді

```
E(A) = k·N · (1 − p)^(−A) ≈ k·N · e^(p·A)
```

Мінімум `k·N` — це стільки передавань потрібно, якби помилок не було зовсім; усе понад нього — множник `e^(pA)`, у який ані `k`, ані `N`, ані місце перевірки не входять окремо. Входить сама площа.

![Три сітки «ділянки × пакети» по три рядки й вісім стовпців: у першій залито одну клітинку (одна ділянка, один пакет, A = 1, ×1.0001), у другій — увесь перший стовпець (весь шлях, один пакет, A = k = 3, ×1.0003), у третій — усю сітку (весь шлях, увесь файл, A = k·N = 30 000, ×20.1); внизу формула E = k·N·(1 − p)⁻ᴬ ≈ k·N·e^(pA)](img/recovery-area.svg)

*Одна клітинка — одне передавання одного пакета однією ділянкою. Залите — те, що доводиться слати наново після однієї знайденої помилки. Вартість схеми визначає площа залитого, а не те, у якому місці маршруту стоїть перевірка: перехід від першої сітки до другої (перевірка поїхала з ділянки на кінець) додає три сотих відсотка, а перехід від другої до третьої (перевірка лишилася на кінці, але блок став усім файлом) — двадцятикратну плату.*

Перевіримо на крайніх точках. `s = 1, u = 1` дає `A = 1` і `k·N/(1−p)` — повтор на ділянці. `s = k, u = N` дає `A = k·N` — наскрізний рестарт усього файла. Але між ними є точка, повз яку легко проскочити: `s = k, u = 1` — **наскрізний повтор, але окремим пакетом**. Її площа `A = k = 3`, і множник `e^(3·10⁻⁴) = 1.0003`. Тобто перенести повтор із ділянки на самий кінець коштує три сотих відсотка зайвих передавань — практично нічого.

Звідси головний числовий висновок цього розділу, і він не той, якого чекають: катастрофу робить **не місце** перевірки, а **розмір одиниці повтору**. `A` — добуток двох множників, і `u` в реальних системах більше за `k` на порядки: три-чотири переходи проти тисяч пакетів. Наскрізна схема з дрібною одиницею дешева; ділянкова схема з грубою одиницею дорога так само, як наскрізна.

Це відразу дає ціну відомої розв'язки в протоколах із вікном: якщо після втрати переслати все вікно завширшки `W`, а не один загублений пакет, одиниця повтору стає `u ≈ W`, і плата росте як `e^(p·k·W)` замість `e^(p·k)` ([ARQ зі ковзним вікном](topic:communications/sliding-window-arq)). Вибіркове підтвердження, яке дозволяє переслати саме те, чого бракує, — це не оптимізація на відсотки, а зменшення показника експоненти у `W` разів.

## Другий вимір: час

Кількість передавань — половина рахунку. Друга половина — затримка, і тут стратегії розходяться з іншої причини: **щоб переслати, треба спершу дізнатися**, а звістка про втрату йде рівно стільки, скільки завширшки відтинок відновлення.

Позначення:

```
b — час передавання одного пакета лінією (серіалізація)
d — одностороння затримка на одній ділянці
h = 2d       — оберт на ділянці (RTT сусідів)
H = 2·k·d    — оберт усього шляху (RTT кінців)
```

![Дві драбинкові діаграми з вузлами A, R₁, R₂, B; час іде вниз, один крок = 5 мс. Ліворуч «повтор між сусідами»: пакет губиться на ділянці R₁→R₂, R₂ шле звістку назад до R₁, R₁ пересилає, пакет доходить до B із запізненням 2d = 10 мс. Праворуч «повтор із кінця»: пакет губиться там само, звістку шле B через увесь маршрут до A, A пересилає через усі три ділянки, запізнення 2kd = 30 мс](img/recovery-latency.svg)

*Ліворуч і праворуч гине той самий пакет на тій самій ділянці; різниця тільки в тому, хто помітив утрату. Сусід помічає її за один оберт своєї ділянки, кінець — за оберт усього шляху, і саме ця різниця, помножена на кількість утрат, є всім, що дає повтор на ділянці. Кількість переданих пакетів у цих двох випадках майже однакова, бо площа блоку різниться лише в `k` разів.*

Чисте передавання без жодної помилки — це проштовхнути `N` пакетів конвеєром і дочекатися підтвердження з кінця:

```
T₀ = N·b + H
```

Кожне невдале передавання додає до цього часу оберт свого відтинка плюс пересилання блоку. Невдалих спроб у середньому

```
M(A) = (k·N / A) · [ (1 − p)^(−A) − 1 ]
```

(пар «блок × відтинок» — `kN/A`, на кожну припадає `1/P − 1` провалів), а кожна коштує `2·s·d + u·b`. Разом, якщо доставка впорядкована і потік на час відновлення стає:

```
T(s, u) ≈ N·b + 2·k·d + (k·N / A) · [ (1 − p)^(−A) − 1 ] · (2·s·d + u·b)
```

Підставмо конкретні лінії: пакет 1500 байтів на 100 Мбіт/с дає `b = 120 мкс`, ділянка на 5 мс дає `d = 5 мс`, тож `h = 10 мс`, `H = 30 мс`, `T₀ = 1.23 с`. Три схеми при `k = 3`, `N = 10⁴`:

```
p        A = 1 (ділянка)   A = 3 (кінець, пакет)   A = 3·10⁴ (кінець, файл)
10⁻⁶     1.2303 с          1.2309 с                1.2675 с
10⁻⁵     1.2330 с          1.2390 с                1.6603 с
10⁻⁴     1.2604 с          1.3204 с                24.71 с
10⁻³     1.5339 с          2.1354 с                1.33·10¹³ с ≈ 423 000 років
```

Три речі в цій таблиці варті окремої уваги. Перша: одна формула відтворює всі три стовпці — це не три моделі, а три точки однієї. Друга: перший і другий стовпці всюди різняться на відсотки, бо різниця між ними — тільки ширина оберту, і вона входить лінійно. Третя: третій стовпець ламається, бо туди входить `e^(pA)` з площею в тридцять тисяч.

Різницю між першими двома стовпцями теж можна виписати формулою. Пакет гине десь на шляху з імовірністю `1 − (1−p)^k ≈ k·p`, таких пакетів `N·k·p`, і кожен коштує зайвих `H − h = 2(k−1)d`:

```
ΔT ≈ N·k·p · 2·(k − 1)·d
```

Це і є **все**, що дає повтор на ділянці порівняно з наскрізним повтором окремого пакета: не надійність, не менше передавань — тільки зекономлені оберти.

## Найдешевша площа

Якщо великий блок дорогий, чому б не робити `A = 1` завжди? Бо перевірки не безплатні: кожна вимагає підтвердження, стану, таймера. Хай одна перевірка коштує `c` пакето-ділянок (підтвердження — теж трафік, та й вузол витрачає роботу). Перевірок рівно `k·N/A`, тож повна робота

```
W(A) = k·N · [ e^(p·A) + c/A ]
```

Перший доданок росте з площею, другий спадає — мінімум є, і його видно з похідної:

```
dW/dA = k·N · [ p·e^(p·A) − c/A² ] = 0
p · A² · e^(p·A) = c
```

За робочих значень `p·A ≪ 1` експонента дорівнює одиниці з точністю до частки відсотка, і рівняння розв'язується в один рядок:

```
A* ≈ √(c / p)

надлишок у мінімумі:  p·A* + c/A* = 2·√(c·p)
```

![Крива зайвої роботи на одну пакето-ділянку залежно від площі блоку A в подвійно логарифмічних осях, p = 10⁻⁴, c = 0.1: спадна пунктирна пряма c/A, зростальна пунктирна крива e^(pA) − 1 і суцільна сума з мінімумом при A = 32; на кривій позначено чотири точки — A = 1 (повтор на ділянці), A = 3 (наскрізний по пакету), A = 32 (найдешевша площа), A = 30 000 (наскрізний усім файлом)](img/cost-vs-area.svg)

*Дві плати тягнуть у різні боки: перевірки дешевшають з ростом блоку як `c/A`, перепосилання дорожчають як `e^(pA) − 1`. Сума має мінімум там, де похідні зрівноважуються, — при `A* = √(c/p)`, і в цій точці на кожну корисну пакето-ділянку припадає лише `2√(cp)` зайвої роботи. Дно широке: у межах порядку навколо `A*` втрати менші за відсоток, тож точне значення не важить — важить не потрапити на схили, а вони круті обидва.*

Числа для `c = 0.1`:

```
p = 10⁻⁶ :  A* = 316   надлишок 0.06 %
p = 10⁻⁴ :  A* = 32    надлишок 0.63 %
p = 10⁻³ :  A* = 10    надлишок 2.0 %
```

Оптимальна площа падає як `1/√p`, а не як `1/p`: удесятеро гірша лінія вимагає зменшити блок лише втричі. І два висновки-нерівності, які з цього випливають. По-перше, `A* = √(c/p)` майже завжди більше за одиницю — тобто дрібнити до одного пакета на одну ділянку не оптимально, накладні витрати з'їдають виграш. По-друге, за `p = 10⁻⁴` оптимум `32` менший за `k·N = 30 000` у тисячу разів: рестарт усім файлом промахується повз мінімум на три порядки, і це промах не в надійності, а суто в бухгалтерії.

## Коли повтор на ділянці лише додає затримки

Лишилося порахувати зворотний бік — випадки, де ділянковий повтор коштує більше, ніж дає.

**За кількістю передавань** він не дає майже нічого, доки площа наскрізного блоку мала. Порівняння `A = 1` проти `A = k` дає множник `(1−p)^(1−k) ≈ e^((k−1)p)` — це `1.0002` за `p = 10⁻⁴`. Отже вся суперечка «ділянка чи кінець» при дрібній одиниці повтору — суперечка про час, а не про трафік.

**За часом** виграш `ΔT ≈ N·k·p·2(k−1)·d` треба порівняти з тривалістю самого передавання `T₀ ≈ N·b`. Вимагаймо, щоб механізм економив хоча б частку `ε`:

```
N·k·p·2(k−1)·d  ≥  ε·N·b
p  ≥  ε·b / (2·k·(k−1)·d)
```

Для `ε = 0.05`, `b = 120 мкс`, `d = 5 мс`, `k = 3`:

```
p*  =  0.05 · 120·10⁻⁶ / (2·3·2·5·10⁻³)  =  10⁻⁴
```

Нижче `10⁻⁴` повтор на ділянці економить менш ніж двадцяту частину часу передавання — і за це доводиться тримати на кожному вузлі буфери, таймери й стан. Зверни увагу на структуру порога: `p*` пропорційне `b/d`. На короткій лінії всередині машинної зали `d` мале, `p*` велике — ділянковий повтор майже ніколи не окупається. На супутниковому плечі `d` величезне, `p*` мале — окупається одразу. Тому механізм повтору живе на радіо й супутнику, а не в стійці.

**Для потоку з терміном придатності** рахунок ще суворіший, бо там пізній пакет дорівнює втраченому. Хай пакет має дійти до відтворення за час `D` від відправлення. Дорога займає `k·d`, а одне відновлення на відтинку завширшки `s` додає `2·s·d + u·b`. Пересилати варто, тільки якщо результат ще встигне:

```
k·d + 2·s·d + u·b  ≤  D
```

Для `k = 3`, `d = 5 мс`, `b = 0.12 мс`, `u = 1`: ділянковий повтор (`s = 1`) вимагає `D ≥ 25.1 мс`, наскрізний (`s = 3`) — `D ≥ 45.1 мс`. Якщо буфер тримає 20 мс, не встигає жоден: переслані пакети приходять уже після своєї миті, займають лінію намарне і — за впорядкованої доставки — затримують ще й усе, що йшло за ними, на ті самі `2·s·d + u·b`. Якщо буфер тримає 60 мс, встигають обидва, і тоді вибір знову зводиться до нерівності з `ΔT`. Саме ця пара нерівностей і стоїть за тим, що для потоків у реальному часі повтор вимикають, а не налаштовують ([затримка й надійність](topic:communications/latency-reliability)).

Виграш, від якого відмовляються, теж рахується: без відновлення частка втрачених пакетів дорівнює `1 − (1−p)^k ≈ k·p`. За `p = 10⁻⁵` і `k = 3` це `3·10⁻⁵` — один пакет із тридцяти трьох тисяч; за пакетів по 20 мс звуку одна подряпина припадає на одинадцять хвилин розмови. Проти цього стоїть стійке погіршення затримки на кожному відновленні. Нерівність, яка розв'язує суперечку, коротка: `k·p` проти ціни зайвих `2·s·d` для всього потоку — і за малих `p` ліва частина програє завжди.
