# Інтерфейс проти реалізації

</preknowlist>

Увімкни світло — і воно засвітиться. Ти клацнув клавішу вимикача, не знаючи нічого про те, що по той бік стіни: чи там реле, чи механічні контакти, чи розумний диммер із мікроконтролером. Вимикач дав тобі **обіцянку** — «клацнеш угору, буде світло» — і сховав за нею **все, як саме** ця обіцянка виконується. Ти покладаєшся на обіцянку; електрик за стіною вільний перекласти проводку як завгодно, поки клавіша працює по-старому. У цьому крихітному побутовому факті сидить, мабуть, найважливіший поділ у всьому програмуванні: різниця між тим, **що** річ обіцяє назовні, і тим, **як** вона це робить усередині.

Ці два боки мають імена. **Інтерфейс (лат. *inter* — між, *facies* — обличчя; «те, чим річ повернена до інших»)** — це обіцянка: набір операцій, які можна викликати, з умовами, що вони приймають і що повертають. **Реалізація (лат. *realis* — дійсний; «втілення в дійсність»)** — це механізм: конкретний код, дані, алгоритми, якими обіцянку виконано. Вимикач — інтерфейс; проводка за стіною — реалізація. І весь фокус доброго дизайну в тому, щоб провести між ними чітку лінію й **тримати її** — бо саме вона вирішує, скільки коштуватиме кожна майбутня зміна.

## Чому саме ця лінія коштує грошей

Придивімося, чому поділ не косметичний, а буквально грошовий. Код живе роками, і майже весь той час його **міняють**: пришвидшують, лагодять, переносять на нову платформу, підмінюють бібліотеку. Питання завжди одне — **скільки місць зачепить одна зміна**. І ось тут між двома боками лінії пролягає різка асиметрія.

Усе, що ти пообіцяв в інтерфейсі, стало **чужою опорою**: інший код тепер викликає твої функції, спираючись на їхні імена, аргументи, поведінку. Зміниш обіцянку — і кожен, хто на неї спирався, ламається. А все, що ти сховав у реалізації, лишилося **твоєю приватною справою**: поки обіцянка стоїть, ти вільний переписати нутрощі хоч щоночі, і жоден клієнт цього не помітить. Один бік лінії застиг під вагою чужих залежностей; другий лишився вільним. Саме тому лінію проводять свідомо: усе, що напевно колись зміниться, ховають **під** нею, а назовні виставляють якомога вужчу, стабільнішу обіцянку.

![Горизонтальна лінія-контракт: над нею червоні блоки «звіт, форма, журнал, тест» прив'язані до обіцянки й ламаються від її зміни; під нею зелені блоки «буфер, структури даних, алгоритм, блокування» можна вільно переписати](/book/programming/software-design/interface-vs-implementation/img/asymmetry.svg)

*Лінія рішення ділить світ навпіл. Над нею — ті, хто викликає: вони прив'язані до обіцянки, і її зміна їх ламає. Під нею — те, як зроблено: його переписують будь-коли, і над лінією ніхто не помічає. Ця асиметрія — вся причина, чому лінію проводять там, де зміна найімовірніша.*

> 🔧 **Навіщо це.** У прошивці асиметрія особливо відчутна. Драйвер давача обіцяє одне: `float read_temp(void)`. За цією обіцянкою може стояти I2C-обмін, потім ти переходиш на SPI-варіант тієї самої мікросхеми, потім додаєш усереднення кількох вибірок — і жоден рядок коду, що кличе `read_temp`, не змінюється. Гроші й нерви, які ти не витратив на правку десятків місць виклику, — це прямий дивіденд від того, що лінія між обіцянкою й обміном по шині проведена чітко.

## Як лінія виглядає в коді

У C цей поділ вбудований у саму мову — його несуть два файли. **Заголовний файл (`.h`)** оголошує обіцянку: які функції існують і як їх кликати. **Файл реалізації (`.c`)** містить тіла цих функцій. Клієнт вмикає лише заголовок і бачить рівно обіцянку — не тіла. Найчистіше це виходить із **непрозорим вказівником**: тип оголошено, але його будову сховано, тож клієнт тримає посилання на річ, нутрощів якої не знає.

**Обіцянка в заголовку — сам лічильник невидимий:**

```c
// counter.h — усе, що бачить клієнт. Жодного поля, лише операції.
typedef struct Counter Counter;   // тип є, будова прихована (непрозорий тип)

Counter *counter_new(void);
void     counter_inc(Counter *c);
int      counter_value(const Counter *c);
void     counter_free(Counter *c);
```

Клієнт не знає — і не може знати, — чи лічильник усередині це просте `int`, чи атомарний тип, чи запис у файл. Він тримається за обіцянку: «створи, збільш, спитай значення, звільни». Реалізація живе окремо й вільна вибирати механізм:

```c
// counter.c — тут, і лише тут, відома справжня будова.
#include "counter.h"
#include <stdlib.h>

struct Counter { int n; };        // приватне рішення: поки що просте int

Counter *counter_new(void)            { Counter *c = malloc(sizeof *c); c->n = 0; return c; }
void     counter_inc(Counter *c)      { c->n++; }
int      counter_value(const Counter *c) { return c->n; }
void     counter_free(Counter *c)     { free(c); }
```

Завтра знадобиться потокобезпечний лічильник — міняєш поле `n` на атомарний тип і додаєш блокування **всередині `counter.c`**. Заголовок не ворухнувся; отже, весь код, що кликав ці функції, навіть **не треба перекомпільовувати наново** заради нової семантики — обіцянка та сама. Повний робочий приклад із підміною реалізації «на льоту» — від простого `int` до стека з перевірками, без правки жодного місця виклику — розібрано покроково в окремому [проєкті з непрозорим вказівником](book:programming/interface-vs-implementation/proj-opaque-handle-c.md).

У C++ ту саму лінію проводять інакше — **чисто віртуальними методами**. Абстрактний клас оголошує обіцянку, а нащадки дають різні реалізації:

```cpp
// Обіцянка: будь-хто, хто вміє віддати температуру.
struct SensorReader {
    virtual float read() = 0;      // = 0 : реалізації тут нема, лише контракт
    virtual ~SensorReader() = default;
};
```

Той, хто користується `SensorReader`, тримає вказівник на обіцянку й не знає, який саме механізм за нею стоїть. А стоятиме будь-який:

```cpp
struct FakeSensor : SensorReader { float read() override { return 25.0f; } };     // для тесту
struct I2cSensor  : SensorReader { float read() override { return i2c_read(); } };// реальний давач

void log_temperature(SensorReader& s) {   // працює з ОБІЦЯНКОЮ, не з механізмом
    printf("t = %.1f\n", s.read());
}
```

Функція `log_temperature` написана раз і працює з **усіма** реалізаціями: підставиш `FakeSensor` у тесті, `I2cSensor` у бойовому коді — код журналювання не змінюється ні на символ.

## Одна обіцянка — багато нутрощів

Ось де поділ віддає найбільший зиск. Коли клієнт залежить лише від інтерфейсу, реалізацію за ним можна **підставляти ззовні** — і клієнт цього не відчує. З одного контракту виростає ціла родина взаємозамінних механізмів.

![Клієнт угорі знає лише інтерфейс SensorReader (float read, bool ok); від інтерфейсу пунктиром униз ідуть три реалізації — FakeSensor (стале число, для тесту), I2cSensor (читає по шині), FileSensor (бере з файлу); підміна реалізації не чіпає клієнта](/book/programming/software-design/interface-vs-implementation/img/one-interface-many.svg)

*Клієнт тримається за єдину обіцянку вгорі. Під нею три різні нутрощі виконують той самий контракт: підробка для тесту, справжній давач, відтворення із запису. Підміна будь-якого не чіпає клієнта — бо клієнт ніколи не знав механізму, лише обіцянку.*

Ця взаємозамінність — не приємний бонус, а робочий інструмент, з якого виростає кілька щоденних практик. **Тестування** стає легким: у тесті підставляєш `FakeSensor`, який повертає передбачуване число, і перевіряєш логіку без справжнього заліза. **Розвиток паралельно**: одна людина пише клієнта проти інтерфейсу, друга — реалізацію, і вони не блокують одне одного, бо домовилися лише про обіцянку. **Заміна постачальника**: перейшли з однієї бібліотеки шифрування на іншу — переписали одну реалізацію за спільним інтерфейсом, решта системи не помітила.

> 🔧 **Навіщо це.** «Підстав підробку в тесті» — це те, без чого прошивку майже неможливо тестувати на звичайному комп'ютері. Реальний давач вимагає реального заліза, шини, часом самого фізичного явища (нагрій, щоб перевірити реакцію на 80 °C). Але якщо код залежить від інтерфейсу `SensorReader`, а не від конкретного `I2cSensor`, тест підставляє `FakeSensor`, який «віддає» будь-яку температуру за командою, — і вся логіка реакції на перегрів перевіряється за секунди на робочому столі, без паяльника й термокамери.

Це саме той механізм, який на рівні великих модулів звуть **інверсією залежностей**: замість того щоб код високого рівня знав конкретну низькорівневу деталь, обидва спираються на спільний інтерфейс, а конкретну реалізацію підставляють ззовні. Хто хоче побачити, як цей прийом перевертає напрямок залежностей у цілій архітектурі, знайде його в окремому [принципі інверсії залежностей (DIP)](book:programming/dependency-inversion). А коли всю систему будують так, що її ядро говорить лише інтерфейсами-«портами», а конкретні реалізації-«адаптери» під'єднують зовні, виходить [архітектура портів і адаптерів](book:programming/hexagonal-architecture) — той самий поділ, доведений до форми всього застосунку.

## Де саме провести лінію

Досі ми говорили, ніби лінія вже проведена. Але провести її — і є найважче й найвідповідальніше рішення дизайну, бо помилка в обидва боки дорога.

Проведеш лінію **надто високо** — і в обіцянку протече те, що мало лишитися прихованим. Класичний приклад: інтерфейс, що повертає не просто «значення», а конкретну структуру бази даних, або обіцяє порядок елементів, який насправді є випадковим наслідком нинішньої реалізації. Клієнти непомітно починають спиратися на цю деталь — і тепер ти не можеш її змінити, не зламавши їх. Лінія формально є, але вона в неправильному місці: приховане просочилося в обіцянку. Це називають **дірявою абстракцією** — обіцянка, крізь яку видно нутрощі, і клієнти встигають за них зачепитися.

Проведеш **надто низько** — і обіцянка стане такою вузькою, що нею неможливо користуватися: клієнт мусить сам робити половину роботи, яку інтерфейс мав узяти на себе. Крайність — узагалі не мати лінії: усе публічне, будь-хто лізе в будь-чиї поля напряму. Тоді кожна зміна будь-якої деталі — потенційний злам будь-де. Це вже не дизайн, а суцільна поверхня зіткнення.

Правильне питання, що ставить лінію на місце, дав ще Девід Парнас у 1972 році: розкладати систему треба **не** за кроками того, що вона робить, а за **рішеннями, які найімовірніше зміняться** — і кожне таке рішення ховати за інтерфейсом. Обіцяй те, що стабільне; ховай те, що мінливе. Ця думка — прямий корінь [приховування інформації](book:programming/information-hiding): модуль тим кращий, чим більше **важких-до-зміни рішень** він сховав від решти. Історію того, як народилися і сам поділ, і слово «непрозорий тип» — від статті Парнаса до абстрактних типів даних Барбари Лісков — зібрано окремо: [як з'явилися інтерфейс і реалізація](book:programming/interface-vs-implementation/hist-parnas-liskov.md).

Той самий критерій «що ховати» — це водночас критерій **зв'язності й зчеплення**: добре проведена лінія дає модулю високу зв'язність усередині й слабке зчеплення з сусідами. Точну мову для вимірювання цієї якості дає окрема тема про [зчеплення і зв'язність](book:programming/coupling-cohesion) — вона й пояснює, чому саме вдалий поділ на інтерфейс і реалізацію робить систему дешевою в супроводі.

## Обіцянка — це поведінка, а не лише підпис

Тут криється пастка, на якій спотикаються навіть досвідчені. Легко подумати, що інтерфейс — це рівно сигнатури функцій: імена, типи аргументів, тип результату. Але справжня обіцянка **ширша за підпис**. Вона включає поведінку, яку клієнт має право очікувати: що функція `pop` на порожньому стеку робить (кидає помилку? повертає ознаку?), у яких межах результат коректний, чи міняє виклик щось поза собою.

Розгляньмо `SensorReader::read()`. Підпис каже лише «повертає `float`». Але клієнт покладається й на неписане: що число — це температура в градусах Цельсія, а не Фаренгейта; що при збої давача повертається щось розпізнаване, а не сміття. Якщо одна реалізація віддає Цельсій, а інша — Фаренгейт, обидві **задовольняють підпис** і обидві **порушують обіцянку** — і клієнт, написаний під одну, тихо ламається на другій. Тому підміна реалізації безпечна лише тоді, коли нова реалізація виконує **всю** обіцянку, включно з поведінкою, а не самі типи.

Правило, що це формалізує, каже: підтип має бути **справжньою заміною** свого інтерфейсу — усюди, де очікують інтерфейс, будь-яка його реалізація мусить поводитися сумісно, не порушуючи очікувань клієнта. Це і є [поведінкова підтипізація](book:programming/behavioral-subtyping) — точна умова, за якої «одна обіцянка, багато нутрощів» справді працює, а не лише вдає, що працює. Саме тому обіцянку варто фіксувати явно — не лише в типах, а й у документації та тестах контракту, які перевіряють поведінку, спільну для всіх реалізацій.

## Лінія не безкоштовна

Наостанок — застереження, без якого поділ перетворюється на догму. **Кожна лінія має ціну.** Абстрактний клас із віртуальними викликами коштує зайвого непрямого стрибка на кожному виклику; щоб зрозуміти, що саме виконається, треба знати, яку реалізацію підставили, — код стає трохи менш очевидним для читання. Непрозорий вказівник вимагає окремого виділення пам'яті й функцій-конструкторів там, де могла б бути проста структура на стеку.

Тому лінію проводять там, де вона **окупається** — де реалізація справді колись зміниться або де взаємозамінність справді потрібна (тест, кілька постачальників, кілька платформ). Ставити повноцінний інтерфейс із родиною реалізацій там, куди зміна ніколи не прийде і де реалізація буде рівно одна, — це заплатити за гнучкість, якою ніхто не скористається. Це прямо перегукується з [YAGNI](book:programming/dry-kiss-yagni): не абстрагуй наперед того, чого ще не потребуєш. Спершу простий прямий код; лінію проводиш, коли з'явилася **друга** реалізація або реальна потреба її підставляти, — тоді вже видно, де саме її провести й що обіцяти.

Поділ на інтерфейс і реалізацію живучий тому, що він, по суті, — **інструмент спілкування** між людьми, розділеними часом і роллю. Інтерфейс — це те, що ти обіцяєш іншому програмістові (часто — собі за півроку): «на це можеш покладатися, воно не зміниться». Реалізація — це те, що ти лишаєш собі: «а тут я вільний, і ти не маєш на це дивитися». Поки код пишуть і читають люди зі скінченною головою, ця лінія лишатиметься головним способом сказати «ось цю обіцянку тримай, а решту — забудь» — і саме вона перетворює купу коду на систему, яку можна міняти, не боячись, що вона розсиплеться.
