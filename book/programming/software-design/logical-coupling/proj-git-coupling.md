# ⚙️ Детектор еволюційного зачеплення: аналіз журналу Git

Автоматичний пошук неявних залежностей у кодовій базі починається зі зчитування структурованого логу комітів і побудови матриці парних переходів між зміненими файлами. Без спеціалізованого аналізатора розробники дізнаються про приховане зачеплення лише постфактум — коли зміна одного модуля ламає інший у продакшені.

Утиліти статичного аналізу аналізують лише моментальний зріз файлової системи: вони будують абстрактні синтаксичні дерева (AST), перевіряють типи аргументів та відстежують директиви імпорту. Проте вони принципово не здатні зафіксувати залежності, засновані на неявних домовленостях, розмазаних константах або несинхронізованих бізнес-правилах.

Інструмент розв'язує конкретне інженерне завдання: перетворити потік виводу команди `git log` на структурований звіт про еволюційне зачеплення, відфільтрувати інформаційний шум (масові рефакторинги, оновлення сторонніх бібліотек, злиття гілок) та розрахувати для кожної пари файлів метрики підтримки (Support), впевненості (Confidence) та коефіцієнта Жаккара (Jaccard Index).

## Архітектура та конвеєр обробки даних

Аналізатор реалізує потоковий конвеєр низького навантаження на пам'ять, здатний обробляти репозиторії з сотнями тисяч комітів за лічені секунди.

```
+------------------+      +--------------------+      +----------------------+      +--------------------+
|  git log потік   | ---> |  Фільтр транзакцій | ---> |  Акумулятор парних   | ---> |  Ранжування та     |
|  (парсинг рядків)|      |  (поріг шуму N<50) |      |  частот (Hash Map)   |      |  звіт (CSV / Text) |
+------------------+      +--------------------+      +----------------------+      +--------------------+
```

### 1. Формат вхідного потоку та генерація журналу

Для мінімізації накладних витрат аналізатор не використовує важкі бібліотеки на кшталт `libgit2` для повного обходу об'єктної бази Git, а споживає текстовий потік стандартної утиліти `git log`. 

Використовується формат виклику:

```bash
git log --no-merges --name-only --pretty=format:"COMMIT:%H|%at"
```

Кожен коміт у цьому потоці починається з унікального рядка-маркера з префіксом `COMMIT:`, після якого через вертикальну риску вказано SHA-1 хеш коміту та час у форматі Unix Timestamp. Наступні рядки містять відносні шляхи до файлів, які зазнали модифікації в рамках цієї транзакції, аж до наступного рядка-маркера або кінця файлу.

Прапорець `--no-merges` має фундаментальне значення: коміти злиття гілок містять штучне об'єднання змін десятків незалежних розробників за тривалий час. Якщо їх не виключити, аналізатор зафіксує псевдозачеплення між усіма файлами, зміненими в паралельних гілках.

### 2. Правила фільтрації та очищення від шуму

У реальних проєктах понад 70% парних зв'язків у сирому лозі є випадковим шумом. Для забезпечення достовірності результатів інструмент застосовує чотири рівні фільтрації:

* **Нижній поріг транзакції:** якщо коміт торкається лише одного файлу (`count < 2`), він не містить міжфайлових зв'язків і пропускається.
* **Верхній поріг транзакції (Churn Threshold):** якщо коміт змінює понад `MAX_FILES_THRESHOLD` файлів (за замовчуванням 50), він класифікується як масове автоматичне редагування (наприклад, запуск автоформатування коду, глобальна зміна ліцензійних шапок або міграція структури каталогів). Включення такого коміту додало б у граф `N · (N - 1) / 2 = 1225` фальшивих ребер, що миттєво зруйнувало б статистику.
* **Фільтрація за розширеннями:** бінарні ресурси, документація (`.md`, `.pdf`), зображення та автоматично згенеровані файли блокування залежностей (`package-lock.json`, `Cargo.lock`, `go.sum`) виключаються з обробки, оскільки вони не несуть архітектурної семантики вихідного коду.
* **Мінімальний поріг підтримки (Min Support):** пари файлів, які зустрілися разом менше ніж `MIN_CO_CHANGES` разів (зазвичай 2 або 3), не потрапляють у фінальний звіт, щоб виключити разові випадкові збіги.

### 3. Алгоритм накопичення пар та структура даних

Для кожного валідного коміту, що містить відсортовану та дедупліковану множину файлів `{f[1], f[2], ..., f[k]}`:
* Збільшується лічильник індивідуальної активності кожного файлу `N[f[i]]`.
* Формуються всі невпорядковані пари `(f[i], f[j])`, де `i < j`.
* Лексикографічне сортування імен файлів гарантує, що пари `(A, B)` та `(B, A)` відображаються в один і той самий канонічний ключ хеш-таблиці.
* Для кожної пари збільшується лічильник спільних змін `N[f[i], f[j]]`.

## Реалізація аналізатора

Нижче наведено повноцінний робочий аналізатор історії Git двома мовами: ефективна системна реалізація мовою C та ідіоматична об'єктно-орієнтована версія мовою C++ з використанням стандартних контейнерів та потоків введення-виведення.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define MAX_LINE 1024
#define MAX_FILES_PER_COMMIT 64
#define MAX_PAIRS 65536
#define MAX_UNIQUE_FILES 8192

typedef struct {
    char name[256];
    int commit_count;
} FileEntry;

typedef struct {
    int file_a;
    int file_b;
    int co_change_count;
} PairEntry;

static FileEntry g_files[MAX_UNIQUE_FILES];
static int g_file_count = 0;

static PairEntry g_pairs[MAX_PAIRS];
static int g_pair_count = 0;

static int get_or_add_file(const char* name) {
    for (int i = 0; i < g_file_count; i++) {
        if (strcmp(g_files[i].name, name) == 0) return i;
    }
    if (g_file_count >= MAX_UNIQUE_FILES) return -1;
    strncpy(g_files[g_file_count].name, name, sizeof(g_files[0].name) - 1);
    g_files[g_file_count].name[sizeof(g_files[0].name) - 1] = '\0';
    g_files[g_file_count].commit_count = 0;
    return g_file_count++;
}

static void add_co_change(int id_a, int id_b) {
    if (id_a > id_b) { int t = id_a; id_a = id_b; id_b = t; }
    for (int i = 0; i < g_pair_count; i++) {
        if (g_pairs[i].file_a == id_a && g_pairs[i].file_b == id_b) {
            g_pairs[i].co_change_count++;
            return;
        }
    }
    if (g_pair_count < MAX_PAIRS) {
        g_pairs[g_pair_count].file_a = id_a;
        g_pairs[g_pair_count].file_b = id_b;
        g_pairs[g_pair_count].co_change_count = 1;
        g_pair_count++;
    }
}

static void process_commit_files(int* ids, int count) {
    if (count < 2 || count > MAX_FILES_PER_COMMIT) return;
    for (int i = 0; i < count; i++) {
        g_files[ids[i]].commit_count++;
    }
    for (int i = 0; i < count; i++) {
        for (int j = i + 1; j < count; j++) {
            if (ids[i] != ids[j]) {
                add_co_change(ids[i], ids[j]);
            }
        }
    }
}

static int compare_pairs(const void* a, const void* b) {
    const PairEntry* pa = (const PairEntry*)a;
    const PairEntry* pb = (const PairEntry*)b;
    return pb->co_change_count - pa->co_change_count;
}

int main(void) {
    char line[MAX_LINE];
    int current_commit_files[MAX_FILES_PER_COMMIT];
    int commit_file_count = 0;
    int total_commits = 0;

    while (fgets(line, sizeof(line), stdin)) {
        size_t len = strlen(line);
        while (len > 0 && (line[len - 1] == '\n' || line[len - 1] == '\r')) line[--len] = '\0';
        if (len == 0) continue;

        if (strncmp(line, "COMMIT:", 7) == 0) {
            if (commit_file_count > 0) {
                process_commit_files(current_commit_files, commit_file_count);
                commit_file_count = 0;
                total_commits++;
            }
        } else {
            if (commit_file_count < MAX_FILES_PER_COMMIT) {
                int fid = get_or_add_file(line);
                if (fid >= 0) {
                    current_commit_files[commit_file_count++] = fid;
                }
            }
        }
    }
    if (commit_file_count > 0) {
        process_commit_files(current_commit_files, commit_file_count);
        total_commits++;
    }

    qsort(g_pairs, g_pair_count, sizeof(PairEntry), compare_pairs);

    printf("=== ТОП ПАР ІЗ ЛОГІЧНИМ ЗАЧЕПЛЕННЯМ (Всього транзакцій: %d) ===\n", total_commits);
    printf("%-35s %-35s %6s %8s %8s %8s\n", "Файл A", "Файл B", "Спільні", "Conf A->B", "Conf B->A", "Jaccard");
    
    for (int i = 0; i < g_pair_count && i < 20; i++) {
        if (g_pairs[i].co_change_count < 2) continue;
        int fa = g_pairs[i].file_a;
        int fb = g_pairs[i].file_b;
        int n_ab = g_pairs[i].co_change_count;
        int n_a = g_files[fa].commit_count;
        int n_b = g_files[fb].commit_count;
        
        double conf_ab = (double)n_ab / n_a * 100.0;
        double conf_ba = (double)n_ab / n_b * 100.0;
        double jaccard = (double)n_ab / (n_a + n_b - n_ab) * 100.0;

        printf("%-35.35s %-35.35s %6d %7.1f%% %7.1f%% %7.1f%%\n",
               g_files[fa].name, g_files[fb].name, n_ab, conf_ab, conf_ba, jaccard);
    }
    return 0;
}
```

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <vector>
#include <unordered_map>
#include <algorithm>
#include <iomanip>

struct PairKey {
    std::string file_a;
    std::string file_b;

    bool operator==(const PairKey& other) const {
        return file_a == other.file_a && file_b == other.file_b;
    }
};

struct PairKeyHash {
    std::size_t operator()(const PairKey& k) const {
        std::size_t h1 = std::hash<std::string>{}(k.file_a);
        std::size_t h2 = std::hash<std::string>{}(k.file_b);
        return h1 ^ (h2 << 1);
    }
};

struct AnalysisResult {
    std::string file_a;
    std::string file_b;
    int co_changes;
    double confidence_a_to_b;
    double confidence_b_to_a;
    double jaccard;
};

class GitCouplingDetector {
public:
    static constexpr int MAX_FILES_THRESHOLD = 50;

    void process_stream(std::istream& in) {
        std::string line;
        std::vector<std::string> current_commit;

        while (std::getline(in, line)) {
            while (!line.empty() && (line.back() == '\r' || line.back() == ' ')) {
                line.pop_back();
            }
            if (line.empty()) continue;

            if (line.rfind("COMMIT:", 0) == 0) {
                flush_commit(current_commit);
                current_commit.clear();
                total_commits_++;
            } else {
                current_commit.push_back(line);
            }
        }
        flush_commit(current_commit);
    }

    std::vector<AnalysisResult> compute_metrics(int min_co_changes = 2) const {
        std::vector<AnalysisResult> results;
        for (const auto& [pair, count] : pair_counts_) {
            if (count < min_co_changes) continue;

            int n_a = file_counts_.at(pair.file_a);
            int n_b = file_counts_.at(pair.file_b);

            double conf_ab = static_cast<double>(count) / n_a * 100.0;
            double conf_ba = static_cast<double>(count) / n_b * 100.0;
            double jaccard = static_cast<double>(count) / (n_a + n_b - count) * 100.0;

            results.push_back({pair.file_a, pair.file_b, count, conf_ab, conf_ba, jaccard});
        }

        std::sort(results.begin(), results.end(), [](const auto& lhs, const auto& rhs) {
            return lhs.jaccard > rhs.jaccard;
        });

        return results;
    }

    int total_commits() const { return total_commits_; }

private:
    void flush_commit(std::vector<std::string>& files) {
        if (files.size() < 2 || files.size() > MAX_FILES_THRESHOLD) return;

        std::sort(files.begin(), files.end());
        files.erase(std::unique(files.begin(), files.end()), files.end());

        for (const auto& f : files) {
            file_counts_[f]++;
        }

        for (std::size_t i = 0; i < files.size(); ++i) {
            for (std::size_t j = i + 1; j < files.size(); ++j) {
                PairKey key{files[i], files[j]};
                pair_counts_[key]++;
            }
        }
    }

    int total_commits_ = 0;
    std::unordered_map<std::string, int> file_counts_;
    std::unordered_map<PairKey, int, PairKeyHash> pair_counts_;
};

int main() {
    GitCouplingDetector detector;
    detector.process_stream(std::cin);

    auto results = detector.compute_metrics(2);

    std::cout << "=== ТОП ПАР ІЗ ЛОГІЧНИМ ЗАЧЕПЛЕННЯМ (Всього транзакцій: " 
              << detector.total_commits() << ") ===\n";
    std::cout << std::left << std::setw(35) << "Файл A" 
              << std::setw(35) << "Файл B" 
              << std::right << std::setw(8) << "Спільні" 
              << std::setw(11) << "Conf A->B" 
              << std::setw(11) << "Conf B->A" 
              << std::setw(10) << "Jaccard" << "\n";

    for (std::size_t i = 0; i < std::min<std::size_t>(results.size(), 20); ++i) {
        const auto& r = results[i];
        std::cout << std::left << std::setw(35) << r.file_a.substr(0, 34)
                  << std::setw(35) << r.file_b.substr(0, 34)
                  << std::right << std::setw(8) << r.co_changes
                  << std::fixed << std::setprecision(1)
                  << std::setw(10) << r.confidence_a_to_b << "%"
                  << std::setw(10) << r.confidence_b_to_a << "%"
                  << std::setw(9) << r.jaccard << "%\n";
    }

    return 0;
}
```

## Інженерний аналіз складності та оптимізація пам'яті

Під час аналізу великих репозиторіїв (понад 100 000 комітів та десятки тисяч вихідних файлів) ключовим фактором стає ефективність використання процесорного часу та пам'яті:

1. **Часова складність алгоритму:**
   Нехай `C` — загальна кількість комітів, а `k_i` — кількість змінених файлів у `i`-му коміті.
   Обробка одного коміту вимагає генерації `k_i · (k_i - 1) / 2` парних комбінацій. Завдяки обмеженню верхнього порогу `k_i ≤ MAX_FILES_THRESHOLD = 50`, кількість операцій на один коміт обмежена константою `O(1)` з верхньою межею `1225` оновлень хеш-таблиці.
   Загальна часова складність парсингу є лінійною відносно довжини журналу: `O(C)`. Фінальне сортування результатів вимагає `O(P · log P)`, де `P` — кількість унікальних пар.

2. **Просторова складність та розміщення в пам'яті:**
   * У C-реалізації використовується статичний пул фіксованого розміру `MAX_PAIRS = 65536`. Кожен запис `PairEntry` займає 12 байтів (два 32-бітні цілі індекси та 32-бітний лічильник). Загальний обсяг пам'яті під пари становить менше ніж 1 мегабайт, що гарантує високу локальність даних та ідеальне розміщення в L2/L3 кешах сучасних процесорів.
   * У C++-реалізації `std::unordered_map` динамічно виділяє пам'ять під вузли, що забезпечує необмежену масштабованість для проєктів будь-якого розміру за рахунок незначного зростання накладних витрат на покажчики вузлів списків колізій.

## Інструкція запуску та інтерпретація результатів

Для практичного використання збережіть код у файл `detector.cpp` та скомпілюйте оптимізований бінарний файл за допомогою компілятора GCC або Clang:

```bash
g++ -O3 -std=c++20 detector.cpp -o git_coupling_detector
```

Після цього передайте журнал цільового репозиторію через стандартний конвеєр shell:

```bash
git log --no-merges --name-only --pretty=format:"COMMIT:%H" | ./git_coupling_detector
```

### Аналіз практичного виводу

Розглянемо типовий звіт, отриманий під час аудиту розподіленого моноліту електронного банкінгу:

```text
=== ТОП ПАР ІЗ ЛОГІЧНИМ ЗАЧЕПЛЕННЯМ (Всього транзакцій: 412) ===
Файл A                              Файл B                              Спільні  Conf A->B  Conf B->A   Jaccard
src/billing/tax_calc.c              src/pdf/invoice_view.c                   38      90.5%      86.4%     79.2%
src/auth/session_manager.c          src/api/auth_middleware.c                29      85.3%      72.5%     64.4%
src/models/order.c                  src/db/migrations/2026_order.c           18      31.0%      94.7%     30.5%
src/controllers/user.c              src/views/user_profile.c                 12      40.0%      42.8%     26.0%
```

### Інженерний розбір знайдених аномалій

1. **Критичне симетричне зачеплення: `tax_calc.c ↔ invoice_view.c`**
   * *Метрики:* `Jaccard = 79.2%`, `Confidence(A → B) = 90.5%`, `Confidence(B → A) = 86.4%`.
   * *Діагноз:* Файли знаходяться в різних підсистемах (`billing` та `pdf`), формально не імпортують один одного і не мають спільних типів. Проте у 9 із 10 випадків зміна правил нарахування податків вимагала синхронної правки шаблону генерації PDF.
   * *Корінна причина:* Правила заокруглення копійок та логіка виділення податкових ставок дублювалися в обох модулях.
   * *Архітектурне лікування:* Виділення незмінного об'єкта `InvoiceSnapshotDTO`, який інкапсулює всі розраховані суми. Генератор PDF перетворюється на чистого рендерера готових текстових полів, позбавленого будь-якої арифметичної логіки.

2. **Несиметрична залежність: `order.c ↔ migrations/2026_order.c`**
   * *Метрики:* `Confidence(B → A) = 94.7%`, `Confidence(A → B) = 31.0%`.
   * *Діагноз:* Кожна міграція структури таблиці бази даних супроводжувалася зміною структури C-моделі `order.c` (94.7%). Проте зворотна впевненість складає лише 31%, оскільки більшість змін у `order.c` стосуються методів бізнес-валідації і не змінюють схему збереження.
   * *Висновки:* Це природне, здорове зачеплення між реляційною схемою та моделлю домену. Воно не вимагає архітектурного втручання.

## Виявлення міжсервісного зачеплення в монорепозиторіях

У великих монорепозиторіях аналізу на рівні окремих файлів часто недостатньо: архітектору необхідно бачити зачеплення між цілими підсистемами або мікросервісами.

Для цього шлях до кожного файлу проєктується на відповідний сервісний простір імен:

```
src/services/billing/handlers/tax.c   --->  [Service: billing]
src/services/pdf/render/invoice.c     --->  [Service: pdf]
```

Якщо агрегований коефіцієнт `Jaccard(Service_A, Service_B) ≥ 40%`, це вказує на **розподілений моноліт (англ. *distributed monolith*)**: сервіси розгорнуті як окремі процеси, але бізнес-логіка вимагає їхньої одночасної модифікації та узгодженого деплою (Lockstep Deployments).

## Обчислення архітектурних гарячих точок (Hotspot Scoring)

Саме по собі еволюційне зачеплення не завжди є критичною проблемою, якщо файли змінюються рідко і містять просту лінійну логіку. Справжня загроза для стабільності виникає тоді, коли зачеплення накладається на високу частоту змін та внутрішню заплутаність коду.

Для пріоритизації рефакторингу інструмент обчислює інтегральний показник критичності **Hotspot Score**:

```
HotspotScore(A, B)
= Jaccard(A, B) · log2(N[A, B] + 1) · (Complexity(A) + Complexity(B))
```

де `Complexity` — цикломатична складність за Маккейбом або кількість рядків коду (SLOC). 

Пари з найвищим індексом `HotspotScore` очолюють беклог архітектурного рефакторингу: їхнє розчеплення дає максимальний економічний ефект у скороченні кількості регресійних помилок.

## Аналіз часової динаміки: ковзні вікна проти повної історії

Репозиторії, які розвиваються роками, містять нашарування різних архітектурних епох. Зачеплення, яке було критичним два роки тому, могло бути успішно усунене рефакторингом три місяці тому. Якщо аналізувати всю історію від першого коміту, застарілі зв'язки продовжуватимуть створювати помилкові спрацьовування.

Щоб оцінити реальний поточний стан системи, рекомендується виконувати порівняльний аналіз у двох часових масштабах:
1. **Глобальний аналіз (останні 12–24 місяці):** виявляє фундаментальні структурні вади та довгострокові тенденції кодової бази.
2. **Локальний ковзний зріз (останні 3 місяці або останні 500 комітів):** відображає поточну активність команди та дозволяє оцінити, чи дав проведений рефакторинг бажаний ефект розчеплення компонентів.

Якщо показник `Jaccard(A, B)` у глобальному зрізі складав 75%, а в локальному тримісячному зрізі впав до 10%, це є числовим доказом успішного архітектурного розв'язання проблеми.

## Зачеплення між тестами та продакшен-кодом (Test Coupling Smell)

Окремим випадком еволюційного аналізу є дослідження зв'язку між файлами реалізації та їхніми автотестами (`*.c ↔ *_test.c`).

* **Здорове зачеплення:** додавання нового бізнес-методу у функціональний модуль вимагає додавання відповідного тестового сценарію. Тут `Confidence(Impl → Test) ≈ 70–90%` є показником високої дисципліни тестування.
* **Патологічне зачеплення (Fragile Tests):** якщо `Confidence(Impl → Test) = 100%` та `Confidence(Test → Impl) = 100%`, і при цьому будь-який внутрішній рефакторинг (наприклад, зміна імені приватної змінної або оптимізація алгоритму без зміни публічного API) змушує переписувати тести — тести надмірно зачеплені за деталі реалізації (Mock-Heavy / White-box Smell).
* **Архітектурне лікування:** переписування тестів на рівні контрактів чорної скриньки (Black-Box Contract Testing), де тест взаємодіє виключно через публічний інтерфейс модуля і не залежить від його внутрішньої будови.

## Практичні шаблони розв'язання виявленого зачеплення

Після виявлення пари з критичним зачепленням архітектор застосовує один із трьох перевірених шаблонів рефакторингу:

### Шаблон 1: Розмазані магічні константи та коди статусів
* **Симптом:** Зміна числового коду статусу замовлення в бекенді ламає фільтрацію у звітах та відображення в інтерфейсі.
* **Рішення:** Створення спільного заголовочного файлу або схеми з типізованим переліком (Enum) та єдиною таблицею текстових назв. Всі модулі посилаються на спільний тип через компільований контракт.

### Шаблон 2: Дзеркальні валідації вхідних даних
* **Симптом:** Правила перевірки формату номера паспорта або пароля дублюються на клієнті (JavaScript) та на сервері (C/C++). Кожна зміна бізнес-вимоги вимагає синхронного коміту в обох репозиторіях.
* **Рішення:** Перехід на декларативні схеми валідації (JSON Schema, OpenAPI). Клієнтський та серверний код генерують валідатори автоматично з єдиного файлу схеми під час збірки.

### Шаблон 3: Розірваний бізнес-інваріант (Temporal Coupling)
* **Симптом:** Для збереження замовлення клієнтський код змушений послідовно викликати три методи: `reserve_stock()`, `charge_card()`, `create_order()`. Якщо бізнес додає четвертий крок `send_receipt()`, модифікуються всі виклики по системі.
* **Рішення:** Об'єднання методів усередину єдиного агрегата або фасаду (`process_checkout()`), який виконує всі кроки як єдину атомарну бізнес-операцію.

## Соціотехнічний аналіз та узгодженість команд

Якщо доповнити вхідний потік команди `git log` інформацією про авторів комітів (`git log --pretty=format:"COMMIT:%H|%an"`), аналізатор отримує можливість будувати матрицю командного зачеплення.

Згідно із Законом Конвея, програмні інтерфейси копіюють комунікаційні структури організацій. Якщо два модулі з `Jaccard ≥ 70%` розробляються двома різними командами:
* Час узгодження змін зростає в кілька разів;
* Зростає ймовірність конфліктів злиття (Merge Conflicts) під час інтеграції гілок;
* Виникає синдром «не мого коду», коли дефекти списуються на суміжний підрозділ.

Виявлення міжкомандного еволюційного зачеплення є прямим сигналом для керівництва щодо реорганізації меж володіння кодом (Inverse Conway Maneuver): або об'єднати обидва модулі під відповідальністю однієї команди, або формалізувати контракт між ними через версіонований API.

## Крайові випадки та фільтрація артефактів Git

Практичний аналіз реальних репозиторіїв зіштовхується з низкою специфічних сценаріїв, які вимагають коректного налаштування інструменту:

### 1. Перейменування файлів та розрив історії
Якщо файл було перейменовано без прапорця відстеження (`git log -M`), Git реєструє це як видалення старого файлу та створення нового. Для аналізатора старе і нове ім'я виглядають як дві незалежні сутності, що штучно розриває історію накопичення зачеплення. Для довгоживучих проєктів рекомендується генерувати лог із прапорцем `git log -M90%` або попередньо будувати карту відповідності старих і нових імен за історією дерева ревізій.

### 2. Squashed Commits та злиття через PR
У багатьох командах прийнято стискати всі коміти функціональної гілки в один результуючий коміт (Squash Merge) під час прийняття Pull Request. 
* *Плюс:* коміт стає повністю атомарним, фіксуючи повний обсяг змін, необхідних для реалізації бізнес-вимоги.
* *Мінус:* якщо PR містив кілька незв'язаних задач (наприклад, реалізацію функції оплати та попутне виправлення кнопки в інтерфейсі), вони опиняються в одній транзакції, створюючи одиничний фальшивий зв'язок. Фільтр `MIN_CO_CHANGES ≥ 3` надійно нівелює такі поодинокі збіги.

### 3. Автоматично згенерований код
Файли, згенеровані компіляторами схем (Protocol Buffers, gRPC, Thrift, OpenAPI Generator), завжди потрапляють у коміт разом із файлом вихідної схеми `.proto` або `.yaml`. 
Їхня наявність у звіті є тривіальною та не несе нової архітектурної інформації. Рекомендується додавати фільтр префіксів/розширень:

```bash
git log --no-merges --name-only --pretty=format:"COMMIT:%H" \
  | grep -vE "\.pb\.|\.generated\.|/vendor/|/third_party/" \
  | ./git_coupling_detector
```

## Інтеграція в конвеєри CI/CD як архітектурний фітнес-тест

Еволюційне зачеплення стає потужним інструментом контролю якості, якщо інтегрувати його у процес автоматизованого тестування (Architectural Fitness Functions).

У конвеєрі перевірки Pull Request утиліта виконує перевірку за таким алгоритмом:
1. Отримує список змінених файлів у поточному PR:
   ```bash
   CHANGED_FILES=$(git diff --name-only origin/main...HEAD)
   ```
2. Для кожного зміненого файлу шукає в історичній матриці партнерів із `Confidence ≥ 80%` та `Support ≥ 5`.
3. Якщо партнер присутній у базі зачеплень, але відсутній у поточному PR, збірка видає попередження:
   ```text
   WARNING: File src/billing/tax_calc.c is modified, but historically coupled src/pdf/invoice_view.c (Confidence 90.5%) was omitted!
   ```
4. Розробник або додає необхідні зміни, або явно підтверджує, що контракт не зазнав порушень.

Така автоматизація ліквідує цілий клас регресійних дефектів ще на етапі створення коду, перетворюючи накопичену історію репозиторію на активний інструмент захисту архітектурної цілісності системи. Багато команд також зберігають кеш підрахованих пар у сховищі CI/CD і щоденно оновлюють його інкрементально, а також генерують інтерактивні теплові карти зачеплення (Heatmaps) як артефакт нічної збірки, що дає змогу архітекторам візуально спостерігати за зниженням міжмодульного тертя в ході планових ітерацій рефакторингу.
