# 🧮 Метрики еволюційного зачеплення: асоціативні правила та кореляція в часі

Щоб відрізнити випадковий збіг у коміті від стійкої архітектурної залежності двох модулів, статистичний аналіз спирається на апарат транзакцій та теорію асоціативних правил (англ. *association rule learning*). Без математично строгої фільтрації будь-який масовий коміт (наприклад, зміна копірайту в заголовках) створить ілюзію тотального зачеплення всієї кодової бази.

Математичний аналіз еволюції коду вирішує фундаментальне завдання: оцінити ступінь статистичного зв'язку між модифікаціями окремих файлів або функцій у просторі дискретних транзакцій системи контролю версій.

## Транзакційна модель репозиторію

Репозиторій розглядається як послідовність транзакцій `T`, де кожна транзакція є дискретним комітом `C[k]`:

```
T = {C[1], C[2], C[3], ..., C[N]}
```

Кожен коміт `C[k]` є підмножиною множини всіх файлів системи `F = {f[1], f[2], ..., f[M]}`. Якщо під час фіксації змін розробник змінив файли `A` та `B`, ми записуємо:

```
{A, B} ⊆ C[k]
```

Загальна кількість комітів у вибірці позначається як `|T| = N`. Кількість комітів, у яких фігурує файл `A`, позначається як `N[A]`, а кількість комітів, де файли `A` та `B` модифіковано одночасно в рамках однієї транзакції, — як `N[A, B]`.

Ця формалізація перетворює історію версій на розріджену бінарну матрицю розмірності `N × M`, де кожен рядок відповідає коміту, а кожен стовпчик — файлу в кодовій базі. Одиничне значення на перетині означає, що відповідний файл зазнав змін у цій транзакції.

## 1. Підтримка (Support): абсолютна частота спільної зміни

**Підтримка (англ. *Support*)** вимірює частку транзакцій у репозиторії, які містять спільну зміну пари файлів `(A, B)`. Вона показує емпіричну ймовірність того, що випадково обраний коміт із репозиторію міститиме правки в обох компонентах.

Для пари файлів `(A, B)` підтримка визначається як відношення кількості спільних комітів до загальної кількості комітів у системі:

```
Support(A, B)
= N[A, B] / N      [частка транзакцій зі спільною зміною файлів A та B]
```

Для окремого файлу `A` підтримка дорівнює:

```
Support(A)
= N[A] / N         [частка транзакцій, що містять модифікацію файлу A]
```

Підтримка — це симетрична величина: `Support(A, B) = Support(B, A)`. Значення належить числовому проміжку від 0 до 1.

> ⚠️ **Обмеження підтримки:** у великих репозиторіях із тисячами файлів абсолютна підтримка навіть критично зачеплених компонентів може бути низькою (наприклад, 0.02 або 2%), оскільки паралельно розробляються десятки інших підсистем. Тому підтримка використовується не як самостійний вирок, а як фільтр мінімальної статистичної значущості (англ. *minimum support threshold*): пари з `N[A, B] < 3` відкидаються, щоб уникнути шуму випадкових одиничних правок.

## 2. Впевненість / Достовірність (Confidence): спрямована ймовірність зачеплення

**Впевненість (англ. *Confidence*)** визначає умовну ймовірність того, що модифікація файлу `A` спричинить необхідність модифікації файлу `B`. На відміну від підтримки, впевненість є **несиметричною** метрикою, що відображає спрямованість залежності.

Математично впевненість правила `A → B` визначається як відношення кількості спільних змін до кількості всіх змін файлу `A`:

```
Confidence(A → B)
= P(B ∈ C | A ∈ C)       [умовна ймовірність присутності B за умови присутності A]
= Support(A, B) / Support(A)
= N[A, B] / N[A]         [спрощення: скорочення загальної кількості комітів N]
```

Аналогічно, зворотна впевненість для правила `B → A` дорівнює:

```
Confidence(B → A)
= N[A, B] / N[B]         [частка комітів файлу B, що також зачепили файл A]
```

### Довірчі інтервали для малих вибірок (Wilson Score Interval)

Якщо файл `A` змінювався лише `N[A] = 3` рази і всі 3 рази разом із `B`, то точкова оцінка дає `Confidence(A → B) = 1.0` (100%). Проте через малий обсяг вибірки статистична невизначеність є вкрай високою.

Для надійної фільтрації використовується нижня межа довірчого інтервалу Вільсона (Wilson Score Interval) для біноміального розподілу на рівні довіри 95%:

```
Confidence_lower(A → B)
= (p + z²/(2·n) - z · √( (p·(1-p) + z²/(4·n)) / n )) / (1 + z²/n)
```

де `p = N[A, B] / N[A]`, `n = N[A]`, а `z = 1.96` для 95%-го довірчого інтервалу. Якщо нижня межа інтервалу `Confidence_lower` перевищує встановлений поріг (наприклад, 0.60), зв'язок вважається достовірним навіть на малих вибірках.

### Асиметрія архітектурного зачеплення

Якщо `Confidence(A → B) = 0.90` (90%), а `Confidence(B → A) = 0.15` (15%), це свідчить про виражену односторонню залежність:
* Модуль `A` є клієнтом або вторинним виконавцем, який жорстко залежить від деталей реалізації `B`. Будь-яка зміна в `A` майже напевно викликана зміною в `B`.
* Модуль `B` є базовим або часто змінюваним компонентом із багатьма іншими обов'язками, лише невелика частка правок якого стосується функціоналу `A`.

Ця несиметрія має вирішальне значення для архітектора: вона вказує, який саме модуль є джерелом нестабільності (Master), а який — залежним реципієнтом (Slave).

## 3. Коефіцієнт Жаккара (Jaccard Index): симетрична міра подібності

Щоб отримати збалансовану оцінку еволюційної спорідненості двох файлів без урахування напрямку, застосовується **коефіцієнт подібності Жаккара (англ. *Jaccard Index*)**, також відомий як перетин над об'єднанням (Intersection over Union, IoU).

Коефіцієнт Жаккара для множин комітів `T[A]` та `T[B]` визначається як:

```
Jaccard(A, B)
= |T[A] ∩ T[B]| / |T[A] ∪ T[B]|
= N[A, B] / (N[A] + N[B] - N[A, B])   [формула включень-виключень для об'єднання]
```

Властивості коефіцієнта Жаккара:
* `Jaccard(A, B) = 1` тоді й лише тоді, коли файли `A` та `B` завжди змінюються виключно разом (`N[A] = N[B] = N[A, B]`). Це ознака абсолютного монолітного зачеплення.
* `Jaccard(A, B) = 0`, коли файли не мають жодної спільної зміни.
* Метрика стійка до загального розміру репозиторію `N`, оскільки враховує лише активність досліджуваної пари.

Відстань Жаккара `d_J(A, B) = 1 - Jaccard(A, B)` є повноцінною математичною метрикою, що задовольняє нерівність трикутника, і може безпосередньо використовуватися в алгоритмах кластеризації кодової бази.

## 4. Підйом (Lift): відхилення від випадкової незалежності

Коли обидва файли змінюються дуже часто (наприклад, файл журналу збірки `build.log` та головний конфіг `app.json`), їхні `Support(A, B)` та `Confidence(A → B)` можуть бути високими лише через високу частоту їх окремих змін `N[A]` та `N[B]`.

Щоб перевірити, чи є спільна поява статистично залежною подією, використовують **коефіцієнт підйому (англ. *Lift*)**:

```
Lift(A, B)
= P(A ∩ B) / (P(A) · P(B))
= Support(A, B) / (Support(A) · Support(B))
= (N[A, B] · N) / (N[A] · N[B])    [зведення дробів до лінійного виразу]
```

Інтерпретація коефіцієнта Lift:
* `Lift(A, B) > 1` — **позитивна кореляція**: поява файлу `A` у коміті істотно підвищує ймовірність появи файлу `B`. Це ознака реального логічного зачеплення.
* `Lift(A, B) = 1` — **статистична незалежність**: спільні зміни є суто випадковим збігом обставин.
* `Lift(A, B) < 1` — **негативна кореляція**: файли взаємно виключають один одного (зміна в одному зменшує ймовірність зміни в іншому).

## 5. Статистична значущість: критерій хі-квадрат (Chi-Square Test)

Щоб переконатися, що зв'язок між файлами `A` та `B` не є випадковою флуктуацією при малій кількості спостережень, будується таблиця спряженості `2 × 2`:

| Стан файлу | Файл B змінено (`B = 1`) | Файл B не змінено (`B = 0`) | Разом |
| :--- | :--- | :--- | :--- |
| **Файл A змінено (`A = 1`)** | `n[11] = N[A, B]` | `n[10] = N[A] - N[A, B]` | `N[A]` |
| **Файл A не змінено (`A = 0`)** | `n[01] = N[B] - N[A, B]` | `n[00] = N - N[A] - N[B] + N[A, B]` | `N - N[A]` |
| **Разом** | `N[B]` | `N - N[B]` | `N` |

Статистика хі-квадрат Пірсона зі ступенем свободи `df = 1` обчислюється за формулою:

```
χ²
= (N · (n[11] · n[00] - n[10] · n[01])²) / (N[A] · (N - N[A]) · N[B] · (N - N[B]))
```

Якщо обчислене значення `χ² > 3.841` (що відповідає рівню значущості `p < 0.05`), нульова гіпотеза про незалежність файлів відкидається: залежність є статистично достовірною.

## 6. Інформаційно-ентропійна модель зв'язку (Mutual Information)

Окрім класичних асоціативних правил, міру спільної інформації між еволюцією файлів описує **взаємна інформація (англ. *Mutual Information, MI*)**.

Нехай `X[A]` та `X[B]` — бінарні випадкові величини, що приймають значення `1`, якщо відповідний файл змінено в коміті, та `0`, якщо не змінено.

Ентропія Шеннона для файлу `A` дорівнює:

```
H(X[A])
= - P(X[A]=1) · log2(P(X[A]=1)) - P(X[A]=0) · log2(P(X[A]=0))
```

Взаємна інформація між двома компонентами обчислюється за формулою:

```
I(X[A]; X[B])
= ∑ ∑ P(X[A]=x, X[B]=y) · log2( P(X[A]=x, X[B]=y) / (P(X[A]=x) · P(X[B]=y)) )
```

де сумування ведеться за всіма комбінаціями `x, y ∈ {0, 1}`.

Для усунення залежності від індивідуальної ентропії застосовується **нормована взаємна інформація (англ. *Normalized Mutual Information, NMI*)**:

```
NMI(A, B)
= (2 · I(X[A]; X[B])) / (H(X[A]) + H(X[B]))
```

Значення `NMI` строго обмежене діапазоном від 0 (повна незалежність сигналів) до 1 (ідеальна детермінована синхронність змін). На відміну від лінійних коефіцієнтів кореляції, взаємна інформація фіксує будь-які нелінійні та комплексні статистичні залежності в поведінці компонентів.

## 7. Пошук N-арних кластерів за алгоритмом Apriori

Логічне зачеплення рідко обмежується двома файлами. Часто бізнес-правило або протокол розмазано між трійками чи четвірками компонентів (`{Controller, Validator, DTO, View}`).

Для знаходження множин розміру `k > 2` використовується принцип монотонності Apriori:
*Будь-яка підмножина частого набору файлів також зобов'язана бути частим набором.*

Алгоритм діє ітеративно:
1. Знаходяться всі часті одиничні файли `L[1] = {f ∈ F : Support(f) ≥ min_sup}`.
2. Формуються пари-кандидати `C[2] = L[1] ⨝ L[1]` та фільтруються за порогом підтримки: `L[2] = {pair ∈ C[2] : Support(pair) ≥ min_sup}`.
3. На кроці `k` кандидати розміру `k` генеруються шляхом об'єднання частих наборів розміру `k-1`, що збігаються в перших `k-2` елементах.
4. Якщо хоча б одна підмножина розміру `k-1` нового кандидата не належить `L[k-1]`, кандидат відкидається без перевірки журналу репозиторію.

Це дає змогу скоротити простір перебору від експоненційного `2^M` до поліноміального, здатного обробляти репозиторії з сотнями тисяч комітів за кілька секунд.

## 8. Часові ковзні вікна для асинхронних комітів

У сучасних розподілених командах зміни не завжди потрапляють в один атомарний коміт: розробник бекенду комітить зміну моделі о 10:00, а розробник клієнтського застосунку адаптує UI о 14:00.

Для виявлення таких асинхронних зв'язків дискретна модель комітів розширюється **ковзним часовим вікном (англ. *sliding time window*)** тривалістю `Δt` (зазвичай від 1 до 24 годин).

Нехай `t(C)` — мітка часу коміту `C`. Два файли `A ∈ C[i]` та `B ∈ C[j]` вважаються спільно зміненими у вікні `Δt`, якщо:

```
|t(C[i]) - t(C[j])| ≤ Δt
```

Крім того, для врахування застарівання зв'язків у великих проєктах вводиться експоненційне зважування в часі. Вага коміту `w(t)` зменшується відповідно до його віку:

```
w(t)
= 2^(-(t_now - t) / T_half)      [експоненційне згасання з періодом напіврозпаду T_half]
```

де:
* `t_now - t` — вік коміту в днях;
* `T_half` — період напіврозпаду впливу (зазвичай 90 або 180 днів).

## 9. Графовий аналіз та топологічні метрики (Centrality Metrics)

Коли обчислено парні метрики, репозиторій представляється у вигляді зваженого графа `G = (V, E, W)`, де вершини `V` — це файли, ребра `E` — пари зі статистично значущим зв'язком, а вага `W(e)` відповідає коефіцієнту `Jaccard` або `NMI`.

На цьому графі обчислюються дві ключові топологічні метрики:

### Ступінь вузла (Degree Centrality)
Кількість інших файлів, з якими даний компонент має стійке еволюційне зачеплення:

```
Degree(A)
= ∑ [1 для всіх B, де Jaccard(A, B) ≥ threshold]
```

Файли з високим `Degree` є **архітектурними восьминогами (англ. *octopus modules*)**: будь-яка зміна такого файлу викликає хвильовий ефект (ripple effect) по всій системі.

### Посередництво (Betweenness Centrality)
Міра того, як часто вершина лежить на найкоротших шляхах між іншими парами вершин у графі еволюційних залежностей:

```
Betweenness(v)
= ∑ (σ_st(v) / σ_st)       [для всіх пар вершин s ≠ v ≠ t]
```

де `σ_st` — загальна кількість найкоротших шляхів між `s` та `t`, а `σ_st(v)` — кількість таких шляхів, що проходять через `v`.

Файл із високим показником `Betweenness` є **прихованим архітектурним мостом (англ. *architectural bottleneck*)**: він з'єднує два ізольовані функціональні кластери системи. Його рефакторинг або виділення в окремий сервіс автоматично розриває зв'язок між двома великими підсистемами.

## Покроковий обчислювальний приклад

Розглянемо вибірку з `N = 100` комітів підсистеми електронної комерції. Проаналізуємо поведінку трьох файлів:
* `Auth.c` — модуль автентифікації користувачів (`N[Auth] = 20` комітів);
* `Token.c` — генератор сесійних криптографічних токенів (`N[Token] = 16` комітів);
* `Logger.c` — глобальний системний логер (`N[Logger] = 50` комітів).

Кількість спільних модифікацій у журналі:
* `N[Auth, Token] = 14` спільних комітів;
* `N[Auth, Logger] = 12` спільних комітів.

### Розрахунок 1: Аналіз пари (Auth, Token)

Обчислюємо метрики зв'язку між `Auth` та `Token`:

```
Support(Auth, Token)
= 14 / 100
= 0.14                     [14% усіх комітів репозиторію містять обидва файли]

Confidence(Auth → Token)
= 14 / 20
= 0.70                     [у 70% випадків правка Auth вимагала правки Token]

Confidence(Token → Auth)
= 14 / 16
= 0.875                    [у 87.5% випадків зміна Token спричиняла зміну Auth]

Jaccard(Auth, Token)
= 14 / (20 + 16 - 14)
= 14 / 22
≈ 0.636                    [коефіцієнт подібності 63.6%]

Lift(Auth, Token)
= (14 · 100) / (20 · 16)
= 1400 / 320
= 4.375                    [спільна зміна у 4.375 раза частіша за випадкову]
```

Перевіримо статистичну значущість через `χ²`:
* `n[11] = 14`
* `n[10] = 20 - 14 = 6`
* `n[01] = 16 - 14 = 2`
* `n[00] = 100 - 20 - 16 + 14 = 78`

```
χ²(Auth, Token)
= (100 · (14 · 78 - 6 · 2)²) / (20 · 80 · 16 · 84)
= (100 · (1092 - 12)²) / (2150400)
= (100 · 1080²) / 2150400
= (100 · 1166400) / 2150400
= 116640000 / 2150400
≈ 54.24                    [значно більше за критичне 3.841, зв'язок безсумнівний]
```

**Висновки щодо (Auth, Token):** показник `Lift = 4.375`, `Confidence(Token → Auth) = 87.5%` та `χ² = 54.24` однозначно підтверджують критичне еволюційне зачеплення. Модулі ділять спільну бізнес-логіку обробки токенів, яка не винесена в спільний стабільний інтерфейс.

### Розрахунок 2: Аналіз пари (Auth, Logger)

Обчислюємо метрики зв'язку між `Auth` та `Logger`:

```
Support(Auth, Logger)
= 12 / 100
= 0.12                     [12% комітів містять обидва файли]

Confidence(Auth → Logger)
= 12 / 20
= 0.60                     [60% правок Auth супроводжувалися правками Logger]

Confidence(Logger → Auth)
= 12 / 50
= 0.24                     [лише 24% правок Logger стосувалися Auth]

Jaccard(Auth, Logger)
= 12 / (20 + 50 - 12)
= 12 / 58
≈ 0.207                    [низький коефіцієнт подібності 20.7%]

Lift(Auth, Logger)
= (12 · 100) / (20 · 50)
= 1200 / 1000
= 1.20                     [зв'язок ледь перевищує випадковий рівень]
```

Обчислимо `χ²` для перевірки випадковості:
* `n[11] = 12`
* `n[10] = 20 - 12 = 8`
* `n[01] = 50 - 12 = 38`
* `n[00] = 100 - 20 - 50 + 12 = 42`

```
χ²(Auth, Logger)
= (100 · (12 · 42 - 8 · 38)²) / (20 · 80 · 50 · 50)
= (100 · (504 - 304)²) / (4000000)
= (100 · 200²) / 4000000
= (100 · 40000) / 4000000
= 4000000 / 4000000
= 1.00                     [менше за критичне 3.841, нульова гіпотеза не відкинута]
```

**Висновки щодо (Auth, Logger):** хоча показник `Confidence(Auth → Logger) = 60%` виглядає високим на перший погляд, значення `Lift = 1.20` та `χ² = 1.00` доводять, що цей зв'язок є статистичною випадковістю. Модуль `Logger` просто змінюється у половині всіх комітів системи, тому будь-який інший файл випадково потраплятиме з ним в один коміт без жодного архітектурного зачеплення.

## 10. Кластеризація логічних зв'язків: алгоритм MCL

Коли парні метрики обчислено для всіх пар файлів у системі, формується симетрична зважена матриця суміжності `W`, де вага ребра між файлами `i` та `j` дорівнює:

```
W[i, j]
= Jaccard(f[i], f[j]) · Lift(f[i], f[j])     [зважена сила еволюційного зв'язку]
```

Для виділення прихованих архітектурних компонентів (груп файлів, що утворюють щільно зачеплені ядра) застосовується алгоритм марковської кластеризації (Markov Cluster Algorithm, MCL). Він чергує дві матричні операції:
1. **Розширення (Expansion):** обчислення степеня матриці `W_new = W · W` (моделює випадкове блукання по графу зв'язків).
2. **Інфляція (Inflation):** поелементне піднесення до степеня `r > 1` з подальшою нормалізацією стовпчиків: `W_new[i, j] = (W[i, j]^r) / (∑ W[k, j]^r)`.

Операція інфляції підсилює сильні зв'язки всередині щільних кластерів і пригнічує слабкі випадкові зв'язки між кластерами. Процес чергування повторюється до досягнення збіжності, коли елементи матриці перестають змінюватися з точністю до `ε = 10^-6`.

На виході алгоритм повертає розбиття графа на неперетинні кластери. Кожен такий кластер є кандидатом на об'єднання в єдиний монолітний компонент або пакет відповідно до Принципу спільного закриття (CCP). Якщо файли всередині кластера змінюються синхронно у 90% випадків, їхнє штучне розділення по різних модулях лише збільшує накладні витрати на координацію та створює ризик помилок.

### Практичне застосування топологічних метрик під час рефакторингу

Поєднання метрик асоціативних правил із топологією графа дозволяє архітектору спланувати безпечний порядок рефакторингу застарілої системи:
1. **Перший крок (усунення вузьких місць):** виявлення компонентів із найвищим показником `Betweenness Centrality`. Їхній рефакторинг та стабілізація публічних контрактів розриває неявні зв'язки між незалежними підсистемами.
2. **Другий крок (ізоляція восьминогів):** компоненти з аномально високим `Degree Centrality` зазвичай страждають від розмитої відповідальності (порушення принципу Single Responsibility). Їх необхідно декомпозувати на окремі спеціалізовані сутності.
3. **Третій крок (консолідація кластерів):** файли, виділені алгоритмом MCL в один щільний кластер, переносяться в один спільний каталог або пакет, перетворюючи логічне зачеплення на явну локальну зв'язність (High Cohesion).

## Зведена таблиця метрик еволюційного зачеплення

| Метрика | Формула | Діапазон | Властивість | Архітектурне призначення |
| :--- | :--- | :--- | :--- | :--- |
| **Support** | `N[A,B] / N` | `[0, 1]` | Симетрична | Фільтр мінімальної статистичної значущості |
| **Confidence** | `N[A,B] / N[A]` | `[0, 1]` | Несиметрична | Виявлення напрямку залежності (Master / Slave) |
| **Jaccard** | `N[A,B] / (N[A]+N[B]-N[A,B])` | `[0, 1]` | Симетрична | Безперервна міра монолітності зв'язку пари |
| **Lift** | `(N[A,B]·N) / (N[A]·N[B])` | `[0, ∞)` | Симетрична | Очищення від шуму глобально активних файлів |
| **Chi-Square (χ²)** | Критерій Пірсона | `[0, ∞)` | Симетрична | Перевірка статистичної гіпотези незалежності |
| **NMI** | `2·I(A;B) / (H(A)+H(B))` | `[0, 1]` | Симетрична | Інформаційно-ентропійна оцінка синхронізації |
| **Betweenness** | Шляхи в графі зв'язків | `[0, 1]` | Топологічна | Пошук прихованих міжсистемних вузьких місць |
