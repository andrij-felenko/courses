# ⚙️ Рефакторинг «спитай-тоді-дій» → наказ: замовлення, що само стереже свої стани

Візьмімо один живий шматок коду й проведімо його від хвороби до здоров'я на очах, крок за кроком. Приклад — замовлення в інтернет-крамниці. У нього є **стан**: воно щойно створене, або оплачене, або відвантажене, або скасоване. Життя замовлення — це переходи між цими станами: оплатити, відвантажити, скасувати. І майже в кожному проєкті ці переходи спершу пишуть **ззовні** об'єкта: хтось витягає з замовлення його статус, дивиться, чи можна, — і вписує новий статус назад. Класична зв'язка «спитав → вирішив → змінив».

Ми пройдемо весь шлях: спершу побачимо, як цей зовнішній код тихо гниє й де саме він ламається; тоді перенесемо кожен перехід усередину замовлення командою, що сама стереже свій інваріант; а наприкінці — найтонше — розберемо, **де зупинитися**: які звернення до стану залишити як чесні запити й чому винищувати їх наосліп було б помилкою, гіршою за початкову.

## Задача: замовлення, яким крутять ззовні

Ось із чого ми стартуємо. Замовлення — голий носій даних: поле статусу та пара «дай статус / постав статус». Уся логіка переходів розсипана по викликачах — по «сервісах», «менеджерах», обробниках запитів.

:::tabs
```cpp
#include <string>
#include <stdexcept>

// Замовлення — лише мішок даних: статус назовні, жодного правила всередині
class Order {
public:
    explicit Order(std::string id) : id_(std::move(id)), status_("new") {}

    std::string getStatus() const { return status_; }
    void setStatus(std::string s) { status_ = std::move(s); }

    const std::string& id() const { return id_; }

private:
    std::string id_;
    std::string status_;   // "new" | "paid" | "shipped" | "cancelled"
};

// --- переходи живуть ЗЗОВНІ, у різних кутках коду ---

// оформлення (шар оплати)
void payOrder(Order& order) {
    if (order.getStatus() == "new") {
        order.setStatus("paid");
    } else {
        throw std::runtime_error("не можна оплатити: " + order.getStatus());
    }
}

// склад (інший шар, часто інший автор)
void shipOrder(Order& order) {
    // тут ЗАБУЛИ перевірити, що замовлення оплачене
    order.setStatus("shipped");
}

// скасування (ще один шар)
void cancelOrder(Order& order) {
    if (order.getStatus() != "shipped") {
        order.setStatus("cancelled");
    } else {
        throw std::runtime_error("відвантажене вже не скасувати");
    }
}
```

```python
    def __init__(self, order_id):
        self.order_id = order_id
        self.status = "new"          # "new" | "paid" | "shipped" | "cancelled"

    def get_status(self):
        return self.status

    def set_status(self, s):
        self.status = s


# --- переходи живуть ЗЗОВНІ, у різних кутках коду ---

# оформлення (шар оплати)
def pay_order(order):

        order.set_status("paid")
    else:
        raise RuntimeError(f"не можна оплатити: {order.get_status()}")

# склад (інший шар, часто інший автор)
def ship_order(order):
    # тут ЗАБУЛИ перевірити, що замовлення оплачене
    order.set_status("shipped")

# скасування (ще один шар)
def cancel_order(order):
    if order.get_status() != "shipped":
        order.set_status("cancelled")
    else:
        raise RuntimeError("відвантажене вже не скасувати")
```

Придивися, і хвороба вилазить сама. Правило «відвантажити можна лише оплачене» — це правило самого замовлення, частина його природи. Але його тут просто **немає**: `shipOrder` бере будь-яке замовлення й ставить `"shipped"`, бо автор складського шару не тримав у голові весь автомат станів і забув перевірку. Правило «скасувати можна все, крім відвантаженого» живе в третьому місці — і воно неповне, бо про скасоване теж треба було подумати, а ніхто не подумав. Кожен викликач тримає **свій уламок** спільного правила, і разом ці уламки не складаються в цілісний закон.

Наслідок не теоретичний. Ось що цей код реально дозволяє:

:::tabs
```cpp
Order o("A-1");
shipOrder(o);                 // "new" -> "shipped": відвантажили НЕОПЛАЧЕНЕ
o.setStatus("banana");        // і взагалі будь-хто може вписати будь-що
// замовлення тепер у стані, якого не існує в природі
```
```python
o = Order("A-1")
ship_order(o)                 # "new" -> "shipped": відвантажили НЕОПЛАЧЕНЕ
o.set_status("banana")        # і взагалі будь-хто може вписати будь-що
# замовлення тепер у стані, якого не існує в природі
```
:::

Об'єкт не володіє власним станом. Стіна нібито є — поле приватне (у C++), доступ через методи, — але `setStatus` пробиває її наскрізь: крізь нього всередину заходить **будь-яке** значення, зокрема неможливе. Замовлення не гарантує про себе нічого. Гарантії, якщо вони десь і є, розкидані по викликачах — і кожен новий викликач може або повторити перевірку (дублювання), або, як склад, її забути (діра).

Тепер уяви найзвичайнішу зміну вимог: додається стан «повернуто» (`refunded`) — повернути можна лише відвантажене замовлення. Скільки місць доведеться відшукати й виправити? Усі, де хтось міняє статус, бо кожне з них тепер може привести замовлення в новий стан або з нього. Ти мусиш пройти весь код, знайти кожен `setStatus`, згадати про новий стан у кожній перевірці — і жодного пропустити. Це і є та калюжа, у яку розтеклося бізнес-правило: зібрати її назад в одне місце вже боляче.

## Ідея: перенести кожен перехід усередину командою

Ліки прямо випливають із діагнозу, і вони — рівно те, що радить «кажи, не питай». Кожен перехід — `pay`, `ship`, `cancel` — це рішення про власний стан замовлення. Отже, він має жити **всередині** замовлення, як його метод-**команда**. Викликач не питатиме статус і не вписуватиме новий; він скаже одне слово — `order.pay()` — а замовлення саме перевірить, чи перехід дозволений із поточного стану, і або виконає його, або відмовить винятком.

Ключове слово тут — **інваріант**: твердження, яке об'єкт обіцяє тримати істинним завжди, у будь-який момент свого життя. Наш інваріант — «замовлення завжди в одному з чотирьох законних станів, і між ними ведуть лише дозволені переходи». Поки переходи були ззовні, тримати цей інваріант не міг ніхто: об'єкт не контролював власні двері. Щойно кожен перехід стає командою з вартовим-перевіркою (англ. *guard clause* — застережний вираз на вході, що відкидає недозволений виклик), інваріант отримує єдиного сторожа — сам об'єкт.

Дозволені переходи зручно бачити як граф. Ось усе життя замовлення на одній картинці — і одразу видно, що більшість пар «стан → стан» переходами **не** є:

![Граф із чотирьох станів замовлення: NEW, PAID, SHIPPED у ряд, CANCELLED під ними. Зелені суцільні стрілки-переходи підписані іменами команд: pay() веде NEW→PAID, ship() веде PAID→SHIPPED, cancel() веде і NEW→CANCELLED, і PAID→CANCELLED. Червона пунктирна перекреслена стрілка SHIPPED→CANCELLED підписана «cancel() → виняток» — заборонений перехід](img/order-state-machine.svg)

*Автомат станів — це і є повний перелік правил замовлення в одній фігурі. Зелені ребра — дозволені переходи (їх мало); усе, чого на графі немає, — заборонене. «Кажи, не питай» просто вимагає, щоб цей граф жив усередині об'єкта, а не вгадувався розкиданими ззовні if-ами.*

Замість чотирьох станів як довільних рядків заведімо їх переліком (англ. *enum* — тип із фіксованого списку значень): тоді сам тип не дасть з'явитися «banana», бо поза списком значень просто не існує. Це вже не про «кажи, не питай», а про споріднену ідею — [зробити неможливий стан невиразним самим типом](book:programming/type-driven-design); тут вона працює пліч-о-пліч із нашою.

## Робочий код: замовлення, що само стереже переходи

Ось той самий приклад після рефакторингу. Стан — перелік. Кожен перехід — команда з вартовим. Недозволений перехід кидає виняток, а не тихо псує стан. Назовні стирчить лише один чесний запит — прочитати поточний статус.

:::tabs
```cpp
#include <string>
#include <stdexcept>

enum class Status { New, Paid, Shipped, Cancelled };

// для повідомлень і показу — стан у людський рядок
std::string toString(Status s) {
    switch (s) {
        case Status::New:       return "new";
        case Status::Paid:      return "paid";
        case Status::Shipped:   return "shipped";
        case Status::Cancelled: return "cancelled";
    }
    return "?";
}

// власний тип помилки — щоб викликач ловив саме недозволений перехід
class OrderError : public std::logic_error {
public:
    explicit OrderError(const std::string& msg) : std::logic_error(msg) {}
};

class Order {
public:
    explicit Order(std::string id)
        : id_(std::move(id)), status_(Status::New) {}

    // --- КОМАНДИ: кожна стереже свій інваріант ---

    void pay() {
        require(status_ == Status::New, "оплатити можна лише нове");
        status_ = Status::Paid;
    }

    void ship() {
        require(status_ == Status::Paid, "відвантажити можна лише оплачене");
        status_ = Status::Shipped;
    }

    void cancel() {
        require(status_ != Status::Shipped && status_ != Status::Cancelled,
                "скасувати вже не можна");
        status_ = Status::Cancelled;
    }

    // --- ЗАПИТ: лише читає, нічого не міняє ---
    Status status() const { return status_; }
    const std::string& id() const { return id_; }

private:
    // спільний вартовий: не виконуй перехід, якщо умова хибна
    void require(bool ok, const char* why) const {
        if (!ok)
            throw OrderError(std::string(why) + " (зараз " + toString(status_) + ")");
    }

    std::string id_;
    Status status_;
};
```
```python
from enum import Enum


class Status(Enum):
    NEW = "new"
    PAID = "paid"
    SHIPPED = "shipped"
    CANCELLED = "cancelled"


class OrderError(Exception):
    """Недозволений перехід стану замовлення."""


class Order:
    def __init__(self, order_id):
        self._id = order_id
        self._status = Status.NEW

    # --- КОМАНДИ: кожна стереже свій інваріант ---

    def pay(self):
        self._require(self._status is Status.NEW, "оплатити можна лише нове")
        self._status = Status.PAID

    def ship(self):
        self._require(self._status is Status.PAID, "відвантажити можна лише оплачене")
        self._status = Status.SHIPPED

    def cancel(self):
        self._require(self._status not in (Status.SHIPPED, Status.CANCELLED),
                      "скасувати вже не можна")
        self._status = Status.CANCELLED

    # --- ЗАПИТ: лише читає, нічого не міняє ---
    @property
    def status(self):
        return self._status

    @property
    def id(self):
        return self._id

    # спільний вартовий: не виконуй перехід, якщо умова хибна
    def _require(self, ok, why):
        if not ok:
            raise OrderError(f"{why} (зараз {self._status.value})")
```
:::

Тепер поглянь, як змінився викликач. Уся зовнішня арифметика станів зникла — лишилися накази:

:::tabs
```cpp
Order o("A-1");

o.ship();     // paid -> shipped
// o.cancel(); // кине OrderError: "скасувати вже не можна (зараз shipped)"

// склад більше НЕ МОЖЕ відвантажити неоплачене — навіть якби забув перевірку:
Order bad("A-2");
try {
    bad.ship();          // OrderError: "відвантажити можна лише оплачене (зараз new)"
} catch (const OrderError& e) {
    // помилку видно ТУТ, а не через тиждень у зіпсованих даних
}
```
```python
o = Order("A-1")
o.pay()       # new -> paid
o.ship()      # paid -> shipped
# o.cancel()  # кине OrderError: "скасувати вже не можна (зараз shipped)"

# склад більше НЕ МОЖЕ відвантажити неоплачене — навіть якби забув перевірку:
bad = Order("A-2")
try:
    bad.ship()           # OrderError: "відвантажити можна лише оплачене (зараз new)"
except OrderError:
    pass                 # помилку видно ТУТ, а не через тиждень у зіпсованих даних
```

Три речі змінилися по суті, не косметично.

**Правило зібралося в одне місце.** Увесь автомат станів — які переходи дозволені з якого стану — тепер живе в трьох командах усередині `Order`. Немає жодного шляху перевести замовлення в інший стан, оминувши ці команди: поля приватні, `setStatus` більше не існує. Автор складського шару фізично не може забути перевірку — перевірка вбудована в `ship`, і забути її можна хіба що переписавши сам `Order`.

**Неможливий стан став неможливим.** Рядок `"banana"` більше нікуди не впишеш — тип `Status` не має такого значення, а єдиний спосіб змінити стан проходить крізь вартових. Замовлення нарешті **володіє** власним станом: щоб про нього не спитали, воно завжди в одному з чотирьох законних станів, і це його гарантія, а не сподівання викликачів.

**Помилка спливає рано і в точці причини.** Спроба недозволеного переходу кидає `OrderError` негайно, у тому рядку, де її вчинили, з повідомленням, що пояснює, з якого стану й куди не можна. Це набагато краще за мовчазне псування, яке колись зловлять за кілометр від причини — у звіті, що не сходиться, або в підтримці, що дивується скасованому-після-відвантаження замовленню. Про те, чому [жодна помилка не має мовчати](book:programming/error-handling), є окрема розмова; тут важливо, що виняток на недозволеному переході — це і є той голос, який не дає діру сховатися.

Повернімося до тієї зміни вимог, що лякала раніше, — новий стан «повернуто». Тепер вона лягає **в один файл**. Додаєш `Refunded` до переліку, дописуєш команду `refund` з її вартовим («повернути можна лише відвантажене») і, якщо треба, вирішуєш, чи веде `cancel` кудись із нового стану. Решта коду — усі викликачі — навіть не помічають, що автомат станів поповнився: вони як казали `order.ship()`, так і кажуть. Правило перестало бути калюжею й стало точкою.

> 🔧 **Навіщо це.** Різниця «до/після» — це різниця в тому, скільки коду тримає одне бізнес-правило. У версії «спитай-тоді-дій» правило переходів розмазане по всіх викликачах, тож кожна зміна правила — це полювання по всьому проєкту з ризиком щось проґавити, а кожен новий викликач — потенційна нова діра. У версії «скажи» правило зібране в об'єкті, який ним володіє: зміна лягає в одне місце, а привести замовлення в неможливий стан ззовні просто нема як. Ти платиш за це трохи більшим об'єктом — і купуєш гарантію, яку раніше ніхто не давав.

## Межа: де наказ, а де чесний запит

Тепер найтонше — і саме тут «кажи, не питай», узяте наосліп, псує код замість лікувати. Спокуса після вдалого рефакторингу — оголосити війну **всім** зверненням до стану й перетворити кожен `status()` на якийсь наказ. Це помилка, і варто зрозуміти, чому саме, а не просто завчити «не роби так».

Орієнтир, що проводить лінію точно, старший за саме гасло «кажи, не питай». Це **розділення команд і запитів** (англ. *command-query separation*, CQS) — принцип, який сформулював Бертран Меєр (Bertrand Meyer) у книжці «Object-Oriented Software Construction» (Prentice-Hall, 1988) навколо мови Eiffel. Його суть в одному образі: **запитання не має міняти відповіді** (англ. *asking a question should not change the answer*). Звідси поділ кожного методу на два різновиди:

- **Команда** щось міняє в об'єкті й нічого змістовного не повертає: `pay`, `ship`, `cancel`. Її можна лише «сказати».
- **Запит** нічого не міняє, лише повертає відповідь про стан: `status`, `isPaid`, `id`. Його цілком нормально спитати й прочитати.

*(Статус доказовості: авторство CQS за Меєром і формулювання «asking a question should not change the answer» — усталений факт, задокументований у первинному джерелі — його ж «Object-Oriented Software Construction» — і в загальновідомих оглядах принципу.)*

І ось ключ, який знімає всю плутанину: **«кажи, не питай» цілиться не в запити, а в команди, замасковані під роботу з запитами**. Небезпечна не сама наявність `status()`. Небезпечна зв'язка **«прочитав запит → вирішив → викликав команду, що міняє той самий об'єкт»** — бо саме тут рішення, яке належить об'єктові, витекло назовні. Голий запит без такого рішення-над-ним нікому не шкодить.

Порівняймо два звернення до одного й того самого `status()` пліч-о-пліч:

:::tabs
```cpp
// (A) ПОРУШЕННЯ: запит, над яким ухвалюють рішення, і воно веде НАЗАД у команду
if (order.status() == Status::Paid) {   // прочитав стан...
    order.ship();                        // ...і на його основі міняє ТОЙ САМИЙ об'єкт
}
// рішення «коли відвантажувати» знову втекло з Order — його місце ВСЕРЕДИНІ ship()

// (B) ЧЕСНИЙ ЗАПИТ: читаємо стан, щоб ПОКАЗАТИ, і нічого не міняємо
std::string badge = "Замовлення " + order.id() + ": " + toString(order.status());
// це не наказ і не має ним ставати — рахунок нічого не вирішує, лише повідомляє
```
```python
# (A) ПОРУШЕННЯ: запит, над яким ухвалюють рішення, і воно веде НАЗАД у команду
if order.status is Status.PAID:          # прочитав стан...
    order.ship()                         # ...і на його основі міняє ТОЙ САМИЙ об'єкт
# рішення «коли відвантажувати» знову втекло з Order — його місце ВСЕРЕДИНІ ship()

# (B) ЧЕСНИЙ ЗАПИТ: читаємо стан, щоб ПОКАЗАТИ, і нічого не міняємо
badge = f"Замовлення {order.id}: {order.status.value}"
# це не наказ і не має ним ставати — замовлення нічого не вирішує, лише повідомляє
```
:::

Випадок (A) — справжнє порушення: винеси рішення всередину, хай `ship()` сам вирішує, чи він доречний із поточного стану (він уже так і робить у нашій версії — просто скажи `order.ship()` і злови виняток, якщо не час). Випадок (B) — **не** порушення й ним ставати не повинен. Показ статусу на екрані, у листі, у теґу — це чистий запит для подання. Замовлення тут нічого не вирішує про себе; хтось інший бере його стан і **малює**. Спроба обернути це на наказ — приліпити до замовлення метод на кшталт `renderBadge()` чи `drawYourselfOnScreen()`, аби формально «не питати статус», — зшила б замовлення з шаром показу намертво. Завтра захочеш інший формат теґа, темну тему, іншу мову — і полізеш правити доменний об'єкт замовлення заради кольору тексту. Це діло [інтерфейсу проти реалізації](book:programming/interface-vs-implementation) навпаки: ти протягуєш крізь чистий доменний об'єкт відповідальність зовсім іншого шару.

Ту саму межу легко перевірити на трьох типових запитах, які **правильно** лишити запитами:

:::tabs
```cpp
// показ — читаємо стан, щоб намалювати
std::string line = "#" + order.id() + " — " + toString(order.status());

// сортування — читаємо стан як ключ; нічого не міняємо
std::sort(orders.begin(), orders.end(),
    [](const Order& a, const Order& b) { return a.status() < b.status(); });

// звіт — рахуємо, скільки замовлень оплачено; жодної зміни станів
long paid = std::count_if(orders.begin(), orders.end(),
    [](const Order& o) { return o.status() == Status::Paid; });
```
```python
# показ — читаємо стан, щоб намалювати
line = f"#{order.id} — {order.status.value}"

# сортування — читаємо стан як ключ; нічого не міняємо
orders.sort(key=lambda o: o.status.value)

# звіт — рахуємо, скільки замовлень оплачено; жодної зміни станів
paid = sum(1 for o in orders if o.status is Status.PAID)
```
:::

У кожному з трьох ми читаємо стан і нічого назад не наказуємо — це чесні запити, і винищувати їх заради букви гасла було б забобоном, а не дизайном. Лінза «кажи, не питай» показує **рішення, що втекло від свого об'єкта**; вона не лічильник геттерів, який тим кращий, чим менше показує.

## Складність і пастки

Рефакторинг простий у задумі, але має кілька країв, об які легко порізатися. Пройдімося по них чесно.

**Пастка перша: перетворити кожен геттер на наказ.** Це головна помилка, і ми щойно її розібрали в розділі про межу, та варто назвати її окремо як пастку, бо піддаються їй найчастіше саме після вдалого рефакторингу — на хвилі «тепер усе буде наказами». Запит, над яким **не** ухвалюють рішення, що веде назад у той самий об'єкт, — не порушення. Показ, сортування, звіт, підрахунок — це законні читання. Ознака, за якою ловити справжнє порушення, одна: **чи йде за читанням стану рішення, що змінює цей самий об'єкт**. Немає такого рішення — немає й порушення.

**Пастка друга: зшити команду з шаром показу.** Близька до першої, але з іншого боку. Коли переселяєш поведінку в об'єкт, є спокуса переселити **забагато** — приліпити до `Order` те, що насправді належить іншому шару: форматування для екрана, запис у базу, надсилання листа-сповіщення про оплату. Команда `pay` має робити **лише** перехід стану, який їй властивий. Якщо їй хочеться ще й лист надіслати — це вже не її робота: об'єкт замовлення не повинен знати ні про пошту, ні про екран. Правило просте: у команду переселяй те, що є **рішенням про власний стан об'єкта**, і нічого поза цим. Змішаєш — і замість чистого доменного об'єкта дістанеш той-таки «менеджер», лише вивернутий навиворіт, зі шматками трьох шарів усередині.

**Пастка третя: сховати запит, який насправді потрібен назовні.** Дзеркало другої. Іноді, женучись за «кажи», ховають те, що чесно потрібне іншим, — і код починає корчитися в обхід. Якщо десятьом місцям треба показати статус, а ти прибрав `status()` «щоб не питали», ці десять місць винайдуть милиці: діставатимуть стан через `toString`, ловитимуть його з тексту помилки, триматимуть власну тіньову копію. Чесний запит `status()` для показу — це нормальна, потрібна частина інтерфейсу. Ховати його — значить плодити гірші обхідні шляхи, ніж чесне читання.

**Край четвертий, тонший: команда, якій справді треба щось повернути.** CQS у чистому вигляді каже: команда нічого змістовного не повертає. Але життя інколи вимагає винятку — наприклад, `pop()` у стека і міняє стек, і повертає знятий елемент; розділити це на дві дії часто гірше, ніж лишити одним. Це відомий компроміс, і сам Меєр визнає такі випадки. Практичне правило: **тримайся розділення за замовчуванням**, а порушуй свідомо й рідко, коли розділення явно шкодить, — не навпаки. Для нашого замовлення потреби порушувати немає: команди переходів нічого не повертають, і це добре.

**Край п'ятий: «анемічна» команда — наказ, що нічого не стереже.** Буває, поведінку нібито «переселили», але команда виявляється порожньою — просто ще одна обгортка над присвоєнням поля, без жодного вартового: `void markPaid() { status_ = Status::Paid; }` без перевірки, що стан був `New`. Це поразка, замаскована під перемогу: перехід переїхав усередину назвою, а інваріант так і лишився без сторожа — привести замовлення в неможливий стан усе ще можна. Команда «кажи, не питай» варта чогось лише тоді, коли всередині неї **є що стерегти** — вартовий, що відкидає недозволений перехід. Гола обгортка над сеттером — це той самий сеттер, лише в новому костюмі.

Підіб'ємо. Рефакторинг «спитай-тоді-дій → наказ» — це не механічна заміна `get`/`set` на дієслова, а перенесення **рішень про стан** туди, де живе сам стан, разом із вартовими, що тримають інваріант. Роби це там, де за читанням стану йде зміна того самого об'єкта, — і не роби там, де стан лише читають, щоб показати, відсортувати чи полічити. Мірило зробленого — не кількість зниклих геттерів, а те, що замовлення тепер **неможливо** привести в стан, якого не існує в його природі, і що весь його автомат станів читається в одному місці, а не збирається по всьому проєкту з розкиданих уламків.
