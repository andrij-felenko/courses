# ⚙️ Ефекти як значення: план намірів і тонкий виконавець

Є прийом, який на перший погляд плутають із простим «винеси обчислення в чисту функцію», а він насправді йде на крок далі й відмикає зовсім інші двері. Щоб побачити той крок ясно, візьмімо функцію, яку соромно показувати, але яку кожен писав: вона питає годинник, кидає гральні кості, читає конфіг, дописує в базу два рядки й шле лист. П'ять різних розмов зі світом в одному тілі. Розчепити її на чисте ядро й тонку оболонку — половина справи; це вміє й [сусідній розтин «обчислення проти ефектів»](topic:programming/pure-functions-side-effects/proj-extract-pure-core.md). Але там оболонка, ставши тонкою, **усе одно сама вирішує, які ефекти робити**: у ній жорстко вписані рядки `db.save(...)` і `notify(...)`. Ми підемо далі й приберемо навіть це рішення з оболонки — зробимо **самі ефекти даними**, які ядро повертає, а безмозкий виконавець на краю просто виконує. Різницю варто відчути на пальцях, бо саме вона — цінність цієї вставки.

Домовмося про два слова, щоб далі не плутатися. **Ефект** — це справжня зміна світу: рядок ліг у базу, лист пішов. А **намір** (те, що ми складатимемо в список) — це лише *опис* такої зміни, звичайне значення, яке саме по собі нічого не робить, доки хтось його не виконає. Ядро вироблятиме **план намірів**; виконавець перетворюватиме кожен намір на ефект. У коді тип для наміру за традицією звуть `Effect`, але поки він лежить у списку — це намір, інертні дані, не дія.

## Задача: функція, що читає час, кидає кості й лізе в базу

Нехай ми робимо щоденний бонус у застосунку: раз на добу гравець «крутить колесо» й отримує монети — зазвичай трохи, зрідка джекпот. Ось успадкований код, у якому все злиплося.

:::tabs
```ts
// ── ДО: одна функція говорить зі світом п'ятьма голосами ──
let clock = () => Date.now();          // глобальний годинник
let rng   = () => Math.random();       // глобальний генератор
let cfg   = loadConfig();              // глобальний конфіг

function claimBonus(userId: number): number {
  const user = db.loadUser(userId);              // читання з БД
  const now  = clock();                          // прихований вхід: час
  if (now - user.lastClaim < cfg.cooldownMs) {   // ще рано
    return 0;
  }
  const roll   = rng();                          // прихований вхід: випадковість
  const amount = roll < cfg.jackpotChance ? cfg.jackpotBonus : cfg.baseBonus;

  user.balance  += amount;                        // мутація входу
  user.lastClaim = now;
  db.saveUser(user);                              // запис у БД
  db.appendLedger(userId, amount, now);           // ще запис у БД
  mailer.send(user.email, `Бонус +${amount}`);    // посилка листа
  return amount;
}
```

Придивись, де тут сховане рішення. Функція не просто рахує суму — вона **вирішує, які саме дії вчинити**: чи взагалі щось робити (гілка кулдауну), скільки нарахувати, який текст листа. І це рішення нероздільно зрощене з самим чиненням: гілка `if` веде до трьох викликів, що б'ють у справжню базу й справжню пошту. Щоб перевірити одну-єдину думку — «на щасливому кидку в джекпот нараховуємо 500, а не 50» — доведеться заморозити годинник, підмінити генератор, виставити конфіг, підставити базу й перехопити пошту. П'ять підготовок заради однієї перевірки арифметики й одного `if`.

> 🔧 **Навіщо це.** Найдорожче в цій функції — не те, що вона робить ефекти, а те, що **рішення про ефекти неможливо роздивитися окремо від їх виконання**. Ти не можеш спитати «а що ця функція збирається зробити на такому вході?», не давши їй це зробити насправді. Уся мета прийому — розірвати саме цей вузол: винести *що робити* в чисте значення, яке можна оглянути, і лишити *робити* тупому шматку на краю.

## Крок перший: приховані входи — явними параметрами

Половина роботи механічна й нецікава, тож проженемо її швидко. Кожен прихований вхід — годинник, конфіг — стає звичайним параметром. Функція більше не питає світ «котра година?» — їй **приносять** годину.

Випадковість заслуговує окремого слова, бо тут легко зробити напівкрок. Здавалося б, досить передати ядру сам генератор — `rng` як параметр. Але це нічого не лікує: `rng()` усередині ядра так само читає прихований стан (внутрішнє зерно генератора) і так само дає щоразу інше на «той самий» вхід. Правильний рух — **витягти випадковість на край і передати ядру вже витягнуте число**. Ядро приймає не генератор, а плаский `roll: number` у проміжку `[0, 1)` — звичайне значення, як будь-яке інше. Хто справді кидає кості — тонка оболонка; ядро лише читає результат кидка.

```
приховані входи        →   явні параметри ядра
─────────────────          ───────────────────
годинник  clock()      →   now:  number      (момент часу)
генератор rng()        →   roll: number      (уже витягнутий кидок ∈ [0,1))
конфіг    global cfg   →   cfg:  Config       (знімок політики)
```

Якщо ядру треба кидати кості багато разів, замість готового `roll` передають **зерно** (англ. *seed* — насінина), а ядро крутить *чистий* генератор `seed → (число, нове_зерно)`, протягуючи зерно крізь обчислення. Це та сама ідея «зроби прихований канал явним», лише вже для стану генератора; для одного кидка вона надлишкова, тож беремо простий шлях — одне число.

Три рядки нудної роботи, і всі приховані входи стоять у дужках. Лишається цікаве — приховані **виходи**.

## Крок другий: ефект — це дані. Об'єднання `Effect`

Ось серце прийому. Замість того щоб ядро **робило** запис у базу, нехай воно **опише** цей запис звичайним значенням. Нам потрібен тип, що каже: «намір буває одного з кількох видів, і кожен вид несе свої поля». Такий тип називають **дискримінованим об'єднанням** (англ. *discriminated union*, від лат. *discriminare* — розрізняти; ще кажуть «розрізнюване об'єднання» або «сума типів»): значення — це рівно один із перелічених варіантів, а спільне поле-мітка (дискримінант) каже, котрий саме.

TypeScript створений для таких типів, тож із нього й почнімо — мітка `kind` розрізняє варіанти, і кожен несе рівно свої поля.

:::tabs
```ts
// намір — рівно один із трьох варіантів; поле kind каже, котрий
type Effect =
  | { kind: "saveUser";     user: User }
  | { kind: "appendLedger"; userId: number; amount: number; at: number }
  | { kind: "notify";       to: string; text: string };
```
```py
from dataclasses import dataclass

# кожен варіант — свій незмінний клас; Effect — їх об'єднання
@dataclass(frozen=True)
class SaveUser:     user: "User"
@dataclass(frozen=True)
class AppendLedger: user_id: int; amount: int; at: int
@dataclass(frozen=True)
class Notify:       to: str; text: str

Effect = SaveUser | AppendLedger | Notify
```
```cpp
// кожен варіант — свій struct; Effect — їх варіант (тег усередині std::variant)
struct SaveUser     { User user; };
struct AppendLedger { int userId; long amount; long at; };
struct Notify       { std::string to; std::string text; };

using Effect = std::variant<SaveUser, AppendLedger, Notify>;
```
:::

Головне тут — не синтаксис, а зсув думки. Значення типу `Effect` **нічого не робить**. `{ kind: "notify", to: "a@b.c", text: "Бонус +50" }` — це не відправлений лист; це папірець із написом «варто б відправити такий лист». Його можна покласти в список, роздрукувати, порівняти, зберегти на диск, відправити по мережі іншому процесу — і жоден байт у поштовому сервері не ворухнеться. Намір інертний за побудовою. Саме ця інертність робить його **даними**, а не дією, і саме тому його можна повертати з чистої функції.

## Ядро повертає план, а не робить ефект

Тепер ядро. Воно приймає всі явні входи й повертає `Effect[]` — **план намірів**. Жодного `db`, жодного `mailer`, жодного годинника: лише вхідні дані на вході й список намірів на виході.

:::tabs
```ts
// ЧИСТЕ ядро: усі входи явні, на виході — план намірів (дані)
function decideBonus(user: User, now: number, roll: number, cfg: Config): Effect[] {
  if (now - user.lastClaim < cfg.cooldownMs)
    return [];                                     // на кулдауні — план ПОРОЖНІЙ

  const amount  = roll < cfg.jackpotChance ? cfg.jackpotBonus : cfg.baseBonus;
  const updated = { ...user, balance: user.balance + amount, lastClaim: now };
  const text    = amount === cfg.jackpotBonus ? `Джекпот! +${amount}` : `Бонус +${amount}`;

  return [
    { kind: "saveUser",     user: updated },
    { kind: "appendLedger", userId: user.id, amount, at: now },
    { kind: "notify",       to: user.email, text },
  ];
}
```
```py
from dataclasses import replace

# ЧИСТЕ ядро: усі входи явні, на виході — план намірів (дані)
def decide_bonus(user: User, now: int, roll: float, cfg: Config) -> list[Effect]:
    if now - user.last_claim < cfg.cooldown_ms:
        return []                                  # на кулдауні — план ПОРОЖНІЙ

    amount  = cfg.jackpot_bonus if roll < cfg.jackpot_chance else cfg.base_bonus
    updated = replace(user, balance=user.balance + amount, last_claim=now)
    text    = f"Джекпот! +{amount}" if amount == cfg.jackpot_bonus else f"Бонус +{amount}"

    return [
        SaveUser(updated),
        AppendLedger(user.id, amount, now),
        Notify(user.email, text),
    ]
```
```cpp
// ЧИСТЕ ядро: усі входи явні, на виході — план намірів (дані)

        return {};                                 // на кулдауні — план ПОРОЖНІЙ

    updated.lastClaim = now;

        ? "Джекпот! +" + std::to_string(amount)
        : "Бонус +"    + std::to_string(amount);

    return {
        SaveUser{updated},
        AppendLedger{user.id, amount, now},
        Notify{user.email, text},
    };
}
```
:::

Зверни увагу на дві речі, у яких і сидить уся сила. Перша: гілка кулдауну повертає `[]` — **порожній план**. «Нічого не робити» стало таким самим значенням, як і «зробити три речі»; це не окрема гілка керування в оболонці, а звичайні дані, які ядро повертає й які так само легко перевірити. Друга: рішення *скільки нарахувати* й *який текст листа* тепер лежить у поверненому значенні. Оболонка про це нічого не знає — вона не бачила ні `cfg.jackpotChance`, ні гілки `if`. **Усе рішення переїхало в чисте ядро й стало даними.**

Проженемо один вхід крізь ядро, щоб побачити, що воно віддає:

**Гравець із балансом 300, минуло 25 годин, кидок 0.03 (конфіг: база 50, джекпот 500, шанс 0.05, кулдаун 24 год).**

```
баланс до        = 300
now − lastClaim  = 25 год     (> 24 год кулдаун)   → не рано, робимо
roll             = 0.03       (< 0.05 шанс)         → джекпот
amount           = 500
баланс після     = 300 + 500  = 800

план =  [ saveUser{ balance: 800, lastClaim: now },
          appendLedger{ userId, amount: 500, at: now },
          notify{ to: email, text: "Джекпот! +500" } ]
```

Виклик повернув три папірці. База не оновилася, лист не пішов — ми лише **дізналися намір**. Зробити його — окрема історія, і вона тривіальна.

## Крихітний виконавець на краю

Намірам потрібен той, хто оживить їх у світі. Це **виконавець** (у теорії його звуть **інтерпретатором**, від лат. *interpres* — тлумач: він тлумачить дані-намір у справжню дію). Він бере один намір і робить рівно один ефект — розгалуження за міткою й нічого більше:

:::tabs
```ts
// ВИКОНАВЕЦЬ: намір → справжній ефект. Жодних рішень, лише розгалуження за kind.
function run(eff: Effect, db: Db, mailer: Mailer): void {
  switch (eff.kind) {
    case "saveUser":     db.saveUser(eff.user); return;
    case "appendLedger": db.appendLedger(eff.userId, eff.amount, eff.at); return;
    case "notify":       mailer.send(eff.to, eff.text); return;
    default:             const _never: never = eff; return _never;   // забув варіант — не збереться
  }
}

// ОБОЛОНКА: принести дані → спитати ядро → прокрутити план. Три рядки, нуль рішень.
function claimBonus(userId: number, deps: Deps): void {
  const user = deps.db.loadUser(userId);
  const plan = decideBonus(user, deps.clock(), deps.rng(), deps.cfg);
  for (const eff of plan) run(eff, deps.db, deps.mailer);
}
```
```py
# ВИКОНАВЕЦЬ: намір → справжній ефект. Жодних рішень, лише розбір за типом.
def run(eff: Effect, db: Db, mailer: Mailer) -> None:
    match eff:
        case SaveUser(user):              db.save_user(user)
        case AppendLedger(uid, amt, at):  db.append_ledger(uid, amt, at)
        case Notify(to, text):            mailer.send(to, text)

# ОБОЛОНКА: принести дані → спитати ядро → прокрутити план. Три рядки, нуль рішень.
def claim_bonus(user_id: int, deps: Deps) -> None:
    user = deps.db.load_user(user_id)
    plan = decide_bonus(user, deps.clock(), deps.rng(), deps.cfg)
    for eff in plan:
        run(eff, deps.db, deps.mailer)
```
```cpp
// ВИКОНАВЕЦЬ: намір → справжній ефект. std::visit розгалужує за активним варіантом.
template<class... Ts> struct overload : Ts... { using Ts::operator()...; };
template<class... Ts> overload(Ts...) -> overload<Ts...>;

void run(const Effect& eff, Database& db, Mailer& mailer) {
    std::visit(overload{
        [&](const SaveUser& e)     { db.saveUser(e.user); },
        [&](const AppendLedger& e) { db.appendLedger(e.userId, e.amount, e.at); },
        [&](const Notify& e)       { mailer.send(e.to, e.text); },
    }, eff);
}

// ОБОЛОНКА: принести дані → спитати ядро → прокрутити план. Нуль рішень.
void claimBonus(int userId, Deps& deps) {
    User user = deps.db.loadUser(userId);
    auto plan = decideBonus(user, deps.clock(), deps.rng(), deps.cfg);
    for (const Effect& eff : plan) run(eff, deps.db, deps.mailer);
}
```
:::

Погляньмо, що вийшло, збоку. Ядро вирішує все й не торкається світу. Виконавець торкається світу й нічого не вирішує — він **написаний раз** і годиться для будь-якого ядра, що повертає ці наміри. Оболонка звелася до «принеси — спитай — прокрути»: у ній не лишилося жодної гілки, жодного числа, жодного рядка тексту листа. Уся розумна частина — по один бік межі; уся брудна — по другий. Цей поділ «чисте всередині, брудне зовні» — окремий структурний принцип, [функціональне ядро, імперативна оболонка](topic:programming/functional-core-imperative-shell); тут ми доводимо його до краю, зробивши даними навіть перелік ефектів.

![Зліва явні входи (дані, час, кидок, конфіг) заходять у чисте ядро decide. Ядро видає праворуч стос карток-намірів (saveUser, appendLedger, notify) — це план як дані, синім. Далі вертикальна пунктирна межа зі світом; за нею крихітний виконавець (for e in план: run e) і стрілки від нього в світ — до БД і пошти, червоним](img/plan-as-data.svg)

*Ядро не робить ефектів — воно повертає план намірів як інертні дані. Світу торкається лише виконавець на самому краю; усе між входами й межею — чиста функція, яку можна оглянути й перевірити, не підіймаючи ні бази, ні пошти.*

Одне слово про **вичерпність**. Коли з'явиться четвертий вид наміру — скажімо, `pushNotify` — гарно, коли компілятор сам нагадає, що виконавець його ще не вміє. У TypeScript це роблять рядком `const _never: never = eff`: якщо лишився неврахований варіант, `eff` не звузиться до `never` і код не збереться. Мова з рідними сумами типів дає це задарма — ось той самий виконавець на Rust, де `match` **зобов'язаний** покрити всі варіанти, інакше помилка компіляції:

```rust
enum Effect {
    SaveUser(User),
    AppendLedger { user_id: u64, amount: i64, at: i64 },
    Notify { to: String, text: String },
}

fn run(eff: Effect, db: &mut Db, mailer: &Mailer) {
    match eff {                        // додаси варіант — доки не обробиш його тут, не збереться
        Effect::SaveUser(u)                          => db.save_user(u),
        Effect::AppendLedger { user_id, amount, at } => db.append_ledger(user_id, amount, at),
        Effect::Notify { to, text }                  => mailer.send(&to, &text),
    }
}
```

Це не дрібниця: перелік намірів — це чесний, видимий у типі список усього, що програма взагалі вміє робити зі світом. Додав нову дію — компілятор проведе тебе за руку туди, де її треба навчити виконувати.

## Тест: ядро — таблиця планів, оболонка — майже порожня

Ось де прийом окупається сповна — і саме тут видно, чим він відрізняється від простого розтину. Тест ядра не звіряє одне число. Він звіряє **весь план цілком**: які наміри, у якому порядку, з якими полями. І робить це прямим порівнянням даних — без жодного підставного об'єкта.

:::tabs
```ts
test("джекпот на щасливому кидку → повний план", () => {
  const user: User = { id: 7, email: "a@b.c", balance: 300, lastClaim: 0 };
  const cfg: Config = { baseBonus: 50, jackpotBonus: 500, jackpotChance: 0.05,
                        cooldownMs: 24 * 3600_000 };

  const plan = decideBonus(user, 25 * 3600_000, 0.03, cfg);   // 25 год, кидок 0.03

  expect(plan).toEqual([                                       // звіряємо ДАНІ, не поведінку
    { kind: "saveUser",     user: { id: 7, email: "a@b.c", balance: 800, lastClaim: 25*3600_000 } },
    { kind: "appendLedger", userId: 7, amount: 500, at: 25 * 3600_000 },
    { kind: "notify",       to: "a@b.c", text: "Джекпот! +500" },
  ]);
});

test("на кулдауні → план порожній", () => {
  const user: User = { id: 7, email: "a@b.c", balance: 300, lastClaim: 0 };
  expect(decideBonus(user, 2 * 3600_000, 0.9, cfg)).toEqual([]);   // 2 год — ще рано
});
```

    user = User(id=7, email="a@b.c", balance=300, last_claim=0)
    cfg  = Config(base_bonus=50, jackpot_bonus=500, jackpot_chance=0.05,
                  cooldown_ms=24 * 3_600_000)

    plan = decide_bonus(user, 25 * 3_600_000, 0.03, cfg)      # 25 год, кидок 0.03

    assert plan == [                                          # звіряємо ДАНІ, не поведінку
        SaveUser(User(id=7, email="a@b.c", balance=800, last_claim=25 * 3_600_000)),

        Notify("a@b.c", "Джекпот! +500"),
    ]

Порівняй це з тим, що звіряє тест у розтині «обчислення проти ефектів». Там ядро повертало число, і тест звіряв **число** — правильна сума. А *які ефекти станеться* — запис у базу, лист — перевіряли окремо, підставними об'єктами в оболонці. Тут ядро повертає весь план, і тест звіряє **самі наміри**: що на джекпот піде лист саме з текстом «Джекпот! +500», що ledger дістане саме +500, що на кулдауні не станеться взагалі нічого. Ми перевірили *рішення про ефекти*, жодного ефекту не вчинивши й жодного мока не написавши. Порожній план на кулдауні перевіряється так само тривіально, як і повний, — це просто `== []`.

Що ж лишилося перевірити в брудній частині? Дуже мало, і це навмисне. Виконавець дістає один вузенький тест: підстав фальшиві `db`/`mailer`, що лише записують, що їх покликали, згодуй по одному наміру кожного виду — і звір, що `saveUser` кличе `db.saveUser`, а `notify` кличе `mailer.send`. Це вся його логіка. Оболонку ж перевіряють одним наскрізним тестом: що дані з `loadUser` дійшли до ядра, а план дійшов до виконавця. Дротів мало — і помилок у них мало.

## Чим це не те саме, що розтин «обчислення проти ефектів»

Варто спинитися й чітко назвати різницю, бо два прийоми легко злити в один.

У розтині ядро повертає **значення** — суму, знижку, розкладку. Оболонка, отримавши значення, **сама вирішує**, що з ним зробити: у її коді жорстко стоять виклики `db.save(...)` і `notify(...)`. Логіка «які ефекти й з чим» лишається в оболонці, просто вона стала коротшою. Якби рішення про ефект розгалужувалося («слати лист лише на джекпот», «на кулдауні нічого не робити»), цей `if` жив би в оболонці — а отже, знову вимагав би мока, щоб його перевірити.

У прийомі «ефекти як значення» ядро повертає **сам план ефектів** — список намірів. Оболонка не вирішує нічого: вона тупо крутить список крізь виконавця. Розгалуження «слати лист лише на джекпот» тепер живе в ядрі як звичайні дані (у плані просто є або нема наміру `notify`), тож перевіряється прямим порівнянням списків. **Рішення «які ефекти» переїхало через межу — з імперативної оболонки в чисте ядро, ставши даними.**

![Два яруси. Угорі «розрізати обчислення й ефекти»: чисте ядро дає значення, а тонка оболонка сама містить вписані вручну db.save та notify — підпис «які ефекти вирішує ОБОЛОНКА». Місток посередині: «рішення які ефекти переносимо в ЯДРО — як дані». Унизу «ефекти як значення»: ядро дає список Effect (план як дані), і generic-виконавець for e: run e лише крутить список — підпис «які ефекти вирішує ЯДРО»](img/value-vs-plan.svg)

*Обидва прийоми лишають брудну частину тонкою, але межу «хто вирішує, які ефекти» вони проводять по-різному. Розтин лишає це рішення в оболонці (імперативно); «ефекти як значення» переносить його в ядро й робить даними — тоді виконавець стає повністю позбавленим рішень і однаковим для будь-якого ядра.*

Що це дає понад тестовність, заради чого варто городити другий рівень? Оскільки план — це дані, з ним можна робити те, чого зі звичайним викликом не зробиш: **записати** його в журнал перед виконанням (аудит: що система збиралася зробити), **відкласти** в чергу й виконати пізніше чи в іншому процесі, **повторити** при збої, **скасувати** (для намірів, що мають обернений), **згорнути** кілька планів в один. Усе це — не нові механізми, а просто наслідок того, що наміри — значення. До цієї спорідненості ми ще повернемось: вона стара й має шляхетні імена.

> 🔧 **Навіщо це.** Не хапайся за цей прийом усюди. Якщо ядро просто рахує число, а оболонка робить один-два безумовні ефекти — досить простого розтину, план намірів буде зайвою церемонією. Тягнися по «ефекти як значення» тоді, коли *рішення, які саме ефекти вчинити*, саме по собі розгалужене й варте перевірки, або коли план треба журналювати, чергувати, повторювати чи скасовувати. Ознака-підказка: тобі кортить написати тест «на такому вході система має зробити саме оці дії, і в такому порядку» — а це і є звірка плану.

## Пастки

Прийом стрункий, але має свої гострі кути. Розберемо три, на яких спотикаються найчастіше.

### Ефект, що читає результат попереднього

Це головна межа прийому, і про неї треба знати з самого початку. Плаский список намірів мовчазно припускає, що всі наміри **відомі наперед** — до того, як хоч один виконано. Але буває, що наступна дія потребує результату попередньої. Класика: вставили рядок у базу — база згенерувала `id` — і цей свіжий `id` треба покласти в наступний намір (скажімо, у лист). У момент складання плану `id` **ще не існує**: він народиться лише при виконанні першого наміру. Плаский `Effect[]` цього виразити не може — у ньому нема куди вписати «те число, що з'явиться пізніше».

![Угорі три незалежні наміри saveUser, appendLedger, notify стоять поряд, підпис «жоден не читає результату іншого — виконуй у будь-якому порядку». Унизу намір insert(row) дає новий id лише ПІСЛЯ виконання, а намір notify(user, id) цього id потребує; стрілка між ними підписана «id є лише після виконання». Нижній підпис: потрібен ЛАНЦЮГ, наступний крок = функція(результат), це форма монади IO (bind)](img/dependent-effects.svg)

*Поки наміри незалежні, плаский список ідеальний. Щойно намір починає потребувати результату попереднього, список ламається: у ньому нема місця для значення, якого ще нема. Це не вада реалізації, а межа самої форми «список».*

Виходів два. Перший — **дешевий і частий**: якщо залежність несправжня, прибери її. Замість того щоб ждати `id` від бази, **згенеруй його в ядрі** й передай як явний вхід (той самий зерновий кидок цілком годиться, щоб зробити унікальний ключ). Тоді обидва наміри — і вставка, і лист — від початку тримають той самий, ядром відомий `id`, і план знов пласкує. Дуже часто «залежність від результату ефекту» — це просто ознака, що якесь значення варто було породити в чистому ядрі, а не виривати зі світу.

Другий вихід — **чесний і глибший**: коли залежність справжня (значення справді може дати лише світ — курс валют із зовнішнього API, відповідь платіжного шлюзу), плаского списку замало **за побудовою**. Потрібна форма, де наступний крок — це **функція від результату попереднього**, а не готовий елемент списку. Тобто не «список намірів», а «намір, а тоді, дивлячись на його результат, наступний намір». Цю форму — зчеплення кроків через «а тоді, з результатом, роби далі» — і звуть **зв'язуванням** (англ. *bind*), і це вже не список, а деревце програми. Саме до нього ми прийдемо в розділі про монаду IO — воно і є її суть.

### Порядок

Список упорядкований, і виконавець іде ним згори вниз. Поки наміри незалежні, порядок ні на що не впливає — це та сама властивість, що й у чистих обчислень: незалежні дії можна робити в будь-якій черзі. Але щойно наміри залежні по світу — зберегти користувача **перед** тим, як слати лист (щоб лист не пішов на невдалий запис), — порядок стає навантаженим змістом. Добра новина: тепер цей порядок — **видимі дані** в плані, а не мовчазна послідовність рядків у тілі функції. Ти можеш його перевірити тестом (`plan[0].kind === "saveUser"`) і побачити очима. Погана: плаский список каже лише «зроби все, згори вниз» — він не вміє сказати «зроби Б, тільки якщо А вдалося». Це умовне «тільки якщо» — знову той самий зв'язок за результатом, знову крок за межу списку.

### Помилки

План — це **мрія**; світ у неї не питає дозволу. Ядро повернуло три наміри, а реальність зламала другий: база лягла, лист відскочив. Хто вирішує, що робити далі — спинитися? Йти далі? Відкотити зроблене? Ключова думка: **це вирішує виконавець, а не ядро**. Ядро планує щасливий шлях і чесно каже, що *хотіло* зробити; політику часткового провалу — «спинись на першій помилці», «спробуй ще тричі», «відкоти саму базу» — тримає виконавець, бо саме він живе на межі, де реальність кусає. Тримай ядро чесним у цьому: воно повертає наміри, але **не сміє припускати, що всі вони вдадуться**. А коли подальше рішення мусить залежати від того, вдався ефект чи ні, — ти знову вийшов зі світу пласких списків у світ зв'язування за результатом. Три пастки, як бачиш, зводяться до однієї межі: щойно наступне залежить від результату попереднього, плаский план треба міняти на ланцюг.

## Рідня: патерн «Команда» і монада IO

Ідея «запакуй дію в дані, а виконай окремо» — не винахід і не мода. Вона стара, і в неї двоє поважних родичів, названих у різні епохи різними спільнотами.

Перший — **[патерн «Команда»](topic:programming/command)** (англ. *Command*). Його описала «банда чотирьох» — Еріх Гамма, Річард Гелм, Ральф Джонсон і Джон Вліссідес — у книзі «Design Patterns» 1994 року (усталений факт). Формулювання майже дослівно про нас: «запакувати запит як об'єкт, щоб параметризувати клієнтів різними запитами, ставити запити в чергу, журналювати їх і підтримувати скасовувані операції». Кожен наш варіант `Effect` — це і є така команда-об'єкт: дія, запакована в дані. Наш `Effect[]` — черга команд; наш виконавець — той, кого в патерні звуть відправником (invoker). Усе, що патерн обіцяє — чергування, журнал, скасування, — падає нам у руки з того самого факту, що намір є значенням. Різниця лише в акценті: об'єктний патерн 90-х пакував команду в об'єкт із методом `execute()`, а ми пакуємо в **чисті дані** без жодного методу, і поведінку дає окремий виконавець. Дух той самий.

Другий родич — глибший і показує, куди веде дорога. Це те, як суто функційні мови приборкали введення-виведення. У Haskell значення типу `IO a` — це **не** виконаний ефект, а **опис** ефекту: програма будує велике таке значення, а виконує його вже середовище виконання на самому краю. Це дослівно наш прийом, доведений до принципу всієї мови: чисте всередині будує план, нечисте зовні його крутить. Модель «увести-вивести через значення, що описує ефект» запропонували Саймон Пейтон-Джонс (Simon Peyton Jones) і Філіп Вадлер (Philip Wadler) у праці «Imperative functional programming» на конференції POPL 1993 року, спираючись на роботу Ежіо Моджі (Eugenio Moggi) про монади 1991-го («Notions of Computation and Monads», журнал *Information and Computation*) (усталено; праця Пейтон-Джонса й Вадлера 2003-го дістала нагороду за десятирічний вплив).

І ось тут дві дороги сходяться. Наш плаский `Effect[]` — це **найпростіший, вироджений випадок** цієї моделі: скінченний список незалежних намірів. Монада IO — повний випадок: вона вміє те, чого список не вміє, — **зв'язати** наступний крок із результатом попереднього (той самий `bind` із пастки про залежні ефекти). Список — це «зроби ось це, тоді ось це» з наперед відомими кроками; монада — «зроби ось це, а тоді, **подивившись на результат**, вирішуй, що робити далі». Коли твій плаский план упирається в залежність за результатом, ти, по суті, доростаєш його до монади.

Загальний бік цієї ідеї — «зобрази програму як структуру даних із інструкцій, а виконання зроби окремим тлумаченням цієї структури» — у теорії звуть **вільною монадою** (англ. *free monad*); класичний виклад — стаття Воутера Свірстри (Wouter Swierstra) «Data Types à la Carte» (*Journal of Functional Programming*, 2008), де ефекти подано як дані, а виконання — як згортку над ними (усталено). Свіжіший берег тієї самої думки — **алгебричні ефекти**: ефект стає окремим елементом типу, який видно в сигнатурі й можна перехопити власним виконавцем. Так влаштовані оброблювачі ефектів в OCaml 5 (перший випуск — 2022 рік, підтримка ефектів експериментальна й поки без типізації самих ефектів; усталено), мова Koka Даана Лейєна (Daan Leijen) у Microsoft Research та «здібності» (abilities) в мові Unison. Усе це — нащадки однієї простої дитячої ідеї, з якої ми почали: намір — це дані, виконання — окремо.

## Коли тягтися по цей прийом

Звести все докупи можна коротким списком-пам'яткою — і водночас чесним застереженням, коли він зайвий.

```
Тягнися по «ефекти як значення», коли:
  – рішення, ЯКІ саме ефекти вчинити, саме по собі розгалужене
    (умовні ефекти, різні набори дій на різних входах) і варте тесту;
  – план треба журналювати / чергувати / повторювати / скасовувати
    (аудит намірів, відкладене чи міжпроцесне виконання);
  – хочеться один виконавець на багато ядер (усі рішення — в даних).

Досить простого розтину (значення + прямі ефекти в оболонці), коли:
  – ефекти безумовні й нечисленні — план буде зайвою церемонією.

Пам'ятай межу:
  – плаский Effect[] годиться, лише поки наміри НЕ залежать
    від результату одне одного;
  – щойно наступний крок = функція(результату попереднього) —
    список доростає до ланцюга (bind), тобто до форми монади IO.
```

Уся сила прийому — в одному зсуві, який легко проґавити за синтаксисом варіантів. Ми не просто винесли обчислення з бруду; ми зробили **саме рішення про бруд** — що робити зі світом, з чим і в якому порядку — звичайним значенням, яке чиста функція повертає, а тупий край виконує. Щойно ефект став даними, він перестав бути дією, яку можна лише вчинити наосліп, і став чимось, що можна оглянути, порівняти, зберегти, відкласти й перевірити прямим `==`. А те єдине, чого плаский список не вміє, — тримати крок, що залежить від результату попереднього, — не глухий кут, а вказівник: там, де він тобі знадобиться, починається монада IO, і ти вже стоятимеш на її порозі, розуміючи, звідки вона росте.
