# ⚙️ Витягуємо чисте ядро з нечистої функції

Ось функція, яку ти зустрінеш у будь-якому реальному проєкті. Її написали три роки тому, за той час вона обросла вимогами, і тепер вона робить усе одразу: рахує складну знижку, читає курс валют із глобального конфіга, пише результат у базу, лишає рядок у лозі й дорогою псує об'єкт, який їй передали. Вона працює. Її бояться чіпати. І кожна спроба покрити її тестом розбивається об те, що для одного `assert` треба підняти базу, налаштувати глобальний стан і перехопити вивід.

Це не вигаданий приклад — це типовий стан коду, який писали під тиском строків. І є рівно один прийом, що перетворює таку функцію з мороку на щось, у чому легко розібратися: **витягти з неї чисте ядро**. Не переписати з нуля, не додати шар абстракцій — а механічно, крок за кроком, відокремити обчислення (яке нічого не чіпає) від ефектів (які тягнуть дані ззовні й виливають назовні). Розберемо це на живому C++, від смердючого «до» до чистого «після», з тестами й вимірами, наскільки простішає життя.

## Задача: функція, що робить усе

Нехай ми пишемо бекенд крамниці. Є замовлення — кошик товарів, — і треба порахувати підсумок: сума позицій, знижка за обсяг, знижка постійного клієнта, податок, доставка. Логіка не тривіальна: знижки не додаються, а множаться каскадом, податок береться після знижок, доставка безкоштовна від певної суми. Ось як воно виглядає в коді, який ми успадкували:

:::tabs
```cpp
// ── ДО: одна функція робить усе ──────────────────────────────────
#include <string>
#include <vector>
#include <iostream>

struct Item { double price; int qty; };

struct Order {
    int              id;
    std::string      customerTier;   // "regular" | "silver" | "gold"
    std::vector<Item> items;
    double           computedTotal;  // ← сюди функція запише результат
};

// глобальний стан — прихований вхід, про який сигнатура мовчить
double g_taxRate      = 0.20;
double g_freeShipFrom = 500.0;
double g_shipCost     = 49.0;

Database db;   // глобальне з'єднання з базою
Logger   log;  // глобальний лог

double computeOrderTotal(Order& order) {          // Order& — не const!
    double subtotal = 0.0;
    for (Item& it : order.items)
        subtotal += it.price * it.qty;

    // знижка за обсяг
    double volumeDisc = 0.0;
    if      (subtotal > 1000.0) volumeDisc = 0.10;
    else if (subtotal >  300.0) volumeDisc = 0.05;

    // знижка за рівень клієнта
    double tierDisc = 0.0;
    if      (order.customerTier == "gold")   tierDisc = 0.08;
    else if (order.customerTier == "silver") tierDisc = 0.04;

    // каскад: спершу обсяг, тоді рівень (множаться, не додаються)
    double afterDisc = subtotal * (1.0 - volumeDisc) * (1.0 - tierDisc);

    // податок із глобального курсу
    double taxed = afterDisc * (1.0 + g_taxRate);

    // доставка
    double shipping = (afterDisc >= g_freeShipFrom) ? 0.0 : g_shipCost;
    double total    = taxed + shipping;

    // ── а тепер ефекти, розсипані по функції ──
    order.computedTotal = total;                       // мутація входу
    db.saveTotal(order.id, total);                     // запис у базу
    log.info("order " + std::to_string(order.id) +
             " total=" + std::to_string(total));       // вивід у лог
    std::cout << "DEBUG total=" << total << "\n";       // ще й у консоль

    return total;
}
```

Придивись, скільки різних відповідальностей злиплося в одному тілі. Функція **рахує** (уся арифметика знижок і податку), **читає світ** (три глобальні змінні), **пише світ** (базу, лог, консоль) і **псує вхід** (поле `computedTotal` переданого `order`). Її сигнатура — `double computeOrderTotal(Order&)` — обіцяє «дай замовлення, отримай число», але це напівправда: насправді відповідь залежить ще й від трьох глобальних змінних, а після виклику змінюється база, лог і сам `order`.

> 🔧 **Навіщо це.** Щоб побачити біль на власні очі, спробуй подумки написати тест «знижка gold на кошику 1200 грн дає правильний підсумок». Тобі треба: (1) виставити `g_taxRate`, `g_freeShipFrom`, `g_shipCost` у відомі значення — і не забути повернути назад, бо інші тести їх читають; (2) підмінити `db`, щоб `saveTotal` не ліз у справжню базу; (3) підмінити `log`; (4) якось приглушити `std::cout`. Чотири підготовки заради однієї перевірки арифметики. Це і є ціна злиплих відповідальностей — вона стягується з тебе щоразу, коли треба щось перевірити.

## Ідея: розрізати по шву «обчислення проти ефектів»

Прийом простий і механічний. У функції є природний шов — межа між «порахувати число» і «щось із цим числом зробити у світі». Уся арифметика від `subtotal` до `total` не залежить від бази, лога чи консолі; вона залежить лише від даних замовлення й трьох параметрів. А ефекти — чотири останні рядки — навпаки, нічого не рахують, лише розносять готове число.

Ми проводимо розтин рівно по цьому шву. **Обчислення** переїжджає у власну функцію, яка бере **все потрібне явним аргументом** (зокрема три колишні глобальні змінні) і **повертає результат значенням**, нічого не чіпаючи. Це чисте ядро. **Ефекти** лишаються в старій функції, яка тепер робиться тонкою: підняти вхідні дані, покликати ядро, рознести результат.

Щоб ядро було по-справжньому чистим, а не «майже», варто ще й прибрати приховані входи в окрему структуру-знімок. Три глобальні змінні податку й доставки — це насправді **політика ціноутворення**; зберемо їх у `Pricing`, і тоді ядро прийматиме її явно. Так само результат не мусить бути голим `double`: якщо ядро поверне структуру з розкладкою (проміжна сума, знижка, податок, доставка), оболонці буде що записати, а тестам — що звірити.

:::tabs
```cpp
// ── знімок політики: колишні глобальні змінні, тепер явний вхід ──
struct Pricing {
    double taxRate      = 0.20;
    double freeShipFrom = 500.0;
    double shipCost     = 49.0;
};

// ── результат: розкладка, а не голе число ──
struct Totals {
    double subtotal;
    double discount;    // сума, на яку знижено
    double tax;
    double shipping;
    double total;
};
```
```python
# ── знімок політики: колишні глобальні змінні, тепер явний вхід ──

@dataclass
class Pricing:
    tax_rate:       float = 0.20
    free_ship_from: float = 500.0
    ship_cost:      float = 49.0

# ── результат: розкладка, а не голе число ──
@dataclass
class Totals:
    subtotal: float
    discount: float     # сума, на яку знижено
    tax:      float
    shipping: float
    total:    float
```

## Робочий C++: чисте ядро й тонка оболонка

Ось те саме, розрізане по шву. Спершу — ядро: жодного `db`, `log`, `cout`, жодної глобальної змінної, вхід `const`, усе повертається значенням.

:::tabs
```cpp
// ── ПІСЛЯ, частина 1: ЧИСТЕ ЯДРО ─────────────────────────────────
// const-посилання на вхід + Pricing явним аргументом + повернення значенням.
// Ніяких db/log/cout/глобалей. Той самий вхід → той самий вихід, завжди.
Totals computeTotals(const Order& order, const Pricing& p) {
    double subtotal = 0.0;
    for (const Item& it : order.items)         // const Item& — не зіпсуємо вхід
        subtotal += it.price * it.qty;

    double volumeDisc = 0.0;
    if      (subtotal > 1000.0) volumeDisc = 0.10;
    else if (subtotal >  300.0) volumeDisc = 0.05;

    double tierDisc = 0.0;
    if      (order.customerTier == "gold")   tierDisc = 0.08;
    else if (order.customerTier == "silver") tierDisc = 0.04;

    double afterDisc = subtotal * (1.0 - volumeDisc) * (1.0 - tierDisc);
    double taxed     = afterDisc * (1.0 + p.taxRate);
    double shipping  = (afterDisc >= p.freeShipFrom) ? 0.0 : p.shipCost;

    return Totals{
        subtotal,
        subtotal - afterDisc,   // скільки всього знижено
        taxed - afterDisc,      // сам податок
        shipping,
        taxed + shipping        // підсумок
    };
}
```
```python

    elif order.customer_tier == "silver": tier_disc = 0.04

    taxed      = after_disc * (1.0 + p.tax_rate)

        subtotal,
        subtotal - after_disc,   # скільки всього знижено
        taxed - after_disc,      # сам податок
        shipping,
        taxed + shipping,        # підсумок
    )
```
:::

Тепер оболонка. Вона робить рівно три речі: приносить дані, кличе ядро, виносить ефекти. Жодного обчислення в ній не лишилося — лише транспорт.

:::tabs
```cpp
// ── ПІСЛЯ, частина 2: ТОНКА ІМПЕРАТИВНА ОБОЛОНКА ─────────────────
// Приносить дані → кличе чисте ядро → виносить ефекти. Рішень тут нема.
double handleOrder(int orderId, Database& db, Logger& log, const Pricing& p) {
    Order order = db.loadOrder(orderId);          // ефект: читання ззовні

    Totals t = computeTotals(order, p);           // ← усе рішення тут, у чистому

    db.saveTotal(orderId, t.total);               // ефект: запис назовні
    log.info("order " + std::to_string(orderId) +
             " total=" + std::to_string(t.total));// ефект: вивід
    return t.total;
}
```
```python
# ── ПІСЛЯ, частина 2: ТОНКА ІМПЕРАТИВНА ОБОЛОНКА ─────────────────
```

Зверни увагу на кілька речей, що сталися ніби між іншим. По-перше, `db`, `log`, `Pricing` тепер **параметри**, а не глобальні змінні — оболонка бере залежності явно, тож у тесті їх легко підмінити, а в проді зібрати з реальних. По-друге, `order` більше **не мутується**: ядро прийняло його `const`, а поле `computedTotal` ми взагалі прибрали як зайве — розкладку тримає `Totals`, і хто хоче зберегти щось у базу, бере це з повернутого значення, а не з попсованого об'єкта. По-третє, налагоджувальний `std::cout` зник — йому не місце в проді (нижче ще повернемось, чому саме лог, а не `cout`).

> 🔧 **Навіщо це.** Розтин не додав жодного нового поняття — ті самі знижки, той самий податок. Він лише **розклав злиплі відповідальності по різних місцях**: рахунок окремо, транспорт окремо. Але саме цього досить, щоб уся складна частина (арифметика) стала тривіальною для тестів, а частина, що лишилась брудною (оболонка), — такою дрібною, що в ній майже нема де сховатися помилці. Цей поділ «чисте всередині, брудне зовні» — окремий структурний принцип, [функціональне ядро, імперативна оболонка](topic:programming/functional-core-imperative-shell); тут ми бачимо його найдрібнішу клітинку — розчеплення однієї функції.

## Тест стискається до кількох assert

Ось де окупається вся робота. Пригадай, що для тесту функції «до» треба було виставити три глобальні змінні, підмінити базу, підмінити лог і приглушити консоль. Тепер тест ядра виглядає так:

:::tabs
```cpp
// ── Тест ЧИСТОГО ядра: увесь тест — вхід і очікуваний вихід ──────
void test_totals() {
    Pricing p;   // дефолтна політика: tax 0.20, freeShip 500, ship 49

    // gold, кошик 1200 → обсяг >1000 дає 10%, gold дає 8%
    // 1200 · 0.90 · 0.92 = 993.6 ; податок ×1.20 = 1192.32
    // 993.6 ≥ 500 → доставка безкоштовна, тож total = 1192.32
    Order gold{1, "gold", {{600.0, 2}}};
    Totals g = computeTotals(gold, p);
    assert(std::abs(g.total - 1192.32) < 1e-6);

    // regular, кошик 200 → жодної знижки, доставка платна
    // 200 ×1.20 = 240 + 49
    Order small{2, "regular", {{200.0, 1}}};
    assert(std::abs(computeTotals(small, p).total - 289.0) < 1e-6);

    // порожній кошик → усе нулі, доставка платна
    Order empty{3, "regular", {}};
    assert(std::abs(computeTotals(empty, p).total - 49.0) < 1e-6);
}
```
```python
# ── Тест ЧИСТОГО ядра: увесь тест — вхід і очікуваний вихід ──────
from math import isclose

def test_totals():
    p = Pricing()   # дефолтна політика: tax 0.20, freeShip 500, ship 49

    # gold, кошик 1200 → обсяг >1000 дає 10%, gold дає 8%
    # 1200 · 0.90 · 0.92 = 993.6 ; податок ×1.20 = 1192.32
    # 993.6 ≥ 500 → доставка безкоштовна, тож total = 1192.32
    gold = Order(1, "gold", [Item(600.0, 2)])
    g = compute_totals(gold, p)
    assert isclose(g.total, 1192.32, abs_tol=1e-6)

    # regular, кошик 200 → жодної знижки, доставка платна
    # 200 ×1.20 = 240 + 49
    small = Order(2, "regular", [Item(200.0, 1)])
    assert isclose(compute_totals(small, p).total, 289.0, abs_tol=1e-6)

    # порожній кошик → усе нулі, доставка платна
    empty = Order(3, "regular", [])
    assert isclose(compute_totals(empty, p).total, 49.0, abs_tol=1e-6)
```
:::

Кожен випадок — три рядки: збери вхід, поклич ядро, звір число. **Немає** налаштування глобального стану, **немає** підміни бази чи лога (моків), **немає** прибирання після себе, **немає** перехоплення `cout`. Тест читається як таблиця «вхід → очікуваний вихід», бо ядро саме такою таблицею і є — прозорість за посиланням у чистому вигляді.

Порахуймо, наскільки стиснувся тест. Умовний тест функції «до», написаний чесно, — це приблизно:

```
рядки коду тесту:
  до  (нечиста):  ~4 підготовки + підміна db + підміна log
                  + перевірка числа + перевірка запису в db
                  + прибирання глобалей          ≈ 15–20 рядків на 1 випадок
  після (ядро):   збери вхід + assert            ≈ 2–3 рядки на 1 випадок
```

І це лінійно: у «до» кожен новий випадок тягне свій блок налаштування-прибирання, у «після» — ще один `assert`. На десяти випадках різниця стає прірвою. Саме тому кажуть, що чистота — це [тестовність](topic:programming/testability-tactics), вбудована в саму форму функції: ти не пишеш тести легше завдяки хитрій бібліотеці, ти пишеш їх легше тому, що функція за побудовою не має чого приховувати.

Оболонку теж треба перевірити — але там перевіряти майже нічого, і це навмисно. Один інтеграційний тест із підставними `db`/`log` (у пам'яті) підтверджує, що оболонка **справді кличе** ядро й **справді розносить** результат — що дані з `loadOrder` доходять до `computeTotals`, а `total` доходить до `saveTotal`. Уся арифметика вже покрита тестами ядра, тож тут ми ловимо лише помилки з'єднання дротів, а їх мало, бо й дротів мало.

## Мемоізація: безпечна саме через чистоту

Тепер найцікавіше — те, що чистота **вмикає**, а нечистота робить неможливим. Уяви, що `computeTotals` кличуть багато й часто, а кошики повторюються: та сама конфігурація замовлення прораховується знову й знову (перерахунок кошика на кожен рух миші у вітрині, масовий перерахунок прайсу тощо). Обчислення саме по собі не безкоштовне — рядкові порівняння рівня, цикл по позиціях. Напрошується: порахувати раз для даного входу й **запам'ятати**, а на повторний той самий вхід віддати збережене.

Це й зветься **мемоізація (англ. *memoization*, від *memo* — пам'ятка)**. Термін увів британський дослідник штучного інтелекту Дональд Мічі 1968 року в статті «"Memo" Functions and Machine Learning» (журнал *Nature*): він назвав «memo-функціями» ті, що ведуть таблицю вже обчислених результатів і на повторний виклик беруть відповідь із неї замість перерахунку (усталений факт).

Механіка — кеш «аргументи → результат». Ключем служить сам вхід (тут — усе, від чого залежить ядро: позиції, рівень клієнта, політика); значенням — уже пораховані `Totals`.

:::tabs
```cpp
// ── Мемоізована обгортка над ЧИСТИМ ядром ────────────────────────
#include <unordered_map>
#include <sstream>

// ключ кеша = усе, від чого залежить результат (весь вхід ядра).
static std::string cacheKey(const Order& o, const Pricing& p) {
    std::ostringstream k;
    k << o.customerTier << '|'
      << p.taxRate << '|' << p.freeShipFrom << '|' << p.shipCost;
    for (const Item& it : o.items) k << '|' << it.price << 'x' << it.qty;
    return k.str();
}

Totals computeTotalsMemo(const Order& order, const Pricing& p) {
    static std::unordered_map<std::string, Totals> cache;

    std::string key = cacheKey(order, p);
    auto found = cache.find(key);
    if (found != cache.end())
        return found->second;                 // ← влучили: віддаємо збережене

    Totals t = computeTotals(order, p);        // промах: рахуємо ядром
    cache.emplace(key, t);                     // і запам'ятовуємо
    return t;
}
```
```python
# ── Мемоізована обгортка над ЧИСТИМ ядром ────────────────────────

# ключ кеша = усе, від чого залежить результат (весь вхід ядра).
def cache_key(o: Order, p: Pricing) -> str:
    parts = [o.customer_tier,
             f"{p.tax_rate}", f"{p.free_ship_from}", f"{p.ship_cost}"]
    parts += [f"{it.price}x{it.qty}" for it in o.items]
    return "|".join(parts)

_cache: dict[str, Totals] = {}   # стан між викликами (роль C++ static)

def compute_totals_memo(order: Order, p: Pricing) -> Totals:
    key = cache_key(order, p)
    found = _cache.get(key)
    if found is not None:
        return found                          # ← влучили: віддаємо збережене

    t = compute_totals(order, p)              # промах: рахуємо ядром
    _cache[key] = t                           # і запам'ятовуємо
    return t
```
:::

І тут — головна думка всієї цієї вставки, заради якої вона й написана. **Чому цей кеш коректний?** Бо ядро чисте. Прозорість за посиланням каже: виклик `computeTotals(order, p)` можна без наслідків замінити його значенням. Кеш робить рівно це — замінює повторний виклик збереженим значенням першого. Оскільки той самий вхід **гарантовано** дає той самий вихід (перша обіцянка чистоти) і виклик **нічого не міняє** у світі (друга обіцянка), пропущений другий виклик нічого не ламає: ані відповідь не з'їхала, ані якийсь ефект не загубився, бо ефектів і не було.

> 🔧 **Навіщо це.** Кеш чистої функції — це найдешевша оптимізація, яку взагалі можна зробити: обгортка на десять рядків, і жодного ризику зіпсувати логіку, бо ти нічого в логіці не змінив — лише пропускаєш повторне обчислення того, що вже точно знаєш. Компілятор, до речі, робить те саме дрібніше: чисту підфункцію без ефектів він може винести з циклу чи порахувати раз, бо знає, що двічі — те саме. Чистота — це дозвіл оптимізувати, виданий наперед.

Тепер спробуй уявити той самий кеш поверх функції «до» — і побачиш, чому це неможливо. Що станеться, якщо ми закешуємо `computeOrderTotal(order)` і на повторний виклик віддамо збережене число, **пропустивши тіло**?

- `db.saveTotal` **не викличеться** — база не оновиться, хоча код гадає, що оновив;
- `log.info` **промовчить** — у лозі зникне запис, за яким хтось стежить;
- `order.computedTotal` **не запишеться** — поле лишиться старим;
- а якщо між викликами хтось змінив `g_taxRate`, кеш віддасть **застаріле** число, бо ключ його не враховує — глобальна змінна не в аргументах, її туди й не покласти чесно.

Кеш поверх нечистого — це не оптимізація, а **тихе гублення ефектів і застарілі відповіді**. Саме тому мемоізацію не можна «прикрутити збоку» до нечистої функції: спочатку треба виділити чисте ядро, і кешувати вже його. Нечистота не просто заважає кешу — вона робить кеш прихованим джерелом багів, які виявляться далеко від місця, де ти його поставив.

## Пастки: що ламає чистоту тихо, а що ні

Розтин здається простим, але кілька речей регулярно псують результат — і не завжди очевидно які. Розберемо їх, бо саме на них спотикаються, коли гадають, що ядро вже чисте, а воно ще ні.

### Прихована мутація через посилання

Найпідступніша пастка. Ти зробив вхід `const`-посиланням — і думаєш, що застрахувався. Але `const` у C++ поверхневий: він забороняє міняти сам об'єкт, а не те, на що той об'єкт вказує чи посилається.

```cpp
struct Cart {
    std::vector<Item>* items;   // ПОКАЖЧИК: const його не захистить
    Discount*          policy;
};

double computeBad(const Cart& cart) {   // cart const, але...
    cart.items->push_back({0,0});       // ← змінюємо чужі дані! компілюється!
    cart.policy->timesUsed++;           // ← і ще раз! теж компілюється
    // ...
}
```

`const Cart&` обіцяє не чіпати `cart`, і формально ми його й не чіпаємо — ми чіпаємо `*cart.items`, чужий вектор, на який `cart` лише вказує. Компілятор пропускає це мовчки, а функція перестає бути чистою: після виклику чийсь вектор виріс. **Правило-запобіжник:** чисте ядро приймає вхід **за значенням або за `const&` на об'єкт, що сам володіє даними** (як `const Order&` вище, де `items` — це `std::vector` усередині, а не покажчик назовні). Покажчики й посилання на змінні дані всередині «чистого» входу — червоний прапорець: крізь них ефект просочується повз `const`.

### Локальні присвоєння — це НЕ порушення чистоти

А ось протилежний бік, де надмірна суворість шкодить. Люди іноді думають, що чиста функція взагалі не сміє нічого присвоювати — мовляв, будь-яка зміна пам'яті нечиста. Це не так, і плутати ці речі означає писати незграбний код на порожньому місці.

```cpp
Totals computeTotals(const Order& order, const Pricing& p) {
    double subtotal = 0.0;              // локальна змінна
    for (const Item& it : order.items)
        subtotal += it.price * it.qty;  // присвоєння в циклі — СКІЛЬКИ завгодно
    // ...
}
```

`subtotal` створюється всередині функції, живе тільки в ній і вмирає з поверненням. Її ніхто ззовні не бачить — ні до виклику, ні після. Тому неважливо, скільки разів ми її змінимо: ефект **не просочується** за межі функції, світ до і після виклику однаковий, той самий вхід дає той самий вихід. Функція лишається **абсолютно чистою** попри цикл із десятком присвоєнь.

Ключ ось у чому: чистоту ламає не зміна пам'яті сама собою, а **зміна, видима назовні**. Локальна змінна невидима — тож роби з нею що завгодно. Глобальна змінна, поле переданого об'єкта, дані за чужим покажчиком — видимі, тож їх чіпати не можна. Різниця не в тому, «присвоюємо чи ні», а в тому, «просочується назовні чи ні». Хто цього не розрізняє, той або дарма мучиться, виганяючи безневинні локальні присвоєння, або дарма спокійний, лишаючи отруйні глобальні.

### Схована `static` — глобальна змінна під маскою

Найлукавіша з отруйних мутацій — локальна `static`. Вона виглядає як локальна змінна (оголошена в тілі функції), але поводиться як глобальна: живе між викликами й пам'ятає.

```cpp
int nextInvoiceNo() {
    static int counter = 1000;   // виглядає локальною, а насправді глобальна
    return counter++;            // ← пам'ять між викликами: НЕ чиста
}
```

`counter` створюється раз на всю програму, не на виклик. Тому `nextInvoiceNo()` порушує першу обіцянку чистоти вже кричуще: той самий (порожній) вхід дає щоразу інше число. Така функція детермінованою бути не може за побудовою, і кешувати її — безглуздя (що кешувати, як щоразу інакше?).

Тут криється тонкість, на якій легко обпектися. У мемоізованій `computeTotalsMemo` вище **теж** стоїть `static` — `static std::unordered_map cache`. Хіба це не робить її нечистою? Формально — так, `computeTotalsMemo` не чиста: у неї є прихований стан (кеш), що живе між викликами. Але цей стан **навмисне невидимий у результаті**: кеш впливає лише на **швидкість**, ніколи на **відповідь**. Той самий вхід дає те саме число — байдуже, влучили ми в кеш чи порахували наново. Це той рідкісний випадок, коли ефект (запис у кеш) свідомо тримають нешкідливим: він не змінює **результату** обчислення, а лише економить час. Тому мемоізована обгортка **зовні поводиться як чиста** (те саме число на той самий вхід), хоча всередині має стан. Різниця з `nextInvoiceNo` — прірва: там прихований стан **керує відповіддю**, тут — лише прискорює її. Перше отруйне, друге терпиме; і саме тому кеш можна ставити на `computeTotals`, а «мемоізувати» `nextInvoiceNo` не має сенсу — її результат і є її стан.

> 🔧 **Навіщо це.** Коли переносиш обчислення в ядро, пройдися очима по тілу й познач кожну `static`: вона майже завжди — прихований вхід або прихований вихід, який зламає чистоту. Або прибери її (винеси стан в аргумент/результат), або свідомо визнай як нешкідливий кеш, що не чіпає відповіді. Третього — «нехай собі буде» — нема: непомічена `static` це та сама пастка, що й глобальна змінна, тільки її гірше видно.

### Лог і `assert` — терпимий бруд

І остання, дрібніша пастка — у протилежний бік. Коли ми викинули `std::cout` з оболонки, могло здатися, що будь-який вивід — зло, і треба гнати й `log.info`. Але це перегин.

Запис у лог — формально ефект (щось з'явилося назовні), але він **не впливає на результат** обчислення й **не псує чужих даних**. Прибери всі логи — числа не зміняться, тести пройдуть так само. Тому лог у **оболонці** — цілком доречний: оболонка й так брудна за призначенням, її діло — виносити ефекти, і лог серед них законний. Так само `assert` усередині ядра (перевірити передумову) — терпимий: він або мовчить, або валить програму, але ніколи не змінює відповіді на нормальному вході.

А `std::cout` ми викинули не тому, що вивід гріх, а тому, що йому не місце в **бізнес-функції** проду: діагностичний друк у консоль — це слід від налагодження, який мав би йти через лог із рівнями, а не сирим потоком. Різниця тонка, але реальна: `log.info` в оболонці — свідомий ефект на своєму місці; `std::cout` посеред розрахунку — забутий сміттєвий слід. Чистота — [шкала](topic:programming/immutability), а не прапорець: ядро тримаємо на ідеально чистому кінці, оболонці дозволяємо нешкідливий бруд на кшталт лога, а безладний `cout` посеред логіки прибираємо як те, що не належить ні там, ні там.

## Що лишається в руках

Розтин однієї роздутої функції звівся до кількох механічних рухів, які варто тримати як список:

```
1. Знайди шов: де кінчається «порахувати» й починається «зробити зі світом».
2. Обчислення → власна функція:
     – вхід за значенням / const& на self-owning дані;
     – усі приховані входи (глобалі) стають явними аргументами;
     – результат повертається значенням (краще розкладкою-структурою);
     – жодного db / log / cout / глобалі всередині.
3. Ефекти → лишаються в тонкій оболонці: принести дані → покликати
   ядро → рознести результат. Рішень в оболонці нема.
4. Познач кожну static: прибрати або визнати нешкідливим кешем.
5. Тести ядра — таблиця «вхід → assert», без моків і прибирання.
6. Треба швидше — став кеш на ЯДРО (не на оболонку): чистота робить
   його коректним даром.
```

Уся сила прийому в тому, що він **нічого не вигадує** — ті самі знижки, той самий податок, той самий результат. Він лише розкладає злиплі відповідальності по місцях, де кожну видно окремо. І з цього розкладу безкоштовно випадає все інше: тести на два рядки, кеш без ризику, безпека в багатьох потоках (чисте ядро нема чим зіпсувати одночасним викликом), баг, що ловиться щоразу. Тому щоразу, коли натрапиш на функцію, яка **і** рахує складне, **і** лізе у світ, — не бійся її, а розріж по шву: складне винеси в чисте, а неминучий бруд лиши тонким шаром зовні, де він найменше шкодить.
