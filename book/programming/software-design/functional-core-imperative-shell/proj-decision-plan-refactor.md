# ⚙️ Рефакторинг до плану ефектів: розчепити переплетений обробник

Ось обробник, який ти напевно вже писав або успадкував. Приходить транзакція, і система має вирішити, що з нею робити: якщо сума підозріло велика — позначити на перевірку; якщо на рахунку раптом мінус — заморозити його; у будь-якому разі — сповістити клієнта й лишити слід в журналі. Логіка не хитра сама по собі: три-чотири `if`, кожен зрозумілий окремо. Але вона зрослася з дією — читає рахунок із бази, пише прапорці назад, шле пуш клієнтові, кладе рядок у лог. І щойно ти сідаєш це перевірити, з'ясовується, що ти не тестуєш логіку, а піднімаєш пів системи навколо неї: фальшива база, фальшивий поштар, фальшивий журнал, перехоплений годинник.

Розберемо, як розчепити такий обробник **до кінця** — не «сховати базу за інтерфейс», а винести все рішення в чисту функцію, яка повертає **план ефектів**: список описів того, що треба зробити, як звичайні дані. Оболонка потім цей план **виконує**. Ми пройдемо шлях від переплетеної версії до плану, поміряємо лінійкою, скільки риштування зникло з тестів, розберемо важчий випадок «читати → вирішити → діяти → читати ще → вирішити», і чесно назвемо, де цей прийом перегинати не варто.

## Задача: обробник, що вирішує й діє в одному тілі

Нехай ми пишемо антифрод бекенду платіжної системи. Функція `handleTransaction` дістає рахунок, дивиться на транзакцію й вирішує долю кількох дій. Ось код, який ми успадкували, — він працює, і його бояться чіпати:

:::tabs
```ts
// ── ДО: рішення й дія намертво сплетені ──
async function handleTransaction(accountId: string, tx: Transaction): Promise<void> {
  const acc = await db.loadAccount(accountId);        // дія: читання

  // ── а тут, упереміш із діями, ховається все рішення ──
  if (tx.amount > acc.dailyLimit) {
    await db.flagTransaction(tx.id, "over-limit");     // дія: запис
    await notifier.push(acc.userId, "Транзакцію відкладено на перевірку");
  }

  const newBalance = acc.balance - tx.amount;
  if (newBalance < 0) {
    await db.freezeAccount(accountId);                 // дія: запис
    await notifier.push(acc.userId, "Рахунок заморожено: недостатньо коштів");
  } else {
    await db.setBalance(accountId, newBalance);        // дія: запис
  }

  await audit.log(`tx ${tx.id} on ${accountId}: amount=${tx.amount}`); // дія: запис
}
```

:::

Придивись, що тут переплелося. Функція **вирішує** — «чи понад ліміт», «чи вистачає коштів», «що з цього випливає» — і в тих самих рядках **діє**: читає базу, пише прапорці, шле пуші, лишає лог. Рішення й дія не просто сусідять, вони **перемішані по рядках**: `if` стоїть, а всередині нього одразу `await db.flag…`. Це найгірший різновид сплетіння — не «спершу все порахували, потім усе зробили», а «вирішили дрібку, зробили дрібку, вирішили ще, зробили ще».

> 🔧 **Навіщо це.** Щоб відчути ціну на власній шкурі, спробуй подумки написати один тест: «транзакція понад денний ліміт має позначитися на перевірку». Тобі треба: підсунути фальшиву `db`, щоб `loadAccount` віддала рахунок із відомим лімітом, а `flagTransaction` не полізла у справжню базу; підмінити `notifier`, щоб `push` не слав справжнього пуша; підмінити `audit`, щоб лог не засмічував систему. Три підробки заради перевірки одного `if`. І це найлегший тест — на «заморозити рахунок» їх буде стільки ж. Кожен новий випадок тягне свій набір підробок, бо перевіряти рішення можна лише **крізь** дії, з якими воно зрослося.

## Ідея: нехай ядро поверне ПЛАН, а не робить

Ключ до розчеплення — питання, яке звучить майже наївно: а що, як функція, замість **робити** дії, просто **скаже**, які дії треба зробити? Не «надішли пуш», а «ось намір надіслати пуш — тримай його як дані». Не «запиши баланс», а «ось опис: треба записати такий баланс». Тоді все рішення — вибір, які наміри покласти в список, — стає чистим обчисленням, бо складання списку нічого у світі не чіпає. А виконання цих намірів — окрема, тупа робота для оболонки.

Ця думка називається **ефекти як дані (англ. *effects as data*)**: замість виконувати побічний ефект на місці, чиста функція повертає його **опис** — звичайне значення, що каже *що* зробити, але саме нічого не робить. Такий опис іноді звуть **командою** або елементом **плану**. Оболонка бере план і **інтерпретує** його — проходить список і для кожного опису виконує справжню дію.

Перше, що треба зробити, — назвати ефекти типами. Що взагалі вміє робити наш обробник зі світом? Позначити транзакцію, заморозити рахунок, виставити баланс, штовхнути пуш, записати в лог. П'ять видів дій — п'ять варіантів опису:

:::tabs
```ts
// ── Ефект як дані: опис дії, а не сама дія ──
type Effect =
  | { kind: "flag";     txId: string; reason: string }
  | { kind: "freeze";   accountId: string }
  | { kind: "setBalance"; accountId: string; amount: number }
  | { kind: "notify";   userId: string; message: string }
  | { kind: "audit";    line: string };

// План — просто список описів. Це чисті дані, у них нічого не «діється».
type Plan = Effect[];
```
```py
from dataclasses import dataclass

# ── Ефект як дані: опис дії, а не сама дія ──
@dataclass(frozen=True)
class Flag:       tx_id: str; reason: str
@dataclass(frozen=True)
class Freeze:     account_id: str
@dataclass(frozen=True)
class SetBalance: account_id: str; amount: float
@dataclass(frozen=True)
class Notify:     user_id: str; message: str
@dataclass(frozen=True)
class Audit:      line: str

# План — просто список описів. Це чисті дані, у них нічого не «діється».
Effect = Flag | Freeze | SetBalance | Notify | Audit
Plan = list[Effect]
```
:::

Зверни увагу: у цих типах **немає жодного дієслова, що чіпає світ**. `Notify` не шле пуша — це просто запис «кому» і «що». `SetBalance` не пише в базу — це пара «рахунок» і «сума». Опис ефекту так само пасивний, як число чи рядок; його можна створити, покласти в список, порівняти, надрукувати — і при цьому нічого не станеться. Уся дія відкладена до того моменту, коли хтось **вирішить його виконати**. Саме ця відкладеність і робить план придатним для чистого ядра: скласти список намірів — операція без побічних ефектів, хоч самі наміри й описують ефекти.

## Робочий код: чисте ядро будує план, тонка оболонка його виконує

Тепер розріжемо обробник по шву. Спершу — ядро. Воно бере **знімок** усього, що потрібно для рішення (рахунок і транзакцію — звичайні значення, які йому **принесли**), і повертає план. Жодного `db`, `notifier`, `audit`, жодного `await` — усередині ядра світу не існує.

:::tabs
```ts
// ── ПІСЛЯ, ядро: чиста функція від даних до ПЛАНУ ──
// Нічого не читає й не пише. Той самий вхід → той самий план, завжди.
function decide(acc: Account, tx: Transaction): Plan {
  const plan: Plan = [];

  if (tx.amount > acc.dailyLimit) {
    plan.push({ kind: "flag", txId: tx.id, reason: "over-limit" });
    plan.push({ kind: "notify", userId: acc.userId,
                message: "Транзакцію відкладено на перевірку" });
  }

  const newBalance = acc.balance - tx.amount;
  if (newBalance < 0) {
    plan.push({ kind: "freeze", accountId: acc.id });
    plan.push({ kind: "notify", userId: acc.userId,
                message: "Рахунок заморожено: недостатньо коштів" });
  } else {
    plan.push({ kind: "setBalance", accountId: acc.id, amount: newBalance });
  }

  plan.push({ kind: "audit", line: `tx ${tx.id} on ${acc.id}: amount=${tx.amount}` });
  return plan;                     // просто дані — досі нічого не сталося
}
```
```py
# ── ПІСЛЯ, ядро: чиста функція від даних до ПЛАНУ ──
# Нічого не читає й не пише. Той самий вхід → той самий план, завжди.

        plan.append(Freeze(account_id=acc.id))
        plan.append(Notify(user_id=acc.user_id,
                           message="Рахунок заморожено: недостатньо коштів"))
    else:
        plan.append(SetBalance(account_id=acc.id, amount=new_balance))

    plan.append(Audit(line=f"tx {tx.id} on {acc.id}: amount={tx.amount}"))
    return plan                     # просто дані — досі нічого не сталося
```
:::

Тепер оболонка. Вона розпадається на дві частини, і поділ цей не випадковий. Перша — **виконавець плану** (`runPlan`): бере список описів і для кожного робить справжню дію. Це єдине місце в усій програмі, де опис `notify` перетворюється на живий пуш, а `setBalance` — на запис у базу. Друга частина — тонка обгортка `handleTransaction`, що приносить дані, кличе ядро, віддає план виконавцеві.

:::tabs
```ts
// ── ПІСЛЯ, оболонка (1): ВИКОНАВЕЦЬ плану ──
// Єдине місце, де опис стає дією. Сам нічого не вирішує.
async function runPlan(plan: Plan): Promise<void> {
  for (const e of plan) {
    switch (e.kind) {
      case "flag":       await db.flagTransaction(e.txId, e.reason); break;
      case "freeze":     await db.freezeAccount(e.accountId);        break;
      case "setBalance": await db.setBalance(e.accountId, e.amount); break;
      case "notify":     await notifier.push(e.userId, e.message);   break;
      case "audit":      await audit.log(e.line);                    break;
    }
  }
}

// ── ПІСЛЯ, оболонка (2): тонка обгортка ──
// Принести → вирішити (ядром) → виконати. Рішень тут нема.
async function handleTransaction(accountId: string, tx: Transaction): Promise<void> {
  const acc  = await db.loadAccount(accountId);   // принести
  const plan = decide(acc, tx);                    // ← усе рішення тут, у ядрі
  await runPlan(plan);                             // винести
}
```
```py
# ── ПІСЛЯ, оболонка (1): ВИКОНАВЕЦЬ плану ──
# Єдине місце, де опис стає дією. Сам нічого не вирішує.
async def run_plan(plan: Plan) -> None:
    for e in plan:
        match e:
            case Flag(tx_id, reason):       await db.flag_transaction(tx_id, reason)
            case Freeze(account_id):        await db.freeze_account(account_id)
            case SetBalance(account_id, a): await db.set_balance(account_id, a)
            case Notify(user_id, message):  await notifier.push(user_id, message)
            case Audit(line):               await audit.log(line)

# ── ПІСЛЯ, оболонка (2): тонка обгортка ──
# Принести → вирішити (ядром) → виконати. Рішень тут нема.
async def handle_transaction(account_id: str, tx: Transaction) -> None:
    acc  = await db.load_account(account_id)    # принести
    plan = decide(acc, tx)                       # ← усе рішення тут, у ядрі
    await run_plan(plan)                         # винести
```
:::

Подивись, що сталося зі структурою. Уся логіка — усі чотири `if/else` — переїхала в `decide`, де немає ні бази, ні пошти. Виконавець `runPlan` **не має жодного розгалуження бізнес-правил**: його `switch` — це не «вирішити, що робити», а «як виконати вже вирішене». Він тупий за побудовою: дай опис — виконаю, і байдуже, чому ядро цей опис додало. А `handleTransaction` стиснувся до трьох рядків, у яких нема де сховатися помилці.

![Ліворуч: коробка «handleTx()» із рядками «читає базу», «рахує рішення», «пише в базу», «шле лист», і до трьох дієвих рядків зліва причеплені підписи «мок БД», «мок БД», «мок пошти» — три моки на одну функцію. Праворуч: коробка «decide() чиста функція» стрілкою вниз до коробки «ПЛАН (дані)» зі списком «запис у базу, надіслати лист», а та стрілкою вниз до коробки «run(plan) виконує описи»; праворуч від плану — підпис «тест ядра звіряє список, нуль моків»](img/mocks-before-after.svg)

*Ліворуч моки чіпляються до кожної дії всередині переплетеної функції — щоб дійти до рішення, тест мусить обставити всі дотики до світу. Праворуч рішення відірване в `decide`, що повертає план як дані: тест дивиться на список описів безпосередньо, а моки лишаються тільки в тонкому виконавці.*

> 🔧 **Навіщо це.** Головний важіль тут — що виконавець плану пишеться **раз** і більше не міняється, хоч би як розросталася логіка. Додалося нове правило («перекази за кордон — окремий прапорець»)? Це новий `push` у `decide` і, щонайбільше, один новий варіант `Effect` із рядком у `runPlan`. Уся складність вибору тече в чисте ядро, а брудна частина лишається кістяком з п'яти рядків. Ти розділив не «базу й логіку», а **зростання складності**: логіка росте в дешевому для перевірки місці, дія не росте взагалі.

## Тести: від купи моків до звіряння списку

Ось де окупається вся робота, і різницю варто побачити поряд. Спершу — як виглядав чесний тест **до** рефакторингу. Щоб перевірити єдине правило «понад ліміт → позначити + сповістити», доводилося зібрати цілий стенд із підробок і потім ще й допитувати їх, чи покликали як слід:

:::tabs
```ts
// ── ДО: тест мусить обставити всі дотики до світу ──
test("over-limit flags and notifies", async () => {
  // 1. підробка бази з потрібним рахунком і шпигунами на записах
  const db = {
    loadAccount: async () => ({ id: "a1", userId: "u1",
                                balance: 500, dailyLimit: 100 }),
    flagTransaction: jest.fn(),
    freezeAccount:   jest.fn(),
    setBalance:      jest.fn(),
  };
  // 2. підробка сповіщувача
  const notifier = { push: jest.fn() };
  // 3. підробка журналу
  const audit = { log: jest.fn() };
  // 4. підмінити глобальні залежності на підробки (DI або monkey-patch)
  inject({ db, notifier, audit });

  await handleTransaction("a1", { id: "t1", amount: 150 });

  // 5. і тепер — допит шпигунів: покликали правильно?
  expect(db.flagTransaction).toHaveBeenCalledWith("t1", "over-limit");
  expect(notifier.push).toHaveBeenCalledWith("u1",
    "Транзакцію відкладено на перевірку");
});
```

П'ять кроків, три підробки, чотири шпигуни (`jest.fn()` / `AsyncMock`) — і все це заради перевірки одного `if`. Гірше того, тест перевіряє не «що вирішено», а «що покликано»: він прив'язаний до того, **як саме** оболонка викликає базу, тож зміна сигнатури `flagTransaction` зламає тест, який мав би стерегти правило, а не проводку.

Тепер той самий випадок **після**. Ядро повертає план — просто список даних, — і тест на нього це звіряння списку: зібрав вхід, покликав `decide`, глянув, що в плані є потрібні описи. Ні бази, ні пошти, ні журналу, ні шпигунів:

:::tabs
```ts
// ── ПІСЛЯ: тест ядра — звіряння списку описів. Нуль моків ──
test("over-limit flags and notifies", () => {
  const acc: Account = { id: "a1", userId: "u1", balance: 500, dailyLimit: 100 };
  const plan = decide(acc, { id: "t1", amount: 150 });
```

Кожен тест — три рядки: збери вхід, поклич ядро, звір список. І зверни увагу на другий тест: перевірити, що чогось у плані **немає** (баланс не чіпаємо, коли морозимо рахунок), — тепер тривіально, бо план — це видимий список, у якому можна шукати відсутність. У версії «до» таку негативну перевірку («`setBalance` не має викликатися») пишуть через `expect(...).not.toHaveBeenCalled()` — знову крізь шпигуна, знову прив'язка до способу виклику. Тут же ти просто дивишся у список: є опис чи нема.

Це і є перехід від «мокати менше» до «мокати нічого». Чистому ядру нема куди підставляти підробки — воно не має каналу ні до бази, ні до пошти, тож у тесті на нього мокати **нема чого** (докладніше про сам поділ дотиків від логіки — у [чистих функціях і побічних ефектах](book:programming/pure-functions-side-effects)).

## Скільки риштування зникло: заміри

Порахуймо різницю не на око, а рядками. Візьмемо ту саму перевірку «понад ліміт → позначити + сповістити» і зважимо два тести.

```
ТЕСТ ОДНОГО ПРАВИЛА — риштування проти суті:

  ДО (крізь дії):
    підробка db (loadAccount + 3 шпигуни)      6 рядків
    підробка notifier                          1 рядок
    підробка audit                             1 рядок
    inject(...) підміна залежностей            1 рядок
    виклик handleTransaction                   1 рядок
    2 допити шпигунів (toHaveBeenCalledWith)    2 рядки
    ─────────────────────────────────────────────────
    усього ≈ 12 рядків, з них РИШТУВАННЯ ≈ 9

  ПІСЛЯ (звіряння списку):
    збір рахунку-входу                         1 рядок
    виклик decide                              1 рядок
    2 звіряння списку (toContainEqual)         2 рядки
    ─────────────────────────────────────────────────
    усього ≈ 4 рядки, з них РИШТУВАННЯ = 0
```

Дев'ять рядків підготовки на один випадок перетворилися на нуль. Але справжня економія — не в цих дев'яти рядках, а в тому, як вони **множаться**. У версії «до» кожен новий тест-випадок тягне свій блок підробок (або спільну громіздку фікстуру, яку доводиться підправляти під кожен випадок). У версії «після» новий випадок — це ще три рядки: вхід, виклик, звіряння. Порахуймо на десяти випадках:

```
РІСТ на N випадків:

  ДО:    базовий стенд підробок ~9 + (виклик + допит) ~3 на випадок
         10 випадків ≈ 9 + 10·3 = 39 рядків
         (і це якщо стенд спільний; часто він розповзається по випадках)

  ПІСЛЯ: 0 стенду + ~4 на випадок (часто менше — вхід спільний)
         10 випадків ≈ 10·4 = 40 рядків суті, 0 риштування

  Ключ не в сумі рядків, а в їх ПРИРОДІ: у «до» третина-половина —
  це підробки й допити (крихкі, чіпляються за спосіб виклику);
  у «після» всі рядки — «вхід → очікуваний опис» (стабільні).
```

Різниця не стільки в довжині, скільки в **крихкості**. Рядки риштування — це не просто зайвий обсяг; це зачепи, якими тест тримається за внутрішній устрій оболонки. Зміни сигнатуру `db.setBalance`, і тести «до» посипляться десятками — хоч правило про баланс не змінилося ні на йоту, бо вони перевіряли виклик, а не рішення. Тести «після» переживуть цю зміну не зморгнувши: вони звіряють опис `{ kind: "setBalance", … }`, а як саме `runPlan` його виконує — їхня не турбота. Один інтеграційний тест на `runPlan` (з підробками в пам'яті) підтвердить проводку **раз** — і саме там, де їй місце.

## Важкий випадок: сендвіч «читати → вирішити → діяти → читати ще»

Досі нам щастило: одне читання на початку, одне рішення, купка дій наприкінці. Але справжня логіка часто не вкладається в один прохід. Наступне рішення залежить від того, що **повернула** попередня дія: зняв кошти — а скільки реально списалося після комісій банку? залежно від цього — або надіслати чек, або відкотити й повідомити про помилку. Годі скласти весь план наперед: половини даних для другого рішення ще не існує, поки не виконано першу дію.

Легко піддатися спокусі й сказати: «ну добре, тут доведеться викликати базу посеред ядра». Це хибний хід — він тягне світ назад у чисту функцію й руйнує весь виграш. Правильна відповідь інша: форма **не ламається, вона повторюється**. Оболонка й ядро чергуються шарами, як у сендвічі — читання, рішення, дія, знову читання, знову рішення, знову дія, — і кожен шматочок ядра лишається чистим окремо. Саме за цей багатошаровий вигляд Ґері Бернгардт, який 2012 року дав цій формі коротку назву «функціональне ядро, імперативна оболонка», описував її як **сендвіч**: тонка імперативна скоринка, товста функціональна начинка, знову скоринка (усталений факт; доповідь «Boundaries», конференція SCNA 2012).

Розберемо на знятті коштів із переказом. Крок за кроком: прочитати рахунок → **ядро вирішує**, чи можна знімати → оболонка знімає → прочитати підсумок операції → **ядро вирішує**, що робити з результатом → оболонка виконує. Два чистих рішення, розділені дією, результат якої потрібен другому рішенню.

Кожне рішення лишається окремою чистою функцією, що повертає план (або вирок). А оболонка зшиває їх, вставляючи дію між двома викликами ядра:

:::tabs
```ts
// ── ДВА чистих рішення, кожне повертає план/вирок ──
type Verdict =
  | { ok: true;  amount: number }             // можна знімати стільки
  | { ok: false; plan: Plan };                // не можна — ось що зробити

// Рішення 1: чи взагалі дозволити зняття (чисте).
function decideWithdraw(acc: Account, req: WithdrawReq): Verdict {
  if (acc.frozen)
    return { ok: false, plan: [{ kind: "notify", userId: acc.userId,
                                 message: "Рахунок заморожено" }] };
  if (req.amount > acc.balance)
    return { ok: false, plan: [{ kind: "notify", userId: acc.userId,
                                 message: "Недостатньо коштів" }] };
  return { ok: true, amount: req.amount };
}

// Рішення 2: що робити ПІСЛЯ зняття, знаючи фактично списану суму (чисте).
function afterWithdraw(acc: Account, requested: number, settled: number): Plan {
  if (settled < requested)                    // банк списав менше, ніж просили
    return [{ kind: "notify", userId: acc.userId,
              message: `Списано частково: ${settled}` },
            { kind: "audit", line: `partial withdraw ${acc.id}: ${settled}` }];
  return [{ kind: "notify", userId: acc.userId, message: `Видано: ${settled}` },
          { kind: "audit", line: `withdraw ${acc.id}: ${settled}` }];
}

// ── ОБОЛОНКА: чергує читання/дію з двома чистими рішеннями ──
async function withdraw(accountId: string, req: WithdrawReq): Promise<void> {
  const acc = await db.loadAccount(accountId);        // читати
  const v = decideWithdraw(acc, req);                  // вирішити (1)
  if (!v.ok) { await runPlan(v.plan); return; }        // діяти (відмова) і вийти

  const settled = await bank.withdraw(accountId, v.amount);  // діяти + читати результат
  const plan = afterWithdraw(acc, v.amount, settled);  // вирішити (2)
  await runPlan(plan);                                 // діяти
}
```

```py
from dataclasses import dataclass

# ── ДВА чистих рішення, кожне повертає план/вирок ──
@dataclass(frozen=True)
class Allow:  amount: float           # можна знімати стільки
@dataclass(frozen=True)
class Deny:   plan: Plan              # не можна — ось що зробити
Verdict = Allow | Deny

# Рішення 1: чи взагалі дозволити зняття (чисте).
def decide_withdraw(acc: Account, req: WithdrawReq) -> Verdict:
    if acc.frozen:
        return Deny([Notify(user_id=acc.user_id, message="Рахунок заморожено")])
    if req.amount > acc.balance:
        return Deny([Notify(user_id=acc.user_id, message="Недостатньо коштів")])
    return Allow(amount=req.amount)

# Рішення 2: що робити ПІСЛЯ зняття, знаючи фактично списану суму (чисте).
def after_withdraw(acc: Account, requested: float, settled: float) -> Plan:

        return [Notify(user_id=acc.user_id, message=f"Списано частково: {settled}"),
                Audit(line=f"partial withdraw {acc.id}: {settled}")]
    return [Notify(user_id=acc.user_id, message=f"Видано: {settled}"),
            Audit(line=f"withdraw {acc.id}: {settled}")]

# ── ОБОЛОНКА: чергує читання/дію з двома чистими рішеннями ──
async def withdraw(account_id: str, req: WithdrawReq) -> None:
    acc = await db.load_account(account_id)             # читати
    v = decide_withdraw(acc, req)                        # вирішити (1)
    if isinstance(v, Deny):
        await run_plan(v.plan); return                   # діяти (відмова) і вийти

    settled = await bank.withdraw(account_id, v.amount)  # діяти + читати результат
    plan = after_withdraw(acc, v.amount, settled)        # вирішити (2)
    await run_plan(plan)                                 # діяти
```

*Один прохід не вміщає логіки, коли друге рішення залежить від результату першої дії. Форма повторюється шарами: між двома чистими рішеннями оболонка вставляє дію й дочитує її результат. Обидві зелені смуги — окремі чисті функції, кожна перевіряється списком без бази.*

І головне — **обидва** рішення лишилися чистими, тож обидва перевіряються звірянням без бази. «Заморожений рахунок → відмова» перевіряється на `decideWithdraw` списком з одного `notify`. «Банк списав менше, ніж просили → частковий чек + лог» перевіряється на `afterWithdraw` — просто передаєш `requested=100, settled=60` і дивишся, що в плані опис про часткове списання. Дію `bank.withdraw` між ними мокати доводиться рівно раз, і то лише в одному інтеграційному тесті на `withdraw`, що стереже проводку — не логіку.

> 🔧 **Навіщо це.** Сендвіч — це відповідь на найпоширеніше заперечення проти всього прийому: «а якщо мені треба дочитати щось посеред рішення?». Не тягни читання в ядро — **розріж рішення на два** в точці, де знадобилися свіжі дані, і встав дію між ними в оболонці. Кожен шматок рішення лишається чистою функцією від того, що вже відомо, до плану. Ти платиш за це трохи менш плоским кодом оболонки (там тепер є `if` про відмову й порядок кроків), але ця складність — **проводка**, її мало й вона тупа, тоді як складність **вибору** сидить у чистих шматках, де її дешево перевіряти.

## Пастки: де прийом перегинати не варто

Прийом сильний, але має чесні межі. Назвати їх важливо, щоб не перетворити добру ідею на догму й не нашкодити там, де вона не лягає.

### Коли план завеликий для пам'яті

Перша й найпрактичніша пастка. План — це список **усіх** ефектів, зібраний **перед** тим, як виконати бодай один. Поки ефектів десятки чи сотні — байдуже. Але уяви ядро, що обробляє мільйон рядків імпорту й на кожен породжує опис «записати в базу». Тепер `decide` спершу збудує список на мільйон елементів у пам'яті, і лише потім `runPlan` почне його виконувати. Тримати мільйон описів у пам'яті одночасно може бути дорожче, ніж виконувати їх на льоту, — а пік пам'яті стрибне рівно на розмір усього плану.

```
Проблема масштабу плану:

  МАЛИЙ план (десятки ефектів):
    зібрати весь список → виконати. Пам'ять дрібниця. Ідеально.

  ВЕЛЕТЕНСЬКИЙ план (мільйони ефектів):
    зібрати ВЕСЬ список у пам'ять → аж тоді виконувати.
    Пік пам'яті = розмір усього плану. Може не влізти / бути повільним.
```

Виходів два, і обидва зберігають дух прийому. Перший — **потік замість списку**: ядро не повертає готовий масив, а **видає** описи по одному (генератор у Python, ітератор/async-генератор у TS), і оболонка виконує кожен, щойно він з'явився. Ядро й далі лише описує, оболонка й далі лише виконує — просто не матеріалізуючи весь план нараз:

:::tabs
```ts
// Ядро ВИДАЄ описи по одному — весь план не тримається в пам'яті.
function* decideStream(rows: Row[]): Generator<Effect> {
  for (const r of rows)
    if (r.valid) yield { kind: "audit", line: `import ${r.id}` };
}
// Оболонка виконує кожен опис одразу, щойно ядро його видало.
async function runStream(effects: Iterable<Effect>): Promise<void> {
  for (const e of effects) await execute(e);   // пам'ять — один опис за раз
}
```
```py
from typing import Iterator

# Ядро ВИДАЄ описи по одному — весь план не тримається в пам'яті.
def decide_stream(rows: list[Row]) -> Iterator[Effect]:
    for r in rows:
        if r.valid:
            yield Audit(line=f"import {r.id}")

# Оболонка виконує кожен опис одразу, щойно ядро його видало.
async def run_stream(effects: Iterator[Effect]) -> None:
    for e in effects:
        await execute(e)                       # пам'ять — один опис за раз
```
:::

Генератор лишається чистим у важливому сенсі: він нічого не читає й не пише, лише **обчислює наступний опис** на вимогу. Тестується він так само списком — просто зібрав видане в масив (`[...decideStream(rows)]`) і звірив. Другий вихід — свідомо **пожертвувати** чистотою заради пам'яті й виконувати ефект просто в циклі. Це нормальний інженерний розмін, аби він був **свідомий**: ти знаєш, що втратив легкість тесту на цій ділянці, і йдеш на це заради конкретної вигоди, а не за звичкою.

### Коли поділ зайвий

Протилежна пастка — тягнути план туди, де логіки на нього нема. Якщо весь обробник — це «прочитати рядок і одразу його записати», то `decide` буде порожній: він поверне план з одного опису, який без жодного рішення веде до однієї дії. Ти додав тип `Effect`, функцію `decide`, виконавець `runPlan` — цілий обряд — заради того, що було одним рядком.

```
Коли план — це церемонія без користі:

  handleThing():
    x = read()
    write(x)          ← жодного рішення. decide() поверне [Write(x)] — і все.

  План додає: тип Effect + decide() + runPlan() — три конструкції
  замість одного рядка. Кістяк важчий за м'ясо. НЕ роби цього.
```

Ознака проста: якщо в `decide` немає **жодного розгалуження** — жодного `if`, який вибирає між різними наборами ефектів, — то вирішувати нічого, і план порожній як поняття. Плата за форму (три конструкції) перевищує виграш (нуль, бо перевіряти нічого). Форма окупається там, де **вибір дій нетривіальний**: кілька умов, що по-різному складають список. На лінійному «прочитав-записав» вона додає церемонії й забирає ясність.

### Коли ефект мусить статися серед рішення заради коректності

Тонша межа, ніж пам'ять. Іноді дію не можна відкласти до кінця не через обсяг, а через **семантику**: рішення посеред обчислення мусить спиратися на щось, що можна дізнатися лише виконавши дію **зараз** — і не просто прочитати (це сендвіч), а саме змінити світ і врахувати наслідок у межах тієї ж атомарної операції. Класика — коли між «вирішив» і «зробив» не можна впускати іншого учасника: перевірка й списання мусять бути неподільні, інакше двоє знімуть той самий залишок.

Тут план як єдиний список наприкінці не рятує, бо вікно між збором плану й його виконанням — це якраз проміжок, у який може втрутитися чужа транзакція. Відповідь — не ламати ядро, а **звузити** те, що воно вирішує: ядро вирішує *політику* («за таких умов дозволити зняти стільки»), а неподільність («перевір-і-спиши одним рухом під замком») лишається дією оболонки, яку та виконує в транзакції бази. Ядро каже *що дозволено*, оболонка забезпечує *як це зробити безпечно*. Коли ж і цього замало — коли саме рішення вимагає бачити проміжний стан бази під тим самим замком, — це той рідкісний випадок, де чистоту свідомо відпускають, і головне тут те саме слово: **свідомо**.

Отже, мета — не «жодного ефекту поза планом» і не «план у кожній функції». Мета скромніша: **тримати вибір дій на чистому боці — як побудову плану, — а виконання плану тонким шаром на краю**, і знати ті кілька місць, де ти від цього відступив (велетенський план, лінійна дрібниця, атомарність) і чому саме. Там, де логіка справді вирішує, *що робити*, план ефектів перетворює найскладнішу частину програми — вибір дій — на чисту функцію, що будує список, а той список читається як таблиця «вхід → наміри» й перевіряється без жодного мока. Розум складає план, руки його виконують — і кожне робить свою справу краще, ніж коли вони сплетені в одному тілі.
