# ⚙️ Властивісне тестування ядра: писати закони, а не приклади

Звичайний тест приколює одну точку: «для цього кошика підсумок дорівнює 1140». Ти вигадав вхід, порахував відповідь руками, записав очікування. Це чесно й корисно, але придивись, що саме ти перевірив, — рівно один рядок нескінченної таблиці істинності. А цікаве ядро — те, що вирішує ціну, пропускає транзакцію, ділить повернення, — має астрономічний простір входів: будь-який набір товарів, будь-яка ставка, будь-який рахунок. Перебрати його прикладами неможливо: скільки б їх ти не написав, лишиться нескінченність неперевіреного, і баг любить сидіти саме там, куди твоя рука не потяглася.

Тепер поміняй питання. Замість «яка відповідь на цей вхід?» запитай «яке твердження істинне для **будь-якого** входу?». Не «1140», а «підсумок **ніколи** не від'ємний». Не «тут знижка спрацювала», а «знижку застосовано **тоді й лише тоді**, коли до-знижковий підсумок перевищив тисячу». Ти більше не приколюєш точки — ти формулюєш **закон**, а машині віддаєш чорну роботу: нехай сама вигадає десять тисяч випадкових входів і на кожному перевірить, що закон тримається. Це і є **властивісне тестування (англ. *property-based testing*)** — і воно стає можливим рівно тому, що ядро чисте.

Розберемо це на робочому коді: візьмемо три рішальні ядра, напишемо над ними закони-інваріанти замість прикладів, зженемо 10⁴ випадкових випадків через кожен, навмисно посадимо баг, який приклади проґавлять, а закон упіймає, і подивимося, як інструмент **звужує** велетенський випадковий контрприклад до найменшого входу, що досі валить правило. А наприкінці — чому весь цей фокус працює лише над чистим детермінованим ядром і де він боляче ламається, якщо не думати.

## Від прикладу до закону

Приклад — це один рядок таблиці істинності: конкретний вхід, конкретний вихід, ти власноруч звірив пару. Закон (його ще звуть **властивістю** або [інваріантом](book:programming/invariants) — твердженням, що має триматися завжди) — це квантор «для всіх»: `∀ вхід. P(вхід)`. Різниця між ними не кількісна, а якісна. Приклад каже «ось тут я подивився»; закон каже «я стверджую про весь простір одразу». Машина не може довести квантор перебором нескінченності, але може зробити наступне найкраще: **насемплювати** простір — накидати сотні й тисячі випадкових входів — і на кожному перевірити `P`. Один провал спростовує закон (контрприклад); десять тисяч успіхів не доводять його, але дають упевненість, яку жоден ручний список не дасть.

Ключ у тому, **що саме** ти стверджуєш. Гарний закон — це те, у що ти віриш **незалежно від того, як написаний код**: специфікація, а не переказ реалізації. «Сума частин розбитого повернення дорівнює цілому» — це закон збереження грошей, він істинний хоч би як ти ділив. «Заморожений рахунок ніколи не породжує списання» — це закон безпеки, він мусить триматися для будь-якого запиту, який тільки можна вигадати. Такі твердження неможливо перевірити прикладами до кінця (запитів нескінченно), зате легко перевірити семплюванням — якщо код, який ти семплюєш, чистий і дешевий, щоб гнати його тисячами.

Ось чотири закони, які ми напишемо над нашими ядрами, і кожен — саме такого штибу «істинно для всіх, а не для одної точки»:

```
ЗАКОНИ (інваріанти) замість прикладів:

  1. ЦІНОУТВОРЕННЯ:  для будь-яких товарів  →  підсумок ≥ 0
  2. ЦІНОУТВОРЕННЯ:  знижку видно в підсумку  ⟺  до-знижковий > 1000
  3. АНТИФРОД:       заморожений рахунок  →  жодного ефекту списання
  4. ПОВЕРНЕННЯ:     сума частин розбитого повернення  =  ціле
```

Перший — інваріант діапазону (значення не вилазить за межу). Другий — біумовність (одне рівно тоді, коли друге). Третій — інваріант безпеки (лиха дія не трапляється **ніколи**, хоч би що на вході). Четвертий — закон збереження (ніщо не губиться й не з'являється). Чотири різні форми законів, і жоден не звучить як «на такому-то вході очікую те-то» — усі говорять про **весь** простір входів.

## Три ядра, які перевіряємо

Щоб закони було над чим перевіряти, спершу — самі ядра. Це чисті функції: беруть звичайні значення, повертають звичайні значення, нічого не читають і не пишуть. Саме тому вони й піддаються цьому методу, але про це — далі; поки що просто код.

Перше — **ціноутворення**. Бере товари й податкову ставку, повертає підсумок, до-знижкову суму (щоб над нею можна було сформулювати закон) і прапорець знижки:

:::tabs
```ts
type Item = { price: number; qty: number };          // ціна в копійках
type Order = { preDiscount: number; total: number; discounted: boolean };

function priceOrder(items: Item[], taxRate: number): Order {
  let subtotal = 0;
  for (const it of items) subtotal += it.price * it.qty;
  const preDiscount = subtotal * (1 + taxRate);        // сума з податком, ДО знижки
  const discounted = preDiscount > 1000;               // знижка за великий чек
  const total = discounted ? preDiscount * 0.95 : preDiscount;
  return { preDiscount, total, discounted };
}
```
```py
from dataclasses import dataclass

@dataclass(frozen=True)
class Item:  price: int; qty: int          # ціна в копійках

@dataclass(frozen=True)
class Order: pre_discount: float; total: float; discounted: bool

def price_order(items: list[Item], tax_rate: float) -> Order:
    subtotal = sum(it.price * it.qty for it in items)
    pre_discount = subtotal * (1 + tax_rate)           # сума з податком, ДО знижки
    discounted = pre_discount > 1000                   # знижка за великий чек
    total = pre_discount * 0.95 if discounted else pre_discount
    return Order(pre_discount=pre_discount, total=total, discounted=discounted)
```
:::

Друге — **антифрод-рішення** про зняття коштів. Бере рахунок і запит, повертає список **описів ефектів** (списати, сповістити) — саме описів, не самих дій; ядро планує, оболонка потім виконає:

:::tabs
```ts
type Account = { id: string; userId: string; balance: number; frozen: boolean };
type WithdrawReq = { amount: number };
type Effect =
  | { kind: "debit";  accountId: string; amount: number }
  | { kind: "notify"; userId: string; message: string };

function decideWithdraw(acc: Account, req: WithdrawReq): Effect[] {
  if (acc.frozen)                                       // заморожено — тільки сповістити
    return [{ kind: "notify", userId: acc.userId, message: "Рахунок заморожено" }];
  if (req.amount > acc.balance)                         // не вистачає — тільки сповістити
    return [{ kind: "notify", userId: acc.userId, message: "Недостатньо коштів" }];
  return [{ kind: "debit", accountId: acc.id, amount: req.amount },
          { kind: "notify", userId: acc.userId, message: `Видано ${req.amount}` }];
}
```
```py
@dataclass(frozen=True)
class Account:     id: str; user_id: str; balance: int; frozen: bool
@dataclass(frozen=True)
class WithdrawReq: amount: int
@dataclass(frozen=True)
class Debit:       account_id: str; amount: int
@dataclass(frozen=True)
class Notify:      user_id: str; message: str

def decide_withdraw(acc: Account, req: WithdrawReq) -> list:
    if acc.frozen:                                       # заморожено — тільки сповістити
        return [Notify(user_id=acc.user_id, message="Рахунок заморожено")]
    if req.amount > acc.balance:                         # не вистачає — тільки сповістити
        return [Notify(user_id=acc.user_id, message="Недостатньо коштів")]
    return [Debit(account_id=acc.id, amount=req.amount),
            Notify(user_id=acc.user_id, message=f"Видано {req.amount}")]
```
:::

Третє — **розбиття повернення** на рівні частини (повернути суму `n` учасникам чи рознести по `n` місяцях). Гроші цілі, у копійках, тож ділити треба чесно — до останньої копійки:

:::tabs
```ts
// Розбити totalCents на n частин так, щоб сума частин дорівнювала цілому.
function splitRefund(totalCents: number, n: number): number[] {
  const base = Math.floor(totalCents / n);
  const rem = totalCents - base * n;             // 0..n−1 «зайвих» копійок
  const parts = Array(n).fill(base);
  for (let i = 0; i < rem; i++) parts[i] += 1;   // роздати остачу по копійці
  return parts;
}
```
```py
# Розбити total_cents на n частин так, щоб сума частин дорівнювала цілому.
def split_refund(total_cents: int, n: int) -> list[int]:
    base, rem = divmod(total_cents, n)           # rem = 0..n−1
    parts = [base] * n
    for i in range(rem):
        parts[i] += 1                            # роздати остачу по копійці
    return parts
```
:::

Три ядра, три різні форми виходу — число, список ефектів, розбиття, — і всі троє чисті: той самий вхід дає той самий вихід, дотику до світу нема. Саме цю [чистоту](book:programming/pure-functions-side-effects) ми зараз обернемо на важіль.

## Генератори: фабрика випадкових входів

Закон каже «для всіх входів». Щоб машина могла його перевіряти, їй треба вміти **виготовляти** входи — не один, а тисячами, випадкових, але правильної форми. Це робить **генератор**: опис того, які значення бувають на вході й у яких межах. Ти не пишеш самі входи — ти описуєш їхню **форму**, а бібліотека сама насемплює конкретику.

У TypeScript це `fast-check`, у Python — `Hypothesis`. Обидві дають однакову думку: складати генератор складних значень із генераторів простих. Ось генератори товару й рахунку:

:::tabs
```ts
import fc from "fast-check";

// товар: ціна — невід'ємне ціле (копійки), кількість — 0..100
const itemGen = fc.record({
  price: fc.nat({ max: 100_000 }),
  qty:   fc.integer({ min: 0, max: 100 }),
});

// заморожений рахунок: усе випадкове, але frozen ЗАВЖДИ true
const frozenAccGen = fc.record({
  id:      fc.string(),
  userId:  fc.string(),
  balance: fc.nat({ max: 1_000_000 }),
  frozen:  fc.constant(true),
});
```
```py
from hypothesis import strategies as st

# товар: ціна — невід'ємне ціле (копійки), кількість — 0..100
item = st.builds(Item,
    price=st.integers(min_value=0, max_value=100_000),
    qty=st.integers(min_value=0, max_value=100))

# заморожений рахунок: усе випадкове, але frozen ЗАВЖДИ True
frozen_acc = st.builds(Account,
    id=st.text(), user_id=st.text(),
    balance=st.integers(min_value=0, max_value=1_000_000),
    frozen=st.just(True))
```
:::

Зверни увагу на дві дрібниці, які насправді велика справа. Перша: `price` генерується **невід'ємним** (`nat`, `min_value=0`). Це не випадковість — це **передумова закону**, вкладена в генератор. Закон «підсумок ≥ 0» істинний лише для товарів з невід'ємною ціною; дозволь генераторові від'ємні ціни — і закон чесно впаде, бо він для такого входу й не мав триматися. Генератор — це те місце, де живе «які входи взагалі коректні». Друга: `frozen: constant(true)` звужує генератор до саме тих рахунків, про які закон №3 щось стверджує. Ти не перевіряєш «для всіх рахунків», ти перевіряєш «для всіх **заморожених** рахунків і будь-яких запитів» — і генератор точно це й описує: `frozen` прибитий, решта вільна.

> 🔧 **Навіщо це.** Генератор — половина закону, і думати про нього треба як про частину специфікації. Заслабкий генератор мовчки звужує «для всіх» до «для тих кількох, які я випадково накидав», і закон проходить, нічого не впіймавши. Засильний (з некоректними входами) — валить закон там, де він і не мав триматися. Правильний генератор описує **рівно множину коректних входів, про яку говорить закон**, — ні більше, ні менше. Коли властивість поводиться дивно, дивись спершу на генератор, а не на код ядра.

## Чотири закони над ядром

Тепер — самі властивості, по одній на кожен закон, і одразу з прогоном **10⁴ випадків**. За замовчуванням обидві бібліотеки женуть сотню; ми свідомо піднімаємо до десяти тисяч (`numRuns` / `max_examples`), бо ядро чисте й дешеве — десять тисяч викликів коштують мілісекунди.

**Закон 1 — підсумок ніколи не від'ємний.** Для будь-яких товарів і будь-якої невід'ємної ставки і до-знижкова сума, і підсумок ≥ 0:

:::tabs
```ts
import { test } from "vitest";

test("підсумок ніколи не від'ємний", () => {
  fc.assert(
    fc.property(
      fc.array(itemGen),
      fc.double({ min: 0, max: 0.3, noNaN: true }),
      (items, taxRate) => {
        const o = priceOrder(items, taxRate);
        return o.preDiscount >= 0 && o.total >= 0;
      }),
    { numRuns: 10_000 },
  );
});
```
```py
from hypothesis import given, settings
import math

@settings(max_examples=10_000)
@given(items=st.lists(item), tax_rate=st.floats(min_value=0, max_value=0.3))
def test_subtotal_never_negative(items, tax_rate):
    o = price_order(items, tax_rate)
    assert o.pre_discount >= 0 and o.total >= 0
```
:::

**Закон 2 — знижку видно в підсумку тоді й лише тоді, коли до-знижкова сума > 1000.** Це біумовність, і перевіряємо її не за прапорцем (це було б переказом коду), а за **фактичними грішми**: якщо сума перейшла тисячу — підсумок мусить бути рівно на 5 % менший; якщо ні — підсумок дорівнює до-знижковій сумі:

:::tabs
```ts
test("знижку видно в підсумку ⟺ до-знижковий > 1000", () => {
  fc.assert(
    fc.property(
      fc.array(itemGen),
      fc.double({ min: 0, max: 0.3, noNaN: true }),
      (items, taxRate) => {
        const o = priceOrder(items, taxRate);
        const expected = o.preDiscount > 1000 ? o.preDiscount * 0.95 : o.preDiscount;
        return o.discounted === (o.preDiscount > 1000)
            && Math.abs(o.total - expected) < 1e-6;
      }),
    { numRuns: 10_000 },
  );
});
```
```py
@settings(max_examples=10_000)
@given(items=st.lists(item), tax_rate=st.floats(min_value=0, max_value=0.3))
def test_discount_iff_over_1000(items, tax_rate):
    o = price_order(items, tax_rate)
    expected = o.pre_discount * 0.95 if o.pre_discount > 1000 else o.pre_discount
    assert o.discounted == (o.pre_discount > 1000)
    assert math.isclose(o.total, expected, rel_tol=1e-9)
```
:::

**Закон 3 — заморожений рахунок ніколи не списують.** Ось де квантор показує силу: властивість каже, що **хоч би який** запит на зняття прийшов на заморожений рахунок, серед ефектів **не буде жодного** `debit`. Прикладами таке не закрити — запитів нескінченно; властивість же кидає тисячі різних сум і кожну перевіряє:

:::tabs
```ts
test("заморожений рахунок ніколи не списують", () => {
  fc.assert(
    fc.property(
      frozenAccGen,
      fc.record({ amount: fc.nat({ max: 2_000_000 }) }),
      (acc, req) => {
        const effects = decideWithdraw(acc, req);
        return effects.every(e => e.kind !== "debit");   // жодного списання
      }),
    { numRuns: 10_000 },
  );
});
```
```py
@settings(max_examples=10_000)
@given(acc=frozen_acc,
       req=st.builds(WithdrawReq, amount=st.integers(min_value=0, max_value=2_000_000)))
def test_frozen_never_debited(acc, req):
    effects = decide_withdraw(acc, req)
    assert all(not isinstance(e, Debit) for e in effects)   # жодного списання
```
:::

**Закон 4 — сума частин дорівнює цілому.** Закон збереження грошей: скільки не ділили б і на скільки частин, сума частин збігається з початковою сумою, і частин рівно `n`:

:::tabs
```ts
test("сума частин розбитого повернення = ціле", () => {
  fc.assert(
    fc.property(
      fc.nat({ max: 1_000_000 }),
      fc.integer({ min: 1, max: 100 }),
      (total, n) => {
        const parts = splitRefund(total, n);
        const sum = parts.reduce((a, b) => a + b, 0);
        return sum === total && parts.length === n;
      }),
    { numRuns: 10_000 },
  );
});
```
```py
@settings(max_examples=10_000)
@given(total=st.integers(min_value=0, max_value=1_000_000),
       n=st.integers(min_value=1, max_value=100))
def test_split_conserves(total, n):
    parts = split_refund(total, n)
    assert sum(parts) == total and len(parts) == n
```
:::

Чотири закони, кожен продавлений крізь десять тисяч випадкових входів, і жодного мока, жодної бази, жодного годинника — бо ядро чисте, семплювати нема чого, крім самих значень. На правильних ядрах усі чотири мовчки зеленіють. Тепер поламаймо одне навмисно й подивимось, хто це помітить.

## Посаджений баг: приклади мовчать, закон кричить

Уяви, що розбиття повернення написав хтось поспіхом — поділив суму порівну й **забув про остачу**:

:::tabs
```ts
// БАГ: поділили порівну й «забули» роздати остачу
function splitRefund(totalCents: number, n: number): number[] {
  const each = Math.floor(totalCents / n);
  return Array(n).fill(each);          // сума = each·n ≤ total, копійки губляться
}
```
```py
# БАГ: поділили порівну й «забули» роздати остачу
def split_refund(total_cents: int, n: int) -> list[int]:
    each = total_cents // n
    return [each] * n                  # сума = each·n ≤ total, копійки губляться
```
:::

Тепер найпідступніше. Хтось же тестував цю функцію прикладами — і тести **зелені**. Бо які приклади пише людина? Круглі, пам'ятні, зручні для усного рахунку:

:::tabs
```ts
test("split — приклади", () => {
  expect(splitRefund(100, 2)).toEqual([50, 50]);
  expect(splitRefund(100, 4)).toEqual([25, 25, 25, 25]);
  expect(splitRefund(900, 3)).toEqual([300, 300, 300]);
});   // ✅ усі проходять і на БАГнутій версії — числа діляться націло
```
```py
def test_split_examples():
    assert split_refund(100, 2) == [50, 50]
    assert split_refund(100, 4) == [25, 25, 25, 25]
    assert split_refund(900, 3) == [300, 300, 300]
    # ✅ усі проходять і на БАГнутій версії — числа діляться націло
```
:::

100 ділиться на 2 і на 4, 900 — на 3; остачі нема, губити нема чого, баг спить. Людина інстинктивно тягнеться до чисел, що діляться націло, — а це рівно ті рідкісні входи, на яких помилка не проявляється. Приклади обходять баг стороною не тому, що їх мало, а тому, що вони **обрані** з безпечної підмножини.

![Прямокутник «простір входів (total, n)», майже весь залитий червоним (баг-зона). Зрідка розсіяні зелені плюсики — безпечні точки, де total кратне n. Кілька синіх крапок сидять рівно на плюсиках: це приклади, обрані людиною. По всьому полю густо розкидані дрібні червоні крапки — 10⁴ випадкових входів, майже всі в баг-зоні; одна обведена — перший контрприклад. Легенда праворуч пояснює кольори](img/examples-vs-property.svg)

*Безпечні входи (total кратне n) — рідкі точки в просторі; людина несвідомо ставить приклади саме на них. Випадковий прогін засіває весь простір і майже одразу влучає в баг-зону, яка займає майже все.*

А тепер запусти над цією ж функцією закон №4. Генератор кидає випадкові `total` і `n` — і **майже одразу** натрапляє на пару, де `total` не ділиться на `n` націло. `splitRefund(100, 3)` баґнутою версією дає `[33, 33, 33]`, сума 99, а не 100 — одна копійка зникла. Закон падає:

```
fast-check (TS):
  Error: Property failed after 3 tests
  { seed: 1284523970, path: "2:1:0:1:0", endOnFailure: true }
  Counterexample: [1, 2]
  Shrunk 21 time(s)
  Got error: Property failed by returning false

Hypothesis (Python):
  Falsifying example: test_split_conserves(
      total=1, n=2,
  )
  assert (0 == 1)   # sum(parts) == total
```

Зверни увагу на дві речі у виводі. Перша — закон упав за лічені випадки (`after 3 tests`): баг-зона така велика, що випадковий постріл влучає в неї миттєво, тоді як ретельно дібрані приклади її обходили. Друга й дивовижніша: у виводі не та випадкова пара, на якій воно спіткнулось (щось на кшталт `total=738421, n=97`), а крихітна `total=1, n=2`. Звідки вона? Це **звуження**.

## Звуження до найменшого контрприкладу

Перший провал майже завжди велетенський і нечитабельний: генератор кинув `total=738421, n=97`, сума частин розійшлася з цілим на 43 копійки — і що тобі з цього дебажити? У цьому числі 43 копійки загубилися, але **де** саме й **чому**, велике число не підказує. Тут вмикається головна риса всієї родини інструментів — **звуження (англ. *shrinking*)**: знайшовши контрприклад, бібліотека не віддає його як є, а починає **зменшувати** вхід, щоразу перевіряючи, чи він **усе ще** валить закон. Менший `total`? Досі падає? Лишаємо, зменшуємо далі. Менше `n`? Досі падає? Лишаємо. І так доти, доки будь-яке подальше зменшення вже не рятує закон, — тобто до **найменшого входу, на якому баг ще живий**.

![Вертикальна лійка з п'яти чипів, що звужуються згори вниз: «total = 73 982, n = 7» → «total = 4 021, n = 7» → «total = 58, n = 3» → «total = 8, n = 3» → виділений зелений «total = 1, n = 2». Між чипами стрілки вниз. Праворуч дужка вздовж усіх кроків із підписом «звуження: щоразу МЕНШИЙ вхід, що ВСЕ ЩЕ ламає закон». Ліворуч угорі примітка «перший провал: випадковий, великий», ліворуч унизу «найменший — його й друкує тест»](img/shrinking-funnel.svg)

*Звуження веде від величезного випадкового провалу до найменшого входу, що досі валить закон. Саме цей найменший контрприклад інструмент і друкує — його читати й дебажити легко.*

Для розбиття повернення звуження сходить до `total=1, n=2`. Прочитай цей контрприклад як речення: «розділи одну копійку на двох». Правильна відповідь — `[1, 0]` (комусь копійка, комусь нуль), сума 1. Баґнута рахує `floor(1/2)=0` і повертає `[0, 0]`, сума 0. Найменший з можливих доказів, що остача губиться: тобі не треба гадати над 43 зниклими копійками у семизначному числі — тобі показують найчистіший випадок, де видно **саме механізм** помилки. Звуження перетворює «десь у великому числі щось не так» на «ось найдрібніший вхід, на якому все ламається».

І остання деталь виводу — `seed` та `path` (у fast-check) чи власна база прикладів (у Hypothesis). Це **зерно** генератора випадковості. Увесь прогін — і сам пошук, і звуження — детермінований: та сама послідовність «випадкових» входів народжується з того самого зерна. Тому інструмент може надрукувати зерно, а ти — відтворити **той самісінький** прогін до останнього кроку: `fc.assert(prop, { seed, path })` або Hypothesis, що сам запам'ятовує впалий приклад у `.hypothesis/` і першим ділом переграє його наступного разу. Провал не «іноді відтворюється» — він відтворюється **завжди**, байт у байт. І ось тут криється причина, чому весь цей механізм узагалі можливий.

## Чому це працює лише над чистим ядром

Усе описане — і прогін 10⁴ разів, і звуження, і відтворення за зерном — тримається на одній властивості коду під тестом: він **чистий і детермінований**. Прибери її — і кожна опора обвалюється.

**Прогін 10⁴ разів.** Ядро — чиста функція, тож десять тисяч викликів — це десять тисяч множень і порівнянь, мілісекунди, і **нічого** при цьому не діється: ні запису, ні читання, ні стану, який треба скидати між викликами. Тепер уяви, що ти хочеш так само продавити крізь тисячі випадків не ядро, а оболонку, що ходить у базу. Кожен випадок — це підняти базу у відомий стан, виконати, відкотити. Десять тисяч разів. Секунди перетворюються на години, а між випадками треба ще й ретельно чистити стан, інакше вони течуть один в один. Те, що над чистим ядром коштує мілісекунди, над брудною оболонкою коштує стільки, що ніхто його гнати не буде. Дешевизна семплювання — **пряме породження** чистоти.

**Відтворення за зерном.** Інструмент друкує зерно й обіцяє: заново з цим зерном — той самий провал. Обіцянка тримається лише якщо код під тестом сам детермінований. Над чистим ядром вона залізна: зерно задає ту саму послідовність входів, ті самі входи дають ті самі виходи, той самий вихід валить закон так само. А тепер хай ядро таємно читає годинник чи базу. Зерно чесно відтворить ті самі **входи** — але код на них поведеться інакше, бо годинник уже інший, а в базі вже інше. Надрукований контрприклад не відтворюється; ти запускаєш «той самий» тест — і він то падає, то ні. Тест стає **мерехтливим (англ. *flaky*)**, а мерехтливому тесту не вірять і кінець кінцем його вимикають.

**Звуження.** Воно тим паче вимагає детермінізму, ще гострішого. Звуження — це десятки повторних запусків на дедалі менших входах, і кожен крок питає: «цей менший вхід усе ще валить закон?». Питання має сенс лише коли відповідь **стабільна** — коли «валить» означає «валить завжди», а не «валить у вівторок». Якби ядро мерехтіло, звуження губилося б навмання: то менший вхід «випадково пройшов» (бо годинник тим часом цокнув), і його відкинули дарма; то великий «випадково впав» з іншої причини. Ланцюжок «менше → досі падає → ще менше» розсипається, і на виході — не найменший контрприклад, а сміття. Детермінізм тут не зручність, а несуча стіна: варто протягти в ядро канал до світу — годинник, базу, мережу, — і кожна з трьох опор осідає разом.

Ось чому властивісне тестування й функціональне ядро — природні супутники. Метод не просто «добре лягає» на чисте ядро — він **можливий лише** над ним. Кожне рішення, яке ти виніс у чисту функцію, стає полем для законів, що продавлюються десятками тисяч випадків за мілісекунди й показують найменший контрприклад. Кожне рішення, що лишилося зрослим із базою чи годинником, для цього методу закрите. Розділення на ядро й оболонку — це, серед іншого, розділення на «те, що можна перевіряти законами» і «те, що доведеться перевіряти дорогими нечастими інтеграційними тестами». Що більше логіки в ядрі, то більше програми під захистом законів.

## Звідки це: лінія QuickCheck

Метод не новий і має чітке коріння. 2000 року Коен Клессен (Koen Claessen) і Джон Г'юз (John Hughes) з Технічного університету Чалмерса (Ґетеборг, Швеція) опублікували на конференції ICFP статтю «QuickCheck: a lightweight tool for random testing of Haskell programs» і саму бібліотеку — крихітну, близько трьохсот рядків. Ідея була рівно та, що ми крутили весь цей час: описуй програму **властивостями**-кванторами, дай інструментові **генератори** випадкових входів, і нехай він шукає контрприклад (усталений факт; ICFP 2000, с. 268–279). Г'юз згодом заснував компанію QuviQ і поніс QuickCheck у промисловість — телеком, автомобільну електроніку, — де випадкові властивості виловлювали баги в протоколах, яких роками не бачили ручні тести.

Ідея розійшлася десятками мов. Наші дві бібліотеки — прямі нащадки тієї лінії. `fast-check` для JavaScript/TypeScript написав Ніколя Дюб'єн (Nicolas Dubien) 2017 року — прямо «як QuickCheck», але з інтегрованим звуженням і рідною для JS композицією генераторів; сьогодні на ньому знаходять баги проєкти рівня Jest і Ramda (усталено). `Hypothesis` для Python створив Девід Мак-Айвер (David R. MacIver) 2015 року, і він відомий власним, «внутрішнім» рушієм звуження, що працює на рівні потоку випадкових бітів, а не типів, — інша механіка з тим самим наслідком (усталено).

Одну історичну дрібницю варто назвати чесно. **Автоматичне** звуження до найменшого контрприкладу, яким ми щойно захоплювались, у первісному QuickCheck 2000 року в теперішньому вигляді ще не жило — там воно задавалося окремими функціями вручну, а «розумне» звуження визріло пізніше (інтегроване звуження в ерлангівському QuickCheck від QuviQ, «внутрішнє» — у Hypothesis). Тобто квантор-властивість і генератори — це справді 2000 рік і Клессен-Г'юз; а звуження, яке сьогодні здається серцем методу, — плід наступних п'ятнадцяти років роботи всієї спільноти, а не одного першого рядка. Розрізняти «хто поклав ідею» й «хто довів її до теперішнього блиску» тут доречно, як і всюди в історії інструментів.

## Пастки: де метод обертається самообманом

Властивісне тестування дає оманливе відчуття сили — «я ж перевірив десять тисяч випадків!», — і саме тому варто твердо знати три способи перевірити нічого.

**Тавтологічна властивість.** Найпідступніша. Це закон, який просто **переказує реалізацію**, а тоді порівнює її саму із собою. Скажімо, ти пишеш властивість на знижку так: `expect(o.discounted).toBe(o.preDiscount > 1000)` — а всередині `priceOrder` буквально `discounted = preDiscount > 1000`. Ти переписав рядок коду в тест і звірив рядок сам із собою: така властивість зелена **завжди**, бо це `x === x`, і не ловить нічого — навіть якщо і код, і «закон» разом помиляються. Ознака тавтології: щоб написати очікування, ти подумки виконуєш ту саму логіку, що й у ядрі. Ліки — **незалежне джерело істини (англ. *oracle*)**: стверджуй не те, як обчислено, а що з обчисленого мусить випливати. Тому закон №2 ми й перевіряли за фактичними грішми (`total` менший рівно на 5 %), а не за прапорцем: реалізація могла б виставити `discounted=true`, але забути помножити — і тавтологія за прапорцем це проґавила б, а закон за грішми впіймав. Класичні джерела істини, що не повторюють код: **закони збереження** (сума частин = ціле), **круговий обхід** (розкодуй закодоване — дістанеш вихідне), **простіша еталонна модель** (повільна, але очевидно правильна реалізація поруч), **метаморфічні** відношення (переставив товари місцями — підсумок не змінився).

**Заслабкий генератор.** Закон буває бездоганний, а генератор ніколи не породжує входу, на якому баг живе, — і властивість зелена, впіймавши порожнечу. Найпоширеніше — **межі**. Згадай закон №2: якщо генерувати ставку й ціни звичайними дробовими числами, `preDiscount` практично **ніколи** не набуде рівно `1000` — а помилка `>=` замість `>` на межі проявляється лише там. Тисячі випадкових дробів пройдуть повз межу й не помітять її. Ліки — **цілити в межі свідомо**: підсовувати граничні значення (`0`, `1`, максимум, і саме `1000`) окремим генератором чи явними прикладами; недарма `fc.nat` і `st.integers` самі частіше підкидають `0` та краї діапазону, ніж рівномірний кидок. Сусідня версія тієї ж пастки — генератор із перекошеним розподілом (списки завжди короткі, рядки завжди з латиниці): цілі класи входів просто не народжуються. Тут допомагає й [дизайн типами](book:programming/type-driven-design): якщо зробити некоректний стан невиразним самим типом, генератор фізично не зможе його породити — і слабкість генератора, і зайва передумова закону зникають разом.

**Незвужуваний вхід.** Уся цінність контрприкладу — у тому, що його звужено до найдрібнішого. Але звуження працює, лише поки вхід зібраний **із примітивів, які бібліотека вміє зменшувати**. Побудуй вхід хитрим способом — склей велику непрозору структуру, серіалізуй її в один рядок, згенеруй JSON суцільним текстом — і звужувачеві нема за що вхопитися: він поверне тобі той самий велетенський провал, який ти й боявся дебажити. Ліки — тримати генератори **композиційними**: складати з `fc.record`, `fc.array`, `st.builds`, `st.lists`, а не з `fc.constant(великий_блоб)` чи ручного парсингу згенерованого рядка. Сюди ж — надто агресивна фільтрація (`fc.pre` / `assume`, що відкидає більшість входів): вона і палить прогони намарно, і збиває звуження зі сліду. Що ближче твій генератор до «дерева простих цеглинок», то дрібніший і зрозуміліший контрприклад ти отримаєш.

І понад усі три — тримати в голові, що десять тисяч зелених прогонів **не є доказом**. Це не верифікація, а дуже широке семплювання: воно різко піднімає шанс наштовхнутися на баг проти жменьки прикладів, але «не знайшов» — не «нема». Властивості не заміняють приклади там, де приклад документує конкретний бізнес-випадок («на цьому реальному кошику має бути рівно стільки»), і не заміняють міркування про коректність. Вони роблять інше, чого приклади не вміють зовсім: перевіряють **закон над усім простором** — і саме тому просяться над кожним чистим ядром, де такий закон можна сформулювати.
