# ⚙️ Самовиклик, що подвоює лічильник: зламаний `InstrumentedHashSet` і пересильний клас, який його лікує

Є пастка, у яку потрапляє мало не кожен, хто вперше вирішує «трохи розширити» готовий клас зі стандартної бібліотеки. Вона підступна тим, що зв'язок «нащадок **є** предок» тут абсолютно чесний — жодного зайвого методу не протекло, жодної обіцянки поведінки не зламано, — а код усе одно рахує неправильно. Причина захована глибоко в тому, **як база кличе сама себе**, і побачити її можна лише простеживши виклик по тактах. Тому візьмемо конкретну дитячу задачу, доведемо наївне рішення до неправильної відповіді, з'ясуємо **точно**, звідки береться зайве число, а тоді перепишемо те саме на композицію й переконаємось, що та сама помилка зникає **сама собою** — не тому, що ми обережніші, а тому, що самовиклик тепер летить в інший бік.

Приклад тут — не вигаданий навчальний, а канонічний. Його поставив **Джошуа Блох (англ. Joshua Bloch)** — американський інженер, який очолював розробку бібліотеки колекцій Java (Java Collections Framework), — у книзі «Effective Java», у розділі, названому рівно нашою порадою: «Favor composition over inheritance» (пункт 18 у 3-му виданні, пункт 16 у 2-му — усталено). Тобто людина, що спроєктувала самі ці `HashSet` і `Set`, на власній бібліотеці показує, чому успадковувати від них наосліп небезпечно.

## Задача: множина, що рахує свої вставки

Потрібна така множина (англ. *set* — набір без повторів), яка додатково пам'ятає, **скільки елементів у неї за весь час намагалися покласти**. Не скільки їх зараз усередині (це `size()`), а скільки разів клієнт викликав додавання — лічильник спроб. Дрібниця, здавалось би: візьми готовий `HashSet`, який уже вміє все про множину, і доший йому лічильник.

Найпряміший об'єктний рефлекс — успадкувати `HashSet` і перевизначити обидва методи, якими додають елементи: `add` (додати один) і `addAll` (додати цілу пачку). Кожен нарощує лічильник на стільки, скільки додав:

```java
import java.util.*;

// Зламано — недоречне вживання спадкування!
class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;               // скільки елементів пробували додати

    @Override public boolean add(E e) {
        addCount++;                          // один елемент
        return super.add(e);
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();                // ціла пачка
        return super.addAll(c);
    }

    public int getAddCount() { return addCount; }
}
```

На вигляд бездоганно. `add` рахує один, `addAll` рахує розмір пачки, обидва чесно передають роботу базі через `super`. Зв'язок «є» тут теж чесний: `InstrumentedHashSet` **справді є** `HashSet` — усюди, де очікують множину, він підійде без застережень, жоден зайвий метод крізь інтерфейс не протік. Здавалося б, комар носа не підточить. Перевірмо.

## Найпряміший рефлекс — і чому він бреше

Додамо пачку з трьох рядків і спитаємо лічильник:

```java
var s = new InstrumentedHashSet<String>();
s.addAll(List.of("раз", "два", "три"));
System.out.println(s.getAddCount());   // очікуєш 3 — отримуєш 6
```

Шість. Ми додали три елементи, а лічильник каже шість. Не помилка на одиницю, не переповнення — рівно вдвічі. Щоб зрозуміти, звідки подвоєння, треба простежити виклик крок за кроком, бо саме в цих кроках схована вся суть:

```
s.addAll(["раз","два","три"])
  └─ InstrumentedHashSet.addAll:  addCount += 3         → addCount = 3
     └─ super.addAll(...)   // це успадкований HashSet.addAll
          для кожного елемента пачки він усередині кличе  this.add(e):
            ├─ this.add("раз")   → this — НАШ нащадок! → InstrumentedHashSet.add: ++  → 4
            ├─ this.add("два")   →                                              ++  → 5
            └─ this.add("три")   →                                              ++  → 6
```

Ось де захована пружина. Метод `addAll` у `HashSet` **не додає елементи сам** — він успадкований від `AbstractCollection` і реалізований так: пробігти пачку й на кожен елемент викликати `add`. Це легко перевірити: `HashSet` не має власного `addAll`, тож бере його від `AbstractCollection`, чий `addAll` дослівно ітерує по колекції та кличе `add(element)` на кожен елемент (усталений факт, звірений за документацією `AbstractCollection`). А `add` усередині цього циклу — це не якийсь абстрактний «add множини», це `this.add`, і `this` під час роботи вказує на **наш** об'єкт. Тому виклик потрапляє в **перевизначений** `add` нащадка, який знову нарощує лічильник — тепер уже втретє, вчетверте, вп'яте на ту саму пачку.

> 🔧 **Навіщо це.** Те, що `this.add` усередині бази потрапляє саме в наш перевизначений метод, а не в оригінальний `HashSet.add`, — не випадковість, а **динамічне зв'язування (англ. dynamic dispatch)**: конкретну реалізацію віртуального методу вибирає не тип змінної на компіляції, а справжній клас об'єкта під час роботи. Без цього механізму не було б ні поліморфізму, ні перевизначення взагалі — але саме він робить так, що внутрішній самовиклик бази «згинається вгору», у код нащадка, про існування якого база й гадки не має. Як саме працює цей вибір реалізації, розібрано в темі про [поліморфізм і динамічне зв'язування](book:programming/polymorphism) — коротко: у кожного об'єкта є прихований покажчик на таблицю його методів, і виклик іде через неї, тож завжди влучає в найпохіднішу версію.

Ось той самий подвійний облік на одному малюнку — і поряд те, у що він перетвориться, коли ту саму задачу розв'язати композицією:

![Ліворуч спадкування: один об'єкт InstrumentedHashSet, виклик addAll додає 3, тоді успадкований HashSet.addAll усередині кличе this.add, і червона крива згинається вгору в перевизначений add нащадка, додаючи ще 3, разом 6, помилка. Праворуч композиція: обгортка InstrumentedSet додає 3 і пересилає в окрему деталь s типу HashSet, чий внутрішній s.add замикається петлею всередині самої деталі й до обгортки не дотягується, разом 3, правильно](/book/programming/software-design/composition-inheritance/img/self-call-bend.svg)

*Той самий `addAll([a, b, c])` двома способами. У спадкуванні нащадок і база — **один об'єкт**, тож внутрішній `this.add` бази згинається вгору, у перевизначений `add`, і пачку рахують двічі. У композиції загорнутий `HashSet` — **окрема деталь**: його самовиклик `s.add` замикається всередині неї й до лічильника обгортки не дотягується.*

## Чому «прибрати подвійний облік» — не лік

Перша думка після трасування — «то приберімо `addCount += c.size()` з `addAll`, хай пачку рахує лише внутрішній `add`». І справді, тоді вийде три. Але це **оманлива перемога**, і зрозуміти, чому саме, важливіше за сам баг.

Прибравши свій `addAll`, ти мовчки поклався на те, що `HashSet.addAll` **завжди** реалізовано поверх `add`. А це — **недокументована деталь реалізації**. У контракті `Set` ніде не написано, що `addAll` зобов'язаний кликати `add`; це просто **як воно влаштоване сьогодні**. Блох називає таку внутрішню звичку класу кликати власні перевизначувані методи **самовикликом (англ. self-use)** і прямо пише: «This "self-use" is an implementation detail, not guaranteed to hold in all implementations of the Java platform and subject to change from release to release» — це деталь реалізації, не гарантована для всіх реалізацій платформи й здатна змінитися від випуску до випуску.

Простежмо, чим це загрожує. Уяви, що в наступній версії бібліотеки автори оптимізують `HashSet.addAll`: замість крутити цикл через `add` він тепер розкладає всю пачку в хеш-таблицю навпростець, жодного разу не кличучи `add`. Ніхто не порушив жодної обіцянки — публічний контракт `addAll` («додати всі елементи») дотримано, — але твій нащадок, підігнаний під стару внутрішню механіку, тепер рахуватиме **нуль** для пачкових додавань. Твій код зламався **сам, без жодної твоєї правки**, від оновлення чужої бібліотеки. Ти будував на піску: твоя коректність залежала від **графа внутрішніх викликів бази**, а цей граф ти не бачиш, він не входить у контракт і може зсунутися під тобою будь-якого релізу.

Зверни увагу, наскільки ця біда тонша за класичний закид спадкуванню. Тут **немає** протікання зайвих методів, немає порушення підстановки: `InstrumentedHashSet` бездоганно проходить перевірку [принципу підстановки Лісков](book:programming/liskov-substitution) — усюди, де очікують `HashSet`, він підійде й поводитиметься як множина. Лісков задоволена, «є» чесне — а клас усе одно крихкий. Це і є **проблема крихкого базового класу (англ. fragile base class problem)** у найтоншій, семантичній подобі: нащадок зрісся не із зайвим методом, а з тим, **як саме база кличе сама себе** — з невидимою деталлю, яку інкапсуляція мала повне право ховати й міняти.

## Ідея: не бути `HashSet`, а тримати `Set` і пересилати

Корінь біди — у тому, що нащадок і база живуть в **одному** об'єкті: `this` там один на двох, тож самовиклик бази неминуче знаходить перевизначення нащадка. Розірвати це зрощення можна одним ходом — **перестати бути** `HashSet` і почати **тримати** його збоку.

Замість «рахувальна множина **є** `HashSet`» скажімо «рахувальна множина **має** всередині якусь `Set` і **пересилає** їй усю роботу». Тоді загорнута множина — окремий об'єкт зі своїм власним `this`; коли всередині неї спрацьовує самовиклик, він знаходить її **власний** `add`, а не наш. Наш лічильник для внутрішніх викликів бази просто недосяжний — і подвоєння нема звідки взятися.

Технічно це розкладається на дві незалежні деталі, і саме розділення робить рішення чистим:

- **пересильний клас (англ. *forwarding class*)** — обгортка, що реалізує інтерфейс `Set` і **кожен** його метод тупо переадресовує загорнутому об'єктові, нічого не додаючи. Сама по собі вона поводиться точнісінько як загорнута множина — це **багаторазова заготовка**, у якій ще нема жодної нашої логіки;
- **лічильник поверх заготовки** — маленький клас, що успадковує пересильну заготовку й перевизначає лише ті два методи, які має рахувати (`add` і `addAll`), додаючи облік і далі передаючи роботу вниз.

## Робочий код: пересильний клас і лічильник поверх нього

Спершу — багаторазова пересильна заготовка. Вона тримає загорнуту `Set` приватним полем `s` і **делегує** їй геть усе. Жодної власної логіки тут нема; її призначення — щоб клас-лічильник не мусив вручну переписувати два десятки методів `Set`, а перевизначав лише потрібні:

```java
import java.util.*;

// Багаторазовий пересильний клас: реалізує Set, усе передає полю s.
class ForwardingSet<E> implements Set<E> {
    private final Set<E> s;                       // загорнута множина
    public ForwardingSet(Set<E> s) { this.s = s; }

    public void clear()                              { s.clear(); }
    public boolean contains(Object o)                { return s.contains(o); }
    public boolean isEmpty()                         { return s.isEmpty(); }
    public int size()                                { return s.size(); }
    public Iterator<E> iterator()                    { return s.iterator(); }
    public boolean add(E e)                          { return s.add(e); }
    public boolean remove(Object o)                  { return s.remove(o); }
    public boolean containsAll(Collection<?> c)      { return s.containsAll(c); }
    public boolean addAll(Collection<? extends E> c) { return s.addAll(c); }
    public boolean removeAll(Collection<?> c)        { return s.removeAll(c); }
    public boolean retainAll(Collection<?> c)        { return s.retainAll(c); }
    public Object[] toArray()                        { return s.toArray(); }
    public <T> T[] toArray(T[] a)                    { return s.toArray(a); }

    @Override public boolean equals(Object o) { return s.equals(o); }
    @Override public int hashCode()           { return s.hashCode(); }
    @Override public String toString()        { return s.toString(); }
}
```

Тепер лічильник. Він успадковує **пересильну заготовку** (а не `HashSet`!) і перевизначає рівно ті самі два методи, що й раніше:

```java
// Обгортка з лічильником — композиція замість спадкування HashSet.
class InstrumentedSet<E> extends ForwardingSet<E> {
    private int addCount = 0;

    public InstrumentedSet(Set<E> s) { super(s); }   // загортаємо будь-яку Set

    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);                          // → ForwardingSet.add → s.add
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);                       // → ForwardingSet.addAll → s.addAll
    }

    public int getAddCount() { return addCount; }
}
```

Код майже дослівно повторює зламану версію — ті самі `addCount++` і `addCount += c.size()`. Але тепер він рахує правильно:

```java
var s = new InstrumentedSet<>(new HashSet<String>());
s.addAll(List.of("раз", "два", "три"));
System.out.println(s.getAddCount());   // 3 — рівно стільки, скільки додали
```

Три. Ті самі два перевизначення, що подвоювали лічильник під спадкуванням, тепер дають точну відповідь. Простежмо чому — різниця вся в одному кроці:

```
s.addAll(["раз","два","три"])              // s — наша обгортка InstrumentedSet
  └─ InstrumentedSet.addAll:  addCount += 3            → addCount = 3
     └─ super.addAll(c)   // ForwardingSet.addAll
          └─ s.addAll(c)  // s — ЗАГОРНУТИЙ HashSet, окремий об'єкт
               усередині HashSet.addAll кличе  this.add(e),
               але this ТУТ — сам загорнутий HashSet, не наша обгортка:
                 ├─ (HashSet).add("раз")   // наш лічильник НЕ зачеплено
                 ├─ (HashSet).add("два")
                 └─ (HashSet).add("три")
                                                        addCount лишається = 3 ✓
```

Ось воно. Виклик `super.addAll` іде в пересильну заготовку, та переадресовує його загорнутому `HashSet`, і всередині того `HashSet` самовиклик `this.add` знаходить **його власний** `add` — бо `this` там указує на загорнутий об'єкт, а не на нашу обгортку. Загорнутий `HashSet` **не знає**, що його хтось обгорнув; він замкнений сам на себе. Самовиклик, який під спадкуванням згинався вгору й дотягувався до нашого лічильника, тепер замикається петлею **всередині деталі** й до нас не долітає. Пачку порахували рівно раз — у нашому `addAll`.

Зверни увагу на дзеркальну симетрію з бідою. Під спадкуванням перевизначення **обох** методів давало подвоєння (самовиклик тік угору); під композицією перевизначення тих самих обох методів **обов'язкове й точне** (самовиклик замкнувся вниз). Один і той самий код — протилежний результат, і вирішує його лише те, куди адресований внутрішній `this.add`.

## Чому це «камінно надійно»

Тепер найголовніше — те, заради чого весь перехід і робився. Наша обгортка спирається **тільки на публічний інтерфейс** `Set`: вона кличе `s.add`, `s.addAll`, `s.size` — методи з контракту, обіцяні назавжди. Вона **ніде** не покладається на те, як `HashSet` улаштований усередині, чи кличе його `addAll` свій `add`, у якому порядку він робить свою роботу. Тому їй байдуже, що там перепишуть автори бібліотеки в наступному релізі: доки `Set` виконує свій публічний контракт, наш лічильник рахує правильно. Блох формулює це коротко: клас виходить «rock solid, with no dependencies on the implementation details of the existing class» — камінно надійним, без жодної залежності від деталей реалізації бази.

І це ще не все, що ми виграли. Оскільки обгортка знає лише інтерфейс `Set`, вона загортає **будь-яку** його реалізацію, а не самий `HashSet`:

```java
Set<String> ordered = new InstrumentedSet<>(new LinkedHashSet<>()); // множина з порядком вставки
Set<String> sorted  = new InstrumentedSet<>(new TreeSet<>());       // відсортована множина
```

Той самий лічильник тепер працює й над `LinkedHashSet`, і над `TreeSet`, і над будь-якою майбутньою множиною, якої ще навіть не написано, — аби вона реалізовувала `Set`. У світі спадкування довелося б заводити окремий `InstrumentedLinkedHashSet`, `InstrumentedTreeSet` і так далі, по класу на кожну базу; тут — одна обгортка на всіх.

> 🔧 **Навіщо це.** Клас, що загортає інший об'єкт того самого інтерфейсу й додає йому поведінку навколо, — це і є патерн **декоратор (англ. *decorator* — оздоблювач)**: обгортка «оздоблює» деталь новим шаром (тут — обліком), не чіпаючи ні її код, ні її тип. Саме на цьому стоять, наприклад, буферизовані потоки в багатьох бібліотеках: `BufferedReader` загортає будь-який `Reader` і додає буфер, нічого не знаючи про конкретне джерело. Механіку й межі цього патерна розібрано в темі про [декоратор](book:programming/decorator).

## Самовиклик — не примха Java

Може здатися, що вся ця біда — примха конкретно `HashSet` чи конкретно Java. Ні. Самовиклик — базовий механізм будь-якої мови з віртуальними методами: щойно метод базового класу кличе інший **перевизначуваний** метод того самого об'єкта, виклик під час роботи полетить у найпохіднішу версію. Щоб побачити це очима, а не на віру, напишімо базу **власноруч** — так, щоб самовиклик було видно в самому коді, — і зробімо це двома різними мовами:

:::tabs
```java
// База, чий пачковий метод САМ кличе перевизначуваний add — самовиклик як на долоні.
class Bag<E> {
    protected List<E> items = new ArrayList<>();
    public void add(E e)                { items.add(e); }
    public void addAll(Collection<E> c) { for (E e : c) add(e); }   // ← самовиклик
}

// Нащадок рахує — і ловить те саме подвоєння, що й з HashSet.
class CountingBag<E> extends Bag<E> {
    int count = 0;
    @Override public void add(E e)                { count++;          super.add(e); }
    @Override public void addAll(Collection<E> c) { count += c.size(); super.addAll(c); }
}
// new CountingBag<String>().addAll(List.of("a","b","c"))  →  count = 6, а не 3
```
```python
# Та сама база: пачковий метод сам кличе перевизначуваний add.
class Bag:
    def __init__(self):        self.items = []
    def add(self, e):          self.items.append(e)
    def add_all(self, xs):
        for e in xs: self.add(e)                    # ← самовиклик

# Нащадок рахує — і ловить те саме подвоєння.
class CountingBag(Bag):
    def __init__(self):
        super().__init__(); self.count = 0
    def add(self, e):     self.count += 1;      super().add(e)
    def add_all(self, xs): self.count += len(xs); super().add_all(xs)

# CountingBag().add_all(["a","b","c"])  →  count == 6, а не 3
```
:::

В обох мовах результат однаковий: `count` виходить 6, бо `add_all` спершу рахує пачку сам, а тоді його самовиклик `add` ще раз проходить її через перевизначений лічильник. Механізм тотожний — різниця лише в синтаксисі `super`.

Одне чесне уточнення саме про Python. Його **вбудований** `set` тут подвоєння не дасть: метод `set.update` (пачкове додавання) реалізовано на рівні C і працює з внутрішньою хеш-таблицею навпростець, **не** кличучи ваш пайтонівський `add`. Тобто конкретний баг «успадкуй вбудований `set` і перевизнач `add`/`update`» у Python не відтвориться — і це якраз ілюструє головну думку: чи є самовиклик, залежить від **невидимої деталі реалізації** конкретної бази, а не від мови. У Java `HashSet.addAll` цей самовиклик має; у CPython `set.update` — ні; а щойно базу пишете ви самі, як `Bag` вище, — самовиклик з'являється однаково в обох мовах. Висновок той самий: не будуй на тому, як чужий клас кличе сам себе, бо ти цього не бачиш.

## Складність і пастки

Композиція з пересиланням — сильний і правильний за замовчуванням хід, але чесний інженер знає його ціну й межі. Назвімо їх поіменно.

**Пастка перша: писати пересилання руками — нудно, і легко змінити не той метод.** Інтерфейс `Set` має півтора десятка методів, і всі їх довелося переписати короткими обгортками, перш ніж додати бодай рядок власної логіки. Для багатших інтерфейсів це десятки однакових на вигляд рядків — шум, у якому легко схибити. На щастя, пересильну заготовку пишуть **раз** і перевикористовують під усі обгортки над цим інтерфейсом; а на практиці її часто й писати не треба — бібліотеки вже дають готові. Приміром, Guava від Google має абстрактні класи `ForwardingSet`, `ForwardingCollection`, `ForwardingMap` і так далі: успадкуй такий, перевизнач один метод `delegate()`, що повертає загорнутий об'єкт, — і решта методів пересилаються самі (звірено за документацією Guava).

**Пастка друга, тонка й повчальна: пересилання «наскрізне», тож перевизначати треба саме ті методи, що несуть логіку — і не забути жодного.** Наша заготовка передає `addAll` **прямо** загорнутій множині, минаючи наш `add`. Це означає: якби ми перевизначили лише `add`, а `addAll` лишили заготовці, то пачкові додавання **не порахувалися б зовсім** (`addAll` пішов би прямо в `s.addAll`, а той — у власний `s.add` деталі, повз наш лічильник) — вийшов би недооблік. Саме тому `InstrumentedSet` перевизначає **обидва** методи. Це не дрібниця й не наша примха: документація тієї ж Guava окремо застерігає, що методи `ForwardingSet` пересилають незалежно один від одного, і перевизначення самого лише `add` не змінить поведінки `addAll` — його треба перевизначати теж. Урок: у пересильній обгортці тримай у голові **всі** шляхи, якими до потрібної поведінки можна дійти, і закрий кожен.

**Пастка третя, найглибша — проблема SELF.** Є ситуація, де обгортка справді програє спадкуванню, і про неї треба знати. Це **фреймворки зі зворотними викликами (англ. *callbacks*)**, де об'єкт передає кудись **посилання на себе**, щоб його потім покликали назад. Загорнутий об'єкт про свою обгортку **не знає** — тож передає посилання на **себе** (`this` деталі), а не на обгортку. Коли фреймворк потім зробить зворотний виклик, він покличе метод **голої деталі**, і весь доданий обгорткою шар (наш облік) буде **обійдено**. Блох називає це **проблемою SELF (англ. *SELF problem*)**: зворотні виклики «вислизають від обгортки», бо деталь не має способу віддати назовні себе-в-обгортці замість себе-голої (звірено за «Effective Java»). Спадкування такої вади не має — там нащадок і база один об'єкт, і `this` завжди найпохідніший. Тож якщо твій клас **мусить** роздавати посилання на себе в callback-фреймворк, обгортка — не твій інструмент.

**Пастка четверта, про рівність.** Пересилати `equals`/`hashCode`/`toString` до деталі — свідоме рішення, а не автоматизм. Наша заготовка їх пересилає, тож обгорнута множина «дорівнює» голій множині з тим самим вмістом — зазвичай це те, чого хочуть від `Set`. Але якщо обгортка додає стан, що **мав би** впливати на рівність, наскрізне пересилання `equals` це проґавить; а необережне змішування обгорнутих і голих об'єктів в одній колекції здатне тихо порушити симетрію рівності. Для простого лічильника, що на тотожність множини не впливає, пересилати правильно — але саме рішення роби свідомо.

**І межа, за якою все це зайве: коли успадковувати таки можна.** Композиція лікує крихкість, якої в успадкуванні **реалізації** не уникнути наосліп. Але спадкування лишається чесним інструментом у двох випадках. Перший — коли база **спроєктована й задокументована під успадкування**: її автор явно виписав свій граф самовикликів (де вона кличе власні перевизначувані методи) і пообіцяв його не ламати; тоді ти успадковуєш не наосліп, а за оприлюдненим контрактом. Другий, майже завжди безпечний, — коли ти успадковуєш **чистий інтерфейс**, а не реалізацію: у абстрактного типу без тіл методів немає нутрощів, немає самовикликів, немає чому протікати чи подвоюватися — крихка база просто не виникає. Уся біда цієї вставки — про успадкування **реалізації** (класу з нутром); саме її й радять за замовчуванням міняти на композицію з пересиланням, лишаючи `extends` для тих вузьких випадків, де база чесно запросила себе успадкувати.
