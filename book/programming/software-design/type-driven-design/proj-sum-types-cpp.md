# ⚙️ Сума-типи й новотипи в C++: робочий код

Стаття показала два прийоми на пальцях: згорнути розсипаний стан у суму (`std::variant`) і дати кожному поняттю власний тип-обгортку (новотип). Тут — той самий матеріал, доведений до коду, який справді компілюється й працює в прошивці, з усіма гострими кутами, об які об'єктивно ріжуться. Бо між «ідея зрозуміла» і «воно скомпілювалося й не впало на дрейфі індексу» лежить купа дрібниць, і саме в них уся різниця.

Розберемо дві задачі. Перша — кінцевий автомат стану мережевого запиту на `std::variant<Loading, Failed, Ready>`: як його розбирати двома способами, чому один з них дає компіляторові шанс зловити забутий випадок, а другий — ні, і які пастки чатують (кинутий `std::get`, valueless-стан, порядок альтернатив). Друга — сильні обгортки над примітивами: `Latitude`/`Longitude`, `Meters`/`Seconds`, з операторами, перетворенням одиниць і шаблоном-помічником проти дублювання. Кінець — про те, коли обгортка справді варта заходу, а коли це порожня церемонія.

---

## Задача 1. Кінцевий автомат стану запиту

**Задача.** Прошивка тягне дані з мережі — телеметрію, конфіг, будь-що. У кожну мить запит перебуває рівно в одному зі станів: **триває** (`Loading`), **впав із помилкою** (`Failed`), **завершився з даними** (`Ready`). UI-код, логіка повторів, індикатор на екрані — усі мусять на цей стан реагувати, і жоден не сміє переплутати чи забути випадок.

**Ідея.** Стан — це сума трьох випадків, а не структура з прапорцями. Кожен випадок — окремий тип рівно з тими полями, що йому потрібні. Розбирати стан — не питати «а раптом і те, і те», а перебрати три чесні альтернативи так, щоб компілятор наглядав за повнотою перебору.

### Кістяк типу

```cpp
#include <variant>
#include <string>
#include <cstdint>

struct Data {                    // те, що зрештою отримали (умовно)
    int32_t  code;
    uint16_t length;
};

struct Loading {};                             // жодного поля — сам факт «триває»
struct Failed  { std::string message;          // текст помилки для лога/екрана
                 int          httpCode; };      // і код відповіді, якщо був
struct Ready   { Data value; };                // лише корисне навантаження

using RequestState = std::variant<Loading, Failed, Ready>;
```

Три речі варто вимовити повільно, бо на них усе тримається.

`Loading` — **порожній тип**. Він не несе даних, лише каже «я — оцей випадок». Це нормально й правильно: сенс тут не в полях, а в самому факті, що активна саме ця альтернатива. Порожня структура займає 1 байт (стандарт забороняє нульовий розмір повного об'єкта), але всередині `variant` цей байт розчиняється в спільному сховищі — окремих витрат нема.

`Failed` **не має** поля `value`, а `Ready` **не має** поля `message`. Це не домовленість «давайте не чіпати чужі поля» — їх фізично немає в цих типах. Стан «помилка, але з даними» неможливо записати: немає структури, куди це вкласти. Саме тут незаконні поєднання зникають не з голови програміста, а з простору можливих значень.

`std::variant<Loading, Failed, Ready>` тримає в собі рівно один з трьох об'єктів за раз плюс маленький **індекс** (зазвичай один байт) — номер активної альтернативи. Розмір усього `variant` — це розмір найбільшої альтернативи плюс індекс плюс вирівнювання; ніякого купи-виділення (англ. *heap allocation*) немає, усе лежить на місці. Для прошивки це важливо: сума-тип не тягне за собою динамічну пам'ять, лягає в статичний буфер, придатний навіть там, де купа заборонена.

> 🔧 **Навіщо це.** У вбудованих системах кожен зайвий байт RAM і кожне непередбачуване виділення пам'яті — біль. `std::variant` дає суму-тип **без купи**: розмір відомий на компіляції, розкладка щільна, час доступу сталий. Ти отримуєш безпеку «рівно один випадок» задарма щодо пам'яті — те, за що в мовах із купою-об'єктами платять алокацією на кожен стан.

### Створення значень

Присвоїти стан — просто покласти в змінну об'єкт потрібного випадку. `variant` сам запам'ятає, який тип активний:

```cpp
RequestState st = Loading{};                 // старт: триває
// ...мережа відповіла помилкою...
st = Failed{ "timeout", 504 };               // тепер активний Failed
// ...або успіхом...
st = Ready{ Data{ 0, 128 } };                // тепер активний Ready
```

Кожне присвоєння руйнує попередній активний об'єкт (викликає його деструктор) і будує новий на тому ж місці. Індекс усередині оновлюється автоматично. Ніякого ручного «спершу занулити старе поле» — цим опікується сам тип.

Коли конструктор випадку неоднозначний або треба збудувати об'єкт на місці без зайвої копії, є `emplace`:

```cpp
st.emplace<Failed>("connection refused", 111);   // будує Failed прямо в variant
```

### Розбір через `std::visit` та overloaded-лямбди

Перший і найсильніший спосіб дістати значення зі стану — **відвідати** його (`std::visit`). Ти даєш набір обробників, по одному на випадок, а `visit` сам добирає той, що пасує активній альтернативі. Найзручніше зібрати обробники з лямбд через ідіому **overloaded**:

```cpp
#include <variant>

// Ідіома overloaded: зліпити кілька лямбд в один об'єкт-візитор.
template <class... Ts>
struct overloaded : Ts... { using Ts::operator()...; };
// Підказка виведення (англ. deduction guide) — потрібна в C++17;
// у C++20 вивід для агрегатів працює й без неї, рядок стає зайвим.
template <class... Ts> overloaded(Ts...) -> overloaded<Ts...>;
```

Це два рядки, але за ними — три можливості C++17, які варто розуміти, бо саме на них ідіома тримається. `struct overloaded : Ts...` — **успадкування від пакета типів**: візитор успадковує від кожної переданої лямбди. `using Ts::operator()...;` — **розгортання пакета в using-оголошенні**: витягуємо `operator()` кожної лямбди в область видимості нащадка, щоб усі вони стали перевантаженнями одного виклику. А підказка виведення дозволяє написати `overloaded{ lambda1, lambda2, lambda3 }` і дати компіляторові самому скласти список базових типів (у C++20 агрегатне виведення робить це саме, тож другий рядок можна викинути). Ось як це працює на нашому стані:

```cpp
#include <string>

std::string describe(const RequestState& st) {
    return std::visit(overloaded{
        [](const Loading&)      { return std::string{"Вантажимо…"}; },
        [](const Failed&  f)    { return "Помилка (" + std::to_string(f.httpCode)
                                         + "): " + f.message; },
        [](const Ready&   r)    { return "Готово, байтів: "
                                         + std::to_string(r.value.length); },
    }, st);
}
```

`std::visit` дивиться на активний індекс `st` і викликає рівно ту лямбду, чий параметр пасує. Жодних `if`, жодних приведень — диспетчеризація за типом, яку компілятор перетворює зазвичай на просту таблицю переходів (англ. *jump table*).

**Ключова властивість, заради якої це все й затіяно:** якщо ти забудеш лямбду для якогось випадку, код **не скомпілюється**. Прибери обробник `Ready` — і `std::visit` не знайде перевантаження для випадку, коли активний `Ready`, тож збірка впаде. Компілятор перетворюється на сторожа повноти: додав у `variant` новий випадок — усі `visit`, які його не обробляють, засвітяться помилкою, і ти фізично не можеш забути жоден. Це і є перевага суми над `switch` по `enum`, де забутий `case` мовчки провалюється у `default` або й у ніщо.

> 🔧 **Навіщо це.** Уяви, що через півроку в стан додали четвертий випадок — `Cancelled`. З `switch` по числовому коду забутий `case` тихо провалиться, і скасований запит поведеться як хтозна-що — баг знайдуть у полі. З `std::visit` без обробника `Cancelled` **проєкт не збереться**, і компілятор пальцем покаже кожне місце, яке треба доповнити. Повнота перебору стає властивістю, яку доводить збірка, а не пам'ять програміста.

Одна тонкість overloaded, об яку спотикаються: **усі лямбди мусять повертати сумісний тип**, бо `std::visit` повинен мати один тип результату. Якщо одна лямбда віддає `std::string`, а інша — `const char*`, компілятор не зведе їх до спільного типу й лайнеться. Тому вище всі гілки явно повертають `std::string` (перша — через `std::string{...}`, щоб не проскочив `const char*`). Коли гілки природно різнотипні, або зводь їх руками до спільного типу, або задай тип результату явно: `std::visit<std::string>(...)`.

### Розбір через `std::get_if`

Другий спосіб — питати по одному: «а зараз активний `Failed`?». Для цього є `std::get_if<T>(&variant)` — він повертає **вказівник** на значення, якщо активний саме `T`, і `nullptr` інакше:

```cpp
std::string describe_getif(const RequestState& st) {
    if (std::get_if<Loading>(&st))              // просто перевірка активності
        return "Вантажимо…";
    if (auto* f = std::get_if<Failed>(&st))     // активний? — маємо вказівник
        return "Помилка (" + std::to_string(f->httpCode) + "): " + f->message;
    if (auto* r = std::get_if<Ready>(&st))
        return "Готово, байтів: " + std::to_string(r->value.length);
    return {};   // сюди не потрапити: інших випадків немає
}
```

`std::get_if` бере **вказівник** на `variant` (не посилання) і повертає **вказівник** на значення — тому перевірка на `nullptr` природна й безпечна. Це чистий, читабельний спосіб, і для двох-трьох випадків він цілком годиться. Часто зручний, коли обробити треба лише один випадок, а решту проігнорувати: `if (auto* r = std::get_if<Ready>(&st)) use(r->value);` — і все.

Але тут і криється принципова різниця з `visit`, яку треба ясно бачити. **Ланцюжок `if`-ів компілятор НЕ перевіряє на повноту.** Додаси в `variant` четвертий випадок `Cancelled` — цей код спокійно скомпілюється, просто мовчки поверне `{}` для скасованого запиту. Ніякої помилки збірки, ніякого попередження. Забутий випадок проживе до рантайму. Ось чому `visit` з overloaded — сильніший інструмент там, де важлива гарантія повноти: він **змушує** обробити все. `get_if` віддає цю гарантію в обмін на простоту. Правило просте: коли перебираєш **усі** випадки й хочеш, щоб компілятор стеріг повноту, — `visit`; коли смикаєш **один-два** випадки принагідно — `get_if`.

Ту саму думку — про повноту перебору й про те, чому сума краща за прапорці — стаття веде на прикладі цього ж стану; історію того, як людство доходило до «незаконний стан не має форми» (аж до Гоарового «null — моя мільярдна помилка»), винесено в [окрему хроніку](book:programming/type-driven-design/hist-null-and-illegal-states.md).

### Пастка перша: `std::get` кидає

Поряд із `std::get_if` живе його підступний родич `std::get<T>(variant)`. Він робить майже те саме — дістає значення альтернативи `T` — але **повертає посилання, а не вказівник**, і якщо активний не `T`, **кидає виняток `std::bad_variant_access`**:

```cpp
RequestState st = Loading{};

auto& f = std::get<Failed>(st);   // активний Loading, а не Failed →
                                  // КИНЕ std::bad_variant_access
```

Це джерело справжніх падінь. Спокуса написати `std::get<Ready>(st).value` замість перевірки виглядає коротшою, але це бомба сповільненої дії: у момент, коли стан виявиться іншим, програма кине виняток, а в прошивці без обробки винятків — просто впаде (`std::terminate`). **Практичне правило: `std::get` бери лише коли активність альтернативи щойно доведено** — наприклад, одразу після `if (st.index() == …)` чи в гілці, де тип гарантований. У всіх інших місцях — `get_if` (повертає `nullptr`, який неможливо не помітити) або `visit`. Різниця з `get_if` рівно в тому, як тип відповідає на «не той випадок»: `get_if` — тихим `nullptr`, `get` — гучним винятком.

### Пастка друга: valueless_by_exception

Є рідкісний, але дратівливий стан, у який `std::variant` здатен провалитися: **valueless-стан** (буквально «без значення через виняток»). У ньому `variant` не тримає жодної альтернативи — `index()` повертає особливе значення `std::variant_npos`, а `visit` і `get` починають кидати `std::bad_variant_access`.

Звідки він береться? Із незручного факту: `variant` **ніколи не виділяє купу**. Коли ти присвоюєш нову альтернативу, старий об'єкт руйнується, а на його місці будується новий. Якщо конструктор нового об'єкта (точніше — переміщення при type-changing присвоєнні) **кине виняток посеред цієї операції**, старе значення вже зруйноване, а нове не добудоване — і `variant` не має куди відступити, бо запасної пам'яті під купою немає. Він лишається порожнім — valueless. За стандартом це **гарантовано трапляється лише при кидку в move-присвоєнні**; при копіюванні реалізація може викрутитися, збудувавши об'єкт спершу на стеку.

```cpp
if (st.valueless_by_exception()) {
    // рідкість, але про всяк випадок: variant порожній.
    // тут visit/get кинуть — не чіпаємо їх, обробляємо окремо
    return "стан втрачено";
}
```

На практиці для прошивки це майже завжди неактуально: наші альтернативи — `Loading` (порожня), `Failed` (рядок), `Ready` (POD-дані) — мають **noexcept-переміщення** або переміщення, що не кидає в звичайних умовах. Поки типи-альтернативи переміщуються без винятків, valueless-стан не настане взагалі. Тому головна порада не «скрізь перевіряй valueless», а **«роби альтернативи дешево-переміщуваними»**: тоді проблема зникає в корені. Явна перевірка `valueless_by_exception()` потрібна лише там, де серед альтернатив є тип із важким, здатним кинути переміщенням.

### Пастка третя: порядок альтернатив і індекс за замовчуванням

Дві дрібниці, що кусають несподівано.

**Перша: за замовчуванням `variant` конструюється в першу альтернативу.** `RequestState st;` без ініціалізатора дасть активний `Loading` — бо він перший у списку. Це зручно (стан «за замовчуванням триває» — розумний старт), але лише тому, що перша альтернатива вибрана свідомо. Якби першим стояв `Failed`, то `RequestState st;` мовчки народжував би стан «помилка» з порожнім повідомленням — очевидна дурниця. **Правило: став першою ту альтернативу, чиє значення за замовчуванням має сенс** (тут — `Loading`). Якщо жодна не годиться за замовчуванням і треба заборонити безпараметрове створення — постав першим `std::monostate` (спеціальний порожній тип-заглушка саме для цього) або зроби першу альтернативу такою, що не конструюється без аргументів.

**Друга: не звертайся до альтернатив за числовим індексом.** `std::get<0>(st)`, `std::get<1>(st)` технічно працюють, але прив'язують код до **порядку** типів у `variant`. Переставиш альтернативи місцями чи вставиш нову — усі числові індекси попливуть, і код тихо почне діставати не те. **Завжди адресуй за типом** (`std::get_if<Failed>`), не за номером: тип не залежить від порядку, і рефакторинг списку альтернатив нічого не ламає. Числовий індекс лишай хіба для `st.index()` у діагностиці, де тобі байдуже, який саме номер, — важливо лише, що він змінився.

### Складність і пастки: підсумок автомата

Автомат на `std::variant` дає рівно те, що обіцяла стаття: **незаконний стан не існує як значення**. Але сила приходить не задарма, і зрілість — тримати в голові весь список гострих кутів:

- **`std::get` кидає** `std::bad_variant_access` на невідповідності — бери його лише коли тип щойно доведено; інакше `get_if` (тихий `nullptr`) або `visit`.
- **`visit` перевіряє повноту, ланцюжок `if`-ів — ні.** Хочеш, щоб компілятор стеріг усі випадки, — `visit` з overloaded; смикаєш один випадок — `get_if`.
- **Overloaded вимагає сумісного типу результату** від усіх лямбд — зводь явно або задавай `std::visit<R>`.
- **valueless_by_exception** — рідкісний порожній стан після кидка в move-присвоєнні; гаситься тим, що альтернативи роблять дешево-переміщуваними (noexcept).
- **Перша альтернатива — стан за замовчуванням**; став першою розумну (тут `Loading`) або `std::monostate`.
- **Адресуй за типом, не за індексом** — числові `get<0>` ламаються від перестановки альтернатив.

Тримаючи цей список, ти отримуєш сумарний тип, який у прошивці лягає в статичну пам'ять, диспетчеризується за таблицею переходів і не дає забути жоден випадок — коштом кількох ідіом, які варто вивчити раз і назавжди.

## Задача 2. Сильні новотипи-обгортки

**Задача.** Прошивка дрона оперує величинами, які легко переплутати, бо всередині вони — той самий `double`: широта й довгота, метри й секунди, градуси й радіани. Функція `moveTo(double, double)` мовчки проковтне переплутані аргументи, і апарат полетить не туди. Треба зробити так, щоб компілятор **не дав** підставити довготу туди, де чекають широту, чи метри туди, де секунди.

**Ідея.** Дати кожному поняттю **власний тип** — тонку структуру-обгортку над одним `double`. Дані ті самі, але **ім'я для компілятора** різне, і цього досить: `Longitude` не є `Latitude`, тож переплутати їх — помилка збірки. Такий тип-обгортку над одним значенням і звуть **новотипом** (англ. *newtype*) — нове ім'я, а не нові дані.

### Наївна обгортка та її дірки

Перший підхід — проста структура:

```cpp
struct Latitude  { double deg; };
struct Longitude { double deg; };

void moveTo(Latitude lat, Longitude lon);
```

Це вже ловить головну помилку: `moveTo(lon, lat)` не скомпілюється, бо `Longitude` і `Latitude` — різні типи. Добре. Але наївна обгортка лишає дві дірки, які варто одразу залатати.

**Дірка перша: неявне будування з голого `double`.** Якщо конструктор не позначено `explicit`, компілятор дозволить мовчазне перетворення:

```cpp
Latitude lat = 50.45;      // без explicit — мовчки загорнув
moveTo(50.45, 30.52);      // а це взагалі повернуло нас у світ голих double?
```

Гола `50.45` тихо стає `Latitude` — і вся охорона просідає, бо число знову вільно перетікає в тип. Ліки — **explicit-конструктор**: тоді загорнути можна лише навмисне, і кожне таке місце впадає в око.

**Дірка друга: агрегат впускає будь-що.** `Latitude{50.45}` — це агрегатна ініціалізація, вона працює й без конструктора, але так само мовчки бере `int`, звужує типи й не дає жодної точки, куди вставити перевірку діапазону. Тож зробімо обгортку як слід — з `explicit`-конструктором.

### Обгортка як слід

```cpp
class Latitude {
    double deg_;
public:
    explicit constexpr Latitude(double d) : deg_(d) {}   // лише навмисне загортання
    constexpr double value() const { return deg_; }      // дістати голе число
};

class Longitude {
    double deg_;
public:
    explicit constexpr Longitude(double d) : deg_(d) {}
    constexpr double value() const { return deg_; }
};

void moveTo(Latitude lat, Longitude lon);
```

Тепер:

```cpp
moveTo(Latitude{50.45}, Longitude{30.52});   // ясно, однозначно, безпечно
moveTo(Longitude{30.52}, Latitude{50.45});   // ПОМИЛКА: типи не на своїх місцях
Latitude x = 50.45;                          // ПОМИЛКА: explicit не пускає неявно
```

`explicit` тут — не прикраса, а серце обгортки. Без нього тип-новотип напівпрозорий: число просочується крізь нього неявно, і захист від плутанини провалюється. З ним будування завжди видиме, а всі інші перетворення — заборонені. `constexpr` дозволяє рахувати з такими типами на компіляції (наприклад, задавати сталі координати без рантайм-витрат), а сама обгортка над одним `double` не коштує **нічого**: компілятор бачить структуру з одного поля й генерує точнісінько той самий код, що й для голого `double`. Безпека тут безкоштовна в машинному сенсі.

> 🔧 **Навіщо це.** Класичні катастрофи з переплутаними одиницями — не байка. Марсіанський орбітальний апарат Mars Climate Orbiter NASA 1999 року втратили саме через це: один модуль (Lockheed Martin) видавав імпульс тяги у фунт-сила·секундах, а навігаційний код очікував ньютон·секунди — рівно вчетверо (1 фунт-сила ≈ 4.45 Н) інше число. Величини були «голі», ніщо не стерегло сумісності, і апарат зайшов у атмосферу Марса надто низько. Це підтверджений факт (звіт комісії NASA). Новотип — рівно той запобіжник: якби імпульс мав тип `NewtonSeconds`, а не `double`, підставити `PoundForceSeconds` було б помилкою збірки. У прошивці дрона та сама логіка рятує від «висота в футах, а автопілот думає, що в метрах».

### Потрібні оператори

Гола обгортка вміє лише зберігати число. Але з величинами треба щось робити: порівнювати, додавати, віднімати. Оператори доводиться дописувати — і саме тут новотип у C++ показує свою ціну (у Rust чи Haskell частину цього виводять автоматично). Розберемо на `Meters`, де арифметика має ясний фізичний сенс:

```cpp
class Meters {
    double m_;
public:
    explicit constexpr Meters(double m) : m_(m) {}
    constexpr double value() const { return m_; }

    // порівняння: метр із метром — коректно
    friend constexpr bool operator<(Meters a, Meters b) { return a.m_ < b.m_; }
    friend constexpr bool operator==(Meters a, Meters b) { return a.m_ == b.m_; }

    // додавання/віднімання: метр + метр = метр (розмірність зберігається)
    friend constexpr Meters operator+(Meters a, Meters b) { return Meters{a.m_ + b.m_}; }
    friend constexpr Meters operator-(Meters a, Meters b) { return Meters{a.m_ - b.m_}; }

    // множення на безрозмірне число: 3 · метр = метр (масштаб)
    friend constexpr Meters operator*(Meters a, double k) { return Meters{a.m_ * k}; }
    friend constexpr Meters operator*(double k, Meters a) { return Meters{a.m_ * k}; }
};
```

Тут захована глибша думка, ніж «додаймо оператори для зручності». **Не кожна арифметична операція над величиною має фізичний сенс, і тип може це відображати.** `Meters + Meters` — метри (додати дві довжини природно). `Meters * double` — метри (масштабувати довжину числом природно). А от `Meters * Meters` — це вже **квадратні метри**, площа, інша розмірність, і навмисне **не** визначати цей оператор — правильний хід: він змусить задуматися, що результат — не довжина. Так само `Meters + double` не визначено — не можна додати голе число до довжини, бо число невідомо в яких одиницях. Тип не просто носить дані — він **кодує правила комбінування**, і компілятор стежить за їх дотриманням. У C++20 частину цієї писанини знімає `operator<=>` (космічний корабель), що з одного рядка генерує всі порівняння:

```cpp
#include <compare>
// в C++20 замість чотирьох операторів порівняння — один:
friend constexpr auto operator<=>(Meters a, Meters b) = default;
friend constexpr bool operator==(Meters a, Meters b) = default;
```

### Перетворення одиниць

Окрема користь від типів-величин — **безпечне перетворення одиниць**. Коли метри й фути обидва «голі» `double`, їх плутають; коли кожне має свій тип, перетворення стає єдиною легальною дорогою між ними, і випадково змішати їх уже не вийде:

```cpp
class Feet {
    double ft_;
public:
    explicit constexpr Feet(double ft) : ft_(ft) {}
    constexpr double value() const { return ft_; }
};

// єдиний легальний міст між одиницями — явне перетворення
constexpr Meters toMeters(Feet f) { return Meters{ f.value() * 0.3048 }; }
constexpr Feet   toFeet(Meters m) { return Feet{   m.value() / 0.3048 }; }
```

Коефіцієнт `0.3048` — точне означення: 1 міжнародний фут = 0.3048 метра рівно (усталено з 1959 року міжнародною угодою про ярд і фунт). Тепер висота від барометра у футах і висота від GPS у метрах не змішаються мовчки — щоб їх зіставити, доведеться явно прогнати одну через `toMeters`, і ця точка перетворення видима в коді. Помилка «додав фути до метрів» стає неможливою: `Feet{100} + Meters{50}` не скомпілюється, бо оператор `+` для різних типів не визначено. Порівняй зі світом голих чисел, де `100 + 50` радо дасть безглузді `150` невідомо чого.

### Шаблон-помічник проти дублювання

Тут стає очевидною ціна новотипів у C++: `Latitude`, `Longitude`, `Meters`, `Seconds`, `Feet` — усі мають **однаковісінький** кістяк: одне поле `double`, explicit-конструктор, `value()`, той самий набір операторів. Копіювати це п'ять разів — саме той дубляж, з яким бореться дизайн. Ліки — **шаблон-база**, що містить спільну механіку раз, а конкретні типи лише називають себе:

```cpp
// Спільний кістяк новотипу над double. Параметр Tag робить кожен
// інстанс ОКРЕМИМ типом, навіть якщо всередині той самий double.
template <class Tag>
class Quantity {
    double v_;
public:
    explicit constexpr Quantity(double v) : v_(v) {}
    constexpr double value() const { return v_; }

    friend constexpr bool operator<(Quantity a, Quantity b) { return a.v_ < b.v_; }
    friend constexpr bool operator==(Quantity a, Quantity b) { return a.v_ == b.v_; }
    friend constexpr Quantity operator+(Quantity a, Quantity b) { return Quantity{a.v_ + b.v_}; }
    friend constexpr Quantity operator-(Quantity a, Quantity b) { return Quantity{a.v_ - b.v_}; }
    friend constexpr Quantity operator*(Quantity a, double k)   { return Quantity{a.v_ * k}; }
    friend constexpr Quantity operator*(double k, Quantity a)   { return Quantity{a.v_ * k}; }
};

// Кожна величина — окремий тег-структура (порожня, лише щоб розрізняти типи):
struct MetersTag; struct SecondsTag; struct LatitudeTag; struct LongitudeTag;

using Meters    = Quantity<MetersTag>;
using Seconds   = Quantity<SecondsTag>;
using Latitude  = Quantity<LatitudeTag>;
using Longitude = Quantity<LongitudeTag>;
```

Механізм, який робить це можливим, — **тег-параметр** (англ. *phantom type*, фантомний тип). `Tag` ніде всередині `Quantity` не використовується — це порожній маркер. Але для системи типів `Quantity<MetersTag>` і `Quantity<SecondsTag>` — **два цілком різні, несумісні типи**, бо різняться параметром шаблона. Тег ніколи не існує в пам'яті (структури `MetersTag`, `SecondsTag` навіть не потрібно означувати — досить оголосити), він живе виключно на рівні типів під час компіляції. Один шаблон дає скільки завгодно взаємонесумісних величин без жодного повтореного рядка:

```cpp
Meters  h  = Meters{120.0};
Seconds t  = Seconds{3.5};

auto h2 = h + Meters{30.0};     // ок: метр + метр = метр
auto bad = h + t;               // ПОМИЛКА: Quantity<MetersTag> + Quantity<SecondsTag>
                                // не існує — фантомні теги різні
double speed = h.value() / t.value();   // а швидкість — навмисне через голі числа,
                                        // бо результат м/с — вже інша розмірність
```

Зверни увагу на останній рядок: **шаблон-помічник не позбавляє тебе рішень про розмірність**. `Meters / Seconds` дало б метри-на-секунду — нову величину, і якщо вона потрібна як тип, її треба завести окремо (`using MetersPerSecond = Quantity<MpsTag>;`) і написати відповідний оператор. Шаблон економить писанину на **однакових** величинах, але межі між **різними** розмірностями ти проводиш свідомо — і це радше плюс, бо кожен перехід між одиницями лишається видимим.

> 🔧 **Навіщо це.** Фантомні теги — це те, що робить обгортки практичними в реальному коді: без них кожен новотип — це десяток скопійованих рядків, і спокуса кинути й повернутися до голих `double` величезна. З одним `Quantity<Tag>` завести нову безпечну величину коштує один рядок `using`, і бар'єр «зробити правильно» падає нижче за бар'єр «зробити абияк». Дизайн виграє тоді, коли правильний шлях — найлегший.

### Складність і пастки: коли обгортка варта заходу

І тут — найважливіше, бо новотипи спокушають перегнути палицю. **Не все варте окремого типу.** Обгорнути кожне число — той самий надмір, що й перевіряти все підряд: код тоне в `.value()`, конструкторах і операторах, які нічому не запобігають. Чуття міри тут вирішує все.

**Обгортка виправдана, коли плутанина реальна й дорога:**
- Різні поняття **однакового примітивного типу**, які легко переплутати місцями, — широта/довгота, `userId`/`orderId`, ширина/висота. Тут новотип ловить переплутані аргументи на компіляції.
- Величини з **одиницями**, де змішування катастрофічне, — метри/фути, секунди/мілісекунди, ньютони/фунт-сили. Тут тип стереже розмірність.
- Значення, яким потрібна **перевірка на вході** (валідна широта в −90..90) — обгортка дає єдину точку, де цю перевірку робиш раз, і далі тип сам є доказом, що вона пройдена. Це те саме «розбирай, не перевіряй», доведене до конструктора.

**Обгортка — порожня церемонія, коли:**
- Значення живе **локально й недовго**, плутати нема з чим — лічильник циклу `for (int i …)` не треба перетворювати на `struct LoopIndex`. Це шум без вигоди.
- Тип **уже унікальний** і ні з чим не змішується в цьому контексті — не кожен `int` потребує іменника.
- Обгортка **просочує зайве** й піднімає зчеплення: якщо публічний тип кодує кожну внутрішню тонкість, клієнти починають залежати від неї, і змінити реалізацію стає важче. Тип на межі модуля має бути точним рівно як контракт — не точнішим.

Тест простий: **напиши подумки помилку, від якої обгортка захищає**. Можеш назвати конкретний баг — «переплутали широту з довготою», «додали фути до метрів», «поклали від'ємну довжину» — обгортка варта заходу. Не можеш («ну… раптом хтось… щось…») — це церемонія, і голий `double` чесніший. Той самий принцип міри, що й у [YAGNI](book:programming/dry-kiss-yagni): не будуй захист від плутанини, якої не буває.

Підсумок другої задачі рими з першою. Новотип, як і сума-тип, **бере знання з голови й кладе в тип**: «це широта, а не довгота», «це метри, а не фути», «це вже перевірена величина». Компілятор починає стерегти те, що інакше стерегла б дисципліна й коментарі, — а коментар бреше мовчки, тип не збреше ніколи. Уся ціна — кілька ідіом (explicit-конструктор, потрібні оператори, фантомний тег проти дублювання), які варто вивчити раз і носити в інструментарії далі.
