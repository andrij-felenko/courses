# ⚙️ Незмінні структури й структурний поділ на робочому C++

Заперечення «а копії ж дорогі» звучить розумно рівно доти, доки ти не поглянув, як влаштована **справжня** незмінна структура. Бо там ніхто не копіює весь масив. Копіюють жменьку вузлів — а решту **ділять** зі старою версією, фізично тим самим шматком пам'яті. Стара версія лишається цілою й правдивою, нова відрізняється від неї на кілька вузлів, і обидві живуть водночас. Цей фокус зветься **структурним поділом (англ. structural sharing)**, і весь цей розбір — про те, як він працює, скільки насправді коштує «зміна», де він граційний, а де ламається так, що доводиться підключати важку математику.

Ми не будемо теоретизувати. Ми напишемо **робочий C++**: незмінний список, незмінне збалансоване дерево-мапу з копіюванням лише вздовж шляху, керування часом життя через `std::shared_ptr` — і на цьому коді порахуємо вартість по кроках. Наприкінці порівняємо з простішим родичем, копіюванням-при-записі, і побачимо, чому це два різні звірі.

## Задача: «змінити» те, що змінювати не можна

Умова парадоксальна на позір. Ми хочемо структуру даних, яку **не можна змінити після народження** (бо саме це дає безпечний поділ, локальні міркування й свободу від гонок), — і водночас хочемо її **оновлювати**: додавати ключі, викидати, правити значення. Як оновити те, що незмінне?

Відповідь у зсуві поняття «оновити». Оновлення незмінної структури не міняє стару — воно **народжує нову версію**, а стара лишається доступною тією самою, якою була. Це і є **персистентність (англ. persistence, від лат. persistere — стояти на своєму, триматися)**: усі версії, старі й нові, живуть одночасно, і будь-яку можна прочитати будь-коли.

> 🔧 **Навіщо це.** Персистентність — не академічна забаганка. Undo/redo в редакторі — це стос старих версій документа. Гілки в git — це версії дерева файлів, що ділять спільну історію. Снапшот стану гри, з якого можна відкотитися. Багатопотоковий сервер, де кожен запит бачить незмінний знімок конфігурації, поки хтось у фоні готує наступний. Скрізь тут потрібне те саме: дешево зробити «майже таку саму, але з однією відмінністю» структуру — так, щоб стара лишилася цілою. Наївна повна копія на кожен крок робить усе це занадто дорогим, щоб узагалі братися.

Наївний спосіб очевидний і жахливий: щоб отримати нову версію, скопіюй усю стару, зміни в копії що треба. Для масиву на мільйон елементів кожне «додати один ключ» — мільйон копіювань. Тисяча оновлень — мільярд операцій і тисяча повних масивів у пам'яті. Це не оптимізовувана дрібниця, це принципова стіна: вартість однієї зміни росте з розміром **усієї** структури, хоча змінили ми крихту.

Уся суть далі — як зробити вартість зміни залежною не від розміру структури, а лише від розміру **зміненого**. Для списку це буде O(1) на додавання в голову. Для дерева-мапи — O(log n) на будь-яке оновлення. І при цьому стара версія лишиться незайманою.

## Ідея структурного поділу: не чіпай того, що не змінилося

Ключове спостереження банальне, аж дивно, що на ньому стоїть цілий розділ інформатики: **якщо новий об'єкт відрізняється від старого лише частиною, то решту не треба копіювати — на неї можна просто послатися**. Незмінність робить це посилання безпечним. Якби спільний шматок можна було змінити, поділ був би пасткою: правка через нову версію потекла б у стару. Але спільний шматок незмінний, тож ним можна ділитися скільки завгодно версій — жодна нікому не зіпсує значення.

Найчистіший приклад цієї ідеї — однозв'язний список, де зміна відбувається на **тому кінці, від якого росте вся решта**. Розберімо його першим, бо на ньому видно механізм у голому вигляді, без балансування й іншого шуму.

### Незмінний список: спільний хвіст

Однозв'язний список — це ланцюжок вузлів, кожен тримає значення й посилання на наступний. Уся хитрість у напрямку посилань: вузол знає свого **наступника**, але наступник не знає про нього. Тому багато різних голів можуть показувати на **той самий** хвіст — хвіст не підозрює, скільки вузлів на нього посилаються, і йому байдуже.

```cpp
#include <memory>

// Незмінний вузол списку. Обидва поля const — після народження вузол застиг.
template <typename T>
struct Node {
    const T                     value;
    const std::shared_ptr<Node> next;   // хвіст — спільний, може бути в кількох списках

    Node(T v, std::shared_ptr<Node> n)
        : value(std::move(v)), next(std::move(n)) {}
};

template <typename T>
using List = std::shared_ptr<Node<T>>;   // список — це просто вказівник на голову (або nullptr)

// "Додати в голову": один новий вузол перед спільним хвостом. Стара голова недоторкана.
template <typename T>
List<T> prepend(T v, List<T> tail) {
    return std::make_shared<Node<T>>(std::move(v), std::move(tail));
}
```

Дивись, що коштує додавання. `prepend` створює **рівно один** вузол — нову голову — і кладе в її поле `next` вказівник на стару голову. Старий список не змінився ані на байт: його вузли ті самі, посилання ті самі. Новий список — це «стара голова плюс один вузол спереду». Обидва правдиві водночас, і спільний хвіст фізично один.

```cpp
List<int> a = prepend(3, prepend(2, prepend(1, nullptr)));  // a = [3, 2, 1]
List<int> b = prepend(9, a);                                // b = [9, 3, 2, 1]
List<int> c = prepend(7, a);                                // c = [7, 3, 2, 1]

// a досі [3,2,1]. b і c ділять з a ВЕСЬ хвіст [3,2,1] — він у пам'яті один,
// на нього тепер посилаються троє (a-голова, b-другий вузол, c-другий вузол).
```

Три списки — `a`, `b`, `c` — і разом вони займають не дванадцять вузлів, а шість: три спільні хвостові плюс три різні голови (`a` ділить свою «голову» як хвіст для `b` і `c`). Ось воно, структурне ділення в чистому вигляді: додати елемент коштує **один вузол і O(1) часу**, незалежно від того, чи в хвості три елементи, чи три мільйони.

> 🔧 **Навіщо це.** Саме так усередині влаштовані незмінні стеки й черги в функційних мовах, і саме тому рекурсія з накопичувачем-списком там дешева: кожен рекурсивний виклик додає один вузол у голову, а не переписує ланцюг. У C++ той самий прийом — спосіб роздати багатьом потокам «майже однакові» конфігураційні ланцюжки без жодного копіювання спільної частини.

Але тут-таки видно й **межу** прийому — і вона повчальна. Дешеве лише те оновлення, що відбувається біля **голови** — того кінця, від якого напрямок посилань веде вглиб. Спробуй змінити елемент **усередині** чи в **хвості** — і поділ раптово перестає рятувати:

```cpp
// Замінити k-й елемент (рахуючи від голови, з 0). Мусимо перебудувати ВСЕ
// до k-го включно, бо кожен вузол перед зміненим тримає next, який тепер інший.
template <typename T>
List<T> setAt(List<T> lst, int k, T v) {
    if (!lst) return nullptr;                       // вихід за межі — тут просто край
    if (k == 0)
        return prepend(std::move(v), lst->next);    // новий вузол зі старим хвостом
    // інакше: новий вузол зі СТАРИМ значенням, але новим (перебудованим) хвостом
    return std::make_shared<Node<T>>(lst->value, setAt(lst->next, k - 1, std::move(v)));
}
```

Щоб замінити k-й вузол, довелося створити **k+1** нових вузлів — усі від голови до зміненого. Чому? Бо вузол номер k−1 тримає `next`, що вказував на старий вузол k; новий вузол k — інший об'єкт, отже вузол k−1 мусить показувати на нього, отже його теж треба створити заново, отже й k−2, і так до самої голови. Хвіст **після** зміненого вузла лишається спільним (його ніхто не чіпав), але вся дорога **до** нього копіюється.

Ось перший точний висновок про вартість, і він задає лейтмотив усього далі:

```
Незмінний список, «змінити» елемент за індексом k від голови:
  нових вузлів      = k + 1        (уся дорога від голови до зміненого)
  спільних вузлів   = решта хвоста (усе після зміненого — не копіюється)
  час               = O(k)

  додавання в голову — окремий випадок k = 0:  один вузол, O(1)
```

Список дешевий біля голови й дорогий у глибині, бо він **лінійний**: дорога до довільного елемента має довжину до n. Копіювати доводиться саме дорогу. Звідси проста, але важлива думка: **вартість персистентного оновлення — це довжина дороги від «входу» в структуру до зміненого місця**. У списку дорога лінійна, тож у гіршому разі копіюємо пів структури. Щоб зробити оновлення дешевим **скрізь**, а не лише біля голови, треба структура, де дорога до будь-якого елемента **коротка**. Дорога завдовжки log n замість n — це і є збалансоване дерево.

## Незмінне збалансоване дерево-мапа: копіювання вздовж шляху

Тепер головна частина. Ми хочемо незмінний асоціативний словник — мапу «ключ → значення» — де будь-яке оновлення (додати ключ, змінити, викинути) коштує O(log n), а не O(n), і стара версія лишається цілою. Побудуємо його на двійковому дереві пошуку, а прийом, що робить оновлення дешевим, зветься **копіюванням уздовж шляху (англ. path copying)**.

Ідея прямо випливає з висновку про список. У двійковому дереві пошуку дорога від кореня до будь-якого вузла має довжину, що дорівнює висоті дерева. Якщо дерево збалансоване, висота — близько log₂ n. Дорога коротка. А правило те саме, що й у списку: щоб «змінити» вузол у незмінному дереві, треба перебудувати **всі вузли на дорозі від кореня до нього** — і **лише** їх. Кожен вузол на дорозі тримає посилання на дитину, яка тепер інша, тож його треба створити заново з новим посиланням. Але дороги дві всього дві на кожному рівні, а решта — ліві чи праві піддерева, яких дорога не торкнулася, — лишаються спільними зі старим деревом.

Ось як це виглядає наочно:

Різниця зі списком лише в геометрії дороги. У списку дорога лінійна (до n вузлів), у збалансованому дереві — логарифмічна (до log n вузлів). Той самий механізм копіювання дороги дає в дереві дешеве оновлення **скрізь**, а не тільки біля одного кінця. Ось ключова таблиця, яку варто тримати перед очима:

### Робочий код: незмінна мапа з балансуванням за розміром

Тепер напишемо це по-справжньому. Просте двійкове дерево пошуку має ваду: якщо вставляти ключі по порядку, воно вироджується в список, і дорога знову стає лінійною — а тоді весь виграш зникає. Тому потрібне **балансування**, яке тримає висоту близько log n за будь-якого порядку вставок. Ми візьмемо **дерево, збалансоване за вагою (англ. weight-balanced tree)**: кожен вузол пам'ятає розмір свого піддерева, і якщо після вставки один бік стає надто важчим за інший, дерево локально повертається. Цей різновид зручний для незмінного світу, бо балансування виражається через ті самі повороти, що самі собою природно копіюють лише дорогу.

Спершу вузол і базові будівельні цеглинки:

```cpp
#include <memory>
#include <functional>

template <typename K, typename V>
struct TNode {
    const K                       key;
    const V                       val;
    const std::shared_ptr<TNode>  left;
    const std::shared_ptr<TNode>  right;
    const int                     size;   // кількість вузлів у цьому піддереві (з собою)

    TNode(K k, V v, std::shared_ptr<TNode> l, std::shared_ptr<TNode> r)
        : key(std::move(k)), val(std::move(v)),
          left(std::move(l)), right(std::move(r)),
          size(1 + sz(left) + sz(right)) {}

    // розмір піддерева, стійкий до nullptr (порожнє піддерево має розмір 0)
    static int sz(const std::shared_ptr<TNode>& t) { return t ? t->size : 0; }
};

template <typename K, typename V>
using Tree = std::shared_ptr<TNode<K, V>>;

// Фабрика вузла — коротший запис make_shared. Розмір рахується в конструкторі.
template <typename K, typename V>
Tree<K, V> mk(K k, V v, Tree<K, V> l, Tree<K, V> r) {
    return std::make_shared<TNode<K, V>>(std::move(k), std::move(v),
                                         std::move(l), std::move(r));
}
```

Зверни увагу на дрібницю, що визначає все: поля вузла — `const`, і серед них `left`, `right`, `size`. Вузол, раз народжений, застигає назавжди. Тому єдиний спосіб «змінити» дерево — побудувати **нові** вузли; старі лишаються, як були, і їх можна безпечно ділити між версіями. `size` теж `const`, бо він — властивість цього незмінного піддерева й ніколи не зміниться.

Тепер повороти — серце балансування. Поворот бере локальну ділянку з трьох вузлів і перевішує її, зберігаючи порядок ключів, але змінюючи, хто над ким. У незмінному світі поворот **не крутить на місці**, а будує кілька нових вузлів із наявних піддерев:

```cpp
// Лівий поворот навколо x: правий син y підіймається над x.
//        x                 y
//       / \               / \
//      a   y     ==>     x   c
//         / \           / \
//        b   c         a   b
// Будуємо ДВА нові вузли (x' і y'); піддерева a, b, c — беруться як є (спільні).
template <typename K, typename V>
Tree<K, V> rotateLeft(const Tree<K, V>& x) {
    const auto& y = x->right;
    auto x2 = mk(x->key, x->val, x->left, y->left);      // новий x з піддеревами a, b
    return   mk(y->key, y->val, x2,      y->right);      // новий y над x2 і c
}

// Правий поворот — дзеркально.
template <typename K, typename V>
Tree<K, V> rotateRight(const Tree<K, V>& y) {
    const auto& x = y->left;
    auto y2 = mk(y->key, y->val, x->right, y->right);    // новий y з піддеревами b, c
    return   mk(x->key, x->val, x->left,  y2);           // новий x над a і y2
}
```

Важливо вгледіти, що поворот **дешевий**: він створює лише два нові вузли, а всі три піддерева (`a`, `b`, `c`) переходять у нові вузли **посиланнями**, без копіювання. Балансування, отже, не додає до вартості оновлення нічого страшного — лише кілька зайвих вузлів на дорозі.

Далі — функція, що після вставки перевіряє локальний баланс і, якщо один бік переважив, лагодить його поворотами. Правило дерева за вагою: піддерево не повинно бути важчим за брата більш ніж у ~3 рази (класичний коефіцієнт для weight-balanced trees). Порогів не мусиш пам'ятати напам'ять — важлива логіка: занадто важкий бік опускаємо поворотом, а якщо він ще й «зігнутий» усередину, спершу випрямляємо його внутрішнім поворотом (той самий випадок «зиґзаґу», що й у AVL-дерева):

```cpp
static const int RATIO = 3;   // допустима перевага одного боку над братом

template <typename K, typename V>
Tree<K, V> balance(const Tree<K, V>& t) {
    int ls = TNode<K, V>::sz(t->left);
    int rs = TNode<K, V>::sz(t->right);

    if (rs > RATIO * ls + 1) {                  // правий бік надто важкий
        const auto& r = t->right;
        if (TNode<K, V>::sz(r->left) > TNode<K, V>::sz(r->right))
            // зиґзаґ: правий син «нахилений» вліво — спершу випрямити його
            return rotateLeft(mk(t->key, t->val, t->left, rotateRight(r)));
        return rotateLeft(t);                   // прямий випадок — один поворот
    }
    if (ls > RATIO * rs + 1) {                  // лівий бік надто важкий — дзеркально
        const auto& l = t->left;
        if (TNode<K, V>::sz(l->right) > TNode<K, V>::sz(l->left))
            return rotateRight(mk(t->key, t->val, rotateLeft(l), t->right));
        return rotateRight(t);
    }
    return t;                                    // баланс у нормі — вузол лишається як є
}
```

І, нарешті, сама вставка — та, заради якої все й затівалося. Вона рекурсивно спускається до місця ключа, будуючи нову дорогу, а піддерева, у які не звертала, чіпляє **посиланнями** зі старого дерева:

```cpp
// Вставити (чи оновити) ключ. Повертає НОВИЙ корінь; старе дерево ціле.
template <typename K, typename V>
Tree<K, V> insert(const Tree<K, V>& t, K k, V v) {
    if (!t)                                      // дійшли до порожнього місця — новий лист
        return mk(std::move(k), std::move(v), Tree<K, V>{}, Tree<K, V>{});

    if (k < t->key)                              // ключ ліворуч: перебудовуємо лівий бік,
        return balance(mk(t->key, t->val,        //   ПРАВИЙ беремо як є (спільний!)
                          insert(t->left, std::move(k), std::move(v)),
                          t->right));
    if (t->key < k)                              // ключ праворуч: дзеркально
        return balance(mk(t->key, t->val,
                          t->left,
                          insert(t->right, std::move(k), std::move(v))));

    // ключ той самий — оновлюємо значення (новий вузол із тими самими дітьми)
    return mk(std::move(k), std::move(v), t->left, t->right);
}
```

Прочитай тіло `insert` очима, тримаючи в голові рядок «ПРАВИЙ беремо як є». Коли ключ менший за поточний, ми йдемо ліворуч і будуємо новий вузол, у якого **лівий** нащадок — результат рекурсивного вставляння (нова дорога далі вниз), а **правий** — той самий `t->right`, що й був. Праве піддерево не скопійоване, воно **спільне** зі старим деревом. І так на кожному рівні: один бік — нова дорога, другий бік — спільне посилання. Дійшовши до дна, ми створили рівно стільки нових вузлів, скільки рівнів пройшли, тобто висоту дерева, тобто O(log n). Усе інше — спільне.

Пошук у цьому дереві звичайнісінький і нічого не будує — він лише читає, а читати незмінне дерево можна з будь-якої версії й з будь-якого потоку без замків:

```cpp
template <typename K, typename V>
const V* find(const Tree<K, V>& t, const K& k) {
    const TNode<K, V>* cur = t.get();
    while (cur) {
        if      (k < cur->key) cur = cur->left.get();
        else if (cur->key < k) cur = cur->right.get();
        else                   return &cur->val;      // знайшли
    }
    return nullptr;                                    // немає такого ключа
}
```

Тепер зберемо все докупи й побачимо персистентність наживо:

```cpp
Tree<int, const char*> v0;                       // порожня мапа (версія 0)
auto v1 = insert(v0, 5, "five");
auto v2 = insert(v1, 3, "three");
auto v3 = insert(v2, 8, "eight");
auto v4 = insert(v3, 5, "FIVE-updated");         // оновили значення ключа 5

// v3 і v4 — РІЗНІ мапи, обидві живі:
*find(v3, 5);   // "five"           — стара версія недоторкана
*find(v4, 5);   // "FIVE-updated"   — нова версія з оновленим ключем
*find(v3, 3);   // "three"          — цей вузол ФІЗИЧНО спільний між v3 і v4
```

`v4` відрізняється від `v3` лише дорогою до ключа 5 — це кілька нових вузлів. Вузол ключа 3 (і його піддерево) у `v3` і `v4` — той самий шматок пам'яті. П'ять версій мапи коштують не п'ять повних мап, а одну мапу плюс кілька коротких доріг.

### Скільки це коштує, по кроках

Порахуймо вартість одного `insert` явно, бо саме в цьому підрахунку — уся суть відповіді на «а копії ж дорогі».

**Умова.** Збалансована мапа на n = 1 000 000 ключів. Вставляємо один новий ключ. Скільки вузлів створимо й скільки часу витратимо, проти наївної повної копії?

```
Висота збалансованого дерева:
  h ≈ log₂(n) = log₂(1 000 000) ≈ 20

Нових вузлів за path copying:
  дорога від кореня до місця ключа   = h        ≈ 20 вузлів
  + кілька вузлів на балансувальні повороти (сталий доважок)
  ─────────────────────────────────────────────────────────
  разом                              ≈ 20…25 нових вузлів

Спільних (не скопійованих) вузлів:
  усе, крім дороги                   ≈ 1 000 000 − 20 ≈ 999 980

Час:
  один прохід згори вниз по дорозі   = O(h) = O(log n) ≈ 20 кроків
```

А тепер наївна повна копія тієї самої вставки:

```
Наївно: скопіювати всю стару мапу, вставити ключ у копію
  нових вузлів  = n = 1 000 000
  час           = O(n) = 1 000 000 кроків
```

Різниця — **20 проти мільйона**. Не «трохи швидше» — на п'ять порядків. Причому виграш росте з розміром: що більша мапа, то дужче path copying випереджає копію, бо його вартість — log n, а копії — n. Оце й є перетворення «дорогої копії» на «дешевий поділ»: ми платимо не за розмір структури, а за логарифм від нього.

**Тепер про амортизацію, і тут ховається тонкість, яку легко проґавити.** Слово «амортизована» вартість означає усереднену по послідовності операцій — окрема операція може бути дорожча, але в середньому по багатьох виходить дешево. Для нашого дерева питання таке: балансувальні повороти інколи спрацьовують, інколи ні; чи не назбирується десь дорога серія поворотів, що псує середнє?

Відповідь для дерева за вагою заспокійлива: **ні, і навіть у гіршому окремому випадку**. Вставка робить один прохід по дорозі завдовжки O(log n), а повороти на кожному рівні — сталу роботу; сума лишається O(log n) **у гіршому разі**, не лише в середньому. Тут амортизація навіть не потрібна: кожне окреме оновлення вже логарифмічне. Це робить weight-balanced дерево особливо приємним для незмінного C++ — жодних сюрпризів у хвостах затримки.

Але не всі незмінні структури такі поблажливі, і наступний блок — саме про ті, що ламаються.

## Де фокус ламається: коли амортизація зустрічає персистентність

Досі все складалося гладко. Настав час чесно показати, **де структурний поділ дає збій** — бо саме на цьому зламі народилася ціла теорія, і не знати про нього означає рано чи пізно вбудувати в код тиху міну.

Проблема виникає не з path copying як таким, а з **амортизованими** структурами під персистентністю. Розберімо на прикладі, який кожен програміст бачив: **черга з двох стеків**.

Класичний трюк — зобразити чергу FIFO двома стеками (списками): «передній» для витягання й «задній» для додавання. Додаєш — кладеш у задній. Витягаєш — береш із переднього; а коли передній спорожнів, **перевертаєш** увесь задній у передній одним махом. Перевертання дороге, O(n), але воно трапляється рідко: кожен елемент перевертають лише раз за своє життя, тож у **середньому** одна операція коштує O(1). Це класична амортизація, і в звичайному, змінному світі вона працює бездоганно.

```cpp
// Черга з двох незмінних списків. front — звідки беремо, back — куди кладемо.
template <typename T>
struct Queue {
    List<T> front;
    List<T> back;
};

template <typename T>
Queue<T> push(Queue<T> q, T v) {                 // додати — дешево, у back
    return { q.front, prepend(std::move(v), q.back) };
}
```

А тепер вставмо це в незмінний, персистентний контекст — і подивімось, як амортизація розсипається. Уяви чергу, у якої передній стек порожній, а задній має n елементів. Наступне витягання мусить перевернути задній — робота O(n). Позначмо чергу перед цим фатальним витяганням як `q`. І ось підступ **персистентності**: ми можемо викликати витягання з `q` **багато разів** — бо `q` незмінна й нікуди не зникла, кожен виклик бачить її в тому самому «зарядженому» стані.

```
q — черга з порожнім front і back на n елементів (одна фіксована версія).

pop(q)  →  перевертає back, робота O(n)
pop(q)  →  q ТА САМА, front досі порожній → знову перевертає, знову O(n)
pop(q)  →  знову O(n)
...   k разів   →   разом O(k · n)
```

Ось де ламається амортизація. Її бухгалтерія побудована на припущенні, що дорогу операцію **оплачено наперед** дешевими, і оплачено **один раз**: перевернули задній — і більше з цього стану дороге перевертання не повториться, бо стан **змінився**. Персистентність це припущення нищить: стара версія `q` **не змінюється**, тож із неї можна знову й знову зривати ту саму дорогу операцію, кожного разу з нуля. «Кредит», яким ми думали сплатити перевертання, кожен виклик намагається витратити **заново** — а він один. Амортизована оцінка O(1) **перетворюється на O(n) за операцію** в гіршому персистентному сценарії.

> 🔧 **Навіщо це.** Це не кабінетний казус. Якщо ти взяв «амортизовано швидку» незмінну структуру з чужої бібліотеки й почав тримати та повторно програвати її старі версії (стос скасувань, пошук із поверненням, спекулятивні гілки обчислення) — ти можеш несподівано впертися в квадратичну поведінку там, де документація обіцяла лінійну. Ознака небезпеки проста: структура **амортизована** (має рідкісні дорогі операції) **і** ти зберігаєш та повторно вживаєш її проміжні версії. Path-copying-дерево з попереднього блоку цим не хворіє — воно O(log n) **у гіршому разі**, там немає «відкладеного боргу», який можна змусити спрацювати двічі.

Хто це розв'язав і як — окрема добра історія. Систематичний спосіб робити зв'язані структури персистентними, зокрема прийом path copying і його вартість, уперше дали **Джеймс Дрісколл, Ніл Сарнак, Деніел Слітор і Роберт Тар'ян** у праці «Making Data Structures Persistent» — спершу на симпозіумі STOC у Берклі навесні 1986-го, потім повною статтею в Journal of Computer and System Sciences 1989 року; там-таки описано й «товсті вузли» (fat nodes) як альтернативу копіюванню дороги, і доведено логарифмічні межі для персистентних дерев пошуку. Це усталений факт, основа основ галузі.

А проблему саме **амортизації** під персистентністю — ту, що ми щойно бачили на черзі, — розв'язав **Кріс Окасакі** (спершу дисертація в Університеті Карнеґі-Меллона, CMU-CS-96-177, 1996; згодом класична книжка «Purely Functional Data Structures», Cambridge University Press, 1999). Його ключова ідея: **лінива обчислюваність із мемоізацією**. Дорога операція (те саме перевертання) не виконується одразу, а лишається відкладеною «обіцянкою»; коли її вперше змушують обчислитися, результат **запам'ятовується** в спільному вузлі. Тому повторний виклик із тієї самої версії не повторює роботу — він бере вже готовий, кешований результат. Кредит стає спільним для всіх версій, і його вже не можна витратити двічі. Окасакі акуратно переніс класичні методи амортизаційного аналізу (метод банкіра й метод фізика) на цей лінивий світ і показав, що з мемоізацією амортизовані межі знову тримаються навіть під персистентністю. У C++ лінивість не вбудована, тож цей прийом доводиться робити руками — відкладене обчислення з мемоізацією в спільному вузлі під `shared_ptr`; але сама наука про те, **чому** без мемоізації амортизація ламається, — та сама.

Підсумок цього блоку одним реченням: **path copying на збалансованому дереві дає гіршовипадкове O(log n) і персистентності не боїться; амортизовані структури дають дешевину лише доти, доки ти не почав повторно програвати їхні старі версії — і тоді рятує тільки лінива мемоізація.**

## Час життя в C++: чому без `shared_ptr` усе тече

У мовах зі збирачем сміття структурний поділ безкоштовний для програміста: вузол живе, доки на нього хоч хтось посилається, а коли останнє посилання зникає — збирач сам його прибирає. У C++ немає збирача, і саме тут поділ ставить хитре питання: **коли звільняти вузол, якщо він спільний між кількома версіями?**

Розглянь. Вузол ключа 3 у нашому прикладі належить водночас версіям `v3` і `v4`. Хто його власник? Обидві. Коли його вилучати? Тоді — і **лише** тоді — коли **зникнуть обидві** версії, тобто коли на вузол не лишиться жодного посилання. Якби ми володіли деревом через `unique_ptr` (єдиний власник) чи звичайний `new`/`delete`, ми б не змогли навіть виразити «цей вузол мають двоє»: `unique_ptr` вимагає рівно одного власника, а ручний `delete` мусив би знати, чи не тримає вузол ще хтось, — а він не знає.

Саме тому весь код вище тримає вузли через `std::shared_ptr` — розумний вказівник із **підрахунком посилань (англ. reference counting)**. Він зберігає лічильник: скільки вказівників зараз дивиться на об'єкт. Копіюєш `shared_ptr` — лічильник росте на 1; вказівник виходить із області видимості — падає на 1; дійшов до нуля — об'єкт негайно звільняється. Це рівно та семантика, якої вимагає поділ: вузол живе, поки на нього посилається хоч одна версія, і зникає, коли остання зникла.

```cpp
{
    Tree<int, const char*> v3 = /* ... дерево з ключами 3, 5, 8 ... */;
    auto v4 = insert(v3, 5, "updated");
    // вузол ключа 3: лічильник = 2 (на нього дивляться і v3, і v4)
    // корінь v3 і корінь v4 — різні вузли, лічильник кожного = 1

}   // виходимо з блоку: спершу зникає v4 → його унікальні вузли (дорога) звільняються;
    // лічильник вузла 3 падає з 2 до 1 (лишився v3). Потім зникає v3 →
    // лічильник вузла 3 падає до 0 → вузол звільняється. Нічого не протекло, нічого
    // не звільнено двічі. Порядок звільнення shared_ptr улагоджує сам.
```

Ось де захована **реальна ціна** незмінних структур у C++ — та сама, про яку в мовах зі збирачем ніхто не думає. По-перше, кожен вузол несе накладні витрати `shared_ptr`: окремий керувальний блок із двома лічильниками (сильних і слабких посилань), а сам блок теж треба десь узяти. По-друге, лічильник **атомарний**: `shared_ptr` розрахований на те, що вузол може ділитися між потоками, тож збільшення й зменшення лічильника — атомарні операції, а вони помітно дорожчі за звичайне додавання. Для незмінної структури, якою справді користуються кілька потоків, це виправдано (у тім і сенс — безпечно ділити). Але якщо структура живе в одному потоці, атомарний лічильник — плата ні за що.

> 🔧 **Навіщо це.** Тут — практичний важіль оптимізації, який варто знати. Якщо профіль показав, що атомарні лічильники `shared_ptr` з'їдають час, а структура **не** ходить між потоками, її можна перевести на неатомарний підрахунок посилань (власний, або через відповідні засоби бібліотек) — і зняти саме цю плату. Це та рідкісна ситуація, коли має сенс не хапатися за `shared_ptr` за звичкою. Але діяти так — лише **після заміру**, а не наперед: передчасно міняти безпечний атомарний лічильник на власний неатомарний, поки профіль мовчить, — саме той рід передчасної оптимізації, що приносить баги замість швидкості. Докладніше про цю пастку — у [передчасній оптимізації](book:programming/premature-optimization).

Є ще одна пастка з часом життя, тонша: **глибина руйнування**. Коли зникає остання версія довгого незмінного списку чи дерева, звільнення йде ланцюжком: звільнили голову — впав лічильник наступного вузла до нуля — звільнили його — впав лічильник наступного — і так рекурсивно. Для дерева завглибшки log n це нестрашно (рекурсія деструкторів завглибшки ~20). Але для незмінного **списку** на мільйон вузлів це рекурсивне звільнення може піти в стек завглибшки мільйон — і переповнити його. Це реальна вада, і лагодять її або ручним ітеративним звільненням довгих ланцюгів, або тим, що довгі лінійні структури взагалі не будують на однозв'язних вузлах. Дерева від цього застраховані самою логарифмічною глибиною — ще одна причина, чому для великих незмінних колекцій беруть дерева, а не списки.

## Простіший родич: копіювання-при-записі — і чому це не те саме

Часто плутають структурний поділ зі значно простішим прийомом — **копіюванням-при-записі (англ. copy-on-write, COW)**. Вони схожі зовні (обидва діляться спільним нутром заради економії), але це різні речі з різними гарантіями, і сплутати їх — джерело хиб, надто в багатопотоковому коді.

COW працює так. Об'єкт зовні поводиться як звичайний змінний, але всередині ділить спільні дані з іншими копіями через лічильник посилань. Поки об'єкт лише **читають**, копії ділять один буфер — дешево. Але тільки-но хтось хоче **писати**, COW перевіряє лічильник: якщо на дані дивиться більш ніж один власник, робиться приватна **повна копія**, і запис іде вже в неї. Далі цей власник псує лише свою копію, нікому не заважаючи.

```cpp
// COW-вектор (спрощено, суть — у гілці «хочу писати»):
template <typename T>
class CowVector {
    std::shared_ptr<std::vector<T>> data_;   // спільний буфер
public:
    const T& operator[](size_t i) const { return (*data_)[i]; }   // читання — дешеве, зі спільного

    void set(size_t i, T v) {                                     // запис — тут і ховається ціна
        if (data_.use_count() > 1)                // на буфер дивиться ще хтось?
            data_ = std::make_shared<std::vector<T>>(*data_);     // так → ПОВНА копія, O(n)
        (*data_)[i] = std::move(v);               // тепер буфер лише мій — пишу на місці
    }
};
```

Придивись до різниці, і вона засаднича. У структурному поділі «зміна» **ніколи не копіює все** — вона будує O(log n) нових вузлів і ділить решту; **обидві** версії, стара й нова, лишаються живі. У COW «зміна» при спільному володінні копіює **весь** буфер за O(n) — і після цього стара спільна версія та нова роз'їжджаються, але сам акт запису коштує повну копію. COW економить, лише **поки не пишуть**; перший же запис у спільний об'єкт коштує повну копію. Тому COW — це відкладена повна копія, а не дешеве оновлення: він виграє на сценарії «багато читань, зрідка запис», а на частих записах вироджується в ту саму наївну копію, від якої ми тікали.

І головна, найпідступніша відмінність — **поведінка між потоками**. Незмінна структура з path copying безпечна між потоками **за будовою**: ніхто нічого не пише, читати можна звідусіль без замків. COW **не** незмінний — він лише прикидається. Сам момент «перевірю лічильник, і якщо треба, скопіюю» — це читання-модифікація спільного стану, і без синхронізації два потоки можуть увійти в нього одночасно, обидва побачити лічильник > 1, обидва почати копіювати — і роздерти спільний буфер навпіл або звільнити його двічі. Тому COW у багатопотоковому світі мусить сам себе боронити замками саме в точці копіювання. Це прямо та [гонка даних](book:programming/atomicity-races), якої незмінність позбавляє безкоштовно, а COW затягує назад.

Звідси чистий підсумок різниці:

```
Структурний поділ (persistent):     COW (copy-on-write):
  зміна        = O(log n) нових        зміна        = O(n) при спільному володінні
                 вузлів, решта спільна                (повна приватна копія)
  версії       = усі живуть разом       версії       = після запису розходяться;
                 (справжня персистентність)             стара доступна лише доти, доки її
                                                        тримають ДО чужого запису
  потоки       = безпечно без замків     потоки       = точку копіювання треба
                 (нічого не пишеться)                   боронити замком (є запис!)
  природа      = незмінність             природа      = імітація незмінності заради
                                                        економії на читаннях
```

COW — добра оптимізація однопотокового коду з переважанням читань (класично так робили рядки й контейнери в старих бібліотеках). Але це **оптимізація**, а не заміна незмінності: він не дає ні гіршовипадкової дешевини оновлення, ні безпеки між потоками. Коли потрібні справжня персистентність і безстрашний поділ між потоками — потрібне path-copying-дерево, а не COW.

## Пастки, які варто тримати в голові

Зберемо докупи те, об що спотикаються на практиці, — кожне з механізмом, а не як список заповідей.

**Незбалансоване дерево вбиває весь виграш.** Уся дешевина path copying тримається на тому, що дорога від кореня до вузла — коротка, O(log n). Якщо взяти просте двійкове дерево без балансування й вставляти ключі по порядку, дерево виродиться в список, дорога стане O(n), і кожне «дешеве» оновлення почне копіювати пів структури — рівно те, від чого ми тікали. Тому незмінна мапа **мусить** бути на самобалансівному дереві (за вагою, червоно-чорне, AVL — байдуже яке, аби тримало висоту). Балансування тут не прикраса, а умова, без якої весь підхід не має сенсу.

**«Незмінний» вузол із мутабельним нутром — діряве відро.** Якщо поле вузла — вказівник на щось змінне, і хтось ту змінну річ таки міняє, поділ обертається катастрофою: правка через одну версію просочується в усі, що ділять цей вузол. Незмінність структури тримається на тому, що **все** досяжне з вузла теж незмінне до дна. Один змінний буфер, захований у спільному вузлі, — і всі гарантії поділу падають тихо й непомітно.

**Атомарний лічильник — плата, яку не завжди треба платити.** `shared_ptr` атомарний, бо розрахований на поділ між потоками. Для структури, що живе в одному потоці, ця атомарність — чистий доважок без користі. Знімати його варто, але лише за показами профілю, і свідомо — перехід на неатомарний підрахунок відбирає багатопотокову безпеку, тож робиться, тільки коли структура точно однопотокова.

**Рекурсивне звільнення довгого ланцюга переповнює стек.** Знищення останньої версії довгого незмінного списку йде рекурсією завглибшки в довжину списку. Мільйон вузлів — мільйон рівнів рекурсії деструкторів — переповнення стека. Дерева рятує логарифмічна глибина; довгі лінійні незмінні структури — ні, тож або звільняй їх ітеративно, або не будуй їх однозв'язними вузлами взагалі.

**Амортизована структура + збереження старих версій = прихована квадратичність.** Найтонша пастка, розібрана вище: якщо структура дешева лише амортизовано (має рідкісні дорогі операції) і ти тримаєш та повторно програєш її старі версії, ту саму дорогу операцію можна змусити спрацювати багато разів, і амортизація ламається. Рятує лінива мемоізація (Окасакі) або вибір структури з **гіршовипадковими**, а не амортизованими межами — як наше дерево за вагою.

Останнє, найпростіше й найважливіше. Незмінні структури з поділом — не «завжди краще». Вони блискучі там, де потрібні **персистентність** (кілька версій живуть разом), **безпечний поділ між потоками** й **дешеве оновлення великих спільних колекцій**. Там, де структура крихітна, живе в одному потоці й не ділиться ні з ким, увесь цей апарат `shared_ptr`, балансування й path copying — марна складність: звичайний змінний контейнер простіший і швидший. Прийом варто діставати тоді, коли його три сили справді потрібні; діставати його всюди за звичкою — та сама помилка надмірної інженерії, тільки з іншого боку.
