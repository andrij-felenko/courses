# Незмінність як прийом дизайну

<preknowlist>
- [Зчеплення і зв'язність](topic:programming/coupling-cohesion) — скільки один шматок коду знає про інший і чому зайве знання про сусіда робить систему крихкою; незмінність — це спосіб урвати найтісніший зв'язок через спільні дані.
- [Атомарність і гонки](topic:programming/atomicity-races) — що стається, коли два потоки правлять ті самі дані водночас; незмінність прибирає саму причину цих гонок.
- [Інтерфейс проти реалізації](topic:programming/interface-vs-implementation) — різниця між тим, що тип обіцяє зовні, і як він влаштований усередині; на цьому поділі стоїть уся інкапсуляція стану.
</preknowlist>

Уяви, що ти передав колезі аркуш із записаним на ньому телефоном. Мине година — і виявляється, що номер уже інший: колега, чи хтось третій, кому колега показав аркуш, узяв і **дописав** до нього цифру. Ти нічого не робив, а число в тебе змінилося. У програмах це діється щодня і зветься так само буденно — **спільний змінний стан**. Один об'єкт бачать кілька частин коду, і будь-яка з них може мовчки його переписати. Той, хто читає далі, отримує не те, що поклав.

Незмінність (англ. *immutability*, від лат. *immutabilis* — незмінний) — це радикально простий прийом проти цілого класу таких бід. Ідея в одному реченні: **об'єкт, створений один раз, більше ніколи не міняється**. Хочеш іншого значення — роби **новий** об'єкт, а старий лишай як був. Аркуш, якого фізично не можна виправити, не піднесе тобі сюрпризу.

Це звучить майже надто просто, щоб бути важливим прийомом дизайну. Але за цією простотою — усунення **першопричини** великої родини помилок, а не боротьба з їхніми наслідками. Розберімося, звідки та родина береться.

## Корінь зла — не зміна, а зміна *чужого* об'єкта

Сама по собі зміна змінної нікого не лякає. Лякає інше: коли на **той самий** об'єкт дивляться з двох місць одночасно. Це називають **аліасингом (англ. *aliasing*, від лат. *alias* — інакше, по-іншому)** — коли в однієї речі кілька імен. У C++ це щоденність: посилання, вказівник, елемент контейнера — усе це способи мати друге ім'я для того самого об'єкта.

Подивись, як тихо народжується баг:

```cpp
struct Config {
    int  timeout;
    bool verbose;
};

void tweak(Config& c) {   // приймає посилання — тобто АЛІАС чужого об'єкта
    c.timeout = 0;        // "тимчасово вимкну таймаут для свого тесту"
}

Config base{ 30, false };
Config& shortcut = base;  // ще один аліас на той самий base
tweak(shortcut);
// base.timeout уже 0, хоча "base" ми ніби не чіпали
```

Ніхто тут не написав помилкового рядка. `tweak` чесно робить, що просили. Проблема в тому, що `base` і `shortcut` — **одне й те саме**, і функція, змінивши одне ім'я, змінила всі. Коли таких імен три, а функцій між ними десяток, ти вже не тримаєш у голові, хто ще дивиться на цей об'єкт, — і зміна прилітає «здалеку», ніби сама собою. Цю дію на відстані англійською влучно звуть *spooky action at a distance*.

Тепер поглянь на це під кутом зчеплення. Два шматки коду, що правлять спільний об'єкт, зчеплені **найтіснішим** із можливих способів — вони ділять не інтерфейс, а внутрішні дані; будь-яка правка одного тече в другий без жодного повідомлення. Це той самий найгірший щабель, який у [зчепленні](topic:programming/coupling-cohesion) зветься зчепленням за спільними даними. Незмінність б'є саме сюди: **якщо об'єкт не можна змінити, то мати на нього десять аліасів безпечно** — жоден із них нікому не зіпсує значення. Аліасинг лишається, а біда з нього зникає. Ти прибрав не симптом (запізнілий баг), а причину (чужу руку на твоїх даних).

> 🔧 **Навіщо це.** У реальному коді 90% часу об'єкт живе так: створили, кілька разів прочитали, викинули. Змінюють його насправді рідко — а можливість змінити відкрита **завжди**, і саме через ту завжди-відкриту кватирку залітають найпідліші баги: значення, яке ти вважав сталим, десь поза очима переписали. Незмінність зачиняє кватирку там, де вона й не була потрібна, — і цілий клас «звідки тут узялося це число?» просто перестає існувати.

## Як зробити тип незмінним у C++

У мовах на кшталт Java достатньо не давати сеттерів і зробити поля `final`. У C++ інструмент прямо в мові — ключове слово `const`. Але тут криється тонкість, через яку новачки думають, що зрозуміли незмінність, а насправді взяли лише її половину.

`const` буває **двох дуже різних сортів**, і плутати їх — джерело хибної безпеки:

```cpp
Config a{ 30, false };
const Config b = a;   // (1) КОНКРЕТНИЙ об'єкт b незмінний
b.timeout = 5;        // помилка компіляції — і добре

void f(const Config& c);   // (2) ЦЯ ФУНКЦІЯ обіцяє не чіпати c...
                            //     ...але сам об'єкт може бути цілком змінним деінде
```

Різниця засаднича. Перший `const` — властивість **самого об'єкта**: він народився незмінним і таким помре. Другий — лише **обіцянка конкретної функції** нічого не псувати; той самий об'єкт хтось інший тримає без `const` і вільно міняє. Другий `const` — гарна гігієна, він каже читачеві «я тут лише дивлюся», але він **не робить тип незмінним**. Справжня незмінність — це коли **не існує жодного шляху** змінити об'єкт після народження, хоч би скільки імен на нього дивилося.

Щоб збудувати по-справжньому незмінний тип, є перевірений рецепт, і кожен його пункт закриває одну лазівку:

```cpp
class Money {
    long cents_;                 // поля приховані — ззовні не дотягтися
    const char* currency_;
public:
    Money(long c, const char* cur) : cents_(c), currency_(cur) {}

    // 1. Жодного методу, що міняє стан. Тільки читання.
    long        cents()    const { return cents_; }
    const char* currency() const { return currency_; }

    // 2. "Зміна" повертає НОВИЙ об'єкт, старий недоторканний.
    Money plus(const Money& o) const {
        return Money(cents_ + o.cents_, currency_);
    }
};

const Money price{ 1999, "UAH" };
Money withTax = price.plus(Money{ 400, "UAH" });  // price лишився 1999
```

Три речі роблять цей тип незмінним, і жодну не можна пропустити. **Поля приховані** — інакше будь-хто перепише їх повз усі правила. **Немає жодного методу, що міняє поле** — кожен метод-читач позначений `const`, і компілятор ловить будь-яку спробу присвоїти всередині. А головне — **операція «додати податок» не міняє `price`, а породжує окремий `withTax`**. Старе значення живе далі точно таким, яким його поклали. Це і є той аркуш, до якого фізично не дописати цифру.

Помітну пастку ховає пункт про приховані поля, коли поле саме є посиланням на щось змінне. Якщо всередині незмінного об'єкта лежить вказівник на буфер, а метод віддає цей вказівник назовні, — незмінність діряве відро: клієнт дістав пряму дорогу до нутрощів і псує їх повз усі `const`. Тому незмінний тип, що тримає всередині щось складене, мусить або віддавати **копію**, або віддавати теж лише під `const`. Цей самий клопіт із «поверненням нутрощів назовні» докладніше розібрано у [чистих функціях і побічних ефектах](topic:programming/pure-functions-side-effects) — незмінність і чистота ростуть з одного кореня: не чіпати нічого поза власним результатом.

## Що з цього виграє код

Один прийом, а віддача з різних боків. І це не збіг — усі вигоди течуть з **однієї** властивості: якщо значення не міняється, то воно **всюди одне й те саме, назавжди**. Пройдімо по головних.

**Про об'єкт можна міркувати локально.** Коли бачиш незмінний `Money price`, ти знаєш його значення до кінця функції, не читаючи ані рядка нижче: змінити його ніхто не може за визначенням. З мінливим об'єктом так не можна — доводиться очима простежити геть увесь код, що має до нього доступ, бо будь-де там могла сидіти прихована зміна. Незмінність перетворює «треба перечитати все довкола» на «досить прочитати оголошення».

**Ділитися стає безкоштовно.** Мінливий об'єкт, який бачать двоє, треба або боронити замком, або про всяк випадок **копіювати оборонно** — робити приватну копію, щоб чужа рука не дотяглася. Незмінний віддаєш просто так: скільки завгодно частин коду тримають на нього посилання, і жодна нікому не нашкодить. Копія не потрібна саме тому, що псувати нічого.

**Багатопотоковість — окремий тріумф.** Гонка даних (англ. *data race*) буває тільки тоді, коли один потік **пише**, а інший тим часом читає ту саму комірку. Приберемо запис — і читай хоч сотнею потоків без жодного замка: ніхто нічого не змінює, отже й ловити нема чого. Незмінні дані **безпечні між потоками за самою будовою**, без синхронізації. Це прямо прибирає причину, з якої виникають [гонки](topic:programming/atomicity-races), — не бореться з наслідком постфактум, а знімає передумову.

Саме на цій властивості тримається одне з найвідоміших рішень у мовах — **незмінний рядок**. У Java, C#, Python текстовий `String` не можна змінити на місці; будь-яка «зміна» дає новий рядок. Спершу здається марнотратством, та плата окуповується сторицею: незмінні рядки можна **вільно ділити** між потоками без замків, безпечно класти ключами в геш-таблицю (ключ не зміниться потай і не «загубиться» у своєму кошику), а однакові літерали — тримати в пам'яті **в одному екземплярі** (пул рядків, англ. *string interning*). Усе це можливе **лише** тому, що рядок незмінний: якби його можна було переписати з-під одного посилання, кожна з цих оптимізацій негайно перетворилася б на джерело хаосу.

![Зверху мінливий об'єкт: три аліаси-стрілки з різних функцій в одну комірку, дві з них позначені як запис — між ними знак зіткнення, підпис «баг: чужа зміна». Знизу незмінний об'єкт: ті самі три стрілки в комірку, усі позначені як читання, жодного зіткнення, підпис «безпечно ділити»](img/shared-mutable-vs-immutable.svg)

*Той самий об'єкт із трьома іменами. Поки хоч хтось пише, спільне володіння небезпечне; забери право писати — і скільки завгодно читачів співіснують мирно. Незмінність не прибирає аліаси, вона прибирає з них жало.*

## Заперечення, яке чуєш першим: а копії ж дорогі?

Тут кожен програміст спотикається однаково. «Стоп. Якщо будь-яка зміна робить новий об'єкт, то додав одне поле в масив на мільйон елементів — і скопіював увесь мільйон? Це ж божевільно повільно.» Заперечення слушне, і відповідь на нього — суть того, чому незмінність працює на практиці, а не лишається кабінетною красою.

Для маленьких значень — `Money`, точка, дата — заперечення просто не діє: скопіювати два поля дешевше, ніж думати про замки й аліаси. Тут копія — не ціна, а звільнення.

Для великих структур відповідь глибша й називається **структурним поділом (англ. *structural sharing*)**. Новий об'єкт **не копіює** старий — він **ділить** із ним усе, що не змінилося, і заводить окремо лише крихітну змінену частину. Найпростіший приклад — незмінний однозв'язний список. «Додати елемент на початок» не чіпає старий список ані на байт:

```cpp
struct Node {
    int         value;
    const Node* next;   // хвіст — спільний, той самий для старого й нового
};

// "prepend" не копіює хвіст — лише чіпляє нову голову перед ним
const Node* prepend(int v, const Node* tail) {
    return new Node{ v, tail };   // один новий вузол; решта — спільна
}

const Node* a = prepend(3, prepend(2, prepend(1, nullptr)));  // [3,2,1]
const Node* b = prepend(9, a);                                // [9,3,2,1]
// a досі [3,2,1] і ЖИВИЙ; b лише додав один вузол перед спільним хвостом a
```

`b` — це «`a` з дев'яткою спереду», але жодного елемента `a` не переписано й не скопійовано. Обидва списки правдиві водночас, а спільний хвіст фізично один. Ціна «зміни» — **один** новий вузол, а не весь список. Цей самий принцип масштабують деревами: справжні незмінні масиви й словники будують на збалансованих деревах, де зміна одного елемента створює лише вузли **вздовж шляху** до нього (порядку log n штук), а всі інші гілки лишаються спільними зі старою версією. Тому «незмінний словник на мільйон ключів» оновлює один ключ за десятки кроків, а не за мільйон копіювань.

Що ця техніка не бере голими руками, а що бере граційно, і чому за незмінні структури довелося платити ретельним математичним аналізом амортизованої вартості — окрема історія, і вона по-справжньому цікава: перший систематичний [розбір незмінних структур і структурного поділу](topic:programming/immutability/proj-persistent-structures.md) з робочим C++ показує, як «дорога копія» перетворюється на дешевий поділ і де межа цього фокуса.

Є й простіший родич цього прийому, який часто плутають зі справжньою незмінністю, — **копіювання-при-записі (англ. *copy-on-write*, COW)**. Тут об'єкт зовні поводиться як незмінний і ділиться спільним нутром, поки його лише читають; а тільки-но хтось справді хоче писати — тихо робиться приватна копія, і далі він псує вже свою. Це не незмінність, а її імітація заради економії, і в багатопотоковому світі вона підступна: момент «а тепер копіюю» сам треба стерегти замком, інакше два потоки роздеруть спільне нутро навпіл. Тому COW — оптимізація однопотокового коду, а не заміна незмінності.

## Де прийом ламається і чого він коштує

Аналогія з незмінним аркушем точна рівно доти, доки об'єктів у грі мало. Ламається вона там, де світ **за своєю природою** мінливий, і вдавати незмінність стає безглуздо.

**Стан, який мусить накопичуватися.** Лічильник відвідувань, банківський баланс, позиція гравця — це речі, чия сама суть у тому, щоб **змінюватися з часом**. Можна щоразу робити новий об'єкт-стан, але десь одна змінна таки мусить показувати на «поточний» — і ця змінна мінлива. Незмінність не скасовує зміну світу, вона лише **зганяє всю мінливість у вузьку, добре видну точку**, а решту коду лишає спокійним. Це не поразка прийому, а правильне його вживання: не «нічого не міняється ніде», а «міняється в одному місці, яке видно, а не розмазано по всій програмі».

**Тиск на пам'ять і збирача сміття.** Кожна «зміна» породжує об'єкт, а старі десь треба прибрати. У мовах зі збиранням сміття це наливає роботи збирачеві; у C++ ти сам відповідаєш за час життя, і незмінний список із прикладу вище **тече пам'яттю**, поки ним не керує щось на кшталт підрахунку посилань. Тому в C++ незмінні структури майже завжди їздять усередині розумного вказівника (`std::shared_ptr`), який рахує, скільки ще імен дивиться на вузол, і звільняє його, коли останнє зникло. Це та реальна ціна, якою C++ платить за поділ, що в мовах зі збирачем захований від очей.

**Гарячі, короткоживучі цикли.** Коли всередині щільного циклу треба тисячу разів підправити локальний буфер, який **нікуди не витікає** й ніхто інший не бачить, робити тисячу нових об'єктів — марнотратство без жодної вигоди: аліасити нічого, ділитися ні з ким. Тут доречний звичайний мінливий буфер, схований усередині функції. Це не зрада принципу — незмінність цінна там, де об'єкт **ділять**; де його не бачить ніхто, крім одного циклу, її захист захищає від порожнечі.

Звідси й практичне правило, до якого прийшла індустрія, — і сформулював його [Джошуа Блох у «Effective Java»](topic:programming/immutability/hist-immutable-string.md) навдивовижу категорично: **роби клас незмінним, якщо немає вагомої причини робити його мінливим**. Не «незмінність там, де зручно», а незмінність **за замовчуванням**, і мінливість — як свідомий виняток, який треба обґрунтувати. Причина такої різкості проста: незмінний тип неможливо вжити неправильно тим підступним способом, коли хтось потай переписав твоє значення, — а мінливий цю можливість тримає відчиненою завжди, і рано чи пізно нею скористаються не туди.

Незмінність не робить код швидшим і не додає йому можливостей — вона **забирає** можливість, ту саму, через яку заводиться цілий рід помилок «звідки взялося це значення». Прибираєш право мовчки переписати спільну річ — і разом із ним зникають гонки на цих даних, оборонні копії, замки заради читання й нічні пошуки того, хто ж зіпсував число. Ти платиш новими об'єктами й трохи — пам'яттю; отримуєш код, про який можна думати шматками, не тримаючи в голові всю решту. Для переважної більшості значень, що живуть у програмі, ця угода вигідна настільки, що незмінність варто ставити стандартом, а мінливість — доводити.
