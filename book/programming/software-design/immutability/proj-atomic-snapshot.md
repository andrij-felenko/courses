# ⚙️ Єдина мінлива комірка: змінний світ крізь незмінні знімки

Якщо все навколо незмінне, як програма взагалі рухається? Світ таки міняється — надходять запити, оновлюється маршрут, росте стан, — а незмінне значення за визначенням не можна підправити. Відповідь, яку варто побудувати власними руками, елегантна до нахабства: лишаємо **одну** мінливу річ — комірку-посилання, — а все, на що воно вказує, робимо незмінним. Мінливість не зникає, вона **стискається в одну точку**, яку видно й яку легко стерегти.

Тут ми зберемо цю точку по-справжньому — робочим кодом трьома мовами, — а тоді копнемо туди, де «очевидно правильний» механізм тихо кусає: у пастку **ABA**. Побачимо, що незмінність знімає одну її половину начисто, а другу не чіпає взагалі, бо та половина — насправді питання не про зміну значення, а про повторне використання пам'яті. І в кінці впізнаємо той самий прийом у ядрі Linux, де він доведений до промислового блиску під назвою RCU.

## Задача: таблицю читають мільйони разів, а правлять зрідка

Візьмімо конкретну річ — **таблицю маршрутів**: відображення «префікс мережі → наступний вузол». Її читають на **кожен пакет**: мільйони разів на секунду, з десятків ядер водночас. А правлять **зрідка**: інколи додається чи зникає маршрут. Це найпоширеніший у системах профіль навантаження — «майже самі читання, запис коли-не-коли», — і саме на ньому наш прийом сяє.

Чого ми хочемо, точно:
- **читання без жодного замка** — читач ніколи не має чекати, бо він на гарячому шляху;
- **цілісний знімок** — читач бачить таблицю як одне застигле ціле, а не набір ключів, частина яких уже оновлена, а частина ще ні;
- **запис, що не псує читача на півдорозі** — поки хтось читає, зміна не сміє поповзти під його руками.

Очевидні підходи спотикаються саме об ці вимоги. Замок на всю таблицю серіалізує читання: на гарячому шляху ядра штовхаються за один м'ютекс, і рідкісний запис карає всі читання. Дрібнозернисті замки чи «конкурентна мапа» знімають частину болю, але кожне читання все одно торкається синхронізації, а головне — читач втрачає **цілісний знімок**: між читанням двох ключів хтось устигає вписати третій, і читач бачить суміш двох версій.

Незмінний знімок розрубує вузол інакше. Сама таблиця — **незмінна мапа**. Єдине мінливе — **одна комірка-посилання** на «поточну версію». Читач робить один атомарний зчит цього посилання й далі читає застиглу мапу **без жодної синхронізації** — і це цілісний знімок, а не клаптик. Писар будує **нову** незмінну мапу (копія плюс зміна) і атомарно підмінює посилання на неї, повторюючи спробу, якщо хтось підмінив першим.

## Комірка й цикл: прочитай, скопіюй, підміни

Механізм тримається на одному апаратному примітиві — **порівняти-й-підмінити** (англ. *compare-and-swap*, CAS): «якщо в комірці досі те значення, що я бачив, — заміни його на нове; інакше скажи, що не вийшло, одним неподільним рухом». Він з'явився не вчора: [CAS](topic:programming/atomicity-races) — невіддільна частина архітектури IBM System/370 ще **від 1970 року**, і на ньому й досі стоїть уся безблокова синхронізація.

Читач бере поточне посилання — і має цілісний застиглий світ, з якого читає без замка. Писар готує нову незмінну версію й пробує підмінити посилання; якщо тим часом хтось устиг підмінити першим — писар повторює з новим знімком.

![Дві панелі. Ліворуч ЧИТАННЯ без замка: ЧИТАЧ бере знімок vN одним атомарним load, далі читає поля незмінного знімка без синхронізації. Праворуч ЗАПИС: цикл із трьох кроків — прочитати prev, збудувати нову незмінну версію next копією зі зміною, зробити CAS; при успіху опубліковано, при збігу червона петля-повтор угору до кроку 1](img/cas-cycle.svg)

*Читач і писар торкаються тієї самої комірки, але живуть у різних режимах: читання — один атомарний зчит і далі спокій, запис — короткий цикл, що повторюється лише коли хтось випередив. Читач ніколи не бачить напівзміни, бо нова версія — це окремий цілий об'єкт, який з'являється однією атомарною підміною, не торкаючись старого.*

Ось той самий прийом ідіоматично трьома мовами. Приклад однаковий — жива таблиця маршрутів, — але кожна мова тримає незмінний знімок і атомарну комірку по-своєму:

:::tabs
```java
import java.util.Map;
import java.util.HashMap;
import java.util.concurrent.atomic.AtomicReference;

public final class RoutingTable {
    // ЄДИНА мінлива комірка: посилання на НЕЗМІННИЙ знімок
    private final AtomicReference<Map<String, String>> ref =
        new AtomicReference<>(Map.of());          // Map.of() — незмінна порожня мапа

    // ЧИТАЧ: миттєвий незмінний знімок, без замка
    public String route(String prefix) {
        return ref.get().get(prefix);             // get() — один атомарний load, далі читаємо застиглу мапу
    }

    // ПИСАР: копіюй-зміни-CAS; при збігу — повтор із новим знімком
    public void put(String prefix, String nextHop) {
        Map<String, String> prev, next;
        do {
            prev = ref.get();                     // знімок, з якого будуємо
            var draft = new HashMap<>(prev);      // мутабельна копія-чернетка
            draft.put(prefix, nextHop);
            next = Map.copyOf(draft);             // заморозити → новий незмінний знімок
        } while (!ref.compareAndSet(prev, next)); // збіг (хтось устиг) → ще коло
    }
}
```
```cpp
#include <atomic>
#include <memory>
#include <string>
#include <unordered_map>

class RoutingTable {
    using Table = std::unordered_map<std::string, std::string>;
    // комірка: атомарний shared_ptr на НЕЗМІННИЙ знімок (const Table)
    std::atomic<std::shared_ptr<const Table>> ref{std::make_shared<const Table>()};

public:
    // ЧИТАЧ: shared_ptr тримає знімок живим, читаємо без замка
    std::string route(const std::string& prefix) const {
        std::shared_ptr<const Table> snap = ref.load();   // атомарний load + утримання знімка
        auto it = snap->find(prefix);
        return it == snap->end() ? std::string{} : it->second;
    }

    // ПИСАР: копіюй-зміни-CAS; при провалі prev оновлюється сам
    void put(const std::string& prefix, const std::string& nextHop) {
        std::shared_ptr<const Table> prev = ref.load();
        std::shared_ptr<const Table> next;
        do {
            auto draft = std::make_shared<Table>(*prev);  // мутабельна копія знімка
            (*draft)[prefix] = nextHop;
            next = std::move(draft);                       // shared_ptr<Table> → shared_ptr<const Table>
        } while (!ref.compare_exchange_weak(prev, next));  // збіг → prev = поточне, ще коло
    }
};
```
```rust
use arc_swap::ArcSwap;
use std::collections::HashMap;

pub struct RoutingTable {
    // комірка: ArcSwap над НЕЗМІННИМ знімком (Arc<HashMap> — ділимо, не міняємо)
    cell: ArcSwap<HashMap<String, String>>,
}

impl RoutingTable {
    pub fn new() -> Self {
        Self { cell: ArcSwap::from_pointee(HashMap::new()) }
    }

    // ЧИТАЧ: майже безкоштовний знімок, без замка
    pub fn route(&self, prefix: &str) -> Option<String> {
        self.cell.load().get(prefix).cloned()
    }

    // ПИСАР: копіюй-зміни-CAS-повтор — arc-swap уже містить цей цикл під назвою rcu()
    pub fn put(&self, prefix: &str, next_hop: &str) {
        self.cell.rcu(|cur| {
            let mut draft: HashMap<String, String> = cur.as_ref().clone();  // копія знімка
            draft.insert(prefix.to_string(), next_hop.to_string());
            draft                                                            // нова незмінна версія
        });
    }
}
```
:::

Три мови, той самий задум, різні руки. Java тримає незмінний знімок у `AtomicReference` і замикає незмінність на `Map.of`/`Map.copyOf` (незмінні мапи стандартної бібліотеки). C++ кладе `shared_ptr<const Table>` в `std::atomic` (спеціалізація з C++20): `const` у типі знімка — це і є заборона правити його з-під читача. Rust бере крейт `arc-swap` (автор — Міхал Ванер під ніком *vorner*), і його метод `rcu()` — це вже готовий цикл «прочитай-скопіюй-підміни-повтори»; назву він узяв прямо з ядрового прийому, до якого ми ще дійдемо. Спільне головне однакове скрізь: **читання — один атомарний зчит посилання, запис — новий цілий знімок замість правки на місці**.

## Чому цикл повторюється — і що насправді порівнює CAS

Придивімося до серця писаря — рядка `while (!compareAndSet(prev, next))`. Чому не просто «прочитав, змінив, записав»? Бо між «прочитав `prev`» і «записав `next`» інший потік міг устигнути підмінити комірку. Якби ми записали наосліп (звичайним присвоєнням), ми б **затерли** його зміну, навіть не помітивши. CAS цього не дасть: він підмінить посилання **тільки якщо** воно досі рівне тому `prev`, з якого ми будували. Якщо ні — CAS повертає «не вийшло», і ми йдемо на нове коло, узявши **свіжий** знімок.

Ось чому повтор безпечний, а не просто впертий: кожне коло перебудовує `next` із **найновішого** `prev`. Проведімо це двома писарями наживо:

```
Старт:      комірка → v0 = {}
Читач:      snap = v0;  route("10/8") → null            (читає застиглий v0, нічого не чекає)

Писар A:    prevA = v0;  nextA = {10/8 → eth1}
Писар B:    prevB = v0;  nextB = {10/8 → eth2}

A: CAS(v0 → nextA)  → УСПІХ, комірка → nextA
B: CAS(v0 → nextB)  → ЗБІГ (комірка вже nextA, не v0) → B бере свіжий знімок і повторює:
   prevB = nextA;  nextB = {10/8 → eth2}          (перебудова вже поверх зміни A)
B: CAS(nextA → nextB) → УСПІХ, комірка → nextB
```

Зверни увагу на суть: коли B повторює, він будує **поверх** знімка A, а не поверх старого `v0`. Тому зміна A **не губиться** — вона вже в тому знімку, з якого B почав друге коло. Наївний запис наосліп загубив би одну з двох; CAS-повтор зберігає обидві дії, просто впорядковуючи їх. Це і є те, заради чого потрібен цикл: не «спробувати ще раз те саме», а «перерахувати від свіжого стану».

І тепер — тонке місце, від якого залежить усе далі. CAS робить висновок: «якщо в комірці досі `prev` — відколи я його прочитав, **нічого не змінилося**, тож моя підміна коректна». Наскільки надійний цей висновок? Він тримається на прихованому припущенні: **те саме посилання означає той самий стан**. Здебільшого так і є. Але є сценарій, де посилання те саме, а світ тим часом сходив і повернувся, — і саме він зветься пасткою ABA.

## Пастка ABA: дві її подоби

Назва — просто послідовність, яку бачить обманутий потік: значення було **A**, стало **B**, знову стало **A**. Потік прочитав A на початку, побачив A перед CAS і зробив висновок «нічого не сталося» — а насправді між двома його поглядами світ устиг побувати в B і повернутися. CAS не бачить історії, лише поточне значення, тож він щиро вважає A на початку і A в кінці за «те саме, нічого не змінилось».

Питання, від якого все залежить: чи це для нас **шкідливо**? І тут виявляється, що під одним іменем «ABA» ховаються дві зовсім різні пастки, і незмінність поводиться з ними протилежно.

![Дві панелі. Ліворуч значеннєва ABA, знята незмінністю: комірка йде v1 → v2 → назад той самий незмінний v1; писар із prev рівним v1 робить CAS у v3 і має рацію, бо те саме посилання означає той самий зміст. Праворуч адресна ABA, не знята: сира комірка на адресу 0xA1 з об'єктом v1; v1 звільнено; аллокатор віддає 0xA1 під новий об'єкт v3; комірка знову вказує на 0xA1, але там уже v3; CAS збігається за адресою, хоча об'єкт інший, і тихо псує стан](img/aba-two-faces.svg)

*Ліва подоба питає «чи змінився зміст?», права — «чи це та сама річ, чи аллокатор віддав стару адресу під нову?». Незмінність відповідає лише на перше питання: вона гарантує, що зміст за живим посиланням не поповз. Керувати аллокатором вона не вміє, тож на праве питання не відповідає взагалі.*

**Значеннєва ABA — і чому незмінність знімає її начисто.** Уяви, що комірка пішла `v1 → v2 → v1`, причому останній `v1` — це **той самий незмінний об'єкт** (хтось відкотив зміну, повернувши те саме посилання). Писар прочитав `prev = v1`, збудував `next = f(v1)` і робить `CAS(v1 → next)`. CAS вдається — і це **правильно**. Бо `v1` незмінний: коли комірка знову дорівнює `v1`, її значення **буквально те саме**, до останнього поля, і `next = f(v1)` досі коректний наступник цього значення. Проміжна екскурсія в `v2` вже завершилась і не лишила слідів у значенні. Писар не цікавиться історією, лише поточним станом, а поточний стан **справді** `v1`. Псування нема.

Порівняй, як це рветься там, де ділянки **мінливі**. Класичний безблоковий стек ловить ABA боляче: потік читає вершину `A`, читає її мінливе поле `A.next = B`, планує `CAS(вершина: A → B)`. Тим часом хтось знімає `A`, знімає наступний вузол, і **повертає той самий вузол `A`** назад на вершину — але `A.next` уже перепризначено на щось інше. Наш потік бачить вершину знову `A`, робить `CAS(A → B)`, той вдається — і встромляє на вершину `B`, який давно знято й, можливо, звільнено. Псування. Корінь біди: план (`B`) обчислено з **мінливого нутра** `A`, яке зсунулося, поки адреса лишалась збіжною. У нашому ж патерні план `next = f(v1)` обчислено з **цілого незмінного** знімка, і ми ніде не розіменовуємо-й-перевикористовуємо мінливе поле. Тому значеннєва подоба ABA нас скалічити не може: незмінність робить «те саме посилання ⇒ той самий зміст» істинним, а висновок CAS — чесним.

**Адресна ABA — і чому незмінність її не чіпає.** Тепер підступніша половина. Незмінність каже про **зміст** об'єкта — що він не поповзе. Вона не каже **нічого** про те, чи не віддасть аллокатор стару адресу під новий об'єкт. А якщо ми порівнюємо не незмінні значення, а **сирі вказівники** з ручним звільненням — саме це й трапляється:

```cpp
// НЕБЕЗПЕЧНО: CAS сирих указівників + ручне звільнення знімка
std::atomic<Snapshot*> cell;              // сирий указівник, НЕ shared_ptr

Snapshot* prev = cell.load();             // писар бачить адресу 0xA1 (там v1)
Snapshot* next = build_from(prev);
//  … тим часом інший потік:  cell = &v2;  delete v1;   // 0xA1 звільнено
//     аллокатор віддає 0xA1 під новий Snapshot* v3;  cell = v3, і &v3 == 0xA1
cell.compare_exchange_strong(prev, next); // ЗБІГ за АДРЕСОЮ 0xA1, хоча там уже v3 → тихе псування
```

Тут `prev` і поточне значення комірки рівні **як числа-адреси** — обидва `0xA1`, — але за цією адресою вже інший об'єкт `v3`. CAS збігається й підміняє, спираючись на брехливу рівність. Незмінність `v1` тут ні до чого: `v1` давно нема, а незмінність нового `v3` не робить його тим самим станом, з якого будував писар. Рівність посилань перестала означати «та сама річ» — бо аллокатор перевикористав адресу.

Звідси разюча за простотою мораль. **У мові зі збирачем сміття над незмінними знімками ти по суті не зустрічаєш шкідливу ABA взагалі.** Дві гарантії складаються в замок: незмінність дає «те саме посилання ⇒ той самий зміст» (немає значеннєвої ABA), а [збирач сміття](topic:programming/garbage-collection) не дасть перевикористати адресу об'єкта, поки хоч один потік тримає на нього посилання (немає адресної ABA — твоя локальна змінна `prev` сама тримає старий знімок живим, тож його адреса не піде під новий об'єкт). Тому в Java-версії таблиці маршрутів `compareAndSet` просто правильний, і жодних хитрощів проти ABA не треба. Пастка повертається рівно тоді, коли ти **береш керування пам'яттю в свої руки**: сирі вказівники в C++ або навіть у Java — коли навмисне переробляєш вузли через власний пул, щоб не смітити.

## Як лагодять адресну ABA

Оскільки адресна ABA — це насправді питання **вивільнення пам'яті**, а не зміни значення, то й ліки лежать там само: зробити так, щоб адресу не перевикористали, поки її ще хтось бачить, **або** щоб CAS помічав повернення. Чотири усталені підходи, від найпростішого:

**Тримати старий об'єкт живим (підрахунок посилань).** Це те, що безкоштовно робить збирач сміття, а в C++ і Rust — розумний вказівник із лічильником. Поки читач тримає `shared_ptr` (чи `Arc`) на знімок, той не звільниться, а отже, його адреса не піде під новий об'єкт. Саме тому C++-версія вище безпечна: `std::atomic<std::shared_ptr>` утримує знімок, доки бодай один читач його не відпустить. Ціна цього прихована й реальна: атомарний `shared_ptr` типово **не безблоковий** — щоб атомарно піднести лічильник посилань під час зчиту, реалізація нерідко бере внутрішній замок. Тобто читання, яке в Java — один голий load, у C++ може коштувати дорожче, ніж здається. Крейт `arc-swap` і ядровий RCU існують саме тому, що обходять цей лічильник хитрішими схемами.

**Штамп версії (лічильник поколінь).** Якщо тримати живим не хочеш, познач кожну зміну номером. Java дає під це готовий `AtomicStampedReference` (автор — Даг Лі з експертною групою JSR-166, у стандарті від Java 5, 2004 року): він тримає **пару** «посилання + ціле-штамп», і CAS удається, лише коли не змінилися **обидва**:

```java
AtomicStampedReference<Route> cell = new AtomicStampedReference<>(initial, 0);

int[] stampHolder = new int[1];
Route prev = cell.get(stampHolder);                       // читаємо і посилання, і штамп
int stamp = stampHolder[0];
Route next = derive(prev);
// A → B → A лишить штамп на +2, тож CAS на (prev, старий штамп) чесно провалиться:
cell.compareAndSet(prev, next, stamp, stamp + 1);
```

Тепер послідовність `A → B → A` не обдурить нікого: посилання повернулося до `A`, але штамп уже `+2`, і CAS на `(A, старий штамп)` провалюється — саме як має бути. Той самий фокус в апаратурі — **тегований вказівник**: у молодші біти адреси (які однаково нульові через вирівнювання) пишуть лічильник змін, і подвійний CAS порівнює адресу разом із тегом. Це історичний спосіб, яким лагодили ABA ще на System/370 через подвійний CAS.

**Газардні вказівники й епохи.** Коли ти будуєш серйозну безблокову структуру з переробкою вузлів, лічильник на кожен зчит задорогий. Тоді читач **оголошує** адресу, яку саме читає (це його «газардний вказівник» — англ. *hazard pointer*, «вказівник-небезпека»), а той, хто хоче звільнити вузол, спершу дивиться, чи не оголосив його хтось; якщо оголосив — відкладає звільнення. Прийом описав Мейджед Майкл (стаття «Hazard Pointers: Safe Memory Reclamation for Lock-Free Objects», IEEE TPDS, 2004). Споріднений підхід — епохове вивільнення, де звільняють цілими «епохами», коли гарантовано жоден читач старої епохи вже не активний. Обидва — про [безблокові структури](topic:programming/lock-free-basics) і всі розв'язують ту саму адресну ABA: не дати перевикористати пам'ять, поки її ще хтось читає.

Спільна нитка крізь усі чотири: адресна ABA — це проблема **безпечного вивільнення**, і лагодять її механізмом вивільнення, а не «ще більшою незмінністю». Незмінність зробила свою половину роботи (знищила значеннєву ABA) і чесно передала другу половину тому, хто керує пам'яттю.

## Той самий прийом у ядрі: RCU

Усе, що ми зібрали, — не екзотика з академії. Це, з точністю до деталей, один із наріжних механізмів ядра Linux — **RCU** (англ. *read-copy-update*, «читай — копіюй — онови»). Його розробили Джон Слінґвайн і Пол Мак-Кенні ще в системі DYNIX/ptx компанії Sequent (патент США 5,442,758, 1995 рік); у ядро Linux його влив Діпанкар Сарма в жовтні 2002 року (версія 2.5.43). Це усталений, задокументований факт, а не легенда.

Відповідність нашому патерну майже дослівна. Ядрова структура під захистом RCU = наш незмінний знімок (читачі не сміють його правити). Комірка-вказівник на «поточну версію» = наш `AtomicReference`. Писар копіює структуру, змінює копію й **атомарно підміняє вказівник** на нову версію — це буквально наш «read-copy-update», рядок у рядок. Причому підміна робиться так, щоб інший потік побачив нову версію **цілком збудованою**, а не напівскладеною — це та сама [безпечна публікація](topic:programming/thread-safety), про яку кажуть, що незмінне «безпечне між потоками»: гарантія тримається на бар'єрі пам'яті всередині публікації, а не з повітря.

А ось де RCU додає те, чого нашій GC-версії дає збирач сміття задарма, — **вивільнення старого**. У ядрі збирача нема, тож стару версію не можна звільнити відразу: раптом якийсь читач досі ходить по ній. RCU вводить **період відкладення** (англ. *grace period*, «пільговий період»): стару версію звільняють лише коли гарантовано жоден **дочасний** читач її вже не тримає.

![Часова вісь. Писар публікує нову версію vN плюс один у певний момент, позначений вертикальним пунктиром. Два дочасні читачі r1 і r2 почалися раніше й тривають після публікації. Новий читач r3 стартує після публікації й одразу бачить нову версію. Період відкладення тягнеться від публікації до кінця останнього дочасного читача r2; лише тоді стару версію звільняють безпечно](img/rcu-grace-period.svg)

*Публікація нової версії миттєва, а от вивільнення старої відкладене: воно чекає, доки допрацюють усі читачі, що могли бачити стару версію. Новий читач r3 стартував уже після публікації, старої версії не торкався й на період відкладення не впливає. Це і є ручне безпечне вивільнення, яке в мові зі збирачем робиться за нас непомітно — те саме, що прибирає адресну ABA.*

Аналогія точна, тож чесно показати, де вона **ламається**:
- **Читання в RCU ще дешевше.** У класичному серверному складанні ядра вхід у read-критичну секцію — це навіть не атомарний зчит, а лише позначка для компілятора. Наш `AtomicReference.get()` — один атомарний load: дешево, але не задарма.
- **RCU впускає лише одного писаря нараз.** Писарі в RCU серіалізуються окремим замком, тож CAS-штурму з повторами там нема — на відміну від нашого оптимістичного циклу, де кілька писарів навперейми повторюють CAS. Ми виграли простоту (жодного замка на запис) ціною змарнованої роботи при збігу.
- **Період відкладення — ручний.** RCU мусить сам вирахувати, коли стару версію вже ніхто не бачить. Наш збирач сміття (чи лічильник у `shared_ptr`/`Arc`) робить це вивільнення невидимо — тому в Java-версії про grace period можна взагалі не думати.

Отже, наш простенький `AtomicReference` над незмінним знімком — це **RCU для бідних**, де всю складну частину (безпечне відкладене вивільнення) за нас тихо тягне середовище виконання.

## Вартість, чесно: дешеве читання, недешевий запис

Порахуймо ціну по кроках — вона різко несиметрична, і саме асиметрія пояснює, коли патерн доречний.

![Таблиця вартості: читач проти писаря за п'ятьма аспектами. Синхронізація: читач без замка, один атомарний load; писар один CAS плюс повтори при збігу. Час: читач O(1) wait-free; писар O(n) копія плюс CAS. Пам'ять: читач нуль; писар O(n) новий знімок, старий стає сміттям. Масштабування: читач лінійно з ядрами; писарі серіалізуються. Кого блокує: читач нікого; писар не блокує читачів, писарі конкурують між собою](img/cost-read-vs-write.svg)

*Читання практично безкоштовне й лінійно масштабується з ядрами, бо читачі не торкаються одне одного взагалі. Запис платить за повну копію знімка й за конкуренцію писарів між собою. Патерн вигідний рівно тоді, коли читань незрівнянно більше за записи.*

**Читання** — один атомарний зчит посилання (одиниці-десятки наносекунд) і далі звичайні читання застиглої мапи **без синхронізації**. Це `O(1)` роботи на синхронізацію, читання **wait-free** (не залежить від інших потоків узагалі), і воно **лінійно** масштабується з числом ядер, бо читачі не блокують ні одне одного, ні писарів. Це найкраще, на що можна сподіватися.

**Запис** дорожчий, і чесно назвати обидві статті. Перша — **копія**: щоб отримати новий знімок, ми копіюємо мапу цілком, `O(n)` часу й `O(n)` пам'яті, а старий знімок стає сміттям. Друга — **конкуренція**: при збігу CAS усе коло, включно з тією `O(n)`-копією, **викидається й переробляється** з нового знімка. Тобто під тиском кількох писарів вони фактично серіалізуються, ще й марнуючи роботу на невдалих колах. Запис тут **безблоковий** (система як ціле завжди просувається — хтось та переможе в CAS), але **не** wait-free: конкретному писареві може не таланити кілька кіл поспіль. На щастя, наш профіль — «зрідка запис», тож штурму писарів просто не буває, і ця ціна лишається теоретичною.

Найбільша реальна стаття — та сама `O(n)`-копія. І тут пряма ниточка до сусіднього прийому: **не обов'язково копіювати весь знімок**. Якщо замість звичайної мапи взяти [незмінну структуру зі структурним поділом](topic:programming/immutability/proj-persistent-structures.md), нова версія ділить зі старою все, крім зміненого шляху, і «копія» коштує `O(log n)`, а не `O(n)`. Тоді запис дешевшає на порядки, а вся решта механіки — комірка, CAS, повтор, знімок для читача — лишається без жодної зміни. Єдина мінлива комірка й персистентна структура — природна пара: перша дає атомарну підміну версій, друга робить кожну нову версію дешевою.

## Пастки й межі прийому

Кілька місць, де прийом мовчки ламається, якщо не глядіти:

- **Знімок мусить бути глибоко незмінним.** Читач ходить по ньому без замків саме тому, що ніхто його не міняє. Досить одному полю знімка лишитися мінливим — і писар, торкнувшись спільного нутра, повертає гонку, від якої ми тікали. Тут поверхневої незмінності мало: діряве дно знімка зводить нанівець усю безблоковість.
- **Не чіпай чернетку після публікації.** Копію-чернетку правлять, **поки** вона приватна; тільки-но її заморозили й підмінили нею комірку, вона стала спільним знімком — жодних дописів навздогін.
- **Запис-важкі чи величезні структури — це не для цього патерну.** Якщо записів стільки ж, скільки читань, або структура така велика, що навіть `O(log n)`-копія болить, — перевага «безкоштовного читання» не окупає вартості версій. Тоді доречніший інший інструмент: дрібнозернисті замки, поділені лічильники, мінливий буфер під захистом.
- **Вийшов із-під збирача — згадай про вивільнення.** Уся легкість щодо ABA трималася на GC чи `shared_ptr`. Тільки-но ти переходиш на сирі вказівники заради швидкості — адресна ABA й безпечне вивільнення знову твій клопіт, і доведеться діставати газардні вказівники, епохи чи штамп версії.

Зрештою, весь прийом — це одне рішення, доведене до коду: не розмазувати мінливість по всій програмі, а **зіпхнути її в одну названу комірку-посилання**, а все навколо лишити незмінними знімками. Тоді читання стає майже безкоштовним і безстрашним, запис — однією атомарною підміною цілого нового значення, а найтонша пастка на дорозі, ABA, чесно розпадається надвоє: значеннєву половину незмінність убиває начисто, а адресна виявляється не про зміну значення, а про повторне використання пам'яті — і лагодиться там, де їй і місце.
