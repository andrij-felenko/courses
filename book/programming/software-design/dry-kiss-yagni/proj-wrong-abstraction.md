# ⚙️ Рятування хибної абстракції: як повернути дублювання й нічого не зламати

Клубок на столі виглядає так:

```c
// Один "універсальний" відправник кадрів на п'ять прапорців.
// 32 можливі комбінації, з яких осмислені хіба чотири.
void send_frame(const uint8_t *payload, size_t len,
                bool with_crc, bool compress, bool big_endian);
```

Кожен, хто це кличе, мусить пам'ятати, які прапорці разом мають сенс, а які — нісенітниця. Тіло — вкладені `if` на кожну гілку. Додати новий формат означає ще один параметр і ще одне розгалуження. Читати страшно, чіпати ще страшніше: не знаєш, який виклик залежить від якої комбінації, тож будь-яка правда може мовчки зламати чужий кадр.

Мета цієї роботи — не «покращити» цю функцію ще одним прапорцем, а **розібрати** її на чесні окремі функції, повернувши по дорозі дублювання, і аж потім знайти справжню спільність, яку клубок ховав. Ключове слово — **не зламати**: наприкінці кожен старий виклик має слати байт-у-байт той самий кадр у той самий порт, що й до рефакторингу. Тому спершу поставимо запобіжник, який це доведе, а тоді підемо кроками, і на кожному кроці цей запобіжник лишатиметься зеленим.

## Спершу — сітка безпеки, без якої рефакторинг сліпий

Рефакторинг за визначенням **не змінює поведінки** — він змінює лише форму коду. Але «не змінює» треба чимось довести, інакше ти просто пересуваєш рядки з надією. Доказ дає **характеризувальний тест** (англ. *characterization test* — «тест, що фіксує наявну поведінку»): ти не описуєш, як воно **має** працювати за специфікацією, а фіксуєш, як воно працює **зараз**, разом з усіма дивацтвами, — і потім стежиш, щоб після кожного кроку відповідь не змінилась.

Щоб зафіксувати поведінку `send_frame`, треба відрізати її від справжнього заліза: справжній UART чи радіо ми в тесті не смикаємо. Зробимо це просто — виведемо саме **відправлення байтів** за тонкий гачок, який у продакшні пише в порт, а в тесті збирає байти в буфер. Це не частина рефакторингу, це його опора.

```c
// Гачок нижнього рівня: у продакшні шле в UART, у тесті — збирає в буфер.
// Уся функція send_frame врешті зводиться до послідовності таких викликів.
void hw_tx(const uint8_t *bytes, size_t n);
```

Тепер сам характеризувальний тест. Він проганяє всі осмислені комбінації прапорців через **поточну** `send_frame`, а `hw_tx` перенаправлений у буфер; байти, що вийшли, ми запам'ятовуємо як **еталон** (англ. *golden* — «золотий зразок»). Після кожного кроку рефакторингу той самий прогін має дати ті самі байти.

```c
// --- test_harness.c: збирає вихід у буфер замість заліза ---
static uint8_t  cap_buf[512];
static size_t   cap_len;

void hw_tx(const uint8_t *bytes, size_t n) {   // підміна на час тесту
    for (size_t i = 0; i < n && cap_len < sizeof cap_buf; i++)
        cap_buf[cap_len++] = bytes[i];
}

static void snapshot(const char *label,
                     const uint8_t *payload, size_t len,
                     bool crc, bool comp, bool be) {
    cap_len = 0;                                // чистимо буфер
    send_frame(payload, len, crc, comp, be);    // ← поточна реалізація
    // друкуємо label + hex(cap_buf[0..cap_len]) — це і є "золотий" відбиток
    print_hex(label, cap_buf, cap_len);
}

int main(void) {
    uint8_t msg[] = { 0x10, 0x20, 0x30 };
    snapshot("raw",  msg, sizeof msg, false, false, false);
    snapshot("crc",  msg, sizeof msg, true,  false, false);
    snapshot("comp", msg, sizeof msg, false, true,  false);
    snapshot("be",   msg, sizeof msg, true,  false, true);
    return 0;
}
```

Перший прогін дає, скажімо, отакі рядки (числа умовні, важливий сам факт фіксації):

```
raw  : AA 03 10 20 30 55
crc  : AA 03 10 20 30 3C 55
comp : AA 02 1A 07 55
be   : AA 03 30 20 10 8F 55
```

Ці чотири рядки — **контракт із самим собою**: «хай там що я роблю з кодом, ці чотири виклики зобов'язані давати саме це». Тепер у мене є очі. Кожен наступний крок я закінчую тим самим прогоном і звіряю рядок-у-рядок; розбіжність бодай в одному байті означає, що я щойно тихо змінив поведінку, і крок треба відкотити.

> 🔧 **Навіщо це.** У прошивці спокуса «порефакторити на око» особливо небезпечна: кадр, що поїхав у радіо трохи іншим, не впаде компілятором і не кине виняток — він просто мовчки розсинхронить приймач на тому кінці, а ти побачиш це аж на польових випробуваннях. Характеризувальний тест перетворює «здається, я нічого не зламав» на «я **бачу**, що всі чотири кадри ті самі». Без цієї сітки описаний нижче рефакторинг — гра наосліп; з нею — керована операція.

## Крок 0: подивитися ворогові в очі

Перш ніж розбирати, треба чесно розкрити, що всередині. Ось те тіло, яке ховалося за одним рядком сигнатури, — вкладені `if` на кожну комбінацію:

```c
// --- ДО: клубок. Один прохід, розгалуження на кожен прапорець. ---
void send_frame(const uint8_t *payload, size_t len,
                bool with_crc, bool compress, bool big_endian) {
    uint8_t body[256];
    size_t  n;

    // 1) тіло: стиснути чи скопіювати як є
    if (compress) {
        n = rle_compress(payload, len, body);       // стиснення RLE
    } else {
        n = len;
        memcpy(body, payload, len);
    }

    // 2) порядок байтів: за прапорцем — перевернути
    if (big_endian) {
        for (size_t i = 0; i < n / 2; i++) {
            uint8_t t = body[i];
            body[i] = body[n - 1 - i];
            body[n - 1 - i] = t;
        }
    }

    // 3) конверт + опційний CRC, усе намішано разом
    uint8_t frame[300];
    size_t  f = 0;
    frame[f++] = 0xAA;                 // старт
    frame[f++] = (uint8_t)n;           // довжина тіла
    memcpy(frame + f, body, n); f += n;
    if (with_crc) {
        frame[f++] = crc8(body, n);    // CRC саме тіла
    }
    frame[f++] = 0x55;                 // стоп

    hw_tx(frame, f);
}
```

Уже з цього видно два болючі місця. По-перше, **не всі 32 комбінації осмислені**: `compress` разом з `big_endian` перевертає *стиснений* потік — приймач такого не розпакує, це прихована нісенітниця, яку сигнатура дозволяє. По-друге, гілки **сплетені**: CRC рахується від `body`, яке вже могло бути стиснене й перевернуте, тож семантика «CRC чого саме?» залежить від інших прапорців. Саме така сплетеність робить клубок нечитним — і саме її ми зараз розчепимо.

## Крок 1: вбудувати тіло назад у виклики (inline)

Найперший рух назад — **інлайн**: узяти тіло абстрактної функції й вписати його прямо в кожне місце виклику, окремою копією під кожен випадок. Це навмисне **збільшує** дублювання. Так і треба: поки випадки зшиті в один клубок, ти не бачиш, де вони справді однакові, а де лише вдавали. Розкладені окремими копіями — вони показують правду.

Уяви, що зараз `send_frame` кличуть із чотирьох місць. Візьмемо перше — відправлення «сирого» кадру без нічого:

```c
// Було: send_frame(payload, len, false, false, false);
// Стало: те саме тіло, але з підставленими прапорцями й викинутими
//        гілками, яких цей випадок не бере.
{
    uint8_t body[256];
    size_t  n = len;
    memcpy(body, payload, len);        // compress=false → просто копія
    // big_endian=false → перевороту нема

    uint8_t frame[300];
    size_t  f = 0;
    frame[f++] = 0xAA;
    frame[f++] = (uint8_t)n;
    memcpy(frame + f, body, n); f += n;
    // with_crc=false → CRC нема
    frame[f++] = 0x55;
    hw_tx(frame, f);
}
```

Зверни увагу, що сталося: підставивши `false` у прапорці, я **викинув мертві гілки**. `if (compress)` з `compress == false` — то завжди `else`, тож лишається сама копія. `if (big_endian)` зникає цілком. `if (with_crc)` зникає. Те, що в клубку було розгалуженням, тут стало прямим лінійним кодом. Це і є сенс інлайну: кожен виклик **розкриває саме свою гілку** й показує її голою.

Так само розписуємо решту трьох викликів — кожен зі своїм набором підставлених прапорців і викинутих гілок. Після цього кроку `send_frame` ще існує (її поки ніхто не кличе, але хай стоїть), а всі чотири місця виклику стали самодостатніми копіями.

**Як звірити, що нічого не змінилось.** Тут характеризувальний тест іще не переписуємо — він і далі кличе `send_frame`. Замість цього прогоняємо **новий** тест, що кличе вже інлайнені блоки (обгорнуті в тимчасові функції `send_raw_inl`, `send_crc_inl`, …), і порівнюємо його вихід з тим самим еталоном:

```
raw  : AA 03 10 20 30 55        ← збіглося з еталоном
crc  : AA 03 10 20 30 3C 55     ← збіглося
comp : AA 02 1A 07 55           ← збіглося
be   : AA 03 30 20 10 8F 55     ← збіглося
```

Усі чотири рядки ті самі — інлайн поведінки не змінив. Це очікувано (ми ж лише підставили константи й прибрали недосяжні гілки), але **перевірити треба**, бо саме на інлайні легко зробити тиху помилку: підставити не той прапорець або забути викинути парну гілку.

> 🔧 **Навіщо це.** Головна пастка інлайну — **зайва свобода при копіюванні**. Коли переписуєш гілку руками, дуже легко «трохи причепурити»: тут поміняти порядок рядків, там винести змінну, і раптом семантика попливла. Правило кроку жорстке: інлайн — це **механічне** розкриття, жодних покращень. Спершу зроби копії буквально такими, як були в клубку (з поправкою лише на викинуті мертві гілки), звір з еталоном — і **лише потім**, окремим кроком, чепури. Змішаєш розкриття з причісуванням — втратиш здатність сказати, який саме рух зламав кадр.

## Крок 2: дати копіям чесні імена й розлучити випадки

Тепер чотири інлайнені блоки живуть у місцях викликів. Наступний рух — зібрати кожен клас у **свою названу функцію**. Не «універсальну» з прапорцями, а вузьку: одне ім'я — одна поведінка, яку видно з сигнатури без жодного булевого аргументу.

```c
// --- ПІСЛЯ інлайну й розлучення: три чесні функції, кожна робить одне. ---

// Сирий кадр: старт, довжина, тіло, стоп. І все.
void send_raw(const uint8_t *payload, size_t len) {
    uint8_t frame[300];
    size_t  f = 0;
    frame[f++] = 0xAA;
    frame[f++] = (uint8_t)len;
    memcpy(frame + f, payload, len); f += len;
    frame[f++] = 0x55;
    hw_tx(frame, f);
}

// Кадр із CRC тіла. Помітно, що це просто raw + один байт контролю.
void send_crc(const uint8_t *payload, size_t len) {
    uint8_t frame[300];
    size_t  f = 0;
    frame[f++] = 0xAA;
    frame[f++] = (uint8_t)len;
    memcpy(frame + f, payload, len); f += len;
    frame[f++] = crc8(payload, len);   // ← єдина відмінність від raw
    frame[f++] = 0x55;
    hw_tx(frame, f);
}

// Кадр зі стисненим тілом. Тіло інше, конверт той самий.
void send_compressed(const uint8_t *payload, size_t len) {
    uint8_t body[256];
    size_t  n = rle_compress(payload, len, body);
    uint8_t frame[300];
    size_t  f = 0;
    frame[f++] = 0xAA;
    frame[f++] = (uint8_t)n;
    memcpy(frame + f, body, n); f += n;
    frame[f++] = 0x55;
    hw_tx(frame, f);
}
```

Погляньмо, що стало видно, чого не було видно в клубку. Три функції лежать поруч, і **справжня спільність кинулася в очі сама**: усі три починають кадр однаково (`0xAA`, довжина), кладуть тіло й закривають `0x55`. Різняться вони лише тим, **яке тіло** кладуть і **чи є** байт CRC перед стопом. Ось воно — те, що клубок ховав за прапорцями: спільне тут не «функція відправлення взагалі», а вужче й конкретніше — **конверт кадру** (старт-довжина-…-стоп). А те, що здавалося спільним (сама «відправка»), насправді троїлося на три різні тіла.

А куди подівся `big_endian`? Ось перша нагорода за розлучення випадків: розписавши всі реальні виклики, ми побачили, що переворот байтів **насправді потрібен лише одному** формату — тому самому «be». Він не окремий поперечний прапорець на всі кадри, а **особливість одного конкретного формату**, який до того ж завжди йде з CRC. Тобто «5 прапорців = 32 комбінації» від початку були брехнею: реальних форматів чотири, і кожен — окрема проста функція. Комбінаторний вибух існував лише в сигнатурі, не в задачі.

**Як звірити.** Оце — головний момент усієї роботи, тож звіряємо прискіпливо. Тепер уже **переписуємо характеризувальний тест**: замість `send_frame(...)` з прапорцями він кличе нові функції за призначенням.

```c
// Тест тепер кличе чесні функції — але еталон той самий!
snapshot_raw ("raw",  msg, sizeof msg);   // → send_raw
snapshot_crc ("crc",  msg, sizeof msg);   // → send_crc
snapshot_comp("comp", msg, sizeof msg);   // → send_compressed
snapshot_be  ("be",   msg, sizeof msg);   // → send_be (нижче)
```

І вихід зобов'язаний лишитися тим самим еталоном до байта:

```
raw  : AA 03 10 20 30 55        ← той самий еталон
crc  : AA 03 10 20 30 3C 55     ← той самий
comp : AA 02 1A 07 55           ← той самий
be   : AA 03 30 20 10 8F 55     ← той самий
```

Збіглося — розлучення чесне. Якби бодай один байт поплив, це б означало, що при винесенні в іменовану функцію я щось непомітно змінив (найчастіше — від чого рахувати CRC чи довжину), і саме цей рядок показав би, який формат я зламав.

> 🔧 **Навіщо це.** Пастка цього кроку — **тиха зміна семантики на межі гілок**. У клубку CRC рахувався від `body` — а `body` могло бути вже стиснене чи перевернуте. Коли розписуєш `send_crc` окремо, страшенно легко за звичкою написати `crc8(payload, len)` там, де оригінал насправді рахував від *обробленого* тіла (чи навпаки). Компілятор цього не спіймає — обидва варіанти валідний C, обидва щось шлють. Спіймає лише еталон: неправильне джерело CRC дасть інший контрольний байт, і рядок `crc` розійдеться. Тому кожну функцію, яку виносиш, звіряй **окремим рядком** еталона, а не «загалом схоже».

## Крок 3: винести справжню спільність тонким хелпером, який кожна кличе явно

Дублювання ми повернули свідомо — і воно зробило свою роботу: показало, що справжнє спільне тут — конверт. Тепер його **можна** винести, бо тепер ми знаємо, що це **справжня** спільність (три реальні випадки її поділяють), а не вигадана. Але виносимо інакше, ніж робив клубок: не «функцією-начальником», що всередині вирішує прапорцями, хто вона сьогодні, а **тонким приватним хелпером-слугою**, який кожна функція кличе **явно** й сама лишається господарем свого кадру.

```c
// --- Справжня спільність: збирання конверта. Приватний хелпер (static). ---
// Кладе старт, довжину і тіло у frame; повертає, скільки байтів уже лежить.
// Стоп-байт (і опційний CRC перед ним) кожна функція дописує САМА —
// хелпер не знає й не вирішує, хто його кличе.
static size_t envelope_begin(uint8_t *frame,
                             const uint8_t *body, size_t n) {
    size_t f = 0;
    frame[f++] = 0xAA;                 // старт
    frame[f++] = (uint8_t)n;           // довжина тіла
    memcpy(frame + f, body, n); f += n;
    return f;                          // курсор: скільки вже записано
}

void send_raw(const uint8_t *payload, size_t len) {
    uint8_t frame[300];
    size_t  f = envelope_begin(frame, payload, len);
    frame[f++] = 0x55;                 // стоп — дописую сам
    hw_tx(frame, f);
}

void send_crc(const uint8_t *payload, size_t len) {
    uint8_t frame[300];
    size_t  f = envelope_begin(frame, payload, len);
    frame[f++] = crc8(payload, len);   // свій байт CRC — явно, тут
    frame[f++] = 0x55;
    hw_tx(frame, f);
}

void send_compressed(const uint8_t *payload, size_t len) {
    uint8_t body[256];
    size_t  n = rle_compress(payload, len, body);
    uint8_t frame[300];
    size_t  f = envelope_begin(frame, body, n);   // тіло вже стиснене
    frame[f++] = 0x55;
    hw_tx(frame, f);
}
```

Відчуй різницю в напрямку керування — вона і є вся суть протиотрути. У клубку керування йшло **згори вниз**: одна функція `send_frame` була начальником і всередині за прапорцями розписувала, ким їй сьогодні бути. Тут — **навпаки**: господар кадру — конкретна `send_crc`, а `envelope_begin` це маленький підлеглий, якого вона кличе, коли **їй** треба, і сама вирішує, що робити з результатом. Спільне винесене, але **жодна функція не втратила контролю над своїм кадром**: додати новий формат — це написати ще одну коротку функцію, що кличе той самий хелпер і дописує своє, а не встромити ще один `if` у чуже тіло.

Це і є та лінія поділу, яку клубок ховав: спільне — **механіка конверта** (як почати кадр), а не **політика формату** (який кадр слати). Клубок змішав механіку з політикою в одну функцію на прапорцях. Розлучивши їх, ми лишили механіку в спільному хелпері, а політику — по одній чесній функції на формат.

**Як звірити.** Утретє — той самий еталон, той самий прогін:

```
raw  : AA 03 10 20 30 55        ← еталон тримається
crc  : AA 03 10 20 30 3C 55     ← тримається
comp : AA 02 1A 07 55           ← тримається
be   : AA 03 30 20 10 8F 55     ← тримається
```

Винесення хелпера не змінило жодного байта — бо `envelope_begin` робить **буквально ті самі** три записи, що раніше стояли на початку кожної функції. Ми не додали й не прибрали жодної дії, лише дали спільним трьом рядкам одне ім'я. Саме тому еталон і не ворухнувся: правильне винесення спільного — це операція, **тотожна за поведінкою** за побудовою, і тест це підтверджує.

![Стан коду на кожному кроці: клубок на прапорцях розкривається інлайном у чотири окремі копії, копії згортаються в чесні названі функції, і врешті справжня спільність — конверт — виноситься тонким хелпером, який кожна функція кличе явно; праворуч на кожному кроці той самий золотий еталон стоїть незмінний](/book/programming/software-design/dry-kiss-yagni/img/refactor-ladder.svg)

*Драбина рефакторингу зверху вниз: від клубка на п'яти прапорцях — крізь інлайн у чотири голі копії — до чесних функцій — до тонкого спільного хелпера. Праворуч на кожному щаблі стоїть той самий золотий еталон незмінним: доказ, що форма коду мінялася, а поведінка — ні.*

## Куди подівся `big_endian`: п'ятий формат як окрема функція

Лишився той самий особливий формат, що вимагав перевернутого порядку байтів. Тепер, коли керування правильне, він теж стає **просто ще однією чесною функцією** — без жодного прапорця, що протікає в чужі кадри:

```c
// Формат "be": перевернуте тіло + CRC перевернутого тіла.
// Це НЕ поперечний прапорець, а окремий формат — тому окрема функція.
void send_be(const uint8_t *payload, size_t len) {
    uint8_t body[256];
    size_t  n = len;
    for (size_t i = 0; i < len; i++)     // копія з переворотом
        body[i] = payload[len - 1 - i];

    uint8_t frame[300];
    size_t  f = envelope_begin(frame, body, n);
    frame[f++] = crc8(body, n);          // CRC саме перевернутого тіла
    frame[f++] = 0x55;
    hw_tx(frame, f);
}
```

Тут явно видно те, що в клубку було приховане й небезпечне: CRC рахується **саме від перевернутого** тіла, бо приймач цього формату розвертає й перевіряє в тому ж порядку. У клубку це залежало від того, чи стоїть `big_endian` до чи після обчислення CRC у плетиві гілок, — і легко було поставити не так. Тут відповідь **вбита в код одного формату** й не залежить від жодного стороннього прапорця: `send_be` сама розвертає, сама рахує CRC від розвернутого, сама закриває. Ніхто інший на це не впливає, і ніхто інший цього не бачить.

І ось де ховалася найгидкіша з можливих комбінацій клубка: `compress=true` **разом** із `big_endian=true`. Сигнатура таке дозволяла — і хтось міг випадково викликати `send_frame(p, l, true, true, true)`, отримавши перевернутий *стиснений* потік, який жоден приймач не розпакує. Розклавши формати по функціях, ми зробили цю нісенітницю **несформульовною**: немає функції, яка стискає й перевертає одночасно, бо немає такого формату. Неможливий стан перестав бути можливим не перевіркою в рантаймі, а **самою формою коду** — його просто ніяк висловити.

## Правило трьох на цьому ж прикладі — коли виносити було зарано

Тепер, тримаючи в руках готовий розбір, легко побачити, **де саме** клубок звернув не туди, — і це рівно те місце, де порушили правило трьох.

Пригадаймо історію хвороби. Спершу було **два** схожі формати — сирий і з CRC. Дехто чесно зауважив «дублювання!» і виніс `send_frame(payload, len, with_crc)`. Ось перша помилка: **на другому випадку ще не видно, що спільне, а що випадкове.** Два формати, які збіглися конвертом, — це замало, щоб знати, чи конверт справді спільний, чи вони зійдуться й розійдуться. Правило трьох каже саме про це: на другому разі **зморщся, але скопіюй** — стерпи дублювання ще трохи. Якби так і зробили, `send_raw` і `send_crc` жили б окремими копіями, і наступні формати лягли б поруч без болю.

А сталося інакше: замість копії — прапорець. І далі кожен новий формат додавав ще прапорець, бо переписувати «майже готову» абстракцію завжди ліньки. Це і є та сама пастка, з якої ми щойно вибиралися, але видно, що **дешевше було в неї не потрапляти**. Порівняй ціну двох шляхів на цьому конкретному прикладі:

```
Шлях прапорців (що сталося):
  2 формати → винесли з прапорцем      (1 функція, 1 if)
  3 формати → +прапорець               (1 функція, вкладені if)
  4 формати → +прапорець               (32 комбінації, 4 осмислені)
  5 формат  → +прапорець               (клубок; розчепити = наскрізна операція)
  вартість розчеплення наприкінці:     ДОРОГО (треба еталон, 4 кроки, ризик)

Шлях правила трьох (як мало бути):
  1 формат  → просто пиши              (send_raw)
  2 формат  → зморщся, копіюй          (send_crc — копія, терпимо дубль)
  3 формат  → тепер видно спільне → виноси envelope_begin
  4-5       → нова коротка функція + той самий хелпер
  вартість:                            ЛОКАЛЬНО, дешево, без ризику
```

Різниця не в кількості коду — вона в **напрямку вартості**. На шляху прапорців кожен формат робив розчеплення **дорожчим** (більше викликів залежить від клубка). На шляху правила трьох кожен формат був **локальною** дією, що нічого чужого не чіпала. Саме тому «дублювання дешевше за хибну абстракцію»: ти порівнюєш дешеву локальну копію **зараз** із дорогою наскрізною операцією **потім** — тією самою, яку ми щойно виконували чотирма обережними кроками під наглядом еталона.

І поворотний момент правила трьох тут дуже конкретний: спільне (`envelope_begin`) стало **видно** аж на третьому форматі. Два формати давали лише здогад «мабуть, конверт спільний»; три формати (сирий, CRC, стиснений) показали конверт як **факт** — усі три його поділяють однаково, а різняться саме тілом і хвостом. Абстракція, виведена з трьох фактів, влучила; та сама абстракція, виведена з двох (той нещасний перший прапорець), була здогадом і породила клубок.

## Дві пастки, які чигають саме на цьому шляху назад

Обидві невидимі компілятору, обидві ловляться лише еталоном — і саме тому їх треба назвати явно.

**Пастка перша — тиха зміна семантики при розкладанні.** Найпідступніше місце — **джерело обчислення**, що в клубку залежало від інших прапорців. CRC від `payload` чи від обробленого `body`? Довжина в конверті — вихідна `len` чи довжина стисненого `n`? У клубку це визначалося порядком гілок; розкладаючи по функціях, ти щоразу приймаєш це рішення **заново**, і легко прийняти не те, що було. Обидва варіанти скомпілюються, обидва щось пошлють — різницю покаже **тільки** контрольний байт чи довжина в еталоні. Тому кожну винесену функцію звіряй **власним рядком** золотого зразка, а не «начебто те саме».

**Пастка друга — забутий виклик.** Розкладаючи один «універсальний» виклик на кілька конкретних, легко **загубити місце виклику**. Було `send_frame(p, l, flags)` у десятьох місцях коду; ти міняєш їх на `send_raw` / `send_crc` / … — і одне місце десь у рідко вживаній гілці лишаєш зі старим викликом, або замінюєш не тим форматом (поставив `send_raw` там, де мало бути `send_crc`). Компілятор мовчить, якщо стара `send_frame` ще існує; а якщо ти її вже прибрав — компілятор спіймає лише **невиклик**, але не **неправильний** виклик. Захист той самий: поки не звірив усі місця виклику, **не видаляй** стару `send_frame` — хай стоїть як мертва, доки характеризувальний тест не підтвердить, що кожен формат шлеться правильно; аж тоді прибирай її одним останнім рухом.

Обидві пастки мають спільний корінь: рефакторинг **виглядає** тривіальним («та я просто переставляю рядки»), і саме через цю оманливу легкість руки роблять його без сітки. Урок усього цього приклада — не в конкретних байтах кадру, а в тому, що **повернути дублювання безпечно можна лише під наглядом**: зафіксуй поведінку еталоном, іди дрібними кроками, після кожного звір рядок-у-рядок, і не викидай старе, поки нове не доведене. Тоді найшвидший шлях уперед — назад — виявляється не стрибком у прірву, а спуском драбиною, де кожен щабель під ногою перевірений.
