# ⚙️ Рефакторинг ієрархії колекцій: як розділити тип, щоб порушення LSP стало неможливим

Найкоротший спосіб зрозуміти принцип підстановки — не прочитати означення, а власноруч написати ієрархію, що його порушує, дати їй зламати чесний код, а тоді полагодити так, щоб зламати вже не вийшло **фізично**. Тут ми це й зробимо, на найзвичайнішому прикладі, який трапляється мало не в кожній кодовій базі: список, який хтось вирішив зробити незмінним, успадкувавши від звичайного списка й «вимкнувши» в нього додавання.

Розберемо все крок за кроком. Спершу зберемо ієрархію, де незмінний список — нащадок змінного, а його `add` кидає виняток; напишемо чесного клієнта під базовий список і подивимось, як він падає. Потім поставимо точний діагноз — не «на відчуття недобре», а за конкретним правилом контракту. Далі перебудуємо типи так, щоб порушення стало неможливим не завдяки дисципліні програміста, а завдяки **системі типів**: щоб компілятор сам не пустив небезпечну підстановку. І наприкінці закріпимо це тестами, які фіксують безпечну підстановку **до** й **після**, та назвемо типові пастки, у які тут вкочуються найчастіше.

Весь код — робочий, двома мовами вкладками: TypeScript і Python. Обидві живуть у загальному об'єктному домені, обидві дають той самий урок, але дають його по-різному — і саме ця різниця наприкінці виявиться повчальною: те, що в TypeScript ловить компілятор, у Python ловить лише перевірка типів осторонь, і це змінює, на що можна покластися.

## Крок 0: ієрархія, яка бреше

Почнемо з бажання, яке саме по собі цілком розумне. Є звичайний список — уміє і читати за індексом, і додавати в кінець. Комусь потрібен список, який після створення **не можна змінювати**: передати кудись і бути певним, що отримувач його не зіпсує. Незмінні колекції — корисна, шанована річ; проблема не в них, а в тому, **як** зараз потягнеться рука їх зробити.

А рука потягнеться до спадкування: «незмінний список — це ж різновид списка, хай успадкує звичайний, а `add` ми йому перевизначимо, щоб він обурювався». Ось ця ієрархія цілком:

:::tabs
```ts
class ArrayList<T> {
  protected items: T[] = [];

  get(i: number): T { return this.items[i]; }
  size(): number { return this.items.length; }
  add(x: T): void { this.items.push(x); }
}

// «Незмінний список — різновид списка?» — і тут закладено пастку:
class ImmutableList<T> extends ArrayList<T> {
  constructor(initial: T[]) {
    super();
    this.items = [...initial];        // наповнили раз, при створенні
  }
  add(_x: T): void {
    throw new Error("список незмінний: додавати не можна");
  }
}
```
```python
class ArrayList:
    def __init__(self):
        self._items = []

    def get(self, i):        return self._items[i]
    def size(self) -> int:   return len(self._items)
    def add(self, x) -> None:
        self._items.append(x)

# «Незмінний список — різновид списка?» — і тут закладено пастку:
class ImmutableList(ArrayList):
    def __init__(self, initial):
        super().__init__()
        self._items = list(initial)        # наповнили раз, при створенні

    def add(self, x) -> None:
        raise TypeError("список незмінний: додавати не можна")
```
:::

Код компілюється (у TypeScript) і запускається (у Python) без жодного зауваження. Метод `add` на місці, сигнатура та сама, тип-перевірка задоволена. `ImmutableList` — законний, з погляду обох систем типів, нащадок `ArrayList`: усе, що вміє база, формально вміє й він.

Це і є та тиша перед бідою. Компілятор дивиться на **форму** — які є методи, що приймають, що повертають — і форма бездоганна. Він не дивиться (і не вміє) на те, що всередині `add` замість роботи стоїть відмова. Розрив між «форма збіглася» і «поводиться правильно» тут не абстрактний — у нього зараз провалиться конкретний, ні в чому не винний код.

## Крок 1: чесний клієнт падає

Напишемо тепер код, який користується списком **чесно** — тобто спираючись рівно на те, що обіцяє `ArrayList`, і нічого не знаючи про існування якогось там незмінного різновиду. Хай це буде функція, що наповнює переданий їй список числами:

:::tabs
```ts
// Клієнт написаний під ArrayList і вірить його контракту:
// «дали список — у нього можна додавати».
function fill(list: ArrayList<number>, n: number): void {
  for (let i = 0; i < n; i++) {
    list.add(i);                    // контракт ArrayList це дозволяє
  }
}

const normal = new ArrayList<number>();
fill(normal, 3);                    // ок: [0, 1, 2]
console.log(normal.size());         // 3

const frozen = new ImmutableList<number>([10, 20]);
fill(frozen, 3);                    // ← ВИБУХ: Error на першому ж add
```
```python
# Клієнт написаний під ArrayList і вірить його контракту:
# «дали список — у нього можна додавати».
def fill(lst: "ArrayList", n: int) -> None:
    for i in range(n):
        lst.add(i)                  # контракт ArrayList це дозволяє

normal = ArrayList()
fill(normal, 3)                     # ок: [0, 1, 2]
print(normal.size())                # 3

frozen = ImmutableList([10, 20])
fill(frozen, 3)                     # ← ВИБУХ: TypeError на першому ж add
```
:::

Придивись, у чому фокус жорстокості цього падіння. Функція `fill` **правильна**. Вона не робить нічого сумнівного: бере тип `ArrayList`, у якого в контракті чорним по білому написано «`add` додає елемент», і викликає `add`. Тип-перевірка на неї не має жодних претензій — і мала б рацію. Автор `fill` не міг передбачити, що комусь спаде на думку підсунути під `ArrayList` об'єкт, чий `add` — це замаскована відмова.

Зламалася не `fill`. Зламалась **обіцянка**, на яку `fill` мала повне право спертися. `ImmutableList` оголосив себе повноцінним `ArrayList`, а тоді порушив те, що `ArrayList` гарантує всім своїм клієнтам. І оскільки підстановка непомітна для системи типів, ця міна лежатиме тихо доти, доки якийсь потік виконання не проведе `ImmutableList` крізь код, писаний під базу, — тоді й рвоне, можливо, за півроку й у зовсім іншому місці, ніж де закладено ієрархію.

![Ліворуч: одна ієрархія, де ImmutableList успадковує ArrayList і перевизначає add на виняток, а клієнт fill(list) викликає add і летить у вибух під час роботи. Праворуч: типи розділено на ReadableList і MutableList, незмінний список реалізує лише ReadableList, тож у місце, де чекають add, компілятор його не пускає.](img/split.svg)

*Зліва напрямок, у якому пастку закладено: одна ієрархія, спільний `add`, виняток усередині — і вибух аж під час роботи. Справа — куди ми зараз переберемося: два типи, і небезпечну підстановку відхиляє компілятор, а не рантайм.*

## Крок 2: діагноз за правилом контракту

Перш ніж лагодити, поставимо точний діагноз. «Недобре пахне» — не діагноз; нам потрібне ім'я хвороби, щоб знати, що саме різати.

Згадаймо, що контракт методу — це передумова (що клієнт мусить забезпечити **перед** викликом), постумова (що метод гарантує **на виході**) та інваріант (що завжди істинне про об'єкт). Нащадок, перевизначаючи метод, може посунути контракт, але лише в безпечний для клієнта бік: **передумову — тільки послабити** (приймати не менше входів, ніж база), **постумову — тільки посилити** (обіцяти не менше). Перевернеш будь-що з цього — і клієнт, написаний під базу, ламається. [Звідки ці правила беруться і як їх вивести суворо](topic:programming/design-by-contract) — окрема тема; тут вони нам потрібні як лінійка, якою міряють підозрюваного.

Прикладімо лінійку до нашого випадку. Яка передумова в `ArrayList.add`?

```
ArrayList.add(x):
  передумова: — (жодної; додавати можна завжди)
  постумова:  size зросло на 1, елемент x лежить у кінці
```

А що зробив `ImmutableList.add`?

```
ImmutableList.add(x):
  передумова: false (не викликати НІКОЛИ — інакше виняток)
  постумова:  — (нічого не гарантує, бо не виконується)
```

Ось воно, чорним по білому. `ImmutableList` **посилив передумову** `add` до найжорсткішого можливого — до `false`, тобто «не смій викликати мене взагалі». База не вимагала від клієнта нічого; нащадок раптом зажадав неможливого. Це пряме, підручникове порушення правила «передумову можна тільки послабити». Клієнт `fill`, що забезпечував рівно те, чого вимагала база (тобто нічого особливого), і сумлінно кликав `add`, — наразився на вимогу, про яку не знав і знати не міг.

> 🔧 **Навіщо це.** Правило контракту перетворює «мені здається, тут проблема» на «ось конкретне порушення, ось метод, ось яку саме частину контракту зламано». Це не педантизм — це те, що дозволяє полагодити **точно**. Ми тепер знаємо: біда не в тому, що список незмінний, а в тому, що `add` вимагає від клієнта неможливого, лишаючись у типі, який усім клієнтам цей `add` обіцяє. Значить, лікування — прибрати `add` із того типу, який бачить чесний клієнт. Не залатати виняток гарнішим повідомленням, а **вийняти обіцянку, якої не можемо дотримати**, з-перед очей того, хто на неї покладається.

Помітьмо заразом, що «кинути виняток» — лише найгрубіший зі способів так порушити LSP, і саме тому найпомітніший. Тихіші родичі того самого гріха — `add`, що мовчки **нічого не робить** (порушив постумову: обіцяв, що size зросте, а воно не зросло), або що повертає якусь **заглушку** замість чесної роботи. Виняток хоч гучно падає; порожня реалізація бреше беззвучно, і її баг ловиться ще пізніше. Усі троє — та сама хвороба: нащадок узяв на себе обіцянку методу, якої не збирається виконувати.

## Крок 3: розділити тип, щоб брехня стала неможливою

Тепер лікування — і воно принципове. Спокуса — залишити ієрархію як є, а `add` у незмінному зробити «розумнішим»: не кидати виняток, а тихо повертати новий незмінний список, чи логувати попередження, чи ще якось викрутитися. Усе це — латання симптому. Хвороба в тому, що **тип бреше про свої можливості**, і поки тип бреше, будь-яка латка лишає під ним ту саму міну.

Правильний хід — перебудувати самі типи так, щоб жоден із них не обіцяв того, чого його реалізації не виконують. Розщепимо єдиний «список» на дві чесні обіцянки:

- **`ReadableList`** — чесний мінімум: уміє лише те, що вміють **усі** списки без винятку, і незмінні теж. Читати за індексом, знати свій розмір. Нічого, що міняє вміст.
- **`MutableList`** — розширює `ReadableList` і додає **окрему, ширшу** обіцянку: `add`. Її беруть на себе тільки ті, хто справді вміє додавати.

Незмінний список тепер реалізує **лише** `ReadableList`. Він більше не оголошує `add` — і тому фізично не може опинитися там, де на `add` розраховують.

Ось цей рефакторинг у TypeScript, де ключова робота лягає на структуру інтерфейсів:

```ts
// Чесний мінімум: тільки читання. Це вміють УСІ списки.
interface ReadableList<T> {
  get(i: number): T;
  size(): number;
}

// Розширення: додавання — окрема обіцянка, лише для тих, хто вміє.
interface MutableList<T> extends ReadableList<T> {
  add(x: T): void;
}

// Змінний список реалізує ОБИДВА інтерфейси.
class ArrayList<T> implements MutableList<T> {
  private items: T[] = [];
  get(i: number): T { return this.items[i]; }
  size(): number { return this.items.length; }
  add(x: T): void { this.items.push(x); }
}

// Незмінний реалізує ЛИШЕ ReadableList — про add навіть не згадує.
class ImmutableList<T> implements ReadableList<T> {
  private readonly items: readonly T[];
  constructor(initial: readonly T[]) { this.items = [...initial]; }
  get(i: number): T { return this.items[i]; }
  size(): number { return this.items.length; }
}
```

Тепер найважливіше — переписати клієнта так, щоб він **просив рівно те, що йому треба**. Функція `fill` додає елементи, отже їй потрібне не «якийсь список», а саме `MutableList`:

```ts
// fill вимагає рівно свою потребу — можливість додавати.
function fill(list: MutableList<number>, n: number): void {
  for (let i = 0; i < n; i++) list.add(i);
}

fill(new ArrayList<number>(), 3);       // ок

const frozen = new ImmutableList<number>([10, 20]);
fill(frozen, 3);
//   ^^^^^^ Argument of type 'ImmutableList<number>' is not
//          assignable to parameter of type 'MutableList<number>'.
//          Property 'add' is missing in type 'ImmutableList<number>'.
```

Ось у цьому рядку й лежить уся перемога. Виклик `fill(frozen, 3)` **не компілюється**. Не «падає в тесті», не «кидає виняток у проді через півроку» — а взагалі не збирається, з чіткою вказівкою: у `ImmutableList` немає `add`, а `MutableList` його вимагає. Небезпечну підстановку відхилено на найранішому можливому рубежі, ще до того, як програма стала програмою. LSP тут не «дотримано зусиллям волі» — його **неможливо порушити**, бо ніхто вже й не обіцяє того, чого не робить.

Зверни увагу на `readonly T[]` усередині `ImmutableList`. Це не косметика. У TypeScript масив, помічений `readonly`, **не можна присвоїти** туди, де чекають звичайний змінний масив, — присвоєння одностороннє: змінний годиться там, де просять `readonly` (звужуємо права — безпечно), але не навпаки (це відкрило б чорний хід до мутації через інший псевдонім). Тобто та сама логіка «розділи можливості типом», що ми провели на рівні своїх інтерфейсів, у TypeScript **вбудована** в самі масиви — і ми нею користуємось, щоб гарантувати незмінність начиння зсередини, а не самою лише дисципліною.

Тепер той самий рефакторинг у Python. Тут інструмент інший — **протокол (`Protocol`)**, структурний інтерфейс: клас вважається його реалізацією не тому, що явно від нього успадкував, а тому, що має потрібні методи:

```python
from typing import Protocol

# Чесний мінімум: тільки читання.
class ReadableList(Protocol):
    def get(self, i: int): ...
    def size(self) -> int: ...

# Розширення: додавання — окрема обіцянка.
class MutableList(ReadableList, Protocol):
    def add(self, x) -> None: ...

# Змінний список має ВСІ методи — отже структурно він MutableList.
class ArrayList:
    def __init__(self):
        self._items = []
    def get(self, i):        return self._items[i]
    def size(self) -> int:   return len(self._items)
    def add(self, x) -> None:
        self._items.append(x)

# Незмінний НЕ має add — отже структурно він лише ReadableList.
class ImmutableList:
    def __init__(self, initial):
        self._items = tuple(initial)      # кортеж: сам не мутує
    def get(self, i):        return self._items[i]
    def size(self) -> int:   return len(self._items)
```

І клієнт, що просить рівно свою потребу:

```python
# fill просить MutableList — тобто «уміє add».
def fill(lst: MutableList, n: int) -> None:
    for i in range(n):
        lst.add(i)

fill(ArrayList(), 3)                       # ок

frozen = ImmutableList([10, 20])
fill(frozen, 3)
#    ^^^^^^ mypy: Argument 1 to "fill" has incompatible type
#           "ImmutableList"; expected "MutableList"
```

Тут криється тонкість, яку чесно назвати обов'язково — бо вона змінює те, на що можна покластися. У TypeScript помилку ловить **компілятор**: код із `fill(frozen)` просто не збереться в JavaScript, і зламати підстановку в зібраній програмі неможливо. У Python помилку ловить **mypy** (чи інший статичний перевіряч типів) — окремий інструмент, який запускають поряд. Якщо його не запустити, Python радо виконає `fill(frozen, 3)` і впаде під час роботи з `AttributeError: 'ImmutableList' object has no attribute 'add'` — бо анотації типів у Python за замовчуванням не перевіряються під час виконання, це підказки для інструментів і людей, а не бар'єр рантайму. Тобто той самий рефакторинг у Python дає той самий захист **лише за умови**, що перевірка типів — частина твого процесу (у CI, у редакторі). Немає перевірки — немає й гарантії; лишається сама структура, яка бодай **документує** намір і скеровує чесного програміста.

Заради повноти: `Protocol` можна позначити `@runtime_checkable`, і тоді `isinstance(x, MutableList)` працюватиме під час виконання. Але й це слабший захист, ніж здається: перевірка дивиться лише, чи **існують** названі методи, а не чи мають вони правильні сигнатури. Тобто вона зловить відсутній `add`, але не зловить `add` із неправильними аргументами. Це рятівне коло, а не стіна.

> 🔧 **Навіщо це.** Мета рефакторингу — пересунути момент, коли ловиться помилка, якнайраніше: з рантайму в проді → у тест → у компіляцію. `ImmutableList extends ArrayList` ловить біду в **рантаймі** й лише там, куди хтось провів незмінний список. Розділення на `ReadableList`/`MutableList` у TypeScript зсуває це в **компіляцію** — помилку видно до запуску, всюди й одразу. У Python — у **перевірку типів**, тобто в CI, якщо ти її туди поставив. Що раніше рубіж, то дешевша помилка й то менше на неї покладаєшся сподіванням, що «хтось здогадається протестувати саме цей шлях». Це та сама думка, що стоїть за [принципом розділення інтерфейсів](topic:programming/interface-segregation): тонкий інтерфейс, який майже нічого не обіцяє понад те, що всі його реалізації справді роблять, **важче** порушити підстановкою, бо порушувати вже майже нема чого.

## Крок 4: тести, що фіксують безпечну підстановку

Рефакторинг без тестів — це надія, а не гарантія. Нам потрібні тести, які закріплюють головну властивість — **безпечну підстановку** — і роблять це так, щоб «до» й «після» було видно як контраст. Тобто тест, який показує, що поламана версія таки ламається, і тест, який показує, що полагоджена — тримається.

Ключова ідея тестування на LSP: тестуй **через тип бази**, а не через конкретний клас. Пиши тест, що бере абстракцію (`ReadableList`) і перевіряє її контракт; тоді **кожна** реалізація мусить цей тест пройти. Якщо якийсь нащадок його провалює — він не підставний, і тест це показує пальцем. Такий тест іноді звуть **контрактним**: він перевіряє не клас, а обіцянку, і його прогонять на всіх, хто цю обіцянку дає.

Спершу закріпимо спільний контракт `ReadableList` — те, що мусить бути істинним для будь-якого списка, змінного й незмінного однаково:

:::tabs
```ts
// Контрактний тест: істинний для БУДЬ-ЯКОГО ReadableList.
// Приймає фабрику, щоб прогнати той самий тест на кожній реалізації.
function readableContract(
  name: string,
  make: (init: number[]) => ReadableList<number>,
): void {
  test(`${name}: читання за контрактом ReadableList`, () => {
    const list = make([10, 20, 30]);
    expect(list.size()).toBe(3);          // постумова size
    expect(list.get(0)).toBe(10);         // постумова get
    expect(list.get(2)).toBe(30);
  });
}

// Той самий контракт — на обох реалізаціях. Обидві мусять пройти.
readableContract("ArrayList", (init) => {
  const l = new ArrayList<number>();
  for (const x of init) l.add(x);
  return l;
});
readableContract("ImmutableList", (init) => new ImmutableList<number>(init));
```
```python
import pytest

# Контрактний тест як параметризована фабрика: той самий тест
# прогоняється на КОЖНІЙ реалізації ReadableList.
def make_arraylist(init):
    l = ArrayList()
    for x in init:
        l.add(x)
    return l

def make_immutable(init):
    return ImmutableList(init)

@pytest.mark.parametrize("make", [make_arraylist, make_immutable])
def test_readable_contract(make):
    lst = make([10, 20, 30])
    assert lst.size() == 3                # постумова size
    assert lst.get(0) == 10               # постумова get
    assert lst.get(2) == 30
```
:::

Обидві реалізації проходять цей тест — і в цьому вся суть. `ImmutableList` **справді** підставний скрізь, де очікують `ReadableList`: як читабельний список він бездоганний, жодної обіцянки не порушує. Проблема ніколи не була в тому, що незмінний список поганий, — проблема була в тому, що його оголосили вміти те, чого він не вміє. Контрактний тест на `ReadableList` це підтверджує: у своєму чесному типі він громадянин першого сорту.

Тепер зафіксуємо другу половину — те, що небезпечну підстановку **відхилено**. Тут «до» й «після» тестуються по-різному, і сама ця різниця — головний висновок:

**«До» (поламана ієрархія): підстановка проходить типи, але вибухає в рантаймі.** Тест мусить зловити виняток — тобто задокументувати, що біда ловиться аж під час виконання:

:::tabs
```ts
// Поведінка ПОЛАМАНОЇ версії (ImmutableList extends ArrayList):
// підстановка компілюється, а падає в рантаймі. Тест це фіксує.
test("до: add на незмінному кидає виняток у рантаймі", () => {
  const frozen: ArrayList<number> = new BrokenImmutableList<number>([1, 2]);
  expect(() => frozen.add(99)).toThrow(/незмінний/);
  // помилку видно ЛИШЕ тут, під час виконання цього рядка
});
```
```python
# Поведінка ПОЛАМАНОЇ версії: підстановка проходить,
# а add падає в рантаймі. Тест це фіксує.
def test_before_add_raises_at_runtime():
    frozen: BrokenImmutableList = BrokenImmutableList([1, 2])
    with pytest.raises(TypeError, match="незмінний"):
        frozen.add(99)
    # помилку видно ЛИШЕ тут, під час виконання
```
:::

**«Після» (розділені типи): підстановку відхиляє компілятор.** А ось цей контраст — найтонший і найважливіший. Правильний тест на те, що «`ImmutableList` не можна дати туди, де просять `add`», — це тест, який **не існує як рантайм-тест**, бо відповідний код просто **не компілюється**. Перевіряємо ми це не звичайним асертом, а перевіркою типів — тобто тестом, що живе на рівні компіляції:

```ts
// «Після»: тест НА РІВНІ ТИПІВ. Ці рядки МУСЯТЬ не компілюватися —
// і це перевіряється утилітою expect-type (або @ts-expect-error).

// @ts-expect-error — ImmutableList не MutableList: немає add
fill(new ImmutableList<number>([1, 2]), 3);

// Директива @ts-expect-error сама є тестом: якщо помилки НЕ станеться
// (тобто хтось випадково зробить підстановку знову можливою),
// компілятор поскаржиться, що @ts-expect-error зайвий, — і збірка впаде.
```

Ця конструкція `@ts-expect-error` — красива саме тим, що працює в обидва боки. Поки підстановка заборонена, рядок нижче не компілюється, а директива це очікує — усе тихо. Але якщо хтось згодом «полагодить зручність» і знову відкриє `add` у незмінному типі, помилка компіляції зникне — і тоді вже сама директива `@ts-expect-error` стане зайвою, а TypeScript цього не подарує й **завалить збірку**. Тобто тест ловить не лише поточне порушення, а й **майбутній регрес**: спробу тихцем повернути небезпечну ієрархію.

У Python прямого аналога «тесту на не-компіляцію» немає — бо немає компіляції як бар'єра. Найближче — прогнати mypy як частину CI й перевірити, що він **лається** на заборонений виклик. Це роблять або через плаґін-перевірку, або найпростіше — окремим файлом-«негативом» із коментарем-очікуванням:

```python
# файл negative_check.py — прогоняється через `mypy negative_check.py`,
# і CI перевіряє, що mypy ВИДАВ саме цю помилку:

fill(ImmutableList([1, 2]), 3)  # type: ignore[arg-type]
# Коментар type: ignore[arg-type] грає ту саму роль, що @ts-expect-error:
# доки помилка типів є — усе тихо; якщо помилка зникне (підстановку знову
# відкрили), mypy у режимі --warn-unused-ignores поскаржиться на зайвий
# ignore — і CI впаде, зловивши регрес.
```

Зведемо докупи, бо саме цей набір тестів і є справжнім результатом рефакторингу:

```
що фіксуємо                             ДО (спадкування)      ПІСЛЯ (розділені типи)
────────────────────────────────────────────────────────────────────────────────
Immutable читається як ReadableList     контрактний тест ✓    контрактний тест ✓
Immutable НЕ підставляється під add     рантайм-виняток       не компілюється (TS)
                                        (ловиться пізно)      / mypy-помилка (Py)
регрес «знову відкрили add»             не ловиться взагалі   ловиться збіркою
```

Найважливіший рядок — останній. Поламана версія не має жодного способу зловити регрес: якщо хтось погіршить ієрархію ще дужче, жоден наявний тест і не писне. Розділена версія перетворює саму систему типів на невсипущого сторожа: спроба повернути небезпечну підстановку валить збірку. Ти вклав роботу один раз — і порушення стало не «тим, за чим треба стежити», а **тим, що система не дає зробити**.

## Складність і типові пастки

Рефакторинг простий на вигляд, але навколо нього юрмиться кілька пасток, у які вкочуються знову й знову. Назвемо кожну поіменно.

**Пастка перша, найпоширеніша: «заглушити» замість «розділити».** Найпряміший рефлекс, коли `add` не пасує незмінному, — не чіпати ієрархію, а зробити `add` «чемнішим»: нехай не кидає виняток, а тихо нічого не робить, або повертає новий список, або логує й іде далі. Це **не лікує, а ховає хворобу**. Мовчазний `add`, що нічого не робить, порушує постумову (клієнт вірить, що size зросло, а воно ні) — і тепер баг ловиться ще пізніше, ніж виняток, бо навіть не падає. Заглушка — не рятунок від порушення LSP, це **тихіша** його форма. Єдине справжнє лікування — прибрати обіцянку з типу, а не підмінювати її беззвучною брехнею.

**Пастка друга: часткова реалізація «на майбутнє».** Буває, тип оголошує метод, який «поки не працює, але потім допишемо» — і лишає в ньому `throw new Error("не реалізовано")` чи `raise NotImplementedError`. З погляду підстановки це рівно та сама міна, що й `ImmutableList`: тип обіцяє вміння, якого не має. Поки метод порожній, кожен клієнт, що на нього спереться, — вже потенційна жертва. Якщо вміння ще нема — його не повинно бути й у типі; додай його тоді, коли він справді запрацює, а не як розписку наперед.

**Пастка третя: інтерфейс завеликий від початку.** Корінь усієї історії — що `ArrayList` від самого народження звалив читання й запис в один тип. Якби «список» одразу проєктували як `ReadableList` + `MutableList`, незмінному різновиду не було б куди вкрасти зайву обіцянку — він реалізував би читабельний інтерфейс, і все. Тому найдешевший рефакторинг — той, якого не довелось робити: проєктуючи тип, питай не «що вміє найбагатша реалізація», а «що вміють **усі** реалізації». Спільний знаменник іде в базовий інтерфейс; ширші вміння — в окремі надбудови. Це прямий важіль [принципу розділення інтерфейсів](topic:programming/interface-segregation), і LSP тут його близький родич: тонкий чесний інтерфейс майже неможливо порушити підстановкою.

**Пастка четверта, підступна у Python: сподівання на захист, якого нема.** Легко провести цей рефакторинг у Python, побачити гарні `Protocol`-и й вирішити, що підстановку тепер захищено, як у TypeScript. Це не так, доки перевірка типів не стоїть у CI. Протокол без запущеного mypy — це документація наміру, а не бар'єр: `fill(frozen)` виконається й впаде вже в рантаймі. Різниця між «компілятор не пустить» і «mypy поскаржиться, якщо його запустити» — не дрібниця, і будувати на ній гарантію можна лише тоді, коли той «якщо» замкнено процесом. Тому в Python-проєкті цей рефакторинг має сенс лише в парі з перевіркою типів як обов'язковим кроком складання; інакше ти пересунув пастку, але не прибрав її.

**Пастка п'ята: боротьба з системою типів замість перепроєктування.** Коли з'являється клас, який «майже» пасує в ієрархію, але один метод у нього зайвий чи бракує, — тягне обійти типи силою: привести тип наниз, вимкнути перевірку, накрити `any` чи `# type: ignore`. Щоразу, коли ловиш себе на цьому, зупинись: система типів не капризує, вона **повідомляє про реальне порушення підстановки**. Правильна відповідь — не заткнути її, а почути й перепроєктувати ієрархію так, щоб примус став непотрібним. Приведення типу тут — не інструмент, а біле прапорець: воно каже, що модель типів розходиться з правдою про поведінку, і латати треба модель, а не глушити сигнал.

Спосіб думати про все це один. Порушення LSP на кшталт `ImmutableList extends ArrayList` — це завжди тип, що **обіцяє більше, ніж уміє**. Ти можеш ховати розрив (виняток, заглушка, `NotImplementedError`, приведення типу) — і тоді він рано чи пізно рвоне під час роботи, у місці й часі на свій вибір. А можеш прибрати сам розрив: розділити тип так, щоб кожна обіцянка давалася лише тими, хто її виконує, — і тоді порушувати стане **нічого**, а система типів із ворога, якого обходять, перетвориться на сторожа, який тримає інваріант замість тебе. Перше — це надія; друге — гарантія, і різниця між ними рівно та сама, що між «баг чекає підстановки» і «баг неможливо написати».
