# ⚙️ Як ростити C-API, нікого не ламаючи: opaque struct, versioned struct, `_v2`-функції

Уяви, що ти написав маленьку бібліотеку для роботи з давачем температури на мікроконтролері. Виклав заголовок `sensor.h`, поклав `libsensor.a` — і за півроку його вже кличуть із трьох різних прошивок у трьох різних командах. А тепер до бібліотеки треба **додати можливості**: підтримати калібрування, дати доступ до внутрішнього кешу, ввести режими точності. Питання не в тому, як це написати. Питання в тому, як це написати так, **щоб жодна з тих трьох прошивок не зламалася** — ні під час компіляції, ні, що страшніше, тихо в проді.

Це і є щоденна задача еволюції C-API. У ній два різні рівні сумісності, і сплутати їх — класична пастка. Перший — **сумісність джерела** (*source compatibility*): чужий код, який перезбирають із твоїм новим заголовком, має скомпілюватися без правок. Другий, підступніший — **бінарна сумісність** (*ABI*, англ. *Application Binary Interface* — двійковий інтерфейс застосунку): уже **скомпільований** чужий об'єктник, який **не перезбирали**, має й далі правильно працювати з новою версією твоєї бібліотеки, підвантаженою як `.so`/`.dll` чи прилінкованою пізніше. C тут особливо суворий: у ньому немає ні простору імен, ні перевантаження, ні механізму версій — сама розкладка структур у пам'яті й імена символів **і є** контракт. Тому весь фокус — навчитися міняти реалізацію, **не рухаючи ці дві речі**.

Нижче — три прийоми, що разом дають майже необмежену свободу зростання, і чіткий перелік того, що вони тримають стабільним. А наприкінці — пастки, де API ламається **мовчки**, бо компілятор не бачить проблеми, а машина бачить.

> 🔧 **Навіщо це.** На вбудованих системах це не абстракція. Виробник чипа дає тобі HAL-бібліотеку; ти пишеш поверх неї; хтось третій пише поверх тебе. Оновлення SDK не має ламати прошивки, які вже пройшли сертифікацію й лежать у польоті. Той самий закон діє для будь-якої `.so` в Linux, для драйверів, для плагінів. Уміти нарощувати C-API без злому — це те, що відрізняє бібліотеку, яку оновлюють спокійно, від тієї, кожне оновлення якої — лотерея.

## Прийом перший: opaque struct — сховай тип, і зможеш міняти нутро

Почнімо з найпотужнішого. Наївний спосіб віддати давач клієнтові — покласти структуру просто в заголовок:

```c
// sensor.h  —  НАЇВНО, так робити не треба
struct sensor {
    int      pin;
    float    scale, offset;
    uint16_t buf[64];      // внутрішній кеш
    uint32_t last_us;
};
struct sensor *sensor_open(int pin);
float          sensor_read(struct sensor *s);
```

Що тут сталося? Ти щойно **опублікував розкладку пам'яті** як частину контракту. Клієнт бачить усі поля — він може написати `s->scale = 2.0f`, може зробити `struct sensor local;` на стеку, може прочитати `s->buf[0]`. І щойно він це зробив, ти **прикутий до цієї розкладки назавжди**. Захотів прибрати `buf` чи змінити його розмір — зсунуться зсуви всіх полів після нього, і кожен уже скомпільований клієнт, що звертався до `s->last_us`, читатиме сміття. Захотів додати мьютекс — той самий біль. Розмір `sizeof(struct sensor)` теж витік назовні: якщо клієнт десь виділив масив таких структур, зміна розміру ламає його арифметику вказівників.

Рішення — **неповний тип** (*incomplete type*): оголоси, що структура існує, але **не показуй її полів**.

```c
// sensor.h  —  ПРАВИЛЬНО: opaque handle
typedef struct sensor sensor_t;        // тип існує, але тіла тут немає

sensor_t *sensor_open(int pin);
float     sensor_read(sensor_t *s);
void      sensor_close(sensor_t *s);
```

Тіло структури живе **тільки в `.c`**, куди клієнт не заглядає:

```c
// sensor.c  —  тіло сховане тут
#include "sensor.h"
#include <stdlib.h>

struct sensor {           // ← справжні поля, видно лише цьому файлу
    int      pin;
    float    scale, offset;
    uint16_t buf[64];
    uint32_t last_us;
};

sensor_t *sensor_open(int pin) {
    sensor_t *s = malloc(sizeof *s);   // sizeof знає повний тип — ми ж усередині
    if (!s) return NULL;
    s->pin = pin;
    s->scale = 1.0f; s->offset = 0.0f;
    s->last_us = 0;
    return s;
}

float sensor_read(sensor_t *s) {
    /* … читаємо АЦП, застосовуємо scale/offset … */
    return 0.0f;
}

void sensor_close(sensor_t *s) { free(s); }
```

Компілятор, збираючи **клієнтський** код, бачить лише рядок `typedef struct sensor sensor_t;`. Він знає, що `sensor_t` — структура, і вміє тримати **вказівник** на неї (`sensor_t *`), бо розмір вказівника той самий незалежно від того, на що він показує. Але він **відмовиться** дати клієнтові розмір (`sizeof(sensor_t)` — помилка компіляції), відмовиться створити її на стеку (`sensor_t local;` — помилка), відмовиться дати доступ до полів (`s->pin` — помилка). Клієнт **фізично не може** зачепитися за нутрощі.

![Ліворуч зелена рамка «sensor.h (бачить клієнт)» з typedef на неповний тип і трьома функціями open/read/close, підпис «неповний тип: розмір і поля невідомі — лише вказівник»; праворуч сіра рамка «sensor.c (сховане нутро)» з повними полями struct sensor і підписом «переставляй, додавай, викидай — заголовок не змінюється»; між ними стрілка «лише *»](img/opaque.svg)

*Клієнт тримає тільки `sensor_t *` і не знає ні розміру, ні полів. Тому нутро — pin, scale, буфер, будь-що — переставляй, додавай, викидай: заголовок не змінюється, а вже скомпільований клієнт продовжує працювати з новою бібліотекою без перезбирання. Обсяг того, що сховано за вказівником, — це буквально міра твоєї майбутньої свободи.*

Ось що цей прийом тримає стабільним: **публічна поверхня — це лише ім'я типу й сигнатури функцій**, а не жодного біта внутрішньої розкладки. Тепер ти можеш переписати `struct sensor` як завгодно: додати поля, викинути `buf`, замінити його на вказівник на динамічний буфер, вставити мьютекс, поміняти порядок полів заради вирівнювання — і **жоден** клієнт цього не помітить, бо жоден клієнт цього не бачив. `sizeof` рахується всередині `.c`, де тип повний; `malloc(sizeof *s)` завжди виділяє рівно стільки, скільки треба **поточній** версії структури. ABI не порушено, бо ABI тут — лише «функція приймає й повертає вказівник», а розкладка вказівника не залежить від того, куди він показує.

Це не екзотика — це найпоширеніший стандартний тип у C, який ти вживаєш щодня: `FILE *`. Ти ніколи не бачив полів `struct _IO_FILE` і ніколи не робив `FILE f;` на стеку — тільки `FILE *f = fopen(...)`. Саме тому стандартна бібліотека десятиліттями перекроює нутрощі `FILE` під нові платформи, а твій код, написаний 1990 року, досі лінкується й працює. Той самий приклад — дескриптори в POSIX, `HANDLE` у Windows, будь-який пристойний C-SDK. Це усталена, а не спірна практика: opaque pointer через неповний тип — канонічний спосіб інформаційного приховування в C, і саме він зберігає ABI без потреби перезбирати залежний код.

> 🔧 **Навіщо це.** Правило-важіль: **якщо клієнтові не конче створювати структуру на стеку самому — роби її opaque**. Ціна — одне динамічне виділення на об'єкт (на МК іноді критично, тоді дають статичний пул усередині бібліотеки). Виграш — уся внутрішня розкладка стає твоєю приватною справою назавжди. Це найдешевша страховка проти найдорожчого класу ABI-зломів, і платиш ти за неї один раз — на етапі дизайну заголовка.

## Прийом другий: коли структуру таки видно — versioned struct із полем size

Іноді opaque не годиться. Клієнт **мусить** сам створити структуру — типово це блок налаштувань, який він заповнює на стеку й передає тобі:

```c
// клієнт хоче писати саме так — без malloc, на стеку
sensor_config_t cfg = { .pin = 4, .rate_hz = 100 };
sensor_t *s = sensor_open(&cfg);
```

Тут структуру **видно** клієнтові — інакше він не заповнить поля. А отже, її розкладка стала публічним контрактом, і питання «як додати нове поле, не зламавши старих клієнтів» повертається з усією гостротою. Бо старий клієнт, зібраний тоді, коли `sensor_config_t` мала два поля, створює на стеку структуру **старого розміру**. Твоя нова бібліотека, якщо наївно читатиме поле, якого в його версії немає, полізе за межі його структури — читатиме сусідні байти стеку.

Рецепт, який тут працює й перевірений галуззю, — **поле розміру першим членом структури**:

```c
// sensor.h  —  versioned config: size ПЕРШИМ полем
typedef struct {
    size_t   size;          // ← скільки байтів у ЦІЙ структурі; заповнює клієнт
    int      pin;
    uint32_t rate_hz;
} sensor_config_t;

// зручний ініціалізатор, що проставляє size автоматично
#define SENSOR_CONFIG_INIT  { .size = sizeof(sensor_config_t) }

sensor_t *sensor_open(const sensor_config_t *cfg);
```

Клієнт заповнює `size` (найпростіше — через макрос `SENSOR_CONFIG_INIT`, тоді розмір підставляє його ж компілятор під його версію заголовка). Бібліотека, отримавши вказівник, **першим ділом читає `cfg->size`** — і так дізнається, скільки полів реально приніс цей клієнт:

```c
// sensor.c
sensor_t *sensor_open(const sensor_config_t *cfg) {
    if (!cfg || cfg->size < sizeof(cfg->size)) return NULL;   // мінімальна перевірка

    // читаємо тільки те, що клієнт ТОЧНО має за своїм розміром:
    int      pin     = cfg->pin;         // ці поля були в найпершій версії
    uint32_t rate_hz = cfg->rate_hz;
    /* … */
}
```

Тепер настає момент розширення. Через рік до налаштувань треба додати підсилення й зсув калібрування. Додаємо їх **у кінець** структури:

```c
// sensor.h  —  v2: нові поля ДОДАНО В КІНЕЦЬ
typedef struct {
    size_t   size;          // не зрушено
    int      pin;           // не зрушено
    uint32_t rate_hz;       // не зрушено
    uint8_t  gain;          // + додано у v2
    float    offset;        // + додано у v2
} sensor_config_t;
```

Ключ у тому, що поля `size`, `pin`, `rate_hz` **лишилися на тих самих зсувах** — 0, і далі. Старий клієнт, зібраний під першу версію, кладе на стек структуру зі `size = 16` (три перші поля) і про `gain`/`offset` не знає. Нова бібліотека, прочитавши `size == 16`, **розуміє: цих полів немає** — і бере для них значення за замовчуванням. Новий клієнт, зібраний під `v2`, кладе `size = 25`, і бібліотека сміливо читає всі п'ять полів. Один і той самий двійковий код бібліотеки обслуговує обидва:

```c
// sensor.c  —  v2: читаємо нові поля ЛИШЕ якщо клієнт їх приніс
sensor_t *sensor_open(const sensor_config_t *cfg) {
    if (!cfg || cfg->size < sizeof(cfg->size)) return NULL;

    int      pin     = cfg->pin;
    uint32_t rate_hz = cfg->rate_hz;

    // калібрування — тільки якщо структура достатньо велика, щоб його вміщати:
    uint8_t gain   = 1;       // дефолти для старих клієнтів
    float   offset = 0.0f;
    if (cfg->size >= offsetof(sensor_config_t, gain) + sizeof cfg->gain)
        gain = cfg->gain;
    if (cfg->size >= offsetof(sensor_config_t, offset) + sizeof cfg->offset)
        offset = cfg->offset;
    /* … застосовуємо pin, rate_hz, gain, offset … */
}
```

![Ліворуч синя колонка «заповнив клієнт, зібраний під v1»: поля size / pin / rate_hz і плашка «полів gain / offset немає», size = 16 байтів; праворуч рожева колонка «struct у новій бібліотеці v2»: ті самі три поля вище пунктирної «межі v1», а нижче — додані gain та offset, size = 25 байтів; унизу висновок про читання за size](img/versioned.svg)

*Поле `size` — це версія, закодована в байтах. Бібліотека читає його першим і за ним знає, докуди структура клієнта «справжня»: дав 16 — беруться лише перші три поля, `gain`/`offset` підставляються за замовчуванням; дав 25 — читаються всі п'ять. Старі виклики лишаються дійсними рівно тому, що нові поля лягли **тільки в кінець**, не зрушивши жодного наявного.*

Ось що цей прийом тримає стабільним: **зсуви всіх старих полів** і **мінімальний розмір, який гарантовано принесе будь-який клієнт**. Порядок читання простий — «спершу дізнайся розмір, потім читай лише те, що в нього вміщається». Це не вигадка одного проєкту: так влаштовані десятки структур у Win32, де перше поле `cbSize` клієнт зобов'язаний проставити перед викликом, аби API розрізнив версії структури й обробив і стару, і нову форму. Той самий підхід — у структурах, що ростуть у системних бібліотеках Linux, і в явному вигляді (поле-тип плюс ланцюг розширень) у сучасних API на кшталт Vulkan. Це усталений галузевий прийом, а не місцева хитрість.

> 🔧 **Навіщо це.** Поле `size` коштує чотири-вісім байтів і одну перевірку — а купує тобі право додавати налаштування роками, не випускаючи нового заголовка з розривом. Без нього кожне нове поле в публічній структурі — це ABI-злом, тобто новий мажор бібліотеки й примусове перезбирання всіх клієнтів. Це той рідкісний випадок, коли один зайвий член структури окупається стократно.

## Прийом третій: `_v2`-функції — нова поруч зі старою, а не замість

Буває, що самим ростом структури не обійтися: треба **змінити саму сигнатуру** функції — додати параметр, повернути інший тип, змінити поведінку так, що стара форма фізично не вміщає нову. Спокуса — «просто дописати параметр до наявної функції». Це і є класичний злом: у C функція визначається своїм **іменем-символом**, і хоч у скількох аргументах, ім'я `sensor_read` в об'єктнику одне. Старий клієнт кличе `sensor_read(s)` з одним аргументом; якщо ти зробив її двоаргументною, у кращому разі падає лінкування, у гіршому (за деяких ABI) — тихе псування стека.

Правильний хід — той самий, що радить Річ Гікі (Rich Hickey) у доповіді «Spec-ulation» (2016): **не міняй наявне — став нове поруч**. Гікі називає корисне зростання API **нарощуванням** (англ. *accretion* — накопичення шар за шаром): добра зміна або **дає більше** (accretion — нова можливість, нова функція), або **вимагає менше** (relaxation — послаблює умову входу); зломом він називає протилежне — коли зміна починає **вимагати більше** або **давати менше**. Друга нова форма поруч зі старою — це чиста accretion: старий символ лишається, новий з'являється, ніхто нічого не втратив.

У C це буквально означає **нове ім'я функції**:

```c
// sensor.h
// ── v1: стара функція лишається НАЗАВЖДИ, без змін ──
float sensor_read(sensor_t *s);

// ── v2: нова функція ПОРУЧ — повертає код помилки, значення через out-параметр ──
typedef enum { SENSOR_OK = 0, SENSOR_ERR_IO = -1, SENSOR_ERR_RANGE = -2 } sensor_status_t;
sensor_status_t sensor_read_v2(sensor_t *s, float *out);
```

Реалізація — стара кличе нову або живе своїм життям; головне, що обидва символи присутні в бібліотеці:

```c
// sensor.c
sensor_status_t sensor_read_v2(sensor_t *s, float *out) {
    if (!s || !out) return SENSOR_ERR_RANGE;
    /* … читаємо АЦП … */
    *out = /* виміряне зі scale/offset */ 0.0f;
    return SENSOR_OK;             // тепер клієнт РОЗРІЗНЯЄ помилку від валідного 0.0
}

float sensor_read(sensor_t *s) {         // стара форма — тонка обгортка над новою
    float v = 0.0f;
    sensor_read_v2(s, &v);               // помилку стара форма мовчки ковтає, як і раніше
    return v;                            // її контракт не змінився — 0.0 при збої
}
```

Старий клієнт лінкується з `sensor_read` і працює точно як раніше — **його поведінка не зрушилась ні на біт**. Новий клієнт бере `sensor_read_v2` і отримує чесний код помилки, який стара форма фізично не могла повернути (у неї `0.0f` означало і «нуль градусів», і «збій» — нерозрізнимо). Обидві живуть у бібліотеці одночасно; жоден клієнт не поставлений перед вибором «перепиши або зламайся».

Так само нарощують і структуру, коли її вже не можна безпечно розширити на місці (наприклад, стара була не versioned): вводять `sensor_config_v2_t` і `sensor_open_v2`, лишивши стару пару недоторканою. Суфікс `_v2` не красивий — але він чесний: він каже «стара обіцянка ціла, ось нова поруч». Саме так десятиліттями росли великі C-API: `...Ex`-функції у Win32 (`CreateWindowEx` поруч із `CreateWindow`), нумеровані ревізії структур, паралельні входи в POSIX. Стара функція **ніколи не зникає** — у цьому вся суть. Її можна лише позначити застарілою (атрибутом `deprecated`, щоб компілятор клієнта видав попередження), але **видаляти — ні**, бо видалення символу є той самий однобічний перехід, від якого ми весь час тікаємо.

> 🔧 **Навіщо це.** `_v2` виглядає як капітуляція перед елегантністю — насправді це найдешевший спосіб дати кращу форму, нікого не рухаючи. Ціна — трохи ширший заголовок і дві функції там, де «хотілося б» одну. Виграш — кожен клієнт мігрує **тоді, коли сам готовий**, а не тоді, коли ти випустив реліз. Прибрати `_v2` можна колись потім, окремим мажором, з довгим вікном попереджень — але це вже інша, свідома розмова, а не побічний ефект твого сьогоднішнього покращення.

## Пастки: де API ламається мовчки

Три прийоми вище дають свободу рости. Але поруч із ними живе клас помилок, у якому **компілятор мовчить, а машина бреше** — і саме тому вони найнебезпечніші. Гучний злом (код не збирається) ти помітиш одразу. Тихий — знайдеш у проді через тиждень.

**Пастка 1: зміна семантики без зміни сигнатури.** Найпідступніше. Ти лишив функцію `sensor_read(sensor_t *)` точно тією ж — те саме ім'я, ті самі аргументи, той самий тип повернення. Але **змінив те, що вона означає**: раніше повертала градуси Цельсія, тепер — десяті градуса; або раніше `0.0f` означало «збій», тепер — «валідний нуль». Сигнатура ідентична, тож компілятор клієнта щасливий, лінкування проходить. А кожен старий виклик тепер отримує число з іншим змістом і мовчки рахує на ньому неправильно. Це той самий однобічний перехід, лише замаскований: ти нічого не «прибрав» із поверхні, але забрав стару **обіцянку про зміст**. За Гікі це і є злом — функція почала «давати інше». Правило: **змінив зміст — зміни ім'я** (`sensor_read_deci` чи `sensor_read_v2`). Тихо перевизначати семантику наявного символу не можна ніколи.

**Пастка 2: зміна розкладки видимої структури.** Вона переслідує саме versioned struct і будь-яку неopaque структуру. Досить порушити одне з двох правил — і старі клієнти, яких не перезібрали, читатимуть не те. Джерело завжди одне: **зсув поля в C — це сума розмірів усього, що лежить перед ним**. Зрушив хоч щось раніше по структурі — «попливли» зсуви всього, що нижче.

- **Поле в середину замість кінця.** Найчастіша помилка. Вставив `int mode` між `rate_hz` і калібруванням — і `gain`, який раніше був за зсувом 8, тепер за зсувом 12. Старий клієнт, зібраний зі знанням «gain @ 8», читає за зсувом 8 те, що тепер там лежить — `rate_hz`. Ніхто не впав, число просто неправильне.
- **Перестановка наявних полів.** Поміняв місцями `pin` і `rate_hz` заради «краси» — ті самі зсуви зрушились, той самий тихий злам.
- **Зміна типу поля.** Зробив `rate_hz` з `uint32_t` на `uint64_t` — поле стало вдвічі ширшим, усе після нього з'їхало, і навіть саме `rate_hz` старий клієнт прочитає лише наполовину.

![Ліворуч колонка «чого чекає v1-клієнт»: pin@0, rate@4, gain@8, підпис «читає gain за зсувом 8»; праворуч колонка «бібліотека вставила поле в середину»: pin@0, нове mode@4, rate@8, gain@12, підпис «gain з'їхав на 12 — клієнт за зсувом 8 бере rate»; між ними стрілка «той самий заголовок?»; унизу три правила про зсуви, зміну змісту й «нове поле — тільки в кінець»](img/traps.svg)

*Той самий тихий механізм у розрізі: варто вставити поле в середину — і всі зсуви нижче «пливуть». Старий клієнт компілювався зі старою картою зсувів (`gain @ 8`) і за нею й читає; нова бібліотека переклала `gain` на зсув 12, а на зсуві 8 тепер `rate`. Ні компілятор, ні лінкер помилки не бачать — байти на місці, лише означають інше. Тому непорушне правило versioned-структур: нове поле — **тільки в кінець**, порядок і тип наявних не чіпати.*

**Пастка 3: вирівнювання й доповнення (padding).** Тонший бік тієї ж розкладки. Компілятор вставляє між полями **невидимі байти-заповнювачі**, щоб кожне поле лягло на свою межу вирівнювання (`uint32_t` — на межу 4 байтів, і так далі). Через це `sizeof` структури — **не** проста сума розмірів полів. Наслідок: додав `uint8_t gain` у кінець — здавалося б, `+1` байт, а `sizeof` виріс на 4, бо наступне за ним `float offset` компілятор вирівняв, доклавши три байти доповнення. Поки ти чесно береш розмір через `sizeof`/`offsetof` (як у коді вище) — усе сходиться само, компілятор рахує padding за тебе. Але варто десь **захардкодити** число (`if (cfg->size >= 16)` замість `offsetof(...) + sizeof(...)`) — і на іншому компіляторі чи іншій розрядності платформи, де доповнення інше, перевірка збрешеться. Правило: **ніколи не рахуй зсуви й розміри руками** — лише `sizeof` та `offsetof`, які знають про вирівнювання конкретної збірки. І пам'ятай, що розкладка структури — частина ABI платформи: та сама структура на 32- і 64-бітній цілі має різні зсуви й розмір, тож «versioned» рятує від еволюції **в межах** однієї ABI, а не від перенесення двійкового блоку між різними.

> 🔧 **Навіщо це.** Спільний корінь усіх трьох пасток один: **клієнта не перезібрали, а ти зрушив те, на що він уже спирався** — чи то зміст функції, чи то зсув поля. Гучні зломи ловить лінкер; тихі не ловить ніхто, окрім проду. Тому дисципліна проста й немилосердна: зміст функції прив'язаний до її імені (змінив зміст — змінив ім'я); наявні поля структури недоторканні, нове — тільки в кінець; усі розміри — через `sizeof`/`offsetof`, ніколи руками. Три прийоми дають рости; ці три заборони не дають зламати те, що вже росте.

## Що з цього лишається в руках

Уся ця механіка зводиться до однієї думки: **міняй те, чого ніхто не бачить, і додавай там, де це нічого не зрушує**. Opaque struct прибирає розкладку з очей клієнта — і нутро стає твоїм назавжди. Поле `size` перетворює видиму структуру на таку, що вміє рости в кінець, лишаючи старі зсуви цілими. Функція `_v2` поруч зі старою дає кращу форму, не забираючи наявної. Усі три — це те саме нарощування: щось **додається**, ніщо наявне не **рухається** й не **змінює зміст**.

А три пастки — дзеркало цього правила: тихий злам щоразу трапляється там, де щось наявне таки зрушили — зміст функції за тим самим іменем, зсув поля вставкою в середину, розмір, порахований в обхід вирівнювання. Компілятор ці зсуви не стереже, бо для нього байти лишилися на місці; стереже їх лише твоя дисципліна. Тому робочий C-API, який житиме роками, будують не з елегантних сигнатур, а з готовності ніколи не рухати те, на що вже хтось сперся, — і завжди мати куди дописати нове, не зачепивши старого.
