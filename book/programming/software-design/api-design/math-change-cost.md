# 🧮 Асиметрія вартості зміни: чому «додати» коштує нуль, а «забрати» — N

Тут ми переводимо в число одну інтуїцію: додати до API дешево, а зрізати з нього дорого. Поки це слова, з ними важко сперечатися, але й важко ними користуватися — «дорого» не скажеш начальникові, який питає, чому не можна просто перейменувати функцію. А от коли «дорого» набуває вигляду `C = N · c`, розмова змінюється: видно, від чого саме залежить ціна, коли вона нестерпна, і де проходить справжня межа між «можна відкотити» й «уже ні». Модель проста — жодної вищої математики, лише лічба й одна пряма лінія, — але вона несе на собі всю обережність дизайну API.

## Означення: що таке N і що таке c

Почнемо з єдиної величини, від якої все залежить.

```
N — кількість місць-викликів (call sites):
    скільки окремих рядків чужого (і твого) коду
    згадують цей елемент API — кличуть функцію,
    читають поле, залежать від формату повідомлення.
```

`N` — це не кількість користувачів і не кількість завантажень. Це кількість **точок дотику до конкретної обіцянки**. Одна людина може викликати твою функцію у двадцятьох місцях — це `N = 20` для неї одної. І навпаки, тисяча людей можуть жодного разу не торкнутися рідко потрібного методу — для нього `N = 0`, хоч популярність бібліотеки величезна. Тому `N` рахуємо **на елемент API**, а не на бібліотеку: у кожної функції, кожного поля, кожного ключа у форматі — свій `N`.

Друга величина — ціна полагодити один такий дотик, коли обіцянку зламано:

```
c — вартість виправити ОДНЕ місце-виклик після ламкої зміни:
    знайти + зрозуміти + виправити + перевірити
    (одиниця — година-людина, або гроші, або просто «одиниця болю»)
```

`c` — це не вартість написати нову версію функції. Це вартість, яку платить **той, хто її кликав**, щоб знову запрацювало. Розкладемо її, бо в цьому розкладі ховається половина відповіді на питання «чому взагалі дорого».

```
c = t_find + t_understand + t_fix + t_verify

    t_find      — знайти всі місця, де це кличеться
    t_understand— зрозуміти, ЩО тут малося на увазі й чому
    t_fix       — власне переписати виклик під нову форму
    t_verify    — переконатися, що поведінка не поїхала
```

Найпідступніший доданок тут — не `t_fix`. Переписати рядок швидко. Дорогі `t_understand` і `t_verify`: щоб виправити чужий виклик, треба спершу відновити в голові, навіщо він був такий, а потім довести, що після правки система поводиться, як і раніше. Ось чому **тиха** зміна змісту (той самий виклик тепер робить інше) страшніша за відверте видалення: коли метод зникає, компілятор сам знаходить усі `N` місць — `t_find → 0`. А коли метод лишився, але почав поводитися інакше, компілятор мовчить, `t_find` вистрілює до небес, і частину місць знайдуть уже в проді, де до `c` додається ще й ціна аварії.

> 🔧 **Навіщо це.** Розклад `c` підказує, як **здешевити** неминучу зміну, навіть не зменшуючи `N`. Даси зміні нове ім'я замість тихої підміни — компілятор бере на себе `t_find`, і `c` падає. Лишиш поруч перехідний період зі старою поведінкою — розмажеш `t_fix` у часі. Тобто інженер не тільки уникає ламких змін, а й, коли вони таки потрібні, свідомо зсуває доданки `c` туди, де вони дешевші.

## Дві дії — дві різні криві

Тепер порахуймо ціну самих двох дій, з яких і складається еволюція API: **додати** щось нове й **зламати** щось наявне.

**Адитивна зміна** — новий метод, новий необов'язковий параметр, нове поле у відповіді, якого старий код не читає. Ключова властивість: усі старі `N` викликів **лишаються дійсними** — вони про новинку не знають і працюють точно як раніше. Скільки з тих `N` місць треба чіпати? Жодного.

```
C_add(N) = 0 · c = 0     для будь-якого N
```

Ціна для клієнтів не залежить від `N` взагалі. Хоч троє тебе кличуть, хоч три мільйони — додавання коштує їм нуль. (Твоя власна ціна написати новий код є, але це не про клієнтів; ми рахуємо рахунок, який лягає **назовні**.)

**Ламка зміна** — прибрати метод, перейменувати, звузити тип аргументу, змінити зміст виклику. Тепер кожне з `N` місць, що на це спиралося, доведеться знайти, зрозуміти, виправити й перевірити:

```
C_break(N) = N · c
```

Проста лінійна функція, і в її простоті вся сіль. Дві дії стартують із однакового нуля місць-правок, але одна лишається на підлозі назавжди, а друга росте прямо пропорційно тому, скільки народу встигло на тебе спертися.

![Дві криві вартості від N: зелена пунктирна пряма адитивної зміни лежить на нулі, червона суцільна пряма ламкої зміни C = N·c піднімається вгору з нахилом c; вертикальний розрив між ними на тому самому N підписано «ціна ламкості»](/book/programming/software-design/api-design/img/cost_lines.svg)

*Одна й та сама зміна на однаковому N: адитивна тримається на підлозі незалежно від аудиторії, ламка тим вища, чим більший N. Вертикальний розрив між точками на тому самому N — це буквально ціна того, що ти обрав ламати, а не нарощувати.*

Нахил червоної прямої — це `c`, ціна одного дотику. Він постійний (припускаємо, що всі місця приблизно однакові коштом; трохи згодом послабимо це). Головне зараз — **форма**: адитивна крива горизонтальна, ламка — похила з додатним нахилом. Саме ця пара форм і є вся асиметрія, доведена до графіка.

## Чому саме лінійно, а не якось інакше

Варто зупинитися й спитати: звідки взялася саме пряма `N · c`, а не, скажімо, `log N` чи `N²`? Бо це не самоочевидно, і межі цієї лінійності важливі.

Лінійність випливає з того, що місця-виклики **незалежні**. Полагодити двадцяте місце не легше й не важче від того, що ти вже полагодив дев'ятнадцять до нього: кожен виклик сидить у своєму контексті, зі своїм оточенням, і вимагає свого власного `t_understand + t_fix + t_verify`. Немає ні економії на масштабі (полагодив багато — навчився, наступні швидші), ні здорожчання (кожен наступний важчий). У чистому вигляді — сума `N` однакових незалежних доданків, а сума `N` однакових величин і є `N · c`. Це модель першого наближення, і вона напрочуд добре тримається.

Де вона ламається — теж повчально, бо каже, коли реальність **гірша** за лінію:

- **Місця нерівні.** Якщо `cᵢ` різні (десь виклик тривіальний, десь загорнутий у складну логіку), точна ціна — сума `C_break = c₁ + c₂ + … + c_N = Σ cᵢ`. Лінія `N · c` — це та сама сума через **середнє** `c = (Σ cᵢ)/N`. Для міркування середнього досить; знати, що хвіст важких місць існує, корисно, коли оцінюєш конкретну міграцію.
- **Прихована залежність між місцями.** Іноді зміна в одному місці тягне зміну в сусідньому (полагодив тип тут — треба міняти виклик, що бере результат). Тоді ефективний `N` більший за кількість прямих дотиків, і крива задирається крутіше за лінію. Це не спростовує модель, а підсилює висновок: реальна ціна зазвичай **не менша** за `N · c`, тож `N · c` — це оптимістична нижня оцінка, а не завищена.

Тобто лінія `N · c` — чесна межа знизу: дешевше ламку зміну провести майже ніколи не вийде, а дорожче — легко.

## Лінійне зростання з аудиторією і парадокс успіху

Тепер з'єднаймо два шматки — і випливе неприємний, але точний висновок.

Ціна зламати обіцянку є `N · c`. А `N` росте разом із тим, наскільки корисним виявився елемент API: що влучніше ти вгадав потрібну функцію, то з більшої кількості місць її кличуть, то більший її `N`. Але ж `N` — це і множник у ціні зламу. Складаємо:

```
корисніше API  →  більший N  →  дорожча будь-яка ламка зміна
```

Ось він, **парадокс успіху**: те, що робить API цінним (його широко вживають), рівно тим самим робить його **жорстким** (його дорого міняти). Успіх і свобода зміни тут — величини, обернені одна до одної. Погана функція, яку ніхто не кличе (`N ≈ 0`), вільна: `C_break ≈ 0`, роби з нею що хочеш. Улюблена функція, на якій тримається півсвіту, — закам'яніла: її `C_break` такий, що зачепити її ніхто не наважиться. Парадокс у тім, що ти **не можеш** мати водночас і популярне, і гнучке API: чим успішніше воно збирає call sites, тим менше в тебе права їх ламати.

Звідси прямо випливає правило Джошуа Блоха (Joshua Bloch) з доповіді «How to Design a Good API and Why it Matters» (OOPSLA, 22 жовтня 2006): **коли вагаєшся — не включай** (англ. *when in doubt, leave it out*), бо «додати можна завжди, а прибрати — ні». У наших позначеннях воно доводиться в один рядок. Порівняймо дві помилки проєктувальника:

```
Помилка ПРОПУСТИТИ потрібне:   пізніше додаси  →  C = C_add = 0
Помилка ДОДАТИ зайве:          пізніше прибереш →  C = C_break = N · c
```

Ціна першої помилки — нуль (додавання завжди дешеве). Ціна другої — `N · c`, і `N` до моменту виправлення встигне вирости. Раціональний вибір під невизначеністю — той, у якого дешевша **помилка**; а помилка «пропустив» коштує нуль проти `N · c` за помилку «додав зайве». Тому в сумніві пропускай. Це не смак і не стиль — це наслідок форми двох кривих. (Статус: усталено; принцип Блоха — канонічний у літературі дизайну API, підтверджений первинним джерелом.)

> 🔧 **Навіщо це.** Парадокс успіху пояснює, чому найстрашніший тягар зрілих бібліотек — це методи, які «здавалися корисними». Вони виявилися корисними — саме тому їх тепер не викорчувати: їхній `N` завеликий. Практичний висновок жорсткий: **вартість зайвого публічного методу платиться не тоді, коли ти його додав, а тоді, коли він вдався**. Тому вузьку поверхню тримають не з естетики, а щоб не наплодити майбутніх незворотних зобов'язань.

## Зважити по невідомому: очікувана ціна

Досі ми рахували ціну зламу так, ніби зміна вже настала. Але на етапі проєктування ти її ще не робиш — ти лише вирішуєш, **чи виносити** щось у публічне API, знаючи, що **колись, можливо**, доведеться це міняти. Тут потрібна не гола `N · c`, а **очікувана** ціна.

Нехай `p` — імовірність, що елемент таки доведеться зламати за час його життя (нова вимога, знайдена вада дизайну, зміна платформи). Тоді очікуваний майбутній рахунок за цей елемент:

```
E[C] = p · N · c
```

Три множники, і кожен — окрема ручка, за яку можна взятися ще до першого рядка коду:

- **зменшити p** — виносити лише те, чия форма справді усталена; сире, недодумане API має високий `p`, бо його доведеться переробляти;
- **обмежити N** — тримати поверхню вузькою (менше публічних елементів — менше сумарних call sites), а зміну вводити нарощуванням, щоб старий `N` не потрапляв під зміну;
- **збити c** — робити зміну знайденою компілятором (нове ім'я, а не тиха підміна), лишати перехідні періоди, документувати причину межі.

Ця формула показує, чому досвід так тисне на **обидва краї**: і «публікуй менше» (це `N`), і «публікуй лише зріле» (це `p`). Новачок бачить лише поточну зручність — нульову ціну сьогодні. Формула `p · N · c` показує рахунок, який прийде поштою через рік, і саме його дорослий інженер намагається зменшити наперед.

## Коли межу варто ламати: поріг вигоди

Модель не каже «ніколи не ламай» — вона каже, **коли варто**. Бо в ламкої зміни буває й зиск: новий, чистіший дизайн економить кожному, хто вже перейшов, якусь величину `b` на місце-виклик (менше плутанини, менше вад, простіший код). Зважмо чесно.

```
Ламати варто, коли сумарна вигода перевищує сумарну ціну:

    N · b   >   N · c          (вигода)   >   (ціна міграції)
       ⟺   b > c
```

Цікаво, що `N` тут **скорочується**: і вигода, і ціна ростуть з аудиторією однаково, тож питання «ламати чи ні» зводиться до порівняння **на одне місце** — чи виграш `b` від чистішого API більший за ціну `c` перейти на нього. Але це наївний рахунок, бо він мовчить про час: ціну міграції всі платять **зараз і разом**, а вигоду збирають **потроху й потім**. Введімо це чесно.

```
Реальний поріг (з урахуванням, що вигода тече в майбутньому):

    N · b · L   >   N · c
        ⟺   b · L > c

    L — очікуваний строк життя API після зміни
        (скільки ще виграш b встигне накопичитися)
```

Тепер видно ключове: **ламати наприкінці життя API майже ніколи не варто** (малий `L` не окупить `c`), а на початку — часто варто (великий `L` попереду виправдає разову ціну). Ось чому болючі, але правильні ламки роблять **рано** — поки `N` малий, а `L` великий; і чому ту саму зміну через десять років уже не роблять — не тому, що вона стала гіршою ідеєю, а тому, що `L` вичерпався, а `N` став непідйомним. Модель дає інженерові не заборону, а точний момент: **вікно для ламкої зміни відкрите на початку й зачиняється з ростом `N` і падінням `L`**.

## Незворотність як строгий критерій: хто володіє множиною N

Тепер найглибше — формалізуймо, що взагалі означає «двері в один бік». Інтуїтивно незворотність — це «не можна відкотити». Але технічно ж файл із твоїм API можна відредагувати назад однаково легко з будь-якого боку. Тож у чому справжня різниця?

Різниця не в тому, чи можеш ти змінити **свій** код, а в тому, чи можеш ти оплатити рахунок `N · c` — тобто чи **дотягуєшся** ти до всіх `N` місць, щоб їх полагодити. А це залежить від одного: **хто володіє множиною call sites**.

```
Зворотність = ти контролюєш усі N місць-викликів.

    внутрішнє API (кличуть із твого ж репозиторію):
        N — мале, скінченне, ВІДОМЕ; grep знаходить кожне.
        Ти можеш оплатити N · c повністю → зміну відкотиш.
        → двобічні двері, рішення ЗВОРОТНЕ.

    публічна бібліотека (тебе взяли тисячі незнайомців):
        N — велике, зростає, НЕВІДОМЕ; частину викликів
        ти навіть не бачиш, а чужі рядки правити не можеш.
        Оплатити N · c ти не в змозі → назад ходу немає.
        → однобічні двері, рішення НЕЗВОРОТНЕ.
```

Ось точне означення: **межа незворотна тоді й лише тоді, коли множина її call sites виходить з-під твого контролю**. Не коли `N` велике саме по собі, а коли `N` — **чуже**. Внутрішнє API з `N = 500` викликів у твоєму монорепозиторії цілком зворотне: дорого, але ти їх усі бачиш, усі можеш полагодити одним рефакторингом, зміну можеш відкотити. Публічне API з `N = 5` невідомих зовнішніх викликів уже незворотне: ти не знаєш, де ті п'ять, не маєш доступу до тих рядків і не можеш гарантувати, що їх лише п'ять.

![Дві колонки: ліворуч зелена «N мале й відоме (твій контроль)» — усі виклики перелічені grep-ом, полагодив усі, C = N·c оплатна, двобічні двері, рішення зворотне; праворуч червона «N поза контролем (не твоє)» — N невідоме й росте, чужі рядки не полагодити, рахунок лягає на чужих, однобічні двері, рішення незворотне](/book/programming/software-design/api-design/img/reversibility.svg)

*Незворотність — не властивість файлу, а властивість того, хто володіє множиною N. Поки всі call sites твої, зміну можна відкотити (двобічні двері); щойно вони чужі й невидимі — обіцянку вже не забрати (однобічні двері), хоч технічно код редагується однаково.*

Це рівно та рамка одно- й двобічних дверей, яку Джефф Безос (Jeff Bezos) сформулював у листі акціонерам Amazon за 2015 рік: рішення-двобічні двері (зворотні) ухвалюють швидко, бо помилку легко відкотити; рішення-однобічні двері (незворотні) — повільно й обачно, бо назад не повернешся. (Статус: усталено; первинне джерело — лист Безоса 2015, там-таки й термінологія «one-way / two-way doors».) Дизайн API — окремий випадок цього загального закону рішень: [зворотні й незворотні рішення](book:programming/reversible-irreversible-decisions) розрізняють саме за тим, чи можна повернутися крізь двері, а вартість повернення для API — це і є наша `N · c`, помножена на те, скільки з тих `N` тобі підвладні.

Звідси — практичний критерій, який заміняє всі балачки про «стабільність»: **перш ніж винести елемент у публічне API, спитай, чи зможеш ти колись оплатити його зміну.** Якщо call sites лишаться твоїми — двері двобічні, помилка виправна, можна ризикнути ширшою поверхнею. Якщо call sites підуть у чужі руки — двері однобічні, і кожен публічний елемент стає незворотним зобов'язанням, яке краще недодати, ніж потім не мати змоги забрати.

> 🔧 **Навіщо це.** Цей критерій — головна причина, чому одну й ту саму функцію винести в приватний заголовок пакета й у публічний API бібліотеки — рішення **різної ваги**. Не через «код красивіший», а через те, хто по той бік межі володітиме множиною `N`. Тому команди й проводять червону лінію «internal» / «public»: усе, що internal, лишається двобічними дверима (правиш вільно, бо `N` твій), а що стало public — переходить у режим однобічних, де діє повна обережність Блоха. Знаючи, від чого залежить незворотність, ти свідомо вирішуєш, **де** цю лінію провести, а не виявляєш її випадково через рік, коли зміну вже нікуди відкочувати.

## Що лишається з цієї арифметики

Уся модель — це три формули й одне означення, і вони тримаються разом. Додати коштує `C_add = 0` незалежно від аудиторії; зламати коштує `C_break = N · c`, лінійно з числом місць-викликів. Через це успіх (великий `N`) робить API жорстким — парадокс, а не збіг. Очікуваний рахунок `p · N · c` дає три ручки — зрілість, вузькість, знайденість зміни, — за які беруться ще до першого рядка. Поріг `b · L > c` каже, що ламати варто рано (великий `L`) і майже ніколи пізно. А незворотність виявляється не властивістю коду, а властивістю власності: межа незворотна рівно тоді, коли множина `N` виходить з-під твого контролю. Тому найдешевший спосіб не платити `N · c` — не створювати обіцянку, за яку доведеться платити: тримати `N` малим і підвладним, а зміну вводити нарощуванням, щоб старі call sites ніколи не потрапляли під ніж.
