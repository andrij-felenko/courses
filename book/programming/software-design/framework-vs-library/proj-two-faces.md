# ⚙️ Одне ядро — два обличчя: бібліотека, на якій виросла оболонка

Тут ми пишемо мережевий засіб один раз, а віддаємо його двічі: ядром без власного циклу — для тих, хто вже має свій, — і тонкою оболонкою `run()` поверх того самого ядра, щоб простий випадок лишався на п'ять рядків. Робочий код на C++ показує, які саме чотири речі ядро мусить уміти сказати чужому циклу, а розбір пасток — чому оболонка, у якій завелося власне знання про справу, перетворює «бібліотечне обличчя» на обіцянку, якої не дотримано.

<preknowlist>
- [Цикл подій](book:programming/event-loop) — цикл, що чекає на джерела подій і роздає їх обробникам; усе нижче — про код, який мусить уміти жити всередині будь-якого такого циклу, свого чи чужого.
- [Блокувальний і неблокувальний ввід-вивід](book:programming/blocking-vs-nonblocking-io) — різниця між «чекати всередині виклику» і «спитати й негайно повернутися»; ядро без власного циклу може бути тільки другим.
- [Інтерфейс сокетів](book:programming/socket-api) — дескриптор, `poll` і та обставина, що «готовий до читання» ще не означає «дані точно є».
- [Монотонний час і час на стіні](book:programming/monotonic-vs-wall-time) — строки рахують за монотонним годинником, бо стінний може стрибнути назад і провалити всі дедлайни одразу.
</preknowlist>

## Задача

Треба перевірити, чи живі кілька сотень вузлів. Кожному шлемо коротку UDP-датаграму й чекаємо відповіді; не відповів за 300 мс — шлемо ще раз, і так до трьох спроб; відповів — записуємо час обертання. Задача навмисно маленька, але в ній є все, через що бібліотека зазвичай і відрощує собі цикл: багато дескрипторів одночасно, строки, повтори, скасування й наслідки, які треба комусь віддати.

Спокуса написати це каркасом велика: `ping_all(hosts, on_result)` — один виклик, усередині цикл, назовні гарний приклад у README. Але тоді той, чия програма вже має власний цикл — малює вікно, обслуговує вебсокети, крутить `epoll` під сотнею з'єднань, — не може взяти цей код узагалі. Тому ядро пишемо так, щоб воно не чекало **ніде і ніколи**, а лише вміло відповісти на питання чужого циклу.

Питань цих рівно чотири, і вони не залежать ні від задачі, ні від мови:

```
1. Що мені зараз зробити?              →  step()
2. Коли мене розбудити, якщо нічого не станеться?   →  next_deadline()
3. На яких дескрипторах і чого я чекаю? →  watches()
4. Що вже сталося, забери наслідок      →  take_event()
```

Перше й четверте — це робота й наслідки. Друге й третє — це рівно те, з чого будь-який цикл складає свій виклик очікування: набір дескрипторів і час, довше за який спати не можна. Ядро, яке вміє відповісти на всі чотири, вставляється в будь-який цикл — свій, чужий, однопотоковий, віконний, — не знаючи про нього нічого.

## Контракт ядра

Ось увесь публічний бік. Код — C++20 і POSIX; на Windows `poll` заміниться на `WSAPoll`, решта лишиться.

```cpp
// probe.hpp — ЯДРО. Жодного циклу, жодного sleep, жодного poll усередині.
#pragma once
#include <chrono>
#include <cstdint>
#include <optional>
#include <span>
#include <string>
#include <netinet/in.h>

namespace probe {

using Clock = std::chrono::steady_clock;
using Id    = std::uint64_t;

enum class Status { replied, timed_out, canceled, failed };

struct Event {
    Id                        id;
    Status                    status;
    std::chrono::milliseconds rtt{0};        // важить лише для replied
    int                       err  = 0;      // errno, важить лише для failed
    void*                     tag  = nullptr;// те, що дав викликач у add()
};

struct Watch { int fd; bool want_read; bool want_write; };

class Core {
public:
    Core(std::chrono::milliseconds rto, int tries);   // rto > 0
    ~Core();                                          // закриє всі свої дескриптори

    // Годинник ядро НЕ читає саме — час приходить аргументом.
    Id   add(Clock::time_point now, const sockaddr_in& to,
             std::string payload, void* tag = nullptr);
    void cancel(Id id) noexcept;        // подія canceled прийде однаково
    void cancel_all() noexcept;

    // ── чотири відповіді чужому циклові ──
    void step(Clock::time_point now, std::span<const int> ready) noexcept;
    std::optional<Clock::time_point> next_deadline() const noexcept;
    std::span<const Watch>           watches() const;      // може виділити пам'ять
    std::uint64_t watch_generation()  const noexcept;      // змінилось — перечитай watches()

    std::optional<Event> take_event() noexcept;
    std::size_t          active() const noexcept;
};

} // namespace probe
```

Дві риси цього заголовка варті окремої уваги, бо саме вони роблять ядро придатним до чужого циклу, а не просто «без `run()`».

**Ядро не читає годинник.** `now` приходить аргументом у `add` і в `step`. Це не педантизм: чужий цикл уже прокинувся й уже знає, котра година, — читати годинник удруге означає отримати трохи інший час, ніж той, за яким ухвалено рішення спати. А ще саме через це ядро тестується без жодного `sleep`: у тесті `now` рухають руками на 301 мс уперед і перевіряють, що пішла друга спроба. Ядро, яке кличе `Clock::now()` усередині, такого тесту не має.

**Наслідки — черга, а не дзвінок.** `step()` нікого не гукає; він лише кладе `Event` у чергу, а забирає їх `take_event()` — уже після того, як `step()` повернувся. Ця дрібниця виглядає незручністю, а насправді знімає цілий клас поламок; чому саме — нижче, у пастці про повторний вхід.

> 🔧 **Навіщо це.** Коли пишеш власне ядро, перевір заголовок трьома питаннями, і всі три — про те, чого в ньому **немає**. Чи є десь усередині `sleep`, `poll`, `select` або власний потік — тобто чи ядро чекає само? Чи кличе воно годинник, чи бере час аргументом? Чи гукає воно обробник із середини своєї роботи? Три «ні» означають, що поверх цього можна написати будь-яку оболонку; хоч одне «так» — і оболонка вже є, просто вона вросла в ядро й називається інакше.

## Нутрощі: де живе рішення «коли»

Приватна частина того самого класу — і три функції, у яких ядро вирішує, що робити.

```cpp
private:
    struct Req {
        int               fd;
        std::string       payload;
        int               left;          // скільки спроб іще лишилось
        void*             tag;
        Clock::time_point sent_at;
        std::multimap<Clock::time_point, Id>::iterator timer;
    };

    void send_probe(Id id, Req& r, Clock::time_point now) noexcept;
    void finish(Id id, Req& r, Status st, int err,
                std::chrono::milliseconds rtt) noexcept;
    void touch_watches() noexcept { ++generation_; watches_dirty_ = true; }

    std::chrono::milliseconds rto_;
    int                       tries_;
    Id                        last_id_ = 0;
    std::unordered_map<Id, Req>          reqs_;
    std::unordered_map<int, Id>          by_fd_;
    std::multimap<Clock::time_point, Id> timers_;   // упорядкований за строком
    std::deque<Event>                    events_;
    mutable std::vector<Watch>           cache_;
    mutable bool                         watches_dirty_ = true;
    std::uint64_t                        generation_    = 0;
```

`timers_` упорядкований за часом, тож найближчий строк — це завжди `timers_.begin()`. Кожен запит тримає ітератор на свій запис, тому перепланування — це стерти й вставити, без пошуку.

```cpp
// probe.cpp
Id Core::add(Clock::time_point now, const sockaddr_in& to,
             std::string payload, void* tag)
{
    const Id id = ++last_id_;                       // id ніколи не повторюється
    int fd = ::socket(AF_INET, SOCK_DGRAM | SOCK_NONBLOCK, 0);  // Linux;
                        // на macOS — окремим fcntl(fd, F_SETFL, O_NONBLOCK)
    if (fd < 0 || ::connect(fd, reinterpret_cast<const sockaddr*>(&to), sizeof to) < 0) {
        if (fd >= 0) ::close(fd);
        events_.push_back(Event{id, Status::failed, {}, errno, tag});
        return id;                 // id виданий, і подія за ним уже лежить у черзі
    }
    auto [it, _] = reqs_.emplace(id, Req{fd, std::move(payload), tries_,
                                         tag, now, timers_.end()});
    by_fd_[fd] = id;
    touch_watches();
    send_probe(id, it->second, now);
    return id;
}

void Core::send_probe(Id id, Req& r, Clock::time_point now) noexcept
{
    const ssize_t n = ::send(r.fd, r.payload.data(), r.payload.size(), 0);
    if (n < 0 && errno != EAGAIN && errno != EWOULDBLOCK && errno != EINTR) {
        finish(id, r, Status::failed, errno, {});
        return;
    }
    r.sent_at = now;                 // EAGAIN тут рахуємо за втрачений пакет:
    --r.left;                        // повторна спроба однаково прийде за строком
    r.timer = timers_.emplace(now + rto_, id);
}
```

`connect` на UDP-сокеті — не церемонія, а спосіб отримувати помилки. Приєднаний сокет приймає відповіді лише від своєї цілі, а ICMP-відмову «порт недосяжний» ядро операційної системи віддає застосункові як `ECONNREFUSED` на наступній дії з сокетом. Linux, за вимогою RFC 1122, віддає такі відкладені помилки навіть неприєднаному сокетові; чимало інших стеків, похідних від BSD, — лише приєднаному, тож `connect` тут ще й про переносність.

Тепер сам крок. Він робить рівно дві речі: читає те, що вже прийшло, і чіпає те, чий строк вийшов.

```cpp
void Core::step(Clock::time_point now, std::span<const int> ready) noexcept
{
    // 1. дескриптори, які викликач побачив готовими
    for (int fd : ready) {
        const auto f = by_fd_.find(fd);
        if (f == by_fd_.end()) continue;          // не наш дескриптор — мовчки повз
        const Id id = f->second;
        Req& r = reqs_.at(id);

        char buf[1500];
        const ssize_t n = ::recv(r.fd, buf, sizeof buf, 0);
        if (n < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK || errno == EINTR) continue;
            finish(id, r, Status::failed, errno, {});   // сюди приходить ECONNREFUSED
            continue;
        }
        const auto rtt =
            std::chrono::duration_cast<std::chrono::milliseconds>(now - r.sent_at);
        finish(id, r, Status::replied, 0, rtt);
    }

    // 2. те, чий строк уже настав
    while (!timers_.empty() && timers_.begin()->first <= now) {
        const Id id = timers_.begin()->second;
        Req& r = reqs_.at(id);
        timers_.erase(timers_.begin());
        r.timer = timers_.end();

        if (r.left > 0) send_probe(id, r, now);            // ще одна спроба
        else            finish(id, r, Status::timed_out, 0, {});
    }
}

void Core::finish(Id id, Req& r, Status st, int err,
                  std::chrono::milliseconds rtt) noexcept
{
    events_.push_back(Event{id, st, rtt, err, r.tag});  // спершу дочитати все з r
    if (r.timer != timers_.end()) timers_.erase(r.timer);
    by_fd_.erase(r.fd);
    ::close(r.fd);
    touch_watches();
    reqs_.erase(id);            // ↓ нижче цього рядка посилання r мертве
}

std::optional<Clock::time_point> Core::next_deadline() const noexcept
{
    if (timers_.empty()) return std::nullopt;   // строку немає взагалі
    return timers_.begin()->first;
}
```

Другий цикл у `step()` завершується тільки тому, що `rto_ > 0`: `send_probe` вставляє новий строк на `now + rto_`, і той уже не менший за `now`. З нульовим `rto_` цей `while` крутився б вічно — тому нуль забороняє конструктор, а не документація.

`finish()` позначено `noexcept`, і єдине місце в ньому, де може забракнути пам'яті, — додавання події в чергу. Це свідомий вибір: у середовищі без винятків черга робиться кільцем сталого розміру, місце в якому виділяє `add()`, і тоді `step()` не виділяє пам'ять взагалі.

## Обличчя перше: цикл твій

Ядро готове. Ось як ним користується той, у кого вже є власний цикл, — і саме заради цього читача ядро писалося без `run()`.

```cpp
// probe.hpp, поруч із Core: помічник потрібен обом обличчям.
inline int ms_until(Clock::time_point when, Clock::time_point now) noexcept
{
    if (when <= now) return 0;
    const auto ms =
        std::chrono::duration_cast<std::chrono::milliseconds>(when - now).count();
    // +1, бо duration_cast відкидає дробову частину: за 0.4 мс до строку
    // без нього вийшов би timeout = 0 і цикл почав би крутитися вхолосту.
    return static_cast<int>(std::min<long long>(ms + 1, 1000));
}

// ── твій головний цикл; ядро тут — звичайна бібліотека ──
std::vector<pollfd> pfds;
std::vector<int>    ready;
std::uint64_t       seen_gen  = ~0ull;
std::size_t         core_base = 0;

while (running) {
    if (core.watch_generation() != seen_gen) {   // набір ядра змінився
        pfds.clear();
        my_own_fds(pfds);                        // спершу СВОЇ дескриптори
        core_base = pfds.size();                 // далі — суцільним шматком ядрові
        for (const probe::Watch& w : core.watches()) {
            pollfd p{};
            p.fd     = w.fd;
            p.events = static_cast<short>((w.want_read  ? POLLIN  : 0) |
                                          (w.want_write ? POLLOUT : 0));
            pfds.push_back(p);
        }
        seen_gen = core.watch_generation();
    }

    const auto now  = probe::Clock::now();
    auto       wake = my_next_deadline();        // std::optional, твій власний строк
    if (auto d = core.next_deadline(); d && (!wake || *d < *wake)) wake = d;
    const int timeout = wake ? ms_until(*wake, now) : 1000;

    if (::poll(pfds.data(), static_cast<nfds_t>(pfds.size()), timeout) < 0) {
        if (errno == EINTR) continue;
        break;
    }

    ready.clear();
    for (std::size_t i = core_base; i < pfds.size(); ++i)
        if (pfds[i].revents) ready.push_back(pfds[i].fd);

    core.step(probe::Clock::now(), ready);              // увесь крок ядра
    while (auto ev = core.take_event()) on_result(*ev); // наслідки — поза кроком

    my_own_work(pfds);                                  // а тут — твої власні справи
}
```

Дві дрібниці в цьому циклі коштують більше, ніж здається.

**Ядрові — суцільний шматок масиву.** Дескриптори ядра лежать хвостом, від `core_base` до кінця, тому зібрати список готових — це прохід по відомому відтинку, без жодного пошуку «а чий це дескриптор». Так само робить кожен, хто зшиває кілька джерел в одному `poll`.

**Строк — ближчий із двох.** Твій дедлайн і дедлайн ядра змагаються, і виграє менший. Коли `next_deadline()` не повертає нічого — ядру зараз нема чого чекати, — спимо не вічно, а обмежену тривалість. Це не забобон: та сама обережність записана в документації libcurl, де `curl_multi_timeout()` віддає `-1` як «строку не збережено», і поруч стоїть пряме застереження не чекати надто довго — «більш ніж кілька секунд, мабуть» — перш ніж покликати бібліотеку знову.

## Обличчя друге: цикл віддано оболонці

Тепер найголовніше в усій конструкції: оболонка пишеться **окремим файлом, самим лише публічним заголовком ядра**. Вона не заглядає в `probe.cpp`, не має друзів і не тримає нічого, крім свого циклу.

```cpp
// probe_run.hpp — ОБОЛОНКА. Нічого, крім циклу.
#pragma once
#include "probe.hpp"
#include <exception>
#include <poll.h>
#include <vector>

namespace probe {

template <class OnEvent>
void run(Core& core, OnEvent&& on_event)
{
    std::vector<pollfd> pfds;
    std::vector<int>    ready;
    std::uint64_t       seen_gen = ~0ull;
    std::exception_ptr  escaped;

    while (!escaped && core.active() > 0) {
        if (core.watch_generation() != seen_gen) {
            pfds.clear();
            for (const Watch& w : core.watches()) {
                pollfd p{};
                p.fd     = w.fd;
                p.events = static_cast<short>(POLLIN);
                pfds.push_back(p);
            }
            seen_gen = core.watch_generation();
        }

        const auto now = Clock::now();
        const auto d   = core.next_deadline();
        const int  timeout = d ? ms_until(*d, now) : 1000;

        if (::poll(pfds.data(), static_cast<nfds_t>(pfds.size()), timeout) < 0) {
            if (errno == EINTR) continue;
            break;
        }

        ready.clear();
        for (const pollfd& p : pfds)
            if (p.revents) ready.push_back(p.fd);

        core.step(Clock::now(), ready);

        while (auto ev = core.take_event()) {
            try { on_event(*ev); }
            catch (...) { escaped = std::current_exception(); break; }
        }
    }
    // Недоставлені події лишаються В ЯДРІ: хто зловить виняток, забере їх
    // тим самим take_event(). Оболонка не ковтає нічого й не тримає нічого.
    if (escaped) std::rethrow_exception(escaped);
}

} // namespace probe
```

І весь простий випадок:

```cpp
std::vector<Host> hosts = load_hosts();          // живе довше за цикл
probe::Core core{std::chrono::milliseconds{300}, 3};

const auto t0 = probe::Clock::now();
for (Host& h : hosts) core.add(t0, h.addr, "ping", &h);

probe::run(core, [](const probe::Event& e) {
    const Host& h = *static_cast<const Host*>(e.tag);
    std::printf("%-20s %-10s %lld мс\n", h.name.c_str(), name(e.status),
                static_cast<long long>(e.rtt.count()));
});
```

Шість рядків проти тридцяти — рівно те, заради чого оболонки й пишуть. Але зверни увагу, чого в цих шести рядках **нема**: жодної можливості, якої не було б у попередніх тридцяти. Оболонка не додала здатностей, вона лише склала виклики в порядку, який усе одно однаковий у дев'яти випадках із десяти.

Посередині — одне ядро з шістьма публічними методами, до яких обидві колонки звертаються однаково; знизу підпис, що оболонку можна написати ззовні самим лише заголовком](/book/programming/software-design/framework-vs-library/img/two-faces.svg)

*Оболонка — це не шар над ядром, а звичайний його користувач. Поки її можна написати ззовні, обидва обличчя рівносильні; щойно не можна — бібліотечне обличчя неповне, і той, кому потрібен власний цикл, упреться в стіну.*

## Прецедент: те саме в libcurl

Ця конструкція не вигадана заради прикладу. libcurl роками возить ту саму пару, і його назви кладуться на наші майже один в один:

| тут | libcurl |
| --- | --- |
| `Core` | множинний дескриптор `CURLM` |
| `add()` | `curl_multi_add_handle()` |
| `cancel()` | `curl_multi_remove_handle()` |
| `step(now, ready)` | `curl_multi_perform()` |
| `next_deadline()` | `curl_multi_timeout()` |
| `watches()` | `curl_multi_fdset()` |
| `take_event()` | `curl_multi_info_read()` |
| `active()` | лічильник `running_handles` |
| `run()` | `curl_easy_perform()` |

Останній рядок — не аналогія, а буквальний факт, записаний у власних матеріалах проєкту curl: `curl_easy_perform()` є обгорткою, яка всередині сама налаштовує й уживає множинний інтерфейс. Тобто «просте обличчя» libcurl — це саме оболонка, написана поверх бібліотечного, і саме тому воно не могло розійтися з ним у можливостях: там нема чому розходитися.

Збігається й `take_event()`: `curl_multi_info_read()` віддає по одному повідомленню про завершені перенесення, доки черга не спорожніє, — застосунок розбирає їх сам, коли `curl_multi_perform()` уже повернувся.

## Чотири пастки

### 1. Оболонка завела власне знання про справу

Це та пастка, через яку конструкція гниє непомітно. Виглядає вона завжди зручно:

```cpp
// ХИБНА оболонка: свій обробник на кожен запит.
template <class OnEvent>
class Runner {
    probe::Core&                           core_;
    std::unordered_map<probe::Id, OnEvent> handlers_;   // ← знання про СПРАВУ
    std::unordered_map<probe::Id, std::string> names_;  // ← і ще одне
public:
    void probe_host(const std::string& name, sockaddr_in to, OnEvent h) {
        const auto id = core_.add(probe::Clock::now(), to, "ping");
        handlers_.emplace(id, std::move(h));            // ядро про це не знає
        names_.emplace(id, name);                       // і про це теж
    }
};
```

Тут усе працює й навіть подобається — доки хтось не візьме бібліотечне обличчя. А він отримає голий `Id` і нічого більше: щоб зв'язати наслідок із запитом, йому доведеться завести ту саму пару словників власноруч. Це ще півбіди. Біда починається, коли в оболонці оселяється не супровідний хвостик, а рішення: скільки разів повторювати, кого пропустити, коли здатися. Тоді два обличчя перестають бути обличчями одного ядра — оболонка робить одне, ядро вміє інше, і той, кому потрібен власний цикл, отримує не «те саме без циклу», а урізаний засіб.

Лікування — розділити стан за строком життя. **Стан справи** — усе, що переживає одну ітерацію циклу: супровідні дані запиту, лічильник спроб, строки, наслідки — живе в ядрі; звідси й `void* tag`, який повертається у події. **Стан циклу** — масив `pollfd`, позначка генерації, буфер готових, `exception_ptr` — може жити в оболонці, бо вмирає разом із нею й будь-якої миті відновлюється з ядра.

Перевірка коротка й безжальна: **чи можна написати оболонку в окремому файлі, маючи самий лише публічний заголовок?** Якщо так — обличчя рівносильні, і це доведено самим фактом. Якщо ні — «бібліотечне обличчя» є на папері, а на ділі є один каркас із зайвим заголовком.

### 2. Помилка, яку треба винести з чужого циклу

Помилки тут ідуть у два боки, і обидва напрямки перетинають чужі кадри стека.

**Знизу вгору — помилки ядра.** У бібліотечному обличчі `step()` кличуть із середини чужого циклу, часом просто з обробника простою віконного каркаса, написаного на C. Виняток, кинутий крізь кадри C-коду, у найкращому разі поводиться так, як домовився компілятор, а зазвичай завершує процес; чужий цикл, крізь який він пролетів, лишається з наполовину зробленою ітерацією. Тому `step()`, `next_deadline()`, `take_event()` і `cancel()` позначені `noexcept`, а кожна поламка — і невдалий `socket()`, і `ECONNREFUSED` від ICMP — стає значенням: `Status::failed` плюс `errno` у події. [Помилка як значення](book:programming/error-handling) — це не питання смаку, коли між тобою й твоїм викликачем стоять чужі кадри: значення переживає таку дорогу, розкрутка стека — ні.

**Згори вниз — виняток із обробника.** В оболонці обробника кличе `run()`, і його виняток летить крізь кадри `run()`. Випустити його просто так означає обірвати ітерацію посередині: масиви `run()` приберуться самі, а от запити лишаться відкритими, черга подій — недорозібраною. Звідси зразок із `exception_ptr`: зловити, зупинити цикл, кинути далі **після** виходу з нього. Недоставлені події при цьому свідомо лишаються в ядрі, а не гинуть в оболонці, — тож той, хто зловив, забирає їх тим самим способом:

```cpp
try {
    probe::run(core, on_event);
} catch (...) {
    while (auto ev = core.take_event()) log_undelivered(*ev);  // нічого не втрачено
    core.cancel_all();
    while (auto ev = core.take_event()) log_undelivered(*ev);
    throw;
}
```

А якщо оболонку віддають назовні через C-інтерфейс, винятки не сміють перетинати межу взагалі: обробник повертає код, `run()` віддає перший ненульовий, і жодного `throw` у сигнатурах.

### 3. Скасування й порядок згасання

**Кожен `Id`, який увійшов, мусить вийти рівно раз.** Тому `cancel()` не викидає запит мовчки, а кладе подію `canceled`. Інакше словник «`Id` → мій контекст» у користувача тихо тече: записи, за якими ніколи не прийде наслідок, нікому й ніколи не видалити. З того самого правила випливає й друге: `cancel()` уже завершеного `Id` — не помилка, а порожня дія (подія за ним пішла раніше), і саме тому лічильник `Id` монотонний і ніколи не повторює номерів. Скасування тут негайне лише тому, що для UDP закрити сокет достатньо; ядро, якому треба ще й сказати «скасовано» по мережі, віддає подію пізніше — і тоді `cancel()` стає [проханням, а не вбивством](book:programming/cooperative-cancellation).

**Номери дескрипторів повторюються, і це найпідступніше.** `finish()` закриває дескриптор, а операційна система віддає той самий номер наступному, хто попросить, — можливо, у тій самій ітерації й зовсім іншій частині програми. Якщо в масиві `pollfd` викликача досі лежить старий номер, він чекатиме на чужий сокет і принесе його готовність назад у `step()`. Тому набір спостережуваних дескрипторів має **версію**: `watch_generation()` збільшується на кожному `add`, `cancel` і завершенні, а викликач перечитує `watches()`, щойно версія змінилася. І тому ж у контракті записано, що набір міняється **тільки** всередині `add()`, `cancel()` і `step()`: власного потоку в ядра немає, отже, за спиною викликача він не зміниться ніколи.

**Порядок згасання — один, і він не той, що спадає на думку.** Спершу перестати додавати нове, потім `cancel_all()`, потім розібрати чергу до кінця, і аж тоді руйнувати `Core`, а після нього — масиви циклу. Зворотний порядок псує тихо: зруйнувати ядро першим — загубити події, які вже сталися, але ще не забрані; зруйнувати масиви першим — лишити відкриті дескриптори й `poll` по сміттю. Деструктор `Core` закриває свої дескриптори й викидає нерозібрані події — це остання лінія, а не спосіб гасити ([акуратне згасання](book:programming/graceful-shutdown) тим і відрізняється від виходу, що наслідки встигають дійти до того, хто їх чекав).

### 4. Повторний вхід в обробник

Уяви на мить, що `step()` гукав би обробник просто там, де завершується запит. Обробник цілком природно робить `core.cancel(other)` — скажімо, «перший відповів, решту не питаємо». І тоді `cancel()` кличе `finish()`, який стирає запис із `reqs_` і `timers_`, — а `step()` саме зараз тримає посилання `Req& r` і перебирає `timers_` зсередини свого `while`. Посилання висить у повітрі, ітератор указує в стерте, і поламка вилазить не одразу, а під навантаженням, коли скасування збігається із завершенням.

![Згори: цикл гукає step(), step() гукає твій обробник, обробник кличе cancel() — і стрілка вертається назад у step(), який саме обходить свої контейнери. Знизу: step() лише кладе події в чергу й повертається, далі власник циклу кличе take_event() і вже звідти — обробник, який вільно кличе cancel() і add()](/book/programming/software-design/framework-vs-library/img/event-queue.svg)

*Черга подій прибирає не окрему поламку, а саму можливість повторного входу: коли обробник працює, ядро вже не всередині свого обходу.*

Звичні латки нічого не лікують. Прапорець «я всередині `step()`» плюс відкладена черга команд переносить складність у ядро — і додає стан, за яким треба стежити. Рядок у документації «не кличте нас із обробника» — це контракт, який ніхто не читає до першої нічної поламки, і [повторний вхід](book:programming/reentrancy) тут особливо злий тим, що нормальний код виглядає нормально рівно доти, доки не збіглися дві події.

Черга знімає питання цілком. `step()` чіпає тільки свої контейнери й повертається; обробник працює тоді, коли ядро в спокої, і має право робити з ним що завгодно. Задарма з цього виходить ще й зчеплення робіт: обробник, який кличе `core.add()` для наступної перевірки, просто продовжує цикл — бо умова в `run()` дивиться на `core.active()`, а воно щойно знову стало ненульовим.

## Чого це коштує

Складність написаного вище — не про красу, а про те, чи витримає ця пара тисячі запитів.

```
next_deadline()      O(1)          — timers_.begin()
перепланування       O(log n)      — стерти + вставити в multimap
step(now, ready)     O(k + m·log n) — k готових дескрипторів, m дозрілих строків
```

Головне тут — чого немає: ані `next_deadline()`, ані `step()` не перебирають усі запити. Наївне ядро робить саме це — шукає найближчий строк проходом по всіх записах і пробує `recv()` на кожному дескрипторі, — і ціна виглядає так:

**Умова.** 10 000 запитів, цикл прокидається 1 000 разів на секунду, системний виклик коштує ≈ 0.3 мкс.

```
наївне ядро:  пошук строку  = 10 000 порівнянь × 1 000/с = 10⁷ порівнянь/с
              крок          = 10 000 марних recv() × 1 000/с = 10⁷ syscall/с
              лише на syscall: 10⁷ × 0.3 мкс = 3 с процесора на 1 с часу

ядро з чергою: пошук строку = 1 порівняння × 1 000/с      = 10³ порівнянь/с
              крок          = стільки recv(), скільки poll назвав готовими
```

**Висновок.** Наївний варіант не «повільніший» — він фізично не встигає: три секунди процесорного часу на кожну секунду роботи означають, що цикл відстає назавжди. Саме тому ядро тримає строки впорядкованими, а готовність дескрипторів приймає ззовні готовим списком, а не з'ясовує сама.

Лишається одне слабке місце — `watches()`: він перебудовує весь набір після кожної зміни, тобто O(n) на кожен завершений запит, а це O(n²) на пачку. Ліки — та сама конструкція поверхом нижче: замість «ось увесь мій набір» ядро повідомляє **різницю** — «почни стежити за дескриптором X на читання», «перестань за Y», — а замість `step(now, ready)` приймає по одному дескриптору за раз. Це рівно те, що в libcurl зветься `curl_multi_socket_action()` разом із зворотними викликами `CURLMOPT_SOCKETFUNCTION` і `CURLMOPT_TIMERFUNCTION`; у документації curl прямо сказано, що звичайні інтерфейси марнують забагато часу на перебирання всіх сокетів, і що саме подієвий варіант дозволяє масштабуватися за тисячі одночасних перенесень. Два обличчя й тут: дешеве та просте — і дороге у вжитку, зате масштабне.

І останнє, найдешевше на слух і найдорожче в наслідках: один сокет на запит означає, що межа — це `RLIMIT_NOFILE`, а `poll` усередині ядра системи проходить увесь масив дескрипторів на кожен виклик, тож за кілька тисяч його міняють на `epoll` чи `kqueue`. Але зверни увагу, **чиє** це рішення. Не ядра. Ядро роздає дескриптори й строки, а обирати спосіб чекати — справа того, хто володіє циклом. Саме тому в `probe.hpp` немає жодної згадки ні про `epoll`, ні про `io_uring`, ні про головний контекст GLib, ні про обробник простою віконного каркаса: ядро, яке не чекає, не мусить знати жодного зі способів чекання — і через це його можна вставити в них усі.
