# ⚙️ Два господарі одного циклу: як зчепити GLUT із libcurl і скільки це коштує

У процесі є одне вікно, один потік і два шматки чужого коду, кожен з яких хоче крутити цикл сам: віконний каркас і мережевий рушій. Тут — три способи звести їх докупи, з робочим кодом і з чесним рахунком, скільки кожен коштує в пробудженнях процесора й у затримці на прибулі байти.

**Задача.** Застосунок на freeglut малює мапу; плитки мапи тягнемо з мережі через `libcurl` у множинному інтерфейсі. Три вимоги, і всі три звичайні: вікно реагує на мишу в межах кадру; плитка з'являється щойно прийшли її байти; коли нічого не відбувається, застосунок не гріє процесор. Заважає одна обставина: `glutMainLoop()` не повертається, а `libcurl` теж хоче, щоб хтось безперервно давав йому ходу.

## Спершу перевір, чи бійка взагалі є

Найдешевша відповідь — та, за якої зчіплювати нічого не треба. У freeglut є `glutMainLoopEvent()`: він проганяє **одну ітерацію** віконного циклу й повертається. Тобто у freeglut, на відміну від класичного GLUT, є бібліотечне обличчя, і цикл можна забрати собі:

```c
while (running) {
    glutMainLoopEvent();                 // одна порція віконних подій
    curl_multi_perform(multi, &n);       // одна порція мережі
}
```

Три рядки, обидва каркаси задоволені, ніхто не володіє циклом, крім тебе. І цей цикл **спалює ціле ядро процесора**, бо ніде не спить: обидва виклики повертаються негайно, а `while` крутиться так швидко, як уміє.

Ось де насправді проходить лінія бою. Тіло циклу — дешеве й ділиться скільки завгодно: гукнути двох по черзі можна завжди. Неподільне — це **сон**: єдиний виклик, у якому потік лежить у ядрі системи й нічого не робить, доки щось не станеться. У процесі є рівно одне місце, де потік спить, і саме за нього змагаються каркаси. Питання «хто володіє циклом» — це насправді питання **«хто спить, і чи знає він, чого чекає другий»**.

> 🔧 **Навіщо це.** Коли зчіплюєш два каркаси, не питай «чий `run()` головніший». Знайди в кожному те місце, де потік засинає (`epoll_wait`, `poll`, `XNextEvent`, `WaitMessage`, `curl_multi_poll`), і спитай про кожен: що його будить і як йому розповісти про чужі джерела. Відповідь на це питання й визначає, який із трьох способів нижче тобі доступний — а не смаки й не архітектурна краса.

Механізм, про який ідеться, — [цикл подій](book:programming/event-loop): нескінченний оберт, що чекає на джерела подій і роздає їх обробникам. Уся його вартість зосереджена в одному виклику — тому, у якому він чекає; саме той виклик вирішує, скільки процесор спить і як швидко програма відповідає.

![Три ряди-часові осі. Ряд перший: господар прокидається за таймером через рівні проміжки, дані приходять між тиками й помічені аж на наступному — затримка до одного періоду. Ряд другий: гість у власному потоці прокидається рівно на прибуття даних, а господар дізнається про це на найближчому черпанні черги. Ряд третій: жодного тика, один сон, пробудження рівно в мить прибуття даних](img/two-loops-sleep.svg)

*Три способи — це три відповіді на питання, хто спить. Від відповіді напряму залежать дві величини: скільки разів за секунду процесор виводиться зі стану спокою і скільки байти чекають, поки їх помітять.*

## Спосіб 1: гість крокує в простої господаря

У GLUT є обробник простою — функція, яку віконний цикл кличе, коли в черзі немає жодної події. Виглядає як ідеальне гніздо для чужої роботи:

```c
static CURLM *multi;

static void reap_finished(void) {
    CURLMsg *m;
    int left;
    while ((m = curl_multi_info_read(multi, &left))) {
        if (m->msg != CURLMSG_DONE) continue;
        CURL *e = m->easy_handle;
        char *priv = NULL;
        curl_easy_getinfo(e, CURLINFO_PRIVATE, &priv);
        tile_ready((struct Tile *)priv, m->data.result);   // тут можна чіпати вікно
        curl_multi_remove_handle(multi, e);
        curl_easy_cleanup(e);
    }
}

static void on_idle(void) {
    int running;
    curl_multi_perform(multi, &running);   // повертається негайно, навіть коли роботи нема
    reap_finished();
}

int main(int argc, char **argv) {
    /* ...glutInit, glutCreateWindow, curl_global_init, multi = curl_multi_init()... */
    glutIdleFunc(on_idle);
    glutMainLoop();
}
```

Це працює — і це найгірша річ, яку можна зробити з ноутбуком користувача. Обробник простою кличуть **не «зрідка, коли нічого не відбувається»**, а безперервно: щойно черга подій порожня, цикл гукає його знову й знову, мільйони разів за секунду. Такий цикл ніде не спить, тож процесор весь час зайнятий на сто відсотків одного ядра — і байдуже, чи є хоч один активний перенос. Це класичне [зайняте очікування](book:programming/polling-vs-events) — спосіб дізнатися про подію, перепитуючи джерело замість того, щоб чекати сигналу від нього; він завжди міняє енергію на затримку, і в обробнику простою міняє її за найгіршим курсом.

Лікують це так: викидають обробник простою й ставлять на його місце **таймер**, який сам себе переставляє, а період беруть у гостя.

```c
#define CAP_MS 16                          // стеля затримки: один кадр 60 Гц

static int gen = 0;                        // мітка покоління таймера
static void tick(int my_gen);

static void arm(void) {
    long ms = -1;
    curl_multi_timeout(multi, &ms);        // −1 → свого дедлайну в libcurl зараз нема
    if (ms < 0 || ms > CAP_MS) ms = CAP_MS;
    glutTimerFunc((unsigned)ms, tick, ++gen);
}

static void tick(int my_gen) {
    if (my_gen != gen) return;             // цей таймер уже скасовано новішим
    int running;
    curl_multi_perform(multi, &running);
    reap_finished();
    if (running > 0) arm();                // нема переносів — нема й таймера
}
```

`curl_multi_timeout` каже, скільки мілісекунд можна не турбувати бібліотеку, поки не настане **її власний** дедлайн: час на з'єднання, на розв'язання імені, на мінімальну швидкість. Значення −1 означає «зараз жодного дедлайну не заведено», і документація окремо просить не спати після цього довше за кілька секунд.

Дві дрібниці в цьому коді варті окремого слова. Мітка покоління потрібна тому, що `glutTimerFunc` **не має скасування**: раз замовлений виклик станеться обов'язково. Цілочисловий аргумент, який таймер передасть назад, — саме те місце, куди кладуть номер покоління; збільшивши `gen`, ти знеструмлюєш усі замовлені раніше таймери одним рухом. А `if (running > 0)` вимикає ланцюжок, коли переносів не лишилося: інакше застосунок із порожньою мережею все одно прокидався б 62 рази на секунду до кінця своїх днів. Відповідно, після кожного `curl_multi_add_handle` треба покликати `arm()` — саме там ланцюжок запускається знову.

**Скільки це коштує.** Тепер головне, заради чого спосіб узагалі розбирають: таймер не рятує від компромісу, він лише дає ним керувати. Таймер будить **за годинником**, а байти приходять **не за годинником**, тож про прибуття даних дізнаються не раніше найближчого тика.

```
Таймер із періодом T:
    пробуджень за секунду  = 1 / T
    затримка на прибуття   ≤ T
    добуток                = 1        ← від T не залежить

    T = 1 мс   → 1000 пробуджень/с,  затримка ≤ 1 мс
    T = 16 мс  →   62 пробудження/с, затримка ≤ 16 мс
    T = 200 мс →    5 пробуджень/с,  затримка ≤ 200 мс
```

Одну величину зменшуєш — друга рівно настільки ж росте. Це і є ціна способу, і жодним налаштуванням її не обійти: обидві цифри — наслідок того, що ми питаємо замість того, щоб чекати.

Далі варто розрізняти два різні рахунки, бо їх постійно плутають. Процесорний час на самі виклики мізерний, а от **пробудження** — ні:

```c
/* Скільки коштує один порожній крок — виміряй у себе, не вір оцінкам. */
struct timespec a, b;
int running, N = 200000;
clock_gettime(CLOCK_MONOTONIC, &a);
for (int i = 0; i < N; i++) curl_multi_perform(multi, &running);
clock_gettime(CLOCK_MONOTONIC, &b);
printf("%.3f мкс на виклик\n",
       ((b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec)) / N / 1000.0);
```

```
Нехай порожній крок вийшов ≈ 0.4 мкс, один активний перенос:
    T = 16 мс → 62 · 0.4 мкс = 25 мкс за секунду = 0.0025 % ядра

Тобто в колонці «% CPU» цього не видно взагалі.
Видно інше: 62 виходи процесора зі стану спокою за секунду —
у диспетчері задач їх не видно, у витраті батареї — видно.
Міряють їх не профайлером, а лічильником пробуджень (powertop і подібні).
```

Звідси випливає найкорисніший практичний висновок про цей спосіб: **він безплатний рівно тоді, коли господар і так прокидається**. Якщо вікно малює анімацію на 60 кадрів за секунду, воно вже будить процесор 60 разів на секунду — і крок мережі, вкладений у той самий кадр, не додає жодного пробудження, а затримку обмежує один кадр, якого око не бачить. Саме тому в іграх спосіб 1 не просто прийнятний, а правильний. І саме тому в застосунку, що більшість часу нерухомо стоїть на екрані, він найгірший з усіх трьох.

## Спосіб 2: гість живе у власному потоці

Наступна ідея очевидна: якщо єдиний сон на двох не ділиться, дай кожному свій потік — хай кожен спить своїм сном. Гість дістає власний потік і повне право блокуватися скільки треба; господар лишається з вікном і нічого про мережу не знає. Єдина точка зустрічі — черга готових результатів.

```cpp
struct Done { long id; CURLcode code; std::string body; };

class Fetcher {
public:
    void start() { th_ = std::thread([this] { loop(); }); }

    void stop() {
        stop_.store(true, std::memory_order_relaxed);
        curl_multi_wakeup(multi_);          // єдиний спосіб урвати чужий сон ззовні
        th_.join();
    }

    std::vector<Done> drain() {             // кличе ПОТІК ВІКНА
        std::vector<Done> out;
        std::lock_guard<std::mutex> g(mx_);
        out.swap(ready_);                   // лок тримаємо наносекунди
        return out;
    }

private:
    void loop() {
        while (!stop_.load(std::memory_order_relaxed)) {
            int running = 0;
            curl_multi_perform(multi_, &running);
            reap();                                             // кладе готове в ready_ під локом
            int numfds = 0;
            curl_multi_poll(multi_, nullptr, 0, 1000, &numfds);  // ТУТ потік спить
        }
    }

    CURLM *multi_;
    std::thread th_;
    std::atomic<bool> stop_{false};
    std::mutex mx_;
    std::vector<Done> ready_;
};
```

`curl_multi_poll` — це і є «бібліотечний сон» гостя: він сам збирає свої сокети, сам рахує свій найближчий дедлайн і кладе потік спати рівно до першої з двох подій. Ніякого опитування, ніякого періоду — гість реагує на байти миттєво.

А от **як розбудити господаря**, коли результат готовий, — це і є справжня ціна способу, і залежить вона не від тебе, а від того, що каркас-господар пропонує. Класичний GLUT не пропонує нічого: у ньому немає виклику «постав мені подію в чергу з іншого потоку». Тож черпати доводиться знову таймером:

```cpp
static void drain_tick(int my_gen) {
    if (my_gen != gen) return;
    for (auto &d : fetcher.drain())
        show_tile(d);                        // GL і GLUT — тільки звідси
    glutTimerFunc(16, drain_tick, ++gen);
}
```

На вигляд ми повернулися до способу 1, але виграш реальний і його варто назвати точно. По-перше, черпання порожньої черги — це захоплення мутекса й обмін двох порожніх векторів, десятки наносекунд проти повного обходу мережевого стану. По-друге, і це важливіше: **повільна мережа більше не гальмує вікно**. Розв'язання імені, що зависло на дві секунди, раніше тримало кадр — тепер воно тримає лише свій потік. Затримка ж лишилася такою самою, як у способі 1, — до одного кадру.

У каркасів, що вміють приймати посилку в свій цикл, цієї плати немає зовсім: `QMetaObject::invokeMethod(w, fn, Qt::QueuedConnection)` у Qt, `g_idle_add` у GLib, `PostMessage(hwnd, WM_APP + 1, 0, 0)` у Win32 будять цикл господаря по-справжньому — нуль пробуджень у спокої і нульова затримка передачі. Наявність такого виклику — окрема, дуже конкретна причина обирати каркас.

**Що можна й чого не можна з робочого потоку.** Це найтихіша частина способу, і порушення тут виявляються не поламкою, а рідкісним дивним збоєм.

- Один дескриптор `CURL` — один потік у кожну мить; документація libcurl забороняє користуватися тим самим дескриптором із двох потоків одночасно. Створюй і вживай дескриптори гостя тільки в його потоці, у чужий бік передавай уже готові байти.
- `curl_global_init` став потокобезпечним лише з libcurl 7.84.0 (і лише там, де `curl_version_info` показує біт `CURL_VERSION_THREADSAFE`). Клич його в `main`, до запуску будь-яких потоків, — це правильно на всіх версіях.
- Зворотний виклик запису працює **в потоці гостя**. Отже, він не сміє чіпати вікно, текстури й будь-що з контексту OpenGL: контекст належить рівно одному потокові, і виклик GL із чужого — це або тихе ніщо, або падіння. Вивантаження текстури живе на боці вікна, у `show_tile`. Ця межа — окремий випадок загального правила [винесення роботи з потоку інтерфейсу](book:programming/ui-thread-offloading): у потоці, що малює, роблять тільки коротке й неблокуюче, а все довге живе поза ним і повертається готовим результатом.
- Лок тримають рівно на обмін контейнерами й **ніколи не кличуть під ним твій код**. Обробник, який під локом перемальовує вікно, зупиняє мережевий потік на цілий кадр — а це вже не черга, а прихована зупинка мережі за розкладом кадрів.

## Спосіб 3: один сон на двох

Третій спосіб знімає компроміс замість того, щоб ним керувати: якщо гість погодиться сказати, **яких саме дескрипторів** він чекає й **коли** його розбудити за годинником, то очікування можна зробити одне на двох. У libcurl для цього є сокетний інтерфейс: два зворотні виклики, через які бібліотека повідомляє свої наміри.

```c
static int ep, tfd;                        // epoll і timerfd
static CURLM *multi;

/* libcurl: «за цим fd стеж ось на що» / «цей fd мені більше не потрібен» */
static int on_socket(CURL *easy, curl_socket_t s, int what, void *userp, void *sockp) {
    if (what == CURL_POLL_REMOVE) {
        epoll_ctl(ep, EPOLL_CTL_DEL, s, NULL);
        curl_multi_assign(multi, s, NULL);
        return 0;
    }
    struct epoll_event ev = {0};
    ev.data.fd = s;
    ev.events = ((what & CURL_POLL_IN)  ? EPOLLIN  : 0)
              | ((what & CURL_POLL_OUT) ? EPOLLOUT : 0);
    epoll_ctl(ep, sockp ? EPOLL_CTL_MOD : EPOLL_CTL_ADD, s, &ev);
    curl_multi_assign(multi, s, (void *)1);   // мітка «цей fd уже в наборі»
    return 0;
}

/* libcurl: «розбуди мене через ms мілісекунд» / «мій таймер більше не потрібен» */
static int on_timer(CURLM *m, long ms, void *userp) {
    struct itimerspec its = {0};              // усі нулі — таймер вимкнено
    if (ms >= 0) {
        if (ms == 0) ms = 1;                  // 0 = «негайно», а нуль у timerfd означає «вимкни»
        its.it_value.tv_sec  = ms / 1000;
        its.it_value.tv_nsec = (ms % 1000) * 1000000L;
    }
    timerfd_settime(tfd, 0, &its, NULL);
    return 0;
}
```

`timerfd` тут потрібен, щоб перетворити час на дескриптор: годинник, який стає готовим до читання, коли настав його момент, — і тоді єдине очікування вміє чекати і на байти, і на час однаково. Пастка з нулем справжня й коштує кількох годин: коли libcurl каже `0`, він просить кроку негайно, а нульова структура в `timerfd_settime` означає «таймер вимкнути». Один мілісекундний зсув рятує від тиші, у якій перенос просто не починається.

Далі — сам цикл. Він твій, і в ньому одне-єдине місце, де процес спить:

```c
curl_multi_setopt(multi, CURLMOPT_SOCKETFUNCTION, on_socket);
curl_multi_setopt(multi, CURLMOPT_TIMERFUNCTION, on_timer);
curl_multi_add_handle(multi, easy);

int running = 0;
curl_multi_socket_action(multi, CURL_SOCKET_TIMEOUT, 0, &running);   // перший поштовх

for (;;) {
    struct epoll_event evs[64];
    int n = epoll_wait(ep, evs, 64, -1);      // −1: спимо, доки не станеться НІЧОГО
    for (int i = 0; i < n; i++) {
        int fd = evs[i].data.fd;
        if (fd == tfd) {
            uint64_t ticks;
            read(tfd, &ticks, sizeof ticks);
            curl_multi_socket_action(multi, CURL_SOCKET_TIMEOUT, 0, &running);
        } else if (fd == ui_fd) {
            pump_ui();                        // одна ітерація циклу господаря
        } else {
            int mask = ((evs[i].events & EPOLLIN)  ? CURL_CSELECT_IN  : 0)
                     | ((evs[i].events & EPOLLOUT) ? CURL_CSELECT_OUT : 0)
                     | ((evs[i].events & EPOLLERR) ? CURL_CSELECT_ERR : 0);
            curl_multi_socket_action(multi, fd, mask, &running);
        }
    }
    reap_finished();
}
```

Читається це просто: `epoll_wait(-1)` — жодних пробуджень, поки нічого не сталося; прокинулись — дивимось, **чий саме** дескриптор став готовим, і робимо крок тому, чий він. Обидві величини з рахунку способу 1 стають найкращими можливими одночасно: нуль зайвих пробуджень і затримка, що дорівнює часу пробудження ядра. Компроміс не налаштований — його **немає**, бо ми більше нічого не питаємо, а справді чекаємо. Механіка самого очікування — у [select, poll, epoll](book:unix-linux/select-poll-epoll): один виклик, у якому потік спить на багатьох джерелах одразу, і саме він робить можливим об'єднання чужих джерел у наше очікування.

![Ліворуч libcurl віддає свої наміри двома зворотними викликами — за якими сокетами стежити й за скільки мілісекунд розбудити; нижче господар віддає свій дескриптор. Посередині все це стікається в один набір epoll: сокети гостя, timerfd гостя, дескриптор господаря. Праворуч єдиний epoll_wait без таймауту — один сон процесу, нуль пробуджень у спокої, — а після пробудження крок робить той, чий дескриптор готовий](img/two-loops-shared-wait.svg)

*Спільне очікування прибирає компроміс «пробудження проти затримки» — але тільки якщо обидві сторони згодні на нього: гість мусить віддати свої дескриптори й таймер, господар — уміти прийняти чужий дескриптор.*

**Чого цей спосіб вимагає — і чому він доступний не завжди.** Гість мусить мати сокетний інтерфейс; у libcurl він є, у закритому SDK з єдиною функцією `sdk_run()` його немає й не з'явиться. Господар мусить уміти прийняти чужий дескриптор у своє очікування — у GLib це `g_unix_fd_add`, у Qt `QSocketNotifier`, у libevent `event_new`, у власноруч написаному циклі просто `epoll_ctl`. У GLUT немає ні першого, ні другого: він не показує ані свого дескриптора, ані способу додати чужий, — і саме тому в нашій задачі з мапою третій спосіб відпадає, хоч він і найчистіший. Це, до речі, чудовий критерій вибору каркаса наперед: чи можна взагалі колись поставити його поруч із чимось іншим.

Дві платформенні деталі, які зазвичай згадують надто пізно. У X11 очікування віконного каркаса — це очікування на дескрипторі з'єднання з сервером, `ConnectionNumber(dpy)`; саме тому GTK і Qt узагалі здатні на такий трюк. А у Windows черга повідомлень — не дескриптор, тож там та сама конструкція виглядає інакше: `MsgWaitForMultipleObjects` чекає одночасно на об'єкти ядра й на повідомлення вікна, а сокети перетворюють на об'єкти через `WSAEventSelect`. Ідея одна, примітив інший.

## Три способи поруч

| | 1. крок у простої | 2. свій потік і черга | 3. один сон на двох |
|---|---|---|---|
| пробуджень у спокої | 1/T (без таймера — зайнятий цикл) | 0 | 0 |
| затримка на байти | ≤ T | ~0 у гостя, до T до вікна | ~0 |
| вимагає від гостя | крок без власного циклу | нічого | віддати fd і таймер |
| вимагає від господаря | простій або таймер | безпечну передачу в його потік | приймати чужий fd |
| повільний гість гальмує вікно | так | ні | ні |
| як ламається | забув стелю T → зайнятий цикл | порушено правило потоків → рідкісний збій | гість ховає fd → способу нема |
| клею | ~15 рядків | ~60 рядків | ~50 рядків і платформенна частина |

## Пастка порядку згасання

Спільна для всіх трьох і найдорожча, бо проявляється не одразу: гасять у порядку, **зворотному до народження**, і той, хто спить, мусить мати чим бути розбудженим. Дрібниці різні для кожного способу.

**Спосіб 1.** Перед виходом збільш `gen`, щоб замовлені таймери, які все одно спрацюють, нічого не робили. Далі — `curl_multi_remove_handle` і `curl_easy_cleanup` для кожного переносу, тільки потім `curl_multi_cleanup`. І окремо: `glutLeaveMainLoop()` поверне керування з `glutMainLoop()` лише тоді, коли ти заздалегідь поставив `glutSetOption(GLUT_ACTION_ON_WINDOW_CLOSE, GLUT_ACTION_GLUTMAINLOOP_RETURNS)`; типова ж поведінка freeglut — просто вийти з процесу, і весь твій код прибирання після `glutMainLoop()` не виконається ніколи.

**Спосіб 2.** `stop_ = true` сам по собі нічого не зупиняє: потік спить усередині `curl_multi_poll` і прапорця не бачить. Тому `curl_multi_wakeup` — не оптимізація, а необхідність; без нього `join()` чекатиме до кінця таймауту очікування, а якщо ти передав туди велике значення, то фактично назавжди. Порядок: підняти прапорець → розбудити → приєднати потік → **ще раз черпнути чергу** (результати могли лягти між останнім черпанням і зупинкою) → аж тоді знищувати об'єкти, на які вказують записи черги.

**Спосіб 3.** Тут пастка задокументована й особливо підступна: `curl_multi_cleanup()` **може покликати твій сокетний зворотний виклик**, коли закриває кешовані з'єднання. Отже, набір `epoll` мусить бути ще живий у цю мить. Правильний порядок — зняти дескриптори переносів, `curl_multi_cleanup`, і лише потім `close(tfd)` і `close(ep)`. Поміняєш два останні кроки місцями — у кращому разі дістанеш `EBADF` у зворотному виклику, у гіршому нічого не помітиш, поки та сама числова адреса дескриптора не дістанеться комусь іншому.

Спільне ім'я цього набору правил — [охайне згасання](book:programming/graceful-shutdown): припинити приймати нове, дати початому дійти до кінця або чесно його обірвати, і звільняти ресурси в порядку, зворотному до захоплення.

І останнє з пасток, спільне для першого й третього способів: **повторний вхід**. Зворотний виклик запису libcurl працює всередині `curl_multi_perform` чи `curl_multi_socket_action`, тобто всередині обробника господаря. Якщо з нього покликати щось, що знову зайде в той самий мультидескриптор, — наприклад «доволі байтів, скасуймо решту плиток» через `curl_multi_remove_handle`, — ти міняєш контейнер, який бібліотека саме обходить. Правило просте: зі зворотного виклику лише **записуй намір** у свою змінну, а виконуй його після повернення з кроку. Це загальний закон [повторного входу](book:programming/reentrancy): функція безпечна для повторного входу лише тоді, коли не спирається на стан, який може змінитися під нею з вкладеного виклику.

## Як обирати

Порядок питань, а не смаки:

1. **Чи є в когось із двох крок на одну ітерацію?** Є в господаря — забери цикл собі, і задача перетворюється на спосіб 3 (де спати вирішуєш ти) або, якщо дескрипторів не дістати, на спосіб 1 із роллю навпаки.
2. **Чи віддає гість свої дескриптори й таймер, а господар уміє їх прийняти?** Обидва «так» — бери спосіб 3 і більше про компроміс не думай.
3. **Гість непрозорий або блокується надовго?** Спосіб 2. Перевір заздалегідь, чи має господар посилку в цикл: якщо має — плати нуль, якщо ні — доплати черпанням раз на кадр.
4. **Не вийшло нічого з попереднього?** Спосіб 1 — але з таймером і зі свідомо вибраним `T`, а не з обробником простою. І якщо господар і так малює кожен кадр, спокійно клади крок гостя в кадр: там цей спосіб не коштує нічого.
