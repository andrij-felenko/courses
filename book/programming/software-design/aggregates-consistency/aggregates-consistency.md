Уяви замовлення в інтернет-магазині. Це не одна річ, а ціле сімейство: сам заголовок замовлення, кілька рядків із товарами й кількостями, адреса доставки, застосована знижка. І десь у цьому сімействі живе правило, яке легко проґавити, поки все не зламається: **сума знижки не може перевищити суму рядків**. Порушиш його — і магазин доплачує клієнтові за те, що той щось купив.

Тепер постав звичайне питання розробника: *хто відповідає за те, щоб це правило ніколи не порушилось?* Якщо рядок замовлення можна взяти окремо й тихо змінити кількість, а хтось інший тим часом окремо міняє знижку, то момент, коли обидві зміни разом порушать правило, настане неминуче — і винного не буде, бо кожен чіпав «своє». Правило, за яке ніхто не відповідає одноосібно, — це правило, яке рано чи пізно порушать.

Ось із цієї незручності й народжується агрегат. **Агрегат (лат. *aggregare* — приєднувати, збирати в купу)** — це група пов'язаних об'єктів, яку система трактує як **одне ціле щодо змін**: усередині діють спільні правила, а ззовні до неї є рівно одні двері. Слово вдале: це не будь-яка купа об'єктів, а купа, зібрана довкола спільної відповідальності. Поняття у програмний ужиток увів [Ерік Еванс у книзі *Domain-Driven Design* 2003 року](book:programming/aggregates-consistency/hist-evans-aggregate.md) — і воно виявилося одним із небагатьох, що переживає зміну мов, баз даних і мод, бо відповідає не на технічне, а на вічне питання: **де провести межу, за якою правила мусять збігатися завжди**.

## Проблема: правило, розмазане по кількох об'єктах

Придивімося, чому наївний підхід ламається. Хай замовлення — це просто заголовок, а рядки й знижка — окремі об'єкти, до яких кожен код має прямий доступ і може міняти незалежно. Виглядає гнучко. Але правило «знижка ≤ сума рядків» тепер не належить нікому: воно натягнуте між трьома об'єктами, а перевірити його може лише той, хто бачить усіх трьох **одночасно**.

Що з цього виходить на практиці, видно на очах:

:::tabs
```ts
// Кожну частину замовлення можна міняти окремо — і правило нікому не належить
order.discount = 500;              // хтось застосував купон на 500
line.quantity = 0;                 // хтось інший прибрав товар з рядка
// Тепер сума рядків = 300, а знижка = 500. Правило порушено.
// Хто мав це помітити? Ніхто: кожен чіпав «своє» поле.
```
```python
# Кожну частину замовлення можна міняти окремо — і правило нікому не належить
order.discount = 500                # хтось застосував купон на 500
line.quantity = 0                   # хтось інший прибрав товар з рядка
# Тепер сума рядків = 300, а знижка = 500. Правило порушено.
# Хто мав це помітити? Ніхто: кожен чіпав «своє» поле.
```
:::

Причина не в тому, що програміст неуважний. Причина структурна: **правило охоплює кілька об'єктів, а доступ до них роздрібнений**. Поки будь-хто може дотягтися до внутрішньої частини й змінити її повз спільну перевірку, узгодженість тримається лише на доброму пильнуванні всіх, хто пише код, — а це не тримається взагалі.

Правильне питання, отже, не «як додати ще перевірок», а «як зробити так, щоб змінити частину **інакше, ніж через спільну точку контролю, було просто неможливо**». Відповідь і є двома пов'язаними ідеями: межа агрегата й корінь.

## Корінь як єдині двері

**Корінь агрегата (англ. *aggregate root*)** — це одна сутність усередині групи, через яку проходять **усі** зміни. Зовнішній код тримає посилання лише на корінь; до внутрішніх об'єктів у нього доступу немає — він навіть не знає їхніх імен. Хоче щось змінити всередині — просить про це корінь, а корінь, перш ніж дозволити зміну, перевіряє спільні правила.

Це той самий хід, що й [інкапсуляція](book:programming/interface-vs-implementation) — сховати нутрощі за інтерфейсом, — але піднятий на рівень **групи об'єктів**, а не одного. Корінь — не просто «головний об'єкт»; це **воротар**, який фізично не лишає іншого способу зайти.

Перепишемо замовлення так, щоб порушити правило стало неможливо:

:::tabs
```ts
class Order {
  // Внутрішні частини — приватні. Ззовні до них не дотягтися.
  #lines: OrderLine[] = [];
  #discount = 0;

  addLine(product: ProductId, qty: number, price: Money): void {
    if (qty <= 0) throw new Error("кількість має бути додатною");
    this.#lines.push(new OrderLine(product, qty, price));
    // правило перевіряти не треба: додавання рядка лише збільшує суму
  }

  applyDiscount(amount: Money): void {
    if (amount.isNegative()) throw new Error("знижка не буває від'ємною");
    if (amount.greaterThan(this.subtotal()))         // ← спільне правило
      throw new Error("знижка не може перевищити суму рядків");
    this.#discount = amount;
  }

  removeLine(product: ProductId): void {
    this.#lines = this.#lines.filter(l => !l.product.equals(product));
    // прибрали рядок → сума впала → знижка могла стати завеликою:
    if (this.#discount > this.subtotal())
      this.#discount = this.subtotal();               // тримаємо правило
  }

  subtotal(): Money { return this.#lines.reduce((s, l) => s.add(l.total()), Money.ZERO); }
  total(): Money    { return this.subtotal().subtract(this.#discount); }
}
```
```python
class Order:
    def __init__(self) -> None:
        # Внутрішні частини — приватні. Ззовні до них не дотягтися.
        self._lines: list[OrderLine] = []
        self._discount = Money.ZERO

    def add_line(self, product: ProductId, qty: int, price: Money) -> None:
        if qty <= 0:
            raise ValueError("кількість має бути додатною")
        self._lines.append(OrderLine(product, qty, price))
        # правило перевіряти не треба: додавання рядка лише збільшує суму

    def apply_discount(self, amount: Money) -> None:
        if amount.is_negative():
            raise ValueError("знижка не буває від'ємною")
        if amount > self.subtotal():                     # ← спільне правило
            raise ValueError("знижка не може перевищити суму рядків")
        self._discount = amount

    def remove_line(self, product: ProductId) -> None:
        self._lines = [l for l in self._lines if l.product != product]
        # прибрали рядок → сума впала → знижка могла стати завеликою:
        if self._discount > self.subtotal():
            self._discount = self.subtotal()             # тримаємо правило

    def subtotal(self) -> Money:
        return sum((l.total() for l in self._lines), Money.ZERO)

    def total(self) -> Money:
        return self.subtotal() - self._discount
```
:::

Придивися, що змінилося по суті. Рядки й знижка більше не окремі об'єкти, до яких хтось має ключі, — вони **всередині** `Order`, за приватним муром. Єдиний спосіб застосувати знижку — гукнути `applyDiscount`, а він **не дасть** порушити правило. Прибирання рядка тягне за собою можливе порушення (сума впала нижче знижки) — і корінь тут-таки його гасить. Тепер немає такого сценарію, у якому правило впаде: код, що змінив би частину повз корінь, **не компілюється** (у типізованій мові) або **не має до чого звернутися** (у динамічній), бо приватного поля просто не видно.

> 🔧 **Навіщо це.** Найдорожчі баги — не ті, де щось падає гучно, а тихі порушення узгодженості: сума не сходиться, статус суперечить залишку, і ти дізнаєшся про це через тиждень з підтримки. Корінь-воротар прибирає цілий клас таких багів **конструктивно** — не «перевіряй уважніше», а «інакше зробити нема як». Це переносить надійність із дисципліни людей у структуру коду, а структура не забуває й не поспішає.

## Інваріант — те, що межа захищає

Правило «знижка ≤ сума рядків» має точну назву — **інваріант (лат. *invariant* — незмінний)**: твердження, яке має бути істинним **щоразу, коли на агрегат хтось дивиться ззовні**. Не «переважно істинним» і не «істинним, коли ми не забули перевірити», а завжди — між будь-якими двома операціями агрегат стоїть у коректному стані.

Ключове слово тут — «ззовні». Усередині однієї операції інваріант **дозволено тимчасово порушити**: коли `removeLine` викидає рядок, на частку секунди сума вже впала, а знижку ще не підрізано — правило в цю мить не виконується. Це нормально, бо назовні цей проміжний стан ніхто не бачить: операція або доходить до кінця й лишає агрегат коректним, або не застосовується взагалі. Саме тому кажуть, що **агрегат — це одиниця узгодженості**: правила зобов'язані збігтися до межі однієї операції над коренем, ані миттю пізніше.

![Замкнена межа агрегата: усередині корінь Order з приватними рядками OrderLine і знижкою; єдина стрілка входить ззовні в корінь, від рядків до кореня стрілок ззовні немає; на межі підпис «інваріант виконується тут»; поруч друге замовлення як окрема замкнена межа, зв'язок між ними — тонка стрілка за ідентифікатором](/book/programming/software-design/aggregates-consistency/img/aggregate-boundary.svg)

*Агрегат — замкнена межа з одними дверима. Зовнішній світ стукає лише в корінь; усе, що всередині, узгоджене на кожен момент, коли межу перетинає погляд ззовні. Сусідній агрегат — окрема межа зі своїм коренем.*

Тепер видно, чому межу проводять саме там, де живуть інваріанти. **Що зобов'язане бути істинним разом — має лежати в одному агрегаті.** Якщо два правила ніколи не переплітаються, тримати їхні об'єкти в одній межі шкідливо: агрегат розбухає, кожна дрібна зміна блокує пів системи, а користі — нуль. Тому провідне запитання розкрою звучить так: *які факти мусять сходитися в одну мить, а які можуть трохи розійтися й вирівнятись потім?* Перші зшивають в агрегат; другі — розводять.

## Тримай агрегати малими

З цього критерію випливає правило, яке досвід DDD виніс на перше місце: **агрегати мають бути малими**. Спокуса завжди тягне в інший бік — «замовлення ж належить клієнтові, тримаймо клієнта і всі його замовлення разом», і ось уже один агрегат `Customer` тягне сотні замовлень, кожне з рядками. Виглядає природно за структурою даних, але провалюється за критерієм інваріантів: чи є правило, що зобов'язує **всі** замовлення клієнта бути узгодженими між собою в одну мить? Майже завжди — ні. Замовлення живуть своїм життям.

А розплата за роздутий агрегат подвійна. Перша — **продуктивність**: щоб змінити один рядок в одному замовленні, доводиться підняти з бази весь агрегат — клієнта з усіма замовленнями. Друга, гостріша, — **суперництво за запис**. Два оператори правлять два **різні** замовлення того самого клієнта; якщо обидва замовлення в одному агрегаті `Customer`, їхні зміни б'ються за одне й те саме — одна перезапише іншу або конфлікт заблокує обох. Це і є причина, чому [оптимістичне блокування](book:programming/optimistic-locking) працює тим краще, чим менший агрегат: колізій менше, бо різні дії торкаються різних агрегатів.

Отже, розводимо: `Customer` — окремий агрегат, `Order` — окремий, і між ними лишається лише зв'язок «це замовлення належить он тому клієнтові».

## Між агрегатами — тільки за ідентифікатором

Як саме тримати цей зв'язок? Спокуса — покласти всередину замовлення живий об'єкт клієнта: `order.customer.email`. Зручно, поки не помічаєш, що цим ти щойно **проламав дві межі в одну**. Тепер, щоб завантажити замовлення, тягнеш і клієнта; код замовлення може непомітно змінити щось у клієнтові повз його корінь; а транзакція, що зберігає замовлення, зачіпає й дані клієнта. Дві одиниці узгодженості злиплися назад в одну — і всі проблеми роздутого агрегата повернулися чорним ходом.

Правило, що це відрубає: **один агрегат посилається на інший лише за його ідентифікатором, ніколи прямим об'єктом.**

:::tabs
```ts
// НЕ так: живий об'єкт чужого агрегата всередині
class Order { customer: Customer; /* ← межа проламана */ }

// А так: лише ідентифікатор. Межі лишаються цілими.
class Order {
  readonly customerId: CustomerId;   // хто замовив — знаємо за id
  // потрібні дані клієнта? завантаж його окремо, через його власний корінь
}
```
```python
# НЕ так: живий об'єкт чужого агрегата всередині
class Order:
    customer: Customer          # ← межа проламана

# А так: лише ідентифікатор. Межі лишаються цілими.
class Order:
    def __init__(self, customer_id: CustomerId) -> None:
        self.customer_id = customer_id   # хто замовив — знаємо за id
        # потрібні дані клієнта? завантаж його окремо, через його власний корінь
```
:::

За таким `id` кожна межа лишається собою: замовлення завантажується без клієнта, зберігається без клієнта, і фізично не може зіпсувати те, що йому не належить. Коли справді потрібні дані клієнта — його дістають окремо, через його **власний** корінь. Той самий підхід малює й фігура межі вище: до сусіднього агрегата веде тонка стрілка «за ідентифікатором», а не жирна «володіє об'єктом».

![Ліворуч — злиплі агрегати: Order тримає прямий об'єкт Customer, який тримає інші Order, усе в одній великій межі, підпис «одна транзакція тягне все»; праворуч — розділені: Order і Customer у власних межах, між ними тонка стрілка з підписом customerId, кожна межа зі своїм коренем і підписом «своя транзакція»](/book/programming/software-design/aggregates-consistency/img/reference-by-id.svg)

*Ліворуч прямий об'єкт зшиває дві межі в одну — будь-яка дія тягне все. Праворуч посилання за ідентифікатором лишає кожен агрегат окремою одиницею узгодженості й окремою транзакцією.*

## А якщо правило таки перетинає межу?

Чесне заперечення: буває, що узгодженість **потрібна** між агрегатами. Класика — «сума всіх замовлень клієнта за місяць не має перевищити його кредитний ліміт». Це правило прямо тягнеться через кілька замовлень і клієнта — саме той випадок, який щойно заборонили тримати в одному агрегаті.

Тут DDD робить хід, який спершу дивує, а потім виявляється чесним відображенням реальності: **між агрегатами узгодженість не миттєва, а відкладена (англ. *eventual consistency* — узгодженість з часом)**. Одна операція міняє один агрегат і **надійно повідомляє** про це — публікує подію «замовлення оформлено». Інший процес цю подію ловить і доводить систему до узгодженого стану: перераховує суму, і якщо ліміт перевищено — скасовує замовлення чи ставить його на розгляд. Між цими двома моментами система коротко живе в стані, який ще не звели докупи, — і це не баг, а свідоме рішення.

Чому так, а не «одна велика транзакція на всіх»? Бо велика транзакція через кілька агрегатів — це той самий роздутий агрегат, лише прихований у базі: та сама блокуюча колізія, та сама втрата продуктивності, лише під іншим ім'ям. Реальний світ теж працює відкладено: коли ти оплачуєш карткою, гроші не переходять «миттєво й атомарно» — банк приймає, тимчасово блокує суму, звіряє й лише потім проводить. Момент, коли рахунки ще не зійшлися, існує й там; система просто чесно його моделює, замість вдавати, ніби його немає.

> 🔧 **Навіщо це.** Різниця «миттєва проти відкладеної» — не академічна: вона визначає, чи витримає система навантаження. Спроба тримати миттєву узгодженість усюди впирається в блокування й падає під конкурентними записами. Правильно проведені межі агрегатів кажуть точно, **де вимагати миттєвості (усередині агрегата), а де достатньо звести докупи трохи згодом (між агрегатами)** — а це прямо визначає, скільки одночасних користувачів застосунок витримає. Механіку надійної доставки таких повідомлень розбирає [подієва архітектура](book:programming/event-driven-architecture).

## Один агрегат — одна транзакція

Із усього цього випливає практичне правило, яким перевіряють дизайн заднім числом: **одна транзакція змінює рівно один агрегат.** Якщо операція мусить атомарно змінити два — це майже завжди сигнал, що межу проведено не там: або ці об'єкти насправді один агрегат (і треба їх звести), або зв'язок між ними має бути відкладеним (і треба подію, а не спільну транзакцію).

Це правило — не бюрократія, а вентиль, що не дає системі непомітно з'їхати назад до великого клубка. Щойно хтось у пориві «зробити зручно» пише операцію, яка одним махом чіпає замовлення й баланс клієнта, це правило спалахує червоним: стоп, ти щойно зшив дві межі. Перевіряти його легко, а користь — та сама, що й від малих агрегатів: локальні зміни, менше колізій, передбачувані транзакції.

Дістають і зберігають агрегат теж як ціле — через окрему абстракцію, [репозиторій](book:programming/repository), що приймає й повертає **корінь** (не внутрішні частини) і ховає, як саме агрегат розкладено по таблицях. Репозиторій — на агрегат, не на кожен клас: він оперує тими самими межами, тримаючи правило «дістав корінь → змінив через корінь → зберіг корінь» замкненим від бази до коду.

## Де межа насправді, а де здається

Найтонше в агрегатах — не механіка приватних полів, а **вибір, що покласти всередину**. І тут легко піти двома хибними шляхами. Перший — зробити один гігантський агрегат «щоб усе було узгоджено»; ми бачили ціну: блокування, повільність, колізії. Другий, протилежний, — покришити все на найдрібніші агрегати «щоб було швидко» й лишити реальний інваріант без захисту, розмазаним між ними, — і повернути ту саму початкову біду з правилом, за яке ніхто не відповідає.

Правильна межа — рівно та, що охоплює **справжній** інваріант і **нічого зайвого**. Вона не збігається ні зі структурою бази даних («усе, що в одній таблиці»), ні з граматикою мови предмета («усе, що згадується разом»). Вона збігається з відповіддю на одне питання: *що зобов'язане бути істинним в одну й ту саму мить?* Ось лінійка, яка все розставляє.

І остання чесність: цю межу **не завжди видно з першого разу**, і це нормально. Розуміння предметної області приходить із роботою, інваріанти проступають поступово, і межу доводиться пересувати. Тому агрегати тримають малими й слабко зчепленими не лише заради продуктивності, а й **щоб їх було легко перекроїти**, коли предмет відкриється глибше. Агрегат — не вічний контур, вирізьблений раз; це найкраща на сьогодні відповідь на питання про узгодженість, яку залишають достатньо гнучкою, щоб виправити завтра. У цьому й уся суть: агрегат бере невловне відчуття «оці речі мусять збігатися, а оці — ні» й перетворює його на межу в коді, яку машина стереже замість людини.
