# ⚙️ Переводимо застосунок на дванадцять факторів — крок за кроком

Найкоротший спосіб зрозуміти, що дванадцять факторів насправді роблять, — узяти застосунок, який їх порушує, і виправляти по одному, дивлячись, як після кожної зміни зникає одна конкретна прив'язка до середовища. Не абстрактно «стало краще», а точно: ось цей рядок коду знав щось про машину, під якою він живе, — тепер не знає, і тому копію застосунку можна поставити на будь-яку іншу машину, вбити, підняти, розмножити, і нічого не зламається.

Візьмемо реальний, упізнаваний застосунок — маленький сервіс, де користувач заходить під своїм іменем і вантажить світлини. Такий пишуть на першому тижні будь-якої роботи, і саме такий найчастіше порушує всі цікаві фактори одразу. Ось він, «до»:

```python
# app.py — застосунок «до». Працює на одній машині й тільки на ній.
from flask import Flask, request, session, send_file

app = Flask(__name__)

# ── прив'язка №1: конфіг зашитий у код ──
app.secret_key = "super-secret-please-change"        # ключ підпису сесій
DATABASE_URL = "postgresql://localhost:5432/photos"  # адреса бази — «localhost»
UPLOAD_DIR = "/var/app/uploads"                       # тека на ЦЬОМУ диску

# ── прив'язка №2: сесія живе в пам'яті ЦЬОГО процесу ──
# (Flask за замовчуванням кладе сесію в підписану cookie, але щойно
#  ми починаємо тримати «залогінених» у власному dict — стан осідає в процесі)
logged_in_users = {}   # session_id -> user_id, у пам'яті процесу

@app.post("/login")
def login():
    user_id = check_password(request.form["user"], request.form["pass"])
    session["sid"] = new_session_id()
    logged_in_users[session["sid"]] = user_id   # ← стан у пам'яті
    return {"ok": True}

@app.post("/upload")
def upload():
    user_id = logged_in_users[session["sid"]]         # хто вантажить
    photo = request.files["photo"]
    path = f"{UPLOAD_DIR}/{user_id}/{photo.filename}"  # ← файл на локальний диск
    photo.save(path)
    return {"stored": path}

@app.get("/photo/<user_id>/<name>")
def get_photo(user_id, name):
    return send_file(f"{UPLOAD_DIR}/{user_id}/{name}")  # ← читаємо з ЦЬОГО диска

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000)   # ← порт зашитий у код
```

Той самий застосунок на Node — щоб було видно, що проблема не в мові, а у **формі**:

```typescript
// app.ts — застосунок «до». Та сама історія іншою мовою.
import express from "express";
import session from "express-session";
import multer from "multer";
import path from "path";

const app = express();

// ── прив'язка №1: конфіг зашитий у код ──
const SECRET = "super-secret-please-change";
const DATABASE_URL = "postgresql://localhost:5432/photos";
const UPLOAD_DIR = "/var/app/uploads";

// ── прив'язка №2: сесія в пам'яті ЦЬОГО процесу ──
// MemoryStore за замовчуванням тримає всі сесії в купі цього процесу
app.use(session({ secret: SECRET, resave: false, saveUninitialized: false }));

const upload = multer({ dest: UPLOAD_DIR });   // ← файли на локальний диск

app.post("/upload", upload.single("photo"), (req, res) => {
  const userId = (req.session as any).userId;
  const dest = path.join(UPLOAD_DIR, userId, req.file!.originalname);
  // ...перекласти файл у dest на ЦЬОМУ диску...
  res.json({ stored: dest });
});

app.get("/photo/:userId/:name", (req, res) => {
  res.sendFile(path.join(UPLOAD_DIR, req.params.userId, req.params.name));
});

app.listen(8000, "0.0.0.0");   // ← порт зашитий у код
```

Порахуймо прив'язки, які тут вросли в код, бо саме їх ми виривати́мемо:

- **адреса бази, ключ підпису, тека — літерали в тексті програми.** Щоб поставити цей застосунок деінде, доведеться правити код і перезбирати — а це вже інший артефакт під кожне середовище;
- **сесія залогінених — у пам'яті процесу** (`logged_in_users`, `MemoryStore`). Другу копію запустити не можна: користувач, що зайшов на першу, для другої — чужий;
- **світлини — на локальному диску тієї машини, де крутиться процес.** Файл, залитий на копію А, копія Б не бачить, а якщо копію А знесуть — файли зникнуть разом із нею;
- **порт зашитий числом, і застосунок стартує-падає без жодного обряду** — його вбивство посеред заливки лишить недописаний файл.

Кожна з цих прив'язок — це те, чим одна машина відрізняється від іншої, зашите всередину застосунку. Приберемо їх по черзі.

## Крок 1. Конфіг — назовні, з перевіркою на старті

**Задача.** Витягти з коду все, чим середовища різняться — адресу бази, ключ підпису, теку, порт — і читати це з середовища при запуску. Причому так, щоб застосунок, якому забули дати обов'язкове значення, **впав одразу й голосно**, а не через дві години з незрозумілою помилкою під живими користувачами.

**Ідея.** Значення заходять зі змінних середовища (англ. *environment variables*) — тих самих `DATABASE_URL`, `SECRET_KEY`, які операційна система передає процесу при старті. Той самий незмінний артефакт заходить у кожне середовище й бере звідти свої значення; код більше не містить жодного літерала, специфічного для машини. Тонкий, але вирішальний штрих — **перевірка на старті (англ. *fail-fast*)**: усі обов'язкові значення читаємо в одному місці на самому початку, і якщо чогось бракує, застосунок падає негайно, ще до першого запиту. Межу «код проти конфіг» і те, чому вона критична, детально розбирає [окрема стаття про конфігурацію](book:programming/config-design); тут — практика.

```python
# config.py — єдине місце, де застосунок торкається середовища.
import os

class MissingConfig(Exception):
    pass

def require(name: str) -> str:
    """Обов'язкове значення: немає — падаємо ЗАРАЗ, а не колись потім."""
    value = os.environ.get(name)
    if not value:
        raise MissingConfig(f"немає обов'язкової змінної середовища {name}")
    return value

def optional(name: str, default: str) -> str:
    return os.environ.get(name) or default

class Config:
    DATABASE_URL = require("DATABASE_URL")
    SECRET_KEY   = require("SECRET_KEY")
    PORT         = int(optional("PORT", "8000"))
    LOG_LEVEL    = optional("LOG_LEVEL", "info")

# Читаємо ОДИН раз при імпорті — тобто на старті процесу.
# Забули задати SECRET_KEY у проді? Процес не підніметься взагалі,
# і ти дізнаєшся про це на деплої, а не з нічної пейджер-тривоги.
config = Config()
```

```typescript
// config.ts — єдине місце, де застосунок торкається середовища.
class MissingConfig extends Error {}

function require(name: string): string {
  const value = process.env[name];
  if (!value) throw new MissingConfig(`немає обов'язкової змінної середовища ${name}`);
  return value;
}

function optional(name: string, fallback: string): string {
  return process.env[name] || fallback;
}

export const config = {
  DATABASE_URL: require("DATABASE_URL"),
  SECRET_KEY:   require("SECRET_KEY"),
  PORT:         Number(optional("PORT", "8000")),
  LOG_LEVEL:    optional("LOG_LEVEL", "info"),
} as const;
// Модуль обчислюється при першому import — тобто при старті процесу.
// Бракує обов'язкового — застосунок кидає на старті й не приймає жодного запиту.
```

Тепер у самому застосунку немає жодного літерала, специфічного для середовища: замість `"postgresql://localhost:5432/photos"` — `config.DATABASE_URL`, замість числа `8000` — `config.PORT`. Той самий код піде на машину розробника (де `DATABASE_URL` указує на локальну базу) і в прод (де він указує на бойову) без єдиної правки тексту програми.

**Яку прив'язку прибрали.** Код більше не припускає, *яке саме* середовище під ним. Раніше адреса `localhost` жорстко означала «база на цій самій машині»; тепер застосунок питає середовище і ходить туди, куди йому скажуть. Копії стали трохи взаємозамінніші: та сама програма з різними змінними — це та сама програма, а не чотири схожі.

**Пастки цього кроку.**

- **Читати `os.environ` розкидано по коду замість одного місця.** Тоді забуту змінну ти знаходиш не на старті, а в той момент, коли вперше викличеться саме той рядок, — часто в проді, часто вночі. Збери все читання середовища в один модуль, що обчислюється на старті. Це і є суть `fail-fast`: помилка конфігу має бути помилкою запуску, а не помилкою запиту.
- **Тихий типовий значенець для секрету.** Спокуса написати `SECRET_KEY = optional("SECRET_KEY", "dev-key")`. Тоді забутий у проді ключ не впаде, а мовчки візьме `"dev-key"` — і твої сесії підписані відомим усьому світу рядком. Секрети — завжди `require`, ніколи не `optional`: краще впасти, ніж підняти діряве.
- **Скласти секрети в репозиторій «щоб зручно».** Файл `.env` із бойовими паролями, закомічений у git, — це той самий літерал у коді, лише переставлений на рядок нижче. Значення в середовищі — означає *поза* артефактом і поза історією версій; секрети живуть у сховищі секретів середовища, а в git лежить хіба `.env.example` із порожніми полями як підказка, які змінні взагалі потрібні.

## Крок 2. Стан — назовні: сесії в спільний кеш, файли в об'єктне сховище

**Задача.** Зробити процес порожнім усередині. Зараз він тримає в собі дві речі, яких не має тримати: перелік залогінених (у пам'яті) і залиті світлини (на локальному диску). Обидві прив'язують користувача до конкретної копії застосунку. Треба винести і те, і те так, щоб **будь-яка копія обслужила будь-який запит**.

**Ідея.** Усе, що має пережити окремий запит, застосунок пише не в себе, а в спільний backing-сервіс, до якого всі копії мають рівний доступ. Сесії переїжджають у спільний кеш — зазвичай це Redis, швидке сховище «ключ→значення», спільне для всіх копій. Файли переїжджають в **об'єктне сховище (англ. *object storage*)** — службу на кшталт Amazon S3 чи сумісного з ним MinIO, куди кладеш об'єкт за ключем і отримуєш назад за тим самим ключем, байдуже з якої машини. Ключове слово — «спільне»: сесія, записана копією А, читається копією Б, бо лежить вона не в А, а в Redis, до якого йдуть обидві. Це і є фактор процесів без стану, серце всієї методики.

Ось сесії. Замість `dict` у пам'яті — виклик до спільного кешу:

```python
# session_store.py — сесії ЗАЛОГІНЕНИХ живуть у спільному Redis, не в процесі.
import redis
from config import config

# Клієнт до спільного кешу; адреса — теж із середовища (крок 1).
r = redis.from_url(config.REDIS_URL)

SESSION_TTL = 3600   # сесія живе годину без активності

def remember_login(sid: str, user_id: int) -> None:
    # Було: logged_in_users[sid] = user_id  (у пам'яті ЦЬОГО процесу)
    r.setex(f"session:{sid}", SESSION_TTL, user_id)   # ← у СПІЛЬНОМУ кеші

def whoami(sid: str) -> int | None:
    value = r.get(f"session:{sid}")
    return int(value) if value else None   # None → сесія протухла або чужа
```

```typescript
// sessionStore.ts — сесії залогінених у спільному Redis.
import { createClient } from "redis";
import { config } from "./config";

const r = createClient({ url: config.REDIS_URL });
await r.connect();

const SESSION_TTL = 3600;

export async function rememberLogin(sid: string, userId: number): Promise<void> {
  // Було: MemoryStore — сесії в купі цього процесу.
  await r.setEx(`session:${sid}`, SESSION_TTL, String(userId));  // ← у СПІЛЬНОМУ кеші
}

export async function whoami(sid: string): Promise<number | null> {
  const value = await r.get(`session:${sid}`);
  return value ? Number(value) : null;   // null → протухла або чужа
}
```

Тепер файли. Замість `photo.save(path)` на локальний диск — заливка в об'єктне сховище за ключем:

```python
# storage.py — світлини живуть в об'єктному сховищі (S3-сумісному), не на диску.
import boto3
from config import config

s3 = boto3.client(
    "s3",
    endpoint_url=config.S3_ENDPOINT,           # адреса сховища — із середовища
    aws_access_key_id=config.S3_KEY,
    aws_secret_access_key=config.S3_SECRET,
)
BUCKET = config.S3_BUCKET

def put_photo(user_id: int, name: str, data) -> str:
    key = f"{user_id}/{name}"                   # ключ об'єкта, не шлях на диску
    s3.upload_fileobj(data, BUCKET, key)        # ← у СПІЛЬНЕ сховище
    return key

def photo_url(user_id: int, name: str) -> str:
    key = f"{user_id}/{name}"
    # Підписане тимчасове посилання — клієнт забирає файл ПРЯМО зі сховища,
    # застосунок навіть не гонить байти крізь себе.
    return s3.generate_presigned_url(
        "get_object", Params={"Bucket": BUCKET, "Key": key}, ExpiresIn=300
    )
```

```typescript
// storage.ts — світлини в S3-сумісному об'єктному сховищі.
import { S3Client, PutObjectCommand, GetObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import { config } from "./config";

const s3 = new S3Client({
  endpoint: config.S3_ENDPOINT,       // адреса сховища — із середовища
  credentials: { accessKeyId: config.S3_KEY, secretAccessKey: config.S3_SECRET },
  region: "auto",
});
const BUCKET = config.S3_BUCKET;

export async function putPhoto(userId: number, name: string, body: Buffer): Promise<string> {
  const key = `${userId}/${name}`;    // ключ об'єкта, не шлях на диску
  await s3.send(new PutObjectCommand({ Bucket: BUCKET, Key: key, Body: body }));
  return key;                          // ← у СПІЛЬНЕ сховище
}

export async function photoUrl(userId: number, name: string): Promise<string> {
  const key = `${userId}/${name}`;
  // Підписане тимчасове посилання — клієнт тягне файл прямо зі сховища.
  return getSignedUrl(s3, new GetObjectCommand({ Bucket: BUCKET, Key: key }), { expiresIn: 300 });
}
```

**Яку прив'язку прибрали.** Оце найважливіший крок, бо він виймає з процесу останнє, що робило копії різними. Раніше кожна копія володіла шматком правди, якого не було в інших: перша знала «цей sid — Оленин», бо тримала це у своїй пам'яті; на другій копії диск був порожній, бо файли лежали на диску першої. Тепер обидві правди живуть назовні — у Redis і в об'єктному сховищі, — і кожна копія має до них рівний доступ. Процеси стали однакові й порожні всередині: запит користувача можна кинути на будь-який із них, бо все, що процесу треба знати, він дістає з backing-сервісу, а не з власних нутрощів. Саме тепер увімкнулося масштабування — «витримати вдвічі більше» стало означати буквально «підняти вдвічі більше однакових процесів».

**Пастки цього кроку.**

- **«Липкі сесії» (англ. *sticky sessions*) як спокуса не виносити стан.** Балансувальник уміє прив'язувати користувача до тієї копії, на яку той зайшов першою, — і тоді сесія в пам'яті ніби «працює». Це не розв'язання, а відкладення болю: щойно та копія впаде або її знесуть при оновленні, усі прив'язані до неї користувачі втратять сесію разом. Прив'язка до конкретного процесу нікуди не поділася, ти лише сховав її в балансувальник. Виноси стан по-справжньому, а не роби копії «трохи менш взаємозамінними».
- **Лишити локальний диск як «тимчасовий кеш».** Спокуса: залити файл спершу на локальний диск, а «потім колись» перекласти у сховище. Але «потім» настає не завжди — процес можуть убити між заливкою на диск і переливкою у сховище, і файл зникне. Пиши в об'єктне сховище **відразу**; локальний диск процесу вважай таким, що зникне будь-якої миті разом із процесом (це прямий наслідок одноразовості — [процес має право вмерти будь-коли](book:programming/graceful-shutdown)).
- **Погнати завантаження файлу крізь застосунок замість підписаного посилання.** Якщо кожне читання світлини йде байтами крізь твій процес, він перетворюється на трубу й забиває собі і пам'ять, і мережу. Об'єктні сховища для того й дають підписані тимчасові посилання (presigned URL), щоб клієнт забрав файл **прямо зі сховища**, а застосунок лише видав йому короткочасний ключ і відійшов убік.
- **Сесії без строку життя.** `r.set` без `TTL` наповнює кеш мертвими сесіями назавжди. Завжди `setex`/`setEx` зі строком: протухла сесія має зникати сама, інакше спільний кеш поволі забивається сміттям, яке ніхто не прибирає.

## Крок 3. Розділити build, release, run — незмінний артефакт плюс конфіг на релізі

**Задача.** Зробити так, щоб у прод фізично не могло поїхати «не те, що тестували». Зараз, якщо застосунок збирають прямо на бойовому сервері (`git pull && встановити залежності && запустити`), він на кожній машині збирається трохи по-різному — підхопить іншу версію бібліотеки, іншу версію мови — і «в мене збиралося» стає діагнозом. Треба розчепити три стадії, які досі злиплися в одну.

**Ідея.** Три чіткі стадії, і кожна робить рівно одне. **Складання (build)** бере код і оголошені залежності й пече з них **незмінний артефакт** — образ контейнера — раз і назавжди. **Реліз (release)** бере цей самий артефакт і склеює його з конфігом конкретного середовища (тими самими змінними з кроку 1) — виходить готовий реліз зі своїм номером. **Запуск (run)** просто виконує реліз процесами. Артефакт печеться **один раз** і байт у байт той самий іде в dev, staging і prod; різняться середовища виключно конфігом, що домішується на релізі. Артефакт і конфіг тут навмисно робимо [незмінними](book:programming/immutability): те, що вже спекли й позначили номером, більше не чіпаємо.

Складання описуємо декларативно — `Dockerfile` пече артефакт із коду й **тільки** оголошених залежностей:

```dockerfile
# Dockerfile — стадія BUILD. Виконується РАЗ, дає незмінний артефакт (образ).
# Жодного конфігу тут немає — конфіг домішається пізніше, на РЕЛІЗІ.
FROM python:3.12-slim

WORKDIR /app
# Спершу лише маніфест залежностей — щоб кеш не ламався на кожній зміні коду.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # ← ізольовані, оголошені залежності

COPY . .                                             # тепер сам код
# У Dockerfile НЕМАЄ ані DATABASE_URL, ані SECRET_KEY, ані ключів S3.
CMD ["python", "-m", "app"]
```

```dockerfile
# Dockerfile — той самий підхід для Node. BUILD раз, конфігу немає.
FROM node:22-slim

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev            # ← рівно те, що в lock-файлі, нічого зайвого

COPY . .
RUN npm run build               # компіляція TS → JS усередину артефакту
# Жодних секретів у шарах образу.
CMD ["node", "dist/app.js"]
```

Тепер **реліз** — це склеювання готового артефакту з конфігом середовища. Ані рядка коду тут не збирається; беремо образ за його незмінним тегом і подаємо йому змінні. Показово це виглядає у файлі оркестрації середовища:

```yaml
# release-prod.yaml — стадія RELEASE+RUN для прода.
# Артефакт — за ТОЧНИМ незмінним тегом (не "latest"!): що зібрали й тестували.
services:
  web:
    image: registry.example.com/photos@sha256:3f9a...c1   # ← той самий байт, що в staging
    environment:                                          # ← КОНФІГ додається ТУТ, на релізі
      DATABASE_URL: ${PROD_DATABASE_URL}
      SECRET_KEY:   ${PROD_SECRET_KEY}
      REDIS_URL:    ${PROD_REDIS_URL}
      S3_ENDPOINT:  ${PROD_S3_ENDPOINT}
      PORT:         "8000"
    deploy:
      replicas: 4          # ← чотири однакові порожні процеси (крок 2 зробив це можливим)
```

**Яку прив'язку прибрали.** Раніше «яка версія коду й залежностей поїхала в прод» залежало від того, що трапилося на бойовій машині в мить складання, — тобто від середовища. Тепер артефакт спечено **до** будь-якого середовища й **однаковий** для всіх; середовище торкається його лише конфігом на релізі й не може вплинути на його вміст. Це робить два попередні фактори механічно неминучими: «конфіг у середовищі» — бо в артефакті його фізично немає; «одна база коду, багато розгортань» — бо той самий образ і є ця «одна база», розгорнута багато разів. І з'являється миттєвий відкіт: кожен реліз має номер, попередній нікуди не зник, тож зламаний випуск лікується поверненням на старий реліз за секунди. Саме на цьому розділенні природно виростає [автоматичний конвеєр складання й доставки (CI/CD)](book:programming/ci-cd).

**Пастки цього кроку.**

- **Тег `latest` замість незмінного.** Якщо реліз посилається на `image: photos:latest`, то «що саме запущено» пливе під ногами: сьогодні `latest` — один образ, завтра хтось перезбирав — інший, а тег той самий. Тоді відкіт неможливий (нема на що відкочуватись) і відтворити збій не вийде. Посилайся на артефакт **незмінним** ідентифікатором — точним тегом версії або дайджестом `sha256:...`.
- **Просочити конфіг у стадію build.** Спокуса зашити `ENV DATABASE_URL=...` прямо в `Dockerfile` «щоб працювало». Тоді конфіг знову в артефакті — і артефакт перестав бути одним для всіх середовищ, ти спік окремий образ під прод. Тримай стадію build стерильною від конфігу: секрети й адреси заходять **тільки** на релізі.
- **Секрети в шарах образу.** Навіть якщо не через `ENV`, а через `COPY .env`, — секрет осідає в шарі образу назавжди, і будь-хто з доступом до реєстру його дістане. Артефакт має бути безпечним для зберігання в спільному реєстрі; секретам місце в сховищі секретів середовища, яке підключається на релізі.
- **Складати наново під час запуску.** Якщо `run`-стадія робить `pip install` чи `npm install` при кожному старті процесу, то build і run знову злиплися: кожен старт може підхопити іншу версію залежності. Усі залежності мусять бути **всередині** спеченого артефакту; старт процесу — це чистий `run`, без жодного складання.

## Крок 4. Штатне завершення й порт із конфігу — процес, який не страшно вбити

**Задача.** Останнє, що лишилось, — навчити процес **чисто вмирати**. Зараз, якщо копію застосунку вбити посеред заливки файлу, вона обірве запит на півслові: клієнт отримає розрив, файл лишиться недописаним. А в світі з кроків 2–3 процеси вбивають постійно — при кожному оновленні гасять старі копії й піднімають нові, при масштабуванні донизу прибирають зайві. Процес мусить переживати власну смерть охайно. Заразом приберемо останній зашитий літерал — номер порту.

**Ідея.** Операційна система (і будь-який оркестратор над нею) просить процес спинитися **сигналом**. Головний сигнал — `SIGTERM` (сигнал 15): це ввічливе «будь ласка, заверши роботу». Процес мусить його **перехопити** й провести обряд **штатного завершення (англ. *graceful shutdown*)**: перестати брати нові запити, дообслужити ті, що вже в роботі, відпустити з'єднання — і лише тоді вийти. Якщо ж процес не вгамувався за відведений строк, система б'є `SIGKILL` (сигнал 9) — це вже не прохання, а розстріл, який процес перехопити не може. Тобто в тебе є вікно між `SIGTERM` і `SIGKILL`, і твоя справа — устигнути прибрати за собою в цьому вікні. Повний розбір, чому це критично й що саме треба встигнути, — [в окремій статті про штатне завершення](book:programming/graceful-shutdown); тут — як це вплести в наш застосунок.

Скільки триває вікно — задає середовище, і числа варто знати, бо на них розраховуєш свій обряд. У Docker після `docker stop` процесу `PID 1` летить `SIGTERM`, і за замовчуванням дається **10 секунд**, після чого — `SIGKILL`. У Kubernetes при видаленні пода йде `SIGTERM`, і типовий `terminationGracePeriodSeconds` — **30 секунд** до `SIGKILL`. Твоє завершення має вкладатися в цей строк із запасом, інакше система доб'є тебе на півдорозі, і весь сенс обряду згорить.

```python
# app.py (фрагмент) — порт із конфігу + штатне завершення за SIGTERM.
import signal
from wsgiref.simple_server import make_server
from config import config

def build_app():
    ...  # той самий Flask/WSGI-застосунок

def main():
    app = build_app()
    # Порт — із середовища (крок 1), а не число в коді.
    httpd = make_server("0.0.0.0", config.PORT, app)

    def on_term(signum, frame):
        # Прийшов SIGTERM: перестати брати нові з'єднання...
        httpd.shutdown()          # ← перестаємо приймати, дообслуговуємо поточні
        # ...тут місце дозакрити те, що почали:
        #    доробити запити в роботі, повернути завдання в чергу,
        #    відпустити з'єднання до бази й кешу — і лише тоді вийти.

    signal.signal(signal.SIGTERM, on_term)   # ← перехоплюємо ввічливе «спинись»
    signal.signal(signal.SIGINT, on_term)    # той самий обряд і на Ctrl-C
    httpd.serve_forever()

if __name__ == "__main__":
    main()
```

```typescript
// app.ts (фрагмент) — порт із конфігу + штатне завершення за SIGTERM.
import http from "http";
import { config } from "./config";

const server = http.createServer(app);   // той самий express-застосунок

// Порт — із середовища (крок 1), а не число в коді.
server.listen(config.PORT, "0.0.0.0");

function shutdown(signal: string) {
  // Прийшов SIGTERM: перестаємо брати НОВІ з'єднання,
  // але даємо тим, що вже в роботі, дожити до відповіді.
  server.close(() => {
    // сюди потрапляємо, коли ВСІ активні запити дообслужено:
    //   тепер закрити пул з'єднань до бази, від'єднати Redis — і вийти
    process.exit(0);
  });

  // Страховка: якщо хтось завис і не дає server.close() завершитись,
  // виходимо самі ДО того, як прилетить SIGKILL (вкладаємось у вікно).
  setTimeout(() => process.exit(1), 9000).unref();
}

process.on("SIGTERM", () => shutdown("SIGTERM"));  // ← ввічливе «спинись» від оркестратора
process.on("SIGINT",  () => shutdown("SIGINT"));   // ← Ctrl-C на розробці
```

**Яку прив'язку прибрали.** Дві останні. Порт перестав бути зашитим числом — застосунок публікує себе на тому порту, який дало середовище, і більше не припускає навіть цього про свій світ. А головне — процес перестав бути крихким: раніше його життя й смерть залежали від того, чи «пощастить» не отримати сигнал у невдалу мить; тепер він смертний **штатно**. Його можна вбивати скільки завгодно — при кожному оновленні, при кожному масштабуванні — і він щоразу прибирає за собою й виходить чисто. Це замикає одноразовість: процеси не лише однакові й порожні (крок 2) і не лише беруться з незмінного артефакту (крок 3), а й **не бояться смерті**. Аж тепер систему по-справжньому не страшно чіпати — рій копій, кожну з яких можна підняти, вбити й замінити без обірваної роботи.

**Пастки цього кроку.**

- **Ловити `SIGKILL`.** Спроба «перехопити» сигнал 9 марна за визначенням: `SIGKILL` не можна ні перехопити, ні відкласти — це запобіжник системи проти завислих процесів. Обряд вішай **тільки** на `SIGTERM` (і `SIGINT` для зручності на розробці), а в саме вікно до `SIGKILL` — укладайся.
- **Обряд, що не вкладається у вікно.** Якщо штатне завершення тягнеться довше за грейс-період середовища (довше 10 с у Docker, 30 с у Kubernetes за замовчуванням), середовище доб'є процес `SIGKILL` посеред прибирання — і обірве саме те, що ти намагався дозакрити. Тримай обряд коротким і став **власну** страховку-таймаут трохи меншу за системну (як `setTimeout(..., 9000)` вище), щоб вийти самому, а не під розстрілом.
- **Продовжувати брати нові запити під час завершення.** Якщо після `SIGTERM` застосунок і далі приймає нові з'єднання, вікно ніколи не спорожніє — нова робота надходить швидше, ніж стара доробляється. Перший крок обряду — **закрити двері** (перестати слухати нові з'єднання), і лише потім доробляти те, що вже всередині.
- **Забути, що `PID 1` у контейнері не має типової обробки сигналів.** Процес, запущений як `PID 1` (а саме таким він стає в контейнері), не успадковує звичних типових реакцій ядра на сигнали: якщо ти сам не повісив обробник `SIGTERM`, сигнал просто **не подіє**, і процес довисить до `SIGKILL`. У контейнері обробник сигналів — не приємна дрібниця, а обов'язок; інакше кожне «ввічливе» зупинення насправді буде розстрілом.

## Що змінилося: та сама програма, інша форма

Складімо шлях докупи. Ми не переписали бізнес-логіку — застосунок як приймав логіни й вантажив світлини, так і приймає. Ми змінили його **форму**: по одному вирвали чотири місця, якими він зростався зі своїм середовищем.

```
Було (одна прив'язана копія)          Стало (рій взаємозамінних копій)
─────────────────────────────         ────────────────────────────────
конфіг зашитий у код          →       конфіг зі середовища, перевірка на старті
сесії в пам'яті процесу       →       сесії у спільному Redis
файли на локальному диску     →       файли в об'єктному сховищі
збірка на бойовій машині      →       незмінний артефакт + конфіг на релізі
порт-літерал, смерть на льоту →       порт із конфігу, штатне завершення за SIGTERM
```

Кожен рядок правої колонки прибрав рівно одну причину, чому копії застосунку були різні. Після першого кроку та сама програма стала однаковою в різних середовищах. Після другого — копії стали порожні всередині, і будь-яка обслуговує будь-який запит. Після третього — у прод поїхав рівно той байт, що тестували. Після четвертого — будь-яку копію не страшно вбити. Разом це й означає ту форму, якої дванадцять факторів домагаються: **переносний** (нічого не припускає про машину), **масштабований** (копії однакові й порожні), **стійкий** (смерть копії — буденність), **передбачуваний** (артефакт той самий скрізь).

Найважливіше, що варто винести з цієї вправи, — це наскрізна логіка, а не список дій. Жоден крок не був «покращенням заради краси». Кожен прибирав конкретну прив'язку до середовища, і рівно тому після кожного копії ставали трохи взаємозамінніші, доки з єдиної прикутої до машини копії не вийшов рій однакових процесів, кожен із яких можна поставити будь-де, розмножити, вбити й замінити, і сервіс цього навіть не помітить. Це і є та сама дисципліна — не давати застосункові зростатися зі світом, — але побачена не як дванадцять правил, а як чотири рухи, після яких застосунок нарешті став вільним від машини, під якою живе.
