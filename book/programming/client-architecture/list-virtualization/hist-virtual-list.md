# 📜 Від віртуальних таблиць Smalltalk до нескінченних стрічок вебу

Коли на початку 1980-х років дослідники з наукового центру Xerox PARC створювали середовище Smalltalk-80, вони зіткнулися з апаратним бар'єром: оперативна пам'ять комп'ютера Xerox Dorado чи Alto вимірювалася сотнями кілобайтів або кількома мегабайтами. Спроба створити окремий графічний об'єкт (*View*) для кожного рядка великого каталогу файлів чи таблиці бази даних миттєво вичерпувала пам'ять робочої станції й зупиняла збирач сміття. Розв'язанням став клас `PluggableListView` і концепція «легковагого малювання» (*flyweight rendering*): замість створення тисяч об'єктів у пам'яті інтерфейс створював один єдиний екземпляр віджета для малювання рядка, переміщував його перо у координати видимого вікна, заповнював даними конкретного запису, малював пікселі на растровому полотні (*BitBlt*) і негайно переходив до наступного рядка.

Цей підхід заклав фундаментальний принцип клієнтської віртуалізації: графічне дерево ніколи не повинно дублювати повний набір даних моделі; воно має відображати лише ту підмножину, яку фізично здатне побачити людське око на екрані заданого розміру.

## NeXTSTEP та шаблон постачальника даних

Наприкінці 1980-х років компанія NeXT під керівництвом Стіва Джобса розробляла об'єктно-орієнтовану операційну систему NeXTSTEP. Архітектори бібліотеки AppKit стандартизували взаємодію між візуальними таблицями та джерелами даних через шаблон *DataSource* (постачальник даних). Класи `NSTableView` та багаторівневий навігатор `NSBrowser` відмовилися від прямого збереження вмісту всередині віджета. 

Таблиця `NSTableView` отримувала від програми лише загальну кількість рядків через виклик `numberOfRowsInTableView:`, самостійно вираховувала видимий діапазон індексів відповідно до висоти свого вікна прокрутки (`NSScrollView`) і запитувала значення лише для видимих комірок через метод `tableView:objectValueForTableColumn:row:`. Завдяки цьому NeXTSTEP могла миттєво відкривати та плавно прокручувати мільйонні списки без виділення додаткової пам'яті під графічні елементи. Цей самий механізм згодом без змін перейшов у macOS Cocoa та ліг в основу архітектури графічних інтерфейсів Apple.

## Віртуальний список Windows: LVS_OWNERDATA

У середині 1990-х років Microsoft переносила графічні оболонки на 32-розрядну архітектуру Windows 95 та Windows NT. Бібліотека спільних елементів керування (*Common Controls*, `comctl32.dll`) містила віджет списку `SysListView32`. Звичайний список вимагав надсилання повідомлення `LVM_INSERTITEM` для кожного рядка. Коли розробники спробували завантажити в нього 100 000 записів із корпоративної бази даних, процес займав десятки секунд і споживав десятки мегабайтів дефіцитної системної пам'яті.

У версії Internet Explorer 3.0 та оновленні Windows 95 Comctl32 (1996 рік) інженери Microsoft впровадили прапорець стилю `LVS_OWNERDATA`, який отримав назву *Virtual List-View* (віртуальний режим списку). У цьому режимі список не зберігав жодних текстових рядків, іконок чи структур елементів у внутрішній пам'яті:

1. Застосунок повідомляв системі лише загальну кількість елементів одним викликом `LVM_SETITEMCOUNT`.
2. Список вираховував висоту повзунка скролбару так, ніби всі елементи присутні.
3. Під час прокручування та перемалювання вікно надсилало батьківському вікну сповіщення `WM_NOTIFY` з кодом `LVN_GETDISPINFO`, де вказувався індекс конкретного елемента, текст і графіку якого треба негайно надати для малювання.
4. Додаткове сповіщення `LVN_ODCACHEHINT` попереджало застосунок про діапазон індексів, які незабаром з'являться на екрані, дозволяючи підвантажити їх із диска або бази даних у фоновому буфері.

Цей дизайн зробив віртуальний список Windows промисловим стандартом для десктопних застосунків високої продуктивності на два десятиліття.

## Мобільна революція: ListView, RecyclerPool та ViewHolder

Поява смартфонів наприкінці 2000-х років загострила проблему до межі. Перші пристрої на Android (HTC Dream, 2008 рік) мали процесор із частотою 528 МГц та лише 192 МБ оперативної пам'яті, з яких під купу (*heap*) одного застосунку виділялося від 16 до 24 МБ. Водночас користувач вимагав плавного інерційного скролу списків контактів, пошти та повідомлень із частотою 60 кадрів на секунду (16.67 мс на кадр).

Інженери команди Android під керівництвом Ромена Ґюї (*Romain Guy*) та Чета Гаазе (*Chet Haase*) реалізували у віджеті `ListView` механізм повторного використання графічних подань через параметр `convertView` у методі `Adapter.getView()`. Коли рядок виходив за верхній край екрана, система не знищувала його об'єкт `View`, а передавала у внутрішній сміттєзбірник (*scrap views*). Коли знизу мав з'явитися новий рядок, система виймала старий `View` зі скрап-пулу й передавала розробнику:

```java
// Історичний патерн Android ListView з convertView (2008–2010)
public View getView(int position, View convertView, ViewGroup parent) {
    if (convertView == null) {
        convertView = inflater.inflate(R.layout.list_item, parent, false);
    }
    TextView title = (TextView) convertView.findViewById(R.id.title);
    title.setText(getItem(position).getTitle());
    return convertView;
}
```

Проте виклики `findViewById()` під час кожного руху пальця виконували рекурсивний обхід дерева вузлів і спричиняли просідання частоти кадрів (*jank*). Спільнота розробників винайшла ідіому *ViewHolder* — збереження посилань на дочірні віджети всередині тегу `View`, щоб уникнути повторного пошуку в дереві.

У 2014 році команда Android під керівництвом Їгіта Бояра (*Yigit Boyar*) випустила бібліотеку `RecyclerView`, де патерн `ViewHolder` став обов'язковим на рівні компілятора та інтерфейсу API. `RecyclerView` повністю розділив відповідальності:
- `LayoutManager` відповідав виключно за геометрію та обчислення видимих меж (лінійний список, сітка, шаховий порядок);
- `Adapter` відповідав за створення та прив'язку даних до `ViewHolder`;
- `RecycledViewPool` зберігав кеш типізованих подань, який міг розділятися навіть між різними списками (наприклад, у вкладених горизонтальних каруселях магазину Google Play);
- `ItemAnimator` керував плавними анімаціями додавання, видалення та переміщення без блокування скролу.

Паралельно Apple в iOS запровадила схожу модель у `UITableView` та `UICollectionView` через метод `dequeueReusableCellWithIdentifier:forIndexPath:`, де кожна комірка реєструвалася за типом і повторно використовувалася з черги системи.

## Веб-епоха: від пагінації до віртуального вікна

У веб-розробці віртуалізація списків з'явилася значно пізніше. До середини 2010-х років стандартом вебу була сторінкова навігація (*pagination*) або «нескінченний скрол» (*infinite scroll*), який просто додавав нові вузли в кінець документа. Коли користувач прокручував стрічку соцмережі на сотні екранів, кількість DOM-вузлів перевищувала десятки тисяч. Це спричиняло лавиноподібне зростання часу перерахунку стилів (*Recalculate Style*) та розкладки (*Layout/Reflow*), а на мобільних браузерах вкладення примусово перезавантажувалося через вичерпання ліміту пам'яті WebKit/Blink.

Перелом стався у 2015 році, коли американський інженер Браян Вон (*Brian Vaughn*) випустив бібліотеку `react-virtualized` (а згодом у 2018 році — її полегшену архітектурну спадкоємицю `react-window`). Вон переніс принципи віртуального вікна (*windowing*) у світ реактивного компонентного рендерингу:
- Абсолютне позиціонування DOM-вузлів через CSS-трансформації (`transform: translateY(...)`);
- Обчислення видимого зрізу масиву на основі `scrollTop` контейнера;
- Використання верхнього та нижнього буферів (*overscan*) для випередження швидкості людського ока під час швидкого руху коліщатка миші.

На початку 2020-х років концепція еволюціонувала до «безголових» (*headless*) рішень (найвідоміше — `TanStack Virtual` Таннера Лінслі), які абстрагують математику індексації, префіксних сум та оцінки динамічних висот від конкретного фреймворку (React, Vue, Svelte, Solid чи чистий TypeScript).

Водночас робоча група W3C та інженери Google Chrome реалізували перші нативні браузерні примітиви оптимізації рендерингу позаекранного вмісту — властивість CSS `content-visibility: auto` (Chrome 85, серпень 2020 року). Ця властивість дозволяє браузеру пропускати розкладку та малювання елементів, які перебувають поза межами видового екрана, зберігаючи при цьому доступність для внутрішнього пошуку браузера (`Ctrl+F`). Хоча `content-visibility` не зменшує кількість DOM-вузлів у пам'яті, вона органічно доповнює прикладну віртуалізацію у сценаріях документів середнього обсягу.
