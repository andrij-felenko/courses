Коли людина заповнює форму реєстрації на двадцять полів, обирає країну зі спадного списку або перемикає сторінку в каталозі товарів, найгірше, що може зробити браузер, — це перезавантажити документ повністю. У класичній моделі багатосторінкового вебу будь-який клік на посилання чи кнопку відправлення форми розриває поточний сеанс. Браузер повністю знищує наявне дерево об'єктної моделі документа (DOM, англ. *Document Object Model*), вивантажує з оперативної пам'яті змінні JavaScript, обриває фонові обчислення, скидає позицію прокрутки вікна та очищує фокус активного поля введення.

На екрані виникає білий спалах (англ. *white flash*). Потім клієнт ініціює новий мережевий запит, отримує від сервера повний HTML-документ обсягом у сотні кілобайтів, заново парсить стилі CSS, завантажує важкі файли шрифтів, компілює бандли скриптів і повторно проходить повний конвеєр рендерингу: компонування (*Layout*) та піксельне малювання (*Paint*). Якщо в цей момент мобільний зв'язок дає збій або пакет затримується на 600 мілісекунд, користувач дивиться на порожній екран і втрачає весь набраний текст.

Виходом із цієї пастки є **фонові мережеві запити** та **часткове оновлення інтерфейсу** (англ. *background requests and partial page updates*). Браузер зберігає поточну сторінку повністю живою, ініціює неблоківний мережевий виклик у фоновому потоці, отримує від сервера лише компактну дельту даних чи фрагмент розмітки й точково підміняє потрібний вузол у DOM без втрати фокусу, каретки введення та стану оточення.

## Механіка повного перезавантаження проти фонового перенесення стану

Щоб зрозуміти ціну повного перезавантаження сторінки, необхідно простежити життєвий цикл документа на рівні внутрішнього рушія браузера.

У разі стандартної навігації (натискання на звичайне гіперпосилання `<a>` або відправлення форми `<form method="POST">`) рушій браузера проходить сім послідовних фаз руйнування та побудови:

```
1. BeforeUnload / Unload: Знищення поточного JS-контексту, зупинка таймерів і збірка сміття
2. HTTP Navigation Request: Відправлення заголовків, проходження через DNS, TCP та TLS
3. TTFB (Time to First Byte): Очікування формування повного HTML сервером
4. HTML Parsing: Потоковий парсинг розмітки та побудова нового DOM-дерева
5. CSSOM Building & Font Loading: Завантаження стилів, блокування рендерингу (Render-blocking CSS)
6. Layout (Reflow): Обчислення точних координат і розмірів кожного прямокутника на екрані
7. Paint & Composite: Растеризація шарів на GPU і виведення пікселів на дисплей
```

Кожен такий цикл не просто забирає від 300 до 1500 мілісекунд процесорного часу та мережевого очікування. Він **стирає ефемерний клієнтський стан** (англ. *transient UI state*):
* позицію вертикальної та горизонтальної прокрутки вікна й окремих внутрішніх контейнерів `overflow: scroll`;
* стан відкритості спадних списків, модальних вікон і вкладок;
* фокус введення (`document.activeElement`) та виділений діапазон тексту (`selectionStart`, `selectionEnd`);
* стан буферів відтворення аудіо та відео;
* невідправлені чернетки у формах, які користувач ще не зафіксував у базі даних.

З точки зору когнітивного навантаження, затримка понад 100 мілісекунд руйнує відчуття прямої маніпуляції інтерфейсом, а затримка понад 1000 мілісекунд змушує людину втрачати нитку міркувань. Коли сторінка блимає білим кольором, очі зазнають різкої зміни яскравості, а мозок змушений заново сканувати геометрію екрана в пошуках потрібного елемента.

![Повне перезавантаження проти фонового часткового оновлення DOM](/book/programming/client-architecture/ajax-partial-updates/img/full-reload-vs-partial-update.svg)
*Повне перезавантаження знищує контекст виконання і спричиняє білий спалах, тоді як фоновий запит змінює лише цільовий фрагмент DOM, зберігаючи стан сесії та фокус користувача.*

У фоновій моделі єдиний кореневий документ завантажується лише один раз під час першого входу. Надалі сторінка виступає довговічним середовищем виконання (англ. *runtime host*). Коли користувач взаємодіє з елементом, обробник події перехоплює стандартну дію браузера (`event.preventDefault()`), формує легковаговий фоновий запит і оновлює виключно той фрагмент дерева, який безпосередньо залежить від отриманої відповіді.

## Еволюція фонового транспорту: від хаків із фреймами до потокового Fetch

Можливість виконувати запити без зміни URL-адреси у вікні браузера пройшла тривалу еволюцію: від небезпечних маніпуляцій з DOM до стандартизованих потокових інтерфейсів.

[Історично перший механізм фонового зв'язку виник у надрах команди Microsoft Outlook Web Access у 1998–1999 роках як обхідне рішення для поштового вебклієнта](book:programming/client-architecture/ajax-partial-updates/hist-ajax-revolution.md). До появи нативних API інженери використовували три обхідні шляхи:
1. **Приховані фрейми (`<iframe style="display:none">`):** цільова форма відправлялася всередину невидимого фрейму через атрибут `target="hidden_frame"`. Сервер повертав у фрейм HTML-сторінку, що містила скрипт `<script>parent.updateData(...)</script>`, який звертався до батьківського вікна. Метод був надзвичайно крихким, ламав історію переходів браузера та видавав характерні клацання системного динаміка під час кожної транзакції.
2. **Зображення-маяки (`Image Beacon`):** для одностороннього відправлення телеметрії скрипт створював об'єкт `new Image()` і призначав йому `src = "/log?event=click&t=" + Date.now()`. Сервер повертав прозорий GIF розміром 1×1 піксель. Метод підтримував лише короткі дані в рядку запиту `GET` і не дозволяв читати відповідь.
3. **Динамічні теги `<script>` (JSONP, JSON with Padding):** для обходу правила одного джерела (англ. *Same-Origin Policy*) скрипт створював вузол `<script src="https://api.example.com/data?callback=myHandler">`. Сервер обгортав JSON у виклик глобальної функції: `myHandler({...})`. Головним недоліком була відсутність підтримки методів `POST`/`PUT`, неможливість перехоплення HTTP-заголовків і колосальні ризики виконання довільного шкідливого коду (XSS).

```
Схема JSONP (1999–2005):
Клієнт створює: <script src="/api?callback=onData">
Сервер віддає:  onData({"user": "Anna", "balance": 450})
Браузер:        Виконує функцію onData() у глобальному скоупі
```

### Епоха XMLHttpRequest

Поява класу `XMLHttpRequest` (XHR) стандартизувала роботу з фоновими HTTP-запитами. Об'єкт надавав можливість надсилати довільні HTTP-методи, налаштовувати користувацькі заголовки (`setRequestHeader`) і отримувати відповідь у вигляді рядка тексту або розпарсеного XML-документа.

В основі XHR лежить скінченний автомат станів `readyState`:
* `0 (UNSENT)`: об'єкт створено, метод `open()` ще не викликано;
* `1 (OPENED)`: викликано метод `open()`, налаштовано метод і цільовий URL;
* `2 (HEADERS_RECEIVED)`: отримано статус відповіді та заголовки від сервера;
* `3 (LOADING)`: завантаження тіла відповіді;
* `4 (DONE)`: транзакцію завершено успішно або перервано збоєм.

```js
// Класичний патерн XMLHttpRequest
const xhr = new XMLHttpRequest();
xhr.open("GET", "/api/products?category=books", true);
xhr.setRequestHeader("Accept", "application/json");

xhr.onreadystatechange = function () {
  if (xhr.readyState === 4) {
    if (xhr.status >= 200 && xhr.status < 300) {
      const data = JSON.parse(xhr.responseText);
      renderProductList(data);
    } else {
      showErrorMessage("Помилка завантаження даних");
    }
  }
};

xhr.onerror = function () {
  showErrorMessage("Помилка мережевого з'єднання");
};

xhr.send(null);
```

Головними архітектурними обмеженнями `XMLHttpRequest` були заплутана колбек-модель (англ. *callback hell*), відсутність нативної підтримки промісів та монолітна буферизація пам'яті: об'єкт накопичував повне тіло відповіді в єдиний рядок або буфер до настання стану `DONE`, що унеможливлювало ефективну обробку великих потоків даних.

### Fetch API та потокове читання байтів (ReadableStream)

Сучасний стандарт `Fetch API` замінив XHR, об'єднавши роботу з мережею навколо стандарту `Promise` та потокового інтерфейсу `WHATWG Streams API`.

На відміну від XHR, проміс `fetch()` переходить у стан успішного виконання (*resolved*) в ту саму мить, коли сервер повертає перші HTTP-заголовки (еквівалент стану `HEADERS_RECEIVED`). Тіло відповіді не завантажується в пам'ять завчасно, а надається у вигляді неблоківного потоку `ReadableStream`:

```ts
// Потокове читання відповіді через Fetch API
async function fetchStreamedData(url: string, onChunk: (text: string) => void): Promise<void> {
  const response = await fetch(url, {
    headers: { "Accept": "text/plain; charset=utf-8" },
  });

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText}`);
  }

  const reader = response.body?.getReader();
  if (!reader) throw new Error("Потік відповіді недоступний");

  const decoder = new TextDecoder("utf-8");
  let isDone = false;

  while (!isDone) {
    const { value, done } = await reader.read();
    if (done) {
      isDone = true;
      break;
    }
    // value є масивом Uint8Array; декодуємо байти у текст без блокування потоку UI
    const chunkText = decoder.decode(value, { stream: true });
    onChunk(chunkText);
  }
}
```

Потоковий `Fetch` дозволяє відображати перші порції даних (наприклад, перші 5 товарів у довгому списку або перші токени у відповіді генеративної мовної моделі) задовго до того, як сервер завершить генерацію всього масиву.

### Мультиплексування з'єднань: HTTP/1.1 проти HTTP/2 та HTTP/3

Ефективність фонових запитів безпосередньо залежить від версії базового протоколу HTTP:
* У **HTTP/1.1** кожен фоновий запит потребував окремого TCP-з'єднання. Браузери встановлювали ліміт у 6 одночасних TCP-з'єднань на один домен. Сьомий паралельний `fetch()` ставав у чергу (*Queued / Stalled*), блокуючи оновлення інтерфейсу.
* У **HTTP/2** з'явилося бінарне мультиплексування (*Binary Framing*): десятки фонових запитів проходять паралельно крізь єдине TCP-з'єднання з власними числовими ідентифікаторами потоків (*Stream ID*). Це повністю ліквідувало черги запитів на клієнті, проте втрата одного TCP-пакета все одно тимчасово призупиняла всі потоки (блокування початку черги на рівні TCP, *Head-of-Line Blocking*).
* У **HTTP/3 (QUIC поверх UDP)** кожен потік мультиплексування є повністю незалежним на транспортному рівні. Втрата пакета в одному фоновому запиті ніяк не затримує отримання даних сусідніми віджетами.

### Постійні канали зв'язку: Server-Sent Events та WebSocket

Для сценаріїв, коли ініціатором оновлення є сервер (надходження нового листа, зміна біржового курсу, повідомлення в чаті), циклічне опитування через `fetch()` (англ. *polling*) є занадто марнотратним: воно перевантажує мережу постійними рукостисканнями TCP/TLS та заголовками HTTP.

Для постійного зв'язку застосовують дві альтернативні технології:

1. **Server-Sent Events (SSE / `EventSource`):** односпрямований потік повідомлень від сервера до клієнта поверх звичайного протоколу HTTP з заголовком `Content-Type: text/event-stream`. З'єднання залишається відкритим, сервер шле текстові блоки виду `data: {...}\n\n`, а браузер автоматично відновлює з'єднання у разі обриву з передачею останнього отриманого ідентифікатора `Last-Event-ID`.
2. **WebSocket (RFC 6455):** повнодуплексний двосторонній протокол поверх єдиного TCP-з'єднання. Після початкового HTTP-рукостискання (`101 Switching Protocols`) клієнт і сервер обмінюються легкими бінарними або текстовими фреймами з накладними витратами всього у 2–10 байтів на повідомлення.

*Хронологія розвитку браузерних фонових транспортів: від хаків із фреймами до повноцінного потокового Fetch та дуплексних сокетів.*

Детальні сигнатури методів, таблицю порівняння заголовків та протокольних контрактів для всіх п'яти типів транспорту наведено в [довіднику мережевих інтерфейсів фонового обміну](book:programming/client-architecture/ajax-partial-updates/api-transport-protocols.md).

## Архітектура корисного навантаження: JSON проти HTML-over-the-wire та RSC

Отримання даних у фоні — це лише половина задачі. Друга половина — визначити, **у якій формі** ці дані мають надходити з сервера та **як саме** клієнт повинен інтегрувати їх у живий DOM.

В сучасній веб-архітектурі конкурують три фундаментальні підходи до часткового оновлення.

```
Три парадигми корисного навантаження (Payload Paradigms):
1. JSON API (SPA):           Сервер (JSON)          ──> Клієнт (JS-шаблонізатор / VDOM) ──> DOM
2. HTML-over-the-wire:       Сервер (HTML-фрагмент) ──> Клієнт (DOM Morphing)           ──> DOM
3. React Server Components:  Сервер (RSC Stream)    ──> Клієнт (Reconciliation graph)   ──> DOM
```

### 1. JSON REST / GraphQL API (Клієнтський SPA-підхід)

У класичних односторінкових застосунках (SPA, англ. *Single Page Applications* на базі React, Vue або Angular) сервер виступає виключно джерелом чистих структурованих даних.

* **Що летить мережею:** чистий JSON виду `{"id": 42, "title": "Клавіатура", "price": 1200}`.
* **Де відбувається рендеринг:** на стороні клієнта за допомогою завантаженого JavaScript-шаблонізатора або віртуального DOM.
* **Переваги:** повне розділення бекенда й фронтенда; той самий JSON API використовується мобільними застосунками під iOS та Android; висока гнучкість клієнтської анімації.
* **Архітектурна ціна:** браузер змушений завантажувати й парсити сотні кілобайтів JavaScript-бібліотек; клієнтський процесор витрачає час на парсинг JSON та звіряння дерев (diffing); виникає проблема дублювання логіки форматування дат, валют та інтернаціоналізації на обох сторонах. Крім того, перший рендеринг вимагає фази гідратації (*Hydration*), яка блокує інтерактивність на слабких мобільних пристроях.

### 2. HTML-over-the-wire (HTMX, Hotwire Turbo)

Підхід *HTML-over-the-wire* повертає генерацію розмітки на сервер, але зберігає плавність SPA без повного перезавантаження сторінки.

* **Що летить мережею:** готовий семантичний HTML-фрагмент (partial), відрендерений шаблонізатором сервера:
  ```html
  <tr id="item-42" class="highlight">
    <td>Клавіатура</td>
    <td>1 200 ₴</td>
  </tr>
  ```
* **Де відбувається рендеринг:** сервер формує готовий HTML, а клієнтський мікрорантайм (розміром усього 10–15 КБ) виконує точкову заміну вузла в DOM.
* **Механізм DOM Morphing:** замість грубої заміни через `innerHTML` (яка знищує стан дочірніх елементів і скидає фокус) рантайм використовує алгоритм морфінгу (наприклад, `Idiomorph` або `morphdom`). Він порівнює наявне дерево DOM із новим HTML-фрагментом, оновлює лише змінені атрибути (`class`, `value`, `disabled`), додає нові вузли, видаляє застарілі та **зберігає незмінним активний фокус і позицію курсора**.

```html
<!-- Приклад декларативного оновлення через HTMX -->
<button hx-post="/cart/items/42/increment"
        hx-target="#cart-summary"
        hx-swap="morph:outerHTML">
  Додати до кошика
</button>
```

### 3. React Server Components (RSC Wire Format)

Архітектура `React Server Components` поєднує переваги обох підходів: компоненти виконуються на сервері (маючи прямий доступ до бази даних та файлової системи), але транслюються клієнту не як сирий HTML і не як JSON, а у вигляді **потокового графа віртуальних вузлів** (формат *Flight*).

* **Що летить мережею:** потік серіалізованих JSON-рядків, що описують структуру компонентного дерева та слоти для інтерактивних клієнтських островів:
  ```
  1:I["./CartButton.client.js",["client.js"],"default"]
  0:["$","div",null,{"className":"cart","children":[["$","h3",null,{"children":"Кошик"}],["$","$L1",null,{"count":3}]]}]
  ```
* **Переваги:** важкі бібліотеки рендерингу (наприклад, парсери Markdown чи утиліти форматування) залишаються на сервері й не потрапляють у клієнтський бандл; клієнтський React отримує можливість безшовно вбудовувати оновлені серверні піддерева всередину клієнтських компонентів зі збереженням локального стану хуків `useState`.

![Архітектури часткового оновлення: JSON API, HTML-over-the-wire та RSC](/book/programming/client-architecture/ajax-partial-updates/img/html-over-wire-vs-json-rsc.svg)
*Порівняння моделей доставки даних: JSON API вимагає важкого клієнтського фреймворку, HTML-over-the-wire оновлює DOM напряму легким морфінгом, а RSC стрімить серіалізований граф віртуальних компонентів.*

## Аномалії паралелізму та гонитви відповідей (Out-of-Order Responses)

Найпідступніший клас дефектів у системах із фоновими запитами пов'язаний із **недетермінованим часом проходження пакетів мережею** (англ. *out-of-order response race conditions*).

Розглянемо класичний сценарій «пошук під час введення» (англ. *search-as-you-type*):
1. Користувач вводить у поле пошуку символ `«c»` о `t = 0 мс`. Скрипт надсилає фоновий запит `Req₁` на адресу `/search?q=c`.
2. Користувач дописує літери й отримує слово `«cat»` о `t = 150 мс`. Скрипт надсилає другий фоновий запит `Req₂` на адресу `/search?q=cat`.
3. Запит `Req₂` потрапляє в кеш сервера й повертається за 120 мс (`t = 270 мс`). Клієнт показує точний список результатів для слова `«cat»`.
4. Запит `Req₁` натрапив на важку вибірку в базі даних та мережевий джитер (RTT = 600 мс) і повертається о `t = 600 мс`.

Якщо клієнтський код наївно записує у DOM кожну отриману відповідь у міру її прибуття, стара відповідь для `Req₁` затре свіжі результати `Req₂`. Користувач бачить у полі введення слово `«cat»`, а в таблиці під ним — неактуальний список товарів на літеру `«c»`.

```
Хронологія гонки некерованих запитів:
t=0 мс:   Надсилання Req₁ ("c")   ───────────────────────────────────────► Прибуття (t=600 мс) ──> ЗАСТАРІЛИЙ СТАН В UI!
t=150 мс: Надсилання Req₂ ("cat") ──────────► Прибуття (t=270 мс) ──> Стан "cat" (перетерто пізніше)
```

Для гарантії узгодженості інтерфейсу застосовують два взаємодоповнюючі інженерні механізми.

### 1. Монотонна нумерація версій (Sequence Stamping)

Клієнтський менеджер запитів веде локальний цілочисельний лічильник `latestRequestId`. Кожен новий запит отримує унікальний номер. Коли асинхронний проміс завершується, обробник перевіряє, чи є номер відповіді рівним поточному максимальному значенню:

```ts
let latestRequestId = 0;

async function handleSearchInput(query: string): Promise<void> {
  const currentRequestId = ++latestRequestId;
  showLoadingIndicator();

  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`);
    const data = await response.json();

    // Якщо за час польоту запиту користувач надіслав новіший запит — ігноруємо стару відповідь
    if (currentRequestId !== latestRequestId) {
      return;
    }

    renderSearchResults(data);
  } finally {
    if (currentRequestId === latestRequestId) {
      hideLoadingIndicator();
    }
  }
}
```

### 2. Примусове скасування з'єднання через AbortController

Нумерація версій захищає DOM від перезаписування, але старий непотрібний запит продовжує споживати радіотрафік мобільного пристрою та навантажувати процесор розбором JSON.

Стандарт `AbortController` дозволяє клієнту фізично розірвати TCP/TLS-з'єднання на рівні сокета браузера:

```ts
let activeAbortController: AbortController | null = null;

async function handleSearchWithAbort(query: string): Promise<void> {
  // Скасовуємо попередній активний запит, якщо він ще в дорозі
  if (activeAbortController) {
    activeAbortController.abort();
  }

  activeAbortController = new AbortController();
  const { signal } = activeAbortController;

  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal });
    const data = await response.json();
    renderSearchResults(data);
  } catch (err: any) {
    if (err.name === "AbortError") {
      // Скасування є штатною ситуацією — тиша в логах
      return;
    }
    showErrorToast(err.message);
  }
}
```

### Дебаунс і тротлінг фонових викликів

Поєднання `AbortController` із затримкою відправлення (дебаунсом на 200–300 мс) є стандартом клієнтської оптимізації. Якщо користувач набирає слово з 10 літер, дебаунс відкладає відправлення запиту до паузи у введенні. Це зменшує кількість фонових викликів із 10 до 1–2, кардинально розвантажуючи мережевий канал та серверний бекенд.

![Гонка відповідей фонових запитів: аномалія перезаписування та захист AbortController](/book/programming/client-architecture/ajax-partial-updates/img/out-of-order-race-abort.svg)
*Некеровані запити призводять до перезаписування свіжого стану старими даними, тоді як зв'язка AbortController та Sequence ID миттєво обриває застарілі транзакції.*

Повнофункціональну реалізацію клієнтського диспетчера каналів із захистом від гонок, чергою запитів та DOM-морфінгом дивіться у [практичному проєкті надійного рушія часткового оновлення](book:programming/client-architecture/ajax-partial-updates/proj-partial-fetch-engine.md).

## Керування станом завантаження, індикаторами та відмовами мережі

Фоновий запит за своєю природою є невидимим для користувача, якщо застосунок явно не повідомить про його виконання. Неякісна обробка проміжних станів призводить або до враження «завислого інтерфейсу», або до випадкових подвійних кліків (англ. *double-submit*).

### Життєвий цикл стану запиту (State Machine)

Архітектурно надійний компонент часткового оновлення моделюється як скінченний автомат із шістьма станами:

```
IDLE ──(trigger)──> LOADING ──(stream)──> STREAMING
  ▲                    │                     │
  │                    ├──(2xx OK)───────────┼──> SETTLED_SUCCESS ──(reset)──> IDLE
  │                    ├──(503/Offline)──────┼──> RETRYING_BACKOFF ──(retry)─► LOADING
  │                    └──(4xx Error)────────┴──> ERROR_STATE ──(user action)─┘
```

1. `IDLE (Стан спокою):` компонент очікує дії користувача або таймера.
2. `LOADING (Завантаження):` мережевий запит надіслано. Відбувається:
   * деактивація кнопки дії (`disabled = true`) для захисту від повторного кліку;
   * відображення плейсхолдера або скелетної структури (*Skeleton Screen*);
   * запуск таймера скасування (*Timeout Controller*).
3. `STREAMING (Потокове читання):` надходження перших байтів через `ReadableStream` або SSE; рендеринг проміжних даних.
4. `SETTLED_SUCCESS (Успіх):` дані повністю отримано, виконано атомарну підміну DOM, стан компонентів очищено.
5. `RETRYING_BACKOFF (Очікування повтору):` тимчасовий збій мережі; інтерфейс показує ненав'язливий індикатор «Відновлення з'єднання...» і планує повторну спробу.
6. `ERROR_STATE (Помилка):` вичерпано спроби повтору або отримано фатальну помилку клієнта (HTTP 4xx); відображається пояснювальний банер із кнопкою «Спробувати знову».

![Скінченний автомат життєвого циклу фонового часткового оновлення](/book/programming/client-architecture/ajax-partial-updates/img/request-lifecycle-state-machine.svg)
*Стани фонового запиту: від початкової ініціалізації до потокового читання, повторних спроб за алгоритмом Backoff та атомарного оновлення DOM.*

### Скелетони проти блокуючих спінерів

Стандартна помилка дизайну фонових запитів — блокування всього екрана напівпрозорим оверлеєм із крутилкою-спінером (англ. *blocking modal spinner*). Такий підхід нівелює всі переваги фонових запитів, позбавляючи людину можливості читати вже завантажений контент або взаємодіяти з іншими частинами форми.

Сучасний дизайн спирається на два правила:
* **Локалізація індикації:** спінер або анімований стан має з'являтися виключно всередині того блоку, який оновлюється (наприклад, всередині самої кнопки або в шапці таблиці).
* **Скелетні екрани (Skeleton Screens):** замість порожнього місця відмальовується сіра геометрія майбутніх рядків і карток однакового розміру з фінальним контентом. Це повністю запобігає стрибкам макета (англ. *Cumulative Layout Shift*, CLS), що є критичним метричним показником продуктивності браузера.

### Класифікація помилок та експоненційний повтор із джитером

Помилки фонового обміну поділяються на три принципово різні категорії, кожна з яких вимагає специфічної реакції клієнтського рушія:

| Категорія помилки | Приклади | Дія клієнтського рушія |
| :--- | :--- | :--- |
| **Транспортний збій** | `TypeError: Failed to fetch`, обрив зв'язку, DNS timeout | Автоматичний повтор (*Exponential Backoff*) зі збереженням локальних чернеток |
| **Збій сервера (5xx)** | `500 Internal Error`, `502 Bad Gateway`, `503 Unavailable` | Повтор для статусів 503/504; для 500 — сповіщення про аварію бекенда |
| **Помилка клієнта (4xx)**| `400 Bad Request`, `401 Unauthorized`, `422 Unprocessable` | **Повтор суворо заборонено!** Показ валідаційних помилок конкретних полів форми |

Для відновлення зв'язку під час тимчасових збоїв використовують алгоритм **експоненційного відкату з випадковим тремтінням** (англ. *Exponential Backoff with Full Jitter*).

Формула розрахунку затримки перед `n`-ю спробою має вигляд:

```
t_delay = min(t_max, t_base · 2ⁿ + random(0, 1) · t_base)
```

Додавання випадкового компонента `random(0, 1) · t_base` (*Jitter*) є критично важливим: якщо сотні тисяч клієнтів втратять зв'язок через перезавантаження балансувальника навантаження, без джитера вони надішлють повторні запити синхронно в одну й ту саму секунду, що спричинить лавиноподібну відмову сервера (англ. *Thundering Herd Problem*).

## Безпека фонового обміну: CORS, CSRF та сесії

Перехід від монолітних сторінок до фонових асинхронних запитів кардинально змінює модель безпеки вебзастосунку. Оскільки скрипт на сторінці має прямий доступ до формування HTTP-запитів, браузери застосовують суворі захисні бар'єри.

### 1. Правило одного джерела та попередні запити CORS

За замовчуванням браузер забороняє JavaScript читати відповіді від іншого домену, порту або протоколу (англ. *Same-Origin Policy*). Якщо фоновий запит направлено на віддалений бекенд `api.example.com` зі сторінки `app.example.com`, браузер автоматично ініціює механізм **CORS** (англ. *Cross-Origin Resource Sharing*).

Якщо запит містить нестандартні заголовки (наприклад, `Authorization: Bearer ...` або `Content-Type: application/json`), браузер виконує попередній запит методом `OPTIONS` (англ. *Preflight Request*):

```http
Клієнт -> Сервер (Preflight):
OPTIONS /api/v1/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization

Сервер -> Клієнт:
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST, GET, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400
```

Якщо сервер не поверне заголовок `Access-Control-Allow-Origin`, браузер заблокує доступ до тіла відповіді, а проміс `fetch()` викине виняток `TypeError: Failed to fetch`.

### 2. Захист від міжсайтової підробки запитів (CSRF)

Коли браузер виконує фоновий запит, він автоматично додає до нього збережені кукі для цільового домену (якщо вказано `credentials: 'include'`). Шкідливий сайт міг би надіслати фоновий запит на `bank.com/transfer` від імені авторизованого користувача.

Для захисту від CSRF у фонових запитах застосовують дві лінії оборони:
* **Атрибут `SameSite=Lax` або `SameSite=Strict` для сесійних кукі:** забороняє браузеру прикріплювати кукі до фонових запитів, ініційованих сторонніми сайтами.
* **Анти-CSRF токени в заголовках (`X-CSRF-Token`):** сервер генерує криптографічно стійкий токен у метатегу сторінки `<meta name="csrf-token" content="...">`. Клієнтський рушій зчитує цей токен і обов'язково вставляє його в HTTP-заголовок кожного фонового мутуючого запиту (`POST`, `PUT`, `DELETE`). Оскільки шкідливий сторонній скрипт не має доступу до читання DOM чужого сайту через Same-Origin Policy, він не може підробити цей заголовок.

## Синхронізація з історією переходів та збереження URL

Коли фоновий запит змінює значну частину сторінки (наприклад, відкриває картку товару в каталозі або перемикає сторінку пагінації), виникає розрив між візуальним станом і рядком адреси браузера. Якщо користувач скопіює URL або натисне кнопку «Назад», він очікує потрапити на попередній крок перегляду, а не вилетіти з сайту.

Для вирішення цієї проблеми використовують **History API**:
* `history.pushState(state, '', newUrl)`: додає новий запис до історії браузера та змінює відображувану адресу в адресному рядку без перезавантаження сторінки.
* `history.replaceState(state, '', currentUrl)`: оновлює параметри поточного запису в історії (наприклад, актуалізує вибрані фільтри під час скролінгу).
* Обробник `window.addEventListener('popstate', event => ...)`: перехоплює натискання кнопок «Назад» і «Вперед», дозволяючи клієнтському рушію завантажити відповідний фрагмент через фоновий `fetch()` замість ініціації повної навігації.

```ts
// Синхронізація фонового оновлення з адресою сторінки
async function navigateToCategory(categoryId: number, pushHistory = true): Promise<void> {
  const url = `/catalog?category=${categoryId}`;
  const success = await engine.updateElement('main-content', '#products-grid', `/partials${url}`);

  if (success && pushHistory) {
    history.pushState({ categoryId }, '', url);
  }
}

window.addEventListener('popstate', (event) => {
  if (event.state?.categoryId) {
    navigateToCategory(event.state.categoryId, false);
  }
});
```

## Відправлення фінальних даних перед закриттям вкладки: beacon та keepalive

Класичною проблемою фонових запитів є збереження останнього стану форми або аналітики в момент закриття вкладки або переходу на інший сайт. Звичайний `fetch()` або XHR, запущений у подіях `beforeunload` чи `pagehide`, примусово обривається браузером, оскільки контекст сторінки негайно знищується.

Для гарантованого фонового збереження використовують два механізми:
1. `navigator.sendBeacon(url, data)`: асинхронно ставить невеликий POST-запит у чергу мережевого стека браузера. Запит виконується операційною системою у фоні навіть після повного закриття вкладки.
2. `fetch(url, { keepalive: true, method: 'POST', body })`: сучасна альтернатива, що дозволяє передавати налаштовані заголовки та підтримує обмежене тіло запиту (до 64 КБ), гарантуючи завершення мережевої транзакції після вивантаження документа.

## Профілювання та діагностика фонових оновлень у DevTools

Діагностика фонових оновлень вимагає системного аналізу мережевого та рендерингового шарів у панелі інструментів розробника браузера (Chrome DevTools, Firefox Developer Tools).

У вкладці **Network**:
1. Використовуйте фільтр `Fetch/XHR` для відсікання статичних картинок і стилів.
2. Звертайте увагу на колонку **Waterfall**:
   * довгий зелений інтервал *Waiting (TTFB)* вказує на повільну роботу бази даних або бекенда;
   * синій інтервал *Content Download* вказує на занадто великий розмір корисного навантаження (необхідність увімкнення компресії Brotli/Gzip або переходу на пагінацію).
3. Колонка **Initiator**: клік на рядок ініціатора відкриває точний стек викликів JavaScript, показуючи, який саме компонент або обробник події породив цей мережевий запит.

У вкладці **Performance**:
1. Запис профілю під час часткового оновлення дозволяє виявити довгі задачі (*Long Tasks* тривалістю понад 50 мс).
2. Якщо після отримання відповіді на графіку виникає високий стовпчик фази *Recalculate Style* та *Layout*, це свідчить про те, що алгоритм підміни DOM зачіпає надто великі піддерева замість точкової мутації цільового вузла.

> 🔧 **Навіщо це.**
>
> Фонове часткове оновлення — це фундаментальний вододіл між вебом як каталогом статичних документів і вебом як платформою для повноцінних програмних систем.
> 
> У реальній інженерній практиці вибір конкретного механізму визначається бізнес-вимогами до затримки, обсягу бандла та складності клієнтської логіки:
> 1. Якщо застосунок є контентним сервісом, адмін-панеллю або платформою електронної комерції — архітектура **HTML-over-the-wire (HTMX / Turbo)** зменшує розмір JavaScript-бандла на 80–90%, прибирає необхідність синхронізації схем DTO і переносить усю бізнес-валідність на сервер.
> 2. Якщо система вимагає складної офлайн-роботи, багатих канвас-редакторів або локальних розрахунків — класичний **JSON API + Single Page Application** надає повний контроль над життєвим циклом даних на клієнті.
> 3. Для високонавантажених стрічок новин та соціальних платформ **React Server Components** та **потоковий Fetch** забезпечують найкоротший час до відображення першого змістовного контенту (First Contentful Paint), позбавляючи клієнт необхідності чекати найповільніший SQL-запит на бекенді.
> 
> Незалежно від обраного стека, ізоляція каналів через `AbortController`, захист від гонок монотонними мітками версій та збереження фокусу через DOM-морфінг залишаються обов'язковим стандартом клієнтської надійності.
