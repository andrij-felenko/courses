# ⚙️ Пошук, який не морозить вікно: повний шлях від натиску до рядка на екрані

Поле пошуку над великим списком — найкоротша задача, у якій зустрічаються всі пастки фонової роботи одразу, тож на ній зручно пройти шлях цілком: від трьох рядків, що вішають вікно на першому ж символі, до робочої версії на C++ і TypeScript, де кожен натиск проходить п'ять воріт і закінчується одним із трьох чесних закінчень.

## Задача

Мільйон записів у пам'яті, поле над списком: набираєш — знизу з'являються збіги. Найкоротша реалізація виглядає безневинно:

```cpp
void onTextChanged(const std::string& text) {
    list_.setRows(search(text));      // прохід по мільйону записів
}
```

Порахуймо, скільки вона коштує:

```
записів у індексі        1 000 000
перевірка одного         ≈ 250 нс (пошук підрядка в назві)
одна відповідь           1 000 000 · 250 нс = 250 мс
слово «холодильник»      12 знаків
разом                    12 · 250 мс = 3000 мс
корисного з них          250 мс — відповідь на повне слово
```

Три секунди мертвого вікна на одне набране слово, і одинадцять відповідей із дванадцяти нікому не потрібні: поки вони рахувалися, людина набрала далі.

Очевидна латка — віддати `search` фоновому пулу:

```cpp
void onTextChanged(std::string text) {
    pool_.submit([this, text] {
        auto rows = search(text);
        postToUiThread([this, rows] { list_.setRows(rows); });
    });
}
```

Вікно перестало мерзнути — і з'явилося чотири нові дефекти. **Перший:** роботи не поменшало, вона розповзлася. Вісім ядер тепер зайняті вісьмома запитами, з яких актуальний рівно один, а решта застосунку бореться за процесор із власними привидами. **Другий:** [пул](book:programming/thread-pool) не обіцяє порядку — робота розкладається по вільних потоках, і відповідь на «холод» може прийти після відповіді на «холодильник» та затерти її. **Третій:** якщо діалог закрити посеред пошуку, завдання прилетить у чергу з покажчиком на знищений об'єкт, і застосунок упаде рівно в мить успіху. **Четвертий:** виняток усередині `search` не має куди спливти — у фоновому потоці немає ані обробника, ані вікна, — тож спінер крутитиметься вічно.

Отже, повний шлях мусить уміти п'ять речей: не запускати роботу, яку одразу викинуть; тримати в роботі щонайбільше один запит; відрізняти свіжу відповідь від застарілої; спиняти роботу, що втратила сенс; і мати дорогу назад для кожного з можливих закінчень.

## Ідея: п'ять воріт і три виходи

Кожна вимога — це одні ворота на шляху натиску.

**Ворота 1 — тиша.** Після натиску чекаємо 150 мс; будь-який новий знак переставляє таймер спочатку.
**Ворота 2 — скриня на одне місце.** Поки робітник зайнятий, нове завдання не стає в чергу, а затирає попереднє, яке ще не почалося.
**Ворота 3 — штамп.** Кожне завдання, що пішло в роботу, дістає номер покоління.
**Ворота 4 — прапорець.** Робочий цикл на межі блоку заглядає, чи його не скасували, і виходить достроково.
**Ворота 5 — дві перевірки на поверненні.** Чи живий адресат і чи не застарів штамп.

*Розподіл ролей тут не випадковий: усе, крім самої роботи, стоїть на потоці інтерфейсу.*

Розподіл справді має причину. Ворота 1–3 живуть на потоці інтерфейсу навмисно: там єдиний власник, тож таймер, скриня й лічильник не потребують ані замків, ані узгодження — їх чіпає рівно один потік. Ворота 4 — єдине, що виконується у фоні. Ворота 5 знову на потоці інтерфейсу, бо міняти дерево елементів має право тільки він.

Ворота 1 і 2 бережуть процесор: вони не дають роботі початися. Ворота 3 і 5 бережуть правильність: вони не дають показати неправильне. Ворота 4 роблять і те, і те.

## Робочий код

Від оболонки потрібно всього два гачки, і вони є в кожній: покласти функцію в чергу потоку інтерфейсу та завести одноразовий таймер, що тікає на ньому ж.

```cpp
// Qt:    void postToUiThread(std::function<void()> f) {
//            QMetaObject::invokeMethod(qApp, std::move(f), Qt::QueuedConnection);
//        }
//        UiTimer — це QTimer із setSingleShot(true)
// Win32: PostMessage(hwnd, WM_APP_RUN, 0,
//                    reinterpret_cast<LPARAM>(new std::function<void()>(f)));
//        UiTimer — SetTimer / KillTimer на тому самому вікні
// Cocoa: dispatch_async(dispatch_get_main_queue(), ^{ f(); });
```

Решта — стандартна бібліотека. Словник скасування (`std::jthread`, `std::stop_source`, `std::stop_token` із заголовка `<stop_token>`) з'явився у C++20; до нього те саме роблять власним `std::atomic<bool>` у `shared_ptr`, і код міняється лише в двох рядках.

```cpp
#include <atomic>
#include <condition_variable>
#include <mutex>
#include <stop_token>
#include <string>
#include <thread>
#include <variant>
#include <vector>

// ── Рівно три можливі закінчення, і тип за цим стежить ──────────────────────
struct Found     { std::vector<std::string> rows; };
struct Failed    { std::string message; };
struct Cancelled {};
using Outcome = std::variant<Found, Failed, Cancelled>;

struct Job {
    std::string     query;
    std::uint64_t   generation;   // штамп покоління
    std::stop_token stop;         // прапорець саме цього завдання
};

// ── Ворота 2: скриня на одне місце ──────────────────────────────────────────
class OneSlotMailbox {
public:
    // Кладе завдання, витісняючи те, що ще не почалося.
    void put(Job job) {
        { std::lock_guard lk(m_); slot_ = std::move(job); has_ = true; }
        cv_.notify_one();
    }

    // Чекає на завдання. false — робітника попросили спинитися.
    bool take(std::stop_token shutdown, Job& out) {
        std::unique_lock lk(m_);
        // Ця версія wait уміє прокинутися на request_stop і повертає значення
        // предиката, тобто false саме тоді, коли нас спиняють.
        if (!cv_.wait(lk, shutdown, [this] { return has_; }))
            return false;
        out = std::move(slot_);
        has_ = false;
        return true;
    }

private:
    std::mutex                  m_;
    std::condition_variable_any cv_;   // _any — бо лише він приймає stop_token
    Job                         slot_;
    bool                        has_ = false;
};

class SearchBox {
public:
    SearchBox(Index& index, UiWidgets& ui)
        : index_(index), ui_(ui),
          alive_(std::make_shared<std::atomic<bool>>(true)) {
        worker_ = std::jthread([this](std::stop_token st) { workerLoop(st); });
    }

    ~SearchBox() {
        alive_->store(false);       // усе, що вже летить назад, побачить мертвий прапорець
        debounce_.cancel();         // таймер не має тікати після смерті власника
        current_.request_stop();    // поточна робота хай вийде достроково
        worker_.request_stop();     // а цикл робітника — завершиться
    }                               // ~jthread приєднає потік сам

    // ── Викликається на потоці інтерфейсу з кожним натиском ──
    void onTextChanged(std::string text) {
        current_.request_stop();                     // те, що біжить, уже не потрібне
        // Ворота 1: кожен знак переставляє таймер спочатку
        debounce_.restart(150, [this, text = std::move(text)] {
            current_ = std::stop_source{};           // нове завдання — новий, чистий прапорець
            const std::uint64_t gen = ++generation_; // ворота 3; пише лише цей потік
            ui_.spinner.show();
            mailbox_.put(Job{ text, gen, current_.get_token() });
        });
    }

private:
    // ── Ворота 4: робота з поглядом у прапорець на межі блоку ──
    Outcome runSearch(const Job& job) {
        try {
            Found found;
            const auto& all = index_.records();
            for (std::size_t i = 0; i < all.size(); ++i) {
                if ((i & 0x1FF) == 0 && job.stop.stop_requested())
                    return Cancelled{};              // 512 — не магія, розрахунок нижче
                if (matches(all[i], job.query)) {
                    found.rows.push_back(all[i].title);
                    if (found.rows.size() == 200) break;   // більше на екран не влізе
                }
            }
            return found;
        } catch (const std::exception& e) {
            // Виняток тут нікуди не спливе: у фоновому потоці немає ані
            // обробника, ані вікна. Перетворюємо його на значення.
            return Failed{ e.what() };
        }
    }

    void workerLoop(std::stop_token shutdown) {
        Job job;
        while (mailbox_.take(shutdown, job)) {
            Outcome out = runSearch(job);
            // ── Ворота 5: маршалінг назад у чергу потоку інтерфейсу ──
            postToUiThread([this, alive = alive_, gen = job.generation,
                            out = std::move(out)]() mutable {
                if (!alive->load()) return;             // вікна вже немає — і крапка
                if (gen != generation_.load()) return;  // відповідь застаріла
                show(std::move(out));
            });
        }
    }

    void show(Outcome out) {          // потік інтерфейсу: ми знову власник дерева
        ui_.spinner.hide();
        if (auto* f = std::get_if<Found>(&out))
            ui_.list.setRows(std::move(f->rows));
        else if (auto* e = std::get_if<Failed>(&out))
            ui_.status.setText("Пошук не вдався: " + e->message);
        // Cancelled — не робимо нічого: запит скасував сам користувач
    }

    Index&         index_;
    UiWidgets&     ui_;
    UiTimer        debounce_;                     // одноразовий таймер потоку інтерфейсу
    OneSlotMailbox mailbox_;
    std::stop_source                   current_;      // прапорець поточного завдання
    std::atomic<std::uint64_t>         generation_{0};// пише інтерфейс, читає фон
    std::shared_ptr<std::atomic<bool>> alive_;        // живе довше за сам об'єкт
    std::jthread                       worker_;       // ОСТАННІМ: руйнується першим
};
```
```ts
// ═══ main.ts — усе тут виконується на потоці інтерфейсу ══════════════════
type Found     = { kind: "found";     ids: Uint32Array };
type Failed    = { kind: "failed";    message: string };
type Cancelled = { kind: "cancelled" };
type Reply = (Found | Failed | Cancelled) & { gen: number };

const worker = new Worker(new URL("./search-worker.js", import.meta.url),
                          { type: "module" });

// Прапорець скасування мусять бачити обидва боки ОДНОЧАСНО, а звичайного
// повідомлення робітник не побачить, доки крутить свій цикл. Тому — спільна
// пам'ять. SharedArrayBuffer живе лише на сторінці з cross-origin isolation
// (COOP: same-origin + COEP: require-corp); інакше запасний план — terminate().
const shared = crossOriginIsolated ? new SharedArrayBuffer(4) : null;
const cancelFlag = shared ? new Int32Array(shared) : null;
if (shared) worker.postMessage({ kind: "init", shared });

let generation = 0;
let debounceTimer: ReturnType<typeof setTimeout> | undefined;
let busy = false;                     // робітник зараз щось рахує
let pending: string | null = null;    // ← скриня на одне місце, ворота 2

// ── Ворота 1: 150 мс тиші ──
export function onInput(text: string): void {
  if (cancelFlag) Atomics.store(cancelFlag, 0, 1);   // те, що біжить, не потрібне
  clearTimeout(debounceTimer);                       // кожен знак переставляє таймер
  debounceTimer = setTimeout(() => start(text), 150);
}

// ── Ворота 2 і 3: скриня та штамп покоління ──
function start(text: string): void {
  if (busy) { pending = text; return; }   // витісняє попереднє нестартоване
  busy = true;
  if (cancelFlag) Atomics.store(cancelFlag, 0, 0);   // нове завдання — чистий прапорець
  const gen = ++generation;
  showSpinner();
  worker.postMessage({ kind: "search", text, gen });
}

// ── Ворота 5: onmessage — це і є маршалінг у чергу потоку інтерфейсу ──
worker.onmessage = (e: MessageEvent<Reply>) => {
  busy = false;                          // ЗВІЛЬНЯЄМО РОБІТНИКА ПЕРШИМ
  if (pending !== null) { const next = pending; pending = null; start(next); }

  const msg = e.data;
  if (msg.gen !== generation) return;    // застаріла відповідь — тихо в нікуди
  hideSpinner();
  switch (msg.kind) {
    case "found":     renderRows(msg.ids); break;
    case "failed":    showError(msg.message); break;
    case "cancelled": break;             // користувач сам передумав
  }
};

// Закриття: без цього робітник живе далі й тримає весь індекс у пам'яті
export function dispose(): void {
  clearTimeout(debounceTimer);
  if (cancelFlag) Atomics.store(cancelFlag, 0, 1);
  worker.terminate();
}

// ═══ search-worker.ts — окремий потік; DOM тут недоступний ═══════════════
let flag: Int32Array | null = null;
const records: Row[] = loadIndex();

self.onmessage = (e: MessageEvent) => {
  const msg = e.data;
  if (msg.kind === "init") { flag = new Int32Array(msg.shared); return; }
  if (msg.kind !== "search") return;

  try {
    const ids = new Uint32Array(200);
    let n = 0;
    for (let i = 0; i < records.length; i++) {
      // ── Ворота 4: погляд у прапорець на межі блоку ──
      if ((i & 0x1ff) === 0 && flag && Atomics.load(flag, 0) === 1) {
        self.postMessage({ kind: "cancelled", gen: msg.gen });
        return;
      }
      if (matches(records[i], msg.text)) {
        ids[n++] = i;
        if (n === ids.length) break;
      }
    }
    const out = ids.slice(0, n);
    // Другий аргумент — список того, що ПЕРЕДАЄМО, а не копіюємо:
    // після цього рядка out.buffer тут уже відірваний (detached).
    self.postMessage({ kind: "found", ids: out, gen: msg.gen }, [out.buffer]);
  } catch (err) {
    self.postMessage({ kind: "failed", message: String(err), gen: msg.gen });
  }
};
```

## Ворота 1: чому 150, а не 300

Затримка перед стартом — не безкоштовна обережність, а прямий платіж: відповідь на **останній** натиск приходить рівно на стільки пізніше. Отже, число не вибирають зі смаку, його виводять відніманням:

```
затримка відповіді = тиша + робота + маршалінг + малювання
150 + 250 + 0.05 + 8 ≈ 408 мс
300 + 250 + 0.05 + 8 ≈ 558 мс
```

Пороги людського сприйняття тут відомі: близько 100 мс відповідь здається миттєвою, до секунди думка ще тримається на місці. Обидва варіанти лягають у другий діапазон, і популярні «300 мс за замовчуванням» — це просто 150 мс чистого чекання ні за що. А головне видно з того ж рядка: у сотню мілісекунд не влазить **жодне** значення тиші, бо самої роботи вже 250. Дебаунс тут не той важіль, який треба крутити.

Тепер друга половина правди, про яку зазвичай мовчать. Щоб ворота 1 узагалі щось фільтрували, поріг тиші мусить перевищувати інтервал між натисками:

```
40 слів/хв ≈ 3.3 знака/с  →  інтервал 300 мс  →  300 > 150: таймер щоразу встигає
80 слів/хв ≈ 6.7 знака/с  →  інтервал 150 мс  →  150 = 150: тримається ледве
```

Для звичайного друкаря 150-мілісекундна тиша не ловить нічого: пауза між сусідніми знаками довша за поріг, тож таймер устигає спрацювати після кожного, і в роботу йдуть усі дванадцять запитів. Справжня робота цих воріт вужча, ніж каже фольклор: вони гасять **сплеск** — вставку з буфера, затиснуту клавішу з автоповтором (десятки подій за секунду), пробіг по клавіші стирання. Рівні натиски спокійного набору вони пропускають, і далі рятують уже ворота 2. Сам прийом і його близького родича названо окремо: [дебаунс і тротлінг](book:programming/debouncing-throttling) — два різні способи проріджувати потік подій, і плутати їх дорого.

## Ворота 2: чому у вебі скриня стоїть на боці інтерфейсу

Скриня на одне місце робить одну зухвалу річ: `put` не питає, чи вільно, — він **затирає**. Це припустимо саме тому, що затерте завдання ще не починалося, а отже, не існувало ні для кого, крім скрині. Рівно один рядок дає всю дисципліну обмеження: у роботі будь-коли не більше одного пошуку, у скрині — не більше одного наступного, і зростати нема чому.

У C++ скриня стоїть **між** потоками, і це працює, бо обидва боки беруть її під замком. У вебі так не вийде, і причина глибша за синтаксис. Робітник у браузері — це окремий потік із **власним** [циклом подій](book:programming/event-loop): він читає свою вхідну чергу тільки тоді, коли не зайнятий. Поки всередині крутиться синхронний `for` по мільйону записів, жодне `postMessage` до нього не буде прочитане. Отже, дванадцять натисків — це дванадцять повідомлень, які тихо лягли в чергу, недоступну ззовні: витіснити з неї нічого не можна. Вони виконаються всі один за одним, а актуальний, дванадцятий, стартує через 11 · 250 = 2750 мс.

Тому у вебі скриня переїжджає туди, де власник єдиний, — на потік інтерфейсу. Пара `busy` + `pending` робить те саме, що `OneSlotMailbox`, тільки без замків: доки попередня відповідь не повернулася, робітникові нічого не надсилають, а нове завдання просто затирає `pending`. Правило узагальнюється: **чергу, якою не керуєш, тримають порожньою**; уся дисципліна лишається на тому боці межі, де є влада щось витіснити.

## Ворота 3: штамп, який перевіряють в останню мить

Лічильник поколінь надійний не тому, що він атомарний. Атомарність тут потрібна лише для того, щоб фоновий потік читав ціле число, а не половину. Надійність дає інше: **порівняння й показ виконуються в одному ході циклу подій**, який ніхто не може розрізати. Між `gen != generation_` та `show(...)` не встигає нічого — ні новий натиск, ні нова відповідь, бо і те, і те прийде в ту саму чергу й чекатиме, доки ми повернемо керування.

Саме тому перевірку не можна робити у фоновому потоці, «щоб не тягти зайве через межу». Там між порівнянням і надсиланням є проміжок, і лічильник устигне зрушити — вийде та сама гонка, тільки на крок раніше.

> 🔧 **Навіщо це.** Тут видно, за що насправді платять правилом «інтерфейсом володіє один потік»: воно дає **безкоштовну неподільність**. Будь-яка послідовність дій усередині одного обробника — прочитати лічильник, звірити, змінити список, сховати спінер — виконується як одне ціле, без замків і без жодного шансу, що хтось утрутиться посередині. У багатопотоковому дереві кожен із цих чотирьох кроків довелося б захищати окремо, а разом — ще й узгоджувати між собою.

## Ворота 4: звідки береться 512

Крок перевірки — компроміс між двома цінами. Рідше перевіряєш — довше не помічаєш скасування; частіше — дорожче обходиться сам погляд. Порахуймо обидві.

```
час на один запис          250 нс
крок K записів  →  найгірша затримка реакції = K · 250 нс
K = 1        →  0.00025 мс
K = 512      →  0.128 мс
K = 100 000  →  25 мс — уже помітно
```

Затримку в частку мілісекунди не побачить ніхто, тож стеля кроку виводиться з простого правила: бери таке K, щоб `K · час_на_елемент ≈ 1 мс`.

```
K ≈ 1 мс / час на елемент
порівняння рядка    250 нс  →  K ≈ 4000   (512 — із запасом)
декодування кадру     4 мс  →  K = 1      (перевірка перед кожним)
```

Друга ціна тонша. Читання [атомарного прапорця](book:programming/std-atomic) з найслабшим порядком на x86 перетворюється на звичайний `mov` — одна інструкція. Але для оптимізатора атомарний доступ непрозорий: компілятор мусить припускати, що значення міняє хтось інший, тож не має права винести читання за цикл і зазвичай відмовляється векторизувати тіло, у якому воно стоїть. Внутрішній цикл, який мав виконувати чотири порівняння за такт, починає виконувати одне. Перевірка на **межі блоку** лишає гарячий цикл недоторканим, а `i & 0x1FF` — це одна інструкція AND, бо 512 є степенем двійки.

Ось звідки береться сама форма скасування: цикл сам зазирає в прапорець і сам вирішує вийти. Убити чужий потік ззовні не можна — він лишить по собі захоплені замки й недобудовані структури, — тому [кооперативне скасування](book:programming/cooperative-cancellation) закладають у роботу з першого дня, а не додають потім у готовий довгий цикл.

## Ворота 5: порядок двох перевірок

Дві перевірки на поверненні виглядають рівноправними, але переставити їх місцями не можна:

```cpp
if (!alive->load()) return;             // спершу — чи є кому показувати
if (gen != generation_.load()) return;  // і лише потім чіпаємо this
```

Другий рядок читає `generation_` — поле об'єкта, якого може вже не існувати. Перший рядок цього не робить: `alive` — це копія `shared_ptr`, узята в саме завдання, тож атомарний прапорець живе рівно доти, доки летить остання відповідь, навіть якщо `SearchBox` знищено секунду тому. Тому прапорець і не може бути звичайним полем: він мусить пережити свого власника. Той самий результат дає [слабке посилання](book:programming/weak-references) на адресата — воно теж уміє чесно сказати «об'єкта вже немає» замість того, щоб віддати покажчик у нікуди.

У JavaScript збирач сміття не дасть розіменувати мертвий об'єкт, але форма помилки повертається під іншим ім'ям: запис у компонент, який давно розмонтовано, або робітник, якого ніхто не спинив і який тримає весь індекс у пам'яті.

## Три виходи, а не два

Спокуса звести все до `optional<Rows>` — «є результат або немає» — коштує дорого, і видно це не в коді, а на екрані. Три закінчення вимагають **трьох різних реакцій інтерфейсу**:

- **результат** — замінити список, сховати спінер;
- **помилка** — очистити список і сказати, що саме сталося;
- **скасування** — сховати спінер і **не чіпати список**.

Остання відмінність і є причиною існування третього варіанта. Скасування означає, що людина набирає далі; якщо на кожен натиск очищати список, він блиматиме гірше, ніж якби показував трохи застарілі рядки. `std::variant<Found, Failed, Cancelled>` у C++ і розмічене об'єднання в TypeScript називають усі три виходи в самому типі — і дають спосіб змусити компілятор перевірити, що жоден не забуто: `std::visit` над набором лямбд не збереться, якщо бракує однієї, а в TypeScript ту саму роль грає гілка з присвоєнням у змінну типу `never`. Тип тут не прикраса, а страховка від пропуску того виходу, який найлегше пропустити.

## Що коштує сам механізм

```
на один запит:
  постановка в скриню (замок без суперечки)   ≈ 0.2 мкс
  пробудження робітника планувальником        ≈ 5–50 мкс
  перевірки прапорця, 1 000 000 / 512 = 1953  ≈ 0.002 мс
  маршалінг відповіді назад                   ≈ 5–50 мкс
  разом накладних                             ≈ 0.1 мс
робота                                        250 мс
частка накладних                              0.1 / 250 ≈ 0.04 %
```

Межа тут майже безкоштовна — але саме «тут». Те саме число проти роботи в 1 мс дає вже 10 %, а проти 50 мкс транспорт коштує дорожче за сам вантаж. Це і є той поріг, нижче якого виносити нема сенсу.

Окремо про пул, з якого починалася невдала спроба. Він нікуди не подівся — просто його місце інше: не тримати вісім застарілих пошуків одночасно, а розділити **один** пошук між ядрами. Мільйон записів ріжеться на вісім діапазонів, кожен зі своїм лічильником збігів, прапорець скасування в усіх один — той самий, що прийшов у завданні. Скриня при цьому й далі гарантує, що таких пошуків у роботі рівно один.

## Пастки

**Гонка на витісненні в скрині.** Найтихіша й найзліша. Перевірка прапорця «є завдання» й засинання мусять бути неподільні, інакше робітник устигає вирішити «порожньо, засну» рівно між тим, як інтерфейс поклав завдання й гукнув.

![Дві панелі по чотири кроки. Ліворуч «наївно: перевірити, потім заснути»: робітник перевіряє — скриня порожня; інтерфейс кладе завдання; інтерфейс кличе notify_one, коли спати ще ніхто не ліг; робітник аж тепер заходить у wait і засинає; висновок — завдання лежить у скрині, спінер крутиться вічно. Праворуч «правильно: перевірити й заснути неподільно»: робітник бере замок і бачить хибний предикат; cv.wait відпускає замок і засинає; інтерфейс бере замок, ставить has_ = true й кличе notify_one; робітник прокидається, предикат істинний, бере завдання; висновок — перевірка й засинання неподільні, прокол неможливий](img/proj-mailbox-race.svg)

*Форма `cv.wait(замок, предикат)` — не синтаксичний цукор над циклом `while`: вона гарантує, що між перевіркою предиката й засинанням замок не відпускався.*

**Живий покажчик на знищене вікно.** Крім порядку перевірок, тут є другий бік — деструктор. `~jthread` приєднує потік, тобто **чекає** на потоці інтерфейсу, а йому чекати заборонено. Припустимим це робить один рядок вище: ми спершу попросили роботу спинитися, тож очікування триває десятки мікросекунд. Приєднання без попереднього `request_stop()` перетворює закриття вікна на повне зависання до кінця пошуку.

**Витік завдання при закритті.** Витікають три різні речі, і кожну треба закрити окремо. Таймер дебаунсу, що тікає після смерті власника, — звідси `debounce_.cancel()` у деструкторі. Робітник, який спить у скрині й не знає про зупинку, — саме тому там `condition_variable_any` зі `stop_token`, а не звичайний `condition_variable`: інакше `request_stop()` не розбудить нікого й приєднання зависне назавжди. І робітник у браузері, якому не викликали `terminate()`, — він переживе компонент і триматиме індекс; на сторінці з маршрутизатором це один мертвий потік на кожен перехід.

**`busy` знімається пізніше за перевірку штампа.** В обробнику `worker.onmessage` рядок `busy = false` мусить стояти **до** раннього виходу по застарілому поколінню. Інакше перша ж застаріла відповідь лишає `busy` піднятим назавжди: `pending` перестає розбиратися, поле пошуку тихо вмирає — без помилки, без падіння й без сліду в журналі.

**Прапорець скасування, який лишився піднятим.** Один спільний прапорець на всі завдання коротший на рядок і неправильний: піднятий для сьомого завдання, він спинить восьме, яке щойно стартувало. Звідси свіжий `std::stop_source{}` на кожне завдання в C++ і `Atomics.store(flag, 0, 0)` просто перед надсиланням у TypeScript.

## Та сама форма для іншої роботи

Жодні з п'яти воріт не знають, що саме рахується у фоні. Заміни пошук на розбір відкритого файлу, побудову попереднього перегляду чи звернення до сервера — і шлях лишиться той самий, зміняться тільки дві деталі. Ворота 4 з прапорця стають перериванням самого запиту: `AbortController` для `fetch` у браузері (виклик `abort()` без аргументів відхиляє обіцянку з `DOMException` на ім'я `AbortError`, а `signal.throwIfAborted()` дає ту саму перевірку на межі блоку). А ворота 2 з локальної скрині перетворюються на [злиття однакових запитів](book:programming/request-coalescing) — коли кілька однакових звернень, що летять одночасно, обслуговує одна відповідь.

І тільки останнє питання лишається спільним для всіх варіантів, бо воно не про потоки: **чи потрібна ця робота взагалі**. Двісті п'ятдесят мілісекунд на лінійний прохід по мільйону записів — це не задача для фонового потоку, це задача для індексу. Ворота лише роблять так, щоб чекання не було видно; прибрати саме чекання вони не вміють.
