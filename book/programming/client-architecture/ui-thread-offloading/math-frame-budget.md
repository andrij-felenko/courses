# 🧮 Арифметика кадрового бюджету

Тут самий рахунок і нічого поза ним: скільки мілісекунд насправді лишається коду в одному кадрі, у скільки кадрів обійдеться задача відомої тривалості, який розмір шматка обрати при нарізці і з якої миті фонова черга перестає бути чергою й починає рости без межі. Кожне число нижче виведене з формули, що стоїть поруч, тож його можна перерахувати під свою частоту, свій рушій і свою машину.

## Скільки часу насправді твоє

Частота оновлення екрана f задає період кадру — єдиний твердий термін у всій системі:

```
P = 1 / f
60 Гц   →  P = 1000 / 60  = 16.67 мс
120 Гц  →  P = 1000 / 120 =  8.33 мс
```

Але весь період коду не належить. Розкладка, растеризація й композиція мусять поміститися в той самий кадр, і їхня частка — назвімо її e — знімається згори. Лишається бюджет коду:

```
B = P − e
```

Команда Chrome оцінює e приблизно в 6 мс і саме звідси виводить свою відому пораду «10 мс на кадр»: 16.67 − 6 = 10.67. *(Статус: усталено — за документацією моделі RAIL на web.dev, де прямо сказано, що з 16 мс браузерові потрібно близько 6 мс, звідки й береться орієнтир у 10 мс.)*

Дивитися варто не на саме B, а на його частку в періоді — вона показує, яка доля кадру взагалі дістається застосунку:

```
δ = B / P = 1 − e·f

60 Гц   →  δ = 1 − 6/16.67 = 0.640
90 Гц   →  δ = 1 − 6/11.11 = 0.460
120 Гц  →  δ = 1 − 6/8.33  = 0.280
144 Гц  →  δ = 1 − 6/6.94  = 0.136
```

Тут ховається найнеочікуваніше в усій темі. Частка e не зменшується, коли f зростає: розкладка й малювання коштують стільки, скільки коштує сцена, а не стільки, скільки разів на секунду її показують. Тому перехід із 60 на 120 Гц не ділить бюджет коду навпіл — він ділить його на 4.6. А з рівняння B = 0 випливає гранична частота, за якої кодові не лишається нічого:

```
f_max = 1 / e = 1000 / 6 ≈ 167 Гц
```

![Графік: по горизонталі частота оновлення від 50 до 170 Гц, по вертикалі бюджет коду B у мілісекундах; крива B = 1000/f − 6 круто падає й упирається в нуль біля 167 Гц, де стоїть вертикальна пунктирна асимптота з підписом; чотири позначені точки — 60, 90, 120 і 144 Гц — сполучені пунктиром із рядом підписів під віссю, у кожному частота, значення B і множник розтягу](img/math-budget-vs-hz.svg)

*Період кадру спадає як 1/f, а стала частка рушія віднімається щоразу однаково — тому бюджет коду падає значно швидше за сам період і обертається на нуль ще в межах частот, які продають у магазині.*

Число e тут — не стала природи, а виміряна властивість конкретної сцени на конкретній машині; складна сторінка з'їдає більше, порожня менше. Усі подальші розрахунки чесні рівно настільки, наскільки чесне твоє власне e.

## Скільки кадрів коштує задача

Нехай задача має чисту тривалість T — це процесорний час, без очікування. Питання «скільки кадрів вона з'їсть» має дві різні відповіді, і плутають їх постійно.

Якщо вона виконується цілою на потоці інтерфейсу, кадр не малюється весь цей час, і рахунок іде по періоду:

```
кадрів без картинки = ⌈T / P⌉
T = 200 мс, 60 Гц   → ⌈200 / 16.67⌉ = 12
```

Якщо ту саму роботу порізати на шматки по бюджету, кожен кадр малюється, але роботи в нього влазить лише B, і рахунок іде вже по бюджету:

```
шматків          n = ⌈T / B⌉ = ⌈200 / 10.67⌉ = 19
загальний час    n · P = 19 · 16.67 = 316.7 мс
```

Нарізка нічого не пришвидшує — вона обмінює одне на інше за твердим курсом:

```
розтяг = P / B = 1 / δ

60 Гц   → 16.67 / 10.67 = ×1.56
120 Гц  →  8.33 /  2.33 = ×3.57
```

Двісті мілісекунд роботи розтягуються на 317 мс при 60 Гц і на 717 мс (86 шматків) при 120 Гц. Отже, що вища частота оновлення, то дорожча плавність: не через коротший кадр сам собою, а через те, що стала частка рушія відбирає дедалі більшу долю кожного періоду.

## Чому середнє нічого не міряє

Спершу арифметика, яка показує саму поломку:

```
100 кадрів по 5 мс + 1 кадр на 200 мс
середнє = (100·5 + 200) / 101 = 6.93 мс
```

6.93 мс затишно вміщається в бюджет 10.67 — а на екрані видно ривок. Середнє провалюється не тому, що воно погано пораховане, а тому, що людина бачить окремий кадр, а не суму кадрів.

Правильна величина — частка провалених кадрів p. Якщо кадри [незалежні](book:math/independent-trials) (до цього припущення ще повернемося), то ймовірність, що ціла секунда при 60 Гц мине без жодного промаху, — це просто добуток шістдесяти однакових множників:

```
P(чиста секунда) = (1 − p)⁶⁰

p = 0.05    →  0.95⁶⁰   = 0.046
p = 0.01    →  0.99⁶⁰   = 0.547
p = 0.001   →  0.999⁶⁰  = 0.942
p = 0.0001  →  0.9999⁶⁰ = 0.994
```

Для малих p зручне наближення: ln(1 − p) ≈ −p, тому

```
(1 − p)^f ≈ e^(−p·f)
p = 0.01, f = 60  →  e^(−0.6) = 0.549   (точно 0.547)
```

Воно каже головне: значення має добуток p·f — очікуване число поганих кадрів за секунду, а не p окремо. Один і той самий відсоток промахів на 120 Гц болить удвічі частіше.

Тепер обернена задача — яке p потрібне під заданий намір:

```
(1 − p)⁶⁰ = 0.95  →  p = 1 − 0.95^(1/60) = 0.00085   (1 кадр із 1170)
(1 − p)⁶⁰ = 0.99  →  p = 1 − 0.99^(1/60) = 0.00017   (1 кадр із 5970)
```

Переклад на мову [перцентилів](book:math/percentiles-quantiles) робить цифри незручними. Умова p = 0.01 означає рівно те, що 99-й перцентиль часу кадру стоїть точно на терміні. Звіт «p99 вкладається в бюджет» звучить як перемога — а насправді описує систему, де чиста секунда трапляється трохи частіше, ніж підкидання монети.

> 🔧 **Навіщо це.** Із цих двох рядків виводиться поріг, який можна поставити у вимірювання замість суперечок. Якщо ти хочеш, щоб типова секунда взаємодії була без ривків, ціль — не 99-й перцентиль, а приблизно 99.91-й: один провалений кадр на тисячу з гаком. Різниця між «p99 під терміном» і «p99.9 під терміном» на слух здається косметичною, а в частці чистих секунд це 0.55 проти 0.94.

Скільки чекати між ривками, каже [геометричний розподіл](book:math/geometric-distribution): число кадрів до першого промаху має середнє 1/p, і в секундах це

```
середній проміжок = 1 / (p · f)
p = 0.01, 60 Гц   → 1 / 0.6 = 1.67 с
медіана = ln 2 / p ≈ 69 кадрів ≈ 1.15 с
```

Ось чому «один поганий кадр зі ста» на практиці читається як смикання приблизно раз на півтори секунди.

![Графік: по горизонталі логарифмічна вісь p від 0.0001 до 0.1, по вертикалі частка чистих секунд від 0 до 1; крива (1 − p)⁶⁰ полого йде від майже одиниці зліва й обвалюється праворуч; горизонтальна зелена пунктирна лінія на рівні 95 % перетинає криву біля p ≈ 0.00085, звідки пунктир веде до підпису; окремо позначені й підписані точки p = 0.01 з часткою 55 % і p = 0.05 з часткою 4.6 %](img/math-clean-second.svg)

*Крива падає найкрутіше саме там, де лежать «нормальні» значення: рух від p = 0.001 до p = 0.01 коштує майже половини всіх чистих секунд, хоча в звіті це виглядає як зміна одного відсотка на десять десятих.*

Тепер про припущення незалежності — воно хибне, і варто знати, у який бік. Погані кадри злипаються: пауза складання сміття, довга задача на кілька періодів, тепловий скид частоти псують не один кадр, а серію. При тій самій частці p злипання **підвищує** частку чистих секунд, бо шкода стягується в кілька місць замість того, щоб розсіятися рівномірно. Тобто (1 − p)⁶⁰ — оцінка знизу, а справжня картина звучить як «рідше, зате гірше»: замість рівномірного дрібного смикання виходять помітні зупинки. Формула лишається корисною саме тому, що помиляється в безпечний бік: якщо навіть за незалежності число виходить погане, реальність кращою його не зробить.

## Найбільший допустимий шматок

Нехай W — увесь обсяг роботи в одиницях часу, o — накладні витрати на одне повернення в цикл (поставити наступний шматок у чергу, повернутися, розігріти кеш), c — корисна робота в одному шматку. Тоді:

```
шматків          n = ⌈W / c⌉
загальний час    T(c) = W + (W / c)·o
обмеження        c + o ≤ B
```

Шукати внутрішній мінімум тут нема де — похідна ніде не обертається на нуль:

```
dT/dc = − W·o / c²  < 0  для всіх c > 0
```

Функція строго спадна, тобто чим менший шматок, тим гірше, і без обмеження оптимум утік би в нескінченність. Отже, розв'язок лежить на межі обмеження — і це весь висновок:

```
c* = B − o
```

Найбільший шматок, що ще влазить у кадр разом зі своїми накладними витратами, і є оптимальний. Частка, яку з'їдають самі накладні витрати:

```
η = o / c* = o / (B − o)

B = 10.67, o = 0.2  →  c* = 10.47 мс,  η = 1.9 %
B = 10.67, o = 1.0  →  c* =  9.67 мс,  η = 10.3 %
B =  2.33, o = 0.2  →  c* =  2.13 мс,  η = 9.4 %
```

Видно дві речі. По-перше, η зростає не пропорційно до o, а вибухає при наближенні o до B; при o ≥ B нарізка стає неможливою взагалі — шматок нульової корисної роботи однаково не влазить. По-друге, ті самі 0.2 мс накладних витрат коштують 1.9 % при 60 Гц і 9.4 % при 120 Гц: вищий бюджет прощає дорожчі переходи, менший — ні.

Далі втручається неподільність. Робота складається з елементів по w кожен, і різати можна лише між ними, тож у шматок їх входить

```
k = ⌊c* / w⌋

5000 рядків по 3 мкс, c* = 10.47 мс
k = ⌊10.47 / 0.003⌋ = 3490 рядків
n = ⌈5000 / 3490⌉ = 2 шматки
```

Звідси тверда підлога всієї затії: якщо w > c*, нарізка не допомагає ніяк, бо найдовший кадр не може бути коротшим за найбільший неподільний елемент. Нарізка обмежує час кадру згори бюджетом — але знизу її обмежує w, і саме w, а не хитрощі планувальника, визначає, чи взагалі можлива плавність.

Лишається ціна самого рішення «пора зупинитися». Питати годинник після кожного елемента коштує q на елемент, і при q, порівнянному з w, робота дорожчає вдвічі задарма. Тому годинник питають раз на m елементів, платячи за це перебігом межі щонайбільше на m·w:

```
m ≤ дозволений перебіг / w = 0.5 мс / 3 мкс ≈ 166   →  беруть m = 128
```

## Черга: закон Літтла і межа стабільності

Коли роботу винесено, з'являється черга, і про неї можна сказати дещо точне, нічого не знаючи ні про розподіл надходжень, ні про розподіл тривалостей. [Закон Літтла](book:math/littles-law) у класичному записі має вигляд L = λ·W, але W у нас уже зайняте обсягом роботи, тому час перебування позначимо R:

```
L = λ · R
```

Середня кількість завдань у системі дорівнює добуткові швидкості надходження на середній час перебування. Джон Літтл довів це 1961 року в статті «A Proof for the Queuing Formula: L = λW» (Operations Research, том 9, № 3, с. 383–387); доведення не спирається на жоден розподіл — потрібна лише стаціонарність системи. *(Статус: усталено — за первинною публікацією.)*

Прикладемо закон спершу до самих виконавців. Нехай [пул](book:programming/thread-pool) має k потоків, середня тривалість завдання s, швидкість обслуговування одного виконавця μ = 1/s. Тоді середнє число зайнятих виконавців — це рівно λ·s, і умова стабільності читається сама собою:

```
завантаження   a = λ · s
стабільність   λ < k · μ    ⟺    a < k
```

Візьмімо фільтр, що перераховується на кожен натиск клавіші за 300 мс, при швидкості друку десять символів на секунду:

```
λ = 10 /с,  s = 0.3 с,  μ = 3.33 /с
a = 10 · 0.3 = 3
```

Одному виконавцеві бракує втричі; щоб мати запас, потрібно k ≥ 4. А коли ρ = λ/(k·μ) перевищує одиницю, черга без стелі росте лінійно за часом, і час очікування разом із нею:

```
L(t) = (λ − k·μ) · t
R(t) = (ρ − 1) · t

k = 1:  λ − μ = 6.67 завдання/с
t = 5 с  →  L = 33 завдання,  R = 10 с
```

Найважливіше в цих двох рядках — чого в них немає. У них немає швидкості машини. Поки ρ > 1, черга й затримка ростуть із часом, і жодне пришвидшення сталого множника цього не змінює: щоб зупинити ріст, треба зменшити λ, збільшити μ або k — або перестати брати роботу.

Останнє й дає скриню на одне місце. Коли в системі щонайбільше одне завдання в роботі й одне на черзі, обидві величини обмежені зверху назавжди:

```
L ≤ 2,  R ≤ 2·s = 0.6 с
```

а закон Літтла тут же каже, що з нього виходить: λ_eff = L / R = μ = 3.33 /с, тобто система приймає рівно свою пропускну здатність, а решта, 6.67 завдання за секунду, відкидається. Це [протитиск](book:programming/backpressure-local) у чистому вигляді — і відкидання не втрата, поки завдання, що зникають, застарілі за побудовою.

![Дві панелі одна над одною зі спільною віссю часу від 0 до 10 секунд. Верхня — черга без стелі: пряма з нахилом 6.67 завдання за секунду росте від нуля до сімдесяти, позначена точка на п'ятій секунді з підписом про 33 завдання й вік відповіді 10 секунд. Нижня — скриня на одне місце: горизонтальна лінія на рівні двох завдань, незмінна за будь-якого напливу](img/math-queue-growth.svg)

*Обидві панелі описують той самий наплив; різниця лише в тому, чи має система право відмовити. Необмежена черга не витримує навантаження довше — вона просто переводить відмову у форму, де замість повідомлення користувач отримує дедалі старіші відповіді.*

Той самий закон працює й на черзі вводу самого потоку інтерфейсу. Під час прокрутки події надходять із частотою близько 100 на секунду; блокування на 200 мс дає R = 0.2 с, а отже

```
L = λ · R = 100 · 0.2 = 20 подій
```

двадцять накопичених подій, які цикл розбиратиме залпом одразу після звільнення.

І нарешті бюджет кадру — це те саме обмеження стабільності, записане інакше. Потік інтерфейсу є обслуговувачем із пропускною здатністю δ одиниць роботи на одиницю часу, тож дрібні операції з частотою λ_ui і ціною d кожна мусять справджувати λ_ui·d < δ:

```
300 операцій на кадр по 0.05 мс = 15 мс роботи в кадрі
15 / 16.67 = 0.90  >  δ = 0.64
```

Жодна операція тут не довга — найдовша триває 0.05 мс, і в профілі не видно нічого підозрілого. Але завантаження перевищує здатність на сорок відсотків, і кадри падатимуть із залізною регулярністю. Термін ніколи не питає, скільки триває одна операція; він питає про добуток частоти на ціну.
