# 🧮 Ціна історії: байти, секунди й корінь у формулі кроку знімка

Історія скасувань коштує двома валютами одразу — байтами пам'яті й секундами затримки на відкоті, — і кожен спосіб її зберігати платить у цих валютах у різній пропорції. Порахуймо обидві точно: скільки байтів і скільки секунд дають чисті знімки, обернені дельти, їхній гібрид і версії зі спільною структурою; після чого виведемо, як часто ставити опорний знімок, — і побачимо, звідки в цій відповіді береться квадратний корінь.

## Шість величин і одне попередження

Уся арифметика тримається на шести числах. Вимірні всі — жодне не є настроюваною думкою.

```
N  число кроків історії, які треба вміти відкотити        [кроки]
S  розмір повного стану документа                          [Б]
d  середній розмір оберненої дельти одного кроку           [Б]
σ  час поставити повний знімок на місце стану              [с]
t  час застосувати одну дельту                             [с]
k  крок опорного знімка в гібриді (знімок раз на k кроків) [кроки]
```

Попередження просте: **байти й секунди не додаються**. Вираз «пам'ять плюс час» не має сенсу, поки не названо курс обміну — скільки байтів ти готовий віддати за одну зекономлену секунду. Без цього числа задачу мінімізації навіть не сформульовано; з ним вона розв'язується в один рядок. Тому далі спершу порахуємо кожну валюту окремо, чесно, а обмінний курс уведемо аж тоді, коли без нього не обійтися.

Ще дві дрібниці, які варто зафіксувати одразу. По-перше, σ і t — це різні речі, і не лише за розміром: σ здебільшого пропорційне S (скопіювати мегабайти), тимчасом як t залежить від того, наскільки дорого коштує **інтерпретувати** дельту, і зовсім не мусить бути пропорційним d. Дельта на шістдесят байтів «змінити відступ абзацу» може коштувати двісті мікросекунд перерозкладки. По-друге, «найгірший час відновлення» — це час **стрибка** в довільну точку минулого, а не одного натискання «назад». Один крок назад коштує t у будь-якій моделі; уся дальша боротьба точиться навколо стрибків — тих, що робить панель історії або затиснута гаряча клавіша.

## Чотири моделі: пам'ять і найгірше відновлення

### Чисті знімки

Перед кожною зміною кладемо в історію повну копію стану. Щоб уміти повернутися в будь-який із N попередніх станів, потрібно N копій — жодна не є похідною від іншої, тож жодну не можна не зберігати:

```
M_знімки(N) = N · S                     [Б]
T_знімки    = σ                         [с]  — сталий, не залежить від N
```

Час відновлення тут не залежить ні від N, ні від того, куди саме стрибати: узяти потрібну копію й поставити її. Це Θ(1) **кроків**; у секундах — Θ(σ), тобто зазвичай Θ(S). Пам'ять же росте як добуток двох великих чисел, і саме це вбиває модель на великих документах.

### Обернені дельти

Замість стану зберігаємо спосіб повернутися: кожен крок тримає рівно те, що знищив, і місце, куди це вставити назад.

```
M_дельти(N) = N · d                     [Б]
T_дельти(j) = (N − j) · t               [с]  — стрибок із кроку N у крок j
T_дельти    = N · t                     [с]  — найгірше (j = 0)
```

Пам'ять пропорційна не розміру стану, а сумарному розміру змін — і це майже завжди на кілька порядків менше. Розплата — час: щоб опинитися в кроці j, треба послідовно обернути всі N − j кроків, що лежать між ним і поточним станом. Це Θ(N) кроків, тобто [лінійна складність там, де знімки давали сталу](topic:algorithms/asymptotic-complexity).

Найважливіше безрозмірне число всієї задачі народжується просто з ділення двох рядків:

```
ρ = S / d          у скільки разів знімок дорожчий за дельту в ПАМ'ЯТІ
ρ_t = σ / t        скільком дельтам знімок дорівнює в ЧАСІ
```

Для тексту ρ легко буває тридцятитисячним, а ρ_t — усього кількадесят. Ця прірва між двома відношеннями і є причиною, чому гібрид узагалі має сенс: знімок страшенно дорогий у байтах і водночас дешевий у секундах.

### Гібрид: знімок раз на k кроків

Дельти лишаємо всі, а понад них розставляємо повні знімки на кроках 0, k, 2k, 3k, …

![Горизонтальна вісь кроків історії: великі зелені кола — повні знімки на кроках 0, k, 2k, 3k, 4k, між ними по шість дрібних сірих кружків — обернені дельти. У проміжку між 2k і 3k позначено ціль стрибка j: щоб туди дістатися, ставимо знімок 2k за час σ, а тоді програємо вперед не більш ніж k−1 дельт. Унизу дві формули: пам'ять N·d + ⌈N/k⌉·S, найгірший час σ + (k−1)·t](img/checkpoint-timeline.svg)

*Обидві формули гібрида читаються просто з малюнка: знімків стільки, скільки разів k вміщається в N, а найдовший шлях до цілі — це один знімок плюс повний проміжок між знімками мінус той крок, на якому знімок уже стоїть.*

Порахуймо обидві величини строго. Знімки стоять на кроках 0, k, 2k, …, і в діапазон 0 ≤ i < N їх потрапляє рівно ⌈N/k⌉. Дельти лишаються всі — вони потрібні, щоб рухатися між знімками:

```
M_гібрид(N, k) = N · d + ⌈N/k⌉ · S ≈ N · d + N · S / k        [Б]
```

Для найгіршого часу знайдімо, як далеко ціль може відстояти від опорної точки. Найближчий знімок на кроці j або перед ним стоїть на кроці k·⌊j/k⌋, тож програти вперед доведеться

```
j − k·⌊j/k⌋   дельт,   і це число лежить у межах 0 … k−1
```

Верхня межа k−1 досягається, коли ціль стоїть безпосередньо перед наступним знімком. Отже:

```
T_гібрид(k) = σ + (k − 1) · t          [с]  — найгірше
T_серед(k)  = σ + ((k − 1)/2) · t      [с]  — у середньому по рівномірній цілі
```

І одразу — межа, за яку не варто заходити. Хоч як зменшуй k, доданок σ лишається: **знімок сам по собі є підлогою часу відновлення**. Якщо взяти k менше за ρ_t = σ/t, то (k−1)·t < σ, і сумарний час уже менш ніж удвічі перевищує підлогу — далі кожен новий знімок купує майже нічого, а платить повних S байтів. Тож корисний діапазон кроку починається приблизно з ρ_t:

```
k ≳ σ / t          нижче цієї межі пам'ять витрачається марно
```

### Версії зі спільною структурою

Четверта модель узагалі не зберігає минулого навмисно — вона його не руйнує. Документ — дерево з n вузлів по w байтів; правка не міняє вузол на місці, а створює нову версію, [переписуючи лише шлях від кореня до зміненого вузла](topic:algorithms/copy-on-write-structures). Що копіюються **рівно** предки — не менше й не більше — доводиться індукцією знизу вгору по шляху, і [це доведення разом із межами висоти для конкретних збалансованих схем розібрано окремо](topic:algorithms/copy-on-write/math-path-copying.md).

Візьмімо результат і порахуймо ціну історії. Правка вузла на глибині h створює h+1 новий вузол (сам вузол і всі його предки, включно з коренем):

```
пам'ять однієї правки = (h + 1) · w                 [Б]
```

Для збалансованого дерева h ≤ c·log₂ n зі сталою c, характерною для схеми: c ≈ 1.44 для AVL, c = 2 для червоно-чорного, c = 1 для ідеально повного. Тому

```
M_версії(N) = N · (h + 1) · w = O(N · w · log n)     [Б]
T_версії     = одне присвоєння покажчика ≈ 0         [с]
```

Час відновлення тут не просто сталий — він **порожній**: щоб повернутися у версію, поточному кореню присвоюють старий покажчик. Ніякого σ, бо нічого не копіюють; ніякого програвання, бо стара версія й так ціла. Це єдина з чотирьох моделей, у якій відкат не залежить ані від S, ані від N, ані від k.

## Чотири рядки поруч

```
модель            пам'ять                     найгірше відновлення
─────────────────────────────────────────────────────────────────────
чисті знімки      N · S                       σ              Θ(1) кроків
обернені дельти   N · d                       N · t          Θ(N) кроків
гібрид, крок k    N · d + ⌈N/k⌉ · S           σ + (k−1) · t  Θ(k) кроків
версії            N · (h+1) · w               ≈ 0            Θ(1)
```

Усі чотири лінійні за N — історія глибиною вдвічі більшою коштує вдвічі більше байтів у будь-якій моделі. Різняться лише **сталі при N**, і різняться на порядки; саме тому в цій задачі асимптотика нічого не вирішує, а вирішують числа.

## Курс обміну й мінімум за k

Тепер до головного числа гібрида. Питання «яке k правильне» має дві різні відповіді, залежно від того, як поставлено задачу.

### Коли затримка — жорстка вимога

Якщо є бюджет T_max, за який відкот мусить укластися, ніякої оптимізації не потрібно взагалі. Пам'ять M_гібрид строго спадає за k, а час строго зростає — отже, найкраще k — це найбільше з допустимих:

```
σ + (k − 1) · t ≤ T_max
k ≤ (T_max − σ) / t + 1
k_опт = min( N, ⌊(T_max − σ)/t⌋ + 1 )
```

Дві перевірки перед тим, як цим користуватися. Якщо σ ≥ T_max — схема неможлива в принципі: сам знімок не вкладається в бюджет, і жодне k не врятує. Якщо N·t ≤ T_max — знімки не потрібні зовсім: чисті дельти вже вкладаються, і k_опт = N залишає єдину опорну точку на кроці 0.

### Коли обидві валюти в грі

Якщо жорсткого бюджету немає, доводиться назвати курс. Позначмо λ — скільки байтів пам'яті ти згоден віддати за одну зекономлену секунду найгіршого відкоту; одиниця λ — байти на секунду. Тоді повна ціна набуває вигляду

```
C(k) = N·d + N·S/k + λ·(σ + (k − 1)·t)                 [Б]
```

Розкладімо на те, що від k залежить, і те, що ні:

```
C(k) = [ N·d + λ·σ − λ·t ]  +  N·S/k  +  λ·t·k
     =        const        +   A/k    +   B·k

A = N · S      [Б · крок]
B = λ · t      [Б / крок]
```

Стала частина на вибір k не впливає, тож мінімізуємо саме A/k + B·k. [Похідна](topic:math/derivative) за k:

```
C′(k) = −A/k² + B
```

Прирівнюємо до нуля й розв'язуємо:

```
−A/k² + B = 0
B · k² = A
k* = √(A / B) = √( N · S / (λ · t) )
```

Що це справді мінімум, а не максимум, видно з другої похідної: C″(k) = 2A/k³ > 0 при k > 0, тож функція [опукла на всьому додатному промені](topic:math/convex-functions) — стаціонарна точка там єдина й [є глобальним мінімумом](topic:math/extrema). Підставимо k* назад:

```
A/k* + B·k* = A·√(B/A) + B·√(A/B) = √(A·B) + √(A·B) = 2·√(A·B)
```

Отже, мінімальна ціна дорівнює подвоєному кореню з добутку — і, що варте окремої уваги, **в оптимумі обидва доданки рівні між собою**: пам'ять на знімки коштує рівно стільки, скільки коштує час на програвання. Це не збіг, і зараз стане видно, чому.

![Графік ціни гібрида як функції k. Синя спадна гіпербола — пам'ять A на k, червона зростна пряма — час B помножити на k, товста темна крива — їхня сума з мінімумом. Штрихові лінії позначають точку k зірочка й рівень два корені з A на B. Світла смуга від k зірочка навпіл до двох k зірочка показує, що всередині неї ціна перевищує мінімум щонайбільше на чверть. Праворуч — формули виведення й зауваження про плаский мінімум](img/cost-curve.svg)

*Дві складові ціни тягнуть k у протилежні боки: пам'ять хоче k якнайбільшого, час — якнайменшого. Мінімум суми стоїть там, де криві перетинаються, — і саме перетин, а не якась особлива точка кожної з них, задає відповідь.*

## Звідки корінь

Корінь у k* не є артефактом обчислення похідної. Він неминучий, і це видно щонайменше з трьох незалежних боків.

**Алгебра без похідної.** Візьмімо тотожність, яку легко перевірити розкриттям квадрата:

```
A/k + B·k = ( √(A/k) − √(B·k) )² + 2·√(A·B)
```

Справді, квадрат різниці дає A/k − 2·√(A/k · B·k) + B·k, а середній доданок дорівнює −2·√(A·B), який другий доданок і повертає. Квадрат ніколи не від'ємний, тож ліва частина ніколи не менша за 2·√(A·B), а рівність настає рівно тоді, коли квадрат дорівнює нулю:

```
√(A/k) = √(B·k)   ⟹   A/k = B·k   ⟹   k² = A/B   ⟹   k* = √(A/B)
```

Той самий результат, здобутий без жодного аналізу, — і водночас доведення, що це глобальний мінімум, а не локальний.

**Чому саме рівність двох доданків.** Перемножмо їх:

```
(A/k) · (B·k) = A · B          — від k НЕ ЗАЛЕЖИТЬ
```

Ось суть справи. Хоч як крути k, добуток двох частин ціни лишається сталим: k здатне лише **перерозподіляти** ціну між пам'яттю й часом, але не зменшити їхній добуток ані на йоту. А серед додатних чисел зі сталим добутком найменшу суму дають рівні числа — і прирівняти щось, пропорційне k, до чогось, пропорційного 1/k, можна лише через k², тобто через корінь. Корінь тут — це просто рівність двох плечей ваги, у якої добуток плечей закріплено.

**Перевірка одиницями.** A вимірюється в байто-кроках, B — у байтах на крок. Побудувати з них величину, що вимірюється в кроках, можна єдиним способом:

```
[A / B] = (Б · крок) / (Б / крок) = крок²
```

Отже, кроки дає лише √(A/B). Розмірність не лишає корінню альтернатив ще до того, як ми взагалі щось порахували.

## Наскільки точним треба бути з k

Практично найважливіше питання про будь-який оптимум: що станеться, якщо промахнутися. Підставмо k = m·k*, де m — множник промаху. Оскільки A/k* = B·k* = √(A·B), маємо

```
A/(m·k*) + B·m·k* = √(A·B) · (1/m + m)
```

Поділивши на мінімум 2·√(A·B), дістаємо чисто число, у якому не лишилося жодного параметра задачі:

```
C(m·k*) / C(k*) = (m + 1/m) / 2
```

```
m      1.0    1.5    2.0    3.0    5.0    10.0
─────────────────────────────────────────────────
плата  1.00   1.08   1.25   1.67   2.60   5.05
```

Мінімум напрочуд плаский і симетричний: помилитися вдвічі — хоч у більший, хоч у менший бік — коштує чверті. Звідси цілком практичний висновок: k* треба порахувати, щоб знати порядок, а тоді округлити до зручного степеня двійки й більше до нього не повертатися. Точність понад «у межах удвічі» купує менш ніж двадцять п'ять відсотків і не варта жодного налаштування.

І зворотний хід, який часто корисніший за прямий. Якщо k уже обрано з бюджету затримки, формулу можна прочитати навпаки й дізнатися, у яку ціну ти неявно оцінив секунду:

```
λ = N · S / (k² · t)          [Б/с]
```

Це гранична ціна — скільки байтів коштує **наступна** зекономлена секунда при поточному k, а не середня по всьому шляху. Через опуклість кривої середня завжди нижча за граничну.

> 🔧 **Навіщо це.** Усі вхідні числа міряються за півгодини: S — розмір серіалізованого стану, d — середній розмір оберненої дельти в журналі, t і σ — час їхнього застосування під профілювальником. Далі формули віддають решту без здогадів. ρ_t = σ/t каже, чи знімки взагалі щось дадуть; k ≤ (T_max − σ)/t + 1 — найбільше k під бажану затримку; k* = √(N·S/(λ·t)) — оптимум, коли жорсткого бюджету немає; λ = N·S/(k²·t) — у скільки байтів обране k неявно оцінило секунду. А (m + 1/m)/2 каже, наскільки взагалі варто цим перейматися.

## Числа

### Текстовий редактор

```
S = 2·10⁶ Б      (2 МБ тексту)
d = 64 Б         (обернена дельта одного натискання)
t = 3·10⁻⁶ с     (застосувати дельту й позначити абзац на перерозкладку)
σ = 2·10⁻⁴ с     (поставити знімок 2 МБ)
N = 10 000
```

```
ρ   = S/d = 2·10⁶ / 64      = 31 250   знімок = 31 тисяча дельт у пам'яті
ρ_t = σ/t = 2·10⁻⁴ / 3·10⁻⁶ ≈ 67       знімок = 67 дельт у часі

чисті знімки:  10⁴ · 2·10⁶  = 2·10¹⁰ Б = 20 ГБ         відкот 0.2 мс
обернені дельти: 10⁴ · 64   = 6.4·10⁵ Б = 640 КБ       відкот 10⁴·3 мкс = 30 мс
```

Тридцять мілісекунд на стрибок — це вже помітно (кадр при 60 Гц триває 16.7 мс), тож поставмо бюджет T_max = 16 мс:

```
k ≤ (16·10⁻³ − 2·10⁻⁴) / 3·10⁻⁶ + 1 = 15.8·10⁻³ / 3·10⁻⁶ + 1 ≈ 5267
беремо k = 5000  ⟹  ⌈10 000 / 5000⌉ = 2 знімки

пам'ять    = 640 КБ + 2 · 2 МБ = 4.64 МБ
найгірше   = 0.2 мс + 4999 · 3 мкс = 15.2 мс          ✓ в бюджеті
```

Ціна питання: чотири мегабайти пам'яті вдвічі скорочують найгірший стрибок. Гранична ціна секунди тут λ = 10⁴·2·10⁶ / (5000² · 3·10⁻⁶) ≈ 2.7·10⁸ Б/с, тобто близько 270 кілобайтів за кожну наступну зекономлену мілісекунду.

### Растровий редактор

```
S = 2.56·10⁸ Б   (полотно 8000 × 8000 × 4 Б = 256 МБ)
d = 1.0·10⁶ Б    (обернена дельта мазка: прямокутник 512 × 512 × 4 Б)
t = 3·10⁻⁴ с     (застосувати дельту в полотно й перескласти шари)
σ = 3.2·10⁻² с   (32 мс на повний знімок полотна)
N = 2000
```

```
ρ   = 2.56·10⁸ / 10⁶      = 256      знімок = 256 дельт у пам'яті
ρ_t = 3.2·10⁻² / 3·10⁻⁴   ≈ 107      знімок = 107 дельт у часі
                                     ⟹ k менше за ~107 не купує нічого

чисті знімки:    2000 · 256 МБ = 512 ГБ                 відкот 32 мс
обернені дельти: 2000 · 1 МБ   = 2 ГБ                   відкот 2000·0.3 мс = 600 мс
```

Тут ρ перевищує ρ_t лише у два з половиною рази — проти майже п'ятисот у текстовому редакторі, — і це відразу видно в результаті: знімок купує менше часу за ту саму пам'ять. Візьмімо бюджет T_max = 200 мс — стільки ще терпимо для стрибка по панелі історії:

```
k ≤ (0.2 − 0.032) / 3·10⁻⁴ + 1 = 561
беремо k = 512  ⟹  ⌈2000 / 512⌉ = 4 знімки

пам'ять    = 2 ГБ + 4 · 256 МБ = 3.02 ГБ
найгірше   = 32 мс + 511 · 0.3 мс = 185 мс             ✓ в бюджеті
```

Один гігабайт пам'яті скорочує найгірший стрибок із 600 мс до 185 мс — і глибше вже не опуститися нижче за підлогу σ = 32 мс, скільки б знімків не ставити.

### Діалог налаштувань

```
S = 4·10³ Б      (тридцять полів)
d = 40 Б
N = 50
```

Тут уся арифметика вкладається в один рядок: чисті знімки коштують 50 · 4 КБ = 200 КБ, обернені дельти — 2 КБ. Обидва числа — нуль на тлі будь-якого бюджету, тож перемагає та модель, у якій менше коду, тобто знімки. Загальне правило-поріг:

```
знімки допустимі, поки  N · S ≤ M_бюджет   ⟺   N ≤ M_бюджет / S
для M_бюджет = 1 МБ і S = 4 КБ:  N ≤ 250 кроків
```

### Версії на векторному документі

```
n = 10⁶ вузлів     w = 64 Б      S = n·w = 64 МБ      N = 10 000 правок
h ≈ log₂ 10⁶ ≈ 20         ідеально збалансоване
h ≤ 1.44 · log₂ n ≈ 28    AVL, найгірше
h ≤ 2 · log₂ n    ≈ 40    червоно-чорне, найгірше
```

```
пам'ять однієї правки = (h+1) · w
                      = 21 · 64 = 1 344 Б   (ідеально)
                      = 29 · 64 = 1 856 Б   (AVL)
                      = 41 · 64 = 2 624 Б   (червоно-чорне)

M_версії(10 000) = 13.4 МБ … 26.2 МБ
M_знімки(10 000) = 10⁴ · 64 МБ = 640 ГБ
```

Відношення — приблизно 1 : 48 000, і це та сама заміна множника S на множник w·log₂ n у сталій при N. Час відновлення при цьому в обох моделях сталий, але у версій він менший навіть за σ: одне присвоєння покажчика проти копіювання 64 МБ.

## Чого ці формули не бачать

Усе пораховане вище рахує **нові** байти — ті, що модель дописує на кожному кроці. Але історія тримає живими ще й старі, і цей доданок у формулах M(N) не з'являється, хоч часто перевершує їх усі разом.

Уяви крок i, який видаляє об'єкт розміром G байтів — вставлене зображення, сторінку, шар. Об'єкт не зникне з пам'яті, поки живий бодай один крок історії, здатний його повернути. Скільки разів він фізично лежить у пам'яті, залежить від моделі:

```
чисті знімки:    G · i        — об'єкт лежить у КОЖНОМУ зі знімків
                                 до кроку i, бо кожен знімок — глибока копія
обернені дельти: G            — рівно один раз, усередині оберненої дії кроку i
версії:          G            — рівно один раз, піддерево лишається досяжним
                                 зі старих коренів
```

Для G = 200 МБ і видалення на сороковому кроці це 8 ГБ проти 200 МБ — сорокакратна різниця, якої в асимптотиках немає взагалі. (Знімки можна врятувати, зберігаючи важкі корисні дані за посиланням, а не копією, — але це вже й є модель версій, лише названа інакше.)

Повний облік живої пам'яті історії має два доданки, і другий не обмежений ані n, ані S:

```
M_жива = M_структури + Σᵢ Gᵢ
       = O(N · w · log n)  +  сума всього видаленого, що ще досяжне
```

Наскільки другий доданок домінує, легко оцінити. Хай сесія в середньому видаляє g байтів корисних даних на крок; тоді на N кроках

```
Σ Gᵢ / M_структури = N·g / (N · (h+1) · w) = g / ((h+1)·w)
для g = 1 МБ, h = 20, w = 64 Б:   10⁶ / 1 344 ≈ 744
```

Сімсот сорок чотири рази. Тобто вся акуратна арифметика логарифмів дає доданок, який тоне в **сімсоткратно** більшому доданку від видалених даних. Практичний наслідок один: обмежувати історію треба не числом кроків, а сумою байтів, які вона тримає живими, — бо один крок може важити сорок байтів, а може двісті мегабайтів, і жодна формула вигляду N·(стала) про це не знає нічого.

Обрізання історії до останніх K кроків обмежує цей доданок згори сумою видаленого за ці K кроків. Але лише за умови, що обрізання справді відпускає посилання: поки на видалений об'єкт указує бодай один живий крок, у формулі M_жива він рахується повністю, скільки б записів формально не викинули зі списку.
