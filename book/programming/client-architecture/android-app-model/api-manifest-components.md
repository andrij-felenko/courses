# 📋 Декларативний контракт Android: вузли маніфесту та атрибути компонентів

Файл `AndroidManifest.xml` є обов'язковим кореневим контрактом кожного пакета Android (APK/AAB). Під час інсталяції системна служба `PackageManagerService` розбирає скомпільований бінарний XML (`axml`), формує внутрішнє дерево об'єктів `PackageParser.Package` та реєструє точки входу, фільтри намірів і вимоги безпеки без завантаження байткоду застосунку в пам'ять.

Під час збирання проєкту вихідний текстовий XML перетворюється компілятором ресурсів AAPT2 у двійковий формат таблиці рядків та вузлів (Binary XML). Це дозволяє демону `system_server` миттєво зчитувати метадані застосунків під час завантаження операційної системи, зіставляти тисячі фільтрів намірів у пам'яті за частки мілісекунди та перевіряти цифрові підписи без запуску віртуальної машини ART.

Нижче наведено структурований довідник ключових XML-вузлів, системних атрибутів та правил маршрутизації.

## Ієрархія кореневих вузлів маніфесту

Типова структура документа складається з оголошення дозволів, блоку застосунку та набору оголошених компонентів:

```xml
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools"
    package="com.example.app">

    <!-- 1. Запити дозволів та апаратних функцій -->
    <uses-permission android:name="android.permission.INTERNET" />
    <uses-feature android:name="android.hardware.camera.any" android:required="false" />

    <!-- 2. Декларація власних дозволів для міжпроцесного зв'язку -->
    <permission
        android:name="com.example.app.permission.READ_DATA"
        android:protectionLevel="signature" />

    <!-- 3. Декларація видимості пакетів (Android 11+) -->
    <queries>
        <intent>
            <action android:name="android.intent.action.VIEW" />
            <data android:scheme="https" />
        </intent>
    </queries>

    <!-- 4. Головний вузол застосунку та його компоненти -->
    <application
        android:name=".AppController"
        android:label="@string/app_name"
        android:icon="@mipmap/ic_launcher"
        android:allowBackup="false"
        android:extractNativeLibs="false">

        <activity android:name=".MainActivity" android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>

        <service android:name=".SyncService" android:exported="false" />
        <receiver android:name=".BootReceiver" android:exported="false" />
        <provider android:name=".DataProvider" android:authorities="com.example.app.provider" android:exported="false" />

    </application>
</manifest>
```

## Атрибути вузлів компонентів та керування стеком задач

Кожен із чотирьох типів компонентів налаштовується спеціалізованим набором XML-атрибутів, які визначають правила їхньої ізоляції, видимість для сторонніх програм та поведінку в стеку задач операційної системи.

Особливе місце посідає атрибут `android:launchMode`, що керує створенням екземплярів `Activity` в об'єктах `TaskRecord` системної служби `ActivityTaskManager`:
- **`standard`:** створює новий екземпляр активності щоразу під час надходження відповідного наміру, навіть якщо такий екран уже існує у поточному стеку.
- **`singleTop`:** якщо екземпляр цієї активності вже знаходиться на самій вершині поточного стека задач, новий екземпляр не створюється. Замість цього система доставляє новий намір через метод зворотного виклику `onNewIntent(Intent)`.
- **`singleTask`:** активність створюється як корінь нового стека задач або переміщується на вершину наявного стека, знищуючи всі інші активності над собою (механізм Clear-Top).
- **`singleInstance`:** активність завжди виконується у власному ізольованому стеку задач, де вона є єдиним елементом; будь-які дочірні екрани, відкриті з неї, запускаються в окремих сторонніх стеках.
- **`singleInstancePerTask`:** активність завжди відкривається як кореневий елемент нового незалежного стека задач (актуально для складних багатовіконних інтерфейсів на планшетах та складних пристроях).

| Компонент | Ключові атрибути | Призначення та поведінка |
| :--- | :--- | :--- |
| `<activity>` | `android:exported` | Доступність для запуску зовнішніми застосунками (`true`/`false`). Починаючи з Android 12, обов'язковий за наявності `<intent-filter>`. |
| `<activity>` | `android:launchMode` | Режим створення екземпляра в стеку задач: `standard`, `singleTop`, `singleTask`, `singleInstance`, `singleInstancePerTask`. |
| `<activity>` | `android:configChanges` | Список апаратних або системних змін (наприклад, `orientation\|screenSize\|uiMode`), які компонент обробляє вручну без перезапуску. |
| `<activity>` | `android:taskAffinity` | Ім'я стека задач, до якого тяжіє активність (за замовчуванням дорівнює імені пакета). |
| `<service>` | `android:process` | Ім'я процесу ОС. Значення з двокрапкою (наприклад, `:sync`) створює ізольований процес пакета. |
| `<service>` | `android:foregroundServiceType` | Обов'язкова типізація фонової служби (Android 10+): `camera`, `location`, `dataSync`, `mediaPlayback`, `shortService`. |
| `<service>` | `android:permission` | Рядковий дозвіл, який повинен мати клієнт для зв'язування чи запуску служби. |
| `<receiver>` | `android:directBootAware` | Дозвіл на запуск приймача до розблокування екрана користувачем (робота з пам'яттю `Device Protected Storage`). |
| `<provider>` | `android:authorities` | Унікальне ідентифікаційне ім'я простору URI (наприклад, `com.example.app.provider`). |
| `<provider>` | `android:grantUriPermissions` | Дозвіл на тимчасову передачу доступу до конкретних URI стороннім застосункам через прапорці Intent. |
| `<provider>` | `android:initOrder` | Цілочисловий порядок ініціалізації провайдерів під час старту процесу (більше число — раніший старт). |

### Небезпека перехоплення конфігурації через `android:configChanges`

Атрибут `android:configChanges` часто використовується розробниками для запобігання знищенню та перестворенню `Activity` під час обертання екрана (`orientation|screenSize`). Проте таке використання створює значний архітектурний борг: застосунок перестає автоматично оновлювати ресурси (розміри шрифтів, локалізовані рядки, альтернативні макети для альбомної орієнтації, кольори темної та світлої теми) та ламається в багатовіконному режимі (Multi-Window) або на складних смартфонах (Foldables), де розмір вікна змінюється динамічно. Правильним підходом є збереження стану через `ViewModel` та `SavedStateHandle`, а не блокування життєвого циклу активності.

## Специфікація фільтрів намірів (`<intent-filter>`)

Фільтр намірів визначає типи явних та неявних повідомлень, на які компонент готовий відповідати у загальній системній шині. Якщо компонент не має жодного оголошеного фільтра, він може бути викликаний виключно явним наміром із зазначенням точного імені класу всередині свого пакета.

Складові фільтра перевіряються системною службою `PackageManagerService` у суворій послідовності:

### 1. Звіряння дії (`<action>`)

Рядковий ідентифікатор операції. У фільтрі може бути оголошено декілька дій. Намір вважається валідним за дією, якщо його рядок `action` збігається хоча б з одним елементом `<action>` у фільтрі. Якщо намір не вказує жодної дії, а фільтр містить хоча б одну, перевірка завершується невдачею.

```xml
<action android:name="android.intent.action.VIEW" />
<action android:name="android.intent.action.EDIT" />
```

### 2. Звіряння категорії (`<category>`)

Додатковий контекст виконання операції. Для неявних намірів, що викликаються через метод `startActivity()`, наявність категорії `android.intent.category.DEFAULT` у фільтрі є обов'язковою, оскільки операційна система автоматично додає цей прапорець до кожного виклику `startActivity`. Якщо фільтр не містить категорії `DEFAULT`, жоден неявний намір запуску активності не зможе його знайти.

| Категорія | Опис |
| :--- | :--- |
| `android.intent.category.DEFAULT` | Дозволяє компоненту відповідати на неявні наміри запуску. |
| `android.intent.category.LAUNCHER` | Позначає активність як головну точку входу для відображення в системному лаунчері. |
| `android.intent.category.BROWSABLE` | Дозволяє відкривати активність через посилання з веббраузера (Deep Links / App Links). |
| `android.intent.category.HOME` | Реєструє активність як альтернативний домашній екран (лаунчер). |

### 3. Звіряння даних та MIME-типів (`<data>`)

Визначає структуру URI та формат корисного навантаження, які компонент здатен обробляти:

```xml
<data
    android:scheme="https"
    android:host="example.com"
    android:port="443"
    android:pathPrefix="/item/"
    android:mimeType="application/pdf" />
```

Атрибути `path`, `pathPrefix` та `pathPattern` підтримують зіставлення шляху:
- `path`: точний збіг рядка.
- `pathPrefix`: зіставлення за початком шляху.
- `pathPattern`: просте зіставлення з використанням символів `*` (будь-яка кількість символів) та `.*`.

## Фільтрація видимості пакетів через блок `<queries>`

Починаючи з Android 11 (API level 30), операційна система за замовчуванням блокує можливість застосунків вичитувати повний список установлених на пристрої програм через метод `PackageManager.getInstalledPackages()`. Це обмеження запроваджено для захисту приватності користувача та унеможливлення цифрового профілювання (fingerprinting) за набором встановленого програмного забезпечення.

Якщо застосунок повинен взаємодіяти з конкретними сторонніми програмами (наприклад, відкривати PDF-файли, надсилати повідомлення через месенджери або перевіряти наявність платіжних клієнтів), він зобов'язаний декларативно вказати свої наміри у вузлі `<queries>`:

```xml
<queries>
    <!-- Дозвіл бачити конкретний відомий пакет -->
    <package android:name="com.example.payment.gateway" />

    <!-- Дозвіл бачити будь-які програми, здатні відкривати вебсторінки -->
    <intent>
        <action android:name="android.intent.action.VIEW" />
        <data android:scheme="https" />
    </intent>
</queries>
```

## Ініціалізація компонентів та порядок старту

Під час запуску процесу застосунку операційна система виконує послідовність викликів у суворо визначеному порядку:
1. Завантаження нативних бібліотек та виклик коду завантажувача класу.
2. Створення екземпляра класу `Application` та виклик його методу `attachBaseContext()`.
3. **Ініціалізація всіх оголошених `<provider>` (ContentProvider):** система створює екземпляри всіх провайдерів цього процесу та викликає їхні методи `onCreate()` у порядку, заданому цілочисловим атрибутом `android:initOrder` (від більшого значення до меншого).
4. Виклик методу `Application.onCreate()`.
5. Створення цільового компонента (`Activity`, `Service` або `BroadcastReceiver`), заради якого процес було піднято.

Ця послідовність активно використовувалася бібліотеками для автоматичної самоініціалізації (наприклад, Firebase чи Jetpack App Startup) до появи стандартизованих механізмів ініціалізації.

## Рівні захисту дозволів (`android:protectionLevel`)

Тег `<permission>` дозволяє застосунку створювати власні дозволи безпеки:

```xml
<permission
    android:name="com.example.app.permission.ACCESS_INTERNAL_API"
    android:protectionLevel="signature" />
```

| Рівень захисту | Правило надання ОС |
| :--- | :--- |
| `normal` | Автоматично надається під час встановлення. Низький ризик (наприклад, доступ до мережі, зміна шпалер). |
| `dangerous` | Вимагає явного запиту в користувача під час виконання (Runtime Permissions) через діалогове вікно (камера, мікрофон, локація). |
| `signature` | Надається автоматично лише тим застосункам, які підписані тим самим сертифікатом (RSA/EC), що й пакет, який оголосив дозвіл. |
| `signatureOrSystem` (застарілий) | Доступний пакетам із тим самим підписом або встановленим у системний розділ `/system/priv-app`. |
| `privileged` | Додатковий прапорець для системних застосунків, внесених у білий список прошивки. |

## Керування злиттям маніфестів (Manifest Merger)

Під час складання проєкту за допомогою Gradle інструмент `Manifest Merger` об'єднує маніфести головного застосунку, бібліотек (AAR) та збіркових варіантів (Build Variants). Дерево пріоритетів виглядає наступним чином: `Build Type` > `Product Flavor` > `Main Manifest` > `Included AAR Libraries`.

Якщо бібліотека декларує властивість або компонент, що конфліктує з конфігурацією головного застосунку (наприклад, інше значення `android:allowBackup` або застарілий `minSdkVersion`), збирач генерує помилку. Для керування злиттям використовуються директиви простору імен `xmlns:tools="http://schemas.android.com/tools"`:

```xml
<application
    android:name=".CustomApp"
    android:allowBackup="false"
    tools:replace="android:allowBackup,android:name">

    <!-- Примусове видалення сервісу зі сторонньої бібліотеки -->
    <service
        android:name="com.library.analytics.TrackerService"
        tools:node="remove" />

    <!-- Примусове об'єднання властивостей -->
    <activity
        android:name="com.library.auth.AuthActivity"
        tools:node="merge" />
</application>
```

| Маркер `tools:node` | Результат роботи Manifest Merger |
| :--- | :--- |
| `merge` (за замовчуванням) | Об'єднує атрибути та дочірні елементи вузлів із бібліотеки та застосунку. |
| `replace` | Повністю замінює вузол із бібліотеки версією з головного маніфесту. |
| `remove` | Видаляє відповідний вузол з остаточного скомпільованого маніфесту. |
| `removeAll` | Видаляє всі екземпляри зазначеного елемента. |
| `strict` | Генерує помилку збірки, якщо елементи з бібліотеки та застосунку не збігаються байт-у-байт. |
