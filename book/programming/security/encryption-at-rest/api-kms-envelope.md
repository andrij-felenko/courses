# 📋 Інтерфейс сервісу ключів KMS для конвертного шифрування

Сервіс керування ключами (англ. *Key Management Service*, KMS) надає централізований криптографічний інтерфейс, який дозволяє клієнтським додаткам виконувати операції шифрування та розгортання ключів без ризику витоку кореневих ключів шифрування ключів (KEK) у відкритому вигляді за межі захищеного апаратного периметра. Нижче наведено вичерпну специфікацію програмного контракту KMS для конвертної моделі (англ. *envelope encryption*), протокольні формати повідомлень, механіку канонізації контексту автентифікації (AAD), життєвий цикл ключів за стандартом NIST SP 800-57 та детальну семантику обробки збоїв.

### Мережева модель та протокольна взаємодія

Взаємодія між клієнтською бібліотекою (SDK) та сервісом KMS будується поверх транспортного протоколу TLS 1.3 із обов'язковою взаємною автентифікацією сторін (mTLS) або підписанням кожного HTTP-запиту асиметричними токенами доступу (наприклад, AWS SigV4 чи OAuth 2.0 PoP). Для мінімізації затримок на встановлення з'єднань клієнтський стек підтримує пул довгоживучих HTTP/2 або gRPC з'єднань із механізмом TCP keep-alive та періодичним зондуванням працездатності.

Усі запити до KMS є строго авторизованими: перед виконанням будь-якої криптографічної операції сервіс обчислює політику доступу (IAM Policy), перевіряє права викликача щодо конкретного ресурсу KEK, зіставляє обмеження за IP-адресою, VPC-ендпоінтом та перевіряє передані контекстні обмеження.

### Специфікація методів API

#### 1. Метод `GenerateDataKey`

Метод генерує новий криптографічно стійкий симетричний ключ шифрування даних (DEK), повертаючи його клієнту одночасно у двох формах: у відкритому вигляді (для негайного виконання локального шифрування в оперативній пам'яті) та в зашифрованому цільовим KEK вигляді (для збереження поруч із шифротекстом у постійному сховищі).

```
RPC:      kms.v1.KeyService/GenerateDataKey
HTTP/REST: POST /v1/keys/{KeyId}/generate-data-key
```

**Параметри запиту (Request Parameters):**

| Поле | Тип | Обов'язкове | Опис |
| :--- | :--- | :--- | :--- |
| `KeyId` | `string` | Так | Унікальний ідентифікатор (ARN, UUID або системний аліас) ключа KEK усередині сховища KMS. |
| `KeySpec` | `string` | Ні | Специфікація стандарту та довжини ключа: `AES_256` (за замовчуванням) або `AES_128`. |
| `NumberOfBytes` | `integer` | Ні | Довільна довжина ключа у байтах (наприклад, 32 або 64). Взаємовиключне з параметром `KeySpec`. |
| `EncryptionContext` | `map<string, string>` | Ні | Набір пар «ключ-значення» додаткових автентифікованих даних (AAD). |
| `GrantTokens` | `list<string>` | Ні | Список криптографічних токенів тимчасового делегування прав для розподілених вузлів. |

**Структура відповіді (Response Parameters):**

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `KeyId` | `string` | Канонічний ідентифікатор (ARN) ключа KEK, який виконав операцію запечатування DEK. |
| `Plaintext` | `bytes` (base64) | Відкритий 256-бітний ключ DEK (32 байти). Додаток зобов'язаний затерти його після шифрування. |
| `CiphertextBlob` | `bytes` (base64) | Зашифрований за допомогою KEK ключ DEK (загорнутий конверт, що містить зашифрований DEK, IV та тег). |
| `KeyProvider` | `string` | Системний ідентифікатор модуля безпеки HSM, у якому сформовано ентропію для ключа. |

**Внутрішній механізм виконання:**
1. Модуль безпеки HSM вичитує апаратну ентропію TRNG і генерує 256 бітів псевдовипадкових даних для відкритого DEK.
2. HSM завантажує в захищений криптопроцесор KEK, ідентифікований параметром `KeyId`.
3. Виконується автентифіковане шифрування відкритого DEK за алгоритмом AES-KeyWrap (NIST SP 800-38F) або AES-256-GCM із додаванням канонізованого `EncryptionContext` як AAD.
4. Відповідь повертається через TLS-сесію, а відкритий DEK негайно вичищається з внутрішньої RAM сервісу KMS.

#### 2. Метод `Decrypt`

Метод приймає раніше сформований загорнутий конверт `CiphertextBlob`, передає його в ізольований криптографічний модуль HSM, перевіряє політику доступу та цілісність AAD-контексту, розшифровує за допомогою KEK і повертає відкритий DEK у пам'ять викликача.

```
RPC:      kms.v1.KeyService/Decrypt
HTTP/REST: POST /v1/decrypt
```

**Параметри запиту (Request Parameters):**

| Поле | Тип | Обов'язкове | Опис |
| :--- | :--- | :--- | :--- |
| `CiphertextBlob` | `bytes` (base64) | Так | Зашифрований конверт DEK разом із заголовком версії та метаданими. |
| `KeyId` | `string` | Ні | Ідентифікатор KEK (якщо опущено, KMS автоматично визначає ключ за заголовком блоба). |
| `EncryptionContext` | `map<string, string>` | Ні | Набір пар AAD. Мусить **побітово збігатися** з контекстом, наданим під час створення! |
| `GrantTokens` | `list<string>` | Ні | Криптографічні маркери доступу. |

**Структура відповіді (Response Parameters):**

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `KeyId` | `string` | ARN використаного ключа KEK. |
| `Plaintext` | `bytes` (base64) | Відкритий 256-бітний ключ DEK, призначений для локального розшифрування корисних даних. |
| `EncryptionAlgorithm` | `string` | Використаний алгоритм обгортання (наприклад, `SYMMETRIC_DEFAULT`). |

#### 3. Метод `ReEncrypt`

Метод перешифровує зашифрований ключ DEK новою версією KEK або геть іншим KEK без передачі відкритого ключа `Plaintext` у клієнтську мережу. Вся операція розгортання та повторного загортання відбувається винятково у захищеній пам'яті HSM.

```
RPC:      kms.v1.KeyService/ReEncrypt
HTTP/REST: POST /v1/re-encrypt
```

**Параметри запиту (Request Parameters):**

| Поле | Тип | Обов'язкове | Опис |
| :--- | :--- | :--- | :--- |
| `CiphertextBlob` | `bytes` (base64) | Так | Поточний зашифрований конверт DEK під старою версією ключа KEK v1. |
| `DestinationKeyId` | `string` | Так | Ідентифікатор цільового ключа KEK v2, яким буде загорнуто DEK. |
| `SourceEncryptionContext` | `map<string, string>` | Ні | AAD-контекст вихідного шифрування. |
| `DestinationEncryptionContext` | `map<string, string>` | Ні | Новий AAD-контекст для оновленого конверта. |

**Структура відповіді (Response Parameters):**

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `CiphertextBlob` | `bytes` (base64) | Оновлений зашифрований конверт DEK під ключем KEK v2. |
| `KeyId` | `string` | ARN цільового ключа KEK v2. |
| `SourceKeyId` | `string` | ARN старого вихідного ключа KEK v1. |

### Структура бінарного загорнутого конверта (CiphertextBlob)

Зашифрований ключ DEK зберігається не як сирий масив байтів, а як структурований бінарний контейнер фіксованого формату. Таке структурування дозволяє клієнтським бібліотекам та серверу KMS однозначно визначати версію протоколу та параметри без звернення до зовнішніх баз даних:

```
Формат бінарного заголовка загорнутого DEK:
+----------------+----------------+----------------+------------------+
| Magic (2B)     | Version (1B)   | KeyProvider(1B)| KEK Key ID (36B) |
| 0x4B 0x4D      | 0x01           | 0x01 (AWS/HSM) | UUID v4          |
+----------------+----------------+----------------+------------------+
| IV Nonce (12B) | Wrapped DEK (32B)               | GCM Tag (16B)    |
| Вектор обгортки| Зашифроване тіло DEK            | Автентифікація   |
+----------------+---------------------------------+------------------+
```

1. **Magic Bytes (2 байти):** Фіксована сигнатура `0x4B 0x4D` (`KM`), яка запобігає передачі випадкових файлів або пошкоджених блоків у дешифратор.
2. **Version (1 байт):** Версія формату загортання (дозволяє підтримувати зворотну сумісність при переході на постквантові алгоритми).
3. **KeyProvider (1 байт):** Прапорець типу криптопровайдера (локальний TPM, хмарний KMS, зовнішній PKCS#11 HSM).
4. **KEK Key ID (36 байтів):** Рядковий або бінарний UUID майстер-ключа, який дозволяє KMS миттєво знайти потрібний KEK у сховищі.
5. **Криптографічне тіло (60 байтів):** 12 байтів випадкового IV, 32 байти зашифрованого DEK та 16 байтів тегу контролю цілісності.

### Канонізація та семантика додаткових автентифікованих даних (AAD)

Параметр `EncryptionContext` є критичним елементом захисту від атак підміни шифротексту між орендарями (multi-tenant cross-account injection) та атак класу «заплутаний заступник» (confused deputy attack). Якщо зашифрований файл перемістити в інший каталог сховища або підставити в обліковий запис іншого клієнта, дешифрування зазнає невдачі, оскільки контекст не зійдеться.

Щоб автентифікаційний тег GHASH був детермінованим на обох сторонах мережевого з'єднання, словник пар рядків проходить обов'язковий алгоритм **канонізації**:

1. **Сортування ключів:** Пари ключ-значення сортуються в строгому порядку зростання числових значень байтів UTF-8 їхніх ключів.
2. **Чутливість до регістру:** Рядки `"TenantId"` та `"tenantid"` вважаються різними сутностями та не замінюють один одного.
3. **Канонічний потік байтів:** Сортовані пари формують потік байтів без пробільних символів, де довжина кожного рядка записується як 16-бітне беззнакове ціле у форматі Big-Endian:
   `[len(k1)][k1][len(v1)][v1][len(k2)][k2][len(v2)][v2]...`

```
Вхідний контекст:
{
  "resource_id": "cust-849102",
  "bucket": "archive-2026",
  "app": "billing"
}

Порядок після канонізації:
1. "app"         -> "billing"
2. "bucket"      -> "archive-2026"
3. "resource_id" -> "cust-849102"
```

Отриманий канонічний байтовий потік передається безпосередньо в криптопроцесор HSM як додаткові дані AAD під час операції `AES-GCM` або `AES-KeyWrapWithPadding`.

### Життєвий цикл ключів KEK та переходи станів (NIST SP 800-57)

Кожен ключ KEK усередині KMS функціонує відповідно до формальної моделі станів, регламентованої рекомендаціями NIST SP 800-57 щодо керування криптографічними ключами:

```
Стани ключа KEK:
[Pre-Active] -> [Active] ---------> [Deactivated] -> [Destroyed]
                    |                     |
                    +-----> [Compromised] +
```

1. **Pre-Active (Створено):** Ключ згенеровано в HSM, згенеровано метадані та політики доступу, проте операції шифрування заблоковані до настання запланованої дати активації.
2. **Active (Активний):** Ключ дозволено використовувати як для операцій шифрування (`GenerateDataKey`, `Encrypt`), так і для операцій розшифрування (`Decrypt`).
3. **Deactivated (Деактивовано / У відставці):** Ключ більше не використовується для генерації нових DEK. Метод `GenerateDataKey` повертає помилку `KMSInvalidStateException`. Проте операція `Decrypt` залишається доступною для читання старих архівних даних.
4. **Compromised (Скомпрометовано):** Ключ позначено як скомпрометований. Дозволяється винятково контрольоване аварійне розшифрування для міграції на новий KEK з обов'язковою фіксацією в аудит-лозі.
5. **Destroyed (Знищено):** Ключовий матеріал фізично стерто з пам'яті всіх HSM-кластерів. Будь-які спроби виклику повертають помилку `NotFoundException`. Відновлення раніше зашифрованих цим ключем DEK стає математично неможливим.

### Помилки виконання та стратегії відновлення

Сервіс повертає структуровані коди помилок, кожен із яких диктує відповідну стратегію поведінки клієнтського додатку:

| Код помилки | HTTP | Опис причини | Стратегія клієнта |
| :--- | :--- | :--- | :--- |
| `InvalidCiphertextException` | 400 | Пошкоджені байти конверта, підроблений тег автентифікації або невідповідність `EncryptionContext`. | Фатальна помилка безпеки. Повтор запиту заборонено; генерується сигнал тривоги в системі аудиту. |
| `AccessDeniedException` | 403 | У викликача відсутні права IAM на роботу з даним KEK або порушено обмеження політики. | Повтор заборонено. Необхідно оновити облікові дані або скоригувати IAM-політику ролі. |
| `NotFoundException` | 404 | Вказаний KEK або аліас відсутній у конфігурації сервісу KMS. | Перевірити коректність ідентифікатора ARN або аліаса ключа в конфігурації мікросервісу. |
| `KeyUnavailableException` | 503 | Апаратні кластери HSM тимчасово перевантажені або проходять синхронізацію реплік. | Тимчасовий збій. Виконується експоненційне відтермінування з джитером (Exponential Backoff with Full Jitter). |
| `ThrottlingException` | 429 | Перевищено ліміт запитів за секунду (RPS) для даного облікового запису або ключа. | Активувати локальне кешування DEK (Data Key Caching) або надіслати запит на збільшення квоти. |
| `KMSInvalidStateException` | 409 | Спроба згенерувати DEK на ключі KEK, який перебуває у стані `Disabled` або `PendingDeletion`. | Переключити конфігурацію додатку на активний KEK нової версії. |

### Аудит, журналювання та безпека операцій

Кожен виклик методів `GenerateDataKey`, `Decrypt` або `ReEncrypt` формує незмінний запис в аудит-лозі інфраструктури (наприклад, AWS CloudTrail або системний auditd). Запис містить точний час операції, унікальний ідентифікатор викликача (IAM Principal), ідентифікатор використаного KEK, IP-адресу клієнта та точну копію переданого `EncryptionContext`.

При цьому сервіс KMS на архітектурному рівні гарантує, що відкритий ключ DEK (`Plaintext`) та корисні дані клієнта **ніколи за жодних обставин не потрапляють у системні журнали**, залишаючись винятково в оперативній пам'яті клієнтського процесу на час поточної транзакції.
