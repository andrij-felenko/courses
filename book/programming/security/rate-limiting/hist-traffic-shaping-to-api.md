# 📜 Еволюція обмеження швидкості: від мереж ATM до хмарних API

Цей історичний огляд розкриває походження алгоритмів обмеження швидкості та пояснює, як інженерні концепції апаратного згладжування мережевих пакетів 1980-х років трансформувалися в розподілені системи захисту сучасних хмарних API від перевантаження та зловживань. Без розуміння цієї еволюції важко збагнути, чому сучасні протоколи одночасно використовують два різні підходи — жорстке відсікання трафіку (policing) та плавне згладжування черг (shaping).

---

## Колапс пропускної здатності в ранньому Інтернеті (1980-ті)

У середині 1980-х років ранній Інтернет (ARPANET та NSFNET) зіткнувся з явищем, яке отримало назву **колапс через перевантаження** (англ. *congestion collapse*). У жовтні 1986 року пропускна здатність магістрального каналу між Каліфорнійським університетом у Берклі та Національною лабораторією імені Лоуренса в Ліверморі (LBL) впала з 32 кбіт/с до 40 біт/с — у вісімсот разів.

Причиною була відсутність будь-якого зворотного зв'язку та контролю темпу надсилання пакетів:
1. Кінцеві вузли відправляли TCP-пакети на максимальній швидкості мережевої карти.
2. Проміжні маршрутизатори переповнювали свої буфери та скидали пакети (англ. *packet drop*).
3. Клієнти, не отримавши підтвердження (ACK), повторно відправляли ті самі пакети, ще більше забиваючи канали зв'язку.

У 1988 році Ван Джейкобсон (англ. *Van Jacobson*) запропонував алгоритми керування перевантаженням для TCP (повільний старт, уникнення перевантаження, швидкий повтор), які регулювали розмір вікна на боці передавача. Проте стало очевидно, що мережа не може покладатися виключно на добру волю клієнтів. Маршрутизатори потребували математично строгих алгоритмів для примусового обмеження темпу вхідних потоків незалежно від поведінки кінцевих вузлів.

## Джонатан Тернер та винайдення дірявого відра (1986)

Концепція алгоритмічного регулювання трафіку на рівні комутаторів виникла під час розробки технології **асинхронного режиму передавання** (англ. *Asynchronous Transfer Mode*, ATM). Мережі ATM проєктувалися для передавання різнорідного трафіку — голосу, відео та файлів — фіксованими 53-байтовими комірками (англ. *cells*).

У 1986 році професор Вашингтонського університету в Сент-Луїсі Джонатан Тернер (англ. *Jonathan S. Turner*) опублікував фундаментальну статтю «New Directions in Communications (or Which Way to the Information Age?)» в журналі *IEEE Communications Magazine*. Тернер запропонував концепцію **дірявого відра** (англ. *Leaky Bucket*) для телекомунікаційних комутаторів.

Мета Тернера полягала у створенні механізму, який гарантує, що жоден користувач каналу зв'язку не зможе перевищити погоджену середню смугу пропускання (англ. *bandwidth contract*). У його моделі вхідні комірки потрапляли в чергу фіксованого розміру, з якої передавалися в лінію зв'язку із суворо константною швидкістю. Якщо вхідний потік перевищував швидкість спорожнення відра і буфер заповнювався, нові комірки скидалися на вході. Це дозволило маршрутизаторам ATM гарантувати якість обслуговування (англ. *Quality of Service*, QoS) для чутливих до затримок телефонних розмов, навіть якщо сусідній користувач передавав великий файл.

## Стандартизація IETF та поява Token Bucket (1990-ті)

Хоча діряве відро ідеально згладжувало трафік, воно мало суттєвий недолік для комп'ютерних мереж: комп'ютерні програми за своєю природою генерують трафік пачками (англ. *bursty traffic*). Наприклад, завантаження вебсторінки вимагає миттєвого передавання десятків пакетів, після чого настає пауза читання користувачем. Застосування суворого Leaky Bucket збільшувало затримку (англ. *latency*) передавання таких сплесків, навіть якщо магістральний канал був повністю вільним.

У відповідь робоча група IETF з інтегрованих послуг (англ. *Integrated Services*, IntServ) стандартизувала алгоритм **накопичувача маркерів** (англ. *Token Bucket*). У 1997 році Джон Вроцлавскі (англ. *John Wroclawski*) описав використання Token Bucket у RFC 2211 (*Specification of the Controlled-Load Network Element Service*).

На відміну від дірявого відра, накопичувач маркерів накопичував право на передавання (токени) під час простою. Коли програма генерувала раптовий сплеск, вона могла миттєво відправити стільки пакетів, скільки токенів було у відрі, не створюючи штучної затримки.

Наприкінці 1990-х років у RFC 2697 та RFC 2698 було стандартизовано алгоритми кольорового маркування трафіку (англ. *Single Rate / Two Rate Three Color Marker* — srTCM / trTCM). Пакети маркувалися зеленим (повна відповідність ліміту), жовтим (сплеск у межах допустимого) або червоним (перевищення, підлягає скиданню) кольором на базі двох паралельних накопичувачів маркерів.

## Веб 2.0 та криза Twitter Fail Whale (2007–2010)

З появою вебсервісів нового покоління та публічних REST API у середині 2000-х років проблема контролю швидкості перемістилася з мережевих комутаторів 3-го рівня на рівень прикладних програм (Layer 7).

Найвідомішим прикладом кризи пропускної здатності став сервіс мікроблогів Twitter у 2007–2008 роках. Зростання популярності сторонніх клієнтів (TweetDeck, Twitterific) та автоматизованих ботів призвело до того, що тисячі програм щохвилини опитували API через нескінченні HTTP-запити (англ. *polling*). Сервери Twitter на базі Ruby on Rails не витримували навантаження, і користувачі постійно бачили знамениту сторінку помилки з китом, якого несуть птахи («Fail Whale»).

Twitter був змушений запровадити один із перших публічних механізмів rate limiting для REST API:
- Спочатку ліміт становив 70 запитів на годину на IP-адресу.
- Згодом його підвищили до 150 запитів на годину для автентифікованих користувачів.
- Для передачі стану ліміту Twitter ввів власні HTTP-заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining` та `X-RateLimit-Reset`, які де-факто стали галузевим стандартом на наступне десятиліття.

## Перехід до розподілених сховищ та сучасних хмарних шлюзів (2010-ті — сьогодення)

Коли архітектура вебдодатків перейшла від поодиноких монолітів до розподілених кластерів із сотнями мікросервісів, локальні лічильники в оперативній пам'яті одного процесу перестали працювати. Користувач, відправляючи 100 запитів на хвилину, потрапляв через балансувальник на 10 різних серверів, ефективно отримуючи десятикратне збільшення ліміту.

Інженерні команди Stripe, GitHub, Cloudflare та AWS у 2012–2016 роках опублікували серії архітектурних рішень для розподіленого обмеження:
1. **Redis + Lua:** Використання швидких оперативних баз даних для виконання атомарних скриптів поповнення токенів без стану гонки.
2. **Generic Cell Rate Algorithm (GCRA):** Запозичений зі специфікацій ATM Forum алгоритм віртуального планування, що замінив класичний Token Bucket в інфраструктурах з обмеженою пам'яттю, скоротивши стан до єдиного числа `TAT` (Theoretical Arrival Time).
3. **Хмарні API Gateways:** Перенесення перевірки лімітів на межу мережі (Edge Computing) — в NGINX, Envoy Proxy, Cloudflare Workers та AWS WAF. Це дозволило відсікати зловмисні сплески до того, як вони досягнуть дорогих серверів баз даних чи генеративних нейромережевих моделей.

Сьогодні обмеження швидкості перетворилося з простого захисту мережевого кабелю на фундаментальний компонент кібербезпеки, фінансового контролю за використанням платних API та забезпечення стабільності глобальних розподілених систем.
