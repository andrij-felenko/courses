# 📋 Специфікація та контракт SPIFFE Workload API (gRPC / UNIX Domain Socket)

У динамічних хмарних середовищах та мікросервісних архітектурах застосунки не повинні покладатися на статичні паролі, зашиті токени чи секрети у змінних оточення. Стандарт **SPIFFE** (англ. *Secure Production Identity Framework for Everyone*) визначає уніфікований програмний інтерфейс **Workload API**, за допомогою якого будь-який локальний процес автоматично отримує криптографічні документи ідентичності (SVID) та довірені кореневі сертифікати через локальний міжпроцесний сокет.

Цей довідник описує специфікацію протоколу gRPC, структури даних Protocol Buffers v3, схему ідентифікаторів SPIFFE ID, механізми атестації вузлів і процесів, коди помилок та правила життєвого циклу короткоживучих криптографічних ключів.

---

### Транспортний рівень та модель підключення

Клієнтський процес взаємодіє з локальним агентом (SPIRE Agent) виключно через локальний сокет домену UNIX (англ. *UNIX Domain Socket*, UDS), шлях до якого передається через стандартну змінну оточення:

```bash
SPIFFE_ENDPOINT_SOCKET="unix:///tmp/spire-agent/public/api.sock"
```

**Механізм взаємної автентифікації на транспортному рівні:**
- Клієнт **не передає жодних паролів чи токенів** для власної автентифікації перед сокетом. Це усуває проблему «секрету нульового дня» (англ. *secret zero problem*), коли для отримання секрету потрібен інший секрет.
- Агент SPIRE перехоплює відкриття дескриптора сокета та викликає системний виклик ядра Linux `getsockopt(fd, SOL_SOCKET, SO_PEERCRED, &ucred, ...)` для отримання структури `ucred` (або `SCM_CREDENTIALS`), яка містить числовий ідентифікатор процесу (`pid`), ідентифікатор користувача (`uid`) та групи (`gid`).
- Агент вичитує з псевдофайлової системи `/proc/<pid>/cgroup` та взаємодіє з середовищем виконання контейнерів (Docker, containerd, Kubernetes Kubelet) для точного зіставлення процесу з набором зареєстрованих правил (селекторів).

---

### Модель атестації: Селектори вузла та ворклоада

Видача ідентичності SPIFFE базується на двоступеневій верифікації: спочатку атестується фізичний або віртуальний вузол, а потім — конкретний процес, запущений на ньому.

#### 1. Атестація вузла (Node Attestation)
Вузловий агент (SPIRE Agent) доводить центральному серверу (SPIRE Server) свою легітимність за допомогою апаратних або хмарних плагінів:
- `tpm`: перевірка криптографічного ключа атестації (AK) та вимірів регістрів конфігурації платформи (PCR) довіреного платформеного модуля TPM 2.0;
- `k8s_psat`: перевірка проєктованого службового токена Kubernetes (*Projected Service Account Token*), підписаного ключем кластера;
- `aws_iid` / `gcp_iit`: перевірка криптографічного документа ідентичності віртуального екземпляра AWS EC2 чи Google Cloud Compute Engine;
- `join_token`: одноразовий випадковий токен попереднього узгодження для ручного підключення вузлів.

#### 2. Атестація ворклоада (Workload Attestation)
Після підключення процесу до локального UNIX-сокета агент SPIRE збирає набір динамічних ознак (селекторів):

| Простір селектора | Приклад селектора | Опис джерела перевірки |
|---|---|---|
| `k8s` | `k8s:ns:production` | Простір імен Kubernetes, у якому виконується Pod |
| `k8s` | `k8s:sa:payment-processor` | Обліковий запис ServiceAccount у маніфесті Pod |
| `k8s` | `k8s:pod-label:tier:backend` | Динамічна мітка контейнера в кластері |
| `docker` | `docker:label:app:billing` | Мітка образу контейнера Docker |
| `unix` | `unix:uid:10001` | Числовий ідентифікатор користувача ОС Linux |
| `unix` | `unix:path:/usr/bin/gateway` | Абсолютний канонічний шлях до виконуваного файлу на диску |

Сервер SPIRE зіставляє зібрані селектори з таблицею записів реєстрації (*Registration Entries*). Якщо знайдено повний збіг усіх обов'язкових умов, процес отримує відповідний `spiffe_id`.

### gRPC Інтерфейс сервісу SpiffeWorkloadAPI

Специфікація інтерфейсу описана синтаксисом Protocol Buffers v3 (`proto3`) у просторі імен `spiffe.workload.api`:

```protobuf
syntax = "proto3";

package spiffe.workload.api;

option go_package = "github.com/spiffe/go-spiffe/v2/proto/spiffe/workload";

// Основний сервіс отримання ідентичностей для робочих навантажень
service SpiffeWorkloadAPI {
    // Отримання та неперервний стрімінг X.509 SVID сертифікатів і зв'язок довіри
    rpc FetchX509SVID(X509SVIDRequest) returns (stream X509SVIDResponse);

    // Отримання виключно публічних зв'язок кореневих сертифікатів (Trust Bundles)
    rpc FetchX509Bundles(X509BundlesRequest) returns (stream X509BundlesResponse);

    // Отримання підписаного JWT токена ідентичності для вказаних аудиторій
    rpc FetchJWTSVID(JWTSVIDRequest) returns (JWTSVIDResponse);

    // Валідація JWT токена через локальний агент без звернення до зовнішнього IDP
    rpc ValidateJWTSVID(ValidateJWTSVIDRequest) returns (ValidateJWTSVIDResponse);

    // Отримання зв'язок публічних ключів JWT для перевірки підписів
    rpc FetchJWTBundles(JWTBundlesRequest) returns (stream JWTBundlesResponse);
}
```

### Структури повідомлень та контракти даних

#### 1. Специфікація X.509 SVID

Повідомлення `X509SVID` містить повний криптографічний матеріал для конфігурації TLS-сервера або клієнта:

```protobuf
message X509SVIDRequest {}

message X509SVIDResponse {
    // Список SVID, призначених даному процесу (головний SVID завжди перший)
    repeated X509SVID svids = 1;
    
    // Словник довірених кореневих зв'язок: ключ — Trust Domain, значення — ASN.1 DER сертифікати
    map<string, bytes> federated_bundles = 2;
}

message X509SVID {
    // Уніфікований SPIFFE ID процесу (наприклад, spiffe://prod.example.com/ns/finance/sa/payment)
    string spiffe_id = 1;

    // Ланцюжок сертифікатів X.509 у бінарному кодуванні ASN.1 DER (Leaf -> Intermediate -> Root)
    bytes x509_svid = 2;

    // Закритий асиметричний ключ у бінарному кодуванні PKCS#8 DER (RSA або ECC Private Key)
    bytes x509_svid_key = 3;

    // Публічний сертифікат кореневого центру сертифікації власного домену довіри (ASN.1 DER)
    bytes bundle = 4;

    // Додатковий текстовий маркер призначення (для мультитенантних сервісів)
    string hint = 5;
}
```

#### 2. Специфікація JWT SVID

Використовується для автентифікації на рівні L7 HTTP/REST викликів або асинхронних черг повідомлень, де неможливо встановити пряме mTLS-з'єднання:

```protobuf
message JWTSVIDRequest {
    // Аудиторія (Audience) — цільовий сервіс, для якого запитується токен
    repeated string audience = 1;

    // Необов'язковий конкретний SPIFFE ID (якщо процес має кілька ідентичностей)
    string spiffe_id = 2;
}

message JWTSVIDResponse {
    repeated JWTSVID svids = 1;
}

message JWTSVID {
    // SPIFFE ID суб'єкта
    string spiffe_id = 1;

    // Підписаний компактний серіалізований JWT (Header.Payload.Signature)
    string token = 2;

    // Час видачі токена (UNIX Timestamp у секундах)
    int64 issued_at = 3;

    // Час завершення дії токена (UNIX Timestamp у секундах)
    int64 expires_at = 4;
}
```

### Специфікація SPIFFE ID та валідація X.509 SAN

Ідентифікатор SPIFFE ID є уніфікованим ресурсом (URI) згідно з RFC 3986 і має сувору структуру:

```
spiffe://<домен-довіри>/<шлях-робочого-навантаження>
```

**Вимоги до криптографічного кодування в сертифікаті X.509:**
1. Ідентифікатор SPIFFE ID **обов'язково** записується у розширення сертифіката `Subject Alternative Name` (SAN) з типом `uniformResourceIdentifier` (URI, OID `2.5.29.17`).
2. Сертифікат X.509-SVID **не повинен** містити жодних DNS-імен або IP-адрес у полі SAN, якщо це сертифікат ідентичності ворклоада (крім спеціальних сертифікатів шлюзів).
3. Поле `Subject.CommonName` (CN) вважається застарілим і ігнорується рушієм валідації SPIFFE.
4. Домен довіри (*Trust Domain*) задає межу криптографічного контролю. Для взаємодії між різними доменами (наприклад, `spiffe://aws.corp` та `spiffe://gcp.corp`) використовується механізм федерації (SPIFFE Federation), за якого агенти обмінюються публічними зв'язками кореневих ключів (`federated_bundles`) через захищений gRPC канал.

### Коди стану gRPC та поведінка клієнта

| Код стану gRPC | Причина помилки | Обов'язкова реакція клієнтської програми |
|---|---|---|
| `OK (0)` | Запит успішно виконано | Застосувати отриманий SVID та слухати оновлення у стрімі |
| `UNAUTHENTICATED (16)` | Агент не зміг визначити PID/UID сокета | Зафіксувати аварію у журналі, повторити через експоненційну паузу |
| `PERMISSION_DENIED (7)` | Для селекторів процесу немає зареєстрованого SPIFFE ID | Процес не має прав; перевірити конфігурацію Kubernetes ServiceAccount |
| `UNAVAILABLE (14)` | Локальний агент SPIRE не запущений або сокет недоступний | Повторювати спробу кожні 500 мс (захист від гонки запуску контейнерів) |
| `DEADLINE_EXCEEDED (4)` | Таймаут очікування генерації сертифіката | Збільшити таймаут виклику (дефолт: 5 секунд) |

### Інваріанти життєвого циклу та правила ротації

1. **Жодного запису ключів на диск**: Клієнтська програма зобов'язана утримувати закритий ключ `x509_svid_key` виключно в оперативній пам'яті процесу. Скидання закритого ключа у файлову систему, кеш чи журнал логів суворо заборонено.
2. **Відсутність важких списків відкликання (No CRL / OCSP Overhead)**:
   - Замість використання повільних і ненадійних протоколів перевірки статусу сертифікатів (CRL або OCSP), SPIFFE використовує надзвичайно короткий час життя сертифіката (зазвичай від 10 хвилин до 1 години).
   - Якщо сервіс або ноду скомпрометовано, адміністратор видаляє запис реєстрації в SPIRE Server. Через кілька хвилин термін дії поточного сертифіката закінчується, а новий сертифікат більше не видається, що автоматично блокує доступ.
3. **Неперервний стрімінг ротації (*Zero-Downtime Rotation*)**:
   - Клієнт відкриває виклик `FetchX509SVID` і не закриває gRPC-канал.
   - Агент SPIRE автоматично надсилає новий кадр `X509SVIDResponse`, коли до завершення терміну дії поточного сертифіката залишається 50% його початкового TTL (наприклад, якщо TTL = 60 хвилин, новий сертифікат прийде через 30 хвилин).
   - Клієнтський TLS-контекст зобов'язаний динамічно замінити активний сертифікат у пам'яті для наступних з'єднань, не розриваючи вже встановлені активні TCP-сесії.
4. **Обробка розриву сокета**: Якщо зв'язок з агентом втрачено (наприклад, перезапуск демона SPIRE Agent), клієнт продовжує використовувати поточний SVID до моменту закінчення його `expires_at`, паралельно виконуючи фонові спроби перепідключення до сокета.
