# 📋 Специфікація предикатів SLSA Provenance v1.0 та атестацій in-toto

Ця довідкова специфікація визначає структуру даних, типи полів, системні інваріанти та алгоритми валідації для стандартизованих метаданих ланцюга постачання програмного забезпечення. Вона охоплює чотири взаємопов'язані стандарти: універсальний криптографічний конверт тверджень in-toto Statement v1.0 (DSSE), предикат походження артефактів SLSA Provenance v1.0, моделі опису компонентів SBOM (CycloneDX та SPDX) та протокол обміну даними про експлуатованість уразливостей OpenVEX.

Мета цієї специфікації — надати вичерпний контракт для інженерів, які розробляють складальні конвеєри, утиліти підпису артефактів, автоматизовані сканери безпеки та точки ухвалення рішень (Policy Decision Points) у контролерах допуску Kubernetes.

---

### Архітектура конверта атестації in-toto (DSSE Envelope та Statement v1.0)

Традиційний підхід до підпису файлів за допомогою відокремлених цифрових підписів (detached signatures) створює неоднозначність інтерпретації: підпис засвідчує послідовність байтів, але не містить формального опису типу корисного навантаження та контексту його застосування. Для подолання цієї проблеми фреймворк in-toto використовує стандарт DSSE (англ. *Dead Simple Signing Envelope*).

Конверт DSSE складається з двох суворо розділених рівнів:
1. **Зовнішній шар (Envelope)**: Стандартизована обгортка, яка містить тип корисного навантаження, саме навантаження у форматі Base64 та масив цифрових підписів уповноважених центрів.
2. **Внутрішній шар (Statement)**: Формалізоване твердження, яке прив'язує один або кілька цільових програмних артефактів (суб'єктів) до конкретного предиката твердження.

```json
{
  "payloadType": "application/vnd.in-toto+json",
  "payload": "eyJfdHlwZSI6ICJodHRwczovL2luLXRvdG8uaW8vU3RhdGVtZW50L3YxIiwg...",
  "signatures": [
    {
      "keyid": "SHA256:4c10a3e8b15d2a9f7e8b2c1d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b9c0d1e2f",
      "sig": "MEQCID...=="
    }
  ]
}
```

#### Семантика полів конверта Envelope

Поле `payloadType` фіксує точний MIME-тип внутрішнього документа. Для всіх тверджень in-toto версії 1.0 це поле зобов'язане містити точний рядок `application/vnd.in-toto+json`. Будь-яке інше значення призводить до негайної відмови валідації на рівні парсера конверта.

Поле `payload` містить повний текст твердження in-toto Statement, закодований за стандартом Base64 (RFC 4648). Кодування в Base64 є критично важливим інженерним рішенням: воно усуває залежність цифрового підпису від особливостей форматування JSON (перенесення рядків, пробіли, сортування ключів). Підпис накладається на байтовий масив, сформований за правилом конкатенації префіксу стандарту DSSE: `PAE(type, payload) = "DSSEv1" + " " + len(type) + " " + type + " " + len(payload) + " " + payload`.

Масив `signatures` містить криптографічні підписи. Кожен запис підпису містить обов'язкове поле `sig` (бінарний підпис у Base64) та необов'язкове поле `keyid`. Поле `keyid` містить канонічний відбиток відкритого ключа, що дозволяє валідатору швидко вибрати відповідний ключ із довіреного набору (*keyring*) без перебору всіх наявних ключів.

### Специфікація твердження in-toto Statement v1.0

Після декодування Base64 з поля `payload` валідатор отримує внутрішній структурований документ твердження:

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "payment-gateway-linux-amd64",
      "digest": {
        "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
      }
    }
  ],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": { }
}
```

#### Інваріанти валідації полів Statement

Поле `_type` є маркером версії схеми і повинно суворо відповідати значенню `https://in-toto.io/Statement/v1`. Якщо валідатор отримує застарілу версію схеми (наприклад, `https://in-toto.io/Statement/v0.1`), він зобов'язаний застосувати відповідний парсер або повернути помилку несумісності версій.

Масив `subject` описує програмні артефакти, цілісність яких засвідчується цією атестацією. Кожен елемент масиву містить:
- `name`: Текстова назва файлу, шлях або повний URI образу контейнера (наприклад, `docker.io/enterprise/payment-service:v1.4.0`);
- `digest`: Словник криптографічних гешів артефакту. Наявність алгоритму `sha256` є строго обов'язковою. Значенням повинен бути шістдесят чотирисимвольний шістнадцятковий рядок у нижньому регістрі. Додатково можуть бути вказані геші `sha512` або `gitCommit`.

Поле `predicateType` визначає структуру об'єкта `predicate`. Для предикатів походження SLSA використовується URI `https://slsa.dev/provenance/v1`. Для вкладених специфікацій компонентів SBOM використовується URI `https://cyclonedx.org/bom` або `https://spdx.dev/Document/v2.3`. Для звітів аналізу вразливостей VEX використовується `https://openvex.dev/ns/v0.2.0`.

### Специфікація предиката SLSA Provenance v1.0

Предикат `https://slsa.dev/provenance/v1` документує точні параметри, вихідні матеріали та платформу збирання бінарного артефакту. Він розділений на дві основні логічні секції: `buildDefinition` (що і як збиралося) та `runDetails` (де, коли і ким виконувалося збирання).

```json
{
  "buildDefinition": {
    "buildType": "https://slsa-framework.github.io/github-actions-buildtypes/workflow/v1",
    "externalParameters": {
      "workflow": {
        "ref": "refs/tags/v1.4.0",
        "repository": "https://github.com/enterprise/payment-gateway",
        "path": ".github/workflows/release.yml"
      }
    },
    "internalParameters": {
      "runnerPlatform": "ubuntu-22.04"
    },
    "resolvedDependencies": [
      {
        "uri": "git+https://github.com/enterprise/payment-gateway@refs/tags/v1.4.0",
        "digest": {
          "gitCommit": "a8f93b216c5478492049e7b2520a02ef65e43c89"
        }
      },
      {
        "uri": "pkg:golang/github.com/gin-gonic/gin@v1.9.1",
        "digest": {
          "sha256": "9b12a84c6e94f1c1a2e3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5"
        }
      }
    ]
  },
  "runDetails": {
    "builder": {
      "id": "https://github.com/slsa-framework/slsa-github-generator/.github/workflows/generator_generic_slsa3.yml@refs/tags/v1.9.0",
      "version": {
        "slsa-builder": "1.9.0"
      }
    },
    "metadata": {
      "invocationId": "https://github.com/enterprise/payment-gateway/actions/runs/8492019382/attempts/1",
      "startedOn": "2026-08-20T14:30:00Z",
      "finishedOn": "2026-08-20T14:34:12Z"
    },
    "byproducts": []
  }
}
```

#### Детальний аналіз секції `buildDefinition`

Секція `buildDefinition` фіксує інженерний контракт збирання:

- **`buildType` (обов'язкове)**: Універсальний URI, який повністю визначає синтаксис та семантику полів `externalParameters` та `internalParameters`. Цей URI слугує схемою конфігурації.
- **`externalParameters` (обов'язкове)**: Об'єкт, що описує вхідні параметри, надані ініціатором процесу збирання (наприклад, розробником або подією пушу в Git). Ці параметри вважаються неконтрольованими з боку збирача: шлях до конвеєра, змінні середовища, передані через тригер, цільова архітектура.
- **`internalParameters` (необов'язкове)**: Параметри, примусово виставлені самою захищеною платформою збирання. Користувач не може переписати ці значення: наприклад, версія операційної системи раннера, налаштування ізоляції мережі, адреси локальних проксі-серверів кешування залежностей.
- **`resolvedDependencies` (необов'язкове)**: Повний масив усіх зовнішніх компонентів, що брали участь у процесі збирання. Для забезпечення рівня SLSA Build L3 кожен елемент масиву зобов'язаний містити як канонічний URI ресурсу (`uri`), так і його незмінний криптографічний геш (`digest`). Будь-яка залежність без зафіксованого гешу порушує вимоги герметичності збирання.

#### Детальний аналіз секції `runDetails`

Секція `runDetails` засвідчує фактичні обставини виконання процесу компіляції:

- **`builder.id` (обов'язкове)**: Головне поле ідентифікації довіреного збирача. Це глобально унікальний URI, який однозначно ідентифікує виконавчий механізм, що згенерував атестацію. У політиках контролерів допуску перевірка `builder.id` за білим списком дозволених корпоративних збирачів є першим і головним правилом.
- **`metadata.invocationId` (необов'язкове)**: Унікальний URI або ідентифікатор сесії збирання. Використовується для аудиту та зіставлення атестації з системними логами платформи CI/CD.
- **`metadata.startedOn` та `metadata.finishedOn` (необов'язкове)**: Часові мітки початку та завершення компіляції у стандартному форматі ISO 8601 / RFC 3339 UTC. Використовуються для перевірки того, що збирання відбулося в межах допустимого вікна часу та не використовує застарілих сертифікатів.

### Специфікація тверджень OpenVEX v0.2.0

Формат OpenVEX надає машиннозчитуваний механізм для фільтрації результатів сканування безпеки на основі реальної експлуатованості уразливостей у конкретному контексті.

```json
{
  "@context": "https://openvex.dev/ns/v0.2.0",
  "@id": "https://enterprise.internal/vex/payment-gateway-v1.4.0",
  "author": "Security Engineering Team <sec@enterprise.internal>",
  "role": "Vendor",
  "timestamp": "2026-08-20T15:00:00Z",
  "version": 1,
  "statements": [
    {
      "vulnerability": {
        "name": "CVE-2023-44487"
      },
      "products": [
        "pkg:golang/github.com/enterprise/payment-gateway@v1.4.0"
      ],
      "status": "not_affected",
      "justification": "code_not_reachable",
      "impact_statement": "Функціонал HTTP/2 Rapid Reset не активується: сервіс використовує gRPC через закритий mTLS шлюз із фіксованими лімітами потоків."
    },
    {
      "vulnerability": {
        "name": "CVE-2024-21626"
      },
      "products": [
        "pkg:golang/github.com/enterprise/payment-gateway@v1.4.0"
      ],
      "status": "affected",
      "action_statement": "Потрібне оновлення базового контейнерного образу до версії Debian 12.5 з виправленим пакетом runc."
    }
  ]
}
```

#### Правила валідації тверджень VEX

Кожен документ OpenVEX містить масив тверджень `statements`. Для кожного твердження контролер безпеки обчислює логічний статус допуску:

1. **Статус `not_affected`**: Вказує, що вразливість не становить загрози для продукту. Вимагає обов'язкової наявності поля `justification` з одним із стандартизованих значень:
   - `component_not_present` — сканер помилково ідентифікував наявність компонента;
   - `code_not_reachable` — уразливий код відсутній у графах викликів виконання;
   - `vulnerable_code_cannot_be_controlled_by_adversary` — відсутня можливість передачі зловмисних даних у вразливий метод;
   - `inline_mitigations_already_exist` — захист забезпечено архітектурними заходами зовнішнього коду;
   - `vulnerable_code_not_in_execute_path` — модуль відключено на рівні конфігурації компіляції.
   Наявність текстового опису в полі `impact_statement` є обов'язковою умовою для проходження аудиту відповідності.

2. **Статус `affected`**: Вказує на наявність підтвердженої загрози. Контролер допуску автоматично блокує розгортання артефакту, якщо критичність CVE перевищує встановлений корпоративний поріг.

3. **Статус `fixed`**: Фіксує факт усунення вразливості у цій версії продукту, що дозволяє сканерам безпеки оновити внутрішні бази знань без генерування повторних сповіщень.

### Таблиця кодів помилок валідації атестацій у точках допуску

| Код помилки | Назва стану | Причина відмови | Дія контролера допуску |
| :--- | :--- | :--- | :--- |
| `ERR_ENV_INVALID_FORMAT` | Невалідний конверт | Відсутній `payloadType` або неможливо розпарсити Base64. | Блокування запуску (400 Bad Request). |
| `ERR_SIG_VERIFY_FAILED` | Помилка підпису | Цифровий підпис не відповідає відкритому ключу чи даним `payload`. | Блокування запуску (403 Forbidden). |
| `ERR_SUBJECT_MISMATCH` | Невідповідність дайджесту | SHA-256 геш бінарного файлу не збігається з масивом `subject`. | Блокування запуску (403 Forbidden). |
| `ERR_BUILDER_UNTRUSTED` | Недовірений збирач | Значення `builder.id` відсутнє у білому списку організації. | Блокування запуску (403 Forbidden). |
| `ERR_SOURCE_UNAUTHORIZED` | Недозволене джерело | `externalParameters.source` вказує на сторонній репозиторій або неофіційну гілку. | Блокування запуску (403 Forbidden). |
| `ERR_VEX_BLOCKING_CVE` | Блокуюча уразливість | Знайдено статус `affected` для критичної CVE без винятку. | Блокування запуску (403 Forbidden). |
