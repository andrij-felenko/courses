# 📋 Інтерфейс та структури даних сесії Double Ratchet

Програмна реалізація протоколу Double Ratchet фіксує точний формат заголовків повідомлень, бінарну структуру криптографічного стану сесії, правила серіалізації кадрів у ненадійному транспортному каналі, вимоги до багатопотокового доступу та контракт відкритих функцій для інтеграції в користувацькі додатки.

### 1. Формат заголовка зашифрованого кадру

Кожне повідомлення, що передається через ненадійний транспортний канал (хмарний сервер, чергу релею або push-сервіс), супроводжується відкритим, але криптографічно автентифікованим заголовком `MessageHeader`. Цей заголовок передається у відкритому вигляді для того, щоб отримувач міг розпізнати сесію, виконати кроки храповика та знайти правильний ключ дешифрування. Водночас заголовок обов'язково передається як асоційовані дані (Associated Authenticated Data, AAD) у шифр AEAD:

| Поле | Тип | Розмір | Бінарний формат | Призначення |
| :--- | :--- | :--- | :--- | :--- |
| `dh_pub` | `uint8_t[32]` | 32 байти | Сирий відкритий ключ X25519 | Поточний відкритий ключ DH-храповика відправника |
| `pn` | `uint32_t` | 4 байти | Big-Endian (мережевий порядок) | Кількість повідомлень у попередньому ланцюгу відправлення (*Previous Chain Length*) |
| `n` | `uint32_t` | 4 байти | Big-Endian (мережевий порядок) | Порядковий номер повідомлення в поточному ланцюгу відправлення (*Message Index*) |

Бінарне представлення заголовка займає рівно 40 байтів:

```
+------------------------------------+------------------+------------------+
|      dh_pub (32 байти X25519)      |  pn (4 байти BE) |  n (4 байти BE)  |
+------------------------------------+------------------+------------------+
0                                    32                 36                 40
```

Будь-яка спроба проміжного сервера або зловмисника змінити порядковий номер `n`, довжину попереднього ланцюга `pn` або підмінити відкритий ключ `dh_pub` призводить до миттєвого збою перевірки 16-байтного тегу автентифікації Poly1305 або GHASH на боці отримувача.

### 2. Структура стану криптографічної сесії (Session State)

Стан сесії інкапсулює всі ключові матеріали, лічильники та таблиці відкладених ключів. Оскільки втрата або пошкодження стану сесії унеможливлює розшифрування наступних вхідних повідомлень, стан зберігається в локальній пам'яті клієнта з періодичною атомарною фіксацією в захищеному сховищі:

| Змінна стану | Розмір | Опис та правила життєвого циклу |
| :--- | :--- | :--- |
| `dhs_priv` | 32 байти | Власний секретний скаляр поточної ефемерної пари DH-храповика. Затирається нулями після зміни на нову пару. |
| `dhs_pub` | 32 байти | Власний відкритий ключ поточної пари DH-храповика. Передається у заголовках вихідних повідомлень. |
| `dhr_pub` | 32 байти | Останній отриманий відкритий ключ DH-храповика співрозмовника. |
| `rk` | 32 байти | Поточний кореневий ключ (*Root Key*). Оновлюється на кожному асиметричному кроці функцією HKDF. |
| `cks` | 32 байти | Ключ ланцюга відправлення (*Chain Key Send*). Оновлюється на кожне вихідне повідомлення через HMAC. |
| `ckr` | 32 байти | Ключ ланцюга отримання (*Chain Key Receive*). Оновлюється на кожне вхідне повідомлення через HMAC. |
| `ns` | 4 байти | Лічильник відправлених повідомлень у поточному ланцюгу відправлення (скидається в `0` при новому DH). |
| `nr` | 4 байти | Лічильник отриманих повідомлень у поточному ланцюгу отримання (скидається в `0` при новому DH). |
| `pn` | 4 байти | Кількість повідомлень у попередньому ланцюгу відправлення (фіксує розмір минулої черги для партнера). |
| `skipped_keys` | Динамічний | Таблиця збережених ключів повідомлень для кадрів, що надійшли з порушенням черги: `(dhr_pub, n) -> MK`. |

### 3. Коди помилок та обробка виняткових ситуацій

Функції API повертають детерміновані статуси помилок, що сигналізують про конкретні відмови криптографічних примітивів або спроби порушення протоколу:

:::tabs
```c
typedef enum {
    RATCHET_OK                    =  0,  // Операція успішна
    RATCHET_ERR_INVALID_PARAM     = -1,  // Некоректні вказівники або нульова довжина буферів
    RATCHET_ERR_AUTH_FAILED       = -2,  // Помилка верифікації тегу AEAD (пошкоджено шифротекст або AAD)
    RATCHET_ERR_TOO_FAR_FORWARD   = -3,  // Стрибок лічильника n перевищує ліміт MAX_FORWARD_STEPS (захист від DoS)
    RATCHET_ERR_MAX_SKIPPED_LIMIT = -4,  // Переповнення таблиці пропущених ключів (вичерпано MAX_SKIPPED_KEYS)
    RATCHET_ERR_DUPLICATE_MESSAGE = -5,  // Повідомлення з таким індексом уже було розшифровано (спроба повтору)
    RATCHET_ERR_OUT_OF_MEMORY     = -6   // Неможливо виділити пам'ять під новий запис таблиці
} ratchet_status_t;
```
```cpp
enum class RatchetStatus {
    Ok                  =  0,  // Операція успішна
    InvalidParam        = -1,  // Некоректні вхідні аргументи
    AuthFailed          = -2,  // Помилка верифікації тегу AEAD (підробка або пошкодження)
    TooFarForward       = -3,  // Стрибок лічильника n перевищує ліміт MAX_FORWARD_STEPS
    MaxSkippedLimit     = -4,  // Переповнення таблиці пропущених ключів
    DuplicateMessage    = -5,  // Спроба повторної обробки вже розшифрованого повідомлення
    OutOfMemory         = -6   // Нестача пам'яті під стан або таблицю
};
```
:::

### 4. Контракт ініціалізації сесії

Ініціалізація сесії виконується після успішного завершення протоколу X3DH. Залежно від ролі учасника (ініціатор чи відповідач), початковий стан налаштовується по-різному:

:::tabs
```c
// Ініціалізація на боці Аліси (ініціатор сесії)
ratchet_status_t ratchet_init_alice(
    ratchet_session_t     *session,
    const uint8_t          shared_master_key[32],
    const uint8_t          bob_dh_public_key[32]
);

// Ініціалізація на боці Боба (відповідач)
ratchet_status_t ratchet_init_bob(
    ratchet_session_t     *session,
    const uint8_t          shared_master_key[32],
    const dh_keypair_t    *bob_dh_keypair
);
```
```cpp
// Ініціалізація на боці Аліси (ініціатор сесії)
RatchetStatus ratchet_init_alice(
    RatchetSession               &session,
    std::span<const uint8_t, 32>  shared_master_key,
    std::span<const uint8_t, 32>  bob_dh_public_key
);

// Ініціалізація на боці Боба (відповідач)
RatchetStatus ratchet_init_bob(
    RatchetSession               &session,
    std::span<const uint8_t, 32>  shared_master_key,
    const DhKeyPair              &bob_dh_keypair
);
```
:::

- **Для Аліси:** функція генерує нову пару ключів `dhs_A`, встановлює відкритий ключ Боба `dhr_pub = bob_dh_public_key`, обчислює `SS = X25519(dhs_priv_A, dhr_pub)` і розгортає перший кореневий ключ `rk` та ланцюг відправлення `cks`. Сесія негайно готова до шифрування вихідних повідомлень.
- **Для Боба:** функція встановлює `rk = shared_master_key`, зберігає локальну пару `dhs_B = bob_dh_keypair` і залишає `dhr_pub` порожнім. Боб очікує першого повідомлення від Аліси для виконання свого першого асиметричного кроку.

### 5. Контракт шифрування та дешифрування повідомлень

Функції шифрування та дешифрування виконують повний цикл криптографічних операцій, включно з оновленням станів храповиків та затиранням одноразових ключів:

:::tabs
```c
// Шифрування відкритого тексту
ratchet_status_t ratchet_encrypt(
    ratchet_session_t     *session,
    const uint8_t         *plaintext,
    size_t                 plaintext_len,
    message_header_t      *out_header,
    uint8_t               *out_ciphertext,
    size_t                *out_ciphertext_len
);

// Дешифрування зашифрованого кадру
ratchet_status_t ratchet_decrypt(
    ratchet_session_t     *session,
    const message_header_t *in_header,
    const uint8_t         *in_ciphertext,
    size_t                 in_ciphertext_len,
    uint8_t               *out_plaintext,
    size_t                *out_plaintext_len
);
```
```cpp
// Шифрування відкритого тексту
std::expected<EncryptedFrame, RatchetStatus> ratchet_encrypt(
    RatchetSession              &session,
    std::span<const uint8_t>     plaintext
);

// Дешифрування зашифрованого кадру
std::expected<std::vector<uint8_t>, RatchetStatus> ratchet_decrypt(
    RatchetSession              &session,
    const MessageHeader         &in_header,
    std::span<const uint8_t>     in_ciphertext
);
```
:::

#### Послідовність виконання `ratchet_encrypt`:
1. Викликається `KDF_CK(cks)` для обчислення 32-байтного ключа повідомлення `MK` та оновлення ключа ланцюга `cks`.
2. Заповнюються поля заголовка: `out_header->dh_pub = session->dhs_pub`, `out_header->pn = session->pn`, `out_header->n = session->ns++`.
3. Виконується шифрування відкритого тексту через алгоритм AEAD (ChaCha20-Poly1305 або AES-256-GCM) з ключем `MK`, де бінарний заголовок `out_header` передається як асоційовані дані `AAD`.
4. Пам'ять буфера `MK` негайно затирається нулями за допомогою `explicit_bzero`.

#### Послідовність виконання `ratchet_decrypt`:
1. Виконується пошук запису `(in_header->dh_pub, in_header->n)` у таблиці `skipped_keys`. Якщо запис знайдено: розшифровується вміст за допомогою збереженого `MK`, запис видаляється з таблиці, пам'ять ключа очищується, функція повертає успіх.
2. Якщо ключ не знайдено і `in_header->dh_pub != session->dhr_pub`:
   - Якщо попередній ключ `dhr_pub` існував, ланцюг отримання `ckr` перемотується вперед до індексу `in_header->pn`, а всі проміжні ключі повідомлень зберігаються в `skipped_keys`.
   - Виконується асиметричний DH-крок: обчислюється спільний секрет із `in_header->dh_pub`, генеруються новий `rk` та новий `ckr`.
   - Генерується свіжа локальна пара ключів `dhs`, обчислюється наступний `rk` та новий ланцюг відправлення `cks`.
   - Оновлюються лічильники: `session->pn = session->ns`, `session->ns = 0`, `session->nr = 0`, `session->dhr_pub = in_header->dh_pub`.
3. Ланцюг отримання `ckr` перемотується від поточного `session->nr` до цільового `in_header->n`. Усі пропущені ключі додаються до таблиці `skipped_keys`.
4. Обчислюється шуканий `MK` для індексу `in_header->n`, збільшується лічильник `session->nr++`.
5. Шифротекст розшифровується та перевіряється алгоритмом AEAD. Одноразовий `MK` затирається нулями.

### 6. Персистенція стану та транзакційна безпека

Стан сесії Double Ratchet є високодинамічним: кожна операція шифрування або дешифрування модифікує внутрішні ключі ланцюгів та лічильники. Якщо програма аварійно завершиться посеред операції дешифрування, коли ключ у пам'яті вже прокручено, але розшифроване повідомлення ще не збережено на диск, сесія опиниться в розсинхронізованому стані, що спричинить постійну втрату всіх наступних повідомлень від цього співрозмовника.

Для гарантування цілісності сховище сесій має відповідати суворим критеріям:
1. **Атомарність оновлення (ACID transactions):** збереження розшифрованого повідомлення в базу даних і оновлення серіалізованого стану `SessionRecord` повинні виконуватися в межах єдиної транзакції бази даних (наприклад, SQLite).
2. **Шифрування стану у спокої:** сам серіалізований стан `SessionRecord` містить закриті ключі `dhs_priv`, `rk`, `cks`, `ckr` та пропущені `MK`. Цей блоб обов'язково шифрується симетричним майстер-ключем бази даних (через SQLCipher або апаратний анклав пристрою iOS Keychain / Android Keystore).
3. **Захист від паралельного доступу (Thread Safety):** об'єкт сесії `ratchet_session_t` не є потокобезпечним. Усі операції шифрування вихідних повідомлень та обробки вхідних пакетів повинні синхронізуватися через індивідуальний м'ютекс для кожної активної сесії (`pthread_mutex_t` або `std::mutex`). Спроба паралельного виклику `ratchet_encrypt` та `ratchet_decrypt` без блокування призведе до пошкодження кореневого ключа та генерації невалідних шифротекстів.

### 7. Конфігураційні ліміти та захист ресурсів

Для запобігання атакам на вичерпання ресурсів пам'яті та процесора через некоректні чи сфабриковані заголовки повідомлень встановлюються суворі обмеження:

- `MAX_FORWARD_STEPS = 2000` — максимальний дозволений інтервал перемотування симетричного ланцюга вперед. Якщо `in_header->n - session->nr > MAX_FORWARD_STEPS`, виклик негайно відхиляється з помилкою `RATCHET_ERR_TOO_FAR_FORWARD` без витрат ресурсів на обчислення HMAC.
- `MAX_SKIPPED_KEYS = 1000` — максимальна кількість пропущених ключів у буфері сесії. При досягненні ліміту найстаріші ключі видаляються за політикою FIFO або сесія повертає помилку `RATCHET_ERR_MAX_SKIPPED_LIMIT`.
- `SKIPPED_KEY_TIMEOUT = 30 діб` — граничний час життя збереженого ключа повідомлення. Після закінчення таймауту невикористані ключі автоматично видаляються фоновим процесом очищення пам'яті.
