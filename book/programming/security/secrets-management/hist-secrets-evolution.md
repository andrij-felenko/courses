# 📜 Історія еволюції систем керування секретами

Цей історичний огляд відстежує фундаментальну трансформацію підходів до збереження та передачі облікових даних у програмних системах — від статичних паролів, зашитих у вихідний код у перших мережевих утилітах 1970-х років, до сучасних динамічних сховищ із нульовою довірою та мікросекундним життєвим циклом ключів. Розуміння цієї еволюції дозволяє усвідомити, чому традиційні методи збереження конфігурацій виявилися фатальними для розподілених систем і які інженерні компроміси зумовили появу спеціалізованих бар'єрів безпеки.

---

### Епоха монолітів: Зашиті рядки та локальні конфігураційні файли (1970–1990-ті)

На світанку розвитку комп'ютерних мереж та багатокористувацьких операційних систем поняття «керування секретами» як окремої інженерної дисципліни не існувало. Програмні комплекси створювалися як монолітні бінарні файли, розгорнуті на поодиноких фізичних серверах під прямим наглядом системних адміністраторів.

У 1970–1980-х роках найпоширенішим способом підключення програми до бази даних або мережевого сервісу було пряме вбудовування паролів у вихідний код мовами C, Pascal або COBOL. Статичний рядок компілювався у секцію даних `.rodata` бінарного файлу. Головною загрозою вважався лише фізичний доступ до сервера або читання бінарного образу сторонніми користувачами системи. Для захисту застосовували базові механізми дискреційного контролю доступу операційної системи — права на виконання файлу `chmod 700`.

Із появою перших систем керування версіями (SCCS у 1972 році, RCS у 1982-му, а згодом CVS та SVN у 1990-х) зашиті у код облікові дані почали масово потрапляти до спільних сховищ вихідного коду. Щойно команда розробників перевищувала кількох осіб, пароль ставав відомим усім, хто мав право на завантаження репозиторію.

Першою спробою відокремити секрети від програмного коду стало винесення облікових записів у локальні текстові файли конфігурацій (`config.ini`, `.conf`, XML-маніфести). Програма зчитувала файл під час старту та зберігала паролі у глобальних змінних. Проте це лише перенесло проблему:
- Файли конфігурацій часто копіювалися між виробничими та тестовими серверами разом із реальними паролями;
- Системні резервні копії створювали десятки незашифрованих копій конфігурацій на магнітних стрічках;
- Будь-яка зміна пароля на боці сервера баз даних вимагала ручного редагування сотень текстових файлів та синхронного перезапуску всіх клієнтських процесів.

### Народження хмар та маніфест дванадцяти факторів (2000–2011)

На початку 2000-х років бурхливий розвиток вебсервісів, трирівневої архітектури та віртуалізації призвів до різкого збільшення кількості серверів. З появою вебсервісів Amazon Web Services (AWS) у 2006 році інфраструктура перестала бути статичною: віртуальні машини почали динамічно запускатися та знищуватися під навантаженням.

У 2011 році команда інженерів платформи Heroku під керівництвом Адама Віггінса (англ. *Adam Wiggins*) опублікувала «Маніфест дванадцяти факторів» (*The Twelve-Factor App*). Третій фактор маніфесту проголошував категоричне правило: «Зберігайте конфігурацію в середовищі» (*Store config in the environment*).

Ідея полягала в тому, що всі параметри, які змінюються між розгортаннями (включно з паролями до баз даних, API-ключами платіжних систем та криптографічними ключами сесій), повинні передаватися процесу через змінні оточення операційної системи (`ENV`).

Цей підхід вирішив проблему випадкового потрапляння паролів до системи контролю версій Git, оскільки вихідний код залишався абсолютно чистим від конкретних значень. Проте незабаром інженери безпеки зіткнулися з фундаментальними вадами змінних оточення:
1. **Небезпечне успадкування процесами**: За замовчуванням у моделі POSIX системний виклик `fork()` копіює весь блок змінних оточення батьківського процесу дочірнім процесам. Сторонній діагностичний скрипт або уразливий плагін автоматично отримував повний набір виробничих секретів.
2. **Витік через діагностичні файли**: У разі аварійного завершення програми (*crash*) діагностичні дампи пам'яті, звіти систем моніторингу (наприклад, Sentry або New Relic) та журнали серверів додатків зчитували вміст `environ` і записували відкриті ключі у відкриті логи.
3. **Доступність через псевдофайлову систему**: Будь-який локальний користувач із правами читання процесів міг переглянути повний список змінних через команду `cat /proc/<PID>/environ`.

Стало очевидним, що змінні оточення спроєктовані для статичних параметрів конфігурації, а не для безпечного зберігання секретів.

### Криза відкритого коду та епідемія витоків через Git (2013–2015)

Масовий перехід світової індустрії розробки на платформу GitHub призвів до лавиноподібного зростання публічних інцидентів безпеки. У 2013–2014 роках дослідники безпеки почали фіксувати роботу автоматизованих ботів, які сканували публічні коміти в режимі реального часу.

Типовий сценарій атаки виглядав так:
1. Розробник помилково додавав файл `.env` або приватний ключ SSH `id_rsa` до комміту;
2. Бот виявляв токен доступу AWS API через 20–40 секунд після публікації;
3. Менш ніж за три хвилини через скомпрометовані ключі запускалися сотні віртуальних машин для видобутку криптовалюти або завантажувався повний вміст сховищ Amazon S3.

Спроби вирішити проблему через шифрування файлів всередині репозиторію за допомогою інструментів на кшталт `git-crypt` або `git-secret` виявилися паліативними. Вони спиралися на довгоживучі ключі розшифрування GPG, які так само потрібно було якось безпечно передавати розробникам та серверам неперервної інтеграції (CI/CD). Виникла парадоксальна проблема «початкового секрету» (*Secret Zero*): щоб отримати доступ до зашифрованих секретів, сервер повинен володіти ключем, для збереження якого знову потрібен безпечний механізм.

### Створення HashiCorp Vault та криптографічний бар'єр (2015)

У квітні 2015 року американські інженери Мітчелл Хашімото (англ. *Mitchell Hashimoto*) та Армон Дадгар (англ. *Armon Dadgar*), засновники компанії HashiCorp, представили проєкт з відкритим кодом **Vault**.

Головна концептуальна зміна, яку запропонував Vault, полягала у переході від парадигми «шифрування файлів конфігурації» до парадигми «централізованого криптографічного посередника та генератора тимчасових повноважень».

Vault спирався на три фундаментальні криптографічні та архітектурні опори:

1. **Модель бар'єра та недовіреного сховища**: Постійне сховище (диск, реляційна база або кластер Consul) розглядається як вороже середовище. Усі дані шифруються ще до потрапляння в дисковий буфер за допомогою симетричного алгоритму AES-256-GCM.
2. **Розподіл секрету Шаміра (*Shamir's Secret Sharing*)**: Щоб уникнути збереження єдиного головного ключа шифрування на диску, ключ розбивається на математичні частки. Для переведення сховища в робочий стан (*unseal*) потрібна присутність кворуму операторів (наприклад, будь-яких 3 із 5).
3. **Динамічні секрети замість статичних**: Замість того, щоб зберігати постійний пароль до бази даних, Vault сам підключається до СУБД із правами адміністратора та за запитом клієнта генерує тимчасовий обліковий запис зі строгим строком життя (*TTL*). Після завершення оренди (*lease*) Vault самостійно виконує команду `DROP USER`.

### Епоха Zero Trust та федеративної машинної ідентичності (2017 — дотепер)

Із поширенням контейнерної оркестрації Kubernetes та парадигми «Нульової довіри» (*Zero Trust*) керування секретами остаточно відмовилося від статичних довгоживучих облікових даних на користь криптографічної атестації платформи.

У 2017 році консорціум Cloud Native Computing Foundation (CNCF) розпочав стандартизацію фреймворку **SPIFFE** (*Secure Production Identity Framework for Everyone*) та його реалізації **SPIRE**. Головним принципом стала повна відмова від поняття «пароль застосунку»:
- Кожен мікросервіс отримує криптографічний сертифікат X.509 на основі перевірки метаданих ядра Linux (cgroups, простори імен PID);
- Авторизація у сховищах секретів відбувається через перевірку підписів платформи (Kubernetes ServiceAccount JWT, AWS IAM STS);
- Застосунок більше ніколи не записує секрети на диск — ключі існують виключно в оперативній пам'яті процесу протягом десятків хвилин, оновлюючись через фонові потоки ротації.

Сучасні системи керування секретами перетворилися з пасивних баз даних на автономні криптографічні центри, здатні в режимі реального часу анулювати тисячі скомпрометованих токенів у сотнях датацентрів одночасно.
