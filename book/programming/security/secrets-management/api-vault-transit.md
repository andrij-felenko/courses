# 📋 Інтерфейс транзитного шифрування та динамічних секретів HashiCorp Vault

Цей довідник описує специфікацію HTTP REST API для взаємодії з криптографічним рушієм транзитного шифрування (*Transit Secrets Engine*) та рушієм генерації динамічних облікових записів баз даних у системі HashiCorp Vault. Довідник визначає контракти кінцевих точок, структури запитів та відповідей, схеми ротації ключів і правила керування життєвим циклом оренди (*lease*), необхідні для побудови захищених клієнтських бібліотек.

---

### Загальні конвенції та заголовки протоколу

Усі запити до API Vault здійснюються за протоколом HTTPS з обов'язковою валідацією TLS-сертифіката сервера. Тіла запитів та відповідей кодуються у форматі JSON (`application/json`). Двійкові дані (відкритий текст для шифрування, шифротекст, ініціалізаційні вектори) передаються закодованими у форматі Base64.

#### Обов'язкові заголовки HTTP

| Заголовок | Тип | Опис |
| :--- | :--- | :--- |
| `X-Vault-Token` | Рядок | Клієнтський токен доступу, виданий під час автентифікації. |
| `X-Vault-Namespace` | Рядок | *(Опціонально)* Простір імен для мультитенентних кластерів Enterprise. |
| `Content-Type` | Рядок | Суворо `application/json` для методів `POST`, `PUT`. |

---

### Рушій транзитного шифрування (Transit Engine)

Транзитний рушій надає послугу «Криптографія як сервіс» (*Cryptography-as-a-Service*): застосунок надсилає відкриті дані та отримує шифротекст, ніколи не маючи прямого доступу до симетричного ключа шифрування. Ключі існують виключно всередині криптографічного бар'єра сховища.

#### 1. Створення або конфігурація іменованого ключа

```http
POST /v1/transit/keys/{name}
```

Створює новий керований криптографічний ключ із зазначеними алгоритмічними параметрами або оновлює конфігурацію наявного.

##### Тіло запиту (JSON)

| Поле | Тип | За замовчуванням | Опис |
| :--- | :--- | :--- | :--- |
| `type` | Рядок | `aes256-gcm96` | Алгоритм: `aes128-gcm96`, `aes256-gcm96`, `chacha20-poly1305`, `ed25519`, `rsa-4096`. |
| `derived` | Булеве | `false` | Чи використовувати деривацію ключів на основі клієнтського контексту (*KDF*). |
| `convergent_encryption` | Булеве | `false` | Чи вмикати детерміністичне шифрування для однакових відкритих текстів (вимагає `derived: true`). |
| `auto_rotate_period` | Рядок | `0` | Інтервал автоматичної ротації ключа (наприклад, `720h`, `30d`). Нуль вимикає авторотацію. |
| `min_decryption_version` | Ціле | `1` | Мінімальна версія ключа, дозволена для розшифрування (захист від використання застарілих ключів). |
| `min_encryption_version` | Ціле | `0` | Мінімальна версія ключа для шифрування (0 вказує на поточну найновішу версію). |
| `deletion_allowed` | Булеве | `false` | Захист від випадкового видалення ключа через API. |

##### Коди відповідей
- `200 OK` / `204 No Content`: Ключ успішно створено або оновлено.
- `400 Bad Request`: Неприпустимий тип криптографічного алгоритму або несумісні прапорці.
- `403 Forbidden`: Відсутній токен або бракує прав у політиці ACL (`create` або `update`).

---

#### 2. Ручна або запланована ротація ключа

```http
POST /v1/transit/keys/{name}/rotate
```

Створює нову версію ключа шифрування (наприклад, `v2 → v3`). Після виклику всі нові операції шифрування автоматично використовують найновішу версію, тоді як попередні версії залишаються доступними виключно для операцій розшифрування старого шифротексту.

##### Коди відповідей
- `200 OK` / `204 No Content`: Нову версію ключа згенеровано.
- `404 Not Found`: Ключ із зазначеним ім'ям не існує.

---

#### 3. Шифрування даних (Encrypt)

```http
POST /v1/transit/encrypt/{name}
```

Застосовується для захисту невеликих обсягів конфіденційної інформації (номери платіжних карток, персональні дані, токени).

##### Тіло запиту (JSON)
```json
{
  "plaintext": "ZGF0YSB0byBlbmNyeXB0",
  "context": "dXNlci0xMjM0NQ==",
  "key_version": 0
}
```

- `plaintext` *(рядок, обов'язкове)*: Відкриті дані для захисту, обов'язково закодовані у форматі Base64.
- `context` *(рядок, обов'язкове, якщо `derived: true`)*: Контекст деривації ключа у форматі Base64 (забезпечує створення унікального похідного ключа для кожного користувача).
- `key_version` *(ціле)*: Конкретна версія ключа (0 означає використання поточної найновішої версії).

##### Тіло відповіді (JSON)
```json
{
  "data": {
    "ciphertext": "vault:v2:8uT1O2b3C9qZaX...==",
    "key_version": 2
  }
}
```

Префікс `vault:v2:` у шифротексті є службовим маркером сховища, що вказує номер версії ключа, використаний для цієї конкретної операції шифрування.

---

#### 4. Розшифрування даних (Decrypt)

```http
POST /v1/transit/decrypt/{name}
```

##### Тіло запиту (JSON)
```json
{
  "ciphertext": "vault:v2:8uT1O2b3C9qZaX...==",
  "context": "dXNlci0xMjM0NQ=="
}
```

##### Тіло відповіді (JSON)
```json
{
  "data": {
    "plaintext": "ZGF0YSB0byBlbmNyeXB0"
  }
}
```

Якщо ключ було ротовано, Vault автоматично зчитує номер версії `v2` з префікса шифротексту, витягує з ізольованої пам'яті відповідний історичний ключ і розшифровує повідомлення без необхідності ручного вибору версії з боку клієнта. Якщо номер версії у шифротексті менший за встановлений `min_decryption_version`, Vault відмовляє у розшифруванні та повертає помилку `400 Bad Request`.

---

#### 5. Перешифрування на найновішу версію ключа (Rewrap)

```http
POST /v1/transit/rewrap/{name}
```

Дозволяє оновити старий шифротекст (наприклад, створений версією `v1`) до найновішої версії ключа `v3` без розкриття відкритого тексту клієнтській програмі. Операція відбувається повністю всередині оперативної пам'яті Vault.

##### Тіло запиту (JSON)
```json
{
  "ciphertext": "vault:v1:7xK0M1a2B...==",
  "context": "dXNlci0xMjM0NQ=="
}
```

##### Тіло відповіді (JSON)
```json
{
  "data": {
    "ciphertext": "vault:v3:9qZ2P3c4D...==",
    "key_version": 3
  }
}
```

---

#### 6. Генерація локального ключа шифрування даних (Data Key Generation)

Для сценаріїв із високою інтенсивністю операцій (наприклад, потокове шифрування гігабайтних файлів або відеопотоків) передача всіх даних через HTTP API створює неприпустиме навантаження на мережу. У таких випадках використовують генерацію тимчасового локального ключа (*Envelope Encryption Data Key*).

```http
POST /v1/transit/datakey/plaintext/{name}
```

##### Тіло запиту (JSON)
```json
{
  "bits": 256,
  "context": "dXNlci0xMjM0NQ=="
}
```

##### Тіло відповіді (JSON)
```json
{
  "data": {
    "plaintext": "u1w8K+7xJ2...",
    "ciphertext": "vault:v2:4yH9P0q1...",
    "key_version": 2
  }
}
```

Клієнт використовує поле `plaintext` для локального шифрування великого файлу в пам'яті алгоритмом AES-GCM-256, після чого негайно занулює відкритий ключ у пам'яті. Поле `ciphertext` зберігається поруч із зашифрованим файлом на диску. Для подальшого читання файлу клієнт надсилає `ciphertext` на кінцеву точку `/v1/transit/decrypt/{name}`, щоб відновити ключ розшифрування.

### Динамічні секрети баз даних (Database Engine)

Динамічний рушій створює унікальні облікові записи у базі даних (PostgreSQL, MySQL, Oracle, MongoDB) за запитом клієнта на основі попередньо сконфігурованих шаблонів ролей.

#### 1. Конфігурація ролі бази даних

```http
POST /v1/database/roles/{role-name}
```

##### Тіло запиту (JSON)
```json
{
  "db_name": "postgresql-production",
  "creation_statements": [
    "CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}';",
    "GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO \"{{name}}\";"
  ],
  "revocation_statements": [
    "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename = '{{name}}';",
    "DROP ROLE IF EXISTS \"{{name}}\";"
  ],
  "default_ttl": "1h",
  "max_ttl": "24h"
}
```

Змінні `{{name}}`, `{{password}}` та `{{expiration}}` динамічно підставляються рушієм Vault під час обробки кожного окремого запиту клієнта.

---

#### 2. Отримання тимчасових облікових даних

```http
GET /v1/database/creds/{role-name}
```

##### Тіло відповіді (JSON)
```json
{
  "request_id": "c3b879a9-4670-65d2-06b3-6db57f495bf4",
  "lease_id": "database/creds/readonly-role/c3b879a9-4670-65d2-06b3-6db57f495bf4",
  "renewable": true,
  "lease_duration": 3600,
  "data": {
    "username": "v-token-readonly-c3b879a9-1692561234",
    "password": "A1b!C2d#E3f$G4h%"
  }
}
```

##### Поля метаданих оренди (Lease Metadata)
- `lease_id`: Унікальний ідентифікатор оренди, необхідний для подальшого продовження або відкликання.
- `renewable`: Прапорець, що дозволяє клієнту подовжувати термін дії цих облікових даних.
- `lease_duration`: Час життя секрету у секундах (*TTL*).

---

### Керування життєвим циклом оренди (Lease Lifecycle)

#### 1. Продовження оренди (Heartbeat Lease Renewal)

Клієнт повинен періодично надсилати запит на продовження оренди до настання завершення `lease_duration` (рекомендовано, коли вичерпано дві третини відведеного часу).

```http
PUT /v1/sys/leases/renew
```

##### Тіло запиту (JSON)
```json
{
  "lease_id": "database/creds/readonly-role/c3b879a9-4670-65d2-06b3-6db57f495bf4",
  "increment": 3600
}
```

##### Тіло відповіді (JSON)
```json
{
  "lease_id": "database/creds/readonly-role/c3b879a9-4670-65d2-06b3-6db57f495bf4",
  "renewable": true,
  "lease_duration": 3600
}
```

Якщо запит на подовження надходить після досягнення параметру `max_ttl`, встановленого у конфігурації ролі, Vault повертає помилку `400 Bad Request` і відмовляє у продовженні. У такому разі клієнтська бібліотека зобов'язана запросити новий динамічний секрет.

---

#### 2. Дострокове відкликання оренди (Revocation)

Викликається під час штатної зупинки сервісу або виявлення підозрілої активності.

```http
PUT /v1/sys/leases/revoke
```

##### Тіло запиту (JSON)
```json
{
  "lease_id": "database/creds/readonly-role/c3b879a9-4670-65d2-06b3-6db57f495bf4"
}
```

Vault негайно підключається до цільової бази даних, виконує набір інструкцій `revocation_statements`, примусово розриває всі активні TCP-сесії цього користувача через запит до системних таблиць СУБД та видаляє запис користувача.

### Коди помилок та інваріанти API

| HTTP статус | Причина відмови | Дія клієнтської бібліотеки |
| :--- | :--- | :--- |
| `400 Bad Request` | Помилка валідації полів або пошкоджений Base64. | Зафіксувати помилку конфігурації, повторні запити без змін заборонені. |
| `403 Forbidden` | Недійсний або прострочений токен `X-Vault-Token`. | Ініціювати повний цикл автентифікації машини (переотримати токен). |
| `404 Not Found` | Не існує зазначеного ключа, ролі або закінчився строк лізи. | Створити новий динамічний секрет (стара оренда вже видалена). |
| `429 Too Many Requests` | Спрацювало обмеження швидкості (*Rate Limit*). | Застосувати експоненційне уповільнення (*exponential backoff*) із джитером. |
| `500 Internal Error` | Помилка з'єднання з бекендом зберігання або базою даних. | Повторити запит через резервний вузол кластера Vault. |
| `503 Service Unavailable` | Вузол перебуває у запечатаному стані (*Sealed*). | Перемкнути маршрутизацію запитів на активний розпечатаний вузол. |
