# 📋 Контракт та матриця безпечних дефолтів системного стека

Цей документ визначає технічний контракт, системні інваріанти та нормативну матрицю конфігурацій за замовчуванням (Secure Baseline Contract) для всіх рівнів сучасного програмного комплексу. Будь-яке відхилення від зазначених базових параметрів у виробничому середовищі має бути явно задокументоване, схвалене офіцером безпеки та обґрунтоване у формальній моделі загроз.

## Концепція нормативного контракту за дефолтом

У промисловій експлуатації система не повинна покладатися на індивідуальні знання адміністратора або розробника щодо увімкнення захисних опцій. Безпечний контракт визначає набір обов'язкових станів середовища, які встановлюються за замовчуванням під час первинної ініціалізації:
1. Будь-яка неконфігурована сутність є заблокованою;
2. Будь-який створюваний ресурс отримує мінімально можливі права доступу;
3. Будь-який протокол передачі використовує найсучасніший криптографічний профіль із відмовою від застарілих версій;
4. Будь-який вхідний потік даних проходить обов'язкову валідацію за суворою типізованою схемою.

## Рівень 1: Ядро Linux та операційна система

Параметри підсистеми `sysctl`, правила створення об'єктів файлової системи, обмеження налагодження та ізоляція системних викликів ядра.

### 1.1. Маска створення файлів та права доступу
За замовчуванням під час створення файлів процес повинен ізолювати їх від будь-яких сторонніх користувачів операційної системи. 
- Для серверних фонових процесів та робочих вузлів обов'язковою є маска `umask 0027` (власник має повний доступ, група — тільки читання, іншим користувачам доступ повністю заборонено);
- Для процесів, що обробляють криптографічні ключі, сесійні токени або паролі, обов'язковою є маска `umask 0077` (права `0600` для файлів та `0700` для каталогів).

### 1.2. Системні параметри ядра (sysctl baseline)
Налаштування ядра забезпечують захист від локального підвищення привілеїв (Local Privilege Escalation), маніпуляцій із файловими дескрипторами та витоків адресного простору ядра.

| Системний параметр `sysctl` | Нормативне безпечне значення | Застаріле небезпечне значення | Механізм захисту та наслідки відхилення |
| :--- | :--- | :--- | :--- |
| `fs.protected_hardlinks` | `1` | `0` | Забороняє створення жорстких посилань на файли, якими користувач не володіє. Запобігає атакам зміни прав на чужі конфіденційні файли через спільні каталоги. |
| `fs.protected_symlinks` | `1` | `0` | Забороняє перехід за символьними посиланнями у світових каталогах (наприклад, `/tmp`), якщо власник симлінка не збігається з власником каталогу (захист від TOCTOU-атак). |
| `fs.protected_fifos` | `2` | `0` | Забороняє відкриття іменованих каналів FIFO у каталогах зі спільним записом процесами, які не є власниками каналу. |
| `fs.protected_regular` | `2` | `0` | Блокує запис у звичайні файли в каталогах спільного доступу, якщо вони не належать поточному користувачу. |
| `kernel.kptr_restrict` | `2` | `0` | Повністю приховує дійсні адреси вказівників ядра у виводі `/proc/kallsyms` та псевдофайлах ядра для запобігання обходу KASLR. |
| `kernel.dmesg_restrict` | `1` | `0` | Обмежує читання системного логу ядра `dmesg` виключно користувачами з привілеями `CAP_SYSLOG`. |
| `kernel.unprivileged_bpf_disabled` | `1` | `0` | Забороняє непривілейованим користувачам завантажувати eBPF-програми у простір ядра, нівелюючи клас атак спекулятивного читання пам'яті типу Spectre. |
| `kernel.yama.ptrace_scope` | `2` (або `3`) | `0` | Забороняє процесам викликати `ptrace` над іншими процесами того самого користувача без явного батьківського зв'язку або привілею `CAP_SYS_PTRACE`. |

### 1.3. Опції монтування тимчасових файлових систем
Файлові системи `/tmp`, `/var/tmp` та `/dev/shm` монтуються з обов'язковими прапорцями безпеки у файлі `/etc/fstab`:
- `noexec`: заборона безпосереднього виконання бінарних файлів та скриптів зі сховища тимчасових файлів;
- `nosuid`: блокування обробки SUID-бітів у файлах, створених у цьому каталозі;
- `nodev`: заборона інтерпретації спеціальних символьних або блокових файлів пристроїв.

## Рівень 2: Мережевий стек, сокети та TLS-термінація

Контракт транспортного рівня визначає умови взаємодії процесу з локальною та зовнішньою мережею.

### 2.1. Мережева прив'язка сервісів (Binding Policy)
Будь-який серверний процес за замовчуванням прив'язується виключно до локального інтерфейсу зворотного зв'язку `127.0.0.1` або `::1`. Експозиція сервісу на зовнішні мережеві карти (`0.0.0.0`) дозволяється лише для зовнішніх балансувальників навантаження (Reverse Proxy / Ingress Controller). Внутрішні бази даних, кеші та сервіси черг ніколи не повинні слухати відкритий мережевий інтерфейс.

### 2.2. Політика фільтрації фаєрвола (Default Deny Firewall)
У конфігурації `nftables` або `iptables` базові ланцюжки пакетів встановлюються у такий стан:
- Ланцюжок `INPUT`: політика `DROP`. Дозволяється лише встановлений зворотний трафік (`ct state established,related accept`) та трафік на явно відкриті порти безпеки;
- Ланцюжок `FORWARD`: політика `DROP`. Маршрутизація пакетів між інтерфейсами заблокована за дефолтом;
- Ланцюжок `OUTPUT`: політика `ACCEPT` (або `DROP` для ізольованих вузлів із суворим білим списком зовнішніх адрес).

### 2.3. Криптографічний профіль TLS
Транспортна безпека встановлює жорсткі вимоги до версій протоколів та алгоритмів шифрування:

| Параметр TLS | Нормативний безпечний дефолт | Заборонені застарілі значення | Поведінка при порушенні |
| :--- | :--- | :--- | :--- |
| Версія протоколу | `TLSv1.3` (допускається `TLSv1.2`) | `SSLv2`, `SSLv3`, `TLSv1.0`, `TLSv1.1` | Негайний розрив з'єднання під час TLS Client Hello з відправкою `handshake_failure`. |
| Шифронабори (Cipher Suites) | `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256` | CBC-шифри (наприклад, `AES-128-CBC`), RC4, 3DES | Відхилення клієнтських шифронаборів без автентифікованого шифрування (AEAD). |
| Валідація сертифіката | `VERIFY_PEER = true` | `VERIFY_NONE`, `InsecureSkipVerify = true` | Блокування з'єднання, якщо сертифікат прострочено або підписано невідомим CA. |
| Захист від відкату версій | Підтримка `TLS_FALLBACK_SCSV` | Відсутність сигналізації відкату | Запобігання атакам навмисного зниження версії протоколу (Downgrade Attacks). |

## Рівень 3: Веб-протоколи та заголовки HTTP API

Браузерний захист вимагає примусового декларування політик безпеки в кожній відповіді сервера.

### 3.1. Обов'язкові захисні HTTP-заголовки
Кожна відповідь веб-сервера повинна містити повний набір заголовків безпеки, які змушують браузер застосовувати ізоляцію контенту:

1. **Content-Security-Policy (CSP)**:
   ```http
   Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self';
   ```
   Політика блокує завантаження будь-яких зовнішніх ресурсів, забороняє виконання вбудованого JavaScript (`unsafe-inline`) та запобігає вбудовуванню сайту у сторонні фрейми.

2. **Strict-Transport-Security (HSTS)**:
   ```http
   Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
   ```
   Примушує браузер взаємодіяти з доменом виключно через HTTPS протягом 2 років, захищаючи від атак SSL Stripping.

3. **X-Content-Type-Options**:
   ```http
   X-Content-Type-Options: nosniff
   ```
   Забороняє браузеру виконувати MIME-sniffing (вгадування типу контенту всупереч заголовку `Content-Type`), що ліквідує атаки маскування виконуваних файлів під зображення.

4. **X-Frame-Options**:
   ```http
   X-Frame-Options: DENY
   ```
   Повністю блокує відображення сторінки у тегах `<iframe>`, захищаючи від клікджекінгу (Clickjacking).

5. **Cross-Origin Resource Sharing (CORS)**:
   За замовчуванням заголовок `Access-Control-Allow-Origin` не надсилається або встановлюється у точну адресу довіреного домену. Використання підстановочного символу `*` для автентифікованих запитів із куками (`Allow-Credentials: true`) суворо заборонено.

### 3.2. Прапорці сесійних файлів cookie
Будь-який файл cookie, який містить ідентифікатор сесії або автентифікаційний токен, повинен мати наступний формат:
```http
Set-Cookie: session_id=abc123xyz; Path=/; Secure; HttpOnly; SameSite=Strict
```
- `SameSite=Strict`: cookie ніколи не надсилаються в міжсайтових запитах, забезпечуючи надійний захист від CSRF;
- `HttpOnly`: захист від крадіжки токена через клієнтський скрипт (`document.cookie`);
- `Secure`: передача дозволена виключно через шифрований канал HTTPS.

## Рівень 4: Парсери даних та десеріалізація

Контракт обробки вхідних даних запобігає атакам через вбудовані інтерпретатори та динамічне створення об'єктів.

### 4.1. Парсери документів XML (XXE Defense)
Парсери XML за замовчуванням повинні бути налаштовані на повну заборону обробки зовнішніх сутностей (External Entities) та DTD-декларацій:
- Вимкнення `http://xml.org/sax/features/external-general-entities`;
- Вимкнення `http://xml.org/sax/features/external-parameter-entities`;
- Вимкнення `http://apache.org/xml/features/nonvalidating/load-external-dtd`;
- Активація режиму `FEATURE_SECURE_PROCESSING = true`.

### 4.2. Десеріалізація JSON / YAML
- Заборона поліморфної десеріалізації з автоматичним створенням довільних класів за іменами у вхідному потоці (наприклад, `TypeNameHandling.All` у Newtonsoft.Json або `yaml.load()` у Python);
- Використання безпечних завантажувачів `yaml.safe_load()`;
- Обов'язкова валідація JSON-документів за суворою схемою JSON Schema перед передачею до бізнес-логіки.

## Рівень 5: Контроль доступу та політики авторизації

Нормативні правила проектування модулів прийняття рішень (PDP) та баз даних авторизації.

### 5.1. Базова модель авторизації (Default Deny Baseline)
- Будь-який запит, для якого не знайдено прямого дозволу у матриці прав, відхиляється;
- Правило прямої заборони (`Explicit Deny`) має абсолютний пріоритет над будь-якими правилами дозволу;
- Будь-який збій зв'язку з провайдером ідентифікації, таймаут бази даних або помилка розбору токена негайно повертає рішення `DENY` (Fail-Closed).

### 5.2. Терміни життя токенів та сесій (TTL Management)
- Токени доступу (Access Tokens): максимальний термін життя 15 хвилин;
- Токени оновлення (Refresh Tokens): обмежені за часом (до 7 днів) із примусовою ротацією при кожному використанні;
- Автоматичне завершення неактивної сесії користувача (Inactivity Timeout): 30 хвилин.

## Верифікація безпечного контракту: системні команди перевірки

Для регулярного аудиту відповідності робочого сервера затвердженому контракту безпечних дефолтів застосовується автоматизований набір команд:

1. **Перевірка параметрів ядра sysctl**:
   ```bash
   sysctl fs.protected_hardlinks fs.protected_symlinks kernel.kptr_restrict kernel.unprivileged_bpf_disabled
   ```
   Усі значення у виводі мають відповідати безпечним дефолтам (`1` або `2`).

2. **Аудит відкритих мережевих сокетів**:
   ```bash
   ss -tulpn | grep LISTEN
   ```
   Перевірка, що внутрішні сервіси (порти 5432, 6379, 27017) прив'язані виключно до `127.0.0.1`, а не до `0.0.0.0`.

3. **Перевірка HTTP-заголовків веб-сервера**:
   ```bash
   curl -s -I https://example.com | grep -Ei "(content-security-policy|strict-transport-security|x-content-type-options|x-frame-options)"
   ```
   Вивід має підтвердити наявність усіх обов'язкових заголовків безпеки.

4. **Аудит конфігурації TLS-сервера**:
   ```bash
   openssl s_client -connect example.com:443 -tls1_1
   ```
   Спроба підключення за застарілим протоколом повинна завершуватися помилкою рукостискання (Handshake Failure).
