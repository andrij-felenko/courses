# 🧮 Математична формалізація автоматів безпечної відмови та решіток доступу

У формальній теорії комп'ютерної безпеки надійність системи розглядається не як емпірична відсутність спостережуваних дефектів, а як математично доведене збереження інваріанту безпеки в усіх досяжних станах обчислювального комплексу. Концепція безпечних дефолтів (Fail-Safe Defaults) знаходить своє строге математичне обґрунтування через теорію скінченних автоматів зі збоями, алгебраїчну теорію напіврешіток рішень та ймовірнісний аналіз деградації безпеки.

## 1. Автоматна модель переходів зі збоями (Faulty State Automata)

Розглянемо систему контролю доступу як формальний детермінований автомат зі станами відмови `M = (S, Σ, δ, s₀, S_safe)`.

### Структура простору станів
Повний простір станів системи `S` розбивається на дві неперетинні множини:

```
S = S_safe ∪ S_unsafe,  де  S_safe ∩ S_unsafe = ∅
```

Де:
- `S_safe` — множина безпечних станів, у яких виконується базовий інваріант ізоляції: жоден неавторизований суб'єкт не має доступу до захищених активів;
- `S_unsafe` — множина скомпрометованих станів, у яких існує хоча б одне порушення прав конфіденційності, цілісності або доступності.

Множина безпечних станів додатково декомпонується на два підтипи:

```
S_safe = S_auth ∪ S_deny,  де  S_auth ∩ S_deny = ∅
```

Де `S_auth` — стан успішного надання доступу після повної позитивної верифікації, а `S_deny` — термінальний стан блокування доступу.

### Вхідний алфавіт подій
Алфавіт подій `Σ` складається зі штатних операцій `Σ_norm` (запити користувачів, валідація токенів, перевірка підписів) та множини виняткових ситуацій або збоїв `Σ_err` (таймаути мережі, помилки виділення пам'яті, збої розбору формату даних, аварії сторонніх сервісів):

```
Σ = Σ_norm ∪ Σ_err,  де  Σ_norm ∩ Σ_err = ∅
```

### Інваріант безпеки та досяжні стани
Нехай `s₀ ∈ S_deny ⊂ S_safe` — початковий стан системи під час старту. Множина досяжних станів `Reach(M)` визначається як замикання початкового стану відносно розширеної функції переходів `δ*`:

```
Reach(M) = { s ∈ S | ∃ w ∈ Σ* : δ*(s₀, w) = s }
```

**Фундаментальний інваріант безпеки:**

```
∀ s ∈ Reach(M) : s ∈ S_safe
```

### Порівняльний аналіз переходів при виникненні збоїв

Розглянемо поведінку функції переходів `δ` для двох протилежних архітектурних моделей:

#### 1. Небезпечна модель (Fail-Open)
У моделі Fail-Open для будь-якої виняткової події `e ∈ Σ_err` (наприклад, таймаут бази даних авторизації) функція переходів задовольняє запит, переходячи у стан дозволу:

```
δ(s, e) = s_permit
```

Якщо вхідний запит було надіслано неавторизованим суб'єктом або атакуючим `u ∉ Authorized`, то стан `s_permit` автоматично належить до підмножини небезпечних станів:

```
s_permit ∈ S_unsafe
```

Отже, існує послідовність подій `w = (w_prefix · e)`, яка виводить систему зі стану безпеки:

```
∃ w ∈ Σ* : δ*(s₀, w) ∈ S_unsafe
```

Це доводить, що за наявності хоча б одного збою `e ∈ Σ_err` інваріант безпеки моделі Fail-Open неминуче руйнується.

#### 2. Безпечна модель (Fail-Safe / Fail-Closed)
У моделі Fail-Safe для будь-якого поточного стану `s ∈ S_safe` та будь-якої виняткової події `e ∈ Σ_err` функція переходу повертає гарантований стан блокування:

```
∀ s ∈ S_safe, ∀ e ∈ Σ_err : δ(s, e) = s_deny
```

Оскільки за означенням `s_deny ∈ S_safe`, індукцією за довжиною ланцюжка подій `|w|` отримуємо:

```
Reach(M) ⊆ S_safe
```

Інваріант безпеки моделі Fail-Safe залишається непорушним за будь-якої кількості та послідовності апаратних і програмних збоїв.

## 2. Алгебраїчна модель: Напіврешітки авторизаційних рішень

Розглянемо процес обчислення вердикту доступу в термінах теорії частково впорядкованих множин (Posets) та теорії напіврешіток.

Множина можливих результатів оцінки правила `D` містить чотири елементи:

```
D = { ⊥, Deny, Allow, ⊤ }
```

Де:
- `⊥` (Bottom) — стан невизначеності або відсутності інформації (таймаут, помилка парсера, відсутність обов'язкового атрибута);
- `Deny` — явне рішення про заборону доступу;
- `Allow` — явне рішення про надання доступу;
- `⊤` (Top) — стан суперечності правил (одночасний збіг взаємовиключних вимог).

Частковий порядок `≤` на множині `D` відображає ступінь наданих привілеїв:

```
⊥ ≤ Deny ≤ Allow ≤ ⊤
```

### Операція точної нижньої грані (Meet, ⊓)
Операція `⊓` моделює консервативне комбінування рішень: якщо між компонентами виникає конфлікт або один із компонентів зазнає збою, результуючий вердикт обирає найбільш суворе та безпечне обмеження.

Таблиця Келі для операції Meet (`a ⊓ b`):

```
⊓     |  ⊥     Deny   Allow    ⊤
------+--------------------------
⊥     |  ⊥     ⊥      ⊥        ⊥
Deny  |  ⊥     Deny   Deny     Deny
Allow |  ⊥     Deny   Allow    Allow
⊤     |  ⊥     Deny   Allow    ⊤
```

Властивості операції `⊓`:
1. **Комутативність**: `a ⊓ b = b ⊓ a`;
2. **Асоціативність**: `(a ⊓ b) ⊓ c = a ⊓ (b ⊓ c)`;
3. **Ідемпотентність**: `a ⊓ a = a`;
4. **Поглинання елементом ⊥**: `a ⊓ ⊥ = ⊥` для будь-якого `a ∈ D`.

### Функція безпечної редукції (Decision Resolution Mapping)

Оскільки фінальне апаратне чи мережеве рішення має бути бінарним (`{ DENY, ALLOW }`), визначимо функцію відображення `Resolve : D → { DENY, ALLOW }`.

Принцип безпечних дефолтів формалізується як відображення, що переводить будь-який невизначений або конфліктний стан у заборону:

```
Resolve(Allow) = ALLOW
Resolve(Deny)  = DENY
Resolve(⊥)     = DENY
Resolve(⊤)     = DENY
```

### Покрокове виведення збереження безпеки за умов неповноти атрибутів

Нехай складна політика доступу вимагає одночасного виконання трьох незалежних перевірок: перевірки ролі користувача `R`, перевірки знаходження IP-адреси в корпоративній підмережі `I` та перевірки наявності валідної MFA-сесії `M`:

```
Dec = R ⊓ I ⊓ M
```

Припустимо, що користувач має валідну роль `R = Allow` та активну сесію `M = Allow`, проте сервіс перевірки IP-адреси зазнав аварії внаслідок мережевого таймауту, повернувши стан невизначеності `I = ⊥`.

Обчислимо покроковий результат конвеєра:

```
Dec = R ⊓ I ⊓ M
    = Allow ⊓ ⊥ ⊓ Allow      [підстановка обчислених станів компонентів]
    = (Allow ⊓ Allow) ⊓ ⊥    [комутативність та асоціативність операції Meet]
    = Allow ⊓ ⊥              [ідемпотентність: Allow ⊓ Allow = Allow]
    = ⊥                      [поглинання: x ⊓ ⊥ = ⊥ для будь-якого x]
```

Застосовуємо функцію відображення `Resolve`:

```
Resolve(Dec)
= Resolve(⊥)                  [підстановка проміжного результату ⊥]
= DENY                        [за правилом безпечного дефолту Resolve(⊥) = DENY]
```

Якщо б система використовувала логіку Fail-Open, функція редукції мала б вигляд `Resolve_open(⊥) = ALLOW`, що призвело б до результату `ALLOW` і відкрило б доступ неперевіреному запиту.

## 3. Ймовірнісний аналіз надійності та ризику компрометації

Оцінимо ймовірність компрометації системи залежно від обраної моделі обробки збоїв.

Нехай:
- `p_err` — ймовірність виникнення технічної помилки, збою або таймауту при обробці одного запиту;
- `p_atk` — частка запитів від зловмисників у загальному вхідному трафіку;
- `N` — середня кількість вхідних запитів за секунду;
- `t` — тривалість спостереження (у секундах);
- `M = N · t` — загальна кількість оброблених запитів.

### Розрахунок для моделі Fail-Open

У моделі Fail-Open компрометація системи (Security Breach) відбувається щоразу, коли зловмисний запит збігається в часі зі збоєм авторизаційного вузла.

Ймовірність успішного проникнення на одному довільному запиті:

```
P(Single_Breach) = p_atk · p_err
```

Ймовірність того, що за час `t` при обробці `M` запитів відбудеться хоча б одна успішна компрометація:

```
P(Breach_Open) = 1 - (1 - P(Single_Breach))ᴹ
               = 1 - (1 - p_atk · p_err)ᴹ
```

Розглянемо типові параметри сучасного веб-сервісу:
- `N = 1000` запитів/сек;
- `t = 86400` секунд (1 доба), отже `M = 8.64 · 10⁷` запитів;
- `p_err = 0.001` (коефіцієнт відмов 0.1%);
- `p_atk = 0.005` (0.5% фонового сканування зловмисниками).

Обчислимо ймовірність компрометації:

```
P(Single_Breach) = 0.005 · 0.001 = 5 · 10⁻⁶
P(Breach_Open) = 1 - (1 - 5 · 10⁻⁶)⁸⁶⁴⁰⁰⁰⁰⁰
               ≈ 1 - e^(-5 · 10⁻⁶ · 8.64 · 10⁷)
               = 1 - e^(-432)
               ≈ 1.0 (100%)
```

Математичний розрахунок доводить: **у системі Fail-Open успішна компрометація є практично неминучою подією протягом першої ж доби експлуатації**.

### Розрахунок для моделі Fail-Safe

У моделі Fail-Safe будь-який збій призводить до переходу в стан `DENY`. Тому:

```
P(Single_Breach) = 0
P(Breach_Safe) = 0
```

Єдиною ціною моделі Fail-Safe є збільшення ймовірності помилкової відмови легітимному користувачу (False Rejection Rate / Availability Loss):

```
P(False_Rejection) = (1 - p_atk) · p_err ≈ p_err = 0.001 (0.1%)
```

Математична перевага очевидна: модель Fail-Safe усуває незворотну катастрофу безпеки (втрату даних), перетворюючи її на зворотне та контрольоване короткочасне зниження доступності.
