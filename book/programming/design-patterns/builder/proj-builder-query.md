# ⚙️ Незмінний будівельник HTTP-запиту, який ловить помилки до запуску

Візьмімо об'єкт, на якому будівельник показує повну силу: **HTTP-запит**. У ньому є те, без чого запит не існує (метод і адреса), і десяток речей, які здебільшого не потрібні (заголовки, тіло, таймаут, повтори, тип автентифікації). Частина цих речей ще й **не поєднується між собою**: не можна одночасно слати тіло в `GET` і казати, що тіла немає; не можна вішати два різні способи автентифікації нараз. Тобто це рівно та задача, де ми хочемо трьох речей заразом:

- виклик читається **за іменами**, а не за позиціями в дужках;
- зібраний запит **застигає незмінним** — після складання його ніхто випадково не перепише;
- **неправильну комбінацію** видно якомога раніше, в ідеалі — ще до запуску, від компілятора.

Розберемо це шар за шаром: спершу простий незмінний будівельник із перевіркою в `build()`, тоді доведемо на пальцях, чому він **не дає** витекти напівзібраному стану, а наприкінці — трюк, яким система типів TypeScript **фізично не пускає** викликати `build()`, поки не задано обов'язкове. Коду тут багато, і він робочий: кожен фрагмент можна вставити й запустити.

## Задача точніше: що обов'язкове, що ні, що конфліктує

Домовмося про об'єкт-продукт. Готовий запит — це незмінний носій кількох полів:

```
HttpRequest
  method   : "GET" | "POST" | "PUT" | "DELETE"   — обов'язкове
  url      : рядок                                 — обов'язкове
  headers  : мапа заголовків                       — за замовч. порожня
  body     : рядок | нема                          — за замовч. нема
  timeoutMs: число                                 — за замовч. 30000
  retries  : число                                 — за замовч. 0
```

Обов'язкові — `method` і `url`: запит без них безглуздий. Решта має розумні значення за замовчуванням. І є **правило узгодженості**, яке легко порушити випадково: `GET` і `DELETE` за семантикою HTTP **не несуть тіла**, тож задати `body` разом із `GET` — майже напевно помилка виклику, і ми хочемо на неї впасти, а не мовчки відкинути тіло. Ось цей вузол — обов'язкове проти необов'язкового плюс взаємовиключні опції — і буде нашим полігоном.

> 🔧 **Навіщо це.** Саме такі об'єкти — запити, конфігурації клієнтів, підключення до баз — автори бібліотек майже завжди віддають через будівельник. Причина практична: користувач бібліотеки в дев'яноста відсотках випадків хоче задати два-три поля, а в решті — якесь рідкісне п'яте. Позиційний конструктор змушує або тримати десяток перевантажень, або писати `null` там, де тобі байдуже. Будівельник робить типовий виклик коротким, рідкісний — можливим, а помилку «переплутав аргументи місцями» — узагалі неможливою, бо аргументів за позицією немає.

## Крок перший: незмінний будівельник із перевіркою в build()

Почнімо з версії, яку пишуть у дев'яти проєктах із десяти. Обов'язкові поля йдуть у конструктор будівельника — так система типів **уже** змушує їх задати. Кожен необов'язковий крок кладе своє значення в приватне поле й **повертає сам будівельник**, щоб виклики зчіплювалися в ланцюжок. А `build()` — єдине місце, де народжується продукт, і єдине місце, де ми перевіряємо узгодженість.

:::tabs
```ts
type Method = "GET" | "POST" | "PUT" | "DELETE";

// ── ПРОДУКТ: незмінний. Поля readonly, конструктор приватний. ──
class HttpRequest {
  private constructor(
    readonly method: Method,
    readonly url: string,
    readonly headers: ReadonlyMap<string, string>,
    readonly body: string | null,
    readonly timeoutMs: number,
    readonly retries: number,
  ) {}

  // Єдиний вхід у створення — статична фабрика, що віддає будівельник.
  static builder(method: Method, url: string): HttpRequestBuilder {
    return new HttpRequestBuilder(method, url);
  }

  // Внутрішній «конструктор для будівельника»: він у тому самому модулі,
  // тож бачить приватний constructor, а зовнішній світ — ні.
  static _assemble(b: HttpRequestBuilder): HttpRequest {
    return new HttpRequest(
      b._method, b._url,
      new Map(b._headers),        // копія — щоб продукт не ділив мапу з будівельником
      b._body, b._timeoutMs, b._retries,
    );
  }
}

// ── БУДІВЕЛЬНИК: змінний і тимчасовий. Копить рішення, нічого не віддає. ──
class HttpRequestBuilder {
  _method: Method;
  _url: string;
  _headers = new Map<string, string>();
  _body: string | null = null;
  _timeoutMs = 30_000;
  _retries = 0;

  constructor(method: Method, url: string) {   // обов'язкове — одразу
    this._method = method;
    this._url = url;
  }

  header(name: string, value: string): this {  // крок повертає САМ будівельник...
    this._headers.set(name, value);
    return this;                               // ...тому виклики й чіпляються в ланцюжок
  }
  body(text: string): this {
    this._body = text;
    return this;
  }
  timeout(ms: number): this {
    this._timeoutMs = ms;
    return this;
  }
  retries(n: number): this {
    this._retries = n;
    return this;
  }

  build(): HttpRequest {
    // ── ЄДИНА точка перевірки: маємо перед собою ВСІ рішення разом ──
    if (this._url.trim() === "") {
      throw new Error("HttpRequest: url порожній");
    }
    if (this._body !== null && (this._method === "GET" || this._method === "DELETE")) {
      throw new Error(
        `HttpRequest: метод ${this._method} не несе тіла, але body задано — ` +
        `прибери body або зміни метод на POST/PUT`,
      );
    }
    if (this._timeoutMs <= 0) {
      throw new Error(`HttpRequest: timeout має бути > 0, а не ${this._timeoutMs}`);
    }
    if (this._retries < 0) {
      throw new Error(`HttpRequest: retries не може бути від'ємним (${this._retries})`);
    }
    return HttpRequest._assemble(this);
  }
}

// ── Виклик читається сам ──
const req = HttpRequest.builder("POST", "https://api.example.com/orders")
  .header("Content-Type", "application/json")
  .body('{"item":"кава","qty":2}')
  .timeout(5_000)
  .retries(3)
  .build();

console.log(req.method, req.url, req.retries);   // POST  https://…/orders  3
```
```py
from __future__ import annotations
from dataclasses import dataclass
from types import MappingProxyType
from typing import Mapping, Optional

# ── ПРОДУКТ: незмінний. frozen=True забороняє переприсвоєння полів. ──
@dataclass(frozen=True)
class HttpRequest:
    method: str
    url: str
    headers: Mapping[str, str]
    body: Optional[str]
    timeout_ms: int
    retries: int

    @staticmethod
    def builder(method: str, url: str) -> "HttpRequestBuilder":
        return HttpRequestBuilder(method, url)


# ── БУДІВЕЛЬНИК: звичайний змінний об'єкт, копить рішення ──
class HttpRequestBuilder:
    def __init__(self, method: str, url: str):   # обов'язкове — одразу
        self._method = method
        self._url = url
        self._headers: dict[str, str] = {}
        self._body: Optional[str] = None
        self._timeout_ms = 30_000
        self._retries = 0

    def header(self, name: str, value: str) -> "HttpRequestBuilder":
        self._headers[name] = value
        return self                              # крок повертає САМ будівельник

    def body(self, text: str) -> "HttpRequestBuilder":
        self._body = text
        return self

    def timeout(self, ms: int) -> "HttpRequestBuilder":
        self._timeout_ms = ms
        return self

    def retries(self, n: int) -> "HttpRequestBuilder":
        self._retries = n
        return self

    def build(self) -> HttpRequest:
        # ── ЄДИНА точка перевірки ──
        if self._url.strip() == "":
            raise ValueError("HttpRequest: url порожній")
        if self._body is not None and self._method in ("GET", "DELETE"):
            raise ValueError(
                f"HttpRequest: метод {self._method} не несе тіла, але body задано — "
                f"прибери body або зміни метод на POST/PUT"
            )
        if self._timeout_ms <= 0:
            raise ValueError(f"HttpRequest: timeout має бути > 0, а не {self._timeout_ms}")
        if self._retries < 0:
            raise ValueError(f"HttpRequest: retries не може бути від'ємним ({self._retries})")
        return HttpRequest(
            method=self._method,
            url=self._url,
            headers=MappingProxyType(dict(self._headers)),  # незмінне read-only view копії
            body=self._body,
            timeout_ms=self._timeout_ms,
            retries=self._retries,
        )


# ── Виклик читається сам ──
req = (HttpRequest.builder("POST", "https://api.example.com/orders")
       .header("Content-Type", "application/json")
       .body('{"item":"кава","qty":2}')
       .timeout(5_000)
       .retries(3)
       .build())

print(req.method, req.url, req.retries)          # POST  https://…/orders  3
```
:::

Пройдімося по чотирьох речах, які тут зроблено навмисне, бо кожна закриває конкретну діру.

**Обов'язкове задане конструктором будівельника.** `builder(method, url)` не має значень за замовчуванням для цих двох. Забув `url` — рядок `HttpRequest.builder("POST")` навіть не скомпілюється в TS (і впаде на бракованому аргументі в Python). Обов'язковість тут стереже той самий механізм, що й у звичайного конструктора; будівельник нічого в цьому не послабив.

**Кожен крок повертає `this` (у TS тип так і пишуть — `: this`).** Оце `return this` в кінці кожного кроку — вся таємниця «плинного» вигляду. Метод віддає той самий будівельник, тож на результаті одразу можна викликати наступний метод, і так до `build()`. Прийом, коли методи повертають об'єкт заради зчеплення викликів, називають [плинним інтерфейсом](topic:programming/fluent-interface).

**Кроки нічого не перевіряють — лише запам'ятовують.** `timeout(-5)` спокійно кладе `-5` у поле й повертає будівельник. Це навмисно: якби кожен сетер сам перевіряв, ми б розмазали перевірку по десятку методів і все одно не змогли б перевірити те, що залежить від **комбінації** полів (як-от «`body` разом із `GET`»). Уся перевірка зібрана в одному місці — `build()`, — і саме тому вона бачить усі рішення разом.

**Продукт віддають незмінним, і не діляться з ним мапою.** У TS поля `HttpRequest` — `readonly`, конструктор `private`, а `headers` типізовано як `ReadonlyMap`. У Python — `@dataclass(frozen=True)` забороняє переприсвоєння полів, а `MappingProxyType` робить мапу read-only. Тонкість, яку легко проґавити: у `_assemble`/конструкторі ми кладемо в продукт **копію** мапи заголовків (`new Map(b._headers)` / `dict(self._headers)`), а не ту саму. Інакше будівельник і продукт ділили б один об'єкт-мапу, і подальший `builder.header(...)` тихо міняв би вже зібраний запит — незмінність продукту протекла б через спільне посилання. Копія розриває цей зв'язок.

## Чому взагалі падати, а не мовчки виправляти

Затримаймося на рядку, який кидає помилку про «`body` при `GET`». Спокуса зробити «розумно» — самому прибрати `body`, раз метод його не несе. Це помилка проєктування, і ось чому. Якщо програміст написав `.body(...)` разом із `GET`, то одне з двох його уявлень хибне: або він думає, що метод інший, або що тіло кудись піде. Мовчки викинувши тіло, ти лишаєш **обидва** хибні уявлення живими — запит піде без даних, які автор вважав відправленими, і баг спливе далеко звідси, у вигляді «сервер каже, що замовлення порожнє». Впавши з осмисленим текстом просто в `build()`, ти показуєш суперечність **там, де її створили**, і змушуєш автора вирішити, що він насправді мав на увазі. Гучний збій у точці помилки завжди дешевший за тихий збій десь потім.

Друга причина винести це саме в `build()`, а не в окремий метод-валідатор, який треба не забути покликати, — **неможливо обійти**. Раз `build()` — єдиний спосіб дістати `HttpRequest`, то повз перевірку продукт не проходить ніяк. Валідатор, який кличуть окремо, рано чи пізно забудуть; перевірка, вбудована в єдиний вхід, спрацьовує завжди.

## Тепер головне: чому напівзібраний стан не витікає

Тут — суть протиставлення будівельника простому «створи порожнім і понаставляй сетерами». Різниця здається дрібною, поки не спробуєш зловити нею баг. Порівняймо два світи.

**Світ сетерів.** Об'єкт `HttpRequest` змінний: створюємо порожнім, тоді ставимо поля.

```ts
// АНТИПРИКЛАД — так робити не будемо, показуємо, ЩО ламається
const r = new MutableHttpRequest();      // ← вже існує, але ще НЕ запит: без методу, без url
r.setMethod("POST");
sendSomewhere(r);                        // ← хтось узяв його ТУТ — між сетерами
r.setUrl("https://…");                   // ← url доставили, але пізно: він уже пішов напівзібраним
```

Проблема не гіпотетична. Між `new` і останнім сетером об'єкт **фізично існує в неконсистентному стані** — з методом, але без адреси. Будь-хто, до кого він потрапив у цю мить (передали в функцію, поклали в колекцію, віддали в іншу нитку), тримає **бите** посилання. І що гірше — компілятор мовчить: `MutableHttpRequest` без `url` для нього такий самий валідний об'єкт, тип нічого не порушено. Помилка суто часова: «взяли зарано». Такі баги найважчі, бо не відтворюються надійно — усе залежить від того, о котрій міліісекунді хтось зазирнув.

**Світ будівельника.** Напівзібраний стан **існує теж** — але не в продукті, а всередині будівельника, і назовні його **нема чим узяти**. Поки ти сипеш `.header().body().timeout()`, жодного `HttpRequest` іще не існує: є тільки будівельник, а він — не запит і нікуди як запит не піде. Перший і єдиний `HttpRequest` народжується на `build()`, **одразу цілим і перевіреним**. Проміжного, битого запиту не буває не тому, що ми домовилися його не чіпати, а тому, що його **фізично нема** — його ніде взяти.

![Дві доріжки складання об'єкта. Ліворуч «сетери»: об'єкт HttpRequest існує з першого кроку, але позначений як БИТИЙ (без url), стрілка «хтось бере його тут» тягнеться до битого стану — витік напівзібраного. Праворуч «будівельник»: усі проміжні кроки — це той самий Builder (не запит), позначений як «взяти нічим», і лише наприкінці build() народжує цілий, перевірений, незмінний HttpRequest](img/half-built-leak.svg)

*Сетери лишають об'єкт існувати напівзібраним — і його можна взяти саме в цю мить. Будівельник тримає незавершений стан у собі; готовий об'єкт з'являється вже цілим на build(), тож брати проміжний просто нема чого.*

Ось точне формулювання різниці, яке варто запам'ятати. Сетери роблять об'єкт **валідним за типом, але невалідним за станом** протягом усього складання — і покладаються на те, що ніхто не гляне в цей проміжок. Будівельник узагалі **не дає існувати** об'єктові-продукту, поки той не готовий: замість «є, але поки не чіпай» — «ще нема». Друге сильніше, бо не залежить від дисципліни того, хто читає код.

## Крок другий: staged-будівельник, що не компілюється без обов'язкового

Версія з перевіркою в `build()` вже добра, але одну помилку вона ловить лише **на запуску** — коли обов'язкове поле не задано. У нашому прикладі обов'язкове (`method`, `url`) ми сховали в конструктор, тож проблеми ніби нема. Але щойно обов'язкових полів стане більше, або якісь із них теж захочеться задавати кроком (наприклад, обов'язковий крок «яку автентифікацію»), — постає питання: чи можна зробити так, щоб **компілятор** не дав викликати `build()`, поки не пройдено обов'язкові кроки?

Можна. Прийом називають **staged builder** або **step builder** (укр. «поетапний» / «покроковий будівельник»). Ідею в широкий ужиток увів Джошуа Блох у книжці «Effective Java», де показав будівельник із плинним інтерфейсом і незмінним продуктом як ліки проти телескопічного конструктора; поетапний різновид — розвиток цієї лінії, коли за допомогою системи типів обов'язкові кроки роблять ще й **непропускними на етапі компіляції** *(добре задокументований прийом; в екосистемі Java його автоматизують кодогенератори на кшталт Jilt і RecordBuilder)*.

Суть трюку — **не давати будівельнику один тип на весь час складання**. Замість цього кожен обов'язковий крок повертає **інший тип-стадію**, і `build()` є **лише в останньої стадії**. Поки ти не пройшов усі обов'язкові кроки, у тебе на руках стадія, де методу `build()` просто **не існує** — не «є, але кине помилку», а нема в типі, тож редактор його навіть не підкаже, а компілятор — відхилить виклик.

Розкладемо на стадії наш запит. Хай обов'язкове задається кроками (щоб трюк було видно на кількох стадіях): спершу метод, тоді url, і аж тоді — необов'язкові й `build()`.

```
стадія 1  ──method()──►  стадія 2  ──url()──►  стадія 3 (необов'язкові + build)
   │                        │                        │
 є лише                   є лише                є header/body/…/build()
 method()                  url()                (можна крутитися тут скільки треба)
```

Кожна стадія — це **окремий інтерфейс** з рівно тими методами, які на цій стадії дозволені. Метод обов'язкового кроку повертає інтерфейс **наступної** стадії. Один клас-будівельник реалізує всі ці інтерфейси, але код-клієнт бачить його **тільки через інтерфейс поточної стадії** — і тому не має доступу до `build()`, доки не дійде до стадії, де той оголошений.

```ts
type Method = "GET" | "POST" | "PUT" | "DELETE";

// ── Стадії як ОКРЕМІ інтерфейси. У кожній — лише дозволене тут. ──
interface NeedMethod {
  method(m: Method): NeedUrl;          // єдине, що можна зробити першим — задати метод
}
interface NeedUrl {
  url(u: string): Ready;               // єдине, що можна другим — задати url
}
interface Ready {
  header(name: string, value: string): Ready;   // необов'язкові — вертають ТУ Ж стадію
  body(text: string): Ready;
  timeout(ms: number): Ready;
  build(): HttpRequest;                // ← build() існує ЛИШЕ тут, у фінальній стадії
}

// ── Один клас реалізує всі стадії; кожен обов'язковий крок «підіймає» стадію. ──
class HttpRequestSteps implements NeedMethod, NeedUrl, Ready {
  private _method!: Method;
  private _url!: string;
  private _headers = new Map<string, string>();
  private _body: string | null = null;
  private _timeoutMs = 30_000;

  method(m: Method): NeedUrl {         // повертаємо СЕБЕ, але під типом наступної стадії
    this._method = m;
    return this;                       // рантайм — той самий об'єкт; ТИП звузив дозволене
  }
  url(u: string): Ready {
    this._url = u;
    return this;
  }
  header(name: string, value: string): Ready { this._headers.set(name, value); return this; }
  body(text: string): Ready { this._body = text; return this; }
  timeout(ms: number): Ready { this._timeoutMs = ms; return this; }

  build(): HttpRequest {
    // Обов'язкові тут ГАРАНТОВАНО задані — інакше ми б сюди не дісталися за типами.
    // Лишається перевірити те, що типами не виразиш: комбінації.
    if (this._body !== null && (this._method === "GET" || this._method === "DELETE")) {
      throw new Error(`HttpRequest: метод ${this._method} не несе тіла`);
    }
    // Складання й КОПІЯ мапи — так само, як у простому будівельнику вище
    // (тут для стислості показано об'єктом-продуктом; у реальному коді —
    //  той самий приватний вхід у створення HttpRequest).
    return HttpRequest.of({
      method: this._method,
      url: this._url,
      headers: new Map(this._headers),   // копія — продукт не ділить мапу зі стадіями
      body: this._body,
      timeoutMs: this._timeoutMs,
      retries: 0,
    });
  }
}

// Вхід у складання віддає ПЕРШУ стадію — і більш нічого звідти не досяжно.
function httpRequest(): NeedMethod {
  return new HttpRequestSteps();
}
```

А тепер — заради чого все це затівалося. Подивись, що каже компілятор на різні виклики:

```ts
// ✓ Проходить: метод → url → (необов'язкові) → build
const ok = httpRequest()
  .method("POST")
  .url("https://api.example.com/orders")
  .body('{"item":"кава"}')
  .build();

// ✗ НЕ КОМПІЛЮЄТЬСЯ: build() нема в стадії NeedUrl
const bad1 = httpRequest()
  .method("POST")
  .build();
//   ~~~~~ Property 'build' does not exist on type 'NeedUrl'.

// ✗ НЕ КОМПІЛЮЄТЬСЯ: header() нема в стартовій стадії NeedMethod —
//    не можна чіпати необов'язкове, поки не задав метод
const bad2 = httpRequest()
  .header("X", "1");
//   ~~~~~~ Property 'header' does not exist on type 'NeedMethod'.

// ✗ НЕ КОМПІЛЮЄТЬСЯ: url() очікує рядок, а не число — звичайна перевірка типу кроку
const bad3 = httpRequest()
  .method("GET")
  .url(123);
//       ~~~ Argument of type 'number' is not assignable to parameter of type 'string'.
```

Зупинися на `bad1` — це і є вся суть. `httpRequest().method("POST")` за типом повертає `NeedUrl`. У `NeedUrl` **нема** методу `build()` — там є лише `url()`. Тому `.build()` після `.method("POST")` — не «помилка, яка спрацює на запуску», а **код, що не збереться взагалі**. Помилку «забув задати url» перенесено з рантайму в компіляцію: неможливий стан став **невиразним у типах**. Те саме з `bad2`: у стартовій стадії `NeedMethod` є тільки `method()`, тож дотягтися до `header()` до задання методу неможливо — порядок обов'язкових кроків зашито в тип.

![Ланцюг із трьох стадій-типів. Стадія NeedMethod: у рамці лише метод method(), стрілка method() веде до наступної рамки. Стадія NeedUrl: лише url(), стрілка url() веде далі; збоку перекреслений червоним напис build() з поміткою «нема в цьому типі». Стадія Ready: header, body, timeout і build() — усі присутні, є петля назад у себе для необов'язкових. Внизу підпис, що build() досяжний лише з фінальної стадії](img/staged-builder-types.svg)

*Кожна стадія — окремий тип рівно з дозволеними методами. Обов'язковий крок повертає тип наступної стадії; build() оголошений лише у фінальній. Тому виклик build() до проходження обов'язкових кроків не існує як код — компілятор відхиляє його, а не програма падає на запуску.*

Прийом спирається на дрібну, але важливу асиметрію. **У рантаймі** `method()`, `url()` і `header()` повертають **один і той самий об'єкт** (`return this`) — жодних нових будівельників не створюється, накладу нуль. Уся робота відбувається **в типах**: `this` щоразу віддають під **вужчим інтерфейсом**, який приховує ще недозволені методи. Компілятор дивиться на оголошений тип виразу й бачить лише те, що стадія обіцяє; що об'єкт «насправді» вміє більше — його не обходить. Ти платиш кількома інтерфейсами за те, що цілий клас помилок «забув обов'язкове / зробив кроки не в тому порядку» стає **неможливим написати**.

## Що staged-будівельник виражає типами, а що — ні

Межу треба провести чесно, бо трюк спокушає повірити, що тепер `build()` не може впасти взагалі. Не так.

Типами виражається **наявність і порядок обов'язкових кроків**: «спершу метод, тоді url, і лише тоді все інше». Це те, що зводиться до питання «чи викликано метод X» — а таке чудово кодується стадіями. Але **узгодженість значень** типами звичайного будівельника не виразиш: правило «`body` не поєднується з `GET`» залежить від того, які саме значення передали в `method()` і чи кликали `body()` взагалі, а це рішення часу виконання. Тому в `build()` staged-версії **все одно лишилася** перевірка комбінації — і має лишатися. Поділ такий: **що обов'язкове й у якому порядку — ловить компілятор; що узгоджене за значеннями — ловить `build()`**. Плутати ці дві гарантії — типова помилка; вони покривають різні класи багів і не заміняють одна одну.

І ціна. Staged-будівельник — це помітно більше коду: інтерфейс на кожну стадію, один клас, що реалізує їх усі, вручну проведені переходи між стадіями. Для запиту з двома обов'язковими полями це, чесно кажучи, забагато — простий будівельник із перевіркою в `build()` дав би майже ту саму безпеку куди дешевше. Staged окупається, коли обов'язкових кроків **кілька** і їх **легко переплутати чи забути**, а ціна помилки висока — публічний API бібліотеки, конфігурація платежу, збірка запиту, де пропущене поле коштує грошей. Саме тому в екосистемах, де це часто потрібно, його не пишуть руками, а **генерують** (у Java — анотаційні процесори Jilt чи RecordBuilder за анотацією над записом). Ручний staged-будівельник виправданий там, де стадій небагато, а гарантія «не зберешся без обов'язкового» справді варта свого коду.

> 🔧 **Навіщо це.** Різниця між «падає на запуску» і «не компілюється» — це різниця між помилкою, яку зловить (якщо пощастить) тест чи користувач, і помилкою, яку **неможливо закомітити**. Для внутрішнього коду, який ти сам і викликаєш, перше часто прийнятне. Для публічного API, де твій будівельник викликають тисячі незнайомих тобі програмістів, кожна гарантія, перенесена в компілятор, — це клас звернень у підтримку, яких не буде взагалі. Staged-будівельник — інструмент саме для цього краю: коли вартість чужої помилки виправдовує твій зайвий код.

## Пастки й межі: коротко про те, на чому спотикаються

**Мапа заголовків, поділена між будівельником і продуктом.** Головна прихована помилка простого будівельника — покласти в продукт **ту саму** колекцію, що й у будівельнику, а не копію. Тоді `readonly`/`frozen` на полі бреше: саме поле не переприсвоїш, але його вміст живий, і будівельник, який ще на руках, може міняти вже «незмінний» продукт крізь спільне посилання. Завжди копіюй змінні колекції на вході в продукт (`new Map(...)`, `dict(...)`), а віддавай їх під read-only типом (`ReadonlyMap`, `MappingProxyType`).

**Повторне використання будівельника після `build()`.** Заманливо покликати `build()` двічі з одного будівельника, трохи змінивши поле між викликами. Це працює, але породжує тонкий ризик: якщо `build()` десь **не** скопіював колекцію, два «різні» продукти поділять один список. Найбезпечніше правило — вважати будівельник **одноразовим**: один будівельник → один `build()`. Треба схожий запит — почни новий будівельник; хочеш «змінену копію готового продукту» — це вже інша операція (метод на кшталт `withTimeout`, що повертає **новий** незмінний об'єкт), і будівельник тут ні до чого.

**`return this` проти нового об'єкта в кроці.** У наших прикладах кроки міняють поле й повертають той самий будівельник — це стандартно й дешево. Існує й строго-незмінний варіант будівельника, де кожен крок повертає **новий** будівельник з оновленим полем; він потрібен, коли будівельник хочуть безпечно ділити між нитками або галузити (взяти напівготовий будівельник і добудувати двома різними способами). Ціна — алокація на кожен крок. Для типового складання одного об'єкта в одній нитці це надмір; знай, що варіант є, але не тягни його без потреби у ділянні чи галуженні будівельника.

**Порядок необов'язкових кроків у staged-версії.** Спокуса розписати стадіями **все**, включно з необов'язковим, і отримати «ідеальний» лінійний ланцюг. Не роби цього: необов'язкові кроки на те й необов'язкові, що їх задають у будь-якому порядку й будь-яку підмножину. Тому фінальна стадія `Ready` повертає **саму себе** з `header()`/`body()`/`timeout()` — щоб по ній можна було крутитися вільно. Стадіями кодуй **лише обов'язкове та його порядок**; необов'язкове лиши плоским у фінальній стадії. Інакше отримаєш комбінаторний вибух інтерфейсів на кожну перестановку опцій — і ненависний собі API.

Підсумок механіки одним рядком: **кроки копчять рішення й вертають будівельник; `build()` — єдиний вхід у створення, єдина перевірка й точка народження незмінного продукту; напівзібраного стану нема чим узяти, бо продукт з'являється вже цілим; а якщо обов'язкове хочеться зробити непропускним ще до запуску — стадії-типи ховають `build()`, поки обов'язкові кроки не пройдено.**
