# ⚙️ Абстрактна фабрика: дві реалізації на шарі доступу до даних

Абстрактну фабрику найчастіше показують на кнопках і темах інтерфейсу, і на цьому прикладі легко пропустити головне: що конкретні фабрики можна побудувати **двома цілком різними способами**, і вибір між ними — не косметика, а рішення про те, де саме ловитимуться помилки. GoF описали обидва способи, але другий у підручниках майже завжди ховають в один абзац. Тут ми зберемо обидва до робочого коду на одній наскрізній задачі й подивимося, де кожен протікає.

Задача — **шар доступу до даних** (англ. *data access layer*), той тонкий прошарок, крізь який застосунок говорить із базою. Для кожної СУБД (системи управління базами даних) нам потрібні три речі, що ходять разом: **з'єднання** (`Connection` — жива сесія з сервером), **команда** (`Command` — підготовлений запит із параметрами) і **транзакція** (`Transaction` — межа атомарності, усередині якої команди або застосуються всі, або жодна). Postgres, MySQL, SQLite — кожна дає свою трійку.

І тут з'являється умова, заради якої взагалі потрібна абстрактна фабрика, а не три окремі фабричні методи. Ця трійка мусить бути **з однієї СУБД**. Команда несе діалект SQL і говорить дротовим протоколом свого драйвера; транзакція керує сесією конкретного з'єднання. Підсунь Postgres-команду в MySQL-з'єднання — і ти не отримаєш чесної помилки «несумісні типи»: ти отримаєш зіпсований байтовий потік, який на тому кінці розтлумачиться як щось інше. Тобто «одна родина» — це не питання смаку, а **умова коректності**. Такі умови коректності, що мусять триматися завжди, звуть [інваріантами](book:programming/invariants) — і вся суть абстрактної фабрики в тому, щоб зробити цей інваріант неможливим порушити випадково.

## Реалізація 1: клас на кожну родину (класичний GoF)

Спершу — спосіб, який мають на увазі за замовчуванням. Оголошуємо **інтерфейс фабрики** з методом на кожен вид продукту, а тоді пишемо **окремий клас-фабрику на кожну СУБД**, який реалізує всі методи в одному стилі — своєму драйвері.

Спочатку самі продукти — лише інтерфейси, бо клієнт має бачити тільки їх:

:::tabs
```ts
interface Connection {
  run(cmd: Command): Promise<Rows>;
  close(): Promise<void>;
}
interface Command {
  readonly sql: string;
  bind(...params: unknown[]): this;
}
interface Transaction {
  commit(): Promise<void>;
  rollback(): Promise<void>;
}
```
```py
from typing import Protocol, Any

class Command(Protocol):
    sql: str
    def bind(self, *params: Any) -> "Command": ...

class Connection(Protocol):
    async def run(self, cmd: Command) -> "Rows": ...
    async def close(self) -> None: ...

class Transaction(Protocol):
    async def commit(self) -> None: ...
    async def rollback(self) -> None: ...
```
:::

Тепер фабрика — метод на кожен продукт — і по конкретному класу на кожну родину:

:::tabs
```ts
interface DbFactory {                       // абстрактна фабрика: метод на КОЖЕН вид
  createConnection(): Connection;
  createCommand(): Command;
  createTransaction(): Transaction;
}

class PostgresFactory implements DbFactory {   // уся трійка — Postgres
  createConnection(): Connection   { return new PgConnection(this.cfg); }
  createCommand():    Command      { return new PgCommand(); }
  createTransaction(): Transaction { return new PgTransaction(); }
  constructor(private cfg: PgConfig) {}
}
class MySqlFactory implements DbFactory {      // уся трійка — MySQL
  createConnection(): Connection   { return new MyConnection(this.cfg); }
  createCommand():    Command      { return new MyCommand(); }
  createTransaction(): Transaction { return new MyTransaction(); }
  constructor(private cfg: MyConfig) {}
}

// клієнт бачить лише DbFactory й тримає ОДНУ фабрику — уся трійка з однієї СУБД
async function loadUser(db: DbFactory, id: number): Promise<User> {
  const conn = db.createConnection();
  const cmd  = db.createCommand().bind(id);   // цей cmd — тієї ж СУБД, що й conn
  const rows = await conn.run(cmd);
  return toUser(rows);
}
```
```py
from abc import ABC, abstractmethod

class DbFactory(ABC):                        # абстрактна фабрика: метод на КОЖЕН вид
    @abstractmethod
    def create_connection(self) -> Connection: ...
    @abstractmethod
    def create_command(self) -> Command: ...
    @abstractmethod
    def create_transaction(self) -> Transaction: ...

class PostgresFactory(DbFactory):            # уся трійка — Postgres
    def __init__(self, cfg: "PgConfig"): self.cfg = cfg
    def create_connection(self) -> Connection:  return PgConnection(self.cfg)
    def create_command(self) -> Command:        return PgCommand()
    def create_transaction(self) -> Transaction: return PgTransaction()

class MySqlFactory(DbFactory):               # уся трійка — MySQL
    def __init__(self, cfg: "MyConfig"): self.cfg = cfg
    def create_connection(self) -> Connection:  return MyConnection(self.cfg)
    def create_command(self) -> Command:        return MyCommand()
    def create_transaction(self) -> Transaction: return MyTransaction()

# клієнт бачить лише DbFactory й тримає ОДНУ фабрику — уся трійка з однієї СУБД
async def load_user(db: DbFactory, id: int) -> "User":
    conn = db.create_connection()
    cmd  = db.create_command().bind(id)       # цей cmd — тієї ж СУБД, що й conn
    rows = await conn.run(cmd)
    return to_user(rows)
```
:::

Придивись, де тут живе інваріант родини. Клієнт `loadUser` тримає **одну** фабрику типу `DbFactory` і будує з неї всю трійку. Він фізично не може взяти з'єднання з `PostgresFactory`, а команду з `MySqlFactory` — у нього на руках лише один об'єкт `db`, і кожен його метод повертає продукт того самого драйвера, бо всередині конкретної фабрики всі `new` прибиті до одного драйвера цвяхом. Щоб змішати родини, довелося б свідомо тримати дві фабрики й перехрещувати їхні виходи — а це вже помітний код, а не тиха друкарська помилка. **Узгодженість гарантована структурою: одна фабрика — одна родина.**

Ціна цього способу видно одразу з форми. Родин `N`, видів продукту `M` — виходить `N` класів, у кожному по `M` методів. Додати нову СУБД дешево: новий клас `SqliteFactory`, старі недоторкані — це чистий [принцип відкритості-закритості](book:programming/open-closed), розширення без хірургії в наявному коді. Але додати новий **вид** продукту — скажімо, `BulkLoader` для масового вставлення — боляче: нова сигнатура з'являється в інтерфейсі `DbFactory`, і тепер **кожна** фабрика мусить її реалізувати. До цієї ціни ми ще повернемось; поки зауваж, що біль тут «дорога вісь» — новий стовпець, а не новий рядок.

> 🔧 **Навіщо це.** Фабрику зазвичай тримають [в одному примірнику](book:programming/singleton) на застосунок — один `PostgresFactory`, зібраний при старті з конфігурації, і переданий усюди, де потрібне створення. Тоді переключити всю систему з Postgres на SQLite (наприклад, для тестів чи локальної розробки) — це **одне місце**: підставити іншу фабрику в точці збірки. Весь інший код, що приймає `DbFactory`, не змінюється ні на рядок, бо він ніколи не називав жодного конкретного класу.

## Реалізація 2: один клас плюс реєстр прототипів

А тепер друга реалізація GoF, яку майже ніколи не показують кодом. Її мотив простий: якщо родин **багато** або вони з'являються динамічно (драйвери-плагіни, конфіговані з'єднувачі), то писати окремий клас-фабрику на кожну — марнотратство. `N` майже однакових класів, що відрізняються лише тим, який `new` кличуть, — це `N` разів переписаний той самий каркас.

GoF пропонують згорнути ці `N` класів в **один**, а відмінність родин винести в **дані**. Спосіб — патерн **Прототип** (гр. *prōtótypon* — первовзір, первісний зразок): новий об'єкт народжується не через `new ConcreteClass()`, а через **клонування наявного взірця**. Тоді одна конфігурована фабрика тримає по одному взірцю кожного виду продукту й на запит просто клонує потрібний. Мовою самих GoF: «конкретна фабрика ініціалізується прототипним примірником кожного продукту родини й створює новий продукт клонуванням свого прототипу… цей підхід усуває потребу в новому класі-фабриці для кожної нової родини продуктів» (*Design Patterns*, розділ Abstract Factory, розділ Implementation; *усталене джерело*).

:::tabs
```ts
interface Prototype { clone(): Prototype; }   // усе, що вміє себе клонувати

// один клас на ВСІ родини: відмінність — у переданому реєстрі взірців
class PrototypeFactory {
  constructor(private registry: Map<string, Prototype>) {}

  private create(kind: string): Prototype {
    const proto = this.registry.get(kind);
    if (!proto) throw new Error(`Немає прототипа для '${kind}'`);
    return proto.clone();                     // народження = клон взірця
  }
  createConnection()  { return this.create("connection")  as Connection; }
  createCommand()     { return this.create("command")     as Command; }
  createTransaction() { return this.create("transaction") as Transaction; }
}

// «Postgres-фабрика» — це той самий клас, лише інший НАБІР даних
const postgres = new PrototypeFactory(new Map<string, Prototype>([
  ["connection",  new PgConnection(pgCfg)],
  ["command",     new PgCommand()],
  ["transaction", new PgTransaction()],
]));
// «MySQL-фабрика» — той самий клас, підмінили дані
const mysql = new PrototypeFactory(new Map<string, Prototype>([
  ["connection",  new MyConnection(myCfg)],
  ["command",     new MyCommand()],
  ["transaction", new MyTransaction()],
]));
```
```py
from typing import Protocol

class Prototype(Protocol):
    def clone(self) -> "Prototype": ...

# один клас на ВСІ родини: відмінність — у переданому реєстрі взірців
class PrototypeFactory:
    def __init__(self, registry: dict[str, Prototype]):
        self._registry = registry

    def _create(self, kind: str) -> Prototype:
        proto = self._registry.get(kind)
        if proto is None:
            raise KeyError(f"Немає прототипа для '{kind}'")
        return proto.clone()                  # народження = клон взірця

    def create_connection(self):  return self._create("connection")
    def create_command(self):     return self._create("command")
    def create_transaction(self): return self._create("transaction")

# «Postgres-фабрика» — той самий клас, лише інший НАБІР даних
postgres = PrototypeFactory({
    "connection":  PgConnection(pg_cfg),
    "command":     PgCommand(),
    "transaction": PgTransaction(),
})
# «MySQL-фабрика» — той самий клас, підмінили дані
mysql = PrototypeFactory({
    "connection":  MyConnection(my_cfg),
    "command":     MyCommand(),
    "transaction": MyTransaction(),
})
```
:::

Ось у чому суть повороту. У першій реалізації «яка це родина» закодовано **типом класу** — є клас `PostgresFactory`, і сам факт, що ти тримаєш його примірник, означає Postgres. У другій «яка це родина» стало **вмістом реєстру** — набором взірців, який ти передав у конструктор. `PrototypeFactory` не знає й знати не хоче, що вона «постгресова»; вона знає лише «клонуй те, що лежить під цим ключем». `N` класів згорнулися в один клас плюс `N` наборів даних.

![Ліворуч класична реалізація: інтерфейс DbFactory з трьома creates, і під ним окремі класи PostgresFactory та MySqlFactory, кожен реалізує всі три методи своїми new — на кожну СУБД свій клас. Праворуч прототипна: один клас PrototypeFactory, що клонує з реєстру, і два змінні набори даних під ним — реєстр Postgres і реєстр MySQL, — які підміняють, лишаючи клас тим самим](/book/programming/design-patterns/factory-method/img/two-impls.svg)

*Та сама абстрактна фабрика, дві реалізації. Ліворуч родину задає ТИП (окремий клас на кожну СУБД, метод на кожен вид). Праворуч родину задають ДАНІ: один клас клонує взірці з реєстру, а зміна СУБД — це підміна набору взірців, не новий клас.*

## Семантика клонування: поверхнева проти глибокої

Уся друга реалізація тримається на слові `clone()` — і саме тут ховається її найпідступніша пастка. Клонувати об'єкт можна на різну **глибину**, і невірна глибина дає помилку, яку майже неможливо знайти очима.

Розберімо на команді, бо в неї є вкладений стан — список параметрів. **Поверхнева копія** (англ. *shallow*) копіює сам об'єкт, але вкладені посилання лишає **спільними**: новий об'єкт указує на **той самий** масив параметрів, що й взірець. **Глибока копія** (англ. *deep*) рекурсивно копіює й вкладене — новий об'єкт дістає **власний** масив.

**Умова: клонуємо взірець команди двічі й додаємо параметр в одну копію.**

:::tabs
```ts
class SqlCommand {
  constructor(public sql: string, public params: unknown[]) {}
  cloneShallow(): SqlCommand {                   // params — ТА САМА ланка
    return new SqlCommand(this.sql, this.params);
  }
  cloneDeep(): SqlCommand {                       // params — власна копія
    return new SqlCommand(this.sql, [...this.params]);
  }
}

const proto = new SqlCommand("INSERT INTO users(name) VALUES (?)", []);

const a = proto.cloneShallow();
const b = proto.cloneShallow();
a.params.push("Ann");
console.log(b.params);      // ["Ann"]  ← b теж має Ann: масив СПІЛЬНИЙ
console.log(proto.params);  // ["Ann"]  ← і сам взірець забруднено

const clean = new SqlCommand("INSERT INTO users(name) VALUES (?)", []);
const c = clean.cloneDeep();
const d = clean.cloneDeep();
c.params.push("Bob");
console.log(d.params);      // []  ← незалежні, як і має бути
```
```py
import copy

class SqlCommand:
    def __init__(self, sql: str, params: list):
        self.sql = sql
        self.params = params

proto = SqlCommand("INSERT INTO users(name) VALUES (%s)", [])

a = copy.copy(proto)        # поверхнева: params — той самий список
b = copy.copy(proto)
a.params.append("Ann")
print(b.params)             # ['Ann']  ← спільний список
print(proto.params)         # ['Ann']  ← і сам взірець забруднено

clean = SqlCommand("INSERT INTO users(name) VALUES (%s)", [])
c = copy.deepcopy(clean)    # глибока: власний список
d = copy.deepcopy(clean)
c.params.append("Bob")
print(d.params)             # []  ← незалежні, як і має бути
```
:::

Помилка тут не гучна — код збирається, тести на одному запиті проходять, і лише під навантаженням, коли команди клонуються пачками, параметри одного запиту раптом просочуються в інший. У Python `copy.copy` — поверхневе за замовчуванням (розділяє вкладене), `copy.deepcopy` — рекурсивне; глибину налаштовують методами `__copy__`/`__deepcopy__`. У TypeScript готового клону немає взагалі — пишеш `clone()` руками; вбудований `structuredClone` копіює глибоко, але **втрачає клас** (повертає звичайний об'єкт без методів) і кидає виняток на тому, що скопіювати не можна.

![Ліворуч поверхневе клонування: взірець і клон, обидві стрілки params ведуть в ОДИН спільний червоний список — зміна в одному видно в іншому. Праворуч глибоке: взірець і клон, кожен зі СВОЄЮ стрілкою у власний зелений список — копії незалежні. Знизу висновок: прототип годиться, лише коли clone копіює на потрібну глибину; продукт-значення клонується, продукт із живим ресурсом як сокет — ні](/book/programming/design-patterns/factory-method/img/clone-depth.svg)

*Поверхнева копія лишає вкладене спільним — стан тече між клонами. Глибока дає кожному власне вкладене. Але глибока копія дорога, а живий ресурс (відкритий сокет, дескриптор файлу) взагалі не копіюється: тому взірцем добре робити продукт-значення (команду), а не з'єднання.*

І тут вилазить обмеження, що вирішує долю всієї другої реалізації для нашого шару даних. **Живе з'єднання не клонується.** `Connection` тримає відкритий сокет до сервера; глибоко скопіювати сокет — беззмістовно (не можна «роздвоїти» TCP-з'єднання), а поверхнево — означає, що всі «створені» з'єднання ділять один сокет, тобто це взагалі не окремі з'єднання. Прототип чудово лягає на продукти-**значення**, у яких стан — це просто дані (команда — це, по суті, шаблон SQL плюс параметри; конфіг; об'єкт, який можна оголосити [незмінним](book:programming/immutability), і тоді поверхневий клон безпечний, бо вкладене нікому міняти). Але на продукти-**ресурси** він не лягає. Тому в реальному шарі даних другу реалізацію майже завжди беруть **частково**: класом на родину роблять `Connection` (яке однак створюється, а не клонується), а прототипом-реєстром — команди.

## Де живе інваріант: типи проти рантайму

Тепер найважливіша відмінність двох реалізацій, заради якої й варто було зводити їх поруч. Питання одне: **де ловиться порушення інваріанта родини** — на компіляції чи в проді?

У першій реалізації інваріант тримають **типи разом зі структурою**. Щоб зібрати змішану трійку, тобі треба мати на руках дві різні фабрики й свідомо перехрестити їхні продукти. Через абстрактний `DbFactory` цього просто нема як зробити: один об'єкт віддає одну родину.

У другій реалізації інваріант тримає лише **дисципліна заповнення реєстру** — а це властивість **рантайму**. Поглянь, що компілятор пропускає без звуку:

:::tabs
```ts
// реєстр нібито Postgres, але хтось помилково поклав MySQL-команду
const registry = new Map<string, Prototype>([
  ["connection",  new PgConnection(pgCfg)],
  ["command",     new MyCommand()],      // ← чужа родина!
  ["transaction", new PgTransaction()],
]);
const db = new PrototypeFactory(registry);

const conn = db.createConnection();       // Postgres-з'єднання
const cmd  = db.createCommand();          // а це — MySQL-команда
await conn.run(cmd);                      // ЗБИРАЄТЬСЯ. Падає лише тут, у рантаймі
```
```py
# реєстр нібито Postgres, але хтось помилково поклав MySQL-команду
registry = {
    "connection":  PgConnection(pg_cfg),
    "command":     MyCommand(),          # ← чужа родина!
    "transaction": PgTransaction(),
}
db = PrototypeFactory(registry)

conn = db.create_connection()             # Postgres-з'єднання
cmd  = db.create_command()                # а це — MySQL-команда
await conn.run(cmd)                       # ЗБИРАЄТЬСЯ. Падає лише тут, у рантаймі
```
:::

`MyCommand` і `PgCommand` обидві реалізують `Command`, тому значення в реєстрі задовольняє тип — компілятор бачить лише «команда», і йому байдуже, з якого вона драйвера. Мапа за рядковим ключем розв'язала кожен елемент від решти, а разом з тим розв'язала й той зв'язок, що робив їх однією родиною. Порушення випливе тільки тоді, коли Postgres-з'єднання спробує виконати MySQL-команду й діалекти не зійдуться — в проді, під навантаженням, у стек-трейсі, за яким не одразу видно, що корінь — у неправильно зібраному реєстрі десь при старті.

Це рівно той компроміс, який GoF назвали «визначенням розширюваних фабрик»: параметризований підхід із єдиною операцією `create(kind)` — «гнучкіший, але **менш безпечний**» (*усталене джерело*), бо всі продукти повертаються під одним абстрактним типом і статична перевірка вже не бачить різниці між родинами. Гнучкість другої реалізації й небезпека другої реалізації — це одна й та сама властивість, побачена з двох боків: родину задають дані, а даним компілятор не вірить.

## Біль нового виду продукту — в обох, але по-різному

Лишилася третя вісь, яку ми відклали: що коштує додати **новий вид** продукту (не нову СУБД, а новий елемент у кожній родині — скажімо, `BulkLoader`). Обом реалізаціям це болить, але біль різної природи.

У першій — новий метод в інтерфейсі, і далі механічно:

```ts
interface DbFactory {
  createConnection(): Connection;
  createCommand(): Command;
  createTransaction(): Transaction;
  createBulkLoader(): BulkLoader;   // ← новий вид
}
// тепер PostgresFactory і MySqlFactory НЕ зберуться, поки кожна не додасть метод
```

Це саме те, про що писали GoF: «додавання нового виду продукту потребує зміни інтерфейсу AbstractFactory й усіх класів, що від нього залежать» (*усталене джерело*). Правок багато — по одній на кожну фабрику — але біль **гучний і безпечний**: компілятор перелічить тобі всі незавершені фабрики поіменно, і забути жодної не вийде, бо код без цього не збереться.

У другій — сигнатура `create(kind)` уже приймає рядок, тож **не змінюється зовсім**. Ти просто дореєстровуєш взірець:

```ts
registryPg.set("bulkLoader", new PgBulkLoader());
// а в registryMy додати забув — помилки збірки НЕ буде.
// factory.create("bulkLoader") впаде лише в рантаймі: "Немає прототипа для 'bulkLoader'"
```

Біль тут **тихий і небезпечний**: жодного червоного рядка на компіляції, зате пропущений взірець в одному з реєстрів вистрілить винятком тоді, коли цей шлях уперше виконають. Та сама розв'язаність, що згорнула `N` класів в один, тепер не дає компіляторові допомогти: він не знає, які ключі «мусять» бути в кожному реєстрі.

## Складність і пастки

Звівши обидві реалізації до коду, дістаємо просту карту вибору — не «яка краща», а «що ти готовий заплатити й де хочеш ловити помилки».

- **Клас на родину — коли родин мало й вони сталі, а продукти тримають ресурси.** Інваріант родини стає структурним: одна фабрика — одна СУБД, змішати нема як. Нова родина дешева (новий клас), новий вид продукту дорогий, але **безпечний** (компілятор жене, поки кожна фабрика не дописала метод). Це дефолт для шару даних, бо `Connection` усе одно не клонується.
- **Один клас плюс реєстр прототипів — коли родин багато, вони динамічні, а продукти клоновані-значення.** `N` класів згортаються в один плюс дані; родину можна вантажити з конфігу чи плагінів. Плата — інваріант родини переїжджає в **рантайм**: чужий взірець у реєстрі компілятор пропустить, а новий вид продукту додається тихо, і забутий взірець впаде лише при виконанні.
- **Клонування — окреме мінне поле.** Поверхнева копія розділяє вкладений стан і дає найпідступнішу з помилок — просочування стану між клонами. Глибока копія рятує, але дорога й **не бере живих ресурсів** (сокет, дескриптор). Тому взірцем роби продукт-значення, а не з'єднання; або роби продукт [незмінним](book:programming/immutability), і тоді поверхневий клон стає безпечним даром.
- **На практиці реалізації змішують.** Реальний драйвер бере класичну фабрику для з'єднання (яке народжується, не клонується) і прототип-реєстр для команд (яких багато, вони — значення, і їх зручно клонувати з наперед налаштованих шаблонів). «Дві реалізації» — це не розвилка «або-або», а дві техніки, які кладуть на різні продукти однієї й тієї ж родини.

За цією картою будь-яку абстрактну фабрику в чужому коді розкладаєш точно: чи родину тримає тип, а чи дані; чи `create` клонує, і якщо так — на яку глибину; і де саме, на компіляції чи в проді, спрацює запобіжник, коли хтось випадково змішає дві родини в одну.
