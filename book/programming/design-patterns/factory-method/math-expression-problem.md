# 🧮 Проблема виразності: чому одна вісь дарована, а друга оплачена

В абстрактній фабриці впадає в око дивна несиметрія. Додати цілу нову **родину** продуктів — скажімо, ще одну тему поруч зі світлою й темною — дешево: пишеш один новий клас, старого не чіпаєш. А додати новий **вид** продукту — до кнопки, поля й прапорця долучити повзунок — боляче: доводиться правити інтерфейс фабрики й **кожну** конкретну фабрику одразу. Легко списати це на невдалу форму патерна, на те, що GoF чогось недодумали. Але несиметрія не в патерні. Вона в самій задачі, має ім'я, доведення й сорокарічну історію, і абстрактна фабрика — лише один її бік.

Зветься ця вилка **проблемою виразності** (англ. *expression problem*). Розберімо її не як цікавинку з теорії мов, а від першопричини: звідки береться те, що одну вісь розширення завжди даровано, а другу оплачено; чому обійти це в лоб неможливо; і чим саме платять ті, хто таки обходить.

## Матриця типів і операцій

Почнімо з об'єкта, який ховається за будь-якою програмою, що чимось маніпулює. Візьми набір **видів даних** (типів, варіантів, випадків) і набір **операцій** над ними. Ці двоє утворюють таблицю: рядок — вид даних, стовпець — операція, а клітина на їх перетині — відповідь на питання «що робить ця операція з цим видом даних».

Найчистіший приклад — обчислювач арифметичних виразів. Види даних: `Число`, `Сума`, `Добуток`. Операції: `обчислити`, `надрукувати`, `спростити`. Виходить матриця 3×3 — дев'ять клітин, і кожну треба заповнити: як надрукувати суму, як спростити добуток, як обчислити число. **Уся поведінка системи — це заповнена матриця.** Нічого більшого в ній немає: дай відповідь у кожній клітині, і програма готова.

```
              обчислити   надрукувати   спростити
  Число         n            "n"           n
  Сума          a+b        "(a+b)"      0+x → x
  Добуток       a·b        "(a·b)"      1·x → x
```

Тепер — головне питання, довкола якого все крутиться. Матриця не застигла: у живій системі з'являються то нові рядки (новий вид даних), то нові стовпці (нова операція). І питання таке: **скільки вже написаного, вже «закритого» коду доведеться відкрити й переписати, щоб дописати рядок або стовпець?** Відповідь виявляється разюче несиметричною, і саме ця несиметрія — суть проблеми.

Формулювання дав британський інформатик **Філіп Вадлер** (Philip Wadler) — у листі до списку розсилки про узагальнення в Java, листопад 1998-го (лист публічний, факт усталений). Він і назвав це «проблемою виразності», одразу зауваживши: «нове ім'я для давньої проблеми». Ціль Вадлер поставив як чотири вимоги, що мусять справдитися **разом**: (1) додавати нові види даних і (2) нові операції над ними, (3) не переписуючи й не перекомпільовуючи наявний код, (4) не втрачаючи статичної типобезпеки — без приведень типів і перевірок у рантаймі. Саму ж вилку — що ці дві осі тягнуть у протилежні боки — за два десятиліття до назви побачили інші. Американець **Джон Рейнольдс** (John C. Reynolds) 1975-го розрізнив «типи, визначені користувачем» і «процедурні структури даних» як два **доповняльні** підходи до абстракції даних, кожен з яких дає те, чого бракує іншому. А **Вільям Кук** (William R. Cook) 1990-го у праці «Object-Oriented Programming Versus Abstract Data Types» показав, що об'єкти впорядковані навколо конструкторів даних, абстрактні типи даних — навколо операцій, і сильні місця одного підходу — це слабкі місця другого (обидва факти усталені).

## Дві одиниці коду, дві вартості

Ось першопричина всієї вилки, і вона напрочуд проста. Матриця одна, але **розкласти її на модулі коду** можна двома способами — по рядках або по стовпцях, — і мова змушує тебе вибрати один.

Об'єктний розклад (той, що в ООП): **одиниця коду — це клас, а клас — це рядок**. Один клас збирає в собі всі операції для одного виду даних. Матриця розрізана на горизонтальні смуги.

```ts
interface Shape {
  area(): number;
  perimeter(): number;          // набір операцій «зашитий» в інтерфейс — це стовпці
}
class Circle implements Shape {
  constructor(private r: number) {}
  area()      { return Math.PI * this.r ** 2; }
  perimeter() { return 2 * Math.PI * this.r; }
}
class Rect implements Shape {
  constructor(private w: number, private h: number) {}
  area()      { return this.w * this.h; }
  perimeter() { return 2 * (this.w + this.h); }
}
// + новий ТИП: один новий клас, старе не чіпаємо ───────────── дешево
class Triangle implements Shape { /* area(); perimeter(); */ }
// + нова ОПЕРАЦІЯ draw(): метод у інтерфейс і в КОЖЕН клас ──── дорого
```

Функційний розклад (той, що в ФП): **одиниця коду — це функція, а функція — це стовпець**. Одна функція збирає в собі всі види даних для однієї операції. Та сама матриця, але розрізана на вертикальні смуги.

```haskell
data Shape = Circle Double | Rect Double Double   -- набір типів «зашитий» у тип — це рядки

area :: Shape -> Double
area (Circle r) = pi * r * r
area (Rect w h) = w * h

perimeter :: Shape -> Double
perimeter (Circle r) = 2 * pi * r
perimeter (Rect w h) = 2 * (w + h)

-- + нова ОПЕРАЦІЯ: одна нова функція, старе не чіпаємо ──────── дешево
draw :: Shape -> String
draw (Circle _) = "○"
draw (Rect _ _) = "▭"
-- + новий ТИП Triangle: нова гілка в area, perimeter, draw ──── дорого
```

Придивись, як дзеркально стоять ці два шматки. У класовому розкладі клас `Circle` містить **увесь рядок** — усі операції над колом. Тому додати нове коло-подібне (новий рядок) легко: пишеш один клас, і він самодостатній. А додати нову операцію (стовпець) важко: її клітина є в кожному рядку, тобто метод треба вписати в кожен клас. У функційному розкладі — точно навпаки: функція `area` містить **увесь стовпець** — площу для всіх фігур, тому нова операція це одна нова функція, а новий вид даних змушує дописати гілку в кожну наявну функцію. Дві картини — точний **транспонований** образ одна одної: що для однієї дешево, для другої дорого, і навпаки.

Праворуч функційний розклад ФП: та сама матриця, але тепер зелена дешева вісь — стовпці-операції (одна нова функція), а червона дорога — рядки-типи, правка кожної функції. *Одна матриця, два розрізи. Об'єктний код — це рядки (класи), функційний — стовпці (функції). Зелена вісь у кожного розкладу — дарована (чисте додавання), червона — оплачена (правка всього наявного). Осі протилежні: це і є вилка.*

## Модель вартості розширення

Порахуймо ціну точно, бо саме число робить вилку неспростовною. Нехай у системі `n` видів даних (рядків) і `m` операцій (стовпців). Новий вид даних — це новий рядок, а рядок має `m` клітин (по одній на кожну наявну операцію). Нова операція — це новий стовпець із `n` клітин. Тобто **саму нову поведінку** — вміст клітин — доведеться написати в будь-якому разі: `m` клітин на новий тип, `n` на нову операцію. Ця робота незборима: ти мусиш сказати, що новий тип робить під кожною операцією, або що нова операція робить для кожного типу. Тут заощадити нема як.

Але проблема виразності не про це. Вона про інше число — **скільки вже написаних модулів доведеться відкрити й переписати**. І ось воно вже несиметричне:

```
                       відкрити наявних модулів    нових модулів
  ООП (модуль = рядок):
    + тип (рядок)                 0                     1        ← дешево: чисте додавання
    + операція (стовпець)         n                     0        ← дорого: правка ВСІХ класів
  ФП (модуль = стовпець):
    + операція (стовпець)         0                     1        ← дешево: чисте додавання
    + тип (рядок)                 m                     0        ← дорого: правка ВСІХ функцій
```

Прочитаймо це повільно. На **дешевій** осі всі нові клітини лягають в **один новий модуль**, а наявних не чіпаємо взагалі — нуль правок у закритому коді. На **дорогій** осі ті самі нові клітини розсипано по всіх наявних модулях — і кожен доводиться відкрити й дописати. Кількість написаного коду та сама (`n` чи `m` клітин), але **локалізація** протилежна: одне — акуратна прибудова збоку, друге — хірургія в живому тілі системи.

> 🔧 **Навіщо це.** Оце й є той самий [принцип відкритості-закритості](book:programming/open-closed) у вигляді числа. «Відкритий до розширення, закритий до зміни» означає рівно нуль у стовпці «відкрити наявних модулів»: приріст має бути новим кодом збоку, а не правкою старого. Проблема виразності каже жорстку річ: у звичайній мові ти можеш отримати цей нуль на **одній** осі — на тій, вздовж якої проходить твій розклад на модулі, — але друга вісь тоді неминуче коштує `Θ(n)` чи `Θ(m)` правок у закритому коді. Обрати парадигму — значить обрати, яка з двох осей розширення тобі дарована, а за яку ти платитимеш щоразу.

## Абстрактна фабрика — це ООП-ріг вилки

Тепер накладімо це просто на абстрактну фабрику — і побачимо, що вона сідає на один ріг вилки з математичною точністю.

Візьми ту саму `UiFactory` з методами `createButton`, `createCheckbox`, `createInput`. Зістав із матрицею:

- **Види продукту** (кнопка, прапорець, поле) — це **операції фабрики**, тобто **стовпці**. Їх набір заморожений в інтерфейсі: скільки методів оголошено, стільки й є.
- **Родини** (темна, світла) — це **конкретні фабрики**, кожна реалізує весь інтерфейс. Родина — це **рядок**.
- Клітина `(родина, вид)` — це конкретний клас продукту, який ця фабрика віддає: `DarkButton`, `LightInput`.

І тепер вартість читається одразу з таблиці вище. Додати родину — це додати рядок: пишеш один новий клас, що реалізує всі методи, старих фабрик не чіпаєш — нуль правок у закритому коді, **дарована ось**. Додати вид продукту — це додати стовпець: нова сигнатура `createSlider()` з'являється в інтерфейсі, а отже, її треба дописати в **кожну** конкретну фабрику — `n` правок, **оплачена ось**.

Це точно лягає на спостереження Вадлера: об'єктна мова робить дешевими рядки (нові підкласи-родини) і дорогими стовпці (нові методи-види). **Абстрактна фабрика не має цієї несиметрії як вади — вона Є цією несиметрією, вбудованою в патерн.** Ось чому її беруть саме тоді, коли осі варіативності — це родини (тем багато, а видів елементів усталений набір: теми оформлення, драйвери СУБД, кросплатформні тулкіти): у цих задачах ти купуєш на дарованій осі й майже ніколи не платиш на оплаченій. А біль від додавання нового виду продукту крізь усі фабрики — це не помилка проєктування, яку можна «полагодити»; це рахунок, який ООП-ріг проблеми виразності виставляє за свою дешеву вісь.

## Дуальність, яку побачив Рейнольдс

Чому взагалі вилка така жорстка — чому не можна просто «зробити обидві осі дешевими» у звичайній мові? Тут ми впираємося в дуальність, яку Рейнольдс і Кук описали глибше за метафору таблиці.

Є два способи заховати представлення даних. Перший — **абстракція типу** (абстрактний тип даних): є одне приховане внутрішнє представлення, а операції — це зовнішні функції, кожна з яких знає цей єдиний внутрішній вигляд і працює з ним. Другий — **абстракція процедурна** (об'єкти): кожен об'єкт **носить свою поведінку в собі**, а «тип» зводиться до «відповідає на цей набір повідомлень», байдуже, як влаштований усередині. Це та сама межа між тим, що тип обіцяє назовні, і тим, як він це робить, — [різниця між інтерфейсом і реалізацією](book:programming/interface-vs-implementation), доведена до питання «хто володіє клітиною матриці».

І от чому осі протилежні. Коли операція — це зовнішня функція, що знає одне представлення (ADT-бік), додати операцію легко (ще одна функція збоку), а додати представлення важко (кожна функція припускала старий вигляд). Коли ж поведінка живе всередині об'єкта (об'єктний бік), додати вид даних легко (ще один клас зі своєю поведінкою), а додати операцію важко (її треба вкласти в кожен клас). **Проблема виразності — це та сама дуальність Рейнольдса, лише перевдягнена в рядки й стовпці.** Вадлерова таблиця — зручний спосіб побачити оком те, що Рейнольдс сформулював як доповняльність двох абстракцій ще 1975-го.

## Як розчепити вилку

Раз вилка неспростовна у звичайній мові, цікаве питання — чим за її обхід платять. Є чотири відомі ходи, і кожен бере свою ціну.

**Відвідувач (Visitor).** Найперша спокуса — прийом всередині самої ООП: винести операцію в окремий об'єкт-відвідувача, що вміє обійти всі види даних. Але придивись, що це насправді робить. Відвідувач — це **стовпець, зроблений об'єктом**: тепер додати операцію дешево (новий відвідувач збоку), зате додати вид даних дорого (кожен відвідувач мусить дописати метод на нього). Тобто відвідувач **не розчіплює вилку — він повертає об'єкт на 90°**, міняючи дешеву вісь ООП на дешеву вісь ФП. Це корисно рівно тоді, коли операції плодяться частіше за типи; але заплатиш ти протилежним боком.

**Мультиметоди (множинна диспетчеризація).** Тут диспетчеризація не належить **ні класу, ні функції**: метод оголошено збоку від обох, а мова добирає його за типами **всіх** аргументів у рантаймі (так у CLOS, Clojure, Julia).

```julia
abstract type Shape end
struct Circle <: Shape; r::Float64 end
struct Rect   <: Shape; w::Float64; h::Float64 end

area(c::Circle) = π * c.r^2          # клітина живе ПОЗА і типом, і операцією
area(r::Rect)   = r.w * r.h
# + новий ТИП: struct Triangle і його area(...)  — старе ціле (рядок задарма)
# + нова ОПЕРАЦІЯ: perimeter(::Circle), perimeter(::Rect) — старе ціле (стовпець задарма)
```

Обидві осі раптом дешеві: і новий тип, і нова операція — це вільні визначення збоку. Ціна — **втрата статичної повноти**: компілятор більше не гарантує, що кожну клітину заповнено. Пропустив пару `(тип, операція)` — і замість помилки складання дістанеш зрив у рантаймі «немає застосовного методу». Вадлерову вимогу (4) — статичну типобезпеку — тут принесено в жертву заради обох осей.

**Класи типів.** Хід із Haskell: **набір операцій** (клас типів) відв'язують від **самих даних** (екземпляри). Новий тип — це новий екземпляр наявного класу (рядок задарма); новий пучок операцій — це новий клас із екземплярами (стовпець задарма) — і все зі статичною перевіркою.

```haskell
class Shape a where
  area      :: a -> Double
  perimeter :: a -> Double

data Circle = Circle Double
instance Shape Circle where
  area      (Circle r) = pi * r * r
  perimeter (Circle r) = 2 * pi * r
-- + новий ТИП: data Triangle + instance Shape Triangle — старе ціле
class Drawable a where draw :: a -> String   -- + нова операція: новий клас — старе ціле
```

Прикметно, що класи типів придумав **той самий Вадлер** (із Стівеном Блоттом, 1989) — за дев'ять років до того, як назвав вилку, він уже виклав один зі способів її розчепити (усталений факт). Ціна тут делікатніша: заповнити `n·m` клітин однаково доведеться (екземпляр на кожну пару), а глобальна узгодженість екземплярів накладає свої обмеження — але обидві осі справді відкриті, і статику збережено.

**Tagless-final та об'єктні алгебри.** І ось найкрасивіший поворот, що замикає коло назад до фабрики. Ідея: подати **конструктори** типу даних як методи **узагальненого інтерфейсу, параметризованого носієм** `A`. Операція стає реалізацією цього інтерфейсу під конкретний `A`; новий варіант — під-інтерфейсом з іще одним методом.

:::tabs
```ts
// об'єктна алгебра: інтерфейс конструкторів, у якого тип продукту — параметр A
interface ExpAlg<A> {
  lit(n: number): A;
  add(a: A, b: A): A;
}
// операція = реалізація під носій A;  + операція — новий клас (СТОВПЕЦЬ задарма)
class Eval implements ExpAlg<number> {
  lit(n: number)            { return n; }
  add(a: number, b: number) { return a + b; }
}
class Print implements ExpAlg<string> {
  lit(n: number)            { return String(n); }
  add(a: string, b: string) { return `(${a}+${b})`; }
}
// + новий ВАРІАНТ mul = під-інтерфейс, старе ціле (РЯДОК задарма)
interface MulAlg<A> extends ExpAlg<A> { mul(a: A, b: A): A; }
```
```haskell
-- те саме як клас типів (tagless-final): конструктори — методи класу
class ExpAlg a where
  lit :: Int -> a
  add :: a -> a -> a

newtype Eval = Eval Int                 -- носій обчислення
instance ExpAlg Eval where
  lit n                 = Eval n
  add (Eval a) (Eval b) = Eval (a + b)
-- + операція (напр. Print) — новий instance, старе ціле (СТОВПЕЦЬ задарма)

class ExpAlg a => MulAlg a where        -- + варіант mul — клас-розширення
  mul :: a -> a -> a                    --   старе ціле (РЯДОК задарма)
```
:::

Обидві осі тут додаються чистим приростом — і зі статичною типобезпекою: новий носій `A` дає операцію, під-інтерфейс дає варіант, наявного не чіпаємо. А тепер придивися, **чим є цей `ExpAlg<A>`**. Це інтерфейс із одним методом на кожен конструктор — тобто **абстрактна фабрика**, у якої тип продукту не зафіксовано наперед, а винесено в параметр `A`. Саме так це й описали Олівейра й Кук (2012): об'єктна алгебра — це «абстрактна фабрика для конструкторів, чий тип результату ще не відомий і залежить від інтерпретатора» (усталений факт). Вихід із дилеми фабрики виявляється **знову фабрикою** — тією самою, лиш узагальненою одним типовим параметром. Ріг, до якого патерн прибивав тебе, розчіплюється не відмовою від фабрики, а її дорощенням.

Відвідувач лише возить між цими двома рогами. Справжній вихід — правий-верхній кут: мультиметоди, класи типів, tagless-final / object algebras відчиняють обидві осі, кожен за свою ціну.*

## Коли знаєш ім'я вилки

Практична вага всього цього — ось у чому. Коли ти тягнешся до абстрактної фабрики, ти **свідомо обираєш ООП-ріг** проблеми виразності: береш дешеві родини ціною дорогих видів продукту. Це правильна покупка там, де родин багато й вони змінюються, а набір видів усталений, — теми, драйвери баз, віконні тулкіти. І коли одного дня додавання ще одного виду продукту крізь усі фабрики починає боліти, ти вже не сплутаєш цей біль із власною помилкою: це рахунок за дешеву вісь, закон, а не недбалість.

А знаючи, що вилка має другий бік і чотири відомі виходи, ти бачиш і куди рухатися, коли ціна стала завеликою. Хочеш дешевих **операцій** замість дешевих типів — розверни об'єкт відвідувачем. Хочеш **обидві** осі й ладен заплатити статичною повнотою — візьми мультиметоди; ладен тримати статику — класи типів або об'єктні алгебри. Найважливіше вже зроблено в ту мить, коли ти назвав вилку: те, що має ім'я, доведення й карту виходів, перестає бути таємничою незручністю патерна й стає інженерним вибором з відомою ціною по кожному напрямку.
