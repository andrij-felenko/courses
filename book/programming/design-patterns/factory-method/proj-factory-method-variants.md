# ⚙️ Три обличчя фабричного методу — робочий розбір

«Фабричний метод» — назва, під якою насправді ховаються три різні прийоми. Їх плутають, бо всі троє прибирають `new` з очей клієнта. Але керує вибором конкретного класу в кожному щось своє: у першому — **тип нащадка**, у другому — **виклик за іменем**, у третьому — **значення вхідних даних**. Переплутати їх — це взяти важкий поліморфний каркас там, де вистачило б однорядкового методу, або накрутити гілки `switch`, які мали б бути таблицею.

Візьмімо конкретну наскрізну область — **розбір користувацьких профілів із зовнішнього джерела**. Дані приходять у різних форматах (JSON з API, CSV з експорту, XML зі старої системи), а всередині ми хочемо один тип `Profile` і одну логіку. На цій задачі три різновиди фабрики самі проступлять один за одним, і на кожному стане видно його межу — де він працює, а де ламається.

## Різновид 1: класичний GoF — нащадок обирає продукт

Почнімо з того, що в книзі «банди чотирьох» і зветься фабричним методом строго. Це **метод у базовому класі, залишений порожнім (абстрактним), який нащадок перевизначає, щоб обрати конкретний продукт**. Керує вибором тут не значення й не параметр, а **тип підкласу**, який опинився на руках у рантаймі.

Задача, де це лягає точно: у нас є **каркас імпорту**, який веде однаковий процес — прочитати сирі байти, розібрати їх у профіль, перевірити обов'язкові поля, залогувати результат. Спільне все, крім однієї ланки: **як саме сирі байти перетворити на профіль**. Це залежить від формату, і саме цю ланку каркас лишає дірою.

:::tabs
```ts
abstract class ProfileImporter {
  // фабричний метод: каркас НЕ знає конкретного парсера, лишає діру
  protected abstract createParser(): ProfileParser;

  // спільний процес — той самий для всіх форматів
  import(raw: string): Profile {
    const parser = this.createParser();   // ...кличе діру...
    const profile = parser.parse(raw);
    this.assertRequiredFields(profile);
    this.log(`Імпортовано ${profile.email}`);
    return profile;
  }

  private assertRequiredFields(p: Profile): void {
    if (!p.email) throw new Error("Профіль без email");
  }
  private log(msg: string): void { /* ... */ }
}

class JsonProfileImporter extends ProfileImporter {
  protected createParser(): ProfileParser {   // нащадок ОБИРАЄ клас
    return new JsonProfileParser();
  }
}
class CsvProfileImporter extends ProfileImporter {
  protected createParser(): ProfileParser {
    return new CsvProfileParser();
  }
}
```
```py
from abc import ABC, abstractmethod

class ProfileImporter(ABC):
    @abstractmethod
    def _create_parser(self) -> "ProfileParser":   # діра для нащадка
        ...

    # спільний процес — той самий для всіх форматів
    def import_(self, raw: str) -> "Profile":
        parser = self._create_parser()             # ...кличе діру...
        profile = parser.parse(raw)
        self._assert_required_fields(profile)
        self._log(f"Імпортовано {profile.email}")
        return profile

    def _assert_required_fields(self, p: "Profile") -> None:
        if not p.email:
            raise ValueError("Профіль без email")

    def _log(self, msg: str) -> None: ...

class JsonProfileImporter(ProfileImporter):
    def _create_parser(self) -> "ProfileParser":   # нащадок ОБИРАЄ клас
        return JsonProfileParser()

class CsvProfileImporter(ProfileImporter):
    def _create_parser(self) -> "ProfileParser":
        return CsvProfileParser()
```
:::

Що тут насправді працює. Метод `import` — код каркаса, і він кличе `createParser()`, **не знаючи**, який об'єкт звідти вийде. У рантаймі виклик потрапить у той метод, який реалізував конкретний нащадок. Каркас пишуть один раз, а він уміє працювати з парсерами, яких на момент його написання ще не було: завтра дописуєш `XmlProfileImporter` — і каркас проведе його тим самим процесом, ні рядка в собі не змінивши.

> 🔧 **Навіщо це.** Ключова тут не економія на `new`, а те, що **спільний процес зафіксовано один раз, а змінну ланку віддано підкласу**. Якби парсер створювався прямо в `import` через `if формат == ...`, то кожен новий формат означав би правку в тілі процесу — і одна помилка ламала б імпорт усіх форматів разом. Діра ж ізолює зміну: новий формат — це новий клас збоку, старий код недоторканий.

**Коли цей варіант справді потрібен, а коли ні.** Він виправданий рівно тоді, коли навколо створення є **спільний процес**, який хочеться написати один раз у базі, і **одна змінна ланка** в ньому. Немає процесу — немає й сенсу в підкласі. Якщо `JsonProfileImporter` не додає нічого, крім однієї стрічки `return new JsonProfileParser()`, то весь ієрархічний апарат — база, два порожні нащадки — це важкий спосіб сказати те, що вміщається в один рядок. Ознака перебору проста: **нащадок складається з єдиного `createParser`, який просто повертає `new`, а більше в ньому нічого немає.** Тоді потрібен не підклас, а наступний різновид.

## Різновид 2: статичний метод-творець замість публічного конструктора

Часто «фабричним методом» звуть зовсім інше — **статичний метод, який стоїть на місці публічного конструктора**: `User.create(...)`, `Duration.ofSeconds(30)`, `LocalDate.of(2026, 7, 8)`. Нащадків тут немає й поліморфізм ні до чого — це радше ідіома, ніж патерн GoF. Але мотив спільний: замість голого `new` дати створенню **ім'я** й **місце, куди складати логіку добору**.

Розберімо, навіщо тут ім'я, бо це не косметика. У конструктора ім'я одне — назва класу. А способів створити профіль може бути кілька, і вони відрізняються не типами аргументів, а **змістом**. Порівняй:

:::tabs
```ts
class Profile {
  // конструктор лишаємо приватним: назовні через нього не ходять
  private constructor(
    readonly email: string,
    readonly displayName: string,
    readonly verified: boolean,
  ) {}

  // осмислені входи в клас — кожен зі СВОЄЮ назвою і своїм добором
  static register(email: string, displayName: string): Profile {
    return new Profile(email.toLowerCase(), displayName, /*verified*/ false);
  }
  static fromVerifiedInvite(email: string): Profile {
    return new Profile(email.toLowerCase(), email.split("@")[0], /*verified*/ true);
  }
  static anonymous(): Profile {
    return new Profile("", "Гість", false);
  }
}

const a = Profile.register("Ann@Ex.com", "Ann");     // → verified=false
const b = Profile.fromVerifiedInvite("bob@ex.com");  // → verified=true
```
```py
from dataclasses import dataclass

@dataclass(frozen=True)
class Profile:
    email: str
    display_name: str
    verified: bool

    # осмислені входи в клас — кожен зі СВОЄЮ назвою і своїм добором
    @classmethod
    def register(cls, email: str, display_name: str) -> "Profile":
        return cls(email.lower(), display_name, False)

    @classmethod
    def from_verified_invite(cls, email: str) -> "Profile":
        return cls(email.lower(), email.split("@")[0], True)

    @classmethod
    def anonymous(cls) -> "Profile":
        return cls("", "Гість", False)

a = Profile.register("Ann@Ex.com", "Ann")       # → verified=False
b = Profile.from_verified_invite("bob@ex.com")  # → verified=True
```
:::

Спробуй уявити те саме на самих конструкторах — і ти впораєшся в глухий кут: `new Profile(email, name, false)` і `new Profile(email, name, true)` виглядають майже однаково, і на місці виклику не видно, що це «реєстрація» проти «підтвердженого запрошення». Ім'я методу — це і є та відсутня в конструкторі інформація: воно **називає намір**. Це перша задокументована перевага статичних фабрик у Джошуа Блоха («Effective Java», Item 1: «статичні фабрики мають імена»; *усталене джерело*).

Тепер — **куди складати логіку добору**. Зверни увагу, що `register` сам приводить email до нижнього регістру, а `fromVerifiedInvite` ще й виводить `displayName` з email і ставить `verified=true`. Це і є логіка добору: **рішення про те, якими вийдуть поля**, живе в методі, а не розмазане по місцях виклику. Якби це робив кожен, хто кличе конструктор, правило «email завжди в нижньому регістрі» довелося б повторювати всюди — і хтось неминуче забув би. Метод-творець збирає правило в одну точку.

> 🔧 **Навіщо це.** Друга перевага імені менш очевидна, але потужна: **метод-творець не зобов'язаний щоразу створювати новий об'єкт** — на відміну від `new`, який завжди робить новий. Він може повернути вже готовий кешований примірник. Так працює `Boolean.valueOf(true)`, що завжди віддає ту саму константу замість нового об'єкта, і `Integer.valueOf`, який кешує невеликі числа. У Java цей кеш `Integer` гарантовано покриває діапазон −128…127 (це вимога специфікації мови для автопакування, JLS §5.1.7; верхню межу можна підняти опцією `-XX:AutoBoxCacheMax`; *усталене джерело*). Конструктор такого не вміє в принципі — він приречений плодити копії. Тому за іменем ховається ще й свобода **не** створювати.

**Типова пастка цього різновиду — сплутати його з патерном там, де він лише перейменований `new`.** Якщо метод-творець рівно один і він просто повертає `new SameClass(args)` без жодного добору, без валідації, без кешу й без вибору підтипу — це не фабрика, а зайвий шар. `static make(x) { return new Thing(x); }` не дає нічого, чого не дав би конструктор, тільки ховає його. Метод-творець виправданий, коли він **несе вагу**: осмислене ім'я замість неоднозначного конструктора, зібраний в одну точку добір полів, кеш або — найсильніше — можливість повернути **різний конкретний клас** залежно від входу. Останнє й веде до третього різновиду.

## Різновид 3: параметризований фабричний метод — вибір класу за даними

Ось де фабрика розкриває найбільшу силу. Тепер вибір конкретного класу робиться **за значенням вхідних даних**: одна точка приймає ключ (розширення файлу, MIME-тип, поле-дискримінатор у payload) і повертає ту реалізацію, яка цьому ключу відповідає. Клієнт віддає дані — отримує готовий об'єкт потрібного підтипу, ні на мить не дізнавшись, який саме клас народився.

Повернімося до імпорту профілів, але зайдімо з іншого боку. Тепер формат не задано типом каркаса — його треба **вивести з самих даних**: нам дали шлях до файлу, і за розширенням треба обрати парсер.

:::tabs
```ts
interface ProfileParser { parse(raw: string): Profile; }

class JsonProfileParser implements ProfileParser { parse(raw: string): Profile { /* ... */ return {} as Profile; } }
class CsvProfileParser  implements ProfileParser { parse(raw: string): Profile { /* ... */ return {} as Profile; } }
class XmlProfileParser  implements ProfileParser { parse(raw: string): Profile { /* ... */ return {} as Profile; } }

// параметризований фабричний метод: за КЛЮЧЕМ (розширення) обирає клас
function parserForFile(path: string): ProfileParser {
  const ext = path.slice(path.lastIndexOf(".") + 1).toLowerCase();
  switch (ext) {
    case "json": return new JsonProfileParser();
    case "csv":  return new CsvProfileParser();
    case "xml":  return new XmlProfileParser();
    default:
      throw new Error(`Немає парсера для формату .${ext}`);
  }
}
```
```py
from typing import Protocol

class ProfileParser(Protocol):
    def parse(self, raw: str) -> "Profile": ...

class JsonProfileParser: 
    def parse(self, raw: str) -> "Profile": ...   # ...
class CsvProfileParser:
    def parse(self, raw: str) -> "Profile": ...
class XmlProfileParser:
    def parse(self, raw: str) -> "Profile": ...

# параметризований фабричний метод: за КЛЮЧЕМ (розширення) обирає клас
def parser_for_file(path: str) -> ProfileParser:
    ext = path.rsplit(".", 1)[-1].lower()
    if ext == "json":
        return JsonProfileParser()
    if ext == "csv":
        return CsvProfileParser()
    if ext == "xml":
        return XmlProfileParser()
    raise ValueError(f"Немає парсера для формату .{ext}")
```
:::

Придивися до сигнатури — і побач другу класичну пастку фабрик, найпідступнішу. Функція повертає `ProfileParser`, **інтерфейс**, а не `JsonProfileParser`. Це не дрібниця. Якби вона повертала конкретний тип, увесь сенс фабрики протік би крізь її ж сигнатуру: клієнт побачив би конкретний клас у типі результату й прив'язався б до нього. **Витік конкретного типу через сигнатуру** зводить фабрику нанівець тихо — код збирається, працює, але зчеплення, яке ми виганяли, повернулося через двері типів.

> 🔧 **Навіщо це.** Правило, яке варто закарбувати: **фабрика мусить приймати й віддавати лише абстракції.** На вході — ключ (рядок, enum) або сирі дані; на виході — інтерфейс продукту. Щойно в сигнатурі з'явився конкретний клас — на вході чи на виході — фабрика перестала ізолювати від нього клієнта. Це та сама помилка, що й `List<String>` проти `ArrayList<String>` у типі параметра, тільки для створення: обіцяй найширше, що можеш, а конкретику лиши всередині.

Тепер головна вада саме цієї форми, і вона видно неозброєно. Це `switch`. Поки форматів три — він читається легко. Але кожен новий формат — це **правка в тілі цього `switch`**: ще один `case`. І така сама гілка з'явиться в кожній іншій точці, що розрізняє формати — у валідаторі, в експортері, у визначенні іконки. **Розростання switch** — це не одна довга функція, це **той самий набір гілок, розсіяний по коду й приречений розсинхронізуватися**: додав формат у парсер, забув у валідаторі. Гілки, які мали б жити разом, живуть нарізно.

## Від switch до реєстрової таблиці

Корінь болю зі `switch` видно, якщо спитати: що таке ці гілки насправді? Це **відображення ключа на клас**: `"json" → JsonProfileParser`, `"csv" → CsvProfileParser`. А відображення в мовах — це не керівна конструкція, це **дані**. Структура даних для «ключ → значення» вже є — це словник (мапа). Тож замість вписувати відповідність у код `switch`, складімо її в таблицю.

:::tabs
```ts
interface ProfileParser { parse(raw: string): Profile; }

// реєстр: ключ → конструктор. Відповідність стала ДАНИМИ, а не гілками коду
const PARSERS = new Map<string, new () => ProfileParser>([
  ["json", JsonProfileParser],
  ["csv",  CsvProfileParser],
  ["xml",  XmlProfileParser],
]);

function parserForFile(path: string): ProfileParser {
  const ext = path.slice(path.lastIndexOf(".") + 1).toLowerCase();
  const Ctor = PARSERS.get(ext);
  if (!Ctor) throw new Error(`Немає парсера для формату .${ext}`);
  return new Ctor();
}

// новий формат — БЕЗ дотику до parserForFile: лише запис у таблицю
export function registerParser(ext: string, ctor: new () => ProfileParser): void {
  PARSERS.set(ext, ctor);
}
```
```py
from typing import Callable

# реєстр: ключ → конструктор. Відповідність стала ДАНИМИ, а не гілками коду
_PARSERS: dict[str, Callable[[], ProfileParser]] = {
    "json": JsonProfileParser,
    "csv":  CsvProfileParser,
    "xml":  XmlProfileParser,
}

def parser_for_file(path: str) -> ProfileParser:
    ext = path.rsplit(".", 1)[-1].lower()
    try:
        ctor = _PARSERS[ext]
    except KeyError:
        raise ValueError(f"Немає парсера для формату .{ext}") from None
    return ctor()

# новий формат — БЕЗ дотику до parser_for_file: лише запис у таблицю
def register_parser(ext: str, ctor: Callable[[], ProfileParser]) -> None:
    _PARSERS[ext] = ctor
```
:::

Що змінилося по суті, а не косметично. У версії зі `switch` знання «які бувають формати» **вшите в керівний потік** функції — щоб його розширити, треба редагувати саму функцію. У версії з таблицею це знання винесене **в дані**, а `parserForFile` стала маленьким сталим рушієм, який просто дивиться в таблицю й ніколи не міняється. Додати формат тепер — це `registerParser("yaml", YamlProfileParser)`, і жодна гілка ніде не чіпається. Це і є [принцип відкритості-закритості](topic:programming/open-closed) у чистому вигляді: поведінка розширюється **новим записом**, а не хірургією в старому коді.

І тут вилазить друга, тихіша вигода. Раз відповідність — це дані, реєстр можна **наповнювати ззовні**, а не одним централізованим літералом. Кожен модуль-парсер сам зголошується в таблицю поряд зі своїм оголошенням — і центральна фабрика взагалі не знає наперед повного списку. У Python це часто роблять декоратором, який реєструє клас у мить його оголошення:

```py
_PARSERS: dict[str, Callable[[], ProfileParser]] = {}

def parses(*extensions: str):
    """Декоратор: реєструє клас-парсер під його розширеннями."""
    def wrap(cls):
        for ext in extensions:
            _PARSERS[ext] = cls
        return cls
    return wrap

@parses("json")
class JsonProfileParser:
    def parse(self, raw: str) -> "Profile": ...

@parses("yml", "yaml")             # два ключі на один клас — вільно
class YamlProfileParser:
    def parse(self, raw: str) -> "Profile": ...
```

Тепер фабрика **не має жодного місця, яке треба правити** при додаванні формату: клас сам себе вписав. Список форматів перестав бути в одному файлі — він зібрався з усіх парсерів, що завантажились. Це доводить розворот до кінця: гілки перетворилися на дані, а дані — на **самореєстрацію**.

Різницю між трьома підходами до вибору за ключем найкоротше видно поруч.

![Три способи вибрати клас за ключем поставлені в ряд і показані знизу як міняється код при додаванні нового формату. Ліворуч ланцюг умовних гілок if-else: кожен новий формат додає ще одну гілку всередину функції, тіло функції росте. Посередині таблиця-реєстр ключ на конструктор: функція мала й стала, новий формат додається рядком у таблицю поза функцією. Праворуч самореєстрація декоратором: кожен клас сам вписує себе поряд зі своїм оголошенням, центральна фабрика взагалі не змінюється й не знає повного списку](img/switch-vs-registry.svg)

*Ті самі гілки проходять шлях від керівного потоку (switch) до даних (таблиця) і далі до самореєстрації. З кожним кроком точка, яку треба правити при новому форматі, відсувається від центральної фабрики: спершу — її тіло, потім — окремий рядок таблиці, врешті — нічого, клас вписує себе сам.*

**Коли зупинитися й не переростати таблицю.** Реєстр — не завжди виграш. Поки варіантів два-три й вони стабільні, `switch` чесніший: він увесь на очах, його видно згори до низу, і зайвої непрямої ланки «загляни в мапу» немає. Таблиця окупається, коли варіантів **багато**, вони **часто додаються**, і особливо коли їх додають **різні модулі** чи плагіни, яким зручно зголоситися самим. Ознака, що час переходити: той самий `switch` за форматом почав дублюватися в другій, третій точці — ось тоді дані варто винести з коду, щоб усі ці точки читали одну таблицю. До того — не ускладнюй.

## Три різновиди поруч — і як не сплутати

Звідусіль вилазив один спільний хребет: **що саме приймає рішення про конкретний клас**. Саме за цією віссю три різновиди й розрізняються — не за тим, що всі троє «створюють об'єкт», а за тим, **звідки береться вибір**.

```
Що керує вибором конкретного класу?
  тип підкласу на руках       → класичний GoF: діра createX(), нащадок реалізує
                                 (потрібен, коли навколо є СПІЛЬНИЙ процес)
  сам факт виклику за іменем   → статичний метод-творець: User.create, ofSeconds
                                 (потрібен заради імені / добору полів / кешу)
  значення вхідних даних       → параметризований: за ключем → клас
                                 (мало ключів → switch; багато й ростуть → реєстр)
```

І три пастки, що псують кожен із них, теж стягуються в три коротких правила, які варто тримати в голові під час рев'ю чужого коду:

- **Фабрика на один клас — не фабрика.** Якщо створюється рівно одна реалізація й другої на видноколі нема, і метод-творець просто повертає `new SameClass(...)` без добору й вибору — прибери шар, пиши `new`. Патерн виправданий вибором, якого тут немає. Це класичний [антипатерн](topic:programming/anti-patterns) — обгортка заради обгортки.
- **Не дай конкретному типу протекти в сигнатуру.** Вхід фабрики — ключ або сирі дані; вихід — інтерфейс продукту. Щойно в сигнатурі (на вході чи на виході) з'явився конкретний клас, фабрика перестала ізолювати від нього клієнта, хоч код і збирається.
- **Розповзлий switch — це прохана таблиця.** Коли той самий розбір за ключем дублюється в кількох місцях, винеси відповідність «ключ → клас» у реєстр: гілки стануть даними, а точка правки при новому варіанті відсунеться від коду фабрики.

За цими трьома питаннями й трьома правилами будь-яку «фабрику» в чужому коді розкладаєш точно: котрий це різновид, чи він тут доречний, і чи не завела його одна з трьох пасток. А коли вибір іде не по одному продукту, а по цілій **узгодженій родині** продуктів разом, що мусять пасувати один одному, — це вже задача не для одного фабричного методу: там потрібен об'єкт із create-методом на кожен вид продукту, і всі три різновиди вибору складаються всередину нього по одному на кожен елемент набору.
