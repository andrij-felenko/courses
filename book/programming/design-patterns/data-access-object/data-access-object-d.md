# Об'єкт доступу до даних (DAO)

<preknowlist>
- [Інтерфейс проти реалізації](topic:programming/interface-vs-implementation) — різниця між тим, ЩО тип обіцяє назовні, і тим, ЯК він це робить; увесь DAO — це інтерфейс, за яким сховано механізм доступу до даних.
- [Принцип інверсії залежностей](topic:programming/dependency-inversion) — високорівнева логіка тримається за контракт, а не за конкретне сховище; саме тому бізнес-код спирається на інтерфейс DAO, а не на драйвер бази.
- [Об'єкт передавання даних (DTO)](topic:programming/dto) — простий носій полів без поведінки; методи DAO класично приймають і повертають саме такі плоскі записи, а не багаті доменні об'єкти.
</preknowlist>

Ось метод, який мав би відповідати на одне ділове питання — «кому надіслати замовлення на погодження»: кому з активних працівників дозволено підписувати закупівлі. Саме правило коротке: роль «погоджувач» і не звільнений. А тепер погляньмо, з чого цей метод складається насправді.

```java
List<String> approverEmails() {
    List<String> emails = new ArrayList<>();
    Connection conn = null;
    try {
        conn = pool.getConnection();
        PreparedStatement st = conn.prepareStatement(
            "SELECT email FROM users WHERE role = ? AND active = 1");
        st.setString(1, "approver");
        ResultSet rs = st.executeQuery();
        while (rs.next()) {
            emails.add(rs.getString("email"));   // єдиний змістовний рядок
        }
        return emails;
    } catch (SQLException e) {
        throw new RuntimeException(e);
    } finally {
        if (conn != null) try { conn.close(); } catch (SQLException ignore) {}
    }
}
```

Змістовного тут — один рядок: `emails.add(rs.getString("email"))`. Усе решта — обслуга одного конкретного сховища: узяти з'єднання з пулу, скласти `SELECT`, підставити параметр, покрутити курсор `ResultSet`, зловити `SQLException`, не забути закрити з'єднання у `finally`. Метод, що мав відповідати на ділове питання, на дев'ять десятих зайнятий тим, **як саме** користувачі лежать у реляційній базі.

Корінь болю — не в кількості рядків. Він у тому, що бізнес-метод **знає механізм доступу**: знає, що це SQL, знає назви колонок, знає про пул з'єднань і про перевірні винятки драйвера. Із цього знання випливають три окремі біди. Перша: правило **не прочитати** — щоб дійти до однієї змістовної умови, око продирається крізь JDBC. Друга: правило **не перевірити** дешево — щоб запустити метод у тесті, потрібна жива база з правильними рядками. Третя, і найгостріша саме тут: правило **не пережити зміну джерела даних**.

Ця третя біда — фірмовий знак цілого класу задач. Уяви, що наступного кварталу користувачі переїжджають зі своєї таблиці в корпоративний каталог LDAP, а згодом — до окремої служби тотожності, куди ходять по HTTP. Питання «кому дозволено погоджувати» до способу зберігання не має жодного стосунку — але метод доведеться переписати повністю, бо `SELECT ... FROM users` в іншому джерелі не працює. Знання механізму просочилося в бізнес-логіку й прив'язало її до одного сховища намертво.

Усі три біди течуть з одного джерела, тож і ліки одні: **зібрати весь доступ до цього джерела даних в одному місці й дати назовні простий інтерфейс**.

## Ідея: одні двері до джерела даних

Замість того щоб розсипати `SELECT`-и й `ResultSet`-и по всьому застосунку, зроби один об'єкт, чия єдина відповідальність — **доступ до цього джерела**. Бізнес-код більше не пише запитів; він просить об'єкт: «дай користувачів із роллю „погоджувач“» — і отримує список, не знаючи й не питаючи, звідки той узявся. Увесь SQL, драйвер, з'єднання, перетворення рядка на запис — усе замкнене всередині цього об'єкта. Його й називають **об'єктом доступу до даних** (англ. *Data Access Object*, DAO — від *data access* «доступ до даних» + *object* «об'єкт»).

Так його й означили там, де він уперше дістав канонічне ім'я: DAO «abstracts and encapsulates all access to the data source» — тобто **вбирає в себе й ховає весь доступ до джерела даних**, сам керуючи з'єднанням, щоб дістати й покласти дані. Уся суть у цих двох половинках: назовні — простий інтерфейс з операціями над даними; усередині — сховані запити, драйвер, механіка сховища. Бізнес-код розмовляє з інтерфейсом; із джерелом розмовляє DAO.

## Кістяк: інтерфейс окремо, реалізація окремо

Щоб бізнес-код не знав механізму, потрібні дві розведені частини. Перша — **інтерфейс DAO**: контракт, що оголошує, які операції над цими даними взагалі є. Друга — **конкретна реалізація**: клас, що виконує контракт над реальним джерелом і тільки там знає про SQL, драйвер і з'єднання.

:::tabs
```java
// контракт — простий носій даних (Transfer Object), без жодної поведінки
record UserRow(long id, String email, String role, boolean active) {}

// інтерфейс DAO — що з цими даними можна робити
interface UserDao {
    UserRow findById(long id);
    List<UserRow> findByRole(String role);
    void insert(UserRow u);
    void update(UserRow u);
    void delete(long id);
}

// бізнес-код залежить ЛИШЕ від інтерфейсу — жодного натяку на сховище
class ApprovalService {
    private final UserDao users;
    ApprovalService(UserDao users) { this.users = users; }

    List<String> approverEmails() {
        return users.findByRole("approver").stream()
            .filter(UserRow::active)
            .map(UserRow::email)
            .toList();
    }
}
```
```ts
// контракт — простий носій даних, без жодної поведінки
type UserRow = { id: number; email: string; role: string; active: boolean };

// інтерфейс DAO — що з цими даними можна робити
interface UserDao {
  findById(id: number): Promise<UserRow | null>;
  findByRole(role: string): Promise<UserRow[]>;
  insert(u: UserRow): Promise<void>;
  update(u: UserRow): Promise<void>;
  delete(id: number): Promise<void>;
}

// бізнес-код залежить ЛИШЕ від інтерфейсу — жодного натяку на сховище
class ApprovalService {
  constructor(private users: UserDao) {}

  async approverEmails(): Promise<string[]> {
    const rows = await this.users.findByRole("approver");
    return rows.filter(u => u.active).map(u => u.email);
  }
}
```
```py
from dataclasses import dataclass
from typing import Protocol, Optional

# контракт — простий носій даних, без жодної поведінки
@dataclass
class UserRow:
    id: int
    email: str
    role: str
    active: bool

# інтерфейс DAO — що з цими даними можна робити
class UserDao(Protocol):
    def find_by_id(self, id: int) -> Optional[UserRow]: ...
    def find_by_role(self, role: str) -> list[UserRow]: ...
    def insert(self, u: UserRow) -> None: ...
    def update(self, u: UserRow) -> None: ...
    def delete(self, id: int) -> None: ...

# бізнес-код залежить ЛИШЕ від інтерфейсу — жодного натяку на сховище
class ApprovalService:
    def __init__(self, users: UserDao):
        self._users = users

    def approver_emails(self) -> list[str]:
        rows = self._users.find_by_role("approver")
        return [u.email for u in rows if u.active]
```
:::

Подивися на `approverEmails`. Це вже чисте ділове правило — воно про погоджувачів, а не про базу. `ApprovalService` тримає поле типу **інтерфейсу** `UserDao` й не має гадки, звідки беруться користувачі. Це те саме, що [принцип інверсії залежностей](topic:programming/dependency-inversion) робить у загальному вигляді: високорівневий код не тягнеться вниз до бази, а оголошує потребу через контракт — і низькорівнева реалізація той контракт виконує. А який саме клас туди підставити, вирішує [впровадження залежностей](topic:programming/dependency-injection): екземпляр DAO подають сервісу ззовні, в одному місці збірки.

Тепер — реалізації. І ось найпереконливіший доказ, що патерн працює: **один і той самий інтерфейс** виконується над геть різними джерелами, а `ApprovalService` різниці не помітить.

```java
// над реляційною базою: тут дозволено знати про SQL і драйвер
class SqlUserDao implements UserDao {
    private final DataSource ds;
    SqlUserDao(DataSource ds) { this.ds = ds; }

    public List<UserRow> findByRole(String role) {
        String sql = "SELECT id, email, role, active FROM users WHERE role = ?";
        try (Connection c = ds.getConnection();
             PreparedStatement st = c.prepareStatement(sql)) {
            st.setString(1, role);
            try (ResultSet rs = st.executeQuery()) {
                List<UserRow> out = new ArrayList<>();
                while (rs.next())
                    out.add(new UserRow(rs.getLong("id"), rs.getString("email"),
                                        rs.getString("role"), rs.getBoolean("active")));
                return out;
            }
        } catch (SQLException e) {
            throw new DataAccessException(e);   // перевинний виняток — не SQLException назовні
        }
    }
    // findById, insert, update, delete — так само над цим самим SQL
    // ...
}

// над звичайною мапою в пам'яті: жодної бази — для тестів
class InMemoryUserDao implements UserDao {
    private final Map<Long, UserRow> store = new HashMap<>();

    public List<UserRow> findByRole(String role) {
        return store.values().stream()
            .filter(u -> u.role().equals(role)).toList();
    }
    public void insert(UserRow u) { store.put(u.id(), u); }
    // findById, update, delete — над цією самою Map
    // ...
}
```

Дві реалізації одного контракту. Одна перекладає кожен виклик на SQL, друга просто тримає записи в `HashMap`. Для `ApprovalService` вони нерозрізненні. І та `SQLException`, що в першому прикладі текла назовні й змушувала весь застосунок знати про JDBC, тут **зупиняється на межі DAO**: `SqlUserDao` ловить її й перевидає власним `DataAccessException`, який уже нічого не розповідає про природу сховища. Механізм замкнено остаточно.

![Угорі блок «Бізнес-логіка · сервіс» із рядком orderDao.findByStatus, від нього пунктирна стрілка залежності вниз до центрального зеленого блока «interface OrderDao» з методами findById, findByStatus, insert, update, delete; від інтерфейсу рейка вниз до трьох реалізацій — SqlOrderDao з циліндром реляційної бази, RestOrderDao з позначкою HTTP до сусідньої служби та InMemoryOrderDao з позначкою Map для тестів; нижня плашка: підмінити реалізацію означає підмінити джерело даних, не чіпаючи клієнта](img/dao-structure.svg)

*Бізнес-код залежить лише від інтерфейсу DAO. Реалізації живуть окремо й ходять кожна у своє джерело — реляційну базу, сусідню службу за HTTP, мапу в пам'яті. Підставити іншу реалізацію — змінити джерело даних, не торкаючись клієнта.*

## Заради чого це насправді: заміна джерела й тест

Перший виграш — **заміна джерела даних**. Поки бізнес-код розмовляє лише з `UserDao`, перевести користувачів із SQL у LDAP, у зовнішню службу тотожності чи в кеш означає **написати новий клас-реалізацію й підставити його на межі**. Той самий `ApprovalService` працюватиме без жодної правки, бо для нього нічого не змінилося — інтерфейс той самий. Той страшний переїзд із першого прикладу, що вимагав переписати бізнес-метод, зводиться до «дописати `LdapUserDao` збоку».

Щоб це перемикання не було розкидане по коду, реалізацію зазвичай обирають не вручну на місці, а через **фабрику DAO**: окремий об'єкт-постачальник видає потрібну реалізацію, і весь застосунок бере DAO тільки в нього. Тоді перехід на інше джерело — це заміна однієї фабрики, а не полювання за кожним `new SqlUserDao(...)` у коді.

> 🔧 **Навіщо це.** Саме на різнорідних і мінливих джерелах DAO окупається найбільше. Дані про клієнта наполовину в старій базі, наполовину в новому мікросервісі? Пишеш дві реалізації одного інтерфейсу й ховаєш склейку за ним — бізнес-код бачить одне джерело. Компанія купує іншу CRM і треба тимчасово читати з обох? Ще одна реалізація, і жоден сервіс про це не дізнається. DAO перетворює «переписати доступ до даних по всьому застосунку» на «дописати ще один клас».

Другий виграш — **тестованість**. Реалізація в пам'яті може здатися іграшкою, а насправді це найбільший щоденний зиск. Щоб перевірити `ApprovalService`, більше не потрібна база: наповнюєш `InMemoryUserDao` потрібними користувачами прямо в пам'яті й ганяєш правило. Тест виходить швидким (немає диску й мережі), передбачуваним (немає чужого стану в спільній базі) і чесним (перевіряє саме ділове правило, а не SQL).

> 🔧 **Навіщо це.** Різниця між «тест іде вісім мілісекунд у пам'яті» і «тест піднімає базу, накатує схему, чистить її по собі» — це різниця між тисячами тестів на кожен коміт і сотнею, яку ганяють раз на ніч, бо довго. Коли правила перевіряються проти DAO в пам'яті, застосунок обростає густою сіткою швидких тестів на саму суть, а повільні, з живою базою, лишаються тонким шаром на межі, де перевіряють уже сам `SqlUserDao`.

Повний робочий приклад — з двома реалізаціями одного DAO, перемиканням джерела через фабрику й тестом, що ганяє сервіс без бази, — розібрано в [окремому проєкті](topic:programming/data-access-object/proj-swappable-dao.md).

## Родина, з якою його плутають

DAO оточений патернами доступу до даних, і межі між ними такі розмиті, що імена вживають як синоніми. Розрізняє їх не форма — усі вони інтерфейс, за яким сховані запити, — а **чим саме мислить абстракція**.

Найчастіше DAO плутають з **[репозиторієм](topic:programming/repository)**. Структурно вони майже однакові. Різниця в тому, **навколо чого вони мислять**. DAO мислить навколо **джерела даних**: типово один DAO на таблицю чи джерело, методи звучать мовою сховища (`insert`, `findByRole`, `findAll`) і класично повертають плоскі записи — ті самі [об'єкти передавання даних](topic:programming/dto), що в первісному описі DAO звалися Transfer Object. Репозиторій мислить навколо **колекції доменних об'єктів**: він per-агрегат, а не per-таблиця, його методи звучать доменною мовою (`approvers()`, `overdue()`), і повертає він готові доменні сутності, а не рядки. На практиці межа тонка, і багато команд називають DAO те, що по суті репозиторій, і навпаки; тримати варто саме намір — DAO абстрагує **джерело даних**, репозиторій симулює **доменну колекцію**.

![Таблиця у три стовпці — вимір, DAO, репозиторій. Заголовки: DAO мислить джерелом даних, репозиторій мислить колекцією об'єктів. Рядки: одиниця — один на таблицю чи джерело проти один на корінь агрегату; методи звучать insert та findByStatus мовою сховища проти forCustomer та overdue мовою домену; повертає плоскі записи Transfer Object проти готових доменних сутностей; прикидається адаптером до джерела даних проти колекції об'єктів у пам'яті. Унизу плашка: форма однакова, різниця в тому, що стоїть у центрі](img/dao-vs-repository.svg)

*Однакова форма — інтерфейс, за яким сховані запити. Різниця в тому, ЩО стоїть у центрі абстракції: у DAO — джерело даних, у репозиторія — доменна колекція. Звідси і per-таблиця проти per-агрегат, і мова сховища проти мови домену, і плоскі записи проти доменних об'єктів.*

Нижче DAO часто стоїть **[Data Mapper](topic:programming/data-mapper)** — вузький перекладач одного об'єкта в рядок і назад. Мапер не знає ні про колекції, ні про пошуки; DAO може спиратися на нього, беручи готовий переклад окремого запису й додаючи згори набір операцій над джерелом. Протилежний за філософією — **[Active Record](topic:programming/active-record)**: там доменний об'єкт **сам уміє зберегтися** (`user.save()`), персистентність вбудована в сам об'єкт. DAO робить рівно навпаки — **виносить доступ до даних з об'єкта геть**, в окремий клас, лишаючи запис чистими даними.

І ще одне ім'я тієї самої ідеї приходить з іншого каталогу. У «Patterns of Enterprise Application Architecture» Мартіна Фаулера DAO не називають цим словом — там його місце посідає **[шлюз таблиці даних](topic:programming/table-data-gateway)** (Table Data Gateway): один об'єкт на всю таблицю, що тримає весь SQL для неї. Поряд живе дрібніший **[шлюз рядка даних](topic:programming/row-data-gateway)** (Row Data Gateway) — один об'єкт на окремий рядок. Сам Фаулер прямо зауважував, що J2EE-шний DAO відповідає його шлюзові таблиці (усталено). Тобто DAO і Table Data Gateway — це та сама річ під двома іменами з двох різних книжок, і саме тому в розмовах про доступ до даних так легко заблукати між назвами.

## Де він ламається

Патерн, який так легко застосувати, легко й **пере**застосувати або скалічити. Три поширені способи зіпсувати DAO варто впізнавати наперед.

Перший — **дірява абстракція**. DAO виглядає як звичайний об'єкт у пам'яті, і за цим виглядом легко забути, що кожен його виклик — це похід у базу. Цикл, що для кожного замовлення кличе `userDao.findById(order.userId())`, читається невинно, а насправді тихо стріляє сотнею окремих запитів — класична біда, яку окремо розбирають як [проблему N+1](topic:programming/active-record). DAO ховає механізм — але не скасовує його ціну, і про цю ціну доводиться пам'ятати самому.

Другий — **узагальнений `Dao<T>`**, що обіцяє `save`, `getAll`, `query` на всі сутності одразу й ще й повертає назовні сирий об'єкт запиту драйвера (`ResultSet`, `Cursor`, `IQueryable`). Такий «DAO» нічого не ховає — він лише перейменовує драйвер і протікає ним крізь себе: бізнес-код знову вміє будувати довільні запити, тобто знову знає про сховище. Абстракція, крізь яку видно те, що вона мала сховати, — це вже [антипатерн](topic:programming/anti-patterns), обгортка заради обгортки.

Третій — **DAO, у який заповзла бізнес-логіка**. Щойно в `SqlUserDao` з'являється метод на кшталт «порахувати знижку постійному клієнтові», доступ до даних і предметне правило знову злиплися — рівно та біда, з якої DAO мав вивести. DAO вартий свого шару лише поки лишається **тонкими дверима до джерела**: дістати, покласти, оновити, видалити — і ні слова про те, що ці дані означають.

## Куди він лягає

У шарах застосунку DAO сидить між **[сервісним шаром](topic:programming/service-layer)** і джерелом даних: сервіс тримає ділові правила й оркеструє, DAO дає йому дані, база (чи служба) їх зберігає. Один важливий кордон DAO свідомо не перетинає — **транзакцію**. Ділова операція часто чіпає кілька DAO (списати з одного рахунку, зарахувати на інший), і звести їхні зміни в одне «усе або нічого» — не робота окремого DAO. Межу транзакції тримають вище: або сервіс явно, або [Unit of Work](topic:programming/unit-of-work), що стежить за всіма змінами й фіксує їх разом. DAO лише виконує окремі дії над даними; де починається й закінчується [транзакція](topic:programming/transactions-acid), вирішує той, хто ними диригує.

Головний сигнал, що DAO доречний, — **джерело даних варте ізоляції**: воно може змінитися, його треба підмінювати в тестах, або доступ до нього достатньо громіздкий, щоб не хотіти бачити його в бізнес-коді. Якщо ж унизу вже лежить зрілий інструмент, що сам дає колекцію-подібний доступ (як багато [ORM](topic:programming/orm)), а застосунок — тонкий CRUD без правил, власний шар DAO часто вироджується в порожнього передавача, де кожен метод — один рядок переадресації. Тоді чесніше обійтися без нього, ніж тримати шар, що нічого не додає.

## Звідки він узявся

Ім'я й канонічну форму DAO дала книга «Core J2EE Patterns: Best Practices and Design Strategies» (2001) — Діпак Алур (Deepak Alur), Джон Крупі (John Crupi) і Ден Малкс (Dan Malks), інженери з групи Sun Java Center; звідти й означення про «абстрагувати й сховати весь доступ до джерела даних» (усталено). Це був світ enterprise-Java, де застосунок мусив ходити по дані в десятки різнорідних місць — реляційні бази, каталоги LDAP, застарілі мейнфрейми, файли, зовнішні служби, — і DAO народився саме як спосіб не дати цій різнорідності протекти в бізнес-код. Роком пізніше, у каталозі Мартіна Фаулера, та сама ідея стала «шлюзом таблиці даних», а ще за рік поряд визрів репозиторій — і три близькі імена відтоді плутають донині. Як саме визрівав DAO у світі J2EE й чому так зрісся з репозиторієм — розгорнуто в [нотатці про його народження](topic:programming/data-access-object/hist-dao-j2ee.md).
