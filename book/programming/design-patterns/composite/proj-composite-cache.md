# ⚙️ Кешований агрегат на компонувальнику: межі, що не рахуються двічі

Відкрий будь-який векторний редактор і виділи групу фігур. Довкола них умить з'являється рамка з ручками — це **габаритний прямокутник** групи (англ. *bounding box*), найменший прямокутник, що вкриває все виділене. Редактор питає цей прямокутник **безперестанку**: щоб намалювати ручки виділення, щоб зрозуміти, у яку фігуру ти влучив кліком, щоб відсікти те, що виїхало за екран і його не треба малювати, щоб виконати «вмістити все у вікно». Десятки таких запитів на кожен кадр, шістдесят кадрів на секунду.

А фігури складені в дерево — компонувальником. Група тримає фігури й інші групи; межа групи — це **об'єднання** меж усіх її дітей, і так рекурсивно до окремих фігур-листків. Найпряміший спосіб відповісти на запит — щоразу спуститися деревом і зібрати об'єднання наново:

```ts
// bounds() групи БЕЗ кешу: щоразу наново обходить усе піддерево
bounds(): Rect {
  let box = EMPTY;
  for (const c of this.children) {
    box = union(box, c.bounds());        // лист віддасть свій прямокутник, група — рекурсивно свій
  }
  return box;                            // нічого не запам'ятали → наступний запит почне все спочатку
}
```

Придивись, що тут марнується. Сцена з десяти тисяч фігур стоїть **нерухомо** — користувач просто дивиться на неї. А редактор шістдесят разів на секунду наново обходить усі десять тисяч вузлів, щоб отримати **той самий** прямокутник, що й мілісекунду тому. Об'єднання ідентичне, вхід не змінився — а робота повторюється сотні тисяч разів на секунду. Це той випадок, коли відповідь варто **запам'ятати** й віддавати готовою, а перераховувати — лише коли щось справді зрушило. Уся хитрість не в тому, щоб зберегти відповідь, — це просто. Хитрість у тому, щоб точно знати, **коли** вона застаріла. Це і робить брудний прапорець.

## Ідея: два зустрічні рухи

Механізм тримається на двох напрямках, і їх варто розділити з самого початку, бо плутанина між ними — джерело половини помилок.

**Униз — лінивий перерахунок.** У кожної групи заводимо поле `cached` (збережений бокс) і `dirty` (брудний прапорець — чи застаріло збережене). Коли в групи питають межі, вона дивиться на прапорець: якщо чистий — миттєво віддає `cached`, не спускаючись нікуди; якщо брудний — перераховує об'єднання дітей, кладе в `cached`, гасить прапорець і аж тоді віддає. Ключове тут: перерахунок **не спускається у чисті піддерева**. Питаючи бокс у дитини, група кличе той самий `bounds()`, і якщо дитина чиста — вона віддає свій `cached` за один такт, не обходячи себе зсередини. Тобто перерахунок торкається лише того, що справді брудне, а чисті гілки лишаються недоторканими.

**Вгору — інвалідизація.** Щоб прапорці відповідали дійсності, будь-яка зміна мусить **позначити брудним** усе, чий бокс від неї залежить. А залежить від фігури не тільки її власна група, а й група тієї групи, і так до кореня: посунув фігуру — поїхав бокс її групи, а отже й бокс усіх груп над нею. Тому інвалідизація йде **вгору** по полю `parent`, від зміненого вузла до кореня, ставлячи брудними всіх пращурів на шляху. І одна економія, без якої весь кеш втратив би сенс: підйом **спиняється на першому вже брудному пращурі**. Бо тут діє інваріант — *якщо вузол брудний, то всі його пращури теж брудні* (їх позначили тоді ж, коли забруднили його). Отже, впершись у брудного, ми знаємо, що вище все вже брудне, і йти далі нема потреби.

Ось повний робочий код обох напрямків. Основна мова — TypeScript (граф сцени редактора природно живе в ній), а поряд C++ — бо кешування світових боксів у графі сцени є щоденним хлібом рушіїв ігор і CAD, де кожен такт на рахунку, і не-власне посилання-вгору `parent` там ідіоматичне.

:::tabs
```ts
type Rect = { minX: number; minY: number; maxX: number; maxY: number };

// порожній бокс — «нескінченно малий»: будь-яке об'єднання одразу його поглинає
const EMPTY: Rect = { minX: Infinity, minY: Infinity, maxX: -Infinity, maxY: -Infinity };

function union(a: Rect, b: Rect): Rect {
  return {
    minX: Math.min(a.minX, b.minX), minY: Math.min(a.minY, b.minY),
    maxX: Math.max(a.maxX, b.maxX), maxY: Math.max(a.maxY, b.maxY),
  };
}

abstract class Shape {
  parent: Group | null = null;          // посилання ВГОРУ — по ньому піде інвалідизація
  abstract bounds(): Rect;
}

class Rectangle extends Shape {
  constructor(public x: number, public y: number, public w: number, public h: number) {
    super();
  }
  bounds(): Rect {                       // листок рахує прямо — власний кеш йому не потрібен
    return { minX: this.x, minY: this.y, maxX: this.x + this.w, maxY: this.y + this.h };
  }
  moveTo(x: number, y: number): void {
    this.x = x; this.y = y;
    this.parent?.invalidate();           // ← зсув ЛИСТКА теж псує кеш групи!
  }
}

class Group extends Shape {
  private children: Shape[] = [];
  private dirty = true;                  // нова/порожня група — брудна
  private cached: Rect = EMPTY;

  add(child: Shape): void {
    child.parent = this;
    this.children.push(child);
    this.invalidate();                   // структура змінилась
  }

  remove(child: Shape): void {
    const i = this.children.indexOf(child);
    if (i < 0) return;
    this.children.splice(i, 1);
    child.parent = null;                 // від'єднаний листок більше нікого не інвалідизує
    this.invalidate();                   // видалення могло стиснути бокс — треба перерахувати
  }

  bounds(): Rect {
    if (this.dirty) {                    // лінивий перерахунок — лише коли брудні
      let box = EMPTY;
      for (const c of this.children) box = union(box, c.bounds());  // чисті діти — O(1)
      this.cached = box;
      this.dirty = false;
    }
    return this.cached;                  // чистий — миттєво, O(1)
  }

  invalidate(): void {                   // себе й усіх пращурів — у брудні, зі зупинкою
    let g: Group | null = this;
    while (g && !g.dirty) {              // уже брудний → вище теж брудні, спиняємось
      g.dirty = true;
      g = g.parent;
    }
  }
}
```
```cpp
#include <vector>
#include <memory>
#include <limits>
#include <algorithm>

struct Rect {
    double minX, minY, maxX, maxY;
    static Rect empty() {                        // «нескінченно малий» бокс
        double inf = std::numeric_limits<double>::infinity();
        return { inf, inf, -inf, -inf };
    }
    void unite(const Rect& r) {                  // розширити себе іншим боксом
        minX = std::min(minX, r.minX);  minY = std::min(minY, r.minY);
        maxX = std::max(maxX, r.maxX);  maxY = std::max(maxY, r.maxY);
    }
};

class Group;                                     // попереднє оголошення для parent

class Shape {
public:
    Group* parent = nullptr;                     // НЕ-власне посилання вгору
    virtual ~Shape() = default;
    virtual Rect bounds() = 0;
};

class Rectangle : public Shape {
    double x, y, w, h;
public:
    Rectangle(double x, double y, double w, double h) : x(x), y(y), w(w), h(h) {}
    Rect bounds() override { return { x, y, x + w, y + h }; }   // листок: прямий рахунок
    void moveTo(double nx, double ny);           // тіло нижче — треба повне визначення Group
};

class Group : public Shape {
    std::vector<std::unique_ptr<Shape>> children;   // композит ВОЛОДІЄ дітьми
    bool dirty = true;
    Rect cached = Rect::empty();
public:
    void add(std::unique_ptr<Shape> child) {
        child->parent = this;
        children.push_back(std::move(child));
        invalidate();                            // структура змінилась
    }

    void remove(Shape* child) {
        auto it = std::find_if(children.begin(), children.end(),
                               [&](auto& c) { return c.get() == child; });
        if (it == children.end()) return;
        child->parent = nullptr;                 // спершу від'єднуємо…
        children.erase(it);                      // …бо erase тут-таки й знищить об'єкт
        invalidate();                            // видалення могло стиснути бокс
    }

    Rect bounds() override {
        if (dirty) {                             // лінивий перерахунок — лише коли брудні
            Rect box = Rect::empty();
            for (auto& c : children) box.unite(c->bounds());   // чисті діти — O(1)
            cached = box;
            dirty = false;
        }
        return cached;                           // чистий — миттєво, O(1)
    }

    void invalidate() {                          // себе й пращурів — у брудні, зі зупинкою
        Group* g = this;
        while (g && !g->dirty) {                 // уже брудний → вище теж брудні
            g->dirty = true;
            g = g->parent;
        }
    }
};

void Rectangle::moveTo(double nx, double ny) {
    x = nx; y = ny;
    if (parent) parent->invalidate();            // ← зсув ЛИСТКА теж псує кеш групи!
}
```
:::

Зверни увагу на симетрію двох напрямків, що зустрічаються в одному полі `parent`. Листок, рухаючись, кличе `invalidate()` **на своєму батькові** — бо власного кешу в листка немає, і перший застарілий бокс — це бокс його групи. Група, змінюючи структуру, кличе `invalidate()` **на собі** — бо застарів насамперед її власний кеш. Одна й та сама процедура підйому обслуговує обидва випадки; різниця лише в тому, з якого вузла починати. А `bounds()` — єдина точка, що взагалі перераховує, і робить це рівно тоді, коли прапорець це дозволяє. Спуск за відповіддю й підйом за інвалідизацією ніколи не плутаються, бо йдуть різними напрямками по одному й тому ж двобічному зв'язку.

## Покроковий розбір

Зберемо маленьку сцену й простежимо за прапорцями. Група `root` тримає групу `inner` (у ній два прямокутники) і ще один прямокутник збоку.

:::tabs
```ts
const root = new Group();
const inner = new Group();
root.add(inner);
const r1 = new Rectangle(0, 0, 10, 10);
inner.add(r1);
inner.add(new Rectangle(20, 0, 10, 10));
root.add(new Rectangle(100, 100, 5, 5));

console.log(root.bounds());   // { minX:0, minY:0, maxX:105, maxY:105 } — ПЕРШИЙ запит: повний перерахунок
root.bounds();                // усе чисте → O(1), не рахує НІЧОГО
r1.moveTo(-50, -50);          // листок поїхав → inner і root стали брудними, сусід — ні
console.log(root.bounds());   // { minX:-50, minY:-50, maxX:105, maxY:105 } — перерахунок ЛИШЕ брудного шляху
```
```cpp
auto root = std::make_unique<Group>();

auto innerOwned = std::make_unique<Group>();
Group* inner = innerOwned.get();                 // тримаємо не-власний доступ, поки не віддали володіння
root->add(std::move(innerOwned));

auto r1Owned = std::make_unique<Rectangle>(0, 0, 10, 10);
Rectangle* r1 = r1Owned.get();
inner->add(std::move(r1Owned));
inner->add(std::make_unique<Rectangle>(20, 0, 10, 10));
root->add(std::make_unique<Rectangle>(100, 100, 5, 5));

root->bounds();        // ПЕРШИЙ запит: повний перерахунок → {0,0,105,105}
root->bounds();        // усе чисте → O(1)
r1->moveTo(-50, -50);  // листок поїхав → inner і root брудні
root->bounds();        // перерахунок лише брудного шляху → {-50,-50,105,105}
```
:::

Розкладемо, що діялось із прапорцями.

- **Побудова.** Кожна нова група народжується брудною (`dirty = true`) — вона ще нічого не рахувала. Тому `add` можна й не змушувати рахувати: група й так брудна.
- **Перший `root.bounds()`.** `root` брудний → перераховуємо: об'єднуємо бокс `inner` (питаємо — `inner` брудний, перераховує з двох прямокутників) і бокс сусіда. Обидві групи гаснуть у чисті. Це єдиний повний обхід — `O(n)`.
- **Другий `root.bounds()`.** `root` чистий → повертає `cached` і **не спускається взагалі**. Нуль роботи по десяти тисячах вузлів, якби вони там були.
- **`r1.moveTo(-50,-50)`.** Листок міняє координати й кличе `parent.invalidate()`. Підйом: `inner` чистий → ставимо брудним, ідемо в `root`; `root` чистий → ставимо брудним, ідемо в `parent` = `null` → стоп. Забруднено `inner` і `root`. Сусідній прямокутник під `root` — не чіпали, він і його бокс лишаються чинними.
- **Третій `root.bounds()`.** `root` брудний → перераховує: питає `inner` (брудний → перераховує свої два) і сусіда (**чистий** → віддає готове за `O(1)`, не спускаючись). Брудний шлях відновлено, усе знову чисте.

Уся суть в останніх двох кроках: зміна одного листка забруднила рівно два вузли — шлях від нього до кореня, — і наступний запит перерахував рівно їх, лишивши все інше в спокої.

## Чому саме прапорець, а не просте підправляння

Тут варто зупинитися на питанні, яке видає, чи людина розуміє механізм чи просто скопіювала його. Навіщо взагалі прапорець і перерахунок? Хіба не можна на `add` просто **вкласти** новий бокс у наявний, а на `remove` — відняти?

Відповідь залежить від того, яку алгебру має твій агрегат — і це справжня, а не схоластична різниця.

Візьми **суму** (той самий підрахунок, тільки замість боксів — розмір теки в байтах). Сума **оборотна**: додав дитину — `cached += x`; прибрав — `cached -= x`; змінився листок на Δ — `cached += Δ`. Усі три випадки правляться за `O(1)`, і брудний прапорець тут узагалі зайвий: агрегат завжди можна підтримувати точним інкрементально.

А тепер **об'єднання боксів**. Додати дитину легко — новий бокс лише **розширює** наявний, тож `cached = union(cached, x)` за `O(1)` і без жодного перерахунку. Але **прибрати**? Об'єднання **необоротне**: у нього немає «мінуса». Прибравши крайню фігуру, ти не знаєш нового боксу — він міг стиснутися будь-як, і дізнатися його можна лише **переглянувши решту дітей**. Те саме зі **зсувом листка всередину**: якщо фігура, що досі підпирала правий край, поїхала ліворуч, новий правий край визначає вже інша фігура — і яка саме, без перегляду не скажеш.

Ось чому брудний прапорець — **загальний** механізм, а інкрементальне підправляння — лише окремий пільговий випадок:

```
агрегат        | додати  | прибрати | зсув листка | що робить прапорець
───────────────┼─────────┼──────────┼─────────────┼─────────────────────
сума (оборотна) | += O(1) | −= O(1)  | += Δ O(1)   | непотрібен — усе точне
об'єднання/макс | ∪ O(1)  | ПЕРЕРАХ. | ПЕРЕРАХ.    | ловить два «ПЕРЕРАХ.»
```

Прапорець дає рівно те, чого не вміє підправляння: він **відкладає** ті зміни, для яких немає дешевої латки (прибирання, стиск), до наступного запиту — і тоді перераховує один раз, замість гарячково шукати неможливий «мінус» на кожній зміні. Тому в загальному коді, який має працювати з будь-яким агрегатом — межами, максимумом, множиною типів усередині, будь-чим необоротним, — ставлять саме прапорець. А інкрементальний `union` на `add` лишають як необов'язкове прискорення поверх нього, коли додавання переважає над прибиранням.

## Скільки це коштує

Тепер порахуймо ціну кожної дії — вона напрочуд прозора. Нехай у дереві `n` вузлів, а глибина (найдовший шлях корінь-листок) — `h`.

- **Чистий запит — `O(1)`.** Прапорець знято, повертаємо `cached`. Жодного спуску.
- **Інвалідизація — `O(h)`.** Підйом від зміненого вузла до кореня, по одному такту на рівень, зі зупинкою на вже брудному. У найгіршому разі — вся висота, `h`.
- **Перерахунок — за кількістю брудного.** Брудний запит спускається лише в брудні піддерева; чисті гілки віддають `cached` за `O(1)`. Після однієї зміни брудний тільки шлях завглибшки `h`, і перерахунок торкається його вузлів та їхніх безпосередніх дітей — а не всіх `n`.

Порахуймо на числах, коли це справді окупається.

**Умова:** сцена з n = 10 000 фігур, дерево завглибшки h ≈ 14. Кадр малюється 60 разів на секунду, і на кожному кадрі UI питає межі кількох груп — хай 200 запитів на кадр. За секунду **спокою** — 0 змін, за секунду **перетягування** — по одному зсуву фігури на кадр (60 змін).

```
                       СЕКУНДА СПОКОЮ (0 змін, 12 000 запитів)
без кешу:  кожен запит — повний обхід O(n)
           12 000 · 10⁴ = 1.2·10⁸ об'єднань — усі однакові, робота на вітер
з кешем:   перший запит O(n) заповнює, решта 11 999 — O(1)
           ≈ 10⁴ + 1.2·10⁴ ≈ 2.2·10⁴          → у ~5 000 разів менше

                       СЕКУНДА ПЕРЕТЯГУВАННЯ (60 змін, 12 000 запитів)
без кешу:  1.2·10⁸ (читання не подешевшали від того, що є зміни)
з кешем:   інвалідизація: 60 · h = 60 · 14 ≈ 840
           перерахунки:   60 брудних шляхів, ~300 об'єднань кожен ≈ 1.8·10⁴
           чисті запити:  ~12 000 · O(1)
           разом ≈ 3·10⁴                        → на кілька порядків менше
```

**Висновок.** Кеш виграє щоразу, коли **читань помітно більше за зміни** — а саме так живе редактор: на сцену дивляться незрівнянно частіше, ніж її правлять. І він не програє навіть у бурю правок під час перетягування — бо брудний прапорець **склеює** зміни: десяток зсувів між двома кадрами забруднюють шлях (дешево), а перерахунок стається **один раз** на наступному кадрі, а не по разу на кожен зсув. Цей другий виграш — злиття багатьох записів в один перерахунок — і є та причина, чому «брудний прапорець» винесено окремим оптимізаційним патерном: Роберт Найстром описав його так у «Game Programming Patterns» (2014, вільно доступна онлайн), і канонічний приклад там той самий, що й тут, — світова матриця вузла графа сцени, яку перераховують ліниво, лише коли локальне перетворення справді змінилось.

Єдиний режим, де кеш не окупається, — **суворе чергування один-в-один**: рівно один запис, за ним рівно одне читання зміненого агрегату, і так по колу. Тоді нема ні повторних читань, щоб зібрати вигоду з готового кешу, ні пачки записів, щоб склеїти їх в один перерахунок, — і бухгалтерія прапорців стає чистим накладом. В інтерактивному редакторі цей режим практично не трапляється, тому кеш там майже завжди у виграші. Це загальний закон будь-якого кешування: воно продає пам'ять і зайву складність за час і перемагає лише там, де є що перевикористати між змінами.

## Пастка перша: забути листок

Найпідступніша помилка ховається саме там, де інтуїція заспокоює. Що «очевидно» псує бокс групи? Додавання й прибирання фігур — структурні зміни. Про них не забувають: рука сама пише `invalidate()` у `add`/`remove`. А от **зсув або зміна розміру самого листка** структуру не чіпає — дерево на вигляд те саме, ті самі вузли на тих самих місцях, — і саме тому інвалідизацію на ньому забувають найчастіше.

Ось як виглядає баг:

```ts
class Rectangle extends Shape {
  // ...
  moveTo(x: number, y: number): void {
    this.x = x;
    this.y = y;
    // ← і все. invalidate() не покликано.
  }
}
```

Фігура зсунулась, її власний `bounds()` уже віддає нові координати — але прапорець групи ніхто не чіпав, `inner.dirty` лишився `false`. Наступний `root.bounds()` бачить чисте дерево й **упевнено віддає старий бокс**, у якому фігура ще на давньому місці. Ручки виділення малюються не там, кліки влучають повз, «вмістити все» лишає фігуру за кадром. І найгірше — помилка **тиха**: жодного винятку, жодного падіння, просто числа тихенько розійшлися з дійсністю, і шукати причину доведеться очима.

![Ліворуч — усе на місці: збережений бокс групи (зелений пунктир) тісно облягає r1 і r2. Праворуч — фігуру r2 зсунули: старий кеш (червоний пунктир) лишився на давньому місці й уже НЕ містить r2, тоді як правильний бокс (зелений суцільний) мав би охопити нове положення. Без інвалідизації група віддасть саме червоний, застарілий прямокутник](/book/programming/design-patterns/composite/img/composite-bounds-stale.svg)

*Кеш чинний, лише поки все нерухоме. Щойно листок зсунувся, а вгору по `parent` не пішла інвалідизація, збережений бокс застигає в минулому — і група впевнено віддає прямокутник, який уже не облягає своїх дітей.*

Ліки прості — той самий рядок, що вже стоїть у робочому коді вище: **кожен** мутатор листка, який рухає координати чи міняє розмір, мусить закінчуватися підйомом `this.parent?.invalidate()`. Правило, яке варто тримати в голові, звучить ширше за компонувальник: **кешований агрегат мусить перехоплювати не лише зміни структури, а й зміни самих значень, що в нього входять.** Забудеш листок — і кеш бреше саме тоді, коли на нього найбільше покладаєшся.

## Пастка друга: спільні вузли й кеш положення

Дотепер ми мовчки припускали, що будова — справжнє **дерево**: у кожного вузла рівно один батько, а `parent` — одне-єдине посилання вгору. На цьому припущенні тримається все — і підйом інвалідизації, і сам зміст «боксу групи». Спокуса його порушити виникає заради економії: якщо на сцені сто однакових значків, кортить завести один об'єкт-листок і підвісити його в сто місць, а не плодити сто копій (це прийом, знаний як **легковаговик** (англ. *Flyweight*) — спільний незмінний об'єкт замість багатьох однакових копій).

Але щойно один листок висить у **двох** груп, кеш положення ламається одразу з двох боків.

**Механічно:** `parent` — одне посилання, а батьків двоє. Інвалідизація піде вгору лише однією гілкою — тією, чиє посилання записане в `parent`, — а кеш **другої** групи тихо застаріє, бо до неї підйом не дійшов. Це та сама тиха брехня, що й у першій пастці, тільки причина глибша: не забули покликати, а фізично нема куди піднятися обома шляхами одразу.

**Суттєво:** навіть якби посилань було два, сам **бокс у світових координатах для спільного листка не визначений**. Значок, підвішений і в заголовку, і в підвалі, стоїть на екрані у **двох різних точках** — то яке його положення? Питати про абсолютний бокс у самого значка безглуздо: відповідь залежить від того, **через кого** до нього прийшли. Кешувати те, що для спільного вузла не має єдиного значення, неможливо в принципі.

Вихід той самий, що дає легковаговик, і він проводить чітку межу. Кешувати можна тільки те, що **не залежить від місця** вузла в дереві: бокс у **власній системі координат** листка (його форма й розмір — однакові скрізь, де б він не висів). Усе, що залежить від положення — абсолютний бокс на екрані, — обчислюють **на льоту** під час обходу, докладаючи перетворення кожної групи згори. Тобто ділять — і кешують спільно — лише **позаконтекстне** (форму), а контекстне (позицію) щоразу накладають ззовні. Правило: **агрегат, прив'язаний до положення, кешують лише в дереві з єдиним батьком; спільні вузли терплять кеш тільки того, що однакове в усіх їхніх місцях.**

## Пастка третя: дві руки на одному прапорці

Кеш перетворив читання на майже безкоштовне — і цим спокушає роздати роботу кільком потокам: хай один рахує межі для відсікання, поки інший обробляє введення. Але `dirty` і `cached` — це **спільний змінний стан**, а `bounds()` робить із ним небезпечну послідовність: **прочитати** прапорець, і якщо брудний — **перерахувати й записати** кеш і **погасити** прапорець. Читання-зміна-запис, яка не є неподільною.

Простеж одне лихе переплетення. Потік R входить у `bounds()`, бачить `dirty = true`, починає об'єднувати бокси дітей. Тим часом потік W рухає листок і кличе `invalidate()` — ставить `dirty = true` (і так уже true, дарма). R завершує об'єднання (зі **старими** координатами, які встиг прочитати), кладе `cached`, і — останнім рухом — гасить `dirty = false`, **затираючи** щойно виставлений W прапорець. Підсумок: у кеші старий бокс, прапорець чистий, а зміна W **загублена** — і випливе вона лише при якійсь наступній, непов'язаній інвалідизації. Тиха стала неправильність, найгірший різновид помилки.

І це ще делікатний випадок. У C++ одночасні незахищені читання й запис того самого `bool` чи `double` — це **гонитва даних** (англ. *data race*), тобто **невизначена поведінка** мовою стандарту: не просто «неправильне число», а право компілятора й процесора на будь-що. У JavaScript у межах одного середовища такої гонитви не буде — цикл подій однопотоковий, ці поля ніхто не чіпає паралельно; вона повертається, лише якщо різати роботу між Web Workers (а вони й так не ділять граф об'єктів). І та однопотоковість — не випадковість, а найпоширеніший **розв'язок**.

Чесних виходів три:

- **Замкнути граф сцени в один потік** (зазвичай — потік UI), а всю важку роботу інших потоків годувати готовими знімками. Так роблять майже всі графічні каркаси, і саме тому браузер обходить пастку за побудовою.
- **Замок** (англ. *mutex*) навколо `bounds()` і мутаторів кожного піддерева. Працює, але блокування вздовж ланцюга `parent` легко родить суперечку за замки й ризик взаємної блокади — порядок захоплення треба стерегти прискіпливо.
- **Не міняти на місці зовсім.** Замість мутувати дерево, будувати нову його версію й **атомарно** підміняти посилання на корінь; читачі завжди тримають цілісний знімок і не бачать напівзмін. Це коштує пам'яті та алокацій, зате знімає замки — підхід [незмінних структур](book:programming/immutability), де стан не правлять, а заміщають новим значенням.

Спільне в усіх трьох — визнати, що кеш є **станом**, а спільний змінний стан під паралельним доступом сам не впорається. Найдешевше й найчастіше — перший вихід: тримати дерево з його прапорцями на одній нитці, а решту світу спілкуватися з ним знімками.

## Що взяти з собою

Кешований агрегат на компонувальнику — це два зустрічні рухи по одному двобічному зв'язку, і вся його справність у тому, щоб їх не сплутати. **Униз** іде лінивий запит: чистий вузол віддає збережене за `O(1)`, брудний перераховує, торкаючись лише брудних піддерев. **Вгору** по `parent` іде інвалідизація — `O(h)`, зі зупинкою на першому вже брудному пращурі, бо над брудним усе вже брудне.

Три речі варто винести твердо. Перше: інвалідизувати треба **не лише структуру, а й значення** — забутий зсув листка робить кеш тихим брехуном саме тоді, коли на нього поклався. Друге: кеш положення живе **тільки в дереві з єдиним батьком**; спільний вузол терпить кеш лише того, що однакове в усіх його місцях, — форми, не позиції. Третє: кеш — це стан, і під кількома потоками він потребує або однопотокового замку сцени, або замків, або незмінних знімків.

А над усім — критерій, коли по кеш узагалі варто братися: **багато читань, мало записів**, або хоч пачки записів, що склеюються в один перерахунок. Редактор, який малює й перевіряє влучання шістдесят разів на секунду, а правиться зрідка, — рівно той випадок, де межі, пораховані раз, окупляться тисячократно.
