# ⚙️ Обхід дерева компонувальника: від рекурсії до явного стека

Дерево компонувальника вміє відповідати на питання про самого себе: скільки в мене вузлів, які в мене імена, який мій найбільший листок. Кожне таке питання — це прохід по **всьому** дереву: спуститися в кожну гілку, зазирнути в кожен листок, звести відповіді докупи. У самій будові компонувальника цей прохід уже наполовину написаний — контейнер тримає своїх дітей і сам є дитиною, тож «спитати ціле» природно розпадається на «спитати кожну частину». Тут ми доведемо цей прохід до робочого коду, а тоді впремося в його межу — глибоке дерево, на якому елегантна рекурсія тихо валить програму, — і побачимо, як ту межу зняти.

Візьмемо дерево, яке вже стоїть перед очима: файлова система. Листок — файл із розміром у байтах; вузол — тека, що тримає список складових (файлів і теки). Один спільний тип `Component`, у нього є ім'я, у теки додатково є діти. Ось кістяк, на якому все стоятиме:

:::tabs
```ts
interface Component {
  readonly name: string;
}

class File implements Component {
  constructor(readonly name: string, readonly bytes: number) {}
}

class Folder implements Component {
  readonly children: Component[] = [];
  constructor(readonly name: string) {}

  add(c: Component): this {
    this.children.push(c);
    return this;                       // зручно ланцюжком будувати дерево
  }
}

// піддослідне дерево
const tree = new Folder("проєкт")
  .add(new Folder("src")
    .add(new File("main.ts", 1200))
    .add(new File("util.ts", 800))
    .add(new Folder("ui")
      .add(new File("button.ts", 640))
      .add(new File("modal.ts", 1500))))
  .add(new Folder("docs")
    .add(new File("guide.md", 300))
    .add(new File("api.md", 950)))
  .add(new File("README.md", 200));
```
```py
from __future__ import annotations
from dataclasses import dataclass, field


class Component:
    name: str


@dataclass
class File(Component):
    name: str
    num_bytes: int


@dataclass
class Folder(Component):
    name: str
    children: list[Component] = field(default_factory=list)

    def add(self, c: Component) -> "Folder":
        self.children.append(c)
        return self                    # зручно ланцюжком будувати дерево


# піддослідне дерево
tree = Folder("проєкт", [
    Folder("src", [
        File("main.ts", 1200),
        File("util.ts", 800),
        Folder("ui", [
            File("button.ts", 640),
            File("modal.ts", 1500),
        ]),
    ]),
    Folder("docs", [
        File("guide.md", 300),
        File("api.md", 950),
    ]),
    File("README.md", 200),
])
```
:::

Це дерево з десяти вузлів: три теки-контейнери (`проєкт`, `src`, `docs`, `ui` — насправді чотири теки) і шість файлів-листків. Далі всі три задачі ганяємо по ньому.

## Задача перша: порахувати вузли

Питання просте: скільки всього вузлів у дереві — рахуючи і теки, і файли? Наївний порив — завести лічильник і якось «пройтися». Але за що зачепитися, щоб пройтися? Ось де будова підказує відповідь сама.

Подумай, що таке «кількість вузлів у піддереві». Якщо піддерево — це листок, у ньому рівно один вузол: він сам. Якщо піддерево — це тека, то в ній один вузол (сама тека) **плюс** кількість вузлів у кожній її дитині. А «кількість вузлів у дитині» — це те саме питання, тільки про менше піддерево. Ось воно: задача для цілого зводиться до тієї самої задачі для частин. Це і є [рекурсія](book:algorithms/recursion) — і вона тут не хитрий прийом, який ми накидаємо зверху, а буквальний переказ того, як дерево збудоване.

Запишімо цей переказ дослівно:

:::tabs
```ts
function countNodes(node: Component): number {
  if (node instanceof Folder) {
    let total = 1;                         // сама тека — один вузол
    for (const child of node.children) {
      total += countNodes(child);          // плюс усе, що в кожній дитині
    }
    return total;
  }
  return 1;                                // листок — рівно один вузол
}

console.log(countNodes(tree));   // 10
```
```py
def count_nodes(node: Component) -> int:
    if isinstance(node, Folder):
        total = 1                          # сама тека — один вузол
        for child in node.children:
            total += count_nodes(child)    # плюс усе, що в кожній дитині
        return total
    return 1                               # листок — рівно один вузол


print(count_nodes(tree))   # 10
```
:::

Зверни увагу на форму. Є **база** — випадок, коли спускатися нема куди: листок повертає 1 і на цьому гілка обриває занурення. Є **крок** — тека складає одиницю за себе з сумою по дітях. Без бази рекурсія не мала б де зупинитися й падала б; тут базу дає сама природа листка — у нього немає дітей, тож нема куди йти глибше. Дерево скінченне, кожен спуск веде до листків, отже занурення гарантовано доходить до дна й повертається.

> 🔧 **Навіщо це.** Той самий кістяк — «база в листку, крок у вузлі складає відповіді дітей» — годиться для будь-якого підрахунку по дереву: скільки в проєкті файлів (лічи лише листки), яка максимальна глибина вкладення (1 + найбільша глибина серед дітей), скільки порожніх тек. Міняється тільки те, що повертає листок і як тека зводить дитячі числа. Розпізнаєш форму — і ціла родина задач стає одним рядком-варіацією.

## Задача друга: зібрати всі імена

Тепер не число, а список: зібрати повні шляхи до всіх листків — щось на кшталт `проєкт/src/main.ts`. Це вже цікавіше, бо відповідь треба **накопичувати**, і по дорозі вниз треба тягнути за собою префікс шляху — те, звідки ми прийшли.

Логіка та сама рекурсивна, але з двома тонкощами. Перша: тека до шляху кожної своєї дитини дописує спереду власне ім'я. Друга: щоб не плодити зайвих списків, зручно передавати список-накопичувач усередину — кожен листок **дописує** в нього свій шлях, а не повертає власний маленький список, який потім хтось зшиватиме.

:::tabs
```ts
function collectPaths(
  node: Component,
  prefix = "",
  out: string[] = [],
): string[] {
  const path = prefix ? `${prefix}/${node.name}` : node.name;
  if (node instanceof Folder) {
    for (const child of node.children) {
      collectPaths(child, path, out);      // спускаємось, несучи шлях сюди
    }
  } else {
    out.push(path);                        // листок — фіксуємо повний шлях
  }
  return out;
}

for (const p of collectPaths(tree)) console.log(p);
// проєкт/src/main.ts
// проєкт/src/util.ts
// проєкт/src/ui/button.ts
// проєкт/src/ui/modal.ts
// проєкт/docs/guide.md
// проєкт/docs/api.md
// проєкт/README.md
```
```py
def collect_paths(
    node: Component,
    prefix: str = "",
    out: list[str] | None = None,
) -> list[str]:
    if out is None:
        out = []                           # не роби [] значенням за замовчуванням!
    path = f"{prefix}/{node.name}" if prefix else node.name
    if isinstance(node, Folder):
        for child in node.children:
            collect_paths(child, path, out)   # спускаємось, несучи шлях сюди
    else:
        out.append(path)                   # листок — фіксуємо повний шлях
    return out


for p in collect_paths(tree):
    print(p)
```
:::

Пітонів рядок `if out is None` — не забаганка. Якби ми написали `out: list[str] = []` у сигнатурі, той список створився б **один раз** при визначенні функції й жив би між викликами; другий виклик `collect_paths(tree)` дописував би імена в той самий, уже непорожній список. Це класична пастка мутабельного значення за замовчуванням у Python — тому загальний ідіом саме `None` як сигнал «створи свіжий усередині».

Помітно, що обидві задачі — той самий обхід, лише дія в листку інша: там повернути 1, тут дописати рядок. Це і є суть того, що обхід у компонувальнику дається задарма: пишеш скелет один раз, а конкретна операція — це те, що ти вставляєш у два місця (що робить листок, як тека зводить дитяче). Коли таких операцій багато, скелет виносять окремим об'єктом-[відвідувачем](book:programming/visitor), щоб не переписувати спуск щоразу.

## Задача третя: знайти найбільший листок

Остання задача поєднує обидві попередні риси: треба пройти все дерево (як у підрахунку) і по дорозі **порівнювати**, тягнучи назовні найкращого кандидата (як накопичення, тільки замість «додати» тут «залишити більшого»). Знайдімо файл із найбільшим розміром.

Рекурсія читається так: найбільший листок піддерева — це, для листка, він сам; для теки — найбільший серед найбільших листків її дітей. Тобто кожна тека питає в дітей «дай свого чемпіона», а тоді з отриманих чемпіонів обирає одного.

:::tabs
```ts
function largestFile(node: Component): File | null {
  if (node instanceof File) return node;   // листок сам собі чемпіон

  let best: File | null = null;
  for (const child of node.children) {
    const candidate = largestFile(child);   // чемпіон піддерева-дитини
    if (candidate && (!best || candidate.bytes > best.bytes)) {
      best = candidate;
    }
  }
  return best;                              // порожня тека поверне null
}

const top = largestFile(tree);
console.log(top?.name, top?.bytes);   // modal.ts 1500
```
```py
def largest_file(node: Component) -> File | None:
    if isinstance(node, File):
        return node                        # листок сам собі чемпіон

    best: File | None = None
    for child in node.children:
        candidate = largest_file(child)    # чемпіон піддерева-дитини
        if candidate and (best is None or candidate.num_bytes > best.num_bytes):
            best = candidate
    return best                            # порожня тека поверне None


top = largest_file(tree)
print(top.name, top.num_bytes if top else None)   # modal.ts 1500
```
:::

Тут база трохи інша: листок повертає себе, а порожня тека (яка теж «дно», але без листка) повертає «нічого» — `null`/`None`. Порівняння `!best || candidate.bytes > best.bytes` акуратно ковтає цей порожній випадок: перший знайдений кандидат стає чемпіоном беззастережно, далі — лише коли строго більший. Так три задачі — підрахунок, збір, пошук екстремуму — виявляються трьома варіаціями одного спуску: різняться тільки базою й тим, як вузол зводить відповіді дітей.

## Скільки це коштує

Тепер порахуймо ціну — і тут вона напрочуд чесна. Нехай у дереві `n` вузлів усього (листки плюс контейнери).

**За часом — O(n).** Кожен вузол обробляється рівно один раз: рекурсія заходить у нього, робить сталу роботу (порівняння, додавання до лічильника чи списку, дописування імені) і йде далі. Жоден вузол не відвідується двічі, бо в дереві до кожного веде єдиний шлях від кореня. Отже, час прямо пропорційний числу вузлів:

```
робота = Σ (стала на вузол) по всіх n вузлах = O(n)
```

Кращого й бути не може: щоб чесно відповісти «скільки вузлів» чи «який найбільший», доведеться бодай раз глянути на кожен — інакше пропущений вузол міг би змінити відповідь. Обхід дерева — це та рідкісна задача, де очевидний алгоритм одразу оптимальний за часом.

**За пам'яттю — O(h), де h — глибина дерева.** Ось найменш очевидна частина, і саме на ній збудована подальша пастка. Здавалося б, рекурсія нічого не зберігає — вона ж не тримає список вузлів. Але вона тримає дещо інше: **стек викликів**. Коли `countNodes(проєкт)` кличе `countNodes(src)`, а той — `countNodes(ui)`, а той — `countNodes(button.ts)`, то в цей момент **усі чотири виклики живі одночасно**: кожен чекає, поки завершиться той, кого він викликав, щоб додати його результат до свого. Кожен незавершений виклик займає кадр (англ. *stack frame*) у системному стеку — з його локальними змінними й адресою повернення.

![Ліворуч — рекурсія: кадри системного стека traverse(root) → traverse(src) → traverse(ui) → traverse(листок) живуть одночасно, доки спуск не сягне дна, тоді згортаються вгору; глибина стосу дорівнює глибині дерева. Праворуч — явний стек: власний список вузлів на обробку лежить у купі, цикл робить pop і push, а стек викликів лишається мілким незалежно від глибини дерева](/book/programming/design-patterns/composite/img/recursion-vs-stack.svg)

*Рекурсія веде свій стек неявно — кадрами викликів у системному стеку, і його висота дорівнює глибині дерева. Явний обхід тримає той самий стек власним списком у купі; стек викликів при цьому лишається мілким, тож глибина дерева йому не страшна.*

Скільки кадрів накопичиться найбільше? Рівно стільки, яка **найдовша гілка від кореня до листка** — це і є глибина `h`. У нашому дереві найдовший шлях `проєкт → src → ui → modal.ts` дає глибину 4, тож у піку живе 4 кадри. Щойно спуск сягає листка й повертається, кадр звільняється — стос згортається знизу вгору. Тому в будь-яку мить кадрів не більше за `h`, а не за `n`:

```
пам'ять стека = (найглибша гілка) × (розмір кадру) = O(h)
```

Для **збалансованого** дерева з `n` вузлів глибина `h ≈ log₂ n` — тобто пам'ять під стек логарифмічна, копійчана: мільйон вузлів дасть десь двадцять кадрів. Але — і ось де ховається біда — дерево не зобов'язане бути збалансованим.

## Пастка: коли дерево вузьке й довге

Уяви дерево-«бурульку»: тека, в ній одна тека, в тій одна тека — і так десять тисяч разів углиб, а на самому дні один файл. Вузлів усього `n ≈ 10000`, і за часом обхід так само O(n) — швидкий. Але глибина `h` тепер теж 10000, бо гілка одна й вона тягнеться до самого низу. Значить, рекурсія в піку триматиме **десять тисяч живих кадрів** — по одному на кожен рівень.

Системний стек — не безмежний. У більшості середовищ він має жорсткий стельовий розмір, і коли кадри його переповнюють, програма падає — не з логічної помилки, а тому що фізично скінчилося місце під виклики.

- **Python** свідомо не пускає рекурсію туди першим: у нього стоїть м'який запобіжник — межа глибини близько **1000** (`sys.getrecursionlimit()`), і на 1000-му вкладеному виклику він кидає `RecursionError: maximum recursion depth exceeded`, не даючи дійти до справжнього краху C-стека ([документована стандартна поведінка](https://docs.python.org/3/library/sys.html#sys.setrecursionlimit)). Тобто наше `count_nodes` на бурульці завглибшки 5000 впаде задовго до кінця — з винятком, а не з тихим псуванням пам'яті.
- **JavaScript** такої явної межі глибини не має — там дно ставить сам розмір стека рушія, і при переповненні летить `RangeError: Maximum call stack size exceeded`. Конкретне число залежить від рушія й машини (у V8/Chrome це порядку десятка тисяч кадрів, в інших рушіях — помітно більше чи менше), тож на нього не можна закладатися як на стале ([типова причина цієї помилки — надто глибока рекурсія](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Errors/Too_much_recursion)).

Мораль: рекурсивний обхід гарний і читабельний, поки глибина дерева **обмежена й невелика** — а це майже завжди так для файлових систем, DOM, меню, розумних AST. Але щойно глибина може стати довільною — дані приходять ззовні, дерево породжене автоматом, у ньому бувають довгі ланцюги, — рекурсія стає бомбою з таймером: на «звичайних» входах працює роками, а на одному патологічно глибокому валить процес. Тоді неявний стек викликів треба замінити на **явний власний стек**, який лежить у купі й росте, скільки треба.

## Той самий обхід без рекурсії

Ідея переходу проста, якщо побачити, **що саме** робила за нас рекурсія. Вона вела стек «вузлів, до яких я ще повернуся». Заведімо цей стек руками — звичайним списком — і крутімо цикл: витягли вузол, обробили, а всіх його дітей поклали назад у стек, щоб дістатися до них згодом. Поки в стеку щось є — робота триває.

Ось підрахунок вузлів явним стеком — та сама відповідь, та сама складність за часом, але **системний стек лишається мілким**, хоч би яким глибоким було дерево:

:::tabs
```ts
function countNodesIter(root: Component): number {
  let total = 0;
  const stack: Component[] = [root];       // наш власний стек — у купі
  while (stack.length > 0) {
    const node = stack.pop()!;             // беремо вузол на обробку
    total++;                               // рахуємо його
    if (node instanceof Folder) {
      for (const child of node.children) {
        stack.push(child);                 // дітей — назад у стек, на потім
      }
    }
  }
  return total;
}

console.log(countNodesIter(tree));   // 10
```
```py
def count_nodes_iter(root: Component) -> int:
    total = 0
    stack: list[Component] = [root]        # наш власний стек — у купі
    while stack:
        node = stack.pop()                 # беремо вузол на обробку
        total += 1                         # рахуємо його
        if isinstance(node, Folder):
            stack.extend(node.children)    # дітей — назад у стек, на потім
    return total


print(count_nodes_iter(tree))   # 10
```
:::

Порівняй два цикли життя. Рекурсивний варіант тримав кадри в **системному** стеку — тому й падав, коли той переповнювався. Ітеративний тримає вузли у **своєму** списку в купі (англ. *heap*) — а купа велика, і список у ній росте, доки вистачає загальної пам'яті процесу, без жодної межі на «глибину викликів». Стек викликів у циклі при цьому весь час мілкий: один кадр самого `countNodesIter`, який крутить `while`. Дерево-бурулька завглибшки мільйон? Список у піку потримає скількись посилань — і все відпрацює, тоді як рекурсія давно б упала.

Є одна тонкість, варта уваги: **порядок**. Стек — «останнім прийшов, першим пішов» (LIFO), тож коли ми штовхаємо дітей зліва направо, а витягуємо з кінця, обходимо їх справа наліво. Якщо порядок важливий (наприклад, треба вивести імена саме в тому порядку, як вони лежать), дітей у стек кладуть **у зворотному порядку** — або беруть іншу структуру.

Бо стек — не єдиний вибір контейнера. Заміни його на **чергу** (англ. *queue*, «першим прийшов, першим пішов», FIFO) — і той самий цикл почне обходити дерево не вглиб, а **вшир**: спершу всі вузли одного рівня, тоді всі наступного. Це вже обхід у ширину (англ. *breadth-first*), і корисний він там, де потрібен «найближчий до кореня» вузол — приміром, знайти файл, лежачи якнайближче до верху:

:::tabs
```ts
function collectByLevel(root: Component): string[] {
  const out: string[] = [];
  const queue: Component[] = [root];       // черга замість стека — обхід ушир
  while (queue.length > 0) {
    const node = queue.shift()!;           // беремо з ПОЧАТКУ (FIFO)
    out.push(node.name);
    if (node instanceof Folder) {
      for (const child of node.children) {
        queue.push(child);                 // діти йдуть у хвіст
      }
    }
  }
  return out;   // [проєкт, src, docs, README.md, main.ts, util.ts, ui, ...]
}
```

```py
from collections import deque

def collect_by_level(root: Component) -> list[str]:
    out: list[str] = []
    queue = deque([root])                  # черга замість стека — обхід ушир
    while queue:
        node = queue.popleft()             # беремо з ПОЧАТКУ (FIFO)
        out.append(node.name)
        if isinstance(node, Folder):
            queue.extend(node.children)    # діти йдуть у хвіст
    return out   # [проєкт, src, docs, README.md, main.ts, util.ts, ui, ...]
```
:::

Одна й та сама механіка — «дістань вузол, обробити, поклади дітей назад» — дає обхід або вглиб, або вшир **лише** залежно від того, з якого кінця контейнера ми забираємо. Це той рідкісний випадок, коли зміна однієї структури даних безшумно перемикає поведінку алгоритму, і варто тримати його в голові: стек → углиб, черга → вшир.

Маленьке зауваження для Python: `queue.popleft()` на `deque` — це стала операція, тоді як `list.pop(0)` зсовує весь список і коштує O(n) за раз, псуючи загальну складість до O(n²). Тому для черги беруть саме `deque`, а не звичайний список. У JavaScript `Array.shift()` формально теж O(n), і на дуже великих деревах його міняють на чергу з двома вказівниками або окрему структуру — але для помірних розмірів масив-як-черга цілком робочий.

## Що взяти з собою

Обхід дерева компонувальника — це та сама операція в трьох одежинах, і всі три варті того, щоб їх бачити разом.

По-перше, **рекурсія тут не трюк, а форма**. Дерево посилається саме на себе — контейнер тримає дітей свого ж типу, — і будь-яке питання про ціле дослівно розкладається на те саме питання про частини, з базою в листку. Підрахунок, збір імен, пошук екстремуму — один скелет, різні тільки «що робить листок» і «як вузол зводить дитяче». Розпізнав скелет — і ціла родина задач лягає варіаціями одного спуску.

По-друге, ціна чесна й прозора: **O(n) за часом** (кожен вузол раз) — і краще неможливо; **O(h) за пам'яттю** — стільки, яка глибина дерева, бо стільки живих кадрів тримає стек викликів у піку. Для збалансованого дерева це логарифм, копійки; для довгого й вузького — стільки ж, скільки вузлів.

По-третє, саме друге й ставить межу. Поки глибина мала й обмежена — рекурсія найчитабельніша, лиши її. Щойно глибина може стати довільною — рекурсія тихо валить процес переповненням стека (`RecursionError` у Python, `RangeError` у JS), і тоді неявний стек викликів замінюють **явним власним стеком у купі**: той самий обхід, та сама складність за часом, але глибина дерева більше не тисне на стек викликів. А обмінявши стек на чергу, тим самим циклом перемикаєшся зі спуску вглиб на обхід ушир — коли потрібен найближчий до кореня вузол.

Дерево ти будуєш компонувальником; **як** його обійти — рекурсією, явним стеком чи чергою — обираєш під те, наскільки глибоким і наскільки контрольованим це дерево буває.
