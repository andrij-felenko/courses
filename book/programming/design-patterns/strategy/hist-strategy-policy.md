# 📜 Як алгоритм став окремою річчю

Патерн стратегії має дату народження — жовтень 1994-го, коли вийшла книжка «банди чотирьох». Але сама **думка**, яку той патерн упіймав і назвав, значно старша за будь-яку книжку про об'єкти. Ця думка звучить так: **спосіб щось зробити можна відірвати від того, хто це робить, і поводитися зі способом як з окремою, іменованою, взаємозамінною річчю — передати його, зберегти, підмінити.** Історія стратегії — це історія того, як цю думку по черзі відкривали в дуже різних куточках програмування, кожен раз під своєю назвою, і як урешті стало видно, що всі говорили про одне.

Розкрутімо цю історію від коренів, бо тільки так видно головне: стратегія — не винахід об'єктно-орієнтованого програмування. ООП лише дало їй одне з облич. Коли ти зрозумієш, скільки різних облич у неї було, ти перестанеш бачити «патерн із книжки» й почнеш бачити фундаментальний прийом, що проступає крізь мови, епохи й парадигми.

## Найдавніший корінь: функція, яку передають

Почнімо з того, що видається сьогодні банальністю, а колись було проривом: **функцію можна передати іншій функції як аргумент**. Якщо це можливо, то «взаємозамінний алгоритм як окрема річ» виходить сам собою — бо функція вже і є та окрема річ, яку ти носиш і підставляєш.

Ця можливість з'явилася майже на світанку програмування. Мова **Lisp**, яку Джон Маккарті (англ. *John McCarthy*) задумав 1958 року, від самого початку трактувала функції як звичайні значення: їх можна було зв'язати з іменем, покласти в список, повернути з іншої функції й — головне для нас — **передати аргументом** (усталений факт; функції як повноправні значення — риса Lisp з його ранніх версій). Це означало, що вже наприкінці 1950-х можна було написати процедуру сортування, якій ти **окремо даєш правило порівняння**. Процес сортування — один; правило — те, що ти приносиш ззовні. Це рівно та сама розв'язка, на якій стоїть стратегія: сталий процес плюс підставний змінний шматок.

> 🔧 **Навіщо це.** Тут важливо не проґавити суть. Коли пізніше об'єктна книжка описуватиме стратегію як «інтерфейс, три класи-реалізації й контекст», це виглядатиме як складна конструкція, винайдена спеціально. Але глибинно вона робить те саме, що робив `sort` із функцією-порівнювачем у Lisp за тридцять із гаком років до GoF: приймає поведінку ззовні. Класи — це лише **упаковка** для мов, де інакше поведінку не передати. Ідея ж — стара, як передавана функція.

Ту саму лінію продовжила родина мов **ML**, яку Робін Мілнер (англ. *Robin Milner*) із помічниками почав розробляти в Единбурзькому університеті від 1973 року як метамову для системи доведення теорем LCF (усталений факт). ML робила функції вищого порядку — ті, що беруть або повертають інші функції — центральним, повсякденним інструментом, ще й із суворою типізацією. У світі ML передати компаратор у сортування, обробник у обхід дерева, перетворювач у згортку — не хитрий трюк, а звичайний спосіб писати. Ідея «алгоритм — це значення, що подорожує» тут уже цілком дозріла й одомашнилась.

Отже, запам'ятаймо перший висновок: **у мовах, де функція — повноправне значення, стратегія існувала завжди й не мала імені, бо не потребувала його.** Вона була просто «передати функцію». Ім'я їй знадобиться пізніше — і саме там, де передати функцію було не можна.

## C: стратегія без замикання, і чому знадобився зайвий аргумент

Наступна зупинка показує, що стається зі стратегією, коли мова передавати функцію дозволяє, а от **пам'ятати щось разом із нею** — ні. Це історія вказівника на функцію в C, і вона напрочуд повчальна.

Стандартна бібліотека C має функцію сортування `qsort`. Її стандартизували в ANSI C 1989 року (усталений факт; сама реалізація старша — версія на C була в Unix уже в 1970-х). Її підпис — жива археологія стратегії:

```c
void qsort(void *base, size_t nmemb, size_t size,
           int (*compar)(const void *, const void *));
```

Придивись до останнього параметра `compar`. Це **вказівник на функцію-порівнювач** — рівно та сама «передана поведінка», що й у Lisp. `qsort` — незмінний процес сортування; `compar` — взаємозамінне правило, яке ти приносиш. Тобто C цілком уміє стратегію: ти пишеш кілька функцій-порівнювачів і підставляєш потрібну.

```c
// два взаємозамінні «правила» — дві окремі стратегії
int by_asc(const void *a, const void *b) {
    return *(const int*)a - *(const int*)b;      // за зростанням
}
int by_desc(const void *a, const void *b) {
    return *(const int*)b - *(const int*)a;      // за спаданням
}

int nums[] = {5, 2, 9, 1};
qsort(nums, 4, sizeof(int), by_asc);             // підставили одну
qsort(nums, 4, sizeof(int), by_desc);            // підставили іншу
```

А тепер — тонкість, яка все й пояснює. Уяви, що правило порівняння **не сталеˊ**, а залежить від чогось, порахованого в рантаймі: скажімо, ти хочеш сортувати рядки за відстанню до якогось заданого зразка. Функції-порівнювачу треба знати той зразок. Але підпис `compar` — жорсткий: рівно два вказівники на елементи, і жодного місця, щоб «просунути» зразок усередину. Функція в C — гола: вона не носить із собою жодного стану, тільки код. У неї немає **замикання** — механізму, яким функція пам'ятає значення з місця свого народження.

Історично цю проблему в C обходили некрасиво — через **глобальну змінну**: клали зразок у глобальну, а порівнювач звідти його читав (усталений факт; саме через цю ваду згодом додали `qsort_r`, що бере додатковий аргумент-контекст, — у BSD- та GNU-системах). Пізніший `qsort_r` полагодив це чисто: у нього є зайвий параметр, який `qsort_r` дбайливо передає у твій порівнювач:

```c
// правило зі станом: порівнюємо за близькістю до pivot
int by_closeness(const void *a, const void *b, void *ctx) {
    int pivot = *(const int*)ctx;                // стан приходить АРГУМЕНТОМ
    return abs(*(const int*)a - pivot) - abs(*(const int*)b - pivot);
}

int pivot = 7;
qsort_r(nums, 4, sizeof(int), by_closeness, &pivot);  // стан подорожує окремо
```

Ось де ховається глибокий урок історії. У мовах із замиканнями (Lisp, ML, згодом майже всі) стратегія-функція **сама носить свій стан** — замикання пам'ятає його непомітно. У C замикань нема, тож стан доводиться **тягати вручну окремим аргументом-контекстом**. І коли за десятиліття банда чотирьох намалює стратегію як **об'єкт** із полями, вона фактично формалізує саме те, чого бракувало C: об'єкт — це «функція плюс її стан, зв'язані разом і названі». Стратегія-об'єкт з полями `rate`, `pivot` тощо — це рукотворне замикання для мов, де замикань бракує, обгорнуте в тип із іменем.

> 🔧 **Навіщо це.** Ця історія — не про застарілий C. Вона показує, **навіщо взагалі клас** у класичній стратегії. Коли алгоритм не має стану — вистачить голої функції (той самий `by_asc`). Щойно алгоритмові потрібно щось пам'ятати між викликами або нести налаштування — потрібне місце для того стану. Замикання дає це місце безкоштовно; там, де замикань нема, місце дає об'єкт-стратегія. Тому «функція чи клас» — це насправді питання «є стан чи нема», а не питання смаку.

## Патерни приходять із архітектури: як визріла ідея каталогу

Поки в одному кутку світу функції спокійно подорожували, в іншому кутку зріла зовсім інша ідея — не про механізм, а про **мову опису рішень**. Без неї стратегія ніколи не стала б «патерном стратегії», а лишилася б безіменним прийомом.

Джерело тут несподіване — архітектура будівель. Архітектор Крістофер Александер (англ. *Christopher Alexander*) із співавторами Сарою Ішикавою та Мюрреєм Сільверстайном 1977 року видав книжку «A Pattern Language» — 253 «патерни» облаштування простору, від міста до кімнати (усталений факт). Кожен патерн там мав ту саму форму: назва, повторюваний **контекст із проблемою** й перевірена **суть розв'язку** — не готове креслення, а зерно рішення, придатне щоразу по-новому. Головна думка Александера: у доброму проєктуванні ті самі проблеми повертаються, тож розв'язки варто **іменувати й описувати як спільну мову**, щоб про них можна було говорити.

Цю думку на програмування перенесли Кент Бек (англ. *Kent Beck*) і Ворд Каннінгем (англ. *Ward Cunningham*) — 1987 року вони почали пробувати «мову патернів» у коді (усталений факт). А довів ідею до вибуху вже квартет, який історія запам'ятала як **банду чотирьох (англ. Gang of Four)**.

## 1994: банда чотирьох дає прийому ім'я й місце

Тепер — центральна подія. Еріх Гамма (нім. *Erich Gamma*), Річард Гелм (англ. *Richard Helm*), Ральф Джонсон (англ. *Ralph Johnson*) і Джон Вліссідс (англ. *John Vlissides*) звели двадцять три повторювані розв'язки об'єктного проєктування в один каталог — книжку «Design Patterns: Elements of Reusable Object-Oriented Software».

Тут варто бути точним із фактами, бо їх часто плутають. Співпраця почалася раніше за книжку: чотирьох звела сесія «birds-of-a-feather» під назвою «Towards an Architecture Handbook» на конференції **OOPSLA 1990** — там Гамма й Гелм познайомилися й виявили спільний інтерес, а згодом до них долучилися Джонсон і Вліссідс (усталений факт). Сама книжка вийшла **21 жовтня 1994 року** (з копірайтом 1995-го) і була вперше представлена публіці на **OOPSLA 1994** (усталений факт). Передмову написав Ґрейді Буч (англ. *Grady Booch*); приклади в книжці — мовами C++ і Smalltalk (усталений факт). Тобто «1994» і «OOPSLA» — правда, але це рік і місце **виходу**, а знайомство авторів — з OOPSLA чотирма роками раніше; це різні події, і легенда любить їх зливати.

У цьому каталозі стратегія (англ. *Strategy*) — один із патернів, віднесений до **поведінкової** категорії: тих, що впорядковують не створення й не склад об'єктів, а **розподіл обов'язків і спосіб взаємодії** між ними. І ось що GoF зробили насправді цінного — не винайшли прийом (він, як ми бачили, був старий), а **дали йому три речі, яких прийому бракувало**:

- **Ім'я.** Відтепер «винеси змінний алгоритм в окремий об'єкт за спільним інтерфейсом» називається одним словом — «стратегія». Двоє інженерів тепер могли за секунду порозумітися.
- **Межі й сусідів.** Каталог поставив стратегію поряд зі схожими за формою патернами — [Стан](book:programming/state), [Команда](book:programming/command) — і показав, що відрізняє їх **намір**, а не структура. Стратегія — «яким із рівноправних способів зробити»; стан — «у якій я фазі»; команда — «дія-запис, що переживе момент». Про те, чому патерни класифікують саме за наміром, — [окремо](book:programming/what-is-pattern).
- **Принцип під сподом.** Стратегія стала хрестоматійним утіленням гасла, яке ті ж автори винесли окремо: [«надавай перевагу композиції об'єктів перед спадкуванням класів»](book:programming/composition-inheritance). Замість «бути підкласом із зашитою поведінкою» об'єкт «має всередині змінний об'єкт-поведінку».

Слово «стратегія» тут не випадкове, і його корінь підсвічує суть. Воно прийшло з грецького *stratēgia* — «служба, мистецтво полководця», від *stratēgós* (полководець): *stratós* — військо, *ágein* — вести (усталена етимологія). Полководець не б'ється сам — він **обирає план дій** із кількох можливих під ситуацію. Рівно це й робить контекст зі стратегією-об'єктом: не виконує алгоритм своїм тілом, а **обирає й доручає** одну поведінку з-поміж взаємозамінних. Назва впіймала намір напрочуд влучно.

![Три доріжки історії — функції як значення (Lisp, ML), вказівник на функцію в C, і об'єктні патерни GoF — сходяться в одну ідею: сталий контекст плюс підставний змінний алгоритм; праворуч показано, що ту саму ідею беруть на двох рівнях — рантайм-об'єкт стратегії та компайл-тайм-параметр типу політики, і обидва роблять по суті те саме](/book/programming/design-patterns/strategy/img/hist-convergence.svg)

*Одна ідея, багато імен: передати функцію, передати вказівник на функцію, підставити об'єкт-стратегію, підставити тип-політику — усе це «сталий процес плюс взаємозамінний змінний шматок», узятий на різних рівнях і в різних мовах.*

## Той самий прийом на етапі компіляції: політики в C++

Історія могла б на цьому спинитись — «прийом старий, GoF дали ім'я». Але є ще одна гілка, і саме вона робить розповідь по-справжньому цікавою, бо показує ту саму ідею, зсунуту в **інший час виконання**. Це історія «дизайну на політиках» у C++.

Спершу — контекст, чому C++ пішов своїм шляхом. У C++ поряд зі звичайними об'єктами й віртуальними викликами (це рантайм-механізм, на якому стоїть класична стратегія) є другий, потужний інструмент — **шаблони (англ. templates)**: код, параметризований **типами**, який компілятор розгортає для кожного набору типів **ще до запуску програми**. Це відкриває дражливу можливість: а що, як підставляти взаємозамінну поведінку не рантайм-об'єктом, а **типом-параметром на етапі компіляції**?

Ця лінія визрівала в C++-спільноті поступово. Її ранній ґрунт — **стандартна бібліотека шаблонів (STL)**, яку Александр Степанов (англ. *Alexander Stepanov*) із колегами (зокрема Девідом Массером) розробляв у 1980-х як методологію відриву алгоритмів від структур даних (усталений факт). У STL уже жили типи-параметри, що визначають поведінку: скажімо, тип-**розподілювач пам'яті (allocator)**, який класи-контейнери беруть параметром і який фактично задає **політику розподілу** пам'яті; чи `char_traits` — параметр, що задає, як поводитися з символами рядка. Це вже була «взаємозамінна поведінка як параметр типу» — стратегія, вибрана компілятором. Просто її ще не називали цим словом і не описували як окремий метод.

Слово й метод викристалізував **Андрей Александреску (рум./англ. *Andrei Alexandrescu*)** — румунсько-американський програміст, народжений 1969 року в Бухаресті (усталений факт; згодом здобув докторат у Вашингтонському університеті, громадянин США з 2014-го). У книжці «Modern C++ Design: Generic Programming and Design Patterns Applied», що вийшла 2001 року у видавництві Addison-Wesley (усталений факт), він увів і розгорнув **дизайн на політиках (англ. policy-based design)**: клас-господар параметризують кількома незалежними типами-**політиками**, кожна з яких відповідає за одну вісь поведінки, і компілятор збирає з них потрібну комбінацію. Увесь код книжки Александреску виклав у вільній бібліотеці **Loki** (усталений факт).

Подивімось, як це виглядає, поставивши поряд рантайм-стратегію й компайл-тайм-політику — щоб побачити, що це те саме двома руками:

```cpp
// (1) КЛАСИЧНА стратегія: поведінка — рантайм-ОБ'ЄКТ за вказівником/посиланням.
//     Який алгоритм — вирішується під час РОБОТИ програми.
struct DiscountPolicy {
    virtual double discount(double total) const = 0;   // спільний інтерфейс
    virtual ~DiscountPolicy() = default;
};
struct VipDiscount : DiscountPolicy {
    double discount(double total) const override { return total * 0.20; }
};

struct Order {
    DiscountPolicy* policy;                             // поле — підставна поведінка
    double total;
    double final_price() const {
        return total - policy->discount(total);         // віртуальний виклик у рантаймі
    }
};
```

```cpp
// (2) ПОЛІТИКА: та сама поведінка — компайл-тайм-ТИП-параметр.
//     Який алгоритм — вирішується під час КОМПІЛЯЦІЇ; віртуальних викликів нема.
struct VipDiscount {
    static double discount(double total) { return total * 0.20; }
};
struct NoDiscount {
    static double discount(double total) { return 0.0; }
};

template <class Policy>                                 // поведінка приходить ТИПОМ
struct Order {
    double total;
    double final_price() const {
        return total - Policy::discount(total);         // підставлено ще до запуску
    }
};

// вибір робиться в типі: компілятор згортає окрему версію під кожну політику
Order<VipDiscount> a{1000};   a.final_price();          // 800
Order<NoDiscount>  b{1000};   b.final_price();          // 1000
```

Порівняй два `Order`. Структурно вони роблять **одне**: тримають сталий процес `final_price` і підставну поведінку `discount`. Різниця тільки в тому, **коли** підставляється поведінка й **чим** вона представлена. У варіанті (1) поведінка — це об'єкт, вибраний під час роботи, і за нього платиш віртуальним викликом, зате можеш підмінити його на льоту через `policy = …`. У варіанті (2) поведінку зашито в тип ще при компіляції: підмінити її під час роботи не можна (тип `Order<VipDiscount>` — це назавжди інший тип, ніж `Order<NoDiscount>`), зате нема жодного рантайм-коштування — компілятор часто вбудовує все в один рядок.

Це та сама розвилка, що ми бачили в C з `qsort` проти `qsort_r`, тільки піднята на новий рівень: вибір між «поведінка як рухома річ під час роботи» й «поведінка, вбудована наглухо до роботи». Обидва — стратегія; вони по різні боки шкали «гнучкість тепер ↔ швидкість потім».

## Чому «стратегія» і «політика» так часто виявляються тим самим

Тепер ми готові розв'язати головну загадку, заради якої й писалася ця нотатка: чому одне поняття народилося двічі під двома назвами — «стратегія» в об'єктному світі та «політика» в шаблонному — і чому досвідчений погляд бачить у них одне.

Відповідь у тому, що **обидві назви іменують ту саму абстракцію — «взаємозамінний шматок поведінки, підставлений у сталий контекст», — і різняться лише механізмом та часом підстановки, а не суттю**. Постав їх поряд:

```
                     стратегія (GoF)         політика (policy-based)
поведінка — це …     об'єкт                  тип
підставляється …     через поле/посилання    через параметр шаблону
коли вибір …         під час роботи          під час компіляції
ціна …               віртуальний виклик      нуль у рантаймі
можна змінити …      так, на льоту           ні, тип фіксований
спільне …            сталий контекст + підставна взаємозамінна поведінка
```

Останній рядок і є розгадкою: **спільне переважує відмінне**. І там, і там є контекст, який не робить роботу власним тілом, а делегує її окремій, названій, взаємозамінній поведінці за спільним контрактом. «Рантайм-об'єкт» проти «компайл-тайм-типу» — це деталь **реалізації тієї самої думки** на різних поверхах мови. Тому ті самі слова — `DiscountPolicy`, `NoDiscount`, `VipDiscount` — однаково природно звучать і для GoF-стратегії, і для політики: вони позначають не механізм, а **роль** — «ось сімейство взаємозамінних правил».

Через це в реальному коді назви «стратегія» й «політика» гуляють майже як синоніми, і кожна ще й зливається з третім іменем — **функція вищого порядку**. Коли ти пишеш `array.sort(порівнювач)`, ти передаєш стратегію функцією. Коли пишеш `Order<VipDiscount>`, ти передаєш стратегію типом. Коли пишеш `order.setPolicy(new VipDiscount())`, ти передаєш стратегію об'єктом. Три різні руки — одна думка, з якої ми й почали: **спосіб щось зробити — це окрема річ, яку носять і підставляють.**

Тож підсумок історії такий. Стратегія не «винайдена» — вона багато разів **перевідкрита**. Її знали як передавану функцію в Lisp кінця 1950-х. Її незграбно, без замикань, тримали на вказівнику функції в C. Її назвали й окреслили як патерн у GoF 1994-го. Її підняли на етап компіляції як політики в C++ Александреску 2001-го. І щоразу під новою назвою жила та сама проста, потужна ідея, варта того, щоб побачити її крізь усі обличчя: **сталий контекст плюс взаємозамінний змінний алгоритм**. Хто цю ідею бачить, той упізнає стратегію там, де інші бачать просто «ще один параметр функції» чи «ще один шаблон».
