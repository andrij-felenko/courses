Уяви замовлення в інтернет-крамниці. Спершу воно **нове**: його можна оплатити або скасувати, але відправити — ще ні, гроші ж не прийшли. Потім **оплачене**: тепер його можна відправити чи повернути гроші, а «оплатити» вдруге — безглуздо. Потім **відправлене**: скасувати вже пізно, лишається хіба оформити повернення. Один і той самий об'єкт, ті самі методи — `pay()`, `ship()`, `cancel()` — але **що кожен із них робить (і чи робить узагалі) залежить від того, у якій фазі життя об'єкт зараз перебуває**.

Найпряміший спосіб це записати — завести поле `state` і в кожному методі питати його наново:

```ts
class Order {
  state: "new" | "paid" | "shipped" = "new";

  pay() {
    if (this.state === "new") { /* провести оплату */ this.state = "paid"; }
    else if (this.state === "paid") throw new Error("уже оплачено");
    else if (this.state === "shipped") throw new Error("надто пізно платити");
  }
  ship() {
    if (this.state === "new") throw new Error("спершу оплатіть");
    else if (this.state === "paid") { /* відвантажити */ this.state = "shipped"; }
    else if (this.state === "shipped") throw new Error("уже відправлено");
  }
  // те саме розгалуження ще й у cancel(), і в refund(), і в кожному новому методі…
}
```

Поки станів два-три, це терпимо. Але придивись, що тут насправді коїться: **одне й те саме розгалуження `if state == …` розмазане по всіх методах**. Логіка одного стану «нове» не зібрана в жодному місці — вона розсипана по гілках `pay`, `ship`, `cancel`, `refund`. А тепер додаймо стан «повернуто» або «на утриманні платежу» — і доведеться повернутися в **кожен** метод і вписати туди новий `case`. Пропустиш один — дістанеш не помилку компіляції, а тихий баг: у новому стані якийсь метод поведеться так, наче стану й не було.

Патерн **Стан (англ. *State*)** прибирає рівно цей біль. Ідея — коротка й сильна: **зроби кожен стан окремим об'єктом, а сам об'єкт хай делегує роботу тому стану, у якому зараз перебуває**. Розберімося, чому це вимикає розгалуження, як воно перетворює об'єкт на керовану машину, і де ця машина стає зайвою вагою.

## Об'єкт замість прапорця

Корінь усього безладу вище — в тому, що стан представлений **даними** (рядок чи число в полі), а поведінка, що від нього залежить, лежить **окремо**, у методах. Тому кожен метод змушений щоразу зводити дані назад до поведінки: «а, стан `paid` — значить тут роби ось так». Це зведення й повторюється в кожній гілці.

Патерн Стан робить один розворот: він представляє стан не даними, а **об'єктом із поведінкою**. Замість поля-рядка `"paid"` власник тримає посилання на об'єкт `PaidState`, який **сам уміє** `pay`, `ship`, `cancel`. Тоді метод власника вже нічого не питає — він просто **перекладає виклик** на поточний об'єкт-стан:

```ts
class Order {
  private state: OrderState = new NewState();
  setState(s: OrderState) { this.state = s; }

  pay()    { this.state.pay(this); }     // жодного if — просто делегуємо
  ship()   { this.state.ship(this); }
  cancel() { this.state.cancel(this); }
}
```

Ось у чому фокус: розгалуження **не зникло**, воно **розчинилося в поліморфізмі**. Раніше `switch(state)` вибирав гілку під час виконання методу; тепер той самий вибір робить механізм [динамічного зв'язування](book:programming/polymorphism) — виклик `this.state.pay()` сам піде в `NewState.pay` чи `PaidState.pay` залежно від того, який об'єкт зараз у полі. Об'єкт-стан **і є** та гілка, тільки винесена в окремий клас. Розгалуження за станом стало вибором реалізації за типом — а це вже не наш клопіт, це робить рантайм.

> 🔧 **Навіщо це.** Головний практичний виграш — уся поведінка одного стану **зібрана в одному місці**. Хочеш зрозуміти, що можна робити з оплаченим замовленням, — відкриваєш клас `PaidState` і бачиш там `pay`, `ship`, `cancel` поруч, а не полюєш за гілками `case "paid"` по п'ятьох методах. А коли з'являється новий стан, ти **дописуєш новий клас збоку** й ніде не чіпаєш старі — це прямий [принцип відкритості-закритості](book:programming/open-closed) в дії. Пропустити гілку теж ніде: якщо стан має реагувати на подію, він **зобов'язаний** мати відповідний метод, інакше код не збереться.

![Ліворуч — розгалуження за станом: методи pay, ship, cancel, кожен із власним switch за станом, і біда в тому, що новий стан змушує правити кожен метод. Праворуч — об'єкт на кожен стан: New, Paid, Shipped, кожен зі своїми pay, ship, cancel зібраними в ньому; новий стан додається новим класом, старі не чіпаються](img/switch-vs-objects.svg)

*Та сама поведінка, два способи її розкласти. Ліворуч логіка одного стану розсипана по гілках усіх методів; праворуч вона зібрана в об'єкті стану. Розгалуження не зникло — воно переїхало з `switch` у вибір типу, який робить поліморфізм.*

## Хто переводить у наступний стан

Лишилося головне питання, без якого патерн — половина: **хто і коли міняє поточний стан**. Бо статичного набору об'єктів мало; уся суть у тому, що замовлення **рухається** з фази у фазу.

Тут патерн Стан робить свій найхарактерніший хід: **перехід — це теж обов'язок стану**. Кожен об'єкт-стан не лише знає, як реагувати на події, а й **знає, у який стан перевести власника** після успішної дії. Оплата в стані «нове» — це не просто «провести гроші», а ще й «переставити власника в `PaidState`»:

:::tabs
```ts
interface OrderState {
  pay(order: Order): void;
  ship(order: Order): void;
}

class NewState implements OrderState {
  pay(order: Order) {
    // ...провести оплату...
    order.setState(new PaidState());   // стан САМ переводить власника далі
  }
  ship(order: Order) {
    throw new Error("спершу оплатіть");  // у цьому стані відправляти не можна
  }
}

class PaidState implements OrderState {
  pay(order: Order)  { throw new Error("уже оплачено"); }
  ship(order: Order) {
    // ...відвантажити...
    order.setState(new ShippedState());
  }
}

class ShippedState implements OrderState {
  pay(order: Order)  { throw new Error("надто пізно"); }
  ship(order: Order) { throw new Error("уже відправлено"); }
}
```
```py
from __future__ import annotations
from typing import Protocol

class OrderState(Protocol):
    def pay(self, order: "Order") -> None: ...
    def ship(self, order: "Order") -> None: ...

class NewState:
    def pay(self, order: "Order") -> None:
        # ...провести оплату...
        order.set_state(PaidState())     # стан САМ переводить власника далі
    def ship(self, order: "Order") -> None:
        raise RuntimeError("спершу оплатіть")  # у цьому стані відправляти не можна

class PaidState:
    def pay(self, order: "Order") -> None:
        raise RuntimeError("уже оплачено")
    def ship(self, order: "Order") -> None:
        # ...відвантажити...
        order.set_state(ShippedState())

class ShippedState:
    def pay(self, order: "Order") -> None:
        raise RuntimeError("надто пізно")
    def ship(self, order: "Order") -> None:
        raise RuntimeError("уже відправлено")
```
:::

Придивись, що це дає. Правило «з оплаченого можна лише відправити, а платити знову — ні» тепер **живе цілком усередині `PaidState`** — і дозволена дія, і заборонена, і те, куди вона веде. Уся таблиця дозволених переходів розкладена по класах: щоб дізнатися, куди можна з певного стану, ти читаєш **один** клас, а не збираєш картину з розкиданих `if`. Заборонений перехід — це метод, що кидає помилку; дозволений — метод, що робить дію й переставляє стан.

Хто саме кличе `setState` — питання смаку: інколи це роблять самі стани (як вище), інколи власник або окремий «контекст», що дивиться на результат. Але суть незмінна: **набір допустимих переходів перестає бути купою розсипаних умов і стає явною, читаною структурою**.

> 🔧 **Навіщо це.** Коли переходи зібрані в станах, з'являється несподіваний бонус: **неможливі переходи стає важко зробити випадково**. У версії з рядком-прапорцем ніщо не заважало десь у коді написати `order.state = "shipped"` просто так, перескочивши оплату. У версії з об'єктами єдиний спосіб опинитися в `ShippedState` — пройти через `PaidState.ship()`, бо тільки він цей об'єкт створює. Правила переходів захищають самі себе — не документацією, а структурою коду.

## Це скінченний автомат, поданий об'єктами

Якщо намалювати те, що ми щойно зібрали, вийде до болю знайома картинка: кружечки-стани й підписані стрілки-події між ними.

![Три стани документа кружечками в ряд: Чернетка, На розгляді, Опубліковано. Стрілка «надіслати» веде від Чернетки до На розгляді, «схвалити» — далі до Опубліковано. Червона дуга «відхилити» повертає з На розгляді назад у Чернетку. Сірий підпис показує, що зміна опублікованого знову веде на розгляд](img/transitions.svg)

*Стани як вузли, події як підписані переходи. Це діаграма скінченного автомата — і патерн Стан є її прямим утіленням у коді: кожен вузол стає класом, кожна стрілка — методом, що переставляє поточний стан.*

Це не випадкова схожість. Патерн Стан — **об'єктне втілення скінченного автомата (англ. *finite-state machine*)**: математичної моделі, де система будь-якої миті перебуває рівно в одному зі скінченного набору станів, реагує на події по-різному залежно від стану й переходить між станами за наперед визначеними правилами. Автомати старші за об'єктне програмування на десятиліття, і в них тисячі застосувань — від розбору тексту до протоколів зв'язку. Патерн Стан бере цю модель і кладе на об'єкти майже один-в-один: **вузол автомата стає класом, стрілка переходу — рядком коду, що переставляє поточний стан**. Звідки взялася сама ідея автомата, як вона доросла від таблиць переходів до діаграм і як зрештою переселилася в об'єкти — розказано в [нотатці про народження машини станів](book:programming/state/hist-fsm-to-state.md).

Через цю рідню патерн Стан і сусідні йому теми часто плутають. Варто розрізняти рівні. **Скінченний автомат** — це математична модель, байдужа до мови й стилю. [Машина станів](book:programming/state-machine) як тема — про те, як цю модель узагалі реалізують: таблицею переходів, великим `switch`, бібліотекою чи об'єктами. Патерн Стан — **лише один із цих способів реалізації**, той, що подає автомат об'єктами. Тож коли автомат маленький і навряд чи розростеться, ніхто не зобов'язує городити класи: чесний `switch` за станом — теж законна машина станів, просто інша її форма.

> 🔧 **Навіщо це.** Розпізнати в задачі автомат — половина справи. Щойно ти можеш намалювати життя об'єкта кружечками й стрілками (замовлення, TCP-з'єднання, програвач, заявка на відпустку, автомат світлофора), у тебе вже є **точна специфікація** поведінки: список станів і таблиця дозволених переходів. Далі лишається технічне рішення — покласти цей автомат у `switch` чи в об'єкти-стани. Патерн Стан — це відповідь «в об'єкти», доречна, коли станів багато, у кожного багата поведінка, і набір станів житиме довго й ростиме.

## Стан і Стратегія: той самий кістяк, протилежний намір

Є патерн, з яким Стан плутають частіше за будь-який інший, — [Стратегія](book:programming/strategy). І не дарма: якщо намалювати їхні структури, вони **збігаються майже буква в букву**. І там, і там є «контекст», що тримає посилання на об'єкт за спільним інтерфейсом і делегує йому роботу; і там, і там цей об'єкт можна підмінити іншою реалізацією. На UML-діаграмі їх не відрізнити.

Різниця — **не в структурі, а в намірі**, і вона глибока.

![Дві однакові за структурою колонки: ліворуч Стратегія, праворуч Стан. Обидві мають Контекст, що тримає поле, і три взаємозамінні реалізації під ним. Але внизу відмінність: у Стратегії поле ставить клієнт зовні один раз, реалізації одна про одну не знають; у Стані поле перемикають самі стани на льоту, і кожен стан знає наступний](img/state-vs-strategy.svg)

*Однаковий кістяк, різна суть. Стратегія — це «як робити одну незмінну справу», обрана зовні й зазвичай на весь час. Стан — це «у якій фазі життя об'єкт», і фаза змінюється сама, зсередини, а стани знають одне про одного.*

Розгорнімо ці дві відмінності, бо вони й вирішують, який патерн перед тобою.

**Хто ставить об'єкт у поле.** У Стратегії реалізацію обирає **клієнт іззовні** й зазвичай **один раз**: сказав «сортуй швидким сортуванням» чи «плати через PayPal» — і об'єкт до кінця роботи такий. У Стані власника перемикають **самі стани зсередини**, у відповідь на події, **багато разів** за життя об'єкта: замовлення саме проходить `new → paid → shipped`, ніхто ззовні цей маршрут не задає покроково.

**Чи знають реалізації одна про одну.** Стратегії **взаємно сліпі**: `QuickSort` гадки не має про існування `MergeSort`, вони просто дві незалежні відповіді на одне питання. Стани ж **знають своїх сусідів**: `PaidState` мусить знати, що після відправлення настає `ShippedState`, — інакше він не зможе зробити перехід. Стани сплетені в граф; стратегії лежать окремими, не пов'язаними варіантами.

Звідси проста перевірка. Спитай: «ці об'єкти — **різні способи зробити одне й те саме**, обрані зовні?» — тоді це Стратегія. Чи «це **фази життя одного об'єкта**, що самі переходять одна в одну?» — тоді це Стан. Однакова механіка «підстав об'єкт за інтерфейсом» обслуговує дві зовсім різні думки.

## Коли Стан НЕ потрібен

Тепер найважливіше — межа, за якою патерн із ліків стає хворобою. Стан не безкоштовний: за зібрану поведінку й безпечні переходи ти платиш **вибухом класів**. Три стани — три класи плюс інтерфейс; десять станів — десять класів. Для об'єкта з двома простими фазами й одним-двома методами це відверто задорого: чесний `switch` за прапорцем там коротший, ясніший і не змушує стрибати по десятку файлів, щоб простежити один сценарій.

Орієнтир простий і випливає з самих сил, що патерн погоджує. Стан виправдовує себе, коли збігаються **всі три** умови: станів **багато** (щоб `switch` уже став громіздким і крихким); у кожного стану **багата, різна поведінка** (щоб було що збирати в клас); набір станів **житиме довго й ростиме** (щоб окупилася легкість додавати нові класом збоку). Немає хоча б однієї — і патерн додає ваги більше, ніж знімає. Два стани, що майже нічим не відрізняються, у клас виносити нема сенсу; автомат, який точно не зміниться, спокійно живе у `switch`.

Ще одна тонкість — **де тримати об'єкти-стани**. Часто стан не має власних даних (уся змінна інформація — у власника), і тоді щоразу створювати `new PaidState()` марнотратно: логічніше зробити стани спільними незмінними об'єктами й перевикористовувати їх — по одному екземпляру на стан на всю програму. Це не окремий патерн, а звичайна економія, але про неї легко забути й плодити однакові об'єкти на порожньому місці.

І головне правило, спільне для всіх патернів: не питай «чи впхнути сюди Стан?», а спитай «**чи є тут автомат?**» — чи справді об'єкт живе фазами, між якими ходить за правилами. Є автомат і він великий та живучий — Стан збере його в чисту, розширювану форму. Немає автомата, а є проста розвилка на два випадки — напиши `if` і не турбуй каталог. Патерн, притягнутий туди, де немає його сил, шкодить рівно тим, чим мав би допомогти: додає рівнів непрямості, не додавши ясності.

Повний робочий автомат — з таблицею переходів, обробкою заборонених подій, перевикористанням станів і поглядом на те, як росте складність із додаванням станів, — зібрано в [окремому розборі коду](book:programming/state/proj-order-state-machine.md).
