# 🧮 Математика розмірування пулу

Пул ставить три числові питання, на які словами відповісти не можна. Наскільки дорогим має бути народження об'єкта, щоб повторне використання окупилося? Скільки об'єктів тримати? І скільки запасу додати понад цей мінімум? На кожне є точна відповідь, і всі три ростуть з першопричин: з простої арифметики вартості, із закону про середню зайнятість і з ймовірності застати всі об'єкти зайнятими. Розберемо ці три машини по черзі, доведемо кожну формулу на очах, а не оголосимо готовою, і будемо весь час міряти на одному наскрізному прикладі — **пулі з'єднань із базою**, де народження (мережа, автентифікація) коштує десятки мілісекунд, а сам запит — частки.

## Break-even: скільки має коштувати народження

Почнімо з питання «а чи взагалі варто». Порахуймо вартість **одного використання** об'єкта у двох світах і подивимося, коли пул дешевший.

Без пулу кожне використання оплачує повний цикл: народити, попрацювати, знищити.

```
T_без = C_new + C_роб + C_free
```

З пулом один об'єкт народжується раз і служить **N** разів, перш ніж його викинуть. Складімо все, що коштує його життя: одне народження, одна смерть і N обертів «узяти з полиці — скинути стан — попрацювати — повернути».

```
за все життя об'єкта:  C_new + C_free + N·(C_acq + C_reset + C_rel + C_роб)
```

Поділивши на N використань, дістанемо вартість **одного** з них під пулом. Народження і смерть діляться на N — вони **розмазуються** по всіх обертах:

```
T_пул = C_acq + C_reset + C_rel + C_роб + (C_new + C_free)/N
         └──── службова робота пулу ────┘  └ народження-смерть, поділені на N ┘
```

Розшифруймо доданки, бо в них уся суть. **C_new** — дороге народження (рукостискання, звернення до ядра, читання диска): та сила, заради якої пул затівають. **C_free** — знищення (закрити сокет, віддати пам'ять). **C_acq, C_rel** — узяти з полиці й повернути: кілька дій із пам'яттю плюс, у багатопотоковому пулі, захоплення замка. **C_reset** — привести повернений об'єкт до чистого стану, бо він приходить із брудом попереднього. **C_роб** — корисна робота; вона однакова в обох світах, тож при порівнянні **скоротиться**.

Пул виграє, коли T_пул < T_без. Підставмо, викиньмо спільний C_роб і згорнімо позначення. Хай **B = C_new + C_free** — повна вартість одного циклу народження-і-смерті, а **V = C_acq + C_reset + C_rel** — службова вартість пулу на одне використання:

```
V + B/N  <  B
V        <  B·(1 − 1/N) = B·(N−1)/N
```

Ось нерівність break-even у повному вигляді — з тим самим B/N, що розмазує народження. З неї одразу видно дві межі.

**Межа великого N.** Хай об'єкт служить дуже довго (сотні, тисячі використань). Тоді B/N → 0, і нерівність спрощується до чистого порівняння:

```
V < B      ⟺      C_acq + C_reset + C_rel  <  C_new + C_free
```

У словах: **службова вартість пулу має бути меншою за вартість народити-і-знищити.** Прикметно, що при великому N сама вартість народження з нерівності **випадає** — лишається порівняння «полиця проти конструктора». Визначмо **виграш на одне використання**:

```
S = B − V = (C_new + C_free) − (C_acq + C_reset + C_rel)
```

Пул при великому N вартий рівно тоді, коли **S > 0**.

**Межа скінченного N — поріг окупності.** А тепер знайдімо точку, де пул саме починає вигравати. Прирівняймо T_пул = T_без, тобто V + B/N = B:

```
B/N = B − V = S      ⟹      N* = B / S
```

Ось поріг: об'єкт мусить послужити **більш ніж N\* = B/S разів**, аби пул окупив своє народження на цьому об'єкті. Якщо S ≤ 0, порога немає зовсім — пул не виграє за жодного N, бо навіть безкоштовне народження (B/N → 0) не рятує від того, що V вже більше за B.

### Найпідступніший доданок — C_reset

Тепер найтонше. Легко задивитися на величезне C_new з'єднання й вирішити «звісно, S додатне». Але придивімося, від чого S залежить найсильніше. Оскільки S лінійне за кожною вартістю, його чутливість до будь-якого доданка — це проста похідна:

```
∂S/∂C_new = +1        ∂S/∂C_free = +1
∂S/∂C_acq = −1        ∂S/∂C_reset = −1        ∂S/∂C_rel = −1
```

Кожна наносекунда, додана до **скидання**, прямо віднімається від виграшу — з тим самим важелем −1, з яким народження виграш **додає**. А що зазвичай C_new набагато більше за все інше, то з доброю точністю S ≈ C_new − C_reset, і весь сенс пулу тримається на **розриві між народженням і скиданням**. Виразімо цей розрив через одне число — частку, яку скидання становить від народження:

```
f = C_reset / C_new
```

Тоді S ≈ C_new·(1 − f), B ≈ C_new, і поріг окупності набуває напрочуд чистого вигляду:

```
N* = B/S ≈ C_new / [C_new·(1 − f)] = 1 / (1 − f)
```

Ось вона — чутливість, згорнута в одну формулу. Скільки разів об'єкт має послужити, щоб окупити народження, залежить **тільки** від того, яку частку народження коштує скидання:

```
f = 0     →  N* ≈ 1     скидання дармове — окупність із першого ж повторення
f = 0.5   →  N* ≈ 2     скидання = ½ народження — окупність за два
f = 0.9   →  N* ≈ 10    скидання = 0.9 народження — аж десять
f = 0.99  →  N* ≈ 100   скидання майже як народження — сотня
f → 1     →  N* → ∞     скидання = народження — пул не виграє НІКОЛИ
```

![Крива N* = 1/(1−f): скільки разів об'єкт має послужити, щоб пул окупив народження, залежно від того, яку частку народження коштує скидання. Ліворуч, при малому f, N* близький до одиниці — окупність майже миттєва. Праворуч, коли f наближається до одиниці (скидання дорожчає до вартості народження), крива стрімко злітає у вертикальну асимптоту: пул перестає вигравати за будь-якого числа повторень](img/break-even.svg)

*Виграш пулу тримається на розриві між дорогим народженням і дешевим скиданням. Коли скидання дорожчає до вартості народження (f → 1), поріг окупності злітає до нескінченності — об'єкт, чия єдина важка частина саме та, яку доводиться стирати, для пулу поганий кандидат, хоч би яким дорогим здавалося його народження.*

> 🔧 **Навіщо це.** Перш ніж заводити пул, оціни не C_new саме по собі, а **дріб f = C_reset/C_new**. Величезне народження з дорогим скиданням (f близьке до 1) означає, що ти не прибираєш роботу, а **переставляєш** її з конструктора в скидання — і платиш ще й за облік пулу згори. Пул любить об'єкти з великим народженням і **дешевим** скиданням: сокет, який досить перевідкрити стан сесії; буфер, який досить обнулити. Об'єкт, який щоб «очистити», доводиться майже наново будувати, до пулу непридатний.

Підставмо реальні числа з'єднання: C_new ≈ 30 мс, C_free ≈ 0.1 мс, C_acq ≈ C_rel ≈ 200 нс, C_reset ≈ 0.5 мс.

**Пул з'єднань: чи вартий і з якого повторення.**
```
B = 30.0 + 0.1        = 30.1 мс
V = 0.0002 + 0.5 + 0.0002 ≈ 0.5 мс
S = B − V             ≈ 29.6 мс          ← додатне, і величезне
f = C_reset/C_new = 0.5/30 ≈ 0.017
N* = B/S = 30.1/29.6 ≈ 1.02  (≈ 1/(1−0.017))   ← окупність уже з першого повторення
```

Скидання коштує якихось 1.7 % народження — розрив велетенський, і пул окупається на **першому ж** повторному використанні. А тепер протилежний полюс — дрібний об'єкт-значення у мові зі збиранням сміття, де народження майже дармове:

**Дрібна структура {x, y} у GC-мові.**
```
C_new = 20 нс   C_free = 0   C_acq = 50 нс   C_reset = 10 нс   C_rel = 50 нс
B = 20 нс       V = 110 нс
S = B − V = 20 − 110 = −90 нс           ← ВІД'ЄМНЕ
```

S від'ємне ще до будь-яких тонкощів: сама лише службова робота (замок на `acquire` дорожчий за все народження) вже програє. Порога окупності не існує — пул повільніший за будь-якого N. Ось чому дрібні об'єкти в керованій мові не пулять: не тому, що «мало заощадиш», а тому, що заощадження **від'ємне**.

Лишилося одне: пул платить наперед не за один об'єкт, а за цілий стартовий банк із P об'єктів — P·C_new одразу. Коли ця плата повертається? Кожне використання дає виграш S, тож після M використань накопичено M·S. Розігрів окупився, щойно

```
M·S > P·C_new      ⟹      M > P·C_new / S
```

Для з'єднань із P = 10: M > 10·30/29.6 ≈ **10 використань**. Тобто вже після десятка запитів цілий пул повністю окупив свій розігрів — а служитиме він мільйони. Розігрів дорогий лише на вигляд; при великому S він амортизується за лічені звернення.

## Закон Літтла: підлога, яку не обійти

Гаразд, S додатне, пул вартий. Скільки об'єктів тримати? Знизу розмір підпирає закон, що діє не лише для пулів, а для **будь-якої** системи, де щось надходить, обслуговується й іде: закон Літтла, L = λW. Він скаже, скільки об'єктів **у середньому** зайнято, і це буде підлога — менше тримати не можна.

Доведімо його — не повіримо, а побачимо, чому він мусить бути істинним. Доказ гарний тим, що майже не потребує припущень: він **траєкторний** (за однією реалізацією процесу, англ. *sample-path*), тобто рахує не ймовірності, а просто площу під однією конкретною картиною подій.

Уяви довгий проміжок часу [0, T]. Кожен запит **i** приходить у мить aᵢ, тримає позичений об'єкт Wᵢ секунд і відпускає його в мить dᵢ = aᵢ + Wᵢ. У будь-яку мить t якесь число об'єктів зайняте — назвемо його N(t) (це ті запити, що вже прийшли, але ще не відпустили). Тепер порахуймо одну-єдину величину — **площу зайнятості**, ∫₀ᵀ N(t) dt — **двома** різними способами.

**Спосіб перший, по вертикалях.** Площа під ступінчастою кривою N(t) — це, за означенням середнього, час T, помножений на середнє значення висоти:

```
∫₀ᵀ N(t) dt = T · (середнє N)  =  T · L
```

де L — середня кількість одночасно зайнятих об'єктів (те, що ми й хочемо знайти).

**Спосіб другий, по смугах.** Та сама площа — це сума внесків окремих запитів. Кожен запит i, поки тримає об'єкт, додає рівно 1 до N(t) протягом свого відрізка [aᵢ, dᵢ]. Отже, його внесок у площу — прямокутна смуга висотою 1 і шириною Wᵢ, тобто просто Wᵢ. Складімо всі смуги:

```
∫₀ᵀ N(t) dt = Σᵢ Wᵢ  =  (число запитів) · (середнє W)  =  n · W
```

Одна площа — два записи. Прирівняймо їх і згадаймо, що число запитів за час T дорівнює темпу надходження, помноженому на T: n = λ·T.

```
T · L = n · W = (λ·T) · W        ⟹        L = λ · W
```

![Доказ закону Літтла «порахуй площу двома способами». Кожен запит зображено горизонтальною смугою від моменту приходу до моменту повернення об'єкта; ширина смуги — час утримання Wᵢ. Вертикальна лінія у довільну мить t перетинає стільки смуг, скільки об'єктів тоді зайнято — це N(t). Площу всіх смуг можна порахувати вшир (сума часів утримання, Σ Wᵢ) або ввись (інтеграл зайнятості, який дорівнює L·T). Прирівнявши два підрахунки, дістаємо L = λW](img/little-area.svg)

*Та сама площа зайнятості, порахована по смугах (Σ Wᵢ = сума часів утримання) і по вертикалях (∫ N(t) dt = L·T), дає рівність, з якої випадає L = λW. Ніде не знадобилося, як саме розподілені надходження — тому закон і не залежить від форми потоку.*

Ось і весь закон: **середня кількість одночасно зайнятих об'єктів дорівнює темпу надходження, помноженому на час утримання.**

```
L = λ · W

L — середня кількість «в роботі» (зайнятих об'єктів)
λ — темп надходження запитів (за секунду)
W — час, який кожен тримає об'єкт (секунди)
```

Прикметне те, чого в доказі **не** було. Ми ніде не припустили, як розподілені надходження — рівномірно чи ривками, за яким законом. Площу можна порахувати двома способами за **будь-якої** форми потоку. Тому L = λW **не залежить від розподілу** — це його головна сила й причина, чому на нього можна спиратися, не знаючи нічого про статистику навантаження.

Що саме потрібно для строгості? Лише щоб три середні **існували й були скінченні**: темп λ = lim A(T)/T, середнє утримання W = lim (1/n)·Σ Wᵢ і середня зайнятість L = lim (1/T)·∫N. За цих умов рівність точна. Історично першим строгий доказ дав Джон Літтл 1961 року, і йому знадобилися сильніші припущення — **строга стаціонарність** процесів і **метрична транзитивність** (ергодичність) потоку надходжень із ненульовим середнім. Пізніше Шейлер Стідем (1974, «A Last Word on L = λW») показав, що суто траєкторний доказ — той, що ми навели, — не потребує **жодної** ймовірності: досить, щоб λ і W існували як границі. А саму рівність у конкретних задачах ужив ще раніше Філіп Морс (1958), до того, як з'явився доказ. Це усталений факт, а не спірна атрибуція: формулу вживав Морс, строго довів Літтл, узагальнив на траєкторії Стідем.

Порахуймо підлогу для нашого пулу.

**Підлога пулу з'єднань за законом Літтла.**
```
λ = 500 запитів/с      W = 10 мс = 0.010 с
L = λ·W = 500 · 0.010 = 5 з'єднань зайнято В СЕРЕДНЬОМУ
```

Отже, пул із менш ніж п'яти з'єднань **завжди насичений**: у середньому потрібно п'ять, а їх менше — комусь постійно бракує. Насправді підлога навіть жорсткіша, ніж «у середньому». Щоб пул **встигав** за потоком, число об'єктів c мусить перевищувати навантаження: якщо c ≤ λW, черга на вході росте без упину (завантаження ρ = λW/c ≥ 1 — система нестабільна). Тож c > λW = 5 — це не побажання, а **умова стабільності**. Підлога і середня зайнятість тут збігаються: обидві дорівнюють λW.

Той самий λ·W розмірює й [пул потоків](book:programming/thread-pool): скільки потоків тримати — це темп надходження задач, помножений на середню тривалість задачі. Патерн один, змінюється лише те, що саме «зайняте».

Але L = λW дає **середнє**. А надходження [пуассонівські](book:math/poisson-process) — випадкові, без пам'яті, ривками; у піку сплеску одночасно зайнятих буде більше за п'ять. Пул рівно на п'ять насичений «упритул»: щойно два запити на мить збіглися понад середнє — комусь уже нема об'єкта. Тому понад підлогу потрібен **запас**. Скільки саме — на це середнього вже замало, тут потрібна ймовірність застати всі об'єкти зайнятими. Її дає формула Ерланга.

## Ерланг C: скільки запасу понад підлогу

Питання загострюється так: якщо в пулі **c** об'єктів, яка ймовірність, що новий запит застане **всі c зайнятими** й муситиме чекати? Це вже не про середнє, а про розподіл, тож задаймо модель випадковості. Вона класична й зветься **M/M/c**:

- надходження — [пуассонівський потік](book:math/poisson-process) із темпом λ (мономи «M» — від *Markovian*, без пам'яті);
- час утримання — випадковий, у середньому W = 1/μ (друге «M»);
- **c** об'єктів-серверів (це наш банк — скінченний, рівно розмір пулу);
- усі зайняті — запит **чекає** в черзі (політика «блокувати й чекати»).

Вводять одну зручну величину — **пропоноване навантаження** (англ. *offered load*), у безрозмірних одиницях-**ерлангах**:

```
a = λ/μ = λ·W
```

Придивися: a = λW — це **той самий** λW, підлога Літтла. Пропоноване навантаження і є середня зайнятість. Тепер запас над підлогою — це запас c над a.

### Виведення з ланцюга народження-загибелі

Стан системи — число запитів у ній, n (зайняті об'єкти плюс ті, що чекають). Це ланцюг **народження-загибелі**: угору веде надходження, униз — завершення роботи.

- **Угору** (прийшов запит): темп λ, за будь-якого n.
- **Униз** (звільнився об'єкт): якщо зайнято n ≤ c об'єктів, кожен може завершитися з темпом μ, разом **nμ**; якщо всі c зайняті (n ≥ c), завершується з темпом **cμ** — більше за c одночасно все одно не обслужиш.

Для ланцюга народження-загибелі рівновага на межі між станами n−1 і n проста: потік угору = потік униз.

```
λ·p_{n−1} = (темп униз у стані n)·p_n
```

Розв'яжімо покроково. Поки не всі зайняті (n ≤ c), темп униз nμ:

```
p_n = (λ / (nμ))·p_{n−1}   ⟹   p_n = p₀ · aⁿ / n!        (n ≤ c)
```

Коли всі зайняті (n ≥ c), темп униз сталий cμ, і кожен наступний стан у ρ = a/c разів рідший:

```
p_n = (λ / (cμ))·p_{n−1} = ρ·p_{n−1}   ⟹   p_n = p₀ · (a^c/c!)·ρ^{n−c}     (n ≥ c)
```

Лишилося знайти p₀ з умови, що всі ймовірності дають одиницю. Розіб'ємо суму на «не всі зайняті» (n від 0 до c−1) і «черга» (n від c і далі — це геометрична прогресія зі знаменником ρ, вона збігається лише за ρ < 1, тобто c > a):

```
1/p₀ = Σ_{k=0}^{c−1} aᵏ/k!  +  (a^c/c!)·Σ_{m=0}^∞ ρ^m
     = Σ_{k=0}^{c−1} aᵏ/k!  +  (a^c/c!)/(1−ρ)
```

Ймовірність очікування — це ймовірність застати систему в стані n ≥ c (усі зайняті). Складімо «хвіст»:

```
P(очікування) = Σ_{n≥c} p_n = p₀ · (a^c/c!)/(1−ρ)
```

Підставивши p₀, дістаємо **формулу Ерланга C** — ймовірність, що запит муситиме чекати на вільний об'єкт:

```
                   (a^c / c!) / (1 − ρ)
C(c, a) = ─────────────────────────────────────────── ,    ρ = a/c
           Σ_{k=0}^{c−1} aᵏ/k!  +  (a^c/c!)/(1−ρ)
```

І одразу — середній час очікування в черзі. Тут закон Літтла спрацьовує вдруге, тепер для самої **черги**: середня довжина черги L_q = λ·W_q. Порахувавши L_q = Σ_{n≥c}(n−c)·p_n = C(c,a)·ρ/(1−ρ) і поділивши на λ, дістаємо напрочуд просте:

```
W_q = C(c, a) · W / (c − a)
```

Час очікування — це ймовірність очікування, помножена на час утримання й поділена на **запас** c − a. Що більший запас над підлогою, то коротша черга — і не лінійно, а через різке падіння самого C(c, a).

### Як із цього обирають запас

Тепер практика. У нас a = λW = 5. Обчислімо C(c, 5) і W_q для кількох розмірів (обчислення — за формулою вище; зручно рекурсією Ерланга):

```
 c    ρ=a/c   P(очікування)   W_q (при W=10 мс)
─────────────────────────────────────────────────
 5    1.000     → 1  (∞)       ∞     нестабільно: c не більший за підлогу
 6    0.833     0.588          5.9 мс
 7    0.714     0.324          1.6 мс
 8    0.625     0.167          0.56 мс
 9    0.556     0.081          0.20 мс
10    0.500     0.036          0.072 мс
11    0.455     0.015          0.025 мс
12    0.417     0.006          0.008 мс
```

![Ймовірність очікування за формулою Ерланга C залежно від розміру пулу c при пропонованому навантаженні a = λW = 5. Крива починається біля одиниці на самій підлозі (c = 5, де завантаження ρ = 1 і система нестабільна) і круто падає з кожним доданим об'єктом. Горизонтальна лінія позначає ціль «не більш ніж 10 % очікувань»: її перетинає розмір c = 9 (близько 8 %), з запасом чотири об'єкти понад підлогу](img/erlang-c.svg)

*Кожен об'єкт, доданий понад підлогу a = 5, різко збиває ймовірність очікування: з 59 % при c = 6 до 8 % при c = 9. Так із формули й обирають запас — беруть найменший c, за якого ймовірність очікування (чи середній час W_q) падає під поставлену ціль.*

Звідси й процедура вибору. Постав ціль якості — скажімо, «не більш ніж 10 % запитів чекають» або «середнє очікування під 1 мс» — і візьми **найменший** c, за якого крива падає під ціль. Для нашого навантаження ціль P(очікування) ≤ 10 % дає c = 9 (запас 4 понад підлогу 5); ціль W_q ≤ 1 мс — уже c = 8. Груба інженерна прикидка «тримай завантаження ρ = a/c нижче 0.7» дала б c ≈ 8 (ρ = 0.625) — вона недалеко, але Ерланг C дає точне число замість здогаду.

### Чому запас росте як √a, а не пропорційно

Тепер найглибше й найкорисніше в цьому апараті. Запас, потрібний для сталої якості, росте **не пропорційно** навантаженню, а як його **корінь**. Це відоме як **правило кореневого запасу** (англ. *square-root staffing*): щоб утримати ймовірність очікування приблизно сталою, беруть

```
c ≈ a + β·√a
```

де β — коефіцієнт якості (більший β → менше очікувань). Звідки корінь? З того самого, звідки корінь скрізь у статистиці сум. Число надходжень за час утримання — це сума багатьох незалежних випадкових подій, а коливання такої суми, за [центральною граничною логікою](book:math/central-limit), масштабуються як **√(середнього)**, тобто як √a. Отже, типовий «перебір» над середнім навантаженням має розмір близько √a — і саме такого порядку запас його покриває. Асимптотично точним це правило зробили Шломо Галфін і Ворд Вітт (1981); нам важливий сам масштаб.

Наслідок — **економія на масштабі**, і він контрінтуїтивний. Порахуймо запас для сталого β ≈ 1.8 (та якість, що дала c = 9 при a = 5):

```
 a = λW    c ≈ a + 1.8·√a    запас c−a    запас у % від a
──────────────────────────────────────────────────────────
    5           ≈ 9              4             80 %
   20          ≈ 28              8             40 %
  100         ≈ 118             18             18 %
  500         ≈ 540             40              8 %
```

Що більший пул, то **менший відсоток** запасу йому треба. Маленький пул на п'ять об'єктів мусить тримати 80 % понад підлогу, щоб не захлинатися; великий на сотні — лічені відсотки. Ось чому один спільний пул майже завжди ефективніший за багато дрібних, розкиданих: злиття навантажень дає кореневу економію. Ця вигода, щоправда, обмежена зверху — про стелю далі.

Історична примітка, варта згадки. Формулу вивів данський математик **Аґнер Краруп Ерланг** (Agner Krarup Erlang) ще 1917 року для Копенгагенської телефонної компанії, у праці про ймовірності на автоматичних станціях — задача там буквально та сама: випадкові дзвінки, скінченний банк ліній, черга, коли всі зайняті. Він дав дві формули: **Ерланга C** — для системи з чергою (наш «блокувати й чекати»), і **Ерланга B** — для системи втрат, де зайнятість означає відмову без черги (це вже наш «відмовити», коли пул повний). Це усталений, перевірений факт теорії черг.

> 🔧 **Навіщо це.** Розмір пулу не вгадують круглим числом — його рахують у два кроки. Спершу підлога λW (закон Літтла): менше — вічна черга на вході. Тоді запас понад неї (Ерланг C): бери найменший c, за якого ймовірність очікування падає під твою ціль. І пам'ятай кореневе правило: подвоїш навантаження — запас треба збільшити не вдвічі, а лише в √2 ≈ 1.4 раза. Якщо ти не знаєш свого λ і W, то й розміру пулу не знаєш — будь-яке число буде здогадом.

## Двобічний оптимум: підлога проти стелі

Досі ми тиснули розмір **знизу**: не менше за λW плюс кореневий запас. Природно подумати, що більше — то безпечніше. Це помилка, і дорога. Понад певну межу кожен доданий об'єкт не прискорює, а **сповільнює** систему. У розміру пулу є й **стеля**, і оптимум затиснутий між двома силами.

Причина стелі в тому, що пул майже ніколи не самотній: він годує **низхідний ресурс** із власною межею паралельності. Пул з'єднань живить базу, а база на K ядрах по-справжньому виконує водночас близько K запитів. Даси їй сто з'єднань, що всі разом шлють запити, — виконуватимуться однаково ~K, а решта стануть у чергу вже **всередині** бази, де тепер юрмляться сто робочих контекстів: вони перемикаються, б'ються за внутрішні замки, витісняють одне одному кеш. Корисна пропускна здатність не росте понад K — вона **падає**, бо координація дорожчає з числом претендентів.

Формалізуймо це. Найточніша модель — **універсальний закон масштабованості** (Neil Gunther): відносна пропускна здатність від числа паралельних робітників c

```
X(c) = c / (1 + σ·(c−1) + κ·c·(c−1))
```

має три доданки в знаменнику. Одиниця — ідеальне лінійне зростання. **σ** (contention) — частка роботи, серіалізована спільним ресурсом (черга за замком): вона обмежує зростання, як у законі Амдала. А **κ** (coherency) — вартість тримати дані узгодженими між робітниками; вона росте як **c²** (кожна пара робітників має узгоджуватися), і саме цей квадратичний доданок урешті пересилює чисельник. Тому X(c) не виходить на плато, а має **пік** і далі **спадає** — режим, що зветься зворотним (англ. *retrograde*). Пік — там, де похідна нуль:

```
c* = √((1 − σ) / κ)
```

Ось стеля в замкненому вигляді: понад c* більше робітників дають **менше** корисної роботи. Емпірично для бази цей злам лягає біля невеликого числа — практики PostgreSQL зводять його до приблизного «(ядра·2) + діючі диски», і для сервера на 4 ядра з одним диском виходить ≈ 10 з'єднань, а не двісті.

Складімо підлогу зі стелею — і в розміру пулу проступає **двобічний оптимум**, здорове вікно:

```
підлога:  c_min ≈ λW + β·√(λW)         (Літтл + Ерланг: менше — черга на вході)
стеля:    c_max ≈ √((1−σ)/κ) ≈ (ядра·2)+диски   (Gunther: більше — задуха бази)

здоровий пул існує ⟺  c_min ≤ c_max
```

І тут відкривається найглибший випадок. Що, як підлога виходить **вища** за стелю, c_min > c_max? Це означає, що навантаження перевищує спроможність низхідного ресурсу — і **жоден** розмір пулу цього не полагодить. Треба більша база, а не більший пул: роздувши пул понад стелю, ти лише прискориш розплаву. Але й тут пул рятує — не швидкістю, а **видимістю**: тримаючи c на стелі, він перетворює тиху задуху бази на чесні, діагностовані чергу очікування й таймаути. Черга на вході в пул — не вада, а **захисний клапан**.

> 🔧 **Навіщо це.** Пул — це **дві машини в одній**. Він **кеш** (заплатив за народження раз, якщо S > 0) і **регулятор** (не дає існувати більш ніж c_max ресурсам водночас). Люди беруть пул заради першого, а рятує їх часто друге: обмежити паралельність бази стелею часто цінніше, ніж заощадити на рукостисканні. Розмір став **між** підлогою λW і стелею низхідного ресурсу — і жодного разу не «про запас, хай буде більше».

## Що з усього цього складається

Три питання — три формули, і всі три ми довели від першопричини, а не взяли на віру.

```
1. Чи варто пулити?     S = (C_new+C_free) − (C_acq+C_reset+C_rel) > 0
                        поріг окупності  N* = B/S ≈ 1/(1−f),  f = C_reset/C_new
                        (дрібний GC-об'єкт: S < 0 — не пулити ніколи)

2. Скільки щонайменше?  підлога  c_min ≈ λW           (закон Літтла, доказ площею)
                        + кореневий запас β·√(λW)     (Ерланг C, вибір під ціль)

3. Не забагато?         стеля  c_max ≈ √((1−σ)/κ)     (закон масштабованості)
                        ≈ (ядра·2)+диски для бази
```

За цими числами й видно суть пулу до кінця. Він не контейнер об'єктів, а машина, що тримає ресурс на **обраному, обмеженому** рівні паралельності: платить за народження раз — якщо арифметика S це виправдовує; ставить нижню межу на підлозі λW, яку диктує закон Літтла; і не дає світові створити більше, ніж стеля, яку витримає низхідний ресурс. Зрозумій обидва краї — і знатимеш точно, коли пул правильний інструмент, а коли лише дорогий спосіб воювати з власним середовищем.
