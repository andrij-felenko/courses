# ⚙️ Безпечний пул об'єктів, зібраний по цеглині

Мінімальний пул на кілька рядків показує ідею, але в бойовому коді він тебе зрадить: віддасть брудний об'єкт, повільно спорожніє через тих, хто забув повернути, і розсиплеться, щойно два потоки торкнуться його водночас. Тут ми зберемо пул, який **не зрадить**. Не одним махом — бо тоді не видно, за що відповідає кожен шматок, — а по цеглині: почнемо з голого кістяка й доростимо його рівно до того, що потрібно, щоб покласти в продакшн. На кожному кроці буде видно **яку конкретну біду** цей шматок закриває.

Домовимося про приклад наскрізь. Хай наш дорогий ресурс — **з'єднання з базою** (`Conn`): народжується повільно (мережа, автентифікація), працює швидко, і — важливо — може лишити по собі бруд: відкриту транзакцію, недочитану відповідь. Це найчесніший приклад, бо на ньому спрацьовують **усі** пастки одразу, а не лише деякі. Ресурс абстрагуємо за трьома методами: `open()` — дороге народження, `reset()` — привести до чистого стану, `is_alive()` — перевірити, чи він ще живий.

Складати будемо мовами загального стеку — пул об'єктів живе в бекендах, іграх, серверах, а не біля регістрів. Ідіому покажемо вкладками **Python** і **TypeScript**: обидві однаково природні для такого коду, і на контрасті видно, що механіка від мови не залежить. Наприкінці окремо додамо **C++**-обгортку — щоб показати, як та сама гарантія повернення в мові з детермінованими деструкторами робиться інакше й навіть надійніше.

## Крок 0. Інваріант, який тримає все

Перш ніж писати бодай рядок, назвемо **головний закон пулу** — умову, яку весь код існує, щоб не порушити. Звучить вона так:

```
Кожен об'єкт пулу в будь-яку мить перебуває РІВНО в одному з двох станів:
    free    — лежить на полиці, доступний до видачі
    in-use  — виданий назовні, ним хтось користується
Ніколи в обох. Ніколи в жодному.
```

Це і є **інваріант пулу**. Уся морока, яку ми зараз розберемо, зводиться до одного: не дати цьому інваріантові зламатися. Придивись, як кожна з відомих пасток — це насправді його порушення:

- Об'єкт **у жодному** стані (загубився між `in-use` і `free`) — це **витік**: ресурс числиться зайнятим, а насправді його ніхто не тримає.
- Об'єкт **в обох** станах водночас (лежить на полиці, але хтось ще пише крізь старе посилання) — це **зомбі**: два власники на один об'єкт.
- Об'єкт у `free`, але з чужим брудом усередині — формально інваріант станів цілий, та зламано **сусідній** інваріант: «на полиці лежить лише чистий об'єкт».

Тримай цю картину в голові, читаючи код далі. Кожна перевірка, кожен замок, кожен `finally` — це вартовий одного з цих інваріантів.

## Крок 1. Кістяк: acquire / release зі скиданням

Почнемо з найменшого, що вже **не бреше**: пул, який видає, приймає — і **скидає стан при поверненні**. Скидання ставимо в `release`, а не в `acquire`, свідомо: так на полиці **завжди** лежить чистий об'єкт, і будь-хто, хто зазирне в пул (діагностика, лічильники), бачить його в передбачуваному стані. Це зручніше й для налагодження.

:::tabs
```py
class Pool:
    def __init__(self, factory, size):
        self._factory = factory                 # як народити Conn: () -> Conn
        self._free = [factory() for _ in range(size)]   # заплатили наперед
        self._in_use = set()

    def acquire(self):
        conn = self._free.pop()                  # знімаємо з полиці
        self._in_use.add(conn)                   # → in-use
        return conn

    def release(self, conn):
        conn.reset()                             # ← стерти чужий стан ДО полиці
        self._in_use.discard(conn)               # більше не in-use
        self._free.append(conn)                  # → free, чистим

pool = Pool(factory=Conn.open, size=8)           # 8 дорогих з'єднань — раз
conn = pool.acquire()
conn.query("select 1")
pool.release(conn)                               # повернули чистим
```
```ts
class Pool<T> {
  private free: T[];
  private inUse = new Set<T>();

  constructor(
    private factory: () => T,                    // як народити Conn
    private reset: (obj: T) => void,             // як його скинути
    size: number,
  ) {
    this.free = Array.from({ length: size }, () => factory());  // наперед
  }

  acquire(): T {
    const obj = this.free.pop()!;                // знімаємо з полиці
    this.inUse.add(obj);                         // → in-use
    return obj;
  }

  release(obj: T): void {
    this.reset(obj);                             // ← стерти чужий стан ДО полиці
    this.inUse.delete(obj);                      // більше не in-use
    this.free.push(obj);                         // → free, чистим
  }
}

const pool = new Pool(() => Conn.open(), (c) => c.reset(), 8);
const conn = pool.acquire();
conn.query("select 1");
pool.release(conn);                              // повернули чистим
```
:::

Зверни увагу на дві дрібниці, що насправді не дрібниці.

Перше — **чому список, а не щось складніше**. Полиця вільних (`_free`) — це стек: беремо з кінця (`pop`), кладемо в кінець (`append`/`push`). І зняти, і покласти — це чіпання **одного кінця** масиву, тому обидві операції **O(1)**: не залежать від того, скільки об'єктів у пулі — вісім чи вісім тисяч. Це критично: пул кличуть на **кожен** запит, тож `acquire`/`release` мусять коштувати сталий, малий час, інакше сам пул стане тим вузьким місцем, від якого ми тікали. (Чому саме стек, а не черга, і що це міняє — за крок.)

Друге — **навіщо взагалі `_in_use`**, якщо для видачі досить `_free`? Формально для механіки видачі множина зайнятих не потрібна: бери з `_free`, повертай у `_free`. Але без неї пул **сліпий** — він не знає, що зараз назовні, скільки об'єктів загалом існує, чи не повертають йому чужий об'єкт. `_in_use` — це очі пулу; на ній триматимуться і лічильник розміру, і перевірка «свій-чужий» при поверненні, і виявлення зомбі. Зараз вона виглядає надлишковою; за три кроки стане незамінною.

> 🔧 **Навіщо це.** Порядок «`reset` перед полицею» — не косметика. Постав скидання в `acquire` (чистити при видачі) — і між поверненням та наступною видачею об'єкт лежить у пулі **брудним**. Якщо в цей проміжок хтось загляне в пул чи трапиться помилка — побачить чужий стан. Скидаючи при поверненні, ти робиш інваріант «на полиці лише чистий об'єкт» **завжди** істинним, а не «істинним аж до наступного acquire». Дешевша дисципліна коштує згодом дорогих годин над плаваючим багом.

Цей кістяк уже безпечний за станом об'єкта, але наївний у трьох інших місцях: він **не має межі** (полиця в конструкторі скінченна, та `acquire` порожню полицю не переживе), **не гарантує повернення** (забудеш `release` — витік), і **не переживе двох потоків**. Доростимо по черзі.

## Крок 2. Межа й політика вичерпання

`acquire` вище має мовчазну бомбу: `self._free.pop()` на порожньому списку — це помилка. А порожнім він стане, щойно назовні опиниться більше об'єктів, ніж ми створили. Отже, треба вирішити головне питання дизайну пулу: **що робити, коли всі об'єкти зайняті, а хтось просить ще?** Це і є **політика вичерпання (англ. *exhaustion policy*)**, і чесних відповідей рівно три.

**Політика A — рости до межі.** Тримаємо не фіксовану полицю, а **верхню межу** `max_size`. Поки створених об'єктів менше за межу — на порожній полиці народжуємо новий (одноразова дорога плата, але programа не стоїть). Дійшли межі — далі так робити не можна, і треба одну з наступних двох політик. Ця «лінива» межа краща за фіксовану: не платимо наперед за пік навантаження, якого може й не бути, але й не даємо ресурсу текти безмежно.

**Політика B — блокувати й чекати.** Усі зайняті, межу досягнуто — той, хто просить, **засинає**, доки хтось не поверне об'єкт. Це природний вибір для з'єднань і потоків: якщо всі двадцять з'єднань бази зайняті, новому запитові й **немає сенсу** бігти далі — база все одно не потягне двадцять першого; хай зачекає своєї черги. Чекати вручну (крутити цикл `while порожньо: спати`) — марнування процесора; правильний інструмент — **семафор** або **умовна змінна (англ. *condition variable*)**, які присипляють потік по-справжньому, віддаючи процесор іншим, і будять рівно тоді, коли з'явився вільний об'єкт.

**Політика C — відмовити з таймаутом.** Чекати вічно теж небезпечно: як усі, хто тримає об'єкти, самі застрягли, охочі позичити повиснуть навік — **дедлок**. Тому зрілі пули чекають **не безмежно, а до таймаута**: не звільнилося за, скажімо, 5 секунд — `acquire` **кидає помилку** «пул вичерпано». Краще чесна швидка відмова, яку код обробить (поверне клієнтові 503, спробує пізніше), ніж мовчазне зависання назавжди.

Найкращі пули поєднують усі три: **ростуть** до `max_size`, далі **чекають** — але **з таймаутом**. Саме це й зберемо. Найчистіший інструмент тут — **потокобезпечна черга з блокувальним `get(timeout=…)`**: вона всередині вже має і замок, і умовну змінну, і таймаут — рівно нашу семантику. У Python це `queue.Queue`; його `get(timeout=t)` [за документацією](https://docs.python.org/3/library/queue.html) блокує потік до появи об'єкта й кидає `queue.Empty`, якщо за `t` секунд нічого не звільнилося.

```py
import queue

class Pool:
    def __init__(self, factory, max_size, timeout=5.0):
        self._factory = factory
        self._max = max_size
        self._timeout = timeout
        self._free = queue.LifoQueue()           # полиця з вбудованим замком
        self._created = 0                        # скільки взагалі народили
        self._lock = __import__("threading").Lock()   # захищає лічильник

    def acquire(self):
        # 1. Є вільний прямо зараз? Забираємо без чекання.
        try:
            return self._free.get_nowait()
        except queue.Empty:
            pass
        # 2. Ще не доросли до межі? Народжуємо новий (політика A).
        with self._lock:
            if self._created < self._max:
                self._created += 1
                return self._factory()           # дорога плата — раз на об'єкт
        # 3. Межу досягнуто — чекаємо звільнення до таймаута (B + C).
        try:
            return self._free.get(timeout=self._timeout)
        except queue.Empty:
            raise PoolExhausted(
                "усі %d об'єктів зайняті понад %.1f с" % (self._max, self._timeout))

    def release(self, conn):
        conn.reset()
        self._free.put(conn)                     # розбудить того, хто чекає в (3)

class PoolExhausted(Exception):
    pass
```

Простеж, як три політики склалися в один `acquire`, і — головне — **чому саме в такому порядку**. Спершу (крок 1) дешева спроба схопити готовий: `get_nowait` не блокує, лише знімає з полиці, якщо там є. Порожньо — пробуємо вирости (крок 2) під захистом замка, бо лічильник `_created` чіпають кілька потоків; тут `max_size` ставить стелю зростанню. І лише коли рости вже нікуди, ми **чекаємо** (крок 3), але не вічно: `get(timeout=…)` або дочекається чужого `release`, або за таймаутом кине `PoolExhausted`. Три гілки — три політики, вишикувані від найдешевшої до найтерплячішої.

Порядок кроків **не випадковий**. Спокусливо було б поставити зростання перед спробою схопити готовий — але тоді пул під легким навантаженням дарма плодив би об'єкти до самої межі, замість перевикористати вже вільні. Дешева спроба **першою** тримає кількість живих об'єктів мінімальною: новий народжується лише коли **справді** нема вільного. Це і є суть пулу — створити якнайменше, а не якнайбільше.

> 🔧 **Навіщо це.** Таймаут у кроці 3 — тонка запобіжна деталь, яку легко пропустити, а вона рятує систему від найгіршого. Без нього перша ж ситуація, коли всі, хто тримає об'єкти, застрягли самі, **вішає весь пул навік**: охочі позичити стоять у черзі, якої ніхто не рухає. З таймаутом та сама ситуація дає **швидку діагностовану помилку** — стек-трейс з `PoolExhausted` прямо вказує «пул вичерпано», і ти шукаєш, хто не повертає, а не гадаєш, чому сервер завис. Тайм-аут перетворює тихий дедлок на гучний виняток.

## Крок 3. Черга проти стека — О(1) і температура кеша

Ти, певно, помітив: у кроці 1 полиця була звичайним списком-**стеком** (беремо останній покладений), а в кроці 2 я взяв `LifoQueue` — теж стек (*LIFO — last in, first out*). Це не випадковість; вибір між стеком і чергою тут має **два боки**, і обидва варті розуміння.

**Бік перший — складність.** І стек (масив, чіпаємо один кінець), і черга (два кінці, `collections.deque` / зв'язаний список) дають O(1) на обох операціях: [зняти й покласти](https://opendatastructures.org/newhtml/ods/latex/linkedlists.html) — сталий час незалежно від розміру пулу. Тут вони рівні, і це головна вимога: пул кличуть на кожну операцію, тож ані `acquire`, ані `release` не сміють залежати від того, скільки об'єктів усередині.

> 🔧 **Навіщо це.** Чому О(1) — не педантизм, а серце всієї витівки. Пул продають як спосіб **пришвидшити** гарячий шлях. Якби видача коштувала О(n) — скажімо, пул щоразу лінійно шукав вільний об'єкт серед усіх, — то на пулі з тисячі з'єднань кожен `acquire` перебирав би тисячу елементів, і «оптимізація» стала б гальмом, тим важчим, чим більший пул. Сталий час — не приємний бонус, а **умова**, за якої пул узагалі має сенс: він мусить бути дешевшим за те, чого уникає (дороге створення), інакше він безглуздий. Тримати вільні у структурі з O(1)-доступом з обох потрібних кінців — те, що робить пул пулом.

**Бік другий — а от температура кеша їх розрізняє.** Тут стек (LIFO) непомітно кращий за чергу (FIFO), і ось чому. Стек **щойно повернутий** об'єкт віддає **наступним**. А цей об'єкт тільки-но працював — його поля свіжі в кеші процесора, сторінки пам'яті «теплі». Черга ж віддає **найдавніше** повернутий — той, що найдовше лежав і найпевніше вихолов із кеша, витіснений іншою роботою. Тому LIFO дає трохи більше влучань у кеш: гарячі об'єкти крутяться, холодні відлежуються. Різниця невелика, але безкоштовна, тож **типовий вибір для пулу — стек**.

Коли ж чергу (FIFO) беруть свідомо? Коли важливіша **рівномірність**, а не температура: FIFO пускає всі об'єкти по колу однаково, ніхто не застоюється. Це доречно, якщо об'єкти псуються від простою — наприклад, з'єднання, яке база тихо закриє, простоявши хвилину: тоді краще регулярно чіпати кожне (FIFO), ніж дати частині вихолонути до розриву, поки жменя гарячих обслуговує все навантаження (LIFO). Тобто вибір між ними — не про швидкість (обидва O(1)), а про те, **що для твого ресурсу дорожче**: холодний кеш чи протухлий від простою об'єкт.

## Крок 4. Потокобезпека: один замок навколо полиці

Досі я мовчки припускав, що з пулом працює один потік. У житті пул — це майже завжди **спільний ресурс під навантаженням**: десятки потоків-обробників рвуться до нього водночас. І тут голий код кроку 1 **розсипається**.

Побач гонитву на власні очі. `acquire` кроку 1 робить три дії: `pop` з `_free`, `add` у `_in_use`, `return`. Уяви два потоки, що ввійшли **одночасно** на пулі, де на полиці лишився **один** об'єкт:

```
Полиця _free = [X]   (один об'єкт)

Потік 1: бачить X на полиці, готується зняти…
Потік 2: бачить X на полиці, готується зняти…   ← обидва бачать той самий X
Потік 1: pop() → отримав X
Потік 2: pop() → CRASH (список уже порожній)     ← або, гірше,
Потік 2: pop() → теж отримав X                    ← ОБИДВА тримають X
```

Другий сценарій — найгірший різновид зламаного інваріанта: **один об'єкт виданий двом**. Обидва потоки певні, що X належить лише їм, обидва пишуть у нього — і дані місяться. Це не рідкісний збіг: під навантаженням у тисячі операцій на секунду такі перетини стаються **постійно**.

Ліки — зробити перехід стану **неподільним (англ. *atomic*)**: жоден інший потік не сміє втрутитися між «побачив вільний» і «позначив зайнятим». Класичний інструмент — **замок (англ. *mutex*, від *mutual exclusion* — взаємне виключення)**: код між захопленням і звільненням замка виконує **лише один** потік водночас, решта чекає на вході.

:::tabs
```py
import threading

class Pool:
    def __init__(self, factory, max_size, timeout=5.0):
        self._factory = factory
        self._max = max_size
        self._timeout = timeout
        self._free = []
        self._in_use = set()
        self._created = 0
        self._cond = threading.Condition()       # замок + черга очікування

    def acquire(self):
        with self._cond:                         # ← зайшов один; решта чекає
            deadline = _now() + self._timeout
            while True:
                if self._free:                   # є вільний — беремо
                    conn = self._free.pop()
                    self._in_use.add(conn)
                    return conn
                if self._created < self._max:    # нема — але можна вирости
                    self._created += 1
                    conn = self._factory()
                    self._in_use.add(conn)
                    return conn
                remaining = deadline - _now()    # усе зайнято — чекаємо
                if remaining <= 0:
                    raise PoolExhausted("пул вичерпано")
                self._cond.wait(remaining)       # спить, ВІДПУСКАЮЧИ замок

    def release(self, conn):
        conn.reset()
        with self._cond:
            self._in_use.discard(conn)
            self._free.append(conn)
            self._cond.notify()                  # будить одного, хто чекає
```
```ts
// TS-рантайм — однопотоковий (event loop), «замка» в сенсі потоків нема.
// Але асинхронність дає СВОЮ гонитву: між await-ами вклинюється чужий код.
// Тому пул тут блокує не потік, а обіцянку (Promise): черга тих, хто чекає.
class Pool<T> {
  private free: T[] = [];
  private created = 0;
  private waiters: Array<(obj: T) => void> = [];   // хто чекає вільного

  constructor(
    private factory: () => T,
    private reset: (o: T) => void,
    private max: number,
    private timeoutMs = 5000,
  ) {}

  async acquire(): Promise<T> {
    if (this.free.length > 0) return this.free.pop()!;   // є вільний
    if (this.created < this.max) {                        // можна вирости
      this.created++;
      return this.factory();
    }
    // усе зайнято — стаємо в чергу обіцянок, з таймаутом
    return new Promise<T>((resolve, reject) => {
      const timer = setTimeout(() => {
        const i = this.waiters.indexOf(give);
        if (i >= 0) this.waiters.splice(i, 1);
        reject(new Error("пул вичерпано"));
      }, this.timeoutMs);
      const give = (obj: T) => { clearTimeout(timer); resolve(obj); };
      this.waiters.push(give);
    });
  }

  release(obj: T): void {
    this.reset(obj);
    const give = this.waiters.shift();            // хтось чекає?
    if (give) give(obj);                          // віддати прямо йому
    else this.free.push(obj);                     // ні — на полицю
  }
}
```

Ці дві вкладки навмисно **не однакові**, і в цій різниці — важливий урок. Python (як і Java, C#, Go, C++) має **справжні потоки**, що біжать одночасно на різних ядрах, тож пул мусить боронитися **замком**: `Condition` — це замок плюс вбудована черга сну, `wait` присипляє потік, **відпускаючи замок** (інакше решта не зайшла б навіть покласти об'єкт), а `notify` у `release` будить одного зі сплячих. У TypeScript інакше: рантайм **однопотоковий**, справжніх гонок за пам'ять нема — але є **асинхронна** гонка. Поки твоя функція чекає на `await`, рантайм пускає **інший** код, і той теж може смикнути пул. Тому TS-пул черги потоків не має, зате тримає **чергу обіцянок** (`waiters`): хто не дістав об'єкта, отримує `Promise`, який `release` **виконає напряму**, віддавши повернутий об'єкт наступному в черзі, — навіть на полицю не кладучи.

> 🔧 **Навіщо це.** Мораль ширша за пул: **потокобезпека — не універсальний рецепт, а відповідь на конкретну модель виконання твого рантайму**. У мові зі справжніми потоками боронишся замком навколо спільного стану. У мові з подієвим циклом замок безглуздий — там боронишся від чужого коду, що вклинюється на точках `await`. Скопіювати сюди «пул із замком» з Java було б помилкою: замок, якого ніщо не оспорює, — марна складність. Спершу спитай, **як саме** твій рантайм дає паралельність, і лише тоді обирай захист.

Одна пастка на завершення кроку. Замок у Python-версії тримають **лише навколо роботи з полицею**, а `conn.reset()` у `release` стоїть **до** входу в `with self._cond` — свідомо. Скидання може бути повільним (мережевий пінг, відкат транзакції), а тримати замок під час повільної операції — злочин: усі інші потоки стоять і чекають, поки ти неспішно чистиш один об'єкт. Правило залізне: **під замком — лише короткі, суто пам'яттєві дії** (зняти зі списку, додати в множину). Усе дороге — мережу, диск, скидання — тримай **за межами** замка.

## Крок 5. Гарантоване повернення — три способи не забути `release`

Тепер закриємо **витік**. Нагадаю пастку: хтось позичив об'єкт і не повернув — забув дописати `release`, або код вискочив із функції через `return` чи виняток раніше, ніж дійшов до повернення. Об'єкт навік числиться `in-use`, полиця повільно порожніє, аж поки пул не почне на кожен `acquire` віддавати `PoolExhausted` — примарами, яких ніхто не тримає.

Корінь у тому, що **ручний `release` наприкінці функції — це обіцянка, яку легко зламати**. Будь-який ранній вихід її обходить:

```py
def handle(pool):
    conn = pool.acquire()
    rows = conn.query("select ...")
    if not rows:
        return None                # ← ВИТІК: вийшли повз release
    process(rows)
    pool.release(conn)             # сюди при порожньому rows не дійшли
```

Лікуємо тим, що робимо повернення **не обіцянкою, а гарантією мови** — прив'язуємо `release` до самої механіки виходу з блоку, хай яким шляхом той вихід стався. Три способи, по одному на різні мови й смаки.

**Спосіб 1 — `try/finally` (працює скрізь).** Блок `finally` виконується **завжди** на виході з `try` — при нормальному завершенні, при `return`, при винятку. Кладемо повернення туди — і воно невідворотне:

```py
def handle(pool):
    conn = pool.acquire()
    try:
        rows = conn.query("select ...")
        if not rows:
            return None            # finally все одно спрацює
        process(rows)
    finally:
        pool.release(conn)         # ← виконається на БУДЬ-ЯКОМУ виході
```

Це вже надійно, але галасливо: `try/finally` доводиться писати щоразу, і його теж можна забути. Тому мови дають цукор, що ховає цю дисципліну.

**Спосіб 2 — контекстний менеджер (Python `with`).** Python дозволяє класу означити, що робити на **вході** в блок `with` і на **виході** з нього — і вихід теж гарантований, як `finally`. Даємо пулу метод, що видає об'єкт **разом із цим механізмом**:

```py
from contextlib import contextmanager

class Pool:
    # ... acquire / release, як у кроці 4 ...

    @contextmanager
    def lease(self):
        conn = self.acquire()          # вхід у with — позичили
        try:
            yield conn                 # віддали користувачеві на час блоку
        finally:
            self.release(conn)         # вихід із with — повернули, завжди

# використання: повернення НЕ можна забути — його робить сам with
def handle(pool):
    with pool.lease() as conn:         # ← позичив
        rows = conn.query("select ...")
        if not rows:
            return None                # release однаково станеться
        process(rows)
    # ← тут conn уже повернутий, хай яким шляхом вийшли з блоку
```

Тепер забути повернення **неможливо в принципі**: воно вшите у вихід із `with`, а не покладене на пам'ять програміста. У TypeScript тієї самої надійності досягають функцією-обгорткою, що бере **колбек** і сама повертає об'єкт у `finally`:

```ts
class Pool<T> {
  // ... acquire / release ...

  async use<R>(fn: (obj: T) => Promise<R>): Promise<R> {
    const obj = await this.acquire();     // позичив
    try {
      return await fn(obj);               // віддав користувачеві
    } finally {
      this.release(obj);                  // повернув — на будь-якому виході,
    }                                     // навіть якщо fn кинув виняток
  }
}

// використання: об'єкт живе рівно стільки, скільки триває колбек
await pool.use(async (conn) => {
  const rows = await conn.query("select ...");
  if (rows.length === 0) return null;     // release однаково станеться
  return process(rows);
});
```

В обох мовах ідея одна: **не давати сирий `acquire` користувачеві напряму**. Хай публічним входом буде `lease`/`use`, що видає об'єкт **лише на час блоку чи колбека** й забирає назад автоматично. Сирий `acquire`/`release` лишається всередині — для рідкісних випадків, коли час життя об'єкта справді не лягає в один блок; але за замовчуванням усі користуються безпечною обгорткою, і витік стає структурно неможливим.

> 🔧 **Навіщо це.** Це прояв глибшого принципу: **зроби правильне легким, а неправильне — важким або неможливим**. Ручний `release` робить правильне (повернути) справою пам'яті, а неправильне (забути) — тихим і легким. Обгортка `with`/`use` перевертає це: правильне стає єдиним природним шляхом, а щоб «забути», довелося б навмисне лізти в сирий `acquire`. Найнадійніший спосіб не припуститися помилки — усунути саму можливість її припуститися, а не пильнувати щоразу.

## Крок 6. C++ і RAII — коли повернення гарантує сам об'єкт

Окремий кут вартий C++, бо він розв'язує гарантоване повернення **найелегантніше з усіх** — так, що ані `finally`, ані обгортки-колбека не треба. Причина — **детермінований деструктор**: коли об'єкт-змінна виходить з області видимості, C++ **негайно й гарантовано** кличе його деструктор — при нормальному виході, при `return`, при винятку, будь-коли. Це той самий механізм, що стоїть за ідіомою **RAII (англ. *Resource Acquisition Is Initialization* — отримання ресурсу є ініціалізацією)**.

Ідея: загорнути позичений об'єкт у маленький клас-«оренду». Його **конструктор** бере об'єкт із пулу, **деструктор** повертає. Далі просто заводимо змінну цього класу — і повернення станеться саме собою на виході з блоку, бо так працює мова:

```cpp
class Pool;                                  // оголошення наперед

// Обгортка-оренда: тримає позичений Conn, повертає його в деструкторі.
class Lease {
public:
    Lease(Pool& pool, Conn* conn) : pool_(pool), conn_(conn) {}
    ~Lease() { if (conn_) pool_.release(conn_); }   // ← повернення тут

    Conn* operator->() { return conn_; }     // щоб писати lease->query(...)
    Conn& operator*()  { return *conn_; }

    // Оренду не можна копіювати (два власники одного Conn = зомбі),
    // але можна ПЕРЕДАВАТИ (move): старий власник знімає з себе conn_.
    Lease(const Lease&) = delete;
    Lease& operator=(const Lease&) = delete;
    Lease(Lease&& o) noexcept : pool_(o.pool_), conn_(o.conn_) { o.conn_ = nullptr; }

private:
    Pool& pool_;
    Conn* conn_;
};

// використання
void handle(Pool& pool) {
    Lease lease = pool.acquire();            // позичив
    auto rows = lease->query("select ...");  // працюємо крізь ->
    if (rows.empty())
        return;                              // ← деструктор Lease поверне Conn
    process(rows);
}                                            // ← або тут: у будь-якому разі release
```

Придивися, скільки пасток C++ закриває **самою будовою типу**, а не дисципліною програміста.

**Повернення невідворотне.** Хоч би як `handle` завершилася — раннім `return` при порожньому результаті, звичайним виходом, чи винятком, кинутим усередині `query`, — змінна `lease` виходить з області видимості, і компілятор **зобов'язаний** покликати `~Lease()`, а той поверне `Conn`. Забути повернення неможливо: за тебе це робить механіка мови. Це та сама гарантія, що `finally`, тільки не дописана вручну, а **вбудована в тип** — оголосив змінну, отримав автоматичне повернення.

**Зомбі заблоковано на етапі компіляції.** Ось де C++ вивищується над іншими. Рядки `Lease(const Lease&) = delete` **забороняють копіювати** оренду. Спробуєш зробити дві копії однієї оренди — тобто двох власників одного `Conn` — і код **не збереться**. Пастку «два власники на один об'єкт», яку в Python чи TS ловиш аж під час виконання (та й то, якщо додав перевірки), C++ робить **несформульовуваною**: компілятор не пропустить. Передати володіння (move-конструктор) можна — але тоді старий власник **обнуляє свій `conn_`** (`o.conn_ = nullptr`), тож повертає об'єкт рівно один власник, і рівно раз.

> 🔧 **Навіщо це.** RAII показує межу можливого в гарантіях: у мові з детермінованими деструкторами повернення ресурсу стає **властивістю типу**, а не поведінкою, якої треба пильнувати. Порівняй сходинки надійності: сирий `release` — сподіваєшся, що згадають; `try/finally` — гарантовано, але треба дописати руками; `with`/`use` — гарантовано й вшито у вхід; RAII — гарантовано, вшито, **та ще й неправильне (копію-зомбі) не збереться**. Що вище сходинка, то менше лишається на людську пам'ять — і то менше багів. Обирай найвищу, яку дає твоя мова.

## Крок 7. Ловимо тих, хто ламає інваріант: валідація й тавро оренди

Останній шар — не для нормального шляху, а для **захисту від помилок у чужому коді**, що користується пулом. Навіть з ідеальними обгортками хтось колись поверне об'єкт, який не можна повертати, або зробить дурницю, від якої варто застерегти голосно. Додамо пулу два вартові.

**Валідація перед видачею — «чи об'єкт іще живий».** Об'єкти в пулі живуть довго, і за час лежання на полиці ресурс **міг тихо зламатися ззовні**: базу перезапустили — з'єднання мертве; сокет закрився по таймауту; ресурс протух. Видати такий об'єкт — віддати клієнтові гранату: він спробує ним скористатися й дістане незрозумілу помилку в **своєму** коді, хоча винний пул. Тому зрілий пул **перевіряє об'єкт перед видачею** й тихо викидає мертві, замінюючи свіжими:

```py
def acquire(self):
    with self._cond:
        deadline = _now() + self._timeout
        while True:
            if self._free:
                conn = self._free.pop()
                if not conn.is_alive():      # ← протух на полиці?
                    self._created -= 1       # списуємо мертвий
                    continue                 # шукаємо/родимо інший
                self._in_use.add(conn)
                return conn                  # віддаємо лише живий
            # ... далі як у кроці 4: рости / чекати / таймаут ...
```

Ціна — один дешевий `is_alive()` на видачу (для з'єднання це, скажімо, легкий пінг чи перевірка прапорця сокета). Вигода — клієнт **ніколи** не отримає з пулу мертвий об'єкт; уся крихкість довгоживучих ресурсів лишається сховraна всередині пулу, де їй і місце.

**Тавро оренди — ловимо подвійне повернення й чужі об'єкти.** Друга дрібниця, що рятує години налагодження. Наївний `release` сліпо вірить, що йому повертають **його ж** об'єкт і **вперше**. А в реальному коді трапляється: повернули двічі (той самий об'єкт лягає на полицю двома копіями — і його видадуть **двом** одразу, готовий зомбі); або повернули чужий об'єкт, зроду не з цього пулу. Ось тут і стає в пригоді множина `_in_use`, яку ми завели ще в кроці 1: вона — реєстр «хто справді виданий». Повернення звіряємо з ним:

```py
def release(self, conn):
    with self._cond:
        if conn not in self._in_use:         # ← тавро: цей об'єкт справді в оренді?
            raise ValueError(
                "повертають об'єкт, якого пул не видавав "
                "(подвійний release або чужий об'єкт)")
        self._in_use.discard(conn)           # знімаємо тавро оренди
    conn.reset()                             # чистимо ПОЗА замком (крок 4)
    with self._cond:
        self._free.append(conn)
        self._cond.notify()
```

Тепер подвійне повернення не тихо сіє зомбі, а **голосно падає** на другому `release`: перший зняв тавро (`discard`), другий не знайшов об'єкта в `_in_use` і кинув `ValueError` з прямою вказівкою на діагноз. Це і є та причина, чому `_in_use` не була надлишковою: без реєстру виданих пул **не може відрізнити** законне повернення від подвійного чи чужого. Множина, що в кроці 1 здавалася зайвою, виявилась вартовим одразу двох поламань інваріанта — зомбі й чужого об'єкта.

> 🔧 **Навіщо це.** Обидва вартові втілюють правило зрілого коду: **не довіряй входам, навіть якщо вони «мають бути» правильні**. `is_alive` не вірить, що об'єкт на полиці досі живий, — бо світ навколо ресурсу міг змінитися без пулу. Тавро оренди не вірить, що повертають саме те й саме раз, — бо чужий код помиляється. Ці перевірки коштують копійки (пошук у множині — O(1), пінг — раз на видачу), а перетворюють **тихі, плавучі, невідтворювані** баги на **гучні винятки з точним діагнозом** у мить самого порушення. Дешева перевірка на межі пулу економить дорогі години гри в детектива.

## Що вийшло: пул станів під наглядом

Зберемо картину складеного пулу — і побачимо, що кожна цеглина стерегла свій інваріант.

```
Інваріант, що ми боронили: кожен об'єкт РІВНО в одному стані — free або in-use.

Крок 1  reset при release  → на полиці лише ЧИСТИЙ об'єкт (сусідній інваріант)
Крок 2  межа + політика     → пул не тече безмежно; вичерпання — керована подія
Крок 3  стек, не черга      → O(1) + теплий кеш на гарячому шляху
Крок 4  один замок          → перехід стану неподільний: не буває «двох на один X»
Крок 5  with / use          → повернення гарантоване → об'єкт не губиться (нема витоку)
Крок 6  RAII (C++)          → те саме, вшите в тип; копію-зомбі НЕ збереться
Крок 7  is_alive + тавро    → не видамо мертвий; спіймаємо подвійне/чуже повернення
```

Складність вийшла така, якою й мусить бути в пулу: **O(1) на acquire і O(1) на release** — сталий, малий час незалежно від розміру пулу (стек чіпає один кінець, множина `_in_use` дає вставку й пошук за сталий час), плюс один дешевий `is_alive` на видачу. Пам'ять — O(max_size): рівно стільки об'єктів, скільки дозволила межа, і ні на один більше. Це і робить пул придатним на гарячому шляху: він **дешевший** за те, чого уникає, — за дороге народження ресурсу.

Головний висновок, заради якого варто було збирати все це по цеглині: **пул — це не контейнер об'єктів, а машина підтримки інваріанта**. Наївний список «вільних» — це десять хвилин роботи. Решта кроків — межа, замок, гарантоване повернення, валідація, тавро — існують не заради самих об'єктів, а заради **закону**: кожен об'єкт завжди рівно в одному чесному стані, чистий, живий, з одним власником. Забери будь-яку цеглину — і закон проламується саме там, де вона стояла: без reset тече бруд, без замка родяться дублікати, без `with` — витік, без тавра — зомбі. Пул складний рівно настільки, наскільки складно **не зламати** цей інваріант під навантаженням багатьох потоків.

Та сама, до речі, логіка працює поверхом нижче — коли перевикористовують не готові об'єкти, а сирі однакові клітини пам'яті; там роль «інваріанта станів» грає карта зайнятих блоків, а роль дорогого народження — виклик системного алокатора. Це рідний брат нашого пулу, [блоковий пул пам'яті](book:programming/heap-dynamic-memory/proj-block-pools.md), і будують його тими самими цеглинами, тільки з фіксованим розміром клітини замість типізованого об'єкта.
