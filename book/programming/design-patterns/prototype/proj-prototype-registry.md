# ⚙️ Реєстр прототипів: коректна глибока копія й пастки clone()

Задача звучить невинно, аж поки не почнеш її писати. Треба система, що плодить сутності гри: маючи ключ на кшталт «орк» чи «лучник», вона видає новий, повністю налаштований об'єкт — і таких треба тисячі за секунду, кожен свій, незалежний. Клас творця писати на кожен вид не хочемо: нові види додаються дизайнером на льоту, без перекомпіляції. Отже, тримаємо **реєстр зразків**: ключ → один заздалегідь налаштований прототип, а `create(ключ)` бере зразок і **клонує** його.

Уся конструкція реєстру — це десяток рядків, і вони оманливо прості. Справжня робота — і всі синці — ховаються в одному методі: `clone()`. Бо клонувати об'єкт із простими полями вміє кожен, а от клонувати об'єкт, який тримає вкладений змінний стан, посилається сам на себе через ланцюг сусідів і стискає в кулаці живий мережевий сокет, — тут наївний `clone()` ламається аж п'ятьма різними способами, і кожен злам тихий: код працює, тести часом зелені, а два «різні» об'єкти потай лишаються одним. Зберемо робочий реєстр із **коректною** глибокою копією, а тоді розберемо кожну з п'яти пасток на живому коді — звідки береться, як виглядає баг і чим лікується.

## Ідея: реєстр — це мапа, уся сіль — у clone()

Розділімо відповідальність чесно, бо саме на цьому розділі все й тримається. **Реєстр** знає рівно дві речі: як покласти зразок під ключем і як за ключем його дістати. Він не знає, що всередині зразка, скільки там вкладених списків і чи є серед полів сокет, — його справа знайти прототип і покликати `clone()`. А **`clone()`** знає геть протилежне: він нічого не відає про ключі й реєстри, зате точно знає, з чого складений його об'єкт і **як глибоко** копіювати кожне поле.

Ця межа — не бюрократія, а те, що робить патерн масштабованим. Додати новий вид — це покласти ще один зразок у мапу; жодного `if` за типом, жодної правки `create`. А вся складність копіювання замкнена в кожному класі окремо: клас сам відповідає за коректність свого `clone()`, і реєстрові байдуже, простий той клас чи носить у собі граф із циклами.

## Робоча модель з коректним clone()

Почнемо з сутності, у якій уже є те, на чому спотикається наївне копіювання: вкладений об'єкт (`Stats`) і вкладений список (`loot`). Обидва **змінні** — тож ділити їх між копіями не можна, інакше правка одного клона тихо зачепить іншого.

:::tabs
```ts
class Stats {
  constructor(
    public attack: number,
    public defense: number,
    public resist: Map<string, number>,   // вкладена ЗМІННА мапа опорів
  ) {}

  clone(): Stats {
    // глибоко: власна нова мапа, а не спільна з оригіналом
    return new Stats(this.attack, this.defense, new Map(this.resist));
  }
}

class Monster {
  constructor(
    public name: string,
    public hp: number,
    public stats: Stats,       // вкладений об'єкт
    public loot: string[],     // вкладений список
  ) {}

  clone(): Monster {
    return new Monster(
      this.name,               // рядок незмінний — просто значення
      this.hp,                 // число — просто значення
      this.stats.clone(),      // глибоко: власний Stats
      [...this.loot],          // глибоко: власний масив (елементи-рядки незмінні)
    );
  }
}
```
```py
class Stats:
    def __init__(self, attack, defense, resist):
        self.attack = attack
        self.defense = defense
        self.resist = resist            # вкладений ЗМІННИЙ dict опорів

    def clone(self):
        # глибоко: власний новий dict, а не спільний з оригіналом
        return Stats(self.attack, self.defense, dict(self.resist))

class Monster:
    def __init__(self, name, hp, stats, loot):
        self.name = name                # рядок незмінний — просто значення
        self.hp = hp                    # число — просто значення
        self.stats = stats              # вкладений об'єкт
        self.loot = loot                # вкладений список

    def clone(self):
        return Monster(
            self.name, self.hp,
            self.stats.clone(),         # глибоко: власний Stats
            list(self.loot),            # глибоко: власний список
        )
```
:::

Придивися до `loot`. `[...this.loot]` (чи `list(self.loot)`) робить **новий** масив, але копіює його елементи «як є». Тут це безпечно рівно тому, що елементи — рядки, а рядок незмінний: ділити його між копіями нема чим зашкодити. Якби в списку лежали **змінні об'єкти**, цього поверхневого масиву було б замало — довелося б клонувати ще й кожен елемент (`this.loot.map(x => x.clone())`). Глибина копії — не властивість контейнера, а властивість **кожного рівня** вкладеності; спинятися можна лише там, де далі йде незмінне.

## Реєстр

Тепер сам реєстр. Він параметризований будь-яким типом, що вміє себе клонувати, — і в цьому вся його універсальність:

:::tabs
```ts
class PrototypeRegistry<T extends { clone(): T }> {
  private prototypes = new Map<string, T>();

  register(key: string, proto: T): void {   // покласти зразок під ключем
    this.prototypes.set(key, proto);
  }

  create(key: string): T {
    const proto = this.prototypes.get(key);
    if (!proto) throw new Error(`немає прототипу: ${key}`);
    return proto.clone();                    // новий об'єкт — копія зразка
  }
}
```
```py
class PrototypeRegistry:
    def __init__(self):
        self._prototypes = {}

    def register(self, key, proto):          # покласти зразок під ключем
        self._prototypes[key] = proto

    def create(self, key):
        proto = self._prototypes.get(key)
        if proto is None:
            raise KeyError(f"немає прототипу: {key}")
        return proto.clone()                 # новий об'єкт — копія зразка
```
:::

Зверни увагу на обмеження `T extends { clone(): T }` у TypeScript: реєстр приймає будь-що з методом `clone()`, що повертає такий самий тип. Це не косметика — це договір, який компілятор змушує дотримати: покласти в реєстр об'єкт без коректного `clone()` просто не вийде. Тепер увімкнемо його й переконаймося, що копії справді незалежні:

:::tabs
```ts
const bestiary = new PrototypeRegistry<Monster>();
bestiary.register("орк",
  new Monster("орк", 30,
    new Stats(8, 4, new Map([["вогонь", -2]])),
    ["монета", "шкура"]));

const a = bestiary.create("орк");
const b = bestiary.create("орк");

a.loot.push("щит");                 // чіпаємо здобич ОДНІЄЇ копії
console.log(b.loot);                // ['монета','шкура'] — інша копія недоторкана
console.log(a.stats === b.stats);   // false — кожна має власний Stats
a.stats.resist.set("вогонь", 0);    // міняємо опір однієї...
console.log(b.stats.resist.get("вогонь")); // -2 — інша не змінилась
```
```py
bestiary = PrototypeRegistry()
bestiary.register("орк",
    Monster("орк", 30, Stats(8, 4, {"вогонь": -2}), ["монета", "шкура"]))

a = bestiary.create("орк")
b = bestiary.create("орк")

a.loot.append("щит")                    # чіпаємо здобич ОДНІЄЇ копії
print(b.loot)                           # ['монета','шкура'] — інша недоторкана
print(a.stats is b.stats)               # False — кожна має власний Stats
a.stats.resist["вогонь"] = 0            # міняємо опір однієї...
print(b.stats.resist["вогонь"])         # -2 — інша не змінилась
```
:::

Оце і є мета: два орки з одного зразка, які поводяться як **два справжні різні орки**, а не як дві назви одного. Кожен рядок перевірки тут проходить рівно тому, що `clone()` чесно відділив кожне змінне поле. Забери з нього хоч один рівень глибини — і одна з цих перевірок мовчки провалиться. Саме цим мовчазним провалам і присвячена решта.

## Віртуальний конструктор: ідіома clone() у C++

Перш ніж до пасток — окремий кут, під яким та сама ідея виглядає інакше. У класових мовах із базовими типами постає питання: маючи в руках `Entity*` невідомого підтипу, як зробити його копію **правильного** класу? Конструктор покликати поліморфно не можна — `new` вимагає знати конкретний тип. Відповідь C++ — усталена ідіома «віртуального конструктора»: віртуальний `clone()`, тіло якого кличе **конструктор копії** свого точного типу.

```cpp
#include <memory>
#include <string>
#include <vector>

struct Entity {
    virtual ~Entity() = default;
    // «віртуальний конструктор»: кожен нащадок віддасть копію СВОГО типу
    virtual std::unique_ptr<Entity> clone() const = 0;
    virtual void render() const = 0;
};

struct Monster : Entity {
    std::string name;
    int hp;
    std::vector<std::string> loot;      // ВЛАСНИЙ вектор

    Monster(std::string name, int hp, std::vector<std::string> loot)
        : name(std::move(name)), hp(hp), loot(std::move(loot)) {}

    std::unique_ptr<Entity> clone() const override {
        // одне тіло — виклик КОНСТРУКТОРА КОПІЇ через *this
        return std::make_unique<Monster>(*this);   // Monster(const Monster&)
    }
    void render() const override { /* намалювати */ }
};
```

Уся хитрість — у рядку `std::make_unique<Monster>(*this)`. `*this` — це `const Monster&`, тож `make_unique` кличе **конструктор копії** `Monster(const Monster&)`. А оскільки метод віртуальний, виклик `proto->clone()` крізь `Entity*` потрапляє в реалізацію справжнього підтипу — і повертає копію саме `Monster`, хоча в місці виклику про `Monster` ніде не сказано:

```cpp
std::unique_ptr<Entity> proto =
    std::make_unique<Monster>("орк", 30,
        std::vector<std::string>{"монета", "шкура"});

std::unique_ptr<Entity> copy = proto->clone();   // у руках Entity* — а копія Monster
```

Термін «віртуальний конструктор» для цієї ідіоми закріпив Джеймс Коплін у книжці «Advanced C++ Programming Styles and Idioms» (1992); та сама техніка згадана й у канонічній книжці «банди чотирьох» як спосіб реалізувати прототип у C++. *(Статус: усталена, добре задокументована ідіома мови.)*

Але найглибше тут — інше, і воно перевертає всю попередню розмову про глибину. У C++ поля-**значення** копіюються самі: `std::string` і `std::vector` мають власні конструктори копії, що копіюють вміст **углиб**. Тому згенерований компілятором конструктор копії `Monster` уже глибокий — кожна копія дістає свій вектор і свій рядок задарма, без жодного ручного `clone()`. Небезпека поверхневості вертається рівно тоді, коли поле — **сирий вказівник** на щось, чим об'єкт володіє:

```cpp
struct Broken : Entity {
    Weapon* weapon;                     // ВОЛОДІЄ зброєю, але сирим вказівником
    // згенерований конструктор копії скопіює лише ВКАЗІВНИК:
    // дві копії дивляться на один Weapon → подвійне звільнення при знищенні
};
```

Тут згенерований конструктор копії тихо скопіює вказівник — дві копії поділять один `Weapon`, і при знищенні кожна спробує його звільнити (подвійне `delete`). Це та сама «мовчазна поверхнева копія», лише в іншому вбранні; ліки — «правило трьох/п'яти» (маєш власний деструктор для ресурсу — напиши й власні конструктор копії та присвоєння) або, чистіше, тримати ресурс через `std::unique_ptr<Weapon>` і в `clone()` копіювати його вглиб. Дрібниця для повноти: якби `clone()` повертав сирий `Entity*`, спрацювала б **коваріантність** — нащадок міг би оголосити `Monster* clone() const override`; з `unique_ptr` коваріантність не працює, тож обидва рівні повертають `unique_ptr<Entity>`.

Ось чому мови з посиланнями за замовчуванням (TypeScript, Python, Java) і мови значень (C++) вимагають протилежної пильності: у перших глибину доводиться **додавати** руками, у C++ — глибина є задарма для значень, а стерегтися треба **сирих ресурсів**. Прототип в обох світах — це одне рішення «наскільки глибоко», просто дефолт у них дзеркальний.

## Пастка 1: забуте поле — напівкопія, синхронна з класом

Тепер до зламів. Найпідступніший починається невинно: об'єкт росте. Через місяць у `Monster` додають поле `speed`, правлять конструктор — і забувають про `clone()`.

:::tabs
```ts
class Monster {
  constructor(
    public name: string,
    public hp: number,
    public stats: Stats,
    public loot: string[],
    public speed = 1,          // ← ДОДАЛИ пізніше
  ) {}

  clone(): Monster {
    // забули про speed! кожен клон тихо дістане speed = 1
    return new Monster(this.name, this.hp, this.stats.clone(), [...this.loot]);
  }
}
```
```py
class Monster:
    def __init__(self, name, hp, stats, loot, speed=1):   # ← speed ДОДАЛИ пізніше
        self.name, self.hp, self.stats, self.loot, self.speed = \
            name, hp, stats, loot, speed

    def clone(self):
        # забули про speed! кожен клон тихо дістане speed = 1
        return Monster(self.name, self.hp, self.stats.clone(), list(self.loot))
```
:::

Баг невидимий, поки не з'явиться швидкий монстр. Зареєстрував прудкого гінця `speed = 3`, наплодив копій — і всі вони плентаються з `speed = 1`. Жодного винятку, жодного попередження: `clone()` віддав **напівкопію** з тихо загубленим полем. Це і є «синхрон `clone()` з полями класу» — постійний обов'язок: кожне нове поле треба **не забути** додати ще й у `clone()`. Обов'язок легко порушити, бо компілятор мовчить: конструктор задовольнили, `clone()` компілюється, тест на `speed` ніхто не написав.

Спокуса — переписати `clone()` так, щоб він **не перелічував** поля поіменно, а брав усі гуртом і лагодив лише ті, що потребують глибини:

:::tabs
```ts
clone(): Monster {
  // поверхнево скопіювати ВСІ власні поля (з правильним прототипом класу)...
  const c = Object.assign(Object.create(Monster.prototype), this);
  // ...і полагодити глибину лише там, де вкладене змінне:
  c.stats = this.stats.clone();
  c.loot = [...this.loot];
  return c;
}
```
```py
import copy

def clone(self):
    c = copy.copy(self)          # поверхнево: усі поля, клас збережено
    c.stats = self.stats.clone() # полагодити глибину лише де треба
    c.loot = list(self.loot)
    return c
```
:::

Тепер новий скалярний `speed` **несеться сам** — поверхневе копіювання захопило всі власні поля, і додане поле-число опиниться в копії без жодної правки `clone()`. Виграш реальний, але дивись, що сталося з обов'язком: він **не зник, а переїхав**. Тепер ти мусиш пам'ятати не про кожне поле, а лише про кожне **посилальне** поле, яке треба поглибити. Забудеш поглибити нове поле-посилання — і поверхневе копіювання тихо поділить його між копіями. Це фундаментальний розмін двох стилів `clone()`: **перелічувати поля** (ризик проґавити новий скаляр) проти **копіювати гуртом і лагодити** (ризик проґавити нове посилання). Другий стиль зазвичай безпечніший, бо посилальні поля додають рідше, ніж скалярні, — але вигадати спосіб, який не вимагає пам'ятати **нічого**, не можна: хтось мусить знати, де кінчається значення й починається спільний стан.

## Пастка 2: мовчазний поверхневий дефолт

Друга пастка — рідна сестра першої, але приходить з іншого боку: коли за копію береш вбудований механізм, гадаючи, що він зробить усе, а він робить лише **поверхневе**.

:::tabs
```ts
clone(): Monster {
  return { ...this };            // ПОВЕРХНЕВО: stats і loot — СПІЛЬНІ
}
```
```py
def clone(self):
    return copy.copy(self)       # ПОВЕРХНЕВО: stats і loot — СПІЛЬНІ
```
:::

`{...this}`, `Object.assign`, `copy.copy` копіюють поля «на один рівень»: числа й рядки лягають значеннями, а `stats` і `loot` лишаються **тими самими** об'єктами. Дві копії ділять один список здобичі й одну мапу опорів — забаффав одного орка, забаффалися всі. І це навіть гірше за першу пастку: там губилося поле, а тут два об'єкти лишаються **зчеплені** прихованою спільністю, і баг випливе далеко від місця копіювання.

Природна відповідь — «то візьму глибокий вбудований механізм»: `structuredClone` у JavaScript чи `copy.deepcopy` у Python. Обидва справді проходять углиб і навіть уміють цикли (про них далі). Але для **реєстру прототипів** у них ховається засідка, і найгостріша — у `structuredClone`. За специфікацією структурного клонування «ланцюг прототипів не обходиться й не відтворюється» — тобто копія екземпляра класу виходить **звичайним об'єктом**, без класу й **без методів**:

```ts
const copy = structuredClone(orc);   // глибоко скопіювало ДАНІ...
copy instanceof Monster;             // false — це вже не Monster!
copy.clone();                        // ✗ TypeError: copy.clone is not a function
```

Для прототипа це смертельно: клон мусить лишатися **того самого класу** — з тим самим `clone()`, `render()`, усією поведінкою, — інакше він і в реєстр більше не годиться, і поводитись уміє лише як мішок даних. До того ж `structuredClone` кидає `DataCloneError` на функціях і вузлах DOM, а `getter`/`setter` і приватні поля не відтворює. `JSON.parse(JSON.stringify(x))` іще гірший — теж губить клас, а на додачу викидає `undefined`, функції й перетворює дати на рядки.

`copy.deepcopy` у Python чемніший — клас зберігає, — але й він спотикається на живих ресурсах (про них — пастка 4) і чесно копіює **весь** досяжний граф, що буває надто дорого. Звідси висновок, який і робить ручний `clone()` неминучим саме для прототипа: коли клон мусить бути **тим самим класом із живою поведінкою**, а поля різнорідні (щось поглибити, щось поділити, щось перевідкрити), — жоден універсальний копіювальник не вгадає за тебе, і `clone()` доводиться писати руками.

## Пастка 3: цикли й таблиця memo

Тепер додамо монстрові належність до загону — і разом із нею **цикл**. `Monster` тримає посилання на свій `Squad`, а `Squad` тримає список членів, серед яких є цей самий монстр. Граф замикається сам на себе.

:::tabs
```ts
class Squad {
  members: Monster[] = [];
}
class Monster {
  squad: Squad | null = null;   // ← назад на загін
  // ...решта полів...
}
// orc.squad === squad;  squad.members[0] === orc  → цикл
```
```py
class Squad:
    def __init__(self):
        self.members = []
class Monster:
    def __init__(self, ...):
        self.squad = None        # ← назад на загін
# orc.squad is squad;  squad.members[0] is orc  → цикл
```
:::

Наївна рекурсивна глибока копія на такому графі **зациклюється**: щоб скопіювати монстра, копіюємо його загін; щоб скопіювати загін, копіюємо його членів; серед членів — той самий монстр, і рекурсія йде на друге коло, і на третє, і в стек-переповнення. Ліки відомі й елегантні — **таблиця memo**: відображення «вже побачений об'єкт → його копія». Перед тим як лізти в поля вузла, реєструємо його копію в memo; коли обхід вертається по циклу до цього вузла, memo вже має відповідь — і рекурсія зупиняється.

![Ліворуч граф-оригінал: вузол monster стрілкою .squad вниз на вузол squad, а squad стрілкою members назад угору на monster — замкнений цикл. У центрі таблиця memo з двома рядками: monster веде до monster штрих, squad веде до squad штрих, з написом «запис ДО рекурсії». Праворуч граф-копія: monster штрих і squad штрих із такими самими двома стрілками, цикл замкнено на себе, копія не вказує на оригінал. Унизу пояснення, що реєстрація копії до рекурсії розриває цикл і зберігає спільну тотожність](img/deepclone-memo.svg)

*memo відображає кожен уже пройдений вузол на його копію. Ключ — записати копію в memo ПЕРЕД тим, як заходити в поля: тоді, дійшовши по циклу назад до вузла, обхід бере готову копію замість нового кола рекурсії. Копія виходить самодостатньою — її цикл замкнено на власні вузли, не на оригінал.*

Ось той самий обхід із memo, руками:

:::tabs
```ts
function deepClone<T>(value: T, memo = new Map<object, any>()): T {
  if (value === null || typeof value !== "object") return value;  // примітив — як є
  if (memo.has(value)) return memo.get(value);   // вже копіювали — ТА САМА копія

  // зберегти клас: копія має той самий прототип, що й оригінал
  const copy = Array.isArray(value)
    ? [] as any
    : Object.create(Object.getPrototypeOf(value));

  memo.set(value, copy);                          // ← реєстрація ДО рекурсії рве цикл
  for (const k of Object.keys(value))
    copy[k] = deepClone((value as any)[k], memo);
  return copy;
}
```
```py
def deep_clone(value, memo=None):
    if memo is None:
        memo = {}
    if isinstance(value, (str, int, float, bool)) or value is None:
        return value                     # примітив — як є
    if id(value) in memo:
        return memo[id(value)]           # вже копіювали — ТА САМА копія

    if isinstance(value, list):
        copy_obj = []
        memo[id(value)] = copy_obj       # ← реєстрація ДО рекурсії рве цикл
        copy_obj.extend(deep_clone(x, memo) for x in value)
        return copy_obj

    cls = value.__class__
    copy_obj = cls.__new__(cls)          # той самий клас, без __init__
    memo[id(value)] = copy_obj           # ← реєстрація ДО рекурсії
    for k, v in value.__dict__.items():
        setattr(copy_obj, k, deep_clone(v, memo))
    return copy_obj
```
:::

Один рядок несе всю вагу: `memo.set(value, copy)` **перед** циклом по полях. Якби ми зареєстрували копію після рекурсії, обхід дійшов би по циклу назад до `value`, не знайшов би його в memo — і пішов би на друге коло, і на нескінченне. Саме так, до речі, і влаштовані вбудовані глибокі копіювальники: `copy.deepcopy` у Python передає в `__deepcopy__(self, memo)` цю саму таблицю, і якщо пишеш хук сам, memo треба **прокинути** далі, зареєструвавши новий об'єкт до рекурсії:

```py
import copy

class Monster:
    def __deepcopy__(self, memo):
        new = Monster.__new__(Monster)
        memo[id(self)] = new             # ЗАРЕЄСТРУВАТИ до рекурсії — інакше цикл зламає
        new.name = self.name             # скаляри — як є
        new.hp = self.hp
        new.stats = copy.deepcopy(self.stats, memo)  # углиб, з тим самим memo
        new.loot = list(self.loot)
        new.squad = copy.deepcopy(self.squad, memo)  # цикл: memo поверне вже створений new
        return new
```

`structuredClone` у JavaScript робить те саме внутрішньо — «підтримує мапу вже відвіданих посилань, щоб не обходити цикли нескінченно», — тому цикли він ковтає задарма. Але пам'ятай пастку 2: задарма він при цьому губить клас. memo рятує не лише від циклів: він ще зберігає **спільну тотожність**. Якщо два різні поля вказують на **один** об'єкт (ромб, а не цикл), memo подбає, щоб на них припала **одна** копія, а не дві, — і структура копії дзеркалить структуру оригіналу, а не роздвоює спільні вузли.

## Пастка 4: клонування живих ресурсів

П'ята пастка — найглибша, бо тут ламається сама ідея «скопіювати». Додамо монстрові канал телеметрії — живий мережевий сокет, куди сипляться події:

:::tabs
```ts
class Monster {
  telemetry: Connection;    // ЖИВИЙ сокет — відкрите з'єднання
  // ...
}
```
```py
class Monster:
    def __init__(self, ...):
        self.telemetry = connection   # ЖИВИЙ сокет — відкрите з'єднання
```
:::

Що означає «глибоко скопіювати сокет»? Нічого. Живе TCP-з'єднання — це не байти в пам'яті, а стан **по той бік**: дескриптор в ядрі, порт, буфери, домовленість із віддаленою стороною. Скопіювати його байт-у-байт — отримати дескриптор, що вказує на чуже з'єднання, яким два об'єкти орудують навперебій. Тому `copy.deepcopy` на об'єкті з сокетом або впаде, або зробить каліку, а `structuredClone` чесно кине `DataCloneError`. І це не вада копіювальників — це вони кажуть тобі правду: **машина не знає, що означає копія цього ресурсу**. Знаєш лише ти, і рішень тут три, залежно від сенсу ресурсу:

:::tabs
```ts
class Monster {
  clone(): Monster {
    const c = Object.assign(Object.create(Monster.prototype), this);
    c.stats = this.stats.clone();
    c.loot = [...this.loot];
    // ЖИВІ ресурси — свідоме рішення на кожен:
    c.telemetry = this.telemetry;        // (а) ПОДІЛИТИ: спільна інфраструктура
    c.socket = null;                     // (б) СКИНУТИ: копія під'єднається сама, ліниво
    c.logFile = openLog(this.logPath);   // (в) ПЕРЕВІДКРИТИ: власний свіжий дескриптор
    return c;
  }
}
```
```py
def clone(self):
    c = copy.copy(self)
    c.stats = self.stats.clone()
    c.loot = list(self.loot)
    # ЖИВІ ресурси — свідоме рішення на кожен:
    c.telemetry = self.telemetry         # (а) ПОДІЛИТИ: спільна інфраструктура
    c.socket = None                      # (б) СКИНУТИ: копія під'єднається сама, ліниво
    c.log_file = open_log(self.log_path) # (в) ПЕРЕВІДКРИТИ: власний свіжий дескриптор
    return c
```
:::

Спільний канал телеметрії, куди всі монстри просто дописують події, — **ділимо** (одне посилання на всіх, копіювати нема чого й нема сенсу). Ігровий сокет, який кожен монстр веде свій, — **скидаємо** в `null`, хай копія відкриє власне з'єднання за потреби. Особистий лог-файл — **перевідкриваємо**, щоб у копії був свій дескриптор, а не спільний із зразком. Жодне з цих рішень не «правильніше» абстрактно — правильність визначає **семантика ресурсу**, а її знає лише автор класу. Це і є найглибша причина, чому `clone()` живе всередині об'єкта, а не в реєстрі: тільки клас знає, які з його полів — значення, які — спільна інфраструктура, а які — живі дескриптори, що їх копіювати не можна взагалі. Розкладання полів на «володіє / позичає» — та сама лінія, за якою [керування ресурсом через час життя (RAII)](topic:programming/raii) відрізняє власника від користувача: копія власника зобов'язана дістати **свій** ресурс, копія користувача — лишити спільне посилання.

## Складність і вартість

Порахуймо холодно, скільки коштує ця машина.

```
пошук у реєстрі:    O(1)              хеш-мапа: ключ → зразок
create(ключ):       O(1) + вартість одного clone()

поверхнева копія:   O(полів)          ≈ O(1) — фіксоване число полів
глибока копія:      O(вузлів графа)   і час, і пам'ять — увесь досяжний граф
memo:               +O(вузлів)        таблиця вже скопійованих
```

Головне тут — де саме ховається ціна. Сам реєстр дешевий: пошук зразка — стала, і хоч тисяча видів у мапі, хоч десяток — `create` коштує однаково. **Уся вартість — у `clone()`**, і росте вона з **розміром об'єкта**, а не з розміром реєстру. Поверхнева копія майже безкоштовна — скопіювати фіксоване число полів. Глибока — платить за **весь досяжний граф**: щоб наплодити тисячу монстрів із важким вкладеним деревом, ти щоразу відтворюєш усе те дерево, і це може стати домінантою профілю.

Ось де прототип змикається з двома сусідніми ідеями. По-перше, з [незмінністю](topic:programming/immutability): якщо частина графа **незмінна**, її не треба копіювати — незмінне безпечно **ділити**, тож глибока копія зупиняється на межі незмінного піддерева й бере його поверхнево. Правильна відповідь на «дорогу глибоку копію» — часто не швидший копіювальник, а **менше того, що взагалі треба копіювати**. По-друге, з [легковаговиком](topic:programming/flyweight): коли тисячі копій ділять однаковий важкий незмінний стан, розумніше тримати той стан **один** і посилатися на нього з усіх, а копіювати лише тонку змінну оболонку. Прототип і легковаговик тут не суперники, а партнери: перший штампує змінну частину, другий ділить незмінну.

І ось коротка мапа всього рішення — що робить коректний `clone()` з полем кожного роду:

![Таблиця з трьох колонок: поле такого роду, що робить коректний clone, приклад-поле. Рядок скаляр число булеве незмінний рядок — скопіювати значення стається саме собою — приклад hp name. Рядок вкладений змінний обєкт або список — глибока копія власний примірник, зелений акцент — приклад loot stats. Рядок незмінний вкладений обєкт — поділити shallow безпечно й дешево — приклад конфіг-константа. Рядок живий ресурс сокет файл лок — не копіювати поділити або перевідкрити наново, червоний акцент — приклад socket fd. Рядок зворотне циклічне посилання — memo та сама копія а не нова гілка, синій акцент — приклад squad member. Унизу підпис, що механізм не вгадає семантику за тебе](img/clone-field-decision.svg)

*Реєстр тривіальний — мапа плюс `clone()`. Уся істина живе в цій таблиці: глибину копії обирають не на об'єкт цілком, а на кожне поле окремо, за його роллю. Скаляр — значення; змінний вкладений — углиб; незмінний — поділити; живий ресурс — поділити чи перевідкрити; цикл — через memo. Механізм не вгадає ці ролі за тебе, тому нетривіальний `clone()` завжди пишуть руками.*

## Підсумок

Реєстр прототипів обіцяє просту річ — «дай ключ, отримай новий налаштований об'єкт» — і виконує її десятком рядків: мапа `ключ → зразок` плюс `create`, що знаходить зразок і кличе `clone()`. Додати вид — покласти ще один зразок; жодного `if` за типом, і нові види можна реєструвати навіть під час роботи.

Але вся чесна складність зсунута в `clone()`, і вона не зникає, а лише набуває форми **рішення на кожне поле**. Скаляр скопіюється сам. Вкладений змінний стан треба взяти вглиб — власний примірник, інакше дві копії лишаться потай одним. Незмінне піддерево можна поділити — і зекономити. Живий ресурс копіювати не можна взагалі — його ділять, скидають або перевідкривають, і що саме — знає лише автор класу. Цикл і спільні вузли розв'язує таблиця memo, зареєстрована **до** рекурсії. А над усім цим висить обов'язок тримати `clone()` у синхроні з полями, бо забуте поле — це тиха напівкопія.

Жоден універсальний копіювальник цих рішень за тебе не ухвалить: `structuredClone` згубить клас із методами, `deepcopy` вдавиться живим сокетом, поверхневий дефолт мовчки зчепить копії. Тому нетривіальний `clone()` пишуть руками — не тому, що бракує інструмента, а тому, що глибина копії кодує **семантику** об'єкта, а семантику знає лише той, хто цей об'єкт спроєктував. Обереш глибину свідомо на кожному полі — дістанеш дешеву, гнучку фабрику, що плодить справді незалежні об'єкти. Обереш недбало — двох, що назавжди лишилися одним.
