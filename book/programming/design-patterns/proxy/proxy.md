- [Зчеплення і зв'язність](book:programming/coupling-cohesion) — мірило «наскільки міцно частини зрощені»; проксі вставляють, щоб клієнт не був зчеплений із дорогими чи небезпечними подробицями доступу до об'єкта.
</preknowlist>

Уяви, що в тебе є об'єкт, який завантажує з диска велике зображення — скажімо, скан на сто мегабайтів. Створити такий об'єкт означає прочитати весь файл у пам'ять. А тепер уяви документ на дві тисячі сторінок, де кожна сторінка має таку картинку. Якщо чесно створити всі об'єкти-картинки, коли відкриваєш документ, програма з'їсть двісті гігабайтів і замре — а користувач, найпевніше, гортатиме лише перші кілька сторінок і решту не гляне ніколи.

Хочеться, щоб об'єкт-картинка **поводився** так, ніби він уже є, — щоб решта коду просила в нього розмір, малювала його, робила все звичне, — але щоб важкий файл із диска підтягувався **тільки тоді**, коли картинку справді треба намалювати. До того моменту хай на її місці сидить щось легке, що вдає з себе картинку.

Оце «щось легке, що вдає з себе справжній об'єкт і підставляється замість нього» і є **проксі (англ. *proxy* — представник, повірений; від середньоангл. *procucie* ← середньолат. *procuratia* ← лат. *procuratio*, *procurare* — вести справи за когось, діяти замість нього)**. Слово прийшло з юридичної мови: проксі — це той, кому доручили діяти від твого імені, поки тебе немає. Той самий сенс переїхав у код без змін: об'єкт-заступник, що стоїть на місці справжнього об'єкта й контролює доступ до нього.

Розберімося, чому підставний об'єкт мусить мати **той самий інтерфейс**, які буває користь від такої підстановки, де проксі легко сплутати з двома дуже схожими на нього патернами — і чим за нього доводиться платити.

## Проксі — це заступник із тим самим інтерфейсом

Ключова умова, без якої нічого не працює: проксі мусить бути для клієнта **невідрізнимим** від справжнього об'єкта. Клієнт тримає в руках тип «картинка» й викликає в нього `draw()` та `width()`. Йому байдуже, чи це та сама важка картинка, чи заступник, — аби відповідав на ті самі виклики. Тому проксі й оригінал реалізують **один інтерфейс**, а клієнт працює через цей інтерфейс, не знаючи, хто перед ним.

> 🔧 **Навіщо це.** Спільний інтерфейс — це те, що робить проксі **непомітним**. Ти можеш узяти вже написану систему, яка всюди працює з `Image`, і підсунути їй проксі замість справжніх картинок — і не змінити в цій системі жодного рядка. Уся вигода (відкладене завантаження, контроль прав, кеш) з'являється в одному місці — там, де створюють об'єкт, — а решта коду не здогадується, що щось помінялося. Саме через це проксі так легко «вкрутити» в наявний код: він грає за правилами інтерфейсу, який уже є.

Усередині проксі тримає **посилання на справжній об'єкт** (або спосіб його дістати) і на кожен виклик вирішує: віддати відповідь самому чи перекласти виклик на справжній об'єкт. Оце «перекласти виклик далі» називають **делегуванням (англ. *delegation* — передавання доручення)** — проксі не робить роботу сам, він доручає її тому, кого заступає, іноді додавши щось до або після.

Ось той самий приклад із картинкою в коді. Спочатку — спільний інтерфейс і важкий об'єкт:

Тепер проксі з тим самим інтерфейсом. Він **не** читає файл у конструкторі — тримає лише шлях, а справжню картинку створює аж коли по неї приходять:

:::tabs
```ts
class ImageProxy implements Image {
  private real: RealImage | null = null;   // ще немає — файл не читаний
  constructor(private path: string) {}     // конструктор дешевий: лише запам'ятали шлях

  private load(): RealImage {
    if (this.real === null) this.real = new RealImage(this.path);   // читаємо ОДИН раз
    return this.real;
  }

  draw(): void { this.load().draw(); }       // прийшли малювати → тепер треба справжній
  width(): number { return this.load().width(); }
}

// Клієнт не бачить різниці — тип той самий:
const gallery: Image[] = paths.map(p => new ImageProxy(p));   // 2000 картинок, 0 читань із диска
gallery[0].draw();   // читається РІВНО одна — перша
```
```py
class ImageProxy:
    def __init__(self, path: str) -> None:
        self.path = path                # конструктор дешевий: лише запам'ятали шлях
        self._real: RealImage | None = None   # ще немає — файл не читаний

    def _load(self) -> RealImage:
        if self._real is None:
            self._real = RealImage(self.path)   # читаємо ОДИН раз
        return self._real

    def draw(self) -> None:
        self._load().draw()             # прийшли малювати → тепер треба справжній

    def width(self) -> int:
        return self._load().width()

# Клієнт не бачить різниці — тип той самий:
gallery: list[Image] = [ImageProxy(p) for p in paths]   # 2000 картинок, 0 читань із диска
gallery[0].draw()   # читається РІВНО одна — перша
```
```java
class ImageProxy implements Image {
    private final String path;
    private RealImage real = null;      // ще немає — файл не читаний
    ImageProxy(String path) { this.path = path; }   // конструктор дешевий

    private RealImage load() {
        if (real == null) real = new RealImage(path);   // читаємо ОДИН раз
        return real;
    }
    public void draw() { load().draw(); }        // прийшли малювати → тепер треба справжній
    public int width() { return load().width(); }
}

// Клієнт не бачить різниці — тип той самий:
List<Image> gallery = paths.stream().map(ImageProxy::new).toList();
gallery.get(0).draw();   // читається РІВНО одна — перша
```
:::

Відкрити документ тепер коштує стільки, скільки коштує створити дві тисячі порожніх заступників, — тобто майже нічого. Файл із диска читається лише для тієї картинки, яку справді намалювали. Ця конкретна різновидність проксі — та, що відкладає створення дорогого об'єкта, — зветься **віртуальний проксі (англ. *virtual* — той, що існує по суті, але не насправді до пори)**, і трюк усередині нього — це [ліниве завантаження](book:programming/lazy-loading): не робити роботу, поки по результат не прийшли.

Від проксі пунктирна стрілка «створюється аж на перший виклик» веде до справжнього важкого об'єкта, який читає весь файл із диска. *Клієнт працює через інтерфейс і не бачить, хто за ним. Проксі стоїть на місці справжнього об'єкта, а важку роботу підтягує лише коли по неї приходять — до того моменту праворуч порожньо.*

## Чотири речі, заради яких вставляють заступника

Віртуальний проксі — лише один із випадків. Спільне в усіх одне: між клієнтом і об'єктом ставлять прошарок, який **контролює доступ**. А от заради чого саме контролюють — різне, і саме мета дала чотири класичні різновиди проксі. Варто побачити їх разом, бо форма коду в них однакова, а призначення геть різне.

**Віртуальний — щоб відкласти дороге створення.** Це той, що з картинками. Об'єкт важкий (великий файл, з'єднання з базою, довге обчислення), а потрібен буває не завжди. Проксі вдає, що об'єкт уже є, а насправді створює його ліниво — лише коли по нього прийшли. Виграш: не платимо за те, чим не скористалися.

**Захисний — щоб перевіряти права (англ. *protection proxy*).** Об'єкт уміє небезпечні речі (видалити запис, змінити зарплату), і не кожен має право їх робити. Проксі стоїть перед ним і на кожен виклик спершу питає: а цьому користувачеві можна? Можна — делегує далі; ні — кидає відмову. Справжній об'єкт при цьому лишається чистим: він робить свою справу й нічого не знає про права — усю охорону винесено в заступника.

**Віддалений — щоб сховати, що об'єкт на іншій машині (англ. *remote proxy*).** Справжній об'єкт живе на сервері за мережею, а в твоїй програмі стоїть його проксі — місцевий об'єкт із тим самим інтерфейсом. Ти викликаєш у нього метод так, ніби він поруч, а проксі під капотом пакує виклик, шле мережею, чекає відповідь і повертає її тобі. Клієнт пише звичайний виклик методу — а їде він через півсвіту. На цьому стоять цілі механізми на кшталт [віддаленого виклику процедур](book:programming/rpc): місцевий заступник, що вдає віддалений об'єкт.

**Розумне посилання — щоб додати облік довкола доступу (англ. *smart reference*).** Замість голого посилання ставлять проксі, який робить щось корисне на кожному дотику до об'єкта: рахує, скільки місць ним користуються (і звільняє, коли лічильник упав до нуля), кешує вже пораховані відповіді, пише в лог кожен виклик, бере й віддає блокування навколо небезпечних ділянок. Об'єкт лишається простим — уся бухгалтерія доступу висить на заступникові.

![Чотири колонки, у кожній — та сама пара «клієнт → проксі → справжній об'єкт», але проксі підписаний різною роботою. Віртуальний: над стрілкою напис «створюю аж на перший виклик». Захисний: «спершу перевіряю права». Віддалений: «пакую й шлю мережею», а справжній об'єкт намальовано за пунктирною межею машини. Розумне посилання: «рахую виклики / кеш / лог». Внизу спільний підпис: форма однакова, мета різна](/book/programming/design-patterns/proxy/img/proxy-kinds.svg)

*Одна форма — заступник із тим самим інтерфейсом — обслуговує чотири різні потреби. Розрізняє їх не будова, а те, що проксі робить довкола делегованого виклику: відкладає, охороняє, шле мережею чи веде облік.*

Робочий приклад одразу двох корисних різновидів — захисного проксі, що перевіряє права, і розумного посилання, що кешує й логує, — зібрано з покроковим розбором у [окремому проєкті-вставці](book:programming/proxy/proj-access-proxy.md): там показано, як один прошарок додає охорону й кеш, не торкнувшись справжнього сервісу.

## Де проксі плутають: адаптер, декоратор, фасад

Проксі — один із **структурних** патернів (тих, що описують, як зі шматків скласти більшу структуру), і зовні він дуже схожий на трьох сусідів по цій родині: усі вони — «об'єкт, що обгортає інший об'єкт». Форма коду майже однакова: тримаєш посилання всередині й делегуєш виклики. Різниця не в будові, а в **намірі** — навіщо обгортка стоїть. Сплутати їх легко, і на співбесідах саме тут ловлять; розведімо їх чітко.

**Проксі проти [адаптера](book:programming/adapter).** Адаптер обгортає об'єкт, щоб **змінити його інтерфейс** — перекласти чужий, незручний набір методів на той, якого чекає твій код. Клієнт адаптера й обгорнутий об'єкт розмовляють **різними** мовами, адаптер їх мирить. Проксі ж навпаки: інтерфейс лишається **той самий**, змінюється не форма викликів, а **контроль доступу** до них. Правило коротко: адаптер міняє інтерфейс і не міняє суті доступу; проксі міняє доступ і не міняє інтерфейсу.

**Проксі проти [декоратора](book:programming/decorator).** Ось найтонша межа, бо обидва зберігають інтерфейс і додають щось довкола виклику. Різниця — у **стосунку до об'єкта та в тому, хто ним керує**. Декоратор **додає нову поведінку** (нову можливість, яку клієнт свідомо хотів навісити) і його зазвичай **чіпляє сам клієнт**, знаючи, що обгортає. Проксі **керує доступом** до об'єкта (створенням, правами, місцем, обліком) і робить це **непомітно** — клієнт часто навіть не знає, що між ним і об'єктом хтось стоїть; проксі нерідко сам **володіє** життєвим циклом справжнього об'єкта (створює його, вирішує, коли він з'явиться). Коротко: декоратор — «дай мені той самий об'єкт, але **з додатковим умінням**», проксі — «дай мені той самий об'єкт, але **під наглядом за доступом**».

**Проксі проти [фасаду](book:programming/facade).** Тут різниця найпростіша. Фасад дає **один спрощений вхід до цілої підсистеми** з багатьох об'єктів — у нього **свій, новий** інтерфейс, і за ним ховається не один об'єкт, а купа. Проксі стоїть перед **одним** об'єктом і має **той самий** інтерфейс, що й той об'єкт. Фасад спрощує складне ціле; проксі підмінює одну конкретну річ.

Одним рядком, щоб трималося в голові: **адаптер міняє інтерфейс, фасад спрощує групу, декоратор додає вміння, проксі контролює доступ.** Форма в усіх схожа — розводить їх лише відповідь на питання «навіщо тут обгортка».

## Дешевша альтернатива і чим доводиться платити

Перш ніж вставляти проксі, чесно постав питання: а чи потрібен окремий клас-заступник узагалі? Часто ту саму мету — «не робити дорогу роботу, поки не попросили» — дає простіший хід: **лінива ініціалізація прямо в об'єкті**. Замість окремого проксі поле лишають порожнім і заповнюють на перший доступ через геттер.

:::tabs
```ts
class Report {
  private chart: Chart | null = null;   // важкий об'єкт, порахуємо ліниво

  getChart(): Chart {
    if (this.chart === null) this.chart = buildExpensiveChart();   // рахуємо ОДИН раз
    return this.chart;
  }
}
```
```py
class Report:
    def __init__(self) -> None:
        self._chart: Chart | None = None    # важкий об'єкт, порахуємо ліниво

    @property
    def chart(self) -> Chart:
        if self._chart is None:
            self._chart = build_expensive_chart()   # рахуємо ОДИН раз
        return self._chart
```
:::

Це не проксі — тут немає окремого об'єкта-заступника з тим самим інтерфейсом, є лише поле, що заповнюється пізно. Такий хід простіший і його варто брати першим. Проксі виграє, коли заступник треба **підставити прозоро замість справжнього об'єкта** в уже написану систему (ту саму галерею з двох тисяч картинок), коли контроль доступу — **не одне поле, а окрема відповідальність** (права, мережа, облік), яку не хочеться розмазувати по об'єкту, або коли заступників треба **багато й однакових**. Немає прозорої підстановки й окремої відповідальності — окремий клас-проксі буде зайвим церемоніалом.

А платить за проксі така ціна. **З'являється ще один рівень непрямості (англ. *indirection*).** Між клієнтом і об'єктом тепер стоїть посередник — кожен виклик іде на стрибок довше, і, читаючи код, треба тримати в голові, що `image.draw()` насправді спершу зайде в заступника. Для рідкісних викликів це не помітно, для гарячого циклу мільйони разів на секунду — вже накладні.

**Проксі мусить чесно повторити весь інтерфейс.** Додав об'єкт новий метод — його треба продублювати й у проксі (згадати про це легко забути, і тоді проксі відстане від оригіналу). У мовах, де інтерфейс широкий, писати таку обгортку руками нудно й помилконебезпечно; частину болю знімають **динамічні проксі** — механізм, що будує заступника автоматично, перехоплюючи будь-який виклик однією точкою, — але й вони не безкоштовні, про них — у [проєкті-вставці](book:programming/proxy/proj-access-proxy.md).

**Прозорість буває підступною.** Саме те, що проксі непомітний, іноді й шкодить: віддалений проксі виглядає як звичайний місцевий об'єкт, і легко забути, що кожен його виклик — це похід у мережу, який може бути повільним або взагалі впасти. Заступник, що вдає простий об'єкт, приховує складність, якої розробникові насправді варто б не забувати. Тому прозорість проксі — сила й пастка водночас: він ховає деталі доступу так добре, що про них перестають думати навіть там, де думати треба.

Підсумок простий. Проксі — це заступник із тим самим інтерфейсом, поставлений перед об'єктом, щоб **контролювати доступ** до нього: відкласти дороге створення, перевірити права, сховати мережу чи додати облік. Він виграє там, де контроль доступу — окрема відповідальність, яку варто винести з об'єкта, а заступника треба підставити прозоро. Але кожен проксі — ще один рівень непрямості й ще один інтерфейс, який треба тримати синхронним; там, де досить лінивого поля чи простого геттера, окремий заступник — зайвий.
