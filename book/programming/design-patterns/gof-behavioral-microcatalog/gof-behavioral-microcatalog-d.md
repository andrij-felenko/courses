# Решта поведінкових оглядово

<preknowlist>
- [Що таке патерн](book:programming/what-is-pattern) — патерн як іменована форма рішення, «сили» задачі, три родини й головне правило «коли патерн НЕ потрібен»; уся стаття міряє два патерни саме цією міркою.
- [Компонувальник](book:programming/composite) — дерево з вузлів за спільним інтерфейсом, де гілка й лист однакові на виклик; дерево виразу в Інтерпретаторі — рівно така структура.
- [Інкапсуляція](book:programming/encapsulation) — приховування внутрішнього стану за інтерфейсом; Знімок існує саме для того, щоб зберегти стан, НЕ ламаючи цього приховування.
- [Рекурсія](book:algorithms/recursion) — обчислення, що кличе себе на менших частинах; так дерево виразу обчислює само себе згори вниз.
</preknowlist>

Поведінкових патернів у класичному каталозі одинадцять, і майже кожен заслужив власну статтю: [Стратегія](book:programming/strategy), [Спостерігач](book:programming/observer), [Команда](book:programming/command), [Стан](book:programming/state), [Ланцюжок обов'язків](book:programming/chain-of-responsibility), [Посередник](book:programming/mediator), [Відвідувач](book:programming/visitor), [Ітератор](book:programming/iterator), [Шаблонний метод](book:programming/template-method) — кожен гасить окремий, широко впізнаваний біль. Лишаються двоє, яких у щоденній роботі зустрічаєш найрідше й тому легко списуєш в «екзотику»: **Інтерпретатор** і **Знімок**. Це не сміттєвий кошик каталогу. Обидва б'ють точно в свою ціль — просто ціль вузька, а обидва до того ж часто читають хибно: Інтерпретатор плутають із «як написати парсер» (це не він), а Знімок — із «та просто збережи копію» (він точніший). Розберімо кожен: яку силу він гасить, який один хід робить і — головне — ту тонку смугу, де він справді окупається.

## Інтерпретатор: граматика стає деревом класів

Уяви, що в програмі завелася маленька власна «мовця». У клітинках таблиці — формули на кшталт `x + 3 * 2`. У фільтрі звітів — правила `ціна > 100 І категорія = "книги"`. У пошуку — булеві запити. Спільне тут одне: є **простий, сталий набір правил**, за якими будуються вирази, і ці вирази треба **обчислювати** — знову і знову, причому самі вирази з'являються **під час роботи** програми (їх набирає користувач), а не пишуться в коді наперед.

Найпряміший підхід — один обчислювач, що дивиться на тип вузла й розгалужується. Спершу текст розбирають у дерево вузлів (число, змінна, додавання, множення), а тоді рекурсивно його обходять:

```ts
type Node =
  | { op: "num"; value: number }
  | { op: "var"; name: string }
  | { op: "add"; left: Node; right: Node }
  | { op: "mul"; left: Node; right: Node };

function evalNode(n: Node, env: Map<string, number>): number {
  switch (n.op) {
    case "num": return n.value;
    case "var": return env.get(n.name)!;
    case "add": return evalNode(n.left, env) + evalNode(n.right, env);
    case "mul": return evalNode(n.left, env) * evalNode(n.right, env);
  }
}
```

Для крихітної граматики це чесне, ясне рішення, і не варто вдавати, ніби воно погане. Але придивись, де воно тисне: **уся логіка всіх правил зібрана в одному `switch`**. З'явилося нове правило граматики — скажімо, віднімання чи виклик функції — і ти повертаєшся в цей центральний обчислювач правити його. А якщо над деревом є ще й інші операції (не лише «обчислити», а й «надрукувати гарно», «перевірити типи»), то кожна з них — свій `switch` з тими самими гілками, і додати правило означає обійти їх усі.

Патерн **Інтерпретатор (лат. *interpres* — тлумач, посередник)** робить один розворот: **зроби кожне правило граматики окремим класом, і хай кожен клас уміє обчислити сам себе**. Число — клас. Змінна — клас. Додавання — клас, що тримає два під-вирази. У кожного з них є метод `interpret()`. Вираз перетворюється на **дерево** таких об'єктів (це і є [абстрактне синтаксичне дерево, AST](book:algorithms/abstract-syntax-tree)), а обчислення — це виклик `interpret()` на корені, який рекурсивно кличе `interpret()` у дітей, і значення спливають знизу вгору:

:::tabs
```ts
// Спільний інтерфейс: кожен вузол уміє обчислити сам себе
interface Expr {
  interpret(env: Map<string, number>): number;
}

// Термінали — листя дерева: обчислюються без звертань кудись далі
class Num implements Expr {
  constructor(private value: number) {}
  interpret(_env: Map<string, number>): number { return this.value; }
}
class Var implements Expr {
  constructor(private name: string) {}
  interpret(env: Map<string, number>): number {
    const v = env.get(this.name);
    if (v === undefined) throw new Error(`невідома змінна ${this.name}`);
    return v;
  }
}

// Нетермінали — тримають під-вирази й рекурсивно їх обчислюють
class Add implements Expr {
  constructor(private left: Expr, private right: Expr) {}
  interpret(env: Map<string, number>): number {
    return this.left.interpret(env) + this.right.interpret(env);
  }
}
class Mul implements Expr {
  constructor(private left: Expr, private right: Expr) {}
  interpret(env: Map<string, number>): number {
    return this.left.interpret(env) * this.right.interpret(env);
  }
}

// Вираз "x + 3 * 2" — зібраний як дерево об'єктів
const tree: Expr = new Add(new Var("x"), new Mul(new Num(3), new Num(2)));
console.log(tree.interpret(new Map([["x", 5]])));   // 11
```
```py
from __future__ import annotations
from typing import Protocol

# Спільний інтерфейс: кожен вузол уміє обчислити сам себе
class Expr(Protocol):
    def interpret(self, env: dict[str, int]) -> int: ...

# Термінали — листя дерева: обчислюються без звертань кудись далі
class Num:
    def __init__(self, value: int): self.value = value
    def interpret(self, env: dict[str, int]) -> int:
        return self.value

class Var:
    def __init__(self, name: str): self.name = name
    def interpret(self, env: dict[str, int]) -> int:
        if self.name not in env:
            raise KeyError(f"невідома змінна {self.name}")
        return env[self.name]

# Нетермінали — тримають під-вирази й рекурсивно їх обчислюють
class Add:
    def __init__(self, left: Expr, right: Expr):
        self.left, self.right = left, right
    def interpret(self, env: dict[str, int]) -> int:
        return self.left.interpret(env) + self.right.interpret(env)

class Mul:
    def __init__(self, left: Expr, right: Expr):
        self.left, self.right = left, right
    def interpret(self, env: dict[str, int]) -> int:
        return self.left.interpret(env) * self.right.interpret(env)

# Вираз "x + 3 * 2" — зібраний як дерево об'єктів
tree: Expr = Add(Var("x"), Mul(Num(3), Num(2)))
print(tree.interpret({"x": 5}))   # 11
```
:::

Ось у чому суть перетворення. Дерево виразу — це [Компонувальник](book:programming/composite), застосований до граматики: корінь `Add` викликає `interpret()` у своїх дітей і **не знає й не питає**, що там під ним — ще одна операція чи голе число, бо і гілка, і лист однакові на цей виклик. Рекурсія робить усю решту: виклик іде вниз по гілках, а значення повертаються вгору й поєднуються. Тому `x + 3 * 2` при `x = 5` дає `5 + (3 · 2) = 11`, і жоден вузол не бачить дерева цілком — кожен знає лише свій шматок.

![Дерево виразу «x + 3 * 2» з об'єктів-вузлів: корінь Add тримає лист Var(x) і вузол Mul, а Mul тримає листя Num(3) і Num(2). Кожен вузол підписаний своїм результатом interpret: Var(x) дає 5, Num(3) дає 3, Num(2) дає 2, Mul дає 6, Add дає 11. Стрілки йдуть від батька до дітей — це виклик interpret вниз, а значення спливають угору](/book/programming/design-patterns/gof-behavioral-microcatalog/img/interpreter-ast.svg)

*Кожне правило граматики стало класом, кожен вузол уміє обчислити себе, а дерево обчислюється рекурсивно: виклик спускається до листя, значення спливають до кореня. Корінь не розрізняє, гілка під ним чи лист — у цьому й полягає Компонувальник під граматикою.*

> 🔧 **Навіщо це.** Виграш патерну — рівно один і його варто назвати чесно: **нове правило граматики додається новим класом, а центральний обчислювач чіпати не треба**. Хочеш додати віднімання — пишеш клас `Sub` збоку, і жоден наявний клас не відкриваєш. Це прямий [принцип відкритості-закритості](book:programming/open-closed) у дії. Але тут-таки ховається й ціна: якщо натомість додаєш нову **операцію** над деревом (не «обчислити», а «надрукувати»), доведеться дописати метод у **кожен** клас-вузол. Класи легко ростуть новими правилами, але важко — новими операціями; `switch` — навпаки. Це дві сторони [проблеми виразу](book:programming/open-closed/math-expression-problem.md), і Інтерпретатор свідомо стає на бік «легко додавати правила».

Тепер найважливіша межа, бо саме на ній Інтерпретатор найчастіше розуміють хибно. Патерн каже **нічого** про те, як із рядка `"x + 3 * 2"` одержати це дерево. Перетворення тексту в дерево — це **розбір (парсинг)**, окрема й зазвичай важча робота: спершу текст ріжуть на лексеми, тоді за граматикою складають дерево ([стадії компілятора](book:programming/compiler-stages) якраз про це). Інтерпретатор покриває лише **другу половину** — обчислити вже готове дерево. Плутанина «Інтерпретатор = парсер» коштує людям марних годин: вони беруться писати класи-правила там, де насправді болить розбір тексту, а це зовсім інша задача.

І друга межа — масштаб. Один клас на одне правило означає, що справжня мова з десятками правил **вибухає** десятками класів. Тому автори каталогу прямо обмежують застосування: патерн — для граматик **простих** і там, де швидкодія не критична. Щойно граматика починає рости, ти кидаєш Інтерпретатор і береш генератор парсерів або повноцінний конвеєр компіляції — це буквально та задача, під яку такі інструменти зроблено.

Виходить вузька, але справжня смуга, де Інтерпретатор окупається: граматика **крихітна й стала** (жменя правил), вирази **змінні** (їх дають під час роботи) і обчислюєш ти їх **часто**. Класичні живі приклади — зіставлення з простими регулярними виразами (саме такою мовою патерн і ілюстрували його автори), рушії правил і фільтрів, обчислення формул у клітинках. А коли операцій над деревом стає багато, патерн природно перевертають у [Відвідувач](book:programming/visitor): вузли лишають тонкими, а операції виносять назовні окремими об'єктами — і тоді вже легко додавати операції, а не правила.

## Знімок: зберегти стан, не зламавши печатку

Друга задача геть з іншого боку життя об'єктів. Тобі потрібне **скасування** (undo): зафіксувати стан об'єкта зараз і повернути його пізніше, якщо користувач передумав. Найпряміше, що спадає на думку, — залізти в об'єкт, прочитати всі його приватні поля, скласти їх кудись, а на скасуванні записати назад.

І тут-таки ти ламаєш найголовніше. Щоб «залізти й прочитати всі поля», доводиться **виставити нутрощі назовні**: зробити поля публічними або додати геттери на кожне. Відтепер увесь світ — стос скасувань, логер, будь-хто — знає й залежить від приватного розкладу об'єкта. Змінив внутрішнє влаштування — і зламав тих, хто робив знімки. [Інкапсуляція](book:programming/encapsulation), заради якої поля й ховали, мертва: приховане перестало бути прихованим рівно тому, що його треба було зберегти.

Патерн **Знімок (англ. *Memento*, від лат. *mementō* — наказ «пам'ятай!»)** розв'язує цю суперечність одним ходом: **хай сам об'єкт видає непрозорий знімок свого стану — і сам-таки вміє відновитися з нього**. Знімок — це **запечатана коробка**. Той, хто скасовує, тримає її в руках, але **заглянути всередину не може**; наповнити її й прочитати вміє лише той об'єкт, що її створив. Стан зберігається — а нутрощі назовні так і не вийшли.

У патерні три ролі, і всю силу дає саме розподіл прав між ними:

- **Джерело (Originator)** — об'єкт, чий стан зберігаємо. Тільки він уміє спакувати свій стан у знімок і розпакувати назад.
- **Знімок (Memento)** — непрозора запечатана коробка зі станом. Для всіх, окрім Джерела, вона без ручок: тримати можна, відкрити — ні.
- **Доглядач (Caretaker)** — той, хто знає, **коли** зберігати й відновлювати (напр. стос скасувань). Тримає знімки, впорядковує їх у часі, але **всередину не заглядає ніколи**.

:::tabs
```ts
// Знімок — непрозора коробка. Доглядач може її ТРИМАТИ,
// але поля читає лише сам редактор, що її створив.
class EditorMemento {
  constructor(
    readonly text: string,       // readonly: знімок — фотографія, не жива змінна
    readonly cursor: number,
  ) {}
}

class Editor {                    // Джерело
  private text = "";
  private cursor = 0;

  type(s: string) {
    this.text = this.text.slice(0, this.cursor) + s + this.text.slice(this.cursor);
    this.cursor += s.length;
  }

  save(): EditorMemento {         // САМЕ пакує свій стан у коробку
    return new EditorMemento(this.text, this.cursor);
  }
  restore(m: EditorMemento) {     // і САМЕ вміє з неї відновитися
    this.text = m.text;
    this.cursor = m.cursor;
  }
  toString() { return this.text; }
}

// Доглядач — стос скасувань: тримає коробки, всередину не заглядає
const editor = new Editor();
const history: EditorMemento[] = [];

editor.type("Привіт");
history.push(editor.save());      // контрольна точка
editor.type(", світе");
console.log(`${editor}`);          // "Привіт, світе"

editor.restore(history.pop()!);   // undo
console.log(`${editor}`);          // "Привіт"
```
```py
from dataclasses import dataclass

# frozen=True: знімок незмінний — справжня фотографія, а не посилання на живий стан
@dataclass(frozen=True)
class EditorMemento:
    text: str
    cursor: int

class Editor:                     # Джерело
    def __init__(self):
        self._text = ""
        self._cursor = 0

    def type(self, s: str) -> None:
        self._text = self._text[:self._cursor] + s + self._text[self._cursor:]
        self._cursor += len(s)

    def save(self) -> EditorMemento:          # САМЕ пакує свій стан
        return EditorMemento(self._text, self._cursor)

    def restore(self, m: EditorMemento) -> None:   # і САМЕ з нього відновлюється
        self._text, self._cursor = m.text, m.cursor

    def __str__(self) -> str:
        return self._text

# Доглядач — стос скасувань: тримає знімки, всередину не заглядає
editor = Editor()
history: list[EditorMemento] = []

editor.type("Привіт")
history.append(editor.save())     # контрольна точка
editor.type(", світе")
print(editor)                      # Привіт, світе

editor.restore(history.pop())     # undo
print(editor)                      # Привіт
```
:::

![Три ролі Знімка. Ліворуч Джерело — редактор із прихованим станом (text, cursor). Посередині Знімок — запечатана коробка з замком, підпис «читає лише Джерело». Праворуч Доглядач — стос таких коробок (історія скасувань) з підписом «тримає, але не відкриває». Стрілка save() веде від Джерела до Знімка (пакує стан), стрілка restore() веде назад (вертає стан), стрілка «у стос» веде від Знімка до Доглядача](/book/programming/design-patterns/gof-behavioral-microcatalog/img/memento-roles.svg)

*Уся дисципліна патерну — в тому, хто має право відкрити коробку. Джерело пакує й розпаковує; Доглядач лише тримає впорядкований стос коробок і всередину не заглядає. Так зберегти-і-відновити стає можливим без витоку нутрощів назовні.*

> 🔧 **Навіщо це.** Практична цінність — не в самому «зберегти стан» (це вміє будь-яка копія), а в тому, що стан зберігається **не пробиваючи інкапсуляцію**. Доглядач тримає хоч тисячу знімків і нічого не знає про поля редактора — тож завтра ти переробиш внутрішнє влаштування редактора, а стос скасувань навіть не помітить. У мовах зі справжнім приватним доступом печатку забезпечує компілятор: у Java Знімок роблять вкладеним класом, у C++ — через `friend`, і тоді поля коробки фізично недосяжні нікому, крім Джерела. У Python і TypeScript такого замка немає — там печатка тримається на домовленості (Доглядач просто не чіпає полів), але сама розстановка ролей лишається тією самою.

Скасування рідко живе саме собою — зазвичай це [Команда](book:programming/command) плюс Знімок. Команда загортає дію в об'єкт; коли дію не можна чисто обернути (немає акуратного «анти-ходу», який точно поверне все як було), Команда перед виконанням бере Знімок стану **до себе**, а на скасуванні просто його відновлює. Два патерни складаються в одну систему undo: Команда відповідає «що зробити й спробувати відкотити», Знімок — «як безпечно повернути стан, коли відкотити ходом не вийшло».

Знімок — не єдина відповідь на «повернути минуле», і його варто бачити на тлі сусіда. Знімок зберігає **повний стан** щоразу; альтернатива — зберігати не стани, а **послідовність змін** і відтворювати їх ([event sourcing](book:programming/event-sourcing)). Різниця — це класичний обмін «пам'ять проти обчислення»:

```
Знімок:        S₀   S₁   S₂   S₃      ← повний стан на кожен крок
               відновити крок 3 = взяти готовий S₃  (миттєво, зате пам'ять на кожен знімок)

Журнал змін:   S₀ · Δ₁ · Δ₂ · Δ₃      ← база плюс дрібні дельти
               відновити крок 3 = S₀ ⊕ Δ₁ ⊕ Δ₂ ⊕ Δ₃  (компактно, зате треба відтворити зміни)
```

![Порівняння двох способів повернути минуле. Верхній ряд — Знімок: чотири однакові повні коробки станів S0, S1, S2, S3; відновлення кроку 3 бере готову коробку S3 миттєво, але кожна коробка займає повну пам'ять. Нижній ряд — журнал змін: одна повна база S0 і три маленькі дельти Δ1, Δ2, Δ3; відновлення кроку 3 складає базу з усіма дельтами — компактно в пам'яті, зате відновлення коштує відтворення](/book/programming/design-patterns/gof-behavioral-microcatalog/img/memento-vs-eventlog.svg)

*Знімок платить пам'яттю за миттєве відновлення; журнал змін платить обчисленням за компактність. Реальні системи часто беруть середину: рідкі повні знімки як опорні точки, а між ними — журнал дрібних змін.*

Звідси й головні пастки Знімка. Перша — **пам'ять**: знімки бувають великі й часті, і наївне «повний знімок на кожне натискання клавіші» роздуває пам'ять до неможливого. Тому на практиці зберігають дельти, або роблять повний знімок раз на кілька кроків, а між ними — журнал змін. Друга, підступніша — **глибина копії**. Якщо знімок зберігає не значення, а посилання на змінний під-об'єкт, який Джерело потім міняє, то знімок «попсується» заднім числом: ти відновиш стан і дістанеш не минуле, а спотворене теперішнє. Знімок мусить бути справжньою фотографією, а не посиланням на живий стан — тому знімають або глибоку копію, або [незмінні структури](book:programming/immutability), для яких «знімок» майже безкоштовний (старе посилання ніхто не зіпсує), або тримають спільні дані [копіюванням-при-записі](book:algorithms/copy-on-write).

## Два різні відповіді, одна родина

Спільного між цими патернами — майже нічого, окрім місця в каталозі, і це варто проговорити прямо. Інтерпретатор — про **структуру поведінки**: маленьку мову, подану деревом об'єктів, що самі себе обчислюють. Знімок — про **стан у часі**: зняти й повернути його, не зламавши печатку інкапсуляції. Один розкладає граматику по класах, другий стереже приватність під час збереження — різні задачі, різні механізми.

Об'єднує їх лише те, з чого стаття й почалася: обидва — не робочі коні. Жоден не варто «застосовувати», бо вивчив; обидва вмикаються, лише коли задача точно збіглася з їхньою вузькою нішею. Інтерпретатор — крихітна стала граматика, яку часто обчислюєш і не збираєшся вирощувати. Знімок — скасування чи відновлення там, де не можна пустити нутрощі об'єкта назовні. Поза цими смугами виграє простіший прямий код — і це не виняток, а той самий закон усіх патернів: [є сила задачі — бери патерн; сили немає — пиши прямо й не чіпай каталогу](book:programming/what-is-pattern).
