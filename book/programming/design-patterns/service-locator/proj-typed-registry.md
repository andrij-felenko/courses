# ⚙️ Реєстр служб по-людськи: типізовані ключі й область на запит

Реєстр служб — таблиця «ключ → готовий об'єкт», з якої код бере потрібне на ім'я, — сам собою не злочин. Є місця, де без нього не обійтися: край веб-каркаса, що сам створює обробник запиту й не питає, які тобі потрібні залежності; система [плагінів](book:programming/plugin-architecture), яка знаходить розширення на льоту, за вмінням; композиційний корінь, де [DI-контейнер](book:programming/di-container) складає граф об'єктів. Питання не «чи можна взагалі», а вужче й практичніше: **як зібрати реєстр так, щоб він не приволік за собою двох найгостріших вад свого наївного варіанта**.

А наївний варіант — оцей:

```ts
class Locator {
  private static map = new Map<string, unknown>();
  static register(key: string, value: unknown): void { Locator.map.set(key, value); }
  static get(key: string): unknown { return Locator.map.get(key); }
}

Locator.register("gateway", new StripeGateway());          // на старті програми

const gateway = Locator.get("gateway") as PaymentGateway;  // ① приведення руками, у кожній точці
gateway.charge(order.total());

const g = Locator.get("getway") as PaymentGateway;         // ② одрук: компілюється, g === undefined
g.charge(order.total());                                    //    → TypeError аж у рантаймі
```

Тут дві незалежні болячки, і плутати їх не варто, бо лікуються вони окремо. Перша — **ключ-рядок**. `get` повертає `unknown` («хтозна-що»), тож на кожному виклику доводиться руками дописувати `as PaymentGateway`, і ніхто не звіряє, що під цим ключем справді лежить шлюз, а не годинник. А `"getway"` замість `"gateway"` — звичайнісінький одрук — компілятор пропускає без єдиного слова: рядок є рядок. Помилка визріває мовчки й вибухає лише тоді, коли по службу нарешті прийдуть, — може, за пів години після старту, під навантаженням, у проді. Друга болячка ортогональна першій: реєстр **статичний і один на всю програму**. Те `static map` — це [глобальний стан](book:programming/global-state), спільне змінне сховище для всіх запитів і всіх тестів заразом.

Дві вади — дві латки, і накладемо їх нарізно: спершу вкладемо **тип у сам ключ**, тоді дамо кожному запитові **свій екземпляр реєстру** замість одного спільного глобала.

## Ключ, що несе тип

Ідея першої латки коротка: якщо ключ носитиме при собі тип служби, яку позначає, то компілятор зможе і перевірити, що ти кладеш під нього правильну реалізацію, і повернути тобі точний тип, коли береш, — без жодного приведення руками. А одрук у ключі стане не «іншим рядком», а посиланням на те, чого не існує, — і компілятор ловитиме його негайно.

:::tabs
```ts
// Токен — звичайне значення, але параметризоване типом служби, яку він позначає.
class Token<T> {
  // Поле-фантом: у типі є, у рантаймі — нема (declare не породжує жодного коду).
  // Без згадки T компілятор вважав би Token<A> і Token<B> взаємозамінними; поле це лікує.
  declare readonly _service: T;
  constructor(readonly description: string) {}
}

class ServiceRegistry {
  private map = new Map<Token<unknown>, unknown>();

  // register вимагає, щоб value був саме тим T, що обіцяє токен.
  register<T>(token: Token<T>, value: T): void {
    this.map.set(token, value);
  }

  // resolve повертає T, не any. Єдине приведення заховане ТУТ і виправдане register.
  resolve<T>(token: Token<T>): T {
    if (!this.map.has(token)) {
      throw new Error(`Служба не зареєстрована: ${token.description}`);
    }
    return this.map.get(token) as T;
  }
}

// Токени — константи в одному місці. Ключ — це вони, а не рядок.
const GATEWAY = new Token<PaymentGateway>("payment-gateway");
const CLOCK   = new Token<Clock>("clock");

registry.register(GATEWAY, new StripeGateway());   // ok: StripeGateway is PaymentGateway
// registry.register(GATEWAY, new SystemClock());  // ✗ компілятор: Clock не є PaymentGateway

const gateway = registry.resolve(GATEWAY);         // тип: PaymentGateway, без приведення
// registry.resolve(GATEWY);                        // ✗ компілятор: Cannot find name 'GATEWY'
```
```csharp
// У .NET ключем стає сам тип служби — рядків нема взагалі.
var services = new ServiceCollection();
services.AddSingleton<IPaymentGateway, StripeGateway>();   // обіцянка → реалізація
var provider = services.BuildServiceProvider();

// GetRequiredService<T> повертає T, не object — тип живе в самому виклику:
IPaymentGateway gateway = provider.GetRequiredService<IPaymentGateway>();
// provider.GetRequiredService<IPymentGateway>();  // ✗ компілятор: такого типу нема

// Два різні втілення одного інтерфейсу — keyed-служби (з .NET 8):
services.AddKeyedScoped<IPaymentGateway, StripeGateway>("primary");
services.AddKeyedScoped<IPaymentGateway, PayPalGateway>("backup");
var backup = provider.GetRequiredKeyedService<IPaymentGateway>("backup");
```
```python
from typing import TypeVar, Protocol, cast

T = TypeVar("T")

class PaymentGateway(Protocol):
    def charge(self, amount: int) -> None: ...

class ServiceRegistry:
    def __init__(self) -> None:
        self._map: dict[type, object] = {}

    def register(self, key: type[T], value: T) -> None:
        self._map[key] = value

    def resolve(self, key: type[T]) -> T:
        if key not in self._map:
            raise LookupError(f"Служба не зареєстрована: {key.__name__}")
        return cast(T, self._map[key])   # єдине приведення, як і в TS

registry.register(PaymentGateway, StripeGateway())  # клас — це ключ
gateway = registry.resolve(PaymentGateway)          # mypy бачить тип PaymentGateway
# registry.resolve(PymentGateway)                   # ✗ NameError на самій згадці
```
:::

Гляньмо, чому ці три версії такі різні на вигляд, хоч ідея одна.

Чому в TypeScript ключем мусить бути об'єкт-токен, а не сам тип? Бо [типи в TypeScript стираються до запуску](book:programming/type-driven-design): у готовому JavaScript від `PaymentGateway` не лишається й сліду, тож узяти тип за ключ нема чим — потрібне *значення*, яке цей тип при собі несе. Токен і є таким значенням: у рантаймі це просто об'єкт з полем `description`, а параметр `<T>` живе винятково в системі типів. Поле `_service: T` — **фантомне** (phantom type — «тип-привид»): його ніколи не читають і не пишуть, `declare` не породжує жодного коду; воно існує лише для того, щоб компілятор вважав `Token<PaymentGateway>` і `Token<Clock>` різними типами, а не однією взаємозамінною формою. У мовах, де тип доступний під час виконання, ця хитрість зайва: у C# ключем стає `typeof(IPaymentGateway)`, у Python — сам об'єкт-клас `PaymentGateway`; там тип — уже повноцінне значення, і носити його в обгортці не треба.

Друге, менш очевидне: ключем у TS-мапі виступає **сам токен, за посиланням** (за тотожністю об'єкта), а зовсім не рядок `description`. Тому два різні `new Token<PaymentGateway>(...)` — це два різні ключі, навіть з однаковим описом; а `description` служить лише тому, щоб було що показати в повідомленні про помилку. Звідси й практика — заводити токени **константами в одному місці** й усюди брати саме їх. Одрук у назві константи (`GATEWY` замість `GATEWAY`) уже не «інший рядок, що тихо не знайдеться», а згадка неоголошеної змінної, і компілятор одразу об неї спотикається.

Найважливіше — куди поділося приведення. Воно не зникло: у TS і Python по одному `as T` / `cast(T, …)` сидить усередині `resolve`. Але сидить воно **в єдиному місці**, і саме там воно виправдане: `register<T>` уже змусив компілятор перевірити, що під токеном `Token<T>` лежить справді `T`. Реєстр бере на себе одне-єдине непідтверджене приведення й натомість роздає всім, хто його вживає, чесно типізований результат. Ззовні жодного `as` більше нема — тип тече сам.

> 🔧 **Навіщо це.** Різниця між `get("gateway") as PaymentGateway` і `resolve(GATEWAY)` — не косметика, а перенесення моменту, коли ловиться помилка, з рантайму на компіляцію. З рядковим ключем кожен одрук і кожна невідповідність типу — це майбутній `TypeError` десь у проді, який ще треба відтворити й вистежити. З типізованим токеном той самий одрук — червоний підкрес у редакторі, поки ти ще пишеш рядок. Ціна латки — кілька констант-токенів; віддача — цілий клас багів, який просто перестає існувати.

![Дві колонки, що ловлять ту саму помилку в різні моменти. Ліворуч, у червоному: рядковий ключ registry.get("getway") з одруком — компілятор пропускає, у рантаймі виходить undefined і виняток; тип повернення unknown, тож усюди потрібне приведення as PaymentGateway. Праворуч, у зеленому: токен registry.resolve(GATEWY) з тим самим одруком — компілятор одразу каже «Cannot find name GATEWY», після виправлення resolve(GATEWAY) повертає точний тип PaymentGateway без жодного приведення. Унизу висновок: секрет один — вкласти тип служби в сам ключ](img/typed-token.svg)

*Той самий одрук у ключі гине у два різні моменти. Рядок доживає до рантайму й падає в проді; токен не компілюється й падає в редакторі. Вклавши тип у ключ, ми перенесли пастку туди, де її видно найраніше.*

## Один екземпляр на запит, а не один на все

Друга латка складніша, бо чіпає не типи, а **строк життя** служби. У наївному локаторі це питання навіть не стоїть: реєстр один, і все в ньому живе рівно стільки, скільки живе програма. Щойно ми забираємо єдиний глобал і даємо кожному запитові власний реєстр, доводиться відповісти на нове запитання: котрі служби мають бути спільні для всіх запитів, а котрі — свої на кожен? Звідси три класичні строки життя (lifetimes), які розрізняє будь-який зрілий [DI-контейнер](book:programming/di-container):

```
singleton — один екземпляр на весь застосунок      (конфіг, годинник, пул з'єднань)
scoped    — один екземпляр на область/запит         (одиниця роботи, поточний користувач)
transient — новий екземпляр на кожне розв'язання     (короткий будівник, разовий об'єкт)
```

Різниця між ними — саме в тому, **де живе кеш готового екземпляра**. І тут криється вся механіка ізоляції, простіша, ніж здається. Заведімо два рівні: **корінь** і **область**.

Корінь створюють один раз на старті. Він тримає рецепти всіх служб (як кожну зробити) і кеш **сінглтонів** — по одному екземпляру на весь застосунок. Після старту корінь **заморожують**: більше в нього нічого не реєструють. На кожен запит від кореня відгалужують **область** (scope) — легкий об'єкт із власним, окремим кешем для **scoped**-служб. Сінглтон область бере з кореня (той самий для всіх), а scoped робить і кладе **до себе**; наступний запит дістане свою, свіжу. Коли запит завершився, область звільняють — і разом з нею гинуть усі її scoped-екземпляри та все, що вони тримали.

:::tabs
```ts
type Lifetime = "singleton" | "scoped" | "transient";
type Factory<T> = (scope: Scope) => T;

class Root {
  private recipes = new Map<Token<unknown>, { life: Lifetime; make: Factory<unknown> }>();
  private singletons = new Map<Token<unknown>, unknown>();   // спільний кеш — на КОРЕНІ
  private frozen = false;

  register<T>(token: Token<T>, life: Lifetime, make: Factory<T>): void {
    if (this.frozen) throw new Error("Реєстрація лише до заморозки кореня");
    this.recipes.set(token, { life, make });
  }
  freeze(): void { this.frozen = true; }

  recipe(token: Token<unknown>) {
    const r = this.recipes.get(token);
    if (!r) throw new Error(`Не зареєстровано: ${token.description}`);
    return r;
  }
  singleton<T>(token: Token<T>, scope: Scope): T {
    if (!this.singletons.has(token)) this.singletons.set(token, this.recipe(token).make(scope));
    return this.singletons.get(token) as T;
  }
  createScope(): Scope { return new Scope(this); }
}

class Scope {
  private cache = new Map<Token<unknown>, unknown>();   // scoped-кеш — свій на КОЖНУ область
  constructor(private root: Root) {}

  resolve<T>(token: Token<T>): T {
    const { life, make } = this.root.recipe(token);
    if (life === "singleton") return this.root.singleton(token, this);
    if (life === "transient") return make(this) as T;    // новий щоразу
    if (!this.cache.has(token)) this.cache.set(token, make(this));  // scoped: один на цю область
    return this.cache.get(token) as T;
  }
}
```
```csharp
// Каркас робить те саме, лиш ховає рівні за словами Singleton/Scoped/Transient.
var services = new ServiceCollection();
services.AddSingleton<IClock, SystemClock>();          // один на весь застосунок
services.AddScoped<IUnitOfWork, EfUnitOfWork>();        // один на область (запит)
services.AddTransient<IEmailBuilder, EmailBuilder>();   // новий на кожне розв'язання
var root = services.BuildServiceProvider();             // корінь; рецепти заморожено

// обробник запиту (спрощено):
using (IServiceScope scope = root.CreateScope())        // нова область на цей запит
{
    var uow = scope.ServiceProvider.GetRequiredService<IUnitOfWork>();
    HandleRequest(uow);
}   // Dispose області: усі її scoped-служби звільнено (транзакція, з'єднання закрито)
```
:::

Уся ізоляція тримається на одному реченні: **кеш сінглтонів лежить на корені (спільний для всіх), а кеш scoped — на області (свій на кожен запит)**. Запит A і запит B бачать той самий `SystemClock`, бо він на корені, — але кожен має власну `UnitOfWork`, бо вона на його області. Спільного змінного сховища між запитами більше нема: те, що мусить бути спільним, свідомо винесене в сінглтони, а решта роз'їхалася по областях.

![Два рівні кешу. Угорі — корінь, заморожений на старті: у ньому рецепти всіх служб і кеш сінглтонів (Clock, Config), спільних для всіх. Донизу від нього createScope() відгалужує дві області — запиту A і запиту B; у кожної свій окремий кеш scoped-служб (UnitOfWork·A і UnitOfWork·B), і одна одної вони не бачать. Сінглтони обидві області беруть з кореня — ті самі. На краю кожного запиту область dispose-иться, і її scoped-екземпляри звільняються разом із утриманими ресурсами](img/scope-tree.svg)

*Сінглтон живе на корені — один на всіх; scoped живе на області — свій на кожен запит і гине разом з нею. Ізоляція запитів і тестів виникає не з дисципліни, а з того, де саме стоїть кеш готового екземпляра.*

Ту саму область на краю системи не смикають зусібіч, а **подають далі [впровадженням](book:programming/dependency-injection)**: обробник дістає з області все потрібне в одній точці й передає чистому нутру вже конкретні служби, а не сам реєстр. Тоді реєстр лишається вузькою смужкою на межі, а ядро про жодні області й токени не знає.

## Пастки, на яких збірка розсипається

Обидві латки прості, поки їх не почати накладати недбало. Ось де це болить найчастіше.

**Реєстрація проти розв'язання — не змішувати в часі.** Це дві різні фази, рознесені й у часі, і в місці. **Реєстрація** (скласти рецепти) стається один раз, на старті, у корені. **Розв'язання** (дістати готовий екземпляр) — багато разів, на кожен запит, з області. Хто починає реєструвати служби посеред обробки запиту — «о, тут якраз бракує, докладу в реєстр» — той повертає собі спільний змінний глобал через чорний хід: два паралельні запити пишуть у ту саму таблицю рецептів і бачать одне одного. Саме тому корінь **заморожують** одразу після старту (у прикладі — прапорець `frozen`, що по заморозці забороняє `register`): після цієї межі реєстр стає **тільки для читання**, і будь-яка спроба щось у нього докласти падає одразу, гучно, а не тихо труїть сусідні запити.

**Полонена залежність — довше життя не сміє тримати коротше.** Найпідступніша пастка строків життя. Уяви сінглтон (живе весь застосунок), який у конструкторі приймає scoped-службу (мала б жити один запит) і кладе її в поле:

```csharp
services.AddSingleton<CurrentUserCache>();          // живе вічно
services.AddScoped<IUnitOfWork, EfUnitOfWork>();     // мав би жити один запит

public class CurrentUserCache            // сінглтон
{
    private readonly IUnitOfWork _uow;   // ← тримає scoped У ПОЛІ
    public CurrentUserCache(IUnitOfWork uow) => _uow = uow;   // полонив його назавжди
}
```

`_uow` — одиниця роботи з живою транзакцією й відкритим з'єднанням до бази — мала померти на краю першого запиту. Але її схопив сінглтон і прибив до себе на весь вік програми. Після першого ж запиту та транзакція протухає, з'єднання закривають на тому боці бази, — а сінглтон і далі тримає цей труп і згодовує його кожному наступному запитові. Помилки повзуть звідусіль і ні на що не схожі, бо причина — не тут, а на місяць тому, коли сінглтон уперше проковтнув чужу scoped-службу.

Правило, що це знімає, просте: **служба може залежати лише від служб рівного або довшого життя**. Сінглтон — тільки від сінглтонів. Scoped — від scoped або сінглтонів. Transient — від будь-кого. Ніколи не навпаки. Термін цей — **полонена залежність (captive dependency)** — увів данський інженер Марк Зеєманн (Mark Seemann), якому на проблему вказав Кшиштоф Козьміц (Krzysztof Koźmic), і розібрав у книжці «Dependency Injection Principles, Practices, and Patterns» (2019, зі Стівеном ван Дьорсеном); статус — усталений галузевий термін. Контейнер Microsoft уміє ловити частину таких випадків прапорцями `ValidateScopes`/`ValidateOnBuild`, але щитом лишається саме правило, а не перевірка.

![Правило життя й полонена залежність. Угорі три смуги-строки життя різної довжини: сінглтон (найдовша — весь застосунок), scoped (середня — один запит), transient (найкоротша — один виклик). Зелені стрілки показують дозволені залежності: щоразу на рівне або довше життя (scoped може залежати від scoped чи сінглтона). Унизу — заборонений випадок: сінглтон тягне стрілку до scoped, тобто до коротшого життя; scoped, схоплений у поле сінглтона, позначено як полоненого — його справжня область скінчилася на пунктирі «кінець запиту», але сінглтон тримає його далі, аж до кінця своєї довгої смуги, з підписом «застаріла транзакція, витік»](img/lifetime-rule.svg)

*Стрілка залежності має вести лише праворуч — на рівне або довше життя. Сінглтон, що вхопив scoped, полонить його поза межами власної області: коротше живе довше, ніж мало, і тягне за собою застарілий стан.*

**Витік стану між запитами — звільняй область і не роби спільним те, що особисте.** Дві сторони однієї монети. Перша: область треба **звільняти** на краю запиту (`dispose`), інакше scoped-екземпляри та їхні ресурси — з'єднання, транзакції, буфери — накопичуються, поки не задушать процес. Друга, підступніша: якщо помилково зробити сінглтоном те, що тримає **особистий** стан запиту (поточного користувача, кошик, буфер відповіді), — цей стан протече в наступний запит, і запит Богдана раптом побачить дані Оксани. Тут вада з розряду прикрих переходить у розряд небезпечних: це вже не баг, а витік між клієнтами. Тому строк життя обирають не «щоб швидше», а за питанням «цей стан спільний для всіх чи особистий для запиту?»: особисте — тільки `scoped` або `transient`, ніколи `singleton`.

**Не «чистити» глобал, а створювати область.** Спокуса, що зводить обидві латки нанівець: лишити один статичний реєстр, а між запитами (чи між тестами) його «очищати» — витерти й наповнити знову. Це той самий спільний змінний глобал, тільки з ілюзією ладу. Варто пустити запити чи тести **паралельно** — і вони почнуть перезаписувати одне одному спільну таблицю: один поклав підробку, другий тим часом іншу, обидва бачать чуже, і жоден тест не відтворюється. Ізоляція виникає не з очищення спільного, а з того, що спільного **нема**: кожен запит і кожен тест **створює власну область** й наповнює її своїм. У тесті це навіть зручніше за глобал — подав у область підробки й перевіряй наодинці, нічого не готуючи й не прибираючи за собою.

**Область має слідувати за логічним викликом, а не за потоком.** Остання, тонша пастка — для асинхронного коду. «Поточна область» мусить триматися логічного ланцюжка запиту, а не фізичного потоку, бо `await` легко перекидає продовження на інший потік. Хто ховає поточну область у звичайну потокову змінну (thread-local), той після першого ж `await` дістане чужу область або порожнечу. Рятує механізм, що несе контекст уздовж *логічного* виконання: у Node.js це `AsyncLocalStorage`, у .NET — `AsyncLocal<T>`, і саме на ньому каркаси тримають прив'язку «цей запит → його область». Правило те саме, що й у всій збірці: область — не глобал, до якого тягнешся, а вузол, який їде разом із запитом.

Складіть латки докупи — і з наївного `Locator.get("gateway")` виходить реєстр, який не бреше й не тече: ключ несе тип, тож одрук ловить компілятор, а не користувач у проді; екземпляр живе рівно свій строк — спільне на корені, особисте на області, — тож ні запити, ні тести не б'ються за одне сховище. Усередині це, як і раніше, кілька мап — просто розставлених на двох рівнях і замкнених типами по краях.
