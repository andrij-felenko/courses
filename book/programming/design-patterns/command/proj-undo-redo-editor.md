# ⚙️ Редактор з undo/redo — від інтерфейсу до історії команд

Завдання звучить буденно, аж поки не сядеш його писати: текстовий редактор, у якому `Ctrl+Z` відкочує будь-яку зміну, а `Ctrl+Y` повертає її назад. Не одну зумисне вибрану дію — **будь-яку**: вставлений абзац, стерте слово, заміну виділеного шматка. І щоб додати завтра нову дію (скажімо, «зробити великими літерами»), не довелося ні рядка чіпати в самому механізмі «назад/вперед».

Ось у цій останній вимозі й ховається вся складність. Легко написати undo для одного конкретного редактора з трьома операціями — наліпити `if` за типом останньої дії й вручну кожну відкотити. Але такий код розповзається: кожна нова операція додає гілку в `undo`, `redo`, у перевірки меж, у логіку очищення. За десяток дій це перетворюється на купу, де одна забута гілка — і `Ctrl+Z` тихо псує документ.

Патерн Команда прибирає цю купу одним ходом: **кожна дія сама знає, як себе відкотити**, а механізм історії працює лише з абстрактним інтерфейсом і не знає жодної конкретної дії в обличчя. Зберемо повний робочий редактор — модель документа, спільний інтерфейс команди, три конкретні команди, макрокоманду й клас `History` з двома стопками — і на живому коді розберемо кожен інваріант і кожен край, об який б'ються наївні реалізації.

## Ідея: дві стопки й контракт «вмію себе відкотити»

Уся конструкція тримається на двох речах.

Перша — **контракт команди**. Кожна дія — це об'єкт з двома методами: `execute()` робить зміну, `undo()` повертає світ у стан «як було рівно перед цим `execute`». Щоб `undo()` спрацював, команда мусить у момент `execute()` **запам'ятати достатньо** для відкату. Це головна дисципліна всього підходу: не «якось відкотити потім», а «зберегти зараз усе, чого зміна незворотно позбавляє».

Друга — **дві стопки в історії**. Стопка *done* (зроблене) тримає команди, які виконані й ще не скасовані. Стопка *undone* (скасоване) тримає ті, що скасовані й чекають на можливе повторення. Три операції ганяють команди між цими стопками:

```
виконати нову дію →  execute(),  покласти на done,  ОЧИСТИТИ undone
скасувати (undo)  →  зняти верх done,  її .undo(),  покласти на undone
повторити (redo)  →  зняти верх undone,  її .execute(),  покласти на done
```

Три рядки — і це вся логіка «назад/вперед» для будь-якого редактора на світі. Решта коду нижче — це чесне наповнення цих трьох рядків та охайна обробка країв (порожні стопки; чому саме нова дія стирає `undone`).

*Механізм історії — це маршрутизатор об'єктів між двома стопками; він жодного разу не питає, що саме команда робить із документом.*

## Модель документа: те, над чим працюють команди

Перш ніж писати команди, потрібен **одержувач** — те, що реально тримає текст і вміє його міняти. Свідомо тримаємо його простим: рядок усередині й кілька елементарних операцій. Уся хитрість undo буде в командах, а не тут — документ навіть не здогадується, що існує якесь скасування.

:::tabs
```ts
class TextDocument {
  private text = "";

  content(): string { return this.text; }
  get length(): number { return this.text.length; }

  // вставити рядок у позицію pos (0 ≤ pos ≤ length)
  insert(pos: number, s: string): void {
    this.text = this.text.slice(0, pos) + s + this.text.slice(pos);
  }

  // вирізати [from, to) і повернути вирізане (щоб команда його запам'ятала)
  remove(from: number, to: number): string {
    const cut = this.text.slice(from, to);
    this.text = this.text.slice(0, from) + this.text.slice(to);
    return cut;
  }

  // межа останнього слова: індекс, з якого воно починається
  lastWordStart(): number {
    const trimmedEnd = this.text.replace(/\s+$/, "").length; // без хвостових пробілів
    const sp = this.text.lastIndexOf(" ", trimmedEnd - 1);
    return sp + 1;                       // -1 → 0 (слово від початку)
  }
}
```
```py
class TextDocument:
    def __init__(self) -> None:
        self._text = ""

    def content(self) -> str:
        return self._text

    def __len__(self) -> int:
        return len(self._text)

    # вставити рядок у позицію pos (0 ≤ pos ≤ len)
    def insert(self, pos: int, s: str) -> None:
        self._text = self._text[:pos] + s + self._text[pos:]

    # вирізати [from, to) і повернути вирізане (щоб команда його запам'ятала)
    def remove(self, frm: int, to: int) -> str:
        cut = self._text[frm:to]
        self._text = self._text[:frm] + self._text[to:]
        return cut

    # межа останнього слова: індекс, з якого воно починається
    def last_word_start(self) -> int:
        trimmed_end = len(self._text.rstrip())    # без хвостових пробілів
        sp = self._text.rfind(" ", 0, trimmed_end)
        return sp + 1                             # -1 → 0 (слово від початку)
```
```cpp
#include <string>

class TextDocument {
  std::string text_;                        // UTF-8; індекси — байтові зсуви
public:
  const std::string& content() const { return text_; }
  std::size_t length() const { return text_.size(); }

  // вставити рядок у позицію pos (0 ≤ pos ≤ length)
  void insert(std::size_t pos, const std::string& s) {
    text_.insert(pos, s);
  }

  // вирізати [from, to) і повернути вирізане (щоб команда його запам'ятала)
  std::string remove(std::size_t from, std::size_t to) {
    std::string cut = text_.substr(from, to - from);
    text_.erase(from, to - from);
    return cut;
  }

  // межа останнього слова: індекс, з якого воно починається
  std::size_t lastWordStart() const {
    std::size_t end = text_.find_last_not_of(" \t\n\r");  // без хвостових пробілів
    if (end == std::string::npos) return 0;               // самі пробіли
    std::size_t sp = text_.rfind(' ', end);
    return sp == std::string::npos ? 0 : sp + 1;          // немає пробілу → від початку
  }
};
```
:::

Зверни увагу на дві дрібниці, які насправді несуть вагу. По-перше, `remove` **повертає вирізане** — не викидає його в порожнечу. Це не примха: саме це повернене значення команда `DeleteLastWord` покладе собі в кишеню, щоб потім було чим відновити. Одержувач тут — джерело правди про те, що зникло. По-друге, `lastWordStart` спершу відкидає хвостові пробіли, а вже потім шукає межу слова: без цього `undo` після видалення слова з пробілом позаду відновив би слово не туди.

Ці два методи — `insert(pos, s)` і `remove(from, to) → вирізане` — виявляться достатньою основою для **всіх** трьох команд. Будь-яка правка тексту зводиться до «вставити шматок у позицію» або «вирізати діапазон», а обидві ці операції взаємно обернені. Це і є причина, чому текстовий редактор так природно лягає на Команду: його елементарні дії вже парні, лишається тільки загорнути їх в об'єкти, що пам'ятають свій шматок.

## Контракт команди

Тепер сам інтерфейс — обіцянка, на яку спиратиметься історія. Два методи, жодної згадки про конкретний документ чи конкретну дію:

:::tabs
```ts
interface Command {
  execute(): void;   // зробити зміну (і запам'ятати все для відкату)
  undo(): void;      // повернути стан рівно до того, що був перед execute()
}
```
```py
from typing import Protocol

class Command(Protocol):
    def execute(self) -> None: ...   # зробити зміну (і запам'ятати все для відкату)
    def undo(self) -> None: ...      # повернути стан рівно до того, що був перед execute()
```
```cpp
struct Command {
  virtual void execute() = 0;   // зробити зміну (і запам'ятати все для відкату)
  virtual void undo() = 0;      // повернути стан рівно до того, що був перед execute()
  virtual ~Command() = default;
};
```
:::

Контракт мовчазно вимагає **симетрії**: після пари `execute(); undo()` документ мусить бути байт-у-байт таким, яким був до `execute()`. Це не «приблизно відновити», а «відновити точно». Кожна конкретна команда нижче доводитиме цю симетрію по-своєму — і саме на цій точності стоїть уся довіра до `Ctrl+Z`.

## Три конкретні команди

### AddText: вставити текст

Найпростіша. Команда пам'ятає, **куди** й **що** вставила, — цього досить, щоб `undo()` вирізав рівно той самий діапазон назад.

:::tabs
```ts
class AddText implements Command {
  constructor(
    private doc: TextDocument,
    private pos: number,
    private text: string,
  ) {}

  execute(): void {
    this.doc.insert(this.pos, this.text);
  }

  undo(): void {
    // вставили text у pos → щоб відкотити, вирізаємо [pos, pos + text.length)
    this.doc.remove(this.pos, this.pos + this.text.length);
  }
}
```
```py
class AddText:
    def __init__(self, doc: TextDocument, pos: int, text: str) -> None:
        self.doc, self.pos, self.text = doc, pos, text

    def execute(self) -> None:
        self.doc.insert(self.pos, self.text)

    def undo(self) -> None:
        # вставили text у pos → щоб відкотити, вирізаємо [pos, pos + len(text))
        self.doc.remove(self.pos, self.pos + len(self.text))
```
```cpp
class AddText : public Command {
  TextDocument& doc_;
  std::size_t pos_;
  std::string text_;
public:
  AddText(TextDocument& doc, std::size_t pos, std::string text)
    : doc_(doc), pos_(pos), text_(std::move(text)) {}

  void execute() override {
    doc_.insert(pos_, text_);
  }

  void undo() override {
    // вставили text у pos → щоб відкотити, вирізаємо [pos, pos + text.size())
    doc_.remove(pos_, pos_ + text_.size());
  }
};
```
:::

Тут `undo()` не потребує нічого, чого команда не знала б із самого початку: `pos` і `text` відомі ще до `execute()`. Це найлегший випадок — коли дія повністю визначена своїми параметрами й нічого не *руйнує*, а лише додає.

### DeleteLastWord: видалити останнє слово

А ось де вступає в дію головна дисципліна. Видалення **знищує** інформацію — слово зникає. Щоб `undo()` міг його повернути, команда мусить перехопити це слово **в момент** `execute()`, перед тим як воно пропаде, і сховати в собі.

:::tabs
```ts
class DeleteLastWord implements Command {
  private from = 0;         // звідки різали
  private removed = "";     // що саме зрізали (запам'ятаємо в execute)

  constructor(private doc: TextDocument) {}

  execute(): void {
    this.from = this.doc.lastWordStart();
    // remove повертає вирізане — ловимо його, поки воно не зникло назавжди
    this.removed = this.doc.remove(this.from, this.doc.length);
  }

  undo(): void {
    // повертаємо зрізане рівно туди, звідки взяли
    this.doc.insert(this.from, this.removed);
  }
}
```
```py
class DeleteLastWord:
    def __init__(self, doc: TextDocument) -> None:
        self.doc = doc
        self.frm = 0          # звідки різали
        self.removed = ""     # що саме зрізали (запам'ятаємо в execute)

    def execute(self) -> None:
        self.frm = self.doc.last_word_start()
        # remove повертає вирізане — ловимо його, поки воно не зникло назавжди
        self.removed = self.doc.remove(self.frm, len(self.doc))

    def undo(self) -> None:
        # повертаємо зрізане рівно туди, звідки взяли
        self.doc.insert(self.frm, self.removed)
```
```cpp
class DeleteLastWord : public Command {
  TextDocument& doc_;
  std::size_t from_ = 0;        // звідки різали
  std::string removed_;         // що саме зрізали (запам'ятаємо в execute)
public:
  explicit DeleteLastWord(TextDocument& doc) : doc_(doc) {}

  void execute() override {
    from_ = doc_.lastWordStart();
    // remove повертає вирізане — ловимо його, поки воно не зникло назавжди
    removed_ = doc_.remove(from_, doc_.length());
  }

  void undo() override {
    // повертаємо зрізане рівно туди, звідки взяли
    doc_.insert(from_, removed_);
  }
};
```
:::

Придивись до порядку в `execute()`: спершу **обчислили й запам'ятали** (`from`, `removed`), і лише через це `remove` віддає нам вирізане. Якби ми спершу різали, а потім намагалися згадати, що там було, — інформація вже пропала б. Тому команда, що руйнує, завжди пише в свою кишеню **до або під час** руйнування, ніколи після. Це правило можна вивести з контракту: `undo()` мусить відновити точно, а відновити можна лише те, що встиг зберегти.

Ще тонкість: `from` і `removed` заповнюються **в `execute()`**, а не в конструкторі. Причина — команда може бути виконана й скасована, а потім **виконана повторно** (redo), і на момент повтору «останнє слово» цілком може бути іншим, ніж коли команду створювали. Тож команда щоразу читає стан свіжо в `execute()` і свіжо його запам'ятовує. Конструктор лише зв'язує команду з документом; уся пам'ять про конкретний відкат народжується в момент виконання.

### ReplaceRange: замінити діапазон

Заміна — це видалення *плюс* вставка в одній дії. Вона знищує старий шматок (треба запам'ятати) і кладе новий (треба знати його довжину, щоб потім вирізати назад). Дві кишені замість однієї:

:::tabs
```ts
class ReplaceRange implements Command {
  private oldText = "";     // що стояло в [from, to) до заміни

  constructor(
    private doc: TextDocument,
    private from: number,
    private to: number,
    private newText: string,
  ) {}

  execute(): void {
    // 1) вирізали старе — і одразу впіймали його в oldText
    this.oldText = this.doc.remove(this.from, this.to);
    // 2) вставили нове на те саме місце
    this.doc.insert(this.from, this.newText);
  }

  undo(): void {
    // дзеркально й у зворотному порядку:
    // 1) прибрати нове (воно завдовжки newText, стоїть від from)
    this.doc.remove(this.from, this.from + this.newText.length);
    // 2) повернути старе на місце
    this.doc.insert(this.from, this.oldText);
  }
}
```
```py

    def __init__(self, doc: TextDocument, frm: int, to: int, new_text: str) -> None:
        self.doc, self.frm, self.to, self.new_text = doc, frm, to, new_text
        self.old_text = ""    # що стояло в [from, to) до заміни

    def execute(self) -> None:
        # 1) вирізали старе — і одразу впіймали його в old_text
        self.old_text = self.doc.remove(self.frm, self.to)
        # 2) вставили нове на те саме місце
        self.doc.insert(self.frm, self.new_text)

    def undo(self) -> None:
        # дзеркально й у зворотному порядку:
        # 1) прибрати нове (воно завдовжки new_text, стоїть від from)
        self.doc.remove(self.frm, self.frm + len(self.new_text))
        # 2) повернути старе на місце
        self.doc.insert(self.frm, self.old_text)
```
```cpp
class ReplaceRange : public Command {
  TextDocument& doc_;
  std::size_t from_, to_;
  std::string newText_;
  std::string oldText_;         // що стояло в [from, to) до заміни
public:
  ReplaceRange(TextDocument& doc, std::size_t from, std::size_t to, std::string newText)
    : doc_(doc), from_(from), to_(to), newText_(std::move(newText)) {}

  void execute() override {
    // 1) вирізали старе — і одразу впіймали його в oldText
    oldText_ = doc_.remove(from_, to_);
    // 2) вставили нове на те саме місце
    doc_.insert(from_, newText_);
  }

  void undo() override {
    // дзеркально й у зворотному порядку:
    // 1) прибрати нове (воно завдовжки newText, стоїть від from)
    doc_.remove(from_, from_ + newText_.size());

    doc_.insert(from_, oldText_);

```
:::

Тут проступає закономірність, яку варто назвати вголос: **`undo` складеної дії — це кроки `execute` у зворотному порядку, кожен обернений**. `execute` спершу вирізав, потім вставив; `undo` спершу прибирає вставлене, потім повертає вирізане. Порядок важить: якби `undo` спершу повертав старе, а потім прибирав нове, індекси поїхали б — старий і новий текст різної довжини, і `from + newText.length` уже вказував би не туди. Ця «дзеркальність у зворотному порядку» — не випадковість саме `ReplaceRange`, а загальний закон відкату будь-якої послідовності дій, і саме на ньому за мить стоятиме макрокоманда.

## History: серце механізму

Тепер збираємо викликача — клас, що тримає дві стопки й проводить кожну команду її маршрутом. Уся публічна поверхня — `run`, `undo`, `redo` та два запити «чи можна».

:::tabs
```ts
class History {
  private done: Command[] = [];      // виконані, ще не скасовані
  private undone: Command[] = [];    // скасовані, чекають на redo

  // виконати НОВУ дію
  run(cmd: Command): void {
    cmd.execute();
    this.done.push(cmd);
    this.undone.length = 0;          // ← інваріант: нова дія стирає redo-гілку
  }

  undo(): void {
    const cmd = this.done.pop();
    if (cmd === undefined) return;   // край: скасовувати нічого
    cmd.undo();
    this.undone.push(cmd);
  }

  redo(): void {
    const cmd = this.undone.pop();
    if (cmd === undefined) return;   // край: повторювати нічого
    cmd.execute();
    this.done.push(cmd);
  }

  canUndo(): boolean { return this.done.length > 0; }
  canRedo(): boolean { return this.undone.length > 0; }
}
```
```py
class History:
    def __init__(self) -> None:
        self._done: list[Command] = []     # виконані, ще не скасовані
        self._undone: list[Command] = []   # скасовані, чекають на redo

    # виконати НОВУ дію
    def run(self, cmd: Command) -> None:
        cmd.execute()
        self._done.append(cmd)
        self._undone.clear()               # ← інваріант: нова дія стирає redo-гілку

    def undo(self) -> None:
        if not self._done:                 # край: скасовувати нічого
            return
        cmd = self._done.pop()
        cmd.undo()
        self._undone.append(cmd)

    def redo(self) -> None:
        if not self._undone:               # край: повторювати нічого
            return
        cmd = self._undone.pop()
        cmd.execute()
        self._done.append(cmd)

    def can_undo(self) -> bool: return len(self._done) > 0
    def can_redo(self) -> bool: return len(self._undone) > 0
```
```cpp
#include <memory>
#include <vector>

class History {
  std::vector<std::unique_ptr<Command>> done_;    // виконані, ще не скасовані
  std::vector<std::unique_ptr<Command>> undone_;  // скасовані, чекають на redo
public:
  // виконати НОВУ дію
  void run(std::unique_ptr<Command> cmd) {
    cmd->execute();
    done_.push_back(std::move(cmd));
    undone_.clear();                     // ← інваріант: нова дія стирає redo-гілку
  }

  void undo() {
    if (done_.empty()) return;           // край: скасовувати нічого
    std::unique_ptr<Command> cmd = std::move(done_.back());
    done_.pop_back();
    cmd->undo();
    undone_.push_back(std::move(cmd));
  }

  void redo() {
    if (undone_.empty()) return;         // край: повторювати нічого
    std::unique_ptr<Command> cmd = std::move(undone_.back());
    undone_.pop_back();
    cmd->execute();
    done_.push_back(std::move(cmd));
  }

  bool canUndo() const { return !done_.empty(); }
  bool canRedo() const { return !undone_.empty(); }
};
```

Три речі в цьому класі варті окремої зупинки, бо саме на них спотикаються наївні реалізації.

**Порожня стопка — це нормальний стан, а не помилка.** `undo` при порожньому `done` і `redo` при порожньому `undone` просто нічого не роблять і тихо повертаються. Не кидають виняток, не логують попередження, не «пікають». Користувач, який тисне `Ctrl+Z` на свіжому документі, не зробив нічого поганого — йому просто нічого відкочувати. Тому край обробляється мовчазним `return`, а не обуренням. Публічні `canUndo`/`canRedo` існують окремо саме щоб UI міг **завчасно** знати стан — приглушити кнопку «назад», коли історія порожня, замість того щоб дозволяти клік і ловити «нічого не сталося».

**Інваріант очищення `undone`.** Це найтонше місце всього механізму, і воно в одному рядку: `run` після `push` у `done` **спорожнює** `undone`. Розберімо, чому інакше не можна. Уяви: ти набрав три слова, тоді двічі натиснув `Ctrl+Z` — дві команди переїхали в `undone`, документ показує одне слово. Тепер ти набираєш **нове** слово. Що має статися з тими двома скасованими? Повернути їх уже не можна — вони належали до майбутнього, якого більше немає. Ти щойно створив **іншу** гілку історії. Лінійна модель (дві стопки) уміє тримати рівно одну лінію «минуле → майбутнє», тож щойно з'явилася розвилка, старе майбутнє доводиться відрізати. Забудеш цей рядок — і `redo` після нового набору спробує «повторити» команду, яка розрахована на давно зниклий стан документа: індекси поїдуть, `undo` тієї команди зруйнує не той шматок. Один пропущений `clear()` — і `Ctrl+Y` стає генератором тихого пошкодження тексту.

**`redo` — це буквально повторний `execute`.** Не окремий «метод повтору», не збережений знімок, а той самий `execute()`, що й уперше. Ось чому кожна команда мусить читати потрібний їй стан у `execute()` і бути готовою, що її викличуть кілька разів поспіль (виконали → скасували → повторили → знову скасували…). Команда — не одноразова: вона мусить лишатися коректною при будь-якій кількості чергувань `execute`/`undo`, аби її гоняли туди-сюди по стопках скільки завгодно.

## Макрокоманда: одна дія з багатьох

Тепер безкоштовний бонус, який дарує сам факт, що команда — звичайний об'єкт. Часто одна логічна дія користувача складається з кількох елементарних: «замінити всі входження» — це низка окремих замін; «оформити абзац» — жирний плюс відступ плюс вирівнювання. Хочемо, щоб `Ctrl+Z` відкочував таку дію **цілком за один раз**, а не по одному кроку.

Рішення виростає прямо з інтерфейсу: **макрокоманда — це команда, що всередині тримає список інших команд**. Ззовні вона не відрізнити від елементарної — той самий `execute()`/`undo()`, — тож `History` кладе її на стопку як одну штуку й гадки не має, що всередині десяток дій.

:::tabs
```ts
class MacroCommand implements Command {
  constructor(private commands: Command[]) {}

  execute(): void {
    for (const c of this.commands) c.execute();          // усі вперед, по порядку
  }

  undo(): void {
    for (let i = this.commands.length - 1; i >= 0; i--)  // ...і назад у ЗВОРОТНОМУ
      this.commands[i].undo();
  }
}
```
```py
class MacroCommand:
    def __init__(self, commands: list[Command]) -> None:
        self.commands = commands

    def execute(self) -> None:
        for c in self.commands:          # усі вперед, по порядку
            c.execute()

    def undo(self) -> None:
        for c in reversed(self.commands):  # ...і назад у ЗВОРОТНОМУ
            c.undo()
```
```cpp
class MacroCommand : public Command {
  std::vector<std::unique_ptr<Command>> commands_;
public:
  explicit MacroCommand(std::vector<std::unique_ptr<Command>> commands)
    : commands_(std::move(commands)) {}

  void execute() override {
    for (auto& c : commands_) c->execute();              // усі вперед, по порядку
  }

  void undo() override {
    for (auto it = commands_.rbegin(); it != commands_.rend(); ++it)
      (*it)->undo();                                     // ...і назад у ЗВОРОТНОМУ
  }
};
```

Той самий закон, що ми вивели на `ReplaceRange`, тут стає явним і центральним: **`undo` макросу проходить підкоманди у зворотному порядку**. Причина фізична, а не естетична. Якщо `execute` зробив A, потім B (де B міг спиратися на результат A), то коректно повернути можна лише знявши спершу B, а тоді A — як стос тарілок розбирають з верхньої. Скасуй у прямому порядку — і `undo` кожної підкоманди побачить стан, якого вона не очікує, бо пізніші дії ще не зняті. Зворотний порядок — єдиний, що гарантує кожній підкоманді рівно той світ, який був перед її власним `execute`.

Макрокоманда — це той самий [Компонувальник (Composite)](topic:programming/composite), приведений у світ дій: «одна команда» й «список команд» мають однаковий інтерфейс, тож клієнт (тут — `History`) працює з деревом дій так само, як з одним листком. Ця однаковість — не збіг двох патернів, а один і той самий структурний хід: дати цілому й частині спільний тип, щоб той, хто ними користується, не мусив їх розрізняти.

## Складність і пам'ять

Тепер холодний рахунок — скільки коштують ці операції.

**Час кожної операції історії — O(1).** Ані `run`, ані `undo`, ані `redo` не проходять по стопках; вони чіпають лише **верхівку**. `push` і `pop` на масиві-стопці — амортизовано стала: додати чи зняти з кінця не залежить від того, скільки там уже лежить. Очищення `undone` в `run` — теж O(1) у сенсі, що воно просто відпускає стопку цілком (обнулити довжину / `clear`), а не знімає елементи по одному. Тобто хоч мільйон дій в історії, хоч десяток — кожен `Ctrl+Z` коштує однаково.

Обережність — усередині самих команд. `undo`/`execute` елементарної команди коштують стільки, скільки коштує сама операція над документом. У нашій моделі `insert`/`remove` перебудовують рядок, тобто це O(довжина документа) через зрізання й склеювання — але це ціна *операції над текстом*, а не механізму історії; у справжньому редакторі під текстом лежить спеціальна структура (мотузка *rope* — збалансоване дерево шматків; або *gap buffer* — масив із «дірою» біля курсора), де вставка коштує O(log n) чи амортизовано O(1). Механізм команд додає до цього рівно нуль: він лише кличе те, що й так довелося б викликати.

Макрокоманда з *k* підкоманд, звісно, коштує суму своїх частин — O(k) викликів; але для `History` вона все одно одна команда, одна `push`, одна `pop`.

**Пам'ять історії росте лінійно від числа дій.** Кожна виконана дія лишає в стопці свій об'єкт-команду, і об'єкт цей несе стільки, скільки запам'ятав для відкату. `AddText` тримає вставлений рядок; `DeleteLastWord` — зрізане слово; `ReplaceRange` — старий шматок. Тобто сумарна пам'ять undo-історії — це приблизно **сума розмірів усього, що дії коли-небудь видалили чи вставили**. Стерли абзац на 5 КБ — команда чесно тримає ті 5 КБ, поки живе в стопці, бо без них не поверне текст.

Звідси випливає єдиний реальний біль лінійного undo — **необмежене зростання пам'яті** в довгій сесії редагування. Класичні ліки — **обмежити глибину історії**: тримати не більш як N останніх команд, а старіші відкидати з дна стопки. Це перетворює `done` на кільцевий буфер фіксованого розміру: користувач може відкотити останні N дій, глибше — ні. Компроміс свідомий: скінченна пам'ять в обмін на скінченну глибину `Ctrl+Z`, і майже завжди він того вартий, бо ніхто не відкочує тисячу кроків.

## Пастки, про які треба знати заздалегідь

**Коалесцінг: одна дія користувача ≠ одна команда UI.** Якщо на кожен натиснутий символ створювати окрему `AddText` і класти в історію, то `Ctrl+Z` відкочуватиме по одній літері — а користувач очікує, що відкотиться ціле щойно набране слово чи речення. Ліки — **склеювати** (coalesce) послідовні однорідні правки в одну команду, поки вони йдуть «серією»: набір без пауз, без переміщення курсору, того самого типу. На практиці команді додають метод на кшталт `merge(previous)` (або `tryMerge`), і `History` перед тим, як покласти нову команду, питає верхню на `done`, чи не поглине вона нову; якщо так — верхня розширює свій діапазон, а нова в стопку не лягає. Серія рветься на паузі введення, на пробілі/розділовому, на русі курсору — і наступна команда вже починає нову «одиницю відкату». Без коалесцінгу механізм формально коректний, але незручний до непридатності; це не оздоба, а частина того, що робить undo *людським*.

**Лінійна історія не тримає розгалуження.** Ми вже бачили інваріант «нова дія стирає `undone`». Варто розуміти, що це **свідома втрата**, а не недогляд. Модель двох стопок уміє рівно одну лінію минуле↔майбутнє; щойно ти після кількох `undo` робиш нову дію, старе майбутнє відрізається безповоротно. Існує потужніша модель — **дерево історії** (undo-tree): замість стирати стару гілку, вона зберігає її як окреме відгалуження, і між гілками можна ходити, нічого не втрачаючи. Так працює undo-tree в редакторах Vim та Emacs (пакет `undo-tree` для Emacs написав Тобі К'юбітт, відомий як «dr-qubit»). Ціна — суттєво складніша структура (не дві стопки, а дерево з навігацією) і незвичний для більшості користувачів UI: після серії відкотів «повтор» стає вибором з кількох напрямків, а не одним шляхом. Тому переважна більшість редакторів свідомо лишаються на лінійній моделі — вона відповідає інтуїції «назад/вперед по одній лінії», яку люди й очікують від `Ctrl+Z`.

**Команда мусить пережити зміну одержувача.** Тонкий баг чигає, якщо команда тримає не сам одержувач, а щось похідне від його *поточного* стану, обчислене надто рано. Наш `DeleteLastWord` читає `lastWordStart()` **у `execute()`**, а не в конструкторі, — і це принципово. Якби він зафіксував позицію в конструкторі, то на момент `redo` (коли документ уже інший) відкотив би не той шматок. Загальне правило: **команда захоплює конкретику стану саме в `execute()`**, бо тільки тоді відомий справжній стан, на якому вона спрацює. Конструктор зв'язує команду з одержувачем; пам'ять про конкретний відкат народжується в момент виконання й оновлюється на кожному повторі.

**Undo зовнішніх ефектів — окрема історія.** Наша симетрія `execute`/`undo` тримається, бо документ — чиста пам'ять: що вставили, те й вирізали назад. Але якщо `execute()` мав **зовнішній ефект** — надіслав мережевий запит, записав файл, посвітив індикатором, — то `undo()` не може просто «повернути рядок». Мережевий лист не «відкликати» назад; для таких дій undo означає **компенсацію** (надіслати лист-спростування), а не буквальний відкат, і не всі ефекти взагалі компенсовні. Тому в стопку undo кладуть лише команди, чий ефект **оборотний у межах моделі**; незворотні дії (надсилання, друк, безповоротне видалення) або не потрапляють в історію, або вимагають окремого механізму підтвердження. Плутати ці дві категорії — типова причина того, що `Ctrl+Z` «наче спрацював», а насправді світ зовні лишився зміненим.

Підіб'ємо суть. Повний undo/redo — це не гора спеціального коду, а **один контракт** (`execute`/`undo` із чесним запам'ятовуванням) плюс **дві стопки** з єдиним нетривіальним інваріантом (нова дія стирає `undone`). Кожна команда локально відповідає за свою оборотність; історія глобально нічого про дії не знає. Саме ця роздільність і робить систему такою, що нова операція вливається в неї даром: напиши їй чесний `undo()` — і `Ctrl+Z` для неї працює сам, без жодної правки механізму.
