# Ланцюжок обов'язків

<preknowlist>
- [Поліморфізм і динамічне зв'язування](book:programming/polymorphism) — виклик через спільний тип, що в рантаймі йде в потрібну реалізацію; кожна ланка ланцюжка — той самий тип «обробник», але поводиться по-своєму, і саме поліморфізм дає передавати запит усім однаково.
- [Інтерфейс проти реалізації](book:programming/interface-vs-implementation) — різниця між тим, ЩО обробник обіцяє назовні (`handle(запит)`), і тим, ЯК він усередині вирішує: узяти запит чи передати далі.
- [Композиція над спадкуванням](book:programming/composition-inheritance) — ланцюжок збирають, зв'язуючи об'єкти посиланням «наступний», а не будуючи ієрархію класів; ланка тримає сусіда полем, а не успадковує його.
- [Єдиний обов'язок (SRP)](book:programming/single-responsibility) — чому кожна ланка відповідає рівно за одну перевірку чи один різновид запиту, а не за все відразу.
</preknowlist>

Уяви, що хтось у компанії просить погодити витрату. На тисячу гривень підпис ставить керівник групи. На десять тисяч — уже начальник відділу. На сто тисяч — директор. Понад це — фінансовий директор особисто. Той, хто просить, зазвичай **не тримає** цих порогів у голові й не має знати всю ієрархію підписів напам'ять. Він робить простіше: віддає заявку найближчому керівнику. Досить у того повноважень — той погодить. Ні — заявка йде вище, до наступного, і так, поки хтось із достатнім правом її не підпише.

Ось і весь патерн. **Ланцюжок обов'язків** (англ. *chain of responsibility*: «ланцюжок» — від низки з'єднаних ланок, «обов'язок» — хто відповідає за обробку) дає запиту пройти **низку можливих обробників**, поки один із них його не візьме, причому **той, хто надіслав запит, не знає наперед, хто саме його обробить**. Відправник тримає в руках лише перший обробник і кидає запит йому; далі запит сам мандрує ланкою.

Це не екзотика для оргсхем. Точно так само влаштовано десятки речей у коді. HTTP-запит проходить через перевірку автентифікації, обмеження частоти, логування — і аж потім потрапляє в бізнес-логіку. Виняток летить угору по стеку викликів, поки якийсь `catch` не вирішить, що це його. Клік у графічному інтерфейсі спливає від кнопки до панелі, від панелі до вікна, поки хтось не скаже «це моє». Скрізь одна форма: **запит іде вздовж низки можливих відповідачів, і кожен вирішує — узяти чи передати далі**.

Розберімо, від чого це лікує, бо без болю патерн виглядає зайвою церемонією.

## Хвороба: відправник, що знає всіх

Спробуймо погодити витрату в лоб, без жодного патерна. У того, хто відправляє заявку, в коді з'являється щось таке:

:::tabs
```ts
function approve(amount: number) {
  if (amount <= 1_000)        teamLead.sign(amount);
  else if (amount <= 10_000)  manager.sign(amount);
  else if (amount <= 100_000) director.sign(amount);
  else                        cfo.sign(amount);
}
```
```py
def approve(amount: float) -> None:
    if amount <= 1_000:
        team_lead.sign(amount)
    elif amount <= 10_000:
        manager.sign(amount)
    elif amount <= 100_000:
        director.sign(amount)
    else:
        cfo.sign(amount)
```
:::

Працює. Але придивись, скільки всього знає ця крихітна функція. Вона знає **всіх** учасників — керівника групи, начальника, директора, фіндиректора. Вона знає **всі пороги** — тисячу, десять тисяч, сто тисяч. Вона знає **порядок** ескалації. Той, хто лише хотів попросити грошей, тепер носить у собі повну карту повноважень усієї організації.

Тепер щоразу, коли щось у цій карті міняється, доведеться правити саме цю функцію. З'явився проміжний рівень — «старший менеджер» до п'ятдесяти тисяч? Лізь у `if`. Змінилися пороги? Лізь у `if`. Директор пішов у відпустку й підписує заступник? Знову сюди. А таких місць, де просять погодження, у великій системі не одне — і кожне доведеться синхронно перекроювати. Логіка «хто за що відповідає» **розмазана по відправниках** замість того, щоб жити там, де їй місце, — у самих відповідачів.

Корінь болю — у напрямі знання. Відправник намертво зчеплений із **кожним** конкретним обробником і з правилами вибору між ними. А хочемо ми протилежного: відправник має знати рівно одне — «є кому це віддати», — а хто саме візьметься, нехай вирішують самі обробники.

## Ліки: кожен вирішує за себе й передає далі

Перевернімо все. Замість того щоб відправник обирав обробника, нехай **кожен обробник сам вирішує**, його це запит чи ні. Правило для однієї ланки просте до безглуздя:

> Мій це запит? Так — обробити й зупинитися. Ні — передати наступному.

Кожна ланка знає лише дві речі: **свій власний критерій** («суми до десяти тисяч — мої») і **хто наступний** у ланцюгу. Вона не знає ні всієї ієрархії, ні порогів сусідів. Відправник теж спрощується до краю: тримає посилання на **першу** ланку й кидає запит їй — а далі його справа скінчена.

Спершу — спільний тип обробника, сама лише обіцянка «мене можна попросити обробити запит, і я або впораюся, або передам далі». Разом із ним — маленька спільна основа, що вміє тримати наступного й за замовчуванням саме передавати далі, щоб кожна конкретна ланка писала тільки свій критерій:

:::tabs
```ts
interface Approver {
  setNext(next: Approver): Approver;
  handle(amount: number): void;
}

// Спільна основа: тримає наступного й уміє передавати далі
abstract class BaseApprover implements Approver {
  private next?: Approver;

  setNext(next: Approver): Approver {
    this.next = next;
    return next;                      // повертаємо наступного — зручно зчіплювати
  }

  handle(amount: number): void {
    if (this.next) this.next.handle(amount);
    else console.log(`Нема кому погодити ${amount}`);
  }
}

class TeamLead extends BaseApprover {
  handle(amount: number): void {
    if (amount <= 1_000) console.log(`Керівник групи погодив ${amount}`);
    else super.handle(amount);        // не моє — передаю далі
  }
}

class Manager extends BaseApprover {
  handle(amount: number): void {
    if (amount <= 10_000) console.log(`Начальник відділу погодив ${amount}`);
    else super.handle(amount);
  }
}

class Director extends BaseApprover {
  handle(amount: number): void {
    if (amount <= 100_000) console.log(`Директор погодив ${amount}`);
    else super.handle(amount);
  }
}
```
```py
from abc import ABC

class Approver(ABC):
    def __init__(self) -> None:
        self._next: "Approver | None" = None

    def set_next(self, nxt: "Approver") -> "Approver":
        self._next = nxt
        return nxt                       # повертаємо наступного — зручно зчіплювати

    def handle(self, amount: float) -> None:
        if self._next:
            self._next.handle(amount)
        else:
            print(f"Нема кому погодити {amount}")


class TeamLead(Approver):
    def handle(self, amount: float) -> None:
        if amount <= 1_000:
            print(f"Керівник групи погодив {amount}")
        else:
            super().handle(amount)       # не моє — передаю далі


class Manager(Approver):
    def handle(self, amount: float) -> None:
        if amount <= 10_000:
            print(f"Начальник відділу погодив {amount}")
        else:
            super().handle(amount)


class Director(Approver):
    def handle(self, amount: float) -> None:
        if amount <= 100_000:
            print(f"Директор погодив {amount}")
        else:
            super().handle(amount)
```
:::

Тепер збираємо ланцюг і кидаємо в нього заявки:

:::tabs
```ts
const lead = new TeamLead();
lead.setNext(new Manager()).setNext(new Director());   // ланцюг: lead → manager → director

lead.handle(500);      // Керівник групи погодив 500
lead.handle(7_000);    // Начальник відділу погодив 7000
lead.handle(90_000);   // Директор погодив 90000
lead.handle(500_000);  // Нема кому погодити 500000
```
```py
lead = TeamLead()
lead.set_next(Manager()).set_next(Director())    # ланцюг: lead → manager → director

lead.handle(500)       # Керівник групи погодив 500
lead.handle(7_000)     # Начальник відділу погодив 7000
lead.handle(90_000)    # Директор погодив 90000
lead.handle(500_000)   # Нема кому погодити 500000
```
:::

Уся вигода — в останньому рядку. Відправник каже `lead.handle(500_000)` першій ланці й іде геть; він **ніколи не дізнається**, хто підписав — керівник групи, директор чи взагалі ніхто. Знання «хто за що відповідає» тепер живе всередині кожної ланки, точно там, де йому місце: клас `Manager` знає межу менеджера й нічого більше.

Придивись і до того, як росте така схема. Треба додати рівень «старший менеджер до п'ятдесяти тисяч» — пишеш **один новий клас** і вставляєш його в складання ланцюга між `Manager` і `Director`. Жоден наявний обробник не змінюється: `TeamLead`, `Manager`, `Director` не знають і не мусять знати, що поруч з'явився сусід. Це в чистому вигляді [принцип відкритості-закритості](book:programming/open-closed) — система відкрита для доповнення (новий клас збоку) й закрита для правок (старе не чіпаємо).

![Відправник кидає запит першій ланці й не знає, хто підпише; запит іде вздовж ланок, кожна перевіряє свій поріг і або бере запит, або передає далі; ланка з достатнім правом бере його й зупиняє рух, а якщо жодна не взяла — запит випадає в кінці як необроблений](/book/programming/design-patterns/chain-of-responsibility/img/chain-flow.svg)
*Відправник зчеплений лише з першою ланкою; рішення «чиє це» ухвалює кожна ланка сама, а не той, хто послав запит.*

> 🔧 **Навіщо це.** Найгостріше вигода відчувається там, де набір обробників живе власним життям окремо від коду, що їх кличе. Проміжні шари веб-сервера (автентифікація, обмеження частоти, розбір тіла), фільтри вхідних повідомлень, правила валідації форми, рівні підтримки «перша лінія → друга → інженер» — усе це низки перевірок, які додають, прибирають і переставляють незалежно від відправника. Коли кожна перевірка — окрема ланка, нову пише інша людина в іншому файлі, вставляє її в потрібне місце ланцюга й ніде не чіпає ні відправника, ні сусідів. Ланцюжок перетворює «дорогу правку розгалуженого відправника» на «дешеве дописування ланки збоку».

## Скелет: інтерфейс, ланка, зчеплення

Розкладімо конструкцію на частини, щоб було видно, що тут несе вагу.

**Інтерфейс обробника** — сама обіцянка `handle(запит)` плюс спосіб зчепити ланку з наступною (`setNext`). Це той спільний тип, крізь який відправник бачить будь-яку ланку однаково, не розрізняючи керівника групи й директора.

**Спільна основа** тримає посилання `next` і має **типову поведінку за замовчуванням**: якщо є наступний — передати запит йому. Саме тут захований весь «рух далі». Завдяки цьому конкретна ланка не пише жодної механіки передавання — вона пише лише свій критерій, а «інакше» доручає основі.

**Конкретні ланки** роблять рівно одне: перевіряють свою умову. Підходить — обробляють і мовчать. Не підходить — кличуть успадковане «передати далі». Кожна ланка — крихітна й займається [єдиним обов'язком](book:programming/single-responsibility): свій поріг, своя дія, і ні слова про сусідів.

![Скелет типів: угорі інтерфейс Approver з методами setNext і handle; під ним спільна основа BaseApprover, що тримає поле next і в handle за замовчуванням передає запит наступному; знизу три конкретні ланки TeamLead, Manager, Director, кожна перевіряє свій поріг і або обробляє, або кличе успадковане передавання; збоку показано, як екземпляри зчеплюються посиланням next у ланцюг](/book/programming/design-patterns/chain-of-responsibility/img/handler-skeleton.svg)
*Механіка «передати далі» живе в основі раз; конкретна ланка додає лише свій критерій — тому ланок легко мати багато й вони лишаються дрібними.*

Зчеплення ланок — це звичайна [композиція](book:programming/composition-inheritance): екземпляр тримає посилання на наступний екземпляр полем `next`. Ланцюг — це, по суті, однозв'язний список обробників, який ти будуєш під час складання системи, а не зашиваєш у типи. Тому один і той самий клас `Manager` може стояти в різних ланцюгах на різних місцях: порядок вирішує складання, не клас.

## Дві породи ланцюгів: хто зупиняє рух

Досі запит зупинявся на **першому**, хто його взяв: підписав керівник — далі заявки ніхто й не бачив. Це класична форма з книжки «банди чотирьох» (автори канонічної праці 1994 року — Ерік Ґамма, Річард Гелм, Ральф Джонсон, Джон Вліссідес): «дати кільком об'єктам шанс обробити запит і передавати його по ланцюгу, поки хтось не візьме». Так само поводиться обробка винятків: перший відповідний `catch` ловить, решта не спрацьовує.

Але та сама конструкція живе й у другій, не менш поширеній подобі: коли **кожна** ланка має відпрацювати, а запит проходить **крізь усі**. Це конвеєр обробки — той, що в вебі звуть проміжним шаром (англ. *middleware*): запит по черзі проходить логування, перевірку прав, розбір тіла, і кожна ланка додає своє, перш ніж пустити далі. Тут ланка не «забирає» запит, а «пропускає крізь себе», роблячи свою частину роботи. Робочий приклад такого конвеєра — з реальним кодом, «цибулевою» моделлю проходу туди-й-назад і коротким замиканням — розібрано в [окремому проєкті про конвеєр проміжних шарів](book:programming/chain-of-responsibility/proj-middleware-chain.md).

![Дві породи ланцюга поруч: ліворуч «перший, хто може — бере» — запит іде вниз, друга ланка бере його й зупиняє рух, нижчі ланки запиту не бачать (погодження, обробка винятків); праворуч «кожен додає своє» — запит проходить крізь усі ланки по черзі, кожна робить свою частину й пускає далі, а перевірка прав може обірвати рух достроково (логування, middleware); внизу підпис, що різниця лише в одному рішенні всередині ланки](/book/programming/design-patterns/chain-of-responsibility/img/two-flavors.svg)
*Обидві породи — той самий каркас; різниця в одному рішенні ланки: зупинити ланцюг чи покликати наступного попри все.*

Різниця між породами — саме в цьому рішенні. У «перший бере» ланка, яка впоралась, не кличе далі — рух завмирає. У конвеєрі — кличе завжди, хіба що навмисне обірве («коротке замикання»: перевірка прав, побачивши, що прав немає, не пускає запит глибше). А якщо приглянутися до конвеєра, де ланка отримує запит **і** посилання «покликати наступного», то ланка — це функція двох аргументів, і вся низка таких функцій згортається в одну операцію правим згортком над списком обробників; на цьому формальному погляді тримається й гарантія, що ланцюг колись доходить кінця. Цей кут — ланцюжок як згортка, інваріанти скінченності й вартість проходу — розгорнуто в [нотатці про математику ланцюга](book:programming/chain-of-responsibility/math-chain-as-fold.md).

## Що, як ніхто не візьме

У ланцюга є хвіст, і з ним пов'язана найтиповіша пастка. Що станеться із запитом, який не підійшов **жодній** ланці? У наївній реалізації він тихо випаде за останню ланку й зникне без сліду — жодного погодження, жодної помилки, просто нічого не сталося. Такий мовчазний провал відшукати потім украй важко: код ніби працює, а результату немає.

Тому кінець ланцюга не лишають відкритим. Ставлять **обробник за замовчуванням**, який ловить усе, що впало крізь ланцюг, і робить осмислене «нічого» — записує в лог, повертає відмову, кидає виняток. Такий обробник, що заступає «нікого» рівною, передбачуваною поведінкою замість `null` чи мовчазної діри, — окремий дрібний патерн, [порожній об'єкт](book:programming/null-object). Головне рішення тут — свідоме: ти **вирішуєш**, що означає «ніхто не взяв», а не лишаєш це на волю випадку.

## Родичі, яких плутають

Ланцюжок обов'язків структурно схожий на кількох сусідів, і плутанина тут звична.

Найближчий двійник — **[Декоратор](book:programming/decorator)**. Обидва — це низка об'єктів, де кожен тримає наступного. Але намір інший. Декоратор **завжди** кличе наступного й **обгортає** його поведінку своєю: кожна обгортка неодмінно додає щось до результату, і сенс не в тому, «хто обробить», а в тому, щоб **накласти шари**. Ланка ж ланцюжка **може обірвати** рух — уся суть у тому, що **хтось один забирає** запит. Декоратор — «усі додають»; ланцюжок — «хтось бере». Конвеєрна порода ланцюжка розмиває цю межу, і те саме middleware часто описують і так, і так, — але класичний ланцюжок якраз про право ланки зупинити рух.

**[Компонувальник](book:programming/composite)** часто стає готовою колією для ланцюжка. «Наступний» тоді — не зібраний вручну список, а вказівник на батька в дереві: клік, не оброблений кнопкою, іде до її панелі, тоді до вікна. Ланцюг тут — це шлях угору деревом компонентів, а не окрема структура.

**[Команда](book:programming/command)** нерідко і є той запит, що мандрує ланцюгом. Замість голого числа по ланках передають об'єкт-команду — дію, загорнуту в річ, яку можна зберегти й передати. Ланцюжок відповідає за те, **як запит рухається** між обробниками; команда — за те, **чим запит є**.

Протилежна за топологією рідня — **[Посередник](book:programming/mediator)**. Де ланцюжок **розподіляє** рішення між незалежними ланками, кожна з яких знає лише сусіда, посередник **зосереджує** його в одному вузлі, що знає всіх. Різні відповіді на те саме питання «як розв'язати зайву зчепленість між об'єктами»: розтягнути в лінію чи стягнути в центр.

## Коли ланцюжок зайвий

Патерн окупається не завжди, і накинути його всюди — легкий спосіб нашкодити.

Якщо можливий обробник **рівно один** або їх фіксований невеликий набір із простим вибором за ключем — прямий виклик чи таблиця відповідностей читаються легше за ланцюг. Обертати ланцюжком кожне розгалуження — відомий різновид [надмірного патернування](book:programming/anti-patterns); патерн має знімати наявний біль, а не передбачати уявний.

Пильнуй і два практичні коштовні боки. Перший — вартість проходу: кожен запит іде по ланках, тобто робить до `n` кроків. На гарячому шляху з довгим ланцюгом мапа, що за типом запиту одразу дає потрібний обробник, розв'язує за один крок замість перебору. Ланцюг заслуговує на свою ціну, коли рішення справді має форму «пробуй по черзі, поки якесь не підійде», а не «дістань точного обробника за ключем». Другий — можливість відлагодження: запит здатен мовчки пройти весь ланцюг і випасти, тож без обробника за замовчуванням і без логування знайти «чому нічого не сталося» буває болісно.

Ланцюжок виправдовує себе, коли кандидатів на обробку кілька, набір їх **міняється**, **порядок важить**, і відправник щиро **не повинен знати**, хто впорається. Тоді низка самостійних ланок, кожна зі своїм критерієм і одним посиланням на сусіда, — найдешевший спосіб рости.
