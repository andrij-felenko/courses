# 📜 Від підказки оптимізатору до контракту лінкера: як еволюціонувало ключове слово inline

Коли в середині 1970-х років у Bell Labs створювали мову C та операційну систему Unix, ресурси комп'ютерів вимірювалися десятками кілобайтів. Легендарна машина PDP-11 мала 16-бітний адресний простір, де програма могла одночасно адресувати лише 64 кілобайти пам'яті. Зробити компілятор, який тримав би в оперативній пам'яті вихідний код усієї операційної системи від початку до кінця, було фізично неможливо. Єдиним життєздатним інженерним рішенням стала модель **роздільної компіляції** (*separate compilation*): програму розбивали на невеликі окремі файли `.c`, кожен із яких компілювався в ізольований об'єктний файл `.o`, після чого простий компонувальник (лінкер) зшивав адреси докупи.

Ця модель уможливила розвиток системного програмування, але породила фундаментальну проблему з гранулярністю коду, яка залишалася головним болем розробників упродовж наступних чотирьох десятиліть.

## Пастка макросів і ціна маленьких функцій

На початку 1980-х років Б'ярн Страуструп (*Bjarne Stroustrup*), працюючи над мовою «C with Classes» (майбутньою C++), запровадив концепцію класів, інкапсуляції та методів доступу (гетерів і сетерів). Ідея полягала в тому, щоб надати програмістові надійні інтерфейси без втрати швидкодії мови C — принцип «абстракцій нульової вартості».

Однак розробники зіткнулися з жорстким протиріччям архітектури C. Якщо клас описує метод доступу:

```cpp
class Point {
    int x_, y_;
public:
    int x() const { return x_; }
};
```

Кожен виклик `pt.x()` у класичній моделі компілятора перетворювався на повноцінну інструкцію виклику підпрограми (`call`), збереження регістрів у стеку, переходу та повернення (`ret`). Накладні витрати на виклик функції, тіло якої складається з єдиної інструкції читання пам'яті `mov eax, [rdi]`, перевищували час корисного обчислення в кілька разів.

У чистому C розробники рятувалися препроцесорними макросами `#define`:

:::tabs
```c
#define POINT_GET_X(pt) ((pt)->x)
```
```cpp
// У C++ ідіоматичний підхід вимагає строгої типізації замість небезпечних макросів
constexpr int get_x(const Point& pt) noexcept {
    return pt.x();
}
```
:::

Макроси розгорталися безпосередньо в місці виклику, уникаючи накладних витрат `call/ret`, але позбавляли програму перевірки типів, не мали власної області видимості, призводили до побічних ефектів при повторному обчисленні аргументів (`POINT_GET_X(pt++)`) і не могли бути членами класів.

Якщо ж розробник намагався винести маленьку допоміжну функцію в заголовочний файл `.h`:

:::tabs
```c
// math_helpers.h
int square(int x) {
    return x * x;
}
```
```cpp
// math_helpers.hpp
int square(int x) {
    return x * x;
}
```
:::

і підключав цей заголовок у два різні файли `main.c` та `physics.c`, збірка завершувалася аварійною зупинкою лінкера:

```
ld: error: duplicate symbol: square in main.o and physics.o
```

Компілятор, не знаючи про інші файли, у кожній одиниці трансляції чесно генерував глобальний символ `square` з зовнішнім зв'язуванням (*external linkage*). Коли лінкер намагався об'єднати `main.o` та `physics.o`, він бачив два однакових символи й завершував роботу з помилкою множинного визначення (*multiple definition*).

Єдиним виходом у C89 було ключове слово `static`:

:::tabs
```c
// math_helpers.h
static int square(int x) {
    return x * x;
}
```
```cpp
// math_helpers.hpp
static int square(int x) {
    return x * x;
}
```
:::

Слово `static` змінювало зв'язування на внутрішнє (*internal linkage*). Лінкер більше не лаявся, але виникала нова проблема: якщо компілятор через рівень оптимізації вирішував не вбудовувати функцію, він породжував окреме машинне тіло `square` у **кожному** об'єктному файлі. У великих проєктах із сотнями файлів вихідний бінарний файл роздувався дублікатами одного й того самого машинного коду, а взяття покажчика на функцію `&square` у різних файлах повертало **різні адреси пам'яті**, руйнуючи логіку порівняння вказівників.

## Народження inline: від підказки до ODR-контракту

Страуструп запропонував ключове слово `inline` як підказку оптимізатору: «спробуй підставити машинний код у місце виклику». У ранніх версіях Cfront (першого транслятора C++ у C) методи, визначені всередині тіла класу, автоматично отримували статус `inline`.

Проте справжня революція відбулася не в алгоритмах підстановки коду, а в моделі лінкування. Комітет стандартизації C++ (ISO/IEC 14882:1998) усвідомив: оптимізатори компіляторів стали достатньо розумними, щоб самостійно вирішувати, коли вбудовувати функцію (inlining heuristics), спираючись на розмір коду, бюджет регістрів та профілювання (PGO). Підказка програміста стала необов'язковою для оптимізації.

Натомість ключове слово `inline` набуло фундаментального значення для лінкера. Стандарт зафіксував **Правило одного визначення** (*One Definition Rule*, ODR):

1. Звичайна не-inline функція з зовнішнім зв'язуванням повинна мати рівно одне визначення в усій програмі.
2. Функція, позначена як `inline`, **може бути визначена в кількох одиницях трансляції**, якщо всі ці визначення є тотожними (складаються з однакової послідовності токенів і мають однаковий зміст).

Це рішення зняло штучні обмеження: розробники отримали можливість описувати повні реалізації класів та функцій у заголовках (`header-only`), що стало фундаментом стандартної бібліотеки шаблонів STL.

## Механізм COMDAT: як лінкери навчилися дедуплікації

Щоб реалізувати нову семантику `inline`, розробникам двійкових форматів та компонувальників довелося змінити внутрішню архітектуру об'єктних файлів.

У традиційних форматах UNIX (a.out) об'єктний файл містив монолітну секцію коду `.text`. Якщо компілятор змушений був згенерувати тіло для невикористаної або невбудованої `inline`-функції, воно потрапляло в загальну секцію `.text`, звідки його неможливо було вирізати без пошкодження релокацій усього файлу.

Розв'язанням стала поява концепції **COMDAT** (або *Common Data / Linkonce sections*), яка з'явилася у форматах PE/COFF (для Windows/OS/2) та згодом була стандартизована в ELF (під прапорцем секцій `SHF_GROUP` та `SHF_COMDAT`).

Замість розміщення коду в монолітному блоці компілятор загортає кожну `inline`-функцію та метод шаблону в окрему іменовану секцію, названу за декорованим іменем символу (mangled name), наприклад `.text._Z6squarei`.

Коли лінкер збирає докупи сотні об'єктних файлів:

1. Він сканує таблицю груп COMDAT у кожному `.o`.
2. Побачивши секцію `.text._Z6squarei` вперше, він виділяє під неї місце у вихідному сегменті коду.
3. Зустрівши секцію з таким самим ім'ям у наступних `.o` файлах, лінкер **просто відкидає її**, а всі посилання на цей символ з інших файлів спрямовує на адресу першої збереженої копії.

Таким чином гарантується єдиність адреси функції в межах виконуваного образу та відсутність зайвого дублювання байтів у пам'яті.

## C99: альтернативна модель inline у мові C

Комітет стандартизації мови C (ANSI/ISO C99) підійшов до проблеми `inline` інакше, ніж C++. Замість покладання на автоматичну дедуплікацію COMDAT у лінкері, стандарт C99 розробив трирівневу модель зв'язування:

:::tabs
```c
// math.h
inline double fast_abs(double x) {
    return x < 0.0 ? -x : x;
}

// math.c
#include "math.h"
// Точка створення глобального екземпляра
extern double fast_abs(double x);
```
```cpp
// У C++ розділення на inline-оголошення та окремий extern у .cpp не потрібне:
// достатньо єдиного inline-визначення у заголовку
#include <cmath>

inline double fast_abs(double x) noexcept {
    return x < 0.0 ? -x : x;
}
```
:::

У C99 визначення з модифікатором `inline` без `extern` у файлі `.h` не генерує експортованого символу для лінкера (це суто локальне визначення для можливої підстановки). Щоб функція мала зовнішнє тіло, якщо компілятор десь вирішить не вбудовувати її, рівно в одному файлі `.c` треба було додати рядок `extern double fast_abs(double x);`.

Ця відмінність між C та C++ довгі роки була джерелом плутанини та непереносного коду при спробі зібрати спільні заголовки різними компіляторами.

## C++17 та розширення на змінні: inline variables

До виходу стандарту C++17 залишалася остання велика прогалина: `inline` можна було застосовувати до функцій і методів, але **не до змінних**.

Якщо бібліотека хотіла надати глобальну константу або глобальний об'єкт конфігурації у форматі header-only:

```cpp
// До C++17: помилка multiple definition при включенні у два .cpp!
const std::string kDefaultHost = "localhost"; // У C++ const має внутрішнє зв'язування, 
                                             // що плодить окремий об'єкт std::string у кожному TU!
```

Створення об'єктів з нетривіальними конструкторами у кожній одиниці трансляції призводило до витоків пам'яті, зайвих викликів алокаторів та хаосу зі статичною ініціалізацією. Програмісти вдавалися до складних трюків зі статичними членами шаблонів класів, оскільки шаблони за правилами мови автоматично підпадали під ODR-дедуплікацію:

```cpp
// До C++17 трюк для створення глобальної змінної в заголовку:
template <typename T = void>
struct GlobalConfig {
    static inline const std::string value = "localhost"; // Не працювало до C++17
    static const std::string legacy_value;
};
template <typename T>
const std::string GlobalConfig<T>::legacy_value = "localhost";
```

Стандарт C++17 нарешті дозволив ключове слово `inline` для змінних:

```cpp
// C++17: безпечно, одна інстанція на всю програму
inline const std::string kDefaultHost = "localhost";
```

Компілятор та лінкер обробляють `inline`-змінні так само, як і `inline`-функції: створюють для них іменовану COMDAT-секцію даних у кожному об'єктному файлі та зливають їх в єдиний об'єкт під час компонування.

## C++20: Модулі як подолання ODR-хаосу

Понад 40 років еволюція ключового слова `inline` та моделі одиниць трансляції була боротьбою з наслідками механізму текстового підключення файлів `#include`. 

Поява стандартних модулів у C++20 (*C++20 Modules*) змінила правила гри. Замість того, щоб копіювати текст заголовка в сотні TU і потім змушувати лінкер дедуплікувати гігабайти однакових COMDAT-секцій, модуль компілюється один раз у двійковий формат інтерфейсу (BMI). Символи, визначені всередині модуля, мають власне **модульне зв'язування** (*module linkage*), що усуває потребу в ODR-дедуплікації для звичайних функцій та назавжди відокремлює логіку видимості імен від низькорівневих оптимізацій компонувальника.
