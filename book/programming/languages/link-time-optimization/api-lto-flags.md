# 📋 Довідник прапорців та інструментів LTO (GCC, Clang, MSVC, Rust)

Цей довідник містить повну номенклатуру прапорців компіляторів, параметрів лінкерів, змінних середовища та конфігураційних файлів для керування оптимізацією на етапі лінкування у провідних інструментальних ланцюгах. Тут також описано внутрішні механізми кожного перемикача, правила дискового кешування, тонкощі роботи з динамічними та статичними бібліотеками, взаємодію між мовами C++ та Rust, а також діагностику типових збоїв лінкування.

### 1. Clang / LLVM: Прапорці та параметри конвеєра

У екосистемі LLVM оптимізація на етапі лінкування спирається на генерацію машинно-незалежного біткоду LLVM IR (`.bc`). Залежно від обраного прапорця компілятор або записує біткод безпосередньо замість машинного коду, або упаковує його у спеціальну секцію `.llvmbc` стандартного ELF/Mach-O файлу.

#### Базові прапорці виклику `clang` та `clang++`

| Прапорець | Опис та внутрішній механізм |
| :--- | :--- |
| `-flto` | Вмикає монолітний Full LTO. Усі модулі проєкту зливаються в єдиний монолітний об'єкт `llvm::Module` всередині процесу лінкера. Забезпечує найглибший глобальний аналіз, але вимагає максимального обсягу оперативної пам'яті. |
| `-flto=full` | Повний синонім до прапорця `-flto`. |
| `-flto=thin` | Вмикає двофазний паралельний ThinLTO. Компілятор створює компактні зведення (*Module Summaries*), лінкер швидко будує глобальний індекс графа викликів, а генерація машинного коду виконується паралельно на всіх доступних ядрах процесора. |
| `-fno-lto` | Вимикає генерацію LTO-інформації; компілятор одразу створює стандартний машинний код для цільової архітектури. |
| `-fwhole-program-vtables` | Вмикає оптимізацію таблиць віртуальних методів `vtable` на рівні всієї програми. Дозволяє виконувати агресивну девіртуалізацію та видалення невикористаних записів у таблицях методів (потребує `-flto` або `-flto=thin`). |
| `-fsplit-lto-unit` | Розділяє проміжне представлення модуля на LTO-частину (необхідну для віртуальних таблиць та перевірки CFI) та звичайну частину, істотно скорочуючи обсяг пам'яті під час роботи ThinLTO. |
| `-fvisibility=hidden` | Встановлює видимість символів за замовчуванням у режим `hidden`. Це критично важливо для ліквідації мертвого коду, оскільки функції без явного експорту дозволяють компілятору повністю видалити їх за відсутності внутрішніх викликів. |
| `-fvisibility-inlines-hidden` | Приховує автоматично згенеровані символи для C++ `inline` методів класів, запобігаючи їх роздуванню в таблиці експорту динамічних бібліотек. |

#### Тонкі налаштування лінкерів `lld` та GNU `gold`

Для передачі параметрів у бекенд LLVM на етапі лінкування використовується префікс `-Wl,-mllvm,<параметр>` або спеціальні ключі лінкера `-Wl,<опція>`:

| Опція лінкера / LLVM | Опис | Приклад використання |
| :--- | :--- | :--- |
| `-Wl,--thinlto-cache-dir=<шлях>` | Задає каталог для дискового кешу скомпільованих модулів ThinLTO. Якщо модуль та його залежності не змінювалися, лінкер завантажує машинний код із кешу без повторної оптимізації. | `-Wl,--thinlto-cache-dir=/tmp/lto-cache` |
| `-Wl,--thinlto-cache-policy=<політика>` | Налаштовує правила інвалідації кешу: інтервал очищення, максимальний розмір у байтах або відсотках вільного місця на диску. | `-Wl,--thinlto-cache-policy=prune_interval=1h:max_size_bytes=10G` |
| `-Wl,--thinlto-jobs=<N>` | Визначає кількість паралельних потоків для бекендів ThinLTO. За замовчуванням використовується кількість апаратних ядер CPU. | `-Wl,--thinlto-jobs=8` |
| `-Wl,-mllvm,-import-instr-limit=<N>` | Поріг орієнтовної кількості інструкцій функції для ухвалення рішення про міжмодульний імпорт у ThinLTO (за замовчуванням 100 інструкцій). Збільшення значення покращує інлайнінг, але збільшує розмір бінарника. | `-Wl,-mllvm,-import-instr-limit=150` |
| `-Wl,-mllvm,-inline-threshold=<N>` | Базовий ліміт вартості інструкцій для стандартного проходу інлайнінгу LLVM (за замовчуванням 225 для `-O2` та 275 для `-O3`). | `-Wl,-mllvm,-inline-threshold=350` |
| `-Wl,-mllvm,-print-imports` | Вмикає детальний діагностичний вивід у консоль зі списком усіх функцій, які кожен модуль імпортував із сусідніх одиниць трансляції. | `-Wl,-mllvm,-print-imports` |

#### Механізм дискового кешування ThinLTO

Дискове кешування у ThinLTO працює за алгоритмом розрахунку криптографічного гешу від усіх факторів, що впливають на генерацію коду конкретного модуля:
1. Власний біткод вихідного модуля та його абстрактне дерево залежностей.
2. Біткоди всіх функцій, які було вирішено імпортувати з інших файлів проєкту на основі глобального індексу.
3. Версія компілятора, цільова архітектура (Target Triple), процесорні прапорці (наприклад, `-march=native`, `-mavx2`) та параметри оптимізатора.

Якщо в каталозі кешу виявлено скомпільований об'єктний файл із точним збігом сумарного гешу, процес лінкування негайно підставляє готовий машинний `.o`. Це усуває потребу в повторному проходженні важких компіляторних фаз аналізу потоків даних, розподілу регістрів та планування машинних інструкцій.

### 2. GCC (GNU Compiler Collection): Архітектура WHOPR

У компіляторі GCC оптимізація на етапі лінкування базується на архітектурі **WHOPR** (*Whole Program Optimizer*). Вона транслює високорівневий код у байткод внутрішнього представлення GIMPLE і записує його у спеціальні ELF-секції `.gnu.lto_*`.

#### Прапорці виклику `gcc` та `g++`

| Прапорець GCC | Опис та поведінка |
| :--- | :--- |
| `-flto` | Вмикає LTO. Якщо не вказано кількість потоків, автоматично обирає монолітний або багатопотоковий режим залежно від можливостей лінкера. |
| `-flto=auto` | Автоматично визначає кількість доступних процесорних ядер через механізм GNU Make Jobserver або запит до операційної системи й запускає відповідну кількість процесів `ltrans`. |
| `-flto=N` | Явно задає запуск `N` паралельних процесів кодогенерації на етапі `LTRANS`. |
| `-flto-partition=balanced` | Алгоритм розбиття всієї програми на збалансовані за обчислювальною складністю партиції (використовується за замовчуванням). |
| `-flto-partition=1to1` | Призначає рівно одну партицію на кожну вихідну одиницю трансляції без перетасування функцій між модулями. |
| `-flto-partition=none` | Вимикає розбиття програми, перемикаючи GCC у режим важкого монолітного Full LTO. |
| `-ffat-lto-objects` | Створює "товсті" об'єктні файли, що одночасно містять як GIMPLE-байткод, так і звичайний скомпільований машинний код. Дозволяє використовувати отриманий `.o` як для LTO-збірки, так і для звичайного швидкого лінкування без LTO. |
| `-fno-fat-lto-objects` | Створює "тонкі" об'єктні файли, що містять лише GIMPLE-байткод. Зменшує розмір тимчасових об'єктних файлів удвічі та прискорює проміжний запис на диск. |
| `-fuse-linker-plugin` | Активує обов'язкове використання бібліотеки `liblto_plugin.so`, що дозволяє компонувальнику розпізнавати LTO-символи всередині статичних архівів бібліотек (`.a`). |

#### Утиліти архівування для статичних бібліотек (`gcc-ar`, `gcc-ranlib`)

Коли бібліотека упаковується у статичний архів `.a` за допомогою стандартної системної утиліти `ar`, вона створює таблицю символів архіву на основі звичайних заголовків ELF. Оскільки в режимі `-fno-fat-lto-objects` об'єктний файл містить лише GIMPLE-байткод у спеціальних секціях, стандартний `ar` не бачить експортованих імен функцій і створює порожній індекс.

Щоб уникнути помилок `undefined reference` при лінкуванні статичних архівів, у тулчейні GCC завжди слід використовувати спеціальні обгортки:
- `gcc-ar` замість звичайного `ar`.
- `gcc-ranlib` замість `ranlib`.
- `gcc-nm` замість `nm`.

Ці обгортки автоматично завантажують `liblto_plugin.so` і коректно витягують таблицю символів із секцій проміжного представлення GIMPLE. Аналогічно в екосистемі LLVM використовуються утиліти `llvm-ar`, `llvm-ranlib` та `llvm-nm`.

### 3. MSVC (Microsoft Visual C++): WPO та LTCG

У середовищі Microsoft Visual Studio оптимізація всієї програми розділена на дві взаємопов'язані частини: **Whole Program Optimization (WPO)** на рівні компілятора `cl.exe` та **Link-Time Code Generation (LTCG)** на рівні лінкера `link.exe`.

#### Прапорці та параметри MSVC

| Прапорець | Інструмент | Опис та механізм дії |
| :--- | :--- | :--- |
| `/GL` | Компілятор `cl.exe` | Вмикає Whole Program Optimization. Створює об'єктні файли `.obj`, що містять внутрішнє проміжне представлення компілятора MSVC замість стандартного машинного коду формату COFF. |
| `/LTCG` | Лінкер `link.exe` | Вмикає генерацію коду під час лінкування. Лінкер завантажує проміжний код з усіх `.obj` файлів, виконує міжмодульний інлайнінг і транслює код у машинний асемблер. |
| `/LTCG:INCREMENTAL` | Лінкер `link.exe` | Вмикає інкрементальний режим LTCG. Лінкер зберігає проміжні стани аналізу й перекомпілює лише ті функції, код яких або залежності яких змінилися. |
| `/LTCG:STATUS` | Лінкер `link.exe` | Виводить детальний текстовий індикатор прогресу генерації коду у відсотках у вікно виводу збірки. |
| `/LTCG:PGINSTRUMENT` | Лінкер `link.exe` | Створює спеціальну версію виконуваного файлу, інструментовану лічильниками для збору статистики профілю виконання (перший крок PGO). |
| `/LTCG:PGOPTIMIZE` | Лінкер `link.exe` | Виконує фінальне компонування з оптимізацією на основі накопиченого файлу профілю `.pgd` (другий крок PGO). |

### 4. Rust: Керування LTO у `Cargo.toml` та міжмовна оптимізація

Мова програмування Rust тісно інтегрована з бекендом LLVM, завдяки чому підтримує всі можливості LTO як між модулями одного крейта, так і через межі зовнішніх бібліотек та мов C/C++.

#### Варіанти конфігурації в `Cargo.toml`

```toml
[profile.release]
# Режими LTO:
# "thin" — паралельний ThinLTO (рекомендовано за замовчуванням)
# "fat" / true — важкий монолітний Full LTO
# false — LTO лише всередині одного крейта (між одиницями кодогенерації)
# "off" — повністю вимкнути будь-яку міжмодульну оптимізацію
lto = "thin"

# Кількість одиниць кодогенерації (паралельних потоків):
# Менше значення = глибший інлайнінг, більше значення = швидша збірка
codegen-units = 1

# Рівень оптимізації (0-3 або "s", "z" для розміру)
opt-level = 3

# Відключення розгортання панік спрощує граф викликів
panic = "abort"
```

#### Наскрізний міжмовний LTO (Cross-Language LTO: Rust + C/C++)

Однією з найпотужніших можливостей сучасного стека LLVM є здатність проводити інлайнінг функцій мови C++ у код на мові Rust (і навпаки). Це широко використовується в браузерах Firefox та Chromium, операційній системі Android та рушіях баз даних.

Для активації міжмовного LTO необхідно:
1. Скомпілювати код на C/C++ за допомогою Clang із прапорцем `-flto=thin`.
2. Передати компілятору `rustc` прапорець `-C linker-plugin-lto`.
3. Використовувати спільний лінкер `lld` з підтримкою LLVM-біткоду.

У результаті функція `extern "C"`, викликана з коду на Rust, безпосередньо інлайниться без жодних накладних витрат на виклик чужорідного інтерфейсу (FFI).

### 5. Підтримка та вибір лінкерів

Для коректної роботи LTO лінкер повинен мати пряму підтримку рушія компілятора або підтримувати протокол плагінів.

```
┌──────────────┬──────────────────┬────────────────────────────────────────────────────────┐
│ Лінкер       │ Тип підтримки    │ Особливості та примітки                                │
├──────────────┼──────────────────┼────────────────────────────────────────────────────────┤
│ lld (LLVM)   │ Вбудована        │ Максимальна швидкість. Вбудована підтримка ThinLTO та   │
│              │ (Native LLVM)    │ Full LTO без потреби у зовнішніх .so плагінах.         │
├──────────────┼──────────────────┼────────────────────────────────────────────────────────┤
│ mold         │ Вбудована /      │ Найшвидший сучасний лінкер. Підтримує передачу біткоду │
│              │ Плагін           │ у бекенди LLVM/GCC; час лінкування скорочується в рази │
├──────────────┼──────────────────┼────────────────────────────────────────────────────────┤
│ GNU gold     │ Через плагін     │ Потребує LLVMgold.so для Clang або liblto_plugin.so    │
│              │                  │ для GCC. Підтримує паралельний ThinLTO.                │
├──────────────┼──────────────────┼────────────────────────────────────────────────────────┤
│ GNU ld (bfd) │ Через плагін     │ Повільніший за gold/lld. Підтримує GCC LTO plugin.     │
├──────────────┼──────────────────┼────────────────────────────────────────────────────────┤
│ Apple ld64   │ Через libLTO     │ Стандартний лінкер macOS/iOS. Використовує libLTO.dylib│
│              │                  │ для прозорої підтримки ThinLTO у середовищі Xcode.     │
└──────────────┴──────────────────┴────────────────────────────────────────────────────────┘
```

### 6. Діагностика типових помилок та збоїв LTO

Під час роботи з LTO розробники часто стикаються зі специфічними проблемами збірки, викликаними невідповідністю форматів проміжного коду або особливостями динамічного зв'язування.

#### Помилка: «file format not recognized» або «plugin not found»
- **Причина**: лінкер (наприклад, старий GNU `ld`) отримав об'єктний файл, який містить біткод LLVM або GIMPLE замість машинного коду, і не має підключеного відповідного плагіна.
- **Виправлення**: додати прапорець `-fuse-ld=lld` для Clang або `-fuse-linker-plugin` для GCC, або встановити пакет плагінів `llvm-gold`.

#### Помилка: «undefined reference to symbol» під час LTO-збірки
- **Причина**: символ було визначено у вбудованій асемблерній вставці (`__asm__`), але компілятор на рівні аналізу IR не побачив звернення до нього у високорівневому коді й видалив його як мертвий код (DCE).
- **Виправлення**: позначити символ атрибутом `__attribute__((used))` у вихідному коді або додати прапорець лінкера `-Wl,-u,symbol_name`, щоб явно заборонити видалення.

#### Роздування розміру динамічної бібліотеки (`.so` / `.dylib`)
- **Причина**: усі нестатичні функції мають за замовчуванням експортну видимість (`default visibility`), тому компілятор не має права видалити їх чи змінити їхні сигнатури, вважаючи, що зовнішній застосунок може викликати їх через `dlsym`.
- **Виправлення**: збирати бібліотеку з прапорцем `-fvisibility=hidden`, позначаючи як експортні лише публічні функції інтерфейсу через макроси типу `__attribute__((visibility("default")))`.
