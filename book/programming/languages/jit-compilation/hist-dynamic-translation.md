# 📜 Від Smalltalk і Self до HotSpot та V8: як народилася динамічна компіляція

У 1980 році в дослідницькому центрі Xerox PARC група дослідників під керівництвом Алана Кея намагалася розв'язати інженерний глухий кут. Їхнє творіння — мова **Smalltalk-80** — втілювало чисту об'єктно-орієнтовану модель: у ній абсолютно все було об'єктом, а кожна операція (навіть додавання двох чисел `3 + 4` або перевірка умови в циклі) відбувалася виключно через надсилання динамічного повідомлення (*message dispatch*).

Ця концептуальна чистота коштувала надзвичайно дорого. Традиційний інтерпретатор байткоду для кожного `+` мусив дістати тип лівого операнда, знайти його таблицю методів, виконати гешування чи лінійний пошук селектора, виділити новий кадр активації на стеку і лише тоді додати два числа. Програми на Smalltalk працювали у 20–50 разів повільніше за аналогічний код мовами Fortran чи C. Комп'ютери Xerox Dorado з потужними мікропроцесорами ледь справлялися з відмальовуванням графічного інтерфейсу.


## Прорив Дойча й Шифмана: динамічна трансляція та інлайн-кеш

Вихід із глухого кута 1984 року знайшли **Пітер Дойч** (*L. Peter Deutsch*) та **Аллан Шифман** (*Allan M. Schiffman*). Їхня стаття *«Efficient Implementation of the Smalltalk-80 System»* заклала фундамент сучасної динамічної трансляції.

Дойч і Шифман помітили дві фундаментальні властивості виконання програм:
1. Значна частина байткоду виконується рідко (ініціалізація, обробка помилок), але вузькі цикли прокручуються мільйони разів.
2. У конкретному місці виклику в тексті програми (*call site*) об'єкт майже завжди має один і той самий тип, попри теоретичну можливість передати туди будь-що.

Замість того, щоб завчасно компілювати весь проект або повільно інтерпретувати байткод, автори створили транслятор, який перетворював методи на машинний код процесора безпосередньо під час їхнього першого виклику й зберігав результат у кеші виконуваного коду. Якщо оперативна пам'ять вичерпувалася, старий скомпільований код просто викидався — за потреби його можна було згенерувати знову.

Найвідомішим винаходом Дойча та Шифмана став **мономорфний інлайн-кеш** (*Inline Cache, IC*). Дослідники вирішили змінювати інструкцію виклику просто в машинному коді: під час першого виконання на місце виклику підставлявся прямий перехід на знайдений метод, а поруч записувалася перевірка: чи збігається клас поточного отримувача з попереднім. Якщо збігається — виклик здійснювався як одна пряма апаратна інструкція `CALL` без жодного пошуку в словниках. Це дало змогу скоротити час диспетчеризації повідомлень у Smalltalk майже на порядок.

## Лабораторія Self: поліморфізм, деоптимізація та OSR

Наприкінці 1980-х років у Стенфордському університеті **Девід Унґар** (*David Ungar*) розпочав проект **Self** — мови на основі прототипів, у якій не було навіть класів, а доступ до будь-якого поля був викликом методу-аксесора. Якщо Smalltalk здавався повільним, то Self мав бути взагалі непрацездатним.

Але в команді Унгара працювали двоє аспірантів: **Крейг Чемберс** (*Craig Chambers*) та швейцарець **Урс Гельцле** (*Urs Hölzle*). У серії робіт 1989–1994 років вони перетворили динамічну компіляцію з простої заміни інтерпретатора на інтелектуальну оптимізуючу систему.

Чемберс і Гельцле виявили, що мономорфний інлайн-кеш Дойча розвалювався, якщо через одне місце коду проходило хоча б два різні типи (наприклад, масив цілих чисел і масив чисел із рухомою комою). Вони створили **поліморфний інлайн-кеш** (*Polymorphic Inline Cache, PIC*, 1991) — невелику згенеровану послідовність перевірок, яка тримала від двох до чотирьох пар «тип → адреса методу».

Поліморфний кеш дав ще один неочікуваний побічний ефект: він перетворився на **інструмент збору статистики типів** (*type feedback*). JIT-компілятор отримав змогу під час виконання запитати кеш: «Які типи об'єктів тут реально з'являлися за останні 10 000 ітерацій?».

Маючи ці дані, Урс Гельцле створив концепцію **спекулятивної оптимізації**:
- JIT робив припущення: «раз тут 99.9% часу приходить тип `Point`, ми скомпілюємо цей шматок як жорстко типізований машинний код і вбудуємо (*inline*) тіло методу прямо в місце виклику».
- На початку оптимізованого блоку ставилася коротка варта (*type guard*).
- Якщо варта спрацьовувала (прийшов несподіваний тип `ColorPoint`), система виконувала **деоптимізацію** (*deoptimization / bailout*) — акуратно розбирала машинний стек і повертала виконання інтерпретатору, відновлюючи змінні так, ніби оптимізації ніколи не було.

Щоб оптимізувати довгі цикли, які вже крутилися в інтерпретаторі й не виходили з нього, Гельцле реалізував **On-Stack Replacement (OSR)** — техніку підміни стекового кадру працюючої функції машинним кодом на льоту.

## Народження HotSpot JVM та ера Java

У 1994 році Девід Унґар, Урс Гельцле та данський інженер **Ларс Бак** (*Lars Bak*) заснували компанію *Animorphic Systems*. Вони розробили надшвидке середовище **Strongtalk** — типізований діалект Smalltalk із JIT-компілятором нового покоління.

У той самий час компанія Sun Microsystems випустила мову Java (1995–1996). Перші версії Java Virtual Machine (JDK 1.0 та 1.1) використовували повільний байткодовий інтерпретатор або примітивний JIT від Symantec, який просто переганяв кожен байткод в інструкції x86 без глибокого аналізу. Java зажила слави повільної та ненажерливої мови.

Sun Microsystems усвідомила загрозу і 1997 року придбала Animorphic Systems разом із усією командою та технологіями. Їхня кодова база стала основою легендарної **HotSpot JVM**, випущеної 1999 року.

Саме в HotSpot було реалізовано двоярусну архітектуру:
- **C1 (Client Compiler)** — швидкий однопрохідний компілятор для графічних додатків, де критичним є швидкий старт.
- **C2 (Server Compiler)** — шедевр архітектора **Кліффа Кліка** (*Cliff Click*), оптимізуючий бекенд на основі графа SSA (*Static Single Assignment*), який виконував глобальний аналіз потоку даних, векторизацію циклів та усунення блокувань пам'яті.

## Революція в браузерах: Lars Bak та Google V8

До 2008 року мова JavaScript у вебпереглядачах виконувалася класичними інтерпретаторами. Вебсайти сприймалися як статичні документи з рідкісними анімаціями, а складні клієнтські програми вважалися неможливими через повільність мови.

Усе змінилося, коли Google найняла Ларса Бака для створення нового рушія JavaScript для браузера Chrome. Бак зібрав у місті Орхус (Данія) команду інженерів і створив **V8**.

Застосувавши принципи, випробувані в Self та Strongtalk, команда Бака реалізувала:
1. **Приховані класи (Hidden Classes / Maps / Shapes)** — динамічні об'єкти JS на льоту отримували внутрішні дескриптори структури, перетворюючи хаотичні хеш-таблиці на фіксовані структури пам'яті з фіксованими зміщеннями полів.
2. **Адаптивну JIT-компіляцію** — V8 компілював JavaScript напряму в машинний код CPU без проміжного байткоду (у перших версіях), спираючись на поліморфні інлайн-кеші.

Вихід V8 у вересні 2008 року дав прискорення JavaScript у 10–20 разів. Це не лише зробило можливими сучасні односторінкові веб-додатки (SPA, Google Maps, Figma), але й дозволило Раяну Далу 2009 року створити **Node.js**, вивівши мову динамічних веб-сторінок у світ серверних розподілених систем.

Сьогодні концепції, винайдені Дойчем, Чемберсом, Гельцле та Баком, працюють у кожному сучасному веб-браузері (V8, SpiderMonkey, JavaScriptCore), віртуальних машинах Java (HotSpot, OpenJ9, GraalVM), середовищі .NET Core (RyuJIT), а також у спеціалізованих динамічних трансляторах, як-от PyPy та LuaJIT Майка Полла (*Mike Pall*).
