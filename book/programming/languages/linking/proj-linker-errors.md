# ⚙️ Помилки лінкера на практиці: undefined reference і multiple definition

Дві найгучніші скарги лінкера — `undefined reference` та `multiple definition` — лякають новачка дужче за будь-яку помилку компілятора: рядка не вказано, текст англійський і незрозумілий, а компілятор же «усе пройшов». Розберімо обидві на справжньому коді — як прочитати таку скаргу, де шукати причину й чим лікувати. Головне, що варто затямити одразу: це скарги на **склад** проєкту (хто з ким зібраний), а не на синтаксис окремого рядка.

## Задача

Збірка проходить компіляцію — кожен `.c` мовчки став своїм `.o`, — а на самому кінці валиться з одним із двох:

```
undefined reference to `digitalWrite'
multiple definition of `helper'
```

Рядка-винуватця немає, бо винен не рядок, а те, **як файли зійшлися разом**. Питання: що насправді означає кожна скарга й куди дивитися, щоб її прибрати.

## Ідея: лінкер скаржиться на склад, не на синтаксис

Лінкер зводить пари «потребує ↔ визначає» по **всіх** поданих йому файлах і вимагає на кожне ім'я **рівно одне** визначення. Звідси й рівно дві біди:

- **`undefined reference`** — на ім'я є попит, а пропозиції нема: жоден поданий `.o` чи бібліотека його не **визначає**. Майже завжди це означає, що ви **забули додати** до збірки потрібний файл або бібліотеку — код функції десь є, але лінкерові не сказали, де його взяти.
- **`multiple definition`** — навпаки, пропозицій **дві**: те саме ім'я визначене в кількох `.o`, і лінкер не знає, котре брати. Найчастіша причина — **повноцінне визначення в заголовку**, який уклеївся (`#include`) у кілька `.c`, тож кожен з них приніс свою копію.

Обидві лікуються правкою **складу**, а не логіки: у першому разі — додати джерело/бібліотеку; у другому — лишити визначення в **одному** місці.

Чому ж компіляція мовчить, а валиться аж лінкування? Бо компілятор бачить **один** файл за раз і вірить заголовкам на слово: оголошення `int helper(int);` — для нього достатня обіцянка, що тіло «десь буде». Він навіть не намагається його знайти — це не його робота. Перевірити обіцянки можна лише тоді, коли **всі** `.o` зійшлися разом, тобто на лінкуванні. Звідси й розподіл праці: компілятор стежить за **синтаксисом** усередині файлу, лінкер — за **зведенням імен** між файлами. Тому «не знайшов функцію» чи «знайшов двічі» — це структурно скарга лінкера, і шукати причину треба не в рядку коду, а в тому, **що з чим зібрано**.

## Як читати саме повідомлення

Скарга лінкера завжди називає **ім'я** (символ), а не файл і не рядок — бо лінкер мислить іменами, не текстом. `undefined reference to 'X'` читається як «хтось кличе `X`, а визначення `X` я ніде не знайшов». `multiple definition of 'X'` — як «визначення `X` я знайшов **більш ніж раз**». Тож перший рух щоразу той самий: узяти це ім'я й спитати про нього два питання — **хто його кличе** і **хто його визначає**. Уся діагностика зводиться до того, щоб привести кількість визначень до рівно одного: підняти з нуля (додати джерело) або збити з двох (винести з заголовка).

Корисно й те, що повідомлення часто йде **парою**: спершу скарга лінкера на символ, а нижче — рядок виду `referenced by main.o` (хто саме кличе) або перелік файлів, де ім'я визначено двічі. Цей «хвіст» і є вашою мапою: він показує **який** `.o` приніс попит чи зайву копію, тож шукати винного наосліп не доводиться.

## Випадок 1: undefined reference — забули додати джерело

Хай функція `helper` живе в окремому файлі:

```c
// helper.c
#include "helper.h"
int helper(int x) { return x * 2; }
```

```c
// main.c
#include "helper.h"
int main(void) { return helper(21); }   // кличе helper
```

Якщо зібрати **лише** `main.c`, лінкер дістане «потребує `helper`» без пари:

```
> gcc main.c -o app
undefined reference to `helper'
```

Компілятор пропустив виклик, бо заголовок `helper.h` **пообіцяв** йому, що `helper` десь існує (`int helper(int);`) — оголошення є, і цього компіляторові досить. По-справжньому перевірити обіцянку можна лише на лінкуванні, коли всі `.o` зійшлися. Лік — **додати джерело** до збірки:

```
> gcc main.c helper.c -o app        ✓ тепер «потребує helper» має пару
```

Те саме з бібліотеками: якщо `undefined reference` показує на функцію зі сторонньої бібліотеки, ви **не вказали саму бібліотеку** (`-lm`, `-lfoo`, потрібний компонент у проєкті). Код її готовий — лінкерові бракує **рядка в списку** того, що зшивати.

> 🔧 **Навіщо це.** Побачивши `undefined reference`, не правте код функції — її код, найімовірніше, цілий. Перевірте **склад збірки**: чи доданий до неї файл/бібліотека, де ця функція написана. У середовищі на кшталт Arduino IDE чи PlatformIO це означає «чи підключена потрібна бібліотека до проєкту», а не «чи правильний рядок».

## Випадок 2: multiple definition — визначення в заголовку

Тепер пастка-двійник. Хтось вписав **тіло** функції просто в заголовок:

```c
// helper.h
int helper(int x) { return x * 2; }   // ❌ повне визначення в заголовку
```

Доки заголовок включав один файл, усе мовчало. Щойно його включили **двоє** — `main.c` і, скажімо, `loop.c`, — кожен приніс свою копію `helper`, і лінкер дістав **два** визначення одного імені:

```
> gcc main.c loop.c -o app
multiple definition of `helper'
```

Причина суто складальна: один **`#include`** — це буквальне вклеювання тексту, тож тіло з заголовка розмножилося по всіх, хто його включив. Лік — лишити визначення **в одному** місці. Три робочі способи:

```c
// 1) Класика: у заголовку — лише ОГОЛОШЕННЯ, тіло — в одному .c
// helper.h
int helper(int x);                    // обіцянка
// helper.c
int helper(int x) { return x * 2; }   // єдине визначення

// 2) inline: дозволяє однакове визначення в кожному файлі (для коротких)
// helper.h
inline int helper(int x) { return x * 2; }

// 3) static: у кожному файлі — СВОЯ прихована копія (роздуває код)
// helper.h
static int helper(int x) { return x * 2; }
```

Перший спосіб — **типовий** для будь-чого нетривіального: заголовок обіцяє, один `.c` виконує. `inline` тут означає не «вбудуй мене заради швидкості», а «це визначення може повторюватися в кількох файлах — вважай їх **одним**»; добре для коротких помічників у заголовку. `static` дає кожному файлу **окрему** копію (конфлікту імен нема, бо назовні їх не видно) — найгрубший варіант, бо роздуває образ і годиться хіба для дрібниць.

> 🔧 **Навіщо це.** Правило під сподом — **одне визначення на ім'я в усій програмі**. Тому в заголовки кладіть **оголошення** (обіцянки), а **тіла** — у `.c`. Побачили `multiple definition` — шукайте не зайвий рядок коду, а **визначення, що потрапило в заголовок** і розмножилося по файлах, які його включили.

## Пастки

- **`undefined reference to vtable…` / на конструктор** — у C++ часто означає, що ви **оголосили** метод класу, але не **написали** його тіло (або не додали відповідний `.cpp`). Та сама хвороба «попит без пропозиції», лише замаскована під клас.
- **Порядок бібліотек у командному рядку** інколи важить, і причина суто в тому, **як** лінкер сканує склад. Класичний `ld` проходить файли **зліва направо** й тягне з бібліотеки символ, лише якщо на нього **вже** є невдоволений попит від чогось, прочитаного раніше. Тож бібліотеку згадують **після** тих, хто її потребує (`gcc main.c -lfoo`, а не `gcc -lfoo main.c`): інакше, дійшовши до бібліотеки, лінкер ще не знає, що `foo` комусь треба, і просто її пропускає. Дивна `undefined reference` на функцію, що **точно** в бібліотеці є, — перший привід перевірити порядок.

- **C-функція з C++-файлу** (часта пастка на МК) дає `undefined reference`, хоч джерело додане: C++ **спотворює імена** (*name mangling* — вшиває в символ типи аргументів), тож кличе він `helper(int)` під одним іменем, а C-файл визначає `helper` під іншим. Лік — обгорнути оголошення C-коду в `extern "C" { … }`, щоб C++ кликав його «простим» іменем без спотворення.
- **`inline` без визначення** — якщо оголосити функцію `inline` у заголовку, а тіло сховати в `.c`, дістанете `undefined reference`: інші файли бачать обіцянку «тіло буде тут», а його там немає. `inline`-функція має нести своє тіло **в заголовку**.
- **Та сама глобальна змінна в кількох `.c`** дає `multiple definition` так само, як функція: у заголовку — `extern int counter;` (обіцянка), а саме `int counter;` — в **одному** `.c`. Слово `extern` тут і означає «**визначення десь в іншому файлі**» — рівно та обіцянка, яку лінкер потім має закрити.

## Загальний рецепт

Обидва випадки лягають в один короткий алгоритм, бо обидва — про **кількість визначень** одного імені:

```
1. Прочитати ІМ'Я символу зі скарги (не файл, не рядок).
2. undefined reference?  → визначень нуль:
      • чи доданий до збірки .c/.cpp, де воно написане?
      • чи вказана бібліотека (-lfoo) — і ПІСЛЯ тих, хто її кличе?
      • C-функція з C++? → загорнути в extern "C".
3. multiple definition?  → визначень два й більше:
      • знайти визначення, що потрапило в ЗАГОЛОВОК;
      • лишити в заголовку лише ОГОЛОШЕННЯ, тіло — в одному .c
        (або inline для коротких; глобалі — extern + одне визначення).
4. Перебудувати. Ціль — рівно одне визначення на ім'я.
```

Жоден крок не чіпає **логіку** функції — лише **склад** збірки та місце визначення. Саме тому помилки лінкера, попри грізний вигляд, лікуються майже механічно: ви не налагоджуєте поведінку, ви балансуєте бухгалтерію імен, яку лінкер веде по всьому проєкту.
