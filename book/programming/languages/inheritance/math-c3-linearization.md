# 🧮 Алгоритм C3-лінеаризації: математичне розв'язання порядку успадкування

У мовах із множинним спадкуванням постає фундаментальне математичне питання: якщо клас має кількох предків, кожен із яких може перевизначати спільні методи, у якому строгому лінійному порядку рантайм повинен шукати реалізацію методу? Цей лінійний список класів називається **порядком розв'язання методів** (англ. *Method Resolution Order*, MRO).

Формально ієрархія спадкування — це скінченна частково впорядкована множина (посет, англ. *partially ordered set*, poset) `(S, <_S)`, де відношення `A <_S B` означає, що клас `A` є безпосереднім або опосередкованим нащадком класу `B`. У термінах теорії графів це орієнтований ациклічний граф (DAG), у якому вершинами є класи, а ребра спрямовані від нащадка до його прямих предків.

Задача лінеаризації полягає у побудові бієктивного відображення `τ: S → {1, 2, ..., |S|}`, яке перетворює частковий порядок у тотальний лінійний порядок (список), задовольняючи три обов'язкові інженерно-математичні аксіоми:

1. **Збереження локального порядку (Local Precedence Order, LPO):** Якщо в оголошенні класу `C` предки записані в порядку `(B₁, B₂, ..., Bₙ)`, то в результуючому списку `B₁` зобов'язаний стояти раніше за `B₂`, `B₂` раніше за `B₃` і так далі. Тобто порядок запису в коді фіксує пріоритет вибору між прямими батьками.
2. **Збереження відношення предка (Subclass before Superclass):** Будь-який клас-нащадок `C` повинен з'являтися в списку раніше за будь-якого зі своїх предків `B`. Нащадок спеціалізує предка, тому його методи завжди мають вищий пріоритет за узагальнені методи пращурів.
3. **Монотонність (Monotonicity):** Якщо клас `A` стоїть раніше за клас `B` у лінеаризації класу `X`, то в лінеаризації будь-якого нащадка `Y` класу `X` клас `A` також **зобов'язаний** стояти раніше за `B`. Порушення монотонності призводить до руйнівних парадоксів у системі типів: додавання проміжного підкласу раптово змінює порядок виклику методів у вже налагоджених базових класах.

## Чому наївні алгоритми обходу ламаються

Ранні об'єктно-орієнтовані системи використовували прості стратегії обходу графів — пошук у глибину (DFS) або пошук у ширину (BFS). Обидві виявилися математично хибними для ромбоподібних ієрархій.

Розглянемо класичний ромб:
- Базовий кореневий клас `O` містить метод `f()`.
- Класи `A` та `B` успадковують `O`. При цьому клас `B` перевизначає `f()`, а `A` залишає реалізацію з `O` без змін.
- Клас `C` успадковує `(A, B)`.

```
        O [f]
       / \
      A   B [f']
       \ /
        C
```

Застосуємо наївний пошук у глибину зліва направо (DFS left-to-right), як це було реалізовано в мові Python до версії 2.2 та в ранніх діалектах Lisp:

```
Порядок обходу DFS(C):
1. Відвідуємо нащадка: C
2. Йдемо в першого лівого предка: A
3. Йдемо в предка класу A: O (досягли вершини)
4. Повертаємося та йдемо в другого предка C: B

Результат обходу DFS: [ C, A, O, B ]
```

Тут криється фундаментальна математична та логічна помилка: узагальнений кореневий клас `O` опинився в списку **раніше** за свій спеціалізований підклас `B`. Коли екземпляр класу `C` викликає метод `f()`, пошук знаходить застарілу реалізацію в `O` і негайно виконує її, повністю проігнорувавши перевизначену версію в `B`. Принцип об'єктного програмування був грубо порушений: узагальнення пращура знищило спеціалізацію нащадка.

Пошук у ширину (BFS) дає порядок `[ C, A, B, O ]` для цього симетричного ромба, але миттєво ламається на асиметричних ієрархіях, де одна гілка довша за іншу. Якщо `A` успадковує `O` через проміжний клас `A₁`, BFS відвідає `B` раніше за `A₁`, грубо порушивши глибину лівої гілки та локальний порядок.

## Формальне визначення алгоритму C3

Алгоритм C3-лінеаризації (англ. *C3 superclass linearization*), розроблений Кімом Барреттом, Бобом Кессомлом, Дейвом Муном, Девідом Фонтеном, Робертом Келлі та Грегорі Голкомбом для мови Dylan у 1996 році (стаття на OOPSLA '96), розв'язує задачу побудови MRO через рекурсивну функцію злиття списків (англ. *merge*).

Нехай клас `C` успадковує впорядкований список прямих предків `(B₁, B₂, ..., Bₙ)`. Повна лінеаризація `L(C)` визначається рекурсивним рівнянням:

```
L(C) = [C] + merge( L(B₁), L(B₂), ..., L(Bₙ), [B₁, B₂, ..., Bₙ] )
```

де:
- `L(Bᵢ)` — рекурсивно обчислений список лінеаризації `i`-го предка;
- `[B₁, B₂, ..., Bₙ]` — список безпосередніх предків класу `C`, доданий наприкінці операції `merge`, який унеможливлює порушення локального порядку (LPO);
- `+` — операція конкатенації списків;
- Базовий випадок для кореневого класу `O` (який не має батьків): `L(O) = [O]`.

### Правила оператора merge

Операція `merge(L₁, L₂, ..., Lₖ)` приймає набір непустих списків і виконує детермінований ітеративний процес вибору елементів:

1. **Визначення кандидата:** Розглядаємо перший елемент (голову, англ. *head*) першого списку в наборі.
2. **Перевірка на чистоту (Tail Check):** Перевіряємо, чи цей елемент не міститься у **хвостах** (англ. *tails*, тобто на будь-якій позиції, крім першої) будь-якого іншого списку з набору `merge`.
3. **Успішний вибір:**
   - Якщо кандидат відсутній у всіх хвостах, він визнається безпечним.
   - Елемент додається в кінець вихідної лінеаризації `L(C)`.
   - Цей елемент видаляється з початку (голів) усіх списків у наборі, де він стояв першим.
   - Алгоритм повертається до кроку 1 з оновленими списками.
4. **Невдалий вибір (конфлікт залежностей):**
   - Якщо кандидат присутній у хвості хоча б одного списку, ми не маємо права брати його зараз, бо якийсь інший клас має бути опрацьований раніше за нього.
   - Переходимо до голови **наступного списку** в наборі та повторюємо перевірку хвостів для нього.
5. **Умова зупинки та коректність:**
   - **Успіх:** Усі списки стали порожніми. Повертається повний лінійний список `L(C)`.
   - **Помилка монотонності (Inconsistent Hierarchy):** Якщо перевірено голови всіх списків, але жодна не є допустимою (виникло циклічне блокування), граф спадкування визнається **математично суперечливим**. Компілятор або рантайм зупиняє роботу й викидає виняток створення типу.

## Покроковий приклад 1: Класичний ромб

Обчислимо MRO для ромба: `O` (корінь), `A(O)`, `B(O)`, `C(A, B)`.

### Базові лінеаризації

```
L(O) = [O]
L(A) = [A] + merge(L(O), [O]) = [A] + merge([O], [O]) = [A, O]
L(B) = [B] + merge(L(O), [O]) = [B] + merge([O], [O]) = [B, O]
```

### Злиття для нащадка C

```
L(C) = [C] + merge( L(A), L(B), [A, B] )
     = [C] + merge( [A, O], [B, O], [A, B] )
```

Виконуємо кроки злиття:

```
Поточні списки: [A, O], [B, O], [A, B]

Ітерація 1:
  Кандидат = голова першого списку = A.
  Хвости інших списків:
    хвіст([B, O]) = [O]  (елемента A немає)
    хвіст([A, B]) = [B]  (елемента A немає)
  → A чистий! Додаємо A.
  Видаляємо A з голів.
  Результат: [ C, A ]
  Залишок списків: [O], [B, O], [B]

Ітерація 2:
  Кандидат = голова першого списку = O.
  Хвости інших списків:
    хвіст([B, O]) = [O]  ← O ЗНАЙДЕНО У ХВОСТІ!
  → O блокується класом B, бо B має стояти перед O.
  
  Беремо голову наступного списку = B (з [B, O]).
  Хвости інших списків:
    хвіст([O]) = []   (елемента B немає)
    хвіст([B]) = []   (елемента B немає)
  → B чистий! Додаємо B.
  Видаляємо B з голів.
  Результат: [ C, A, B ]
  Залишок списків: [O], [O], []

Ітерація 3:
  Кандидат = голова першого списку = O.
  Хвости інших списків:
    хвіст([O]) = []
    хвіст([])  = []
  → O чистий! Додаємо O.
  Результат: [ C, A, B, O ]
  Залишок списків: [], [], []  → Завершено успішно!
```

Підсумковий список `L(C) = [ C, A, B, O ]` бездоганно дотримується принципу підстановки: будь-який виклик методу спочатку шукатиме реалізацію в нащадках (`C`), потім у спеціалізаціях (`A`, `B`) і лише в останню чергу — в узагальненому корені `O`.

## Покроковий приклад 2: Складна асиметрична ієрархія

Розглянемо складніший приклад, де наївні підходи завжди припускаються помилок:
- `O` (базовий клас)
- `A(O)`, `B(O)`, `C(O)`
- `D(A, B)` — успадковує `A` та `B`
- `E(B, C)` — успадковує `B` та `C`
- `K(D, E)` — фінальний клас, що поєднує `D` та `E`

```
          O
       /  |  \
      A   B   C
       \ / \ /
        D   E
         \ /
          K
```

Обчислимо проміжні лінеаризації:

```
L(D) = [D] + merge(L(A), L(B), [A, B])
     = [D] + merge([A, O], [B, O], [A, B])
     = [D, A, B, O]

L(E) = [E] + merge(L(B), L(C), [B, C])
     = [E] + merge([B, O], [C, O], [B, C])
     = [E, B, C, O]
```

Тепер обчислимо лінеаризацію фінального класу `K`:

```
L(K) = [K] + merge( L(D), L(E), [D, E] )
     = [K] + merge( [D, A, B, O], [E, B, C, O], [D, E] )
```

Трасування злиття:

```
Крок 1:
  Кандидат D (з 1-го списку).
  Хвости [E, B, C, O] та [D, E]: D є тільки головою в [D, E], у хвостах його немає.
  → Обираємо D.
  Результат: [ K, D ]
  Списки: [A, B, O], [E, B, C, O], [E]

Крок 2:
  Кандидат A (з 1-го списку).
  Хвости: у [E, B, C, O] та [E] елемента A немає.
  → Обираємо A.
  Результат: [ K, D, A ]
  Списки: [B, O], [E, B, C, O], [E]

Крок 3:
  Кандидат B (з 1-го списку).
  Хвіст [E, B, C, O] містить B! (B стоїть на другій позиції після E).
  → B заблоковано, бо клас E має йти раніше за B.
  Беремо голову 2-го списку: E.
  Хвости: у [B, O] елемента E немає, у [E] він є головою.
  → Обираємо E.
  Результат: [ K, D, A, E ]
  Списки: [B, O], [B, C, O], []

Крок 4:
  Кандидат B (з 1-го списку).
  Хвіст [B, C, O] має тільки [C, O] (B немає у хвості).
  → Обираємо B.
  Результат: [ K, D, A, E, B ]
  Списки: [O], [C, O], []

Крок 5:
  Кандидат O (з 1-го списку).
  Хвіст [C, O] містить O!
  → O заблоковано.
  Беремо голову 2-го списку: C.
  Хвіст [O] порожній від C.
  → Обираємо C.
  Результат: [ K, D, A, E, B, C ]
  Списки: [O], [O], []

Крок 6:
  Кандидат O.
  → Обираємо O.
  Остаточний результат: [ K, D, A, E, B, C, O ]
```

Зверніть увагу: клас `B` є спільним предком як для `D`, так і для `E`. Алгоритм C3 розмістив `E` раніше за `B`, тому що в ланцюжку `E(B, C)` клас `E` є безпосереднім спеціалізатором `B`. Це зберегло абсолютну узгодженість для всіх гілок ієрархії.

## Кооперативне множинне спадкування та super()

У мовах на кшталт Python 3 виклик `super()` спирається безпосередньо на згенерований список `__mro__`.

Важливо усвідомити: виклик `super().method()` усередині класу `A` **не викликає статично метод свого батька `O`**. Він знаходить клас `A` у поточному ланцюжку `__mro__` конкретного екземпляра під час виконання і передає керування **наступному за списком класу**.

У нашому прикладі `L(K) = [ K, D, A, E, B, C, O ]`:
- Виклик `super()` всередині `A` передасть керування в клас `E` (який взагалі не є родичем `A` по вертикалі!).
- Такий механізм називається **кооперативним диспетчеризуванням** (англ. *cooperative multiple inheritance*).

Він вимагає суворої дисципліни сигнатур: усі спільні методи в ієрархії повинні приймати спільний набір аргументів через `*args, **kwargs` та обов'язково продовжувати ланцюжок викликом `super()`, доки керування не дійде до кореневого класу `object`.

## Несумісні ієрархії: доведення суперечності

Математична строгість C3 гарантує виявлення помилок проєктування на етапі створення класів. Якщо розробник створює циклічний або суперечливий порядок успадкування, алгоритм доводить неможливість лінеаризації.

Розглянемо конфлікт:
- `X(O)`
- `Y(O)`
- `A(X, Y)` — фіксує локальний порядок `X < A Y` (X перед Y)
- `B(Y, X)` — фіксує локальний порядок `Y < B X` (Y перед X)
- `Z(A, B)` — спроба створити нащадка, що поєднує обидва класи

Спробуємо обчислити `L(Z)`:

```
L(A) = [A, X, Y, O]
L(B) = [B, Y, X, O]

L(Z) = [Z] + merge( [A, X, Y, O], [B, Y, X, O], [A, B] )
     = [Z, A] + merge( [X, Y, O], [B, Y, X, O], [B] )
     = [Z, A, B] + merge( [X, Y, O], [Y, X, O] )
```

Аналізуємо залишок `merge([X, Y, O], [Y, X, O])`:
1. Кандидат 1: `X`. Перевіряємо хвіст другого списку `[Y, X, O]` — він містить `X` на другій позиції! Вибір `X` заблоковано класом `Y`.
2. Кандидат 2: `Y`. Перевіряємо хвіст першого списку `[X, Y, O]` — він містить `Y` на другій позиції! Вибір `Y` заблоковано класом `X`.

Виник взаємний тупик: жоден кандидат не може бути обраний без порушення локального порядку одного з батьківських класів. Алгоритм зупиняється та генерує помилку `TypeError: Cannot create a consistent method resolution order (MRO)`.

Ця властивість робить C3 надійним математичним фільтром, що унеможливлює існування прихованих дефектів диспетчеризації у великих кодових базах.
