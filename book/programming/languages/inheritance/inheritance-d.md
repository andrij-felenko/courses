Коли програма зростає, нові структури даних неминуче виявляються розширенням уже наявних. Наприклад, системний буфер вводу-виводу має базовий дескриптор, розмір та лічильник байтів, а мережевий буфер додає до них адресу сокета й прапорці шифрування. Якщо описувати мережевий буфер як абсолютно нову сутність, доведеться переписати всі наявні функції обробки, валідації та логування базового буфера. Якщо ж обернути базовий буфер у нову структуру як окреме поле, то кожна передача в наявні функції вимагатиме явного розіменування або витягування внутрішньої адреси.

У машинному коді постає жорстка вимога: як гарантувати, що функція, скомпільована для роботи з базовим типом, зможе без жодних змін і без накладних обгорток опрацьовувати розширений тип? Пам'ять процесора — це плоский масив байтів, а доступ до полів виконується через жорстко зашиті в інструкції зсуви адрес від початку структури. Якщо поля базового типу в розширеному об'єкті змістяться хоча б на один байт, звичайна процесорна інструкція прочитає сміття.

Відповіддю трансляторів мов програмування стало **спадкування** (англ. *inheritance*, від лат. *hereditas* — «майно, що передається нащадкам»). Це механізм мови, який одночасно вирішує дві задачі: задає відношення підтипізації на рівні системи типів («розширений тип *є* базовим типом») та визначає детерміноване двійкове розміщення полів у пам'яті (англ. *subobject layout*), за якого базовий блок стає невіддільною частиною нового об'єкта.

> 🔧 **Навіщо це.** Спадкування об'єднує дві різні речі: повторне використання двійкової структури даних (англ. *implementation inheritance*) та контрактний поліморфізм підтипів (англ. *subtyping*). Розуміння того, як компілятор транслює класи у зміщення байтів, вказівники на таблиці та thunk-перехідники, дає змогу бачити точну ціну абстракцій: від безкоштовного нульового зсуву в одиничному спадкуванні до прихованих розіменувань пам'яті у віртуальних ромбах.

## Під-об'єкти та двійкова розкладка при одиничному спадкуванні

Основою реалізації спадкування в пам'яті є поняття **під-об'єкта** (англ. *subobject*). Коли клас `Derived` успадковує клас `Base`, компілятор не змішує їхні поля в довільному порядку, а вбудовує повноцінний екземпляр `Base` на початок виділеного блоку пам'яті `Derived`.

Таке вбудовування називається префіксним розміщенням (англ. *prefix layout*). Поля базового класу займають діапазон байтів від зсуву `0` до `sizeof(Base) - 1`. Одразу після них (з урахуванням правил вирівнювання) розміщуються власні поля класу-нащадка.

![Розкладка пам'яті при одиничному спадкуванні: під-об'єкт Base розташовано на зсуві 0, поля Derived додаються одразу після нього, адреси Base* і Derived* збігаються](/book/programming/languages/inheritance/img/subobject-single.svg)
*Двійкова розкладка об'єкта при одиничному спадкуванні. Оскільки під-об'єкт Base починається з нульового байта об'єкта Derived, адреса нащадка в точності дорівнює адресі предка, а приведення типу є безкоштовною операцією часу компіляції.*

Розглянемо це розміщення на конкретному прикладі коду:

:::tabs
```c
#include <stdio.h>
#include <stddef.h>

/* Базовий під-об'єкт */
typedef struct {
    int id;
    int flags;
} Base;

/* Похідна структура: базовий блок стоїть строго першим */
typedef struct {
    Base base;         /* Зсув 0 байтів */
    double score;      /* Зсув 8 байтів (після вирівнювання) */
    int extra;         /* Зсув 16 байтів */
} Derived;

void print_base(const Base* b) {
    printf("Base id: %d, flags: 0x%X\n", b->id, b->flags);
}

int main(void) {
    Derived d;
    d.base.id = 42;
    d.base.flags = 0x01;
    d.score = 99.5;
    d.extra = 7;

    /* Безпечне приведення вказівника: адреса d збігається з адресою d.base */
    const Base* b_ptr = (const Base*)&d;
    print_base(b_ptr);

    printf("Зсув base:  %zu B\n", offsetof(Derived, base));
    printf("Зсув score: %zu B\n", offsetof(Derived, score));
    return 0;
}
```
```cpp
#include <iostream>
#include <cstddef>

class Base {
public:
    int id{42};
    int flags{0x01};
};

class Derived : public Base {
public:
    double score{99.5};
    int extra{7};
};

void print_base(const Base* b) {
    std::cout << "Base id: " << b->id << ", flags: 0x" << std::hex << b->flags << std::dec << "\n";
}

int main() {
    Derived d;

    // Upcast: компілятор не генерує жодної машинної інструкції зміщення
    const Base* b_ptr = &d;
    print_base(b_ptr);

    std::cout << "Адреса Derived: " << static_cast<const void*>(&d) << "\n";
    std::cout << "Адреса Base:    " << static_cast<const void*>(b_ptr) << "\n";
    std::cout << "Різниця адрес:  " << reinterpret_cast<uintptr_t>(b_ptr) - reinterpret_cast<uintptr_t>(&d) << " B\n";
    return 0;
}
```

Завдяки префіксному розташуванню виникає ключова інваріантна властивість одиничного спадкування: **приведення типу вгору по ієрархії (англ. *upcasting*) є абсолютно безкоштовною операцією часу компіляції (zero-cost abstraction)**. Чисельне значення адреси `Derived*` та `Base*` ідентичне:

```
адреса(Derived) == адреса(Base)  [зсув Δ = 0 байтів]
```

Коли функція приймає `Base*`, вона звертається до поля `flags` за фіксованим зміщенням `+4` байти. Оскільки в `Derived` поле `flags` лежить на тих самих `+4` байтах від початку об'єкта, процесор виконує операцію зчитування пам'яті без жодних посередників і без знання про існування класу `Derived`.

Якщо клас містить віртуальні методи, компілятор розміщує вказівник на таблицю віртуальних функцій (`vptr`) також на початку під-об'єкта (зсув `0`). При одиничному спадкуванні похідний клас **розділяє той самий `vptr` зі своїм базовим класом**: компілятор просто розширює таблицю `vtable`, дописуючи адреси нових методів нащадка в її кінець і замінюючи покажчики перевизначених (*overridden*) методів.

### Оптимізація порожнього базового класу (EBO)

Особливим випадком під-об'єктної моделі є успадкування від класів без полів даних (англ. *empty base classes*), які використовуються як мітки типів або постачальники статичних функцій.

Згідно зі стандартом C++, будь-який самостійний об'єкт мусить мати розмір щонайменше `1` байт, щоб два різні екземпляри завжди мали унікальні адреси в пам'яті (`sizeof(Empty) == 1`). Проте якщо такий клас стає базовим, спрацьовує **оптимізація порожнього базового класу** (англ. *Empty Base Optimization*, EBO). Компілятор виділяє для під-об'єкта порожньої бази рівно `0` байтів, не збільшуючи розмір похідного класу:

```cpp
struct Empty {};
struct Holder : public Empty {
    int data; // sizeof(Holder) == 4 байти (EBO спрацювала, 1 байт Empty не додається)
};
```

У C++20 цю оптимізацію розширили на композицію за допомогою атрибута `[[no_unique_address]]`, що дозволило отримувати нульовий розмір порожніх полів без використання спадкування.

### Небезпека зрізання об'єкта (Object Slicing)

Прямим наслідком двійкового розташування під-об'єктів є небезпека **зрізання об'єкта** (англ. *object slicing*). Вона виникає тоді, коли об'єкт похідного класу присвоюється змінній базового класу за значенням (*by value*), а не за вказівником чи посиланням:

```cpp
Derived d;
Base b = d; // Зрізання: копіюються лише sizeof(Base) байтів
```

У цей момент процесор виконує побайтове копіювання (або виклик конструктора копіювання `Base(const Base&)`), який копіює рівно перші `sizeof(Base)` байтів пам'яті `d`. Усі додаткові поля `Derived` безслідно відкидаються.

Якщо базовий клас містив віртуальні методи, новий об'єкт `b` отримує таблицю віртуальних методів `Base::vtable`, а не `Derived::vtable`. Будь-який поліморфізм повністю втрачається. Запобігти цьому дефекту можна оголошенням копіювальних конструкторів базових поліморфних класів як захищених (`protected`) або заборонених (`= delete`), гарантуючи роботу з ієрархіями виключно через покажчики чи посилання.

### Порядок конструювання та знищення

Двійкова залежність накладає строгий закон на життєвий цикл об'єкта:
1. **Конструювання відбувається строго знизу вгору по ієрархії (від предка до нащадка).** Спершу виділяється пам'ять під повний об'єкт. Потім викликається конструктор `Base`, який ініціалізує свої поля та налаштовує `vptr` на таблицю базового класу. Лише після його успішного завершення починає працювати конструктор `Derived`, який перезаписує `vptr` на таблицю нащадка та ініціалізує власні поля.
2. **Знищення відбувається у строго зворотному порядку (від нащадка до предка).** Спочатку деструктор `Derived` очищає власні ресурси та повертає `vptr` до стану `Base`, після чого деструктор `Base` звільняє базові ресурси.

Як зароджувався цей механізм і чому розробники перших мов обрали саме префіксний підхід, докладно висвітлює [історія еволюції спадкування від Simula до Cfront](book:programming/inheritance/hist-simula-cfront.md).

## Множинне спадкування та зміщення вказівників (Pointer Adjustment)

Коли один клас успадковує два або більше незалежних базових класів, принцип єдиного нульового зсуву порушується. Об'єкт не може одночасно розмістити два різних під-об'єкти на нульовому зміщенні.

Нехай клас `Derived` успадковує `BaseA` та `BaseB`:

```cpp
class BaseA {
public:
    virtual void opA();
    int a;
};

class BaseB {
public:
    virtual void opB();
    int b;
};

class Derived : public BaseA, public BaseB {
public:
    void opA() override;
    void opB() override;
    int d;
};
```

Компілятор змушений вибудувати під-об'єкти послідовно один за одним. Перший базовий клас (`BaseA`) отримує зсув `0`. Другий базовий клас (`BaseB`) розміщується зі зсувом `Δ = sizeof(BaseA)` (з урахуванням вирівнювання).

![Розкладка пам'яті при множинному спадкуванні: під-об'єкт BaseA на зсуві 0, під-об'єкт BaseB на зсуві +16B, власні поля Derived на зсуві +32B](/book/programming/languages/inheritance/img/subobject-multiple.svg)
*Розкладка пам'яті при множинному спадкуванні. Для отримання коректного вказівника на BaseB компілятор виконує pointer adjustment (+16 байтів). Приведення Derived* до BaseB* вимагає арифметики під час виконання.*

### Механізм Pointer Adjustment

Внаслідок такого розташування вказівник на об'єкт `Derived` більше **не дорівнює** вказівнику на його базовий клас `BaseB`:

```
BaseA* pa = &derived;  // pa == 0x2000 (зсув 0 байтів)
BaseB* pb = &derived;  // pb == 0x2010 (зсув +16 байтів)
```

Операція приведення типу `Derived* → BaseB*` перестає бути безкоштовною абстракцією: компілятор генерує інструкцію додавання константи зміщення до адреси.

Ще важливішим є приведення вниз по ієрархії (англ. *downcasting*) від `BaseB*` назад до `Derived*`:

```cpp
Derived* pd = static_cast<Derived*>(pb);
// Компільований машинний код: pd = (pb != nullptr) ? (char*)pb - 16 : nullptr;
```

Компілятор зобов'язаний згенерувати умовну перевірку на `nullptr`. Якби він наївно відняв `16` байтів від нульового покажчика, програма отримала б псевдоадресу `0xFFFFFFF0` (чи інше некоректне число), що призвело б до падіння під час подальшої перевірки на `NULL`.

### Перехресне приведення типів (Cross-Casting) та dynamic_cast

Якщо програма володіє покажчиком на другий базовий клас `BaseB*` і хоче перетворити його на перший базовий клас `BaseA*`, статичне приведення `static_cast<BaseA*>(pb)` видасть помилку компіляції: типи `BaseA` та `BaseB` не перебувають у відношенні спорідненості.

Єдиним способом виконати таке бічне приведення (англ. *cross-cast* або *sideways cast*) є поліморфний оператор `dynamic_cast`:

```cpp
BaseA* pa = dynamic_cast<BaseA*>(pb);
```

Оператор `dynamic_cast` звертається до RTTI-метаданих: він зчитує зміщення `offset-to-top` з таблиці `vtable` для `BaseB`, обчислює початок повного об'єкта `Derived` (`0x2000`) і перевіряє за дескриптором типів, чи містить `Derived` гілку `BaseA`. Якщо так, повертається адреса `BaseA*` (зсув `0`).

### Вказівники на таблиці та thunk-функції

Оскільки `BaseA` та `BaseB` мають власні набори віртуальних методів, об'єкт `Derived` містить **два окремі вказівники на віртуальні таблиці**:
1. `vptr_A` на зсуві `0` — вказує на основну таблицю віртуальних функцій (англ. *primary vtable*), яка містить методи `BaseA` та нові методи `Derived`.
2. `vptr_B` на зсуві `+16` — вказує на вторинну таблицю (англ. *secondary vtable*), що описує методи `BaseB`.

Уявімо ситуацію: клієнтський код володіє вказівником `BaseB* ptr` і викликає віртуальний метод `ptr->opB()`. За поліморфізмом має виконатися перевизначений метод `Derived::opB()`.

Але виникає апаратна колізія:
- Метод `Derived::opB()` розраховує отримати в регістрі першого аргументу (`this`, наприклад, у регістрі `RDI` для System V AMD64 ABI) адресу **початку повного об'єкта `Derived`** (тобто `0x2000`).
- Клієнт викликає метод через вказівник `BaseB*`, тому передає значення `0x2010`.

Якби метод виконав прямий доступ до поля `d`, що лежить на зсуві `+32` від початку `Derived`, він звернувся б за адресою `0x2010 + 32 = 0x2030` замість правильної адреси `0x2020` і пошкодив би пам'ять.

Для подолання цієї розбіжності компілятор створює спеціальний мікрокод — **thunk-функцію** (англ. *this-adjustment thunk*). У вторинній таблиці віртуальних методів `BaseB` адреса методу `opB` вказує не безпосередньо на `Derived::opB`, а на перехідник:

```
[Secondary vtable для BaseB]:
  slot 0 (opB) → non-virtual thunk to Derived::opB()

Код thunk-функції:
  sub rdi, 16                 ; коректуємо вказівник this: віднімаємо 16 байтів
  jmp Derived::opB            ; переходимо до справжнього методу Derived::opB
```

Thunk відновлює правильну адресу `this` за один такт процесора без створення додаткового кадру стека. Побачити на власні очі двійкові зміщення, таблиці та поведінку `static_cast` проти `reinterpret_cast` можна у [практичному проєкті з дослідження під-об'єктів і зсувів](book:programming/inheritance/proj-subobject-offsets.md).

## Ромбоподібне спадкування (The Diamond Problem)

Справжні труднощі множинного спадкування виникають тоді, коли два базові класи самі мають спільного предка. Ця конфігурація утворює ромб у графі спадкування.

```
       Base [ int counter; ]
       /  \
     Left  Right
       \  /
      Bottom
```

Розглянемо, що відбувається за звичайного (невіртуального) спадкування:

```cpp
struct Base {
    int counter;
};

struct Left : public Base {
    void stepLeft() { counter++; }
};

struct Right : public Base {
    void stepRight() { counter += 2; }
};

struct Bottom : public Left, public Right {
    void stepBoth() {
        // counter++; // ПОМИЛКА КОМПІЛЯЦІЇ: неоднозначність!
        Left::counter++;   // змінює копію Base всередині Left
        Right::counter++;  // змінює копію Base всередині Right
    }
};
```

![Ромбоподібне невіртуальне спадкування: об'єкт Bottom містить два незалежні екземпляри Base, викликаючи неоднозначність доступу та дублювання стану](/book/programming/languages/inheritance/img/diamond-problem.svg)
*Ромбоподібне спадкування без віртуальних баз. Усередині об'єкта Bottom утворюються два незалежні під-об'єкти Base. Доступ до поля counter без явної вказівки гілки Left:: або Right:: викликає помилку компілятора.*

### Анатомія проблеми

У невіртуальному ромбі об'єкт `Bottom` містить **два абсолютно незалежні екземпляри `Base`**:
1. Перший `Base` входить до складу під-об'єкта `Left` (зсув `0`).
2. Другий `Base` входить до складу під-об'єкта `Right` (зсув `sizeof(Left)`).

Це породжує дві проблеми:
- **Семантична неоднозначність (Ambiguity).** Пряме звернення `bottom.counter` не компілюється: компілятор не знає, яке саме з двох незалежних полів `counter` має на увазі розробник. Потрібна громіздка кваліфікація `bottom.Left::counter`.
- **Розсинхронізація стану.** Виклик `stepLeft()` модифікує лівий лічильник, а виклик `stepRight()` — правий. Якщо логіка програми вимагала єдиного спільного стану, об'єкт стає внутрішньо суперечливим.

## Віртуальне базове спадкування: vbtable, vbptr та рантайм-ціна

Щоб гарантувати наявність рівно **одного спільного екземпляра** базового класу в усій ієрархії нащадка, мова C++ надає механізм **віртуального базового спадкування** (англ. *virtual base inheritance*):

```cpp
struct Base {
    int counter;
};

struct Left : virtual public Base {
    int left_data;
};

struct Right : virtual public Base {
    int right_data;
};

struct Bottom : public Left, public Right {
    int bot_data;
};
```

Ключове слово `virtual` докорінно змінює фізичну розкладку об'єкта.

### Дилема невідомого зсуву

У звичайному класі зсув будь-якого базового під-об'єкта є фіксованою константою часу компіляції. Для `Left` під-об'єкт `Base` завжди лежав на зсуві `0`.

Але коли `Base` оголошено як `virtual`, клас `Left` більше **не знає, де лежатиме `Base`**.
- Якщо створюється окремий самостійний екземпляр `Left`, під-об'єкт `Base` може лежати одразу за полями `Left`.
- Якщо ж створюється екземпляр `Bottom`, спільний під-об'єкт `Base` виноситься в самий кінець повного об'єкта (після полів `Left`, `Right` та `Bottom`), щоб обидві гілки могли ділитися ним.

Оскільки зсув між `Left` та `Base` змінюється залежно від того, частиною якого саме підсумкового об'єкта є `Left`, компілятор не може зашити статичну константу в машинний код методів класу `Left`. Зсув має визначатися **динамічно під час виконання**.

![Розкладка пам'яті з віртуальним спадкуванням: під-об'єкти Left і Right містять vbptr, що вказують на таблиці зсувів vbtable, через які знаходиться спільний Virtual Base](/book/programming/languages/inheritance/img/virtual-inheritance-layout.svg)
*Віртуальне спадкування. Спільний під-об'єкт Base розміщується в єдиному екземплярі наприкінці структури. Доступ до нього з методів Left і Right виконується через непряму адресацію за допомогою таблиць зсувів (vbtable або зміщень у vtable).*

### Механізми реалізації: MSVC проти Itanium ABI

Для динамічного пошуку спільної бази різні компілятори застосовують дві моделі ABI:

1. **Модель вказівника на таблицю віртуальних баз (MSVC ABI: `vbptr` / `vbtable`).**
   Компілятор додає в кожен клас, що віртуально успадковує базу, невидиме поле `vbptr` (англ. *virtual base pointer*). Воно вказує на масив 32-бітних цілих чисел — `vbtable` (англ. *virtual base table*). Перше число задає зсув власного `vbptr` від початку поточного під-об'єкта, а друге — зсув до спільного віртуального під-об'єкта `Base`.
   
   Машинний код доступу до `counter` з методу `Left`:
   ```
   mov rax, [rdi]        ; читаємо vbptr
   mov eax, [rax + 4]    ; читаємо з vbtable зсув до віртуальної бази Base (+48 B)
   mov ecx, [rdi + rax]  ; читаємо поле counter за знайденим зсувом
   ```

2. **Модель зміщень у таблиці віртуальних функцій (Itanium C++ ABI: GCC, Clang, Linux, ARM, macOS).**
   Замість окремого `vbptr` компілятор використовує наявний `vptr`. Зсуви до віртуальних базових класів записуються за **від'ємними індексами** відносно точки входу у віртуальну таблицю `vtable` (поруч зі зміщенням `offset-to-top` та інформацією RTTI). Під час конструювання складних ієрархій компілятор генерує додаткові таблиці таблиць — `VTT` (англ. *Virtual Table Table*), щоб правильно ініціалізувати проміжні таблиці предків.

### Механіка VTT та таблиць конструювання

Під час виконання конструктора базового класу віртуальні виклики не повинні переходити в методи ще не сконструйованих нащадків.

Коли створюється об'єкт `Bottom`, спочатку запускається конструктор `Base`, потім `Left`, потім `Right` і нарешті `Bottom`. Поки виконується конструктор `Left`, під-об'єкт `Right` ще не існує в пам'яті!

Щоб забезпечити коректну диспетчеризацію на кожному кроці конструювання, компілятор створює **конструкційні віртуальні таблиці** (англ. *construction vtables*). Вказівники на них передаються в конструктори предків через прихований службовий масив — `VTT` (англ. *Virtual Table Table*). Під час роботи конструктора `Left` поле `vptr` тимчасово налаштовується на конструкційну таблицю `Left-in-Bottom`, і лише у фінальному конструкторі `Bottom` воно отримує остаточну таблицю повністю готового об'єкта.

### Рантайм-ціна віртуального спадкування

Віртуальні бази повністю усувають дублювання даних і проблему неоднозначності, але накладають відчутні апаратні витрати:
- **Розбухання розміру об'єкта (Memory Bloat):** Кожен клас у віртуальній гілці отримує додатковий вказівник (`vbptr` або `vptr`, 8 байтів на 64-бітних архітектурах) плюс вирівнювання.
- **Подвійне розіменування пам'яті:** Будь-яке читання чи запис поля віртуального предка вимагає спершу зчитати таблицю зміщень, виконати індексацію, додати зсув до регістра і лише потім звернутися до даних. Це збиває конвеєр процесора і може спричинити додатковий промах кешу даних L1.
- **Особливість конструювання:** Обов'язок викликати конструктор віртуального базового класу `Base` покладається **виключно на найбільш похідний клас (`Bottom`)**. Конструктори `Left` та `Right` ігнорують виклики конструктора `Base`, коли вони створюються у складі `Bottom`.

## Порядок розв'язання методів у динамічних мовах: C3-лінеаризація

У динамічних мовах (Python, Common Lisp, Dylan, Perl 6/Raku, Scala) множинне спадкування вирішується не через жорстке розміщення під-об'єктів і thunk-функції, а через побудову динамічного лінійного списку виклику методів — **порядку розв'язання методів** (англ. *Method Resolution Order*, MRO).

Якщо клас `C` успадковує `A` і `B`, а вони обидва мають предка `O`, постає питання: в якому порядку викликати методи `super()`?

![Граф спадкування та результат лінеаризації за алгоритмом C3 для ромбоподібної ієрархії](/book/programming/languages/inheritance/img/c3-linearization-graph.svg)
*Побудова лінійного списку розв'язання методів (MRO) за алгоритмом C3. Алгоритм забезпечує властивість монотонності: нащадки завжди йдуть раніше за предків, а порядок батьків у списку оголошення суворо зберігається.*

Наївний пошук у глибину (DFS) ламав спеціалізацію: він піднімався до самого кореня `O` по лівій гілці раніше, ніж заходив у праву гілку `B`, внаслідок чого застарілий метод `O` перекривав свіжий перевизначений метод `B`.

Сучасним стандартом став **алгоритм C3-лінеаризації** (англ. *C3 superclass linearization*). Він гарантує збереження локального порядку оголошення предків та ключову властивість **монотонності**: якщо клас `A` передує `B` для одного нащадка, він ніколи не опиниться після `B` для будь-якого іншого підкласу. Повне математичне виведення, покрокову роботу оператора `merge` та доведення суперечливості конфліктних графів наведено у [математичному аналізі алгоритму C3-лінеаризації](book:programming/inheritance/math-c3-linearization.md).

## Альтернативні моделі розширення: Міксини та Трейти

Через громіздкість множинного спадкування зі станом у дизайні мов виникли альтернативні підходи, які відокремлюють повторне використання коду від побудови жорстких ієрархій типів.

### Міксини (Mixins)

**Міксин** (англ. *mixin*) — це клас, призначений для додавання фіксованого набору методів до інших класів без утворення самостійної сутності в ієрархії. Міксини зазвичай не інстанціюються самі по собі.

У мовах зі статичною типізацією (C++) міксини реалізують через параметризоване спадкування (шаблони):

:::tabs
```cpp
#include <iostream>
#include <string>

// Міксин логування: приймає базовий клас як параметр шаблону
template <typename BaseClass>
class LoggingMixin : public BaseClass {
public:
    template <typename... Args>
    LoggingMixin(Args&&... args) : BaseClass(std::forward<Args>(args)...) {}

    void executeWithLog() {
        std::cout << "[LOG] Початок виконання операції\n";
        this->execute(); // Викликає метод базового класу
        std::cout << "[LOG] Операцію завершено\n";
    }
};

class Task {
public:
    void execute() {
        std::cout << "Виконуються корисні обчислення...\n";
    }
};

// Лінеаризація під час компіляції: LoggingTask є нащадком Task
using LoggingTask = LoggingMixin<Task>;

int main() {
    LoggingTask task;
    task.executeWithLog();
    return 0;
}
```
```c
#include <stdio.h>

/* В C міксини імітують через таблиці функціональних покажчиків та агрегацію */
typedef struct {
    void (*log_start)(void);
    void (*log_end)(void);
} LoggerOps;

static void default_start(void) { printf("[LOG] Початок виконання операції\n"); }
static void default_end(void)   { printf("[LOG] Операцію завершено\n"); }

static const LoggerOps g_default_logger = { default_start, default_end };

typedef struct {
    const LoggerOps* logger;
    int task_id;
} TaskWithLogging;

void task_execute(TaskWithLogging* self) {
    self->logger->log_start();
    printf("Виконуються корисні обчислення для завдання %d...\n", self->task_id);
    self->logger->log_end();
}

int main(void) {
    TaskWithLogging task = { &g_default_logger, 101 };
    task_execute(&task);
    return 0;
}
```
:::

Міксини на базі шаблонів перетворюють дерево спадкування на строго лінійний ланцюжок під час компіляції. Це усуває ромбоподібні конфлікти, зберігає інлайнінг методів і не створює жодних прихованих `vbtable`.

### Статичний поліморфізм: шаблон CRTP

Особливою формою міксину є **ідіома дивно рекурентного шаблону** (англ. *Curiously Recurring Template Pattern*, CRTP). У цій моделі клас-нащадок передає сам себе як параметр шаблону своєму базовому класу:

```cpp
template <typename Derived>
class NumericOperations {
public:
    void increment() {
        // Статичний upcast без віртуальної таблиці та без витрат пам'яті
        static_cast<Derived*>(this)->add(1);
    }
};

class Counter : public NumericOperations<Counter> {
public:
    int value{0};
    void add(int n) { value += n; }
};
```

CRTP забезпечує поліморфне перевизначення поведінки під час компіляції:
- Об'єкт `Counter` не містить `vptr` (0 байтів накладних витрат).
- Виклик `increment()` інлайниться безпосередньо в процесорну інструкцію `add [rdi], 1`.
- Неможливо випадково створити ромбоподібну неоднозначність під час виконання.

### Трейти (Traits)

**Трейт** (англ. *trait* — «характерна риса») — це семантичний будівельний блок, що інкапсулює набір методів, але, на відміну від класичного класу чи міксину, **не містить власного змінного стану (полів даних)**.

Концепція трейтів (введена Натаніелем Шерлі та Стефаном Дюкассом у 2003 році) спирається на три закони:
1. **Трейт надає поведінку, але вимагає реалізації:** трейт може містити готові методи, але оголошує вимоги до абстрактних функцій, які клас-споживач зобов'язаний надати.
2. **Пріоритет класу над трейтом:** якщо клас визначає метод із такою самою назвою, як у трейті, перемагає реалізація класу.
3. **Явне розв'язання конфліктів:** якщо два трейти надають методи з однаковими іменами, компілятор зупиняє збірку з помилкою. Клас зобов'язаний явно вказати, яку версію викликати, або перевизначити метод власноруч.

У сучасних мовах системного програмування, таких як Rust, трейти (`trait`) повністю витіснили класичне спадкування реалізації, гарантуючи нульові накладні витрати на рівні машинних інструкцій.

## Ламкість базового класу (Fragile Base Class) та Принцип Лісков

Головна небезпека надмірного захоплення спадкуванням полягає у знищенні інкапсуляції. У класичному об'єктному проєктуванні спадкування є формою повторного використання за принципом **«білої скриньки»** (англ. *white-box reuse*): похідний клас залежить не лише від відкритого інтерфейсу предка, а й від внутрішніх деталей його реалізації та порядку взаємних викликів методів (*self-calls*).

### Проблема ламкого базового класу

**Проблема ламкого базового класу** (англ. *Fragile Base Class Problem*) виникає тоді, коли цілком коректна модифікація внутрішньої логіки базового класу непомітно ламає поведінку його нащадків.

Класичний сценарій: підрахунок елементів у колекції.

```cpp
// Базовий клас бібліотеки версії 1.0
class CustomArray {
public:
    virtual void add(int item) {
        // Додає елемент у буфер...
    }

    virtual void addAll(const int* items, size_t count) {
        for (size_t i = 0; i < count; ++i) {
            add(items[i]); // Версія 1.0: addAll викликає add для кожного елемента
        }
    }
};

// Користувацький клас, який хоче рахувати кількість доданих елементів
class CountingArray : public CustomArray {
public:
    size_t added_count{0};

    void add(int item) override {
        added_count++;
        CustomArray::add(item);
    }

    void addAll(const int* items, size_t count) override {
        added_count += count;
        CustomArray::addAll(items, count);
    }
};
```

У версії 1.0 виклик `CountingArray::addAll` з масивом із 3 елементів дасть катастрофічний результат:
1. `CountingArray::addAll` збільшує лічильник на `3`.
2. Викликається `CustomArray::addAll`.
3. Базовий `CustomArray::addAll` у циклі викликає віртуальний метод `add()`.
4. Оскільки метод віртуальний, керування повертається в `CountingArray::add()`, який додає до лічильника ще `1` на кожній ітерації.
5. Підсумок: замість 3 елементів лічильник показує 6!

Якщо розробник `CountingArray` прибере власне перевизначення `addAll`, код запрацює. Але через рік автор бібліотеки оновить базовий клас до **версії 2.0**, де заради оптимізації метод `addAll` записуватиме дані напряму в пам'ять через системний виклик `memcpy`, більше не викликаючи `add()`. У ту саму мить клас `CountingArray` знову зламається: тепер лічильник показуватиме 0 замість 3!

### Принцип підстановки Лісков (LSP)

Щоб спадкування не перетворювало архітектуру на мінне поле, воно зобов'язане відповідати **принципу підстановки Лісков** (англ. *Liskov Substitution Principle*, сформульованому Барбарою Лісков у 1987 році):

> Якщо для кожної функції `f`, визначеної для об'єктів типу `T`, поведінка `f` залишається коректною, коли замість екземпляра `T` передається екземпляр типу `S`, то `S` є підтипом `T`.

Формальні вимоги LSP до спадкування:
1. **Контраваріантність передумов:** нащадок не має права вимагати суворіших вхідних умов, ніж базовий клас (передумови не можуть бути посилені).
2. **Коваріантність післямов:** нащадок зобов'язаний гарантувати щонайменше ті самі результати й інваріанти, що й предок (післямови не можуть бути послаблені).
3. **Збереження інваріантів:** усі логічні правила базового типу (наприклад, незмінність розміру чи діапазону значень) мусять залишатися непорушними в нащадку.

Порушенням LSP є хрестоматійний приклад успадкування `Square` (квадрат) від `Rectangle` (прямокутник). З точки зору шкільної геометрії квадрат є прямокутником. Але в коді метод `Rectangle::setWidth(w)` передбачає, що довжина залишається незмінною. Якщо `Square` перевизначить `setWidth` так, що він змінюватиме і висоту, будь-яка функція, яка розраховує на незалежність сторін прямокутника, зазнає збою.

## Пастка таксономічної класифікації

Типовою помилкою раннього об'єктно-орієнтованого дизайну була спроба відобразити світ через глибокі ієрархії спадкування. Наприклад, в ігрових рушіях на початку 2000-х років будували деревоподібні структури:

```
Object -> Entity -> Renderable -> Movable -> Character -> Player
```

Така модель неминуче заходить у глухий кут, щойно з'являються сутності, які перетинають штучні класифікаційні межі:
- Як додати `ParticleEffect` (візуальний ефект часток), який є `Renderable` та `Movable`, але не є сутністю `Entity` зі здоров'ям та інвентарем?
- Як створити нерухому автоматичну турель `Turret`, яка має поведінку персонажа (`Character`), але не вміє рухатися (`Movable`)?
- Як реалізувати безтілесного примари `Ghost`, який рухається, але ігнорує колізії базового класу `PhysicalBody`?

Спроби вирішити ці суперечності множинним спадкуванням призводять до вибуху кількості класів, ромбоподібних залежностей і захаращення базових класів неактуальними полями-заглушками. Саме це спонукало розробників ігрових та високонавантажених систем перейти до компонентно-орієнтованих архітектур (Entity-Component-System, ECS), де сутність — це простий числовий ідентифікатор, а поведінка формується довільним набором незалежних компонентів.

## Композиція проти спадкування

Через ламкість базових класів та складність двійкових розкладок фундаментальне правило об'єктно-орієнтованої архітектури стверджує: **надавайте перевагу композиції об'єктів над спадкуванням класів** (англ. *favor object composition over class inheritance*).

![Спадкування (біла скринька з тісною зв'язаністю) проти Композиції (чорна скринька з чітким інтерфейсним бар'єром)](/book/programming/languages/inheritance/img/composition-vs-inheritance.svg)
*Порівняння двох підходів. Спадкування жорстко зв'язує похідний клас із внутрішньою будовою предка. Композиція будує систему з незалежних чорних скриньок, які спілкуються через стабільні контракти.*

:::tabs
```cpp
#include <iostream>
#include <memory>

// Інтерфейс (контракт)
class OutputDevice {
public:
    virtual ~OutputDevice() = default;
    virtual void write(const std::string& msg) = 0;
};

class ConsoleOutput : public OutputDevice {
public:
    void write(const std::string& msg) override {
        std::cout << "[Консоль]: " << msg << "\n";
    }
};

class FileOutput : public OutputDevice {
public:
    void write(const std::string& msg) override {
        std::cout << "[Файл]: " << msg << "\n";
    }
};

// Замість спадкування від конкретного виводу — володіння через інтерфейс (HAS-A)
class ApplicationLogger {
private:
    std::unique_ptr<OutputDevice> device_;

public:
    explicit ApplicationLogger(std::unique_ptr<OutputDevice> dev) : device_(std::move(dev)) {}

    void setDevice(std::unique_ptr<OutputDevice> dev) {
        device_ = std::move(dev);
    }

    void log(const std::string& text) {
        if (device_) {
            device_->write(text);
        }
    }
};

int main() {
    ApplicationLogger app_logger(std::make_unique<ConsoleOutput>());
    app_logger.log("Старт системи");

    // Заміна стратегії під час виконання без зміни коду логера
    app_logger.setDevice(std::make_unique<FileOutput>());
    app_logger.log("Дані збережено у звіт");
    return 0;
}
```
```c
#include <stdio.h>
#include <stdlib.h>

/* Контракт виводу на C через покажчик на функцію */
typedef struct OutputDevice {
    void (*write)(struct OutputDevice* self, const char* msg);
} OutputDevice;

static void console_write(OutputDevice* self, const char* msg) {
    (void)self;
    printf("[Консоль]: %s\n", msg);
}

static void file_write(OutputDevice* self, const char* msg) {
    (void)self;
    printf("[Файл]: %s\n", msg);
}

/* Композиція (HAS-A) */
typedef struct {
    OutputDevice* device;
} ApplicationLogger;

void logger_log(ApplicationLogger* self, const char* text) {
    if (self->device && self->device->write) {
        self->device->write(self->device, text);
    }
}

int main(void) {
    OutputDevice console_dev = { console_write };
    OutputDevice file_dev = { file_write };

    ApplicationLogger app_logger = { &console_dev };
    logger_log(&app_logger, "Старт системи");

    /* Зміна поведінки без перекомпіляції */
    app_logger.device = &file_dev;
    logger_log(&app_logger, "Дані збережено у звіт");

    return 0;
}
```

### Коли обирати спадкування, а коли композицію

| Критерій | Спадкування (IS-A) | Композиція (HAS-A) |
| :--- | :--- | :--- |
| **Зв'язаність (Coupling)** | Жорстка (*tight*): нащадок залежить від внутрішньої будови предка | Слабка (*loose*): взаємодія лише через публічний інтерфейс |
| **Зміна поведінки** | Фіксується під час компіляції | Можлива динамічно під час виконання |
| **Пам'ять та ABI** | Єдиний блок пам'яті, можливий зсув покажчиків і `vptr` | Окремий покажчик чи вкладене поле |
| **Безпека рефакторингу** | Ризик проблеми ламкого базового класу | Повна ізоляція змін усередині компонента |
| **Тестування** | Важко підмінити поведінку предка | Легко передати дублер (мок/стаб) |

## Практичні інженерні правила

1. **Глибина ієрархії не повинна перевищувати 2–3 рівнів.** Глибокі дерева класів створюють ланцюжки неявних залежностей, де зміна на кореневому рівні породжує каскадні збої на листках.
2. **Множинне спадкування безпечне лише для чистих інтерфейсів.** Якщо базові класи не містять полів даних і не мають конструкторів (інтерфейси в Java/C# або абстрактні класи без полів у C++), воно ніколи не породжує дублювання стану чи потреби у віртуальних таблицях `vbtable`.
3. **Віртуальний деструктор обов'язковий у поліморфних базах.** Якщо об'єкт видаляється через вказівник на базовий клас `Base*`, відсутність `virtual ~Base()` призведе до того, що деструктор нащадка `~Derived()` не буде викликано взагалі, що спричинить витік пам'яті та ресурсів.
4. **Використовуйте спадкування для вираження поведінкового підтипу (LSP), а не для скорочення коду.** Якщо мета полягає лише в тому, щоб повторно використати три готові функції, зробіть відповідний об'єкт полем класу, а не його предком.
