# 📜 Народження чистої віртуальності: від Simula до синтаксису = 0

Ідея розділити опис поведінки та її конкретне виконання народилася разом із самим об'єктно-орієнтованим програмуванням. У 1967 році норвезькі вчені Оле-Йоган Даль (Ole-Johan Dahl) та Крістен Нюгор (Kristen Nygaard) у Норвезькому обчислювальному центрі в Осло створили мову Simula 67. Саме вони ввели концепцію класів, екземплярів і віртуальних процедур (`virtual procedure`). У Simula базовий клас міг оголосити віртуальну процедуру, а похідний клас — замінити її власним блоком коду. Проте в ранній об'єктній моделі була суттєва прогалина: мова не мала механізму, який забороняв би створювати об'єкт базового класу, чия поведінка була неповною або позбавленою фізичного змісту. Якщо програміст забував перевизначити процедуру в нащадку або випадково створював екземпляр абстрактного поняття, помилка виявлялася лише під час виконання або взагалі призводила до мовчазної некоректної поведінки.

Коли наприкінці 1970-х років данський інформатик [Б'ярне Страуструп](book:programming/zero-cost-abstractions/hist-zero-overhead.md) розпочав роботу в лабораторіях Bell Labs над мовою «C з класами» (яка згодом стала C++), його метою було поєднати виразність Simula з безкомпромісною швидкістю та системним контролем мови C. На перших етапах C++ підтримував звичайні віртуальні функції: базовий клас міг надати порожнє тіло `{}` або стандартну заглушку, а похідні класи перевизначали її за потреби.

Проте зі зростанням розміру програмних систем у середині 1980-х років розробники зіткнулися з новою архітектурною проблемою: як виразити чистий інтерфейс — клас, який слугує виключно специфікацією контракту і не повинен мати жодного власного екземпляра в пам'яті?

Порожнє тіло функції на кшталт `virtual void draw() {}` створювало дві небезпечні пастки. По-перше, компілятор дозволяв безперешкодно писати `Shape s;` або `new Shape()`, створюючи фіктивні об'єкти без форми. По-друге, якщо автор похідного класу припускався помилки в сигнатурі методу (наприклад, писав `draw(int)` замість `draw()`), компілятор не видавав жодного попередження: він вважав, що нащадок просто вирішив скористатися базовою порожньою реалізацією. Програма компілювалася, але під час запуску малювала порожнечу.

Розробникам була потрібна мовна конструкція з двома залізними гарантіями на етапі компіляції:
1. Метод не має реалізації в цьому класі й **зобов'язаний** бути реалізованим у кожному конкретному нащадку.
2. Клас, який містить хоча б один такий метод, є принципово неповним, тому створення його прямих екземплярів **суворо заборонено**.

У період між 1987 і 1989 роками, під час підготовки релізу C++ 2.0 та написання фундаментальної праці *The Annotated C++ Reference Manual* (знаної як ARM, 1990 рік, у співавторстві з Маргарет Елліс), Страуструп шукав синтаксис для цього механізму.

Природним і найпершим бажанням було запровадити нове зарезервоване ключове слово. Розглядалися варіанти `pure`, `abstract` або конструкції на зразок `virtual void draw() = abstract;`. Проте в реаліях кінця 1980-х років це натрапило на нездоланну перешкоду — вимогу зворотної сумісності з мовою C.

C++ позиціонувався як мова, здатна без змін компілювати мільйони рядків наявного коду мовою C та підключати стандартні заголовні файли операційних систем (зокрема UNIX). Слова `pure` та `abstract` були надзвичайно популярними ідентифікаторами: розробники використовували їх як назви локальних змінних, аргументів функцій, прапорців у структурах операційної системи та макросів. Оголошення слова `pure` зарезервованим ключовим словом автоматично зламало б величезні кодові бази промислових систем по всьому світу.

Тоді Страуструп звернувся до внутрішнього механізму реалізації віртуальних викликів. У системній реалізації C++ віртуальний метод представляється слотом у таблиці покажчиків на функції — [таблиці віртуальних методів](book:programming/virtual-dispatch-cpp). Якщо функція не визначена, що має стояти в таблиці на її місці? Нульовий покажчик — константа `0`.

Математична та системна інтуїція підказала елегантне рішення: замість нового слова використати вже наявне позначення присвоєння нуля:

```cpp
virtual void draw() = 0;
```

Синтаксис `= 0` не потребував жодного нового ключового слова, не порушував жодного наявного заголовного файлу C і водночас наочно передавав суть: «у цьому класі адреса коду дорівнює нулю». Класи з такими функціями отримали назву **абстрактних класів** (англ. *abstract classes*), а самі методи — **чистих віртуальних функцій** (англ. *pure virtual functions*).

Цей вибір породив чимало суперечок у першому комітеті стандартизації ANSI/ISO C++ (WG21). Критики називали синтаксис `= 0` «дивним хаком» та «криптографічним записом». Проте практичність і бездоганна зворотна сумісність узяли гору: конструкція стала офіційною частиною міжнародного стандарту ISO/IEC 14882:1998 (C++98).

Більше того, через два десятиліття, під час розробки стандарту C++11, комітет стандартизації повернувся до цієї самої семантичної моделі: для керування автоматичною генерацією конструкторів і операторів копіювання було введено синтаксис `= default` та `= delete`. Уся родина директив компілятору виросла з одного практичного компромісу 1989 року.

Мови наступного покоління, такі як Java (1995) та C# (2000), створювалися з чистого аркуша і не були скуті спадщиною препроцесора та синтаксису C. Вони повернулися до первинної ідеї Страуструпа й узаконили явні ключові слова `abstract` для методів і класів та `interface` для чистих специфікацій контрактів. Проте фундаментальна модель — статична заборона інстанціювання та примусове перевизначення слотів таблиці диспетчеризації — залишилася незмінною в усіх об'єктних мовах.
