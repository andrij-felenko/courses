# 📜 Еволюція препроцесора C: від зовнішньої утиліти до стандарту

У перших версіях мови C на машинах PDP-11 не було жодного препроцесора. Компілятор Денніса Рітчі (Dennis Ritchie) 1972 року був компактною програмою, обмеженою 64 кілобайтами пам'яті адресного простору процесора. Будь-яке розширення синтаксису чи додавання складного синтаксичного аналізатора переповнило б пам'ять компілятора. Проте програмістам була життєво необхідна можливість підставляти константи (розміри буферів, адреси регістрів) та включати спільні описи структур даних у різні файли без ручного дублювання коду.

### Перші кроки: макропроцесор Алана Снайдера

У 1974–1975 роках Алан Снайдер (Alan Snyder) із Массачусетського технологічного інституту (MIT) запропонував вирішення проблеми: винести текстову підготовку коду в окрему зовнішню програму-фільтр, яка працює перед компілятором. Снайдер створив прототип препроцесора, що реалізовував базові директиви `#include` та `#define`.

Головна перевага цього підходу полягала в повній незалежності від самого компілятора. Компілятору C не потрібно було знати, звідки взялися числа або як підставився текст: він отримував на вхід уже «розгорнутий» потік символів мови C. Це дозволило зберегти мінімальний розмір ядра компілятора й водночас дало розробникам інструмент конфігурації вихідного коду.

Рітчі швидко оцінив зручність цієї ідеї та інтегрував препроцесор як обов'язкову першу стадію компіляції в Bell Labs. У сьомій редакції Unix (Unix V7, 1979 рік) препроцесор уже був оформлений як окремий виконуваний бінарний файл `cpp` (*C PreProcessor*), який викликався драйвером компілятора `cc` через конвеєр або тимчасові файли.

### Епоха хаосу: препроцесор Райзера та неформальні трюки

Наприкінці 1970-х Джон Райзер (John Reiser) написав високоефективну версію `cpp`, яка стала де-факто стандартом для BSD Unix та компіляторів PCC (*Portable C Compiler*) Стіва Джонсона. Цей препроцесор працював на рівні окремих символів та лексем, проте не мав формальної специфікації. У поведінці різних версій препроцесора виникли серйозні розбіжності.

Найбільше проблем викликали операції склеювання імен і перетворення аргументів на рядки:

1. **Склеювання токенів через коментарі.** До стандартизації оператора `##` програмісти використовували трюк із пустими коментарями:
:::tabs
```c
#define IDENT(a, b) a/**/b
```
```cpp
// До стандартизації C++ використовував той самий C-препроцесорний трюк
#define IDENT(a, b) a/**/b
```
:::
   Препроцесор Райзера видаляв коментар `/**/`, залишаючи ідентифікатори `a` та `b` впритул один до одного, завдяки чому наступний лексичний аналізатор зчитував їх як одне ім'я `ab`. Проте інші препроцесори замінювали будь-який коментар на пробіл, породжуючи `a b`, що призводило до помилок компіляції під час перенесення коду між різними Unix-системами.

2. **Заміна всередині рядкових літералів.** У версії Райзера аргументи макросу підставлялися навіть усередину рядкових констант:
:::tabs
```c
#define WARN(msg) printf("msg: %d\n", msg)
```
```cpp
#include <iostream>
// У ранніх версіях C++ підстановка всередину рядків ламала вивід
#define WARN(msg) std::cout << "msg: " << (msg) << "\n"
```
:::
   Виклик `WARN(count)` перетворювався на друк тексту `count: %d`. Якщо ж у рядку випадково зустрічалося слово, що збігалося з ім'ям параметра, воно непередбачувано замінювалося, ламаючи текст повідомлень.

Кожна реалізація компілятора трактувала рекурсивні виклики, правила пересканування та директиви умовного збирання на власний розсуд, що суттєво гальмувало портування коду між машинами DEC VAX, PDP-11, IBM System/370 та Motorola 68000.

### Стандартизація ANSI C (1989): народження сучасного препроцесора

Коли комітет ANSI X3J11 у 1983–1989 роках розпочав роботу над стандартизацією мови C (результатом якої став стандарт ANSI X3.159-1989, відомий як C89 або C90), препроцесор став однією з найгарячіших тем для дискусій.

Комітет ухвалив фундаментальне рішення: **препроцесор оперує не сирими символами, а токенами препроцесора (*preprocessing tokens*)**. Було чітко розмежовано фази трансляції (визначено 8 фаз) і введено суворі формальні правила:

- **Оператор стрінгіфікації `#`** замінив небезпечну підстановку параметрів усередину рядків. Тепер перетворення параметра макросу на рядковий літерал стало явним і контрольованим.
- **Оператор конкатенації токенів `##`** назавжди усунув хакерський трюк `a/**/b`. Було формалізовано вимогу: результат склеювання двох токенів зобов'язаний бути коректним лексичним токеном препроцесора.
- **Заборона рекурсії (правило "blue paint").** Було встановлено алгоритм розгортання: якщо під час розгортання макросу `FOO` у згенерованому тексті знову зустрічається ім'я `FOO`, воно «маркується синім» (*painted blue*) і більше не розгортається. Це запобігло нескінченним циклам компілятора при розгортанні самопосилань.
- **Argument Prescan.** Було зафіксовано точний порядок: аргументи функціонального макросу повністю розгортаються *до* підстановки в тіло макросу, за винятком випадків, коли вони стоять поруч з операторами `#` або `##`.

### Розширення C99: макроси зі змінною кількістю аргументів

З розвитком складних бібліотек логування та обробки помилок стандарту бракувало можливості створювати макроси з довільною кількістю параметрів (на зразок функції `printf`).

У стандарті ISO/IEC 9899:1999 (C99) було стандартизовано **варіативні макроси**:
- Спеціальний ідентифікатор трикрапки `...` у списку формальних параметрів;
- Вбудований ідентифікатор `__VA_ARGS__`, що підставляє всі передані варіативні аргументи через кому.

Проте виникла крайова проблема порожнього списку аргументів:
:::tabs
```c
#define LOG(fmt, ...) printf(fmt, __VA_ARGS__)
/* Виклик LOG("Hello\n") розгортався у: printf("Hello\n", ); -> синтаксична помилка */
```
```cpp
#include <iostream>
#define LOG(fmt, ...) std::printf(fmt, __VA_ARGS__)
// Виклик LOG("Hello\n") давав ту саму синтаксичну помилку висячої коми
```
:::

Компілятори GCC та Clang вирішили це власним розширенням `, ##__VA_ARGS__` (де оператор `##` перед комою видаляв попередню кому, якщо список варіативних аргументів був порожнім). Проте це розширення не було частиною стандарту ISO C.

### Сучасна доба: `__VA_OPT__`, C++20 та C23

Лише у стандарті C++20 (а згодом і в C23) проблему зайвої коми було розв'язано на рівні стандарту за допомогою функціонального макрооператора `__VA_OPT__(...)`. Якщо варіативні аргументи передано, `__VA_OPT__(...)` розгортається у свій вміст; якщо ж список порожній — вираз зникає повністю:

:::tabs
```c
#define LOG(fmt, ...) printf(fmt __VA_OPT__(,) __VA_ARGS__)
```
```cpp
#include <iostream>
#define LOG(fmt, ...) std::printf(fmt __VA_OPT__(,) __VA_ARGS__)
```
:::

Паралельно з розвитком препроцесора мови C++ та C вели постійну роботу з витіснення препроцесора там, де його текстова природа шкодила надійності:
- Впровадження `const` та `inline` функцій у C89 та C++98;
- Поява шаблонів (templates) для безпечного узагальненого програмування;
- Розвиток механізму `constexpr` у C++11, C++14 та C++20, що переніс обчислення констант на рівень синтаксичного дерева компілятора;
- Поява модулів (C++20 Modules), покликаних замінити механічне текстове включення `#include` на семантичний імпорт скомпільованого інтерфейсу.

Попри появу потужних засобів метапрограмування в сучасних мовах, класичний текстовий препроцесор залишається фундаментом збирання системного програмного забезпечення на C і C++, забезпечуючи низькорівневу конфігурацію, роботу з платформовими прагмами та сумісність із мільярдами рядків інфраструктурного коду.
