# 📋 Специфікація двійкового кадрування gRPC поверх HTTP/2

Протокол gRPC інкапсулює виклики віддалених процедур у транспортний протокол HTTP/2, транслюючи стан виконання процедури через заголовки, потік двійкових кадрів фіксованого формату та кінцеві метадані (трейлери). Ця специфікація визначає структуру кадру `Length-Prefixed-Message`, обов'язкові псевдозаголовки HTTP/2, формат метаданих, таблицю статус-кодів, розширену модель помилок, діаграму переходів станів потоку та правила відображення помилок транспортного рівня.

### 1. Формат повідомлення з префіксом довжини (Length-Prefixed-Message)

Кожне корисне навантаження запиту або відповіді gRPC розбивається на одне або кілька двійкових повідомлень, що мають обов'язковий 5-байтовий заголовок перед серіалізованими даними:

```
 +------------------+------------------------------+-------------------------------+
 | Compressed (1 B) | Message-Length (4 B, Big-End)| Data (Message-Length bytes)   |
 +------------------+------------------------------+-------------------------------+
```

Поля заголовка повідомлення:
- **`Compressed-Flag` (1 байт):**
  - `0x00` — дані не стиснуті (сирий двійковий потік, наприклад, Protocol Buffers);
  - `0x01` — корисне навантаження стиснене алгоритмом, узгодженим у заголовку `grpc-encoding` (наприклад, `gzip`, `snappy` або `zstd`).
- **`Message-Length` (4 байти, беззнакове 32-бітне ціле в мережевому порядку big-endian):** точна довжина поля `Data` в байтах. Максимальний теоретичний розмір одного повідомлення — `2^32 - 1` байтів (4 ГБ), однак типове обмеження реалізацій за замовчуванням становить 4 МБ (налаштовується параметром каналу `grpc.max_receive_message_length`).
- **`Data` (змінна довжина):** серіалізовані байти повідомлення.

Одне повідомлення з 5-байтовим префіксом може бути розбите транспортом HTTP/2 на кілька дрібних кадрів `DATA` (розміром до `SETTINGS_MAX_FRAME_SIZE`, зазвичай 16 КБ). Так само один HTTP/2 кадр `DATA` може містити кілька послідовних gRPC-повідомлень під час потокового передавання.

### 2. Встановлення з'єднання та узгодження параметрів HTTP/2

Перед виконанням першого RPC-виклику клієнт і сервер встановлюють транспортний канал.

1. **Клієнтський префікс з'єднання (Client Connection Preface):** клієнт відправляє 24-байтову магічну послідовність:
   ```
   PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n
   ```
2. **Обмін кадрами `SETTINGS`:** сторони узгоджують ліміти:
   - `SETTINGS_HEADER_TABLE_SIZE` — розмір динамічної таблиці декодера HPACK (типово 4096 байтів);
   - `SETTINGS_ENABLE_PUSH = 0` — механізм Server Push у gRPC заборонений і завжди вимикається;
   - `SETTINGS_MAX_CONCURRENT_STREAMS` — максимальна кількість одночасно відкритих паралельних RPC-потоків у цьому з'єднанні (рекомендовано не менше 100);
   - `SETTINGS_INITIAL_WINDOW_SIZE` — початковий розмір вікна керування потоком для нових стрімів (типово 65535 байтів або 1 МБ);
   - `SETTINGS_MAX_FRAME_SIZE` — максимальний розмір одного HTTP/2 кадру `DATA` (від 16384 до 16777215 байтів).

### 3. Структура HTTP/2 заголовків запиту (Request Headers)

Клієнт ініціює виклик, відкриваючи новий непарний потік HTTP/2 (Stream ID: 1, 3, 5, ...) та надсилаючи кадр `HEADERS`.

| Заголовок HTTP/2 | Обов'язковість | Формат та опис |
| :--- | :--- | :--- |
| `:method` | Обов'язковий | Завжди значення `POST` |
| `:scheme` | Обов'язковий | `http` (незахищене з'єднання) або `https` (TLS) |
| `:path` | Обов'язковий | `/{package}.{ServiceName}/{MethodName}` (чутливий до регістру) |
| `:authority` | Обов'язковий | Доменне ім'я або IP-адреса та порт цільового хоста |
| `content-type` | Обов'язковий | `application/grpc` або `application/grpc+{custom}` (`application/grpc+proto`) |
| `te` | Обов'язковий | Завжди значення `trailers` (сигналізує проміжним проксі про наявність трейлерів) |
| `grpc-timeout` | Опціональний | Бюджет часу на виконання виклику: `{число}{одиниця}` |
| `grpc-encoding` | Опціональний | Алгоритм компресії тіла: `identity`, `gzip`, `deflate`, `snappy`, `zstd` |
| `grpc-accept-encoding`| Опціональний | Перелік підтримуваних клієнтом алгоритмів компресії через кому |

#### Одиниці вимірювання дедлайну (`grpc-timeout`):
- `H` — години (Hours)
- `M` — хвилини (Minutes)
- `S` — секунди (Seconds)
- `m` — мілісекунди (Milliseconds)
- `u` — мікросекунди (Microseconds)
- `n` — наносекунди (Nanoseconds)

*Приклад:* `grpc-timeout: 500m` означає жорсткий ліміт виконання у 500 мілісекунд. Якщо сервер не вкладається в цей час, виклик автоматично завершується зі статусом `DEADLINE_EXCEEDED`.

#### Двійкові метадані (Custom Binary Metadata):
Користувацькі метадані передаються як звичайні HTTP/2 заголовки. Якщо ім'я заголовка закінчується на суфікс `-bin` (наприклад, `trace-token-bin`), його значення трактується бібліотекою як сирі байти і кодується за стандартом Base64 без вирівнювання символами `=`.

### 4. Структура відповіді та трейлерів (Response & Trailers)

Повна відповідь gRPC зазвичай складається з трьох послідовних фаз у межах одного HTTP/2 потоку:

1. **Початкові заголовки відповіді (Initial Headers):** кадр `HEADERS` від сервера:
   - `:status: 200` (HTTP-код на рівні транспорту завжди 200, якщо з'єднання дійсне);
   - `content-type: application/grpc`;
   - `grpc-encoding` (якщо тіло відповіді стиснене).
2. **Тіло відповіді (Response Payload):** один або кілька кадрів `DATA`, що несуть `Length-Prefixed-Message`.
3. **Кінцеві метадані (Trailers):** фінальний кадр `HEADERS` із встановленим прапорцем `END_STREAM`:
   - `grpc-status`: числовий код завершення RPC (від 0 до 16);
   - `grpc-message`: текстовий опис помилки (якщо `grpc-status != 0`), закодований у форматі Percent-Encoding (RFC 3986);
   - `grpc-status-details-bin`: додаткове двійкове повідомлення `google.rpc.Status` (формат Protobuf Any), що містить багату типізовану модель помилки.

#### Однофазна відповідь (Trailers-Only):
Якщо виклик завершився помилкою ще до початку генерації тіла (наприклад, метод не знайдено, або запит відхилено авторизаційним фільтром), сервер повертає єдиний кадр `HEADERS` із прапорцем `END_STREAM`, який одночасно містить `:status`, `content-type`, `grpc-status` та `grpc-message` без проміжних кадрів `DATA`.

### 5. Повний перелік статус-кодів gRPC

| Код | Назва статусу | Опис та семантика відмови | Типові причини виникнення |
| :---: | :--- | :--- | :--- |
| **0** | `OK` | Успішне завершення операції | Запит виконано без помилок |
| **1** | `CANCELLED` | Операцію скасовано ініціатором | Клієнт розірвав з'єднання або контекст скасовано |
| **2** | `UNKNOWN` | Невідома або некласифікована помилка | Неперехоплений виняток у серверному коді |
| **3** | `INVALID_ARGUMENT` | Некоректні аргументи клієнта | Порушено валідацію полів, недійсний формат |
| **4** | `DEADLINE_EXCEEDED` | Вичерпано ліміт часу (`grpc-timeout`) | Сервер не встиг відповісти до спливу дедлайну |
| **5** | `NOT_FOUND` | Запитуваний ресурс не знайдено | Відсутній запис у БД або відсутній файл |
| **6** | `ALREADY_EXISTS` | Спроба створити існуючий ресурс | Конфлікт унікального ключа або ідентифікатора |
| **7** | `PERMISSION_DENIED` | Недостатньо прав для виконання дії | Користувач автентифікований, але не має доступу |
| **8** | `RESOURCE_EXHAUSTED` | Вичерпано квоту або ліміт запитів | Перевищено Rate-Limit або брак пам'яті/диска |
| **9** | `FAILED_PRECONDITION` | Стан системи не дозволяє виконання | Порушено бізнес-правило (наприклад, баланс < 0) |
| **10**| `ABORTED` | Операцію перервано через конфлікт | Конфлікт транзакцій, виявлено стан перегонів |
| **11**| `OUT_OF_RANGE` | Значення виходить за допустимі межі | Зміщення пагінації більше за розмір масиву |
| **12**| `UNIMPLEMENTED` | Метод або сервіс не реалізовано | Запитаний шлях `:path` відсутній на сервері |
| **13**| `INTERNAL` | Критичний внутрішній збій системи | Пошкодження інваріантів, збій підсистем |
| **14**| `UNAVAILABLE` | Сервіс тимчасово недоступний | Сервер перезавантажується, відмова мережі (retryable) |
| **15**| `DATA_LOSS` | Непоправна втрата або пошкодження даних| Пошкоджено диск або невідновлювану репліку |
| **16**| `UNAUTHENTICATED` | Відсутні дійсні облікові дані | Невалідний, прострочений або відсутній токен |

### 6. Розширена модель помилок (`google.rpc.Status`)

Для передачі детальних відомостей про помилку (перелік некоректних полів форми, час затримки перед повторною спробою, квоти) використовується серіалізована структура `google.rpc.Status`, яка пакується в заголовок `grpc-status-details-bin`:

```protobuf
message Status {
    int32 code = 1;
    string message = 2;
    repeated google.protobuf.Any details = 3;
}
```

Стандартні типи повідомлень у списку `details`:
- `google.rpc.RetryInfo` — вказує клієнту точний інтервал `retry_delay`, через який дозволено повторити запит;
- `google.rpc.BadRequest` — містить список порушень `FieldViolation` (ім'я поля та опис помилки валідації);
- `google.rpc.QuotaFailure` — деталізує вичерпану квоту (назва суб'єкта, ліміт);
- `google.rpc.ErrorInfo` — стабільна машиночитабельна причина помилки (`reason`), домен (`domain`) та метадані для логів.

### 7. Діаграма переходів станів потоку HTTP/2 під час RPC-виклику

Кожен RPC-виклик ізольовано проходить скінченний автомат станів стріму HTTP/2 (RFC 7540):

```
       +---------------------------------------------+
       |                    IDLE                     |
       +---------------------------------------------+
                              |  Клієнт надсилає HEADERS
                              v
       +---------------------------------------------+
       |                    OPEN                     |
       +---------------------------------------------+
          | (Клієнт надсилає DATA з END_STREAM)
          v
       +---------------------------------------------+
       |              HALF-CLOSED (LOCAL)            |
       +---------------------------------------------+
          | (Сервер повертає HEADERS + DATA + TRAILERS)
          v
       +---------------------------------------------+
       |                   CLOSED                    |
       +---------------------------------------------+
```

1. **`IDLE`:** Потік ще не створено.
2. **`OPEN`:** Клієнт надіслав `HEADERS` і може відправляти кадри `DATA`. Сервер може надсилати попередні заголовки та свої кадри `DATA`.
3. **`HALF-CLOSED (LOCAL)`:** Клієнт завершив надсилання тіла запиту (прапорець `END_STREAM` у кадрі `DATA`). Клієнт більше не може писати у потік, але продовжує читати відповіді від сервера.
4. **`CLOSED`:** Сервер надіслав фінальний кадр `HEADERS` із трейлерами та прапорцем `END_STREAM`. Потік повністю звільняє свій `Stream-ID` у таблиці активних з'єднань.

### 8. Відображення помилок протоколу HTTP/2 на статус-коди gRPC

Якщо помилка сталася на транспортному рівні HTTP/2 (через кадр скидання потоку `RST_STREAM` або помилку з'єднання `GOAWAY`), gRPC відображає код помилки HTTP/2 на стандартний статус RPC:

| Код помилки HTTP/2 | Значення HTTP/2 | Результуючий статус gRPC | Семантика для клієнта |
| :--- | :---: | :--- | :--- |
| `NO_ERROR` | `0x0` | `INTERNAL` (якщо потік закрився невчасно) | Несподіване завершення стріму |
| `PROTOCOL_ERROR` | `0x1` | `INTERNAL` | Порушення специфікації HTTP/2 |
| `INTERNAL_ERROR` | `0x2` | `INTERNAL` | Збій реалізації HTTP/2 стека |
| `FLOW_CONTROL_ERROR`| `0x3` | `INTERNAL` | Порушення вікна керування потоком |
| `STREAM_CLOSED` | `0x5` | `INTERNAL` | Запис у вже закритий потік |
| `FRAME_SIZE_ERROR` | `0x6` | `INTERNAL` | Розмір кадру перевищив ліміт |
| `REFUSED_STREAM` | `0x7` | `UNAVAILABLE` | Сервер відхилив потік до обробки (безпечно повторити) |
| `CANCEL` | `0x8` | `CANCELLED` | Потік явно скасовано ініціатором |
| `ENHANCE_YOUR_CALM` | `0xb` | `RESOURCE_EXHAUSTED` | Сервер перевантажений або виявлено спам |

Така сувора таблиця трансляції гарантує, що клієнтські бібліотеки отримують уніфіковані статус-коди навіть у випадках, коли відмова сталася на рівні проміжних балансувальників або мережевих сокетів.
