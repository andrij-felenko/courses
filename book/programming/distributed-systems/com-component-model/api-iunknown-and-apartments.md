# 📋 Довідник системних інтерфейсів та API COM

Цей довідник містить вичерпний опис сигнатур, структур бінарного інтерфейсу застосунків (ABI), системних викликів ініціалізації середовища, конфігураційних ключів реєстру та кодів помилок `HRESULT`. Усі елементи специфікації описано з точки зору їхньої бінарної поведінки в пам'яті, вимог до синхронізації та правил передачі прав власності на ресурси.

## 1. Фундаментальний інтерфейс IUnknown

`IUnknown` є базисом усієї об'єктної моделі Windows. Будь-який COM-інтерфейс у системі зобов'язаний успадковувати його методи. Перші три елементи віртуальної таблиці будь-якого інтерфейсного вказівника завжди вказують на реалізації цих трьох функцій.

### Бінарна декларація методів (C / C++)

```cpp
struct IUnknown {
    virtual HRESULT STDMETHODCALLTYPE QueryInterface(
        /* [in] */  REFIID riid,
        /* [out] */ void **ppvObject
    ) = 0;

    virtual ULONG STDMETHODCALLTYPE AddRef(void) = 0;

    virtual ULONG STDMETHODCALLTYPE Release(void) = 0;
};
```

### Специфікація поведінки та правила виклику

- **`QueryInterface`**:
  Слугує для динамічного виявлення можливостей об'єкта під час виконання програми без використання механізмів RTTI мови C++. Клієнт передає константне посилання на 128-бітний ідентифікатор `riid` та адресу вихідного покажчика `ppvObject`.
  
  Якщо запитаний інтерфейс підтримується об'єктом, реалізація зобов'язана:
  1. Записати валідну адресу віртуальної таблиці відповідного інтерфейсу у комірку `*ppvObject`;
  2. Атомарно збільшити лічильник посилань через виклик `AddRef()`;
  3. Повернути код успіху `S_OK`.
  
  Якщо об'єкт не підтримує запитаний інтерфейс, реалізація зобов'язана записати `NULL` у `*ppvObject` та повернути статус `E_NOINTERFACE`. Запис `NULL` є критично важливим для запобігання використанню висячих покажчиків клієнтським кодом у разі помилки.

- **`AddRef`**:
  Збільшує внутрішній лічильник активних посилань на об'єкт. Метод зобов'язаний бути потокобезпечним в усіх апартаментах, окрім однопотокових компонентів, що виконуються виключно в головному STA. У багатопотокових середовищах збільшення реалізується через системну інструкцію `InterlockedIncrement` (або `std::atomic`). Значення, яке повертає метод, є інформаційним і призначене виключно для діагностики під час налагодження.

- **`Release`**:
  Зменшує лічильник посилань екземпляра через `InterlockedDecrement`. Якщо після декременту лічильник досягає нульового значення, об'єкт повинен негайно звільнити всі виділені ресурси, викликати деструктори внутрішніх полів та повернути зайняту пам'ять у системну купу через відповідний алокатор.

| Метод | Параметри | Повертає | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `QueryInterface` | `riid`: 128-бітний ідентифікатор інтерфейсу.<br>`ppvObject`: адреса вихідного вказівника. | `S_OK`<br>`E_NOINTERFACE`<br>`E_POINTER` | Запитує інтерфейс за ідентифікатором `riid`. У разі успіху викликає `AddRef()` для знайденого інтерфейсу та записує адресу в `*ppvObject`. |
| `AddRef` | Немає. | `ULONG` (поточне значення лічильника) | Атомарно збільшує лічильник посилань екземпляра. Значення повернення використовується лише для діагностики та логування. |
| `Release` | Немає. | `ULONG` (поточне значення лічильника) | Атомарно зменшує лічильник посилань. Коли значення сягає 0, об'єкт самознищується та звільняє пам'ять. |

## 2. Інтерфейс активації IClassFactory

`IClassFactory` абстрагує процес виділення пам'яті та створення нових екземплярів об'єктів. Завдяки фабриці клієнт не залежить від конкретного механізму розміщення об'єкта в пам'яті (чи то статична пам'ять, чи то локальна купа DLL, чи то пул об'єктів COM+).

```cpp
struct IClassFactory : public IUnknown {
    virtual HRESULT STDMETHODCALLTYPE CreateInstance(
        /* [in]  */ IUnknown *pUnkOuter,
        /* [in]  */ REFIID   riid,
        /* [out] */ void     **ppvObject
    ) = 0;

    virtual HRESULT STDMETHODCALLTYPE LockServer(
        /* [in] */ BOOL fLock
    ) = 0;
};
```

- **`CreateInstance`**:
  Створює неініціалізований екземпляр класу, запитує в нього стартовий інтерфейс `riid` та повертає його клієнту. Параметр `pUnkOuter` використовується для підтримки агрегації — патерну повторного використання коду в COM, де зовнішній об'єкт делегує виклики внутрішньому компоненту. Якщо компонент не підтримує агрегацію, а клієнт передав ненульовий `pUnkOuter`, фабрика зобов'язана негайно повернути статус `CLASS_E_NOAGGREGATION`.

- **`LockServer`**:
  Змінює системний лічильник блокування динамічної бібліотеки DLL. Якщо клієнт планує створювати велику кількість об'єктів послідовно, він викликає `LockServer(TRUE)`, щоб утримати модуль сервера в оперативній пам'яті та уникнути витрат на повторні операції вивантаження й завантаження бібліотеки з диска.

| Метод | Параметри | Коди помилок | Опис та інваріанти |
| :--- | :--- | :--- | :--- |
| `CreateInstance` | `pUnkOuter`: контролюючий `IUnknown` під час агрегації (або `NULL`).<br>`riid`: ідентифікатор бажаного інтерфейсу.<br>`ppvObject`: вихідний вказівник. | `S_OK`<br>`CLASS_E_NOAGGREGATION`<br>`E_NOINTERFACE`<br>`E_OUTOFMEMORY` | Виділяє пам'ять об'єкта, ініціалізує стан і повертає початковий інтерфейс. Якщо агрегація не підтримується, а `pUnkOuter != NULL`, зобов'язаний повернути `CLASS_E_NOAGGREGATION`. |
| `LockServer` | `fLock`: `TRUE` (заблокувати) або `FALSE` (розблокувати). | `S_OK`<br>`E_FAIL` | Збільшує або зменшує лічильник блокування сервера. Поки лічильник `> 0`, DLL не може бути вивантажена з пам'яті через `DllCanUnloadNow`. |

## 3. Системні функції ініціалізації та активації

### Ініціалізація апартаменту потоку

Функція `CoInitializeEx` повинна бути викликана хоча б один раз у кожному потоці процесу перед виконанням будь-яких викликів COM API. Вона прив'язує потік до конкретного типу апартаменту та ініціалізує внутрішні структури OLE32.

```cpp
HRESULT CoInitializeEx(
    LPVOID pvReserved, /* Завжди NULL */
    DWORD  dwCoInit    /* Прапорці моделі апартаменту */
);

void CoUninitialize(void);
```

Кожен успішний виклик `CoInitializeEx` повинен мати парний виклик `CoUninitialize` перед завершенням роботи потоку. Порушення цього правила призводить до блокування системних дескрипторів та витоку ресурсів середовища виконання.

#### Прапорці `dwCoInit` (конкурентний контекст потоку)

| Прапорець | Значення | Тип апартаменту | Особливості виконання |
| :--- | :--- | :--- | :--- |
| `COINIT_APARTMENTTHREADED` | `0x2` | STA (Single-Threaded) | Потік має власний цикл `GetMessage`/`DispatchMessage`. Вхідні виклики серіалізуються через віконні повідомлення. |
| `COINIT_MULTITHREADED` | `0x0` | MTA (Multi-Threaded) | Потік входить у спільний багатопотоковий апартамент процесу. Виклики заходять паралельно без синхронізації. |
| `COINIT_DISABLE_OLE1DDE` | `0x4` | Модифікатор | Вимикає застарілу підсистему OLE 1.0 DDE для усунення зайвих накладних витрат. |

---

### Створення екземпляра компонента

Функція `CoCreateInstance` є зручною високорівневою обгорткою над механізмом фабрик. Вона знаходить CLSID у реєстрі, завантажує виконуваний модуль через Service Control Manager (SCM), запитує фабрику `IClassFactory`, викликає `CreateInstance` та відпускає фабрику, повертаючи клієнту готовий інтерфейсний вказівник.

```cpp
HRESULT CoCreateInstance(
    REFCLSID  rclsid,     /* CLSID класу компонента */
    LPUNKNOWN pUnkOuter,  /* Контролюючий IUnknown для агрегації */
    DWORD     dwClsContext,/* Контекст розташування виконуваного модуля */
    REFIID    riid,       /* IID запитуваного інтерфейсу */
    LPVOID    *ppv        /* Адреса вихідного вказівника */
);
```

#### Прапорці контексту виконання `CLSCTX`

Параметр `dwClsContext` визначає допустиме фізичне розташування сервера відносно викликаючого коду:

| Константа | Значення | Тип сервера | Спосіб завантаження |
| :--- | :--- | :--- | :--- |
| `CLSCTX_INPROC_SERVER` | `0x1` | DLL (In-Process) | Завантажується безпосередньо в адресний простір клієнта (`LoadLibrary`). |
| `CLSCTX_INPROC_HANDLER`| `0x2` | DLL-обробник | Спеціальний внутрішньопроцесний фільтр перед віддаленим сервером. |
| `CLSCTX_LOCAL_SERVER`  | `0x4` | EXE (Local Server) | Запускається як окремий процес на тій самій машині. Зв'язок через ALPC / IPC. |
| `CLSCTX_REMOTE_SERVER` | `0x10` | DCOM Server | Виконується на віддаленому мережевому вузлі. Зв'язок через MS-RPCE. |
| `CLSCTX_ALL`           | `0x17` | Будь-який | Обирає найшвидший доступний варіант: Inproc -> Local -> Remote. |

## 4. Моделі потоків у реєстрі Windows (ThreadingModel)

Під час реєстрації внутрішньопроцесного сервера DLL у системному реєстрі створюється розділ за адресою:
`HKEY_CLASSES_ROOT\CLSID\{CLSID}\InprocServer32`. Рядкове значення `ThreadingModel` інформує менеджер COM, у якому апартаменті дозволено виконувати код компонента.

Якщо потік клієнта намагається створити об'єкт із несумісною моделлю `ThreadingModel` (наприклад, потік STA створює об'єкт із моделлю `Free`), COM автоматично створить об'єкт у фоновому потоці MTA та поверне клієнту проксі-обгортку. Усі подальші виклики методів будуть маршалитись через чергу, що додає затримку перемикання контексту ядра.

| Значення `ThreadingModel` | Апартамент створення | Поведінка викликів | Вимоги до синхронізації |
| :--- | :--- | :--- | :--- |
| *(відсутнє)* | Головний STA (Main STA) | Завжди створюється в першому STA процесу. Виклики з інших потоків маршаляться через чергу повідомлень. | Синхронізація не потрібна (виконується в одному потоці). |
| `"Apartment"` | Будь-який STA | Створюється в поточному STA потоку, який викликав `CoCreateInstance`. | Синхронізація екземпляра не потрібна; глобальні змінні DLL вимагають м'ютексів. |
| `"Free"` | MTA процесу | Завжди створюється в MTA. Виклики з STA маршаляться через проксі. | **Повна потокобезпека:** об'єкт мусить захищати всі змінні критичними секціями або атоміками. |
| `"Both"` | Апартамент викликача | Створюється безпосередньо в апартаменті клієнта (STA або MTA) без проксі. | **Повна потокобезпека:** може викликатися паралельно, якщо клієнт працює в MTA. |
| `"Neutral"` | Нейтральний (TNA) | Виконується в потоці викликача, але поза межами STA/MTA. Блокування серіалізуються контекстом. | Синхронізація керується інфраструктурою COM+. |

## 5. Міжапартаментний маршалінг та Global Interface Table (GIT)

Пряма передача сирого інтерфейсного покажчика між потоками, що належать до різних апартаментів, суворо заборонена. Прямий виклик методу на об'єкті STA з чужого потоку призводить до стану гонитви, пошкодження внутрішнього стану або помилки `RPC_E_WRONG_THREAD`.

Щоб передати інтерфейс в інший потік, його необхідно серіалізувати (змаршалити) в бінарний потік або зареєструвати у глобальній системній таблиці:

### 1. Потоковий маршалінг через IStream

Потік-відправник викликає `CoMarshalInterThreadInterfaceInStream`, який створює бінарний дескриптор об'єкта в пам'яті (IStream). Потік-отримувач читає потік функцією `CoGetInterfaceAndReleaseStream`, яка повертає валідний проксі, прив'язаний до поточного апартаменту отримувача, та автоматично звільняє потік.

```cpp
/* У потоці-відправнику: */
HRESULT CoMarshalInterThreadInterfaceInStream(
    REFIID    riid,     /* IID інтерфейсу */
    IUnknown *pUnk,     /* Вказівник на об'єкт */
    LPSTREAM *ppStm     /* Вихідний потік маршалінгу */
);

/* У потоці-отримувачі: */
HRESULT CoGetInterfaceAndReleaseStream(
    LPSTREAM  pStm,     /* Потік, створений відправником */
    REFIID    riid,     /* IID інтерфейсу */
    LPVOID   *ppv       /* Вихідний проксі-вказівник */
);
```

### 2. Таблиця глобальних інтерфейсів IGlobalInterfaceTable (GIT)

GIT є системним внутрішньопроцесним сервісом, доступним за ідентифікатором `CLSID_StdGlobalInterfaceTable`. Вона дозволяє зареєструвати інтерфейс один раз і безпечно отримувати проксі в довільній кількості робочих потоків за числовим 32-бітним маркером (Cookie), усуваючи необхідність створення індивідуальних потоків IStream для кожного клієнта.

```cpp
struct IGlobalInterfaceTable : public IUnknown {
    virtual HRESULT STDMETHODCALLTYPE RegisterInterfaceInGlobal(
        /* [in]  */ IUnknown *pUnk,
        /* [in]  */ REFIID   riid,
        /* [out] */ DWORD    *pdwCookie
    ) = 0;

    virtual HRESULT STDMETHODCALLTYPE RevokeInterfaceFromGlobal(
        /* [in] */ DWORD dwCookie
    ) = 0;

    virtual HRESULT STDMETHODCALLTYPE GetInterfaceFromGlobal(
        /* [in]  */ DWORD  dwCookie,
        /* [in]  */ REFIID riid,
        /* [out] */ void   **ppv
    ) = 0;
};
```

## 6. Бінарна структура статусів HRESULT

Кожен метод інтерфейсу COM зобов'язаний повертати 32-бітне ціле число зі знаком `HRESULT`. Воно інформує викликача про результат операції та причину відмови.

```
 31 30 29 28 27              16 15                             0
+--+--+--+--+------------------+--------------------------------+
|S |R |C |N |    Facility      |             Code               |
+--+--+--+--+------------------+--------------------------------+
```

### Бітові поля структури HRESULT

- **Bit 31 (S - Severity):** Визначає успішність операції. `0` — успішне виконання (Success), `1` — помилка (Error). Стандартні макроси Windows SDK:
  - `SUCCEEDED(hr)`: повертає `TRUE`, якщо біт `S` дорівнює `0` (`hr >= 0`).
  - `FAILED(hr)`: повертає `TRUE`, якщо біт `S` дорівнює `1` (`hr < 0`).
- **Bit 30 (R - Reserved):** Зарезервовано для системного використання; завжди дорівнює `0`.
- **Bit 29 (C - Customer):** Прапорець простору кодів. `0` — стандартний код помилки Microsoft, `1` — власний код, визначений розробником додатку.
- **Bit 28 (N - NTSTATUS):** Ознака того, що код трансльовано з нативного NTSTATUS ядра Windows.
- **Bits 26–16 (Facility):** Джерело виникнення помилки:
  - `FACILITY_WIN32` (`7`): системні помилки Win32 API.
  - `FACILITY_RPC` (`1`): збої віддаленого виклику процедур та мережевого зв'язку DCOM.
  - `FACILITY_ITF` (`4`): специфічні помилки конкретного інтерфейсу.
  - `FACILITY_DISPATCH` (`2`): помилки підсистеми OLE Automation (`IDispatch`).
- **Bits 15–0 (Code):** Числовий код помилки або додатковий статус успіху.

### Таблиця канонічних кодів HRESULT

| Шістнадцятковий код | Символьне ім'я | Значення та інженерна причина виникнення |
| :--- | :--- | :--- |
| `0x00000000` | `S_OK` | Операція успішно завершена. |
| `0x00000001` | `S_FALSE` | Операція завершена успішно, але повернула логічне "хибно" або частковий результат. |
| `0x80004002` | `E_NOINTERFACE` | Запитаний інтерфейс не підтримується об'єктом. |
| `0x80004003` | `E_POINTER` | Передано недійсний або нульовий вказівник пам'яті (`NULL`). |
| `0x80004005` | `E_FAIL` | Неспецифікована внутрішня помилка виконання. |
| `0x8007000E` | `E_OUTOFMEMORY` | Не вдалося виділити необхідний обсяг оперативної пам'яті. |
| `0x8000FFFF` | `E_UNEXPECTED` | Катастрофічний збій інваріантів системи або внутрішня аномалія. |
| `0x80040110` | `CLASS_E_NOAGGREGATION` | Клас не підтримує агрегацію через зовнішній `pUnkOuter`. |
| `0x80040111` | `CLASS_E_CLASSNOTAVAILABLE`| Фабрика класів для зазначеного CLSID не знайдена в DLL або сервері. |
| `0x800401F0` | `CO_E_NOTINITIALIZED` | Виклик API COM виконано без попередньої ініціалізації через `CoInitializeEx`. |
| `0x8001010E` | `RPC_E_WRONG_THREAD` | Виклик методу на об'єкті STA виконано з чужого потоку без маршалінгу. |
