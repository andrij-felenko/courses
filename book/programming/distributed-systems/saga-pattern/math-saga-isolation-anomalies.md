# 🧮 Формальна модель Саги: аномалії відсутності ізоляції, семантичні інваріанти та властивості напівґраток

Розподілена Сага розв'язує задачу збереження узгодженості даних без глобальних блокувань. Проте відмова від централізованого менеджера транзакцій руйнує класичні гарантії моделі ACID. Сага гарантує атомарність (через компенсації), узгодженість (у фіналі) та довговічність локальних записів, але повністю позбавлена **ізоляції** (властивості ACD замість ACID).

Щоб будувати надійні бізнес-процеси, інженер повинен володіти формальним апаратом поведінки Саги, точно класифікувати аномалії паралельного виконання та знати математичні умови, за яких система гарантовано сходиться до коректного стану.

## Формальний простір станів та історія виконання

Нехай `S` — розподілена система, стан якої визначається вектором локальних станів окремих сервісів:

```
S = (s[1], s[2], ..., s[m])
```

Сага `G` визначається як впорядкована послідовність із `n` прямих локальних транзакцій `T[1], T[2], ..., T[n]` та множини із `n - 1` компенсаційних транзакцій `C[1], C[2], ..., C[n-1]`:

```
G = ( {T[1], T[2], ..., T[n]}, {C[1], C[2], ..., C[n-1]} )
```

Кожна пряма транзакція `T[i]` є чистим трансформатором стану певної підсистеми:

```
s'[k] = T[i](s[k])
```

Повний успішний ланцюг виконання позначається як пряма послідовність:

```
H_succ = (T[1], T[2], ..., T[n])
```

Фінальний стан системи після успішної саги:

```
S_final = (T[n] ∘ ... ∘ T[2] ∘ T[1])(S_0)
```

Якщо на кроці `k` (де `1 ≤ k ≤ n`) пряма транзакція `T[k]` зазнає невідновного збою, сага переривається. Простір виконання породжує компенсовану історію `H_fail(k)`:

```
H_fail(k) = (T[1], T[2], ..., T[k-1], T[k]^abort, C[k-1], C[k-2], ..., C[1])
```

![Формальний простір станів саги: прямий ланцюг транзакцій та компенсаційний відкат при збої](/book/programming/distributed-systems/saga-pattern/img/saga-forward-backward-flow.svg)
*Формальна траєкторія станів: прямі переходи T[i] змінюють простір станів; при збої T3 компенсації C2 та C1 повертають систему до узгодженого стану.*

### Семантична компенсація проти фізичного відкату

Ключова математична відмінність компенсації від класичного відкату транзакції (`ROLLBACK` за журналом WAL) полягає в тому, що компенсація не повертає систему до тотожного початкового фізичного стану `S_0`:

```
(C[1] ∘ T[1])(S_0) ≠ S_0
```

Компенсація `C[i]` є **семантичним еквівалентом скасування**. Вона переводить систему в новий стан `S_comp`, який задовольняє бізнес-інваріанти еквівалентності порожньої дії:

```
State(S_comp) ≡ State(S_0) + Δ_audit    [де Δ_audit — незмінний запис в аудиторському журналі]
```

Наприклад, якщо `T[1]` списала 500 гривень, то `C[1]` зараховує 500 гривень назад новою транзакцією. Первинний баланс відновлено, але номери чеків та записи в історії транзакцій безповоротно змінилися.

## Анатомія аномалій неізольованого виконання (ACD)

Оскільки локальні транзакції фіксують зміни (`COMMIT`) негайно, проміжні стани саги відкриті для читання та модифікації сторонніми конкурентними процесами. Нехай паралельно виконуються дві саги `G^A` та `G^B`.

### 1. Брудне читання (Dirty Read / Reading Uncommitted State)

Аномалія виникає, коли Сага `G^B` зчитує стан, змінений підтранзакцією `T[i]^A`, проте Сага `G^A` згодом зазнає аварії та компенсує цей крок через `C[i]^A`.

Послідовність подій у часі:

```
крок 1:  T[1]^A  ->  balance = balance - 1000   [успішний коміт, баланс став 0]
крок 2:  T[1]^B  ->  read(balance) == 0         [Сага B бачить 0 і відхиляє кредит]
крок 3:  T[2]^A  ->  error / abort              [збій у сазі A]
крок 4:  C[1]^A  ->  balance = balance + 1000   [баланс відновлено до 1000]
```

Результат: Сага `G^B` ухвалила фатальне бізнес-рішення на основі «брудного» значення, якого насправді ніколи не мало існувати як кінцевого результату.

### 2. Втрачене оновлення (Lost Update / Overwriting Uncommitted State)

Аномалія виникає, коли дві незалежні саги модифікують один і той самий об'єкт без взаємного блокування, після чого перша сага виконує компенсацію й перезаписує результат другої саги.

Послідовність подій у часі:

```
крок 1:  T[1]^A  ->  stock = stock - 5   [початковий склад: 10, залишилося 5]
крок 2:  T[1]^B  ->  stock = stock - 2   [склад: 5, залишилося 3]
крок 3:  T[2]^A  ->  error / abort       [збій у сазі A]
крок 4:  C[1]^A  ->  stock = 10          [наївна компенсація: повернення вихідного значення!]
```

Результат: списання 2 одиниць товару Сагою `G^B` повністю знищено наївною компенсацією Саги `G^A`. На складі опинилося 10 одиниць товару замість коректних 8.

```
Справжній залишок:
stock_real = 10 - 5 - 2 + 5
           = 8                           [коректний розрахунок]

Результат наївної компенсації:
stock_corrupted = 10                     [втрачене оновлення саги B]
```

### 3. Неповторюване (розмите) читання (Fuzzy / Non-repeatable Read)

Сага `G^A` зчитує значення ресурсу на кроці `T[1]^A`, після чого Сага `G^B` вносить і фіксує зміну `T[1]^B`. Коли Сага `G^A` повторно зчитує той самий ресурс на кроці `T[3]^A`, значення виявляється іншим, що руйнує внутрішню логіку перевірок.

## Семантичні контрзаходи та їхні математичні умови

Щоб усунути аномалії відсутності ізоляції, теорія розподілених саг висуває п'ять інженерних стратегій, кожна з яких спирається на строгі математичні передумови.

![Аномалії неізольованого виконання та засоби їх нейтралізації](/book/programming/distributed-systems/saga-pattern/img/saga-isolation-anomalies.svg)
*Порівняння небезпечного брудного читання та безпечної моделі із семантичним замком і станом очікування.*

### 1. Семантичний замок (Semantic Lock) та інваріант фазового стану

Замість прямої мутації фінального значення ресурс переводиться у стан тимчасового блокування (*pending / tentative state*):

```
s.status = PENDING_RESERVATION
s.locked_amount = amount
```

Будь-яка паралельна операція `T^B`, яка потребує доступу до ресурсу `s`, зобов'язана перевіряти статусний інваріант:

```
is_available(s, req) = (s.status == FREE) ∧ (s.total_amount - s.locked_amount ≥ req)
```

Якщо умова не виконується, операція `T^B` або блокується у черзі, або відхиляється без порушення узгодженості. Компенсація `C[i]^A` у такому разі лише знімає позначку блокування:

```
s.locked_amount = s.locked_amount - amount
s.status = (s.locked_amount == 0) ? FREE : PENDING_RESERVATION
```

### 2. Комутативність операцій (Commutative Updates)

Операції `T[i]` та `T[j]` називаються комутативними, якщо порядок їхнього застосування не впливає на підсумковий стан системи:

```
(T[i] ∘ T[j])(S) = (T[j] ∘ T[i])(S)
```

Якщо всі прямі та компенсаційні транзакції проєктуються як відносні дельти (додавання й віднімання чисел замість абсолютного присвоєння), проблема втраченого оновлення зникає:

```
C[1]^A(stock) = stock + 5                [відносна дельта замість stock = 10]
```

Перевіримо коректність для попереднього сценарію втраченого оновлення:

```
S_0 = 10
S_1 = T[1]^A(10)  = 10 - 5 = 5
S_2 = T[1]^B(5)   = 5 - 2 = 3
S_3 = C[1]^A(3)   = 3 + 5 = 8            [результат точний і узгоджений]
```

### 3. Структура напівґратки для прямого відновлення (Forward-only Recovery)

Якщо операції володіють властивостями ідемпотентності, комутативності та асоціативності, простір станів саги утворює **верхню напівґратку** (англ. *join-semilattice*) `(L, ⊔)`.

Оператор об'єднання станів `⊔` задовольняє аксіоми:

```
x ⊔ x = x            [ідемпотентність: повтори повідомлень не змінюють стан]
x ⊔ y = y ⊔ x        [комутативність: порядок приходу пакетів не має значення]
(x ⊔ y) ⊔ z = x ⊔ (y ⊔ z)  [асоціативність: довільне групування подій]
```

У напівґратці будь-яка послідовність дій лише монотонно наближає систему до найменшої верхньої межі (*Least Upper Bound*). Це дозволяє проєктувати саги з **виключно прямим відновленням (forward recovery)**: замість складного відкату та компенсацій система повторює неуспішні кроки до гарантованого успіху.

## Матриця класифікації кроків саги

Теоретично повна сага ділиться на три функціональні зони відносно так званої **поворотної точки** (*Pivot Transaction*):

```
G = ( {T[1], ..., T[p-1]},  T[p],  {T[p+1], ..., T[n]} )
      └──────┬──────────┘   └─┬─┘  └─────────┬────────┘
        Компенсовні        Pivot         Повторювані
```

1. **Компенсовні кроки (`1 ≤ i < p`):** транзакції, які мають обов'язкові парні компенсації `C[i]`. Вони можуть завершитися бізнес-відмовою (наприклад, недостатньо грошей).
2. **Поворотний крок (`i = p`):** точка неповернення. Якщо `T[p]` завершилася успішно, сага **гарантовано не буде компенсуватися**. Якщо `T[p]` впала — запускається повний ланцюг компенсацій `C[p-1], ..., C[1]`.
3. **Повторювані кроки (`p < i ≤ n`):** транзакції, які йдуть після поворотної точки. Вони проєктуються так, що не можуть отримати логічної відмови в предметній області. При технічних збоях (таймаут, падіння вузла) вони повторюються за експоненційним розкладом до обов'язкового успіху.

Ця формальна структура мінімізує кількість необхідних компенсацій у системі: для кроків після pivot писати компенсаційну логіку непотрібно.
