# 📋 Специфікація Reactive Streams та протокольні контракти протитиску

Цей довідник містить формальні специфікації інтерфейсів, правила взаємодії компонентів, двійкові структури кадрів та протокольні контракти для реалізації надійного кредитного протитиску в прикладних і мережевих конвеєрах.

У розподілених асинхронних системах відсутність суворого протокольного контракту між компонентами неминуче призводить до розриву зворотного зв'язку, накопичення гігабайтів невідпрацьованих об'єктів у купі та взаємних блокувань. Наведені нижче специфікації визначають точні механічні гарантії передачі попиту (англ. *demand*) від споживача до виробника на рівнях рантайму мов, транспортних протоколів та брокерів повідомлень.

## Інтерфейси специфікації Reactive Streams (JVM / Поліглотний стандарт)

Специфікація Reactive Streams (версія 1.0.4) стандартизує асинхронну неблокуючу обробку потоків із зворотним протитиском на рівні рантайму JVM та мовних екосистем.

```
                  ┌──────────────────────────────┐
                  │         Publisher<T>         │
                  └──────────────┬───────────────┘
                                 │ subscribe(Subscriber<T>)
                                 ▼
                  ┌──────────────────────────────┐
                  │        Subscriber<T>         │
                  └──────────────┬───────────────┘
                                 │ onSubscribe(Subscription)
                                 ▼
                  ┌──────────────────────────────┐
                  │         Subscription         │
                  └──────────────┬───────────────┘
                                 │ request(long n) / cancel()
                                 ▼
 ┌───────────────────────────────────────────────────────────────┐
 │ Сигнали даних: onNext(T) → onNext(T) → onComplete() / onError()│
 └───────────────────────────────────────────────────────────────┘
```

### 1. `Publisher<T>`

Виробник потенційно необмеженої послідовності елементів, що публікує їх відповідно до отриманого від підписника попиту.

```java
public interface Publisher<T> {
    void subscribe(Subscriber<? super T> subscriber);
}
```

| Метод | Опис поведінки | Винятки та крайові випадки |
| :--- | :--- | :--- |
| `subscribe(Subscriber<? super T> s)` | Реєструє споживача в системі. Виробник зобов'язаний викликати `s.onSubscribe(Subscription)` до виклику будь-яких інших сигналів. | Якщо передано `null`, зобов'язаний викинути `NullPointerException`. Якщо підписка відхилена — викликати `s.onSubscribe()`, після чого негайно `s.onError()`. |

### 2. `Subscriber<T>`

Одержувач повідомлень і сигналів зміни стану підписки.

```java
public interface Subscriber<T> {
    void onSubscribe(Subscription s);
    void onNext(T t);
    void onError(Throwable t);
    void onComplete();
}
```

| Метод | Призначення | Обмеження виконання |
| :--- | :--- | :--- |
| `onSubscribe(Subscription s)` | Отримання маркера керування підпискою. | Викликається рівно один раз для кожної підписки. Не повинен викликати блокуючих операцій. |
| `onNext(T t)` | Доставка чергового елемента даних від виробника. | Викликається не більше разів, ніж сумарно запитано через `Subscription.request(n)`. Якщо `t == null`, генерує `NullPointerException`. |
| `onError(Throwable t)` | Термінальний сигнал про аварійне завершення потоку. | Після виклику жодні інші методи не викликаються. Переводить підписку в недійсний стан. |
| `onComplete()` | Термінальний сигнал про успішне вичерпання потоку. | Викликається тільки після доставки всіх запитаних елементів. Жодні наступні сигнали неприпустимі. |

### 3. `Subscription`

Маркер життєвого циклу підписки, через який підписник регулює потік даних та ініціює завершення.

```java
public interface Subscription {
    void request(long n);
    void cancel();
}
```

| Метод | Семантика | Правила валідації |
| :--- | :--- | :--- |
| `request(long n)` | Додає `n` одиниць попиту до активного кредиту підписника. | `n > 0`. Якщо `n <= 0`, підписка зобов'язана надіслати `onError(IllegalArgumentException)`. Сума запитів обмежується `Long.MAX_VALUE` (що інтерпретується як нескінченний попит / push). |
| `cancel()` | Асинхронне скасування підписки. Виробник зобов'язаний припинити надсилання елементів. | Метод ідемпотентний. Операція є неблокуючою і потокобезпечною. |

### 4. `Processor<T, R>`

Проміжний трансформаційний вузол, який одночасно виступає і як `Subscriber`, і як `Publisher`.

```java
public interface Processor<T, R> extends Subscriber<T>, Publisher<R> {}
```

## Формальні правила протоколу Reactive Streams (Нормативні вимоги)

1. **Правило збереження попиту (Demand Invariant §1.1):** Загальна кількість викликів `Subscriber.onNext(t)` ніколи не може перевищувати поточний сумарний лічильник `n`, накопичений через виклики `Subscription.request(n)`.
2. **Правило послідовного виклику (Signal Ordering §1.3):** Для будь-якого екземпляра `Subscriber` виклики `onSubscribe`, `onNext`, `onError` та `onComplete` повинні виконуватися строго послідовно (thread-safe, без паралельного виконання сигналів у різних потоках).
3. **Неблокуючий контракт (Non-blocking Execution §1.9):** Жоден із методів (`subscribe`, `onSubscribe`, `onNext`, `request`, `cancel`) не має права блокувати викликаючий потік (заборонено виклики `sleep`, `wait`, блокуючий ввід-вивід або утримання довгих моніторів).
4. **Запобігання переповненню лічильника (Overflow Protection §3.17):** Виробник зобов'язаний коректно обробляти додавання попиту так, щоб сума `current_demand + n` при переході через `Long.MAX_VALUE` не переповнювалася в негативні значення, а залишалася рівною `Long.MAX_VALUE`.
5. **Ідемпотентність скасування (§3.5):** Виклик `Subscription.cancel()` повинен бути ідемпотентним, потокобезпечним і негайно припиняти генерацію нових викликів `onNext`.

## Мережевий рівень: Кадр `WINDOW_UPDATE` протоколу HTTP/2 (RFC 7540)

На рівні двійкового транспорту HTTP/2 протитиск реалізується передачею кадрів оновлення кредитного вікна як для окремого логічного потоку (Stream Flow Control), так і для з'єднання загалом (Connection Flow Control).

```
+---------------------------------------------------------------+
|                        Length (24 bits)                       |
+---------------+---------------+-------------------------------+
|   Type (8)    |   Flags (8)   | R |     Stream ID (31 bits)   |
|     0x08      |     0x00      | 0 |                           |
+---------------+---------------+-------------------------------+
| R |                Window Size Increment (31 bits)            |
| 0 |                      (1 to 2^31 - 1)                      |
+---+-----------------------------------------------------------+
```

### Поля структури кадру HTTP/2 `WINDOW_UPDATE`:

* **Length (24 біти):** Завжди дорівнює `0x000004` (4 байти корисного навантаження).
* **Type (8 бітів):** Фіксоване значення `0x08` (ідентифікатор кадру `WINDOW_UPDATE`).
* **Flags (8 бітів):** Прапорці відсутні (встановлено `0x00`).
* **Stream ID (31 біт):** Ідентифікатор потоку.
  * Якщо `Stream ID == 0x00000000` — оновлення вікна стосується **всього TCP-з'єднання**.
  * Якщо `Stream ID > 0` — оновлення вікна застосовується **виключно до вказаного потоку**.
* **Window Size Increment (31 біт):** Беззнакове ціле число від `1` до `2^31 - 1` (`2 147 483 647`), що вказує кількість байтів, яку відправник може додатково надіслати. Значення `0` є грубою помилкою протоколу (`PROTOCOL_ERROR`).

## Протокол RSocket: Кредитний кадр `REQUEST_N`

Протокол RSocket реалізує семантику Reactive Streams безпосередньо поверх транспортів TCP, WebSocket та Aeron за допомогою двійкових кадрів керування потоком.

```
+---------------------------------------------------------------+
|                       Frame Length (24 bits)                  |
+---------------------------------------------------------------+
|                       Stream ID (32 bits)                     |
+---------------+---------------+-------------------------------+
|Frame Type (6) |   Flags (10)  |        (Flags continued)      |
|    0x08       |               |                               |
+---------------+---------------+-------------------------------+
|                        Request N (32 bits)                    |
|                          (1 to 2^31 - 1)                      |
+---------------------------------------------------------------+
```

### Бітові характеристики кадру RSocket `REQUEST_N`:

* **Stream ID (32 біти):** Номер активного потоку взаємодії (`Request-Stream` або `Channel`).
* **Frame Type (6 бітів):** Значення `0x08` ідентифікує кадр як запит кредиту.
* **Flags (10 бітів):**
  * `0x200` (Ignore): Ігнорувати кадр, якщо версія протоколу одержувача не підтримує цей тип.
* **Request N (32 біти):** Кількість повідомлень (логічних об'єктів), які одержувач дозволяє передати виробнику. Задає квоту в дискретних повідомленнях, а не в байтах.

## Протокол AMQP 1.0: Кредитний кадр `FLOW`

У стандарті AMQP 1.0 (ISO/IEC 19464) передача повідомлень між вузлами брокера керується спеціальним перформативом `flow`:

```
+---------------------------------------------------------------+
| AMQP Frame Header (8 bytes)                                   |
+---------------------------------------------------------------+
| Performative: FLOW (Type code 0x13)                           |
| • next-incoming-id: uint (очікуваний номер вхідного трансферу)│
| • incoming-window:  uint (розмір вхідного вікна сесії)        |
| • next-outgoing-id: uint (номер наступного вихідного трансферу│
| • outgoing-window:  uint (розмір вихідного вікна сесії)       |
| • handle:           uint (ідентифікатор конкретного лінка)    |
| • delivery-count:   uint (поточний лічильник доставок лінка)  |
| • link-credit:      uint (доступний кредит лінка для відправки│
+---------------------------------------------------------------+
```

### Правило кредитування в AMQP 1.0:
Відправник має право надіслати повідомлення по лінку тоді і тільки тоді, коли виконується умова:
`delivery-count + link-credit > current-delivery-sequence`.
Коли `link-credit == 0`, лінк повністю блокується до отримання нового кадру `flow` від споживача.

## Програмний інтерфейс gRPC Manual Flow Control (C++ та Java)

У високопродуктивних gRPC-сервісах автоматичне керування потоком вимикається для усунення буферизації пам'яті в користувацькому просторі.

### Таблиця методів керування потоком у gRPC C++ API:

```cpp
#include <grpcpp/grpcpp.h>

namespace grpc {

template <class RequestType, class ResponseType>
class ServerReaderWriter {
public:
    // Вимикає автоматичне читання для переходу на кредитну модель
    // Запит на читання одного повідомлення з транспортного буфера ядра
    void Read(RequestType* msg, void* tag);

    // Запис повідомлення в буфер відправки
    void Write(const ResponseType& msg, void* tag);

    // Перевірка готовності мережевого буфера до прийому нових даних
    // true: буфер вільний (Low Watermark); false: буфер заповнений (High Watermark)
    // Доступно через Reactor API (grpc::ServerWriteReactor)
};

}
```

| Інтерфейс / Метод | Призначення | Стан зворотного зв'язку |
| :--- | :--- | :--- |
| `ServerWriteReactor::OnWriteDone(bool ok)` | Подія завершення скидання попереднього повідомлення в мережевий сокет. | Дозволяє надіслати наступний `Write()`. Запобігає накопиченню повідомлень у внутрішній черзі gRPC. |
| `ServerReadReactor::StartRead(RequestType* resp)` | Явний запит на вичитування рівно одного вхідного повідомлення. | Поки `StartRead()` не викликано, сокет HTTP/2 утримує `WINDOW_UPDATE`, призупиняючи відправника. |
| `ClientContext::set_initial_metadata()` | Передача параметрів початкового кредитного вікна під час встановлення RPC-виклику. | `x-flow-control-initial-credit: 128` |

## Протокол Aeron: Кредитний потік для наднизьких затримок (Ultra-Low Latency)

У високочастотних торгових системах та розподілених фінансових ядрах (LMAX Disruptor, Aeron Messaging від Мартіна Томпсона) замість TCP використовується транспорт UDP із власним високоефективним протоколом керування потоком.

Aeron реалізує кредитний механізм на рівні кадрів `Status Message` (SM):

```
+---------------------------------------------------------------+
| Aeron Header (32 bytes): Frame Length, Version, Flags, Type   |
+---------------------------------------------------------------+
| Type: 0x02 (Status Message / Flow Control)                    |
| • Session ID:     int32 (унікальний ідентифікатор сесії)      |
| • Stream ID:      int32 (номер логічного каналу)              |
| • Consumption Term ID:     int32 (номер поточного буфера)     |
| • Consumption Term Offset: int32 (позиція вичитаного байта)   |
| • Receiver Window Length:  int32 (доступне вікно прийому в B) |
+---------------------------------------------------------------+
```

### Механізм роботи зворотного зв'язку Aeron:
* Джерело (Publisher) записує повідомлення безпосередньо в циклічний буфер пам'яті (Memory-Mapped Ring Buffer);
* Одержувач (Subscriber) оновлює свою позицію вичитування `Consumption Term Offset` і транслює кадр SM через регулярні часові інтервали;
* Ліміт відправника розраховується як `Limit = Consumption Term Offset + Receiver Window Length`. Відправник відстежує цей ліміт атомарною операцією пам'яті без системних викликів ядра;
* Якщо ліміт вичерпано, відправник негайно зупиняється на рівні користувацького простору, що гарантує детерміновану затримку в субмікросекундному діапазоні.

## Семантика життєвого циклу: Гарячі (Hot) проти Холодних (Cold) джерел

Поведінка підсистеми протитиску кардинально різниться залежно від природи джерела даних:

1. **Холодні джерела (Cold Publishers):** потік створюється індивідуально для кожного нового підписника (читання файлу з диска, SQL-запит до реляційної бази даних, генерація послідовності чисел). У цьому режимі кредитний протитиск працює ідеально: якщо споживач не викликає `request(n)`, джерело просто не виконує читання з диска чи мережі.
2. **Гарячі джерела (Hot Publishers):** потік існує незалежно від наявності підписників і генерує події в реальному часі (біржовий тікер, датчик температури, мережевий трафік інтерфейсу). Якщо підписник сповільнюється, гаряче джерело не може призупинити фізичну реальність. У цьому разі на рівні `Processor` підключається обов'язковий буфер із вибраною стратегією скидання (`DROP_OLDEST`, `LATEST` або тимчасове дискове кешування).

## Порівняльна таблиця транспортних протоколів керування потоком

| Характеристика | TCP Flow Control | HTTP/2 / HTTP/3 | Reactive Streams (JVM) | AMQP 1.0 (Link Credit) | Aeron (Status Message) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Одиниця обліку** | Байти (`rcv_wnd`) | Байти (`WINDOW_UPDATE`) | Дискретні об'єкти (`n`) | Повідомлення (`link-credit`) | Зсув у байтах (`Term Offset`) |
| **Гранулярність** | Все TCP-з'єднання | З'єднання + окремий Stream | Екземпляр підписки | Сесія + окремий Link | Стрім усередині сесії |
| **Сигнал зупинки** | `Window = 0` (ZeroWindow) | Вичерпання Stream Window | Вичерпання попиту `n == 0` | `link-credit == 0` | Перетин `Receiver Window` |
| **Захист від HoL Blocking** | Відсутній | Повний на рівні потоків | Повний між підписками | Повний між лінками | Повний між стрімами |
| **Рівень реалізації** | Ядро ОС (Kernel Space) | Протокольний парсер | Користувацький рантайм | Брокер повідомлень | Shared Memory / Lockless ring |
