# 🧮 Математичний апарат XFetch: імовірнісне завчасне оновлення та динаміка навантаження

Навала на кеш є прямим наслідком часового розриву між миттю вичерпання терміну дії даних і миттю завершення розрахунку нового значення. Щоб усунути цей розрив без надлишкових блокувань, застосовують імовірнісне моделювання вхідного потоку запитів.

## Ймовірнісна модель наївного кешування

Розглянемо потік запитів до кешованого ключа як стаціонарний Пуассонівський процес із параметром інтенсивності `λ` (кількість вхідних звернень за одиницю часу).

Нехай:
- `T` — номінальний термін життя запису в кеші (TTL);
- `t_write` — фізичний момент часу, коли поточну версію запису було збережено в кеш;
- `t_expiry = t_write + T` — абсолютний момент часу вичерпання терміну дії ключа;
- `δ` (дельта) — тривалість виконання важкого обчислення або SQL-запиту до основного сховища для отримання свіжого значення;
- `t` — поточний момент часу надходження чергового клієнтського запиту.

У класичній моделі Cache-Aside обчислення нового значення ініціюється в момент першого промаху, тобто коли `t ≥ t_expiry`. 

Якщо перший потік зафіксував промах у момент `t₀ ≥ t_expiry`, він починає операцію обчислення, яка триватиме до моменту `t₀ + δ`. Упродовж цього інтервалу часу довжиною `δ` кеш залишається порожнім або недійсним.

Оскільки надходження запитів підпорядковується розподілу Пуассона, випадкова величина кількості запитів `N`, що надійдуть у часове вікно вразливості `[t₀, t₀ + δ]`, має математичне сподівання:

```
E[N] = λ · δ
```

Якщо `λ = 5000` запитів на секунду, а тривалість звернення до бази даних `δ = 0.25` секунди (250 мілісекунд), то математичне сподівання кількості одночасних важких запитів, спрямованих до джерела даних:

```
E[N] = 5000 · 0.25 = 1250 запитів
```

Замість одного контрольованого читання реляційна база даних отримує 1250 паралельних запитів на вибірку одного й того самого ресурсу, що призводить до насичення пулу з'єднань і різкого зростання затримки.

## Розподіл інтервалів надходження запитів

У пуассонівському потоці проміжки часу між послідовними запитами `Δtᵢ = tᵢ₊₁ − tᵢ` є незалежними однаково розподіленими випадковими величинами з експоненційним розподілом `Δt ~ Exp(λ)`:

```
P(Δt ≤ x) = 1 − exp(-λ · x)
```

Математичне сподівання інтервалу між сусідніми зверненнями дорівнює:

```
E[Δt] = 1 / λ
```

Для інтенсивного потоку з `λ = 5000` зап/с середній інтервал між запитами становить `1 / 5000 = 0.0002` секунди (0.2 мілісекунди). Це означає, що запити надходять практично неперервно.

## Виведення умови алгоритму XFetch

Мета алгоритму XFetch полягає в тому, щоб виконати повторне обчислення значення **до** настання моменту `t_expiry`, залучивши для цього одного з випадкових реальних читачів, які звертаються до системи в зоні наближення до закінчення терміну дії.

Алгоритм формулює умову завчасного оновлення:

```
t − δ · β · ln(U) > t_expiry
```

де:
- `t` — поточний час надходження запиту;
- `δ` — виміряний час виконання попереднього обчислення цього значення;
- `β > 0` — коефіцієнт агресивності оновлення (за замовчуванням `β = 1.0`);
- `U` — випадкова величина, рівномірно розподілена на неперервному інтервалі `(0, 1]`;
- `ln(U)` — натуральний логарифм величини `U`.

### Властивості випадкової складової

Оскільки `U ∈ (0, 1]`, значення `ln(U)` завжди є недодатним: `ln(U) ≤ 0`. 

Отже, величина `-ln(U)` є строго невід'ємною: `-ln(U) ≥ 0`.

Згідно з фундаментальною теоремою про зворотне перетворення розподілів, якщо `U ~ Uniform(0, 1)`, то випадкова величина `Y = -ln(U)` підпорядковується стандартному показниковому (експоненційному) розподілу з параметром масштабу `1`:

```
P(Y ≤ y) = P(-ln(U) ≤ y)
= P(ln(U) ≥ -y)         [множення на -1 змінює знак нерівності]
= P(U ≥ e⁻ʸ)            [експоненціювання обох частин]
= 1 − e⁻ʸ               [властивість рівномірного розподілу на (0, 1)]
```

Таким чином, доданок `X = -δ · β · ln(U)` являє собою випадковий додатний часовий зсув, розподілений за експоненційним законом із математичним сподіванням:

```
E[X] = δ · β
```

### Ймовірність раннього спрацьовування в момент t

Перетворимо умову спрацьовування XFetch відносно випадкової величини `U`:

```
t − δ · β · ln(U) > t_expiry
-δ · β · ln(U) > t_expiry − t     [віднімання t від обох частин]
-ln(U) > (t_expiry − t) / (δ · β)  [ділення на додатну величину δ · β]
ln(U) < -(t_expiry − t) / (δ · β)  [множення на -1]
U < exp( -(t_expiry − t) / (δ · β) ) [експоненціювання]
```

Оскільки `U` розподілена рівномірно на відрізку `[0, 1]`, ймовірність події `U < p` для `p ∈ [0, 1]` дорівнює точно значенню `p`.

Отже, ймовірність того, що окремий запит у момент часу `t` ініціює фоновий перерахунок кешу `P_recompute(t)`, визначається аналітичною формулою:

```
P_recompute(t) = exp( -(t_expiry − t) / (β · δ) )    для t ≤ t_expiry
P_recompute(t) = 1.0                                 для t > t_expiry
```

## Динаміка ймовірності та саморегуляція системи

Проаналізуємо поведінку функції `P_recompute(t)` у різні періоди життя кешованого запису:

```
1. Далеко від закінчення терміну (t = t_expiry − 10 · β · δ):
   P(t) = exp(-10) ≈ 0.000045 (ймовірність практично нульова, кеш стабільний).

2. Початок зони ризику (t = t_expiry − 3 · β · δ):
   P(t) = exp(-3) ≈ 0.0498 (ймовірність близько 5%).

3. Безпосереднє наближення (t = t_expiry − β · δ):
   P(t) = exp(-1) ≈ 0.3679 (ймовірність близько 36.8%).

4. Момент фізичного вичерпання TTL (t = t_expiry):
   P(t) = exp(0) = 1.0 (ймовірність 100%, гарантоване спрацьовування).
```

### Гарантія оновлення при високому потоці запитів

Нехай у проміжок часу `[t_expiry − β · δ, t_expiry]` надходить потік запитів з інтенсивністю `λ`. Загальна кількість звернень за цей інтервал становить `K = λ · β · δ`.

Ймовірність того, що **жоден** із `K` запитів не запустить оновлення:

```
P(жодного оновлення) = ∏ [1 − P(tᵢ)]
```

Для спрощеної консервативної оцінки візьмемо мінімальну ймовірність на початку інтервалу `P = exp(-1) ≈ 0.368`. Тоді:

```
P(жодного оновлення) ≤ (1 − 0.368)ᴷ = (0.632)ᴷ
```

Якщо `λ = 1000` запитів/с, `δ = 0.1` с, а `β = 1.0`, маємо `K = 1000 · 0.1 = 100` запитів.

```
P(жодного оновлення) ≤ (0.632)¹⁰⁰ ≈ 1.37 · 10⁻²¹ ≈ 0
```

Ймовірність того, що гарячий ключ не встигне оновитися до моменту вичерпання TTL, є нескінченно малою величиною. Кеш гарантовано оновлюється завчасно, зводячи кількість промахів для клієнтів строго до нуля.

## Оптимізація коефіцієнта агресивності β

Параметр `β` регулює баланс між ризиком промаху та накладними витратами на раннє оновлення.

Формалізуємо задачу як мінімізацію сукупної цільової функції втрат `Cost(β)`:

```
Cost(β) = C_miss · P_miss(β) + C_compute · E[N_early(β)]
```

де:
- `C_miss` — вартість промаху кешу (деградація сервісу, ризик падіння СУБД);
- `P_miss(β)` — ймовірність того, що до моменту `t_expiry` оновлення не відбудеться;
- `C_compute` — вартість одного зайвого обчислення значення на бекенді;
- `E[N_early(β)]` — математичне сподівання кількості передчасних перерахунків.

```
Аналіз крайових значень β:
1. При β → 0:
   - Зона завчасного оновлення звужується до нуля.
   - P_miss(β) різко зростає, наближаючись до поведінки наївного Cache-Aside.
2. При β >> 1:
   - Оновлення починається надто рано (наприклад, на середині TTL).
   - Кеш оновлюється набагато частіше, ніж потрібно, штучно збільшуючи фонове навантаження на джерело.
```

Математичні дослідження Ваттані та співавторів довели, що значення `β = 1.0` є теоретично оптимальним для широкого спектра стаціонарних пуассонівських процесів. Для систем із високою варіативністю затримок мережі або нестабільним часом відповіді бази даних рекомендується обирати `β ∈ [1.2, 1.5]`.

## Дисперсія згоряння ключів під дією TTL Jitter

Коли система одночасно створює `M` споріднених ключів (наприклад, під час нічного пакетного імпорту бази даних) із фіксованим терміном `T`, щільність розподілу моментів їхнього вичерпання являє собою дельта-функцію Дірака:

```
f(t) = δ(t − (t₀ + T))
```

Усі `M` ключів стають недійсними в одну й ту саму мить часу, викликаючи резонансний стрибок навантаження амплітудою `M · λ` операцій на секунду.

Для розмивання резонансу застосовують операцію внесення рівномірного випадкового шуму (TTL Jitter):

```
T_actual = T_base + ΔT
де ΔT ~ Uniform(-J, +J),  0 < J < T_base
```

Щільність розподілу часу життя ключа стає рівномірною на відрізку `[T_base − J, T_base + J]`:

```
f_jitter(t) = 1 / (2 · J)    для t ∈ [T_base − J, T_base + J]
f_jitter(t) = 0              поза межами відрізка
```

Дисперсія моменту вичерпання окремого ключа становить:

```
Var(T_actual) = (2 · J)² / 12 = J² / 3
```

Пікова інтенсивність промахів по групі з `M` ключів знижується в рази:

```
Peak_Miss_Rate = M / (2 · J)
```

Якщо `M = 100 000` ключів з базовим терміном `T = 3600` секунд отримують випадковий розкид `J = 300` секунд (±5 хвилин), пікове навантаження на перерахунок знижується від синхронного імпульсу в 100 000 операцій/с до плавної константи:

```
Peak_Miss_Rate = 100000 / (2 · 300) = 100000 / 600 ≈ 166.7 операцій/с
```

Зниження пікового навантаження в `600` разів перетворює потенційну катастрофу відмови кластера на рівномірний, передбачуваний фоновий потік оновлень.

### Порівняння з гаусовим шумом (Gaussian Jitter)

У деяких реалізаціях замість рівномірного використовують усічений нормальний розподіл `ΔT ~ N(0, σ²)` з відсіканням на рівні `±3σ`:

```
Var_gaussian = σ²
```

Хоча нормальний розподіл забезпечує більш гладкий спад на межах інтервалу, рівномірний розподіл є переважним для захисту від навали на кеш, оскільки він гарантує строго обмежений інтервал та однакову щільність імовірності на всій довжині вікна оновлення.
