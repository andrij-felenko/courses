# 🧮 Теорія масового обслуговування: закон Літтла, модель M/M/1, пул воркерів M/M/c та формула Кінгмана

Коли розробник проєктує чергу повідомлень для згладжування піків навантаження, виникає інтуїтивна спокуса вважати: якщо середня швидкість надходження повідомлень `λ` (наприклад, 800 повідомлень за секунду) є меншою за максимальну продуктивність пулу споживачів `μ` (наприклад, 1000 повідомлень за секунду), то черга завжди залишатиметься майже порожньою, а час очікування завдання буде близьким до нуля.

Проте в реальній експлуатації система раптово стикається з гігантськими затримками: повідомлення проводять у черзі секунди або десятки секунд, хоча сервери споживачів завантажені лише на 80 %.

Причина цього явища криється не в помилках реалізації брокера, а у фундаментальних законах теорії масового обслуговування (англ. *Queueing Theory*). Випадковий характер інтервалів між надходженням повідомлень та варіативність часу їх обробки спричиняють нелінійне накопичення черги. Нижче наведено строгий математичний аналіз поведінки черг повідомлень під навантаженням.

## Базові параметри та закон Літтла

Розглянемо чергу повідомлень типу «точка-точка» як відкриту систему масового обслуговування:

```
Потік вхідних повідомлень (темп λ) ──> [ Буфер черги (L_q, W_q) ] ──> [ Пул споживачів (темп μ) ] ──> Вихід
```

Введемо ключові змінні системи:
- `λ` (лямбда) — інтенсивність вхідного потоку (середня кількість повідомлень, що надходять до черги за одиницю часу, наприклад `msg / s`).
- `μ` (мю) — інтенсивність обслуговування одного каналу (середня кількість повідомлень, яку один споживач може повністю обробити за одиницю часу).
- `1 / μ` — середній час обробки одного повідомлення споживачем (англ. *Service Time*, `T_s`).
- `ρ` (ро) — коефіцієнт завантаження або утилізація системи (англ. *Traffic Intensity* або *Utilization*):

```
ρ = λ / μ
```

Для стабільності черги з одним споживачем обов'язковою є умова `ρ < 1` (`λ < μ`). Якщо `ρ ≥ 1`, швидкість надходження перевищує швидкість вичитування, довжина черги зростає до нескінченності, і буфер брокера неминуче переповнюється.

Фундаментальним мостом між кількістю повідомлень і часом їх перебування в системі є **закон Літтла** (англ. *Little's Law*), доведений Джоном Літтлом 1961 року:

```
L = λ · W
```

де:
- `L` — середня кількість повідомлень у всій системі (у черзі + в процесі обробки на воркерах).
- `W` — середній повний час перебування повідомлення в системі (час очікування в черзі + час виконання).

Аналогічно закон Літтла діє окремо для самого буфера очікування черги:

```
L_q = λ · W_q
```

де:
- `L_q` — середня довжина черги (кількість повідомлень, що очікують на звільнення воркера, `Queue Depth`).
- `W_q` — середній час очікування повідомлення в черзі до моменту взяття в обробку (англ. *Wait Time*).

Повний час відгуку системи `W` складається з часу очікування в черзі `W_q` та чистого часу обробки `1 / μ`:

```
W = W_q + 1 / μ
```

## Модель M/M/1: Пуассонівський потік та експоненційний час обробки

Найпростішою аналітичною моделлю черги є система **M/M/1** за класифікацією Кендалла (англ. *Kendall's Notation*):
- Перша літера **M** (*Markovian / Memoryless*): інтервали між надходженням повідомлень розподілені за експоненційним законом (вхідний потік є найпростішим пуассонівським із параметром `λ`).
- Друга літера **M**: час обробки повідомлення споживачем також розподілений за експоненційним законом із параметром `μ`.
- Цифра **1**: один активний споживач (один канал обслуговування).

Нехай `P_n` — імовірність того, що в системі в стаціонарному режимі перебуває рівно `n` повідомлень (`n = 0, 1, 2, ...`).

Складемо рівняння балансу переходів між станами системи (рівняння Колмогорова). Для кожного стану `n` потік переходів у стан `n` дорівнює потоку переходів зі стану `n`:

```
λ · P₀ = μ · P₁                         [баланс для стану n = 0]
(λ + μ) · P_n = λ · P_(n-1) + μ · P_(n+1)   [баланс для стану n ≥ 1]
```

Звідси методом підстановки отримуємо вираз для ймовірності довільного стану `P_n` через ймовірність порожньої системи `P₀`:

```
P_n = (λ / μ)ⁿ · P₀ = ρⁿ · P₀
```

Оскільки повна група подій вимагає, щоб сума всіх імовірностей дорівнювала одиниці (`∑ P_n = 1` для `n` від 0 до `∞`), скористаємося формулою суми нескінченно спадної геометричної прогресії:

```
∑_{n=0}^{∞} P_n = 1
P₀ · ∑_{n=0}^{∞} ρⁿ = 1              [винесення спільного множника P₀]
= P₀ · (1 / (1 - ρ)) = 1             [сума нескінченної геометричної прогресії для ρ < 1]
= P₀ = 1 - ρ                         [вираження ймовірності порожньої черги]
```

Підставляючи вираз для `P₀`, отримуємо точний розподіл кількості повідомлень у системі:

```
P_n = (1 - ρ) · ρⁿ
```

Тепер обчислимо математичне сподівання загальної кількості повідомлень у системі `L`:

```
L = ∑_{n=0}^{∞} n · P_n
= ∑_{n=0}^{∞} n · (1 - ρ) · ρⁿ       [підстановка точного виразу P_n]
= (1 - ρ) · ρ · ∑_{n=1}^{∞} n · ρⁿ⁻¹  [винесення множника (1 - ρ) · ρ за суму]
= (1 - ρ) · ρ · (d/dρ (∑_{n=0}^{∞} ρⁿ))  [заміна суми похідною геометричного ряду]
= (1 - ρ) · ρ · (d/dρ (1 / (1 - ρ))) [згортання суми в дріб 1 / (1 - ρ)]
= (1 - ρ) · ρ · (1 / (1 - ρ)²)      [обчислення похідної за змінною ρ]
= ρ / (1 - ρ)                       [скорочення однакового множника (1 - ρ)]
```

Знаючи `L`, за законом Літтла (`W = L / λ`) знаходимо середній повний час перебування повідомлення в системі:

```
W = L / λ
= (ρ / (1 - ρ)) / λ                 [підстановка знайденого значення L]
= (λ / μ) / (λ · (1 - ρ))           [розкриття коефіцієнта завантаження ρ = λ / μ]
= 1 / (μ · (1 - ρ))                 [скорочення інтенсивності входу λ]
= 1 / (μ - λ)                       [розкриття дужок у знаменнику: μ - μ · (λ / μ)]
```

Віднімаючи чистий середній час виконання `1 / μ`, отримуємо середній час очікування в черзі `W_q`:

```
W_q = W - 1 / μ
= 1 / (μ - λ) - 1 / μ               [підстановка повного часу перебування W]
= (μ - (μ - λ)) / (μ · (μ - λ))     [зведення двох дробів до спільного знаменника]
= λ / (μ · (μ - λ))                 [спрощення чисельника: μ - μ + λ = λ]
= (λ / μ) / (μ · (1 - λ / μ))       [ділення чисельника і знаменника на швидкість μ]
= ρ / (μ · (1 - ρ))                 [заміна відношення λ / μ на утилізацію ρ]
```

Також обчислимо середню кількість повідомлень у черзі `L_q` (глибину черги):

```
L_q = λ · W_q
= λ · (ρ / (μ · (1 - ρ)))           [застосування закону Літтла для часу очікування W_q]
= (λ / μ) · (ρ / (1 - ρ))           [перегрупування множників у чисельнику]
= ρ² / (1 - ρ)                      [підстановка визначення утилізації ρ = λ / μ]
```

## Нелінійний колапс затримки: аналіз поведінки формули

Погляньмо, що відбувається з часом очікування `W_q = (ρ / (1 - ρ)) · (1 / μ)`, коли утилізація системи `ρ` наближається до 1.0.

Припустимо, споживач обробляє одне повідомлення в середньому за 10 мс (`1 / μ = 10 мс`, `μ = 100 msg / s`).

Розрахуємо середній час очікування в черзі `W_q` для різних рівнів завантаження:

```
Утилізація (ρ)   Коефіцієнт ρ / (1 - ρ)   Середній час у черзі (W_q)   Глибина черги (L_q)
0.50 (50 %)      0.50 / 0.50 = 1.0        1.0 · 10 мс = 10 мс          0.5 повідомлення
0.70 (70 %)      0.70 / 0.30 = 2.33       2.33 · 10 мс = 23.3 мс       1.63 повідомлення
0.80 (80 %)      0.80 / 0.20 = 4.0        4.0 · 10 мс = 40.0 мс        3.20 повідомлення
0.90 (90 %)      0.90 / 0.10 = 9.0        9.0 · 10 мс = 90.0 мс        8.10 повідомлення
0.95 (95 %)      0.95 / 0.05 = 19.0       19.0 · 10 мс = 190.0 мс      18.05 повідомлень
0.99 (99 %)      0.99 / 0.01 = 99.0       99.0 · 10 мс = 990.0 мс      98.01 повідомлення
```

**Критичний інженерний висновок:**
Зростання утилізації з 50 % до 95 % (менш ніж удвічі) збільшує затримку в черзі **в 19 разів**! При 99 % завантаження час очікування зростає в **99 разів**.

Знаменник `(1 - ρ)` створює гіперболічну асимптоту при `ρ → 1`. Будь-яка система з випадковим вхідним трафіком, завантажена понад 80–85 %, стає екстремально нестабільною: найменше коливання швидкості надходження викликає вибухове зростання черги.

## Багатоканальна черга M/M/c: пул конкурентних воркерів та формула Ерланга-C

У реальних системах чергу зазвичай вичитує не один споживач, а пул із `c` однакових паралельних воркерів (модель **M/M/c**).

Кожен воркер має продуктивність `μ`. Сумарна продуктивність пулу становить `c · μ`. Загальний коефіцієнт утилізації багатоканальної системи:

```
ρ = λ / (c · μ)
```

Система залишається стаціонарною, якщо `ρ < 1` (`λ < c · μ`).

Імовірність того, що новоприбуле повідомлення застане всі `c` воркерів зайнятими й буде змушене стати в чергу очікування, визначається **формулою Ерланга-C** (англ. *Erlang-C formula*, `C(c, a)`, де `a = λ / μ = c · ρ` — запропоноване навантаження в ерлангах):

```
P_wait = C(c, a) = ((aᶜ / c!) · (1 / (1 - ρ))) / (∑_{k=0}^{c-1} (aᵏ / k!) + (aᶜ / c!) · (1 / (1 - ρ)))
```

Знаючи ймовірність очікування `P_wait`, середній час очікування в черзі для моделі M/M/c виражається формулою:

```
W_q = (P_wait / (c · μ · (1 - ρ)))
```

А середня довжина черги `L_q`:

```
L_q = λ · W_q = P_wait · (ρ / (1 - ρ))
```

### Ефект концентрації потужності (Pooling Principle)

Порівняймо дві архітектури з однаковою сумарною потужністю `λ = 80 msg/s`, `1 / μ = 100 мс`:

**Варіант А (4 роздільні черги M/M/1):**
Кожен із 4 воркерів має власну окрему чергу. На кожну чергу надходить `λ_i = 20 msg/s`.
- Утилізація кожного воркера: `ρ = 20 / 10 = 0.8` (80 %).
- Час очікування в кожній черзі: `W_q = 0.8 / (10 · (1 - 0.8)) = 0.8 / 2 = 0.4 с = 400 мс`.

**Варіант Б (1 спільна черга M/M/4 з пулом 4 воркерів):**
Одна точка-точка черга роздає завдання 4 вільним воркерам. `λ = 80 msg/s`, `c = 4`, `μ = 10 msg/s`, `a = 8`, `ρ = 0.8`.
- За формулою Ерланга-C: `P_wait ≈ 0.554`.
- Час очікування в спільній черзі:
```
W_q = 0.554 / (4 · 10 · (1 - 0.8))
= 0.554 / (40 · 0.2)                 [множення в знаменнику: 40 · 0.2 = 8]
= 0.554 / 8                         [ділення ймовірності очікування на залишок потужності]
= 0.06925 с ≈ 69.3 мс
```

**Висновок:**
Об'єднання воркерів у єдиний пул навколо однієї черги скорочує середній час очікування **майже в 6 разів** (з 400 мс до 69 мс) за абсолютно однакових серверних витрат. Це пояснює, чому модель централізованої черги з пулом конкурентних споживачів переважає архітектури з роздільними статичними буферами.

## Реальний світ: формула Кінгмана для загальних черг G/G/1

Модель M/M/1 припускає експоненційний розподіл інтервалів надходження та часу обробки (коефіцієнт варіації `C = σ / m = 1`). Але в реальних розподілених системах:
- Продюсери часто публікують повідомлення пачками (англ. *Batching*), через що дисперсія інтервалів значно вища за експоненційну (`C_a > 1`).
- Завдання мають різну складність: одне повідомлення обробляється за 2 мс (простий запис у кеш), а інше за 500 мс (важкий SQL-запит із блокуванням таблиці), тобто час обробки має важкі хвости розподілу (`C_s > 1`).

Для довільних розподілів інтервалів надходження та часу виконання (модель **G/G/1**) застосовують **наближення Кінгмана** (англ. *Kingman's Formula*, виведена Джоном Кінгманом 1961 року):

```
W_q ≈ ((C_a² + C_s²) / 2) · (ρ / (1 - ρ)) · (1 / μ)
```

де:
- `C_a` — коефіцієнт варіації інтервалів між надходженням повідомлень (`C_a = σ_a / E[A]`).
- `C_s` — коефіцієнт варіації часу обробки повідомлень споживачем (`C_s = σ_s / E[S]`).

Формула Кінгмана показує, що час очікування в черзі є добутком трьох незалежних факторів:
1. **Фактор варіативності (Variability Factor):** `(C_a² + C_s²) / 2`.
2. **Фактор завантаження (Utilization Factor):** `ρ / (1 - ρ)`.
3. **Фактор часу обслуговування (Service Time):** `1 / μ`.

### Чому нерівномірність вбиває продуктивність

Припустимо, утилізація системи становить `ρ = 0.8` (80 %), а середній час виконання `1 / μ = 10 мс`.

**Сценарій 1: Ідеально детермінована черга (D/D/1).**
Повідомлення надходять строго кожні 12.5 мс (`C_a = 0`), кожне завдання виконується рівно за 10 мс (`C_s = 0`).
```
W_q = ((0² + 0²) / 2) · (0.8 / 0.2) · 10 мс = 0 мс
```
Черги немає взагалі.

**Сценарій 2: Марковська черга (M/M/1).**
Експоненційний вхід і час виконання (`C_a = 1`, `C_s = 1`).
```
W_q = ((1² + 1²) / 2) · (0.8 / 0.2) · 10 мс = 1 · 4 · 10 мс = 40 мс
```

**Сценарій 3: Пакетний вхід і важкі завдання (реальний мікросервіс).**
Продюсер публікує дані батчами (`C_a = 2.0`), а тривалість обробки містить рідкісні, але важкі затримки (`C_s = 2.0`):
```
W_q ≈ ((2.0² + 2.0²) / 2) · (0.8 / 0.2) · 10 мс
= ((4.0 + 4.0) / 2) · 4.0 · 10 мс   [піднесення коефіцієнтів варіації до квадрата]
= (8.0 / 2) · 40.0 мс              [обчислення суми квадратів дисперсій]
= 4.0 · 40.0 мс                    [ділення на 2 у факторі варіативності]
= 160.0 мс                         [фінальний час очікування в черзі]
```

За абсолютно однакової середньої пропускної здатності та однакового завантаження серверів (80 %), затримка в реальній черзі виявилася **в 4 рази вищою за марковську та нескінченно вищою за детерміновану**.

## Хвостові затримки (Percentile Latencies)

Для моделі M/M/1 функція розподілу часу очікування `P(W_q ≤ t)` має вигляд:

```
P(W_q ≤ t) = 1 - ρ · e^(-μ · (1 - ρ) · t)
```

Звідси можна точно вивести затримку на заданому процентилі `p` (наприклад, 95-й чи 99-й процентиль, `W_q(p)`):

```
1 - ρ · e^(-μ · (1 - ρ) · t) = p
= ρ · e^(-μ · (1 - ρ) · t) = 1 - p  [перенесення доданка в праву частину]
= e^(-μ · (1 - ρ) · t) = (1 - p) / ρ [ділення обох частин на утилізацію ρ]
= -μ · (1 - ρ) · t = ln((1 - p) / ρ) [логарифмування обох частин рівняння]
= t = (ln(ρ / (1 - p))) / (μ · (1 - ρ)) [множення на -1 та зміна знаку логарифма]
```

Для системи з `μ = 100 msg/s` (10 мс) та `ρ = 0.8`:
- Середній час `W_q = 40 мс`.
- 95-й процентиль (`p = 0.95`):
```
W_q(0.95) = (ln(0.8 / (1 - 0.95))) / (100 · 0.2)
= (ln(0.8 / 0.05)) / 20            [віднімання в знаменнику логарифма]
= ln(16) / 20                      [ділення аргументу: 0.8 / 0.05 = 16]
= 2.7726 / 20                      [наближене значення натурального логарифма]
= 0.1386 с ≈ 138.6 мс              [фінальний 95-й процентиль затримки]
```
- 99-й процентиль (`p = 0.99`):
```
W_q(0.99) = (ln(0.8 / 0.01)) / 20
= ln(80) / 20                      [ділення аргументу: 0.8 / 0.01 = 80]
= 4.3820 / 20                      [наближене значення натурального логарифма]
= 0.2191 с ≈ 219.1 мс              [фінальний 99-й процентиль затримки]
```

Один із сотні запитів чекає в черзі понад 219 мс — **у 5.5 раза довше за середній час**.

## Обмежений буфер: модель M/M/1/K та ймовірність відкидання повідомлень (Drop-tail)

У практичних системах оперативна пам'ять або дисковий розділ брокера ніколи не бувають нескінченними. Коли черга досягає максимальної місткості `K` повідомлень (де `K` включає елемент в обробці та `K - 1` елементів у буфері), брокер змушений або відхиляти нові повідомлення з помилкою відправнику (*Drop-tail / NACK*), або блокувати продюсера (*Backpressure*).

Цей режим описується моделлю **M/M/1/K**.

Рівняння стаціонарного стану для скінченної системи з граничною місткістю `K`:

```
P₀ = (1 - ρ) / (1 - ρ^(K + 1))       [для ρ ≠ 1]
P_n = P₀ · ρⁿ = ((1 - ρ) · ρⁿ) / (1 - ρ^(K + 1))   [для 0 ≤ n ≤ K]
P_n = 0                             [для n > K, вихід за межі буфера]
```

Імовірність блокування або втрати вхідного повідомлення `P_loss` дорівнює ймовірності того, що система заповнена вщерть (`n = K`):

```
P_loss = P_K
= ((1 - ρ) · ρᴷ) / (1 - ρ^(K + 1))  [імовірність відмови новоприбулому повідомленню]
```

Ефективна швидкість прийому повідомлень у чергу `λ_eff` з урахуванням втрат становить:

```
λ_eff = λ · (1 - P_loss)
```

Середня кількість повідомлень у системі `L` для моделі M/M/1/K:

```
L = (ρ / (1 - ρ)) - ((K + 1) · ρ^(K + 1)) / (1 - ρ^(K + 1))
```

А середній час перебування в системі за законом Літтла з ефективною швидкістю `λ_eff`:

```
W = L / λ_eff = L / (λ · (1 - P_loss))
```

### Практичний розрахунок розміру буфера `K` під заданий SLA втрат

Припустимо, черга працює з утилізацією `ρ = 0.9` (90 %). Необхідно розрахувати, яку мінімальну місткість буфера `K` повинен виділити брокер, щоб частка відхилених через переповнення повідомлень не перевищувала `0.01 %` (`P_loss ≤ 10⁻⁴ = 0.0001`):

```
((1 - 0.9) · 0.9ᴷ) / (1 - 0.9^(K + 1)) ≤ 0.0001
= (0.1 · 0.9ᴷ) / (1 - 0.9^(K + 1)) ≤ 0.0001 [обчислення коефіцієнта 1 - ρ = 0.1]
≈ 0.1 · 0.9ᴷ ≤ 0.0001               [наближення для великих K, де 1 - 0.9^(K+1) ≈ 1]
= 0.9ᴷ ≤ 0.001                      [ділення обох частин на 0.1]
= K · ln(0.9) ≤ ln(0.001)           [логарифмування обох частин]
= K · (-0.10536) ≤ -6.90775         [обчислення натуральних логарифмів]
= K ≥ (-6.90775) / (-0.10536)       [зміна знаку нерівності при діленні на від'ємне число]
= K ≥ 65.56                         [ділення чисел: K має бути цілим]
= K = 66 повідомлень                [округлення до найближчого більшого цілого]
```

Буфер розміром усього на 66 повідомлень гарантує, що при 90 % навантаженні втрачатиметься менше одного повідомлення з десяти тисяч.

## Пріоритетні черги: диференціація затримок (Non-preemptive Priority)

Коли в одній черзі змішуються критичні замовлення (VIP-клієнти) та фонові аналітичні задачі, застосовують пріоритетну дисципліну обслуговування.

Розглянемо систему з двома класами пріоритетів без переривання поточної обробки (англ. *Non-preemptive Head-of-Line Priority*):
- Клас 1 (Високий пріоритет): потік `λ₁`, утилізація `ρ₁ = λ₁ / μ`.
- Клас 2 (Низький пріоритет): потік `λ₂`, утилізація `ρ₂ = λ₂ / μ`.
- Загальна утилізація `ρ = ρ₁ + ρ₂ < 1`.

Середній залишковий час завершення завдання, яке вже перебуває на сервері:
```
W₀ = (λ₁ + λ₂) / (2 · μ²) = ρ / (2 · μ)
```

Середній час очікування в черзі для високопріоритетних завдань `W_{q,1}`:
```
W_{q,1} = W₀ / (1 - ρ₁) = (ρ / (2 · μ)) / (1 - ρ₁)
```

Середній час очікування в черзі для низькопріоритетних завдань `W_{q,2}`:
```
W_{q,2} = W₀ / ((1 - ρ₁) · (1 - ρ₁ - ρ₂)) = (ρ / (2 · μ)) / ((1 - ρ₁) · (1 - ρ))
```

### Порівняльний приклад:

Нехай `μ = 100 msg/s` (10 мс), `λ₁ = 40 msg/s` (`ρ₁ = 0.4`), `λ₂ = 40 msg/s` (`ρ₂ = 0.4`), загальна утилізація `ρ = 0.8`.

1. **Без пріоритетів (загальна FIFO черга):**
```
W_q = 0.8 / (100 · (1 - 0.8)) = 0.8 / 20 = 0.04 с = 40 мс
```

2. **Із двома класами пріоритетів:**
- Залишковий час `W₀ = 0.8 / (2 · 100) = 0.8 / 200 = 0.004 с = 4 мс`.
- Час очікування VIP-повідомлень (Клас 1):
```
W_{q,1} = 4 мс / (1 - 0.4)
= 4 мс / 0.6                        [віднімання у знаменнику]
= 6.67 мс                           [затримка VIP скоротилася в 6 разів!]
```
- Час очікування фонових повідомлень (Клас 2):
```
W_{q,2} = 4 мс / ((1 - 0.4) · (1 - 0.8))
= 4 мс / (0.6 · 0.2)                [множення залишків у знаменнику]
= 4 мс / 0.12                       [обчислення знаменника: 0.6 · 0.2 = 0.12]
= 33.33 мс                          [затримка фонових завдань]
```

Введення пріоритетів скоротило затримку для критичних бізнес-операцій з 40 мс до 6.67 мс, практично не погіршивши обробку решти потоку.

## Практичний розрахунок: розмір дискового буфера та час розсмоктування черги

Розглянемо практичну інженерну задачу розрахунку черги для високонавантаженого сервісу.

### Умова задачі:
- Сервіс оформлення замовлень генерує піковий потік `λ_peak = 5000 msg / s`.
- База даних споживача планово перезавантажується для оновлення схеми, що спричиняє повну зупинку обробки на час `T_down = 120 с` (2 хвилини, `μ_down = 0`).
- У звичайному режимі потік замовлень становить `λ_norm = 2000 msg / s`.
- Пул воркерів має сумарну продуктивність `μ_total = 3500 msg / s`.
- Середній розмір одного серіалізованого повідомлення `S_msg = 2 КБ` (2048 байтів).

### 1. Розрахунок необхідної місткості дискового буфера:

Кількість повідомлень `N_accum`, накопичених за час аварії під час пікового навантаження:
```
N_accum = λ_peak · T_down
= 5000 msg/s · 120 s                [підстановка темпу піку та часу простою]
= 600 000 повідомлень               [добуток кількості замовлень]
```

Необхідний обсяг енергонезалежного дискового сховища брокера (WAL):
```
V_disk = N_accum · S_msg
= 600 000 · 2048 байтів             [множення кількості повідомлень на розмір 2 КБ]
= 1 228 800 000 байтів              [обсяг байтів на диску]
= 1.144 ГБ                          [переведення у двійкові гігабайти: ділення на 1024³]
```

З урахуванням коефіцієнта запасу 1.5 на метадані та індекси брокера, диск має гарантувати щонайменше `1.85 ГБ` вільного місця.

### 2. Розрахунок часу повного розсмоктування черги (Drain Time):

Після відновлення бази даних споживачі починають вичитувати чергу з продуктивністю `μ_total = 3500 msg / s`. Водночас у чергу продовжує надходити фоновий потік `λ_norm = 2000 msg / s`.

Ефективна швидкість ліквідації відставання `R_drain`:
```
R_drain = μ_total - λ_norm
= 3500 msg/s - 2000 msg/s           [різниця потужності воркерів та темпу надходження]
= 1500 msg / s                      [чиста швидкість зменшення беклогу]
```

Час повного відновлення черги до нормального стану `T_drain`:
```
T_drain = N_accum / R_drain
= 600 000 / 1500 msg/s              [ділення накопиченого обсягу на чисту швидкість]
= 400 секунд                        [час вичерпання черги у секундах]
= 6.67 хвилин                       [переведення часу у хвилини]
```

### 3. Максимальний час очікування (найгірший SLA):

Повідомлення, яке надійшло на 120-й секунді аварії (останнє перед відновленням БД), проведе в системі максимальний час:
```
W_max = T_down + N_accum / μ_total
= 120 s + 600 000 / 3500 msg/s      [сума часу простою та часу вичитування воркерами]
= 120 s + 171.4 s                   [час обробки 600 000 повідомлень пулом]
= 291.4 секунди                     [повна сумарна затримка]
= 4.86 хвилин                       [переведення у хвилини]
```

Якщо бізнес-вимоги вимагають повернення черги до норми не довше ніж за 2 хвилини (`T_drain_target = 120 с`), архітектор зобов'язаний розширити пул воркерів:
```
μ_required = λ_norm + N_accum / T_drain_target
= 2000 + 600 000 / 120              [додавання необхідної швидкості розвантаження]
= 2000 + 5000                       [сума фонового темпу та темпу дренажу]
= 7000 msg / s                      [необхідна сумарна продуктивність воркерів]
```
Тобто потужність воркерів необхідно подвоїти (з 3500 до 7000 msg/s) на період ліквідації беклогу.

Ці математичні моделі перетворюють проєктування черг повідомлень з емпіричного вгадування на точну інженерну дисципліну з розрахунком допустимих ризиків та ресурсів.
