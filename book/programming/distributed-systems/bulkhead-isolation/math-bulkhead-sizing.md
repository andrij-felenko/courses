# 🧮 Математика перебірок: теорія черг, закон Літтла і розрахунок місткості

Проектування перебірок у розподілених системах вимагає суворого кількісного балансу. Якщо встановити ліміт перебірки занадто малим, система почне безпідставно відхиляти легітимні клієнтські запити під час штатних короткочасних сплесків трафіку. Якщо встановити ліміт занадто великим, перебірка перестане виконувати свою захисну функцію: повільна залежність встигне захопити критичну частку процесорних потоків чи з'єднань до бази даних ще до досягнення встановленої стелі.

Математичний апарат розрахунку місткості перебірок базується на законі Літтла, теорії масового обслуговування (черги `M/M/c/K`) та аналізі дисперсії розподілених ресурсів.

## Закон Літтла та середній рівень конкурентності

Фундаментальною основою для розрахунку будь-якої перебірки є **закон Літтла (англ. *Little's Law*)**, сформульований Джоном Літтлом у 1961 році. Він стверджує, що для будь-якої стаціонарної системи середня кількість одночасно оброблюваних запитів `L` дорівнює добутку середньої інтенсивності вхідного потоку запитів `λ` (запитів на секунду, RPS) на середній час перебування запиту в системі `W` (час відгуку або тривалість виконання, секунди):

```
L = λ · W
```

де:
- `L` — середня кількість паралельно активних запитів (англ. *in-flight requests* або зайнятих потоків / семафорних дозволів);
- `λ` — середня швидкість надходження запитів (RPS);
- `W` — середній час виконання запиту сервісом (у секундах).

Розглянемо числовий приклад. Якщо сервіс авторизації приймає `λ = 400` запитів на секунду, а середній час виконання одного запиту становить `W = 0.025` секунди (25 мілісекунд), то середня кількість потоків, необхідних для його роботи в стаціонарному режимі, становить:

```
L = 400 · 0.025 = 10 потоків
```

Це означає, що за відсутності коливань 10 потоків або семафорних дозволів повністю покривають навантаження 400 RPS. Проте реальний мережевий трафік не є детермінованим: він підпорядковується стохастичним процесам із випадковими інтервалами прибуття та варіативною латентністю.

## Врахування хвостової латентності та пікових сплесків

Розрахунок ємності перебірки `C` не можна проводити за середніми показниками `W_mean`. Якщо час відгуку на 99-му перцентилі (`P99`) зростає до 200 мс (наприклад, через збирання сміття GC або мережеві ретрансмісії), середня формула дасть катастрофічний дефіцит ресурсів.

Для гарантування стабільності місткість відсіку перебірки `C` розраховується з урахуванням пікової інтенсивності `λ_peak` та хвостової латентності `W_p99`:

```
C_base = λ_peak · W_p99
```

Оскільки вхідний потік запитів у коротких вікнах моделюється як пуассонівський процес, кількість одночасних подій має стандартне відхилення, пропорційне квадратному кореню з математичного сподівання. Тому фінальна формула місткості перебірки включає захисний буфер сплеску (англ. *burst headroom*):

```
C = ⌈C_base + k_burst · √(C_base)⌉
```

де:
- `⌈x⌉` — округлення вгору до найближчого цілого числа (стеля);
- `k_burst` — коефіцієнт надійності для покриття флуктуацій. Для покриття 95% сплесків обирають `k_burst = 1.65`, для 99% — `k_burst = 2.33`, для 99.9% — `k_burst = 3.0`.

**Покроковий розрахунок:**
1. Піковий вхідний потік на сервіс оплат: `λ_peak = 500` RPS.
2. 99-й перцентиль латентності виклику платіжного шлюзу: `W_p99 = 0.080` с (80 мс).
3. Базовий рівень одночасних викликів:

```
C_base = 500 · 0.080 = 40
```

4. Захисний буфер для надійності 99% (`k_burst = 2.33`):

```
Buffer = 2.33 · √(40) = 2.33 · 6.3245 ≈ 14.73
```

5. Повна розрахункова місткість перебірки:

```
C = ⌈40 + 14.73⌉ = ⌈54.73⌉ = 55 слотів (потоків / семафорів)
```

Встановлення ліміту перебірки на рівні 55 гарантує, що під час нормальної роботи з урахуванням пікового навантаження та стрибків затримки легітимні виклики не відхилятимуться, але в разі зависання залежності вона зможе захопити щонайбільше 55 потоків, захистивши решту пулу сервера.

## Модель черги M/M/c/K та ймовірність блокування

Коли перебірка реалізується з чергою очікування перед пулом воркерів, поведінка системи описується моделлю **`M/M/c/K`**, де:
- `M` — марковський (пуассонівський) вхідний потік з інтенсивністю `λ`;
- `M` — експоненційний розподіл часу обслуговування з інтенсивністю `μ = 1 / W`;
- `c` — кількість паралельних серверів / потоків обробки (місткість перебірки `C`);
- `K` — максимальна загальна місткість системи (кількість потоків `c` плюс довжина черги `Q_max`, тобто `K = c + Q_max`).

Якщо система заповнена (усі `c` потоків зайняті і в черзі вже стоїть `Q_max` запитів), будь-який наступний запит негайно відхиляється (скидається з кодом 429 або 503).

### Формула Ерланга-B для перебірки без черги (K = c)

Якщо перебірка реалізована через семафор без черги (англ. *zero-queue bulkhead*), ймовірність того, що вхідний запит буде відхилено через відсутність вільних дозволів `P_block`, описується класичною **першою формулою Ерланга (Erlang-B)**:

```
              (A^c) / c!
P_block = ─────────────────────
          ∑ [k=0..c] (A^k / k!)
```

де `A = λ / μ = λ · W` — запропоноване навантаження в ерлангах (англ. *offered load in Erlangs*).

Якщо навантаження `A = 40` ерлангів, а місткість перебірки встановлена `c = 55`:
- При нормальному навантаженні `P_block ≈ 0.003` (0.3% відхилень у піку);
- Якщо залежність уповільнюється втричі (`W` зростає від 80 мс до 240 мс), навантаження стає `A = 500 · 0.240 = 120` ерлангів.
- За формулою Ерланга-B ймовірність відхилення миттєво підскакує до:

```
P_block (A=120, c=55) ≈ 0.548 (54.8% запитів відсікаються на вході)
```

Перебірка автоматично починає відсікати надлишок трафіку, утримуючи завантаження системи рівно на рівні `c = 55` і не дозволяючи повільному сервісу захопити більше ресурсів.

## Розрахунок граничної довжини черги: захист від роздуття затримки

Однією з найпоширеніших помилок є конфігурація перебірки з гігантською чергою очікування (наприклад, 20 потоків і черга на 1000 запитів).

Якщо всі `c` потоків зайняті виконанням запитів, середній час очікування нового запиту в кінці черги довжиною `Q` дорівнює:

```
T_queue = Q / (c · μ) = (Q · W) / c
```

Якщо `W = 100` мс, `c = 10` потоків, а черга заповнена на `Q = 500` елементів, час перебування запиту лише в черзі становитиме:

```
T_queue = (500 · 0.100) / 10 = 5.0 секунд
```

Якщо клієнтський таймаут дорівнює 2 секундам, то кожен запит, який провів у черзі 5 секунд, вийде з неї вже мертвим (клієнт давно закрив з'єднання). Процесор витратить час на його виконання марно.

**Математичне правило допустимої довжини черги:** довжина черги перебірки `Q_max` зобов'язана обмежуватися допустимим бюджетом затримки очікування `T_wait_max` (який повинен бути значно меншим за клієнтський дедлайн `T_deadline − W`):

```
Q_max ≤ ⌊(c · T_wait_max) / W⌋
```

Якщо допустима затримка в черзі `T_wait_max = 50` мс, час виконання `W = 100` мс, а місткість `c = 20` потоків:

```
Q_max ≤ ⌊(20 · 0.050) / 0.100⌋ = ⌊10.0⌋ = 10 елементів
```

Черга перебірки не повинна перевищувати 10 елементів. Будь-яке більше значення веде до накопичення мертвої черги і зомбі-обчислень.

## Математичний доказ дилеми «заморожених ресурсів» (Resource Stranding)

Розглянемо компроміс між надійністю ізоляції та утилізацією обчислювальних ресурсів.

Нехай система має `N` незалежних типів бізнес-операцій. Кожна операція генерує пуассонівський трафік з інтенсивністю `λ_i` та однаковим середнім часом обслуговування `W`.
Сумарне навантаження системи:

```
λ_total = ∑ [i=1..N] λ_i
```

### Варіант А: Єдиний спільний пул без перебірок
Дисперсія сумарної кількості активних запитів у спільному пулі:

```
Var(L_total) = λ_total · W = ∑ [i=1..N] (λ_i · W)
```

Стандартне відхилення сумарного пулу:

```
σ_shared = √(λ_total · W)
```

Необхідний спільний резервний буфер для покриття сплесків із коефіцієнтом `k`:

```
Buffer_shared = k · √(λ_total · W)
```

### Варіант Б: Повний поділ на N незалежних статичних перебірок
Для кожного окремого відсіку `i` стандартне відхилення становить:

```
σ_i = √(λ_i · W)
```

Сумарний резервний буфер, необхідний для всіх `N` окремих перебірок:

```
Buffer_partitioned = ∑ [i=1..N] (k · √(λ_i · W)) = k · √W · ∑ [i=1..N] √(λ_i)
```

За нерівністю Коші-Буняковського для довільних додатних чисел:

```
∑ [i=1..N] √(λ_i) > √(∑ [i=1..N] λ_i)   [при N > 1]
```

Якщо всі `N` потоків мають однакову інтенсивність `λ_i = λ_total / N`, отримаємо точне співвідношення:

```
Buffer_partitioned = k · √W · N · √(λ_total / N)
                   = k · √W · N · (√(λ_total) / √N)       [властивість кореня частки]
                   = k · √W · (N / √N) · √(λ_total)       [перегрупування множників]
                   = k · √W · √N · √(λ_total)             [скорочення: N / √N = √N]
                   = √N · (k · √(λ_total · W))            [властивість добутку коренів: √W · √(λ_total) = √(λ_total · W)]
                   = √N · Buffer_shared                   [підстановка: Buffer_shared = k · √(λ_total · W)]
```

Це рівняння формулює **закон квадратичного кореня для розділення місткості**:
**Сумарний захисний буфер ресурсів, необхідний при розділенні системи на `N` статичних перебірок, зростає у `√N` разів порівняно зі спільним пулом.**

Наприклад, якщо систему розбито на `N = 16` ізольованих перебірок, сумарний розмір замороженого в буферах запасу ресурсів зростає у `√16 = 4` рази. Це математичне явище називають **заморожуванням ресурсів (англ. *resource stranding*)**: вільні слоти в недовантажених перебірках залишаються заблокованими і не можуть бути передані перевантаженому відсіку.

Саме цей закон стимулює застосування дворівневих перебірок: гарантований мінімальний ізольований резерв (англ. *floor allocation*) плюс контрольований спільний буфер для згладжування сплесків.
