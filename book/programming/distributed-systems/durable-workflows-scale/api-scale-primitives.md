# 📋 Специфікація API-контрактів та примітивів масштабування довговічних процесів

Довідник системних інтерфейсів, структур даних та політик керування для високопродуктивних рушіїв довговічного виконання (Durable Execution). Наведені специфікації описують системний контракт між прикладним кодом воркера та розподіленим кластером оркестрації при роботі під навантаженням у мільйони активних процесів.

## 1. Атомарне відсікання історії: ContinueAsNew

Примітив `ContinueAsNew` перериває поточне виконання процесу та атомарно ініціалізує новий запуск (`RunID`) з тим самим ідентифікатором `WorkflowID`, передаючи йому компактний знімок стану як вхідний аргумент.

### Сигнатури функцій у мовних SDK

:::tabs
```go
// Go SDK: повернення спеціального типу помилки, що перехоплюється середовищем виконання
func NewContinueAsNewError(ctx workflow.Context, wfn interface{}, args ...interface{}) error
```
```typescript
// TypeScript SDK: генерація спеціального керуючого винятку
export function makeContinueAsNewFunc<TWorkflow extends Workflow>(
  workflow: TWorkflow,
  options?: ContinueAsNewOptions
): (...args: Parameters<TWorkflow>) => Promise<never>;
```
```cpp
// C++ SDK: виклик контекстного методу відсікання з передачею серіалізованого знімка
class WorkflowContext {
public:
    template <typename... Args>
    [[noreturn]] void continue_as_new(const std::string& workflow_type, 
                                      const ContinueAsNewOptions& options, 
                                      Args&&... args);
};
```
:::

### Параметри конфігурації (ContinueAsNewOptions)

| Поле | Тип | За замовчуванням | Опис і поведінка на масштабі |
| :--- | :--- | :--- | :--- |
| `TaskQueue` | `string` | Поточна черга | Дозволяє перевести новий запуск процесу на інший пул воркерів (наприклад, для балансування навантаження або міграції на нову версію коду). |
| `WorkflowRunTimeout` | `Duration` | Необмежено | Максимальний час життя конкретного нового запуску (`RunID`). Якщо час вичерпано, процес переходить у статус `TIMED_OUT`. |
| `WorkflowTaskTimeout` | `Duration` | 10 секунд | Таймаут виконання одного циклу рішень на воркері. Захищає від зависання воркера під час детермінованого відтворення. |
| `SearchAttributes` | `map[string]interface{}` | Успадковуються | Оновлений набір індексованих атрибутів для вторинного пошукового рушія (OpenSearch/Elasticsearch). |
| `Memo` | `map[string]interface{}` | Успадковуються | Неіндексовані метадані для швидкого відображення в системних інтерфейсах без десеріалізації повного знімка стану. |
| `Header` | `map[string][]byte` | Успадковуються | Контекст трасування (Distributed Tracing, OpenTelemetry заголовки, TraceID, SpanID). |

### Поведінка черги сигналів під час переходу

Коли воркер ініціює команду `ContinueAsNew`, кластер виконує наступну атомарну послідовність у межах однієї транзакції шарду:

1. Поточний запуск маркується подією `WorkflowExecutionContinuedAsNew` і переходить у термінальний стан `CONTINUED_AS_NEW`.
2. Створюється новий запуск із новим `RunID`, але тим самим `WorkflowID`.
3. Усі нерозглянуті сигнали (Buffered Signals), що надійшли від зовнішніх систем у проміжку між викликом команди та фіксацією транзакції, автоматично мігрують у журнал нового запуску і записуються безпосередньо після події `WorkflowExecutionStarted`.
4. Втрата сигналів під час атомарного перемикання повністю виключена на рівні транзакційного протоколу сховища.

## 2. Керування дочірніми процесами: ChildWorkflowOptions

Використовується для декомпозиції масивних завдань на паралельні гілки, ізоляції збоїв та побудови ієрархій деревоподібної агрегації (Tree Fan-out).

### Параметри виклику та конфігурація

| Параметр | Тип | Можливі значення | Системний вплив |
| :--- | :--- | :--- | :--- |
| `WorkflowID` | `string` | Довільний унікальний рядок | Якщо не задано, кластер генерує детермінований UUID. На масштабі рекомендується детермінований ID на основі ключа бізнес-сутності. |
| `ParentClosePolicy` | `Enum` | `TERMINATE`, `ABANDON`, `REQUEST_CANCEL` | Визначає життєвий цикл дочірнього процесу при завершенні, скасуванні або падінні батьківського процесу. |
| `WorkflowIDReusePolicy` | `Enum` | `ALLOW_DUPLICATE`, `REJECT_DUPLICATE` | Забороняє повторний запуск процесу з тим самим ID, якщо попередній ще активний або завершився успішно. |
| `WaitForCancellation` | `bool` | `true`, `false` | Чи чекає батьківський процес підтвердження успішного скасування дочірнього перед власним виходом. |
| `RetryPolicy` | `RetryPolicy` | Структура параметрів повторів | Індивідуальна політика експоненційного відкладення при збоях дочірнього процесу. |

### Специфікація режимів ParentClosePolicy

* `PARENT_CLOSE_POLICY_TERMINATE` (за замовчуванням): якщо батьківський процес завершується, скасовується або падає, кластер негайно надсилає команду примусового припинення (`TerminateWorkflowExecution`) усім дочірнім процесам. Виключає утворення «процесів-зомбі», що споживають ресурси кластера.
* `PARENT_CLOSE_POLICY_ABANDON`: дочірній процес стає автономним (orphaned workflow) і продовжує своє виконання до логічного завершення незалежно від долі батьківського процесу.
* `PARENT_CLOSE_POLICY_REQUEST_CANCEL`: батьківський процес надсилає дочірньому м'який сигнал скасування (`RequestCancelWorkflowExecution`), дозволяючи дочірньому коду перехопити скасування та виконати компенсаційні транзакції (Rollback).

## 3. Атомарний запуск із сигналом: SignalWithStart

Примітив запобігає стану перегонів (Race Condition) при одночасному створенні сутності та доставці їй першого вхідного повідомлення від зовнішніх систем.

### Контракт виконання

```
SignalWithStart(WorkflowID, WorkflowType, TaskQueue, StartArgs, SignalName, SignalArgs)
```

1. **Якщо процес із зазначеним `WorkflowID` не існує:** кластер атомарно створює новий процес із параметрами `StartArgs` і в тій самій транзакції додає подію `WorkflowExecutionSignaled` з корисним навантаженням `SignalArgs`.
2. **Якщо процес із зазначеним `WorkflowID` уже активний:** запуск ігнорується, а сигнал `SignalName` додається в чергу сигналів існуючого процесу.
3. **Гарантія на масштабі:** ліквідує антипатерн «перевірити наявність через API, потім створити або надіслати сигнал» (Check-Then-Act), що запобігає подвійним ініціалізаціям процесів під час сплесків трафіку.

## 4. Синхронні мутації стану: UpdateWorkflowExecution

На відміну від асинхронних сигналів (Fire-and-Forget Signals), механізм оновлення (Workflow Update) дозволяє клієнту надіслати запит на зміну стану, виконати функцію валідації безпосередньо на воркері та отримати синхронну відповідь або відхилення.

### Фази життєвого циклу Update

```
Клієнт -> Шлюз (Ingress) -> Воркер (Validator) -> Воркер (Handler) -> Фіксація в журналі -> Відповідь клієнту
```

1. **Фаза валідації (Validator):** виконується в пам'яті воркера без запису в журнал історії. Якщо валідатор повертає помилку (наприклад, `InsufficientBalanceError`), запит відхиляється негайно без навантаження на сховище бази даних.
2. **Фаза обробки (Handler):** детермінований код модифікує внутрішній стан процесу.
3. **Фаза фіксації:** подія `WorkflowExecutionUpdateAccepted` та результат виконання записуються в журнал подій єдиною транзакцією.

## 5. Схема кастомних атрибутів пошуку: SearchAttributes

Дозволяє індексувати ключові бізнес-поля у вторинному пошуковому рушії (OpenSearch / Elasticsearch) для виконання фільтрації та аналітичної вибірки серед сотень мільйонів процесів.

### Типізація атрибутів

| Тип атрибута | Специфікація даних | Приклад запиту (SQL Filter) |
| :--- | :--- | :--- |
| `Keyword` | Точний рядок (без морфологічного розбиття) | `CustomAccountID = 'acc_49201'` |
| `Text` | Повнотекстовий пошук із токенізацією | `CustomErrorMessage LIKE '%timeout%'` |
| `Int` | 64-бітне ціле число зі знаком | `CustomRetryCount > 5` |
| `Double` | 64-бітне число з плаваючою крапкою | `CustomAmount >= 1500.50` |
| `Bool` | Булеве значення (`true` / `false`) | `CustomIsVipTenant = true` |
| `Datetime` | Мітка часу у форматі UTC (ISO 8601) | `CustomCloseTime < '2026-08-20T12:00:00Z'` |

### Обмеження масштабування та оптимізація запису

* Максимальна кількість кастомних атрибутів на один процес: **100 полів**.
* Розмір значення одного текстового поля: **≤ 2 КБ**. Зберігання великих JSON-документів в атрибутах пошуку суворо заборонено; для цього використовується зовнішнє сховище об'єктів (патерн Claim Check).
* Оновлення атрибутів пошуку відбувається асинхронно через чергу змін (Change Data Capture / Dual Write), тому лаг між фіксацією кроку процесу та появою в результатах пошуку становить від 100 до 500 мілісекунд.

## 6. Конфігурація черг задач та квот (Task Queue & Rate Limiting)

Для ізоляції багатоарендного навантаження (Multi-tenancy) та запобігання голодуванню критичних черг застосовуються системні ліміти на рівні просторів імен (Namespaces) та пулів воркерів.

### Параметри конфігурації черги

```yaml
task_queue_configuration:
  # Максимальна кількість задач активностей на секунду на рівні кластера (Rate Limit)
  max_tasks_per_second: 5000.0

  # Розмір внутрішнього буфера черги задач до застосування Backpressure
  dispatch_buffer_size: 10000

  # Політика розподілу задач між воркерами: FIFO або Deficit Round Robin (DRR)
  routing_policy: "DEFICIT_ROUND_ROBIN"

  # Максимальний час очікування задачі в черзі до генерації сповіщення про лаг
  max_queue_delay_threshold: "30s"

worker_concurrency_options:
  # Максимальна кількість одночасних корутин робочих процесів на один воркер
  max_concurrent_workflow_executors: 200

  # Максимальна кількість паралельних важких I/O активностей на один воркер
  max_concurrent_activity_executors: 500

  # Розмір локального LRU-кешу станів (Sticky Execution Cache)
  sticky_cache_size: 10000

  # Таймаут утримання процесу в пам'яті воркера після завершення задачі
  sticky_schedule_to_start_timeout: "5s"
```

## 7. Політика архівування історії: ArchivalPolicy

Коли робочий процес переходить у фінальний стан (`COMPLETED`, `FAILED`, `TIMED_OUT`, `TERMINATED`, `CONTINUED_AS_NEW`), зберігання повного журналу подій у дорогій транзакційній базі даних (Cassandra / PostgreSQL) стає економічно невигідним.

### Контракт дворівневого архівування

| Рівень сховища | Технологія | Час утримання (Retention) | Доступність і вартість |
| :--- | :--- | :--- | :--- |
| **Гарячий рівень (Hot Tier)** | Cassandra / PostgreSQL / CockroachDB | 1–30 днів (налаштовується для простору імен) | Миттєве детерміноване відтворення, підтримка сигналів, висока вартість гігабайта. |
| **Холодний рівень (Cold Tier / Archival)** | AWS S3, Google Cloud Storage, Azure Blob | 1–7 років (вимоги регуляторів / аудит) | Асинхронне вивантаження стиснутих блоків (Parquet/Protobuf), мінімальна вартість зберігання. |

### Механізм асинхронного вивантаження

1. Після завершення процесу та закінчення періоду утримання (Retention Window) спеціальний фоновий сервіс кластера (`Archival Worker`) вичитує всі події процесу.
2. Події пакуються у стиснуті блоки формату Zstandard або Gzip і записуються в об'єктне сховище за ключем `s3://bucket/namespace/workflow_id/run_id.history`.
3. Рядки в основній транзакційній базі даних видаляються пакетною операцією `DELETE`, звільняючи дисковий простір та пам'ять таблиць.

## 8. Версіонування коду на масштабі: Dynamic Versioning API

Коли в кластері одночасно виконуються мільйони довготривалих процесів, зупинити систему для синхронного оновлення коду неможливо. Зміна коду функції без версіонування призводить до недетермінізму під час Replay.

### Примітив GetVersion

```go
// Go SDK: безпечне розгалуження поведінки за версією
v := workflow.GetVersion(ctx, "billing_calculation_change", workflow.DefaultVersion, 2)
if v == workflow.DefaultVersion {
    // Стара логіка для процесів, що стартували до релізу
    amount = calculateLegacyFee(account)
} else {
    // Нова логіка для процесів після релізу версії 2
    amount = calculateNewTariff(account)
}
```

### Правила застосування GetVersion

1. Перший аргумент (`change_id`) — унікальний ідентифікатор архітектурної зміни.
2. `min_supported_version` (`DefaultVersion` або `-1`): базова версія для запущених раніше процесів.
3. `max_supported_version` (`2`): актуальна версія, яку записує новий код.
4. При першому проходженні нового рядка кластер фіксує подію `MarkerRecorded(ChangeID, Version=2)`. Під час усіх наступних Replay значення версії повертається з маркера без виконання перевірок.

## 9. Системні коди помилок та відмов на масштабі

| Код помилки | Причина виникнення | Рекомендована дія системи / воркера |
| :--- | :--- | :--- |
| `HistorySizeExceededError` | Розмір історії перевищив системний ліміт (наприклад, 50 000 подій або 50 МБ). | Негайне виконання `ContinueAsNew` або аварійне завершення процесу. |
| `ShardOwnershipLostError` | Вузол історії втратив лідерство над шардом через мережевий збій або ребалансування. | Перенаправлення запиту на новий вузол-власник шарду через внутрішнє кільце хешування. |
| `ResourceExhaustedError` | Перевищено квоту запитів (RPS) простору імен або вичерпано пам'ять буфера черги. | Застосування клієнтського експоненційного відкладення з джитером (Exponential Backoff with Jitter). |
| `WorkflowExecutionAlreadyStartedError` | Спроба запуску процесу з існуючим `WorkflowID` при активній політиці `REJECT_DUPLICATE`. | Обробка ідемпотентного результату або підключення до існуючого процесу. |
| `WorkflowTaskFailedError` | Недетермінована поведінка коду процесу (розходження історії з кодом) або необроблений панічний виняток. | Зупинка просування черги рішень даного процесу до виправлення коду у воркері. |
