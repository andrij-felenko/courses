# 🧮 Обчислювальна складність детермінованого відтворення, шардингу та колізій сигналів

Математичний аналіз обчислювальної складності довговічного виконання дозволяє кількісно обґрунтувати межі застосування детермінованого відтворення (Deterministic Replay), розрахувати оптимальну частоту відсікання історії через `Continue-As-New`, оцінити ризик колапсу пропускної здатності при високій частоті вхідних сигналів та розрахувати ємність кешу пам'яті воркерів.

## Квадратичне зростання вартості невідсіченої історії (Unbounded Replay)

Розглянемо довговічний процес, який складається з послідовності `N` кроків (активностей, таймерів або обробок сигналів).

При класичному детермінованому відтворенні для виконання кожного нового кроку `k` (де `k ∈ [1, N]`) воркер зчитує з бази даних усю попередню історію подій довжиною `k - 1`, передає її мережею, десеріалізує в оперативну пам'ять і повторно проганяє детерміновану функцію через `k - 1` попередніх станів.

### Сумарна кількість оброблених подій на CPU

Загальна кількість операцій перевірки та зіставлення подій `S_cpu(N)` за весь час життя процесу дорівнює сумі арифметичної прогресії:

```
S_cpu(N) = 1 + 2 + 3 + ... + N
         = ∑ [i = 1 .. N] i
         = N · (N + 1) ÷ 2
         = 0.5 · N² + 0.5 · N
         = O(N²)              [квадратична складність за кількістю кроків]
```

### Сумарний обсяг переданих мережею даних (I/O)

Нехай середній розмір серіалізованої події в журналі становить `E` байтів (зазвичай 200–500 байтів структурованого JSON/Protobuf).

На кожному кроці `k` воркер завантажує з бази даних корисне навантаження розміром `k · E`. Сумарний обсяг переданих даних `B_io(N)` за `N` кроків становить:

```
B_io(N) = ∑ [i = 1 .. N] (i · E)
        = E · ∑ [i = 1 .. N] i
        = E · N · (N + 1) ÷ 2
        = O(N² · E)           [квадратичне зростання мережевого та дискового трафіку]
```

### Числовий приклад катастрофічного зростання

Якщо процес обробляє `N = 100 000` сигналів без відсікання історії при `E = 300` байтів:

* Кількість операцій відтворення подій: `0.5 · 100 000 · 100 001 = 5 000 050 000` операцій (5 мільярдів порівнянь).
* Сумарний мережевий трафік на зчитування історії: `5 000 050 000 · 300` байтів `≈ 1.5` терабайта трафіку для єдиного робочого процесу.

## Лінеаризація складності через Continue-As-New

При використанні примітиву `Continue-As-New` процес розбивається на послідовні незалежні запуски (Runs) фіксованої довжини `K` подій (наприклад, `K = 1 000`).

Наприкінці кожного запуску поточний стан процесу серіалізується в компактний знімок розміром `S_snap`, поточний запуск завершується, а новий запуск стартує з чистою історією розміром в 1 подію (`WorkflowExecutionStarted`), яка містить цей знімок.

### Сумарна складність при розбитті на чанки

Кількість запусків дорівнює `M = N ÷ K`.

Сумарна кількість операцій відтворення на CPU складається з вартості виконання `M` окремих запусків довжиною `K`:

```
S_can(N, K) = M · S_cpu(K)
            = (N ÷ K) · (K · (K + 1) ÷ 2)
            = N · (K + 1) ÷ 2
            = O(N · K)
            = O(N)            [лінійна складність від N при константному K]
```

Порівняємо навантаження для тих самих `N = 100 000` кроків при `K = 1 000`:
* Кількість запусків: `M = 100 000 ÷ 1 000 = 100` запусків.
* Кількість операцій відтворення: `100 · (1 000 · 1 001 ÷ 2) = 50 050 000` операцій.
* **Ефект оптимізації:** кількість обчислень скоротилася рівно в 100 разів (з 5 мільярдів до 50 мільйонів), а піковий розмір історії не перевищує 300 кілобайтів замість 30 мегабайтів.

## Оптимальний поріг відсікання K*

Вибір занадто малого `K` (наприклад, `K = 10`) створює високі накладні витрати на серіалізацію знімка стану та створення нових запусків у базі даних. Вибір занадто великого `K` повертає квадратичні накладні витрати на Replay.

Знайдемо аналітичний мінімум питомої вартості одного кроку. Нехай:
* `C_snap` — фіксована вартість створення знімка стану та нового запуску (в умовних одиницях часу/CPU).
* `c_rep` — вартість відтворення однієї події в пам'яті.

Середня вартість обробки однієї події `f(K)` як функція від порогу `K`:

```
f(K) = (C_snap ÷ K) + (c_rep · K ÷ 2)
```

Для знаходження мінімуму візьмемо похідну за `K` і прирівняємо до нуля:

```
df ÷ dK = -C_snap ÷ K² + c_rep ÷ 2 = 0
C_snap ÷ K² = c_rep ÷ 2
K² = 2 · C_snap ÷ c_rep
K* = √(2 · C_snap ÷ c_rep)
```

На практиці для більшості хмарних середовищ (де `C_snap ≈ 10–20` мс транзакції в БД, а `c_rep ≈ 0.01` мс на подію в пам'яті):

```
K* = √(2 · 15 ÷ 0.01) = √3000 ≈ 55–60 подій
```

Проте на практиці знімки можуть мати ненульовий розмір пам'яті в базі, тому рушії обирають компромісний діапазон від 500 до 2 000 подій, що забезпечує стабільну продуктивність без перевантаження транзакційного журналу.

## Оцінка пам'яті LRU-кешу при високій конкурентності

Коли в системі одночасно виконується `W` активних довговічних процесів, воркери підтримують кеш детермінованих станів (Sticky Execution Cache), щоб уникати повного зчитування історії з диска при кожному новому завданні.

Нехай:
* `W_active` — загальна кількість одночасних активних процесів.
* `S_mem` — середній розмір стану одного процесу в пам'яті воркера (стек виконання, корутина, буфери змінних), зазвичай `S_mem ≈ 200–500` КБ.
* `C_limit` — розмір LRU-кешу воркера (максимальна кількість утримуваних процесів).

Сумарний обсяг пам'яті, необхідний для утримання всіх активних процесів без деградації до вичитування з диска:

```
M_total = W_active · S_mem
```

Якщо `W_active = 50 000` і `S_mem = 300` КБ:

```
M_total = 50 000 · 300 КБ = 15 000 000 КБ ≈ 14.3 ГБ
```

Якщо сумарна ємність кешу пулу воркерів `∑ C_limit < W_active`, коефіцієнт влучання в кеш (Cache Hit Ratio `H`) падає:

```
H = (∑ C_limit) ÷ W_active
```

Кожен промах повз кеш (`1 - H`) призводить до повного холодного вичитування історії з бази даних та детермінованого відтворення на CPU, що збільшує затримку обробки задачі (Latency) з 1–3 мс (гарячий кеш) до 50–200 мс (холодне відновлення).

## Ймовірність колізій при штурмі одного процесу (Hot Workflow)

Коли зовнішні системи надсилають сигнали до одного конкретного процесу (`WorkflowID`), сервер оркестратора мусить заблокувати відповідний логічний шард або застосувати оптимістичний контроль версій (CAS — *Compare-And-Swap*).

Нехай надходження сигналів описується Пуассонівським процесом з інтенсивністю `λ` сигналів на секунду. Тривалість транзакції оновлення стану процесу (блокування шарду, зчитування, виконання рішення та запис у БД) становить `τ` секунд.

Ймовірність того, що протягом часу виконання транзакції `τ` надійде хоча б один новий конфліктуючий сигнал `k ≥ 1`, становить:

```
P(conflict) = 1 - P(k = 0 у вікні τ)
            = 1 - e^(-λ · τ)
```

### Режими навантаження

1. **Низьке навантаження (`λ · τ ≪ 1`):**
   Використовуючи розклад у ряд Тейлора `e^(-x) ≈ 1 - x`:
   ```
   P(conflict) ≈ λ · τ
   ```
   При `λ = 2` сигнали/сек і `τ = 20` мс (`0.02` с): `P(conflict) ≈ 2 · 0.02 = 0.04` (4% колізій, ретраї непомітні).

2. **Критичне навантаження (`λ · τ ≥ 1`):**
   При `λ = 100` сигналів/сек і `τ = 20` мс:
   ```
   P(conflict) = 1 - e^(-100 · 0.02) = 1 - e^(-2) ≈ 1 - 0.135 = 0.865  [86.5% конфліктів]
   ```
   При 86.5% конфліктів середня кількість повторних спроб на кожен успішний запис зростає експоненційно:
   ```
   N_retries = 1 ÷ (1 - P(conflict)) = 1 ÷ 0.135 ≈ 7.4 спроби
   ```
   Це спричиняє лавиноподібне перевантаження CPU шарду, ріст `τ` у кілька разів і повну зупинку обробки черги задач (Throughput Collapse).

## Деревоподібна агрегація (Tree Fan-out) та зниження колізій

Для подолання колізій `λ · τ ≥ 1` вхідний потік сигналів розділяється на дерево з `L` рівнів та фактором розгалуження `B` (Branching Factor).

Кожен листковий процес приймає сигнали з інтенсивністю:

```
λ_leaf = λ ÷ B^(L - 1)
```

Якщо загальний вхідний потік `λ = 10 000` сигналів/сек розподілити через дерево з `L = 2` рівнів та фактором розгалуження `B = 100`:

```
λ_leaf = 10 000 ÷ 100 = 100 сигналів/сек на 100 окремих процесів
```

Листкові процеси агрегують по `K_batch = 100` сигналів у пам'яті й надсилають кореневому процесу один агрегований батч раз на 1 секунду. Інтенсивність надходження повідомлень до кореневого процесу падає:

```
λ_root = (λ_leaf ÷ K_batch) · B = (100 ÷ 100) · 100 = 100 батчів/сек
```

Ймовірність колізій на кореневому процесі контролюється розміром батча і часом його фіксації в журналі.

## Складність диспетчеризації таймерів: Poller vs Timer Wheel

Порівняємо часову складність виявлення готових до виконання таймерів серед `T` активних таймерів у системі:

| Механізм планування | Вставка нового таймера | Перевірка настання часу (Tick) | Навантаження на сховище |
| :--- | :--- | :--- | :--- |
| **Глобальний SQL Poller** | `O(log T)` (B-Tree індекс) | `O(K · log T)` (сканування діапазону) | Високе (періодичні `SELECT ... FOR UPDATE`) |
| **Купа в пам'яті (Min-Heap)** | `O(log T)` | `O(1)` (перевірка кореня купи) | Низьке, але вимагає пам'яті під усі `T` вузлів |
| **Ієрархічне колесо (Timer Wheel)** | `O(1)` | `O(1)` амортизовано | Мінімальне (партиційне зчитування бакетів) |

### Каскадне пересипання в ієрархічному колесі

Нехай колесо має `R` рівнів (наприклад, 3 рівні: 60 секунд, 60 хвилин, 24 години).
Кількість слотів на рівні `r` дорівнює `S_r`.
Час обертання рівня `r` дорівнює `P_r = P_(r-1) · S_(r-1)`.

При переміщенні годинника на один слот рівня `r` усі таймери з цього слота пересипаються (каскадуються) на рівень `r - 1`. Оскільки каскадування рівня `r` відбувається лише один раз на `P_r` секунд, сумарна амортизована складність операції Tick залишається строго константною:

```
Cost_tick = 1 + (1 ÷ 60) + (1 ÷ 3600) + ... ≈ O(1)
```

Це дозволяє логічному шарду керувати мільйонами таймерів із постійним часом відгуку незалежно від загального масштабу системи.
