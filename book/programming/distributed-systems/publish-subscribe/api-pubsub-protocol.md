# 📋 Інтерфейс і протокольний контракт Pub/Sub: методи, структури кадрів та рівні QoS

Протокольний контракт системи публікації-підписки (Pub/Sub) визначає стандартизований набір операцій для реєстрації підписників, публікації повідомлень, підтвердження обробки та узгодження рівнів якості обслуговування (QoS) між клієнтами та брокером.

Нижче наведено повну специфікацію базового програмного інтерфейсу (API), двійкових форматів керівних пакетів, алгоритмів кодування довжини та автоматів станів доставки для промислових протоколів MQTT 5.0, AMQP 1.0 та gRPC-сервісів.

## 1. Базові сигнатури клієнтського API (Контракт клієнта)

Будь-яка клієнтська бібліотека Pub/Sub реалізує набір операцій керування життєвим циклом з'єднань, підписок і повідомлень.

### `Publish` — Публікація повідомлення в тему

```
Status Publish(
    string topic,
    bytes payload,
    QoSLevel qos,
    PublishOptions options
)
```

**Параметри:**
- `topic` (`string`, обов'язковий) — ієрархічний шлях призначення (наприклад, `orders/eu/ua/created`). Заборонено використання символів масок `+`, `#`, `*`, `>`.
- `payload` (`bytes`, обов'язковий) — двійкове тіло повідомлення (JSON, Protobuf, Avro або сирий масив байтів).
- `qos` (`enum`, за замовчуванням `QoS_1`) — рівень гарантії доставки:
  - `QoS_0` (*At-most-once*): відправка без очікування відповіді.
  - `QoS_1` (*At-least-once*): очікування підтвердження `PUBACK` від брокера з автоматичними повторами.
  - `QoS_2` (*Exactly-once equivalent*): чотиристоронній сеанс узгодження `PUBLISH -> PUBREC -> PUBREL -> PUBCOMP`.
- `options` (`PublishOptions`):
  - `retain` (`bool`): чи зберігати повідомлення як останнє відоме значення для нових підписників.
  - `message_expiry_interval` (`uint32_t`): час життя повідомлення на брокері в секундах (TTL). Якщо підписник офлайн довше цього часу, повідомлення видаляється без доставки.
  - `user_properties` (`map<string, string>`): метадані та заголовки трасування (OpenTelemetry traceparent, час відправки, версія схеми).
  - `correlation_data` (`bytes`): двійковий ідентифікатор для реалізації асинхронного запиту-відповіді (*request-reply pattern*).
  - `response_topic` (`string`): назва теми, в яку клієнт-відповідач повинен надіслати результат обробки.

**Повертає:**
- `Status::OK` або код помилки (`ERR_TOPIC_INVALID`, `ERR_PAYLOAD_TOO_LARGE`, `ERR_NOT_AUTHORIZED`, `ERR_TIMEOUT`).

---

### `Subscribe` — Оформлення підписки на шаблон тем

```
SubscriptionHandle Subscribe(
    string topic_filter,
    SubscriptionOptions options,
    MessageCallback handler
)
```

**Параметри:**
- `topic_filter` (`string`, обов'язковий) — шаблон тем, що може містити маски:
  - `+` або `*` — підстановка рівно одного рівня ієрархії.
  - `#` або `>` — підстановка всіх дочірніх піддерев.
  - `$share/{group_id}/{topic_filter}` — спільна підписка (Shared Subscription) для балансування навантаження між групою однакових споживачів.
- `options` (`SubscriptionOptions`):
  - `max_qos` (`QoSLevel`): максимальний рівень QoS, який згоден приймати споживач.
  - `no_local` (`bool`): прапорець, що блокує отримання клієнтом власних повідомлень, якщо клієнт одночасно публікує і підписаний на ту саму тему.
  - `retain_handling` (`enum`): `SendOnSubscribe` (надсилати збережене повідомлення одразу при підписці), `SendOnlyIfNew` (надсилати лише якщо підписка створюється вперше), `DoNotSend` (не надсилати збережені повідомлення).
  - `subscription_id` (`uint32_t`, від 1 до 268 435 455): числовий ідентифікатор для швидкої локальної диспетчеризації в клієнтському драйвері.
- `handler` (`function<void(MessageContext, bytes)>`) — функція зворотного виклику, що виконується в потоці подієвого циклу при надходженні пакета.

---

### `Acknowledge (ACK)` — Підтвердження успішної обробки

```
Status Ack(
    uint64_t delivery_tag,
    AckOptions options
)
```

**Параметри:**
- `delivery_tag` (`uint64_t`) — унікальний локальний ідентифікатор сесії доставки, наданий брокером у структурі `MessageContext`.
- `options` (`AckOptions`):
  - `multiple` (`bool`): якщо `true`, підтверджує всі попередні повідомлення до вказаного номера включно, зменшуючи кількість мережевих пакетів підтверджень (Cumulative ACK).

---

### `Negative Acknowledge (NACK / Reject)` — Відхилення повідомлення

```
Status Nack(
    uint64_t delivery_tag,
    NackReason reason,
    bool requeue
)
```

**Параметри:**
- `reason` (`NackReason`): причина відхилення (`ERR_TRANSIENT` — тимчасовий збій бази, `ERR_POISON_PILL` — помилка десеріалізації тіла, `ERR_CAPACITY_EXCEEDED` — вичерпання ресурсів пам'яті).
- `requeue` (`bool`): чи повертати повідомлення в початок черги для повторної спроби іншим споживачем, чи негайно скинути його в мертву чергу (Dead-Letter Queue, DLQ).

## 2. Структура керівних пакетів MQTT 5.0 (Двійковий кадр)

У протоколі MQTT кожен керівний пакет складається з фіксованого заголовка (Fixed Header, 2–5 байтів), змінної частини (Variable Header) та корисного навантаження (Payload).

```
Загальна структура двійкового кадру MQTT 5.0:
┌───────────────────────────┬───────────────────────────┬───────────────────────────┐
│ Fixed Header (2..5 байт)  │ Variable Header (змінний) │ Payload (корисне тіло)    │
├─────────────┬─────────────┼─────────────┬─────────────┼───────────────────────────┤
│ Packet Type │ Flags       │ Packet ID   │ Properties  │ Двійкові дані або         │
│ (4 біти)    │ (4 біти)    │ (2 байти)   │ (VarInt+TLS)│ параметри підписки        │
└─────────────┴─────────────┴─────────────┴─────────────┴───────────────────────────┘
```

| Байт / Поле | Розмір | Опис |
| :--- | :--- | :--- |
| **Packet Type** | 4 біти | Тип кадру: `0x01` = `CONNECT`, `0x02` = `CONNACK`, `0x03` = `PUBLISH`, `0x04` = `PUBACK`, `0x08` = `SUBSCRIBE`, `0x09` = `SUBACK`, `0x0C` = `PINGREQ`, `0x0D` = `PINGRESP`, `0x0E` = `DISCONNECT` |
| **Flags** | 4 біти | DUP (повторна відправка), QoS Level (0, 1, 2), RETAIN (збереження на брокері) |
| **Remaining Length** | 1..4 байти | Змінна довжина тіла пакета (Variable Byte Integer, макс 256 МБ = 268 435 455 байт) |
| **Topic Length** | 2 байти (Big-Endian) | Довжина рядка назви теми в байтах |
| **Topic String** | N байтів | Текстовий рядок теми у кодуванні UTF-8 |
| **Packet Identifier** | 2 байти | Унікальний числовий ID повідомлення (присутній лише при QoS ≥ 1) |
| **Property Length** | VarInt | Довжина списку властивостей MQTT 5.0 |
| **User Properties** | Змінний | Пари ключ-значення метаданих (заголовки) |
| **Payload Data** | Змінний | Двійкові дані повідомлення від видавця |

### Алгоритм кодування змінної довжини (Variable Byte Integer)

Для економії мережевого трафіку розмір пакета `Remaining Length` кодується 7-бітними фрагментами:
- Молодші 7 бітів кожного байта несуть значення числа.
- Старший 8-й біт (*continuation bit*) є прапорцем: `1` означає, що наступний байт також належить до числа; `0` означає останній байт.

```
Діапазони значень Variable Byte Integer:
1 байт:  0 (0x00)                 .. 127 (0x7F)
2 байти: 128 (0x80 0x01)          .. 16 383 (0xFF 0x7F)
3 байти: 16 384 (0x80 0x80 0x01)  .. 2 097 151 (0xFF 0xFF 0x7F)
4 байти: 2 097 152                .. 268 435 455 (0xFF 0xFF 0xFF 0x7F)
```

## 3. Автомат станів рукостискань QoS 0, 1 та 2

```
QoS 0 (At-most-once / Fire-and-forget):
Видавець                                Брокер
   │                                      │
   ├────── PUBLISH (QoS=0) ──────────────>┤  (доставка без квитанцій)
   │                                      │

QoS 1 (At-least-once / Підтвердження квитанцією):
Видавець                                Брокер
   │                                      │
   ├────── PUBLISH (PacketId=42) ────────>┤  (збереження в буфері)
   │                                      │
   │<───── PUBACK (PacketId=42) ──────────┤  (квитанція успіху)
   │                                      │
   [Якщо PUBACK не надійшов до таймауту]: │
   ├────── PUBLISH (PacketId=42, DUP=1) ─>┤  (повтор повідомлення)

QoS 2 (Exactly-once equivalent / 4-way Handshake):
Видавець                                Брокер
   │                                      │
   ├────── PUBLISH (PacketId=99) ────────>┤  (крок 1: збереження пакета в очікуванні)
   │                                      │
   │<───── PUBREC  (PacketId=99) ─────────┤  (крок 2: брокер підтвердив прийом і заблокував дублі)
   │                                      │
   ├────── PUBREL  (PacketId=99) ────────>┤  (крок 3: команда брокеру відправити в черги підписників)
   │                                      │
   │<───── PUBCOMP (PacketId=99) ─────────┤  (крок 4: транзакцію повністю завершено)
   │                                      │
```

### Детальний аналіз надійності QoS 2

Чотиристороннє рукостискання QoS 2 гарантує, що повідомлення буде передано підписникам рівно один раз навіть при втраті будь-якого з чотирьох пакетів:
1. **Втрата `PUBLISH`:** видавець не отримує `PUBREC`, вичікує таймаут і надсилає пакет повторно з прапорцем `DUP=1`.
2. **Втрата `PUBREC`:** видавець повторює `PUBLISH (DUP=1)`. Брокер бачить збережений `PacketId=99`, не дублює повідомлення в черги підписників, а лише повторно надсилає `PUBREC`.
3. **Втрата `PUBREL`:** брокер чекає команди на реліз, але видавець після таймауту повторює `PUBREL`. Брокер повторно надсилає `PUBCOMP`.
4. **Втрата `PUBCOMP`:** видавець повторює `PUBREL`, на що брокер знову відповідає `PUBCOMP`.

Цей протокол повністю усуває проблему розриву транзакцій, але вимагає збереження стану транзакції в пам'яті як клієнта, так і брокера на весь час чотириетапного обміну.

## 4. Механізми контролю живості (Keep-Alive) та Заповіту (LWT)

### 1. Серцебиття (Heartbeat / Keep-Alive)

Під час встановлення з'єднання через пакет `CONNECT` клієнт передає параметр `Keep Alive` (у секундах).
- Якщо клієнт не має даних для публікації протягом інтервалу `Keep Alive`, він зобов'язаний надіслати мінімальний 2-байтний пакет `PINGREQ` (`0xC0 0x00`).
- Брокер зобов'язаний відповісти 2-байтним пакетом `PINGRESP` (`0xD0 0x00`).
- Якщо брокер не отримує жодного пакета від клієнта протягом `1.5 × KeepAlive` секунд, брокер примусово розриває TCP-з'єднання як напіввідкрите (*half-open connection*) і переводить сесію в офлайн.

### 2. Заповіт (Last Will and Testament, LWT)

LWT дозволяє іншим сервісам дізнатися про аварійне падіння вузла.
- При підключенні (`CONNECT`) клієнт реєструє параметри заповіту: `Will Topic` (наприклад, `status/node-42`), `Will Payload` (`{"status": "offline", "reason": "crash"}`) та `Will QoS`.
- Якщо клієнт відключається штатно, він надсилає пакет `DISCONNECT (ReasonCode=0x00)`, і брокер **знищує заповіт без публікації**.
- Якщо клієнт падає через збій живлення або розрив мережі (не надіславши `DISCONNECT`), брокер автоматично публікує збережене повідомлення заповіту в тему `status/node-42` від імені мертвого вузла.

## 5. Інтерфейси хмарних систем: gRPC Streaming у Google Cloud Pub/Sub

У сучасних хмарних бекендах протокол Pub/Sub часто реалізується поверх HTTP/2 та gRPC. Клієнти використовують двосторонній потоковий RPC (*Bidirectional Streaming RPC*), що забезпечує високу пропускну здатність без накладних витрат на встановлення окремих HTTP-з'єднань.

```protobuf
syntax = "proto3";
package google.pubsub.v1;

service Subscriber {
  // Двосторонній потік: клієнт надсилає підтвердження (ACK) та модифікації таймаутів,
  // а брокер надсилає потік призначених повідомлень.
  rpc StreamingPull(stream StreamingPullRequest) returns (stream StreamingPullResponse);
}

message StreamingPullRequest {
  string subscription = 1;
  repeated string ack_ids = 2;
  repeated int32 modify_deadline_seconds = 3;
  int32 stream_ack_deadline_seconds = 4;
}

message StreamingPullResponse {
  repeated ReceivedMessage received_messages = 1;
  SubscriptionProperties subscription_properties = 2;
}

message ReceivedMessage {
  string ack_id = 1;
  PubsubMessage message = 2;
  int32 delivery_attempt = 3;
}

message PubsubMessage {
  bytes data = 1;
  map<string, string> attributes = 2;
  string message_id = 3;
  int64 publish_time = 4;
  string ordering_key = 5;
}
```

### Механізм подовження оренди повідомлень (Lease Extension)

У моделі gRPC Streaming брокер призначає повідомленню початковий таймаут підтвердження (*Ack Deadline*, наприклад 10 секунд). Якщо важкий фоновий процес обробляє повідомлення довше (наприклад, виконує навчання ML-моделі 45 секунд), клієнтська бібліотека автоматично надсилає періодичні запити `modify_deadline_seconds`, подовжуючи оренду повідомлення. Якщо процес зазнає аварії, відправка подовжень припиняється, і після вичерпання останнього дедлайну брокер негайно передає повідомлення іншому доступному споживачу.

## 7. Життєвий цикл ідентифікаторів пакетів (PacketId Recycling)

У протоколах MQTT та AMQP числовий ідентифікатор `Packet Identifier` є 16-бітним цілим числом без знака (від 1 до 65 535).
- Ідентифікатор `0x0000` зарезервований і заборонений специфікацією.
- Коли клієнт публікує тисячі повідомлень за секунду з QoS 1 або QoS 2, пул із 65 535 номерів швидко вичерпується.
- Клієнтський драйвер зобов'язаний тримати бітову маску зайнятих ідентифікаторів. Номер `PacketId = 42` може бути повторно використаний для нового повідомлення **тільки після того**, як брокер надіслав підтвердження `PUBACK` або `PUBCOMP` для попереднього повідомлення з цим номером.
- Якщо клієнт досягає ліміту одночасних непідтверджених повідомлень (*Max Inflight Messages*), виклик `Publish()` блокується або повертає помилку буферизації `ERR_INFLIGHT_LIMIT_REACHED`.

## 8. Типові коди помилок та обробка збоїв

У протоколі MQTT 5.0 усі підтвердження (`CONNACK`, `PUBACK`, `SUBACK`, `DISCONNECT`) містять байт причини (*Reason Code*):
- `0x00 (Success)` — успішне виконання операції.
- `0x80 (Unspecified Error)` — внутрішній збій брокера, клієнт повинен повторити спробу з експоненційним відступом (*exponential backoff*).
- `0x83 (Implementation Specific Error)` — помилка бізнес-валідації або несумісність версій схеми повідомлення.
- `0x87 (Not Authorized)` — спроба публікації або підписки на тему, заборонену політикою ACL (Access Control List).
- `0x90 (Topic Filter Invalid)` — використання заборонених символів масок або перевищення максимальної глибини вкладеності теми (максимум 64 рівні).
- `0x97 (Quota Exceeded)` — перевищено ліміт кількості активних підписок або вичерпано квоту пам'яті брокера на сесію.
- `0x99 (Payload Format Invalid)` — корисне навантаження не відповідає заявленому формату індикатора (наприклад, пошкоджений UTF-8 при `Payload Format Indicator = 1`).
