Розподілена платформа електронної комерції обробляє потік замовлень, платежів та клієнтських кліків із сумарною інтенсивністю 120 000 подій на секунду. До центральної шини подій підключено спеціалізований мікросервіс фіскального обліку та європейського оподаткування `tax-eu-service`. Цей сервіс повинен обробляти виключно успішно завершені замовлення, здійснені резидентами країн Європейського Союзу у валюті євро з нарахуванням ПДВ. У загальній масі трансляції такі цільові події становлять лише 2.5% від усього потоку (3 000 повідомлень на секунду), тоді як решта 97.5% (117 000 под/с) є кліками інтерфейсу, логами IoT-складів та транзакціями зі США й Азії.

Якщо підключити податковий сервіс до загального каналу без попереднього відбору, споживач зазнає каскадного колапсу:
1. Мережевий інтерфейс мікросервісу безперервно прокачує 150 МБ/с вхідного трафіку, вичерпуючи виділену пропускну здатність віртуальної машини.
2. Процесор споживача витрачає 97.5% своїх тактів на вичитування сокетів, парсинг JSON-документів у пам'ять та роботу збирача сміття лише для того, щоб виконати перевірку умови `if (region != "EU") return;` і негайно знищити створений об'єкт.
3. Під час сезонних сплесків навантаження (Black Friday) потік зростає до 500 000 под/с. Час обробки сміттєвого трафіку перевищує таймаути пульсу (*heartbeat*), брокер вважає воркер мертвим і запускає нескінченну лавину ребалансувань кластера.
4. Передача всіх глобальних транзакцій у контур одного сервісу грубо порушує вимоги регламентів безпеки (GDPR та PCI-DSS), оскільки воркер отримує доступ до чужих конфіденційних даних до моменту їх локального відкидання.

Цей сценарій демонструє фундаментальну проблему асинхронних архітектур: необмежене поширення подій перетворює переваги слабкого зв'язування на мережевий та обчислювальний параліч. Розв'язанням цієї проблеми є застосування архітектурного патерну **Фільтр повідомлень**.

## Сутність патерну та математична модель предикату

**Фільтр повідомлень** (англ. *message filter*, від лат. *filtrum* — повсть, цідилко; *mittere* — посилати) — це компонент інтеграції розподілених систем, який приймає повідомлення із вхідного каналу, оцінює над ним логічний предикат і або передає повідомлення у вихідний канал без жодних змін, або безповоротно відкидає його.

Формально поведінка фільтра визначається булевою функцією-предикатом `P`, визначеною над множиною всіх можливих повідомлень `M`:

```
P: M → {TRUE, FALSE}
```

Для кожного вхідного повідомлення `m ∈ M` фільтр реалізує детерміноване правило переходу:

```
Filter(m) = {
    Передати m у вихідний канал,    якщо P(m) = TRUE
    Скинути (Drop) або в карантин, якщо P(m) = FALSE або Помилка
}
```

Фільтр повідомлень є спеціалізованим окремим випадком родини патернів інтеграції корпоративних систем (Enterprise Integration Patterns, EIP). Важливо чітко розмежовувати його з сусідніми концепціями:

```
+──────────────────────────+──────────────────────────────────────────────────────────+
| Патерн інтеграції        | Характер трансформації та поведінка потоку               |
+──────────────────────────+──────────────────────────────────────────────────────────+
| Фільтр повідомлень       | Бінарне рішення: 1 вхід → 0 або 1 вихід (тіло незмінне)  |
| Маршрутизатор (Router)   | Розподіл за адресами: 1 вхід → 1 з N цільових каналів    |
| Транслятор (Translator)  | Зміна структури: 1 вхід (Формат A) → 1 вихід (Формат B)  |
| Контентний фільтр        | Зрізання полів: видаляє чутливі поля зсередини тіла      |
| Мертва черга (DLQ)       | Карантин аварій: ловить збої обробки, а не бізнес-відсів |
+──────────────────────────+──────────────────────────────────────────────────────────+
```

Фільтр повідомлень **ніколи не змінює вміст самого повідомлення**. Його єдина функція — керувати фактом проходження повідомлення крізь комунікаційну межу.

## Архітектурні рівні розміщення: де виконувати відсікання

Головне інженерне рішення під час проєктування системи фільтрації — визначення фізичного вузла, на якому обчислюється предикат `P(m)`. У розподілених системах існує три класичні топології розміщення фільтрів.

![Три архітектурні рівні розміщення фільтра повідомлень](/book/programming/distributed-systems/message-filter/img/filter-placement-topology.svg)
*Порівняння архітектурних рівнів: фільтрація на продюсері заощаджує мережу, але створює жорстку залежність; брокерський фільтр забезпечує повну розв'язаність; клієнтський фільтр дає необмежену гнучкість ціною максимальних витрат трафіку.*

### 1. Фільтрація на боці джерела (Producer-Side Filtering)
Продюсер самостійно оцінює предикати підписників перед відправкою повідомлення у фізичний сокет. Якщо подія не відповідає жодному критерію, вона взагалі не публікується в шину.

* **Переваги:** абсолютна економія мережевого трафіку та ресурсів брокера; нульові накладні витрати на передачу непотрібних байтів.
* **Недоліки:** критичне порушення принципу слабкого зв'язування (*tight coupling*). Продюсер змушений знати бізнес-вимоги всіх потенційних споживачів. Якщо у системі з'являється новий мікросервіс з унікальним критерієм відбору, код продюсера доводиться переписувати й перезапускати.

### 2. Серверна фільтрація на брокері (Broker-Side / Middleware Filtering)
Продюсер сліпо публікує всі події в центральний брокер (або тему Pub/Sub). Брокер під час обробки підписок перевіряє предикат кожного підписника над заголовками повідомлення і копіює кадри лише у черги зацікавлених клієнтів.

* **Переваги:** ідеальне архітектурне розв'язання продюсерів і споживачів; значна економія пропускної здатності локальних мереж споживачів; захист конфіденційних даних на рівні інфраструктурного ядра.
* **Недоліки:** процесор брокера стає спільною точкою навантаження. Складні вирази фільтрації можуть знизити загальну пропускну здатність кластера черг.

### 3. Клієнтська фільтрація (Consumer-Side Filtering / Interceptor Pipeline)
Брокер транслює повний широкомовний потік споживачу. Всередині процесу споживача перший шар конвеєра (перехоплювач або middleware) перевіряє предикат до передачі об'єкта в бізнес-обробник.

* **Переваги:** доступ до повної доменної моделі, локальних кешів у пам'яті та реляційних баз даних споживача під час перевірки умов; нульове обчислювальне навантаження на брокер.
* **Недоліки:** максимальні втрати пропускної здатності мережі, блокування пам'яті та деградація продуктивності споживачів під час сплесків стороннього трафіку.

Детальний математичний аналіз точки беззбитковості та порогової селективності, за якої брокерський фільтр стає вигіднішим за клієнтський, виведено окремо: [математична модель вартості фільтрації та поріг вигідності брокерського фільтра](book:programming/distributed-systems/message-filter/math-filter-cost-analysis.md).

## Анатомія рушія: швидкий шлях метаданих проти глибокого парсингу

Продуктивність фільтрації визначається глибиною інспекції структури повідомлення. За цією ознакою фільтри поділяються на два принципово різні механізми:

![Швидкий та повільний шляхи виконання фільтра повідомлень](/book/programming/distributed-systems/message-filter/img/filter-evaluation-internals.svg)
*Внутрішня дихотомія рушія: швидкий шлях оперує фіксованими заголовками у L1-кеші без десеріалізації тіла, тоді як повільний контентний шлях розпаковує важкі дерева об'єктів.*

### 1. Швидкий шлях: Фільтрація за метаданими заголовків (Header Filtering)
Сучасні бінарні та текстові протоколи черг (AMQP, Kafka, MQTT, CloudEvents) ділять повідомлення на службовий конверт (*Headers/Properties*) та непрозоре тіло (*Payload*).

У схемі фільтрації за метаданими всі параметри маршрутизації виносяться продюсером у типізовані заголовки:

```json
{
  "headers": {
    "ce-type": "com.ecommerce.order.paid",
    "ce-source": "/billing/eu-west",
    "tenant_id": 1042,
    "region": "EU",
    "priority": 5,
    "flags": 12
  },
  "payload": "<бінарний стиснений Avro/Protobuf масив розміром 8 КБ>"
}
```

Рушій фільтрації зчитує лише блок метаданих. Оскільки заголовки мають фіксовану типізацію та компактний розмір (100–300 байтів), перевірка умов `region == "EU" AND priority > 3` виконується процесором за 50–200 наносекунд за допомогою простих операцій порівняння регістрів або виклику `memcmp`.

Головна перевага цього шляху — **збереження нульового копіювання (Zero-Copy)**. Тіло повідомлення розміром 8 КБ взагалі не десеріалізується брокером і передається цільовому споживачу просто з дискового сторінкового кешу Linux через системний виклик `sendfile()`.

### 2. Повільний шлях: Контентна фільтрація за вмістом (Content-Based Filtering)
Якщо атрибути відбору сховані всередині корисного навантаження (наприклад, у вкладеному полі JSON чи XML), фільтр змушений здійснити повну десеріалізацію:
1. Виділити сотні тимчасових об'єктів у купі для побудови абстрактного синтаксичного дерева (DOM/AST).
2. Розіпарсити текст за допомогою правил XPath чи JSONPath.
3. Обчислити умову над розпакованими полями.
4. Знищити дерево об'єктів, створивши пікове навантаження на підсистему пам'яті.

Контентна фільтрація знижує пропускну здатність вузла з 1 000 000 до 15 000 повідомлень на секунду.

Історія того, як корпоративні шини 2000-х років зайшли в глухий кут через важку контентну фільтрацію XML, і як сучасні хмари повернулися до швидких бінарних селекторів, описана у вставці: [як розвивалася фільтрація повідомлень від селекторів JMS до хмарного pub/sub та сервісних сіток](book:programming/distributed-systems/message-filter/hist-jms-to-cloud-filtering.md).

## Механізми фільтрації в промислових платформах

Розглянемо, як саме реалізовано фільтрацію повідомлень у провідних розподілених платформах та хмарних брокерах:

### 1. AWS SNS та EventBridge: Політики відбору (Subscription Filter Policies)
У сервісах Amazon Web Services фільтрація повідомлень здійснюється повністю на рівні керованого сервера. Підписник черги SQS або Lambda-функції декларує декларативний JSON-маніфест правил, який застосовується до атрибутів `MessageAttributes`:

```json
{
  "region": ["EU", "UK"],
  "priority": [{"numeric": [">=", 5]}],
  "event_type": [{"prefix": "order."}],
  "customer_tier": [{"anything-but": "anonymous"}]
}
```

Брокер AWS компілює цей JSON-маніфест у внутрішній високоефективний бінарний автомат. Повідомлення, що не проходять фільтр, відкидаються всередині дата-центру AWS без генерації вихідного мережевого трафіку до черги споживача та без списання вартості за операції SQS ReceiveMessage.

### 2. Azure Service Bus: SQL-фільтри проти кореляційних фільтрів
У шині Microsoft Azure Service Bus кожна підписка на тему підтримує два типи фільтрів:
* **`SqlFilter`:** дозволяє записувати предикати синтаксисом стандарту SQL-92 над системними та користувацькими властивостями заголовків (наприклад, `sys.Label = 'Order' AND CustomAmount > 500.0`).
* **`CorrelationFilter`:** оптимізований фільтр суворої еквівалентності над фіксованим набором полів (`CorrelationId`, `MessageId`, `To`, `ReplyTo`, `SessionId`).

На практиці `CorrelationFilter` виконується на порядки швидше за `SqlFilter`, оскільки брокер зіставляє значення через прямий пошук у хеш-таблиці в оперативній пам'яті без необхідності синтаксичного розбору виразу.

### 3. RabbitMQ: Headers Exchange проти Topic Exchange
Брокер RabbitMQ пропонує дві моделі фільтрації на рівні обмінників (Exchanges):
* **`Topic Exchange`:** фільтрує повідомлення за ієрархічним ключем маршрутизації (*Routing Key*), розділеним крапками (наприклад, `orders.eu.retail.paid`). Черга прив'язується до обмінника з патерном `orders.eu.#` (де `#` замінює нуль або більше слів, а `*` — рівно одне слово). Зіставляння здійснюється через префіксне дерево токенів у рантаймі Erlang.
* **`Headers Exchange`:** маршрутизує повідомлення на основі словника заголовків таблиці `headers`. Прив'язка черги задає аргумент `x-match: all` (логічне `AND`) або `x-match: any` (логічне `OR`) над списком ключів і значень.

### 4. Apache Pulsar: Серверне відсікання сегментів
На відміну від Apache Kafka, де брокер історично відмовлявся від серверних фільтрів на користь тупого commit log, брокер Apache Pulsar підтримує підписки з серверною фільтрацією властивостей (*Subscription Properties Filtering*).

Брокер Pulsar під час читання сегментів із розподіленого сховища Apache BookKeeper інспектує метадані повідомлення і передає через TCP-з'єднання споживачу лише ті кадри, які відповідають конфігурації селектора підписки. Це дозволяє споживачам працювати з величезними спільними темами без засмічення власного мережевого інтерфейсу.

### 5. NATS JetStream: Багатосегментна фільтрація тем
У високошвидкісній шині NATS JetStream фільтрація побудована на адресації суб'єктів (*Subjects*). Продюсери публікують повідомлення в деталізовані теми:

```
events.eu.orders.created.enterprise
```

Споживач створює довговічний потік (*Durable Consumer*) із фільтром `events.eu.orders.*.enterprise`. Рушій NATS реалізує зіставляння тем мовою Go через бінарні дерева пошуку в пам'яті, забезпечуючи час прийняття рішення менше 10 наносекунд на повідомлення.

## Фільтри у сервісних сітках (Service Mesh & Envoy CEL)

У сучасних хмарних кластерах Kubernetes фільтрація повідомлень та потоків запитів дедалі частіше виноситься за межі коду застосунку на рівень sidecar-проксі (Envoy).

За допомогою мови **Common Expression Language (CEL)**, створеної Google, інженери можуть описувати декларативні правила відбору над gRPC-метаданими та HTTP-заголовками:

```cel
request.headers['x-tenant-id'] == 'enterprise-corp' && int(request.headers['x-priority']) >= 5
```

Проксі-сервер Envoy компілює ці вирази у внутрішнє двійкове синтаксичне дерево під час старту. Коли вхідний мережевий кадр надходить у мережевий стек ядра, Envoy оцінює предикат безпосередньо в нативному C++ коді до передачі запиту через локальний Unix Domain Socket до контейнера програми. Якщо предикат повертає `false`, запит негайно відхиляється або скидається. Це повністю розвантажує середовище виконання застосунку (JVM, Node.js, Python) від необхідності прокидати через власний стек потоки нецільових подій.

## Економіка хмарного трафіку та Egress Costs

У публічних хмарах (AWS, Google Cloud, Microsoft Azure) передача мережевого трафіку між різними зонами доступності (Cross-AZ) або між географічними регіонами (Cross-Region) є платною послугою. Тариф за міжзонний трафік становить від $0.01 до $0.02 за гігабайт, а міжрегіональний вихідний трафік (*Egress Traffic*) коштує від $0.08 до $0.12 за гігабайт.

У великих розподілених системах, які транслюють 100 000 повідомлень на секунду середнім розміром 5 КБ, сумарний добовий обсяг трафіку сягає `43.2 терабайта`. Якщо такий широкомовний потік передавати через кордони хмарних регіонів 10 споживачам без попереднього брокерського відбору, щомісячний рахунок лише за мережевий egress складе понад **$100 000**.

Розміщення брокерського фільтра на межі відправного регіону, який відсікає 95% нецільових даних, скорочує обсяг переданого трафіку до 2.1 ТБ на добу. Це миттєво знижує інфраструктурні витрати компанії на $95 000 щомісяця, повністю окупаючи процесорні витрати кластера брокерів.

## Фільтри зі станом (Stateful Filters) та часові вікна

Більшість класичних фільтрів є чистими функціями без стану (*stateless*): результат `P(m)` залежить виключно від полів поточного повідомлення `m`.

Проте в сучасних розподілених системах існує клас задач, де рішення про пропуск вимагає аналізу історії попередніх повідомлень. Такі компоненти називаються **фільтрами повідомлень зі станом** (англ. *stateful message filters*).

### 1. Дедуплікаційний фільтр ковзного вікна (Deduplication Filter)
Мережеві повтори на стороні продюсера або брокера неминуче створюють дублікати подій (гарантія at-least-once).

Фільтр дедуплікації підтримує в оперативній пам'яті історію ідентифікаторів повідомлень `message_id` за останні `W` секунд (наприклад, 60 секунд):
* Якщо ідентифікатор зустрічається вперше, повідомлення пропускається, а його ID записується в стан.
* Якщо такий ідентифікатор уже зафіксовано в межах поточного вікна, повідомлення відкидається як дублікат.

Для мінімізації споживання пам'яті застосовують комбіновану структуру: двопоколінний фільтр Блума (Generational Bloom Filter) для миттєвої ймовірнісної перевірки та LRU-буфер для точного підтвердження.

### 2. Динамічний фільтр обмеження швидкості (Rate-Limiting / Throttling Filter)
Якщо вхідний потік перевищує безпечну пропускну здатність споживача (наприклад, сервіс генерації PDF-звітів може обробляти не більше 50 документів на секунду), фільтр обмежує частоту за алгоритмом **маркерного кошика (Token Bucket)** або **протікаючого відра (Leaky Bucket)**. Повідомлення, що надходять понад встановлений ліміт, або відкидаються, або скидаються у повільний буфер.

### 3. Дельта-фільтр істотних змін (Delta / Change-Only Filter)
У системах Інтернету речей (IoT) та збору телеметрії датчики температури, тиску або вібрації генерують сотні показів на секунду. Якщо температура котла залишається стабільною на рівні `85.0°C`, відправка кожного незмінного вимірювання в аналітичну базу створює пусте навантаження.

Дельта-фільтр зберігає останній пропущений стан датчика `V_last` і обчислює предикат зміни:

```
P_delta(m) = (|m.value - V_last| >= ε) OR (m.timestamp - T_last >= MaxSilenceInterval)
```

Повідомлення пропускається лише тоді, коли показник змінився більше ніж на поріг `ε`, або якщо минув максимальний інтервал тиші (для підтвердження живості приладу). Це скорочує обсяг телеметрії на 90–98% без втрати фізичної точності спостереження.

## Конвеєри та композиція фільтрів (Filter Chaining)

У промислових системах фільтрація рідко складається з одного правила. Зазвичай повідомлення проходить крізь багатоступеневий конвеєр (*Filter Chain*), де кожна ланка відповідає за окремий інженерний або безпековий аспект.

![Композиція конвеєра фільтрації з раннім скиданням](/book/programming/distributed-systems/message-filter/img/filter-pipeline-composition.svg)
*Конвеєр фільтрів реалізує принцип раннього відсікання (Fail-Fast): кожен етап звужує потік, залишаючи важким бізнес-правилам лише мінімальну частку валідних даних.*

Типовий конвеєр обробки складається з чотирьох послідовних стадій:

1. **Фільтр валідації схеми та версії (Format Filter):**
   Миттєво відсікає застарілі (*legacy*) повідомлення, версії схем яких більше не підтримуються споживачем (наприклад, `schema_id < 4`). Це захищає воркер від падінь десеріалізації (*poison pills*).

2. **Фільтр безпеки та ізоляції орендарів (Tenant Security Filter):**
   Перевіряє криптографічний підпис або ідентифікатор орендаря (`tenant_id == context.current_tenant`). Гарантує, що в захищений контур мікросервісу не потраплять дані сусідніх клієнтів у мультитенантній базі.

3. **Фільтр дедуплікації зі станом (Stateful Deduplication Filter):**
   Відкидає повторні екземпляри повідомлень, згенеровані мережевими повторами продюсерів (гарантія at-least-once). Використовує ковзне вікно в пам'яті на основі фільтра Блума та LRU-буфера ідентифікаторів `message_id`.

4. **Доменний бізнес-предикат (Domain Rule Filter):**
   Оцінює специфічні функціональні критерії замовлення (наприклад, `amount > 5000 AND status == 'PAID'`).

### Принцип раннього переривання (Short-Circuit Evaluation)
Конвеєр фільтрів виконується суворо зліва направо за принципом короткого замикання. Щойно будь-яка попередня стадія повертає `FALSE`, виконання наступних стадій **миттєво скасовується**, а повідомлення скидається.

Тому найдешевші предикати заголовків (перевірка цілих чисел та бітових масок) завжди розташовуються на початку конвеєра, а дорогі предикати зі зверненням до пам'яті чи криптографії — наприкінці.

Повна практична реалізація швидкого багатостадійного конвеєра фільтрації з нульовим копіюванням розібрана у проєкті: [високопродуктивний конвеєр фільтрації заголовків на C та C++](book:programming/distributed-systems/message-filter/proj-header-filter-pipeline.md).

## Взаємодія з іншими архітектурними патернами

Фільтр повідомлень рідко існує у вакуумі. У зрілих розподілених архітектурах він тісно співпрацює з іншими патернами забезпечення надійності:

### 1. Фільтр та Transactional Inbox (Вхідна скринька)
Патерн Transactional Inbox вимагає збереження кожного вхідного повідомлення в таблицю реляційної бази даних споживача перед його обробкою для гарантії ідемпотентності.

Якщо підключити Transactional Inbox до широкомовного топіка без фільтра, база даних споживача буде здійснювати тисячі безглуздих операцій `INSERT` на секунду для нецільових подій, що призведе до вичерпання пулу з'єднань (*connection pool exhaustion*) та блокування дискового I/O. Розміщення швидкого фільтра заголовків перед Transactional Inbox відсікає 95% сміття в оперативній пам'яті процесу, зберігаючи ресурс бази даних лише для транзакцій свого домену.

### 2. Фільтр та Competing Consumers (Конкурентні споживачі)
Коли групу з кількох воркерів підключено до черги за патерном Competing Consumers, розподіл фільтрації залежить від типу підписки:
* Якщо фільтрація серверна (брокерська), брокер розподіляє між воркерами лише відфільтрований потік цільових повідомлень.
* Якщо фільтрація клієнтська, кожен воркер витрачає частину своєї обчислювальної квоти на відкидання чужих завдань. Це вимагає збільшення кількості реплік контейнерів у 5–10 разів для компенсації непродуктивних витрат CPU.

### 3. Фільтр та Circuit Breaker (Запобіжник)
Патерн Circuit Breaker можна розглядати як адаптивний, динамічний фільтр повідомлень. У нормальному стані (*Closed*) запобіжник пропускає всі події крізь конвеєр. Коли цільова підсистема (наприклад, зовнішній банківський шлюз) починає повертати помилки, запобіжник переходить у стан *Open* і починає функціонувати як жорсткий фільтр, скидаючи або перенаправляючи в DLQ 100% вхідних повідомлень до моменту відновлення працездатності залежного сервісу.

## Розподілене трасування та діагностика скинутих подій

У складних розподілених ландшафтах, що складаються з сотень мікросервісів, відсутність повідомлення в кінцевій точці створює складну діагностичну загадку: чи повідомлення загубилося в мережі через аварію, чи воно було штатно відкинуте фільтром?

Для забезпечення повної прозорості рушії фільтрації інтегруються зі стандартом розподіленого трасування **W3C TraceContext** та екосистемою **OpenTelemetry**:

1. **Прокидання контексту (Context Propagation):** кожне повідомлення несе в заголовках ідентифікатори `traceparent` та `tracestate`.
2. **Фіксація рішення фільтра в спані:** коли фільтр відкидає повідомлення, він не просто інкрементує лічильник, а завершує локальний спан трасування зі спеціальними атрибутами:

```
messaging.system = "kafka"
messaging.destination = "orders.global"
messaging.filter.decision = "DROP"
messaging.filter.rule_id = "tenant_isolation_filter"
messaging.filter.reason = "tenant_id mismatch (expected 1042, got 9912)"
```

Завдяки цьому інженер у системі візуалізації трас (Jaeger, Tempo) може за кілька секунд знайти точне місце, час та причину припинення життєвого циклу будь-якої транзакції, не вдаючись до здогадок чи аналізу гігабайтів сирих логів.

## Безпека, аудит та регуляторний комплаєнс (GDPR / HIPAA)

У корпоративних системах фільтрація повідомлень виконує критичну роль у забезпеченні інформаційної безпеки:

### 1. Принцип найменших привілеїв (Least Privilege)
Передача повного журналу подій підприємства в усі мікросервісні контейнери створює величезну площину атаки. Якщо зловмисник скомпрометує другорядний контейнер аналітики, він зможе вичитати з незахищеного сокета конфіденційні платіжні дані або медичні картки пацієнтів.

Серверні фільтри брокера створюють непереборний бар'єр безпеки: кожен мікросервіс має доступ до черги, у яку фізично доставляються виключно дозволені події згідно з його ACL-політикою.

### 2. Захист від підміни заголовків (Header Tampering)
Оскільки швидка фільтрація спирається на метадані заголовків (`tenant_id`, `user_role`), зловмисний клієнт може спробувати опублікувати подію з підробленим заголовком `tenant_id=0` для отримання адміністративного доступу.

Для запобігання цій загрозі API-шлюзи та продюсери додають до повідомлення криптографічний HMAC-підпис заголовків або JWT-токен. Фільтр безпеки перевіряє валідність підпису до оцінки бізнес-правил.

## Типові помилки та антипатерни проектування

В інженерній практиці часто зустрічаються чотири класичні помилки під час роботи з фільтрами повідомлень:

### 1. Антипатерн «Контентна фільтрація за замовчуванням»
Розробники проектують подію так, що всі ідентифікатори (регіон, валюта, версія) розміщуються глибоко всередині стисненого тіла Protobuf або вкладеного JSON.
* *Наслідок:* брокери та шлюзи втрачають здатність до швидкої фільтрації та змушені виконувати повну десеріалізацію кожного повідомлення.
* *Виправлення:* усі атрибути, за якими може здійснюватися маршрутизація, відбір чи шардинг, повинні дублюватися у відкритих бінарних або текстових заголовках (*Envelope Properties*).

### 2. Антипатерн «Мовчазне зникнення без метрик»
Фільтр реалізується у вигляді простої конструкції `if (!condition) return;` без збору логів та лічильників.
* *Наслідок:* якщо розробник продюсера змінює регістр значення заголовка з `"EU"` на `"eu"`, фільтр починає відкидати 100% корисних повідомлень. Система зовні виглядає абсолютно здоровою (немає помилок чи падінь), але бізнес-процеси повністю зупиняються.
* *Виправлення:* будь-яке відкидання повідомлення повинно негайно фіксуватися в метриках із деталізацією причини відсіювання.

### 3. Антипатерн «Фільтр як заміна доменної валідації»
Спроба закодувати складні багатокрокові правила валідації бізнес-об'єктів (наприклад, перевірка залишку на складі через запит до бази даних) безпосередньо у вирази підписки брокера.
* *Наслідок:* брокер стає надмірно зв'язаним із доменною моделлю, а затримка маршрутизації зростає в тисячі разів.
* *Виправлення:* фільтр повідомлень повинен відповідати виключно за первинний структурний та контекстний відбір; глибока валідація бізнес-інваріантів має виконуватися всередині цільового сервісу.

### 4. Антипатерн «Неоптимальний порядок ланцюга»
Розміщення важких стадій (HMAC-валідація, розпакування JSON) на початку конвеєра перед дешевими числовими перевірками.
* *Наслідок:* процесор витрачає сотні мікросекунд на криптографію подій, які за один крок будуть відкинуті через невідповідність простого поля `region`.
* *Виправлення:* суворе дотримання принципу Fail-Fast — найдешевші фільтри з найвищою силою відсікання завжди повинні стояти першими.

## Семантика збоїв: Fail-Open, Fail-Closed та Карантин

Під час виконання фільтра неминуче виникають позаштатні ситуації: обов'язковий заголовок відсутній через баг у новому релізі продюсера, поле має несумісний тип даних, або пошкоджено мережевий фрейм.

Архітектура фільтрації вимагає чіткого вибору політики обробки таких дефектів:

```
+──────────────────────────+──────────────────────────────────────────────────────────+
| Політика збою            | Поведінка системи та сфера застосування                  |
+──────────────────────────+──────────────────────────────────────────────────────────+
| Fail-Closed (Сувора)     | Помилка = Скидання (Drop). Застосовується в білінгу,     |
|                          | безпеці та ізоляції орендарів.                           |
| Fail-Open (М'яка)        | Помилка = Пропуск (Pass). Застосовується в телеметрії    |
|                          | та аналітиці для запобігання втраті сирих даних.         |
| Quarantine / DLQ         | Помилка = Перенаправлення в Мертву чергу (Dead Letter).  |
|                          | Забезпечує 100% аудит без зупинки основного потоку.      |
+──────────────────────────+──────────────────────────────────────────────────────────+
```

## Спостережуваність: метрики та діагностика

Фільтр повідомлень, який мовчки знищує дані без належного моніторингу, є джерелом найнебезпечніших прихованих аварій у розподілених системах (команда може місяцями не помічати, що новий сервіс не отримує замовлень через помилку в предикаті).

Промисловий фільтр повідомлень зобов'язаний експортувати чотири фундаментальні метрики:
1. **Коефіцієнт селективності (`selectivity_ratio = passed / evaluated`):** показує частку цільового трафіку. Раптове падіння селективності до нуля сигналізує про розсинхронізацію схем між продюсером і фільтром.
2. **Лічильник аварійних скидань (`filter_error_drops_total`):** фіксує кількість повідомлень, відкинутих через відсутність обов'язкових полів.
3. **Затримка обчислення (`filter_latency_ns`):** 99.9-й процентиль часу виконання предикату (має утримуватися в межах мікросекунд).
4. **Обсяг заощадженого трафіку (`bytes_filtered_total`):** сумарна кількість байтів, яку фільтр не допустив до мережі споживачів.
