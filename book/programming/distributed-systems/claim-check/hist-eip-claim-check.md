# 📜 Походження шаблону: від гардеробів до лімітів корпоративних шин

Патерн Claim Check народився на стику двох світів: столітньої практики логістики фізичного багажу та жорстких апаратних обмежень перших корпоративних систем обміну повідомленнями кінця 1990-х і початку 2000-х років.

Без розуміння цих історичних передумов сучасні розробники часто сприймають патерн як суто хмарну оптимізацію для AWS S3, втрачаючи з поля зору головну причину його появи: фундаментальну несумісність черг пам'яті з масивними бінарними станами.

## Від багажних номерків до корпоративних шин

Термін «Claim Check» прийшов у програмну інженерію з транспортної індустрії XIX століття. З розвитком пасажирських залізниць у Великій Британії та США виникла проблема: пасажири не могли перевозити численні важкі скрині у вагонах першого та другого класів через брак місця та ризик травмування під час різкого гальмування. 

Залізничні компанії створили багажні вагони, де вантаж маркувався латунним або паперовим талоном із відривною частиною. Пасажир отримував відривний корінець (*claim check*), який слугував юридичним доказом права власності під час прибуття на кінцеву станцію. Той самий механізм використовували готельні камери схову та театральні гардероби (*coat check*).

У 2003 році архітектори Ґреґор Гопе (*Gregor Hohpe*) та Боббі Вулф (*Bobby Woolf*) опублікували фундаментальну працю «Enterprise Integration Patterns: Designing, Building, and Deploying Messaging Solutions». Серед десятків патернів маршрутизації та трансформації вони формалізували шаблон Claim Check як спосіб збереження пропускної здатності корпоративних шин даних (ESB) та брокерів повідомлень.

## Апаратні бар'єри епохи раннього Enterprise

На початку 2000-х років корпоративна інфраструктура спиралася на технології Microsoft Message Queuing (MSMQ), IBM WebSphere MQ (раніше MQSeries), TIBCO Rendezvous та специфікацію Java Message Service (JMS 1.0/1.1).

Розробники зіткнулися з низкою нездоланних технічних бар'єрів:

### 1. Жорсткий ліміт MSMQ у 4 МБ
Операційні системи Windows NT 4.0 та Windows 2000 містили службу черг MSMQ, яка мала жорстке архітектурне обмеження: максимальний розмір одного повідомлення не міг перевищувати 4 мегабайти (а на практиці при роботі з транзакційними чергами перевищення 1.5–2 МБ спричиняло деградацію сховища `\MSMQ\Storage\*.mq`). Будь-який PDF-документ або бінарний звіт сканера, що перевищував цей ліміт, просто відхилявся стеком операційної системи.

### 2. Пул буферів IBM MQ
У серверах IBM WebSphere MQ черги спиралися на конфігуровані буферні пули (*Buffer Pools*) фіксованого розміру (зазвичай 4 КБ або 64 КБ на сторінку). Надходження повідомлень обсягом у десятки мегабайтів вичерпувало сторінки буферного пулу, блокуючи виконання транзакцій `MQPUT` для всіх інших додатків на мейнфреймі чи UNIX-сервері.

### 3. 32-бітний адресний простір і JVM Heap
Більшість серверів додатків (BEA WebLogic, IBM WebSphere Application Server, JBoss) працювали на 32-бітних процесорах і операційних системах, де адресний простір одного процесу JVM обмежувався 2 ГБ (у Windows) або 3–3.5 ГБ (у Linux/Solaris). Якщо JMS-брокер отримував 20 одночасних повідомлень по 50 МБ у вигляді XML-дерев DOM (де пам'ять на структури вузлів роздувалася в 4–8 разів), процес гарантовано аварійно завершувався з помилкою `java.lang.OutOfMemoryError`.

```
Клієнт ──(XML 50 МБ)──> [32-bit JVM Broker (Max Heap: 1.5 ГБ)] ──> 💥 OutOfMemoryError!
```

Гопе та Вулф запропонували виносити тіло у реляційну базу даних або спільну файлову систему (NFS/SMB), а в чергу відправляти XML-конверт із первинним ключем або шляхом до файлу. Це дозволило корпоративним шинам обробляти десятки тисяч повідомлень на секунду без ризику падіння через нестачу пам'яті.

## Еволюція в еру хмарних технологій та Apache Kafka

З переходом індустрії на розподілені хмарні платформи у 2010-х роках характер обмежень змінився, але їхня суть залишилася незмінною.

Компанія Amazon Web Services у сервісі Amazon SQS встановила стандартний ліміт на розмір повідомлення у 256 кілобайтів. Щоб надати розробникам прозоре рішення для більших об'єктів, AWS випустила офіційну бібліотеку `Amazon SQS Extended Client Library for Java/Python`. Ця бібліотека автоматично реалізувала патерн Claim Check «під капотом»: якщо розмір корисного навантаження перевищував 256 КБ, клієнт прозоро вивантажував тіло в бакет Amazon S3, а в чергу SQS надсилав JSON-повідомлення з посиланням на S3-об'єкт.

У світі Apache Kafka патерн отримав друге дихання завдяки концепції багаторівневого зберігання (*Tiered Storage*). Хоча брокери Kafka мають параметр `message.max.bytes` (за замовчуванням 1 МБ), підвищення цього ліміту до 50–100 МБ критично уповільнює реплікацію між брокерами (`replica.fetch.max.bytes`) та збільшує споживання пам'яті споживачами. Патерн Claim Check залишається стандартом де-факто для передачі важких аналітичних наборів, зображень та моделей машинного навчання через сучасні потокові шини даних.
