# 📋 Контракт конверта Claim Check та схеми дескрипторів

У розподілених асинхронних конвеєрах із використанням патерна Claim Check взаємодія між видавцями, брокерами повідомлень та споживачами базується на суворому контракті метаданих. Цей контракт встановлює єдині правила для всієї інфраструктури: структуру легкого конверта повідомлення, стандартизовану ідентифікацію зовнішнього сховища, алгоритми криптографічної перевірки цілісності, формати серіалізації та регламент обробки виняткових ситуацій.

Головне завдання контракту — забезпечити повну сумісність між гетерогенними мікросервісами, написаними різними мовами програмування. Без формально зафіксованої схеми дескриптора один сервіс може зберегти файл у бакет S3 і передати прямий внутрішній шлях, тоді як інший сервіс очікуватиме підписаний публічний HTTP-URL або додатковий вектор ініціалізації для клієнтського розшифрування. Уніфікований контракт перетворює квитанцію на самодостатній документ, який містить вичерпні інструкції для безпечного вилучення та верифікації корисного навантаження.

## Специфікація Protobuf (версія v3)

Для високопродуктивних бінарних брокерів (як-от Apache Kafka чи gRPC-шини) контракт оголошується у вигляді протоколу Google Protocol Buffers:

```protobuf
syntax = "proto3";

package claimcheck.v1;

enum StorageProvider {
  STORAGE_PROVIDER_UNSPECIFIED = 0;
  STORAGE_PROVIDER_S3 = 1;
  STORAGE_PROVIDER_GCS = 2;
  STORAGE_PROVIDER_AZURE_BLOB = 3;
  STORAGE_PROVIDER_MINIO = 4;
  STORAGE_PROVIDER_HTTP_PRESIGNED = 5;
}

enum HashAlgorithm {
  HASH_ALGORITHM_UNSPECIFIED = 0;
  HASH_ALGORITHM_SHA256 = 1;
  HASH_ALGORITHM_SHA512 = 2;
  HASH_ALGORITHM_BLAKE3 = 3;
}

enum CompressionCodec {
  COMPRESSION_CODEC_NONE = 0;
  COMPRESSION_CODEC_GZIP = 1;
  COMPRESSION_CODEC_ZSTD = 2;
  COMPRESSION_CODEC_SNAPPY = 3;
}

message StorageDescriptor {
  StorageProvider provider = 1;
  string uri = 2;
  string region = 3;
  string bucket = 4;
  string key = 5;
}

message IntegrityDescriptor {
  HashAlgorithm algorithm = 1;
  string digest = 2;
  int64 size_bytes = 3;
  string media_type = 4;
  CompressionCodec compression = 5;
}

message SecurityDescriptor {
  bool encrypted = 1;
  string algorithm = 2;
  string kms_key_id = 3;
  bytes encrypted_dek = 4;
  bytes iv = 5;
  bytes auth_tag = 6;
}

message ClaimCheckEnvelope {
  string spec_version = 1;
  string claim_id = 2;
  string event_type = 3;
  string correlation_id = 4;
  int64 created_at_unix_ms = 5;
  int64 expires_at_unix_ms = 6;
  StorageDescriptor storage = 7;
  IntegrityDescriptor integrity = 8;
  SecurityDescriptor security = 9;
  map<string, string> summary_attributes = 10;
}
```

## Семантика ключових секцій дескриптора

Структура квитанції логічно поділена на кілька ізольованих блоків, кожен з яких відповідає за конкретний аспект обробки:

### 1. Блок ідентифікації та трасування
Поля `spec_version`, `claim_id` та `correlation_id` є обов'язковими для забезпечення спостережуваності (*Observability*). Значення `claim_id` генерується видавцем як незмінний UUIDv4. Воно слугує ключем для аудиту операцій у журналах, зіставлення підтверджень від споживачів та запобігання дублюванню обробки. Поле `correlation_id` містить наскрізний контекст W3C TraceContext або Jaeger, що дозволяє пов'язати завантаження блоба з S3 із загальним деревом розподілених викликів.

### 2. Секція адресації сховища (`storage`)
Цей блок описує фізичне місцезнаходження блоба. Поле `provider` вказує клієнтському SDK, який драйвер сховища слід активувати (наприклад, AWS S3 SDK, Azure Storage SDK чи звичайний HTTP-клієнт для підписаних посилань). Поле `uri` містить канонічний ідентифікатор ресурсу. Якщо в системі активована мультирегіональна реплікація, поля `region` та `bucket` дозволяють споживачу з іншого географічного регіону спочатку спробувати зчитати локальну репліку, а в разі затримки реплікації — виконати прямий запит до вказаного первинного регіону.

### 3. Секція контролю цілісності (`integrity`)
Блок цілісності гарантує, що передане корисне навантаження дійшло до споживача без пошкоджень та спотворень. Поле `algorithm` визначає математичну функцію хешування. Стандартом за замовчуванням є `sha256`, проте для надвисокопродуктивних систем із потоковим розбором відео чи бінарних матриць дозволено використання `blake3`. Поле `digest` містить контрольний рядок у шістнадцятковому форматі. Якщо споживач після завантаження отримує інший дайджест, обробка негайно переривається. Поле `compression` вказує, чи був блоб стиснутий алгоритмом `zstd` або `gzip` перед відправкою у сховище, щоб споживач міг прозоро розпакувати потік до передачі у бізнес-логіку.

### 4. Секція конвертного шифрування (`security`)
Якщо корисне навантаження класифіковане як конфіденційне, цей блок містить усі параметри для локального розшифрування. Блоб у сховищі зберігається у вигляді сирого шифротексту. Ключ шифрування даних (*Data Encryption Key*, DEK) генерується видавцем, зашифровується майстер-ключем сервісу KMS і передається у полі `encrypted_dek`. Споживач звертається до KMS із цим полем для отримання відкритого ключа DEK, після чого виконує розшифрування завантаженого блоба алгоритмом AES-256-GCM із використанням вектора ініціалізації `iv` та тегу автентифікації `auth_tag`.

## Класифікація помилок та протокол реакції споживача

Під час роботи з дескрипторами Claim Check споживач може натрапити на апаратні або логічні збої. Кожна помилка має суворий протокол обробки:

| Код помилки | HTTP / gRPC аналог | Причина виникнення | Дія споживача |
| :--- | :--- | :--- | :--- |
| `ERR_PAYLOAD_NOT_FOUND` | `404 Not Found` | Гонка запису або об'єкт передчасно видалено політикою TTL сховища. | Повторити запит із експоненційним відступом (до 3 спроб). Якщо не знайдено — скинути в DLQ. |
| `ERR_CHECKSUM_MISMATCH` | `422 Unprocessable` | Завантажений блоб пошкоджено в мережі або перезаписано іншим вмістом. | Негайна зупинка обробки, критичний алерт безпеки, скидання в DLQ без повтору. |
| `ERR_CLAIM_EXPIRED` | `410 Gone` | Поточний час перевищує поле `expires_at`, сховище гарантовано видалило блоб. | Відхилити повідомлення, зафіксувати дедлайн у системі аудиту. |
| `ERR_STORAGE_UNAVAILABLE` | `503 Unavailable` | Тимчасовий збій мережі або сервісу S3/MinIO. | Повторна спроба вичитування (Retry) із паузою без скидання в DLQ. |
| `ERR_DECRYPTION_FAILED` | `403 Forbidden` | Недійсний ключ KMS, пошкоджений тег автентифікації GCM. | Скидання в DLQ, сповіщення команди безпеки про помилку ключів. |
| `ERR_PAYLOAD_TOO_LARGE` | `413 Payload Too Large` | Розмір перевищує локальну квоту оперативної пам'яті споживача. | Перехід на потокове читання на диск або передача завданню більшого воркера. |

## Еволюція схем та правила зворотної сумісності

У довготривалих виробничих системах контракти Claim Check неминуче змінюються: додаються нові підтримувані алгоритми хешування (наприклад, перехід із SHA-256 на BLAKE3 для зниження навантаження на CPU), впроваджуються нові хмарні провайдери або розширюються поля аудиту.

Щоб запобігти збоям при одночасній роботі старих і нових версій сервісів, контракт регламентує чотири правила зворотної та прямої сумісності:

1. **Заборона перейменування обов'язкових полів**: Поля `claim_id`, `storage.uri`, `integrity.digest` та `integrity.size_bytes` є незмінними. Будь-яке розширення функціональності додається як нове опціональне поле.
2. **Толерантне читання (Tolerant Reader Pattern)**: Клієнтський SDK споживача зобов'язаний ігнорувати невідомі поля у вхідному JSON-документі квитанції. Якщо видавець версії 1.2 додає нову секцію телеметрії, споживач версії 1.0 повинен успішно прочитати секції `storage` та `integrity`, не викидаючи помилок десеріалізації.
3. **Версіонування алгоритмів цілісності**: Якщо споживач отримує квитанцію з невідомим значенням `integrity.algorithm` (наприклад, новий алгоритм `sha3_256`, не підтримуваний старою версією бібліотеки), клієнт зобов'язаний повернути детерміновану помилку `ERR_UNSUPPORTED_INTEGRITY_ALGO` та відправити повідомлення на ручний розбір, а не пропускати перевірку цілісності.
4. **Ізоляція бізнес-заголовків від дескриптора сховища**: Поля бізнес-метаданих (ідентифікатор клієнта, сума замовлення, гео-зона) розташовуються у корені або у мапі `summary`, щоб зміни в драйверах сховища не впливали на фільтри маршрутизації в брокері повідомлень.

## Накладні витрати на серіалізацію та бінарні формати

Вибір формату передачі квитанції безпосередньо впливає на наскрізну пропускну здатність шини повідомлень. Хоча JSON є найбільш читабельним форматом, для високонавантажених брокерів (понад 100 000 квитанцій на секунду) текстовий оверхед стає помітним фактором.

Порівняння форматів серіалізації дескриптора Claim Check:

- **Текстовий JSON (без стиснення)**: середній розмір квитанції становить 450–650 байтів. Основна частина обсягу припадає на повторювані назви ключів (`storage_uri`, `content_sha256`). Десеріалізація вимагає парсингу рядків і виділення динамічної пам'яті під вузли JSON DOM.
- **Бінарний Protobuf v3**: розмір квитанції скорочується до 140–210 байтів завдяки використанню числових тегів полів та кодуванню Varint. Десеріалізація виконується в 5–8 разів швидше за JSON і практично не створює сміття в кеші.
- **FlatBuffers / Cap'n Proto**: дозволяє зчитувати окремі поля квитанції (наприклад, лише `event_type` для фільтрації) за константний час `O(1)` без повного розбору байтового буфера повідомлення.

## Службові заголовки транспорту (Transport Metadata Headers)

Якщо брокер повідомлень підтримує нативні заголовки повідомлень (наприклад, Kafka Record Headers або RabbitMQ Message Properties), частина метаданих квитанції може дублюватися в заголовках для фільтрації на рівні брокерських брокерів без десеріалізації тіла:

- `X-Claim-ID`: строковий UUID квитанції;
- `X-Claim-Provider`: тип сховища (`s3`, `azure_blob`);
- `X-Claim-Size-Bytes`: числовий розмір у байтах;
- `X-Claim-SHA256`: контрольний хеш корисного навантаження;
- `X-Claim-Expires-At`: ISO-8601 мітка часу завершення життя об'єкта.

Ці заголовки дозволяють брокерам повідомлень або легкому проміжному ПЗ (як-от маршрутизаторам повідомлень чи фільтрам) відхиляти застарілі квитанції або спрямовувати повідомлення у спеціалізовані черги без повного парсингу JSON-документа квитанції.
