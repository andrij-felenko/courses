# 📋 Специфікація канонічного конверта та інтерфейс модуля трансляції

У розподілених сервісно-орієнтованих та подієво-орієнтованих архітектурах канонічна модель даних існує не як абстрактна домовленість, а як строгий машинний контракт. Без формалізованої специфікації полів конверта, правил валідації доменного навантаження та стандартизованих кодів помилок транслятор повідомлень перетворюється на джерело прихованих несумісностей між сервісами. Коли сервіс білінгу інтерпретує суму замовлення у доларах з плаваючою комою, а складська система очікує цілі копійки, будь-яка неточність призводить до фінансових втрат або зупинки конвеєра відвантаження товарів.

Цей документ визначає повну технічну специфікацію канонічного конверта (*Canonical Envelope*), контракт доменної події замовлення (*Order Event Payload*), матрицю семантичної конверсії статусів, інтерфейс модуля транслятора для мов C/C++, механізми захисту від підробки та контракт мертвої черги (*Dead Letter Queue*).

## 1. Специфікація канонічного конверта (Canonical Envelope)

Канонічний конверт огортає будь-яке бізнес-повідомлення у внутрішній розподіленій шині, відокремлюючи службові метадані маршрутизації, трасування та безпеки від внутрішнього корисного навантаження (*payload*).

```
┌────────────────────────────────────────────────────────────────────────────┐
│                        CANONICAL MESSAGE ENVELOPE                          │
├────────────────────────────────────────────────────────────────────────────┤
│  message_id          : UUIDv4 (36 байтів ASCII / 16 байтів двійково)       │
│  correlation_id      : String (до 64 байтів, ідентифікатор ланцюжка)       │
│  causation_id        : UUIDv4 (ідентифікатор події-причини)                │
│  schema_version      : uint32_t (мажорна версія контракту)                 │
│  timestamp_utc_ms    : uint64_t (мілісекунди Unix Epoch від 1970-01-01)    │
│  origin_service      : String (до 32 байтів, назва сервісу-джерела)        │
│  event_type          : String (FQDN, наприклад: ua.retail.order.created)   │
│  tenant_id           : String (до 32 байтів, ключ мультиарендності)        │
│  traceparent         : String (55 байтів, W3C Trace Context стандарт)      │
├────────────────────────────────────────────────────────────────────────────┤
│                               PAYLOAD BODY                                 │
│  (Типізована бінарна або Protobuf/Avro структура доменної моделі)          │
└────────────────────────────────────────────────────────────────────────────┘
```

### Призначення полів та правила валідації конверта

Конверт виконує роль стандартизованого паспорта повідомлення в усій розподіленій системі. Незалежно від того, яка саме бізнес-сутність передається всередині (замовлення, платіж чи оновлення залишків на складі), інфраструктурний рівень брокера та моніторингу оперує виключно полями цього заголовка.

- **`message_id`**: глобально унікальний ідентифікатор конкретного фізичного повідомлення. Він генерується у форматі UUID версії 4 (RFC 4122) під час формування конверта. Це поле є фундаментальним для забезпечення ідемпотентності споживання: кінцеві мікросервіси перевіряють цей ключ у своїх реєстрах дедуплікації і відкидають повторні копії при збоях мережі.
- **`correlation_id`**: наскрізний ідентифікатор усього бізнес-процесу. Якщо клієнт оформлює покупку в мобільному додатку, `correlation_id` генерується на API-шлюзі і передається без змін крізь сервіс кошика, платіжний транслятор, банківський шлюз, систему складського обліку та генератор фіскальних чеків. За цим ідентифікатором інженери знаходять усі пов'язані логи в централізованих сховищах (Elasticsearch, Loki).
- **`causation_id`**: ідентифікатор безпосереднього повідомлення-попередника, що спричинило появу поточної події. Якщо подія `PaymentReceived` була згенерована у відповідь на команду `ChargeCard`, то `causation_id` нової події дорівнює `message_id` команди. Це дозволяє будувати орієнтовані графи причинно-наслідкових зв'язків для аудиту складних розподілених саг.
- **`schema_version`**: цілочисельна версія схеми корисного навантаження. Збільшується лише при внесенні несумісних змін (видалення обов'язкового поля або зміна типу даних). Дозволяє споживачам обирати відповідну функцію десеріалізації.
- **`timestamp_utc_ms`**: точний час створення повідомлення у мілісекундах від початку епохи Unix (1970-01-01T00:00:00Z). Використання локальних часових зон або рядкових представлень заборонено для уникнення проблем із літнім/зимовим часом.
- **`origin_service`**: фіксована назва підсистеми, що опублікувала повідомлення (наприклад, `"checkout-api"`). Дозволяє контролювати топологію потоків даних та налаштовувати політики доступу.
- **`event_type`**: повне кваліфіковане ім'я події у стилі Java-пакетів (`"ua.retail.orders.OrderPlaced"`). Використовується маршрутизаторами повідомлень для фільтрації та направлення пакетів у відповідні черги підписників.
- **`tenant_id`**: ідентифікатор орендаря в мультиарендних системах (*multi-tenant architecture*). Використовується для ізоляції даних та шардингу брокера.
- **`traceparent`**: рядок розподіленого трасування стандарту W3C Trace Context. Забезпечує інтеграцію з OpenTelemetry без необхідності розбирати тіло бізнес-повідомлення.

## 2. Контракт доменного навантаження (Order Event Payload)

Корисне навантаження канонічного замовлення містить нормалізований бізнес-стан замовлення, повністю відв'язаний від технічних особливостей конкретних баз даних або зовнішніх API.

### Принципи типізації та фінансової цілісності

Доменна модель замовлення підпорядковується суворим інваріантам, спрямованим на запобігання пошкодженню даних та розбіжностей в обліку:

1. **Фіксована точність грошових сум**: усі фінансові величини (`total_amount_cents`, `unit_price_cents`, `tax_cents`) передаються виключно як невід'ємні 64-бітні цілі числа `uint64_t` у найменших неподільних одиницях валюти (копійках, центах). Використання чисел із плаваючою комою суворо заборонено через накопичення похибок округлення стандарту IEEE 754.
2. **Валідація кодів валют**: поле `currency` приймає виключно трилітерні коди стандарту ISO 4217 у верхньому регістрі (`"UAH"`, `"USD"`, `"EUR"`). Використання нестандартних символів (`"₴"`, `"$"`) заборонено.
3. **Контроль інваріанту суми замовлення**: під час валідації транслятор обов'язково перевіряє арифметичну рівність: загальна сума `total_amount_cents` повинна точно дорівнювати сумі вартостей усіх позицій `quantity · unit_price_cents` плюс податок `tax_cents`. Порушення цього правила розцінюється як спроба шахрайства або збій розрахунків, і пакет негайно блокується.
4. **Уніфікований артикул SKU**: ідентифікатор товару на складі нормалізується до верхнього регістру з обмеженням допустимих символів `[A-Z0-9\-_]`.

### Структура полів товарної позиції (`OrderItem`)

Кожен елемент масиву `items` описує окремий рядок чека замовлення. Він містить ідентифікатор рядка `item_id`, складський артикул `sku`, цілу кількість одиниць товару `quantity` (від 1 до 10 000), базову ціну за одиницю в копійках `unit_price_cents` та нарахований податок на додану вартість `tax_cents`. Масив не може бути порожнім: замовлення повинно містити щонайменше одну товарну позицію.

## 3. Матриця семантичного мапінгу статусів

У гетерогенних корпоративних середовищах кожна підсистема історично використовує власні формати та найменування для позначення життєвого циклу замовлення. Транслятор виступає універсальним нормалізатором, який перетворює ці відмінності на фіксоване перерахування `CanonicalOrderStatus`.

### Таблиця взаємної відповідності статусів

- **`CANONICAL_STATUS_CREATED = 1`**:
  - У застарілій системі ERP: числовий код `101`.
  - У клієнтському JSON API: текстовий статус `"PENDING_PAYMENT"`.
  - У протоколі логістики EDIFACT: сегментний статус `1`.
  - *Бізнес-значення*: замовлення успішно створене користувачем на сайті, товари зарезервовані на складі, очікується авторизація платіжного шлюзу.
- **`CANONICAL_STATUS_CONFIRMED = 2`**:
  - У застарілій системі ERP: коди `102` або `104`.
  - У клієнтському JSON API: статус `"PAYMENT_SETTLED"`.
  - У протоколі логістики EDIFACT: сегментний статус `12`.
  - *Бізнес-значення*: банк підтвердив списання коштів з картки клієнта, замовлення автоматично передано до складської підсистеми для друку накладних та збирання.
- **`CANONICAL_STATUS_SHIPPED = 3`**:
  - У застарілій системі ERP: числовий код `103`.
  - У клієнтському JSON API: статус `"FULFILLED"`.
  - У протоколі логістики EDIFACT: сегментний статус `21`.
  - *Бізнес-значення*: посилка сформована, запакована та фізично передана представнику кур'єрської або поштової служби разом із супровідними документами.
- **`CANONICAL_STATUS_CANCELLED = 4`**:
  - У застарілій системі ERP: коди `999` або `-1`.
  - У клієнтському JSON API: статуси `"REJECTED"` або `"VOID"`.
  - У протоколі логістики EDIFACT: сегментний статус `99`.
  - *Бізнес-значення*: транзакція скасована через відхилення платежу банком, брак товару на складі або пряме скасування користувачем до моменту відвантаження.

Якщо вхідний пакет містить невідомий числовий або рядковий статус (наприклад, `109` або `"PROCESSING"`), транслятор не намагається вгадати його значення. Будь-який невідомий код кваліфікується як фатальна семантична помилка `ERR_SEMANTIC_UNKNOWN_STATUS`, і повідомлення негайно відправляється в мертву чергу для ручного розбору інженерами інтеграції.

## 4. Контракт мертвої черги (Dead Letter Queue Envelope)

Коли транслятор стикається з синтаксично некоректним, семантично невалідним або несумісним пакетом, він не може зупинити роботу процесу або заблокувати вхідну чергу нескінченними повторами. Він упаковує проблемне повідомлення у стандартизований діагностичний запис для відправки в спеціальний карантинний топік брокера `system.dlq.orders`.

```
┌────────────────────────────────────────────────────────────────────────────┐
│                        DEAD LETTER QUEUE (DLQ) RECORD                      │
├────────────────────────────────────────────────────────────────────────────┤
│  dlq_id              : UUIDv4 (унікальний ID аварійного запису)            │
│  source_topic        : String (назва вхідного топіка/черги)                │
│  consumer_group      : String (ідентифікатор групи споживачів)             │
│  failed_at_utc_ms    : uint64_t (мітка часу відмови)                       │
│  retry_count         : uint32_t (кількість виконаних спроб)                │
│  error_code          : DlqErrorCode (стандартизований числовий код)        │
│  error_message       : String (детальний машинний та людський опис збою)   │
│  raw_payload_bytes   : Binary Blob / Base64 (оригінальні незмінні байти)   │
│  headers_dump        : Map<String, String> (оригінальні заголовки пакету)  │
└────────────────────────────────────────────────────────────────────────────┘
```

### Класифікація помилок трансляції та правила реагування

Карантинні записи діляться на три функціональні категорії відповідно до природи відмови:

1. **Синтаксичні помилки (`ERR_SYNTAX_MALFORMED = 1001`)**: виникають при порушенні структури передачі даних (обірваний JSON-документ, відсутність закриваючого тегу в XML, невалідні двійкові маркери). Такі помилки свідчать про проблеми транспортного рівня або баги в коді відправника. Автоматичні повтори (*retries*) для них суворо заборонені, оскільки вони не мають шансів на успіх.
2. **Помилки валідації схеми (`ERR_SCHEMA_VALIDATION_FAILED = 1002`)**: виникають, коли вхідний документ синтаксично коректний, але в ньому відсутнє обов'язкове поле (наприклад, немає ідентифікатора покупця `customer_ref`) або тип даних поля не відповідає очікуваному (рядок замість числа).
3. **Семантичні помилки бізнес-правил (`ERR_SEMANTIC_* = 2001..2003`)**: виникають при порушенні логічних інваріантів (невідомий код валюти `"GBP"`, від'ємна ціна або сума замовлення, що не збігається з сумою рядків). Повідомлення зберігається в DLQ із детальним описом причини порушення інваріанту.
4. **Інфраструктурні таймаути (`ERR_ENRICHMENT_TIMEOUT = 3001`)**: виникають у разі тимчасової недоступності зовнішніх довідників або розподіленого кешу Redis при спробі збагатити повідомлення. Це єдиний клас помилок, для якого дозволені обмежені автоматичні повтори з експоненційним відступом (*Exponential Backoff*). Якщо ліміт спроб вичерпано, пакет остаточно поміщається в DLQ.

Для вбудовування транслятора у високопродуктивні брокери повідомлень, проксі-сервери (Envoy, Nginx) та сайдкар-контейнери визначається стабільний C-ABI інтерфейс, сумісний із будь-якими компіляторами та мовами зв'язування (FFI).

### Контракт управління пам'яттю та володіння ресурсами

Робота з пам'яттю на високих швидкостях вимагає строгого розподілу прав володіння буферами:

1. **Ініціалізація (`translator_create`)**:
   - Функція виділяє внутрішні структури, компілює регулярні вирази, завантажує таблиці мапінгу статусів та виділяє локальний робочий пул пам'яті (*scratchpad*) розміром, вказаним у `TranslatorConfig` (за замовчуванням 64 КБ).
   - Повернений дескриптор `TranslatorInstance*` не є безпечним для паралельного виклику з кількох потоків одночасно. У багатопотокових додатках кожен робочий потік створює власний незалежний екземпляр транслятора (*thread-local translator*), що виключає необхідність використання м'ютексів на гарячому шляху обробки.

2. **Обробка пакету (`translator_process_packet`)**:
   - Функція приймає незмінний вказівник на вхідні байти `input_raw_bytes`. Вхідна пам'ять належить викликаючій стороні (мережевому стеку чи драйверу сокета) і не звільняється транслятором.
   - Усі проміжні операції парсингу відбуваються всередині попередньо виділеного пулу пам'яті екземпляра.
   - Якщо трансляція успішна, вихідний буфер `output_buffer` містить сформоване канонічне повідомлення. Якщо трансляція зазнала невдачі, вихідний буфер `dlq_envelope_buffer` містить готовий бінарний запис для мертвої черги.
   - Виклик функції гарантує відсутність блокуючих операцій вводу-виводу і виконується за лінійний час `O(N)` від довжини вхідного пакету.

3. **Звільнення результатів (`translator_free_result`)**:
   - Викликаюча сторона зобов'язана викликати `translator_free_result` після того, як вихідні байти були відправлені в сокет або чергу брокера.
   - Ця операція не викликає системний виклик `free()`, а лише скидає вказівник зсуву у внутрішньому пулі потоку, роблячи буфер миттєво доступним для наступного повідомлення.

## 6. Бінарне представлення в пам'яті та вирівнювання (Memory Alignment)

Для досягнення максимальної швидкості десеріалізації на рівні мов C та C++ канонічний двійковий формат використовує строге вирівнювання полів за природними межами слів процесора (8 байтів для `uint64_t`, 4 байти для `uint32_t`).

### Схема двійкового фрейму

Всі багатобайтні цілі числа зберігаються у порядку байтів від молодшого до старшого (*Little-Endian*). Якщо транслятор виконується на архітектурі Big-Endian, операції серіалізації автоматично виконують зворотну перестановку байтів за допомогою інструкцій процесора `bswap` (`__builtin_bswap64`).

Рядкові значення змінної довжини предваряються байтом довжини (*Length-Prefix*), що усуває необхідність пошуку нуль-термінатора та дозволяє безпечно передавати довільні двійкові послідовності.

## 7. Криптографічний підпис та захист від спотворення

У розподілених системах із підвищеними вимогами до безпеки (банківські платежі, електронний документообіг) канонічний конверт доповнюється полем криптографічного підпису HMAC-SHA256 (`signature_bytes`).

Транслятор обчислює підпис від конкатенації `message_id + timestamp_utc_ms + payload_bytes` із використанням спільного симетричного ключа сервісу. Споживачі перевіряють підпис перед виконанням бізнес-логіки, що гарантує: повідомлення не було підроблено або спотворено сторонніми процесами під час проходження через проміжні брокери та черги.

## 8. Профілі серіалізації: Protobuf та Schema Registry

Для взаємодії з розподіленими брокерами (Apache Kafka, gRPC) канонічна модель транслюється в бінарний контракт Protocol Buffers v3.

```protobuf
syntax = "proto3";

package ua.retail.orders.v1;

enum CanonicalOrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;
  ORDER_STATUS_CREATED = 1;
  ORDER_STATUS_CONFIRMED = 2;
  ORDER_STATUS_SHIPPED = 3;
  ORDER_STATUS_CANCELLED = 4;
}

message OrderItem {
  uint64 item_id = 1;
  string sku = 2;
  uint32 quantity = 3;
  uint64 unit_price_cents = 4;
  uint64 tax_cents = 5;
}

message CanonicalOrderPayload {
  uint64 order_id = 1;
  string customer_ref = 2;
  string currency = 3;
  uint64 total_amount_cents = 4;
  CanonicalOrderStatus status = 5;
  repeated OrderItem items = 6;
  map<string, string> extensions = 7;
}

message CanonicalMessageEnvelope {
  string message_id = 1;
  string correlation_id = 2;
  string causation_id = 3;
  uint32 schema_version = 4;
  uint64 timestamp_utc_ms = 5;
  string origin_service = 6;
  string event_type = 7;
  string tenant_id = 8;
  string traceparent = 9;

  CanonicalOrderPayload payload = 10;
}
```

### Правила еволюції схем та версіонування у реєстрі (Schema Registry)

У промисловій експлуатації зміна структури канонічного повідомлення контролюється централізованим реєстром схем (*Schema Registry*) за такими обов'язковими правилами:

1. **Режим повної сумісності (Full Compatibility)**: нова версія схеми зобов'язана бути як прямо, так і зворотно сумісною. Старі сервіси повинні без помилок читати повідомлення, записані новими сервісами, а нові сервіси — читати старі повідомлення.
2. **Заборона видалення або перейменування тегів**: номери тегів полів у Protobuf (`= 1`, `= 2`) закріплюються назавжди. Видалення поля або зміна його числового тегу суворо заборонені. Застаріле поле позначається ключовим словом `deprecated` або `reserved`.
3. **Використання словника розширень (`extensions`)**: для передачі специфічних атрибутів, які ще не стандартизовані в загальній канонічній моделі, використовується поле `map<string, string> extensions`. Це дозволяє окремим командам експериментувати з новими атрибутами без необхідності негайного оновлення центрального контракту схеми для всієї компанії.
