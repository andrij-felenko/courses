Користувач маркетплейсу купує товар і натискає кнопку оплати. Веб-інтерфейс формує сучасний JSON-документ із полями `orderId`, `customerEmail`, `totalAmountCents` та масивом товарів. Але щоб замовлення було виконане, ці дані мають потрапити до шести різних підсистем: платіжного шлюзу (який вимагає двійковий Protobuf із фіксованими числовими тегами), головної складської системи ERP 2004 року випуску (яка приймає лише XML із SOAP-конвертами та специфічними назвами атрибутів на кшталт `CUST_REF_NO`), служби зовнішньої кур'єрської доставки (яка працює за протоколом EDIFACT із текстовими роздільниками сегментів), сервісу білінгу (де сума потрібна як дробове число у валюті рахунку), аналітичного озера даних (яке вичитує події у форматі Apache Avro зі зміїним регістром полів `total_amount_cents`) та підсистеми боротьби з шахрайством (яка очікує стиснутий бінарний MsgPack).

Якщо кожен із цих сервісів спробує спілкуватися з іншими напряму, розробники зіткнуться з комбінаторним вибухом складності.

Для прямого зв'язку `N` незалежних систем кожна підсистема повинна вміти розбирати формати всіх інших учасників обміну. Математично кількість необхідних двосторонніх конвертерів визначається числом пар:

```
K = N · (N − 1)
```

Для 8 систем це вимагає розробки, тестування та постійної підтримки `8 · 7 = 56` унікальних адаптерів. Коли через рік компанія підключає дев'яту систему (наприклад, нового міжнародного логістичного партнера), інженери змушені написати ще 16 нових конвертерів — по два для кожної з наявних систем. Найгірше те, що будь-яка внутрішня зміна схеми даних або перейменування одного поля в складській системі миттєво ламає 8 сторонніх конвертерів, розкиданих по різних репозиторіях і командах.

Розподілена система перетворюється на крихке «спагеті інтеграцій», де кожне оновлення релізу загрожує зупинкою всього бізнесу.

## Анатомія патерну Message Translator: розчеплення форматів

Щоб розірвати комбінаторну залежність між форматами джерел та одержувачів, у теорію розподіленої інтеграції введено патерн **Message Translator (Транслятор повідомлень)**.

Транслятор — це спеціалізований посередник або компонент-фільтр, який перетворює повідомлення з формату системи-відправника у формат, очікуваний системою-отримувачем, зберігаючи незмінним вихідний семантичний зміст бізнес-наміру.

![Порівняння прямої інтеграції Point-to-Point з експоненційним зростанням зв'язків та централізованої канонічної моделі з лінійною кількістю трансляторів](/book/programming/distributed-systems/message-translator/img/point-to-point-vs-canonical.svg)
*При переході від зв'язків кожен-з-кожним до єдиного проміжного формату кількість необхідних адаптерів скорочується з O(N²) до O(N). Кожна система відповідає лише за взаємодію з канонічним контрактом.*

Трансляція ніколи не є простою зміною текстового розширення файлу. Вона складається з трьох послідовних рівнів перетворення, кожен із яких розв'язує власний клас інженерних несумісностей:

```
┌────────────────────────────────────────────────────────────────────────────┐
│                    ТРИ РІВНІ ТРАНСЛЯЦІЇ ПОВІДОМЛЕННЯ                       │
├────────────────────────────────────────────────────────────────────────────┤
│ 1. Транспортно-синтаксичний шар (Transport & Wire Protocol)                │
│    • Декодування байтів: UTF-8 ⇄ Windows-1251 ⇄ EBCDIC                     │
│    • Зміна формату серіалізації: JSON ⇄ XML ⇄ Protobuf ⇄ Avro ⇄ CBOR       │
│    • Розпакування транспортних фреймів (HTTP/gRPC/AMQP/Kafka headers)      │
├────────────────────────────────────────────────────────────────────────────┤
│ 2. Структурний шар (Structural Hierarchy Mapping)                          │
│    • Сплощення вкладених об'єктів (Flattening: `user.addr.city` → `city`)  │
│    • Перегрупування масивів у асоціативні словники (Maps)                  │
│    • Відокремлення службових метаданих від корисного тіла (Payload)        │
├────────────────────────────────────────────────────────────────────────────┤
│ 3. Семантичний шар (Semantic Translation & Business Normalization)         │
│    • Конверсія типів та одиниць: $ 19.99 (float) ⇄ 1999 cents (uint64)     │
│    • Мапінг перерахувань (Enum): `"NEW"` ⇄ `101` ⇄ `ORDER_CREATED`         │
│    • Нормалізація дат: `"20/08/2026"` ⇄ `1787220000000 ms UTC Epoch`      │
│    • Збагачення ідентифікаторів (UUID ⇄ Legacy Customer Integer ID)        │
└────────────────────────────────────────────────────────────────────────────┘
```

Розглянемо кожен рівень детально.

### 1. Транспортно-синтаксичний шар

На цьому рівні транслятор працює як бінарний декодер. Він приймає сирий потік байтів із мережевого сокета або черги повідомлень, перевіряє цілісність контрольної суми CRC, визначає кодування символів та перетворює послідовність байтів на типізоване синтаксичне дерево в оперативній пам'яті.

Якщо відправник надіслав XML-документ у застарілому однобайтному кодуванні Windows-1251, транслятор перекодовує символи у валідний Юнікод UTF-8, відсікає мітки порядку байтів (BOM) та розбирає XML-теги без внесення змін у бізнес-значення полів.

### 2. Структурний шар

Різні технологічні стеки структурують однакові сутності по-різному. Реляційна система зберігає адресу клієнта у вигляді окремого плоского списку полів (`street_name`, `building_no`, `zip_code`), документна база даних оперує глибоко вкладеними об'єктами (`customer: { shipping: { address: { ... } } }`), а протокол EDI передає дані у вигляді позиційних сегментів, розділених символом `+`.

Структурний транслятор перегруповує ієрархію: він витягує дані з вкладених вузлів, зшиває розділені масиви та очищає корисне навантаження від специфічних обгорток транспортного протоколу (наприклад, тегів `<SOAP-ENV:Body>` або конвертів AWS SNS).

### 3. Семантичний шар

Це найбільш відповідальна стадія трансляції, де дані набувають точного бізнес-значення. Саме тут виправляються концептуальні розбіжності між системами:
- **Перетворення грошових одиниць**: переведення неточних чисел із плаваючою комою у строго фіксовані цілі копійки (`1999 cents`).
- **Словниковий мапінг статусів**: перетворення рядка `"PAID"` або магічного числа `104` на суворе канонічне перерахування `CanonicalOrderStatus::Confirmed`.
- **Нормалізація часових поясів**: перетворення локального рядка часу без часового поясу в абсолютну мітку часу Unix Epoch у мілісекундах відносно нульового меридіана UTC.

Детальна історія того, як індустрія пройшла шлях від перших нічних batch-скриптів і бінарного маршалінгу CORBA до формалізації патернів Хопе та сучасної мікросервісної архітектури, розкрита окремо: [еволюція інтеграційних патернів та подолання хаосу спагеті](book:programming/distributed-systems/message-translator/hist-integration-evolution.md).

## Споріднені патерни трансформації: Enricher, Filter, Claim-Check

У складних інтеграційних потоках транслятор рідко працює як ізольована функція типу `f(A) -> B`. Він тісно співпрацює з трьома іншими патернами трансформації з каталогу Enterprise Integration Patterns:

```
┌────────────────────────────────────────────────────────────────────────────┐
│                    СІМЕЙСТВО ПАТЕРНІВ ТРАНСФОРМАЦІЇ ДАНИХ                  │
├────────────────────────────────────────────────────────────────────────────┤
│ 1. Content Enricher (Збагачувач змісту)                                    │
│    Вхід: { "order_id": 100, "cust_id": 42 }                               │
│    Дія : Запит у кеш/БД за даними клієнта 42 (Email, Податковий номер)     │
│    Вихід: { "order_id": 100, "customer": { "email": "a@b.ua", ... } }      │
├────────────────────────────────────────────────────────────────────────────┤
│ 2. Content Filter (Фільтр змісту)                                          │
│    Вхід: Повний платіжний документ із номером картки, CVV та паспортними   │
│    Дія : Видалення чутливих атрибутів згідно з вимогами безпеки PCI-DSS    │
│    Вихід: Очищений документ із маскованим номером: `****-****-****-1234`   │
├────────────────────────────────────────────────────────────────────────────┤
│ 3. Claim Check (Квитанція камери схову)                                   │
│    Вхід: Повідомлення з важким PDF-сканом договору на 50 МБ                │
│    Дія : Збереження PDF у S3-сховищі, заміна бінарника на URL-посилання    │
│    Вихід: Легке канонічне повідомлення з посиланням: `s3://docs/doc42.pdf` │
└────────────────────────────────────────────────────────────────────────────┘
```

- **Content Enricher (Збагачувач)**: застарілі системи часто публікують так звані «тонкі повідомлення» (*Thin Messages*), які містять лише числові ключі без описових атрибутів. Якщо цільовому сервісу сповіщень потрібна електронна пошта клієнта, транслятор під час обробки пакета звертається до локального кешу Redis або сервісу профілів, збагачує об'єкт потрібними полями та формує повне канонічне повідомлення.
- **Content Filter (Фільтр)**: протилежність збагачувачу. Коли повідомлення передається у зовнішній партнерський контур або аналітичне сховище, транслятор-фільтр видаляє конфіденційні банківські реквізити, паролі та персональні дані (GDPR), залишаючи лише дозволений піднабір полів.
- **Claim Check (Квитанція)**: передача важких бінарних файлів безпосередньо через чергу повідомлень перевантажує оперативну пам'ять брокера. Транслятор вивантажує файл у хмарне сховище (AWS S3, MinIO), а в канонічний конверт записує лише контрольний хеш та URI файлу.

## Канонічна модель даних (Canonical Data Model, CDM)

Якщо створювати окремий транслятор для кожної пари взаємодіючих систем, загальна складність архітектури все одно залишиться на рівні `O(N^2)`. Щоб звести складність інтеграції до лінійної, патерн *Message Translator* поєднують із концепцією **канонічної моделі даних** (англ. *Canonical Data Model, CDM*).

Канонічна модель — це уніфікований, узгоджений у межах організації формат даних, який визначає спільну мову спілкування між усіма підсистемами.

```
Транслятори без CDM:            K = N · (N − 1)  [квадратична складність O(N²)]
Транслятори з канонічною CDM:   K = 2 · N        [лінійна складність O(N)]
```

Замість того, щоб кожна система знала про формати всіх своїх сусідів, кожен сервіс реалізує рівно два адаптери:
1. **Вхідний транслятор (Inbound Translator)**: транслює повідомлення з власного пропрієтарного формату системи в канонічну модель.
2. **Вихідний транслятор (Outbound Translator)**: транслює канонічне повідомлення з внутрішньої шини у формат, зрозумілий цільовому сервісу.

Коли в екосистему додається нова 9-та підсистема, розробникам потрібно створити лише 2 нових транслятори (вхідний і вихідний до канонічної моделі). Решта 8 систем продовжують працювати без найменших змін, навіть не знаючи про появу нового учасника обміну.

### Розділення на конверт і корисне навантаження

Канонічне повідомлення завжди будується з двох чітко розмежованих частин:

1. **Канонічний конверт (Canonical Envelope)**: стандартизований набір метаданих, спільний для абсолютно всіх типів повідомлень у системі. Конверт містить:
   - `message_id`: унікальний ідентифікатор конкретного фізичного повідомлення (UUIDv4) для дедуплікації на стороні [ідемпотентного консюмера](book:programming/idempotency).
   - `correlation_id`: наскрізний ідентифікатор бізнес-транзакції для наскрізного трасування крізь десятки мікросервісів.
   - `causation_id`: ідентифікатор події, яка безпосередньо породила поточне повідомлення.
   - `schema_version`: версія схеми даних для підтримки еволюції контрактів у [schema-registry](book:programming/schema-registry).
   - `timestamp_utc_ms`: точний час генерації події за шкалою UTC.
   - `traceparent`: заголовок розподіленого трасування стандарту W3C Trace Context.

2. **Корисне навантаження (Canonical Payload Body)**: строго типізована бізнес-структура (наприклад, `OrderPlacedEvent` або `PaymentSettledEvent`), яка валідується відповідно до контракту схеми.

Повна технічна специфікація полів канонічного конверта, двійкове вирівнювання пам'яті, матриця статусів та інтерфейси для мов C/C++ задокументовані у довідці: [повна специфікація канонічного конверта та інтерфейс модуля трансляції](book:programming/distributed-systems/message-translator/api-canonical-schema.md).

## Пастка канонічної моделі та відповідь Domain-Driven Design

На хвилі популярності сервісно-орієнтованої архітектури (SOA) та сервісних шин підприємства (ESB) у середині 2000-х років великі корпорації спробували створити **єдину універсальну канонічну модель для всієї організації** (*Enterprise-Wide Canonical Schema*).

Ця спроба зазнала нищівного фіаско і призвела до появи антипатерну, відомого як **«пастка канонічної моделі»** (*The Canonical Model Trap*).

![Порівняння антипатерну глобальної супер-схеми підприємства з прагматичними локальними канонічними моделями за межами обмежених контекстів](/book/programming/distributed-systems/message-translator/img/canonical-model-trap-vs-bounded-context.svg)
*Спроба створити єдину модель усього підприємства призводить до роздутих об'єктів та блокування релізів. Сучасна архітектура будує локальні канонічні контракти в межах конкретних обмежених контекстів.*

Глобальна супер-схема не працює з трьох об'єктивних причин:

1. **Семантичний розрив (Semantic Dissonance)**: одне й те саме слово в різних підрозділах бізнесу означає зовсім різні сутності. Для сервісу аутентифікації «Користувач» — це `email`, хеш пароля та прапорець двофакторної авторизації. Для відділу маркетингу «Клієнт» — це історія переглядів, рекламні сегменти та згода на отримання розсилок. Для служби доставки «Клієнт» — це фізична адреса, код під'їзду та номер телефону кур'єра. Спроба об'єднати ці вимоги в одну структуру породжує гігантський «божественний об'єкт» (*God Object*) із сотнями необов'язкових полів, де кожному окремому мікросервісу потрібно лише 5% даних.
2. **Бюрократичний параліч змін**: якщо центральна схема одна на всю компанію, будь-яка спроба однієї команди додати нове поле вимагає погодження з десятком інших відділів. Цикл релізу розтягується на місяці через страх зламати суміжні системи.
3. **Обчислювальні накладні витрати**: десеріалізація та валідація надлишкових гігантських XML- або JSON-схем створюють величезні затримки на кожному вузлі маршрутизації.

### Рішення: Обмежені контексти (Bounded Contexts) та захисний шар (ACL)

Сучасна архітектура, заснована на принципах предметно-орієнтованого проєктування (*Domain-Driven Design, DDD*), розв'язує цю проблему через поділ системи на **обмежені контексти** (*Bounded Contexts*).

Замість однієї всесвітньої схеми кожна доменна область (Замовлення, Доставка, Білінг, Склад) розробляє власну **локальну канонічну модель**, яка ідеально відображає її внутрішню термінологію (*Ubiquitous Language*).

Коли чистий внутрішній мікросервіс змушений взаємодіяти із застарілою або неконтрольованою зовнішньою системою, транслятор вбудовується як складова патерну **Anti-Corruption Layer (Захисний шар, ACL)**.

![Архітектура захисного шару Anti-Corruption Layer: транслятор на межі контексту захищає внутрішню модель від проникнення застарілих концепцій](/book/programming/distributed-systems/message-translator/img/anti-corruption-layer-ddd.svg)
*Захисний шар (ACL) ізолює чисту доменну модель. Транслятор бере на себе всю брудну роботу з перетворення чужих типів і статусів, не дозволяючи зовнішньому хаосу забруднити бізнес-логіку.*

Захисний шар розміщується на межі контексту і виконує роль активного брандмауера:
- Він приймає пакети від сторонніх систем через [адаптери портів](book:programming/hexagonal-architecture).
- Транслятор очищає дані, відкидає зайві артефакти застарілих форматів і транслює чужі структури у чисті внутрішні об'єкти-значення (*Value Objects*) та доменні сутності (*Entities*).
- Внутрішня бізнес-логіка оперує виключно власними строго типізованими класами, залишаючись повністю ізольованою від змін у зовнішньому світі.

## Безстатусні проти трансляторів зі станом (Stateless vs Stateful)

Залежно від складності необхідної трансформації, транслятори діляться на дві категорії за способом управління пам'яттю та станом:

### 1. Безстатусні транслятори (Stateless Translators)

Працюють як чисті математичні функції: результат обробки повідомлення залежить виключно від байтів поточного вхідного пакета.
- **Властивості**: миттєва горизонтальна масштабованість (можна запустити 100 паралельних воркерів без координації), відсутність потреби в локальних дисках або базах даних, нульовий стан після перезапуску.
- **Застосування**: пряма конверсія синтаксису (JSON у Protobuf), перерахунок валютних копійок, мапінг статусних перерахувань.

### 2. Транслятори зі станом (Stateful Translators)

Необхідні у випадках, коли одне канонічне повідомлення формується з кількох розрізнених вхідних пакетів або коли джерело розбиває велике замовлення на окремі потокові події.
- **Патерни Aggregator та Splitter**: транслятор-агрегатор накопичує окремі рядки замовлення (`OrderLineItem`) у локальному сховищі стану (вбудованій базі даних RocksDB або розподіленому кеші Redis) протягом заданого часового вікна (*Time Window*) і формує єдине канонічне замовлення `OrderPlaced` лише після отримання маркера завершення.
- **Стійкість до збоїв**: транслятор зі станом фіксує свій прогрес у журналі випереджального запису (WAL), що дозволяє відновити стан буфера після аварійного перезапуску контейнера без дублювання або втрати агрегованих даних.

## Топології розміщення транслятора в розподіленій системі

Залежно від вимог до продуктивності, затримки (*latency*) та автономності команд, транслятор повідомлень може бути розгорнутий в одній із чотирьох архітектурних топологій:

```
1. Вбудована бібліотека (In-Process Library)
   [Мережа] ──► [ Consumer ──► ( In-Process Translator ) ──► Domain Logic ]
   • Затримка: мінімальна (0 додаткових мережевих стрибків)
   • Ресурси : спільна пам'ять процесу

2. Окремий сервіс трансляції (Dedicated Microservice)
   [Вхідна черга A] ──► [ Translator Service Cluster ] ──► [ Канонічна черга B ]
   • Затримка: +1 мережевий стрибок (+1..3 мс)
   • Переваги: незалежне горизонтальне масштабування, ізоляція аварій

3. Сайдкар у контейнері (Sidecar / Envoy Filter)
   ┌─── Kubernetes Pod ──────────────────────────────────────────────────┐
   │ [ Sidecar Translator (Envoy/C++) ] ──(localhost)──► [ Main App ]    │
   └─────────────────────────────────────────────────────────────────────┘
   • Затримка: субмілісекундна (Unix Domain Socket / Localhost)
   • Переваги: мовна незалежність основного додатка

4. Шлюз на межі периметра (Edge / API Gateway)
   [Зовнішній клієнт] ──► [ API Gateway Translator ] ──► [ Внутрішня шина gRPC ]
   • Затримка: виконується безпосередньо під час первинного прийому запиту
   • Переваги: не пропускає невалідований трафік у внутрішню мережу
```

- **In-Process Library**: транслятор реалізовано як статичну або динамічну бібліотеку на мовах C/C++ чи Rust, яка компілюється безпосередньо в бінарник мікросервісу. Це надає максимально можливу продуктивність (сотні тисяч операцій на секунду на ядро) і нульову мережеву затримку.
- **Dedicated Service**: транслятор запускається як незалежний пул воркерів у Kubernetes. Ця топологія ідеально підходить для пакетних або асинхронних черг (Kafka, RabbitMQ), де потік вхідних повідомлень ізолюється від внутрішніх споживачів.
- **Sidecar Proxy**: транслятор виконується в окремому контейнері всередині того самого Pod у Kubernetes поруч із основним сервісом. Сайдкар перехоплює вхідний трафік, виконує трансформацію та передає чисті дані основному додатку через локальний сокет `localhost`. Це дозволяє писати бізнес-логіку на високорівневих мовах (Python, Node.js, Go), покладаючи важкі низькорівневі трансформації на високопродуктивний C++ сайдкар.

## Анатомія конвеєра трансляції та обробка відмов

На практиці транслятор повідомлень проєктується як строго послідовний конвеєр (*pipeline*), де кожен етап перевіряє конкретний тип інваріантів і має чітко визначений маршрут обробки помилок.

![Послідовні стадії конвеєра транслятора: від розпакування вхідного пакета та синтаксичного парсингу до семантичного мапінгу, валідації та ізоляції помилок у DLQ](/book/programming/distributed-systems/message-translator/img/translator-pipeline-anatomy.svg)
*Помилка на будь-якій стадії конвеєра не повинна викликати аварію процесу або зупиняти чергу. Пошкоджений пакет негайно упаковується в карантинний конверт DLQ зі збереженням діагностичного контексту.*

Розглянемо шлях повідомлення крізь конвеєр крок за кроком:

### Стадія 1: Ingress та розпакування конверта

Транслятор вичитує сирі байти з черги або сокета. Він витягує заголовки транспортного протоколу (ідентифікатори трасування, мітки часу, контрольні суми) та відокремлює метадані від сирого бізнес-навантаження.

### Стадія 2: Синтаксичний аналіз та базова валідація

Парсер перевіряє структурну коректність формату: чи є вхідний потік валідним JSON, чи закриті всі теги в XML, чи не пошкоджено магічні байти бінарного фрейму.
- Якщо байти пошкоджено (наприклад, пакет обірвано через мережевий збій), парсер зупиняє розбір.
- Пакет негайно направляється у гілку формування карантинного запису з кодом `ERR_SYNTAX_MALFORMED`.

### Стадія 3: Семантичний мапінг та збагачення (Enrichment)

Транслятор перевіряє бізнес-правила: переводить статуси за допомогою таблиць відповідності, конвертує коди валют, нормалізує формат телефонних номерів та перераховує часові пояси.
- Якщо системі потрібні додаткові дані, яких немає у вихідному повідомленні (наприклад, застаріла система передала лише числовий код клієнта `cust_id = 4812`, а канонічній моделі потрібен глобальний UUID), транслятор звертається до розподіленого кешу за патерном *Content Enricher*.
- Якщо зовнішній довідник тимчасово недоступний, повідомлення може бути відправлено на обмежену кількість повторів (*retries*) з експоненційним відступом.

### Стадія 4: Побудова канонічного DTO та контроль інваріантів

Формується чистий канонічний об'єкт. Виконується фінальна перевірка доменних інваріантів: загальна сума не може бути від'ємною, список товарів не може бути порожнім, обов'язкові поля не можуть бути `null`. Порушення інваріанту свідчить про логічну помилку в системі-відправнику і веде до перенаправлення пакета в карантин.

### Стадія 5: Серіалізація та публікація в цільову чергу

Валідний канонічний об'єкт серіалізується у цільовий формат (двійковий Protobuf або компактний бінарний фрейм) і публікується у внутрішню чергу чи розподілений топік брокера (наприклад, Apache Kafka).

Повноцінний працюючий код конвеєра на мовах C та C++ з ручним контролем пам'яті, типізованими структурами `std::expected` та детальною обробкою винятків наведено у практичному посібнику: [реалізація надійного транслятора повідомлень мовами C та C++ з карантином DLQ](book:programming/distributed-systems/message-translator/proj-message-translator.md).

## Еволюція схем і правила сумісності на практиці

Оскільки в реальних системах сервіси оновлюються асинхронно різними командами, транслятор повинен гарантувати стабільність роботи в умовах зміни схем даних.

Централізований [Schema Registry](book:programming/schema-registry) забезпечує один із трьох режимів сумісності:

```
1. Зворотна сумісність (Backward Compatibility)
   • Споживач оновлено до версії V2 ──► успішно читає старі повідомлення V1
   • Вимога: нові поля обов'язково мають значення за замовчуванням (Default values).

2. Пряма сумісність (Forward Compatibility)
   • Споживач старої версії V1 ──► успішно читає нові повідомлення V2
   • Вимога: старий сервіс ігнорує нові невідомі поля (Tolerant Reader).

3. Повна сумісність (Full Compatibility)
   • Одночасне дотримання прямої та зворотної сумісності (Full = Backward + Forward).
   • Заборонено: видалення полів, зміна типів даних, зміна числових тегів Protobuf.
```

Транслятор на практиці реалізує правило збереження невідомих полів (*Unknown Fields Preservation*). Якщо зовнішнє джерело додає новий атрибут `delivery_instructions`, який ще не описаний у поточній версії канонічного DTO, транслятор не відкидає його. Він упаковує цей фрагмент у спеціальну карту розширень `map<string, string> extensions`, зберігаючи байти для тих сервісів наступного покоління, які вже готові їх обробляти.

## Карантин отруйних повідомлень (Poison Pills) та стратегії Replay

Одне з головних призначень транслятора — захист внутрішніх мікросервісів від так званих «отруйних пігулок» (*Poison Pills*). Отруйне повідомлення — це пакет, який синтаксично виглядає валідним, але через внутрішній дефект призводить до аварійного завершення споживача або нескінченного циклу обробки.

Якщо транслятор зустрічає повідомлення з від'ємною ціною або пошкодженим UTF-8, наївна спроба виконати автоматичний повтор (*Retry*) призведе до катастрофи:
- Транслятор зациклюється, повторюючи обробку 10 разів на секунду.
- Черга блокується, зміщення (*offset*) не просувається вперед.
- Накопичується гігантський лаг черги (*Consumer Lag*), і вся система перестає обробляти навіть повністю валідні замовлення інших клієнтів.

Правильна стратегія ізоляції включає такі кроки:
1. **Негайне відсікання термінальних помилок**: синтаксичні та семантичні помилки не підлягають автоматичним повторам. Пакет одразу маркується як дефектний.
2. **Формування діагностичного запису DLQ**: пошкоджені байти разом із кодом помилки, стектрейсом, міткою часу та оригінальними заголовками записуються в карантинний топік [мертвої черги (Dead Letter Queue)](book:programming/dead-letter-queue).
3. **Фіксація зміщення (Commit Offset)**: транслятор підтверджує брокеру, що проблемний пакет вилучено з основного конвеєра, і миттєво переходить до обробки наступного повідомлення в черзі.
4. **Конвеєр повторного програвання (Replay Pipeline)**: після того як розробники виправлять помилку в схемі або налаштують таблиці мапінгу, спеціальна фонова утиліта зчитує відхилені повідомлення з DLQ і публікує їх назад у вхідний топік транслятора, забезпечуючи нульову втрату бізнес-транзакцій.

## Криптографічний захист та перевірка цілісності трансляцій

Під час міжсистемної взаємодії через ненадійні публічні канали зв'язку або партнерські шлюзи транслятор виступає рубежем перевірки автентичності та цілісності переданих даних.

1. **Перевірка вхідного підпису (Ingress HMAC Verification)**:
   - Зовнішнє джерело формує криптографічний підпис від сирого корисного навантаження (наприклад, `HMAC-SHA256(secret_key, raw_bytes)`).
   - Транслятор перед початком парсингу обчислює локальний хеш і порівнює його з заголовком `X-Signature` за константний час `O(1)` за допомогою функції `CRYPTO_memcmp` для захисту від атак за часом (*Timing Attacks*).
   - Якщо підписи не збігаються, пакет негайно відхиляється без витрат ресурсів процесора на десеріалізацію.
2. **Формування внутрішнього цифрового підпису (Egress Token Signing)**:
   - Після успішної трансформації у канонічну модель транслятор підписує сформований канонічний пакет власним асиметричним закритим ключем або додає криптографічний токен довіри.
   - Це гарантує внутрішнім сервісам, що повідомлення дійсно пройшло повний контур санітизації, валідації та не було підроблене зловмисниками всередині периметра локальної мережі.

## Продуктивність, виділення пам'яті та нуль-копіювання

У високонавантажених системах, де транслятор обробляє десятки тисяч повідомлень за секунду, операції трансформації можуть стати головним вузьким місцем усієї платформи (*bottleneck*).

Основні фактори, що визначають швидкодію транслятора:

1. **DOM-парсери проти потокових парсерів (Streaming Parsers)**:
   - DOM-парсери (наприклад, класичний `DOMDocument` для XML або `cJSON_Parse` для JSON) вичитують весь документ повністю і будують дерево об'єктів у динамічній пам'яті. Це вимагає в 5–10 разів більше пам'яті, ніж розмір самого повідомлення, і створює колосальне навантаження на збирач сміття (*Garbage Collector*) або системний алокатор `malloc`.
   - Потокові SAX/StAX парсери або нуль-копіювальні парсери (наприклад, `simdjson` чи Protobuf) зчитують байти послідовно в один прохід без виділення об'єктів під проміжні вузли.
   - Використання векторних інструкцій процесора (SIMD AVX2 / AVX-512 та ARM NEON) дозволяє парсити JSON-структури на швидкості 2.5–3.5 ГБ/с на одне процесорне ядро, знаходячи лапки, роздільники та числа за один машинний такт без побайтового перебору в циклах.
2. **Техніка нуль-копіювання (Zero-Copy Processing) та вирівнювання кеш-ліній**:
   - Замість виділення окремого динамічного буфера під кожне рядкове поле транслятор використовує структури типу `std::string_view` (вказівник на початок підрядка у вхідному буфері + довжина).
   - Пам'ять виділяється лише один раз для кінцевого результуючого пакету.
   - Структури даних у пам'яті вирівнюються за межами 64-байтних ліній кешу процесора L1/L2 (`alignas(64)`), що повністю усуває ефект хибного розділення пам'яті (*false sharing*) під час паралельної обробки різних партицій черги різними ядрами CPU.
3. **Локальні буфери потоку (Thread-Local Memory Pools)**:
   - Робочі потоки транслятора використовують попередньо виділені статичні арени пам'яті розміром 64–128 КБ. Це усуває конкуренцію за м'ютекси глобального алокатора (*malloc lock contention*) під час паралельної обробки повідомлень на багатьох ядрах процесора.
   - Скидання вказівника арени на початок після публікації пакету в брокер займає лише одну інструкцію запису в регістр замість сотень викликів `free()`, що забезпечує стабільні низькі затримки без просідань на збирання сміття.

## Простеження через eBPF, трасування W3C та метрики моніторингу

У промисловому середовищі Linux роботу транслятора можна контролювати на рівні ядра операційної системи за допомогою утиліт eBPF (`bpftrace`) та інтерфейсів `procfs`.

```
Вимірювання часу трансляції через eBPF tracepoint:
  bpftrace -e '
    uprobe:/usr/bin/translator:translator_process_packet { @start[tid] = nsecs; }
    uretprobe:/usr/bin/translator:translator_process_packet /@start[tid]/ {
      @latency_us = hist((nsecs - @start[tid]) / 1000);
      delete(@start[tid]);
    }'
```

Аналіз такого гістограмного розподілу дозволяє виявити приховані затримки:
- Якщо медіанний час виконання операції трансляції становить 12 мікросекунд, але 99-й перцентиль (`p99`) підскакує до 45 мілісекунд, це сигналізує про періодичне блокування робочих потоків під час запитів до зовнішніх довідників або про конкуренцію за системні блокування виділення пам'яті.
- Моніторинг метрик `messages_translated_total` та `dlq_messages_total` у Prometheus дає миттєву картину справності інтеграційних каналів у режимі реального часу.

## Інженерні компроміси та практичні критерії вибору

Вибір архітектури інтеграції завжди є зважуванням інженерних компромісів між гнучкістю, швидкістю розробки та продуктивністю системи.

| Критерій порівняння | Пряма інтеграція (Point-to-Point) | Централізована канонічна модель (CDM) | Локальний захисний шар (DDD ACL) |
| :--- | :--- | :--- | :--- |
| **Кількість систем** | Оптимально для 2–3 тісно зв'язаних сервісів. | Ідеально для 10–50 сервісів у межах підприємства. | Оптимально для інтеграції мікросервісів з Legacy та 3rd-party API. |
| **Складність зв'язків** | Квадратична `O(N²)`. Швидкий старт, але катастрофічне масштабування. | Лінійна `O(N)`. Фіксовані витрати на підключення нових систем. | Локалізована `O(1)` для кожного обмеженого контексту. |
| **Зачеплення схем (Coupling)** | Максимальне. Зміна однієї системи вимагає правок у всіх клієнтах. | Мінімальне між сервісами, але високе зачеплення за центральну схему. | Повна ізоляція. Внутрішня доменна модель захищена від зовнішніх змін. |
| **Накладні витрати CPU** | Нульові або мінімальні (прямий виклик). | Подвійна трансляція: `A → CDM → B` (додаткові мікросекунди затримки). | Одинарна трансляція на межі входу в контекст. |
| **Управління змінами (Governance)** | Децентралізоване, але хаотичне. | Вимагає суворого версіонування через Schema Registry. | Повна автономія окремих продуктових команд. |

Практичне правило архітектора: **використовуйте прямі адаптери лише тоді, коли систем не більше трьох і вони належать одній команді; впроваджуйте локальні канонічні моделі та транслятори Anti-Corruption Layer на межах доменних контекстів, щойно система починає масштабуватися.**
