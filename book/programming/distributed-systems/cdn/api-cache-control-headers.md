# 📋 Протокольний контракт HTTP-кешування та API керування CDN

Довідник протокольних заголовків керування кешуванням (RFC 9111, RFC 9211, RFC 9213), специфікацій сурогатних ключів, обробки часткового контенту, ранніх підказок (Early Hints) та API інвалідації на периферійних вузлах CDN визначає точний контракт взаємодії між сервером-джерелом (Origin), периферійним проксі (Edge) та клієнтським браузером.

---

### 1. Заголовки сімейства Cache-Control (RFC 9111)

Заголовок `Cache-Control` є основним механізмом узгодження поведінки кешування вздовж усього шляху передачі даних. Значення складається з розділеного комами переліку директив, які інтерпретуються клієнтськими браузерами, проміжними корпоративними проксі та публічними вузлами CDN.

| Директива | Цільовий рівень | Семантика та протокольна поведінка |
| :--- | :--- | :--- |
| `public` | Усі (Edge + Браузер) | Відповідь може кешуватися будь-яким проміжним вузлом, навіть якщо первинний HTTP-запит містив авторизаційний заголовок `Authorization`. |
| `private` | Лише кінцевий браузер | Відповідь є персоналізованою для конкретного користувача; проміжні CDN Edge-вузли **не мають права** зберігати її в загальному кеші. |
| `no-cache` | Усі | Відповідь **може** бути збережена в кеші, але проксі **зобов'язаний** виконати умовну валідацію (`ETag` або `Last-Modified`) на Origin перед кожною повторною видачею клієнту. |
| `no-store` | Усі | Сувора заборона будь-якого збереження вмісту в оперативній пам'яті або на накопичувачі. Проксі передає потік байтів наскрізно без збереження стану. |
| `max-age=<sec>` | Усі | Максимальний час свіжості ресурсу в секундах від моменту його генерації на сервері-джерелі. |
| `s-maxage=<sec>` | Shared Caches (CDN Edge) | Перевизначає значення `max-age` виключно для публічних спільних проксі (CDN). Клієнтський браузер ігнорує `s-maxage` та керується виключно `max-age`. |
| `must-revalidate` | Усі | Забороняє видачу застарілого (stale) ресурсу у разі втрати зв'язку з сервером-джерелом. Якщо перевірка свіжості неможлива, проксі повертає код `504 Gateway Timeout`. |
| `proxy-revalidate` | Shared Caches | Аналог `must-revalidate`, що діє виключно на проміжні CDN Edge-вузли, не обмежуючи поведінку браузера. |
| `stale-while-revalidate=<sec>` | Усі | Дозволяє Edge негайно віддати клієнту збережену застарілу копію протягом вказаного вікна секунд, одночасно ініціюючи асинхронний фоновий запит до Origin для оновлення кешу. |
| `stale-if-error=<sec>` | Усі | Дозволяє Edge видавати застарілий кеш, якщо сервер-джерело повертає помилку `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable` або `504 Gateway Timeout`. |
| `immutable` | Браузер | Повідомляє браузеру, що тіло відповіді гарантовано не зміниться протягом свого `max-age`. Браузер блокує генерацію умовних валідаційних запитів навіть при примусовому оновленні сторінки (F5). |

### 2. Заголовки цільового керування та розмежування рівнів (RFC 9213 / RFC 9211)

У багаторівневих інфраструктурах виникає потреба розділити правила кешування: наприклад, змусити браузер запитувати перевірку кожні 60 секунд, а периферійний проксі CDN утримувати копію протягом 30 днів. Для цього застосовуються спеціалізовані розширення.

#### `CDN-Cache-Control` та `Surrogate-Control`
Якщо сервер-джерело повертає заголовок `CDN-Cache-Control` або вендорний заголовок (наприклад, `Cloudflare-CDN-Cache-Control`, `Fastly-Orig-Cache-Control`), периферійний проксі CDN використовує директиви саме цього заголовка, а клієнтському браузеру транслює загальний `Cache-Control`.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=60
CDN-Cache-Control: max-age=86400, stale-while-revalidate=3600
Surrogate-Control: max-age=604800, stale-if-error=86400
```
*У цьому сценарії:*
1. Клієнтський браузер вважає ресурс свіжим рівно 60 секунд.
2. Периферійний вузол CDN L1 зберігає об'єкт 24 години (86 400 с) і має право протягом 1 години віддавати застарілий кеш у фоновому режимі ревалідації.
3. Регіональний щит Origin Shield L2 утримує об'єкт 7 днів (604 800 с) та маскує збої джерела протягом доби.

#### Тегування сутностей: `Surrogate-Key` та `Cache-Tag`
Для групової інвалідації ресурсів сервер маркує HTTP-відповіді простором логічних міток.

```http
Surrogate-Key: product-9481 category-laptops brand-lenovo currency-usd
```
```http
Cache-Tag: user-4412, checkout-flow, tenant-enterprise
```
*При зміні параметрів товару (наприклад, ціни ноутбука) система надсилає сигнал інвалідації за тегом `product-9481`, і проксі миттєво анулює всі пов'язані сторінки каталогу, віджети та API-відповіді в глобальній мережі.*

### 3. Варіативність контенту та заголовок `Vary`

Заголовок `Vary` інструктує CDN Edge створювати окремі слоти кешу для різних значень заголовків клієнтського запиту:

```http
Vary: Accept-Encoding, User-Agent, Origin
```

#### Небезпека вибуху варіативності (Vary Explosion):
Якщо бекенд встановлює `Vary: User-Agent`, проксі створить тисячі окремих копій одного й того самого файлу під кожну унікальну версію браузера, що обнулить коефіцієнт попадання в кеш (Cache Hit Ratio) та перевантажить пам'ять вузла.

**Правило нормалізації на Edge:**
Периферійний проксі зобов'язаний нормалізувати значення варіативних заголовків перед обчисленням кеш-ключа. Наприклад, заголовок `Accept-Encoding` згортається до трьох дискретних значень: `br`, `gzip` або `identity`.

### 4. Діагностичні та транзитні заголовки CDN

Периферійні проксі маркують транзитні запити та відповіді службовими метаданими, що дозволяє інженерам відстежувати маршрутизацію пакетів та стан кеш-рушія.

| Заголовок | Приклад значення | Призначення |
| :--- | :--- | :--- |
| `Age` | `Age: 342` | Час у секундах, який об'єкт провів у кеші CDN від моменту отримання або ревалідації. |
| `Via` | `1.1 edge-fra-1 (Cloudflare)` | Список проміжних проксі-серверів, крізь які пройшов пакет. |
| `CDN-Loop` | `cloudflare; count=1` (RFC 8586) | Запобігання нескінченним петлям перенаправлення трафіку між різними CDN-мережами. |
| `Cache-Status` | `Cache-Status: "EdgeCache"; hit; ttl=3600` (RFC 9211) | Стандартизований заголовок звітування про результат кешування (`hit`, `miss`, `fwd=uri`). |
| `X-Cache` | `X-Cache: HIT` / `X-Cache: MISS` | Пропрієтарний заголовок статусу кешу (HIT, MISS, STALE, REVALIDATED). |
| `X-Served-By` | `cache-kbp-ukbb-1` | Фізичний ідентифікатор сервера та локації, що згенерував відповідь. |

### 5. Обробка діапазонів байтів (Range Requests & RFC 7233)

Для потокового передавання важкого відеоконтенту та докачування файлів клієнти надсилають запити фрагментів:

```http
GET /videos/4k-stream.mp4 HTTP/1.1
Host: cdn.example.com
Range: bytes=1048576-2097151
If-Range: "etag-video-v1"
```

**Поведінка Edge:**
* Якщо повний відеофайл уже закешовано, Edge самостійно нарізає потрібний діапазон байтів і повертає статус `206 Partial Content` із заголовком `Content-Range: bytes 1048576-2097151/52428800`.
* Якщо файлу немає в кеші, просунуті CDN виконують фонове зчитування блоками фіксованого розміру (Chunked Slice Caching), щоб не завантажувати гігабайтний файл цілком заради запиту перших кілобайтів.

### 6. Ранні підказки (Early Hints, RFC 8297 та HTTP 103)

Для ліквідації часу простою браузера, поки сервер-джерело обчислює динамічний HTML-документ, CDN підтримує проміжну відповідь `103 Early Hints`:

```http
HTTP/1.1 103 Early Hints
Link: </assets/main.css>; rel=preload; as=style
Link: </assets/app.js>; rel=preload; as=script
Link: <https://fonts.gstatic.com>; rel=preconnect
```

Периферійний вузол миттєво повертає статус 103 клієнту, щойно отримує вхідний запит (або на основі статичних правил Edge), дозволяючи браузеру розпочати паралельне завантаження критичних стилів та встановлення TLS-рукостискання зі шрифтовими серверами ще до отримання першого байта основного коду `200 OK`.

### 7. Безпека кешування: атаки отруєння кешу та витік сесій

Некоректна конфігурація взаємодії CDN та Origin створює два критичні класи вразливостей:

1. **Отруєння кешу (Cache Poisoning):**
   Якщо бекенд змінює тіло відповіді на основі неключових заголовків (Unkeyed Headers, таких як `X-Forwarded-Host`, `X-Original-URL` або `Host`), зловмисник може надіслати запит із шкідливим значенням. Якщо CDN зберігає цю відповідь за стандартним ключем `GET /`, усі наступні користувачі завантажуватимуть скрипти зі стороннього домену атакуючого.
   * *Контракт захисту:* Усі заголовки, що впливають на генерацію відповіді, зобов'язані бути явно внесені або до директиви `Vary`, або нормалізуватися та відсікатися на Edge.

2. **Витік сесійних кук (Cookie Leakage):**
   Якщо динамічний ендпоінт повертає заголовок `Set-Cookie` поруч із директивою `Cache-Control: public, s-maxage=3600`, CDN збереже значення куки сесії першого користувача і віддаватиме її тисячам інших відвідувачів.
   * *Контракт захисту:* Периферійний проксі зобов'язаний автоматично видаляти заголовок `Set-Cookie` з будь-якої відповіді, яка зберігається в публічному кеші, або примусово переводити такий ресурс у режим `private / no-store`.

### 8. Контракт REST API для активної інвалідації (Purge API)

Коли стан даних у базі джерела змінюється, бекенд викликає REST API провайдера CDN для очищення кеш-записів на всіх периферійних вузлах світу.

#### Стратегії очищення:
* **Hard Purge (Жорстке видалення):** Повне фізичне видалення об'єкта зі сховищ RAM та NVMe. Наступний клієнтський запит гарантовано блокується в очікуванні відповіді від Origin.
* **Soft Purge (М'яка інвалідація):** Об'єкт позначається як застарілий (`stale`), але залишається на диску. Проксі негайно повертає його першому клієнту, паралельно запускаючи фонове оновлення (`stale-while-revalidate`), що усуває сплески латентності для користувачів.

#### Ендпоінт інвалідації:
`POST /v1/zones/{zone_id}/purge`

#### Схема JSON-запиту:
```json
{
  "purge_everything": false,
  "soft": true,
  "files": [
    "https://cdn.example.com/assets/app.js",
    {
      "url": "https://cdn.example.com/images/hero.webp",
      "headers": {
        "Origin": "https://example.com",
        "Accept-Encoding": "gzip, br"
      }
    }
  ],
  "tags": [
    "product-9481",
    "category-laptops"
  ],
  "hosts": [
    "api.example.com"
  ],
  "prefixes": [
    "https://cdn.example.com/videos/hls/stream-42/"
  ]
}
```

#### Параметри запиту:
* `purge_everything` (`boolean`, опціонально) — повне глобальне скидання всіх кешів зони (викликає масовий шторм запитів на Origin, застосовується лише у критичних аварійних випадках).
* `soft` (`boolean`, опціонально) — виконання м'якої інвалідації замість фізичного видалення записів.
* `files` (`array`, опціонально) — точкові абсолютні URL конкретних файлів з можливістю уточнення варіативних заголовків.
* `tags` (`array of strings`, опціонально) — інвалідація всіх об'єктів, помічених відповідними ключами `Surrogate-Key` або `Cache-Tag`.
* `prefixes` (`array of strings`, опціонально) — масове скидання всіх ресурсів, що починаються з вказаного шляху-префікса.

#### Відповідь сервера керування:
```json
{
  "success": true,
  "errors": [],
  "messages": [],
  "result": {
    "id": "purge_task_9c2b48e1a7",
    "status": "propagating",
    "estimated_propagation_ms": 115
  }
}
```
*Успішна відповідь повертає ідентифікатор задачі глобальної інвалідації, яка поширюється протоколом Pub/Sub по всіх точках присутності мережі протягом 100–150 мілісекунд.*
