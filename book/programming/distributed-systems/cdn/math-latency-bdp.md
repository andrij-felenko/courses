# 🧮 Фізика мережевої затримки, Bandwidth-Delay Product та пропускна здатність TCP

Математичний розрахунок затримки передачі пакетів, добутку пропускної здатності на затримку (Bandwidth-Delay Product, BDP), моделі пропускної здатності Матіса та аналіз коефіцієнта попадання в кеш (Cache Hit Ratio) пояснює, чому збільшення швидкості інтернет-каналу не здатне скоротити час завантаження сторінок без наближення сервера до клієнта, і як високий показник RTT накладає фізичне обмеження на швидкість протоколу TCP.

---

### Фізична межа поширення сигналу та Round Trip Time (RTT)

Час поширення сигналу в середовищі (Propagation Delay, `T_prop`) обмежений швидкістю світла у вакуумі `c ≈ 300 000` км/с. В оптоволоконному кабелі показник заломлення кварцового скла становить `n ≈ 1.47`, тому швидкість поширення світла в оптичній жилі (`v_fiber`) розраховується так:

```
v_fiber = c ÷ n
        = 300 000 км/с ÷ 1.47        [підстановка показника заломлення кварцу]
        ≈ 204 081 км/с               [швидкість фотонів в оптичному волокні]
```

Оптоволоконні магістралі не прокладаються ідеальними прямими лініями. Коефіцієнт непрямості траси (Cable Routing Factor) у середньому становить `k_route ≈ 1.35`. Для географічної відстані між клієнтом у Києві та сервером у Далласі (США) `d_geo ≈ 9 200` км довжина оптичного шляху складає `L = d_geo · k_route ≈ 12 420` км.

Розрахуємо мінімальний односторонній фізичний час польоту фотонів (`T_prop_oneway`):

```
T_prop_oneway = L ÷ v_fiber
              = 12 420 км ÷ 204 081 км/с   [ділення довжини траси на швидкість]
              ≈ 0.06085 с                  [переведення у секунди]
              = 60.85 мс                   [фізичний мінімум в один бік]
```

Повний час кругового обігу (Round Trip Time, `RTT_phys`):

```
RTT_phys = 2 · T_prop_oneway
         = 2 · 60.85 мс                    [час сигналу туди й назад]
         = 121.7 мс                        [фізичний мінімум без урахування активного обладнання]
```

З урахуванням комутаторів, маршрутизаторів, буферизації черг та оптоелектронної регенерації на трансокеанських підводних кабелях реальний виміряний `RTT_real` між Києвом і Далласом становить приблизно `180` мс.

Якщо ж клієнт у Києві звертається до локального вузла CDN (Edge PoP) у Києві або Франкфурті (`d_geo ≈ 1 500` км):

```
L_edge = 1 500 км · 1.35                   [коефіцієнт траси до регіонального PoP]
       = 2 025 км                          [довжина оптоволокна]

RTT_edge_phys = (2 · 2 025 км) ÷ 204 081 км/с
              = 4 050 км ÷ 204 081 км/с    [круговий обіг]
              ≈ 0.0198 с                   [секунди]
              ≈ 19.8 мс                    [реальний RTT з обладнанням: ~20-25 мс; локально в Києві: ~4-6 мс]
```

### Розрахунок затримки встановлення з'єднання: 3-RTT проти локального Edge

Класичний цикл відкриття безпечного HTTPS-з'єднання поверх TCP з протоколом TLS 1.3 та передачею першого HTTP GET-запиту вимагає послідовного проходження трьох фаз (3 RTT):

1. **TCP 3-Way Handshake:** `SYN` → `SYN-ACK` → `ACK` (1 RTT)
2. **TLS 1.3 Handshake:** `ClientHello + KeyShare` → `ServerHello + EncryptedExtensions + Certificate + Finished` (1 RTT)
3. **HTTP Request & First Response Byte (TTFB):** `GET /` → `HTTP 200 OK (First Chunk)` (1 RTT)

Загальний час до отримання першого байта корисних даних (Time To First Byte, `TTFB`):

```
TTFB = 3 · RTT + T_proc                    [де T_proc — час обробки запиту сервером]
```

Порівняємо сценарій прямого підключення до Origin (Даллас, `RTT = 180` мс) та сценарій з використанням периферійного CDN (Київський PoP, `RTT = 5` мс) за умови `T_proc = 20` мс:

**1. Пряме підключення до Origin (без CDN):**
```
TTFB_origin = 3 · 180 мс + 20 мс
            = 540 мс + 20 мс               [3 цикли RTT через океан]
            = 560 мс                       [понад пів секунди до першого байта]
```

**2. Підключення через Edge PoP CDN (кешована відповідь):**
```
TTFB_edge = 3 · 5 мс + 2 мс
          = 15 мс + 2 мс                   [3 цикли RTT до найближчого вузла]
          = 17 мс                          [у 33 рази швидше]
```

### Bandwidth-Delay Product (BDP) та обмеження пропускної здатності TCP

Добуток пропускної здатності на затримку (Bandwidth-Delay Product, `BDP`) визначає обсяг даних (у байтах), який одночасно перебуває «в дорозі» в оптичній магістралі між відправником і отримувачем:

```
BDP = C · RTT                              [де C — пропускна здатність каналу в байт/с, RTT — час обігу в секундах]
```

Для гігабітного інтернет-каналу (`C = 1 Гбіт/с = 125 000 000` байт/с) розрахуємо BDP для трансатлантичного з'єднання (`RTT = 0.180` с) та локального CDN Edge (`RTT = 0.005` с):

```
BDP_transatlantic = 125 000 000 байт/с · 0.180 с
                  = 22 500 000 байт        [множення швидкості на час затримки]
                  ≈ 21.46 МБ               [необхідний розмір TCP-вікна для повної утилізації гігабітного каналу]

BDP_edge = 125 000 000 байт/с · 0.005 с
         = 625 000 байт                    [множення для периферійного з'єднання]
         ≈ 610.35 КБ                       [достатнє вікно TCP для утилізації гігабіта]
```

Якщо розмір буфера прийому операційної системи або максимальне вікно перевантаження (`W_max`) обмежене величиною `64 КБ = 65 536 байтів` (стандартне вікно без опції TCP Window Scaling, RFC 7323), теоретична максимальна пропускна здатність TCP (`Throughput_max`) обмежена формулою:

```
Throughput_max = W_max ÷ RTT
```

Розрахуємо максимальну пропускну здатність для обох випадків:

```
Throughput_origin = 65 536 байтів ÷ 0.180 с
                  = 364 088 байт/с         [ділення максимального вікна на RTT]
                  ≈ 2.91 Мбіт/с            [критична деградація гігабітного каналу через затримку]

Throughput_edge = 65 536 байтів ÷ 0.005 с
                = 13 107 200 байт/с        [ділення вікна на локальний RTT]
                ≈ 104.86 Мбіт/с            [у 36 разів вища швидкість на тому самому вікні]
```

### Формула Матіса: вплив втрат пакетів на швидкість TCP

У реальних глобальних мережах передача пакетів супроводжується випадковими втратами (Packet Loss). Формула Метью Матіса (англ. *Matt Mathis*) визначає граничну пропускну здатність TCP за наявності втрат з імовірністю `p`:

```
Throughput_Mathis = (MSS · C_const) ÷ (RTT · √p)
```
де `MSS = 1460` байтів (Maximum Segment Size), `C_const ≈ 1.22` для алгоритму Reno/Cubic, `RTT` у секундах, `p` — частка втрачених пакетів.

Зіставимо швидкість при ймовірності втрат `p = 1% = 0.01` (типовий рівень для трансконтинентального інтернету):

```
Throughput_loss_origin = (1460 · 1.22) ÷ (0.180 · √0.01)
                       = 1781.2 ÷ (0.180 · 0.1)        [обчислення квадратного кореня з втрат]
                       = 1781.2 ÷ 0.018                [добуток затримки на корінь втрат]
                       ≈ 98 955 байт/с                 [байтів за секунду]
                       ≈ 0.79 Мбіт/с                   [катастрофічне падіння швидкості на великому RTT]

Throughput_loss_edge = (1460 · 1.22) ÷ (0.005 · √0.01)
                     = 1781.2 ÷ (0.005 · 0.1)          [обчислення для локального CDN]
                     = 1781.2 ÷ 0.0005                 [добуток для короткого RTT]
                     ≈ 3 562 400 байт/с                [байтів за секунду]
                     ≈ 28.50 Мбіт/с                    [у 36 разів більша швидкість навіть при втратах]
```

### Динаміка фази повільного старту (TCP Slow Start)

Під час встановлення нового TCP-з'єднання протокол починає передачу з початкового вікна перевантаження (Initial Congestion Window, `initcwnd ≈ 10` MSS, де MSS = 1460 байтів, тобто `~14.6 КБ`).

На кожному кроці RTT вікно подвоюється (`cwnd(k) = initcwnd · 2^k`) до моменту досягнення BDP або порогу втрати пакетів. 

Розрахуємо час, необхідний для передачі веб-бандлу розміром `S = 1.5 МБ = 1 572 864 байти` (~1078 сегментів MSS) без втрат пакетів:

Кількість сегментів, переданих на кожному RTT:
- RTT 1: `10` сегментів (14.6 КБ), накопичено: 14.6 КБ
- RTT 2: `20` сегментів (29.2 КБ), накопичено: 43.8 КБ
- RTT 3: `40` сегментів (58.4 КБ), накопичено: 102.2 КБ
- RTT 4: `80` сегментів (116.8 КБ), накопичено: 219.0 КБ
- RTT 5: `160` сегментів (233.6 КБ), накопичено: 452.6 КБ
- RTT 6: `320` сегментів (467.2 КБ), накопичено: 919.8 КБ
- RTT 7: `640` сегментів (934.4 КБ), накопичено: 1854.2 КБ (передачу 1.5 МБ завершено)

Загальний час передачі файлу 1.5 МБ складається з 3 RTT (встановлення TCP+TLS) та 7 RTT (Slow Start):

```
T_total_origin = (3 + 7) · 180 мс
               = 10 · 180 мс               [10 повних циклів RTT]
               = 1 800 мс                  [1.8 секунди на завантаження 1.5 МБ на 1 Гбіт/с каналі]

T_total_edge = (3 + 7) · 5 мс
             = 10 · 5 мс                   [10 локальних циклів RTT]
             = 50 мс                       [0.05 секунди на завантаження того самого файлу]
```

### Математична модель коефіцієнта попадання в кеш (Cache Hit Ratio)

Навантаження на сервер-джерело (`B_origin`) пов'язане з сумарним запитаним трафіком (`B_total`) через коефіцієнт попадання в кеш (`H`, де `0 ≤ H ≤ 1`):

```
B_origin = B_total · (1 - H)
```

Зіставимо навантаження при системному зростанні коефіцієнта попадання `H` з 95% (`0.95`) до 99% (`0.99`) для платформи з сумарним вихідним трафіком `B_total = 100 Гбіт/с`:

```
B_origin_95 = 100 Гбіт/с · (1 - 0.95)
            = 100 Гбіт/с · 0.05            [частка промахів 5%]
            = 5 Гбіт/с                     [навантаження на дата-центр]

B_origin_99 = 100 Гбіт/с · (1 - 0.99)
            = 100 Гбіт/с · 0.01            [частка промахів 1%]
            = 1 Гбіт/с                     [навантаження на дата-центр]
```

Коефіцієнт розвантаження джерела (Offload Factor, `K_offload`):

```
K_offload = B_origin_95 ÷ B_origin_99
          = 5 Гбіт/с ÷ 1 Гбіт/с            [відношення трафіку промахів]
          = 5                              [зниження навантаження на сервери-джерела рівно у 5 разів]
```

Підсумок: скорочення RTT за допомогою периферійних CDN усуває деградацію TCP-вікна та пом'якшує наслідки втрат пакетів, а підвищення Cache Hit Ratio навіть на кілька відсотків експоненційно скорочує витрати на серверну інфраструктуру Origin.
