# 📜 Від Xerox PARC до SWIM і Dynamo: народження та еволюція епідемічних протоколів

У 1980-х роках дослідницький центр Xerox PARC (Пало-Альто, Каліфорнія) зіткнувся з несподіваною кризою інфраструктури: внутрішня корпоративна база даних Clearinghouse, що зберігала маршрутизацію електронної пошти, списки користувачів та мережеві сервери, розрослася до кількох сотень вузлів, з'єднаних повільними телефонними лініями зі швидкістю 9.6–56 кбіт/с. Традиційні протоколи повної реплікації через деревоподібне або повне broadcast-розсилання (all-to-all) перевантажували канали зв'язку. Кожне додавання нового користувача породжувало лавину оновлень, яка блокувала передачу робочих повідомлень.

## 1987: Прорив Алана Демерса та народження епідемічних алгоритмів

У 1987 році група дослідників Xerox PARC — Алан Демерс (Alan Demers), Ден Грін (Dan Greene), Карл Гаузер (Carl Hauser), Вес Айріш (Wes Irish), Джон Ларсон (John Larson) та Говард Стерджис (Howard Sturgis) — опублікувала класичну статтю *«Epidemic Algorithms for Replicated Database Maintenance»*.

```
   Xerox PARC (1987)                      Cornell (2002)                    Amazon Dynamo (2007)
  [Алан Демерс і колеги]                 [SWIM: Дас, Гупта, Мотивала]      [ДеКандія та архітектори]
           │                                       │                                   │
           ▼                                       ▼                                   ▼
  • Anti-Entropy (Push/Pull)             • Прямий + непрямий зонд          • Токен-кільце через Gossip
  • Rumor Mongering (Плітки)             • Механізм підозри (Suspect)     • Повна децентралізація
  • Логарифмічне поширення               • O(1) навантаження на вузол      • Merkle-дерева в анти-ентропії
```

Демерс і його колеги звернулися до класичної математичної епідеміології (зокрема моделей розповсюдження інфекцій Нормана Бейлі). Замість надійного широкомовного розсилання вони запропонували стахастичний підхід: кожен сервер періодично обирає випадкового партнера для обміну оновленнями.

Автори чітко розмежували два фундаментальні класи алгоритмів:
1. **Анти-ентропія (Anti-Entropy):** важкий фоновий процес, де два вузли попарно порівнюють увесь свій стан (через контрольні суми або дайджести) та ліквідують будь-які розбіжності. Демерс математично довів, що поєднання Push (надсилання свого стану) та Pull (запит стану партнера) забезпечує експоненційну збіжність за час `O(log N)`.
2. **Поширення пліток (Rumor Mongering):** легкий процес для швидкого доставлення нових мутацій. Коли вузол дізнається про оновлення, він стає «інфікованим» і протягом фіксованої кількості раундів активно переповідає плітку випадковим сусідам, після чого «одужує» й замовкає, запобігаючи нескінченному циркулюванню пакетів.

Ця робота заклала математичний фундамент, проте на практиці алгоритми Демерса ще не вирішували проблему динамічного виявлення збоїв у групах: склад кластера вважався умовно сталим або налаштовувався адміністративно.

## 1990-ті: Bimodal Multicast і подолання ненадійності IP Multicast

Наприкінці 1990-х років академічна спільнота намагалася використовувати апаратний IP Multicast для побудови надійних розподілених систем. Проте в глобальних мережах (WAN) або під час комутаційних перевантажень IP Multicast страждав від «шторму квитанцій» (ACK/NAK implosion): коли сотні вузлів одночасно фіксували втрату пакета й надсилали запит на повторну передачу, джерело захлиналося й падало.

У 1999 році професор Корнелльського університету Кен Бірман (Ken Birman) разом із колегами запропонував протокол **Bimodal Multicast** (також відомий як `pbcast` — *probabilistic broadcast*). Алгоритм поєднував звичайний ненадійний IP Multicast для первинної швидкої доставки з епідемічним gossip-протоколом на базі UDP для локального затягування втрачених пакетів між сусідами. Якщо вузол втрачав пакет, він звертався не до першоджерела, а до випадкових сусідів по кластеру.

Bimodal Multicast показав дивовижну стійкість: навіть якщо комутатор втрачав до 30–50% пакетів, епідемічне досилання гарантувало, що понад 99.999% вузлів отримували повідомлення без навантаження на джерело.

## 2002: Протокол SWIM — революція у виявленні збоїв

Головним бар'єром на шляху масштабування розподілених систем до тисяч вузлів лишався моніторинг живості (membership & failure detection). Класичні протоколи вимагали періодичного опитування кожного сервера кожним (`O(N^2)` повідомлень) або розсилання пульсу (heartbeat) через координатора (`O(N)` навантаження на один сервер).

У 2002 році дослідники Корнелльського університету Абхінандан Дас (Abhinandan Das), Індраніл Гупта (Indranil Gupta) та Ашіш Мотивала (Ashish Motivala) представили протокол **SWIM** (*Scalable Weakly-Consistent Infection-Style Process Group Membership Protocol*).

```
   Традиційний моніторинг (All-to-All)              SWIM (Scalable Weakly-Consistent)
  ┌─────────────────────────────────────┐         ┌─────────────────────────────────────┐
  │ • N вузлів шлють пульс N-1 сусідам  │         │ • Вузол пінгує 1 випадкового сусіда │
  │ • Трафік мережі: O(N²)              │         │ • Трафік на вузол: O(1) [константа] │
  │ • При N = 1000: 1 000 000 пінґів    │         │ • Непрямий ping-req долає дропи     │
  │ • Хибні тривоги через сплески RTT   │         │ • Механізм підозри захищає від GC   │
  └─────────────────────────────────────┘         └─────────────────────────────────────┘
```

SWIM зробив три фундаментальні відкриття:
1. **Зниження навантаження до `O(1)`:** кожен вузол у кожному інтервалі пінгує лише одного випадкового учасника, тому локальне процесорне та мережеве навантаження абсолютно не залежить від загального розміру кластера.
2. **Непряме зондування (Indirect Probing):** якщо прямий пінг не отримав відповіді через локальний мережевий збій або втрату пакета, вузол просить `k` випадкових посередників надіслати запит `ping-req`. Це виключило хибні спрацьовування через асиметричну маршрутизацію.
3. **Механізм підозри (Suspicion Mechanism) та інкарнації:** вузол не оголошується мертвим негайно; замість цього кластером розсилається плітка про стан `Suspect`. Якщо «підозрюваний» вузол насправді живий (наприклад, перебував у паузі збирача сміття JVM), він має час збільшити свій лічильник інкарнації й розіслати спростування `Alive`.

SWIM став стандартом де-факто для побудови сучасних однорангових і безлідерних кластерів.

## 2007: Amazon Dynamo та промисловий тріумф

У жовтні 2007 року інженери Amazon Джузеппе ДеКандія (Giuseppe DeCandia), Деніз Гастінгс (Deniz Hastorun) та їхні співавтори опублікували знакову статтю про сховище **Dynamo** (*Dynamo: Amazon’s Highly Available Key-value Store*).

Dynamo був покликаний забезпечити нульовий час простою кошика покупок інтернет-магазину Amazon під час Чорної п'ятниці. В архітектурі Dynamo gossip-протокол вперше керував не просто членством, а фізичним розподілом даних:
- Вузли через плітки обмінювалися позиціями у кільці погодженого хешування (Consistent Hash Ring).
- Кожен вузол незалежно формував повну карту розподілу токенів, усуваючи потребу в централізованих маршрутизаторах.
- Відновлення стану після тривалих аварій виконувалося через анти-ентропію на деревах Меркла.

Принципи Dynamo лягли в основу **Apache Cassandra** (створеної в Facebook у 2008 році та переданої в open-source) та **Riak** (Basho Technologies). У Cassandra протокол Gossip відповідає за підтримання поколінь вузлів (`generation`), версійованих карт станів застосунків (`ApplicationState`) та адаптивного детектора збоїв `Phi Accrual Failure Detector` (розробленого Наохіро Хаяшібарою у 2004 році).

## 2013–дотепер: HashiCorp Memberlist, Serf та сучасні сервісні сітки

У 2013 році Мітчелл Хашімото (Mitchell Hashimoto) та Армон Дадгар (Armon Dadgar) заснували компанію HashiCorp і випустили бібліотеку **Memberlist** та утиліту **Serf**.

Memberlist розвинув ідеї SWIM, додавши агресивне підсаджування пліток (piggybacking): будь-які повідомлення про зміну членства пакуються безпосередньо в корисне навантаження стандартних UDP-пакетів Ping та Ack. Це перетворило Memberlist на фундамент для **Consul** (оркестрація та виявлення сервісів) та **Nomad** (планувальник контейнерів), які щодня обслуговують мільйони серверів у хмарних дата-центрах.

Сьогодні епідемічні протоколи еволюціонували від експериментальних академічних моделей до незамінного шару критичної інфраструктури: від Redis Cluster до блокчейн-мереж (Bitcoin, Ethereum) та P2P-комунікацій Libp2p, забезпечуючи масштабування систем без єдиної точки відмови.
