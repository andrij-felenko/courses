# 📋 Інтерфейс конфігурації, станів та телеметрії виробничого запобіжника

Повноцінний виробничий запобіжник вимагає строгого контракту конфігурації, програмного інтерфейсу управління станами, системи зворотних викликів (Event Listeners) для спостережуваності та експорту метрик у форматі Prometheus/OpenTelemetry. Нижче наведено повну специфікацію інтерфейсів та параметрів стійкості.

## Параметри конфігурації (Configuration Contract)

Конфігурація запобіжника задає правила збору статистики, критерії розпізнавання аварійного стану та часові параметри відновлення.

| Параметр | Тип | Значення за замовчуванням | Опис та семантика |
| :--- | :--- | :--- | :--- |
| `slidingWindowType` | `COUNT_BASED` \| `TIME_BASED` | `COUNT_BASED` | Тип ковзного вікна: на основі фіксованої кількості останніх викликів або на основі часового зрізу в секундах. |
| `slidingWindowSize` | Ціле додатне число | `100` | Розмір вікна: кількість викликів для `COUNT_BASED` (напр. 100) або тривалість у секундах для `TIME_BASED` (напр. 60 с). |
| `minimumNumberOfCalls` | Ціле додатне число | `20` | Мінімальна кількість зареєстрованих викликів у вікні перед початком обчислення відсотків помилок і затримок (захист від хибних спрацьовувань при холодному старті). |
| `failureRateThreshold` | Дійсне число (0.0–100.0) | `50.0` | Відсотковий поріг збоїв: якщо частка помилкових викликів у вікні перевищує цей поріг, запобіжник переходить у стан `OPEN`. |
| `slowCallRateThreshold` | Дійсне число (0.0–100.0) | `100.0` | Відсотковий поріг повільних викликів: якщо частка викликів, тривалість яких перевищила `slowCallDurationThreshold`, більша за поріг, ланцюг розмикається. |
| `slowCallDurationThreshold` | Тривалість часу (Duration) | `2000 ms` | Граничний час виконання одного виклику: операції, що тривають довше, кваліфікуються як повільні («slow calls»). |
| `waitDurationInOpenState` | Тривалість часу (Duration) | `60000 ms` (60 с) | Час перебування у стані `OPEN` перед переходом у пробний стан `HALF_OPEN`. |
| `permittedNumberOfCallsInHalfOpenState` | Ціле додатне число | `10` | Кількість дозволених пробних викликів у стані `HALF_OPEN`. Решта паралельних запитів відхиляється негайно. |
| `automaticTransitionFromOpenToHalfOpenEnabled` | Булеве (`true`/`false`) | `true` | Чи запускається автоматичний фоновий таймер переходу в `HALF_OPEN` без очікування вхідного користувацького запиту. |
| `recordExceptions` | Список класів / кодів | `[5xx, Timeout, TransportError]` | Перелік помилок та кодів статусів, які враховуються як збій при підрахунку статистики. |
| `ignoreExceptions` | Список класів / кодів | `[400 Bad Request, 404 Not Found]` | Перелік очікуваних клієнтських або бізнес-помилок, які ігноруються і не впливають на стан запобіжника. |

## Детальний розбір конфігураційних параметрів

Кожен конфігураційний параметр запобіжника безпосередньо впливає на математичну стійкість та чутливість системи до мережевих збоїв:

### 1. Вибір типу ковзного вікна: `COUNT_BASED` проти `TIME_BASED`

* **Кількісне вікно (`COUNT_BASED`):** аналізує останні `N` викликів незалежно від часу їх надходження. Це ідеальний вибір для сервісів зі стабільним або високим потоком трафіку (від сотень до десятків тисяч RPS). Кількісне вікно миттєво реагує на різкий шквал помилок у межах кількох мілісекунд, оскільки буфер заповнюється зі швидкістю вхідних запитів. Проте для низьконавантажених інтерфейсів (наприклад, 1 запит на хвилину) кількісне вікно зберігає застарілу історію надто довго: одиничний збій, що стався годину тому, продовжуватиме спотворювати статистику, доки буфер не витіснить його новими викликами.
* **Часове вікно (`TIME_BASED`):** розбиває часовий інтервал на дискретні кошики (наприклад, 10 кошиків по 1 секунді). Воно автоматично витісняє застарілі збої після завершення часового періоду, що робить його стійким до нерівномірного або пакетного (Burst) трафіку. Недоліком часового вікна є дискретна затримка реакції: події агрегуються з точністю до розміру окремого бакета (1 секунда).

### 2. Захисний поріг `minimumNumberOfCalls` та запобігання хибним спрацьовуванням

Критичною помилкою конфігурації є встановлення заниженого значення `minimumNumberOfCalls` (наприклад, 2 чи 3). Якщо після старту сервісу перші два виклики випадково зазнають невдачі через прогрів сокетного пулу, відсоток помилок миттєво досягає 100%, і запобіжник необґрунтовано розмикає ланцюг, блокуючи подальший трафік.

Параметр `minimumNumberOfCalls` визначає нижню межу статистичної вибірки: доки в поточному вікні не буде накопичено вказану кількість результатів, розрахунок відсотка помилок не виконується взагалі, і запобіжник безумовно залишається в стані `CLOSED`. Рекомендоване значення складає не менше 20–50 викликів.

### 3. Відстеження повільних викликів: `slowCallRateThreshold` та `slowCallDurationThreshold`

У розподілених системах деградація продуктивності через надмірну затримку (Lethal Latency) є набагато небезпечнішою за миттєві помилки `500 Internal Server Error`. Якщо залежний сервіс не падає, але збільшує час відповіді з 20 мс до 8 секунд, клієнтські пули потоків вичерпуються, і клієнт зазнає каскадної відмови.

Параметр `slowCallDurationThreshold` задає часову межу, перевищення якої класифікує виклик як аномально повільний, навіть якщо він зрештою повернув статус `200 OK`. Якщо частка таких повільних викликів у вікні перевищує `slowCallRateThreshold` (наприклад, понад 50% запитів тривають довше 2 секунд), запобіжник розмикає ланцюг, захищаючи клієнтські ресурси від виснаження.

### 4. Адаптивне очікування у стані OPEN (`waitDurationInOpenState`)

Параметр `waitDurationInOpenState` визначає, скільки часу система витримує повну ізоляцію деградованого бекенда перед тим, як надати йому шанс на реабілітацію в стані `HALF_OPEN`.

У простих сценаріях використовується фіксований інтервал (наприклад, 60 секунд). Проте у високонавантажених промислових системах рекомендується застосовувати експоненційне зростання часу очікування: якщо перша спроба в `HALF_OPEN` завершилася невдачею, наступна пауза в `OPEN` подвоюється (120 с, 240 с, 480 с аж до верхньої межі `maxWaitDurationInOpenState`). Це запобігає постійному циклічному коливанню (Flapping) між розімкненим і пробним станами, коли віддалений сервіс перебуває в стані тривалої аварії.

### 5. Семантична класифікація помилок: `recordExceptions` проти `ignoreExceptions`

Запобіжник повинен реагувати виключно на інфраструктурні та системні збої доступності. Змішування клієнтських бізнес-помилок із системними збоями призводить до помилкового блокування цілком здорових сервісів:

* **Помилки, що повинні фіксуватися (`recordExceptions`):** вичерпання таймаутів з'єднання (`ConnectTimeout`) та читання (`ReadTimeout`), скидання TCP-пакетів (`ECONNRESET`, `EPIPE`), внутрішні збої сервера (HTTP `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`), помилки протоколу gRPC (`UNAVAILABLE`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED`).
* **Помилки, що категорично ігноруються (`ignoreExceptions`):** клієнтські помилки валідації вхідних даних (HTTP `400 Bad Request`, `422 Unprocessable Entity`), помилки аутентифікації та прав доступу (HTTP `401 Unauthorized`, `403 Forbidden`), відсутність сутності в базі даних (HTTP `404 Not Found`), бізнес-відхилення операцій (наприклад, недостатність коштів на рахунку). Якщо користувач уводить невалідний номер банківської картки, повернення помилки `422` є штатною поведінкою платіжного шлюзу і жодним чином не свідчить про його деградацію.

## Інтерфейс управління та запиту стану (Public Control API)

Інтерфейс запобіжника забезпечує як стандартний шлях виконання запитів, так і методи примусового операційного втручання (Maintenance Mode):

```cpp
namespace resilience {

class ICircuitBreaker {
public:
    virtual ~ICircuitBreaker() = default;

    // Основний цикл виконання
    virtual bool allow_request() noexcept = 0;
    virtual void record_success(std::chrono::nanoseconds duration) noexcept = 0;
    virtual void record_error(std::chrono::nanoseconds duration, const std::exception& error) noexcept = 0;

    // Запит поточного стану та метрик
    virtual State get_state() const noexcept = 0;
    virtual Metrics get_metrics() const noexcept = 0;

    // Примусове операційне втручання
    virtual void transition_to_disabled_state() noexcept = 0;   // Запобіжник вимкнено (завжди пропускає)
    virtual void transition_to_forced_open_state() noexcept = 0; // Запобіжник примусово розімкнено (блокує все)
    virtual void reset() noexcept = 0;                          // Скидання статистики та повернення в CLOSED
};

} // namespace resilience
```

```go
package resilience

import (
	"context"
	"time"
)

type ICircuitBreaker interface {
	// Основний цикл перевірки та запису
	AllowRequest() bool
	RecordSuccess(duration time.Duration)
	RecordError(duration time.Duration, err error)

	// Запит стану та метрик
	GetState() State
	GetMetrics() Metrics

	// Операційне управління
	TransitionToDisabled()
	TransitionToForcedOpen()
	Reset()

	// Обгортка для виконання функцій
	Execute(ctx context.Context, action func(ctx context.Context) error) error
}
```

## Система подій та слухачів (Lifecycle Event Listeners)

Для інтеграції з системами аудиту, логування та сповіщення запобіжник генерує структуровані події життєвого циклу:

```
+--------------------------+-------------------------------------------------------------+
| Тип події (Event Type)   | Опис та контекст події                                      |
+--------------------------+-------------------------------------------------------------+
| STATE_TRANSITION         | Зміна стану автомата (наприклад, CLOSED -> OPEN).           |
|                          | Передає: попередній стан, новий стан, мітку часу.           |
| SUCCESS                  | Успішне завершення виклику в межах допустимого часу.        |
|                          | Передає: тривалість виконання виклику.                      |
| ERROR                    | Виклик завершився збоєм або винятком із `recordExceptions`.  |
|                          | Передає: тривалість, причину помилки.                       |
| SLOW_CALL                | Виклик успішний, але тривалість перевищила поріг затримки.  |
|                          | Передає: фактичну тривалість, поріг `slowCallDuration`.     |
| CALL_NOT_PERMITTED       | Запит відхилено без виконання через стан OPEN або ліміт     |
|                          | пробних викликів у стані HALF_OPEN.                         |
| IGNORED_ERROR            | Зафіксовано помилку зі списку `ignoreExceptions`.           |
+--------------------------+-------------------------------------------------------------+
```

## Специфікація метрик Prometheus / OpenTelemetry

Виробничий запобіжник експортує стандартизований набір метрик у реєстр Prometheus із обов'язковою міткою `name="<назва_залежності>"`.

```prometheus
# Поточний стан запобіжника (0 = CLOSED, 1 = OPEN, 2 = HALF_OPEN, 3 = DISABLED, 4 = FORCED_OPEN)
# TYPE circuitbreaker_state gauge
circuitbreaker_state{name="payment_service",state="closed"} 1
circuitbreaker_state{name="payment_service",state="open"} 0
circuitbreaker_state{name="payment_service",state="half_open"} 0

# Загальна кількість зареєстрованих викликів за результатами
# TYPE circuitbreaker_calls_total counter
circuitbreaker_calls_total{name="payment_service",kind="successful"} 142850
circuitbreaker_calls_total{name="payment_service",kind="failed"} 320
circuitbreaker_calls_total{name="payment_service",kind="slow_successful"} 45
circuitbreaker_calls_total{name="payment_service",kind="slow_failed"} 12
circuitbreaker_calls_total{name="payment_service",kind="not_permitted"} 8900
circuitbreaker_calls_total{name="payment_service",kind="ignored"} 150

# Поточний розрахований відсоток збоїв у ковзному вікні (0.0 - 100.0)
# TYPE circuitbreaker_failure_rate gauge
circuitbreaker_failure_rate{name="payment_service"} 0.22

# Поточний розрахований відсоток повільних викликів у вікні (0.0 - 100.0)
# TYPE circuitbreaker_slow_call_rate gauge
circuitbreaker_slow_call_rate{name="payment_service"} 0.04

# Кількість буферизованих викликів у поточному вікні
# TYPE circuitbreaker_buffered_calls gauge
circuitbreaker_buffered_calls{name="payment_service"} 100
```

## Протокольна інтеграція: HTTP та gRPC

Коли запобіжник блокує виклик у стані `OPEN` або перевищенні квоти `HALF_OPEN`, клієнтський або проксі-шар повинен сформувати семантично коректну відповідь протоколу, яка дозволить клієнтам вищого рівня розпізнати тимчасову недоступність вузла:

### 1. Протокол HTTP / REST
* **HTTP Status Code:** `503 Service Unavailable` (або `429 Too Many Requests` за специфічних конфігурацій шлюзу).
* **HTTP Заголовок `Retry-After`:** вказує залишок часу очікування в секундах до наступної спроби у стані `HALF_OPEN` (наприклад, `Retry-After: 30`).
* **HTTP Заголовок `X-Circuit-Breaker-State`:** діагностичний заголовок зі значенням `OPEN` для швидкого розбору інцидентів інженерами чергової зміни.
* **Тіло відповіді (JSON Problem Details за RFC 7807):**

```json
{
  "type": "https://api.example.com/errors/circuit-breaker-open",
  "title": "Service Dependency Unavailable",
  "status": 503,
  "detail": "Circuit breaker for dependency 'payment_service' is currently OPEN. Requests are temporarily rejected to allow the downstream dependency to recover.",
  "instance": "/orders/checkout",
  "retry_after_seconds": 30
}
```

### 2. Протокол gRPC
* **gRPC Status Code:** `codes.Unavailable` (числове значення `14`).
* **gRPC Error Details:** у метаданих статусу передається структура `google.rpc.RetryInfo` з полем `retry_delay`, що містить точну тривалість очікування до переходу в стан `HALF_OPEN`.

## Атрибути розподіленого трасування OpenTelemetry

При інтеграції з системами розподіленого трасування (OpenTelemetry / Jaeger) стан запобіжника фіксується у відповідному спані (Span):

* `resilience.circuit_breaker.name`: ім'я цільового екземпляра запобіжника (наприклад, `payment_service_client`);
* `resilience.circuit_breaker.state`: стан на момент початку виконання запиту (`closed`, `open`, `half_open`);
* `resilience.circuit_breaker.event`: подія життєвого циклу, якщо виклик спричинив зміну стану (наприклад, `state_transition_open`);
* `resilience.circuit_breaker.fallback`: булевий прапорець (`true`/`false`), що позначає успішне виконання аварійної fallback-гілки.
