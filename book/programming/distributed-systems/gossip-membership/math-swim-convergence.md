# 🧮 Математика збіжності та ймовірнісні оцінки SWIM

У великих розподілених системах неможливо гарантувати абсолютну надійність мережевих каналів чи миттєву синхронізацію годинників. Будь-який протокол членства має спиратися на ймовірнісні моделі: оцінку ймовірності хибного виявлення відмов (False Positive Rate), час гарантованого поширення інформації про зміну топології (Dissemination Latency) та стійкість до втрат транзитних UDP-пакетів.

---

## Ймовірність хибного спрацьовування: прямий зонд проти непрямого запиту

Нехай у кластері з `N` вузлів мережеве середовище характеризується незалежною ймовірністю втрати окремого UDP-пакета `p`, де `0 < p < 1`. Вважаємо, що вузол-ціль є абсолютно здоровим і відповідає на запити без затримок.

Під час прямого зондування вузол `A` надсилає дейтаграму `Ping` на вузол `B`, а вузол `B` повертає дейтаграму `Ack`. Обидва пакети мають бути успішно доставлені.

Ймовірність успішного завершення прямого раунду зондування `P_succ_dir`:

```
P_succ_dir
= (1 - p) · (1 - p)      [правило добутку для двох незалежних подій доставки]
= (1 - p)²               [квадрат імовірності успішної доставки дейтаграми]
```

Ймовірність провалу прямого зондування `P_fail_dir` через мережеву втрату пакета (за умови, що вузол `B` насправді живий):

```
P_fail_dir
= 1 - P_succ_dir         [ймовірність протилежної події]
= 1 - (1 - p)²           [підстановка формули успіху]
= 1 - (1 - 2p + p²)      [розкриття квадрата двочлена]
= 2p - p²                [ймовірність втрати бодай одного з двох пакетів]
```

Якщо мережевий комутатор перевантажений і втрачає `p = 0.05` (5% пакетів), імовірність хибної підозри при прямому зондуванні становить:

```
P_fail_dir
= 2 · (0.05) - (0.05)²   [підстановка p = 0.05]
= 0.10 - 0.0025          [обчислення компонентів]
= 0.0975                 [9.75% раундів завершуються помилкою]
```

Майже кожен десятий прямий пінг здорового сервера завершується таймаутом. Якщо оголошувати вузол підозрілим або мертвим після першого ж невдалого прямого пінгу, кластер захлинеться в хибних спрацьовуваннях.

### Непряме зондування через k посередників

У протоколі SWIM при вичерпанні таймауту `T_ack` вузол `A` обирає `k` випадкових посередників `C₁, C₂, ..., C_k` і надсилає їм запит `ping-req(B)`.

Маршрут через окремого посередника `C_i` складається з чотирьох послідовних відрізків:
1. `A → C_i` (`ping-req`)
2. `C_i → B` (`ping`)
3. `B → C_i` (`ack`)
4. `C_i → A` (`ack`)

Ймовірність успішного проходження всіх чотирьох дейтаграм через посередника `C_i`:

```
P_succ_ind
= (1 - p) · (1 - p) · (1 - p) · (1 - p)   [добуток імовірностей 4 незалежних доставок]
= (1 - p)⁴                                [успіх непрямого ланцюга]
```

Ймовірність того, що конкретний непрямий шлях через вузол `C_i` провалиться:

```
P_fail_ind
= 1 - P_succ_ind                          [ймовірність протилежної події]
= 1 - (1 - p)⁴                            [провал через втрату бодай однієї з 4 дейтаграм]
```

Вузол `A` вважає вузол `B` недоступним лише тоді, коли прямий зонд провалився **І** всі `k` незалежних посередників не змогли отримати відповідь від `B`.

Сумарна ймовірність хибного спрацьовування детектора `P_false_positive`:

```
P_false_positive
= P_fail_dir · (P_fail_ind)^k             [спільна ймовірність незалежних провалів]
= (2p - p²) · (1 - (1 - p)⁴)^k            [аналітична формула хибної тривоги SWIM]
```

### Числовий розрахунок для p = 0.05 при різних значеннях k

Для `p = 0.05`:
`P_fail_dir = 0.0975`
`P_succ_ind = (0.95)⁴ ≈ 0.8145`
`P_fail_ind = 1 - 0.8145 = 0.1855`

Для `k = 1` (один посередник):

```
P_fp(k=1)
= 0.0975 · 0.1855
= 0.01808               [1.81% хибних спрацьовувань]
```

Для `k = 3` (типове значення за замовчуванням):

```
P_fp(k=3)
= 0.0975 · (0.1855)³     [піднесення до степеня k=3]
= 0.0975 · 0.006383      [імовірність одночасного провалу трьох посередників]
= 0.000622               [0.062% хибних спрацьовувань]
```

Для `k = 5`:

```
P_fp(k=5)
= 0.0975 · (0.1855)⁵     [піднесення до степеня k=5]
= 0.0975 · 0.0002196     [імовірність одночасного провалу п'яти посередників]
= 0.0000214              [0.0021% хибних спрацьовувань]
```

Перехід від прямого зондування до непрямого з `k = 3` зменшує частоту хибних тривог у:

```
Factor_gain
= 0.0975 ÷ 0.000622      [відношення ймовірностей помилки]
≈ 156.7                  [зниження рівня хибних детекцій у 157 разів]
```

При цьому навантаження на мережу збільшується лише на фіксовану константу `O(k)` пакетів у разі локального збою, не порушуючи загальну асимптотику `O(1)` на вузол.

## Математична динаміка епідемічного поширення (Infection Bounds)

Поширення інформації про стан членства (Alive, Suspect, Dead) здійснюється за допомогою епідемічного алгоритму розповсюдження пліток (gossip dissemination).

Нехай у системі з `N` вузлів з'явилося нове оновлення (наприклад, вузол `X` перейшов у стан `Suspect`).
Нехай `x(t)` — частка вузлів, які отримали це повідомлення (інфіковані вузли), а `1 - x(t)` — частка вузлів, які ще не знають про подію (вразливі вузли), де `x(0) = 1 / N`.

У кожному раунді кожен інфікований вузол передає інформацію `β` випадково обраним сусідам (параметр fanout).

Диференціальне рівняння класичної SI-моделі епідемії:

```
dx / dt
= β · x(t) · (1 - x(t))                   [швидкість приросту інфікованої частки]
```

Розв'язок цього рівняння є логістичною кривою (сигмоїдою):

```
x(t)
= 1 / (1 + (N - 1) · e^(-β · t))          [частка інфікованих вузлів у момент часу t]
```

### Кількість раундів до повного охоплення кластера

Щоб знайти кількість періодів `R`, необхідних для інфікування всіх `N` вузлів із заданою залишковою ймовірністю помилки `ε` (де частка непоінформованих вузлів `1 - x(R) ≤ ε / N`), розв'яжемо рівняння відносно `t = R`:

```
1 - x(R) ≤ ε / N
(N - 1) · e^(-β · R) ≈ ε / N              [наближення для x(R) близького до 1]
e^(-β · R) ≈ ε / (N · (N - 1))            [ділення на N - 1]
-β · R = ln(ε) - ln(N²)                  [логарифмування обох частин]
β · R = 2 · ln(N) - ln(ε)                [зміна знаків]
R = (2 · ln(N) - ln(ε)) / β              [аналітичний час повного поширення]
```

Звідси випливає фундаментальна теорема епідемічного зв'язку:
Час доставки оновлення до всіх вузлів масштабується як:

```
R = O(log N)                              [логарифмічна асимптотика раундів]
```

Для кластера з `N = 10 000` серверів при fanout `β = 3` та допустимому залишку `ε = 0.001`:

```
R
= (2 · ln(10000) - ln(0.001)) / 3        [підстановка параметрів]
= (2 · 9.2103 - (-6.9077)) / 3           [обчислення натуральних логарифмів]
= (18.4206 + 6.9077) / 3                 [сума компонентів]
= 25.3283 / 3                            [ділення на fanout]
≈ 8.44                                   [достатньо 9 раундів пліток]
```

Якщо тривалість періоду зондування `T_probe = 500 мс`, повне оновлення інформації про стан вузла серед 10 000 серверів досягається за:

```
T_total
= 9 · 0.5 с                              [добуток раундів на тривалість періоду]
= 4.5 с                                  [4.5 секунди до повної узгодженості]
```

### Бюджет ретрансляцій у буфері Piggybacking

Щоб окремий вузол не зберігав і не пересилав подію вічно, встановлюється ліміт кількості передач `RetransmitLimit`. Кожна подія додається до черги зі спадним лічильником:

```
RetransmitLimit
= λ · ⌈log₂(N + 1)⌉                      [формула бюджету відправлень]
```

де `λ` — коефіцієнт надійності розповсюдження (у промислових реалізаціях на кшталт HashiCorp Memberlist `λ = 3..5`).

Для кластера з `N = 1000` вузлів:
`log₂(1001) ≈ 9.967 → ⌈log₂(1001)⌉ = 10`.
При `λ = 3`:

```
RetransmitLimit
= 3 · 10                                 [добуток множника на стелю логарифма]
= 30 відправлень                         [після 30 передач подію витісняють із черги]
```

## Динамічний таймаут підозри Lifeguard (Dogpiling / Corroboration)

У класичному SWIM таймаут стану `Suspect` є фіксованим: `T_suspect = SuspicionMult · log(N) · T_probe`. Це захищає від помилкових вилучень, але затримує виявлення справді аварійних серверів.

Розширення Lifeguard вводить динамічний таймаут підозри, який зменшується експоненційно в міру надходження незалежних підтверджень підозри (консенсус через підтвердження, або *dogpiling*):

```
T_suspect(C)
= T_max - (T_max - T_min) · min(1, log(C + 1) / log(K + 1))
```

де:
* `C` — кількість незалежних вузлів, які надіслали підтвердження підозри `Suspect(B, inc)` для тієї самої інкарнації;
* `K` — гранична кількість підтверджень для досягнення мінімального таймауту (зазвичай `K = 3` або `K = 4`);
* `T_max = SuspicionMult · log(N) · T_probe` — максимальний час очікування спростування (для одиничної підозри);
* `T_min = SuspicionMinMult · T_probe` — мінімальний час очікування при масовому підтвердженні аварії.

### Розрахунок скорочення таймера підозри

Нехай `N = 1000`, `T_probe = 1000 мс`, `SuspicionMult = 4`, `SuspicionMinMult = 1`, `K = 3`.
`T_max = 4 · ln(1000) · 1000 мс ≈ 4 · 6.907 · 1000 ≈ 27 630 мс (27.6 с)`.
`T_min = 1 · 1000 мс = 1000 мс (1.0 с)`.
`T_diff = T_max - T_min = 26 630 мс`.
`log(K + 1) = log(4) = 1.3863`.

1. При `C = 0` (одинична підозра від одного вузла):

```
Ratio(C=0)
= log(1) / log(4)
= 0 / 1.3863
= 0

T_suspect(0)
= T_max - 26630 · 0
= 27630 мс                              [повний час 27.6 с на спростування]
```

2. При `C = 1` (ще один незалежний вузол підтвердив недоступність):

```
Ratio(C=1)
= log(2) / log(4)
= 0.6931 / 1.3863
= 0.5

T_suspect(1)
= 27630 - 26630 · 0.5
= 27630 - 13315
= 14315 мс                              [час очікування скоротився до 14.3 с]
```

3. При `C = 3` (поріг `K = 3` досягнуто, консенсус 4 вузлів):

```
Ratio(C=3)
= log(4) / log(4)
= 1.0

T_suspect(3)
= 27630 - 26630 · 1.0
= 1000 мс                               [таймаут скоротився до 1.0 с]
```

Якщо падіння вузла реальне, кілька сусідніх зондувальників майже одночасно зафіксують відсутність відповіді, і кластер визнає вузол мертвим за 1–2 секунди замість 27 секунд. Якщо ж збій спричинений короткочасним мережевим дрижанням на одному каналі, вузол має повні 27.6 секунди, щоб відновитися і надіслати спростування `Alive(inc + 1)`.

## Локальний множник здоров'я (Local Health Multiplier, LHM)

Для запобігання ситуаціям, коли локально перевантажений вузол (через тривалу паузу збирача сміття GC або 100% завантаження CPU) починає помилково підозрювати здорових сусідів, Lifeguard розраховує локальний множник стану `LHM ∈ [0, 8]`.

Динаміка зміни `LHM`:
* Провал власного прямого чи непрямого зонду: `LHM = min(8, LHM + 1)`.
* Отримання повідомлення `Suspect` на свою власну адресу (симптом того, що локальний вузол гальмує і не встигає відповідати на вхідні пінги): `LHM = min(8, LHM + 1)`.
* Успішне завершення чергового раунду зондування: `LHM = max(0, LHM - 1)`.

Адаптація часових параметрів зондування:

```
T_probe_actual
= T_probe · (1 + LHM)                    [збільшення інтервалу зондування]
```

```
T_ack_actual
= T_ack · (1 + LHM)                      [подовження очікування відповіді]
```

```
T_suspect_actual
= T_suspect · (1 + LHM)                  [подовження вікна спростування]
```

Коли вузол деградує, він автоматично знижує частоту відправлення запитів і дає своїм сусідам більше часу на відповідь, що повністю ліквідує каскадні лавини помилкових виключень у високонавантажених системах.
