# 🧮 Математичний аналіз накладних витрат: затримка сокетів, черги M/M/1 та мультиплікація пам'яті

Цей аналіз надає точний інженерний апарат для кількісної оцінки вартості використання патерна Sidecar: розрахунку додаткової затримки через подвійне проходження мережевого стека ядра Linux і перемикання контексту процесора, математичного моделювання черг буферів сокетів за теорією масового обслуговування M/M/1, виведення граничного порогу вичерпання ефемерних портів через накопичення з'єднань у стані TIME_WAIT, а також розрахунку кластерної точки беззбитковості оперативної пам'яті між моделлю супутніх контейнерів Pod-Sidecar та загальновузловим агентом DaemonSet.

## 1. Моделювання затримки подвійного проходу сокета та перемикання контексту

У традиційній безсайдкарній архітектурі, коли застосунок надсилає вихідний мережевий запит безпосередньо, мережевий пакет долає мінімальний апаратний шлях:
`Застосунок (User Space) → Системний виклик (Kernel Space) → Мережевий драйвер NIC`.

У разі впровадження супутнього проксі-контейнера (Ambassador або Sidecar) шлях проходження кожного байта подвоюється, оскільки пакет спочатку перехоплюється локальним проксі-процесом, аналізується в його користувацькому просторі й лише потім відправляється у фізичну мережу:
`Застосунок (User) → Kernel (lo сокет) → Sidecar (User) → Kernel (eth0 сокет) → Драйвер NIC`.

Повна часова затримка передачі складається з часу виконання системних викликів, копіювання даних у буфери сокетів ядра, затримки проходження протокольного стека loopback та перемикання контексту процесора між користувацьким простором і ядром:

```
T_direct = 2·T_syscall + T_ctx + T_nic                                                   [прямий шлях: виклик write та обробка драйвером]
T_sidecar = 4·T_syscall + 3·T_ctx + 2·T_tcp_loopback + T_nic                             [сайдкар: подвійний сокетний прохід та перемикання]
ΔT = T_sidecar - T_direct                                                                [визначення додаткової затримки сайдкара]
   = (4·T_syscall + 3·T_ctx + 2·T_tcp_loopback + T_nic) - (2·T_syscall + T_ctx + T_nic) [підстановка повних виразів]
   = 2·T_syscall + 2·T_ctx + 2·T_tcp_loopback                                            [алгебраїчне спрощення: взаємне скорочення T_nic]
```

Для сучасного багатоядерного x86-64 процесора під управлінням Linux за відсутності перевантаження черг типові апаратні константи становлять:
* `T_syscall` (час виконання системних викликів `read()` та `write()` з урахуванням механізмів ізоляції сторінок ядра KPTI від атак Spectre/Meltdown) ≈ `0.8 мкс`.
* `T_ctx` (час збереження регістрів процесора та перемикання таблиць сторінок пам'яті CR3 між потоками) ≈ `1.5 мкс`.
* `T_tcp_loopback` (час проходження TCP-стека ядра через віртуальний інтерфейс `lo`, розрахунку контрольних сум та проходження ланцюжків Netfilter) ≈ `4.2 мкс`.

Підставимо ці виміряні емпіричні значення у виведену формулу додаткової затримки:

```
ΔT = 2·(0.8) + 2·(1.5) + 2·(4.2) [підстановка числових параметрів мікросекунд]
   = 1.6 + 3.0 + 8.4             [проміжне множення доданків]
   = 13.0 мкс                    [чистий апаратний оверхед в один бік]
```

Для повного циклу передачі «запит-відповідь» (Round-Trip Time) сумарна гарантована затримка подвоюється і становить `26.0 мкс`. Якщо проксі-сайдкар додатково здійснює L7-парсинг HTTP/2 заголовків, перевірку сертифікатів mTLS та десеріалізацію метаданих трейсингу, чиста затримка обробки зростає до `0.8–2.5 мс` на кожну міжсервісну ланку.

## 2. Нелінійне зростання затримок у чергах буферів за моделлю M/M/1

Коли частота вхідних запитів наближається до максимальної пропускної здатності сайдкара, затримка перестає бути константою і починає стрімко зростати через утворення черг у системних буферах прийому `sk_rcvbuf` та відправки `sk_sndbuf`.

Змоделюємо Ambassador-проксі як класичну систему масового обслуговування типу `M/M/1` з найпростішим пуассонівським вхідним потоком і експоненційним часом обробки:
* `λ` — інтенсивність надходження вхідних запитів від основного застосунку (запитів за секунду).
* `μ` — середня продуктивність обробки та перенаправлення пакетів сайдкаром (запитів за секунду).
* `ρ = λ / μ` — коефіцієнт завантаження (утилізації) системи, де для стабільності черги обов'язково виконується умова `0 ≤ ρ < 1`.

За формулою Літтла середній час повного перебування запиту в системі `W` (час очікування в черзі сокета плюс час його обробки проксі) дорівнює:

```
W = 1 / (μ - λ) [формула Літтла для системи масового обслуговування M/M/1]
```

Виділимо з повного часу `W` чистий час очікування пакета в черзі сокета `W_q`, віднявши час безпосередньої обробки `1/μ`:

```
W_q = W - 1/μ                     [визначення часу очікування в черзі]
    = (1 / (μ - λ)) - (1 / μ)     [підстановка формули повного часу W]
    = (μ - (μ - λ)) / (μ·(μ - λ)) [зведення дробів до спільного знаменника]
    = λ / (μ·(μ - λ))             [розкриття дужок у чисельнику: μ - μ + λ = λ]
    = (λ / μ) · (1 / (μ - λ))     [винесення відношення λ/μ]
    = ρ / (μ·(1 - ρ))             [заміна λ/μ на коефіцієнт завантаження ρ]
```

Проаналізуємо поведінку черги на прикладі проксі-сайдкара з продуктивністю `μ = 10 000` запитів на секунду:

```
W_q(0.50) = 0.50 / (10000 · (1 - 0.50)) [розрахунок для утилізації 50%]
          = 0.50 / 5000                 [обчислення знаменника]
          = 0.00010 сек = 0.10 мс       [затримка черги при 50% навантаженні]

W_q(0.90) = 0.90 / (10000 · (1 - 0.90)) [розрахунок для утилізації 90%]
          = 0.90 / 1000                 [обчислення знаменника]
          = 0.00090 сек = 0.90 мс       [зростання затримки в 9 разів]

W_q(0.98) = 0.98 / (10000 · (1 - 0.98)) [розрахунок для утилізації 98%]
          = 0.98 / 200                  [обчислення знаменника]
          = 0.00490 сек = 4.90 мс       [критичне уповільнення у 49 разів]
```

Цей висновок пояснює, чому при утилізації процесора сайдкара понад 85–90% система переживає раптовий стрибок 99-го перцентиля затримок (p99 latency degradation): час очікування в сокетних буферах зростає гіперболічно, викликаючи переповнення черги `listen(backlog)` і масове скидання вхідних TCP SYN пакетів.

## 3. Критичний поріг вичерпання ефемерних портів (TIME_WAIT Starvation)

Якщо застосунок підключається до сайдкара через локальний TCP-сокет без використання пулу постійних з'єднань (короткоживучі HTTP-запити без заголовка `Connection: keep-alive`), кожне закрите з'єднання переходить у системний стан ядра `TIME_WAIT`.

Цей стан необхідний стеку TCP для того, щоб переконатися, що всі запізнілі або дубльовані пакети в мережі зникли, а фінальний пакет підтвердження `ACK` гарантовано дійшов до відправника. Тривалість перебування закритого сокета у стані `TIME_WAIT` жорстко зафіксована у вихідному коді ядра Linux константою `TCP_TIMEWAIT_LEN`:

```
T_wait = 2 · MSL = 60 секунд [де MSL = 30 с — Maximum Segment Lifetime ядра Linux]
```

Кількість доступних ефемерних портів для клієнтських сокетів на хості визначається діапазоном у конфігурації `/proc/sys/net/ipv4/ip_local_port_range` (типово від 32768 до 60999):

```
N_ports = 60999 - 32768 + 1 = 28232 порти [загальна місткість простору локальних портів]
```

При сталій частоті генерації нових короткоживучих з'єднань `R` (кількість нових TCP-сесій за секунду) кількість одночасно заблокованих сокетів у стані `TIME_WAIT` становить:

```
S_tw = R · T_wait [закон збереження: темп надходження помножений на час життя]
```

Для того щоб стек сокетів не заблокував нові з'єднання, кількість зайнятих портів повинна бути строго меншою за загальну місткість пулу:

```
R · T_wait < N_ports   [умова стабільності без вичерпання номерів портів]
R < N_ports / T_wait   [ділення обох частин нерівності на константу часу T_wait]
```

Підставимо граничні системні значення для інтерфейсу `127.0.0.1`:

```
R_max = 28232 / 60     [підстановка значень діапазону портів та часу 60 секунд]
      ≈ 470.53 порт/с  [теоретичний максимум частоти створення коротких TCP-сесій]
```

Цей розрахунок доводить фундаментальне обмеження: якщо інтенсивність локальних короткоживучих викликів до сайдкара перевищує **470 запитів на секунду** на одну пару IP-адрес, виклик ядра `connect()` гарантовано завершиться системною помилкою `EADDRNOTAVAIL` (Cannot assign requested address). Для подолання цього бар'єра інженери зобов'язані переходити на Unix Domain Sockets (`AF_UNIX`) або вмикати агресивний пул Keep-Alive з'єднань.

## 4. Кластерний баланс пам'яті: Sidecar проти DaemonSet

Порівняємо сумарні витрати оперативної пам'яті на рівні всього кластера між двома альтернативними інфраструктурними підходами:
1. **Модель Sidecar:** кожен Pod запускає власний ізольований екземпляр проксі (наприклад, Envoy).
2. **Модель DaemonSet:** один спільний екземпляр проксі запускається на кожному фізичному або віртуальному сервері (Node) і обслуговує всі локальні Pods цього вузла.

Введемо такі параметри системи:
* `N_nodes` — загальна кількість фізичних або віртуальних вузлів у кластері.
* `N_pods` — сумарна кількість контейнерних Pod у кластері.
* `P_node = N_pods / N_nodes` — середня щільність розміщення (кількість Pod на одному сервері).
* `M_base` — базовий обсяг оперативної пам'яті, необхідний для запуску одного екземпляра проксі (код, таблиці конфігурації xDS, кеш маршрутів).
* `M_conn` — обсяг системної пам'яті ядра та буферів на обслуговування одного активного клієнтського TCP-з'єднання.
* `C_pod` — середня кількість одночасних з'єднань, які підтримує один Pod.

Виведемо формули сумарного споживання пам'яті:

```
M_total_sidecar = N_pods · M_base + N_pods · C_pod · M_conn   [сумарна пам'ять моделі Sidecar]
                = N_pods · (M_base + C_pod · M_conn)          [винесення N_pods за дужки]
M_total_daemon  = N_nodes · M_base + N_pods · C_pod · M_conn  [сумарна пам'ять моделі DaemonSet]
```

Визначимо коефіцієнт надлишковості споживання пам'яті `K_overhead`:

```
K_overhead = M_total_sidecar / M_total_daemon                                                        [визначення коефіцієнта відношення]
           = (N_pods · (M_base + C_pod · M_conn)) / (N_nodes · M_base + N_pods · C_pod · M_conn)    [підстановка повних формул]
           ≈ (N_pods · M_base) / (N_nodes · M_base)                                                  [наближення: базовий рантайм M_base набагато більший за пам'ять сокетів]
           = N_pods / N_nodes                                                                        [скорочення базового обсягу пам'яті M_base]
           = P_node                                                                                  [коефіцієнт оверхеду дорівнює щільності Pods на вузол]
```

Розрахуємо практичний виробничий приклад для типового хмарного кластера Kubernetes:
* Кількість серверних вузлів: `N_nodes = 50`.
* Загальна кількість робочих навантажень: `N_pods = 2000` (тобто середня щільність `P_node = 40` Pod на сервер).
* Базовий розмір рантайму Envoy: `M_base = 50 МБ`.
* Пам'ять з'єднань: `M_conn = 10 КБ = 0.01 МБ`, при `C_pod = 20` з'єднань на Pod.

```
M_total_sidecar = 2000 · (50 + 20 · 0.01) [підстановка параметрів для Sidecar]
                = 2000 · (50 + 0.2)       [обчислення виразу в дужках]
                = 2000 · 50.2             [множення на кількість Pods]
                = 100400 МБ ≈ 100.4 ГБ    [сумарні витрати RAM для моделі Sidecar]

M_total_daemon  = 50 · 50 + 2000 · 20 · 0.01 [підстановка параметрів для DaemonSet]
                = 2500 + 400                 [додавання базової пам'яті та з'єднань]
                = 2900 МБ ≈ 2.9 ГБ           [сумарні витрати RAM для моделі DaemonSet]

ΔM = 100.4 ГБ - 2.9 ГБ                       [розрахунок різниці споживання пам'яті]
   = 97.5 ГБ                                 [чиста економія пам'яті при виборі DaemonSet]
```

Отриманий математичний результат чітко формулює архітектурний компроміс: ізоляція збоїв та простота управління моделлю Sidecar коштує кластеру **майже у 35 разів більше оперативної пам'яті** у порівнянні з моделлю загальновузлового DaemonSet.
