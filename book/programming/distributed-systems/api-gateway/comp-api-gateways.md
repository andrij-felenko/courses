# 🔌 Класи та архітектури API-шлюзів: зворотні проксі, шлюзи на краю, BFF та сервісні сітки

У розподілених системах існує кілька типів мережевих посередників, які виконують схожі функції маршрутизації та пересилання трафіку, проте оптимізовані під принципово різні архітектурні межі та шаблони використання. Помилка у виборі призводить або до надмірної складності й роздування затримок, або до перетворення шлюзу на монолітне вузьке місце команди розробки.

## Таксономія мережевих посередників

| Характеристика | Зворотний проксі (Reverse Proxy) | Загальний API-шлюз (API Gateway) | Бекенд для фронтенда (BFF) | Сервісна сітка (Service Mesh Sidecar) |
|---|---|---|---|---|
| **Типові реалізації** | Nginx, HAProxy, AWS ALB | Envoy, Kong, Apache APISIX, Traefik | Власний мікросервіс (Node.js/Go/Java) | Envoy (під керуванням Istio/Linkerd) |
| **Основна роль** | L4/L7 балансування, термінація TLS, кешування статики | Захист периметра, автентифікація, ліміти, маршрутизація API | Формування та агрегація специфічного DTO для конкретного UI | Внутрішня безпека сервіс-до-сервісу (mTLS, RBAC, спостережливість) |
| **Напрямок трафіку** | Північ-Південь (зовнішній) | Північ-Південь (зовнішній) | Північ-Південь (зовнішній) | Схід-Захід (внутрішній) |
| **Власник компонента** | Інфраструктурна / DevOps команда | Платформна команда / Core Architecture | Команда конкретного клієнта (Mobile/Web) | Платформна / SRE команда |
| **Рівень бізнес-логіки** | Відсутня (суто транспортний рівень) | Мінімальна (універсальні наскрізні фільтри) | Середня (агрегація, трансформація DTO) | Нульова (прозоре проксіювання) |
| **Життєвий цикл релізів** | Рідкісні зміни інфраструктури | Стабільний, централізований реліз плагінів | Часті релізи синхронно з мобільним/веб UI | Автоматичне інжектування sidecar-контейнера |

### Зворотний проксі проти API-шлюзу
Зворотний проксі (англ. *reverse proxy*) оперує базовими поняттями мережі та протоколу HTTP: IP-адреса, порт, шлях, заголовки, SSL-сертифікати. Його головна перевага — максимальна продуктивність і низьке споживання ресурсів при простому пересиланні байтів. Він ідеально підходить для балансування навантаження між однаковими копіями монолітного бекенда.

API-шлюз (англ. *API Gateway*) надбудовує над транспортом семантику прикладного інтерфейсу: він розуміє схеми даних (OpenAPI, JSON Schema, Protobuf), валідує криптографічні підписи JWT-токенів із публічних ключів JWKS, підтримує розподілені алгоритми обмеження швидкості (Token Bucket з інтеграцією в Redis), взаємодіє з динамічними реєстрами сервісів (Consul, Eureka, Kubernetes DNS) та веде розширену аналітику бізнес-викликів.

### Загальний шлюз проти патерна BFF
Загальний API-шлюз обслуговує **всіх** клієнтів через спільні, нейтральні до клієнта контракти. Якщо шлюз починає формувати різні варіанти відповідей окремо для iOS, окремо для Android, окремо для смарт-годинників та окремо для партнерського REST API, він швидко перетворюється на організаційне вузьке місце: десятки продуктових команд змушені ставати в чергу на реліз центрального шлюзу.

Патерн BFF (англ. *Backend-for-Frontend*) розв'язує цю проблему децентралізацією: кожна команда інтерфейсу володіє власним невеликим вузькоспеціалізованим бекендом, що стоїть **за** або **поруч** з API-шлюзом. Загальний шлюз перевіряє спільний токен і маршрутизує `/mobile/*` на Mobile-BFF, а `/web/*` на Web-BFF, залишаючи специфічну агрегацію полів відповідним продуктовим командам.

### API-шлюз проти сервісної сітки (Service Mesh)
API-шлюз захищає зовнішній периметр системи — напрямок «Північ-Південь» (англ. *North-South traffic*). Тут клієнт перебуває у відкритому ворожому інтернеті, не має фіксованої IP-адреси, використовує нестабільне з'єднання та автентифікується через Bearer-токени користувача.

Сервісна сітка (англ. *Service Mesh*) контролює внутрішні комунікації між сервісами всередині захищеного кластера — напрямок «Схід-Захід» (англ. *East-West traffic*). Вона запускається у вигляді локального процесу-помічника (sidecar) поруч із кожним контейнером застосунку, забезпечуючи автоматичне взаємне TLS-шифрування (mTLS) між сервісами, ротацію сертифікатів за протоколом SPIFFE/SPIRE та точні метрики затримок між вузлами кластера.

## Порівняння рушіїв: пам'ять, планувальник та мови реалізації

Продуктивність, затримки на високих перцентилях (p99/p99.9 latency) та стійкість до перевантажень безпосередньо залежать від мови реалізації шлюзу та моделі його планувальника подій:

### 1. C++ (Envoy Proxy)
* **Архітектура:** Модель *thread-per-core* на базі бібліотеки `libevent` та системного виклику `epoll`. Кількість робочих потоків дорівнює кількості ядер процесора; кожен потік володіє власним циклом подій і не блокується жодними операціями.
* **Пам'ять:** Повна відсутність збирача сміття (Garbage Collector). Пам'ять для буферів сокетів виділяється та звільняється детерміновано. Одне відкрите з'єднання споживає всього 1–3 КБ пам'яті.
* **Затримка:** Субмілісекундна базова затримка (<0.3 мс), абсолютна стабільність таймінгів p99 під екстремальним навантаженням.
* **Розширюваність:** C++ фільтри, підключення модулів WebAssembly (WASM) на базі рушія V8 або Wasmtime без перекомпіляції бінарника.

### 2. C / LuaJIT (Kong / Apache APISIX / OpenResty)
* **Архітектура:** Воркери Nginx на базі `epoll` з інтегрованим JIT-компілятором LuaJIT.
* **Пам'ять:** Базове ядро Nginx на C надзвичайно швидке та економне. Проте під час активного виконання складних Lua-плагінів створюються тимчасові таблиці Lua, що запускає збирач сміття LuaJIT GC.
* **Затримка:** Базове проксіювання триває менше 0.5 мс. Проте при неоптимальних Lua-скриптах з частими алокаціями можливі періодичні сплески затримок.
* **Розширюваність:** Величезна екосистема готових Lua-плагінів, підтримка зовнішніх плагінів на Go, Python, JavaScript через RPC-сокети.

### 3. Go (Traefik)
* **Архітектура:** Модель горутин (Goroutines) поверх вбудованого мережевого полінгу Go Runtime `netpoller`.
* **Пам'ять:** Кожна горутина має стартовий стек розміром 2 КБ, що динамічно зростає. Пам'ять контролюється триколірним збирачем сміття (Tri-color Concurrent GC).
* **Затримка:** Дуже висока швидкість розробки нових плагінів та надійна безпека пам'яті. Проте при десятках тисяч алокацій об'єктів на секунду цикли сканування пам'яті Go GC створюють паузи від 1 до 5 мс, що видно на 99.9-му перцентилі.
* **Розширюваність:** Автоматична інтеграція з Docker, Kubernetes, Consul, вбудований інтерпретатор Yaegi для динамічних плагінів на Go.

### 4. Java / Netty (Netflix Zuul 2 / Spring Cloud Gateway)
* **Архітектура:** Неблокуючий подієвий конвеєр на базі Netty (Java NIO Channels та EventLoopGroup).
* **Пам'ять:** Використовує пули позакупової пам'яті (Direct ByteBuffers) для уникнення копіювання байтів (Zero-Copy). Проте створення складних ланцюжків об'єктів запитів у JVM створює навантаження на Garbage Collector.
* **Затримка:** Від 1 до 3 мс. Вимагає ретельного налаштування параметрів збирача сміття (ZGC або G1GC) та прогріву JVM перед отриманням бойового трафіку.
* **Розширюваність:** Глибока інтеграція в екосистему Java / Spring Boot, використання реактивних потоків Project Reactor / RxJava.

## Блокуюча модель проти неблокуючої

```
1. Блокуюча модель (Thread-per-request / Blocking I/O):
   Клієнт 1 ────► [ Потік ОС 1: читання ──► чекання бекенда (блок) ──► відповідь ] (Стек 1–2 МБ)
   Клієнт 2 ────► [ Потік ОС 2: читання ──► чекання бекенда (блок) ──► відповідь ] (Стек 1–2 МБ)
   (10 000 клієнтів = 10 000 потоків = 10–20 ГБ пам'яті лише на стеки + шалений context switch)

2. Подієва асинхронна модель (Event Loop / epoll / kqueue):
   10 000 з'єднань ──► [ epoll_wait() ] ──► [ 1–4 робочі потоки ] ──► Неблокуючий автомат станів
   (10 000 клієнтів = 20–40 МБ пам'яті, потоки ніколи не блокуються, 100% утилізація CPU-кешу)
```

У блокуючій моделі виділення потоку ОС під кожне з'єднання накладає жорстку межу масштабування: планувальник ядра змушений постійно перемикати контексти між тисячами сплячих потоків, вимиваючи дані з кешів L1/L2 процесора.

У неблокуючій моделі сокети додаються до списку інтересів ядра через `epoll_ctl()`. Робочий потік ніколи не зупиняється в очікуванні відповіді від повільного мобільного клієнта чи бекенда: він отримує готові порції байтів через подієвий виклик `epoll_wait()` і миттєво передає їх у конвеєр фільтрів.

## Динамічна площина керування (Control Plane) проти перезавантаження

Традиційні вебсервери змінюють конфігурацію шляхом надсилання сигналу `SIGHUP` (`nginx -s reload`). Під час перезавантаження запускаються нові робочі процеси, а старі переходять у режим плавного вичерпання активних сесій (Connection Draining). У динамічному кластері Kubernetes, де автоскейлінг змінює адреси подів щохвилини, постійні перезапуски воркерів створюють навантаження на процесор, призводять до накопичення пам'яті та зривають відкриті стрімінгові з'єднання WebSocket.

Сучасні шлюзи Envoy використовують динамічний протокол **xDS** (Discovery Service API поверх gRPC):
* **LDS (Listener Discovery Service):** динамічне додавання портів, зміна TLS-сертифікатів та ланцюжків фільтрів.
* **RDS (Route Discovery Service):** потокове оновлення правил маршрутизації шляхів без зупинки процесу.
* **CDS (Cluster Discovery Service):** додавання, видалення та зміна конфігурації upstream-кластерів.
* **EDS (Endpoint Discovery Service):** миттєва потокова синхронізація списків IP-адрес здорових подів.

Завдяки xDS шлюз отримує нові маршрути та адреси за частки мілісекунди без жодного перезапуску, гарантуючи нульовий простій (Zero-Downtime) та неперервність з'єднань користувачів.
