# 📋 Інтерфейс та конфігурація адаптивного лімітера конкурентності

Адаптивний лімітер конкурентності надає програмний та декларативний конфігураційний контракт для інтеграції в мережеві шлюзи (API Gateway), сервісні сітки (Service Mesh / Envoy) та прикладні RPC/HTTP-сервери. Інтерфейс забезпечує повне відокремлення бізнес-логіки обробки запитів від механізмів вимірювання затримок, динамічного обчислення пропускної здатності та раннього відсікання перевантаження.

Нижче наведено детальну специфікацію параметрів конфігурації, програмних інтерфейсів, протокольних кодів відповідей, конфігурації Envoy Proxy, взаємодії з автоскейлерами Kubernetes, метрик спостережуваності та процедур верифікації.

## Конфігураційні параметри та їхній вплив на стабільність

Адаптація ліміту регулюється набором параметрів, що визначають діапазон безпеки, чутливість до зростання черг та динаміку оновлення базової затримки.

| Параметр | Тип | За замовчуванням | Опис і вплив на систему |
| :--- | :--- | :--- | :--- |
| `min_limit` | `float` | `5.0` | Нижня межа паралелізму. Захищає від повного блокування трафіку під час аномальних сплесків затримки або збоїв вимірювання. |
| `max_limit` | `float` | `1000.0` | Верхня межа паралелізму. Запобігає неконтрольованому виділенню пам'яті та дефіциту дескрипторів сокетів операційної системи. |
| `initial_limit` | `float` | `20.0` | Стартовий ліміт при запуску сервісу до накопичення першого вікна телеметрії. |
| `headroom` | `float` | `10.0` | Параметр запасу черги `h` (або `β` у Vegas). Задає допустиму кількість запитів у черзі для зондування максимальної пропускної здатності. |
| `smoothing` | `float` | `0.2` | Вага експоненційного згладжування `σ ∈ (0, 1]`. Менші значення згладжують шум, більші — прискорюють реакцію на перевантаження. |
| `sample_window_size` | `uint32` | `50` | Кількість завершених запитів у межах одного вікна для розрахунку вибіркового `sampleRTT`. |
| `sample_window_duration_ms` | `uint32` | `500` | Максимальний інтервал часу для закриття вікна вибірки за низького вхідного трафіку. |
| `min_rtt_ttl_sec` | `uint32` | `300` | Час життя базового `minRTT` (5 хвилин). Після спливання базис вимірюється наново для адаптації до легітимного дрейфу затримки. |
| `backoff_factor` | `float` | `0.7` | Мультиплікативний коефіцієнт екстреного стискання ліміту при виявленні сплеску помилок таймаутів. |

### Детальний аналіз інженерних компромісів

Кожен конфігураційний параметр безпосередньо впливає на форму перехідного процесу системи:

1. **Баланс між чутливістю та стійкістю (`smoothing`):**
   При значенні `smoothing = 0.5` лімітер реагує на перевантаження вдвічі швидше, проте стає схильним до хибних коливань через поодинокі важкі запити. При значенні `smoothing = 0.05` система ідеально фільтрує стохастичний шум, але в разі раптового уповільнення бази даних буде занадто довго тримати високий ліміт, пропускаючи руйнівні черги.
2. **Розмір вікна вибірки (`sample_window_size`):**
   Мале вікно (10–20 запитів) забезпечує субсекундну реакцію на сплески трафіку, але створює високу дисперсію оцінки `sampleRTT`. Велике вікно (100–500 запитів) гарантує високу статистичну точність, але затримує коригування ліміту на кілька секунд.
3. **Параметр запасу черги (`headroom`):**
   Якщо встановити `headroom = 0`, лімітер ніколи не спробує збільшити конкурентність вище поточної точки, оскільки будь-яке збільшення призводить до зростання затримки і відкидає градієнт `g < 1`. Значення `headroom > 0` створює постійний контрольований тиск угору, змушуючи систему досліджувати, чи не з'явилися додаткові ресурси.

## Програмний контракт (C++ / IDL)

Контракт лімітера передбачає мінімалістичний інтерфейс із двох основних фаз: допуску (`try_acquire`) та повернення телеметрії (`complete`).

```cpp
namespace concurrency {

enum class Priority {
    Critical = 0,   // Авторизація, платіжні транзакції, Health Checks
    Standard = 1,   // Типові користувацькі операції читання та запису
    Background = 2  // Пакетні задачі, аналітика, оновлення індексів
};

struct RequestTelemetry {
    double duration_ms;       // Фактична тривалість обробки запиту
    bool is_success;          // Чи завершився запит успішно
    int http_status;          // Код відповіді HTTP або gRPC
    Priority priority;        // Пріоритет запиту
};

class ILimiterToken {
public:
    virtual ~ILimiterToken() = default;
    
    // Завершення обробки з явною передачею телеметрії
    virtual void complete(const RequestTelemetry& telemetry) = 0;
    
    // Скасування операції без врахування у вибірці затримок
    virtual void cancel() = 0;
};

class IAdaptiveConcurrencyLimiter {
public:
    virtual ~IAdaptiveConcurrencyLimiter() = default;

    // Спроба отримати допуск до виконання
    virtual std::unique_ptr<ILimiterToken> try_acquire(Priority priority) = 0;

    // Поточні показники стану для моніторингу
    virtual double get_current_limit() const noexcept = 0;
    virtual int get_in_flight() const noexcept = 0;
    virtual double get_min_rtt_ms() const noexcept = 0;
};

} // namespace concurrency
```

## Протокольний контракт: HTTP та gRPC

Коли кількість активних запитів перевищує розрахований ліміт, сервіс зобов'язаний негайно повертати стандартизовані протокольні статуси без виділення пулів обробки:

### HTTP / REST
- **HTTP Status:** `429 Too Many Requests` або `503 Service Unavailable`;
- **Заголовок `Retry-After:`** рекомендує клієнту інтервал очікування перед повторною спробою (наприклад, `Retry-After: 1` або `Retry-After: 0.5`);
- **Заголовок `X-Envoy-Degraded:`** `true` (для інформування балансувальника про перевантаження вузла);
- **Тіло відповіді:** компактний JSON з інформацією про причину відмови:
  ```json
  {
    "error": "concurrency_limit_exceeded",
    "message": "Service is operating at maximum capacity. Please retry later.",
    "retry_after_ms": 500
  }
  ```

### gRPC
- **Статус-код:** `codes.ResourceExhausted` (14) або `codes.Unavailable` (14);
- **Деталі помилки (Error Details):** об'єкт `google.rpc.RetryInfo` із зазначенням рекомендованого інтервалу затримки `retry_delay`.

## Декларативна конфігурація у сервісній сітці (Envoy Adaptive Concurrency)

У сучасних хмарних інфраструктурах адаптивний лімітер часто конфігурується декларативно на рівні sidecar-проксі Envoy без модифікації коду сервісу. Фільтр `envoy.filters.http.adaptive_concurrency` вбудовується безпосередньо в HTTP-конвеєр проксі:

```yaml
name: envoy.filters.http.adaptive_concurrency
typed_config:
  "@type": type.googleapis.com/envoy.extensions.filters.http.adaptive_concurrency.v3.AdaptiveConcurrency
  gradient_controller_config:
    sample_aggregate_percentile:
      value: 90.0
    concurrency_limit_params:
      concurrency_update_interval: 0.5s
      max_concurrency_limit: 1000
    min_rtt_calc_params:
      jitter:
        value: 10.0
      interval: 300s
      request_count: 50
      min_concurrency: 5
      buffer:
        value: 10.0
  enabled:
    default_value: true
    runtime_key: "adaptive_concurrency.enabled"
```

У наведеній конфігурації Envoy використовує 90-й перцентиль затримки для вибірки, що усуває вплив поодиноких викидів, кожні 5 хвилин виконує калібрування `minRTT` через короткочасне зменшення ліміту до 5 з'єднань, а також надає динамічний перемикач через Runtime Flags для екстреного вимкнення за потреби.

## Взаємодія з автоскейлерами Kubernetes (HPA Integration)

При експлуатації в кластерах Kubernetes адаптивні лімітери працюють у тандемі з горизонтальним автоскейлером (Horizontal Pod Autoscaler):

1. **Запобігання пастці псевдо-розвантаження:**
   Коли сервіс скидає надлишковий трафік на вході через швидкі помилки `429`, завантаження процесора (CPU utilization) може знизитися, створюючи хибне враження недовантаження. Якщо HPA орієнтується суто на метрику CPU, він почне масштабувати кластер униз, поглиблюючи дефіцит ресурсів;
2. **Орієнтація на кастомні метрики лімітера:**
   Рекомендується налаштовувати HPA за метрикою `adaptive_concurrency_in_flight / adaptive_concurrency_limit` або за кількістю скинутих запитів `adaptive_concurrency_dropped_total`. Якщо відношення наближається до 0.9, автоскейлер додає нові поди до того, як система почне масово відхиляти виклики.

## Розподілений контекст та каскадне сповіщення

Коли мікросервіс на глибині дерева викликів починає скидати трафік через адаптивний ліміт, вкрай важливо, щоб батьківські сервіси не повторювали безнадійні запити:

1. **Транзитна передача заголовків деградації:**
   Якщо внутрішній бекенд повертає `429 Too Many Requests` з заголовком `X-Upstream-Shed: true`, шлюз зобов'язаний прокинути цей сигнал клієнту або перемкнутися на аварійний локальний кеш (Fallback);
2. **Атрибути трейсингу OpenTelemetry:**
   Кожен відхилений або допущений виклик збагачує активний спан трейсингу такими атрибутами:
   - `concurrency.limit` — значення ліміту на момент ухвалення рішення;
   - `concurrency.in_flight` — поточна кількість активних завдань;
   - `concurrency.admitted` — булевий прапорець результату перевірки (`true/false`);
   - `concurrency.gradient` — розрахований коефіцієнт градієнта затримки.

## Метрики спостережуваності (Prometheus / OpenTelemetry)

Для моніторингу працездатності адаптивного лімітера, раннього виявлення аномалій та налаштування сповіщень експортуються такі ключові метрики:

| Назва метрики | Тип | Опис та діагностичне призначення |
| :--- | :--- | :--- |
| `adaptive_concurrency_limit` | `Gauge` | Поточне розраховане значення ліміту паралелізму. Різке падіння свідчить про уповільнення бекенду. |
| `adaptive_concurrency_in_flight` | `Gauge` | Кількість запитів, що виконуються в даний момент. Досягнення рівня `limit` сигналізує про переповнення. |
| `adaptive_concurrency_rtt_sample_ms` | `Gauge` | Середня або P90 затримка завершених запитів у поточному вікні вибірки. |
| `adaptive_concurrency_rtt_min_ms` | `Gauge` | Базова затримка системи без навантаження (`minRTT`). |
| `adaptive_concurrency_gradient` | `Gauge` | Значення коефіцієнта `g = minRTT / sampleRTT`. Значення менше 1.0 свідчить про накопичення черг. |
| `adaptive_concurrency_dropped_total` | `Counter` | Кількість відхилених запитів з розподілом за пріоритетами (`priority="critical|standard|background"`). |

### Практичні правила налаштування сповіщень (Alerting Rules)

На основі експортованих метрик чергові інженери налаштовують автоматичні алерти:

1. **Тривале затискання ліміту (`LimitNearMin`):**
   Якщо значення `adaptive_concurrency_limit` тримається біля `min_limit` понад 3 хвилини поспіль, це сигналізує про стійку аварію в системі (блокування в базі даних, втрата кешу або деградація каналу зв'язку);
2. **Високий відсоток скидання трафіку (`HighDropRate`):**
   Якщо швидкість зростання `adaptive_concurrency_dropped_total` перевищує 5% від загального вхідного потоку, це означає, що система увійшла в режим жорсткого захисту від перевантаження і потребує горизонтального масштабування (Auto-scaling);
3. **Аномальний дрейф градієнта (`GradientSuppression`):**
   Коли коефіцієнт `adaptive_concurrency_gradient < 0.5` тримається протягом багатьох вікон підряд, це свідчить про глибоке переповнення внутрішніх черг, яке не встигає розвантажитися штатним темпом.

## Процедура тестування та хаос-інжинірингу

Перед розгортанням у продакшені поведінку лімітера верифікують двома обов'язковими сценаріями тестування навантаженням:

1. **Тест стрибкоподібного навантаження (Step Load Test):**
   Навантаження штучно збільшують у 5 разів за одну секунду. Правильно налаштований лімітер повинен миттєво відхилити близько 80% запитів з кодом `429`, при цьому затримка 20% успішно допущених запитів не повинна зрости більш ніж на 15% від базового `minRTT`.
2. **Тест ін'єкції затримок (Latency Injection Test):**
   У бізнес-метод додається штучна затримка (sleep 100 мс). Лімітер зобов'язаний за кілька ітерацій автоматично зменшити `current_limit` пропорційно зростанню затримки, зберігши стабільність пулу потоків та відсутність нескінченних черг.
