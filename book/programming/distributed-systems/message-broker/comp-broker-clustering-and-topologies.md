# 🔌 Архітектурні топології брокерів: від Active-Passive до Raft-кворумів і міжхмарних мостів

Кластеризація сервера-брокера повідомлень є принципово складнішим інженерним завданням, ніж масштабування звичайних вебсерверів чи безстанних API-шлюзів. Якщо безстанний шлюз можна легко розмножити на сотні екземплярів за звичайним балансувальником навантаження (L4/L7 Load Balancer), то брокер повідомлень є **глибоко станною системою** (англ. *Stateful System*).

Кожне повідомлення в черзі має унікальний стан: воно може бути готовим до видачі, перебувати в стані оренди конкретним воркером (In-Flight), очікувати підтвердження (ACK), бути відхиленим (NACK) або підлягати списанню за таймаутом (TTL). Ба більше, класичні черги вимагають збереження порядку надходження (FIFO) та інваріанта руйнівного вичитування (одне повідомлення видається строго одному споживачу й видаляється після обробки). Спроба одночасної видачі одного й того самого елемента двом воркерам із різних вузлів кластера призводить до подвійного списання грошей чи дублювання замовлень.

Щоб збалансувати надійність, продуктивність та стійкість до мережевих розривів, в індустрії розподілених систем сформувалося п'ять базових архітектурних топологій розгортання брокерів.

## 1. Автономний брокер з гарячим резервом (Active-Passive Shared Storage)

Найпростіша та історично перша модель забезпечення високої доступності брокера. Вона спирається на надійність апаратного рівня або спільного дискового масиву замість складної мережевої реплікації стану.

```
Топологія Active-Passive зі спільним диском:
                    ┌───────────────────────────────┐
                    │ Віртуальна IP / Балансувальник │
                    └──────────────┬────────────────┘
                                   │ (Активний трафік)
                                   ▼
┌───────────────────────────┐             ┌───────────────────────────┐
│     Основний брокер       │             │     Резервний брокер      │
│        (ACTIVE)           │ ◄─Heartbeat─► │        (STANDBY)          │
│   • Обробляє I/O клієнтів │             │   • Процес зупинений або  │
│   • Утримує блокування    │             │     чекає вивільнення     │
└─────────────┬─────────────┘             └─────────────┬─────────────┘
              │                                         │
              │ (Ексклюзивне монтування)                │ (Холодний монтаж при аварії)
              ▼                                         ▼
       ┌───────────────────────────────────────────────────────┐
       │     Спільне дискове сховище (SAN / NAS / AWS EBS)     │
       │        • Файли черг, WAL-журнали та індекси           │
       └───────────────────────────────────────────────────────┘
```

### Механізм роботи
- В інфраструктурі розгортаються два сервери: Основний (*Primary / Active*) та Резервний (*Secondary / Standby*).
- Основний вузол монтує спільний том мережевого блокового сховища (SAN, Fibre Channel, iSCSI, DRBD або хмарний том на зразок AWS EBS) і накладає на нього ексклюзивне файлове блокування.
- Клієнтські застосунки підключаються до основного вузла через віртуальну IP-адресу (VIP, керовану демоном Keepalived) або DNS-запис із низьким TTL.
- Сторонній менеджер кластера (Pacemaker, Corosync) постійно опитує стан основного сервера через контрольні сигнали пульсу (*heartbeat*).
- Якщо основний вузол зазнає апаратної аварії, менеджер кластера примусово знімає блокування диска, монтує файлову систему на резервному вузлі, перемикає віртуальну IP-адресу й запускає процес брокера.

### Переваги та обмеження
- **Переваги:** Повна відсутність ризику роздвоєння стану (Split-Brain) на рівні даних — спільний диск є єдиним джерелом правди. Простота розробки клієнтів (брокер виглядає як звичайний одиничний сервер).
- **Недоліки:** Тривалий час відновлення працездатності (англ. *Recovery Time Objective, RTO* становить від 30 до 90 секунд, поки новий процес перевірить журнал файлової системи та відновить індекси). Нераціональне використання ресурсів (резервний сервер простоює).

## 2. Кластер без спільного стану з дзеркальними чергами (Classic Mirrored Queues)

Ця топологія, реалізована в класичних версіях RabbitMQ, об'єднує кілька незалежних вузлів у єдиний логічний кластер через внутрішню розподілену базу метаданих (наприклад, Mnesia в середовищі Erlang/OTP).

```
Класичні дзеркальні черги (Master-Slave усередині кластера):
┌───────────────────────────┐             ┌───────────────────────────┐
│          Вузол 1          │             │          Вузол 2          │
│   ┌───────────────────┐   │             │   ┌───────────────────┐   │
│   │  Лідер черги A    │───┼─Реплікація──┼──►│ Дзеркало черги A  │   │
│   │     (MASTER)      │   │ (Sync/Async)│   │      (SLAVE)      │   │
│   └───────────────────┘   │             │   └───────────────────┘   │
│   ┌───────────────────┐   │             │   ┌───────────────────┐   │
│   │ Дзеркало черги B  │◄──┼─Реплікація──┼───│  Лідер черги B    │   │
│   │      (SLAVE)      │   │             │   │     (MASTER)      │   │
│   └───────────────────┘   │             │   └───────────────────┘   │
└───────────────────────────┘             └───────────────────────────┘
```

### Механізм роботи
- Усі вузли кластера мають повну копію метаданих: вони знають про всі обмінники, черги, зв'язки та права користувачів.
- Клієнт може підключитися до **будь-якого** вузла кластера. Якщо клієнт звертається до черги, лідер якої розташований на іншому вузлі, локальний вузол прозоро маршрутизує запит через внутрішню мережу кластера (Erlang Distribution Protocol).
- Для кожної черги призначається один вузол-лідер (*Master*) та одне або кілька дзеркал (*Slaves*).
- Усі операції запису та підтвердження надходять виключно до лідера, який послідовно транслює їх на всі активні дзеркала.

### Пастка синхронізації та режими розділення мережі
Класичні дзеркальні черги страждають від двох фундаментальних вад:
1. **Блокування під час синхронізації:** якщо дзеркальний вузол перезавантажується, він підключається як «несинхронізований». Якщо адміністратор увімкне автоматичну синхронізацію (`ha-sync-mode: automatic`), черга **повністю блокує прийом нових повідомлень та видачу споживачам**, поки гігабайти накопичених даних передаються мережею на новий вузол.
2. **Вразливість до розриву мережі (Split-Brain):** якщо мережевий зв'язок між вузлами переривається, вузли в ізольованому сегменті вважають лідера загиблим і самостійно обирають нових лідерів для дзеркальних черг. У системі виникає два незалежні майстри для однієї черги. Коли зв'язок відновлюється, автоматичне злиття неможливе — одна з гілок даних буде безповоротно знищена.

Для боротьби з цим класичні кластери пропонують три евристичні стратегії розділення (`cluster_partition_handling`):
- `ignore`: кластер ігнорує розрив. Обидва сегменти продовжують працювати, що гарантує втрату або дублювання даних після відновлення зв'язку.
- `pause_minority`: вузли кластера, які бачать менше половини загальної кількості вузлів, автоматично призупиняють прийом трафіку, запобігаючи неконтрольованій модифікації стану.
- `autoheal`: після відновлення зв'язку обирається сегмент-переможець із найбільшою кількістю клієнтів, а всі вузли з меншості примусово перезавантажуються з повною втратою локально записаних даних.

## 3. Кворумні черги на базі консенсусу Raft (Quorum Queues)

Сучасний стандарт побудови відмовостійких брокерів повідомлень (впроваджений у RabbitMQ 3.8+ та сучасних хмарних брокерах). Топологія спирається на алгоритм розподіленого консенсусу **Raft**.

```
Кворумна черга з 3 вузлів (консенсус Raft 2F+1):
Продюсер
   │  1. basic.publish
   ▼
┌─────────────────────────────────┐
│ Вузол 1 (Raft Leader черги)     │
│ • Приймає повідомлення          │
│ • Записує у власний WAL-лог     │
└───────┬─────────────────┬───────┘
        │                 │
        │ 2. AppendEntries│ 2. AppendEntries
        ▼                 ▼
┌──────────────────┐   ┌──────────────────┐
│ Вузол 2 (Follower│   │ Вузол 3 (Follower│
│ • Запис у WAL    │   │ • Офлайн / Збій  │
│ • Відповідь: OK  │   │   немає зв'язку  │
└───────┬──────────┘   └──────────────────┘
        │
        │ 3. Log Replication ACK (Кворум 2/3 досягнуто!)
        ▼
   4. Publisher Confirm (Продюсеру повернено успіх)
```

### Механізм роботи
- Кворумна черга розподіляється строго по непарній кількості вузлів кластера: `2F + 1` (зазвичай 3 або 5 вузлів, де `F` — допустима кількість одночасних аварій).
- Кожна черга є повністю незалежним екземпляром реплікованого автомата станів Raft.
- Для успішної фіксації повідомлення або операції підтвердження (ACK) лідер зобов'язаний отримати підтвердження запису у дисковий журнал випереджального запису від **простої мажоритарної більшості вузлів** (кворуму):
```
Q = ⌊N / 2⌋ + 1      [розрахунок мінімального кворуму для кластера з N вузлів]
```
Для кластера з 3 вузлів `Q = ⌊3/2⌋ + 1 = 2`. Якщо один вузол зазнає аварії, кластер продовжує обслуговувати операції читання та запису без затримок.

### Ущільнення журналу (Log Compaction) та збереження стану
Оскільки Raft веде безперервний журнал операцій (`publish`, `deliver`, `ack`), зі зростанням кількості повідомлень журнал вичерпав би дисковий простір. Кворумні черги реалізують періодичне скидання знімків стану (англ. *Snapshots*) та ущільнення журналу:
- Коли всі підтверджені (`ACK`) повідомлення видаляються зі стану черги, відповідні записи вилучаються з журналу Raft.
- Якщо відстаючий вузол повертається до мережі після тривалого збою, лідер передає йому компактний моментальний знімок стану замість повторного відтворення мільйонів застарілих транзакцій.

### Чому кворумні черги безпечні
- **Імунітет до Split-Brain:** меншість вузлів (наприклад, 1 вузол із 3) фізично не здатна зібрати кворум (`1 < 2`) і переходить у стан очікування, відмовляючи клієнтам у записі. Тільки сегмент із більшістю вузлів обирає нового лідера.
- **Неблокуюче підключення вузлів:** новий або відновлений вузол наздоганяє лідера у фоновому режимі через потік записів Raft, не блокуючи поточну роботу черги.

## 4. Федерація брокерів та конвеєрні мости (Federation & Shovels)

Коли розподілена система масштабується між різними географічними регіонами (наприклад, дата-центр у Франкфурті та дата-центр у Сінгапурі) або різними хмарними провайдерами (AWS та Google Cloud), створення єдиного тісно пов'язаного кластера стає неможливим через високу мережеву затримку WAN (100–250 мс) та ризик частих розривів трансконтинентальних каналів.

Для таких сценаріїв використовують слабкозв'язані топології: **Федерацію (Federation)** та **Конвеєрні мости (Shovels)**.

```
Федерація брокерів через глобальну мережу (WAN):
┌───────────────────────────────────────┐            ┌───────────────────────────────────────┐
│     Кластер Франкфурт (EU-West)       │            │      Кластер Сінгапур (AP-South)      │
│                                       │            │                                       │
│ ┌──────────────┐    ┌──────────────┐  │            │ ┌──────────────┐    ┌──────────────┐  │
│ │  Exchange A  │───►│ Локальна     │  │            │ │ Федеративний │───►│ Локальна     │  │
│ │  (Upstream)  │    │ Черга EU     │  │            │ │ Exchange A   │    │ Черга SG     │  │
│ └──────┬───────┘    └──────────────┘  │            │ └──────▲───────┘    └──────────────┘  │
│        │                              │            │        │                              │
└────────┼──────────────────────────────┘            └────────┼──────────────────────────────┘
         │                                                    │
         └───────────── Асинхронний WAN-канал (AMQP/TLS) ─────┘
                       (Буферизація, повтори при обривах)
```

### Механізм роботи
- Кожен дата-центр має власний автономний кластер брокерів. Усі локальні операції виконуються з мікросекундними затримками у приватній мережі.
- **Федеративний обмінник (Federated Exchange):** підключається до висхідного обмінника (*Upstream*) у віддаленому регіоні як звичайний споживач. Коли клієнт у Сінгапурі підписується на повідомлення з ключем `orders.eu`, федеративний механізм прозоро транслює цей інтерес у Франкфурт і пересилає лише відповідні повідомлення.
- **Міст-лопата (Shovel):** простий фоновий процес, який безперервно вичитує повідомлення з черги в одному брокері й перепублікує їх у чергу іншого брокера. Якщо WAN-зв'язок зникає на 4 години, повідомлення спокійно накопичуються в локальній черзі відправника й передаються одразу після відновлення каналу.

### Захист від зациклення повідомлень (Loop Detection)
У складних багатоланкових федераціях, де брокери з'єднані в кільцеві топології (наприклад, Київ → Франкфурт → Лондон → Київ), існує небезпека безкінечного циклічного пересилання одного й того самого повідомлення.

Для розриву таких петель федеративні механізми використовують службові заголовки трасування:
- Кожен брокер під час пересилання додає своє ім'я до списку `x-received-from` у властивостях повідомлення.
- Якщо брокер отримує повідомлення, в заголовку якого вже зазначено його власний вузол або перевищено ліміт переходів (`max-hops`), він негайно знищує дублікат без повторної публікації.

## 5. Периферійно-хмарний міст (Edge-to-Cloud Broker Bridge)

У системах Інтернету речей (IoT), підключеного транспорту та промислової автоматизації мільйони пристроїв генерують телеметрію на периферії мережі (*Edge*).

```
Периферійно-хмарна топологія:
Локальні сенсори (Завод 1)                 Хмарний дата-центр
┌────────────┐                               ┌─────────────────────────────────┐
│ Датчик #1  ├──MQTT QoS 0──┐                │      Центральний кластер        │
└────────────┘              ▼                │      (RabbitMQ / EMQX Cluster)  │
┌────────────┐     ┌─────────────────┐       │                                 │
│ Датчик #2  ├───► │ Локальний Edge  ├─mTLS──┼─► ┌───────────────────────────┐ │
└────────────┘     │ Брокер          │(Пакет)│   │  Хмарний обмінник / Тема  │ │
┌────────────┐     │ (Mosquitto/EMQX)│       │   └─────────────┬─────────────┘ │
│ Датчик #3  ├───► └─────────────────┘       │                 │               │
└────────────┘                               └─────────────────┼───────────────┘
                                                               ▼
                                                    Аналітика та сховища
```

- На кожному заводі, судні чи вежі зв'язку встановлюється легковагий периферійний брокер (Mosquitto, EMQX Edge).
- Локальні сенсори публікують сотні тисяч дрібних повідомлень за секунду через локальну Wi-Fi або RS-485 мережу без затримок.
- Периферійний брокер фільтрує шум, виконує агрегацію, стискає дані в пакети та передає їх у центральний хмарний кластер через захищене TLS-з'єднання.

## Порівняльна матриця архітектурних топологій

```
Критерій             Active-Passive       Класичні дзеркала    Кворумні черги (Raft)  Федерація / Shovels  Edge-to-Cloud Bridge
Модель консистентності Strong (Спільний диск) Ненадійна (AP)       Strong Majority (CP)   Eventual Consistency Eventual Consistency
Стійкість до Split-Brain Абсолютна        Вразлива             Повна (через мажоритарій) Повна (ізольовані зони) Повна (буфер на краю)
Накладні витрати I/O Низькі               Середні              Високі (диск + кворум) Низькі               Мінімальні (пакетування)
Час перемикання (RTO) 30–90 секунд        1–5 секунд           0.5–2 секунди          Неперервно           Неперервно
```
