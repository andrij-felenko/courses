# 📜 Еволюція ідемпотентної обробки повідомлень: від XA/2PC до семантики Effectively-Once

У розподілених обчислювальних системах спроба побудувати надійний обмін повідомленнями без дублювання пройшла сорокарічний шлях від наївного сподівання на прозорі розподілені транзакції до усвідомлення простого факту: фізичний транспорт завжди дублює пакети, а захист від повторів є фундаментальною відповідальністю прикладного споживача.

## 1980–1990-ті: Ера моніторів транзакцій та ілюзія стандарту XA

Наприкінці 1980-х років розвиток корпоративних клієнт-серверних систем породив концепцію моніторів обробки транзакцій (TP-Monitors, від англійського *Transaction Processing Monitor*). Системи Tuxedo (розроблена в Bell Labs у 1983 році) та IBM Encina намагалися поширити класичні властивості ACID (атомарність, узгодженість, ізольованість, довговічність) на кілька незалежних вузлів через мережу.

1991 року консорціум The Open Group опублікував стандарт XA (від англійського *eXtended Architecture* — розширена архітектура), який стандартизував протокол двофазної фіксації (2PC, від англійського *Two-Phase Commit*). Архітектура описувала взаємодію трьох компонентів:
* **Менеджер додатків** (Application Program, AP) — визначає межі глобальної транзакції.
* **Менеджер ресурсів** (Resource Manager, RM) — база даних або черга повідомлень.
* **Менеджер транзакцій** (Transaction Manager, TM) — центральний координатор, який керує фазами підготовки (`PREPARE`) та фіксації (`COMMIT`).

```
AP (Додаток) ───► TM (Координатор) ───► Фаза 1: PREPARE (БД + Черга)
                                   ───► Фаза 2: COMMIT (Всі вузли)
```

У межах стандарту XA здавалося, що проблему доставки повідомлень розв'язано: вичитка з черги та запис у реляційну базу об'єднувалися в єдину розподілену транзакцію. Якщо процес падав або мережа давала збій, координатор відкочував зміни в обох системах, гарантуючи виконання «строго один раз».

Проте на практиці протокол XA виявився критично вразливим до мережевих збоїв. Протокол 2PC є блокуючим за своєю природою: якщо координатор зазнає аварії після того, як база даних відповіла `PREPARED`, рядки в таблицях залишаються заблокованими на невизначений термін. Усі паралельні транзакції вишиковуються в чергу очікування, пам'ять вичерпується, а пропускна здатність кластера падає до нуля. Крім того, накладні витрати на синхронні мережеві раунди робили XA непридатним для систем із затримками понад 5–10 мілісекунд.

## 2000-ні: Повідомні шини та патерн Idempotent Receiver

На початку 2000-х років із переходом до сервісно-орієнтованої архітектури (SOA) індустрія відмовилася від розподілених блокувань на користь асинхронного обміну повідомленнями через брокери (IBM MQSeries, TIBCO Rendezvous, специфікація Java Message Service — JMS).

2003 року Грегор Гопе (Gregor Hohpe) та Боббі Вулф (Bobby Woolf) опублікували фундаментальну працю *Enterprise Integration Patterns*. У цій книзі вперше на рівні загальноприйнятого архітектурного шаблону було зафіксовано патерн **Idempotent Receiver** (Ідемпотентний отримувач).

Автори сформулювали фундаментальний принцип: замість намагання змусити мережу доставляти повідомлення рівно один раз, транспорт повинен гарантувати простішу й надійнішу семантику «щонайменше один раз» (*at-least-once*), а отримувач зобов'язаний самостійно фільтрувати або безпечно поглинати повторні копії.

Для ідентифікації повторів використовувалися унікальні ідентифікатори повідомлень (`JMSMessageID`), які споживачі зберігали в локальних таблицях дедуплікації. Проте в межах технологій 2000-х років таблиці велися наївно: без обмеження розміру вікна зберігання, без врахування витоку ключів пам'яті та без захисту від збоїв під час виклику зовнішніх сторонніх систем.

## 2010-ті: Журнали подій Apache Kafka та KIP-98

Справжня революція у масштабованій обробці потокових даних відбулася у 2010–2011 роках, коли інженери LinkedIn (Джей Крепс, Неха Нархеде, Джун Рао) створили Apache Kafka — розподілений розподілений журнал подій (append-only commit log), що масштабувався через партиціювання.

Kafka довела, що найефективніша модель брокера — це послідовний незмінний лог із монотонними числовими зсувами (offset), де брокер не відстежує стан кожного окремого повідомлення для кожного споживача, а споживач сам контролює свій вказівник зчитування.

У 2017 році команда Kafka випустила оновлення **KIP-98** (*Exactly Once Delivery and Transactional Messaging*). У межах KIP-98 було впроваджено:
1. **Ідемпотентний продюсер** (Idempotent Producer): кожному клієнту-відправнику брокер призначає 64-бітний ідентифікатор продюсера (`PID`, від англійського *Producer ID*) та епоху (`Epoch`). Кожне повідомлення отримує монотонний порядковий номер (`Sequence Number`). Брокер записує подію в партицію лише тоді, коли її номер строго дорівнює `Last_Seen_Seq + 1`, автоматично відкидаючи дублікати, викликані повторними спробами мережевого клієнта.
2. **Транзакційний координатор** (Transaction Coordinator): механізм атомарного запису повідомлень у кілька топіків та фіксації зсувів споживача в рамках єдиної транзакції (патерн *consume-transform-produce*).

KIP-98 забезпечив строгу семантику «рівно один раз» у замкненому контурі «Kafka-to-Kafka». Проте інженерна спільнота швидко виявила межу цього рішення: щойно в ланцюг обробки додається зовнішній світ — виклик REST API платіжного шлюзу (Stripe, Adyen), відправлення електронного листа або запис у стороннє сховище без підтримки Kafka-транзакцій, — магія KIP-98 вимикається.

## 2018–2020-ті: Сучасні стандарти та семантика Effectively-Once

Сучасний етап розвитку розподілених систем остаточно закріпив термін **Effectively-Once Processing** (обробка з ефектом однократної дії). Інженери визнали, що фізично доставка залишається *at-least-once*, але комбінація детермінованих ключів ідемпотентності, транзакційного збереження намірів та протоколів зовнішньої дедуплікації забезпечує бізнес-результат, невідрізненний від однократного виконання.

Ключовими віхами сучасної епохи стали:
* **Стандартизація заголовка `Idempotency-Key` в IETF**: протокол, популяризований платіжною системою Stripe у 2015–2017 роках, ліг в основу проєкту чернетки стандарту IETF (*The Idempotency-Key HTTP Header Field*), що уніфікував передачу 128-бітних токенів дедуплікації між мікросервісами.
* **Хмарні інструменти дедуплікації**: поява FIFO-черг у Amazon SQS з автоматичним 5-хвилинним вікном дедуплікації (`MessageDeduplicationId`) та бібліотек на зразок AWS Lambda Powertools Idempotency.
* **Рушії тривких процесів (Durable Execution Engines)**: платформи Temporal, Cadence та AWS Step Functions перенесли ідемпотентність на рівень оркестрації розподілених саг, де кожен крок робочого процесу детерміновано фіксує свій результат у незмінній історії виконання (Event History).

Сьогодні проєктування ідемпотентного споживача розглядається не як окрема утилітарна функція, а як системна архітектурна дисципліна, що поєднує управління вікнами дедуплікації, ізоляцію побічних ефектів та захист від аварійних циклів перезапуску.
