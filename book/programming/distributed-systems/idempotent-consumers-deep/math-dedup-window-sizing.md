# 🧮 Розрахунок вікна дедуплікації та ймовірності витоку дублікатів

Цей математичний апарат установлює суворі кількісні межі для проєктування вікна дедуплікації: як обчислити мінімальну безпечну тривалість зберігання ключів, який обсяг пам'яті знадобиться для фільтрації мільярдів повідомлень і яка ймовірність пропуску дубліката при використанні ймовірнісних структур даних.

## 1. Розрахунок мінімального безпечного вікна дедуплікації

Вікно дедуплікації `T_w` (від англійського *window time*) — це часовий інтервал, протягом якого споживач гарантовано зберігає ідентифікатори або контрольні точки оброблених повідомлень.

Щоб дублікат, породжений мережевим збоєм, перезапуском воркера або переграванням черги, не був хибно розпізнаний як нове повідомлення, тривалість `T_w` повинна перекривати максимальний сумарний лаг транспортної системи:

```
T_w = T_retention + T_lag_max + T_recovery + Δ_skew
```

Де:
* `T_retention` — гарантований час утримання повідомлень у топіку або черзі брокера (наприклад, 7 діб у Kafka за замовчуванням).
* `T_lag_max` — максимальний допустимий час відставання споживача (Consumer Lag) під час пікового навантаження до спрацювання аварійного сповіщення.
* `T_recovery` — максимальний час відновлення інфраструктури споживача після повної аварії кластера (включно з розгортанням з резервної копії).
* `Δ_skew` — максимальна розбіжність системних годинників між різними серверами кластера (Clock Skew).

### Приклад інженерного розрахунку:
Нехай сервіс обробки платежів працює з чергою Kafka:
* `T_retention = 7 діб = 604 800 с`
* `T_lag_max = 24 години = 86 400 с`
* `T_recovery = 12 годин = 43 200 с`
* `Δ_skew = 60 с`

Обчислимо необхідну тривалість вікна:

```
T_w = 604 800 + 86 400 + 43 200 + 60
    = 734 460 с                          [сума всіх затримок]
    ≈ 8.5 діб                            [переведення в доби: 734460 / 86400]
```

Отже, мінімальне безпечне вікно дедуплікації для такої системи становить не менше 9 діб. Будь-яке скорочення цього терміну (наприклад, до 24 годин) створює прямий ризик пропуску дублікатів при планових роботах або відновленні після збоїв.

## 2. Обсяг сховища для точного обліку ключів

При точній дедуплікації через реляційну базу даних (inbox-таблиця) кількість активних ключів `N` у вікні прямо пропорційна вхідній швидкості потоку `R` (повідомлень на секунду) та тривалості вікна `T_w`:

```
N = R · T_w
```

Загальний обсяг дискового простору `V_total` (у байтах), необхідний для збереження таблиці дедуплікації та її індексів, обчислюється як:

```
V_total = N · (S_key + S_metadata + S_btree_overhead)
```

Де:
* `S_key` — розмір ідентифікатора повідомлення (16 байтів для бінарного UUID або 36 байтів для рядкового представлення).
* `S_metadata` — розмір службових полів рядка (мітка часу 8 байтів, статус 2 байти, посилання на зовнішній ефект 16 байтів, заголовок рядка PostgreSQL 24 байти).
* `S_btree_overhead` — накладні витрати на індексацію B-Tree (орієнтовно 32–48 байтів на один індексний запис).

### Числовий розрахунок для високонавантаженої системи:
Нехай потік складає `R = 5 000` повідомлень/секунду, а вікно зберігання становить `T_w = 9 діб = 777 600 с`:

```
N = 5 000 · 777 600
  = 3 888 000 000 ключів                 [добуток швидкості й тривалості]
```

При середньому розмірі одного індексованого рядка в PostgreSQL `S_row ≈ 120 байтів`:

```
V_total = 3 888 000 000 · 120
        = 466 560 000 000 байтів         [множення кількості ключів на розмір рядка]
        ≈ 466.56 ГБ                      [переведення в гігабайти]
```

Збереження 466 ГБ тільки для ключів дедуплікації створює колосальне навантаження на підсистему вводу-виводу (IOPS) та кеш сторінок бази даних (`shared_buffers`). Це математично обґрунтовує необхідність застосування дворівневої фільтрації: швидкий in-memory фільтр Блума на першому етапі та звернення до бази даних лише за потреби.

## 3. Генераційний фільтр Блума (Sliding Bloom Filter)

Для зменшення навантаження на базу даних використовують генераційні фільтри Блума, розділені на `G` поколінь (підфільтрів), де кожне покоління покриває часовий проміжок `τ = T_w / (G - 1)`.

При переході часу найстаріше покоління фільтра очищується, а нове створюється для запису поточних подій. Загальна пам'ять генераційного фільтра масштабується як `M_gen = (G / (G - 1)) · M_bloom`. Для `G = 3` надлишковість по пам'яті становить 50%, а для `G = 5` — лише 25%.

Нехай розмір фільтра в бітах дорівнює `m`, кількість збережених елементів `n`, а кількість хеш-функцій `k`.

Ймовірність хибнопозитивного спрацьовування (False Positive Rate, `P_FP`) для одного фільтра Блума описується формулою:

```
P_FP ≈ (1 - e^(-k · n / m))^k
```

Оптимальна кількість хеш-функцій `k`, яка мінімізує `P_FP` для заданого відношення `m / n`, дорівнює:

```
k = (m / n) · ln(2)
```

Підставивши оптимальне значення `k` у формулу ймовірності, отримуємо залежність необхідної кількості бітів на один ключ `b = m / n` від бажаної ймовірності хибної тривоги `P_FP`:

```
b = - ln(P_FP) / (ln(2))²
  ≈ - 1.44269 · log2(P_FP)
```

### Покроковий розрахунок пам'яті для генераційного фільтра:
Поставимо інженерну вимогу: хибнопозитивна ймовірність фільтра Блума не повинна перевищувати `P_FP = 0.001` (0.1%, тобто лише 1 з 1000 нових повідомлень дасть хибне спрацювання і вимагатиме додаткової перевірки в базі даних).

Кількість бітів на один ключ:

```
b = - 1.44269 · log2(0.001)
  = - 1.44269 · (-9.96578)               [log2(0.001) ≈ -9.96578]
  = 14.377                               [множення коефіцієнтів]
  ≈ 14.4 біта на ключ                    [округлення вгору]
```

Оптимальна кількість хеш-функцій:

```
k = 14.4 · ln(2)
  = 14.4 · 0.69315                       [ln(2) ≈ 0.69315]
  = 9.981                                [множення]
  ≈ 10 хеш-функцій                       [округлення до найближчого цілого]
```

Для активного вікна з `N = 100 000 000` повідомлень (100 млн ключів) сумарний розмір пам'яті в RAM становитиме:

```
M_bloom = 100 000 000 · 14.4 бітів
        = 1 440 000 000 бітів            [множення кількості ключів на біти]
        = 180 000 000 байтів             [ділення на 8 бітів у байті]
        ≈ 180 МБ                         [переведення в мегабайти]
```

З урахуванням генераційної надлишковості для `G = 4` поколінь сумарна пам'ять складе `180 · (4 / 3) = 240 МБ`. Генераційний фільтр об'ємом усього 240 МБ оперативної пам'яті відсікає 99.9% повторних звернень до бази даних, знижуючи кількість дискових операцій у тисячу разів.

## 4. Ймовірність колізій хешів за парадоксом днів народження

При формуванні детермінованих ключів ідемпотентності критично важливо правильно обрати розрядність хеш-функції. За парадоксом днів народження ймовірність колізії `P_coll` для `N` згенерованих ключів у просторі розміром `S = 2^B` бітів оцінюється за формулою:

```
P_coll ≈ 1 - e^(- N² / (2 · S))
       ≈ N² / (2 · 2^B)                  [при N² ≪ 2^B]
```

### Порівняння 64-бітних та 128-бітних хешів:
Розглянемо річний потік з `N = 10^9` повідомлень (1 мільярд подій):

1. Для 64-бітного простору (`B = 64`, `S = 2^64 ≈ 1.844 · 10^19`):
```
P_coll ≈ (10^9)² / (2 · 1.844 · 10^19)
       = 10^18 / (3.688 · 10^19)         [піднесення до квадрата і множення]
       ≈ 0.0271                          [ділення]
       ≈ 2.71%                           [колізія стається з імовірністю майже 3%]
```
Імовірність колізії 2.7% є неприпустимою для фінансових та облікових систем, оскільки 27 мільйонів транзакцій отримають чужий ключ дедуплікації.

2. Для 128-бітного простору (`B = 128`, `S = 2^128 ≈ 3.402 · 10^38`):
```
P_coll ≈ (10^9)² / (2 · 3.402 · 10^38)
       = 10^18 / (6.804 · 10^38)         [піднесення до квадрата і знаменник]
       ≈ 1.47 · 10^(-21)                 [ділення]
```
Ймовірність колізії `1.47 · 10^(-21)` менша за ймовірність апаратного збою процесора від космічних променів, що робить 128-бітні та 256-бітні хеші (SHA-256) абсолютно безпечними для глобальної ідентифікації.

## 5. Модель ймовірності витоку пізніх дублікатів

Якщо повідомлення приходить із затримкою `t > T_w`, воно виходить за межі активного вікна дедуплікації. У реальних мережах інтервали між первинною відправкою та пізнім переграванням повідомлення (наприклад, ручний replay з DLQ) добре описуються важкохвостим розподілом Парето з функцією розподілу:

```
F(t) = 1 - (t_min / t)^α    [для t ≥ t_min]
```

Де `α > 0` — показник форми розподілу (для розподілених черг зазвичай `1.2 ≤ α ≤ 1.8`), а `t_min` — мінімальний мережевий таймаут.

Ймовірність того, що випадковий дублікат з'явиться після закінчення вікна дедуплікації `T_w` (ймовірність витоку `P_leak`), дорівнює:

```
P_leak = P(t > T_w)
       = (t_min / T_w)^α                 [підстановка вікна у хвіст розподілу Парето]
```

### Порівняння розмірів вікон та ризику подвійної обробки:
Приймемо `t_min = 10 с` та показник форми `α = 1.5`:

1. При вузькому вікні `T_w = 1 година = 3 600 с`:
```
P_leak = (10 / 3 600)^1.5
       = (0.002778)^1.5                  [обчислення відношення 10/3600]
       = 0.000146                        [піднесення до степеня 1.5]
       ≈ 0.015%                          [150 витоків на 1 млн дублікатів]
```

2. При розширеному вікні `T_w = 7 діб = 604 800 с`:
```
P_leak = (10 / 604 800)^1.5
       = (0.0000165)^1.5                 [обчислення відношення 10/604800]
       = 0.000000067                     [піднесення до степеня 1.5]
       ≈ 0.0000067%                      [менше 1 витоку на 15 млн дублікатів]
```

Збільшення вікна зберігання з 1 години до 7 діб зменшує ймовірність прориву дубліката у понад 2100 разів, що математично доводить критичну важливість узгодження вікна споживача з часом утримання брокера.
