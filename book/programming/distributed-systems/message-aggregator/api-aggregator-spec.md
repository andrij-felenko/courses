# 📋 Специфікація метаданих, конфігурації та сховища агрегатора повідомлень

Ця специфікація встановлює нормативні вимоги до інтерфейсів, транспортних конвертів, форматів серіалізації, конфігураційних моделей та абстракцій збереження стану для розподілених систем агрегації та ресеквенсингу повідомлень. Стандарт призначений для інженерів розподілених платформ, розробників високонавантажених брокерів та інтеграційних шин підприємств.

Специфікація стандартизує взаємодію між джерелами подій (розділювачами, паралельними воркерами, шлюзами API), станційними посередниками-агрегаторами та кінцевими споживачами складених результатів.

## 1. Транспортні заголовки (Metadata Header Contract)

Кожне атомарне повідомлення, що надходить до агрегатора або ресеквенсера через ненадійну мережу, повинно супроводжуватися стандартизованим набором метаданих у транспортних заголовках протоколу (HTTP/2 Headers, AMQP BasicProperties, Kafka Record Headers або gRPC Metadata).

| Заголовок / Поле | Тип | Обов'язковість | Опис та семантичні інваріанти |
| :--- | :--- | :--- | :--- |
| `x-correlation-id` | `String (UUID / ASCII)` | **Обов'язкове** | Унікальний ідентифікатор сесії або бізнес-транзакції. Усі повідомлення одного складеного пакета мають однакове значення. |
| `x-sequence-number` | `uint64` | **Обов'язкове** | Монотонний 1-індексований порядковий номер елемента в межах поточної кореляційної групи (`1, 2, ..., N`). |
| `x-sequence-size` | `uint64` | Опційне | Загальна кількість елементів `N` у групі. Якщо значення `<= 0` або відсутнє, розмір вважається заздалегідь невідомим (потоковий режим). |
| `x-is-last-element` | `bool` | Опційне | Прапорець термінального елемента (`true` для останнього повідомлення, `false` для інших). Необхідний при невідомому `x-sequence-size`. |
| `x-aggregation-timeout-ms` | `uint32` | Опційне | Динамічний ліміт очікування для конкретного кошика в мілісекундах. Перевизначає системне налаштування за замовчуванням. |
| `x-message-timestamp` | `int64 (Unix Epoch ms)` | **Обов'язкове** | Часова мітка відправки повідомлення на джерелі (подієвий час, *Event Time*). |
| `x-aggregate-version` | `uint32` | Опційне | Числовий лічильник оптимістичного блокування для контролю паралельних змін стану кошика. |
| `traceparent` | `String (W3C Trace)` | Опційне | Наскрізний ідентифікатор розподіленого трасування стандарту W3C Trace Context (`version-trace_id-parent_id-flags`). |

### Інваріанти транспортних заголовків:

1. **Унікальність кореляції та послідовності:** Пара значень `(x-correlation-id, x-sequence-number)` є глобально унікальною в межах життєвого циклу розподіленої системи. Будь-яке повторне надходження повідомлення з тією ж парою вважається дублікатом транспортного рівня і не повинно викликати повторну обробку чи модифікацію бізнес-стану кошика.
2. **Монотонність нумерації:** Значення `x-sequence-number` повинно починатися з одиниці (`1`) для першого елемента і суворо зростати з кроком `+1` для кожного наступного елемента. Використання довільних або розріджених індексів заборонено, якщо система працює в режимі строгого ресеквенсингу.
3. **Узгодженість прапорця завершення:** Якщо заголовок `x-sequence-size` встановлено у значення `N > 0`, повідомлення з номером `x-sequence-number = N` повинно містити заголовок `x-is-last-element: true`. Для всіх повідомлень із номерами від `1` до `N - 1` значення `x-is-last-element` повинно бути суворо `false`.
4. **Успадкування розподіленого контексту трасування:** Агрегатор зобов'язаний зберігати вихідний ідентифікатор трасування `trace_id` із заголовка `traceparent`, створюючи новий батьківський спан (*Span*) для зведеного вихідного повідомлення з фіксацією посилань на всі проміжні спани оброблених елементів.

## 2. Схеми повідомлень: Protocol Buffers v3

Для високонавантажених бінарних каналів зв'язку та gRPC-сервісів взаємодія з агрегатором стандартизується схемою Protocol Buffers v3.

```protobuf
syntax = "proto3";

package eip.aggregator.v1;

import "google/protobuf/timestamp.proto";
import "google/protobuf/any.proto";

// Атомарне вхідне повідомлення, що підлягає агрегації або ресеквенсингу
message InboundMessage {
  string message_id = 1;
  string correlation_id = 2;
  uint64 sequence_number = 3;
  uint64 sequence_size = 4;
  bool is_last_element = 5;
  google.protobuf.Timestamp timestamp = 6;
  string traceparent = 7;
  uint32 aggregate_version = 8;
  
  // Корисне бізнес-навантаження
  string payload_type = 9;
  bytes payload = 10;
}

// Статус завершення агрегаційного кошика
enum CompletionReason {
  COMPLETION_REASON_UNSPECIFIED = 0;
  COMPLETION_REASON_FULL_SIZE_REACHED = 1;
  COMPLETION_REASON_FIN_MARKER_RECEIVED = 2;
  COMPLETION_REASON_INACTIVITY_TIMEOUT = 3;
  COMPLETION_REASON_HARD_DEADLINE_EXPIRED = 4;
  COMPLETION_REASON_BUFFER_CAPACITY_OVERFLOW = 5;
  COMPLETION_REASON_PREDICATE_SATISFIED = 6;
}

// Вихідне складене повідомлення після агрегації
message CompositeMessage {
  string composite_id = 1;
  string correlation_id = 2;
  CompletionReason completion_reason = 3;
  bool is_partial = 4;
  
  uint64 expected_items_count = 5;
  uint64 received_items_count = 6;
  repeated uint64 missing_sequence_numbers = 7;
  
  google.protobuf.Timestamp aggregation_started_at = 8;
  google.protobuf.Timestamp aggregation_completed_at = 9;
  
  // Впорядкований масив агрегованих елементів
  repeated InboundMessage items = 10;
}
```

### Семантика полів Protocol Buffers:

* `InboundMessage.message_id`: Унікальний ідентифікатор фізичного пакета в черзі (наприклад, `UUIDv4`), що використовується для дедуплікації на рівні брокера повідомлень.
* `InboundMessage.payload_type`: MIME-тип або FQCN (Fully Qualified Class Name) серіалізованого об'єкта, що міститься в полі `payload` (наприклад, `application/json` або `orders.v1.ItemDTO`).
* `CompositeMessage.missing_sequence_numbers`: Масив порядкових номерів, які не надійшли до моменту закриття кошика за тайм-аутом. Дозволяє споживачам часткового пакета точно знати, які підсистеми не надіслали відповідь.
* `CompositeMessage.is_partial`: Булевий прапорець, що сигналізує про деградацію або аварійний випуск пакета через неповний збір елементів.

## 3. Схема конфігурації стратегії завершення (JSON Schema)

Поведінка агрегаційного рушія налаштовується декларативно за допомогою стандартизованої конфігураційної схеми JSON Schema Draft 2020-12.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "AggregatorCompletionStrategyConfig",
  "type": "object",
  "required": ["strategy_type", "timeout_policy"],
  "properties": {
    "strategy_type": {
      "type": "string",
      "enum": ["SIZE_BASED", "PREDICATE_BASED", "TIMEOUT_ONLY", "HYBRID"]
    },
    "max_batch_size": {
      "type": "integer",
      "minimum": 1,
      "description": "Максимальна місткість буфера до примусового скидання"
    },
    "timeout_policy": {
      "type": "object",
      "required": ["hard_deadline_ms", "inactivity_timeout_ms", "on_timeout_action"],
      "properties": {
        "hard_deadline_ms": {
          "type": "integer",
          "minimum": 10,
          "description": "Абсолютний ліміт існування кошика від моменту першого повідомлення"
        },
        "inactivity_timeout_ms": {
          "type": "integer",
          "minimum": 10,
          "description": "Ліміт очікування наступного повідомлення у кошик"
        },
        "on_timeout_action": {
          "type": "string",
          "enum": ["EMIT_PARTIAL", "ROUTE_TO_DLQ", "DISCARD", "TRIGGER_COMPENSATION"]
        }
      }
    },
    "tombstone_ttl_sec": {
      "type": "integer",
      "minimum": 1,
      "default": 3600,
      "description": "Час життя запису про закритий кошик для відсікання запізнілих повідомлень"
    }
  }
}
```

### Правила валідації конфігурації:

1. **Взаємозв'язок тайм-аутів:** Значення `inactivity_timeout_ms` не повинно перевищувати значення `hard_deadline_ms`. У разі виявлення конфігурації, де `inactivity_timeout_ms > hard_deadline_ms`, система ініціалізації агрегатора зобов'язана згенерувати фатальну помилку конфігурації та зупинити запуск сервісу.
2. **Обмеження розміру буфера:** Параметр `max_batch_size` є запобіжником проти атак типу «відмова в обслуговуванні» (DoS) та аномальних пакетів. Якщо потік повідомлень перевищує `max_batch_size` без сигналу завершення, агрегатор негайно примусово закриває поточний батч, формує складене повідомлення з причиною `COMPLETION_REASON_BUFFER_CAPACITY_OVERFLOW` і починає накопичення наступного блоку.
3. **Політика надгробків:** Параметр `tombstone_ttl_sec` повинен бути встановлений щонайменше у 3–5 разів більше за максимальний розрахунковий SLA повторної доставки повідомлень брокером, щоб гарантувати надійне відсікання запізнілих дублікатів.

## 4. Контракт інтерфейсу сховища стану (State Store SPI)

Для забезпечення незалежності агрегаційного рушія від конкретної технології зберігання (in-memory пам'ять, RocksDB на локальному NVMe або розподілений Redis/PostgreSQL) взаємодія зі станом здійснюється через строгий абстрактний інтерфейс сховища стану.

```
+-----------------------------------------------------------------------------------+
|                            AggregationStateStore                                  |
+-----------------------------------------------------------------------------------+
| + PutMessage(corr_id, msg) -> PutResult (ADDED | DUPLICATE | TOMBSTONE_REJECTED)    |
| + GetBucket(corr_id) -> AggregationBucket                                         |
| + MarkCompleted(corr_id, reason) -> bool                                          |
| + RecordTombstone(corr_id, ttl_seconds) -> void                                   |
| + SweepExpiredBuckets(now_ts) -> List[TimedOutBucket]                             |
| + SweepExpiredTombstones(now_ts) -> uint64                                        |
+-----------------------------------------------------------------------------------+
```

### Семантичні вимоги до методів сховища:

* **`PutMessage` (Атомарне додавання елемента):**
  Метод зобов'язаний виконуватися атомарно в межах одного `correlation_id`. Якщо для зазначеного ідентифікатора вже існує активний запис надгробка, метод негайно повертає результат `TOMBSTONE_REJECTED` без зміни стану. Якщо кошик існує і вже містить елемент із таким самим `sequence_number`, метод повертає статус `DUPLICATE`. В іншому разі елемент додається до кошика, оновлюється часова мітка `last_activity` і повертається статус `ADDED`.

* **`GetBucket` (Читання стану кошика):**
  Повертає повний знімок накопичених елементів, бітову маску отриманих послідовностей, загальну кількість очікуваних елементів та системні часові мітки створення й останньої активності.

* **`MarkCompleted` (Фіксація успішного завершення):**
  Атомарно переводить стан кошика в `COMPLETED`, вилучає накопичений масив елементів із пам'яті для передачі вихідному конвеєру та ініціює запис надгробка.

* **`RecordTombstone` (Створення надгробка):**
  Зберігає ключ `correlation_id` у таблиці закритих сесій із встановленим часом життя `TTL`. У розподілених сховищах (наприклад, Redis) цей метод реалізується через команду `SET key EX ttl`.

* **`SweepExpiredBuckets` (Сканування прострочених сесій):**
  Виконує пошук усіх кошиків, де `now_ts - last_activity >= inactivity_timeout_ms` або `now_ts - created_at >= hard_deadline_ms`. Усі знайдені кошики вилучаються зі сховища й повертаються агрегатору для виконання аварійної емісії.

## 5. Протокольне відображення та мережеві контракти (Wire Protocol Mappings)

Для забезпечення безшовної інтеграції в гетерогенних корпоративних середовищах заголовки агрегатора транслюються у специфічні протокольні структури:

1. **HTTP/2 та gRPC:**
   Заголовки передаються у нижньому регістрі (`x-correlation-id`, `x-sequence-number`, `x-is-last-element`). Бінарні корисні навантаження передаються у форматі `application/grpc+proto` або `application/json`.
2. **Apache Kafka:**
   Службові метадані кодуються в `RecordHeaders` як масиви байтів у форматі UTF-8 або Big-Endian цілих чисел. Ключ запису Kafka обов'язково встановлюється рівним значенню `Correlation ID`, що забезпечує автоматичне детерміноване партиціонування брокером за формулою `murmur2(key) % partition_count`.
3. **AMQP 0-9-1 (RabbitMQ):**
   Заголовок `correlation_id` мапиться на стандартне поле структури `BasicProperties.correlation_id`. Додаткові поля (`sequence_number`, `sequence_size`, `is_last`) записуються у користувацьку таблицю заголовків `BasicProperties.headers` (таблиця типу `amqp_table_t`).

## 6. Класифікація помилок та статусних кодів

| Код помилки | Символічний ідентифікатор | Рівень критичності | Дія підсистеми |
| :--- | :--- | :--- | :--- |
| `1001` | `ERR_DUPLICATE_SEQUENCE` | Попередження | Повідомлення відкидається як ідемпотентний дублікат; стан кошика не змінюється. |
| `1002` | `ERR_LATE_ARRIVAL_TOMBSTONE` | Попередження | Повідомлення надійшло після закриття кошика; спрямовується до `late_events_dlq`. |
| `1003` | `ERR_AGGREGATION_TIMEOUT` | Помилка | Кошик не зібрав повний набір за відведений час; виконання дії згідно з `on_timeout_action`. |
| `1004` | `ERR_BUFFER_OVERFLOW` | Критична помилка | Перевищено максимальний ліміт місткості елементів; примусова емісія для захисту від OOM. |
| `1005` | `ERR_SEQUENCE_GAP_ABORT` | Помилка | У режимі строгого ресеквенсингу тайм-аут очікування прогалини сплив; аварійна зупинка потоку або скидання пропуску. |
| `1006` | `ERR_CORRELATION_CORRUPTED` | Фатальна помилка | Відсутній обов'язковий заголовок `x-correlation-id` або пошкоджена схема payload; ізоляція в DLQ. |

Кожна виявлена помилка повинна супроводжуватися структурованим записом у системний журнал та інкрементом відповідного лічильника метрик моніторингу (Prometheus / OpenTelemetry).
