# 📋 Контракт інтерфейсу, протокольні заголовки та телеметрія скидання навантаження

Надійне скидання навантаження неможливе без узгодженого двостороннього протокольного контракту між клієнтом і сервером. Якщо сервер відхиляє запит без точного зазначення причини або без вказівки інтервалу відновлення, клієнтські бібліотеки сприймають відмову як мережевий збій і починають агресивний шторм повторів. Ця довідкова вставка містить повну специфікацію статус-кодів HTTP та gRPC, стандартних заголовків прокидання дедлайнів, схем машиночитаних повідомлень про помилки за стандартом RFC 7807, конфігурації проксі Envoy та метрик моніторингу OpenTelemetry і Prometheus.

## 1. Специфікація протоколу HTTP/1.1 та HTTP/2

У протоколі HTTP для скидання навантаження використовуються стандартизовані статус-коди, заголовки метаданих та машиночитані тіла відповідей:

### Статус-коди відповіді HTTP

| Код HTTP | Назва стандарту | Контекст застосування під час скидання навантаження |
| :--- | :--- | :--- |
| **`503 Service Unavailable`** | Сервіс тимчасово недоступний | **Основний код для Load Shedding.** Вказує, що сервер справний, але тимчасово перевантажений і скидає глобальний надлишок трафіку для захисту свого здоров'я. Обов'язково супроводжується заголовком `Retry-After`. |
| **`429 Too Many Requests`** | Забагато запитів (RFC 6585) | Застосовується, якщо запит відхилено через перевищення індивідуальної квоти клієнта (Rate Limiting або персональний Tenant Throttling). |
| **`504 Gateway Timeout`** | Вичерпано таймаут шлюзу | Повертається зворотним проксі (Envoy / NGINX), якщо черга бекенда не відповіла за відведений час очікування. |

### Заголовки запиту (Client Request Headers)

Клієнтські застосунки зобов'язані передавати метадані дедлайну та очікуваного бюджету часу:

| Заголовок | Тип даних | Опис та приклад |
| :--- | :--- | :--- |
| `X-Request-Deadline` | `Integer (Unix Epoch ms)` | Абсолютна мітка часу, після якої клієнт гарантовано розірве з'єднання. Приклад: `1700000015500`. |
| `Request-Timeout` | `Float (секунди)` | Відносний бюджет часу на виконання операції. Приклад: `2.5` (2500 мс). |
| `X-Request-Priority` | `String (Enum)` | Декларативний рівень важливості клієнтського виклику: `tier0-system`, `tier1-critical`, `tier2-interactive`, `tier3-background`. |

Використання відносного заголовка `Request-Timeout` є значно надійнішим за абсолютний `X-Request-Deadline`, оскільки воно повністю усуває проблеми розбіжності системних годинників (Clock Skew) між розподіленими вузлами. Проміжні проксі-сервери (Envoy / API Gateway) зменшують значення `Request-Timeout` на величину вже витраченого часу перед передачею запиту наступному мікросервісу в ланцюжку.

### Заголовки відповіді сервера (Server Response Headers)

Під час ухвалення рішення про скидання виклику сервер повертає структурований набір діагностичних заголовків:

| Заголовок | Тип даних | Опис та семантика |
| :--- | :--- | :--- |
| `Retry-After` | `Integer (сек)` або `HTTP-Date` | **Критично обов'язковий заголовок.** Вказує мінімальний час, протягом якого клієнт зобов'язаний утриматися від повторних викликів. Приклад: `Retry-After: 4`. |
| `X-Shed-Reason` | `String (Enum)` | Машиночитана причина відхилення: `sojourn-time-exceeded`, `deadline-expired`, `capacity-exhausted`, `priority-tier-shed`. |
| `X-Shed-Sojourn-Ms` | `Float (мс)` | Фактичний час, який запит провів у черзі до моменту ухвалення рішення про скидання. Приклад: `38.4`. |
| `X-Do-Not-Retry` | `Boolean` | Вказівка клієнтському SDK не робити повторних спроб (наприклад, для фонових аналітичних операцій). Приклад: `true`. |

### Машиночитане тіло помилки за стандартом RFC 7807 (Problem Details)

Під час скидання навантаження сервер повертає структуру `application/problem+json`:

```json
{
  "type": "https://api.example.com/errors/load-shedding",
  "title": "Service Temporarily Overloaded",
  "status": 503,
  "detail": "Request was shedded because queue wait time (38.4ms) exceeded target SLA (20.0ms).",
  "instance": "/orders/checkout/req_98a7fbc31",
  "shed_reason": "sojourn-time-exceeded",
  "request_tier": "tier2-interactive",
  "sojourn_time_ms": 38.4,
  "retry_after_seconds": 4,
  "server_capacity_utilization": 0.96
}
```

## 2. Специфікація протоколу gRPC

У високопродуктивному бінарному протоколі gRPC скидання навантаження спирається на вбудовані статус-коди та бінарні метадані Google RPC:

### Статус-коди gRPC

| gRPC Status Code | Числовий код | Семантичне значення під час перевантаження |
| :--- | :--- | :--- |
| **`UNAVAILABLE`** | `14` | **Основний код для скидання навантаження.** Сигналізує про тимчасову неспроможність сервера виконати запит. Клієнтський SDK повинен виконати експоненційний відступ з рандомізованим шумом (Jitter). |
| **`RESOURCE_EXHAUSTED`** | `8` | Вказує на вичерпання активної квоти (пам'яті, потоків воркерів або токенів конкурентності). |
| **`DEADLINE_EXCEEDED`** | `4` | Повертається, якщо залишковий дедлайн виклику минув до початку виконання операції або під час перебування в черзі. |

### Метадані та заголовки дедлайнів gRPC

* **`grpc-timeout`:** стандартний заголовок gRPC для передачі бюджету часу. Формат: ціле число та одиниця виміру (`H` — години, `M` — хвилини, `S` — секунди, `m` — мілісекунди, `u` — мікросекунди, `n` — наносекунди). Приклад: `grpc-timeout: 200m` (дедлайн 200 мілісекунд).
* **`grpc-status-details-bin`:** бінарно серіалізоване повідомлення Protobuf `google.rpc.Status`, що містить структури `google.rpc.RetryInfo` та `google.rpc.ErrorInfo`. Передається в HTTP/2-трейлерах (Trailers-Only) без витрат на передачу тіла повідомлення.

### Схема повідомлення деталей помилки (Protobuf IDL)

```protobuf
syntax = "proto3";

package google.rpc;

import "google/protobuf/duration.proto";

// Стандартний опис затримки перед повтором
message RetryInfo {
    google.protobuf.Duration retry_delay = 1; // Рекомендована пауза (наприклад, 3.5s)
}

// Деталізований опис причини скидання навантаження
message LoadSheddingDetails {
    enum Reason {
        REASON_UNSPECIFIED = 0;
        SOJOURN_TIME_EXCEEDED = 1;
        DEADLINE_EXPIRED = 2;
        CAPACITY_EXHAUSTED = 3;
        PRIORITY_TIER_SHED = 4;
    }

    Reason reason = 1;
    string tier = 2;
    float sojourn_time_ms = 3;
    float current_concurrency_limit = 4;
    bool is_retryable = 5;
}
```

## 3. Скидання навантаження для потокових RPC (Streaming RPCs)

Для довгоживучих потокових з'єднань gRPC (Server-Streaming, Client-Streaming та Bi-Directional Streaming) застосовується спеціалізована логіка управління ресурсами:

1. **Етап ініціалізації потоку:** перед відкриттям потоку шеддер оцінює поточну кількість активних стрімів і затримку черги. Якщо ліміт вичерпано, запит на створення потоку негайно відхиляється статусом `UNAVAILABLE` ще до виділення буферів пам'яті.
2. **Плавне завершення активних потоків (Graceful Stream Draining):** якщо перевантаження виникає під час активної передачі даних, сервер не розриває TCP-з'єднання грубо. Замість цього сервер надсилає фінальне повідомлення з метаданими останнього успішно обробленого зміщення (Offset / Sequence ID) та завершує потік HTTP/2-трейлерами з кодом `UNAVAILABLE` та структурою `RetryInfo`. Клієнтський SDK відновлює читання з наступного зміщення після завершення інтервалу відступу.

## 4. Конфігурація фільтрів перевантаження в Envoy Proxy

У сучасних хмарних інфраструктурах перший ешелон скидання навантаження реалізується на рівні сервісної сітки або вхідного проксі за допомогою модуля **Envoy Overload Manager**:

```yaml
overload_manager:
  refresh_interval: 0.25s
  resource_monitors:
    - name: "envoy.resource_monitors.fixed_heap"
      typed_config:
        "@type": type.googleapis.com/envoy.extensions.resource_monitors.fixed_heap.v3.FixedHeapConfig
        max_heap_size_bytes: 2147483648 # 2 GiB
  actions:
    - name: "envoy.overload_actions.disable_keepalive"
      triggers:
        - name: "envoy.resource_monitors.fixed_heap"
          threshold:
            value: 0.80 # При 80% пам'яті вимикаємо keep-alive
    - name: "envoy.overload_actions.stop_accepting_requests"
      triggers:
        - name: "envoy.resource_monitors.fixed_heap"
          threshold:
            value: 0.90 # При 90% пам'яті відхиляємо нові запити з кодом 503
```

Цей конфігураційний блок забезпечує дворівневий захист: спочатку проксі припиняє повторне використання з'єднань, стимулюючи клієнтів зменшити навантаження, а при подальшому зростанні пам'яті повністю відсікає нові запити, запобігаючи аварійному перезапуску контейнера через вичерпання лімітів пам'яті Kubernetes.

## 5. Захист системних проб Kubernetes (Health Probes Isolation)

Головною небезпекою під час скидання навантаження в середовищі Kubernetes є випадкове потрапляння перевірок працездатності (Liveness та Readiness Probes) під загальні фільтри відсікання.

Якщо ендпоінт `/readyz` або `/healthz` обслуговується загальним пулом воркерів вебсервера:
* Під час перевантаження системна проба стає в загальну переповнену чергу завдань.
* Не отримавши відповіді за відведений ліміт таймауту (наприклад, 2 секунди), оркестратор Kubernetes вирішує, що контейнер завис, і надсилає йому сигнал примусового перезапуску `SIGKILL`.
* Масовий перезапуск здорових контейнерів під навантаженням викликає повний блекаут кластера (Cascading Pod Death Spiral).

Щоб унеможливити цю катастрофу, контракт розгортання вимагає:
1. **Виділений порт управління (Dedicated Management Port):** системні проби `/healthz` та метрики Prometheus обслуговуються на окремому TCP-порті (наприклад, `:9090`) через незалежний легковажний HTTP-сервер, що не має спільних черг із бізнес-трафіком.
2. **Безумовний Tier 0 Bypass:** якщо проби надходять на основний порт, шеддер ідентифікує шлях `/healthz` на етапі парсингу URI і пропускає запит в обхід черги CoDel та лімітів активної конкурентності.

## 6. Специфікація метрик OpenTelemetry та Prometheus

Для наскрізного спостереження (Observability) за поведінкою шеддера в промисловому кластері експортуються такі стандартизовані метрики:

### Лічильники (Counters)

| Ім'я метрики Prometheus | Тип | Лейбли (Dimensions) | Опис |
| :--- | :--- | :--- | :--- |
| `http_requests_shed_total` | Counter | `tier`, `reason`, `handler`, `method` | Загальна кількість HTTP-запитів, скинутих шеддером без обробки. |
| `grpc_server_handled_shed_total` | Counter | `grpc_service`, `grpc_method`, `tier`, `reason` | Кількість RPC-викликів, відхилених на вході в сервіс. |
| `load_shedder_codel_state_changes_total` | Counter | `from_state`, `to_state` | Кількість переходів між нормальним станом та станом скидання (Dropping). |

### Гістограми (Histograms)

| Ім'я метрики Prometheus | Одиниці | Лейбли | Бакети (Le/Buckets) | Опис |
| :--- | :--- | :--- | :--- | :--- |
| `request_sojourn_time_seconds` | Секунди | `tier`, `admitted` | `[0.001, 0.005, 0.010, 0.020, 0.050, 0.100, 0.250, 0.500, 1.0, 2.5]` | **Ключова метрика.** Час перебування запиту в черзі до моменту вибірки воркером. |
| `request_execution_time_seconds` | Секунди | `tier`, `status` | `[0.005, 0.010, 0.025, 0.050, 0.100, 0.250, 0.500, 1.0, 5.0]` | Чистий час виконання бізнес-логіки воркером (без урахування черги). |

### Миттєві показники (Gauges)

| Ім'я метрики Prometheus | Одиниці | Опис |
| :--- | :--- | :--- |
| `load_shedder_active_inflight_requests` | Ціле число | Поточна кількість запитів, що виконуються воркерами в даний момент. |
| `load_shedder_dynamic_capacity_limit` | Ціле число | Поточний адаптивний ліміт активних запитів, розрахований алгоритмом AIMD/Vegas. |
| `load_shedder_min_sojourn_seconds` | Секунди | Мінімальний зафіксований час перебування в черзі за поточну епоху CoDel. |
| `load_shedder_in_dropping_state` | 0 або 1 | Бінарний прапорець: 1 — шеддер перебуває в режимі активного скидання трафіку. |

### Семантичні конвенції трасування OpenTelemetry (Span Attributes)

Під час створення спанів розподіленого трасування (Tracing) шеддер додає такі атрибути до кореневого спану запиту:

* `rpc.load_shedding.admitted`: `true` або `false`.
* `rpc.load_shedding.reason`: рядок причини скидання (`"sojourn_time_exceeded"`).
* `rpc.load_shedding.sojourn_time_ms`: числовий час очікування в черзі.
* `rpc.load_shedding.tier`: категорія важливості (`"tier1_critical"`).
* `rpc.load_shedding.limit`: поточний адаптивний ліміт конкурентності.

## 7. Конфігурація клієнтських повторів та інтеграція із запобіжником

Клієнтські бібліотеки, що взаємодіють із сервісами, які використовують скидання навантаження, повинні конфігуруватися за принципом **Full Jitter Exponential Backoff**:

```
t_sleep = min(backoff_max, backoff_base · 2^attempt)
t_actual_sleep = uniform_random(0, t_sleep)
```

При отриманні скинутого запиту клієнт застосовує такі правила:

1. **Повага до заголовка `Retry-After`:** якщо сервер повернув заголовок `Retry-After: N`, клієнт ігнорує розрахунковий експоненційний відступ і засинає на час `N + uniform_random(0, 0.5 · N)` секунд.
2. **Максимальний ліміт спроб (Retry Budget):** клієнт обмежує кількість повторів максимум двома спробами. Якщо частка повторних запитів перевищує 10% від загального трафіку клієнта, SDK примусово блокує нові повтори для запобігання шторму.
3. **Неповторюваність неідемпотентних викликів:** повторні виклики дозволені виключно для безпечних ідемпотентних методів (`GET`, `PUT`, `DELETE` з унікальним `Idempotency-Key`).
4. **Розділення метрик запобіжника (Circuit Breaker Isolation):** клієнтський запобіжник не повинен розмикати ланцюг за наявності поодиноких відповідей `503 Service Unavailable` з коректним `Retry-After`, якщо ці відповіді є результатом штатного згладжування сплесків. Запобіжник реагує лише на неконтрольоване зростання фатальних помилок 5xx та жорстких мережевих розривів.

## 8. Правила сповіщень Prometheus (PromQL Alerting Rules)

Для чергової інженерної зміни SRE налаштовуються два ключові правила моніторингу:

```yaml
groups:
  - name: load_shedding_alerts
    rules:
      - alert: CriticalLoadSheddingActive
        expr: sum(rate(http_requests_shed_total{tier="tier1-critical"}[2m])) > 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Сервер скидає критичні транзакції Tier 1"
          description: "Частка скидання Tier 1 становить {{ $value }} req/s. Потрібне негайне горизонтальне масштабування кластера."

      - alert: HighQueueSojournTime
        expr: histogram_quantile(0.95, sum(rate(request_sojourn_time_seconds_bucket[5m])) by (le)) > 0.050
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "95-й перцентиль часу очікування в черзі перевищує 50 мс"
          description: "Черга завдань деградує; шеддер перейшов у стан активного відсікання фонового трафіку."
```
