# 📋 Специфікація маршрутизації та квот мультиарендного шлюзу

У мультиарендній розподіленій архітектурі прикладний програмний інтерфейс (API Gateway) або вхідний проксі-сервер (Ingress Proxy) виконує роль першої лінії оборони платформи. Шлюз приймає весь зовнішній потік трафіку, ідентифікує конкретного орендаря (Tenant Resolution), валідує його криптографічні облікові дані, перевіряє поточний стан лічильників пропускної здатності та транслює запит у відповідний ізольований контур — автономну комірку (Cell) або виділений фізичний силос.

Цей документ визначає структурну специфікацію конфігураційних моделей, формати метаданих, протокол узгодження HTTP-заголовків, структури відповідей лімітування швидкості, механіку взаємного TLS (mTLS), регламент плавного виведення комірок з експлуатації (Graceful Draining) та стандартні контракти обробки помилок.

---

## 1. Схема конфігурації орендаря (Tenant Routing Entry)

Реєстр орендарів (Tenant Control Plane) зберігає та синхронізує параметри конфігурації для кожного активного клієнта платформи. Вхідний шлюз кешує ці записи в локальній оперативній пам'яті та оновлює їх за подіями через шину конфігурацій або протокол gRPC xDS.

Конфігураційний запис описується структурою JSON Schema:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "tenant_id": "t-acme-corp-001",
  "slug": "acme",
  "status": "ACTIVE",
  "tier": "ENTERPRISE",
  "isolation_model": "HYBRID",
  "routing": {
    "cell_id": "cell-eu-central-02",
    "cluster_endpoint": "https://internal.cell-02.eu.app.net",
    "storage": {
      "strategy": "DATABASE_PER_TENANT",
      "dsn_secret_arn": "arn:aws:secretsmanager:eu-central-1:123456:secret:tenant-acme-db-xyz",
      "read_replica_endpoint": "postgres-ro-cell02.internal.net:5432"
    }
  },
  "quotas": {
    "rate_limit_rps": 2500,
    "burst_capacity": 5000,
    "concurrent_requests": 150,
    "max_payload_size_mb": 25,
    "storage_quota_gb": 500
  },
  "security": {
    "auth_provider": "OIDC",
    "issuer": "https://auth.acme.com/",
    "jwks_uri": "https://auth.acme.com/.well-known/jwks.json",
    "enforce_mtls": true,
    "allowed_ip_ranges": [
      "198.51.100.0/24",
      "203.0.113.50/32"
    ]
  }
}
```

### Детальний опис полів та семантики конфігурації

Кожне поле конфігурації виконує чітко визначену роль у ланцюжку обробки запиту:

1. `tenant_id`: Глобально унікальний ідентифікатор орендаря, що залишається незмінним протягом усього життєвого циклу клієнта. Використовується в усіх внутрішніх таблицях бази даних, ключах кешу та мітках аудиту.
2. `slug`: Людсько-зрозумілий псевдонім орендаря, що використовується для маршрутизації за субдоменами або в префіксах URL.
3. `status`: Життєвий стан клієнта (`PROVISIONING`, `ACTIVE`, `SUSPENDED`, `DRAINING`, `DECOMMISSIONED`). Запити до орендарів у стані `SUSPENDED` миттєво блокуються на рівні шлюзу з поверненням коду `423 Locked`.
4. `tier`: Категорія обслуговування орендаря (`FREE`, `STARTER`, `PRO`, `ENTERPRISE`), що визначає пріоритет у чергах планувальника, гарантії доступності та максимальний ліміт паралельних потоків обробки.
5. `isolation_model`: Модель архітектурного розміщення. Значення `SILO` спрямовує запит на виділений стек серверів і бази даних; `HYBRID` використовує спільний кластер мікросервісів з виділеною базою даних або схемою; `POOL` спрямовує трафік у спільний багатоорендний кластер із захистом через Row-Level Security.
6. `routing.cell_id`: Ідентифікатор автономної комірки відмовостійкості, в якій розгорнуто інфраструктуру цього клієнта. Дозволяє повністю локалізувати можливі апаратні аварії.
7. `quotas`: Числові параметри лімітування трафіку за алгоритмом Token Bucket (швидкість генерації токенів `rate_limit_rps`, місткість кошика для обробки сплесків `burst_capacity` та гранична кількість одночасних з'єднань `concurrent_requests`).

## 2. Протокол резолюції та ієрархія пріоритетів вилучення Tenant ID

Для детермінованого визначення орендаря шлюз виконує покроковий аналіз метаданих запиту за строгою ієрархією пріоритетів:

```
+─────────────────────────────────────────────────────────────+
| 1. Перевірений JWT Claim (Пріоритет 1 - Найвищий):         |
|    Вилучається з поля "tid" або "tenant_id" валідованого    |
|    криптографічним підписом токена Bearer.                 |
+─────────────────────────────────────────────────────────────+
                              ↓ (якщо запит без токена або публічний)
+─────────────────────────────────────────────────────────────+
| 2. Субдомен у заголовку Host (Пріоритет 2):                 |
|    Приклад: "acme.api.service.io" -> slug="acme"            |
+─────────────────────────────────────────────────────────────+
                              ↓ (якщо використовується спільний домен)
+─────────────────────────────────────────────────────────────+
| 3. Префікс шляху URL (Пріоритет 3):                         |
|    Приклад: "/v1/tenants/t-acme-corp-001/orders"            |
+─────────────────────────────────────────────────────────────+
```

### Алгоритм перевірки та запобігання підміні орендаря (Tenant Spoofing)

Процес ідентифікації та перевірки повноважень складається з чотирьох послідовних кроків:

1. **Крок 1 (Вилучення токена):** Шлюз витягує рядок авторизації `Authorization: Bearer <JWT>`. Якщо токен присутній, шлюз перевіряє криптографічний підпис асиметричним ключем за протоколом OIDC/JWKS.
2. **Крок 2 (Валідація клеймів):** З розшифрованого тіла токена зчитується поле `tenant_id`. Якщо токен містить недійсний або невідомий ідентифікатор, шлюз негайно повертає код `401 Unauthorized`.
3. **Крок 3 (Перевірка цілісності контексту):** Якщо запит був надісланий на субдомен конкретного клієнта (наприклад, `beta.app.io`), але JWT містить `tenant_id` іншого клієнта (`alpha`), шлюз фіксує спробу міжклієнтської підміни (Cross-Tenant Spoofing Attempt) і повертає `403 Forbidden` із детальним аудиторським записом.
4. **Крок 4 (Санітизація заголовків):** Будь-який сирий заголовок `X-Tenant-ID`, надісланий зовнішнім клієнтом, примусово видаляється або замінюється перевіреним значенням із токена. Внутрішня мережа мікросервісів отримує лише авторизовані дані.

### Обробка взаємного TLS (mTLS) для корпоративних інтеграцій

Для замовників рівня Enterprise шлюз підтримує взаємну автентифікацію через сертифікати X.509 (mTLS). Під час встановлення TLS-з'єднання шлюз:
* Вилучає поле `Subject Alternative Name` (SAN) або `Common Name` (CN) із наданого клієнтського сертифіката;
* Звіряє відбиток (fingerprint) сертифіката із зареєстрованим публічним ключем орендаря в модулі безпеки;
* При успішному збігу інжектує атрибут `X-Tenant-Auth-Method: mTLS` у внутрішній контекст запиту, дозволяючи обробку без традиційного Bearer токена.

## 3. Специфікація внутрішніх заголовків (Gateway to Upstream)

Після успішної перевірки автентичності та застосування лімітів пропускної здатності шлюз транслює запит у внутрішній кластер мікросервісів, додаючи стандартизований набір службових метаданих:

```http
POST /api/v2/orders HTTP/1.1
Host: internal.cell-02.eu.app.net
X-Forwarded-For: 203.0.113.195
X-Tenant-ID: t-acme-corp-001
X-Tenant-Tier: ENTERPRISE
X-Tenant-Cell: cell-eu-central-02
X-Tenant-Isolation-Model: HYBRID
baggage: tenant.id=t-acme-corp-001,tenant.tier=ENTERPRISE
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

### Таблиця внутрішніх заголовків і вимог до мікросервісів

| Заголовок | Формат | Опис та правила обробки в сервісі |
| :--- | :--- | :--- |
| `X-Tenant-ID` | `string` | Канонічний ідентифікатор орендаря. Обов'язково використовується для встановлення `SET LOCAL app.current_tenant_id` у базі даних. |
| `X-Tenant-Tier` | `string` | Рівень тарифу. Використовується чергами воркерів для визначення пріоритету виконання фонових завдань. |
| `X-Tenant-Cell` | `string` | Ідентифікатор комірки, в якій обробляється запит. Дозволяє виявляти помилки некоректної міжкоміркової маршрутизації. |
| `baggage` | W3C Baggage | Наскрізні мітки OpenTelemetry. Автоматично прокидаються клієнтськими HTTP-бібліотеками в усі наступні мікросервіси в ланцюжку викликів. |
| `traceparent` | W3C Trace Context | Глобальний ідентифікатор розподіленого трейсу для кореляції логів, затримок і помилок конкретного орендаря. |

## 4. Контракт лімітування швидкості (Rate Limiting Protocol)

Для захисту спільних вузлів від монополізації окремими клієнтами шлюз реалізує дворівневий алгоритм Token Bucket на базі розподіленого кешу Redis:
* **Рівень 1 (Глобальний ліміт шлюзу):** Захищає фізичну ноду від загального перевантаження мережевого стека.
* **Рівень 2 (Квота орендаря):** Обмежує інтенсивність викликів конкретного клієнта згідно з його тарифом.

### Успішна відповідь у межах квоти

Якщо лічильник токенів орендаря не вичерпаний, шлюз додає до відповіді інформаційні заголовки про залишок ліміту:

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-RateLimit-Tenant-Limit: 2500
X-RateLimit-Tenant-Remaining: 1842
X-RateLimit-Tenant-Reset: 1718928000
```

### Відповідь при перевищенні квоти (HTTP 429)

Якщо орендар вичерпав баланс токенів у кошику сплеску, шлюз негайно скидає запит без звернення до бази даних і повертає стандартизований документ про помилку RFC 7807 (Problem Details for HTTP APIs):

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 3
X-RateLimit-Tenant-Limit: 2500
X-RateLimit-Tenant-Remaining: 0
X-RateLimit-Tenant-Reset: 1718928003

{
  "type": "https://api.service.io/errors/tenant-rate-limit-exceeded",
  "title": "Tenant Rate Limit Exceeded",
  "status": 429,
  "detail": "Tenant 't-acme-corp-001' has exceeded the provisioned throughput quota of 2500 RPS.",
  "instance": "/v1/orders/req-991823",
  "tenant_id": "t-acme-corp-001",
  "retry_after_seconds": 3
}
```

## 5. Протокол плавного виведення комірок з експлуатації (Graceful Draining)

Під час проведення регламентних робіт, оновлення версій ядра або виведення з ладу апаратних серверів певної комірки шлюз підтримує протокол керованого вичерпання трафіку (Graceful Draining):

1. **Фаза сповіщення (Health Check Status):** Реєстр переводить статус комірки в `DRAINING`. Внутрішні перевірки живості `/health/readiness` починають сигналізувати шлюзу про небажаність надходження нових довготривалих сесій.
2. **Фаза завершення активних з'єднань:** Шлюз дозволяє завершити виконання всіх уже розпочатих HTTP-запитів і транзакцій, але додає до заголовків відповідей директиву `Connection: close`.
3. **Фаза динамічного перемикання:** Усі нові запити клієнтів автоматично перенаправляються на резервну або оновлену комірку згідно з оновленими записами маршрутизатора.

## 6. Специфікація стандартних кодів помилок та станів відмови

Для запобігання невизначеності на стороні клієнтських додатків уся підсистема ізоляції використовує уніфіковану таблицю кодів відповідей:

| HTTP Код | Машинний Error Code | Причина виникнення та рекомендації щодо виправлення |
| :--- | :--- | :--- |
| `401 Unauthorized` | `TENANT_AUTH_REQUIRED` | Запит не містить валідного токена автентифікації або закінчився термін дії JWT-підпису. |
| `403 Forbidden` | `TENANT_MISMATCH` | Ідентифікатор орендаря в токені не збігається з цільовим ресурсом або субдоменом у заголовку Host. |
| `404 Not Found` | `TENANT_NOT_FOUND` | Запитуваний клієнтський субдомен або slug не зареєстрований у системі або був видалений. |
| `423 Locked` | `TENANT_SUSPENDED` | Орендаря тимчасово заблоковано через несплату рахунків або виявлення підозрілої активності. |
| `429 Too Many Requests` | `TENANT_QUOTA_EXCEEDED` | Перевищено секундну квоту запитів (RPS) або ліміт паралельних з'єднань; клієнту слід застосувати експоненційне відкладання. |
| `503 Service Unavailable` | `TENANT_CELL_MAINTENANCE` | Автономна комірка, в якій розміщено ресурси клієнта, перебуває в режимі планового регламентного обслуговування. |
