# 📜 Еволюція зворотних проксі: від акселератора Squid до NGINX та Envoy

У середині 1990-х років архітектура Всесвітнього павутиння базувалася на гранично простій моделі: клієнтський браузер встановлював пряме TCP-з'єднання з вебсервером (переважно NCSA HTTPd або ранніми версіями Apache HTTP Server), надсилав текстовий рядок `GET /index.html HTTP/1.0` і отримував статичний HTML-документ. Сервери тієї епохи використовували модель обробки з виділенням окремого системного процесу під кожне вхідне з'єднання через системний виклик `fork()`. Доки кількість одночасних відвідувачів вимірювалася десятками, ця схема працювала бездоганно.

Криза вибухнула наприкінці 1990-х із бурхливим зростанням комерційного інтернету. Коли на один сайт одночасно приходили тисячі користувачів, операційна система витрачала майже весь процесорний час на перемикання контексту між тисячами важких процесів, а оперативна пам'ять вичерпувалася за лічені секунди. Кожен процес Apache споживав від 5 до 20 мегабайтів оперативної пам'яті; двісті паралельних з'єднань блокували гігабайти пам'яті, змушуючи ядро вмикати повільний дисковий свопінг (англ. *swap*).

## Відкриття навиворіт: «акселератор httpd» у проєкті Harvest та Squid

Ідея зворотного проксі народилася як несподіване переосмислення технології прямого клієнтського кешування. У 1994–1996 роках дослідники Університету Південної Каліфорнії та Університету Колорадо на чолі з Пітером Данцигом (англ. *Peter Danzig*) розробляли проєкт Harvest — систему розподіленого кешування вебсторінок для університетських мереж. Згодом Двейн Весселс (англ. *Duane Wessels*) виокремив кешувальний демон у незалежний проєкт з відкритим кодом під назвою **Squid**.

Squid створювався як класичний **прямий проксі** (англ. *forward proxy*): сотні комп'ютерів локальної мережі кампусу надсилали свої вихідні запити через один спільний сервер, який кешував популярні вебсторінки й тим самим економив дорогий зовнішній супутниковий чи магістральний трафік.

```
Класичний прямий кеш Harvest/Squid (1996):
[Клієнт A] ──┐
[Клієнт B] ──┼─► [ Squid Forward Proxy ] ──WAN──► [ Відкритий Інтернет ]
[Клієнт C] ──┘
```

У 1997 році інженери помітили, що архітектуру Squid можна розгорнути на 180 градусів. Замість того, щоб ставити проксі перед клієнтами для прискорення їхнього виходу в інтернет, його поставили безпосередньо **перед вебсервером** Apache. Проксі-сервер почав слухати публічний порт 80, приймаючи на себе весь вхідний потік з інтернету, тоді як сам важкий Apache перенесли на внутрішній порт 8080.

```
Режим «акселератора httpd» (народження зворотного проксі):
[ Інтернет-трафік ] ──► [ Squid у режимі прискорювача :80 ] ──LAN──► [ Apache :8080 ]
                               │
                       [ Локальний кеш RAM/Disk ]
```

У документації Squid цей режим отримав назву **«httpd-акселератор»** (англ. *httpd accelerator mode*). Squid відповідав на 80–90% запитів до картинок та статичних файлів прямо з оперативної пам'яті або локального диска за мілісекунди, навіть не торкаючись процесів Apache. До бекенда доходили лише динамічні запити, для яких формувалися CGI-скрипти.

Офіційне закріплення термінології відбулося на рівні інженерних стандартів IETF: у січні 2001 року було опубліковано RFC 3040 (*Internet Web Replication and Caching Taxonomy*), де термін **Reverse Proxy** (зворотний проксі) було стандартизовано як синонім до понять *Surrogate* та *Server-Side Accelerator*.

## Проблема C10K та криза блокуючого вводу-виводу

Попри успіх кешування, на початку 2000-х років інтернет зіткнувся з фундаментальним бар'єром масштабування операційних систем, який інженер Ден Кегель (англ. *Dan Kegel*) у 1999 році назвав **проблемою C10K** (англ. *The C10K Problem* — обслуговування десяти тисяч одночасних клієнтських з'єднань на одному фізичному сервері).

Традиційні вебсервери використовували блокуючі сокети (англ. *blocking I/O*) та механізми мультиплексування `select()` або `poll()`. Складність опитування дескрипторів у цих системних викликах становила `O(N)`: операційна система мусила послідовно перебирати весь масив із 10 000 сокетів при кожній появі бодай одного байта в будь-якому з них. Це призводило до катастрофічної деградації продуктивності:

```
Складність опитування сокетів у ядрі:
select() / poll() :  O(N)  ── час зростає лінійно від загальної кількості відкритих сокетів
epoll / kqueue    :  O(1)  ── час залежить виключно від кількості активних подій
```

Щоб подолати цей глухий кут, розробники операційних систем створили нові неблокуючі механізми повідомлення про події, що працюють зі складністю `O(1)`:
* У 2000 році Джонатан Лемон (англ. *Jonathan Lemon*) представив підсистему **kqueue** у FreeBSD 4.1.
* У 2002 році Девід Лібелі (англ. *Davide Libenzi*) розробив підсистему **epoll** для ядра Linux (включена в реліз Linux 2.5.44 і закріплена у стабільній гілці Linux 2.6).

Потрібна була принципово нова архітектура сервера, яка б відмовилася від парадигми «один потік на з'єднання» на користь однопотокового неблокуючого циклу подій (англ. *Event Loop*).

## Ігор Сисоєв та поява NGINX (2002–2004)

У 2002 році системний адміністратор російського інтернет-порталу «Рамблер» Ігор Сисоєв зіткнувся з практичною проблемою: серверна інфраструктура захлиналася від повільних клієнтів. У ті роки користувачі підключалися до інтернету через повільні комутовані телефонні лінії (Dial-Up) зі швидкістю 33.6–56 кбіт/с. Коли користувач завантажував зображення розміром 500 кілобайтів, передача тривала понад дві хвилини.

Вебсервер Apache тримав робочий процес заблокованим протягом усіх двох хвилин просто для того, щоб байт за байтом проштовхувати статичний файл крізь повільне з'єднання. Сотні таких повільних користувачів повністю вичерпували пул воркерів Apache, блокуючи доступ для всіх інших.

Сисоєв вирішив написати з нуля ультралегкий зворотний проксі мовою C, використовуючи архітектуру неблокуючих подій:
1. Кілька робочих процесів (воркерів), зафіксованих за кількістю ядер процесора.
2. Неблокуючий цикл подій на основі системних викликів `kqueue` (FreeBSD) та `epoll` (Linux).
3. Асинхронна буферизація: проксі з блискавичною швидкістю зчитував відповідь від бекенда Apache через локальну петлю `127.0.0.1` за кілька мілісекунд, відпускав процес Apache для обробки наступного запиту, а потім самостійно утримував повільне TCP-з'єднання з користувачем, повільно віддаючи байти зі свого буфера в пам'яті.

Перший публічний реліз **NGINX** (версія 0.1.0) відбувся 4 жовтня 2004 року. Завдяки феноменальній енергоефективності та здатності утримувати понад 50 000 одночасних з'єднань на скромному комп'ютері з 512 МБ пам'яті, NGINX став стандартом де-факто для зворотного проксіювання у глобальному масштабі.

## Віллі Тарро та HAProxy (2001–2006)

Паралельно з NGINX розвивався інший знаковий проєкт — **HAProxy** (англ. *High Availability Proxy*), створений французьким інженером Віллі Тарро (фр. *Willy Tarreau*) у грудні 2001 року.

Тарро сконцентрувався на задачі надійного розподілу TCP- та HTTP-трафіку (L4/L7) між кластерами бекендів. На відміну від універсальних вебсерверів, HAProxy створювався виключно як високопродуктивний проксі та балансувальник:
* Повна відсутність операцій із локальною дисковою файловою системою (нуль операцій читання файлів із диска, що усувало блокування процесорних потоків).
* Однопотокова архітектура на основі спеціалізованих пулів буферів і власних планувальників завдань (англ. *elastic pollers*).
* Глибока інспекція заголовків на швидкості фізичного каналу та введення розширеного моніторингу працездатності бекендів (Health Checks).

У 2006 році вийшов HAProxy 1.3, де було реалізовано підтримку мультиплексування з'єднань та протоколу HTTP Keep-Alive, що закріпило за ним статус найнадійнішого інструмента для термінації та маршрутизації корпоративного трафіку.

## Хмарна ера та поява Envoy у компанії Lyft (2015)

З переходом індустрії до мікросервісної архітектури, динамічних контейнерів (Docker, Kubernetes) та сервісних сіток (Service Mesh) класичні зворотні проксі першого покоління зіткнулися з новими обмеженнями:
1. **Статична конфігурація:** NGINX та HAProxy вимагали перезавантаження конфігураційного файлу (`reload`) при зміні списку IP-адрес бекендів. У кластері з тисячами подів, які створюються й видаляються щосекунди, постійні перезавантаження спричиняли накопичення сокетів у стані очікування та деградацію затримок.
2. **Нестача спостережуваності:** Для діагностики відмов у ланцюжках із десятків мікросервісів були потрібні наскрізне трасування (Distributed Tracing), прозорий збір метрик для Prometheus та підтримка сучасних протоколів HTTP/2 і gRPC як першокласних громадян.

У 2015 році Метт Кляйн (англ. *Matt Klein*) та команда інженерів компанії Lyft створили **Envoy** — зворотний проксі нового покоління, написаний сучасною мовою C++11.

```
Еволюція зворотних проксі в інфраструктурі:
┌─────────────────────────┐     ┌─────────────────────────┐     ┌─────────────────────────┐
│ 1996–2000: Squid / ESI  │ ──► │  2002–2010: NGINX/HAProxy│ ──► │   2015+: Envoy / Traefik│
│ • Кешування статики     │     │ • Розрив WAN/LAN        │     │ • Динамічний xDS gRPC   │
│ • Зняття пікового навант│     │ • Неблокуючий epoll     │     │ • Service Mesh Sidecar  │
│ • httpd-акселератор     │     │ • Термінація TLS        │     │ • Вбудований mTLS/Trace │
└─────────────────────────┘     └─────────────────────────┘     └─────────────────────────┘
```

Envoy запровадив парадигму **динамічного керування площиною даних (xDS API)**: проксі більше не читає статичні файли, а підключається через двонаправлений gRPC-стрім до сервера управління (Control Plane), оновлюючи маршрути, кластери бекендів та сертифікати TLS на льоту без втрати жодного з'єднання.

Сьогодні зворотний проксі трансформувався з простого буферного щита для Apache у фундамент усієї сучасної хмарної інфраструктури: від прикордонних шлюзів Ingress у Kubernetes до локальних процесів-помічників Sidecar у сервісних сітках.
