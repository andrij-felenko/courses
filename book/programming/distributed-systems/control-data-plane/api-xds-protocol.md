# 📋 Протокол xDS: контракт взаємодії між площиною управління та площиною даних

Протокол **xDS (англ. *x Discovery Service*)** є відкритим універсальним контрактом взаємодії між серверами площини управління (Control Plane) та проксі-рушіями або бібліотеками площини даних (Data Plane). Спочатку розроблений для L7-проксі Envoy, протокол став міжгалузевим стандартом, який підтримується в сервісних сітках (Istio, Linkerd, Kuma), API-шлюзах (Envoy Gateway, Gloo), клієнтських бібліотеках gRPC (gRPC xDS для C++, Java, Go, Python) та контролерах ingress-трафіку.

Транспортний шар xDS реалізовано поверх протоколу gRPC (HTTP/2) з використанням двійкової серіалізації Protocol Buffers версії 3. Це забезпечує потокову двосторонню доставку конфігурацій із мінімальними накладними витратами на парсинг та передачу даних мережею.

## Архітектурний розподіл ресурсів xDS

Конфігурація площини даних у моделі xDS не є монолітним файлом, а розбита на слабопов'язані ресурси з чітко визначеними межами відповідальності. Кожен тип ресурсу обслуговується власним Discovery Service:

| Сервіс | Повна назва | Type URL у Protobuf | Зона відповідальності |
| :--- | :--- | :--- | :--- |
| **LDS** | Listener Discovery Service | `type.googleapis.com/envoy.config.listener.v3.Listener` | Конфігурація відкритих TCP/UDP сокетів, TLS-контексти, ланцюжки фільтрів L4/L7 |
| **RDS** | Route Discovery Service | `type.googleapis.com/envoy.config.route.v3.RouteConfiguration` | Таблиці маршрутизації, зіставлення префіксів URL, HTTP-заголовків, правила перенаправлення, канареечні спліти |
| **CDS** | Cluster Discovery Service | `type.googleapis.com/envoy.config.cluster.v3.Cluster` | Логічні пули сервісів (вибір алгоритму балансування, параметри виявлення DNS/EDS, таймаути підключення, запобіжники) |
| **EDS** | Endpoint Discovery Service | `type.googleapis.com/envoy.config.endpoint.v3.ClusterLoadAssignment` | Фізичні IP-адреси та порти конкретних подів/вузлів, вагові коефіцієнти, пріоритети зон доступності та стан здоров'я |
| **SDS** | Secret Discovery Service | `type.googleapis.com/envoy.extensions.transport_sockets.tls.v3.Secret` | Динамічна доставка криптографічних ключів, TLS-сертифікатів робочих навантажень та кореневих довірених сертифікатів CA |
| **ADS** | Aggregated Discovery Service | Мультиплексований gRPC потік | Агрегований сервіс, що об'єднує доставку всіх ресурсів (LDS, RDS, CDS, EDS, SDS) у межах єдиного TCP-з'єднання зі збереженням причинно-наслідкового порядку |
| **ECDS** | Extension Config Discovery | `type.googleapis.com/envoy.config.core.v3.TypedExtensionConfig` | Динамічне підвантаження та гаряче оновлення фільтрів розширення (Wasm-плагіни, власні Lua-скрипти) |
| **RTDS** | Runtime Discovery Service | `type.googleapis.com/envoy.service.runtime.v3.Runtime` | Динамічні прапорці функціоналу (Feature Flags), відсоткові ліміти та налаштування поведінки під навантаженням |
| **VHDS** | Virtual Host Discovery | `type.googleapis.com/envoy.config.route.v3.VirtualHost` | Динамічне завантаження окремих віртуальних хостів для масштабних RDS-таблиць із десятками тисяч доменів |

## Порядок залежностей ресурсів (Resource Ordering Graph)

Між різними ресурсами xDS існує сувора причинно-наслідкова залежність. Неправильний порядок застосування конфігурацій призводить до скидання користувацького трафіку через тимчасову відсутність цільового об'єкта в локальній пам'яті проксі:

```
                  +--------------------------------+
                  |  1. CDS (Створення кластера)   |
                  +--------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  |  2. EDS (Додавання адрес подів)|
                  +--------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  |  3. SDS (Завантаження ключів)  |
                  +--------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  |  4. LDS (Створення слухача)    |
                  +--------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  |  5. RDS (Маршрут на кластер)   |
                  +--------------------------------+
```

1. **CDS передує EDS:** Проксі-сервер не може зареєструвати конкретні кінцеві IP-адреси бекендів (EDS), доки в пам'яті не створено сам логічний кластер (CDS), якому ці адреси належать.
2. **CDS/EDS передують RDS:** Правило маршрутизації (RDS) не може направляти HTTP-трафік на ім'я кластера `srv_payments`, якщо цей кластер ще не ініціалізовано. Спроба виконати такий маршрут призведе до генерації помилки `503 Service Unavailable`.
3. **SDS передує LDS:** TLS-сертифікати та закриті ключі повинні бути успішно завантажені в криптографічний контекст до того, як слухач сокета почне приймати вхідні TLS-рукостискання від клієнтів.
4. **LDS передує RDS:** Слухач портів (LDS) зв'язується з назвою конфігурації маршрутів (RouteConfigurationName).

Сервіс **ADS (Aggregated Discovery Service)** був створений спеціально для того, щоб площина управління могла передавати оновлення всіх типів ресурсів через єдиний упорядкований потік, усуваючи стан гонитви (race conditions), який неминуче виникав під час використання окремих незалежних gRPC-з'єднань для кожного сервісу.

## Специфікація Protocol Buffers v3

### Базові структури State-of-the-World (SotW)

У класичній моделі State-of-the-World площина управління передає повний перелік усіх ресурсів заданого типу під час кожного оновлення:

```protobuf
syntax = "proto3";

package envoy.service.discovery.v3;

import "google/protobuf/any.proto";
import "google/rpc/status.proto";

// Ідентифікація клієнтського вузла площини даних
message Node {
  string id = 1;                     // Унікальний рядок (наприклад: "sidecar~10.244.0.12~order-pod.default~cluster.local")
  string cluster = 2;                // Логічна назва групи сервісу
  map<string, string> metadata = 3;  // Довільні атрибути (версія бінарника, зона доступності, регіон)
  string user_agent_name = 4;        // Назва рушія (Envoy, gRPC-Go, gRPC-C++)
  string user_agent_version = 5;     // Версія клієнтської бібліотеки
}

// Запит на отримання ресурсів від площини даних
message DiscoveryRequest {
  string version_info = 1;           // Номер поточної активної версії на боці клієнта
  Node node = 2;                     // Метадані вузла (надсилаються обов'язково в першому запиті)
  repeated string resource_names = 3;// Список імен потрібних ресурсів (порожній = підписка на всі)
  string type_url = 4;               // Схема ресурсу (LDS, RDS, CDS, EDS, SDS)
  string response_nonce = 5;         // Одноразовий токен для підтвердження обробки відповіді
  google.rpc.Status error_detail = 6;// Заповнюється тільки у разі відхилення конфігурації (NACK)
}

// Відповідь з конфігурацією від площини управління
message DiscoveryResponse {
  string version_info = 1;           // Номер версії згенерованого зліпка
  repeated google.protobuf.Any resources = 2; // Масив серіалізованих об'єктів заданого type_url
  bool canary = 3;                   // Ознака експериментального канареечного оновлення
  string type_url = 4;               // Схема переданих ресурсів
  string nonce = 5;                  // Унікальний одноразовий ідентифікатор транзакції
  string control_plane_id = 6;       // Ідентифікатор вузла управління для діагностики
}
```

## Протокол узгодження та квитування (ACK/NACK State Machine)

Для гарантії цілісності та запобігання застосуванню некоректних конфігурацій протокол xDS використовує детермінований автомат станів із двостороннім підтвердженням:

```
Площина даних (Envoy)                              Площина управління (Istiod)
        |                                                     |
        |=== 1. DiscoveryRequest ============================>|
        |    version_info: ""                                 |
        |    response_nonce: ""                               |
        |    type_url: "type.../Cluster"                      |
        |                                                     |
        |<== 2. DiscoveryResponse ============================|
        |    version_info: "v101"                             |
        |    nonce: "nonce-AAA"                               |
        |    resources: [Cluster "srv-auth", "srv-pay"]       |
        |                                                     |
  [Валідація пройшла успішно]                                 |
        |                                                     |
        |=== 3. DiscoveryRequest (ACK) ======================>|
        |    version_info: "v101"                             |
        |    response_nonce: "nonce-AAA"                      |
        |    error_detail: NULL                               |
        |                                                     |
        |<== 4. DiscoveryResponse ============================|
        |    version_info: "v102"                             |
        |    nonce: "nonce-BBB"                               |
        |    resources: [Cluster з некоректним таймаутом -5s] |
        |                                                     |
  [Помилка: валідація схеми провалена!]                       |
        |                                                     |
        |=== 5. DiscoveryRequest (NACK) =====================>|
        |    version_info: "v101"  <-- Залишаємо версію v101! |
        |    response_nonce: "nonce-BBB"                      |
        |    error_detail: { code: 3, message: "Timeout < 0" }|
        |                                                     |
  *Проксі продовжує безпечну роботу на старій версії v101*
```

### Правила обробки підтверджень:

1. **Ініціалізація зв'язку:** Клієнт відкриває gRPC-потік і надсилає початковий `DiscoveryRequest`, де `version_info` та `response_nonce` мають порожні значення `""`.
2. **Формування відповіді:** Сервер управління генерує відповідь `DiscoveryResponse` з новим значенням `version_info` (наприклад, `"v101"`) та унікальним випадковим рядком `nonce` (наприклад, `"nonce-AAA"`).
3. **Позитивне квитування (ACK):** Клієнт перевіряє отримані ресурси на синтаксичну та семантичну коректність. Якщо валідація успішна, нова конфігурація атомарно застосовується в пам'яті, а клієнт надсилає наступний `DiscoveryRequest`, у якому встановлює `version_info = "v101"`, `response_nonce = "nonce-AAA"` та очищає поле `error_detail`.
4. **Негативне квитування (NACK):** Якщо проксі виявляє помилку (дублікати портів слухачів, невалідні регулярні вирази в маршрутах, відсутність сертифікатів), клієнт відхиляє зліпок. Він відправляє `DiscoveryRequest`, де обов'язково вказує отриманий `response_nonce = "nonce-BBB"`, але зберігає значення `version_info = "v101"` (попередню валідну версію) та заповнює поле `error_detail` описом дефекту. Сервер управління фіксує NACK у метриках і сповіщає операторів про збій генерації конфігурації.
5. **Захист від застарілих відповідей (Stale Nonce):** Якщо сервер отримує підтвердження з `response_nonce`, який не збігається з останнім надісланим токеном для цього типу ресурсу, пакет вважається застарілим і мовчки ігнорується, що усуває проблеми розсинхронізації під час мережевих затримок.

## Інкрементальний протокол Delta xDS

У масштабних кластерах із тисячами мікросервісів модель передачі повного стану (SotW) створює надмірне навантаження: зміна IP-адреси одного пода призводить до генерації багатомегабайтних відповідей для кожного проксі.

Для вирішення цієї проблеми специфікація xDS визначає інкрементальний протокол **Delta xDS**, що функціонує за моделлю підписок та дельта-змін:

```protobuf
message DeltaDiscoveryRequest {
  Node node = 1;
  string type_url = 2;
  repeated string resource_names_subscribe = 3;   // Нові ресурси для підписки
  repeated string resource_names_unsubscribe = 4; // Ресурси, підписку на які скасовано
  map<string, string> initial_resource_versions = 5; // Поточні версії ресурсів { назва: версія }
  string response_nonce = 6;
  google.rpc.Status error_detail = 7;
}

message Resource {
  string name = 1;                    // Унікальна назва ресурсу
  repeated string aliases = 2;        // Псевдоніми ресурсу
  string version = 3;                 // Версія конкретного ресурсу
  google.protobuf.Any resource = 4;   // Тіло ресурсу
  google.protobuf.Duration ttl = 5;   // Опціональний час життя (Time-to-Live)
}

message DeltaDiscoveryResponse {
  string system_version_info = 1;     // Загальна версія стану системи
  repeated Resource resources = 2;    // Тільки створені або змінені ресурси
  repeated string removed_resources = 3; // Список видалених назв ресурсів
  string nonce = 4;
}
```

### Переваги моделі Delta xDS:

* **Економія мережевого трафіку:** Розмір пакетів оновлення скорочується на 95–99%, оскільки передаються лише дельти.
* **Зниження навантаження на процесор:** Проксі оновлює в локальній таблиці лише один змінений запис без необхідності повної рекомпіляції всієї таблиці маршрутизації.
* **Підтримка TTL:** Ресурси можуть мати термін дії, після завершення якого проксі самостійно видаляє застарілий бекенд, якщо оновлення не надійшло вчасно.

## Керування транспортом, зворотний тиск та ротація сертифікатів

Надійність роботи xDS у виробничих середовищах спирається на три ключові механізми транспортного рівня:

1. **Контроль потоку gRPC (Flow Control та Backpressure):** Завдяки віконному механізму керування потоком HTTP/2, повільний клієнт площини даних не буде затоплений оновленнями від швидкого контролера. Якщо буфер сокета проксі заповнюється, потік gRPC призупиняє генерацію нових відповідей на боці Control Plane до звільнення черги.
2. **Періодичні перевірки зв'язку (HTTP/2 PING Keepalives):** Оскільки керуючі gRPC-з'єднання є довгоживучими, проміжні мережеві шлюзи чи фаєрволи можуть скидати неактивні TCP-сесії. Контролер періодично надсилає PING-фрейми кожні 30 секунд для збереження відкритого транзитного стану.
3. **Безшовна ротація сертифікатів через SDS:** Коли термін дії mTLS-сертифіката добігає кінця, агент безпеки надсилає новий секрет через SDS-потік. Envoy оновлює криптографічний контекст пам'яті в реальному часі без переривання активних користувацьких з'єднань і без перезапуску процесу.
