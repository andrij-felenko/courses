# 📋 Специфікація контрактів, протокольних конвертів та сигналів деградації

У розподілених архітектурах часткова відповідь не є помилкою — це штатна форма виконання запиту в умовах дефіциту часу чи збою залежностей. Якщо система стикається з відмовою або уповільненням другорядних компонентів, агрегатор не скидає з'єднання, а формує корисну відповідь на основі збереженого ядра транзакції. Проте для того, щоб клієнтські додатки (браузерний JavaScript, мобільні клієнти iOS та Android, сторонні інтеграційні шлюзи) могли коректно інтерпретувати неповні дані та адаптувати інтерфейс без аварійних завершень, взаємодія повинна спиратися на стандартизований протокольний контракт.

Нижче наведено детальну специфікацію сигнальних HTTP-заголовків, правила поширення бюджету дедлайну по розподіленому графу, директиви запобігання отруєнню кешу, схеми Protobuf v3, структуру JSON-конверта, семантичні атрибути розподіленого трасування та інструкції для клієнтських SDK.

## 1. Стандартизовані HTTP-заголовки деградації

Шлюзи та бекенд-сервіси передають стан деградації через набір HTTP-заголовків, що доповнюють стандартні директиви RFC 7234 та RFC 9110:

| Заголовок | Тип значення | Призначення та семантика |
| :--- | :--- | :--- |
| `X-Degraded` | `string` | Перелік деградованих рівнів системи (наприклад: `Tier-1,Tier-2`). |
| `X-Degraded-Features` | `string` | Перелік конкретних бізнес-функцій, які було відсічено або замінено на фолбек (наприклад: `ml_recommendations,live_reviews`). |
| `X-Data-Staleness-Sec` | `integer` | Вік застарілих даних у секундах, якщо відповідь сформовано з кешу замість свіжого запиту до БД. |
| `X-Latency-Budget-Remaining-Ms` | `integer` | Залишок наскрізного бюджету часу запиту на момент виходу з поточного сервісу. |
| `Warning` | `string` | Стандартне попередження за RFC 7234 (наприклад: `199 - "Partial response: Tier-2 shed due to deadline exceeded"`). |
| `Cache-Control` | `string` | Директиви клієнтського кешування для деградованих відповідей: `private, no-cache, stale-if-error=300`. |

## 2. Наскрізне поширення бюджету часу (Distributed Deadline Propagation)

Кожен вхідний HTTP- або gRPC-запит на рівні API Gateway отримує фіксований квант часу — загальний дедлайн (наприклад, 120 мілісекунд від моменту прийому сокета). Під час звернення до внутрішніх мікросервісів шлюз зобов'язаний динамічно перераховувати залишок цього бюджету і передавати його у заголовку `X-Latency-Budget-Remaining-Ms` (для HTTP/REST) або `grpc-timeout` (для gRPC).

Якщо внутрішній сервіс бачить, що отриманий залишок бюджету становить менше ніж 10 мс, а його власна середня тривалість обробки становить 25 мс, він навіть не починає важку транзакцію до бази даних. Сервіс негайно повертає локальний фолбек, заощаджуючи процесорні такти кластера та дозволяючи агрегатору встигнути віддати відповідь клієнту до спрацьовування жорсткого таймауту.

## 3. Захист від отруєння публічного кешу (Cache Invalidation & Poisoning)

Критична небезпека часткових відповідей полягає у випадковому кешуванні деградованого стану спільними проміжними проксі-серверами (NGINX, Envoy, Cloudflare CDN). Якщо сервіс віддав відповідь без блоку персональних рекомендацій, а CDN зберегла цей документ на 10 хвилин, то тисячі наступних користувачів отримуватимуть обрізану сторінку навіть після того, як проблемний мікросервіс повністю відновив свою роботу.

Щоб уникнути цього дефекту, протокол деградації висуває суворі вимоги до заголовка `Cache-Control`:
- Будь-яка відповідь із прапорцем деградації `X-Degraded` **заборонена** для публічного кешування (`Cache-Control: private, no-cache, no-store`).
- Для умовно застарілих даних із L2-кешу використовується директива `stale-while-revalidate=60, stale-if-error=300`, яка дозволяє браузеру показувати збережену копію, одночасно ініціюючи фонове оновлення свіжого стану без блокування користувача.

## 4. Схема Protobuf v3: Протокольний конверт часткової відповіді

Для міжсервісної взаємодії через gRPC використовується уніфікований конверт метаданих деградації `DegradationMetadata`, що вбудовується в кожне бізнес-повідомлення:

```protobuf
syntax = "proto3";

package resilience.v1;

import "google/protobuf/timestamp.proto";
import "google/protobuf/duration.proto";

enum DegradationLevel {
  DEGRADATION_LEVEL_UNSPECIFIED = 0;
  DEGRADATION_LEVEL_NONE = 1;        // Повний режим (100% свіжості та повноти)
  DEGRADATION_LEVEL_MINOR = 2;       // Tier-2 відсічено (косметика / рекомендації)
  DEGRADATION_LEVEL_MODERATE = 3;    // Tier-1 деградовано (ціни / каталог з кешу)
  DEGRADATION_LEVEL_CRITICAL = 4;    // Працює виключно транзакційне ядро Tier-0
}

enum FallbackSource {
  FALLBACK_SOURCE_UNSPECIFIED = 0;
  FALLBACK_SOURCE_LOCAL_CACHE = 1;   // Локальний L1/L2 кеш інстансу
  FALLBACK_SOURCE_STATIC_STUB = 2;   // Статична заздалегідь скомпільована заглушка
  FALLBACK_SOURCE_HEURISTIC = 3;     // Евристичний розрахунок замість ML-моделі
  FALLBACK_SOURCE_EMPTY_LIST = 4;    // Порожній масив (відсікання блоку)
}

message DegradedFieldInfo {
  string field_path = 1;             // JSON-path або ім'я поля (наприклад: "order.price")
  FallbackSource source = 2;         // Джерело походження даних
  google.protobuf.Duration age = 3;  // Вік кешованих даних
  string reason = 4;                 // Причина (наприклад: "timeout_exceeded_35ms")
}

message DegradationMetadata {
  bool is_degraded = 1;
  DegradationLevel level = 2;
  repeated DegradedFieldInfo degraded_fields = 3;
  google.protobuf.Duration processing_time = 4;
  google.protobuf.Duration latency_budget_remaining = 5;
}

// Приклад сервісної відповіді замовлення
message GetOrderDetailsResponse {
  uint64 order_id = 1;
  double total_amount = 2;
  repeated string item_names = 3;
  repeated string recommended_item_ids = 4;
  
  DegradationMetadata degradation = 15; // Метадані завжди займають фіксований тег
}
```

## 5. JSON REST-контракт

Для зовнішніх клієнтів REST API шлюз повертає HTTP-статус `200 OK` (або `206 Partial Content`, якщо клієнт явно передав заголовок `Prefer: handling=lenient`), загортаючи дані у двосекційну структуру `data` + `meta`:

```json
{
  "data": {
    "order_id": 987654321,
    "status": "CONFIRMED",
    "total_amount": 450.00,
    "currency": "UAH",
    "items": [
      {
        "id": "item_101",
        "name": "Механічна клавіатура",
        "quantity": 1
      }
    ],
    "recommendations": [
      "item_default_bestseller_1",
      "item_default_bestseller_2",
      "item_default_bestseller_3"
    ]
  },
  "meta": {
    "degraded": true,
    "level": "MODERATE",
    "execution_time_ms": 41.8,
    "degraded_components": [
      {
        "field": "data.total_amount",
        "fallback": "LOCAL_CACHE",
        "data_age_sec": 142,
        "warning": "Ціна отримана з реплікованого кешу залишків"
      },
      {
        "field": "data.recommendations",
        "fallback": "STATIC_TOP",
        "data_age_sec": 0,
        "warning": "AI-персоналізація пропущена за дедлайном 35 мс"
      }
    ]
  }
}
```

## 6. Конвенція HTTP-кодів стану та крайові випадки

Вибір коду відповіді залежить від того, чи збережено цілісність критичного транзакційного ядра (Tier-0), та від типу HTTP-методу (мутація чи безпечне читання):

| Стан обробки запиту | Метод | HTTP-код | Семантика для клієнта |
| :--- | :--- | :--- | :--- |
| **Усі сервіси відповіли вчасно** | `GET / POST` | `200 OK` | Повна свіжа відповідь, `meta.degraded = false`. |
| **Tier-2 / Tier-1 деградовано, Tier-0 успішний** | `GET` | `200 OK` | Частковий успіх. Клієнт рендерить сторінку, підсвічуючи застарілі поля. |
| **Запит клієнта вимагав лише повноту** | `GET` | `206 Partial` | Клієнт передав `Prefer: return=representation`, отримав часткові дані. |
| **Мутація збережена в черзі (Outbox)** | `POST / PUT` | `202 Accepted` | Замовлення збережено в локальному журналі; транзакція виконується асинхронно. |
| **Відмова Tier-0 (платіж не пройшов)** | `POST` | `503 Service Unavail` | Критична відмова. Клієнт показує екран помилки та пропонує повторити спробу. |

### Крайовий випадок: мутації стану (POST/PUT/DELETE)
Деградація для операцій запису вимагає особливої обережності: не можна «деградувати» списання грошей поверненням дефолтної константи. Якщо падає банківський шлюз або транзакційна база даних замовлень, запит зобов'язаний повернути чистий `503 Service Unavailable` з обов'язковим заголовком `Retry-After: 5`. Деградація на рівні запису допустима лише за наявності ідемпотентного транзакційного буфера (Transactional Outbox), коли агрегатор гарантує, що збережений намір буде доставлено адресату після відновлення зв'язку без ризику подвійного списання.

## 7. Простеження та діагностика через OpenTelemetry

Для моніторингу та розслідування інцидентів (RCA, англ. *Root Cause Analysis*) агрегатор додає стандартизовані атрибути у спани розподіленого трасування (OpenTelemetry Tracing):

- `resilience.degraded` (`bool`): чи було застосовано деградацію під час формування спану;
- `resilience.degraded_tier` (`string`): перелік рівнів, що перейшли у фолбек (`tier1`, `tier2`);
- `resilience.fallback_latency_us` (`int`): час виконання фолбеку в мікросекундах (має бути `< 100 µs`);
- `resilience.original_error` (`string`): первинна причина відсікання (`deadline_exceeded`, `circuit_breaker_open`).

Завдяки цим міткам інженери SRE можуть одним SQL-подібним запитом у Jaeger чи Zipkin відфільтрувати всі деградовані запити та локалізувати сервіс, чия хвостова затримка спровокувала каскадний перехід на резервний шлях.

## 8. Політика клієнтських SDK та захист від шторму повторів

Головна вимога до клієнтських додатків при отриманні деградованої відповіді — **сувора заборона автоматичних повторів** (англ. *no immediate retries*).

Якщо мобільний застосунок отримує `HTTP 200 OK` із заголовком `X-Degraded: Tier-2`, він зобов'язаний відмалювати отримані дані без повторного негайного надсилання запиту. Якщо клієнт вирішить «перезапитати свіжі рекомендації через 100 мс», тисячі додатків синхронно повторять запити, викликавши лавинний шторм повторів (англ. *retry storm*), який остаточно доб'є знесилений бекенд.

Єдиний коректний патерн для клієнта — тихе фонове опитування (Background Polling) з експоненційним відступом та обов'язковим випадковим джитером (Full Jitter), яке починається не раніше ніж через 30–60 секунд після первинної часткової відповіді.

## 9. Узгодження схем при версіонуванні API (Schema Evolution)

Коли контракт деградованої відповіді розвивається з часом (додаються нові поля, змінюється структура вкладених блоків метаданих), критично важливо гарантувати **зворотну сумісність** фолбек-структур. 

У двійкових форматах (Protobuf, FlatBuffers) нові поля деградації завжди додаються з новими числовими тегами, а старі клієнти ігнорують невідомі поля через механізм збереження невідомих байтів (unknown fields). У текстових форматах (JSON) парсери на клієнтських платформах зобов'язані налаштовуватися в режимі стійкості до невідомих ключів (англ. *lenient parsing* / `FAIL_ON_UNKNOWN_PROPERTIES = false`), що унеможливлює падіння інтерфейсу при додаванні нового типу метаданих про стан кластера.
