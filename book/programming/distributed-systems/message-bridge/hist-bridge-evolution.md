# 📜 Від закритих MOM-каналів до хмарних реплікаторів: еволюція мостів повідомлень

Коли в середині 1980-х років великі фінансові корпорації та промислові підприємства почали об'єднувати мейнфрейми IBM System/370 з першими відомчими серверами на базі Unix та VAX/VMS, інженери зіткнулися з фундаментальним розривом зв'язку. Програми на мейнфреймах оперували блоковими терміналами SNA (Systems Network Architecture) та кодуванням EBCDIC, тоді як робочі станції взаємодіяли через сокети TCP/IP та набір символів ASCII. Прямий віддалений виклик процедур (RPC) між цими світами був неможливий: будь-яка мережева затримка чи тимчасове перезавантаження шлюзу спричиняли аварійне завершення клієнтських транзакцій.

Подолання цієї прірви породило окремий клас програмного забезпечення — проміжне ПЗ, орієнтоване на повідомлення (англ. *Message-Oriented Middleware*, MOM). Замість синхронного очікування відповіді програми передавали структуровані пакети даних у локальні буфери черг. Проте кожна черга існувала лише в межах одного вузла чи одного екземпляра менеджера черг. Виникла потреба в автономному механізмі, який здатний вичитувати повідомлення з локальної черги на одній машині та надійно транспортувати їх через ненадійну мережу в чергу іншої системи, не вимагаючи змін у коді прикладних програм.

```
+------------------+      +-------------------------+      +------------------+
|  Queue Manager A | ---> | Message Channel Agent   | ---> |  Queue Manager B |
|  (MVS Mainframe) |      | (SDR -> Network -> RCVR)|      |  (AIX / Unix)    |
+------------------+      +-------------------------+      +------------------+
```

## Канали черг IBM MQSeries та зародження концепції зв'язування

У 1993 році лабораторія IBM у Гайрслі (Велика Британія, під керівництвом Джона О'Коннора) у співпраці з компанією Systems Strategies Inc. представила комерційний продукт MQSeries (згодом перейменований на WebSphere MQ, а нині IBM MQ). Головною інновацією системи стала концепція каналів передачі повідомлень (Message Channels) та керуючих ними агентів — Message Channel Agents (MCA).

Архітектура каналу MQSeries втілювала перший промисловий міст повідомлень:
1. Прикладний процес публікував повідомлення у спеціальну локальну чергу передачі (Transmission Queue).
2. Агент відправки (Sender MCA) у фоновому потоці вичитував повідомлення з черги передачі, пакував їх у мережеві кадри та відкривав TCP/IP або SNA-сесію до віддаленого хоста.
3. Агент прийому (Receiver MCA) на боці адресата приймав байти, перевіряв цілісність, перекодовував корисне навантаження з EBCDIC в ASCII та записував пакет у цільову чергу.
4. Лише після того, як Receiver MCA фіксував повідомлення на диску свого менеджера черг, Sender MCA видаляв оригінал із черги передачі.

Паралельно компанія Digital Equipment Corporation (DEC) розвивала систему DECmessageQ (пізніше придбану BEA Systems), де взаємодія між різними шинами повідомлень (Message Buses) здійснювалася через крос-шинні маршрутизатори (Cross-Bus Routers). Ці механізми довели життєздатність принципу: зв'язування комунікаційних систем має відбуватися на рівні самої інфраструктури доставки, залишаючи кінцеві бізнес-сервіси в повній ізоляції від мережевої топології.

## Формалізація патерну в каталозі Хопа та Вульфа

До початку 2000-х років корпоративні ІТ-ландшафти перетворилися на зоопарк несумісних технологій: поряд з IBM MQ з'явилися брокери TIBCO Rendezvous, Microsoft MSMQ, SonicMQ та стандартизований інтерфейс Java Message Service (JMS 1.0, випущений Sun Microsystems у 1998 році). Підприємства не могли замінити всі існуючі черги на одну систему через величезну вартість ліцензій та міграцій.

У 2003 році Ґреґор Хоп (Gregor Hohpe) та Боббі Вульф (Bobby Woolf) опублікували фундаментальну працю «Enterprise Integration Patterns: Designing, Building, and Deploying Messaging Solutions». Автори узагальнили накопичений індустрією досвід і вперше формалізували **Міст повідомлень** (Message Bridge) як самостійний архітектурний шаблон.

Хоп і Вульф провели чітку межу між мостом та іншими інтеграційними патернами:
* [Маршрутизатор повідомлень](book:programming/message-router) (Message Router) обирає шлях для повідомлення всередині однієї системи обміну повідомленнями.
* [Транслятор повідомлень](book:programming/message-translator) (Message Translator) змінює бізнес-схему та формат корисного навантаження.
* **Міст повідомлень** (Message Bridge) з'єднує дві або більше різних систем обміну повідомленнями (або два фізично відокремлених домени однієї системи), роблячи повідомлення, опубліковані в одній системі, доступними в іншій без втручання відправника.

```
+-------------------+      +-------------------------+      +-------------------+
| Messaging System A| ---> |      MESSAGE BRIDGE     | ---> | Messaging System B|
| (JMS / ActiveMQ)  |      | Consumer A -> Producer B|      | (AMQP / RabbitMQ) |
+-------------------+      +-------------------------+      +-------------------+
```

У середині 2000-х років цей шаблон став фундаментом для фреймворків інтеграції з відкритим кодом. У 2007 році Джеймс Страчан (James Strachan) створив Apache Camel, а Росс Мейсон (Ross Mason) у 2005 році заснував Mule ESB. У цих інструментах міст описувався декларативними DSL-маршрутами: споживач підключався до одного брокера через спеціалізований адаптер компонента, перекладав заголовки в узагальнений внутрішній об'єкт обміну (Exchange) і передавав його продюсеру цільового брокера.

## Епоха IoT та протоколу MQTT: мости між периферією та хмарою

На початку 2010-х років бурхливий розвиток інтернету речей (IoT) створив новий виклик масштабованості та мережевої зв'язності. Сенсори та польові контролери мали вкрай обмежені обчислювальні ресурси й підключалися через дорогі стільникові або супутникові канали з високим рівнем втрати пакетів.

Для таких умов стандартом став протокол MQTT (створений у 1999 році Енді Стенфорд-Кларком з IBM та Арленом Ніппером з Arcom Control Systems, стандартизований OASIS у 2014 році). Невеликі локальні брокери (наприклад, Eclipse Mosquitto, розроблений Роджером Лайтом у 2009 році) встановлювалися безпосередньо на заводах, нафтових вишках чи транспортних засобах.

Однак аналітичні платформи підприємств будувалися в централізованих хмарах. Змушувати десятки тисяч периферійних датчиків відкривати прямі TLS-з'єднання з хмарою було економічно невигідно й ненадійно через часті розриви зв'язку.

Вирішенням став вбудований у Mosquitto та EMQX механізм MQTT Bridge:
* Локальний брокер на заводі збирає тисячі телеметричних повідомлень від сенсорів по стабільній локальній мережі.
* Вбудований клієнт моста відкриває єдине захищене TCP-з'єднання до хмарного брокера (наприклад, AWS IoT Core або центрального кластера Mosquitto).
* Міст пересилає агреговані топіки за правилом префіксації (наприклад, `factory/berlin/sensors/#` → `cloud/eu/berlin/sensors/#`), буферизуючи дані на локальному накопичувачі у разі обриву зовнішнього інтернет-каналу.

## Великі дані та криза геореплікації: шлях від MirrorMaker 1 до MirrorMaker 2

У 2011 році Джей Крепс (Jay Kreps), Неха Нархеде (Neha Narkhede) та Джун Рао (Jun Rao) створили в надрах LinkedIn розподілений журнал подій Apache Kafka. Kafka кардинально відрізнялася від традиційних черг: замість деструктивного вичитування повідомлень вона пропонувала незмінний розподілений лог із партиціями та збереженням історії.

Зі зростанням глобальної інфраструктури компанії виникла потреба в міжрегіональній реплікації даних: потоки подій із дата-центрів у Європі та Азії мали стікатися в центральний аналітичний кластер у США для навчання моделей машинного навчання та побудови глобальних звітів.

### Падіння першого покоління (MirrorMaker 1)

Першою відповіддю спільноти Kafka став інструмент MirrorMaker 1 (MM1). Це була проста консольна програма, що запускала пул стандартних Kafka Consumer, які вичитували дані з вихідного кластера, і передавала байти пулу стандартних Kafka Producer для запису в цільовий кластер.

На практиці під високим навантаженням MM1 виявився вкрай нестабільним:
1. **Шторми ребалансування:** Будь-яка зміна кількості партицій у топіку або тимчасовий збій одного процесу споживача активували протокол ребалансування групи в Kafka. Під час ребалансування весь процес реплікації зупинявся на десятки секунд або хвилини, накопичуючи гігабайти відставання (лагу).
2. **Втрата відповідності офсетів:** MM1 записував повідомлення в цільовий кластер як абсолютно новий потік даних. Офсети вихідного та цільового кластерів не збігалися. Якщо сервіс споживача падав і мав переключитися на резервний кластер, він не знав, з якого саме зміщення продовжувати читання, що призводило або до масової втрати даних, або до мільйонних дублікатів.
3. **Неможливість динамічного оновлення:** Додавання нових топіків до списку реплікації вимагало повної зупинки процесу MM1 і ручного редагування конфігураційного файлу.

Для порятунку власних критичних систем компанія Uber у 2015 році розробила власну заміну під назвою **uReplicator**, яка використовувала Apache Helix для динамічного управління партиціями без зупинки споживачів.

### Революція MirrorMaker 2 (KIP-382)

У грудні 2019 року в релізі Apache Kafka 2.4.0 інженер Раянн Долан (Ryanne Dolan) представив повністю переосмислену архітектуру — **MirrorMaker 2.0** (MM2), засновану на стандартному фреймворку Kafka Connect.

```
+-------------------------------------------------------------------------+
|                  Apache Kafka MirrorMaker 2.0 (KIP-382)                 |
|                                                                         |
|  +------------------------+  +-------------------+  +----------------+  |
|  | MirrorSourceConnector  |  | CheckpointConnect |  | HeartbeatConn  |  |
|  | (Дані + простори імен) |  | (Мапінг офсетів)  |  | (Моніторинг)   |  |
|  +------------------------+  +-------------------+  +----------------+  |
+-------------------------------------------------------------------------+
```

MirrorMaker 2 запровадив три фундаментальні інженерні рішення, що визначили сучасний стандарт мостів розподілених журналів:
* **Автоматичне запобігання петлям через простори імен:** MM2 реплікує топік `orders` із кластера `us-east` у кластер `eu-west` під префіксованим іменем `us-east.orders`. Це унеможливило циклічне зациклення повідомлень у топологіях active-active (де обидва дата-центри одночасно приймають записи).
* **Синхронізація офсетів (Checkpoint Connector):** MM2 безперервно транслює стан зміщень груп споживачів між кластерами, записуючи мапінг вихідних і цільових офсетів у службовий топік `checkpoints`. Це дозволило споживачам виконувати прозорий failover між дата-центрами за частки секунди.
* **Динамічний моніторинг конфігурацій:** Міст автоматично відстежує створення нових топіків, зміну кількості партицій та ACL-прав на джерелі, синхронізуючи ці параметри з цільовим кластером у реальному часі.

## Сучасність: безсерверні та мультихмарні мости подій

У 2020-х роках концепція моста повідомлень вийшла на рівень глобальних хмарних платформ. Розподілені системи дедалі частіше будуються на базі сервісів від різних постачальників: AWS, Google Cloud Platform, Microsoft Azure та сторонніх SaaS-рішень (Shopify, Stripe, Salesforce).

Компанія Amazon Web Services представила AWS EventBridge Pipes — керований безсерверний міст, що зв'язує понад 14 джерел подій (DynamoDB Streams, Kinesis, SQS, MSK) з десятками цільових сервісів. Google Cloud розгорнув аналогічний сервіс Eventarc.

Сучасні мости подій спираються на відкритий стандарт **CloudEvents** (прийнятий Cloud Native Computing Foundation, CNCF у 2019 році), який уніфікує метадані повідомлень (ідентифікатор, джерело, тип події, часова мітка). Це перетворило міст повідомлень із вузькоспеціалізованого шлюзу між двома чергами на універсальну шину синхронізації цифрового простору, що об'єднує мікроконтролери на периферії, приватні корпоративні дата-центри та глобальні хмарні інфраструктури.
