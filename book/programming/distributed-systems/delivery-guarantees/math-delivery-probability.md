## 1. Базова модель стохастичного каналу

Розглянемо двох учасників: відправника `A` та отримувача `B`, з'єднаних двонаправленим асинхронним каналом зв'язку.

Нехай:
- `p` — імовірність втрати прямого повідомлення від `A` до `B` (`0 < p < 1`);
- `q` — імовірність втрати зворотного повідомлення-підтвердження (ACK) від `B` до `A` (`0 < q < 1`).

Припустимо на першому кроці, що події втрати окремих пакетів є статистично незалежними.

Для кожної окремої спроби передачі повідомлення можливі три взаємовиключні наслідки:

```
Подія S (успіх):      повідомлення дійшло до B, і ACK дійшов до A
Подія D (дублікатний): повідомлення дійшло до B, але ACK загубився
Подія L (втрата):      повідомлення загубилося на шляху до B
```

Обчислимо ймовірності кожної з цих елементарних подій для одного раунду передачі:

```
P(L) = p                                      [прямий пакет загубився]
P(D) = (1 - p)·q                              [прямий дійшов, зворотний загубився]
P(S) = (1 - p)·(1 - q)                        [обидва пакети успішно доставлені]
```

Перевіримо повноту простору елементарних подій:

```
P(L) + P(D) + P(S)
= p + (1 - p)·q + (1 - p)·(1 - q)             [підставили вирази ймовірностей]
= p + (1 - p)·(q + 1 - q)                     [винесли (1 - p) за дужки]
= p + (1 - p)·1                               [спростили суму q + 1 - q = 1]
= p + 1 - p                                   [розкрили дужки]
= 1                                           [сума ймовірностей дорівнює одиниці]
```

## 2. Імовірність неуспіху раунду та геометричний розподіл спроб

Відправник `A` вважає раунд успішним лише тоді, коли настає подія `S` (отримано ACK). Якщо ж настає подія `L` або `D`, відправник фіксує таймаут і змушений ініціювати повторну спробу.

Позначимо ймовірність успіху одного раунду через `r`, а ймовірність таймауту (неуспіху з погляду відправника) через `f`:

```
r = P(S) = (1 - p)·(1 - q)
f = 1 - r = 1 - (1 - p)·(1 - q)
= 1 - (1 - q - p + p·q)                       [перемножили дужки]
= p + q - p·q                                 [ймовірність таймауту відправника]
```

Якщо відправник налаштований повторювати запит до першого успішного отримання квитанції, випадкова величина `K` (кількість необхідних спроб) підпорядковується геометричному розподілу з параметром успіху `r`:

```
P(K = k) = f^(k - 1) · r                      [ймовірність успіху рівно на k-й спробі]
```

Математичне сподівання кількості спроб `E[K]` та дисперсія `Var(K)` обчислюються за класичними формулами геометричного розподілу:

```
E[K]
= ∑ (k · f^(k - 1) · r)                       [за означенням матсподівання, k від 1 до ∞]
= r · ∑ (k · f^(k - 1))                       [винесли сталу r за знак суми]
= r · (1 / (1 - f)²)                          [сума похідної геометричного ряду]
= r · (1 / r²)                                [оскільки 1 - f = r]
= 1 / r                                       [підсумкове матсподівання спроб]
= 1 / ((1 - p)·(1 - q))                       [виразили через імовірності втрат]
```

```
Var(K)
= (1 - r) / r²                                [дисперсія геометричного розподілу]
= f / r²                                      [виразили через f та r]
= (p + q - p·q) / ((1 - p)² · (1 - q)²)       [у термінах параметрів мережі]
```

**Числовий приклад:**
Якщо ймовірність втрати пакета в прямому напрямку становить `p = 0.05` (5 %), а у зворотному `q = 0.05` (5 %):

```
r = (1 - 0.05)·(1 - 0.05) = 0.95 · 0.95 = 0.9025
f = 1 - 0.9025 = 0.0975 (9.75 %)
E[K] = 1 / 0.9025 ≈ 1.108 спроби
```

## 3. Гарантія надійності при обмеженні `k` спроб

У реальних системах відправник не може чекати вічно. Кількість спроб обмежують числом `k_max`.

Ймовірність повної втрати повідомлення `P_loss(k_max)` (коли всі `k_max` спроб зазнали невдачі) становить:

```
P_loss(k_max) = f^(k_max) = (p + q - p·q)^(k_max)
```

Відповідно, підсумкова надійність доставки `R(k_max)` (імовірність того, що хоча б одна спроба увінчалася успіхом) дорівнює:

```
R(k_max) = 1 - P_loss(k_max) = 1 - (p + q - p·q)^(k_max)
```

Щоб досягти цільового рівня надійності `R_target` (наприклад, `0.99999` — «п'ять дев'яток»), мінімальна кількість повторів `k_min` визначається логарифмуванням:

```
1 - f^k ≥ R_target                            [нерівність цільової надійності]
f^k ≤ 1 - R_target                            [перенесли одиницю]
k · ln(f) ≤ ln(1 - R_target)                  [прологарифмували обидві частини]
k ≥ ln(1 - R_target) / ln(f)                  [врахували, що ln(f) < 0, знак змінився]
```

**Приклад розрахунку:**
При `p = 0.05`, `q = 0.05` маємо `f = 0.0975`. Для досягнення `R_target = 0.999999` (шість дев'яток, тобто ризик втрати не більше 1 на мільйон):

```
ln(1 - 0.999999) = ln(10⁻⁶) = -13.8155
ln(0.0975) = -2.3279
k_min = ceil(-13.8155 / -2.3279) = ceil(5.935) = 6 спроб
```

Шість спроб гарантують необхідну надійність за умови незалежності збоїв.

## 4. Математичне виведення ризику дублювання

Головна плата за усунення втрат через повторні спроби — неминуча поява дублікатів.

Дублікат виникає тоді, коли отримувач `B` отримав і виконав повідомлення на спробі `i < k`, але відправник `A` не отримав ACK і виконав повторну спробу `i + 1`.

Ймовірність того, що конкретна невдала спроба (яка закінчилася таймаутом у `A`) насправді призвела до виконання дії на стороні `B`, є умовною ймовірністю події `D` за умови, що не настала подія `S`:

```
P(D | timeout)
= P(D) / P(timeout)                           [за формулою умовної ймовірності Байєса]
= P(D) / (P(D) + P(L))                        [розписали простір невдалих подій]
= ((1 - p)·q) / ((1 - p)·q + p)               [підставили значення ймовірностей]
= ((1 - p)·q) / (q - p·q + p)                 [розкрили дужки в знаменнику]
= ((1 - p)·q) / f                             [оскільки f = p + q - p·q]
```

Якщо система виконує `k` спроб до першого успішного завершення, математичне сподівання кількості фактичних доставок повідомлення до вузла `B` (позначимо як `M`) становить:

```
E[M]
= E[K] · (1 - p)                              [кожна спроба доходить до B з імовірністю 1 - p]
= (1 / ((1 - p)·(1 - q))) · (1 - p)           [підставили E[K]]
= 1 / (1 - q)                                 [спростили дріб]
```

**Фундаментальний висновок:**
Середня кількість разів, яку отримувач бачить повідомлення, **взагалі не залежить від втрат у прямому каналі `p`**, а залежить **виключно від утрат квитанцій `q`**.

Якщо `q = 0.1` (10 % квитанцій губиться):

```
E[M] = 1 / (1 - 0.1) = 1 / 0.9 ≈ 1.111 доставок
```

Кожне десяте повідомлення в середньому обробляється двічі або більше разів. Це математично підтверджує: механізм повторів (*at-least-once*) перетворює проблему втрат на проблему дублювання.

## 5. Корельовані втрати: модель Гілберта-Елліотта

У реальних мережах втрати пакетів рідко бувають статистично незалежними. Коли мережевий комутатор або маршрутизатор зазнає переповнення буфера черги (*tail drop*), він скидає цілі пачки послідовних пакетів (*packet bursts*).

Для опису такої поведінки застосовують двостанову марковську модель **Гілберта-Елліотта** (англ. *Gilbert-Elliott Model*).

Мережевий канал перебуває в одному з двох станів:
- Стан `G` (Good — добрий): канал працює стабільно, імовірність втрати пакета `p_G ≈ 0`.
- Стан `B` (Bad — поганий): буфер переповнений або лінк деградував, імовірність втрати пакета `p_B ≈ 1`.

Ймовірності переходу між станами:
- `α = P(G → B)` — імовірність переходу з доброго стану в поганий за один такт.
- `β = P(B → G)` — імовірність відновлення з поганого стану в добрий за один такт.

Стаціонарні ймовірності перебування каналу в доброму та поганому станах:

```
π_G = β / (α + β)                             [стаціонарна ймовірність доброго стану]
π_B = α / (α + β)                             [стаціонарна ймовірність поганого стану]
```

Середня тривалість пачки втрат (*Burst Length*, кількість послідовно втрачених пакетів):

```
L_burst = 1 / β                               [середній час перебування в стані Bad]
```

**Математичний висновок для дизайну повторів:**
Якщо система виконує негайний повтор (*immediate retry*) з інтервалом `Δt < L_burst`, наступний пакет із майже 100 % імовірністю потрапить у той самий стан `B` і знову буде втрачений.

Саме тому алгоритм **експоненційного відтермінування (Exponential Backoff)** є математичною необхідністю: він прогресивно збільшує інтервал очікування `T_retry`, щоб гарантовано перевищити середню довжину сплеску `L_burst` і дочекатися повернення марковського ланцюга в стан `G`.

## 6. Вплив хвоста затримок (Tail Latency) на хибні таймаути

Дублікати виникають не лише через фізичну втрату пакетів, а й через затримки.

Нехай час кругового обігу запиту (*Round-Trip Time, RTT*) є випадковою величиною `T_rtt` з логнормальним або парето-розподілом (характерним для затримок у хмарних дата-центрах).

Нехай клієнт встановив статичний таймаут `T_out`.

Ймовірність виникнення **хибного таймауту** (коли пакет не загубився, але відповідь прийшла пізніше, ніж клієнт припинив чекати) дорівнює:

```
P_false_timeout = P(T_rtt > T_out) = 1 - F_rtt(T_out)
```

де `F_rtt` — функція кумулятивного розподілу затримки.

Якщо в системі `p = 0` та `q = 0` (мережа фізично не губить жодного байта), але клієнт обрав таймаут `T_out` на рівні 99-го перцентиля затримок (`p99`), то:

```
P_false_timeout = 1 - 0.99 = 0.01 (1 %)
```

Це означає, що рівно **1 % усіх успішно оброблених запитів буде повторено клієнтом як дублікати**, виключно через затримку відповіді. При потоці в 100 000 запитів за секунду це створює 1 000 непотрібних повторних мутацій щосекунди.

Це математично доводить: збільшення таймауту зменшує кількість дублікатів, але збільшує час виявлення реальних аварій.

## 7. Оптимізація таймауту: компроміс затримки та дублікатів

Вибір тривалості таймауту `T_out` є класичною задачею оптимізації загальної вартості системи (*Total Cost Function*).

Визначимо цільову функцію сукупних витрат `C(T_out)` як суму двох протилежних факторів:
1. **Ціна затримки виявлення аварії:** якщо запит справді загубився, клієнт даремно чекає `T_out` секунд. Нехай вартість одиниці часу очікування становить `c_delay`.
2. **Ціна обробки дубліката:** якщо таймаут виявився хибним, система витрачає ресурси на повторну передачу, транзакцію дедуплікації та навантаження бази даних. Нехай вартість одного дубліката становить `c_dup`.

Функція вартості має вигляд:

```
C(T_out) = c_delay · (1 - P(L)) · E[T_rtt | T_rtt ≤ T_out] + c_delay · P(L) · T_out + c_dup · P(T_rtt > T_out)
```

Для експоненційного розподілу затримок `F_rtt(t) = 1 - exp(-λ·t)` (де `1/λ` — середня затримка RTT):

```
P(T_rtt > T_out) = exp(-λ·T_out)              [хвіст експоненційного розподілу]
```

Диференціюючи функцію `C(T_out)` за змінною `T_out` та прирівнюючи похідну до нуля, отримуємо оптимальне значення таймауту `T_out^*`:

```
dC/dT_out = c_delay · P(L) - c_dup · λ · exp(-λ·T_out) = 0
c_dup · λ · exp(-λ·T_out) = c_delay · P(L)     [перенесли доданки]
exp(-λ·T_out) = (c_delay · P(L)) / (c_dup · λ) [поділили на коефіцієнт]
-λ·T_out = ln((c_delay · P(L)) / (c_dup · λ))  [прологарифмували]
T_out^* = (1 / λ) · ln((c_dup · λ) / (c_delay · P(L))) [оптимальний таймаут]
```

Ця формула математично показує:
- Чим дорожче коштує обробка дубліката (`c_dup`), тим більшим має бути таймаут (зсув у правий хвіст).
- Чим частіше губляться пакети (`P(L)`), тим коротшим має бути таймаут, щоб швидше запускати повтори.

## 8. Імовірності в кворумній реплікації (Quorum Delivery)

Коли повідомлення записується не в один вузол, а в реплікований кластер із `N` вузлів із кворумом запису `W` (наприклад, `N = 3`, `W = 2`), імовірність успішного збереження обчислюється через біноміальний розподіл.

Нехай кожен вузол доступний незалежно з імовірністю `a = 1 - p`.

Ймовірність того, що повідомлення буде успішно збережено на кворумі з щонайменше `W` вузлів за одну спробу:

```
P_quorum_success = ∑ (C(N, k) · a^k · (1 - a)^(N - k))   [сума для k від W до N]
```

де `C(N, k) = N! / (k! · (N - k)!)` — біноміальний коефіцієнт.

Для класичної конфігурації `N = 3`, `W = 2`:

```
P_quorum_success
= C(3, 2) · a² · (1 - a) + C(3, 3) · a³ · (1 - a)⁰ [розписали суму для k = 2 та k = 3]
= 3 · a² · (1 - a) + a³                       [обчислили коефіцієнти C(3,2)=3, C(3,3)=1]
= 3·a² - 3·a³ + a³                            [розкрили дужки]
= 3·a² - 2·a³                                 [звели подібні доданки: 3·a² - 2·a³]
```

Якщо доступність окремого вузла становить `a = 0.9` (90 %):

```
P_quorum_success
= 3 · (0.9)² - 2 · (0.9)³                     [підставили a = 0.9 у виведену формулу]
= 3 · 0.81 - 2 · 0.729                        [піднесли 0.9 до степенів 2 і 3]
= 2.43 - 1.458                                [виконали множення на коефіцієнти]
= 0.972                                       [підсумкова ймовірність успіху 97.2 %]
```

Кворумна схема підняла надійність з 90 % до 97.2 %, але якщо клієнт не дочекався підтвердження від другого вузла і повторив запит, перший вузол уже зафіксував дані — повторний запит гарантовано стає дублікатом.

## 9. Асиметрія каналів зв'язку та ефект блокування черги (HOL Blocking)

У реальних гетерогенних мережах імовірність втрати прямого каналу `p` (наприклад, мобільного висхідного каналу *Uplink*) часто в рази перевищує втрати зворотного каналу `q` (*Downlink*).

Нехай `p = 0.15` (15 % втрат на слабкому клієнтському передавачі), а `q = 0.01` (1 % втрат на потужному серверному каналі).

Обчислимо співвідношення між втратами запиту та втратами квитанції:

```
P(L) = p = 0.15                               [імовірність втрати запиту]
P(D) = (1 - p)·q = 0.85 · 0.01 = 0.0085       [імовірність втрати ACK]
P(S) = (1 - p)·(1 - q) = 0.85 · 0.99 = 0.8415 [успішний раунд]
```

У цій асиметричній конфігурації умовна частка дублікатів серед усіх таймаутів:

```
P(D | timeout)
= P(D) / (P(D) + P(L))                        [за формулою умовної ймовірності]
= 0.0085 / (0.0085 + 0.15)                    [підставили чисельні значення]
= 0.0085 / 0.1585                             [обчислили знаменник]
≈ 0.0536                                      [частка дублікатів становить 5.36 %]
```

Більшість таймаутів (94.6 %) тут спричинені реальною втратою запиту, тож повторні спроби є високоефективними.

Проте, якщо передача ведеться через одне TCP-з'єднання з гарантією впорядкованості байтів, втрата одного пакета блокує всі наступні незалежні повідомлення в буфері сокета — явище **Head-of-Line (HOL) Blocking**. Затримка доставки всіх чергових повідомлень стрибає з нормальних 20 мс до часу повторної передачі TCP `RTO` (200–1000 мс), що викликає каскадну хвилю хибних таймаутів у клієнтів.

## 10. Доведення неможливості детермінованого exactly-once

Доведемо теорему про неможливість фізичної доставки «рівно один раз» у ненадійному каналі методом від супротивного через редукцію до задачі двох генералів.

### Формальна постановка теореми

**Теорема:** Нехай існує розподілена система з двох вузлів `A` та `B`, з'єднаних каналом зв'язку, де будь-яке повідомлення може бути втрачене з імовірністю `0 < p < 1`. Тоді не існує детермінованого протоколу з кінцевою кількістю повідомлень `N`, який гарантує одночасно:
1. **Safety (безпека):** Вузол `B` обробляє дію рівно один раз.
2. **Liveness (живість):** Вузол `A` отримує точне підтвердження про виконання дії за скінченний час.
3. **Agreement (узгодженість):** Обидва вузли досягають однакового стану щодо факту завершення операції.

### Доведення (за індукцією по довжині протоколу)

Припустимо супротивне: такий коректний детермінований протокол `Π` існує.

Нехай `m` — мінімальна кількість повідомлень, необхідна протоколу `Π` для досягнення узгодженості в найкращому випадку (без втрат).

Розглянемо останнє повідомлення в протоколі — `m`-те повідомлення (позначимо його `msg_m`), надіслане, наприклад, від `B` до `A`.

Оскільки канал зв'язку є ненадійним, існує ненульова ймовірність, що повідомлення `msg_m` буде втрачено в мережі.

Розглянемо два сценарії виконання:

1. **Сценарій 1:** Усі `m` повідомлень успішно дійшли. Вузол `A` отримав `msg_m` і перейшов у стан завершеності `Commit`.
2. **Сценарій 2:** Перші `m - 1` повідомлень дійшли, а `msg_m` загубилося.

Оцінимо стан вузла `B` перед відправкою `msg_m`:
- Вузол `B` надіслав `msg_m` і більше не очікує жодних відповідей (оскільки `msg_m` — останнє повідомлення протоколу).
- Отже, вузол `B` зобов'язаний зафіксувати свій фінальний стан (`Commit`) **у момент відправки**, оскільки він ніколи не дізнається, чи дійшло `msg_m` до `A`.

Оцінимо стан вузла `A` у Сценарії 2:
- Вузол `A` не отримав `msg_m`.
- Чи має право `A` перейти в стан `Commit`?
  - Якщо `A` переходить у `Commit` без отримання `msg_m`, це означає, що повідомлення `msg_m` було зайвим і протокол міг завершитися за `m - 1` повідомлень. Це суперечить припущенню про мінімальність `m`.
  - Якщо `A` НЕ переходить у `Commit` (бо не знає, чи живий `B` і чи надіслав він повідомлення), то `B` зафіксував `Commit`, а `A` — ні. Це порушує умову **Agreement**.

Отже, останнє повідомлення `msg_m` не може бути гарантом узгодженості. Його можна або викреслити (зменшивши довжину протоколу до `m - 1`), або воно не рятує від розриву станів.

Застосовуючи цей крок за індукцією від `m` до `m - 1`, `m - 2`, ..., ми доходимо до базового випадку `m = 1`.

При `m = 1` відправник `A` надсилає єдине повідомлення до `B`. Якщо воно губиться, `A` не знає, чи воно загубилося в дорозі, чи `B` впав після обробки. Будь-яке детерміноване рішення `A` призводить або до втрати даних (якщо не повторити), або до дублювання (якщо повторити).

**Висновок доведення:**
Детермінована узгодженість через ненадійний канал зв'язку за скінченну кількість повідомлень є математично недосяжною. Єдиний спосіб подолати це обмеження на практиці — перенести задачу з рівня транспорту (*delivery*) на рівень алгебри стану (*state idempotency*).
