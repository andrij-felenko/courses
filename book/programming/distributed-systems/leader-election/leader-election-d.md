О третій годині ночі під час виконання планового розрахунку взаєморозрахунків із банками чотири екземпляри білінгового мікросервісу одночасно запустили щоденну процедуру клірингу. Кожен із чотирьох серверів вичитав із черги однаковий список із 18 400 очікуючих платежів на загальну суму 4.8 мільйона доларів і відправив запити на списання коштів у банківський шлюз. Оскільки в системі був відсутній єдиний координатор, кожен платіж було виконано чотири рази поспіль, перш ніж чергові інженери встигли зупинити процеси.

Цей інцидент оголює фундаментальну суперечність сучасної архітектури: з одного боку, мікросервіси масштабують горизонтально у вигляді десятків ідентичних екземплярів задля відмовостійкості та розподілу навантаження; з іншого — певні системні обов'язки є строго **поодинокими (монопольними)**. До таких задач належать:
- Запуск періодичних розкладів (Cron-джоби, нарахування відсотків, генерація щоденної звітності);
- Координація та динамічний розподіл партицій у потокових брокерах (наприклад, призначення топіків Kafka конкретним воркерам);
- Виконання міграцій схем баз даних або прогріву спільних кешів;
- Оркестрація розподілених транзакцій у патерні Сага;
- Гарячий резерв (Active-Passive Failover) для систем, які не підтримують паралельний запис.

Якщо такі операції виконуватимуть усі репліки одночасно, система зазнає дублювання транзакцій та пошкодження даних. Якщо ж жорстко зашити виконання на один статичний сервер, його апаратний збій миттєво паралізує всю підсистему (утворюється єдина точка відмови — SPOF).

**Вибори лідера (від англ. *leader* / давньоангл. *lǣdan* — вести, направляти; та англ. *election* / лат. *electio* — обрання)** — це архітектурний патерн координації, який динамічно призначає **рівно один активний екземпляр** серед групи однакових вузлів кластера для виконання монопольних задач, гарантуючи прозоре та автоматичне передавання повноважень (Failover) у разі відмови діючого лідера.

## 1. Делегований консенсус проти вбудованого консенсусу

Перше запитання, яке постає перед системним архітектором: чому прикладні мікросервіси не повинні реалізовувати протокол консенсусу (такий як Paxos або Raft) безпосередньо всередині власного коду?

У теоретичних роботах 1980-х років вузли кластера вважалися статичними серверами з фіксованими IP-адресами. Проте в сучасних хмарних середовищах (Kubernetes, AWS ECS, Nomad) контейнери постійно перебувають у динамічному русі:
- Автоматичне горизонтальне масштабування (HPA) додає та видаляє поди щогодини залежно від графіка навантаження;
- Процедури плавного оновлення (Rolling Updates) перезапускають кожен контейнер із новою версією коду, змінюючи його IP-адресу та ім'я хоста;
- Механізми витіснення (Pod Preemption / Node Spot Interruption) можуть примусово знищити контейнер у будь-яку секунду.

Якщо вбудувати алгоритм Raft у кожен бізнес-сервіс, будь-яке додавання чи перезапуск репліки вимагатиме виконання важкої процедури динамічної реконфігурації кворуму консенсусу (Joint Consensus). Крім того, Raft вимагає наявності локального диска з гарантованою синхронізацією запису (`fsync`), що прямо суперечить принципу безстанності (stateless) мікросервісів.

Тому сучасний золотий стандарт інженерії — **делеговані вибори лідера (Delegated Lease-Based Election)**:
1. Прикладний сервіс залишається повністю безстанним і масштабованим;
2. Задача забезпечення розподіленого консенсусу виноситься в спеціалізований зовнішній координатор (etcd, Apache ZooKeeper, Consul або Kubernetes Lease API), що працює на окремому виділеному кворумі з 3 або 5 машин;
3. Вибори лідера всередині додатку зводяться до простої клієнтської операції: **захоплення та періодичного поновлення розподіленої лізи (Lease)**.

Глибокий історичний шлях від перших локальних алгоритмів виборів до сучасних хмарних ліз розкрито в історичному нарисі: [Від алгоритму хулігана до хмарних ліз: еволюція виборів лідера](book:programming/distributed-systems/leader-election/hist-election-algorithms.md).

## 2. Анатомія лізи: три константи життєвого циклу

**Ліза (оренда прав, від англ. *lease* / давньофр. *laissier* — залишати, здавати в оренду)** — це механізм розподіленого блокування, який надає вузлу монопольне право володіння ресурсом на строго визначений, обмежений інтервал часу.

На відміну від класичних м'ютексів, де блокування тримається до явного виклику `unlock()`, ліза володіє властивістю автоматичного згасання (Time-To-Live, TTL). Якщо вузол-лідер раптово згорить або втратить живлення, ліза автоматично спливе в координаторі, дозволяючи іншим вузлам перехопити керування без виникнення вічного дедлоку.

Життєвий цикл лідерства тримається на трьох узгоджених часових константах:

```
[Початок лізи] ──────────────── TTL = 15 с ────────────────> [Спливання лізи]
      │                                                              │
      ├───── T_renew = 5 с ─────> [Keep-Alive 1]                     │
      │                                                              │
      ├──────────────── T_renew = 10 с ────────────> [Keep-Alive 2]  │
      │                                                              │
      └──────────────── T_deadline = 10 с ─────────> [ВТРАТА ЛІДЕРСТВА!]
                                                     (самоскидання)
```

1. **`LeaseDuration` (Час життя лізи / TTL):** Базовий інтервал дії оренди в координаторі (типово 10–15 секунд).
2. **`RenewDeadline` (Інтервал оновлення / Keep-Alive):** Періодичність, із якою лідер надсилає повідомлення-серцебиття координатору для продовження лізи. Золоте правило розподілених систем:
   ```
   T_renew ≤ LeaseDuration ÷ 3
   ```
   Якщо час життя лізи становить 15 секунд, поновлення має надсилатися кожні 5 секунд. Це надає лідеру щонайменше дві спроби повторного надсилання запиту у разі поодиноких втрат мережевих пакетів або спайків затримки.
3. **`RetryPeriod` (Період опитування кандидатів):** Інтервал, з яким стендбай-вузли намагаються перехопити лізу у разі її звільнення (типово 2–3 секунди).

### Математика затримки виявлення відмови (Failover Latency)
Повний час, необхідний системі для передачі лідерства новому вузлу після раптового падіння активного лідера, визначається формулою:
```
T_failover = LeaseDuration + RetryPeriod + 2·RTT
```
де `RTT` (Round-Trip Time) — мережева затримка запиту до координатора. Якщо `LeaseDuration = 15` с, а `RetryPeriod = 2` с, кластер гарантовано переобере лідера за 17 секунд. Зменшення `LeaseDuration` прискорює реакцію на відмови, але пропорційно збільшує навантаження на координатор частими запитами `Keep-Alive`.

### Вимога монотонного годинника
Будь-які таймери очікування та дедлайни всередині лідера повинні вимірюватися виключно за допомогою **монотонного годинника** (`CLOCK_MONOTONIC` у POSIX, `std::chrono::steady_clock` у C++, `time.monotonic()` у Python). Настінний системний час (`CLOCK_REALTIME`) синхронізується через NTP і може стрибати назад або вперед. Якщо NTP-сервер скоригує час на 10 секунд назад, настінний таймер вважатиме, що ліза ще діє вічно, хоча координатор уже давно передав її іншому вузлу. Детально цю фундаментальну пастку розібрано у статті [Монотонний проти настінного часу](book:programming/monotonic-vs-wall-time).

## 3. Пастка паузи пам'яті та аномалія зомбі-лідера

Незважаючи на простоту концепції ліз, використання ліз самих по собі **не гарантує** взаємного виключення (Safety) у реальних розподілених системах. Причиною цього є так звана **проблема паузи виконання (The Pause Problem)**.

Уявимо типовий виробничий сценарій:
1. Вузол 1 успішно захоплює лізу в координаторі на 10 секунд і стає лідером.
2. Вузол 1 готується виконати фінансову транзакцію: списує 10 000 доларів з рахунку клієнта в базі даних.
3. Одразу після формування запиту, але **до** його відправки мережею у сокет, віртуальна машина Вузла 1 зазнає глибокої паузи збирання сміття (Garbage Collection Stop-The-World), гіпервізорного заморожування (VM Live Migration Freeze) або масивного свопінгу пам'яті тривалістю 15 секунд.
4. Поки Вузол 1 «спить», на його процесорі не виконується жоден рядок коду. Таймери стоять, Keep-Alive не надсилається.
5. На 10-й секунді координатор фіксує таймаут лізи Вузла 1, анулює її та реєструє нову лізу для Вузла 2.
6. Вузол 2 стає легітимним лідером і записує до бази даних новий баланс рахунку.
7. На 15-й секунді Вузол 1 прокидається від GC-паузи. З точки зору локального коду Вузла 1, він щойно перевірив свій статус лідера. Він не знає, що пройшло 15 секунд реального часу.
8. Вузол 1 відправляє сформований 15 секунд тому запит у базу даних.

У результаті в системі одночасно виконують модифікації **два лідери**: чинний лідер (Вузол 2) та старий «зомбі-лідер» (Вузол 1). Це спричиняє класичне розщеплення мозку (Split-Brain) та невідновне руйнування даних.

## 4. Протокол фенсингових токенів (Fencing Tokens)

Неможливо гарантувати, що процес не зависне після перевірки статусу лідера. Тому єдиний математично надійний спосіб захисту від зомбі-лідерів — це перенесення фінальної валідації на рівень **цільового сховища даних (Storage Layer)** за допомогою **фенсингових токенів (Fencing Tokens / Generation Numbers; від давньоангл. *tācen* — знак, свідчення)**.

Механізм працює за таким протоколом:
1. Щоразу, коли координатор видає нову лізу або переобирає лідера, він генерує строго **монотонно зростаючий числовий лічильник** — номер епохи `fencing_token` (наприклад, `e = 101`, `e = 102`, `e = 103`).
2. Координатор повертає цей токен новообраному лідеру разом із підтвердженням лізи.
3. Лідер зобов'язаний додавати свій поточний номер токена до **кожного** мережевого запиту на запис чи зміну стану, що надсилається до бази даних, файлового сховища або черги повідомлень.
4. Цільове сховище зберігає найбільший номер токена, який воно коли-небудь бачило (`last_fencing_token`).
5. При отриманні запиту сховище виконує атомарну умовну перевірку:
   ```
   ЯКЩО запит.token ≥ last_fencing_token:
       last_fencing_token = запит.token
       ВИКОНАТИ мутацію даних
   ІНАКШЕ:
       ВІДХИЛИТИ запит з помилкою «Stale Fencing Token»
   ```

Коли Вузол 1 прокидається після 15-секундної GC-паузи і шле запис із токеном `e = 101`, база даних бачить, що вона вже успішно прийняла запис від Вузла 2 з токеном `e = 102`. Оскільки `101 < 102`, запит зомбі-лідера негайно відхиляється. Дані залишаються неушкодженими.

> 🔧 **Навіщо це.** Без фенсингових токенів жодна система на лізах (включно з Kubernetes або etcd) не здатна захистити базу даних від подвійного запису при GC-паузах чи мережевих флапах. Ліза гарантує лише те, що кластер обере нового лідера (Liveness), але не захищає сховище від запізнілих пакетів старого лідера. Тільки фенсинговий токен гарантує сувору безпеку даних (Safety).

## 5. Дискусія Клеппмана — Санфіліппо: межі Redlock та алгоритмів без токенів

У 2016 році відомий дослідник розподілених систем **Мартін Клеппман** (*Martin Kleppmann*, автор книги *«Designing Data-Intensive Applications»*) опублікував аналітичну статтю *«How to do distributed locking»*, де піддав нищівній критиці алгоритм Redlock у Redis.

Автор Redis **Сальваторе Санфіліппо** (*Salvatore Sanfilippo*) стверджував, що за наявності кворуму з 5 незалежних вузлів Redis та перевірки часу за монотонним годинником алгоритм Redlock гарантує взаємне виключення без потреби у зовнішніх токенах.

Клеппман довів хибність цієї тези за допомогою двох фактів:
1. **Асинхронна мережа та затримки виконання:** Навіть якщо клієнт успішно захопив замок у 3 з 5 вузлів Redis за 5 мілісекунд, жоден алгоритм не може гарантувати, що клієнт не зависне на 20 секунд одразу після захоплення блокування.
2. **Неможливість безпеки без підтримки сховища:** Будь-який розподілений замок, який не повертає монотонний інкрементний токен для перевірки в цільовому сховищі, є придатним лише для оптимізації ефективності (Efficiency Locks — наприклад, щоб два воркери не рахували один і той самий кеш двічі), але **абсолютно непридатним для забезпечення коректності та збереження цілісності даних (Correctness Locks)**.

Ця дискусія остаточно закріпила в індустрії аксіому: вибори лідера та розподілені блокування для критичних даних мають спиратися або на кворумні транзакційні координатори з монотонними ревізіями, або на строгі фенсингові токени.

## 6. Координаційні бекенди та прикладні рецепти

Розглянемо, як патерн виборів лідера реалізується на практиці в найпоширеніших координаційних системах індустрії.

### 1. Apache ZooKeeper: Ефемерні послідовні вузли та ланцюгове спостереження

Найвідоміший класичний патерн виборів лідера був розроблений для Apache ZooKeeper.

#### Наївний підхід та проблема «Шторму пробудження» (Thundering Herd)
У наївному варіанті всі `N` кандидатів намагаються створити один спільний ефемерний znode: `/app/leader`. Перемагає той, чий запит прийшов першим. Решта `N - 1` вузлів встановлюють тригер спостереження (`Watch`) на видалення цього єдиного вузла.
Коли лідер падає, ZooKeeper надсилає сповіщення одночасно всім `N - 1` клієнтам. Усі `N - 1` вузлів миттєво прокидаються і шлють паралельні запити на створення `/app/leader`. При великих кластерах (сотні воркерів) це викликає сплеск із `O(N)` мережевих сповіщень та `O(N²)` спроб запису, що здатне перевантажити кластер координатора.

#### Оптимальний ланцюговий рецепт ZooKeeper
Для усунення шторму пробудження застосовують **ефемерні послідовні вузли (Ephemeral Sequential Nodes)**:
1. Кожен кандидат створює ефемерний вузол із послідовним автоінкрементним номером у спільній директорії: `/election/guid-n_0000000001`, `/election/guid-n_0000000002` тощо.
2. Вузол вичитує список усіх дітей у директорії `/election`.
3. **Лідером стає вузол із найменшим порядковим номером.**
4. Якщо номер вузла не є найменшим, він знаходить вузол із **безпосередньо попереднім номером** і встановлює `Watch` **тільки на нього**.
   - Вузол `n_2` спостерігає лише за `n_1`.
   - Вузол `n_3` спостерігає лише за `n_2`.
   - Вузол `n_k` спостерігає лише за `n_{k-1}`.

![Порівняння наївного спостереження зі штормом пробудження та ланцюгового спостереження послідовних вузлів у ZooKeeper](/book/programming/distributed-systems/leader-election/img/zookeeper-watcher-chain.svg)
*Порівняння архітектур спостереження в ZooKeeper: шторм пробудження при наївному підході проти ланцюгового спостереження за попередником*

Коли лідер (`n_1`) падає, його ефемерний вузол зникає. Сповіщення отримує **рівно один вузол** — `n_2`. Він перевіряє директорію, бачить, що його номер тепер найменший, і стає новим лідером. Складність передачі лідерства становить строго `O(1)`, що забезпечує ідеальне масштабування на тисячі машин.

### 2. etcd: Транзакції Compare-And-Swap та gRPC Keep-Alive

У сховищі etcd v3 вибори лідера будуються на поєднанні двох примітивів: **об'єкта лізи (`Lease`)** та **атомарних транзакцій (`Txn`)**.

Клієнт виконує три послідовні кроки:
1. **Створення лізи з TTL:** Клієнт викликає `LeaseGrant(TTL = 10s)`, отримуючи числовий ідентифікатор `LeaseID`.
2. **Атомарне захоплення через `Txn`:** Клієнт надсилає транзакцію Compare-And-Swap:
   ```
   ЯКЩО CreateRevision("/service/leader") == 0:
       ПОКЛАСТИ key="/service/leader", value="node-42", lease=LeaseID
   ІНАКШЕ:
       ПРОЧИТАТИ key="/service/leader"
   ```
   Якщо ключ ще не існував (`CreateRevision == 0`), etcd атомарно записує ключ і прив'язує його до лізи клієнта. Вузол стає лідером. Номер модифікації ключа (`ModRevision`) стає його монотонним фенсинговим токеном.
3. **Підтримка серцебиття через gRPC-стрим:** Лідер відкриває двоспрямований потік `LeaseKeepAlive`, куди періодично надсилає `LeaseID`. etcd автоматично скидає таймер лізи на початкові 10 секунд.
4. **Спостереження за зміною:** Усі претенденти встановлюють `Watch("/service/leader")`. Щойно лідер падає і ліза згасає, etcd видаляє ключ і надсилає подію `DELETE`, спонукаючи претендентів повторити транзакцію.

### 3. Kubernetes Lease API (`coordination.k8s.io/v1`)

Управляючі компоненти Kubernetes (`kube-controller-manager`, `kube-scheduler`, оператори баз даних) використовують вбудований ресурс `Lease`.

Маніфест об'єкта лізи в etcd Kubernetes виглядає так:
```yaml
apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: billing-controller-leader
  namespace: production
spec:
  holderIdentity: "billing-pod-7b9f8d6c-4x2q"
  leaseDurationSeconds: 15
  acquireTime: "2026-08-20T03:00:00.000000Z"
  renewTime: "2026-08-20T03:00:10.500000Z"
  leaseTransitions: 3
```

- `holderIdentity`: ідентифікатор пода, який зараз утримує лідерство;
- `renewTime`: мітка часу останнього успішного поновлення лідером;
- `leaseTransitions`: монотонний лічильник кількості змін лідерів (готовий фенсинговий токен епохи);
- Оновлення лізи виконується через HTTP `PUT` / `PATCH` запити з оптимістичним контролем версій за полем `metadata.resourceVersion`. Якщо два поди спробують оновити лізу одночасно, API-сервер пропустить запит першого, а другому поверне помилку `409 Conflict`.

Бібліотека Go `k8s.io/client-go/tools/leaderelection` стандартизувала цей підхід, надаючи розробникам уніфікований інтерфейс зворотних викликів:

```go
leaderelection.RunOrDie(ctx, leaderelection.LeaderElectionConfig{
    Lock:          leaseLock,
    LeaseDuration: 15 * time.Second,
    RenewDeadline: 10 * time.Second,
    RetryPeriod:   2 * time.Second,
    Callbacks: leaderelection.LeaderCallbacks{
        OnStartedLeading: func(ctx context.Context) {
            // Запуск монопольних горутин (білінг, шедулер)
            runBillingWorker(ctx)
        },
        OnStoppedLeading: func() {
            // Аварійне скасування: процес втратив лідерство
            log.Fatalf("Втрачено лідерство! Зупинка процесу.")
        },
        OnNewLeader: func(identity string) {
            log.Printf("Обрано нового лідера: %s", identity)
        },
    },
})
```

### 4. HashiCorp Consul: Сесії та блокування з параметром Lock-Delay

У системі HashiCorp Consul вибори лідера реалізуються через комбінацію **сесій (Sessions)** та K/V сховища.

Клієнт створює сесію із заданим TTL:
```json
{
  "Session": {
    "Name": "billing-leader-session",
    "TTL": "15s",
    "Behavior": "release",
    "LockDelay": "5s"
  }
}
```
Після створення сесії клієнт намагається записати ключ із параметром `?acquire=<session_id>`. Якщо ключ вільний, Consul прив'язує його до сесії і повертає `true`.

**Унікальна перевага Consul — параметр `LockDelay`:**
Коли лідер падає і його сесія згасає, Consul блокує повторне захоплення цього ключа будь-яким іншим вузлом на додаткові 5 секунд (`LockDelay = 5s`). Цей інтервал спеціально спроєктовано для того, щоб старий лідер, якщо він завис у короткочасній GC-паузі або мережевому спайку, встиг виявити втрату власної сесії та коректно зупинити виконання активних фонових задач до того, як новий лідер розпочне роботу.

Повний робочий код клієнта виборів лідера мовами C та C++, включаючи обробку потоків, атомарні бар'єри та валідацію токенів у сховищі, наведено у практичному проєкті: [Реалізація виборів лідера на базі ліз і фенсингових токенів](book:programming/distributed-systems/leader-election/proj-lease-election.md).

## 7. Скінченний автомат та контракт життєвого циклу

Щоб прикладний сервіс працював стабільно, він повинен чітко розділяти свій стан на три фази життєвого циклу:

```
[ Ініціалізація ]
       │
       ▼
┌──────────────┐   Успіх CAS    ┌──────────────┐   Таймаут TTL / Помилка KeepAlive   ┌──────────────┐
│   STANDBY    │ ─────────────> │ LEADER ACTIVE│ ──────────────────────────────────> │ LEADER LOST  │
│ (Кандидат)   │ <───────────── │ (Монополія)  │                                     │ (Скасування) │
└──────────────┘  Штатний вихід └──────────────┘                                     └──────┬───────┘
       ▲          (StepDown)                                                                │
       │                                                                                    │
       └──────────────────────── Дренаж ресурсів завершено ─────────────────────────────────┘
```

### 1. Вхід у лідерство (`OnStartedLeading`)
Коли клієнт отримує підтвердження лізи та номер токена `e`:
1. Створюється кореневий контекст виконання з підтримкою скасування (`CancellationToken` / `context.Context`);
2. Ініціалізуються монопольні підсистеми (відкриваються з'єднання, підключаються черги подій);
3. Запускаються робочі фонові потоки. Усі виклики до зовнішніх баз даних передають токен `e`.

### 2. Втрата лідерства (`OnStoppedLeading`)
Якщо потік оновлення лізи зафіксував мережевий збій або спливання дедлайну:
1. Клієнт **негайно** переводить прапорець скасування в стан `cancelled = true`;
2. Робочі потоки повинні негайно припинити виконання нових ітерацій бізнес-логіки;
3. Встановлюється жорсткий захисний ліміт часу (Hard Drain Timeout, наприклад `LeaseDuration / 3` = 5 с) на коректне закриття з'єднань і завершення активних потоків.
4. Якщо потоки не зупинилися впродовж захисного ліміту, процес зобов'язаний виконати самознищення (`abort()` або `SIGKILL`), щоб унеможливити роботу зомбі-воркера.

### 3. Штатне складання повноважень (Graceful Resign)
Під час планового оновлення сервісу (SIGTERM при деплої) чинний лідер не повинен чекати 15 секунд, поки його ліза згасне за таймаутом.
Він зупиняє фонові задачі, викликає команду видалення лізи в координаторі (`Release / Resign`) і закриває процес. Новий лідер обирається за лічені мілісекунди, забезпечуючи нульовий час простою (Zero Downtime Failover).

## 8. Вибори лідера в розподіленій потоковій обробці

Патерн виборів лідера знаходить специфічне застосування в сучасних розподілених рушіях обробки потоків (Stream Processing):

### 1. Apache Flink: Висока доступність JobManager (High Availability)
У кластері Apache Flink вузол `JobManager` координує розподіл обчислювальних графів між сотнями `TaskManager`, ініціює створення контрольних точок (Checkpoints) та відновлює стан після збоїв.
Для усунення єдиної точки відмови запускають кілька реплік `JobManager`, кожна з яких змагається за лідерство через ZooKeeper або Kubernetes Lease.
Усі `TaskManager` використовують компонент `LeaderRetrievalService`, який підписується на зміну лідера. Щойно новий `JobManager` перемагає у виборах, він завантажує останню успішну контрольну точку з персистентного сховища (Amazon S3 / Ceph), надсилає свій новий ідентифікатор лідера та фенсинговий токен усім воркерам, і відновлює обчислення потоку без втрати жодної події (гарантія Exactly-Once).

### 2. Apache Kafka: Лідер групи споживачів (Consumer Group Leader)
У клієнтських групах споживачів Kafka брокер-координатор (`GroupCoordinator`) не розподіляє партиції топіків між воркерами самостійно. Натомість він обирає одного зі споживачів лідером групи (`Consumer Group Leader`).
- Лідер групи отримує від координатора список усіх активних підключених споживачів.
- Лідер виконує алгоритм розподілу партицій (Partition Assignor — наприклад, `CooperativeStickyAssignor`).
- Лідер відправляє сформовану карту призначень назад координатору, який розсилає її іншим учасникам групи через відповіді `SyncGroup`.
Це розвантажує брокери Kafka від складної бізнес-логіки розподілу і дозволяє клієнтам оновлювати стратегії балансування без переконфігурації серверів брокера.

## 9. Виробничі пастки та аномалії

Розглянемо найтиповіші помилки реалізації виборів лідера у високонавантажених системах:

### 1. Флапінг лідерства (Leader Flapping / Thrashing)
Якщо в мережі виникають періодичні короткочасні сплески затримок (Jitter), лідер може пропустити один Keep-Alive, втратити лізу і передати її Вузлу 2. За 2 секунди мережа відновлюється, Вузол 1 знову перехоплює лізу, змушуючи Вузол 2 скинути задачі.
Постійне перемикання ролей паралізує систему: фонові задачі не встигають виконатися, ресурси витрачаються на постійну ініціалізацію та дренаж з'єднань.

**Як запобігти:**
- Встановлювати мінімальний час утримання лідерства (Hold-off time);
- Застосовувати експоненційне відтермінування (Backoff) перед повторною спробою захоплення лізи вузлом, який щойно її втратив;
- Додавати випадкове тремтіння (Jitter, `±20%`) до інтервалів `RetryPeriod`.

### 2. Асиметричне мережеве розділення (Asymmetric Network Partition)
Вузол-лідер може втратити зв'язок із кластером etcd, але зберігати ідеальне підключення до клієнтів та основної бази даних PostgreSQL.
Координатор вважатиме лідера мертвим і обере нового лідера. Якщо старий лідер не перевіряє статус своєї лізи перед кожним зверненням до бази даних, виникає паралельний запис.
**Єдиний порятунок:** обов'язкова перевірка фенсингового токена в базі даних (`UPDATE ... WHERE token >= last_seen_token`).

### 3. Зависання напіввідкритих сокетів (TCP Half-Open)
Якщо мережевий комутатор скинув стан з'єднання без відправки пакетів `TCP RST` або `FIN`, сокет лідера може залишатися відкритим протягом 15–20 хвилин (стандартний таймаут ядра Linux для відправки `keepalive`). Лідер вважатиме, що запит на поновлення надіслано, і продовжуватиме виконувати задачі.
**Як запобігти:** обов'язкове налаштування сокетних опцій `TCP_USER_TIMEOUT` на рівні операційної системи та жорсткі клієнтські таймаути запитів, що не перевищують `T_renew`.

### 4. Географічно розподілені кластери та затримки WAN (Multi-Region Traps)
Якщо координаційний кластер (наприклад, etcd або Consul) розгорнуто в трьох географічно віддалених регіонах (Франкфурт, Вірджинія, Сінгапур), мережева затримка між регіонами (RTT ~80–180 мс) суттєво впливає на стабільність ліз:
- При надто короткому `TTL` (наприклад, 3 секунди) будь-який тимчасовий сплеск затримки трансатлантичного оптичного каналу призведе до помилкового розриву зв'язку та небажаного переобрання лідера.
- У крос-регіональних архітектурах тривалість лізи `TTL` збільшують до 30–60 секунд, а консенсусний кворум координатора намагаються утримувати в межах однієї метрополітарної зони (Availability Zones одного регіону) із затримкою RTT < 2 мс.

## 10. Еволюція в інфраструктурі: уроки Apache Kafka та Elasticsearch

Інфраструктурні платформи пройшли довгу еволюцію від зовнішніх виборів лідера до оптимізованих внутрішніх протоколів:

### 1. Apache Kafka: від ZkUtils до KRaft (KIP-500)
У ранніх версіях Kafka вибори контролера кластера (Controller) виконувалися через створення ефемерного вузла `/controller` у ZooKeeper.
При масштабуванні кластерів до сотень брокерів і мільйонів розділів (partitions) передача лідерства контролера займала хвилини: новообраний контролер мусив перечитати весь стан метаданих із ZooKeeper.
У 2021 році Kafka впровадила архітектуру **KRaft (Kafka Raft Metadata Mode)**: вибори контролера та реплікація метаданих були перенесені на власний кворум брокерів-контролерів із реплікованим журналом подій. Час передачі лідерства скоротився з хвилин до кількох мілісекунд.

### 2. Elasticsearch: від Zen Discovery до детерміністичного консенсусу
До версії 7.0 Elasticsearch використовував власний модуль виборів майстер-вузла — Zen Discovery. Адміністратори мусили вручну задавати конфігураційний параметр `discovery.zen.minimum_master_nodes = (N / 2) + 1`. Якщо адміністратор помилявся у розрахунку або забував оновити параметр при масштабуванні кластера з 3 до 5 машин, мережеве розділення миттєво призводило до вибору двох майстрів і розколу індексів.
У версії 7.0 Elasticsearch повністю переписав координацію, запровадивши алгоритм консенсусу на основі Raft із безпечним автоматичним визначенням кворуму.

## 11. Чекліст проектування виборів лідера

| Критерій | Наївний / Небезпечний підхід | Промисловий надійний стандарт |
| :--- | :--- | :--- |
| **Реалізація консенсусу** | Власний протокол виборів всередині мікросервісу | Делегування координатору (etcd, ZooKeeper, K8s Lease) |
| **Вимірювання дедлайнів** | Настінний системний час (`CLOCK_REALTIME`) | Строго монотонний годинник (`CLOCK_MONOTONIC`) |
| **Інтервал серцебиття** | `T_renew = TTL / 2` (одна спроба) | `T_renew ≤ TTL / 3` (щонайменше 2–3 спроби повтору) |
| **Захист від GC-пауз** | Припущення, що ліза ще діє | Монотонні фенсингові токени (Fencing Tokens / Epochs) |
| **Валідація у сховищі** | Безумовний `UPDATE / INSERT` | Атомарна перевірка `WHERE token >= last_token` |
| **Зупинка воркерів** | `pthread_cancel` / примусовий kill | Кооперативне скасування (`stop_token`) + Hard Drain Timeout |
| **Штатне завершення** | Очікування спливання TTL лізи | Явний виклик `Resign()` для миттєвого failover |

Вибори лідера перетворюють групу незалежних, динамічних безстанних контейнерів на злагоджену відмовостійку систему: рутинні операції масштабуються паралельно, а критичні монопольні процедури виконуються строго одним активним вузлом під надійним захистом розподілених ліз та фенсингових токенів.
