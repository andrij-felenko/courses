# 📋 Довідник конфігурацій та параметрів захисту від гримучої отари

Уніфікований довідник системних параметрів, налаштувань ядра операційної системи, шлюзів Envoy і Nginx, а також клієнтських інтерфейсів керування повторними спробами для запобігання штормам пробудження та перепідключення.

## Системні параметри ядра Linux (`sysctl` та сокети)

Мережевий стек ядра Linux містить дві послідовні черги для кожного слухаючого TCP-сокета: чергу напіввідкритих з'єднань (SYN Queue) та чергу повністю встановлених з'єднань (Accept Queue). Під час шторму перепідключення правильне налаштування розмірів цих черг та реакції ядра на переповнення визначає, чи зможе сервер витримати навантаження без переривання роботи.

| Параметр / Опція | Значення за замовчуванням | Рекомендоване для High-Load | Опис механізму |
| :--- | :--- | :--- | :--- |
| `net.core.somaxconn` | `128` (або `4096`) | `65535` | Максимальна довжина черги повністю встановлених з'єднань (`accept_queue`). Запобігає відкиданню клієнтів під час сплесків. |
| `net.ipv4.tcp_max_syn_backlog` | `1024` | `65535` | Максимальна кількість напіввідкритих з'єднань (очікують завершення SYN-ACK). |
| `net.ipv4.tcp_syncookies` | `1` | `1` | Увімкнення криптографічних SYN-куків при переповненні черги, що захищає пам'ять ядра від вичерпання. |
| `net.ipv4.tcp_abort_on_overflow` | `0` | `0` | При переповненні черги ядро відкидає SYN (клієнт повторить спробу пізніше), а не надсилає миттєвий TCP RST. |
| `net.ipv4.ip_local_port_range` | `32768 60999` | `10240 65535` | Розширення діапазону ефемерних портів для запобігання вичерпанню портів проксі під час шторму з'єднань. |
| `net.ipv4.tcp_tw_reuse` | `2` | `1` | Дозволяє безпечно перевикористовувати сокети у стані `TIME_WAIT` для нових вихідних з'єднань до бекендів. |
| `net.ipv4.tcp_fin_timeout` | `60` | `15` | Скорочення часу очікування остаточного закриття сокета, що прискорює звільнення файлових дескрипторів. |
| `SO_REUSEPORT` | `0` (вимкнено) | `1` (увімкнено) | Дозволяє кільком процесам слухати один TCP-порт. Ядро шардує черги за хешем 4-кортежу. |
| `EPOLLEXCLUSIVE` | Прапорець вимкнено | Прапорець додано до `ev.events` | Гарантує, що при надходженні події прокидається строго один воркер у `epoll_wait()`. |

### Механізм поведінки черг ядра при переповненні
Коли на сервер накочується хвиля з мільйона TCP SYN пакетів:
1. Якщо черга `tcp_max_syn_backlog` переповнюється, ядро за увімкненого параметра `tcp_syncookies = 1` перестає виділяти в пам'яті структуру стану `struct inet_request_sock`. Замість цього початковий порядковий номер TCP (ISN) у пакеті SYN-ACK формується як криптографічний хеш від 4-кортежу, часового штампа та максимального розміру сегмента (MSS).
2. Коли клієнт повертає фінальний ACK, ядро валідує хеш і намагається перенести з'єднання до черги `accept_queue`.
3. Якщо черга `accept_queue` заповнена до ліміту `somaxconn`, значення параметра `tcp_abort_on_overflow = 0` примушує ядро тихо проігнорувати вхідний ACK. Клієнт вважає з'єднання встановленим і надсилає перші дані, які сервер не приймає, змушуючи клієнтський стек TCP виконати повторну передачу з експоненційним затриманням. Якщо ж помилково встановити `tcp_abort_on_overflow = 1`, ядро надішле клієнту пакет `TCP RST`, що змусить прикладний код клієнта негайно знову піти на штурм системи.

## Системні ліміти дескрипторів та процесів (Systemd та cgroups)

Під час масових сплесків з'єднань високонавантажений сервіс може миттєво впертися в ліміти операційної системи на кількість відкритих файлів (`file-max`) або процесів. Налаштування юніта Systemd запобігає аварійному завершенню демонів:

```ini
# /etc/systemd/system/gateway.service.d/limits.conf
[Service]
LimitNOFILE=1048576       # Максимальна кількість відкритих сокетів/дескрипторів
LimitNPROC=512000        # Максимальна кількість активних потоків ядра
TasksMax=infinity        # Зняття обмеження cgroup на кількість задач
```

Ці параметри гарантують, що при надходженні десятків тисяч паралельних підключень процес не отримає системну помилку `EMFILE` («Too many open files») або `EAGAIN` при створенні нового робочого потоку.

## Конфігурація шлюзу Envoy (Edge Admission & Jitter)

У розподілених архітектурах проксі Envoy виступає вхідним бар'єром (Edge Ingress), який повинен десинхронізувати трафік між сервісами та захищати внутрішні мікросервіси від сплесків.

```yaml
# Envoy Route Configuration with Herd-Proof Retry Policy
routes:
  - match:
      prefix: "/api/v1/"
    route:
      cluster: backend_service
      timeout: 2.5s
      retry_policy:
        retry_on: "5xx,connect-failure,refused-stream"
        num_retries: 3
        retry_back_off:
          base_interval: 0.25s    # Базовий інтервал t_base = 250 мс
          max_interval: 10.0s     # Верхня стеля T_max = 10 с
        # Envoy використовує алгоритм Full Jitter за замовчуванням
        retry_priority:
          name: envoy.retry_priorities.previous_priorities
          typed_config:
            "@type": type.googleapis.com/envoy.extensions.retry.priority.previous_priorities.v3.PreviousPrioritiesConfig
            update_frequency: 2
        rate_limited_retry_back_off:
          reset_headers:
            - name: "Retry-After"
              format: SECONDS

# Захист шлюзу від шторму відкриття TLS-з'єднань
clusters:
  - name: backend_service
    connect_timeout: 0.5s
    circuit_breakers:
      thresholds:
        - priority: DEFAULT
          max_connections: 10000        # Максимальна кількість відкритих TCP-сокетів
          max_pending_requests: 2000    # Черга запитів до бекенду
          max_requests: 5000            # Активні паралельні RPC-виклики
          max_retries: 1000             # Бюджет повторів: не більше 20% від загалу
```

### Пояснення параметрів захисту Envoy:
- **`retry_back_off.base_interval` та `max_interval`:** Задають границі експоненційного діапазону. За замовчуванням Envoy накладає алгоритм Full Jitter, обираючи затримку рівномірно з інтервалу `[0, min(max_interval, base_interval · 2ᵏ)]`.
- **`circuit_breakers.thresholds.max_retries`:** Задає жорсткий бюджет повторів. Якщо кількість одночасних повторних запитів досягає 1000, усі наступні невдалі запити відкидаються негайно без повторних спроб, запобігаючи перетворенню повторів на лавину.
- **`max_pending_requests`:** Обмежує кількість запитів, які очікують на вільне підключення до бекенду. При перевищенні ліміту Envoy повертає код HTTP 503 з нульовою затримкою.

## Конфігурація Nginx (`SO_REUSEPORT` та захист від сплесків)

Вебсервер Nginx підтримує апаратний шардинг слухаючих сокетів на базі `SO_REUSEPORT` та багаторівневе кешування сесій TLS:

```nginx
# Nginx /etc/nginx/nginx.conf
http {
    # Зона обмеження швидкості встановлення нових з'єднань з однієї IP-адреси
    limit_conn_zone $binary_remote_addr zone=addr_limit:10m;
    limit_req_zone $binary_remote_addr zone=req_limit:10m rate=100r/s;

    server {
        # SO_REUSEPORT створює окремий сокет ядра для кожного робочого процесу worker_process
        listen 443 ssl http2 reuseport backlog=65535;
        server_name api.example.com;

        # TLS Session Resumption для уникнення важких хендшейків під час шторму
        ssl_session_cache shared:SSL:50m;
        ssl_session_timeout 1d;
        ssl_session_tickets on;

        location / {
            # Дозволяє короткочасний сплеск у 50 запитів із затримкою у черзі (nodelay вимикає затримку)
            limit_req zone=req_limit burst=50 nodelay;
            limit_conn addr_limit 20;

            proxy_pass http://backend_pool;
            proxy_connect_timeout 1s;
            proxy_read_timeout 5s;
            
            # Повторні спроби лише для безпечних помилок підключення
            proxy_next_upstream error timeout invalid_header http_503;
            proxy_next_upstream_tries 3;
            proxy_next_upstream_timeout 4s;
        }
    }
}
```

### Пояснення параметрів Nginx:
- **`reuseport backlog=65535`:** Вмикає прапорець `SO_REUSEPORT` на системному сокеті та збільшує розмір черги `listen()`. Nginx автоматично створює окремий дескриптор для кожного `worker_process`, що усуває конкуренцію за accept-мутекс між робочими процесами.
- **`ssl_session_cache shared:SSL:50m` та `ssl_session_tickets on`:** Виділяють спільну зону пам'яті розміром 50 МБ для збереження ідентифікаторів TLS-сесій (дозволяє кешувати близько 200 000 сесій) та вмикають підтримку криптографічних Session Tickets (RFC 5077 / RFC 8446). Це дозволяє клієнтам відновлювати з'єднання без виконання асиметричної криптографії, скорочуючи час обробки на 95%.
- **`limit_req burst=50 nodelay`:** Реалізує алгоритм витікаючого відра (Leaky Bucket). Параметр `burst=50` дозволяє короткочасний сплеск до 50 запитів, а `nodelay` гарантує, що дозволені запити обробляються миттєво, а надлишок скидається з кодом HTTP 429.

## Специфікація конфігурації повторів gRPC (Service Config)

Фреймворк gRPC підтримує декларативне налаштування повторних спроб на рівні сервісної конфігурації каналу (gRPC ServiceConfig у форматі JSON). Це дозволяє централізовано керувати політикою відступання через службу Service Discovery без зміни клієнтського бінарного коду:

```json
{
  "methodConfig": [
    {
      "name": [
        { "service": "order.v1.OrderService" }
      ],
      "retryPolicy": {
        "maxAttempts": 4,
        "initialBackoff": "0.2s",
        "maxBackoff": "10s",
        "backoffMultiplier": 2.0,
        "retryableStatusCodes": [
          "UNAVAILABLE",
          "RESOURCE_EXHAUSTED"
        ]
      }
    }
  ],
  "retryThrottling": {
    "maxTokens": 10,
    "tokenRatio": 0.1
  }
}
```

### Пояснення параметрів gRPC:
- **`retryThrottling.maxTokens` та `tokenRatio`:** Реалізують клієнтський захист від лавинного навантаження. За кожен успішний RPC-виклик клієнт отримує `tokenRatio` токенів (у даному прикладі `0.1`). Кожна невдала спроба списує `1.0` токен. Якщо баланс токенів опускається нижче половини `maxTokens / 2 = 5`, клієнтський канал автоматично вимикає повтори, скидаючи помилку прямо в прикладний код і не створюючи шторму запитів.
- **`retryableStatusCodes`:** Список статусів помилок, для яких дозволено повтор. Повторювати операції дозволено лише для тимчасових мережевих або інфраструктурних помилок (`UNAVAILABLE`, `RESOURCE_EXHAUSTED`), тоді як бізнес-помилки (`INVALID_ARGUMENT`, `NOT_FOUND`) повинні завершуватися негайно.

## Параметри кластерного консенсусу (Raft та etcd)

Для запобігання штормам виборів та колізій лідерства у розподілених сховищах консенсусу (etcd, Consul, Raft) критично важливим є правильне співвідношення між інтервалами серцебиття та діапазоном рандомізації виборів:

```ini
# etcd configuration flags for cluster resilience
ETCD_HEARTBEAT_INTERVAL=100     # Інтервал надсилання серцебиття лідера (100 мс)
ETCD_ELECTION_TIMEOUT=1000       # Базовий таймаут виборів нового лідера (1000 мс)
ETCD_AUTO_COMPACTION_RETENTION=1h # Автоматичне стиснення журналу для зниження навантаження
```

### Правило вибору таймаутів у Raft:
Щоб уникнути ситуації, коли кілька фоловерів одночасно вирішують, що лідер помер, і починають паралельні вибори (розкол голосів, Split Vote), алгоритм Raft призначає кожному вузлу випадковий таймаут очікування `T_election` у діапазоні:

```
T_election ∈ [ElectionTimeout, 2 · ElectionTimeout]
```

Для стабільної роботи має виконуватися фундаментальна нерівність:

```
HeartbeatInterval ≪ ElectionTimeout ≪ MTBF (Mean Time Between Failures)
```

Зазвичай `ElectionTimeout` обирають у межах від 150 мс до 1000 мс, що як мінімум у 5–10 разів перевищує затримку передачі повідомлення у мережі кластера, гарантуючи швидке та безконфліктне обрання єдиного лідера.

## Специфікація клієнтських інтерфейсів та бюджетів повторів

Клієнтські бібліотеки (Finagle, Polly, Resilience4j) використовують формальні контракти для програмного керування повторами та десинхронізацією навантаження:

```protobuf
// Protobuf специфікація параметрів політики стійкості клієнта
syntax = "proto3";

package resilience.v1;

enum JitterStrategy {
  JITTER_STRATEGY_UNSPECIFIED = 0;
  JITTER_STRATEGY_FULL = 1;          // Uniform(0, min(Max, Base * 2^attempt))
  JITTER_STRATEGY_EQUAL = 2;         // Min/2 + Uniform(0, Min/2)
  JITTER_STRATEGY_DECORRELATED = 3;  // Uniform(Base, Prev * 3)
}

message RetryPolicyContract {
  uint32 max_attempts = 1;                     // Максимальна кількість спроб (зазвичай 3..5)
  uint32 initial_backoff_ms = 2;               // Базова пауза (наприклад, 200 мс)
  uint32 max_backoff_ms = 3;                   // Максимальна стеля паузи (наприклад, 15000 мс)
  double backoff_multiplier = 4;               // Множник експоненти (зазвичай 1.5 або 2.0)
  JitterStrategy jitter_strategy = 5;          // Стратегія накладання випадкового шуму
  
  // Клієнтський бюджет повторів (Retry Budget):
  // Клієнт може здійснювати повтор лише якщо частка повторів не перевищує заданий відсоток
  double retry_budget_ratio = 6;               // Наприклад, 0.10 (не більше 10% повторів)
  uint32 retry_budget_min_retries_per_sec = 7; // Мінімальна квота для низького RPS (наприклад, 5)
}
```

Дотримання цих інтерфейсних контрактів та системних параметрів гарантує багаторівневий та узгоджений захист розподіленої архітектури від будь-яких проявів гримучої отари.
