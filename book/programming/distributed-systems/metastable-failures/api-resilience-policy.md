# 📋 Специфікація політик та протоколів захисту від метастабільності

Цей довідник містить формальні специфікації протокольних заголовків, конфігураційні схеми та адміністративні інтерфейси для запобігання виникненню петель позитивного зворотного зв'язку в розподіленій архітектурі.

## 1. Протокольний контракт передачі дедлайнів та метаданих

Для забезпечення наскрізного контролю бюджету часу та запобігання виникненню штормів повторних спроб усі міжсервісні виклики (HTTP/1.1, HTTP/2, gRPC) повинні підтримувати стандартизований набір протокольних метаданих.

Кожен запит, що проходить крізь межу сервісів, супроводжується інформацією про кінцевий час актуальності результату та історію попередніх спроб. Це дозволяє проміжним шлюзам і кінцевим серверам приймати обґрунтоване рішення про доцільність виконання обчислень.

### Специфікація заголовків запиту (Request Headers Contract)

| Заголовок / Метадані | Тип | Опис та формат | Приклад значення |
| :--- | :--- | :--- | :--- |
| `X-Request-Deadline-Ms` | `uint64` | Абсолютний час дедлайну у мілісекундах від початку епохи Unix (UTC). | `1771598400150` |
| `grpc-timeout` | `string` | Відносний таймаут у стандартному форматі gRPC (`[0-9]+[HMSmun]`). | `500m` (500 мілісекунд) |
| `X-Retry-Attempt` | `uint8` | Номер поточної спроби клієнта (0 — первинний запит, 1..N — повтори). | `2` |
| `X-Retry-Reason` | `string` | Причина попереднього збою (`timeout`, `http_503`, `connection_reset`). | `timeout` |
| `X-Origin-Client-ID` | `string` | Ідентифікатор вихідного сервісу для ізоляції квот та перебірок. | `checkout-gateway-prod` |

### Семантика обробки дедлайнів та вимоги до синхронізації годинників

Використання заголовка `X-Request-Deadline-Ms` вимагає дотримання кількох обов'язкових правил:
1. **Синхронізація часу за протоколом NTP:** вузли кластера повинні бути синхронізовані через локальні NTP-сервери (Chrony). Максимально допустиме відхилення системних годинників (Clock Skew) між серверами в межах одного регіону не повинно перевищувати 5 мілісекунд.
2. **Перетворення відносного часу у абсолютний на межі шлюзу:** якщо зовнішній клієнт надсилає запит через публічний API, де неможливо гарантувати синхронізацію часу мобільного пристрою, прикордонний шлюз (API Gateway) зобов'язаний зчитати відносний таймаут клієнта, додати його до свого локального монотонного часу та згенерувати абсолютний заголовок `X-Request-Deadline-Ms` для внутрішньої сервісної мережі.
3. **Поведінка за відсутності заголовка:** якщо заголовок дедлайну відсутній у вхідному запиті, сервер призначає дефолтний консервативний бюджет часу (наприклад, 2 000 мілісекунд), щоб унеможливити безстрокове зависання потоків.

### Специфікація статусних кодів та заголовків скидання навантаження

| HTTP-код | Статус gRPC | Заголовок відповіді | Призначення |
| :--- | :--- | :--- | :--- |
| `429 Too Many Requests` | `RESOURCE_EXHAUSTED` | `Retry-After: 2` | Сигнал клієнту про вичерпання лімітів черги з вимогою затримки перед повтором. |
| `503 Service Unavailable`| `UNAVAILABLE` | `X-Shed-Reason: sojourn_exceeded` | Сигнал негайного скидання через надлишковий час очікування в черзі. |
| `504 Gateway Timeout` | `DEADLINE_EXCEEDED` | `X-Shed-Reason: deadline_expired` | Запит скинуто на вході, оскільки залишковий час менший за мінімальний час обробки. |

## 2. Конфігураційна схема політики бюджету повторів (Retry Budget)

Політика бюджету повторних спроб регулює поведінку клієнтських проксі (Envoy, Linkerd, Istio) або вбудованих бібліотек SDK. Головна мета конфігурації — унеможливити ситуацію, коли через локальні збої сервіс-споживач починає надсилати більше 10% додаткового паразитного трафіку.

```yaml
resilience_policy:
  version: "v1alpha1"
  target_service: "payment-processing-service"
  
  # Політика контролю повторних спроб
  retry_budget:
    enabled: true
    # Частка від успішних запитів, що дозволяється для повторів (0.1 = 10%)
    max_retry_percentage: 10.0
    # Мінімальна гарантована місткість токенів при низькому трафіку
    min_retry_tokens: 100
    # Максимальна ємність кошика для запобігання накопиченню токенів
    max_token_capacity: 1000
    # Тривалість ковзного вікна обліку первинних запитів
    aggregation_window_ms: 10000

  # Параметри експоненційного відступу (Exponential Backoff)
  backoff:
    base_interval_ms: 50
    max_interval_ms: 2000
    multiplier: 2.0
    # Режим додавання випадкового шуму (Full Jitter запобігає резонансу)
    jitter_mode: "FULL_JITTER"
    
  # Список кодів відповідей, для яких дозволено повтор
  retryable_status_codes:
    - 429
    - 503
    - 504
```

### Пояснення поведінки параметрів:
* `max_retry_percentage`: встановлює жорстку верхню межу посилення трафіку. Значення `10.0` гарантує, що коефіцієнт підсилення роботи `A(q)` ніколи не перевищить `1.10`, що робить виникнення метастабільної петлі повторів математично неможливим.
* `max_token_capacity`: обмежує максимальний запас накопичених токенів. Якщо сервіс тривалий час працював стабільно, кошик не повинен накопичити мільйони токенів, які могли б спричинити короткочасний шторм у момент першого падіння бекенду.
* `jitter_mode: "FULL_JITTER"`: розраховує фактичний час сну клієнта як випадкове число, рівномірно розподілене в інтервалі від нуля до поточного значення експоненційного відступу `random_between(0, base · multiplier^attempt)`. Це повністю руйнує фазову синхронізацію клієнтів.

## 3. Схема активного скидання навантаження та контролю черг (CoDel Shedding)

Конфігурація вхідного шлюзу для відстеження часу перебування запитів у чергах та автоматичного увімкнення екстреного режиму обслуговування.

```yaml
load_shedding_policy:
  version: "v1alpha1"
  service_port: 8080

  # Контролер часу перебування в черзі (Controlled Delay)
  queue_sojourn_controller:
    enabled: true
    # Цільовий допустимий час очікування в черзі
    target_sojourn_ms: 25
    # Інтервал аналізу мінімальної затримки
    interval_ms: 100
    # Поріг тривалості перевантаження для перемикання в аварійний режим
    overload_threshold_ms: 200

  # Стратегія дисципліни черги під час деградації
  overload_strategy:
    # Перемикання з FIFO на LIFO при перевищенні порогу затримки
    mode: "DYNAMIC_LIFO"
    # Автоматичне скидання запитів, якщо залишок дедлайну менший за час виконання
    drop_unviable_deadlines: true
    # Оцінка мінімального часу виконання бізнес-логіки
    estimated_p50_execution_ms: 15
```

### Семантика станів контролера черги:
1. **Стан «Звичайний» (NORMAL):** мінімальний час перебування в черзі у вікні `interval_ms` менший за `target_sojourn_ms` (25 мс). Обробка виконується за стандартною чесною чергою FIFO.
2. **Стан «Спостереження» (SURVEILLANCE):** мінімальна затримка перевищила цільову позначку. Запускається таймер контролю. Якщо стан триває менше `overload_threshold_ms`, жодні запити не відхиляються.
3. **Стан «Аварійне скидання» (OVERLOAD_DROP):** якщо затримка залишається вищою за 25 мс протягом понад 200 мс, контролер перемикає вибірку завдань на алгоритм LIFO і починає відсікати нежиттєздатні елементи з голови черги, повертаючи помилки HTTP 503 з заголовком `Retry-After`.

## 4. Специфікація захисту від вимивання кешу (Cache Stampede & Singleflight)

Конфігурація дедуплікації запитів до сховища даних при виникненні масових промахів кешу.

```yaml
cache_resilience:
  version: "v1alpha1"
  cache_cluster: "redis-sessions"

  # Захист Singleflight (Request Coalescing)
  request_coalescing:
    enabled: true
    # Максимальний час утримання блокування на один ключ
    lock_timeout_ms: 500
    # Максимальна кількість одночасних запитів, що очікують спільний результат
    max_waiters_per_key: 1000

  # Імовірнісне раннє оновлення (Алгоритм XFetch)
  probabilistic_early_refresh:
    enabled: true
    # Параметр бета: чим вище значення, тим раніше починається фонове оновлення
    beta: 1.5
    # Дельта часу обчислення нового значення (P99 тривалість запиту до БД)
    delta_computation_ms: 45
```

### Механіка алгоритму XFetch:
Під час кожного зчитування значення з кешу клієнт обчислює ймовірнісну умову раннього фонового оновлення:
```
delta_computation · beta · ln(random()) > (TTL_expiration - now())
```
де `random()` — випадкове число від 0 до 1, а `ln` — натуральний логарифм.

Якщо умова виконується, поточний потік асинхронно відправляє запит на оновлення даних у базу, не чекаючи фізичного вичерпання TTL. Це запобігає утворенню прогалин у кеші для гарячих ключів навіть під час інтенсивного навантаження.

## 5. Адміністративний REST/gRPC API протоколу екстреного відновлення

Коли система зазнає метастабільного колапсу, автоматичні алгоритми не можуть повернути її на стабільну гілку. Для ручного або автоматизованого виведення кластера з аварії використовується спеціальний ізольований адміністративний порт (`admin_port: 9090`).

### 1. Екстрене обмеження вхідного трафіку (Emergency Quarantine)

* **Ендпоінт:** `POST /api/v1/admin/resilience/quarantine`
* **Призначення:** Миттєве примусове скидання вхідного потоку до безпечного рівня відновлення `L_rec`.

**Тіло запиту (Request JSON):**
```json
{
  "action": "ENABLE_QUARANTINE",
  "target_service": "payment-api",
  "max_admitted_rps": 2500,
  "drop_reason": "metastable_recovery_protocol",
  "duration_seconds": 300,
  "allowed_client_ids": ["health-checker", "internal-canary"]
}
```

**Відповідь (Response 200 OK):**
```json
{
  "status": "QUARANTINE_ACTIVE",
  "admitted_rps_limit": 2500,
  "previous_inbound_rps": 18500,
  "quarantine_expires_at": "2026-08-20T17:30:00Z"
}
```

### 2. Ступеневе відкриття шлюзів (Slow-Start Ramp-Up)

* **Ендпоінт:** `POST /api/v1/admin/resilience/slow-start`
* **Призначення:** Поступове збільшення пропускної спроможності після спорожнення черг та прогріву кешів.

**Тіло запиту (Request JSON):**
```json
{
  "action": "START_RAMP_UP",
  "initial_rps": 2500,
  "step_rps": 1000,
  "step_interval_seconds": 30,
  "target_rps": 10000,
  "abort_condition": {
    "max_p99_latency_ms": 100,
    "max_error_rate_percentage": 1.0
  }
}
```

**Відповідь (Response 200 OK):**
```json
{
  "status": "RAMP_UP_IN_PROGRESS",
  "current_step": 1,
  "current_limit_rps": 2500,
  "target_limit_rps": 10000,
  "estimated_completion_seconds": 240
}
```

### Порядок виконання операцій черговим інженером (Runbook):
1. **Активація карантину:** надіслати запит `ENABLE_QUARANTINE`, обмеживши трафік до розрахункового `L_rec = C / A_max`.
2. **Моніторинг затримок:** переконатися за метриками Prometheus/Grafana, що час перебування в черзі (`sojourn_time_p99`) опустився нижче 10 мілісекунд, а завантаження процесорів впало нижче 30%.
3. **Запуск ступеневого повернення:** викликати `START_RAMP_UP`. Якщо під час ступеневого збільшення трафіку метрика `max_p99_latency_ms` перевищить 100 мс або частка помилок перевищить 1%, контролер автоматично призупиняє збільшення лімітів і повертається на попередній безпечний крок.

## 6. Метрики та телеметрія спостережуваності (Prometheus & OpenTelemetry)

Для раннього виявлення формування петель позитивного зворотного зв'язку система повинна експортувати спеціалізовані метрики стійкості:

| Назва метрики | Тип | Опис та сигнальне призначення |
| :--- | :--- | :--- |
| `resilience_retry_budget_tokens_available` | Gauge | Поточний залишок токенів повторних спроб у клієнтському пулі. |
| `resilience_retry_requests_rejected_total` | Counter | Кількість повторних викликів, заблокованих через вичерпання бюджету повторів. |
| `resilience_queue_sojourn_time_seconds` | Histogram | Розподіл реального часу перебування запитів у чергах до початку обробки. |
| `resilience_wasted_work_aborted_total` | Counter | Кількість операцій, зупинених через виявлення мертвого клієнтського сокета або дедлайну. |
| `resilience_work_amplification_ratio` | Gauge | Співвідношення сукупного внутрішнього трафіку до первинного зовнішнього (`A = L_total / L_primary`). |

Значення метрики `resilience_work_amplification_ratio > 1.20` протягом 30 секунд свідчить про початок замикання метастабільної петлі та вимагає негайної активації захисних контурів.
