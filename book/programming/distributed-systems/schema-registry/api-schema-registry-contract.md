# 📋 Специфікація кадру Wire Format та REST API реєстру схем

Ця специфікація описує точний двійковий формат кадрування повідомлень у транспортній мережі (англ. *Wire Format*) та повний контракт інтерфейсу REST API реєстру схем для реєстрації, версіонування, перевірки сумісності, управління залежностями та вичитування схем даних.

## 1. Двійковий формат кадрування (Wire Format)

Усі повідомлення, що публікуються в брокери повідомлень (Apache Kafka, Apache Pulsar тощо) із застосуванням реєстру схем, починаються зі стандартизованого 5-байтового службового префікса, за яким слідують двійкові дані корисного навантаження.

### 1.1. Загальна структура кадру для Apache Avro та JSON Schema

```
+----------------+-------------------+--------------------------------------+
| Байт 0         | Байти 1–4         | Байти 5...N                          |
| Magic Byte     | Schema ID         | Serialized Binary Payload            |
| (1 байт, 0x00) | (4 байти, uint32) | (двійкові дані Avro / JSON Schema)   |
+----------------+-------------------+--------------------------------------+
```

* **Байт 0 (Magic Byte):** Фіксоване значення `0x00`. Служить маркером протоколу, що дозволяє клієнтам відрізнити структуровані повідомлення від довільних сирих байтів або повідомлень у застарілих форматах.
* **Байти 1–4 (Schema ID):** 32-бітне беззнакове ціле число в мережевому порядку байтів (англ. *big-endian* / *most significant byte first*). Вказує на глобальний унікальний ідентифікатор схеми в реєстрі, використаний продюсером для серіалізації цього конкретного повідомлення.
* **Байти 5...N (Payload):** Сирий двійковий потік, згенерований серіалізатором (наприклад, бінарний Avro без заголовка контейнера або UTF-8 байти JSON).

### 1.2. Розширення структури для Google Protocol Buffers

Оскільки один `.proto`-файл може містити кілька вкладених повідомлень (`message`), формат кадрування для Protobuf додає між Schema ID та корисним навантаженням масив індексів цільового типу:

```
+----------------+-------------------+---------------------+-------------------------+
| Байт 0         | Байти 1–4         | Змінна довжина      | Залишок байтів          |
| Magic Byte     | Schema ID         | Message Index Array | Protobuf Binary Payload |
| (1 байт, 0x00) | (4 байти, uint32) | (varint довжина +   | (сирі байти protobuf)   |
|                |                   | varint індекси)     |                         |
+----------------+-------------------+---------------------+-------------------------+
```

* **Message Index Array:** Послідовність цілих чисел у кодуванні *ZigZag Varint*.
  * Перший `varint` вказує на кількість рівнів вкладеності (довжину шляху до повідомлення у файлі). Значення `0` означає, що корисне навантаження відповідає першому кореневому повідомленню в `.proto`-файлі.
  * Якщо файл містить кілька типів повідомлень, масив містить порядкові індекси (наприклад, шлях `[0, 2]` вказує на третє повідомлення всередині першого кореневого блоку).

## 2. Стратегії іменування суб'єктів (Subject Naming Strategies)

Реєстр схем групує версії схем у простори імен, які називаються **суб'єктами** (англ. *subjects*). Стратегія визначає, як ім'я топіка та типи подій відображаються в назву суб'єкта:

| Стратегія | Формат назви суб'єкта | Область застосування та правила |
|---|---|---|
| `TopicNameStrategy` (типова) | `<topic>-key`<br>`<topic>-value` | Усі повідомлення в топіку повинні відповідати єдиній схемі, яка еволюціонує в часі. Окремий суб'єкт для ключа повідомлення та окремий для значення. |
| `RecordNameStrategy` | `<fully.qualified.RecordName>` | Дозволяє передавати в один топік події різних типів (наприклад, `com.shop.OrderCreated` та `com.shop.OrderCancelled`). Схема прив'язана до глобального імені структури, незалежно від топіка. |
| `TopicRecordNameStrategy` | `<topic>-<fully.qualified.RecordName>` | Поєднує дві попередні: обмежує схему конкретного типу запису рамками конкретного топіка, запобігаючи перетинанню схем між різними середовищами. |

## 3. Режими сумісності (Compatibility Modes)

Реєстр підтримує 7 конфігурацій валідації сумісності при реєстрації нової версії схеми:

| Режим | Умова перевірки сумісності | Відносно яких версій перевіряється | Хто оновлюється першим |
|---|---|---|---|
| `BACKWARD` | `R(V_new) ← W(V_prev)` | Лише попередня (`V[N-1]`) | Споживачі (Consumers) |
| `BACKWARD_TRANSITIVE` | `∀ i < N: R(V_N) ← W(V_i)` | Усі зареєстровані (`V[1] … V[N-1]`) | Споживачі (Consumers) |
| `FORWARD` | `R(V_prev) ← W(V_new)` | Лише попередня (`V[N-1]`) | Продюсери (Producers) |
| `FORWARD_TRANSITIVE` | `∀ i < N: R(V_i) ← W(V_N)` | Усі зареєстровані (`V[1] … V[N-1]`) | Продюсери (Producers) |
| `FULL` | `R(V_new) ↔ W(V_prev)` | Лише попередня (`V[N-1]`) | Будь-який порядок |
| `FULL_TRANSITIVE` | `∀ i < N: R(V_N) ↔ W(V_i)` | Усі зареєстровані (`V[1] … V[N-1]`) | Будь-який порядок |
| `NONE` | Жодної перевірки | Не перевіряється | Неконтрольований ризик |

## 4. Канонічна нормалізація схем та обчислення відбитків (Fingerprints)

Коли два різні клієнти реєструють ту саму схему, текст файлів JSON може відрізнятися несуттєвими деталями: пробілами, переносами рядків, порядком атрибутів або наявністю коментарів (`doc`).

Щоб запобігти створенню дублікатів схем із різними `Schema ID`, реєстр виконує **канонічну нормалізацію** (англ. *Parsing Canonical Form*):
1. **Видалення несуттєвих атрибутів:** Усі поля документації (`doc`), псевдоніми (`aliases`) та користувацькі метадані відкидаються, оскільки вони не впливають на бінарне кодування.
2. **Лексикографічне сортування ключів:** Усі JSON-атрибути всередині об'єктів упорядковуються за алфавітом (наприклад, `"name"` завжди передує `"type"`).
3. **Очищення пробілів:** Видаляються всі пробільні символи за межами рядкових літералів.
4. **Обчислення цифрового відбитка (Schema Fingerprint):** Від канонічного рядка обчислюється 64-бітний хеш за алгоритмом `CRC-64-AVRO` або 256-бітний `SHA-256`. Якщо отриманий хеш збігається з раніше збереженою схемою, реєстр повертає вже існуючий `id`, не збільшуючи номер версії в суб'єкті.

## 5. Управління міжсхемними залежностями (Schema References)

Сучасні архітектури часто використовують спільні типи даних (наприклад, структуру `com.common.Money` або `com.geo.Coordinates`), які імпортуються в десятки різних подій.

Реєстр схем підтримує механізм посилань (англ. *Schema References*). Замість дублювання визначення типу в кожному файлі, схема продюсера декларує масив `references`:

```json
{
  "schema": "syntax = \"proto3\"; package com.shop; import \"common/money.proto\"; message Order { int64 id = 1; com.common.Money total = 2; }",
  "schemaType": "PROTOBUF",
  "references": [
    {
      "name": "common/money.proto",
      "subject": "common-money-value",
      "version": 3
    }
  ]
}
```

* **`name`:** Шлях або назва файлу, під якою тип імпортується у вихідному коді схеми.
* **`subject`:** Назва суб'єкта в реєстрі, де зберігається контракт цього спільного типу.
* **`version`:** Конкретна зафіксована версія суб'єкта залежності. Реєстр автоматично перевіряє існування зазначеної версії перед реєстрацією головної схеми.

## 6. Специфікація REST API

Усі запити передаються протоколом HTTP/1.1 або HTTP/2. Заголовки запиту повинні містити:
* `Content-Type: application/vnd.schemaregistry.v1+json` (або `application/json`)
* `Accept: application/vnd.schemaregistry.v1+json, application/json`

### 6.1. Реєстрація схеми під суб'єктом

* **Метод та шлях:** `POST /subjects/{subject}/versions`
* **Призначення:** Зареєструвати нову версію схеми для зазначеного суб'єкта. Якщо тотожна схема вже існує в цьому суб'єкті, реєстр повертає її існуючий ідентифікатор без створення нової версії.

#### Тіло запиту (JSON):
```json
{
  "schema": "{\"type\":\"record\",\"name\":\"OrderPlaced\",\"namespace\":\"com.shop\",\"fields\":[{\"name\":\"order_id\",\"type\":\"long\"},{\"name\":\"amount_cents\",\"type\":\"long\"},{\"name\":\"currency\",\"type\":\"string\",\"default\":\"EUR\"}]}",
  "schemaType": "AVRO"
}
```
*(Поле `schemaType` опціональне; за замовчуванням — `"AVRO"`. Інші допустимі значення: `"PROTOBUF"`, `"JSON"`).*

#### Тіло успішної відповіді (`200 OK`):
```json
{
  "id": 42
}
```

---

### 6.2. Отримання схеми за глобальним ідентифікатором

* **Метод та шлях:** `GET /schemas/ids/{id}`
* **Призначення:** Вичитування визначення схеми за 32-бітним числом з заголовка повідомлення. Цей ендпоінт викликається споживачами при першому виявленні нового `Schema ID`.

#### Тіло успішної відповіді (`200 OK`):
```json
{
  "schema": "{\"type\":\"record\",\"name\":\"OrderPlaced\",\"namespace\":\"com.shop\",\"fields\":[{\"name\":\"order_id\",\"type\":\"long\"},{\"name\":\"amount_cents\",\"type\":\"long\"},{\"name\":\"currency\",\"type\":\"string\",\"default\":\"EUR\"}]}",
  "schemaType": "AVRO"
}
```

---

### 6.3. Отримання схеми за версією суб'єкта

* **Метод та шлях:** `GET /subjects/{subject}/versions/{version}`
* **Параметри:** `{version}` може бути цілим числом (наприклад, `1`, `2`) або ключовим словом `latest` для отримання найактуальнішої схеми.

#### Тіло успішної відповіді (`200 OK`):
```json
{
  "subject": "orders.placed-value",
  "id": 42,
  "version": 2,
  "schemaType": "AVRO",
  "schema": "{\"type\":\"record\",\"name\":\"OrderPlaced\",\"namespace\":\"com.shop\",\"fields\":[{\"name\":\"order_id\",\"type\":\"long\"},{\"name\":\"amount_cents\",\"type\":\"long\"},{\"name\":\"currency\",\"type\":\"string\",\"default\":\"EUR\"}]}"
}
```

---

### 6.4. Перевірка сумісності схеми без реєстрації (Dry Run)

* **Метод та шлях:** `POST /compatibility/subjects/{subject}/versions/{version}`
* **Призначення:** Використовується в CI/CD пайплайнах для перевірки, чи не зламає запланований пулл-реквест сумісність із робочою схемою в продакшені. `{version}` зазвичай вказується як `latest`.

#### Тіло запиту (JSON):
```json
{
  "schema": "{\"type\":\"record\",\"name\":\"OrderPlaced\",\"namespace\":\"com.shop\",\"fields\":[{\"name\":\"order_id\",\"type\":\"long\"},{\"name\":\"amount_cents\",\"type\":\"long\"},{\"name\":\"currency\",\"type\":\"string\",\"default\":\"EUR\"},{\"name\":\"loyalty_points\",\"type\":\"int\",\"default\":0}]}",
  "schemaType": "AVRO"
}
```

#### Тіло відповіді при успішній сумісності (`200 OK`):
```json
{
  "is_compatible": true
}
```

#### Тіло відповіді при несумісній зміні (`200 OK`):
```json
{
  "is_compatible": false,
  "messages": [
    "Field 'billing_address' is present in reader schema but missing in writer schema and has no default value"
  ]
}
```

### 6.5. Управління рівнем сумісності

* **Глобальний рівень:**
  * `GET /config` — отримати поточний системний рівень за замовчуванням.
  * `PUT /config` — встановити глобальний рівень для всіх нових суб'єктів.
* **Рівень конкретного суб'єкта:**
  * `GET /config/{subject}` — отримати конфігурацію для суб'єкта.
  * `PUT /config/{subject}` — перевизначити режим сумісності для суб'єкта.
  * `DELETE /config/{subject}` — скинути налаштування суб'єкта до глобального значення.

#### Тіло запиту на зміну конфігурації (`PUT`):
```json
{
  "compatibility": "FULL_TRANSITIVE"
}
```

#### Відповідь (`200 OK`):
```json
{
  "compatibility": "FULL_TRANSITIVE"
}
```

### 6.6. Управління операційними режимами (Mode API)

Реєстр підтримує перемикання операційних режимів на глобальному рівні або для окремих суб'єктів:

* `GET /mode` та `PUT /mode` — глобальний режим.
* `GET /mode/{subject}` та `PUT /mode/{subject}` — режим конкретного суб'єкта.

Допустимі режими роботи:
* `READWRITE` (типовий): Повний доступ. Дозволено читання існуючих схем та реєстрацію нових версій.
* `READONLY`: Режим обслуговування або заморожування змін. Читання схем за ID чи версією дозволене, проте будь-яка спроба `POST` відхиляється помилкою `403 Forbidden`. Використовується під час технічних робіт або під час міграції інфраструктури.
* `IMPORT`: Спеціальний режим для інструментів міграції та реплікації (MirrorMaker 2, Schema Exporter). Дозволяє примусово зареєструвати схему із заздалегідь визначеним історичним `id` та `version`, запобігаючи генерації нових номерів під час перенесення даних між кластерами.

### 6.7. Мультитенентність та простори контекстів (Contexts API)

Для ізоляції схем між різними відділами або середовищами (наприклад, `dev`, `staging`, `prod`) реєстр підтримує простори контекстів. Контекст вказується як префікс шляху:

```http
GET /contexts
POST /contexts/{context}/subjects/{subject}/versions
GET /contexts/{context}/schemas/ids/{id}
```

Кожен контекст діє як повністю ізольований простір імен: схема з `id: 42` у контексті `.staging` не перетинається і не впливає на схему з `id: 42` у контексті `.production`.

---

### 6.8. Експортери схем та міжкластерна реплікація (Schema Exporters)

Для синхронізації схем між регіонами використовується вбудований інтерфейс управління експортерами:

* `POST /exporters` — створити новий синхронізатор схем.
* `GET /exporters/{name}` — перевірити стан та лаг реплікації.
* `PUT /exporters/{name}/pause` та `PUT /exporters/{name}/resume` — призупинення та відновлення синхронізації.

#### Тіло конфігурації експортера (`POST /exporters`):
```json
{
  "name": "eu-to-us-sync",
  "subjects": ["orders.*", "payments.*"],
  "contextType": "CUSTOM",
  "context": ".europe-replica",
  "config": {
    "schema.registry.url": "https://us-east-registry.internal.example.com"
  }
}
```

### 6.9. Повний життєвий цикл та видалення схем

Реєстр схем підтримує двоетапну модель видалення, яка захищає активні топіки від випадкового знищення метаданих:

* **М'яке видалення (Soft Delete):**
  * `DELETE /subjects/{subject}` або `DELETE /subjects/{subject}/versions/{version}` (без параметрів або з `?permanent=false`).
  * Схема позначається як видалена (`deleted: true`), проте її визначення залишається в сховищі, а `Schema ID` не звільняється.
  * Споживачі продовжують читати старі повідомлення за цим ID.
  * Суб'єкт можна відновити або зареєструвати повторно.
* **Жорстке видалення (Hard Delete):**
  * Повторний виклик `DELETE /subjects/{subject}?permanent=true` після виконання м'якого видалення.
  * Визначення схеми фізично вичищається з журналу `_schemas`.
  * Будь-яка спроба прочитати повідомлення з цим ID завершується помилкою `404 Not Found`.

## 7. Специфіка валідації JSON Schema та Protocol Buffers

Окрім Apache Avro, реєстр схем підтримує формати JSON Schema та Protocol Buffers, для яких діють спеціалізовані правила резолюції:

### 7.1. Правила сумісності JSON Schema (Draft 7 / Draft 2020-12)
* **Закриті схеми (`additionalProperties: false`):** Якщо стара схема забороняла додаткові властивості, додавання нового поля у нову схему порушує `FORWARD`-сумісність, оскільки старий валідатор відхилить об'єкт із незнайомим ключем.
* **Масиви обов'язкових полів (`required`):** Додавання нового імені в масив `required` дозволене в режимі `FORWARD`, але суворо заборонене в режимі `BACKWARD`, якщо старі повідомлення не містили цього ключа.
* **Обмеження числових діапазонів (`minimum`, `maximum`):** Звуження діапазону (наприклад, зміна `minimum: 0` на `minimum: 100`) порушує `BACKWARD`-сумісність, оскільки старі повідомлення зі значенням `50` стануть невалідними для нового читача.

### 7.2. Правила сумісності Protocol Buffers (proto3)
* **Незмінність номерів тегів:** Номери полів є первинними ключами бінарного потоку. Будь-яка спроба змінити номер існуючого поля або повторно використати номер видаленого поля відхиляється валідатором із помилкою `409 Conflict`.
* **Використання `reserved`:** Видалені поля зобов'язані позначатися як `reserved` із зазначенням номера тегу та імені поля.
* **Правило розширення типів:** У proto3 усі числові типи `int32`, `uint32`, `int64`, `uint64`, `bool` є двійково сумісними на рівні wire-типу `varint`. Читач автоматично виконує розширення розрядності, проте зміна `fixed32` на `int32` є фатальною помилкою через невідповідність двійкового пакування.

### 7.3. Специфікація логічних типів та їхнє просування
Реєстр валідує відповідність логічних типів базовим типам серіалізації:

| Логічний тип | Базовий двійковий тип | Параметри валідації | Правила еволюції |
|---|---|---|---|
| `decimal` | `bytes` або `fixed` | `precision` (точність), `scale` (масштаб) | Збільшення `precision` дозволене (розширення). Зменшення `precision` або зміна `scale` заборонені. |
| `uuid` | `string` | Відповідність регулярному виразу RFC 4122 | Зміна на довільний `string` без валідації UUID порушує сумісність. |
| `date` | `int` (кількість днів від Unix Epoch) | 32-бітне ціле число | Сумісний виключно з цілими числовими типами. |
| `timestamp-millis` | `long` (мілісекунди від Unix Epoch) | 64-бітне ціле число | Конвертація у `timestamp-micros` вимагає узгодження точності з читачами. |
| `timestamp-micros` | `long` (мікросекунди від Unix Epoch) | 64-бітне ціле число | Зворотне звуження до мілісекунд призводить до втрати точності й блокується. |

## 8. Метадані системи та діагностичні ендпоінти

Реєстр надає додаткові інтерфейси для моніторингу та інвентаризації схем:

### 8.1. Отримання списку підтримуваних плагінів серіалізації
* **Метод та шлях:** `GET /schemas/types`
* **Призначення:** Повертає список активних парсерів форматів, скомпільованих у поточній інсталяції реєстру.
* **Відповідь (`200 OK`):**
  ```json
  [
    "AVRO",
    "PROTOBUF",
    "JSON"
  ]
  ```

### 8.2. Пагінований список зареєстрованих суб'єктів
* **Метод та шлях:** `GET /subjects`
* **Параметри запиту:**
  * `subjectPrefix` (опціонально) — фільтрація за префіксом (наприклад, `orders.*`).
  * `deleted=true` (опціонально) — включати м'яко видалені суб'єкти.
* **Відповідь (`200 OK`):**
  ```json
  [
    "orders.placed-key",
    "orders.placed-value",
    "payments.processed-value",
    "users.created-value"
  ]
  ```

### 8.4. Зворотний пошук ідентифікатора за тілом схеми (Lookup Without Registration)
* **Метод та шлях:** `POST /subjects/{subject}`
* **Призначення:** Дозволяє продюсеру перевірити, чи вже зареєстрована тотожна схема в суб'єкті, та отримати її `id` і `version` без спроби створити нову версію чи змінити стан реєстру.
* **Тіло запиту:** JSON із визначенням схеми.
* **Відповідь (`200 OK`):**
  ```json
  {
    "subject": "orders.placed-value",
    "id": 42,
    "version": 2,
    "schema": "{\"type\":\"record\",\"name\":\"OrderPlaced\",...}"
  }
  ```
* Якщо схема не зареєстрована в зазначеному суб'єкті, реєстр повертає код `404 Not Found (40403)`.

### 8.5. Перелік усіх використань глобального ідентифікатора
* **Метод та шлях:** `GET /schemas/ids/{id}/versions`
* **Призначення:** Повертає список усіх суб'єктів та версій, які посилаються на зазначений числовий `Schema ID`. Дозволяє проводити аудит впливу видалення або міграції схем у великих мультитенантних кластерах.
* **Відповідь (`200 OK`):**
  ```json
  [
    {
      "subject": "orders.placed-value",
      "version": 2
    },
    {
      "subject": "audit.orders-value",
      "version": 1
    }
  ]
  ```

### 8.6. Режим глобальної сумісності та скидання налаштувань
* **Метод та шлях:** `DELETE /config/{subject}`
* **Призначення:** Видаляє індивідуальні налаштування сумісності для конкретного суб'єкта, повертаючи його до глобального системного рівня сумісності (`BACKWARD`, `FULL` тощо).
* **Відповідь (`200 OK`):**
  ```json
  {
    "compatibility": "BACKWARD"
  }
  ```
* Цей виклик є ідемпотентним і повертає поточний активний глобальний режим після успішного скидання локального перекриття.

## 9. Правила рівня полів та декларативні контракти якості (RuleSets)

Сучасні версії реєстру схем підтримують виконання правил якості даних (англ. *Data Quality Rules*) безпосередньо під час серіалізації та десеріалізації повідомлень клієнтом.

Схема може містити блок `ruleSet`:

```json
{
  "schema": "{\"type\":\"record\",\"name\":\"UserRegistered\",\"fields\":[{\"name\":\"email\",\"type\":\"string\"},{\"name\":\"age\",\"type\":\"int\"}]}",
  "schemaType": "AVRO",
  "ruleSet": {
    "domainRules": [
      {
        "name": "checkAge",
        "kind": "CONDITION",
        "mode": "WRITE",
        "type": "CEL",
        "expr": "message.age >= 18",
        "onFailure": "ERROR,DLQ"
      }
    ]
  }
}
```

* **`kind`:** `CONDITION` (перевірка предикату), `TRANSFORM` (мутація або маскування полів) або `ENCRYPTION` (клієнтське шифрування окремих чутливих полів PII за алгоритмом AES-GCM).
* **`mode`:** `WRITE` (виконується серіалізатором продюсера) або `READ` (виконується десеріалізатором споживача).
* **`expr`:** Вираз на декларативній мові Google Common Expression Language (CEL) або JSONata.
* **`onFailure`:** Дія при порушенні правила (`ERROR` — кинути виняток, `DLQ` — перенаправити в чергу мертвих листів, `NONE` — залогувати попередження).

## 10. Безпека, автентифікація та авторизація (RBAC)

У корпоративних мережах доступ до реєстру схем суворо розмежовується:

1. **Транспортний захист (TLS):** Усі комунікації між продюсерами/споживачами та реєстром проходять через шифровані канали HTTPS з використанням TLS 1.3.
2. **Взаємна автентифікація (mTLS):** Клієнти надають власні X.509-сертифікати, підписані корпоративним центром сертифікації (CA).
3. **Рольовий контроль доступу (RBAC):**
   * `Subject:Read` — право отримувати схеми за ID чи версією (видається всім сервісам-споживачам).
   * `Subject:Write` — право реєструвати нові версії схем (видається виключно сервісним акаунтам CI/CD пайплайнів).
   * `Subject:Config` — право змінювати режими сумісності (видається системним адміністраторам платформи).

## 11. Телеметрія, метрики Prometheus та моніторинг стану

Для інтеграції з корпоративними системами моніторингу (Prometheus, Datadog, Grafana) реєстр схем надає стандартний ендпоінт вивантаження метрик у текстовому форматі OpenMetrics:

* **Метод та шлях:** `GET /metrics`

### Ключові лічильники та гістограми:

| Назва метрики Prometheus | Тип | Опис та інтерпретація |
|---|---|---|
| `schema_registry_requests_total{method, status}` | Counter | Загальна кількість HTTP-запитів із розбивкою за методами та кодами відповідей (2xx, 4xx, 5xx). |
| `schema_registry_request_latency_seconds` | Histogram | Розподіл тривалості обробки запитів (p50, p95, p99) для виявлення сповільнень при реєстрації. |
| `schema_registry_master_slave_role` | Gauge | Поточна роль вузла у виборах лідера (`1` — Master/Leader, `0` — Slave/Follower). |
| `schema_registry_schemas_total` | Gauge | Загальна кількість зареєстрованих унікальних схем у пам'яті State Store. |
| `schema_registry_compatibility_failures_total` | Counter | Кількість спроб реєстрації несумісних схем, заблокованих валідатором. |

## 12. Стандартизована структура помилок

Усі помилки REST API повертають відповідний код стану HTTP та структуроване JSON-тіло:

```json
{
  "error_code": 40401,
  "message": "Subject 'orders.placed-value' not found."
}
```

### Основні коди помилок протоколу:

| HTTP Status | Error Code | Опис та причина помилки |
|---|---|---|
| `404 Not Found` | `40401` | Суб'єкт із зазначеною назвою не зареєстрований у системі. |
| `404 Not Found` | `40402` | Зазначена версія не знайдена у вказаному суб'єкті. |
| `404 Not Found` | `40403` | Глобальний числовий ідентифікатор `Schema ID` не існує в базі реєстру. |
| `409 Conflict` | `40901` | Схема несумісна з попередніми версіями згідно з встановленим правилом валідації. |
| `422 Unprocessable` | `42201` | Схема містить синтаксичні або структурні помилки (невалідний JSON або некоректні типи Avro/Protobuf). |
| `500 Server Error` | `50001` | Внутрішня помилка сховища (наприклад, недоступність внутрішнього системного топіка `_schemas`). |
