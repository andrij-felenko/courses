# 📜 Від монолітних IDL та XML до потокової еволюції схем

Коли наприкінці 1980-х років комітет OMG (англ. *Object Management Group*) розробляв архітектуру CORBA (англ. *Common Object Request Broker Architecture*), прихованим інваріантом усієї системи була ідея спільного компілятора: обидві сторони взаємодії отримують ідентичний файл мови опису інтерфейсів IDL (англ. *Interface Definition Language*) і генерують із нього симетричні бінарні заглушки (англ. *stubs* і *skeletons*).

У такій моделі формат повідомлень у мережі вважався неподільною монолітною структурою: якщо сервер додавав новий аргумент до методу або змінював тип поля з 16-бітного цілого числа на 32-бітне, клієнт із застарілим кодом просто не міг розпарсити двійковий потік CDR (англ. *Common Data Representation*). Зв'язок миттєво обривався винятком `BAD_OPERATION` або `MARSHAL_ERROR`. Єдиним способом провести реліз було одночасне зупинення всієї корпоративної мережі, перезбирання сотень клієнтських програм і синхронний перезапуск усіх вузлів. Поки розподілені системи обмежувалися десятком серверів у межах однієї локальної мережі банку, цей ритуал ще витримували, проте з появою веб-сервісів та тисяч незалежних клієнтів синхронні оновлення стали фізично неможливими.

## Маятник хитнувся: XML, SOAP та ілюзія самоопису

На зламі 1990-х і 2000-х років індустрія спробувала розв'язати проблему жорстких бінарних форматів переходом до повної текстової гнучкості. На зміну двійковим протоколам прийшов XML (англ. *Extensible Markup Language*) та протокол SOAP (англ. *Simple Object Access Protocol*).

Головною ідеєю XML була самоописність (англ. *self-describing format*): кожен елемент даних супроводжувався відкриваючим і закриваючим текстовим тегом на кшталт `<user_identification_number>10492</user_identification_number>`. Парсер, зустрічаючи незнайомий тег, міг просто пропустити його і продовжити читання документа. Для валідації структури використовували окремі файли XML Schema (XSD) та WSDL (англ. *Web Services Description Language*).

Проте ціна такої гнучкості виявилася катастрофічною для продуктивності:
1. **Роздування корисного навантаження (Payload Bloat):** До 80–90% обсягу повідомлення займали повторювані рядки імен тегів, простори імен XML (`xmlns`) та службові дужки. Повідомлення з двома числовими полями розросталося з 8 байтів до 600 байтів.
2. **Низька швидкість парсингу:** Текстовий розбір XML вимагав постійного виділення пам'яті в купі (англ. *heap allocation*), побудови складних дерев об'єктів DOM (англ. *Document Object Model*) та перетворення рядків у двійкові числа. Сервери витрачали до 60% процесорного часу виключно на роботу парсерів.
3. **Крихкість WSD/XSD версіонування:** Попри декларативну гнучкість, специфікація XML Schema вимагала суворого дотримання порядку елементів у блоках `<xs:sequence>`. Якщо сервер додавав нове поле не в кінець послідовності, старі клієнтські парсери все одно ламалися фатальною помилкою `cvc-complex-type.2.4.a`.

Світ веб-розробки згодом утік від складності SOAP до формату JSON (англ. *JavaScript Object Notation*), який був значно простішим і легшим. Проте JSON успадкував головну ваду самоописних текстових форматів: він не мав обов'язкового суворого контракту, змушував передавати імена полів у кожному повідомленні та не надавав жодних машинних гарантій сумісності при зміні типів.

## Внутрішній прорив Google: Protocol Buffers та дисципліна числових тегів

Усередині корпорації Google схожа проблема постала ще у 2001 році. Тисячі сервісів пошуку, реклами та індексації невпинно обмінювалися даними через RPC. Використання XML на таких масштабах випалювало мегавати електроенергії в дата-центрах.

Інженери Google (зокрема Джефф Дін та Санджай Ґемават) розробили **Protocol Buffers** (protobuf). Вони повернулися до компактного двійкового кодування, проте докорінно переосмислили спосіб ідентифікації полів. Замість прив'язки до позиції поля в пам'яті (як у C-структурах) і замість передачі текстових імен полів (як у XML/JSON), кожному полю в схемі було призначено постійний унікальний числовий номер — **тег** (англ. *field tag*):

```protobuf
message UserProfile {
  int64 user_id = 1;
  string display_name = 2;
  string email = 3;
}
```

У двійковому потоці protobuf кожен елемент кодувався у форматі `(tag << 3) | wire_type`, за яким слідувало саме значення. Це дало дві фундаментальні властивості:
* Якщо десеріалізатор зустрічає тег з невідомим номером (наприклад, сервер додав поле `int32 loyalty_tier = 4`, а клієнт використовує стару схему), він не падає з помилкою. Знаючи двійковий тип (`wire_type`), парсер точно знає довжину невідомого блоку, пропускає його і продовжує читання.
* Номери полів є незмінними. Ім'я поля `display_name` можна перейменувати на `full_name` без порушення сумісності, оскільки двійковий формат передає лише число `2`.

У 2008 році Google випустила Protocol Buffers у відкритий доступ, що задало новий стандарт ефективності для синхронних мікросервісних RPC-з'єднань.

## Виклик великих даних: Дуг Каттінг і створення Apache Avro

У 2009 році творець Apache Lucene та Apache Hadoop Дуг Каттінг (англ. *Doug Cutting*) зіткнувся з іншим викликом. У екосистемі Hadoop гігантські масиви даних (терабайти й петабайти) зберігалися у файлах на HDFS і оброблялися через MapReduce.

Protocol Buffers мав два обмеження, які були критичними для аналітики великих даних:
1. **Оверхед тегів:** Навіть 1–2 байти тегу перед кожним полем у таблиці з мільярдами рядків давали гігабайти марних витрат дискового простору.
2. **Обов'язкова кодогенерація:** Щоб прочитати protobuf-повідомлення, аналітичний інструмент (наприклад, Apache Pig або Hive) мусив мати заздалегідь скомпільовані Java-класи кожної сутності, що унеможливлювало динамічні SQL-запити до довільних схем.

Дуг Каттінг створив **Apache Avro**. У форматі Avro двійкові дані позбавлені будь-яких тегів чи маркерів — це чисті послідовності байтів значень. Щоб прочитати такий запис, десеріалізатор зобов'язаний мати на руках точну JSON-схему, за якою цей запис створювався (англ. *Writer Schema*).

Avro ввів концепцію **резолюції схем** (англ. *schema resolution*): споживач може мати власну схему (англ. *Reader Schema*), яка відрізняється від схеми запису. Бібліотека Avro автоматично зіставляє поля за іменами, підставляє значення за замовчуванням для нових полів і відкидає видалені.

Для файлового зберігання в Hadoop це було ідеальним рішенням: повна JSON-схема записувалася рівно один раз у заголовок великого Avro-файла (`.avro`), а далі слідували мільйони компактних двійкових блоків без жодного зайвого байта метаданих.

## Потоковий колапс у LinkedIn і народження Schema Registry

Проблема спалахнула з новою силою приблизно у 2011–2013 роках у компанії LinkedIn, де стрімко розвивалася розподілена платформа обміну подіями Apache Kafka.

На відміну від великих файлів Hadoop, де один заголовок обслуговує мільйон записів, у Kafka кожне повідомлення є окремим незалежним кадром розміром від кількох десятків байтів до кількох кілобайтів.

Інженери LinkedIn (серед яких були Джей Крепс, Неха Нархеде, Джун Рао та Мартін Клеппманн) створили конвеєр Camus для вивантаження подій із Kafka в HDFS:
* Спершу повідомлення передавали в JSON. Проте на швидкостях у сотні тисяч подій на секунду брокери Kafka захлиналися від трафіку, а кластери знемагали від CPU-навантаження на парсинг рядків.
* Спроба пакувати Avro-схему (розміром 1.5–3 КБ у форматі JSON) у кожне окреме 50-байтове повідомлення Kafka призвела до того, що службовий оверхед перевищив корисне навантаження у 50 разів.

Тоді інженери звернули увагу на фундаментальну властивість розподілених систем: схеми даних змінюються відносно рідко (дні чи тижні), тоді як повідомлення за цими схемами генеруються мільярдами разів на секунду.

Рішення полягало в тому, щоб **винести схеми за межі потоку даних**:
1. Створити централізований легкий мережевий сервіс — **Реєстр схем** (англ. *Schema Registry*), який зберігає всі відомі версії схем та присвоює кожній унікальний 32-бітний числовий ідентифікатор (`Schema ID`).
2. Замість передачі всього тексту схеми продюсер додає до двійкового тіла повідомлення мінімальний заголовок: 1 магічний байт `0x00` та 4 байти ідентифікатора схеми (разом рівно 5 байтів).
3. Споживач вичитує 4 байти ID, одноразово запитує схему з реєстру через HTTP, назавжди зберігає її у локальній пам'яті (RAM-кеші) та виконує швидку десеріалізацію без звернень до мережі.
4. Сам реєстр бере на себе роль **захисних воріт сумісності**: якщо розробник продюсера намагається зареєструвати схему, яка ламає існуючих споживачів, реєстр відхиляє запит із кодом помилки, запобігаючи потраплянню битих даних у Kafka.

Варто зазначити, що сама концепція відокремлення опису структури від бінарного потоку не була абсолютно новою. Ще у 1984 році Міжнародний союз електрозв'язку (ITU-T) створив стандарт **ASN.1** (англ. *Abstract Syntax Notation One*), який використовувався в телекомунікаціях, криптографічних сертифікатах X.509 та протоколах стільникового зв'язку GSM/LTE. ASN.1 підтримував правила кодування BER, DER та особливо PER (англ. *Packed Encoding Rules*), де бінарне повідомлення стискалося до окремих бітів без жодних метаданих. Проте інструменти для роботи з ASN.1 були надзвичайно складними, дорогими й закритими, а компілятори вимагали жорсткої прив'язки до скомпільованого C-коду. Справжня революція Apache Avro та Schema Registry полягала в тому, що вони зробили двійкову серіалізацію доступною, динамічною та прозорою для сучасних хмарних веб-застосунків і розподілених журналів подій.

У 2014 році команда засновників Kafka утворила компанію Confluent і відкрила вихідний код Confluent Schema Registry. З цього моменту управління еволюцією схем перетворилося з ручної домовленості між інженерними командами на повністю автоматизований фундамент сучасної потокової архітектури підприємств.
