# 🧮 Математика розподіленого кешу: дисперсія ключів, деградація хітрейту та закон Зіпфа

Ефективність розподіленого кешу описується трьома математичними законами:
1. Ймовірністю збереження ключів на кільці під час зміни кількості вузлів.
2. Дисперсією навантаження між фізичними серверами залежно від кількості віртуальних вузлів (англ. *virtual nodes*, vnodes).
3. Розподілом популярності запитів (законом Зіпфа), що створює феномен «гарячих шардингів».

Нижче наведено строгий математичний аналіз цих явищ.

---

## 1. Деградація коефіцієнта влучань при відмові вузла: Modulo проти Consistent Hashing

Нехай розподілений кеш складається з `N` однакових вузлів, зберігає `K` ключів, а середній коефіцієнт влучання (англ. *cache hit ratio*) системи в стаціонарному режимі дорівнює `h₀` (де `0 < h₀ ≤ 1`).

Припустимо, що один із `N` вузлів раптово зазнав апаратної аварії. Розглянемо, яка частка запитів збереже здатність потрапляти в кеш (новий хітрейт `h₁`) до моменту перезаповнення даних для двох схем адресації.

### Схема 1: Наївне шардування за модулем `hash(key) mod N`

При зміні кількості доступних серверів з `N` на `N - 1` цільовий вузол для довільного ключа `k` обчислюється як:
- До відмови: `node_old = hash(k) mod N`
- Після відмови: `node_new = hash(k) mod (N - 1)`

Ключ залишається на тому самому фізичному сервері тоді й лише тоді, коли:
```
hash(k) mod N = hash(k) mod (N - 1)
```

За Китайською теоремою про залишки та властивостями рівномірного хешування, ймовірність того, що випадкове число за модулями `N` та `N - 1` дасть однаковий залишок, дорівнює:

```
P(збереження_позиції_modulo)
= 1 / (N · (N - 1)) · (N - 1)    [кількість збігів від 0 до N-2]
= 1 / N                          [спрощення дробу]
```

Оскільки один вузол із `N` фізично втрачено, решта `N - 1` вузлів зберігають лише свою частку уцілілих ключів:

```
h₁_modulo
= h₀ · (1 / N)                   [результат масового перехешування]
```

**Числовий наслідок:** для кластера з `N = 10` вузлів та базового хітрейту `h₀ = 0.95` (95%), аварія одного сервера обвалює хітрейт до:
```
h₁_modulo = 0.95 · (1 / 10) = 0.095  (9.5%)
```
Тобто **90.5% усього трафіку застосунку миттєво перенаправляється на первинну базу даних**, що неминуче спричиняє її повну зупинку.

### Схема 2: Консистентне хешування (Consistent Hashing Ring)

У консистентному кільці простір хеш-функції `[0, 2³² - 1]` замкнений у коло. Кожен ключ `k` закріплюється за першим вузлом, чия координата на кільці є більшою або рівною `hash(k)`.

Коли один вузол `V_failed` вибуває з кільця, його дуга довжиною в середньому `1 / N` переходить до його безпосереднього сусіда за годинниковою стрілкою. Дуги решти `N - 1` вузлів залишаються незмінними.

```
P(ключ_належав_живому_вузлу)
= (N - 1) / N                    [частка ключів на вцілілих вузлах]
```

Усі ключі, що належали решті `N - 1` вузлів, адресуються на ті самі сервери, де вони вже лежать у пам'яті. Втрачаються лише ключі, що фізично знаходилися на впалому вузлі (частка `1 / N`).

```
h₁_consistent
= h₀ · ((N - 1) / N)
= h₀ · (1 - 1 / N)              [лінійна деградація]
```

**Числовий наслідок:** для тих самих `N = 10` вузлів та `h₀ = 0.95`:
```
h₁_consistent = 0.95 · (9 / 10) = 0.855  (85.5%)
```
Навантаження на базу даних зростає з `1.0 - 0.95 = 0.05` (5%) до `1.0 - 0.855 = 0.145` (14.5%) — тобто лише в 2.9 раза, що вкладається в типовий запас міцності (headroom) первинного сховища.

## 2. Дисперсія розподілу ключів та роль віртуальних вузлів (vnodes)

Якщо розмістити на кільці лише `N` фізичних точок, випадковий вибір координат призводить до нерівномірних дуг.

Нехай `X_i` — довжина дуги кільця, що дісталася вузлу `i`. Довжини інтервалів між `N` випадковими точками на одиничному колі описуються розподілом випадкових відрізків.

Математичне сподівання частки ключів на одному вузлі:
```
E[X_i] = 1 / N
```

Стандартне відхилення довжини дуги без віртуальних вузлів:
```
σ(X_i) ≈ 1 / N
```
Це означає, що з високою ймовірністю один із вузлів отримає дугу в 2–3 рази більшу за середню (`3 / N`), що призведе до передчасного вичерпання його оперативної пам'яті (OOM) та лавинного витіснення даних за LRU.

### Зменшення дисперсії через `V` віртуальних вузлів

Якщо кожен із `N` фізичних серверів представляється на кільці `V` випадковими псевдонімами (віртуальними вузлами), загальна кількість точок на колі стає рівною `M = N · V`.

Частка пам'яті `S_i`, закріплена за фізичним сервером `i`, є сумою `V` випадкових дуг:
```
S_i = ∑_{j=1}^{V} X_{i,j}
```

За Центральною граничною теоремою, для великих `V` (типово `V = 100..256`):

```
E[S_i] = V · (1 / (N · V)) = 1 / N
Var[S_i] ≈ 1 / (N² · V)
σ(S_i) ≈ 1 / (N · √V)
```

Відносна дисперсія (коефіцієнт варіації навантаження) зменшується пропорційно кореню з кількості віртуальних вузлів:

```
CV = σ(S_i) / E[S_i]
   = (1 / (N · √V)) / (1 / N)
   = 1 / √V                     [закон зменшення похибки]
```

**Розрахункова таблиця відхилення пам'яті:**

| Кількість vnodes (`V`) | Теоретичний розкид `1 / √V` | Максимальне перевантаження пам'яті найгіршого вузла (3σ) |
| :--- | :--- | :--- |
| `1` (без vnodes) | 100.0% | +200% .. +300% (аварійний дисбаланс) |
| `10` | 31.6% | +94.8% |
| `64` | 12.5% | +37.5% |
| `128` | 8.8% | +26.4% |
| `256` | 6.25% | +18.7% (стандарт для продакшну) |

## 3. Закон Зіпфа та математична неминучість «гарячих ключів»

У реальних системах розподіл частоти звернення до ключів не є рівномірним. Він підпорядковується дискретному закону Зіпфа (степеневому розподілу):

Ймовірність звернення до `k`-го за популярністю ключа в системі з `K` унікальних ключів дорівнює:

```
P(k) = (1 / kˢ) / (∑_{m=1}^{K} (1 / mˢ))
```
де `s` — параметр скошеності розподілу (для інтернет-трафіку `s ∈ [0.8, 1.2]`).

### Чому кластеризація не захищає від гарячих ключів

Нехай система шардована на `N = 100` однакових вузлів Redis. Сумарне навантаження становить `R = 1 000 000` запитів/с. За умови ідеально рівномірного розподілу кожен вузол мав би отримувати:
```
R_node = R / N = 1 000 000 / 100 = 10 000 req/s
```

Проте, якщо ключ №1 (наприклад, профіль популярної особи або глобальна конфігурація) має параметр Зіпфа `s = 1.0` при `K = 1 000 000` ключів:

Сума гармонійного ряду (знаменник):
```
H(K) = ∑_{m=1}^{10⁶} (1 / m) ≈ ln(10⁶) + 0.5772 ≈ 13.82 + 0.58 = 14.4
```

Частка запитів до одного найпопулярнішого ключа `k = 1`:
```
P(1) = (1 / 1¹) / 14.4 = 1 / 14.4 ≈ 0.0694  (6.94% усього трафіку!)
```

Навантаження на шард, де живе ключ №1:
```
R_hot_shard
= R · P(1) + (R · (1 - P(1))) / N              [сума прямого трафіку ключа та рівномірної частки решти]
= 1000000 · 0.0694 + (1000000 · 0.9306) / 100   [підстановка параметрів R=10⁶, N=100, P(1)=6.94%]
= 69400 + 9306                                  [арифметика доданків]
= 78706 req/s                                   [підсумкове навантаження на гарячий шард]
```

**Висновок:** Шард із найпопулярнішим ключем отримує **78 706 req/s замість середніх 10 000 req/s (майже у 8 разів більше!)**.

Жодне збільшення кількості вузлів `N` не зменшить першу складову `R · P(1) = 69 400 req/s`, оскільки весь потік до ключа №1 потрапляє на один процесорний потік єдиного сервера. Це математично доводить, що масштабування за гарячими ключами вимагає або локального кешування на клієнті (L1 In-Process Cache), або штучного розмноження ключа на `M` копій (`key#1`, `key#2`, ..., `key#M`).
