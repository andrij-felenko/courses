# 🧮 Математична модель збіжності бекфілу та динаміка реплікаційного лагу

Фонове перенесення мільярдів рядків у живу базу даних під час активного користувацького трафіку — це динамічна система з двома конкуруючими потоками: процесом копіювання історичних даних і зустрічним потоком нових бізнес-мутацій. Якщо швидкість наповнення є нижчою за темп генерації змін або якщо розмір пачки вибрано некоректно, процес міграції розходиться (*divergence*), а реплікаційний лаг зростає нескінченно, вичерпуючи дисковий простір для журналу транзакцій.

## Динаміка черги бекфілу та аналітичний час збіжності

Розглянемо вихідну таблицю, яка на момент запуску міграційного процесу містить фіксовану кількість історичних рядків `D₀`.
Нехай фоновий рушій бекфілу зчитує та записує дані з середньою швидкістю `R_mig` (рядків за секунду). Одночасно з цим живі користувачі генерують потік нових вставок та оновлень з інтенсивністю `R_write` (рядків за секунду).

Залишковий обсяг неперенесених історичних даних у довільний момент часу `t` описується диференціальним рівнянням балансу:

```
dD(t)/dt = -R_mig + R_write · (D(t) / D₀)   [баланс: швидкість копіювання мінус повторні мутації ще не скопійованих рядків]
```

У цій моделі множник `(D(t) / D₀)` відображає ймовірність того, що випадкова користувацька мутація потрапить у ту частину таблиці, яку бекфіл ще не встиг скопіювати. У міру просування воркера залишок `D(t)` зменшується, і частка неперенесених рядків монотонно прямує до нуля.

Для того щоб процес міграції завершився за скінченний час `T`, швидкість копіювання повинна строго перевищувати швидкість надходження нових мутацій:

```
R_mig > R_write                            [умова збіжності: швидкість міграції перевищує швидкість мутацій]
```

Якщо ця фундаментальна нерівність порушується (`R_mig ≤ R_write`), цільове сховище ніколи не наздожене первинне: обсяг накопичених змін зростатиме швидше, ніж рушій встигає їх обробляти, і система перейде в стан катастрофічної розбіжності.

При виконанні умови збіжності час повного завершення історичного копіювання `T_backfill` знаходиться інтегруванням диференціального балансу від початкового стану `D₀` до нульового залишку:

```
T_backfill
= ∫[0..D₀] (1 / (R_mig - R_write · (x / D₀))) dx    [інтеграл часу за спадним залишком]
= (D₀ / R_write) · ln(R_mig / (R_mig - R_write))      [аналітичний розв'язок логарифмічного запізнення]
```

Якщо швидкість міграції значно перевершує інтенсивність живого трафіку (`R_mig ≫ R_write`), аргумент логарифма розкладається в степеневий ряд Тейлора:

```
ln(R_mig / (R_mig - R_write))
= -ln(1 - R_write / R_mig)                          [перетворення аргументу логарифма]
= (R_write / R_mig) + 0.5 · (R_write / R_mig)² + …    [розклад у степеневий ряд при малих R_write/R_mig]
```

Підставляючи головний член ряду в формулу часу, отримуємо класичну інженерну оцінку тривалості процесу:

```
T_backfill ≈ D₀ / R_mig                            [асимптотичний час бекфілу при домінуючій швидкості рушія]
```

## Оптимізація розміру транзакційної пачки (Batch Size)

Швидкість роботи рушія `R_mig` безпосередньо залежить від кількості рядків `B`, які вибираються за один SQL-запит і фіксуються в єдиній транзакції.

Повний час обробки однієї пачки `t_batch(B)` складається з двох фундаментальних складових:
1. Фіксовані накладні витрати транзакції `t_fixed` — мережевий раунд-трип (*Round-Trip Time, RTT*), час парсингу SQL-запиту оптимізатором, захоплення блокувань транзакції та синхронізація запису журналу на диск (`fsync`).
2. Маргінальний час обробки кожного рядка `c_row` — зчитування зі сторінки пам'яті, серіалізація в мережевий буфер і перебудова B-дерева індексів.

```
t_batch(B) = t_fixed + c_row · B                  [лінійна функція часу виконання однієї транзакційної пачки]
```

Пропускна здатність міграції `P(B)` (кількість перенесених рядків за одну секунду) визначається співвідношенням:

```
P(B)
= B / t_batch(B)                                  [визначення пропускної здатності: обсяг / час]
= B / (t_fixed + c_row · B)                       [підстановка компонентів часу]
= 1 / (c_row + t_fixed / B)                       [ділення чисельника і знаменника на B]
```

З аналізу функції видно, що зі збільшенням розміру пачки `B` питома вага фіксованих накладних витрат `(t_fixed / B)` прямує до нуля, а продуктивність наближається до теоретичної стелі `1 / c_row`.

Проте вибір занадто великої пачки різко погіршує роботу живої системи. Кожна транзакція утримує блокування рядків або діапазонів індексів протягом усього часу свого виконання `t_batch(B)`. Конкурентні прикладні транзакції змушені чекати звільнення блокувань. Згідно з теорією масового обслуговування, ймовірність конфлікту блокувань зростає квадратично від розміру пачки: `C_lock(B) = α · B²`, де `α` — коефіцієнт конкуренції транзакцій.

Формуємо загальну функцію оптимізаційних втрат `J(B)`, що поєднує накладні витрати та штраф за блокування:

```
J(B) = (t_fixed / B) + c_row + α · B              [цільова функція втрат: накладні витрати плюс штраф за блокування]
```

Знаходимо оптимальний розмір пачки `B*` взяттям першої похідної за параметром `B` і прирівнюванням її до нуля:

```
dJ(B)/dB
= -t_fixed / B² + α                               [перша похідна за розміром пачки]
= 0                                               [умова екстремуму функції втрат]
```

Розв'язуючи це рівняння, отримуємо аналітичну формулу оптимального розміру чанка:

```
B* = √(t_fixed / α)                               [оптимальний розмір пачки бекфілу]
```

Для сучасних NVMe-сховищ і локальних 10-гігабітних мереж типові параметри становлять:
* `t_fixed ≈ 3...5 мс`
* `α ≈ 2 · 10⁻⁶ мс / рядок²`
* `B* = √(4 / 2·10⁻⁶) = √2 000 000 ≈ 1414 рядків`.

Саме тому діапазон пачок у `1000–2000` рядків є стандартом для промислових баз даних: менші пачки марнують процесорний час на транзакційні накладні витрати, а більші — спричиняють мікрозависання запитів живих користувачів.

## Моделювання ймовірності конфлікту при Пуассонівському потоці оновлень

Якщо потік користувацьких мутацій підпорядковується закону Пуассона з параметром інтенсивності `λ_update`, ймовірність виникнення конфлікту (коли той самий рядок одночасно оновлюється клієнтом і копіюється воркером протягом інтервалу `Δt_batch`) обчислюється як:

```
P(conflict) = 1 - e^(-λ_update · Δt_batch)         [ймовірність перетину мутацій у часовому вікні пачки]
```

Для коротких пачок (`Δt_batch ≈ 10...50 мс`) показник експоненти малий, і формула спрощується:

```
P(conflict) ≈ λ_update · Δt_batch                 [лінійна апроксимація ймовірності конфлікту]
```

Цей результат доводить необхідність підтримки мінімального часу виконання кожної пачки `Δt_batch`: чим швидше фіксується окрема транзакція бекфілу, тим менше вікно виникнення гонки між живим подвійним записом та фоновим воркером.

## Динаміка реплікаційного лагу та зворотний зв'язок

Згідно з законом Літтла для систем масового обслуговування, поточний лаг реплікації `L(t)` (в секундах) визначається обсягом черги невичитаних байтів у журналі транзакцій `Q(t)` відносно швидкості застосування змін реплікою `μ_replica`:

```
L(t) = Q(t) / μ_replica                           [лаг: кількість накопичених байтів у черзі WAL / швидкість застосування реплікою]
```

Швидкість зміни обсягу черги є різницею між сумарною генерацією журналу та швидкістю його відтворення:

```
dQ(t)/dt = (R_write + R_mig) · S_row - μ_replica  [динаміка накопичення черги журналу транзакцій]
```

де `S_row` — середній розмір одного рядка разом із журналами індексів у байтах.

Якщо загальна швидкість запису перевищує можливості репліки (`(R_write + R_mig) · S_row > μ_replica`), лаг зростає монотонно. Щоб стабілізувати чергу на безпечному рівні `L_max`, застосовується пропорційно-диференціальний регулятор затримки між пачками `Δt_sleep`:

```
Δt_sleep(t) = K_p · max(0, L(t) - L_max) + K_d · (dL(t)/dt)   [адаптивне дроселювання воркера за лагом і швидкістю його зростання]
```

Завдяки цьому алгоритму при виникненні раптового піку клієнтського навантаження швидкість бекфілу `R_mig` автоматично падає майже до нуля, запобігаючи переповненню диска реплікаційними журналами та забезпечуючи стабільну роботу основного бізнес-сервісу.
