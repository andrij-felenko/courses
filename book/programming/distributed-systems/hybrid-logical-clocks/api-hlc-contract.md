# 📋 Специфікація та бінарний контракт HLC

Взаємодія між серверами розподіленої бази даних та клієнтськими драйверами вимагає стандартизованого бінарного протоколу представлення часових координат. Якщо різні вузли або мікросервіси інтерпретують бітові маски, порядок байтів (англ. *endianness*) чи коди помилок розсинхронізації по-різному, транзакційний рушій не зможе гарантувати ізоляцію знімків. Неузгодженість формату призводить до спотворення порядку транзакцій під час серіалізації в мережеві пакети або збереження в індекси дискового рушія.

Цей контракт визначає структури даних, бінарний формат мережевого кадру, сигнатури операцій, інваріанти серіалізації та коди повернення рушія HLC. Специфікація розрахована на використання у високонавантажених розподілених базах даних, сховищах ключ-значення (Key-Value) з багатоверсійним керуванням конкурентним доступом (MVCC) та брокерах повідомлень із гарантіями причинного порядку.

## Бінарні формати мережевого представлення

Контракт підтримує два формати представлення: 64-бітний компактний (для вбудованих сховищ та високої пропускної здатності) та 96-бітний розширений (для аналітичних систем високої точності).

### 1. 64-бітний компактний формат (Мілісекундна точність)

У 64-бітному форматі фізичний час та логічний лічильник упаковані в єдине беззнакове 64-бітне ціле число:

| Бітовий діапазон | Поле | Розмірність | Опис |
| :--- | :--- | :--- | :--- |
| `63..16` (48 бітів) | `physical_ms` | Мілісекунди | Фізичний час Unix Epoch (діапазон до 8925 року н. е.) |
| `15..0` (16 бітів) | `logical` | Ціле число | Логічний лічильник (до 65 535 подій на мілісекунду) |

**Вимога до порядку байтів:** При передачі мережею або зберіганні в індексах баз даних (LSM-tree / B-tree) значення обов'язково кодується у форматі **Big-Endian** (мережевий порядок байтів). Завдяки цьому звичайне побайтове лексикографічне порівняння функцією `memcmp()` повністю збігається з причинним часовим порядком HLC, що дозволяє дисковим рушіям порівнювати версії ключів без декодування структури.

### 2. 96-бітний високоточний формат (Наносекундна точність)

Використовується в промислових розподілених СУБД (CockroachDB, YugabyteDB) для роботи з високочастотними транзакціями:

```
+-------------------------------------------------------+
| Байти 0..7 (64 біти) : physical_nanos (Unix Epoch ns) |
+-------------------------------------------------------+
| Байти 8..11 (32 біти): logical_counter                |
+-------------------------------------------------------+
| Байти 12..15 (опція) : node_id (uint32)               |
+-------------------------------------------------------+
```

## Програмний інтерфейс (C та C++ API)

Для забезпечення максимальної сумісності та продуктивності контракт визначає як чистий інтерфейс мовою C для системного рівня, так і типізований об'єктний інтерфейс мовою C++ з підтримкою сучасних стандартів обробки помилок через `std::expected` та тристороннього порівняння.

```c
#ifndef HLC_CONTRACT_H
#define HLC_CONTRACT_H

#include <stdint.h>
#include <stdbool.h>

#ifdef __cplusplus
extern "C" {
#endif

/* Статуси виконання операцій */
typedef enum {
    HLC_STATUS_OK                 = 0, /* Успішна операція */
    HLC_STATUS_ERR_DRIFT_EXCEEDED = 1, /* Фізичний час повідомлення перевищує поріг max_drift */
    HLC_STATUS_ERR_OVERFLOW       = 2, /* Переповнення логічного лічильника в межах тіку */
    HLC_STATUS_ERR_INVALID_ARG    = 3  /* Недійсні вказівники або параметри */
} hlc_status_t;

/* Структура канонічної мітки часу */
typedef struct {
    uint64_t physical_ms; /* Старша компонента l (мс) */
    uint32_t logical;     /* Молодша компонента c */
    uint32_t node_id;     /* Ідентифікатор вузла */
} hlc_timestamp_t;

/* Непрозорий дескриптор рушія годинника */
typedef struct hlc_engine hlc_engine_t;

/* Створення та знищення екземпляра рушія */
hlc_engine_t* hlc_engine_create(uint32_t node_id, uint64_t max_drift_ms);
void          hlc_engine_destroy(hlc_engine_t* engine);

/* Генерація мітки для локальної події або відправки */
hlc_status_t hlc_now(hlc_engine_t* engine, hlc_timestamp_t* out_ts);

/* Оновлення стану при отриманні вхідного пакета */
hlc_status_t hlc_update(hlc_engine_t* engine, const hlc_timestamp_t* remote_ts, hlc_timestamp_t* out_ts);

/* Повне лексикографічне порівняння двох міток */
/* Повертає -1 якщо a < b, 0 якщо a == b, +1 якщо a > b */
int hlc_compare(const hlc_timestamp_t* a, const hlc_timestamp_t* b);

/* Серіалізація та десеріалізація 64-бітного бінарного формату */
uint64_t hlc_serialize_wire64(const hlc_timestamp_t* ts);
void     hlc_deserialize_wire64(uint64_t wire, uint32_t node_id, hlc_timestamp_t* out_ts);

#ifdef __cplusplus
}
#endif

#endif /* HLC_CONTRACT_H */
```

```cpp
#pragma once

#include <cstdint>
#include <chrono>
#include <compare>
#include <expected>
#include <memory>
#include <span>

namespace hlc {

enum class Status : uint8_t {
    Ok = 0,
    ClockDriftExceeded = 1,
    CounterOverflow = 2,
    InvalidArgument = 3
};

/* Канонічна незмінна мітка HLC */
struct Timestamp {
    uint64_t physical_ms{0};
    uint32_t logical{0};
    uint32_t node_id{0};

    auto operator<=>(const Timestamp&) const = default;

    [[nodiscard]] uint64_t to_wire64() const noexcept {
        return ((physical_ms & 0x0000FFFFFFFFFFFFULL) << 16) | (logical & 0xFFFFULL);
    }

    [[nodiscard]] static Timestamp from_wire64(uint64_t wire, uint32_t node_id = 0) noexcept {
        return Timestamp{
            .physical_ms = (wire >> 16) & 0x0000FFFFFFFFFFFFULL,
            .logical = static_cast<uint32_t>(wire & 0xFFFFULL),
            .node_id = node_id
        };
    }
};

/* Абстрактний інтерфейс годинникового рушія */
class IEngine {
public:
    virtual ~IEngine() = default;

    [[nodiscard]] virtual std::expected<Timestamp, Status> now() noexcept = 0;
    [[nodiscard]] virtual std::expected<Timestamp, Status> update(const Timestamp& remote_ts) noexcept = 0;
    [[nodiscard]] virtual uint32_t node_id() const noexcept = 0;
    [[nodiscard]] virtual std::chrono::milliseconds max_drift() const noexcept = 0;
};

/* Фабрика створення стандартного потокобезпечного рушія */
std::unique_ptr<IEngine> create_engine(uint32_t node_id,
                                       std::chrono::milliseconds max_drift = std::chrono::milliseconds(500));

} // namespace hlc
```

## Інваріанти обробки помилок та аномалій

1. **Поріг максимального дрейфу (`HLC_STATUS_ERR_DRIFT_EXCEEDED`):**
   Якщо вхідне повідомлення містить фізичну мітку `remote_ts.physical_ms > pt_local + max_drift_ms`, рушій не оновлює внутрішній стан і негайно повертає помилку. Викликаючий сервіс зобов'язаний закрити мережеве з'єднання з вузлом-відправником та зафіксувати подію в системі моніторингу. Забороняється примусово приймати такі мітки, оскільки це спричинить стрибок часу на всіх вузлах кластера. Сервер із викривленим годинником підлягає ізоляції (англ. *node eviction / self-fencing*).
2. **Переповнення логічного лічильника (`HLC_STATUS_ERR_OVERFLOW`):**
   Якщо кількість подій у межах однієї мілісекунди перевищує максимальну місткість лічильника `UINT16_MAX` (або `UINT32_MAX`), рушій повертає код переповнення. Обробник зобов'язаний виконати мікропаузу (англ. *busy-wait* або `nanosleep`) тривалістю до наступного тіка системного таймера (`pt > l`), після чого повторити виклик `hlc_now()`. Такий підхід гарантує безпечне пригальмовування (англ. *backpressure*) без ризику спотворення монотонності.
3. **Стрибок системного часу назад (NTP Backward Step):**
   Якщо демон NTP здійснює крокову корекцію фізичного годинника назад (`pt_now < pt_prev`), алгоритм HLC ігнорує спад `pt`, зберігаючи `l = max(l_old, pt) = l_old`. Монотонність міток ніколи не порушується, а лічильник `c` продовжує монотонно інкрементуватися, доки фізичний час системи не перевищить попереднє значення `l`.

## Інтеграція з консенсусом Raft та реплікацією

У розподілених системах із консенсусом на базі Raft або Multi-Paxos взаємодія між лідером та фоловерами підпорядковується чіткому протоколу:
- **Штампування записів лідером:** Лідер групи консенсусу генерує HLC мітку часу для кожної клієнтської транзакції у момент формування запису в журнал (`Raft.Log`). Ця мітка вкладається в пакет RPC `AppendEntries`;
- **Оновлення стану фоловерами:** Кожен фоловер при отриманні `AppendEntries` викликає `hlc_update(entry.timestamp)`, підтягуючи свій локальний HLC до мітки лідера. Якщо репліка відставала через мережеву ізоляцію, її фізична компонента `l` миттєво синхронізується з актуальним часом групи;
- **Передача лідерства:** При виборах нового лідера новий координатор гарантовано володіє станом HLC, не меншим за мітки всіх раніше підтверджених транзакцій попереднього терміну (англ. *term*), що виключає появу дублікатів або інверсій часу при зміні топології.

## Інтеграція зі сховищами MVCC

При використанні HLC у багатоверсійних рушіях зберігання (LSM-дерева на базі RocksDB або Pebble) ключ запису формується конкатенацією:

```
[ Користувацький ключ ] + [ 0x00 (роздільник) ] + [ Big-Endian HLC Wire Bytes ]
```

Оскільки Big-Endian представлення зберігає природний числовий порядок, ітератор дискового рушія здійснює пошук потрібної версії знімка `T_read` через стандартний префіксний пошук `Seek(key + T_read)`:
- Найновіша версія запису, менша або рівна `T_read`, знаходиться першою за `O(log K)` дискових операцій;
- Видалені записи (англ. *tombstones*) кодуються аналогічно, забезпечуючи коректне приховування видалених об'єктів для знімків минулого часу;
- Процес фонового ущільнення даних (англ. *compaction / garbage collection*) порівнює HLC мітку кожної версії з мінімальним активним знімком кластера `T_gc_watermark` і безпечно утилізує застарілі байти.

## Метрики спостережуваності та трасування

Кожен виробничий вузол HLC зобов'язаний експортувати три стандартні телеметричні метрики для систем Prometheus / OpenTelemetry:
- `hlc_clock_offset_milliseconds` (`Gauge`): Різниця між максимальною компонентою `l` та локальним фізичним часом `pt` (`l - pt`). Стійке зростання метрики понад 50% від `max_drift_ms` сигналізує про систематичне відставання локального годинника від решти кластера або високе навантаження;
- `hlc_logical_counter_current` (`Gauge`): Поточне значення лічильника `c`. Значення, близькі до граничних, свідчать про екстремальну локальну частоту транзакцій на одне ядро;
- `hlc_drift_errors_total` (`Counter`): Кількість відхилених пакетів через перевищення порогу `max_drift`. Будь-яке ненульове значення вимагає негайного сповіщення чергового інженера інфраструктури.

Для діагностики низькорівневих аномалій ядро рушія надає статичні точки зондування (DTrace / eBPF tracepoints): `hlc_drift_warning`, `hlc_counter_bump` та `hlc_backward_step`.
