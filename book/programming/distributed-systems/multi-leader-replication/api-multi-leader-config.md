# 📋 Конфігурація та діагностичний інтерфейс мультилідерної реплікації

Розгортання та експлуатація систем із багатьма активними лідерами вимагає точного налаштування параметрів виявлення конфліктів, керування топологією вузлів та моніторингу затримок передачі журналів. Цей довідник містить детальний опис конфігураційних директив, системних таблиць, SQL-процедур, REST-контрактів та метрик телеметрії для провідних промислових рушіїв мультилідерної реплікації: PostgreSQL BDR (Bi-Directional Replication), MySQL Group Replication та Apache CouchDB.

### Призначення та архітектурний контекст конфігурації

На відміну від класичної однолідерної реплікації, де вторинні вузли перебувають у режимі «лише для читання» і пасивно застосовують бінарний потік WAL, мультилідерні рушії функціонують в умовах постійного ризику паралельних конфліктних транзакцій. Кожен вузол-лідер зобов'язаний виконувати подвійну роботу:
1. Локально обслуговувати транзакції клієнтів із мінімальною латентністю, фіксуючи зміни в локальному журналі предзапису.
2. Асинхронно транслювати дельту змін віддаленим лідерам через логічні реплікаційні слоти або групи консенсусу, одночасно приймаючи та верифікуючи зустрічні потоки від пірів.

Якщо конфігурація виявлення колізій налаштована некоректно, система зазнає або розходження даних (англ. *silent data divergence*), або аварійної зупинки фонових реплікаційних процесів. Нижче систематизовано інтерфейси керування, діагностики та автоматичного відновлення таких систем.

### 1. PostgreSQL BDR: Параметри ядра та налаштування конфліктів

Розширення BDR (Bi-Directional Replication) для PostgreSQL реалізує логічну мультимайстер-реплікацію на рівні декодування WAL-журналу. Воно перехоплює атомарні операції зміни рядків (`INSERT`, `UPDATE`, `DELETE`) і передає їх у формі логічних повідомлень між екземплярами PostgreSQL.

#### Механіка роботи та параметри конфігурації (`postgresql.conf`)

Конфігурація BDR визначає поведінку системи в момент, коли вхідна зміна з віддаленого вузла стикається з локально модифікованим рядком.

Головний параметр `bdr.conflict_resolution_mode` задає глобальну політику збіжності. Значення `error` вимикає автоматичне злиття: при першому ж конфлікті реплікаційний процес переривається з помилкою, запобігаючи неконтрольованій зміні даних до втручання адміністратора. Режим `lww` вмикає евристику Last-Write-Wins, де рушій порівнює часові мітки коміту транзакцій на вузлах-джерелах. Якщо мітки збігаються до мілісекунди, розрив нічиєї здійснюється на основі числового пріоритету вузла `bdr.node_priority`.

Режим `priority` повністю ігнорує час і завжди віддає перевагу лідеру з вищим пріоритетом (наприклад, центральний датацентр завжди перемагає регіональні філії). Режим `custom` делегує прийняття рішення користувацькій PL/pgSQL або C-функції, передаючи їй повні бінарні образи старого, локального та вхідного рядків.

Параметр `bdr.max_clock_skew_ms` виступає запобіжником проти аномалій системного часу: якщо різниця фізичних годинників між серверами перевищує заданий поріг (наприклад, 5000 мс), BDR блокує реплікацію, захищаючи базу від знищення свіжих даних через апаратний збій NTP на одному з вузлів.

Параметр `bdr.strict_ddl_replication` контролює безпеку зміни структури таблиць. При увімкненому параметрі будь-яка команда `ALTER TABLE` або `CREATE INDEX` автоматично захоплює глобальний розподілений замок (англ. *global DDL lock*) на всіх вузлах кластера, гарантуючи ідентичність схем перед відновленням прийому DML-запитів.

#### Огляд параметрів ядра BDR

- `bdr.conflict_resolution_mode` (тип `enum`, за замовчуванням `error`): режим вирішення конфліктів (`error`, `lww`, `priority`, `custom`).
- `bdr.default_conflict_handler` (тип `string`, за замовчуванням порожній): ім'я глобальної функції-резолвера для режиму `custom`.
- `bdr.log_conflicts` (тип `bool`, за замовчуванням `on`): протоколювання всіх випадків розбіжності даних.
- `bdr.conflict_logging_level` (тип `enum`, за замовчуванням `log`): рівень деталізації журналу конфліктів (`debug`, `info`, `notice`, `log`, `warning`, `error`).
- `bdr.node_priority` (тип `int`, за замовчуванням `100`, діапазон `1..1000`): пріоритет вузла для детермінованого розв'язання колізій.
- `bdr.max_clock_skew_ms` (тип `int`, за замовчуванням `5000`): максимально допустимий дрейф фізичного часу між лідерами в мілісекундах.
- `bdr.strict_ddl_replication` (тип `bool`, за замовчуванням `on`): обов'язкова глобальна координація при зміні схеми бази даних.

#### Адміністративні SQL-функції керування топологією

Для створення вузлів, об'єднання їх у реплікаційні групи та призначення специфічних обробників використовуються вбудовані процедури:

```sql
-- 1. Створення та реєстрація локального лідера в кластері
SELECT bdr.create_node(
    node_name := 'node_frankfurt_1',
    local_dsn := 'host=10.0.1.5 port=5432 dbname=production user=bdr_admin password=secret'
);

-- 2. Приєднання до існуючого кластера через віддалений лідер
SELECT bdr.join_node_group(
    join_target_dsn := 'host=10.0.2.5 port=5432 dbname=production user=bdr_admin password=secret',
    node_group_name := 'global_ecommerce_cluster',
    pause_on_join := false
);

-- 3. Реєстрація спеціалізованого резолвера для конкретної таблиці
SELECT bdr.alter_table_conflict_handler(
    relation := 'orders'::regclass,
    handler_name := 'orders_crdt_field_merge',
    handler_type := 'custom_function',
    function_name := 'public.resolve_orders_conflict(bdr.conflict_data)'
);
```

#### Системні таблиці діагностики BDR

Для оперативного контролю стану кластера адміністратори здійснюють моніторинг двох ключових системних уявлень:

1. **`bdr.node_slots`:** відображає активність логічних слотів реплікації між локальним сервером і всіма пірами. Ключовими полями є `slot_name` (ім'я фізичного слота), `active` (прапорець живого TCP-з'єднання), `sent_lsn` (остання позиція надісланого журналу), `write_lag_bytes` (обсяг невідправленого WAL у байтах) та `replay_lag_seconds` (фізичний час відставання репліки від джерела).

2. **`bdr.conflict_history`:** детальний журнал аудиту колізій. Містить точний час виявлення інциденту (`conflict_time`), цільову таблицю (`table_name`), категорію конфлікту (`conflict_type`: вставка вже існуючого первинного ключа `insert_exists`, паралельне оновлення різних полів `update_differ`, оновлення відсутнього рядка `update_missing`), прийняте рішення (`resolution`: застосовано віддалений запис, збережено локальний, пропущено або оброблено функцією), а також JSON-зліпки локального і вхідного рядків (`local_tuple`, `remote_tuple`) із зазначенням вузла-ініціатора (`origin_node`).

### 2. MySQL Group Replication: Мультипервинний режим (Multi-Primary Mode)

MySQL Group Replication (MGR) надає синхронно-сертифіковану мультилідерну модель на основі протоколу групового зв'язку Paxos (Paxos-based Group Communication System).

#### Механізм сертифікації транзакцій

У режимі Multi-Primary кожен вузол кластера здатний приймати транзакції на запис. Проте, на відміну від суто асинхронного BDR, MySQL Group Replication застосовує фазу оптимістичної розподіленої сертифікації (англ. *optimistic transaction certification*):
1. Транзакція виконується на локальному вузлі без блокування віддалених серверів, накопичуючи набір прочитаних та змінених рядків (англ. *read-set* та *write-set* у формі 64-бітних хешів первинних ключів).
2. Перед фіксацією (commit) вузол транслює свій write-set усім іншим учасникам групи через упорядкований атомарний канал зв'язку (Atomic Broadcast).
3. Кожен вузол групи (включно з ініціатором) у суворо однаковому детермінованому порядку перевіряє вхідний write-set проти локальних транзакцій, які перебувають у процесі виконання.
4. Якщо виявлено перетин за первинними або унікальними ключами, локальна транзакція, що запізнилася, зазнає краху сертифікації та примусово відкочується (`ROLLBACK`), а перша транзакція успішно фіксується на всіх серверах.

#### Конфігурація мультимайстра в `my.cnf`

```ini
[mysqld]
# Увімкнення глобальних транзакційних ідентифікаторів (обов'язково)
gtid_mode = ON
enforce_gtid_consistency = ON

# Налаштування двійкового журналу
binlog_format = ROW
binlog_checksum = NONE
log_slave_updates = ON
master_info_repository = TABLE
relay_log_info_repository = TABLE

# Group Replication у мультилідерному режимі
plugin-load-add = group_replication.so
group_replication_group_name = "8a94fde6-abdc-4d1e-8e6d-9b50bf62d980"
group_replication_start_on_boot = ON
group_replication_local_address = "10.0.1.10:33061"
group_replication_group_seeds = "10.0.1.10:33061,10.0.2.10:33061,10.0.3.10:33061"
group_replication_single_primary_mode = OFF
group_replication_enforce_update_everywhere_checks = ON

# Ліміти та керування потоком (Flow Control)
group_replication_transaction_size_limit = 150000000
group_replication_flow_control_mode = "QUOTA"
group_replication_flow_control_certifier_threshold = 25000
```

#### Діагностика стану MGR через `performance_schema`

Для перевірки здоров'я групи використовуються запити до таблиць продуктивності:

```sql
-- Статус учасників групи та їхні ролі
SELECT 
    member_id, 
    member_host, 
    member_port, 
    member_state, 
    member_role, 
    member_version 
FROM performance_schema.replication_group_members;

-- Моніторинг черги сертифікації та кількості відхилених транзакцій
SELECT 
    channel_name,
    count_transactions_in_queue AS cert_queue_len,
    count_transactions_checked AS total_checked,
    count_conflicts_detected AS total_conflicts,
    count_transactions_rows_validating AS cert_db_size
FROM performance_schema.replication_group_member_stats;
```

Значення `member_state = ONLINE` свідчить про повну працездатність, `RECOVERING` — про процес наздоганяння пропущеного бінарного журналу під час старту, а `UNREACHABLE` — про підозру на мережеву ізоляцію або аварію вузла.

### 3. Apache CouchDB: REST API та протокол двоспрямованої реплікації

Apache CouchDB базується на філософії документно-орієнтованого сховища без блокувань, де реплікація є рівноправним обміном змінами через протокол HTTP/REST.

#### Протокол реплікації та ендпоінт `POST /_replicate`

Для запуску процесу синхронізації клієнт відправляє JSON-маніфест на системний ендпоінт `/_replicate`. Реплікація може бути одноразовою (виконується до вичерпання поточних змін) або безперервною (`"continuous": true`), за якої джерело утримує відкрите HTTP-з'єднання зі стримінгом потоку змін (`_changes?feed=continuous`).

Параметр `"create_target": true` автоматично створює базу на приймачі, якщо вона відсутня. Параметр `"filter": "_selector"` дозволяє реплікувати лише підмножину документів, що відповідають JSON-запиту, суттєво заощаджуючи трансконтинентальний трафік.

```http
POST /_replicate HTTP/1.1
Host: couchdb-node-a.internal:5984
Content-Type: application/json
Authorization: Basic YWRtaW46c2VjcmV0

{
  "source": "http://couchdb-node-a.internal:5984/customers",
  "target": "http://couchdb-node-b.internal:5984/customers",
  "continuous": true,
  "create_target": true,
  "winning_revs_only": false,
  "filter": "_selector",
  "selector": {
    "region": { "$in": ["EMEA", "GLOBAL"] }
  },
  "retry_delay": 5,
  "worker_processes": 4,
  "http_connections": 20
}
```

У відповідь сервер повертає унікальний ідентифікатор сесії `"session_id"` та локальний ідентифікатор завдання реплікації `"_local_id"`, за якими можна відстежувати прогрес або скасувати завдання (`"cancel": true`).

#### Інтерфейс виявлення та злиття розгалужень (Siblings)

Коли два вузли одночасно модифікують один документ, CouchDB створює дві паралельні гілки ревізій. Детектор вибирає одну гілку як «переможця за замовчуванням» на основі детермінованого порівняння глибини дерева та лексикографічного порядку хешів ревізій, гарантуючи, що всі вузли відображатимуть однаковий документ.

Щоб знайти всі паралельні гілки та виконати бізнес-злиття, клієнт виконує запит із прапорцем `conflicts=true`:

```http
GET /customers/cust_99812?conflicts=true HTTP/1.1
Host: couchdb-node-a.internal:5984
Accept: application/json
```

Сервер повертає актуальний стан документа разом із масивом альтернативних версій у полі `_conflicts`:

```json
{
  "_id": "cust_99812",
  "_rev": "3-9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d",
  "name": "Acme Corp Europe",
  "status": "active",
  "balance": 15400.50,
  "_conflicts": [
    "3-4f5e6d7c8b9a0f1e2d3c4b5a6f7e8d9c",
    "2-1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d"
  ]
}
```

Для остаточного розв'язання конфлікту клієнтський застосунок записує фінальний синтезований документ із черговим номером ревізії `4-...`, після чого надсилає явні HTTP-запити на видалення кожної конфліктної гілки: `DELETE /customers/cust_99812?rev=3-4f5e6d7c8b9a0f1e2d3c4b5a6f7e8d9c`. Після видалення конфліктних ревізій дерево розгалуження згортається в єдину лінійну історію.

### 4. Хмарні керовані платформи: DynamoDB Global Tables та Azure Cosmos DB

Сучасні публічні хмари надають повністю керовані сервіси мультилідерної реплікації, де рушії беруть на себе автоматичне масштабування каналів передачі та детекцію колізій.

#### Amazon DynamoDB Global Tables: Конфігурація та CloudWatch метрики

DynamoDB Global Tables забезпечує повністю керовану мультимайстер-реплікацію між регіонами AWS. Будь-який регіональний екземпляр таблиці приймає операції `PutItem`, `UpdateItem` та `DeleteItem`, які асинхронно транслюються в інші обрані регіони за допомогою внутрішнього журналу DynamoDB Streams.

##### Налаштування реплікації через AWS CLI
```bash
# Створення глобальної таблиці у двох регіонах (eu-central-1 та ap-northeast-1)
aws dynamodb create-global-table \
    --global-table-name CustomerAccounts \
    --replication-group RegionName=eu-central-1 RegionName=ap-northeast-1
```

##### Механіка розв'язання конфліктів у DynamoDB
DynamoDB Global Tables використовує сувору евристику Last-Write-Wins (LWW) на рівні атрибутів системного часу. DynamoDB докладає максимальних зусиль для синхронізації годинників своїх серверів через службу Time Sync Service (точність у межах кількох мікросекунд відносно UTC). Якщо два клієнти одночасно оновлюють різні поля одного елемента (наприклад, Регіон 1 змінює `email`, а Регіон 2 змінює `phone_number`), обидві зміни об'єднуються без конфлікту. Проте якщо оновлюється одне й те саме поле, запис із пізнішою міткою часу повністю замінює попередній.

##### Ключові метрики AWS CloudWatch для Global Tables
- `ReplicationLatency` (мілісекунди): час, необхідний для того, щоб оновлення, виконане в джерелі, з'явилося в цільовій регіональній таблиці. Нормальний показник становить від 50 до 300 мс залежно від географічної відстані.
- `PendingReplicationCount` (кількість елементів): число транзакцій, які очікують передачі через міжрегіональний бекбон AWS. Постійне зростання сигналізує про вичерпання виділеної пропускної здатності (WCUs) у цільовому регіоні.

#### Azure Cosmos DB Multi-Master: Політики вирішення конфліктів

Azure Cosmos DB надає можливість налаштування політики розв'язання конфліктів безпосередньо у властивостях колекції (Container Definition).

##### Підтримувані режими `conflictResolutionPolicy`

1. **Last-Writer-Wins (`LastWriterWins`):**
   Керується числовим полем, шлях до якого задається параметром `conflictResolutionPath` (за замовчуванням це системна мітка часу `/_ts`). Розробник може вказати власне поле з монотонним логічним лічильником, наприклад `/customEpochCounter`. Перемагає документ із найбільшим числовим значенням.

2. **Користувацька збережена процедура (`Custom` / Stored Procedure):**
   При виявленні конкурентних записів Cosmos DB автоматично викликає зареєстровану JavaScript-процедуру на сервері. Процедура отримує вхідний документ, локальний документ та базову версію, самостійно формуючи фінальний JSON-об'єкт.

3. **Ручне розв'язання через канал колізій (`None` / Conflicts Feed):**
   Система відмовляється від автоматичного злиття і записує всі конфліктні версії у спеціальний системний журнал колізій (`Conflicts Feed`). Клієнтський мікросервіс вичитує цей канал і виконує бізнес-злиття асинхронно.

##### Маніфест налаштування контейнера Cosmos DB (ARM / Bicep шаблон)
```json
{
  "conflictResolutionPolicy": {
    "mode": "LastWriterWins",
    "conflictResolutionPath": "/userModifiedTimestamp"
  }
}
```

### 5. Мережевий контракт та вимоги до безпеки міжлідерного зв'язку

Передача реплікаційного трафіку між географічно рознесеними лідерами вимагає суворого дотримання стандартів мережевої безпеки та оптимізації буферів TCP:

- **Взаємна автентифікація (mTLS):** Усі міжлідерні канали повинні захищатися протоколом TLS версії 1.3 з перевіркою клієнтських X.509-сертифікатів з обох сторін. Це запобігає атакам типу Man-in-the-Middle та несанкціонованому підключенню підроблених лідерів до реплікаційної групи.
- **Оптимізація вікна TCP (BDP — Bandwidth-Delay Product):** Оскільки міжконтинентальний канал має високий RTT (200–250 мс), стандартні розміри буферів сокетів операційної системи (64 КБ) призводять до різкого падіння швидкості реплікації. Системний адміністратор зобов'язаний збільшити параметри ядра Linux:
  `sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"` та `sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"`.
- **Стиснення трафіку:** Логічні потоки WAL/Binlog містять текстові назви таблиць та повторювані структури, які ефективно стискаються алгоритмами LZ4 або Zstandard безпосередньо в пам'яті перед відправкою у сокет, зменшуючи вимоги до смуги пропускання на 60–75%.

### 6. Метрики телеметрії та діагностичні пороги

Для запобігання втраті даних та вчасного виявлення аномалій операційні інженери налаштовують спостереження за такими ключовими показниками:

- **`replication_lag_seconds` (Gauge):** фізичний час затримки доставки та застосування журналу від конкретного піра. Поріг тривоги (Warning) становить понад 2.0 секунди, критичний поріг (Critical) — понад 10.0 секунд. Зростання свідчить про деградацію мережевого каналу або перевантаження дискової підсистеми репліки.
- **`replication_conflicts_total` (Counter):** сумарна кількість виявлених конфліктів за одиницю часу (Conflict Rate). Різкий спалах метрики сигналізує про збій у балансувальнику навантаження, через який запити одного клієнта почали надходити одночасно у два різні датацентри.
- **`replication_conflict_resolution_duration_seconds` (Histogram):** час, що витрачається обробниками на виконання SQL-процедур чи CRDT-злиття.
- **`replication_bytes_in_flight` (Gauge):** обсяг бінарного журналу, який перебуває в процесі передачі через міжрегіональний канал WAN.
- **`replication_active_siblings_count` (Gauge):** кількість записів у базі даних, що містять нерозв'язані паралельні гілки. Постійне накопичення siblings понад 1000 об'єктів свідчить про відсутність процесу фонового злиття з боку застосунку.
- **`replication_clock_skew_seconds` (Gauge):** поточна різниця фізичного часу між лідерами. Перевищення порогу 50 мілісекунд є критичним для систем на основі Last-Write-Wins.

### 7. Інструкції з ліквідації аварійних ситуацій (Runbooks)

#### Сценарій A: Подолання розриву через перевищення дрейфу часу (`ERR_BDR_CLOCK_SKEW`)
1. Перевірити стан системної служби синхронізації часу на проблемному вузлі командою `chronyc tracking` або `timedatectl status`.
2. Якщо виявлено десинхронізацію, перезапустити демон часу: `systemctl restart chrony`.
3. Перевірити, чи увійшов дрейф часу в межі `bdr.max_clock_skew_ms`.
4. Якщо з'єднання не відновилося автоматично, виконати примусовий перезапуск реплікаційного воркера: `SELECT bdr.node_group_resume();`.

#### Сценарій B: Очищення черги та розв'язання конфліктів при переповненні Siblings (`ERR_SIBLINGS_OVERFLOW`)
1. Визначити проблемні ключі запитом до таблиці статистики розгалужень.
2. Запустити адміністративний скрипт примусового схлопування гілок за правилом LWW.
3. Перевірити налаштування `max_siblings` у конфігурації рушія та збільшити виділену пам'ять для буфера злиття.
4. Перевірити роботу фонового воркера збирання надгробків (tombstone cleaner).

#### Сценарій C: Розбіжність схеми даних між регіональними лідерами (`ERR_SCHEMA_DIVERGENCE`)
1. Перевести реплікацію в режим паузи: `SELECT bdr.node_group_pause();`.
2. За допомогою утиліт порівняння схем (`pg_dump -s` або `mysqldump --no-data`) знайти відмінності у структурі таблиць між серверами.
3. Вручну виконати коригуючі DDL-запити на відстаючому вузлі для приведення схеми до канонічного вигляду.
4. Відновити двоспрямовану реплікацію: `SELECT bdr.node_group_resume();`.
