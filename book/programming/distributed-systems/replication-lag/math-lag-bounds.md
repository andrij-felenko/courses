# 🧮 Математична оцінка реплікаційного лагу та ймовірності застарілих читань

Щоб проєктувати розподілені сховища з асинхронною реплікацією без несподіваних деградацій продуктивності, необхідно кількісно оцінювати реплікаційний лаг як випадковий процес і вміти точно розраховувати ймовірність застарілих читань, квантилі затримки та оптимальний бюджет очікування транзакційних маркерів.

## Модель конвеєра реплікації як системи масового обслуговування

Конвеєр асинхронної реплікації між вузлом-лідером (Primary) та вузлом-реплікою (Follower) утворює класичну систему масового обслуговування.

Процес складається з двох основних випадкових потоків:
1. **Потік генерації транзакцій на лідері:** нові операції запису надходять у журнал випереджального запису (WAL) із середньою інтенсивністю `λ` транзакцій за секунду. Інтервали між фіксаціями транзакцій є незалежними випадковими величинами.
2. **Потік передачі та відтворення на репліці:** репліка зчитує потік журналу по мережі, парсить записи, захоплює необхідні блокування рядків у пам'яті та застосовує зміни до свого сховища з інтенсивністю `μ` транзакцій за секунду.

Для забезпечення стаціонарного режиму (щоб репліка не відставала нескінченно) пропускна здатність відтворення повинна перевищувати інтенсивність надходження: `μ > λ`.

Відношення цих величин визначає **коефіцієнт завантаження конвеєра реплікації** `ρ`:

```
ρ = λ ÷ μ
```

У стаціонарному режимі `0 < ρ < 1`. Величина `1 - ρ` визначає відносний запас продуктивності репліки, який використовується для компенсації тимчасових сплесків трафіку.

## Розподіл невідтвореного буфера в моделі M/M/1

Якщо інтервали між записами на лідері розподілені експоненційно з параметром `λ` (пуассонівський потік надходження), а час застосування транзакції на репліці є експоненційним із параметром `μ`, конвеєр описується моделлю `M/M/1`.

Позначимо через `Q(t)` кількість транзакцій, які вже зафіксовані лідером, але ще не відтворені реплікою на момент `t` (довжина черги реплікаційного відставання).

Імовірність того, що в черзі реплікації накопичилося рівно `k` невідтворених транзакцій (`k = 0, 1, 2, …`), виводиться зі стаціонарних рівнянь балансу станів:

```
P(Q = 0) = 1 - ρ                                  [ймовірність, що репліка повністю наздогнала лідер]
P(Q = k) = (1 - ρ) · ρᵏ                           [геометричний розподіл розміру черги]
```

Середня кількість невідтворених транзакцій у буфері репліки `E[Q]`:

```
E[Q]
= ∑_{k=0}^∞ k · (1 - ρ) · ρᵏ                      [означення математичного сподівання]
= (1 - ρ) · ρ · ∑_{k=1}^∞ k · ρᵏ⁻¹                [винесення множника (1 - ρ) · ρ]
= (1 - ρ) · ρ · (1 ÷ (1 - ρ)²)                    [сума похідної геометричного ряду]
= ρ ÷ (1 - ρ)                                     [скорочення спільного множника (1 - ρ)]
```

## Виведення розподілу часового лагу реплікації

Часовий реплікаційний лаг `L` — це випадкова величина, яка показує, на скільки секунд назад у часі зміщений поточний стан репліки відносно стану лідера. Фізично це час, який знадобиться репліці для послідовного застосування всіх `Q` накопичених у черзі транзакцій плюс залишковий час поточної транзакції.

За законом Літтла та властивостями експоненційної черги `M/M/1`, час очікування транзакції в черзі має неперервний розподіл зі спадною експоненційною щільністю.

Знайдемо ймовірність того, що реплікаційний лаг `L` перевищує довільне порогове значення `t` (`t ≥ 0`):

```
P(L > t)
= ∑_{k=1}^∞ P(Q = k) · P(застосування k транзакцій триває > t)   [формула повної ймовірності за довжиною черги]
= ∑_{k=1}^∞ (1 - ρ) · ρᵏ · e^(-μ·t) · ∑_{j=0}^{k-1} ((μ·t)ʲ ÷ j!) [ерлангівський розподіл суми k експоненційних величин]
= (1 - ρ) · e^(-μ·t) · ∑_{j=0}^∞ ((μ·t)ʲ ÷ j!) · ∑_{k=j+1}^∞ ρᵏ   [перегрупування подвійної суми за індексами j та k]
= (1 - ρ) · e^(-μ·t) · ∑_{j=0}^∞ ((μ·t)ʲ ÷ j!) · (ρʲ⁺¹ ÷ (1 - ρ)) [сума нескінченної спадної геометричної прогресії]
= ρ · e^(-μ·t) · ∑_{j=0}^∞ (ρ · μ · t)ʲ ÷ j!                     [скорочення (1 - ρ) та винесення коефіцієнта ρ]
= ρ · e^(-μ·t) · e^(ρ·μ·t)                                       [згортка ряду Тейлора для експоненти e^(ρ·μ·t)]
= ρ · e^(-μ·(1 - ρ)·t)                                           [додавання показників степенів]
```

Отриманий результат є **законом хвоста розподілу реплікаційного лагу**:

```
P(L > t) = ρ · e^(-μ·(1 - ρ)·t)
```

Інтегруючи хвіст розподілу від `0` до нескінченності, отримуємо середнє значення реплікаційного лагу `E[L]`:

```
E[L]
= ∫₀^∞ P(L > t) dt                                [інтегральна формула сподівання невід'ємної величини]
= ∫₀^∞ ρ · e^(-μ·(1 - ρ)·t) dt                    [підстановка виведеної функції хвоста]
= ρ · [- (1 ÷ (μ · (1 - ρ))) · e^(-μ·(1 - ρ)·t)]₀^∞ [первісна експоненційної функції]
= ρ · (0 - (- 1 ÷ (μ · (1 - ρ))))                 [обчислення на межах інтегрування]
= ρ ÷ (μ · (1 - ρ))                               [остаточний вираз для середнього лагу]
```

Дисперсія часового лагу `Var(L)`:

```
Var(L)
= E[L²] - (E[L])²                                 [загальне означення дисперсії через другий момент]
= (2 · ρ ÷ (μ² · (1 - ρ)²)) - (ρ² ÷ (μ² · (1 - ρ)²)) [обчислення другого моменту розподілу]
= (2 · ρ - ρ²) ÷ (μ² · (1 - ρ)²)                  [зведення до спільного знаменника]
```

З формули видно, що при наближенні коефіцієнта завантаження `ρ` до `1` (наприклад, коли швидкість надходження записів наближається до швидкості їх застосування), середній лаг зростає не лінійно, а гіперболічно як `1 ÷ (1 - ρ)`.

## Вплив дисперсії тривалості транзакцій: модель M/G/1

У реальних базах даних час застосування транзакції не є строго експоненційним. Прості оновлення окремих ключів виконуються за частки мілісекунди, тоді як пакетні операції (batch inserts або оновлення агрегатів) можуть займати сотні мілісекунд.

Нехай тривалість застосування транзакції є довільною випадковою величиною `S` із середнім значенням `E[S] = 1 ÷ μ` та дисперсією `Var(S) = σ²`.

За **формулою Поллачека — Хінчина**, середній розмір черги невідтворених транзакцій у системі `M/G/1` дорівнює:

```
E[Q]_{M/G/1}
= ρ + (λ² · σ² + ρ²) ÷ (2 · (1 - ρ))              [формула Поллачека — Хінчина для черги M/G/1]
```

Застосовуючи формулу Літтла `E[L] = E[Q] ÷ λ`, знаходимо середній реплікаційний лаг з урахуванням дисперсії тривалості транзакцій:

```
E[L]_{M/G/1}
= (1 ÷ μ) + (λ · σ² + ρ · (1 ÷ μ)) ÷ (2 · (1 - ρ)) [ділення довжини черги на інтенсивність надходження λ]
= (1 ÷ μ) · (1 + (ρ · (1 + C_v²)) ÷ (2 · (1 - ρ))) [винесення середнього часу обробки через коефіцієнт варіації]
```

де `C_v = σ ÷ E[S] = σ · μ` — коефіцієнт варіації часу застосування транзакцій.

Це рівняння показує критичний практичний ефект: **навіть якщо середня швидкість репліки `μ` залишається незмінною, наявність важких неоднорідних транзакцій із високою дисперсією `σ²` безпосередньо збільшує реплікаційний лаг у рази**.

## Ймовірність аномалії «читання після запису» (Stale Read Probability)

Нехай клієнт здійснив запис у момент часу `t₀`, отримав від лідера підтвердження успішної фіксації, а через інтервал `Δt` виконав читання оновленого запису.

Якщо запит на читання маршрутизується на випадкову репліку без передачі версійного маркера, клієнт побачить застарілий стан (порушення сесійної гарантії Read-Your-Writes) тоді й тільки тоді, коли лаг цієї репліки на момент читання перевищує інтервал `Δt`.

Для окремої репліки ймовірність застарілого читання `P(stale | Δt)`:

```
P(stale | Δt)
= P(L > Δt)                                       [умова застарілості даних на репліці]
= ρ · e^(-μ·(1 - ρ)·Δt)                           [підстановка закону розподілу хвоста лагу]
```

### Пул із N незалежних реплік

Якщо система містить пул із `N` однотипних реплік, і балансувальник навантаження розподіляє запити між ними, ймовірність того, що **всі N реплік одночасно відстають** більше ніж на `Δt`:

```
P(all_stale | Δt)
= ∏_{i=1}^N P(L_i > Δt)                           [незалежність процесів відтворення на різних репліках]
= (P(L > Δt))ᴺ                                    [однаковість параметрів реплік у пулі]
= (ρ · e^(-μ·(1 - ρ)·Δt))ᴺ                        [підстановка ймовірності відставання однієї репліки]
= ρᴺ · e^(-N · μ · (1 - ρ) · Δt)                  [піднесення до степеня N]
```

Ймовірність того, що в пулі знайдеться **хоча б одна репліка**, стан якої достатньо свіжий для задоволення запиту:

```
P(at_least_one_fresh | Δt)
= 1 - P(all_stale | Δt)                           [перехід до протилежної події]
= 1 - ρᴺ · e^(-N · μ · (1 - ρ) · Δt)              [підстановка виведеного виразу для всіх застарілих реплік]
```

## Розрахунок квантилів лагу для SLA свіжості

Для формулювання інженерних угод про рівень обслуговування (SLA) необхідно визначати граничні значення затримки, які покривають заданий відсоток запитів (наприклад, 95% або 99%).

Квантиль лагу `L_p` для заданої ймовірності `p` (`0 < p < 1`) визначається з рівняння:

```
P(L ≤ L_p) = p                                    [визначення квантиля функції розподілу]
```

Виведемо аналітичну формулу для `L_p`:

```
1 - P(L > L_p) = p                                [вираження через додаткову ймовірність хвоста]
1 - ρ · e^(-μ·(1 - ρ)·L_p) = p                    [підстановка закону розподілу хвоста]
ρ · e^(-μ·(1 - ρ)·L_p) = 1 - p                    [перенесення одиниці та зміна знаків]
e^(-μ·(1 - ρ)·L_p) = (1 - p) ÷ ρ                  [ділення обох частин на коефіцієнт завантаження ρ]
-μ · (1 - ρ) · L_p = ln((1 - p) ÷ ρ)              [натуральне логарифмування обох частин рівняння]
L_p = - ln((1 - p) ÷ ρ) ÷ (μ · (1 - ρ))           [ділення на від'ємний коефіцієнт -μ·(1 - ρ)]
L_p = ln(ρ ÷ (1 - p)) ÷ (μ · (1 - ρ))             [використання властивості -ln(a/b) = ln(b/a)]
```

### Покроковий розрахунковий приклад

Розглянемо високосервісну систему зі швидкістю запису `λ = 800` транзакцій/с та пропускною здатністю застосування WAL на репліці `μ = 1000` транзакцій/с.

1. **Розрахунок базових параметрів конвеєра:**
```
ρ = 800 ÷ 1000 = 0.80                             [коефіцієнт завантаження 80%]
1 - ρ = 1 - 0.80 = 0.20                           [відносний запас швидкості відтворення]
μ · (1 - ρ) = 1000 · 0.20 = 200                   [абсолютний надлишок пропускної здатності, tx/s]
```

2. **Середній реплікаційний лаг:**
```
E[L] = 0.80 ÷ 200 = 0.004 с = 4.0 мс              [середній час відставання репліки від лідера]
```

3. **95-й перцентиль лагу (`p = 0.95`):**
```
L_0.95
= ln(0.80 ÷ (1 - 0.95)) ÷ 200                     [підстановка параметрів у загальну формулу квантиля]
= ln(0.80 ÷ 0.05) ÷ 200                           [обчислення знаменника 1 - 0.95]
= ln(16.0) ÷ 200                                  [обчислення відношення 0.80 / 0.05]
= 2.772589 ÷ 200                                  [значення натурального логарифма ln(16)]
= 0.013863 с ≈ 13.9 мс                            [ділення на надлишок пропускної здатності 200]
```

4. **99-й перцентиль лагу (`p = 0.99`):**
```
L_0.99
= ln(0.80 ÷ (1 - 0.99)) ÷ 200                     [підстановка параметрів у формулу 99-го перцентиля]
= ln(0.80 ÷ 0.01) ÷ 200                           [обчислення знаменника 1 - 0.99]
= ln(80.0) ÷ 200                                  [обчислення відношення 0.80 / 0.01]
= 4.382027 ÷ 200                                  [значення натурального логарифма ln(80)]
= 0.021910 с ≈ 21.9 мс                            [кінцеве значення 99-го перцентиля лагу]
```

5. **99.9-й перцентиль лагу (`p = 0.999`):**
```
L_0.999
= ln(0.80 ÷ (1 - 0.999)) ÷ 200                    [підстановка параметрів у формулу 99.9-го перцентиля]
= ln(0.80 ÷ 0.001) ÷ 200                          [обчислення знаменника 1 - 0.999]
= ln(800.0) ÷ 200                                 [обчислення відношення 0.80 / 0.001]
= 6.684612 ÷ 200                                  [значення натурального логарифма ln(800)]
= 0.033423 с ≈ 33.4 мс                            [кінцеве значення 99.9-го перцентиля лагу]
```

### Наслідки деградації відтворення під час сплеску

Припустимо, що внаслідок запуску великого аналітичного запиту або блокування індексів продуктивність репліки знизилася на 15%: `μ_new = 850` транзакцій/с.

```
ρ_new = 800 ÷ 850 ≈ 0.941176                      [зростання завантаження репліки до 94.1%]
μ_new · (1 - ρ_new) = 850 · (1 - 0.941176) = 50.0 [запас продуктивності впав у 4 рази: з 200 до 50 tx/s]
E[L]_new = 0.941176 ÷ 50.0 ≈ 0.018824 с ≈ 18.8 мс  [середній лаг виріс майже у 5 разів]
```

Перерахуємо 99-й перцентиль за нових умов:

```
L_0.99_new
= ln(0.941176 ÷ 0.01) ÷ 50.0                      [підстановка нового завантаження у формулу]
= ln(94.1176) ÷ 50.0                              [обчислення аргументу логарифма]
= 4.544545 ÷ 50.0                                 [натуральний логарифм ln(94.1176)]
= 0.090891 с ≈ 90.9 мс                            [зростання 99-го перцентиля лагу з 21.9 мс до 90.9 мс]
```

Зниження продуктивності всього на 15% збільшило хвіст затримки більш ніж у 4 рази.

## Вплив мережевого транспорту та обмеження BDP

У розподілених географічних конфігураціях час затримки реплікації складається не лише з черги відтворення, але й із фізичної передачі байтів журналу по мережі.

Позначимо через `RTT` (англ. *Round-Trip Time*) час кругового обігу пакетів між лідером і реплікою, а через `B` — пропускну здатність мережевого каналу (в байтах за секунду).

Об'єм даних журналу, які генеруються за час одного кругового обігу, визначає добуток пропускної здатності на затримку (англ. *Bandwidth-Delay Product / BDP*):

```
BDP = B · RTT
```

Якщо розмір буфера сокета TCP `W_tcp` менший за `BDP`, протокол TCP обмежує швидкість відправлення сегментів через очікування підтверджень (ACK).

Середня мережева складова затримки передачі транзакції розміром `S_tx` байтів:

```
T_net
= (RTT ÷ 2) + (S_tx ÷ B)                          [сума односторонньої латентності та часу передачі пакетів]
```

Якщо мережевий канал має випадковий джитер (флуктуацію часу доставки) `J` із дисперсією `σ_net²`, сумарний реплікаційний лаг `L_total` стає сумою випадкових величин:

```
L_total = T_net + L_queue                         [сума мережевої затримки та часу очікування в черзі відтворення]
E[L_total] = E[T_net] + E[L_queue]                [адитивність математичного сподівання]
Var(L_total) = Var(T_net) + Var(L_queue)          [незалежність мережевих коливань від черги бази даних]
```

## Математична модель паралельного відтворення транзакцій (Parallel Apply)

Щоб збільшити продуктивність `μ` реплікаційного конвеєра, сучасні СКБД використовують багатопотокове застосування журналу (наприклад, Multi-Threaded Slave у MySQL або Parallel Logical Replication у PostgreSQL).

Нехай репліка має `M` паралельних робочих потоків. Транзакції розподіляються між потоками за хешем ключа або первинного ключа таблиці.

Якщо всі транзакції модифікують абсолютно незалежні записи, сумарна продуктивність репліки зростає у `M` разів: `μ_eff = M · μ₀`, де `μ₀` — продуктивність одного потоку.

Однак частина транзакцій `γ` (`0 ≤ γ ≤ 1`) мають спільні конфліктні рядки або глобальні блокування таблиць (наприклад, DDL), тому вони не можуть виконуватися паралельно і змушують усі `M` потоків чекати завершення бар'єру синхронізації.

За **законом Амдала**, ефективне прискорення відтворення `S(M)` дорівнює:

```
S(M)
= 1 ÷ (γ + ((1 - γ) ÷ M))                         [закон Амдала для системи з часткою послідовного коду γ]
```

Ефективна продуктивність пулу відтворення `μ_eff(M)`:

```
μ_eff(M)
= μ₀ · S(M)                                       [масштабування базової швидкості потоку]
= μ₀ ÷ (γ + ((1 - γ) ÷ M))                        [підстановка формули прискорення Амдала]
```

При необмеженому збільшенні кількості ядер (`M → ∞`) продуктивність відтворення на репліці асимптотично впирається в стелю, що визначається часткою конфліктних транзакцій `γ`:

```
lim_{M → ∞} μ_eff(M)
= μ₀ ÷ γ                                          [гранична пропускна здатність паралельного відтворення]
```

Це доводить, що за наявності хоча б 5% транзакцій із взаємними конфліктами блокувань (`γ = 0.05`), максимальна теоретична швидкість відтворення не може перевищити `μ₀ ÷ 0.05 = 20 · μ₀` незалежно від кількості процесорних ядер репліки.

## Імовірність відкату часу при немонотонному читанні

Розглянемо випадок, коли клієнт виконує два послідовні запити на читання до різних реплік `R₁` та `R₂`.

Перший запит надсилається на репліку `R₁` у момент часу `t₁` і повертає стан даних, що відповідає моменту `t₁ - L₁`.
Другий запит надсилається на репліку `R₂` у момент часу `t₂` (`t₂ > t₁`) і повертає стан даних, що відповідає `t₂ - L₂`.

Аномалія порушення монотонного читання (Monotonic Reads Anomaly) виникає, коли другий стан виявляється старішим за перший:

```
t₂ - L₂ < t₁ - L₁                                 [умова спостереження відкату часу назад]
L₂ - L₁ > t₂ - t₁                                 [різниця лагів перевищує інтервал між запитами]
```

Позначимо інтервал між запитами через `Δt = t₂ - t₁` (`Δt > 0`).

Якщо процеси відтворення на репліках `R₁` та `R₂` є незалежними однаково розподіленими експоненційними величинами із параметром `θ = μ · (1 - ρ)`, різниця лагів `D = L₂ - L₁` підпорядковується симетричному двосторонньому експоненційному розподілу (розподілу Лапласа).

Щільність розподілу різниці `f_D(x)` для `x ≥ 0`:

```
f_D(x)
= (θ ÷ 2) · e^(-θ · x)                            [щільність розподілу Лапласа для різниці експоненційних величин]
```

Імовірність того, що клієнт спостерігатиме відкат часу на величину більше `Δt`:

```
P(відкат | Δt)
= P(L₂ - L₁ > Δt)                                 [ймовірність порушення монотонності]
= ∫_{Δt}^∞ (θ ÷ 2) · e^(-θ · x) dx                [інтегрування хвоста щільності Лапласа]
= (1 ÷ 2) · e^(-θ · Δt)                           [обчислення інтеграла на нескінченності]
= (1 ÷ 2) · e^(-μ · (1 - ρ) · Δt)                 [підстановка параметра експоненційного хвоста θ]
```

Якщо клієнт надсилає другий запит майже миттєво після першого (`Δt → 0`), імовірність відкату на випадковій репліці дорівнює:

```
lim_{Δt → 0} P(відкат | Δt)
= (1 ÷ 2) · e⁰                                    [границя при нульовому інтервалі між читаннями]
= 1 ÷ 2 = 0.50                                    [50% ймовірність потрапити на більш відсталу репліку]
```

Це доводить, що без використання сесійних маркерів або прив'язки сесії (Sticky Session) рівно кожен другий швидкий запит між двома репліками призводить до спостереження відкату часу назад.

## Оптимізація таймауту очікування LSN (Wait-for-LSN Budget)

У маркерній схемі сесійної узгодженості маршрутизатор перевіряє `min_lsn` клієнта: якщо репліка відстає, запит блокується на репліці на час до `T_wait`. Якщо за цей час репліка не встигла наздогнати маркер, запит перенаправляється на Primary (або повертає помилку).

Нехай:
- `R_rep` — базова латентність читання з репліки без очікування;
- `R_pri` — латентність читання з лідера;
- `C_pri` — штраф за використання дефіцитної пропускної здатності Primary.

Частка запитів `α(T_wait)`, які вичерпують таймаут і перенаправляються на лідер:

```
α(T_wait)
= P(L > T_wait)                                   [ймовірність того, що лаг перевищить виділений бюджет часу]
= ρ · e^(-μ·(1 - ρ)·T_wait)                       [підстановка закону розподілу хвоста лагу]
```

Середній час очікування для запитів, які успішно дочекалися відтворення на репліці (`L ≤ T_wait`):

```
E[Wait | L ≤ T_wait]
= (∫₀^{T_wait} t · μ · (1 - ρ) · e^(-μ·(1 - ρ)·t) dt) ÷ (1 - e^(-μ·(1 - ρ)·T_wait))
= (1 ÷ (μ · (1 - ρ))) - (T_wait · e^(-μ·(1 - ρ)·T_wait)) ÷ (1 - e^(-μ·(1 - ρ)·T_wait))
```

Сумарна очікувана латентність сесійного читання:

```
E[Latency]
= (1 - α(T_wait)) · (R_rep + E[Wait | L ≤ T_wait]) + α(T_wait) · (T_wait + R_pri)
```

## Моделювання ймовірності конкурентних конфліктів у мультилідерній реплікації

Якщо система використовує кілька лідерських вузлів у різних дата-центрах (Multi-Leader Replication), реплікаційний лаг визначає ймовірність виникнення конкурентних конфліктів запису (англ. *write conflicts*).

Нехай у системі функціонують `K` незалежних лідерів. Кожен вузол `i` генерує операції запису над спільним простором ключів із пуассонівською інтенсивністю `λ_i`.

Час поширення оновлення між вузлами `i` та `j` позначимо як `Δt_{ij}`. Це вікно вразливості: якщо два різні користувачі модифікують один і той самий запис на різних лідерах протягом інтервалу `Δt_{ij}`, виникає конкурентний конфлікт, який неможливо впорядкувати за простим причинним слідуванням.

Нехай загальна кількість ключів у базі даних дорівнює `N_keys`, а звернення до ключів розподілені рівномірно.

Інтенсивність записів у конкретний ключ на вузлі `i`:

```
λ_{i, key} = λ_i ÷ N_keys                          [інтенсивність записів на один ключ]
```

Імовірність того, що протягом вікна реплікаційного лагу `Δt_{ij}` на вузлі `j` відбудеться хоча б один запис у той самий ключ:

```
P(конфлікт_{ij} | ключ)
= 1 - e^(-λ_{j, key} · Δt_{ij})                    [ймовірність хоча б однієї події в пуассонівському процесі]
= 1 - e^(-(λ_j ÷ N_keys) · Δt_{ij})                [підстановка інтенсивності для одного ключа]
```

Оскільки показник степеня `(λ_j ÷ N_keys) · Δt_{ij} \ll 1`, застосуємо лінійне наближення Тейлора `1 - e^(-x) ≈ x`:

```
P(конфлікт_{ij} | ключ)
≈ (λ_j · Δt_{ij}) ÷ N_keys                         [лінійне наближення Тейлора першого порядку]
```

Сумарна очікувана частота виникнення конфліктів запису у всій системі за секунду `Rate_{conflicts}`:

```
Rate_{conflicts}
= ∑_{i=1}^K ∑_{j \ne i} λ_i · P(конфлікт_{ij} | ключ) [сумування ймовірностей по всіх парах лідерів]
= ∑_{i=1}^K ∑_{j \ne i} (λ_i · λ_j · Δt_{ij}) ÷ N_keys [підстановка попарної ймовірності конфлікту]
```

Для симетричної системи з `K` однаковими лідерами (`λ_i = λ_0`) та середнім міжрегіональним лагом `Δt_{lag}`:

```
Rate_{conflicts}
= K · (K - 1) · (λ_0² · Δt_{lag}) ÷ N_keys         [спрощення для однорідного симетричного кластера]
```

### Практичний розрахунок для кластера з двома дата-центрами

Нехай система працює у двох регіонах: Франкфурт (`EU`) та Вірджинія (`US`).
- Міжрегіональний реплікаційний лаг `Δt_{lag} = 80 мс = 0.08 с`.
- Кожен регіон обробляє `λ_0 = 5000` записів за секунду.
- Гаряча підмножина активних сутностей містить `N_keys = 100000` записів.

Розрахуємо частоту конфліктів:

```
Rate_{conflicts}
= 2 · (2 - 1) · (5000² · 0.08) ÷ 100000            [підстановка значень у загальну формулу]
= 2 · 1 · (25000000 · 0.08) ÷ 100000              [піднесення до квадрата інтенсивності 5000²]
= 2 · (2000000) ÷ 100000                          [множення на інтервал лагу 0.08 с]
= 4000000 ÷ 100000                                [множення на кількість пар вузлів]
= 40.0 конфліктів за секунду                      [кінцева частота виникнення колізій]
```

## Розрахунок дискового буфера та ліміту утримання журналу (WAL Retention Bounds)

Під час аварійного обриву мережевого зв'язку або планового обслуговування репліка тимчасово перестає зчитувати потік оновлень. У цей період вузол-лідер зобов'язаний накопичувати всі згенеровані сегменти WAL на локальному диску (наприклад, через механізм слотів реплікації `replication slots` у PostgreSQL або `expire_logs_days` у MySQL).

Нехай:
- `λ` — середня швидкість генерації транзакцій на лідері (транзакцій за секунду);
- `s_tx` — середній розмір запису WAL на одну транзакцію (в байтах);
- `T_max_down` — максимально допустима тривалість недоступності репліки (в секундах), яку система має витримати без розриву реплікації.

Об'єм дискового простору `V_{WAL}`, який лідер накопичить за час простою `T_max_down`:

```
V_{WAL} = λ · s_tx · T_max_down                    [загальний об'єм накопиченого журналу в байтах]
```

Якщо дисковий простір, виділений під зберігання журналу на лідері, обмежений об'ємом `V_disk`, критичний час до вичерпання диска `T_critical` розраховується як:

```
T_critical = V_disk ÷ (λ · s_tx)                  [граничний час до аварійного переповнення диска]
```

Якщо за час `T_critical` зв'язок із реплікою не відновлюється, лідер стикається з дилемою:
1. Зупинити прийом нових операцій запису (повна відмова доступності для клієнтів через переповнення диска).
2. Примусово видалити старі сегменти WAL (інвалідація репліки, після чого її неможливо відновити звичайним доганянням журналу, і потрібен повний знімок бази даних `pg_basebackup` або відновлення з бекапу).

Для запобігання переповненню диска сучасні системи встановлюють поріг `max_slot_wal_keep_size`, який автоматично інвалідує відсталу репліку при досягненні 80% вільного дискового простору.
