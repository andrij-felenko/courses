# 🧮 Математичний аналіз затримок, розміру черги та дискового множника Outbox

Ця вставка містить формальний розрахунок середнього часу доставки повідомлень, умов стабільності черги вихідної скриньки при пуассонівському потоці подій та кількісне порівняння коефіцієнта дискового посилення запису (*Write Amplification*) для методів SQL-опитування та вилучення змін із журналу транзакцій (CDC).

## Модель наскрізної затримки доставки події

Розглянемо часовий інтервал від моменту фіксації транзакції застосунку в базі даних (`t_commit`) до моменту отримання підтвердження від брокера повідомлень (`t_broker_ack`).

У розподіленій системі загальна затримка є випадковою величиною, яка залежить від обраного механізму ретрансляції: синхронного очікування наступного такту опитування або асинхронного читання журналу випереджального запису.

### 1. Затримка при періодичному опитуванні (Polling Publisher)

Нехай фоновий воркер опитує таблицю `outbox` з фіксованим інтервалом `T_p` секунд (період опитування). Припустимо, що момент фіксації транзакції `t_commit` є випадковою величиною, рівномірно розподіленою на інтервалі опитування `[0, T_p]`.

Час очікування початку наступного циклу опитування `W` має неперервний рівномірний розподіл:

```
W ~ Uniform(0, T_p)
```

Математичне сподівання часу очікування становить:

```
E[W]
= (0 + T_p) / 2          [середнє значення рівномірного розподілу]
= T_p / 2
```

Повна середня затримка доставки `E[L_poll]` складається з часу очікування циклу `E[W]`, часу виконання SQL-запиту вибірки `T_query`, мережевого часу передачі в брокер `T_net`, часу фіксації брокером `T_ack` та часу видалення або оновлення рядка в базі `T_cleanup`:

```
E[L_poll]
= E[W] + T_query + T_net + T_ack + T_cleanup          [сума незалежних фаз]
= T_p / 2 + T_query + T_net + T_ack + T_cleanup      [підстановка E[W] = T_p / 2]
```

Для типових інженерних значень високопродуктивної системи (`T_p = 1.0` с, `T_query = 5` мс, `T_net = 2` мс, `T_ack = 5` мс, `T_cleanup = 4` мс) отримаємо:

```
E[L_poll]
= 1000 / 2 + 5 + 2 + 5 + 4                            [переведення T_p у мілісекунди]
= 500 + 16
= 516 мс
```

Головним лімітуючим фактором виступає сам період сну опитувача `T_p`. Спроба зменшити `T_p` до 10 мс призводить до того, що база даних зазнає 100 порожніх запитів на секунду від кожного вузла, що створює непродуктивне навантаження на процесор та блокувальні структури пам'яті СКБД.

### 2. Затримка при потоковому вилученні змін (CDC / WAL Tailing)

При використанні CDC відсутня фаза дискретного сну опитувача (`T_p = 0`). Щойно транзакція фіксується застосунком, рушій бази даних скидає сторінку журналу WAL на диск і миттєво сповіщає процес логічного декодування через механізм міжпроцесної синхронізації операційної системи.

Повна середня затримка доставки для CDC `E[L_cdc]` визначається сумою суто фізичних етапів конвеєра:

```
E[L_cdc]
= T_wal_flush + T_decode + T_net + T_ack             [сума неперервних кроків конвеєра]
```

де складові мають таку фізичну природу:
* `T_wal_flush` — тривалість синхронізації буфера журналу на енергонезалежний накопичувач за допомогою системного виклику `fdatasync` (зазвичай `0.5`–`2.0` мс для SSD/NVMe).
* `T_decode` — тривалість бінарного розбору запису плагіном `pgoutput` та його перетворення на внутрішній об'єкт Debezium (зазвичай `1.0`–`4.0` мс).
* `T_net` — час транзиту TCP-пакета від Kafka Connect до брокера Kafka (`1.0`–`3.0` мс).
* `T_ack` — час запису повідомлення в партицію Kafka з урахуванням конфігурації `acks=all` (`3.0`–`7.0` мс).

Підставивши емпіричні медіанні значення:

```
E[L_cdc]
= 1.5 + 2.5 + 2.0 + 5.0                               [сума складових у мілісекундах]
= 11.0 мс
```

Порівняння середніх затримок доставки демонструє виграш потокової ретрансляції:

```
E[L_poll] / E[L_cdc]
= 516 / 11.0                                          [відношення розрахованих значень]
≈ 46.9                                                [CDC швидший у ~47 разів]
```

## Динаміка черги та умова стійкості системи

Нехай події записуються в таблицю `outbox` пуассонівським потоком транзакцій з інтенсивністю `λ` подій за секунду.

Опитувач обробляє накопичені записи пачками розміром не більше `B` подій за один SQL-запит. Час повного циклу обробки складається з періоду сну та тривалості виконання запитів: `T_cycle = T_p + T_proc`, де `T_proc` — час виконання SQL-запитів вибірки, мережевої відправки та фіксації видалення.

Максимальна пропускна здатність опитувача `μ_max` (подій/с) обмежена розміром пачки:

```
μ_max
= B / (T_p + T_proc)                                  [гранична швидкість вивантаження]
```

### Умова збіжності черги за законом Літтла

Згідно з теорією масового обслуговування, черга вихідної скриньки залишається обмеженою в часі, а середній розмір черги стабільним тоді й тільки тоді, коли коефіцієнт завантаження системи `ρ` строго менший за одиницю:

```
ρ
= λ / μ_max                                           [визначення завантаженості системи]
= (λ · (T_p + T_proc)) / B                            [підстановка виразу для μ_max]
< 1                                                   [критерій ергодичності та стабільності]
```

З цієї нерівності випливає мінімально допустимий розмір пачки `B_min` для запобігання нескінченному накопиченню подій:

```
B_min
> λ · (T_p + T_proc)                                  [гарантія своєчасного очищення черги]
```

Якщо в системі генерується `λ = 500` подій/с, час сну становить `T_p = 0.2` с, а час обробки пачки `T_proc = 0.05` с, мінімальний розмір батчу повинен перевищувати:

```
B_min
> 500 · (0.2 + 0.05)                                  [підстановка числових параметрів]
= 500 · 0.25
= 125 рядків
```

### Фазовий перехід у режим метастабільного колапсу

Якщо вхідний потік подій тимчасово перевищує критичний поріг (`λ > μ_max`), кількість рядків у таблиці `outbox` починає зростати лінійно за законом:

```
Q(t)
= Q(0) + (λ - μ_max) · t                              [інтеграл дефіциту швидкості за час t]
```

При накопиченні `Q(t) > 100 000` рядків виникає ефект деградації багатоверсійного рушія бази даних (*MVCC Snapshot Degradation*). Запит `SELECT ... FOR UPDATE SKIP LOCKED` змушений перевіряти видимість транзакцій для величезної кількості мертвих кортежів, що збільшує `T_proc` від 5 мс до 150 мс.

Це спричиняє падіння реальної пропускної здатності `μ_max`, що ще сильніше прискорює накопичення черги `Q(t)`:

```
T_proc ↑  ⇒  μ_max ↓  ⇒  dQ/dt ↑  ⇒  T_proc ↑
```

Виникає небезпечна позитивна петля зворотного зв'язку, яка призводить до повного зависання бази даних.

## Посилення дискового запису (Write Amplification Analysis)

Кожна операція модифікації даних у реляційній СКБД спричиняє запис додаткових службових байтів на рівні сторінок таблиць, індексів та журналу транзакцій.

Коефіцієнт посилення запису (*Write Amplification, WA*) визначається як відношення сумарної кількості байтів, фізично записаних на диск, до корисного розміру збережених бізнес-даних `S_p`:

```
WA
= Total_Bytes_Written / S_p
```

### 1. Модель для Polling Outbox з видаленням рядків (Hard Delete)

Для кожної окремої події розміром `S_p` байтів рушій PostgreSQL виконує такі фізичні дії:
1. **Вставка (`INSERT`):** запис кортежу в сторінку даних (`S_p`), додавання покажчика в індекс первинного ключа `pk_outbox` (`S_idx`), додавання покажчика в індекс за часом `idx_outbox_polling` (`S_idx`), створення WAL-запису вставки (`S_wal_ins ≈ S_p + 120`).
2. **Видалення (`DELETE`):** модифікація заголовка кортежу для встановлення прапорця видалення (*tombstone*, `S_hdr ≈ 32`), створення WAL-запису видалення (`S_wal_del ≈ 80`).
3. **Очищення (`AutoVacuum`):** читання сторінки, вилучення мертвого кортежу, очищення вузлів обох індексів та генерація WAL-записів очищення (`S_vac ≈ S_p + 2 · S_idx`).

Сумарні дискові витрати на одну подію `IO_poll`:

```
IO_poll
= S_p + 2·S_idx + S_wal_ins + S_hdr + S_wal_del + S_vac
= S_p + 2·S_idx + (S_p + 120) + 32 + 80 + (S_p + 2·S_idx)  [розкриття складових витрат]
= 3·S_p + 4·S_idx + 232                                     [зведення подібних доданків]
```

Для типового розміру корисного навантаження `S_p = 512` байтів та розміру індексного запису `S_idx = 64` байти:

```
IO_poll
= 3 · 512 + 4 · 64 + 232
= 1536 + 256 + 232
= 2024 байти на одну подію
```

Коефіцієнт посилення запису при опитуванні:

```
WA_poll
= IO_poll / S_p                                       [відношення фізичного запису до корисного]
= 2024 / 512
≈ 3.95
```

### 2. Модель для CDC (Debezium) із секціонуванням таблиці

При використанні CDC вичитування змін відбувається безпосередньо з кільцевого буфера WAL у пам'яті без звернення до табличних сторінок. Якщо таблиця `outbox` розбита на секції за часом (наприклад, по одній секції на годину), старі події видаляються миттєвою операцією `DROP TABLE partition_name`:

1. **Вставка (`INSERT`):** запис рядка в сторінку даних (`S_p`) та запис у WAL (`S_wal_ins ≈ S_p + 120`). Оскільки SQL-запитів за часом немає, додатковий індекс `idx_outbox_polling` не створюється.
2. **Очищення (`DROP TABLE`):** операція змінює лише системний каталог, записуючи фіксовані `S_drop ≈ 2048` байтів метаданих на всю секцію з `N = 100 000` записів.
3. **AutoVacuum:** нуль витрат (секції видаляються цілком, дефрагментація не запускається).

Сумарні дискові витрати на одну подію для CDC `IO_cdc`:

```
IO_cdc
= S_p + S_wal_ins + (S_drop / N)                      [сума вставки та амортизованого видалення]
= 512 + (512 + 120) + (2048 / 100000)                 [підстановка параметрів]
= 512 + 632 + 0.02
= 1144.02 байти на одну подію
```

Коефіцієнт посилення запису для CDC:

```
WA_cdc
= IO_cdc / S_p                                        [визначення коефіцієнта для CDC]
= 1144.02 / 512
≈ 2.23
```

Порівняння фізичного навантаження на підсистему зберігання:

```
IO_poll / IO_cdc
= 2024 / 1144.02                                      [співвідношення дискового вводу-виводу]
≈ 1.77
```

Перехід від класичного опитування з поодиноким видаленням рядків до архітектури CDC із секціонуванням таблиці знижує сумарне навантаження на дисковий масив на 44%, усуває блокування таблиць та повністю ліквідує деградацію індексів.
