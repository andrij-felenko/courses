# 🧮 Математична модель місткості вхідної скриньки та ризику колізій

Утримання таблиці вхідної скриньки вимагає балансування двох взаємно протилежних інженерних вимог: забезпечення достатнього горизонту збереження для гарантованого відсікання запізнілих дублікатів та обмеження обсягу дискового простору, накладних витрат на індекси й фрагментації таблиць.

Нижче наведено математичні моделі накопичення даних, теорії черг для оцінки затримок, ймовірнісного ризику витоку зомбі-повторів, накладних витрат B-дерев при різних типах ключів та оптимізації вартості володіння сховищем.

## Модель накопичення обсягу сховища та закон Літтла

Нехай вхідний потік повідомлень надходить до системи з середньою інтенсивністю `λ` (повідомлень на секунду), середній розмір збереженого запису вхідної скриньки становить `m` байтів, а встановлений період збереження (Time-to-Live, TTL) дорівнює `T` секунд.

Швидкість накопичення нових сирих даних у неперервному часі:

```
R_write
= λ · m            [потік байтів у таблицю за одиницю часу]
```

Загальний обсяг даних у стаціонарному стані (після виходу фонового процесу очищення на регулярний баланс вилучення при `t ≥ T`):

```
S_table
= R_write · T      [інтеграл вхідного потоку за часовий інтервал T]
= λ · m · T        [підстановка швидкості запису]
```

З урахуванням закону Літтла (Little's Law) середня кількість активних записів у таблиці `L` дорівнює добутку інтенсивності надходження на середній час перебування запису в системі:

```
L
= λ · T            [закон Літтла: середня кількість рядків у таблиці]
```

Реальний дисковий простір СУБД додатково включає накладні витрати на обслуговування B-дерев первинного ключа та індексів опитування з коефіцієнтом `k_idx`, коефіцієнт заповнення сторінок `f` (fillfactor, де типово `0.7 ≤ f ≤ 0.85`), а також коефіцієнт фрагментації та версійності рядків (MVCC dead tuples) `k_mvcc`:

```
S_total
= S_table · (1 + k_idx) · (1 + k_mvcc) ÷ f
```

### Розрахунковий приклад для платіжного шлюзу

Припустимо, високонавантажений платіжний сервіс обробляє потік `λ = 1000` повідомлень/с. Середній розмір збереженого запису вхідної скриньки `m = 512` байтів (включаючи JSON-тіло події). Період збереження становить `14` днів (`T = 14 · 86400 = 1 209 600` секунд).

Розрахунок кількості рядків та стаціонарного обсягу таблиці:

```
L
= 1000 · 1209600
= 1209600000 записів          [1.2 мільярда рядків у таблиці]

S_table
= 1000 · 512 · 1209600
= 619315200000 байтів         [базовий обсяг сирих рядків]
≈ 619.3 ГБ                    [переведення в гігабайти]
```

При коефіцієнті індексів `k_idx = 0.5`, факторі MVCC `k_mvcc = 0.15` та заповненні сторінок `f = 0.8`:

```
S_total
= 619.3 · (1 + 0.5) · (1 + 0.15) ÷ 0.8
= 619.3 · 1.5 · 1.15 ÷ 0.8
= 1068.29 ÷ 0.8
≈ 1335.36 ГБ                  [близько 1.34 ТБ дискового простору]
```

Якщо оптимізувати схему та винести сирий JSON payload в окреме сховище (або стискати його), розмір рядка скорочується до `m_compact ≈ 64` байти (`message_id` + дата):

```
S_compact
= 1000 · 64 · 1209600 · 1.5 · 1.15 ÷ 0.8
≈ 166.9 ГБ                    [економія дискового простору у 8 разів]
```

## Накладні витрати B-дерев та розщеплення сторінок (Page Splits)

Характер генерації ідентифікаторів повідомлень `message_id` кардинально впливає на продуктивність операцій вставки та ступінь фрагментації сторінок пам'яті B-дерева.

1. **Випадкові ідентифікатори (UUIDv4):**
   При рівномірному випадковому розподілі ключів новий запис із однаковою ймовірністю потрапляє в довільний листок B-дерева. Коли сторінка розміром `B = 8192` байти заповнюється, відбувається її розщеплення навпіл (50/50 page split).
   У результаті середній коефіцієнт заповнення сторінок індексу прямує до асимптотичної константи:
   ```
   f_random
   ≈ ln(2)
   ≈ 0.693                    [лише 69.3% простору сторінки використовується корисно]
   ```
   Це призводить до розростання індексу на `1 ÷ 0.693 - 1 ≈ 44.3%` та постійного вимивання сторінок із буферного пулу (buffer pool thrashing).

2. **Монотонно зростаючі ідентифікатори (UUIDv7 / Snowflake ID / ULID):**
   Ключі містять префікс часу з мілісекундною точністю. Нові записи завжди додаються в крайній правий листок B-дерева. Сторінки заповнюються на 90–99% перед переходом до наступної без розщеплення проміжних вузлів:
   ```
   f_monotonic
   ≈ 0.95                     [95% корисного заповнення сторінки]
   ```

Зниження коефіцієнта підсилення запису (Write Amplification) при переході на монотонні ключі:

```
WA_ratio
= f_monotonic ÷ f_random
= 0.95 ÷ 0.693
≈ 1.37                        [на 37% менше дискових операцій запису індексу]
```

## Ймовірнісна модель зомбі-дублікатів

«Зомбі-повтором» називається аварійний випадок, коли дублікат повідомлення, надісланого в момент `t = 0`, надходить до споживача у момент `t_arrival > T_ttl`, коли оригінальний запис про попередню обробку вже видалено процедурою очищення таблиці.

Нехай час затримки доставки повторного повідомлення `X` є випадковою величиною з функцією розподілу ймовірностей `F(x) = P(X ≤ x)` та щільністю ймовірності `f(x)`.

Ймовірність того, що окреме повторне повідомлення запізниться понад встановлене вікно збереження `T_ttl`:

```
P_zombie
= P(X > T_ttl)
= 1 - F(T_ttl)                [хвіст розподілу затримки повторної доставки]
```

Якщо в розподіленій системі загальна частка повідомлень, що зазнають повторної доставки через тайм-аути або збої мережі, становить `p_dup`, то сумарна ймовірність помилкової повторної обробки (витоку дубліката) для довільного вхідного повідомлення дорівнює:

```
P_leak
= p_dup · P_zombie
= p_dup · (1 - F(T_ttl))      [добуток ймовірності дубля та ймовірності запізнення понад TTL]
```

Середня кількість інцидентів подвійної обробки `N_leak` за інтервал спостереження `t_obs`:

```
N_leak
= λ · t_obs · P_leak                  [загальна кількість інцидентів за інтервал спостереження]
= λ · t_obs · p_dup · (1 - F(T_ttl))  [розгортання формули витоку дублікатів]
```

### Моделювання затримок за розподілом Парето (Heavy-Tail Delays)

Затримки повторів при каскадних відмовах, довгих чергах відновлення та ручному переграванні з черг мертвих повідомлень (Dead Letter Queue, DLQ) мають важкий степеневий хвіст і описуються розподілом Парето з параметром форми `α` та мінімальним часом реакції `x_min`:

```
1 - F(T_ttl)
= (x_min ÷ T_ttl)^α           [для всіх T_ttl ≥ x_min]
```

Припустимо, мінімальний регламентний час підйому завислих черг становить `x_min = 1` година, параметр форми `α = 1.5`, частка повідомлень із повторами `p_dup = 0.001` (0.1%), а потік становить `λ = 1000` повідомлень/с.

Порівняємо два варіанти конфігурації TTL:

**Варіант 1: TTL = 24 години (1 доба)**

```
P_zombie(24h)
= (1 ÷ 24)^1.5
≈ 0.00851                     [0.85% повторів виходять за межі доби]

P_leak(24h)
= 0.001 · 0.00851
≈ 8.51 · 10⁻⁶                 [8.5 інцидентів на мільйон повідомлень]

N_leak_per_day
= 1000 · 86400 · 8.51 · 10⁻⁶
≈ 735.26                      [понад 700 подвійних списань на добу!]
```

**Варіант 2: TTL = 168 годин (7 діб)**

```
P_zombie(168h)
= (1 ÷ 168)^1.5
≈ 0.000459                    [0.046% повторів виходять за межі 7 діб]

P_leak(168h)
= 0.001 · 0.000459
≈ 4.59 · 10⁻⁷                 [менше 0.5 інцидентів на мільйон повідомлень]

N_leak_per_day
= 1000 · 86400 · 4.59 · 10⁻⁷
≈ 39.65                       [зменшення кількості колізій у 18.5 разів]
```

**Варіант 3: TTL = 720 годин (30 діб)**

```
P_zombie(720h)
= (1 ÷ 720)^1.5               [підстановка TTL = 720 у формулу Парето]
≈ 0.0000517                   [ймовірність затримки понад 30 днів]

P_leak(720h)
= 0.001 · 0.0000517           [множення на частку дублікатів]
≈ 5.17 · 10⁻⁸                 [ймовірність витоку на одне повідомлення]

N_leak_per_day
= 1000 · 86400 · 5.17 · 10⁻⁸  [розрахунок добової кількості інцидентів]
≈ 4.46                        [менше 5 поодиноких випадків на добу при гігантському потоці]
```

## Теорія черг для пулу конкурентних воркерів

У двоетапному асинхронному режимі (Staged Inbox) таблиця працює як багатоканальна система обслуговування типу `M/M/k` або `M/G/k`, де:
- `λ` — інтенсивність надходження повідомлень у таблицю;
- `μ` — середня швидкість обробки одним воркером (`1 ÷ μ` — середній час транзакції);
- `k` — кількість паралельних процесів-воркерів.

Умова стабільності системи (відсутність нескінченного росту беклогу):

```
ρ
= λ ÷ (k · μ) < 1             [коефіцієнт завантаження системи]
```

Мінімально необхідна кількість воркерів `k_min`:

```
k_min
> λ ÷ μ                       [гранична кількість обробників]
```

Якщо середня тривалість обробки транзакції `t_proc = 0.05` с (`μ = 20` завдань/с на потік), а вхідний потік `λ = 500` повідомлень/с:

```
k_min
> 500 ÷ 20
= 25 воркерів
```

Для забезпечення запасу надійності при сплесках трафіку з коефіцієнтом піку `k_peak = 2.0` та цільовим завантаженням `ρ_target = 0.7`:

```
k_target
= (λ · k_peak) ÷ (μ · ρ_target)
= (500 · 2.0) ÷ (20 · 0.7)
= 1000 ÷ 14
≈ 72 паралельних воркерів
```

## Функція оптимальної вартості володіння (TCO Optimization)

Вибір величини `T` можна сформулювати як задачу оптимізації цільової функції сумарних витрат `C_total(T)`, яка складається з вартості зберігання гігабайтів у хмарі та середніх фінансових втрат від інцидентів подвійної обробки:

```
C_total(T)
= C_storage(T) + C_incidents(T)
```

де:
- `C_storage(T) = c_byte · λ · m · T` — вартість оренди дискового простору за одиницю часу (де `c_byte` — вартість зберігання одного байта);
- `C_incidents(T) = c_loss · λ · p_dup · (x_min ÷ T)^α` — очікувані фінансові збитки від витоку дублікатів (де `c_loss` — середня вартість ліквідації одного інциденту подвійного списання).

Для знаходження мінімуму диференціюємо за `T` і прирівнюємо похідну до нуля:

```
d C_total / dT
= c_byte · λ · m - α · c_loss · λ · p_dup · x_min^α · T^(-α - 1)
= 0                           [умова екстремуму функції вартості]
```

Розв'язуючи відносно оптимального періоду `T*`:

```
c_byte · m
= α · c_loss · p_dup · x_min^α ÷ T^(α + 1)

T^(α + 1)
= (α · c_loss · p_dup · x_min^α) ÷ (c_byte · m)

T*
= [ (α · c_loss · p_dup · x_min^α) ÷ (c_byte · m) ]^(1 ÷ (α + 1))
```

Ця формула доводить: що вища ціна бізнес-помилки `c_loss` (наприклад, у банківському процесингу чи криптографічних реєстрах), то більшим зобов'язаний бути період зберігання `T*`, навіть якщо це вимагає додаткових витрат на масштабування дискового масиву.

## Детермінована інженерна межа

Для систем, де будь-яка повторна обробка є абсолютно неприпустимою (`c_loss → ∞`), горизонт збереження `T_ttl` повинен задовольняти строгу детерміновану нерівність:

```
T_ttl > T_backoff_max + T_dlq_sla + T_clock_skew
```

де:
- `T_backoff_max` — максимальний сумарний інтервал усіх автоматичних повторів клієнтів та брокерів;
- `T_dlq_sla` — граничний час реакції та регламентного повторного прогону завдань черги помилок інженерами підтримки;
- `T_clock_skew` — максимальне можливе розходження апаратних годинників серверів у розподіленому кластері.
