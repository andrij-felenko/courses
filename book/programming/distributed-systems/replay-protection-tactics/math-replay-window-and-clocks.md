# 🧮 Математичний розрахунок вікна захисту та розсинхронізації годинників

Надійність механізмів захисту від перегравання базується на строгих математичних обмеженнях двох параметрів: розміру ковзного вікна порядкових номерів `W` та тривалості часового вікна валідності `T_w`. Помилка в розрахунках призводить або до помилкового відхилення легітимних повідомлень (False Rejection), або до витоку пам'яті (Memory Exhaustion), або до прориву дедуплікації (Replay Leak).

## Модель мережевого джитеру та розмір бітмап-вікна

Нехай відправник генерує повідомлення зі строго монотонними порядковими номерами `seq ∈ {1, 2, 3, ...}` з інтенсивністю `λ` повідомлень на секунду.

Кожне повідомлення зазнає випадкової мережевої затримки передачі `D`, яка лежить у діапазоні між мінімальною та максимальною затримкою маршрутизації:

```
D_min ≤ D ≤ D_max
```

Мережевий джитер (розкид затримки доставки) визначається як:

```
J = D_max - D_min
```

Розглянемо два повідомлення: повідомлення `A` з номером `seq_A` та повідомлення `B` з номером `seq_B`, де `seq_B > seq_A`. Повідомлення `A` відправлено в момент часу `t_A`, а `B` — у момент `t_B = t_A + (seq_B - seq_A) / λ`.

Повідомлення `B` може випередити повідомлення `A` і прибути на приймач раніше, якщо `B` зазнає мінімальної затримки `D_min`, а `A` — максимальної затримки `D_max`. Час прибуття на приймач:

```
t_arr(A) = t_A + D_max
t_arr(B) = t_B + D_min = t_A + (seq_B - seq_A) / λ + D_min
```

Умова прибуття `B` раніше за `A` (`t_arr(B) < t_arr(A)`):

```
t_A + (seq_B - seq_A) / λ + D_min < t_A + D_max
(seq_B - seq_A) / λ < D_max - D_min
(seq_B - seq_A) < λ · (D_max - D_min)
Δ_seq < λ · J
```

Звідси випливає максимальна дистанція перевпорядкування `Δ_seq_max`, яку може зафіксувати приймач:

```
Δ_seq_max = ⌈λ · J⌉
```

Щоб легітимне повідомлення `A`, яке прибуло після повідомлення `B`, не було помилково відкинуте як застаріле (`diff ≥ W`), розмір ковзного вікна `W` зобов'язаний задовольняти фундаментальну нерівність:

```
W ≥ ⌈λ · J⌉ + 1
```

### Розрахунок параметрів для високонавантаженого каналу

**Вхідні дані:** Канал обробки фінансових котирувань із навантаженням `λ = 40 000` повідомлень/сек. Мінімальна затримка в мережі `D_min = 2.0` мс, максимальна затримка при пікових сплесках маршрутизації `D_max = 18.0` мс.

Обчислення мінімального розміру вікна `W`:

```
J = D_max - D_min
= 0.018 - 0.002           [підстановка граничних затримок D_max і D_min]
= 0.016 с (16 мс)         [величина мережевого джитеру J]

W_min = ⌈λ · J⌉ + 1
= ⌈40 000 · 0.016⌉ + 1    [підстановка інтенсивності потоку λ та джитеру J]
= ⌈640⌉ + 1               [обчислення добутку λ·J]
= 641 біт                 [теоретична нижня межа розміру вікна W]
```

**Висновок:** Стандартного 64-бітного вікна недостатньо: легітимні пакети будуть втрачатися. Необхідно застосувати багатослівний бітмап із `M` слів по 64 біти:

```
M = ⌈641 / 64⌉            [ділення мінімального розміру вікна на розмір слова]
= 11 слів (704 біти)      [округлення вгору до цілого числа слів]
```

Рекомендується обрати ступінь двійки `M = 16` слів (1024 біти), що забезпечує запас надійності `1024 / 640 = 1.6` (60% запасу по джитеру) за витрат пам'яті всього 128 байтів на сесію.

## Модель розсинхронізації годинників та розмір кешу Nonce

У протоколах прикладного рівня (REST API, gRPC) клієнт передає часову мітку `t_client` та випадкове число `nonce`. Сервер перевіряє потрапляння мітки в допустиме часове вікно `[t_server - Δ_t, t_server + Δ_t]` і зберігає `nonce` в оперативній пам'яті протягом часу `2 · Δ_t`.

Нехай абсолютна розбіжність між фізичним годинником клієнта та сервера обмежена похибкою синхронізації протоколу NTP:

```
|Clock_client - Clock_server| ≤ ε_clock
```

Максимальний мережевий час передачі запиту становить `RTT_max / 2`.

Щоб жоден легітимний запит не був відхилений через нормальний дрейф годинників або затримку в мережі, півширина вікна валідності `Δ_t` повинна задовольняти умову:

```
Δ_t ≥ ε_clock + (RTT_max / 2) + T_processing_margin
```

Якщо сервіс обробляє вхідний потік `λ` запитів на секунду, то середнє число активних унікальних значень `nonce`, які сервер зобов'язаний одночасно утримувати в оперативній пам'яті, становить:

```
N_nonce = λ · (2 · Δ_t)
```

### Розрахунок витрат пам'яті розподіленого кешу

**Вхідні дані:** Публічний платіжний API з інтенсивністю `λ = 10 000` запитів/сек. Похибка годинників клієнтів (мобільні додатки) `ε_clock = 120` секунд, максимальний мережевий таймаут `RTT_max / 2 = 10` секунд, запас `T_processing_margin = 20` секунд. Розмір одного запису в Redis (128-бітний UUID `nonce` + службові метадані хеш-таблиці) становить `S_entry = 96` байтів.

Обчислення півширини вікна та обсягу пам'яті:

```
Δ_t = ε_clock + (RTT_max / 2) + T_processing_margin
= 120 + 10 + 20           [додавання складових затримки та похибки годинників]
= 150 с                   [півширина вікна валідності (±2.5 хвилини)]

T_retention = 2 · Δ_t
= 2 · 150                 [подвоєння півширини для охоплення всього діапазону]
= 300 с (5 хв)            [повний час утримання ключа в кеші (TTL)]

N_nonce = λ · T_retention
= 10 000 · 300            [множення інтенсивності потоку на час утримання TTL]
= 3 000 000 ключів        [кількість одночасно збережених записів у кеші]

Memory_total = N_nonce · S_entry
= 3 000 000 · 96 байтів   [множення кількості ключів на розмір одного запису]
= 288 000 000 байтів      [загальний обсяг пам'яті у байтах]
= 274.65 МБ               [переведення байтів у мегабайти: 288 000 000 / 1024²]
```

**Висновок:** Використання часового вікна тривалістю 5 хвилин дозволяє обмежити пам'ять сховища дедуплікації фіксованим обсягом ~275 МБ незалежно від загальної кількості років роботи сервісу. Якби часове вікно не застосовувалося, за один рік обсяг бази дедуплікації досяг би:

```
315.36 · 10⁹ записів · 96 байтів = 30.27 ТБ
```

## Імовірність колізії випадкових одноразових чисел (Nonce)

Якщо `nonce` генерується клієнтом як випадкове двійкове число довжиною `b` бітів, простір можливих значень становить `V = 2ᵇ`.

За парадоксом днів народження (Birthday Paradox), імовірність виникнення хоча б однієї випадкової колізії `P_collision` (коли два різні легітимні клієнти випадково згенерують однаковий `nonce` всередині одного вікна `T_retention`) оцінюється формулою:

```
P_collision ≈ 1 - exp(- (N_nonce)² / (2 · V))
```

Розкладанням експоненти в ряд Тейлора при `(N_nonce)² ≪ 2 · V`:

```
P_collision ≈ (N_nonce)² / (2 · 2ᵇ)
```

Для 128-бітного числа (`b = 128`, `V = 2¹²⁸ ≈ 3.4 · 10³⁸`) та вибірки `N_nonce = 3 · 10⁶`:

```
(N_nonce)² = (3 · 10⁶)²
= 9 · 10¹²                [піднесення розміру вибірки до квадрата]

2 · 2¹²⁸ = 2¹²⁹
≈ 6.8 · 10³⁸              [обчислення знаменника для 128-бітного простору]

P_collision = (9 · 10¹²) / (6.8 · 10³⁸)
≈ 1.32 · 10⁻²⁶            [ділення чисельника на знаменник]
```

**Висновок:** Імовірність випадкової колізії для 128-бітного випадкового `nonce` (UUIDv4 або криптографічний токен CSPRNG) нескінченно мала і не створює ризику помилкового блокування легітимних запитів. Для 64-бітних `nonce` (`V = 2⁶⁴ ≈ 1.84 · 10¹⁹`) колізійна ймовірність склала б `P_collision ≈ 2.4 · 10⁻⁷`, що неприпустимо для платіжних систем високої надійності.

## Оптимізація пам'яті через генераційні фільтри Блума

Щоб зменшити витрати оперативної пам'яті на зберігання мільйонів ключів у Redis або локальному процесі, застосовують імовірнісні фільтри Блума (Bloom Filter).

Для множини з `n` елементів, бітового масиву розміром `m` бітів та `k` незалежних хеш-функцій імовірність хибнопозитивного спрацьовування `p` (коли нове повідомлення помилково вважається дублікатом) визначається як:

```
p ≈ (1 - exp(- (k · n) / m))ᵏ
```

Оптимальна кількість хеш-функцій `k`, яка мінімізує імовірність помилки `p` для фіксованого відношення `m / n`:

```
k_opt = (m / n) · ln(2) ≈ 0.69315 · (m / n)
```

Мінімально необхідний розмір бітового масиву `m` для забезпечення допустимої ймовірності помилки `p_target`:

```
m_min = - (n · ln(p_target)) / (ln(2))²
≈ - (n · ln(p_target)) / 0.48045
≈ - 2.08137 · n · ln(p_target)
```

### Розрахунок трипоколінного фільтра L1-дедуплікації

**Вхідні дані:** Потік `n = 10 000 000` повідомлень у межах активного вікна `T_w = 600` секунд. Допустима ймовірність хибного відхилення легітимного запиту `p_target = 10⁻⁶` (один хибний дублікат на мільйон транзакцій).

Розрахунок необхідного розміру пам'яті:

```
ln(p_target) = ln(10⁻⁶)
= -13.8155                [натуральний логарифм цільової ймовірності помилки]

m_min = - 2.08137 · 10 000 000 · (-13.8155)
= 287 551 777 бітів       [обчислення мінімальної кількості бітів за формулою]
= 35 943 972 байти        [ділення бітів на 8 для отримання байтів]
≈ 34.28 МБ                [переведення байтів у мегабайти: 35 943 972 / 1024²]

k_opt = (287 551 777 / 10 000 000) · 0.69315
= 28.755 · 0.69315        [множення питомої кількості бітів на ln(2)]
= 19.93 ≈ 20              [округлення до найближчого цілого числа хеш-функцій]
```

Щоб забезпечити неперервне витіснення застарілих елементів без повного блокування фільтра, пам'ять ділять на `G = 3` генерації (покоління): `F_current`, `F_previous`, `F_oldest`. Кожні `T_step = T_w / (G - 1) = 300` секунд найстаріший фільтр `F_oldest` скидається в нуль і стає новим `F_current`.

Сумарні витрати пам'яті для трипоколінного фільтра складають `3 · 34.28 МБ ≈ 102.8 МБ`, що дозволяє фільтрувати 10 мільйонів повідомлень за частки мікросекунди прямо в кеші другого/третього рівня (L2/L3) процесора.
