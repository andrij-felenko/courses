# 📜 Історія коміркової інженерії: від монолітів Amazon та eBay до архітектури Salesforce PODs та AWS Cells

У 1999 році сервіс електронної комерції eBay зіткнувся з непереборним бар'єром масштабування: монолітна база даних Oracle на сервері Sun Microsystems перестала витримувати обсяг транзакцій. Записи про користувачів, лоти аукціонів та історію ставок перебували в єдиному масиві дисків. Коли частота транзакцій перевищила фізичну пропускну здатність шини пам'яті та дискових контролерів, система почала зазнавати аварій, які тривали цілодобово. Класична відповідь індустрії — купівля потужнішого сервера — вичерпала себе, бо найпотужнішого на ринку комп'ютера більше не вистачало для пікового навантаження.

У цей самий період, на початку 2000-х років, інженери Amazon переживали аналогічну кризу зі своїм монолітним додатком `Obidos`. Спільна реляційна база даних блокувала паралельну розробку та обслуговування сотень тисяч одночасних кошиків покупців. Спроби побудувати єдиний гігантський розподілений кластер натрапили на фундаментальні фізичні обмеження: накладні витрати на підтримку мережевого консенсусу, переповнення пулів з'єднань і, що найнебезпечніше, стовідсотковий радіус ураження. Помилка в коді одного звіту або пошкоджений запис у спільній таблиці призводили до повної зупинки бізнесу на глобальному рівні.

## Народження концепції автономних блоків: Salesforce PODs (2006)

Перше масштабне і формалізоване впровадження коміркового підходу в комерційному секторі хмарного програмного забезпечення здійснила компанія Salesforce у 2006 році. Зростання корпоративної клієнтської бази вимагало гарантій ізоляції та надійності, яких не міг надати єдиний багатоорендарний моноліт.

Замість спроб нескінченно масштабувати єдиний розподілений кластер інженери Salesforce ввели поняття **POD (англ. *Point of Delivery* — пункт доставки)**. Кожен такий блок являв собою повністю автономний комплекс апаратного забезпечення, мережевих комутаторів, серверів додатків та кластера бази даних Oracle (згодом PostgreSQL), здатний самостійно обслуговувати фіксовану кількість корпоративних клієнтів (зазвичай від 5 000 до 10 000 організацій).

```
[Користувач / Браузер]
         │
         ▼
[Глобальний маршрутизатор (L7 Traffic Router)]
         │  (Перевірка організації: TenantID -> POD-042)
         ▼
 ┌────────────────────────────────────────────────────────┐
 │                      POD-042                           │
 │  ┌──────────────────────────────────────────────────┐  │
 │  │      Власний пул вебсерверів (App Servers)       │  │
 │  └──────────────────────────┬───────────────────────┘  │
 │                             │                          │
 │  ┌──────────────────────────▼───────────────────────┐  │
 │  │        Власна виділена база даних (RDBMS)        │  │
 │  └──────────────────────────────────────────────────┘  │
 └────────────────────────────────────────────────────────┘
```

Архітектура POD встановила ключові інженерні принципи, які згодом лягли в основу сучасних комірок:
- **Фіксований розмір одиниці:** кожен POD проектувався і тестувався на строго обмежену граничну ємність. Масштабування всієї компанії відбувалося не через збільшення існуючого блоку, а через розгортання нових (POD-1, POD-2, POD-3 тощо).
- **Ізоляція відмов:** збій апаратного забезпечення, аварія дискового масиву або фатальна помилка оновлення в межах POD-42 зачіпали лише клієнтів, закріплених за цим конкретним блоком. Решта POD продовжували роботу без жодних змін у затримках чи доступності.

## Криза масштабування Route 53 та революція клітинної архітектури AWS (2011–2014)

У 2011 році компанія Amazon Web Services зіткнулася з проблемою надійності при проектуванні глобальної служби доменних імен **Amazon Route 53** та служби управління ідентифікацією **AWS Identity and Access Management (IAM)**. Ці системи повинні були демонструвати доступність рівня п'яти дев'яток (99.999%), проте класичні архітектури з балансуванням навантаження виявлялися вразливими до розподілених атак на відмову в обслуговуванні (DDoS) та шкідливих запитів (англ. *poison pill queries*).

Якщо мільйон клієнтів використовує спільний пул DNS-серверів, зловмисна атака на одного клієнта переповнює вхідні мережеві черги, спричиняючи деградацію сервісу для всіх інших користувачів у глобальному масштабі.

Команда під керівництвом віцепрезидента та головного технічного директора Amazon Вернера Фоґельса (англ. *Werner Vogels*) розробила концепцію **клітинної архітектури (англ. *Cell-based Architecture*)**, поєднавши її з математичним механізмом **перемішаного шардування (англ. *Shuffle Sharding*)**.

У Route 53 кожному розміщеному клієнтському домену виділялася віртуальна комбінація з 4 різних серверів імен, вибраних із загального пулу з сотень фізичних вузлів. Завдяки комбінаторному вибуху ймовірність того, що атака на одного користувача призведе до відмови хоча б одного іншого клієнта, знизилася з 100% до сотих часток відсотка.

У 2018 році на щорічній конференції AWS re:Invent інженери AWS офіційно опублікували детальний опис клітинної моделі для критичних служб: Amazon DynamoDB, AWS STS та CloudFront. Ключовою тезою стало твердження: «Найкращий спосіб побудувати надійну велику систему — це побудувати безліч маленьких систем, які не знають про існування одна одної».

## Патерн «Штампи розгортання» від Microsoft Azure (2018–2020)

Паралельно з розвитком клітинних систем у AWS архітектори Microsoft Cloud Platform сформулювали патерн **«Штампи розгортання» (англ. *Deployment Stamps Pattern*)** у межах бібліотеки архітектурних шаблонів Azure Architecture Center.

Microsoft підійшла до проблеми з позиції інфраструктури як коду (англ. *Infrastructure as Code, IaC*). Поняття «штамп» підкреслювало процес виготовлення: замість ручного налаштування інфраструктури розробляється декларативний шаблон (ARM / Bicep / Terraform), який дозволяє однією командою «відштампувати» копію всієї виробничої системи в будь-якому регіоні світу або локальному датацентрі.

```
       [Декларативний опис штампу (IaC Template)]
                           │
         ┌─────────────────┼─────────────────┐
         ▼                 ▼                 ▼
  [Штамп №1 (AZ 1)] [Штамп №2 (AZ 2)] [Штамп №3 (AZ 3)]
   - Web App Fleet   - Web App Fleet   - Web App Fleet
   - Azure SQL       - Azure SQL       - Azure SQL
   - Service Bus     - Service Bus     - Service Bus
   - Key Vault       - Key Vault       - Key Vault
```

Підхід Microsoft стандартизував автоматизацію життєвого циклу штампів: створення тимчасових штампів для тестування під повним навантаженням, безпечні канарочні оновлення версій шляхом розгортання нового штампу поруч із діючим та поступове перенаправлення орендарів.

## Сучасний консенсус інженерії високих навантажень

Сьогодні комірковий підхід став стандартом проектування для платформ із десятками мільйонів користувачів:
- **Slack:** кожен корпоративний простір (Workspace) закріплюється за окремим клітинним екземпляром сервісів та сховищ.
- **Discord:** сервери спільнот (Guilds) розподілені між незалежними кластерами Elixir/Rust, де збій одного сервера чату фізично не здатний вплинути на інші гільдії.
- **Meta (Facebook):** регіональні автономні кластери (Prism) здатні повністю ізолюватися від глобальної мережі та функціонувати в режимі внутрішньої узгодженості під час міжконтинентальних розривів оптоволокна.

Історична еволюція довела: спроба побудувати єдину нескінченно масштабовану систему завжди програє дисципліні тиражування простих, надійно протестованих та повністю ізольованих одиниць розгортання.
