# 📋 Специфікація штампу розгортання та протокол управління станами комірки

Інтерфейс управління комірковою архітектурою визначає декларативну специфікацію інфраструктурного штампу (англ. *Cell Deployment Stamp*), протокол динамічної синхронізації таблиць маршрутизації та контракт скінченного автомата життєвого циклу комірки.

Кожна комірка розгортається автоматизовано як неподільний програмно-апаратний комплекс. Для забезпечення повної відтворюваності конфігурація описується декларативним маніфестом, який валідується оркестратором перед створенням фізичних або хмарних ресурсів.

## 1. Декларативна схема маніфесту штампу розгортання

Штамп розгортання являє собою єдиний опис інфраструктури, мережевих топологій, лімітів обчислювальних ресурсів, параметрів сховищ даних та політик життєвого циклу.

```yaml
apiVersion: architecture.distributed/v1alpha1
kind: DeploymentStamp
metadata:
  cellId: "cell-eu-central-042"
  region: "eu-central-1"
  availabilityZone: "eu-central-1a"
  version: "v2.14.0"
spec:
  capacity:
    maxTenants: 10000
    targetRPS: 25000
    maxDbConnections: 800
  network:
    ingressEndpoint: "https://ingress.cell-042.internal.net"
    internalSubnet: "10.142.0.0/16"
  services:
    - name: "api-gateway"
      replicas: 12
      cpuLimit: "4000m"
      memoryLimit: "8Gi"
    - name: "order-service"
      replicas: 24
      cpuLimit: "8000m"
      memoryLimit: "16Gi"
    - name: "payment-service"
      replicas: 16
      cpuLimit: "4000m"
      memoryLimit: "8Gi"
  storage:
    databaseCluster:
      engine: "postgresql"
      version: "16.2"
      instanceType: "db.r6g.4xlarge"
      storageGb: 2000
      maxConnections: 1000
    cacheCluster:
      engine: "valkey"
      clusterMode: true
      nodeCount: 6
      memoryPerNodeGb: 16
  lifecyclePolicy:
    drainTimeoutSeconds: 3600
    warmupDurationSeconds: 300
    healthCheckIntervalSeconds: 5
    leaseDurationSeconds: 60
```

### Семантика секцій та полів маніфесту штампу

1. **Секція метаданих (`metadata`):**
   - `cellId` — унікальний текстовий ідентифікатор комірки у глобальному реєстрі. Використовується маршрутизаторами та системами моніторингу для адресації та збору телеметрії.
   - `region` та `availabilityZone` — фізична локація розміщення. Жорстка прив'язка до зони доступності усуває міжзональні мережеві затримки та витрати на транзит трафіку в межах комірки.
   - `version` — фіксований ідентифікатор релізу всього програмного стека комірки. Зміна версії здійснюється не через оновлення компонентів на місці, а через розгортання нового штампу з наступною міграцією орендарів.

2. **Секція ємності та обмежень (`spec.capacity`):**
   - `maxTenants` — гранична кількість організацій (орендарів), яку дозволено реєструвати на даному штампі. При досягненні цього ліміту площина управління блокує нові призначення та ініціює створення наступної комірки.
   - `targetRPS` — розрахункова пропускна здатність (запитів за секунду), на яку откалібровані обчислювальні та дискові ресурси.
   - `maxDbConnections` — бюджет пулу TCP-з'єднань до бази даних, розподілений між усіма сервісами комірки. Гарантує, що сервіси не вичерпають доступні дескриптори ядра СУБД.

3. **Секція топології сервісів та сховищ (`spec.services`, `spec.storage`):**
   - Описує точну кількість реплік мікросервісів, ліміти процесорного часу (`cpuLimit`) та оперативної пам'яті (`memoryLimit`).
   - Параметри бази даних та розподіленого кешу містять жорстко зафіксовані обсяги оперативної пам'яті та кількості вузлів, що виключає випадковий дисбаланс між обчислювальними потужностями та швидкістю дискової підсистеми.

## 2. HTTP-протокол зондування здоров'я комірки (Cell Health Protocol)

Маршрутизатори комірок (Cell Routers) повинні безперервно відстежувати стан працездатності та рівень завантаженості кожного штампу для прийняття рішень про спрямування трафіку.

### Специфікація запиту зондування
- **HTTP-метод:** `GET`
- **Шлях:** `/v1/cell/status`
- **Обов'язкові заголовки:** `X-Router-ID: <ідентифікатор_маршрутизатора>`
- **Таймаут очікування відповіді:** 500 мілісекунд (жорсткий таймаут для запобігання підвисанню маршрутизатора).

### Формат тіла відповіді (`HTTP 200 OK`)
```json
{
  "cellId": "cell-eu-central-042",
  "state": "ACTIVE",
  "health": {
    "status": "HEALTHY",
    "cpuUtilization": 0.42,
    "memoryUtilization": 0.58,
    "dbConnectionPoolUsage": 0.35,
    "queueLagMs": 14
  },
  "capacity": {
    "assignedTenants": 8420,
    "currentRPS": 14200,
    "availableSlots": 1580
  },
  "timestamp": "2026-08-20T14:32:00.102Z"
}
```

### Алгоритм інтерпретації метрик здоров'я

Маршрутизатор аналізує поля відповіді за такими правилами:
1. Якщо `status` дорівнює `HEALTHY` і всі показники утилізації (`cpuUtilization`, `dbConnectionPoolUsage`) нижче 0.75, комірка вважається повноцінною і отримує повний обсяг вхідного трафіку.
2. Якщо `cpuUtilization > 0.85` або `dbConnectionPoolUsage > 0.90` протягом 3 послідовних опитувань, комірка автоматично переводиться у внутрішній статус `DEGRADED`. Маршрутизатор продовжує обслуговувати діючі сесії закріплених орендарів, але тимчасово не направляє на цю комірку запити в режимі перемішаного шардування (Shuffle Sharding), віддаючи перевагу дублюючим здоровим вузлам.
3. Якщо контролер повертає статус `state = "DRAINING"`, маршрутизатор негайно блокує реєстрацію нових сесій і пропускає лише повторні виклики з існуючими сесійними куками.
4. Якщо запит завершується таймаутом або повертає код помилки `5xx`, комірка позначається як `UNHEALTHY` і вилучається з активного балансування протягом 50 мілісекунд.

## 3. Протокол динамічного оновлення маршрутизації (Control Plane API)

Площина управління взаємодіє з розподіленими маршрутизаторами через механізм синхронізації таблиць відповідності орендарів.

### Ендпоінт прив'язки орендаря до комірок
Коли створюється нова організація або відбувається міграція, площина управління надсилає команду на маршрутизатори.

- **HTTP-метод:** `POST`
- **Шлях:** `/v1/routing/tenants/bind`
- **Тіло запиту:**
```json
{
  "tenantId": "org-acme-corp-99",
  "primaryCellId": "cell-eu-central-042",
  "shuffleShards": [
    "cell-eu-central-042",
    "cell-eu-central-018",
    "cell-eu-central-007"
  ],
  "routingEpoch": 10482,
  "action": "ACTIVATE"
}
```

Поле `routingEpoch` являє собою монотонно зростаючий лічильник версії правил. Якщо маршрутизатор отримує повідомлення з епохою, меншою за вже зафіксовану в його локальній пам'яті, запит відхиляється з кодом `409 Conflict`, що запобігає застосуванню застарілих правил у разі порушення порядку доставки мережевих пакетів.

## 4. Контракт виведення комірки з експлуатації та міграції орендарів

Процес виведення комірки з експлуатації (Cell Drain) виконується за суворою послідовністю кроків без переривання сервісу для користувачів.

```
 [1. Запит на дренаж] ──> [2. DRAINING у роутерах] ──> [3. Фонова реплікація БД]
                                                               │
 [6. TERMINATED (IaC)] <── [5. Атомне перемикання] <─── [4. Зупинка черг]
```

### Кроки протоколу міграції
1. **Ініціація дренажу:** Площина управління надсилає команду `POST /v1/lifecycle/cells/{cellId}/drain`. Стан комірки змінюється на `DRAINING`.
2. **Оновлення маршрутизаторів:** Маршрутизатори отримують повідомлення і перестають направляти трафік нових користувачів на цей штамп.
3. **Фонова синхронізація даних:** Дані орендарів копіюються з бази даних старої комірки до бази нової комірки за допомогою Change Data Capture (CDC).
4. **Злив асинхронних черг:** Внутрішні черги повідомлень опрацьовуються робочими пулами до нульового залишку (`queueLagMs = 0`).
5. **Атомне перемикання:** Площина управління розсилає оновлення маршрутизації з новою епохою (`routingEpoch++`). Усі подальші запити орендарів спрямовуються на новий штамп.
6. **Знищення штампу:** Після витримки захисного інтервалу (наприклад, 1800 секунд) інфраструктура старої комірки безповоротно видаляється.

## 5. Механізми лізингу та захист від розколу системи (Split-Brain Protection)

Для захисту від ситуацій, коли через мережеву ізоляцію стара комірка продовжує вважати себе активною і приймати записи під час міграції, застосовується механізм орендних сертифікатів (англ. *Cell Lease*).

Кожна активна комірка зобов'язана регулярно продовжувати свій сертифікат лізингу (`leaseDurationSeconds: 60`) у центральному консенсусному сховищі площини управління (etcd або DynamoDB). Якщо через мережевий розкол комірка втрачає зв'язок із площиною управління на час, що перевищує інтервал лізингу, її внутрішній шлюз (Cell Ingress) автоматично переходить у режим «тільки для читання» (`Read-Only Mode`), запобігаючи виникненню конфліктів даних і розбіжності реплік.

## 6. Коди помилок та заголовки спостережливості

Для забезпечення наскрізної діагностики кожен маршрутизатор та сервіс комірки додає стандартизовані HTTP-заголовки телеметрії:

| Заголовок HTTP | Опис та призначення |
| :--- | :--- |
| `X-Cell-ID` | Ідентифікатор комірки, яка фактично обробила даний запит. |
| `X-Router-ID` | Ідентифікатор вузла маршрутизації, що виконав первинне проксування. |
| `X-Routing-Strategy` | Стратегія маршрутизації (`DIRECT` або `SHUFFLE_SHARD`). |
| `X-Cell-Drain` | Прапорець (`true`/`false`), що сигналізує клієнту про перебування комірки у фазі дренажу. |

### Стандартні коди помилок маршрутизації
- `HTTP 429 Too Many Requests` (`Code: CELL_CAPACITY_EXCEEDED`): повертається, якщо цільова комірка досягла граничного ліміту `targetRPS` і скидає надлишковий трафік.
- `HTTP 307 Temporary Redirect` (`Code: CELL_DRAINING_REDIRECT`): інформує розумного клієнта про необхідність оновити адресу комірки під час планового дренажу.
- `HTTP 503 Service Unavailable` (`Code: NO_HEALTHY_CELLS_IN_SHARD`): виникає лише у винятковому випадку, коли всі `K` комірок з виділеного набору орендаря одночасно недоступні.
