# 📋 Специфікація інтерфейсу проміжного шару контролю допуску

Контроль допуску на практиці вбудовується як проміжний шар або перехоплювач (Middleware / Interceptor / Filter) на зовнішньому кордоні веб-сервісу, шлюзу API або у сервісній сітці (наприклад, у проксі Envoy чи Linkerd). Щоб підсистема допуску працювала стабільно, передбачувано та захищала ресурси без створення додаткових накладних витрат, взаємодія між мережевим транспортом і ядром контролера має підпорядковуватися суворому контракту.

Тут наведено повну структурну специфікацію цього інтерфейсу: моделі контексту вхідного запиту, структуру ухвалення рішення, правила формування діагностичних заголовків для протоколів HTTP та gRPC, обробники зворотного зв'язку телеметрії, механізми захисту від відмов самої підсистеми допуску та конфігураційний маніфест.

## 1. Модель контексту вхідного запиту

Перед тим як звернутися до підсистеми контролю допуску, мережевий шар сервісу зобов'язаний витягти метадані з протокольного пакета та сформувати контекст запиту. Головний принцип архітектурної безпеки полягає в тому, що рішення про допуск має ухвалюватися на найранішому етапі — до виділення динамічної пам'яті під тіло запиту (Request Body) та до запуску ресурсоємної десеріалізації корисного навантаження (JSON або Protobuf).

Контекст формується на основі заголовків протоколу та маршрутної інформації. Кожен запит обов'язково містить унікальний трасувальний ідентифікатор `request_id`, який витягується зі стандартного заголовка W3C TraceContext (`traceparent`) або генерується локально, якщо клієнт не надав інформації для трасування. Це дозволяє пов'язати подію відхилення на вході з подальшим аудитом у розподілених системах моніторингу.

Ідентифікатор орендаря або клієнта `tenant_id` витягується з токена авторизації (JWT), API-ключа або спеціального заголовка шлюзу. Це поле використовується для запобігання ситуації «галасливого сусіда» (Noisy Neighbor), коли надмірна активність одного споживача вичерпує ліміти всієї системи.

Рівень пріоритету `priority` класифікує важливість операції для бізнесу. Запит може належати до одного з трьох базових рівнів: критичний (`CRITICAL`), стандартний (`STANDARD`) або фоновий (`BACKGROUND`). Якщо заголовок пріоритету відсутній, маршрутизатор призначає пріоритет на основі конфігурації конкретного маршруту (наприклад, операції створення платежу автоматично маркуються як критичні).

Дедлайн запиту `deadline_ms` визначає абсолютну часову позначку, після якої клієнт гарантовано розірве з'єднання за таймаутом. Час обов'язково переводиться в шкалу монотонного годинника приймача під час читання заголовків, щоб уникнути збоїв через розбіжність системних годинників між різними серверами.

Вага вартості запиту `cost_weight` дозволяє враховувати нерівномірність ресурсоємності. За замовчуванням кожна операція має вагу `1.0`. Важкі аналітичні агрегації або запити, що модифікують великі обсяги даних у базі, отримують вагу `5.0` або `10.0`, резервуючи відповідну кількість слотів паралелізму.

Шлях маршруту `route_path` передається у нормалізованому вигляді (наприклад, `/api/v1/orders/{id}/pay`) для застосування специфічних лімітів конкретного ендпоінта.

| Поле | Тип | Обов'язкове | Опис і призначення |
| :--- | :--- | :--- | :--- |
| `request_id` | `String` | Так | Унікальний ідентифікатор виклику для наскрізного трасування (UUID або заголовок W3C `traceparent`). |
| `tenant_id` | `String` | Ні | Ідентифікатор організації або клієнта для перевірки договірних квот і запобігання монополізації ресурсів. |
| `priority` | `Enum` | Так | Рівень важливості операції: `CRITICAL` (платежі, авторизація), `STANDARD` (каталог), `BACKGROUND` (звіти). |
| `deadline_ms` | `Int64` | Ні | Абсолютний час монотонного годинника, після якого клієнт відмовиться від очікування. `0` — таймаут відсутній. |
| `cost_weight` | `Float32` | Ні | Оцінка відносної ресурсоємності операції. За замовчуванням `1.0`; важкі запити — `5.0` або `10.0`. |
| `route_path` | `String` | Так | Нормалізований шлях маршруту для застосування специфічних лімітів кінцевої точки. |

## 2. Контракт рішення про допуск (Admission Decision)

Функція перевірки допуску `evaluate_admission(context)` викликається синхронно на гарячому шляху мережевого стека. Її внутрішня реалізація не повинна виконувати блокуючих операцій вводу-виводу, звернень до дисків чи віддалених мережевих сервісів. Час ухвалення рішення має бути детермінованим і становити від 1 до 5 мікросекунд.

Результат перевірки повертає строго типізоване рішення з наступного переліку кодів:

```
enum AdmissionDecisionCode {
    ADMIT                   = 0,  // Допущено: виділено слот паралелізму в пулі потоків
    REJECT_OVERLOAD         = 1,  // Відхилено: загальне перевантаження сервера (ліміт in-flight вичерпано)
    REJECT_RATE_LIMIT       = 2,  // Відхилено: клієнт перевищив персональну квоту запитів на одиницю часу
    REJECT_TIMEOUT_EXPIRED  = 3,  // Відхилено: час очікування в черзі вже перевищив клієнтський дедлайн
    SHED_LOW_PRIORITY       = 4   // Відхилено: низький пріоритет скинуто для резервування ресурсів критичним викликам
}
```

Коли контролер повертає статус `ADMIT`, об'єкт рішення обов'язково містить валідний дескриптор дозволу `permit_handle`. Цей дескриптор фіксує монотонний час взяття завдання в роботу та тримає захоплений слот у лічильнику активного паралелізму `in_flight`. Мережевий шар зобов'язаний передати цей дескриптор разом із контекстом виконання та гарантувати його повернення при завершенні обробки.

Якщо контролер повертає будь-який код відмови (`REJECT_*` або `SHED_*`), об'єкт рішення містить розрахований інтервал відтермінування `retry_after_ms`. Цей інтервал обчислюється на основі поточної глибини перевантаження з обов'язковим додаванням випадкового джитеру (Jitter). Додатково повертається машинночитний та людиночитний опис причини відмови `rejection_reason` для формування системних журналів.

| Поле | Тип | Опис поведінки |
| :--- | :--- | :--- |
| `decision_code` | `AdmissionDecisionCode` | Головний вердикт. При `ADMIT` запит виконується; при інших кодах — негайно переривається. |
| `retry_after_ms` | `Int32` | Рекомендована затримка перед повтором у мілісекундах з урахуванням випадкового джитеру. |
| `rejection_reason` | `String` | Текстова мітка причини відмови для аудиту (наприклад, `sojourn_time_exceeded_deadline`). |
| `permit_handle` | `Handle` | Непрозорий дескриптор слота паралелізму. Обов'язково повертається після завершення операції. |

## 3. Протокольні заголовки та семантика кодів статусів

Формування мережевої відповіді при відхиленні запиту повинно суворо відповідати специфікаціям протоколів. Некоректне відображення кодів помилок може зруйнувати захист: якщо сервер поверне код `500 Internal Server Error` замість `503 Service Unavailable`, клієнтські бібліотеки можуть розцінити це як фатальний програмний збій бізнес-логіки та припинити повтори, або навпаки — не увімкнуть алгоритм адаптивного відтермінування.

Для протоколу HTTP при перевантаженні сервера повертається статус `503 Service Unavailable` разом із заголовком `Retry-After`. Якщо запит відхилено через вичерпання індивідуальної квоти клієнта, повертається статус `429 Too Many Requests`. Якщо ж запит провів у внутрішній черзі сервера більше часу, ніж дозволяв клієнтський таймаут, повертається код `504 Gateway Timeout` без заголовка повтору (оскільки дана конкретна спроба остаточно втратила сенс).

Для протоколу gRPC використовуються стандартизовані статус-коди з багатого набору помилок: код `UNAVAILABLE (14)` сигналізує про тимчасове перевантаження вузла та дозволяє балансувальнику перенаправити виклик на іншу репліку, код `RESOURCE_EXHAUSTED (8)` вказує на вичерпання квоти орендаря, а код `DEADLINE_EXCEEDED (4)` свідчить про спливання часу очікування.

| Код вердикту | HTTP статус | gRPC статус | Заголовок `Retry-After` | Семантика для клієнта |
| :--- | :--- | :--- | :--- | :--- |
| `ADMIT` | `200 OK` | `OK (0)` | Відсутній | Запит обробляється штатно. |
| `REJECT_OVERLOAD` | `503 Service Unavailable` | `UNAVAILABLE (14)` | Присутній | Сервер перевантажений. Балансувальник може обрати іншу ноду або почекати. |
| `REJECT_RATE_LIMIT` | `429 Too Many Requests` | `RESOURCE_EXHAUSTED (8)` | Присутній | Клієнт вичерпав квоту. Не перемикати на інші ноди; чекати вказаний інтервал. |
| `REJECT_TIMEOUT_EXPIRED` | `504 Gateway Timeout` | `DEADLINE_EXCEEDED (4)` | Відсутній | Запит протух у черзі. Повторювати лише якщо операція ще потрібна бізнесу. |
| `SHED_LOW_PRIORITY` | `503 Service Unavailable` | `UNAVAILABLE (14)` | Присутній | Сервер захищає критичне ядро. Фоновий виклик тимчасово скасовано. |

Діагностичні HTTP-заголовки дозволяють інженерам експлуатації та автоматизованим системам моніторингу аналізувати стан контролера допуску безпосередньо з мережевих трасувань:

```http
HTTP/1.1 503 Service Unavailable
Date: Thu, 20 Aug 2026 12:00:00 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 178
Connection: keep-alive
Retry-After: 2
X-Admission-Status: shed_low_priority
X-Admission-Current-Limit: 120
X-Admission-In-Flight: 115
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1718900002

{
  "error": "service_degraded_load_shedding",
  "message": "Non-critical request dropped due to server capacity protection.",
  "retry_after_seconds": 2,
  "request_id": "req-9b8c2d1e-4f3a"
}
```

## 4. Контракт спостережуваності та зворотного зв'язку (Feedback Telemetry)

Адаптивні алгоритми керування допуском базуються на динамічному зворотному зв'язку. Після того, як допущений запит завершив виконання, мережевий шар зобов'язаний повідомити підсистему допуску про тривалість обробки та код завершення.

Інтерфейс спостережуваності визначає два типи повідомлень:

```
interface AdmissionTelemetryObserver {
    // Викликається після завершення запиту, який отримав статус ADMIT
    void on_request_completed(
        Handle permit_handle,
        Int64 execution_time_us,     // Час безпосереднього виконання в мікросекундах
        Int64 queue_sojourn_time_us, // Час очікування в черзі до взяття в роботу
        Int32 status_code,           // HTTP або gRPC код результату
        Boolean is_backend_error     // Ознака збою внутрішньої залежності (бази, сховища)
    );

    // Викликається негайно при відхиленні запиту на вході
    void on_request_rejected(
        AdmissionDecisionCode reason,
        Enum priority,
        String tenant_id,
        String route_path
    );
}
```

Під час обробки результату діють суворі правила фільтрації сигналів:
1. **Ізоляція клієнтських помилок:** Помилки валідації користувацьких даних (HTTP `400 Bad Request`, `401 Unauthorized`, `404 Not Found`) не є ознакою перевантаження системи. Вони обробляються швидко і не повинні сприйматися алгоритмом адаптації як деградація продуктивності бекенду;
2. **Облік помилок бекенду:** Помилки типу `500 Internal Server Error`, `503` від внутрішніх мікросервісів або таймаути запитів до бази даних маркуються прапорцем `is_backend_error = true`. Алгоритм адаптації враховує зростання частки таких помилок як прямий сигнал для звуження ліміту паралелізму;
3. **Гарантія звільнення слотів:** Якщо під час виконання обробника сталася фатальна помилка або паніка процесу, блок перехоплення (try-finally або деструктор об'єкта `Permit`) зобов'язаний гарантовано викликати `on_request_completed()`, щоб запобігти витоку лічильника зайнятих ресурсів.

## 5. Обробка відмов підсистеми допуску: Fail-Open проти Fail-Closed

Окремий розділ контракту регулює поведінку проміжного шару у разі збою самого контролера допуску (наприклад, пошкодження пам'яті внутрішніх структур або виникнення взаємного блокування м'ютексів).

Контролер підтримує два взаємовиключні режими відмовостійкості:
- **Режим Fail-Open (Допуск за замовчуванням):** Якщо модуль допуску зазнає внутрішньої помилки, запит автоматично пропускається до обробника. Цей режим є обов'язковим для звичайних сервісів інтернет-користувачів, де краще ризикнути короткочасним перевантаженням, ніж повністю заблокувати роботу сайту через збій у службовому коді;
- **Режим Fail-Closed (Відмова за замовчуванням):** Якщо модуль допуску не може ухвалити рішення, запит безумовно відхиляється. Цей режим застосовується у фінансових та транзакційних системах високої критичності, де обслуговування запиту за невідомого стану системи може призвести до розриву консистентності або невідворотного пошкодження бази даних.

Для службових маршрутів платформи оркестрації (Liveness та Readiness проби Kubernetes `/healthz`, `/ready`) контроль допуску **завжди** працює в режимі безумовного пропуску (Bypass). Заборонено відхиляти проби життєздатності через перевантаження сервісу: якщо відхилити пробу `healthz`, Kubernetes вирішить, що контейнер завис, і примусово перезапустить його, спричинивши масове падіння всього кластера саме в момент найвищого піку трафіку.

## 6. Конфігураційний маніфест

Типова декларативна конфігурація модуля контролю допуску визначає поведінку черг, адаптивних лімітів та пріоритетів у форматі JSON або YAML:

```json
{
  "admission_control": {
    "enabled": true,
    "algorithm": "gradient_v2",
    "fail_mode": "fail_open",
    "bypass_routes": [
      "/healthz",
      "/ready",
      "/metrics"
    ],
    "concurrency_limits": {
      "initial_limit": 50,
      "min_limit": 10,
      "max_limit": 800,
      "headroom_factor": 1.15,
      "smoothing_factor": 0.1
    },
    "queue_management": {
      "max_queue_size": 250,
      "max_sojourn_time_ms": 75,
      "drop_strategy": "lifo_under_stress"
    },
    "priority_shedding": {
      "background_threshold_ratio": 0.80,
      "standard_threshold_ratio": 0.95,
      "critical_threshold_ratio": 1.00
    },
    "retry_policy": {
      "base_retry_delay_ms": 300,
      "max_retry_delay_ms": 3000,
      "jitter_percentage": 0.35
    }
  }
}
```

Чітке дотримання описаного контракту перетворює підсистему контролю допуску на надійний та прозорий ізолюючий бар'єр, який гарантує стабільну роботу прикладного коду за будь-якого зовнішнього навантаження.
