# 🧮 Математика черг, затримки та ймовірнісного допуску

Контроль допуску спирається на сувору математичну теорію масового обслуговування. Без розуміння того, чому затримка в системі зростає нелінійно при наближенні до насичення, будь-яке налаштування лімітів перетворюється на сліпе вгадування. Тут розібрано виведення формули затримки в системі M/M/1, багатоканальну систему M/M/c, наближення Кінгмана для довільних розподілів, зв'язок закону Літтла з паралелізмом, розрахунок граничного розміру черги та формулу адаптивного тротлінгу Google SRE.

## 1. Закон Літтла та паралелізм системи

У 1961 році Джон Літтл (John Little) довів фундаментальну теорему, яка пов'язує середню кількість завдань у стабільній системі з інтенсивністю їх надходження та середнім часом перебування:

```
L = λ · W
```

де:
- `L` — середня кількість запитів у системі (як тих, що очікують у черзі, так і тих, що зараз обробляються потоками);
- `λ` — середня інтенсивність вхідного потоку запитів (запитів за секунду, RPS);
- `W` — повний середній час перебування запиту в системі (від моменту надходження до повернення відповіді).

Якщо розділити систему на чергу очікування та безпосередній блок обробки (пул робочих потоків), закон Літтла розпадається на дві незалежні частини:

```
L_q = λ · W_q      [у черзі: середня довжина черги = потік · час очікування]
L_s = λ · W_s      [у процесорі: активні потоки = потік · час обробки]
```

Звідси випливає фундаментальний зв'язок для контролера допуску: **якщо сервіс має фіксовану кількість обчислювальних потоків `C`, максимальна теоретична пропускна здатність `μ` жорстко обмежена середнім часом виконання одного запиту `W_s`**:

```
μ = C / W_s        [гранична пропускна здатність при 100% завантаженні потоків]
```

**Приклад розрахунку:**
Якщо пул потоків сервера має розмір `C = 100` потоків, а середня тривалість обробки запиту (з урахуванням запитів до бази даних) становить `W_s = 50 мс = 0.05 с`, то максимальна пропускна здатність сервісу дорівнює:

```
μ = 100 / 0.05 = 2000 запитів/с
```

Будь-який вхідний потік `λ > 2000` неминуче спричинить нескінченне зростання черги `L_q`, якщо надлишкові запити не будуть відкинуті контролером допуску.

## 2. Модель М/М/1 і нелінійний вибух затримки

Розгляньмо класичну модель черги M/M/1 (пуассонівський вхідний потік з інтенсивністю `λ`, експоненційний розподіл часу обслуговування з інтенсивністю `μ`, один обслуговуючий канал або еквівалентний монолітний пул).

Коефіцієнт завантаження (утилізації) системи позначається як:

```
ρ = λ / μ          [утилізація системи, де 0 ≤ ρ < 1 для стабільного стану]
```

Ймовірність того, що в системі перебуває рівно `k` запитів, становить:

```
P(k) = (1 − ρ) · ρᵏ
```

Середня кількість запитів у системі `L` обчислюється як сума нескінченного ряду:

```
L = ∑ [k=0..∞] k · P(k)
= (1 − ρ) · ∑ [k=0..∞] k · ρᵏ
= (1 − ρ) · (ρ / (1 − ρ)²)       [сума похідної геометричної прогресії]
= ρ / (1 − ρ)                    [середнє число запитів у системі]
```

Застосовуючи закон Літтла `W = L / λ`, знаходимо повний час перебування запиту в системі:

```
W = L / λ
= (ρ / (1 − ρ)) / λ              [підставляємо вираз для L]
= ( (λ / μ) / (1 − λ / μ) ) / λ  [розкриваємо ρ = λ / μ]
= 1 / (μ − λ)                    [середній повний час перебування]
= (1 / μ) / (1 − ρ)              [час обробки, помножений на коефіцієнт роздуву]
```

Час очікування суто в черзі `W_q` дорівнює повному часу мінус час безпосереднього виконання `1 / μ`:

```
W_q = W − (1 / μ)                    [від повного часу віднімаємо час виконання]
= (1 / (μ − λ)) − (1 / μ)            [підставляємо повний час W з моделі M/M/1]
= (μ − (μ − λ)) / (μ · (μ − λ))      [зведення до спільного знаменника]
= λ / (μ · (μ − λ))                  [спрощення чисельника: μ − μ + λ = λ]
= (ρ / (1 − ρ)) · (1 / μ)            [час у черзі як функція завантаження ρ = λ/μ]
```

**Ключовий висновок:** залежність часу очікування від завантаження `ρ` є гіперболічною. Розрахуємо приріст часу очікування відносно базового часу виконання `W_0 = 1 / μ`:

```
ρ = 0.50 (50% CPU)  →  W_q = (0.50 / 0.50) · W_0 = 1.0 · W_0    (час очікування = 1x часу виконання)
ρ = 0.80 (80% CPU)  →  W_q = (0.80 / 0.20) · W_0 = 4.0 · W_0    (час очікування = 4x часу виконання)
ρ = 0.90 (90% CPU)  →  W_q = (0.90 / 0.10) · W_0 = 9.0 · W_0    (час очікування = 9x часу виконання)
ρ = 0.95 (95% CPU)  →  W_q = (0.95 / 0.05) · W_0 = 19.0 · W_0   (час очікування = 19x часу виконання)
ρ = 0.99 (99% CPU)  →  W_q = (0.99 / 0.01) · W_0 = 99.0 · W_0   (час очікування = 99x часу виконання)
```

При зростанні завантаження з 80% до 95% затримка в черзі збільшується майже в 5 разів. Якщо контролер допуску не відсікає запити до перетину позначки `ρ ≈ 0.85–0.90`, черга миттєво поглинає весь часовий бюджет клієнта.

## 3. Багатоканальні системи M/M/c та формула Erlang C

Реальний веб-сервер або кластер містить не один, а `c` паралельних робочих потоків або серверних інстансів. Така система моделюється чергою M/M/c з інтенсивністю обслуговування кожного каналу `μ` та загальним навантаженням `A = λ / μ`. Загальний коефіцієнт утилізації дорівнює:

```
ρ = λ / (c · μ) = A / c
```

Ймовірність того, що новий запит застане всі `c` каналів зайнятими й буде змушений стати в чергу очікування, описується формулою **Erlang C**:

```
C(c, A) = (Aᶜ / (c! · (1 − ρ))) / ( ∑ [k=0..c-1] (Aᵏ / k!) + (Aᶜ / (c! · (1 − ρ))) )
```

Середній час очікування в черзі для системи M/M/c виражається через формулу Erlang C:

```
W_q = C(c, A) / (c · μ − λ)          [визначення через імовірність очікування Erlang C]
= C(c, A) / (c · μ · (1 − ρ))        [винесення c·μ за дужки: 1 − λ/(c·μ) = 1 − ρ]
= (C(c, A) / c) · (ρ / (1 − ρ)) · (1 / μ) [розклад на множник системи та роздув черги]
```

При великій кількості паралельних каналів `c` (наприклад, `c = 64` ядра) система демонструє набагато крутіший фазовий перехід («коліно затримки»): поки `ρ < 0.85`, черга майже завжди порожня (`C(c, A) ≈ 0`), але при переході за `ρ > 0.92` затримка вибухає навіть швидше, ніж у системі M/M/1.

## 4. Вплив варіативності: наближення Кінгмана (G/G/1)

У реальних додатках час виконання запитів не підпорядковується ідеальному експоненційному розподілу. Важкі запити до бази даних або паузи збирача сміття створюють високу дисперсію.

Для систем із довільним розподілом інтервалів приходу та часу обслуговування (черга G/G/1) Джон Кінгман (John Kingman) у 1961 році вивів знамениту наближену формулу для середнього часу в черзі:

```
W_q ≈ (ρ / (1 − ρ)) · ( (C_a² + C_s²) / 2 ) · (1 / μ)
```

де:
- `C_a = σ_a / E[a]` — коефіцієнт варіації інтервалів між приходами запитів (міра пачковості вхідного трафіку);
- `C_s = σ_s / E[s]` — коефіцієнт варіації тривалості виконання запитів (міра неоднорідності завдань).

### Фізичний зміст формули Кінгмана:
1. Час очікування в черзі пропорційний квадрату коефіцієнтів варіації `(C_a² + C_s²) / 2`;
2. Якщо сервіс має високий розкид затримки (наприклад, важкі звіти та швидкі читання виконуються в одному пулі, де `C_s = 3.0`), множник варіативності становить `(1 + 9) / 2 = 5.0`;
3. Це означає, що при однаковій утилізації `ρ = 0.8` черга з високою дисперсією буде **в 5 разів довшою**, ніж черга з передбачуваним часом виконання.

Контролер допуску запобігає цій проблемі шляхом ізоляції пулів (Bulkhead) та відсікання важких запитів на основі динамічної ваги `cost_weight`.

## 5. Модель корисної пропускної здатності (Goodput) під таймаутом

Нехай кожен клієнт встановлює жорсткий таймаут `T_out`. Якщо повний час очікування та виконання `W` перевищує `T_out`, клієнт обриває з'єднання. Робота, виконана сервером після спливання `T_out`, є марною (*wasted work*).

У системі M/M/1 повний час перебування `t` розподілений за експоненційним законом із параметром `(μ − λ)`. Ймовірність того, що запит успішно завершиться в межах таймауту, становить:

```
P(t ≤ T_out) = 1 − e^(−(μ − λ) · T_out)
```

Корисна пропускна здатність системи (Goodput, `G`) — це кількість запитів за секунду, які не лише оброблені сервером, а й встигли повернутися клієнту до таймауту:

```
G(λ) = λ · P(t ≤ T_out) = λ · (1 − e^(−(μ − λ) · T_out))
```

Дослідимо поведінку `G(λ)` при наближенні `λ` до точки насичення `μ`:

```
lim [λ → μ] G(λ)
= μ · (1 − e^(0))                [бо (μ − λ) → 0]
= μ · (1 − 1)
= 0                              [колапс корисної пропускної здатності]
```

**Математичний парадокс:** при перевантаженні (`λ ≥ μ`) процесор зайнятий на 100% (сира пропускна здатність Throughput дорівнює `μ`), але корисна пропускна здатність Goodput спадає до нуля, оскільки 100% запитів перевищують таймаут `T_out` під час очікування в черзі.

Контролер допуску штучно фіксує ефективну інтенсивність входу `λ_admitted ≤ λ_opt < μ`, що максимізує `G(λ)`:

```
G_max ≈ μ · (1 − e^(−(μ − λ_opt) · T_out))
```

де надлишок `λ − λ_admitted` миттєво відхиляється на вході за час `t ≈ 0`.

## 6. Розрахунок граничного розміру черги (Queue Limit)

Щоб запобігти прийому запитів, які неминуче перевищать допустимий час очікування `T_wait_max`, контролер допуску обмежує максимальну глибину черги `Q_max`.

Зв'язок між глибиною черги `Q`, швидкістю обробки `μ` та максимальним часом очікування `T_wait_max` випливає з детермінованого розвантаження черги:

```
T_wait = Q / μ
```

Звідси максимальний дозволений розмір черги становить:

```
Q_max = ⌊ μ · T_wait_max ⌋
```

**Приклад розрахунку:**
Сервіс обробляє `μ = 1000` запитів/с. Допустимий час очікування в черзі до початку виконання не повинен перевищувати `T_wait_max = 50 мс = 0.05 с` (щоб залишити 150 мс на виконання та мережу при клієнтському таймауті 200 мс).

```
Q_max = 1000 · 0.05 = 50 запитів
```

Якщо в черзі вже є 50 запитів, 51-й запит, поставлений у хвіст черги, гарантовано проведе в ній понад 50 мс. Контролер допуску зобов'язаний відкинути його миттєво (*Tail Drop* або *Early Drop*), не ставлячи в буфер.

## 7. Формула адаптивного тротлінгу Google SRE

Для захисту бекенду від лавиноподібного перевантаження при повторних спробах клієнтів (Retry Storms) інженери Google розробили ймовірнісну модель контролю допуску на стороні клієнта (*Client-side Adaptive Throttling*).

Клієнтська бібліотека в ковзному вікні (наприклад, за останні 120 секунд) підраховує:
- `requests` — загальну кількість запитів, відправлених додатком;
- `accepts` — кількість запитів, успішно прийнятих і оброблених бекендом (відповіді без кодів перевантаження).

Ймовірність локального відкидання нового запиту `P_drop` обчислюється за формулою:

```
P_drop = max( 0, (requests − K · accepts) / (requests + 1) )
```

де `K` — мультиплікатор агресивності допуску (зазвичай `K = 2.0` або `K = 1.5`).

### Аналіз поведінки формули:

1. **Штатний режим:**
   Якщо бекенд приймає всі запити (`accepts = requests`), то при `K = 2`:
   ```
   P_drop = max(0, (requests − 2 · requests) / (requests + 1))
          = max(0, −requests / (requests + 1))
          = 0                      [жоден запит не відкидається]
   ```

2. **Початок відмов:**
   Клієнт продовжує надсилати 100% трафіку, доки частка успішних відповідей перевищує `1 / K`:
   ```
   requests − K · accepts ≤ 0
   accepts / requests ≥ 1 / K      [поріг увімкнення тротлінгу]
   ```
   При `K = 2` клієнт дозволяє бекенду відхиляти до 50% запитів без увімкнення клієнтського дропання.

3. **Глибоке перевантаження:**
   Якщо бекенд перевантажений і приймає лише 100 запитів із 1000 (`requests = 1000`, `accepts = 100`, `K = 2`):
   ```
   P_drop = (1000 − 2 · 100) / (1000 + 1)
          = (1000 − 200) / 1001
          = 800 / 1001
          ≈ 0.799 (79.9% запитів відкидаються локально)
   ```
   Клієнт пропустить до сервера лише `1000 · (1 − 0.799) ≈ 201` запит, що точно відповідає пропускній здатності сервера `K · accepts = 200` з невеликим запасом для перевірки його відновлення.

## 8. Зважений розподіл ємності за пріоритетами

Коли система працює в режимі дефіциту ресурсів (`λ > μ`), контролер допуску ділить доступну ємність `μ` між різними класами пріоритетів `P_i`.

Нехай вхідний потік розділений на три класи пріоритетів:
- `λ_1` — критичний трафік (платежі, авторизація);
- `λ_2` — стандартний трафік (показ контенту);
- `λ_3` — фоновий трафік (аналітика, асинхронні індексації).

```
λ_total = λ_1 + λ_2 + λ_3
```

Політика допуску гарантує виділення квот `C_i` таких, що:

```
C_1 + C_2 + C_3 = μ
```

Ймовірність допуску запиту класу `i` обчислюється ступінчасто:

```
P_admit(1) = min(1, μ / λ_1)
P_admit(2) = min(1, max(0, μ − λ_1) / λ_2)
P_admit(3) = min(1, max(0, μ − λ_1 − λ_2) / λ_3)
```

Якщо критичний потік `λ_1` повністю вичерпує ресурс системи (`λ_1 ≥ μ`), то:
```
P_admit(1) = μ / λ_1
P_admit(2) = 0
P_admit(3) = 0
```
Фоновий та стандартний трафік повністю скидаються на кордоні, дозволяючи зберегти працездатність критичного ядра системи.
