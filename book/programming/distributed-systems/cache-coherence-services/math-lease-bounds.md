# 🧮 Математичні межі застарілості кешу та розрахунок часу оренди

Підтримання когерентності розподіленого кешу за допомогою асинхронних повідомлень завжди пов'язане з часовими затримками в мережі, чергах брокерів та конвеєрах вилучення змін (CDC). Щоб гарантувати захист від отруєння кешу застарілими даними й мінімізувати навантаження на базу даних, параметри оренди (*lease timeout*) та вікна узгодженості необхідно розраховувати на основі ймовірнісних розподілів затримок.

Коли архітектор обирає між простою інвалідацією та орендою, ключовим критерієм є математична оцінка двох конкуруючих ризиків: імовірності збереження застарілого зрізу (*stale-overwrite probability*) та імовірності відхилення легітимного запису через занадто короткий тайм-аут оренди.

## Модель часового вікна застарілості (Staleness Window)

Розглянемо часову шкалу подій, коли клієнт модифікує стан сутності в первинній СКБД, а інші сервіси продовжують читати дані з локальних кешів або реплік.

Позначимо ключові випадкові величини та параметри системи:
* `t₀` — момент часу, коли клієнт-читач ініціював запит до бази даних при кеш-промаху;
* `T_db` — тривалість виконання SQL-запиту читання в базі даних (випадкова величина з функцією розподілу `F_db(t)`);
* `t_w` — момент фіксації транзакції запису (COMMIT) у первинній СКБД (`t_w ≥ t₀`);
* `T_cdc` — затримка вилучення події транзакції з бінарного журналу бази (CDC processing lag);
* `D_net` — затримка передачі повідомлення інвалідації мережею від брокера до вузла кешу;
* `L_rep` — лаг асинхронної реплікації між Master-вузлом та Read-реплікою бази;
* `ε` — максимальна похибка синхронізації локальних годинників вузлів (Clock Drift Bound за протоколом NTP);
* `λ` — інтенсивність вхідного потоку читацьких запитів до ключа (запитів на секунду).

```
Часова шкала подій без маркерів оренди:

t₀ (Читач: промах) ───[ T_db = 60 мс ]───────────────────────> t_read (Запис у кеш V1)
         │                                                            ▲
         ▼                                                            │
t_w (Письменник: COMMIT V2) ───[ T_cdc + D_net = 15 мс ]──> t_inval ──┘
                                                            (DEL виконано)
                                                            Кеш отруєно V1!
```

### 1. Ймовірність виникнення гонки застарілого запису

Без використання маркерів оренди кеш отруюється застарілим значенням `V1`, якщо повідомлення інвалідації від запису `V2` надійшло в кеш **раніше**, ніж повільний читач встиг зберегти зчитане значення `V1`:

```
t_inval = t_w + T_cdc + D_net
t_read  = t₀ + T_db + D_net

Умова отруєння кешу:
t_read > t_inval
(t₀ + T_db + D_net) > (t_w + T_cdc + D_net)
T_db > (t_w - t₀) + T_cdc
```

Якщо мутація відбувається практично одночасно з початком читання (`t_w ≈ t₀`), умова спрощується до нерівності:

```
T_db > T_cdc
```

Ймовірність отруєння кешу `P(StaleSet)` визначається ймовірністю того, що час виконання читацького запиту до бази даних перевищить час проходження конвеєра інвалідації:

```
P(StaleSet) = 1 - F_db(T_cdc)
```

У реальних виробничих системах час виконання SQL-запитів `T_db` добре описується логнормальним розподілом `ln N(μ_db, σ_db²)` з важким «хвостом» затримок через черги до пулу з'єднань або блокування рядків.

Оскільки сучасні CDC-рушії (Debezium, tailing WAL) здатні вилучити та доставити подію за `T_cdc ≈ 5–15 мс`, а читацький SQL-запит під навантаженням або під час пауз збирача сміття (GC) на `p99` триває `50–200 мс`, імовірність отруєння неізольованого кешу становить:

```
P(StaleSet) = P(T_db > 15 мс) ≈ 0.05 ... 0.25 (від 5% до 25% запитів при паралельних мутаціях)
```

Це означає, що від кожної четвертої до кожної двадцятої конкурентної операції запису кеш зазнає довготривалого отруєння застарілим станом, якщо в системі не застосовуються маркери оренди.

## Розрахунок мінімально безпечного часу оренди (Lease Duration)

Маркер оренди видається кеш-сервером на фіксований проміжок часу `T_lease`. Клієнт має право оновити кеш лише тоді, коли його локальний час виконання не перевищив тривалість оренди, а сервер не отримав жодного сигналу інвалідації за цей інтервал.

Для гарантованого заповнення кешу без помилкових відхилень тривалість `T_lease` повинна покривати:
1. Час виконання SQL-запиту в базі даних із заданим квантилем надійності (наприклад, `p99.9`);
2. Двосторонню мережеву затримку між клієнтом і кешем `2 · D_net`;
3. Запас на можливий дрейф годинників між різними серверами `2 · ε`.

```
T_lease ≥ Q_db(1 - α) + 2·D_net + 2·ε
```

де:
* `Q_db(1 - α)` — квантиль розподілу часу відповіді СКБД рівня `1 - α` (де `α = 10⁻³` для надійності 99.9%);
* `D_net` — максимальна мережева затримка в межах дата-центру;
* `ε` — максимальний дрейф годинників.

### Практичний розрахунок параметрів

**Вихідні виміряні параметри виробничого середовища:**
* Математичне сподівання часу запиту до БД: `E[T_db] = 12 мс`;
* Стандартне відхилення за логнормальним розподілом: `σ_db = 6 мс`;
* Квантиль `p99.9` часу читання з бази: `Q_db(0.999) = 48 мс`;
* Затримка передачі пакета в локальній мережі: `D_net = 1.5 мс`;
* Затримка конвеєра CDC Debezium: `T_cdc = 8 мс`;
* Максимальний дрейф годинників за протоколом NTP: `ε = 1.0 мс`.

**Покрокове обчислення мінімального часу оренди `T_lease`:**

```
T_lease_min
= Q_db(0.999) + 2·D_net + 2·ε          [підстановка формули границі оренди]
= 48 + 2·1.5 + 2·1.0                   [підстановка числових значень у мс]
= 48 + 3.0 + 2.0                       [множення мережевих та годинникових похибок]
= 53.0 мс                              [мінімальна тривалість безпечної оренди]
```

З урахуванням інженерного коефіцієнта запасу на сплески навантаження (Safety Margin ×1.5):

```
T_lease_prod = 53.0 · 1.5 ≈ 80 мс
```

## Математична модель придушення лавинного шторму (Thundering Herd Suppression)

Оренда одночасно виконує функцію координатора навантаження на базу даних під час кеш-промахів гарячих ключів.

Нехай інтенсивність читацьких запитів до популярного ключа становить `λ` запитів на секунду (наприклад, `λ = 10 000` запитів/с для головної сторінки).

### 1. Кількість запитів до СКБД без використання оренди

Під час кеш-промаху тривалістю `T_db` кожен вхідний запит читання не знаходить значення в кеші й негайно ініціює власний SQL-запит до бази:

```
N_db_naive = λ · T_db
= 10000 · 0.048 с
= 480 одночасних SQL-запитів до бази даних
```

Це викликає миттєве вичерпання пулу з'єднань СКБД та каскадне зростання затримок для всіх сусідніх мікросервісів.

### 2. Кількість запитів до СКБД з механізмом оренди

Кеш-сервер видає маркер оренди лише **першому** клієнту, який звернувся під час промаху. Наступні клієнти, які надходять протягом часу дії оренди `T_lease`, отримують спеціальну відповідь «оренда активна, зачекайте» (*HOT_MISS*) або зчитують старе значення з коротким додатковим часом життя.

Кількість реальних запитів до бази даних зменшується до одиниці:

```
N_db_lease = 1
```

Коефіцієнт придушення навантаження на СКБД становить:

```
K_suppression = N_db_naive / N_db_lease
= 480 / 1
= 480 (зниження навантаження на 99.79%)
```

## Межа застарілості при асинхронній реплікації (Replication Lag Bound)

Якщо клієнтські запити читання спрямовуються на Read-репліки бази даних, виникає додаткове джерело неузгодженості: репліка відстає від Master-вузла на величину `L_rep`.

Максимальне часове вікно застарілості даних `W_stale`, яке може спостерігати зовнішній клієнт при читанні з кешу після фіксації транзакції, обмежується виразом:

```
W_stale = T_cdc + D_net + max(0, L_rep - T_cdc)
```

**Аналіз двох режимів роботи:**

```
1. Випадок швидкої реплікації (L_rep ≤ T_cdc):
W_stale = T_cdc + D_net
= 8 мс + 1.5 мс
= 9.5 мс      [застарілість визначається виключно швидкістю шини CDC]

2. Випадок відставання репліки (L_rep > T_cdc, наприклад L_rep = 150 мс):
W_stale = T_cdc + D_net + (L_rep - T_cdc)
= D_net + L_rep
= 1.5 мс + 150 мс
= 151.5 мс    [вікно застарілості розширюється на весь лаг реплікації]
```

### Висновок для проектування систем

1. **Без оренди або версіонування:** Навіть при нульовому лагу реплікації `L_rep = 0` існує нездоланна ймовірність `P(StaleSet) ≈ 5–25%` безповоротного отруєння кешу старим значенням на весь час TTL.
2. **З маркерами оренди:** Ймовірність отруєння кешу падає до `0%`, оскільки будь-яка інвалідація, що надійшла під час виконання читацького запиту, гарантовано анулює маркер оренди.
3. **Обмеження реплікації:** За наявності Read-реплік для усунення вікна застарілості `W_stale` необхідно використовувати механізм віддалених маркерів (*Remote Markers*) або примусове спрямування читань при кеш-промахах на Master-вузол протягом часу `t < L_rep_max`.
