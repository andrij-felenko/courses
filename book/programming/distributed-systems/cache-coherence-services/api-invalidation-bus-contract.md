# 📋 Специфікація шини інвалідації кешів та протокол взаємодії L1/L2

Для підтримання наскрізної узгодженості між десятками мікросервісів та їхніми локальними кешами необхідний суворий і стандартизований контракт обміну подіями інвалідації. Коли десятки незалежних вузлів кешують стан одного й того самого бізнес-агрегату (наприклад, балансу рахунку, каталогу товарів чи прав доступу користувача), будь-яка неточність у структурі повідомлень або порядку їхньої доставки призводить до розходження даних між репліками.

Нижче наведено формальну специфікацію подій інвалідації для розподіленої шини повідомлень (Apache Kafka, NATS JetStream, RabbitMQ) та керуючих команд протоколу клієнтського трекінгу Redis версій 6 і вище (протокол RESP3).

## Схема конверта події інвалідації (Invalidation Event Envelope)

Кожна мутація даних у первинній СКБД, зафіксована конвеєром захоплення змін (Change Data Capture) або сервісом-власником даних, транслюється в спільний топік `system.cache.invalidations`.

Конверт події проєктується за принципом самодостатності: споживач події не повинен робити додаткових звернень до бази даних, аби з'ясувати, які саме ключі втратили чинність і чи є ця подія новішою за локально збережений стан.

```json
{
  "event_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp_epoch_ms": 1724164800125,
  "sequence_number": 849201948,
  "source_service": "billing-account-service",
  "origin_datacenter": "eu-central-1",
  "aggregate_type": "Account",
  "aggregate_id": "acc-94812",
  "action": "EVICT_KEYS",
  "entity_version": 42,
  "target_keys": [
    "account:acc-94812",
    "account_balance:acc-94812",
    "user_accounts:usr-1049"
  ],
  "invalidation_scope": "GLOBAL_ALL_TIERS"
}
```

### Детальний опис полів контракту

Кожне поле конверта виконує суворо визначену функцію в протоколі когерентності:

* **`event_id` (UUIDv4):** Унікальний ідентифікатор конкретного екземпляра повідомлення. Використовується для дедуплікації на стороні L1-слухачів за допомогою кільцевого буфера або фільтра Блума. Якщо брокер доставить дублікат повідомлення (семантика at-least-once), клієнт ідентифікує повтор за `event_id` і не виконуватиме зайвих скидань пам'яті.
* **`trace_id` (String / W3C Trace Context):** Наскрізний ідентифікатор розподіленого трасування. Дозволяє системам спостережуваності (OpenTelemetry, Jaeger) пов'язати бізнес-запит, транзакцію в СКБД, подію CDC та момент вилучення ключа з L1 кешу на кожному мікросервісі.
* **`timestamp_epoch_ms` (Int64):** Фізичний час фіксації транзакції в СКБД за шкалою UTC у мілісекундах. Слугує орієнтиром для моніторингу наскрізного лагу інвалідації (різниця між часом отримання події та цим таймстемпом).
* **`sequence_number` (UInt64):** Монотонно зростаючий порядковий номер мутації у журналі транзакцій (наприклад, PostgreSQL LSN або Kafka Offset). Гарантує виявлення пропущених повідомлень або порушення послідовності доставки.
* **`source_service` (String):** Канонічна назва мікросервісу, який ініціював зміну стану. Допомагає локалізувати джерело спаму інвалідацій при аномальних сплесках трафіку.
* **`origin_datacenter` (String):** Ідентифікатор географічного регіону чи дата-центру, де відбулася первинна фіксація запису. Необхідний для коректної обробки віддалених маркерів (Remote Markers) у мультирегіональних кластерах із затримками реплікації.
* **`aggregate_type` (String):** Тип доменного агрегату (`Order`, `Product`, `Account`, `UserProfile`). Дозволяє фільтрувати події на рівні клієнтських бібліотек.
* **`aggregate_id` (String):** Первинний бізнес-ідентифікатор сутності.
* **`action` (Enum):** Тип операції інвалідації:
  * `EVICT_KEYS` — точкове видалення перелічених ключів із локальних та спільних кешів;
  * `EVICT_PREFIX` — скидання всіх ключів, що відповідають префіксу агрегату (наприклад, `products:99:*`);
  * `TOUCH_VERSION` — оновлення метаданих версії без негайного вилучення тіла об'єкта.
* **`entity_version` (UInt64):** Номер версії агрегату після застосування мутації. Критично важливий для фільтрації запізнілих пакетів.
* **`target_keys` (Array of Strings):** Масив точних ключів сховища, які втратили чинність унаслідок цієї транзакції.
* **`invalidation_scope` (Enum):** Рівень застосування: `GLOBAL_ALL_TIERS` (скидання у спільному Redis L2 та локальних L1 усіх подів) або `L1_ONLY_LOCAL` (скидання лише локальної пам'яті).

## Керуючі директиви клієнтського трекінгу Redis 6+ (RESP3)

Для зв'язування локальної пам'яті процесу (L1) зі спільним сервером Redis (L2) застосовується вбудований протокол `CLIENT TRACKING`.

### Специфікація команди увімкнення

```text
CLIENT TRACKING on|off 
    [REDIRECT client-id] 
    [PREFIX prefix [PREFIX prefix ...]] 
    [BCAST] 
    [OPTIN] 
    [OPTOUT] 
    [NOLOOP]
```

### Призначення параметрів та режими роботи

1. **Режим прямого відстеження (Default Tracking Mode):**
   Клієнт виконує `CLIENT TRACKING on`. Сервер Redis запам'ятовує кожен ключ, зчитаний цим клієнтом, у внутрішній таблиці недійсності (*Invalidation Table*). Таблиця організована як префіксне Radix-дерево. Коли інший клієнт змінює цей ключ, Redis надсилає клієнту позачергове push-повідомлення і негайно видаляє зв'язку з таблиці трекінгу. Це мінімізує обсяг мережевого трафіку: якщо ключ змінюється 100 разів поспіль, клієнт отримає рівно одне сповіщення, оскільки повторний трекінг активується лише після нового читання `GET`.
2. **Режим широкомовлення за префіксами (BCAST Mode):**
   Клієнт виконує `CLIENT TRACKING on BCAST PREFIX "catalog:" PREFIX "prices:"`. У цьому режимі Redis не витрачає оперативну пам'ять на реєстрацію мільйонів окремих ключів. Замість цього сервер перевіряє змінені ключі за списком префіксів і надсилає широкомовне сповіщення всім підписаним клієнтам. Цей режим рекомендований для великих сховищ із мільйонами дрібних об'єктів.
3. **Параметр `REDIRECT client-id`:**
   У протоколі RESP2 або при використанні синхронних клієнтських пулів з'єднань складно обробляти асинхронні вхідні push-пакети всередині звичайного конвеєра запит-відповідь. Директива `REDIRECT` наказує Redis надсилати всі повідомлення інвалідації в окреме спеціалізоване TCP-з'єднання з номером `client-id`, де працює окремий фоновий потік-слухач.
4. **Параметр `NOLOOP`:**
   Запобігає отриманню сповіщень про власні зміни: якщо сервіс оновив ключ, він уже знає про факт зміни і не витрачає ресурси на обробку зворотного луна-пакета.

### Формат бінарного push-фрейму інвалідації (RESP3 Wire Protocol)

Коли ключ мутує в базі Redis, клієнт отримує через сокет спеціальний push-тип даних:

```text
>2\r\n
$10\r\n
invalidate\r\n
*1\r\n
$18\r\n
account:acc-94812\r\n
```

У разі одночасної зміни декількох ключів (наприклад, у блоці `MSET` або транзакції `MULTI ... EXEC`) масив містить повний перелік недійсних ключів.

## Алгоритми обробки подій та правила відновлення після збоїв

Підтримання когерентності вимагає від клієнтської бібліотеки чітких дій у разі виникнення позаштатних ситуацій:

### 1. Фільтрація порушеного порядку доставки (Monotonic Version Guard)

Через мережевий джиттер повідомлення інвалідації версії `v=41` може дістатися до вузла пізніше, ніж повідомлення версії `v=42`. Клієнт зобов'язаний застосовувати таку логіку:

```
Якщо вхідне_повідомлення.entity_version < локальний_елемент.version:
    Ігнорувати подію (застарілий пакет із мережі)
Інакше:
    Видалити локальний_елемент з L1
    Анулювати активні токени оренди для цього ключа
```

### 2. Протокол відновлення після обриву з'єднання (Connection Loss Resync)

Якщо TCP-з'єднання з Redis або брокером Kafka переривається (тайм-аут сокета, перезапуск проксі-сервера або падіння мережевого інтерфейсу), клієнтська бібліотека переходить у стан аварії:
* Під час відсутності зв'язку повідомлення інвалідації губляться;
* Після успішного відновлення з'єднання клієнт **зобов'язаний виконати повне очищення (FLUSH) усієї локальної таблиці L1**;
* Будь-які запити, що надходять під час обриву зв'язку, повинні оминати L1 і йти безпосередньо в L2 або первинну СКБД.

### 3. Обробка помилок операцій оренди

Клієнт повинен обробляти такі стандартні коди відповідей кеш-сервера:
* `ERR_LEASE_INVALIDATED`: Запис відхилено через паралельну мутацію або надходження інвалідації. Клієнт повинен повторити спробу читання або повернути свіжий стан.
* `ERR_LEASE_EXPIRED`: Час оренди вичерпано. Запобігає збереженню результатів надто повільних або підвислих запитів до бази.
* `ERR_TRACKING_OVERFLOW`: Таблиця трекінгу на боці Redis досягла граничного ліміту пам'яті (`tracking-table-max-keys`). Клієнт зобов'язаний тимчасово очистити L1 та перейти в префіксний режим `BCAST`.
