# 📜 Від заліза до eBPF: як Google Maglev та Facebook Katran переписали балансування на 4-му рівні

Наприкінці 1990-х та на початку 2000-х років масштабування мережевої інфраструктури впиралося в апаратну межу. Компанії, що будували веб-портали та пошукові системи, купували спеціалізовані апаратні балансувальники — пропрієтарні стійкові прилади від F5 Networks (BIG-IP), Cisco (LocalDirector, CSS, ACE) або Foundry Networks. Ці пристрої коштували сотні тисяч доларів, базувалися на спеціалізованих мікросхемах (ASIC) або мережевих процесорах (NPU) і продавалися в парі «активний — пасивний» (active-passive failover).

Модель активного й резервного пристроїв мала дві фундаментальні вади. По-перше, половина дорогого обладнання простоювала, чекаючи на аварію основного блоку. По-друге, масштабування було виключно вертикальним: якщо піковий трафік перевершував пропускну здатність материнської плати чи процесора балансувальника, єдиним виходом була заміна всієї шасі на ще дорожчу модель наступного покоління. Коли обсяг вхідного трафіку почав вимірюватися десятками гігабітів, а згодом і терабітами за секунду, вертикальна межа перетворилася на глухий кут.

### Народження Google Maglev: балансування на звичайних серверах (2008–2016)

У 2008 році інженери Google зіткнулися з тим, що жоден комерційний балансувальник у світі не здатен обслуговувати сумарний трафік пошуку, пошти та стрімко зростаючого YouTube. Замість закупівлі чергових апаратних коробок команда під керівництвом Деніела Айзенбуда (Daniel E. Eisenbud) вирішила розробити програмний L4-балансувальник, який працював би на звичайних серверах стандартної архітектури x86 під керуванням Linux. Проєкт отримав назву Maglev (від *magnetic levitation* — потяг на магнітній подушці, як метафора відсутності тертя та затримок).

Головний архітектурний виклик полягав у тому, як об'єднати десятки звичайних машин у єдиний логічний балансувальник без спільної точки відмови. Інженери Google поєднали дві технології: протокол динамічної маршрутизації BGP (Border Gateway Protocol) з механізмом ECMP (Equal-Cost Multi-Path) та консистентне хешування у просторі користувача.

```
                  ┌──────────────────────────────┐
                  │   Граничний BGP-маршрутизатор │
                  └──────────────┬───────────────┘
                                 │ ECMP (5-tuple hash)
                ┌────────────────┼────────────────┐
                ▼                ▼                ▼
         ┌────────────┐   ┌────────────┐   ┌────────────┐
         │  Maglev 1  │   │  Maglev 2  │   │  Maglev 3  │
         └─────┬──────┘   └─────┬──────┘   └─────┬──────┘
               │                │ DSR             │
               └────────────────┼─────────────────┘
                                ▼
                       ┌─────────────────┐
                       │  Пул бекендів   │
                       └─────────────────┘
```

Граничні маршрутизатори анонсували єдину віртуальну IP-адресу (VIP) через BGP Anycast. Маршрутизатор ділив пакети між пулом машин Maglev за допомогою апаратного хешу 5-tuple (IP джерела/призначення, порти джерела/призначення, протокол). Проте маршрутизатори нічого не знали про стан TCP-з'єднань. Якщо один сервер Maglev перезавантажувався, хеш ECMP у маршрутизаторі зміщувався, і наступний пакет існуючого з'єднання потрапляв на сусідній Maglev.

Якби новий Maglev обрав інший бекенд, ніж попередній, клієнт отримав би розрив TCP-сесії (TCP RST). Щоб запобігти цьому без синхронізації таблиць з'єднань між серверами через мережу (що створило б колосальний оверхед), Google розробила детермінований алгоритм побудови таблиці консистентного хешування. Кожен вузол Maglev самостійно генерував ідентичну таблицю підстановки фіксованого розміру, завдяки чому будь-який вузол кластера направляв пакети одного TCP-потоку на той самий бекенд.

Щоб обробляти мільйони пакетів за секунду на ядрах загального призначення, Maglev обходив мережевий стек ядра Linux. Програма працювала в просторі користувача, напряму читаючи дескриптори кільцевих буферів мережевої карти (NIC ring buffers) через власний драйвер, повністю уникаючи системних викликів, переривань та алокацій системних структур `sk_buff`.

### Від IPVS до BPF/XDP: еволюція у Facebook та проєкт Katran (2018)

Паралельно компанія Facebook вирішувала ту саму проблему, проте тривалий час спиралася на вбудований у ядро Linux механізм IPVS (IP Virtual Server) у поєднанні з LVS (Linux Virtual Server). IPVS надавав ефективну маршрутизацію на 4-му рівні прямо всередині ядра за схемою DSR (Direct Server Return).

Проте зі зростанням трафіку до сотень терабіт на секунду та посиленням DDoS-атак інфраструктура IPVS вперлася у внутрішні обмеження ядра:
1. **Блокування таблиці з'єднань (`ip_vs_conn_tab`):** створення та читання записів про мільйони паралельних з'єднань спричиняло жорстку конкуренцію за блокування (lock contention) між ядрами процесора.
2. **Накладні витрати на виділення пам'яті:** ядро виділяло структуру `sk_buff` для кожного вхідного пакета ще до того, як IPVS вирішував його перенаправити, витрачаючи цінні такти процесора на непотрібну роботу.
3. **Неефективність проти SYN-флуду:** за умов масованої DDoS-атаки таблиця станів IPVS миттєво переповнювалася, викликаючи відмову в обслуговуванні легітимних користувачів.

У 2018 році команда інженерів Facebook під керівництвом Максима Краснянського (Maxim Krasnyansky) представила Katran — L4-балансувальник нового покоління з відкритим вихідним кодом. Katran переніс всю логіку Maglev-подібного консистентного хешування в XDP (eXpress Data Path) — технологію ядра Linux, яка виконує верифіковані BPF-програми (Berkeley Packet Filter) безпосередньо в драйвері мережевої карти, до виділення `sk_buff` і до передачі пакета в основний мережевий стек.

```
       Мережева карта (NIC) ──► XDP драйвер ──► BPF-програма (Katran)
                                                    │
                 ┌──────────────────────────────────┴──────────────────────────────────┐
                 ▼                                                                     ▼
     [Пакет збігається з VIP]                                              [Пакет для самого вузла]
     1. Пошук у BPF-таблиці з'єднань                                       Передача в мережевий стек ядра
     2. Якщо немає: Maglev Hashing                                         (SSH, BGP-демони, моніторинг)
     3. Інкапсуляція в IPIP / GUE
     4. Повернення XDP_TX (відправка назад у дріт)
```

Katran досяг практично лінійної швидкості обробки: один сучасний x86-сервер став здатним маршрутизувати понад 30–40 мільйонів пакетів за секунду на швидкостях 100 Gbps, витрачаючи лише частку потужності процесора. У разі надходження SYN-пакетів або DDoS-трафіку Katran навіть не зберігав стан у пам'яті, а обчислював цільовий бекенд чисто функціонально через таблицю Maglev, нівелюючи атаки на вичерпання таблиці з'єднань.

### Значення для сучасної індустрії

Створення Maglev та Katran остаточно знищило ринок монолітних апаратних балансувальників на межі мережі. Усі провідні хмарні провайдери та платформи (Google Cloud, Meta, Cloudflare з їхньою системою Unimog, AWS із Network Load Balancer, Microsoft Azure із Ananta) перейшли на дворівневу архітектуру: програмний L4-рівень на базі eBPF/DPDK з консистентним хешуванням і DSR на межі, який розподіляє сирий потік пакетів між динамічно масштабованими пулами L7-проксі (Envoy, HAProxy, NGINX).
