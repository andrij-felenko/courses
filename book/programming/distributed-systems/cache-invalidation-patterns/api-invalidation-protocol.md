# 📋 Протокол подій інвалідації, HTTP-заголовки Surrogate-Key та Lua-інтерфейс

Цей документ визначає структурні контракти, формати повідомлень та програмні інтерфейси для координації інвалідації між джерелами змін (база даних, CDC), брокерами повідомлень, кеш-серверами (Redis) та прикордонними проксі (CDN / Varnish).

## 1. Схема події інвалідації CDC (Change Data Capture)

Коли агент захоплення змін (Debezium / Canal) фіксує транзакцію в журналі WAL бази даних, він публікує в брокер повідомлень (Kafka / Pulsar) подію стандартизованого формату.

### Семантика доставки та гарантії впорядкування

1. **Ключ партиціонування (Partition Key):** Повідомлення в топік Kafka публікуються з обов'язковим ключем партиціонування виду `<entity>:<key_id>` (наприклад, `products:42`). Це гарантує, що всі послідовні модифікації одного й того самого рядка потрапляють в одну партицію Kafka і обробляються суворо монотонно в порядку їхньої фіксації в базі даних.
2. **Монотонність LSN:** Кожна подія містить системний номер позиції в журналі транзакцій (`Log Sequence Number`, LSN). Споживач інвалідації відкидає будь-яке повідомлення, якщо його LSN менший за останній оброблений LSN для цієї сутності, захищаючи систему від перевпорядкування повідомлень під час аварійного перезапуску воркерів.
3. **Ідемпотентність:** Повторна доставка тієї самої події (семантика `at-least-once`) є безпечною, оскільки операції `DEL key` та `PURGE tag` є строго ідемпотентними.

### Специфікація полів JSON-повідомлення

| Поле | Тип | Опис |
| :--- | :--- | :--- |
| `event_id` | `UUID` | Унікальний ідентифікатор події для дедуплікації в сховищі стану воркера. |
| `lsn` | `uint64` | Позиція в журналі транзакцій (Log Sequence Number) для контролю порядку. |
| `timestamp` | `int64` | Unix timestamp фіксації транзакції на майстрі БД (мілісекунди). |
| `entity` | `string` | Назва таблиці або логічного агрегату (наприклад, `products`). |
| `op` | `enum` | Тип мутації: `"c"` (створення), `"u"` (оновлення), `"d"` (видалення). |
| `key_id` | `string` | Первинний ключ зміненого запису в базі даних. |
| `purge_tags` | `array<string>` | Згенерований перелік семантичних тегів для групового очищення. |
| `delay_ms` | `uint32` | Затримка відкладеного подвійного видалення (мс) для компенсації лагу реплікації. |

```json
{
  "event_id": "c4a71d28-72b1-4f1e-92a1-0f4b1d6e8901",
  "lsn": 48291049281,
  "timestamp": 1724160000123,
  "entity": "products",
  "op": "u",
  "key_id": "42",
  "purge_tags": [
    "item:42",
    "brand:apple",
    "cat:laptops"
  ],
  "delay_ms": 300
}
```

## 2. Специфікація HTTP-заголовків Surrogate-Key

Для індексування сторінок у зворотних проксі (Varnish, Nginx) та CDN (Fastly, Cloudflare) сервер походження (Origin Server) формує мета-заголовки відповіді.

### Правила токенізації та обмеження заголовків

* **Розділювач тегів:** Теги в заголовку `Surrogate-Key` розділяються одним пробілом (ASCII `0x20`).
* **Допустимі символи:** Дозволено латинські літери в нижньому регістрі, цифри, дефіс, підкреслення та двокрапку (`[a-z0-9-_:]`).
* **Ліміти довжини:** Довжина одного тегу не повинна перевищувати 256 байтів, а сумарний розмір заголовка `Surrogate-Key` — не більше 16 КБ (ліміт буфера більшості CDN-провайдерів).
* **Видалення перед клієнтом:** Прикордонний CDN-проксі зобов'язаний вирізати заголовки `Surrogate-Key` та `Surrogate-Control` перед відправкою відповіді кінцевому веб-браузеру, щоб не розкривати внутрішню топологію сутностей.

### Заголовки відповіді Origin-сервера

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: public, max-age=86400, stale-while-revalidate=60
Surrogate-Key: item:42 cat:laptops brand:apple tenant:10
Edge-Control: cache-maxage=86400
```

### Запит на інвалідацію (Fastly / Varnish Purge API)

Для очищення кешу клієнт надсилає POST-запит до API прикордонного проксі. Заголовок `Fastly-Soft-Purge: 1` активує режим м'якого очищення (`stale-while-revalidate`), при якому кеш продовжує віддавати старий знімок під час фонового оновлення.

```http
POST /service/SUBCONFIG_ID/purge/item:42 HTTP/1.1
Host: api.fastly.com
Fastly-Key: secret_api_token_here
Fastly-Soft-Purge: 1
Accept: application/json
```

Відповідь кеш-вузла підтверджує успішну реєстрацію команди інвалідації:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "status": "ok",
  "id": "purge-req-84920481",
  "purged_tags": ["item:42"]
}
```

## 3. Lua-скрипти для атомарної інвалідації в Redis

Оскільки Redis виконує скрипти Lua атомарно в єдиному потоці обробки подій, використання Lua гарантує відсутність гонок між паралельними читачами та записувачами.

### Скрипт 1: Атомарне очищення за тегом (`tag_purge.lua`)

Скрипт зчитує всі ключі з множини `tag:<tag_name>`, видаляє ці ключі з кешу, а потім видаляє сам ключ множини тегу. Для запобігання блокуванню Redis при великій кількості ключів (>10 000) замість важкого `DEL` застосовується неблокуюча команда `UNLINK`.

```lua
-- KEYS[1]: Ключ тегу (наприклад, "tag:item:42")
-- Повертає: Кількість видалених ключів

local tag_key = KEYS[1]
local keys_to_del = redis.call('SMEMBERS', tag_key)

if #keys_to_del == 0 then
    redis.call('UNLINK', tag_key)
    return 0
end

-- Неблокуюче видалення всіх пов'язаних ключів у фоновому потоці Redis
local deleted_count = redis.call('UNLINK', unpack(keys_to_del))

-- Видаляємо сам індексний ключ тегу
redis.call('UNLINK', tag_key)

return deleted_count
```

### Скрипт 2: Атомарний запис із валідацією лізи (`set_if_lease_valid.lua`)

Запобігає гонці застарілого запису (Stale-Read Race), перевіряючи, чи видана читачеві ліза все ще є чинною на момент завершення запиту до бази даних.

```lua
-- KEYS[1]: Ключ кешу (наприклад, "product:42")
-- ARGV[1]: Нове значення (JSON рядок)
-- ARGV[2]: TTL у секундах
-- ARGV[3]: Токен лізи клієнта (lease_token)

local key = KEYS[1]
local value = ARGV[1]
local ttl = tonumber(ARGV[2])
local client_lease = tonumber(ARGV[3])
local lease_key = "lease:" .. key

local current_lease = tonumber(redis.call('GET', lease_key))

-- Якщо ліза в системі змінилася (відбувся запис/інвалідація), відхиляємо запізнілий запис
if current_lease and current_lease > client_lease then
    return 0 -- Відхилено: застаріла ліза (захист від Stale-Read Race)
end

redis.call('SET', key, value, 'EX', ttl)
return 1 -- Успішно записано
```

## 4. Інтерфейс Purge Router (gRPC IDL)

Для взаємодії між мікросервісами та маршрутизатором інвалідації застосовується високопродуктивний gRPC-контракт.

Маршрутизатор інвалідації (Purge Router) бере на себе обов'язки:
1. Маршрутизації команди видалення на відповідні шарди Redis за алгоритмом узгодженого хешування (Consistent Hashing).
2. Паралельного віялового надсилання HTTP PURGE запитів до глобальних CDN POP-вузлів.
3. Постановки завдання відкладеного повторного видалення у чергу відкладених повідомлень.

```protobuf
syntax = "proto3";

package cache.invalidation.v1;

// Сервіс координації та доставки команд інвалідації
service InvalidationService {
  // Точкова інвалідація одного конкретного ключа
  rpc PurgeKey (PurgeKeyRequest) returns (PurgeResponse);

  // Групова інвалідація за списком семантичних тегів
  rpc PurgeTags (PurgeTagsRequest) returns (PurgeResponse);

  // Інвалідація всього простору імен через інкремент епохи за O(1)
  rpc BumpNamespaceGeneration (BumpGenerationRequest) returns (BumpGenerationResponse);
}

// Запит точкового видалення
message PurgeKeyRequest {
  string key = 1;
  bool delayed_double_delete = 2;
  uint32 delay_ms = 3;
}

// Запит групового очищення за тегами
message PurgeTagsRequest {
  repeated string tags = 1;
  bool soft_purge = 2;
  bool synchronous = 3;
}

// Запит інкременту версійної епохи
message BumpGenerationRequest {
  string namespace = 1;
}

// Відповідь з новим номером епохи
message BumpGenerationResponse {
  string namespace = 1;
  uint64 new_generation = 2;
}

// Загальна відповідь про результат виконання інвалідації
message PurgeResponse {
  bool success = 1;
  uint64 keys_purged = 2;
  string error_details = 3;
}
```

## 5. Обробка збоїв, повторні спроби та карантин (Dead-Letter Queue)

У розподіленій інфраструктурі мережеві тайм-аути, перевантаження вузлів Redis та тимчасова недоступність CDN-провайдерів є неминучими. Для забезпечення надійної доставки інвалідації застосовується багаторівнева стратегія стійкості:

1. **Експоненційне відтермінування з джитером (Exponential Backoff with Jitter):**
   При отриманні помилки від кеш-вузла або брокера воркер повторює спробу інвалідації з інтервалом:
   `T_retry = min(T_max, T_base · 2^attempt) + Uniform(0, σ_jitter)`. Додавання випадкового джитера запобігає синхронному штурму відновленого кеш-сервера сотнями паралельних воркерів.
2. **Запобіжник перевантаження (Circuit Breaker):**
   Якщо частота помилок звернення до Redis перевищує поріг 20% за вікно в 10 секунд, маршрутизатор тимчасово переходить у стан `OPEN`. У цьому режимі інвалідаційні повідомлення не скидаються, а акумулюються у вторинній персистентній черзі для захисту падаючого кеш-кластера від лавинної відмови.
3. **Карантинна черга помилок (Dead-Letter Queue, DLQ):**
   Якщо повідомлення інвалідації не вдалося доставити після 5 послідовних спроб (наприклад, через некоректний формат ключа або постійну відмову шарда), воно переміщується в чергу `cache-invalidation-dlq`. Операційна команда налаштовує сповіщення на появу повідомлень у DLQ, а спеціальний сервіс реконсиляції періодично перевіряє застряглі записи й виконує примусову звірку стану з первинною базою даних.
4. **Вибір поведінки Fail-Open проти Fail-Closed:**
   Для більшості веб-сервісів застосовується модель `Fail-Open`: якщо маршрутизатор інвалідації тимчасово недоступний, запити на запис у базу даних **не блокуються**, але система фіксує метрику ризику застарілості й спирається на резервний захисний `TTL` (наприклад, 300 секунд), який виступає останньою лінією оборони від нескінченного розходження даних.

## 6. Метрики, спостережуваність та розподілене трасування

Для контролю за здоров'ям конвеєра інвалідації підсистема експортує стандартизовані метрики Prometheus та контекст розподіленого трасування OpenTelemetry:

* `cache_invalidation_lag_seconds`: Різниця між моментом фіксації транзакції в WAL базі даних і моментом успішного видалення ключа з кешу. Це ключова метрика SLA свіжості системи.
* `cache_purged_keys_total`: Лічильник кількості анульованих ключів із мітками за типом операції (`point`, `tag`, `generation_bump`).
* `cache_lease_rejections_total`: Кількість відхилених запізнілих записів (Stale-Read Race) за допомогою скрипта перевірки ліз.
* **Трасування OpenTelemetry:** Заголовки повідомлень Kafka та метадані gRPC-викликів містять бінарний контекст трасування `traceparent`, що дозволяє інженеру в єдиному графіку Jaeger/Zipkin побачити повний шлях зміни: від SQL-запиту клієнта до фінального видалення ключа на прикордонному сервері в іншому регіоні.
