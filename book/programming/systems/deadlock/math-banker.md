# 🧮 Алгоритм банкіра: математична модель безпечних станів

Алгоритм банкіра, запропонований Едсгером Дейкстрою 1965 року, є класичним математичним методом **динамічного уникнення дедлоків** (англ. *deadlock avoidance*). На відміну від статичного запобігання, яке обмежує свободу написання коду суворими правилами захоплення замків, алгоритм банкіра аналізує кожен запит на виділення ресурсів у реальному часі й відмовляє у виділенні або відкладає його, якщо операція переводить систему в потенційно небезпечний стан.

Математична суть алгоритму полягає у визначенні того, чи існує хоча б одна **безпечна послідовність** виконання процесів, за якої кожен процес гарантовано зможе отримати свої заявлені максимальні ресурси, завершити роботу та повернути ресурси в спільний пул.

## Формальна модель системи

Нехай у системі функціонує `n` процесів і `m` різних типів ресурсів. Позначимо множину процесів через `P = {P₀, P₁, ..., Pₙ₋₁}`, а множину типів ресурсів через `R = {R₀, R₁, ..., Rₘ₋₁}`.

Стан системи в кожен момент часу повністю описується чотирма основними структурами даних:

1. **Вектор доступних ресурсів** `Available` розмірності `m`:
   Якщо `Available[j] = k`, це означає, що наразі доступно `k` екземплярів ресурсу типу `R[j]`.

2. **Матриця максимальних вимог** `Max` розмірності `n × m`:
   Елемент `Max[i][j]` визначає максимальну кількість екземплярів ресурсу `R[j]`, яку процес `P[i]` може одночасно запитати протягом свого життєвого циклу.

3. **Матриця поточного виділення** `Allocation` розмірності `n × m`:
   Елемент `Allocation[i][j]` вказує, скільки екземплярів ресурсу `R[j]` наразі вже виділено та утримується процесом `P[i]`.

4. **Матриця залишкових потреб** `Need` розмірності `n × m`:
   Елемент `Need[i][j]` задає залишок екземплярів ресурсу `R[j]`, які процес `P[i]` має право додатково запитати для успішного завершення роботи:

```
Need[i][j] = Max[i][j] - Allocation[i][j]    [інваріант залишку потреби]
```

Для векторів однакової довжини введемо відношення часткового порядку `≤`:
`X ≤ Y` тоді й лише тоді, коли `X[j] ≤ Y[j]` для всіх `j ∈ [0, m - 1]`.

## Визначення безпечного стану

Стан системи називається **безпечним** (англ. *safe state*), якщо існує така перестановка процесів `<P[s₀], P[s₁], ..., P[sₙ₋₁]>` (звана *безпечною послідовністю*), що для кожного процесу `P[sᵢ]` його залишкові потреби можуть бути задоволені за рахунок наявних вільних ресурсів плюс усіх ресурсів, які на цей момент уже утримуються попередніми процесами послідовності `P[s₀], ..., P[sᵢ₋₁]`.

Формально, для кожного `i` від `0` до `n - 1`:

```
Need[sᵢ] ≤ Available + ∑ Allocation[sₖ]    [де сума береться по k від 0 до i - 1]
```

Якщо така послідовність існує, дедлок неможливий у принципі: навіть якщо всі процеси одночасно запитають свої максимальні потреби, система зможе послідовно виконати процес `P[s₀]`, отримати всі його ресурси назад, потім виконати `P[s₁]`, і так далі до завершення останнього процесу `P[sₙ₋₁]`.

Небезпечний стан (англ. *unsafe state*) **не є дедлоком сам по собі**, але він містить математичну ймовірність переходу в дедлок, якщо процеси одночасно зажадають свої максимальні ресурси.

## Алгоритм перевірки безпеки (Safety Algorithm)

Для перевірки, чи є поточний стан системи безпечним, використовується ітераційний алгоритм зі складністю `O(m · n²)`:

1. Ініціалізувати робочий вектор `Work` розмірності `m` та логічний вектор `Finish` розмірності `n`:
   ```
   Work = Available
   Finish[i] = false    для всіх i ∈ [0, n - 1]
   ```

2. Знайти такий індекс `i`, для якого одночасно виконуються дві умови:
   - `Finish[i] == false`
   - `Need[i] ≤ Work`
   Якщо такого індексу не існує, перейти до кроку 4.

3. Процес `P[i]` може гарантовано завершитися. Вважаємо, що він виконав роботу та повернув усі свої ресурси:
   ```
   Work = Work + Allocation[i]
   Finish[i] = true
   ```
   Повернутися до кроку 2.

4. Якщо `Finish[i] == true` для всіх `i ∈ [0, n - 1]`, система перебуває в **безпечному стані**. Якщо ж хоча б для одного процесу `Finish[i] == false`, стан є **небезпечним**.

## Алгоритм запиту ресурсів (Resource-Request Algorithm)

Нехай процес `P[i]` генерує вектор запиту `Request[i]`. Операційна система виконує такі кроки:

1. Перевірити, чи не перевищує запит раніше задекларовану потребу:
   ```
   Якщо Request[i] ≤ Need[i] → перейти до кроку 2
   Інакше → помилка: процес перевищив заявлений ліміт Max[i]
   ```

2. Перевірити, чи є в наявності достатня кількість вільних ресурсів:
   ```
   Якщо Request[i] ≤ Available → перейти до кроку 3
   Інакше → процес P[i] переводиться в стан очікування (ресурсів недостатньо)
   ```

3. **Гіпотетичне виділення**: тимчасово модифікувати стан системи, ніби запит уже задоволено:
   ```
   Available'   = Available   - Request[i]
   Allocation'[i] = Allocation[i] + Request[i]
   Need'[i]       = Need[i]       - Request[i]
   ```

4. Запустити *Алгоритм перевірки безпеки* для гіпотетичного стану `(Available', Allocation', Need')`:
   - Якщо стан **безпечний** → транзакція фіксується, ресурси реально виділяються процесу `P[i]`.
   - Якщо стан **небезпечний** → гіпотетичні зміни відкочуються назад, процес `P[i]` блокується в очікуванні, доки інші процеси не звільнять ресурси.

## Покроковий числовий приклад

Розглянемо систему з `5` процесів (`P₀, P₁, P₂, P₃, P₄`) та `3` типів ресурсів (`A, B, C`).
Загальна кількість фізичних ресурсів у системі:
`Total = (10, 5, 7)` — тобто 10 одиниць A, 5 одиниць B, 7 одиниць C.

### Початковий стан системи

| Процес | `Allocation` (A B C) | `Max` (A B C) | `Need = Max - Allocation` (A B C) |
|---|---|---|---|
| `P₀` | 0 1 0 | 7 5 3 | 7 4 3 |
| `P₁` | 2 0 0 | 3 2 2 | 1 2 2 |
| `P₂` | 3 0 2 | 9 0 2 | 6 0 0 |
| `P₃` | 2 1 1 | 2 2 2 | 0 1 1 |
| `P₄` | 0 0 2 | 4 3 3 | 4 3 1 |

Сумарно виділено ресурсів:
```
∑ Allocation = (0+2+3+2+0, 1+0+0+1+0, 0+0+2+1+2) = (7, 2, 5)
```

Вектор вільних ресурсів `Available`:
```
Available = Total - ∑ Allocation
= (10, 5, 7) - (7, 2, 5)    [віднімання зайнятого від загального]
= (3, 3, 2)
```

### Перевірка безпеки початкового стану

Ініціалізація:
`Work = (3, 3, 2)`, `Finish = [F, F, F, F, F]`.

**Крок 1:** Перевіряємо процеси з `Finish[i] == false`:
- `P₀`: `Need[0] = (7, 4, 3) ≤ (3, 3, 2)` → Ні (не вистачає A, B, C).
- `P₁`: `Need[1] = (1, 2, 2) ≤ (3, 3, 2)` → **Так!**
  Оновлюємо `Work`:
  ```
  Work = Work + Allocation[1]
  = (3, 3, 2) + (2, 0, 0)    [P₁ завершився і повернув ресурси]
  = (5, 3, 2)
  Finish[1] = true
  ```

**Крок 2:** При `Work = (5, 3, 2)`:
- `P₃`: `Need[3] = (0, 1, 1) ≤ (5, 3, 2)` → **Так!**
  Оновлюємо `Work`:
  ```
  Work = Work + Allocation[3]
  = (5, 3, 2) + (2, 1, 1)    [P₃ завершився і повернув ресурси]
  = (7, 4, 3)
  Finish[3] = true
  ```

**Крок 3:** При `Work = (7, 4, 3)`:
- `P₀`: `Need[0] = (7, 4, 3) ≤ (7, 4, 3)` → **Так!**
  Оновлюємо `Work`:
  ```
  Work = Work + Allocation[0]
  = (7, 4, 3) + (0, 1, 0)    [P₀ завершився і повернув ресурси]
  = (7, 5, 3)
  Finish[0] = true
  ```

**Крок 4:** При `Work = (7, 5, 3)`:
- `P₂`: `Need[2] = (6, 0, 0) ≤ (7, 5, 3)` → **Так!**
  Оновлюємо `Work`:
  ```
  Work = Work + Allocation[2]
  = (7, 5, 3) + (3, 0, 2)    [P₂ завершився і повернув ресурси]
  = (10, 5, 5)
  Finish[2] = true
  ```

**Крок 5:** При `Work = (10, 5, 5)`:
- `P₄`: `Need[4] = (4, 3, 1) ≤ (10, 5, 5)` → **Так!**
  Оновлюємо `Work`:
  ```
  Work = Work + Allocation[4]
  = (10, 5, 5) + (0, 0, 2)    [P₄ завершився і повернув ресурси]
  = (10, 5, 7)
  Finish[4] = true
  ```

Усі елементи вектора `Finish` рівні `true`. Знайдено безпечну послідовність:
`<P₁, P₃, P₀, P₂, P₄>`.
Початковий стан є **абсолютно безпечним**.

### Обробка динамічного запиту

Нехай тепер процес `P₁` робить запит:
`Request[1] = (1, 0, 2)`.

1. `Request[1] = (1, 0, 2) ≤ Need[1] = (1, 2, 2)` → Умова 1 виконана.
2. `Request[1] = (1, 0, 2) ≤ Available = (3, 3, 2)` → Умова 2 виконана.
3. Гіпотетичне виділення:
   ```
   Available' = (3, 3, 2) - (1, 0, 2) = (2, 3, 0)
   Allocation'[1] = (2, 0, 0) + (1, 0, 2) = (3, 0, 2)
   Need'[1] = (1, 2, 2) - (1, 0, 2) = (0, 2, 0)
   ```

4. Запускаємо перевірку безпеки для нового стану:
   При `Work = (2, 3, 0)`:
   - `P₁`: `Need'[1] = (0, 2, 0) ≤ (2, 3, 0)` → **Так!**
     `Work = (2, 3, 0) + (3, 0, 2) = (5, 3, 2)`, `Finish[1] = true`.
   - Далі черга безпеки повністю збігається з попередньою: `<P₁, P₃, P₀, P₂, P₄>`.

Висновок: запит `Request[1]` задовольняється негайно, оскільки система залишається в безпечному стані.

## Теорема про відсутність дедлоків у безпечному стані

**Твердження:** Якщо система перебуває в безпечному стані, дедлок неможливий.

**Доведення:**
За означенням безпечного стану існує впорядкована послідовність процесів `S = <P[s₀], P[s₁], ..., P[sₙ₋₁]>`. Для першого процесу `P[s₀]` залишкова потреба `Need[s₀] ≤ Available`. Отже, процес `P[s₀]` не може бути заблокований через брак ресурсів, навіть якщо він запитає максимальну кількість. Він гарантовано виконається за скінченний час і звільнить `Allocation[s₀]` ресурсів.

Для довільного `k`-го процесу `P[sₖ]` за індукцією всі попередні процеси `P[s₀]..P[sₖ₋₁]` вже завершилися і повернули ресурси. Наявний пул ресурсів становить `Available + ∑ Allocation[sᵢ]` (для `i < k`), що за умовою не менше за `Need[sₖ]`. Отже, процес `P[sₖ]` також гарантовано отримає необхідні ресурси й завершиться.

Оскільки всі процеси гарантовано завершуються за скінченний час, виникнення циклічного очікування (четвертої умови Кофмана) є неможливим. Отже, дедлок не виникає. ■

## Обчислювальна складність і практичні обмеження

Математична строгість алгоритму банкіра має свою ціну, через яку він рідко застосовується в ядрах операційних систем загального призначення:

1. **Складність алгоритму**: Перевірка безпеки вимагає `O(m · n²)` операцій порівняння та додавання векторів на кожен системний виклик захоплення ресурсу. Для системи з тисячами потоків (`n = 10000`) та сотнями замків це створює неприйнятний оверхед на процесор.
2. **Вимога апріорного знання**: Алгоритм вимагає, щоб кожен процес наперед знав свою матрицю `Max`. У реальних операційних системах програма не може знати заздалегідь, скільки пам'яті чи дескрипторів сокетів їй знадобиться, оскільки це залежить від дій користувача та мережевого трафіку.
3. **Статичність множини процесів**: Модель передбачає фіксовану кількість процесів `n`, тоді як у сучасних ОС процеси постійно створюються (`fork`) та завершуються (`exit`).

Саме тому в практичному програмуванні алгоритм банкіра слугує теоретичним еталоном, а для реальних систем обирають або дешеве **статичне запобігання** (ієрархію замків), або механізми **виявлення та розриву** (як у СКБД).
