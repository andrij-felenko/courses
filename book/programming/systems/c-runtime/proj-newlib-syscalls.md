# ⚙️ Стаби newlib і syscalls: оживити libc на голому залізі

newlib дає вам `printf`, `malloc`, `strtol`, `time` — але всі вони впираються в коротку поличку **системних викликів** (*syscalls* — звернень до операційної системи), яких на голому МК ніхто не реалізував. Поки ці дірки порожні, libc формально злінкована, а на ділі мовчить або падає. Задача проста на словах: написати десяток функцій-стабів, щоб бібліотека дістала опору в залізі. Тонкощі — в тому, що частина з них мусить робити справжню роботу, частина — лише чесно відмовляти, а одна (`errno`) ще й має лишатися коректною під багатозадачністю.

## Який саме набір потрібен

newlib очікує, що «операційна система» під нею надасть невелику фіксовану поличку функцій. На голому залізі їх ділять на три купки за тим, скільки роботи реально треба.

**Працюють по-справжньому (без них libc безпорадна):**

```
_sbrk    — розсунути купу: дати malloc наступний шматок RAM
_write   — вивести байти (printf, fputs, fwrite → сюди)
_read    — увести байти (scanf, fgets → сюди), часто з UART
```

**Чесно відмовляють (заглушка повертає помилку або нейтральне значення):**

```
_close   — «закрити дескриптор»: на МК файлів нема → повернути 0 чи -1
_lseek   — «перемотати файл»: позиціювання немає → 0
_fstat   — «який тип дескриптора»: кажемо «символьний пристрій» (термінал)
_isatty  — «це термінал?»: для stdout/stderr → 1, інакше → 0
```

**Аварійні / процесні (на МК зводяться до зупинки чи помилки):**

```
_exit    — «завершити процес»: на МК — нескінченний цикл або reset
_kill    — надіслати сигнал: процесів нема → errno=EINVAL, -1
_getpid  — «мій PID»: фіктивне число (1)
```

Контрольний критерій, що відрізняє першу купку від решти: **чи має виклик принести реальний ресурс заліза**. `_sbrk` приносить пам'ять, `_write` — доступ до UART, `_read` — вхідні байти; це справжня робота. Решта стосується сутностей ОС (файли, процеси, сигнали), яких на МК немає, тому їхня єдина чесна реалізація — повернути нейтральне значення або помилку, **не вдаючи**, що ресурс є.

> 🔧 **Навіщо це.** Лінкер не скаже, що стаб «несправжній» — заглушка лінкується так само тихо, як робоча функція. Тому помилка «`printf` нічого не виводить» або «`scanf` висне» діагностується не компілятором, а знанням, що за кожним стандартним викликом стоїть syscall, і саме його стаб треба перевірити першим.

## `_sbrk` — серце купи

`malloc` сам не знає, де в системі вільна RAM. Коли його внутрішньому пулу бракує місця, він кличе `_sbrk(increment)` — «посунь межу купи на `increment` байтів і верни стару межу». Уся динамічна пам'ять МК тримається на цій одній функції.

Звідки `_sbrk` бере першу адресу? З **лінкера**. Лінкер-скрипт лишає по кінці статичних секцій символ (класично `_end`, або `end`) — це перший вільний байт RAM одразу за `.bss`. Купа росте вгору від нього; стек росте вниз від вершини RAM. `_sbrk` лише веде покажчик `heap_end` і стежить, щоб той не наїхав на стек.

```c
#include <errno.h>
#include <sys/types.h>

extern char _end;            // символ із лінкер-скрипта: кінець .bss = початок купи
extern char _estack;         // вершина RAM (низ стека) — теж із лінкер-скрипта

static char *heap_end = 0;

void *_sbrk(ptrdiff_t increment) {
    if (heap_end == 0)
        heap_end = &_end;                 // перший виклик: купа стартує за .bss

    char *prev = heap_end;
    char *next = heap_end + increment;

    // межа: не дати купі врости у стек (лишаємо запас під поточний кадр)
    char *limit = &_estack - 512;         // 512 Б оберегу під стек
    if (next > limit) {
        errno = ENOMEM;                   // пам'ять скінчилась
        return (void *) -1;               // malloc побачить -1 → поверне NULL
    }

    heap_end = next;
    return prev;                          // стара межа = адреса нового блоку
}
```

Три пастки тут гострі. **Перша:** забути перевірку межі — тоді `malloc` радо «виділить» пам'ять, що накладається на стек, і програма впаде не в момент виділення, а пізніше й в іншому місці, коли стек перепише купу (або навпаки). **Друга:** повернути на помилці `0` (`NULL`) замість `(void *)-1` — newlib чекає саме `-1` як знак провалу; `NULL` вона прийме за валідну адресу 0 і піде писати туди. **Третя:** оберіг (`-512`) надто малий — глибокий ланцюг викликів або велике переривання роздує стек нижче розрахунку, і він мовчки потре верхівку купи.

## `_write` і `_read` — міст до UART

`printf` усю важку роботу (форматування) робить сам, а наприкінці виштовхує готові байти одним викликом `_write(fd, buf, len)`. Дескриптор `fd` тут — домовленість POSIX: `1` — stdout, `2` — stderr. На МК обидва зазвичай ведуть в один UART.

```c
#include <unistd.h>
#include "driver/uart.h"          // приклад під ESP-IDF; ідея спільна для будь-якого UART

int _write(int fd, const char *buf, int len) {
    if (fd != STDOUT_FILENO && fd != STDERR_FILENO) {
        errno = EBADF;            // у нас лише консоль; інші дескриптори невідомі
        return -1;
    }
    uart_write_bytes(UART_NUM_0, buf, len);
    return len;                   // скільки байтів прийняли (тут — усі)
}

int _read(int fd, char *buf, int len) {
    if (fd != STDIN_FILENO) { errno = EBADF; return -1; }
    int n = uart_read_bytes(UART_NUM_0, (uint8_t *)buf, len, pdMS_TO_TICKS(20));
    return n < 0 ? 0 : n;         // 0 = «поки нема даних» (EOF-семантика для stdin)
}
```

Чому повернене число важливе: newlib вірить `_write` на слово. Повернете менше за `len` — бібліотека вважатиме, що решта не пішла, і спробує дослати «хвіст» наступним викликом; повернете більше — зіпсуєте внутрішній облік `stdio`. Тому або віддавайте рівно `len` (UART-драйвер сам поставить байти в чергу), або повертайте реально прийняту кількість і будьте готові, що `printf` гукне `_write` ще раз.

## Заглушки, що чесно нічого не роблять

Решта викликів на МК не мають сенсу — але злінкуватися мусять, інакше `printf` потягне за собою `undefined reference` на `_fstat` чи `_isatty` (бо `stdio` всередині питає в системи, чи дескриптор — термінал, щоб обрати буферизацію). Тому стаб має не «робити нічого», а **повертати таке значення, яке не зламає логіку newlib**.

```c
#include <sys/stat.h>

int _close(int fd)              { (void)fd; return -1; }      // нема чого закривати
int _lseek(int fd, int p, int w){ (void)fd;(void)p;(void)w; return 0; }
int _isatty(int fd)             { (void)fd; return 1; }       // консоль = термінал
int _fstat(int fd, struct stat *st) {
    (void)fd;
    st->st_mode = S_IFCHR;      // «символьний пристрій»: stdio вимкне блочну буферизацію
    return 0;
}
void _exit(int code)            { (void)code; while (1) {} }  // на МК нема куди «вийти»
int _kill(int pid, int sig)     { (void)pid;(void)sig; errno = EINVAL; return -1; }
int _getpid(void)               { return 1; }
```

Найтонше тут — `_fstat`, що повертає `S_IFCHR`. Якби стаб збрехав, що дескриптор — звичайний файл (`S_IFREG`), `stdio` увімкнув би повну буферизацію, і ваш `printf("готовий\n")` осів би в буфері, **не з'явившись на екрані**, доки буфер не переповниться або не буде `fflush`. Класична загадка «чому лог видно лише після краху» — часто саме брехливий `_fstat` (або відсутній `_isatty`).

## errno під FreeRTOS: чому глобал тут не годиться

`errno` за стандартом — «остання помилка», і наївно це глобальна змінна. Під RTOS це міна: задача A викликала `strtol`, та поставила `errno = ERANGE`; перш ніж A прочитала помилку, планувальник перемкнувся на задачу B, що зробила `malloc` і записала свій `errno = ENOMEM`. A прокидається й бачить чужу помилку. Гонитва не у вашому коді, а **всередині libc**.

newlib вирішує це **реентерабельністю** (*reentrancy* — здатністю функції правильно працювати, коли її «перебили» посеред виконання). Уся змінна частина стану бібліотеки (`errno`, буфери `stdio`, стан `rand`, контекст `strtok`) винесена в структуру `struct _reent`. Активну структуру вказує глобальний покажчик `_impure_ptr`; макрос `errno` насправді розкривається в поле `_impure_ptr->_errno`.

Звідси два способи зробити libc потокобезпечною:

- **Перемикати `_impure_ptr` на кожному контекст-світчі.** Кожна задача дістає власну `struct _reent` (newlib додає ~96 байтів на задачу), а планувальник при переключенні ставить `_impure_ptr` на reent поточної задачі.
- **Збирати newlib із `__DYNAMIC_REENT__`.** Тоді `errno` розкривається не в `_impure_ptr`, а у виклик `__getreent()`, який платформа реалізує сама — повертаючи reent поточної задачі. Цей спосіб новіший і не вимагає чіпати `_impure_ptr` руками.

```c
// ESP-IDF іде другим шляхом: кожна задача FreeRTOS тримає власну _reent у TCB,
// а __getreent() повертає її. Тому errno у вас і так потокобезпечний — за рахунок
// ~96 байтів на задачу. Якщо порт цього НЕ робить, errno стає спільним глобалом,
// і дві задачі, що читають його, бачитимуть чужі помилки.

struct _reent *__getreent(void) {
    return &pxCurrentTCB->xNewLib_reent;   // спрощено: reent із блоку керування задачею
}
```

Практичний наслідок для діагностики: дивний `errno`, що «стрибає» між задачами, — не ваш баг, а ознака, що reent не перемикається. На ESP-IDF це працює з коробки; на саморобному порті це треба свідомо ввімкнути, інакше потокобезпечні на вигляд `strtol`/`malloc`/`printf` тихо труять одне одному стан.

## newlib-nano: де урізали

Коли Flash і RAM лічені, тулчейн пропонує **newlib-nano** — ту саму бібліотеку з вирізаним «дорогим». Зрізане б'є саме там, де новачок не чекає:

- **`printf`/`scanf` без плаваючої коми за замовчуванням.** `printf("%f", 3.14)` у nano виведе порожнечу або сміття, доки не злінкуєте з прапором `-u _printf_float` (підтягнути ваговиту float-гілку явно). Це економить кілобайти, бо форматування `double` тягне велику частину libm.
- **Спрощений алокатор і реентерабельність.** Структура `_reent` у nano менша, частина перевірок прибрана.
- **Менше locale й широких символів.** Багатобайтні рядки, локалі — або відсутні, або скорочені до C-locale.

Пастка проста: код, що працював із повним newlib, після переходу на nano раптом мовчить на `%f` або калічить `%g`. Лік — або явно ввімкнути float-форматування прапором, або (краще для МК) узагалі не форматувати числа з комою, а виводити фіксованою комою цілими.

## Як скласти це докупи

Порядок дій на новій платформі без готового SDK складається в короткий рецепт:

1. У лінкер-скрипті переконатися, що є символ кінця `.bss` (`_end`) і вершини стека (`_estack`) — без них `_sbrk` не знатиме меж купи.
2. Написати `_sbrk` із перевіркою колізії зі стеком (повертати `-1` і `ENOMEM` на межі).
3. Написати `_write`/`_read` на ваш UART — це оживить `printf`/`scanf`.
4. Додати чесні заглушки `_close`/`_lseek`/`_isatty`/`_fstat`/`_exit`/`_kill`/`_getpid`, щоб лінкер не лаявся, а `stdio` обрав правильну (небуферизовану) поведінку через `_fstat = S_IFCHR`.
5. Якщо є RTOS — упевнитися, що `errno`/reent перемикається на задачу (на ESP-IDF — уже так).

Після цих п'яти кроків злінкована libc перестає бути декорацією: `printf` виводить, `malloc` виділяє, `errno` каже правду — і голе залізо нарешті поводиться як «майже ПК», рівно настільки, наскільки ви самі принесли йому опору.
