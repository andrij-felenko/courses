# 📋 Довідник операцій, станів та інваріантів каналів

Цей довідник містить повну контрактну специфікацію, таблиці переходів станів, правила впорядкування пам'яті та механізми діагностики для типізованих каналів передачі повідомлень за моделлю CSP (Communicating Sequential Processes).

### Базові операції та сигнатури контрактів

Кожен рантайм, що реалізує семантику CSP, надає набір фундаментальних примітивів для створення, передачі, отримання, закриття та мультиплексування каналів.

| Операція | Призначення | Семантика блокування | Результат виконання |
| :--- | :--- | :--- | :--- |
| `make(chan T, cap)` | Створення дескриптора каналу типу `T` з місткістю буфера `cap` | Не блокує | Повертає валідне посилання на канал |
| `send(c, val)` | Запис значення `val` у канал `c` | Блокує, якщо буфер повний або `cap == 0` без активного читача | Успіх або виняткова ситуація (якщо канал закритий) |
| `recv(c)` | Вилучення чергового значення з каналу `c` | Блокує, якщо буфер порожній і канал відкритий | Повертає `(val, ok)`: `ok=true` для валідних даних, `ok=false` при вичерпанні закритого каналу |
| `try_send(c, val)` | Неблокувальна спроба запису значення | Ніколи не блокує | Повертає статус успіху або `WouldBlock` |
| `try_recv(c)` | Неблокувальна спроба читання значення | Ніколи не блокує | Повертає значення або індикатор відсутності даних |
| `close(c)` | Переведення каналу в термінальний стан | Не блокує | Широкомовне сповіщення всіх заблокованих потоків |
| `select(cases...)` | Атомарний недетермінований вибір готової події | Блокує, якщо жодна гілка не готова і відсутній `default` | Виконує тіло рівно однієї обраної гілки |

### Детальний опис семи станів дескриптора каналу

Дескриптор каналу протягом свого життєвого циклу перебуває в одному з семи чітко розмежованих станів. Поведінка рантайму для кожної операції детерміновано визначається поточним станом:

1. **Нільний канал (Nil Channel / Null Pointer):** Дескриптор не ініціалізовано (значення змінної дорівнює `nil` або `nullptr`).
   - Операція `send` блокує потік назавжди.
   - Операція `recv` блокує потік назавжди.
   - Операція `close` викликає негайну аварійну зупинку (паніку або розіменування нульового покажчика).
   - У виразі `select` гілка з нільним каналом вважається неактивною і ніколи не обирається. Це використовується як спеціальний патерн для динамічного вимкнення окремих гілок вибору без перебудови керуючої конструкції.

2. **Відкритий синхронний канал (Open Unbuffered, `cap == 0`):** Внутрішній буфер відсутній.
   - Операція `send` блокує відправника у черзі `sendq` до появи активного отримувача.
   - Операція `recv` блокує отримувача у черзі `recvq` до появи відправника.
   - Передача даних здійснюється шляхом прямого копіювання зі стека відправника у стек отримувача.

3. **Відкритий буферизований канал з вільним місцем (Open Buffered, `0 < count < cap`):**
   - Операція `send` записує елемент у кільцевий буфер за індексом `tail`, інкрементує лічильник елементів і повертає керування миттєво.
   - Операція `recv` вилучає елемент за індексом `head`, декрементує лічильник і повертає значення з прапорцем `ok = true`.

4. **Відкритий буферизований канал, заповнений вщент (Open Buffered Full, `count == cap`):**
   - Операція `send` блокує відправника у черзі `sendq`.
   - Операція `recv` забирає найстаріший елемент, звільняє комірку буфера, пробуджує першого відправника з черги `sendq`, переносячи його дані в буфер, і повертає прочитане значення.

5. **Відкритий буферизований канал, порожній (Open Buffered Empty, `count == 0`):**
   - Операція `send` записує елемент у буфер або пробуджує першого заблокованого читача з черги `recvq`.
   - Операція `recv` блокує отримувача у черзі `recvq`.

6. **Закритий канал із залишками даних (Closed Non-Empty, `closed == true && count > 0`):**
   - Операція `send` заборонена і викликає аварійну паніку.
   - Операція `recv` успішно вилучає накопичені в буфері елементи по одному, повертаючи `(val, true)`.
   - Повторний виклик `close` заборонений і викликає паніку.

7. **Закритий порожній канал (Closed Empty, `closed == true && count == 0`):**
   - Операція `send` заборонена і викликає паніку.
   - Операція `recv` ніколи не блокує потік: вона негайно повертає дефолтне нульове значення типу даних каналу та прапорець `ok = false`.
   - Повторний виклик `close` заборонений і викликає паніку.

### Матриця переходів і поведінки операцій

| Стан каналу | Операція `send(c, v)` | Операція `recv(c)` | Операція `close(c)` |
| :--- | :--- | :--- | :--- |
| **Нільний канал (`nil`)** | Блокує потік назавжди | Блокує потік назавжди | Аварія (Panic / SIGSEGV) |
| **Синхронний відкритий** | Рандеву або блок у `sendq` | Рандеву або блок у `recvq` | Закриває, будить усіх очікуючих |
| **Буферизований (є місце)** | Запис у буфер, успіх | Вилучення з буфера, `(val, true)` | Закриває, зберігає дані |
| **Буферизований (повний)** | Блок у `sendq` до звільнення | Вилучення з буфера, будить `sendq` | Закриває, зберігає дані |
| **Буферизований (порожній)** | Запис у буфер, будить `recvq` | Блок у `recvq` до надходження | Закриває, будить `recvq` з `ok=false` |
| **Закритий (є дані)** | Аварія (Panic / Error) | Вилучення з буфера, `(val, true)` | Аварія (Panic / Double Close) |
| **Закритий (порожній)** | Аварія (Panic / Error) | Дефолтне значення, `(zero, false)` | Аварія (Panic / Double Close) |

### Інваріанти синхронізації пам'яті та відношення Happens-Before

Канали є не лише механізмом транспортування даних, а й формальними бар'єрами синхронізації пам'яті відповідно до моделей пам'яті сучасних мов програмування (Go Memory Model, C++20 Memory Model, Rust Memory Model):

1. **Синхронізація передачі даних (Send Synchronizes-With Receive):**
   Успішне відправлення значення в канал суворо передує у відношенні *happens-before* завершенню відповідної операції отримання з цього ж каналу.
   Якщо потік `A` записує значення у звичайну пам'ять `x = 42`, після чого викликає `send(c, 1)`, а потік `B` виконує `<-c` і після цього читає `x`, потоку `B` гарантовано видно запис `x = 42`. Жодних додаткових замків чи атоміків для захисту `x` не потрібно.

2. **Синхронізація закриття каналу (Close Synchronizes-With Final Receive):**
   Виклик операції `close(c)` суворо передує у відношенні *happens-before* поверненню нульового значення `ok = false` у будь-якому потоці, що читає з цього каналу. Усі побічні ефекти в пам'яті, створені потоком-відправником до моменту закриття каналу, гарантовано стають видимими для всіх потоків, що отримали сигнал закриття.

3. **Інваріант передачі повного володіння (Exclusive Ownership Transfer):**
   Якщо через канал передається покажчик або посилання на структуру в купі, відправник зобов'язаний повністю відмовитися від подальшого читання або мутації цього об'єкта. Порушення цього інваріанта призводить до прихованих гонок даних поза контролем рантайму каналів.

### Контрактні гарантії мультиплексора `select`

1. **Одночасна готовність кількох каналів:** Якщо в момент виконання оператора `select` готові до передачі дві або більше гілок `case`, рантайм здійснює вибір гілки за псевдовипадковим законом із рівномірним розподілом імовірностей. Це запобігає системному голодуванню нижніх гілок.
2. **Атомарність блокування:** Якщо жодна гілка не готова, потік блокується атомарно щодо всіх задіяних каналів. Неможлива ситуація, коли потік пропустив подію в одному каналі через затримку реєстрації в іншому.
3. **Неблокувальний запит (`default`):** Якщо в блоці `select` оголошено секцію `default:`, блокування потоку не відбувається за жодних обставин. Якщо жоден канал не готовий, тіло `default` виконується негайно.

### Системна діагностика та аналіз блокувань

Під час профілювання висококонкурентних систем стан каналів аналізується через інструменти діагностики рантайму:

- **Стан `chan send` у стек-трейсі:** Потік зупинено в очікуванні звільнення буфера або появи читача на синхронному каналі. Якщо такий стан зберігається тривалий час, це свідчить про перевантаження споживача або витік горутини.
- **Стан `chan receive` у стек-трейсі:** Потік очікує на появу повідомлення з порожнього каналу.
- **Стан `chan send (nil chan)` або `chan receive (nil chan)`:** Спроба взаємодії з неініціалізованим каналом, що призводить до перманентного зависання потоку.
- **Профілювання витоків через `pprof`:** Знімок профілю горутин (`goroutine profile`) дозволяє миттєво локалізувати накопичення заблокованих задач, згрупованих за адресою виклику `runtime.chansend` або `runtime.chanrecv`.
