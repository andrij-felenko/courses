# 📋 Системні інтерфейси та контракти локального протитиску

Керування зворотним тиском у локальній системі базується на контрактах між користувацьким процесом та ядром операційної системи (дескриптори файлів, пайпів і сокетів) або між асинхронними модулями всередині одного адресного простору (рантайми потоків та циклів подій). У цьому довіднику зведено системні виклики, прапорці конфігурації, коди помилок, інспекційні інтерфейси procfs/sysfs та сигнатури інтерфейсів, які забезпечують контроль переповнення черг.

### 1. Системні виклики POSIX: Пайпи та міжпроцесні канали

Пайпи (`pipes`) є базовим примітивом міжпроцесного обміну даними (IPC) в операційних системах сімейства Unix.

| Системний виклик / Функція | Заголовний файл | Призначення в механізмі протитиску |
| :--- | :--- | :--- |
| `pipe(int pipefd[2])` | `<unistd.h>` | Створює односпрямований канал даних із блокуючим буфером за замовчуванням. |
| `pipe2(int pipefd[2], int flags)` | `<unistd.h>`, `<fcntl.h>` | Створює канал із прапорцями `O_NONBLOCK` (неблокуючий) та `O_CLOEXEC`. |
| `fcntl(fd, F_GETPIPE_SZ)` | `<fcntl.h>` | Повертає поточний розмір буфера пайпа ядра в байтах (Linux 2.6.35+). |
| `fcntl(fd, F_SETPIPE_SZ, size)` | `<fcntl.h>` | Динамічно змінює ємність буфера пайпа (округлюється до розміру сторінки пам'яті). |

#### Константи та системні обмеження ядра Linux

- `PIPE_BUF` (4096 байтів на Linux): Максимальний розмір запису, для якого ядро гарантує **атомарність**. Записи розміром `<= PIPE_BUF` ніколи не перемішуються з даними інших паралельних процесів. Якщо виробник записує більше ніж `PIPE_BUF` байтів, а вільне місце в буфері менше за розмір запису, ядро має право записати лише частину даних, змушуючи джерело очікувати або повертаючи частковий результат.
- За замовчуванням розмір буфера пайпа в сучасних ядрах Linux становить **65 536 байтів (64 КБ)**, що відповідає 16 сторінкам пам'яті по 4 КБ.
- `/proc/sys/fs/pipe-max-size`: Глобальний системний ліміт максимального розміру буфера пайпа, який дозволено виділяти непривілейованим процесам користувача (типове значення — 1 МБ).
- `/proc/sys/fs/pipe-user-pages-hard`: Системний ліміт загальної кількості сторінок оперативної пам'яті, які один користувач (`UID`) має право сукупно виділити під буфери всіх створених пайпів.

#### Коди повернення та системні помилки POSIX

- `EAGAIN` або `EWOULDBLOCK`: Буфер каналу повністю заповнений у неблокуючому режимі (`O_NONBLOCK`). Це однозначний сигнал джерелу: призупинити надсилання байтів і чекати сповіщення від підсистеми опитування дескрипторів.
- `EPIPE`: Спроба запису в пайп або сокет, де закритий кінець читання (`closed reader`). Ядро також надсилає процесу асинхронний сигнал `SIGPIPE`. Якщо сигнал не перехоплено, процес аварійно завершує роботу.
- `EINTR`: Системний виклик `write()` було перервано обробником системного сигналу до того, як вдалося записати байти. Вимагає повторення спроби запису залишку буфера.

#### Безкопіювальна передача через `splice(2)` та протитиск ядра

Системний виклик `splice(2)` переміщує дані між двома дескрипторами (один із яких обов'язково є пайпом) без копіювання байтів через простір користувача:

```
[Вхідний сокет] ──splice()──> [Пайп ядра: буфер сторінок] ──splice()──> [Вихідний файл]
```

Якщо вихідний дескриптор сповільнює споживання (наприклад, дисковий масив зайнятий скиданням кешу), буфер сторінок пайпа заповнюється. При досягненні ліміту виклик `splice()` блокується або повертає `EAGAIN` (з прапорцем `SPLICE_F_NONBLOCK`), транслюючи зворотний тиск на вхідний мережевий сокет без участі коду користувача.

### 2. Буфери локальних сокетів (AF_UNIX та Loopback TCP)

Для передачі потокових повідомлень через сокети домену Unix (`AF_UNIX`) та локальні TCP-петлі (`127.0.0.1`) розмір черги ядра контролюється опціями сокетів підсистеми `SOL_SOCKET`.

| Опція сокета | Рівень (`level`) | Тип аргументу | Опис поведінки |
| :--- | :--- | :--- | :--- |
| `SO_SNDBUF` | `SOL_SOCKET` | `int` | Максимальний розмір буфера відправки ядра (Send Buffer). При заповненні `write()` блокується або повертає `EAGAIN`. |
| `SO_RCVBUF` | `SOL_SOCKET` | `int` | Розмір буфера прийому ядра (Receive Buffer). При заповненні сокет сигналізує відправнику нульове вікно (TCP Zero Window) або призупиняє передачу. |

#### Інспекція заповненості черг сокетів

Для динамічного моніторингу черг без блокування застосовують спеціальні керуючі виклики `ioctl`.

:::tabs
```c
#include <sys/ioctl.h>
#include <linux/sockios.h>
#include <unistd.h>
#include <stdio.h>

/* Отримання поточного стану черг сокета ядра */
int get_socket_queue_depth(int sock_fd, int *rx_bytes, int *tx_bytes) {
    /* Кількість байтів, готових до читання у вхідному буфері ядра */
    if (ioctl(sock_fd, FIONREAD, rx_bytes) == -1) {
        return -1;
    }
    /* Кількість байтів, які ще не надіслані у вихідному буфері ядра */
    if (ioctl(sock_fd, SIOCOUTQ, tx_bytes) == -1) {
        return -1;
    }
    return 0;
}
```
```cpp
#include <sys/ioctl.h>
#include <linux/sockios.h>
#include <unistd.h>
#include <expected>
#include <system_error>

struct SocketQueueDepth {
    int rx_bytes{0}; // Непрочитані байти у вхідному буфері
    int tx_bytes{0}; // Ненадіслані байти у вихідному буфері
};

// Безпечне отримання глибини черг сокета засобами C++
std::expected<SocketQueueDepth, std::error_code> get_socket_queue_depth(int sock_fd) {
    SocketQueueDepth depth{};
    if (::ioctl(sock_fd, FIONREAD, &depth.rx_bytes) == -1) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    if (::ioctl(sock_fd, SIOCOUTQ, &depth.tx_bytes) == -1) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    return depth;
}
```
:::

#### Системні параметри ядра для налаштування пам'яті сокетів

- `/proc/sys/net/core/wmem_default` та `rmem_default`: розміри буферів відправки та прийому сокетів за замовчуванням у байтах (типово 212 992 байти).
- `/proc/sys/net/core/wmem_max` та `rmem_max`: жорстка верхня межа пам'яті, яку процес може запросити через `setsockopt(SO_SNDBUF)`.
- `/proc/sys/net/ipv4/tcp_wmem` (три числа: `min`, `default`, `max`): діапазон автопідбору розміру вікна передачі TCP ядра. При локальному IPC автопідбір розширює вікно до максимуму, що за відсутності протитиску в користувацькому коді може призводити до накопичення мегабайтів непотрібних даних у чергах ядра.

### 3. Мультиплексування та маски готовності (Linux epoll)

У високопродуктивних асинхронних архітектурах протитиск реалізується через динамічне перемикання прапорців готовності дескрипторів у системі `epoll`.

| Операція (`op`) | Прапорець події | Призначення в ланцюгу протитиску |
| :--- | :--- | :--- |
| `EPOLL_CTL_MOD` | `EPOLLIN` | **Читання джерела:** Якщо внутрішня черга застосунку переповнена, застосунок знімає `EPOLLIN`. Ядро перестає будити процес новими пакетами, примушуючи відправника чекати. |
| `EPOLL_CTL_MOD` | `EPOLLOUT` | **Запис у приймач:** Реєструється виключно тоді, коли виклик `write()` повернув `EAGAIN`. Як тільки ядро звільняє місце в буфері сокета, epoll сигналізує готовність до запису. |
| `EPOLL_CTL_MOD` | `0` (пуста маска) | Тимчасове повне вимкнення моніторингу дескриптора на час важкої локальної обробки. |
| `EPOLL_CTL_DEL` | — | Повне видалення дескриптора з таблиці інтересів ядра при закритті з'єднання. |

#### Керування маскою дескриптора для увімкнення та вимкнення читання

:::tabs
```c
#include <sys/epoll.h>
#include <stdbool.h>
#include <errno.h>

/* Призупинення або відновлення читання з дескриптора джерела */
int toggle_source_reading(int epfd, int source_fd, bool enable_reading) {
    struct epoll_event ev;
    ev.events = enable_reading ? (EPOLLIN | EPOLLRDHUP) : 0;
    ev.data.fd = source_fd;

    if (epoll_ctl(epfd, EPOLL_CTL_MOD, source_fd, &ev) == -1) {
        return -errno;
    }
    return 0;
}
```
```cpp
#include <sys/epoll.h>
#include <cerrno>
#include <expected>
#include <system_error>

// Ідіоматичне керування маскою epoll для асинхронного протитиску
std::expected<void, std::error_code> toggle_source_reading(int epfd, int source_fd, bool enable_reading) {
    epoll_event ev{};
    ev.events = enable_reading ? (EPOLLIN | EPOLLRDHUP) : 0;
    ev.data.fd = source_fd;

    if (::epoll_ctl(epfd, EPOLL_CTL_MOD, source_fd, &ev) == -1) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    return {};
}
```
:::

#### Відмінність між режимами Level-Triggered та Edge-Triggered (`EPOLLET`)

Підсистема epoll підтримує два принципово різних режими сповіщення про готовність дескрипторів:
1. **Level-Triggered (за замовчуванням):** epoll повертає подію `EPOLLOUT` на кожній ітерації циклу подій, доки в буфері сокета є вільне місце. Якщо черга порожня, застосунок **зобов'язаний негайно зняти прапорець `EPOLLOUT`**, інакше цикл подій зазнає 100% утилізації процесора через нескінченні миттєві пробудження.
2. **Edge-Triggered (`EPOLLET`):** подія генерується **лише в момент зміни стану** (переходу від переповненого буфера до наявності вільного місця). Застосунок зобов'язаний викликати `write()` у циклі до отримання коду `EAGAIN`. Якщо не вичитати або не записати весь буфер до кінця, наступне сповіщення не надійде ніколи, що призведе до мертвого зависання потоку даних.

#### Канонічний алгоритм асинхронного дренажу черги

1. Застосунок отримує порцію байтів і виконує запис у дескриптор: `bytes = write(fd_out, buf, len)`.
2. Якщо `bytes < len` або виклик повернув помилку `errno == EAGAIN`:
   - Залишок невідправлених даних зберігається у внутрішній черзі користувацького простору.
   - Дескриптор `fd_out` реєструється на подію `EPOLLOUT`.
   - Вхідний дескриптор `fd_in` призупиняється (з нього знімається прапорець `EPOLLIN`).
3. При надходженні сповіщення `EPOLLOUT` від ядра:
   - Застосунок досилає залишок накопичених байтів у вихідний канал.
   - Як тільки локальна черга повністю спорожніла (`occupancy == 0`), прапорець `EPOLLOUT` **обов'язково знімається**.
   - На вхідний дескриптор `fd_in` повертається прапорець `EPOLLIN`, відновлюючи надходження нових даних.

### 4. Інспекція стану буферів через утиліти Linux

Для діагностики та простеження застряглих буферів у промисловій експлуатації застосовують стандартні системні інструменти:

- `ss -t -i -a`: відображає розмір вхідних (`Recv-Q`) та вихідних (`Send-Q`) черг усіх активних сокетів, а також статус TCP вікна (`wscale`, `rtt`, `cwnd`).
- `cat /proc/net/unix`: показує список локальних Unix-сокетів та стан прапорців їхніх внутрішніх черг.
- `bpftrace`: дозволяє підключитися до точок трасування ядра (`tracepoint:syscalls:sys_enter_write`) і фіксувати точну кількість подій повернення коду `EAGAIN` для виявлення вузьких місць у системі.
