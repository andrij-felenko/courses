# 📋 Інтерфейс та життєвий цикл libuv loop

Бібліотека **libuv** є еталонною високопродуктивною C-бібліотекою асинхронного введення-виведення на базі циклу подій. Вона абстрагує різнорідні низькорівневі механізми різних операційних систем — epoll на Linux, kqueue на macOS та BSD, IOCP на Windows та event ports на Solaris — надаючи розробникам єдиний, надійний та високопродуктивний програмний інтерфейс.

Цей довідник містить вичерпний системний опис структурного контракту головного циклу `uv_loop_t`, правил взаємодії з довгоживучими об’єктами (handles), короткоживучими запитами (requests), лічильником посилань та системним пулом робочих потоків.

---

### Життєвий цикл структури uv_loop_t

Структура `uv_loop_t` інкапсулює повний внутрішній стан екземпляра циклу подій: зареєстровані мережеві дескриптори, двійкову мін-купу таймерів, черги мікрозадач та системний дескриптор демультиплексора ядра.

| Функція | Повна сигнатура C | Системний контракт та поведінка |
| :--- | :--- | :--- |
| `uv_loop_init` | `int uv_loop_init(uv_loop_t* loop)` | Ініціалізує попередньо виділену структуру циклу. Створює системний дескриптор epoll або kqueue. Повертає 0 або системний код помилки (< 0). |
| `uv_default_loop` | `uv_loop_t* uv_default_loop(void)` | Повертає вказівник на глобальний цикл за замовчуванням процесу (ініціалізує його при першому зверненні). |
| `uv_run` | `int uv_run(uv_loop_t* loop, uv_run_mode mode)` | Запускає нескінченну диспетчеризацію фаз циклу подій у поточному системному потоці відповідно до обраного режиму mode. |
| `uv_stop` | `void uv_stop(uv_loop_t* loop)` | Виставляє внутрішній прапорець зупинки. Цикл перериває роботу після завершення поточної фази обробки. |
| `uv_loop_close` | `int uv_loop_close(uv_loop_t* loop)` | Звільняє всі внутрішні дескриптори ядра. Повертає UV_EBUSY, якщо в циклі залишилися активні чи незакриті дескриптори. |
| `uv_loop_alive` | `int uv_loop_alive(const uv_loop_t* loop)` | Повертає ненульове значення, якщо в циклі є активні об’єкти, що утримують його від завершення. |

### Режими виконання: uv_run_mode

Параметр `mode` у виклику `uv_run(loop, mode)` визначає тривалість роботи та політику блокування потоку:

```
[Виклик uv_run]
       │
       ├─► UV_RUN_DEFAULT ──► Працює нескінченно, поки є активні handles/requests
       │
       ├─► UV_RUN_ONCE ────► Рівно 1 оберт: очікує в epoll_wait, обслуговує і виходить
       │
       └─► UV_RUN_NOWAIT ──► Рівно 1 оберт: таймаут epoll_wait = 0, негайне повернення
```

1. **`UV_RUN_DEFAULT`**: Основний режим для мережевих серверів. Цикл неперервно виконує фази по колу доти, доки лічильник активних посилань не стане рівним нулю або доки не буде викликано функцію `uv_stop()`.
2. **`UV_RUN_ONCE`**: Виконує рівно один повний оберт (tick). Якщо готових подій немає, блокує потік у системному демультиплексорі ядра до надходження першого I/O-пакета або дедлайну найближчого таймера, виконує зворотні виклики і повертає керування викликачу.
3. **`UV_RUN_NOWAIT`**: Виконує неблокуючу перевірку стану демультиплексора з нульовим таймаутом. Якщо є готові сокети, їхні обробники виконуються негайно, після чого функція повертає керування без засинання. Ідеально підходить для інтеграції мережевої підсистеми в ігрові цикли та графічні інтерфейси користувача (UI).

### Контракт дескрипторів (Handles) та лічильник посилань

В архітектурі libuv усі сутності строго розділені на два класи:

* **Довгоживучі об’єкти (`uv_handle_t`)**: Представляють ресурси, що існують протягом тривалого часу (TCP-сокети `uv_tcp_t`, таймери `uv_timer_t`, сповіщувачі міжпотокової взаємодії `uv_async_t`, спостерігачі фаз `uv_prepare_t`, `uv_check_t`, `uv_idle_t`).
* **Короткоживучі запити (`uv_req_t`)**: Представляють окремі асинхронні операції (запит на відправку даних `uv_write_t`, підключення до сервера `uv_connect_t`, фонова задача пулу потоків `uv_work_t`, файлова операція `uv_fs_t`).

#### Керування лічильником посилань (uv_ref / uv_unref)
За замовчуванням кожен створений дескриптор handle збільшує лічильник активних посилань циклу, утримуючи його від завершення. Якщо сервер повинен виконувати фонову періодичну задачу (наприклад, надсилати статистику кожні 60 секунд), але не повинен висіти в пам’яті, коли всі клієнти відключилися, дескриптор таймера можна відв’язати:

:::tabs
@tab C
```c
// Вимкнення утримання циклу для фонового таймера
uv_unref((uv_handle_t*)&heartbeat_timer);

// Повернення утримання циклу (таймер знову блокує вихід)
uv_ref((uv_handle_t*)&heartbeat_timer);
```
@tab C++
```cpp
// Вимкнення утримання циклу для фонового таймера
uv_unref(reinterpret_cast<uv_handle_t*>(&heartbeat_timer));

// Повернення утримання циклу (таймер знову блокує вихід)
uv_ref(reinterpret_cast<uv_handle_t*>(&heartbeat_timer));
```
:::

#### Асинхронний протокол закриття дескрипторів: uv_close
У libuv **категорично заборонено викликати free() або видаляти пам’ять дескриптора до повного завершення системної процедури закриття**. Звільнення дескриптора відбувається у два етапи:

:::tabs
@tab C
```c
static void on_socket_closed(uv_handle_t *handle) {
    // Пам'ять дозволено звільняти ЛИШЕ всередині close-колбека!
    printf("Дескриптор успішно видалено з ядра, звільняємо пам'ять.
");
    free(handle);
}

void safe_close_client(uv_tcp_t *client) {
    // 1. Повідомляємо libuv про необхідність закриття
    uv_close((uv_handle_t*)client, on_socket_closed);
}
```
@tab C++
```cpp
auto on_socket_closed = [](uv_handle_t* handle) {
    // Пам'ять дозволено звільняти ЛИШЕ всередині close-колбека!
    std::cout << "Дескриптор успішно видалено з ядра, звільняємо пам'ять.
";
    delete reinterpret_cast<uv_tcp_t*>(handle);
};

void safe_close_client(uv_tcp_t* client) {
    // 1. Повідомляємо libuv про необхідність закриття
    uv_close(reinterpret_cast<uv_handle_t*>(client), on_socket_closed);
}
```

### Винесення важких операцій у пул потоків: uv_queue_work

Операції над локальною файловою системою в Linux не підтримують неблокуючий режим через epoll, а складні математичні обчислення (хешування паролів, стиснення даних) блокують головний потік. Для розв’язання цієї проблеми libuv надає внутрішній багатопотоковий пул робітників (розмір пулу за замовчуванням становить 4 потоки й налаштовується через змінну оточення `UV_THREADPOOL_SIZE`).

```
   Головний потік (Event Loop)                Пул робітників (Worker Threadpool)
 ┌─────────────────────────────┐            ┌──────────────────────────────────┐
 │ uv_queue_work(loop, req,    │ ──task───► │ Вільний потік пулу:              │
 │               work_cb,      │            │ виконує важкий work_cb()         │
 │               after_work_cb)│            │ (блокує лише себе, не loop!)     │
 │                             │ ◄─eventfd─ │ Сигналізує про завершення        │
 │ Фаза I/O Callbacks:         │            └──────────────────────────────────┘
 │ виконує after_work_cb()     │
 └─────────────────────────────┘
```

Повний робочий приклад делегування обчислень у пул робітників:

:::tabs
@tab C
```c
#include <stdio.h>
#include <stdlib.h>
#include <uv.h>

void heavy_work_task(uv_work_t *req) {
    // Виконується у фоновому потоці з пулу робітників!
    long sum = 0;
    for (long i = 0; i < 100000000L; ++i) {
        sum += i;
    }
    req->data = (void*)sum;
}

void on_work_completed(uv_work_t *req, int status) {
    // Виконується у головному потоці циклу подій!
    printf("Фонову задачу завершено, результат: %ld
", (long)req->data);
    free(req);
}

int main(void) {
    uv_loop_t *loop = uv_default_loop();

    uv_work_t *req = malloc(sizeof(uv_work_t));
    uv_queue_work(loop, req, heavy_work_task, on_work_completed);

    printf("Головний цикл подій запущено...
");
    uv_run(loop, UV_RUN_DEFAULT);

    uv_loop_close(loop);
    return 0;
}
```
@tab C++
```cpp
#include <iostream>
#include <memory>
#include <uv.h>

struct WorkTask {
    uv_work_t req;
    long result{0};
};

int main() {
    uv_loop_t* loop = uv_default_loop();

    auto task = std::make_unique<WorkTask>();
    task->req.data = task.get();

    auto work_cb = [](uv_work_t* req) {
        // Виконується у фоновому потоці з пулу робітників!
        auto* t = static_cast<WorkTask*>(req->data);
        long sum = 0;
        for (long i = 0; i < 100000000L; ++i) {
            sum += i;
        }
        t->result = sum;
    };

    auto after_work_cb = [](uv_work_t* req, int status) {
        // Виконується у головному потоці циклу подій!
        auto* t = static_cast<WorkTask*>(req->data);
        std::cout << "Фонову задачу завершено, результат: " << t->result << std::endl;
        delete t;
    };

    auto* raw_task = task.release();
    uv_queue_work(loop, &raw_task->req, work_cb, after_work_cb);

    std::cout << "Головний цикл подій запущено...
";
    uv_run(loop, UV_RUN_DEFAULT);

    uv_loop_close(loop);
    return 0;
}
```
:::

### Фази виконання одного оберту (Tick Lifecycle)

Кожен повний оберт циклу під час виконання `uv_run(loop, UV_RUN_DEFAULT)` проходить через строго детерміновану послідовність внутрішніх фаз. Розуміння черговості фаз є критичним для передбачення затримок та уникнення блокувань:

1. **Оновлення монотонного часу (`uv__update_time`)**: На початку ітерації цикл робить системний виклик для отримання поточного монотонного часу ядра і кешує його в структурі `loop->time`. Це запобігає надмірним системним викликам `clock_gettime` під час обробки тисяч дрібних подій.
2. **Обробка таймерів (`Timers Phase`)**: Цикл вилучає з мін-купи всі таймери `uv_timer_t`, дедлайн яких менший або дорівнює поточному кешованому часу `loop->time`, та послідовно викликає їхні функції зворотного виклику.
3. **Обробка відкладених колбеків (`Pending Callbacks / I/O Callbacks`)**: Виконуються обробники введення-виведення, які були відкладені з попередньої ітерації (наприклад, помилки попереднього запису в сокет або специфічні мережеві сповіщення).
4. **Фази підготовки (`Idle` та `Prepare Handles`)**: Виконуються обробники `uv_idle_t` (якщо вони активні) та `uv_prepare_t`. Фаза prepare виконується безпосередньо перед тим, як потік засне в демультиплексорі ядра, що дозволяє підготувати структури даних або скинути буфери.
5. **Розрахунок таймауту та очікування в ядрі (`I/O Poll Phase`)**: Цикл обчислює, скільки мілісекунд потік може спати в системному виклику демультиплексора (`epoll_wait` у Linux, `kevent` у BSD/macOS, `GetQueuedCompletionStatus` у Windows IOCP). Таймаут дорівнює різниці між дедлайном найближчого таймера в купі та поточним часом. Якщо в черзі є готові задачі `idle` або виставлено режим `UV_RUN_NOWAIT`, таймаут дорівнює 0. Після пробудження викликаються обробники всіх дескрипторів, для яких надійшли мережеві пакети чи події готовності сокетів.
6. **Фаза перевірки (`Check Handles`)**: Виконуються обробники `uv_check_t`. Ця фаза запускається негайно після повернення з демультиплексора введення-виведення. Саме на цій фазі в середовищі Node.js виконуються колбеки функції `setImmediate()`.
7. **Фаза закриття (`Close Callbacks`)**: Виконуються функції зворотного виклику для всіх дескрипторів, які були закриті за допомогою `uv_close()` під час поточного оберту. Лише після проходження цієї фази пам'ять дескриптора вважається остаточно вільною.

### Міжпотокова сигналізація: uv_async_t

Головний цикл подій зазвичай працює в одному виділеному системному потоці. Якщо зовнішній фоновий потік хоче передати повідомлення або викликати функцію в контексті циклу подій, прямий виклик призведе до стану гонитви (race condition).

Для безпечної передачі сигналів у libuv існує дескриптор `uv_async_t`:
1. Головний потік ініціалізує `uv_async_init(loop, &async_handle, async_cb)`.
2. Фоновий потік у будь-який момент викликає `uv_async_send(&async_handle)`.
3. `uv_async_send` здійснює запис у внутрішній системний сигнальний дескриптор (`eventfd` на Linux або `self-pipe` на POSIX) під м’ютексом.
4. Ядро ОС негайно будить системний демультиплексор циклу подій з `epoll_wait()`, і цикл виконує функцію `async_cb` у своєму власному потоці.

Особливість контракту `uv_async_send` полягає в тому, що багаторазові виклики можуть об’єднуватися в один виклик `async_cb` (coalescing), тому обмін даними між потоками зазвичай організовують через захищену потокобезпечну чергу або кільцевий буфер.

### Інтеграція системних сигналів та обробка помилок

Системні сигнали операційної системи (такі як `SIGINT`, `SIGTERM`, `SIGHUP`) у традиційних синхронних програмах переривають виконання довільної інструкції асемблера, що робить виклик більшості функцій стандартної бібліотеки небезпечним (не async-signal-safe). Бібліотека `libuv` повністю ізолює розробника від цієї небезпеки через дескриптор `uv_signal_t`.

Внутрішній механізм обробки сигналів у `libuv`:
* При виклику `uv_signal_init` та `uv_signal_start` бібліотека реєструє глобальний обробник сигналу через системний виклик `sigaction`.
* Всередині низькорівневого обробника сигналу єдиною дією є запис одного байта у внутрішній сигнальний пайп (або виклик `eventfd_write`), що є абсолютно безпечним з погляду async-signal-safety.
* Головний цикл подій тримає кінець цього сигнального каналу зареєстрованим у системному демультиплексорі `epoll`. Коли байт надходить, цикл прокидається на фазі I/O і викликає зареєстрований високорівневий колбек користувача у звичайному безпечному контексті стека головного потоку.

#### Таблиця типових системних статусів та кодів помилок libuv

Усі системні виклики `libuv` повертають від'ємні цілі числа у випадку помилки. Для отримання текстового опису використовують функції `uv_strerror(err)` та `uv_err_name(err)`:

| Код помилки libuv | Системний еквівалент | Причина виникнення та діагностика |
| :--- | :--- | :--- |
| `UV_EAGAIN` / `UV_EWOULDBLOCK` | `EAGAIN` | Ресурс тимчасово недоступний. Сокетний буфер порожній при читанні або переповнений при записі в неблокуючому режимі. |
| `UV_EBUSY` | `EBUSY` | Ресурс зайнятий. Спроба закрити цикл через `uv_loop_close`, коли в ньому залишаються активні дескриптори або незавершені запити. |
| `UV_ECANCELED` | `ECANCELED` | Операцію скасовано до її фактичного виконання (наприклад, через виклик `uv_cancel` для фонового запиту в пулі потоків). |
| `UV_ECONNREFUSED` | `ECONNREFUSED` | Віддалений сервер відхилив TCP-з'єднання (наприклад, цільовий порт не слухається демоном). |
| `UV_ECONNRESET` | `ECONNRESET` | З'єднання примусово розірвано віддаленим вузлом через відправку TCP-пакета `RST`. |
| `UV_EMFILE` / `UV_ENFILE` | `EMFILE` | Вичерпано системний ліміт відкритих файлових дескрипторів процесу або всієї операційної системи. |
| `UV_EINVAL` | `EINVAL` | Передано невалідний аргумент (наприклад, нульовий вказівник на дескриптор або некоректні прапорці запуску циклу). |
