# 🧮 Математичний аналіз пулу потоків: від закону Літтла до розміру черги

Вибір розміру пулу потоків і місткості черги завдань «на око» неминуче призводить до однієї з двох крайнощів: або процесорні ядра простоюють під час очікування операцій вводу-виводу, або система перевантажується сотнями конкуруючих потоків, а час відгуку зростає лавиноподібно. Щоб налаштувати пул передбачувано й утримати затримки в межах угоди про рівень послуг (SLA), інженеру потрібен математичний апарат: закон Літтла, баланс часу процесорного ядра та базова модель теорії масового обслуговування.

### 1. Закон Літтла та динаміка черги

Основою аналізу будь-якої системи обробки завдань є **закон Літтла** (англ. *Little's Law*), доведений Джоном Літтлом у 1961 році. Закон встановлює фундаментальний зв'язок між трьома стаціонарними характеристиками системи:
* `L` — середня кількість завдань, що перебувають у системі одночасно (у черзі та на виконанні);
* `λ` (лямбда) — середня інтенсивність надходження нових завдань (завдань за секунду, req/s);
* `W` — середній повний час перебування одного завдання в системі (секунд).

Закон Літтла стверджує, що для будь-якої стаціонарної системи:

```
L = λ · W
```

Повний час перебування завдання в системі `W` природно розкладається на дві складові: час очікування в черзі `W_queue` та безпосередній час обробки потоком-робітником `W_service`:

```
W = W_queue + W_service
```

Якщо застосувати закон Літтла окремо до черги очікування, отримаємо формулу для середньої довжини черги `L_queue`:

```
L_queue = λ · W_queue
```

Звідси випливає критичний системний наслідок: якщо інтенсивність вхідного потоку `λ` перевищує пропускну здатність пулу потоків `μ_total`, різниця `(λ - μ_total)` починає безперервно накопичуватися в черзі. Якщо черга є необмеженою, `W_queue` зростає лінійно з часом, а клієнти гарантовано отримують тайм-аут затримки.

### 2. Формула розрахунку кількості потоків Брайана Ґетца

Скільки потоків-робітників потрібно виділити пулу, щоб утилізувати процесорні ядра без зайвих накладних витрат? Відповідь залежить від профілю навантаження: чи обмежена задача суто обчисленнями (CPU-bound), чи вона проводить частину часу в очікуванні зовнішніх ресурсів — дисків, бази даних, мережевих відповідей (I/O-bound).

#### Виведення формули для змішаного навантаження

Нехай кожне завдання вимагає:
* `C` (Compute time) — сумарний час, протягом якого завдання реально виконує інструкції на ядрі процесора;
* `W_io` (Wait time) — час очікування операцій вводу-виводу, замків або віддалених сервісів, коли потік заблокований і не споживає такти ядра.

Повний час виконання одного завдання дорівнює `T_task = C + W_io`. Тоді коефіцієнт зайнятості процесорного ядра одним окремим потоком дорівнює частці часу `C` у загальному часі `T_task`:

```
η = C ÷ (C + W_io)
  = 1 ÷ (1 + W_io/C)
```

Якщо в системі працює пул із `N` однотипних потоків, сумарне навантаження, яке вони створюють на обчислювальні ядра, становить `N · η`.

Нехай апаратна платформа має `N_cpu` фізичних ядер (або логічних апаратних потоків у разі технології Hyper-Threading / SMT), а бажаний цільовий коефіцієнт завантаження процесора позначено як `U_cpu` (де `0.0 < U_cpu ≤ 1.0`, зазвичай обирають `0.70–0.80`).

Рівняння балансу використання обчислювальної потужності набуває вигляду:

```
N · η = N_cpu · U_cpu
```

Підставивши вираз для `η`, отримуємо класичну формулу розрахунку розміру пулу потоків, сформульовану архітектором мови Java Брайаном Ґетцом (Brian Goetz):

```
N = N_cpu · U_cpu · (1 + W_io / C)
```

#### Покроковий приклад розрахунку

Розглянемо практичну ситуацію: бекенд-сервіс працює на 8-ядерному сервері (`N_cpu = 8`). Цільове завантаження ядер встановлено на рівні 80% (`U_cpu = 0.80`), щоб лишити 20% запасу на піки та системні переривання. За даними профілювання, середня транзакція триває 100 мс, з яких 10 мс витрачається на парсинг JSON та бізнес-логіку (`C = 10` мс), а 90 мс — на очікування відповіді від реляційної СУБД (`W_io = 90` мс).

Обчислимо необхідну кількість потоків для пулу:

```
W_io / C
= 90 / 10                          [відношення часу очікування до обчислень]
= 9                                [один потік чекає в 9 разів довше, ніж рахує]

1 + W_io / C
= 1 + 9                            [мультиплікатор паралелізму]
= 10

N
= N_cpu · U_cpu · (1 + W_io / C)   [формула Ґетца]
= 8 · 0.80 · 10                    [підстановка параметрів системи]
= 6.4 · 10                         [добуток базової потужності на множник]
= 64                               [необхідний розмір пулу потоків]
```

Висновок: для повного навантаження 8 ядер на 80% системі необхідно утримувати рівно 64 активних потоки-робітники.

### 3. Модель масового обслуговування M/M/k та ефект насичення

Щоб оцінити, що відбувається із затримкою обробки при коливаннях навантаження, звернемося до теорії масового обслуговування (теорії черг). Пул із `k` потоків-робітників моделюється як система типу **M/M/k**:
* Перша `M` (Markovian) — Пуассонівський потік вхідних заявок із параметром `λ` (інтервали між запитами розподілені експоненційно);
* Друга `M` — тривалість обслуговування кожної заявки розподілена за експоненційним законом із середньою інтенсивністю `μ` (де `1/μ = C` — середній час роботи потоку над задачею);
* `k` — кількість паралельних обслуговуючих каналів (потоків-робітників у нашому пулі).

#### Коефіцієнт завантаження системи (System Utilization)

Сумарна продуктивність `k` потоків становить `k · μ`. Коефіцієнт навантаження системи `ρ` (ро) визначається як відношення швидкості надходження задач до максимальної швидкості їх виконання:

```
ρ = λ ÷ (k · μ)
```

Головна умова стаціонарності черги (щоб черга не зростала до нескінченності):

```
ρ < 1.0
```

#### Ймовірність очікування та формула Ерланга C

Ймовірність того, що новоприбула задача застане всі `k` потоків зайнятими і змушена буде чекати в черзі, визначається **формулою Ерланга C** (англ. *Erlang C formula*). Позначимо запропоноване навантаження в ерлангах як `a = λ / μ`:

```
P_wait = C(k, a)
       = [ aᵏ ÷ (k! · (1 - ρ)) ] ÷ [ ∑ᵢ₌₀ᵏ⁻¹ (aⁱ ÷ i!) + aᵏ ÷ (k! · (1 - ρ)) ]
```

Середній час очікування в черзі `W_queue` для системи M/M/k виражається через `P_wait`:

```
W_queue = P_wait ÷ [ k · μ · (1 - ρ) ]
```

А повний середній час відгуку системи `T_response` становить:

```
T_response = W_queue + 1/μ
           = 1/μ · [ 1 + P_wait ÷ (k · (1 - ρ)) ]
```

#### Ефект «хокейної ключки» (Hockey Stick Effect)

Зверніть увагу на знаменник `(1 - ρ)` у формулі часу очікування. При зростанні коефіцієнта завантаження `ρ`:
* Коли `ρ = 0.50` (50% навантаження), `1 / (1 - ρ) = 2.0` — затримка черги мінімальна;
* Коли `ρ = 0.80` (80% навантаження), `1 / (1 - ρ) = 5.0` — система працює стабільно з помірною чергою;
* Коли `ρ = 0.95` (95% навантаження), `1 / (1 - ρ) = 20.0` — затримка черги зростає у 4 рази порівняно з рівнем 80%;
* Коли `ρ → 1.00`, знаменник прямує до нуля, а середній час відгуку прямує до нескінченності: `T_response → ∞`.

```
Залежність коефіцієнта затримки f(ρ) = 1 / (1 - ρ):
ρ = 0.00 ──► f(ρ) = 1.0  [ідеальний час без черги]
ρ = 0.50 ──► f(ρ) = 2.0
ρ = 0.75 ──► f(ρ) = 4.0
ρ = 0.85 ──► f(ρ) = 6.67  ──► Точка перегину (Knee)
ρ = 0.95 ──► f(ρ) = 20.0
ρ = 0.99 ──► f(ρ) = 100.0 [колапс системи, тайм-аути]
```

Графік функції `1 / (1 - ρ)` нагадує хокейну ключку: пологий підйом до 75–80% і майже вертикальний зліт після 85%. Саме тому на практиці розмір пулу розраховують так, щоб при типовому піковому навантаженні система перебувала в робочій зоні `ρ ≤ 0.75–0.80`.

### 4. Розрахунок місткості черги завдань (Queue Capacity)

Обмеження черги (Bounded Queue) — це головний запобіжник від вичерпання пам'яті (Out-Of-Memory) та деградації затримки. Якщо черга заповнена, нові задачі не повинні прийматися, а система має застосувати зворотний тиск (Backpressure).

#### Розрахунок граничного розміру черги за SLA

Нехай клієнтська угода про рівень обслуговування (SLA) встановлює максимально допустимий час очікування задачі в черзі `T_wait_max` (після якого клієнт скидає з'єднання за тайм-аутом). Якщо пікова швидкість надходження нових завдань становить `λ_peak`, то максимальна кількість задач `Q_max`, яку має сенс утримувати в черзі, визначається безпосередньо з закону Літтла:

```
Q_max = λ_peak · T_wait_max
```

Тримати чергу більшого розміру шкідливо: будь-яке завдання, що стало в чергу за позицією `Q_max`, гарантовано проведе в черзі час `T > T_wait_max`, отримає тайм-аут на клієнті, але все одно з'їсть ресурси потоку-робітника пізніше (марна робота).

#### Приклад розрахунку місткості та споживання пам'яті

Нехай веб-сервіс очікує піковий наплив `λ_peak = 2000` req/s. Клієнтський тайм-аут очікування становить 250 мс (`T_wait_max = 0.25` с). Кожен об'єкт задачі в черзі (дескриптор, захоплені аргументи, замикання лямбди) займає в купі в середньому 256 байтів (`sizeof(Task) = 256`).

Розрахуємо місткість черги та обсяг оперативної пам'яті:

```
Q_max
= λ_peak · T_wait_max              [закон Літтла для максимальної черги]
= 2000 · 0.25                      [2000 запитів/с протягом 250 мс]
= 500                              [максимальна кількість слотів у черзі]

M_queue
= Q_max · sizeof(Task)             [обсяг оперативної пам'яті для черги]
= 500 · 256                        [500 задач по 256 байтів]
= 128000                           [байтів]
= 128                              [кілобайтів]
```

Висновок: обмеження черги величиною у 500 елементів гарантує, що час очікування в черзі ніколи не перевищить 250 мс при навантаженні до 2000 req/s, а вся черга забиратиме лише 128 КБ пам'яті. Усі запити понад цю межу повинні негайно відхилятися через механізм швидкої відмови (Fast Fail), сигналізуючи клієнтам про перевантаження (код HTTP 429 Too Many Requests або 503 Service Unavailable).
