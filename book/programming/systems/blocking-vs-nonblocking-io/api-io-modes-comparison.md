# 📋 Специфікація режимів вводу-виводу, прапорців та кодів помилок POSIX

Цей довідник містить вичерпну контрактну специфікацію системних прапорців, функцій конфігурації, кодів помилок ядра та поведінкових гарантій для блокуючого й неблокуючого вводу-виводу в операційних системах сімейства POSIX (Linux, FreeBSD, macOS) та їхніх еквівалентів у Windows Winsock.

---

### Механізми встановлення неблокуючого режиму

У системному програмуванні переведення дескриптора в неблокуючий стан здійснюється двома основними шляхами: динамічною зміною прапорців відкритого файлового опису або атомарним створенням дескриптора з уже встановленим прапорцем.

#### 1. Модифікація через `fcntl()`

Системний виклик `fcntl()` маніпулює прапорцями стану відкритого файлу (`struct file` у ядрі).

:::tabs
```c
int set_nonblocking(int fd) {
    int flags = fcntl(fd, F_GETFL, 0);
    if (flags == -1) return -1;
    return fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}
```
```cpp
bool set_nonblocking(int fd) noexcept {
    int flags = ::fcntl(fd, F_GETFL, 0);
    if (flags == -1) return false;
    return ::fcntl(fd, F_SETFL, flags | O_NONBLOCK) != -1;
}
```
:::

- **Область дії**: Прапорець `O_NONBLOCK` зберігається в системному описі відкритого файлу (*open file description*), а не в таблиці дескрипторів конкретного процесу. Це означає, що якщо дескриптор було продубльовано через `dup()`, `dup2()` або успадковано дочірнім процесом через `fork()`, зміна прапорця в одному дескрипторі негайно вплине на всі пов'язані дескриптори в усіх процесах.
- **Вимога збереження попередніх прапорців**: Ніколи не слід викликати `fcntl(fd, F_SETFL, O_NONBLOCK)` без попереднього `F_GETFL`, оскільки це затре інші важливі прапорці стану (наприклад, `O_APPEND` чи `O_ASYNC`).

#### 2. Атомарне створення сокетів та каналів

У багатопотокових системах роздільний виклик `socket()` та `fcntl()` створює стан перегонів (*race condition*): якщо між створенням сокета й встановленням `O_NONBLOCK` інший потік викличе `fork()` та `execve()`, дескриптор може випадково витекти в дочірній процес у блокуючому стані. Для усунення цієї вразливості сучасні стандарти надають атомарні прапорці:

- **`SOCK_NONBLOCK`**: передається безпосередньо у виклик `socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0)` або `socketpair()`.
- **`accept4()`**: розширення Linux/FreeBSD, що дозволяє приймати вхідне клієнтське з'єднання й одразу створювати новий клієнтський сокет із прапорцями `SOCK_NONBLOCK | SOCK_CLOEXEC`.
- **`pipe2()`**: атомарне створення пари дескрипторів каналу з прапорцем `O_NONBLOCK`.

#### 3. Одноразовий прапорець `MSG_DONTWAIT`

Якщо сокет сконфігуровано як звичайний блокуючий, але програмі необхідно виконати одну окрему операцію без зупинки потоку, системні виклики `recv()`, `recvfrom()`, `send()`, `sendto()` та `sendmsg()` приймають бітовий прапорець `MSG_DONTWAIT`. Він активує неблокуючу семантику виключно на час виконання цього єдиного виклику.

### Контракт системних викликів read() та write()

Контракт вводу-виводу в POSIX спирається на три взаємовиключні випадки повертаного значення типу `ssize_t`:

```
                       ┌──────────────────────────────────────┐
                       │   РЕЗУЛЬТАТ ВИКЛИКУ read() / write() │
                       └──────────────────┬───────────────────┘
                                          │
            ┌─────────────────────────────┼─────────────────────────────┐
            ▼                             ▼                             ▼
   ┌───────────────────┐        ┌───────────────────┐        ┌───────────────────┐
   │    n > 0 (УСПІХ)  │        │     n == 0 (EOF)  │        │   n == -1 (ПОМИЛКА│
   ├───────────────────┤        ├───────────────────┤        ├───────────────────┤
   │ Передано n байтів │        │ Канал/сокет       │        │ Операція не вдала-│
   │ (можливий частко- │        │ закрито віддале-  │        │ ся. Код причини   │
   │ вий трансфер).    │        │ ною стороною.     │        │ збережено в errno.│
   └───────────────────┘        └───────────────────┘        └───────────────────┘
```

#### Семантика читання: `ssize_t read(int fd, void *buf, size_t count)`

1. **Значення `> 0`**: успішно зчитано вказану кількість байтів. Важливо: повернуте значення може бути меншим за запитаний `count` (часткове читання). Це нормальна поведінка для сокетів і каналів, коли в буфері ядра наразі менше даних, ніж розмір виділеного буфера.
2. **Значення `== 0` (Кінець файлу / EOF)**: для звичайного дискового файлу вказує на досягнення кінця файлу; для мережевого TCP-сокета означає, що віддалений вузол ініціював коректне закриття з'єднання й надіслав TCP-пакет `FIN`. Подальші виклики читання завжди повертатимуть `0`.
3. **Значення `== -1`**: виникла помилка, деталі якої записані в змінну `errno`. Якщо `errno` дорівнює `EAGAIN` або `EWOULDBLOCK`, це свідчить про відсутність байтів у буфері неблокуючого сокета; якщо `EINTR` — виклик перервано сигналом.

#### Семантика запису: `ssize_t write(int fd, const void *buf, size_t count)`

1. **Значення `> 0`**: байти успішно перенесені з простору користувача в передавальний буфер ядра. У неблокуючому режимі повернення числа, меншого за `count`, є штатним явищем і вказує на заповнення вихідного буфера ядра.
2. **Значення `== -1`**: помилка запису. Якщо `errno` дорівнює `EAGAIN`, буфер ядра повністю заповнений, і запис не зміг прийняти жодного байта; якщо `EPIPE`, спроба запису спрямована в закритий сокет чи розірваний канал.

### Детальна класифікація кодів помилок ядра (errno)

При роботі з неблокуючими дескрипторами критично важливо розрізняти тимчасові стани неготовності від невідновних апаратних або мережевих збоїв.

#### Тимчасові стани очікування (не є фатальними помилками)

- **`EAGAIN` / `EWOULDBLOCK`**: ресурс тимчасово недоступний. При читанні це означає, що в буфері прийому немає жодного байта; при записі — передавальний буфер заповнений під зав'язку; при `accept()` — у черзі `listen()` немає нових клієнтських підключень; при неблокуючому `connect()` — з'єднання ще встановлюється (у цьому випадку зазвичай повертається `EINPROGRESS`). У стандарті POSIX.1-2001 обидва макроси дозволено мати однаковими або різними, тому портативний код завжди перевіряє обидва варіанти.
- **`EINPROGRESS`**: повертається системним викликом `connect()` на неблокуючому сокеті, коли TCP-рукостискання (*3-way handshake*) ініційовано, але ще не завершено. Програма мусить додати сокет у мультиплексор на запис (`EPOLLOUT`), після чого перевірити код завершення через `getsockopt(fd, SOL_SOCKET, SO_ERROR, ...)`.
- **`EINTR`**: системний виклик перервано доставкою сигналу операційної системи процесу до того, як було передано бодай один байт. Коректна реакція — негайний повтор виклику в циклі.

#### Фатальні помилки з'єднання та дескрипторів

- **`EPIPE`**: спроба запису в канал (*pipe*) або сокет, де читальний кінець закрито. Супроводжується генерацією сигналу `SIGPIPE`.
- **`ECONNRESET`**: з'єднання примусово скинуто віддаленим хостом (отримано пакет `RST`). Виникає при раптовому аварійному падінні віддаленого процесу або переповненні черг комутатора.
- **`ETIMEDOUT`**: перевищено ліміт часу TCP на доставку підтвердження або спрацював системний таймаут сокета `SO_RCVTIMEO` / `SO_SNDTIMEO`.
- **`EBADF`**: передано недійсний файловий дескриптор (дескриптор не відкритий або вже був закритий іншим потоком).
- **`ENOTSOCK`**: системний виклик, специфічний для сокетів (наприклад, `setsockopt` або `accept`), викликано для звичайного дискового файлу чи каталогу.
- **`EMSGSIZE`**: для дейтаграмних сокетів (UDP) розмір переданого повідомлення перевищує максимальний ліміт MTU/інтерфейсу.

### Семантика O_NONBLOCK для різних типів системних ресурсів

Поведінка прапорця `O_NONBLOCK` суттєво різниться залежно від внутрішнього драйвера ядра, що стоїть за файловим дескриптором:

```
        ┌─────────────────────────────────────────────────────────────┐
        │            ДЕЙСНА ПОВЕДІНКА ПРАПОРЦЯ O_NONBLOCK             │
        └──────────────────────────────┬──────────────────────────────┘
                                       │
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
┌──────────────────┐          ┌──────────────────┐          ┌──────────────────┐
│ МЕРЕЖЕВІ СОКЕТИ  │          │ КАНАЛИ ТА TTY    │          │ ЗВИЧАЙНІ ФАЙЛИ   │
├──────────────────┤          ├──────────────────┤          ├──────────────────┤
│ Повна неблокуюча │          │ Повна неблокуюча │          │ O_NONBLOCK       │
│ семантика для    │          │ семантика для    │          │ ІГНОРУЄТЬСЯ.     │
│ read, write,     │          │ труб (pipes),    │          │ Потік блокується │
│ accept, connect. │          │ FIFO та терміна- │          │ на час дискового │
│ Повертає EAGAIN. │          │ лів.             │          │ зчитування.      │
└──────────────────┘          └──────────────────┘          └──────────────────┘
```

1. **Мережеві сокети (TCP, UDP, UNIX domain)**: забезпечують повну підтримку неблокуючого вводу-виводу для всіх операцій (`connect`, `accept`, `send`, `recv`).
2. **Анонімні та іменовані канали (Pipes, FIFOs)**: повністю підтримують `O_NONBLOCK`. Запис у заповнений pipe негайно повертає `EAGAIN`. Специфічний випадок: відкриття FIFO-файлу `open(..., O_WRONLY | O_NONBLOCK)` без активного читача негайно повертає помилку `-1` з `errno = ENXIO`.
3. **Термінали, віртуальні консолі та послідовні порти (TTY/PTY)**: підтримують `O_NONBLOCK`. Якщо черга вводу термінала порожня, читання негайно повертає `EAGAIN`.
4. **Звичайні дискові файли (ext4, xfs, btrfs, NTFS)**: **`O_NONBLOCK` повністю ігнорується**. Ядро операційної системи вважає дискові файли завжди готовими на рівні VFS, тому виклик `read()` заблокує потік на час підкачування сторінок із фізичного накопичувача. Для неблокуючого доступу до диска слід застосовувати пул потоків або інтерфейс `io_uring`.

### Конфігурація буферів та таймаутів сокетів через setsockopt()

Для тонкого налаштування поведінки сокетів застосовують системний виклик `setsockopt()`:

:::tabs
```c
#include <sys/socket.h>
#include <sys/time.h>
#include <netinet/tcp.h>

/* 1. Встановлення таймаутів на блокуючі операції (альтернатива O_NONBLOCK) */
struct timeval timeout;
timeout.tv_sec = 5;  /* 5 секунд */
timeout.tv_usec = 0;

setsockopt(sockfd, SOL_SOCKET, SO_RCVTIMEO, &timeout, sizeof(timeout));
setsockopt(sockfd, SOL_SOCKET, SO_SNDTIMEO, &timeout, sizeof(timeout));

/* 2. Зміна розмірів буферів ядра */
int buf_size = 256 * 1024; /* 256 КБ */
setsockopt(sockfd, SOL_SOCKET, SO_RCVBUF, &buf_size, sizeof(buf_size));
setsockopt(sockfd, SOL_SOCKET, SO_SNDBUF, &buf_size, sizeof(buf_size));

/* 3. Вимкнення алгоритму Нейгла для мінімізації затримок (TCP_NODELAY) */
int flag = 1;
setsockopt(sockfd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
```
```cpp
#include <sys/socket.h>
#include <sys/time.h>
#include <netinet/tcp.h>
#include <chrono>

// 1. Встановлення таймаутів на блокуючі операції через std::chrono
struct timeval timeout{};
auto sec = std::chrono::seconds(5);
timeout.tv_sec = static_cast<decltype(timeout.tv_sec)>(sec.count());
timeout.tv_usec = 0;

::setsockopt(sockfd, SOL_SOCKET, SO_RCVTIMEO, &timeout, sizeof(timeout));
::setsockopt(sockfd, SOL_SOCKET, SO_SNDTIMEO, &timeout, sizeof(timeout));

// 2. Зміна розмірів буферів ядра
int buf_size = 256 * 1024; // 256 КБ
::setsockopt(sockfd, SOL_SOCKET, SO_RCVBUF, &buf_size, sizeof(buf_size));
::setsockopt(sockfd, SOL_SOCKET, SO_SNDBUF, &buf_size, sizeof(buf_size));

// 3. Вимкнення алгоритму Нейгла (TCP_NODELAY)
int flag = 1;
::setsockopt(sockfd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
```
:::

- **`SO_RCVTIMEO` / `SO_SNDTIMEO`**: дозволяють блокуючому сокету не зависати назавжди, якщо віддалений клієнт перестав відповідати. Після закінчення таймера системний виклик повертає `-1` з `errno = EAGAIN` або `EWOULDBLOCK`.
- **`SO_RCVBUF` / `SO_SNDBUF`**: задають максимальний обсяг пам'яті ядра під черги прийому й передачі. Ядро Linux подвоює вказане значення для розміщення внутрішніх службових структур `sk_buff`.
- **`TCP_NODELAY`**: вимикає буферизацію дрібних пакетів алгоритмом Нейгла (*Nagle's algorithm*), забезпечуючи негайне відправлення кожного фрагмента даних без штучної затримки до 40 мс.
