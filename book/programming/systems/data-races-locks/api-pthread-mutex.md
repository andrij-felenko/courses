# 📋 Інтерфейс POSIX Threads Mutex і примітиви синхронізації C++

Замок взаємного виключення ([м'ютекс](topic:programming/data-races-locks)) є базовим будівельним блоком системного багатопотокового програмування. У середовищах стандарту POSIX (Linux, macOS, BSD, операційні системи реального часу) низькорівневим інтерфейсом взаємного виключення виступає бібліотека `pthread`, а мова C++ починаючи зі стандарту C++11 надає набір типізованих класів та RAII-обгорток у заголовках `<mutex>` і `<shared_mutex>`.

Цей довідник містить повний опис сигнатур, типів поведінки, життєвого циклу, протоколів успадкування пріоритетів, кодів помилок та ідіоматичних патернів використання для обох мов.

---

### 1. Життєвий цикл і низькорівневий інтерфейс POSIX (`pthread_mutex_t`)

Усі функції стандарту POSIX повертають ціле число: `0` у разі успішного виконання або додатне значення коду помилки. На відміну від класичних системних викликів ядра, функції потоків `pthread` не модифікують глобальну змінну `errno`, а повертають числовий код помилки безпосередньо як результат функції.

#### Статична та динамічна ініціалізація

Замок може бути створений статично під час компіляції або динамічно під час роботи програми:

:::tabs
```c
#include <pthread.h>

// 1. Статична ініціалізація (тільки зі стандартними атрибутами)
pthread_mutex_t g_static_lock = PTHREAD_MUTEX_INITIALIZER;

// 2. Динамічна ініціалізація (дозволяє налаштовувати атрибути)
void init_dynamic_mutex(void) {
    pthread_mutex_t dynamic_lock;
    pthread_mutexattr_t attr;
    
    pthread_mutexattr_init(&attr);
    pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_ERRORCHECK);
    
    pthread_mutex_init(&dynamic_lock, &attr);
    
    pthread_mutexattr_destroy(&attr); // Атрибути можна знищити одразу після ініціалізації
    pthread_mutex_destroy(&dynamic_lock);
}
```
```cpp
#include <mutex>

// 1. Статична ініціалізація (C++ гарантує константну ініціалізацію з C++20)
constinit std::mutex g_static_lock;

// 2. Динамічна ініціалізація (конструктор викликається автоматично під час створення)
void init_dynamic_mutex() {
    std::mutex dynamic_lock;
    // Деструктор автоматично звільнить системні ресурси при виході з області видимості
}
```
:::

#### Сигнатури основних функцій POSIX

| Функція | Призначення | Опис поведінки |
|---|---|---|
| `int pthread_mutex_init(pthread_mutex_t *m, const pthread_mutexattr_t *attr)` | Динамічна ініціалізація | Ініціалізує замок із заданими атрибутами. Якщо `attr == NULL`, застосовуються стандартні атрибути. Повторна ініціалізація вже ініціалізованого замка призводить до невизначеної поведінки. |
| `int pthread_mutex_destroy(pthread_mutex_t *m)` | Знищення замка | Звільняє виділені ресурси ядра та рантайму. Знищення захопленого замка або замка, на який очікують інші потоки, є грубою помилкою і веде до невизначеної поведінки. |
| `int pthread_mutex_lock(pthread_mutex_t *m)` | Блокуюче захоплення | Захоплює замок. Якщо замок вільний, потік стає його власником. Якщо зайнятий — потік блокується і переводиться планувальником у стан сну. |
| `int pthread_mutex_trylock(pthread_mutex_t *m)` | Неблокуюча спроба захоплення | Перевіряє статус замка без зупинки потоку. Якщо замок вільний — захоплює і повертає `0`. Якщо зайнятий — негайно повертає `EBUSY`. |
| `int pthread_mutex_timedlock(pthread_mutex_t *m, const struct timespec *abstime)` | Захоплення з таймаутом | Очікує на замок до настання абсолютного моменту часу `abstime`. Якщо таймаут минув, повертає `ETIMEDOUT`. |
| `int pthread_mutex_unlock(pthread_mutex_t *m)` | Звільнення замка | Звільняє володіння замком, встановлює бар'єр пам'яті та будить один із потоків, заблокованих у черзі очікування. |

### 2. Типи замків та їхня внутрішня семантика

Стандарт POSIX дозволяє керувати поведінкою замка в позаштатних ситуаціях (наприклад, при спробі потоку повторно захопити замок, яким він уже володіє) за допомогою функції `pthread_mutexattr_settype`:

#### 1. Нормальний замок (`PTHREAD_MUTEX_NORMAL` або `DEFAULT`)
Це найпростіший і найшвидший тип замка. Він не зберігає ідентифікатор потоку-власника і не виконує жодних захисних перевірок на швидкому шляху:
- **Повторний виклик `lock()` тим самим потоком:** Призводить до негайного **самодедлоку** (потік чекає сам на себе навічно).
- **Виклик `unlock()` чужим потоком:** Невизначена поведінка (може пошкодити внутрішній стан лічильника futex).
- **Рекомендація:** Використовувати у високонавантажених циклах, де коректність блокування гарантована архітектурно.

#### 2. Замок із перевіркою помилок (`PTHREAD_MUTEX_ERRORCHECK`)
Зберігає всередині числовий ідентифікатор потоку (`pthread_t`), що захопив ресурс:
- **Повторний виклик `lock()`:** Не викликає дедлок, а негайно повертає помилку `EDEADLK`.
- **Виклик `unlock()` незахопленого або чужого замка:** Повертає помилку `EPERM`.
- **Рекомендація:** Ідеальний вибір для налагоджувальних збірок та систем підвищеної надійності, де помилки синхронізації мають виявлятися програмно під час виконання.

#### 3. Рекурсивний замок (`PTHREAD_MUTEX_RECURSIVE`)
Дозволяє одному й тому самому потоку захоплювати замок кілька разів поспіль без дедлоку:
- Всередині структури зберігається лічильник глибини захоплення (recursion depth counter).
- Кожен успішний виклик `lock()` збільшує лічильник на одиницю, а виклик `unlock()` зменшує його на одиницю.
- Замок стає вільним для інших потоків лише тоді, коли лічильник скидається до нуля (тобто виконано рівно стільки ж викликів `unlock()`, скільки й `lock()`).
- **Застереження:** Рекурсивні замки маскують погану архітектуру програми. Якщо внутрішня функція вимагає захопленого замка, краще винести незахищену версію окремо, ніж ускладнювати інваріанти рекурсивним блокуванням.

#### 4. Адаптивний замок (`PTHREAD_MUTEX_ADAPTIVE_NP` у GNU/Linux)
Нестандартне розширення glibc для багатоядерних серверних систем. Перш ніж викликати ядро для блокування потоку через `futex`, замок робить кілька сотень ітерацій активного спін-опитування в надії, що інше ядро швидко завершить коротку критичну секцію.

### 3. Протоколи боротьби з інверсією пріоритетів

У системах реального часу низькопріоритетний потік, захопивши замок, може бути витіснений середньоприорітетним потоком, що заблокує виконання критично важливого високопріоритетного потоку на невизначений час ([інверсія пріоритетів](topic:programming/priority-inversion)).

Стандарт POSIX визначає атрибут `pthread_mutexattr_setprotocol`:

1. `PTHREAD_PRIO_NONE` — стандартна поведінка (пріоритети потоків не змінюються під час володіння замком).
2. `PTHREAD_PRIO_INHERIT` — **успадкування пріоритету (Priority Inheritance)**. Якщо високопріоритетний потік блокується на замку, потік-власник замка тимчасово підвищує свій пріоритет до рівня найвищого з очікувачів, поки не виконає `unlock`.
3. `PTHREAD_PRIO_PROTECT` — **стеля пріоритету (Priority Ceiling)**. Замок має заздалегідь визначений пріоритет стелі. Будь-який потік, що захоплює цей замок, автоматично піднімає свій пріоритет до рівня стелі на весь час перебування в критичній секції.

### 4. Класи замків у стандартній бібліотеці C++

Починаючи з C++11, стандартна бібліотека визначає чіткі інтерфейсні концепції для примітивів синхронізації:

```
+-------------------------------------------------------------------------------+
| ІЄРАРХІЯ ПРИМІТИВІВ СИНХРОНІЗАЦІЇ C++                                         |
+-------------------------------------------------------------------------------+
| 1. Концепція BasicLockable:   .lock()  /  .unlock()                           |
| 2. Концепція Lockable:        додатково .try_lock()                           |
| 3. Концепція TimedLockable:   додатково .try_lock_for() / .try_lock_until()   |
| 4. Концепція SharedLockable:  .lock_shared()  /  .unlock_shared()              |
+-------------------------------------------------------------------------------+
```

#### Зведена таблиця класів м'ютексів C++

| Клас | Заголовок | Рекурсія | Таймаути | Роздільне блокування (RW) | Типовий сценарій |
|---|---|---|---|---|---|
| `std::mutex` | `<mutex>` | Ні | Ні | Ні | Базовий вибір для 95% критичних секцій. |
| `std::recursive_mutex` | `<mutex>` | Так | Ні | Ні | Складні рекурсивні алгоритми або сумісність зі старим кодом. |
| `std::timed_mutex` | `<mutex>` | Ні | Так | Ні | Системи реального часу, запобігання вічним зависанням через таймаут. |
| `std::recursive_timed_mutex` | `<mutex>` | Так | Так | Ні | Поєднання рекурсивного доступу з обмеженням часу очікування. |
| `std::shared_mutex` (C++17) | `<shared_mutex>` | Ні | Ні | Так | Патерн «Багато читачів, один письменник» (читачі не блокують один одного). |
| `std::shared_timed_mutex` (C++14) | `<shared_mutex>` | Ні | Так | Так | Розділюваний замок із підтримкою таймаутів очікування. |

### 5. Захисні RAII-обгортки C++

Прямі виклики `.lock()` і `.unlock()` у C++ вважаються серйозним антипатерном, оскільки генерація винятку або передчасний вихід із функції призводить до витоку замка і вічного дедлоку всієї програми.

#### Порівняння обгорток керування володінням

| Обгортка | Стандарт | Підтримка переміщення | Гнучкість | Рекомендований ужиток |
|---|---|---|---|---|
| `std::lock_guard<Mutex>` | C++11 | Ні (non-movable) | Мінімальна: суворе захоплення в конструкторі, звільнення в деструкторі. | Прості локальні критичні секції всередині функції чи блоку. |
| `std::unique_lock<Mutex>` | C++11 | Так (Move-only) | Максимальна: відкладене захоплення, ручний `unlock/lock`, робота з умовними змінними. | Передача в `std::condition_variable`, складні протоколи передачі володіння. |
| `std::scoped_lock<Mutex...>` | C++17 | Ні (non-movable) | Підтримує одночасне безпечне захоплення від 1 до N м'ютексів без ризику дедлоку. | **Головний вибір за замовчуванням** для будь-яких критичних секцій у сучасному C++. |
| `std::shared_lock<SharedMutex>` | C++14 | Так (Move-only) | Захоплює розділюваний м'ютекс у режимі спільного читання. | Огортання операцій зчитування для `std::shared_mutex`. |

#### Теги конструкторів для стратегій захоплення

Конструктори `std::unique_lock` та `std::lock_guard` приймають спеціальні службові теги:

```cpp
std::mutex m1, m2;

// 1. std::defer_lock — створити обгортку, але не захоплювати замок зараз
std::unique_lock<std::mutex> lock1(m1, std::defer_lock);
std::unique_lock<std::mutex> lock2(m2, std::defer_lock);
// Захопити обидва одночасно за алгоритмом уникнення дедлоку
std::lock(lock1, lock2);

// 2. std::try_to_lock — спробувати захопити через try_lock()
std::unique_lock<std::mutex> try_l(m1, std::try_to_lock);
if (try_l.owns_lock()) {
    // Критична секція успішно захоплена
}

// 3. std::adopt_lock — повідомити обгортці, що замок ВЖЕ захоплено раніше
m1.lock();
std::lock_guard<std::mutex> adopt_g(m1, std::adopt_lock);
// Тепер adopt_g відповідає за звільнення m1 у деструкторі
```

### 6. Внутрішня будова в glibc та розрядні маски стану

У бібліотеці `glibc` для Linux структура `pthread_mutex_t` містить 32-бітне ціле поле `__data.__lock`, яке використовується безпосередньо як адреса користувацького слова `futex`.

Це поле розбите на бітові прапорці:
- **Значення `0` (Нічийний):** Замок повністю вільний, очікувачів немає. Будь-яке ядро може захопити його атомарною інструкцією `CAS(0, 1)`.
- **Значення `1` (Захоплений без черги):** Замок утримується одним потоком. Інші потоки ще не намагалися увійти або не перейшли в режим сну.
- **Значення `2` (Захоплений з чергою):** Хоча б один потік зазнав невдачі під час швидкого захоплення і звернувся до ядра операційної системи. Власник замка при звільненні бачить двійку і знає, що зобов'язаний виконати системний виклик `FUTEX_WAKE` для пробудження очікувачів.

У разі використання замків з успадкуванням пріоритетів (`FUTEX_LOCK_PI`) старші біти слова стану кодують числовий ідентифікатор потоку (TID) власника, що дозволяє ядру Linux миттєво знаходити структуру задачі (`task_struct`) для підвищення її пріоритету.

### 7. Небезпека в обробниках сигналів Unix (Async-Signal Safety)

Критично важливим системним обмеженням є те, що жодна з функцій сімейства `pthread_mutex_*` **не є асинхронно-безпечною для сигналів (async-signal-safe)**:

Якщо потік захопив `pthread_mutex_t`, і в цей момент на те саме процесорне ядро надходить сигнал ОС (наприклад, `SIGUSR1`, `SIGALRM` чи `SIGINT`), виконання потоку призупиняється, і керування передається в обробник сигналу (`signal handler`). Якщо обробник сигналу спробує викликати `pthread_mutex_lock` для того самого замка, виникає миттєвий **невиправний дедлок**:
- Обробник сигналу очікує, поки замок звільнить основний потік.
- Основний потік не може виконати жодної інструкції, доки обробник сигналу не завершить роботу і не поверне стек.

У середині обробників сигналів дозволено використовувати лише спеціальні асинхронно-безпечні атомарні примітиви (`sig_atomic_t`, lock-free черги або системний виклик запису в неблокуючий пайп `write(pipe_fd, ...)`).

### 8. Робота з монотонним часом у `pthread_mutex_timedlock`

За замовчуванням функція `pthread_mutex_timedlock` очікує абсолютний час у форматі системного годинника реального часу `CLOCK_REALTIME`.

Це створює серйозну пастку в надійних серверах: якщо системний адміністратор або служба синхронізації часу NTP змінить системний час (наприклад, переведе годинник назад на кілька хвилин), блокування `pthread_mutex_timedlock` зависне на весь цей додатковий інтервал часу!

Щоб уникнути подібних збоїв, сучасні стандарти POSIX дозволяють прив'язати замок до строго монотонного годинника `CLOCK_MONOTONIC`, який ніколи не скаче назад:

:::tabs
```c
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setclock(&attr, CLOCK_MONOTONIC);
pthread_mutex_init(&lock, &attr);
pthread_mutexattr_destroy(&attr);
```
```cpp
// У C++ стандартні типи timed_mutex (std::timed_mutex, std::shared_timed_mutex)
// у методах try_lock_for автоматично використовують монотонний годинник std::chrono::steady_clock
std::timed_mutex mtx;
if (mtx.try_lock_for(std::chrono::milliseconds(100))) {
    std::lock_guard<std::timed_mutex> guard(mtx, std::adopt_lock);
    // Робота під замком з гарантованим захистом від стрибків годинника
}
```
:::

### 9. Зведена таблиця помилок і діагностика

| Помилка | Наслідок у C | Наслідок у C++ | Як уникнути |
|---|---|---|---|
| Забутий `unlock` при виході з функції | Вічний дедлок програми | Вічний дедлок програми | Завжди використовувати `std::scoped_lock` / `std::lock_guard` або GNU cleanup-атрибути. |
| Звільнення чужого або незахопленого замка | Невизначена поведінка (UB) або помилка `EPERM` | Невизначена поведінка | Суворе правило: замок звільняє виключно той потік і той контекст, який його захопив. |
| Знищення захопленого замка | Пошкодження внутрішніх черг ядра ОС, UB | Невизначена поведінка | Гарантувати завершення всіх потоків-виконавців до знищення захищеної структури. |
| Неузгоджений порядок захоплення кількох замків | Взаємне блокування (Deadlock) | Взаємне блокування (Deadlock) | Використовувати `std::scoped_lock(m1, m2)` або сортувати покажчики за адресою перед захопленням. |
| Захоплення блокуючого замка в обробнику переривань (ISR) | Миттєве зависання системи або Kernel Panic | Миттєве зависання або паніка | Заборонено викликати блокуючі замки в ISR. Застосовувати атомарні операції або lock-free буфери. |
