# 🧮 Математика замків: закон Амдала та ймовірність змагання за критичну секцію

Коли розробник розпаралелює програму на кілька процесорних ядер, він очікує пропорційного зростання продуктивності: два ядра мають подвоїти швидкість обробки даних, а шістдесят чотири ядра — виконати задачу в 64 рази швидше. Проте захист спільних ресурсів за допомогою [замків (м'ютексів)](topic:programming/data-races-locks) створює ділянки примусової серіалізації, де паралельні потоки змушені шикуватися в чергу.

Нижче наведено математичне виведення меж масштабування за законом Амдала, аналіз деградації пропускної здатності за універсальним законом масштабованості Гюнтера (Universal Scalability Law) та ймовірнісний розрахунок часу затримки в черзі контеншну на основі теорії масового обслуговування.

---

### 1. Закон Амдала: послідовне вузьке місце критичних секцій

Нехай повний обсяг обчислювальної роботи, яку виконує програма, нормалізовано до `1`.

Позначимо через `s` сумарну частку часу, яку програма проводить усередині критичних секцій під замками. Оскільки замок забезпечує взаємне виключення, ця частка коду є суто послідовною (serial) і принципово не може виконуватися більш ніж одним ядром одночасно.

Частка коду, що ідеально розпаралелюється на `N` однакових процесорних ядер без взаємних завад, дорівнює `p = 1 - s`.

Підсумковий час виконання задачі на системі з `N` процесорних ядер `T(N)` складається з послідовного часу та паралельного часу, поділеного на кількість ядер:

```
T(N)
= s + (1 - s) ÷ N                      [сума послідовного часу та паралельного часу на N ядрах]
```

Коефіцієнт прискорення системи `S(N)`, що визначається як відношення часу виконання на одному ядрі `T(1) = 1` до часу `T(N)`:

```
S(N)
= T(1) ÷ T(N)                          [означення коефіцієнта прискорення продуктивності]
= 1 ÷ (s + (1 - s) ÷ N)                [підстановка формули часу виконання T(N)]
```

#### Асимптотична межа прискорення

Дослідимо поведінку прискорення при необмеженому збільшенні кількості ядер (`N → ∞`):

```
lim S(N) [при N → ∞]
= lim (1 ÷ (s + (1 - s) ÷ N))          [підстановка границі за кількістю ядер N]
= 1 ÷ (s + 0)                          [оскільки доданок (1 - s) ÷ N прямує до 0]
= 1 ÷ s                                [максимальне теоретичне прискорення системи]
```

#### Числовий розрахунок реальних втрат продуктивності

Нехай критична секція займає лише `5%` від загального часу виконання задачі (`s = 0.05`), а паралельна частина складає `95%` (`p = 0.95`). Обчислимо реальне прискорення на сервері з `128` процесорними ядрами (`N = 128`):

```
S(128)
= 1 ÷ (0.05 + (1 - 0.05) ÷ 128)        [підстановка параметрів s = 0.05 та N = 128]
= 1 ÷ (0.05 + 0.95 ÷ 128)              [обчислення паралельного доданка]
= 1 ÷ (0.05 + 0.00742)                 [ділення 0.95 на 128 процесорних ядер]
= 1 ÷ 0.05742                          [додавання послідовної та паралельної складових]
≈ 17.41                                [підсумковий коефіцієнт прискорення]
```

**Інженерний висновок:** Додавання 128 фізичних ядер до системи з 5-відсотковою критичною секцією дає прискорення лише у `17.4` раза замість очікуваних 128. А граничне прискорення навіть на мільйоні ядер ніколи не перевищить `1 ÷ 0.05 = 20`. Решта 95% обчислювальної потужності обладнання буде змарнована на очікування замка.

### 2. Універсальний закон масштабованості (USL): ефект когерентного шторму

Закон Амдала оптимістично припускає, що при зростанні кількості ядер крива продуктивності виходить на горизонтальне плато `1 ÷ s`. Проте на практиці при великій кількості ядер спостерігається **ретроградна деградація** (програма на 64 ядрах працює повільніше, ніж на 16 ядрах).

Причиною цього є апаратна ціна когерентності кеш-пам'яті (протокол MESI/MOESI). Коли десятки ядер одночасно намагаються захопити замок, вони виконують атомарні операції `compare-and-swap` над однією коміркою пам'яті. Це спричиняє постійну інвалідацію кеш-ліній (англ. *cache line bouncing*) та забиває спільну між'ядерну шину широкомовними запитами на інвалідацію.

Ніл Гюнтер (Neil J. Gunther) розширив модель Амдала, додавши фактор узгодженості даних:

```
C(N)
= N ÷ (1 + σ · (N - 1) + κ · N · (N - 1))  [універсальний закон масштабованості Гюнтера]
```

У цій формулі:
- `σ` (sigma) — коефіцієнт черги контеншну (послідовна частина за Амдалом).
- `κ` (kappa) — коефіцієнт витрат на пересилку даних когерентності між кешами ядер, який зростає пропорційно кількості пар взаємодіючих ядер `N · (N - 1)`.

Через наявність квадратичного члена `κ · N²` у знаменнику, функція `C(N)` досягає максимуму в точці:

```
N_max
= √((1 - σ) ÷ κ)                       [оптимальна кількість ядер для пікової швидкодії]
```

Після проходження точки `N_max` будь-яке додавання нових ядер лише зменшує загальну продуктивність програми, оскільки ядра витрачають більше часу на пересилку службових сигналів когерентності кешів, ніж на корисні обчислення.

### 3. Теорія черг: розрахунок часу затримки потоків (Модель M/M/1)

Розглянемо замок як одноканальний пристрій обслуговування із чергою очікування типу `M/M/1`:

Введемо робочі змінні системи:
- `T_cs` — середня тривалість виконання критичної секції одним потоком (у секундах).
- `μ = 1 ÷ T_cs` — пропускна здатність замка (кількість критичних секцій, яку замок здатний пропустити за одиницю часу).
- `λ` — сумарна інтенсивність надходження запитів на захоплення замка від усіх працюючих потоків програми (запитів за секунду).
- `ρ = λ ÷ μ = λ · T_cs` — коефіцієнт завантаження замка (інтенсивність трафіку).

#### Ймовірність виникнення контеншну

Ймовірність `P_busy` того, що потік при виклику `lock()` застане замок уже захопленим іншим потоком і буде змушений заснути в ядрі операційної системи:

```
P_busy
= ρ                                    [ймовірність зайнятості замка в черзі M/M/1]
= λ · T_cs                             [добуток частоти запитів на тривалість секції]
```

#### Середній час очікування в черзі `W_q`

Згідно з формулою Хінчина–Поллачека, середній час, який потік проводить у черзі очікування до моменту фактичного отримання доступу до замка:

```
W_q
= ρ ÷ (μ · (1 - ρ))                    [середній час затримки в черзі M/M/1]
= (λ · T_cs) ÷ ((1 ÷ T_cs) · (1 - ρ))  [підстановка ρ = λ · T_cs та μ = 1 ÷ T_cs]
= (λ · T_cs²) ÷ (1 - λ · T_cs)         [час очікування через змагання за ресурс]
```

#### Повний час операції під замком `T_total`

Загальний час, який витрачає потік на проходження захищеної ділянки (час простою в черзі + час безпосереднього виконання критичної секції):

```
T_total
= W_q + T_cs                           [сума часу очікування та часу виконання секції]
= (ρ ÷ (μ · (1 - ρ))) + (1 ÷ μ)        [підстановка значень W_q та T_cs = 1 ÷ μ]
= (1 ÷ μ) · ((ρ ÷ (1 - ρ)) + 1)        [винесення спільного множника 1 ÷ μ]
= (1 ÷ μ) · ((ρ + 1 - ρ) ÷ (1 - ρ))    [зведення дробів до спільного знаменника]
= (1 ÷ μ) · (1 ÷ (1 - ρ))              [спрощення чисельника в дужках]
= T_cs ÷ (1 - ρ)                       [підсумкова тривалість із урахуванням черги]
```

#### Довжина черги за законом Літтла (Little's Law)

Згідно з універсальним законом Літтла, середня кількість заблокованих потоків `L_q`, які стоять у черзі очікування замка, дорівнює добутку інтенсивності вхідного потоку запитів `λ` на середній час очікування `W_q`:

```
L_q
= λ · W_q                              [закон Літтла для довжини черги]
= λ · ((λ · T_cs²) ÷ (1 - λ · T_cs))   [підстановка виведеної раніше формули W_q]
= (λ² · T_cs²) ÷ (1 - λ · T_cs)        [множення в чисельнику]
= ρ² ÷ (1 - ρ)                         [вираження через коефіцієнт завантаження ρ = λ · T_cs]
```

**Порівняльний аналіз зростання черги залежно від завантаження `ρ`:**
- При `ρ = 0.50` (замок завантажений на 50% часу): `L_q = 0.5² ÷ 0.5 = 0.50` потоку (у середньому замок вільний або чекає один потік).
- При `ρ = 0.80` (завантаження 80%): `L_q = 0.8² ÷ 0.2 = 3.20` потоки у черзі.
- При `ρ = 0.95` (завантаження 95%): `L_q = 0.95² ÷ 0.05 = 18.05` потоків чекають у ядрі.
- При `ρ = 0.99` (завантаження 99%): `L_q = 0.99² ÷ 0.01 = 98.01` потоків стоять у черзі.

Це наочно демонструє нелінійний, гіперболічний характер деградації: зростання навантаження всього на 4% (з 95% до 99%) збільшує чергу очікування у понад 5 разів!

### 4. Вплив дисперсії тривалості критичної секції (Модель M/G/1)

У реальних програмах тривалість перебування в критичній секції не є суворо константною: вона може варіюватися через кеш-промахи, звернення до пам'яті чи розгалуження коду.

Якщо тривалість секції має довільний розподіл із дисперсією `Var(T_cs) = σ_cs²`, узагальнена формула Хінчина–Поллачека дає скоригований час очікування:

```
W_q [M/G/1]
= (λ · (T_cs² + σ_cs²)) ÷ (2 · (1 - ρ)) [формула Хінчина–Поллачека для загального розподілу]
= W_q [M/M/1] · ((1 + C_v²) ÷ 2)        [де C_v = σ_cs ÷ T_cs — коефіцієнт варіації]
```

**Практичний висновок:** Навіть якщо середня тривалість критичної секції коротка, поодинокі «важкі» операції всередині замка (висока дисперсія `σ_cs²`) різко збільшують середній час очікування для всіх інших потоків. Тому критична секція повинна бути не лише короткою, але й детермінованою за часом виконання.

### 5. Ефект конвойного колапсу при наближенні до насичення (`ρ → 1`)

Якщо інтенсивність звернень `λ` наближається до максимальної пропускної здатності замка `1 ÷ T_cs`, коефіцієнт завантаження `ρ` прямує до `1`:

```
lim T_total [при ρ → 1]
= lim (T_cs ÷ (1 - ρ))                 [підстановка граничного переходу за коефіцієнтом ρ]
= ∞                                    [необмежене лавиноподібне зростання затримки]
```

Коли завантаження замка `ρ` перевищує значення `0.7–0.8`, черга потоків починає зростати експоненційно. Виникає явище **конвою замків (lock convoying)**: усі потоки програми опиняються заблокованими в ядрі операційної системи, частота перемикання контексту перевантажує планувальник, і корисна продуктивність системи катастрофічно падає до нуля.
