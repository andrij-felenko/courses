# ⚙️ Скінченний автомат замість задачі: коли FSM простіший за RTOS

> Алгоритмічна вставка про межу між [задачами](book:programming/tasks) і простим автоматом. Коли [ручні машини станів вибухають](root:embedded/super-loop-limits), рука тягнеться до задач — а тут зробимо чесний поворот: для **правильної** задачі один явний автомат буває **простішим** за весь RTOS. Не «завжди», а «коли».

## Задача

Задачі часто продають як ліки від спагеті-станів: [ручні машини станів розповзаються](root:embedded/super-loop-limits), стають непридатними, і з полегшенням переходиш до `xTaskCreate`. Але є небезпека крену: варто побачити кілька блокувальних пауз чи кілька справ — і рука вже тягнеться до задач, навіть коли в цьому немає потреби.

Питання цієї вставки пряме: чи завжди подієво-послідовна логіка **одного** пристрою варта окремої задачі зі своїм стеком, планувальником і ризиком гонок? Ні — є клас задач, де RTOS це з гармати по горобцях. Розглянемо конкретний наскрізний приклад: **контролер послідовності** — маленький пристрій, що за натисканням кнопки запускає насос через двосекундну продувку клапана і потім витримує трисекундне охолодження. Логіка проста й природна: `Idle → Purge → Running → Cooldown → Idle`. Це та сама «увімкни — зачекай — увімкни — зачекай» послідовність, яку наводять як приклад того, що «розповзається», — і ми тут покажемо, що проблема була не в автоматі, а в тому, щоб вантажити на один автомат **одразу кілька незалежних справ**.

## Ідея

[Машини станів «вибухають»](root:embedded/super-loop-limits) з конкретної причини: коли в один цикл намагаються вмістити **багато незалежних справ** — блимання, читання давача, мережу, — їх стани переплітаються і утворюють той самий клубок, від якого так хочеться втекти до задач. Але якщо справа **одна** і вона за своєю природою послідовно-подієва — скінченне число чітких режимів, і кожен перехід між ними спричиняється конкретною умовою — то явний **скінченний автомат** (англ. *finite-state machine*, FSM — «машина зі скінченним числом станів») не є милицею. Він і є найточнішим описом такої логіки. Тут **стани** (англ. *state* — «стан, режим») не маскують простоту — вони і є структура.

Скінченний автомат — це чотири поняття: скінченна множина **станів**, **поточний стан** (рівно один у будь-який момент часу), **події (events)** або умови, що можуть спричинити зміну стану, і **таблиця переходів (transitions)**, яка говорить «у стані X за умови Y перейди в Z». Інтуїтивно: пристрій завжди перебуває в одному з кількох ясно названих режимів; подія штовхає його в інший режим, і при цьому виконується певна дія. Для контролера послідовності станами є `Idle` (очікування кнопки), `Purge` (клапан відкрито, йде продувка), `Running` (насос увімкнено, чекаємо зупинки) і `Cooldown` (насос вимкнено, охолодження). Саме рівно стільки — і жодного більше.

Ключова відмінність від задачі: автомат живе у звичайному `loop()` і є **неблокувальним**. На кожному оберті він дивиться на поточний стан, [час за лічильником `millis`](book:programming/millis-micros) і входи, робить дію, можливо перемикає стан і **миттєво повертає** керування. Жодного `delay`, жодного власного стека, жодного планувальника. Цей підхід — прямий родич [кооперативного планувальника](book:programming/nonblocking-time): кожен учасник добровільно короткий, не тягне ковдру. Різниця лише в тому, що тут учасник один.

![Коло з чотирьох станів контролера послідовності з умовами переходів](/book/programming/systems/tasks/img/state-diagram.svg)
*Діаграма станів наскрізного прикладу — контролер послідовності: чотири стани (Idle / Purge / Running / Cooldown) і чотири переходи. Біля кожної стрілки — умова переходу: кнопка або таймаут. Під кожним станом — дія, що виконується в ньому. Схема компактна — бо справа одна, без спагеті з кількох незалежних справ. Замкнене коло станів відображає природний цикл пристрою.*

## Автомат у коді

Канонічна ідіома для МК: `enum class` для переліку станів і `switch` у функції, що викликається щооберту з `loop()`. Нижче — реальний, компільований ESP32-Arduino фрагмент:

:::tabs
```cpp
#include <Arduino.h>

enum class State { Idle, Purge, Running, Cooldown };

static State     state = State::Idle;
static uint32_t  t0    = 0;        // мітка входу в поточний стан (millis)

constexpr uint32_t PURGE_MS    = 2000;   // 2 с продувки
constexpr uint32_t COOLDOWN_MS = 3000;   // 3 с охолодження

constexpr uint8_t PIN_VALVE = 5;
constexpr uint8_t PIN_PUMP  = 6;

// Вхід у новий стан: зберегти + перезапустити таймер
static void enter(State s) {
    state = s;
    t0    = millis();
}

// Детектор натискання — фронт з антибрязкотом (§4.4.5 / ⚙️ §4.4.5a)
static bool buttonPressed() {
    // реалізацію детектора фронту взято з §4.4.5a
    return false; // заглушка
}

// Головна функція автомата — зветься щооберту, НЕ блокує
void fsmStep() {
    const uint32_t now = millis();

    switch (state) {
        case State::Idle:
            if (buttonPressed())            enter(State::Purge);      // подія
            break;

        case State::Purge:
            digitalWrite(PIN_VALVE, LOW);                              // дія стану
            if (now - t0 >= PURGE_MS)       enter(State::Running);    // час
            break;

        case State::Running:
            digitalWrite(PIN_PUMP, HIGH);
            if (buttonPressed())            enter(State::Cooldown);   // подія
            break;

        case State::Cooldown:
            digitalWrite(PIN_PUMP, LOW);
            if (now - t0 >= COOLDOWN_MS)    enter(State::Idle);       // час → коло
            break;
    }
}

void setup() {
    pinMode(PIN_VALVE, OUTPUT);
    pinMode(PIN_PUMP,  OUTPUT);
}

void loop() {
    fsmStep();   // весь автомат — один виклик
}
```
```py
# MicroPython на ESP32 — той самий автомат.
from machine import Pin
import time

# Стани — цілі константи (в MicroPython Enum зазвичай не тягнуть).
IDLE, PURGE, RUNNING, COOLDOWN = range(4)

PURGE_MS    = 2000   # 2 с продувки
COOLDOWN_MS = 3000   # 3 с охолодження

valve = Pin(5, Pin.OUT)
pump  = Pin(6, Pin.OUT)

state = IDLE
t0    = time.ticks_ms()   # мітка входу в поточний стан


def enter(s):
    # Вхід у новий стан: зберегти + перезапустити таймер.
    global state, t0
    state = s
    t0    = time.ticks_ms()


def button_pressed():
    # Детектор натискання — фронт з антибрязкотом (§4.4.5a).
    return False   # заглушка


def fsm_step():
    # Головна функція автомата — зветься щооберту, НЕ блокує.
    now = time.ticks_ms()

    if state == IDLE:
        if button_pressed():
            enter(PURGE)                                   # подія

    elif state == PURGE:
        valve.value(0)                                     # дія стану
        if time.ticks_diff(now, t0) >= PURGE_MS:
            enter(RUNNING)                                 # час

    elif state == RUNNING:
        pump.value(1)
        if button_pressed():
            enter(COOLDOWN)                                # подія

    elif state == COOLDOWN:
        pump.value(0)
        if time.ticks_diff(now, t0) >= COOLDOWN_MS:
            enter(IDLE)                                     # час → коло


while True:
    fsm_step()   # весь автомат — один виклик
```
:::

Пройдемо одне повне коло. Натискання кнопки в стані `Idle` переводить автомат у стан `Purge`: відкривається клапан (`VALVE = LOW`), і запускається таймер. Коли `millis` набирає 2000 мс, автомат переходить у `Running`: вмикається насос (`PUMP = HIGH`). Наступне натискання переводить у `Cooldown`: насос вимикається, таймер знову перезапускається. Через 3 с — `Idle`, і все починається спочатку. Вся **пам'ять** цього пристрою — дві змінні: `state` (поточний режим) і `t0` (коли в нього увійшли). Жодного окремого стека, жодної задачі.

Помітьте прийом `enter()`: він завжди встановлює `state` і `t0` **разом**. Це страховка від типової помилки — забути перезапустити таймер при переході, через що паузи «поїдуть». Кожен стан ділиться на дії «при вході» (виконуються функцією `enter`, один раз) і «поки в стані» (виконуються в `case`, щооберту). Ця межа — важлива архітектурна лінія.

Коли станів стає більше десяти й переходи ускладнюються, `switch` можна замінити на **таблицю переходів** — масив структур `{стан, умова, наступний_стан, дія}` — але для компактних автоматів `switch` виграє в читабельності.

## Чому простіше за задачу

![Порівняння: що має автомат у loop() і чого додатково потребує задача RTOS](/book/programming/systems/tasks/img/fsm-vs-task.svg)
*Чого автомат у `loop()` **не потребує** порівняно з задачею RTOS: власного стека, планувальника, черг і м'ютексів. Критерій вибору: «одна послідовна справа» хилить ліворуч; «багато незалежних чи блокувальні виклики» — праворуч. Автомат не «дешевший» у всьому — він відповідає іншому класу задач.*

Задача RTOS тягне за собою цілий пакет вартості. [Власний стек](book:programming/task-stacks) займає RAM — кілька сотень байтів на задачу, що на мікроконтролері з 32 чи 64 КіБ помітно. [Планувальник](book:programming/scheduler) і перемикання контексту додають час і невизначеність: навіть передбачувані, вони є. Коли кілька задач ділять дані, з'являються [черги, м'ютекси, семафори](book:programming/task-ipc) — ціла інфраструктура, в якій виникають **гонки** і **дедлоки**. Автомат у `loop()` не потребує нічого з цього: він один, його стан видно в дебагері одним поглядом, і відтворити баг можна, просто пославши ту саму послідовність подій.

> 🔧 **Навіщо це.** Практичне правило вибору: якщо перед вами **одна** послідовно-подієва справа, що ріжеться на короткі неблокувальні кроки, — явний автомат у `loop()` буде і простішим, і надійнішим за задачу. Якщо справ **багато** й вони незалежні, або є принципово блокувальні виклики (мережа, файлова система, повільний давач) — тоді задачі й RTOS є правильним вибором. Там, де [super-loop вичерпується](root:embedded/super-loop-limits), потрібні задачі; ця ж рамка — про те, коли навіть до RTOS не треба.

## Складність і пастки на МК

- **Кожен стан мусить вертати керування швидко.** Автомат [кооперативний](book:programming/nonblocking-time): жодного `delay`, жодного довгого циклу всередині `case`. Якщо будь-яка гілка затримається, весь `loop()` завмирає — так само, як [super-loop без автомата](root:embedded/super-loop-limits). Час слід вимірювати лише через `millis`-мітку, а не через очікування.

- **Один вхід у стан — одна точка скидання таймера.** Прийом `enter()` ставить `state` і `t0` разом. Якщо писати їх окремо в різних місцях, легко забути одне з двох і отримати «поїхавші» таймаути. Розрізняйте дії «при вході в стан» (одноразові) і «поки в стані» (щооберту).

- **Не загубити подію між оборотами.** Натискання кнопки — миттєвий фронт; якщо `loop()` якраз займався довгою операцією, можна пропустити його. Використовуйте детектор фронту з латчуванням ([переривання](book:programming/interrupts), [антибрязкіт](book:electronics/contact-debounce)), а не просте зчитування миттєвого рівня. Переривання фіксує подію у прапорець — автомат прочитає його наступного оберту.

- **Комбінаторний вибух — реальна межа.** Один автомат із 5–8 станами читається природно. Коли станів стає кілька десятків або потрібно кілька автоматів, що активно взаємодіють між собою, — знову отримуємо [той самий спагеті-клубок](root:embedded/super-loop-limits), і тут уже чесна відповідь — задачі. Як проміжний крок між плоским автоматом і задачами існують **ієрархічні скінченні автомати (hierarchical FSM)** — стани, всередині яких є власні підстани; про них розказують окремі книги з патернів вбудованих систем.

- **`millis()` переповнюється — рахуйте різницею.** Завжди пишіть `now - t0 >= T` з беззнаковою арифметикою `uint32_t`: при [переповненні лічильника](book:programming/timer-overflow) через ~49 діб беззнакова різниця коректно «загортається». Запис `now >= t0 + T` переповнюється й дає хибний результат.

- **Кілька автоматів — кожен зі своїм `state` і `t0`.** Якщо пристрій керує двома незалежними послідовностями (наприклад, два насоси), для кожної заведіть окрему пару змінних. Не змішуйте стани в одній змінній — це та сама [пастка «один big-state для всього»](root:embedded/super-loop-limits).

## Підсумок

[Машини станів вибухають](root:embedded/super-loop-limits), коли ними **імітують** багатозадачність — коли в одну змінну-стан запихають кілька незалежних справ, і вони переплітаються. Але та сама конструкція, прикладена до **однієї** ясно-послідовної справи, — це найпростіший і найлегший інструмент, який RTOS лише обважив би власним стеком, планувальником і ризиком гонок. Два рядки (`state`, `t0`), одна функція `fsmStep()`, виклик з `loop()` — і контролер послідовності готовий, детермінований і прозорий.

Запам'ятайте правило: перш ніж тягнутися до `xTaskCreate`, запитайте себе — це «багато незалежних справ» чи «один чіткий автомат»? Не кожне «почекати» вимагає задачі зі стеком. Коли ж автомат таки переростає себе — накопичуючи стани, взаємодіючи з іншими автоматами, чи потребуючи блокувальних викликів — настає час задач: [планувальника](book:programming/scheduler) і [FreeRTOS на ESP32](book:programming/freertos), уже з повним розумінням того, чому вони там потрібні.
