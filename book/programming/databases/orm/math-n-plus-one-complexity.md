# 📐 Математичний аналіз обчислювальної складності та мережевих затримок проблеми N+1

Проблема N+1 запитів є класичною інженерною пасткою у системах із ледачим завантаженням (Lazy Loading). Вона демонструє, як наївна трансляція обходу об'єктного графа у послідовність реляційних запитів перетворює операцію константної часової складності на лінійну відносно кількості сутностей, багаторазово збільшуючи мережеві затримки (Network Latency).

Ця вставка містить формальну модель аналізу загального часу виконання запитів (Total Execution Time), оцінку накладних витрат мережевого обміну (Round-Trip Time, RTT), використання пам'яті та доведення асимптотичної переваги реляційних операцій `JOIN` та `IN (...)`.

---

### Формальна модель компонентів затримки запиту до СУБД

Загальний час виконання довільного SQL-запиту `T_{query}` складається з чотирьох послідовних фізичних компонентів:

```text
T_{query} = T_{net} + T_{parse} + T_{exec} + T_{serial}
```

Де:
* `T_{net} = 2 * RTT`: Час передачі запиту мережею від додатку до сервера бази даних і повернення відповіді.
* `T_{parse}`: Час синтаксичного розбору SQL-рядка, перевірки прав доступу та генерації плану виконання в СУБД.
* `T_{exec}`: Час фізичного сканування таблиці або індексу на дискових сторінках у пам'яті buffer pool.
* `T_{serial}`: Час серіалізації бінарного протоколу СУБД на стороні сервера та десеріалізації у структури мови програмування на стороні клієнта.

У сучасних дата-центрах та хмарних середовищах із високошвидкісними NVMe-дисками час виконання індексного пошуку `T_{exec}` становить мікросекунди (0.05–0.2 мс), тоді як затримка мережі `T_{net}` зазвичай варіюється від 0.5 мс (всередині однієї зони доступності) до 2–5 мс (між різними зонами або серверами додатку).

---

### Порівняльний аналіз стратегій вибірки даних

Нехай система отримує список із `N` користувачів (Users), для кожного з яких необхідно завантажити список їхніх замовлень (Orders). Нехай у середньому кожен користувач має `k` замовлень, тобто сумарна кількість дочірніх рядків становить `M = N * k`.

#### 1. Стратегія Lazy Loading (Проблема N+1)

При ледачому завантаженні додаток виконує 1 первинний запит для отримання батьківських сутностей, а потім у циклі робить `N` окремих точкових запитів для кожного користувача:

```text
T_{lazy}(N) = T_{primary} + \sum_{i=1}^N T_{child, i}
```

Оскільки всі `N` запитів виконуються строго послідовно через один сесійний сокет:

```text
T_{lazy}(N) = (2 * RTT + T_{parse} + T_{exec}) + N * (2 * RTT + T_{parse} + T_{exec})
```

Асимптотична часова складність за часом очікування становить:

```text
T_{lazy}(N) \in O(N * RTT)
```

При зростанні кількості користувачів час виконання масштабується лінійно від мережевої затримки дата-центру, незалежно від потужності процесорів сервера бази даних.

#### 2. Стратегія Eager Loading через SQL JOIN

При жадібному завантаженні виконується рівно 1 комбінований SQL-запит із об'єднанням таблиць:

```sql
SELECT * FROM users u LEFT JOIN orders o ON o.user_id = u.id WHERE u.active = true;
```

Час виконання:

```text
T_{join}(N) = 2 * RTT + T_{parse} + T_{index\_join}(N, k) + T_{serial}(N * k)
```

Асимптотична складність за кількістю мережевих звернень становить:

```text
T_{join}(N) \in O(1 * RTT)
```

Вся операція об'єднання виконується безпосередньо в оперативній пам'яті рушія СУБД із використанням швидкого злиття (Hash Join або Merge Join).

#### 3. Стратегія Batch Fetching (IN-clause Loading)

При пакетному завантаженні виконується рівно 2 SQL-запити:
1. Завантаження `N` користувачів: `SELECT * FROM users;`
2. Завантаження замовлень для всіх отриманих ідентифікаторів одним запитом: `SELECT * FROM orders WHERE user_id IN (id_1, id_2, ..., id_N);`

Час виконання:

```text
T_{batch}(N) = 2 * (2 * RTT) + 2 * T_{parse} + T_{exec, users} + T_{exec, orders}
```

Асимптотична складність також становить:

```text
T_{batch}(N) \in O(1 * RTT)
```

### Числовий розрахунок реальних затримок

Розглянемо практичний приклад завантаження сторінки з `N = 200` користувачами у хмарному оточенні:
* Мережева затримка RTT: `1.0` мс.
* Час індексного пошуку одного замовлення: `T_{exec} = 0.1` мс.
* Час парсингу запиту: `T_{parse} = 0.05` мс.

#### Розрахунок для Lazy Loading:
```text
T_{lazy} = (2.0 + 0.05 + 0.1) + 200 * (2.0 + 0.05 + 0.1)
T_{lazy} = 2.15 + 200 * 2.15 = 2.15 + 430.0 = 432.15 мс
```

#### Розрахунок для Eager Loading (JOIN):
```text
T_{join} = 2.0 + 0.05 + 1.2 + 0.4 = 3.65 мс
```

#### Розрахунок прискорення (Speedup Factor):
```text
Speedup = T_{lazy} / T_{join} = 432.15 / 3.65 \approx 118.4 раза
```

Завдяки заміні N окремих мережевих запитів на один єдиний реляційний `JOIN` загальний час відповіді користувачу скорочується у понад **118 разів**, а навантаження на мережеві інтерфейси та пул з'єднань зменшується на два порядки.

### Аналіз накладних витрат декартового добутку при JOIN

Важливо зазначити обмеження стратегії `JOIN`: якщо батьківська сутність має декілька незалежних колекцій зв'язків один-до-багатьох (`1:M` замовлень та `1:M` адрес доставки), одночасний `JOIN` обох таблиць породжує декартовий добуток (Cartesian Product), розмір якого становить `N * k_1 * k_2` рядків.

У таких випадках стратегія пакетного завантаження (Batch Fetching / Split Queries) є оптимальною: вона виконує `1 + C` запитів (де `C` — кількість пов'язаних колекцій), запобігаючи передачі дубльованих даних мережею та зберігаючи константну кількість RTT.

### Математична оцінка утримання пулу з'єднань (Connection Holding Time)

Нехай інтенсивність вхідного веб-трафіку становить `\lambda` HTTP-запитів на секунду.

За законом Літтла (Little's Law), середня кількість одночасно зайнятих підключень до бази даних `L` визначається формулою:

```text
L = \lambda * T_{hold}
```

Де `T_{hold}` — час, протягом якого потік додатку утримує підключення з пулу (Connection Pool).

При використанні Lazy Loading `T_{hold} \approx T_{lazy} = 432` мс.
При `\lambda = 100` запитів/сек:

```text
L_{lazy} = 100 * 0.432 = 43.2 підключення
```

При використанні Eager Loading `T_{hold} \approx T_{join} = 3.65` мс:

```text
L_{join} = 100 * 0.00365 = 0.365 підключення
```

Зменшення часу утримання з'єднання у 118 разів дозволяє тому самому пулу підключень обслуговувати у сотні разів більший потік користувачів без ризику вичерпання лімітів СУБД.

### Аналіз пропускної здатності каналу (Bandwidth Utilization)

Нехай розмір бінарного заголовка мережевого пакета SQL-драйвера (TDS, PostgreSQL FE/BE Protocol) становить `H = 128` байтів, а розмір корисного навантаження одного рядка — `B = 64` байти.

Сумарний мережевий оверхед при Lazy Loading:

```text
Overhead_{lazy} = N * (H + B) + H
```

Сумарний оверхед при Eager Loading (JOIN):

```text
Overhead_{join} = H + N * k * B
```

При великих значеннях `N` співвідношення протокольного сміття при точкових запитах досягає `(N * H) / (H) = N` разів, що призводить до непотрібного нагрівання мережевих стеків ядра ОС та додаткового навантаження на комутатори дата-центру.
