# 📋 Практичний довідник оптимізації продуктивності ORM

Використання об'єктно-реляційного відображення (ORM) значно прискорює розробку бізнес-логіки, проте без належної конфігурації генерації запитів призводить до катастрофічної деградації продуктивності: надлишкового споживання оперативної пам'яті, блокування пулу підключень та генерації неоптимального SQL.

Цей довідник містить перелік критичних параметрів налаштування, шаблони оптимізованих запитів для провідних ORM (Hibernate, SQLAlchemy, Entity Framework Core), правила керування контекстом persistence context та практичний чекліст діагностики.

---

### Порівняльна матриця механізмів оптимізації в популярних ORM

| Завдання оптимізації | Hibernate (JPA / Java) | SQLAlchemy (Python) | Entity Framework Core (.NET) | Prisma (TypeScript) |
| :--- | :--- | :--- | :--- | :--- |
| **Жадібне завантаження (JOIN)** | `JOIN FETCH` у HQL / `@EntityGraph` | `joinedload()` | `.Include()` | `include: { orders: true }` |
| **Пакетна вибірка (Batch IN)** | `@BatchSize(size = 50)` | `selectinload()` | `.AsSplitQuery()` | Автоматичний dataloader |
| **Тільки читання (No-Tracking)** | `@QueryHint(READ_ONLY)` / DTO | `.yield_per(100)` / DTO | `.AsNoTracking()` | `prisma.user.findMany()` (дефолт) |
| **Пакетна вставка (Batch Insert)** | `hibernate.jdbc.batch_size=50` | `session.bulk_insert_mappings()` | `AddRange()` / EF Core Batching | `createMany()` |
| **Проекції (Вибірка полів)** | Constructor Expression (`new DTO(...)`) | `session.query(User.id, User.name)` | `.Select(u => new { u.Id })` | `select: { id: true, name: true }` |

### Детальні рецепти конфігурації

#### 1. Усунення проблеми N+1 через вибір правильної стратегії Fetching

За замовчуванням зв'язки один-до-багатьох (`@OneToMany`) налаштовані як `LAZY`. Щоб уникнути сотень повторних звернень до СУБД, використовуйте відповідні декларативні стратегії:

```python
# Приклад SQLAlchemy: Пакетне завантаження через selectinload
from sqlalchemy.orm import selectinload

users = session.query(User).options(selectinload(User.orders)).filter(User.active == True).all()
# Результат: Рівно 2 SQL запити незалежно від кількості користувачів
```

```csharp
// Приклад Entity Framework Core: Розділення запитів для уникнення Cartesian Explosion
var usersWithOrders = context.Users
    .Include(u => u.Orders)
    .Include(u => u.Addresses)
    .AsSplitQuery() // Запобігає декартовому розмноженню рядків
    .ToList();
```

### Вимкнення Change Tracking для звітів та операцій читання

Коли сутність завантажується ORM, рушій зберігає її копію в Identity Map для подальшого Dirty Checking. Для операцій, що лише читають дані (Web API, генерація PDF-звітів, аналітика), це створює марні накладні витрати пам'яті та процесора.

#### Приклад вимкнення відстеження в EF Core:
```csharp
// Економія до 60% пам'яті та дворазове прискорення десеріалізації
var activeUsers = context.Users
    .AsNoTracking()
    .Where(u => u.IsActive)
    .ToList();
```

#### Приклад DTO-проекцій у Hibernate (JPA):
```java
// Замість завантаження важких Entity об'єктів з усіма зв'язками
List<UserSummaryDTO> dtos = entityManager.createQuery(
    "SELECT new com.app.dto.UserSummaryDTO(u.id, u.email, COUNT(o.id)) " +
    "FROM User u LEFT JOIN u.orders o " +
    "GROUP BY u.id, u.email", UserSummaryDTO.class)
    .getResultList();
```

### Налаштування пакетних операцій (JDBC Batching)

За замовчуванням виклик `save()` для 1000 нових сутностей генерує 1000 окремих мережевих викликів `INSERT INTO ...`. Увімкнення пакетування дозволяє об'єднувати команди в єдиний TCP-пакет драйвера бази даних.

#### Конфігурація `application.properties` для Spring Data JPA / Hibernate:
```properties
# Кількість операцій в одному пакеті
spring.jpa.properties.hibernate.jdbc.batch_size=50

# Впорядкування операцій для групування однакових SQL-виразів
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true

# Генерація ключів: уникайте GenerationType.IDENTITY при пакетній вставці!
# Використовуйте GenerationType.SEQUENCE з allocationSize=50
```

> **Важливе застереження**: Стратегія `GenerationType.IDENTITY` (автоінкрементні стовпці у MySQL або `SERIAL` у старих PostgreSQL) примусово вимикає JDBC Batching у Hibernate, оскільки драйвер зобов'язаний негайно виконувати `INSERT` для отримання згенерованого базою значення ID. Завжди віддавайте перевагу генераторам `SEQUENCE` або клієнтським `UUIDv7`.

### Робота з кешем другого рівня (Second-Level Cache, L2)

Кеш першого рівня (L1 / Session) живе лише в межах поточної транзакції або HTTP-запиту. Кеш другого рівня (L2) є спільним для всіх потоків додатку (наприклад, Redis або Hazelcast).

#### Правила безпечного використання кешу L2:
1. **Кешуйте лише рідкозмінні дані**: Довідники країн, ролей, категорій або системних налаштувань.
2. **Уникайте кешування сутностей із частими записами**: Висока частота інвалідації кешу зведе нанівець усю вигоду та створить навантаження на мережу.
3. **Використовуйте версіонування сутностей (`@Version`)**: Оптимістичне блокування гарантує відсутність використання застарілих кешованих даних.

### Патерни Keyset Pagination замість OFFSET у великих наборах даних

Класична пагінація `LIMIT 50 OFFSET 100000` змушує рушій бази даних сканувати та відкидати 100 000 рядків, перш ніж повернути потрібні 50 записів. При використанні ORM це призводить до різкого падіння швидкості завантаження наступних сторінок.

#### Оптимальний патерн Keyset (Seek) Pagination:

```python
# Замість OFFSET використовуємо порівняння за первинним ключем або індексованим часом
last_seen_id = request.args.get('after_id')
query = session.query(User).filter(User.id > last_seen_id).order_by(User.id.asc()).limit(50)
```

Такий підхід забезпечує стабільний час виконання `O(1)` за рахунок прямого B-Tree пошуку в індексі, незалежно від глибини сторінки.

### Оптимістичне блокування (Optimistic Locking) проти песимістичного (Pessimistic Locking)

При конкурентному оновленні сутностей декількома клієнтами виникає ризик втрати змін (Lost Update).

#### Реалізація Optimistic Locking у JPA:
```java
@Entity
public class Account {
    @Id
    private Long id;
    private BigDecimal balance;
    
    @Version
    private Long version; // Автоматично перевіряється: WHERE id = ? AND version = ?
}
```

Якщо інша транзакція встигла змінити рядок і збільшити `version`, поточний комміт викине виняток `OptimisticLockException`, не блокуючи інші потоки на рівні рядків СУБД.

#### Коли застосовувати Pessimistic Locking (`SELECT FOR UPDATE`):
Песимістичне блокування виправдане у критичних фінансових балансах із високим рівнем конкуренції, де повторні спроби (Retries) дорожчі за коротке блокування рядка в базі даних:

```csharp
// Блокування рядка до кінця поточної транзакції
var account = await context.Accounts
    .FromSqlRaw("SELECT * FROM Accounts WITH (UPDLOCK, ROWLOCK) WHERE Id = {0}", accountId)
    .SingleAsync();
```

### Моніторинг затримок через APM та інструменти трасування (OpenTelemetry)

Для виявлення прихованих деградацій у продакшені налаштовують інструменти APM (Datadog, New Relic, OpenTelemetry). Вони автоматично створюють спани (Spans) для кожного виконаного SQL-запиту, підсвічуючи кількість згенерованих звернень на один HTTP-ендпоінт. Якщо лічильник запитів перевищує поріг (наприклад, більше 10 SQL на один HTTP-запит), система надсилає сповіщення про виявлення аномалії N+1.

### Контрольний чекліст діагностики та аудиту ORM для розробників

1. **Моніторинг згенерованого SQL**: У тестовому середовищі обов'язково увімкніть логування вихідних запитів (`show_sql: true`, `generate_statistics: true` або p6spy).
2. **Перевірка відсутності циклічних вибірок**: Жоден бізнес-метод не повинен виконувати запити до бази даних всередині циклів `for / while`.
3. **Використання пагінації (Pagination)**: Завжди обмежуйте розмір результатів за допомогою `LIMIT / OFFSET` або Keyset Pagination; заборонено вичитувати всю таблицю в пам'ять.
4. **Контроль розміру persistence context**: При тривалій пакетній обробці періодично викликайте `flush()` та `clear()` для звільнення пам'яті.
5. **Тестування на реальному обсязі даних**: Продуктивність запитів, яка здається швидкою на тестовій базі з 10 рядками, повинна бути верифікована на стейджингу з мільйонами рядків для виявлення відсутності необхідних індексів.
6. **Захист від блокування пулу з'єднань (Connection Pool Sizing)**: Час утримання з'єднання з базою повинен обмежуватися тривалістю виконання SQL-запитів; тривалі HTTP-виклики до зовнішніх сервісів повинні виконуватися поза транзакційними межами ORM.
7. **Аудит типів стовпців у мапінгу**: Переконайтеся, що типи полів у класах точно збігаються з типами в базі даних (наприклад, `UUID` проти `VARCHAR(36)`), щоб уникнути неявного приведення типів (Implicit Type Cast), яке вимикає використання індексів.
8. **Вимкнення Open-Session-In-View (OSIV)**: Антипатерн OSIV утримує відкрите підключення до бази під час рендерингу HTML або серіалізації JSON у контролері; вимкніть `spring.jpa.open-in-view=false` для захисту пулу з'єднань.
9. **Захист від каскадного завантаження великих бінарних полів**: Позначайте поля `byte[]` або великі текстові описи анотацією `@Basic(fetch = FetchType.LAZY)` або виносьте їх в окрему денормалізовану таблицю.
