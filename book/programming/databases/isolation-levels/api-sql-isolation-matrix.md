# 📋 Інтерфейси керування ізоляцією в SQL та матриця поведінки рушіїв

Керування ізоляцією транзакцій у реляційних базах даних здійснюється через декларативні команди SQL-інтерфейсу, параметри сесійного підключення та явні блокувальні директиви. Незважаючи на наявність формального стандарту ANSI SQL-92, провідні системи керування базами даних (PostgreSQL, MySQL InnoDB, Oracle Database та Microsoft SQL Server) реалізують рівні ізоляції на основі принципово різних внутрішніх архітектур — від класичного двофазного блокування (2PL) до багатоверсійності (MVCC) та серіалізовної знімкової ізоляції (SSI).

У цьому довіднику зведено синтаксичні контракти налаштування транзакцій, матрицю реальної поведінки промислових рушіїв, системні механізми ядра СУБД, оператори явного блокування рядків та системні коди помилок.

## Синтаксис керування ізоляцією в стандарті SQL

Стандарт SQL визначає три основні рівні конфігурації ізоляції:

### 1. Налаштування окремої транзакції
Команда виконується перед виконанням будь-яких операцій читання або запису в межах поточної транзакції:

```sql
SET TRANSACTION ISOLATION LEVEL { 
    READ UNCOMMITTED 
  | READ COMMITTED 
  | REPEATABLE READ 
  | SERIALIZABLE 
} [ READ WRITE | READ ONLY ] [ DEFERRABLE | NOT DEFERRABLE ];
```

Параметр `READ ONLY` оптимізує внутрішні структури рушія: СУБД знає, що транзакція не генеруватиме записів у WAL та не створюватиме нових версій рядків. Параметр `DEFERRABLE` (у PostgreSQL на рівні `SERIALIZABLE READ ONLY`) дозволяє транзакції відкласти свій старт до моменту, коли вона зможе отримати знімок, гарантовано вільний від будь-яких конфліктів серіалізації, що унеможливлює її аварійне переривання через помилку `40001`.

### 2. Запуск транзакції з явним рівнем (PostgreSQL / MySQL)
```sql
-- PostgreSQL
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- MySQL (InnoDB)
START TRANSACTION WITH CONSISTENT SNAPSHOT;
```

Директива `WITH CONSISTENT SNAPSHOT` у MySQL змушує рушій InnoDB сформувати знімок прочитання негайно в момент виклику команди, не чекаючи виконання першого оператора `SELECT`.

### 3. Налаштування за замовчуванням для всієї сесії
```sql
-- PostgreSQL
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- MySQL
SET SESSION transaction_isolation = 'REPEATABLE-READ';

-- Microsoft SQL Server
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

## Матриця поведінки промислових СУБД

Реальна поведінка бази даних часто суттєво відрізняється від буквального тексту стандарту ANSI:

| СУБД | Рівень за замовчуванням | READ UNCOMMITTED | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **PostgreSQL** | `READ COMMITTED` | Автоматично підвищується до `READ COMMITTED` (брудне читання фізично неможливе в MVCC). | Знімок оновлюється на кожен окремий SQL-вираз (*Statement Snapshot*). | Реалізовано як **Snapshot Isolation** (знімок на початок транзакції; захищає від фантомів, допускає Write Skew). | Повноцінний **Serializable Snapshot Isolation (SSI)** з відстеженням `SIREAD`-замків та помилкою 40001. |
| **MySQL (InnoDB)** | `REPEATABLE READ` | Брудне читання дозволено (читання без перевірки версій транзакцій). | Знімок на кожен вираз. Неблокувальні читання без блокувань рядків. | Знімок на початок транзакції для `SELECT`. Для модифікацій (`UPDATE`, `DELETE`) та `FOR UPDATE` використовуються **Next-Key Locks**, що блокують фантоми. | Усі звичайні `SELECT` неявно перетворюються на `SELECT ... LOCK IN SHARE MODE` (чисте двофазне блокування). |
| **Oracle Database** | `READ COMMITTED` | Не підтримується (викликає синтаксичну помилку). | Стандартний багатоверсійний знімок на рівні виразу через сегменти відкату (*Undo Segments*). | Не підтримується як окремий рівень (замінюється на `SERIALIZABLE`). | Реалізовано як **Snapshot Isolation** (НЕ є повноцінною серіалізовністю; можливий Write Skew). |
| **MS SQL Server** | `READ COMMITTED` (Блокувальний) | Читання без блокувань (брудне читання дозволено). | За замовчуванням бере короткі S-замки (блокує письменників). При ввімкненні `READ_COMMITTED_SNAPSHOT` переходить на версійне читання з `tempdb`. | Утримує спільні S-замки до кінця транзакції (блокує паралельні модифікації прочитаних рядків). | Діапазонні блокування ключів індексу (*Key-Range Locks*); класичне песимістичне 2PL. |

## Глибинна архітектура рушіїв ізоляції

Кожна СУБД спирається на власні системні структури та параметри ядра для забезпечення заявлених гарантій:

### 1. Архітектурні деталі PostgreSQL
У PostgreSQL версії рядків (кортежі, *tuples*) зберігаються безпосередньо в сторінках таблиць. Кожен заголовок кортежу містить системні поля `xmin` (ідентифікатор транзакції, що створила рядок) та `xmax` (ідентифікатор транзакції, що видалила або оновила рядок).

Знімок транзакції (`SnapshotData`) містить чотири ключові значення:
- `xmin`: найменший номер транзакції, яка все ще була активною на момент створення знімка (усі транзакції з `id < xmin` гарантовано зафіксовані і їхні зміни видно).
- `xmax`: перший ще не призначений номер транзакції на момент знімка (усі транзакції з `id >= xmax` ще не існували, тому їхні зміни невидимі).
- `xip_list`: точний список ідентифікаторів транзакцій, які були активними (незафіксованими) в діапазоні між `xmin` та `xmax`.
- `xcnt`: кількість елементів у списку `xip_list`.

На рівні `SERIALIZABLE` рушій SSI використовує спільну оперативну пам'ять для ведення таблиці блокувань `SIREAD`. Пам'ять під ці блокування регулюється параметром конфігурації `max_pred_locks_per_transaction` (за замовчуванням 64). Якщо кількість заблокованих рядків перевищує доступні слоти пам'яті, рушій виконує динамічну ескалацію блокувань (*Lock Escalation*): дрібні блокування рядків об'єднуються в блокування сторінки, а блокування сторінок — у блокування всієї таблиці (`PredicateLockRelation`). Це може збільшити кількість хибних спрацьовувань (*False Positives*) та відкатів транзакцій, які насправді не мали циклічних конфліктів.

### 2. Архітектурні деталі MySQL InnoDB
Рушій InnoDB реалізує принципово іншу модель: у сторінках таблиць зберігається лише найостанніша (найсвіжіша) версія рядка. Усі попередні версії динамічно реконструюються в пам'яті на льоту через ланцюжки відкату в просторі таблиць (*Undo Logs / Rollback Segments*).

Головна особливість InnoDB на рівні `REPEATABLE READ` — комбінація MVCC для звичайних запитів `SELECT` та алгоритму **Next-Key Locking** для операторів модифікації. Next-Key замок складається з блокування самого запису в індексі (*Record Lock*) та блокування проміжку перед ним (*Gap Lock*).
Наприклад, якщо індекс містить значення 10 та 20, Next-Key блокування на запис 20 блокує інтервал `(10, 20]`. Завдяки цьому жодна паралельна транзакція не може вставити значення 15, що повністю виключає появу фантомів при виконанні блокувальних оновлень.

Таймаут очікування блокування регулюється параметром `innodb_lock_wait_timeout` (за замовчуванням 50 секунд). Якщо процес за цей час не отримує замок, операція переривається з помилкою `1205: Lock wait timeout exceeded`.

### 3. Архітектурні особливості Oracle Database
У СУБД Oracle рівень `READ COMMITTED` забезпечує узгоджене читання на рівні виразу без жодних блокувань читання завдяки сегментам відкату (*Undo Tablespace*). Якщо довгий аналітичний запит читає таблицю, яку в цей час активно модифікують паралельні транзакції, Oracle зчитує змінені блоки і відновлює їхній вихідний вигляд через Undo-журнал.

Якщо обсяг сегмента відкату вичерпується або старі блоки журналу перетираються новими транзакціями до завершення довгого запиту, виникає легендарна системна помилка **`ORA-01555: snapshot too old`**. Для запобігання цій помилці адміністратори налаштовують параметр `UNDO_RETENTION` (мінімальний час збереження історії версій у секундах).

### 4. Архітектурні особливості Microsoft SQL Server
MS SQL Server історично був суто песимістичною блокувальною СУБД. На рівні `READ COMMITTED` читачі захоплюють спільні S-замки на рядки або сторінки, що блокує паралельних письменників (вони не можуть отримати X-замок).

Для переходу на сучасну багатоверсійну модель адміністратор бази даних повинен явно активувати відповідні прапорці на рівні бази:
- `ALTER DATABASE dbname SET READ_COMMITTED_SNAPSHOT ON;` (RCSI): перетворює рівень `Read Committed` на неблокувальний MVCC, де знімки виразів зберігаються у версійному сховищі системної бази `tempdb`.
- `ALTER DATABASE dbname SET ALLOW_SNAPSHOT_ISOLATION ON;`: дозволяє клієнтам явно запитувати рівень `SNAPSHOT` (повноцінний Snapshot Isolation).

## Оператори явного блокування рядків (Locking Reads)

Коли прикладній програмі необхідно забезпечити строгий захист від втраченого оновлення або зсуву запису без переходу на важкий рівень `SERIALIZABLE`, застосовуються модифікатори вибірки:

```sql
SELECT columns FROM table WHERE condition
[ FOR { UPDATE | NO KEY UPDATE | SHARE | KEY SHARE } ]
[ OF table_name ]
[ NOWAIT | SKIP LOCKED ];
```

### Типи блокувальних режимів (PostgreSQL):
- **`FOR UPDATE`**:
  Встановлює монопольне блокування (X-lock) на всі відібрані рядки. Блокує будь-які паралельні `UPDATE`, `DELETE`, `SELECT FOR UPDATE` та `SELECT FOR SHARE`. Застосовується перед модифікацією балансів.
- **`FOR NO KEY UPDATE`**:
  Слабший варіант `FOR UPDATE`: блокує оновлення даних, але дозволяє паралельні операції `FOR KEY SHARE` (наприклад, перевірку зовнішніх ключів, якщо унікальний ключ не змінюється).
- **`FOR SHARE`**:
  Встановлює спільне блокування (S-lock). Кілька транзакцій можуть одночасно утримувати `FOR SHARE`, але жодна не може змінити рядок до завершення всіх читачів.
- **`FOR KEY SHARE`**:
  Найслабше блокування, призначене для гарантії незмінності первинного/зовнішнього ключа під час вставки пов'язаних записів.

### Режими поведінки при конфлікті блокувань:
- **За замовчуванням**: транзакція засинає і чекає звільнення блокування іншим процесом (небезпека дедлоку або вичерпання таймауту).
- **`NOWAIT`**: якщо рядок заблокований іншою транзакцією, запит негайно аварійно завершується з помилкою `55P03: lock_not_available`, не чекаючи зняття блокування.
- **`SKIP LOCKED`**: запит пропускає заблоковані рядки і повертає лише вільні. Ідеальний інструмент для реалізації розподілених черг завдань (*Job Queues*): паралельні обробники ніколи не блокують один одного.

## Стандартні коди помилок транзакційного шару (SQLSTATE)

Клієнтський драйвер та пул з'єднань повинні перевіряти стандартизовані п'ятисимвольні коди помилок SQLSTATE:

| Код SQLSTATE | Символічне ім'я | Причина виникнення | Рекомендована дія клієнта |
| :--- | :--- | :--- | :--- |
| **`40001`** | `serialization_failure` | Виявлено небезпечну структуру в SSI (PostgreSQL) або паралельна транзакція першою змінила рядок під Snapshot Isolation. | Автоматичний повтор транзакції з експоненційною затримкою та джитером. |
| **`40P01`** | `deadlock_detected` | Дві або більше транзакцій заблокували ресурси у взаємно протилежному порядку (дедлок). Рушій примусово відкотив одну з них. | Автоматичний повтор транзакції. Рефакторинг бізнес-логіки для фіксації однакового порядку сортування блокувань. |
| **`55P03`** | `lock_not_available` | Спроба захоплення блокування з модифікатором `NOWAIT` на вже заблокованому рядку. | Спробувати пізніше або передати керування на рівень бізнес-логіки. |
| **`25P02`** | `in_failed_sql_transaction` | Спроба виконати запит у сесії, де попередня команда завершилася помилкою, а `ROLLBACK` ще не викликано. | Негайне виконання команди `ROLLBACK` для закриття зіпсованого контексту. |
| **`08006`** | `connection_failure` | Фізичний розрив TCP-з'єднання під час виконання запиту або фіксації транзакції. | Перевірка стану через пул з'єднань та ідемпотентний повтор із новим з'єднанням. |
