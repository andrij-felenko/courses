# 📋 Специфікація інтерфейсу pgoutput та конфігурація Debezium

Логічна реплікація та захоплення змінних даних у середовищі PostgreSQL базуються на безперервній взаємодії трьох ключових компонентів: транзакційного ядра СУБД, плагіна логічного декодування `pgoutput` та клієнтського конектора (зокрема Debezium for PostgreSQL). На відміну від застарілих сторонніх плагінів логічного декодування (таких як `wal2json` або `decoderbufs`), `pgoutput` є стандартним вбудованим бінарним плагіном ядра PostgreSQL, починаючи з версії 10. Він функціонує безпосередньо в адресному просторі фонового процесу `walsender` і не вимагає компіляції чи встановлення додаткових бібліотек мовою C на хості СУБД.

Нижче наведено вичерпну специфікацію системних параметрів, протоколу передачі повідомлень, структури подій та діагностики помилок.

---

### Системні параметри конфігурації СУБД (postgresql.conf)

Для активації логічного декодування ядро PostgreSQL вимагає попереднього налаштування транзакційного журналу та процесів передачі:

| Параметр | Рекомендоване значення | Опис та системний вплив |
| :--- | :--- | :--- |
| `wal_level` | `logical` | Включає збереження розширеної інформації про кортежі у WAL, необхідної для реконструкції логічних рядків. Вимагає перезапуску СУБД. |
| `max_replication_slots` | `≥ 10` | Максимальна кількість активних слотів реплікації (по одному слоту на кожен CDC-конектор). |
| `max_wal_senders` | `≥ 10` | Кількість одночасних фонових процесів `walsender`, які обслуговують клієнтські з'єднання. |
| `track_commit_timestamp` | `on` | Дозволяє фіксувати точний системний час фіксації транзакції (`commit_ts`), який транслюється в поле `ts_ms` події CDC. |
| `max_slot_wal_keep_size` | `65536` (64 ГБ) | Захисний ліміт дискового простору для одного слота. Запобігає повному переповненню диска WAL-сегментами при аварії конектора. |
| `wal_sender_timeout` | `60000` (60 с) | Час очікування підтвердження зв'язку від клієнта CDC перед примусовим розривом підвислого з'єднання. |

Параметр `wal_level = logical` призводить до помірного збільшення обсягу генерованого журналу WAL (зазвичай на 10–25%), оскільки до записів додаються метадані структури таблиць та ідентифікатори кортежів. Значення `max_slot_wal_keep_size` є обов'язковим запобіжником: у разі зупинки споживача CDC на невизначений час сервер видалить застарілі сегменти WAL після досягнення ліміту (наприклад, 64 ГБ), що переведе слот у стан `lost`, але збереже основну базу даних від аварійної зупинки через переповнення файлової системи.

### Керування публікаціями та ідентифікатором репліки (SQL DDL)

Клієнтський конектор підключається до іменованої публікації (Publication) та використовує логічний слот реплікації (Replication Slot):

```sql
-- Створення публікації для вибіркового переліку таблиць
CREATE PUBLICATION cdc_publication FOR TABLE orders, order_items, customers;

-- Створення публікації для абсолютно всіх таблиць бази даних (включно з майбутніми)
CREATE PUBLICATION cdc_all_tables FOR ALL TABLES;

-- Налаштування ідентифікатора репліки для коректного отримання попереднього образу рядка (before-image)
ALTER TABLE orders REPLICA IDENTITY FULL;
```

#### Режими REPLICA IDENTITY:
* `DEFAULT`: При виконанні операцій `UPDATE` та `DELETE` у журнал WAL записуються лише старі значення стовпців первинного ключа. Якщо первинний ключ відсутній, оновлення рядків через логічну реплікацію блокується ядром СУБД.
* `FULL`: У транзакційний журнал записується повний старий образ рядка (всі стовпці у стані до виконання модифікації). Це необхідно для систем аудиту, патерну CQRS або аналітичних споживачів, яким потрібен детальний диференційний аналіз усіх полів.
* `INDEX index_name`: Використовує вказаний унікальний індекс без умовних предикатів замість первинного ключа для ідентифікації рядка.
* `NOTHING`: Інформація про старі рядки не записується взагалі. Операції `UPDATE` та `DELETE` для такої таблиці стають недоступними для логічної реплікації.

### Двійковий протокол повідомлень pgoutput (Wire Protocol)

Плагін `pgoutput` транслює потік логічних змін через клієнтський протокол потокової реплікації PostgreSQL у вигляді строго типізованої послідовності двійкових повідомлень.

#### Специфікація типів повідомлень:

1. **`B` (Begin)**: Позначає відкриття атомарного транзакційного блоку.
   * `int8`: Символ `'B'`.
   * `int64`: Фінальний LSN фіксації транзакції (Final LSN).
   * `int64`: Мітка часу фіксації транзакції (кількість мікросекунд з 2000-01-01 UTC).
   * `int32`: Унікальний ідентифікатор транзакції (XID).

2. **`R` (Relation)**: Описує схему відношення (метадані таблиці). Надсилається перед першою появою операцій з таблицею або при зміні її DDL-структури.
   * `int8`: Символ `'R'`.
   * `int32`: Унікальний числовий ідентифікатор (OID) таблиці в каталозі `pg_class`.
   * `string`: Простір імен (схема таблиці, завершується нульовим байтом `\0`).
   * `string`: Назва таблиці (завершується `\0`).
   * `int8`: Тип ідентифікатора репліки (`'d'` = default, `'n'` = nothing, `'f'` = full, `'i'` = index).
   * `int16`: Кількість стовпців `N`.
   * Для кожного стовпця:
     * `int8`: Прапорці стовпця (біт `1` позначає, що стовпець входить до складу первинного ключа).
     * `string`: Назва стовпця (`\0`).
     * `int32`: OID типу даних стовпця у системному каталозі `pg_type`.
     * `int32`: Модифікатор типу (`atttypmod`).

3. **`I` (Insert)**: Додавання нового кортежу.
   * `int8`: Символ `'I'`.
   * `int32`: OID відношення (посилається на попереднє повідомлення `'R'`).
   * `int8`: Символ `'N'` (New Tuple).
   * `TupleData`: Структура значень доданого кортежу.

4. **`U` (Update)**: Оновлення існуючого кортежу.
   * `int8`: Символ `'U'`.
   * `int32`: OID відношення.
   * Опціонально: `int8` (`'K'` — старий первинний ключ, або `'O'` — старий кортеж при `REPLICA IDENTITY FULL`) + `TupleData`.
   * `int8`: Символ `'N'` (новий стан кортежу) + `TupleData`.

5. **`D` (Delete)**: Видалення кортежу.
   * `int8`: Символ `'D'`.
   * `int32`: OID відношення.
   * `int8`: Символ `'K'` або `'O'` + `TupleData` видаленого кортежу.

6. **`C` (Commit)**: Фіксація поточної транзакції.
   * `int8`: Символ `'C'`.
   * `int8`: Прапорці поведінки (зарезервовано, 0).
   * `int64`: Позиція LSN операції Commit у потоці WAL.
   * `int64`: Кінцевий LSN транзакції.
   * `int64`: Системна мітка часу фіксації транзакції.

#### Формат передачі значень стовпців (TupleData):
* `int16`: Кількість стовпців у кортежі.
* Для кожного стовпця:
  * `'n'`: Поле містить явне значення `NULL`.
  * `'u'`: Незмінене значення TOAST (The Oversized-Attribute Storage Technique). Якщо велике текстове чи двійкове поле не змінювалося під час `UPDATE`, ядро надсилає маркер `'u'` замість повторного передавання мегабайтів даних, що суттєво заощаджує мережевий трафік.
  * `'t'`: Текстове представлення значення + `int32` (довжина в байтах) + байти UTF-8 рядка.

### Специфікація конверта подій Debezium (Event Envelope Contract)

Debezium перетворює бінарні повідомлення СУБД в уніфіковану JSON- або Apache Avro-структуру:

```json
{
  "schema": {
    "type": "struct",
    "fields": [
      { "field": "before", "type": "struct", "optional": true, "name": "orders.Value" },
      { "field": "after", "type": "struct", "optional": true, "name": "orders.Value" },
      { "field": "source", "type": "struct", "optional": false, "name": "io.debezium.connector.postgresql.Source" },
      { "field": "op", "type": "string", "optional": false },
      { "field": "ts_ms", "type": "int64", "optional": true },
      { "field": "transaction", "type": "struct", "optional": true }
    ],
    "optional": false,
    "name": "dbserver1.inventory.orders.Envelope"
  },
  "payload": {
    "before": {
      "id": 1001,
      "customer_id": 42,
      "total_amount": "150.00",
      "status": "PENDING"
    },
    "after": {
      "id": 1001,
      "customer_id": 42,
      "total_amount": "150.00",
      "status": "PAID"
    },
    "source": {
      "version": "2.5.0.Final",
      "connector": "postgresql",
      "name": "dbserver1",
      "ts_ms": 1718880000123,
      "snapshot": "false",
      "db": "shop",
      "sequence": "[\"24001288\",\"24001352\"]",
      "schema": "public",
      "table": "orders",
      "txId": 58421,
      "lsn": 24001352
    },
    "op": "u",
    "ts_ms": 1718880000456
  }
}
```

#### Семантика коду операції (`op`):
* `"r"` (Read): Початковий або інкрементний знімок існуючих даних (Snapshot read).
* `"c"` (Create): Операція додавання рядка `INSERT`.
* `"u"` (Update): Операція оновлення рядка `UPDATE`.
* `"d"` (Delete): Операція видалення рядка `DELETE`.
* `"t"` (Truncate): Операція повного очищення таблиці `TRUNCATE`.

### Еталонна конфігурація конектора Debezium PostgreSQL

Конфігураційний маніфест для розгортання конектора у розподіленому середовищі Apache Kafka Connect:

```json
{
  "name": "postgres-orders-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "tasks.max": "1",
    "plugin.name": "pgoutput",
    "database.hostname": "pg-primary.internal",
    "database.port": "5432",
    "database.user": "cdc_user",
    "database.password": "${file:/secrets.properties:pg_pass}",
    "database.dbname": "shop",
    "database.server.name": "production_db",
    "slot.name": "debezium_orders_slot",
    "slot.drop.on.stop": "false",
    "publication.name": "cdc_publication",
    "publication.autocreate.mode": "filtered",
    "table.include.list": "public.orders,public.order_items",
    "decimal.handling.mode": "double",
    "time.precision.mode": "connect",
    "tombstones.on.delete": "true",
    "snapshot.mode": "initial",
    "snapshot.locking.mode": "none",
    "heartbeat.interval.ms": "10000"
  }
}
```

#### Інженерний розбір критичних параметрів конфігурації:
* `slot.drop.on.stop = false`: Категорично забороняє автоматичне видалення слота реплікації при плановій зупинці конектора чи оновленні версії. Якщо цей параметр встановити у `true`, будь-який перезапуск конектора призведе до втрати зв'язку з позицією LSN і неможливості продовжити читання без нового важкого знімка бази даних.
* `tombstones.on.delete = true`: При видаленні рядка Debezium відправляє в топік Kafka спершу стандартне повідомлення з кодом `op: "d"`, а слідом за ним — маркерне порожнє повідомлення з ключем запису та тілом `null` (Tombstone). Це дає вказівку рушію Kafka Log Compaction остаточно видалити всі старі версії цього ключа з диска після закінчення періоду `delete.retention.ms`.
* `heartbeat.interval.ms = 10000`: Конектор генерує періодичні штучні службові повідомлення в окремий службовий топік або таблицю. Це критично необхідно для баз даних із низькою частотою оновлення цільових таблиць: регулярний пульс змушує конектор підтверджувати прогрес LSN серверу СУБД, дозволяючи процесу Checkpointer вчасно переробляти та очищати застарілі WAL-сегменти.

### Діагностика типових протокольних помилок

1. **`ERROR: cannot update table "orders" because it has no replica identity`**
   * *Причина*: У таблиці відсутній первинний ключ або `REPLICA IDENTITY` встановлено у значення `DEFAULT` без індексу, а користувач виконав команду `UPDATE` чи `DELETE`.
   * *Виправлення*: Виконати `ALTER TABLE orders REPLICA IDENTITY FULL;` або додати суворий первинний ключ `ALTER TABLE orders ADD PRIMARY KEY (id);`.

2. **`ERROR: requested WAL segment 00000001000000A10000003F has already been removed`**
   * *Причина*: Конектор був вимкнений занадто довго, і обсяг накопиченого журналу перевищив системний ліміт `max_slot_wal_keep_size`. Сервер PostgreSQL видалив старий сегмент WAL для порятунку вільного місця на диску.
   * *Виправлення*: Слот реплікації вважається інвалідованим (`wal_status = 'lost'`). Необхідно перестворити слот та ініціювати повторний повний знімок даних (`snapshot.mode = 'always'`).
