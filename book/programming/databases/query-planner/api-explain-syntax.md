# 📋 Довідник параметрів EXPLAIN та фізичних операторів

Команда `EXPLAIN` відкриває внутрішнє представлення плану виконання запиту, згенерованого оптимізатором СУБД. Вона дозволяє розробнику побачити дерево фізичних операторів, оцінку вартості, прогнозовану та фактичну кількість рядків, а також статистику використання дискового кешу й апаратних ресурсів.

## 1. Синтаксис команди в популярних СУБД

Різні реляційні рушії надають власний синтаксис для інспектування планів виконання.

### PostgreSQL
У PostgreSQL параметри передаються у круглих дужках через кому, що дозволяє комбінувати діагностичні прапорці:

```sql
EXPLAIN [ ( option [, ...] ) ] statement
EXPLAIN [ ANALYZE ] [ VERBOSE ] statement

-- Де option може бути:
-- ANALYZE [ boolean ]
-- VERBOSE [ boolean ]
-- COSTS [ boolean ]
-- SETTINGS [ boolean ]
-- BUFFERS [ boolean ]
-- WAL [ boolean ]
-- TIMING [ boolean ]
-- SUMMARY [ boolean ]
-- FORMAT { TEXT | XML | JSON | YAML }
```

### MySQL (від версії 8.0.18)
У MySQL починаючи з версії 8.0.18 впроваджено підтримку деревоподібного виводу та замірів часу:

```sql
EXPLAIN [FORMAT = { TRADITIONAL | JSON | TREE }] statement;
EXPLAIN ANALYZE statement;
```

### SQLite
У SQLite команда `EXPLAIN QUERY PLAN` повертає високорівневий опис стратегії пошуку та використаних індексів:

```sql
EXPLAIN QUERY PLAN statement;
```

## 2. Опції команди EXPLAIN у PostgreSQL

Кожен прапорець керує окремим аспектом деталізації звіту або режимом виконання запиту.

| Опція | За замовчуванням | Призначення | Вплив на виконання |
| :--- | :--- | :--- | :--- |
| `ANALYZE` | `FALSE` | **Реально виконує запит** і заміряє фактичний час, кількість рядків та ітерацій для кожного вузла. | ⚠️ **Виконує оператори `INSERT`/`UPDATE`/`DELETE`!** Для безпечного тестування загортайте у транзакцію `BEGIN; ... ROLLBACK;`. |
| `BUFFERS` | `FALSE` | Виводить статистику дискового вводу-виводу: кількість сторінок, знайдених у кеші (`hit`), зчитаних із диска (`read`), брудних (`dirtied`) та записаних (`written`). Працює лише разом із `ANALYZE`. | Додає мінімальні накладні витрати на читання лічильників пам'яті. |
| `VERBOSE` | `FALSE` | Виводить повні імена стовпців (з іменами таблиць), схеми, список вихідних полів кожного вузла (Output), а також внутрішні ID тригерів та функцій. | Збільшує обсяг текстового виводу плану. |
| `COSTS` | `TRUE` | Показує оцінку вартості (`cost=startup..total`), очікувану кількість рядків (`rows`) та середню ширину рядка в байтах (`width`). | Не впливає на час виконання. |
| `TIMING` | `TRUE` | Заміряє фактичний час початку (`first`) та завершення (`last`) роботи кожного вузла у мілісекундах. Працює лише з `ANALYZE`. Якщо встановити у `FALSE`, заміряє лише рядки без виклику системного таймера. | На деяких архітектурах частий виклик системного таймера додає помітні накладні витрати. |
| `WAL` | `FALSE` | Виводить статистику використання журналу випереджального запису (WAL): кількість згенерованих записів, повносторінкових образів (FPI) та обсяг згенерованого журналу в байтах. Працює лише з `ANALYZE`. | Корисно для аналізу запитів модифікації даних (`UPDATE`, `INSERT`). |
| `SETTINGS` | `FALSE` | Додає до звіту блок конфігураційних параметрів планувальника, значення яких відрізняються від стандартних (наприклад, `work_mem`, `random_page_cost`, `enable_nestloop`). | Допомагає відтворювати плани на різних серверах. |
| `SUMMARY` | `ANALYZE` | Додає підсумковий рядок із часом планування (Planning Time) та загальним часом виконання (Execution Time). | Не впливає на продуктивність. |
| `FORMAT` | `TEXT` | Задає формат структури плану: `TEXT` (людинозрозуміле дерево з відступами), `JSON` (для автоматичного парсингу інструментами), `YAML`, `XML`. | Тільки форматування виводу. |

## 3. Фізичні оператори сканування таблиць (Scan Nodes)

Оператори сканування визначають, у який спосіб рушій видобуває сирі кортежі з фізичних файлів на диску чи зі сторінок оперативного буфера.

| Фізичний оператор | Опис роботи | Коли використовується оптимізатором |
| :--- | :--- | :--- |
| `Seq Scan` | Послідовно читає всі блоки таблиці з диска/кешу, застосовуючи фільтр `Filter` до кожного кортежу. | Таблиця невелика, відсутній відповідний індекс, або запит вибирає понад 15–20% рядків. |
| `Index Scan` | Спускається по B-дереву до листків за умовою `Index Cond`, отримує фізичні покажчики на сторінки купи (TID) і читає відповідні рядки з таблиці. | Високоселективні вибірки (менше 3–5% рядків), коли потрібні стовпці, яких немає в індексі. |
| `Index Only Scan` | Читає дані виключно зі сторінок індексу без звернення до таблиці, якщо карта видимості (Visibility Map) підтверджує актуальність сторінки. | Усі поля вибірки входять до складу індексу (покривний індекс / `INCLUDE`), а таблиця регулярно очищується `VACUUM`. |
| `Bitmap Index Scan` | Сканує листки індексу та створює в оперативній пам'яті бітову карту номерів сторінок, де містяться потрібні рядки. | Перша фаза двоетапного сканування або при об'єднанні кількох індексів через `BitmapAnd` / `BitmapOr`. |
| `Bitmap Heap Scan` | Впорядковує номери сторінок із бітової карти та зчитує блоки таблиці у послідовному фізичному порядку, мінімізуючи стрибки головки диска. | Друга фаза сканування при вибірці 1–15% рядків або при комбінуванні умов за різними індексами. |
| `Tid Scan` | Зчитує кортеж безпосередньо за його фізичною адресою `ctid = '(page, offset)'`. | Прямий доступ за системним ідентифікатором рядка. |
| `CTE Scan` | Сканує тимчасову матеріалізовану таблицю, створену виразом `WITH ... AS MATERIALIZED`. | Обробка результату попередньо матеріалізованого загального табличного виразу. |
| `Function Scan` | Отримує набір рядків, згенерований функцією, що повертає таблицю (наприклад, `generate_series()`, `json_to_recordset()`). | Виклики табличних функцій у секції `FROM`. |

## 4. Фізичні оператори з'єднання (Join Nodes)

Оператори з'єднання комбінують кортежі з двох джерел у єдиний потік рядків відповідно до предиката з'єднання.

| Оператор з'єднання | Принцип роботи | Вимоги до ресурсів та оптимізація |
| :--- | :--- | :--- |
| `Nested Loop` | Для кожного рядка зовнішнього джерела (Outer) виконує пошук у внутрішньому джерелі (Inner). | Мінімальна початкова вартість (`startup ≈ 0`). Ідеальний, коли зовнішній набір дуже малий (1–100 рядків), а внутрішній має швидкий `Index Scan`. |
| `Hash Join` | **Фаза 1 (Build):** зчитує весь внутрішній набір і будує хеш-таблицю в пам'яті за ключем з'єднання.<br>**Фаза 2 (Probe):** послідовно читає зовнішній набір і шукає збіги в хеш-таблиці. | Вимагає оперативної пам'яті для хеш-таблиці. Якщо таблиця не вміщається у `work_mem`, вона розбивається на батчі й скидається на диск (`Batches: > 1`). |
| `Merge Join` | Синхронно просуває два курсори по обох відсортованих входах, зіставляючи рівні ключі, подібно до алгоритму сортування злиттям. | Потребує впорядкованості обох входів за ключем з'єднання (або попередній `Sort`, або отримання з `Index Scan`). Пам'ять практично не використовується. |

## 5. Допоміжні оператори плану

Допоміжні вузли виконують агрегацію, перевпорядкування, сортування та паралелізацію обчислень.

| Вузол | Призначення | Діагностичні маркери в плані |
| :--- | :--- | :--- |
| `Sort` | Сортує вхідний потік кортежів за вказаними ключами. | `Sort Method: quicksort Memory: ...kB` (швидко в RAM) проти `Sort Method: external merge Disk: ...kB` (повільно через диск при малому `work_mem`). |
| `Incremental Sort` | Досортовує дані, які вже частково впорядковані за префіксом ключів (наприклад, сортування за `(a, b)`, коли дані вже впорядковані за `a`). | Значно економить пам'ять і процесорний час у порівнянні з повним сортуванням. |
| `Hash` | Будує хеш-таблицю в оперативній пам'яті для батьківського вузла `Hash Join`. | `Buckets: N  Batches: M  Memory Usage: XkB`. |
| `Aggregate` | Обчислює агрегатні функції (`SUM`, `COUNT`, `AVG`, `GROUP BY`). | Види: `HashAggregate` (групування через хеш-таблицю в пам'яті) або `GroupAggregate` (групування по відсортованому входу). |
| `Materialize` | Зберігає результат виконання дочірнього вузла в оперативній пам'яті або на диску для багаторазового повторного сканування без повторних обчислень. | Часто з'являється у правій гілці `Nested Loop`, коли внутрішній підзапит не має індексу. |
| `Gather` / `Gather Merge` | Збирає результати паралельної обробки від фонових робочих процесів (Parallel Workers) в єдиний потік. | `Workers Planned: N  Workers Launched: M`. |
| `Limit` | Припиняє виконання дочірніх операторів після отримання вказаної кількості рядків (`LIMIT / OFFSET`). | Дозволяє оптимізатору обрати план із низьким `startup cost`, зупиняючи повне сканування. |

## 6. Метрики блочного кешу (BUFFERS) та життєвий цикл сторінки

При запуску `EXPLAIN (ANALYZE, BUFFERS)` у звіті з'являється детальна розкладка роботи з дисковими блоками (за замовчуванням розмір блоку в PostgreSQL — 8 КБ):

```text
Buffers: shared hit=4210 read=120 dirtied=5 written=0, temp read=340 written=340
```

Ці показники відображають взаємодію рушія виконання з багаторівневою підсистемою пам'яті:

- **`shared hit`:** кількість 8-КБ блоків, які в момент звернення вже перебували у спільному буферному пулі СУБД (`shared_buffers`). Доступ до таких сторінок відбувається через оперативну пам'ять із взяттям короткочасного блокування сторінки (buffer pin / lightweight lock) і триває частки мікросекунди без жодних системних викликів вводу-виводу.
- **`shared read`:** кількість блоків, які були відсутні в `shared_buffers`. СУБД була змушена виділити вільний слот у буферному пулі та виконати системний виклик `read()`. Якщо сторінка вже перебувала в кеші сторінок операційної системи (Page Cache ядра Linux), операція завершиться за кілька мікросекунд без фізичного звернення до SSD. Якщо ж сторінки не було і в кеші ОС, виклик призводить до фізичного зчитування з накопичувача (затримка від 0.1 мс на швидких NVMe до 10 мс на магнітних дисках).
- **`shared dirtied`:** кількість блоків, вміст яких було модифіковано поточним запитом (наприклад, вставка, оновлення кортежу або встановлення бітів інфомаски видимості рядка). Ці сторінки помічаються як «брудні» й залишаються в пам'яті до моменту їх скидання на диск фоновими службами.
- **`shared written`:** кількість брудних блоків, які поточний процес виконання був змушений самостійно синхронно записати на накопичувач. Це трапляється тоді, коли всі буфери зайняті, а фоновий процес фонового запису (Background Writer) не встигає звільняти чисті сторінки. Синхронний запис клієнтським бекендом суттєво сповільнює виконання запиту.
- **`temp read / temp written`:** кількість тимчасових блоків, зчитаних та записаних на диск. Виникає тоді, коли операція сортування (`Sort`), агрегації (`HashAggregate`) або побудови хеш-таблиці (`Hash Join`) перевищує ліміт пам'яті сесії `work_mem`.

## 7. Керування поведінкою планувальника через прапорці (GUCs)

Для діагностики та перевірки альтернативних планів адміністратор може тимчасово змінювати параметри конфігурації планувальника в межах поточної сесії або транзакції:

- **`enable_seqscan`, `enable_indexscan`, `enable_bitmapscan`:** вмикають або вимикають відповідні методи сканування. Важливо розуміти, що вимкнення (наприклад, `SET enable_seqscan = off;`) не забороняє послідовне сканування абсолютно, а лише додає штучний штраф `10^{10}` до його вартості. Якщо таблиця не має жодного індексу, оптимізатор все одно буде змушений обрати `Seq Scan`.
- **`enable_nestloop`, `enable_hashjoin`, `enable_mergejoin`:** дозволяють примусово перевірити поведінку запиту з конкретним типом з'єднання для оцінки чутливості до помилок кардинальності.
- **`work_mem`:** задає обсяг пам'яті для кожної окремої операції сортування або хешування перед скиданням на диск. Складний запит із 4 з'єднаннями та 2 сортуваннями може одночасно виділити до `6 × work_mem` оперативної пам'яті.
- **`effective_cache_size`:** повідомляє планувальнику приблизний обсяг пам'яті, доступної для кешування даних (сума `shared_buffers` та кешу файлової системи ОС). Вище значення заохочує оптимізатор частіше використовувати індексні сканування, припускаючи високу ймовірність потрапляння сторінок у кеш.

## 8. Практичні правила інтерпретації звіту

Під час аналізу складних планів рекомендується дотримуватися системної послідовності кроків:

1. **Знайти вузол із найбільшим власним часом (Exclusive Time):** час виконання батьківського вузла завжди включає час усіх його нащадків. Щоб знайти справжнє вузьке місце, відніміть сумарний час дочірніх операторів від загального часу вузла. Наприклад, якщо `Hash Join` тривав 15 мс, а його дочірній `Seq Scan` — 14 мс, власні витрати вузла з'єднання складають лише 1 мс, а оптимізувати потрібно дочірнє сканування.
2. **Зіставити прогноз із фактом:** знайдіть вузли, де різниця між `rows` (прогноз) та `actual rows` перевищує порядок величини. Саме в цьому місці планувальник припустився помилки через неточну статистику або приховану кореляцію стовпців.
3. **Оцінити дисковий профіль через BUFFERS:** підрахуйте коефіцієнт попадання в кеш `hit / (hit + read)`. Якщо він нижчий за 99% для частих транзакційних запитів, це свідчить про неефективне використання індексів або дефіцит виділеної оперативної пам'яті сервера.
4. **Перевірити наявність скидань на диск:** будь-яка згадка `Disk` у рядках `Sort Method` або `Batches > 1` у вузлах `Hash` вимагає перегляду конфігурації `work_mem` для усунення зайвих операцій запису у тимчасові файли.
5. **Проаналізувати вплив паралелізму:** зверніть увагу на співвідношення `Workers Planned` та `Workers Launched`. Якщо планувальник розраховував на 4 фонові процеси, а запустити вдалося лише 1 (через вичерпання загального пулу процесів `max_parallel_workers`), реальний час запиту пропорційно зросте.
6. **Оцінити накладні витрати JIT:** якщо в кінці плану присутній блок `JIT` із часом оптимізації та емісії коду `Total: 45.0 ms`, тоді як сам запит виконувався 5 мс, це пряме свідчення того, що JIT-компілятор увімкнений для занадто дрібного запиту і його доцільно деактивувати.
