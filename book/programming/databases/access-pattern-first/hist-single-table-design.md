# 📜 Еволюція патерну Single Table Design: від нормалізації до перевантаження ключів

У реляційній парадигмі єдиним правильним способом організації сховища вважалася декомпозиція сутностей за нормальними формами (1NF, 2NF, 3NF, BCNF) з окремою таблицею для кожного типу бізнес-об'єкта. Проте при переході до хмарних розподілених баз даних (таких як Amazon DynamoDB або Apache Cassandra) мультитабличний підхід призвів до значного зростання затримок та фінансових витрат.

Розглянемо історію виникнення патерну Single Table Design, інженерні практики компанії Amazon, внесок Ріка Хуліхана та еволюцію інструментів моделювання NoSQL даних.

### Чому мультитабличний дизайн виявився неефективним у DynamoDB

Коли у 2012 році Amazon запустив публічний сервіс **DynamoDB**, більшість інженерів перенесли свій звичний реляційний досвід: створили окрему таблицю `Users`, окрему `Orders`, `OrderItems` та `Addresses`.

Дуже швидко команди зіткнулися з чотирма критичними проблемами:

1. **Проблема N+1 мережевих викликів (RTT Overhead)**: Щоб відрендерити головну сторінку користувача (профіль + 5 останніх замовлень + адреса доставки), додаток був змушений послідовно виконати 7 окремих HTTP-запитів до різних таблиць через інтернет, що створювало затримку понад 100–200 мс.
2. **Неможливість атомарного збереження**: До появи транзакцій `TransactWriteItems` у 2018 році запис пов'язаних сутностей у різні таблиці не мав транзакційних гарантій і вимагав написання складних розподілених саг.
3. **Фінансові перевитрати на Provisioned Throughput**: У DynamoDB пропускна здатність на читання (RCU) та запис (WCU) виділяється та тарифікується для кожної таблиці окремо. Якщо сервіс мав 20 таблиць, більшість виділених одиниць потужності простоювали, але щомісяця оплачувалися компанією.
4. **Холодний старт та управління з'єднаннями**: Кожна окрема таблиця вимагала власної автентифікації IAM, дескрипторів з'єднань та моніторингу метрик CloudWatch.

### Прорив Ріка Хуліхана та стандартизація Single Table Design

Головним ідеологом та популяризатором парадигми Single Table Design став головний архітектор баз даних AWS **Рік Хуліхан (Rick Houlihan)**.

У серії легендарних доповідей на конференціях **AWS re:Invent (2018–2020)** під назвою *«Amazon DynamoDB Deep Dive: Advanced Design Patterns»* Хуліхан продемонстрував, як розміщення всіх доменних сутностей мікросервісу в **одній-єдиній таблиці** вирішує всі проблеми мультитабличної архітектури:

* **Перевантаження ключів (Key Overloading)**: Використання абстрактних назв стовпців `PK` (Partition Key) та `SK` (Sort Key), куди записуються композитні рядки з префіксами (`USER#101`, `ORDER#2024#05`, `PRODUCT#A42`).
* **Локалізація пов'язаних сутностей (Item Collections)**: Збереження профілю користувача та всіх його замовлень під одним значенням `PK`. Це дозволило отримувати весь граф зв'язаних даних за **1 єдиний запит `Query`** за час менше 10 мс.
* **Глобальні вторинні індекси (GSI)**: Використання спільних індексів `GSI1PK` та `GSI1SK` для розгортання альтернативних сценаріїв вибірки без створення нових фізичних таблиць.

### Сучасний стан: Інструменти та баланс між гнучкістю та складністю

Single Table Design здійснив революцію у побудові високонавантажених serverless-додатків на AWS Lambda, забезпечивши стабільну мілісекундну затримку при мільйонах запитів на секунду.

Для спрощення візуалізації таких таблиць AWS випустила інструмент **NoSQL Workbench**, а ком'юніті створило типізовані бібліотеки (DynamoDB Toolbox, ElectroDB), які дозволяють описувати схеми поліморфних сутностей декларативно.

Водночас індустрія усвідомила межі застосування патерну: Single Table Design вимагає високої дисципліни проєктування та точного знання всіх шаблонів доступу наперед. Якщо бізнес-вимоги часто змінюються або системі потрібна довільна аналітика, надмірна денормалізація ускладнює супровід коду, тому в сучасній практиці застосовують гібридний підхід: Single Table для високоінтенсивного транзакційного ядра та реплікація через Change Data Capture (DynamoDB Streams) в аналітичні реляційні або колонкові бази.

Це закріпило Single Table Design як один із найефективніших інструментів сучасної хмарної архітектури при роботі з передбачуваними навантаженнями.
