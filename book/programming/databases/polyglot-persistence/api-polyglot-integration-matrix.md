# 📋 Довідник архітектури Polyglot Persistence: Матриця вибору сховищ

Поліглотне збереження даних вимагає точного зіставлення вимог конкретного мікросервісу з технічними характеристиками рушіїв зберігання.

Цей довідник містить порівняльну матрицю спеціалізованих СУБД, протоколи міжбазової синхронізації, патерни обробки мережевих відмов, правила вибору сховищ, аналіз ліцензійних ризиків та контрольний чекліст оцінки сукупної вартості володіння (TCO).

---

| Спеціалізація | Типові СУБД | Модель даних | Оптимальний сценарій використання | Цільова затримка | Ризики та компроміси |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Транзакційне ядро (OLTP)** | PostgreSQL, MySQL, CockroachDB | Реляційні таблиці (3NF) | Фінансові транзакції, білінг, замовлення | 5–20 мс | Важке горизонтальне масштабування на запис |
| **Кеш та швидкі стани** | Redis, KeyDB, Dragonfly | Ключ — Значення (RAM) | Сесії користувачів, лімітери швидкості, черги | < 1 мс | Обмеження обсягом оперативної пам'яті |
| **Повнотекстовий пошук** | Elasticsearch, OpenSearch, Meilisearch | Інвертований індекс (Lucene) | Каталог товарів з фільтрами, автокомпліт, логи | 10–50 мс | Високе споживання CPU та пам'яті на індексацію |
| **Графові зв'язки** | Neo4j, Memgraph, Amazon Neptune | Вузли та ребра (LPG) | Антифрод, соціальні графи, рекомендаційні рушії | 5–30 мс | Складність шардування великих графів |
| **Колонкова аналітика (OLAP)**| ClickHouse, Snowflake, DuckDB | Колонкове стиснення | Аналітика подій, бізнес-звіти, метрики телеметрії | 20–200 мс | Повна непридатність для точкових мутацій |
| **Часові ряди (Time-Series)** | TimescaleDB, InfluxDB | Часові чанки | IoT-сенсори, фінансовий тікер, метрики серверів | 5–15 мс | Вимагає політик автоматичного очищення (Retention) |
| **Векторний пошук (AI/RAG)** | Qdrant, Milvus, pgvector | Векторні графи HNSW | Семантичний пошук, RAG для великих мовних моделей | 10–40 мс | Вимагає попереднього обчислення ембедінгів |

### Порівняння механізмів міжбазової синхронізації

#### 1. Dual-Write з боку додатку (Антипатерн)
* **Механізм**: Прикладний код послідовно викликає `db.save()` та `elastic.index()`.
* **Переваги**: Простота первинної реалізації без додаткової інфраструктури.
* **Недоліки**: Неминуче виникнення розходжень при збоях мережі та станах гонитви при конкурентному записі.
* **Вердикт**: Категорично заборонено для продакшен-систем.

#### 2. Change Data Capture (CDC) через журнал транзакцій
* **Механізм**: Агент (Debezium) безперервно читає Write-Ahead Log (WAL) первинної бази даних і публікує події в Apache Kafka.
* **Переваги**: Нульовий вплив на транзакційний потік, гарантія фіксації всіх змін, порядок подій.
* **Недоліки**: Необхідність адміністрування кластера Kafka та Debezium Connectors.
* **Вердикт**: Золотий індустріальний стандарт для Enterprise-архітектури.

#### 3. Патерн Transactional Outbox
* **Механізм**: Подія зберігається в окрему таблицю `Outbox` у межах тієї ж транзакції, що й основні бізнес-дані, після чого асинхронно вичитується релеєм (Outbox Relay).
* **Переваги**: Працює на рівні стандартного SQL без прямого доступу до системних журналів СУБД.
* **Недоліки**: Додаткове навантаження на таблицю Outbox при високій інтенсивності запису.
* **Вердикт**: Оптимальний вибір для мікросервісів середнього масштабу.

### Стратегії узгодженості та відновлення після збоїв

1. **Ідемпотентні споживачі (Idempotent Consumers)**: Усі підсистеми синхронізації повинні підтримувати повторну обробку однакових повідомлень без зміни кінцевого стану. Застосовуйте перевірку унікальних ідентифікаторів повідомлень (Message Deduplication) у Redis або локальній таблиці споживача.
2. **Версіонування сутностей (Optimistic Concurrency Control)**: Кожне повідомлення містить монотонно зростаючий номер версії `version`; споживач відкидає застарілі оновлення, якщо в сховищі вже зафіксована новіша версія.
3. **Регулярне звірення та аудит розбіжностей (Reconciliation Engine)**: Фоновий процес (наприклад, щонічний скрипт порівняння), який зіставляє хеш-суми записів у первинній базі та вторинних індексах, автоматично виправляючи виявлені аномалії.
4. **Черга мертвих листів (Dead-Letter Queue, DLQ)**: Події, обробка яких провалилася через несумісність схеми або помилки парсингу після 3–5 повторних спроб (Retries with Exponential Backoff), автоматично перенаправляються в DLQ для ручного аналізу інженерами.
5. **Компенсаційні транзакції (Saga Pattern)**: Якщо бізнес-процес охоплює кілька незалежних мікросервісів із власними базами даних, у разі помилки на проміжному етапі запускаються зворотні компенсуючі транзакції для повернення системи до узгодженого стану.
6. **Контроль затримки реплікації (Lag Monitoring)**: Вимірювання часу між створенням події в PostgreSQL та її індексацією в Elasticsearch за допомогою міток часу `event_timestamp`.
7. **Автоматичне переіндексування (Backfill Pipeline)**: Наявність скриптів для повного повторного перекачування даних із первинної реляційної бази в Elasticsearch або ClickHouse при зміні маппінгу або пошкодженні індексів.

### Типові помилки архітектури поліглотного збереження

* **Помилка 1: Передчасна оптимізація**: Додавання трьох різних NoSQL баз на етапі запуску стартапу, коли навантаження становить менше 10 запитів на секунду.
* **Помилка 2: Спільне володіння базою (Shared Database)**: Дозвіл кільком мікросервісам напряму читати та модифікувати таблиці однієї фізичної бази, що руйнує межі контекстів (Bounded Contexts) та призводить до неконтрольованих взаємних блокувань.
* **Помилка 3: Відсутність моніторингу затримки реплікації**: Неконтрольоване зростання затримки між первинною базою та Elasticsearch призводить до того, що користувачі хвилинами не бачать своїх щойно опублікованих товарів.
* **Помилка 4: Використання кешу як основного сховища**: Збереження критичних бізнес-даних виключно в Redis без скидання на диск або збереження в реляційній базі загрожує повною втратою інформації при аварійному перезапуску сервера.
* **Помилка 5: Ігнорування вартості оновлення індексів**: Масивний паралельний запис у повнотекстовий індекс викликає перевантаження CPU через безперервне злиття сегментів Lucene (Segment Merging).
* **Помилка 6: Відсутність версіонування подій**: Передача повідомлень без явного поля `schema_version` унеможливлює безпечне оновлення коду споживачів.

### Контрольний чекліст оцінки сукупної вартості володіння (TCO)

Перед додаванням нової спеціалізованої СУБД до архітектури проекту дайте відповідь на запитання:

1. **Критерій порядку величини (> 10x)**: Чи забезпечує нова база прискорення вибірки або скорочення витрат щонайменше у 10 разів порівняно з наявним PostgreSQL / MySQL? Якщо різниця становить лише 20–30%, використовуйте наявну базу з оптимізацією індексів.
2. **Експертиза команди**: Чи вміють чергові інженери діагностувати аварії, оптимізувати пам'ять та налаштовувати реплікацію нової СУБД о 3-й годині ночі?
3. **Стратегія резервного копіювання**: Чи розроблено процедуру створення снепшотів та Disaster Recovery для нової бази?
4. **Моніторинг та алертинг**: Чи інтегровано метрики нової бази в загальний моніторинг (Prometheus, Datadog)?
5. **Механізм міграції схеми**: Чи підтримує нова СУБД версіонування схем та нульовий час простою (Zero-Downtime Migration)?
6. **Оцінка ліцензійної політики**: Перевірте тип ліцензії (SSPL, AGPL, BSL, Apache 2.0) на предмет юридичних обмежень для хмарного хостингу.
7. **Безпека та шифрування**: Перевірте наявність підтримки TLS 1.3, шифрування дисків у спокої (Encryption at Rest) та рольового доступу (RBAC).
8. **Екологія інструментів міграції**: Перевірте наявність зручних інструментів для автоматизованого виконання DDL-скриптів (Liquibase, Flyway) під обрану СУБД.
9. **Тестування навантаження (Load Testing)**: Чи перевірено поведінку нової СУБД при пікових навантаженнях за допомогою таких інструментів як k6 або Locust?
