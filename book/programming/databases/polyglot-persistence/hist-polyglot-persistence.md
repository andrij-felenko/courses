# 📜 Історія та еволюція концепції Polyglot Persistence

У 1990-х та на початку 2000-х років у корпоративній розробці панувала догма єдиної реляційної бази даних: усі підсистеми підприємства (бухгалтерія, склад, веб-сайт, аналітика) підключалися до одного централізованого кластера Oracle, IBM DB2 або Microsoft SQL Server. Вважалося, що будь-яка спеціалізована база даних створює зайву фрагментацію, вимагає додаткових ліцензій та збільшує операційні ризики компанії.

Розглянемо походження терміну Polyglot Persistence, внесок Ніла Форда та Мартіна Фаулера, розквіт мікросервісної архітектури, створення технологій Change Data Capture, вплив хмарних керованих сервісів та перехід індустрії до прагматичного комбінування сховищ.

### Від поліглотного програмування до поліглотного збереження

У 2006 році відомий архітектор **Ніл Форд (Neal Ford)** ввів термін **Polyglot Programming (Поліглотне програмування)**, стверджуючи, що сучасні складні додатки не повинні писатися однією універсальною мовою: математичні обчислення краще виконувати на R/Python, високонавантажене ядро — на C/C++ або Java, а користувацький інтерфейс — на JavaScript.

У 2011 році провідний архітектор ThoughtWorks **Мартін Фаулер (Martin Fowler)** разом із Прамодом Садалаге (Pramod Sadalage) екстраполювали цю ідею на рівень збереження даних, опублікувавши програмну статтю *«Polyglot Persistence»*.

Фаулер сформулював ключову тезу:
> «Різні типи даних мають принципово різну структуру та характер навантаження. Спроба запхати реляційні таблиці, графові зв'язки, кеші та неструктуровані документи в одну реляційну СУБД створює колосальний об'єктно-реляційний імпеданс і знижує продуктивність системи».

Фаулер та Садалаге у своїй книзі *«NoSQL Distilled»* (2012) детально описали, як комбінація реляційних баз, Key-Value сховищ, документоорієнтованих та графових СУБД дозволяє досягти небаченої раніше продуктивності для великих веб-порталів.

### Рушії популяризації: Мікросервіси та революція Apache Kafka

Широке впровадження поліглотного збереження стало можливим завдяки одночасному розвитку кількох взаємопов'язаних технологічних напрямків:

1. **Мікросервісна архітектура (Microservices)**:
   Принцип *Database-per-Service* закріпив правило: кожен мікросервіс повністю володіє своєю базою даних, а прямий доступ інших сервісів до таблиць суворо заборонено. Це дало командам розробки свободу вибору: сервіс авторизації обрав Redis для зберігання JWT-сесій, сервіс каталогу — MongoDB, сервіс рекомендацій — Neo4j, а платіжний шлюз — PostgreSQL.
2. **Розподілені шини подій (Apache Kafka, RabbitMQ)**:
   Поява надійних розподілених журналів повідомлень вирішила головну проблему поліглотного підходу — як підтримувати актуальність копій даних у різних сховищах без блокуючих двофазних транзакцій (2PC).
3. **Стандартизація технологій Change Data Capture (CDC)**:
   Створення відкритих фреймворків (Debezium, Kafka Connect) дозволило вичитувати бінарні логи транзакцій (WAL, Binlog) і прозоро реплікувати дані в пошукові системи та аналітичні сховища без внесення змін у код додатку.
4. **Хмарні керовані СУБД (Cloud Managed Databases)**:
   Поява сервісів AWS DynamoDB, Amazon OpenSearch, Google BigQuery та Cloud MemoryStore усунула необхідність самостійного розгортання кластерів, зробивши запуск спеціалізованих сховищ питанням кількох хвилин.
5. **Розвиток контейнеризації та Kubernetes**:
   Поява Docker та Kubernetes Operators спростила локальне тестування та автоматизоване оркестрування гетерогенних кластерів баз даних у тестових та виробничих середовищах.

### Сучасний синтез: Спеціалізовані бази проти мультимодельних СУБД

Сьогодні індустрія досягла зрілості у розумінні меж застосування поліглотного збереження. Ейфорія від підключення десятка різних NoSQL-баз змінилася тверезим розрахунком сукупної вартості володіння (TCO):

* Для критичних специфічних навантажень (повнотекстовий пошук у мільйонах документів, аналітика мільярдів подій у ClickHouse) виділені поліглотні сховища залишаються безальтернативним стандартом.
* Водночас сучасні реляційні СУБД (PostgreSQL із розширеннями `JSONB`, `pgvector`, `PostGIS`, `TimescaleDB`) перетворилися на потужні мультимодельні платформи, що дозволяє невеликим та середнім проектам уникати операційного оверхеду поліглотного стека на ранніх етапах розвитку.

Цей баланс формує сучасну культуру системного проєктування, де вибір сховища є зваженим компромісом між продуктивністю та простотою супроводу.
