# 🏛️ Еволюція міграцій баз даних: від ручних патчів до онлайн-DDL

Розвиток методологій міграції схем визначався боротьбою між потребою швидкого розгортання бізнес-фіч та фундаментальними обмеженнями надійного збереження даних: появою декларативного та імперативного підходів, революцію ActiveRecord у 2004 році, стандартизацією інструментів Liquibase та Flyway, а також появою безблокувальних онлайн-інструментів нового покоління від інженерів Flickr та GitHub.

---

### Епоха ручних SQL-патчів (1970–1990-ті)

У перші десятиліття розвитку реляційних баз даних поняття «міграції схеми» як версіонованого коду в репозиторії не існувало. Зміни таблиць вносилися безпосередньо адміністраторами баз даних (DBA) за допомогою інтерактивних терміналів або заздалегідь підготовлених текстових файлів `patch_v1.2.sql`.

Такий підхід супроводжувався численними критичними проблемами:
1. **Відсутність єдиного джерела правди**: Стан схеми на тестовому сервері (Staging) та у виробничому середовищі (Production) неминуче розходився через невраховані ручні виправлення (Schema Drift).
2. **Неможливість автоматичного відкату**: Помилка в середині масивного SQL-скрипта залишала таблиці в напівмодифікованому стані, що вимагало багатогодинного відновлення з резервних копій.
3. **Обов'язкове технічне вікно обслуговування (Maintenance Window)**: Будь-яке оновлення схеми вимагало повної зупинки вебсерверів або додатків у нічний час, оскільки команди `ALTER TABLE` блокували доступ до таблиць на тривалий період.

### Революція Ruby on Rails та ActiveRecord (2004)

Справжній тектонічний зсув у культурі розробки програмного забезпечення відбувся у 2004 році з релізом фреймворку Ruby on Rails, створеного Девідом Хейнемейєром Ханссоном (DHH).

ActiveRecord вперше запропонував концепцію **міграцій як версіонованого коду (Database Migrations as Code)**:
* Кожна зміна схеми оформлювалася як окремий файл із таймстемпом або порядковим номером (наприклад, `20080906120000_create_users.rb`).
* Стан бази даних відстежувався безпосередньо всередині самої СУБД у спеціальній системній таблиці `schema_migrations`.
* Міграції містили дві дзеркальні функції: `up` (застосування зміни) та `down` (скасування зміни).

```ruby
class AddStatusToOrders < ActiveRecord::Migration[5.0]
  def change
    add_column :orders, :status, :string, default: 'pending'
  end
end
```

Ця парадигма перетворила базу даних на повноцінного учасника системи контролю версій (Git), дозволивши розробникам розгортати зміни разом із кодом додатку за допомогою єдиної команди `rake db:migrate`.

### Стандартизація корпоративного рівня: Liquibase (2006) та Flyway (2010)

Зростання популярності мікросервісів та мов Java, Python і C# вимагало універсальних інструментів, незалежних від конкретного вебфреймворку:

* **Liquibase (2006)**, створений Натаном Воксом: Запропонував декларативний формат опису змін (ChangeSets) у XML, YAML та JSON. Liquibase автоматично генерував діалекти SQL під десятки різних СУБД (Oracle, DB2, PostgreSQL, MySQL) та підтримував контрольні суми для захисту від випадкової модифікації старих міграцій.
* **Flyway (2010)**, розроблений Акселем Фонтейном: Спирався на філософію простоти та використання чистого SQL. Замість складних XML-абстракцій розробники знову писали звичайні файли `V1__init.sql`, `V2__add_index.sql`, а Flyway гарантував їх суворе послідовне виконання та блокування через метатаблицю `flyway_schema_history`.

### Онлайн-перебудова таблиць: pt-online-schema-change та GitHub gh-ost (2016)

Зі зростанням масштабів інтернет-сервісів (Flickr, Facebook, GitHub) таблиці досягли сотень мільйонів рядків. Виконання навіть найпростішої операції `ALTER TABLE` у MySQL призводило до копіювання всієї таблиці та повного блокування запису на кілька годин.

У 2008 році Шахар Евані (Shlomi Noach) та інженери компанії Percona представили інструмент `pt-online-schema-change` (на базі ідей `oak-online-alter` від OpenArk):
1. Створюється порожня тіньова таблиця з новою схемою `_users_new`.
2. На оригінальну таблицю вішаються тригери на `INSERT`, `UPDATE`, `DELETE`, які синхронізують зміни в реальному часі.
3. Фоновий процес порціями (Chunking) копіює старі дані.
4. Після завершення копіювання таблиці атомарно перейменовуються.

Проте тригери створювали велике додаткове навантаження на процесор та викликали блокування метаданих.

У 2016 році Шломі Ноах, працюючи в команді GitHub, створив **`gh-ost` (GitHub Online Schema Transformations)**. Новий інструмент повністю відмовився від використання тригерів, перейшовши на пряме читання бінарного журналу реплікації (Binlog Stream) MySQL як клієнт-репліка. Це дозволило проводити міграції на таблицях розміром у терабайти з можливістю динамічного призупинення (Throttling) за навантаженням або затримкою реплікації.

### Хронологічна таблиця еволюції підходів

| Період | Домінуючий інструмент / Концепція | Ключова інновація | Головне обмеження |
| :--- | :--- | :--- | :--- |
| **1980–1990-ті** | Ручні SQL-скрипти DBA | Прямий контроль над СУБД | Людський фактор, Schema Drift, Downtime |
| **2004** | Rails ActiveRecord Migrations | Міграції як код, таблиця `schema_migrations` | Прив'язка до стеку Ruby, наївні блокування DDL |
| **2006–2010** | Liquibase, Flyway | Контрольні суми, декларативність, підтримка CI/CD | Небезпека блокування живих таблиць у продакшені |
| **2012** | Percona `pt-online-schema-change` | Тригерне онлайн-копіювання таблиць | Накладні витрати CPU, блокування на тригерах |
| **2016** | GitHub `gh-ost` | Онлайн-міграції через Binlog CDC без тригерів | Специфічність під MySQL |
| **Сучасність** | Декларативні мігратори (Atlas, Prisma, Bytebase) | Спектральний аналіз diff схеми, авто-лінтинг блокувань | Складність інтеграції в розподілені кластери |
