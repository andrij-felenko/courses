# 📜 Історія Snowflake: як Twitter відмовився від MySQL Auto-Increment у пошуках 64-бітної шкали часу

Влітку 2010 року під час Чемпіонату світу з футболу в ПАР інфраструктура Twitter опинилася на межі колапсу. Коли збірна Японії забила переможний гол у матчі проти Камеруну, потік твітів сягнув безпрецедентних на той час 3 283 повідомлень на секунду. Користувачі щохвилини спостерігали «Fail Whale» — знамениту заглушку з китом, якого підіймають птахи, що свідчила про падіння внутрішніх сервісів. Головною точкою відмови виявилася не мережа чи кеш, а монолітна база даних MySQL, яка задихалася від боротьби за блокування на єдиному лічильнику ідентифікаторів.

### Вузьке місце тикет-серверів Flickr

До 2010 року Twitter використовував підхід, запозичений у фотохостингу Flickr — виділені централізовані бази даних, які виконували виключно роль «тикет-серверів» (Ticket Servers). Схема спиралася на атомарний механізм MySQL:

```sql
REPLACE INTO Tickets64 (stub) VALUES ('a');
SELECT LAST_INSERT_ID();
```

Таблиця містила один-єдиний стовпчик і постійно перезаписувала один рядок, видаючи монотонно зростаючий 64-бітний `AUTO_INCREMENT`. Щоб усунути єдину точку відмови (Single Point of Failure), інженери запускали два незалежні сервери MySQL: один генерував лише непарні числа (`auto_increment_increment=2`, `auto_increment_offset=1`), а другий — лише парні (`auto_increment_offset=2`).

Ця схема вичерпала себе з трьох непереборних причин:
1. **Мережева затримка (Round-trip Overhead)**: Створення кожного твіта вимагало блокуючого мережевого запиту до тикет-сервера перед тим, як дані взагалі потрапляли в чергу на запис.
2. **Неможливість масштабування за межі двох машин**: Додавання третього чи четвертого сервера вимагало глобальної зміни конфігурації кроку зміщення та зупинки кластера, інакше виникали колізії ID.
3. **Міграція на Cassandra**: Команда Twitter під керівництвом Раяна Кінга (Ryan King) почала масштабний перехід від монолітного MySQL до розподіленого сховища Apache Cassandra. У децентралізованій Cassandra не було центрального координатора, який міг би атомарно роздавати інкременти.

### Чому випадковий UUIDv4 не підійшов

Першим очевидним кандидатом на роль розподіленого ідентифікатора був 128-бітний випадковий UUIDv4. Він вирішував проблему децентралізації: будь-який сервер додатків міг згенерувати ID локально без звернення до координатора з мізерною ймовірністю колізії.

Проте інженери Twitter швидко відкинули UUIDv4 через несумісність із фундаментальними бізнес-вимогами платформи:

* **Розмір та пам'ять**: 128-бітний UUID займає 16 байтів замість 8 байтів для 64-бітного цілого числа. У масштабах мільярдів твітів і зв'язків підписників подвоєння розміру первинних і вторинних індексів призводило до катастрофічного роздування оперативної пам'яті (RAM) та вимивання дискового кешу.
* **Втрата часової локальності (Rough Time Ordering)**: Стрічка новин (Timeline) формується в хронологічному порядку. Клієнти запитують сторінки твітів за допомогою пагінації «покажи повідомлення після ID=X». Випадковий UUID не містить інформації про час, змушуючи базу будувати окремий композитний вторинний індекс `(created_at, id)`.
* **Фрагментація дискового сховища**: Випадкові ключі при вставці в B-Tree індекси та LSM-дерева спричиняли лавинне розщеплення сторінок (Page Splits), фрагментацію пам'яті та багатократне зростання коефіцієнта підсилення запису (Write Amplification).

### Народження концепції Snowflake

Восени 2010 року команда платформи Twitter представила відкритий сервіс під назвою **Snowflake** (сніжинка — метафора унікальності кожного згенерованого об'єкта в природі).

Замість важкої міжсерверної координації інженери упакували час, топологію кластера та локальний лічильник у єдине 64-бітне ціле число:

1. **1 біт** — знаковий біт (завжди 0), щоб уникнути проблем із від'ємними числами у мовах програмування без беззнакових типів (наприклад, Java та Scala, на якій було написано сервіс).
2. **41 біт** — часова мітка в мілісекундах від спеціально обраної власної епохи Twitter (Custom Epoch: 4 листопада 2010 року, `1288834974657` мс). 41 біт надавав запас автономної роботи на 69.7 року (до 2080 року).
3. **10 бітів** — ідентифікатор машини/процесу (5 бітів на Datacenter ID + 5 бітів на Worker ID), що дозволяло утримувати до 1024 незалежних генераторів.
4. **12 бітів** — локальний монотонний лічильник у межах поточної мілісекунди. Він дозволяв кожному воркеру видавати до `4096` унікальних ID щомілісекунди (понад 4 мільйони операцій на секунду на одну ноду).

Сервіс запускався як незалежний демон на базі протоколу Apache Thrift. Генерація відбувалася виключно в оперативній пам'яті процесу за бітовими зсувами, що скоротило час генерації ID з десятків мілісекунд дискового SQL до субмікросекундних показників.

### Пастка 53 бітів у JavaScript

Після запуску Snowflake виникла неочікувана інженерна проблема на стороні вебклієнтів. Стандарт ECMAScript визначає тип `Number` як 64-бітне число з плаваючою комою подвійної точності за стандартом IEEE 754. Це означає, що точне представлення цілих чисел обмежене 53 бітами:

```
Number.MAX_SAFE_INTEGER = 2⁵³ - 1 = 9 007 199 254 740 991
```

Коли 64-бітний Snowflake ID перевищив це значення (що стається, коли значення часового зсуву заповнює старші біти), браузери почали спотворювати молодші біти ідентифікаторів при парсингу JSON: ID `1050118621198921728` перетворювався на `1050118621198921700`. Кліки на твіти відкривали хибні або неіснуючі сторінки.

Twitter був змушений терміново змінити формат публічного REST API, додавши поряд із числовим полем `id` текстовий дублікат `id_str` (строкове представлення). Це правило стало стандартом індустрії для всіх розподілених систем, що використовують 64-бітні ідентифікатори.

### Спадщина та еволюція

Успіх Snowflake спричинив появу цілого сімейства похідних алгоритмів:
* **Sonyflake (Sony)**: перерозподілив біти на користь більшої кількості машин (16 бітів під Worker ID) та довшого життєвого циклу (174 роки) коштом дискретизації часу в 10 мс.
* **Instagram ID**: реалізував ту саму концепцію безпосередньо всередині збережених процедур PostgreSQL через PL/pgSQL, прив'язавши Machine ID до номера логічного шарду бази.
* **ULID та UUIDv7**: масштабували ідею сортування за часом у 128-бітний простір, об'єднавши переваги 48-бітної мілісекундної шкали та криптографічної ентропії, що повністю усунуло потребу в координації воркерів через централізований конфігуратор.
