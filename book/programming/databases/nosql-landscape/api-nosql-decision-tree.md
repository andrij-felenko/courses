# 📋 Практичний довідник архітектора: Дерево рішень щодо вибору NoSQL СУБД

Сучасний ринок баз даних налічує сотні спеціалізованих рішень. Неправильний вибір моделі даних на етапі проєктування системи призводить до колосальних інженерних витрат на емуляцію відсутньої функціональності у прикладному коді або до повної перебудови архітектури під час зростання навантаження.

Цей довідник містить практичне дерево ухвалення рішень (Decision Tree), матрицю порівняння характеристик провідних СУБД, аналіз типів навантажень за категоріями, матрицю розрахунку вартості володіння (TCO), розбір типових помилок міграції та контрольний чекліст оцінки вимог проекту.

### Порівняльна матриця провідних NoSQL та NewSQL систем

| Категорія | СУБД | Модель даних | Первинний сценарій використання | Переваги | Обмеження |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Key-Value** | **Redis** | In-Memory Key-Value | Кешування, сесії, лічильники, черги | Субмілісекундна затримка (<1 мс), багаті структури | Обмеження обсягом оперативної пам'яті |
| **Key-Value** | **AWS DynamoDB** | Керований Key-Value / Doc | Serverless веб-додатки, e-commerce | Автоматичне масштабування, фіксований SLA | Складність запитів поза Partition Key |
| **Document** | **MongoDB** | BSON Документи | Каталоги товарів, CMS, профілі користувачів | Гнучка схема, багаті вторинні індекси, агрегації | Більший розмір на диску через дублювання ключів |
| **Wide-Column** | **Apache Cassandra** | Wide-Column (LSM-Tree) | Телеметрія, IoT, фінансові транзакції, логи | Необмежене лінійне масштабування на запис, AP | Відсутність `JOIN`, запити суворо за Primary Key |
| **Graph** | **Neo4j** | Labeled Property Graph | Соціальні графи, антифрод, рекомендації | Обхід зв'язків за O(1) без табличних `JOIN` | Складність горизонтального шардування графа |
| **Search Engine** | **Elasticsearch** | Інвертований індекс | Повнотекстовий пошук, аналіз логів (ELK) | Складний морфологічний та нечіткий пошук | Високі накладні витрати пам'яті, не є primary DB |
| **NewSQL** | **CockroachDB** | Distributed Relational | Глобальні фінансові системи, мультиядерний SQL | Повний SQL, горизонтальне шардування, serializable ACID | Вища затримка запису через консенсус Raft |
| **Vector DB** | **Milvus / Qdrant** | HNSW Векторний граф | Семантичний пошук, RAG для LLM | Пошук найближчих сусідів (ANN) за косинусною відстанню | Вимагає попереднього обчислення ембедінгів |

### Детальні профілі сценаріїв використання за моделями даних

#### 1. Key-Value сховища (Redis, KeyDB, Dragonfly)
* **Головні механізми**: Зберігання в оперативній пам'яті (RAM), однопотоковий або lock-free мультиплексований цикл подій (Event Loop), підтримка структур даних (Lists, Sets, Sorted Sets, HyperLogLog, Streams).
* **Сценарії застосування**:
  - Розподілені блокування через алгоритм Redlock.
  - Обмеження частоти запитів (Rate Limiting) за допомогою ковзного вікна (Sliding Window).
  - Швидка публікація/підписка на повідомлення (Pub/Sub) та кешування результатів важких SQL-запитів із політикою витіснення LRU/LFU.

#### 2. Document сховища (MongoDB, Couchbase)
* **Головні механізми**: Формат BSON з типізованими полями, вбудований рушій WiredTiger з підтримкою кешування сторінок, розгалужені конвеєри агрегацій (Aggregation Pipelines), вторинні та складені індекси, шардування на основі діапазонів (Range Sharding) або хешів (Hashed Sharding).
* **Сценарії застосування**:
  - Каталоги товарів інтернет-магазинів із динамічними характеристиками (розмір, колір, технічні специфікації).
  - Зберігання користувацьких налаштувань та конфігурацій додатків у форматі вкладених об'єктів.

#### 3. Wide-Column сховища (Apache Cassandra, ScyllaDB)
* **Головні механізми**: Peer-to-peer архітектура без єдиної точки відмови (Masterless), кільцеве узгоджене хешування (Consistent Hash Ring), рушій LSM-Tree з незмінними SSTables, мова запитів CQL (Cassandra Query Language).
* **Сценарії застосування**:
  - Збір високочастотних метрик та телеметрії (мільйони подій на секунду від IoT-датчиків).
  - Історія чатів і миттєвих повідомлень у месенджерах із пагінацією за Clustering Key (часовою міткою).

#### 4. Graph бази даних (Neo4j, Amazon Neptune)
* **Головні механізми**: Пряме збереження вказівників на суміжні вершини (Index-free Adjacency), декларативна мова графових шаблонів Cypher / Gremlin, алгоритми пошуку найкоротшого шляху (Dijkstra, A*), обчислення центральності та кластеризації (PageRank, Louvain).
* **Сценарії застосування**:
  - Виявлення фінансових кілець шахрайства (Fraud Rings) та аналіз ланцюжків транзакцій у реальному часі.
  - Побудова рекомендаційних систем на основі спільного кола інтересів та друзів.

### Матриця сукупної вартості володіння (Total Cost of Ownership, TCO)

При розрахунку вартості експлуатації бази даних враховують не лише ціну серверів, але й витрати інженерного часу:

| Фактор витрат | Self-Hosted RDBMS (PostgreSQL) | Managed Cloud NoSQL (DynamoDB / Cosmos) | Self-Hosted NoSQL Cluster (Cassandra) |
| :--- | :--- | :--- | :--- |
| **Витрати на інфраструктуру** | Низькі (один-два потужні інстанси) | Змінні (Pay-per-request / Provisioned RCU/WCU) | Високі (мінімум 6-9 вузлів для кворумів) |
| **Складність супроводу** | Середня (авто-бекграунд вакуум, WAL) | Мінімальна (повністю автоматизовано провайдером)| Екстремальна (ручне налаштування GC, compaction) |
| **Ризик перевитрат (Spike Cost)**| Нульовий (фіксована оренда сервера) | Високий під час раптових DDoS-атак або сплесків | Низький (потребує попереднього планування ємності)|

### Типові інженерні антипатерни та помилки міграції

1. **Емуляція реляційних `JOIN` на рівні додатку**: Спроба використовувати MongoDB або Cassandra як звичайну реляційну базу, з вибіркою сотень ID у першому запиті та подальшим обходом у циклі. Це породжує проблему N+1 у масштабі розподіленої системи.
2. **Зловживання unbounded масивами в документах**: Збереження нескінченно зростаючих масивів (наприклад, усіх коментарів або логів активності користувача) всередині одного BSON документа. Це призводить до перевищення ліміту розміру документа (16MB у MongoDB) та постійної фрагментації пам'яті.
3. **Вибір Cassandra для випадкових вибірок без Clustering Key**: Спроба виконати `SELECT * FROM table WHERE non_key_column = 'val' ALLOW FILTERING;` змушує всі вузли кластера сканувати власні диски, що спричиняє повну деградацію продуктивності.
4. **Ігнорування гарячих ключів (Hot Partition Keys)**: Неправильно обраний ключ шардування (наприклад, `country_code = 'UA'`) спрямовує 90% трафіку на один єдиний сервер кластера, перетворюючи інші вузли на марний баласт.
5. **Спроба збереження часових рядів у неіндексованих реляційних таблицях**: Запис мільярдів логів у PostgreSQL без партиціонування таблиць (`pg_partman` або TimescaleDB) спричиняє деградацію B-Tree індексів та вичерпання пулу підключень.

### Практичний чекліст оцінки вимог проєкту

Перед вибором конкретної СУБД надайте відповіді на такі критичні інженерні запитання:

#### 1. Обсяг даних та швидкість зростання
* Чи перевищить обсяг бази 1–2 ТБ у найближчі 2 роки? Якщо ні — класичний **PostgreSQL** закриє 99% потреб бізнесу без ускладнення розподіленими системами.
* Яка інтенсивність операцій запису (Writes/sec)? Для понад 100 000 записів/сек рекомендуються LSM-базовані системи (**ScyllaDB**, **Cassandra**).

#### 2. Модель запитів (Query Patterns)
* Чи відомі всі варіанти вибірки даних наперед? Wide-column бази вимагають проєктування таблиць суворо під конкретний `SELECT` (Access-Pattern-First).
* Чи потрібні довільні аналітичні вибірки за будь-якими полями? Якщо так — обирайте реляційні СУБД або **Elasticsearch** як вторинний індекс.

#### 3. Вимоги до узгодженості (Consistency SLA)
* Що важливіше під час аварійного розділення дата-центрів: доступність (AP) чи абсолютна строгість (CP)?
* Чи допустимо, щоб користувач бачив застарілий баланс протягом 100–500 мс після операції? Якщо ні — потрібна строга лінеаризовність (CP/NewSQL).

#### 4. Операційні витрати (Operational Complexity)
* Чи готова команда підтримувати власний розподілений кластер (управління ZooKeeper, Compaction, Tombstones, Repair)?
* За браку експертизи з розподілених систем віддавайте перевагу керованим хмарним рішенням (Managed Cloud / Serverless).
* Чи забезпечено автоматичне резервне копіювання знімків (Point-in-time Recovery) та відновлення у разі виходу з ладу цілих зон доступності?
