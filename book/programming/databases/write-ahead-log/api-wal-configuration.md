# 📋 Довідник конфігурації та моніторингу WAL і Redo Log

Журнал попереднього запису (Write-Ahead Log, WAL) є фундаментом довговічності (Durability) транзакцій та надійності реплікації в реляційних базах даних. Некоректно підібрані розміри сегментів журналу, зависока частота контрольних точок або неоптимальний режим дискової синхронізації `fsync()` створюють пікові сплески латентності запитів (Checkpoint Spikes) та значно знижують пропускну здатність дискової підсистеми I/O.

Цей довідник містить детальний опис системних параметрів конфігурації підсистеми WAL у PostgreSQL та журналу Redo Log у MySQL InnoDB, включаючи повний перелік системних функцій керування, діагностичні каталоги, метрики продуктивності та готові запити для виробничого моніторингу.

---

### Архітектура фонових процесів скидання WAL у PostgreSQL

У PostgreSQL процес запису та синхронізації журналу розподілений між кількома спеціалізованими фоновими демонами:

1. **Серверні бекенди (PostgreSQL Backends)**: Коли користувацький потік генерує транзакцію, він записує дельти у виділений кільцевий буфер оперативної пам'яті `wal_buffers`. Якщо виконується `COMMIT` під режимом `synchronous_commit = on`, бекенд самостійно ініціює виклик `fsync()` для синхронізації сегмента на диск, або очікує завершення групового коміту.
2. **Фоновий записувач WAL (WalWriter)**: Періодично пробуджується (з інтервалом `wal_writer_delay`) та скидає накопичені в пам'яті незафіксовані буфери на дисковий накопичувач. Це суттєво зменшує затримку наступних транзакційних фіксацій.
3. **Процес контрольних точок (Checkpointer)**: Відповідає за планове скидання брудних сторінок із Buffer Pool на диск. Процес розраховує графік скидання на основі параметрів `checkpoint_timeout` та `checkpoint_completion_target`.
4. **Процес архівації (Archiver)**: Копіює заповнені 16-мегабайтні сегменти WAL у зовнішнє сховище резервних копій (наприклад, S3 або NFS) за допомогою системної команди `archive_command`.
5. **Процеси відправки та прийому реплікації (WalSender та WalReceiver)**: Організовують фізичну потокову передачу бінарних записів LSN по TCP-з'єднанню до вузлів Standby.

### Конфігураційні параметри WAL у postgresql.conf

У PostgreSQL параметри журналу керують обсягом виділеної оперативної пам'яті під буфери, частотою створення контрольних точок та глибиною деталізації для потокової реплікації.

#### Повний перелік системних параметрів

| Назва параметра | Тип даних | Дефолт | Рекомендація для OLTP | Призначення та архітектурний вплив |
| :--- | :--- | :--- | :--- | :--- |
| `wal_level` | enum | `replica` | `replica` | Рівень деталізації журналу (`minimal`, `replica`, `logical`). Режим `replica` записує дані, достатні для відновлення після збоїв та підтримки фізичних Standby реплік. |
| `wal_buffers` | size | `-1` (1/32 shared_buffers) | `64MB - 128MB` | Обсяг оперативної пам'яті під кільцевий буфер записів WAL до їх скидання на диск. Запобігає очікуванню вільного місця в пам'яті при масивних транзакціях. |
| `max_wal_size` | size | `1GB` | `16GB - 64GB` | Максимальний сумарний розмір сегментів журналу між автоматичними контрольними точками. Збільшення зменшує частоту чекпойнтів та згладжує дискове навантаження. |
| `min_wal_size` | size | `80MB` | `2GB - 8GB` | Мінімальний резерв місця під сегменти WAL, які не вилучаються, а перейменовуються та використовуються повторно. Усуває накладні витрати файлової системи на виділення нових блоків. |
| `checkpoint_timeout` | time | `5min` | `15min - 30min` | Максимальний інтервал між плановими контрольними точками. Довші інтервали зменшують зношування SSD, але подовжують час відновлення після аварії. |
| `checkpoint_completion_target` | float | `0.9` | `0.9` | Частка інтервалу чекпойнта, протягом якої процес `checkpointer` плавно розмазує скидання брудних сторінок на диск, усуваючи лавиноподібні сплески запису. |
| `checkpoint_warning` | time | `30s` | `1min` | Виводить попередження в системний журнал, якщо чекпойнти через заповнення WAL відбуваються частіше за вказаний інтервал. Сигналізує про необхідність збільшення `max_wal_size`. |
| `synchronous_commit` | enum | `on` | `on` (або `off` для некритичних черг) | Режим очікування фізичного скидання журналу через `fsync()` перед поверненням успішної відповіді клієнту. Значення `off` збільшує продуктивність у 5-10 разів ціною ризику втрати кількох останніх мілісекунд даних при збої. |
| `wal_writer_delay` | time | `200ms` | `20ms - 50ms` | Періодичність пробудження фонового процесу `walwriter` для асинхронного скидання накопичених буферів. Менше значення знижує затримки навантажених OLTP вузлів. |
| `wal_writer_flush_after` | size | `1MB` | `1MB` | Обсяг накопичених даних, після якого `walwriter` викликає примусовий запис на диск. |
| `full_page_writes` | bool | `on` | `on` | Примусовий запис повної сторінки розміром 8 КБ у WAL після першої модифікації після чекпойнта. Захищає від пошкодження сторінок при частковому записі (Torn Pages). |
| `wal_compression` | enum | `off` | `lz4` або `zstd` | Стиснення повносторінкових знімків у WAL. Дозволяє зменшити дисковий трафік на 40–70% за мінімальних витрат CPU. |
| `wal_keep_size` | size | `0` | `4GB - 16GB` | Мінімальний обсяг сегментів журналу, який обов'язково утримується в `pg_wal` для повільних фізичних реплік без слотів. |
| `wal_sync_method` | enum | `fdatasync` | `fdatasync` (Linux) / `open_datasync` | Системний виклик, який використовується для примусового скидання кешів диска на фізичний носій. |

### Налаштування синхронної реплікації: synchronous_standby_names

Для побудови високонадійних катастрофостійких кластерів PostgreSQL підтримує синхронну реплікацію WAL:

```ini
# Очікування підтвердження запису у WAL від перших 2 доступних вузлів
synchronous_standby_names = 'FIRST 2 (node1, node2, node3)'

# Кворумний режим: очікування будь-яких 2 із 3 Standby серверів
synchronous_standby_names = 'ANY 2 (node1, node2, node3)'
```

У поєднанні з `synchronous_commit = remote_apply` ведучий сервер віддає клієнту відповідь про успішний `COMMIT` лише після того, як транзакція була фізично накладена на сторінки пам'яті на віддалених репліках. Якщо ж використовується `synchronous_commit = remote_write`, сервер очікує лише запису дельт в операційну систему репліки без виклику `fsync()`.

### Налаштування архівації та резервного копіювання Point-In-Time Recovery (PITR)

Безперервна архівація сегментів журналу дозволяє відновити стан кластера на будь-яку точну секунду в минулому (Point-In-Time Recovery, PITR).

Для налаштування процесу архівації використовуються такі ключові директиви:

```ini
# Активація режиму архівації
archive_mode = on

# Команда копіювання заповненого 16-мегабайтного сегмента (виклик оболонки)
archive_command = 'test ! -f /mnt/nfs_backup/%f && cp %p /mnt/nfs_backup/%f'

# Максимальний час утримання незаповненого сегмента (примусове перемикання)
archive_timeout = 600s
```

Де змінні `%p` та `%f` автоматично підставляються рушієм:
* `%p` — повний відносний шлях до файлу сегмента у каталозі `pg_wal` (наприклад, `pg_wal/00000001000000A10000003F`);
* `%f` — лише базове ім'я файлу сегмента.

Для відновлення на репліці або новому вузлі створюється файл `standby.signal` або `recovery.signal` із директивою `restore_command`:

```ini
restore_command = 'cp /mnt/nfs_backup/%f %p'
recovery_target_time = '2026-08-20 14:30:00 UTC'
recovery_target_action = 'promote'
```

### Відновлення розгалужених історій за допомогою утиліти pg_rewind

Коли в кластері з реплікацією трапляється аварійне перемикання на Standby вузол (Failover), старий Master сервер може мати кілька непереданих на репліку транзакцій. Це призводить до розбіжності часових ліній (Timeline Divergence / Split-Brain).

Утиліта `pg_rewind` дозволяє повернути старий Master до точки розгалуження без необхідності повного копіювання сотень гігабайт бази даних з нового вузла:

```bash
# Синхронізація старого майстра з новим лідером
pg_rewind --target-pgdata=/var/lib/postgresql/data \
          --source-server='host=new_master user=postgres dbname=postgres' \
          --progress
```

`pg_rewind` читає журнал WAL на старому майстрі у зворотному напрямку від точки розгалуження, знаходить усі змінені сторінки даних, копіює лише ці конкретні блоки з нового майстра і переписує часову лінію, дозволяючи знову запустити вузол як звичайний Standby.

### Консольні утиліти для аналізу WAL: pg_waldump

PostgreSQL постачається зі спеціалізованою утилітою командного рядка `pg_waldump` для низькорівневої інспекції записів журналу:

```bash
# Перегляд записів у вказаному діапазоні LSN
pg_waldump -p /var/lib/postgresql/data/pg_wal -s 0/16B3740 -e 0/16B9000

# Збір агрегованої статистики за типами операцій (Resource Managers)
pg_waldump -p /var/lib/postgresql/data/pg_wal --stats 000000010000000000000001
```

Утиліта дозволяє точно розрахувати, які таблиці генерують найбільший обсяг журнальних дельт, скільки повносторінкових знімків (Full Page Images) було записано, та виявити неефективні масивні операції `UPDATE`.

### Системні SQL-функції керування WAL у PostgreSQL

PostgreSQL надає набір вбудованих функцій для адміністративного контролю за журналом транзакцій та моніторингу стану реплікаційного потоку:

```sql
-- Примусове перемикання на новий 16-мегабайтний сегмент WAL
SELECT pg_switch_wal();

-- Примусовий запуск неблокуючої контрольної точки
CHECKPOINT;

-- Отримання поточної позиції запису у журналі
SELECT pg_current_wal_lsn();

-- Отримання поточної позиції, гарантовано скинутої на диск
SELECT pg_current_wal_flush_lsn();

-- Розрахунок різниці в байтах між двома позиціями LSN (наприклад, затримка реплікації)
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), '0/16B3740'::pg_lsn);
```

### Конфігурація Redo Log у MySQL InnoDB

У рушії MySQL InnoDB журнал змін зберігається у виділених файлах `ib_logfile0`, `ib_logfile1` (або в динамічних сегментах `#innodb_redo` починаючи з MySQL 8.0.30).

#### Режими синхронізації innodb_flush_log_at_trx_commit

Головним важелем надійності та продуктивності в InnoDB є змінна `innodb_flush_log_at_trx_commit`:

| Значення | Поведінка під час COMMIT | Гарантія надійності (Durability) | Продуктивність |
| :--- | :--- | :--- | :--- |
| `1` (Дефолт) | Лог записується в кеш ОС і синхронізується на диск викликом `fsync()` при кожній фіксації. | 100% ACID гарантія. Втрата даних неможлива навіть при раптовому вимкненні живлення сервера. | Обмежена кількістю дискових операцій запису (IOPS). |
| `0` | Лог буферизується в пам'яті InnoDB і скидається на диск фоновим потоком раз на 1 секунду. | При аварії СУБД або ОС втрачаються останні транзакції за 1 секунду. | Максимальна швидкість виконання транзакцій. |
| `2` | Лог записується в буфер ОС при кожному `COMMIT`, а `fsync()` викликається раз на 1 секунду. | Дані витримують падіння процесу `mysqld`, але втрачаються при краху операційної системи за останню секунду. | Дуже висока швидкість запису. |

#### Додаткові параметри InnoDB Redo

* `innodb_redo_log_capacity`: Загальний дисковий простір під файли Redo Log у MySQL 8.0.30+ (рекомендовано від 8 ГБ до 32 ГБ).
* `innodb_log_buffer_size`: Обсяг оперативної пам'яті під буфер Redo (рекомендовано від 64 МБ до 256 МБ для великих транзакцій).
* `innodb_log_write_ahead_size`: Розмір блоку випереджального запису для вирівнювання з фізичними секторами накопичувача (512B, 4KB).

### Діагностичні SQL-запити для моніторингу WAL

#### 1. Моніторинг генерації обсягу WAL та частоти контрольних точок у PostgreSQL

```sql
SELECT 
    checkpoints_timed AS scheduled_checkpoints,
    checkpoints_req AS requested_checkpoints,
    checkpoint_write_time AS total_write_ms,
    checkpoint_sync_time AS total_sync_ms,
    buffers_checkpoint,
    buffers_clean,
    buffers_backend
FROM pg_stat_bgwriter;
```

*Примітка:* Якщо кількість запитаних контрольних точок (`checkpoints_req`) значно перевищує кількість запланованих за часом (`checkpoints_timed`), це означає, що параметр `max_wal_size` є заниженим і потребує збільшення.

#### 2. Моніторинг слотів фізичної та логічної реплікації

```sql
SELECT 
    slot_name,
    plugin,
    slot_type,
    active,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal_bytes
FROM pg_replication_slots;
```

#### 3. Моніторинг стану журналу Redo Log у MySQL

```sql
SHOW STATUS LIKE 'Innodb_os_log_%';
-- Аналізуйте співвідношення між Innodb_os_log_written та Innodb_os_log_fsyncs
```
