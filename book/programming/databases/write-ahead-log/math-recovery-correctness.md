# 📐 Математична формалізація протоколу ARIES та доказ коректності

Протокол відновлення після відмов ARIES спирається на суворі математичні інваріанти монотонно зростаючого простору номерів послідовності журналу (Log Sequence Numbers, LSN) та властивість алгебраїчної напівідемпотентності фази Redo.

Транзакційне відновлення спирається на три взаємопов'язані математичні сутності: монотонний часовий простір журналу, інваріант випереджального запису та рекурентний оператор зворотного скасування. Усі переходи станів моделюються через детерміновані скінченні автомати та алгебру напівгруп над простором дискових сторінок.

---

### Формальна модель транзакційного простору

Розглянемо дискретну модель стану бази даних:

1. **Послідовність журналу**: Потік записів `L = <r_1, r_2, ..., r_n>` є строго впорядкованим ланцюжком елементів, де кожен елемент має унікальний номер `LSN(r_i)`. Для номерів діє відношення строгого лінійного монотонного порядку: для будь-якого індексу `i` виконується `LSN(r_i) < LSN(r_{i+1})`.
2. **Простір сторінок пам'яті**: Множина сторінок `P = {p_1, p_2, ..., p_m}` представляє фізичні блоки фіксованого розміру (зазвичай 8 КБ). Кожна сторінка `p` містить системний заголовок із полем `PageLSN(p)`, що позначає найновіший номер операції, зміни від якої були фізично накладені на цей блок.
3. **Межа дискової синхронізації**: Змінна `FlushedLSN` фіксує максимальну точку монотонного журналу, яка була гарантовано та синхронно скинута в енергонезалежну пам'ять накопичувача за допомогою виклику системної інструкції `fsync()`.

---

### Фундаментальний інваріант WAL (Write-Ahead Logging Invariant)

Для будь-якої сторінки `p` із множини `P`, яка вивантажується на дисковий накопичувач або модифікується в буферному пулі, система підтримує непорушний логічний інваріант:

```text
Для кожної сторінки p у пам'яті та на диску: PageLSN(p) <= FlushedLSN
```

**Інженерне значення інваріанту:** Жодна модифікована (брудна) сторінка даних не може бути виштовхнута з оперативної пам'яті на дисковий накопичувач раніше, ніж відповідний запис журналу змін (разом з усіма попередніми записами) буде зафіксовано на енергонезалежному носії.

Якщо цей інваріант порушується, і непідтверджена зміна потрапляє на диск до запису у WAL, аварійний збій живлення зробить неможливим відновлення попереднього стану, оскільки журнал не міститиме інформації про старі байти (Undo-інформації) для відкату.

---

### Алгебраїчна ідемпотентність оператора Redo

Нехай `S` — фізичний стан сторінки пам'яті, а `Apply(r, S)` — функція застосування дельт із запису журналу `r` до стану `S`.

Оператор оновлення сторінки під час фази Redo формально визначається кусочно-заданою функцією:

```text
ApplyRedo(r, p) = Apply(r, p), якщо LSN(r) > PageLSN(p)
ApplyRedo(r, p) = p,           якщо LSN(r) <= PageLSN(p) (пропуск операції)
```

#### Теорема про ідемпотентність повторення історії

Для будь-якого запису `r` та будь-якої сторінки `p`, багаторазове повторне виконання фази Redo над довільним станом сторінки призводить до тотожного стабільного стану:

```text
ApplyRedo(r, ApplyRedo(r, p)) = ApplyRedo(r, p)
```

**Доведення:**
1. Нехай початковий стан сторінки має `PageLSN(p) < LSN(r)`.
2. Перший виклик `ApplyRedo(r, p)` виконує перетворення `Apply(r, p)`, яке оновлює дані кортежів та обов'язково встановлює нове значення `PageLSN(p') = LSN(r)`.
3. При наступному виклику `ApplyRedo(r, p')` обчислюється предикат `LSN(r) > PageLSN(p')`.
4. Оскільки `LSN(r)` дорівнює `PageLSN(p')`, предикат набуває значення хибності (`false`), і спрацьовує правило пропуску: функція повертає сторінку `p'` без додаткових модифікацій.
5. Отже, оператор `ApplyRedo` утворює напівгруповий ідемпотентний проектор на просторі станів сторінок, що гарантує абсолютну безпеку довільної кількості аварійних перезапусків під час відновлення.

---

### Теорема про збіжність фази Undo з використанням CLR

Під час відкату дій транзакції формується зворотний граф операцій. Кожна дія скасування супроводжується записом компенсаційного журналу `CLR`, який фіксує покажчик переходу:

```text
UndoNextLSN(CLR) = PrevLSN(r_undone)
```

#### Теорема про детерміновану скінченність відновлення

Кількість кроків фази Undo монотонно спадає до 0 за скінченний час навіть за умови повторних збоїв живлення.

**Доведення:**
1. Нехай множина активних незафіксованих транзакцій на момент завершення фази Analysis містить записи з номерами `ActiveLSN`.
2. Кожна операція створення `CLR` переміщує покажчик `UndoNextLSN` строго ліворуч за шкалою послідовності: `UndoNextLSN < LSN(r_undone)`.
3. Оскільки множина номерів LSN є строго спадним дискретним ланцюжком цілих чисел, обмеженим знизу початком журналу (`LSN = 0`), ланцюжок переходів утворює строго спадну послідовність:
   ```text
   LSN_1 > LSN_2 > LSN_3 > ... > LSN_k = 0
   ```
4. При падінні живлення під час виконання фази Undo, наступний цикл відновлення виконає фазу Redo (яка ідемпотентно накатить раніше згенеровані записи `CLR`), а нова фаза Undo одразу розпочне сканування за адресою `UndoNextLSN`, не повторюючи вже виконану роботу.
5. Отже, загальна кількість незавершених кроків скасування є монотонно спадною функцією, що доводить абсолютну збіжність алгоритму ARIES до повністю узгодженого стану.

---

### Оцінка часової складності та верхні межі відновлення

Часова складність алгоритму ARIES залежить від інтервалу між контрольними точками та пропускної здатності дискової підсистеми:

* **Фаза Analysis**: Час виконання `O(N_wal)`, де `N_wal` — кількість записів від останнього чекпойнта до кінця журналу. Процес виконує виключно читання метаданих заголовків без модифікації сторінок даних.
* **Фаза Redo**: Час виконання `O(N_redo)`, де `N_redo` — кількість записів, починаючи від найменшого `RecLSN` у Dirty Page Table. Оскільки сторінки перевіряються через `PageLSN`, повторні дорогі дискові записи пропускаються.
* **Фаза Undo**: Час виконання `O(N_undo)`, де `N_undo` — сумарна кількість модифікацій, виконаних активними транзакціями.

Завдяки нечітким контрольним точкам обсяг роботи у фазах Analysis та Redo строго обмежений конфігураційними параметрами `checkpoint_timeout` та `max_wal_size`. Навіть при обробці терабайтних баз даних час відновлення ARIES зазвичай не перевищує кількох хвилин. Математична строгість інваріантів гарантує повну транзакційну атомарність без ризику втрати даних.
