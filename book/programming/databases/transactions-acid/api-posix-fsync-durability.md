# 📋 Системні виклики та дискові бар'єри: fsync, fdatasync та контракт довговічності

Виклик стандартної функції `write()` лише копіює байти з буфера процесу в дисковий кеш ядра (*Page Cache*) і повертає керування, не гарантуючи фізичного збереження даних на енергонезалежному накопичувачі. Якщо операційна система або живлення машини аварійно вимикаються до скидання кешу, модифікації безповоротно втрачаються. Щоб гарантувати довговічність (*Durability*) за стандартом ACID, програмне забезпечення передає ядру та контролеру накопичувача команди примусової синхронізації через інтерфейси POSIX (`fsync`, `fdatasync`, `O_DSYNC`) або Win32 API (`FlushFileBuffers`, `FILE_FLAG_WRITE_THROUGH`).

## Шлях даних від програми до постійного носія

Коли база даних записує журнал WAL або сторінку даних, байти проходять чотири рівні буферизації:

```
[ Процес СУБД ] 
      │ (write / pwrite)
      ▼
[ Кеш сторінок ядра (OS Page Cache) ]  ← енергозалежний (DRAM)
      │ (I/O драйвера / DMA)
      ▼
[ Кеш контролера накопичувача (Disk Write Cache) ] ← енергозалежний DRAM (якщо без BBU/PLP)
      │ (FLUSH CACHE / NVMe Flush)
      ▼
[ Фізичні комірки Flash NAND / Магнітні пластини ] ← ЕНЕРГОНЕЗАЛЕЖНИЙ СТАН (ACID Durability)
```

Без спеціального бар'єра синхронізації знеструмлення машини на будь-якому з проміжних етапів призводить до непоправної втрати або пошкодження даних. Операційна система відкладає фізичний запис брудних сторінок (*dirty pages*), оптимізуючи загальну пропускну здатність вводу-виводу за рахунок пакетування (*batching*) та сортування запитів до дискового контролера.

Ядро Linux періодично запускає фонові потоки скидання брудних сторінок (`flusher threads`), орієнтуючись на системні пороги `vm.dirty_background_ratio` (за замовчуванням близько 10% доступної оперативної пам'яті) та `vm.dirty_ratio` (поріг, при досягненні якого процес-письменник примусово блокується і переводиться в режим синхронного запису). Без викликів `fsync` або `fdatasync` брудні сторінки можуть перебувати в енергозалежній пам'яті до 30 секунд (значення параметра `vm.dirty_expire_centisecs`).

## Системні виклики POSIX

### `int fsync(int fd)`

Примусово скидає всі модифіковані дані файлу з кешу сторінок ядра на фізичний накопичувач, а також оновлює службові метадані файлової системи (розмір файлу, час модифікації `mtime`, час доступу `atime`, карту екстентів та дискових блоків inode).

:::tabs
```c
#include <unistd.h>

int fsync(int fd);
```
```cpp
#include <unistd.h>
#include <system_error>

void sync_file_all(int fd) {
    if (::fsync(fd) != 0) {
        throw std::system_error(errno, std::generic_category(), "fsync failed");
    }
}
```
:::

- **Параметри**:
  - `fd` — відкритий файловий дескриптор.
- **Повертане значення**: `0` у разі успіху; `-1` при помилці (значення помилки встановлюється в `errno`).
- **Можливі помилки (`errno`)**:
  - `EBADF` — некоректний дескриптор або файл відкритий лише на читання.
  - `EIO` — апаратна помилка низькорівневого вводу-виводу або фізичний збій сектора носія.
  - `ENOSPC` — брак вільного місця на накопичувачі для запису метаданих чи виділення нових блоків.
  - `EROFS` / `EINVAL` — файл розташовано на файловій системі, що не підтримує синхронізацію (наприклад, спеціальні файлові системи пам'яті).

### `int fdatasync(int fd)`

Оптимізована версія `fsync`. Скидає на диск дані файлу та **лише ті метадані**, які є критично необхідними для подальшого зчитування цих даних (наприклад, зміну розміру файлу). Не скидає другорядні метадані (такі як `mtime` чи `atime`), заощаджуючи один або два випадкових I/O-запити до структур файлової системи на кожен комміт.

:::tabs
```c
#include <unistd.h>

int fdatasync(int fd);
```
```cpp
#include <unistd.h>
#include <system_error>

void sync_file_data_only(int fd) {
    if (::fdatasync(fd) != 0) {
        throw std::system_error(errno, std::generic_category(), "fdatasync failed");
    }
}
```
:::

> **Порада для WAL:** Оскільки журнал транзакцій є файлом з послідовним додаванням фіксованого розміру, використання `fdatasync()` замість `fsync()` скорочує накладні витрати на комміт у 1.5–2 рази за рахунок усунення зайвих оновлень inode.

### Прапорці `open()` для прямої синхронізації

При відкритті файлу через системний виклик `open()` можна задати поведінку синхронізації на рівні кожного виклику `write()`:

:::tabs
```c
#include <fcntl.h>
#include <unistd.h>

int fd = open("wal.log", O_WRONLY | O_CREAT | O_DSYNC, 0644);
```
```cpp
#include <fcntl.h>
#include <unistd.h>
#include <memory>
#include <string_view>
#include <system_error>

struct FdDeleter {
    void operator()(int* fd_ptr) const noexcept {
        if (fd_ptr && *fd_ptr >= 0) {
            ::close(*fd_ptr);
            delete fd_ptr;
        }
    }
};

using ScopedFd = std::unique_ptr<int, FdDeleter>;

ScopedFd open_synchronous_wal(std::string_view path) {
    int fd = ::open(path.data(), O_WRONLY | O_CREAT | O_DSYNC, 0644);
    if (fd < 0) {
        throw std::system_error(errno, std::generic_category(), "open failed");
    }
    return ScopedFd(new int(fd));
}
```
:::

| Прапорець | Семантика | Вплив на продуктивність |
| :--- | :--- | :--- |
| `O_SYNC` | Кожен виклик `write()` неявно виконує `fsync()` (дані + усі метадані). | Дуже повільно; блокує потік на час I/O. |
| `O_DSYNC` | Кожен виклик `write()` неявно виконує `fdatasync()` (дані + розмір). | Оптимально для виділених файлів WAL. |
| `O_DIRECT` | Обхід кешу сторінок ядра (прямий DMA між пам'яттю програми та диском). | Вимагає вирівнювання буферів і зміщень за розміром сектора (512 / 4096 B). Не скасовує кеш контролера (потрібен `fsync`!). |

## Бар'єри файлових систем (Filesystem Write Barriers)

Файлові системи (ext4, XFS, Btrfs) використовують механізм бар'єрів запису (*Write Barriers*), щоб гарантувати правильний порядок запису власних журналів файлової системи на диск.

- **ext4**: за замовчуванням монтується з опцією `barrier=1`. Це змушує драйвер надсилати команду скидання кешу контролера перед кожним оновленням журналу jbd2. Вимкнення (`barrier=0`) прискорює операції запису, але у разі знеструмлення призводить до руйнування структури файлової системи.
- **XFS**: використовує бар'єри постійно (опція `nobarrier` вважається застарілою в сучасних версіях ядра Linux).
- **ZFS**: використовує ZIL (*ZFS Intent Log*) для синхронних операцій запису. Параметр `sync=always` примушує скидати кожен запис у виділений швидкий журнал на енергонезалежному накопичувачі (SLOG), тоді як `sync=disabled` ігнорує запити `fsync`, покладаючись лише на регулярні транзакційні знімки (кожні 5 секунд).

## Еквіваленти в Microsoft Windows

В операційній системі Windows синхронізація реалізується через функції Win32 API:

:::tabs
```c
#include <windows.h>

BOOL FlushFileBuffers(HANDLE hFile);
```
```cpp
#include <windows.h>
#include <system_error>

void flush_windows_handle(HANDLE handle) {
    if (!::FlushFileBuffers(handle)) {
        throw std::system_error(static_cast<int>(::GetLastError()),
                                std::system_category(),
                                "FlushFileBuffers failed");
    }
}
```
:::

- **Призначення**: Записує всі буферизовані дані та оновлює метадані для вказаного файлу, надсилаючи команду очищення кешу на контролер носія.
- **Прапорці створення файлу (`CreateFileW`)**:
  - `FILE_FLAG_WRITE_THROUGH` — забороняє проміжну буферизацію; кожен запис одразу спрямовується до накопичувача (аналог `O_SYNC`).
  - `FILE_FLAG_NO_BUFFERING` — обхід системного кешу (аналог `O_DIRECT`).

## Апаратні бар'єри накопичувача (Flush Commands)

Коли ядро операційної системи виконує `fsync()`, воно формує спеціальну команду для шини накопичувача, яка наказує апаратному контролеру скинути вміст внутрішнього DRAM-буфера на енергонезалежні мікросхеми Flash чи пластини:
- **SATA / ATA**: надсилається команда `FLUSH CACHE` (`0xE7`) або `FLUSH CACHE EXT` (`0xEA`).
- **SCSI / SAS**: надсилається команда `SYNCHRONIZE CACHE (10)` (`0x35`) або `SYNCHRONIZE CACHE (16)` (`0x91`).
- **NVMe**: надсилається команда `Flush` (Opcode `0x00`) черги команд NVMe Submission Queue.

Сучасні асинхронні інтерфейси вводу-виводу в Linux, такі як `io_uring`, надають спеціальний код операції `IORING_OP_FSYNC`. Він дозволяє відправляти запит на синхронізацію файлу без блокування викликаючого потоку процесу, отримуючи сповіщення про завершення фізичного скидання через чергу завершення (*Completion Queue*).

## Груповий комміт (Group Commit) у промислових СУБД

Окремий виклик `fdatasync()` на класичному твердотільному накопичувачі NVMe займає від 20 до 100 мікросекунд, а на магнітному диску HDD — від 5 до 15 мілісекунд (через очікування оберту пластини). Якщо кожен комміт викликатиме фізичний `fsync` індивідуально, система не зможе обробляти більше ніж кілька сотень або тисяч транзакцій на секунду на один потік.

Для подолання цього фізичного бар'єра СУБД використовують техніку **групового комміту (*Group Commit*)**:
1. Перша транзакція, що підійшла до фази фіксації, стає лідером групи (*Group Leader*) і блокує буфер журналу WAL.
2. Поки лідер готує та ініціює системний виклик `fdatasync()`, інші паралельні потоки (послідовники) записують свої коміти у спільний буфер пам'яті й переходять у стан очікування на умовній змінній (*Condition Variable*).
3. Лідер викликає один спільний `fdatasync()`, який фізично скидає на диск записи відразу десятків або сотень транзакцій за одну дискову операцію.
4. Після завершення I/O лідер будить усі транзакції групи, і всі вони одночасно повертають клієнтам успішне підтвердження.

## Конфігурація скидання журналу в популярних СУБД

| СУБД | Параметр конфігурації | Значення для повної надійності ACID | Значення для компромісу з продуктивністю |
| :--- | :--- | :--- | :--- |
| **PostgreSQL** | `wal_sync_method` | `fdatasync` (Linux) / `open_datasync` | `fsync_writethrough` |
| **PostgreSQL** | `synchronous_commit` | `on` (чекає на фізичний запис WAL) | `off` (асинхронний комміт: до 3×`wal_writer_delay` втрати даних при аварії) |
| **MySQL / InnoDB** | `innodb_flush_log_at_trx_commit` | `1` (запис і скид `fsync` на кожен комміт) | `2` (запис у кеш ОС, скид на диск раз на секунду) |
| **SQLite** | `PRAGMA synchronous;` | `FULL` (2) / `EXTRA` (3) | `NORMAL` (1) / `OFF` (0) |
| **RocksDB** | `SyncWAL()` / `WriteOptions.sync` | `sync = true` (виклик `fdatasync`) | `sync = false` (лише додавання у буфер WAL) |

## Пастки реалізації та помилки («Fsyncgate»)

1. **Аварійне скидання помилок у Linux (Fsyncgate)**:
   У версіях ядра Linux до 4.19 існував критичний дефект поведінки сторінкового кешу: якщо у фонового скидання сторінки виникала помилка вводу-виводу (`EIO`), сторінка позначалася як «чиста» і викидалася з пам'яті. Перший наступний виклик `fsync()` повертав `EIO`, але повторний виклик `fsync()` повертав `0` (успіх), створюючи у СУБД (зокрема, PostgreSQL) ілюзію, що дані збережені на диску, хоча вони були безповоротно втрачені. Сучасні ядра коректно утримують прапорець помилки дескриптора файлу.
2. **Обман накопичувачів споживчого класу (Consumer SSDs)**:
   Деякі дешеві споживчі накопичувачі ігнорують команду `FLUSH CACHE` або фіктивно повертають статус успіху, залишаючи дані в енергозалежному DRAM-буфері для підвищення результатів у синтетичних тестах продуктивності. Серверні корпоративні SSD обов'язково мають захист від втрати живлення **PLP** (*Power Loss Protection*) на базі танталових конденсаторів, які забезпечують енергію для завершення запису DRAM-буфера при раптовому знеструмленні.
