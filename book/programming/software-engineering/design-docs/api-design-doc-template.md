# 📋 Еталонна структура та специфікація розділів Design Doc

Ця специфікація визначає обов'язкові метадані, структуру розділів, правила переходів життєвого циклу, протоколи обробки збоїв та валідаційні критерії для інженерних документів проектування (Design Doc) і технічних пропозицій (RFC).

## Метадані документу (Frontmatter Schema)

Кожен документ починається з блоку метаданих у форматі YAML, розміщеного на початку Markdown-файлу. Блок забезпечує машинне парсування та автоматизовану валідацію в конвеєрі неперервної інтеграції (CI/CD).

```yaml
---
rfc_id: "RFC-0042"
title: "Асинхронний шар реплікації сховища замовлень"
status: "review" # draft | review | approved | rejected | in_progress | implemented | superseded
authors:
  - name: "Олександр Коваленко"
    email: "o.kovalenko@company.internal"
    role: "Lead Backend Engineer"
reviewers:
  - name: "Ірина Мельник"
    role: "Staff Architect"
    status: "pending" # pending | approved | changes_requested
  - name: "Тарас Шевчук"
    role: "Principal SRE"
    status: "approved"
created_date: "2026-06-10"
last_updated: "2026-06-18"
target_milestone: "2026-Q3"
supersedes: "RFC-0018"
superseded_by: null
tags:
  - "storage"
  - "replication"
  - "distributed-systems"
---
```

### Словник полів заголовка

| Поле | Тип | Обов'язковість | Опис та обмеження |
| :--- | :--- | :--- | :--- |
| `rfc_id` | String | Так | Унікальний ідентифікатор у форматі `RFC-XXXX` (або `DD-XXXX`), де `XXXX` — чотиризначне число. |
| `title` | String | Так | Лаконічна назва проекту (від 10 до 80 символів). |
| `status` | Enum | Так | Поточний стан: `draft`, `review`, `approved`, `rejected`, `in_progress`, `implemented`, `superseded`. |
| `authors` | List | Так | Список авторів (ім'я, корпоративна адреса, інженерна роль). |
| `reviewers` | List | Так | Призначені обов'язкові рецензенти та їхні поточні вердикти. |
| `created_date`| Date | Так | Дата створення у форматі ISO 8601 (`YYYY-MM-DD`). |
| `last_updated`| Date | Так | Дата останнього редагування документу. |
| `target_milestone` | String | Ні | Цільовий релізний квартал чи версія системи (наприклад, `2026-Q3` або `v2.4.0`). |
| `supersedes` | String | Ні | Ідентифікатор старого RFC, який скасовується цим дизайном. |
| `superseded_by` | String | Ні | Ідентифікатор нового RFC, що замінив цей документ у майбутньому. |
| `tags` | List | Ні | Тематичні мітки для каталогізації, фільтрації та пошуку в базі знань. |

## Специфікація та вимоги до розділів

Тіло документу складається із семи канонічних розділів першого та другого рівнів (`##`). Відсутність будь-якого з обов'язкових розділів вважається дефектом оформлення.

```markdown
# RFC-0042: Асинхронний шар реплікації сховища замовлень

## 1. Контекст і формулювання проблеми (Context & Problem Statement)
## 2. Цілі та не-цілі (Goals & Non-Goals)
## 3. Пропоноване архітектурне рішення (Proposed Architecture)
### 3.1. Топологія та взаємодія компонентів
### 3.2. Контракти API та моделі даних
### 3.3. Обробка помилок та поведінка у разі збоїв
## 4. Наскрізні інженерні вимоги (Cross-cutting Concerns)
### 4.1. Безпека та контроль доступу
### 4.2. Розрахунок навантаження та ліміти ресурсів (Capacity Planning)
### 4.3. Спостережуваність і телеметрія (Observability)
## 5. Розглянуті альтернативи (Alternatives Considered)
## 6. План впровадження, міграції та відкату (Rollout & Migration)
## 7. Відкриті питання (Open Questions)
```

### Детальні вимоги до змісту розділів

#### 1. Контекст і формулювання проблеми
- **Опис поточного стану:** Чітка фіксація наявної архітектури системи без прикрашання та евфемізмів.
- **Драйвер зміни:** Що саме змушує змінювати систему (вичерпання пропускної здатності дискової підсистеми, зміна регуляторних вимог, затримка реплікації понад допустиму межу).
- **Числові показники проблеми:** Метрики поточного стану (наприклад, «p99 затримки читання зросла з 15 мс до 180 мс при навантаженні 50 000 QPS; 1.2% запитів завершуються таймаутом через блокування рядків у реляційній базі даних»).

#### 2. Цілі та не-цілі (Goals & Non-Goals)
- **Goals (Цілі):**
  - Вимірні технічні критерії, досягнення яких однозначно свідчить про успішне виконання проекту.
  - Приклад: «Знизити p99 затримки операції читання до < 25 мс при навантаженні 100 000 QPS зі збереженням гарантії Read-Your-Writes для користувача, що створив замовлення».
- **Non-Goals (Не-цілі):**
  - Свідомо відкинуті та виключені вимоги, які команда категорично відмовляється реалізовувати в межах цього проекту.
  - Головний інструмент захисту від розмивання меж проекту (англ. *scope creep*).
  - Приклад: «Цей дизайн НЕ забезпечує мультирегіональну синхронну реплікацію між континентами; трансконтинентальна синхронізація буде спроектована в окремому документі наступного року».

#### 3. Пропоноване архітектурне рішення
- **Топологія:** Архітектурна діаграма компонентів із чітким позначенням меж сервісів, брокерів повідомлень та сховищ даних.
- **Схеми даних:** Формальний опис нових структур у форматі `Protocol Buffers`, `JSON Schema` або `SQL DDL`.
- **Контракти інтерфейсів:** Сигнатури RPC/REST-методів, протоколи передачі, заголовки ідемпотентності та схеми відповідей.
- **Обробка збоїв:** Специфікація поведінки при розриві мережі (network partition), переповненні черг, недоступності лідера кластера або деградації сторонніх API.

#### 4. Наскрізні інженерні вимоги
- **Безпека:** Модель автентифікації та авторизації (mTLS, JWT, RBAC), шифрування у спокої (at rest) та в русі (in transit), відповідність вимогам захисту персональних даних (GDPR).
- **Capacity Planning:** Розрахунок споживання CPU, пам'яті, IOPS дисків та смуги пропускання мережі на пікових навантаженнях з урахуванням росту бази даних на 12–24 місяці.
- **Observability:** Перелік нових бізнес-метрик та інфраструктурних лічильників (Prometheus/OpenTelemetry), політика трасування викликів, рівні тривог (P1/P2/P3) та пряме посилання на робочу інструкцію експлуатації (Runbook).

#### 5. Розглянуті альтернативи
- Мінімум дві альтернативи, які реально розглядалися як конкуренти обраного дизайну.
- Таблиця зіставлення за спільними архітектурними критеріями з вагами:

```
критерій               вага  варіант А (Kafka)  варіант Б (Postgres CDC)  варіант В (Redis)
затримка читання        ×3          4                      2                     5
надійність доставки     ×3          5                      4                     2
складність операцій     ×2          2                      4                     4
вартість інфраструктури ×2          3                      4                     2
──────────────────────────────────────────────────────────────────────────────────────────
разом (зважено)                     37                     34                    32
```

- Чітке пояснення причини відхилення кожного варіанту: варіант Б відхилено через надмірне навантаження на диск основної бази при пікових сплесках; варіант В відхилено через неприйнятний ризик втрати повідомлень при аварійному перезавантаженні вузла.

#### 6. План впровадження, міграції та відкату
- **Поетапний запуск:** Використання прапорців функціональності (feature flags), темний запуск (dark launch) без показу результатів користувачам, тіньовий трафік (shadow traffic), канареечний реліз (1% → 5% → 25% → 100%).
- **Міграція даних:** Стратегія паралельного запису (Dual-write) та фонового перенесення історичних записів (Backfill) із верифікацією контрольних сум.
- **План аварійного відкату (Rollback):** Покроковий чеклист дій чергового інженера при виявленні критичної деградації, включаючи порядок вимкнення нових воркерів та зворотне перемикання маршрутизатора трафіку.

#### 7. Відкриті питання
- Список інженерних невизначеностей, щодо яких автор просить технічної консультації у рецензентів.
- Перед фінальним схваленням кожне відкрите питання повинно містити підсумок досягнутого консенсусу або посилання на окремий експеримент.

## Критерії переходів між статусами (State Machine Contract)

| Поточний стан | Цільовий стан | Умови переходу (Вхідні ворота) |
| :--- | :--- | :--- |
| `draft` | `review` | Заповнено всі 7 обов'язкових розділів. Призначено мінімум двох обов'язкових рецензентів. Пройдено валідацію автоматичного лінтера. |
| `review` | `approved` | Отримано схвалення (`approved`) від усіх обов'язкових рецензентів (SRE, Security, Tech Lead). Усі відкриті питання позначені як вирішені. |
| `review` | `rejected` | Виявлено непереборні ризики або проект визнано економічно недоцільним. Зафіксовано технічну причину відхилення в тілі документу. |
| `approved` | `in_progress` | Розпочато створення Pull Request-ів із кодом у відповідних репозиторіях проекту. |
| `in_progress` | `implemented` | Увесь код влито в основну гілку, міграцію бази даних завершено, функціонал працює на 100% продакшен-трафіку без критичних інцидентів. |
| `approved` / `implemented` | `superseded` | Ухвалено новий RFC, що замінює поточний підхід. У полі `superseded_by` проставлено посилання на новий документ. |

## Чеклист валідації перед схваленням (Review Gates)

Перед наданням фінального схвалення (`sign-off`) перевіряються чотири ворота інженерної якості:

1. **Ворота безпеки та приватності (Security & Privacy Gate):**
   - [ ] Дані користувачів шифруються згідно зі стандартами TLS 1.3 / AES-256-GCM.
   - [ ] Визначено сувору модель контролю доступу (RBAC / ABAC) та принципи найменших привілеїв.
   - [ ] Перевірено захист від ін'єкцій, витоку ключів та атак типу переповнення буфера.
   - [ ] Визначено терміни зберігання персональних даних (Data Retention Policy) та процедуру їх повного видалення.

2. **Ворота надійності та SRE (Reliability & Resilience Gate):**
   - [ ] Усі зовнішні мережеві виклики захищені явними таймаутами та механізмом запобігання каскадним збоям (Circuit Breaker).
   - [ ] Операції модифікації стану підтримують унікальні ідемпотентні ключі клієнта.
   - [ ] Визначено цільові показники надійності (SLO/SLI) та налаштовано пороги сповіщення чергових інженерів.
   - [ ] Описано процедуру обробки «отруйних повідомлень» (Dead Letter Queue, DLQ).

3. **Ворота сумісності та міграції (Compatibility & Migration Gate):**
   - [ ] Зміна схеми API не порушує роботу клієнтів попередньої версії (дотримано принципу розширення-звуження, expand-contract).
   - [ ] Старі поля позначені як застарілі (`deprecated`) з оголошеним терміном підтримки.
   - [ ] Скрипт міграції перевірено на тестовому наборі даних розміром не менше 100% реальної бази.

4. **Ворота відкату та деградації (Rollback & Graceful Degradation Gate):**
   - [ ] Команда має автоматизований та перевірений скрипт зворотного перемикання трафіку.
   - [ ] Нова схема бази даних дозволяє безпечну роботу попередньої версії бінарного коду.
   - [ ] Визначено план деградації функціональності при відмові вторинних залежностей (наприклад, повернення кешованих даних замість помилки 500).
