# 📋 Специфікація контрактів застарівання та фазового переходу API

Будь-який перехід у патерні Expand–Contract (паралельна зміна) спирається на чіткі, машинозчитувані та стандартизовані протоколи взаємодії між постачальником сервісу (англ. *provider*) та його споживачами (англ. *consumers*). Ця специфікація встановлює єдині правила оголошення застарівання (англ. *deprecation*), термінів виведення з експлуатації (англ. *sunsetting*), аудиту трафіку через метрики OpenTelemetry/Prometheus, статусів gRPC та сигналізації на рівні вихідного коду для мов зі статичною та динамічною типізацією.

Головна мета контрактів застарівання — усунути невизначеність і припущення. Споживач не повинен дізнаватися про відключення інтерфейсу з аварійного збою у виробничому середовищі. Інформація про термін життя контракту має автоматично вичитуватися клієнтськими бібліотеками, шлюзами API та системами статичного аналізу коду ще на етапі компіляції чи тестування.

## 1. Мережевий HTTP/REST контракт: Заголовки RFC 8594 та Draft Deprecation

Для HTTP-інтерфейсів сигналізація про життєвий цикл кінцевої точки здійснюється за допомогою стандартизованих HTTP-заголовків відповідей. Це дозволяє проксі-серверам, балансувальникам навантаження та клієнтським SDK автоматично реєструвати використання застарілих маршрутів без аналізу тіла відповіді.

Заголовок `Deprecation` визначає факт або дату, коли кінцева точка була офіційно визнана застарілою. Згідно з чернеткою стандарту IETF, значенням може бути точна дата у форматі HTTP-Date або уніфікована позначка часу Unix. Якщо дата вказує на минулий час, це означає, що функціональність уже вважається застарілою, але залишається доступною для викликів.

Заголовок `Sunset` стандартизований документом RFC 8594. Він вказує на незворотну дату та час, коли ресурс буде остаточно вимкнено або видалено. Клієнтські застосунки зобов'язані завершити міграцію на наступну версію API до настання моменту, вказаного в цьому заголовку. Будь-які проміжні кешувальні сервери (CDN, Reverse Proxies) використовують значення `Sunset` для обмеження максимального часу життя закешованих відповідей (`max-age`).

Заголовок `Link` з атрибутом `rel="sunset"` надає пряме машинне посилання на вебдокументацію або специфікацію OpenAPI, яка описує покроковий план міграції на новий контракт. Додатковий зв'язок `rel="successor-version"` може вказувати на пряму URI-адресу нового маршруту.

Заголовок `Warning` (код 299) забезпечує текстове повідомлення, призначене для відображення в системних журналах або на консолі розробника під час виконання запитів у тестовому середовищі.

### Приклад HTTP-відповіді у фазі застарівання (Phase 2: Transition)

Коли клієнт звертається до застарілого маршруту v1 під час перехідного періоду, сервер повертає успішний результат запиту разом із повним набором метаданих міграції:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Date: Thu, 20 Aug 2026 16:45:00 GMT
Deprecation: @1755705600
Sunset: Wed, 11 Nov 2026 00:00:00 GMT
Link: <https://api.service.internal/docs/migrations/v2-user-profile>; rel="sunset"; type="text/html"
Link: <https://api.service.internal/v2/users/usr_481516>; rel="successor-version"
Warning: 299 - "Endpoint /v1/users is deprecated. Migrate to /v2/users before Sunset date."
X-API-Contract-Phase: transition

{
  "id": "usr_481516",
  "name": "Олена Коваль",
  "email": "olena@example.com"
}
```

### Поведінка та коди повернення на різних фазах життєвого циклу

У фазі 1 (Expand) сервер повертає стандартні коди успіху `200 OK` або `201 Created`. Працюють як старі, так і нові маршрути. Заголовок `Deprecation` відсутній, оскільки новий контракт проходить стабілізацію під робочим навантаженням.

У фазі 2 (Transition / Deprecation) сервер повертає код `200 OK` з обов'язковими заголовками `Deprecation`, `Sunset` та `Link`. За один-два тижні до настання дати `Sunset` постачальник має право проводити контрольовані планові затемнення (англ. *brownouts*), повертаючи коди `429 Too Many Requests` або `503 Service Unavailable` для невеликої частки запитів (наприклад, 1–5%), щоб змусити пасивних споживачів звернути увагу на сповіщення моніторингу.

У фазі 3 (Contract) кінцеву точку остаточно вилучають з маршрутизатора. Будь-які подальші запити до старого шляху отримують код `410 Gone` (якщо сервер фіксує, що ресурс існував раніше, але був назавжди видалений) або код `404 Not Found`.

## 2. Специфікація gRPC та бінарних протоколів

У бінарних RPC-інтерфейсах на базі gRPC та Protocol Buffers застарівання регулюється як на рівні статичної схеми файлу `.proto`, так і на рівні динамічних метаданих і кодів помилок статусів виклику під час виконання.

На рівні схеми кожен RPC-метод або окреме поле повідомлення позначається стандартною опцією `deprecated = true`. Це змушує компілятор `protoc` генерувати мовнозалежні атрибути застарівання у цільовому коді (наприклад, анотації `@Deprecated` у Java або атрибути `[[deprecated]]` у C++).

```protobuf
syntax = "proto3";

package users.v1;

service UserService {
  // Застарілий RPC-метод: позначається опцією deprecated
  rpc GetUserById(GetUserRequest) returns (UserResponse) {
    option deprecated = true;
  }

  // Новий розширений RPC-метод
  rpc FindUser(FindUserRequest) returns (UserResponse);
}

message GetUserRequest {
  string user_id = 1;
}

message FindUserRequest {
  string user_id = 1;
  string tenant_id = 2;
  uint32 flags = 3;
}

message UserResponse {
  string user_id = 1;
  string full_name = 2 [deprecated = true]; // Застаріле поле
  string first_name = 3;
  string last_name = 4;
}
```

Під час фази застарівання виклик методу gRPC повертає успішний статус `OK` (числовий код 0), а метадані відповіді (англ. *trailing metadata*) містять текстові ключі `x-endpoint-deprecated: true` та `x-endpoint-sunset: 2026-11-11T00:00:00Z`. Клієнтські перехоплювачі (англ. *interceptors*) можуть автоматично зчитувати ці метадані та реєструвати попередження в системі аудиту.

Після настання дедлайну у фазі Contract виклик методу завершується статусом помилки `Status::UNIMPLEMENTED` (код 12) або `Status::FAILED_PRECONDITION` (код 9) із детальним описом причини у стандартизованій структурі `google.rpc.ErrorInfo`.

## 3. Контракт застарівання на рівні мов програмування

Для внутрішніх бібліотек, системних компонентів та спільних модулів попередження про застарівання повинно виникати безпосередньо під час компіляції клієнтського проєкту або під час статичного аналізу коду лінтерами.

У мовах зі статичною типізацією використовуються спеціалізовані мовні атрибути та прагми. У стандарті C++14 та новіших версіях застосовується уніфікований атрибут `[[deprecated("пояснення")]]`. У мові C стандарт C23 закріпив аналогічний синтаксис, тоді як у C99/C11 застосовуються розширення компіляторів GCC, Clang та MSVC.

:::tabs
```c
/* c_deprecation.h — Застарівання для C99/C11/C23 */
#ifndef C_DEPRECATION_H
#define C_DEPRECATION_H

#include <stddef.h>
#include <stdbool.h>

#if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 202311L
#  define API_DEPRECATED(msg) [[deprecated(msg)]]
#elif defined(__GNUC__) || defined(__clang__)
#  define API_DEPRECATED(msg) __attribute__((deprecated(msg)))
#elif defined(_MSC_VER)
#  define API_DEPRECATED(msg) __declspec(deprecated(msg))
#else
#  define API_DEPRECATED(msg)
#endif

typedef struct {
    const char* user_id;
    const char* tenant_id;
    unsigned int flags;
} user_options_t;

/* Застаріла функція: компілятор видасть warning при її виклику */
API_DEPRECATED("legacy_get_user is deprecated. Migrate to user_store_find before v3.0 release.")
int legacy_get_user(const char* id, char* out_buf, size_t buf_len);

/* Новий розширений контракт */
int user_store_find(const user_options_t* opts, char* out_buf, size_t buf_len);

#endif /* C_DEPRECATION_H */
```
```cpp
// cpp_deprecation.hpp — Застарівання для C++14/C++17/C++20
#pragma once

#include <string>
#include <string_view>
#include <optional>
#include <cstdint>

struct UserOptions {
    std::string_view user_id;
    std::string_view tenant_id{"tenant_default"};
    uint32_t flags{0};
};

class [[deprecated("UserStore v1 is deprecated. Migrate to TenantUserStore.")]] LegacyUserStore {
public:
    // Застарілий метод з обов'язковим текстовим поясненням і версією видалення
    [[deprecated("Use find_user(UserOptions const&) instead. Removal scheduled for v3.0.0.")]]
    std::optional<std::string> get_user_by_id(std::string_view id);

    // Новий метод розширеного контракту
    std::optional<std::string> find_user(UserOptions const& options);
};
```
:::

У середовищі Go контракт застарівання встановлюється конвенцією форматованого коментаря, що починається з префікса `// Deprecated:`. Утиліти статичного аналізу `go vet` та мовний сервер `gopls` розпізнають цю конструкцію та підсвічують виклик закресленим шрифтом у редакторі коду.

У екосистемах JavaScript та TypeScript застосовується анотація JSDoc `/** @deprecated опис */`. Правило `deprecation/deprecation` плагіна ESLint блокує збірку проєкту у системі неперервної інтеграції, якщо новий код використовує застарілі функції.

У мові Rust використовується стандартний атрибут `#[deprecated(since = "2.1.0", note = "Використовуйте new_fn")]`. Компілятор `rustc` генерує попередження із зазначенням версії, в якій функція була оголошена застарілою, та альтернативного методу.

## 4. Специфікація метрик та аудиту телеметрії (OpenTelemetry / Prometheus)

Перехід від Фази 2 (Transition) до Фази 3 (Contract) дозволяється здійснювати **виключно** на основі кількісних показників телеметрії. Жодне видалення коду, схеми бази чи маршруту API не може базуватися на суб'єктивних припущеннях розробників або усних домовленостях.

Система моніторингу повинна агрегувати показники використання застарілих маршрутів у розрізі ідентифікаторів споживачів, версій клієнтських застосунків та конкретних полів даних.

```prometheus
# HELP api_requests_total Загальна кількість запитів до сервісу за маршрутами та версіями
# TYPE api_requests_total counter
api_requests_total{route="/v1/users",method="GET",status="200",contract_version="v1",contract_status="deprecated",client_id="billing-service",client_version="1.14.2"} 0

api_requests_total{route="/v2/users",method="GET",status="200",contract_version="v2",contract_status="active",client_id="billing-service",client_version="2.0.1"} 148209

# HELP api_contract_phase Поточна активна фаза контракту (1=Expand, 2=Transition, 3=Contract)
# TYPE api_contract_phase gauge
api_contract_phase{api_name="users_service",target_version="v2"} 2

# HELP api_deprecated_field_access_total Кількість звернень до застарілих полів у тілі запиту/відповіді
# TYPE api_deprecated_field_access_total counter
api_deprecated_field_access_total{schema="UserProfile",field="legacy_phone",client_id="legacy-importer"} 0
```

Кожен запис телеметрії містить стандартні виміри: нормалізований шаблон маршруту `route`, версію контракту `contract_version`, юридичний статус `contract_status` (`active`, `deprecated`, `sunset`), ідентифікатор клієнтської системи `client_id` (отриманий з токена автентифікації або заголовка `X-Client-ID`) та номер версії клієнтського застосунку `client_version`.

Ці метрики дозволяють команді постачальника будувати динамічні графіки спадання старого трафіку у Grafana, налаштовувати сповіщення у разі появи нових викликів до застарілого API та точно ідентифікувати системи, які затримують завершення міграції.

## 5. Контрактний гейт переходу у фазу Contract (Gate Invariants)

Перед запуском Фази 3 (фізичне видалення коду, таблиць або кінцевих точок) інженерна команда зобов'язана отримати автоматичне підтвердження виконання трьох обов'язкових інваріантів перевірки якості:

Перший інваріант вимагає нульової швидкості запитів до застарілого інтерфейсу:
```
rate(api_requests_total{contract_version="v1"}[7d]) == 0
```
Ця умова вимагає повної відсутності трафіку на застарілому інтерфейсі протягом щонайменше семи повних діб поспіль. Семиденне вікно є обов'язковим для того, щоб охопити робочі дні, вихідні дні, нічні регламентні розрахунки та щотижневі пакетні завдання формування фінансової звітності.

Другий інваріант контролює настання офіційного дедлайну за часом:
```
current_timestamp >= sunset_timestamp
```
Поточний системний час повинен перевищувати дату, оголошену в заголовку `Sunset` або договорі про рівень обслуговування (SLA).

Третій інваріант перевіряє стан підсистем зберігання даних:
```
database_dual_write_status == "disabled" AND database_legacy_reads == 0
```
Операції читання та запису в застарілі структури зберігання повинні бути повністю зупинені у конфігурації всіх працюючих екземплярів сервісу.

Порушення хоча б одного з цих інваріантів автоматично блокує виконання злиття коду в системі неперервної інтеграції (CI/CD Quality Gate), надійно захищаючи систему від аварій через передчасне звуження контракту.
