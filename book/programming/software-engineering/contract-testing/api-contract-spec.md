# 📋 Специфікація та правила зіставлення контрактів (Pact Specification)

Контрактний тест є надійним рівно настільки, наскільки однозначно визначено його артефакт. У розподіленій системі контракт — це не довільний набір записів у щоденнику розробника, а формальний документ із строгою схемою, який однаково інтерпретується інструментами на різних мовах програмування: від Rust і C++ до Python, TypeScript чи Java.

Цей довідник описує повну структуру документа специфікації контракту (згідно зі стандартами Pact Specification v2, v3 та v4), семантику взаємодій, правила зіставлення даних (Matching Rules), роботу динамічних генераторів, обробку бінарних форматів та інтерфейс взаємодії з брокером контрактів для інструмента розгортання `can-i-deploy`.

## Структура документа контракту (Pact Document Schema)

Контрактний документ являє собою деревоподібний JSON-об'єкт, що зв'язує рівно одного споживача з одним постачальником. Навіть якщо споживач викликає десять різних сервісів, для кожного з них створюється окремий незалежний файл контракту.

```json
{
  "consumer": {
    "name": "OrderServiceClient"
  },
  "provider": {
    "name": "PaymentService"
  },
  "interactions": [
    {
      "description": "запит на проведення транзакції для активного рахунку",
      "providerStates": [
        {
          "name": "користувач 42 має достатній баланс",
          "params": { "userId": 42, "amount": 250.0 }
        }
      ],
      "request": {
        "method": "POST",
        "path": "/api/v1/payments",
        "headers": {
          "Content-Type": "application/json",
          "Accept": "application/json"
        },
        "body": {
          "userId": 42,
          "amount": 250.0,
          "currency": "UAH"
        },
        "matchingRules": {
          "body": {
            "$.userId": { "matchers": [{ "match": "type" }] },
            "$.amount": { "matchers": [{ "match": "number" }] },
            "$.currency": { "matchers": [{ "match": "regex", "regex": "^[A-Z]{3}$" }] }
          }
        }
      },
      "response": {
        "status": 200,
        "headers": {
          "Content-Type": "application/json"
        },
        "body": {
          "paymentId": "pay_987abc",
          "status": "COMPLETED",
          "processedAt": "2026-08-20T19:45:00Z"
        },
        "matchingRules": {
          "body": {
            "$.paymentId": { "matchers": [{ "match": "type" }] },
            "$.status": { "matchers": [{ "match": "equality" }] },
            "$.processedAt": { "matchers": [{ "match": "date", "format": "yyyy-MM-dd'T'HH:mm:ssX" }] }
          }
        }
      }
    }
  ],
  "metadata": {
    "pactSpecification": {
      "version": "3.0.0"
    },
    "pactRust": {
      "version": "0.4.0"
    }
  }
}
```

У корені документа розташовано чотири базові вузли:
1. `consumer` — містить поле `name` (унікальне ідентифікаційне ім'я сервісу-споживача в екосистемі).
2. `provider` — містить поле `name` (унікальне ідентифікаційне ім'я сервісу-постачальника).
3. `interactions` — упорядкований масив окремих мережевих діалогів (HTTP-запитів або повідомлень черги), що складають контракт.
4. `metadata` — версія специфікації Pact (наприклад, `3.0.0` або `4.0.0`) та ідентифікатор генератора файлу.

## Анатомія взаємодії (Interaction)

Кожна взаємодія моделює один ізольований цикл «запит–відповідь». Взаємодія мусить бути самодостатньою: вона не може покладатися на побічні ефекти попередньої взаємодії з масиву.

| Поле | Тип | Обов'язкове | Призначення |
| :--- | :--- | :--- | :--- |
| `description` | `string` | Так | Унікальний текстовий опис сценарію, що виводиться у звітах проходження тестів. |
| `providerStates` | `array` | Ні | Список назв станів та контекстних параметрів, які постачальник зобов'язаний налаштувати перед тестом. |
| `request` | `object` | Так | Опис форми HTTP-запиту: метод, шлях, query-параметри, заголовки та тіло. |
| `response` | `object` | Так | Опис форми HTTP-відповіді: очікуваний числовий статус-код, заголовки та тіло. |
| `matchingRules` | `object` | Ні | Декларативні правила нежорсткого порівняння значень замість точного збігу. |
| `generators` | `object` | Ні | Генератори динамічних даних під час прогону на боці постачальника. |

## Каталог правил зіставлення (Matching Rules)

Правила зіставлення відокремлюють структуру даних від конкретних значень. У тілі запиту чи відповіді вказується приклад значення (використовується Mock-сервером на боці споживача), а в блоці `matchingRules` задається вираз шляху JSONPath (наприклад, `$.user.id`) та масив застосовних матчерів.

### 1. Зіставлення за типом (`type` / `like`)
Перевіряє, що фактичне значення має той самий базовий тип, що й зразок (число, рядок, булеве значення, об'єкт чи масив). Конкретне числове значення чи символи рядка можуть бути будь-якими.

```json
{
  "match": "type"
}
```

Якщо зразок у контракті містить `"id": 42`, то повернення постачальником `"id": 100500` буде успішно прийнято, але `"id": "42"` (рядок замість числа) спричинить помилку верифікації.

### 2. Регулярний вираз (`regex`)
Використовується для текстових полів, значення яких мають підпорядковуватися строгому синтаксичному формату: ідентифікатори UUID, телефонні номери, коди валют, хеші чи поштові адреси.

```json
{
  "match": "regex",
  "regex": "^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$"
}
```

Під час верифікації фактичний рядок постачальника перевіряється регулярним виразом. Якщо вираз не збігається, раннер повертає діагностику з вказівкою невідповідного рядка.

### 3. Точна рівність (`equality`)
Вимагає абсолютного збігу байтів або значень. Застосовується тоді, коли значення є бізнес-константою: фіксований статус енумерації (`"PENDING"`, `"COMPLETED"`), конкретний код валюти або службовий прапорець.

```json
{
  "match": "equality"
}
```

### 4. Зіставлення масивів та колекцій (`min`, `max`, `eachLike`)
Перевіряє масиви змінної довжини. Правило `min` гарантує, що у відповіді повернеться щонайменше `N` елементів, і кожен елемент задовольнятиме внутрішню структуру зразка.

```json
{
  "match": "type",
  "min": 1,
  "max": 50
}
```

Це дозволяє клієнту перевірити, що список транзакцій повертає валідні об'єкти транзакцій, навіть якщо реальна тестова база постачальника містить 15 записів замість одного тестового.

### 5. Формати дати та часу (`date`, `time`, `datetime`)
Перевіряє, чи текстовий рядок можна розібрати за стандартною маскою дати й часу (ISO-8601, RFC-3339 тощо) без необхідності жорстко прив'язуватися до секунд у минулому.

```json
{
  "match": "datetime",
  "format": "yyyy-MM-dd'T'HH:mm:ss.SSSX"
}
```

### 6. Входження підрядка (`include`)
Застосовується переважно для заголовків або складених рядків, де достатньо перевірити наявність ключового фрагмента (наприклад, перевірка типу вмісту `application/json; charset=utf-8` через пошук підрядка `application/json`).

```json
{
  "match": "include",
  "value": "application/json"
}
```

## Динамічні генератори значень (Generators AST)

Починаючи зі специфікації Pact v3, у контрактах з'явився блок `generators`. Генератори розв'язують проблему даних, які швидко старіють. Якщо контракт вимагає передати дату народження або токен, який діє лише 5 хвилин, жорстко закодована дата в тілі запиту стане невалідною вже наступного тижня.

Блок генераторів наказує верифікаційному раннеру підставити свіже значення безпосередньо в момент виконання тесту:

```json
{
  "generators": {
    "body": {
      "$.createdTimestamp": {
        "type": "DateTime",
        "format": "yyyy-MM-dd'T'HH:mm:ssZ"
      },
      "$.trackingId": {
        "type": "RandomDecimal",
        "digits": 10
      }
    }
  }
}
```

Під час тестування споживача генератор підставляє статичний приклад, а під час верифікації постачальника раннер генерує свіже значення за правилом генератора, гарантуючи проходження валідації часу на сервері.

## Специфікація асинхронних контрактів (Message Contracts)

Для взаємодії через брокери подій (Apache Kafka, RabbitMQ, Google Pub/Sub) використовується спрощена схема взаємодії, де вилучено мережеві поняття URL-шляхів, HTTP-методів та кодів стану.

```json
{
  "description": "подія публікації нового платежу",
  "providerStates": [
    { "name": "платіж 550 успішно підтверджено банком" }
  ],
  "contents": {
    "eventId": "evt_998811",
    "eventType": "PAYMENT_CONFIRMED",
    "amount": 450.0,
    "currency": "UAH"
  },
  "matchingRules": {
    "body": {
      "$.eventId": { "matchers": [{ "match": "type" }] },
      "$.eventType": { "matchers": [{ "match": "equality" }] },
      "$.amount": { "matchers": [{ "match": "number" }] }
    }
  },
  "metadata": {
    "contentType": "application/json",
    "kafka_topic": "billing.payments.v1"
  }
}
```

Тест споживача підтверджує, що функція-слухач черги здатна розібрати об'єкт `contents`, а тест постачальника підтверджує, що продюсер формує подію, яка задовольняє всі правила розділу `matchingRules`.

## Підтримка бінарних протоколів та gRPC (Pact v4)

У специфікації Pact v4 реалізовано підтримку плагінів (Pact Plugins), що дозволяє використовувати контрактне тестування для бінарних протоколів: Google Protocol Buffers (Protobuf), gRPC, Apache Avro та форматів із MIME-типом `multipart/form-data`.

При роботі з gRPC замість HTTP-шляху контракт фіксує ім'я сервісу та RPC-методу (наприклад, `payments.PaymentService/ProcessTransaction`), бінарне тіло запиту та бінарне тіло відповіді, що зберігаються у вигляді base64-рядків або структурованих описів proto-полів. Раннер декодує повідомлення через відповідний плагін протоколу і застосовує стандартні правила матчингу до десеріалізованих полів структури.

## Коди завершення та протокол шлюзу розгортання `can-i-deploy`

Централізований брокер контрактів (Pact Broker) надає REST API, через яке системи неперервного розгортання (CI/CD) отримують дозвіл на деплой версії сервісу в цільове середовище.

Команда CLI викликає матричний ендпоінт брокера:
```bash
pact-broker can-i-deploy \
  --pacticipant PaymentService \
  --version 2.4.1 \
  --to-environment production \
  --broker-base-url https://pact-broker.corp.internal
```

Брокер обчислює перетин матриці версій: знаходить усі активні сервіси в середовищі `production`, відшукує відповідні контракти та звіряє наявність успішних записів верифікації.

```json
{
  "summary": {
    "deployable": true,
    "reason": "Усі контракти успішно верифіковано для цільового середовища",
    "total": 2,
    "success": 2,
    "failed": 0,
    "unknown": 0
  },
  "matrix": [
    {
      "consumer": { "name": "OrderService", "version": "1.8.0" },
      "provider": { "name": "PaymentService", "version": "2.4.1" },
      "verificationResult": { "success": true, "verifiedAt": "2026-08-20T18:30:00Z" }
    },
    {
      "consumer": { "name": "MobileGateway", "version": "3.1.2" },
      "provider": { "name": "PaymentService", "version": "2.4.1" },
      "verificationResult": { "success": true, "verifiedAt": "2026-08-20T18:32:00Z" }
    }
  ]
}
```

Утиліта повертає стандартні коди завершення (exit codes), що безпосередньо керують поведінкою пайплайну автоматизації:
- **Код 0 (Success):** Усі перевірки пройдено успішно (`summary.deployable == true`), версія сумісна з усіма споживачами у цільовому середовищі, розгортання дозволено.
- **Код 1 (Verification Failed / Incompatible):** Виявлено пряму несумісність між контрактами або зафіксовано падіння верифікаційного тесту постачальника. Розгортання негайно блокується.
- **Код 2 (Missing Verification / Pending):** Контракт опубліковано, але постачальник ще жодного разу не прогнав верифікацію для цієї пари версій. Деплой зупиняється до завершення збірки постачальника.
