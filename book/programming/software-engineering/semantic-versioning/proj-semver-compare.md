# ⚙️ Порівняти дві версії SemVer: розбір рядка й старшинство за правилами специфікації

Менеджер пакетів щодня робить одну непомітну дію мільйони разів: бере два рядки на кшталт `1.0.0-rc.1` і `1.0.0`, і мусить сказати, який із них новіший. Здається дрібницею, аж поки не сядеш писати це сам — і не спіткнешся об передвипуски, де числа порівнюють числами, а не рядками, буквене старше за числове, а готовий випуск обходить будь-яке своє «майже-готове» передчуття. Тут ми напишемо робочий розбирач і порівнювач версій мовою C — справжній, компільований код, а не псевдо, — і розберемо саме те місце, де спотикаються всі.

<preknowlist>
- [Невизначена поведінка](book:programming/undefined-behavior) — чому в C арифметичне переповнення знакового цілого не «загортається за модулем», а робить програму недійсною; на цьому тримається одна з пасток порівняння числових ідентифікаторів.
</preknowlist>

## Задача: перетворити рядок на вирок «новіший / старіший / та сама»

Сформулюймо точно, бо від точності формулювання залежить уся конструкція. На вході — два рядки формату **`МАЖОР.МІНОР.ЛАТКА[-передвипуск][+метадані]`**: три обов'язкові числа через крапку, за ними необов'язковий передвипуск через дефіс (`-rc.1`) і необов'язкові метадані збірки через плюс (`+build.9`). На виході — один із трьох вироків: перша версія **менша**, **рівна** чи **більша** за другу за старшинством.

Робимо це у два кроки, і поділ між ними принциповий. Спершу **розбір**: перетворити плаский рядок на структуру, де кожне поле лежить окремо, — бо порівнювати рядок символ-за-символом наосліп якраз і породжує всі помилки. Тоді **порівняння** розібраних структур за правилами старшинства зі специфікації. Вирок віддамо в тій самій формі, що й `strcmp` чи компаратор для `qsort`: від'ємне число, нуль або додатне — сталу, з якою C-програміст працює не думаючи.

## Ідея: структура, що повторює граматику

Гарний розбирач починається не з коду, а з типу даних, у якому граматика вже видно оком. Версія має рівно чотири значущі частини — три числа ядра й, можливо, набір ідентифікаторів передвипуску. Метадані збірки в структурі не тримаємо взагалі: специфікація прямо каже, що **у старшинстві вони не беруть участі**, тож зберігати їх, щоб потім не забути проігнорувати, — тільки напрошуватися на помилку. Чого немає в структурі, того неможливо випадково врахувати.

```c
#include <ctype.h>
#include <errno.h>
#include <string.h>
#include <stdlib.h>
#include <stdbool.h>

#define SEMVER_MAX_IDS 16          // стелі з головою вистачає на будь-який реальний передвипуск

typedef enum { SEMVER_OK = 0, SEMVER_EINVAL = -1 } semver_err;

typedef struct {
    unsigned long major, minor, patch;
    int  pre_count;                // 0 → це готовий випуск, без передвипуску
    char pre[SEMVER_MAX_IDS][64];  // ідентифікатори передвипуску; числові теж тримаємо ТЕКСТОМ
    // метадані збірки навмисно не зберігаємо: на старшинство не впливають
} semver_t;
```

Одне рішення тут варте окремого слова: числові ідентифікатори передвипуску (`beta.**2**`) ми тримаємо **рядком**, а не переганяємо в число під час розбору. Це не лінь — це передбачливість, і чому саме, стане видно, коли дійдемо до їхнього порівняння: специфікація не кладе стелі на розмір числового ідентифікатора, тож будь-яке фіксоване ціле рано чи пізно на ньому переллється.

## Розбір: розрізати рядок за його роздільниками

Розбір — це послідовне зрізання хвостів. Рядок збудований так, що кожна необов'язкова частина відділена власним знаком-роздільником, і ці знаки не плутаються між собою: спершу з кінця відрізаємо метадані збірки за `+`, тоді передвипуск за `-`, а що лишилось — то ядро з трьох чисел. Порядок різання важливий: `+` завжди стоїть **після** `-` у граматиці, тож відрізавши метадані першими, ми прибираємо з розгляду єдине місце, де дефіс міг би завести в оману.

```c
// Ціле без провідних нулів ("0" — можна, "01" — ні); заразом ловить переповнення.
static semver_err parse_u(const char *p, char **end, unsigned long *out) {
    if (!isdigit((unsigned char)*p))                 return SEMVER_EINVAL;
    if (p[0] == '0' && isdigit((unsigned char)p[1])) return SEMVER_EINVAL;  // провідний нуль
    errno = 0;
    *out = strtoul(p, end, 10);
    return errno == ERANGE ? SEMVER_EINVAL : SEMVER_OK;
}

semver_err semver_parse(const char *s, semver_t *v) {
    char buf[256];
    if (!s || strlen(s) >= sizeof buf) return SEMVER_EINVAL;
    strcpy(buf, s);                     // працюємо з КОПІЄЮ: розбір псує рядок роздільниками
    memset(v, 0, sizeof *v);

    // 1. Відрізати метадані збірки за першим '+' — у старшинстві їх немає.
    char *plus = strchr(buf, '+');
    if (plus) *plus = '\0';

    // 2. Відділити передвипуск за першим '-'. Ядро — самі цифри й крапки,
    //    тож найперший '-' у рядку — це саме межа ядра й передвипуску.
    char *pre  = NULL;
    char *dash = strchr(buf, '-');
    if (dash) { *dash = '\0'; pre = dash + 1; }

    // 3. Ядро: рівно три числа через крапку, і нічого зайвого після латки.
    char *p = buf, *end;
    if (parse_u(p, &end, &v->major) || *end != '.') return SEMVER_EINVAL;
    p = end + 1;
    if (parse_u(p, &end, &v->minor) || *end != '.') return SEMVER_EINVAL;
    p = end + 1;
    if (parse_u(p, &end, &v->patch) || *end != '\0') return SEMVER_EINVAL;

    // 4. Передвипуск: ідентифікатори через '.'.
    while (pre) {
        char *dot = strchr(pre, '.');
        if (dot) *dot = '\0';
        size_t len = strlen(pre);
        if (len == 0 || len >= sizeof v->pre[0]) return SEMVER_EINVAL;  // порожній чи задовгий
        if (v->pre_count == SEMVER_MAX_IDS)       return SEMVER_EINVAL;

        // числовий ідентифікатор не сміє мати провідний нуль — інакше
        // порівняння за довжиною (нижче) брехало б: "007" виглядало б більшим за "7".
        bool digits = true;
        for (const char *c = pre; *c; ++c)
            if (!isdigit((unsigned char)*c)) { digits = false; break; }
        if (digits && pre[0] == '0' && len > 1) return SEMVER_EINVAL;

        strcpy(v->pre[v->pre_count++], pre);
        if (!dot) break;
        pre = dot + 1;
    }
    return SEMVER_OK;
}
```

Тут варто назвати три свідомі рішення. Перше — ми копіюємо рядок у власний буфер `buf` і псуємо саме копію: розбір **записує** нулі-термінатори на місце роздільників, і робити це з рядком, що прийшов ззовні, було б грубою помилкою (той рядок може бути літералом у пам'яті лише для читання чи спільним із рештою програми). Друге — `parse_u` відхиляє провідні нулі (`01`) не з педантизму, а тому, що специфікація їх забороняє, і наша ж перевірка потім спирається на цю заборону. Третє — `errno == ERANGE` після `strtoul` ловить число, що не влазить у `unsigned long`: розбір, який тихо приймає `99999999999999999999.0.0` за якесь обрізане значення, — це розбір, що бреше.

## Ядро — найлегша частина: три числа числами

Розібравши обидві версії, більшу частину порівняння робимо майже задарма. Мажор, мінор і латка порівнюють по черзі, зліва направо, і — головне — **числами, а не рядками**. Це не причіпка: як рядки, `"10"` менше за `"2"`, бо символ `'1'` іде в таблиці раніше за `'2'`; як числа — навпаки. Саме на цьому валяться саморобні порівнювачі, що наївно згодовують версії у `strcmp`.

```c
// Три-значне порівняння без жодної гілки: повертає -1, 0 або +1.
static int cmp_u(unsigned long a, unsigned long b) { return (a > b) - (a < b); }

int cmp_core(const semver_t *a, const semver_t *b) {
    int c;
    if ((c = cmp_u(a->major, b->major))) return c;   // мажор вирішив — далі не дивимось
    if ((c = cmp_u(a->minor, b->minor))) return c;
    return cmp_u(a->patch, b->patch);
}
```

Вираз `(a > b) - (a < b)` — маленька, але варта уваги ідіома. Кожне з порівнянь дає 0 або 1; їхня різниця сама складається в потрібні −1, 0, +1 без жодного `if`. Логіка «старший розряд вирішив — молодші не дивимось» — це рівно те, що робить `cmp_core`: перша ж ненульова відповідь стає остаточною.

## Серце: старшинство передвипусків, де спотикаються всі

Уся складність SemVer зібрана в одному місці — коли мажор, мінор і латка **збіглися**, і доля порівняння лягає на передвипуск. Тут специфікація ставить п'ять правил, і кожне неочевидне рівно настільки, щоб наївна реалізація його прогледіла. Випишемо їх по порядку, бо код нижче — це просто їхній буквальний переклад.

- **Готовий випуск старший за будь-який свій передвипуск.** `1.0.0-rc.1` іде **перед** `1.0.0`: передвипуск — лише передчуття, він молодший за справжній реліз. Формально: набір ідентифікаторів проти порожнього набору — порожній перемагає.
- **Далі — ідентифікатор за ідентифікатором**, зліва направо, і перша ж пара, що відрізняється, вирішує все.
- **Обидва ідентифікатори числові — порівнюй числами.** `beta.2` < `beta.11`, а не навпаки, як вийшло б за рядкового порівняння.
- **Один числовий, другий буквений — числовий завжди нижчий.** `alpha.1` < `alpha.beta`.
- **Обидва буквені — лексично, в ASCII-порядку.** `alpha` < `beta` < `rc`.
- **Спільний префікс рівний, але один набір довший — довший старший.** `1.0.0-alpha` < `1.0.0-alpha.1`.

Ось це серце двома мовами. Ліворуч — C, якою складено всю програму; праворуч — Rust, де сума-тип `Ordering` та ітератори дають ту саму логіку в іншій формі, і корисно побачити, як мова змінює обриси однакового алгоритму. Правила ті самі; різняться лише слова, якими їх записано.

```c
static bool all_digits(const char *s) {
    for (; *s; ++s) if (!isdigit((unsigned char)*s)) return false;
    return true;                         // порожніх ідентифікаторів тут не буває — відсіяв розбір
}

// Одна пара ідентифікаторів передвипуску: правила 11.4.1–11.4.3 специфікації.
static int cmp_id(const char *a, const char *b) {
    bool na = all_digits(a), nb = all_digits(b);
    if (na && nb) {                      // обидва числові — ЧИСЛАМИ, а не рядками
        size_t la = strlen(a), lb = strlen(b);
        if (la != lb) return (la > lb) - (la < lb);  // без провідних нулів довший = більший
        return strcmp(a, b);             // рівні завдовжки — лексичне дасть саме числовий порядок
    }
    if (na != nb) return na ? -1 : +1;   // числовий ЗАВЖДИ нижчий за буквений
    return strcmp(a, b);                 // обидва буквені — лексично, в ASCII-порядку
}

// Передвипуски двох версій з РІВНИМ ядром: правила 11.2 і 11.4.
int cmp_prerelease(const semver_t *a, const semver_t *b) {
    if (a->pre_count == 0 && b->pre_count == 0) return 0;   // обидва готові — рівні
    if (a->pre_count == 0) return +1;    // готовий випуск старший за передвипуск
    if (b->pre_count == 0) return -1;

    int n = a->pre_count < b->pre_count ? a->pre_count : b->pre_count;
    for (int i = 0; i < n; ++i) {
        int c = cmp_id(a->pre[i], b->pre[i]);
        if (c) return c;                 // перша ж відмінність вирішує все
    }
    // спільний префікс рівний — довший набір ідентифікаторів старший
    return (a->pre_count > b->pre_count) - (a->pre_count < b->pre_count);
}
```
```rust
use std::cmp::Ordering;

// Одна пара ідентифікаторів передвипуску: правила 11.4.1–11.4.3 специфікації.
fn cmp_id(a: &str, b: &str) -> Ordering {
    let num = |s: &str| s.bytes().all(|c| c.is_ascii_digit());
    match (num(a), num(b)) {
        // обидва числові: без провідних нулів довший = більший, за рівної довжини — лексично.
        (true, true)   => a.len().cmp(&b.len()).then_with(|| a.cmp(b)),
        (true, false)  => Ordering::Less,     // числовий ЗАВЖДИ нижчий за буквений
        (false, true)  => Ordering::Greater,
        (false, false) => a.cmp(b),           // обидва буквені — лексично, в ASCII-порядку
    }
}

// Передвипуски двох версій з РІВНИМ ядром: правила 11.2 і 11.4.
fn cmp_prerelease(a: &[&str], b: &[&str]) -> Ordering {
    match (a.is_empty(), b.is_empty()) {
        (true, true)   => Ordering::Equal,     // обидва готові — рівні
        (true, false)  => Ordering::Greater,   // готовий випуск старший за передвипуск
        (false, true)  => Ordering::Less,
        (false, false) => a.iter().copied().zip(b.iter().copied())
            .map(|(x, y)| cmp_id(x, y))
            .find(|o| o.is_ne())               // перша ж відмінність вирішує все
            .unwrap_or_else(|| a.len().cmp(&b.len())),  // рівний префікс → довший набір старший
    }
}
```

*Уся логіка передвипусків на одному аркуші. Спершу два крайні випадки (готовий проти передвипуску; рівний префікс різної довжини), інакше — пара за парою, і кожну пару за трьома правилами внизу. Найпідступніше — ліва колонка: числові ідентифікатори порівнюють числами, тож `beta.2` молодший за `beta.11`, хоч рядком `"11"` іде раніше за `"2"`.*

Найтонше місце — порівняння двох числових ідентифікаторів, і саме тут наша передбачливість зі зберіганням їх текстом окупається. Замість переганяти `"11"` у число (де на велетенському ідентифікаторі чекало б переповнення), ми порівнюємо **за довжиною**: раз провідних нулів немає — а розбір їх відкинув, — то довший рядок цифр є більшим числом, а за рівної довжини звичайне лексичне порівняння цифра-за-цифрою дає точно числовий порядок. Так ми дістаємо правильне «числами» **без жодного цілого**, а отже, без жодної стелі на розмір.

> 🔧 **Навіщо це.** Помилитися бодай в одному з цих п'яти правил — означає, що менеджер пакетів вибере не ту версію. Переплутати «числовий нижчий за буквений» — і `rc` опиниться перед `alpha`, а фінальний реліз-кандидат програє першому чорновику. Порівнювати числові ідентифікатори рядками — і `beta.11` стане молодшим за `beta.2`, тобто одинадцятий чорновик «старіший» за другий. Це не косметика: на цих порівняннях розв'язувач залежностей щодня вирішує, який саме код опиниться у твоїй збірці.

## Складання докупи

Повне старшинство — це просто ядро, а за рівного ядра — передвипуск. Метадані збірки не згадуються тут узагалі, бо ми їх навіть не зберігали: правило «ігнорувати в старшинстві» втілене не рядком коду, а **відсутністю** поля.

```c
// Повне старшинство: negative / 0 / positive, як у strcmp. Метадані збірки не беруть участі.
int semver_compare(const semver_t *a, const semver_t *b) {
    int c = cmp_core(a, b);
    return c ? c : cmp_prerelease(a, b);
}
```

## Перевірка: ланцюг зростання зі специфікації

Найкраща перевірка порівнювача версій уже написана за нас — це канонічний ланцюг зростання зі [специфікації SemVer 2.0.0](https://semver.org/), де кожна наступна версія строго старша за попередню. Якщо наш код проходить весь ланцюг, він реалізує саме ті правила, а не схожі на них.

```c
#include <assert.h>
#include <stdio.h>

static int cmp_str(const char *a, const char *b) {
    semver_t va, vb;
    assert(semver_parse(a, &va) == SEMVER_OK);
    assert(semver_parse(b, &vb) == SEMVER_OK);
    return semver_compare(&va, &vb);
}

int main(void) {
    // Числами, не рядками — класична пастка саморобних порівнянь:
    assert(cmp_str("1.2.0", "1.10.0") < 0);          // 2 < 10 як числа
    assert(cmp_str("1.10.0", "1.2.0") > 0);

    // Канонічний ланцюг зростання зі специфікації — кожен строго менший за наступний:
    const char *chain[] = {
        "1.0.0-alpha", "1.0.0-alpha.1", "1.0.0-alpha.beta",
        "1.0.0-beta",  "1.0.0-beta.2",  "1.0.0-beta.11",
        "1.0.0-rc.1",  "1.0.0",
    };
    for (int i = 0; i + 1 < (int)(sizeof chain / sizeof *chain); ++i)
        assert(cmp_str(chain[i], chain[i + 1]) < 0);

    // Окремо — три місця, де саморобні порівнювачі найчастіше брешуть:
    assert(cmp_str("1.0.0-beta.2",  "1.0.0-beta.11")   < 0);  // числове: 2 < 11, не "11" < "2"
    assert(cmp_str("1.0.0-alpha.1", "1.0.0-alpha.beta") < 0);  // числовий нижчий за буквений
    assert(cmp_str("1.0.0-rc.1",    "1.0.0")            < 0);  // передвипуск нижчий за випуск

    // Метадані збірки ігноруються — це та сама версія за старшинством:
    assert(cmp_str("1.0.0+build.9", "1.0.0+build.5")       == 0);
    assert(cmp_str("1.0.0+exp.sha.5114f85", "1.0.0")       == 0);

    puts("усі перевірки пройдено");
    return 0;
}
```

Кожен `assert` тут — це одне з правил, зафіксоване як виконуваний факт. Ланцюг перевіряє їх у зчепленні; окремі рядки під ним б'ють точково по трьох найпопулярніших помилках. Разом вони кажуть: реалізація не просто «схожа на SemVer», а робить рівно те, що написано в специфікації.

## Складність: лінійна, і нічого понад

Порахуймо чесно, скільки це коштує. Розбір читає рядок **один раз** — `strchr` пробігає його, `strtoul` пробігає числа, цикл передвипуску пробігає ідентифікатори, і жоден символ не оглядається двічі. Отже розбір — це `O(L)` від довжини рядка `L`. Порівняння теж лінійне: ядро — три сталі порівняння, передвипуск — прохід по щонайбільше `min(k_a, k_b)` ідентифікаторах, і кожна пара порівнюється за час, пропорційний довжині коротшого. Разом усе впирається в `O(L)` — лінію від розміру входу.

```
розбір:      один прохід по рядку           →  O(L)
порівняння:  ядро (стала) + пара за парою    →  O(довжини передвипуску)
─────────────────────────────────────────────────────────────────────
разом:  лінійно від довжини рядка
```

Це найкраще, на що взагалі можна сподіватися: щоб винести вирок, версію треба бодай раз прочитати, а прочитати її — це вже `O(L)`. Жодного повторного блукання тим самим рядком, жодного вкладеного циклу, що перечитував би ідентифікатори. Порівняння версій — операція, яку менеджер пакетів робить тисячами під час розв'язання залежностей, і те, що кожне коштує рівно одне читання, — саме те, що робить розв'язання взагалі здійсненним.

## Пастки: де наївний порівнювач починає брехати

Написане вище працює й проходить канонічний ланцюг — але кілька спрощень у чужих реалізаціях (а часом і в цій, якщо неуважно її розширювати) обертаються тихими помилками. Назвімо головні, бо саме на них порівнювачі версій найчастіше й розходяться між собою.

**Числовий ідентифікатор не влазить у ціле.** Спокуса очевидна: щоб порівняти `"2"` і `"11"` числами, перегнати обидва в `int` і відняти. Пастка подвійна. По-перше, специфікація **не кладе стелі** на числовий ідентифікатор — `1.0.0-0.0.0.0.0.99999999999999999999` цілком законний, — і будь-яке фіксоване ціле на ньому переллється, віддавши сміття замість числа. По-друге, навіть коли числа влазять, порівняння **відніманням** (`atoi(a) - atoi(b)`) саме переливається, щойно різниця виходить за межі `int`: а переповнення знакового цілого в C — це не «загорнулось за модулем», а [невизначена поведінка](book:programming/undefined-behavior), тобто програма стає недійсною цілком. Саме тому наш `cmp_id` порівнює числові ідентифікатори за довжиною й лексично, **не переганяючи їх у ціле** й тим уникаючи обох країв ями.

**Провідні нулі ламають порівняння за довжиною.** Трюк «довший рядок цифр = більше число» чесний рівно доти, доки немає провідних нулів: `"007"` за довжиною виглядало б більшим за `"7"`, хоча це те саме число (та ще й недійсне за специфікацією). Ось чому розбір **відхиляє** числові ідентифікатори з провідним нулем — не з педантизму, а щоб пізніша оптимізація лишалась правдивою. Приймати такий вхід і потім плутатись у порівнянні — гірше, ніж чесно відмовити на вході.

**Розбір псує вхідний рядок.** Наш `semver_parse` розставляє нулі-термінатори на місце `+`, `-`, `.` — тобто **записує** в буфер. Робити це просто з переданим рядком означало б зіпсувати чужу пам'ять, а якщо рядок — літерал у сегменті лише для читання, ще й впасти на місці. Тому ми копіюємо в локальний `buf` і ріжемо копію. Це не дрібниця смаку: розбирачі, що мутують вхід, — джерело найпідступніших помилок, коли той самий рядок десь іще потрібен цілим.

**Порожні й криві ідентифікатори.** `1.0.0-` (дефіс без нічого), `1.0.0-alpha..1` (порожній ідентифікатор між крапками), `1.0.0-alpha_1` (недозволений символ) — усе це недійсний SemVer, і чесний розбір має його **відхилити**, а не мовчки проковтнути. Ми ловимо порожні ідентифікатори (`len == 0`) і задовгі, але навмисно не перевіряємо повний склад символів (лише `[0-9A-Za-z-]` дозволено специфікацією) — це свідома межа прикладу, яку в бойовому коді варто закрити. Головне — знати, де твій розбір поблажливий, і сказати про це вголос.

**Регістр і нормалізація.** Лексичне порівняння в ASCII-порядку робить `Alpha` і `alpha` **різними** ідентифікаторами (велика `A` — це 65, мала `a` — 97, тож `Alpha` вийде «молодшим»). Специфікація саме цього й вимагає — порівняння чутливе до регістру, — але автори тегів іноді очікують іншого, і розбіжність «мій `RC` проти чийогось `rc`» породжує тихо неправильний порядок. Нічого «виправляти» тут не треба: правильно — робити рівно те, що каже специфікація, і не піддаватися спокусі «полагодити» регістр самотужки.

## Від порівняння до діапазонів

Сам по собі `semver_compare` — це цеглина, а не будинок. Справжній розв'язувач залежностей надбудовує над ним ще один шар: споживач майже ніколи не прибиває версію намертво, а задає **діапазон** — `^1.2.3`, `~1.2.3`, `>=1.2.0 <2.0.0`, — і розв'язувач мусить із багатьох доступних версій вибрати найвищу, що в цей діапазон вкладається. Кожен такий діапазон розкладається на **інтервал** із нижньою й верхньою межею: каретка `^1.2.3` — це `>=1.2.3` і `<2.0.0`, тильда `~1.2.3` — `>=1.2.3` і `<1.3.0`. І вся перевірка «чи потрапляє версія `v` в інтервал» зводиться до двох викликів того самого `semver_compare`: `compare(v, low) >= 0` і `compare(v, high) < 0`. Побудований чесно, порівнювач стає тим фундаментом, на якому решта — сортування, вибір найвищої, задоволення діапазону — вже тривіальна надбудова: усе це лише повторні запити «яка з двох новіша», на які ми вже вміємо відповідати за одне читання рядка.
