# Assert і паніка

Помітивши помилку, інженер вибирає **силу відповіді** — від «поверни код і дай викликачу вирішити» до «зупини все негайно». Помилитися дорого в обидва боки: занадто гучно — пристрій падає від дрібниці; занадто тихо — їдемо далі зі зіпсованим станом у прірву. Два найгучніші щаблі мають власні назви й власні правила: **assert** (англ. *to assert* — «стверджувати», від латин. *asserere*, «заявляти, обстоювати») і **паніка** (англ. *panic*, від грец. *πανικός* — «безтямний страх», тут: аварійна зупинка системи).

**Походження збою, а не його тяжкість.** Силу відповіді диктує не те, наскільки страшно виглядає симптом, а те, **звідки** збій узявся. Три джерела — три рівні. (1) **Код повернення / статус** — «це очікувана, відновна ситуація, хай вирішує викликач»: давач не відповів, файл не знайдено, буфер повний, мережа недоступна. Зовнішній світ ненадійний — це норма, не баг. (2) **Assert** — «це порушення припущення програміста; такого не має бути НІКОЛИ»: NULL-вказівник там, де він гарантовано не NULL, індекс за межами масиву, автомат у забороненому стані. Assert стверджує **інваріант** (англ. *invariant*, від латин. *in-* «не» + *variare* «змінюватися» — умову, яка має триматися завжди) і при хибі впадає гучно й одразу — це робочий інструмент [проєктування за контрактом](book:programming/design-by-contract), де такі умови задають явно. (3) **Паніка / reset** — «стан невідновний, далі працювати небезпечно, рятуємося перезапуском»: пошкоджена критична структура в RAM, виявлене псування стеку, ситуація, де будь-яка дія може зробити гірше.

![Три рівні реакції: одне питання про походження збою, три різні відповіді](/book/programming/software-engineering/assert-panic/img/three-levels.svg)

*Одне питання — «звідки збій?» — розгалужується на три відповіді. Очікувана ситуація зовнішнього світу → код повернення, хай вирішує викликач. Порушене припущення коду → assert зі стопом і вказівкою на файл та рядок. Невідновний стан → паніка й reset. Рівень добирають за походженням збою, не за тим, як гучно він виглядає.*

**Критерій вибору — одне запитання.** Чи ситуація **очікувана** в нормальній роботі? Давач може не відповісти — це нормально (погані контакти, зайнята шина, тайм-аут), тож код повернення. Хибний NULL-вказівник у таблиці обробників — це вже баг ініціалізації, якого «не має бути», тож assert. Пошкоджена контрольна сума критичної структури в RAM — стан, де продовжувати небезпечно, тож паніка. Коротко: зовнішній світ ненадійний → код повернення; внутрішня логіка зламалась → assert або паніка.

Той самий симптом може лягти на різні рівні — і рівень визначає **джерело**, не симптом. Порожній буфер після читання з мережі — очікувано (пакет загубився), тож код повернення; порожній буфер після виклику власної функції, яка **зобов'язана** його заповнити, — порушене припущення, тож assert. Різниця не в тому, що сталося, а в тому, **хто за це відповідає**: ненадійний зовнішній світ чи ваш власний код, який мав гарантувати результат. Тому перше, що варто запитати про кожну перевірку: «чи могло це статися за абсолютно правильного коду й заліза?» Якщо так — це не баг, це світ, і реакція м'яка. Якщо ні — це баг, і ховати його за кодом повернення означає лише відсунути падіння подалі від причини.

> 🔧 **Навіщо це.** Плутати рівні дорого в обидва боки. Assert на те, що буває в нормі (давач відвалився), → пристрій падає від звичайної дрібниці, клієнт незадоволений. Код повернення там, де стан уже зіпсовано, → їдемо далі в прірву й падаємо де-небудь непередбачувано, за «кілометр» від причини. Правильний рівень робить пристрій і стійким, і чесним водночас.

**`assert` зсередини й чесно.** Макрос `assert(expr)` (оголошений у `<assert.h>`) розгортається приблизно в таке:
```c
if (!(expr)) {
    fprintf(stderr, "Assertion failed: %s, file %s, line %d\n",
            #expr, __FILE__, __LINE__);
    abort();
}
```
Перевіряє інваріант; якщо хибний — друкує сам вираз, файл і рядок, тоді кличе `abort()`. У режимі релізу, де визначено `NDEBUG` (англ. *no debug*), препроцесор вирізає весь рядок цілком — і тут криється **головна пастка**:

```c
// НЕБЕЗПЕЧНО: init() зникне разом із assert у релізі
assert(init_peripheral() == ESP_OK);   // NDEBUG → рядок вирізано → init не викликано!

// БЕЗПЕЧНО: перевірка і робота розділені
esp_err_t err = init_peripheral();
assert(err == ESP_OK);                 // лише перевірка — ok вирізати в релізі
```

Якщо `init_peripheral()` має побічний ефект (а ініціалізація периферії завжди має), то в релізі пристрій стартує без ініціалізації й падає «загадково». Правило незмінне: в `assert` — лише **чиста перевірка**, ніякої роботи.

![Пастка assert: робота, схована всередині, зникає в релізі під NDEBUG](/book/programming/software-engineering/assert-panic/img/ndebug-pitfall.svg)

*Дві лінії часу для одного коду. Зліва, в debug, `assert(init() == OK)` працює: init викликано, перевірку зроблено. Справа, у релізі під NDEBUG, препроцесор вирізає весь рядок разом із викликом — init не відбувається, і система стартує неініціалізованою. Звідси правило: усередині assert лише чиста перевірка, жодної роботи з побічним ефектом.*

**Що таке «паніка» на ESP32 конкретно.** При критичному збої — `HardFault` ядра, переповнення стеку, спрацьований сторожовий таймер чи явний виклик `abort()` / `esp_system_abort()` — ESP-IDF запускає panic handler: виводить у консоль зворотне трасування стека й причину збою, а далі, залежно від налаштування menuconfig, або робить reset, або зависає в нескінченному циклі (щоб під'єднати JTAG), або записує [core dump у Flash](root:embedded/core-dump) для подальшого аналізу. На відміну від «великих» ОС, де падіння одного процесу не б'є інші, на МК без блока керування пам'яттю (MMU) падіння будь-якого коду = падіння всього. Тому паніка на ESP32 майже завжди веде до reset — і це [виправдана стратегія перезапуску](book:programming/reboot-strategy).

![Паніка на ESP32: різні тригери збігаються в один handler, далі — налаштована реакція](/book/programming/software-engineering/assert-panic/img/panic-flow.svg)

*Різні причини — HardFault, переповнення стеку, abort/assert, сторожовий таймер — збігаються в один panic handler, який друкує трасування й причину. Звідти три налаштовані шляхи: штатний reset, зависання для під'єднання JTAG або запис core dump у Flash. На МК без MMU падіння будь-якого коду валить усе, тож штатний шлях — майже завжди reset.*

**Assert у продуктивному коді.** Вимкнути assert через `NDEBUG` здається розумним (швидше, менше коду), але баги тихнуть. Лишити увімкненими — ловить, але reset у полі непередбачений. Зрілий компроміс: **критичні інваріанти залишати увімкненими навіть у релізі** (керований reset із відомою причиною кращий за невизначену роботу на зіпсованому стані), а «дорогі» перевірки — обхід усього масиву задля контролю цілісності — лишати тільки під `#ifdef DEBUG`.

Чому керований reset кращий за «просто їхати далі»: коли інваріант уже порушено, кожна наступна інструкція працює на стані, якому не можна вірити, і наслідок непередбачуваний — від тихо неправильного виходу до псування сусідніх даних. Reset повертає пристрій у єдиний стан, про який ми точно знаємо, що він добрий, — початковий. Ціна — секунда недоступності; виграш — пристрій ніколи не діє на зламаному припущенні. Тому навіть у фінальній прошивці дешевий контроль критичного інваріанта лишають живим: він коштує одне порівняння на такт, а рятує від найдорожчого — мовчазної роботи на зіпсованому стані.

**Worked-приклад.** Одна функція обробки команди — три помилки трьох різних рівнів:

```c
#include "esp_log.h"
#include <assert.h>
static const char *TAG = "cmd_handler";

// Таблиця обробників — заповнюється при ініціалізації (не NULL!)
typedef void (*cmd_fn_t)(const uint8_t *payload, size_t len);
static cmd_fn_t s_handlers[CMD_COUNT];

// Критична структура зі своєю контрольною сумою
typedef struct {
    uint32_t magic;
    uint32_t value;
    uint32_t crc;
} critical_state_t;
extern critical_state_t g_state;  // у RAM

esp_err_t handle_command(uint8_t cmd_id, const uint8_t *payload, size_t len) {
    // Рівень 1: ОЧІКУВАНА ситуація — невідома команда від користувача
    if (cmd_id >= CMD_COUNT) {
        ESP_LOGW(TAG, "unknown cmd 0x%02x", cmd_id);
        return ESP_ERR_NOT_SUPPORTED;   // код повернення — викликач вирішить
    }

    // Рівень 2: ПОРУШЕННЯ ПРИПУЩЕННЯ — обробник мусить бути заповнений
    // (баг ініціалізації, якщо NULL)
    assert(s_handlers[cmd_id] != NULL);

    // Рівень 3: НЕВІДНОВНИЙ СТАН — структура в RAM зіпсована
    uint32_t expected_crc = crc32_calc(&g_state, offsetof(critical_state_t, crc));
    if (g_state.crc != expected_crc || g_state.magic != STATE_MAGIC) {
        ESP_LOGE(TAG, "state corrupt! crc=0x%08lx exp=0x%08lx", g_state.crc, expected_crc);
        esp_system_abort("state corrupt");   // паніка → reset
    }

    s_handlers[cmd_id](payload, len);
    return ESP_OK;
}
```

Той самий «збій» різного походження дістає різну відповідь. Невідома команда — цілком нормально, хай викликач поверне користувачу помилку. NULL-обробник — баг, якого не має бути; assert одразу вкаже на рядок у відладчику. Зіпсована структура — критичний стан, де продовжувати небезпечно; паніка з відомою причиною й перезапуск.

> ⚙️ Апаратний родич паніки — [HardFault ядра](book:programming/hardfault), що зберігає зворотне трасування стека й регістри в момент збою; там же — що саме ядро кладе в стек при збої і як це читати. Збережений [core dump у Flash](root:embedded/core-dump) дає змогу проаналізувати збій уже після перезапуску.

Assert і паніка — це реакція **в момент** збою. Доповнює їх [захисне програмування](book:programming/defensive-programming), яке перевіряє припущення **до того**, як на них покладемось, і не дає збоєві статися взагалі.
