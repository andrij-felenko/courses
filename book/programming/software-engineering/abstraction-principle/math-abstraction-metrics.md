# 🧮 Метрики абстрактності та баланс головної послідовності

Часто розробники сперечаються про абстракції суто інтуїтивно: «тут забагато інтерфейсів» або «цей модуль занадто жорсткий для змін». Проте в інженерії програмного забезпечення існує математичний апарат, що дозволяє виміряти структурний рівень абстракції компонентів і дати об'єктивну числову оцінку архітектурного балансу.

Цю систему метрик запропонував Роберт Мартін (Robert C. Martin). Вона пов'язує ступінь абстрактності пакета з конфігурацією його залежностей і визначає так звану **головну послідовність** (англ. *Main Sequence*) — лінію оптимального співвідношення між гнучкістю та стабільністю.

## Визначення базових метрик пакета

Розглянемо архітектурний модуль (пакет, бібліотеку чи простір імен) як орієнтований граф, вершинами якого є типи даних (класи, структури, інтерфейси), а ребрами — статичні та динамічні залежності між ними.

### 1. Абстрактність (Abstractness, A)

Метрика вимірює відношення кількості абстрактних типів до загальної кількості оголошених у модулі типів:

```
A = Na / Ntotal
```

де:
- `Na` — кількість суто абстрактних типів (інтерфейсів, чисто віртуальних класів, трейтів, концептів без конкретних тіл);
- `Ntotal` — загальна кількість типів (структур, класів, перелічень, інтерфейсів), визначених у цьому модулі.

Значення метрики строго нормоване в діапазоні від 0 до 1:
- `A = 0` — модуль є повністю **конкретним**. Він складається виключно з реалізацій і структур даних; жодного контракту не виділено назовні;
- `A = 1` — модуль є повністю **абстрактним**. Він містить лише сигнатури операцій, протоколи та інтерфейси без жодного рядка коду втілення;
- `0 < A < 1` — гібридний модуль, що містить як інтерфейси, так і їхні базові чи типові реалізації.

### 2. Нестабільність (Instability, I)

Нестабільність у контексті теорії графів показує, наскільки легко модуль піддається зовнішньому впливу та наскільки вільно його можна модифікувати без ризику зламати чужий код. Вона базується на двох видах зчеплення:

- **Аферентне зчеплення (Afferent Coupling, Ca):** кількість зовнішніх класів або модулів, які **залежать від цього модуля** (кількість стрілок, що входять у модуль). Високе `Ca` означає, що модуль несе високу відповідальність: будь-яка зміна його поведінки зачепить багатьох споживачів.
- **Еферентне зчеплення (Efferent Coupling, Ce):** кількість зовнішніх класів або модулів, **від яких залежить цей модуль** (кількість стрілок, що виходять з модуля). Високе `Ce` означає, що модуль залежить від зовнішнього середовища: зміна будь-якого зовнішнього типу змусить перекомпілювати цей модуль.

Формула нестабільності обчислює частку вихідних залежностей у загальному потоці зв'язків:

```
I = Ce / (Ca + Ce)
```

Значення `I` змінюється від 0 до 1:
- `I = 0` — модуль є **максимально стабільним** (незалежним). Від нього залежить багато компонентів системи (`Ca > 0`), але сам він не імпортує жодного стороннього модуля (`Ce = 0`). Такий модуль дуже важко змінювати, оскільки його контракт зацементований чужими очікуваннями;
- `I = 1` — модуль є **максимально нестабільним** (залежним). Він спирається на безліч зовнішніх бібліотек (`Ce > 0`), але від нього самого не залежить жоден інший компонент системи (`Ca = 0`). Такий модуль на периферії можна безпечно змінювати, переписувати або викидати в будь-який момент.

## Граничні випадки формули нестабільності

Окремої уваги заслуговує граничний випадок ізольованого модуля, для якого `Ca = 0` і `Ce = 0` (модуль не має жодних зовнішніх залежностей і сам ніким не викликається, наприклад, утилітарна функція або мертвий код). У такому разі знаменник перетворюється на нуль `0 / 0`.

В інженерному аналізі для повністю ізольованих модулів приймається домовленість:
- Якщо модуль містить самостійні алгоритми без зовнішніх залежностей (наприклад, чиста математична функція обчислення CRC), його вважають стабільним ядром з `I = 0`.
- Якщо модуль є тупиковим кінцевим скриптом чи експериментом, його вважають граничним клієнтом з `I = 1`.

## Головна послідовність і баланс проектування

Головний закон проектування залежностей стверджує: **що вища стабільність модуля (менше `I`), то більш абстрактним він має бути (більше `A`)**.

Чому це так? Якщо модуль має `I = 0`, від нього залежить уся програма. Якщо при цьому він повністю конкретний (`A = 0`), ми потрапляємо в пастку: ми не можемо внести в нього жодної зміни без ризику зламати пів проекту. Єдиний порятунок для стабільного модуля — бути абстрактним (складатися з інтерфейсів), щоб нову функціональність можна було додавати через підстановку нових реалізацій ззовні згідно з принципом відкритості/закритості (OCP).

І навпаки: якщо модуль має `I = 1`, від нього не залежить ніхто. У такому модулі плодити інтерфейси безглуздо: конкретний код тут нікому не шкодить, оскільки зміна цього модуля є локальною і дешевою.

Цей ідеальний компроміс виражається лінійним рівнянням:

```
A + I = 1
```

![Головна послідовність Мартіна: баланс між абстрактністю A та нестабільністю I](/book/programming/software-engineering/abstraction-principle/img/main-sequence.svg)

*Головна послідовність Мартіна. Зелена пряма лінія A + I = 1 задає оптимальний баланс системи. Що ближче точка модуля до цієї прямої, то гармонійніше збалансовані його гнучкість та стабільність.*

### Відхилення від балансу (Normalized Distance, D)

Щоб кількісно оцінити якість архітектури, розраховують нормалізовану відстань `D` від точки модуля `(I, A)` до прямої головної послідовності:

```
D = |A + I - 1|
```

Геометрично величина `D` дорівнює проекції точки на нормаль до лінії `A + I = 1`, масштабованій до одиничного відрізка:
- `D = 0` — модуль розташований рівно на головній послідовності (ідеальний архітектурний стан);
- `D < 0.2` — чудовий стан, відхилення в межах природної інженерної похибки;
- `D > 0.5` — критичне відхилення, модуль знаходиться в зоні високого архітектурного ризику.

### Анатомія небезпечних зон

Площина `(I, A)` містить два протилежні кути, де абстракція ламається:

1. **Зона болю (Zone of Pain, `A ≈ 0, I ≈ 0`):**
   Модуль має нульову абстрактність і нульову нестабільність. Від нього залежать усі, але сам він жорстко зашитий на конкретну структуру даних або бібліотеку.
   - *Типовий приклад:* монолітна глобальна структура конфігурації `GlobalSettings`, поля якої напряму читають 80 різних файлів проекту, або сира таблиця бази даних без репозиторію.
   - *Наслідок:* будь-яка спроба оптимізувати пам'ять чи змінити тип поля призводить до каскадного зламу всієї програми.
2. **Зона марноти (Zone of Uselessness, `A ≈ 1, I ≈ 1`):**
   Модуль є повністю абстрактним, але водночас повністю нестабільним: від нього не залежить жоден компонент системи, а сам він залежить від інших.
   - *Типовий приклад:* інтерфейс `IOrderValidator`, створений для єдиного класу без наміру коли-небудь мати іншу реалізацію, або набір узагальнених абстракцій, які забули підключити до реальної логіки.
   - *Наслідок:* надлишковий когнітивний шум, збільшення часу компіляції та зайві шари викликів, які нічого не захищають.

## Практичний розрахунок двох модулів підсистеми

Порівняймо два модулі реальної бортової системи зв'язку: модуль контрактів транспорту `TelemetryProtocol` та модуль графічного виводу налагоджувальних повідомлень `DebugUiSink`.

### Модуль 1: `TelemetryProtocol` (Ядро системи)

**Вхідні метрики графа:**
- Загальна кількість типів: `Ntotal = 10`
- Кількість абстрактних інтерфейсів: `Na = 8` (`ITransport`, `IPacketFramer`, `IChecksum`, `ISerializer`, `IHeaderCodec`, `IStreamSink`, `IValidator`, `IEntropySource`)
- Кількість конкретних структур (дескриптори та помилки): 2
- Зовнішні модулі, що імпортують цей контракт: `Ca = 18`
- Зовнішні залежності самого модуля: `Ce = 1` (лише базові числові типи ядра)

**Покрокове обчислення:**

```
A = Na / Ntotal
  = 8 / 10                [8 інтерфейсів з 10 типів]
  = 0.80                  [абстрактність A = 0.8]

I = Ce / (Ca + Ce)
  = 1 / (18 + 1)          [1 вихідне зчеплення з 19 загальних]
  = 1 / 19                [ділення]
  ≈ 0.053                 [висока стабільність I = 0.05]

A + I = 0.80 + 0.053
      = 0.853             [сума координат]

D = |A + I - 1|
  = |0.853 - 1.000|       [відхилення від головної послідовності]
  = 0.147                 [нормалізована відстань D = 0.15]
```

**Оцінка:** Модуль `TelemetryProtocol` з `D = 0.15` розташований у безпечному коридорі головної послідовності. Його висока стабільність (`I = 0.05`) надійно компенсована високою абстрактністю (`A = 0.80`).

### Модуль 2: `LegacySettingsStore` (Невдалий моноліт)

**Вхідні метрики графа:**
- Загальна кількість типів: `Ntotal = 12`
- Кількість абстрактних інтерфейсів: `Na = 0` (всі 12 типів — жорсткі конкретні класи з прямим доступом до файлів)
- Кількість споживачів: `Ca = 24` (24 модулі читають налаштування напряму)
- Зовнішні залежності: `Ce = 2` (файлова система та системний реєстр)

**Покрокове обчислення:**

```
A = Na / Ntotal
  = 0 / 12                [жодного інтерфейсу]
  = 0.00                  [абстрактність A = 0.0]

I = Ce / (Ca + Ce)
  = 2 / (24 + 2)          [2 вихідні залежності з 26]
  = 2 / 26                [ділення]
  ≈ 0.077                 [дуже висока стабільність I = 0.08]

A + I = 0.00 + 0.077
      = 0.077             [сума координат]

D = |A + I - 1|
  = |0.077 - 1.000|       [відхилення від балансу]
  = 0.923                 [критична відстань D = 0.92]
```

**Оцінка:** Значення `D = 0.92` демонструє глибоке падіння в **Зону болю**. Модуль є критичною точкою відмови всієї системи: оскільки 24 модулі жорстко прив'язані до конкретних полів `LegacySettingsStore`, будь-який рефакторинг збереження налаштувань паралізує розробку. Виправлення полягає у винесенні інтерфейсу `ISettingsProvider` та переведенні клієнтів на залежність від абстракції.
