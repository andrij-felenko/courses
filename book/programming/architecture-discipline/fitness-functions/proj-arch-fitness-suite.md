# ⚙️ Набір архітектурних фітнес-функцій: граф залежностей як ворота складання

Уяви програму-воротаря. На кожен коміт, ще перед повільними тестами, прокидається маленький інструмент, читає все дерево вихідних файлів, будує з нього **один** об'єкт — граф залежностей модулів — і ставить йому три питання. Якщо бодай на одне відповідь «так, правило порушено», він друкує точне ребро-порушника, виходить із ненульовим кодом, і складання падає. Оце і весь виріб. Решта — деталі. Але саме в деталях він живе або вмирає.

Бо три ці питання, як теорія графів, до образливого прості — досяжність, порівняння рівнів, пошук циклу: кожне — вправа з першого курсу, кожне коштує один прохід. Якби вся складність сиділа в алгоритмі, цей текст був би виноскою на три рядки. Справжня складність — у чотирьох інших місцях: побудувати **чесний** граф із неохайних живих імпортів; тримати перевірку такою швидкою, щоб вона бігла буквально на кожен коміт; **назвати винуватця** так, щоб червоне складання було вказівкою, а не загадкою; і не залити ворота кров'ю першого ж дня на legacy-системі, де порушень уже двісті. Цей проєкт будує інструмент і кладе всю вагу рівно туди.

Терміни, якими користуємося: **граф** (грец. γράφω — пишу, креслю) — вузли й ребра між ними; **вузол** тут — модуль (лат. modulus — мірка, вузлик), тобто пакет чи тека верхнього рівня; напрямлене **ребро** A → B читаємо «A прямо залежить від B» (імпортує, інклюдить, вимагає). Усе далі — операції над цим одним графом.

## Граф із імпортів: єдина структура, з якої все виростає

Граф зберігаємо найдешевше — **списком суміжності** (англ. *adjacency* — сусідство): відображення «модуль → множина модулів, від яких він прямо залежить». Множина, а не список, бо той самий імпорт трапляється в коді десятки разів, а нас цікавить сам факт ребра, не його кратність.

:::tabs
```cpp
#include <string>
#include <vector>
#include <utility>
#include <unordered_map>
#include <unordered_set>

using Graph = std::unordered_map<std::string, std::unordered_set<std::string>>;

// граф: модуль → модулі, від яких він ПРЯМО залежить
Graph build_graph(const std::vector<std::pair<std::string, std::string>>& edges) {
    Graph g;
    for (const auto& [src, dst] : edges) {
        g[src];                               // вузол існує навіть без вихідних ребер
        g[dst];
        if (src != dst)                       // самопосилання модуля на себе — не ребро
            g[src].insert(dst);
    }
    return g;
}
```
```python
# граф: модуль → модулі, від яких він ПРЯМО залежить
def build_graph(edges: list[tuple[str, str]]) -> dict[str, set[str]]:
    g: dict[str, set[str]] = {}
    for src, dst in edges:
        g.setdefault(src, set())          # вузол існує навіть без вихідних ребер
        g.setdefault(dst, set())
        if src != dst:                    # самопосилання модуля на себе — не ребро
            g[src].add(dst)
    return g
```
```typescript
// граф: модуль → модулі, від яких він ПРЯМО залежить
type Graph = Map<string, Set<string>>;

function buildGraph(edges: [string, string][]): Graph {
  const g: Graph = new Map();
  const node = (m: string) => g.get(m) ?? g.set(m, new Set()).get(m)!;
  for (const [src, dst] of edges) {
    node(src); node(dst);                 // вузол існує навіть без вихідних ребер
    if (src !== dst) node(src).add(dst);  // самопосилання модуля на себе — не ребро
  }
  return g;
}
```
:::

Зверни увагу на дві дрібниці, що вже тут відсіюють хибні тривоги: ми заводимо вузол навіть без ребер (щоб самотній модуль не зник із перевірки) і викидаємо самопосилання `src == dst` (файл модуля імпортує сусідній файл того самого модуля — усередині це не міжмодульне ребро). Обидві — не з теорії графів, а з того, як виглядають справжні репозиторії.

А звідки береться список `edges`? Оце і є той складний крок, який усі недооцінюють. Побудова графа — не теорія, а **розбір коду**, і він завжди прив'язаний до мови, яку аналізуємо. Для Python найчесніший спосіб — не регулярка, а справжнє синтаксичне дерево через модуль `ast` (англ. *abstract syntax tree*): він бачить рівно те, що бачить інтерпретатор, і не спіткнеться на рядку, де слово `import` трапилось у коментарі чи в стрічці.

```python
import ast, pathlib

def extract_edges(root: str, internal: set[str]) -> list[tuple[str, str]]:
    edges = []
    for path in pathlib.Path(root).rglob("*.py"):
        module = path.relative_to(root).parts[0]         # верхня тека = модуль
        tree = ast.parse(path.read_text(encoding="utf-8"), filename=str(path))
        for node in ast.walk(tree):
            if isinstance(node, ast.Import):             # import a.b, c
                targets = [alias.name for alias in node.names]
            elif isinstance(node, ast.ImportFrom) and node.module:  # from a.b import c
                targets = [node.module]
            else:
                continue
            for t in targets:
                dep = t.split(".")[0]                    # 'db.pool' → 'db'
                if dep in internal:                      # лише СВОЇ модулі
                    edges.append((module, dep))
    return edges
```

Тут уже видно три рішення, кожне з яких — потенційна діра. **Ґранулярність**: ми згортаємо файл до його верхньої теки (`parts[0]`), тобто граф — на рівні модулів, не файлів; хочеш дрібніше — бери два сегменти, але тоді граф росте. **Фільтр `internal`**: чужі бібліотеки (стандартна бібліотека, пакети з реєстру) відкидаємо — граф про **твою** структуру, а не про півсвіту залежностей. **Резолюція шляху**: `'db.pool' → 'db'` бере верхній пакет; якщо в тебе перейменування шляхів (аліаси в `tsconfig`, namespace-пакети Python), цей рядок доведеться зробити розумнішим, бо інакше ребро проґавиться.

У світі TypeScript структура тулу та сама, а розбір інший: замість `ast` беруть компіляторний API (`ts.createSourceFile` або обгортку `ts-morph`), обходять вузли `ImportDeclaration` і читають `moduleSpecifier`. Регулярка `/from\s+['"]([^'"]+)['"]/` теж дасть щось на око, але вона сліпа до реекспортів `export * from`, до динамічного `import()` і до типових-лише імпортів — тому в проді парсять деревом, а регулярку лишають хіба для чернетки. Головне тут одне: **щойно граф зібрано, він — просто дані**, і всі три перевірки нижче вже не знають і не хочуть знати, якою мовою написаний код, що його породив.

Ось наш робочий приклад — маленький сервіс на сім модулів, розкладений за шарами (рівень: `util`=0, `db`=1, домени `orders`/`billing`/`report`=2, `web`=3; `legacy`=0 — застарілий листок):

```
web     → orders, billing, report
report  → db, util, orders
orders  → db, util
billing → db, util, legacy
db      → util
legacy  → util
util    → (нічого)
```

Цей граф здоровий: усі ребра ведуть униз або вбік (жодне не пнеться на вищий рівень), циклів немає, а домени `orders` й `billing` одне одного не дістають. Тепер зробімо три різні лихі коміти — кожен додасть **одне** ребро, і кожне впіймає рівно своя перевірка.

![Три панелі: ліворуч заборонена залежність — нове ребро db → legacy робить так, що orders через db досягає legacy; посередині порушення шарів — ребро legacy(рівень 0) → report(рівень 2) веде вгору крізь шар; праворуч цикл — orders і report починають імпортувати одне одного, злипаючись у взаємному імпорті](img/three-regressions.svg)
*Три регресії в одному графі, кожна ловиться окремим питанням. Ліва — досяжність: нове ребро db → legacy відкриває шлях orders → db → legacy, хоча саме ребро йде вниз і циклу не творить. Середня — частковий порядок: ребро від нижчого рівня до вищого. Права — цикл: два модулі того самого шару починають посилатися одне на одного. Три різні хвороби — три різні детектори.*

## Перевірка 1 — заборонена залежність: питання про досяжність

Правило «модуль X не сміє залежати від модуля Y» майже ніколи не про пряме ребро. Пряме ребро видно очима в рев'ю; підступне — це коли X дістає Y **через ланцюжок**, якого ніхто не тримав у голові: X → щось → щось → Y. Тому чесне питання — не «чи є ребро X → Y», а «чи є **шлях** X → … → Y», тобто питання про **досяжність** (англ. *reachability*). А досяжність — це просто обхід графа від X: усе, куди можна дійти, і є множина досяжного.

:::tabs
```cpp
// Чи є напрямлений шлях src → … → dst.
bool reaches(const Graph& g, const std::string& src, const std::string& dst) {
    std::unordered_set<std::string> seen{src};
    std::vector<std::string> stack{src};
    while (!stack.empty()) {
        std::string u = stack.back();
        stack.pop_back();
        auto it = g.find(u);
        if (it == g.end()) continue;
        for (const std::string& v : it->second) {   // порядок обходу не важить
            if (v == dst) return true;
            if (seen.insert(v).second)               // вставили вперше → у стек
                stack.push_back(v);
        }
    }
    return false;
}

// rules: пари (X, Y) зі змістом «X не сміє досягати Y».
std::vector<std::string> check_forbidden(
        const Graph& g,
        const std::vector<std::pair<std::string, std::string>>& rules) {
    std::vector<std::string> bad;
    for (const auto& [x, y] : rules)
        if (reaches(g, x, y))
            bad.push_back(x + " ⇏ " + y + ": є шлях " + x + " → … → " + y);
    return bad;
}
```
```python
def reaches(g: dict[str, set[str]], src: str, dst: str) -> bool:
    """Чи є напрямлений шлях src → … → dst."""
    seen, stack = {src}, [src]
    while stack:
        u = stack.pop()
        for v in g.get(u, ()):        # порядок обходу не важить — шукаємо сам факт шляху
            if v == dst:
                return True
            if v not in seen:
                seen.add(v)
                stack.append(v)
    return False

def check_forbidden(g, rules: list[tuple[str, str]]) -> list[str]:
    """rules: пари (X, Y) зі змістом «X не сміє досягати Y»."""
    return [f"{x} ⇏ {y}: є шлях {x} → … → {y}"
            for x, y in rules if reaches(g, x, y)]
```
```typescript
function reaches(g: Graph, src: string, dst: string): boolean {
  // Чи є напрямлений шлях src → … → dst.
  const seen = new Set([src]);
  const stack = [src];
  while (stack.length) {
    const u = stack.pop()!;
    for (const v of g.get(u) ?? []) {   // порядок обходу не важить — шукаємо сам факт шляху
      if (v === dst) return true;
      if (!seen.has(v)) { seen.add(v); stack.push(v); }
    }
  }
  return false;
}

function checkForbidden(g: Graph, rules: [string, string][]): string[] {
  // rules: пари (X, Y) зі змістом «X не сміє досягати Y».
  return rules
    .filter(([x, y]) => reaches(g, x, y))
    .map(([x, y]) => `${x} ⇏ ${y}: є шлях ${x} → … → ${y}`);
}
```
:::

Прогорнімо лихий коміт номер один. Хтось у модулі `db` імпортує застарілий помічник із `legacy` — додає ребро `db → legacy`. Саме по собі воно невинне: `db`(рівень 1) → `legacy`(рівень 0) веде вниз, циклу не творить. Але правило в нас таке: **`orders` уже відучили від `legacy`, і назад дороги нема** — `orders ⇏ legacy`. Питаємо `reaches(g, "orders", "legacy")`: обхід від `orders` іде `orders → db`, звідти вже `db → legacy` — і ми на місці. Перевірка друкує `orders ⇏ legacy: є шлях orders → … → legacy`, складання падає. Жодне око в рев'ю коміта в `db` не побачило б, що воно ламає правило про `orders`, — а обхід графа побачив за мікросекунди.

Правило-близнюк — **взаємна незалежність**: «`orders` і `billing` не сміють дістати одне одного в жоден бік». Це дві заборони, `orders ⇏ billing` і `billing ⇏ orders`, або один симетричний виклик. Саме такий контракт у реальних інструментах зветься *independence* — і про це трохи згодом.

Кожен виклик `reaches` — один обхід, тобто O(V + E) на пару. Якщо заборон M, наївно виходить O(M · (V + E)); коли M велике, дешевше піти з іншого боку — один обхід у **зворотному** графі від кожного забороненого Y дає всіх, хто його дістає, за раз. Але на практиці заборон — жменя (це найважливіші межі, не всі підряд), тож поштучний обхід і так нічого не коштує.

## Перевірка 2 — порушення шарів: ребро, що веде вгору

Шарувата архітектура — це домовленість про напрям: вищі шари спираються на нижчі, ніколи навпаки. `web` кличе домен, домен кличе `db`, `db` кличе `util` — і жоден із них не сміє потягнутися вгору, бо тоді фундамент починає залежати від даху. Формально це **частковий порядок** (лат. *ordo* — лад): припиши кожному модулеві рівень-число, і закон один — ребро не сміє вести з нижчого рівня у вищий.

:::tabs
```cpp
// level: модуль → номер шару (більший = вищий). Ребро вгору — порушення.
std::vector<std::string> check_layers(
        const Graph& g, const std::unordered_map<std::string, int>& level) {
    auto lv = [&](const std::string& m) {
        auto it = level.find(m);
        return it == level.end() ? 0 : it->second;
    };
    std::vector<std::string> bad;
    for (const auto& [u, deps] : g)
        for (const std::string& v : deps)
            if (lv(u) < lv(v))                        // залежність веде ВГОРУ
                bad.push_back(u + "(р." + std::to_string(lv(u)) + ") → " +
                              v + "(р." + std::to_string(lv(v)) + "): ребро вгору");
    return bad;
}
```
```python
def check_layers(g, level: dict[str, int]) -> list[str]:
    """level: модуль → номер шару (більший = вищий). Ребро вгору — порушення."""
    bad = []
    for u, deps in g.items():
        for v in deps:
            if level.get(u, 0) < level.get(v, 0):     # залежність веде ВГОРУ
                bad.append(f"{u}(р.{level[u]}) → {v}(р.{level[v]}): ребро вгору")
    return bad
```
```typescript
function checkLayers(g: Graph, level: Map<string, number>): string[] {
  // level: модуль → номер шару (більший = вищий). Ребро вгору — порушення.
  const bad: string[] = [];
  const lv = (m: string) => level.get(m) ?? 0;
  for (const [u, deps] of g)
    for (const v of deps)
      if (lv(u) < lv(v))                               // залежність веде ВГОРУ
        bad.push(`${u}(р.${lv(u)}) → ${v}(р.${lv(v)}): ребро вгору`);
  return bad;
}
```
:::

Уся перевірка — один прохід усіма ребрами з порівнянням двох чисел, O(V + E), без жодного обходу. Лихий коміт номер два: застарілий листок `legacy` раптом імпортує високорівневий `report` — ребро `legacy → report`. Рівні: `legacy`=0, `report`=2, отже 0 < 2 — залежність пнеться вгору крізь два шари. Перевірка друкує `legacy(р.0) → report(р.2): ребро вгору`. Зверни увагу, що це ребро **не** цикл (з `report` назад до `legacy` шляху нема) і **не** підпадає під жодну названу заборону — його ловить саме й тільки закон рівнів.

Ключова тонкість, за яку інакше боляче: `<` , а не `≠`. Ребро того самого рівня (`report`(2) → `orders`(2)) закон шарів **пропускає** — сусіди по шару можуть спиратися одне на одного, це не порушення ієрархії. І тут ховається пастка, яку видно лише коли зіставити всі три перевірки, — до неї ще дійдемо.

## Перевірка 3 — цикли: трибарвний обхід і називання винуватця

Найпідступніше правило — «жодних циклічних залежностей», і воно найцінніше. Цикл між модулями означає, що вони вже не два модулі, а один нерозривний ком: жоден не зібрати окремо, не змінити без оглядки на сусіда, не підмінити заглушкою на тесті. Це рівно [зчеплення, що вийшло з-під контролю](topic:programming/coupling-cohesion), тільки записане ребрами графа. Зловити його треба в мить, коли додано ребро-замикач, — поки розірвати цикл коштує один рядок, а не місяць.

Класичний детектор — **обхід у глибину з трибарвним розфарбуванням** вузлів, і три кольори тут несуть точний зміст. **Білий** — вузол, якого ще не чіпали. **Сірий** — вузол, у якого зайшли, але ще не вийшли: він **просто зараз лежить у стеку обходу**, тобто на шляху від кореня до нас. **Чорний** — вузол, повністю оброблений, разом з усім, що під ним. І весь фокус в одному спостереженні: якщо, обходячи вузол `u`, ми йдемо ребром у вузол `v`, **пофарбований у сіре**, — значить, `v` лежить у нас під ногами на поточному шляху, і ребро `u → v` замикає цей шлях у петлю. Таке ребро в теорії графів зветься **зворотним** (англ. *back edge*), і його наявність рівносильна наявності циклу.

![Трибарвний обхід у глибину на графі, де A, B, C сірі (лежать у стеку обходу), D чорний (завершений), E білий (ще не чіпаний); від C ребро веде назад у сірий вузол A, і саме це ребро — замкнений шлях назад, тобто цикл A → B → C → A; праворуч показано стек обходу з A внизу і C на вершині](img/tricolor-dfs.svg)
*Момент, коли обхід ловить цикл. A, B, C — сірі, бо всі троє ще в стеку обходу; D уже повністю оброблено (чорний); E ще білий. Обробляючи C, детектор іде ребром C → A й бачить, що A — сіре, тобто ще в стеку. Отже, від A донизу через B і C і назад до A замкнулася петля. Стек праворуч — це і є той шлях, по якому ми відновлюємо назву циклу.*

Тепер найважливіше для практики: детектор мусить не просто сказати «цикл є», а **назвати його**. «Десь у ста модулях є цикл» — це не допомога, це знущання; корисне повідомлення — це `orders → report → orders`. Тому поряд із кольорами ведемо мапу батьків: для кожного вузла пам'ятаємо, з якого ми в нього прийшли. Коли натрапляємо на сіре ребро `u → v`, підіймаємося по батьках від `u` вгору, аж поки не впремося у `v`, — це і є тіло циклу, лишається його розвернути й дописати замикач.

:::tabs
```cpp
#include <optional>
#include <functional>
#include <algorithm>

enum Color { WHITE, GRAY, BLACK };

std::optional<std::vector<std::string>> find_cycle(const Graph& g) {
    std::unordered_map<std::string, Color> color;
    for (const auto& [u, _] : g) color[u] = WHITE;
    std::unordered_map<std::string, std::string> parent;

    std::function<std::optional<std::vector<std::string>>(const std::string&)> walk =
        [&](const std::string& u) -> std::optional<std::vector<std::string>> {
        color[u] = GRAY;                              // u зайшов у стек обходу
        std::vector<std::string> nbrs(g.at(u).begin(), g.at(u).end());
        std::sort(nbrs.begin(), nbrs.end());          // детермінований звіт
        for (const auto& v : nbrs) {
            if (color[v] == GRAY) {                   // ребро у СІРЕ = замкнення назад
                std::vector<std::string> path{u};
                while (path.back() != v)              // підіймаємось по батьках u → … → v
                    path.push_back(parent[path.back()]);
                std::reverse(path.begin(), path.end());  // тепер v → … → u
                path.push_back(v);                    // ребро u → v замикає цикл
                return path;
            }
            if (color[v] == WHITE) {
                parent[v] = u;
                if (auto found = walk(v)) return found;
            }
        }
        color[u] = BLACK;                             // u й усе під ним оброблено
        return std::nullopt;
    };

    for (const auto& [u, _] : g)
        if (color[u] == WHITE)
            if (auto found = walk(u)) return found;    // напр. {"orders","report","orders"}
    return std::nullopt;
}
```

```python
WHITE, GRAY, BLACK = 0, 1, 2

def find_cycle(g: dict[str, set[str]]) -> list[str] | None:
    color = {u: WHITE for u in g}
    parent: dict[str, str] = {}

    def walk(u: str) -> list[str] | None:
```

```typescript
const WHITE = 0, GRAY = 1, BLACK = 2;

function findCycle(g: Graph): string[] | null {
  const color = new Map<string, number>([...g.keys()].map(u => [u, WHITE] as [string, number]));
  const parent = new Map<string, string>();

  function walk(u: string): string[] | null {
    color.set(u, GRAY);                              // u зайшов у стек обходу
    for (const v of [...g.get(u)!].sort()) {         // sort — щоб звіт був детермінований
      if (color.get(v) === GRAY) {                   // ребро у СІРЕ = замкнення назад
        const path = [u];
        while (path[path.length - 1] !== v)          // підіймаємось по батьках u → … → v
          path.push(parent.get(path[path.length - 1])!);
        path.reverse();                              // тепер v → … → u
        path.push(v);                                // ребро u → v замикає цикл
        return path;
      }
      if (color.get(v) === WHITE) {
        parent.set(v, u);
        const found = walk(v);
        if (found) return found;
      }
    }
    color.set(u, BLACK);                             // u й усе під ним оброблено
    return null;
  }

  for (const u of g.keys())
    if (color.get(u) === WHITE) {
      const found = walk(u);
      if (found) return found;                       // напр. ['orders','report','orders']
    }
  return null;
}
```

Лихий коміт номер три: `report` уже спокійно кликав `orders` (сусіди по шару 2, законно), а тепер хтось у `orders` додає імпорт `report` — ребро `orders → report`. Обхід від `orders` фарбує його в сіре, іде в `report`, з `report` доходить до `orders` — а `orders` сіре, воно ж у стеку. Зворотне ребро. Піднявшись по батьках, детектор повертає `['orders', 'report', 'orders']` і друкує саме цю петлю. Закон шарів тут мовчить (обидва на рівні 2), заборон між ними нема — цикл ловить лише циклова перевірка.

Дві історичні примітки, бо інструмент варто знати з родоводом. Сам обхід у глибину — техніка старезна: як спосіб пройти лабіринт її описав ще у XIX столітті француз **Шарль П'єр Тремо** (Charles Pierre Trémaux), і DFS-дерево досі звуть його ім'ям — *дерево Тремо* (це усталено, хоч першоджерело — переказ Едуара Люка́, а не публікація самого Тремо). У сучасний, лінійний за часом інструмент для графів DFS перетворив **Роберт Тарджан** (Robert Endre Tarjan) статтею 1972 року «Depth-First Search and Linear Graph Algorithms» (SIAM J. Computing), де з одного обходу вивів і сильно зв'язні компоненти, і мости. А самé трибарвне «біле/сіре/чорне» — це вже дидактичний виклад із підручника Кормена, Лейзерсона, Рівеста й Стайна «Introduction to Algorithms», що став стандартною мовою, якою про цей обхід говорять.

Одна пастка реалізації, суто інженерна: рекурсія. `walk` кличе себе на глибину найдовшого шляху, а в реальному монорепо ланцюг залежностей буває на тисячі вузлів — і стандартна межа рекурсії Python (близько тисячі кадрів) впаде першою, ще до того, як знайдеться цикл. Тому на великих графах `walk` розгортають у **явний стек** (ітеративний обхід із власним списком-стеком замість викликів функції); логіка кольорів та сама, лягає лише інакше. Для наочності тут лишаю рекурсивну форму — вона читабельніша, — але в бойовому тулі тримай ітеративну.

## Складність і швидкість на кожен коміт

Тепер зведімо ціну докупи, бо вся ідея воріт тримається на тому, що вони бігтимуть на **кожен** коміт і ніхто не помітить затримки.

```
побудова графа       :  O(V + E)   + розбір коду O(розміру джерел)
заборонена, 1 пара   :  O(V + E)   один обхід від X
    M пар            :  O(M·(V+E)); зворотним обходом — O(V+E) на кожен Y
порушення шарів      :  O(V + E)   один прохід усіма ребрами
цикли, трибарвний DFS :  O(V + E)   кожен вузол і ребро — рівно раз
─────────────────────────────────
разом на коміт       :  O(V + E)   стала кількість проходів
```

Ключ до спокою — усвідомити, що таке тут V і E. Це **не** рядки коду й **не** файли: V — це модулі (теки/пакети), а E — міжмодульні ребра. Навіть у величезному репозиторії модулів — сотні, ну тисячі, а не мільйони. Порахуймо чесно:

```
монорепо:  V = 2 000 модулів,  E = 10 000 ребер
один прохід O(V+E) ≈ 12 000 елементарних кроків
п'ять перевірок    ≈ 60 000 кроків     →  частки мілісекунди на графі
розбір 300 000 рядків коду             →  секунди (ОСЬ справжня ціна)
```

Мораль пряма: сам граф — безкоштовний, а платимо ми за **розбір джерел**, і саме його треба берегти. Два прийоми тримають ворота швидкими. Перший — **кеш розбору за хешем вмісту файлу**: збережи витягнуті з файлу імпорти під ключем-хешем його тексту, і на наступному коміті переробляй лише ті файли, чий хеш змінився, — а їх зазвичай одиниці. Другий — **місце в конвеєрі**: ці перевірки ставлять найпершими у [конвеєрі складання](topic:programming/ci-cd), **перед** повільними юніт- та інтеграційними тестами. Граф збирається й перевіряється за секунду-дві на розбір плюс частки мілісекунди на самі перевірки — тобто розробник, що зламав шар, дізнається про це майже миттєво, а не після двадцятихвилинного тестового прогону. Дешева перевірка попереду дорогих — це не лише економія, це ще й коротша петля зворотного зв'язку, а короткість петлі й вирішує, чи виправлять поламане одразу, чи забудуть.

## Пастки: де набір тихо бреше

Алгоритми тут не помиляються — помиляється все навколо них. Перелічмо, де набір архітектурних перевірок починає брехати, бо кожна пастка вже когось коштувала.

**Розбір — це і є вся складність, і він недобачає.** Граф чесний рівно настільки, наскільки повний список ребер. А статичний розбір сліпий до всього, що вирішується під час виконання: динамічний імпорт за рядком-змінною (`importlib.import_module(name)`, `require(varname)`, `import()` з обчисленим шляхом), реекспорти `export * from`, впорскування залежностей через контейнер, пошук за рефлексією. Такі ребра в граф не потраплять — і перевірка спокійно пропустить порушення, зроблене через чорний хід. Це не привід кидати інструмент, а привід **знати його горизонт**: він стереже статичні залежності, а сховані за рядком-змінною лишаються поза зором, і про них треба пам'ятати окремо.

**Тихий провал розбору — найгірше зелене.** Якщо парсер спіткнувся на файлі (новий синтаксис, биті кодування) і твій код той файл мовчки пропустив — його ребра зникли з графа, а отже, порушення в ньому стало невидимим. Ворота **зеленіють помилково**, і це найпідступніший стан з усіх, бо всі вірять, що межу стережуть. Правило залізне: на помилці розбору перевірка **падає голосно**, а не тихо ковтає файл.

**Фільтр «своє / чуже» вирішує все.** Забудеш відсіяти зовнішні бібліотеки — граф розбухне сотнями вузлів стороннього коду, серед яких твої правила потонуть, а обходи сповільняться. Забереш забагато — проґавиш справжнє ребро. Список префіксів «внутрішнього» — не дрібниця конфігурації, а частина визначення того, **про що взагалі ця перевірка**.

**Недетермінований звіт дратує до відключення.** Якщо в графі кілька циклів, обхід повідомить той, на який натрапить першим, а це залежить від порядку перебору сусідів. Сьогодні тобі покажуть один цикл, завтра після дрібної правки — інший, і команда вирішить, що інструмент «плаває». Тому сусідів перебираємо **впорядковано** (`sorted`) — той самий граф щоразу дає той самий звіт, і провал відтворюваний.

## Legacy: базова лінія на множині ребер

Останній, найпрактичніший бік. Ти не вмикаєш ці ворота на чистому полі — ти вмикаєш їх на системі, де порушень уже двісті, і залити складання червоним першого ж дня означало б спинити всю роботу. Потрібен спосіб **заморозити відоме й ловити лише нове**.

Найгрубший храповик (англ. *ratchet* — механізм, що крутиться лише в один бік) стереже саме **число**: «порушень не більш як двісті, і планка може тіснитися лише вниз». Він годиться для агрегатних метрик, де важлива кількість, а не поіменність. Але для графа залежностей є точніший інструмент — **базова лінія на множині конкретних ребер**. Заморозь у файл рівно ту множину порушень, що є зараз (кожне як рядок `"legacy→report"`), закомить її в репозиторій — і хай ворота падають лише на порушеннях, яких у базі **не було**. Полагоджене порушення випадає з бази й **уже ніколи не повернеться**.

:::tabs
```cpp
// current — нинішні порушення (напр. "legacy→report"); baseline — заморожені.
// Падаємо лише на НОВИХ; базу тіснимо до тих старих, що ще лишилися.
std::pair<bool, std::unordered_set<std::string>> gate(
        const std::unordered_set<std::string>& current,
        const std::unordered_set<std::string>& baseline) {
    std::unordered_set<std::string> fresh, kept;
    for (const auto& v : current) {
        if (baseline.count(v)) kept.insert(v);        // старі, що ще лишилися → нова база
        else                   fresh.insert(v);       // порушення, яких у базі не було
    }
    return { fresh.empty(), kept };
}
```
```python
def gate(current: set[str], baseline: set[str]) -> tuple[bool, set[str]]:
    """current — нинішні порушення (напр. 'legacy→report'); baseline — заморожені.
    Падаємо лише на НОВИХ; базу тіснимо до тих старих, що ще лишилися."""
    new  = current - baseline          # порушення, яких у базі не було
    kept = current & baseline          # старі, що ще лишилися → нова база
    return (len(new) == 0, kept)
```
```typescript
function gate(current: Set<string>, baseline: Set<string>): { pass: boolean; kept: Set<string> } {
  // current — нинішні порушення; baseline — заморожені.
  // Падаємо лише на НОВИХ; базу тіснимо до тих старих, що ще лишилися.
  const isNew = [...current].filter(v => !baseline.has(v));        // яких у базі не було
  const kept  = new Set([...current].filter(v => baseline.has(v))); // старі, що лишилися → нова база
  return { pass: isNew.length === 0, kept };
}
```
:::

Уся сила — у двох операціях над множинами. Різниця `current − baseline` — це рівно нові гріхи, і лише на них ворота падають, тож жодна свіжа заборонена залежність не прослизне. Перетин `current ∩ baseline` стає **новою базою**: як тільки хтось полагодив старе порушення, воно зникає з `current`, отже, випадає й з перетину — і база тісниться на одне ребро, назавжди. Це точніше за скалярний храповик, бо пришпилює **які саме** двісті порушень пробачені: не можна «виторгувати» полагоджене старе за нове, підмінивши одне іншим при тому самому числі. Один перетин множин відділяє чесний ратчет від такого, що дає торгувати гріхами.

## Три перевірки, один граф: що кожна потребує і що ловить

Наостанок — спостереження, яке видно лише коли покласти всі три перевірки поруч, і саме воно пояснює, чому їх **три**, а не одна. Вони різняться не силою, а тим, **що кожній треба на вході** і **що вона за це ловить**.

![Три перевірки як лінійки: заборонена потребує названої пари X ⇏ Y і ловить будь-який шлях між ними, навіть того самого рівня чи вниз; шари потребують карти рівнів і ловлять будь-яке ребро вгору; цикли не потребують нічого, крім графа, і ловлять будь-який цикл; унизу висновок, що кожен цикл несе ребро вгору, тож повні рівні вже підказують цикли, а названа пара ловить те, що обидві інші пропускають](img/gate-lattice.svg)
*Три перевірки за входом і покриттям. Циклова не потребує нічого, крім графа, — тому універсальна. Шарова потребує рівня для кожного модуля — за це ловить будь-яке ребро вгору. Заборонна потребує названої пари — і ловить те, чого дві інші не бачать: заборонену залежність того самого рівня або спрямовану вниз.*

Розкладімо це в маленьку істину про типи ребер. Візьми будь-яке нове ребро й спитай, хто його впіймає:

```
ребро вгору (рівень зростає)      →  шари; і майже завжди ще й цикл
заборонена пара, той самий рівень →  лише заборона (шари й цикл мовчать)
заборонена пара, униз по рівнях   →  лише заборона (шлях законний за шарами)
цикл між рівними модулями         →  лише цикл (шари дозволяють ребро вбік)
```

Звідси видно дивовижну річ. **Кожен цикл несе щонайменше одне ребро вгору** — бо, обійшовши петлю, рівень мусить повернутися до старту, а якщо він десь падав, то десь мусив і рости. Отже, якби рівні були розставлені на **всіх** модулях і бездоганно, шарова перевірка сама по собі вже виловлювала б і всі цикли. Але рівні є не завжди: усередині одного шару їх не розставиш, та й у купі кодових баз шарів просто не оголошено. Циклова ж перевірка **не потребує рівнів зовсім** — їй досить графа, тому вона універсальна там, де шарова сліпа. А заборонна ловить третє: конкретну пару, яку і шари, і цикл пропускають, — заборонену залежність того самого рівня або спрямовану законно вниз (як `orders → legacy` у нашому прикладі). Три різні входи, три різні покриття, і разом вони затуляють діри одне одного.

Що це не вигадка, а рівно те, що роблять бойові інструменти, легко перевірити. Python-івський **import-linter** визначає контракти трьох типів — *forbidden* (заборонена пара), *layers* (шари) і *independence* (взаємна незалежність), — і це майже дослівно наші три перевірки. У світі JavaScript/TypeScript **dependency-cruiser** дає правила заборонених імпортів і рве складання в конвеєрі; у Java **ArchUnit** пише архітектуру юніт-тестами — `layeredArchitecture`, заборони доступу між пакетами, перевірку на цикли. Усі вони під капотом будують той самий граф залежностей і ганяють по ньому ті самі обходи, що й ми щойно написали. Різні мови, різні синтаксиси конфігів — один граф і три питання до нього.
