# ⚙️ Багатовимірний фітнес-харнес: набір перевірок, що стереже кілька осей системи одразу

<preknowlist>
- [Фітнес-функції](book:programming/fitness-functions) — автоматична об'єктивна перевірка якісного атрибута, що падає, коли правило порушено; різниця між атомарною (одна властивість) і цілісною (поєднання, що можуть суперечити) перевіркою.
- [Теорія графів](book:math/graph-theory) — вершини й напрямлені ребра, шлях і цикл, DAG (напрямлений ациклічний граф) і топологічний порядок, обхід у глибину; тут вершина = модуль, ребро = «модуль X імпортує модуль Y».
</preknowlist>

Одна фітнес-функція стереже одну межу. Але жива система тримається не на одній межі, а на кількох одразу, і кожна лежить на своїй осі: структура (хто від кого залежить), форма графа залежностей (чи можна модулі складати нарізно), швидкодія, розмір артефакту постачання. Зміна, що поліпшила одну вісь, легко нищить іншу — прибрав зайвий шар непрямості й пришвидшив код, а заразом протягнув домен до бази; порізав великий пакунок на шматки й зменшив артефакт, а заразом додав мережевих кругорейсів і просадив час відповіді. Стерегти таку систему однією перевіркою — все одно що охороняти будинок з чотирма дверима, поставивши вартового лише біля одних.

Тому «напрямну зміну за кількома вимірами» втілюють не однією фітнес-функцією, а **набором** — харнесом (англ. *harness* — упряж, оснастка): кількома перевірками спільної форми, які запускають разом на кожну зміну, кожна пильнує свою вісь, а всі разом зводяться в один вирок на воротах. Тут ми зберемо такий харнес — робочий, а не на словах. Три осі, три фітнес-функції: атомарне правило шарів, детектор циклів, що боронить інваріант «граф залежностей — DAG», і цілісний бюджет часу з розміром. Мова прикладу — TypeScript і Python: харнес живе там, де живе код, а сучасний продуктовий код — це найчастіше TS-моноріпо з імпортами між модулями й бюджетом на розмір зібраного пакунка.

## Задача: одна зміна, кілька осей, один код виходу

Сформулюймо точно, бо від точності залежить уся конструкція. На вході — дерево вихідників (теки-модулі, вони ж шари), **карта дозволених залежностей** між шарами, і **бюджети** (гранична 95-та перцентиль часу відповіді, граничний розмір артефакту). Кожна зміна, що заходить у систему, має одночасно вдовольнити три умови: не завести забороненого ребра між шарами, не замкнути циклу (тобто лишити граф залежностей ациклічним), і не вибити систему за спільний бюджет часу-й-розміру.

На виході — по одному **вироку на кожну вісь** («пройшло / не пройшло» з подробицею, де саме зламалося) і одне **число зверху** — скільки осей не втрималося, — з якого харнес робить код виходу для воріт складання: нуль пропускає зміну, ненуль валить конвеєр. Головне в цьому формулюванні — слово «одночасно». Ми не питаємо систему по черзі про кожну вісь у різні моменти на різних збірках; ми питаємо про всі осі **разом, на тій самій зміні**, бо тільки так видно, що зміна виправила одне коштом іншого.

> 🔧 **Навіщо це.** Найпідступніша регресія — не та, де щось очевидно зламалося, а та, де на вигляд стало краще. Розробник щиро пришвидшив запит і показує графік: латентність упала. А те, що заради цього кеш роздувся й артефакт переступив бюджет постачання, не видно нікому — бо ніхто не дивився на дві осі одночасно. Харнес, що міряє всі осі на одному прогоні, ловить саме такі приховані розміни: він не дає полагодити одну вісь, тихо зламавши сусідню.

## Ідея: фітнес-функція як об'єкт зі спільною формою

Щоб перевірки складалися в набір, а не лежали купою розрізнених скриптів, дамо їм **єдину форму**. Фітнес-функція для нас — це щось, що має ім'я, знає, яку вісь стереже, і вміє винести вирок. Вирок — це прапорець «пройшло» плюс людський опис, куди йти дивитися, коли не пройшло.

:::tabs
```typescript
// Спільний контракт: усе, що вміє винести вирок про одну вісь системи.
interface Verdict {
  readonly passed: boolean;
  readonly detail: string;               // куди дивитися, коли не пройшло
}

interface FitnessFunction {
  readonly name: string;
  readonly axis: string;                 // яку вісь системи стереже
  run(): Verdict | Promise<Verdict>;     // синхронна (структура) чи асинхронна (вимір)
}
```
```python
from dataclasses import dataclass
from typing import Callable

# Спільний контракт: усе, що вміє винести вирок про одну вісь системи.
@dataclass(frozen=True)
class Verdict:
    passed: bool
    detail: str                          # куди дивитися, коли не пройшло

@dataclass(frozen=True)
class FitnessFunction:
    name: str
    axis: str                            # яку вісь системи стереже
    run: Callable[[], Verdict]           # виносить вирок
```
:::

Уся сила харнеса — саме в цій одноманітності. Кожна перевірка, хоч яка різна всередині (одна читає імпорти статично, інша ганяє живу систему й міряє час), назовні виглядає однаково: спитали `run()` — дістали `Verdict`. Тому «додати ще одну вісь під нагляд» коштує рівно стільки, скільки написати ще один об'єкт цієї форми й дописати його в список. Набір не переписують — його **доростають**.

А сам харнес — це список фітнес-функцій і той, хто по черзі їх питає, друкує вироки й зводить усе в код виходу:

:::tabs
```typescript
async function runHarness(ffs: FitnessFunction[]): Promise<number> {
  let failed = 0;
  for (const ff of ffs) {
    const v = await ff.run();            // await не заважає синхронним — вони теж підійдуть
    console.log(`[${v.passed ? "PASS" : "FAIL"}] ${ff.name} — ${ff.axis}\n        ${v.detail}`);
    if (!v.passed) failed++;
  }
  console.log(`\nпідсумок: ${ffs.length - failed}/${ffs.length} осей тримається`);
  return failed === 0 ? 0 : 1;           // код виходу для воріт CI
}
```
```python
def run_harness(ffs: list[FitnessFunction]) -> int:
    failed = 0
    for ff in ffs:
        v = ff.run()
        mark = "PASS" if v.passed else "FAIL"
        print(f"[{mark}] {ff.name} — {ff.axis}\n        {v.detail}")
        failed += not v.passed
    print(f"\nпідсумок: {len(ffs) - failed}/{len(ffs)} осей тримається")
    return 0 if failed == 0 else 1        # код виходу для воріт CI
```
:::

## Спільна основа: граф залежностей модулів

Дві з трьох осей — структура й форма графа — читаються з одного джерела: **графа залежностей модулів**. Тому спершу зберемо його раз, а тоді двічі поставимо йому різні запитання. Вершина графа — модуль (візьмімо його як теку верхнього рівня, вона ж шар), ребро `X → Y` означає «якийсь файл модуля `X` імпортує з модуля `Y`».

У TS-проєкті з базовими (не відносними) імпортами — коли `import { save } from "db/postgres"` резолвиться від кореня вихідників — ціль ребра видно просто в тексті: перший сегмент рядка в лапках і є модуль-ціль, точнісінько як у C перший сегмент `#include`. Зберімо всі теки-модулі, тоді пройдімо файли й на кожен внутрішній імпорт додаймо ребро:

:::tabs
```typescript
import { readdirSync, statSync, readFileSync } from "node:fs";
import { join, relative, sep } from "node:path";

type Graph = Map<string, Set<string>>;   // модуль → модулі, від яких він залежить

// import ... from "spec"  /  export ... from "spec"
const IMPORT_RE = /(?:import|export)[^'"]*?from\s*['"]([^'"]+)['"]/g;

const moduleOf = (root: string, file: string) => relative(root, file).split(sep)[0];

function walk(dir: string): string[] {
  const out: string[] = [];
  for (const name of readdirSync(dir)) {
    const full = join(dir, name);
    if (statSync(full).isDirectory()) out.push(...walk(full));
    else if (/\.tsx?$/.test(name)) out.push(full);
  }
  return out;
}

function buildGraph(root: string): Graph {
  const files = walk(root);
  const layers = new Set(files.map(f => moduleOf(root, f)));      // усі реальні модулі-теки
  const g: Graph = new Map([...layers].map(l => [l, new Set()]));

  for (const file of files) {
    const from = moduleOf(root, file);
    for (const m of readFileSync(file, "utf8").matchAll(IMPORT_RE)) {
      const to = m[1].split("/")[0];                             // перший сегмент специфікатора
      if (layers.has(to) && to !== from) g.get(from)!.add(to);   // лише внутрішні міжмодульні ребра
    }
  }
  return g;
}
```
```python
import re
from pathlib import Path

IMPORT_RE = re.compile(r'''(?:import|export)[^'"]*?from\s*['"]([^'"]+)['"]''')

def module_of(root: Path, file: Path) -> str:
    return file.relative_to(root).parts[0]            # перший сегмент шляху = модуль/шар

def build_graph(root: Path) -> dict[str, set[str]]:
    files = [p for p in root.rglob("*") if p.suffix in {".ts", ".tsx"}]
    layers = {module_of(root, f) for f in files}      # усі реальні модулі-теки
    g: dict[str, set[str]] = {l: set() for l in layers}

    for file in files:
        frm = module_of(root, file)
        for spec in IMPORT_RE.findall(file.read_text(encoding="utf-8", errors="ignore")):
            to = spec.split("/")[0]                    # перший сегмент специфікатора
            if to in layers and to != frm:             # лише внутрішні міжмодульні ребра
                g[frm].add(to)
    return g
```
:::

Два свідомі спрощення варто назвати вголос. По-перше, зовнішні пакунки (`"react"`, `"zod"`) самі відсіюються — їхнього першого сегмента немає серед наших тек, тож ребро не додається; нас цікавить **внутрішня** структура, не залежність від бібліотек. По-друге, відносні імпорти (`"./util"`, `"../db/pg"`) цей наївний збирач **пропускає** — їхній перший сегмент (`.` або `..`) теж не модуль. У проєкті, де межі шарів перетинають лише базовими імпортами, цього досить; щойно між шарами ходять відносними шляхами, кожен імпорт треба резолвити до реального файлу тим самим набором шляхів, що й складач. Повний, чесний до резолвінгу й до згенерованих файлів збирач графа (і чому саме цикл — найтоксичніший сигнал у ньому) розібрано окремо на прикладі C-дерева з `#include` — [інструмент, що будує граф залежностей і ловить порушення шарів та цикли](book:programming/architecture-erosion/proj-dependency-checker.md); тут нам граф потрібен лише як спільна основа для двох осей.

## Вісь структури: атомарне правило шарів

Перше запитання до графа найпростіше й **локальне**: чи кожне окреме ребро дозволене картою шарів? Карту тримаємо як множину дозволених пар «шар → шар»; усе, чого в множині немає, заборонено за замовчуванням — політика «заборонено все, крім дозволеного» надійніша за зворотну, бо нове порушення не прослизне крізь діру в списку заборон.

:::tabs
```typescript
const edge = (a: string, b: string) => `${a}->${b}`;

function layerRule(g: Graph, allowed: Set<string>): FitnessFunction {
  return {
    name: "layers",
    axis: "структура: залежності шарів",
    run(): Verdict {
      const bad: string[] = [];
      for (const [from, tos] of g)
        for (const to of tos)
          if (!allowed.has(edge(from, to))) bad.push(`${from} → ${to}`);
      return {
        passed: bad.length === 0,
        detail: bad.length ? `заборонені ребра: ${bad.join(", ")}`
                           : "усі залежності дозволені",
      };
    },
  };
}
```
```python
def layer_rule(g: dict[str, set[str]], allowed: set[tuple[str, str]]) -> FitnessFunction:
    def run() -> Verdict:
        bad = [f"{frm} → {to}"
               for frm, tos in g.items() for to in tos
               if (frm, to) not in allowed]
        detail = ("заборонені ребра: " + ", ".join(bad)) if bad else "усі залежності дозволені"
        return Verdict(not bad, detail)
    return FitnessFunction("layers", "структура: залежності шарів", run)
```
:::

Ця перевірка **атомарна** в точному сенсі: вона пильнує одну властивість — дозволеність залежностей — і виносить вирок кожному ребру, дивлячись лише на дві його вершини й карту. Ніякого знання про решту графа не треба: `domain → db` заборонене саме по собі, незалежно від того, що ще є в системі. Саме тому воно дешеве й миттєве навіть на великому дереві — і саме тому його зручно ставити на ворота першим.

## Вісь форми графа: цикли й інваріант DAG

Друге запитання до того самого графа — зовсім іншої природи. Заборонене ребро видно з погляду на дві вершини; **цикл** видно лише з погляду на форму цілого графа. І тут вступає інваріант, задля якого шари взагалі існують.

Шарова архітектура впорядковує модулі **частковим порядком**: якщо шар `A` має право залежати від `B`, то `B` не сміє залежати від `A`. Такий порядок можливий тоді й лише тоді, коли граф залежностей **ациклічний** — тобто є DAG (англ. *directed acyclic graph*, напрямлений ациклічний граф). Ациклічність рівносильна існуванню **топологічного порядку**: модулі можна вишикувати в лінію так, що всі ребра йдуть в один бік. Оце і є формальний зміст слова «шари»: DAG розкладається на рівні, цикл — ні. Замкни коло `ui → domain → ports → ui` — і топологічного порядку більше немає: три модулі злипаються в один нерозривний блок, який ти вже не можеш ні зібрати, ні протестувати, ні перенести **нарізно** (це та сама взаємозалежність, що робить [зчеплення](book:programming/coupling-cohesion) фатальним). Отже, фітнес-функція форми графа стереже один інваріант: **граф залежностей шарової архітектури лишається DAG**.

Як **знайти** цикл? Заборонене ребро видно зразу, а цикл — це шлях, що повертається у вихідну вершину, тож потрібен обхід. Класичний і найощадливіший спосіб — обхід у глибину (DFS) з **трьома кольорами** вершин, де колір кодує рівно те, що треба знати:

- **білий** — ще не заходили;
- **сірий** — **зайшли, але ще не вийшли**: вершина просто зараз лежить у нашому ланцюжку занурення, на стеку рекурсії;
- **чорний** — **вийшли остаточно**: вершину й усіх її нащадків повністю пройдено.

Уся магія — в одному спостереженні. Ідучи по ребру `v → w`, дивимося на колір `w`. Якщо `w` **сіра** — значить, вона вже лежить у нашому ж поточному ланцюжку занурення, і ми щойно замкнули на неї стрілку. Це **зворотне ребро** (англ. *back edge*), а зворотне ребро в напрямленому графі **завжди означає цикл** — це усталена теорема теорії графів: напрямлений граф ациклічний тоді й лише тоді, коли DFS не знаходить жодного зворотного ребра. Ребро в **білу** вершину — просто крок углиб. Ребро в **чорну** — безпечне: та гілка вже вийдена, повернутися нею в поточний ланцюжок неможливо (два шляхи, що сходяться в одну вже пройдену вершину, — це не цикл). Отже, цикл є **тоді й лише тоді**, коли обхід зустрічає ребро в сіру вершину — і в цю мить сам цикл лежить у стеку, від сірої цілі до поточної вершини.

:::tabs
```typescript
enum Color { White, Gray, Black }

function findCycles(g: Graph): string[][] {
  const color = new Map<string, Color>([...g.keys()].map(v => [v, Color.White]));
  const stack: string[] = [];                    // поточний ланцюжок занурення (сірі вершини)
  const cycles: string[][] = [];

  const dfs = (v: string): void => {
    color.set(v, Color.Gray);                    // входимо — вершина тепер у ланцюжку
    stack.push(v);
    for (const w of g.get(v) ?? []) {
      const c = color.get(w) ?? Color.White;
      if (c === Color.Gray) {                    // ребро в СІРУ → зворотне ребро → цикл
        cycles.push(stack.slice(stack.indexOf(w)));   // хвіст стеку від w до v — саме коло
      } else if (c === Color.White) {
        dfs(w);                                  // ще не ходили — крок углиб
      }
      // Black — гілка вже вийдена, пропускаємо
    }
    color.set(v, Color.Black);                   // виходимо — вершина й нащадки позаду
    stack.pop();
  };

  for (const v of g.keys())
    if (color.get(v) === Color.White) dfs(v);    // ліс: запуск із кожної ще білої вершини
  return cycles;
}
```
```python
WHITE, GRAY, BLACK = 0, 1, 2

def find_cycles(g: dict[str, set[str]]) -> list[list[str]]:
    color = {v: WHITE for v in g}
    stack: list[str] = []                        # поточний ланцюжок занурення (сірі вершини)
    cycles: list[list[str]] = []

    def dfs(v: str) -> None:
        color[v] = GRAY                          # входимо — вершина тепер у ланцюжку
        stack.append(v)
        for w in g.get(v, ()):
            if color.get(w, WHITE) == GRAY:      # ребро в СІРУ → зворотне ребро → цикл
                cycles.append(stack[stack.index(w):])   # хвіст стеку від w до v — саме коло
            elif color.get(w, WHITE) == WHITE:
                dfs(w)                           # ще не ходили — крок углиб
            # BLACK — гілка вже вийдена, пропускаємо
        color[v] = BLACK                         # виходимо — вершина й нащадки позаду
        stack.pop()

    for v in g:
        if color[v] == WHITE:                    # ліс: запуск із кожної ще білої вершини
            dfs(v)
    return cycles
```
:::

Чому три кольори, а не два? Простого «відвіданий / невідвіданий» замало: вершина, у яку ми вже заходили й **вийшли** (чорна), — це геть не те саме, що вершина, у якій ми **зараз перебуваємо** (сіра). Стрілка в першу — нормальний повторний прихід у вже пройдений вузол; стрілка в другу — цикл. Змішати ці два стани в один колір — і алгоритм або проґавить справжні цикли, або нафантазує неіснуючі. Зовнішній цикл у кінці — не окремий обхід щоразу, а один прохід «лісом»: граф залежностей майже завжди не зв'язний одним коренем (верхні шари — вершини, у які ніхто не входить), тож DFS запускають із кожної ще білої вершини, і сумарно кожну фарбують один раз.

Лишається загорнути цей обхід у фітнес-функцію спільної форми:

:::tabs
```typescript
function acyclic(g: Graph): FitnessFunction {
  return {
    name: "acyclic",
    axis: "форма графа: шари утворюють DAG",
    run(): Verdict {
      const cycles = findCycles(g);
      return {
        passed: cycles.length === 0,
        detail: cycles.length
          ? cycles.map(c => [...c, c[0]].join(" → ")).join("; ")   // замкнути коло у звіті
          : "граф ациклічний — DAG тримається",
      };
    },
  };
}
```
```python
def acyclic(g: dict[str, set[str]]) -> FitnessFunction:
    def run() -> Verdict:
        cycles = find_cycles(g)
        detail = ("; ".join(" → ".join(c + [c[0]]) for c in cycles)   # замкнути коло у звіті
                  if cycles else "граф ациклічний — DAG тримається")

Ця перевірка теж атомарна — вона пильнує одну властивість (ациклічність), — але, на відміну від правила шарів, її погляд **глобальний**: жодне окреме ребро циклу саме по собі не заборонене, отруйне саме замкнене коло з них.

## Складність: чому O(V + E) і чому це важить для воріт

Порахуймо чесно, скільки коштує обхід, — бо від цього залежить, чи можна ставити перевірку на **кожен** комміт. Позначимо `V` — кількість вершин (модулів), `E` — кількість ребер (міжмодульних імпортів після групування). У трикольоровому DFS:

```
кожну вершину фарбуємо GRAY і BLACK рівно по разу     →  робота ∝ V
список суміжності кожної вершини пробігаємо один раз   →  робота ∝ E
──────────────────────────────────────────────────────────────
разом:  O(V + E)
```

Це **лінійно** від розміру графа — найкраще, на що взагалі можна сподіватися, бо граф треба бодай раз прочитати цілком, а прочитати його — це вже V + E. Ключове, чому не гірше: кольори не дають зайти в жодну вершину вдруге (біла стає сірою, повторний вхід відсікає перевірка `White`), а список суміжності кожної вершини теж пробігають один раз. Порівняйте з наївом без кольорів — якби на кожну вершину ми заново перебирали всі маршрути «чи веде звідси шлях назад у мене»: кількість шляхів у графі росте комбінаторно, і така перевірка зривається в експоненту, на реальному дереві просто не добігши. Три кольори перетворюють потенційно нездоланну задачу на один лінійний прохід саме тому, що **пам'ятають** стан кожної вершини.

Практичний висновок прямий: `O(V + E)` — це та дешевизна, яка й робить перевірку придатною для воріт. Навіть на дереві з тисяч файлів граф модулів після групування по теках малий (модулів десятки-сотні, не тисячі), тож і шари, і цикли рахуються за частку секунди. Перевірку, що коштує стільки, не шкода запускати на кожен комміт; дорогу — почали б вимикати «на час авралу», і сенс воріт випарувався б.

## Вісь швидкодії й постачання: цілісний бюджет

Дві попередні осі читаються з коду статично, не запускаючи його. Третя інша: багато найважливішого проявляється лише в русі. Бюджет часу відповіді не побачиш в імпортах — його видно, тільки коли система працює; розмір артефакту не побачиш у графі модулів — його видно, тільки коли пакунок зібрано. І тут вирішальне: ці дві величини **міряють з одного артефакту й перевіряють разом**, бо вони **розмінюються** одна на одну. Порізав пакунок на шматки — зменшив розмір, але додав мережевих кругорейсів і підняв час відповіді. Наростив кеш заради часу — прискорив відповідь, але роздув артефакт. Дві **окремі** атомарні перевірки цього розміну не спіймають: перевірка розміру на одній збірці й перевірка часу на іншій можуть обидві світитися зеленим, поки реальний постачений артефакт вибиває один із бюджетів. Саме тому це **цілісна** (англ. *holistic*) фітнес-функція: вона пильнує не властивість, а **поєднання** властивостей, які тягнуть у різні боки.

:::tabs
```typescript
interface Reading { p95Ms: number; artifactKb: number; }    // обидві величини з ОДНОГО артефакту
interface Budget  { maxP95Ms: number; maxArtifactKb: number; }

function budget(measure: () => Promise<Reading>, b: Budget): FitnessFunction {
  return {
    name: "budget",
    axis: "швидкодія + постачання: час відповіді й розмір разом",
    async run(): Promise<Verdict> {
      const r = await measure();                              // один прогін — обидві величини разом
      const over: string[] = [];
      if (r.p95Ms > b.maxP95Ms)          over.push(`p95 ${r.p95Ms}мс > ${b.maxP95Ms}мс`);
      if (r.artifactKb > b.maxArtifactKb) over.push(`артефакт ${r.artifactKb}КБ > ${b.maxArtifactKb}КБ`);
      return {
        passed: over.length === 0,                            // тримаються ОБИДВА бюджети — чи жодного розміну
        detail: over.length ? over.join("; ") : "обидва бюджети витримано",
      };
    },
  };
}
```
```python
@dataclass(frozen=True)
class Reading:                            # обидві величини з ОДНОГО артефакту

    artifact_kb: int

@dataclass(frozen=True)
class Budget:
    max_p95_ms: float
    max_artifact_kb: int

def budget(measure: Callable[[], Reading], b: Budget) -> FitnessFunction:

        over = []
        if r.p95_ms > b.max_p95_ms:

        if r.artifact_kb > b.max_artifact_kb:

        return Verdict(not over, detail)  # тримаються ОБИДВА — чи жодного розміну
    return FitnessFunction("budget", "швидкодія + постачання: час і розмір разом", run)

Ось його форма (`percentile` — звичайне сортування й вибір за індексом, `loadTest` — постріляти N запитів і записати тривалості; суть не в них):

Фітнес-функція не вигадує бюджет — вона **стереже** вже ухвалений.

## Складання харнеса й ворота

Лишилось з'єднати три осі в одну програму, що повертає код виходу. Саме його читає конвеєр, щоб пропустити зміну або завалити її:

Список `ffs` — це і є харнес: додати нову вісь (скажімо, «жоден пакет команди A не залежить від пакета команди B») означає дописати сюди ще один рядок тієї самої форми.

## Пастки: де харнес починає брехати

Написане працює, але цілісні перевірки, що торкаються живої системи, підступніші за статичні — і саме на них харнес втрачає довіру команди. А харнес, якому не вірять, тихо вимикають — і петля еволюції знову перетворюється на деградацію. Три пастки варто знати заздалегідь.

**Флапаюча цілісна ФФ — вимір, що мигтить.** Бюджет часу міряють на живій системі, а живий вимір **дрижить**: пауза збирача сміття, сусід по спільному раннеру, стрибок мережі — і p95 на кількох запитах підскакує без жодної справжньої регресії. Перевірка падає то зеленим, то червоним на **тому самому** коді, і команда швидко вивчає рефлекс «а, знову мигнуло, перезапусти». Тієї миті сторож перетворюється на шум. Лік — зробити вимір **правдивим**: досить велика вибірка й прогрів перед заміром (щоб не ловити холодний старт), стабільна перцентиль над достатнім вікном, а не над жменею запитів, вимір на контрольованому стенді, а не на галасливому спільному раннері, і — головне — **запас** між бюджетом воріт і справжньою цільовою межею, щоб звичайний шум не перетинав лінію. Ворота мають падати від регресії, а не від тремтіння.

**Повільна ФФ, яку вимикають.** Цілісна перевірка, що збирає артефакт і ганяє навантаження, коштує хвилини — а повільні ворота першими йдуть під ніж «на час авралу». Тому харнес **розшаровують за ціною**: дешеве й статичне (шари, цикли, розмір артефакту) лишають на кожному комміті, дорогий вимір часу виносять на злиття чи в ніч, збірку кешують, навантаження дають на представницький зріз, а не на весь світ. Швидкі ворота, що біжать завжди, стережуть краще за ідеальні, які ганяють раз на тиждень, бо між рідкими прогонами встигає натекти стільки порушень, що розплутувати їх так само боляче, як і без воріт.

**Хибний зелений — найглибша пастка.** Уявіть найгірше: перевірка світиться зеленим не тому, що все добре, а тому, що вона **нічого не перевірила**. Збирач графа дістав порожню теку (хтось перейменував корінь) — нуль модулів, нуль ребер, нуль порушень, `acyclic` радісно повертає «DAG тримається». Або складання тихо впало, а `measureLive` прочитав **старий** `dist/bundle.js` із учорашнього прогону. Зелене, що означає «я нічого не бачив», гірше за червоне: воно присипляє пильність — усі думають, що осі стережуть, а сторож давно спить. Лік один — **фейлити закрито, а не відкрито**: харнес мусить сам переконатися, що бачив нетривіальний вхід, і падати, коли ні.

:::tabs

Спільна нитка всіх трьох пасток одна: **зелений вирок вартий рівно стільки, скільки вартий вимір за ним**. Цілісна ФФ дає найбільше — вона єдина ловить розміни між осями, — але й найлегше бреше, якщо її не тримати швидкою й правдивою. Тому кожну нову цілісну перевірку заводять з тим самим питанням: як саме вона може дати хибний зелений, і що падає закрито, коли дасть.

## Як суміш осей стереже систему цілком

Зберімо думку докупи, бо саме зв'язка дає підхід, а не кожна ФФ окремо. Три перевірки в харнесі — різної природи не випадково. Дві атомарні ловлять структурний дрейф: правило шарів — локально, ребро за ребром; інваріант DAG — глобально, за формою всього графа. Одна цілісна ловить те, чого не бачить жодна атомарна поодинці: **розмін між осями**, коли зміна виправила швидкодію коштом постачання. Атомарні кажуть «ця межа ціла»; цілісна каже «ці межі не куплено одна за одну».

І тепер видно, чому набір, а не одна перевірка, і є втілення «напрямної зміни за кількома вимірами». Кожна вісь дістає свого сторожа спільної форми; усі сторожі біжать на **тій самій** зміні; один код виходу зводить їхні вироки у ворота. Зміна проходить, лише коли тримаються **всі** осі одразу — а це рівно те, чого вимагає означення: не одну властивість стерегти, а весь набір вимірів разом. Додати вимір під нагляд — дописати ще одну фітнес-функцію в список; система росте, а харнес доростає з нею. Так «напрямна зміна за кількома вимірами» перестає бути гарною фразою й стає кодом, що біжить на кожен комміт і не дає жодній осі тихо просісти, поки латають сусідню.
