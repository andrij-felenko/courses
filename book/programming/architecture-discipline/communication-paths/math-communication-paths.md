# 🧮 Скільки зв'язків у команді: арифметика, з якої росте квадрат

Формула комунікаційних шляхів — `n·(n−1)/2` — виглядає як дрібничка, яку можна вивести за пів хвилини й забути. Але за нею стоїть один із найупертіших законів у житті команд: **вартість «усі говорять з усіма» росте не як розмір групи, а майже як його квадрат.** І щойно ти по-справжньому зрозумієш, *чому* саме `n²`, а не `n` і не `n³`, ти почнеш бачити цей квадрат усюди — у тому, чому команда з десяти раптом застрягає, чому «додати людей» рідко рятує строк, чому індустрія одержимо ріже монолітами на сервіси. Тож розберімо це число до самого дна: звідки воно, чому саме таке, і що воно насправді каже про межу, за яку група не масштабується.

## Означення: що ми взагалі рахуємо

Спершу треба чітко назвати об'єкт підрахунку, бо тут легко змішати два різні числа.

Є `n` людей. **Комунікаційний шлях** — це **невпорядкована пара** різних людей, канал між двома, яким вони можуть узгоджувати роботу. Невпорядкована — бо канал між Анною і Богданом той самий, що між Богданом і Анною; це один зв'язок, не два. Різних — бо сам із собою ніхто не «узгоджує стик». Питання формули: **скільки таких пар можна скласти з `n` людей?**

Позначмо цю кількість `P(n)`. Мова комбінаторики зве її **числом сполук по два з `n`** (лат. *combinatio* — поєднання) і пише `C(n, 2)`, читається «це з ен по два»:

```
P(n) = C(n, 2) = число способів вибрати 2 предмети з n,
                 коли порядок вибору байдужий
```

Ось і вся постановка. Тепер — три різні способи це порахувати, бо кожен висвітлює свою грань того самого числа, і разом вони роблять формулу очевидною, а не завченою.

## Виведення перше: кожен тисне руку кожному, і ділимо надвоє

Це найпряміший шлях, і він одразу пояснює загадкове `/2`.

Постав `n` людей у коло й попроси кожного потиснути руку кожному іншому. Візьми одну людину — скажімо, Анну. Скільки рук вона тисне? Усіх, окрім себе, тобто `n − 1`. Те саме для Богдана: `n − 1`. І для кожного з `n` учасників — рівно `n − 1` потисків. Перемножмо:

```
n людей × (n − 1) потисків кожен = n·(n − 1) потисків
```

Але тут схована подвійність, і саме вона — серце формули. Коли Анна тисне руку Богданові, це **той самий** потиск, що коли Богдан тисне руку Анні. Ми ж у добутку `n·(n−1)` порахували його **двічі**: раз із боку Анни, раз із боку Богдана. Кожен реальний потиск ми зарахували двічі — з обох кінців. Отже, щоб дістати число *справжніх* потисків, поділи навпіл:

```
P(n) = n·(n − 1) / 2
```

> 🔧 **Навіщо це.** Оте `/2` — не косметика й не «щоб число було менше». Воно кодує фізичний факт: **зв'язок належить обом кінцям порівну**. Коли в реальному проєкті ти рахуєш вартість узгодження, ти рахуєш саме канали (пари), а не «вихідні контакти кожного»: одна домовленість про стик обслуговує обидві сторони, її не варто рахувати двічі. Плутанина «пари проти напрямків» — типова помилка на серветці, і рівно тут вона живе.

Перевірмо на дрібному, де можна перелічити руками. Три людини — Анна, Богдан, Василь. Пари: (А,Б), (А,В), (Б,В) — рівно три. Формула: `3·2/2 = 3`. Збігається. П'ятеро: `5·4/2 = 10`; випиши всі пари з п'яти імен — їх справді десять. Формула тримається.

## Виведення друге: додаємо людей по одному й дивимось, що приростає

Перше виведення дало відповідь, але не дало **відчуття росту**. А нас цікавить саме ріст — як `P(n)` поводиться, коли команда набухає. Тож збудуймо число інакше: не одним махом, а **нарощуючи групу по одній людині** й питаючи щоразу — скільки *нових* зв'язків приніс новачок?

Почнімо з порожнечі й додаваймо.

```
було 1 людина  → пар: 0   (нема з ким)
+1 → 2 людини  → новачок додав 1 зв'язок (з тим, хто був) → усього 1
+1 → 3 людини  → новачок додав 2 (з обома, хто були)      → усього 3
+1 → 4 людини  → новачок додав 3                          → усього 6
+1 → 5 людей   → новачок додав 4                          → усього 10
+1 → 6 людей   → новачок додав 5                          → усього 15
```

Ось воно, головне спостереження, задля якого це виведення й потрібне: **k-та людина, входячи в групу, де вже було `k−1` осіб, приносить рівно `k−1` нових зв'язків** — по одному до кожного, хто там уже сидів. Не один зв'язок. Не сталу кількість. А стільки, скільки в групі *вже* людей.

Тому повне число пар — це сума приростів:

```
P(n) = 0 + 1 + 2 + 3 + … + (n − 1)
```

Сума перших `n−1` натуральних чисел. І тут спрацьовує старий трюк, який приписують малому Карлові Гаусу (нім. *Carl Friedrich Gauss*): склади ряд сам із собою, записаний навпаки, і побачиш пари, що дають однакову суму.

```
        S =   1  +   2  +  3  + … + (n−2) + (n−1)
        S = (n−1) + (n−2) + …  +   2   +   1
      ─────────────────────────────────────────
       2S =  n   +   n  +  n  + … +   n   +   n     ← (n−1) доданків, кожен = n
```

Кожен стовпчик дає `n` (бо `1+(n−1)=n`, `2+(n−2)=n`, і так далі), а стовпчиків рівно `n−1`. Отже `2S = n·(n−1)`, звідки `S = n·(n−1)/2` — те саме число. Два різні шляхи зійшлися в одну точку, і це не збіг: вони рахують одну множину пар, просто в різному порядку.

> 🔧 **Навіщо це.** Це виведення дає те, чого не дало перше, — **маргінальну ціну ще однієї людини**. Наймаєш у команду з двадцяти двадцять першого — він приносить не «трохи більше роботи», а **двадцять** нових каналів, які хтось має обслуговувати. Саме цей приріст `n−1`, що росте з кожним наймом, а не саме `P(n)`, відчувають на собі команди: чим більша група, тим *дорожче* коштує кожен наступний член — не тому, що він гірший, а тому, що він в'яжеться з дедалі більшою кількістю людей.

## Виведення третє: це просто ребра повного графа

Третій погляд — найкоротший і водночас найглибший, бо він прив'язує наше число до цілого розділу математики й дозволяє позичити готові результати.

Намалюй `n` людей крапками (вершинами) і з'єднай **кожну пару** лінією (ребром). Дістанеш фігуру, яку в теорії графів звуть **повним графом** на `n` вершинах і позначають `Kₙ` (K — від нім. *komplett*, повний). У повному графі є всі можливі ребра — і жодного зайвого. А ребро — це рівно наша невпорядкована пара. Тому:

```
число комунікаційних шляхів у групі з n людей = число ребер у Kₙ
```

І тут спрацьовує фундаментальна теорема теорії графів — **лема про рукостискання** (англ. *handshaking lemma*), яку строго довів ще [Леонард Ойлер](book:math/graph-theory) (нім. *Leonhard Euler*) 1736 року, розбираючи задачу про кеніґсберзькі мости. Лема каже: **сума степенів усіх вершин дорівнює подвоєному числу ребер.**

```
Σ (степінь кожної вершини) = 2 · (число ребер)
```

Чому подвоєному — з тієї ж причини, що й наше `/2`: кожне ребро має **два кінці**, тож, обходячи вершини й рахуючи, скільки ребер стирчить із кожної, ти лічиш кожне ребро двічі — по разу з кожного кінця. У повному графі `Kₙ` кожна вершина сполучена з усіма іншими, тобто має степінь `n−1`. Вершин `n`, отже сума степенів — `n·(n−1)`. За лемою це подвоєне число ребер, тож ребер:

```
ребер у Kₙ = n·(n − 1) / 2
```

Знову те саме. Три незалежні дороги — прямий підрахунок, нарощування, теорія графів — привели в одну точку. Коли результат стійкий до способу виведення, це вже не формула, яку треба пам'ятати, а **факт про світ**, який годі спростувати.

> 🔧 **Навіщо це.** Погляд «команда — це граф `Kₙ`» — не прикраса. Він відкриває цілий інструментарій: щойно ти бачиш людей вершинами, а канали ребрами, ти можеш **навмисне видаляти ребра** (зменшувати зв'язність), і граф перестає бути повним — а разом із ним падає й число `P`. Саме це робить архітектор, коли ріже команду на автономні групи: він переводить структуру з дорогого `Kₙ` у дешевший граф із рідкими ребрами між кластерами. Формула ребер — це лічильник ціни; теорія графів — важіль, яким цю ціну знижують.

![Повні графи K₃, K₅ і K₁₀: три вершини з трьома ребрами, п'ять із десятьма, десять із сорока п'ятьма — видно, як павутина ребер густішає набагато швидше за коло вершин](/book/programming/architecture-discipline/communication-paths/img/complete-graphs.svg)

*Кожна людина — вершина, кожен канал — ребро; повний граз означає «всі говорять з усіма». Вершини додаються по колу рівномірно, а ребра всередині вибухають — у цьому наочна суть квадратичного росту.*

## Чому саме квадрат: розкриваємо дужки

Ми маємо число. Тепер головне питання всієї теми: як швидко воно росте? Розкриймо добуток і подивімось на нього як на многочлен:

```
P(n) = n·(n − 1) / 2 = (n² − n) / 2 = ½·n² − ½·n
```

Це квадратний многочлен від `n`. Він має два доданки — `½·n²` і `−½·n` — і вони змагаються за те, хто визначає поведінку. На малих `n` вони порівнянні, але щойно `n` росте, квадратичний доданок **безнадійно обганяє** лінійний, бо `n²` росте швидше за `n`. Порахуймо їхнє співвідношення: `(½·n²) / (½·n) = n`. Тобто квадратичний доданок більший за лінійний рівно в `n` разів. При десяти людях — у десять разів, при ста — у сто. Лінійний доданок стає похибкою, шумом на тлі квадрата.

Тому для великих `n` можна сміливо казати: `P(n)` **поводиться як `n²`** (з точністю до сталого множника ½ і зникомого лінійного хвоста). Формально це записують так:

```
P(n) = Θ(n²)
```

Позначка `Θ` (грец. «тета») — це **точний порядок росту**. Запис `P(n) = Θ(n²)` означає строгу річ: існують дві додатні сталі, `c₁` і `c₂`, і поріг `n₀`, такі що для всіх `n ≥ n₀`

```
c₁·n²  ≤  P(n)  ≤  c₂·n²
```

Простими словами: `P(n)` затиснуте між двома параболами `n²` — знизу й зверху. Воно не може рости повільніше за `n²` (не `Θ(n)`), бо тоді не було б нижньої межі `c₁·n²`; і не може швидше (не `Θ(n³)`), бо є верхня `c₂·n²`. Перевірмо, що межі справді існують. Візьмімо `n ≥ 2`:

```
верхня межа:  P(n) = ½n² − ½n  ≤  ½n²           → тобто c₂ = ½ годиться
нижня межа:   при n ≥ 2 маємо  n ≥ 2, отже −½n ≥ −¼n²,
              звідки P(n) = ½n² − ½n ≥ ½n² − ¼n² = ¼n²  → c₁ = ¼ годиться
```

Отже для всіх `n ≥ 2` виконано `¼·n² ≤ P(n) ≤ ½·n²`. Число пар назавжди затиснуте між чвертю й половиною `n²`. Це і є суворий сенс фрази «росте квадратично»: не приблизно, не на око — а доведено затиснуте між двома параболами.

> 🔧 **Навіщо це.** `Θ(n²)` — не педантизм, а прогноз. Він каже: **подвоїш команду — учетверо зросте вартість зв'язків.** Бо якщо `P` пропорційне `n²`, то заміна `n` на `2n` дає `(2n)² = 4n²` — рівно вчетверо. Потроїш команду — удев'ятеро. Це та сама механіка, за якою `O`-нотацію вживають для алгоритмів: вона відкидає несуттєве (сталі, дрібні доданки) і лишає **закон масштабування** — єдине, що справді важить, коли `n` велике. Для команди цей закон нещадний: лінійно більше людей коштують квадратично більше координації.

## Лінійне проти квадратичного: точка, де все ламається

Тепер зіставмо два ростá в лоб, бо саме їхнє зіткнення — математичне серце того, чому великі команди буксують.

Коли ти додаєш людину, приростають **дві** різні величини, і ростуть вони з різною швидкістю.

**Корисна праця** росте (у найкращому разі) **лінійно**: одна людина — одна пара рук, `k` людей — приблизно `k` одиниць роботи за одиницю часу. Пропорція `Θ(n)`. Це оптимістична межа — вона припускає, що робота ідеально ділиться й нема втрат; реальність гірша, але не краща за лінію.

**Вартість координації** росте **квадратично**: `Θ(n²)`, як ми щойно довели. Кожен новачок в'яжеться з усіма наявними.

Постав їх поруч і спитай: що переможе? На малих `n` лінія попереду — праці більше, ніж накладних витрат, група працює. Але дві криві мають різну *форму*: пряма й парабола. Парабола, хоч би з яким малим коефіцієнтом стартувала, рано чи пізно **перетне пряму й піде вгору крутіше назавжди**. Знайдімо ту точку перетину — умовно, коли «одиниць координації» стає більше, ніж «одиниць праці»:

```
праця(n)        ≈ a · n           (лінійний виграш, коефіцієнт a)
координація(n)  ≈ b · n·(n−1)/2   (квадратична ціна, коефіцієнт b)

рівність настає, коли:   a · n = b · n·(n−1)/2
скоротимо n (n>0):       a = b · (n−1)/2
розв'яжемо на n:         n = 2a/b + 1
```

Точна точка залежить від `a` (наскільки продуктивна людина) і `b` (наскільки дорогий один канал у цій команді). Але **сам факт перетину неминучий**: хай `b` мале (легке спілкування, гарні інструменти) — точка `n = 2a/b + 1` просто відсунеться далі, та вона *існує*. Немає такого `n`, для якого лінія назавжди попереду параболи. Ось чому будь-яка команда має стелю росту — не «якщо», а «на якому саме `n`».

![Дві криві на одних осях: пряма лінія «корисна праця» росте рівномірно, парабола «вартість координації» стартує нижче, але перетинає пряму й круто йде вгору; точка перетину підписана як межа, за якою координація з'їдає виграш](/book/programming/architecture-discipline/communication-paths/img/linear-vs-quadratic.svg)

*До точки перетину додавання людей допомагає — праці більше за накладні витрати. Після неї парабола координації обганяє лінію праці, і кожен новий член віднімає більше, ніж додає. Ця точка — математична межа розміру команди.*

Саме звідси випливає **закон Брукса** (англ. *Brooks's Law*) — «додавання людей до запізнілого проєкту робить його ще пізнішим», який сформулював [Фред Брукс](book:programming/communication-paths/hist-conway-law.md) 1975 року в «Міфічному людино-місяці». Люди часто переказують його як «спілкування росте експоненційно» — це **неточно**, і варто виправити раз назавжди: `n·(n−1)/2` — це **многочлен** (квадрат), а не показникова функція `2ⁿ`. Різниця величезна: квадрат при `n=50` дає 1225, а `2⁵⁰` — понад квадрильйон. Брукс мав рацію по суті (координація обганяє працю), але механізм — **квадратичний, не експоненційний**; сам Брукс у книзі наводить саме `n·(n−1)/2`. Точність тут не занудство: плутати `n²` з `2ⁿ` — означає не розуміти, наскільки саме важко, і приймати неправильні рішення про масштаб.

> 🔧 **Навіщо це.** Ось чому «кинути більше людей на пожежу» так часто підпалює сильніше. Новачок додає працю лінійно (та й то не одразу — спершу він її *віднімає*, поки хтось уводить його в контекст), а координацію — квадратично. Якщо проєкт уже за точкою перетину, кожен новий член математично гарантовано **сповільнює** ціле. Формула не радить «ніколи не наймати» — вона каже, **де** межа й **як** її відсунути: не збільшенням `n`, а зменшенням `b` (дешевший канал) або, радикальніше, розбиттям одного великого `Kₙ` на кілька малих графів.

## Як розбиття б'є квадрат: арифметика автономних команд

Тепер зберімо все докупи й покажімо математично, *чому* дроблення на автономні групи перемагає — бо це прямий наслідок квадратичності, а не архітектурна мода.

Ідея проста: квадрат жорстокий до **великого** `n`, але майже лагідний до **малого**. Розбий `n` людей на `g` груп по `m` осіб (`n = g·m`). Усередині кожної групи хай спілкуються всі — це `P(m) = m·(m−1)/2` пар на групу. Між групами лишаємо не всі пари, а по **одному тонкому контракту** на межу — скажімо, `g−1` контрактів, якщо групи вишикувати ланцюжком, або близько того. Порахуймо сумарну ціну й порівняймо з монолітом `P(n)`.

```
моноліт:      P(n)      = n·(n−1)/2                    ← один великий Kₙ
розбиття:     всередині = g · m·(m−1)/2                ← g малих Kₘ
              між        ≈ (g − 1)  тонких контрактів
              разом      = g·m·(m−1)/2 + (g − 1)
```

Підставмо конкретне: `n = 12`, розбите на `g = 3` групи по `m = 4`.

```
моноліт:      12·11/2                 = 66 пар
розбиття:     3 · (4·3/2) + (3 − 1)
            = 3 · 6       + 2
            = 18          + 2         = 20
```

**66 проти 20.** Та сама дюжина людей, та сама робота — а ціна координації впала більш ніж утричі. Звідки виграш? Уся суть у тому, що ми **розрізали одне велике `n²` на кілька маленьких**. Квадрат від дванадцяти — 66; а квадрат від чотирьох — лише 6, і навіть узятий тричі це 18. Множник ½ той самий, але аргумент квадрата став утричі меншим, а квадрат від утричі меншого — **вдев'ятеро** менший (`4² проти 12²`); навіть помножений на три групи, він виграє. Плюс дешевий місток між групами замість густої павутини.

Загальний висновок, який варто винести навіть без чисел: розбиття працює, **бо квадратична функція вигідна до дроблення аргументу**. Для будь-якої функції виду `n²` справджується `(a+b)² > a² + b²` — сума квадратів частин *менша* за квадрат цілого (на подвоєний добуток `2ab`, який і є «зекономленими» міжгруповими зв'язками, що ми їх викинули). Це чиста алгебра, і саме вона — фундамент під усією ідеєю мікросервісів, автономних команд і слабкого зчеплення: не платити `n²` за ціле, коли можна заплатити суму дрібних квадратів за частини.

## Крихітна модель у коді

Щоб число перестало бути гаслом, заведімо структуру команди **як дані** і змусимо машину порахувати обидва виведення — і суму степенів (лему про рукостискання), і формулу пар, — а тоді зважмо моноліт проти розбиття. Код реальний, компільований, без псевдокоду.

**Умова: порахувати число комунікаційних шляхів двома незалежними способами (лема про рукостискання й пряма формула — мусять збігтися), тоді порівняти один моноліт із 12 людей проти трьох автономних команд по 4.**

```cpp
#include <vector>
#include <cstdio>

// Число пар (комунікаційних шляхів) у групі з n людей: n·(n−1)/2.
// Порядок множення (n−1) перед діленням гарантує, що n·(n−1) — завжди
// парне (два послідовні цілі), тож ділення на 2 точне, без утрати дробу.
long long paths(long long n) {
    return n * (n - 1) / 2;
}

// Незалежна перевірка через лему про рукостискання:
// у повному графі кожна з n вершин має степінь (n−1);
// сума степенів = подвоєне число ребер, тож ребер = сума/2.
long long paths_via_handshake(long long n) {
    long long sum_of_degrees = 0;
    for (long long v = 0; v < n; ++v)
        sum_of_degrees += (n - 1);        // степінь кожної вершини у Kₙ
    return sum_of_degrees / 2;            // ребро лічиться з обох кінців
}

int main() {
    // 1) Дві формули мають дати те саме число — це наша страховка.
    for (long long n : {3, 5, 10, 20, 50}) {
        long long a = paths(n);
        long long b = paths_via_handshake(n);
        std::printf("n=%2lld:  формула=%lld  лема=%lld  %s\n",
                    n, a, b, (a == b ? "збіг" : "РОЗБІЖНІСТЬ!"));
    }
    std::printf("\n");

    // 2) Моноліт із 12 у купі проти трьох автономних команд по 4.
    long long mono = paths(12);

    std::vector<long long> teams = {4, 4, 4};
    long long inside = 0;
    for (long long t : teams) inside += paths(t);   // густо всередині кожної
    long long between = teams.size() - 1;           // тонкі контракти між ними

    std::printf("Моноліт (12 разом):        %lld шляхів\n", mono);
    std::printf("3 команди — усередині:     %lld шляхів\n", inside);
    std::printf("3 команди — між командами: %lld контракти\n", between);
    std::printf("Разом при розбитті:        %lld проти %lld\n",
                inside + between, mono);
    return 0;
}
```

```
n= 3:  формула=3  лема=3  збіг
n= 5:  формула=10  лема=10  збіг
n=10:  формула=45  лема=45  збіг
n=20:  формула=190  лема=190  збіг
n=50:  формула=1225  лема=1225  збіг

Моноліт (12 разом):        66 шляхів
3 команди — усередині:     18 шляхів
3 команди — між командами: 2 контракти
Разом при розбитті:        20 проти 66
```

Два рядки коду варті окремої уваги. По-перше, `paths` і `paths_via_handshake` рахують те саме число **різними шляхами** й завжди збігаються — це наша жива перевірка, що формула не помилка: якби десь був зайвий множник чи забуте ділення, розбіжність вилізла б одразу. По-друге, тип `long long` тут не перестраховка: `n·(n−1)` росте квадратично, і на команді в кількадесят тисяч (уся інженерія великої компанії) 32-бітове `int` тихо переповниться — а це рівно та пастка, від якої застерігає квадратичний ріст. Число, що росте як `n²`, першим ламає розрядність; хто працює з масштабом, тримає це в голові.

Модель, звісно, груба — реальні міжкомандні контракти не безкоштовні, і всередині групи говорять не всі пари однаково щільно. Але напрям вона показує чесно, і показує його **числом**, а не вірою: розрізати велике `n²` на суму дрібних квадратів — це не архітектурна релігія, це арифметика, яку щойно перевірив компілятор.
