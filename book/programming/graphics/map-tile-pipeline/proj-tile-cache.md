# ⚙️ Ядро тайлового кешу й планувальника: адреса, цінність, купа, політ

Тут зібрано на C++ те, що в справжніх картах зазвичай розповзається по десятку файлів: адреса тайла з арифметикою предка, кеш із межею в байтах і витісненням за близькістю до екрана, купа запитів із поколінням, таблиця польоту й квота завантажень на кадр. Разом це — п'ятсот рядків, які й вирішують, чи карта їде за пальцем, чи «доганяє» його з наростанням; і майже всі відомі помилки тайлових конвеєрів живуть не всередині цих п'яти шматків, а на стиках між ними.

## Задача

Кожного кадру потік малювання знає, які адреси йому потрібні: сто-півтораста трійок z/x/y плюс кільце запасу навколо екрана. Частина вже лежить розпакована в пам'яті. Решту треба десь узяти, і на це є 16.6 мілісекунди, з яких на всю нашу бухгалтерію можна витратити хіба десяту частину.

Від ядра вимагають шести речей одночасно:

- **знайти в пам'яті за наносекунди** й не платити за пошук навіть на промаху;
- **тримати межу в байтах**, а не в штуках, і викидати те, що зараз найдалі від ока;
- **упорядкувати замовлення** так, щоб центр екрана й свій рівень ішли першими;
- **не замовляти двічі** те, що вже летить;
- **дешево скасовувати** те, що застаріло, — і не скасовувати того, за що вже заплачено;
- **не з'їсти кадр** завантаженням текстур і не застигнути на замку, який тримає фоновий потік.

## Три рішення, на яких усе тримається

**Адресна арифметика — це зсуви.** Сітки рівнів вкладені: тайл рівня z рівно накриває чотири тайли рівня z+1. Тому предок, номер квадранта й пакування адреси в одне 64-бітне число — це кілька зсувів без жодного пошуку й без жодної алокації.

**Пріоритет і цінність — функції поточного вікна, тому їх не можна зберігати.** Щойно карта зрушила, змінилася цінність **усіх** записів одразу. Купа, впорядкована за старим вікном, стає не «трохи неточною», а просто неправильною. Звідси два висновки, які й визначають форму коду: купа запитів живе рівно одне покоління й перескладається щокадру, а порядок витіснення не підтримують — його рахують одним проходом у ту мить, коли справді треба когось викинути.

**Кеш належить одному потокові.** Розпакований кеш чіпає лише потік малювання. Фонові потоки не бачать його взагалі й спілкуються з ним через одну чергу, замок на якій тримають рівно стільки, скільки триває обмін двома векторами. Так зникає цілий клас гонитв — не тому, що їх акуратно синхронізували, а тому, що спільного стану просто немає.

*Спільного стану рівно чотири структури, і жодна з них не тримає піксельних даних — тільки адреси, ключі й покажчики.*

## Адреса: усе, що можна зробити зсувом

Адреса — не трійка, а четвірка. П'ятий байт її ключа несе `variant`: джерело (супутник чи схема), стиль, щільність пікселів, мова підписів. Забути його — це не «дрібна неточність», а кеш, який на екрані подвійної щільности назавжди віддає картинку звичайної.

```cpp
#include <algorithm>
#include <atomic>
#include <cassert>
#include <chrono>
#include <cmath>
#include <condition_variable>
#include <cstdint>
#include <cstdlib>
#include <deque>
#include <memory>
#include <mutex>
#include <queue>
#include <unordered_map>
#include <unordered_set>
#include <vector>

// Адреса тайла. variant — усе, що робить два тайли з тими самими z/x/y
// різними картинками: джерело, стиль, щільність, мова підписів.
struct TileId {
    int32_t  z = 0;
    int32_t  x = 0;
    int32_t  y = 0;
    uint32_t variant = 0;

    // Сітки вкладені, тому предок — це зсув, а не пошук.
    constexpr TileId parent() const noexcept {
        return TileId{ z - 1, x >> 1, y >> 1, variant };
    }
    constexpr TileId ancestor(int32_t up) const noexcept {
        return TileId{ z - up, x >> up, y >> up, variant };
    }
    // Який із чотирьох квадрантів предка займає цей тайл: 0…3.
    // Саме це число каже, яку чверть предка розтягувати на місце діри.
    constexpr int quadrant() const noexcept {
        return int(((y & 1) << 1) | (x & 1));
    }
    // Уся адреса в одному 64-бітному числі: z 6 біт, x і y по 24, variant 10.
    // Межі: z ≤ 24 (звідси x, y < 2²⁴) і variant < 1024 — з запасом
    // на будь-яку карту, яку віддає тайл-сервер.
    constexpr uint64_t key() const noexcept {
        return (uint64_t(uint32_t(z)) << 58)
             | (uint64_t(uint32_t(x)) << 34)
             | (uint64_t(uint32_t(y)) << 10)
             |  uint64_t(variant & 0x3FFu);
    }
};

constexpr bool operator==(const TileId& a, const TileId& b) noexcept {
    return a.key() == b.key();
}

// Карта замикається по довготі: тайл «за правим краєм світу» — це тайл
// біля лівого. Нормалізують ДО створення TileId: від'ємний x дав би
// і неправильний зсув у parent(), і чужий ключ у кеші.
constexpr int32_t wrapX(int32_t x, int32_t z) noexcept {
    const int32_t n = int32_t(1) << z;
    return ((x % n) + n) % n;
}

struct TileHash {
    size_t operator()(const TileId& t) const noexcept {
        uint64_t k = t.key();                        // фіналізатор splitmix64
        k ^= k >> 30;  k *= 0xbf58476d1ce4e5b9ull;
        k ^= k >> 27;  k *= 0x94d049bb133111ebull;
        k ^= k >> 31;
        return size_t(k);
    }
};
```

Три деталі варті пояснення.

`key()` укладає поля так, що число зростає разом із (z, x, y) — дамп кеша виходить упорядкований сам собою, без окремого компаратора. Порівняння адрес звелося до порівняння двох `uint64_t`, тому `operator==` не має жодної гілки.

Хеш **перемішує біти явно**. Ключі сусідніх тайлів різняться тільки молодшими бітами `y` — це найщільніший і найрегулярніший вхід, який може дістати [хеш-таблиця](book:algorithms/hash-table). Стандарт нічого не обіцяє про якість `std::hash` для цілих типів: реалізація має право повернути саме число. Три множення й три зсуви коштують дешевше за один довгий ланцюг колізій, тож питання закривають на місці, а не сподіваються на бібліотеку.

`quadrant()` виглядає дрібницею, але саме він перетворює «немає тайла» на «намалюй чверть предка»: молодший біт `x` каже ліворуч чи праворуч, молодший біт `y` — вгорі чи внизу.

## Цінність тайла: чому її не можна зберігати

Порядок витіснення задає одна функція. На вхід їй ідуть адреса й **поточне** вікно; на виході — число, де більше означає цінніше.

```cpp
struct Viewport {
    int32_t  zoom = 0;              // цілий рівень, який малюють цього кадру
    double   cx = 0, cy = 0;        // центр екрана в тайлових координатах цього рівня
    double   halfW = 1, halfH = 1;  // піврозміри екрана в тих самих одиницях
    uint32_t variant = 0;
    uint64_t generation = 0;        // росте на КОЖНУ зміну положення чи масштабу
};

// Квадрат нормованої відстані від центра екрана: 1.0 — приблизно край екрана.
// ldexp множить на 2ᵏ точно й без ділень, тому переведення тайла рівня t.z
// в одиниці рівня vp.zoom — це правка порядку числа, а не арифметика.
inline double dist2(const TileId& t, const Viewport& vp) noexcept {
    const int    shift = vp.zoom - t.z;
    const double tx = std::ldexp(t.x + 0.5, shift);
    const double ty = std::ldexp(t.y + 0.5, shift);
    const double dx = (tx - vp.cx) / vp.halfW;
    const double dy = (ty - vp.cy) / vp.halfH;
    return dx * dx + dy * dy;
}

// Цінність для КЕША: більше — цінніше; витісняємо найменш цінне.
inline double cacheValue(const TileId& t, const Viewport& vp) noexcept {
    if (t.variant != vp.variant) return -1e300;   // чужий стиль чи щільність — геть першим
    const int dl = std::abs(vp.zoom - t.z);
    double v = -2.0 * dl - dist2(t, vp);
    if (t.z < vp.zoom) v += 2.0;                  // предки закривають діри — тримаємо
    return v;
}
```

Дві сталі — `2.0` за рівень і `+2.0` предкам — не з естетики. Вони калібрують один порядок, який видно в числах:

```
тайл у центрі екрана, свій рівень          −0.4
той самий тайл біля краю екрана            −1.0     (d² = 1 за означенням)
предок цього тайла, рівень z−1     −2·1 − 0.5 + 2 = −0.5
дитина, що лишилася після віддалення  −2·1 − 0.4  = −2.4
сусід за екраном, d² ≈ 5                   −5.0
чужий variant                            −10³⁰⁰
```

Предок дешевший за свій тайл, але дорожчий за все, що за межами екрана, — а це рівно те, чого від нього хочуть: предків у піраміді на третину більше за нижній рівень, коштують вони мало, а рятують від дір завжди. Дитина бонусу не отримує навмисно: після віддалення її вчетверо більше на ту саму площу, і корисна вона рівно один короткий момент.

![Сітка тайлів, зафарбована за цінністю: центр екрана найтепліший, кути найхолодніші; збоку — формула й три особливі випадки](/book/programming/graphics/map-tile-pipeline/img/evict-value.svg)

*Цінність — це поле навколо екрана, а не позначка часу на записі. Тому воно й не зберігається: один рух карти зміщує все поле цілком.*

> 🔧 **Навіщо це.** Класичне «викидай те, до чого найдовше не зверталися» тут працює погано з конкретної причини: оператор веде карту вправо, тайли за лівим краєм стають найстарішими й вилітають першими — а через секунду він веде назад, і всі вони потрібні знову. Витрачено канал, час і батарею на те, що щойно було в руках. Позначка часу описує **минуле** звертання, а поле цінности — **наступне**, і на карті друге передбачуване, бо рука рухається неперервно.

## Кеш, обмежений байтами

```cpp
struct Raster {
    int32_t width = 0, height = 0, bytesPerPixel = 4;
    std::vector<uint8_t> pixels;
    // Скільки пам'яті РЕАЛЬНО зайнято, а не скільки мало б бути.
    size_t footprint() const noexcept { return pixels.capacity(); }
};

using RasterPtr = std::shared_ptr<const Raster>;

class TileCache {
public:
    explicit TileCache(size_t budgetBytes) : budget_(budgetBytes) {}

    // Влучання віддає ВОЛОДІННЯ. Покажчик у нутрощі кеша віддавати не можна:
    // до наступного кадру запис переїде на інше місце або зникне зовсім.
    RasterPtr find(const TileId& id) const {
        const auto it = index_.find(id);
        return it == index_.end() ? RasterPtr{} : entries_[it->second].raster;
    }

    void insert(const TileId& id, RasterPtr raster) {
        const size_t bytes = raster->footprint() + kEntryOverhead;
        const auto [it, fresh] = index_.emplace(id, entries_.size());
        if (!fresh) {
            Entry& old = entries_[it->second];
            bytes_ -= old.bytes;            // ← спершу відняти старе, і лише потім додати
            old.raster = std::move(raster);
            old.bytes  = bytes;
            bytes_ += bytes;
            return;
        }
        entries_.push_back(Entry{ id, std::move(raster), bytes });
        bytes_ += bytes;
    }

    void erase(const TileId& id) {
        const auto it = index_.find(id);
        if (it == index_.end()) return;
        const size_t i = it->second;
        bytes_ -= entries_[i].bytes;
        index_.erase(it);                   // ітератор далі не потрібен — знімаємо його першим
        const size_t last = entries_.size() - 1;
        if (i != last) {                    // дірку в масиві затикаємо останнім елементом
            entries_[i] = std::move(entries_[last]);
            index_.find(entries_[i].id)->second = i;   // переставленому — новий індекс
        }
        entries_.pop_back();
    }

    size_t bytes() const noexcept { return bytes_; }

    // Один прохід до НИЖНЬОЇ межі. Кличуть у потоці малювання й лише коли перебір.
    void trim(const Viewport& vp) {
        if (bytes_ <= budget_) return;
        const size_t target = size_t(double(budget_) * kLowWater);

        order_.resize(entries_.size());
        value_.resize(entries_.size());
        for (size_t i = 0; i < entries_.size(); ++i) {
            order_[i] = uint32_t(i);
            value_[i] = cacheValue(entries_[i].id, vp);
        }
        std::sort(order_.begin(), order_.end(),
                  [this](uint32_t a, uint32_t b) { return value_[a] < value_[b]; });

        // Спершу зібрати АДРЕСИ, і тільки потім видаляти: erase() переставляє
        // елементи вектора, і збережені індекси після першого ж видалення брешуть.
        victims_.clear();
        size_t freed = 0;
        for (const uint32_t i : order_) {
            if (bytes_ - freed <= target) break;
            freed += entries_[i].bytes;
            victims_.push_back(entries_[i].id);
        }
        for (const TileId& id : victims_) erase(id);
    }

private:
    struct Entry { TileId id; RasterPtr raster; size_t bytes; };

    // Entry + вузол хеш-таблиці + блок керування shared_ptr + заголовок алокатора.
    static constexpr size_t kEntryOverhead = 128;
    static constexpr double kLowWater      = 0.85;

    std::vector<Entry> entries_;
    std::unordered_map<TileId, size_t, TileHash> index_;
    size_t bytes_ = 0;
    size_t budget_;

    std::vector<uint32_t> order_;    // робочі буфери trim — щоб він не алокував
    std::vector<double>   value_;
    std::vector<TileId>   victims_;
};
```

Записи лежать у щільному векторі, а хеш-таблиця тримає лише індекси. Це дає локальність під час `trim`: прохід по цінності читає суміжну пам'ять, а не гуляє по вузлах таблиці. Платня за щільність — видалення через перестановку останнього елемента на місце вилученого, і саме через неї `find` не сміє віддавати `const Raster*`: до наступного кадру цей запис може виявитися зовсім іншим тайлом.

`shared_ptr<const Raster>` тут не церемонія, а те, що робить витіснення безпечним. Потік малювання взяв покажчик, за мить `trim` викинув запис із кеша — пікселі живі, бо на них є посилання, і помруть аж тоді, коли кадр домалюється. Слово `const` закриває другий бік: опублікований растр більше ніхто не переписує.

`trim` не підтримує впорядкованости — він її будує щоразу наново, бо цінність цілком залежить від вікна. Це виглядає марнотратно рівно доти, доки не помітити другу половину рішення: витісняють **не до стелі, а до 85 %**. Один прохід звільняє місце під півтори сотні наступних вставок, тобто на кілька секунд роботи; без цієї гістерези кеш опинявся б на самій межі й сортувався щокадру.

Три робочі вектори — поля класу, а не локальні змінні: після першого шторму вони вже потрібного розміру й більше не звертаються до алокатора.

## Купа запитів, що живе одне покоління

Ключ пріоритету — трійка, яку порівнюють лексикографічно.

```cpp
struct Request {
    TileId   id;
    uint64_t generation = 0;
    int32_t  levelDelta = 0;
    double   d2 = 0.0;
};

// Раніше йде той, у кого свіже покоління; далі — свій рівень; далі — центр.
inline bool better(const Request& a, const Request& b) noexcept {
    if (a.generation != b.generation) return a.generation > b.generation;
    if (a.levelDelta != b.levelDelta) return a.levelDelta < b.levelDelta;
    return a.d2 < b.d2;
}
// std::priority_queue кладе наверх «найбільший за Compare»,
// тому Compare мусить означати саме «гірший».
struct Worse {
    bool operator()(const Request& a, const Request& b) const noexcept {
        return better(b, a);
    }
};
```

Відстань бережуть **у квадраті**: корінь не змінює порядку, а коштує на кожному порівнянні всередині [купи](book:algorithms/priority-queue).

Тепер головне рішення планувальника. Коли карта зрушила, все, що чекає в купі, описує вже не той екран. Замість того щоб переоцінювати тисячі записів, купу **викидають цілком** — і той самий кадр за мікросекунду складе потребу наново й покладе актуальні запити з правильними ключами.

```cpp
class TileScheduler {
public:
    struct Flight {
        explicit Flight(uint64_t g) : startGeneration(g) {}
        uint64_t            startGeneration;
        std::atomic<bool>   abort{false};
        std::atomic<size_t> bytesReceived{0};
    };
    using FlightPtr = std::shared_ptr<Flight>;

    explicit TileScheduler(size_t maxInFlight) : maxInFlight_(maxInFlight) {}

    // ── Потік малювання ───────────────────────────────────────────────────
    // Нове покоління: усе, що чекало, більше не описує екран. Гуртом за борт.
    void newGeneration(uint64_t g) {
        {
            std::lock_guard<std::mutex> lock(m_);
            generation_ = g;
            heap_ = Heap{};        // у std::priority_queue немає clear()
            pending_.clear();      // те, що ще потрібне, цей же кадр покладе знову
        }
        cv_.notify_all();
    }

    void request(const TileId& id, const Viewport& vp) {
        {
            std::lock_guard<std::mutex> lock(m_);
            if (vp.generation != generation_) return;   // кадр спізнився — його потреба не наша
            if (inFlight_.count(id)) return;            // уже летить — мовчки приєдналися
            if (!pending_.insert(id).second) return;    // уже в купі цього покоління
            heap_.push(Request{ id, vp.generation,
                                std::abs(vp.zoom - id.z), dist2(id, vp) });
        }
        cv_.notify_one();
    }

    // ── Фонові потоки ─────────────────────────────────────────────────────
    // Блокується, доки не з'явиться робота або доки не скажуть спинитися.
    bool take(Request& out, FlightPtr& flight) {
        std::unique_lock<std::mutex> lock(m_);
        for (;;) {
            if (!heap_.empty() && inFlight_.size() < maxInFlight_) {
                const Request r = heap_.top();
                heap_.pop();
                pending_.erase(r.id);
                assert(r.generation == generation_);   // купу чистять на зміні покоління
                flight = std::make_shared<Flight>(r.generation);
                inFlight_.emplace(r.id, flight);
                out = r;
                return true;
            }
            if (stop_) return false;
            cv_.wait(lock);
        }
    }

    // Стирання запису про політ — робота ДЕСТРУКТОРА, а не щасливого шляху.
    class FlightGuard {
    public:
        FlightGuard(TileScheduler& s, TileId id) : s_(s), id_(id) {}
        ~FlightGuard() { s_.retire(id_); }
        FlightGuard(const FlightGuard&) = delete;
        FlightGuard& operator=(const FlightGuard&) = delete;
    private:
        TileScheduler& s_;
        TileId id_;
    };

    void retire(const TileId& id) {
        {
            std::lock_guard<std::mutex> lock(m_);
            inFlight_.erase(id);
        }
        cv_.notify_all();
    }

    // Скасувати в польоті можна ЛИШЕ те, що ще не прийняло жодного байта,
    // і лише коли всі з'єднання зайняті, а в купі чекає свіжий запит.
    void reclaimSlot() {
        std::lock_guard<std::mutex> lock(m_);
        if (heap_.empty() || inFlight_.size() < maxInFlight_) return;
        for (auto& [id, f] : inFlight_) {
            if (f->startGeneration == generation_) continue;                  // актуальний
            if (f->bytesReceived.load(std::memory_order_relaxed) != 0) continue;  // вже платимо
            f->abort.store(true, std::memory_order_relaxed);
            return;                                                           // одне з'єднання за раз
        }
    }

    void stop() {
        { std::lock_guard<std::mutex> lock(m_); stop_ = true; }
        cv_.notify_all();
    }

private:
    using Heap = std::priority_queue<Request, std::vector<Request>, Worse>;

    std::mutex              m_;
    std::condition_variable cv_;
    Heap                    heap_;
    std::unordered_set<TileId, TileHash>            pending_;
    std::unordered_map<TileId, FlightPtr, TileHash> inFlight_;
    uint64_t generation_ = 0;
    size_t   maxInFlight_;
    bool     stop_ = false;
};
```

Купа живе один кадр — і це не втрата, а точний розрахунок. За шістнадцять мілісекунд фонові потоки встигають зняти з неї кілька найкращих запитів; рівно ті, що були найкращими **на момент цього кадру**. Наступний кадр складе купу з нуля з новими ключами. Скасування «всього, що не почалося» виходить безкоштовним: воно звелося до одного присвоєння порожньої купи.

`pending_` — це просто множина адрес, які зараз лежать у купі. Вона потрібна, щоб та сама адреса не потрапила туди двічі: під час нерухомої карти покоління не змінюється, і без цієї перевірки кожен кадр докладав би ту саму сотню запитів. `inFlight_` тримає адреси, які вже полетіли. Разом ці дві таблиці й дають [об'єднання однакових запитів](book:programming/request-coalescing): друга й третя згадка адреси — байдуже, чи вона потрібна сама по собі, чи як предок-заповнювач для сусіда — не породжують ані байта трафіку.

`Flight` живе за `shared_ptr` навмисно. Фоновий потік тримає свою копію й читає `abort` без замка, а планувальник під замком може будь-коли стерти запис із таблиці — об'єкт від цього не помре. Обидва поля атомарні, бо їх пише один потік, а читає інший, і жодного порядку між ними не потрібно: `relaxed` тут не мікрооптимізація, а точний опис вимоги.

Політика скасування записана в `reclaimSlot` буквально. Обірвати запит, який уже прийняв байти, — заплатити двічі: встановлення з'єднання коштує кілька обертів по мережі, і повторне замовлення заплатить за них знову. Тому скасовують лише те, що стоїть на нулі, лише коли з'єднань більше немає, і лише по одному за раз.

## Кадр: злити, вставити, підрізати, вивантажити

Готові растри переходять із фонових потоків у потік малювання через одну чергу, замок якої тримають рівно на обмін двома векторами — той самий прийом, що й у [подвійній буферизації](book:programming/double-buffering).

```cpp
struct Ready {
    TileId    id;
    RasterPtr raster;
    uint64_t  generation;
};

class ReadyQueue {
public:
    void publish(Ready r) {
        std::lock_guard<std::mutex> lock(m_);
        q_.push_back(std::move(r));
    }
    // Забрати все одним обміном. Викликач подає ПОРОЖНІЙ вектор:
    // буфери просто міняються місцями, і після розігріву ніхто не алокує.
    void drain(std::vector<Ready>& out) {
        std::lock_guard<std::mutex> lock(m_);
        out.swap(q_);
        q_.clear();
    }
private:
    std::mutex m_;
    std::vector<Ready> q_;
};
```

Фоновий потік у циклі виглядає так:

```cpp
void workerLoop(TileScheduler& sched, ReadyQueue& ready, TileSource& source) {
    Request r;
    TileScheduler::FlightPtr flight;
    while (sched.take(r, flight)) {
        TileScheduler::FlightGuard guard(sched, r.id);   // запис зникне за БУДЬ-ЯКОГО виходу

        std::vector<uint8_t> encoded;
        if (!source.fetch(r.id, encoded, *flight)) continue;   // 404, обрив, скасування

        Raster raster;
        if (!decode(encoded, raster)) continue;

        // Байти вже заплачено. Навіть якщо тайл застарів для екрана — він піде
        // в кеш; рішення «малювати чи ні» ухвалює потік малювання, не ми.
        ready.publish(Ready{ r.id,
                             std::make_shared<const Raster>(std::move(raster)),
                             r.generation });
    }
}
```

`source.fetch` дивиться на `flight.abort` у своєму зворотному виклику й нарощує `flight.bytesReceived`, щойно поїхали перші байти; `decode` і `uploadTexture` — межі прикладу, вони належать бібліотеці зображень і графічному API. Адреси для потреби кадру дає арифметика [тайлової сітки](book:math/web-mercator-tiles).

А ось увесь кадр:

```cpp
void TileRenderer::beginFrame(const Viewport& vp) {
    if (vp.generation != lastGeneration_) {
        scheduler_.newGeneration(vp.generation);
        lastGeneration_ = vp.generation;
    }

    // 1. Забрати доспіле. У кеш кладемо ВСЕ: байти вже заплачено.
    drained_.clear();
    ready_.drain(drained_);
    for (Ready& r : drained_) {
        cache_.insert(r.id, r.raster);
        uploadQueue_.push_back(std::move(r));
    }
    // Черга на завантаження не має рости: викинуте з неї лишається в кеші
    // й підніметься наступного кадру, якщо ще буде потрібне.
    while (uploadQueue_.size() > kMaxUploadBacklog) uploadQueue_.pop_front();

    // 2. Скласти потребу кадру й замовити те, чого немає.
    need_.clear();
    for (const TileId& id : visibleTiles(vp)) {
        need_.insert(id);
        if (!cache_.find(id)) scheduler_.request(id, vp);
    }
    scheduler_.reclaimSlot();

    // 3. Підрізати кеш — один раз, тут, у відомій точці кадру.
    cache_.trim(vp);

    // 4. Квота завантажень текстур: і за штуками, і за часом.
    const auto deadline = frameStart_ + std::chrono::microseconds(kUploadBudgetUs);
    int uploaded = 0;
    while (!uploadQueue_.empty() && uploaded < kMaxUploadsPerFrame
           && std::chrono::steady_clock::now() < deadline) {
        Ready r = std::move(uploadQueue_.front());
        uploadQueue_.pop_front();
        if (!need_.count(r.id)) continue;    // поки летів, перестав бути потрібним
        uploadTexture(r.id, *r.raster);      // растр живий, поки живий shared_ptr
        ++uploaded;
    }
}
```

Порядок кроків тут не довільний. Спершу вставляють доспіле — щоб потреба кадру одразу знайшла його в кеші й не замовила вдруге. Потім складають потребу — і лише після цього підрізають, бо `trim` має бачити вже нове вікно. Завантаження текстур іде останнім, коли решта [бюджету кадру](book:programming/frame-budget) вже відома.

Квота подвійна навмисно. Лічильник штук захищає від очевидного випадку — тридцяти готових тайлів одночасно. Строк за годинником захищає від неочевидного: перше завантаження після зміни формату текстури може коштувати не сто мікросекунд, а кілька мілісекунд, і жодна константа «скільки штук» цього не передбачить. Перевірка `need_.count` — не оптимізація, а коректність: тайл, що приїхав уже непотрібним, лежить у кеші й чекає, а відеопам'ять на нього не витрачають.

## Складність і числа

```
TileId::parent, ancestor, quadrant, key    O(1)              зсуви, без пам'яті
cache.find                                 O(1) очікувано    хеш-таблиця
cache.insert                               O(1) амортизовано push_back + один запис
cache.erase                                O(1) очікувано    перестановка + правка індексу
cache.trim                                 O(n log n)        один прохід на шторм
scheduler.request                          O(log m)          вставка в купу
scheduler.take                             O(log m)          зняття вершини
scheduler.newGeneration                    O(m)              звільнити вектор купи
```

n — записів у кеші, m — запитів у купі. Обидва числа малі й обмежені зверху конструкцією, і це видно з арифметики:

```
тайл 256×256 RGBA        256 · 256 · 4          = 262 144 Б = 256 КіБ
запис у кеші             262 144 + 128          = 262 272 Б
кеш на 256 МіБ           268 435 456 / 262 272  ≈ 1023 записи      → n
потреба кадру 3200×1800  ≈ 108 видимих + кільце запасу ≈ 150 адрес → m
```

Тисяча записів — це `std::sort` приблизно на 10⁴ порівнянь, тобто десятки мікросекунд. Один такий прохід звільняє 15 % бюджету:

```
268 435 456 · 0.15 ≈ 40.3 МБ ≈ 153 тайли
```

Сто п'ятдесят вставок — це кілька секунд активного возіння карти. Отже `trim` бачить кадр разів у сто рідше, ніж сам кадр, і його вартість розчиняється. Якби записи були однакового розміру, `std::sort` можна замінити на `std::nth_element` із наперед порахованою кількістю жертв — стандарт обіцяє йому лінійність у середньому; при тисячі записів різниця не варта ускладнення, при сотні тисяч — варта.

Купа на півтори сотні елементів дає log₂150 ≈ 7.2 порівняння на операцію. `newGeneration` під час руху викидає її щокадру — це один `free` на вектор, мікросекунди.

## Де це ламається

**Лічильник штук замість байтів.** Тайл 256×256 RGBA — 256 КіБ, той самий тайл 512×512 — рівно мегабайт. Межа «дві тисячі тайлів» означає будь-що між 375 МіБ і 2 ГіБ залежно від того, який сервер відповів. Тому в `Entry` лежить `bytes`, а не одиниця. Той самий рядок ховає другу пастку, тоншу: `footprint()` бере `capacity()`, а не `size()` — вектор, який ріс подвоєнням, легко тримає вдвічі більше, ніж використовує, і ця різниця в кеші на гігабайт коштує сотні мегабайтів «нізвідки».

**Лічильник, що поїхав.** Найпідступніша помилка в `insert` — забути `bytes_ -= old.bytes` на перезаписі наявного ключа. Кеш працює, тайли віддаються, нічого не падає; просто `bytes_` повзе вгору швидше за реальність, `trim` починає викидати робочий набір, і карта йде в холостий цикл перезавантажень. Симптом читається як «кеш не працює», а причина — одне віднімання. Тому інваріант варто перевіряти: у зневаджувальній збірці — сума `entries_[i].bytes` проти `bytes_` раз на секунду.

**Скасування вже початих запитів.** Спокуса «на зміну вікна скасувати геть усе» під час руху вбивча: покоління змінюється щокадру, кожен запит скасовується за кілька мілісекунд після старту, і жоден не доживає до кінця. Карта, яку «оптимізували» скасуванням, не наповнюється взагалі, доки палець не зупиниться. Правило рятує однією умовою: у купі — скасовуємо все й безкоштовно; у польоті — тільки те, що на нулі байтів, і тільки коли потрібне з'єднання.

**Витік у таблиці польоту.** Якщо фоновий потік вийде раніше — 404, таймаут, виняток — і не зітре запис із `inFlight_`, адреса залишиться «в польоті» назавжди. `request` мовчки її пропускатиме, тайл не замовлять більше ніколи, і на карті буде одна діра, яка не заростає ніколи й тільки в одному місці. Знайти таке за симптомом майже неможливо. Ліки не в тому, щоб не забути `retire()` на кожному виході, а в тому, щоб виходів не рахувати: `FlightGuard` стирає запис у деструкторі — [ресурс прив'язаний до часу життя](book:programming/raii), і жодна нова гілка в коді не може цього зламати.

**Гонитва між розпакуванням і малюванням.** Три різні поломки з однієї причини — спільний стан там, де його могло не бути.

Перша: покласти кеш під спільний замок, щоб фонові потоки вставляли туди самі. Формально коректно, практично — потік малювання час від часу застигає рівно на той час, поки хтось усередині робить `trim` із сортуванням. Тому в цьому коді фонові потоки кеша **не бачать**; єдина спільна річ — вектор у `ReadyQueue`, і замок на ньому тримають на час перестановки покажчиків.

Друга: віддати з кеша `const Raster*`. Покажчик переживе `trim` цього ж кадру, і малювання піде по звільненій пам'яті. Ще веселіше без витіснення: `entries_.push_back` перевиділяє вектор, і всі раніше видані покажчики стають сміттям тихо, без жодного видимого приводу. `shared_ptr<const Raster>` знімає обидва випадки.

Третя: перевикористати буфер розпакування. Пул буферів здається розумною економією — доки той самий буфер не віддадуть під новий тайл, поки попередній ще малюють. Растр після `publish` — незмінний, і `const` у `RasterPtr` це не позначка наміру, а заборона на рівні типу.

**Ключ без варіанта.** І найтихіша з усіх: `variant`, забутий у `key()`. Кеш працює бездоганно на машині розробника й показує підписи чужою мовою або розмиту картинку на екрані подвійної щільности — і лише в тих користувачів, у кого налаштування відрізняються від типових. Десять бітів у ключі коштують нуль; їхня відсутність коштує тижня пошуків.
