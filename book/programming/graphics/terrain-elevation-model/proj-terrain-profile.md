# ⚙️ Профіль висот уздовж маршруту: кеш квадратів, хід сіткою, точний максимум

Тут зібрано робочий C++, який бере маршрут — ламану з пар «широта, довгота» — а віддає не ряд вибраних точок, а **ряд інтервалів із точними межами висоти рельєфу** в кожному, і на цій основі відповідає на два питання, заради яких профіль і будують: чи вистачає запасу над землею й чи видно одну точку з іншої. Три рішення в ньому відрізняються від очевидних, і саме вони відділяють правильну відповідь від правдоподібної.

## Задача

На вході — вершини маршруту: пари (широта, довгота) у [WGS-84](book:math/wgs84-datum). На диску — тека з градусними файлами `.hgt`: квадрати 1° × 1°, у кожному 3601 × 3601 знакових шістнадцятибітних висот у метрах, big-endian, рядки з півночі на південь, значення −32768 означає прогалину. Разом на регіон це десятки гігабайтів, і в пам'ять вони не влазять.

Від коду вимагають чотирьох речей одночасно.

**Не пропустити жодної комірки.** Перешкода завширшки з одну комірку — насип, скеля, щогла — має потрапити у відповідь, а не провалитися між точками вибірки.

**Дати точний максимум, а не оцінку.** Реконструкція всередині комірки відома аналітично, тож питати її вибіркою — це самому собі створювати похибку там, де її могло не бути.

**Не збрехати ні на межі квадратів, ні на прогалині.** Обидва місця дають правдоподібне число замість правильного й не викликають ані винятку, ані попередження.

**Укластися в мілісекунди на сотню кілометрів** — інакше планувальник маршруту не зможе перерахувати профіль, поки оператор тягне точку мишею.

## Три рішення, на яких усе тримається

**Адресу вузла рахують ПЕРШОЮ, квадрат — наслідок.** Звичний хід думки такий: знайти потрібний файл, відкрити його, узяти в ньому рядок і стовпець. З цього хибного порядку й народжується весь клас помилок «шов»: комірка на межі квадратів має кути в двох різних файлах, і код, який спершу вибрав файл, змушений щось із цим робити. Тут порядок обернено. Є **одна глобальна сітка вузлів** на всю планету, вузол має глобальну адресу (gi, gj), а який файл його обслуговує — обчислюється з цієї адреси в останню чергу. Комірка на межі просто бере чотири кути, кожен із яких сам знаходить свій файл. Шва тут не існує як поняття: немає моменту, у який його можна було б завести.

**Хід сіткою замість рівномірного кроку.** Рівномірний крок або пропускає комірки, або кілька разів питає ту саму, і жодне згущення кроку не дає гарантії: комірку, зрізану біля кута, відрізок перетинає на довжині, яка може бути як завгодно малою, тож будь-який фіксований крок її прогледить. Хід від перетину до перетину з лініями сітки — той самий, що в растеризації відрізка, — дає **кожну перетнуту комірку рівно один раз** і разом із нею параметри входу й виходу. Це алгоритм [Аманатідеса й Ву](https://www.eecs.yorku.ca/~amana/research/) (J. Amanatides, A. Woo, *A Fast Voxel Traversal Algorithm for Ray Tracing*, Proc. Eurographics '87, Amsterdam, серпень 1987) — він писався для трасування променя крізь воксельну сітку, і задача тут та сама з точністю до розмірности.

**Екстремум у комірці беруть точно, а не вибіркою.** Білінійна реконструкція має вигляд h = h₀₀ + c₁u + c₂v + c₃uv, а вздовж відрізка u й v лінійні за параметром. Підстановка дає **квадратний тричлен від параметра** — і його найбільше та найменше значення на відрізку [0, 1] знаходять формулою, а не пошуком: кінці плюс щонайбільше одна внутрішня точка, де похідна нульова. Одне ділення замість десятка вибірок, і відповідь при цьому не наближена, а точна.

![Ліворуч сітка комірок із відрізком, точками перетину з лініями сітки й позначеними відвіданими комірками; праворуч графік висоти вздовж відрізка всередині однієї комірки: парабола, хорда між кінцями й внутрішній максимум](/book/programming/graphics/terrain-elevation-model/img/grid-walk.svg)

*Хід дає повний список комірок, тричлен дає точний максимум у кожній. Вибірка з фіксованим кроком не дає ні першого, ні другого — і мовчки повертає менше число.*

## Кеш градусних квадратів

Файл відображають у пам'ять, а не читають у буфер: [сторінковий збій](book:unix-linux/page-fault) підтягне лише ті сторінки, яких код торкнувся, а під тиском пам'яті ядро викине їх само, бо вони чисті й мають копію на диску. Механіка [відображення файла в пам'ять](book:unix-linux/mmap-model) тут працює саме так, як задумана, — а скільки на цьому насправді заощаджено, залежить від напрямку маршруту, і нижче це пораховано точно.

```cpp
#include <algorithm>
#include <cmath>
#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <limits>
#include <list>
#include <string>
#include <unordered_map>
#include <unordered_set>
#include <vector>

#include <fcntl.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <unistd.h>

static constexpr int     SPD  = 3600;             // інтервалів сітки на градус (1″)
static constexpr int64_t GW   = int64_t(360) * SPD;   // ширина світу у вузлах
static constexpr int64_t GH   = int64_t(180) * SPD;   // висота світу у вузлах
static constexpr int16_t VOID = -32768;           // прогалина: НЕ число, арифметики не терпить

// Один градусний файл: N×N вузлів, big-endian int16, рядок 0 — північний край.
struct HgtTile {
    const uint8_t* data  = nullptr;
    size_t         bytes = 0;
    int            n     = 0;      // 3601 (1″) або 1201 (3″)
    int            step  = 0;      // інтервалів на градус: n − 1

    int16_t node(int row, int col) const noexcept {
        const uint8_t* p = data + 2 * (size_t(row) * n + col);
        // p[0] << 8 підіймається до int; звужуємо ЯВНО через uint16_t, щоб не
        // залежати від того, як стандарт трактує втрату старших бітів
        // (до C++20 — визначено реалізацією, з C++20 — обгортання).
        return int16_t(uint16_t((uint16_t(p[0]) << 8) | uint16_t(p[1])));
    }
};

class HgtLibrary {
public:
    HgtLibrary(std::string dir, size_t budgetBytes, int advice = MADV_NORMAL)
        : dir_(std::move(dir)), budget_(budgetBytes), advice_(advice) {}

    ~HgtLibrary() {
        for (Entry& e : lru_) ::munmap(const_cast<uint8_t*>(e.tile.data), e.tile.bytes);
    }

    // Висота у вузлі глобальної сітки. false — прогалина або немає покриття.
    // Значення КОПІЮЄТЬСЯ негайно: покажчик на квадрат назовні не виходить,
    // тому витіснення між двома викликами нікому не шкодить.
    bool node(int64_t gi, int64_t gj, int16_t& out) {
        gi = ((gi % GW) + GW) % GW;              // світ замикається по довготі
        if (gj < 0 || gj >= GH) return false;    // за полюс виходу немає

        const HgtTile* t = acquire(int(gi / SPD) - 180, 89 - int(gj / SPD));
        if (!t) return false;

        // Крок квадрата може бути грубішим за робочу сітку — тоді це
        // східчаста передискретизація; змішувати роздільності в одному
        // маршруті краще не тут, а заздалегідь, перегнавши 3″ у 1″.
        const int col = int(gi % SPD) * t->step / SPD;
        const int row = int(gj % SPD) * t->step / SPD;

        const int16_t h = t->node(row, col);
        if (h == VOID) return false;             // ← перевірка ДО будь-якої арифметики
        out = h;
        return true;
    }

private:
    struct Entry { uint64_t key; HgtTile tile; };

    static uint64_t keyOf(int lonDeg, int latDeg) noexcept {
        return (uint64_t(uint32_t(lonDeg + 180)) << 16) | uint32_t(latDeg + 90);
    }

    const HgtTile* acquire(int lonDeg, int latDeg) {
        const uint64_t k = keyOf(lonDeg, latDeg);
        if (k == memoKey_) return memoTile_;             // чотири кути комірки — майже завжди один квадрат
        if (missing_.count(k)) { memoKey_ = k; memoTile_ = nullptr; return nullptr; }

        if (auto it = index_.find(k); it != index_.end()) {
            lru_.splice(lru_.begin(), lru_, it->second); // список — ітератори переживають перестановку
            memoKey_ = k; memoTile_ = &lru_.front().tile;
            return memoTile_;
        }

        HgtTile t;
        if (!mapFile(lonDeg, latDeg, t)) {
            missing_.insert(k);   // ← без негативного кеша кожна вибірка над океаном робить невдалий open()
            memoKey_ = k; memoTile_ = nullptr;
            return nullptr;
        }

        memoKey_ = kNoKey; memoTile_ = nullptr;          // витіснення нижче може знести memo
        while (bytes_ + t.bytes > budget_ && lru_.size() >= kMinResident) {
            Entry& victim = lru_.back();
            ::munmap(const_cast<uint8_t*>(victim.tile.data), victim.tile.bytes);
            bytes_ -= victim.tile.bytes;
            index_.erase(victim.key);
            lru_.pop_back();
        }

        lru_.push_front(Entry{ k, t });
        index_[k] = lru_.begin();
        bytes_ += t.bytes;
        memoKey_ = k; memoTile_ = &lru_.front().tile;
        return memoTile_;
    }

    bool mapFile(int lonDeg, int latDeg, HgtTile& out) const {
        char name[32];
        std::snprintf(name, sizeof name, "%c%02d%c%03d.hgt",
                      latDeg < 0 ? 'S' : 'N', std::abs(latDeg),
                      lonDeg < 0 ? 'W' : 'E', std::abs(lonDeg));
        const std::string path = dir_ + "/" + name;

        const int fd = ::open(path.c_str(), O_RDONLY);
        if (fd < 0) return false;
        struct stat st {};
        if (::fstat(fd, &st) != 0) { ::close(fd); return false; }

        // Заголовка у .hgt немає взагалі — роздільність каже сам розмір файла.
        int n = 0;
        if      (st.st_size == 3601LL * 3601 * 2) n = 3601;
        else if (st.st_size == 1201LL * 1201 * 2) n = 1201;
        else { ::close(fd); return false; }

        void* p = ::mmap(nullptr, size_t(st.st_size), PROT_READ, MAP_PRIVATE, fd, 0);
        ::close(fd);                    // відображення тримає файл саме — дескриптор більше не потрібен
        if (p == MAP_FAILED) return false;

        // Підказку ядру дають ЗА ХАРАКТЕРОМ запиту, а не «про всяк випадок»:
        // хід уздовж маршруту рухається рядками майже монотонно, і попереднє
        // читання йому допомагає; розсіяним поодиноким вибіркам — шкодить.
        if (advice_ != MADV_NORMAL) ::madvise(p, size_t(st.st_size), advice_);

        out.data = static_cast<const uint8_t*>(p);
        out.bytes = size_t(st.st_size);
        out.n = n;
        out.step = n - 1;
        return true;
    }

    static constexpr uint64_t kNoKey = ~uint64_t(0);
    static constexpr size_t kMinResident = 4;   // комірка в куті квадрата чіпає рівно чотири файли

    std::string dir_;
    size_t      budget_;
    int         advice_;
    size_t      bytes_ = 0;

    std::list<Entry> lru_;                                    // найсвіжіший спереду
    std::unordered_map<uint64_t, std::list<Entry>::iterator> index_;
    std::unordered_set<uint64_t> missing_;

    uint64_t       memoKey_  = kNoKey;
    const HgtTile* memoTile_ = nullptr;
};
```

Три деталі варті окремого слова.

`kMinResident = 4` — не запобіжник від дурня, а точна межа. Комірка, що стоїть рівно в куті градусного квадрата, має чотири кути в чотирьох різних файлах; менша межа означала б, що читання четвертого кута витісняє квадрат, з якого щойно взято перший, і кожна така комірка коштувала б чотирьох `mmap` замість нуля.

`missing_` — негативний кеш, і без нього код над морем працює втричі повільніше, ніж над сушею. Океанські квадрати у сховищі просто відсутні; без пам'яті про це кожна вибірка йде в `open()`, отримує `ENOENT` і платить за системний виклик. Це та сама причина, з якої [кеш](book:programming/cache) взагалі мусить пам'ятати не лише влучання, а й промахи.

Межа кеша в байтах на 64-бітній машині обмежує не стільки пам'ять, скільки **кількість живих відображень і дескрипторів, які через них тримають файли**: сторінки самі по собі чисті й ядро забирає їх без нашої участи. Тому лічильник байтів тут — проксі, і чесно це знати: справжня стеля, у яку впирається довгий маршрут, — не резидентна пам'ять, а адресний простір і таблиця відображень процесу.

## Глобальна адреса вузла

Ось те місце, де рішення про порядок обчислення дає свій ужиток.

```
gi = (λ + 180°) · 3600        стовпець у світі, на схід від −180°
gj = (90° − φ)  · 3600        рядок у світі, на південь від +90°

квадрат:  lon = gi div 3600 − 180 ,  lat = 89 − gj div 3600
вузол:    col = gi mod 3600 ,        row = gj mod 3600
```

Зсуви на +180° і +90° стоять у цих формулах не для краси. Цілочислове ділення в C++ відкидає дріб **до нуля**, а не вниз: `-1 / 3600` дає `0`, а не `-1`. Тому в сирих градусах квадрат на захід від Гринвіча вибрався б на градус східніше, ніж треба, а на південь від екватора — на градус північніше, і ця помилка не відтворилася б у жодному тесті, поставленому в Європі. Зсунута сітка робить обидві координати невід'ємними, і питання зникає разом із гілкою, яка мала б його розв'язувати. Той самий рядок нормалізації gi по модулю світу потрібен саме на цю тему: після переходу через 180-й меридіан адреса комірки може вийти від'ємною, і без нормалізації ділення знову збрехало б.

Тепер головне. `col = gi mod 3600` ніколи не дорівнює 3600. Отже дубльований крайній стовпець кожного файла — той самий, що існує і як стовпець 3600 західного квадрата, і як стовпець 0 східного, — **читається рівно з одного місця**. Ані подвійного врахування межової лінії, ані розриву на стику: обидві помилки потребують коду, який їх робить, а такого коду тут нема.

![Ліворуч чотири градусні квадрати з маршрутом навскіс через їхній спільний кут; праворуч таблиця, у якій той самий глобальний вузол показано як стовпець 3600 західного файла і стовпець 0 східного, і комірка на межі з кутами у двох файлах](/book/programming/graphics/terrain-elevation-model/img/tile-seam.svg)

*Шов виникає тоді, коли спершу вибирають файл, а потім шукають у ньому вузол. У зворотному порядку зшивати нема чого.*

## Комірка й точний екстремум у ній

```cpp
struct Cell { double h00, h10, h01, h11; };   // 00 — вузол (gi, gj); 10 — схід; 01 — південь

// false, якщо ХОЧ ОДИН кут є прогалиною: інтерполювати прогалину не можна.
inline bool readCell(HgtLibrary& lib, int64_t gi, int64_t gj, Cell& c) {
    int16_t a, b, d, e;
    if (!lib.node(gi,     gj    , a) || !lib.node(gi + 1, gj    , b) ||
        !lib.node(gi,     gj + 1, d) || !lib.node(gi + 1, gj + 1, e)) return false;
    c = Cell{ double(a), double(b), double(d), double(e) };
    return true;
}

struct Range { double lo, hi; };

// Найменше й найбільше значення білінійної поверхні комірки на відрізку
// (u₀, v₀) → (u₀+du, v₀+dv), параметр τ ∈ [0, 1].
//
//   h(u, v) = h₀₀ + c₁·u + c₂·v + c₃·u·v
//   u = u₀ + du·τ ,  v = v₀ + dv·τ
//   ⟹ h(τ) = A·τ² + B·τ + C
//     A = c₃·du·dv
//     B = c₁·du + c₂·dv + c₃·(u₀·dv + du·v₀)
//     C = h₀₀ + c₁·u₀ + c₂·v₀ + c₃·u₀·v₀
inline Range cellRange(const Cell& c, double u0, double v0, double du, double dv) {
    const double c1 = c.h10 - c.h00;
    const double c2 = c.h01 - c.h00;
    const double c3 = c.h00 - c.h10 - c.h01 + c.h11;   // «перекіс» комірки

    const double A = c3 * du * dv;
    const double B = c1 * du + c2 * dv + c3 * (u0 * dv + du * v0);
    const double C = c.h00 + c1 * u0 + c2 * v0 + c3 * u0 * v0;

    const double h0 = C, h1 = A + B + C;
    Range r{ std::min(h0, h1), std::max(h0, h1) };

    // A == 0 — відрізок паралельний осі сітки: висота вздовж нього ЛІНІЙНА,
    // і кінці вже дали остаточну відповідь.
    if (A != 0.0) {
        const double tv = -B / (2.0 * A);
        if (tv > 0.0 && tv < 1.0) {
            const double hv = (A * tv + B) * tv + C;
            if (A < 0.0) r.hi = std::max(r.hi, hv);   // вітки вниз — усередині максимум
            else         r.lo = std::min(r.lo, hv);   // вітки вгору — усередині мінімум
        }
    }
    return r;
}
```

Число c₃ = h₀₀ − h₁₀ − h₀₁ + h₁₁ і є тим, через що ця морока має сенс. Воно міряє **перекіс** комірки — наскільки чотири кути не лежать в одній площині. На рівному схилі воно близьке до нуля, поверхня майже плоска, і вздовж відрізка висота майже лінійна: кінці дають усе. На зламі гребеня воно велике, і різниця стає відчутною.

**Комірка на плечі гребеня, крок 30 м: кути 1840, 1852, 1874, 1844 метра; відрізок іде повною діагоналлю з першого кута в четвертий.**

```
c₁ = 1852 − 1840 =  12
c₂ = 1874 − 1840 =  34
c₃ = 1840 − 1852 − 1874 + 1844 = −42

A = −42 · 1 · 1 = −42        B = 12 + 34 = 46        C = 1840

кінці:      h(0) = 1840        h(1) = −42 + 46 + 1840 = 1844
вершина:    τ* = −46 / (2·(−42)) = 0.5476
            h(τ*) = −42·0.2999 + 46·0.5476 + 1840 = 1852.6

максимум за кінцями:  1844 м
справжній максимум:   1852.6 м
різниця:               8.6 м
```

Вісім із половиною метрів на одній комірці — це більше, ніж уся похибка сучасних глобальних наборів, і ці метри губляться не в даних, а в тому, як їх спитали. Загальна межа тут проста: відхилення параболи від хорди не перевищує |A|/4, а |A| ≤ |c₃|, тож помилка «лише за кінцями» обмежена чвертю перекосу комірки. Властивості самого правила реконструкції розібрано в [білінійній інтерполяції](book:math/bilinear-interpolation), а форму вершини параболи дає звичайне [квадратне рівняння](book:math/quadratic-equations).

> 🔧 **Навіщо це.** Спокуса замінити тричлен вибіркою — «візьму п'ять точок усередині комірки, вистачить» — коштує дорожче й водночас дає гірше. П'ять вибірок означають п'ять обчислень білінійної форми з перерахунком u й v, тобто близько півсотні операцій; тричлен — це три коефіцієнти, два кінці, одне ділення й одна підстановка, десь двадцять п'ять. І вибірка з кроком Δτ принципово недобирає до |A|·Δτ²/4: на комірці з прикладу вище це ще пів метра, на різкому зламі гребеня — метр із гаком. Тричлен не недобирає нічого, бо він максимум не наближає, а знаходить.

## Хід сіткою

```cpp
struct CellHit {
    int64_t gi, gj;      // адреса комірки в глобальній сітці
    double  t0, t1;      // параметр уздовж відрізка на вході й на виході
};

// Хід Аманатідеса–Ву: від перетину до перетину з лініями сітки.
template <class F>
void walkSegment(double x0, double y0, double x1, double y1, F&& visit) {
    const double dx = x1 - x0, dy = y1 - y0;
    const double INF = std::numeric_limits<double>::infinity();

    // floor, а НЕ приведення до цілого: (int)(-0.5) дає 0, а треба −1.
    // Після поправки на 180-й меридіан координата тут буває від'ємною.
    int64_t i = int64_t(std::floor(x0)), j = int64_t(std::floor(y0));
    const int64_t iEnd = int64_t(std::floor(x1)), jEnd = int64_t(std::floor(y1));

    const int si = dx > 0 ? 1 : (dx < 0 ? -1 : 0);
    const int sj = dy > 0 ? 1 : (dy < 0 ? -1 : 0);

    const double tdx = si ? std::fabs(1.0 / dx) : INF;   // приріст t на одну комірку
    const double tdy = sj ? std::fabs(1.0 / dy) : INF;
    double tmx = si > 0 ? (double(i) + 1.0 - x0) / dx
               : si < 0 ? (double(i)       - x0) / dx : INF;   // t до найближчої вертикалі
    double tmy = sj > 0 ? (double(j) + 1.0 - y0) / dy
               : sj < 0 ? (double(j)       - y0) / dy : INF;   // t до найближчої горизонталі

    // Кількість кроків відома НАПЕРЕД. Це і межа циклу, і захист від того,
    // що накопичена похибка порівнянь t не дасть ходові дійти до кінця.
    const int64_t steps = (iEnd > i ? iEnd - i : i - iEnd) + (jEnd > j ? jEnd - j : j - jEnd);

    double t = 0.0;
    for (int64_t k = 0; k <= steps; ++k) {
        const double tNext = (k == steps) ? 1.0 : std::min(std::min(tmx, tmy), 1.0);
        visit(CellHit{ i, j, t, tNext });
        if (tNext >= 1.0) return;
        t = tNext;
        if (tmx < tmy) { i += si; tmx += tdx; }   // крокуємо туди, де перетин ближчий
        else           { j += sj; tmy += tdy; }
    }
}
```

Увесь алгоритм — у порівнянні `tmx < tmy`. Кожна з двох величин каже, скільки ще параметра лишилося до найближчої лінії сітки свого напрямку; менша й визначає, крізь яке ребро відрізок вийде з поточної комірки. Після кроку відповідна величина зростає рівно на «ціну» однієї комірки в цьому напрямку — а ціна стала, бо комірки однакові.

Три ситуації, у яких наївний варіант ламається, тут закриті будовою. Вертикальний або горизонтальний відрізок дає нескінченність замість `tdx` чи `tdy` — порівняння з нескінченністю коректне, і хід іде однією віссю без жодної особливої гілки. Точна діагональ, де `tmx == tmy`, бере `else`-гілку, потім наступного разу — `if`-гілку з тим самим t, і видає одну комірку з нульовою довжиною влучання: марна, але не помилкова, і `cellRange` на ній просто двічі порахує ту саму точку. А відрізок, що не виходить за межі однієї комірки, дає `steps == 0` і рівно одне влучання [0, 1].

## Профіль і два запити

Ребро маршруту в координатах «широта–довгота» — це не велике коло. Різниця росте як квадрат довжини ребра, і на дистанціях, які реально літають, вона вже не косметична.

**Ребро 100 км строго на схід, широта 50°.**

```
1° довготи на 50°   = 111.32 · cos 50° = 71.56 км
Δλ = 100 / 71.56    = 1.3975°          = 0.024391 рад

відхилення великого кола від прямої в координатах:
Δφ ≈ (Δλ² / 16) · sin 2φ = (5.949·10⁻⁴ / 16) · 0.9848 = 3.662·10⁻⁵ рад
у метрах            = 3.662·10⁻⁵ · 6 371 000 = 233 м
```

Двісті тридцять метрів убік — це вісім комірок сітки: профіль побудують уздовж лінії, якою апарат не полетить. Тому довгі ребра ріжуть на шматки, кожна вершина яких лежить **точно** на великому колі, і лише всередині шматка йдуть прямою. Квадратична залежність тут працює на нас: десятикілометровий шматок дає в сто разів менше відхилення, тобто 2.3 метра — менше за десяту частину комірки, і далі дрібнити нема сенсу.

```cpp
struct Geo  { double lat, lon; };            // градуси
struct Vec3 { double x, y, z; };

static constexpr double kDeg = 3.14159265358979323846 / 180.0;
static constexpr double kR   = 6371000.0;    // середній радіус Землі, м
static constexpr double kMaxLeg = 10000.0;   // довша ділянка ріжеться на шматки, м

inline Vec3 toVec(const Geo& g) {
    const double la = g.lat * kDeg, lo = g.lon * kDeg, c = std::cos(la);
    return Vec3{ c * std::cos(lo), c * std::sin(lo), std::sin(la) };
}
inline Geo toGeo(const Vec3& v) {
    return Geo{ std::atan2(v.z, std::sqrt(v.x * v.x + v.y * v.y)) / kDeg,
                std::atan2(v.y, v.x) / kDeg };
}
// Центральний кут через atan2 від синуса й косинуса: чистий acos(dot)
// втрачає значущі цифри саме на малих кутах, а тут вони й є.
inline double centralAngle(const Vec3& a, const Vec3& b) {
    const Vec3 c{ a.y * b.z - a.z * b.y, a.z * b.x - a.x * b.z, a.x * b.y - a.y * b.x };
    return std::atan2(std::sqrt(c.x * c.x + c.y * c.y + c.z * c.z),
                      a.x * b.x + a.y * b.y + a.z * b.z);
}
inline Geo slerp(const Vec3& a, const Vec3& b, double ang, double f) {
    if (ang < 1e-12) return toGeo(a);
    const double s = std::sin(ang);
    const double ka = std::sin((1.0 - f) * ang) / s, kb = std::sin(f * ang) / s;
    return toGeo(Vec3{ ka * a.x + kb * b.x, ka * a.y + kb * b.y, ka * a.z + kb * b.z });
}
```

Профіль — це послідовність **ділянок**, а не точок. Кожна ділянка відповідає одній перетнутій комірці, і в ній лежать точні межі висоти рельєфу.

```cpp
struct ProfileSpan {
    double s0, s1;      // від і до, метри від початку маршруту (по великому колу)
    double lo, hi;      // ТОЧНІ межі висоти рельєфу на цій ділянці, м AMSL
    bool   known;       // false — у комірці прогалина: відповіді немає взагалі
};

inline double gxOf(double lon) { return (lon + 180.0) * SPD; }
inline double gyOf(double lat) { return (90.0  - lat) * SPD; }

std::vector<ProfileSpan> buildProfile(HgtLibrary& lib, const std::vector<Geo>& route) {
    std::vector<ProfileSpan> out;
    double travelled = 0.0;

    for (size_t v = 0; v + 1 < route.size(); ++v) {
        const Vec3 va = toVec(route[v]), vb = toVec(route[v + 1]);
        const double ang = centralAngle(va, vb), edge = ang * kR;
        const int parts = std::max(1, int(std::ceil(edge / kMaxLeg)));

        for (int q = 0; q < parts; ++q) {
            const Geo a = slerp(va, vb, ang, double(q)     / parts);
            const Geo b = slerp(va, vb, ang, double(q + 1) / parts);
            const double legLen = edge / parts;

            double x0 = gxOf(a.lon), y0 = gyOf(a.lat);
            double x1 = gxOf(b.lon), y1 = gyOf(b.lat);
            // 180-й меридіан: іти коротшим боком, а не через увесь світ.
            if (x1 - x0 >  GW / 2.0) x1 -= GW;
            if (x1 - x0 < -GW / 2.0) x1 += GW;

            const double dx = x1 - x0, dy = y1 - y0, base = travelled;
            walkSegment(x0, y0, x1, y1, [&](const CellHit& h) {
                ProfileSpan s{ base + legLen * h.t0, base + legLen * h.t1, 0.0, 0.0, false };
                Cell c;
                if (readCell(lib, h.gi, h.gj, c)) {
                    // Локальні координати входу в комірку — і локальний приріст.
                    // Різниця (x₀ + dx·t − gi) віднімає два числа порядку 7·10⁵
                    // з відповіддю порядку одиниці. У double похибка лишається
                    // близько 10⁻¹⁰; у float сусідні представні значення там
                    // стоять через 1/16, і комірка перетворилася б на сходинки.
                    // Тому сіткова геометрія тут ЛИШЕ в double, а всередині
                    // комірки параметр уже свій і малий: τ ∈ [0, 1].
                    const double u0 = std::min(1.0, std::max(0.0, x0 + dx * h.t0 - double(h.gi)));
                    const double v0 = std::min(1.0, std::max(0.0, y0 + dy * h.t0 - double(h.gj)));
                    const double du = dx * (h.t1 - h.t0), dv = dy * (h.t1 - h.t0);
                    const Range r = cellRange(c, u0, v0, du, dv);
                    s.lo = r.lo; s.hi = r.hi; s.known = true;
                }
                out.push_back(s);
            });
            travelled += legLen;
        }
    }
    return out;
}
```

Тепер два запити, заради яких усе це й будувалося.

```cpp
// ── 1. Мінімальний запас над рельєфом ──────────────────────────────────────
struct Clearance {
    double minGap    = std::numeric_limits<double>::infinity();
    double atDistance = 0.0;
    bool   complete   = true;     // false — на маршруті є прогалини даних
};

// flightAmsl — саме НАД РІВНЕМ МОРЯ. Висота з навігаційного приймача відлічена
// від еліпсоїда; підставити її сюди — систематично занизити запас на ундуляцію.
Clearance minClearance(const std::vector<ProfileSpan>& p, double flightAmsl) {
    Clearance c;
    for (const ProfileSpan& s : p) {
        if (!s.known) { c.complete = false; continue; }   // ← не нуль і не «мовчки далі»
        const double gap = flightAmsl - s.hi;             // найгірше на ділянці
        if (gap < c.minGap) { c.minGap = gap; c.atDistance = s.s0; }
    }
    return c;
}

// ── 2. Пряма видимість A → B ───────────────────────────────────────────────
// Радіус першої зони Френеля в точці d траси довжиною D, м.
inline double fresnel1(double d, double total, double lambda) {
    return std::sqrt(lambda * d * (total - d) / total);
}

struct Sight {
    bool   clear      = true;   // ЧИТАТИ лише разом із complete: на суцільній
    double atDistance = 0.0;    // прогалині траса «вільна» просто через брак даних
    double margin     = std::numeric_limits<double>::infinity();  // ≤ 0 — перекрито
    bool   complete   = true;
};

Sight lineOfSight(const std::vector<ProfileSpan>& p,
                  double antennaA, double antennaB,   // м AMSL, разом із щоглою
                  double total,                        // повна довжина траси, м
                  double lambda = 0.0,                 // 0 — чиста геометрія, без Френеля
                  double kFactor = 4.0 / 3.0)          // 4/3 — рефракція для радіо
{
    Sight best;
    for (const ProfileSpan& s : p) {
        if (!s.known) { best.complete = false; continue; }
        for (const double d : { s.s0, s.s1 }) {
            // Здуття планети над хордою між кінцями траси піднімає рельєф.
            const double bulge = d * (total - d) / (2.0 * kFactor * kR);
            const double need  = lambda > 0.0 ? 0.6 * fresnel1(d, total, lambda) : 0.0;
            const double sight = antennaA + (antennaB - antennaA) * (d / total);
            const double margin = sight - (s.hi + bulge + need);
            if (margin < best.margin) {
                best.margin = margin;
                best.atDistance = d;
                best.clear = margin > 0.0;
            }
        }
    }
    return best;
}
```

Поправка b = d₁·d₂/(2kR) — це висота, на яку поверхня планети піднімається над хордою, проведеною між кінцями траси; для радіо атмосфера злегка загинає промінь донизу, і це враховують, збільшуючи радіус у k = 4/3 разів, щоб промінь далі рахувати прямим.

**Траса 20 км, точка посередині, канал 2.4 ГГц.**

```
λ = 3·10⁸ / 2.4·10⁹ = 0.125 м

здуття:       b  = 10 000 · 10 000 / (2 · 1.3333 · 6 371 000) =  5.9 м
перша зона:   F₁ = √(0.125 · 10 000 · 10 000 / 20 000)        = 25.0 м
робоча вимога: 0.6 · F₁                                        = 15.0 м
──────────────────────────────────────────────────────────────────────
рельєф має лежати нижче за лінію візування на                   20.9 м
```

Майже двадцять один метр, з яких плоска геометрична перевірка не бачить жодного. Скільки саме простору навколо лінії має бути вільним і звідки береться множник 0.6 — предмет [зон Френеля](book:communications/fresnel-zones); тут важить лише те, що обидві поправки залежать від відстані й додаються до висоти рельєфу, а не віднімаються від висоти антен.

## Складність і числа

Робота на ребро — рівно кількість перетнутих комірок, і вона рахується наперед:

```
комірок = |Δgi| + |Δgj| + 1
```

На кожну комірку — чотири читання вузлів (майже завжди в один і той самий квадрат, тобто через memo без жодного пошуку в таблиці) і близько двадцяти операцій із рухомою комою на тричлен. Пошуків, дерев і сортувань немає ніде.

**Ребро 100 км під азимутом 45°, широта 50°, сітка 1″.**

```
1″ по меридіану  = 30.89 м            1″ по паралелі = 30.89 · cos 50° = 19.85 м
північна складова = 70.71 км  → Δgj = 70 710 / 30.89 = 2289 комірок
східна складова   = 70.71 км  → Δgi = 70 710 / 19.85 = 3562 комірки
разом                                                 ≈ 5852 комірки
```

Звідси й порядки часу — не з вимірювання на чужій машині, а з рахунку операцій, який кожен перевірить на своїй:

```
арифметика ходу й тричленів   ≈ 1.2·10⁵ операцій        десятки мікросекунд
читання 23 408 вузлів по 2 Б  ≈ 46 КіБ корисних даних   одиниці мікросекунд
сторінкові збої, файл у RAM   ≈ 2 300 · 1…3 мкс         2…7 мс      ← панує
сторінкові збої, холодний SSD ≈ 2 300 · 4 КіБ           десятки мілісекунд
```

Останні два рядки й пояснюють, де насправді живе вартість. Рядок квадрата 3601 × 3601 займає 7202 байти, тобто майже дві сторінки по 4 КіБ; сусідні рядки завжди лежать у різних сторінках. Діагональне ребро перетинає 2289 рядків — отже чіпає близько 2300 сторінок, тобто **дев'ять мегабайтів із двадцяти п'яти**, хоча корисних даних читає сорок шість кілобайтів. Ліниве відображення економить дуже багато на ребрі «схід–захід», яке сидить у кількох рядках, і майже нічого — на діагональному. Знати це варто до того, як обирати підказку ядру: для маршрутного ходу рядки йдуть монотонно, і попереднє читання допомагає, а `MADV_RANDOM`, поставлений «щоб не читало зайвого», його вимикає й робить гірше.

Для порівняння, рівномірна вибірка з кроком 20 метрів дала б на тих самих ста кілометрах 5000 звертань — той самий порядок роботи. Тобто хід сіткою не коштує дорожче; він коштує стільки ж і при цьому відповідає точно, тоді як вибірка з тим самим бюджетом лишає неспитаною щонайменше сьому частину комірок — а насправді більше, бо частина звертань припадає на комірки, уже відвідані сусіднім кроком.

## Де це ламається

**Прогалина, що потрапила в арифметику.** Одне значення −32768 в білінійній суміші дає висоту близько −8000 метрів. Далі трактом іде запас у вісім кілометрів, і жодна перевірка діапазону цього не спіймає, бо число саме собою правдоподібне за типом. Тому `readCell` віддає `false`, а не «щось замість». І тому ж у `ProfileSpan` є окреме поле `known`: підставити нуль означало б оголосити рівень моря, а протягнути попереднє значення — вигадати рельєф, якого ніхто не міряв.

**Крок вибірки більший за крок сітки.** Профіль виходить гладкий, правдоподібний і без перешкоди, яка на маршруті стоїть. Хід сіткою знімає це остаточно, але варто розуміти, чому саме він, а не просто менший крок: комірка, зрізана біля кута, перетинається відрізком на довжині, яка може бути як завгодно малою, тож **жоден** фіксований крок не гарантує її відвідин.

**Плоска відстань замість великого кола.** Довжину ділянки міряють лінійкою по меркаторівському екрану або за теоремою Піфагора просто в градусах — і східна складова виходить більшою за справжню в 1/cos φ разів, тобто на широті 50° у півтора раза. Профіль розтягується, і кожна перешкода на ньому стоїть не там, де насправді. Тут довжину ребра дає центральний кут ([відстань великого кола](book:math/great-circle-distance)), а не різниця координат.

**Пряма в координатах замість великого кола.** Тонший різновид тієї самої помилки: довжину порахували правильно, а сам профіль побудували вздовж прямої в широті-довготі. На ребрі 100 км це до 233 метрів убік — вісім комірок повз ту гору, задля якої профіль і будували.

**Байти прочитано не в тому порядку.** Висота 300 (0x012C) стає 11265, а прогалина −32768 (0x8000) — висотою 128 метрів, яку жодна перевірка не відрізнить від справжньої. Механіка підміни — у [порядку байтів](book:programming/bits-bytes-endianness).

**Приведення до цілого замість `floor`.** `(int)(-0.5)` дорівнює нулю, а не мінус одиниці: приведення відкидає дробову частину до нуля, а не вниз. Тут це знешкоджено зсувами сітки, які роблять обидві координати невід'ємними, — але варто комусь почати рахувати комірки прямо в градусах або пропустити нормалізацію після 180-го меридіана, і хід почнеться в сусідній комірці, а квадрат вибереться на градус не туди. Помилка не відтворюється в Європі, де все додатне, і саме тому доживає до польових випробувань.

**Витіснення квадрата, чий покажчик ще тримають.** Тут його немає з двох причин відразу: `HgtLibrary::node` копіює висоту негайно й покажчика назовні не віддає, а межа `kMinResident` не дає викинути жоден із чотирьох квадратів, які може одночасно потребувати комірка в куті. Забути друге — і код працюватиме бездоганно скрізь, крім рівно тих комірок, що лежать у кутах градусних квадратів.

**Немає негативного кеша.** Над морем, над полярними широтами й будь-де за межами покриття зйомки кожна вибірка робить приречений `open()`. Профіль прибережного маршруту стає в рази повільнішим за той самий маршрут суходолом — і причина в лічильнику системних викликів, а не в даних.

**Сіткові координати в одинарній точності.** Глобальна адреса вузла — число порядку 7·10⁵, і у `float` сусідні представні значення там стоять через 1/16. Локальна координата всередині комірки, отримана відніманням, квантується грубими сходинками: тричлен рахує екстремум не в тій точці, а результат лишається правдоподібним. Порятунок не в «акуратному округленні», а в тому, щоб великі числа жили в `double`, а параметр усередині комірки був свій і малий. Загальна механіка втрати значущих цифр на відніманні близьких величин — у [числах із рухомою комою](book:programming/floating-point).

**180-й меридіан.** Без нормалізації різниці по довготі ребро з 179.9° на −179.9° перетинає не двісті метрів, а майже весь світ — і хід чесно пройде 2.6 мільйона комірок, доки не скінчиться терпіння того, хто на це дивиться.

**Максимум узято за істину.** Профіль дає точну верхню межу **реконструкції**, а не рельєфу. До неї ще додаються похибка самої моделі, невидимий між вузлами гребінь і дрейф висотоміра, і складати їх треба явно, як у будь-якому [бюджеті похибок](book:math/error-budget). Точність цього коду означає лише те, що він не додає до цих похибок своєї власної, — і це єдине, чого від коду взагалі можна вимагати.
