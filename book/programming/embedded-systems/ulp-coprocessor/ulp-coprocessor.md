# ULP-співпроцесор: міряти, поки ядра сплять

Будити велике ядро на кожну подію — дорого: [сам boot плюс реініціалізація](book:programming/wakeup-sources) коштують заряду й часу. Звідси проста й сильна ідея ULP (англ. *ultra-low-power* — наднизьке споживання): нехай у deep-sleep лишається живим **крихітний** процесор у RTC-домені, який сам прокидається за таймером, читає давач, порівнює значення з порогом — і піднімає «велике» ядро ЛИШЕ тоді, коли є про що повідомити. Майже всі виміри він відсіює за наноджоулі, а середній струм системи лишається на рівні одиниць мікроампер.

Чому RTC-домен? У глибокому сні живлення мікроконтролера ділиться на острівці, які можна гасити окремо. Дорогі острівці — процесорні ядра, основна SRAM, радіо — у deep-sleep знеструмлені повністю. Живим лишається один маленький — домен реального часу (RTC, англ. *real-time clock*): годинник, трохи повільної пам'яті й та дрібна логіка, що тримає систему «при свідомості». ULP сидить саме там. Він не вмикає дорогі острівці, поки сам не вирішить, що пора, — у цьому вся економія, а не в обчислювальній потужності.

## Два ULP-ядра ESP32

ESP32 має два різні втілення цієї ідеї, і їх легко переплутати. Класичний ESP32 містить **ULP-FSM** (англ. *finite-state machine* — скінченний автомат): примітивний автомат на десятку асемблерних інструкцій, рівно достатніх, щоб прочитати АЦП чи GPIO, додати, порівняти й розгалузитися. C там немає — лише власний асемблер або макрос-набір `ulp_insn_t`. Новіші ESP32-S2 та ESP32-S3 отримали **ULP-RISC-V** — справжнє маленьке ядро архітектури RISC-V, яке програмують підмножиною C через ESP-IDF і компілюють окремим тулчейном. Робоча програма для нього — у вставці [⚙️ Програма для ULP](book:programming/ulp-coprocessor/proj-ulp-program.md): як її залити, запустити й де пастка.

Різниця між втіленнями практична. На FSM кожну дію доводиться викладати інструкціями автомата вручну — підходить для геть простих перевірок «зчитав і порівняв». RISC-V дає звичний C і трохи більше волі (галуження, прості функції, легше читання коду), лишаючись таким самим ощадливим. Спільне головне: обидва живуть у RTC-домені й активні лічені мікросекунди за цикл, а решту часу стоять у halt.

Окреме питання — коли ULP взагалі потрібен, а не звичайне пробудження ядра за RTC-таймером. ULP виграє там, де вимір треба робити **часто** (десятки разів на секунду), а реальна подія трапляється **рідко**. Тоді ядро будиться лише на події, а не на кожен вимір. Якщо ж вимір потрібен раз на хвилину чи рідше, простіше дати ядру прокинутися за таймером, зняти давач і заснути: ULP тут зайвий клопіт без виграшу. ULP — інструмент для «частого ока за повільним сигналом», не універсальна заміна сну.

## Що ULP вміє і чого ні

Межа його можливостей — не дрібниця, а суть конструкції. ULP **вміє**: читати RTC-АЦП (англ. *SAR ADC* — АЦП послідовного наближення, що належить RTC-домену) і RTC-здатні піни GPIO, на новіших чіпах — спілкуватися RTC-варіантом I²C і знімати вбудований датчик температури; рахувати, порівнювати, писати проміжне в RTC-пам'ять і будити велике ядро. ULP **не вміє**: Wi-Fi і Bluetooth, складних обчислень, доступу до основної SRAM чи Flash, до звичайної периферії high-power домену. Його сила — не в потужності, а в тому, що для частих простих перевірок він **не вимагає вмикати дорогі домени**.

Числа підтверджують задум. Саме ядро ULP під час роботи бере порядку сотні мікроампер, але активне воно лише мікросекунди за тік, тож його внесок у середній струм мізерний. Сам же deep-sleep із живим RTC-доменом тримає систему на рівні приблизно десяти мікроампер — на три порядки нижче за активне ядро з радіо (десятки-сотні міліампер). Тому весь сенс — лишати дорогі домени знеструмленими якомога довше, а ULP саме це й забезпечує, ухвалюючи рішення без них.

![ULP сам крутить цикл «таймер → вимір → поріг?» у RTC-домені; гілка «норма» веде назад у сон, велике ядро так і спить; гілка «поріг» будить велике ядро. Майже всі виміри йдуть ліворуч — у сон — тому середній струм лишається мікроамперним.](/book/programming/embedded-systems/ulp-coprocessor/img/ulp-guard.svg)

*ULP за таймером прокидається, читає RTC-АЦП і питає «поза порогом?». Норма — записати вимір і повернутися в сон при струмі в одиниці мкА. Поріг — підняти велике ядро, що коротко спалахне на міліампери й передасть тривогу.*

## Патерн «сторож порога»

Найпоширеніший сценарій ULP — сторож порога. Уявімо термостат у глибокому сні: раз на секунду ULP знімає [термістор](book:electronics/ntc-thermistor) через RTC-АЦП, переводить у температуру, порівнює з межами −10…+40 °C. У нормі — записує вимір у RTC-пам'ять і паркується назад у halt (англ. *halt* — зупинка). Поза межами — будить ядро, яке підключається до Wi-Fi і шле тривогу. Велике ядро спрацьовує раз на кілька годин, хоч вимірів за цей час відбулися тисячі.

[RTC-пам'ять](book:programming/rtc-memory), куди ULP кладе проміжні результати, переживає deep-sleep і доступна великому ядру після пробудження. Це «склад» між снами: ULP лишає там останній вимір чи лічильник тривог, а ядро, прокинувшись, забирає накопичене — без шини, UART чи I²C, прямим зверненням до пам'яті.

> 🔧 **Навіщо це.** ULP вартий заходу, коли треба **часто дивитися** на повільний сигнал (температура, рівень рідини, рух) і **рідко реагувати**. Якщо реагувати треба мало не на кожен вимір — виграшу немає, простіше будити ядро таймером: ULP економить саме на відсіюванні непотрібних пробуджень.

## Економіка ULP у числах

Чому це взагалі окупається — видно з арифметики заряду. Заряд за інтервал — це площа під кривою струму; різні стратегії дають площі, що різняться на порядки.

![Та сама частота вимірів, але два профілі струму. (а) Кожен вимір — дорогий прямокутний сплеск ядра, площа велика. (б) ULP веде виміри за мікроамперним фоном, велике ядро спалахує лише зрідка, площа крихітна. Виграш — у відсіяних пробудженнях, а не в самих вимірах.](/book/programming/embedded-systems/ulp-coprocessor/img/ulp-economics.svg)

*Зліва ядро будиться на кожен вимір — рівномірні дорогі сплески, середній струм у міліамперах. Справа ті самі виміри робить ULP майже задарма, а ядро вмикається раз на годину — плаский мікроамперний фон із рідкісним сплеском.*

Порахуймо для типового «частий вимір, рідка реакція»:

```
Стратегія А — будити ядро щосекунди на 50 мс при 30 мА:
  заряд за пробудження:  30 мА × 50 мс = 1.5 мА·с
  за годину (3600 разів): 3600 × 1.5  = 5400 мА·с = 1.5 мА·год
  I_сер ≈ 1.5 мА

Стратегія Б — ULP міряє щосекунди (~10 мкА × 5 мс),
  ядро будиться раз на годину на 2 с при 120 мА:
  ULP за годину:  3600 × (0.01 мА × 5 мс) = 0.18 мА·с ≈ 0.00005 мА·год
  ядро 1 раз:     120 мА × 2 с = 240 мА·с = 0.067 мА·год
  I_сер ≈ 0.067 мА·год / 1 год ≈ 67 мкА

Виграш: 1.5 мА / 0.067 мА ≈ 22 рази
```

Двадцять два рази — це різниця між тижнем і півроку від однієї батареї. Що рідші реальні події відносно вимірів, то більший виграш; що ближча реакція до кожного виміру — то він менший. Як саме мікроампери складаються в дні автономності, докладніше показують [арифметика циклу й середнього струму](book:programming/duty-cycle-current) та [бюджет батареї](book:programming/battery-budget).

## Worked-приклад: сторож температури на ULP-RISC-V

**Умова.** ESP32-S3 у deep-sleep раз на тік RTC-таймера читає термістор через RTC-АЦП. Поки сире значення в межах вікна 400…700 (12-бітний код при опорних 3.3 В — приблизно 15…35 °C), велике ядро не чіпаємо. Вийшло за вікно — будимо ядро й рахуємо тривогу.

```c
// Виконується на ядрі ULP-RISC-V (ESP-IDF).
// Компілюється окремо і завантажується в RTC-пам'ять до старту deep-sleep.
#include "ulp_riscv_utils.h"
#include "ulp_riscv_adc_ulp_core.h"

// Змінні в RTC-пам'яті — спільні для ULP і великого ядра.
uint32_t ulp_last_adc_value;
uint32_t ulp_alarm_count;

#define THRESHOLD_LOW   400   // ~15 °C на 12-бітному АЦП при 3.3 В
#define THRESHOLD_HIGH  700   // ~35 °C

int main(void) {
    // RTC-варіант читання АЦП: звичайний esp_adc у сні недоступний.
    uint32_t adc = ulp_riscv_adc_read_channel(ADC_UNIT_1, ADC_CHANNEL_6);
    ulp_last_adc_value = adc;

    if (adc < THRESHOLD_LOW || adc > THRESHOLD_HIGH) {
        ulp_alarm_count++;                    // поза вікном — є подія
        ulp_riscv_wakeup_main_processor();    // піднімаємо велике ядро
    }
    return 0;
    // Після return ulp_riscv_halt() викликається АВТОМАТИЧНО:
    // ULP паркується до наступного тіку RTC-таймера.
    // Свій while(1) чи явний halt тут не потрібні й шкідливі.
}
```

Один вимір за виклик, жодного `while(1)`: циклічність задає апаратний RTC-таймер, а не код. ULP активний мікросекунди на тік і знову гасне. Велике ядро прокидається лише на тривогу: двадцять три години з двадцяти чотирьох ULP веде спостереження сам, тримаючи середній струм у мікроамперах, і реагує на аномалію за секунди.

> 🔧 **Навіщо це.** Поріг тут — у сирих кодах АЦП, не у вольтах: так рішення коштує одне порівняння цілих, без перерахунку в RTC-домені. Точний перерахунок у градуси (з урахуванням обраного послаблення входу) дешевше зробити вже на великому ядрі після пробудження — коли заряд і так витрачається.
