# ⚙️ Шаблони на millis/micros і дві пастки, що ламають час

## Задача

[`millis()` і `micros()`](book:programming/millis-micros) дають час від старту, а вся робота з ними зводиться до трьох прийомів — мітка, інтервал, тайм-аут. Прийоми прості на словах, та на практиці той самий «правильний» на вигляд код раптом починає збиватися: таймер спрацьовує не тоді, інтервал виходить від'ємний, а годинник «застрягає». Майже завжди винна одна з **двох пасток** — неправильний тип мітки або змішані одиниці. Обидві підступні тим, що довго мовчать і виявляють себе лише через дні чи хвилини безперервної роботи, коли пристрій уже в полі. Розберімо обидві на реальному C, покажемо, **як** саме код ламається й коли саме «вистрелить», і зберемо кілька готових шаблонів, які можна копіювати без думки.

## Ідея

Усі надійні прийоми тримаються на одному: працюй із **різницею** беззнакових значень тієї самої ширини. Віднімання `now - t0` стійке до переповнення лічильника, бо беззнакова арифметика в C означена за модулем 2³² — оборот сам компенсується (детально це розписано в сусідній вставці про [модульну арифметику](book:programming/timer-overflow/math-unsigned-wrap.md)). Варто ж порушити одну з двох умов — «беззнакова» або «та сама ширина», — і компенсація зникає. Звідси обидві пастки й виростають.

Підступність обох у тому, що вони не дають збою **відразу**. Код компілюється без жодного попередження, на стенді працює бездоганно годинами, проходить усі ручні перевірки — і саме тому потрапляє у виріб. А спрацьовує пастка лише тоді, коли лічильник набіжить до критичної позначки: десятки днів для `millis()`, лічені хвилини для `micros()`. Інженер, що бачив код «робочим», навіть не згадає про нього, коли через місяць пристрій раптом зависне. Тому два правила нижче варто завчити як рефлекс і застосовувати завжди, не чекаючи, доки конкретний випадок «вистрелить».

## Пастка 1: знаковий або вузький тип

`millis()` повертає `unsigned long` — беззнакове 32-бітне. Якщо зберегти його мітку в `int`, усе ніби працює на стенді, та ламається двічі.

```c
int t0 = millis();          // ПАСТКА: int — знаковий, на AVR ще й 16-бітний
// ...
if (millis() - t0 > 1000) { /* ... */ }
```

На AVR (Arduino Uno) `int` — **16-бітний**, тож у `t0` влізе лише 0…65535 мс. Уже за 65.5 секунди мітка переповнить свій вузький тип, і збережений момент не матиме нічого спільного зі справжнім — таймер «спрацює» будь-коли. На 32-бітному ESP32 `int` хоч і ширший, та **знаковий**: щойно `millis()` перевалить за 2³¹ (≈ 24.8 дня), число в знаковому типі стане **від'ємним**, а віднімання поповзе в знакову арифметику, де переповнення в C — узагалі невизначена поведінка. Кільце, що мало б само компенсувати оборот, виявляється «не тим» кільцем — і компенсація зривається.

Лікування одне — той самий тип, що й у функції:

```c
unsigned long t0 = millis();        // ПРАВИЛЬНО: беззнакове 32-бітне
// ...
if (millis() - t0 > 1000UL) { /* ... */ }   // і стала теж UL
```

Зверни увагу на суфікс `UL` біля сталої `1000UL`. Без нього `1000` — звичайний `int`, і в деяких порівняннях компілятор може «підвищити» весь вираз до знакового типу, тихо повернувши пастку. Тримай **обидва** боки порівняння беззнаковими, і час лишиться в правильному кільці.

> 🔧 **Навіщо це.** Це найчастіша причина «довгограючих» збоїв, яких не видно за столом: щоб помітити зрив на 24.8 чи 49.7 дня, треба тримати пристрій увімкненим тижнями. У лабораторії код «працює», а у виробі через місяць раптом зависає. Звичка завжди писати `unsigned long` для міток прибирає цілий клас таких відмов наперед.

## Пастка 2: змішані одиниці

Друга пастка тонша: мітку взяли в одних одиницях, а порівнюють з іншими.

```c
unsigned long t0 = micros();        // мітка в МІКРОсекундах
// ...
if (millis() - t0 > 500) { ... }    // ПАСТКА: millis() — у МІЛІсекундах
```

Тут `t0` — мікросекунди (число велике), а `millis()` — мілісекунди (число у тисячу разів менше). Різниця `millis() - t0` дає беззнакове «маленьке мінус велике», тобто величезне число близько 2³², і умова майже завжди хибно істинна. Код поводиться хаотично, і причину довго не видно, бо синтаксично все законно. Правило просте: **в одному обчисленні — одні одиниці**. Або всюди `millis()`, або всюди `micros()`; мітку й поріг тримай в однакових одиницях.

**Порахуймо, коли саме «вистрелить».** Корисно побачити критичні позначки числом, щоб відчути, чому пастка така невловна на стенді.

```
int на AVR (16-біт):   t0 переповнюється за 65 536 мс ≈ 65.5 с
int на ESP32 (32-біт): millis() стає від'ємним за 2³¹ мс
                       = 2 147 483 648 / 86 400 000 ≈ 24.8 дня
unsigned long:         коректний оборот аж за 2³² мс ≈ 49.7 дня

Змішані одиниці (мітка micros, поріг millis):
   t0 = micros() ≈ 5 000 000      (через 5 с роботи)
   millis()      ≈ 5 000
   millis() − t0 = (5 000 − 5 000 000) mod 2³² ≈ 4 290 000 000  → умова «істинна» одразу
```

На цих числах видно головне: знаковий `int` на ESP32 «доживає» майже місяць, перш ніж зрадити, — тому за столом його ніколи не ловлять. А змішані одиниці брешуть **відразу**, проте збій схожий радше на «логічну дивину», ніж на проблему з типом, тож причину шукають не там.

## Готові шаблони

Зібравши обидві застороги, дістаємо кілька заготовок, які працюють «з коробки». Кожна з них — це лише комбінація трьох базових прийомів (мітка, інтервал, тайм-аут), та зведена в готовий вигляд, який можна копіювати в проєкт майже без думки.

**Неблокуюче блимання (мітка + інтервал).** Це найвідоміший шаблон, з якого зазвичай і починають відмову від `delay()`. Замість того щоб спинити всю програму на час паузи, ми лише **позначаємо** момент останнього перемикання й щооберту циклу питаємо, чи минув уже період. Поки не минув — керування одразу йде далі, тож решта коду крутиться без затримки:

```c
const unsigned long PERIOD = 500;   // мс
unsigned long last = 0;
bool on = false;

void loop() {
    unsigned long now = millis();
    if (now - last >= PERIOD) {      // настав час?
        last = now;                  // оновили мітку (саме now, не millis() ще раз)
        on = !on;
        digitalWrite(LED_BUILTIN, on);
    }
    // ... тут крутиться решта коду, нічого не чекаючи ...
}
```

Дрібний, але важливий момент: у `last` кладемо саме `now`, а не свіжий виклик `millis()`. Якщо викликати функцію вдруге, між двома викликами встигне минути трохи часу, і мітка поповзе — період потроху «попливе». Ще одна тонкість — порівняння `>=`, а не `==`: якщо порівнювати на точну рівність, а цикл одного разу затримається й перескочить потрібну мілісекунду, умова `==` ніколи не справдиться і блимання спиниться назавжди. `>=` ловить мить «уже час або пізніше» й тому стійке до затримок циклу.

**Тайм-аут із дією (мітка + межа).** Дуже частий випадок: ми чогось чекаємо — відповіді давача, готовності модуля, — та не можемо ждати вічно, бо завислий пристрій нікому не потрібен. Запам'ятовуємо мить початку й крутимося, доки не сталася подія **або** не вийшов відведений час:

```c
unsigned long start = millis();
bool got = false;

while (millis() - start < 2000UL) { // ждемо щонайбільше 2 с
    if (dataReady()) { got = true; break; }
}
if (!got) {
    // тайм-аут: подія не настала за 2 с — обробляємо як збій
}
```

**Вимір короткого імпульсу (micros + інтервал).** Коли важать мікросекунди — тривалість луна-імпульсу далекоміра, час відгуку давача, ширина одного фронту, — мілісекундної роздільності замало, і беремо `micros()`. Прийом той самий «мітка + інтервал», лише в дрібніших одиницях; різниця так само стійка до обороту лічильника, тільки оборот цей настає вже за ~71 хвилину, а не за 49.7 дня:

```c
while (digitalRead(ECHO) == LOW)  ;     // ждемо фронту
unsigned long t0 = micros();
while (digitalRead(ECHO) == HIGH) ;     // ждемо спаду
unsigned long width = micros() - t0;    // тривалість імпульсу, мкс
```

## Пастки

- **`delay()` всередині шаблону.** Якщо між перевірками часу вставити `delay()`, уся принада неблокуючого підходу зникає — програма знову стоїть. Тримай цикл «легким».
- **Порівняння замість віднімання.** Форма `if (now >= last + PERIOD)` виглядає рівнозначною, та на обороті лічильника зривається: сума `last + PERIOD` теж обертається, і порівняння бреше. Завжди `now - last >= PERIOD`, не `now >= last + PERIOD`.
- **Затягнута ітерація.** Неблокуючий час відмірює проміжки точно лише доти, доки сам `loop()` крутиться швидко. Якщо десь у циклі є довга дія на сотні мілісекунд, усі «таймери» на `millis()` спізняться рівно на неї — перевірка ж трапляється лише раз за оберт циклу.
- **`micros()` на довгих інтервалах.** Його роздільність спокуслива, та оборот за ~71 хв робить його непридатним для проміжків у години. Довгий інтервал — завжди `millis()`.
- **Свіжий виклик замість збереженого `now`.** Записувати в мітку `last = millis()` замість `last = now` — дрібна на вигляд недбалість, що додає до кожного періоду той крихітний час, який минув від початку ітерації. На одному блиманні непомітно, та в довгому ланцюгу подій ці дрібки накопичуються в помітний зсув. Бери час один раз на оберт і користуйся збереженим значенням.

Усі ці шаблони — то лише три базові прийоми в різних поєднаннях, а вся їхня надійність тримається на двох звичках: мітка завжди `unsigned long`, одиниці завжди однакові. Засвоївши це як рефлекс, ти отримуєш час, що працює стільки днів, скільки пристрій узагалі здатен пропрацювати без перезавантаження.
