# ⚙️ Загартований лічильник перезавантажень

> Базовий лічильник у `RTC_NOINIT` ловить цикл смерті, але в полі його підстерігає три біди: сміття в пам'яті після повного знеструмлення, надто грубе вікно порога й втрата рішення про ескалацію при вимиканні живлення. Доведемо лічильник до стану, якому можна довіряти на пристрої, до якого не приїдеш із кабелем.

## Задача

Базовий варіант рахує патологічні рестарти в одній змінній `RTC_NOINIT` і скидається після хвилини спокою. Цього досить, щоб показати ідею, але на справжньому пристрої виринають три діри.

**Перша — сміття після System Reset.** Brown-out і power-on скидають домен RTC, тож після них у `RTC_NOINIT` лежить не нуль, а випадкові біти з минулого життя чипа (або з ввімкнення зовсім нової плати). Наївний лічильник прийме це сміття за справжнє велике значення й піде в safe mode на рівному місці.

**Друга — занадто грубе вікно.** «П'ять рестартів, обнулити після хвилини» плутає два різні сценарії. Швидкий цикл смерті (п'ять падінь за п'ять секунд) — справжня халепа. А п'ять поодиноких збоїв, розкиданих по годинах роботи, — це здоровий пристрій, який просто інколи перечіпається. Лічильник без поняття про **щільність** подій карає обидва однаково.

**Третя — лічильник знає «скільки», але не «що ми вже пробували».** Рішення «відкотити конфіг» чи «відкотити прошивку» мусить пережити навіть повне знеструмлення: інакше після відкату й чергового падіння пристрій забуде, що вже відкочувався, і відкотиться по колу. RTC цього не гарантує — потрібен журнал у [NVS](topic:programming/nvs).

Залатаємо всі три, не втративши простоти базової ідеї.

## Ідея

**Проти сміття — структура з контрольною сумою.** Замість голої змінної кладемо в `RTC_NOINIT` маленьку структуру: магічне число, лічильник, мітку часу останнього збою — і [CRC](topic:communications/crc) над усім цим. На старті спершу перевіряємо: магія на місці й CRC збігається? Ні — отже, пам'ять зіпсута (сміття після brown-out, нова плата, рідкісний збій біта), і ми чесно починаємо з чистого нуля. Магічне число відсіює грубе сміття, а CRC ловить тонке — поодинокий перевернутий біт, який магію лишив би цілою.

**Проти грубого вікна — мітка часу.** Якщо разом із лічильником зберігати, **коли** стався попередній збій, то на новому збої можна спитати: чи близько він до попереднього? Близько (за лічені секунди) — нарощуємо лічильник, це щільна серія. Далеко (минули хвилини) — серія розпалася, скидаємо лічильник в одиницю, бо попередній збій уже «застарів». Так у поріг б'є лише справжній швидкий цикл, а рідкі поодинокі збої не накопичуються.

Час до повної ініціалізації годинника беремо з `esp_timer_get_time()` — лічильник мікросекунд від старту — лише як грубий орієнтир «давно/нещодавно» в межах кількох життів. Він обнуляється на кожному старті, тож зберігаємо не сам момент, а **скільки секунд пристрій прожив** до падіння; якщо торік пристрій ледь устиг піднятися перед падінням, це й є ознака щільного циклу.

**Проти забутого рішення — журнал у NVS.** Стан ескалації (на якому ми щаблі: норма / safe mode / конфіг відкочено / прошивку відкочено) кладемо в NVS, який переживає знеструмлення. Пишемо туди **рідко** — лише в мить переходу на новий щабель, — щоб не [зношувати Flash](topic:programming/wear-leveling). RTC лишається швидким робочим лічильником, NVS — рідко оновлюваною довгою пам'яттю рішень.

Три латки лягають на природний розподіл праці між двома сховищами. RTC — швидке й безкоштовне на запис, але летке щодо повного знеструмлення; туди йде те, що змінюється часто й має сенс лише в межах кількох сусідніх життів: сам лічильник серії та аптайм для оцінки щільності. NVS — повільне й конечне за ресурсом, зате стійке до будь-якого вимикання; туди йде те, що змінюється рідко, але мусить пережити все: один-єдиний байт щабля ескалації. Контрольна сума — спільний вартовий обох ідей у RTC: вона перетворює «довіряй сліпо» на «довіряй, лише коли дані цілі». Жодна з трьох латок не ускладнює базову думку — лічильник так само рахує патологічні рестарти, — а лише прибирає три способи, якими наївна версія тихо помиляється в полі.

## Робочий код

Структура лічильника з вартовим і CRC у `RTC_NOINIT`:

```c
#include "esp_system.h"
#include "esp_timer.h"
#include "esp_log.h"
#include "esp_crc.h"
#include "nvs.h"
#include "nvs_flash.h"

#define RTC_MAGIC        0xB007C0DEu   // вартовий структури в RTC
#define BURST_WINDOW_S   30            // збої ближче 30 с — одна серія
#define FAULT_THRESHOLD  5             // щільних рестартів → ескалація

static const char *TAG = "reboot";

typedef struct {
    uint32_t magic;        // RTC_MAGIC, якщо структура жива
    uint32_t fail_cnt;     // патологічних рестартів у поточній серії
    uint32_t last_uptime;  // скільки секунд прожив перед попереднім збоєм
    uint32_t crc;          // CRC32 над попередніми полями
} boot_state_t;

RTC_NOINIT_ATTR static boot_state_t s_bs;

// CRC над усіма полями, крім самого crc (останні 4 байти структури)
static uint32_t bs_crc(const boot_state_t *b) {
    return esp_crc32_le(0, (const uint8_t *)b, sizeof(*b) - sizeof(b->crc));
}

static bool bs_valid(const boot_state_t *b) {
    return b->magic == RTC_MAGIC && b->crc == bs_crc(b);
}

static void bs_commit(boot_state_t *b) {   // перерахувати CRC після зміни полів
    b->magic = RTC_MAGIC;
    b->crc = bs_crc(b);
}
```

Стани ескалації — окремий перелік; його чинне значення тримаємо в NVS, бо воно мусить пережити знеструмлення:

```c
typedef enum {
    ESC_NORMAL = 0,     // усе гаразд
    ESC_SAFE_MODE,      // зайшли в safe mode
    ESC_CONFIG_ROLLED,  // конфіг уже відкочено
    ESC_FW_ROLLED,      // прошивку вже відкочено — далі тільки кликати на поміч
} esc_level_t;

static esc_level_t esc_load(void) {
    nvs_handle_t h;
    uint8_t v = ESC_NORMAL;
    if (nvs_open("reboot", NVS_READONLY, &h) == ESP_OK) {
        nvs_get_u8(h, "esc", &v);     // нема ключа → лишається ESC_NORMAL
        nvs_close(h);
    }
    return (esc_level_t)v;
}

static void esc_store(esc_level_t level) {   // ТІЛЬКИ в мить переходу — щадимо Flash
    nvs_handle_t h;
    if (nvs_open("reboot", NVS_READWRITE, &h) == ESP_OK) {
        nvs_set_u8(h, "esc", (uint8_t)level);
        nvs_commit(h);
        nvs_close(h);
    }
}
```

Перевірка на старті зводить усе докупи: оживити структуру, врахувати причину reset, оцінити щільність за `last_uptime`, тоді вирішити крок:

```c
void startup_check(void) {
    esp_reset_reason_t reason = esp_reset_reason();

    // 1. Структура зіпсута (System Reset / нова плата / збій біта)? Почати з нуля.
    if (!bs_valid(&s_bs) || reason == ESP_RST_POWERON) {
        s_bs.fail_cnt = 0;
        s_bs.last_uptime = 0;
        bs_commit(&s_bs);
    }

    bool pathological = (reason == ESP_RST_TASK_WDT ||
                         reason == ESP_RST_INT_WDT  ||
                         reason == ESP_RST_PANIC);

    if (pathological) {
        // 2. Щільність: попередній збій стався після короткого життя?
        //    last_uptime малий → пристрій ледь піднявся й упав → щільна серія.
        if (s_bs.last_uptime <= BURST_WINDOW_S) {
            s_bs.fail_cnt++;                 // та сама серія росте
        } else {
            s_bs.fail_cnt = 1;              // попереднє застаріло — нова серія
        }
        ESP_LOGW(TAG, "fault (%d), burst_cnt=%u", reason, s_bs.fail_cnt);
        bs_commit(&s_bs);
    }

    // 3. Поріг щільної серії перейдено — лізти драбиною, спираючись на NVS-журнал.
    if (s_bs.fail_cnt >= FAULT_THRESHOLD) {
        esc_level_t level = esc_load();      // що ми вже пробували?
        switch (level) {
            case ESC_NORMAL:
                esc_store(ESC_CONFIG_ROLLED);
                config_rollback();           // спершу відкотити конфіг
                break;
            case ESC_CONFIG_ROLLED:
                esc_store(ESC_FW_ROLLED);
                esp_ota_mark_app_invalid_rollback_and_reboot();  // тоді прошивку
                break;
            default:
                break;                       // усе вичерпано — лишаємось у safe mode
        }
        enter_safe_mode();
        return;
    }

    // 4. Нормальний старт: завести таймер стабільності.
    start_stability_timer();
    // ... звичайна ініціалізація
}
```

Таймер стабільності тепер робить дві справи: обнуляє серію **і** знімає журнал ескалації — пристрій довів, що живий, тож наступну біду слід зустрічати з чистого аркуша:

```c
static void stability_timer_cb(TimerHandle_t t) {
    ESP_LOGI(TAG, "stable — clearing counter and escalation log");
    s_bs.fail_cnt = 0;
    s_bs.last_uptime = 0;
    bs_commit(&s_bs);
    if (esc_load() != ESC_NORMAL)
        esc_store(ESC_NORMAL);   // запис у NVS лише якщо було не NORMAL
}
```

І останнє: десь у нормальному ході роботи треба запам'ятовувати поточний аптайм, щоб наступне падіння знало, як довго пристрій прожив. Достатньо оновлювати `last_uptime` періодично (наприклад, у тій самій секундній задачі, що годує watchdog):

```c
void note_uptime(void) {                     // кликати раз на секунду
    s_bs.last_uptime = (uint32_t)(esp_timer_get_time() / 1000000);
    bs_commit(&s_bs);                         // RTC-пам'ять, не Flash — зносу нема
}
```

## Порахуймо на сценаріях

**Нова плата, перше ввімкнення.** `RTC_NOINIT` — сміття, але `bs_valid()` бачить хибну магію або CRC і повертає старт із нуля. Жодної хибної тривоги.

**Швидкий цикл смерті.** Прошивка валить watchdog через дві секунди після старту. На наступному старті `last_uptime == 2 <= 30`, тож `fail_cnt` росте: `1, 2, 3, 4, 5`. На п'ятому — `esc_load()` каже `ESC_NORMAL`, відкочуємо конфіг і записуємо `ESC_CONFIG_ROLLED`. Конфіг не вилікував, серія добігає порога знову — тепер `esc_load()` каже `ESC_CONFIG_ROLLED`, тож відкочуємо вже прошивку. Кожен щабель проходимо рівно раз, бо NVS пам'ятає попередній.

**Рідкі поодинокі збої.** Пристрій падає раз на десять хвилин. На кожному наступному старті `last_uptime ≈ 600 > 30`, тож `fail_cnt` щоразу скидається в одиницю й ніколи не доходить до п'яти. Здоровий пристрій спокійно працює, safe mode не вмикається — саме те, чого грубий лічильник не вмів.

**Знеструмлення посеред відкату.** Вимкнули живлення одразу після `esc_store(ESC_CONFIG_ROLLED)`, але до перезавантаження. RTC втрачено (power-on занулить серію), зате NVS зберіг `ESC_CONFIG_ROLLED`. Якщо цикл повернеться, наступна ескалація піде з правильного щабля — відкотить прошивку, а не почне конфіг наново.

## Пастки

**CRC без `esp_crc.h` під рукою.** Якщо не хочеться тягти апаратний CRC, згодиться будь-яка стала хеш-функція над тими ж байтами — головне, щоб вона була незмінна між збірками; інакше після оновлення прошивки стара структура раптом стане «несправною». Магічне число тут запобіжник: воно й так змусить почати з нуля, тож втрата — лише один зайвий «чистий» старт.

**Запис у NVS у гарячому циклі.** Спокуса оновлювати журнал ескалації частіше «про всяк випадок» прямо шкідлива: кожен запис зношує Flash, а в циклі смерті старти йдуть густо. Пиши в NVS **лише** в мить зміни щабля — не на кожному старті й точно не в `note_uptime()`.

**`last_uptime` у Flash.** Спокуса-двійник — класти аптайм у NVS «щоб напевно пережив». Не треба: він потрібен лише між сусідніми життями, які пов'язує Core Reset, а той RTC зберігає. У Flash аптайм лише вбивав би ресурс пам'яті частими записами.

**Поріг проти повільного псування.** Лічильник ловить швидкий цикл, але не повільну деградацію — пристрій, що падає раз на годину місяцями. Для такого потрібен не лічильник рестартів, а телеметрія й [деградація з гідністю](topic:programming/graceful-degradation); не намагайся розв'язати обидві задачі одним порогом.

**Гонка таймера стабільності.** Якщо `STABILITY_TIMEOUT_MS` коротший за час реальної ініціалізації важких підсистем (Wi-Fi, монтування файлової системи), таймер скине лічильник ще до того, як стане ясно, чи пристрій справді стабільний. Запускай відлік **після** того, як підняв усе критичне, а не на самому початку `app_main()`.
