# ⚙️ Від паніки у полі до рядка коду: повний цикл ESP-IDF core dump

Пристрій у клієнта перезавантажується «раз на кілька днів», логи нічого підозрілого не показують, а вдома на столі він працює тижнями без жодного збою. Це класична ситуація, де core dump варто увімкнути ще до того, як проблема стане видимою. Цінність тут не в самому дампі, а в тому, що його готують **заздалегідь**: коли збій нарешті стається, ловити вже пізно — або знімок є, або його немає назавжди. Пройдемо весь цикл: налаштувати збереження, дочекатися збою, видобути дамп і дійти до конкретного рядка — на робочому ESP-IDF без жодного зонда в мить падіння.

## Крок 1. Увімкнути збереження у Flash

Дамп нікуди не подінеться сам — для нього потрібні дві речі: ввімкнена опція і місце у Flash. Опція в `menuconfig` (Component config → Core dump) лишає у `sdkconfig` головний вибір призначення:

```
CONFIG_ESP_COREDUMP_TO_FLASH_OR_UART=y
CONFIG_ESP_COREDUMP_DATA_FORMAT_ELF=y
CONFIG_ESP_COREDUMP_CHECKSUM_SHA256=y
CONFIG_ESP_COREDUMP_MAX_TASKS_NUM=32
```

Формат ELF тут не примха: він дає тому самому GDB читати дамп як звичайний образ, а контрольна сума SHA256 ловить дамп, побитий під час запису в напівживій системі (інакше офлайн-розбір піде хибним слідом по сміттю).

Місце задаємо окремим розділом у таблиці розділів (`partitions.csv`) — тип `data`, підтип `coredump`:

```
# Name,   Type, SubType,  Offset,   Size
nvs,      data, nvs,      0x9000,   0x6000
phy_init, data, phy,      0xf000,   0x1000
coredump, data, coredump, 0x10000,  0x10000
factory,  app,  factory,  0x20000,  0x300000
```

Розмір розділу — не «на око». Документація Espressif дає орієнтир: `20 + N·(12 + розмір_TCB + макс_стек_задачі)` байтів, де `N` — `CONFIG_ESP_COREDUMP_MAX_TASKS_NUM`. Тридцяти двох задач зі стеками по кілька кілобайтів вистачає, щоб 64 КБ вщент заповнилися; якщо розділ замалий, дамп просто обріжеться, і на хості ти отримаєш половину картини без жодного попередження. Краще перекласти із запасом, ніж недорахувати.

> 🔧 **Навіщо це.** Розділ `coredump` коштує кілобайти Flash, які лежать без діла, поки все гаразд. Це страховка: один збій у полі — і замість «незрозуміло перезавантажується» ти маєш точний стек. Кілобайти Flash дешевші за відрядження до клієнта.

## Крок 2. Дочекатися збою і не стерти дамп

Дамп пишеться автоматично: коли ядро ловить фатальну помилку, обробник паніки обходить задачі й скидає знімок у розділ перед перезавантаженням. Твоя робота на цьому кроці — нічого не зіпсувати. Дамп лежить у Flash до явного очищення, тож не треба викликати `esp_core_dump_image_erase()` у звичайному старті «про всяк випадок» — інакше першими ж секундами після reboot ти затреш єдиний доказ.

Натомість на старті корисно спитати, чому ми взагалі прокинулися, і чи є що читати:

```c
void app_main(void) {
    esp_reset_reason_t reason = esp_reset_reason();
    if (reason == ESP_RST_PANIC) {
        size_t addr = 0, size = 0;
        if (esp_core_dump_image_get(&addr, &size) == ESP_OK) {
            ESP_LOGE("boot", "panic reboot, core dump %u B at 0x%x", size, addr);
            // підняти прапор у NVS: «є свіжий дамп, забери при нагоді»
        }
    }
    // ... звичайний старт
}
```

Причина reset відповідає на питання «що сталося» (`ESP_RST_PANIC` — впав у паніку; `ESP_RST_BROWNOUT` — просів струм; `ESP_RST_TASK_WDT` — застрягла задача). Дамп відповідає на «де і чому». Перше доступне завжди, друге — лише коли обробник устиг записатися. Перевірка причини reset першою рятує від марної роботи: якщо прокинулися не з паніки, дамп або старий (від попереднього збою), або його взагалі немає, і лізти по нього сенсу нема.

Прапор у NVS тут не зайвий. Пристрій у полі не завжди можна підключити одразу після збою; буває, дамп заберуть наступного разу, коли техніка приїде до клієнта. Якщо в момент перезавантаження лишити в енергонезалежній пам'яті відмітку «є свіжий дамп, дата така-то», то прошивка зможе сама повідомити про нього в телеметрії — і ти дізнаєшся про падіння раніше, ніж клієнт устигне поскаржитися.

## Крок 3. Видобути й розібрати на хості

Пристрій повернувся на стіл (або ти підключився віддалено по USB). Найкоротший шлях — попросити інструментарій зчитати дамп просто з Flash і відразу показати розбір:

```bash
# зчитати з пристрою і одразу показати стан задач та причину
idf.py coredump-info

# або підняти повноцінну GDB-сесію над дампом і .elf
idf.py coredump-debug
```

Під капотом обидві команди кличуть `esp-coredump` (новіша назва колишнього `espcoredump.py`), якому потрібні дві речі: сам дамп і `build/<твій-проєкт>.elf` — той самий образ, з якого зібрано прошивку. Якщо `.elf` не той (зібрали ще раз, з іншими прапорцями), адреси не зійдуться з іменами, і backtrace перетвориться на купу безіменних чисел. Тому `.elf` кожного релізу варто зберігати поруч із прошивкою.

Якщо дамп треба не розбирати тут, а відкласти (надіслати колезі, покласти в баг-трекер), його зручно витягти у файл і працювати офлайн:

```bash
esp-coredump info_corefile -c coredump.elf -t elf build/myapp.elf
```

## Крок 4. Прочитати картину збою

Ось що дає `coredump-info` після типового NULL-розіменування у задачі давачів:

```
Crashed task handle: 0x3ffb7e9c, name: 'sensor_task'

==================== CURRENT THREAD REGISTERS =====================
pc       0x400d1f88   sensor_read + 12
exccause 0x1d         (StoreProhibitedCause)
excvaddr 0x00000000
a1 (sp)  0x3ffb7e80   a10      0x00000000

==================== CURRENT THREAD STACK =========================
#0  sensor_read (dev=0x3ffb1234, buf=0x0) at main/sensor.c:88
#1  update_sensors () at main/tasks.c:45
#2  sensor_task (arg=0x0) at main/tasks.c:120

==================== ALL THREADS ==================================
'sensor_task'  → sensor_read, sensor.c:88   (crashed)
'wifi_task'    → xQueueReceive, queue.c:112  (blocked on queue)
'app_task'     → xSemaphoreTake, semphr.h    (blocked on semaphore)
```

Розбір лягає в один ланцюжок. `exccause 0x1d` — це `StoreProhibited`, тобто спроба **записати** за забороненою адресою. Куди саме писали, каже `excvaddr`: тут `0x00000000`, а запис за нульовою адресою майже завжди означає розіменування `NULL`. Верхній кадр backtrace показує, **де** це сталося: `sensor_read` на рядку `sensor.c:88`. Аргументи кадру домальовують **чому**: `buf=0x0` — у функцію передали порожній покажчик, і вона спробувала покласти туди байт. Лишається піднятися на кадр `update_sensors` і знайти, звідки прийшов `NULL`.

Решта задач у зведенні `ALL THREADS` — не шум, а контекст. `wifi_task`, що завмерла на `xQueueReceive`, і `app_task`, що чекає семафор, — це нормальний стан заблокованих задач, а не співучасники збою. Але саме на цьому зрізі видно, чи не тримала якась задача ресурс, потрібний тій, що впала, чи не склався взаємний клінч (deadlock). Жива задача в backtrace — найдешевший спосіб відрізнити «впало через цей рядок» від «впало, бо інша задача застрягла й не віддала чергу».

Те саме дав би живий зонд із зупинкою на момент HardFault — але тут ніхто не сидів поруч у мить збою. Один збережений файл відтворив повну сцену: яка задача впала, на якому рядку, з якими аргументами і що в той час робили решта задач.

## Пастки, через які цикл «не спрацьовує»

- **Збій у самому Flash-драйвері.** Обробник паніки пише дамп через звичайний Flash-драйвер. Якщо паніка сталася всередині нього (або під час іншого запису у Flash), писати нема чим — дамп не з'явиться. Це не баг, а межа методу: останній рубіж тут — UART-дамп або причина reset.
- **Не той `.elf`.** Найчастіша причина «беззмістовного» backtrace. Дамп зберігає голі адреси, а імена функцій і номери рядків живуть в `.elf`; досить перезібрати проєкт з іншим рівнем оптимізації або навіть тим самим компілятором іншої версії — і адреси поїдуть, бо лінкер розкладе код інакше. GDB слухняно припне адреси до того, що знайде в неправильному `.elf`, і видасть упевнений, але цілком хибний стек. Тому образ кожного релізу варто архівувати поруч із прошивкою — без рідного `.elf` дамп майже марний.
- **Затертий дамп.** Виклик очищення розділу на старті «для чистоти» стирає єдиний доказ ще до того, як ти його забрав. Очищай дамп лише після того, як успішно зчитав.
- **Замалий розділ.** Дамп тихо обрізається до розміру розділу. Backtrace головної задачі може вціліти, а стан решти — пропасти. Рахуй розмір за формулою з запасом.
- **Купа поза кадром.** За замовчуванням дамп не несе купи — лише стеки задач і TCB. Якщо баг живе в структурі на купі, у дампі ти побачиш хіба покажчик на неї. Уся RAM додається окремою опцією (`CONFIG_ESP_COREDUMP_CAPTURE_DRAM`) ціною місця в розділі.
