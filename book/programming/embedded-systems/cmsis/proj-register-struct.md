# ⚙️ Доступ до регістрів через структуру: від голого покажчика до заголовка, що не бреше

Завдання просте на вигляд: підняти вивід PA5 і прочитати стан PC13 на STM32F407, не беручи жодної бібліотеки виробника — самими регістрами. Написати це «в лоб» вдається за десять хвилин. Зробити так, щоб воно не розсипалося від зміни рівня оптимізації, від переривання посеред рядка чи від одного пропущеного слова в карті регістрів, — робота іншого порядку, і саме на ній тримається кожен device-заголовок, який ти коли-небудь підключав.

## Крок 0: голий покажчик

Периферія мікроконтролера лежить у тому самому адресному просторі, що й пам'ять ([регістри, відображені в пам'ять](book:programming/memory-mapped-io)): у регістра є адреса, і запис за цією адресою — це і є команда залізу. Отже, найкоротший робочий код — просто покажчик на потрібне число:

```c
#include <stdint.h>

#define RCC_AHB1ENR   (*(volatile uint32_t *) 0x40023830u)  /* тактування шини AHB1 */
#define GPIOA_MODER   (*(volatile uint32_t *) 0x40020000u)  /* режим виводів порту A */
#define GPIOA_BSRR    (*(volatile uint32_t *) 0x40020018u)  /* атомарний set/reset   */
#define GPIOC_IDR     (*(volatile uint32_t *) 0x40020810u)  /* вхідні дані порту C   */

int main(void)
{
    RCC_AHB1ENR |= (1u << 0) | (1u << 2);   /* увімкнути такт GPIOA і GPIOC */

    GPIOA_MODER &= ~(3u << (5 * 2));        /* очистити двобітове поле MODER5 */
    GPIOA_MODER |=  (1u << (5 * 2));        /* 01 = цифровий вихід            */

    GPIOA_BSRR = (1u << 5);                 /* підняти PA5 */

    uint32_t pc13 = (GPIOC_IDR >> 13) & 1u; /* прочитати PC13 */
    (void) pc13;

    for (;;) { }
}
```

Це не псевдокод — воно збереться і працюватиме. Звідки взялися числа:

```
PERIPH_BASE      = 0x4000_0000
AHB1PERIPH_BASE  = 0x4000_0000 + 0x0002_0000 = 0x4002_0000
GPIOA            = AHB1PERIPH_BASE + 0x000   = 0x4002_0000
GPIOC            = AHB1PERIPH_BASE + 0x800   = 0x4002_0800
RCC              = AHB1PERIPH_BASE + 0x3800  = 0x4002_3800

GPIOA_BSRR = 0x4002_0000 + 0x18 = 0x4002_0018
GPIOC_IDR  = 0x4002_0800 + 0x10 = 0x4002_0810
RCC_AHB1ENR = 0x4002_3800 + 0x30 = 0x4002_3830
```

І тут же видно, чому так ніхто не пише далі за перший експеримент. По-перше, кожен порт треба виписати заново: у GPIOA десять регістрів, у GPIOC ті самі десять з іншою базою — двадцять рядків, у яких відрізняється одна шістнадцяткова цифра, і жоден компілятор не помітить, якщо цю цифру набрати не ту. По-друге — і це важливіше — з таких визначень **не написати функції**. `GPIOA_BSRR` — це константа, вшита в текст макроса; передати «порт» параметром неможливо, бо порт тут не значення, а частина імені. Один світлодіод так засвітити можна, драйвер — ні.

## Крок 1: одна структура на всі порти

Регістри порту йдуть у пам'яті суцільним блоком з фіксованим кроком, а порти відрізняються лише базою. Це рівно та форма, яку описує `struct`: набір полів із відомими зміщеннями, накладений на будь-яку адресу.

```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    volatile uint32_t MODER;    /* 0x00  режим кожного виводу, 2 біти на вивід */
    volatile uint32_t OTYPER;   /* 0x04  push-pull / відкритий стік            */
    volatile uint32_t OSPEEDR;  /* 0x08  швидкість фронту                      */
    volatile uint32_t PUPDR;    /* 0x0C  підтяжки                              */
    volatile uint32_t IDR;      /* 0x10  вхідні дані (тільки читання)          */
    volatile uint32_t ODR;      /* 0x14  вихідні дані                          */
    volatile uint32_t BSRR;     /* 0x18  атомарний set/reset                   */
    volatile uint32_t LCKR;     /* 0x1C  замок конфігурації                    */
    volatile uint32_t AFR[2];   /* 0x20–0x24  альтернативні функції            */
} GPIO_TypeDef;

#define GPIOA  ((GPIO_TypeDef *) 0x40020000u)
#define GPIOB  ((GPIO_TypeDef *) 0x40020400u)
#define GPIOC  ((GPIO_TypeDef *) 0x40020800u)
```

Тепер порт — звичайне значення типу `GPIO_TypeDef *`, і функція нарешті пишеться:

```c
void gpio_set_output(GPIO_TypeDef *port, unsigned pin)
{
    port->MODER &= ~(3u << (pin * 2));
    port->MODER |=  (1u << (pin * 2));
}

void gpio_write(GPIO_TypeDef *port, unsigned pin, bool on)
{
    port->BSRR = on ? (1u << pin)          /* молодша половина — звести  */
                    : (1u << (pin + 16));  /* старша половина — скинути  */
}

bool gpio_read(const GPIO_TypeDef *port, unsigned pin)
{
    return (port->IDR >> pin) & 1u;
}
```

Двадцять макросів звелися до однієї структури й трьох баз, а замість магічного `0x40020818` у коді стоїть `GPIOC->BSRR`, яке компілятор перевірить за типом і доповнить у редакторі. Платити за це не доводиться нічим: зміщення поля відоме на етапі компіляції й запікається просто в команду доступу — `str r1, [r0, #24]`. Ніякого додавання під час виконання, ніякого зайвого регістра. Структура — це форма запису, а не шар коду.

Ця сама конструкція — типізована структура плюс макрос бази — і є те, що виробник постачає в device-заголовку. Кожна дрібниця в ньому стоїть там не з естетики: прибери `volatile` з одного поля, забудь безіменну заглушку між регістрами або спробуй «упакувати» структуру щільніше — і код зламається способом, який важко впізнати.

## Пастка перша: `volatile` тримає компіляторові руки

Ключове слово `volatile` перед кожним полем виглядає ритуалом, доки не побачиш, що без нього зникає. Компілятор оптимізує, виходячи з одного припущення: значення в пам'яті міняється тільки тоді, коли його міняє програма. Для регістра заліза це припущення хибне.

Ось код очікування готовності передавача:

```c
while ((USART1->SR & (1u << 7)) == 0) { }   /* чекаємо, поки TXE стане 1 */
```

Якщо поле `SR` оголошене без `volatile`, компілятор міркує так: у тілі циклу `SR` ніхто не змінює, отже читати його щоразу немає сенсу — досить прочитати один раз перед циклом. Вийде вічний цикл на копії значення, яка вже ніколи не оновиться. Найпідступніше тут те, що на `-O0` код працює (компілятор і так нічого не кешує), а на `-O2` зависає — і різниця вилазить аж при складанні релізу.

Зворотний бік — викинутий запис. Для звичайної змінної два поспіль присвоєння в одну комірку — це один запис: перше значення все одно ніхто не побачить. Для регістра даних передавача з апаратною чергою кожен запис штовхає в цю чергу свій байт, і «оптимізація» тихо вдвічі скорочує вихідний потік.

`volatile` дає рівно одну обіцянку, зате тверду: **скільки доступів написано в тексті — стільки машинних доступів і буде, у тому самому порядку відносно інших volatile-доступів**. Цього досить, щоб цикл опитування працював, а кожен запис дійшов до заліза.

Чого `volatile` **не** дає — треба знати так само точно, бо на цьому будують хибні надії. Він не робить операцію атомарною: `port->ODR |= 1u` лишається трьома командами. Він не впорядковує volatile-доступ відносно звичайної пам'яті — для цього потрібні [бар'єри пам'яті](book:programming/memory-ordering). І він не дочікується, поки запис фізично дійде через шину до периферії: команда `STR` завершується, щойно транзакцію прийнято, а не виконано. Докладніше про межі цієї обіцянки — [`volatile` і компілятор](book:programming/volatile-register).

CMSIS іде на крок далі за голе `volatile` і типізує ще й **напрям** доступу. У `core_cm4.h` визначено три окремі імені саме для полів структур:

```c
#define     __IM     volatile const   /* тільки читання */
#define     __OM     volatile         /* тільки запис   */
#define     __IOM    volatile         /* читання й запис */
```

`__IM` — це `volatile const`, і присвоєння в таке поле не збереться взагалі: `SCB->CPUID` оголошено саме так, тож спроба щось у нього записати впаде на етапі компіляції — регістр із ідентифікатором ядра тільки читають. Варто знати, що виробники цим користуються нерівно: у ST для STM32F4 навіть суто вхідний `IDR` позначено як `__IO`, тож помилковий запис у нього компілятор пропустить. Перевірка є в стандарті — але спрацьовує рівно там, де заголовок її розставив.

## Пастка друга: розкладка мусить збігтися до байта

Структура працює доти, доки її поля стоять точно там, де стоять регістри. Карти регістрів майже завжди мають діри — адреси, за якими нічого немає або є щось, зарезервоване на майбутнє. Пропустити діру в оголошенні означає зсунути **все, що йде далі**.

Ось справжній шматок карти RCC у STM32F407: після `AHB3RSTR` за зміщенням 0x18 наступний живий регістр `APB1RSTR` починається аж із 0x20, а 0x1C зарезервовано; далі знову двослівна діра на 0x28–0x2C, і лише тоді, з 0x30, — `AHB1ENR`, регістр увімкнення тактування шини AHB1. Заголовок ST виписує ці діри полями-заглушками явно:

```c
typedef struct {
    __IO uint32_t CR;            /* 0x00 */
    __IO uint32_t PLLCFGR;       /* 0x04 */
    __IO uint32_t CFGR;          /* 0x08 */
    __IO uint32_t CIR;           /* 0x0C */
    __IO uint32_t AHB1RSTR;      /* 0x10 */
    __IO uint32_t AHB2RSTR;      /* 0x14 */
    __IO uint32_t AHB3RSTR;      /* 0x18 */
    uint32_t      RESERVED0;     /* 0x1C — зарезервовано */
    __IO uint32_t APB1RSTR;      /* 0x20 */
    __IO uint32_t APB2RSTR;      /* 0x24 */
    uint32_t      RESERVED1[2];  /* 0x28–0x2C — зарезервовано */
    __IO uint32_t AHB1ENR;       /* 0x30 */
    /* … */
} RCC_TypeDef;
```

Заглушки навмисно **без** `volatile`: до них ніхто не звертається, вони існують лише щоб зайняти місце. Тепер уяви, що їх не написали — «навіщо оголошувати те, чого немає».

![Карта RCC поруч зі структурою без заглушок і зі структурою із заглушками: без заглушок кожне поле після діри з'їжджає на слово, і AHB1ENR потрапляє на адресу APB2RSTR](/book/programming/embedded-systems/cmsis/img/reg-layout-check.svg)
*Пропущене слово не «губиться» — воно зсуває кожне наступне поле. Найгірше в цій помилці те, що код збирається без єдиного попередження й навіть щось робить: просто не те.*

Наслідок конкретний і повчальний. `RCC->AHB1ENR |= 1u` за зсунутою розкладкою пише за зміщенням 0x24 — а це `APB2RSTR`, регістр скидання периферії на шині APB2, у якого молодший біт зветься `TIM1RST`. Тобто тактування GPIOA так і не ввімкнеться (усі подальші записи в порт підуть у нікуди, бо знеструмлений блок їх не бачить), зате таймер TIM1 стане в постійний reset. Два симптоми, які виглядають абсолютно неспорідненими, а причина одна — пропущений `uint32_t`.

Ловиться це одним рядком на кожен критичний регістр:

```c
#include <stddef.h>

_Static_assert(offsetof(RCC_TypeDef,  AHB1ENR) == 0x30, "RCC: AHB1ENR не за своїм зміщенням");
_Static_assert(offsetof(GPIO_TypeDef, BSRR)    == 0x18, "GPIO: BSRR не за своїм зміщенням");
_Static_assert(sizeof(GPIO_TypeDef)            == 0x28, "GPIO: розмір блоку не збігся");
```

`_Static_assert` — [перевірка на етапі компіляції](book:programming/static-assert): якщо умова хибна, збірка падає з написаним текстом і жодного коду не породжується. У C++ це `static_assert`, у старому C89/C99 без цієї конструкції той самий ефект дає `typedef char check[(умова) ? 1 : -1]` — масив від'ємної довжини оголосити не можна. Перевірку `sizeof` варто ставити завжди: вона ловить не лише пропуск усередині, а й забуту заглушку в самому кінці блоку.

Що це не паранойя, видно з того, що ARM робить так само у власних заголовках. У `NVIC_Type` з `core_cm4.h` між масивами регістрів стоять здоровенні заглушки — `uint32_t RESERVED0[24U]`, `RESERVED4[56U]`, `RESERVED5[644U]`, — бо блоки NVIC розкидані по 0x100 байтів. І ці описи теж набирають руками: у CMSIS 4 друге поле-заглушку звали `RSERVED1` — з проковтнутою літерою, — і одруківка спокійно дожила до CMSIS 5, бо на код вона не впливає, а очей на неї ніхто не клав.

## Пастка третя: `packed` — не ліки, а отрута

Дійшовши сюди, майже кожен ставить логічне питання: гаразд, діри я випишу, але як **гарантувати**, що компілятор не додасть чогось від себе? І майже кожен знаходить те саме «рішення» — `__attribute__((packed))`.

Спершу — звідки взагалі береться те, чого бояться. Компілятор додає доповнення (англ. *padding* — «набивка») лише через [вирівнювання](book:programming/alignment): `uint32_t` має бути на адресі, кратній чотирьом, тож якщо попередні поля закінчилися на непарному місці, між ними з'явиться безіменна дірка. Це реально трапляється, щойно в карті є вузькі регістри. Модуль CRC у STM32F4 саме такий: 32-бітний `DR` на 0x00, **однобайтний** `IDR` на 0x04, і наступний 32-бітний `CR` — на 0x08. ST виписує проміжок явно:

```c
typedef struct {
    __IO uint32_t DR;         /* 0x00  дані */
    __IO uint8_t  IDR;        /* 0x04  один байт */
    uint8_t       RESERVED0;  /* 0x05 */
    uint16_t      RESERVED1;  /* 0x06 */
    __IO uint32_t CR;         /* 0x08  керування */
} CRC_TypeDef;
```

Компілятор поставив би `CR` на 0x08 і сам — доповнення вийшло б рівно те саме. Але неявне доповнення це обіцянка, якої ти не контролюєш і не можеш перевірити: у нього немає імені, його не видно в коді, на нього не напишеш `offsetof`. Явні заглушки перетворюють мовчазну домовленість із компілятором на текст, який читає й людина, і `_Static_assert`.

А тепер про те, чому `packed` тут — рівно навпаки. Цей атрибут не «прибирає доповнення»; він **знімає з полів припущення про вирівнювання**, оголошуючи, що кожне поле може лежати на будь-якій адресі. Далі компілятор змушений породити код, який працює і для невирівняної адреси. Для звичайного поля він ще може ризикнути широкою командою, а для `volatile` — не має права: обіцянка «один доступ у тексті = один доступ у машині» несумісна з тим, що широка команда на невирівняній адресі може відмовити. Тож він переходить на побайтовий доступ.

Це не гіпотеза. У баг-репорті GNU Arm Embedded Toolchain (#1738730) розробник показав, що звичайний запис у регістр `USART`

```c
NVM_SPI->CTRL = USART_CTRL_SYNC | USART_CTRL_MSBF;
```

після ввімкнення пакування перетворився з одного `str` на вервечку `ldrb`/`strb` — по байту на кожну чверть слова. Супровідники відповіли, що це не дефект, а свідоме рішення: за `volatile`-доступу до потенційно невирівняного поля побайтовий варіант — єдиний безпечний для компілятора.

Безпечний для компілятора — і згубний для заліза. 32-бітний регістр, у який пишуть чотирма байтами, багато периферійних блоків просто не приймуть (вимога доступу цілим словом — звичайна річ у даташитах). Атомарність `BSRR` розсипається: замість однієї транзакції їх стає чотири, і між ними влазить будь-що. А на Cortex-M невирівняний доступ до периферійної області (тип пам'яті Device) породжує відмову незалежно від біта `CCR.UNALIGN_TRP` — тобто [HardFault](book:programming/hardfault) там, де очікували запис.

Висновок із цього виходить сильніший, ніж «не вживай packed». Реальні карти регістрів завжди кладуть N-байтовий регістр на адресу, кратну N — інакше залізо саме не змогло б його адресувати. Отже, **правильно переписана структура ніколи не потребує пакування**. Якщо без `packed` розкладка не сходиться — сходиться не структура, а твоє читання карти: десь пропущена діра або взято не ту ширину поля. `packed` не лагодить цю помилку, він її ховає, дописуючи згори другу, гіршу. Правило вміщується в три слова: перевіряй, а не пакуй.

Це стосується й глобального прапорця `-fpack-struct` — саме він і спричинив той баг-репорт. Одна опція в збірковому файлі отруює всі структури проєкту одразу, включно з device-заголовком виробника, який ти навіть не відкривав.

> 🔧 **Навіщо це.** Три перелічені пастки об'єднує одна риса: вони не дають діагностики. Забуте `volatile` дає зависання, помітне лише на релізній оптимізації; зсунута розкладка дає симптом у чужому периферійному блоці; пакування дає HardFault за адресою, яку писали правильно. Жодна не виглядає як «помилка доступу до регістрів», і всі три ведуть відлагодження хибним слідом — у бік логіки застосунку. Тому три рядки `_Static_assert` під оголошенням структури окупаються вже на першому разі, коли інакше довелося б лізти в дизасемблер.

## Пастка четверта: `|=` губить чужі зміни

Лишається остання, і вона не про компілятор, а про час. Рядок

```c
GPIOA->ODR |= (1u << 5);
```

виглядає однією дією, але одною не є. У Cortex-M немає команди «зміни біт у пам'яті»; є завантаження, арифметика в регістрі й збереження:

```
ldr  r3, [r2]         ; прочитати ODR
orr  r3, r3, #0x20    ; звести біт 5
str  r3, [r2]         ; записати назад
```

Між `ldr` і `str` минає час, і в цей проміжок може влізти [переривання](book:programming/interrupts). Якщо його обробник теж чіпає порт A — скажімо, вмикає світлодіод помилки на PA7, — станеться таке: обробник запише в `ODR` значення з піднятим бітом 7, поверне керування, а перерваний код спокійно покладе поверх нього своє старе значення, прочитане **до** переривання. Зміни обробника більше немає, і жодного сліду вона не лишила. Це класична [гонка](book:programming/atomicity-races): вона не залежить від того, наскільки швидкий чип, — вікно між двома командами є завжди, і рано чи пізно переривання в нього влучить.

![Порівняння двох послідовностей: ODR |= — три команди з перериванням між читанням і записом, зміна ISR затерта; BSRR — одна команда, переривання може влучити лише до або після](/book/programming/embedded-systems/cmsis/img/bsrr-vs-rmw.svg)
*Помилка спрацьовує від збігу в часі, а не від даних, — тому під відлагоджувачем вона не відтворюється: покроковий прохід розсуває команди так, що переривання встигає лягти між ними «безпечно».*

Виробники знають про цю діру й дають на неї апаратну відповідь. `BSRR` — регістр, у якому молодші 16 біт означають «звести відповідний вивід», а старші 16 — «скинути»; при збігу перемагає зведення. Читати його не треба взагалі: залізо саме розбирає записане слово й чіпає тільки названі виводи.

```c
GPIOA->BSRR = (1u << 5) | (1u << (3 + 16));
/*             ↑ підняти PA5    ↑ опустити PA3  — одна команда STR */
```

Атомарність тут береться не з `volatile` і не з розумного компілятора, а з того, що вся операція — одна шинна транзакція. Перервати всередині нічого, бо всередині нічого немає.

Що робити з регістрами, у яких такого дублера немає — а це більшість, той-таки `MODER`. Три робочі варіанти, кожен зі своєю ціною:

```c
/* 1. Критична секція: зберегти маску, заборонити переривання, повернути як було. */
uint32_t primask = __get_PRIMASK();
__disable_irq();
GPIOA->MODER = (GPIOA->MODER & ~(3u << 10)) | (1u << 10);
__set_PRIMASK(primask);
```

Це найпростіший варіант і працює на будь-якому ядрі — ціною кількох тактів, на які глухнуть усі переривання, а вони прямо додаються до [затримки переривання](book:programming/interrupt-latency). Саме тому маску `PRIMASK` зберігають і відновлюють, а не вмикають переривання наосліп: зовнішня критична секція може бути вже відкрита ([критичні секції](book:programming/critical-sections)).

Другий варіант — **бітова смуга** (англ. *bit-banding*): на Cortex-M3 і M4 кожен біт периферійної області має власне слово-псевдонім, і запис у це слово шина перетворює на атомарну зміну одного біта. Ціна — механізм є не скрізь: ані на M0/M0+, ані на M7 його немає ([бітова смуга в Cortex-M](book:programming/bit-banding)). Третій — цикл `__LDREXW()`/`__STREXW()` на ексклюзивному доступі: працює всюди, де є ці команди, але пишеться помітно багатослівніше.

Зворотний бік тієї самої проблеми — читання. Якщо величина не вміщується в одне слово (скажімо, 64-бітна мітка часу зібрана з двох 32-бітних регістрів), то між двома читаннями молодша половина може переповнитися й старша вже не відповідатиме молодшій ([розривне читання](book:programming/torn-reads)). Периферія на це зазвичай має захисну засувку: прочитав молодший регістр — старший зафіксувався.

## Чому перший запис іноді пропадає намарне

Є ще одна поведінка, через яку правильна структура з правильними `volatile` дає нуль ефекту, і вона зовсім не з мови C. Запис у `RCC->AHB1ENR` вмикає тактування блоку — але тактування не з'являється в ту саму мить, коли команда `STR` завершилася. ST описує це прямо в переліку відхилень: між увімкненням такту й моментом, коли блок реально відповідає, минає близько двох тактів AHB (для периферії на APB — один плюс дільник). Найближчий запис у щойно ввімкнений порт потрапляє у вікно, коли блок ще спить, і зникає.

Лікується читанням-назад:

```c
static inline void rcc_ahb1_enable(uint32_t mask)
{
    RCC->AHB1ENR |= mask;
    (void) RCC->AHB1ENR;   /* читання-назад: транзакція мусить дійти й повернутися */
}
```

Читання не може завершитися раніше за попередній запис на тій самій шині: ядро стоїть, доки не повернеться значення, — і цього стояння якраз вистачає, щоб такт устиг піти. Той самий прийом стоїть усередині фірмових макросів ST `__HAL_RCC_..._CLK_ENABLE()` — там теж є холостий зчит. І тут стає видно ще одну роль `volatile`: без нього компілятор викинув би цей `(void) RCC->AHB1ENR` як читання, результат якого нікому не потрібен, і затримка зникла б разом із ним.

## Модуль цілком

Складене докупи, з усіма перевірками, воно займає менше екрана:

```c
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>
#include "cmsis_gcc.h"   /* __disable_irq / __get_PRIMASK / __set_PRIMASK */

typedef struct {
    volatile uint32_t MODER, OTYPER, OSPEEDR, PUPDR;
    volatile uint32_t IDR;                /* лише читання за призначенням */
    volatile uint32_t ODR, BSRR, LCKR;
    volatile uint32_t AFR[2];
} GPIO_TypeDef;

_Static_assert(offsetof(GPIO_TypeDef, IDR)  == 0x10, "GPIO: IDR зсунуто");
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x18, "GPIO: BSRR зсунуто");
_Static_assert(sizeof(GPIO_TypeDef)         == 0x28, "GPIO: розмір блоку не той");

typedef struct {
    volatile uint32_t CR, PLLCFGR, CFGR, CIR;
    volatile uint32_t AHB1RSTR, AHB2RSTR, AHB3RSTR;
    uint32_t          RESERVED0;          /* 0x1C */
    volatile uint32_t APB1RSTR, APB2RSTR;
    uint32_t          RESERVED1[2];       /* 0x28–0x2C */
    volatile uint32_t AHB1ENR;            /* 0x30 */
} RCC_TypeDef;

_Static_assert(offsetof(RCC_TypeDef, AHB1ENR) == 0x30, "RCC: AHB1ENR зсунуто");

#define GPIOA  ((GPIO_TypeDef *) 0x40020000u)
#define GPIOC  ((GPIO_TypeDef *) 0x40020800u)
#define RCC    ((RCC_TypeDef  *) 0x40023800u)

#define MODE_OUTPUT  1u

static inline void rcc_ahb1_enable(uint32_t mask)
{
    RCC->AHB1ENR |= mask;
    (void) RCC->AHB1ENR;                  /* читання-назад замість «двох тактів» */
}

static void gpio_mode(GPIO_TypeDef *port, unsigned pin, uint32_t mode)
{
    uint32_t primask = __get_PRIMASK();
    __disable_irq();                                    /* MODER не має атомарного дублера */
    port->MODER = (port->MODER & ~(3u << (pin * 2))) | (mode << (pin * 2));
    __set_PRIMASK(primask);
}

static inline void gpio_write(GPIO_TypeDef *port, unsigned pin, bool on)
{
    port->BSRR = on ? (1u << pin) : (1u << (pin + 16));  /* одна транзакція */
}

static inline bool gpio_read(const GPIO_TypeDef *port, unsigned pin)
{
    return (port->IDR >> pin) & 1u;
}

int main(void)
{
    rcc_ahb1_enable((1u << 0) | (1u << 2));   /* такт GPIOA і GPIOC + читання-назад */
    gpio_mode(GPIOA, 5, MODE_OUTPUT);

    for (;;) {
        gpio_write(GPIOA, 5, gpio_read(GPIOC, 13));
    }
}
```

Від версії з голими покажчиками цей код відрізняється не обсягом, а тим, що всі перелічені способи зламатися тут або унеможливлені (`volatile`, `_Static_assert`, `BSRR`, читання-назад), або зведені до одного видимого місця (критична секція навколо `MODER`). У бойовому проєкті обидві структури беруть готовими з device-заголовка виробника, а не оголошують заново — тут вони виписані повністю лише щоб кожна перевірка була на очах.

## Що кусає далі

Три речі, які вилазять уже після того, як усе описане зроблено правильно.

**Відлагоджувач читає по-справжньому.** Вікно перегляду регістрів у середовищі не «дивиться» на них — воно виконує реальні читання через порт налагодження. Регістр статусу, прапорці якого гасяться самим читанням (класика — `SR` у USART від ST), очиститься від того, що ти просто розгорнув вузол у дереві периферії. Прапорець зникає, обробник переривання не спрацьовує, і симптом існує лише поки відкрите вікно.

**Адресу поля не можна віддавати назовні.** `&port->ODR` має тип `volatile uint32_t *`, але щойно ти передаси його в `memcpy` чи будь-яку функцію з параметром `void *`, обіцянка зникає: усередині немає жодної інформації про volatile, і бібліотечна реалізація вільна копіювати як завгодно — хоч побайтово, хоч широкими командами через невирівняну адресу. Периферію читають і пишуть тільки полями структури.

**Карта регістрів існує в машинному вигляді.** Переписувати сотні зміщень руками не варто взагалі: виробник постачає [файл SVD](book:programming/svd-format) — XML з описом кожного регістра, поля й біта, з якого device-заголовок генерують автоматично. Той самий файл читає й відлагоджувач, коли показує імена бітів. Тоді `_Static_assert` міняє роль: він перевіряє не твою уважність, а те, що згенерований заголовок і даташит на столі досі говорять про одну версію чипа.
