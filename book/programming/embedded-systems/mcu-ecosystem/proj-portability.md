# ⚙️ Один код — різні МК: HAL-шар і умовна компіляція

> Алгоритмічна вставка про **інженерну механіку переносності**: як саме один прикладний код переживає зміну чипа, коли [екосистема важить більше за мегагерци](book:programming/mcu-ecosystem) — коли SDK, HAL і спільнота вирішують більше, ніж тактова частота. Інструмент подвійний — тонкий HAL-шар плюс умовна компіляція. Увесь код нижче — реальний C/C++.

## Задача

Уявімо маленьку прошивку «блимни світлодіодом і надішли рядок у UART». Писали під ESP32, все працює. Тепер замовник хоче той самий виріб на дешевшому AVR-класі — заради вартості (бо [вибір МК](root:embedded/mcu-selection) завжди впирається в ціну). Або команда переходить на STM32-клас, бо ESP32 зник із постачання. Переписувати всю логіку — нераціонально.

Що саме ламається при переносі? Прикладна логіка — стан машини, таймінги, послідовність байтів у протоколі — переносна: вона не знає нічого про чип. А кожне **торкання заліза** прибите цвяхами до конкретного API. Один і той самий GPIO-запис виглядає по-різному залежно від платформи: `digitalWrite(pin, HIGH)` на Arduino/ESP32, `gpio_set_level(pin, 1)` в ESP-IDF, `HAL_GPIO_WritePin(GPIOA, pin, GPIO_PIN_SET)` на STM32, `PORTB |= (1<<pin)` на «голому» AVR. Усі чотири роблять одне й те саме — скидають ніжку у «1», — але звуться по-різному: останній варіант лягає прямо на [регістри GPIO](book:programming/gpio-registers) через [пам'яттєвоадресований ввід-вивід](book:programming/memory-mapped-io). Разом із GPIO страждають UART, затримка, лічильник часу — увесь низькорівневий шар.

Питання вставки просте і пряме: як написати бізнес-логіку **раз** — так, щоб зміна чипа чіпала лише тонкий нижній шар, а не весь виріб? Спиратимемося лише на базову периферію МК: [GPIO-регістри](book:programming/gpio-registers), [UART](book:programming/stream-parser) і [таймер](book:programming/timer-counter).

## Ідея: тонка «талія» — інтерфейс заліза окремо від логіки

Уявімо пісковий годинник. Верхня колба широка — це прикладна логіка з усіма її станами, умовами, алгоритмами. Нижня колба теж широка — це різноманітні чипи з різними API. А між ними — вузька шийка, через яку проходить увесь пісок: **шар абстракції заліза** (*hardware abstraction layer, HAL*). Логіка звертається лише до цього шару і ніколи — до чипових API напряму. Шар і є тим стабільним інтерфейсом, що не змінюється.

У парі з HAL-шаром завжди іде **умовна компіляція** (*conditional compilation*): препроцесор при збірці обирає саме ту реалізацію, яка підходить поточному чипу. Це дві окремі речі, які легко сплутати в одну, — тому назвемо їх явно.

**Контракт** — заголовок `hal.h`: набір функцій-обіцянок (`hal_gpio_write`, `hal_uart_puts`, `hal_delay_ms`, `hal_millis`) з однаковими іменами й сигнатурами для **всіх** чипів. Логіка інклудить тільки його. **Реалізації** — окремий код під кожен чип, що виконує цей контракт своїм рідним API; потрібну гілку вибирає **[препроцесор](book:programming/compiler-stages)** за тим, для якого чипа йде збірка.

Варто підкреслити паралель: одне [ядро Cortex-M](book:programming/cortex-m) живе в десятках різних чипів, а ST постачає вендорський [HAL як офіційний API STM32](book:programming/stm32). HAL у нашому коді й HAL від вендора — той самий принцип, але на різних рівнях абстракції. Ми будуємо свій тонкий шар поверх вендорського чи Arduino-рівня.

![HAL як вузька талія між переносною логікою і різними чипами](/book/programming/embedded-systems/mcu-ecosystem/img/hal-waist.svg)

*HAL як вузька «талія» між переносною логікою і різними чипами: широкий блок зверху — прикладна логіка, що пишеться раз; вузька шийка — стабільний контракт `hal.h` із чотирма функціями; нижній ярус — три реалізації, кожна огорнута своїм макросом-перемикачем. Препроцесор обирає рівно одну гілку при збірці, тож зміна чипа чіпає лише нижній ярус.*

Спершу — як препроцесор взагалі дізнається, який чип перед ним.

### Крок 1. Як код дізнається, на якому він чипі: передвизначені макроси

Тулчейн кожного чипа сам **передвизначає** макроси-маркери, що читаються препроцесором до компіляції. Їх не треба оголошувати — вони вже є в середовищі збірки.

На Arduino-рівні доступні архітектурні макроси: `ARDUINO_ARCH_ESP32`, `ARDUINO_ARCH_AVR`, `ARDUINO_ARCH_RP2040`, `ARDUINO_ARCH_STM32`; на рівні чипа: `ESP32`, `__AVR__`, `__arm__`. У ESP-IDF (через `sdkconfig.h`): `CONFIG_IDF_TARGET_ESP32`, `CONFIG_IDF_TARGET_ESP32S3`, `CONFIG_IDF_TARGET_ESP32C3`; архітектура — `__XTENSA__` проти `__riscv`; факт збірки в IDF — `ESP_PLATFORM`. Важливий нюанс: архітектурний макрос (`ARDUINO_ARCH_*` або `__AVR__`) надійніший за макрос конкретної плати — не треба перераховувати десятки різних плат; достатньо перевірити архітектуру.

```c
// Діагностика: яка платформа йде у збірку?
#if defined(ARDUINO_ARCH_ESP32)
  #pragma message("Target: ESP32 (Arduino core)")
#elif defined(__AVR__)
  #pragma message("Target: AVR (bare-metal or Arduino AVR)")
#elif defined(ARDUINO_ARCH_STM32)
  #pragma message("Target: STM32 (Arduino_STM32 core)")
#elif defined(ESP_PLATFORM)
  #pragma message("Target: ESP32 (ESP-IDF)")
#else
  #error "Непідтримувана платформа — додайте гілку HAL для цього чипа!"
#endif
```

Цей самий каскад `#if` — і є перемикачем, яким нижче виберемо реалізацію HAL. Зверніть увагу на обов'язковий `#else #error`: без нього нова, ще не портована платформа мовчки збереться з порожніми функціями.

### Крок 2. Контракт: заголовок hal.h (однаковий для всіх)

Контракт не знає про жоден чип — лише оголошення. Прикладна логіка інклудить тільки його і ніколи не бачить ані `Arduino.h`, ані IDF-заголовків.

```c
// hal.h — єдиний заголовок, що бачить прикладна логіка
#pragma once
#include <stdint.h>
#include <stdbool.h>

#ifdef __cplusplus
extern "C" {
#endif

// Записати логічний рівень у ніжку
void hal_gpio_write(uint8_t pin, bool on);

// Надіслати рядок у UART (нуль-термінований)
void hal_uart_puts(const char* s);

// Призупинити виконання на ms мілісекунд
void hal_delay_ms(uint32_t ms);

// Повернути кількість мілісекунд від старту
uint32_t hal_millis(void);

#ifdef __cplusplus
}
#endif
```

Жодного `#include <Arduino.h>` чи IDF-заголовка тут нема. Лише обіцянки — чотири функції, однакові для всіх цільових чипів.

### Крок 3. Реалізації під кожен чип (умовна компіляція)

Є два способи рознести реалізації. Перший — один `hal.cpp` із `#if`-гілками всередині кожної функції: зручно при двох чипах, але швидко перетворюється на нечитабельний клубок. Другий — окремі файли `hal_esp32.cpp`, `hal_avr.cpp`, `hal_stm32.cpp`, де кожен цілком огорнутий своїм `#if defined(...)` на початку: масштабованіший і рекомендований патерн. Нижче — саме він.

```cpp
// ─── hal_esp32.cpp ─────────────────────────────────────────────────────────
#if defined(ARDUINO_ARCH_ESP32)

#include "hal.h"
#include <Arduino.h>   // лише тут, не в прикладному коді

void hal_gpio_write(uint8_t pin, bool on) {
    digitalWrite(pin, on ? HIGH : LOW);
}

void hal_uart_puts(const char* s) {
    Serial.print(s);
}

void hal_delay_ms(uint32_t ms) {
    delay(ms);
}

uint32_t hal_millis(void) {
    return millis();
}

#endif // ARDUINO_ARCH_ESP32


// ─── hal_avr.cpp ───────────────────────────────────────────────────────────
// «Голий» AVR — не Arduino, прямий регістровий доступ до портів.
// Для стислості показана лише hal_gpio_write; решта — аналогічно.
#if defined(__AVR__)

#include "hal.h"
#include <avr/io.h>
#include <util/delay.h>
extern volatile uint32_t timer0_millis;  // з вбудованого ISR таймера

// УВАГА: hal_init() мусить виконати DDRB |= (1<<pin), щоб пін був виходом.
void hal_gpio_write(uint8_t pin, bool on) {
    if (on)  PORTB |=  (1 << pin);  // встановити біт
    else     PORTB &= ~(1 << pin);  // скинути біт
}

void hal_uart_puts(const char* s) {
    while (*s) {
        while (!(UCSR0A & (1 << UDRE0)));  // чекати, поки буфер вільний
        UDR0 = (uint8_t)(*s++);
    }
}

void hal_delay_ms(uint32_t ms) {
    while (ms--) _delay_ms(1);
}

uint32_t hal_millis(void) {
    return timer0_millis;
}

#endif // __AVR__


// ─── hal_stm32.cpp ─────────────────────────────────────────────────────────
#if defined(ARDUINO_ARCH_STM32)

#include "hal.h"
#include <Arduino.h>

void hal_gpio_write(uint8_t pin, bool on) {
    digitalWrite(pin, on ? HIGH : LOW);
}

void hal_uart_puts(const char* s) {
    Serial.print(s);
}

void hal_delay_ms(uint32_t ms) {
    delay(ms);
}

uint32_t hal_millis(void) {
    return millis();
}

#endif // ARDUINO_ARCH_STM32


// ─── #else: не допустити тихої збірки для непідтримуваного чипа ─────────────
#if !defined(ARDUINO_ARCH_ESP32) && !defined(__AVR__) && !defined(ARDUINO_ARCH_STM32)
  #error "hal: невідома цільова платформа — реалізуйте HAL для цього чипа!"
#endif
```

Зверніть: для ESP32 і STM32 (обидва на Arduino-core) реалізація майже ідентична — `digitalWrite`, `Serial.print`, `delay`, `millis`. Але для «голого» AVR `hal_gpio_write` звертається напряму до регістра `PORTB` і маски `(1<<pin)` — той самий контракт, нутрощі радикально різні. Саме це й ілюструє ціну абстракції: контракт один, а що за ним — диктує залізо аж до прямого [регістрового доступу](book:programming/gpio-registers).

Тепер — прикладний код, що **не змінюється** між чипами:

```cpp
// app.cpp — прикладна логіка; не інклудить Arduino.h, IDF, avr/io.h
#include "hal.h"

#define LED_PIN 2   // номер ніжки: оголошено у board_config.h або тут

void app_main(void) {
    hal_gpio_write(LED_PIN, false);   // старт — LED вимкнено
    for (;;) {
        hal_gpio_write(LED_PIN, true);
        hal_delay_ms(200);
        hal_gpio_write(LED_PIN, false);
        hal_delay_ms(200);
        hal_uart_puts("tick\n");
    }
}
```

Цей файл компілюється байт-у-байт однаково під усі три чипи — препроцесор бачить лише `#include "hal.h"` і більше нічого. Саме в цьому й суть: логіка написана раз, а мінімальна зміна при переносі — це новий `hal_новийчип.cpp` і оновлені `hal_init()` / `board_config.h`.

> 🔧 **Навіщо це.** Це не академізм — це спосіб не переписувати виріб, коли постачальник зняв чип із виробництва або маркетинг попросив здешевити плату — типова стаття [чек-листа вибору МК](root:embedded/mcu-checklist). HAL + умовна компіляція = одна перевірена бізнес-логіка × будь-яка кількість чипів. Саме на цьому стоять переносні стеки: Arduino core, [вендорські HAL](book:programming/stm32), [FreeRTOS-порти](book:programming/freertos). Правило залізне: усе залізо — лише за HAL-контрактом; жодного чипового виклику у прикладному коді.

## Складність і пастки на МК

- **Тонка талія, а не діра.** Спокуса «я лише цей разочок гукну `digitalWrite` напряму в логіці» — і переносність мертва. Дисципліна: прикладний код не інклудить ані `Arduino.h`, ані IDF-заголовків. Якщо допустити в логіку хоч один чиповий виклик, наступний перенос завалить збірку в найнесподіванішому місці.

- **Контракт мусить бути найменшим спільним знаменником.** Якщо в HAL потрапить те, чого на дешевому чипі фізично нема — другий ADC, апаратний поділ, DAC — портувати нікуди. Тримайте інтерфейс вузьким; екзотичні функції виносьте за умовну ознаку (`HAL_HAS_DAC`, `HAL_HAS_HW_DIVIDE`), щоб логіка явно обирала між реалізацією та заглушкою.

- **Ціна абстракції в тактах і байтах.** Зайвий шар викликів коштує тактів — це та сама компромісна межа, що й між [«голим залізом» і фреймворком](root:embedded/baremetal-vs-framework). Рятують `static inline` у заголовку та `-O2` — оптимізатор «розчиняє» тонкий HAL у прямий регістровий доступ. Але не загортайте в HAL гарячі цикли [біт-бангінгу](book:programming/gpio-registers), де важливий кожен такт: там шар прибирають, а HAL використовують лише для ініціалізації.

- **Різні розрядності й типи.** `int` — 16-біт на AVR і 32-біт на ESP32/Cortex-M; покладатися варто лише на точні `uint32_t`/`uint8_t` зі `<stdint.h>`. Інакше `hal_millis()` мовчки переповниться по-різному залежно від платформи — і таймаути почнуть «плисти» через [беззнакове переповнення лічильника](book:programming/timer-overflow).

- **Семантика «однакових» викликів різниться.** Той самий пін на одній платі має внутрішній підтягувальний резистор, на іншій — ні; активний-low світлодіод перевертає логіку. HAL ховає API, але не фізику — звідси `hal_init()` під кожен чип із чесними коментарями про напрямок пінів (`DDRB |= …`) і початковий рівень.

- **`#error` — обов'язковий запобіжник.** Без фінального `#else #error` нова, ще не портована платформа збереться з порожніми функціями й «тихо нічого не робитиме» — найгірший клас помилки: прошивка компілюється, заливається, і нічого не відбувається. Краще зламати збірку голосно й отримати зрозуміле повідомлення.

- **Не плутати рівні HAL.** Свій тонкий HAL поверх Arduino — це HAL над HAL. Для прототипу нормально; на серійному виробі іноді вигідніше лягти прямо на [вендорський HAL](book:programming/stm32) — заради детальнішого контролю тактування, DMA й переривань, яких Arduino-рівень не відкриває.

## Підсумок

Один контракт-заголовок `hal.h` плюс умовно скомпільовані реалізації роблять прикладну логіку незалежною від чипа: зміна МК чіпає лише тонкий нижній шар, а не весь виріб. Так на практиці справджується теза, що [екосистема й переносний код важать більше за мегагерци](book:programming/mcu-ecosystem): технічно ця переносність тримається на [препроцесорі](book:programming/compiler-stages) і залізній дисципліні «все залізо — лише за контрактом».
