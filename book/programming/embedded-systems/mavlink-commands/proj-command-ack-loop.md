# ⚙️ Надійний цикл «команда → ACK»

**Задача.** Послати апарату команду `COMMAND_LONG` так, щоб або **переконатися**, що вона виконана, або **чесно здатися** — а не зависнути назавжди й не вистрелити дію двічі. Лінк між землею й бортом ненадійний за самою своєю природою: радіоканал телеметрії втрачає кадри від завад, відстані й завантаженості, причому губиться і сама команда дорогою «туди», і її підтвердження дорогою «назад». Для коду це означає, що відсутність ACK **неоднозначна**: команда могла не дійти зовсім, могла дійти й виконатися, але загубити ACK, могла дійти й бути відкинутою. Наївний `send(); ack = recv();` не виживає в жодному з цих випадків — `recv` або блокується навіки на загубленому пакеті, або хапає перший-ліпший `COMMAND_ACK` у потоці й видає чужу відповідь за свою. Потрібен крихітний протокол поверх одного повідомлення.

**Ідея.** Команда стає маленьким **автоматом із повтором і таймаутом** — рівно тим, що передбачає сам стандарт MAVLink для команд. Шлемо `COMMAND_LONG`, заводимо таймер і чекаємо `COMMAND_ACK` **саме на цю** команду. Прийшов вчасно — читаємо `result` і виходимо. Минув таймаут — шлемо **ту саму** команду знову, збільшивши `confirmation`, і так до межі спроб. Вичерпали спроби — повертаємо помилку нагору, хай вирішує логіка місії (наприклад, переходить у безпечний стан). Уся надійність тримається на двох опорах. Перша: ACK треба **звіряти за полем `command`**, бо в потоці одночасно літають підтвердження на десятки інших команд — своїх і чужих компонентів. Друга: сама дія має бути **ідемпотентною**, щоб зайвий повтор після загубленого ACK лишив апарат у тому самому стані, а не виконав дію вдруге. Обидві опори — не прикраси, а умова коректності; прибери будь-яку — і автомат почне тихо брехати про стан апарата.

**Робочий C++.** Узагальнена відправка будь-якої команди з очікуванням підтвердження. Розбір вхідного потоку винесено у `poll_command_ack()`, що повертає `true`, щойно надійшов ACK із потрібним `command`:

```cpp
#include <stdint.h>
#include "mavlink.h"

// Прочитати з лінка наявні байти, згодувати їх парсеру MAVLink і,
// якщо зібрався COMMAND_ACK саме на очікувану команду, віддати його.
// Повертає true один раз — коли такий ACK з'явився.
bool poll_command_ack(uint16_t want_cmd, mavlink_command_ack_t *out);

// Зібрати й відіслати один кадр COMMAND_LONG.
static void send_command(uint16_t cmd, uint8_t confirmation,
                         float p1, float p2, float p3,
                         float p4, float p5, float p6, float p7) {
    mavlink_message_t m;
    mavlink_msg_command_long_pack(MY_SYSID, MY_COMPID, &m,
        TARGET_SYS, TARGET_COMP, cmd, confirmation,
        p1, p2, p3, p4, p5, p6, p7);
    uint8_t buf[MAVLINK_MAX_PACKET_LEN];
    int n = mavlink_msg_to_send_buffer(buf, &m);
    serial_write(buf, n);
}

// Надіслати команду й дочекатися результату.
// Повертає код MAV_RESULT, або -1, якщо ACK так і не прийшов за всі спроби.
int send_command_blocking(uint16_t cmd,
                          float p1, float p2 = 0, float p3 = 0, float p4 = 0,
                          float p5 = 0, float p6 = 0, float p7 = 0,
                          uint32_t ack_timeout_ms = 1000,
                          uint8_t max_tries = 4) {
    for (uint8_t attempt = 0; attempt < max_tries; ++attempt) {
        send_command(cmd, attempt, p1, p2, p3, p4, p5, p6, p7);  // confirmation = № спроби
        uint32_t deadline = millis() + ack_timeout_ms;
        while ((int32_t)(deadline - millis()) > 0) {
            mavlink_command_ack_t ack;
            if (poll_command_ack(cmd, &ack)) {
                if (ack.result == MAV_RESULT_IN_PROGRESS) {
                    deadline = millis() + 5000;   // довга дія: відсунути таймаут, чекати далі
                    continue;
                }
                return ack.result;                // ACCEPTED / DENIED / FAILED / UNSUPPORTED…
            }
            // тут-таки крутимо приймання телеметрії, щоб не «оглухнути» на час очікування
        }
        // таймаут вийшов — наступна ітерація перешле ту саму команду з confirmation+1
    }
    return -1;   // апарат мовчить: лінк мертвий або апарат не відповідає
}

// Виклик: озброїти апарат.
int r = send_command_blocking(MAV_CMD_COMPONENT_ARM_DISARM, /*param1=*/1.0f);
if (r == MAV_RESULT_ACCEPTED)      { /* мотори озброєно */ }
else if (r == MAV_RESULT_DENIED)   { /* не пройшли передпольотні перевірки */ }
else if (r == -1)                  { /* зв'язку немає — у безпечний стан */ }
```

**Пастки.** Кожна з них уже коштувала комусь години відлагодження або гіршого — розберімо механізм, а не лише симптом.

Перша й найпідступніша — **не звіряти `command` в ACK**. Команди й телеметрія йдуть **одним** потоком, тож у вікно очікування легко влітає `COMMAND_ACK` на зовсім іншу команду: апарат щойно підтвердив замовлений `SET_MESSAGE_INTERVAL` чи зміну режиму, а ваш код, який чекає на `ARM`, хапає цей ACK першим. Результат — найгірший із можливих: програма «вважає» апарат озброєним, поки той спокійно стоїть, бо справжній ACK на `ARM` ще в дорозі або взагалі загубився. Лікування одне — брати лише той `COMMAND_ACK`, у якого поле `command` дорівнює надісланому; а в системі, де команди шле не один відправник (наземна станція **і** бортовий комп'ютер), звіряти ще й `target_component`, щоб не привласнити чуже підтвердження.

Друга — **глухе очікування**. Поки крутиться внутрішній цикл чекання ACK, код **не повинен** переставати читати решту потоку. Якщо на ці пів секунди приймання телеметрії стає, апаратний чи драйверний буфер UART переповнюється, нові байти кадрів губляться, і коли ви нарешті повертаєтесь до читання, парсер давиться обірваними кадрами — телеметрія «відстає» й сиплеться рівно тоді, коли ви найбільше чекаєте від неї підтвердження. Тому очікування ACK і приймання телеметрії — це фізично **один** неблокувальний цикл: на кожній ітерації згодовуєш парсеру все, що накопичилося на лінку, дивишся, чи серед розібраного є потрібний ACK, і заодно віддаєш свіжу телеметрію решті програми. Двох почергових циклів («спершу дочекаюся ACK, потім читатиму телеметрію») тут бути не може.

Третя — **повтор неідемпотентної дії**. Якщо команда сама по собі не ідемпотентна, загублений ACK обертається подвійним виконанням: апарат прийняв команду й виконав, ACK не дійшов, автомат за таймаутом переслав — і апарат виконав **ще раз**. Для абсолютної більшості `MAV_CMD` це не страшно, бо їх свідомо спроєктовано ідемпотентними: `ARM=1` двічі лишає апарат озброєним, `DO_SET_MODE` у той самий режим двічі нічого не змінює, `NAV_TAKEOFF` на ту саму абсолютну висоту не підкидає апарат удвічі вище. Небезпечні — рідкісні **відносні** дії, де «ще раз» означає «ще на стільки ж». Перш ніж покладатися на сліпий повтор, переконайся, що конкретна команда дійсно ідемпотентна; якщо ні — не повторюй наосліп, а спершу окремим запитом звір поточний стан апарата й шли повтор, лише коли дія справді не відбулася.

Четверта — **сплутати `confirmation` з лічильником невдач для здавання**. Поле `confirmation` зростає для **апарата**: за ним приймач відрізняє повторно надісланий екземпляр команди від нового запиту тієї самої команди. Кількість спроб до здавання — це **ваш** внутрішній лічильник (`max_tries`), про який апарат нічого не знає. Якщо їх сплутати — наприклад, рахувати спроби за значенням `confirmation`, що прийшло звідкись, — автомат або здаватиметься надто рано, або не здаватиметься ніколи. Тримай їх окремо: `confirmation` росте з кожною відправкою, `attempt` рахує саме ваші спроби.

П'ята — **єдиний короткий таймаут на всі команди**. Швидкі дії (`ARM`, `SET_MODE`) відповідають за десятки мілісекунд, а довгі — калібрування давачів, складний `NAV_TAKEOFF` із набором висоти — чесно присилають `MAV_RESULT_IN_PROGRESS` і тривають секунди. Жорсткий таймаут у пів секунди на всіх перетворить нормальну довгу дію на чергу нікому не потрібних повторів: ви знов і знов шлете команду, яку апарат **уже виконує**. Саме для цього в автоматі є окрема гілка `IN_PROGRESS`: отримав «роблю» — не вважай це кінцевою відповіддю й не перешивай команду, а лише **відсунь дедлайн** і чекай далі, аж поки прийде остаточний `ACCEPTED` чи `FAILED`. Кінцевий результат завжди приходить **після** проміжних `IN_PROGRESS`, і саме його повертають нагору.

Шоста, тонша — **реагувати на всі коди відмови однаково**. ACK прийшов, але `result` не `ACCEPTED` — і тут важливо розрізняти, що повтор **поверне до життя**, а що ні. `MAV_RESULT_TEMPORARILY_REJECTED` означає «апарат зараз зайнятий іншою командою» — це єдина відмова, яку має сенс повторити трохи згодом, бо стан минущий. `MAV_RESULT_DENIED` — відмова по суті (умови не дозволяють: не пройдено передпольотні перевірки, апарат у повітрі тощо), і повтор лише марно навантажить канал. `MAV_RESULT_UNSUPPORTED` — апарат такої команди взагалі не знає, повторювати безглуздо. `MAV_RESULT_FAILED` — узявся, але не зміг; тут рішення за логікою місії, а не за сліпим повтором. Тому автомат угорі при будь-якому **остаточному** коді виходить і віддає його нагору: вирішувати, повторювати чи здаватися, має не цикл відправки, а той, хто знає контекст дії.

Сьома — **слати координатну команду через `COMMAND_LONG`**. Та сама функція годиться для дій без координат, але точку на Землі вона зіпсує: широта й довгота, передані як `float` у `param5`/`param6`, втратять молодші розряди й апарат полетить за десятки метрів від цілі. Для таких команд є окремий `COMMAND_INT`, де ці два параметри — цілі масштабовані координати (градуси × 10⁷); автомат повтору й перевірки ACK лишається той самий, змінюється лише пакувальник кадру (`mavlink_msg_command_int_pack`). Простіше тримати дві відправки — `_long` і `_int` — за спільним очікуванням ACK, ніж намагатися втиснути координати у float.

Варто написати цей автомат **один раз** і сховати за функцією на кшталт `send_command_blocking` — і весь інший код стає чистим: «озброїти», «змінити режим», «злетіти», «додому» перетворюються на однорядкові виклики, що повертають зрозумілий результат. Уся ненадійність лінка, повтори, фільтрація чужих ACK і обробка довгих дій лишаються замкненими в одному місці, а логіка місії читається як послідовність намірів, а не як перемішане з нею мереживо таймерів і перевірок. Це і є та межа, за якою керування апаратом із власного коду перестає бути крихким експериментом і стає надійним інструментом.
