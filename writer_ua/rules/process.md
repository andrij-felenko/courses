# process

**Обсяг:** статуси, маніфест — тільки оркестраторові

## Що знаємо

<!-- канон: початок -->
**Маніфест — єдине джерело** навігації, плану, черги, статусів. **Схема 7, JSON, розбита по групах**; нові поля поза схемою не вигадуємо.

```
root/<вид>/<книга>/manifest.json     { schema:7, kind, slug, title, groups:[слуг…] }
root/<вид>/<книга>/<група>.json      { schema:7, kind, book, slug, title, scope,
                                       chapters:[ {slug, title, topics:[…]} ],
                                       megachapters?:[{title, chapters:[слуг…]}] }   ← НЕ рендериться
```

Тема в розділі — **або власна**, **або вказівник** на чужу (тільки в курсах):

```json
{ "slug": "…", "title": "…",
  "basic":    { "status": "…" },
  "detailed": { "status": "…" },
  "hist": [ { "file": "hist-<name>.md", "status": "…" } ],
  "comp": [ … ], "math": [ … ], "proj": [ … ], "api": [ … ] }

{ "ref": "<книга>/<тема>", "title": "…" }
```

**Кожна версія (`basic`, `detailed`) має власний `status`** (enum §9); версія доступна читачу ⟺ її статус `done`. Вставки — масив на тип, елемент `{file, status}`.

**Група й розділ живуть ТІЛЬКИ тут.** У шляху їх немає, тема лежить пласко під книгою. Тому перекроїти книгу — правка одного JSON, а не рух файлів. Нумерація курсу (Модуль · Розділ · Крок) рахується з **порядку** в маніфесті, не з поля-числа.

**Маніфест руками не редагують.** Письменник маніфесту не чіпає взагалі: статуси розставляє окрема фаза батчу.

**500–1200 слів І щонайменше ВДВІЧІ КОРОТША за свою детальну** (заліза обсягу — нижче).

**1000–6500 слів**; зрідка, коли тема цього справді вимагає, — **до 9000** (те саме й для каталогу, §8).

**ГЕЙТ БАЗОВОЇ: чотири «так» і жодного відсіву.** Рішення ухвалюють **за готовою детальною** (§9), а не наперед. Базову пишемо, лише коли збіглися **всі чотири** ознаки:

1. **Обсяг — ТРИ ЗОНИ.** Рахуємо **прозу** детальної (так, як міряє `wordcount.js`):
   - **< 2250 слів → базової НЕ пишемо.** Коротка детальна сама і є входом у тему.
   - **> 4000 слів → базова ПОТРІБНА** — пишемо, якщо ознаки 2–4 не відсіяли тему. Тут «потрібна», а не «можна»: дефолт «ні» в цій зоні **не діє**.
   - **2250–4000 → вирішує зміст**, тобто ознаки 2–4: пишемо, лише коли всі три кажуть «так»; вагання → ні.
2. **Один стрижень.** Ти можеш назвати **одним реченням** причинно-наслідковий стрижень теми, і він тримається **без жодного** з викинутих шматків. Якщо суть теми — **перелік рівноправних речей** (варіанти, режими, поля, команди, кроки процедури), базової **не пишемо**: скорочений перелік — це не огляд, а обрізаний довідник.
3. **Є що викинути.** Щонайменше **половина** детальної — виведення, варіації, крайні випадки, приклади, тобто матеріал, який базова законно **не бере**. Детальна-кістяк, де кожен абзац несе новий потрібний факт, не стискається: різати довелося б істину.
4. **Детальна не є входом сама по собі.** Якщо перші два-три абзаци детальної вже дають картину теми, вхід у читача **вже є** — базова його лише продублює.

**Безумовні відсіви** (діють попри будь-який обсяг): тема **довідкова** — ядро це API, протокол, формат, набір параметрів, таблиця · тема **вузька**, існує лише як деталь більшої · детальна ще **не написана** (без неї базову не вирішують).

> ⚠️ **«Довідкова» — про ядро САМОЇ СТАТТІ, а не про вид книги.** Відсів питає: чи є ядром **цієї теми** перелік (API, поля, прапорці, коди помилок, таблиця параметрів)? Він **НЕ** питає, чи лежить тема в довідник або каталог. Тема «Планувальник: як ядро ділить час» має причинно-наслідковий стрижень і відсів **не проходить** — хай вона й у довіднику; тема «Набір ioctl підсистеми X» — проходить. Читати відсів як «книга-довідник → базових не буває» **заборонено**: так рівень базової вмирає цілком. 

**Вагання 50/50 — НЕ пишемо.** Дефолт гейта — «ні». Помилка «не написали базову» коштує читачеві одного зайвого кроку в детальну; помилка «написали зайву» — це другий текст про те саме, який далі треба тримати синхронним із першим.

**ЗАЛІЗО ОБСЯГУ: базова ≤ половини детальної.** Дві межі діють **одночасно**, обидві обов'язкові:

```
базова:  500 ≤ слів ≤ 1200        І        слів(базова) ≤ слів(детальна) ÷ 2
```

Рахуємо **прозу** (без код-блоків, фігур, таблиць, розмітки) — так, як міряє `node scripts/wordcount.js <тека-книги> --all`: у блоці «ПАРИ базова↔детальна» він показує пару, відношення й стелю базової, а рядок `✖ ПОРУШЕННЯ` — це **порушення, не попередження**. Порядок дій, коли не сходиться:
1. **Спершу скороти базову** — вона майже завжди довша, ніж треба: другий шар, варіації, крайні випадки й виведення в базовій **зайві**, їхнє місце — детальна.
2. **Не сходиться після скорочення — базової не пишемо взагалі** (`basic:empty`, §9). «Не стискається до половини без втрати суті» означає рівно одне: тема **не потребує** базової, а не що межу можна посунути.
3. **Ніколи не роздувай детальну**, щоб «дотягнути» відношення, і не розбавляй базову водою до 500 слів — обсяг детальної диктує тема, а не арифметика.

Підлога 2250 стоїть там, де базова ще не вироджується в переказ: за детальної в 2250 слів базова має вміститись у 1125, і це вже інший текст, а не скорочений той самий. Поріг 4000 — там, де тема виросла настільки, що швидкий огляд їй **потрібен**, а не «можливий».

**ДОПУСК ±10% — на смуги Й на пороги.** Обсяг — не арифметична вправа: **якість важить більше за число**. Базова на 1290 слів (стеля 1200 + 7%) — не порушення, якщо текст того вартий; детальна на 2100 при підлозі 2250 — законна підстава написати базову, коли зміст її просить. `wordcount.js` у межах 10% **попереджає**, а не лається. Але допуск — це запас на живий текст, **а не нова межа**: систематично сидіти на +10% означає, що смугу треба міняти, а не обходити.

Маніфест (§2): кожна версія має свій `status` — `basic:{status}`, `detailed:{status}`. **`pending` = треба написати** (саме це беруть скрипти-письма) · **`empty` = не треба** · **`done` = написано й доступно читачу**. Детальна — основна черга (`pending`→`done`); базова — `empty`, коли детальна коротка (дубль), або `pending`, коли велика тема варта швидкого огляду. **Нову тему заводимо ЗАВЖДИ як `basic:{status:"empty"}` + `detailed:{status:"pending"}`** (§6): у чергу йде детальна, а базову вирішують уже за готовою детальною.

**Обсяг статті задає складність її предмета — і більше ніщо.** Проста тема, вичерпана на 1400 словах, написана правильно; складна, якій тісно в 4000, теж. Рівняти всі статті до середини діапазону — значить доливати простим темам того, чого в них немає, і підрізати складні.

**Обсяг вставки — за типом:** `hist-` 600–6000 · `math-` 600–6500 · `comp-` 800–7500 · `proj-` 800–6000 · `api-` 1100–11000 слів. Верхня половина смуги — зона винятку: туди йде лише те, що за природою є **великим переліком** (набір команд, таблиця полів, довідка API), який ділити на частини шкідливо. Матеріалу багато й він ділиться — **розділити на кілька**. Реєстр у маніфесті — **окремо за типом**.

**Медіана — властивість КНИГИ, а не мета для файлу, і конкретних її чисел тут навмисно немає.** Медіана описує розподіл: половина статей коротша, половина довша, і саме так і має бути. Вимагати медіани від кожної статті — те саме, що вимагати від кожної людини бути середнього зросту. Тому окрему статтю за орієнтиром НЕ судять: `06-size.js` перевіряє лише смугу, а медіану по книзі показує `wordcount.js`.

Числа медіани показує `wordcount.js` по книзі — авторові вони не потрібні й шкодять: число
перед очима стає ціллю, хоч би що написали біля нього, і статті вирівнюються між собою
замість того, щоб різнитися за предметом.

Що справді читають із медіани: якщо вона повзе до стелі, впав **поріг входу** для матеріалу — у статті стало проходити те, що раніше не проходило. Це розмова про книгу, і лікується вона порогом, а не скороченням написаного. Стеля (6500 / 5000) — це «більше не можна», а не «до цього треба дотягнути».

⚠️ Це **не** суперечить §4 («коротше не додає розуміння»): ми не ріжемо готовий текст, а **піднімаємо поріг входу** для матеріалу. Наслідок — менший обсяг; ціль — щільність. Порядок думки й повнота нитки лишаються недоторканними: якщо скорочення робить пояснення діркуватим, скорочувати не можна.

Вставка **зареєстрована в маніфесті** (масив свого типу, §2) і **згадана в тексті** ref-вставкою (§6).

**Цілі ще нема — створюємо й ref-имо заздалегідь.** Ціль — або **тема-стаття**, або **допоміжна вставка** (історія/приклад/математика/пристрій — `<type>-<name>.md`):
1. Визнач **правильне місце** (тема — книга+галузь; вставка — тека теми).
2. Створи **порожній файл** (md теми або `<type>-<name>.md`).
3. **ПЕРЕД заведенням — перевір, чи це не СИНОНІМ наявної теми.** «Один термін на поняття» (§4) стосується й слугів. Грепни маніфест книги за ключовим словом майбутнього слуга; знайшов близьке — **нової теми НЕ заводь**, постав ref на наявну (а як її назва вужча за твій випадок — уточни назву, не плоди другу). Три пастки, на яких це ламається найчастіше:
   - **вужче й ширше про те саме** — `aslr` ↔ `rop-and-aslr`;
   - **абревіатура й розшифровка** — `ksm` ↔ `ksm-page-merging`;
   - **два боки одного механізму** — `threads-and-queues` ↔ `streaming-threads`, `events-and-queries` ↔ `pipeline-events`.

   **Але схожа назва — ще не дубль.** Перш ніж відмовитися від теми, спитай, чи є між ними СПРАВЖНЯ різниця: одна описує предмет, друга — як його роблять; одна дає поняття, друга випадок ужитку; одна про механізм, друга про його ціну. Якщо різниця є — це **дві теми**, і лікується вона **назвою, а не відмовою**: уточни обидві так, щоб з кожної було видно, чим саме вона відрізняється. Оманлива назва гірша за зайву тему — саме через них пари дублів і виникли.

   Ціна дубля: зайва стаття, лінки, роздвоєні між двома теками, і читач, що не знає, котру з двох читати. Ловиться пізно — коли обидві вже написані. `manifest-patch.js` друкує «⚠ МОЖЛИВІ ДУБЛІ ПОНЯТТЯ» (спільне рідкісне слово або вкладений слуг), але **не блокує**: об'єднувати чи ні — рішення людське.
4. Зареєструй у маніфесті: тема — **`basic:{status:"empty"}` + `detailed:{status:"pending"}`** (у чергу йде **детальна** — вона основна версія, §3; базову вирішують ПІСЛЯ детальної: вийшла велика — тоді `basic:pending`). Вставка — `pending` у масиві свого типу. **Новій темі `basic:pending` не ставимо.**
4. Постав ref — попап покаже стаб, **підтягне текст** по заповненні.

 (У конвеєрі `write-batch.js` це поле `newTopics` автора статті; фаза «Маніфест» реєструє нове як `pending` і відсіює дублі.)

**Опційний файл правил книги — `<тека-книги>/_canon.md`.** Якщо в корені книги/курсу/каталогу/довідника лежить `_canon.md` (`root/<вид>/<книга>/_canon.md`, `root/course/<курс>/_canon.md`, `root/cat/<каталог>/_canon.md`, `root/sys/<довідник>/_canon.md`) — це **додаткові правила саме для неї** понад цей загальний канон: наскрізний приклад, єдині терміни та імена, мова прикладів, стильові домовленості. Письменник (і статті, і вставки) **першою дією читає його**, якщо він існує, і суворо тримається — там, де `_canon` уточнює загальне, **перевагу має `_canon`**. **Файлу немає → для цієї книги/курсу/каталогу/довідника додаткових правил немає**, пишемо за загальним каноном. (Технічно `write-batch` перевіряє наявність файлу перед письмом кожної теми.)

**Статуси (enum у маніфесті, на КОЖНУ версію `basic`/`detailed` й КОЖНУ вставку):** `done` (написано, канон, доступно читачу) · **`pending`** (**треба написати** — саме це беруть скрипти-письма) · **`empty`** (**писати НЕ треба** — версія/вставка не передбачена) · `update` (переписати) · `deeper` (поглибити; зокрема — на тему посилаються як на детальну `/detail`, §6) · `recheck` (передивитися за чинними правилами; **явні неточності** — число/факт/дата/одиниця/формула/логіка — виправляємо точково, але **готове не переписуємо**). Міняємо **прямо в маніфесті** одразу після правки. *(Зміна v4→v5: раніше `empty` означало «не почато» — тепер це `pending`; `empty` = «не потрібно».)*

**Процес.** Беремо **найперший** `pending`/`update`/`deeper`/`recheck` (саме **`pending`** — черга на письмо; `empty` НЕ беремо, це «не треба»). **Одна версія = один хід** (текст + фігури + статус версії→`done`). Великий крок **делегуємо сабагенту** з повними шляхами; у головну loop-сесію — лише короткий звіт.

**Порядок у батчі — детальні, тоді базові.** Черга набирається з **пріоритетом на `detailed`**; `basic` беремо, лише коли детальних у черзі не вистачає. Пишемо **спершу всі детальні**, і вже за готовою детальною вирішуємо, **чи потрібна їй базова**. Виходів рівно три: базова **вже написана** → **нічого не міняємо** (ні файла, ні статусу); базової **нема й вона потрібна** (детальна велика, §3) → пишемо її на наступному етапі; базової **нема й вона не потрібна** (детальна коротка/вузька) → `basic:empty`, і то лише якщо стояло `pending` (інших статусів не рухаємо). Аж тоді пишемо базові: **ті, що знайшов скаут, плюс ті, що додалися після детальних**. Далі — вставки, локальний гейт фігур, маніфест. **Нові залежні теми (§6) можуть зʼявитися на будь-якому етапі** — і зі статті, і зі вставки; усі вони реєструються `basic:empty` + `detailed:pending`.

**Паралельність.** Маніфест **один на книгу/курс/каталог/довідник** → ізоляція **по книзі**: кілька `/loop` працюють паралельно, лише якщо кожен — у **своїй** книзі/курсі. Двох `/loop` на одну книгу **не запускати** (спільний маніфест → конфлікт). Працюй лише в маніфесті своєї книги.

**Дисципліна.** **Слідуй інструкціям точно — завжди.** Узгоджену чи готову структуру/зміст **самовільно не міняй** і не чіпай того, що просили не чіпати. Бачиш, як покращити, — **спершу спитай** (про структуру й зміст), не роби сам.
