## Що знаємо

<!-- канон: початок -->
**Мова коду — за доменом, НЕ завжди C/C++.** C/C++ обов'язковий лише там, де його диктує предмет: **embedded/прошивка, регістри, залізо, базові алгоритми з наголосом на швидкодію**. Для **загального програмування / веб / бекенду** пиши мовами, що там реально живуть (JS/TS, Python, Go, Rust, Java…). Мова має бути **правдивою для прикладу**: доменно-замкнений код (регістри МК, syscalls) лишається однією мовою; загальну ідею, коректну в кількох мовах, **можна показати кількома**.

**Чи потрібен тут код узагалі — питання ПЕРЕД вибором мови.** Код доречний, коли показує те, чого проза й формула показати не можуть: послідовність кроків із станом, розгалуження на крайовому випадку, поведінку на межі, справжній інтерфейс. Обчислення за формулою, яку стаття вже навела, кодом НЕ стає ціннішим — формула вже і є приклад, а тридцять рядків навколо неї додають читачеві роботи, не додаючи знання. Особливо це стосується книг, де код не є предметом (фізика, математика, хімія): там програма мусить заробити своє місце, а не бути доказом старанності. Немає що показати кодом — не пиши його; правило вибору мови нижче відповідає на питання «якою», а не «чи».

**Вибір мов — зважена оцінка (яку мову писати).** Для кожного прикладу коду оціни кожну кандидат-мову **0–10** за доречністю саме тут — **з усіх боків**: наскільки природно й повчально приклад виглядає нею в цьому домені **та наскільки вона ефективна для цього завдання** (швидкодія, пам'ять, паралелізм) — **не за популярністю мови**. Де приклад про продуктивність, системний рівень, паралелізм чи гарячий шлях — перформанс-мови (C/C++/Rust/Go/Zig) дістають **вищу сиру оцінку**, навіть якщо для загального коду популярніші TS/Python; де приклад про виразність домену / DTO / скрипт — навпаки. Помнож на коефіцієнт: **C++ і TypeScript — ×1.5**, решта мов — ×1. Пиши тими, чий добуток **> 5** (кілька — вкладками `:::tabs`, кожна ідіоматична; одна — звичайний код-блок). Приклад: C++ із сирою 4 → 4·1.5 = 6 (**пишемо**); Python із 4 → 4 (**ні**). Так C++/TS з'являються частіше — але **лише де справді лягають**: низька сира оцінка й ×1.5 не витягне (регістри Python-ом не пишемо, DTO асемблером — ні). Коефіцієнт схиляє на межі, не силує недоречне.

**Є C — має бути й C++, скрізь, де C++ узагалі можливий.** Це не «C або C++ на вибір», а **C і C++**: щойно приклад написано мовою C, до нього додається вкладка C++ — якщо тільки C++ там не заборонений фізично. Причина проста: те саме завдання на C++ читається інакше й показує читачеві другий спосіб думати про ту саму задачу — час життя замість ручного звільнення, тип замість домовленості, контейнер замість пари «вказівник + довжина».

**Три випадки, коли C++ справді неможливий** — і лише вони є винятком:

- **простір ядра**: модулі, драйвери, будь-що, що лінкується в ядро Linux. Там немає ані бібліотеки, ані винятків, ані розкрутки стека — C++ не варіант, і вкладку не додаємо;
- **приклад про сам C як мову**: препроцесор, домовленості ABI, генерований компілятором код, `_Generic`, гнучкий масив у кінці структури. Тут предметом є C, а не задача;
- **чужий інтерфейс, показаний як є**: заголовок бібліотеки, оголошення системного виклику, структура з `uapi/`. Ми цитуємо, а не пишемо.

Усе інше — простір користувача, робота з файлами й сокетами, розбір форматів, обчислення, структури даних, утиліти — **дістає обидві вкладки**.

⚠️ **Вкладка C++ мусить бути C++, а не C з іншим розширенням.** Механічний переклад із `printf` і `malloc` усередині нічого не показує й гірший за відсутність вкладки. Ідіоматичний еквівалент означає рівно те, чим C++ відрізняється в цій задачі:

```
C                                  C++
malloc / free                  →   контейнер або std::unique_ptr
close(fd) наприкінці й у goto  →   обгортка з деструктором (RAII)
char* + окрема довжина         →   std::string_view / std::span
код помилки через return       →   std::expected або виняток — за домовленістю прикладу
макрос-обгортка                →   шаблон або constexpr-функція
void* + size                   →   шаблон із типом
```

Якщо після такого перекладу вкладка C++ **не відрізняється нічим, крім заголовків** — це знак, що приклад суто C-шний за природою: краще лишити одну вкладку, ніж показувати різницю, якої немає.

**Кілька мов одночасно — вкладки `:::tabs`.** Коли той самий приклад однаково доречний у 2–5 мовах (типово в книгах для широкого загалу програмістів), обгорни фенси в контейнер — рушій дасть **перемикач-вкладки зверху**, спільний на всю сторінку (вибір запам'ятовується). **КОЖНА вкладка — самостійно коректний, ідіоматичний еквівалент саме цього прикладу, не механічна транслітерація.** Мова, що на приклад не лягає гарно, — **викидається, а не притягується**. Синтаксис (мова у fence-info дає назву вкладки):
````
:::tabs
```py
def add(a, b): return a + b
```
```js
const add = (a, b) => a + b;
```
:::
````
Одна мова (без потреби у вкладках) — **звичайний код-блок із мовою у fence** (` ```py `), і мова вмикає підсвітку синтаксису.

**Код від десяти рядків живе у файлах, а не в огорожах.** Блок від **10 рядків** справжньою мовою виїжджає з прози у файл, а в тексті на його місці лишається директива `:::code`. Дрібніший фрагмент лишається в огорожі як був: там він **пояснює**, а не працює.

Тека проєкту названа тим `.md`, у який код вставляють, а всередині неї — тека мови:

```
<тема>/<ім'я .md без розширення>/<мова>/<файли>

i2c-expander/i2c-expander-d/c/main.c        детальна стаття
i2c-expander/proj-i2c-scanner/c/main.c      вставка proj
i2c-expander/api-i2c-ioctl/c/main.c         вставка api
```

Ім'я файла-носія в шляху — не прикраса: у 56% тем поруч живуть `proj` і `api`, і обидва хочуть свій `main.c`. Побічний виграш — `.h` перестав бути безрідним: мову вирішує тека, спільний заголовок на дві мови став неможливим, а отже неможлива й підробка «C++ версії», де той самий `.h` підключено з `.cpp`.

**Тека мови — корінь проєкту.** Усередині — звичайна для цієї мови розкладка, з підтеками включно: `rust/src/`, `go/internal/`, пакет у Python, у C пари `<модуль>.c` + `<модуль>.h`. Розбивай на модулі так, як розбивають у справжніх проєктах. Платформа — це не мова: `arduino`, `esp-idf`, `stm32` лягають **під** мову зайвим рівнем (`c/esp-idf/`), і тека мови лишається чесною.

**Синтаксис — один `:::code` на файл**, шлях від теки теми:

```
:::code proj-ring-buffer/c/ring.c
```

Кілька мов — **по одному `:::code` на вкладку `:::tabs`**, точно як із фенсами. **Пара C↔C++ перевіряється наявністю теки `cpp/`, а не збігом імен файлів**: ідіоматичний C++ ділиться на модулі інакше, і однакові імена в `c/` та `cpp/` були б ознакою поганого перекладу, а не доброго.

**Скільки коду — з ролі, не з лічильника.** Ти професіонал і показуєш студентам, як воно працює насправді: пишеш при них, у темпі заняття. Такий код працює **по-справжньому** — обробка помилок і незручні випадки в ньому Є, бо професіонал інакше не пише. Але будується він **не для користувачів і не для ринку**: без конфігурованості, без шарів «щоб потім підмінити», без узагальнень на випадки, яких у темі немає, без обв'язки навколо. ⛔ **Десятків файлів не пишемо** — модулів стільки, скільки їх має сама річ, а річ тут навчальна й мала. Тягне завести ще один файл «щоб було правильно» — спитай, чи піде студент його читати; ні — це не модуль, а звичка.

**Пиши те, про що файл.** Предмет файла вирішує вміст теки, а не уявлення про «повний репозиторій». Про кільцевий буфер — кільцевий буфер; про систему збірки — `CMakeLists.txt`, бо він і є предмет; про тести — тести; про діагностику в GDB — скрипт GDB. **README не доречний ніколи**: його роль виконує сама стаття. Конфіги середовища (OpenOCD, `.clang-format`, CI) — лише коли самі стали предметом; файл збірки — лише коли без нього приклад не запускається взагалі, і тоді він один і мінімальний. Кожен файл поза предметом розбавляє те, заради чого читач відкрив статтю.

**Повнота — головне правило.** Код реалізує **все**, що проза назвала механізмом: жодного «залишаємо читачеві», «за аналогією», «решта симетрично», жодної заглушки там, де текст пообіцяв поведінку. Коментарі в коді — українською.

**Приклад для мікроконтролера НЕ буває «під Arduino».** Arduino — це одне з утілень, а не сама тема. Тому:
- **пояснення веде від загальної електроніки**: спершу те, що правда для будь-якого МК (ніжка з перериванням, таймер, шина, регістр), і лише потім — як це зветься в конкретному середовищі. Читач на STM32 чи ESP32 має впізнати свою задачу, а не перекладати її з чужої;
- **код Arduino ніколи не стоїть сам**: поруч щонайменше ще одна платформа вкладками — типово **ESP-IDF** і **STM32 HAL**, за доречності MicroPython чи голі регістри. Не переклад рядок-у-рядок, а те саме завдання так, як його справді пишуть на тій платформі;
- **тег fence називає ПЛАТФОРМУ, а не мову**: `arduino`, `esp-idf`, `stm32` (а також `stm32-ll`, `zephyr`, `pico-sdk`, `avr`) — інакше три вкладки поспіль підписалися б однаково «C». Рушій знає ці теги й підсвічує їх як C-родину;
- **Arduino не викидаємо** — він часто найзрозуміліший вхід у тему. Ідеться лише про те, щоб він був ПЕРШИМ прикладом, а не ЄДИНИМ.

### Код однієї статті серед інших статей

Ми цінуємо якість, але це код **однієї статті серед інших**: надто великий код нам не
потрібен.

Код реалізує **лише те, що названо цією статтею**, а не охоплює все. Треба показати інше —
це нова тема на майбутнє й посилання на неї, а не ще один модуль тут.
