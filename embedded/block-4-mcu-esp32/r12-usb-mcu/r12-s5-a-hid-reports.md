# ⚙️ HID-звіти: як МК прикидається клавіатурою (макро-пад)

> **Алгоритмічна вставка до теми [§4.12.5 «Класи пристроїв: CDC, HID, MSC»](r12-usb-mcu.md).** Ми вже знаємо, що HID-клас має готовий драйвер у кожній ОС (§4.12.5) і спілкується короткими interrupt-передачами кожні кілька мілісекунд (§4.12.4). Але залишилося головне питання: що саме треба надіслати, щоб система повірила, що до неї підключили клавіатуру, і натиснула за нас Win+R? Жодної магії тут немає — лише два кроки: один раз описати формат, потім слати прості бінарні пакети. Розберемо детально, без острахів і без огляду на BadUSB-етику (це — у 📜 [`r12-s5-history-badusb.md`](r12-s5-history-badusb.md)).

## Задача

Інженерна мета конкретна: змусити ESP32-S2 або ESP32-S3 з нативним USB-OTG (§4.12.6) зенумеруватися в системі як HID-клавіатура і по натисканню однієї фізичної кнопки надіслати готову комбінацію клавіш або рядок — тобто зробити макро-пад.

Чому це нетривіально? Хост не чекає «рядок тексту» через UART. Він чекає суворо **бінарний звіт (report)** — пакет точно того формату, який пристрій сам оголосив у **дескрипторі звіту (report descriptor)** під час енумерації (§4.12.3). Маємо два окремих завдання: **(1) одноразово описати формат** при підключенні й **(2) раз по раз надсилати заповнені звіти** під час роботи. Пропустити перше — хост просто не зрозуміє байти; пропустити відпускання — клавіша «залипне» назавжди.

Межі цієї вставки: ми не заглиблюємося в реалізацію USB-стека — TinyUSB береться як данність, він реалізує транспорт. Нас цікавить **що саме за байти** ми формуємо і чому саме так.

## Ідея: дескриптор оголошує формат, звіт його заповнює

Уявіть, що дескриптор звіту — це **бланк-шаблон**. Він описує: «поле 1 — 8 біт модифікаторів; поле 2 — резервний байт; поля 3–8 — шість кодів клавіш». Хост читає цей шаблон рівно один раз при енумерації і зберігає у драйвері. Після цього кожен пакет від пристрою хост тлумачить за цим шаблоном автоматично. Звіт — це **заповнений бланк**: ті самі поля, тільки вже з конкретними значеннями.

Де аналогія ламається: шаблон надсилається один раз і живе у пам'яті драйвера, а заповнені копії летять потоком кожні кілька мілісекунд — хост їх опитує по interrupt-IN endpoint (§4.12.4).

Канонічний формат для клавіатур — **boot keyboard report**: рівно 8 байтів, і саме на нього є вбудований драйвер у будь-якій ОС — це і є практичний сенс HID-класу, про який ідеться в §4.12.5. Перший байт — **бітова маска модифікаторів (modifier)**: кожен біт відповідає одній спеціальній клавіші. Другий байт — зарезервований, завжди 0x00. Байти 2–7 — масив із шести **кодів використання (usage ID)** з таблиці Keyboard/Keypad (usage page 0x07): сюди кладуться коди одночасно натиснутих звичайних клавіш.

> 🔧 **Навіщо це.** Чому не «надіслати ASCII»? Тому що ОС отримує не символ, а фізичну позицію клавіші. Usage ID 0x04 — це позиція «A» на американській розкладці. ОС перекладає цей код у символ через **власну** системну розкладку клавіатури. При US English ви отримаєте «a», при Ukrainian — «ф». Макро-пад «друкує» те, що бачить ОС, а не те, що ви задумали. Це найпоширеніша практична пастка — вона детальніше розібрана в розділі «Складність і пастки» нижче.

## Як «натиснути» й «відпустити»: семантика звіту

Критична ідея, без якої код хибний: звіт описує **стан клавіатури прямо зараз**, а не подію. Це не «надіслати сигнал натиску». «Натиск» — це надіслати звіт із кодом клавіші у слоті. «Відпускання» — надіслати **порожній** звіт, де всі вісім байтів дорівнюють нулю. Без порожнього звіту хост вважає клавішу затиснутою нескінченно й увімкне авторепіт — символи сипатимуться самі.

Звідси будь-яке макро — це послідовність пар: {звіт-натиск → звіт-відпускання} для кожного символу або комбінації. Комбінація Win+R складається з одного звіту `{modifier=0x08 (LGUI), key[0]=0x15 ('R'), решта=0}` і одного порожнього звіту слідом.

Отже, нам потрібні рівно дві невеликі функції — надіслати один стан і відпустити — та таблиця «символ → (модифікатор, usage ID)».

## Робочий код (C/C++, ESP32-S2/S3, TinyUSB/Arduino)

**Блок 1 — структура звіту і дескриптор.**

Структура `kbd_report_t` дзеркалює Рис. 4.12.5a.1 побайтово — це не випадковий вибір, а канонічний формат HID boot keyboard:

```cpp
#include "Adafruit_TinyUSB.h"   // або esp_tinyusb.h на ESP-IDF

// Модифікатори (byte 0, бітові маски)
#define KEY_LCTRL  0x01
#define KEY_LSHIFT 0x02
#define KEY_LALT   0x04
#define KEY_LGUI   0x08   // Win/Cmd — ліва
#define KEY_RCTRL  0x10
#define KEY_RSHIFT 0x20
#define KEY_RALT   0x40
#define KEY_RGUI   0x80

// Usage ID (Keyboard/Keypad page 0x07), вибірка
#define KEY_A  0x04
#define KEY_R  0x15
#define KEY_NONE 0x00

typedef struct __attribute__((packed)) {
    uint8_t modifier;   // byte 0: бітова маска модифікаторів
    uint8_t reserved;   // byte 1: завжди 0x00
    uint8_t keys[6];    // byte 2..7: до 6 одночасних usage ID
} kbd_report_t;

// Дескриптор звіту — цей «бланк» стек віддає хосту при енумерації (§4.12.3).
// TUD_HID_REPORT_DESC_KEYBOARD() розгортається у повний набір HID-item-байтів;
// побайтовий розбір — у вставці r12-s3-a-descriptors.md.
uint8_t const desc_hid_report[] = { TUD_HID_REPORT_DESC_KEYBOARD() };

Adafruit_USBD_HID usb_hid;
```

Рядок `TUD_HID_REPORT_DESC_KEYBOARD()` — готовий макрос TinyUSB, який генерує той самий «бланк», описаний вище. Переписувати його вручну не потрібно: стек знає формат і передає хосту при запиті дескриптора.

**Блок 2 — дві примітивні операції.**

```cpp
// Надіслати стан: modifier — бітова маска, usage — код звичайної клавіші.
// Якщо потрібно кілька клавіш одночасно — заповнити кілька слотів keys[].
void key_send(uint8_t modifier, uint8_t usage) {
    if (!usb_hid.ready()) return;   // endpoint ще не готовий — пропускаємо
    uint8_t keys[6] = { usage, 0, 0, 0, 0, 0 };  // масив 6 байтів, решта — 0
    // tud_hid_keyboard_report(report_id, modifier, keys[6])
    usb_hid.keyboardReport(0, modifier, keys);   // стан, не подія!
}

// Відпустити всі клавіші — порожній звіт (0x00 × 8).
// ОБОВ'ЯЗКОВО після кожного key_send(), інакше хост вважає клавішу затиснутою.
void key_release(void) {
    if (!usb_hid.ready()) return;
    usb_hid.keyboardRelease(0);
}
```

Зверніть увагу: `usb_hid.ready()` перевіряє, чи endpoint готовий прийняти наступний звіт. Виклик без перевірки мовчки провалюється — натиск губиться. Затримка між `key_send()` і `key_release()` має бути мінімальною, але ненульовою: хост повинен встигнути забрати перший звіт до того, як надійде другий.

**Блок 3 — макро-пад: фізична кнопка → комбінація і рядок.**

```cpp
// Мінімальна таблиця ASCII → usage ID (тільки US-layout, нижній регістр).
// Для верхнього регістру потрібен modifier KEY_LSHIFT; кирилиця — неможлива
// без знання системної розкладки хоста (пастка №2 нижче).
struct { char ascii; uint8_t usage; } ascii_map[] = {
    { 'a', 0x04 }, { 'b', 0x05 }, { 'r', 0x15 },
    // ... повна таблиця 'a'-'z': usage 0x04..0x1D
    { ' ', 0x2C }, { '\n', 0x28 },
};

uint8_t ascii_to_usage(char c) {
    for (auto& e : ascii_map)
        if (e.ascii == c) return e.usage;
    return KEY_NONE;
}

// Надрукувати C-рядок символ за символом (тільки US-layout).
void type_string(const char* s) {
    for (; *s; s++) {
        uint8_t u = ascii_to_usage(*s);
        if (u == KEY_NONE) continue;
        key_send(KEY_NONE, u);
        delay(8);          // дати хосту забрати звіт (залежить від bInterval)
        key_release();
        delay(8);
    }
}

// Антидребезг — деталі в §4.4.5 / ch22-s5-a-debounce.md.
bool button_pressed_edge();   // повертає true один раз при фронті

void loop() {
    if (button_pressed_edge()) {
        // Комбінація Win+R → відкрити «Виконати»
        key_send(KEY_LGUI, KEY_R);
        delay(8);
        key_release();
        delay(50);         // пауза перед наступним макро

        // Або надрукувати рядок (тільки US-layout, нижній регістр):
        // type_string("hello");
    }
}
```

Функція `type_string()` демонструє принцип: цикл по символах, кожен — окрема пара send/release. `delay(8)` тут — не магічне число, а оцінка: при `bInterval=1 мс` хост опитує кожну мілісекунду, але між надсиланням і тим, як хост підніме звіт, потрібен мінімум один повний інтервал опитування. Занадто короткий `delay` губить символи; занадто довгий сповільнює набір.

## Складність і пастки на МК

**Звіт — це стан, не натиск.** Забули порожній звіт після `key_send()` — клавіша «залипла», хост увімкнув авторепіт, символи сиплються самі. Найпоширеніша перша помилка — і найпростіша: завжди викликайте `key_release()` після кожного `key_send()`.

**Розкладка хоста.** Usage ID 0x04 — це фізична позиція клавіші «A» на американській розкладці, а не сама літера «A». При системній розкладці Ukrainian (ЙЦУКЕН) той самий 0x04 дасть «ф». Макро-пад «друкує» те, що бачить ОС — ваш код байдужий до мови системи. Якщо потрібна портативність — або фіксуйте розкладку на хості, або переходьте на кастомний дескриптор з абсолютними Unicode-кодами (вихід за межі boot protocol).

**Максимум 6 клавіш одночасно (boot protocol).** У масиві `keys[6]` лише шість слотів. Сьомий код просто нікуди покласти. Апаратні клавіатури при переповненні заповнюють усі слоти кодом 0x01 (Keyboard ErrorRollOver) — хост розуміє, що стався rollover. У boot protocol це обмеження конструктивне; для N-key rollover потрібен кастомний дескриптор із бітовою картою всіх клавіш.

**Час між звітами і `bInterval`.** Темп опитування визначає поле `bInterval` interrupt-IN endpoint'а (§4.12.4) — наприклад, 1 мс. Надсилати наступний звіт до того, як хост забрав попередній, безглуздо: стек або відкине дані, або заблокує виклик. `delay()` у коді — лише груба оцінка; правильний підхід — перевіряти `usb_hid.ready()` перед кожним викликом.

**`usb_hid.ready()` / готовність endpoint.** Перед будь-яким `keyboardReport()` або `keyboardRelease()` перевіряйте готовність. Якщо пристрій ще не завершив енумерацію або попередній звіт ще «в польоті», виклик повертає false і нічого не надсилає — тихо, без помилки. Типова ситуація: код стартує в `setup()`, а хост ще не встиг підняти endpoint.

**Нативний USB лише на ESP32-S2/S3.** Класичний ESP32 (без суфікса) не має вбудованого USB-контролера (§4.12.6) — там HID можливий лише через зовнішній чип (CH340G, CP2102) або BLE HID, але не через прямий USB Device. На S2/S3 USB-стек і Serial-монітор конкурують за один контролер: при прошивці через нативний USB порт він може зникати з Device Manager — це норма, а не зависання.

**Це справжній HID, а не емуляція.** Хост не відрізняє ваш ESP32 від залізної клавіатури — у нього немає механізму перевірки «справжності». Звідси виникає ціла категорія вразливостей; технічна основа і реальна історія — у 📜 [`r12-s5-history-badusb.md`](r12-s5-history-badusb.md). Тут лише фіксуємо факт: інструмент потужний і потребує усвідомленого застосування.

## Підсумок

HID-клавіатура на МК — це **оголошений формат звіту (дескриптор) плюс потік 8-байтових станів**: «натиснути» означає заповнити потрібні біти модифікаторів і покласти usage ID у слоти, «відпустити» — надіслати вісім нулів. Енумерацію, транспорт по interrupt-IN endpoint і тайминги бере на себе стек — ваш код зводиться до двох функцій і таблиці символів. Дві невеликі функції плюс таблиця перетворюють будь-яку кнопку на макро-пад.

А як ці байти фізично летять дротом без окремої лінії такту — у 🧮 NRZI ([`r12-s2-m-nrzi.md`](r12-s2-m-nrzi.md)).
