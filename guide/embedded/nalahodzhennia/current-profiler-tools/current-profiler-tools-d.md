# Вимірювання профілю струму: прив'язати кожен міліампер до рядка коду

У попередніх кроках ми звели рваний профіль до [середнього струму за робочим циклом](guide:embedded/duty-cycle-current) і з'ясували, [чому мультиметр на імпульсах бреше](guide:embedded/measure-consumption), а чесну криву знімає окремий [клас приладів-профілювальників](guide:embedded/measure-consumption/comp-current-profiler.md). Тепер у нас на екрані є та сама крива I(t): рівне плато сну, гострі піки передачі, площа під кожним. І тут більшість інженерів спотикаються вдруге.

Профіль каже, **скільки** струму й **коли**. Він мовчить про головне — **чому саме тут**. Бачиш пік 180 мА завширшки 40 мс — а що його породило? Wi-Fi-передача? Запис у Flash? Ініціалізація давача, яку забули вимкнути? Дивлячись на голу криву, ти гадаєш. А оптимізувати наосліп — те саме, що лагодити код за логами без номерів рядків. Цей крок — про те, як перекинути міст від форми струму до конкретного місця в прошивці, як вибрати під задачу правильний прилад і як перетворити разовий вимір на автоматичну перевірку, що ловить регресію енергії ще до відвантаження.

## Сліпа пляма профілю: крива без підписів

Поставмо себе на місце приладу. Профілювальник (від англ. *to profile* — «зняти обрис збоку», через латинське *filum* «нитка»: обрис, проведений однією лінією) бачить лише струм на своєму шунті. Він не знає, що робить чип усередині: для нього і передача пакета, і запис логу у Flash — однакові «300 мА протягом стількох-то мілісекунд». Форма імпульсу буває схожа до невідрізнення, а вартість для батареї — різна, і лікуються вони по-різному.

Звідси типова сцена. Інженер бачить на профілі підозріло товстий пік і півдня вгадує його природу: вимикає радіо — пік лишається; зрізає частоту АЦП — не зникає; нарешті виявляє, що то драйвер дисплея щоразу перезаливає всю відеопам'ять. Півдня здогадів там, де відповідь могла бути миттєвою — якби крива була підписана.

Підписати її можна. Ключ у тому, що профілювальник майже завжди має не лише аналоговий вхід для струму, а й **цифрові входи** — кілька ліній, які він оцифровує **в той самий час, на тій самій осі**, що й струм. Якщо прошивка сама смикне такою лінією на межах своїх фаз, прилад накладе ці перемикання на криву струму — і кожен пік дістане підпис від самого коду.

> 🔧 **Навіщо це.** Без підписів оптимізація енергії перетворюється на ворожіння: міняєш щось наосліп, переміряєш, сподіваєшся. З підписами вона стає адресною — видно, що «boot+Wi-Fi коштує 144 мА·с, а сам вимір лише 5», тож зрозуміло, за який важіль тягнути. Та сама [таблиця фаз із розрахунку циклу](guide:embedded/duty-cycle-current), але вже не на папері, а зчитана з реального заліза.

## Маркер у прошивці: GPIO як підпис над піком

Найпростіший і найнадійніший спосіб підписати криву — **GPIO-маркер**. Ідея гранично проста: виділяєш один вільний вивід чипа, заводиш його в цифровий вхід профілювальника й піднімаєш на час фази, яку хочеш бачити. Профілювальник малює цей рівень окремою доріжкою точно під кривою струму — і ти бачиш не «якийсь пік», а «пік, поки маркер фази TX був угорі».

Реалізація — два рядки прошивки навколо цікавого коду. Маркер мусить смикатися якомога ближче до самої події, тому пишемо прямо в регістр порту, без важких обгорток:

```c
// ESP-IDF, ESP32: GPIO як маркер фаз для профілювальника
#define MARK_GPIO   25                 // вільний вивід → цифровий вхід приладу
#define MARK_MASK   (1u << MARK_GPIO)

static inline void mark_high(void) { REG_WRITE(GPIO_OUT_W1TS_REG, MARK_MASK); }
static inline void mark_low (void) { REG_WRITE(GPIO_OUT_W1TC_REG, MARK_MASK); }

void measure_cycle(void) {
    gpio_set_direction(MARK_GPIO, GPIO_MODE_OUTPUT);

    mark_high();                        // ── межа фази: почалася передача
    wifi_send(packet, len);
    mark_low();                         // ── фаза скінчилася

    sensor_read();                      // ця фаза без маркера — поки нецікава
}
```

Запис прямо в `GPIO_OUT_W1TS_REG` / `W1TC_REG` (set/clear окремими регістрами) перемикає вивід за одну машинну інструкцію — маркер встає рівно на межі коду, а не за десятки тактів по дорозі через бібліотеку. На екрані профілювальника проти піку струму тепер стоїть прямокутна сходинка маркера: видно з точністю до фронту, де передача почалася й де скінчилась, і скільки заряду припало саме на неї.

![Крива струму I(t) з накладеною доріжкою GPIO-маркера: фронт маркера вгору збігається з початком піку передачі, фронт униз — з його кінцем. Заряд під піком належить саме розміченій фазі, бо її межі задає код, а не око.](/guide/embedded/nalahodzhennia/current-profiler-tools/img/gpio-marker.svg)

*Угорі — струм у часі, унизу — рівень GPIO-маркера на тій самій осі. Маркер ставить прошивка на вході й виході з фази, тож площа під піком прив'язана до коду точно, а не на око.*

Одного маркера досить, щоб відокремити «цікаву» фазу від решти. Та коли фаз кілька — boot, вимір, передача, запис — одного біта мало. Тут і стає в пригоді те, що цифрових входів у приладу не один.

> 🔧 **Навіщо це.** Маркер коштує один вивід і дві інструкції, а економить години здогадів. Перший крок будь-якого профілювання з прошивкою — вивести GPIO-маркер на межах головних фаз. Далі весь профіль читається не «що це за горб», а «фаза X триває стільки, бере стільки заряду» — прямо в одиницях твоєї [таблиці робочого циклу](guide:embedded/duty-cycle-current).

## Кілька бітів: підписати всі фази коду

Профілювальники несуть **кілька цифрових ліній** — наприклад, [PPK2 має вісім входів](guide:embedded/current-profiler-tools/comp-power-profiler-instruments.md), які можна читати як простенький логічний аналізатор. Це відмикає природний прийом: вивести станом не одну фазу, а **номер фази двійковим кодом** на 2–3 виводи. Три лінії дають вісім станів — більш ніж досить, щоб підписати весь цикл давача.

```c
// Номер поточної фази двійково на 3 GPIO → 3 цифрові входи приладу
typedef enum { PH_SLEEP=0, PH_BOOT=1, PH_SENSE=2, PH_TX=3, PH_FLASH=4 } phase_t;

#define PH_GPIO0 25
#define PH_GPIO1 26
#define PH_GPIO2 27

static inline void phase_set(phase_t p) {
    uint32_t set = 0, clr = 0;
    ((p >> 0) & 1 ? set : clr) |= (1u << PH_GPIO0);
    ((p >> 1) & 1 ? set : clr) |= (1u << PH_GPIO1);
    ((p >> 2) & 1 ? set : clr) |= (1u << PH_GPIO2);
    REG_WRITE(GPIO_OUT_W1TS_REG, set);   // одночасно: підняти потрібні біти
    REG_WRITE(GPIO_OUT_W1TC_REG, clr);   //            й опустити решту
}

void cycle(void) {
    phase_set(PH_BOOT);   boot_init();
    phase_set(PH_SENSE);  sensor_read();
    phase_set(PH_TX);     wifi_send(pkt, len);
    phase_set(PH_FLASH);  log_append(pkt, len);
    phase_set(PH_SLEEP);  enter_deep_sleep();
}
```

Тепер на профілі під кривою струму йде доріжка номера фази, що міняється сходинками: 1→2→3→4→0. Програма приладу на ПК уміє більше — виділиш на кривій будь-який інтервал, і вона підрахує **середній струм і заряд саме в межах одного значення маркера**. Ти дістаєш не картинку, а вже готову таблицю: фаза boot — стільки мА·с, фаза TX — стільки, фаза Flash — стільки. Рівно ті числа, що йшли в розрахунок [середнього струму](guide:embedded/duty-cycle-current), тільки виміряні, а не оцінені.

Є одна важлива розплата, про яку мовчать недосвідчені. У деяких приладів цифровий вхід ділить розрядність із аналого-цифровим перетворювачем струму: коли вмикаєш запис маркера, молодший біт відліку струму віддається під маркер, тож точність струму трохи падає. На [JS110, наприклад, увімкнення цифрового входу зрізає відлік струму з 14 до 13 біт](guide:embedded/current-profiler-tools/comp-power-profiler-instruments.md) — для розмітки фаз це невідчутно, але знати про компроміс варто.

## Коли пінів нема: підпис через лог

GPIO-маркери — золотий стандарт, бо вони миттєві й не залежать від того, що чип робить далі. Та інколи вільних виводів просто немає, або хочеться підпису багатшого за «номер фази» — з власне текстом події. Тоді другий шлях — **синхронний лог**: прилад одночасно зі струмом слухає UART-вихід пристрою й кладе рядки логу на ту саму вісь часу.

Так працює, зокрема, [Otii: він пише UART-лог поряд із кривою струму, і виділення на кривій підсвічує відповідний рядок логу — і навпаки](guide:embedded/current-profiler-tools/comp-power-profiler-instruments.md). Прошивка просто друкує звичні повідомлення:

```c
printf("PHASE tx start\n");
wifi_send(pkt, len);
printf("PHASE tx done  %u bytes\n", len);
```

— а на екрані ці рядки стоять рівно проти своїх піків. Перевага — читабельність: бачиш не код `011`, а живий текст. Недолік теж очевидний: сам `printf` через UART коштує часу й струму, і він домішується до виміру тієї фази. Тому лог-підпис добрий для грубої прив'язки й налагодження логіки, а коли треба чесно зміряти заряд саме фази — повертаються до GPIO-маркера, що майже нічого не коштує.

Третій, найгрубіший спосіб — **синхронізація очима по характерній події**. Запускаєш на пристрої впізнаваний патерн (наприклад, три коротких спалахи світлодіода поспіль), він лишає на профілі три однакові піки-«реперні точки», і від них відлічуєш решту вручну. Підходить як остання змога, коли ні зайвого виводу, ні UART під рукою немає.

## Який прилад під яку задачу

Маркери лягають на будь-який профілювальник — але самі прилади різні, і брати найдорожчий «про запас» немарно. Вибір диктують три речі: **розмах струмів** твого вузла (скільки [порядків динамічного діапазону](guide:embedded/measure-consumption/math-dynamic-range.md) треба охопити), **потрібна смуга** (наскільки гострі піки треба не змазати) і **бюджет**. Конкретні моделі та їхні числа зведено в [компонентній вставці про прилади-профілювальники](guide:embedded/current-profiler-tools/comp-power-profiler-instruments.md); тут — логіка вибору.

**Низькоспоживний IoT на батарейці, аматор чи стартап.** Вузол спить у мікроамперах, зрідка стріляє сотнею мА; розмах 5–6 порядків, піки в десятки мілісекунд. Тут вистачить недорогого приладу класу Power Profiler Kit: автодіапазон від сотень наноамперів до ампера, вибірка близько 100 тисяч відліків за секунду, вісім цифрових входів для маркерів і живлення DUT із самого приладу. Це робоча конячка масового розробника.

**Метрологія, сертифікація, тонка оптимізація.** Коли треба не «приблизно», а підтверджене число заряду й енергії, гострі мікросекундні фронти й глибокий діапазон — беруть точний енергоаналізатор класу Joulescope: мільйони відліків за секунду, наноамперна роздільність, широчезний динамічний діапазон в одному вимірі без ручного перемикання. Дорожче, але результат можна класти в звіт.

**Профіль із керованим живленням і автоматизацією.** Коли вимір треба ганяти в циклі регресійних тестів, живити пристрій заданим профілем напруги (просадки, провали) і синхронно писати UART-лог — підходить інструмент-SMU класу Otii: помірна вибірка, зате джерело-вимірювач плюс лог плюс програмний доступ для автоматики.

**Самороб «шунт + підсилювач + осцилограф».** Найдешевший шлях, коли заздалегідь відомо, що пристрій сидить в одному-двох порядках струму без глибокого сну. Один шунт бере один-два порядки — і впирається рівно в [межу динамічного діапазону](guide:embedded/measure-consumption/math-dynamic-range.md), яку ми вже рахували. Маркер сюди теж заводиться — другим каналом осцилографа.

**Вибір одним реченням:** один-два порядки струму й мінімум грошей — шунт з осцилографом; повний профіль від нА до ампера «з коробки» — Power-Profiler-клас; метрологія — Joulescope; кероване живлення й автотести — Otii.

![Карта вибору приладу на двох осях: по горизонталі — розмах струмів вузла в порядках, по вертикалі — потрібна смуга й частота вибірки. Шунт з осцилографом сидить у вузькому діапазоні, Power-Profiler покриває весь розмах за середньої смуги, Joulescope — найширший діапазон і найвищу смугу, Otii — широкий діапазон із джерелом живлення й автотестами.](/guide/embedded/nalahodzhennia/current-profiler-tools/img/tool-selection.svg)

*Дві осі рішення: розмах струмів вузла (скільки порядків треба охопити) і потрібна смуга. Кожен клас приладів займає свою зону — бери найдешевший, що накриває обидві координати твоєї задачі.*

## Не змазати пік: смуга, шунт, дроти

Будь-який із цих приладів дасть брехливу криву, якщо знехтувати трьома речами — і всі три ми вже зустрічали, тепер зведімо їх у чек перед виміром.

**Смуга й частота вибірки.** Фронт Wi-Fi- чи BLE-пакета — мікросекунди. Якщо прилад вибирає повільно, він згладить гострий пік так само, як [це робив мультиметр](guide:embedded/measure-consumption) — і ти знову побачиш «середнє» замість справжньої висоти. Правило: частота вибірки має бути на порядки вища за найкоротший фронт, який треба побачити. Сто тисяч відліків за секунду беруть мілісекундні фази впевнено; щоб роздивитися мікросекундний фронт радіо — потрібні мільйони.

**Напруга втрат на шунті.** [Спад на вимірювальному шунті (burden voltage)](guide:embedded/measure-consumption) на піку струму просаджує живлення чипа й може кинути його в скид по [детектору просадки (brownout)](book:programming/brownout) — і ти зміряєш не пристрій, а власне втручання. Готові профілювальники тримають цей спад у мілівольтах автоперемиканням діапазонів; із саморобним шунтом стеж сам, щоб I_max × R_шунт лишалося малим проти живлення.

**Дроти й земля.** На наноамперному дні сну зайвий сантиметр дроту ловить наводку, що топить корисний сигнал у шумі, а паразитна ємність довгого кабелю згладжує фронти піків. З'єднання — короткі, земля DUT і приладу — в одній точці, маркерний провід — окремою короткою лінією, щоб його перемикання не наводилось на струмовий вхід.

І найголовніша пастка місця врізання, яку ми зустрічали в [споживанні всієї плати](guide:embedded/board-consumption): міряти треба там, де тече струм самого чипа, а не за USB-роз'ємом плати розробника — інакше до виміру домішається USB-UART міст і стабілізатор плати, і «сплячий» чип покаже міліампери, яких у ньому немає.

## Профіль як регресійний тест

Найбільша віддача приходить, коли вимір перестає бути разовим. Енергія тече так само непомітно, як і витоки пам'яті: невинна правка прошивки — забули погасити давач, додали зайве пробудження, поставили бібліотеку, що не дає чипу заснути, — і середній струм тихо подвоюється. У лабораторії все добре, біда вилазить у полі через тижні. Ліки ті самі, що від регресій коду: **зробити споживання числом, яке перевіряється автоматично на кожній збірці**.

Прилади класу Otii мають для цього програмний доступ — приладом [керують по TCP командами у форматі JSON](guide:embedded/current-profiler-tools/comp-power-profiler-instruments.md): сценарій сам виставляє живлення, запускає захоплення, виділяє цикл за маркером, дістає заряд і енергію числом. Звідси — звичайний тест: прошив білд, прогнав один робочий цикл, узяв заряд за цикл і порівняв із порогом.

**Worked-приклад. Енергетичний тест, що валить білд при регресії.**

```c
// Псевдо-API приладу (реальні виклики залежать від моделі):
//   profiler_set_voltage(V)        — виставити живлення DUT
//   profiler_capture(sec)          — захопити вікно довжиною sec секунд
//   profiler_charge_uas()          — інтеграл струму за вікно, у мкА·с

// Міряємо заряд ОДНОГО активного сплеску (boot → вимір → TX → знову сон):
// він короткий, тож тест швидкий. Поріг — із розрахунку робочого циклу.
#define WINDOW_S          3.0       // вікно довше за активну фазу (~1.7 с)
#define Q_BUDGET_UAS   203000.0     // бюджет заряду активної фази, мкА·с (=203 мА·с)
#define Q_TOLERANCE       1.10      // допуск +10 % на розкид між вимірами

int energy_regression_test(void) {
    profiler_set_voltage(3.3);
    profiler_capture(WINDOW_S);                 // охопити весь активний сплеск

    double q = profiler_charge_uas();           // заряд за вікно, мкА·с
    double i_avg_ua = q / WINDOW_S;             // мкА·с / с = мкА (середнє за вікно)

    printf("burst charge = %.0f uA*s,  I_avg(window) = %.0f uA\n", q, i_avg_ua);

    if (q > Q_BUDGET_UAS * Q_TOLERANCE) {       // порівнюємо саме заряд, не середнє
        printf("FAIL: charge %.0f > budget %.0f (+%.0f%%)\n",
               q, Q_BUDGET_UAS, (Q_TOLERANCE - 1.0) * 100);
        return 1;                               // ненульовий код → CI валить білд
    }
    printf("PASS: within energy budget\n");
    return 0;
}
```

Поріг тут — заряд саме активного сплеску (boot+вимір+TX), бо ганяти в тесті повний 600-секундний цикл недоцільно: активна частина коротка, її й міряємо. Порівнюємо **заряд**, а не середній струм, бо заряд адитивний і не залежить від того, яким вибрали вікно, аби воно покривало весь сплеск. Тепер бюджет заряду з [розрахунку робочого циклу](guide:embedded/duty-cycle-current) перестає бути числом на папері й стає **порогом у тесті**. Додав хтось зайве пробудження чи забув погасити давач — заряд активної фази переліз поріг, тест червоний, причину видно ще до зливання гілки, а не через місяць у полі по сівших батареях. Площа під профілем, яку ми весь час називали єдиною чесною метрикою автономності, нарешті працює сама, без людини над приладом.

На цьому замикається вся лінія енергоощадності: [звели профіль до середнього струму](guide:embedded/duty-cycle-current) → [зрозуміли, чому його треба міряти приладом, а не мультиметром](guide:embedded/measure-consumption) → навчилися підписувати криву маркерами, вибирати прилад під задачу й тримати споживання під автоматичним наглядом. Далі лишається інженерна рутина: дивитися на профіль, знаходити найтовстіший доданок заряду й тягнути за відповідний важіль — але вже з повністю підписаною, виміряною й автоматично вартованою кривою в руках.
