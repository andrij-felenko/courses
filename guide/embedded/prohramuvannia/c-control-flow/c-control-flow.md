# Розгалуження й цикли

Досі кожна наша програма була **прямою лінією**. Процесор брав інструкції одну за одною, згори вниз, і ця послідовність ніколи не зверталася: оголосили змінну, порахували, вивели — кінець. Це рівно те, що вміє [цикл вибірки-виконання](book:programming/fetch-decode-execute): узяти інструкцію за адресою, виконати, перейти до наступної адреси. Але прямою лінією не напишеш нічого цікавого. Термостат мусить **вирішувати**: гріти чи не гріти. Опитування десяти давачів мусить **повторюватися** десять разів, а не бути десятьма копіями одного коду. Обидві потреби — вибір і повтор — і є те, що зветься **керуванням потоком** (англ. *control flow*, «керування течією» виконання): як саме процесор рухається кодом, коли не просто йде вниз.

Найкрасивіше тут те, що потрібно **лише дві** нові ідеї. Виявляється, будь-яку програму — від блимання світлодіодом до операційної системи — можна скласти з трьох цеглин: **послідовність** (одне за одним, це вже маємо), **розгалуження** (вибір із двох шляхів) і **повтор** (те саме кілька разів). Що цих трьох досить для геть усього — не наша здогадка, а [доведена теорема](guide:embedded/c-control-flow/hist-structured-programming.md): двоє математиків показали це ще в 1966 році, і відтоді структурне програмування будується саме на цих трьох формах. Розберімо дві нові.

## Розгалуження: коли шлях роздвоюється

Уся ідея розгалуження тримається на одному запитанні, на яке є лише дві відповіді: **так** чи **ні**. «Температура нижча за поріг?» «Кнопку натиснуто?» «Лічильник дійшов до нуля?» Процесор обчислює таку умову, дістає одну з двох відповідей — і залежно від неї йде **однією з двох гілок**. Слово тут точне: як річка на розвилці, потік роздвоюється, кожна гілка робить своє, а потім вони знову зливаються в один шлях.

![Потік виконання доходить до ромба-умови й роздвоюється: гілка «так» робить одне, гілка «ні» — інше, далі шляхи зливаються](/guide/embedded/prohramuvannia/c-control-flow/img/branch-fork.svg)
*Розгалуження: виконання йде згори вниз, доходить до умови й роздвоюється. Умова істинна — потік іде гілкою `if`; хибна — гілкою `else`. Хай яку гілку обрано, за нею шляхи знову зливаються, і далі код спільний.*

У C це записує оператор `if` (англ. *if* — «якщо») з необов'язковим `else` (англ. *else* — «інакше»):

```c
if (temperature < 20) {
    heater_on();          // гілка «так»: холодно — вмикаємо
} else {
    heater_off();         // гілка «ні»: тепло — вимикаємо
}
```

Читається майже як українською: **якщо** температура нижча за 20 — увімкнути нагрів, **інакше** — вимкнути. Дужки після `if` містять **умову**; фігурні дужки `{…}` — **блок**, тобто гурт інструкцій, що йдуть як одне ціле. Гілку `else` можна й опустити — тоді при хибній умові просто нічого не стається, і потік іде далі.

Що ж таке та умова всередині дужок? Це вираз, який дає **правду або неправду** — те, що ми вже бачили як тип `bool` у [змінних і типах](guide:embedded/c-variables-types). C тут прямолінійний: **нуль — це «ні», будь-що інше — «так»**. `if (x)` спрацює для кожного ненульового `x` і промине лише при `x == 0`. Ця дрібниця — джерело і зручності, і найпоширенішої в мові пастки, до якої ми дійдемо.

Умову будують **операторами порівняння**. Їх шість, і вони віддають рівно `1` (правда) або `0` (неправда):

```c
a == b     // дорівнює        (УВАГА: подвійне =)
a != b     // не дорівнює
a <  b     // менше
a <= b     // менше або дорівнює
a >  b     // більше
a >= b     // більше або дорівнює
```

Кілька умов зшивають **логічними операторами**: `&&` (і — правда, коли обидві сторони правдиві), `||` (або — правда, коли хоч одна), `!` (не — перевертає правду на неправду). Це та сама [булева алгебра](book:math/boolean-algebra), що керує логічними вентилями в залізі, тільки записана символами мови; закони в неї ті самі.

> 🔧 **Навіщо це.** Уся «поведінка» пристрою — це дерево `if`-ів на давачах. «Якщо напруга акумулятора впала нижче 3.3 В **і** двигун усе ще крутиться — вимкнути двигун і підняти прапорець аварії.» Прошивка не «розуміє» ситуацію — вона проганяє вхідні числа крізь умови й обирає гілку. Навчитися чітко ставити умову — половина вміння писати керування.

Один оператор порівняння варто закарбувати окремо, бо на ньому спотикаються всі. **Порівняння — це `==`, подвійне.** Одинарне `=` — це **присвоєння**, воно кладе значення в змінну. І ось де ховається капкан: у C присвоєння саме є виразом, чиє значення — те, що присвоїли. Тому `if (x = 0)` не помилка компіляції — це «поклади 0 у `x`, а тоді перевір результат», результат нуль, гілка ніколи не спрацює. А `if (x = 5)` спрацює **завжди** і мовчки зіпсує `x`. Компілятор такий код здебільшого пропустить (або лиш кине попередження). Тому давнє правило захисту: за звички писати сталу **ліворуч** — `if (0 == x)` — випадкове одинарне `=` стане `if (0 = x)`, а це вже помилка компіляції, і машина спіймає описку за вас.

### Кілька розвилок поспіль

Розвилка рідко буває одна. Часто треба перебрати кілька випадків: якщо перше — то це, якщо друге — то те, а як ніщо не збіглося — щось за замовчуванням. Для цього гілки нанизують ланцюжком `else if`:

```c
if (temp < 10) {
    status = COLD;
} else if (temp < 25) {
    status = OK;              // 10..24: не COLD, але < 25
} else if (temp < 40) {
    status = WARM;
} else {
    status = HOT;             // усе інше: 40 і вище
}
```

Порядок тут важливий, і в цьому вся суть. Умови перевіряються **згори вниз**, і перша ж істинна забирає керування — решту навіть не читають. Тому до другої гілки потік дійде, лише **не** потрапивши в першу; отже, коли перевіряють `temp < 25`, ми вже точно знаємо, що `temp >= 10`. Ланцюжок природно ділить числову вісь на непересічні смуги, і кожна умова говорить про свій відрізок, спираючись на те, що попередні вже відсіяли.

Коли ж вибір іде не за діапазоном, а за **точним значенням** однієї змінної — станом автомата, кодом команди, номером режиму, — зручніший `switch` (англ. *switch* — «перемикач»): він розводить потік за конкретними значеннями, як стрілка на залізниці розводить колію.

```c
switch (command) {
    case CMD_START:
        motor_start();
        break;              // без break потік «протече» в наступний case
    case CMD_STOP:
        motor_stop();
        break;
    default:
        log_unknown(command);   // жоден case не збігся
}
```

Тут криється своя славнозвісна пастка — **провал крізь** (англ. *fall-through*). Дійшовши до кінця `case` без `break`, потік **не** виходить зі `switch`, а тече в наступний `case`, ігноруючи його умову. Іноді це роблять навмисне (кілька значень з однією дією), але частіше забутий `break` — це притаєна вада, коли `CMD_START` мовчки виконує ще й тіло `CMD_STOP`.

## Цикли: коли те саме треба повторити

Друга нова ідея — **повтор**. Опитати не один давач, а всі шістнадцять. Почекати, доки біт готовності стане одиницею. Пробігти масив і скласти суму. Скрізь та сама форма: роби щось **знов і знов**, доки виконується якась умова, — і саме тому це зветься **цикл** (гр. *kýklos* — «коло, кільце»): виконання ходить по колу, щоразу повертаючись до тієї самої перевірки.

Виходить, цикл — це та сама розвилка, але з **петлею назад**. Перевіряємо умову; якщо істинна — робимо тіло й **повертаємося до перевірки знову**; якщо хибна — виходимо й ідемо далі. Уся різниця між трьома формами циклу в C — лише в тому, **де стоїть ця перевірка** відносно тіла.

![Три форми циклу поруч: while перевіряє перед тілом, do-while — після тіла, for тримає старт, перевірку й крок разом](/guide/embedded/prohramuvannia/c-control-flow/img/loop-shapes.svg)
*Три форми циклу різняться лише місцем перевірки. `while` перевіряє **перед** тілом — тіло може не виконатися жодного разу. `do…while` перевіряє **після** — тіло виконається щонайменше раз. `for` тримає три частини (старт, перевірку, крок) поруч, тож лічильник видно одразу.*

Найпростіший — `while` (англ. *while* — «доки»): «доки умова істинна — виконуй тіло».

```c
while (!data_ready()) {
    // нічого не робимо — просто чекаємо, доки давач буде готовий
}
value = read_data();       // сюди дійдемо, лише коли data_ready() стане true
```

Перевірка стоїть **перед** тілом, і це визначає поведінку в межовому випадку: якщо умова хибна вже на вході, тіло не виконається **жодного разу**. Коли треба навпаки — щоб тіло спрацювало хоч раз, а перевірка була вже після нього, — беруть `do…while`:

```c
do {
    sample = adc_read();       // хоча б один вимір робимо завжди
} while (sample > threshold);   // і повторюємо, доки він завеликий
```

Найчастіша ж форма — `for` (англ. *for* — «для»). Вона створена для випадку «повторити рівно N разів» і збирає три речі, що завжди йдуть разом, в один рядок: **старт**, **умову продовження** й **крок**.

```c
for (int i = 0; i < 16; i++) {
    read_sensor(i);        // опитати давач номер i, для i = 0,1,…,15
}
```

Читати треба так: `int i = 0` — один раз на початку (завести лічильник); `i < 16` — перевіряти **перед кожним** проходом (умова продовження); `i++` — виконувати **після кожного** проходу (крок, тут — збільшити `i` на одиницю). Ті самі три частини можна було б розкидати навколо `while`, але `for` тримає їх на очах в одному місці, і тому очиткою важче загубити крок і зробити нескінченний цикл. По суті, `for` — це причесаний `while`, спеціалізований під лічені повтори.

Два оператори дають точніше керування зсередини тіла. `break` (англ. *break* — «розірвати») негайно **виходить** із циклу, хай яка там умова, — зручно, коли знайшли потрібне й далі шукати нема сенсу. `continue` (англ. *continue* — «продовжити») **пропускає решту тіла** й переходить одразу до наступного проходу — коли цей конкретний елемент нецікавий.

```c
for (int i = 0; i < count; i++) {
    if (sensors[i].disabled) continue;     // вимкнений — пропустити й далі
    if (sensors[i].value > LIMIT) {
        alarm();
        break;                              // знайшли аварійний — годі шукати
    }
}
```

### Пастка нескінченного циклу

За повтор доводиться платити пильністю, бо в циклі легко застрягти назавжди. Цикл добігає кінця, лише коли його умова колись стане хибною. Якщо в тілі **ніщо не рухає її до хибності** — процесор крутитиме те саме тіло вічно, і програма «зависне». Класика — забути крок лічильника:

```c
int i = 0;
while (i < 10) {
    read_sensor(i);
    // забули i++ — умова i < 10 істинна ВІЧНО, цикл не скінчиться
}
```

Тому за кожним циклом ставте одне подумки запитання: **що саме тут наближає умову до виходу — і чи справді воно спрацює за всіх вхідних даних?** У `for` крок стоїть на видноті й забути його важче; у `while` за просування відповідає тіло, і саме там нескінченні цикли й зароджуються.

> 🔧 **Навіщо це.** У прошивці зависнути в циклі означає, що пристрій просто перестав реагувати — не гірше, не краще, а **мертвий**: не читає кнопок, не крутить моторів, поки не смикнеш живлення. Ще підступніше — очікування апаратної події (`while (!flag)`): якщо давач через несправність ніколи не виставить `flag`, прошивка застрягне тут навіки. Тому такі очікування страхують: або обмежують число спроб (лічильник-тайм-аут), або доручають окремому «сторожу» — [сторожовому таймеру](book:programming/watchdog), що сам перезавантажить систему, коли головний цикл надто довго не подає ознак життя.

## Один цикл, що не має скінчитися

Досі нескінченний цикл був вадою. У прошивці ж є один — **навмисний і головний**, без якого не працює майже жоден пристрій. Настільна програма запускається, робить своє й **завершується**, повертаючи керування операційній системі. А мікроконтролер віддавати керування нікому: під ним немає ОС, і «завершитися» йому нема куди — за останньою інструкцією процесор просто піде виконувати випадкове сміття в пам'яті. Тому прошивка **ніколи не завершується**. Вона робить одноразове налаштування, а тоді входить у нескінченний цикл і крутиться в ньому, доки є живлення.

![Суперцикл: setup() виконується один раз, далі while(1) без кінця повторює зчитати - вирішити - подіяти](/guide/embedded/prohramuvannia/c-control-flow/img/superloop.svg)
*Суперцикл — кістяк будь-якої прошивки. Спершу `setup()` один раз готує залізо (тактування, виводи, периферію). Далі `while(1)` без кінця жене одне коло: **зчитати** входи, **вирішити** за станом (ті самі `if`-и), **подіяти** на виходи — і знову спочатку.*

Той нескінченний цикл так і звуть — **суперцикл** (англ. *superloop*, «над-цикл»), і виглядає він так:

```c
int main(void) {
    hardware_init();               // один раз: тактування, GPIO, периферія

    while (1) {                    // 1 — завжди істина, тож це «крутитися вічно»
        int temp = read_temp();    // зчитати входи
        if (temp > LIMIT) {        // вирішити
            fan_on();              // подіяти
        } else {
            fan_off();
        }
    }
    // сюди виконання не доходить ніколи
}
```

Уся керувальна логіка пристрою живе всередині цього `while (1)`, і кожен оберт кола — це одне «сприйняти світ і відреагувати». `while (1)` (часом пишуть `for (;;)` — `for` без жодної з трьох частин, теж «вічно») — не помилка, а свідомий каркас. І зверніть увагу, як усе сьогоднішнє склалося докупи: суперцикл — це **повтор**, а всередині нього **розгалуження** розводить поведінку за станом входів. Дві прості цеглини — а виходить жива, безперервно чуйна до світу машина.

Ця форма — найпростіша з можливих, і в неї є природна межа: усе робиться по черзі, тож повільна дія затримує всі інші. Як тільки завдань стає багато й вони конкурують за час, суперцикл переростає або в керування за перериваннями, або в невеличку операційну систему реального часу. Але це вже наступні поверхи; фундамент під ними — усе той самий цикл із розвилками всередині.

Ми навчилися гнути пряму лінію виконання: **розгалуження** дає вибір, **цикл** дає повтор, а їхня спілка в суперциклі оживляє пристрій. Досі, щоправда, увесь код лежав однією купою в `main`. Далі ми навчимося різати його на іменовані шматки, які можна викликати звідусіль, — на [функції](guide:embedded/c-functions).
