# ⚙️ Готовий переносний Makefile для прошивки

Механіку ми вже розібрали: шаблонне правило `%.o: %.c`, авто-залежності через `-MMD -MP`, порядок лінкування бібліотек, фіктивні цілі `.PHONY`. Але між «розумію, як це працює» і «маю робочий файл, який заллє прошивку в чип» лежить прірва. Знати, що таке `-MMD`, і зібрати з десятка правильно поставлених дрібниць `Makefile`, який не розсиплеться на першому ж новому модулі, — різні вміння. Тут — саме той файл, цілий: копіюйте, підставте свій чип і теку — і воно збирається.

Мета цієї вставки — дати вам **артефакт**, а не ще один урок. Один повний `Makefile` для реальної прошивки під `arm-none-eabi-gcc`, у якому кожен рядок пояснено — навіщо він і що станеться, якщо його прибрати. Не навчальна іграшка на три файли, а той кістяк, з якого починають справжній проєкт: із власною текою `build/`, автоматичними залежностями від заголовків, правильним порядком бібліотек і цілями `flash`/`clean`. Далі — задача, ідея пристрою файлу, сам код і — найважливіше — місця, де при пристосуванні під себе ви найімовірніше спіткнетеся.

## Задача: один файл, з якого росте весь проєкт

Уявіть типовий початок. Плата на STM32 (сімейство Cortex-M4), кілька модулів — `main.c`, `led.c`, `uart.c`, `sensor.c`, — стартовий код і компонувальний скрипт від виробника. Треба зібрати образ `.elf`, з нього витягти «сирий» `.bin` для прошивальника, залити в чип і мати змогу все стерти й почати спочатку. І — головна вимога реального життя — щоб додавання нового модуля коштувало **один рядок**, а не правку п'яти місць.

Наївний `Makefile` з окремим правилом на кожен файл (як у самому кроці) цю вимогу провалює: кожен новий `.c` — нове правило, нова згадка в списку лінкування, нова ручна залежність від заголовків. Через місяць це болото, у якому хтось забуде дописати залежність — і почнуться примарні баги «змінив заголовок, а старий код лишився». Робочий `Makefile` будують так, щоб **список файлів був єдиним джерелом правди**, а все інше виводилося з нього автоматично.

## Ідея: список джерел → усе інше саме

Уся конструкція тримається на одній думці: ви пишете **тільки** перелік `.c`-файлів. З нього заміною суфікса виводиться перелік `.o` (кожен — у теці `build/`). Шаблонне правило перетворює будь-який `.c` на його `.o`, попутно наказуючи компіляторові виписати `.d`-файл зі списком включених заголовків. Ці `.d` затягуються назад у `Makefile` — і граф залежностей від заголовків будується сам, точний і повний. Правило образу лінкує весь список `.o` разом зі стандартними бібліотеками в правильному порядку. А `.PHONY`-цілі дають зручні дієслова: `make` (зібрати), `make flash` (залити), `make clean` (стерти).

Це рівно та драбина, яку ми проходили, зібрана в один файл. Далі — сам файл.

## Робочий Makefile

```make
# ── Makefile для прошивки під ARM Cortex-M (arm-none-eabi-gcc) ──
# Збирає всі .c у build/, лінкує в .elf, робить .bin і .hex, заливає.

# 1. Тулчейн: префікс і власне інструменти.
PREFIX  = arm-none-eabi-          # спільний початок імен усіх утиліт крос-тулчейну
CC      = $(PREFIX)gcc            # компілятор (він же кличе лінкер на кроці лінкування)
OBJCOPY = $(PREFIX)objcopy        # витягує сирий образ (.bin/.hex) з .elf
SIZE    = $(PREFIX)size           # показує, скільки зайняли .text/.data/.bss

# 2. Що збираємо і з чого — ЄДИНЕ джерело правди.
TARGET  = firmware               # базове ім'я образу (буде firmware.elf, .bin, .hex)
BUILD   = build                  # окрема тека для всього згенерованого
SRCS    = main.c led.c uart.c sensor.c startup_stm32f407.s
# кожен новий модуль додаєте САМЕ сюди — і більше ніде

# 3. Виводимо список об'єктних файлів із SRCS: замінюємо суфікс і кладемо в build/.
#    main.c → build/main.o, startup_stm32f407.s → build/startup_stm32f407.o
OBJS    = $(addprefix $(BUILD)/,$(patsubst %.c,%.o,$(patsubst %.s,%.o,$(SRCS))))

# 4. Прапорці збірки — усе, що стосується ЦЬОГО чипа, живе тут.
CPU     = -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16
CFLAGS  = $(CPU) -Os -g3 -Wall -Wextra -ffunction-sections -fdata-sections
CFLAGS += -MMD -MP                       # ← попутно генерувати .d із залежностями
CFLAGS += -DSTM32F407xx -Iinc            # макрос для HAL і тека із заголовками

# 5. Прапорці лінкування — компонувальний скрипт, бібліотеки, викидання зайвого.
LDSCRIPT = STM32F407VGTx_FLASH.ld        # карта пам'яті чипа (дає виробник)
LDFLAGS  = $(CPU) -T$(LDSCRIPT) --specs=nano.specs --specs=nosys.specs
LDFLAGS += -Wl,--gc-sections             # викинути невживані секції (economy флешу)
LDFLAGS += -Wl,-Map=$(BUILD)/$(TARGET).map   # карта пам'яті для розбору «що скільки з'їло»

# 6. Бібліотеки — СТРОГО в кінці команди лінкування (див. пастку нижче).
LDLIBS   = -lm                           # математична libm (sinf, sqrtf, …)

# ── Цілі ──────────────────────────────────────────────────────────

all: $(BUILD)/$(TARGET).bin $(BUILD)/$(TARGET).hex   # ← ціль за замовчуванням

# Лінкування: усі .o + бібліотеки → .elf. $^ підставить весь список OBJS.
$(BUILD)/$(TARGET).elf: $(OBJS)
	$(CC) $(LDFLAGS) $^ $(LDLIBS) -o $@
	$(SIZE) $@                            # одразу показати зайнятий обсяг

# Сирий двійковий образ для прошивальника (без ELF-обгортки).
$(BUILD)/$(TARGET).bin: $(BUILD)/$(TARGET).elf
	$(OBJCOPY) -O binary $< $@

# Intel HEX — інший формат образу, який їдять багато прошивальників.
$(BUILD)/$(TARGET).hex: $(BUILD)/$(TARGET).elf
	$(OBJCOPY) -O ihex $< $@

# Шаблон: будь-який build/X.o з X.c. | $(BUILD) — теку створити ПЕРШОЮ.
$(BUILD)/%.o: %.c | $(BUILD)
	$(CC) $(CFLAGS) -c $< -o $@

# Той самий шаблон для асемблера (стартовий код виробника — часто .s).
$(BUILD)/%.o: %.s | $(BUILD)
	$(CC) $(CFLAGS) -c $< -o $@

# Створити теку build/. Order-only (за |), тож її час не тягне перезбірку.
$(BUILD):
	mkdir -p $(BUILD)

flash: $(BUILD)/$(TARGET).elf            # залити образ у чип через st-flash/openocd
	st-flash write $(BUILD)/$(TARGET).bin 0x08000000

clean:                                    # стерти все згенероване одним махом
	rm -rf $(BUILD)

.PHONY: all flash clean                   # це дієслова, не файли — робити ЗАВЖДИ

# 7. Затягнути згенеровані залежності від заголовків. Дефіс = «нема .d — мовчи».
-include $(OBJS:.o=.d)
```

Це не скорочений навчальний уламок — це справді той файл, з якого можна стартувати проєкт на STM32. Заміните чотири речі (перелічу нижче) — і він збиратиме вашу плату.

## Читаємо блок за блоком

**Тулчейн (1).** Усі утиліти крос-компілятора мають спільний префікс `arm-none-eabi-`: `arm-none-eabi-gcc`, `-objcopy`, `-size`. Виносимо префікс у `PREFIX` — і зміна тулчейну (скажімо, на `riscv64-unknown-elf-` для RISC-V-мікроконтролера) стає правкою **одного рядка**. Чому саме `gcc`, а не `ld` напряму на лінкуванні? Бо `gcc` на кроці лінкування сам підставляє потрібні стартові об'єкти й правильно розуміє `--specs=...`; голий `ld` цього не вміє, і зібрати ним прошивку з newlib руками — окрема морока. Тому образ лінкуємо **компілятором**.

**Джерело правди (2–3).** `SRCS` — єдине місце, де ви перелічуєте файли. Рядок `OBJS` виводить із них список об'єктних файлів: `patsubst` міняє суфікс (`.c`→`.o`, `.s`→`.o`), `addprefix` дописує `build/`. Отже `sensor.c` автоматично стає `build/sensor.o`. Додали новий модуль у `SRCS` — його `.o` з'явився в графі сам, лінкування його підхопило, залежності від його заголовків згенерувалися. Одна правка замість п'яти — заради цього вся конструкція й затівалася.

**Прапорці компіляції (4).** Тут живе все, що стосується конкретного чипа. `-mcpu=cortex-m4 -mthumb` каже, під яке ядро й у якому наборі інструкцій компілювати; `-mfloat-abi=hard -mfpu=fpv4-sp-d16` вмикає апаратний блок плаваючої коми цього ядра (поставите софтовий ABI на чип із FPU — і втратите швидкодію дарма). `-Os` оптимізує за розміром (флеш тісний), `-g3` кладе повну зневаджувальну інформацію (у `.elf`, не в чип). Пара `-ffunction-sections -fdata-sections` кладе кожну функцію й змінну в окрему секцію — щоб на лінкуванні `--gc-sections` викинув усе невживане й образ схуд. І ключове для нашої теми — `-MMD -MP`: компілятор попутно виписує `.d`-файл зі списком реально включених заголовків. Саме він далі закриває проблему забутого заголовка.

> 🔧 **Навіщо це.** Рядок `-MMD -MP` — це страховка від найпідступнішого класу помилок збірки. Без нього ви мусили б руками писати «`main.o` залежить від `led.h`, `uart.h`, `config.h`» — і рано чи пізно забули б дописати новий заголовок. Тоді Make не помітив би його зміни й лишив застарілий `.o`: ви правите структуру в заголовку, а половина модулів досі бачить стару. Годину ловите привида, якого в коді немає. `-MMD -MP` віддає складання цього списку самому компіляторові — єдиному, хто точно знає, що куди включилося. [Препроцесор і заголовки](guide:embedded/c-preprocessor-headers) — про те, як `#include` фізично вклеює вміст заголовка, і чому саме тому зміна `.h` зобов'язує перекомпілювати всіх, хто його включив.

**Лінкування (5–6).** `-T$(LDSCRIPT)` дає лінкеру компонувальний скрипт — карту пам'яті чипа (де флеш, де RAM, куди що класти). Без нього лінкер не знає фізики вашого кристала й образ буде нікчемний. `--specs=nano.specs` підключає newlib-nano — урізану стандартну бібліотеку C, у рази меншу за повну (критично для флешу МК); `--specs=nosys.specs` підставляє заглушки системних викликів (`_write`, `_sbrk` тощо) для «голого заліза» без операційної системи — без них `printf` чи `malloc` дадуть `undefined reference` на системні функції, яких на bare-metal просто нема. `-Wl,--gc-sections` разом із `-ffunction-sections` вище викидає з образу невживаний код. `-Wl,-Map=...` пише карту — текстовий звіт, що куди лягло і скільки з'їло; безцінний, коли образ не влазить у флеш і треба знайти ненажеру.

**Порядок бібліотек (6).** `LDLIBS = -lm` стоїть окремо — і в команді лінкування підставляється **після** `$^` (після всіх ваших `.o`). Це не косметика, а сама механіка статичного лінкування. Лінкер читає аргументи зліва направо й тягне з бібліотеки лише те, на що на момент її читання **вже є відкрита дірка**. Ваш код кличе `sqrtf` — дірка з'являється, коли лінкер проходить ваші `.o`; отже `-lm` мусить стояти **після** них, інакше на момент `-lm` дірки ще нема, бібліотеку минають порожньою, а потім — `undefined reference to sqrtf`, хоч `#include <math.h>` на місці. Те саме з бібліотеками SDK виробника: спершу ваші `.o`, тоді `-l...` бібліотеки, у порядку «хто кого потребує». Детальний розбір цього порядку зі схемою — у самій детальній статті теми, тут важливо лише **де** `LDLIBS` стоїть у команді: у хвості.

**Цілі й образи.** Ціль `all` (перша в файлі, тож типова для голого `make`) просить `.bin` і `.hex`. Обидва роблять з `.elf` через `objcopy`: `-O binary` — сирий образ рівно тих байтів, що ляжуть у флеш (його їсть `st-flash`); `-O ihex` — текстовий Intel HEX, який приймають багато інших прошивальників. Сам `.elf` — це образ **плюс** метадані й символи для зневадника; у чип іде не він, а витягнутий з нього сирий вміст.

**Тека build/ через order-only (7 і правило `$(BUILD)`).** Придивіться до `| $(BUILD)` у шаблонних правилах — вертикальна риска робить теку **порядковою залежністю** (англ. *order-only prerequisite*). Це тонкість, без якої `build/`-підхід ламається. Теку треба створити **до** того, як у неї покласти перший `.o`. Але якщо зробити її звичайною залежністю, вилізе халепа: час зміни теки оновлюється щоразу, коли в ній щось з'являється чи зникає, — і Make вважав би всі `.o` застарілими після кожної збірки, перебудовуючи геть усе дарма. Order-only каже точно те, що треба: «спершу переконайся, що тека є, але її свіжість **не** роби приводом до перезбірки». Це офіційно рекомендований у документації GNU Make спосіб робити теку під вихідні файли — не костур, а канон.

**`-include` наприкінці.** Останній рядок `-include $(OBJS:.o=.d)` затягує всі згенеровані `.d`-файли (той самий `$(OBJS)`, лише з суфіксом `.d`). Кожен `.d` — це готове Make-правило зі списком заголовків, тож після цього рядка граф залежностей від заголовків повний і точний. Ведучий дефіс (`-include`, не `include`) каже «не лайся, якщо файлу ще нема» — а першого разу їх справді нема, вони народяться після першої компіляції; з другого запуску вони вже на місці. `-MP` (із `CFLAGS`) при цьому дописує в кожен `.d` порожнє фіктивне правило на кожен заголовок, щоб **видалення** заголовка не валило збірку з «нема правила зробити `old.h`».

## Складність і пастки

Файл виглядає спокійним, але при пристосуванні під себе тут кілька місць, де новачок неминуче обпечеться. Пройдімося по них — це рівно ті граблі, на які натрапляє кожен.

**Таб, не пробіли.** Найперша й найтупіша. Кожен рядок команди **під** правилом відступлено символом табуляції, а не пробілами. Скопіюєте цей файл через редактор, що мовчки заміняє таби на пробіли, — і Make впаде з загадковим `missing separator`. Виглядає ідентично, ламається насмерть. Якщо збірка падає з цим повідомленням — перше, що перевіряйте, це чи справді там таб. (Чому взагалі таб, а не будь-що інше, — окрема майже анекдотична історія, винесена в [історію Make і CMake](guide:embedded/c-modules-build/hist-make-cmake.md).)

**Порядок бібліотек — знову.** Повторю, бо це помилка №1 у прошивкових `Makefile`. Додаєте бібліотеку SDK (скажімо, HAL-драйвери зібрані в `libstm32.a`) — куди її в `LDLIBS`? За принципом «хто кого потребує»: ваш код потребує HAL, HAL потребує `libm`, отже порядок `... $^ -lstm32 -lm` — потрібне стоїть праворуч від того, хто його просить. Якщо дві бібліотеки потребують одна одну взаємно (кільцева залежність), лінкер за один прохід не впорається — тоді їх загортають у `-Wl,--start-group ... -Wl,--end-group`, і лінкер крутить їх, доки не закриє всі дірки. Побачили `undefined reference` на функцію з бібліотеки, хоч заголовок включено, — на дев'ять із десяти це порядок, а не відсутність файлу.

**Чотири речі, які треба замінити під свою плату.** Цей файл — під STM32F407, і щоб перевести його на інший чип, змінюють рівно чотири місця: (1) `CPU` — під ядро вашого кристала (`cortex-m0`, `cortex-m7`, з FPU чи без); (2) `LDSCRIPT` — компонувальний скрипт вашого чипа (дає виробник у своєму SDK); (3) макрос `-D...` і `-Iinc` — під заголовки й визначення вашого HAL; (4) команду в `flash` — під ваш прошивальник (`st-flash`, `openocd`, `pyocd`). Стартовий `.s`-файл у `SRCS` теж міняється на відповідний вашому чипу. Усе інше — механіка Make — лишається як є. Саме тому цей кістяк переносний: специфіка чипа зібрана в кількох рядках зверху, а не розмазана файлом.

**FPU-ABI мусить збігатися всюди.** Тонка й болюча пастка. Прапорці `-mfloat-abi` та `-mfpu` мають бути **однакові** і при компіляції (`CFLAGS`), і при лінкуванні (`LDFLAGS`), і — головне — збігатися з тим, як зібрані бібліотеки, які ви лінкуєте (та сама newlib). Тому `CPU` і винесено в спільну змінну, що йде в обидва набори прапорців. Змішаєте hard-float ваш код із soft-float бібліотекою — лінкер видасть щось на кшталт «uses VFP register arguments, output does not», і це не попередження, а стіна. Одна змінна `CPU` в обох місцях знімає питання.

**`clean` мусить бути `.PHONY`.** Уявіть, що хтось випадково створив у корені файл із назвою `clean`. Без рядка `.PHONY` Make побачив би цей файл, вирішив, що ціль `clean` «вже зроблена й свіжа», і `make clean` **нічого б не стер**. Оголошення `clean` фіктивною каже Make: це дієслово, а не файл, виконуй його команду завжди, ні з чим не звіряючи. Те саме — для `all` і `flash`. Забути `.PHONY` — класична причина «чому `make clean` іноді не працює».

**`build/` не потрапляє в систему контролю версій.** Дрібниця з гігієни: усе згенероване лежить в одній теці `build/`, тож у `.gitignore` досить одного рядка `build/`. Тримати похідні артефакти поряд із кодом — засмічувати репозиторій і плутати, де джерело, а де продукт; викинути `build/` і зібрати заново — завжди чистий, відтворюваний стан.

Ось і весь файл. Він свідомо мінімальний — без рекурсивних під-`Makefile`, без хитрих функцій, — щоб його можна було прочитати очима згори донизу й зрозуміти цілком. Це саме той рівень, з якого варто починати: достатньо повний, щоб зібрати справжню прошивку, і достатньо простий, щоб ви тримали в голові кожен його рядок. А коли проєкт виросте настільки, що навіть цього замало, ви вже знатимете, куди дивитися далі — бо розумітимете не рецепт, а механіку, з якої він зроблений. І щойно образ зібрано й `make flash` його залив — далі починається робота з живою платою: [esptool: прошивання й читання Flash](guide:embedded/esptool-workflow) показує ту саму «заливку», але з боку конкретного інструмента й конкретного чипа.
