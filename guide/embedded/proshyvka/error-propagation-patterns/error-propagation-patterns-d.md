# Патерни поширення помилок

Коли ми обирали, [як донести збій до того, хто його обробить](guide:embedded/error-codes-vs-exceptions), висновок для прошивки був однозначний: коди повернення. Передбачуваний час, малий код, помилка видима прямо в типі. Але та сама розмова чесно назвала і ціну цього вибору: код повернення доводиться **нести нагору руками, рамка за рамкою**, а щасливий шлях тоне у перевірках. Ми навіть бачили живий приклад біди — `nvs_close(h)`, який доводилося кликати **двічі**, бо ресурс треба звільнити і на щасливому шляху, і окремо в гілці помилки; забудеш одне закриття — і дескриптор тече.

Отже, коди ми вибрали — але «носити руками» не означає «носити абияк». За десятиліття на C склався невеликий набір **патернів поширення** (від латин. *patronus* — взірець; тут: усталена форма коду під типову задачу), що перетворюють цю ручну роботу на чисту, передбачувану й таку, що сама не дає помилці впасти. Ця стаття — про них. Не про новий механізм замість кодів, а про **дисципліну**, з якою коди застосовують, щоб ручне перенесення помилки нагору перестало бути джерелом бруду й витоків.

Розберемо чотири речі по черзі, бо кожна виростає з попередньої: як зробити тіло функції пласким (сторожі), як не загубити слід помилки дорогою нагору (контекст), як гарантовано прибрати ресурси за будь-якого виходу (сходи cleanup) і як на кожному щаблі вирішити долю помилки (провести, обробити чи проковтнути).

## Сторожі: зрізаємо піраміду

Найперше, що псує код помилок, — **вкладеність**. Інтуїтивна реакція новачка: «зробимо корисну дію, якщо все добре». Виходить ланцюг вкладених `if`, де кожна вдала перевірка додає рівень, а сама робота заривається все глибше праворуч-униз:

```c
esp_err_t read_sample(int16_t *out) {
    if (sensor_wake() == ESP_OK) {
        if (sensor_trigger() == ESP_OK) {
            if (sensor_fetch(out) == ESP_OK) {
                return ESP_OK;          // корисна дія — аж тут, найглибше
            }
        }
    }
    return ESP_FAIL;                     // а яка саме з трьох помилок? втрачено
}
```

Тут дві біди. Перша — **форма**: око мусить пройти три рівні відступу, щоб дістатися суті, а додай по `else` до кожного `if` — і код розповзеться сходами вниз (англ. *pyramid of doom*, «піраміда приреченості»). Друга, гірша, — **зміст**: усі три різні причини збою злилися в один безликий `ESP_FAIL`, тож той, хто кликав `read_sample`, уже не дізнається, що саме сталося — давач не прокинувся, не запустив вимір чи не віддав дані.

Лік — **сторож** (англ. *guard clause*, «застережна умова»; термін поширив Кент Бек, а до каталогу рефакторингу вписав Мартін Фаулер у прийомі «Replace Nested Conditional with Guard Clauses»). Ідея перевертає логіку: замість «зробити дію, якщо успіх» пишемо «**вийти одразу, якщо невдача**». Кожна перевірка стає коротким бар'єром на початку, що випускає негодящий випадок геть, а нижче лишається сам щасливий шлях — плаский, на одному рівні відступу:

```c
esp_err_t read_sample(int16_t *out) {
    esp_err_t err = sensor_wake();
    if (err != ESP_OK) return err;      // не прокинувся — назад із точною причиною

    err = sensor_trigger();
    if (err != ESP_OK) return err;      // не запустив вимір — назад

    return sensor_fetch(out);           // дійшли сюди — лишилась тільки корисна дія
}
```

Логіка та сама, але форма й зміст вилікувані разом. Вкладеності нема — кожна перевірка пласка; причина збою збережена — ми повертаємо **те саме** `err`, що повернув давач, а не стираємо його в `ESP_FAIL`. Щасливий шлях читається згори вниз як проста розповідь: «розбуди, запусти, забери». Це і є перший патерн: **рання перевірка на невдачу, ранній вихід**.

![Та сама логіка двома формами: ліворуч вкладені if-перевірки успіху женуть корисну дію все глибше праворуч, праворуч сторожі виходять на невдачі й лишають щасливий шлях пласким](/guide/embedded/proshyvka/error-propagation-patterns/img/pyramid-vs-flat.svg)

*Одна функція двома способами. Ліворуч перевіряємо успіх — кожна вдала умова додає рівень вкладеності, корисна дія тоне найглибше праворуч, а гілки `else` сповзали б ще нижче. Праворуч перевіряємо невдачу й виходимо одразу — щасливий шлях лишається на лівому, рівному рівні, читається як список кроків. Сторожі зрізають піраміду й заразом зберігають точну причину збою.*

> 🔧 **Навіщо це.** На мікроконтролері функція-драйвер — це майже завжди ланцюг «налаштуй регістр → дай команду → дочекайся → прочитай результат», де кожен крок може провалитися. Без сторожів такий драйвер за три-чотири кроки перетворюється на нечитну піраміду, у якій легко загубити перевірку. Зі сторожами тіло будь-якого драйвера має один і той самий упізнаваний вигляд: смуга коротких бар'єрів зверху, корисна дія знизу. Це не косметика — це те, що дає змогу за секунду побачити, чи **всі** кроки перевірено, чи якийсь прослизнув без `if`.

## Не глуши помилку дорогою: контекст

Сторожі зробили тіло пласким, але оголили нову проблему. Помилка від `sensor_fetch` піднімається через `read_sample`, та віддає її своєму викликачеві, той — ще вище, аж до місця, де хтось нарешті вирішить, що з нею робити. На кожному щаблі це той самий голий числовий код. І коли він нарешті спливе нагору — наприклад, у головний цикл — там буде відомо лише *що* сталося (`ESP_ERR_TIMEOUT`), але вже **не відомо, де саме**. Помилка зародилася на дні стека, а обробляється на вершині, і весь шлях між ними німий.

Це окрема, дуже типова вада ручного поширення: **код помилки несе значення, але не несе сліду**. На хості цей слід дає виняток, тягнучи зі собою стек викликів. У світі кодів повернення слід доводиться лишати самотужки — **записати в лог саме там, де збій стався**, поки контекст ще під рукою.

Наївна спроба робити це руками знову роздуває код: до кожного сторожа доводиться чіпляти рядок логування.

```c
err = sensor_trigger();
if (err != ESP_OK) {
    ESP_LOGE(TAG, "sensor_trigger failed: %s", esp_err_to_name(err));
    return err;                         // правильно, але по три рядки на кожен крок
}
```

Працює, але це знову багатослів'я, від якого ми тікали: пласко, та довго, і легко десь забути лог. Тому ESP-IDF дає на цей самий патерн готовий **макрос-помічник** — `ESP_RETURN_ON_ERROR`. Він робить рівно те, що ми писали руками: перевіряє код, і якщо це не `ESP_OK` — друкує повідомлення (з тегом, ім'ям файла, функції та номером рядка, де стався збій) і повертає цей код нагору.

```c
#include "esp_check.h"
static const char *TAG = "sensor";

esp_err_t read_sample(int16_t *out) {
    ESP_RETURN_ON_ERROR(sensor_wake(),       TAG, "wake");
    ESP_RETURN_ON_ERROR(sensor_trigger(),    TAG, "trigger");
    ESP_RETURN_ON_ERROR(sensor_fetch(out),   TAG, "fetch");
    return ESP_OK;
}
```

Це той самий сторож-патерн, стиснутий до одного рядка на крок — але тепер кожна невдача дорогою нагору лишає в лозі точну позначку, де вона народилася. Коли в полі прилетить аварія, лог покаже не безликий тайм-аут на вершині стека, а рядок `sensor: trigger` із номером рядка у файлі давача. Поряд живе `ESP_RETURN_ON_FALSE(cond, err_code, TAG, msg)` — для перевірки не коду, а **умови** (наприклад, аргументів на вході: `ESP_RETURN_ON_FALSE(out != NULL, ESP_ERR_INVALID_ARG, TAG, "out is null")`).

> 🔧 **Навіщо це.** Різниця між «німим» і «промовистим» поширенням — це різниця між годинами й хвилинами налагодження в полі. Голий `return err` дає на вершині лише номер помилки без адреси; `ESP_RETURN_ON_ERROR` лишає слід у кожній рамці, тож [посмертний лог](guide:embedded/core-dump) сам показує ланцюг до першопричини. Платити за це нема чим: на щасливому шляху макрос — це те саме порівняння з нулем, а рядки логів можна геть прибрати з прошивки одним прапорцем (`CONFIG_COMPILER_OPTIMIZATION_CHECKS_SILENT`), коли релізу зайвий і байт Flash. Тобто промовистість безкоштовна на щасливому шляху й вимикається, коли треба.

## Сходи cleanup: один вихід для всіх збоїв

Лишилася та сама біда, з якої ми починали, — **ресурси**. Сторож елегантно вискакує з функції на першій невдачі. Але якщо до тієї невдачі ми вже **щось захопили** — відкрили порт, виділили буфер, відкрили файл, — то простий `return err` покине функцію, **не звільнивши захоплене**. Саме тут народжувався подвійний `nvs_close` зі вступу: щоб не текло, доводилося повторювати звільнення в кожній гілці виходу.

Подивімося, як ця біда росте з кількістю ресурсів. Два ресурси — і код звільнення вже двоїться, троїться:

```c
esp_err_t process(void) {
    port_t *p = port_open();
    if (p == NULL) return ESP_FAIL;

    uint8_t *buf = malloc(1024);
    if (buf == NULL) {
        port_close(p);                  // звільнити те, що вже взяли
        return ESP_ERR_NO_MEM;
    }

    esp_err_t err = port_read(p, buf, 1024);
    if (err != ESP_OK) {
        free(buf);                      // і знову...
        port_close(p);                  // ...повторюємо звільнення
        return err;
    }

    free(buf);                          // і на щасливому шляху теж
    port_close(p);
    return ESP_OK;
}
```

Звільнення повторюється на кожному виході, і з кожним новим ресурсом це повторення росте квадратично. Це не просто негарно — це **розсадник витоків**: вистачить додати четвертий вихід і забути в ньому одне `free`, і пам'ять тектиме лише на тій рідкісній гілці, якої ніхто не тестував.

C дає на це класичний лік — **єдину точку виходу з прибиранням**, патерн, відомий як `goto cleanup` (також «cleanup pattern» чи, у ядрі Linux, «centralized exiting of functions»). Логіка проста: жодна гілка помилки не звільняє нічого сама. Замість цього кожна **стрибає до однієї спільної мітки** наприкінці функції, де звільнення зібране в одному місці — і виконується **у зворотному до захоплення порядку**:

```c
esp_err_t process(void) {
    esp_err_t ret = ESP_OK;
    uint8_t  *buf = NULL;

    port_t *p = port_open();
    if (p == NULL) return ESP_FAIL;     // ще нічого не взяли — звичайний return

    buf = malloc(1024);
    if (buf == NULL) { ret = ESP_ERR_NO_MEM; goto cleanup; }

    ret = port_read(p, buf, 1024);
    if (ret != ESP_OK) goto cleanup;    // збій — туди ж, де й усі

    // ... тут далі робота з buf і p ...

cleanup:
    free(buf);                          // звільнення — РІВНО ОДИН раз
    port_close(p);                      // у зворотному порядку до взяття
    return ret;
}
```

Тепер `free(buf)` і `port_close(p)` написані **по одному разу**, хоч скільки гілок виходу. Додаєш п'ятий ресурс — дописуєш одне звільнення в `cleanup`, і всі шляхи виходу одразу його врахували. Це і є відповідь C на ту саму [ідіому RAII](guide:embedded/error-codes-vs-exceptions/detail), якою в C++ хвалилися винятки: там деструктор звільняє ресурс автоматично на будь-якому виході, тут ту саму гарантію «звільнити за всіма шляхами» ми будуємо руками через спільну мітку.

Чому **зворотний порядок**? Бо ресурси часто залежать один від одного: буфер міг бути виділений уже після відкриття порту й під нього, файл — під уже наявне з'єднання. Звільняти треба в порядку, протилежному до взяття, — спершу те, що взяли останнім, — інакше ризикуєш закрити те, на що ще спирається незвільнене. Та сама логіка, що зі стосом тарілок: знімаєш згори.

![Сходи cleanup: ліворуч ресурси захоплюються згори вниз по черзі, посередині мітка cleanup, до якої дашем збігаються всі гілки невдачі, праворуч звільнення йде знизу вгору у зворотному порядку](/guide/embedded/proshyvka/error-propagation-patterns/img/cleanup-ladder.svg)

*Як працює спільний вихід. Ліворуч ресурси беруться по черзі — порт, буфер, файл. Будь-яка невдача (пунктир) стрибає до однієї мітки `cleanup`. Звільнення (праворуч) виконується у зворотному порядку — останнє взяте звільняється першим — і тільки для того, що встигли взяти, бо незахоплені вказівники лишилися нульовими, а `free(NULL)` і перевірка перед закриттям безпечні. Один вихід, нуль дубльованого коду звільнення.*

Цей патерн настільки типовий, що ESP-IDF дає під нього свій макрос — `ESP_GOTO_ON_ERROR(x, goto_tag, TAG, msg)`. Він поєднує сторожа, логування й стрибок: перевіряє код, і якщо збій — друкує промовисте повідомлення, кладе код у локальну змінну `ret` і стрибає на мітку `goto_tag`. Він **вимагає** в функції рівно тих двох речей, які ми завели вручну: змінної `ret` і мітки наприкінці. Повне розгортання цих макросів, чому `goto` тут — добра практика всупереч славнозвісному «goto considered harmful», і робочий приклад на чотирьох взаємозалежних ресурсах винесено в окремий розбір — [сходи cleanup і макроси ESP-IDF у живому коді](guide:embedded/error-propagation-patterns/proj-cleanup-pattern.md).

> 🔧 **Навіщо це.** На пристрої ресурс, що протік, рідко вбиває програму одразу — він з'їдає її повільно. Незакритий дескриптор файла, невіддана пам'ять, незвільнена шина: один-два витоки на рідкісній гілці помилки, і прошивка, що мала працювати тижнями, падає на третю добу з вичерпаною купою — і саме тоді, коли пристрій уже в полі, а не на столі. `goto cleanup` робить **неможливим** забути звільнення на якомусь із виходів, бо вихід **один**. Це чи не найважливіший патерн поширення для довготривкої прошивки: він прибирає за помилкою так само надійно, як і за успіхом.

## Доля помилки в кожній рамці: провести, обробити, проковтнути

Досі ми мовчки робили одне й те саме: будь-яку помилку **проводили нагору**. Це правильний типовий вибір, але не єдиний. Коли помилка дійшла до твоєї функції, є рівно три чесні відповіді, і вибір між ними — окреме рішення на **кожному** щаблі стека.

**Провести далі** (`return err` / `goto cleanup`) — відповідь за замовчуванням. Сенс її простий і чесний: «мені тут не зарадити; той, хто кликав мене, знає більше про контекст — нехай вирішує він». Драйвер давача не знає, чи тайм-аут шини — це привід повторити вимір, узяти старе значення чи зупинити апарат; це знає логіка вище. Тож драйвер просто чесно віддає помилку нагору й не вдає, ніби розуміє, що з нею робити.

**Обробити тут** — відповідь для рівня, де **справді є чим зарадити**. Це місце, де ланцюг поширення нарешті уривається, бо знайшовся той, хто має запасний план: повторити операцію кілька разів, підставити значення за замовчуванням, перемкнутися на резервний давач, перейти в безпечний режим. Обробка — це не «зловити й знову мовчки кинути», а **дати збоєві осмислену відповідь**. Зазвичай вона живе високо — у завданні-обгортці чи головному циклі, — бо саме там видно всю картину.

**Проковтнути** — найнебезпечніша відповідь, і користуватися нею треба рідко та свідомо. Проковтнути означає отримати помилку й **не зробити з нею нічого** — ні передати, ні обробити. Це майже завжди вада, бо так збій зникає безслідно. Але кілька законних випадків є, і майже всі вони — на **шляху прибирання**. У `cleanup` вище, якщо саме `port_close(p)` теж поверне помилку, реагувати на неї зазвичай нема як: ми вже виходимо з функції через попередній збій, нову помилку нема куди вести, та й нема що з нею робити. Тоді її свідомо ігнорують — але **з коментарем**, що пояснює, чому це безпечно. Різниця між законним ковтанням і вадою — рівно в цьому: законне завжди супроводжене явним рішенням і приміткою, а не мовчазним пропуском, який легко сплутати з недоглядом.

```c
cleanup:
    free(buf);
    // помилку закриття на шляху виходу свідомо ігноруємо:
    // ми вже повертаємо попередній ret, вести нову помилку нікуди
    (void) port_close(p);
    return ret;
```

![Три відповіді на помилку, що прийшла в цю функцію: провести нагору (типовий вибір), обробити тут (де є запасний план) чи свідомо проковтнути з приміткою (рідко, на шляху прибирання)](/guide/embedded/proshyvka/error-propagation-patterns/img/frame-choice.svg)

*Коли помилка дійшла до функції, чесних відповідей рівно три. Провести нагору — типове рішення: тут нема контексту, щоб зарадити. Обробити — там, де є запасний план (ретрай, значення за замовчуванням, резерв). Проковтнути — лише свідомо, з коментарем і майже завжди на шляху прибирання; мовчазне ковтання без примітки — це не четвертий варіант, а вада.*

> 🔧 **Навіщо це.** Найпідступніші помилки в прошивці — не ті, що валять програму, а ті, що **зникають мовчки**: десь проковтнутий код перетворює реальний збій давача на тихе старе значення, і апарат летить за хибними даними, ніби все гаразд. Свідоме рішення на кожній рамці — провести, обробити чи (рідко й з приміткою) проковтнути — це і є практичне втілення правила [«жодна помилка не мовчить»](book:programming/error-handling): помилка або їде до того, хто зарадить, або тут-таки отримує відповідь, або її ігнорування **записане як обдумане рішення**, а не лишене на випадок.

## Переклад на межі шарів

Останній патерн стосується великих систем, де код розкладено на шари: драйвери внизу, прикладна логіка зверху. Помилки з нижнього шару несуть його, нижній, словник: `ESP_ERR_TIMEOUT`, `ESP_ERR_INVALID_CRC`, коди конкретної шини. Якщо пропускати їх просто наскрізь до самого верху, прикладний рівень опиниться **прив'язаним до деталей** того, як саме реалізовано низ. Заміниш давач I²C на SPI — і помилки на вершині зміняться, хоч прикладна логіка та сама.

Тому на **межі шару** помилку часто варто не просто провести, а **перекласти** — згорнути дрібні низькорівневі коди в один осмислений код свого рівня. Драйвер усередині розрізняє десяток причин, чому не вдалося прочитати давач, але назовні, прикладному коду, віддає одне зрозуміле йому поняття — скажімо, «давач недоступний», — лишивши подробицю лежати в лозі (саме для цього ми й лишали слід макросами):

```c
// межа шару давача: усередині — деталі шини, назовні — одне поняття
esp_err_t sensor_read(int16_t *out) {
    esp_err_t err = bus_transfer(...);          // низ говорить мовою шини
    if (err == ESP_ERR_TIMEOUT ||
        err == ESP_ERR_INVALID_CRC) {
        ESP_LOGW(TAG, "bus error %s", esp_err_to_name(err));  // подробиця — у лог
        return ESP_ERR_SENSOR_OFFLINE;          // нагору — одне поняття шару
    }
    return err;
}
```

Тут спрацьовують усі попередні патерни разом: сторож ловить негодящі коди, лог лишає точну причину для налагодження, а нагору йде стабільне, незалежне від шини поняття. Прикладний рівень тепер бачить «давач офлайн» і вирішує, що робити, **не знаючи й не дбаючи**, на якій шині той давач сидить.

> 🔧 **Навіщо це.** Переклад на межі — це те, що дає змогу **міняти залізо, не переписуючи логіку**. Поки прикладний код реагує на «давач офлайн», а не на конкретний код шини, ти вільний перевести давач з I²C на SPI, додати повторну спробу всередині драйвера чи геть змінити мікросхему — верх не помітить. Без цього перекладу низькорівневі коди розповзаються по всій програмі, і кожна заміна компонента тягне правки в десятках місць. Шар, що віддає назовні свій власний словник помилок, — це шар, який можна замінити цілком.

## Як це збирається докупи

Чотири патерни — це не окремі прийоми, а один спосіб мислення, нанизаний на просте питання: **як зробити, щоб жоден збій не їхав далі ні непоміченим, ні безслідним, ні з протіканням за собою**. Сторож робить тіло пласким і зберігає точну причину. Промовисте повернення лишає слід там, де збій народився. Сходи cleanup гарантують, що за помилкою приберуть так само, як за успіхом. Свідоме рішення в кожній рамці не дає помилці мовчки зникнути. А переклад на межі тримає шари незалежними. Разом вони перетворюють «носити помилку руками» з джерела бруду на надійний, упізнаваний з першого погляду каркас.

І це лише одна вісь питання. Патерни поширення кажуть, **як** провести збій чисто; окреме рішення — на якому **рівні гучності** взагалі реагувати: тихо повернути код, гучно зупинитися [assert'ом чи панікою](book:programming/assert-panic), коли працювати далі небезпечно, чи перевірити припущення наперед [захисним програмуванням](book:programming/defensive-programming), щоб збій не стався взагалі. Поширення й гучність — дві сторони одного ремесла: зробити так, щоб у прошивці, яка живе місяцями без нагляду, жодна помилка не загубилась дорогою до того, хто здатен дати їй раду.
