# ⚙️ Програмування гама-таблиці при старті панелі

Контролер дисплея має апаратну **гама-таблицю** — вузол, що набором регістрів задає криву «код → яскравість» панелі (як він улаштований усередині — резисторна драбина, дві полярності, карта регістрів, різновиди — розібрано у вставці [Гама-таблиця в контролері дисплея](guide:embedded/color-management/api-gamma-table.md)). Тут — інша половина справи: **як** цю таблицю реально залити в контролер під час ініціалізації, у якому місці послідовности й чому саме там, як побачити результат на **сірій шкалі** і які помилки псують картинку. Бо навіть правильні значення з даташита, залиті не туди чи не активовані, дадуть не ту криву, — а найпідступніші з тутешніх пасток виявляються не на столі, а через тиждень роботи виробу.

---

### Як її «підключають»: програмування в init-послідовності

Тепер найпрактичніше — де й як цей вузол чіпають. Гама-таблиця — це **частина ініціалізації контролера**, той самий клас дій, що й «вийти зі сну», «задати формат пікселя RGB565», «увімкнути дисплей». Її заливають **один раз при старті**, у складі ініт-послідовности, і далі зазвичай не торкаються. Послідовність загалом має чіткий порядок (живлення → сон геть → формат → гама → дисплей увімкнути), і місце гами в ньому **не випадкове**: її ставлять після налаштування живлення панелі (бо опорні напруги драбини залежать від нього), але до того, як показати першу картинку, — щоб найперший же кадр ліг уже з правильною кривою.

Виглядає це як низка команд тим самим способом, яким ви шлете будь-яку команду контролеру: байт-команда «починаю гама-регістри» (DC=0), за нею потік байтів-параметрів (DC=1) — увесь набір зломів однієї полярности. Потім друга команда — другий набір. Покажемо на типовому класі ILI9341/ST7789, але суть ідентична для будь-якого контролера з програмованою гамою.

**Заливання обох гама-таблиць у складі ініт-послідовности**

```c
/* lcd_cmd(cmd, data, len): шле байт-команду (DC=0), потім len байтів
   параметрів (DC=1) — той самий помічник, що й для решти ініту.    */

/* (опційно) вибір базової кривої / увімкнення правленої гами.
   Значення 0x01 = крива «G2.2» — типовий старт.                    */
static const uint8_t gamma_set[] = { 0x01 };
lcd_cmd(0x26, gamma_set, 1);                 /* Gamma Set            */

/* Позитивна гама — 15 зломів (значення з даташита ПАНЕЛІ, не з неба) */
static const uint8_t gmctrp1[] = {
    0x0F, 0x31, 0x2B, 0x0C, 0x0E, 0x08, 0x4E, 0xF1,
    0x37, 0x07, 0x10, 0x03, 0x0E, 0x09, 0x00
};
lcd_cmd(0xE0, gmctrp1, sizeof(gmctrp1));     /* Positive Gamma       */

/* Негативна гама — дзеркальний, але ОКРЕМИЙ набір (проти мерехтіння) */
static const uint8_t gmctrn1[] = {
    0x00, 0x0E, 0x14, 0x03, 0x11, 0x07, 0x31, 0xC1,
    0x48, 0x08, 0x0F, 0x0C, 0x31, 0x36, 0x0F
};
lcd_cmd(0xE1, gmctrn1, sizeof(gmctrn1));     /* Negative Gamma       */
```

Зверніть увагу на дві речі. Перша — наборів справді **два** і вони **різні** (порівняйте байти: це не копія). Друга — ці магічні байти **не вигадані й не універсальні**: їх дає **виробник панелі** у своєму рекомендованому ініт-листі під своє конкретне скло. Тому в реальному проєкті їх не підбирають з голови, а **беруть із даташита чи прикладу від виробника модуля** — як готову константу. Це класичний випадок «магічних чисел ініту»: ви не мусите розуміти кожен байт, але мусите взяти правильний набір і залити його в правильному місці.

> 🔧 **Навіщо це.** У 95% проєктів робота з гама-таблицею зводиться рівно до цього: **скопіювати рекомендований виробником набір у свою ініт-послідовність і не чіпати**. Самостійно крутити ці байти треба лише тоді, коли ви свідомо калібруєте панель (приладова точність кольору) або женете навмисний ефект — наприклад, «розтягуєте» тіні для кращої видимости в темряві. Для звичайного виробу: взяли набір з даташита, залили після налаштування живлення, активували — забули.

### Перший байт: з чого почати на новій панелі

Що зробити першим, коли перед вами нова панель і питання кольору? Не лізти в гама-байти. **Спершу залийте рекомендований виробником повний ініт** — з його гама-набором включно — і подивіться на реальну картинку: градієнт від чорного до білого й кілька еталонних кольорів. У дев'яти випадках з десяти цього досить: виробник уже підібрав гаму під своє скло, і нічого правити не треба.

Лізти в самі регістри варто **лише якщо ви бачите конкретну ваду** й розумієте, що це гама, а не щось інше. Найперший діагностичний крок — **сіра шкала**: виведіть смугу рівними кроками коду від 0 до 255 і дивіться, чи рівно зростає яскравість.

```c
/* Діагностична сіра шкала: рівні кроки КОДУ по горизонталі.
   Якщо панель калібрована — яскравість росте візуально рівно;
   якщо тіні «злипаються» в чорне або світла вибілені — крива крива. */
void draw_gray_ramp(int x, int y, int w, int h) {
    for (int i = 0; i < w; i++) {
        uint8_t g = (uint8_t)(i * 255 / (w - 1));   /* 0..255 рівномірно */
        uint16_t c = ((g & 0xF8) << 8) |            /* R (5 біт) RGB565  */
                     ((g & 0xFC) << 3) |            /* G (6 біт)         */
                     (g >> 3);                       /* B (5 біт)         */
        fill_rect(x + i, y, 1, h, c);
    }
}
```

Читати результат просто. Якщо **тіні злипаються** в суцільне чорне (нижні коди не розрізнити) — крива в тінях задавлена. Якщо **світла вибілені** в суцільне біле (верхні коди злилися) — задавлені світла. Якщо сірий **поплив у колір** (наприклад, до синього у світлах) — три канали мають різні криві, дисбаланс. І лише побачивши *конкретно* це, ви знаєте, який кінець гама-набору рухати. Без сірої шкали правка гами — це гра наосліп, де кожен дотик до байта псує криву в непередбачуваний бік.

### Типові граблі класу

- **Порядок у послідовності.** Гаму залили **раніше**, ніж налаштували живлення панелі (опорні напруги драбини), — і вона лягла на ще не готові опорні рівні: крива виходить не та, що в даташиті. Гама-команди ставлять **після** блоку живлення й **до** ввімкнення дисплея. Місце в ініт-листі — не косметика, а вимога.

- **Забули активувати.** Записали 15 байтів, але не виставили біт «використовувати правлену гаму» (чи не послали команду вибору набору) — контролер далі крутить **зашиту заводську** криву, ваші значення лежать мертвим вантажем. Перевірте: чи є в послідовності команда-вмикач і чи стоїть вона.

- **Позитивну скопіювали в негативну.** Вирішили, що два однакових набори — марнотратство, і залили той самий байт-у-байт в обидві полярности. Результат — **мерехтіння** (flicker): піксель ледь пульсує в такт інверсії полярности. Два набори тому й окремі, що скло несиметричне; беріть **обидва** з даташита.

- **Перезапис при reset.** Дисплей зробив апаратний reset (зник і повернувся живлення, спрацював сторожовий таймер, смикнули лінію RST) — і **вся ваша гама злетіла** до заводської, бо контролер повернувся в стан за замовчуванням. Це найпідступніша пастка: працювало, після ребуту «кольори попливли». Лік — гаму (як і весь ініт) **заливати наново після кожного reset панелі**, а не лише раз на старті прошивки. Це частина дисципліни [життєвого циклу дисплея](guide:embedded/display-lifecycle): стан контролера летючий, його треба відновлювати.

- **Подвійна корекція.** Найтонша й найковарніша. Ви налаштували гаму **в контролері** (крива панелі → 2.2) — і **заразом** проганяєте кольори через гама-таблицю **у своєму коді**, думаючи, що так «точніше». Дві корекції накладаються — крива зводиться в квадрат, картинка летить у різкий контраст або вибілюється. Гама в системі застосовується **рівно один раз**: або панель декодує сама (тоді ви шлете гама-кодовані коди й нічого не чіпаєте), або ви свідомо перебираєте перетворення на себе (рідко). Двічі — ніколи. Це той самий клас помилки, що й [змішування напівпрозорих кольорів у кодах замість лінійного світла](guide:embedded/color-management): гама має спрацювати один раз, не двічі й не жодного.

- **Крутили байти без сірої шкали.** Правили гама-значення «на око» по реальному кадру (фото, інтерфейс) — і ганялися за хвостом, бо на строкатій картинці не видно, який саме кінець кривої винен. Спершу **сіра шкала**, вона ізолює ваду; правка — лише потім.
