# ⚙️ Блокове зіставлення: код, що робить карту глибини

У самій темі ми дійшли до головного: вся арифметика `Z = f·b/d` вмикається лише тоді, коли для точки лівого кадру знайдено її **пару** на правому. Сказати «ковзаємо віконцем по рядку й шукаємо найсхожіше місце» легко. А тепер сядьмо й **напишемо це** так, щоб воно крутилося на мікроконтролері й видавало карту, якій можна вірити. Бо між однорядковим описом і робочим кодом лежить десяток інженерних дрібниць, кожна з яких тихо перетворює карту глибини на красивий, але брехливий шум.

Домовмося про вхід. Камери вже **вирівняні** (ректифіковані) — це зробив попередній крок конвеєра, тож пара будь-якої точки лежить на тому самому рядку другого кадру. Ми тримаємо два зображення у відтінках сірого, лівий `L` і правий `R`, обидва шириною `W` і висотою `H`, по одному байту на піксель:

```c
#include <stdint.h>

#define W 320          // ширина кадру в пікселях
#define H 240          // висота
#define HALF 4         // піввікно: вікно 9×9 (2·HALF+1)
#define DMIN 0         // мінімальний диспаритет (далека межа)
#define DMAX 63        // максимальний диспаритет (близька межа)

static uint8_t L[H][W];   // лівий кадр (опорний)
static uint8_t R[H][W];   // правий кадр (де шукаємо пару)
static uint8_t disp[H][W];// результат: диспаритет кожного пікселя
```

Зверніть увагу на `DMIN`/`DMAX` — це **діапазон пошуку**, і вже тут захована перша інженерна думка, до якої ми ще повернемося. А поки що — найголовніше питання: як одне віконце вирішує, що інше віконце на нього «схоже»?

## Метрика схожості: SAD і SSD

Віконце — це квадратик пікселів, скажімо 9×9. У ньому 81 число-яскравість. Поставимо віконце з лівого кадру навпроти віконця-кандидата з правого і спитаємо: **наскільки вони різні?** Найпрямолінійніша відповідь — порахувати різницю яскравостей піксель-у-піксель і скласти ці різниці. Якщо складати **модулі** різниць — це сума абсолютних різниць, **SAD** (англ. *Sum of Absolute Differences*):

```
SAD = Σ |L(x+i, y+j) − R(x−d+i, y+j)|
```

де сума береться по всіх `i, j` всередині віконця (від −HALF до +HALF), а `d` — припущений диспаритет: наскільки правий кадр зсунутий вліво відносно лівого. Чим менший SAD, тим схожіші віконця; нуль означав би ідеальний збіг піксель-у-піксель.

Друга поширена метрика — сума **квадратів** різниць, **SSD** (англ. *Sum of Squared Differences*):

```
SSD = Σ (L(x+i, y+j) − R(x−d+i, y+j))²
```

Різниця між ними тонка, але реальна, і варто розуміти **чому** вона є. SAD рахує кожну розбіжність прямо пропорційно її величині: піксель, що відрізняється на 40, дає вдвічі більший внесок, ніж той, що на 20. SSD ж підносить різницю до квадрата — і тим **карає великі розбіжності значно жорсткіше**: одна-єдина яскрава пляма (відблиск, гарячий піксель, пилинка на одній з матриць) дає різницю 100, що у SSD перетворюється на 10000 і затоплює внесок усіх решти. Тому SSD гостріше реагує на справжні відмінності текстури, але водночас **крихкіший до викидів** і шуму. SAD грубіший, зате стійкіший — і, що для мікроконтролера вирішально, **дешевший**: модуль різниці це віднімання й, можливо, заперечення знака, тоді як квадрат — це множення, яке на ядрі без апаратного множника коштує помітно дорожче. Через цю пару причин — стійкість і дешевизна — на вбудованих системах майже завжди беруть **SAD**. Ми теж візьмемо його.

> 🔧 **Навіщо це.** Вибір SAD проти SSD — це не косметика, а свідома торгівля. На дроні, де камера труситься й ловить різке контрове сонце, поодинокі пересвічені пікселі — норма життя; квадратична метрика на них зривається, лінійна терпить. Плюс бюджет тактів: SAD по вікну 9×9 на кожен з 64 диспаритетів для кадру 320×240 — це вже мільйони операцій на кадр, і заміна кожного віднімання на множення може коштувати вам частоти кадрів. Метрику обирають не за красою формули, а за тим, що витримає реальна сцена й потягне реальне ядро.

Є й третя, важливіша за обидві там, де освітлення лівої та правої камери різниться, — але про неї згодом, бо спершу треба, щоб запрацював кістяк.

## Кістяк: пошук мінімуму вздовж рядка

Ідея в одному реченні: для кожного пікселя лівого кадру переберемо всі допустимі диспаритети `d` від `DMIN` до `DMAX`, для кожного порахуємо SAD між лівим віконцем і зсунутим правим, і **запам'ятаємо той `d`, де SAD найменший**. Цей переможець і є диспаритет пікселя. Стратегію «бери кандидата з найменшою ціною» так і називають — **переможець забирає все** (англ. *winner-take-all*, WTA): жодного зважування сусідів, жодного зговору між пікселями, кожен сам за себе обирає свій найкращий збіг.

Ось прямий, ще не оптимізований, але повністю робочий кістяк:

```c
#include <stdlib.h>   // для abs()

void block_match_naive(void)
{
    // межі: не виходимо за край ні вікном, ні зсувом диспаритету
    for (int y = HALF; y < H - HALF; ++y) {
        for (int x = HALF + DMAX; x < W - HALF; ++x) {

            uint32_t best_cost = UINT32_MAX;
            int      best_d    = 0;

            // перебір кандидатів-диспаритетів
            for (int d = DMIN; d <= DMAX; ++d) {
                uint32_t cost = 0;

                // SAD по вікну (2·HALF+1)×(2·HALF+1)
                for (int j = -HALF; j <= HALF; ++j) {
                    for (int i = -HALF; i <= HALF; ++i) {
                        int lv = L[y + j][x + i];
                        int rv = R[y + j][x - d + i];
                        cost += abs(lv - rv);
                    }
                }

                if (cost < best_cost) {
                    best_cost = cost;
                    best_d    = d;
                }
            }
            disp[y][x] = (uint8_t)best_d;
        }
    }
}
```

Прочитаймо межі циклів, бо в них уже сидить коректність. Зовнішні `y` і `x` обходять лише ті пікселі, навколо яких **уміщається повне віконце** — звідси `HALF` від країв. По `x` нижня межа ще й піднята на `DMAX`: коли ми зсуваємо правий індекс на `x − d`, при `d` аж до `DMAX` цей індекс не повинен піти у від'ємні стовпці. Простіше кажучи, найлівіша смуга кадру шириною `DMAX` пікселів **фізично не має де шукати близькі цілі** — для них пара виїхала б за лівий край правого кадру. Це не лінь алгоритму, а геометрія: близька точка біля лівого краю лівої камери правій камері просто не видна. Така смуга «сліпоти» — нормальна риса будь-якого блокового зіставлення, і її лишають порожньою (нуль).

Цей код працює. Він навіть дасть пристойну карту на текстурній сцені. Але якщо запустити його на МК as-is, ви отримаєте два неприємні сюрпризи: він **повзе** (про швидкість — окремий великий розділ нижче) і його карта **рвана** — діри, сходинки, поодинокі шалені пікселі. Розберімося спершу з якістю, бо швидкий, але брехливий далекомір нікому не потрібен.

## Перша пастка: однотонні ділянки і неоднозначний збіг

Уявімо, що віконце стоїть посеред рівної світло-сірої стіни. Ковзаємо ним по рядку правого кадру — і **кожне** положення дає майже однаковий, дуже малий SAD, бо всюди той самий рівний сірий. Мінімум формально є (якесь `d` дасть SAD на одиницю менший за сусідів), але він **випадковий** — його визначив не справжній збіг, а тінь шуму матриці. WTA слухняно оголосить переможцем цей шум, і піксель отримає диспаритет «зі стелі». Поруч такий самий піксель отримає інший випадковий диспаритет. Звідси характерна «сіль із перцем» на однотонних поверхнях: глибина там не просто неточна, вона **вигадана**.

Лікувати це підгонкою параметрів марно — проблема не в коді, а в тому, що **інформації немає**: на гладкій стіні немає чого зіставляти. Чесний алгоритм має не вгадувати, а **зізнаватися**, що не знає. Найпростіший і найдієвіший спосіб зізнатися — порахувати, **наскільки впевнений** переможець, і відкинути невпевнених.

Впевненість міряють так: дивляться не лише на найменший SAD, а й на **другий за дешевизною** мінімум. Якщо найкращий збіг помітно кращий за наступного претендента — пік гострий, збіг однозначний, віримо. Якщо найкращий лише трохи кращий за купу інших — пік розмитий, претендентів багато, збіг сумнівний, **викидаємо**. Це і є перевірка **унікальності** (англ. *uniqueness ratio*).

```c
// результат пошуку для одного пікселя
typedef struct {
    uint32_t best_cost;     // найменший SAD
    uint32_t second_cost;   // другий найменший SAD (поза околом переможця)
    int      best_d;
} match_t;

#define INVALID_DISP 0xFF   // позначка «диспаритет невідомий»

// у внутрішньому циклі, замість простого порівняння, ведемо ДВА мінімуми:
//   if (cost < best_cost) { second_cost = best_cost; best_cost = cost; best_d = d; }
//   else if (cost < second_cost) second_cost = cost;
// (другий мінімум беремо лише поза ±1 від best_d — сусідні d природно близькі)

static uint8_t accept_or_reject(const match_t *m)
{
    // унікальність: наскільки другий претендент гірший за переможця, у відсотках.
    // якщо другий лише трохи гірший — пік нечіткий, збіг ненадійний.
    // (best+1) у знаменнику страхує від ділення на нуль на ідеальному збігу.
    uint32_t margin = m->second_cost - m->best_cost;
    if (margin * 100 < UNIQUE_PCT * (m->best_cost + 1))
        return INVALID_DISP;            // надто близькі претенденти — не віримо

    return (uint8_t)m->best_d;
}
```

`UNIQUE_PCT` — поріг у відсотках, типово десь 10–25. Більший поріг суворіший: відкидає більше пікселів, карта стає **дірчастішою, але чеснішою**. Менший — заповнює карту щільніше ціною того, що частина значень вигадана. Це класична ручка «повнота проти достовірності», і правильне її положення залежить від задачі: для обходу перешкод краще діра (об'їдемо обережно), ніж фальшива «вільно попереду».

Тут варто наголосити на головному, бо це душа всього стереозору: **діра в карті глибини — не баг, а чесність**. Метод, що замість «не знаю» видає правдоподібне число, небезпечніший за метод, що лишає порожнечу. Дрон вірить карті; нехай краще вона мовчить там, де сліпа, ніж бреше.

## Друга пастка: оклюзії і перевірка лівим-правим

Є точки сцени, які видно одній камері й **не видно** іншій — їх затуляє щось ближче. Біля кожного вертикального краю предмета лежить така смужка фону, що для лівого ока виглядає з-за предмета, а для правого вже сховалася за ним (чи навпаки). Це **оклюзія** (лат. *occludere* — затуляти). Для затуленої точки пари на іншому кадрі **просто не існує** — а блокове зіставлення цього не знає й слухняно знайде «найсхожіше» місце, тобто чисту вигадку. Унікальність тут часто не рятує: збіг може випадково вийти гострим.

Класичний і напрочуд елегантний спосіб виловити оклюзії — **перевірка лівим-правим** (англ. *left-right consistency check*). Ідея — проста до краси. Ми зіставляли ліве з правим: для пікселя `(x, y)` ліворуч знайшли його найкращий зсув `d`, тобто пару в стовпці `x − d` праворуч. А тепер зробімо те саме **навпаки** — для того правого пікселя пошукаймо його найкращу пару в лівому кадрі й дістанемо власний диспаритет `d'`. Якщо обидва зіставлення вказують одне на одного — `d` і `d'` збігаються (з точністю до пікселя) — це **взаємно підтверджений** збіг, йому віримо. Якщо ж ліве показує на правого, а праве показує деінде — згоди немає, точку **викидаємо**. Затулена точка майже завжди провалює цей тест, бо її «пара» фіктивна й назад не вказує.

```c
static uint8_t dispL[H][W];   // диспаритет, порахований L→R (опора — лівий)
static uint8_t dispR[H][W];   // диспаритет, порахований R→L (опора — правий)

#define LR_TOL 1              // допуск розбіжності, пікселів

void left_right_check(void)
{
    for (int y = HALF; y < H - HALF; ++y) {
        for (int x = HALF + DMAX; x < W - HALF; ++x) {

            uint8_t d = dispL[y][x];
            if (d == INVALID_DISP) continue;

            // піксель праворуч, на який показує лівий збіг
            int xr = x - d;
            if (xr < HALF) { dispL[y][x] = INVALID_DISP; continue; }

            uint8_t d2 = dispR[y][xr];        // що каже зворотне зіставлення
            if (d2 == INVALID_DISP) { dispL[y][x] = INVALID_DISP; continue; }

            // згода в межах допуску — лишаємо; ні — викидаємо як оклюзію/помилку
            int diff = (int)d - (int)d2;
            if (diff < 0) diff = -diff;
            if (diff > LR_TOL)
                dispL[y][x] = INVALID_DISP;
        }
    }
}
```

Платня очевидна й болюча: щоб мати `dispR`, треба **прогнати зіставлення двічі** — повний цикл L→R і повний цикл R→L. Для мікроконтролера це буквально подвоєння й без того найдорожчої частини. Тому на найслабшому залізі перевіркою лівим-правим іноді жертвують, лишаючись на самій унікальності; на трохи потужнішому — роблять її, бо саме вона прибирає найпідступніші помилки на краях об'єктів, де карта глибини найважливіша (адже саме краї — це межі перешкод). Чи варта згода подвоєння рахунку — інженерне рішення під конкретний апарат і конкретну задачу.

> 🔧 **Навіщо це.** Унікальність і перевірка лівим-правим ловлять **різні** хвороби, тому в серйозному конвеєрі стоять разом. Унікальність відсікає невпевненість на бідній текстурі — однотонні стіни, небо, туман. Перевірка лівим-правим відсікає геометрично неможливе — оклюзії на краях предметів. Перша каже «я не певен», друга — «ми двоє не домовилися». Карта після обох — дірчаста, зате кожне число в ній **двічі заслужене**, і саме на таку карту можна посадити обхід перешкод, не боячись фантомів.

## Третя пастка: межі діапазону диспаритету

Повернімося до `DMIN`/`DMAX`, бо з ними пов'язана тиха, але капосна помилка. Згадаймо з теми: `d` обернено пов'язаний з глибиною, `d = f·b/Z`. Отже, **великий** диспаритет — близька ціль, **малий** — далека. Діапазон `[DMIN, DMAX]`, який ми перебираємо, прямо задає **робочу зону дальності** давача:

```
найближча видима глибина  Zмін = f · b / DMAX
найдальша видима глибина  Zмакс = f · b / DMIN   (при DMIN=0 — нескінченність)
```

Тепер пастка. WTA шукає мінімум SAD **лише всередині** цього діапазону. Якщо справжня пара точки лежить **за** `DMAX` (ціль ближча, ніж ми передбачили) — істинного мінімуму в нашому вікні пошуку **немає**, і алгоритм віддасть найкраще з поганого: пришпилить диспаритет до краю `DMAX` або знайде випадковий хибний збіг усередині діапазону. Класичний симптом — стіна «прилиплих» до `DMAX` пікселів на дуже близькому предметі, або шум там, де мала б бути близька суцільна поверхня. Дзеркально, надто широкий `DMAX` теж шкодить: що більший діапазон, то більше випадкових кандидатів перебирає WTA, то вища ймовірність хибного збігу — **і** то довше рахунок (час лінійний від `DMAX − DMIN`).

Звідси практичне правило: `DMAX` ставлять не «з запасом», а **точно під найближчу дистанцію**, яку давач мусить бачити, порахувавши його з `f`, `b` і бажаної `Zмін`. Ставити більше — платити тактами й точністю за дальність, якої не потребуєш.

**Приклад (порахувати DMAX під задачу).** Дрон має впевнено бачити перешкоди починаючи з 0.5 м. Камери: фокус `f = 700` пікселів, база `b = 0.08` м. Який потрібен `DMAX`?

```
DMAX = f · b / Zмін = 700 · 0.08 / 0.5
     = 56 / 0.5 = 112 пікселів
```

Округлюємо вгору до зручного значення (скажімо, 112 або 128). Якби ми лишили типове `DMAX = 63`, найближча видима глибина була б `Zмін = 56 / 63 ≈ 0.89` м — і все, що ближче за 0.89 м, давач бачив би хибно: рівно ту небезпечну зону, заради якої він і стоїть. Діапазон диспаритету — це не магічна константа з прикладу, а **прямий переклад** робочої дальності в пікселі.

## Субпіксельне уточнення: вичавити частку пікселя

Дотепер диспаритет у нас **цілий** — переможець `best_d` це номер кроку. Але згадаймо з теми головну біду стерео: похибка глибини росте як `Z²`, тож кожна частка пікселя диспаритету вдалині коштує метрів. Якщо лишити диспаритет цілим, карта глибини на середніх дистанціях розпадеться на видимі **сходинки** — концентричні «теракотові тераси» замість плавної поверхні. Хочеться дістати дробову частину: не просто «мінімум на `d = 17`», а «мінімум десь між 17 і 18, ближче до 17».

Інформація для цього вже порахована — вона у **формі** кривої SAD навколо переможця. Уявімо три сусідні значення: SAD на `d−1`, на `d` (найменше) і на `d+1`. Біля справжнього мінімуму крива схожості гладка, її дно схоже на **параболу**. А в параболи вершина знаходиться аналітично, однією формулою, по трьох точках. Підженемо параболу під ці три SAD і візьмемо її вершину як уточнений, **субпіксельний** диспаритет:

```
                    C(d−1) − C(d+1)
d_sub = d  +  ───────────────────────────────
              2·(C(d−1) − 2·C(d) + C(d+1))
```

де `C(·)` — це SAD на відповідному кроці. Чисельник вловлює **перекіс**: якщо ліве плече вище за праве, мінімум насправді правіше за `d`, і навпаки. Знаменник — це «кривина» дна (друга різниця); він нормує поправку: на гострому піку поправка мала, на пологому — більша. Поправка завжди лежить у межах ±0.5 пікселя — далі вершина параболи виходити не може, бо `C(d)` за побудовою найменше з трьох.

```c
// уточнення цілого диспаритету best_d до субпіксельного.
// c_lo, c_mid, c_hi — SAD на best_d−1, best_d, best_d+1.
// повертає диспаритет, помножений на 16 (формат Q4: 4 дробові біти),
// щоб лишитися в цілих числах — на МК це звично і швидко.
static int subpixel_refine(int best_d, uint32_t c_lo,
                           uint32_t c_mid, uint32_t c_hi)
{
    int num = (int)c_lo - (int)c_hi;             // перекіс плечей
    int den = (int)c_lo - 2 * (int)c_mid + (int)c_hi;  // кривина дна (>0)

    if (den <= 0)                  // дно не опукле — параболі нема за що зачепитися
        return best_d << 4;        // лишаємо ціле (·16)

    // поправка (num / (2·den)) у межах ±0.5; ведемо її в Q4 без float:
    //   correction_Q4 = round( 16 · num / (2·den) ) = (8·num) / den, з округленням
    int corr_q4 = (8 * num + (num >= 0 ? den : -den) / 2) / den;

    // страховка: поправка не може вийти за ±0.5 пікселя (±8 у Q4)
    if (corr_q4 >  8) corr_q4 =  8;
    if (corr_q4 < -8) corr_q4 = -8;

    return (best_d << 4) + corr_q4;
}
```

Тут варто зупинитися на двох інженерних рішеннях. Перше: ми навмисне **не використали `float`**. Багато мікроконтролерів не мають апаратного блока для дробових чисел, тож кожна операція з `float` емулюється бібліотекою й коштує десятки тактів. Тому диспаритет ведемо в **нерухомій коми** — формат Q4, тобто ціле число, помножене на 16, де чотири молодші біти означають дробову частину (1/16 пікселя — більш ніж досить, бо реальна точність зіставлення все одно близько 0.1–0.2 пікселя). Усе лишається в цілій арифметиці. Друге: перевірка `den <= 0`. Якщо дно кривої не опукле (буває на шумі чи на тому самому неоднозначному збігу), парабола вивернулася б і дала маячню — тоді чесно лишаємо цілий диспаритет без уточнення.

> 🔧 **Навіщо це.** Субпіксель — це майже безплатний виграш у точності там, де він найдорожчий. Три значення SAD навколо переможця **вже пораховані** головним циклом, тож уточнення — це кілька додавань і одне ділення на піксель, мізер проти вартості самого пошуку. А віддача велика саме на середніх і далеких дистанціях, де `Z²` нещадний: без субпікселя карта глибини там — сходи, з ним — плавна поверхня. Це той рідкісний випадок, коли копійчана поправка рятує метри.

## Складніша метрика: чому SAD ламається на різному освітленні

Тепер можна повернутися до обіцяної третьої метрики. У SAD і SSD заховане тихе припущення: один і той самий шматок сцени дає **однакову яскравість** на обох камерах. У житті це не так. Дві матриці мають трохи різне підсилення й експозицію; той самий край може бути яскравішим у лівому кадрі й тьмянішим у правому — через відблиск, віньєтування об'єктива, різницю автоекспозиції двох сенсорів. SAD сприймає цю **рівномірну** різницю яскравості як справжню відмінність текстури й псує збіг: правильна пара дає ненульовий SAD просто тому, що вся праворуч на двадцятку темніша.

Розв'язок придумали Рамін Забіх і Джон Вудфілл у 1994 році (стаття «Non-parametric local transforms for computing visual correspondence», ECCV 1994) — це **перетворення Цензу** (англ. *Census transform*; статус: усталено, оригінальна праця цитована тисячі разів). Ідея геніально проста: відмовмося порівнювати **абсолютні** яскравості й порівнюймо лише їхній **порядок**. Для кожного пікселя обійдемо його сусідів у віконці й запишемо один біт на сусіда: 1, якщо сусід **яскравіший** за центр, 0 — якщо ні. Виходить бітовий рядок-«відбиток» локального рельєфу. А схожість двох відбитків — це **відстань Геммінга**: скільки бітів відрізняється (`popcount` від XOR двох рядків).

Чому це лікує освітлення? Бо якщо вся ділянка стала рівномірно темніша чи яскравіша, **відношення** «сусід проти центра» не змінюється: де було яскравіше, там і лишилося яскравіше. Бітовий відбиток той самий, відстань Геммінга нуль — збіг ідеальний, попри різну абсолютну яскравість. Перетворення Цензу **інваріантне до монотонної зміни яскравості** — рівно те, що губить SAD.

```c
// перетворення Цензу у вікні 5×5: 24 сусіди → 24-бітний відбиток.
// (центр не кодуємо; беремо менше вікно, бо 9×9 дало б 80 біт — незручно)
static uint32_t census_5x5(const uint8_t img[H][W], int x, int y)
{
    uint8_t  c   = img[y][x];      // яскравість центрального пікселя
    uint32_t bits = 0;
    for (int j = -2; j <= 2; ++j) {
        for (int i = -2; i <= 2; ++i) {
            if (i == 0 && j == 0) continue;   // центр пропускаємо
            bits <<= 1;
            if (img[y + j][x + i] > c)         // сусід яскравіший за центр?
                bits |= 1u;
        }
    }
    return bits;                   // 24-бітний «відбиток» локального рельєфу
}

// вартість збігу = відстань Геммінга між відбитками (кількість різних бітів)
static inline uint32_t hamming(uint32_t a, uint32_t b)
{
    uint32_t x = a ^ b;            // біти, де відбитки розходяться
    // popcount: на Cortex-M часто є __builtin_popcount або інструкція;
    // тут — переносний варіант Кернігана (рахує лише встановлені біти)
    uint32_t n = 0;
    while (x) { x &= (x - 1); ++n; }
    return n;
}
```

Цензу платить за стійкість трьома речами, і їх треба знати. По-перше, він **відкидає величину** різниці — нам важливо лише «яскравіше/темніше», тож на дуже тонкій, малоконтрастній текстурі він менш чутливий, ніж SAD. По-друге, він трохи дорожчий на підготовці (для кожного пікселя обох кадрів спершу рахуємо відбиток), зате сам збіг — `XOR` + `popcount` — дуже дешевий, а на багатьох Cortex-M `popcount` є апаратною інструкцією за один такт. По-третє, центральний піксель у класичному Цензу не кодується, тож рівно на центрі він трохи «сліпий» до шуму — це лікують варіаціями (наприклад, порівнянням не з центром, а з локальним середнім). На вбудованому стерео, де освітлення двох камер ніколи не однакове ідеально, Цензу часто **перемагає** SAD за якістю карти при цілком стерпній ціні — тому його варто мати в арсеналі поряд із SAD, а не замість нього.

## Обчислювальна ціна: чому це важка частина на МК

Тепер найчесніша розмова — про **вартість**. Усе красиве вище нічого не варте, якщо воно не вкладається в бюджет тактів мікроконтролера. Порахуймо чесно, скільки коштує наш наївний кістяк на скромному кадрі 320×240.

```
пікселів у кадрі:           320 · 240          ≈ 76 800
кандидатів на піксель:      DMAX − DMIN + 1  =  64
пікселів у вікні (SAD):     9 · 9            =  81
операцій SAD на піксель:    64 · 81          ≈ 5 184
усього на кадр:             76 800 · 5 184   ≈ 398 000 000
```

Майже **чотириста мільйонів** операцій (віднімання + модуль + додавання) на один-єдиний кадр. На ядрі 100 МГц, оптимістично рахуючи операцію за такт, це **щонайменше чотири секунди на кадр** — а реально вдвічі-втричі довше через доступи до пам'яті. Карта глибини раз на десять секунд для дрона, що летить, — це не далекомір, а слайд-шоу. І це **без** перевірки лівим-правим, яка подвоює рахунок, і без Цензу.

Чому так дорого, видно прямо з формули: вартість — це **добуток чотирьох чисел**, і кожне хоче рости. Більший кадр — краще видно, але квадратично дорожче. Ширший діапазон `DMAX` — ближча робоча зона, але лінійно дорожче. Більше вікно — стійкіший збіг, але квадратично дорожче. Стерео — це **потрійно вкладений цикл поверх кожного пікселя**, і кожен рівень множить навантаження. Ось чому зіставлення — найважча, найненажерливіша частина всього стереоконвеєра, і чому на МК воно завжди вимагає хитрощів.

Хитрощі бувають трьох сортів, і всі ґрунтуються на одному спостереженні: **сусідні обчислення страшенно надлишкові**.

**Перше — ковзне сумування SAD.** Коли віконце 9×9 зсувається на один піксель управо, до нової суми входить лише новий правий стовпець, а випадає старий лівий — решта 7 стовпців ті самі. Замість 81 операції на піксель можна за допомогою буфера часткових сум по стовпцях обходитися кількома: відняти стовпець, що випав, додати той, що ввійшов. Це перетворює залежність вартості від розміру вікна з квадратичної майже на сталу — вікно 15×15 коштує практично як 5×5. Прийом називають **інтегральним** (або ковзним) сумуванням, і для блокового зіставлення він обов'язковий:

```c
// ескіз ковзного SAD уздовж рядка для ОДНОГО фіксованого диспаритету d.
// col_sad[x] тримає вертикальну суму |L−R| по стовпцю x (висотою у вікно).
// тоді SAD вікна = сума col_sad по 2·HALF+1 сусідніх стовпцях, і при зсуві
// вікна вправо ми лише додаємо новий стовпець і віднімаємо той, що вийшов.
static uint16_t col_sad[W];

static void slide_row_for_d(int y, int d)
{
    // 1) порахувати вертикальні суми стовпців один раз на рядок
    for (int x = d; x < W; ++x) {
        uint16_t s = 0;
        for (int j = -HALF; j <= HALF; ++j)
            s += (uint16_t)abs((int)L[y + j][x] - (int)R[y + j][x - d]);
        col_sad[x] = s;
    }
    // 2) перша віконна сума зліва
    uint32_t win = 0;
    for (int x = d; x < d + 2 * HALF + 1; ++x) win += col_sad[x];
    // 3) ковзаємо вікном: +новий стовпець, −старий (О(1) на піксель)
    for (int xc = d + HALF + 1; xc < W - HALF; ++xc) {
        // тут win — це SAD вікна з центром (xc-1) при цьому d;
        // порівнюємо з найкращим для цього пікселя й оновлюємо best/second...
        win += col_sad[xc + HALF];
        win -= col_sad[xc - HALF - 1];
    }
}
```

**Друге — порядок циклів і пам'ять.** Наївний код тримає `d` у внутрішньому циклі, перечитуючи ті самі пікселі знову й знову з повільної зовнішньої пам'яті. Якщо натомість обробляти кадр **смугами рядків**, що вміщаються в швидку внутрішню пам'ять (а на дешевих МК уся картинка 320×240 у внутрішній SRAM не лежить), доступи стають локальними й кеш/SRAM перестають бути вузьким місцем. На вбудованих системах **рух даних коштує дорожче за саму арифметику** — і часто головний виграш дає не швидший лічильник, а розумніше розкладена пам'ять.

**Третє — звузити саму задачу.** Менший `DMAX` точно під дистанцію (як ми рахували вище), менший кадр, переможець забирає все без надмірної точності там, де вона не потрібна. Кожне таке звуження множиться на решту.

> 🔧 **Навіщо це.** Саме обчислювальна ціна пояснює, **чому в апараті стереозір часто винесений в окремий чип**, а не крутиться на головному МК. Спеціалізована логіка (FPGA чи стереоблок усередині SoC) робить ті самі 9×9-зіставлення **паралельно** для всіх диспаритетів і всіх пікселів рядка одночасно — і видає карту глибини на кожен кадр у реальному часі, поки головний процесор зайнятий польотом. На голому МК повноцінне щільне стерео в реальному часі — на межі можливого; його тягнуть або на маленькому кадрі з вузьким діапазоном і всіма хитрощами вище, або взагалі віддають залізу. Ця стіна вартості — не вада вашого коду, а фундаментальна риса задачі, і знати її треба ще **до** того, як обирати, на чому будувати давач глибини.

## Зведімо конвеєр докупи

Складімо тепер усе в один порядок дій — це і є робочий конвеєр блокового зіставлення, від двох вирівняних кадрів до карти диспаритету, якій можна вірити:

```
1. (за потреби) порахувати відбитки Цензу для L і R   — стійкість до освітлення
2. для кожного пікселя L:
     перебрати d ∈ [DMIN, DMAX]                         — діапазон = робоча дальність
       порахувати вартість (SAD ковзним сумуванням / Hamming)
       вести два мінімуми: best і second               — для унікальності
3. прийняти або відкинути за унікальністю              — відсікти бідну текстуру
4. (за можливості) повторити R→L і перевірити згоду    — відсікти оклюзії
5. для вцілілих — субпіксельне уточнення параболою     — прибрати сходинки глибини
6. (опційно) Z = f·b/d_sub                             — диспаритет у метри
```

Кожен крок тут не прикраса, а ліки від конкретної хвороби, яку ми пройшли: діапазон стереже робочу зону, унікальність ловить однотонність, перевірка лівим-правим ловить оклюзії, субпіксель ловить квадратичну похибку глибини, ковзне сумування й розкладка пам'яті ловлять обвал швидкості, Цензу ловить різне освітлення двох камер. Виплигнути можна будь-який крок — і карта глибини захворіє рівно тією хворобою, ліки від якої ви прибрали. Саме тому блокове зіставлення оманливо просте на словах і по-справжньому інженерне в коді: один цикл пошуку мінімуму обростає шаром захистів, і кожен шар відповідає за свій спосіб, яким реальний світ намагається стерео обдурити.
