# ⚙️ Безпечний обмін між контуром керування і зором

**Задача.** У статті ми вивели правило шва між твердим контуром керування й бортовим комп'ютером зору: контур ніколи не блокується, читає **останнє** значення, перевіряє його **свіжість** — і, головне, бере **узгоджений знімок**, копіюючи всю структуру одним махом. Там ми відбулися одним рядком `vision_hint_t h = g_hint;` і фразою «на МК читання структури не атомарне». Настав час зазирнути під цей рядок, бо саме тут ховається клас помилок, що не ловляться на стенді й вилазять раз на тисячу зчитувань уже в польоті.

Сформулюймо точно. По одну руку — **писар**: перерва приймача UART, яка щойно розібрала пакет MAVLink від комп'ютера зору й хоче оновити структуру `{ кут, штамп часу, чинність }`. По другу — **читач**: виток контуру керування на 1–8 кГц, який хоче ту структуру прочитати цілком і несуперечливо. Вони працюють **асинхронно**: перерва може вклинитися **будь-якої миті**, зокрема **посеред** того, як контур читає структуру поле за полем. Якщо не подбати, читач дістане **напівоновлені** дані — новий кут зі старим штампом (чи навпаки), безглузду пару, за якою апарат смикнеться невідомо куди.

Наша мета — обмін, у якому читач **завжди** бачить структуру або цілком старою, або цілком новою, **ніколи напівоновленою**, і при цьому контур **жодного разу не блокується** довше, ніж на кілька машинних інструкцій. Розберемо три робочі способи це зробити — коротке вимкнення переривань, подвійний буфер (ping-pong) і seqlock, — покажемо для кожного реальний C, і чесно назвемо, коли який брати й де кожен ламається.

## Ідея: чому «просто прочитати структуру» — це вже гонка

Спинімося на самій природі біди, бо доки вона не стала відчутною, будь-яке «лікування» виглядає зайвим марнуванням.

На великому комп'ютері присвоєння `h = g_hint` виглядає **однією** дією. На мікроконтролері це ілюзія. Структура з `float` (4 байти), `uint32_t` (4 байти) і `bool` — це щонайменше дев'ять байтів, і процесор копіює їх **кількома** інструкціями завантаження-збереження. Між будь-якими двома з цих інструкцій апаратна перерва має повне право вклинитися, виконати свій обробник **до кінця** й повернути керування. Ось точний сценарій катастрофи:

```
контур (читач)                          перерва UART (писар)
─────────────────────────────────       ────────────────────────────────
1. читає target_angle = 30.0°   (старий кут)
                                    ← ПЕРЕРВА вклинюється тут →
                                    2. пише target_angle = 12.0°  (новий кут)
                                    3. пише stamp_ms     = 88000  (новий штамп)
                                    4. пише valid        = true
                                    ← повернення з перерви →
5. читає stamp_ms = 88000        (новий штамп!)
6. читач має пару { 30.0°, 88000 } — РОЗІРВАНУ:
   кут старий, штамп новий. Контур вирішить, що
   ціль щойно бачена під кутом 30°, хоча вона вже під 12°.
```

Результат — не «трохи неточно». Контур повірить, що **свіжо** (штамп-бо новий) бачив ціль під **старим** кутом, поведе апарат туди, де цілі вже немає, і зробить це впевнено. Найгидкіший різновид помилки: без збою, без винятку, просто раз на багато тисяч зчитувань апарат смикається «в нікуди». На землі під час налагодження ти цього майже не зловиш — вікно гонки завширшки в кілька інструкцій; у польоті, де контур крутиться годинами по 8000 разів на секунду, воно неминуче спрацює.

> 🔧 **Навіщо це.** Правило залізне: **дані, що їх пише перерва, а читає головний код (чи навпаки), не можна читати «наївно» кількома зверненнями** — між ними влізе перерва й лишить тобі розірвану пару. Питай про кожну спільну змінну складнішу за один машинний тип: «а що, як перерва вклиниться посередині мого читання?» Якщо відповідь «дістану суміш старого й нового» — потрібен один із захистів нижче. Це стосується не лише кута зору: будь-яка пара «значення + його штамп/прапорець», яку оновлює перерва, має той самий ґандж.

Є ще одна тонкість, чому не рятує «зроблю поле `volatile`». `volatile` каже компілятору «не кешуй цю змінну в регістрі, перечитуй з пам'яті» — і тільки. Воно не робить читання **кількох** полів однією неподільною дією й ніяк не заважає перерві вклинитися між ними. `volatile` потрібне (щоб компілятор не «оптимізував» повторні читання й бачив зміни з перерви), але його **замало**: воно бореться з компілятором, а не з гонкою в часі. Гонку прибирають три способи нижче.

## Спосіб 1: короткочасне вимкнення переривань

Найпряміша думка: якщо біда в тому, що перерва вклинюється посеред читання, — **заборонімо їй вклинюватися** саме на ці кілька інструкцій. Вимкнули переривання, скопіювали структуру цілком, увімкнули назад. Поки переривання вимкнені, писар фізично не може втрутитися, тож знімок вийде цілісним за побудовою.

```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    float    target_angle;   // кут на ціль від зору
    uint32_t stamp_ms;       // коли прийшов (мс від старту)
    bool     valid;          // чи взагалі щось приходило
} vision_hint_t;

// Спільна змінна: пише перерва UART, читає контур.
static volatile vision_hint_t g_hint = { 0.0f, 0, false };

// ── писар: у перерві приймача, коли розібрано пакет MAVLink ──
void on_vision_msg(float angle, uint32_t now_ms) {
    g_hint.target_angle = angle;   // перерва не переривається контуром,
    g_hint.stamp_ms     = now_ms;  // тож тут окремий захист не потрібен
    g_hint.valid        = true;
}

// ── читач: у витку контуру. Бере ЦІЛІСНИЙ знімок ──
vision_hint_t hint_read_critical(void) {
    vision_hint_t snap;

    __disable_irq();          // заборонили перерви (CMSIS; або своя обгортка)
    snap = g_hint;            // копіюємо цілком — перерва вклинитись не може
    __enable_irq();           // одразу повернули перерви

    return snap;              // далі працюємо з копією скільки завгодно
}
```

Механіка проста й надійна, але має **ціну, яку треба поважати**: доки переривання вимкнені, процесор **глухий до всього** — до того ж UART, до таймера контуру, до всіх інших джерел. Якщо тримати їх вимкненими довго, ти прогавиш вхідні байти (переповниться приймач) або зсунеш такт контуру — тобто, рятуючи знімок, наробиш гіршого. Тому залізне обмеження: **під вимкненими перериваннями роби якнайменше** — рівно копію структури, і ні інструкцією більше. Ніякого друку, ніякої обробки, ніяких обчислень усередині.

> 🔧 **Навіщо це.** Вимкнення переривань — молоток: працює завжди, але **зупиняє реакцію на весь час дії**. Правило користування: заходь у критичну секцію на мінімум інструкцій і виходь. Скопіювати дев'ять байтів — це десяток тактів, невидима пауза, безпечно. А от викликати звідти щось важче — пряма дорога загубити дані на іншому периферійному вузлі. Якщо бачиш `__disable_irq()`, а між ним і `__enable_irq()` більш ніж кілька рядків присвоєнь — це вже пахне бідою.

Один нюанс, який часто роблять неправильно: якщо перерви **вже** могли бути вимкнені вище по стеку (ти в іншій критичній секції), грубий `__enable_irq()` **увімкне** їх передчасно й зламає зовнішню секцію. Правильно — **зберегти й відновити** попередній стан, а не вмикати наосліп:

```c
// Безпечніше: зберегти маску, вимкнути, відновити рівно як було.
vision_hint_t hint_read_saferestore(void) {
    vision_hint_t snap;
    uint32_t primask = __get_PRIMASK();  // запам'ятали, чи перерви вже вимкнені
    __disable_irq();
    snap = g_hint;
    __set_PRIMASK(primask);              // відновили ТОЧНО попередній стан
    return snap;
}
```

Це той самий прийом «зберегти-відновити», що й із будь-яким глобальним станом: не «увімкнути», а «повернути як було». Дрібниця, але без неї вкладені критичні секції тихо ламаються.

## Спосіб 2: подвійний буфер (ping-pong) з індексом-прапорцем

Вимкнення переривань чудове для дев'яти байтів. А якщо знімок зору більший — не самий кут, а, скажімо, координати кількох цілей, матриця чи ціла структура стану на сотні байтів? Копіювати сотні байтів під вимкненими перериваннями вже довго — можна прогавити UART. Потрібен спосіб, де читач і писар **не заважають одне одному взагалі**, бо працюють із **різними** ділянками пам'яті.

Ідея — **подвійний буфер** (англ. *double buffer*, у грі слів — *ping-pong*): тримаємо **два** екземпляри структури й один **індекс**, який каже, котрий із них зараз «готовий для читання». Писар завжди заповнює **той, що не читається**, а коли закінчив — **перемикає індекс** одним записом. Читач завжди бере той, на який показує індекс. Вони фізично не торкаються одного буфера одночасно.

```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    float    target_angle;
    uint32_t stamp_ms;
    bool     valid;
    // …тут може бути скільки завгодно полів: буфер копіюється не читачем…
} vision_hint_t;

static vision_hint_t   g_buf[2];             // два екземпляри: ping і pong
static volatile uint8_t g_ready = 0;         // індекс ГОТОВОГО буфера (0 або 1)

// ── писар: у перерві. Пише в НЕактивний буфер, тоді перемикає індекс ──
void on_vision_msg(float angle, uint32_t now_ms) {
    uint8_t back = g_ready ^ 1u;             // «задній» буфер — той, що НЕ читається
    g_buf[back].target_angle = angle;        // спокійно заповнюємо його цілком:
    g_buf[back].stamp_ms     = now_ms;       // читач зараз дивиться в ІНШИЙ буфер
    g_buf[back].valid        = true;

    g_ready = back;                          // ← АТОМАРНЕ перемикання: один запис байта
}

// ── читач: у витку контуру. Читає активний буфер, НЕ блокуючи перерву ──
vision_hint_t hint_read_pingpong(void) {
    uint8_t idx = g_ready;                    // зафіксували, котрий читати
    return g_buf[idx];                        // копіюємо готовий буфер
}
```

Уся безпека тут тримається на **одному** факті: перемикання `g_ready = back` — це запис **одного байта**, а такий запис на будь-якому притомному МК **атомарний** (виконується однією інструкцією, перерва не розколе його навпіл). Тому читач бачить `g_ready` або старим, або новим — ніколи «напівперемкненим». Поки писар длубається в задньому буфері (хоч сто полів), читач спокійно черпає з переднього; у мить `g_ready = back` фокус миттєво переводиться на щойно готовий буфер цілком.

Але тут зачаїлася **власна пастка**, тонша за першу, і назвати її треба чесно. Що, як писар **перемкнув** індекс на буфер `back`, а читач саме тепер почав з нього копіювати — і **тим часом надійшов наступний пакет**, і писар кинувся заповнювати цей самий буфер знову (бо тепер уже інший став «заднім»… ні — тепер задній це той, що читач лишив)? Розкладімо акуратно. Після `g_ready = back` ролі помінялись: щойно записаний буфер став переднім (його читають), а колишній передній — заднім. Наступний пакет писар покладе в **новий** задній, тобто в **той, що читач щойно покинув**. Здавалося б, безпечно. Небезпека лишається у **вузькому** вікні: читач зафіксував `idx`, і поки він копіює `g_buf[idx]`, приходять **два** пакети поспіль — перший ляже в інший буфер (гаразд), але **другий** знову цілить у `idx`, який читач ще копіює. Тоді писар почне переписувати буфер прямо під читачем — знову розірвана пара, лише рідша.

Для нашого випадку — контур на кілька кГц, пакети зору десятки разів на секунду — два пакети за один короткий акт копіювання практично неможливі, тож простий ping-pong надійний. Але якщо писар **швидкий**, а знімок великий (копіювання довге), цю дірку закривають **трьома** буферами замість двох (щоб писар завжди мав вільний, не той, що читається, і не той, що щойно віддали) — або переходять до seqlock, який ловить саме цей випадок за побудовою.

> 🔧 **Навіщо це.** Подвійний буфер — правильний вибір, коли знімок **завеликий**, щоб копіювати його під вимкненими перериваннями. Він не глушить перерв ані на такт: писар і читач розведені по різних буферах, синхронізує їх один атомарний запис індексу. Ціна — вдвічі більше пам'яті (два екземпляри) і згадана вузька гонка при дуже частому писареві. Практичне правило: **два буфери, якщо писар помітно повільніший за акт читання; три, якщо ні.** І пам'ятай: працює лише доти, доки перемикання індексу справді вміщається в одну атомарну інструкцію — байт або машинне слово, вирівняне.

## Спосіб 3: seqlock — читач сам помічає, що його підмінили

Є третій спосіб, найелегантніший, коли писар — це перерва, а читач — цикл: **seqlock** (від англ. *sequence lock* — «замок за лічильником послідовності»). Він не глушить перерв і не подвоює пам'ять. Ідея інша й гарна: писар лишає **слід** кожного разу, коли щось міняє, а читач **перечитує**, доки не переконається, що під час його читання ніхто нічого не чіпав.

Слід — це **лічильник послідовності** (англ. *sequence counter*). Домовляємось так: писар збільшує лічильник **на початку** запису й **ще раз** наприкінці. Звідси проста арифметика — **непарний** лічильник означає «запис саме йде», **парний** — «запис завершено, дані цілі». Читач робить так: зчитав лічильник (мусить бути парний), скопіював дані, зчитав лічильник **знову** — і якщо він не змінився, знімок чистий; якщо змінився чи став непарним, то писар вклинився під час копіювання — **читаємо все наново**.

```c
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    float    target_angle;
    uint32_t stamp_ms;
    bool     valid;
} vision_hint_t;

static vision_hint_t    g_hint;
static volatile uint32_t g_seq = 0;   // парний = стабільно, непарний = триває запис

// ── писар: у перерві. Обгортає запис збільшенням лічильника ──
void on_vision_msg(float angle, uint32_t now_ms) {
    g_seq++;                           // → непарний: «увага, я пишу»
    __asm volatile ("dmb" ::: "memory");  // бар'єр: лічильник змінився ДО даних

    g_hint.target_angle = angle;
    g_hint.stamp_ms     = now_ms;
    g_hint.valid        = true;

    __asm volatile ("dmb" ::: "memory");  // бар'єр: дані записані ДО лічильника
    g_seq++;                           // → знову парний: «готово, дані цілі»
}

// ── читач: у витку контуру. Перечитує, поки не впіймає стабільний знімок ──
vision_hint_t hint_read_seqlock(void) {
    vision_hint_t snap;
    uint32_t before, after;

    do {
        before = g_seq;                     // 1) зчитали лічильник…
        if (before & 1u)                    //    непарний → писар саме пише
            continue;                       //    не морочимось, одразу наново
        __asm volatile ("dmb" ::: "memory");

        snap = g_hint;                      // 2) скопіювали дані

        __asm volatile ("dmb" ::: "memory");
        after = g_seq;                      // 3) …і зчитали лічильник ЗНОВУ
    } while (before != after);              // змінився? писар вклинився → наново

    return snap;                            // before == after (парні) → знімок чистий
}
```

Придивись, чому це працює. Якщо перерва-писар вклинилась **у будь-яку мить** копіювання `snap = g_hint`, вона неодмінно смикнула лічильник (двічі: до й після), тож `after != before`, і читач **викине** підозрілий знімок і зробить ще один захід. Він крутитиме `do/while` рівно доти, доки не спіймає **вікно тиші** між записами, у яке копіювання пролізе цілим. А оскільки писар (короткий обробник перерви) працює мікросекунди, а між пакетами зору — десятки мілісекунд, таких вікон більш ніж досить: читач майже завжди проходить із **першого** разу, зрідка з другого.

Тут два тонкі місця, які легко проґавити.

Перше — **бар'єри пам'яті** (`dmb` — *data memory barrier*). На сучасних ядрах (Cortex-M7 і вище, будь-який процесор із перевпорядкуванням доступів) компілятор чи залізо можуть **переставити** запис даних і запис лічильника місцями — і тоді читач побачить «готово» (парний лічильник) **раніше**, ніж дані реально лягли. Бар'єр забороняє цю перестановку: він каже «усе, що до тебе, завершити до того, що після тебе». Без бар'єрів seqlock на такому ядрі тихо ламається саме там, де здається робочим (на простенькому Cortex-M0 без перевпорядкування зійде й без них, але ставити варто завжди — код переносний, і думати не треба).

Друге — seqlock **не годиться**, коли писарем є **головний код**, а читачем — перерва (тобто навпаки). Бо якщо перерва-читач вклиниться, поки головний писар лишив лічильник **непарним** (посеред запису), читач крутитиме `do/while` **вічно**: писар-бо зупинений тією ж перервою й ніколи не докінчить, лічильник ніколи не стане парним — заклинення. Тому seqlock — саме для нашого розкладу: **писар у перерві** (завжди добігає до кінця, бо його ніхто не витісняє), **читач у циклі** (може дозволити собі перечитати). Наш випадок — рівно такий.

> 🔧 **Навіщо це.** Seqlock — найкращий вибір, коли читань **багато** (контур на 8 кГц!), а записів мало, і глушити перерви не хочеться. Читач у щасливому випадку не платить майже нічого — два читання лічильника й копія; писар теж дешевий. Але користуйся ним лише у правильному напрямку (**писар — перерва, читач — цикл**) і **не забувай бар'єри** на ядрах із перевпорядкуванням. Переплутаєш напрямок — дістанеш вічне перечитування; забудеш бар'єр — рідкісний розірваний знімок на швидкому ядрі. Обидві біди мовчазні, тому запам'ятай умови вживання разом із самим патерном.

## Що обрати: чесне порівняння

Три способи розв'язують ту саму задачу, але ціна й межі різні. Ось як обирати, щоб не бити з гармати по горобцях і не ставити двобайтовий замок на сейф:

```
спосіб              коли брати                          ціна / межа
──────────────────  ─────────────────────────────────  ───────────────────────────
вимкнути перерви    знімок МАЛЕНЬКИЙ (одиниці байтів);  глушить УСІ перерви на
                    найпростіший, завжди коректний      час копії — тримай мінімальним

подвійний буфер     знімок ВЕЛИКИЙ; не хочемо глушити   вдвічі більше пам'яті; вузька
(ping-pong)         перерви; писар нечастий             гонка при частому писареві
                                                        (лікують третім буфером)

seqlock             читань БАГАТО, записів мало;        лише «писар=перерва,
                    не хочемо ні глушити, ні подвоювати читач=цикл»; потрібні бар'єри
                                                        пам'яті на швидких ядрах
```

Для нашого конкретного шва — кут зору (дев'ять байтів), контур на кілька кГц, пакети MAVLink десятки разів на секунду — **найпростіший спосіб 1 бездоганний**: знімок крихітний, копіювання під вимкненими перериваннями триває десяток тактів, невидима пауза. Саме тому в статті-власнику ми й показали `vision_hint_t h = g_hint;` як «знімок з коротко вимкненими перериваннями» — це рівно спосіб 1, розкритий тепер повністю. Подвійний буфер знадобиться, коли зір почне слати не один кут, а цілий стан сцени; seqlock — коли зчитувань стане *дуже* багато й кожен зайвий такт вимкнених перервань муляє. Але **суть** у всіх трьох одна, і вона — головний висновок цієї вставки.

## Складність і пастки: що лишилось за кадром

Зберемо докупи пастки, бо на них спотикаються навіть ті, хто патерн начебто знає.

**`volatile` ≠ атомарність.** Найпоширеніша ілюзія. `volatile` змушує компілятор перечитувати змінну з пам'яті й бачити зміни з перерви — і тільки. Воно **не** робить читання кількох полів неподільним і не заважає перерві вклинитися між ними. Потрібне (щоб компілятор не викинув «зайві» читання), але саме по собі гонки не лікує. Бачиш `volatile struct` і наївне присвоєння — знай, що захисту тут **немає**.

**Розірвана пара «значення + штамп».** Корінь усієї теми: кут і його штамп часу мусять читатися **разом**, як одне ціле, інакше контур повірить, що *свіжо* бачив ціль під *старим* кутом. Будь-який спосіб вище зберігає пару цілою; наївне читання поле-за-полем — ні. Це не про кут зору зокрема — про будь-яку пару «дані + їхня мітка часу/чинності», що її оновлює перерва.

**Проблема ABA в ping-pong.** Підступна саме тим, що рідкісна. Якщо писар устигне двічі перемкнути буфери, поки читач копіює один із них, читач дістане суміш — попри те, що індекс «начебто той самий». Для повільного писаря неможливо, для швидкого — лікується третім буфером. Не будуй ping-pong, не оцінивши, чи може писар обернутися двічі за один акт читання.

**Гонка запису під час читання.** Загальна назва всього, від чого ми боронимось: писар змінює структуру рівно тоді, коли читач її черпає. Кожен із трьох способів закриває її по-своєму — вимкненням перерв (писар не може втрутитися), розведенням по буферах (пишуть і читають різне), лічильником послідовності (читач помічає втручання й перечитує). Немає захисту — буде розірваний знімок, гарантовано, лише питання, як рідко.

**Напрямок seqlock і бар'єри.** Дві мовчазні біди seqlock: неправильний напрямок (писар — головний код, читач — перерва) дає **вічне перечитування** при заклиненні посеред запису; забуті бар'єри пам'яті на ядрі з перевпорядкуванням дають **рідкісний розірваний знімок**. Обидві не проявляються на стенді. Вживай seqlock лише як «писар=перерва, читач=цикл» і завжди став бар'єри — код від того не сповільниться на простому ядрі, а на складному не зламається.

**Свіжість — окремий шар поверх узгодженості.** Усі три способи гарантують лише, що знімок **цілісний** (не розірваний). Але цілісний ще не значить **свіжий**: кут, узгоджено прочитаний, міг бути записаний 300 мс тому. Тому поверх будь-якого з цих способів лишається перевірка штампа `now_ms - snap.stamp_ms < поріг` зі статті — узгодженість і свіжість це **два різні** запобіжники, і потрібні обидва. Спосіб обміну дає перший; перевірка часу — другий.

Зібравши все: наївне присвоєння спільної структури на МК — це гонка, що спрацює раз на тисячі зчитувань уже в польоті й лишить контур із розірваною парою «кут-штамп». Три способи її закривають — вимкнення перерв для крихітного знімка, подвійний буфер для великого, seqlock для потоку читань, — кожен зі своєю ціною й своїми умовами вживання. А поверх узгодженого знімка завжди лишається перевірка свіжості, бо цілий, але протухлий кут не менш небезпечний за розірваний. Оце і є повний зміст того одного рядка `vision_hint_t h = g_hint;` — рядка, за яким стоїть межа між живим гібридним апаратом і тим, що раз на політ смикається невідомо куди.
