# Шов (seam) як точка зміни

<preknowlist>
- [Інтерфейс проти реалізації](book:programming/interface-vs-implementation) — різниця між тим, ЩО частина обіцяє зовні, і тим, ЯК вона це робить; без цього поділу «підмінити за межею» не має сенсу.
- [Поліморфізм](book:programming/polymorphism) — один і той самий виклик, різні реалізації за спільним інтерфейсом; це і є механізм, яким підміняють поведінку в об'єктному шві.
</preknowlist>

Весь цей модуль ми вчилися, **де** різати. Зчеплення і зв'язність сказали, скільки сусіди мають знати одне про одного. [Приховування інформації](book:programming/information-hiding) за Парнасом — ховати саме те, що змінюється. [Інверсія залежностей](book:programming/dependency-inversion) — розвертати стрілку, щоб політику можна було лишити на місці, а деталь підмінити. [Проєктування за контрактом](book:programming/design-by-contract) — домовитися, що саме дві сторони одна одній обіцяють. Усі ці принципи, кожен зі свого боку, показують пальцем на ту саму фізичну річ: **місце в коді, де дві частини стикаються так, що одну можна змінити, не чіпаючи другу.** Майкл Фезерс дав цьому місцю ім'я — і, що важливіше, простий операційний тест, за яким його впізнають.

Ім'я знайоме. Пригадай [найперший Digital Homes](guide:progarch/dh-v0-one-sensor) — двадцять рядків, що вмикали обігрівач. Ми тоді сказали руками: між «дізнатися температуру», «вирішити» й «увімкнути розетку» **немає жодного шва**, тож розтинати їх пізніше доведеться по живому. Слово вжили побіжно, на дотик. Тепер настав час назвати його точно й перетворити з відчуття на інструмент.

## Питання, яке ставить шов

Уяви звичну ситуацію. Є робочий код — той самий зварений цикл v0, або чужа функція на триста рядків, яку ти боїшся торкати. І тобі треба змінити **одну** поведінку всередині: обкласти її тестом, підмінити вендора давача, вклинити ще один крок. Перший порух — відкрити те місце й переписати. Але саме там, де поведінка живе, редагувати найдорожче й найстрашніше: тестів нема, код чужий, від нього залежить пів системи.

Фезерс пропонує розвернути питання. Не «як мені відредагувати цей рядок?», а: **«де я можу змінити цю поведінку, НЕ редагуючи там, де вона живе?»** Те місце, звідки поведінку можна підмінити ззовні, і є шов.

> 🔧 **Навіщо це.** Різниця не словесна — вона визначає, скільки коду ти мусиш зачепити, щоб зробити зміну. Правити всередині зварки — означає розварювати перевірене й ризикувати всім, що на ньому висить. Підмінити через шов — означає лишити старий код недоторканим і додати нове збоку. Один той самий результат, але ціна й ризик відрізняються на порядок. Тому досвідчений розробник, зустрівши вимогу зміни, спершу шукає очима шов — а вже як не знайде, відкриває новий.

## Що таке шов, точно

Означення Фезерса з його книжки [«Working Effectively with Legacy Code»](guide:progarch/seams-and-boundaries/hist-seam-origin.md) (2004) коротке: **шов — це місце, де можна змінити поведінку програми, не редагуючи в цьому місці.**

Слово він узяв у кравців. Шов (англ. *seam*, від давньоангл. *sēam* — стик, з'єднання) — це лінія, де зшито два шматки тканини. Кравець випускає або вшиває одяг **по шву**: розпорює стик, переставляє, зшиває наново — і жодна нитка самого полотна при цьому не чіпається. Код-шов працює так само: це стик, на якому одну сторону можна переробити, не розпускаючи другу. Аналогія точна, але зверни увагу, **де вона ламається**: шов на тканині видно й можна намацати пальцем, а шов у коді часто невидимий — це може бути просто параметр функції чи аргумент конструктора. Він стає швом лише тоді, коли є спосіб **підмінити те, що крізь нього проходить**, не переписуючи код навколо.

І тут ключова, найлегша для пропуску деталь. У кожного шва є **точка ввімкнення (англ. *enabling point*)** — місце, де ти вирішуєш, котру з поведінок увімкнути. Шов — це отвір, де поведінка *може* різнитися; точка ввімкнення — вимикач, яким ти обираєш, *яка саме* цього разу. І вимикач той стоїть **поза** кодом, який ти бережеш. Це і є перевірка: якщо змінити поведінку не можна, не відредагувавши саме те місце, — шва ще нема. Якщо є звідки перемкнути, не торкаючись захищеного коду, — шов є, і ось його точка ввімкнення.

## Відкриваємо шов у Digital Homes

Повернімося до зварки v0 і подивімося на неї цим питанням. Ось серце циклу:

:::tabs
```py
def control_loop():
    while True:
        t = read_sensor()            # виклик прибитий цвяхом до циклу
        if t < THRESHOLD:            # політика
            heater_on()
        else:
            heater_off()
        sleep(30)
```
```ts
async function controlLoop() {
  while (true) {
    const t = await readSensor();    // виклик прибитий цвяхом до циклу
    if (t < THRESHOLD) await heaterOn();   // політика
    else await heaterOff();
    await sleep(30_000);
  }
}
```
:::

Чи є тут шов на давачі? Немає. `read_sensor()` — це конкретний виклик, вбитий у тіло циклу. Щоб згодувати політиці іншу температуру — з підробленого давача в тесті чи з давача іншого вендора, — доведеться редагувати сам цикл. Немає жодної точки ззовні, звідки перемкнути. Це рівно те «зрощення», яке ми намацали у v0.

Тепер відкриймо шов. Витягнемо давач і розетку **назовні** — хай політика приймає їх як входи, а не створює сама:

:::tabs
```py
def decide(sensor, heater, threshold):
    t = sensor.read()                # ← шов: чим є sensor — вирішують ЗЗОВНІ
    if t < threshold:
        heater.on()
    else:
        heater.off()

# точка ввімкнення — головний код обирає, ЩО під'єднати до шва:
decide(RealSensor(), RealHeater(), 20.0)      # у продакшені — справжнє залізо
decide(FakeSensor(reads=19.0), SpyHeater(), 20.0)  # у тесті — підробки
```
```ts
interface Sensor { read(): number; }
interface Heater { on(): void; off(): void; }

function decide(sensor: Sensor, heater: Heater, threshold: number) {
  const t = sensor.read();           // ← шов: чим є sensor — вирішують ЗЗОВНІ
  if (t < threshold) heater.on();
  else heater.off();
}

// точка ввімкнення — головний код обирає, ЩО під'єднати до шва:
decide(new RealSensor(), new RealHeater(), 20.0);        // продакшен
decide(new FakeSensor(19.0), new SpyHeater(), 20.0);     // тест
```
:::

Придивися, що сталося. Тіло `decide` не знає й не хоче знати, звідки береться температура: воно кличе `sensor.read()` — і на цьому вхідному стику тепер **шов**. Підмінити давач можна, не торкнувшись жодного рядка політики; вимикач — це той рядок збірки, де вирішено, `RealSensor` чи `FakeSensor` передати. Ось вона, точка ввімкнення, і стоїть вона зовні, у головному коді. Повний робочий приклад — відкритий шов, тест, що жене крізь нього підроблений давач і доводить, що поведінка змінилася без жодної правки політики, і той самий трюк для чужої бібліотеки, якої не переписати зсередини — зібрано в [робочому прикладі шва](guide:progarch/seams-and-boundaries/proj-dh-sensor-seam.md).

Це той самий об'єктний шов, який ми щойно ввели в означенні, і водночас — [інверсія залежностей](book:programming/dependency-inversion) у дії. DIP казав принцип: «залежи від абстракції, не від конкретного давача». Шов — це те, що цей принцип **купує**: готову точку підміни. Спільний інтерфейс `Sensor` — це [контракт](book:programming/design-by-contract), який мусить дотримати будь-хто, кого встромлять у шов: повертає температуру в градусах, не кидає виняток крізь межу. А те дрібне, що крізь шов проходить, — одне число-показник — і є найпростіший [DTO](book:programming/dto), пакет даних на межі. Чотири принципи модуля сходяться в одній точці, і точка ця має ім'я.

![Ліворуч давач вбито в політику — щоб підмінити, треба правити всередині; праворуч політика приймає давач через шов, а точка ввімкнення ззовні обирає, справжній чи підроблений під'єднати](/guide/progarch/structure-in-the-small/seams-and-boundaries/img/seam.svg)
*Без шва підміна означає правити захищений код; зі швом політика лишається недоторканою, а що саме крізь неї проходить, вирішує точка ввімкнення ззовні.*

## Три шви — за рівнем, де стається підміна

Об'єктний шов, який ми відкрили, — не єдиний. Фезерс розрізняє три роди швів, і різняться вони одним: **на якому рівні збірки програми ти встигаєш підмінити поведінку.**

**Об'єктний шов** (англ. *object seam*) — той, що ми щойно зробили. Підміна стається **під час виконання**, через поліморфізм: за спільним інтерфейсом стоять різні об'єкти, і який саме працює — вирішено при з'єднанні. Це найгнучкіший і найчистіший рід, синонім «впорскування залежності» (dependency injection), і саме до нього тягнешся першим, коли код у твоїх руках.

**Лінк-шов** (англ. *link seam*) — підміна на **етапі збірки чи лінкування**. Ти не чіпаєш вихідний код узагалі: підсовуєш інший об'єктний файл, іншу бібліотеку, або через `LD_PRELOAD` підміняєш функцію в уже скомпонованому бінарнику. Це рятує, коли джерела в тебе немає — чужа бібліотека, закритий модуль, — а поведінку її на час тесту треба замінити.

**Препроцесорний шов** (англ. *preprocessing seam*) — підміна **до компіляції**, текстом. У мовах із препроцесором C/C++ макрос `#define` чи `#ifdef` переписує сам текст програми, перш ніж його побачить компілятор:

```c
#ifdef TESTING
  #define read_sensor  fake_read_sensor   /* у тесті — інша функція */
#endif
```

Це найгрубіший рід — текстова заміна наосліп, легко заплутатися, — тож його лишають на крайній випадок, коли ні об'єктного, ні лінк-шва відкрити не вдається.

![Три роди швів на конвеєрі збірки: препроцесорний підміняє текст до компіляції, лінк-шов — об'єктний файл при збірці, об'єктний — об'єкт за інтерфейсом під час виконання](/guide/progarch/structure-in-the-small/seams-and-boundaries/img/seam-levels.svg)
*Що пізніше в житті програми ще можна відкрити шов, то менше початкового коду довелося зачепити — тому об'єктний шов зазвичай найзручніший.*

Логіка цієї трійці одна: чим **пізніше** на шляху від тексту до живого процесу ти ще здатен встромити підміну, тим менше вихідного коду мусив зачепити, щоб її дістати. Об'єктний шов дає підміну в останню мить, нічого не переписуючи наперед, — тому він і найзручніший.

> 🔧 **Навіщо це.** Найчастіша практична причина відкрити шов — обкласти тестом код, який тестувати «неможливо». Функція лізе в мережу, у годинник, у справжній давач — у тесті цього не хочеш. Знаходиш шов на тому вході, згодовуєш крізь нього підробку, що повертає передбачуване, — і от уже поведінку видно й перевірено, а самого коду ти не переписував. Коли [дійдемо до дублерів у тестах](guide:progarch/test-doubles-when), уся їхня механіка стоятиме саме на цьому: дублер — це те, що вставляють у шов.

## Шов — не лише для тестів

Тестами користь не вичерпується. Той самий отвір, крізь який у тест заходить підробка, у продакшені пускає й інше. Можна встромити в шов **зонд спостережності** — обгортку, що рахує виклики чи міряє час, не змінюючи поведінки. Можна крізь шов **поступово заміняти старе новим**: перемикач у точці ввімкнення пускає частину викликів на нову реалізацію, решту — на стару, і ти переносиш систему по шматку, а не одним стрибком. Шов — це загальна **точка керованої зміни**; тестування — лише найчастіший її вжиток.

## Скільки швів різати

Спокуса, знайома після кожного гарного інструмента, — понаставляти швів усюди «про запас». Не варто, і ти вже знаєш чому: [YAGNI](book:programming/dry-kiss-yagni) діє й тут. Кожен шов — це зобов'язання: зайвий інтерфейс, зайва точка ввімкнення, ще одна абстракція, яку треба тримати чесною. Порізати систему на сто пласких швів «щоб гнулося скрізь» — це та сама передчасна складність, від якої курс застерігав із першого дому.

Тому вправа роздвоюється. Перше — **упізнавати шви, які вже є задарма**: кожен параметр функції, кожна вже впорскнута залежність — це готовий шов, підміна крізь який нічого не коштує. Часто потрібний шов уже стоїть, просто його не бачили. Друге — **відкривати новий шов тоді, коли справжня зміна цього вимагає**, а не раніше. Це рівно урок v0: ми не кинулися розварювати зчеплення в перший вечір — ми **назвали**, де шва бракує, і відкрили його того дня, коли по-справжньому прийшла спальня з другим давачем. Шов ставлять не тому, що вміють, а тому, що є причина.

Ось чим шов завершує цей модуль. Зчеплення, приховування, інверсія, контракт — усі вони, кожен зі свого боку, будували ту саму річ: **місце, де систему можна змінити дешево.** Шов — це те місце, назване й перевірене одним питанням: чи можу я змінити поведінку тут, не редагуючи тут? Коли [Digital Homes уперше по-справжньому переріжуть межами](guide:progarch/dh-v1-modules), різатимуть саме по швах — і вже свідомо.
