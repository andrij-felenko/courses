# ⚙️ Інвентаризація підрослого хаба: знайти стан і стиснути його

Мінімальний хаб на двох змінних у пам'яті ми вже розбирали — і навіть той примудрився заховати два баги. Але справжній хаб двома змінними не живе. За рік він обростає: пристроїв уже не один, а десяток; у кожного — жива сесія з сокетом і часом останньої відповіді; розклад гріння лежить у файлі, щоб власник міг його правити; список пристроїв переїхав у базу; а щоб застосунок на телефоні відповідав миттєво, з'явився кеш статусів. Стан розповз по п'ятьох різних місцях — і жодне з них не кричить «я стан, стережися мене».

Ця вправа — систематичний обхід такого хаба. Спершу візьмемо його знімок і чесно випишемо **кожен** шматок стану в таблицю: час життя, охоплення, джерело правди, інваріант, єдиний писар. Уже сама таблиця тицьне пальцем у три хвороби. Тоді полагодимо їх робочим кодом — виведемо похідне замість зберігати, призначимо одного писаря, перенесемо критичний стан у тривкий запис, зведемо дубль до одного джерела. Ми не додаємо хабу можливостей; ми **прибираємо** з нього приховану пам'ять. Мета — не переписати систему наново, а натренувати око, яке за півгодини знаходить у чужому коді все, що згинатиме відповідь.

## Знімок: де осів стан

Ось фрагмент хаба, як він виглядає після року дописування. Кожен рядок, що заводить стан, я позначив коментарем — не тому, що так пишуть, а щоб інвентар було видно просто в коді:

:::tabs
```py
# hub.py — підрослий хаб Digital Homes (фрагмент): пристрої, розклад, БД, кеш
import json, sqlite3
from time import time as now

TIMEOUT_S = 90                          # мовчить довше — вважаємо офлайн
db = sqlite3.connect("hub.db")          # ← джерело правди про пристрої: на диску

class Device:                           # сесія пристрою — живе в ПАМʼЯТІ процесу
    def __init__(self, id, name, relay):
        self.id, self.name, self.relay = id, name, relay
        self.last_seen = 0.0
        self.online = False             # ← похідне від last_seen, а ЗБЕРІГАЄМО окремо
        self.temp = None

devices = {}                            # ← список у памʼяті: ДУБЛЬ таблиці devices
status_cache = {}                       # ← кеш статусів для застосунку: похідне
schedule = json.load(open("schedule.json"))   # ← розклад гріння: з ФАЙЛУ
heated_since = None                     # ← лічильник «2 год поспіль»: ТІЛЬКИ в памʼяті

def reload_devices():                   # тягнемо список із БД у памʼятний кеш
    devices.clear()
    for id, name, relay in db.execute("SELECT id, name, relay FROM devices"):
        devices[id] = Device(id, name, relay)

def poll():                             # опитувач: раз на виток питає кожен пристрій
    for d in devices.values():
        t = ping(d)                     # локальна змінна — живе один виток
        if t is not None:
            d.temp, d.last_seen, d.online = t, now(), True     # писар online №1
        status_cache[d.id] = {"temp": d.temp, "online": d.online, "ts": now()}

def on_push(msg):                       # пристрій сам штовхнув пакет
    d = devices.get(msg["id"])
    if d:
        d.last_seen, d.online = now(), True                    # писар online №2
        status_cache[d.id]["temp"] = msg["temp"]               # писар у кеш повз опитувач

def api_status(device_id):              # застосунок питає статус — читає кеш
    return status_cache.get(device_id)
```
```ts
// hub.ts — підрослий хаб Digital Homes (фрагмент): пристрої, розклад, БД, кеш
import Database from "better-sqlite3";
import { readFileSync } from "node:fs";

const TIMEOUT_S = 90;                       // мовчить довше — вважаємо офлайн
const db = new Database("hub.db");          // ← джерело правди про пристрої: на диску

class Device {                              // сесія пристрою — живе в ПАМʼЯТІ процесу
  lastSeen = 0;
  online = false;                           // ← похідне від lastSeen, а ЗБЕРІГАЄМО окремо
  temp: number | null = null;
  constructor(public id: number, public name: string, public relay: number) {}
}

const devices = new Map<number, Device>();  // ← список у памʼяті: ДУБЛЬ таблиці devices
const statusCache = new Map<number, any>(); // ← кеш статусів для застосунку: похідне
const schedule = JSON.parse(readFileSync("schedule.json", "utf8"));  // ← розклад: з ФАЙЛУ
let heatedSince: number | null = null;      // ← лічильник «2 год»: ТІЛЬКИ в памʼяті

function reloadDevices(): void {            // тягнемо список із БД у памʼятний кеш
  devices.clear();
  for (const r of db.prepare("SELECT id, name, relay FROM devices").all() as any[])
    devices.set(r.id, new Device(r.id, r.name, r.relay));
}

function poll(): void {                     // опитувач: раз на виток питає кожен пристрій
  for (const d of devices.values()) {
    const t = ping(d);                      // локальна змінна — живе один виток
    if (t !== null) { d.temp = t; d.lastSeen = Date.now(); d.online = true; }  // писар online №1
    statusCache.set(d.id, { temp: d.temp, online: d.online, ts: Date.now() });
  }
}

function onPush(msg: { id: number; temp: number }): void {   // пристрій штовхнув пакет
  const d = devices.get(msg.id);
  if (d) {
    d.lastSeen = Date.now(); d.online = true;                 // писар online №2
    statusCache.get(msg.id).temp = msg.temp;                  // писар у кеш повз опитувач
  }
}

function apiStatus(deviceId: number) {      // застосунок питає статус — читає кеш
  return statusCache.get(deviceId);
}
```
:::

Прочитаймо, що тут насправді живе, від найтихішого до найгучнішого. `t` в опитувачі — **локальна змінна**: народжується на витку, вмирає з ним, ніхто інший її не бачить, клопоту з нею нуль. `last_seen`, `online`, `temp` у кожного `Device` — **поле сесії в пам'яті**: живе, поки живий об'єкт, і його бачать усі, хто має посилання на пристрій. `schedule` завантажений **з файлу**: переживе перезапуск, і його редагує не лише хаб, а й власник через застосунок. `devices` у пам'яті **дублює** рядки таблиці `devices` у базі. `status_cache` — **похідний** зліпок, порахований з пристроїв і відданий телефону. А `heated_since` — той самий критичний лічильник, що й у мінімальному хабі, тільки тепер загублений серед іншого.

Сім шматків, кожен зі своєю природою. Поки вони просто перелічені, вони виглядають рівнозначними. Мапа з двох осей — час життя й охоплення — миттєво розводить їх за ризиком.

## Інвентар: таблиця на сім рядків

Зведімо знімок у таблицю. Для кожного шматка — п'ять питань: скільки він живе, хто його бачить, де його справжнє джерело правди, який [інваріант](book:programming/invariants) він мусить берегти (умова, що має лишатися істинною за будь-яких коректних даних), і хто **єдиний** має право його міняти. Остання колонка — найважливіша: порожнє чи подвоєне «хто писар» майже завжди і є хвороба.

| Шматок стану | Час життя | Охоплення | Джерело правди | Інваріант | Єдиний писар? |
|---|---|---|---|---|---|
| `t`, `want_on` | виклик | 1 функція | давач (жива відповідь) | — | так |
| `dev.temp`, `dev.last_seen` | процес | усі, хто має пристрій | сам пристрій | `last_seen` лише зростає | так (опитувач і push пишуть той самий факт) |
| `dev.online` | процес | усі, хто має пристрій | **виводиться** з `last_seen` | `online ⇔ недавно відповідав` | **ні — два писарі** |
| `schedule` (файл) | тривкий | увесь процес + застосунок | файл `schedule.json` | години валідні, `t` у межах | **питання: і хаб, і застосунок** |
| `devices` (пам'ять) | процес | увесь процес | **БД `devices`** (дубль) | збігається з БД | **ні — дубль джерела** |
| `status_cache` | процес | застосунок через API | **виводиться** з пристроїв | не старіший за `TIMEOUT_S` | **ні — три писарі** |
| `heated_since` | процес *(мусить бути тривким)* | критичний | має бути тривкий запис | не обнуляється рестартом | ні — гине з процесом |

Таблиця сама себе прочитала. Перший рядок зелений — локальні змінні не варті й секунди уваги. А от нижні п'ять світяться. Розставмо їх на тих самих двох осях, що й абстрактну мапу зі статті, — і побачимо ту саму картину, але вже з іменами файлів і змінних:

![Мапа стану підрослого хаба на двох осях: горизонталь — час життя (виклик → процес → тривкий на диску), вертикаль — охоплення (одна функція → поле сесії → увесь процес → застосунок). Зеленими у безпечних кутах — локальні змінні та список пристроїв у БД як джерело; бурштиновими — dev.online (похідне, збережене), devices у пам'яті (дубль БД) і schedule.json (два писарі); червоними в найдорожчих кутах — status_cache (друга правда) і heated_since (мусить бути тривким, а живе в пам'яті)](/guide/progarch/structure-in-the-small/state-inventory/img/hub-state-map.svg)
*Той самий інвентар, тепер на конкретному хабі. Ліворуч унизу — тихі локальні змінні, з якими нема мороки. Праворуч угорі, де стан широкий і довговічний, зібралися всі клопоти: кеш, що став другою правдою; лічильник, чиє місце на диску, а живе в пам'яті; список, роздвоєний між базою й пам'яттю. Червоне й бурштинове — це список того, що зараз рефакторитимемо.*

Три хвороби видно прямо з колонки «єдиний писар»: у `dev.online` та `status_cache` писарів кілька; `devices` роздвоєний на джерело й копію; `heated_since` живе не там, де мусить. Полікуємо кожну — по черзі, робочим кодом.

## Рефакторинг

### Вивести похідне замість зберігати

Перший і найдешевший хід: `dev.online` **не зберігати взагалі**. Онлайн-пристрій — це не окремий факт, а висновок з одного-єдиного факту «коли ми востаннє про нього чули». Тримати булеву поруч із `last_seen` — це тримати другу копію того, що вже є, і потім ганятися, щоб копія не збрехала. Обидва писарі прапорця зникнуть самі, щойно писати стане нічого:

:::tabs
```py
class Device:
    def __init__(self, id, name, relay):
        self.id, self.name, self.relay = id, name, relay
        self.last_seen = 0.0            # ЄДИНИЙ факт, який пишемо
        self.temp = None

    @property
    def online(self):                  # похідне: рахуємо на льоту, а не зберігаємо
        return now() - self.last_seen < TIMEOUT_S
```
```ts
class Device {
  lastSeen = 0;                        // ЄДИНИЙ факт, який пишемо
  temp: number | null = null;
  constructor(public id: number, public name: string, public relay: number) {}

  get online(): boolean {              // похідне: рахуємо на льоту, а не зберігаємо
    return Date.now() - this.lastSeen < TIMEOUT_S * 1000;
  }
}
```
:::

Дивись, що зникло разом із полем. Зник цілий інваріант, який ми мусили тримати вручну, — «`online` збігається з `last_seen`». Тепер він виконується **за побудовою**: `online` не може розійтися з `last_seen`, бо він і є `last_seen`, тільки прочитаний іншими очима. Обидва писарі — опитувач і push — тепер чіпають лише `last_seen`, той самий монотонний час, і сваритися їм більше нема за що. Найдешевший стан — той, якого немає; ми щойно прибрали одне поле й один клас багів разом із ним.

### Один писар на комірку

`status_cache` небезпечніший. У знімку в нього **троє** пишуть: опитувач кладе повний зліпок, `on_push` домальовує температуру збоку (та ще й через `status_cache[d.id]["temp"]`, що впаде помилкою, якщо опитувач ще жодного разу не заходив), а завтра якийсь «оптимістичний» рядок у застосунку захоче тицьнути в кеш напряму, щоб кнопка реагувала швидше. Три писарі на один кеш — це три версії правди, що чекають нагоди розійтися.

Ліки — замкнути кеш за одними дверима. Кеш стає об'єктом з **однією** точкою запису, і та точка завжди рахує значення **з пристрою**, а не приймає його збоку. Хто завгодно може попросити кеш оновитися по пристрою; ніхто не може вписати в кеш число від себе:

:::tabs
```py
class StatusView:
    """Похідний погляд на пристрої для застосунку. Записати можна лише З ПРИСТРОЮ."""
    def __init__(self):
        self._by_id = {}

    def refresh(self, d):                       # ЄДИНИЙ шлях запису — завжди з пристрою
        self._by_id[d.id] = {"temp": d.temp, "online": d.online, "ts": now()}

    def get(self, device_id):                   # усі інші лише читають
        row = self._by_id.get(device_id)
        if row and now() - row["ts"] > TIMEOUT_S:
            return {**row, "stale": True}        # свіжість позначена, а не прихована
        return row
```
```ts
class StatusView {
  private byId = new Map<number, any>();

  refresh(d: Device): void {                    // ЄДИНИЙ шлях запису — завжди з пристрою
    this.byId.set(d.id, { temp: d.temp, online: d.online, ts: Date.now() });
  }

  get(deviceId: number) {                       // усі інші лише читають
    const row = this.byId.get(deviceId);
    if (row && Date.now() - row.ts > TIMEOUT_S * 1000)
      return { ...row, stale: true };           // свіжість позначена, а не прихована
    return row;
  }
}
```
:::

Тепер і `poll`, і `on_push` після того, як оновили сам пристрій, кличуть `status.refresh(d)` — і кеш ніколи не тримає числа, якого нема в пристрої. Він фізично не може стати другою правдою, бо в нього нема способу набути значення повз пристрій. А позначка `stale` знімає останню пастку кешу: замість тихо віддавати протухле число, він каже вголос «це старе». Один писар не просто прибирає перегони — він робить кеш чесним похідним, яким кеш і мусить бути.

> 🔧 **Навіщо це.** «Один писар на комірку» — це не про акуратність, а про те, скільки місць треба тримати в голові, щоб пояснити значення. Поки в кеш пишуть троє, відповідь на питання «звідки тут це число?» — «з одного з трьох місць, залежно від того, хто встиг останнім». Після замикання відповідь одна: «порахувалося з пристрою, ось у цей момент часу». Ти звів охоплення писання з «будь-хто звідусіль» до «одна функція» — і зсунув кеш по вертикальній осі мапи вниз, у безпечніший кут, не чіпаючи жодної можливості.

### Критичний стан — у тривкий запис

`heated_since` — той самий баг, що й у мінімальному хабі, і тут ми доводимо його до кінця. Захисна межа «не гріти довше двох годин поспіль» рахує час від цієї змінної. А змінна живе в пам'яті процесу. Отже, кожен перезапуск — збій живлення, викочення нової версії, звичайний краш — нишком обнуляє дволітровий лічильник. Деплой раз на годину, і «безпека» не спрацює жодного разу, поки в кімнаті пече.

Правило з інвентаря пряме: якщо стан **мусить пережити процес**, то це не змінна, а тривкий запис. Кладемо лічильник на диск — у той самий `hub.db`, поруч із пристроями, — і рахуємо межу від нього:

:::tabs
```py
MAX_RUN_S = 2 * 3600

def set_heating_since(ts):                       # тривкий запис — переживе рестарт
    db.execute("INSERT OR REPLACE INTO kv(k, v) VALUES ('heated_since', ?)", (ts,))
    db.commit()

def heating_since():
    row = db.execute("SELECT v FROM kv WHERE k = 'heated_since'").fetchone()
    return row[0] if row else None

def guard():                                     # межа рахує від ДИСКА, не від памʼяті
    since = heating_since()
    if relay_is_on() and since and now() - since > MAX_RUN_S:
        relay_off(); set_heating_since(None)
```
```ts
const MAX_RUN_S = 2 * 3600;

function setHeatingSince(ts: number | null): void {   // тривкий запис — переживе рестарт
  db.prepare("INSERT OR REPLACE INTO kv(k, v) VALUES ('heated_since', ?)").run(ts);
}

function heatingSince(): number | null {
  const row = db.prepare("SELECT v FROM kv WHERE k = 'heated_since'").get() as any;
  return row ? row.v : null;
}

function guard(): void {                               // межа рахує від ДИСКА, не від памʼяті
  const since = heatingSince();
  if (relayIsOn() && since && Date.now() / 1000 - since > MAX_RUN_S) {
    relayOff(); setHeatingSince(null);
  }
}
```
:::

Тепер перезапуск нічого не забуває: хаб піднявся, прочитав `heated_since` з диска й побачив, що гріє вже півтори години, — межа спрацює вчасно. Але зверни увагу на `relay_is_on()` у `guard`: піднявшись, хаб питає **реле у світі**, а не вірить своїй пам'яті. Це той самий хід, що й з `online`, тільки назовні: «увімкнено чи ні» — теж похідне, і його джерело правди — реле, а не змінна, яку рестарт скинув у `False`. Критичний стан ми поклали на диск; похідний від світу — читаємо зі світу.

### Звести дубль до одного джерела

Лишився `devices`, роздвоєний між таблицею в базі та словником у пам'яті. Сам по собі пам'ятний словник — не гріх: це кеш, щоб не бити в базу щовитка. Гріх починається тоді, коли в цей кеш **пишуть окремо** від бази. Уяви цілком природний рядок «додати пристрій»:

```py
# ❌ Як НЕ треба: пишемо в памʼять, забувши про джерело.
devices[new_id] = Device(new_id, name, relay)     # памʼять знає про пристрій
# ...а в БД його нема. Перезапуск — і пристрій зник, наче й не було.
```

Пам'ять і база розійшлися тієї ж миті, а перезапуск зробив розбіжність видимою: `reload_devices` перечитав базу, і доданий пристрій випарувався. Лікування — залізне правило «пиши в джерело, читай із похідного»: будь-яка зміна списку йде **в базу**, а пам'ятний словник лише перечитує її, ніколи не редагується напряму:

:::tabs
```py
def add_device(name, relay):
    db.execute("INSERT INTO devices(name, relay) VALUES (?, ?)", (name, relay))
    db.commit()                        # пишемо в ДЖЕРЕЛО (БД)
    reload_devices()                   # памʼять — лише перечитане похідне, не другий запис
```
```ts
function addDevice(name: string, relay: number): void {
  db.prepare("INSERT INTO devices(name, relay) VALUES (?, ?)").run(name, relay);  // ДЖЕРЕЛО
  reloadDevices();                     // памʼять — лише перечитане похідне, не другий запис
}
```
:::

Тепер у списку пристроїв рівно одне джерело правди — база, — а словник у пам'яті чесно те, чим і мав бути: похідна копія, у яку **ніхто не пише окремо**. Той самий рецепт, що й із кешем статусів: одне джерело, решта виводиться; ніхто не редагує похідне повз джерело. Дубль лишився (копія в пам'яті нікуди не поділася й далі економить звернення до бази), але він перестав бути **другою правдою** — став просто швидшим поглядом на першу.

## Складність і пастки

Полагодивши три хвороби, назвемо дві пастки, у які ця вправа втрапляє найчастіше, — бо обидві виглядають як розумна оптимізація, аж поки не куснуть.

**Кеш як друга правда.** Найпоширеніший. Кеш заводять заради швидкості й дуже скоро починають у нього **писати** — то «оптимістично» оновити статус, щоб кнопка в застосунку реагувала миттєво, то домалювати поле збоку, як робив наш `on_push`. Тієї ж миті кеш перестає бути похідним і стає окремим джерелом, яке дрейфує від світу: застосунок бадьоро показує «обігрівач увімкнено», бо хтось тицьнув у кеш, а реле тим часом вимкнене. Це прихована форма [зчеплення](book:programming/coupling-cohesion) — далекий рядок в UI тихо змінює те, що мало би визначатися лише пристроєм. Ліки ми вже застосували: у кеш є рівно один шлях запису, і той завжди рахує з джерела; свіжість позначена, а не прихована. Якщо очевидно кортить писати в кеш напряму заради відгуку — це сигнал, що тобі потрібен не другий запис, а швидший перерахунок або чесний «оптимістичний» шар, який знає, що він тимчасовий, і сам себе звіряє з джерелом.

**Лічильник, що гине з процесом.** Другий підступніший, бо мовчазний. Будь-яке число, що **накопичується** і живе лише в пам'яті, тихо обнуляється на кожному рестарті — і майже завжди в найгірший бік. Наш `heated_since` дав обігрівачу гріти вічно повз двогодинну межу. Але та сама пастка має родину: лічильник «спалено за сьогодні» занижує рахунок після кожного деплою; кошик токенів rate-limit наливається по вінця при перезапуску, і сусід продавлює твій ліміт, просто дочекавшись викочення; лічильник спроб ретраю забуває, що вже тричі обпікся. Спільний корінь один: значення, яке **мусить пережити процес**, тримали як звичайну змінну. Правило-фільтр коротке — постав кожному лічильнику питання «що станеться, якщо процес перезапуститься саме зараз?». Якщо відповідь гірша за «нічого» — це тривкий стан, не змінна: клади на диск, рахуй від диска, роби запис ідемпотентним, щоб краш посеред нього не подвоїв число, і на старті **перечитуй світ**, а не довіряй свіжообнуленій пам'яті.

Обидві пастки — дзеркальні половини однієї дисципліни. Кеш каже: не давай похідному стати джерелом. Лічильник каже: не давай джерелу жити там, звідки його здуває перезапуск. Між ними — уся вправа: кожен шматок стану або джерело, і тоді йому місце в тривкому записі з одним писарем, або похідне, і тоді його не зберігають, а виводять. Третього стану, який «трохи джерело, трохи копія», не буває — саме він і є баг.

## Що лишилося в руках

Ми пройшли підрослий хаб рядок за рядком і зробили з ним рівно те, що обіцяла мапа. Локальні змінні лишили як є — з ними нема клопоту. `dev.online` **вивели** замість зберігати, і цілий інваріант почав триматися за побудовою. `status_cache` замкнули за **одним писарем**, і кеш перестав уміти брехати. `heated_since` **перенесли** з волатильної пам'яті в тривкий запис, і двогодинна межа нарешті пережила деплой. `devices` **звели** до одного джерела — база пише, пам'ять лише виводить.

Жоден із цих ходів не додав хабу можливостей і не забрав жодної — кімнати гріються так само. Змінилося інше: тепер про кожен шматок стану можна за секунду сказати, скільки він живе, хто його бачить і хто єдиний його пише. Це й є вся навичка. Спершу — назвати стан таблицею, потім — стиснути його чотирма ходами до двох чесних видів: тривке джерело з одним писарем і похідне, яке виводять, а не бережуть. Куди саме зганяти те неминуче джерело, щоб решта програми лишалася чистими функціями над значеннями, — розбирає крок про [функціональне ядро й імперативну оболонку](book:programming/functional-core-imperative-shell); але половину роботи ти вже зробив тут, самим тим, що перестав тримати правду у двох місцях.
