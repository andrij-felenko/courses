# ⚙️ Кліп як довга операція: від POST до згорілого посилання

Форма в нас уже є: операція — ресурс, робота живе в черзі, стан і поступ — рядок у сховищі, результат тлінний. Але форма, яку не можна запустити, — це діаграма, а не система. Щойно сідаєш будувати її по-справжньому — від обробника `POST` до згорілого посилання, — вилазять три місця, де наївна збірка мовчки ламається, і жодне з них на діаграмі не видно. **Де саме розв'язується гонка двох однакових запитів. Що рівно пише робітник, щоб рядок не збрехав про мертву роботу. Хто, зрештою, видаляє файл.** Тут ми збудуємо всі три — трьома дійовими особами: крайовий обробник, рядок у сховищі, робітник контексту **Відео**. Крайовий обробник і читання — мовами, якими DH говорить із застосунком (TypeScript і Python); цикл робітника — з ними ж, і поруч **Go**, де серцебиття на таймері й скасування через `select` — рідна говірка мови.

## Один рядок — і операція, і задача

Перше рішення, яке діаграма ховає: **чим є черга?** Спокуса — завести окрему чергу (Kafka, Redis, SQS) і класти в неї задачу після того, як створив рядок операції. Але тоді два записи в дві різні системи мусять статися **атомарно**: створив операцію, а поставити задачу не встиг (упав між ними) — і рядок навіки застряг у `queued`, задачі по нього нема. Це класична біда двох записів, і латають її окремим механізмом (транзакційна скринька-`outbox`).

Ми оминемо всю цю халепу одним ходом: **той самий рядок операції і є задачею в черзі.** Створити операцію — це вставити рядок зі станом `queued`; забрати задачу — це знайти найстаріший рядок у стані `queued` й перевести його в `running`. Одна вставка робить обидві справи, атомарність — задарма. Ось таблиця, у якій операція-ресурс і задача-черги — та сама сутність:

```sql
CREATE TABLE operations (
  id               text PRIMARY KEY,            -- op-42 у /operations/{id}
  idempotency_key  text UNIQUE NOT NULL,        -- ← один намір = один рядок (гонку розсудить індекс)
  status           text NOT NULL DEFAULT 'queued'
                   CHECK (status IN ('queued','running','succeeded','failed','canceled')),
  request          jsonb NOT NULL,              -- {cameraId, from, to} — що саме просили
  progress         int  NOT NULL DEFAULT 0,     -- 0..100, поки running
  result           jsonb,                       -- {url, expiresAt} — коли succeeded
  error            jsonb,                       -- {code, message} — коли failed
  cancel_requested boolean NOT NULL DEFAULT false,
  -- поля черги (той самий рядок працює й задачею):
  lease_id         text,                        -- жетон поточної оренди — НОВИЙ на кожен забір
  lease_expires_at timestamptz,                 -- доки триває оренда цього робітника
  attempt          int  NOT NULL DEFAULT 0,     -- скільки разів задачу забирали
  user_id          text NOT NULL,               -- кому слати пуш наприкінці
  created_at       timestamptz NOT NULL DEFAULT now(),
  expires_at       timestamptz NOT NULL         -- коли прибрати сам запис операції
);

-- індекс для забору: цікаві лише ті, що чекають або чия оренда згасла
CREATE INDEX ops_claimable ON operations (created_at)
  WHERE status IN ('queued','running');
```

Дві колонки тут несуть усю вагу решти вставки. `idempotency_key UNIQUE` — це те, що не дасть завести дві операції на один намір: індекс — арбітр гонки, і за мить ми побачимо, як саме. А `lease_id` разом із `lease_expires_at` — це те, що не дасть операції збрехати про мертвого робітника: жетон оренди, який робітник носить у кожному записі, і строк, по якому оренда згасає, якщо серце перестало битися.

## 202 за двадцять мілісекунд — і жоден ключ не пройде двічі

Обробник `POST` мусить зробити три речі й жодної зайвої: завести операцію, дедуплікувати за ключем, віддати `202` з адресою. Уся хитрість — у слові «дедуплікувати», бо саме тут ховається гонка. Наївний код питає «чи є вже операція з таким ключем?», не бачить її й вставляє свою. Але два однакові запити (палець тицьнув двічі; телефон [сам повторив на поганій мережі команду з ключем ідемпотентності](guide:progarch/dh-bad-network)) біжать **паралельно**: обидва питають, обидва не бачать, обидва вставляють — і ми маємо дві операції й подвійний рендер. Це перегони «перевірив-тоді-зроби» ([TOCTOU: між перевіркою й дією стан змінюється](book:programming/data-races-locks)), і латати їх перевіркою в коді — гнатися за власним хвостом.

Розв'язок — не перевіряти в коді взагалі, а **дати арбітром базу**. `UNIQUE(idempotency_key)` фізично не дозволить двом рядкам мати той самий ключ; лишається одним запитом спробувати вставити й чемно прийняти відмову, якщо хтось випередив. У Postgres це `INSERT … ON CONFLICT DO NOTHING RETURNING`: вставка або кладе рядок і повертає його, або, наткнувшись на зайнятий ключ, тихо повертає нуль рядків:

:::tabs
```ts
// POST /cameras/:id/clips — прийняти, дедуплікувати за ключем, віддати 202 + Location.
app.post("/cameras/:id/clips", async (req, res) => {
  const key = req.header("Idempotency-Key");
  if (!key) return res.status(400).json({ code: "missing_idempotency_key" });

  const request = { cameraId: req.params.id, from: req.body.from, to: req.body.to };
  const id = "op-" + newId();

  // ОДНА вставка = і операція, і задача в черзі. UNIQUE(idempotency_key) розсудить гонку.
  const rows = await db.query(
    `INSERT INTO operations (id, idempotency_key, status, request, user_id, expires_at)
     VALUES ($1, $2, 'queued', $3, $4, now() + interval '30 days')
     ON CONFLICT (idempotency_key) DO NOTHING
     RETURNING id`,
    [id, key, request, req.userId]);

  if (rows.length === 1) {                       // ми ВИГРАЛИ гонку: рядок наш, рендер у черзі
    res.setHeader("Location", `/operations/${id}`);
    return res.status(202).json({ id, status: "queued" });
  }

  // 0 рядків → хтось із тим самим ключем нас випередив. Читаємо ЙОГО операцію.
  const { rows: [op] } = await db.query(
    `SELECT id, request FROM operations WHERE idempotency_key = $1`, [key]);

  // той самий ключ, але інші параметри — це помилка клієнта, а не мовчазний підмін наміру
  if (!sameRequest(op.request, request))
    return res.status(422).json({ code: "idempotency_key_reused" });

  res.setHeader("Location", `/operations/${op.id}`);
  return res.status(202).json({ id: op.id, status: "queued" });   // ТА САМА операція
});
```
```py
# POST /cameras/{camera_id}/clips — прийняти, дедуплікувати за ключем, віддати 202 + Location.
@app.post("/cameras/{camera_id}/clips", status_code=202)
async def create_clip(camera_id: str, body: ClipRequest, req: Request, resp: Response):
    key = req.headers.get("Idempotency-Key")
    if not key:
        raise HTTPException(400, "missing_idempotency_key")

    request = {"cameraId": camera_id, "from": body.from_, "to": body.to}
    op_id = "op-" + new_id()

    # ОДНА вставка = і операція, і задача в черзі. UNIQUE(idempotency_key) розсудить гонку.
    row = await db.fetchrow(
        """INSERT INTO operations (id, idempotency_key, status, request, user_id, expires_at)
           VALUES ($1, $2, 'queued', $3, $4, now() + interval '30 days')
           ON CONFLICT (idempotency_key) DO NOTHING
           RETURNING id""",
        op_id, key, request, req.state.user_id)

    if row is not None:                          # ми ВИГРАЛИ гонку: рядок наш, рендер у черзі
        resp.headers["Location"] = f"/operations/{op_id}"
        return {"id": op_id, "status": "queued"}

    # 0 рядків → нас випередили тим самим ключем. Читаємо ЇХНЮ операцію.
    op = await db.fetchrow(
        "SELECT id, request FROM operations WHERE idempotency_key = $1", key)
    if not same_request(op["request"], request):  # той самий ключ, інші параметри — помилка клієнта
        raise HTTPException(422, "idempotency_key_reused")

    resp.headers["Location"] = f"/operations/{op['id']}"
    return {"id": op["id"], "status": "queued"}    # ТА САМА операція
```
:::

Придивімося, що робить база, коли обидва запити натрапляють на індекс тієї самої миті. Один — назвімо його A — вставляє першим, індекс приймає його ключ. Другий, B, зі своїм `INSERT` **упирається в той самий ключ і зупиняється** просто на рівні індексу: у режимі `READ COMMITTED` його вставка чекає, поки транзакція A закомітиться або відкотиться. Закомітилась — `DO NOTHING` бачить конфлікт, повертає B нуль рядків, і наступним запитом B **читає** вже видимий рядок A. Відкотилась (A упав) — вставка B проходить, і власником стає він. У кожному разі народжується **рівно одна** операція, а другий обробник віддає адресу тієї самої. Ніякого коду-перевірки — арбітраж зробив унікальний індекс.

![Дві доріжки запитів A і B з тим самим ключем K. A: POST → INSERT ON CONFLICT DO NOTHING RETURNING → повертає 1 рядок (op-42), виграв, ставить у чергу → 202 з Location на op-42. B: POST з тим самим ключем → INSERT блокується на унікальному індексі, поки A не закомітить → повертає 0 рядків → SELECT за ключем дістає ту саму op-42 → 202 з Location на ту саму op-42. Між доріжками — пунктир «A комітить → індекс відпускає B»](/guide/progarch/nodes-time-jobs-async/dh-long-ops/img/idempotency-race.svg)

*Унікальний індекс пропускає першого й тримає другого, поки перший не закомітить; тоді другий бачить нуль рядків і читає ту саму операцію. Два однакові запити зливаються в один намір — і рендер стається рівно раз, без жодної перевірки в коді.*

> 🔧 **Навіщо це.** Гонку дедуплікації розв'язуй **там, де вже є атомарність, — у сховищі**, а не перевіркою «спершу глянь, чи є» у застосунку: між твоїм `SELECT` і `INSERT` завжди влізе другий запит. Унікальний індекс серіалізує вставки безкоштовно й без гонки; твоя робота — лише чемно прийняти «нуль рядків» як «мене випередили» й дочитати чужу операцію. І одна тонкість, яку легко проґавити: [ідемпотентний ключ](book:programming/idempotency) прив'язаний до **наміру**, тож той самий ключ із іншими параметрами — це не повтор, а помилка клієнта; мовчки віддати стару операцію на новий запит гірше за чесний `422`.

## Подивитися й передумати

Операція є — тепер клієнтові треба два дієслова понад «створити»: **глянути** й **скасувати**. Обидва — короткі обробники, але кожен має свою пастку.

`GET` для поллінгу — чисте читання, і саме тому воно безпечне: клієнт [полить із відступом — 2, 4, 8 секунд](guide:progarch/polling-vs-callback), і жоден повтор нічого не псує. Єдине, про що не можна забути, — заборонити кеш: проксі, що закешує проміжний `progress: 45`, показуватиме сорок п'ять відсотків і по завершенні. Скасування ж — не читання, а натяк: воно **не вбиває** роботу, лише лишає прапорець, який робітник помітить між шматками. Якщо операція ще в черзі — гасимо її одразу; якщо вже біжить — ставимо `cancel_requested`, і хай робітник спиниться сам на межі наступного шматка:

:::tabs
```ts
// GET /operations/:id — чисте читання; клієнт полить із відступом. Кеш заборонено.
app.get("/operations/:id", async (req, res) => {
  const op = await repo.find(req.params.id);
  if (!op) return res.status(404).end();
  res.setHeader("Cache-Control", "no-store");
  res.json({ id: op.id, status: op.status, progress: op.progress,
             result: op.result, error: op.error });
});

// POST /operations/:id:cancel — кооперативно: queued гасне одразу, running лишає прапорець.
app.post("/operations/:id\\:cancel", async (req, res) => {
  await db.query(
    `UPDATE operations
        SET status = CASE WHEN status = 'queued' THEN 'canceled' ELSE status END,
            cancel_requested = true
      WHERE id = $1 AND status IN ('queued','running')`, [req.params.id]);
  res.status(202).end();                          // «прийнято до скасування», не «скасовано»
});
```
```py
# GET /operations/{op_id} — чисте читання; клієнт полить із відступом. Кеш заборонено.
@app.get("/operations/{op_id}")
async def get_operation(op_id: str, resp: Response):
    op = await repo.find(op_id)
    if op is None:
        raise HTTPException(404)
    resp.headers["Cache-Control"] = "no-store"
    return {"id": op.id, "status": op.status, "progress": op.progress,
            "result": op.result, "error": op.error}

# POST /operations/{op_id}:cancel — кооперативно: queued гасне одразу, running лишає прапорець.
@app.post("/operations/{op_id}:cancel", status_code=202)
async def cancel_operation(op_id: str):
    await db.execute(
        """UPDATE operations
              SET status = CASE WHEN status = 'queued' THEN 'canceled' ELSE status END,
                  cancel_requested = true
            WHERE id = $1 AND status IN ('queued','running')""", op_id)
    return {"status": "canceling"}                 # «прийнято до скасування», не «скасовано»
```
:::

Зверни увагу на `202` у відповіді на скасування — не `200`. Скасувати довгу операцію теж **не миттєво**: ми пообіцяли передати намір, а не виконати його тут-таки. Ця чесність коду — «прийнято до скасування» — уся в різниці двох станів: `canceling` (прапорець стоїть, робота ще доходить до межі шматка) і `canceled` (робітник справді спинився). Клієнт, який хоче побачити кінець, і далі полить `GET`.

## Робітник, що не має права збрехати

Ось серце вставки. Робітник у контексті **Відео** крутить один цикл: забери задачу, тримай оренду серцебиттям, між шматками перевіряй скасування й стелю часу, наприкінці — поклади результат і штовхни пуш. Скелет цього циклу ми вже бачили, але скелет ховав три речі, які «робочий код» мусить сказати вголос.

**Перша: забір задачі — атомарний.** Знайти найстарішу `queued` (або `running`, чия оренда згасла, — це мертвий робітник, якого перехоплюємо) і тим самим запитом перевести її в `running`, поставивши свіжий жетон оренди. Ключ — `FOR UPDATE SKIP LOCKED`: він блокує рядок для нас і **перестрибує** рядки, уже взяті іншими робітниками, тож десяток робітників розбирає чергу без штовханини й без того, щоб двоє схопили одну задачу. (Postgres дав `SKIP LOCKED` у версії 9.5, випущеній 2016 року, MySQL — у 8.0 — саме під такі черги-в-таблиці.)

```sql
-- Claim: атомарно забрати задачу й поставити СВІЖИЙ жетон оренди $2.
UPDATE operations SET
  status           = 'running',
  lease_id         = $2,                          -- новий жетон на кожен забір (фенс на майбутнє)
  lease_expires_at = now() + ($3 || ' seconds')::interval,
  attempt          = attempt + 1
WHERE id = (
  SELECT id FROM operations
   WHERE status = 'queued'
      OR (status = 'running' AND lease_expires_at < now())   -- перехопити мертвого робітника
   ORDER BY created_at
   FOR UPDATE SKIP LOCKED                          -- перестрибнути вже взяті іншими
   LIMIT 1)
RETURNING id, request, attempt, lease_id, user_id;
```

**Друга: серцебиття — на таймері, а не між шматками.** У скелеті серцебиття стояло після кожного шматка. Але один шматок може виявитися довшим за всю оренду — і тоді, поки триває перекодування одного важкого відрізка, оренда згасне, і жива робота дістане удар у спину: її перехопить другий робітник. Тому серцебиття мусить жити **окремо, за годинником**, незалежно від того, скільки триває шматок. А кооперативні перевірки — скасування й дедлайн — навпаки, доречні саме між шматками, бо це точки, де роботу безпечно урвати. Розділення чітке: **живучість — за часом, зупинка — за згодою.**

**Третя: кожен запис робітника несе жетон-фенс.** Серцебиття, завершення, невдача — усі оновлюють рядок лише за умови `WHERE lease_id = мій`. Якщо робітника перехопили (новий забір поставив інший `lease_id`), його оновлення торкнеться **нуля рядків** — і він дізнається, що більше не власник, саме з цього нуля. Це той самий [жетон-загорожа проти застряглого власника](book:programming/optimistic-locking), тільки роль монотонного жетона грає свіжий `lease_id` кожного забору: спізнілий не пройде, бо в рядку вже інший жетон.

Ось цикл цілком. Go веде — таймер, `select` і `context`-дедлайн тут ідіоматичні; TypeScript і Python дзеркалять його стеком застосунку:

:::tabs
```go
// Робітник у контексті Відео: забрати, тримати оренду, урвати за згодою, закрити чесно.
const (
	leaseTTL  = 30 * time.Second
	beatEvery = 10 * time.Second // втричі частіше за оренду → переживе один пропуск серцебиття
	hardCap   = 5 * time.Minute
	maxTries  = 3
)

func (w *Worker) runOne(parent context.Context) (bool, error) {
	op, ok, err := w.store.Claim(parent, w.id, leaseTTL) // атомарний SELECT…SKIP LOCKED + UPDATE
	if err != nil || !ok {
		return false, err // черга порожня — піти поспати
	}
	if op.Attempt > maxTries { // падало забагато разів — закриваємо чесною помилкою
		w.store.Finish(parent, op.ID, op.LeaseID, "failed", nil, &OpError{Code: "too_many_attempts"})
		return true, nil
	}

	// Тверда стеля тривалості на МОНОТОННОМУ годиннику: WithTimeout рахує від time.Now(),
	// таймер рантайму глухий до стрибків настінного часу й корекцій NTP.
	ctx, cancel := context.WithTimeout(parent, hardCap)
	defer cancel()

	// Серцебиття у власній горутині — ЗА ГОДИННИКОМ, не між шматками: подовжує оренду,
	// несе поступ і саме воно ловить фенс.
	var progress atomic.Int64
	beat := time.NewTicker(beatEvery)
	defer beat.Stop()
	go func() {
		for {
			select {
			case <-ctx.Done():
				return
			case <-beat.C:
				mine, _ := w.store.Heartbeat(ctx, op.ID, op.LeaseID, int(progress.Load()), leaseTTL)
				if !mine { // 0 рядків → нас перехопили (у рядку інший lease_id) → фенс
					cancel() // рвемо ctx — головний цикл побачить це на межі шматка
					return
				}
			}
		}
	}()

	for _, chunk := range planChunks(op.Request) {
		select {
		case <-ctx.Done(): // стеля часу, фенс або зупинка процесу — НЕ пишемо succeeded
			return true, nil
		default:
		}
		if canceled, _ := w.store.CancelRequested(ctx, op.ID); canceled {
			w.store.Finish(ctx, op.ID, op.LeaseID, "canceled", nil, nil)
			return true, nil
		}
		if err := transcode(ctx, chunk); err != nil {
			return true, err // не пишемо failed самі: відпускаємо — оренда згасне, задачу заберуть знову
		}
		progress.Store(int64(chunk.Percent)) // атомарно — серцебиття прочитає свіже число
	}

	// Результат — у об'єктне сховище; у рядок — лише підписане тимчасове посилання.
	key := "clips/" + op.ID + ".mp4" // ДЕТЕРМІНОВАНИЙ ключ → повторний рендер перезапише той самий об'єкт
	if err := w.objects.Put(ctx, key, renderedBytes(op.ID)); err != nil {
		return true, err
	}
	url := w.objects.SignedURL(key, 15*time.Minute) // підпис діє 15 хв
	result := &OpResult{URL: url, ExpiresAt: time.Now().Add(15 * time.Minute)}

	// Finish із ФЕНСОМ (WHERE lease_id = наш): якщо нас перехопили — запис відкинуть, пуш не піде.
	if done, _ := w.store.Finish(ctx, op.ID, op.LeaseID, "succeeded", result, nil); done {
		w.notify.ClipReady(op.UserID, op.ID) // штовх пушу ЛИШЕ якщо ми справді закрили операцію
	}
	return true, nil
}
```

Простеж живучість очима цього коду. Серцебиття б'ється кожні десять секунд і щоразу відсуває оренду на тридцять уперед — тож здоровий робітник тримає її з потрійним запасом, і випадкова затримка (пауза складання сміття, повільний запит) з'їдає щонайбільше один удар, не роняючи оренди. Але коли робітник **замерзає** по-справжньому — довга пауза GC, зависла машина, — серцебиття стихає, оренда більше не оновлюється й гасне за тридцять секунд від останнього удару. Тоді наступний `Claim` побачить `running` із простроченою орендою, перехопить операцію й **поставить новий жетон**. А коли перший робітник прокинеться (він же не знав, що спав), його серцебиття чи завершення зі **старим** жетоном торкнеться нуля рядків — і він чесно спиниться. Настінний час тут безсилий: заморожений робітник не знає, що минув час; рятує лише те, що ресурс сам відсіює старий жетон.

![Три доріжки в часі. Робітник A: claim із жетоном L1, серцебиття на 10, 20, 30 с (щоразу подовжує оренду), потім заморозка GC з 32 с — серцебиття стихло; на 70 с A прокидається, його запис із L1 дає 0 рядків — фенс, A спиняється. Смуга «оренда op-42»: подовжується серцебиттям до 60 с, там гасне. Робітник B: на 62 с бачить running з простроченою орендою, перехоплює з новим жетоном L2 і рендерить, б'ючись на 72, 82, 92 с](/guide/progarch/nodes-time-jobs-async/dh-long-ops/img/lease-heartbeat.svg)

*Серцебиття що десять секунд подовжує тридцятисекундну оренду, тож жива робота тримає її із запасом. Коли робітник замерзає, оренда гасне сама, і задачу перехоплює інший — з новим жетоном. Спізнілий запис першого відсіює фенс: у рядку вже чужий жетон, тож старий пише в нуль рядків.*

> 🔧 **Навіщо це.** Робітник не має права лишити операцію у брехливому `running`. Три механізми доводять кожну до чесного кінця, і кожен б'є свою біду: **серцебиття на таймері** (жива робота тримає оренду, навіть коли шматок довший за неї), **перехоплення за згаслою орендою** (мертвий робітник не тримає задачу вічно), **жетон-фенс у кожному записі** (той, кого перехопили, не затре живого наступника). Найтонше — саме розділення обов'язків: живучість міряй **часом** (серцебиття не питає згоди), а зупинку роби **за згодою** (скасування й дедлайн — між шматками, де рвати безпечно). Сплутаєш їх — або оренда згасне посеред чесної роботи, або скасування вб'є робітника з півфайлом.

## Результат, що згорає за розкладом

Кліп готовий, лежить об'єктом у сховищі, у рядку — підписане посилання. Здавалося б, кінець. Але тут ховається третя тиха біда, і вона про гроші й приватність водночас: **хто видалить файл?** Наївна відповідь — «ніхто, хай лежить» — означає, що кожен кліп, який хтось колись попросив, живе вічно, рахунок за сховище росте без стелі, а прострочене посилання на чужу камеру лишається відчиненими дверима назавжди.

Ліки — три **окремі** строки, і плутати їх не можна. Перший — строк **підпису**: посилання дозволяє звантажити цей один файл лише п'ятнадцять хвилин, далі підпис протухає й сховище віддає `403`. Це обмежує не файл, а **поширення посилання**: переслав його — воно скоро змертвіє. Другий — строк **файла**: сам об'єкт прибирає **політика життєвого циклу сховища** через, скажімо, сім днів. І це головна пастка: протухлий підпис **не видаляє байтів** — файл спокійно лежить далі, і без окремого правила сховища він там навіки. Тому правило задають явно:

```
Lifecycle правило (S3 / GCS / MinIO): усе під clips/ прибрати через 7 днів.
  filter:     prefix = "clips/"
  expiration: 7 днів після створення об'єкта
→ підпис (15 хв) стереже посилання; lifecycle (7 днів) стирає байти — це РІЗНІ строки.
```

Третій строк — сам **запис операції**: тримати мільйони «кліп такий-то, зроблено торік» — марно платити за рядки, тож `expires_at` кладе їм близько місяця, по якому окремий прибиральник видаляє їх пачками. Три вкладені строки — і жоден не «назавжди»:

![Три горизонтальні смуги від спільного початку «t=0: кліп готовий», кожна своєї довжини. Найкоротша — «підписане посилання», 15 хв, далі «підпис протух → 403». Довша — «файл у сховищі», 7 днів за політикою сховища, далі «прибрано автоматично». Найдовша — «запис операції у БД», близько 30 днів, далі «застарів → прибрано»](/guide/progarch/nodes-time-jobs-async/dh-long-ops/img/result-lifetimes.svg)

*Три строки, і кожен заданий явно. Поки живий файл, за операцією можна щоразу взяти свіже п'ятнадцятихвилинне посилання; коли політика сховища прибирає файл, зникає й сенс запису. Ніщо не задано «назавжди» — тому ніщо й не тече в нескінченність.*

Ось чому в `result` лягає посилання, а не сам ролик, і чому `expiresAt` там не косметика: клієнт, що спізнився на свої п'ятнадцять хвилин, не сердиться на «зламане» посилання, а просто перечитує операцію й дістає свіже — **доки живий файл**. А коли файл прибрано, чесно дістане `410 Gone` замість вічного мертвого посилання.

## Складність і пастки

Кожен із трьох вузлів ламається на дрібниці, і кожна дрібниця вже стелила комусь нічну зміну.

**Подвійний рендер без ключа.** Прибери `Idempotency-Key` і `UNIQUE`-індекс — і два паралельні `POST` заведуть дві операції, спаливши процесор двічі на той самий кліп. Спокуслива «латка» — перевіряти в коді (`SELECT`, і якщо нема — `INSERT`) — не латка зовсім: між твоїм читанням і вставкою влазить другий запит, який теж прочитав «нема». Єдине справжнє місце для арбітражу — унікальний індекс у сховищі. І пам'ятай про **обсяг ключа**: він мусить бути один на намір користувача (клієнт генерує його раз і несе крізь усі авто-повтори), інакше кожен повтор — новий ключ і новий рендер.

**Вічний `running` без серцебиття.** Прибери оренду й серцебиття — і робітник, що впав посеред кадру, лишить операцію в `running` навіки, з брехливим `progress: 70` над мертвою роботою. Ніхто її не перехопить, клієнт полить у порожнечу. Але й невдале **співвідношення** двох чисел кусає: постав серцебиття рідше за оренду (скажімо, бий раз на 30 с при оренді 30 с) — і одна випадкова затримка згасить оренду живого робітника, задачу перехопить другий, і два робітники змарнують подвійний рендер (сховищу шкоди не буде — фенс відкине запис програвшого, — але процесор спалено дарма). Тому серцебиття б'ють **помітно частіше** за оренду; потрійний запас — здоровий орієнтир.

**Витік файлів без TTL.** Забудь політику життєвого циклу сховища — і протухлий підпис приспить пильність: посилання не працює, а байти лежать. Тисячі кліпів, які ніхто вже не звантажить, тихо надимають рахунок, а кожен колись витеклий підпис — це відео з чужої камери, доступне рівно доти, доки живий файл. Підпис і lifecycle — **різні** строки: перший стереже посилання, другий стирає дані; потрібні **обидва**.

Ще кілька, менш очевидних, але не менш підступних.

**«Щонайменше раз» означає, що робітник мусить терпіти повтор.** Черга з орендою [гарантує доставку «щонайменше раз»](book:programming/delivery-guarantees), не «рівно раз»: робітник, що дорендерив, поклав файл, але впав **до** `Finish`, буде перехоплений і зробить усе вдруге. Рятує детермінований ключ об'єкта (`clips/{op.id}.mp4`) — повторний `Put` перезаписує **той самий** об'єкт, а не плодить другий, — і фенс на `Finish`. Разом вони роблять побічні дії ідемпотентними, тож «щонайменше раз» на вході дає «однаково як раз» на виході. Робітник, чиї побічні дії не витримують повтору, у такій черзі приречений.

**Кооперативне скасування не миттєве — і це видно клієнтові.** Ми перевіряємо прапорець між шматками, тож шматок у польоті доробиться. Великі шматки — довге скасування: якщо один відрізок рендериться пів хвилини, стільки ж клієнт бачитиме `canceling`. Розмір шматка — це і є стеля затримки скасування (і, до речі, стеля частоти оновлень `progress`); дрібніші шматки чуйніші, але частіші записи в базу.

**Поступ може стрибнути назад.** Перехоплений робітник починає рендер спочатку (або з контрольної точки, якщо ти її ведеш), тож `progress` після перехоплення легко впаде з 70 на 5. Клієнтові, який малює смужку, варто знати, що поступ — **орієнтир, а не монотонна обіцянка**; або веди контрольні точки й віднов з них, або чесно попередь, що смужка може відкотитися.

**Стелю тривалості міряй монотонним годинником.** П'ятихвилинна стеля на настінному часі — бомба: [нічна корекція NTP або переведення часу](book:programming/monotonic-vs-wall-time) зсуне дедлайн на годину вперед або назад, і операція або обірветься вмить, або зависне надовго. Тому `context.WithTimeout`, `performance.now()` і `time.monotonic()` у коді вище — не примха стилю: усі троє живуть на монотонному годиннику рантайму, якому байдуже до стрибків настінного.

**Пуш — не гарантія, а поштовх.** Штовх пушу [через контекст Сповіщення](guide:progarch/dh-notification-pipeline) наприкінці — зручність для того, хто вийшов із застосунку, а не заміна операції. Пуш може загубитися, прийти двічі чи спізнитися; істина завжди в рядку операції, який клієнт може перечитати. Тому пуш ми шлемо **лише** після того, як `Finish` під фенсом справді закрив операцію, — інакше перехоплений робітник надіслав би «ваш кліп готовий» на роботу, яку насправді завершує вже інший.
