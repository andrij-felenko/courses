# Program architecture v4 — «Архітектура програм: репертуар архітектора»

**slug:** `progarch` · **type:** guide · **статус: ПЛАН v4** (у репозиторії нічого не змінено)
**Пререквізит:** модуль «Вхід у програмування» курсу embedded або еквівалент — читач ВМІЄ писати код. Синтаксису не вчимо. Це курс РІШЕНЬ, не реалізацій: механізм, який архітектор споживає готовим, дається компактним атомом або ref-ом, а крок курсу витрачається лише там, де є розвилка, ціна, межа або відмова.
**Обсяг:** 497 кроків · 32 модулі · 10 частин · ~100 розділів.
**Ціль:** РЕПЕРТУАР архітектурних рішень — патерни, підходи «як архітектори думають», тактики обходу проблем, розв'язання важливих вузлів. НЕ енциклопедія суміжних фахів, НЕ підручник за доменом.
**Наскрізний приклад:** платформа розумного дому **Digital Homes** — ілюструє ТОЧКОВО, НЕ організовує структуру. Де слабший — платіжка, соцмережа-fan-out, data-пайплайн, ticketing.

## Що змінилось від v3 (і чому)

v3 (530 кроків) був щільним репертуаром (~80% корисних кроків за аудитом), але тримався на осі «предмет → домен» (принципи · патерни · застосунок · виконання · мережа · безпека · вузли · масштаб · флот · еволюція) — і мав три зони торгу: мікро-GoF заради каталогу 23/23, роздутий флот-модуль (М20–21, дублі offline/sync і thundering-herd «для заліза» + media-plane-спадок), гігієна-коду й OWASP-дроблення. Плюс системну діру: **репертуар МЕХАНІЗМІВ покрито щедро, а репертуар СПОСОБІВ МИСЛЕННЯ — тонко**.

**v4 перебудовує хребет на вісь «масштаб турботи»** (рядок → машина → дані → багато машин → сервіси/вузли → планета → організація). Ця вісь дає монотонний кумулятивний градієнт (класи відмов адитивні з масштабом), розділи-за-призначенням (розділ = один клас турботи на одному масштабі), і структурно НЕ впускає доменні підручники. Два графти: повноцінний КАПСТОН (з осі decision-lifecycle) і тонша нарізка критичних вузлів на родини-за-призначенням (з осі problem-kind).

**ВИКИНУТО баласт (~55 кроків, за скептичним аудитом):**
- **8 мікро-GoF** (bridge/flyweight/prototype/iterator/template-method/memento/visitor/interpreter) — стиснуто у 2 оглядові кроки; повні атоми лишаються book-полицею (design-patterns done для довідки).
- **Дублі М21-флоту**, що повторюють offline/sync (тепер М26/критичні вузли) і thundering-herd/shedding (М25/М27): dh-hub-cloud-reconcile, dh-blackout-day, dh-evening-peak, dh-blackout-recovery — знято як окремі кроки (механіка вже в тактиках/вузлах).
- **Гігієна коду** (error-handling/assert-panic/defensive-programming трьома ref-кроками) — злито в один вузол «контракт помилки»; ці три лишаються ref-передумовами, не кроками-власниками.
- **SOLID** п'ятьма кроками → 3 кроки (SRP+OCP+LSP+ISP+DIP по одному в одному розділі + композиція окремо).
- **OWASP-лікнеп** (sql-injection/xss/csrf трьома кроками) → 1 крок «вразливість = зламана межа» + приклади інлайн.
- **Теорію-як-кроки** М17 (heavy-tail/queue-theory/zipf) → висновок-секції в кроках масштабу, не окремі кроки-власники.
- **Спадки доменів** (ігрова реконсиляція 8.21, media-plane 21.20, particle-flyweight/prototype-вставки, file-format-design 6.21) → book-запас, НЕ в курс.

**ДОДАНО (крило «ЯК АРХІТЕКТОР ВИРІШУЄ» + відсутні вузли):**
- **Модуль «Рішення під невизначеністю» (М2, 16 кроків, НОВИЙ):** reversible/irreversible (one-way/two-way doors), спайк=купівля інформації, last responsible moment, коли НЕ будувати / YAGNI-дефолт, ризик-мислення (pre-mortem, ймовірність×вплив), купівля-vs-оренда-vs-build. Це найдешевший і найцінніший хід — курс учив зважувати ВІДОМЕ, тепер учить діяти БЕЗ даних.
- **Multi-tenant billing/metering/entitlements як вузол** (М24) — найчастіший SaaS-вузол, у v3 матеріал був (ledger+events+tenancy+reconciliation), але не зібраний у вузол.
- **Прикладний час** (М22) — таймзони/DST/рекурентність/зберігання наміру; у v3 був лише розподілений clock-skew.
- **Кеш-когерентність між сервісами / read-model-лаг** (М26) — «показує старе» після запису в іншому сервісі; у v3 кеш покрито лише над однією БД.
- **i18n як архітектура** (М22) — локаль-контекст, collation/пошук, plural у нотифікаціях; без UI-хвоста.
- **ETL/pipeline consistency** (М14) — data contracts + lineage + ідемпотентний reprocessing.
- **Ідемпотентні консюмери глибше** (М19) — dedup-вікно+TTL, side-effects (лист/платіж), poison-loop після side-effect до commit offset.

## Принципи структури

1. **Курс універсальний і доменно-нейтральний.** Хребет — за МАСШТАБОМ турботи (рядок→машина→дані→багато машин→сервіси→планета→організація); приклади всередині — з різних доменів; курс НЕ фільтрується жодним прикладом.
2. **Залізне правило розкладки:** самодостатня тема (патерн, механізм, вузол, тактика) → book-атом (`ref`/`nb`); кумулятивне, синтез, варіантні розбори, великі кейси → `own`-крок курсу. Доменну МЕХАНІКУ, яку архітектор споживає готовою, у курс не тягнемо — лише РІШЕННЯ навколо неї.
3. **Розділ = один клас турботи на одному масштабі** — мета-однорядник у дужках; жодних розділів «різне». Варіантний блок — окремий розділ «Рішення: …».
4. **Спіралі повертаються глибше на вищому масштабі** (↻): контракт, ідемпотентність, кеш, консистентність, час, ризик/зворотність, ретрай/таймаут, авторизація, спостережність — кожна вводиться на своєму масштабі й дозріває вище. Ніщо не вживається до введення.
5. **Варіантні рішення:** для ключових розвилок — 2–3 own-«варіант» із чесною адвокатурою (де виграє, хто так робить, чим платиш) + own-стаття-вибір з рамкою критеріїв. Читаються мовою М1–М2 (сценарії, чутливі точки, one-way/two-way).
6. **Каталог патернів свідомо:** GoF — архітектурно-значущі розгорнуто, мікродизайнові — 2 оглядові кроки (book-полиця повна). PoEAA-ядро, EIP-магістраль, resilience/cloud — у відповідних масштабах.
7. **Кейси компаній:** історія рішення → `hist`; прийом робочим кодом → `proj`; клас систем → `comp`; модель → `math`; великий розбір → `own`. Усі числа й атрибуції — письменнику веб-звіряти (AUTHORING §7), колективні внески замість одноосібних міфів.
8. **Роль архітектора наскрізною ниткою**, не останнім кроком; «смак архітектора» й «чеклист» у фіналі — payoff-рима до Частини I.

# ЧАСТИНА I. Ремесло архітектора: як думати й доносити рішення
*Рамка на весь курс. Масштаб: сам спосіб мислення й комунікації, ще до коду. Крило «Дисципліна» + графт «Як архітектор вирішує».*
**Бюджет: 48 кроків.**

## Модуль 1 — Що таке архітектурне рішення [mindset]

Один скрипт на одноплатнику читає температуру і смикає реле — Digital Homes v0. Він працює, але кожна зміна щось ламає. Модуль переводить інженера з «як написати» на «що і чому обрати»: що робить рішення архітектурним, як зробити «-ільності» вимірюваними, і що кожне рішення щось коштує. Тут-таки заводяться дві наскрізні нитки — роль архітектора і мова якостей.

**1.1. Архітектура як потік значущих рішень** (мета: визначити предмет — що робить рішення «архітектурним»)
1. [own:what-is-architecture] Архітектура — це рішення, які дорого змінити: межа значущого (дороге змінити ≠ дешеве), архітектура vs дизайн vs деталь реалізації
   · hist-big-ball-of-mud.md — Кейс: «Big Ball of Mud» Фута і Йодера (1997) — найпоширеніша архітектура світу
2. [nb:programming/architecture-discipline/architect-role] Роль архітектора: рішення, комунікація, відповідальність — властивість команди, а не посада й не диктатура; enterprise/solution/team-рівні; міф «намалював і пішов»
3. [nb:programming/software-design/technical-debt] Технічний борг і вартість зміни — борг як свідоме рішення, не аварія
   · hist-tech-debt.md — Кейс: метафора боргу Ворда Каннінгема (1992) і що вона означала насправді
4. [own:dh-v0-one-sensor] Digital Homes v0: один датчик, одне реле, один файл — і чому він приречений (наскрізний масштаб-приклад: датчик→хмара; суттєва vs привнесена складність — Брукс, срібної кулі нема, секцією)
   · proj-dh-v0.md — робочий однофайловий «хаб»: читання датчика, поріг, реле; його курс розвиватиме до фіналу

**1.2. Якісні атрибути й сценарії** (мета: зробити «-ільності» вимірюваними, а не гаслами)
5. [nb:programming/architecture-discipline/quality-attributes] Якісні атрибути («-ilities»): performance, availability, scalability, modifiability, security, observability, operability, cost — і чому «швидко і надійно» без числа не вимога
   · comp-quality-models.md — класи моделей якості: ISO 25010, SEI-список, FURPS+ — карти, не території; чому жодна не канон
6. [nb:programming/architecture-discipline/attribute-scenarios] Сценарії атрибутів: стимул → середовище → відповідь → міра (форма SEI); сценарій — це майбутній SLO (форвард на М29)
   · proj-dh-scenarios.md — 12 сценаріїв для DH («команда замку p99 < 500 мс», «новий тип датчика ≤ 2 дні», «хмара впала — дім живий») — дедлайни всього курсу
7. [nb:programming/architecture-discipline/stakeholders] Стейкхолдери та їхні системи: власник, розробник, ops, безпека, юрист, користувач — кожен бачить свою; якості народжуються з їхніх страхів
8. [nb:programming/architecture-discipline/architectural-drivers] Архітектурні драйвери: функційні вимоги + якості + обмеження → те, що формує систему; драйвер = вимога, під яку гнеться форма
9. [own:dh-utility-tree] Дерево корисності Digital Homes: продукт → зважені сценарії → топ-7 драйверів (довідник, до якого курс повертається в М18, М29, М32)

**1.3. Trade-off і його ціна** (мета: бачити, що кожне рішення щось коштує — і коли воно не має значення)
10. [nb:programming/architecture-discipline/tradeoff-analysis] Trade-off-аналіз: конфлікти атрибутів (латентність↔консистентність, простота↔гнучкість, пропускна↔латентність); чутливі точки, точки компромісу, ризики й неризики — рішення як явний обмін
11. [nb:programming/architecture-discipline/atam-lite] ATAM-лайт: прогін дерева корисності крізь кандидат-архітектуру; матриця варіант×атрибут — полегшене оцінювання за сценаріями
    · hist-atam-sei.md — Кейс: SEI, SAAM→ATAM (1990-ті–2000) — як оцінювання архітектур стало методом (атрибуції веб-звірити)
12. [nb:programming/architecture-discipline/architectural-tactics] Тактика проти патерна: атомарний хід під ОДИН атрибут; каталог тактик як мапа решти курсу
    · hist-tactics-catalog.md — Кейс: Bass/Clements/Kazman, «Software Architecture in Practice» — каталог тактик за атрибутами (видання/роки веб-звірити)
13. [nb:programming/architecture-discipline/modifiability-tactics] Тактики змінюваності: локалізувати зміну, зменшити зчеплення, відкласти зв'язування — уже працює на М4-поняттях (анонс)
14. [nb:programming/architecture-discipline/back-of-envelope] Прикидка «на серветці»: порядки RPS/обсягу/латентності як інструмент відсіву ДО того, як будувати; коли рішення не має значення (і це висновок)
    · math-latency-numbers.md — «числа, які має знати кожен» (за Діном): від наносекунд кешу до міжконтинентального RTT
15. [own:dh-v0-scenario-audit] Перше рев'ю: DH v0 проти дерева корисності — 9 із 12 сценаріїв провалено; чесна мотивація всього курсу (спіраль: далі М18, М32-ретроспектива)
16. [own:variant-block-anatomy] Анатомія варіантного блоку: варіанти → сценарії → чутливі точки → зворотність → вибір-рамка; як читати всі ~19 виборів курсу (мета-крок; тизер one-way/two-way М2)

## Модуль 2 — Рішення під невизначеністю та ризиком [decisions-under-uncertainty]

Мова якостей (М1) дає, ЧИМ зважувати відомі варіанти. Але 80% роботи архітектора — рішення там, де варіанти й дані невідомі, а помилка коштує. Цей модуль — інструменти вибору без даних: калібрувати темп під ціну відкату, купувати інформацію замість вгадувати, думати ймовірностями, а не страхами, і зробити «нічого не будувати» повноправною опцією. (НОВИЙ модуль v4, крило «Як архітектор вирішує» — найбільша діра v3; спирається лише на М1.)

**2.1. Зворотні й незворотні рішення** (мета: калібрувати темп/суворість під ціну відкату)
1. [nb:programming/architecture-discipline/reversible-irreversible-decisions] Зворотні й незворотні рішення: **one-way / two-way doors** (Безос, type-1/type-2); швидко й делеговано для two-way, повільно й консенсусно для one-way — ціна відкату визначає, скільки думати — **↻ризик (уводиться тут)**
   · hist-bezos-doors.md — Кейс: лист акціонерам Amazon (2015) — «більшість рішень оборотні, не треба вивченості на 90%» (переказ, звірити)
2. [nb:programming/architecture-discipline/last-responsible-moment] Останній відповідальний момент: відкласти рішення, поки не мусиш, — але не пізніше; тримати опції живими коштує, закрити рано коштує більше; як розпізнати «мусиш зараз»
3. [own:what-makes-irreversible] Що робить рішення незворотним: публічний контракт, формат на диску, вибір сховища під стан, крипто-протокол, залежність команд; і як зробити рішення зворотним — абстракція, відкладання, порт-адаптер (форвард на гексагон М8; ціна відкату як вимір КОЖНОГО варіантного блоку курсу)

**2.2. Купівля інформації** (мета: перетворити невизначеність на дію)
4. [nb:programming/architecture-discipline/deciding-under-uncertainty] Рішення під невизначеністю: **спайк як купівля інформації** (timeboxed), прототип-на-викид, set-based-design (тримати кілька опцій живими); що саме хочемо дізнатися і за скільки; розрізнення припущень і фактів та їх запис
5. [nb:programming/architecture-discipline/walking-skeleton] Walking skeleton: найтонший наскрізний зріз, що працює end-to-end, — як зняти інтеграційний ризик найдешевше й найраніше (тизер: та сама ідея в капстоні М32)
6. [own:cost-of-delay] Вартість зволікання проти вартості помилки: коли невизначеність варто просто прожити, коли — купити спайком, коли — вирішити зараз попри туман; спайк vs walking skeleton — що коли

**2.3. Ризик-мислення** (мета: думати ймовірностями й наслідками, а не страхами)
7. [nb:programming/architecture-discipline/risk-thinking] Ризик-мислення: **pre-mortem** («уяви, що впало — чому»), ймовірність×вплив (карта ризиків); «безпечно-до-провалу» замість «безпомилково» — **↻ризик**
   · hist-risk-storming.md — Кейс: risk-storming і pre-mortem (Ґері Кляйн, 2007) — як команди знаходять ризики до, а не після (звірити)
8. [nb:programming/architecture-discipline/risk-register] Ризик-реєстр як живий артефакт: перелік → оцінка → власник → мітигація → перегляд; спорідненість із threat-modeling (М28) — це ризик-мислення для безпеки; зв'язок ризику з архітектурним драйвером (М1)
9. [own:dh-risk-register] Ризик-реєстр Digital Homes: топ-ризики платформи (замок відчиняється чужому, флот не оновити, витік телеметрії присутності) — ймовірність×вплив, власник, мітигація; артефакт, до якого курс повертається

**2.4. Коли НЕ будувати** (мета: зробити «нічого не робити» повноправною опцією — головна помилка практиків)
10. [nb:programming/software-design/dry-kiss-yagni] **YAGNI за замовчуванням**, DRY і його межа (передчасне узагальнення), KISS; складність як пасив/борг; вартість передчасної абстракції — рамка «не будуй зайвого» ДО каталогу патернів (payoff-рекап у overengineering М31)
11. [nb:programming/architecture-discipline/evolutionary-architecture] Еволюційна архітектура як дефолт: «найпростіше, що спрацює» + запланована придатність до зміни; розпізнати, коли складність доречна, а коли культ; будувати під зміну, а не під усі майбутні вимоги
12. [nb:programming/architecture-discipline/build-vs-buy] **Build vs buy** (і оренда/SaaS/adopt): диференціююче ядро vs контекст; прихована ціна «свого»; **«нудна технологія»** як свідомий вибір (форвард на зрілу оптику М31)
    · hist-boring-tech.md — Кейс: Маккінлі (Etsy) — «інноваційні жетони»: скільки нового собі дозволити
13. [nb:programming/architecture-discipline/cost-as-attribute] Вартість як атрибут: у кожної якості цінник; вартість зміни ↔ вартість простою ↔ вартість залізом/людьми (тизер економіки М31, FinOps-лайт)
14. [own:dh-not-building] DH: три речі, які вирішили НЕ будувати (власний брокер, власна аналітика, власний біометричний вхід) — і чому кожен «свій» коштував би дорожче за куплений; критерії достатності
15. [own:assumptions-vs-facts] Припущення проти фактів як дисципліна: явно позначати, що ми ЗНАЄМО, а що ПРИПУСКАЄМО; записувати припущення поруч із рішенням (ADR); переглядати, коли припущення падає — рішення під невизначеністю на щодень
16. [own:dh-decisions-under-uncertainty] DH під невизначеністю: не знаємо навантаження й ринок — walking skeleton + спайк на вибір брокера + last-responsible-moment на мультирегіон; що вирішили відкласти й чому (синтез М2, ADR)

## Модуль 3 — В'ю та комунікація архітектури [views-and-communication]

Цегла гарна, а рішення розчиняється: ніхто не знає, ЧОМУ так, і одна діаграма бреше про все. Архітектор мусить креслити систему в масштабованих в'ю, фіксувати ЧОМУ письмово й проводити рішення крізь людей без наказу. C4 буквально дзеркалить вісь курсу (context→container→component→code), тож інструмент комунікації й хребет підсилюють одне одного. (Крило «Дисципліна», гніздо B.)

**3.1. Множинні в'ю однієї системи** (мета: одна діаграма не описує все)
1. [nb:programming/architecture-discipline/architecture-views] Архітектурні в'ю: **4+1** Кручтена (logical/process/development/physical/scenarios); в'ю = відповідь конкретному читачу (модель≠територія); чому одна діаграма бреше
   · hist-4plus1.md — Кейс: Кручтен (1995) і «одна діаграма всього бреше»; злет і відлив UML — чому виграли легкі нотації (веб-звірити)
2. [nb:programming/architecture-discipline/c4-model] C4: context → container → component → code — зум по масштабу, що дзеркалить вісь курсу; межа деталізації на кожному рівні; що на якому рівні НЕ малювати; типові помилки C4
   · proj-dh-c4.md — контекст і контейнери DH v2 кодом (Structurizr DSL/PlantUML), рендер локально
3. [nb:programming/architecture-discipline/deployment-view] В'ю розгортання і динамічні в'ю: процеси на машинах, мережі, зони відмови (діаграма, яку читає ops); runtime-sequence сценарію й діаграма станів життєвого циклу — статичне vs динамічне (луни в М27/М29)
4. [nb:programming/architecture-discipline/diagrams-as-code] Діаграми як код: текст у git, рев'ю, регенерація — діаграма перестає брехати
   · comp-diagram-tools.md — клас інструментів: PlantUML / Mermaid / Structurizr / D2 — межі кожного
5. [nb:programming/architecture-discipline/viewpoints-perspectives] Viewpoints і perspectives (Rozanski/Woods): в'ю відповідає на питання конкретного стейкхолдера (viewpoint), а якісні атрибути (perspective) проходять крізь усі в'ю; чому «намалюй усе» — не план; arc42 як легкий шаблон опису
6. [own:dh-v2-views] DH на папері: контекст, контейнери, deployment, один sequence («ніч, рух у вітальні») — комплект-довідник курсу поруч із мапою контекстів (М9)

**3.2. Письмові рішення: ADR / RFC / design-doc** (мета: зафіксувати ЧОМУ, а не лише ЩО)
7. [nb:programming/software-design/architecture-decision-records] Журнал архітектурних рішень (ADR): контекст→рішення→наслідки; журнал ADR як пам'ять/історія системи — **↻контракт (слід рішення як контракт із майбутнім собою)**
   · hist-nygard-adr.md — Кейс: Нігард (2011) — ADR як легкий формат, що прижився там, де важкі документи вмерли (веб-звірити)
8. [nb:programming/software-engineering/design-docs] Design docs і RFC: проєктування письмом для великих змін; хто рецензент; що записувати, а що ні; як не перетворити на бюрократію
   · hist-rfc-culture.md — Кейс: від IETF RFC до design docs Google і Rust RFC — культура рішень письмом
9. [nb:programming/software-design/api-design] Дизайн API модуля/бібліотеки як рішення письмом: мінімальна поверхня, contract-first vs code-first — рішення, яке ADR фіксує найчастіше (повниться в М10 назовні)
10. [own:writing-as-thinking] Проєктування письмом як інструмент мислення: чому текст ловить дірки, які діаграма ховає; коли ADR, коли RFC, коли одноразова нотатка; документ як засіб узгодження, не архів

**3.3. Рев'ю та вплив без влади** (мета: провести рішення через людей)
11. [nb:programming/architecture-discipline/architecture-review] Рев'ю архітектури як практика: що питати, як вести; RFC-цикл, легке рев'ю чи комітет, коли рев'ю блокує; зв'язка з ATAM-лайт
    · proj-arch-fitness.md — правило залежностей як тест у CI («домен не імпортує адаптери»); еволюційна архітектура (Форд/Парсонс) — фітнес-функції як анонс М32
12. [nb:programming/architecture-discipline/fitness-functions] Фітнес-функції: архітектурні правила, що самі себе перевіряють («домен не імпортує адаптери» як тест у CI) — рев'ю, яке не спить; анонс архітектурних тестів проти ерозії (М32)
13. [own:influence-without-authority] Вплив без наказу: переконання доказом і сценарієм, не посадою; прототип-спайк як аргумент (від М2), цінник варіантів, право на незгоду-й-виконання; донести trade-off нетехнічним; архітектор радить — команда володіє
14. [own:dh-review-workshop] Рев'ю-воркшоп DH: проводимо ATAM-лайт по дереву корисності (М1) проти кандидат-архітектури хаба; хто в кімнаті, які питання, як зафіксувати ризики в ADR — рев'ю на практиці

**3.4. Місток до організації й наскрізний слід** (мета: анонсувати Конвея й завести журнал рішень курсу)
15. [own:conway-teaser] Закон Конвея як анонс: чому межі, які ми малюємо, копіюють комунікацію команд — і чому це повернеться повноцінним модулем у Частині X; зв'язок в'ю з володінням (хто малює цей контейнер — той його й пише)
16. [own:dh-decision-log] Наскрізний слід рішень: заводимо журнал ADR Digital Homes, у який ляжуть усі ~19 варіантних блоків курсу — кожна велика розвилка далі супроводжується «як це в ADR» (payoff у ретроспективі М32)

3. [nb:programming/software-design/coupling-cohesion] Зчеплення і зв'язність: види зчеплення від змісту до даних (ціна кожного) / зв'язність; «low coupling / high cohesion» як компас; temporal coupling; цикли залежностей як сигнал біди
   · hist-structured-design.md — Кейс: Константайн і Йордан, structured design (1974) — пара coupling/cohesion за 20 років до ООП
4. [nb:programming/software-design/law-of-demeter] Закон Деметри: не звертайся через голову сусіда; ланцюги викликів як витік знання про структуру; де правило допомагає, де стає культом крапок

**4.2. Напрям залежностей і межі** (мета: керувати стрілками; ставити шов там, де тримає)
5. [nb:programming/software-design/dependency-inversion] Принцип інверсії залежностей (DIP): залежати від абстракцій, не деталей — граф залежностей, стабільні vs нестабільні залежності; вступ до DI (анонс М7)
6. [ref:programming/software-engineering/design-by-contract] Проєктування за контрактом: перед/постумови, інваріанти — контракт як обіцянка — (done, detailed:done); **↻контракт (старт)**
   · hist-mars-climate-orbiter.md — Кейс: Mars Climate Orbiter (1999) — фунт-секунди проти ньютон-секунд: контракт — це сенс даних, не сигнатура
7. [nb:programming/software-design/dto] DTO: дані через межу без поведінки — контракт форми, не логіки (повернеться в серіалізації М15)
8. [own:seams-and-boundaries] Шов (seam) як точка зміни: де ставити межу, щоб дешево було міняти; вартість зміни як тест межі; неявний контракт як борг (форвард на branch-by-abstraction М26 і legacy-seams М32)

**4.3. Незмінність і стан** (мета: менше стану = менше багів)
9. [nb:programming/software-design/immutability] Незмінність як прийом дизайну: value objects, значення vs ідентичність, копія замість мутації
10. [ref:algorithms/data-structures/copy-on-write] Copy-on-write — (pending)
11. [nb:programming/software-design/pure-functions-side-effects] Чисті функції і побічні ефекти: чисте — тестовне, ефекти — на краю; чистота як межа; спільний мутабельний стан як майбутнє джерело болю (насіння для М11)
12. [nb:programming/software-design/type-driven-design] Типи як дизайн: неможливі стани непредставні (parse, don't validate) — контракт, який тримає компілятор
13. [own:state-inventory] Де живе стан: у пам'яті, в сесії, у сховищі — інвентар стану хаба; де стан справді потрібен, а де його можна прибрати (форвард на state-management клієнта й твін)

**4.4. Помилки й перший рефакторинг межами** (мета: помилка — частина контракту; звести теорію в код)

## Модуль 5 — SOLID та композиція над спадкуванням [solid-and-composition]

П'ять принципів, які всі цитують і мало хто застосовує як інструмент, а не догму. Кожен — відповідь на конкретний біль і своя ціна надмірного застосування. Плюс головна альтернатива крихким ієрархіям: збирати поведінку композицією, а не спадкуванням. (Кат.3; SOLID стиснуто з 5 кроків у 3 — за аудитом; ↻кат.1 через межі DRY.)

**5.1. SOLID по одному, як інструмент** (мета: кожен принцип — відповідь на біль і своя ціна)
1. [nb:programming/software-design/single-responsibility] SRP: одна причина змінюватись — і де сліпе дроблення шкодить
2. [nb:programming/software-design/open-closed] OCP: відкритий для розширення, закритий для зміни — і ціна передчасної точки розширення
3. [own:lsp-isp-together] LSP та ISP разом: поведінкова підтипізація (контракт підтипу) + розділення інтерфейсів (клієнт не залежить від зайвого) — два принципи, одна ідея «не обіцяй більше, ніж тримаєш»
   · (ref-передумови інлайн: [ref:programming/software-engineering/behavioral-subtyping] done, [ref:programming/software-engineering/interface-segregation] pending — згадкою)

**5.2. Композиція, делегування, наслідування** (мета: збирати поведінку без крихких ієрархій)
4. [nb:programming/software-design/composition-inheritance] Композиція над спадкуванням: «has-a проти is-a» як рішення; делегування; домішки/трейти; крихкість глибоких ієрархій; параметризація поведінкою
   · hist-inheritance-fragility.md — Кейс: fragile base class і чому індустрія відвернулася від глибоких ієрархій (веб-звірити приклади)
5. [own:solid-audit] SOLID разом: аудит DH v1 п'ятьма принципами — де кожен допоміг, де перегин; DIP як міст до DI (анонс М7)

**5.3. Інші компаси коду** (мета: доповнити SOLID межами застосовності)
6. [nb:programming/software-design/functional-core-imperative-shell] Функціональне ядро, імперативна оболонка: ефекти на краю як архітектура (payoff pure-functions М4)
7. [own:cqs-command-query] CQS: розділення команди й запиту як компас коду — читання без ефектів, запис без повернення; зерно CQRS (анонс М19)
8. [own:principles-as-tools-not-dogma] Принципи як інструменти, не догми: коли DRY/SOLID/композиція шкодять; вартість надмірного застосування; вибір принципу під конкретний біль (рекап-містком у М6 і М7)

## Модуль 6 — Контракти, тестованість, рефакторинг [contracts-and-testability]

Код, у якому легко міркувати, який легко перевіряти й безпечно міняти. Явна угода замість неявної; «важко тестувати = поганий дизайн»; і як міняти форму, не ламаючи поведінку. Патерн тут ВИРОСТАЄ з коду — місток у каталог М7. (Кат.3; тестованість як атрибут — заміна вирізаної TDD-методики.)

**6.1. Контракт як межа й design-by-contract** (мета: явна угода замість неявної)
1. [own:contract-as-boundary] Контракт як межа: перед/постумови й інваріанти на рівні модуля; **толерантний читач / суворий писар (Postel)** — анонс сумісності (М10); версія контракту; чому неявний контракт — борг — **↻контракт**
2. [nb:programming/software-engineering/contract-testing] Контрактні тести: споживач диктує контракт (consumer-driven) — контракт як виконуваний артефакт (повниться між сервісами в М10/М19)
   · proj-contract-pact.md — контракт «мобільний застосунок DH ↔ хмара»: зміна поля ловиться до релізу
3. [own:invariants-and-validation] Інваріанти й валідація на межі: де перевіряти вхід (не довіряй зовнішньому), де покладатися на тип; валідація як частина контракту, а не розсип if-ів по коду (форвард на валідацію-на-межі безпеки М28)

**6.2. Тестованість як дизайн і рефакторинг** (мета: важко тестувати = поганий дизайн; міняти форму безпечно)
4. [nb:programming/architecture-discipline/testability-tactics] Тактики тестовності: керованість входів і спостережність виходів; шви, ін'єкція, детермінізм; «не тестується — погано розрізано»
5. [own:test-doubles-when] Дублери як рішення дизайну: fake / stub / mock — коли який; тест як споживач контракту; детермінізм як властивість форми
6. [own:test-boundaries] Що і на якому рівні тестувати: піраміда проти «трофея», тест як специфікація поведінки, крихкий тест як запах зчеплення з реалізацією — тестування як зворотний зв'язок про дизайн, не як обов'язок
7. [own:refactoring-safe] Рефакторинг безпечно: малі кроки, зелені тести як страховка; запахи коду як тригери; **патерн ВИРОСТАЄ з коду** (місток у М7)
8. [own:characterization-tests] Характеризаційні тести як страховка над кодом без тестів: зафіксувати поточну поведінку, щоб міняти безпечно (анонс legacy-археології М32; «код без тестів = legacy» — Фізерс)
9. [own:observability-as-testability] Спостережність як тестованість у проді: те, чого не можна відтворити в тесті, ловиться логом/метрикою/трейсом (анонс М29); проектувати систему так, щоб її було видно — властивість дизайну, не додаток
10. [own:debt-as-decision] Технічний борг як свідоме рішення, не аварія: коли брати, коли повертати, як зробити видимим (реєстр боргу поруч із ризик-реєстром М2)
11. [own:dh-testability-refactor] DH: робимо драйвер вендора тестовним — шов, ін'єкція годинника й мережі, характеризаційний тест перед зміною; «важко тестувати» як діагноз поганої межі (payoff М4–М6)

## Модуль 7 — GoF за призначенням + DI/репозиторій/антипатерни [gof-by-intent]

Одні й ті самі задачі щоразу розв'язуються наново. Патерн — назване типове рішення й спільна мова команди; мета — впізнавати задачу й бачити ціну, а не завчити 23 картки. Архітектурно-значущі GoF (ті, що «виростають» у системи) — розгорнуто; мікродизайнові — двома оглядовими кроками (повний каталог — book-полиця). Плюс DI, репозиторій і антипатерни. (Кат.4; мікро-GoF стиснуто з 8 кроків у 2 — за аудитом.)

**7.1. Патерн як словник, не рецепт** (мета: коли патерн доречний, коли культ)
1. [nb:programming/design-patterns/what-is-pattern] Що таке патерн: ім'я + контекст + сила + наслідок (ціна = trade-off з М1); чому «за призначенням»; over-engineering патернами як антипатерн
   · hist-gof-alexander.md — Кейс: від Крістофера Александера (патерни будівель, 1977) до «банди чотирьох» (1994)

**7.2. Творення (creational)** (мета: керувати тим, ЯК народжуються об'єкти)

4. [nb:programming/design-patterns/object-pool] Пул об'єктів: з'єднання, потоки, частинки (виросте в пули М11/М27)
5. [nb:programming/design-patterns/singleton] Сінглтон: рівно один екземпляр — і чому це часто пастка
   · hist-singleton-wars.md — Кейс: від GoF до бунту Google — «сінглтони — патологічні брехуни» (Геврі, 2008)

**7.3. Структура (structural)** (мета: складати об'єкти у більші форми без жорсткості)

7. [nb:programming/design-patterns/decorator] Декоратор: нашарувати поведінку (зерно наскрізних зрізів М8)

10. [nb:programming/design-patterns/proxy] Проксі: об'єкт-представник (виросте в reverse proxy М27 і RPC-стаби М15) — **↻кеш (кеш-проксі анонс)**

**7.4. Поведінка (behavioral)** (мета: розподіляти обов'язки й потік керування)
11. [nb:programming/design-patterns/strategy] Стратегія: алгоритм як замінна деталь (виросте в policy-as-code М28)
12. [nb:programming/design-patterns/observer] Спостерігач: подія знаходить слухачів (виросте в pub/sub М19)
13. [nb:programming/design-patterns/command] Команда: дія як об'єкт (виросте в чергу задач М22 і undo)
14. [nb:programming/design-patterns/state] Стан: поведінка залежить від фази життя (машина станів)

## Модуль 8 — Форми застосунку: шари, гексагон, чиста арх., PoEAA [application-shape]

Модулі є, а будинок — клубок: правила розмазані, база протікає в UI. Потрібні великі форми, у які складається застосунок, і критерій вибору між ними. Шари, порти-адаптери, наскрізні зрізи — і перевірені цеглинки шару даних із PoEAA, тепер коли масштаб застосунку це виправдовує. (Кат.5 + Кат.4-PoEAA; ↻контракт, ↻консистентність-насіння через UoW.)

1. [nb:programming/software-design/layered-architecture] Шарова архітектура: презентація / логіка / дані; правило залежностей (усередину); наскрізні зрізи vs горизонтальні шари; протікання/анемічність шарів як запах
2. [nb:programming/software-design/service-layer] Сервісний шар: операції застосунку як контракт; transaction script vs domain model vs table module (інлайн — три способи, де жити бізнес-правилам)

**8.2. Порти й адаптери (гексагон), чиста/цибулева** (мета: домен у центрі, деталі — назовні)

   · hist-hexagonal-cockburn.md — Кейс: Кокберн (2005) і «чиста архітектура» Мартіна — одна ідея різними словами
4. [nb:programming/software-design/di-container] DI-контейнер і composition root: одне місце, де все зв'язано (DI-патерн — М7); залежність ізсередини назовні
5. [own:hexagon-when-overkill] Коли гексагон — overkill: ціна портів на маленькому застосунку; назад до YAGNI (М2); критерій «скільки адаптерів насправді буде»

## Модуль 11 — Моделі конкурентності й виконання [concurrency-models]

## Модуль 16 — Реплікація й моделі консистентності [replication-and-consistency]

Одна машина — одна точка відмови, і вона вже не тягне 500 тисяч домів. Копії даних на різних вузлах дають витривалість — ціною питань, яких на одній машині не існувало: чия копія правдива, як жити з відставанням, і який компроміс між «сильно всюди» й «доступно завжди» обрати чесно. (Кат.8; ↻консистентність — розподілена.)

**16.1. Реплікація, лаг, кворум** (мета: керувати копіями під відмовами)
1. [nb:programming/distributed-systems/replication-leader-follower] Лідер-фоловер / мультилідер / leaderless: синхронно vs асинхронно; топології (кільце/зірка/all-to-all); git і календарі як побутові мультилідери (конфлікти стають нормою)
2. [nb:programming/distributed-systems/replication-lag] Реплікаційний лаг і сесійні гарантії: read-your-writes, monotonic reads — читаєш, а там минуле; лаг як фізика, з якою жити
3. [nb:programming/distributed-systems/quorum-and-leaderless] Кворуми: R+W>N (чому перетин гарантовано); хінтований гандовер, read-repair, anti-entropy — три механізми сходження реплік
   · hist-dynamo.md — Кейс: Amazon Dynamo (2007) — кошик, який не сміє відмовити; родовід Cassandra/Riak
   · math-quorum-intersection.md — чому W+R>N гарантує перетин: проста комбінаторика
4. [nb:programming/distributed-systems/split-brain] Failover і розщеплення мозку: два лідери гірше, ніж жодного; фенсинг, epoch/generation, кворумний свідок (анонс консенсусу М17)
   · hist-github-split-brain.md — Кейс: GitHub 21.10.2018 — 43 секунди розриву, доба реконсиляції
5. [own:dh-replicas] Твін дому на репліках: розводимо читання — і ловимо «вимкнув світло, а застосунок показує ввімкнене»; де read-your-writes обов'язковий (стан замка), де лаг припустимий (телеметрія)

**16.2. Мультилідер, конфлікти, сходження** (мета: писати можна всюди — конфлікти стають нормою)
6. [nb:programming/distributed-systems/multi-leader-replication] Мультилідерна реплікація: писати можна в кожному регіоні — конфлікти правок стають нормою; та сама задача, що конфлікти правок клієнта (М24); LWW і його межі як найпростіше розв'язання
7. [own:conflict-resolution-strategies] Стратегії розв'язання конфліктів: last-write-wins / merge-функція / версійні вектори / «спитати людину»; конфлікт як UX, не лише алгоритм (payoff у sync-конфліктах критичних вузлів; анонс CRDT)

**16.3. Моделі консистентності й CAP** (мета: обрати чесний компроміс замість «сильно всюди»)
8. [nb:programming/distributed-systems/consistency-models] Спектр консистентності: strong/лінеаризовність → causal → eventual; read-your-writes, монотонність — обрати чесний рівень, а не «сильно всюди»
9. [nb:programming/distributed-systems/cap-theorem] CAP (і чому не «оберіть 2») + PACELC (латентність теж у ціні): що обираєш під час розриву — і що щодня; чому сильна консистентність дорога
   · hist-cap-brewer.md — Кейс: гіпотеза Брюера (2000) → доведення Гілберт–Лінч → критика «двох із трьох»
10. [nb:programming/distributed-systems/eventual-consistency] Кінцева узгодженість на практиці: коли eventual чесно достатньо, коли ховає баг; конвергенція й «як жити з лагом»; місток у лаг read-model (М26)
11. [nb:programming/distributed-systems/anti-entropy-repair] Анти-ентропія: read repair, hinted handoff, фонова звірка Merkle-деревом — репліки розходяться, три механізми сходження (звірка як штатний цикл, не аварія); та сама ідея у reconciliation грошей (М24)
12. [own:dh-consistency-choice] Що в DH строго, а що «зрештою»: замки й доступи — строго (лінеаризовність), телеметрія і лічильники — eventual; консистентність як явний вибір на кожен клас даних, з ADR
13. [own:consistency-cost-tradeoff] Ціна консистентності як trade-off: латентність↔консистентність (від М1); чому «сильно скрізь» коштує кругову затримку; PACELC-рамка для щоденного рішення
14. [own:replication-choice] Вибір моделі реплікації: single-leader (просто, але лідер — вузьке місце) / multi-leader (пиши всюди, але конфлікти) / leaderless-кворум (доступність, але складність читань); критерій: де пишемо, чи припустимий лаг, ціна конфлікту; one-way чи two-way (М2)

## Модуль 17 — Час, порядок, консенсус, координація [time-order-consensus]

Машин багато — і з'являються питання, яких на одній не існувало: котра година, хто раніше, хто головний, як багато вузлів ухвалюють ОДНЕ рішення, і як різати дані так, щоб потім не збирати. 3. [own:causality-over-walltime] Причинність важливіша за настінний час: чому «пізніше за годинником» ≠ «сталося після»; де це кусає (конфлікти правок, дедуп, аудит) — payoff у out-of-order (М25) і sync-конфліктах (критичні вузли)

**17.3. Координація й розміщення** (мета: рідкісні, але критичні спільні рішення й розкладка даних)

## Модуль 18 — Сервісні межі: різати чи ні; знаходити одне одного [to-microservices-or-not]

Хмара DH не влазить в один деплой і одну команду. Найдорожче структурне рішення курсу — чесно, не за модою: межа ≠ мережа, моноліт-перш-ніж-сервіси як стратегія, і базова інфраструктура, якою сервіси знаходять одне одного. Розпил незворотний — тому проходить крізь one-way/two-way (М2). (Кат.5/9; ↻кат.1, ↻DDD, ↻Конвей.)

   · hist-amazon-two-pizza.md — Кейс: мандат Безоса (~2002, переказ Єґґе — подавати як переказ) і команди на дві піци → AWS

**18.2. Коли й як різати на сервіси** (мета: критерій розпаду, а не гасло)

6. [nb:programming/distributed-systems/service-discovery] Виявлення сервісів: реєстр, health-based, клієнт/сервер-сторона; плинні адреси як норма

## Модуль 20 — Інфраструктура й стійкість зв'язку сервісів [service-infrastructure-resilience]

## Модуль 21 — Критичний вузол: хто ти й що тобі можна [nodes-identity-access]

## Модуль 22 — Критичний вузол: час, фон, довгі операції [nodes-time-jobs-async]

Усе, що не вміщається в один синхронний запит: робота поза запитом, розклади на кластер, операції довші за таймаут. І прикладний час — джерело підступних багів, який курс досі бачив лише як розподілений clock-skew. Плюс i18n як архітектура (не переклад). (Кат.10; ↻час — прикладний, ↻ідемпотентність — джоби; ДОДАНО прикладний час та i18n за аудитом.)

**22.1. Прикладний час та i18n** (мета: час і локаль у бізнес-логіці — джерело підступних багів)

   · hist-time-bugs.md — Кейс: DST-баги в проді (пропущені будильники, подвійні нарахування) — чому час ловить усіх (звірити приклади)

[nb:programming/web-backend/i18n-as-architecture] i18n як архітектура (не переклад): локаль як наскрізний контекст запиту; формати грошей/чисел/дат на межі; collation й пошук за не-латиницею (↻search М24); plural rules у нотифікаціях (↻М23); RTL; дані vs представлення; зберігання перекладів як контент-пайплайн (ДОДАНО v4)

**22.2. Фонові джоби й розподілений cron** (мета: робити роботу поза запитом надійно)

   · comp-job-queue-systems.md — клас систем: БД-черги, Redis-черги, брокерні, керовані

## Модуль 25 — Тактики стійкості під навантаженням [resilience-tactics]

Система вже розподілена — і починає ламатися під тиском не там, де очікуєш. Прийоми, якими вона гнеться, а не ламається: свідомо відмовити частині, врятувати ціле; прибрати повільні хвости й зайві виклики; пережити «погані» й невпорядковані повідомлення. Це репертуар обходів, а не теорія. (Кат.11; ↻кат.1, ↻ретрай, ↻кеш, ↻ідемпотентність, ↻вектор.)

**25.1. Керування прийомом навантаження** (мета: свідомо відмовити частині, врятувати ціле)
1. [nb:programming/distributed-systems/queue-load-leveling] Черга як вирівнювач: пік — у чергу, а не в базу (Літтл + протитиск з М11); черга з відмовою, коли переповнена — **↻backpressure**
2. [nb:programming/distributed-systems/admission-control] Admission control: хто заходить під час перевантаження — критичність запиту (health і платежі перед аналітикою), деградований впуск (читання пускаємо, запис — ні); відмовити НА ВХОДІ дешевше, ніж усередині
3. [nb:programming/distributed-systems/load-shedding] Скидання навантаження і плавна деградація: відмовити дешево і рано; brownout (керована часткова недоступність, вимкнути другорядне); fail-fast vs fail-soft як рішення (розведення з admission: не прийняти ↔ скинути прийняте)
4. [nb:programming/distributed-systems/graceful-degradation-primary] Graceful degradation як ПЕРВИННА стратегія: fallback-значення, кешований останній стан як відповідь, «функція вимкнена, сервіс живий», feature-degradation під навантаженням — деградувати й лишитись корисним, а не лише «скинути»
   · (ref-фундамент інлайн: [ref:programming/embedded-systems/graceful-degradation] done)
5. [nb:programming/distributed-systems/adaptive-concurrency] Адаптивні ліміти конкурентності: статичний ліміт бреше — шукаємо місткість динамічно (AIMD/gradient за latency, TCP-ідея на рівні застосунку); взаємодія з ретраями (посилюють) і чергами (ховають)
   · hist-netflix-concurrency.md — Кейс: Netflix concurrency-limits (2018): від Hystrix-порогів до градієнтних лімітів
   · proj-aimd-limiter.md — AIMD-ліміт робочим кодом під синтетичним навантаженням
6. [nb:programming/distributed-systems/fairness-quotas] Чесність розподілу: rate limit захищає СИСТЕМУ, fairness захищає СУСІДІВ — per-tenant квоти, weighted fair queuing/DRR, per-key ліміти проти гарячого ключа, голодування дрібних під батчами
7. [own:priority-and-shedding-choice] Пріоритезація трафіку як рішення: що впустити першим, що скинути під тиском; критичність як атрибут запиту; brownout-план DH (відео-аплоад → історія → presence → команди — сходи деградації)

**25.2. Приборкання хвостів і дублювання роботи** (мета: прибрати повільні хвости й зайві виклики)
8. [nb:programming/distributed-systems/hedged-requests] Хеджовані запити: другий постріл по хвосту — ціна подвоєного трафіку (потрібна ідемпотентність М15!); анонс перцентилів (М27)
   · hist-tail-at-scale.md — Кейс: Дін і Баррозо, «The Tail at Scale» (2013)
9. [nb:programming/distributed-systems/request-coalescing] Request coalescing / single-flight: склеїти однакові одночасні запити в один; зв'язок із thundering herd (↻кеш М26)
10. [nb:programming/distributed-systems/backpressure-end-to-end] Наскрізний протитиск: клієнт → API → черга → воркер → БД — хто кому каже «повільніше»; протитиск як єдина нитка, а не локальний прийом (↻backpressure М11; reactive-streams)

**25.3. Отруйні й позачергові повідомлення** (мета: пережити «погані» й невпорядковані дані)
11. [nb:programming/distributed-systems/poison-message] Poison message / карантин: dead-letter (від poison-loop М19), парковка й ручний розбір; чому «просто ретраїти» зациклює — **↻ідемпотентність**
12. [nb:programming/distributed-systems/out-of-order-tolerance] Толерантність до безладу: версія-переможець (LWW з межами), монотонні перевірки, буфер перевпорядкування з вікном, комутативні операції, watermark — порядок дорогий, частіше дешевше ТЕРПІТИ безлад (↻векторні годинники М17)
    · proj-out-of-order.md — споживач із вікном перевпорядкування + версійним відкиданням
13. [own:dedup-boundary] Дедуп на межі vs у логіці: де ловити дублі — на вході (широко, дешево) чи в бізнес-логіці (точно, дорого); вікно й TTL ключа (↻ідемпотентні консюмери М19)
14. [nb:programming/distributed-systems/replay-protection-tactics] Захист від переграних повідомлень як тактика: підпис + вікно + монотонний лічильник у потоці подій (↻replay М15/М28); межа між дедуп (випадковий дубль) і replay-захистом (навмисний повтор)

**25.4. Метастабільність і рекап** (мета: не застрягнути в поганому стані — і зібрати арсенал)
15. [nb:programming/distributed-systems/metastable-failures] Метастабільні відмови: система застрягає в поганому стані сама (кеш холодний, усі повторюють) — і не встає після зняття тригера; як розпізнати й розірвати (зв'язок із health-каскадом М20, retry-штормом М15)
    · hist-metastable-outages.md — Кейс: від папера Bronson et al. до реальних каскадів (звірити)
16. [own:dh-resilience-tactics-map] Тактики стійкості DH разом: пік 18:00 (корельований сплеск presence/команд/камер) — вирівнювання, пріоритети, прогрів, деградація; чому «джитер з першого дня» рятує там, де клієнта не оновиш за годину (рекап-мапа тактик)

## Модуль 26 — Обходи змін даних і кешу [change-and-cache-tactics]

Міняти живу систему, не зупиняючи рейс, і тримати кеш чесним, коли правду міняє інший сервіс. Тактики зміни даних без простою (шов, подвійний запис, backfill, rollback-план) і кеш-тактики з когерентністю між сервісами й лагом read-model — те, чого v3 не мав (кеш лише над однією БД). (Кат.11; ↻контракт — вершина, ↻зворотність, ↻кеш — ВЕРШИНА, ↻консистентність; ДОДАНО когерентність між сервісами й лаг read-model за аудитом.)

**26.1. Зміна живої системи без простою** (мета: мігрувати й перемикати, поки все працює)
1. [nb:programming/software-design/branch-by-abstraction] Branch by abstraction: шов, за яким міняємо реалізацію (↻порти-адаптери М8; DIP з М4 у часі) — перебудова без довгих гілок — **↻зворотність**
2. [nb:programming/distributed-systems/zero-downtime-migration] Zero-downtime міграції даних: expand → migrate → contract; подвійний запис під час переходу (↻outbox); зворотно-сумісна схема (↻контракт М10/М14) — **↻контракт (вершина)**
   · proj-online-backfill.md — dual-write + тротльований backfill + dual-read verify на живій табличці
3. [nb:programming/operations/dark-launch] Темний запуск і feature-flag-міграція: фіча в проді, якої ніхто не бачить; dark launch, shadow traffic, поступове ввімкнення (↻feature-flags М10) — місток у канарку (М29)
   · hist-facebook-dark-launch.md — Кейс: чат Facebook (2008) — прод тестував себе сам місяцями
4. [nb:programming/operations/parallel-run] Parallel run: стара й нова логіка поруч для звірки на живому трафіку; harness порівняння; коли розбіжність — стоп
   · proj-parallel-run.md — harness порівняння старої/нової реалізації на живому трафіку
5. [own:backfill-and-reprocess] Backfill і reprocessing: перерахувати минуле (↻CDC/лог як джерело М14); online-backfill із тротлінгом; backfill, що не подвоює (↻ідемпотентний reprocessing М14)
6. [own:rollback-as-plan] Rollback міграції як план, не надія: зворотно-сумісні кроки, точка неповернення, як відкотити дані (↻зворотність кат.1); чому big-bang міграція — one-way door
   · hist-tsb-migration.md — Кейс: банк TSB (2018) — міграція «великим вибухом»: £330 млн і штраф (звірити)

**26.2. Кеш-тактики й когерентність між сервісами** (мета: зробити кеш швидким і не брехливим)
7. [nb:programming/distributed-systems/cache-stampede] Thundering herd / cache stampede і lock/coalescing: синхронізовані клієнти (крон о :00, реліз, кінець блекауту); request coalescing, м'який TTL (від М25)
   · proj-stampede-protection.md — request coalescing і м'який TTL — робочий код
8. [nb:programming/distributed-systems/cache-tactics] Дрібні кеш-тактики, що рятують проди: negative caching (кешуй «нема»), TTL jitter (лавина не збирається), refresh-ahead/stale-while-revalidate, write-behind coalescing — **↻кеш**
9. [nb:programming/distributed-systems/cache-key-design] Дизайн ключів і гарячі ключі: гранулярність ключа (per-entity vs per-query), версійні ключі для інвалідації без видалення, гарячий ключ як точка контеншну (↻fairness М25); що кешувати, а що ні
10. [nb:programming/distributed-systems/cache-invalidation-patterns] Патерни інвалідації: TTL / write-through-інвалідація / подія-інвалідатор / версійний ключ — чотири способи не показати старе; чому «інвалідація — одна з двох важких проблем»
11. [nb:programming/distributed-systems/cache-coherence-services] Кеш-когерентність МІЖ СЕРВІСАМИ: інвалідація, коли правду змінив ІНШИЙ сервіс — подія-інвалідатор проти TTL (↻pub/sub М19); версійні ключі між сервісами; read-your-writes через шар кешу (ДОДАНО v4)
12. [nb:programming/distributed-systems/read-model-lag] Лаг read-model як контракт: CQRS-читання завжди трохи позаду (від М19 і консистентності М16); «як жити з лагом проєкції» — показати застаріле чесно (stale-while-revalidate) vs заблокувати; узгодження очікувань користувача (ДОДАНО v4)
13. [own:cache-coherence-choice] Вибір стратегії свіжості між сервісами: TTL (просто, але лаг) / подія-інвалідатор (свіжо, але зчеплення через шину) / версійний ключ (без видалення, але зростання) — критерій: ціна застарілого, частота змін, зчеплення
14. [own:stale-data-honestly] Показати застаріле чесно: індикатор свіжості, «оновлено N хв тому», оптимістичне читання з корекцією; узгодити очікування замість ховати лаг — кеш і read-model як UX-рішення, не лише технічне
15. [own:dh-change-cache-final] DH: переїзд твіна з варіанта Б у В без зупинки флоту (М19) + інвалідація кешу стану дому подією з іншого сервісу + чесний лаг телеметрії — увесь арсенал змін і кешу; ADR фаз і точок неповернення
16. [own:migration-strategy-choice] Вибір стратегії зміни живої системи: expand-contract / dark launch + flag / parallel run / branch-by-abstraction — критерій: ризик, зворотність (М2), скільки читачів; що коли (рамка обходів змін)

## Модуль 28 — Безпека як архітектура [security-architecture]

Курс збудував платформу, що відчиняє двері й дивиться у вітальню, — а зловмисник як сила архітектури досі звучав лише розсипом (replay М15, authz М21). Тепер безпеку вбудовуємо в структуру, а не прикручуємо збоку: побачити систему очима нападника, керувати доступом і таємницями системно, захистити дані/збірку/від зловмисного трафіку. (Кат.13; ↻C4, ↻кат.1, ↻авторизація — глибше, ↻конфіг, ↻аудит, ↻rate-limit; OWASP-дроблення стиснуто в 1 крок за аудитом.)

**28.1. Моделювання загроз і межі довіри** (мета: побачити систему очима нападника)
1. [own:attacker-as-force] Зловмисник як сила архітектури: активи, супротивники, бюджет атаки проти бюджету захисту; безпека — властивість структури, не фіча; чому «додамо потім» не працює (як із продуктивністю); спорідненість із ризик-мисленням (М2)
2. [nb:programming/security/threat-modeling] Моделювання загроз: чотири питання (що будуємо → що може піти не так → що робимо → чи добре впорались) і **STRIDE** по елементах діаграми потоків даних (↻C4 М3)
   · hist-stride-sdl.md — Кейс: STRIDE (Кохнфельдер/Гарг, 1999) і меморандум Гейтса (2002) → SDL — безпека стає етапом проєктування (атрибуції веб-звірити)
   · proj-dh-threat-model.md — STRIDE-воркшоп на C4-діаграмі хмари DH: таблиця «елемент × загроза × контрзахід»
3. [nb:programming/security/trust-boundaries] Межі довіри: де змінюється «хто говорить» — процес, машина, мережа, оргмежа; межа довіри = точка автентифікації і валідації; наносимо на мапу контекстів (М9); валідація на межі (не довіряй входу) — **↻авторизація**
   · hist-target-hvac.md — Кейс: Target (2013) — 40 млн карток через підрядника вентиляції: плоска мережа без внутрішніх меж (числа звірити)
4. [nb:programming/security/attack-surface] Поверхня атаки: кожен вхід — двері (порти, API, вебхуки, файли, залежності, люди); інвентар входів як артефакт; мінімізація — закрито за замовчуванням, відкрито за рішенням
5. [nb:programming/security/web-vulnerability-classes] Вразливість = зламана межа: класи (ін'єкції, зламаний контроль доступу, десеріалізація недовіреного, SSRF, XSS/CSRF) як таксономія зламаних меж — «дані перетнули межу без перевірки»; параметризація/екранування/CSP як архітектурні бар'єри, а не дисципліна кожного розробника (OWASP-дроблення стиснуто в 1 крок)
   · proj-injection-demo.md — вразливий і виправлений шар даних поруч; тест, що ловить конкатенацію SQL у CI (фітнес-функція з М3!)
6. [nb:programming/security/zero-trust] Zero-trust: не довіряй за розташуванням — кожен запит автентифікований і авторизований незалежно від мережі (↻авторизація М21); безпека як якісний атрибут (↻драйвери М1)
7. [own:dh-threat-model] Threat model Digital Homes: замок — spoofing команд, камера — розголошення, OTA — tampering, білінг — repudiation, брокер — DoS; таблиця «загроза → тактика → де в курсі» як мапа безпеки платформи

**28.2. Ідентичність, авторизація, секрети** (мета: керувати доступом і таємницями системно)
8. [nb:programming/security/least-privilege] Найменші привілеї й deny-by-default: кожен компонент може рівно своє — сервісні акаунти, scoped-токени, радіус вибуху краденого ключа (перебірки М20 — тепер для прав); аудит дозволів
9. [nb:programming/security/password-hashing] Зберігання паролів: хеш, повільний за дизайном — сіль, вартість, перець; міграція схеми хешування наживо (автентифікація М21 — тепер її сховище)
10. [nb:programming/security/secrets-management] Секрети й ротація: не в коді, не в образі, не в env назавжди — сховища, injection при старті, короткоживучі, від коду подалі (↻конфіг М10)
    · hist-uber-github-key.md — Кейс: Uber (2016) — AWS-ключ у репозиторії → 57 млн записів і рік замовчування: секрет у коді = секрет у кожному клоні (звірити)

**28.3. Крипто, ланцюг постачання, зловживання, безпечні дефолти** (мета: захистити дані, збірку й від зловмисного трафіку)

## Модуль 29 — Спостережність і експлуатація [observability-and-operations]

Планетарна система живе в проді: її треба бачити зсередини, безпечно випускати й тримати живою цілодобово. ## Модуль 30 — Закон Конвея й топології команд [conway-and-teams]

Структура системи й структура команд — одне дзеркало (анонс М3): проєктуй обидві. Найдорожчі структурні рішення курсу (розпил М18, межі контекстів М9) виявляються рішеннями про людей. Свідомо проєктувати організацію під бажану архітектуру — і розкласти роботу так, щоб її можна було нести. (Кат.15; ↻обмежені-контексти, ↻мікросервіси.)

**30.1. Конвей і зворотний маневр** (мета: свідомо проєктувати організацію під бажану архітектуру)
1. [nb:programming/software-design/conways-law] Закон Конвея: система копіює структуру команд; чому межі сервісів (М18) = межі команд; чому реорг ламає/лагодить систему
2. [nb:programming/architecture-discipline/inverse-conway] Inverse Conway maneuver: проєктувати команди під бажану архітектуру, а не навпаки; коли це працює, коли — карго-культ; межі контекстів (М9) як межі володіння
3. [nb:programming/architecture-discipline/communication-paths] Комунікаційні шляхи як обмеження архітектури: інтеграція між командами дорожча за інтеграцію в команді; чому «два сервіси однієї команди» ≠ «два сервіси двох команд»; API як контракт між командами (↻контракт)
4. [own:dh-conway-map] Мапа команд DH проти мапи контекстів: хто володіє твіном, флотом, відео, платформою; де межа сервісу не збіглася з межею команди — і що зламалось; зворотний Конвей на практиці

**30.2. Топології команд і навантаження** (мета: розкласти роботу так, щоб її можна було нести)
5. [nb:programming/architecture-discipline/team-topologies] Team topologies: stream-aligned / platform / enabling / complicated-subsystem; чотири типи команд і три режими взаємодії (collaboration / X-as-a-service / facilitating)
   · hist-team-topologies.md — Кейс: Скелтон і Пейс (2019) — від закону Конвея до операційної моделі (атрибуції/приклади веб-звірити)
6. [nb:programming/architecture-discipline/cognitive-load-teams] Когнітивне навантаження команди як межа розміру сервісу: скільки системи влазить у голови; навантаження внутрішнє/стороннє/доречне; когнітивне навантаження, а не «мікро», задає розмір
7. [nb:programming/architecture-discipline/platform-engineering] Платформна інженерія: внутрішня платформа як продукт; golden path / paved road; self-service; де платформа передчасна (від service-infra М20 і IaC М29)
   · comp-internal-platforms.md — клас внутрішніх платформ: від wiki+скрипти до IDP-порталів (Backstage-клас)
8. [own:cognitive-load-as-boundary] Когнітивне навантаження як критерій розкрою: коли команда «не тримає» систему в головах — сигнал різати або спрощувати; navantaження команди проти розміру сервісу як реальна межа (payoff мікросервіси М18 — не «мікро», а «носимо»)
9. [own:dh-team-topology-choice] Топологія команд DH: stream-aligned на домени (твін, автоматизації), platform на інфру, enabling на безпеку; де провести межі, щоб когнітивне навантаження було носимим; ADR організації
10. [own:handoffs-and-ownership] Передачі й володіння як джерело затримки: кожна передача між командами — черга й ризик; «ти будуєш — ти й тримаєш» (you build it, you run it); володіння сервісом як межа відповідальності (зв'язок із on-call та SLO М29)
11. [own:platform-vs-premature] Платформа проти передчасної платформи: коли внутрішня платформа окупається, коли це втеча від продукту; golden path як пропозиція, не мандат; ознаки, що платформу будують зарано (від М2 — не будуй зайвого)
12. [own:org-as-architecture] Організація як архітектура: реорг — це рефакторинг системи; чому не можна змінити архітектуру, не змінивши команди (і навпаки); соціотехнічна система як єдине ціле (рекап-місток у капстон М32)

## Модуль 31 — Гроші, залежність, вибір постачальника [cost-and-lock-in]

Рахувати економіку архітектури й вартість виходу — рівень портфеля й гаманця. Форма рахунку залежить від архітектури; замок — усвідомлений кредит; вибір «своє/куплене» тепер із даними експлуатації, а не з ентузіазму. Payoff cost-as-attribute (М2) і build-vs-buy (М2) у зрілій оптиці. (Кат.15; ↻кат.1 — зріло, ↻зворотність, ↻порти-адаптери.)

**31.1. Хмарна економіка й вартість виходу** (мета: бачити рахунок і пастку замка)
1. [nb:programming/architecture-discipline/cloud-cost-model] Cloud cost як архітектурний драйвер: unit-економіка (вартість запиту/користувача/пристрою); форма рахунку від архітектури (↻драйвери М1); вартість як fitness-функція — коли дизайн визначає рахунок
   · math-unit-economics.md — проста модель: трафік × шлях × цінник = маржа фічі; поріг «кеш дешевший за перерахунок»
2. [nb:programming/architecture-discipline/finops-levers] FinOps-важелі: egress як прихований драйвер, reserved/spot/on-demand, right-sizing, data gravity (дані тягнуть обчислення до себе); чому «просто в хмару» дає рахунок-сюрприз
3. [nb:programming/architecture-discipline/lock-in-exit-cost] Прив'язка і вартість виходу: API, дані, формати, egress, компетенції — **lock-in як усвідомлений кредит**; exit cost як критерій вибору (↻зворотність); оборотні межі — порт-адаптер знову (↻М8)
   · comp-lock-in-shapes.md — форми прив'язки і exit-стратегії: подвійний постачальник, відкриті формати, шар абстракції та його ціна
4. [own:exit-strategy] Стратегія виходу як частина вибору: подвійний постачальник / відкриті формати / шар абстракції — і ціна кожної страховки; коли lock-in — раціональний борг, коли — пастка; exit cost у ADR вибору постачальника
5. [own:rozbir-cloud-or-metal] Розбір: хмара чи залізо — Netflix у хмару, Dropbox і Basecamp з хмари; три різні правильні відповіді; egress і форма рахунку вирішують
6. [own:build-vs-buy-mature] Build vs buy у зрілій оптиці: черга, база, автентифікація, брокер — тепер із даними експлуатації (від М2); керований сервіс як той самий вибір; коли «своє» нарешті окупається
7. [nb:programming/architecture-discipline/tech-radar] Техрадар: adopt/trial/assess/hold — керувати зоопарком технологій без диктату; губернанс і стандарти; пара до boring-technology (М2); свідома технічна ставка
   · hist-tw-radar.md — Кейс: ThoughtWorks Tech Radar (з 2010) — радар як інструмент компанії, не журнал мод (веб-звірити)
8. [nb:programming/operations/capacity-planning] Планування потужностей і headroom: прогноз росту, запас, worst-case; вартість недо- й переоцінки (↻закон Літтла М27)
   · hist-pokemon-go.md — Кейс: Pokémon GO (2016) — ×50 від плану при worst-case ×5; жива міграція під вогнем
9. [own:overengineering] Перепроєктування: та сама задача без журналу подій і кластера — моноліт + крон; критерії достатності (payoff-рекап YAGNI М2 — over-engineering тут, а не мораль наприкінці)
10. [own:cost-as-fitness-function] Вартість як fitness-функція в CI: алерт на unit-cost-регресію, бюджет на запит як тест; коли архітектурне рішення тихо потроює рахунок і як це побачити рано (↻fitness-functions М3)
11. [own:economics-decision-recap] Економіка рішення як рамка: вартість побудови ↔ вартість експлуатації ↔ вартість виходу ↔ вартість зміни — чотири цінники кожного вибору; чому «дешево збудувати» часто «дорого володіти»
12. [own:dh-cost-decisions] Економічні рішення DH: де хмара, де замовлене залізо для відеосховища; egress відео як драйвер архітектури; замок на керованому брокері vs власний — з даними експлуатації; ADR

## Модуль 32 — Легасі, ерозія, стратегії переходу + КАПСТОН [legacy-and-evolution]

Жити зі старим, виводити його з ладу — і зібрати весь репертуар докупи. Система живе довше за свою першу архітектуру; форма гниє непомітно; переписати чи оздоровити — свідоме рішення про незворотність. І фінал: провести одну систему через усі масштаби, показавши, як рішення зчіплюються. (Кат.15; ГРАФТ: повноцінний капстон; ↻зворотність — вершина.)

**32.1. Ерозія й археологія legacy** (мета: зрозуміти й приборкати те, що вже гниє)
1. [nb:programming/architecture-discipline/architecture-erosion] Ерозія архітектури: дрейф від задуму (задумана ≠ реалізована); як форма гниє непомітно і чому «ще один виняток» — це процес; архітектурні тести як запобіжник (↻модульний моноліт М18, fitness-functions М3)
   · comp-arch-conformance-tools.md — клас інструментів контролю форми: ArchUnit-клас, dependency-cruiser, правила збірки
2. [nb:programming/architecture-discipline/legacy-archaeology] Археологія legacy: реверс-розуміння без документації; шви (від М4), характеризаційні тести (від М6), гарячі точки з git-історії; відновлення в'ю через C4/ADR як діагностика
   · hist-legacy-seams.md — Кейс: Фізерс (2004) — шов як одиниця свободи; «код без тестів = legacy»
   · proj-hotspot-map.md — карта гарячих точок: churn × складність із git log робочим скриптом
3. [own:reading-unknown-system] Прийшов у чужу систему: план на 30 днів — згори (відновити C4 з М3), знизу (логи/трейси М29), збоку (люди, ADR-и, git); ризики й швидкі перемоги. Приклад: «нова команда успадкувала DH без документації» — курс навиворіт

**32.2. Переписати, обгорнути чи оздоровити** (мета: обрати стратегію зміни великого свідомо)
4. [nb:programming/architecture-discipline/rewrite-vs-refactor] Rewrite vs refactor: коли big rewrite виправданий, ефект другої системи, чому big-bang зазвичай програє (незворотність — ↻кат.1, вершина); стренглер як третій шлях
   · hist-netscape-rewrite.md — Кейс: Netscape 6 (2000) і теза Спольскі про «найгіршу стратегічну помилку» — плюс чесні контрприклади вдалих переписувань (веб-звірити обидва боки)
5. [nb:programming/software-design/strangler-fig] Strangler fig: нове обростає старе, поки старе не всохне (від branch-by-abstraction М26, API-gateway М18); пара — BBA код, стренглер система
6. [nb:programming/architecture-discipline/deprecation-policy] Deprecation як керований процес: політика виводу API/фіч/сервісів — терміни, міграційні шляхи, комунікація болю (↻контракт/версіонування М10) — **↻контракт**
   · hist-python2-sunset.md — Кейс: Python 2→3 (2008–2020) — деприкейшн довжиною в епоху: що зламалось і що спрацювало
7. [own:migration-choice] Вибір стратегії переходу великого: big bang / стренглер / branch-by-abstraction + жива міграція даних — DH-хмара v1→v2 як наскрізний приклад; точки неповернення; ADR
8. [own:dh-cloud-v2] DH переїздить: твін з варіанта Б у В (М19) без зупинки флоту — план, фази, точки неповернення; fitness-контроль ерозії (М3) ловить дрейф машиною

**32.3. Наскрізний кейс (капстон-синтез)** (мета: провести одну систему через усі масштаби й показати, як рішення зчіплюються)
9. [own:request-journey-final] Життя одного запиту і однієї команди: DNS → TLS → LB → шлюз → авторизація → твін → черга → пристрій → ack → push — наскрізний розбір усіх шарів курсу на одному потоці
10. [own:dh-platform-retrospective] Ретроспектива Digital Homes: карта всіх ~19 варіантних рішень курсу (журнал ADR М3) — що обрали, чому, що б переграли на інших вимогах; звірка проти дерева корисності (М1); які one-way/two-way doors спрацювали
11. [own:capstone-setup] Капстон, крок 1 — постановка: беремо нетривіальну не-DH вимогу («маркетплейс або платіжка виходить у 3 регіони з платними тарифами на мільйон користувачів»); драйвери/атрибути, дерево корисності, walking skeleton (М2) — рамка без підказок нитки
12. [own:capstone-shape-data] Капстон, крок 2 — форма й дані: в'ю (C4)/ADR → форма застосунку й межі контекстів → дані й консистентність → де строго, де eventual; ADR на кожній розвилці
13. [own:capstone-services-nodes] Капстон, крок 3 — сервіси й вузли: різати чи ні → інтеграція й саги → критичні вузли (identity, гроші/ledger, час, вебхуки, tenancy); ідемпотентність і контракти між сервісами
14. [own:capstone-scale-secure-ops] Капстон, крок 4 — обходи, масштаб, безпека, експлуатація: тактики під тиском → масштаб/край/регіони → threat model → SLO/деплой/DR; де які trade-off спрацювали
15. [own:capstone-org-evolution] Капстон, крок 5 — організація й еволюція: топологія команд під архітектуру (Конвей) → економіка й lock-in → план еволюції й deprecation; повний ланцюг зчеплено

**32.4. Смак архітектора** (мета: що лишається, коли забув патерни)
16. [own:architect-taste] Смак архітектора: як тримати цілість системи під тиском; коли свідомо порушити власні правила; смак як натренована інтуїція компромісу; ознаки зрілого архітектурного судження
17. [own:architect-checklist] Чеклист архітектора: організований за атрибутами й тактиками (payoff-рима до Частини I — М1/М2); наскрізні спіралі як контрольні питання (контракт? ідемпотентність? зворотність? межа довіри?)
18. [own:decision-heuristics] Евристики рішення на щодень: one-way/two-way перш ніж занурюватись, «нудне» за замовчуванням, YAGNI-дефолт, pre-mortem перед великим, вимірюй перш ніж оптимізуй — компас, коли немає часу на повний аналіз
19. [own:where-next] Куди рости після progarch: домени-профілі (fintech, gamedev, ML-платформи), книги полиці (вирізані домени як запас), курс embedded; що читати й практикувати далі
20. [own:course-farewell] Прощання з курсом: від скрипта на одноплатнику (М1) до платформи на три регіони (капстон) — як масштаб турботи ріс, а спіралі поверталися глибше; архітектура як потік значущих рішень, а не набір діаграм

# Варіантні блоки (~19)

Кожен блок = 2–3 own-«варіант» з чесною адвокатурою (де виграє / хто так робить / чим платиш) + own-стаття-вибір з рамкою критеріїв (у компактах адвокатура й вибір злиті). Читаються мовою М1–М2 (сценарії, чутливі точки, **зворотність one-way/two-way** — крок variant-block-anatomy М1.16).

**Повні блоки (2–3 кроки):**
1. **Рантайм конкурентності** (М11): потоки+локи / event loop / актори + вибір — відеосервер проти ігрового сервера.
2. **Реплікація** (М16): single-leader / multi-leader / leaderless-кворум (replication-choice).
3. **Твін дому** (М19): актор-на-дім / шардована БД / журнал подій + вибір.
4. **Подієвий підхід** (М19): нотифікація / ECST / event-sourcing / CQRS (eventdriven-choice).
5. **Стиль саги** (М19): оркестрація / хореографія / без саги / workflow-рушій (saga-style-choice).
6. **Розміщення стійкості** (М20): бібліотека / sidecar-mesh / шлюз (resilience-placement-choice).
7. **Авторизація** (М21): у сервісах / центральна політика (PDP) + вибір-гібрид.
8. **Де живе сесія** (М21): server-side store / stateless JWT / гібрид access+refresh.
9. **Де живе черга задач** (М22): БД (SKIP LOCKED) / брокер / керована+serverless + вибір.
10. **Мультиарендність** (М24): спільна схема (pool) / схема-на-орендаря / база-на-орендаря (silo) + вибір.
11. **Де живе правда про гроші** (М24): статуси+звірка / гросбух / провайдер-джерело + вибір-еволюція.
12. **Fan-out сповіщень** (М23): on-write / on-read / гібрид (notification-fanout-choice).
13. **Стратегія зміни живої системи** (М26): expand-contract / dark-launch+flag / parallel-run / branch-by-abstraction (migration-strategy-choice).
