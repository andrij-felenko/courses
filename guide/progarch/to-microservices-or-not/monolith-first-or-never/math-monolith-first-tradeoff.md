# 🧮 Математична модель доцільності Monolith-First: поріг складності предметної області та інфраструктурного накладного чеку

У цій математичній вставці виведено формальну функцію сумарної вартості володіння системою (Total Cost of Ownership, TCO) та інженерного тертя для розрахунку аналітичної точки перетину доцільності між Модульним монолітом та сервісним розкроєм на «зеленому газоні».

## Формалізація параметрів та змінних системи

Опишемо стан софтверного проєкту, команди та інфраструктури за допомогою вектора параметрів:

- `S` — чисельність інженерної команди розробки (кількість програмістів);
- `N` — кількість фізично ізольованих мережевих сервісів чи процесів у системі (`N = 1` відповідає монолітній архітектурі);
- `D_drift` — коефіцієнт волатильності (нестабільності) доменних меж предметної області (`0 ≤ D_drift ≤ 1.0`). Значення `D_drift = 1.0` відповідає початковому стадії стартапу («зелений газон»), де бізнес-модель та межі контекстів змінюються щотижня. Значення `D_drift = 0.05` відповідає зрілому домену зі стабільними специфікаціями;
- `L` — інтенсивність вхідного навантаження на систему (кількість запитів на секунду, Requests Per Second, RPS);
- `α` — питома вартість рефакторингу логіки та виправлення меж усередині єдиного процесу в пам'яті (базовий норматив прийнято за `α = 1.0`);
- `β` — питома вартість рефакторингу меж між незалежними мережевими сервісами. Включає оновлення gRPC/REST-контрактів, підтримання зворотної сумісності API, написання миграцій даних CDC та переписання Saga-транзакцій (`β ≈ 15.0 ... 50.0`);
- `C_node` — постійні фіксовані витрати на інфраструктурне обслуговування одного виділеного сервісного процесу (резервування ресурсів RAM/CPU під Sidecar-контейнери Envoy/Fluentbit, підтримання окремого CI/CD конвеєра, репозиторію та панелей у Grafana).

## Сумарна функція архітектурного тертя та витрат (TCO)

Загальна функція вартості володіння та еволюції системи `C_total` складається з трьох ключових компонентів: витрат на розробку й рефакторингу `C_dev`, інфраструктурного чека `C_infra` та мережево-транзакційного податку `C_tax`:

```
C_total = C_dev + C_infra + C_tax
```

Розглянемо структуру цієї функції для двох порівнюваних архітектурних стилів.

### 1. Модель для Модульного моноліта (`N = 1`)

У Модульному моноліті всі класи та модулі знаходяться в єдиному адресному просторі. Зміна меж виконується компилятором чи середовищем розробки (`α = 1.0`), а міжсервісний мережевий та транзакційний податок є тотожно рівним нулю:

```
C_dev(1) = α · S · D_drift    [витрати на еволюцію коду в єдиній оперативній пам'яті]

C_infra(1) = 1 · C_node       [інфраструктурні витрати на розгортання єдиного монолітного процесу]

C_tax(1) = 0                  [відсутність мережевих затримок та Saga-оркестрацій]

C_monolith = α · S · D_drift + C_node    [сума розробки у пам'яті та 1 вузла інфраструктури]
```

### 2. Модель для Greenfield-мікросервісів (`N > 1`)

При розкрої нової системи на `N` мікросервісів із першого дня будь-яка зміна невизначеної межі вимагає мережевого рефакторингу (`β · N`), інфраструктурний чек зростає у `N` разів, а також виникає мережево-транзакційний податок `C_tax(N)`:

```
C_dev(N) = β · S · N · D_drift    [витрати на зміну мережевих API та миграцію ізольованих баз даних]

C_infra(N) = N · C_node           [інфраструктура для N сервісів та їхніх Sidecar-контейнерів]

C_tax(N) = N · L · Latency_Tax + P_fail · C_saga    [мережева затримка та обробка часткових відмов]

C_services = β · S · N · D_drift + N · C_node + C_tax(N)    [сума мережевої розробки, N вузлів та мережевого податку]
```

## Виведення критичного порогу доменної нестабільності

Знайдемо граничне значення нестабільності домену `D_drift*`, за якого витрати на сервісну архітектуру зрівнюються з витратами на Модульний моноліт:

```
α · S · D_drift* + C_node = β · S · N · D_drift* + N · C_node + C_tax(N)    [рівняння рівності C_monolith = C_services]
= α · S · D_drift* - β · S · N · D_drift* = (N - 1) · C_node + C_tax(N)      [перегрупування доданків з D_drift*]
= D_drift* · S · (α - β · N) = (N - 1) · C_node + C_tax(N)                   [винесення D_drift* за дужки]
= D_drift* = [(N - 1) · C_node + C_tax(N)] / [S · (α - β · N)]                [виведення порогу критичної волатильності]
```

Отриманий математичний результат показує фундаментальну залежність: знаменник виразу містить фактор `(α - β · N)`. Оскільки вартість мережевого рефакторингу `β` перевищує внутрішньопроцесорний `α` у десятки разів (`β / α ≈ 20`), для будь-якої кількості сервісів `N ≥ 2` знаменник стає від'ємним при високих значеннях `D_drift`.

Це означає, що при зростанні волатильності домену `D_drift` сумарні витрати на сервісну архітектуру зростають у `β · N` разів швидше за витрати на моноліт.

## Числовий розрахунок для стартапу на зеленому газоні

Підставимо числові параметри типового проєкту на етапі запуску:
- Чисельність інженерів: `S = 6` розробників;
- Спроба передчасного розкрою на: `N = 6` мікросервісів;
- Норматив рефакторингу у моноліті: `α = 1.0`;
- Мережевий норматив рефакторингу: `β = 20.0`.

Проведем детальний підрахунок знаменника функції:

```
S · (α - β · N)
= 6 · (1.0 - 20.0 · 6)    [підстановка параметрів S=6, N=6, α=1, β=20]
= 6 · (1.0 - 120.0)       [множення в дужках: 20 · 6 = 120]
= 6 · (-119.0)            [віднімання в дужках: 1 - 120 = -119]
= -714.0                  [підсумковий добуток: 6 · (-119) = -714]
```

Отримане значення `-714.0` показує, що на зеленому газоні, де волатильність домену прямує до максимуму (`D_drift → 1.0`), член `β · S · N · D_drift` стає домінуючим фактором у рівнянні TCO. Інженерна команда витрачатиме 95% свого робочого часу не на написання продуктових фіч, а на рефакторинг мережевих контрактів та синхронізацію міжсервісних меж.

## Математична деградація доступності та підсумування затримок

Окрім витрат на розробку `C_dev`, виділення `N` мережевих сервісів створює строгу математичну деградацію показників надійності та затримки системи.

### 1. Множення ймовірностей доступності (Availability Multiplication)

Якщо у Модульному моноліті доступність двох модулів тотожна доступності єдиного процесу (`A = 99.9%`), то у випадку синхронного ланцюжка з `N` мікросервісів підсумкова доступність обчислюється як добуток доступностей кожної мережевої ланки:

```
A_chain = A_1 · A_2 · A_3 · ... · A_N
```

При підставці `N = 10` сервісів із доступністю кожного `A_i = 0.999` (три дев'ятки), підсумкова доступність ланцюга становить:

```
A_chain = 0.999^10 ≈ 0.990    [зменшення доступності з 99.9% до 99.0%]
```

Падіння доступності з `99.9%` до `99.0%` означає збільшення незапланованого простою системи з **8.76 годин** до **87.6 годин на рік** (у 10 разів більше аварійних збоїв).

### 2. Ампліфікація хводових затримок (Tail Latency Amplification P99)

Розглянемо виклик, який послідовно проходить крізь `N` мікросервісів. Якщо кожен окремий сервіс має квантиль затримки `P99 = 100` мс (тобто 1% запитів виконуються довше 100 мс), ймовірність того, що клієнтський запит **не зіткнеться** із затримкою P99 на жодній з `N` ланок, становить `(1 - 0.01)^N`.

Відповідно, ймовірність потрапляння клієнтського запиту у повільний хвіст затримки обчислюється як:

```
P_tail_delay = 1 - (1 - 0.01)^N
```

Для `N = 10` послідовних сервісів маємо:

```
P_tail_delay = 1 - 0.99^10 = 1 - 0.904 = 0.096    [9.6% усіх користувацьких запитів гальмують]
```

Таким чином, майже кожен 10-й користувач відчує істотну затримку відповіді системи виключно через мережеву мультиплікацію хводових затримок P99.

## Три фази еволюції домену та підсумкова матриця

Математична модель дозволяє виділити три чіткі архітектурні фази життя системи залежно від волатильності домену та масштабу команди:

```
Фаза 1: Зелений газон (D_drift > 0.4) ─────► C_services >> C_monolith ──► МОДУЛЬНИЙ МОНОЛІТ
Фаза 2: Стабілізація (D_drift < 0.1) ─────► C_services ≈ C_monolith ──► ОЦІНКА КРИТЕРІЇВ
Фаза 3: Масштаб Конвея (S > 50) ──────────► C_monolith >> C_services ──► ВИДІЛЕННЯ СЕРВІСІВ
```

### Порівняльна матриця TCO для трьох системних профілів

| Параметр моделі | Стартап (Зелений газон) | Зрілий продуктовий бізнес | Корпоративний масштаб |
| :--- | :--- | :--- | :--- |
| **Кількість розробників (`S`)** | 4–8 інженерів | 15–30 інженерів | 100+ інженерів |
| **Волатильність домену (`D_drift`)** | 0.8–1.0 (дуже висока) | 0.1–0.2 (низька) | 0.05 (стабільна) |
| **Кількість сервісів (`N`)** | 1 (Модульний моноліт) | 3–5 (Прагматичні сервіси) | 20+ (DOMA / Сервіси) |
| **Головна стаття витрат** | Рефакторингове тертя | Операційне масштабування | Організаційна автономія |
| **Архітектурний вибір** | **Monolith-First** | **Прагматичний розкрій** | **Microservices** |

**Остаточний математичний висновок:** Стратегія Monolith-First є не стилістичною вподобанням, а жорстким математичним наслідком мінімізації функції TCO в умовах високої доменної невизначеності.
