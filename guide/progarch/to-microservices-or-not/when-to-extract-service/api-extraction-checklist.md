# 📋 Специфікація та оціночний чек-лист виділення сервісу

Цей довідник надає формальний архітектурний контракт, кількісну матрицю оцінки та операційний чек-лист готовності для ухвалення рішень про виділення нового сервісу з моноліта. Він слугує нормативним стандартом для проведення архітектурних ревю (Architecture Review Board) та складання документів ADR (Architecture Decision Record).

Специфікація встановлює жорсткі порогові значення для вимірюваних параметрів системи. Невиконання встановлених критеріїв веде до категоричного вето на створення нового мережевого сервісу, запобігаючи неконтрольованій появі наносервісів та розподілених монолітів.

## Розділ 1: Матриця кваліфікації обґрунтованих критеріїв

Для підтвердження доцільності виділення кандидат на сервіс мусить набрати позитивну оцінку щонайменше за **одним** із чотирьох фундаментальних критеріїв і надати цифровий доказ, отриманий з моніторингу або систем версіонування коду (метрики Prometheus, логи, CI/CD графіки, звіт CODEOWNERS).

Приймаючи рішення, архітектурний комітет оцінює не побажання розробників, а об'єктивні числові покажчики:

1. **Незалежний реліз-цикл (Deployment Velocity Mismatch):** Оцінюється різниця у частоті релізів між кандидатом та рештою моноліта. Якщо компонент потребує щоденного розгортання термінових фіч або A/B тестів, але змушений чекати тижневого релізного вікна моноліта через ризик зламати суміжні модулі, мережева межа стає обґрунтованою інвестицією. Оцінюються показники Lead Time for Changes та Deployment Frequency.
2. **Асиметричний масштаб та гетерогенні ресурси (Resource Profile Asymmetry):** Порівнюється профіль навантаження за чотирма основними ресурсами (CPU, RAM, Disk IO, GPU). Якщо 90% монолітного вузла споживає один-єдиний модуль (наприклад, кодування відео чи важка криптографія), горизонтальне масштабування всього моноліта означає марне витрачання 90% ресурсів на копіювання невикористовуваного коду.
3. **Ізоляція відмов та межі комплаєнсу (Fault & Security Boundary):** Оцінюються юридичні та системні ризики. Якщо компонент обробляє дані платіжних карток (зони PCI-DSS Level 1) або медичні записи (HIPAA), винесення його за мережеву межу дозволяє звузити контур аудиту безпеки до одного сервісу замість усього монолітного застосунку. Також сюди відносяться модулі із нестабільними сторонніми C-бібліотеками, краш яких не повинен валити процес ядра.
4. **Конвеївська автономія команд (Conway Organizational Seam):** Оцінюється кількість інженерів, які працюють над кодом. Коли кількість розробників моноліта перевищує 15–20 осіб, міжкомандні наради щодо міграцій бази даних та злиття PR перетворюються на бюрократичний кортор. Виділення сервісу під володіння однієї сформованої продуктової команди (від 4 до 8 людей) відновлює автономію розробки.

### Формальна таблиця оцінки критеріїв

| Критерій | Метрика оцінки | Порогове значення для схвалення | Необхідне документальне підтвердження |
| :--- | :--- | :--- | :--- |
| **1. Незалежний реліз-цикл** | Час очікування у черзі деплою та частота випусків | Різниця частоти релізів ≥ 5× (наприклад, модуль А котиться 10 разів на день, а решта моноліта — раз на 2 тижні) | Графіки Deployment Velocity з GitHub/GitLab за останні 60 днів |
| **2. Асиметричний масштаб** | Співвідношення CPU / RAM / Disk IO / GPU навантаження | Профіль споживання відрізняється від медіани моноліта ≥ 10× | Метрики Prometheus `node_cpu_seconds_total`, `container_memory_working_set_bytes` |
| **3. Ізоляція відмов та безпека** | Вимоги комплаєнсу (PCI-DSS, HIPAA) або ризик крашу процесу | Модуль містить C/C++ native кодеки або обробляє банківські картки (Zone 0) | Аудиторський висновок безпеки або логи системних крашів (SIGSEGV/OOM) |
| **4. Автономія команди (Конвей)** | Розмір команди та когнітивне навантаження | У моноліті працює ≥ 15 інженерів, а кандидат володіється окремою групою ≥ 4 людей | Організаційна структура компанії та карта розподілу володіння кодом (CODEOWNERS) |

### Порядок підрахунку балів критеріїв

Підсумковий кваліфікаційний індекс обчислюється за ваговевшеною формулою:

```
Кваліфікаційний бал = K1·Weight(Deployment) + K2·Weight(Scale) + K3·Weight(Security) + K4·Weight(Conway)
```

- Якщо сумарний бал < 1.0 — виділення сервісу **категорично заборонено**. Код залишається у моноліті у вигляді модуля.
- Якщо сумарний бал ≥ 1.0 — кандидат допускається до перевірки вето-дискваліфікаторами у Розділі 2.

## Розділ 2: Матриця дискваліфікаторів (Хибні приводи та вето)

Наявність хоча б **одного** з наведених нижче п'яти дискваліфікаторів веде до автоматичного накладення вето на виділення сервісу, незалежно від балів, набраних у Розділі 1. Цей перелік захищає архітектуру від передчасної складності.

Розглянемо детальніше сутність кожного вето-приводу:

- **VETO-01 (Clean Code Falsehood):** Найпоширеніша помилка початківців — намагатися виправити спагеті-код у моноліті шляхом створення сервісу. Якщо межа модуля всередині моноліта брудна й заплутана, перенесення її через мережу лише додасть затримки та мережеві помилки до існуючого хаосу. Спочатку потрібно провести рефакторинг та створити чистий мовний інтерфейс у пам'яті.
- **VETO-02 (Premature Scalability):** Спроба винести сервіс «під мільйони користувачів у майбутньому». Фінансова плата за мережу починається негайно, тоді як очікуваний трафік може не з'явитися ніколи. Архітектура повинна масштабуватися за реальними виміряними показниками навантаження.
- **VETO-03 (Shared Database Trap):** Сервіс створюється в окремому процесі, але продовжує читати або писати в таблиці бази даних моноліта. Це знищує незалежний деплоймент і створює приховане зчеплення на рівні схеми СУБД. Будь-яка міграція схеми `ALTER TABLE` ламатиме обидві частини системи одночасно.
- **VETO-04 (Entity-per-Service / Nano-services):** Нарізання сервісів за таблицями баз даних (наприклад, окремий сервіс `User`, окремий `Order`, окремий `Product`). Це призводить до появи наносервісів, де кожна бізнес-операція розгортається у каскад синхронних викликів. Граф викликів моноліта переноситься на мережу, створюючи катастрофічні затримки.
- **VETO-05 (Shared Library Coupling):** Виділені сервіси ділять спільну бізнес-бібліотеку з кодом домену. Будь-яке оновлення цієї бібліотеки змушує команди котити всі сервіси одночасно, скасовуючи переваги незалежного деплою.

### Таблиця вето-правил

| Код вето | Назва хибного приводу | Опис порушення меж | Формальні ліки замість розпилу |
| :--- | :--- | :--- | :--- |
| **VETO-01** | *Clean Code Falsehood* | Намір винести сервіс «щоб зробити код чистішим» без наявності ізольованого модуля у моноліті | Рефакторинг коду в окремий мовний модуль / пакет усередині моноліта |
| **VETO-02** | *Premature Scalability* | Заявка на розпил під гіпотетичний трафік, якого немає у поточних метриках | Скасування розпилу до досягнення 80% порогу навантаження моноліта |
| **VETO-03** | *Shared Database Trap* | Намір створити сервіс, що звертається до існуючих таблиць бази даних моноліта | Повне розділення схем і таблиць до моменту мережевого розпилу |
| **VETO-04** | *Entity-per-Service (Nano-services)* | Спроба винести окрему таблицю або одну сутність (CRUD над однією таблицею) | Злиття сутностей у єдиний Bounded Context за методологією DDD |

## Розділ 3: Формули та обмеження бюджетів надійності й затримок

Будь-який проєкт виділення сервісу повинен містити чіткий розрахунок трьох інженерних бюджетів. Якщо розрахункові значення виходять за встановлені нормативні межі, архітектурний комітет відхиляє заявку до виправлення топології.

### 1. Бюджет глибини синхронного ланцюжка (Max Chain Depth)

Заборонено створювати синхронні послідовні ланцюжки викликів між сервісами глибиною більше ніж 2:

```
N_sync_depth <= 2
```

Якщо для відповіді на запит користувача Сервіс А викликає Сервіс Б, а той викликає Сервіс В, який у свою чергу викликає Сервіс Г (ланцюжок глибиною N = 4) — архітектура вважається дискваліфікованою.
*Нормативні ліки:* Перехід на асинхронну публікацію подій (Event-Driven Architecture) або реплікацію даних у read-модель на рівні BFF.

### 2. Бюджет додаткової затримки (Latency Budget Floor)

Додаткова затримка, внесена мережевою межею нового сервісу на рівні P99, не повинна перевищувати 5% від загального SLA користувацького запиту:

```
T_extra_p99 = (T_serde + T_rtt + T_mesh) <= 0.05 · SLA_user_p99
```

Аналітичний приклад:
- Якщо `SLA_user_p99 = 200 мс`, то `T_extra_p99` не має перевищувати `10 мс`.
- Якщо мережевий виклик до нового сервісу додає 18 мс затримки, виділення синхронного сервісу відхиляється. Дозволяється лише асинхронна фонова обробка через чергу повідомлень.

### 3. Бюджет доступності ланцюжка (Availability Floor)

Підсумкова розрахункова доступність ланцюжка викликів з урахуванням нового сервісу повинна відповідати цільовому SLA продукту:

```
A_chain = A_monolith · A_new_service >= SLA_target
```

Якщо цільова доступність `SLA_target = 99.9%` (3 дев'ятки), а `A_monolith = 99.9%` і `A_new_service = 99.5%`, то підсумкова доступність `A_chain = 99.4%`, що порушує бюджет доступності й веде до вето.

## Розділ 4: Специфікація автономії даних (Data Ownership Verification)

Виділений сервіс вважається сервісом лише тоді, коли він повністю й беззастережно володіє своїми даними. Для проходження перевірки команда повинна надати формальне підтвердження виконання наступного чек-листа:

```
[ ] 1. ПРИВАТНЕ СХОВИЩЕ: Сервіс має власну базу даних (або окремий фізичний інстанс / ізольовану схему).
[ ] 2. ВІДСУТНІСТЬ CROSS-DB JOIN: Жоден SQL-запит або транзакція не об'єднує таблиці моноліта та нового сервісу.
[ ] 3. ЗАБОРОНА ЗВ'ЯЗКІВ FOREIGN KEY: Між таблицями моноліта та нового сервісу немає зовнішніх ключів на рівні СУБД.
[ ] 4. ШИНИ ПОДІЙ (OUTBOX PATTERN): Зміна стану в базі сервісу публікується у брокер подій через Transactional Outbox.
[ ] 5. КЕРУВАННЯ СХЕМАМИ ПОДІЙ: Усі події версіонуються через Schema Registry (Protobuf / Avro) з підтримкою backward compatibility.
```

Розберемо практичний зміст кожного з п'яти пунктів автономії даних:

1. **Приватне сховище:** База даних сервісу має бути закритою від зовнішніх підключень. Жоден інший сервіс або бізнес-модуль не має права підключатися до цієї бази під службовим користувачем СУБД.
2. **Відсутність Cross-DB JOIN:** Операції об'єднання даних між таблицями різних доменів виконуються у пам'яті на рівні application-коду або додатка BFF, а не SQL-оператором `JOIN` на рівні бази даних.
3. **Заборона Foreign Keys:** Зв'язки між ідентифікаторами сутностей зберігаються як звичайні UUID / integer значення без створення індексу зовнішнього ключа на рівні СУБД, оскільки це унеможливлює фізичний розпіл баз на різні сервери.
4. **Transactional Outbox Pattern:** Зміна бізнес-сутності та запис події у таблицю `outbox` виконуються в одній локальній ACID-транзакції бази сервісу. Окремий фоновий процесор (Debezium / Kafka Connect) зчитує outbox-таблицю й публікує події у брокер.
5. **Schema Registry & Versioning:** Контракти подій визначаються у protobuf/avro файлах із чіткими правилами сумісності (Backward/Forward Compatibility). Руйнівні зміни схем категорично заборонені.

## Розділ 5: Операційний чек-лист готовності інфраструктури (Operational Readiness Gate)

Перш ніж переключити реальний продуктивний трафік моноліта на новий виділений сервіс, команда розробки зобов'язана виконати інфраструктурні стандарти готовності (Production Readiness Review):

### 1. Обов'язкові ендпоінти перевірки здоров'я (Health Checks)

Сервіс повинен надавати три окремі HTTP/gRPC ендпоінти для кубернетес-проб:

- `/livez` (Liveness probe): повертає HTTP 200, якщо процес живий та не заблокований взаємним блокуванням потоків (Deadlock).
- `/readyz` (Readiness probe): повертає HTTP 200 лише тоді, коли сервіс успішно підключився до своєї бази даних, брокера подій та готовий приймати мережевий трафік.
- `/healthz` (Detailed health): розширений інспекційний ендпоінт внутрішніх компонентів для діагностики під час чергування.

### 2. Обов'язкові стандартні метрики (Prometheus RED Pattern)

Сервіс зобов'язаний експортувати метрики за стандартом RED (Rate, Errors, Duration):

- `http_requests_total{service="X", status="2xx|4xx|5xx"}` — загальна кількість запитів та розподіл кодів відповідей.
- `http_request_duration_seconds_bucket{service="X", le="..."}` — гістограма затримок викликів для розрахунку P50, P95 та P99.
- `app_queue_depth{service="X"}` — глибина внутрішніх черг обробки для виявлення заторів.

### 3. Наскрізне трасування (OpenTelemetry Tracing)

Сервіс зобов'язаний витягувати заголовок `traceparent` із вхідних запитів, збагачувати його власним `span_id` та передавати у всі вихідні HTTP/gRPC виклики та події Kafka.

### 4. Інфраструктурне забезпечення (SLA Pod Requirements)

```
- Minimum Replica Count: 2 (Multi-AZ Deployment)
- Resource Limits: memory limit <= 2 * memory request
- Graceful Shutdown: SIGTERM handling with 30s drain window
- Rolling Update Strategy: maxSurge = 25%, maxUnavailable = 0
```

## Розділ 6: Шаблон документа ADR для виділення сервісу

Для ухвалення рішення на архітектурному комітеті команда зобов'язана заповнити наступний стандартний документ ADR (Architecture Decision Record):

```markdown
# ADR-0XX: Виділення сервісу [Назва Сервісу] з моноліта

## Статус: [Пропоновано / Схвалено / Відхилено]
## Автор: [Ім'я Архітектора / Ліда]
## Дата: [YYYY-MM-DD]

### 1. Кваліфікація за критеріями (Розділ 1)
- Обраний критерій: [Незалежний деплой / Асиметричний масштаб / Безпека / Конвей]
- Поточні метрики болю: [Вказати числа: затримка релізу в днях, CPU % моноліта, розмір бази]
- Очікуваний виграш від мережевої межі: [Конкретні цифри]

### 2. Перевірка дискваліфікаторів (Розділ 2)
- VETO-01..VETO-05 перевірено: [ТАК / НІ]
- Чи існує ізольований модуль у моноліті: [ТАК / НІ]

### 3. Розрахунок бюджетів (Розділ 3)
- Максимальна глибина синхронного ланцюга (N): [Вказати N]
- Додаткова затримка P99 (T_extra): [Вказати мс]
- Розрахункова доступність (A_chain): [Вказати %]

### 4. План автономії даних (Розділ 4)
- Назва нової бази даних: [наприклад, Postgresql / Cassandra]
- Стратегія міграції даних: [Outbox pattern / Dual writing]

### 5. Інфраструктурний кошторис (TCO)
- Очікувані витрати на Pods / Cloud: [$X / місяць]
```
