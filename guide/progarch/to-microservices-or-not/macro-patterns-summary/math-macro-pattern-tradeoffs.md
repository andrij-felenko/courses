# 🧮 Математична модель витрат та доступності макро-патернів

Ця математична вставка будує формальні моделі розповсюдження затримок (p99 latency cascade), загальної доступності системи (availability breakdown), теорії масового обслуговування для черг та операційної складності для п'яти макро-патернів організації систем, виводячи точний поріг перетину доцільності розколу моноліта на розподілені вузли.

## 1. Модель затримки та деградації хвоста (p99 Latency Cascade)

Розглянемо бізнес-операцію, що вимагає послідовної обробки в `K` функціональних вузлах (наприклад: Перевірка прав → Отримання профілю → Розрахунок знижки → Формування замовлення → Ініціалізація платежу).

Позначимо затримку обробки в пам'яті всередині одного процесу як `t_proc`, а затримку мережевого стрибка (серіалізація JSON/Protobuf, сокетний ввід-вивід, RTT мережі, TLS-шифрування) як `t_net`.

### Модульний моноліт (виклики у спільному адресному просторі):
Усі `K` вузлів викликаються як звичайні функції мови програмування через таблицю віртуальних методів або прямі адреси в пам'яті.

```
T_monolith = ∑(t_proc[i])   [i від 1 до K]
```

Оскільки `t_proc` вимірюється в наносекундах (10–100 ns), загальна затримка обчислень становить одиниці мікросекунд, а основний час витрачається на єдину транзакцію в БД:

```
T_total_monolith = ∑(t_proc[i]) + t_db_commit ≈ 2.5 ms
```

### Мікросервіси або Розподілений моноліт (послідовний синхронний ланцюг):
Кожен із `K` вузлів винесено в окремий мережевий процес.

```
T_dist = ∑(t_proc[i] + t_net[i])   [i від 1 до K]
= ∑(t_proc[i]) + K · t_net         [якщо t_net стабільне]
```

Якщо `t_net` у середньому становить 5–12 ms (з урахуванням серіалізатора та проходження через Service Mesh / Sidecar proxy), а `t_proc` — 1 ms, то для `K = 5` послідовних синхронних викликів:

```
T_monolith = 5 · 1 ms + 2 ms (DB) = 7 ms
T_dist = 5 · 1 ms + 5 · 10 ms + 5 · 2 ms (N DBs) = 65 ms
```

Затримка зростає у 9.2 раза на порожньому місці — виключно через наявність мережевих меж.

### Ймовірнісна деградація квантиля p99 в мережевих ланцюгах:
Нехай затримка одного мережевого виклику є випадковою величиною `X` із функцією розподілу `F(t) = P(X ≤ t)`. Позначимо через `p` імовірність того, що поодинокий виклик вкладеться в запланований SLA (наприклад, `p = 0.99` для p99 = 10 ms).

При послідовному синхронному виклику `K` незалежних сервісів підсумкова затримка операції дорівнює сумі випадкових величин. Ймовірність того, що **кожен** із `K` викликів вкладеться в межі свого p99 квантиля, визначається як добуток незалежних ймовірностей:

```
P_chain_success(K) = ∏(p[i])   [i від 1 до K]
P_chain_success(K) = p^K       [при однакових p]
```

Розглянемо деградацію якості обслуговування при рості глибини ланцюга `K` для `p = 0.99`:

```
K = 1  → P = 0.99¹ = 0.9900  (1.0% аномально повільних відповідей)
K = 3  → P = 0.99³ = 0.9703  (3.0% аномально повільних відповідей)
K = 5  → P = 0.99⁵ = 0.9510  (4.9% аномально повільних відповідей)
K = 10 → P = 0.99¹⁰ = 0.9044 (9.6% аномально повільних відповідей — кожен 10-й запит гальмує!)
K = 20 → P = 0.99²⁰ = 0.8179 (18.2% аномально повільних відповідей — кожен 5-й запит гальмує!)
```

**Математичний висновок**: Синхронний ланцюг у мікросервісах або розподіленому моноліті експоненціально накопичує хвости затримок. Модульний моноліт має `K = 1` для зовнішнього мережевого зв'язку, тому його p99 зберігає вихідну стабільність.

## 2. Модель системної доступності та каскадні відмови (Availability Breakdown)

Розглянемо надійність системи. Нехай кожен з `K` вузлів має власну коефіцієнтну доступність `A[i] ∈ [0, 1]`, яка визначається як відношення часу справної роботи (Uptime) до загального часу.

### Синхронна послідовна топологія (Мікросервіси без фалбеків або Розподілений моноліт):
Якщо для виконання бізнес-транзакції потрібна синхронна участь усіх `K` вузлів, система утворює послідовне з'єднання в теорії надійності. Загальна доступність системи визначається як:

```
A_system = ∏(A[i])   [i від 1 до K]
```

Для вузлів із високим рівнем доступності `A[i] = 0.999` (три дев'ятки, що відповідає ~8.76 годинам простою на рік):

```
K = 1  → A_system = 0.9990  (~8.76 годин простою на рік)
K = 3  → A_system = 0.9970  (~26.3 годин простою на рік)
K = 5  → A_system = 0.9950  (~43.8 годин простою на рік)
K = 10 → A_system = 0.9900  (~87.6 годин простою на рік — доступність впала до двох дев'яток!)
K = 50 → A_system = 0.9512  (~427 годин простою на рік — катастрофа для бізнесу!)
```

Синхронний розкрій системи на `K` мережевих вузлів **помножує недоступність** у `K` разів.

### Компенсація через паттерн Circuit Breaker та асинхронну розв'язку:
Щоб запобігти каскадному падінню доступності, в ізольованих мікросервісах застосовують асинхронні канали зв'язку (Broker / Transactional Outbox) та запобіжники (Circuit Breakers).

Якщо вузол `B` стає недоступним, запобіжник розмикає ланцюг, а вузол `A` повертає дегродрану відповідь (Fallback) або зберігає подію в журнал. Тоді підсумкова доступність прийому запитів відновлюється до доступності поодинокого вузла:

```
A_accept = A[A] = 0.999
```

Однак це вимагає від розробників написання складного коду обробки часткових відмов (Partial Failure Handling), якого взагалі не існує в модульному моноліті.

## 3. Теорія масового обслуговування та пропускна здатність (Queueing Theory)

Згідно з **законом Літтла** (Little's Law), середня кількість запитів у системі `L` дорівнює добутку середньої інтенсивності вхідного потоку `λ` на середній час обслуговування `W`:

```
L = λ · W
```

У мікросервісах через додавання мережевої затримки середній час обслуговування запиту `W` зростає в `N` разів (`W_dist = W_monolith + K · t_net`).

Якщо інтенсивність трафіку `λ` залишається незмінною, кількість одночасних активних запитів `L`, що утримують потоки виконання (Thread Pool) та сокети, зростає пропорційно:

```
L_dist = λ · (W_monolith + K · t_net)
```

Це пояснює, чому розподілений моноліт з синхронними викликами швидко вичерпує пули потоків серверів застосунків (Thread Pool Exhaustion) під навантаженням і падає через каскадне вичерпання ресурсів.

## 4. Графова модель складності мережевих меж (Inter-Service Edge Complexity)

Оцінимо складність зв'язків у системі з `N` доменних контекстів за допомогою теорії графів.

Позначимо через `E` кількість потенційних інтерфейсних зв'язків між контекстами.

### Погано розрізана система (Розподілений моноліт):
Якщо кожен сервіс може довільно кликати інші сервіси по мережі або заглядати в їхні бази даних, граф залежностей стає повним графом $K_N$:

```
E_max = N · (N - 1) / 2 = O(N²)
```

Для `N = 10` сервісів кількість мережевих зв'язків, які необхідно документувати, версіонувати та захищати mTLS, дорівнює:

```
E_max = 10 · 9 / 2 = 45 меж
```

### Модульний моноліт з ієрархічною архітектурою:
У модульному моноліті виклики між модулями підпорядковані суворій шаруватій або гексагональній архітектурі (наприклад, Дерево залежностей чи Directed Acyclic Graph — DAG):

```
E_monolith = O(N)
```

Для `N = 10` модулів кількість внутрішньопроцесових меж не перевищує 9–12 строго контрольованих фасадів.

## 5. Формалізована математична модель витрат (Total Cost of Ownership)

Підсумкова економічна вартість утримання системи `C_total` визначається як функція від кількості обмежених контекстів `N` та кількості фізичних деплоймент-одиниць `K`:

```
C_total(N, K) = C_dev(N) + C_infra(N, K) + C_ops(N, K)
```

### 1. Модульний моноліт (`K = 1`, `N` модулів у єдиному бінарнику):
```
C_infra = C_server_instance + C_primary_db
C_ops = O(1)   [1 CI/CD пайплайн, 1 дашборд моніторингу, 1 артефакт]
C_dev = O(N)   [пряма лінійна складність бізнес-коду]

C_monolith = C_server_instance + C_primary_db + O(1) + O(N)
```

### 2. Мікросервісна система (`K = N`, кожен контекст у своєму сервісі):
```
C_infra = N · C_container_min + N · C_db_instance + C_mesh + C_egress_traffic
C_ops = O(N · log N)   [N CI/CD пайплайнів, N сервіс-мешів, трасування]
C_dev = O(N) + O(K_inter_service_contracts)   [версіонування API, саги, DTO-мапери]

C_microservices = N · (C_container_min + C_db_instance) + O(N · log N) + O(N)
```

### Формула поргу розколу (Break-even Threshold):
Розкрій модульного моноліта на `K` сервісів є математично та економічно обґрунтованим лише тоді, коли значення вигоди від автономії розгортання окремих команд `V_autonomy(K)` перевищує надбавку за розподіленість (Microservice Premium):

```
V_autonomy(K) > C_microservices - C_monolith
```

Оскільки для малих команд (`Teams < 4`) значення `V_autonomy ≈ 0`, різниця `C_microservices - C_monolith` стає чистим фінансовим та часовим збитком компанії. Це математично доводить, чому Модульний Моноліт є єдино правильним дефолтним стартовим макро-патерном.
