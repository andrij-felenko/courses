# ⚙️ Одна потреба білінгу трьома стилями — і що ламає перейменування колонки

Меню з чотирьох стилів ми вже розклали, а пастку спільної бази назвали словами. Але словам легко кивнути й піти писати `JOIN` далі — звичка сильніша за пораду. Різницю, від якої звичка справді відступає, дає не схема на дошці, а код, що ліг на диск і чекає наступного релізу сусіда. Тож візьмімо **одну** потребу Digital Homes і зберімо її **тричі**: сирим `JOIN`-ом у чужу таблицю, синхронним викликом до власника, власною проєкцією на подіях. Та сама потреба щоразу — а поміряємо на кожній три речі: **до чого білінг причепився** (схема, контракт чи факт-подія), **наскільки свіжі дані** він бачить і **що саме трісне**, коли власник за стіною змінить одне слово в своїй схемі.

Одразу пуант, щоб тримати його весь розбір: код усіх трьох майже однаковий за обсягом, і жоден при написанні не виглядає ні розумнішим, ні дурнішим за інші. Різниця спить доти, доки власник пристроїв не перейменує колонку `active` на `status`. Отоді один зі стилів тихо збреше в рахунку, другий встоїть, третій навіть не помітить руху — і саме те, що трісне (або не трісне), **заднім числом** називає, до чого ти насправді причепився.

## Задача — одна потреба, прибита цвяхами

Випишімо її точно. Наприкінці місяця білінг виставляє рахунок за домом за формулою «активних пристроїв × ціна за пристрій». Тобто йому треба одне число: **скільки пристроїв у домі зараз активні**. А пристроями володіє **інший** контекст — «Пристрої», — і саме він тримає таблицю, де цей факт живе:

```sql
-- ВЛАСНІСТЬ контексту «Пристрої». Білінг тут — чужий, що зайшов по число.
CREATE TABLE devices (
  id       TEXT PRIMARY KEY,
  home_id  INTEGER NOT NULL,
  active   BOOLEAN NOT NULL DEFAULT false   -- ← слово, яке за пів року стане status
);
```

Щоб порівняння було чесним, прибиваємо цвяхами все, крім самого стилю. Потреба **одна** — число активних на дім. Схема власника **одна** — та, що вгорі. І весь службовий код обох контекстів — **одна мова, TypeScript**: хмарний бекенд DH живе на Node, тож і білінг, і сервіс пристроїв, і обробник подій говорять нею. Це не дрібниця. Напиши я `JOIN` на Python, RPC на Go, а проєкцію на Rust — і не розбереш, звідки взялася різниця: від стилю інтеграції чи від мови. Прибиваємо мову — тоді все, що побачимо, належить **стилю** й нічому більше. Міняється рівно одне: **де** живе спільне число й **через що** воно долає межу між контекстами.

Три осі, які намацуватимемо на кожному стилі: до чого білінг **зчеплений** (що мусить лишитися незмінним, щоб він працював); яку **свіжість** дає стиль (число «зараз» чи «якийсь час тому»); і що станеться, коли власник **змінить свою внутрішню схему**, нікого не спитавши, — бо він має на це повне право, це ж його таблиця.

## Стиль перший — спільна таблиця, сирий JOIN

Найпряміший шлях: білінг просто читає чужу таблицю. Ніякого API, ніякої серіалізації — один запит, і чуже число твоє.

```sql
-- Білінг рахує активних, читаючи ТАБЛИЦЮ контексту пристроїв напряму
SELECT count(*)::int AS active_devices
FROM devices
WHERE home_id = $1 AND active = true;
```

У коді білінгу це кілька рядків на `pg`:

```ts
// billing/active-count.ts — білінг тримає з'єднання ДО БАЗИ ПРИСТРОЇВ
async function activeDeviceCount(devicesDb: Pool, homeId: number): Promise<number> {
  const { rows } = await devicesDb.query(
    `SELECT count(*)::int AS n
       FROM devices
      WHERE home_id = $1 AND active = true`,   // ← ім'я таблиці, колонки й зміст «active=true»
    [homeId],
  );
  return rows[0].n;
}
```

Придивімося, до чого тут причепився білінг, бо це не «до пристроїв» узагалі, а до дуже конкретного. Він причепився до **імені таблиці** `devices`, до **імені колонки** `home_id`, до **імені колонки** `active`, до її **типу** (булеве) і — найтонше — до її **змісту**: що `active = true` означає саме «пристрій зараз увімкнений і рахується в рахунок». Це не вузький контракт на два слова, це залежність від **схеми** — найдетальнішого опису даних, що взагалі існує. Кожна з цих п'яти зачіпок мовчить, доки схема не рухається, і кожна — зведений міст, яким білінг заліз у чужий дім.

Свіжість тут **ідеальна**: білінг читає джерело істини напряму, тож бачить число тієї самої миті, коли воно правдиве, без жодного лагу. За це, власне, спокуса й тримається — свіжо, миттєво, п'ять рядків. Але цю ціну ми ще не заплатили; рахунок прийде в розділі про перейменування, і саме він виявиться найдорожчим із трьох.

## Стиль другий — синхронний виклик до власника

Тепер винесімо число за **явну межу**. Білінг більше не знає про таблицю нічого; він знає лише **контракт**, який контекст пристроїв опублікував і пообіцяв тримати:

```ts
// devices/contract.ts — ВЛАСНИК публікує це; білінг залежить від ЦЬОГО, не від таблиці
export interface DeviceCatalog {
  activeCount(input: { homeId: number }): Promise<{ count: number }>;
}
```

Реалізацію тримає власник — і всередині вона робить рівно той самий запит, що й білінг робив у стилі першому. Але тепер запит живе **по той бік межі**, у коді того, хто володіє таблицею:

```ts
// devices/service.ts — усередині контексту пристроїв, за його власною стіною
class DevicesService implements DeviceCatalog {
  constructor(private db: Pool) {}                    // ← ЙОГО база, тільки його

  async activeCount({ homeId }: { homeId: number }): Promise<{ count: number }> {
    const { rows } = await this.db.query(
      `SELECT count(*)::int AS n
         FROM devices
        WHERE home_id = $1 AND active = true`,          // той самий SQL — але це ЙОГО SQL
      [homeId],
    );
    return { count: rows[0].n };
  }
}
```

А білінг тепер тримає в руках не рядок SQL, а виклик:

```ts
// billing/active-count.ts — жодного знання про таблицю, лише про обіцяну форму
const { count } = await devices.activeCount({ homeId: 42 });
```

Зчеплення переїхало. Білінг більше не причеплений до п'яти імен зі схеми — він причеплений до **однієї обіцянки**: є метод `activeCount`, він бере `{ homeId }` і повертає `{ count }`, і `count` означає «активних пристроїв у домі зараз». Уся внутрішня схема власника сховалася за цією обіцянкою; білінг її не бачить і бачити не мусить. Свіжість лишилася **живою** — виклик синхронний, відповідь відображає стан тієї самої миті, як і прямий `JOIN`.

Але зчеплення, як завжди, не зникло — воно **змінило валюту**. Замість зчеплення схемою білінг тепер зчеплений із власником **у часі**: `await` означає, що обидва мусять бути живі одночасно, і якщо сервіс пристроїв лежить у мить нарахування — білінг стоїть і чекає або падає з ним разом. Плюс друга ціна, яку власник статті вже назвав: рахунок місячний, а виклик — на кожен дім окремо, тож заради звіту раз на місяць білінг зробить **тисячі** синхронних оборотів по мережі. Живе число «зараз» коштує саме цього: обидва вгорі, і по стрибку на кожну відповідь.

## Стиль третій — власна проєкція на подіях

Третій шлях відвертає напрям потоку. Замість білінга, що **тягне** число (сам читає таблицю чи сам кличе власника), тепер власник **штовхає** факти, а білінг веде з них власну копію. Контекст пристроїв публікує дві доменні події — щоразу, коли пристрій оживає чи гасне:

```ts
// devices ПУБЛІКУЄ факти, а не свою схему. Це — увесь контракт між контекстами.
type DeviceEvent =
  | { type: "device.activated";   deviceId: string; homeId: number; at: number }
  | { type: "device.deactivated"; deviceId: string; homeId: number; at: number };
```

Білінг тримає **свою власну** табличку — приватну, у своїй базі, якої власник пристроїв ніколи не бачить. У ній він складає ці факти докупи. Наївний порив — тримати один лічильник на дім і робити `+1`/`−1` на кожну подію; але лічильник тече, щойно подія прилетить двічі або не в тому порядку, а під мережею і те, і те — щоденна норма. Тому проєкцію ведемо **на стан пристрою**, а не на дельту лічильника:

```sql
-- ВЛАСНІСТЬ БІЛІНГА. Приватна табличка білінга, власник пристроїв її не знає.
CREATE TABLE home_device_state (
  device_id TEXT PRIMARY KEY,
  home_id   INTEGER NOT NULL,
  active    BOOLEAN NOT NULL,
  at        BIGINT  NOT NULL          -- час події: щоб пізніша перемагала, а дубль був пустим
);
```

Обробник згортає кожну подію в цю табличку. Ключовий рядок — умова `at > ...at`: вона робить згортку **ідемпотентною** (повторна доставка несе той самий `at`, тож `>` хибне — подія просто нічого не змінює) і **стійкою до переупорядкування** (стара подія, що приповзла із запізненням, програє свіжішому станові). Ось той самий обробник двома ідіомами — TypeScript, як усюди в DH, і Go, рідний дім споживачів подій, де явний `Exec` показує згортку без жодного ORM:

:::tabs
```ts
// billing/projection.ts — згортаємо ПОДІЮ у власну табличку
async function onDeviceEvent(db: Pool, e: DeviceEvent): Promise<void> {
  const active = e.type === "device.activated";
  await db.query(
    `INSERT INTO home_device_state (device_id, home_id, active, at)
     VALUES ($1, $2, $3, $4)
     ON CONFLICT (device_id) DO UPDATE
       SET active = EXCLUDED.active, at = EXCLUDED.at
       WHERE EXCLUDED.at > home_device_state.at`,   // дубль/стара подія → пустий хід
    [e.deviceId, e.homeId, active, e.at],
  );
}

// нарахування читає ВЛАСНУ табличку — ні виклику, ні чужої схеми, ні чужого «вгорі»
async function activeDeviceCount(db: Pool, homeId: number): Promise<number> {
  const { rows } = await db.query(
    `SELECT count(*)::int AS n
       FROM home_device_state
      WHERE home_id = $1 AND active = true`,
    [homeId],
  );
  return rows[0].n;
}
```
```go
// billing/projection.go — та сама згортка, явним SQL без ORM
func onDeviceEvent(db *sql.DB, e DeviceEvent) error {
    active := e.Type == "device.activated"
    _, err := db.Exec(`
        INSERT INTO home_device_state (device_id, home_id, active, at)
        VALUES ($1, $2, $3, $4)
        ON CONFLICT (device_id) DO UPDATE
            SET active = EXCLUDED.active, at = EXCLUDED.at
            WHERE EXCLUDED.at > home_device_state.at`, // дубль/стара подія → пустий хід
        e.DeviceID, e.HomeID, active, e.At)
    return err
}

// нарахування читає ВЛАСНУ табличку білінга
func activeDeviceCount(db *sql.DB, homeID int) (int, error) {
    var n int
    err := db.QueryRow(`
        SELECT count(*) FROM home_device_state
        WHERE home_id = $1 AND active = true`, homeID).Scan(&n)
    return n, err
}
```
:::

Дві мови — той самий задум: подія-факт заходить, стан пристрою оновлюється, а число нарахування береться з **власної** таблиці білінга. Зчеплення переїхало втретє — тепер білінг причеплений лише до **форми події** (`device.activated` з полями `deviceId`, `homeId`, `at`), і більше ні до чого: ні до чужої таблиці, ні навіть до того, щоб власник був **живий** у мить нарахування. Це найслабше зчеплення з трьох.

Ціну теж видно одразу, і вона інша, ніж у попередніх. Свіжість тут **кінцева** (англ. *eventual*): білінгове число відстає від правди рівно на час доставки події — зазвичай мілісекунди, але якщо споживач відстав, дріф росте. Білінг більше не читає джерело істини — він читає **свою тінь** джерела, яка наздоганяє його з лагом. За розчеплення в часі й у схемі платиш тим, що твоє число майже правдиве, а не строго правдиве.

> 🔧 **Навіщо це.** Умова `WHERE EXCLUDED.at > ...at` — не оздоба, а різниця між проєкцією, що тримає правду, і лічильником, що поволі бреше. Доставку подій майже завжди роблять «щонайменше раз», тобто дубль — не аварія, а гарантія; а мережа переупорядковує повідомлення без попиту. Наївний `+1`/`−1` під цими двома фактами накопичує помилку тихо: одного місяця дім має 7 активних, а білінг думає, що 9, і виставляє рахунок на два зайвих пристрої. Згортка на стан пристрою з часовою печаткою робить [повтори й переупорядкування нешкідливими за побудовою](guide:progarch/duplicates-and-reorder) — те, що по-іншому вимагало б окремого шару [ідемпотентності](book:programming/idempotency), тут лягає в один `WHERE`.

## Удар: власник перейменовує active → status

Тепер той самий рух, заради якого весь розбір і затіяно. Команда пристроїв дозріла: булеве `active` замало — пристрій буває не лише «увімкнений/ні», а ще й «у процесі підготовки», «знятий із гарантії», «архівний». Тож вони роблять цілком розумну міграцію своєї **власної** схеми:

```sql
-- Міграція В КОНТЕКСТІ ПРИСТРОЇВ. Їхня таблиця, їхнє право.
ALTER TABLE devices DROP COLUMN active;
ALTER TABLE devices ADD  COLUMN status TEXT NOT NULL DEFAULT 'inactive';
--                                    ^ тепер стан — 'active' | 'inactive' | 'provisioning' | 'retired'
```

Пройдімо цією зміною по всіх трьох стилях і подивімося, де трісне.

**Стиль перший — спільна таблиця — ламається, і це найгірший із двох варіантів злому.** Колонки `active` більше нема, тож запит білінга `WHERE active = true` кидає `ERROR: column "active" does not exist` — на **наступному** нарахуванні, у **чужому** on-call. І найтихіше в цьому те, **чому** ніхто не попередив: команда пристроїв прогнала свої тести — вони зелені, бо їхній код на `active` більше не спирається; CI зелений, бо про запит білінга він нічого не знає — той запит живе рядком-текстом, а не спільним білдом. Залежність була **невидима**, тож і зламалася невидимо для того, хто ламав. Але є ще гірший сценарій, ніж чесна помилка. Уяви, що команда пристроїв, аби «нікого не зачепити», **лишає** стару колонку `active`, але переосмислює її — тепер `active` означає «рядок не видалено», а справжнє увімкнення переїхало в `status = 'active'`. Тоді запит білінга **не падає**. Він далі зелений, далі рахує — але рахує **не той набір**, бо бере всі невидалені пристрої замість увімкнених. Рахунки місяцями йдуть завищені, ніхто не бачить помилки, аж поки клієнт не оскаржить свій рахунок. Зчеплення було на **зміст** колонки, а в змісту немає компілятора: ніщо не крикне, коли слово тихо змінило значення.

**Стиль другий — RPC — встоює цілий.** Власник міняє свою схему й править **свій** запит усередині `activeCount`: тепер там `WHERE status = 'active'`. Контракт при цьому — той самий: `activeCount({ homeId }) → { count }`, і зміст `count` не зрушив. Білінгів виклик `await devices.activeCount({ homeId })` не міняється ні на символ, компілюється й біжить, як біг. Межа **вбрала** зміну в себе: те, що для стилю першого було зламом, тут відбулося цілком усередині власника, за стіною, якої білінг не переходить. Приватність схеми, яку спільна таблиця віддала, контракт повернув.

**Стиль третій — проєкція — навіть не помічає руху.** Білінг не читає таблицю пристроїв — ні прямо, ні через виклик. Він читає **свою** `home_device_state`. Доки контекст пристроїв на перейменування `active → status` далі **випускає** ті самі події `device.activated` / `device.deactivated` тієї самої форми, білінгова згортка працює незмінно, бо спирається на **факт-подію**, а не на сховище, з якого той факт народився. Незалежність тут навіть глибша за RPC: RPC вцілів, бо контракт не зрушив, але білінг усе одно мусив би **дочекатися** живого власника; проєкція ж не потребує власника вгорі взагалі — вона вже має все потрібне у своїй таблиці. Внутрішня схема власника для неї — річ, якої вона ніколи не торкалася.

![Три горизонтальні доріжки однієї потреби, ліворуч у кожній коробка «Білінг», праворуч зона «Контекст пристроїв» зі своєю таблицею. Вертикальний червоний зигзаг-розряд «перейменування active → status» проходить крізь усі три на межі власності. Верхня доріжка «спільна таблиця»: стрілка від білінга протикає стіну власності й встромляється просто в таблицю devices — розряд розриває цю стрілку, червоний підпис «тріщина тут: column active does not exist / або тихо не той набір». Середня «RPC»: стрілка білінга впирається в плитку-контракт «activeCount → count» на стіні, за плиткою — таблиця власника; розряд б'є в таблицю ЗА контрактом, стрілка й плитка цілі, зелений підпис «зміна всередині власника — контракт той самий». Нижня «проєкція»: у білінга СВОЯ маленька таблиця, від власника до неї тонка стрілка-подія «device.activated», розряд б'є в таблицю власника, подія й білінгова таблиця недоторкані, зелений підпис «білінг чужого сховища взагалі не читає».](/guide/progarch/to-microservices-or-not/integration-styles-choice/img/rename-hit-three-styles.svg)

*Один рух власника — і три різні наслідки. Спільна таблиця тріскає, бо білінгова стрілка простромила стіну власності просто в чужу схему. RPC вбирає зміну за контрактом. Проєкція живе окремо — власникове сховище для неї не існує. Де лягла тріщина, там і був твій справжній міст.*

> 🔧 **Навіщо це.** Перейменування колонки — найдешевший у світі спосіб дізнатися, до чого ти насправді причепився, не питаючи нікого. На рев'ю чужого пул-реквесту з міграцією `active → status` ти не побачиш ні білінга, ні його запиту — вони в іншому репозиторії, в іншій команді. Тому питання «хто зламається від цієї міграції?» має ставити не рев'ю, а **сама форма інтеграції**: якщо між контекстами лежить сира таблиця, відповідь — «хтось, і дізнаємось на його черговому нарахуванні»; якщо контракт чи подія — «ніхто, бо зміна не переходить стіни». Правило на щодень: коли мусиш зазирнути в число з чужого контексту, спитай себе, що станеться, коли власник перейменує в себе одну колонку. Спокійна відповідь на це питання і є мірою того, чи правильний міст ти будуєш.

## Три рахунки поруч

Спинімося й покладімо три стилі на ті самі три осі, бо саме контраст — уся сіль. Той самий рядок потреби, той самий SQL усередині — а причеплений білінг щоразу до іншого, свіжість щоразу інша, і перейменування б'є щоразу деінде.

| | Білінг зчеплений із | Свіжість числа | Перейменування `active→status` | Додаткова ціна стилю |
|---|---|---|---|---|
| **Спільна таблиця** | **схемою** власника: таблиця + колонка + тип + зміст | жива, джерело істини | **ламає**: жорстка помилка або тихо не той набір | розподілений моноліт; власник не може рефакторити своє |
| **RPC-виклик** | **контрактом**: `activeCount → count` | жива, синхронна відповідь | **цілий**: зміна за стіною контракту | зчеплення в часі (обидва вгорі); тисячі викликів на звіт |
| **Проєкція на подіях** | **фактом-подією**: форма `device.activated` | **кінцева** (лаг доставки) | **цілий**: власника взагалі не читає | дублі/переупорядкування, добудова з нуля, лаг |

Тепер видно, що зчеплення нікуди не поділося — воно **переїхало трьома зупинками**: схема → контракт → подія. І кожен переїзд купує власникові більше свободи міняти свої нутрощі — ціною іншого податку на білінг. Спільна таблиця не бере з білінга нічого наперед, зате замикає власникову схему в кайдани: перейменувати колонку він уже не сміє. RPC звільняє власникову схему, але прив'язує білінг у часі й гатить мережею на кожен дім. Проєкція звільняє і схему, і час, зате кладе на білінг цілий новий клопіт — вести похідну копію, добудовувати її й терпіти, що вона трохи відстала. **«Найкращого» стилю тут нема** — є три різні рахунки, і потреба сама каже, який із них по кишені: місячному звітові кінцева свіжість байдужа, тож найдорожче зчеплення (схема) купує найдешевшу на вигляд свіжість, яка йому й не потрібна, — гірший з можливих обмінів.

![Три вертикальні смуги-поверхні зчеплення, зверху вниз від найширшої до найвужчої. Найширша червона «СХЕМА» розписана дрібними плитками: ім'я таблиці, ім'я колонки, тип, зміст «active=true», ще колонки — підпис «спільна таблиця: залежиш від усього цього; будь-яка зміна може зачепити». Середня жовта «КОНТРАКТ» — одна плитка «activeCount(homeId) → count» — підпис «RPC: залежиш лише від обіцяної форми; схема під нею вільна». Найвужча зелена «ФАКТ-ПОДІЯ» — одна плитка «device.activated{deviceId,homeId,at}» — підпис «проєкція: залежиш лише від форми факту; ще й розчеплений у часі». Збоку стрілка вниз «менша поверхня зчеплення = менше того, що може зламатися», навпроти неї стрілка «але більший операційний клопіт (лаг, дублі, добудова)».](/guide/progarch/to-microservices-or-not/integration-styles-choice/img/coupling-surface.svg)

*Що вужча поверхня, до якої причеплений білінг, то менше в ній того, що може зламатися під чужою зміною, — і то більший клопіт вести обмін. Схема дає нуль клопоту наперед і найбільший ризик; подія — найменший ризик і власний операційний оброк. Вибір стилю і є вибором цього обміну.*

## Складність і пастки

Три стилі — три різні набори граблів, і кожні ростуть із того самого кореня, що й перевага.

**Спільна таблиця: зручність, за яку платить власник, а зламається в тебе.** Найгостріше ми вже бачили — невидиму залежність, що тріскає на чужому релізі. Поряд ідуть сусіди. Власникова схема застигає: він не може перейменувати колонку, розбити таблицю чи змінити тип, бо не знає, хто ще в неї заглядає, — ти позбавив його права рефакторити власне. Транзакційна межа розмивається: білінг і пристрої тепер ділять базу, тож міграція схеми одного зачіпає другого, і незалежний деплой, за який платили розколом, зникає. Це і є [розподілений моноліт](guide:progarch/context-as-service-candidate) на дотик — усе зчеплення моноліта плюс уся біль мережі. Якщо читати чуже сховище **справді** необхідно (буває — звітність, аналітика), не роби це сирим `JOIN`-ом у бойову таблицю: постав між собою й чужою схемою [антикорупційний шар](book:programming/anti-corruption-layer) або тягни зміни через [захоплення змін даних (CDC)](book:programming/change-data-capture), щоб чужа форма не протекла тобі всередину.

**RPC: жива відповідь, за яку тримаєш обох живими.** Синхронний виклик прив'язує білінг до власника в часі — і глибокий ланцюг таких викликів крихкий, бо доступність уздовж нього перемножується: якщо сервіс пристроїв лежить у мить нарахування, білінг стоїть або падає. Друга грабля — обсяг: тисячі викликів заради місячного звіту не лише повільні, а й крихкі під сплеском. Третя, тонша: контракт застигає тієї миті, коли перший споживач на нього сперся — перейменувати колонку власник тепер вільний, а от змінити зміст чи форму `activeCount` уже мусить версійно, як і будь-який опублікований API. RPC не прибирає жорсткості зчеплення — він **звужує** її з усієї схеми до однієї обіцянки, і за цю обіцянку відповідаєш уже свідомо.

**Проєкція: незалежність, за яку ведеш друге господарство.** Розчеплення в часі й у схемі не безкоштовне — воно кладе на білінг цілий новий клас турбот. Найперша, яку ми вже закрили в коді, — [дублі й переупорядкування](guide:progarch/duplicates-and-reorder): без часової печатки згортка тихо тече. Друга — **холодний старт**: проєкція, заведена сьогодні, не знає нічого про пристрої, активовані вчора, бо подій вона тоді не чула; новому споживачеві потрібна разова добудова — знімок поточного стану або програвання [журналу подій](book:programming/event-log) з початку. Третя — **відбудова**: проєкція це похідний стан, тож якщо її таблиця зіпсувалася чи згубилася, її треба вміти відтворити наново з того самого журналу; звідси й вимога, щоб події були відтворні, а не одноразові. Проєкція — це, по суті, [окрема читальна модель, яку веде споживач](book:programming/cqrs); вона дає найслабше зчеплення з трьох саме тому, що ти погодився тримати другу копію правди й доглядати за нею.

## Що лишається в руках

Ми взяли одну потребу — число активних пристроїв на дім — і зібрали її тричі однією мовою, з тим самим SQL усередині. І хоч писалися всі три майже однаково, причепили вони білінг до трьох різних речей: до **схеми** власника, до його **контракту**, до його **події**. Доки ніщо не рухалося, різниці не було видно — три зелені стовпчики, обирай будь-який. А тоді власник перейменував одне слово у своїй таблиці — і три стовпчики розійшлися: спільна таблиця тріснула (ще й гірше — могла тихо збрехати), RPC устояв за незрушним контрактом, проєкція навіть не глянула в той бік, бо чужого сховища не читає зовсім.

Ось де пуант лягає доказом у руки. **Зчеплення не зникає — його переносять**, і перейменування колонки — це проявник, що показує, куди саме ти його переніс: там, де лягла тріщина, і був твій справжній міст. Спільна таблиця віддала за п'ять рядків зручності приватність власникової схеми; RPC викупив приватність назад ціною життя обох в одну мить; проєкція викупила ще й час — ціною другого господарства, яке відтепер веде сам білінг. Обирати стиль означає читати не «що модніше» і не «що швидше написати», а рівно це питання: **чию зміну ти готовий пережити не помітивши** — і скільки за це право згоден платити щодня.
