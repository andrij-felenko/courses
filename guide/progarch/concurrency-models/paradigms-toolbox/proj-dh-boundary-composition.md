# ⚙️ Зшити чотири парадигми DH — і зламати кожен шов

Мапа DH уже перед нами: цикл подій на краю приймає кадри, актор зі скринькою тримає стан кожного пристрою, обмежена черга віддає важкий рахунок пулу воркерів, канал несе вироки до правил. На папері вона переконлива. Але папір не будить пейджер о третій ночі — будить код. Тож зберімо цю мапу так, щоб її можна було запустити, проженімо крізь неї щасливий кадр, а тоді зробімо те, заради чого ця картка існує: **зламаймо кожен шов по черзі** — точно так, як він ламається у проді, — і полагодьмо однією й тією ж парою ручок.

Нитку тримай перед очима від першого рядка. Парадигми ми вже вміємо поодинці; тут ідеться не про них, а про **порожнечу між ними**, яка насправді не порожнеча. Кожне з'єднання двох моделей — цикл із актором, ядро з пулом, пул із правилами — це окремий предмет, у якого є дві ручки: скільки він терпить і що робить, коли терпець уривається. Проґавиш ці дві ручки — і найкращі парадигми обабіч не врятують.

## Задача

Випишемо сцену точно. Хаб у кожному домі тримає живе з'єднання до хмари й шле кадри телеметрії — дрібний JSON, рядок за рядком. Хабів сотні, кадрів густо. Хмара має з кожним кадром зробити дві геть різні речі:

- **оновити стан того пристрою** — ковзне середнє, останнє показання, чи не вискочив стрибок. Робота копійчана, але **на пристрій**, і стан одного не сміє бачити стан іншого;
- **прогнати важку аналітику аномалій** — приблизно 40 мс чистого процесора на кадр: вікно, кореляції, поріг. Цю роботу можна різати паралельно на всіх ядрах, а її вироки віддати стадії правил, яка вже вмикає-вимикає розетки.

Звідси й чотири парадигми, кожна на своїй формі, і **три шви** між ними (плюс четвертий, прихований — сам факт винесення рахунку з циклу):

```
пристрої → [цикл подій] ── скринька ──→ [актор на пристрій]     ← стан, ізоляція
                       └─ обмежена черга ─→ [пул воркерів] ── канал ──→ [правила]
                          (це той-таки offload:                         ← важкий CPU
                           рахунок ПОКИДАЄ смугу циклу)
```

Мета проста на словах і підступна в коді: **щасливий шлях має текти рівно, а кожен шов — терпіти десятикратний сплеск, не поклавши систему.** Зберемо його, тоді зламаємо чотири рази.

## Ідея: шов — це ⟨місткість, політика⟩

Перш ніж писати, назвімо ту саму думку, яку картка вже підвела: шов — не труба, а **об'єкт із двома ручками**. Перша — **місткість**: скільки одиниць роботи він тримає, поки хтось відстає. Друга — **політика переповнення**: що робити, коли місткість вичерпано.

Це не наша вигадка й не абстракція заради краси. Кожен зрілий інструмент потокової обробки **прямо перелічує ці політики окремим типом**. Akka Streams має `OverflowStrategy` рівно з таких значень: `backpressure` (блокувати джерело), `dropHead` (викинути найстаріший), `dropTail`/`dropNew` (викинути найновіший), `dropBuffer` (скинути весь буфер) і `fail` (впасти з помилкою). Reactive Streams перелічує майже те саме під іменами `BUFFER`, `DROP`, `LATEST`, `ERROR`. Різні бібліотеки, той самий скелет: **шов = ⟨місткість, політика⟩**, і політика — це закритий список із кількох чесних варіантів.

Знизу — зворотний тиск від шва назад до продюсера.](/guide/progarch/concurrency-models/paradigms-toolbox/img/seam-anatomy.svg)

*Дві ручки роблять шов предметом проєктування, окремим від того, що по боках. Місткість має золоту середину: 0 — крихко, ∞ — падіння за пам'яттю; політика — закритий список із кількох варіантів, які галузь давно назвала.*

Тримаймо цю рамку — і кожен збій нижче стане тим самим діагнозом: **не та місткість або не та політика на конкретному шві**. Пишемо мапу.

## Щасливий шлях: зшита мапа

Мапа різномовна — і це не примха, а сама суть картки: кожен шов пишемо мовою, якою його **найкраще видно**. Край на циклі подій і актори — рідний дім TypeScript/Node; важкий бік — обмежена черга, пул і канал — рідний дім системних мов: Go з його каналами й C++ із потоками та обмеженою чергою. У проді ці боки й справді часто різні процеси (Node-шлюз, Go- чи C++-аналітика), зшиті транспортом; шов від того не змінює природи.

Спершу край: одне ядро на циклі подій приймає кадри від сотень з'єднань і **розгалужує** кожен кадр на два шви — у скриньку його актора й у чергу аналітики.

```ts
// core.ts — ядро на циклі подій: приймає кадри, розгалужує на два шви (рідний дім TS)
import { createServer, Socket } from "node:net";

export type Frame = { deviceId: string; ts: number; value: number };

const actors = new Map<string, DeviceActor>();
function actorFor(id: string): DeviceActor {
  let a = actors.get(id);
  if (!a) actors.set(id, (a = new DeviceActor(id, raiseAlert)));
  return a;
}

createServer((sock: Socket) => {
  sock.setEncoding("utf8");
  let buf = "";
  sock.on("data", (chunk: string) => {
    buf += chunk;
    for (let nl = buf.indexOf("\n"); nl >= 0; nl = buf.indexOf("\n")) {
      const line = buf.slice(0, nl); buf = buf.slice(nl + 1);
      let f: Frame;
      try { f = JSON.parse(line); } catch { continue; }  // биту телеметрію мовчки кидаємо
      actorFor(f.deviceId).post(f);   // ШОВ А: скринька актора — ізольований стан пристрою
      analytics.submit(f);            // ШОВ Б: обмежена черга → пул воркерів (важкий CPU)
    }
  });
  sock.on("error", () => sock.destroy());
}).listen(9099);
```

Актор — це поштова скринька плюс серійна обробка плюс стан, якого ніхто ззовні не торкається. Ядро лиш **кладе** кадр у скриньку й одразу йде далі; актор сам, у свій час, вибере кадр і оновить стан. Оце й є [модель акторів](book:programming/actor-model) у мініатюрі — і шов А тут буквально одне поле `mailbox`.

```ts
// device-actor.ts — один актор на пристрій: скринька + серійна обробка + ізольований стан
import { Frame } from "./core";

class DeviceActor {
  private mailbox: Frame[] = [];       // ШОВ А: єдина щілина в актора
  private draining = false;
  private state = { ewma: 0 };         // стан-автомат; назовні невидимий

  constructor(readonly id: string, private readonly onAnomaly: (f: Frame) => void) {}

  post(f: Frame): void {               // ядро кладе кадр — і вертається на смугу
    this.mailbox.push(f);
    if (!this.draining) { this.draining = true; setImmediate(() => this.drain()); }
  }

  private drain(): void {              // один споживач: по кадру за такт циклу
    const f = this.mailbox.shift();
    if (f === undefined) { this.draining = false; return; }
    this.step(f);
    setImmediate(() => this.drain()); // поступаємось смузі між кадрами — не тримаємо її
  }

  private step(f: Frame): void {       // дешевий крок: ковзне середнє + позначка стрибка
    this.state.ewma = this.state.ewma === 0 ? f.value : 0.9 * this.state.ewma + 0.1 * f.value;
    if (Math.abs(f.value - this.state.ewma) > 0.5 * this.state.ewma) this.onAnomaly(f);
  }
}
```

Тепер важкий бік — шов Б (черга → пул) і шов В (канал → правила). Обмежений канал у Go — найпрозоріша на світі ілюстрація «шов = місткість + політика»: `make(chan Frame, 256)` **і передає, і тисне назад** одним рядком. У C++ каналу немає — і саме тому шов стає ще наочнішим: обмежена блокувальна черга, у якій обидві ручки лежать перед очима — перевірка `size < cap` і очікування на `condition_variable`, коли повно, — а пул воркерів це `std::thread` на кожне ядро. Той самий шов у Node-варіанті (для крамниці без Go) — обмежена черга перед пулом `worker_threads`. Три мови, три вкладки — перемкни й побач, що ручки в усіх ті самі:

```go
// analytics.go — важкий бік: обмежена черга → пул → канал → правила (рідний дім каналів)
package main

import "runtime"

type Frame   struct{ DeviceID string; Value float64 }
type Verdict struct{ DeviceID string; Risk  float64 }

// ШОВ Б: обмежена черга між ядром (продюсер) і пулом (споживачі). 256 — це і є шов.
var work = make(chan Frame, 256)
// ШОВ В: канал від пулу до стадії правил.
```

```cpp
// analytics.cpp — той самий шов у C++: обмежена черга + пул std::thread → черга вироків
#include <condition_variable>
#include <cstddef>
#include <deque>
#include <mutex>
#include <string>
#include <thread>

struct Frame   { std::string deviceId; double value; };
struct Verdict { std::string deviceId; double risk;  };

// Шов = ⟨місткість, політика⟩ окремим типом. Політика «блокувати» — це очікування на
// condition_variable: коли повно, продюсер жде місця (зворотний тиск угору, до джерела).
template <typename T>
class BoundedQueue {
    std::deque<T>           buf_;
    std::size_t             cap_;
    std::mutex              m_;
    std::condition_variable notFull_, notEmpty_;
public:
    explicit BoundedQueue(std::size_t cap) : cap_(cap) {}

    void push(T v) {                                   // повно → блокуємось саме тут
        std::unique_lock lk(m_);
        notFull_.wait(lk, [&]{ return buf_.size() < cap_; });
        buf_.push_back(std::move(v));
        notEmpty_.notify_one();
    }
    T pop() {
        std::unique_lock lk(m_);
        notEmpty_.wait(lk, [&]{ return !buf_.empty(); });
        T v = std::move(buf_.front()); buf_.pop_front();
        notFull_.notify_one();                         // звільнили місце — будимо продюсера
        return v;
    }
};

BoundedQueue<Frame>   work{256};       // ШОВ Б: 256 — це і є шов
BoundedQueue<Verdict> verdicts{64};    // ШОВ В: канал до стадії правил

double scoreAnomaly(const Frame& f) { /* ~40 мс чистого CPU: вікно, кореляції, поріг */ return 0; }

void startPool() {
    unsigned n = std::thread::hardware_concurrency();
    for (unsigned i = 0; i < n; ++i)
        std::thread([]{
            for (;;) {                                 // N воркерів — з однієї черги
                Frame f = work.pop();
                verdicts.push({f.deviceId, scoreAnomaly(f)});  // ШОВ В: вирок у правила
            }
        }).detach();
}

void startRules() {
    std::thread([]{
        for (;;) {                                     // стадія правил споживає вироки
            Verdict v = verdicts.pop();
            if (v.risk > 0.9) { /* дія: сповістити, вимкнути розетку */ }
        }
    }).detach();
}

// міст від ядра: кладе кадр у чергу. Повно → push блокується (зворотний тиск до джерела).
void submit(const Frame& f) { work.push(f); }
```
```ts
// analytics.ts — той самий шов у Node: обмежена черга перед пулом worker_threads
import { Worker } from "node:worker_threads";
import os from "node:os";
import { Frame } from "./core";

const CAP = 256;                                    // ШОВ Б: місткість черги
const queue: Frame[] = [];
const pool = Array.from({ length: os.cpus().length }, () => new Worker("./score.js"));
const idle = [...pool];

export const analytics = {
  submit(f: Frame): boolean {
    if (queue.length >= CAP) return false;          // повно → політика вирішує тут
    queue.push(f); pump(); return true;
  },
};

function pump(): void {
  while (idle.length && queue.length) {
    const w = idle.pop()!, f = queue.shift()!;
    w.once("message", (v) => { rules.post(v); idle.push(w); pump(); }); // ШОВ В → правила
    w.postMessage(f);                               // важкий CPU — на окремому потоці V8
  }
}
```

Проженімо крізь це щасливий кадр. Прийшов рядок → цикл розібрав його, майже не торкнувшись смуги → **шов А**: кадр ліг у скриньку свого актора, актор оновив ковзне середнє на своєму такті → **шов Б**: копія кадру стала в чергу, вільний воркер узяв її, за 40 мс на своєму ядрі порахував ризик → **шов В**: вирок пішов каналом у правила, і при ризику понад 0.9 спрацювала дія. Чотири парадигми, і жодна не заважає іншій: цикл не рахує, актор не блокує сусідів, пул не морозить край. Поки навантаження в межах — усе тече.

А тепер зламаймо це чотири рази. Кожного разу винен буде **шов**, і кожного разу ліки — та сама пара ручок.

## Шов 1 — синхронний CPU морозить смугу

Найприродніший, найгірший спосіб зіпсувати мапу — прибрати шов Б зовсім і покликати аналітику **просто в циклі**, так само, як покликав би будь-яку функцію:

```ts
sock.on("data", (chunk: string) => {
  // ...розбір рядка у f...
  const risk = scoreAnomaly(f);   // ← 40 мс чистого CPU ПРЯМО НА СМУЗІ
  if (risk > 0.9) raiseAlert(f);  // жодного шва, жодного пулу — рахунок сидить у циклі
});
```

У термінах наших двох ручок це шов **із місткістю 0 і політикою «рахувати тут-таки»** — тобто відсутність шва. Наслідок точний: поки одне ядро гризе 40 мс для одного кадру, кадри від **усіх** інших сотень пристроїв стоять готові й ждуть єдину смугу. Десять кадрів у секунду — і смуга мертва пів секунди з кожної. Не «повільніше» — **застигло**.

Ліки — не переписати рантайм, а **повернути шов**: замість інлайн-виклику `analytics.submit(f)`, який кладе кадр в обмежену чергу до пулу (рівно щасливий шлях вище). Рахунок покидає смугу, цикл дихає. Цей шов — offload між циклом і пулом — заслуговує окремої, глибшої розмови: [як прийняти телеметрію на однім циклі й не отруїти смугу важким рахунком](guide:progarch/runtime-eventloop-variant/proj-dh-telemetry-loop.md) розібрано там до дна, з мірянням затримки циклу. Нам тут досить бачити його як перший із чотирьох швів: **його місткість мусить бути більшою за нуль, інакше CPU й ввід-вивід ділять одну смугу — і CPU завжди виграє.**

> 🔧 **Навіщо це.** Найпідступніше тут — що баг виглядає невинно: звичайний виклик функції, жодного `await`, код чистий. Але шва, якого нема, на код-рев'ю не побачиш очима — його видно лише як питання: «а де тут CPU-робота покидає смугу циклу?» Якщо відповіді нема — offload-шов пропущено, і перший же важкий кадр заморозить край. Відсутній шов — теж проєктне рішення, тільки ухвалене недбальством.

## Шов 2 — необмежена черга з'їдає пам'ять під сплеском

Тепер поширеніша, підступніша пастка. Шов Б є, але його зробили з **нескінченною** місткістю — «щоб прийом ніколи не гальмував». У Go це найчастіше має вигляд не гігантського буфера, а горутини на кожен кадр:

```go
// ПАСТКА: щоб submit «ніколи не блокувався», кожному кадру — своя горутина.
func submit(f Frame) {
    go func() {                        // ← необмежений фан-аут = необмежена черга
        verdicts <- Verdict{f.DeviceID, scoreAnomaly(f)}
    }()
}
```

На щасливому навантаженні воно навіть працює — і саме тому доживає до прода. Але прийде сплеск: рій пристроїв прокинувся, 100 000 кадрів за секунду, а кожен `scoreAnomaly` — 40 мс. Порахуймо на серветці: за секунду народжується 100 000 горутин, а завершується щонайбільше `ядер × 25` (по 40 мс кожна) — скажімо, 400 на 16 ядрах. Різниця, 99 600 горутин щосекунди, **накопичується**: кожна тримає стек (від 2 КБ) і копію кадру. Купа росте лінійно в часі, поки OOM-killer не пристрелить процес. Черга не «повільна» — вона **необмежена**, і необмежена черга під тривалим перевантаженням завжди має один кінець: пам'ять скінчилась.

Той самий диявол ховається й у чесній на вигляд заміні — `make(chan Frame, 100_000_000)`: «нехай буде мільйон, аби не блокувалось». Тут гірше подвійно. По-перше, Go виділяє **весь** кільцевий буфер одразу — сотні мегабайтів на старті ні за що. По-друге, навіть якби ріс ліниво, велика місткість не лікує затор, а **ховає** його: кадр, що став у чергу зараз, чекатиме за мільйоном попередників — свіжа команда «вимкни перегрітий обігрівач» вилежиться хвилини, поки дійде черга. Необмежений буфер міняє швидкий чесний збій на повільну тиху деградацію.

Ліки — рівно щасливий шлях: **обмежити місткість і поставити політику «блокувати»**. `make(chan Frame, 256)` плюс сталий пул із `N` воркерів. Коли пул відстає, буфер повниться, `work <- f` блокує продюсера — і [зворотний тиск](book:programming/backpressure-local) доходить угору, до самого джерела. Місткість 256 — це «скільки ривка ми готові з'їсти буфером»; політика «блокувати» — це «нічого не губимо, а джерело хай зачекає». Необмежене «ніколи не гальмувати» ми свідомо міняємо на «іноді пригальмувати, зате ніколи не впасти».

## Шов 3 — нульова місткість робить систему крихкою

Полагодивши шов 2, легко перестрибнути в дзеркальну помилку: «якщо ∞ погано, то навіщо взагалі буфер — хай передають з рук у руки». Це місткість **0**:

```go
var work = make(chan Frame)   // ПАСТКА: місткість 0 — рандеву, «з рук у руки»
```

Ненульова відмінність. Небуферизований канал у Go — це **рандеву**: `submit` (надсилання) блокується доти, доки бодай один воркер саме цієї миті не стоїть на `range work`, готовий прийняти. Поки навантаження легке й хтось із пулу завжди вільний — усе гладко, жодної прихованої латентності. Але під справжнім навантаженням усі `N` воркерів більшість часу зайняті своїми 40 мс, і «вільний воркер саме зараз» трапляється лише в ту коротку мить, коли хтось домолов кадр. Продюсерові більше **ніде перечекати** ці вікна цілковитої зайнятості пулу: він блокується щоразу, коли всі воркери водночас під роботою, — а це раз у раз, навіть без жодного сталого перевантаження. Нульова місткість не має **жодного люфту**, щоб згладити звичайний джитер часу обробки; продюсер іде в лок-степ із завершеннями, а край над ним застигає разом із продюсером. Досить, щоб час обробки кадрів трохи «злипся» — усі 16 закінчили, усі 16 знову зайняті, — і прийом іде рвучкими поштовхами замість рівного потоку.

Ось чому шви 2 і 3 разом **беруть у вилку** правильну відповідь. ∞ ховає затор і падає за пам'яттю; 0 не має де перечекати нормальний джитер і робить прийом рвучким. Правильне — мале скінченне число, підібране саме під той джитер, який треба пережити: буфер має проковтнути кілька хвиль повної зайнятості пулу, щоб продюсер їх не помітив, — але не бути таким великим, щоб сховати справжнє, стале відставання. Оце й уся суть «256» на пул із півтора десятка воркерів: досить люфту, щоб пережити звичайні збіги зайнятості, замало, щоб замаскувати хронічну недостачу ядер. Місткість — це не «побільше про запас» і не «поменше для чесності», а **скільки джитеру шов має мовчки з'їсти, лишивши сталий затор видимим**.

## Шов 4 — переповнення скриньки

Лишився шов А, і він найтонший, бо ламається тихо й б'є по обіцянці, заради якої акторів і брали, — ізоляції. У щасливому коді скринька актора необмежена (`this.mailbox.push(f)` без стелі). Це не наша недбалість — це **дефолт цілої платформи**: у Erlang поштова скринька процесу за замовчуванням росте без межі, і це класична пастка, яку тамтешня спільнота знає напам'ять. Повільний споживач із швидкими продюсерами роздуває чергу повідомлень, а що всі процеси ділять одну купу вузла, одна відстала скринька тихо кладе весь вузол.

У нас те саме. Один пристрій із зіпсованою прошивкою шле не раз на секунду, а 10 000 разів; його актор, що серійно бере по кадру за такт, не встигає, і `mailbox` пухне. А що всі актори живуть в одному процесі й ділять купу, **один навіжений пристрій з'їдає пам'ять цілого хаба** — рівно те, чого актори мали не допустити. Ізоляція стану без ізоляції **ресурсу** — це напівізоляція.

Ліки знову ті самі дві ручки — але політика тут **інша, ніж на шві Б**, і ось де вся сіль. Обмежимо скриньку й доберемо політику під **сенс даних**:

```ts
private static readonly CAP = 64;
private dropped = 0;

post(f: Frame): void {
  if (this.mailbox.length >= DeviceActor.CAP) {
    this.mailbox.shift();     // політика для СТАНУ: викинь найстаріший (dropHead) = конфляція
    this.dropped++;           // але порахуй викинуте — німа втрата гірша за гучну
  }
  this.mailbox.push(f);
  if (!this.draining) { this.draining = true; setImmediate(() => this.drain()); }
}
```

Чому саме «викинути найстаріший», а не «блокувати», як на шві Б? Бо на шві Б **кожен кадр треба порахувати** — його не можна губити, тож єдина чесна відповідь на перевантаження — пригальмувати джерело. А на шві А зберігається **стан**: ковзне середнє й останнє показання. Для стану старе показання, що застрягло в черзі за трьома свіжішими, — не борг, а **сміття**: коли актор нарешті до нього дійде, воно вже неправда. Отже правильно не гальмувати джерело й не губити найновіше, а **стискати чергу до найсвіжішого** — викидати з голови старі, лишати молоді. У крайності місткість 1 дає чисту **конфляцію** (англ. *conflation* — стиснення потоку оновлень в одне, останнє): актор завжди бачить лише свіжий кадр.

І це не саморобка — це давно названий патерн із біржових стрічок. Коли на розподільник ринкових даних сиплеться 1000 котирувань MSFT за секунду, а споживачеві потрібна лише поточна ціна, стрічка **конфлює** тисячу повідомлень в одне останнє. Точнісінько наш випадок: пристрій сипле показаннями, актору потрібне лише поточне значення стану. Той самий шов, той самий механізм обмеженого буфера — а політика протилежна до шва Б, бо **дані означають різне**.

![Таблиця чотирьох швів DH: скринька актора — місткість 64→1, конфляція (тримай найсвіжіший), бо для стану важить лише останнє показання; черга→пул — 256, блокувати (тиск до джерела), бо кожен кадр треба порахувати; канал→правила — 64, блокувати, щоб не загубити вироки; offload циклу — місткість >0, винести CPU в пул, бо 0 морозить прийом.](/guide/progarch/concurrency-models/paradigms-toolbox/img/four-seams.svg)

*Той самий механізм — обмежений буфер — на всіх чотирьох швах, а політика щоразу інша, бо різний сенс даних. Стан пристрою конфлюємо до найсвіжішого; кадри для рахунку бережемо всі й тиснемо назад; вироки не губимо; рахунок неодмінно виносимо з циклу.*

> 🔧 **Навіщо це.** Ось головний висновок картки в дії: **політику переповнення диктує сенс даних на шві, а не смак і не дефолт бібліотеки.** Постав «блокувати» там, де треба конфлювати, — і один балакучий пристрій зчепить увесь хаб через його скриньку. Постав «викинути найновіший» там, де кожен кадр цінний, — і тихо втратиш саме те показання, задля якого система й існує. На рев'ю питання не «яка місткість», а **«що ці дані означають, коли їх забагато»** — і відповідь сама називає одну з політик Akka-переліку.

## Складність і пастки

Мапа зшита, чотири шви полагоджені. Лишилося окреслити, де композиція все ще ріже руки.

**Зворотний тиск мусить дійти до джерела, інакше це театр.** Заблокований `work <- f` тисне на ядро — але ядро мусить, своєю чергою, **припинити читати** з сокета пристрою (`sock.pause()`), інакше необмежене зростання просто переповзе на рівень вище: у буфер прийому самого ядра. Шов допомагає лише тоді, коли тиск доходить до того, хто справді може пригальмувати, — до пристрою (або до краю, де кадр свідомо кидають). Обмежити один шов і лишити необмеженим сусідній угору по течії — значить пересунути OOM, а не прибрати його.

**Мір глибину шва — це найдешевший датчик здоров'я.** У Go `len(work)` проти `cap(work)` — миттєвий манометр: черга, що стало тримається під зав'язку, кричить не «збільш буфер» (це лише сховає лаг), а «доклади воркерів або ядер — споживач хронічно не встигає». А лічильник `dropped` на скриньці конче **виставляй назовні**: конфляція, якої ніхто не міряє, зовні не відрізнити від утрати даних. Тиха політика без метрики — те саме, що забутий `await`.

**Не сплутай дешевий крок актора з важким рахунком пулу.** Спокуса — покласти `scoreAnomaly` прямо в `step` актора: «стан і аналітика ж про той самий пристрій». Але тоді актор серіалізує 40-мілісекундні брили по одній на пристрій, його скринька миттю набивається — і ти власноруч злив шов 4 у шов 1. Поділ навмисний: **у акторі — копійчаний стан, у пулі — важкий CPU**, і між ними шов Б. Стан ділиться за ключем-пристроєм і має бути ізольований; рахунок ділиться за ядрами й має бути паралельний — це дві різні форми, отже два різні інструменти.

**Шов через транспорт — той самий шов, тільки місткість схована.** У різномовній мапі шви Б і В часто перетинають межу процесу: Node-ядро годує Go-аналітику сокетом чи через брокер. Пара ⟨місткість, політика⟩ нікуди не дівається — але місткість тепер живе ще й у транспорті (вікно TCP, глибина черги брокера), і про неї так само легко забути. Необмежений топік у брокері — це рівно баг шва 2, лише більшого масштабу й з чужим ім'ям на дашборді. Питай про місткість і політику **кожної** труби, а не лише тих, що в твоєму коді.

**Політик рівно жменя — вивчи весь перелік.** `backpressure`, `dropHead`, `dropTail`/`dropNew`, `dropBuffer`, `fail` — це закритий список, і кожен пункт має свій рідний випадок. Блокувати — коли втрата неприпустима, а джерело здатне зачекати (шов Б). Викинути найстаріший — коли важить лише свіже (шов А, стан). Викинути найновіший — коли вже прийняте цінніше за щойно прибуле (напр., ідемпотентна дія в польоті). Впасти — коли переповнення означає баг, який має спливти голосно, а не тихо ковтнутись. Обрати політику — значить чесно відповісти, **чим жертвувати під перевантаженням**; відмовитися обирати — значить лишити цей вибір випадковому дефолту бібліотеки.

І під усім — один рядок, задля якого картка й винесла шви в окремий предмет: **між двома парадигмами завжди є третя річ, і в неї дві ручки.** Найкращий цикл подій, найчистіші актори й найшвидший пул не врятують систему, якщо шов між ними має нескінченну місткість, нульову місткість або політику, що суперечить сенсу даних. Парадигми ти вже вмів; тепер умієш і те, що між ними.
