# 📋 Специфікація політик контролю витрат та тирування Digital Homes

Цей довідковий документ містить повну специфікацію контракту API, YAML-схему конфігурації політик контролю витрат (Cost Control Policy Engine) та реєстр кодових помилок обмеження квот Digital Homes. Специфікація визначає правила тирування даних, ліміти смуги пропускання відеопотоків, адаптивні параметри дельта-фільтрації та контракти переходу між гарячим локальним сховищем і холодним хмарним архівом.

У системі Digital Homes сервіс політик витрат є центральним арбітром, який гарантує, що жоден пристрій чи мобільний клієнт не зможе вийти за межі відведеного фінансового бюджету. Політика формується хмарним сервісом контролю FinOps, підписується асиметричним ключем ECDSA-SHA256 та поширюється на всі 5 мільйонів хабів через MQTT-топік конфігурації.

Уся модель управління витратами побудована на декларативному описі правил. Замість того щоб зашивати параметри опитування давачів у прошивку хаба, хмара централізовано керує поведінкою флоту. Це дозволяє в реальному часі коригувати обсяг інгестії під час вечірніх піків, аварійних ситуацій чи зміні тарифних планів провайдерів.

## 1. Схема конфігурації політик витрат (DH Cost Policy Schema)

Конфігурація політики витрат публікується хмарою та підписується ECDSA-ключем. Хаб викачує її при онбордингу та оновлює через підписку на MQTT-топік `dh/v1/control/cost-policy`.

```yaml
# dh-cost-policy-v1.yaml — Загальносистемна політика контролю витрат DH
version: "1.2.0"
updated_at: "2026-08-18T10:00:00Z"

fleet_limits:
  max_unit_cost_usd_per_home_month: 0.015
  global_ingress_rate_limit_msg_sec: 50000
  emergency_bypass_priority: "qos_1"

telemetry_tiering:
  default_sample_interval_sec: 15
  default_batch_window_sec: 900
  delta_filtering:
    enabled: true
    rules:
      - sensor_type: "temperature"
        min_delta_celsius: 0.2
        max_silent_time_sec: 3600
      - sensor_type: "humidity"
        min_delta_percent: 2.0
        max_silent_time_sec: 3600
      - sensor_type: "power_meter"
        min_delta_watts: 5.0
        max_silent_time_sec: 300
      - sensor_type: "motion"
        min_delta_boolean: 1.0
        max_silent_time_sec: 0 # Негайна передача

storage_retention:
  edge_sqlite_hot_days: 7
  edge_max_db_size_mb: 512
  cloud_parquet_warm_days: 90
  cloud_glacier_cold_days: 365
  compaction_interval_hours: 6

video_egress_policy:
  max_cloud_relay_minutes_per_day: 15
  webrtc_p2p_prefer_local_lan: true
  max_stream_resolution_cellular: "720p"
  max_stream_bitrate_kbps_cellular: 800
  event_clip_duration_sec: 10
  cloud_clip_quota_per_day: 20
```

## 2. Специфікація полів контракту політики

Нижче наведено вичерпний опис кожного поля конфігурації з вказанням типів даних, обов'язковості та поведінки системи при виході значень за межі діапазону.

Секція `fleet_limits` задає макроекономічні рамки для всієї системи. Поле `max_unit_cost_usd_per_home_month` із значенням `0.015` визначає граничну межу витрат на один будинок. Якщо сумарні хмарні витрати перевищують цю цифру, брокери автоматично вмикають режим дроппінгу некритичного трафіку. Поле `global_ingress_rate_limit_msg_sec` зі значенням `50000` задає максимум вхідних пакетів на секунду для запобігання перевантаженню брокерів.

Секція `telemetry_tiering` описує детальні параметри фільтрації. Поле `default_sample_interval_sec` задає базовий крок опитування локальних давачів контролером хаба (15 секунд). Поле `default_batch_window_sec` визначає тривалість батчування у локальній SQLite (900 секунд або 15 хвилин). Список `delta_filtering.rules` визначає індивідуальні пороги чутливості для кожного типу давачів.

Секція `storage_retention` визначає життєвий цикл даних на краю та у хмарі. Поле `edge_sqlite_hot_days` вказує зберігати детальні виміри у локальній базі хаба протягом 7 днів. Поле `edge_max_db_size_mb` задає жорстку дискову квоту в 512 Мегабайтів. Поле `cloud_parquet_warm_days` задає термін перебування даних у гарячому Parquet-архіві (90 днів), а `cloud_glacier_cold_days` переводить дані в довготривале глибоке сховище на 365 днів.

Секція `video_egress_policy` регулює найдорожчий елемент — вихідний відеотрафік. Поле `max_cloud_relay_minutes_per_day` лімітує безкоштовну ретрансляцію через TURN-сервер до 15 хвилин на добу. Поле `webrtc_p2p_prefer_local_lan` зобов'язує мобільні застосунки першочергово шукати хаб у локальній мережі Wi-Fi. Поле `max_stream_bitrate_kbps_cellular` обмежує бітрейт відео до 800 Кбіт/сек при роботі через мобільний інтернет.

| Поле | Тип | Обов'язкове | Опис |
| :--- | :--- | :--- | :--- |
| `version` | String | Так | Версія контракту політики у форматі SemVer (`1.2.0`). Клієнти перевіряють мажорну версію для сумісності. |
| `fleet_limits.max_unit_cost_usd_per_home_month` | Float | Так | Порогове значення unit-cost. При перевищенні включається автоматичне стримування трафіку. |
| `telemetry_tiering.default_batch_window_sec` | Integer | Так | Інтервал об'єднання вимірів у локальній SQLite перед відправкою (секунди). |
| `telemetry_tiering.delta_filtering.rules[].min_delta` | Float | Так | Мінімальний поріг зміни показника давача для генерування події. |
| `telemetry_tiering.delta_filtering.rules[].max_silent_time_sec` | Integer | Так | Максимальний час мовчання давача до примусового скидання стану на хмару. |
| `storage_retention.edge_sqlite_hot_days` | Integer | Так | Час зберігання деталей вимірів у гарячій базі хаба до очищення або ущільнення. |
| `video_egress_policy.max_cloud_relay_minutes_per_day` | Integer | Так | Безкоштовний ліміт ретрансляції відео через хмарний TURN-сервер на добу. |
| `video_egress_policy.webrtc_p2p_prefer_local_lan` | Boolean | Так | Прапорець примусового перенаправлення відео в локальну мережу Wi-Fi при наявності. |

## 3. REST API інтерфейсу управління квотами й витратами

Сервіс витрат надає підсистемі мобільних застосунків та внутрішнім дашбордам REST API для перевірки поточного стану витрат та отримання квитків на використання хмарного ретранслятора відео.

### GET /api/v1/homes/{home_id}/cost-metrics

Цей ендпойнт використовується мобільним застосунком та дашбордом адміністратора для отримання повної калькуляції спожитих ресурсів конкретним будинком за поточний місяць. Сервіс агрегує дані про кількість переданих MQTT-повідомлень, обсяг вихідного трафіку відео та кількість збережених тривожних кліпів.

**Запити (Request Headers):**
```http
GET /api/v1/homes/home-884910/cost-metrics HTTP/1.1
Host: api.digitalhomes.io
Authorization: Bearer eyJhbGciOi...
Accept: application/json
```

**Успішна відповідь (Response 200 OK):**
```json
{
  "home_id": "home-884910",
  "billing_period": "2026-08",
  "telemetry": {
    "mqtt_messages_sent": 1420,
    "bytes_transmitted": 184500,
    "delta_filtered_count": 48200,
    "estimated_cost_usd": 0.0031
  },
  "video": {
    "p2p_direct_minutes": 145.5,
    "cloud_relay_turn_minutes": 2.1,
    "cloud_relay_quota_remaining_minutes": 12.9,
    "event_clips_uploaded": 4,
    "estimated_cost_usd": 0.0042
  },
  "total_unit_cost_usd": 0.0073,
  "budget_status": "NORMAL"
}
```

У відповіді поле `delta_filtered_count` показує кількість вимірів, які були успішно відфільтровані локально на хабі й не потребували хмарної інгестії. Поле `cloud_relay_quota_remaining_minutes` показує залишок добового ліміту безкоштовної трансляції через хмарний TURN-сервер. Поле `budget_status` може набувати значень `NORMAL`, `WARNING` або `EXCEEDED`.

### POST /api/v1/homes/{home_id}/video/stream-ticket

Перед початком трансляції live-відео мобільний застосунок надсилає запит на отримання тимчасового квитка доступу (Stream Ticket). Сервіс перевіряє залишок квоти користувача, оцінює тип мережі (Wi-Fi, 4G, 5G) і повертає список ICE-серверів із примусово встановленими обмеженнями бітрейту.

**Тіло запиту (Request Body):**
```json
{
  "camera_id": "cam-front-door",
  "client_network_type": "cellular_5g",
  "requested_resolution": "1080p"
}
```

**Успішна відповідь (Response 200 OK):**
```json
{
  "ticket_id": "tkt-99182374",
  "ice_servers": [
    {
      "urls": "stun:stun.digitalhomes.io:3478"
    },
    {
      "urls": "turn:turn-region1.digitalhomes.io:5349?transport=udp",
      "username": "home-884910",
      "credential": "temp-token-secret"
    }
  ],
  "enforced_max_bitrate_kbps": 800,
  "allocated_mode": "P2P_PREFERRED",
  "expires_in_sec": 300
}
```

Поле `allocated_mode` приймає значення `P2P_PREFERRED`, якщо користувач має достатній залишок квоти, або `P2P_ONLY`, якщо хмарна квота TURN повністю вичерпана і трансляція дозволена лише при прямому з'єднанні.

## 4. Реєстр кодових помилок обмеження квот та витрат (Cost & Quota Error Codes)

При перевищенні фінансових або мережевих квот сервіси Digital Homes віддають типізовані помилки у стандартному конверті `application/problem+json` відповідно до RFC 9457. Це дозволяє мобільним застосункам та автоматичним агентам хаба однозначно ідентифікувати причину відмови й застосовувати відповідну стратегію відновлення.

Кожна помилка містить унікальний атрибут `code` з машиночитаним ключем у нижньому змішаному регістрі (snake_case), який є стабільною частиною публічного контракту.

| HTTP Status | Machine-Key Code | Опис | Дії Клієнта |
| :--- | :--- | :--- | :--- |
| `429 Too Many Requests` | `cost_quota_telemetry_exceeded` | Перевищено добову кількість MQTT-повідомлень без дельта-фільтрації. | Хаб мусить примусово збільшити `default_batch_window_sec` до 3600 с. |
| `429 Too Many Requests` | `cost_quota_turn_relay_exceeded` | Вичерпано добовий ліміт безкоштовної хмарної ретрансляції TURN (15 хв). | Застосунок має переключитися на P2P або запропонувати платний токен. |
| `403 Forbidden` | `cost_policy_signature_invalid` | Підпис політики витрат не збігається з відкритим ключем хаба. | Відхилити політику, повернутися до безпечного локального профілю. |
| `503 Service Unavailable` | `cost_circuit_breaker_active` | Хмарний запобіжник зупинив непріоритетний інгест через сплеск витрат. | Застосувати експоненційну затримку повтору (Exponential Backoff). |
| `507 Insufficient Storage` | `storage_edge_disk_full` | Переповнення локального диска хаба (SQLite DB > 512 MB). | Ініціювати примусове ущільнення та видалення найстаріших вимірів. |

Приклад конверта помилки при вичерпанні TURN-квоти:

```json
{
  "type": "https://digitalhomes.io/errors/cost-quota-turn-relay-exceeded",
  "title": "TURN Relay Quota Exceeded",
  "status": 429,
  "code": "cost_quota_turn_relay_exceeded",
  "detail": "Daily cloud relay video limit (15 mins) has been exhausted for home-884910. Direct WebRTC P2P is still available.",
  "instance": "/api/v1/homes/home-884910/video/stream-ticket",
  "retry_after_sec": 14400,
  "quota_reset_at": "2026-08-19T00:00:00Z"
}
```

У разі отримання помилки `cost_quota_telemetry_exceeded` клієнтський стек хаба не зупиняє роботу, а переходить у режим занепаду функціональності (Graceful Degradation). Виміри некритичних давачів перестають надходити у хмару, але зберігаються в локальній SQLite для локального перегляду.

## 5. Крайові випадки та обробка збоїв зв'язку (Edge Cases & Fallbacks)

Система управління витратами повинна зберігати стійкість та передбачуваність навіть у разі мережевих збоїв, знеструмлення або спроб зламу. Нище описано п'ять ключових крайових сценаріїв та алгоритми їх нейтралізації:

1. **Мережева ізоляція хаба (Network Partitioning):** Якщо хаб втрачає зв'язок із хмарою, він зберігає поточну політику витрат у незалежній енергонезалежній пам'яті (Flash / NVM). При переповненні локальної SQLite (> 512 MB) хаб автоматично переходить у режим агресивного ущільнення (Compaction), усереднюючи показники за кожні 60 хвилин і видаляючи проміжні виміри.
2. **Резервний мобільний канал (LTE / Cellular Backup):** При відключенні основного провайдера інтернет хаб переключається на резервний SIM-модуль. У цьому режимі політика контролю витрат миттєво активує профіль `cellular_emergency`: повністю відключається батчинговий передавач некритичних вимірів, відео за запитом обмежується роздільною здатністю 480p (250 Kbps), а передаються лише тривожні сигнали безпеки.
3. **Аварійне знеструмлення регіону (Blackout Recovery Storm):** Після відновлення живлення мільйон хабів одночасно намагаються оновити свої політики витрат. Для запобігання колапсу хмарного API хаби застосовують випадковий джитер (Jitter) у діапазоні від 1 до 300 секунд перед відправкою запиту оновлення.
4. **Спроба підміни політики (Tamper Resistance):** Якщо зловмисник намагається модифікувати локальний файл політики на хабі, щоб зняти обмеження на передачу відео, криптографічна перевірка підпису ECDSA-SHA256 зазнає невдачі. Хаб негайно скидає конфігурацію до жорстко зашитого в прошивці безпечного профілю (Fail-Safe Profile).
5. **Вичерпання квоти зберігання у хмарі (Cloud Storage Quota Full):** Якщо місячний обсяг Parquet-архіву досягає граничного ліміту підписки, хмарний сервіс не відкидає нові тривожні події, а автоматично переводить найстаріші Parquet-файли з warm-ярусу в cold-ярус (AWS Glacier / Wasabi), вивільняючи ліміти без зупинки системи.
