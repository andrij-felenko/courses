# 🧮 Математична модель TCO та дерева компенсацій

Інтуїтивні суперечки інженерів про «дорого чи дешево» не мають практичної цінності без математичної формалізації сукупної вартості володіння (англ. *Total Cost of Ownership*, TCO), Unit-економіки та валової маржинальності (англ. *Gross Margin*). Без чіткого алгебраїчного апарату неможливо обчислити точку перетину (англ. *crossover point*), у якій високий початковий капітальний чек компенсується низькими оперативними витратами, та запобігти передчасному руйнуванню економіки продукту. Ця вставка розкладає архітектурне рішення на чотири компоненти витрат у часі та виводить математичні формули їх розрахунку.

## Сукупна вартість володіння (TCO) як інтеграл життєвого циклу

Сукупна вартість володіння архітектурним рішенням на горизонті часу `T` (виміряному в місяцях) складається з одноразових початкових інвестицій, інтегралу поточних витрат на володіння й еволюцію та математичного сподівання ризику виходу з технології.

Враховуючи часову вартість грошей через ставку дисконтування `r` (англ. *discount rate*),ведена формула приведеної вартості (NPV, англ. *Net Present Value*) набирає вигляду:

```
TCO_NPV(T) = CapEx + ∫₀ᵀ [OpEx(t) + ChangeCost(t)] · e^(−r·t) dt + P(Exit; T) · ExitCost(T) · e^(−r·T)
```

Розкладемо кожну зі складових частини рівняння на первинні змінні:

1. **CapEx** (англ. *Capital Expenditure* — капітальні витрати) — одноразові витрати на проєктування, прототипування, написання первинного коду, розгортання інфраструктури та навчання команди:

```
CapEx = M_dev · Rate_dev + Cost_setup + Cost_training
```
[де `M_dev` — людські ресурси в людино-місяцях, `Rate_dev` — повна місячна ставка інженера з урахуванням податків та робочого місця, `Cost_setup` — ліцензії та первинні сервери]

2. **OpEx(t)** (англ. *Operational Expenditure* — оперативні витрати) — щомісячний рахунок за інфраструктуру й обслуговування при обсязі навантаження `N(t)` активних користувачів чи пристроїв:

```
OpEx(t) = C_fixed + N(t) · c_unit(N(t))
```
[де `C_fixed` — умовно-постійні витрати на мінімальний контур, `c_unit(N)` — питома вартість обробки одиниці навантаження]

3. **ChangeCost(t)** (вартість еволюційної зміни) — очікувана вартість внесення змін у систему за одиницю часу:

```
ChangeCost(t) = λ_change · c_base_change · (1 + k_coupling · Complexity(t))
```
[де `λ_change` — частота нових вимог на місяць, `c_base_change` — базова ціна фічі, `k_coupling` — коефіцієнт зчеплення модулів, `Complexity(t)` — індекс складності кодової бази]

4. **ExitCost(T)** (вартість виходу з прив'язки) — ціна повної заміни постачальника чи технології на момент `T`, помножена на ймовірність такого виходу `P(Exit; T)`:

```
ExitCost(T) = C_rewrite + C_data_egress(Volume(T)) + C_retraining
```

Динаміка зростання вартості виходу з часом моделюється як ефектом гравітації даних (англ. *Data Gravity*): що більше гігабайт накопичено в пропрацевому сховищі, то дорожче коштує вивід трафіку й конверсія схем:

```
ExitCost(t) = C₀ · e^(γ·t)
```
[де `C₀` — базова вартість міграції на старті, `γ` — коефіцієнт накопичення власності й даних]

## Unit-економіка та валова маржинальність (Gross Margin)

Для софтверного продукту вартість проданих товарів та послуг (COGS, англ. *Cost of Goods Sold*) безпосередньо залежить від хмарної інфраструктури, підтримки першої/другої лінії та ліцензій. Валова маржинальність у відсотках визначається як:

```
Gross Margin % = (Revenue(N) - COGS(N)) / Revenue(N) · 100%
```

Якщо дохід на користувача сталий (`Revenue(N) = N · ARPU`), а `COGS(N) ≈ OpEx(N) = C_fixed + N · c_unit(N)`, то питома маржинальність на один юніт дорівнює:

```
c_margin = ARPU - c_unit(N) - (C_fixed / N)
```

Залежно від архітектури, функція питомих витрат `c_unit(N)` поводиться по-різному:

- **Сублінійна / Стала (`O(1)` або `O(log N)`):** завдяки кешуванню, агрегації та ефективним індексам `c_unit(N)` спадає або лишається сталою при зростанні `N`. Маржа прагне до `ARPU - c_unit`.
- **Суперлінійна (`O(N)` або `O(N log N)`):** через каскадні запити (`N+1`), надлишковий fan-out або відсутність індексів `c_unit(N) = c₀ + α · N`. Тоді загальні витрати ростуть як `O(N²)`.

Точка критичного зламу економіки (банкрутство на масштабі) настає, коли питомі витрати зрівнюються з ARPU:

```
c_unit(N_critical) = ARPU
⇒ c₀ + α · N_critical = ARPU            [підстановка лінійної функції c_unit]
⇒ α · N_critical = ARPU - c₀            [віднімання сталого c₀ з обох боків]
⇒ N_critical = (ARPU - c₀) / α          [ділення на коефіцієнт α]
```

При `N > N_critical` кожен новий користувач генерує прямий збиток, і зростання масштабу прискорює вичерпання грошових резервів компанії.

## Математичні кейси та порівняльний розрахунок

### Кейс 1: Розрахунок точки інфлексії (Crossover Point) для бази даних телеметрії

Розглянемо покроковий розрахунок вибору бази даних телеметрії для системи Digital Homes (DH) між двома варіантами на горизонті `T = 36` місяців при `N = 100 000` активних осель. ARPU становить `1.20 €` на місяць за одну оселю.

**Варіант А: Повністю керована хмарна Serverless TSDB (AWS Timestream)**
- `CapEx_A = 15 000 €` (швидкий старт за 0.5 місяця інженера)
- `c_unit_A = 0.45 €` / оселю / місяць (агресивне позапитне ціноутворення та збереження даних)
- `C_fixed_A = 1 000 €` / місяць
- `ExitCost_A = 90 000 €`, `P(Exit) = 0.15`

**Варіант Б: Власний кластер TimescaleDB на гібридному залізі (Bare Metal)**
- `CapEx_B = 125 000 €` (проєктування, міграція, автоматизація failover, 3 місяці інженерії)
- `c_unit_B = 0.05 €` / оселю / місяць (фіксовані сервери, дешевше обчислення)
- `C_fixed_B = 4 000 €` / місяць (оренда стійки та ліцензії)
- `ExitCost_B = 25 000 €`, `P(Exit) = 0.05`

Обчислимо щомісячні операційні витрати `OpEx` для обох варіантів при `N = 100 000`:

```
OpEx_A = 1 000 + 100 000 · 0.45        [формула OpEx = C_fixed + N · c_unit]
       = 1 000 + 45 000
       = 46 000 € / місяць

OpEx_B = 4 000 + 100 000 · 0.05        [обчислення OpEx для Варіанта Б]
       = 4 000 + 5 000
       = 9 000 € / місяць

ΔOpEx  = OpEx_A - OpEx_B                [різниця щомісячних операційних витрат]
       = 46 000 - 9 000
       = 37 000 € / місяць
```

Обчислимо сукупну вартість TCO для Варіанта А на горизонті `T = 36` місяців:

```
TCO_A(36)
= CapEx_A + 36 · OpEx_A + P_A · ExitCost_A    [формула TCO на 36 місяців]
= 15 000 + 36 · 46 000 + 0.15 · 90 000         [підстановка значень Варіанта А]
= 15 000 + 1 656 000 + 13 500                  [обчислення оперативного інтегралу й ризику]
= 1 684 500 €                                  [сукупні витрати Варіанта А]
```

Обчислимо сукупну вартість TCO для Варіанта Б на горизонті `T = 36` місяців:

```
TCO_B(36)
= CapEx_B + 36 · OpEx_B + P_B · ExitCost_B    [формула TCO на 36 місяців]
= 125 000 + 36 · 9 000 + 0.05 · 25 000         [підстановка значень Варіанта Б]
= 125 000 + 324 000 + 1 250                    [обчислення оперативного інтегралу й ризику]
= 450 250 €                                    [сукупні витрати Варіанта Б]
```

Точка окупності капітальних витрат (англ. *payback period*) за часом `T_payback` розраховується з рівності додаткових CapEx і зекономленого OpEx:

```
CapEx_B - CapEx_A = T_payback · ΔOpEx          [умова окупності початкових інвестицій]
125 000 - 15 000  = T_payback · 37 000         [підстановка капітальних витрат і різниці OpEx]
110 000           = T_payback · 37 000         [різниця початкових капіталовкладень]
T_payback         = 110 000 / 37 000           [ділення доданого CapEx на щомісячний виграш]
                  ≈ 2.97 місяця                [строк повного повернення інвестицій]
```

Вже на третьому місяці експлуатації при навантаженні 100 000 осель додаткові капітальні витрати Варіанта Б у розмірі 110 000 € повністю перекриваються економією на оперативних рахунках хмари. А за 3 роки чиста економія становить понад 1.23 мільйона євро, підвищуючи валову маржу продукту з 59.2% (`(120 000 - 49 000) / 120 000`) до 89.2% (`(120 000 - 13 000) / 120 000`).

### Кейс 2: Економіка репатріації медіа-сховища (S3 vs On-Premises MinIO)

Припустімо, система збереження відеоархіву з камер спостереження DH зберігає `500 TB` даних і генерує `50 TB` вихідного трафіку (Egress) на місяць для перегляду користувачами.

**Варіант А: Хмарне сховище AWS S3 Standard**
- Збереження: `500 TB · 1024 GB/TB · 0.023 $/GB = 11,776 $/місяць`
- Egress-трафік: `50 TB · 1024 GB/TB · 0.09 $/GB = 4,608 $/місяць`
- `OpEx_S3 = 11,776 + 4,608 = 16,384 $/місяць`

**Варіант Б: Власний JBOD-сервер із MinIO у Co-location стійці**
- Закупівля заліза (CapEx): 4 сервери Supermicro з дисками NVMe/HDD по 150 TB netto (із запасом та redundancy) = `45,000 $` (амортизація на 3 роки = `1,250 $/місяць`).
- Оренда стійки та живлення (OpEx): `1,200 $/місяць`.
- Безлімітний транзитний канал 10 Gbps unmetered (OpEx): `1,500 $/місяць`.
- `OpEx_MinIO = 1,250 + 1,200 + 1,500 = 3,950 $/місяць`

Порівняння щомісячної економії на масиві відеоданих:

```
ΔOpEx_storage = OpEx_S3 - OpEx_MinIO
              = 16,384 - 3,950
              = 12,434 $/місяць
```

За термін амортизації у 3 роки (36 місяців) репатріація відеосховища заощаджує:

```
Total_Savings
= 36 · 12,434 - CapEx_setup        [формула 36 місяців економії за вирахуванням початкового CapEx]
= 447,624 - 15,000                 [підстановка 36-місячного накопиченого OpEx та CapEx]
= 432,624 $                        [чиста 3-річна економія від репатріації]
```

### Кейс 3: Нелінійна штрафна функція затримок у теорії масового обслуговування

Коли утилізація CPU процесів обробки `ρ` (англ. *CPU utilization*) наближається до 100%, затримка обробки запиту `W` зростає нелінійно за законом теорії масового обслуговування M/M/1:

```
W(ρ) = W₀ / (1 - ρ)
```
[де `W₀` — час обробки запиту при нульовому навантаженні]

Якщо для запобігання сплескам затримок інфраструктура налаштована на вимушене автомасштабування при `ρ > 50%`, коефіцієнт переплати за зарезервовану потужність (англ. *headroom cost factor*) становить:

```
k_headroom = 1 / ρ_target = 1 / 0.50 = 2.0
```

Це означає, що 50% усіх сплачених vCPU хмари перебувають у простої заради гасіння пікових сплесків затримок. Асинхронна архітектура з буферизацією в RabbitMQ/Kafka дозволяє підвищити цільову утилізацію до `ρ_target = 85%`, зменшуючи коефіцієнт переплати до `k_headroom = 1 / 0.85 ≈ 1.17`, що знижує загальні інфраструктурні витрати на обчислення на 41.5%.
