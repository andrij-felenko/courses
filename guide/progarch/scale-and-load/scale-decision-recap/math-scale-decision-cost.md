# 🧮 Математична модель TCO та ефективності масштабування

Ця вставка формулює строгий математичний апарат для розрахунку сукупної вартості володіння (TCO), ефективності масштабування за розширеним Законом Амдала, аналізу накопичення затримок у розподілених RPC-ланцюжках та теорії масового обслуговування. Обчислення дозволяють кількісно обґрунтувати межу, за якою подальше горизонтальне масштабування стає збитковим та деградує продуктивність системи.

## 1. Розширений Закон Амдала з урахуванням координувального оверхеду

Класичний Закон Амдала оцінює теоретичне прискорення виконання обчислювальної задачі при збільшенні кількості паралельних вузлів `N`. Проте класична формула припускає, що міжвузлові комунікаційні витрати дорівнюють нулю.

У реальних розподілених системах додавання кожного нового вузла створює додатковий оверхед на мережеву синхронізацію, консенсус, реплікацію та оновлення топології. Модель Гюнтера (Universal Scalability Law, USL) враховує як послідовну частку коду `1 - p`, так і два типи міжвузлових втрат: контенцію ресурсів (пропорційну `N`) та накладні витрати когерентності/синхронізації (пропорційні `N · (N - 1)`).

Позначимо:
*   `p` — частка коду, що піддається паралелізації (`0 ≤ p ≤ 1`).
*   `1 - p` — послідовна частка коду (критична секція, синхронний запис у WAL, єдина точка координування).
*   `α` — коефіцієнт контенції ресурсів (очікування блокувань, конкуренція за спільні шини чи канали).
*   `β` — коефіцієнт когерентності міжвузлового обміну (затримки узгодження стану, кворумні виклики).

Розширена формула ефективного прискорення `S(N)` має вигляд:

```
S(N)
= N / (1 + α·(N - 1) + β·N·(N - 1))                      [базова формула USL Гюнтера]
= 1 / ((1/N) + α·(1 - 1/N) + β·(N - 1))                 [приведення до питомого вузла]
```

Фізичний зміст коефіцієнтів у контексті розподілених баз даних:
*   `α` (Контенція) відображає конкуренцію за фізичні ресурси накопичувачів, мережеві сокети та блокування рядків у базі даних. Зі зростанням `N` ймовірність того, що два вузли намагатимуться оновити один і той самий ресурс, зростає лінійно.
*   `β` (Когерентність) відображає затримки поширення інформації про стан між вузлами (Cache Coherence Overhead). У кластері з `N` вузлів підтримка узгодженого стану вимагає `N · (N - 1) / 2` двосторонніх зв'язків. Для консенсусних протоколів (Raft, Paxos) кожен коміт вимагає кворумного підтвердження від більшості вузлів, що створює квадратне зростання трафіку інвалідації.

Якщо знехтувати вторинним ефектом контенції (`α ≈ 0`) і розглядати лише лінійний оверхед мережевої координування `γ · N` (де `γ` — питомий оверхед на вузол), формула спрощується до моделі розподіленого прискорення:

```
S_dist(N)
= 1 / ((1 - p) + (p / N) + γ · N)                       [модель розподіленого прискорення]
```

Обчислимо точку екстремуму (оптимальну кількість вузлів `N_opt`), при якій прискорення `S_dist(N)` досягає свого фізичного максимуму:

```
dS_dist / dN
= -1 / ((1 - p) + (p / N) + γ · N)² · (-p / N² + γ)     [взяття першої похідної за N]

-p / N² + γ = 0                                         [умова досягнення екстремуму]

γ = p / N²                                             [ізоляція коефіцієнта оверхеду]

N_opt = √(p / γ)                                       [формула оптимального розміру кластера]
```

### Практичний розрахунок точки насичення та деградації

Розглянемо приклад: паралельна частка обробки запитів становить `p = 0.95` (95% коду виконується паралельно), а питомий оверхед координування вузлів кластера дорівнює `γ = 0.0005` (0.05% на кожну додаткову ноду через сервіс-діскавері та хеш-кільце).

Обчислимо оптимальний розмір кластера `N_opt`:

```
N_opt
= √(0.95 / 0.0005)                                      [підстановка параметрів p та gamma]
= √1900                                                [обчислення частки під коренем]
= 43.58                                                [значення оптимальної кількості вузлів]
```

Обчислимо прискорення `S(N)` для `N = 10`, `N = 44` та `N = 100`:

```
S(10)
= 1 / ((1 - 0.95) + (0.95 / 10) + 0.0005 · 10)         [підстановка N = 10 у формулу прискорення]
= 1 / (0.05 + 0.095 + 0.005)                            [обчислення суми знаменника]
= 1 / 0.150                                             [значення знаменника]
= 6.67                                                 [підсумкове прискорення 6.67x на 10 вузлах]
```

```
S(44)
= 1 / ((1 - 0.95) + (0.95 / 44) + 0.0005 · 44)         [підстановка N = 44 у формулу прискорення]
= 1 / (0.05 + 0.02159 + 0.02200)                        [обчислення значень компонентів]
= 1 / 0.09359                                           [значення знаменника в точці екстремуму]
= 10.68                                                [максимальне прискорення 10.68x на 44 вузлах]
```

```
S(100)
= 1 / ((1 - 0.95) + (0.95 / 100) + 0.0005 · 100)       [підстановка N = 100 у формулу прискорення]
= 1 / (0.05 + 0.0095 + 0.050)                           [обчислення переважного оверхеду]
= 1 / 0.1095                                            [значення знаменника при перевищенні оптимуму]
= 9.13                                                 [деградація прискорення до 9.13x при 100 вузлах]
```

Збільшення кластера з 44 до 100 вузлів не лише не збільшило пропускну здатність, а навпаки **зменшило загальне прискорення на 14.5%** через переважання міжвузлового координувального оверхеду.

## 2. Математична модель TCO (Total Cost of Ownership)

Загальна вартість володіння інфраструктурою складається з двох компонентів: прямих інфраструктурних витрат (сервери, хмара, мережа, ліцензії) та непрямих операційних витрат (зарплати інженерів, інциденти, підтримка Kubernetes, SRE-чергування).

Формула TCO за місяць:

```
TCO(N)
= C_infra(N) + C_ops(N)                                 [базова загальна формула TCO]
```

Де прямі інфраструктурні витрати `C_infra(N)` для кластера з `N` вузлів обчислюються як:

```
C_infra(N)
= N · C_node + C_lb + C_mesh + C_storage               [компоненти інфраструктурних витрат]
```

*   `C_node` — щомісячна оренда/амортизація одного обчислювального вузла.
*   `C_lb` — вартість балансувальників трафіку (L4/L7 LB, Ingress).
*   `C_mesh` — вартість керованих контрольних площин (Service Mesh, Control Plane).
*   `C_storage` — витрати на розподілені сховища та мережеві диски.

Операційні витрати `C_ops(N)` є нелінійною функцією від кількості розподілених елементів через зростання когнітивного навантаження на команду:

```
C_ops(N)
= C_base_eng · (1 + λ · N^η)                             [нелінійна модель операційних витрат]
```

*   `C_base_eng` — базова місячна ставка інженерної підтримки монолітного застосунку (наприклад, $10,000/місяць).
*   `λ` — коефіцієнт складності розподіленого середовища (`0.05 ≤ λ ≤ 0.15`).
*   `η` — степенний показник зростання складності конфігурації та моніторингу (`1.1 ≤ η ≤ 1.4`).

### Порівняльний розрахунок TCO: Scale-Up проти Scale-Out

Розглянемо дві еквівалентні за пропускною здатністю конфігурації для обробки 50,000 QPS:

#### Варіант A: Вертикальне масштабування (Scale-Up Моноліт)
*   `N = 2` вузли (1 Active primary 128-core, 1 Standby failover).
*   `C_node` = $1,800/місяць за сервер (128 vCPU, 512GB RAM, 2x NVMe 3.84TB).
*   `C_lb` = $100/місяць.
*   `C_ops` = $10,000 · (1 + 0.05 · 2^1.1) = $10,000 · 1.107 = $11,070/місяць.

```
TCO_ScaleUp
= (2 · 1800 + 100) + 11 070                             [підстановка вартості 2 нод, LB та операційних витрат]
= 3700 + 11 070                                         [обчислення суми інфраструктурних та SRE витрат]
= 14 770 $/month                                        [підсумкова вартість володіння на місяць]
```

#### Варіант B: Горизонтальне масштабування (Scale-Out 40 Мікросервісів у K8s)
*   `N = 30` дрібних вузлів (8 vCPU, 16GB RAM) по $150/місяць кожен.
*   `C_lb` + `C_mesh` + `Managed Kafka/Redis` = $2,500/місяць.
*   `C_ops` = $10,000 · (1 + 0.05 · 30^1.1) = $10,000 · (1 + 0.05 · 42.16) = $10,000 · 3.108 = $31,080/місяць.

```
TCO_ScaleOut
= (30 · 150 + 2500) + 31 080                            [підстановка 30 нод, LB/Mesh та операційних витрат SRE]
= 7000 + 31 080                                         [обчислення суми інфраструктурних та SRE витрат]
= 38 080 $/month                                        [підсумкова вартість володіння на місяць]
```

Сукупна вартість володіння варіанта Scale-Out виявилася у **2.57 рази вищою** ($38,080 проти $14,770 на місяць) при тому самому цільовому рівні навантаження, причому 81.6% усіх витрат мікросервісного підходу складають не сервери, а операційна складність обслуговування розподіленого середовища.

## 3. Накопичення затримок у RPC-ланцюжках та хвостова латентність

При мікросервісному розпилі один вхідний користувацький запит часто викликає каскад з `m` послідовних або паралельних RPC-викликів між сервісами.

Обчислимо підсумкову затримку `L_total` для послідовного ланцюжка з `m` хопів:

```
L_total
= ∑_{i=1}^{m} (L_exec_i + L_net_i + L_ser_i)             [сума затримок усіх хопів ланцюжка]
```

*   `L_exec_i` — час виконання бізнес-логіки на сервісі `i`.
*   `L_net_i` — мережевий RTT між сервісом `i` та `i+1` (включаючи DNS, TLS handshake, TCP/IP overhead).
*   `L_ser_i` — час серіалізації/десеріалізації Protobuf/JSON.

Навіть якщо мережева затримка на один хоп становить всього `L_net = 2 ms`, а серіалізація `L_ser = 0.5 ms`, для ланцюжка з `m = 8` сервісів сумарний мережево-десеріалізаційний оверхед складе:

```
L_overhead_total
= 8 · (2.0 + 0.5)                                      [підстановка 8 хопів із затримкою 2.5 ms кожен]
= 20.0 ms                                              [чистий оверхед без урахування обчислень]
```

У монолітному застосунку ці самі 8 викликів є локальними викликами функцій у пам'яті процесу із затримкою `0.001 ms` на кожен виклик (загальний оверхед `0.008 ms`), що у **2500 разів швидше**.

### Ефект множення хвостової затримки (Tail Latency Amplification)

Нехай ймовірність того, що окремий сервіс відповість із затримкою вище перцентиля p99 (тобто потрапить у 1% найповільніших відповідей), дорівнює `q = 0.01`.

Якщо бізнес-операція вимагає паралельного виклику `m` незалежних сервісів, підсумковий запит вважається успішним лише тоді, коли *усі* `m` сервісів відповіли вчасно. Ймовірність `P_system_p99` того, що підсумковий запит **зазнає деградації tail latency**, обчислюється як:

```
P_system_ok
= (1 - q)^m                                            [ймовірність виконання усіх m викликів без затримок]

P_system_p99
= 1 - P_system_ok                                      [доповнення до повної ймовірності]
= 1 - (1 - q)^m                                        [формула ймовірності потрапляння підсумкового запиту в tail]
```

Обчислимо деградацію p99 затримки для різної кількості мікросервісів у каскаді:

```
m = 1   (Моноліт / 1 сервіс):
P_system_p99
= 1 - (1 - 0.01)¹                                      [підстановка m = 1]
= 0.010                                                [1.0% запитів зазнають p99 затримки]

m = 10  (10 мікросервісів):
P_system_p99
= 1 - (0.99)¹⁰                                         [підстановка m = 10]
= 1 - 0.9044
= 0.0956                                               [9.56% запитів зазнають p99 затримки]

m = 50  (50 мікросервісів):
P_system_p99
= 1 - (0.99)⁵⁰                                         [підстановка m = 50]
= 1 - 0.6050
= 0.3950                                               [39.5% запитів зазнають p99 затримки]

m = 100 (100 мікросервісів):
P_system_p99
= 1 - (0.99)¹⁰⁰                                        [підстановка m = 100]
= 1 - 0.3660
= 0.6340                                               [63.4% запитів зазнають p99 затримки]
```

При 50 мікросервісах у ланцюжку **майже 40% усіх користувацьких запитів** зіштовхуються з високою затримкою перцентиля p99. Система стає нестабільною, а показник p99 фактично деградує до рівня середнього значення p60.

## 4. Теорія масового обслуговування: Перевага об'єднаного пулу (M/M/c проти M/M/1)

Теорія масового обслуговування (Queuing Theory) надає ще одне математичне доведення переваги одного великого сервера перед кластером дрібних вузлів.

Розглянемо систему із загальним вхідним потоком запитів `λ` та загальною обчислювальною потужністю `μ`.

### Модель A: N ізольованих малих серверів (N окремих черг)
Кожен із `N` серверів має власну чергу та продуктивність `μ / N`. Вхідний потік ділиться рівномірно: `λ_i = λ / N`.

Середній час очікування запиту у черзі `W_isolated` за формулою M/M/1 дорівнює:

```
W_isolated
= 1 / ((μ / N) - (λ / N))                              [формула очікування M/M/1 для малих вузлів]
= N / (μ - λ)                                          [спрощення: очікування зростає в N разів]
```

### Модель B: Один великий об'єднаний сервер (Scale-Up єдина черга)
Один сервер обробляє увесь потік `λ` із продуктивністю `μ`.

Середній час очікування у черзі `W_pooled` за формулою M/M/1 дорівнює:

```
W_pooled
= 1 / (μ - λ)                                          [формула очікування M/M/1 для великого вузла]
```

Зіставляючи два вирази, отримуємо:

```
W_isolated / W_pooled
= (N / (μ - λ)) / (1 / (μ - λ))                         [ділення формул очікування моделей A та B]
= N                                                    [виграш об'єднаної черги становить N разів]
```

Об'єднання обчислювальної потужності у один великий сервер зменшує середній час очікування у черзі в `N` разів за рахунок ефективнішого згладжування випадкових сплесків трафіку (Statistical Multiplexing Gain).

## 5. Математична модель споживання оперативної пам'яті сокетами ядра

При масштабуванні з'єднань важливим чинником є розрахунок витрат оперативної пам'яті на підтримку відкритих TCP/TLS сокетів у ядрі Linux.

Загальний обсяг пам'яті `RAM_sockets` для `K` активних з'єднань обчислюється як:

```
RAM_sockets
= K · (sk_rcvbuf + sk_wmem + TLS_context + App_state)  [загальні витрати пам'яті сокетів]
```

Де:
*   `sk_rcvbuf` — буфер прийому сокета ядра Linux (типово від 8 KB до 128 KB при заторках мережі).
*   `sk_wmem` — буфер передачі сокета ядра Linux (від 8 KB до 64 KB).
*   `TLS_context` — криптографічний контекст симетричних ключів та буферів шифрування (16 KB для OpenSSL/BoringSSL).
*   `App_state` — доменна сесія у пам'яті процесу (16–32 KB).

Підставимо значення для `K = 100,000` з'єднань при стандартному буфері `sk_rcvbuf = 16 KB`:

```
RAM_single_socket
= 16 KB + 16 KB + 16 KB + 32 KB                        [додавання компонентів одного сокета]
= 80 KB                                                [витрати пам'яті на 1 сокет]

RAM_sockets_total
= 100 000 · 80 KB                                      [підстановка 100k сокетів]
= 8 000 000 KB                                         [обчислення у кілобайтах]
= 8.0 GB                                               [підсумковий обсяг RAM лише під сокети]
```

Якщо через деградацію диска буфер `sk_rcvbuf` розшириться ядром до `128 KB`, загальний обсяг пам'яті зросте до `19.2 GB`, що може активувати механізм Linux Kernel OOM Killer при відсутності закладеного запасу (Headroom).

Ці математичні моделі переконливо доводять: передчасне розбиття системи на розподілені вузли експоненційно підвищує операційні витрати, збільшує затримку відповіді та деградує надійність.
