# 📋 Специфікація протоколу та токенів доступу Virtual Waiting Room

Цей документ встановлює формальний контракт HTTP-протоколу, структуру токенів доступу, формат JSON-схем, специфікацію Server-Sent Events (SSE) та коди відповідей для взаємодії між Edge Gatekeeper, веб-клієнтами (браузерами та мобільними застосунками) та сервісом оркестрації черги Virtual Waiting Room.

Специфікація гарантує повну сумісність між шлюзами первинної перевірки на Edge (Cloudflare Workers, NGINX Lua, Envoy Proxy) та закритим мікросервісом сертифікації черги, забезпечуючи нульову неузгодженість при передачі прав на покупку квитків та виключаючи можливість несанкціонованого обходу.

## Архітектурний розподіл відповідальності та зони контракту

У разі побудови системи Virtual Waiting Room мережевий потік ділиться на дві чітко розмежовані території: зовнішній край (Edge Layer) та закриту зону обробки (Origin Zone). Кожна зона обробляє лише свою частину протокольного контракту.

Edge Gatekeeper працює на передньому краї Термінації TLS. Його єдина задача — провести швидку локальну перевірку наявності та криптографічної цілісності токену доступу. Якщо токен присутній, його підпис HMAC-SHA256 відповідає секретному ключу, а термін дії `exp` ще не вичерпано, Edge Gatekeeper пропускає HTTP-запит до Origin без жодного мережевого виклику у внутрішню мережу чи базу даних.

Сервіс очікування (Queue Orchestrator) живе на окремому субдомені (наприклад, `queue.domain.com`) і повністю бере на себе взаємодію з клієнтами, які не мають токену доступу. Він підтримує WebSocket або SSE-з'єднання, розраховує динамічну позицію користувача в FIFO-структурі Redis та випускає підписані токени доступу (Pass Tokens) при виникненні вільних слотів в Origin.

Origin Backend отримує лише ті запити, які пройшли перевірку на Edge. Завдяки цьому Origin гарантовано захищений від трафікових сплесків і обробляє лише контрольовану кількість покупців.

## Заголовки HTTP та Cookie контракту

Взаємодія між клієнтським браузером, шлюзом Edge Gatekeeper та сервісом черги здійснюється за допомогою набору стандартних та розширених HTTP-заголовків і криптографічно підписаних Cookie.

### Вхідні та вихідні заголовки Edge Gatekeeper

Нижче наведено повний перелік HTTP-заголовків, які беруть участь у контракті допуску, із зазначенням їхнього напрямку, допустимих значень та правил обробки:

| Назва заголовка | Напрямок | Семантика та формат | Приклад значення |
| :--- | :--- | :--- | :--- |
| `X-Waiting-Room-Token` | Client -> Edge | Передача підписаного токену доступу у заголовку HTTP-запиту. Використовується мобільними застосунками та SPA-клієнтами, де використання Cookie обмежене. | `eyJhbGciOiJIUzI1NiJ9...` |
| `Cookie: vwr_token` | Client -> Edge | Резервний та основний спосіб передачі токену для веб-браузерів. Автоматично додається браузером до кожного HTTP-запиту. | `vwr_token=usr_123:evt_456...` |
| `X-Waiting-Room-Status` | Edge -> Origin | Службовий заголовок, який Edge додає до запиту перед проксіюванням на Origin. Повідомляє Origin про спосіб допуску запиту. | `ADMITTED`, `BYPASS`, `QUEUED` |
| `X-Queue-Position` | Queue -> Client | Заголовок відповіді сервісу черги, що показує поточну абсолютну позицію користувача у списку очікування. | `1420` |
| `X-Queue-ETA` | Queue -> Client | Заголовок відповіді, що передає розрахований залишок часу очікування у секундах до моменту можливого допуску. | `180` |
| `X-Queue-Target-URL` | Edge -> Queue | Службовий заголовок перенаправлення, у якому Edge кодує оригінальну URL-адресу, яку намагався відкрити користувач. | `https://tickets.com/buy/123` |

### Детальна специфікація Cookie `vwr_token`

При випуску токену доступу сервісом черги, він кодується й записується у браузер користувача за допомогою HTTP-заголовка `Set-Cookie`. Для забезпечення максимального рівня безпеки та запобігання витоку токена через сторонні скрипти застосовуються такі суворі атрибути:

1. `HttpOnly`: Встановлюється в значення `true`. Це повністю блокує доступ до кукі з боку JavaScript (`document.cookie`), роблячи неможливим викрадення токена через XSS-вразливості у сторонніх виджетах або аналітичних скриптах.
2. `Secure`: Встановлюється в значення `true`. Прапор вимагає від браузера надсилати кукі виключно через зашифровані TLS/HTTPS-з'єднання. Передача токена через відкритий HTTP-протокол заборонена.
3. `SameSite=Lax`: Забезпечує передачу Cookie при перенаправленні користувача зі стороннього домену кімнати очікування (`queue.domain.com`) назад на основний домен продажів (`tickets.domain.com`). Значення `Lax` захищає від Cross-Site Request Forgery (CSRF) атак, але дозволяє безпечні переході за посиланнями Top-Level Navigation.
4. `Path`: Обмежує дію кукі конкретним шляхом події (наприклад, `/buy/event-123`) або встановлюється в `/` для всієї платформи.
5. `Max-Age`: Встановлює час життя кукі у браузері, який чітко відповідає тривалості активної сесії купівлі (зазвичай `600` секунд, тобто 10 хвилин).

## Специфікація структури токену доступу (Token Payload Schema)

Токен доступу випускається у форматі стандартного JSON Web Token (JWT) з підписом HMAC-SHA256 або у вигляді оптимізованого компактного бінарно-текстового рядка `payload.signature`.

### Формальна JSON-схема Payload (стандарт JWT)

Для валідації вмісту payload на стороні Origin або при інспекції токенів розробниками використовується наступна формальна схема JSON Schema Draft-07:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "WaitingRoomTokenPayload",
  "type": "object",
  "properties": {
    "sub": {
      "type": "string",
      "description": "Унікальний ідентифікатор користувача або анонімної сесії клієнта"
    },
    "event_id": {
      "type": "string",
      "description": "Ідентифікатор цільової події чи концерту"
    },
    "pos": {
      "type": "integer",
      "minimum": 1,
      "description": "Фінальний порядковий номер, із яким користувач вийшов із черги"
    },
    "iat": {
      "type": "integer",
      "description": "UNIX timestamp випуску токену (Unix epoch seconds)"
    },
    "exp": {
      "type": "integer",
      "description": "UNIX timestamp закінчення терміну дії токену"
    },
    "nonce": {
      "type": "string",
      "description": "Криптографічний сеансовий випадковий nonce для відсікання повторних відтворень"
    }
  },
  "required": ["sub", "event_id", "pos", "iat", "exp", "nonce"]
}
```

### Компактний string-формат для мінімізації накладних витрат

З метою зменшення обсягу мережевого трафіку на Edge Gatekeeper розроблено бінарно-текстовий формат токену без використання важких JSON-структур:

```
<customer_id>:<event_id>:<position>:<exp_timestamp>:<nonce>.<hmac_sha256_base64url>
```

Розберемо елементи цього формату на конкретному прикладі:
`usr_8f92a:evt_taylor_2026:1420:1784280000:c4ca4238.M0I0ZjE4YTEyMzQ1Njc4OWFiY2RlZmdoaWprbG1ub3A`

- `usr_8f92a`: Унікальний ідентифікатор покупця у системі.
- `evt_taylor_2026`: Ідентифікатор концертного туру.
- `1420`: Порядковий номер у черзі, за яким було видано допуск.
- `1784280000`: Час вигасання токена у форматі Unix Timestamp.
- `c4ca4238`: Одноразовий nonce хеш для запобігання підробок.
- `M0I0ZjE4...`: Base64URL-кодований HMAC-SHA256 підпис першої частини рядка (до крапки).

## Специфікація ендпоінтів сервісу оркестрації черги

Сервіс оркестрації черги надає два основних методи взаємодії для веб-клієнтів: традиційне опитування через REST API та потік подій у режимі реального часу через Server-Sent Events (SSE).

### 1. Опитування статусу черги (REST API Status Polling)

Застосовується браузерами у разі відсутності підтримки SSE або при нестабільному мобільному з'єднанні.

При виконанні опитування клієнтський застосунок зобов'язаний аналізувати параметр `poll_interval_ms`, повернутий у тілі відповіді. Цей параметр розраховується сервісом черги адаптивно: якщо загальна кількість користувачів у черзі зростає, сервіс динамічно збільшує інтервал опитування з 3 000 мс до 10 000 мс, щоб захистити власну інфраструктуру від шторму опитування (Polling Storm).

Якщо клієнт ігнорує переданий інтервал і надсилає запити частіше, ніж дозволено, Edge WAF повертає код `429 Too Many Requests` із заголовком `Retry-After: 10`, блокуючи запити клієнта на 10 секунд.

**HTTP Запит:**
```http
GET /api/v1/queue/status?event_id=evt_taylor_2026&customer_id=usr_8f92a HTTP/1.1
Host: queue.domain.com
Accept: application/json
X-Waiting-Room-Session: sess_9988776655
```

**Відповідь HTTP 200 OK (Стан очікування у черзі):**
Сервіс повертає статус `WAITING`, поточну позицію користувача та рекомендований інтервал наступного опитування `poll_interval_ms`. Дотримання цього інтервалу є обов'язковим для клієнта: надсилання запитів частіше за вказаний інтервал призводить до блокування за кодом `429 Too Many Requests`.

```json
{
  "status": "WAITING",
  "event_id": "evt_taylor_2026",
  "customer_id": "usr_8f92a",
  "position": 342,
  "total_queued": 45000,
  "eta_seconds": 180,
  "poll_interval_ms": 5000,
  "pass_token": null
}
```

**Відповідь HTTP 200 OK (Настання черги — Admitted):**
Коли позиція користувача досягає порогу допуску, сервіс змінює статус на `ADMITTED`, повертає згенерований `pass_token` та цільову URL-адресу для перенаправлення `target_url`.

```json
{
  "status": "ADMITTED",
  "event_id": "evt_taylor_2026",
  "customer_id": "usr_8f92a",
  "position": 342,
  "eta_seconds": 0,
  "target_url": "https://tickets.domain.com/buy/evt_taylor_2026",
  "pass_token": "usr_8f92a:evt_taylor_2026:342:1784280000:c4ca4238.M0I0ZjE4YTEyMzQ1...",
  "expires_in_seconds": 600
}
```

### 2. Потік подій у режимі реального часу (Server-Sent Events Stream)

Для мінімізації накладних витрат на HTTP-заголовки рекомендується використовувати постійне SSE-з'єднання.

SSE-з'єднання підтримується у відкритому стані за допомогою періодичних серцебиттєвих повідомлень (Heartbeat Pings) `comment: ping` кожні 15 секунд. Це запобігає розриву TCP-сесії проміжними проксі-серверами та NAT-шлюзами мобільних операторів.

У разі аварійного обриву зв'язку браузер автоматично перепідключається до ендпоінту, передаючи заголовок `Last-Event-ID`. Сервіс черги відновлює стан користувача без втрати його позиції.

**HTTP Запит на відкриття потоку:**
```http
GET /api/v1/queue/stream?event_id=evt_taylor_2026&session_id=sess_9988776655 HTTP/1.1
Host: queue.domain.com
Accept: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```

**Специфікація подій SSE-потоку:**

Сервіс черги генерує два типи подій: `queue_update` (періодичне оновлення позиції) та `queue_admitted` (видача дозволу на покупку).

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no

event: queue_update
data: {"position": 310, "eta_seconds": 160, "total_queued": 44800}

event: queue_update
data: {"position": 140, "eta_seconds": 70, "total_queued": 43500}

event: queue_admitted
data: {"status": "ADMITTED", "pass_token": "usr_8f92a:evt_taylor_2026:342:1784280000:c4ca4238.M0I0ZjE4...", "target_url": "https://tickets.domain.com/buy/evt_taylor_2026"}
```

### 3. Продовження активної сесії (Heartbeat Checkout Endpoint)

Під час вибору місць на схемі залу або введення реквізитів банківської картки клієнтський застосунок кожні 60 секунд надсилає фоновий heartbeat-запит. Це запобігає анулюванню токена до закінчення процедури оплати.

Якщо протягом 3 хвилин від клієнта не надходить жодного heartbeat-запиту, або якщо таймер `T_checkout` досягає граничного значення 10 хвилин, Origin вважає сесію покинутою і надсилає сигнал до сервісу черги про анулювання токена.

**HTTP Запит:**
```http
POST /api/v1/queue/checkout/heartbeat HTTP/1.1
Host: tickets.domain.com
Content-Type: application/json
X-Waiting-Room-Token: usr_8f92a:evt_taylor_2026:342:1784280000:c4ca4238.M0I0Zj...

{
  "event_id": "evt_taylor_2026",
  "checkout_session_id": "cs_1122334455"
}
```

**Відповідь HTTP 200 OK:**
```json
{
  "status": "EXTENDED",
  "new_exp": 1784280600,
  "remaining_checkout_seconds": 540
}
```

## Контракт кодів відповідей та специфікація помилок

Для забезпечення однозначної обробки ситуацій на Edge Gatekeeper та клієнтських пристроях визначено чітку матрицю кодів відповідей HTTP:

| Код HTTP | Сценарій використання | Формат відповіді та дії клієнта |
| :--- | :--- | :--- |
| `302 Found` | Запит до Origin без токену або з простроченим токеном. | Перенаправлення браузера на `queue.domain.com`. |
| `307 Temporary Redirect` | Перенаправлення із збереженням HTTP-методу POST. | Використовується при спробі відправки форми без токена. |
| `401 Unauthorized` | Токен підроблено або HMAC-підпис не відповідає ключу. | Скидання кукі `vwr_token` та перенаправлення в кінець черги. |
| `403 Forbidden` | Токен випущено для іншої події (`event_id` mismatch). | Відображення помилки недоступності квитків для цієї події. |
| `410 Gone` | Термін дії токену повністю вичерпано (Session Expired). | Анулювання слота й повернення користувача в кімнату очікування. |
| `429 Too Many Requests` | Перевищення дозволеної частоти опитування статусу. | Повторна спроба через час, вказаний у заголовку `Retry-After`. |

### Схема обробки помилок за стандартом RFC 7807 (Problem Details)

У разі відмови у допуску або виникнення помилок валідації токена Origin повертає деталізований об'єкт помилки у форматі JSON:

```json
{
  "type": "https://errors.domain.com/vwr/token-expired",
  "title": "Pass Token Expired",
  "status": 410,
  "detail": "Таймаут сесії оформлення квитка (10 хвилин) вичерпано. Ваш слот повернуто в загальну чергу.",
  "instance": "/buy/evt_taylor_2026",
  "code": "VWR_TOKEN_EXPIRED",
  "timestamp": 1784280650,
  "action_required": "REJOIN_QUEUE"
}
```

## Правила обходу черги (Bypass Rules Contract)

Для забезпечення безперебійної роботи адміністраторів платформи, автоматичних систем моніторингу (Health Checks) та платіжних вебхуків від банківських еквайєрів Edge Gatekeeper підтримує приватоний механізм обходу черги (Bypass).

Запит вважається службовим і пропускається до Origin без перевірки токена черги виключно при дотриманні двох обов'язкових умов:
1. Запит містить приватний заголовок високої ентропії `X-VWR-Bypass-Key: <secret_key_64_hex_chars>`.
2. IP-адреса джерела запиту входить до строго визначеної внутрішньої CIDR-підмережі (наприклад, `10.0.0.0/8` або зареєстровані IP-адреси платіжного шлюзу).

При успішній перевірці обох умов Edge Gatekeeper додає заголовок `X-Waiting-Room-Status: BYPASS` і передає запит до Origin без перенаправлення на кімнату очікування.
