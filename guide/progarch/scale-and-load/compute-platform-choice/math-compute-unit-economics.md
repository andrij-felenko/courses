# 🧮 Математична модель TCO та утилізації compute

Розрахунок економічної доцільності обчислювальної платформи спирається на формальне співвідношення між коефіцієнтом утилізації виділених ресурсів, профілем пилкоподібного навантаження та структурою ціноутворення хмарного чи фізичного провайдера. Помилкова оцінка цих математичних залежностей призводить до перевитрат бюджету в 5–10 разів при масштабуванні Highload-систем.

## 1. Загальна формалізація TCO обчислень

Сукупна вартість володіння обчислювальною інфраструктурою (`TCO`, Total Cost of Ownership) за місячний період (730 годин) виражається сумою трьох складових:

```
TCO = C_compute + C_control + C_ops
```

Де:
- `C_compute` — прямі витрати на процесорний час (vCPU) та оперативну пам'ять (RAM);
- `C_control` — фіксовані накладні витрати на оркестрацію та керовані сервіси (Control Plane, Master-вузли);
- `C_ops` — вартість операційного обслуговування (інженерні людино-години на підтримку ОС, оновлення кластера, чергування).

Для порівняння трьох парадигм обчислень розрахуємо `TCO` як функцію від сукупної кількості оброблених запитів `N_req`, середнього часу виконання запиту `T_sec` (в секундах), розміру виділеної пам'яті `M_gb` (в гігабайтах) та коефіцієнта утилізації виділеного обладнання `U`.

Коефіцієнт утилізації `U` визначається як відношення середнього споживання CPU до пікової зарезервованої потужності:

```
U = CPU_avg / CPU_peak     [де 0 < U ≤ 1.0]
```

Коефіцієнт спалаховості (Burstiness Ratio `R_burst`) визначає амплітуду піків відносно середнього значення:

```
R_burst = CPU_peak / CPU_avg = 1 / U
```

При значеннях `R_burst > 10` навантаження вважається суворо спалаховим, а при `R_burst < 1.5` — монотонним (цілодобовий фоновий потік).

## 2. Модель 1: Serverless (AWS Lambda / Cloud Run)

У бессерверній моделі провайдер тарифікує фактично спожиті мілісекунди обчислень та кількість викликів. При відсутності трафіку витрати дорівнюють нулю (`C_idle = 0`).

Формула щомісячних витрат Serverless:

```
TCO_serverless = N_req · P_req + N_req · T_sec · M_gb · P_gbsec
```

Де:
- `P_req` — вартість 1 мільйона HTTP/Event викликів (наприклад, 0.20 USD за 1M);
- `P_gbsec` — вартість 1 гігабайт-секунди виконання (наприклад, 0.0000166667 USD за GB-sec);
- `M_gb` — виділена оперативна пам'ять на екземпляр функції;
- `T_sec` — тривалість виконання одного запиту.

Припускаючи `C_control = 0` та `C_ops ≈ 0` (провайдер повністю бере на себе управління ОС та масштабуванням), підставимо сукупний процесорний час `CPU_total_sec = N_req · T_sec`:

```
TCO_serverless = N_req · P_req + CPU_total_sec · (M_gb · P_gbsec)
```

**Особливість:** Ціна за одиницю обчислень `P_gbsec` містить високу маржу провайдера за готовність миттєво виділити ресурси під пилкоподібний спалах без фіксованої плати за простої.

## 3. Модель 2: Managed Kubernetes (EKS / GKE)

У кластерній моделі Kubernetes витрати складаються з фіксованої плати за управляючий шар (Control Plane `P_cp`) та погодинної плати за оренду виділених нод (Worker Nodes).

Нехай `C_node` — потужність однієї ноди (наприклад, 8 vCPU, 32 GB RAM), `P_node_hr` — вартість ноди за годину. Кількість необхідних нод `N_nodes` визначається піковим навантаженням `CPU_peak` та цільовим порогом автоскейлінгу `U_target` (зазвичай 70% або 0.70):

```
N_nodes = ⌈ CPU_peak / (C_node · U_target) ⌉
```

Формула щомісячних витрат Managed Kubernetes:

```
TCO_k8s = P_cp + 730 · N_nodes · P_node_hr + C_ops_k8s
```

Де:
- `P_cp` = 73 USD / місяць (фіксована плата за EKS control plane);
- `C_ops_k8s` — витрати на адміністрування K8s (ingress, CNI, storage, security monitoring).

Виразимо `N_nodes` через середнє навантаження `CPU_avg` та коефіцієнт утилізації `U`:

```
N_nodes = ⌈ (CPU_avg / U) / (C_node · U_target) ⌉
        = ⌈ CPU_avg / (U · C_node · U_target) ⌉      [підстановка CPU_peak = CPU_avg / U]
```

Звідси очевидно: якщо середня утилізація `U` падає до 5% (дуже спалахове навантаження), кількість необхідних нод `N_nodes` зростає у 20 разів порівняно з рівномірним навантаженням, оскільки ноди мусять постійно підтримувати кворум для згладжування піків.

### Вплив використання Spot-нод у Kubernetes

Використання перериваних нод (Spot/Preemptible Instances) дозволяє зменшити `P_node_hr` на 60–80%, проте запроваджує імовірність раптового вилучення ноди `P_evict`. Модель TCO з урахуванням Spot-нод вимагає введення коефіцієнта резервного кворуму `B_spot = 1.20`:

```
TCO_k8s_spot = P_cp + 730 · (N_nodes · B_spot) · (P_node_hr · 0.30) + C_ops_k8s
```

## 4. Модель 3: Bare Metal / Dedicated VM Fleet

У физичній моделі компанія купує або орендує фізичні сервери з фіксованою щомісячною платою.

```
TCO_baremetal = N_servers · P_server_month + C_datacenter + C_ops_hw
```

Де:
- `P_server_month` — оренда сервера або амортизація заліза `CAPEX / 36` місяців;
- `C_datacenter` — плата за стійку, електроенергію (PUE) та канали зв'язку;
- `C_ops_hw` — зарплата інженерів підтримки заліза, заміна збійних дисків та планок RAM.

У цій моделі вартість однієї процесорної секунди `P_core_sec_bm` є мінімальною на ринку, але `TCO_baremetal` повністю фіксований і не залежить від поточного трафіку (`N_req`). При `N_req = 0` витрати залишаються 100% максимальними (`Idle Penalty`).

## 5. Виведення точок економічного перетину (Breakeven Points)

Знайдемо критичне значення утилізації `U_crit1`, при якому витрати на Serverless дорівнюють витратам на Managed Kubernetes (`TCO_serverless = TCO_k8s`).

Прирівняємо дві моделі для потоку запитів `N_req` з тривалістю `T_sec`:

```
N_req · P_req + (N_req · T_sec) · M_gb · P_gbsec
= P_cp + 730 · (CPU_avg / (U · C_node · U_target)) · P_node_hr + C_ops_k8s
```

Спростимо рівняння, згрупувавши сукупний процесорний час `CPU_total_sec = N_req · T_sec` та виразивши `CPU_avg = CPU_total_sec / (730 · 3600)`:

```
CPU_total_sec · [ P_gbsec · M_gb + (P_req / T_sec) ]
= P_cp + C_ops_k8s + CPU_total_sec · [ P_node_hr / (3600 · U · C_node · U_target) ]
```

Розв'яжемо відносно `U`:

```
U_crit1 = P_node_hr / [ 3600 · C_node · U_target · (P_gbsec · M_gb + P_req / T_sec - (P_cp + C_ops) / CPU_total_sec) ]
```

Аналогічним чином обчислимо точну точку перетину `U_crit2` між Managed Kubernetes та Bare Metal (`TCO_k8s = TCO_baremetal`):

```
U_crit2 = (730 · CPU_avg · P_node_hr) / [ C_node · U_target · (TCO_baremetal - P_cp - C_ops_k8s) ]
```

## 6. Аналіз чутливості та числові результати

Підставимо реальні тарифи хмарних провайдерів (AWS us-east-1):
- `P_gbsec` = 0.00001667 USD
- `M_gb` = 1 GB
- `P_node_hr` = 0.34 USD (для c6i.2xlarge: 8 vCPU, 16 GB RAM)
- `C_node` = 8 vCPU
- `U_target` = 0.70

Аналіз отриманого рівняння дає три фундаментальні висновки:

1. **Вплив розміру оперативної пам'яті (`M_gb`):** Збільшення пам'яті функції з 512 MB до 2 GB пропорційно підвищує `P_gbsec · M_gb`, що зміщує точку перетину `U_crit1` ліворуч (з 18% до 8%). Це означає, що для важких додатків з великим RAM footprint Kubernetes стає економічно вигіднішим значно раніше.
2. **Вплив тривалості запиту (`T_sec`):** Для довгих запитів (`T_sec > 10` секунд) частка фіксованої плати за виклик `P_req` нівелюється, і вартість Serverless визначається виключно чистим споживанням `GB·sec`.
3. **Граничні зони вибору:**
   - При `U < 15%`: Serverless є безумовним лідером завдяки нульовій платі за простій.
   - При `15% ≤ U ≤ 65%`: Managed Kubernetes забезпечує найдешевший баланс за рахунок HPA та Spot-нод.
   - При `U > 65%`: Bare Metal або довгострокові Reserved Instances зменшують TCO на 70% порівняно з будь-якими хмарними ефемерними сервісами.
