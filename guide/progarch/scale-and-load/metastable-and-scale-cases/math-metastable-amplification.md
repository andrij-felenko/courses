# 🧮 Математична модель метастабільного підсилення та гістерезису

Математичний аналіз стійкості розподілених систем спирається на моделювання залежності між зовнішнім вхідним навантаженням (Offered Load) `L`, фактично виконаною внутрішньою роботою (Work Performed) `W(L)` та пропускною спроможністю системи (Capacity) `C`. У стабільному стані внутрішня робота лінійно відповідає вхідному навантаженню (`W(L) ≈ L`). Проте виникнення відмов та повторних спроб створює нелінійний коефіціент підсилення (Work Amplification Factor), який перетворює систему на бістабільну динамічну модель із гістерезисом.

## Коефіцієнт підсилення роботи W(L)

Розглянемо потік вхідних запитів з інтенсивністю `L` (запитів за секунду). Нехай кожен запит у разі успішного виконання вимагає `1` одиницю обчислитеної роботи. Якщо затримка відповіді сервісу `T(L)` перевищує клієнтський таймаут `T_timeout`, клієнт анулює поточний виклик і з ймовірністю `r` надсилає повторний запит.

Ймовірність того, що запит зазнає таймауту або відмови `P_retry(L)`, залежить від завантаження сервісу `U = W(L) / C`. У найпростішій моделі одноканального обслуговування M/M/1 середня затримка відповіді `T(L)` виражається як:

```
T(L) = T_base / (1 - W(L) / C)      [модель затримки M/M/1 при завантаженні U = W/C]
```

Фізичний зміст цього рівняння полягає у тому, що при наближенні завантаження `W(L)` до граничної спроможності `C` черга запитів стає нескінченно довгою, а затримка зростає гіперболічно.

Для систем із обмеженим буфером черги M/M/1/K довжина черги `Q` обмежується величиною `K`. У разі переповнення черги запити починають відкидатися з ймовірністю переповнення `P_drop`:

```
P_drop = (1 - U) · U^K / (1 - U^(K+1))   [ймовірність відкидання у черзі M/M/1/K]
```

Сукупна ймовірність того, що запит не поверне успішну відповідь у межах таймауту `P_retry(L)`, є сумою ймовірності спрацьовування таймауту та ймовірності відкидання у черзі:

```
P_retry(L) = 1 - (1 - P_drop) · exp(-T_timeout / T(L))
```

Сукупне внутрішнє навантаження `W(L)`, з урахуванням первинних запитів та повторних спроб, визначається самоузгодженим рівнянням:

```
W(L) = L · (1 + r · P_retry(L) + r² · (P_retry(L))² + ...)
= L / (1 - r · P_retry(L))           [сума нескінченної геометричної прогресії повторів при r · P_retry < 1]
```

Підставляючи вираз для ймовірності повтору `P_retry(L)`, отримуємо нелінійне рівняння внутрішнього навантаження:

```
W(L) = L / (1 - r · (1 - exp(-T_timeout · (1 - W(L) / C) / T_base)))
```

Цікавим є поведінковий розклад цього рівняння. Коли завантаження невелике (`W(L) << C`), затримка близька до базової `T(L) ≈ T_base << T_timeout`, тому ймовірність повтору `P_retry ≈ 0`, і внутрішнє навантаження дорівнює вхідному: `W(L) = L`.

Проте коли вхідне навантаження `L` наближається до спроможності `C`, затримка стрімко зростає. Коли `T(L) > T_timeout`, ймовірність повтору `P_retry` прямує до `1`. Рівняння набуває граничного значення:

```
W_amplified = L / (1 - r)            [граничне підсилення роботи під час повного шторму повторів]
```

Якщо коефіцієнт повтору `r = 0.8` (80% клієнтів роблять ретраї), внутрішнє навантаження зростає у `5` разів: `W_amplified = 5 · L`. Якщо вхідний потік становив `C` (100% спроможності), система отримує внутрішній потік `5 · C`, який перевищує фізичну межу в 5 разів!

## Фазовий перехід та точка біфуркації

Для визначення точки зриву системи побудуємо залежність внутрішнього навантаження `W` від вхідного навантаження `L`. Рівняння `W(L)` має дві стабільні гілки розв'язків та одну нестабільну гілку, що утворює класичну S-подібну криву біфуркації.

Динаміку зміни довжини черги `Q(t)` можна описати диференціальним рівнянням масового обслуговування:

```
dQ/dt = W(L) - C                      [динаміка накопичення черги]
```

Якщо `W(L) <= C`, черга залишається обмеженою (`dQ/dt <= 0`), і система стабільна. Якщо `W(L) > C`, черга зростає лінійно у часі (`dQ/dt > 0`), що викликає неминуче виснаження пам'яті (OOM) або масовий Head-of-Line drop.

Нижня гілка відповідає нормальному робочому режиму, де затримка мала, а повторні спроби майже відсутні. Верхня гілка відповідає метастабільному стану відмови, де затримки перевищують таймаут, а черги запитів вичерпують усю оперативну пам'ять.

Критична точка зриву `L_crit` наступає тоді, коли вхідний потік досягає значення, за якого затримка в нижній гілці починає відчутно наближатися до клієнтського таймауту:

```
L_crit = C · (1 - T_base / T_timeout)   [поріг, за яким стабільний розв'язок зникає]
```

Обчислимо числові значення для типової високонавантаженої системи:
- Фізична спроможність сервісу `C = 10 000` r/s.
- Базова затримка обробки `T_base = 20` ms.
- Клієнтський таймаут `T_timeout = 200` ms.
- Коефіцієнт повторних спроб `r = 0.9` (90% клієнтів повторюють запит).

Обчислимо критичну точку зриву `L_crit`:

```
L_crit = 10000 · (1 - 20 / 200)       [підстановка базових параметрів]
= 10000 · (1 - 0.10)                 [обчислення відношення затримок]
= 9000 r/s                           [критичний поріг вхідного трафіку]
```

Як тільки вхідний трафік `L` перевищує `9000` r/s (навіть не досягаючи номінальних 10 000 r/s!), затримка зростає до рівня `T_timeout / 2`. Ймовірність повторів досягає критичної позначки, і система здійснює фазовий перехід з нижньої (стабільної) гілки на верхню (метастабільну) гілку відмови.

На верхній гілці завантаження становить `W(L) = 9000 / (1 - 0.9) = 90 000` r/s, що у 9 разів перевищує спроможність `C = 10 000` r/s.

## Гістерезис продуктивності та поріг відновлення L_rec

Головна пастка метастабільного стану полягає в тому, що після повернення вхідного навантаження `L` з `9500` r/s назад до нормального значення `8000` r/s система **не повертається** на стабільну гілку!

На верхній гілці затримки залишаються високими (`T(L) >> T_timeout`), тому ймовірність повтору `P_retry` залишається близькою до `1`. Навіть при `L = 8000` r/s внутрішнє навантаження залишається рівним:

```
W_upper(8000) = 8000 / (1 - 0.9) = 80 000 r/s >> C = 10 000 r/s
```

Система залишається під 100% завантаженням, а клієнти отримують 100% помилок за таймаутом.

Щоб змусити систему зіскочити з верхньої метастабільної гілки назад на нижню стабільну гілку, вхідне навантаження потрібно знизити до порогу відновлення `L_rec`, де верхня гілка втрачає стійкість:

```
L_rec = C · (1 - r)                   [поріг скидання трафіку для виходу з метастабільності]
```

Для нашого числового прикладу обчислимо `L_rec`:

```
L_rec = 10000 · (1 - 0.9)             [підстановка параметрів]
= 10000 · 0.10                        [множення на фактор загасання]
= 1000 r/s                            [поріг відновлення]
```

Це означає, що для виведення системи з колапсу інженерам необхідно штучно скинути вхідний трафік з 8000 r/s до **1000 r/s** (тобто зрізати 87.5% трафіку!) й утримувати його на цьому рівні протягом часу, необхідного для розвантаження внутрішніх черг.

Фізична природа гістерезису полягає у тому, що система «пам'ятає» свій попередній стан через накопичені у чергах запити. Необхідно повністю спустошити внутрішні буфери та черги з'єднань, перш ніж система відновить здатність обробляти звичайний потік.

## Закон Літтла та математика багатоярусних пулів з'єднань

Голодування пулів з'єднань під час метастабільної відмови виражається Законом Літтла для каскадних систем масового обслуговування.

Нехай `N_sys` — середня кількість активних з'єднань у пулі між API Gateway та базою даних, `λ` — інтенсивність оброблюваного потоку запитів, а `W_res` — середній час утримання з'єднання (latency операції):

```
N_sys = λ · W_res                      [Закон Літтла для пулу з'єднань]
```

У багатоярусній архітектурі (Ingress Gateway → Service A → Service B → Database) Закон Літтла діє мультиплікативно. Якщо затримка бази даних зростає на величину `ΔW_db`, затримка вищих шарів зростає адитивно:

```
W_gateway = W_local + W_serviceA + W_serviceB + ΔW_db
```

Обчислимо необхідні пули з'єднань на усіх ярусах під час нормального режиму та під час деградації:

У нормальному режимі:
- `λ = 5 000` r/s.
- `W_db = 0.010` s (10 ms затримка SQL-запиту).
- `W_gateway = 0.025` s (25 ms загальна затримка).
- Необхідний розмір пулу до DB: `N_db = 5000 · 0.010 = 50` з'єднань.
- Необхідний розмір пулу Gateway: `N_gw = 5000 · 0.025 = 125` воркерів.

Під час метастабільного зриву затримка бази даних зростає через блокування або виснаження I/O з 10 ms до 2000 ms (`W_db = 2.0` s). Обчислимо необхідну кількість з'єднань для збереження тієї ж пропускної здатності `λ = 5000` r/s:

```
N_required_db = 5000 · 2.0 = 10 000 з'єднань
N_required_gw = 5000 · (0.015 + 2.0) = 10 075 воркерів
```

Оскільки максимальний фізичний розмір пулу обмежений конфігурацією (`N_max_db = 100`), реальна пропускна здатність системи падає пропорційно зростанню затримки:

```
λ_actual = N_max_db / W_db            [деградація пропускної здатності]
= 100 / 2.0                           [підстановка нових затримок]
= 50 r/s                              [реальна спроможність обробки]
```

Пропускна здатність падає з `5000` r/s до `50` r/s (у 100 разів!). Усі 200 воркерів API Gateway блокуються в очікуванні вільного з'єднання з пулу. Час очікування у черзі пулу `T_wait` описується формулою:

```
T_wait = (N_queue / N_max_db) · W_db [час очікування у черзі пулу з'єднань]
```

При черзі в `1000` очікуючих запитів час чекання досягає `(1000 / 100) · 2.0 = 20` секунд, що гарантовано викликає таймаути вищого рівня на усіх вхідних балансувальниках.

## Математичне обґрунтування Retry Budget та Token Bucket

Для математичного розриву замкненої петлі підсилення `W(L)` вводиться обмеження на сукупну частку повторних спроб — **Retry Budget**.

Нехай `B` — баланс токенів у Token Bucket алгоритмі клієнтських повторів. Кожен успішний первинний запит додає у кошик `k` токенів (наприклад, `k = 0.1`), а кожен повторний запит списує `1` токен. Якщо `B = 0`, повторний запит забороняється, і клієнту повертається негайна помилка.

Це обмежує максимальну частку повторних запитів у сукупному трафіку величиною `r_max = k / (1 + k)`.

Для `k = 0.1` максимальна частка повторів становить:

```
r_max = 0.1 / (1 + 0.1) = 0.0909 (9.09%)
```

Максимальне внутрішнє підсилення роботи під час метастабільного збою обмежується величиною:

```
W_bounded = L / (1 - r_max)           [граничне підсилення під захистом Retry Budget]
= L / (1 - 0.0909)                    [підстановка максимальної частки повторів]
= 1.10 · L                            [підсилення не перевищує 10%]
```

Завдяки введенню Retry Budget внутрішнє навантаження `W(L)` зростає максимум на 10% замість 900%, що робить фазовий перехід у метастабільний стан фізично неможливим навіть під час найсильнішого зовнішнього тригера.
