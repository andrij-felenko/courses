# 📋 Специфікація контрактів скидання навантаження та готовності вузлів

Цей довідник містить повний опис протокольних контрактів, HTTP-заголовків, статус-кодів gRPC, конфігураційних схем пулів з'єднань, параметрів ядра Linux (sysctl), CLI-прапорців та специфікацій Health Check / Readiness Probe, які використовуються для узгодженої взаємодії між Ingress-балансувальниками, API Gateway, мікросервісами та мобільними клієнтами під час запобігання метастабільним відмовам.

Формування чітких протокольних контрактів між компонентами високонавантаженої системи є вирішальним фактором зупинки каскадних відмов. Коли сервіс починає деградувати, він не має права просто мовчки ігнорувати запити або повертати узагальнену помилку без інструкцій щодо повтору. Клієнти, які не отримують вказівок про затримку `Retry-After`, починають повторювати запити з високою частотою, перетворюючи звичайне локальне уповільнення на глобальний шторм повторів (Retry Storm). Стандартизований контракт дозволяє клієнтським бібліотекам та балансувальникам автоматично знижувати інтенсивність потоку до безпечного рівня.

## HTTP-заголовки скидання навантаження та управління повторами

Під час адаптивного скидання навантаження (Load Shedding) або спрацьовування автоматичного вимикача (Circuit Breaker) API Gateway або мікросервіс повинен повертати чіткі стандартизовані заголовки у відповіді HTTP 429 Too Many Requests або 503 Service Unavailable, щоб запобігти неузгодженим ретраям клієнта.

Заголовки відповіді несуть критичну інформацію про поточний стан інфраструктури. Коли вхідна брама зрізає надлишок трафіку, вона використовує заголовок `Retry-After`, який підтримується більшістю стандартизованих HTTP-клієнтів. Це запобігає повторним спробам до завершення вказаного інтервалу. Додаткові заголовки серії `X-LoadShed-*` надають телеметричну деталізацію для моніторингу та налагодження.

### Детальний опис заголовків відповіді (Response Headers)

- `Retry-After: <seconds | http-date>`  
  Обов'язковий заголовок специфікації RFC 7231. Вказує клієнту точний мінімальний інтервал у секундах (наприклад, `Retry-After: 5`), протягом якого заборонено надсилати повторні запити цього типу. Для високонавантажених API рекомендовано повертати значення у діапазоні від 3 до 15 секунд залежно від поточної глибини черги обробника.
- `X-LoadShed-Reason: <concurrency_limit | queue_timeout | cpu_exhaustion | circuit_open>`  
  Вказує системну причину скидання навантаження. Використовується для діагностики у клієнтських SDK, мобільних застосунках та на балансувальнику. Дозволяє відокремити локальне обмеження швидкості від колапсу обчислювальних ресурсів backend-кластера.
- `X-Retry-Budget-Remaining: <percentage | count>`  
  Передає поточний залишок токенів у клієнтському кошику повторів (наприклад, `X-Retry-Budget-Remaining: 8.5%`). Повертається для того, щоб клієнтський SDK міг завчасно призупинити фонові повторні спроби до вичерпання глобального ліміту.
- `X-Degradation-Level: <none | partial_read_only | fallback_cached>`  
  Повідомляє мобільний застосунок про те, що сервіс працює у режимі деградації (наприклад, віддає кешований стан без гарантії свіжості). Це дозволяє графічному інтерфейсу показати відповідний індикатор користувачеві замість помилки завантаження.

### Приклад HTTP 503 відповіді при скиданні навантаження

Приклад структурованого об'єкта відповіді при скиданні навантаження на рівні API Gateway:

```http
HTTP/1.1 503 Service Unavailable
Date: Tue, 18 Aug 2026 09:30:00 GMT
Content-Type: application/json; charset=utf-8
Content-Length: 148
Retry-After: 5
X-LoadShed-Reason: queue_timeout
X-Degradation-Level: fallback_cached
Connection: close

{
  "error": {
    "code": "LOAD_SHEDDING_REJECT",
    "message": "Service is under heavy load. Please retry after delay.",
    "retry_after_seconds": 5
  }
}
```

## gRPC Статус-коди та метадані помилок

У внутрішньокластерній взаємодії між мікросервісами за протоколом gRPC скидання навантаження та виснаження пулів з'єднань транслюються через спеціалізовані статус-коди з долученням структурованих метаданих (gRPC Rich Error Model).

Правильний вибір статусу gRPC є принциповим для поведінки балансувальника (gRPC Load Balancer / Envoy). Наприклад, статус `UNAVAILABLE` свідчить про те, що даний конкретний екземпляр не може виконати обробку (Circuit Breaker відчинено), і балансувальник може прозоро перенаправити запит на інший екземпляр. Натомість статус `RESOURCE_EXHAUSTED` означає глобальне перевантаження підсистеми, тому перенаправлення на сусідній вузол заборонено, оскільки це спричинить каскадний колапс всього кластера.

### Карта статус-кодів стійкості

| gRPC Статус | Назва статусу | Сценарій використання | Рекомендована дія клієнта |
| :--- | :--- | :--- | :--- |
| `14` | `UNAVAILABLE` | Спрацював Circuit Breaker або вузол переходить у стан Drain | Повторити запит до ІНШОГО вузла з використанням Full Jitter |
| `8` | `RESOURCE_EXHAUSTED` | Переповнено семафор Bulkhead або виснажено пул з'єднань | Спинити ретраї, зменшити конрадіус, чекати `Retry-After` |
| `4` | `DEADLINE_EXCEEDED` | Запит вилетів за таймаут у черзі обробника | Анулювати контекст, НЕ повторювати якщо час вичерпано |
| `10` | `ABORTED` | Запит анульовано через конфлікт контенції | Повторити запит після короткої паузи |

### Специфікація Protobuf метаданих помилки (`RetryInfo`)

Для передачі інструкцій повтору gRPC використовує стандартне повідомлення `google.rpc.RetryInfo`. Долучення цього бінарного об'єкта у заголовок `grpc-status-details-bin` дозволяє клієнтському gRPC-інтерцептору розпарсити затримку й застосувати асинхронний таймер без аналізу текстового опису помилки.

```protobuf
syntax = "proto3";
package google.rpc;

import "google/protobuf/duration.proto";

message RetryInfo {
  // Мінімальна пауза, яку клієнт повинен витримати перед наступною спробою
  google.protobuf.Duration retry_delay = 1;
}

message Help {
  message Link {
    string description = 1;
    string url = 2;
  }
  repeated Link links = 1;
}
```

## Налаштування параметрів ядра Linux (sysctl) для мережевого стека

Під час перевантаження мережевий стек ядра Linux може ставати першим вузьким місцем, де скидаються TCP-пакети та втрачаються рукостискання. Нижче наведено нормативну конфігурацію `/etc/sysctl.d/99-resilience.conf` для сервісних вузлів API Gateway:

- `net.core.somaxconn = 8192` — Максимальна довжина черги нерозпарсених сокетів `listen()` (захист від SYN Flood та переповнення черги рукостискання).
- `net.ipv4.tcp_max_syn_backlog = 8192` — Максимальна кількість незавершених TCP-рукостискань у стані `SYN_RECV`.
- `net.core.netdev_max_backlog = 16384` — Максимальна кількість пакетів у черзі мережевої карти перед передачею в протокольний стек.
- `net.ipv4.tcp_tw_reuse = 1` — Безпечне повторне використання сокетів у стані `TIME_WAIT` для вихідних з'єднань (захист від виснаження ефемерних портів).
- `net.ipv4.tcp_fin_timeout = 15` — Зменшення часу перебування сокета у стані `FIN-WAIT-2` з 60 до 15 секунд.

## Специфікація CLI-прапорців утиліти Resilience Proxy

Для локального тестування стійкості у середовищі Chaos Engineering застосовується проксі-утиліта `resilience-proxy`. Нижче наведено специфікацію CLI-параметрів керування:

- `--max-concurrency=<int>` — Встановлює граничну кількість паралельних з'єднань (Bulkhead). За замовчуванням: `200`.
- `--codel-target-ms=<int>` — Цільова затримка черги CoDel у мілісекундах. За замовчуванням: `5`.
- `--codel-interval-ms=<int>` — Вікно оцінки затримки CoDel у мілісекундах. За замовчуванням: `100`.
- `--cb-failure-threshold=<int>` — Кількість помилок для спрацьовування Circuit Breaker. За замовчуванням: `10`.
- `--cb-cooldown-ms=<int>` — Тривалість перебування у стані `OPEN`. За замовчуванням: `10000`.
- `--retry-budget-ratio=<float>` — Максимально дозволена частка повторів (наприклад, `0.10` для 10%).

## Специфікація контракту Readiness Probe для Kubernetes / LB

Однією з найпоширеніших помилок під час відновлення після збою є спрощений індикатор готовності (Readiness Probe), який перевіряє лише відкриття TCP-порту. Під час метастабільної відмови новий екземпляр сервісу вже відкриває TCP-порт, але його внутрішній кеш ще порожній, а пул з'єднань до бази даних перевантажений.

Якщо балансувальник почне спрямовувати 100% робочого трафіку на такий «холодний» вузол, це викличе миттєвий сплеск затримок і знову повалить екземпляр. Контракт правильного ендпойнта `GET /health/ready` повинен оцінювати **факт реальної пропускної спроможності**, а не лише факт запуску ОС або мережевого сокета.

Сервіс повинен вертати HTTP status `200 OK` лише тоді, коли всі внутрішні ресурси відповідають нормативним показникам затримки. Якщо хоча б один із критичних індикаторів перевищує поріг, сервіс повертає `503 Service Unavailable`, сигналізуючи Kubernetes Kubelet або NGINX про необхідність тимчасово виключити вузол із таблиці роутингу.

### Таблиця критеріїв статусу готовності

| Перевіряємий індикатор | Порогове значення для `200 OK` | Статус при порушенні порогу | Наслідок для балансувальника |
| :--- | :--- | :--- | :--- |
| **CPU Utilization** | `< 90%` протягом останніх 5с | `503 Service Unavailable` | Вилучення вузла з балансування (No Ingress Traffic) |
| **DB Connection Pool** | `< 95%` зайнятих з'єднань | `503 Service Unavailable` | Тимчасовий Drain вузла до звільнення пулу |
| **Local Cache Warmup** | `>= 80%` критичних ключів завантажено | `503 Service Unavailable` | Запобігання кеш-шторму при холодній стадії |
| **Active Queue Latency** | `P99 < 500 ms` | `503 Service Unavailable` | Запобігання нарощуванню черги у збоєному вузлі |

### Приклад конфігурації Kubernetes Readiness Probe

Нижче наведено маніфест конфігурації Readiness Probe для Pod у Kubernetes, який налаштований на регулярне опитування стану пропускної здатності:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
    httpHeaders:
      - name: X-Probe-Source
        value: kubelet
  initialDelaySeconds: 15
  periodSeconds: 5
  timeoutSeconds: 2
  successThreshold: 2
  failureThreshold: 2
```

## Конфігураційний контракт пулу з'єднань та таймаутів

Параметризація пулів з'єднань має гарантувати захист від голодування потоків за Законом Літтла. Якщо конфігурація пулу містить занадто велику кількість з'єднань, сервіс виснажить ресурси бази даних. Якщо ж пул занадто малий, воркери вилаштуються у довгу чергу очікування, викликаючи таймаути вищого рівня.

Наведена нижче конфігураційна схема об'єднує параметри пулу з'єднань, налаштування Circuit Breaker та ліміти адаптивного скидання навантаження в єдиний декларативний документ.

### Конфігураційний документ (YAML)

```yaml
resilience_policy:
  connection_pool:
    max_connections: 50            # Максимальна кількість сокетів до DB
    min_idle_connections: 10       # Підтримувана кількість гарячих з'єднань
    max_wait_timeout_ms: 100       # Максимальне чекання вільного з'єднання у черзі
    idle_timeout_ms: 30000         # Час життя неактивного з'єднання
    connection_warmup_rate: 5      # Максимум 5 нових з'єднань на секунду (захист DB)

  circuit_breaker:
    failure_rate_threshold: 50.0   # Повідомляти про відкриття при 50% помилок
    slow_call_rate_threshold: 75.0 # Повідомляти при 75% повільних запитів
    slow_call_duration_ms: 1000    # Запит вважається повільним після 1000 ms
    sliding_window_size: 100       # Розмір вікна оцінки (останні 100 запитів)
    minimum_number_of_calls: 20    # Мінімальна кількість викликів для розрахунку
    wait_duration_in_open_state_ms: 10000 # Час перебування у стані OPEN (10s)

  load_shedder:
    max_concurrent_requests: 200   # Жорсткий Bulkhead паралелізму
    queue_capacity: 50             # Гранична глибина внутрішньої черги
    max_queue_latency_ms: 200      # Максимальне чекання у черзі перед відкиданням
```

## Телеметричні метрики та правила тривог (Alerting Rules)

Для завчасного виявлення появи самопідтримуваної петлі підсилення `W(L) > 1` у розрізі Prometheus / OpenTelemetry збираються спеціалізовані метрики. Головним завданням систем моніторингу є розрахунок коефіцієнта підсилення роботи у реальному часі.

### Правила тривог Prometheus (PromQL)

```yaml
groups:
  - name: metastable_protection
    rules:
      - alert: WorkAmplificationSpike
        expr: (sum(rate(http_requests_total[1m])) by (service)) / (sum(rate(ingress_http_requests_total[1m])) by (service)) > 1.3
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "High work amplification ratio on {{ $labels.service }}"
          description: "Internal requests exceed incoming traffic by >30%. System is entering metastable state."

      - alert: ConnectionPoolStarvation
        expr: histogram_quantile(0.99, sum(rate(connection_pool_wait_duration_seconds_bucket[1m])) by (le, service)) > 0.1
        for: 1m
        labels:
          severity: warning
        annotations:
          summary: "Connection pool starvation on {{ $labels.service }}"
          description: "P99 wait time for DB connections exceeds 100ms."
```

### Перелік ключових Prometheus-метрики

- `http_requests_load_shed_total{reason="..."}` — Лічильник скинутих запитів на вхідній брамі. Зростання цього показника свідчить про активну роботу адаптивного відсікання трафіку.
- `circuit_breaker_state{name="...", state="open|closed|half_open"}` — Поточний стан автоматичного вимикача. Дозволяє візуалізувати розмикання ланцюгів у графу мікросервісів.
- `connection_pool_wait_duration_seconds_bucket` — Гістограма часу чекання з'єднання з пулу. Зсув P99 квантиля праворуч є першим індикатором майбутнього голодування потоків.
- `work_amplification_ratio` — Відношення сукупної кількості внутрішніх викликів до первинних вхідних HTTP-запитів (`W / L`). Якщо значення перевищує `1.2`, система автоматично генерує аларм високого пріоритету (Critical Alert).
