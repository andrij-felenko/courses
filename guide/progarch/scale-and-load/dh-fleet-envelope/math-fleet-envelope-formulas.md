# 🧮 Математика оцінки ємності: від Закону Літтла до буферів IOPS

У цій вставці викладено математичний апарат, який лежить в основі розрахунків навантаження розподілених систем (Envelope Calculation). Тут розібрано математичні виведення для обчислення обсягу оперативної пам'яті TCP-сесій, пропускної здатності мережі, CPU-бюджету TLS-хендшейків, моделей теорії масового обслуговування (Закон Літтла, M/M/c та M/D/1 черги) та коефіцієнтів агрегації дискового WAL.

## 1. Закон Літтла та теорія масового обслуговування черги Gateway

Фундаментом оцінки кількості одночасних з'єднань та елементів у системі обробки є Закон Літтла (Little's Law). Цей закон є одним із небагатьох абсолютних інваріантів у комп'ютерних науках: він справджується для будь-якої системи масового обслуговування незалежно від розпроділу часу прибуття та дисципліни черги.

Закон Літтла пов'язує середню кількість елементів у системі `L`, середню інтенсивність вхідного потоку `λ` (повідомлень або запитів за секунду) та середній час перебування елемента у системі `W` (latency):

```
L = λ · W
```

Для інженера розподілених систем Закон Літтла є головним інструментом оцінки розміру буферів оперативної пам'яті. Якщо вхідний потік повідомлень від 200 000 пристроїв у піковому режимі становить 20 000 повідомлень на секунду (`λ = 20 000 msg/s`), а середня тривалість обробки одного евенту воркером шлюзу дорівнює 15 мілісекундам (`W = 0.015 s`), то середня кількість повідомлень, які одночасно знаходяться в операційній пам'яті шлюзу у стадії обробки, дорівнює: `L = 20 000 · 0.015 = 300 msg`.

Проте під час деградації суміжних сервісів (наприклад, уповільнення відповіді бази даних або накопичення затримок у черзі Kafka) час перебування повідомлення в пам'яті шлюзу `W` зростає від 15 мілісекунд до 3 секунд. За Законом Літтла кількість повідомлень у черзі пам'яті негайно роздувається до: `L_degraded = 20 000 · 3.0 = 60 000 msg`. 

Якщо розмір буфера шлюзу не був заздалегідь розрахований під такий роздув, процес упадає за помилкою Out-Of-Memory (OOM).

### Модель черги M/D/1 та математична оцінка лавиноподібної затримки

Оскільки час парсингу та відправки повідомлення вхідним шлюзом є детермінованим (`D`), обробка описується моделлю черги M/D/1 (детермінований час обробки, пуассонівський вхідний потік).

Формула середнього часу очікування в черзі `W_q` за теорією Поллачека-Хінчина (Pollaczek-Khinchine formula) має вигляд:

```
W_q = (ρ / (2 · μ · (1 - ρ)))
```

Де `μ` — максимальна пропускна здатність одного воркера (msg/s), а `ρ = λ / μ` — рівень завантаження системи (utilization factor).

Розглянемо, як змінюється час очікування в черзі при зміні рівня завантаження шлюзу з максимальною спроможністю воркера `μ = 25 000 msg/s`.

При завантаженні системи на 80% (`λ = 20 000 msg/s`, `ρ = 0.80`) середній час очікування повідомлення в черзі становить лише 0.08 мілісекунди (`0.00008 s`). Система працює практично миттєво.

Якщо вхідний потік зростає до 24 000 повідомлень на секунду і завантаження досягає 96% (`ρ = 0.96`), час очікування в черзі зростає у 6 разів і становить 0.48 мілісекунди.

При наближенні завантаження до 99% (`ρ = 0.99`, `λ = 24 750 msg/s`) час очікування вибухає до 1.98 мілісекунди (зростання у 25 разів порівняно з 80% завантаженням!).

Головний математичний висновок з моделі M/D/1 полягає в тому, що затримка очікування в черзі зростає за гіперболічною кривою `1 / (1 - ρ)`. Наближення завантаження до 100% призводить до нескінченної черги та колапсу системи. Саме тому інженерне правило envelope-обчислень вимагає проєктувати системи з максимальним розрахунковим завантаженням `ρ ≤ 0.70` (70%).

## 2. Математичне виведення обсягу оперативної пам'яті сокетів

Загальний обсяг оперативної пам'яті, необхідний для утримання `N` відкритих TCP/TLS з'єднань, обчислюється як сума витрат ядра операційної системи та простору користувача.

Формула розрахунку пам'яті:

```
RAM_total = N_conns · (RAM_kernel_rx + RAM_kernel_tx + RAM_tls + RAM_app_state)
```

Проведемо крок за кроком обчислення для `N = 200 000` хабів DH при стандартних налаштуваннях ядра.

Кожен сокет вимагає 8192 байти під буфер прийому ядра Linux (`RAM_kernel_rx`), 8192 байти під буфер передачі ядра (`RAM_kernel_tx`), 16 384 байти під контекст шифрування OpenSSL (`RAM_tls`) та 16 384 байти під стан сесії застосунку (`RAM_app_state`).

Загальний обсяг пам'яті на одну сесію становить: `RAM_session = 8192 + 8192 + 16 384 + 16 384 = 49 152 bytes (48 KB)`.

Для всього флоту з 200 000 пристроїв підсумкова потреба у пам'яті обчислюється як: `RAM_total = 200 000 · 49 152 bytes = 9 830 400 000 bytes = 9.155 GB`.

Додавання коефіцієнта запасу 1.5x на випадок тимчасового розширення буферів сокетів під час мережевих сплесків дає підсумковий бюджет пам'яті: `RAM_budget = 9.155 GB · 1.5 = 13.73 GB RAM`.

## 3. Математика мережевої смуги та BDP (Bandwidth-Delay Product)

Обчислення мережевої смуги вимагає врахування корисної корисного payload та протокольних заголовків усіх рівнів.

Загальний розмір мережевого кадру обчислюється за формулою:

```
Packet_size = Payload + Overhead_TLS + Overhead_TCP + Overhead_IP + Overhead_Ethernet
```

Для корисного payload Protobuf у 500 байтів заголовки додають: 29 байтів (TLS 1.3), 32 байти (TCP з опціями), 20 байтів (IPv4) та 26 байтів (Ethernet II frame overhead). Повний розмір кадру становить 607 байтів.

При піковому потоці 20 000 повідомлень на секунду пропускна здатність у байтах дорівнює: `Throughput_bytes = 20 000 · 607 = 12 140 000 bytes/s (12.14 MB/s)`.

Переведення у мегабіти на секунду: `Throughput_bits = 12.14 MB/s · 8 = 97.12 Mbps`.

### Добуток смуги на затримку (Bandwidth-Delay Product, BDP)

Для оцінки необхідного розміру TCP-вікна повернення підтверджень обчислимо BDP для підключень хабів через мобільний зв'язок 4G/LTE (де затримка RTT становить близько 80 ms):

```
BDP = Bandwidth_per_conn · RTT

Bandwidth_per_conn = (607 bytes / 30 s) = 20.23 bytes/s = 161.8 bps
RTT = 0.080 s

BDP_raw = 20.23 bytes/s · 0.080 s = 1.62 bytes
```

Оскільки BDP одного хаба становить лічені байти, стандартне TCP-вікно в 8 KB повністю перекриває потреби передачі без ризику виникнення паузи через виснаження вікна (Window Exhaustion).

## 4. Бюджет CPU для TLS 1.3 хендшейків

Найважчою обчислювальною операцією на шлюзі є встановлення нового TLS-з'єднання з обміном ключами на основі асиметричної криптографії (ECDHE-RSA або ECDHE-ECDSA).

Формула розрахунку необхідних ядер CPU для процесингу хендшейків:

```
CPU_cores = (N_handshakes_sec · T_handshake_ms) / 1000
```

Проведемо розрахунок для випадку блекауту, коли 100 000 пристроїв повертаються у мережу протягом 60 секунд.

Темп встановлення хендшейків становить: `N_handshakes_sec = 100 000 / 60 s = 1 666.67 handshakes/s`.

При виконанні повного TLS 1.3 хендшейку без відновлення сесії (`T_handshake_full = 0.6 ms`) обчислимо потребу у CPU: `CPU_full = (1 666.67 · 0.6) / 1000 = 1.00 CPU core` (повне завантаження 1 ядра суто під криптографію).

При використанні TLS 1.3 Session Resumption (`T_handshake_resume = 0.05 ms`) потреба в обчислювальних ядрах падає до: `CPU_resume = (1 666.67 · 0.05) / 1000 = 0.083 CPU core` (всього 8.3% від одного ядра).

Математичний висновок: впровадження TLS Session Resumption скорочує обчислювальне навантаження на процесори шлюзу під час шторму реконектів у 12 разів.

## 5. Трансформація IOPS через кільцевий буфер

Якщо записувати кожну подію телеметрії на диск окремою операцією `fsync()`, кількість дискових операцій запису (IOPS) дорівнюватиме кількості вхідних повідомлень (20 000 IOPS).

Математичне перетворення хаотичних поодиноких записів у послідовний Write-Ahead Log (WAL) через кільцевий буфер з вікном скидання `T_flush = 0.1 s` (100 мілісекунд) описується формулами:

```
IOPS_batched = 1 / T_flush = 1 / 0.1 s = 10 IOPS

Flush_size = N_msg_sec · T_flush · Frame_size = 20 000 · 0.1 s · 500 bytes = 1 000 000 bytes (1.0 MB)

Write_throughput = 10 IOPS · 1.0 MB = 10 MB/s
```

Завдяки буферизації в оперативній пам'яті дискова підсистема отримує 10 послідовних записів на секунду замість 20 000 випадкових записів, що знижує навантаження на диск за показником IOPS у 2000 разів.
