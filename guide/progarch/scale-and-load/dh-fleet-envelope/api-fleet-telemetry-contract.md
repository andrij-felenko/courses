# 📋 Контракт та параметри обчислення ємності флоту DH

У цій вставці наведено довідкові таблиці, технічні специфікації, схеми оверхеду протоколів, бюджети пам'яті сокетів, конфігураційні ліміти операційної системи Linux та нормативи спостережуваності для флоту пристроїв Digital Homes. Ці специфікації слугують офіційним контрактом при розрахунку ємності (Envelope Calculation) мережевих шлюзів, сервісів обробки евентів та систем зберігання.

## 1. Специфікація протоколів та інженерний розбір мережевого оверхеду

При проєктуванні мережевого ярусу шлюзу Digital Homes критично важливо розуміти, що жоден пакет не передається мережею у чистому вигляді. Кожен рівень мережевої моделі OSI додає власний заголовок, створюючи каскадний оверхед, який суттєво впливає на загальне мережеве навантаження.

На канальному рівні (L2 Data Link) протокол Ethernet II вимагає 14 байтів для заголовка (MAC-адреси джерела та призначення, а також EtherType 0x0800 для IPv4). До додаткових фізичних витрат належать 4 байти контрольної суми кадру (Frame Check Sequence, FCS), 8 байтів преамбули та синхронізації, а також міжкадровий інтервал (Interpacket Gap). Таким чином, загальні фізичні витрати канального рівня становлять 26 байтів на кожен кадр.

На мережевому рівні (L3 Network) базовий заголовок IPv4 додає 20 байтів. Він містить IP-адреси відправника та отримувача, час життя пакета (TTL), ідентифікатор фрагментації та контрольну суму заголовка. У випадках, коли інфраструктура розгортається у мережах з безальтернативним IPv6-адресуванням, розмір заголовка зростає до 40 байтів, що вимагає додаткового корегування розрахунків смуги.

На транспортному рівні (L4 Transport) заголовок TCP без додаткових опцій займає 20 байтів. Проте для довготривалих з'єднань із високим навантаженням використовуються додаткові опції TCP, такі як розширення вікна (Window Scale) та часові мітки (Timestamps, TSval/TSecr), що збільшує розмір заголовка TCP до 32 байтів.

На захищеному рівні сесії (L5 Security) протокол TLS 1.3 додає заголовок шар записів (Record Layer) розміром 5 байтів (тип контенту, версія протоколу та довжина запису), а також 24 байти для аутентифікаційного тегу сучасної симетричної шифросьюти (AES-128-GCM або ChaCha20-Poly1305). Загальний оверхед TLS становить 29 байтів.

Нарешті, на прикладному рівні (L7 Application) бінарний протокол розмежування кадрів (Framing Protocol) додає 12 байтів, які містять сигнатурні байти (Magic Bytes), варіант довжини Protobuf-пакета, ідентифікатор типу повідомлення та контрольну суму CRC32.

У сумі фіксований протокольний оверхед становить 119 байтів на кожен пакет, що обов'язково враховується при розрахунку пропускної здатності.

### Таблиця структури мережевого оверхеду

| Шар протоколу | Протокол / Заголовок | Розмір (байти) | Функціональне призначення |
| :--- | :--- | :--- | :--- |
| L2 Data Link | Ethernet II Frame Header | 14 | MAC-адреси джерела та призначення, EtherType (0x0800) |
| L2 Data Link | Ethernet FCS & Interframe Gap | 12 | Frame Check Sequence (4B), Preamble (8B), Interpacket Gap |
| L3 Network | IPv4 Header | 20 | IP-адреси, TTL, Type of Service (ToS/DSCP), Header Checksum |
| L3 Network | IPv6 Header (опціонально) | 40 | Вживається у мережах із безальтернативним IPv6-адресуванням |
| L4 Transport | TCP Header | 32 | Порти джерела/призначення, Sequence/ACK, Window Scale, Timestamps |
| L5 Security | TLS 1.3 Record Layer | 29 | ContentType (1B), Protocol Version (2B), Length (2B), Tag/MAC (24B) |
| L7 Application | Framing Header | 12 | Magic Bytes (2B), Protobuf Varint Length (4B), Message Type ID (2B), CRC32 (4B) |

### Аналіз класів повідомлень та відсоткового відношення оверхеду

Вплив оверхеду заголовків суттєво різниться залежно від класу повідомлення. Для малих пакетів серцебиття (Heartbeat Ping), де корисне навантаження становить лише 48 байтів, протокольний оверхед у 119 байтів становить понад 71% від загального розміру кадру (167 байтів). Це демонструє, чому занадто часті пінги є неефективними з точки зору мережевого трафіку.

Для стандартних пакетів телеметрії датчиків (Sensor Delta Telemetry) з розміром Protobuf-пакета у 500 байтів оверхед становить 19.2% від загального кадру (619 байтів). Для великих тривожних евентів (Security State Alert) розміром 1200 байтів оверхед знижується до 9.0%, а для евентів із метаданими відеознімків (Video Snapshot Metadata) розміром 8500 байтів оверхед становить лише 1.4%.

### Порівняльна характеристика класів повідомлень телеметрії

| Клас евенту | Частота відправки | Корисний payload (Protobuf) | Повний кадр із заголовками | Оверхед заголовків (%) |
| :--- | :--- | :--- | :--- | :--- |
| Heartbeat Ping | Кожні 30 с | 48 bytes | 167 bytes | 71.2% |
| Sensor Delta Telemetry | Кожні 30 с | 500 bytes | 619 bytes | 19.2% |
| Security State Alert | За подією (event-driven) | 1 200 bytes | 1 319 bytes | 9.0% |
| Video Snapshot Metadata | За подією (motion detected) | 8 500 bytes | 8 619 bytes | 1.4% |

## 2. Інженерний розбір розподілу оперативної пам'яті на сокет

Утримання 200 000 довготривалих TCP/TLS сесій вимагає ретельного планування оперативної пам'яті на рівні ядра операційної системи Linux та простору користувача (user space).

У ядрі Linux кожне TCP-з'єднання представлене двома основними структурами: `struct socket` та `struct sock`. Вони займають 4096 байтів (4 KB) системної пам'яті. Крім того, ядро виділяє буфери сокета для операцій прийому (`sk_rcvbuf`) та передачі (`sk_sndbuf`). При мінімальних налаштуваннях системних параметрів `net.ipv4.tcp_rmem` та `net.ipv4.tcp_wmem` ці буфери займають по 8192 байти (8 KB) кожен.

У просторі користувача процес шлюзу (наприклад, сервіс на C++ або Go) виділяє структуру стану OpenSSL `SSL*` та кеш сесії, що вимагає близько 4096 байтів (4 KB). Крім того, для виконання шифрування та розшифрування подій OpenSSL використовує кільцеві буфери BIO (Basic I/O), які вимагають близько 12 288 байтів (12 KB).

Нарешті, доменна логіка шлюзу виділяє контекст сесії пристрою (Device Session Context), який містить унікальний ідентифікатор пристрою (UUID), токен доступу JWT, маршрутизаційні таблиці підписок та локальний кеш стану твіна пристрою, що займає близько 16 384 байтів (16 KB).

Загальний базовий бюджет на одну сесію становить 52 480 байтів (52 KB). Для флоту з 200 000 пристроїв це дає сумарну потребу в 9.918 Гігабайтах оперативної пам'яті.

### Структура виділення пам'яті на сокет

| Компонент пам'яті | Розмір у пам'яті | Призначення та рівень системного виділення |
| :--- | :--- | :--- |
| Kernel struct socket / sock | 4 096 bytes (4 KB) | Системні об'єкти сокета ядра Linux у пам'яті ядра |
| Kernel TCP RX Window | 8 192 bytes (8 KB) | `sysctl net.ipv4.tcp_rmem` (буфер прийому ядра) |
| Kernel TCP TX Window | 8 192 bytes (8 KB) | `sysctl net.ipv4.tcp_wmem` (буфер передачі ядра) |
| OpenSSL SSL Struct | 4 096 bytes (4 KB) | Структура `SSL*` та кеш SSL_SESSION |
| OpenSSL Cipher BIO Buffers | 12 288 bytes (12 KB) | Кільцеві буфери шифрування/розшифрування івентів |
| Gateway Device Context | 16 384 bytes (16 KB) | ID пристрою, токен доступу, маршрути, кеш твіна |
| **Разом на сесію** | **53 248 bytes (52 KB)** | **Множиться на кількість пристроїв N** |

## 3. Детальний аналіз налаштувань ядра Linux (`sysctl.conf`)

Для забезпечення стабільної роботи мережевого шлюзу під навантаженням у 200 000 одночасних з'єднань стандартні налаштування операційної системи Linux є непридатними і призводять до відмови у підключенні вже при досягненні 1024 або 4096 сокетів.

Параметр `fs.file-max` визначає системну стелю відкритих файлових дескрипторів для всієї операційної системи. Його значення збільшується з типових 209 715 до 2 097 152, щоб гарантувати, що процес шлюзу та інші системні служби не виснажать файлові дескриптори.

Параметри `net.core.somaxconn` та `net.ipv4.tcp_max_syn_backlog` регулюють глибину черг слухаючого сокета. При масовому встановленні з'єднань (наприклад, під час реконекту після блекауту) стандартна черга у 256 чи 4096 елементів миттєво переповнюється, внаслідок чого ядро починає мовчки скидати нові SYN-пакети. Збільшення цих параметрів до 65 535 дозволяє згладити піки реконектів.

Параметри `net.ipv4.tcp_rmem` та `net.ipv4.tcp_wmem` контролюють розміри буферів прийому та передачі. Налаштування векторів `4096 8192 2097152` встановлює мінімальний розмір буфера у 4 KB, стандартний у 8 KB та максимум у 2 MB, що запобігає надмірному споживанню пам'яті неактивними сокетами.

Параметр `net.ipv4.tcp_tw_reuse` дозволяє ядру безпечно повторно використовувати сокети у стані TIME_WAIT для нових вихідних з'єднань, що запобігає виснаженню локальних портів при високій частоті перепідключень.

| Параметр sysctl | Значення за замовчуванням | Налаштування під 200k сесій | Обґрунтування налаштування |
| :--- | :--- | :--- | :--- |
| `fs.file-max` | 209 715 | 2 097 152 | Загальний ліміт відкритих файлових дескрипторів у системі |
| `net.core.somaxconn` | 4 096 | 65 535 | Глибина черги нерозглядних з'єднань (listen backlog queue) |
| `net.ipv4.tcp_max_syn_backlog` | 256 | 65 535 | Максимальна кількість незавершених SYN-запитів у черзі |
| `net.ipv4.tcp_rmem` | 4096 87380 6291456 | 4096 8192 2097152 | Мінімум, стандарт і максимум буфера прийому сокета (bytes) |
| `net.ipv4.tcp_wmem` | 4096 16384 4194304 | 4096 8192 2097152 | Мінімум, стандарт і максимум буфера передачі сокета (bytes) |

## 4. Специфікація станів з'єднання та таймаутів FSM

Кожне з'єднання домашнього хаба підпорядковується чітким правилам скінченного автомата станів (Connection Finite State Machine). Утримання неактивних або напівзруйнованих з'єднань у пам'яті марно витрачає ресурси, тому шлюз застосовує жорстку сітку таймаутів.

У стані `CONNECTING` пристрій намагається встановити TCP-з'єднання. Якщо відповідь SYN-ACK не надходить протягом 10 секунд, з'єднання розривається і хаб переходить до повторної спроби. У стані `TLS_HANDSHAKE` виконується узгодження ключів шифрування. Якщо асиметрична криптографія не завершується за 5 секунд (наприклад, через CPU Throttling), шлюз відправляє TCP RST і вивільняє виділену пам'ять.

У стаціонарному стані `ESTABLISHED` хаб надсилає Heartbeat Ping кожні 30 секунд. Якщо протягом 90 секунд від хаба не надійшло жодного пакета (стан `KEEPALIVE_WAIT`), шлюз маркує пристрій як `DEGRADED`. Після 300 секунд відсутності зв'язку контекст сесії повністю видаляється з оперативної пам'яті шлюзу, а пристрій отримує статус `Offline`.

### Специфікація таймаутів та дій автомата станів

| Стан FSM | Таймаут виходу | Автоматична дія при досягненні таймауту |
| :--- | :--- | :--- |
| `CONNECTING` | 10 секунд | Закриття SYN-пакета, ретрай з експоненційним запізненням |
| `TLS_HANDSHAKE` | 5 секунд | Анулювання TLS-сесії, скидання сокета (RST), звільнення пам'яті |
| `ESTABLISHED` | 30 секунд | Відправка Heartbeat-пінга від хаба до хмари |
| `KEEPALIVE_WAIT` | 90 секунд | Відсутність даних/пінгів → перехід у degraded стан Offline |
| `DEGRADED` | 300 секунд | Очищення контексту сесії з оперативної пам'яті шлюзу |

## 5. Нормативи спостережуваності та метрики Prometheus

Для забезпечення безперервного контролю відповідності реального навантаження обчисленому envelope-бюджету система моніторингу Prometheus збирає ключові показники продуктивності шлюзу.

Метрика `dh_gateway_active_connections` відстежує кількість активних з'єднань. Якщо це значення перевищує 180 000 на один вузол, система автоматично виставляє попередження про наближення до ліміту оперативної пам'яті.

Метрика `dh_gateway_tls_handshakes_total` вимірює темп встановлення нових TLS-сесій. Перевищення порогу у 3000 хендшейків на секунду вказує на виникнення шторму реконектів і небезпеку CPU Saturation.

Гістограма `dh_gateway_ingress_latency_seconds` фіксує затримку обробки вхідних пакетів. Якщо перцентиль P99 перевищує 50 мілісекунд, це є прямим сигналом про переповнення вхідних черг шлюзу та необхідність горизонтального масштабування.

### Нормативи метрик моніторингу

| Назва метрики Prometheus | Тип метрики | Порогове значення тривоги (Alerting Threshold) |
| :--- | :--- | :--- |
| `dh_gateway_active_connections` | Gauge | `> 180 000` на вузол (наближення до ліміту RAM) |
| `dh_gateway_ingress_bytes_total` | Counter | `> 85 000 000` bytes/s (~680 Mbps) |
| `dh_gateway_tls_handshakes_total` | Counter | `> 3 000` handshakes/s (загроза CPU Saturation) |
| `dh_gateway_ingress_latency_seconds` | Histogram | `P99 > 0.050` s (50 ms queue latency) |
| `dh_wal_write_iops_current` | Gauge | `> 500` IOPS (провал батчингу, диск у небезпеці) |
| `dh_kernel_socket_memory_bytes` | Gauge | `> 12 000 000 000` bytes (~12 GB allocated) |
