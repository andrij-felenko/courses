# 🧮 Математика каскадного кешу: Hit-Rate, латентність і трафік крізь яруси

Для системи управління розумними будинками Digital Homes (DH) швидкість доступу до стану пристроїв визначена не швидкістю накопичувачів бази даних, а ймовірністю того, що запит зріжеться на одному з проміжних ярусів кешування. Коли 500 000 активних будинків генерують 100 000 запитів на секунду для оновлення дашбордів, перегляду списків пристроїв та перевірки давачів, прямому запиту до накопичувача просто не залишається шансів: навіть потужний кластер БД здатний витримати не більше 2 000–5 000 складних SQL/NoSQL запитів читання на секунду без деградації latencies.

Цей математичний розбір виводить математичну модель трирівневої кеш-ієрархії (L3 Edge CDN → L1 Process Memory → L2 Distributed Redis Cluster → Origin DB), розраховує підсумковий коефіцієнт влучань (Overall Hit-Rate), середнє запізнення (Average Read Latency), розподіл запізнень та коефіцієнт посилення навантаження під час кеш-шторму (Stampede Amplification Factor).

## 1. Повна формальна модель трирівневого каскаду

Розглянемо послідовний процес обробки запиту на читання стану дому `GET /api/v1/homes/{home_id}/devices`. Потік запитів інтенсивністю `R_0` (запитів/сек) проходить крізь три яруси кешу перед тим, як дістатися джерела правди (Origin DB):

1. **L3 (Edge CDN):** Географічно наближений до користувача вузол. Приймає потік `R_0`. Влучає з ймовірністю `H_3`. Латентність відповіді `L_3`.
2. **L1 (In-Process Memory):** Оперативна пам'ять вузла API Gateway / Worker. Приймає пропущений з Edge потік `R_3 = R_0 · (1 - H_3)`. Влучає з ймовірністю `H_1`. Латентність відповіді `L_1`.
3. **L2 (Distributed Shared Cache — Redis):** Централізований в-пам'яті кластер. Приймає пропущений з L1 потік `R_1 = R_3 · (1 - H_1)`. Влучає з ймовірністю `H_2`. Латентність відповіді `L_2`.
4. **Origin DB:** База даних (PostgreSQL / ScyllaDB). Приймає підсумковий пропущений потік `R_origin = R_2 = R_1 · (1 - H_2)`. Латентність обробки `L_origin`.

```
R_0 (100k) ──> [ L3 CDN ] ──(miss: R_3)──> [ L1 Memory ] ──(miss: R_1)──> [ L2 Redis ] ──(miss: R_origin)──> [ Origin DB ]
                (H_3, L_3)                   (H_1, L_1)                     (H_2, L_2)                       (L_origin)
```

### Формальне виведення підсумкового Hit-Rate

Запит потрапляє до Origin DB лише тоді, коли він зазнає промаху (Cache Miss) на **усіх трьох** ярусах послідовно.

Ймовірність промаху на окремому ярусі `i` становить `M_i = 1 - H_i`. Оскільки події вимивання або відсутності ключа на кожному ярусі в умові стаціонарного стану є статистично незалежними за умови правильного налаштування TTL, сукупна ймовірність промаху всього каскаду `M_total` виражається добутком ймовірностей промаху на кожному кроці:

```
M_total = M_3 · M_1 · M_2
= (1 - H_3) · (1 - H_1) · (1 - H_2)      [закон добутку незалежних подій]
```

Відповідно, підсумковий коефіцієнт влучань каскаду `H_total` становить:

```
H_total = 1 - M_total
= 1 - (1 - H_3) · (1 - H_1) · (1 - H_2)  [доповнення до повної ймовірності]
```

Розкривши дужки, отримуємо повну формулу каскадного влучання:

```
H_total = H_3 + H_1 · (1 - H_3) + H_2 · (1 - H_3) · (1 - H_1)
```

Кожен доданок цієї суми показує частку запитів, які зупиняються на відповідному ярусі:
- `H_3` — частка запитів, обслугованих на L3 (Edge);
- `H_1 · (1 - H_3)` — частка запитів, обслугованих на L1 (Process Memory);
- `H_2 · (1 - H_3) · (1 - H_1)` — частка запитів, обслугованих на L2 (Redis).

### Числовий розрахунок для Digital Homes

Припустимо наступні реалістичні параметри кешування для списку пристроїв будинку:
- `H_3 = 0.90` (90% запитів зрізає Edge CDN за рахунок Stale-While-Revalidate та локального CDN-покриття);
- `H_1 = 0.80` (80% пропущених CDN запитів є повторними до того самого вузла API й знаходять стан у локальній пам'яті);
- `H_2 = 0.95` (95% пропущених з L1 запитів знаходять гарячий JSON стану у кластері Redis).

Обчислимо сукупний промах `M_total`:

```
M_3 = 1 - 0.90 = 0.10
M_1 = 1 - 0.80 = 0.20
M_2 = 1 - 0.95 = 0.05

M_total = 0.10 · 0.20 · 0.05
= 0.001 (тобто 0.1%)
```

Підсумковий hit-rate системи становить:

```
H_total = 1 - 0.001
= 0.999 (тобто 99.9%)
```

З початкового потоку `R_0 = 100 000` запитів/сек:
- L3 CDN обробляє **90 000 r/s**;
- L1 Memory обробляє **8 000 r/s**;
- L2 Redis обробляє **1 900 r/s**;
- Origin DB отримує лише **100 r/s**.

Навантаження на основне сховище даних зменшилося у **1000 разів** (`1 / M_total = 1 / 0.001 = 1000`).

## 2. Статистичний розподіл нерівномірності трафіку (Закон Зіпфа)

У реальних системах розумного дому популярність будинків та запитів не є рівномірною. Розподіл частоти опитування будинків підпорядковується **закону Зіпфа (Zipf's Law)** з параметром `s ≈ 0.8`.

Ймовірність того, що запит буде спрямовано до `k`-го за популярністю будинку серед `N` активних будинків, виражається формулою:

```
P(k) = (1 / k^s) / ∑_{j=1}^{N} (1 / j^s)
```

За `N = 500 000` та `s = 0.8`:
- Топові **1% будинків** (5 000 найактивніших об'єктів) генерують **52% всього трафіку читання**.
- Топові **10% будинків** (50 000 об'єктів) генерують **84% всього трафіку читання**.

### Вплив закону Зіпфа на розмір L1-кешу

Ця математична властивість визначає необхідний обсяг L1-пам'яті на вузлах API. Щоб покрити 84% усіх потенційних HIT у локальному L1-кеші, вузлу API не потрібно тримати у пам'яті всі 500 000 будинків. Достатньо розмістити LRU-кеш розміром у **10 000 елементів**, що вимагає лише `10 000 · 50 KB ≈ 500 MB` RAM на процес.

Маленький L1-кеш розміром у пів гігабайта забезпечує `H_1 > 0.80` завдяки високій концентрації трафіку за законом Зіпфа.

## 3. Модель математичного очікування латентності (Average Latency)

Латентність відповіді системи `L` є випадковою величиною. Математичне очікування латентності `E[L]` (або `L_avg`) обчислюється як зважена сума запізнень на кожному ярусі, де вагою є частка запитів, що завершилися на цьому ярусі:

```
L_avg = L_3 
        + (1 - H_3) · L_1 
        + (1 - H_3) · (1 - H_1) · L_2 
        + (1 - H_3) · (1 - H_1) · (1 - H_2) · L_origin
```

### Числовий розрахунок середньої латентності

Підставимо типові значення фізичних затримок у мережі та пам'яті для архітектури DH:
- `L_3 = 20 ms` (Edge CDN RTT);
- `L_1 = 0.1 ms` (Process Memory lookup);
- `L_2 = 2.0 ms` (Redis network RTT);
- `L_origin = 50.0 ms` (Database query execution + RTT).

З тими самими значеннями `H_3 = 0.90`, `H_1 = 0.80`, `H_2 = 0.95`:

```
L_avg = 20 + (0.10) · 0.1 + (0.10 · 0.20) · 2.0 + (0.10 · 0.20 · 0.05) · 50.0   [підстановка затримок і промахів]
= 20 + 0.01 + 0.04 + 0.05                                                      [перемноження затримок на ймовірності]
= 20.10 ms                                                                     [сумування внесків усіх ярусів]
```

Середня латентність системи практично дорівнює затримці найпершого Edge-ярусу (`20.10 ms` проти `20.0 ms`), хоча прямий запит до бази даних займає `50 ms` плюс проміжні затримки (`20 + 0.1 + 2 + 50 = 72.1 ms`).

### Обчислення перцентилів p99 та p99.9

Аналіз середнього значення (L_avg) не розкриває хвостів розподілу. Порахуємо перцентилі запізнення:
- **p90 перцентиль:** 90% запитів зупиняються на L3 Edge CDN. Отже, `p90 = 20.0 ms`.
- **p98 перцентиль:** 90% (L3) + 8% (L1) = 98% запитів зупиняються на L1. Отже, `p98 = 20.1 ms`.
- **p99.9 перцентиль:** 99.9% запитів обслуговуються у межах L3+L1+L2. Отже, `p99.9 = 20 + 0.1 + 2.0 = 22.1 ms`.
- **p99.99 перцентиль (найгірший хвіст):** Лише 0.01% запитів пробиваються до Origin DB. Для них `p99.99 = 20 + 0.1 + 2.0 + 50.0 = 72.1 ms`.

Завдяки трирівневому каскаду навіть p99.9 перцентиль затримки системи складає **22.1 ms**.

## 4. Математика кеш-шторму (Stampede Amplification Factor)

Найнебезпечніший випадок у каскадному кешуванні виникає тоді, коли гарячий ключ прострочується за TTL одночасно на всіх ярусах.

Нехай `N_c` — кількість паралельних запитів, що надходять у вузьке часове вікно `Δt` (тривалість виконання запиту до Origin DB `L_origin`).

Якщо в системі **відсутнє** схлопування однакових запитів (Singleflight / Request Coalescing):

```
Q_origin_without_singleflight = N_c
```

Кожен із `N_c` запитів виявляє промах кешу й генерує окремий запит до Origin DB. Посилення навантаження (Stampede Factor `A_stampede`):

```
A_stampede = N_c / 1 = N_c
```

При `N_c = 500` навантаження на базу зростає у 500 разів миттєво.

Якщо в системі **встановлено Singleflight-блоки** на рівні L1 та L2:
Тільки 1-й запит отримує дозвіл на виконання Origin Fetch, отримуючи м'ютекс блокування кеш-ключа `Lock(key)`. Решта `N_c - 1` запитів піддаються блокуванню `Wait(Lock(key))` і підхоплюють результат першого виклику.

```
Q_origin_with_singleflight = 1
A_stampede = 1 / 1 = 1
```

Коефіцієнт посилення шторму знижується до одиниці, ізолюючи Origin DB від колапсу при простроченні кешу.

### Імовірнісне дострокове вимивання (XFetch Algorithm)

Альтернативою м'ютексному блокуванню Singleflight для виключення синхронних сплесків є алгоритм ймовірнісного раннього оновлення кешу (XFetch):

Під час читання об'єкта з кешу обчислюється предикат повернення дострокового промаху:

```
t_now - β · δ · ln(rnd()) > t_expire
```

Де:
- `β > 0` — коефіцієнт агресивності оновлення (зазвичай `β = 1.0`);
- `δ` — обчислена тривалість виконання запиту до Origin DB (`L_origin`);
- `rnd()` — випадкова величина, рівномірно розподілена на інтервалі `(0, 1]`;
- `t_expire` — момент абсолютного прострочення ключа за TTL.

Що ближче поточний час `t_now` до моменту прострочення `t_expire`, то вищою є ймовірність того, що випадковий запит поверне «ранній промах» і асинхронно оновлює кеш до того, як ключ повністю згасне. Це розмазує відновлення кешу за часом і повністю виключає синхронний кеш-шторм.
