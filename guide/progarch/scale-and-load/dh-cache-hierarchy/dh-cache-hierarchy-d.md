Коли платформа Digital Homes розростається до 500 000 активних розумних будинків, у яких понад 10 мільйонів давачів, вимикачів та контролерів постійно оновлюють свій стан, профіль навантаження системи набуває гострої асиметрії. Мобільні застосунки мешканців, настінні сенсорні панелі, автоматичні сценарії та зовнішні інтеграції згенеровують понад 100 000 запитів на секунду на читання поточного стану будинку `GET /api/v1/homes/{id}/devices`. Якщо кожен такий запит проходитиме крізь усі шари застосунку й виконуватиме SQL-запит до основних накопичувачів, кластер бази даних ляже за лічені секунди від вичерпання пулу з'єднань, дискового I/O та контенції блокувань.

Спроба розв'язати цю проблему «в лоб» — шляхом встановлення одного централізованого кеш-сервера Redis перед базою даних — швидко впирається у власні фізичні межі. За навантаження 100 000 r/s мережевий інтерфейс та єдине ядро Redis стають вузьким місцем, десеріалізація великих JSON-структур списків пристроїв спалює CPU API-вузлів, а будь-яка затримка у мережевому RTT додає декілька мілісекунд до кожного запиту користувача. Щоб забезпечити миттєвий відгук інтерфейсу (< 20 ms) і захистити сховище правди, потрібна **багатоярусна кеш-ієрархія** (L1 memory, L2 Redis, L3 CDN/Edge), де кожен ярус зрізає свою частку трафіку, володіє власними правилами свіжості та бере участь у загальній мережі інвалідації.

![Багатоярусна кеш-ієрархія стану розумних будинків DH](/guide/progarch/scale-and-load/dh-cache-hierarchy/img/cache-hierarchy-overview.svg)
*Три яруси кешування (L3 CDN Edge, L1 Process Memory, L2 Redis Cluster) формують захисний бар'єр перед Origin DB, зрізаючи 99.9% трафіку читання та зменшуючи затримку відповіді.*

> 🔧 **Навіщо це.** Кешування в Highload-архітектурі — це не просто «покласти значення в Redis по ключу». Це проєкт координації пам'яті: що ближче дані до обчислення чи клієнта, то менша затримка й дешевше читання, але то важче підтримувати узгодженість при змінах. Побудова трьох ярусів із правильним розподілом TTL, Stale-While-Revalidate та інвалідацією дозволяє системі DH витримувати мільйонний потік читань із нульовим приростом навантаження на основні бази даних.

## Прірва читання розумного дому

Усі об'єкти в системі Digital Homes можна чітко розділити за динамікою їхнього життя та співвідношенням читань до записів (Read-to-Write Ratio):

1. **Конфігурація та список пристроїв (`/homes/{id}/devices`):** Перелік кімнат, підключених реле, термостатів та давачів. Записується рідко (під час парного підключення або перейменування пристрою), але читається при кожному відкритті мобільного застосунку або перемиканні екрана настінної панелі. Співвідношення читань до записів вище за `1000:1`.
2. **Телеметричний стан давачів (`/homes/{id}/telemetry`):** Показання температури, вологості, поточного енергоспоживання. Оновлюються давачами раз на 5–10 секунд або за порогом зміни. Співвідношення читань до записів становить приблизно `10:1`.
3. **Стан безпеки та тривог (`/homes/{id}/security`):** Стан охоронного контуру, герконів дверей та датчиків руху. Вимагає суворої узгодженості (Strict Consistency), оскільки хибне кешування знятої сигналізації створює загрозу фізичній безпеці дому.

Прірва читання виникає тоді, коли сотні тисяч мобільних клієнтів опитують список пристроїв та їхній поточний стан. Якщо кожен обробник API виконує ORM-мапінг, десеріалізує зв'язані таблиці `devices`, `rooms`, `capabilities` і формує JSON-відповідь розміром 50 КБ, система витрачає колосальні ресурси на обчислення одного й того самого результату, який не змінювався останні кілька годин.

Першим кроком до розв'язання цієї проблеми є винесення сформованої відповіді у кеш. Проте де саме має жити цей кеш?

Якщо розмістити кеш лише на рівні бази даних (Query Cache), ми заощадимо дисковий I/O, але витратимо мережевий RTT, CPU бази даних на з'єднання та CPU сервісу на парсинг. Якщо покласти кеш у Redis (L2), ми знімемо навантаження з бази, але впремося в мережу Redis та серіалізацію в API-воркерах. Якщо зберегти JSON у пам'яті самого API-воркера (L1), ми отримаємо нульовий I/O, але зіткнемося з локальним вимиванням та неузгодженістю між десятками вузлів API-кластера. Якщо, нарешті, віддати кеш на географічний край мережі (L3 Edge CDN), клієнт отримає відповідь за 20 мілісекунд, взагалі не доходивши до нашої інфраструктури, але інвалідація на краю вимагатиме спеціальних інструментів.

Справді ефективна архітектура не обирає один з цих рівнів — вона об'єднує їх у каскад, де кожен ярус захищає наступний.

## Анатомія трьох ярусів кеш-ієрархії

Побудуємо багатоярусну кеш-ієрархію для Digital Homes, розібравши пристрої, затримки та відповідальність кожного ярусу.

### L1: Локальна оперативна пам'ять процесу (In-Process Memory)

L1-кеш лежить просто в адресному просторі процесу API Gateway або Microservice Worker (`std::unordered_map` у C++, `Map` у TypeScript чи `dict` у Python).

- **Латентність доступу:** `< 0.1 ms` (наносекунди на пошук у хеш-таблиці та копіювання вказівника).
- **Мережеві витрати:** `0 bytes` I/O, відсутність серіалізації/десеріалізації (якщо об'єкти зберігаються у формі готових структур даних).
- **Обмеження:** Обсяг пам'яті одного вузла (RAM footprint), локальність (кожен з 50 вузлів API має свій власний L1-кеш), ризик прострочення при відсутності синхронізації між вузлами.
- **Стратегія вимивання (Eviction):** Bounded LRU (Least Recently Used) із жорстким обмеженням за кількістю елементів (наприклад, не більше 10 000 найактивніших будинків на вузол) та коротким локальним TTL (5–15 секунд).

### L2: Розподілений спільний кеш (Redis Cluster)

L2-кеш живе у централізованому або шардованому кластері Redis / KeyDB, спільному для всіх горизонтально масштабованих вузлів API.

- **Латентність доступу:** `1–3 ms` (включає локальний RTT усередині дата-центру).
- **Мережеві витрати:** Мережевий трафік між API та Redis, необхідність серіалізації (JSON, Protobuf або MessagePack).
- **Обмеження:** Спроможність мережевих карт Redis-вузлів, пропускна здатність CPU на підключення та серіалізацію.
- **Призначення:** Єдине джерело свіжості для всього backend-кластера. Якщо запит промахується повз локальний L1-кеш API-вузла A, він звертається до L2 Redis і витягує стан, залитий туди хвилину тому API-вузлом B.
- **TTL:** 5–15 хвилин із підтримкою автоматичного відновлення при промаху.

### L3: Край мережі (Edge CDN / Reverse Proxy Cache)

L3-кеш знаходиться на географічно розподілених edge-серверах CDN (Cloudflare, Fastly, NGINX Edge) у безпосередній близькості до мобільних пристроїв та користувачів.

- **Латентність доступу:** `10–30 ms` (RTT останньої милі клієнтської мережі).
- **Мережеві витрати:** Повністю знімає мережевий та обчислювальний трафік із центрів обробки даних DH.
- **Призначення:** Відповідь на HTTP-запити читання `GET` на рівні повністю сформованого заголовка та тіла HTTP-відповіді.
- **Механізм керування:** Заголовки `Cache-Control`, `Surrogate-Control`, `Surrogate-Key` (Cache-Tags) та `stale-while-revalidate`.

## Математика каскадного Hit-Rate та збереження Origin

Головний ефект каскадного кешування полягає у **мультиплікативному зрізанні трафіку**. Ймовірності промаху на окремих ярусах перемножуються, що дає експоненційне падіння кількості запитів, які досягають джерела правди.

Детально [математичну модель каскадного hit-rate та латентності](guide:progarch/scale-and-load/dh-cache-hierarchy/math-cache-hierarchy-rates.md) виведено в окремому матеріалі. Основне рівняння підсумкового промаху каскаду `M_total` виглядає так:

```
M_total = (1 - H_3) · (1 - H_1) · (1 - H_2)
```

Де `H_3`, `H_1`, `H_2` — коефіцієнти влучання на ярусах L3 (CDN), L1 (Memory) та L2 (Redis) відповідно.

![Воронка зрізання трафіку та підсумковий Hit-Rate крізь яруси](/guide/progarch/scale-and-load/dh-cache-hierarchy/img/traffic-funnel-rates.svg)
*Множення ймовірностей влучання на трьох ярусах перетворює потік 100 000 запитів/сек на 100 запитів/сек до бази даних, забезпечуючи сукупний Hit-Rate на рівні 99.9%.*

Якщо L3 CDN зрізає 90% трафіку (`H_3 = 0.90`), з 100 000 запитів/сек до нашого дата-центру доходить лише 10 000 r/s. Якщо L1 Process Memory зрізає 80% пропущеного трафіку (`H_1 = 0.80`), до Redis доходить 2 000 r/s. Якщо L2 Redis зрізає 95% пропущеного з L1 трафіку (`H_2 = 0.95`), до основної бази даних PostgreSQL / ScyllaDB доходить лише **100 запитів на секунду**.

Сукупний Hit-Rate системи виражається як:

```
H_total = 1 - M_total = 1 - (0.10 · 0.20 · 0.05) = 1 - 0.001 = 0.999 (99.9%)
```

Завдяки цьому середня латентність відповіді системи `L_avg` наближається до швидкої латентності Edge CDN:

```
L_avg ≈ L_3 + (1 - H_3) · L_1 + (1 - H_3) · (1 - H_1) · L_2 + M_total · L_origin
= 20 + 0.10 · 0.1 + 0.02 · 2.0 + 0.001 · 50.0   [підстановка числових параметрів затримок і hit-rate]
= 20.10 ms                                       [сумування внесків усіх ярусів]
```

Клієнт отримує середню латентність 20.1 ms замість 72.1 ms, а база даних працює у розслабленому режимі, обробляючи 100 r/s замість 100 000 r/s.

## Проблема когерентності та асинхронна інвалідація

Найскладніший виклик багатоярусного кешування — підтримання свіжості даних. Якщо користувач вимикає світло у вітальні через мобільний застосунок, стан пристрою в базі даних оновлюється миттєво. Але якщо у цей момент L1-кеш API-вузла та L3-кеш CDN продовжують віддавати старий JSON, користувач побачить, що вимикач на екрані повернувся у положення «увімкнено». Це породжує відчуття зламаного інтерфейсу та змушує людину хаотично тиснути кнопку повторно.

Просте очікування завершення TTL (Time-To-Live) тут не працює: якщо зробити TTL надто коротким (1 сек), ми втратимо Hit-Rate на Edge; якщо зробити його довгим (60 сек), ми отримаємо 60 секунд рассинхронізації.

Виходом є **подієво-орієнтована активна інвалідація (Event-Driven Invalidation Fanout)** у поєднанні з м'яким TTL.

![Послідовність інвалідації при оновленні стану пристрою](/guide/progarch/scale-and-load/dh-cache-hierarchy/img/cache-invalidation-fanout.svg)
*При зміні стану пристрою сервіс атомарно оновлює БД та L2 Redis, транслює подію вимивання через Redis Pub/Sub на всі L1-вузли та викликає Edge CDN Purge API за Surrogate-Key.*

Повний ланцюжок оновлення стану (Write Path) влаштований наступним чином:

1. **Запис у базу та L2 Redis:** Сервіс обробляє команду `PUT /devices/dev-42`, оновлює рядок у базі даних і атомарно перезаписує новий JSON у L2 Redis.
2. **Pub/Sub трансляція для L1:** Сервіс публікує коротке повідомлення у глобальний шинний канал Redis Pub/Sub: `PUBLISH dh:invalidation "dh:home:101"`. Усі 50 вузлів API-кластера, підписані на цей канал, миттєво отримують подію й видаляють ключ `dh:home:101` зі своїх локальних L1 `std::unordered_map`.
3. **Purge API для L3 Edge CDN:** Сервіс викликає асинхронний HTTP Purge API мережі CDN, передаючи заголовок `Surrogate-Key: home-101`. Edge-сервери CDN по всьому світу позначають відповідні cached HTTP-відповіді як прострочені (Soft Purge).

Докладно специфікацію заголовків кешування та ендпойнта інвалідації описано в [контракті кеш-заголовків та Edge Purge API](guide:progarch/scale-and-load/dh-cache-hierarchy/api-cache-control-contract.md).

Зверніть увагу: ми використовуємо саме **Soft Purge** (stale-while-revalidate) на Edge. Це означає, що наступний читач не чекатиме повної генерації нового стану з Origin: CDN віддасть йому останню відому копію, але в фоні негайно надішле асинхронний запит оновлення до нашого backend.

## Захист від кеш-шторму (Cache Stampede / Thundering Herd)

Навіть за наявності каскаду кешів виникає критична крайова ситуація — **кеш-шторм (Cache Stampede)**.

Уяви ситуацію: будинок відомого блогера або популярна зона автоматизації містить 100 пристроїв. О 19:00 закінчується TTL ключа кешу `dh:home:777` одночасно на L1, L2 та L3. У цю ж мікросекунду 500 паралельних мобільних застосунків та панелей надсилають запит `GET /homes/777/devices`.

Усі 500 запитів виявляють промах кешу на L3, переходять на L1, виявляють промах на L1, йдуть у L2 Redis, виявляють промах у Redis — і **усі 500 одночасно пробивають систему до Origin DB**. 500 важких SQL-запитів миттєво падають на базу даних, викликаючи стрибок CPU до 100%, вичерпання пулу з'єднань і каскадний колапс API.

![Захист від кеш-шторму за допомогою схлопування запитів (Singleflight)](/guide/progarch/scale-and-load/dh-cache-hierarchy/img/stampede-mitigation.svg)
*Схлопування запитів за допомогою Singleflight-блоки зводить 500 паралельних промахів кешу до одного SQL-запиту, роздаючи отриманий результат усім очікуючим клієнтам.*

Для захисту від кеш-шторму застосовують паттерн **Singleflight (Request Coalescing / Mutex Locking)**.

При виникненні промаху кешу API-вузол не біжить одразу в базу даних. Замість цього він намагається захопити локальний м'ютекс для ключа `dh:home:777`:
- **Перший запит** успішно захоплює м'ютекс і бере на себе борг виконати реальний запит до Origin DB або L2 Redis.
- **Решта 499 запитів**, що надійшли у цей же момент, виявляють, що для ключа `dh:home:777` вже виконується обчислення. Вони не генерують нових SQL-запитів, а підписуються на результат (Future / Promise) першого запиту й блокуються в очікуванні.

Коли перший запит повертає дані з бази даних і записує їх назад у кеш, він розсилає отриманий результат усім 499 очікуючим запитам. База даних виконує **рівно один SQL-запит** замість 500.

Повну [реалізацію трирівневого кешу з Pub/Sub інвалідацією](guide:progarch/scale-and-load/dh-cache-hierarchy/proj-dh-tiered-cache.md) та Singleflight-групою мовами C++ та TypeScript наведено у практичному проєктному файлі теми.

Розглянемо фрагмент коду C++, який ілюструє роботу Singleflight та каскадного читання:

:::tabs
```cpp
// Читання з каскаду L1 -> L2 -> Singleflight(Origin DB)
HomeState TieredCacheManager::getHomeState(
    const std::string& homeId, 
    std::function<HomeState(const std::string&)> originDBFetch
) {
    std::string cacheKey = "dh:home:" + homeId;

    // 1.Перевірка L1 Process Memory (без мережевого I/O)
    {
        std::shared_lock<std::shared_mutex> lock(l1Mutex_);
        auto it = l1Cache_.find(cacheKey);
        if (it != l1Cache_.end()) {
            return it->second; // L1 HIT
        }
    }

    // 2. Перевірка L2 Redis Cluster (мережевий RTT 1-2 ms)
    auto l2Val = redis_->get(cacheKey);
    if (l2Val.has_value()) {
        populateL1(cacheKey, l2Val.value()); // заповнюємо L1 для наступних викликів
        return l2Val.value(); // L2 HIT
    }

    // 3. L1 & L2 MISS: Викликаємо Singleflight для ізоляції Origin DB
    return singleflight_.doCall(cacheKey, [&]() {
        HomeState freshState = originDBFetch(homeId); // 1 SQL-запит на весь кластер
        redis_->set(cacheKey, freshState, std::chrono::seconds(300));
        populateL1(cacheKey, freshState);
        return freshState;
    });
}
```

```ts
async getHomeState(
  homeId: string,
  originDBFetch: (id: string) => Promise<HomeState>
): Promise<HomeState> {
  const cacheKey = `dh:home:${homeId}`;

  // 1. L1 Process Memory Check
  if (this.l1Memory.has(cacheKey)) {
    return this.l1Memory.get(cacheKey)!;
  }

  // 2. L2 Redis Check
  const redisVal = await this.redisClient.get(cacheKey);
  if (redisVal) {
    const parsed = JSON.parse(redisVal) as HomeState;
    this.l1Memory.set(cacheKey, parsed);
    return parsed;
  }

  // 3. Singleflight Coalescing for Origin DB Fetch
  return this.singleflight.doCall(cacheKey, async () => {
    const freshState = await originDBFetch(homeId);
    await this.redisClient.set(cacheKey, JSON.stringify(freshState), "EX", 300);
    this.l1Memory.set(cacheKey, freshState);
    return freshState;
  });
}
```

## Поверхня рішень: Що кешувати на краю, а що ні

Спроба закешувати геть усе на L3 Edge CDN призведе до критичних помилок безпеки та порушення інваріантів системи. Не кожні дані допускають компроміс з евентуальною узгодженістю (Eventual Consistency).

Сформулюємо матрицю рішень для вибору ярусів кешування в Digital Homes:

| Тип даних / Ендпойнт | L1 (Process Memory) | L2 (Redis Cluster) | L3 (Edge CDN) | Стратегія інвалідації |
| :--- | :--- | :--- | :--- | :--- |
| **Список пристроїв дому** (`/homes/{id}/devices`) | Так (TTL 10s, LRU) | Так (TTL 15m) | Так (Surrogate-Key) | Pub/Sub + Edge Purge API при додаванні/видаленні пристрою. |
| **Телеметрія давачів** (`/homes/{id}/telemetry`) | Так (TTL 2s) | Так (TTL 30s) | Ні (або SWR 2s) | Коротка плинність TTL. Інвалідація недоцільна через високий потік events. |
| **Стан охорони та замків** (`/homes/{id}/security`) | Так (TTL 1s, volatile) | Ні (пряме читання) | **ЗАБОРОНЕНО** (`no-store`) | Прямий bypass кешу Edge. Негайне читання з DB/Redis з Pub/Sub evict. |
| **Агрегована аналітика** (`/stats/daily`) | Ні (великий розмір) | Так (TTL 1h) | Так (TTL 1d) | Довгий TTL на Edge, перевизначення при зміні доби. |

Правило просте: **Що вища вартість помилки рассинхронізації даних, то менше ярусів кешування має проходити запит**, і то більше система має покладатися на сувору синхронність читання.

## Спостережність та трасування крізь яруси

У розподіленій багатоярусній системі неможливо діагностувати проблеми запізнення без наскрізного розподіленого трасування (Distributed Tracing).

Запит користувача `GET /api/v1/homes/101/devices` отримує унікальний заголовок трасування `traceparent` (за стандартом W3C Trace Context). Цей заголовок проходить крізь усі три яруси кешування та записується у метрики OpenTelemetry:

1. **Edge CDN Span (`span:edge_l3`):** Записує час перевірки Edge-кешу, статус (`HIT-L3` чи `MISS-L3`) та географічний регіон edge-вузла.
2. **API Gateway Span (`span:gateway_l1`):** Записує затримку локального пошуку в операційній пам'яті processes RAM.
3. **Shared Cache Span (`span:redis_l2`):** Записує мережевий RTT до кластера Redis та розмір десеріалізованого payload.
4. **Database Span (`span:postgres_origin`):** Записує час виконання SQL-запиту, якщо попередні яруси зазнали промаху.

Дашборд спостережності фіксує два ключових показники здоров'я кеш-ієрархії:
- **Cache Hit Ratio per Tier:** Відношення влучань до загальної кількості запитів для L3, L1 та L2 окремо.
- **Cache Degradation Index:** Раптове падіння Hit-Rate на L3 з 90% до 10% свідчить про помилку у Purge API або збій формування заголовків `Surrogate-Key`.

## Аварійні режими та деградація (Failure Modes)

Будь-який ярус кешу може вийти з ладу. Проєктування багатоярусної ієрархії вимагає чітких сценаріїв деградації:

### Сценарій 1: Відмова кластера L2 Redis (Network Split / Redis Down)
Якщо кластер Redis стає недоступним, виклики читання L2 падають за таймаутом. Сервіс вмикає паттерн **Circuit Breaker**: L2-ярус тимчасово виключається з каскаду. Запити промаху L1 спрямовуються напряму до Singleflight-групи Origin DB. Щоб не перевантажити базу даних у цьому режимі, TTL локального L1-кешу у пам'яті тимчасово автоматично збільшується з 10 секунд до 30 секунд.

### Сценарій 2: Відновлення дата-центру та прогрів (Cold Start / Cache Warming)
При відновленні регіону після знеструмлення або запуску нового дата-центру L1 та L2 є повністю порожніми. Пуск користувацького трафіку на холодний кеш призведе до промаху 100% запитів. Для запобігання цьому під час фази розгортання фоновий сервіс **Cache Warmer** вичитує зі сховища перелік 5% найпопулярніших будинків (за законом Зіпфа) і заповнює L2 Redis до моменту перемикання публічного DNS-трафіку.

## Еволюція схем даних у кеші (Cache Schema Evolution)

Коли система розширюється й версія DTO змінюється з `HomeState v1` на `HomeState v2` (наприклад, додається нове поле `battery_level`), у кеші L2 Redis та на Edge CDN одночасно лежать закешовані об'єкти старої та нова версії.

Для відсутності десеріалізаційних винятків під час деплою застосовують два правила:
1. **Конверт версії схеми (Envelope Pattern):** Кешований рядок у Redis зберігається у вигляді конверта:
   ```json
   {
     "schema_version": 2,
     "payload": { "homeId": "101", "devices": [...], "battery_level": 95 }
   }
   ```
2. **Поблажливий читач (Tolerant Reader):** Нові API-вузли під час читання старої `v1` структури з кешу не падають з винятком, а заповнюють відсутні нові поля дефолтними значеннями (`battery_level = null`), доки фонова інвалідація не замінить об'єкт на новий.

## Економічний та інфраструктурний баланс (CAPEX/OPEX Analysis)

Розгортання трирівневої кеш-ієрархії суттєво змінює фінансову структуру витрат на інфраструктуру Digital Homes.

Без L3 Edge-кешування обробка 100 000 r/s вимагає утримання потужного кластера API Gateway (щонайменше 40–50 великих серверних вузлів) та масштабної реплікованої бази даних із великою кількістю RAM для підтримання гарячих даних у томах дискового кешу. Це генерує значні капітальні та операційні витрати на серверне обладнання (CAPEX/OPEX) у внутрішньому дата-центрі.

Впровадження L3 Edge CDN зміщує баланс витрат:
- **Зменшення обчислювальних потужностей backend:** Оскільки 90% запитів зрізаються на Edge, кількість необхідних API-вузлів зменшується з 50 до 10. Навантаження на базу даних падає в 1000 разів, що дозволяє зменшити розмір кластера PostgreSQL / ScyllaDB.
- **Модель оплати за вихідний трафік (CDN Bandwidth Pricing):** Витрати на сервери замінюються платою за смугу пропускання Edge CDN (Egress Data Transfer). Оскільки вартість 1 ГБ вихідного трафіку на Edge постійно знижується, сукупна вартість володіння інфраструктурою (TCO) зменшується на **60–75%** при одночасному зростанні швидкодії для кінцевих користувачів.

## Підсумок

Багатоярусна кеш-ієрархія — це не просто набір незалежних інструментів, а злагоджений оркестр передачі стану.
- **L1 (Process Memory)** дає наносекундний відгук і знімає мережевий I/O з backend-серверів.
- **L2 (Redis Cluster)** виступає спільною точки синхронізації та захищає систему при перезапуску або масштабуванні API-вузлів.
- **L3 (Edge CDN)** зрізає 90% трафіку ще на підході до дата-центру, гарантуючи миттєвий відгук мобільним клієнтам у будь-якій точці світу.
- **Pub/Sub + Edge Purge API** створюють активну шину інвалідації, яка гарантує свіжість даних при змінах.
- **Singleflight** ізолює базу даних від руйнівних кеш-штормів при простроченні гарячих ключів.

Правильно спроєктована кеш-ієрархія перетворює вразливу базу даних на надійне джерело правди, яке обробляє мінімальний, безпечний потік запитів незалежно від того, скільки мільйонів користувачів відкрили застосунок цієї секунди.
