# 📋 Довідник евристик архітектора: правила, тригери та метрики

Цей довідник містить повну порівняльну матрицю, тригери спрацювання, кількісні пороги та чек-лісти п'яти щоденних евристик прийняття рішень для архітекторів програмного забезпечення.

Документ слугує оперативним плейбуком для проведения архітектурних рев'ю, оцінки RFC та формалізації журналів прийняття рішень (ADR). Опираючись на цей довідник, архітектурна команда отримує чіткі критерії розмежування ситуацій, де потрібен глибокий аналіз, і ситуацій, де будь-яка затримка прийняття рішення шкодить бізнесу більше, ніж потенційна помилка. Довідник усуває невизначеність під час обговорень і дає чіткий алгоритм дій під час рефакторингу, вибору стеків чи оптимізації.

```
КРАТКИЙ ПЛЕЙБУК ПРИЙНЯТТЯ РІШЕНЬ (Triage Matrix)
┌─────────────────────────┬─────────────────────────┬───────────────────────────┐
│ Евристика               │ Тригер спрацювання       │ Обов'язкова дія           │
├─────────────────────────┼─────────────────────────┼───────────────────────────┤
│ 1. Reversibility Filter │ Вибір БД / API / Крипто │ Визначити One-Way vs 2-Way│
│ 2. YAGNI Default        │ «А що як у майбутньому» │ Default to NO, зрізати    │
│ 3. Boring Tech Budget   │ Новий інструмент/мова   │ Перевірити жетони (≤ 3)   │
│ 4. Pre-Mortem Audit     │ Великий редеплой/архіт. │ 30-хв сесія відмов        │
│ 5. Measure First        │ Пропозиція оптимізації  │ Вимоги flamegraph/метрики │
└─────────────────────────┴─────────────────────────┴───────────────────────────┘
```

### 1. Зведена таблиця та класифікація п'яти щоденних евристик

Практичне застосування евристик вимагає від архітектора вміння миттєво ідентифікувати тип проблеми за вхідними сигналами. У таблиці нижче зведено ключові характеристики п'яти евристик, їх кількісні індикатори та граничні значення, які задіяні у щоденній інженерній дисципліні.

Кожна евристика адресує конкретне когнітивне або операційне ризикове поле. Перша евристика (фільтр зворотності) керує темпом прийняття рішень; друга (YAGNI) захищає від накопичення передчасної складності; третя (бюджет жетонів) контролює операційний ризик технологічного стеку; четверта (Pre-Mortem) нейтралізує групове засліплення оптимізмом; п'ята (Measure First) блокує створення незапитаних абстракцій під виглядом оптимізації.

| Евристика | Фундаментальне питання | Вхідний тригер | Кількісний поріг спрацювання | Червоний прапорець (Red Flag) | Prescribed Action (Обов'язковий алгоритм дій) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. Reversibility Filter** (Фільтр зворотності) | Скільки коштує відкотити зміну назад при аварії? | Створення баз даних, публічних API, схем зберігання, вибір хмари. | Час відкату > 4 годин або втрата даних = One-Way Door. | «Це стандарт ринку, давайте зробимо так раз і назавжди». | **One-Way:** RFC + Pre-Mortem + ARB approval.<br>**Two-Way:** Негайне делегування розробнику. |
| **2. YAGNI Default** (Принцип неминучої відмови) | Чи існує поточна нагальна потреба бізнесу в цій абстракції? | Пропозиція додати «універсальний шар», додатковий DTO або фабрику. | Потреба з'явиться лише через > 3 місяці або припустиме гіпотетичне навантаження. | «Нам це знадобиться, коли ми виростемо в 100 разів». | Відхилити абстракцію. Написати найпростішу реалізацію сьогодні, закласти шов рефакторингу. |
| **3. Boring Technology Budget** (Бюджет жетонів) | Скільки незвіданого операційного ризику ми додаємо в стек? | Впровадження нової мови, баз даних, кастомних RPC або фреймворків. | Сума інноваційних жетонів у проєкті > 3. | «Ця нова NoSQL БД зараз у тренді на GitHub». | Заборонити новий інструмент. Використати PostgreSQL / Redis / Go / C++ / TypeScript із 10-річною історією. |
| **4. Pre-Mortem Audit** (Передсмертний аналіз) | Що саме знищить цю систему через один рік після деплою? | Затвердження архітектури One-Way Door або міграція ядра системи. | Ризик важкості Severity ≥ 4 за шкалою від 1 до 5. | «Всі розробники підтримують проєкт, проблем не буде». | Провести 30-хвилинну сесію тихого мозкового штурму провалився проєкту. Внести коригування в дизайн. |
| **5. Measure First** (Вимірюй перш ніж оптимізувати) | Де об'єктивні докази того, що тут є пляшкове горло? | Пул-реквест або RFC з міткою «оптимізація продуктивності/пам'яті». | Відсутність бенчмарків або flamegraph профілювання. | «Заміна JSON на Protobuf прискорить систему у 5 разів». | Автоматично відхилити PR у CI. Заборонити оптимізацію до надання метрик з виміряним p99 лаг-фактором. |

### 2. Детальні алгоритми та критерії прийняття рішень

#### 2.1. Алгоритм зворотності рішень (Reversibility Decision Tree)

Оцінка зворотності є першим і найважливішим кроком у процедурі архітектурного триажу. Коли інженер висуває пропозицію про зміну в системі, архітектор не аналізує її технічні переваги доти, доки не пройде кроки алгоритмічного дерева зворотності. Головне завдання цього етапу — відсікти передчасну бюрократію для зворотних дій і зберегти ресурси команди для критичних вузлів.

Головне завдання дерева — відфільтрувати 80% рутинних рішень, які є двосторонніми дверима (Two-Way Doors), і передати їх на рівень автономного виконання розробниками. Лише 20% рішень, які потрапляють під критерії односторонніх дверей (One-Way Doors), направляються на важку процедуру колегіального оцінювання.

```
[НОВА ІНІЦІАТИВА]
       │
       ▼
1. Чи є зміна формату зберігання на диску або деструктивною міграцією БД?
       ├── ТАК ──> [ONE-WAY DOOR]
       └── НІ  ──> ▼
2. Чи міняє це публічний контракт API для зовнішніх клієнтів?
       ├── ТАК ──> [ONE-WAY DOOR]
       └── НІ  ──> ▼
3. Чи вимагає зміна зупинки всього сервісу (Downtime > 15 хв) для відкату?
       ├── ТАК ──> [ONE-WAY DOOR]
       └── НІ  ──> ▼
4. [TWO-WAY DOOR] ──> Делегувати розробнику (Час прийняття < 15 хвилин)
```

##### Глибокий розбір категорій зворотності та часові пороги:

Аналіз зворотності спирається на три вимірювані характеристики: тривалість відкату (*Rollback Duration*), ризик деструктивної втрати даних (*Data Loss Severity*) та вплив на сумісність публічних контрактів (*Contract Compatibility Impact*).

* **Інтервал 1.0 – 0.8 (Висока зворотність):** Зміна повністю ізольована всередині одного модуля або ховається за прапорцем фічі (*Feature Flag*). Відкат виконується зміною конфігурації або викликом `git revert` протягом кількох хвилин без зупинки обробки трафіку та без будь-якої втрати даних. Приклад: зміна внутрішнього алгоритму фільтрації в пам'яті. Регламент: розробник приймає рішення самостійно без скликання мітингів та без попереднього погодження з архітектором.
* **Інтервал 0.7 – 0.4 (Середня зворотність):** Зміна зачіпає внутрішні контракти між двома мікросервісами одного домену або додає нову колонку в таблицю бази даних, що допускає значення `NULL`. Відкат вимагає повторного деплою сервісів протягом 1–2 годин. Приклад: додавання нового опціонального поля у внутрішню чергу подій. Регламент: проведення короткого асинхронного рев'ю в Slack/GitLab тривалістю не більше 1 дня з залученням одного колеги.
* **Інтервал 0.3 – 0.0 (Низька зворотність / One-Way Door):** Зміна змінює фундаментальну топологію баз даних, міняє публічний REST/gRPC контракт для сторонніх інтеграторів або переносить інфраструктуру до іншого хмарного провайдера. Відкат вимагає тижнів ручної міграції даних та узгодження з клієнтами. Приклад: перехід з SQL на NoSQL сховище. Регламент: написання RFC, проведення сесії Pre-Mortem та обов'язковий захист на Architecture Review Board (ARB).

#### 2.2. Бюджет інноваційних жетонів та ліміти складності (Boring Technology Audit)

Впровадження нових технологічних інструментів завжди створює операційний борг, який проявляється під час нічних аварій, коли черговий інженер опиняється наодинці з незнайомою системою. Евристика «нудної технології» вимагає суворого обліку інноваційного ризику за допомогою бюджету жетонів. Кожен експериментальний інструмент розмиває когнітивний фокус команди та ускладнює ротацію спеціалістів.

Кожен проєкт має ліміт у **3.0 інноваційні жетони**. Якщо пропозиція вимагає перевищення цього ліміту, вона відхиляється незалежно від того, наскільки привабливими є її технічні характеристики на папері.

| Категорія інструменту | Опис технології | Вартість у жетонах | Операційний ризик та наслідки |
| :--- | :--- | :--- | :--- |
| **Основна мова розробки** | Впровадження мови, якою раніше не писали сервіси в компанії (наприклад, Rust або Elixir замість Go). | **1.5 жетони** | Відсутність інструментарію профілювання, складність найму, брак експертизи у CI. |
| **Не-реляційне сховище** | Впровадження нової NoSQL / Graph / Vector баз даних (наприклад, Neo4j, Milvus, Cassandra). | **1.0 жетон** | Складність створення резервних копій, невідомі граничні випадки при розщепленні мережі (*split-brain*). |
| **Кастомний протокол** | Саморобний бінарний протокол поверх TCP/UDP замість gRPC / HTTP2 / JSON. | **1.0 жетон** | Відсутність стандартних аналізаторів трафіку (Wireshark), складність відлагодження. |
| **Експериментальний фреймворк** | Фреймворк з версією < 1.0 або менше 2 років історії відкритої розробки. | **1.0 жетон** | Високий ризик припинення підтримки розробниками, неперевірена безпека. |
| **Нудний стандарт** | PostgreSQL, Redis, Linux, Docker, Nginx, C++, Go, TypeScript. | **0.0 жетонів** | Зрозуміла поведінка, вичерпні інструкції, тисячі фахівців на ринку. |

Обчислення суми жетонів виконується за виразом:

```
tokens_total = sum(tokens_i) <= 3.0
```

При досягненні суми в 3.0 жетони будь-які нові технологічні експерименти заморожуються. Щоб ввести новий експериментальний інструмент, команда повинна спочатку вивести з експлуатації один із раніше впроваджених нестандартних елементів.

##### Практичні правила аудиту інноваційних жетонів:
1. **Жетон витрачається на клас технології, а не на її конкретне ім'я:** Якщо у компанії вже є експертиза з PostgreSQL, впровадження MySQL вважається витратою 0.5 жетона (нова СУБД, хоча й одного класу).
2. **Термін утилізації жетона:** Інноваційний жетон вважається «повернутим у бюджет» лише після 1 року беззаварійної експлуатації технології у продакшні та наявності принаймні 3 спеціалістів у команді, які вміють її обслуговувати.
3. **Заборона паралельних жетонів:** Заборонено витрачати більше 1 інноваційного жетона в межах одного спринту чи одного релізу.

### 3. Регламент проведення сесії Pre-Mortem

Перед затвердженням будь-якої архітектурної зміни категорії **One-Way Door** проводиться обов'язковий 30-хвилинний воркшоп Pre-Mortem. Мета воркшопу — зламати психологічний ефект «групового мислення» (*groupthink*) та завчасно виявити приховані точки відмови, які ігноруються через надмірний оптимізм команди.

#### Покрокова фасилітація сесії Pre-Mortem:

##### Фаза 1: Постановка фатальної гіпотези (Тривалість: 5 хвилин)
Фасилітатор (архітектор або лід теми) збирає розробників, інженерів з експлуатації, тестувальників та представників продукту. Модератор робить вступну заяву за жорстким шаблоном:
> *«Уявіть, що сьогодні [Поточна дата + 1 рік]. Ми затвердили пропозицію, побудували систему і витили її в продакшн. Минув рік. Система зазнала повного катастрофічного провалу: дані користувачів втрачено, сервіси лежать понад 48 годин, компанія зазнала величезних збитків, а нашу команду звільнено. Ми зібралися в цій кімнаті для того, щоб за 5 хвилин мовчки написати історію про те, як саме це сталося»*.

##### Фаза 2: Мовчазний генеративний штурм (Тривалість: 5 хвилин)
Усі учасники воркшопу в повній тиші виписують на картки або у спільну онлайн-дошку причини катастрофи.
* **Правило 1:** Категорично заборонено спілкуватися, коментувати чи сперечатися.
* **Правило 2:** Дозволено вказувати будь-які причини — від технічних (дедлок у базі даних) до організаційних (звільнився єдиний інженер, який знав пароль від консолі).
* **Правило 3:** Повна анонімність нотаток для зняття психологічного тиску авторитету старших інженерів.

##### Фаза 3: Кластеризація та агрегація (Тривалість: 10 хвилин)
Фасилітатор зачитає кожну картку вголос і групує їх за категоріями ризику (мережеві відмови, консистентність даних, людський фактор, навантажувальні піки, безпека).

##### Фаза 4: Ранжування та розробка мітигацій (Тривалість: 10 хвилин)
Для кожного кластера обчислюється підсумковий бал ризику:

```
risk_score = likelihood * impact
```

Де `likelihood` та `impact` оцінюються за шкалою від 1 до 5.

Якщо `risk_score >= 12`, рішення **не допускається до реалізації** у початковому вигляді. Команда повинна внести зміни у дизайн (додати ізоляцію, переписати контракт або ввести fallback), щоб знизити бал ризику нижче порогу 12.

### 4. Стандарт картки вимірювань продуктивності (Measure First Rule)

Заборонено приймати будь-які оптимізаційні PR/RFC без заповнення такої картки вимірювань. Вимоги до вимірювань базуються на принципі: якщо оптимізація не може бути підтверджена графіком Flamegraph або зміщенням латентності на реальному навантажувальному стенді, вона створює лише випадкову складність і має бути відхилена.

```markdown
### Картка вимірювань продуктивності (Measure First Card)

1. **Базові метрики до зміни (Baseline):**
   - Latency p50: [значення ms]
   - Latency p99: [значення ms]
   - CPU Utilization: [значення %]
   - Memory RSS: [значення MB]
   - Throughput (RPS): [значення]

2. **Докази пляшкового горла (Bottleneck Evidence):**
   - Додано Flamegraph / CPU profile: [посилання на артефакт]
   - Додано Memory allocation profile: [посилання на артефакт]
   - Локація гарячої точки (Hotspot): [файл, метод, рядок коду]

3. **Результати після зміни на бенчмарку (After Benchmark):**
   - Абсолютне покращення p99: [значення ms]
   - Відносне покращення: [%]
   - Ціна випадкової складності: [кількість нових рядків / шарів індирекції]

4. **Висновок архітектора:**
   - [ ] Виграш продуктивності перевищує вартість підтримки складності коду.
   - [ ] Виграш несуттєвий (< 15%), оптимізацію відхилено згідно з YAGNI.
```

### 5. Реєстр типових антипатернів та інженерних відхилень

У таблиці наведено типові помилки інженерів при спробах обходу евристичних правил та способи їх нейтралізації на рівні процесів.

| Anti-Pattern (Антипатерн) | Прояв у поведінці розробників | Шкода для системи | Архітектурна нейтралізація |
| :--- | :--- | :--- | :--- |
| **Premature Generalization** (Передчасне узагальнення) | Створення універсальних інтерфейсів та плагінів для кожної сутності «про всяк випадок». | Зростання когнітивного навантаження, 5 шарів індирекції на кожен чистий виклик. | Примусове застосування YAGNI: дублювання коду дозволено до появи 3 реальних споживачів. |
| **Resume-Driven Development** (Розробка ради резюме) | Вибір нових фреймворків чи мов ради вивчення за рахунок проєкту. | Операційний колапс при виході авторів системи з компанії. | Жорстке лімітування бюджету інноваційних жетонів (максимум 2–3 на проєкт). |
| **Analysis Paralysis** (Аналітичний параліч) | Витрата місяців на вибір між двома повністю зворотними бібліотеками логування. | Втрата ринкового вікна, висока вартість зволікання (*Cost of Delay*). | Застосування фільтра зворотності: якщо рішення є Two-Way Door, час прийняття обмежується 15 хвилинами. |
| **Faith-Based Optimization** (Оптимізація на вірі) | Переписування систем на C++/Rust ради прискорення без вимірювання затримок. | Витрачені місяці розробки без реального зміщення p99 латентності. | Застосування правила Measure First: PR відхиляється у CI без flamegraph-доказів. |

Аналіз цих антипатернів показує, що більшість невдалих архітектурних рішень є наслідком когнітивних пасток, а не браку технічних знань. Систематичне застосування поданого довідника нейтралізує суб'єктивні чинники та підтримує високу якість дизайну системи на всіх етапах її еволюції.

### 6. Рекомендована процедура інтеграції довідника в інженерний процес

Для успішного застосування довідника в команді рекомендується наступний чотирикроковий інституційний маршрут:
1. **Первинний триаж при створенні Issue:** Автор завдання заповнює 3 поля: `Reversibility Score`, `Innovation Tokens`, `Has Metrics`.
2. **Автоматична перевірка у CI:** Бот перевіряє суму жетонів проєкту та наявність метрик для оптимізаційних задач.
3. **Асинхронний розбір Two-Way Doors:** 80% завдань проходять без проведення зустрічей протягом 15 хвилин після рев'ю одного інженера.
4. **Колегіальний розбір One-Way Doors:** Для 20% критичних завдань призначається 30-хвилинна сесія Pre-Mortem та захист на Architecture Review Board.

Дотримання цієї процедури мінімізує бюрократичні затримки й забезпечує надійний захист системи від катастрофічних помилок.
