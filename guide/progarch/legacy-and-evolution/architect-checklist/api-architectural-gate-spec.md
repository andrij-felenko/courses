# 📋 Специфікація Readiness Gate: Контракт перевірки 7 вимірів архітектури

Специфікація **Architectural Readiness Gate** описує машинно-читаний та інженерний контракт перевірки готовності архітектурного рішення до розгортання у продуктивному середовищі. Контракт формалізує 7 критичних вимірів готовності, визначає правила вагового оцінювання, критичні вето-пороги (Hard Stop Thresholds) та вимоги до підтверджувальних артефактів.

Головна мета даної специфікації — перетворити суб'єктивні архітектурні суперечки на прозорий, ретельно вимірюваний та перевіряємий інженерний процес. Замість абстрактних тверджень про «високу якість» або «чистоту коду», кожна команда висуває реліз разом із декларативним маніфестом, у якому чітко вказані виміряні метрики затримок, зафіксовані ліміти вибухового радіуса, підтверджені схеми безпеки та посилання на оперативні інструкції з ліквідації аварій.

Використання стандартизованого декларативного маніфесту дозволяє інтегрувати процес оцінки архітектури безпосередньо в конвеєр автоматичного збирання та розгортання. Завдяки цьому архітектурний гейт перестає бути бюрократичним органом і перетворюється на автоматизований інженерний фільтр, який захищає продакшн від непідготовлених змін.

## 1. Структура та параметри декларації архітектурної готовності (`readiness-gate.json`)

Кожен компонент або мікросервіс, що висувається на розгортання у продуктивне середовище, зобов'язаний містити у своєму репозиторії файл декларації `readiness-gate.json` (або `readiness-gate.yaml`). Цей маніфест автоматично валідується на етапі CI/CD й слугує основним документом при проведенні peer-review перевірки.

### Деталізація полів та семантика контрольних точок

Маніфест розбито на 7 вимірів, кожен з яких відповідає за конкретний атрибут якості системи:

- `component_id` та `version`: Унікальний ідентифікатор компонента в загальному реєстрі сервісів та його точна семантична версія.
- `owner_team`: Назва однієї інженерної команди, яка повністю володіє даним сервісом, відповідає за його чергування, підтримку та еволюцію (згідно з принципами Team Topologies).
- `adr_reference`: Ідентифікатор затвердженого запису про архітектурне рішення (Architecture Decision Record), що описує фундаментальний вибір технологій або топології для даної версії.
- `resilience.max_blast_radius_pct`: Максимально допустимий відсоток користувачів або системних функцій, які можуть постраждати у разі повного краху даного сервісу. Для Tier-1 сервісів цей показник не повинен перевищувати 5%.
- `scalability.measured_p99_latency_ms`: Реально виміряна затримка на 99-му перцентилі під час тестового синтетичного навантаження. Вона повинна бути нижчою за цільовий поріг `target_p99_latency_ms`.
- `security.mtls_enforced`: Прапорець, що підтверджує обов'язкове використання взаємного шифрування mTLS для всіх вхідних і вихідних мережевих сокетів.
- `tco.unit_cost_usd_per_1M_req`: Розрахункова вартість обробки 1 мільйона запитів у хмарі (включаючи обчислення, оперативну пам'ять, мережевий трафік та сховище).
- `observability.runbook_url`: Пряме та перевірене посилання на оперативну інструкцію для чергового інженера (On-Call Engineer) з кроками діагностики та локалізації збоїв.

Обов'язковою вимогою до кожного поля маніфесту є наявність підтверджувального джерела даних. Наприклад, показник затримки `measured_p99_latency_ms` не може вводитися вручну на основі припущень — він автоматично витягується з останнього успішного запуску навантажувального тесту у CI/CD.

## 2. Повна матриця критеріїв та блокуючих умов (Hard Blockers)

Для кожного виміру встановлюється чітке правило оцінювання. Наявність бодай однієї блокуючої умови (Hard Blocker) призводить до автоматичного вето на реліз, незалежно від того, скільки позитивних балів набрали інші розділи.

| Вимір | Ключовий показник (KPI) | Нормативний поріг | Блокуюча умова (Hard Blocker) |
| :--- | :--- | :--- | :--- |
| **1. Стійкість** | Blast Radius Limit | ≤ 5% загального трафіку | Відсутній Circuit Breaker або сокетні таймаути > 3s |
| **2. Масштабованість** | Tail Latency `p99.9` | ≤ заданого SLO (напр. 50 мс) | Деградація затримки > 200% при 1.5× від пікового навантаження |
| **3. Безпека** | STRIDE Coverage | 100% меж публічного I/O | Наявність відкритих креденшалів у коді або відсутній mTLS |
| **4. TCO** | Cloud Unit Cost | ≤ закладеного кошторису | Неконтрольований витік пам'яті або відсутність розкладу retention |
| **5. Еволіціонованість** | Backward Compatibility | 100% сумісність контракту | Деструктивна зміна схеми БД без фази Expand-Contract |
| **6. Соціотехніка** | Service Ownership | Точно 1 відповідальна команда | Розмита власність (2+ команди правлять сервіс без API-контракту) |
| **7. Спостережуваність** | OpenTelemetry Traversal | 100% викликів з Trace ID | Відсутність індикаторів у моніторингу та посилання на Runbook |

### Процедура обробки Hard Blockers у конвеєрі

Коли аналізатор CI/CD виявляє порушення блокуючої умови (наприклад, у коді виявлено виклик зовнішнього HTTP-сервісу без Circuit Breaker або у схемі бази даних знайдено видалення колонки без проміжного стану), система виконує такі дії:

1. Завершує етап збирання з помилкою execution status code 1.
2. Формує чіткий звіт про порушений інваріант із зазначенням конкретного файлу, рядка коду та номера правила з даної специфікації.
3. Автоматично залишає блокуючий коментар у pull request та блокує можливість злиття коду в основну гілку `main` до надання виправити дефект або отримання офіційного відхилення (Waiver) від архітектурного комітету.

## 3. Математична модель та вагове обчислення індексу готовності

Загальний індекс готовності архітектури до продакшну (`R_arch`) обчислюється як зважена сума оцінок 7 вимірів за умови відсутності блокуючих вето:

```
R_arch = ∑ (w[i] · S[i])  при ∀ i: Blocker[i] == FALSE
```

Де:
- `w[i]` — нормалізована вага виміру (`∑ w[i] = 1.0`). Залежно від типу сервісу ваги можуть перерозподілятися. Наприклад, для сервісів обробки платежів та керування замками вагові коефіцієнти безпеки та стійкості встановлюються на рівні `w[resilience] = 0.25` та `w[security] = 0.25`, тоді як для внутрішніх аналітичних звітів пріоритет зміщується у бік `w[tco] = 0.30`.
- `S[i]` — оцінка виміру за 5-бальною шкалою (від 1 до 5), визначена на основі виміряних автоматичних метрик та результатів peer-review.
- Якщо хоча б для одного виміру `Blocker[i] == TRUE`, підсумковий індекс `R_arch = 0`, і реліз безумовно блокується на рівні CI/CD.

### Градація прохідних порогів

Залежно від рівня критичності сервісу (Service Tier), встановлюються наступні прохідні значення індексу готовності:

- **Tier-1 (Критичні ядра системи):** Прохідний поріг `R_arch ≥ 4.7`. Не допускається жодної оцінки по окремих вимірах нижче 4 балів. Будь-яке відхилення вимагає письмової санкції Головного архітектора.
- **Tier-2 (Основні бізнес-сервіси):** Прохідний поріг `R_arch ≥ 4.0`. Припускаються окремі оцінки уровня 3 бали за умови наявності чіткого плану усунення технічного боргу у наступному спринті.
- **Tier-3 (Внутрішній фоновий інструментарій):** Прохідний поріг `R_arch ≥ 3.2`. Фокус робиться на відсутності блокерів безпеки та TCO.

Формалізація даної специфікації дозволяє уникнути вибіркового дотримання вимог та робить процес випуску програмного забезпечення передбачуваним, безпечним та економічно обґрунтованим.
