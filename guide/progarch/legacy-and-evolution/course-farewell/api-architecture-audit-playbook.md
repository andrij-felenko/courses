# 📋 Плейбук та інтерфейс комплексного архітектурного аудиту системи

Цей плейбук регламентує нормативний порядок, вхідні інваріанти, матрицю контрольних запитань та вихідні артефакти для проведення комплексного архітектурного аудиту програмної системи будь-якого масштабу.

Архітектурний аудит — це систематичне оцінювання спроможності поточного дизайну системи забезпечувати задані бізнес-драйвери та якісні атрибути в умовах постійної еволюції та технічного боргу. Аудит проводиться при передачі системи новій команді, перед підготовкою до масштабування, або у разі підвищеної частоти аварійних інцидентів (Incidents & Outages).

```
[Вхідні дані аудиту]
  ├── Дерево корисності (Utility Tree) & Сценарії атрибутів
  ├── Джерельний код, CI-конфігурації та Git Log
  └── Продакешн-телеметрія (Metrics, Traces, Incident Logs)
            │
            ▼
┌────────────────────────────────────────────────────────┐
│             ФАЗИ АРХІТЕКТУРНОГО АУДИТУ                 │
├────────────────────────┬───────────────────────────────┤
│ 1. Reconnaissance      │ Відновлення C4 та контекстів  │
│ 2. Quality Evaluation  │ ATAM-лайт оцінка за якістю    │
│ 3. Erosion Audit       │ Пошук циклів та гарячих точок │
│ 4. Risk Classification │ Карта ризиків & One-way doors │
│ 5. Action Plan         │ План модернізації та ADR      │
└────────────────────────┴───────────────────────────────┘
            │
            ▼
[Вихідні артефакти]
  ├── Карта гарячих точок (Hotspot Map)
  ├── Реєстр незворотних ризиків та ADR-журнал
  └── Автоматизовані фітнес-функції для CI/CD
```

## 1. Детальний нормативний регламент фаз аудиту

Аудит виконується за строго визначеною п'ятифазною процедурою. Кожна фаза має зафіксовані вхідні вимоги, інструментарій, коло відповідальних осіб та вихідні артефакти.

### Фаза 1: Рекогносцировка та відновлення контексту (Reconnaissance)
* **Мета**: Побудувати об'єктивну картину поточного стану системи, незалежно від наявної застарілої документації чи усних переказів.
* **Вхідні дані**: Джерельний код репозиторіїв, схеми баз даних, CI/CD скрипти, конфігурації Kubernetes/IaC, інтерв'ю зі стейкхолдерами та розробниками.
* **Покрокові дії**:
  1. **Відновлення контекстного рівня C4 (Level 1: System Context)**: ідентифікація зовнішніх користувачів, суміжних систем, сторонніх SaaS-сервісів та апаратних пристроїв.
  2. **Відновлення контейнерного рівня C4 (Level 2: Container Diagram)**: визначення меж процесів, сховищ даних (СУБД, кеші, черги) та мережевих периметрів.
  3. **Аналіз історії змін (Git Archaeology)**: збір логів git-історії за останні 6–12 місяців. Обчислення метрики гарячих точок (Hotspots) шляхом множення частоти коммітів (Churn) на складність коду (Cyclomatic Complexity).
* **Вихідні артефакти**: Актуальна C4-модель у форматі Structurizr DSL / Mermaid, карта гарячих точок (Hotspot Map), список ідентифікованих обмежених контекстів (Bounded Contexts).

### Фаза 2: Оцінка якісних атрибутів за методикою ATAM-Лайт
* **Мета**: Перевірити відповідність архітектури ключовим сценаріям якості та знайти приховані точкові вразливості.
* **Вхідні дані**: Дерево корисності (Utility Tree), сформоване разом із бізнес-стейкхолдерами, сценарії якісних атрибутів (Stimulus → Source → Environment → Response → Response Measure).
* **Покрокові дії**:
  1. Проведення оціночного воркшопу ATAM-лайт за участю архітектора, техліда, SRE-інженера та продакт-менеджера.
  2. Прогін кожного пріоритетного сценарію крізь поточну архітектуру контейнерів та сервісів.
  3. **Фіксація Чутливих Точок (Sensitivity Points)**: визначення параметрів архітектури, зміна яких критично впливає на конкретний атрибут (наприклад, розмір пулу з'єднань з БД безпосередньо визначає латентність).
  4. **Фіксація Точок Компромісу (Trade-off Points)**: визначення параметрів, які покращують один атрибут ціною погіршення іншого (наприклад, синхронне дублювання записів у три регіони підвищує доступність, але збільшує латентність p99 на 120 мс).
* **Вихідні артефакти**: Матриця оцінки якісних атрибутів, список ідентифікованих архітектурних ризиків та не-ризиків.

### Фаза 3: Аналіз архітектурної ерозії та деградації коду
* **Мета**: Виявити місця порушення меж модулів, циклічні залежності та вичерпання запасу міцності.
* **Вхідні дані**: Граф залежностей коду, статичні аналізатори (ArchUnit, dependency-cruiser, clang-tidy), метрики зчеплення (`Ca`, `Ce`).
* **Покрокові дії**:
  1. Обчислення метрики нестабільності `I = Ce / (Ca + Ce)` для кожного модуля та оцінка його відстані `D` від Головної Послідовності.
  2. Пошук орієнтованих циклів у графі залежностей за допомогою алгоритму Тарджана або DFS.
  3. Перевірка дотримання правил шарів: виявлення випадків, коли доменне ядро викликає зовнішні веб-контролери або адаптери СУБД.
* **Вихідні артефакти**: Звіт про рівень архітектурної ерозії, конфігураційний файл фітнес-функцій для включення у CI/CD.

### Фаза 4: Класифікація ризиків та оцінка незворотності
* **Мета**: Розділити виявлені проблеми за пріоритетом і ціною відкату для запобігання паралічу аналізу.
* **Вхідні дані**: Звіт фаз 2 та 3, матриця ризиків.
* **Покрокові дії**:
  1. Оцінка ймовірності настання аварійної події (Probability: Low / Medium / High).
  2. Оцінка фінансового та операційного впливу події (Impact: Low / Medium / Critical).
  3. Класифікація рішень за ціною відкату: One-Way Doors (незворотні) проти Two-Way Doors (зворотні).
* **Вихідні артефакти**: Затверджений ризик-реєстр (Risk Register), розрахована матриця незворотних рішень.

### Фаза 5: План модернізації та формування ADR-журналу
* **Мета**: Сформувати покрокову дорожню карту виправлення дефектів без зупинки працюючого бізнесу.
* **Вхідні дані**: Ризик-реєстр, C4-модель, бюджет модернізації.
* **Покрокові дії**:
  1. Складання покрокового плану рефакторингу за допомогою паттернів Strangler Fig, Branch-by-Abstraction та двофазних міграцій.
  2. Оформлення прийнятих незворотних рішень у вигляді нормативних ADR-документів.
  3. Налаштування операційних Quality Gates у CI/CD.
* **Вихідні артефакти**: Дорожня карта модернізації (Roadmap), серія ADR-документів, оновлені правила збірки.

## 2. Нормативна матриця перевірки якісних атрибутів

| Атрибут якості | Контрольне запитання аудиту | Індикатор деструкції (Red Flag) | Необхідна тактика мітигації |
|---|---|---|---|
| **Продуктивність (Performance)** | Яким є p99 латентності під час пікового навантаження? | Наявність N+1 запитів до БД у циклі обробки | Read-model caching, Coalescing, Index tuning |
| **Доступність (Availability)** | Що відбувається при виході з ладу одного вузла або зональному збої? | Синхронний каскадний таймаут між сервісами | Circuit Breaker, Bulkhead, Fallback |
| **Масштабованість (Scalability)** | Як система реагує на 10-кратне зростання обсягу даних та RPS? | Глобальні блокування у реляційній БД | Horizontal Sharding, Event Sourcing, Outbox |
| **Змінюваність (Modifiability)** | Скільки часу займе додавання нового типу оплати або датчика? | Зміна одного поля вимагає правок у 8 сервісах | Hexagonal boundaries, ACL, Branch-by-Abstraction |
| **Безпека (Security)** | Як перевіряється авторизація на межі між внутрішніми сервісами? | Нешифрований внутрішній HTTP без перевірки прав | Zero Trust, mTLS, Short-lived JWT/SPIFFE |
| **Спостережність (Observability)** | Чи можна відстежити шлях запиту, що завершився помилкою 500? | Відсутність наскрізного `Trace-ID` у чергах | OpenTelemetry tracing, Structured JSON logs |
| **Економічність (Cost / FinOps)** | Якою є вартість обслуговування одного активного користувача ($/MAU)? | Неконтрольоване зростання плати за закриті SaaS | Boring Technology, Auto-scaling, Rightsizing |
| **Тестованість (Testability)** | Чи можна протестувати бізнес-логіку без запуску СУБД та Docker? | Тести вимагають 20 хвилин на підняття середовища | Hexagonal Ports/Adapters, In-Memory Mocks |
| **Експлуатованість (Operability)** | Скільки кроків вимагає відкат невдалого релізу у продакшені? | Ручні інструкції на 15 сторінок у Wiki | Automated Blue-Green / Canary, GitOps |

## 3. Регламент оцінки ризиків та незворотності рішень

Під час аудиту кожне виявлене деструктивне відхилення класифікується за двома параметрами: **Ціна відкату (Reversibility)** та **Рівень ризику (Impact × Probability)**.

```
                  В ПЛИВ  (IMPACT)
                Низький          Високий
            ┌──────────────┬────────────────┐
  Висока    │   ЗОНА 1     │     ЗОНА 2     │
  (Two-Way) │  Делегувати  │  Купити спайк  │
ЦІНА        ├──────────────┼────────────────┤
ВІДКАТУ     │   ЗОНА 3     │     ЗОНА 4     │
  Низька    │  Прийняти    │  ADR & Комітет │
  (One-Way) │  як борг     │  (Критична)    │
            └──────────────┴────────────────┘
```

1. **Two-Way Door (Швидкі зворотні рішення)**: зміна конфігурації кешу, додавання індексу в БД, створення локального DTO. Аудит не блокує такі рішення; вони делегуються командам.
2. **One-Way Door (Незворотні рішення)**: вибір СУБД для транзакційного ядра, публічний контракт API для зовнішніх клієнтів, формат даних на диску. Вимагають обов'язкового оформлення ADR, рев'ю комітету та колегіального узгодження.

## 4. Канонічний шаблон Architectural Decision Record (ADR)

Кожне значуще рішення, прийняте за результатами аудиту, обов'язково фіксується у файлі `doc/adr/ADR-XXXX-<slug>.md` за наступним стандартом:

```markdown
# ADR-0042: Перехід від синхронного REST до подійно-орієнтованого Outbox у сервісі платежів

* **Статус**: [Прийнято | Замінено на ADR-0050 | На розгляді]
* **Дата**: 2026-08-18
* **Автори**: Інженерна команда платформи Digital Homes

## 1. Контекст та проблематика
При проведення аудиту виявлено, що під час пікових навантажень прямий HTTP-виклик між сервісом замовлень та сервісом еквайрингу призводить до таймаутів у 12% випадків. Це викликає подвійне списання коштів та блокування потоків виконання.

## 2. Розглянуті альтернативи
1. **Збільшення таймаутів та агресивний Retry**: відхилено через загрозу метастабільного колапсу.
2. **Запровадження Distributed 2PC Transactions**: відхилено через високе зчеплення та низьку доступність.
3. **Transactional Outbox Pattern + Kafka Consumer**: обрана альтернатива.

## 3. Прийняте рішення
Запровадити таблицю `outbox` у базу даних Postgres сервісу замовлень та CDC-демон (Debezium) для асинхронної публікації подій у Kafka з гарантією At-Least-Once.

## 4. Наслідки та прийнятий борг
* **Позитивні**: Латентність створення замовлення знизилася з 1200 мс до 45 мс.
* **Негативні/Борг**: Клієнти мусять підтримувати eventual consistency у UI та обробляти стан "Pending Payment". Потрібно реалізувати ідемпотентний консюмер у сервісі сповіщень.
```

## 5. Поріг прийняття рішень та індикатори зупинки (Quality Gates)

Аудит вважається **успішно пройденим**, якщо система відповідає наступним мінімальним інваріантам:

* **Циклічні залежності між модулями**: рівні `0` (будь-який цикл є дефектом блокуючого пріоритету).
* **Порушення шарів у коді**: `0` випадків виклику адаптерів чи представлення з доменного ядра.
* **Покриття ключових роздоріж журналами ADR**: `100%` для усіх незворотних рішень (One-Way Doors).
* **Наявність розриву мережевого зв'язку (Circuit Breaker)**: реалізовано на всіх зовнішніх HTTP/gRPC викликах.
* **Наявність ідемпотентних ключів**: реалізовано на всіх мутуючих API-ендпоінтах.
* **Запас бюджету помилок (Error Budget)**: виснаження за місяць не перевищує 50% від заданого SLO.
