# 📋 Специфікація скрізного конвеєра запиту і заголовків телеметрії

Цей довідник містить технічну специфікацію структур даних, заголовків мережевого транспорту, схем реляційних баз даних, алгоритмів авторизації, контракту брокерів повідомлень та матриць статусів помилок, які використовуються для забезпечення скрізного проходження керуючих команд у платформі Digital Homes.

Документ слугує єдиним джерелом правди (Single Source of Truth) для розробників мобільних застосунків, інженерів API Gateway, авторів доменних мікросервісів та інженерів прошивок для IoT-пристроїв.

## 1. Заголовки HTTP-транспорту та специфікація W3C Trace Context

Кожен вихідний HTTP-запит від мобільного застосунку або зовнішнього інтегратора на API Gateway платформи мусить містити стандартний набір заголовків для автентифікації, гарантії ідемпотентності та простеження.

Передача контексту трасування здійснюється суворо відповідно до специфікації W3C Trace Context. Заголовок `traceparent` є обов'язковим для всіх мутуючих запитів. Якщо зовнішній мобільний клієнт надсилає запит без заголовка `traceparent` (або заголовок містить синтаксичні помилки), L7-балансувальник Envoy або API Gateway зобов'язані згенерувати новий унікальний `trace_id` і інжектувати валідний заголовок перед передачею запиту у внутрішню мікросервісну мережу.

### Таблиця специфікації транспортних заголовків

| Заголовок | Тип даних | Обов'язковість | Опис, правила валідації та обробка помилок | Приклад значення |
|---|---|---|---|---|
| `Authorization` | String | Так | Bearer JWT access token користувача. Перевіряється на API Gateway. | `Bearer eyJhbGciOiJSUzI1Ni...` |
| `traceparent` | String | Так | Стандарт W3C Trace Context (`version-trace_id-parent_id-flags`). | `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01` |
| `tracestate` | String | Ні | Непрозорий список пар ключ-значення для передачі вендорських параметрів. | `dh=s:1;vendor=x1` |
| `Idempotency-Key` | UUIDv4 | Так | Ключ ідемпотентності для запобігання повторному виконанню однакових команд. | `9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d` |
| `X-Request-ID` | UUIDv4 | Ні | Legacy ідентифікатор запиту (використовується для зворотної сумісності). | `c56a4180-65aa-42ec-a945-5fd21dec0538` |
| `Content-Type` | String | Так | Специфікація кодування тіла запиту. Дозволено лише `application/json`. | `application/json` |

### Байтова структура та розбір заголовка `traceparent`

Поле `traceparent` має суворо фіксовану довжину 55 символів і розбивається на чотири поля, розділені дефісом:

```
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
│  │                                │                │
│  │                                │                └─ Trace Flags: 8-бітне поле (01 = Sampled)
│  │                                └─ Parent Span ID: 16 hex-знаків (64 біти)
│  └─ Trace ID: 32 hex-знаки (128-бітний унікальний UUID)
└─ Version: 2 hex-знаки (поточна версія стандарту — 00)
```

Правила обробки полів у шлюзі та сервісах:
- **Version (2 шестнадцятерічні символи):** Наразі підтримується лише версія `00`. Запити з невідомою версією не відхиляються, але розбираються за правилами версії `00`.
- **Trace ID (32 шестнадцятерічні символи):** 16-байтний глобальний ідентифікатор транзакції. Заборонено значення, що складається з усіх нулів (`00000000000000000000000000000000`). У разі виявлення нульового `trace_id` шлюз вважає заголовок невалідним і генерує новий UUIDv4.
- **Parent Span ID (16 шестнадцятерічних символів):** 8-байтний ідентифікатор батьківського спану. Заборонено значення з усіх нулів (`0000000000000000`).
- **Trace Flags (8-бітне поле):** Найменш значущий біт (`01`) відповідає за прапорець семплювання (Sampled flag). Якщо біт дорівнює `1`, усі внутрішні сервіси зобов'язані зберігати зібрану телеметрію і надсилати спани до OpenTelemetry Collector. Якщо біт дорівнює `0`, контекст передається далі, але спани не зберігаються у базі даних трасування.

### Захист від підробки контексту (Trace Context Forgery Protection)

Оскільки зовнішній мобільний клієнт потенційно може надіслати підроблений `traceparent` з метою переповнення систем спостережуваності або фальсифікації логів, API Gateway застосовує політику санітизації (Sanitization Policy):
- Для неавтентифікованих викликів або зовнішніх вебхуків початковий `traceparent` перезаписується шлюзом.
- Для автентифікованих клієнтів `trace_id` зберігається, але шлюз генерує новий `parent_span_id` і створює дочірній спан для внутрішнього контуру.

## 2. Схема JWT Access Token та алгоритми авторизації

Автентифікація та авторизація запиту спираються на використання JSON Web Token (JWT). Токен підписується асиметричним приватним ключем Auth Service за допомогою алгоритму RS256 (RSA Signature with SHA-256) або Ed256 (EdDSA) і перевіряється шлюзом API Gateway через криптографічний кеш публічних ключів JWKS (JSON Web Key Set).

### Структура JWT Claims (JSON Payload)

Тіло декодованого JWT-токена містить наступні стандартні атрибути (RFC 7519) та доменні розширення платформи Digital Homes:

```json
{
  "iss": "https://auth.digitalhomes.io",
  "sub": "usr_99a8b7c6d5",
  "aud": "https://api.digitalhomes.io",
  "exp": 1776512400,
  "iat": 1776508800,
  "home_id": "hm_77a112233",
  "roles": ["owner"],
  "scopes": ["locks:read", "locks:write", "devices:control"],
  "device_access": {
    "hm_77a112233": ["lock_front_door", "lock_garage"]
  }
}
```

### Детальна семантика полів та інваріанти перевірки:
- `iss` (Issuer): Унікальний URI сервісу видачі токенів. Шлюз відхиляє токени від невідомих `iss`.
- `sub` (Subject): Унікальний постійний ідентифікатор користувача у формі UUID.
- `aud` (Audience): Цільова адреса API. Повинна збігатися з `https://api.digitalhomes.io`.
- `exp` (Expiration Time): Часова мітка Unix epoch, що визначає термін придатності токена. Шлюз враховує допустимий часовий зсув (Clock Skew) тривалістю не більше 60 секунд. Якщо `exp + 60s < NOW()`, запит відхиляється з кодом `401 Unauthorized`.
- `iat` (Issued At): Час видачі токена. Використовується для відкликання токенів, виданих до глобального скидання сесій.
- `home_id`: Ідентифікатор основного будинку користувача.
- `roles`: Ролі користувача в системі (`owner`, `family_member`, `guest`).
- `scopes`: Перелік системних прав доступу (OAuth2 Scopes), які запитав мобільний застосунок.
- `device_access`: Матриця безпосереднього доступу до ідентифікаторів пристроїв у конкретних будинках для забезпечення перевірок ReBAC (Relationship-Based Access Control).

### Алгоритм перевірки відкликання токенів (Token Revocation List)

Якщо токен користувача компрометовано або користувач вийшов із системи, токен додається у списки відкликання (Token Revocation List / Bloom Filter) в і-пам'яті Redis. Перед декодуванням підпису API Gateway здійснює швидку перевірку хешу токена у Bloom Filter. Це дозволяє миттєво відхиляти відкликані токени без витрат ресурсів ЦПУ на криптографічну перевірку підпису RSA.

## 3. Схема aggregate Device Twin у БД та пам'яті

Двійник пристрою (Device Twin) є центральним агрегатом доменної моделі платформи. Він зберігає розділені стани `desired` (бажаний стан, встановлений користувачем) та `reported` (фактичний стан, підтверджений фізичним пристроєм).

```json
{
  "device_id": "lock_front_door",
  "home_id": "hm_77a112233",
  "device_type": "smart_lock",
  "version": 42,
  "state": {
    "desired": {
      "lock_state": "UNLOCKED",
      "updated_at": "2026-08-18T10:14:02.102Z",
      "updated_by": "usr_99a8b7c6d5"
    },
    "reported": {
      "lock_state": "LOCKED",
      "battery_level": 88,
      "updated_at": "2026-08-18T10:10:00.000Z"
    },
    "delta": {
      "lock_state": "UNLOCKED"
    }
  }
}
```

### Механіка узгодження станів (Reconciliation & Delta Calculation)

Обчислюване поле `delta` містить різницю між `desired` та `reported`. Загальні правила обчислення дельти:
1. Якщо `desired.lock_state == reported.lock_state`, то `delta` дорівнює порожньому об'єкту `{}`. Це означає, що пристрій знаходиться в узгодженому стані і не потребує надсилання нових команд.
2. Якщо `desired.lock_state != reported.lock_state`, то `delta` містить ключ `lock_state` із бажаним значенням. Це запускає конвеєр доставки команд.
3. Кожна мутація полів `desired` супроводжується обов'язковим інкрементом поля `version` (`version = version + 1`). Це забезпечує оптимістичне блокування (Optimistic Concurrency Control) у базі даних і запобігає стану гонки (Race Condition), коли два паралельних запити намагаються змінити стан пристрою одночасно.

## 4. Схема транзакційної таблиці `outbox_messages` (PostgreSQL)

Для реалізації шаблону Transactional Outbox реляційна база даних PostgreSQL містить виділену таблицю `outbox_messages`. Запис у цю таблицю відбувається в межах тієї ж ACID-транзакції, що й оновлення стану у таблиці `device_twins`.

```sql
CREATE TABLE outbox_messages (
    id              BIGSERIAL PRIMARY KEY,
    aggregate_type  VARCHAR(64) NOT NULL,      -- 'DeviceTwin'
    aggregate_id    VARCHAR(64) NOT NULL,      -- 'lock_front_door'
    event_type      VARCHAR(64) NOT NULL,      -- 'LockUnlockCommanded'
    payload         JSONB NOT NULL,            -- Тіло команди
    trace_id        VARCHAR(32) NOT NULL,      -- W3C Trace ID
    span_id         VARCHAR(16) NOT NULL,      -- W3C Span ID
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    processed_at    TIMESTAMPTZ NULL,          -- NULL доки CDC / Relay не відправив у Kafka
    retry_count     INT NOT NULL DEFAULT 0
);

CREATE INDEX idx_outbox_unprocessed ON outbox_messages (created_at) WHERE processed_at IS NULL;
```

### Детальна інженерна семантика полів таблиці:
- `id`: Автоматично зростаючий первинний ключ типа `BIGSERIAL` для точного впорядкування подій.
- `aggregate_type`: Назва типу доменного агрегату (`DeviceTwin`, `User`, `Home`).
- `aggregate_id`: Унікальний ідентифікатор конкретного екземпляра агрегату (`lock_front_door`).
- `event_type`: Назва доменної події (`LockUnlockCommanded`, `LockLockedCommanded`).
- `payload`: Вміст доменної події у форматі `JSONB`.
- `trace_id` та `span_id`: Збережені атрибути W3C Trace Context для забезпечення наскрізного трасування при зчитуванні події з WAL-логу.
- `processed_at`: Часова мітка підтвердження доставки події в Kafka. Початкове значення `NULL`.
- `retry_count`: Лічильник спроб відправки у разі тимчасових мережевих помилок.

Процес CDC (Debezium) зчитує нові рядки з WAL-логу PostgreSQL. Після успішного підтвердження публікації події у Kafka процес оновлює поле `processed_at = NOW()`. Періодичний фоновий процес (Cron Job) видаляє оброблені рядки, вік яких перевищує 24 години, запобігаючи неконтрольованому розростанню дискового простору бази даних.

## 5. Специфікація MQTT-топіків та payload для IoT-краю

Взаємодія між хмарним брокером та фізичним пристроєм здійснюється через захищений протокол MQTT v5.0 поверх mTLS.

### Ієрархія топіків MQTT:

- **Канал команд (Cloud -> Device):** `dh/v1/homes/{home_id}/devices/{device_id}/command` (QoS 1)
- **Канал підтверджень (Device -> Cloud):** `dh/v1/homes/{home_id}/devices/{device_id}/ack` (QoS 1)
- **Канал телеметрії (Device -> Cloud):** `dh/v1/homes/{home_id}/devices/{device_id}/telemetry` (QoS 0)

### Формат payload команди (`command`):

```json
{
  "command_id": "cmd_88f7a6b5c4",
  "action": "SET_LOCK_STATE",
  "params": {
    "state": "UNLOCKED"
  },
  "auth": {
    "nonce": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "signature": "3045022100a8f9..."
  },
  "trace": {
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7"
  }
}
```

### Формат payload підтвердження (`ack`):

```json
{
  "command_id": "cmd_88f7a6b5c4",
  "status": "SUCCESS",
  "execution_time_ms": 340,
  "reported_state": {
    "lock_state": "UNLOCKED",
    "bolt_contact": "RETRACTED",
    "battery_level": 88
  },
  "trace": {
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7"
  }
}
```

### Детальні правила використання рівнів QoS (Quality of Service)

- **QoS 0 (At most once):** Використовується виключно для фонової телеметрії (наприклад, періодичний вимір температури або рівня заряду батареї раз на годину). Втрата окремого пакета телеметрії не є критичною для системи.
- **QoS 1 (At least once):** Використовується для всіх мутуючих команд керування (`command`) та підтверджень (`ack`). MQTT-брокер та пристрій зберігають незапідтверджені пакети в енергонезалежній пам'яті й повторюють відправку до отримання `PUBACK`. Це гарантує доставку команд навіть у разі нестабільного Wi-Fi або Cellular-з'єднання.

## 6. Матриця помилок та кодів відповідей

Платформа гарантує трансляцію помилок від найнижчого рівня апаратури до стандартизованих кодів HTTP та gRPC:

| HTTP Status | Внутрішній код помилки | Джерело | Причина винекнення | Рекомендована дія клієнта |
|---|---|---|---|---|
| `400 Bad Request` | `ERR_INVALID_TRACEPARENT` | API Gateway | Синтаксична помилка у W3C Traceparent | Сформувати валідний traceparent за специфікацією |
| `401 Unauthorized` | `ERR_TOKEN_EXPIRED` | Auth Service | Прострочено термін дії JWT access token | Запитати новий токен через Refresh Token |
| `403 Forbidden` | `ERR_INSUFFICIENT_RIGHTS` | OPA Policy | Користувач не має прав на цей будинок або пристрій | Перевірити матрицю прав у налаштуваннях сім'ї |
| `409 Conflict` | `ERR_LOCK_ALREADY_UNLOCKED` | SmartLockService | Замок вже перебуває у затребуваному стані | Оновити локальне відображення стану у UI |
| `429 Too Many Requests` | `ERR_RATE_LIMIT_EXCEEDED` | Gateway Rate Limiter | Перевищено добову або хвилинну квоту викликів | Уповільнити повторні виклики (Exponential Backoff) |
| `504 Gateway Timeout` | `ERR_DEVICE_OFFLINE_TIMEOUT` | MQTT Worker | Пристрій не надіслав `ack` протягом 10 секунд | Повідомити користувача, що пристрій не на зв'язку |

### Детальні алгоритми обробки помилок на клієнті

1. **Обробка `429 Too Many Requests`:** Мобільний застосунок зобов'язаний припинити надсилання викликів і застосувати алгоритм **Exponential Backoff із Jitter**. Початковий інтервал затримки становить `t_0 = 1s`, наступні спроби розраховуються за формулою `t_n = min(t_max, t_0 * 2^n + random_jitter)`.
2. **Обробка `504 Gateway Timeout`:** Отримання статусу 504 не означає, що команда не виконається в майбутньому. Оскільки бажаний стан збережено у `device_twins` у базі даних, команда буде доставлена на замок одразу після його появи в мережі. Застосунок відображає користувачу статус «Запит прийнято, очікується підключення замка».
