# 📜 Еволюція розподіленого простеження: від монолітних логів до OpenTelemetry

Коли весь застосунок працює в одному процесі на одній фізичній машині, з'ясувати шлях виконання запиту не становить труднощів. Системний журнал на кшталт `access.log` або стандартний `syslog` послідовно записує події від моменту надходження HTTP-запиту до формування відповіді. Помилка або затримка локалізується вивченням стектрейсу в межах одного лог-файлу, де часові мітки мають єдине джерело сили — системне годинникове ядро цієї ж машини.

З появою мікросервісних архітектур, асинхронних черг та розподіленого виконання єдина нитка логування розірвалася. Один клієнтський клік на смартфоні перетворився на каскад із десятків взаємодій: від шлюзу до сервісу автентифікації, доменної логіки, брокера повідомлень, баз даних і фізичних IoT-пристроїв. Логи розпалися на тисячі окремих файлів на сотнях серверів, а мережеві затримки та відсутність синхронізації годинників зробили неможливим відновлення послідовності подій за самими лише часовими мітками.

П'ятдесятирічна еволюція інструментарію та стандартів простеження запитів (англ. *request tracing*) простягається від перших ідентифікаторів кореляції в монолітах до сучасного стандарту W3C Trace Context та екосистеми OpenTelemetry, без яких неможливо контролювати складні розподілені системи.

## 1. Доба монолітів: локальний ідентифікатор кореляції

Наприкінці 1990-х років, зі зростанням навантаження на перші веб-платформи та появою базових триланкових архітектур (веб-сервер → сервер застосунків → база даних), розробники вперше зіткнулися з потребою групувати записи логів у межах однієї сесії або одного HTTP-з'єднання. Першим кроком став **ідентифікатор кореляції** (англ. *correlation ID*) — довільний унікальний рядок (UUID або хеш), який інжектувався на вході у веб-сервер (наприклад, Apache HTTP Server або Nginx) і прокидався крізь шари застосунку в межах одного потоку виконання.

```
[2002-04-12 10:14:02.102] [req_4a8f9c] INFO  http_ingress: Incoming POST /login from 192.168.1.10
[2002-04-12 10:14:02.105] [req_4a8f9c] DEBUG auth_service: Validating password hash for user_id=42
[2002-04-12 10:14:02.118] [req_4a8f9c] INFO  db_client:   Query SELECT * FROM users WHERE id=42 (13ms)
[2002-04-12 10:14:02.120] [req_4a8f9c] INFO  http_ingress: 200 OK sent (18ms total)
```

Цей підхід чудово працював, поки моделлю виконання залишався принцип «один запит — один побічний потік» (англ. *thread-per-request*). Контекст запиту зберігався в локальній пам'яті потоку (Thread-Local Storage, TLS), і кожна функція логування автоматично дописувала `req_id` до вихідного рядка.

Проте механіка зазнала краху у двох випадках:
1. **Асинхронний ввід-вивід та event-driven моделі:** коли один потік обробляє сотні паралельних з'єднань через подійні цикли (Event Loop на кшталт Node.js чи Nginx), Thread-Local Storage перестає ділити події за запитами. Контекст плутається, бо той самий потік обробляє фрагменти різних запитів.
2. **Перетин межі мережі:** коли сервіс робить вихідний виклик на іншу машину або кладе повідомлення в чергу, correlation ID втрачається, якщо його явно не серіалізувати в заголовки протоколу (наприклад, HTTP-заголовки або бінарні межі RPC).

## 2. Прорив Google Dapper (2010): концепція спанів та спадковості

У 2010 році інженери Google опублікували фундаментальну статтю *«Dapper, a Large-Scale Distributed Systems Tracing Infrastructure»* (автори: бен Сигельман, Луїз Андре Баррозо та ін.). Dapper заклав теоретичний і практичний фундамент для всього сучасного distributed tracing.

Головним внеском Dapper стало розрізнення двох рівнів ідентифікації:
- **Trace ID (ідентифікатор траси):** глобально унікальний ідентифікатор, який народжується на межі периметра (Edge / API Gateway) і залишається незмінним уздовж усього шляху запиту, незалежно від кількості мікросервісів та черг.
- **Span ID (ідентифікатор спану):** унікальний ідентифікатор атомарного відрізка роботи (наприклад, виконання SQL-запиту, розкодування JWT або виклику по RPC).
- **Parent Span ID (батьківський спан):** посилання на спан, який ініціював поточну операцію. Завдяки цьому сукупність спанів утворює орієнтоване ациклічне дерево (DAG), яке відтворює точну причинно-наслідкову ієрархію викликів.

```
Trace: 4bf92f3577b34da6a3ce929d0e0e4736
├── Span A: HTTP POST /api/v1/locks/unlock (Gateway) [0ms - 445ms]
│   ├── Span B: JWT Verification & OPA Policy [22ms - 32ms]
│   └── Span C: SmartLockService.unlock() [32ms - 50ms]
│       └── Span D: PostgreSQL ACID Transaction [36ms - 48ms]
└── Span E: MQTT Publish & Hardware Motor Ack [50ms - 410ms]
```

### Технічні інновації Dapper:

1. **Непримітність (Low Overhead):** Dapper був спроєктований так, щоб його присутність не знижувала продуктивність основних веб-сервісів. Збір спанів здійснювався поза основним потоком обробки (Out-of-band collection): демон `dapperd` зчитував кругові буфери пам'яті локально і відправляв їх у колонкову базу даних Bigtable.
2. **Адаптивне імовірнісне семплювання (Probabilistic Sampling):** На масштабах Google суцільне простеження кожного запиту створювало б гігабайти телеметричного сміття й споживало б до 15% обчислювальної потужності. Dapper увів імовірнісне семплювання: лише 1 із 10 000 запитів (0.01%) позначався прапорцем `sampled = true`, але для обраних запитів телеметрія збиралася повністю по всьому ланцюгу.

## 3. Поява відкритих систем: Zipkin, Jaeger та війна стандартів

У 2012 році компанія Twitter випустила відкритий аналог Dapper — **Zipkin**, написаний на Java. Zipkin надав зручний веб-інтерфейс для візуалізації «водоспадів» (waterfalls) затримок та збору телеметрії через Thrift / HTTP. Згодом Uber створив **Jaeger** (2015, мова Go), який став стандартом у екосистемі Cloud Native Computing Foundation (CNCF).

Однак у період з 2015 по 2019 рік індустрія зіткнулася з роздробленістю (англ. *vendor lock-in trap*):
- **OpenTracing (2015):** спроба створити вендорсько-незалежний API для трасування. Бібліотека надавала абстрактні інтерфейси, а розробники підключали конкретні вендорські «тримери» (Jaeger Tracer, Zipkin Tracer, Datadog Tracer).
- **OpenCensus (2017):** ініціатива Google та Microsoft, яка об'єднувала простеження та збір метрик в єдиний SDK, але мала власний несумісний API.

Розробники відкритих бібліотек опинилися в глухому куті: щоб зробити HTTP-клієнт або веб-фреймворк простежуваним, доводилося підтримувати обидва конкуруючі стандарти.

## 4. Об'єднання в OpenTelemetry (2019) та стандарт W3C Trace Context (2020)

У травні 2019 року проєкти OpenTracing та OpenCensus офіційно об'єдналися під егідою CNCF у єдиний глобальний стандарт — **OpenTelemetry (OTel)**. OpenTelemetry надав єдину специфікацію API, SDK та збирач (OTel Collector) для трьох головних стовпів спостережуваності: метрик, логів та трас (M-L-T).

Паралельно консорціум W3C опублікував офіційну рекомендацію **W3C Trace Context (2020)**, яка вперше стандартизувала формат HTTP-заголовків для передачі контексту між системами різних виробників.

Стандарт W3C закріпив заголовок `traceparent` наступного формату:

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  │                                │                └─ Trace Flags (01 = sampled)
             │  │                                └─ Parent Span ID (16 hex hex-digit)
             │  └─ Trace ID (32 hex-digit UUID)
             └─ Version (00)
```

Завдяки W3C Trace Context системні компоненти, написані на C++, Go, Java чи Python, а також мережеві проксі (Envoy, Nginx, HAProxy) й брокери повідомлень (Kafka, MQTT) навчилися передавати контекст запиту транзитом, не порушуючи причинно-наслідковий ланцюг.

Сьогодні розподілене простеження — це не окрема розкіш, а фундаментальна властивість програмної архітектури. Кожен запит у системі Digital Homes несе в собі інжектований W3C-контекст, який проходить крізь балансувальники, шлюзи, доменні сервіси, транзакційні outbox-таблиці та брокери повідомлень, гарантуючи повну прозорість виконання від клієнта до фізичного пристрою.
