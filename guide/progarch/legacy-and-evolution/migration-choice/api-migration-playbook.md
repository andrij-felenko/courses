# 📋 Довідник архітектора: Матриця вибору стратегії та чек-лист міграції

Цей довідник містить порівняльну матрицю прийняття рішень, алгоритм вибору стратегії міграції залежно від характеристик системи, граничні значення метрик для автоматичного аварійного відкату (Rollback Triggers), послідовний п'ятифазний чек-лист безпечного переходу великих систем, детальний протокол міграції схем баз даних за патерном Expand & Contract, а також аварійні інструкції (Runbooks).

Головна мета довідника — надати архітектору готовий інструментарій для оцінки ризиків та вибору правильного поєднання стратегій переходу. Вибір стратегії міграції не є одноразовою дією; він вимагає чіткого структурування вимог до цілісності даних, допустимого часу зупинки (DOWNTIME SLA) та спроможності команди контролювати трафік на мережевих межах.

## 1. Повний аналіз та порівняльна матриця стратегій міграції

Вибір стратегії міграції визначає не лише технічний порядок розгортання коду, а й економіку проекту, рівень ризику для бізнесу та когнітивне навантаження на інженерну команду. Кожен із чотирьох патернів — Big Bang, Strangler Fig, Dark Launching та Branch by Abstraction — має свою чітко визначену область ефективного застосування.

Нижче наведено порівняльний аналіз за ключовими інженерними та експлуатаційними критеріями:

| Архітектурний вектор | Big Bang (Одномоментне перемикання) | Strangler Fig Pattern | Dark Launching / Traffic Shadowing | Branch by Abstraction |
| :--- | :--- | :--- | :--- | :--- |
| **Область застосування** | Мережева межа / Вся система | Мережева межа (API Gateway / Ingress) | Мережева межа або сервісна сітка | Внутрішній шов кодової бази |
| **Рівень ризику** | Критично високий (All-or-Nothing) | Низький (Інкрементальний) | Мінімальний (Без впливу на UX) | Низький (Контроль через прапорці) |
| **Точка неповернення (Point of No Return)** | Настає миттєво після старт-запуску | Відсутня (Гнучкий зворотний рух) | Відсутня (Відповіді відкидаються) | Відсутня (До видалення legacy) |
| **Швидкість отримання значень** | Запізніла (Лише в кінці міграції) | Рання (Після першого винесеного роуту) | Дуже рання (На етапі тіньового тесту) | Постійна (Поліпшення в main-гілці) |
| **Вимоги до дублювання даних** | Немає (Одноразова конверсія в зупинці) | Високі (Dual Writes / CDC / Reconciler) | Низькі (Read-only або isolated dry-run) | Залежить від підсистеми |
| **Накладні витрати інфраструктури** | Мінімальні | Середні (API Gateway, Proxy) | Високі (Дублювання 100% трафіку, Diffing) | Нульові (Все в межах процесу) |
| **Складність розробки** | Низька (Без проміжних шарів) | Середня (Маршрутизація, контракти) | Висока (Diff-engine, mock side effects) | Низька / Середня (Створення Seam) |

### Детальна розшифровка параметрів порівняння

1. **Точка неповернення (Point of No Return):** При виборі Big Bang точка неповернення настає в момент, коли нова система приймає перший мутуючий запит від користувача. Повернення на стару систему стає неможливим без втрати нових даних. При Strangler Fig та Branch by Abstraction точка неповернення відтерміновується до моменту фінального демонтажу legacy-коду.
2. **Вимоги до синхронізації стану:** Big Bang не вимагає паралельного дублювання даних, але вимагає одноразової атомарної конверсії всієї СУБД. Strangler Fig вимагає створення безперервних конвеєрів Change Data Capture (CDC) або подвійного запису з реконсиляторами.
3. **Накладні витрати на інфраструктуру:** Dark Launching вимагає подвоєння обчислювальних потужностей (процесорів, пам'яті, мережевої смуги) для обробки продуктивного та тіньового потоків трафіку одночасно.

## 2. Покроковий алгоритм прийняття рішення про стратегію

Для вибору оптимальної комбінації стратегій використовуйте наступний деревоподібний алгоритм оцінки. Основні критерії вибору — наявність стану (Statefulness), вимоги до безперервності роботи 24/7 та наявність чітких мережевих меж або внутрішніх інтерфейсів у коді.

```text
               [Аналіз межі зміни]
                      │
       ┌──────────────┴──────────────┐
  [Внутрішній модуль коду]     [Мережевий сервіс / API]
       │                             │
 [Branch by Abstraction]      [Чи є стан / СУБД?]
                                     │
                      ┌──────────────┴──────────────┐
                  [Stateless]                   [Stateful]
                      │                             │
             [Strangler Fig]           [Чи можливе безперервне дублювання?]
                                                    │
                                     ┌──────────────┴──────────────┐
                                   [Так]                          [Ні]
                                     │                             │
                         [Strangler Fig + CDC]          [Вікно обслуговування?]
                                                                   │
                                                    ┌──────────────┴──────────────┐
                                                  [Так]                          [Ні]
                                                    │                             │
                                              [Big Bang]               [Розщеплення домену]
```

Оцінка за цим алгоритмом дозволяє швидко відсіяти завідомо небезпечні рішення (наприклад, застосування Big Bang до банківського або IoT-ядра зі станом) і підібрати комбіновану стратегію.

### Пояснення розгалужень алгоритму

- **Внутрішній модуль коду:** Якщо функціонал знаходиться всередині одного процесу (наприклад, заміна бібліотеки розрахунку тарифів у моноліті), застосовується Branch by Abstraction.
- **Stateless мережевий сервіс:** Якщо сервіс не має власної бази даних, застосовується Strangler Fig із канарейковим перемиканням трафіку на API Gateway.
- **Stateful система з безперервним дублюванням:** Застосовується комбінація Strangler Fig + Change Data Capture (CDC на основі Debezium) для асинхронної синхронізації бази даних.
- **Stateful система без можливості дублювання:** Якщо дублювання даних неможливе з технічних причин, перевіряється наявність допустимого вікна зупинки (Downtime Window). Якщо вікно є — допускається Big Bang; якщо вікна немає — домен розділяється на дрібніші сутності.

## 3. Протокол міграції схем баз даних (Expand & Contract Pattern)

Найскладнішим елементом міграції стан-залежних систем є зміна структури реляційних або документальних баз даних без зупинки роботи сервісу. Пряме видалення або перейменування колонок в SQL СУБД у продуктивному середовищі негайно призводить до збоїв у працюючих екземплярах моноліту.

Для безпечної міграції СУБД застосовується трифазний патерн **Expand & Contract (Розширення та Скорочення)**:

### Фаза 1. Expand (Розширення бази даних)
База даних розширюється новими колонками або таблицями без видалення старих. Старий та новий код можуть співіснувати одночасно:
- Додається нова колонка `phone_v2` поруч із `phone`.Стара колонка залишається недоторканою.
- До бази даних додається тригер СУБД або Change Data Capture (CDC), який при записі у `phone` автоматично копіює значення у `phone_v2`.
- Код додатка розгортається у стан, де він вміє читати з `phone_v2`, але при її відсутності використовує значення з `phone`.

### Фаза 2. Transition (Перехідний період та подвійний запис)
- Весь додаток переводиться на запис у нову колонку `phone_v2` та читання з `phone_v2`.
- Запускається фоновий скрипт міграції історичних даних (Backfill Data Migrator), який трансформує всі старі записи з `phone` у `phone_v2` для тих рядків, де нове поле ще не заповнено.
- Проводиться перевірка цілісності: реконсилятор перевіряє, що `COUNT(*) WHERE phone_v2 IS NULL` дорівнює нулю.

### Фаза 3. Contract (Скорочення та зачистка)
- Видаляється підтримка старої колонки `phone` у коді застосунку.
- Видаляється застарілий тригер синхронізації.
- В окремій плановій міграції СУБД колонка `phone` випускається з таблиці (`ALTER TABLE users DROP COLUMN phone`).

Цей підхід забезпечує 100% зворотну сумісність на всіх етапах розгортання та гарантує відсутність блокувань таблиць у СУБД.

## 4. Граничні значення метрик та автоматичні тригери відкату (Rollback Triggers)

Під час канарейкового переключення трафіку або активації тіньового дублювання автоматизована система моніторингу (Prometheus / Grafana / Datadog) має безперервно обчислювати ключові метрики здоров'я. Якщо будь-яка з метрик виходить за межі безпечного порогу, спрацьовує автоматичний аварійний вимикач (Circuit Breaker Rollback), який миттєво повертає 100% трафіку на legacy-систему без участі людини.

Нижче наведено нормативні граничні значення для критичних сервісів:

| Показник / Метрика | Порогове значення тригера відкату | Дія системи при спрацюванні |
| :--- | :--- | :--- |
| **Error Rate Ratio (5xx/4xx)** | `> 0.05%` відхилення від базлайну legacy | Негаційне скидання ваги трафіку нового сервісу до `0%`. |
| **p99 Latency Delta** | `> 50 ms` уповільнення відносно legacy | Автоматичний перехід на legacy; аналіз профілю CPU/пам'яті. |
| **Diff Engine Mismatch Rate** | `> 0.01%` непогоджених відповідей | Зупинка просування вагового коефіцієнта; генерація alert. |
| **DB Replication Lag (CDC)** | `> 1000 ms` для primary sync | Зупинка переключення нових користувачів на нове сховище. |
| **Circuit Breaker Trip Rate** | `> 3` трипи за 5 хвилин | Блокування перемикача Feature Flag на користь legacy-блоку. |

### Деталізація реакцій автоматики відкату

1. **Error Rate Ratio:** Автоматичний скрипт Prometheus Alertmanager порівнює відсоток HTTP 5xx помилок нового сервісу з плаваючим базлайном legacy-системи за останні 15 хвилин. При перевищенні порогу 0.05% API Gateway автоматично встановлює ваговий коефіцієнт нового сервісу в `0`.
2. **p99 Latency Delta:** Уповільнення 99-го перцентилю відповіді нового сервісу на понад 50 мс свідчить про проблему з пул-з'єднаннями СУБД, Garbage Collection або невиявлені витоки пам'яті. Автоматика повертає трафік на legacy-систему.
3. **Diff Engine Mismatch Rate:** При канарейковому або тіньовому тесті відсоток відмінностей у структурах JSON/Protobuf відповідей не повинен перевищувати 0.01%. Будь-яке більше розходження вказує на дефект у бізнес-логіці нового сервісу.

### Приклад PromQL-запитів для контролю канарейкового перемикання

Для автоматичного відстеження здоров'я нового сервісу в Prometheus використовуються наступні PromQL-вирази:

```promql
# 1. Відсоток помилок 5xx нового сервісу відносно загального трафіку
sum(rate(http_requests_total{job="new-telemetry-service", status=~"5.."}[5m]))
/
sum(rate(http_requests_total{job="new-telemetry-service"}[5m])) * 100 > 0.05

# 2. Різниця p99 латентності між New та Legacy сервісами (у секундах)
(
  histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{job="new-telemetry-service"}[5m])) by (le))
  -
  histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{job="legacy-monolith"}[5m])) by (le))
) > 0.050
```

## 5. Чек-лист 5-фазного безпечного переходу (Migration Execution Playbook)

Послідовне виконання цього чек-листа забезпечує мінімізацію ризиків на всіх етапах життєвого циклу міграції — від початкового огородження до остаточного видалення застарілого коду.

### Фаза 1. Підготовка та створення Огородження (Days 1–14)
- [ ] Виділено мережеву межу або внутрішній шов (API Gateway або C++ / Go Interface).
- [ ] Реалізовано характеристичні тести на існуючу поведінку legacy-системи.
- [ ] Налаштовано прокидання скрізного Correlation ID крізь усі компоненти.
- [ ] Оформлено ADR (Architecture Decision Record) із визначенням меж міграції та критеріїв успіху.
- [ ] Створено базові графіки моніторингу в Grafana для зіставлення показників Legacy та New.

### Фаза 2. Тіньове випробування (Dark Launching & Shadowing) (Days 15–30)
- [ ] Розгорнуто новий сервіс у продакшн-середовищі без доступу live-користувачів.
- [ ] Налаштовано асинхронне дублювання трафіку на Proxy/Service Mesh рівні.
- [ ] Ізольовано побічні ефекти (Email, SMS, платежі переведено в Mock/Dry-Run режим).
- [ ] Запущено Diff Engine для порівняння JSON/Protobuf відповідей.
- [ ] Усунуто всі виявлені розходження у бізнес-логіці та форматах даних.
- [ ] Проведено стрес-тестування нового сервісу під 100% дубльованого навантаження.

### Фаза 3. Синхронізація стану та підготовка даних (Days 31–45)
- [ ] Налаштовано Change Data Capture (CDC на основі Debezium/Kafka) зі старої БД у нову.
- [ ] Проведено первинне заповнення (Backfill) історичних даних з перевіркою контрольних сум.
- [ ] Перевірено відсутність розходження даних за допомогою фонового реконсилятора (Data Drift Reconciler).
- [ ] Налаштовано зворотну синхронізацію даних для забезпечення 100% зворотного відкату при необхідності.

### Фаза 4. Канарейкове перемикання (Canary Traffic Cutover) (Days 46–60)
- [ ] Переключено 1% live-трафіку (або внутрішніх тестових користувачів) на новий сервіс.
- [ ] Перевірено відсутність аномалій у логах та метриках протягом 24 годин.
- [ ] Послідовне підвищення ваги трафіку за сіткою: `1% → 5% → 25% → 50% → 100%`.
- [ ] Перевірено готовність чергової інженерної зміни до ручного аварійного відкату.

### Фаза 5. Демонтаж та очищення legacy (Days 61–75)
- [ ] Legacy-система переведена в режим спостереження на 7–14 днів під 0% трафіку.
- [ ] Видалено асинхронні дзеркала трафіку та Diff Engine.
- [ ] Видалено застарілі Feature Flags, конфігураційні перемикачі та legacy-код з main-гілки.
- [ ] Зупинено інфраструктурні ресурси легасі-моноліту (сервери, застарілі СУБД).
- [ ] Оновлено C4-діаграми та документацію платформи.

## 6. Аварійні інструкції відкату (Emergency Rollback Runbooks)

При виникненні непередбачуваної ситуації під час розгортання або канарейкового перемикання черговий інженер повинен дотримуватися чіткої послідовності дій для відновлення стабільності платформи.

### Runbook A. Аварійний відкат канарейкового трафіку на API Gateway

1. **Ідентифікація проблеми:** Grafana фіксує спайк 5xx помилок або p99 латентності на новому сервісі.
2. **Виконання команди відкату:** Черговий інженер виконує CLI-команду скидання ваги трафіку на API Gateway:
   ```bash
   kubectl exec -it gateway-control-plane -- gateway-cli set-weight --route=telemetry --legacy=100 --new=0
   ```
3. **Верифікація:** Перевірити за графіками Grafana, що 100% трафіку повернулося на legacy-моноліт і показники помилок стабілізувалися.
4. **Пост-мортем:** Зберегти логи нового сервісу та трассировки Jaeger за період збою для подальшого аналізу.

### Runbook B. Аварійний відкат Branch by Abstraction всередині коду

1. **Ідентифікація проблеми:** Логи моноліту DH показують винятки або некоректні розрахунки у новому модулі тарифів.
2. **Перемикання Feature Flag:** Зміна прапорця у системі конфігурації (Consul/Etcd або Feature Flag Provider) без перезапуску процесів:
   ```bash
   curl -X POST http://config-service/v1/flags/use_new_tariff_engine -d '{"enabled": false}'
   ```
3. **Верифікація:** Атомарний перемикач `TariffServiceBoundary` миттєво переводить усі нові обчислення на `LegacyTariffCalculator`.
