# 🧮 Математична модель окупності платформи

Побудова внутрішньої платформи розробки (англ. *Internal Developer Platform, IDP*) та створення виділеної платформної команди є фундаментальним фінансовим та організаційним рішенням. Багато організацій припускаються фатальної архітектурної помилки, сприймаючи платформну інженерію як абсолютне благо без урахування її чистої економічної ефективності. Ця вставка формалізує математичну модель окупності платформи, виводить умову точки рівноваги (англ. *break-even threshold*) та кількісно описує штраф за передчасну абстракцію.

## Параметри системи та змінні моделі

Для побудови суворої математичної моделі, яка враховує як прямооплачуваний робочий час, так і непрямі втрати від затримок, введемо такий набір параметрів та змінних:

- `N_s` — кількість продуктових (stream-aligned) команд у компанії.
- `E_s` — середня кількість інженерів у кожній продуктовій команді (типово `E_s ∈ [4, 8]`).
- `W_s` — середня повна вартість людино-години продуктового інженера (з урахуванням заробітної плати, податків, накладних витрат та забезпечення робочого місця, $/год).
- `T_infra` — частка робочого часу продуктового інженера, яка витрачається на рутинні інфраструктурні задачі (написання Dockerfile, маніфестів Kubernetes, конфігурацій Terraform, налаштування CI/CD та траблшутинг мереж) за відсутності виділеної платформи (`T_infra ∈ [0.20, 0.45]`).
- `N_p` — кількість інженерів у виділеній платформній команді.
- `W_p` — середня вартість людино-години платформного інженера ($/год).
- `E_reduce` — коефіцієнт ефективності платформи: частка рутинного інфраструктурного часу, яку платформа успішно усуває завдяки самообслуговуванню та готовим асфальтованим шляхам (Golden Paths) (`E_reduce ∈ [0.60, 0.85]` для зрілої платформи).
- `C_friction` — штраф за передчасне тертя (англ. *premature friction tax*): додаткові затримки й витрати часу продуктових інженерів на розбір нестабільних, недокументованих або жорстких абстракцій незрілої платформи.
- `H_year` — кількість робочих годин на рік на одного інженера (типово прийнято `H_year = 1920` годин для стандартного п'ятиденного робочого тижня).

## Базова вартість розробки без платформи

За відсутності виділеної платформи кожна продуктова команда виконує повний спектр інфраструктурних задач самостійно у класичному режимі «You build it, you run it». Сумарні річні витрати компанії на утримання цього інфраструктурного навантаження `C_base` визначаються як добуток кількості інженерів на вартість години та частку інфраструктурного часу:

```
C_base = N_s · E_s · W_s · T_infra · H_year
```

Наприклад, якщо компанія має `N_s = 3` продуктивні команди по `E_s = 5` інженерів (`W_s = 50` $/год), і кожен інженер витрачає `T_infra = 0.30` (30% свого робочого часу) на інфраструктурний рутинний траблшутинг та підготовку середовищ:

```
C_base = 3 · 5 · 50 · 0.30 · 1920
       = 15 · 50 · 0.30 · 1920
       = 432 000 $ на рік
```

Ці 432 000 $ являють собою прихований «інфраструктурний податок» або оверхед розробки, який компанія щороку сплачує у вигляді втраченого часу продуктових інженерів, який міг бути спрямований на створення бізнес-функціональності.

## Сумарні витрати при впровадженні платформної команди

При створенні виділеної платформної команди сумарні витрати компанії `C_platform` перестають бути монолітними і складаються з трьох чітко розмежованих компонентів:
1. Прямі витрати на утримання платформної команди `C_team`.
2. Залишкові інфраструктурні витрати продуктових команд `C_rem` (оскільки жодна платформа не усуває 100% інфраструктурного контексту).
3. Штраф за передчасне тертя `C_friction`, який виникає через незрілість абстракцій та бюрократичні затримки.

Обчислимо кожен компонент моделі послідовно:

```
C_team = N_p · W_p · H_year

C_rem = N_s · E_s · W_s · T_infra · (1 - E_reduce) · H_year

C_friction = N_s · E_s · W_s · T_delay · H_year
```

де `T_delay` — частка робочого часу, втрачена продуктовим інженером на очікування виконання ручних тікетів платформною командою або обхід некоректно спроєктованих обгорток.

Сумарне підсумкове рівняння витрат організації з платформою має вигляд:

```
C_platform
= C_team + C_rem + C_friction
= H_year · [ N_p·W_p + N_s·E_s·W_s·T_infra·(1 - E_reduce) + N_s·E_s·W_s·T_delay ]
```

## Чистий економічний ефект та критерій окупності

Інвестиція в створення платформи є фінансово та архітектурно виправданою для організації тоді й лише тоді, коли чистий економічний ефект `ΔV` є суворо додатним (`ΔV > 0`):

```
ΔV = C_base - C_platform > 0
```

Розкриємо та спростимо цей вираз, підставивши виведені формули для `C_base` та `C_platform`:

```
ΔV = N_s · E_s · W_s · T_infra · H_year
     - H_year · [ N_p·W_p + N_s·E_s·W_s·T_infra·(1 - E_reduce) + N_s·E_s·W_s·T_delay ]

= H_year · [ N_s·E_s·W_s·T_infra · (1 - (1 - E_reduce)) - N_p·W_p - N_s·E_s·W_s·T_delay ]

= H_year · [ N_s·E_s·W_s · (T_infra · E_reduce - T_delay) - N_p·W_p ]
      [винесено спільні множники N_s·E_s·W_s та N_p·W_p]
```

З виведеної формули випливає сувора умова, за якої чистий ефект є додатним (`ΔV > 0`):

```
N_s · E_s · W_s · (T_infra · E_reduce - T_delay) > N_p · W_p
```

Звідси ми можемо вивести критичне значення кількості продуктових команд `N_{s,crit}`, при якому інвестиції у платформну команду повертають нульовий чистий прибуток (точка рівноваги або break-even point):

```
N_{s,crit} = (N_p · W_p) / [ E_s · W_s · (T_infra · E_reduce - T_delay) ]
```

Аналіз отриманого рівняння показує, що критичний поріг `N_{s,crit}` прямо пропорційний витратам на платформну команду `N_p · W_p` і обернено пропорційний ефективності економії часу продуктових команд.

## Порівняльний числовий аналіз двох сценаріїв розвитку

### Сценарій А: Зріла платформа при достатньому масштабі організацій (N_s = 6)

Припустимо, що компанія має 6 продуктових команд (`N_s = 6`, `E_s = 5` інженерів у команді, `W_s = 50` $/год) та створює невелику, але висококваліфіковану платформну команду з 2 інженерів (`N_p = 2`, `W_p = 60` $/год). Платформа спроєктована якісно за принципом Thinnest Viable Platform (`E_reduce = 0.75`, `T_delay = 0.02`):

```
Обчислимо чистий виграш на одну продуктову команду у грошовому вираженні за одну годину:
S_unit = E_s · W_s · (T_infra · E_reduce - T_delay)
       = 5 · 50 · (0.30 · 0.75 - 0.02)
       = 250 · (0.225 - 0.02)
       = 250 · 0.205
       = 51.25 $/год

Вартість утримання платформної команди за одну годину:
P_unit = N_p · W_p = 2 · 60 = 120 $/год

Критична точка рівноваги N_{s,crit}:
N_{s,crit} = 120 / 51.25 ≈ 2.34 команди

Оскільки фактична кількість команд N_s = 6 значно перевищує поріг 2.34, обчислимо сумарний річний чистий ефект ΔV:
ΔV = (6 · 51.25 - 120) · 1920
   = (307.50 - 120) · 1920
   = 187.50 · 1920
   = 360 000 $ на рік
```

У даному сценарії платформа забезпечує **чисту річну економію у 360 000 $**, паралельно вивільняючи інженерну спроможність для прискорення доставки нових продуктів.

### Сценарій Б: Передчасна платформа при малому масштабі (N_s = 2)

Розглянемо протилежну ситуацію: стартап із 2 продуктовими командами (`N_s = 2`, `E_s = 4`, `W_s = 50` $/год). Керівництво вирішує завчасно побудувати повноцінну платформу і наймає 3 платформних інженерів (`N_p = 3`, `W_p = 65` $/год). Через передчасність і жорсткість абстракцій продуктові команди витрачають багато часу на боротьбу з її незавершеним функціоналом та очікування у тікетах (`E_reduce = 0.25`, `T_delay = 0.12`):

```
S_unit = 4 · 50 · (0.30 · 0.25 - 0.12)
       = 200 · (0.075 - 0.12)
       = 200 · (-0.045)
       = -9 $/год  (негативна ефективність платформи)

P_unit = 3 · 65 = 195 $/год

Обчислимо річний чистий ефект ΔV:
ΔV = (2 · (-9) - 195) · 1920
   = (-18 - 195) · 1920
   = -213 · 1920
   = -408 960 $ на рік
```

Спроба створити передчасну платформу в даному випадку призвела до **прямих збитків організації у розмірі понад 408 000 $ на рік**, суттєво уповільнивши швидкість релізів продуктових фіч.

## Закони та висновки математичної моделі

1. **Закон нелінійного масштабування `N_s`:** Фіксовані витрати на платформну команду `N_p · W_p` діляться між усіма споживачами платформи. Досягнення порогу `N_{s,crit}` є необхідною умовою виправданості виділеного платформного підрозділу.
2. **Критичність фактора тертя `T_delay`:** Якщо незріла або бюрократична платформа створює затримки, які перевищують виграш від автоматизації (`T_delay > T_infra · E_reduce`), показник чистой економії `S_unit` стає від'ємним, перетворюючи платформу на джерело руйнування вартості.
3. **Принцип мінімізації TVP:** На ранніх етапах розвитку компанія зобов'язана утримувати `N_p` на найнижчому можливому рівні (використовуючи легкі шаблони та розшерингові IaC-модулі), підвищуючи `E_reduce` без роздування фіксованих витрат.
