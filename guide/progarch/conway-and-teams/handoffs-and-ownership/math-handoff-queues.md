# 🧮 Математика черг і накопичення затримок при передачах

Затримка доставки функціоналу в розробці програмного забезпечення рідко росте лінійно від обсягу написаного коду. Повсюдно спостерігається нелінійний ефект: команда з п'яти інженерів створює нову фічу за 4 години чистої роботи, але кінцевий користувач отримує її в продакшні лише через 6 тижнів. Головний внесок у загальний термін доставки (Lead Time) дає не безпосередня інженерна праця над задачею (`T_work`), а час очікування в міжкомандних чергах (`T_wait`).

У цьому матеріалі ми розберемо математичні моделі теорії масового обслуговування, закони накопичення помилок через втрату контексту та математичне обґрунтування зменшення розміру партій (Batch Size).

## 1. Модель накопичення втрат контексту та повторної переробки

Розглянемо потік створення цінності як послідовність з `N` функціональних етапів (наприклад: Бізнес-аналіз → Бекенд-розробка → DBA-міграція → QA-тестування → SecOps-сертифікація → Release Ops).

На кожному етапі `i` відбуваються два паралельні процеси: виконання роботи тривалістю `T_base,i` та передача артефакту наступній команді. Ручна передача через документацію або тикет-систему неминуче супроводжується деградацією тактичного (неявного) контексту. 

Неявний контекст охоплює архітектурні припущення, вихідні межі домену, приховані залежності та усвідомлені компроміси, які неможливо повністю формалізувати у вигляді тексту. Позначимо частку втрати контексту при одній ручній передачі через `δ`, де `0 < δ < 1`. Залишкова частка розуміння системи `C(n)` після `n` послідовних передач визначається експоненційним законом спадання:

```
C(n) = C₀ · (1 - δ)ⁿ
```

де `C₀ = 1.0` — початковий повний контекст автора ідеї. 

При оцінці емпіричного коефіцієнта втрати `δ = 0.4` (40% втрати деталей розуміння при ручній передачі тикета між колодязями) залишкова частка контексту на різних етапах становить:

```
C(0) = 1.000             [початковий контекст автора]
C(1) = 1.0 · 0.60 = 0.600 [після 1 передачі: 60% контексту]
C(2) = 1.0 · (0.60)² = 0.360 [після 2 передач: 36% контексту]
C(3) = 1.0 · (0.60)³ = 0.216 [після 3 передач: 21.6% контексту]
C(4) = 1.0 · (0.60)⁴ = 0.1296 [після 4 передач: 13% контексту]
C(5) = 1.0 · (0.60)⁵ = 0.0777 [після 5 передач: менше 8% контексту!]
```

Втрата контексту породжує дефекти розуміння, які змушують команди повертати задачу на попередній етап (повторна переробка або «квитковий теніс»). Ввівши ймовірність виникнення дефекту `P_err(n)` як функцію від втраченого контексту:

```
P_err(n) = 1 - e^( - α · (1 - C(n)) )
```

де `α` — коефіцієнт складності домену, ми отримуємо математичне пояснення того, чому на 4-й та 5-й передачах кількість повернень задачі назад росте експоненційно. Підсумковий реальний час чистої роботи `T_work,i` з урахуванням повторних ітерацій виражається формулою:

```
T_work,i = T_base,i / (1 - P_err(i))
```

Отже, навіть без урахування черг очікування, втрата контексту при 5 ручних передачах збільшує чистий час виконання роботи у 2.5–4 рази за рахунок виправлення непорозумінь та повторного уточнення вимог.

## 2. Математичне виведення наближення Кінґмана для черг очікування

Найбільшим руйнівником швидкості доставки є час перебування задачі в міжкомандних чергах. У теорії масового обслуговування міжкомандний колодязь (наприклад, окрема команда DBA чи Security) моделюється як система обслуговування G/G/1 (довільний розподіл надходження задач та довільний розподіл часу обслуговування з одним сервером).

Математичне виведення наближення Кінґмана спирається на аналіз часу очікування в системі M/G/1 за формулою Поллачека-Хінчина (Pollaczek-Khinchine formula). У системі M/G/1 із пуассонівським приходом задач (з параметром `λ`) та довільним часом обслуговування із середнім `τ = 1/μ` і дисперсією `σ_v²`, середній час очікування в черзі `W_q` дорівнює:

```
W_q = ( λ · (τ² + σ_v²) ) / ( 2 · (1 - ρ) )
    = ( ρ · τ · (1 + c_v²) ) / ( 2 · (1 - ρ) )      [оскільки λ = ρ / τ, c_v = σ_v / τ]
```

Джон Кінґман (John Kingman) у 1961 році узагальнив цю формулу для систем G/G/1, де прихід задач також не є пуассонівським, а має довільну дисперсію `σ_a²` з коефіцієнтом варіації `c_a = σ_a / μ_a`. Це дало відоме наближення Кінґмана (Kingman's formula):

```
W_q ≈ ( (c_a² + c_v²) / 2 ) · ( ρ / (1 - ρ) ) · τ
```

Позначення та фізична інтерпретація параметрів:
- `ρ` (утилізація) — коефіцієнт завантаженості команди роботою, `ρ = λ / μ`, де `λ` — середня швидкість прибуття нових задач у беклог, `μ` — середня швидкість виконання задач командою (`0 ≤ ρ < 1`).
- `τ` — середній чистий час виконання однієї задачі (`τ = 1 / μ`).
- `c_a` — коефіцієнт варіації інтервалів надходження задач (`c_a = σ_a / μ_a`), який характеризує нерівномірність потоку викликів (наприклад, раптові напливи тикетів перед кінцем спринту або релізом).
- `c_v` — коефіцієнт варіації часу виконання задач (`c_v = σ_v / τ`), який вимірює розкид складності задач (від дрібних правок до важких архітектурних рефакторингів).

Ключовим елементом формули є нелінійний мультиплікатор утилізації `M(ρ)`:

```
M(ρ) = ρ / (1 - ρ)
```

Прослідкуємо поведінку `M(ρ)` та відповідного часу очікування при виконанні задачі з середнім часом обробки `τ = 2` дні та помірній варіативності `c_a = c_v = 1.0` (отже варіаційний множник `(c_a² + c_v²) / 2 = 1.0`):

```
При ρ = 0.30 (30% утилізації):
M(0.30) = 0.30 / 0.70 = 0.43  →  W_q = 0.43 · 2 = 0.86 днів очікування

При ρ = 0.50 (50% утилізації):
M(0.50) = 0.50 / 0.50 = 1.00  →  W_q = 1.00 · 2 = 2.00 днів очікування

При ρ = 0.70 (70% утилізації):
M(0.70) = 0.70 / 0.30 = 2.33  →  W_q = 2.33 · 2 = 4.66 днів очікування

При ρ = 0.80 (80% утилізації):
M(0.80) = 0.80 / 0.20 = 4.00  →  W_q = 4.00 · 2 = 8.00 днів очікування

При ρ = 0.85 (85% утилізації):
M(0.85) = 0.85 / 0.15 = 5.67  →  W_q = 5.67 · 2 = 11.34 днів очікування

При ρ = 0.90 (90% утилізації):
M(0.90) = 0.90 / 0.10 = 9.00  →  W_q = 9.00 · 2 = 18.00 днів очікування

При ρ = 0.95 (95% утилізації):
M(0.95) = 0.95 / 0.05 = 19.00 →  W_q = 19.00 · 2 = 38.00 днів очікування!
```

Цей розрахунок наочно пояснює парадокс завантаженості: коли менеджмент домагається 95% утилізації інженерів, очікування задачі в черзі зростає з 8 днів до 38 днів. Невелике підвищення навантаження на 15% спричиняє п'ятикратне уповільнення системи.

Для багатьох інженерних команд із багатьма виконатилями (система G/G/m з `m` паралельними інженерами) наближення Кінґмана модифікується виразом:

```
W_q(m) ≈ ( (c_a² + c_v²) / 2 ) · ( ρ^(√(2·(m+1)) - 1) / (m · (1 - ρ)) ) · τ
```

Хоча наявність `m` паралельних виконавців зсуває точку вибуху черги, нелінійне зростання при `ρ → 1.0` залишається неминучим законам математики.

## 3. Математичний аналіз багатокаскадного ланцюга передач

Розглянемо систему розробки, де реалізація фічі вимагає послідовного проходження крізь `N = 4` спеціалізовані команди:
1. Команда розробки бекенду (`τ₁ = 3` дні, `ρ₁ = 0.75`)
2. Команда адміністраторів баз даних DBA (`τ₂ = 1` день, `ρ₂ = 0.90`)
3. Окрема команда тестувальників QA (`τ₃ = 2` дні, `ρ₃ = 0.85`)
4. Команда інфраструктури та безпеки Ops/Sec (`τ₄ = 1` день, `ρ₄ = 0.92`)

Припустимо помірну варіативність процесів `(c_a² + c_v²) / 2 = 1.2` на кожному етапі.

Обчислимо час очікування `W_q,i` для кожної ланки каскаду:

```
Ланка 1 (Бекенд):
W_q,1 = 1.2 · (0.75 / (1 - 0.75)) · 3
      = 1.2 · 3.00 · 3 = 10.8 днів

Ланка 2 (DBA):
W_q,2 = 1.2 · (0.90 / (1 - 0.90)) · 1
      = 1.2 · 9.00 · 1 = 10.8 днів

Ланка 3 (QA):
W_q,3 = 1.2 · (0.85 / (1 - 0.85)) · 2
      = 1.2 · 5.67 · 2 = 13.6 днів

Ланка 4 (Ops/Sec):
W_q,4 = 1.2 · (0.92 / (1 - 0.92)) · 1
      = 1.2 · 11.50 · 1 = 13.8 днів
```

Сумарний час перебування в чергах очікування:

```
T_wait_total = ∑ [i=1..4] W_q,i
             = 10.8 + 10.8 + 13.6 + 13.8 = 49.0 днів
```

Сумарний час чистої роботи над фічею:

```
T_work_total = ∑ [i=1..4] τ_i
             = 3 + 1 + 2 + 1 = 7.0 днів
```

Підсумковий Lead Time та ефективність потоку (Flow Efficiency):

```
T_total = T_work_total + T_wait_total = 7.0 + 49.0 = 56.0 днів

Flow_Efficiency = T_work_total / T_total
                = 7.0 / 56.0 = 0.125  (12.5%)
```

Результат обчислення вражає: у колодязній організації з чотирма передачами фіча перебуває у стані корисної обробки лише 12.5% часу свого життя. Більше ніж 87% часу (49 днів із 56) фіча не рухається вперед, а чекає в чергах перевантажених спеціалізованих команд.

## 4. Закон Літтла та математика зменшення розміру партій (Batch Size)

Зв'язок між кількістю незавершеної розробки (Work In Progress, WIP), часом очікування та швидкістю проходження задач описується **Законом Літтла** (Little's Law):

```
WIP = TH · Lead_Time
```

де `TH` (Throughput) — пропускна здатність системи (кількість завершених задач за одиницю часу).

Перепишемо закон для визначення часу доставки:

```
Lead_Time = WIP / TH
```

Якщо організація передає роботи великими партіями (наприклад, гігантські релізи раз на квартал чи пулл-реквести на 5000 рядків коду), значення `WIP` стрибає у рази. Зростання `WIP` безпосередньо збільшує `Lead_Time`.

Зменшення розміру партії (Batch Size) діє на затримки двома математичними шляхами:
1. **Зниження варіативності `c_v`**: Малі PR (100–200 рядків коду) мають передбачувану складність. Зменшення `c_v` з 2.0 до 0.5 у формулі Кінґмана зменшує варіаційний множник `(c_a² + c_v²) / 2` з 2.5 до 0.625 (скорочення очікування в 4 рази!).
2. **Скорочення часу обробки `τ`**: Перевірка малого PR триває хвилин, а не днів.

## 5. Математичний ефект реорганізації у Stream-Aligned команди

Перехід від колодязної структури до **Stream-Aligned команд** та **Self-Service платформи** змінює структуру рівняння:
- Кількість ручних міжкомандних передач скорочується з `N = 4` до `N = 1` (команда володіє фічею наскрізно від UI до DB).
- Замість ручних очікувань у чергах DBA та Ops, середовище виділяється через автоматичний платформений API з утилізацією `ρ_platform ≈ 0.05` та високим паралелізмом, де `W_platform ≈ 0`.

Обчислимо новий Lead Time для тої самої фічі:

```
T_work_stream = 7.0 днів (наскрізна робота однієї мультидисциплінарної команди)
W_q_stream    = 1.2 · (0.70 / (1 - 0.70)) · 7.0
              = 1.2 · 2.33 · 7.0 = 19.57 днів  (зауважте: черга лише одна!)
W_platform    = 0.01 днів (автоматичні CI/CD перевірки та IaC)

T_total_new = 7.0 + 19.57 + 0.01 = 26.58 днів
```

Якщо додатково обмежити WIP усередині Stream-Aligned команди (знизивши її внутрішню утилізацію до `ρ = 0.50` за рахунок резервування ємності):

```
W_q_stream_optimized = 1.2 · (0.50 / (1 - 0.50)) · 7.0 = 8.4 днів
T_total_optimal = 7.0 + 8.4 = 15.4 днів
```

Скорочення терміну доставки в порівнянні з початковим колодязним ланцюжком (56 днів):

```
Абсолютне скорочення = 56.0 - 15.4 = 40.6 днів
Відносне прискорення = 56.0 / 15.4 = 3.63 рази (прискорення на 263%)
```

Математичні моделі доводять: найбільший важіль прискорення софтверної інженерії полягає не в локальній оптимізації скорості набору коду, а в **усуненні міжкомандних передач, зниженні утилізації вузьких місць та переході до малих партій розробки**.
