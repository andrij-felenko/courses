# ⚙️ Аудит координації DH: кожну операцію — крізь драбину

Рамка легко лишається гарною теорією. «Проведи кожен клас роботи крізь одні ворота й спусти на найнижчий коректний щабель» — звучить переконливо, доки не сядеш і не проведеш нею **справжній** список операцій: не три показові приклади, а весь робочий обшир системи, включно з тими операціями, що прикидаються не тим, чим є. Тож зробімо це руками — перетворімо рамку на артефакт, який можна покласти на стіл команді.

Робимо три речі поспіль, і кожна відповідає на своє питання. Спершу — **аудит-таблиця**: провести кожну операцію DH крізь ворота, поставити щабель і назвати причину, а тоді окремо розглянути три рядки, де чуйка тягне не на той щабель, — бо саме на них ламаються реальні системи. Тоді — **ескіз коду**: крихітне консенсус-ядро проти локального шард-шляху, щоб на очах побачити, що ядро торкають зрідка, а майже вся робота локальна. І наостанок — **серветка**: порахувати, скільки коштує раунд консенсусу проти локальної операції, і чому ядро не стає ані на крихту швидшим від того, що ти доклав у нього вузлів.

## 1. Аудит-таблиця: кожну операцію крізь ворота

Ворота одні, і питання до кожної операції те саме: **чи вимагає її коректність, щоб усі вузли зійшлися на ОДНІЙ упорядкованій відповіді — чи кожен вузол може вирішити сам, а розбіжність звести потім (або не зводити ніколи)?** Тверде «так, рівно один» — щабель 2, консенсус. «Ні, аби значення вціліло під збоєм» — щабель 1, кворум. «Ні, усе живе в межах одного дому» — щабель 0, локальний шард. Ось увесь обшир DH, проведений цими воротами:

| Операція DH | Рівно один / строгий порядок? | Чому саме так | Щабель | Механізм |
|---|---|---|---|---|
| Записати показання давача | ні | покази дому незалежні, лягають за часом у межах свого дому | **0** | шард за `home_id` |
| Прочитати стан твіна одного дому | ні | увесь стан дому — на його шарді | **0** | локальне читання шарда |
| Порахувати правило автоматизації | ні | правило бачить лише свій дім | **0** | локально на шарді |
| Виставити бажаний стан пристрою | ні | остання команда перемагає, повтор нешкідливий | **0** | шард + [ідемпотентність](book:programming/idempotency) |
| Додати пристрій у множину дому | ні | комутативно: будь-який порядок → та сама множина | **0** | шард (монотонне злиття) |
| Широке читання твіна для панелей | ні | зведення по регіонах, невеликий лаг терпимо | **1** | [кворум-репліки](guide:progarch/replication-choice) |
| Останнє відоме показання для віджета | ні | трохи застаріле значення прийнятне | **1** | кворум-читання |
| Хто лідер нічних джоб | **ТАК** | рівно один крутить ребаланс, інакше двоє топчуться | **2** | [вибір лідера](book:programming/leader-election) через лізу |
| Який чинний shard-map | **ТАК** | усі мусять бачити ту саму мапу «дім → шард» | **2** | консенсус-ядро |
| Який чинний конфіг кластера | **ТАК** | одна версія правди для всіх вузлів | **2** | консенсус-ядро |
| Замок оновлення прошивки | **ТАК** | двоє не сміють лити прошивку в один пристрій | **2** | [замок із fencing-токеном](book:programming/distributed-locks) |
| Видати унікальний ID | і так, і ні | «рівно один» глобально — але **не** на кожен номер | **0/2** | ліза блоку ID (пастка 1) |
| Лічильник використання / білінг | ні | точність — від суми, не від згоди в реальному часі | **0** | лічильники домів, сума потім |
| Членство вузлів у кластері | **ТАК** | усі згодні, хто «в» групі, хто випав | **2** | консенсус-ядро |

Прочитаймо, що випало. Переважна маса рядків — покази, стан, правила, команди, множини — сидить на щаблі 0, бо все це замкнене в **одному домі**, а цілий дім живе на одному шарді за `home_id`. Два рядки — широкі читання твіна для зведених панелей — спускаються на щабель 1: там свіжість не критична, невеликий лаг терпимо, тож [кворум-репліки](guide:progarch/replication-choice) дешевші за похід у сильно-узгоджене ядро й свідомо хиляться до доступності. І лише жменька рядків — хто лідер, який shard-map, який конфіг, хто тримає замок прошивки, хто в кластері — лізе на щабель 2, бо кожен із них вимагає одного глобального «рівно один».

Але сама таблиця — ще не наука. Наука ховається в тих рядках, де правильна відповідь **суперечить** першому чуттю. Їх якраз варто розглянути поіменно.

### Три пастки: де чуйка бреше про щабель

**Пастка перша: унікальний ID — «очевидно» щабель 2.** Здається, що кожен глобально унікальний номер вимагає консенсусу: два вузли, вирішивши незалежно, видадуть однакове число — колізія, яку ми бачили в основному кроці. Звідси рефлекс — ганяти **кожен** `next_id` через ядро. Але це найдорожчий спосіб зробити просту річ. Придивімося, що саме потребує згоди: не окремий номер, а лише **право на діапазон**. Тож попроси в ядра один раз блок — скажімо, `[8000, 9000)` — і видавай усю тисячу номерів **локально**, без жодного дотику до ядра. Ядро торкаєш раз на тисячу видач, а не на кожну:

```py
class IdAllocator:
    """Один CAS у ядро на цілий блок; далі — локальна лічба без раундів."""
    def __init__(self, core, key="/dh/id-block", block=1000):
        self.core, self.key, self.block = core, key, block
        self.next = self.end = 0                 # порожньо → перший mint візьме блок

    async def mint(self) -> int:
        if self.next >= self.end:                # блок вичерпано (раз на 1000 разів)
            await self._lease_block()            # ← єдиний дотик до щабля 2
        v, self.next = self.next, self.next + 1  # ← 999 разів із 1000: чиста локальна лічба
        return v

    async def _lease_block(self):
        while True:                              # CAS-цикл: атомарно посунути «водомір»
            hi, rev = await self.core.get(self.key)
            hi = int(hi or 0)
            new_rev, ok = await self.core.cas(self.key, str(hi + self.block), expect_rev=rev)
            if ok:
                self.next, self.end = hi, hi + self.block
                return
```

Результат — операція, що зовні виглядала як «щабель 2 на кожен клац», насправді живе на щаблі 0 на 99.9% викликів і зачіпає консенсус лише зрідка. Ось звідки клітинка **0/2** у таблиці: правильний щабель — не «де операція здається», а «де насправді потрібна згода», а згода тут потрібна не про номер, а про **межу блока**.

**Пастка друга: оновлення прошивки — «очевидно» щабель 0.** Зворотний випадок. «Залити прошивку в пристрій» — це ж просто запис у межах одного дому, найприродніший щабель 0. Пастка в тому, що щабель диктує не сам запис, а **вимога взаємного виключення** довкола нього: якщо два оркестратори (скажімо, планова кампанія й ручний ретрай інженера) почнуть лити в один пристрій **водночас**, вони можуть лишити його з напів-переписаною прошивкою — цеглиною. Тут коректність вимагає, щоб у будь-яку мить лив **рівно один**, а «рівно один за раз» без спільної згоди про власника не існує. Тож рядок лізе на щабель 2 — [замок](book:programming/distributed-locks), але обов'язково з **fencing-токеном**: замок із самим таймаутом бреше, бо процес, що заснув під час паузи, прокинеться з простроченим замком і все одно спробує лити. Токен рятує так: пристрій приймає команду, лише якщо її номер-токен **не менший** за найбільший бачений, — і застряглий-та-прокинутий писар зі старим токеном буде відбитий.

**Пастка третя: лічильник білінгу — «очевидно» щабель 2.** «Це ж гроші, тут усе мусить бути точно» — і рука тягнеться до строгої узгодженості. Але придивімося, звідки береться точність рахунку. Вона береться не з того, що кожне `+1` пройшло крізь консенсус у реальному часі, а з того, що **сума** всіх подій наприкінці правильна. А для правильної суми порядок додавань байдужий — воно [комутативне](book:programming/eventual-consistency), як і множина пристроїв: `a+b+c` дає те саме, у якому б порядку вузли не рахували. Тож кожен дім веде **свій** лічильник локально (щабель 0), а білінг раз на період підсумовує їх; точність гарантує арифметика підсумку, а не координація на гарячому шляху. Плутанина тут — між «результат мусить бути точним» (так) і «кожен інкремент мусить бути узгодженим негайно» (ні); ворота розрізняють саме друге.

![Три горизонтальні доріжки. У кожній ліворуч операція DH, посередині амбер-рамка «як підказує чуйка» з наївним щаблем, праворуч рамка «що каже питання воріт» зі справжнім щаблем. Доріжка 1: «Унікальний ID» — наче щабель 2 (кожен номер через ядро) → насправді щабель 0 (ліза блоку ID, далі локально). Доріжка 2: «Оновлення прошивки» — наче щабель 0 (просто запис у пристрій) → насправді щабель 2 (двоє не разом, замок плюс fencing). Доріжка 3: «Лічильник білінгу» — наче щабель 2 (має бути точно) → насправді щабель 0 (лічильники домів, сума потім)](/guide/progarch/time-order-consensus/sharding-consensus-choice/img/audit-traps.svg)
*Три операції, що падають не туди, куди підказує чуйка. Наївний щабель — амбер, справжній — зелений (0) чи червоний (2). Урок аудиту саме в цих рядках: ворота питають не «де операція здається важливою», а «про що конкретно тут потрібна згода» — і відповідь часто інша, ніж перше чуття.*

> 🔧 **Навіщо це.** Коли аудитуєш свою систему, найкорисніші рядки — не ті, що очевидно щабель 0 чи очевидно щабель 2, а ці межові. На кожній операції став уточнене питання: «згода потрібна про **що саме** — про кожну дію чи лише про якусь рідкісну межу?». Часто виявиться, що дороге «рівно один» треба не на гарячому шляху, а раз на блок (ліза діапазону), або що дешеве «просто запис» насправді ховає взаємне виключення (замок). Пастка — не в складності операції, а в підміні питання: «це важливо» ≠ «це треба координувати на кожному кроці».

## 2. Ескіз ядра: control plane проти data plane

Таблиця сказала, **скільки** координації треба; тепер подивімося, як це лягає в код — і головне, переконаймося на очах, що щабель 2 справді торкають зрідка. Форма, що випадає з аудиту, — це [площина управління й площина даних](book:programming/control-data-plane): крихітне сильно-узгоджене ядро тримає кілька глобальних фактів зі щабля 2 (shard-map, лідер, конфіг), а велика площина роботи лише **зчитує** їх зрідка й усю решту робить локально на своєму шарді.

Ядро — це не наш винахід, а готова коробка: [etcd](book:algorithms/raft) (Raft усередині, написаний мовою Go, тримає стан керування Kubernetes) чи ZooKeeper дають рівно те, що треба, — маленьке KV із трьома операціями: **читання**, **CAS** (compare-and-swap: записати, лише якщо ревізія ключа та, що ти бачив) і **watch** (потік змін ключа), плюс **лізи** з TTL. Історично цей клас систем започаткував Chubby — сервіс блокувань Google (Майк Барровз, стаття 2006 року, Paxos усередині), який робив саме це: вибір лідера, дрібний конфіг і грубозернисті замки для слабозв'язаних систем. Прикметно, що вже в Chubby була **послідовність** (sequencer) — токен, який клієнт передавав зовнішньому сервісу як fencing-токен: та сама ідея, що рятує наш замок прошивки з пастки 2.

Домовмося про мінімальний інтерфейс ядра й напишімо два шматки: **гарячий шлях даних**, що маршрутизує запит із локального кешу без жодного раунду, і **лідера нічних джоб**, що тримає лізу через CAS. Перемикай вкладки — та сама логіка мовою систем (Go) і мовою ясності (Python):

```go
package dh

import (
	"context"
	"sort"
	"sync"
	"time"
)

// Core — крихітне сильно-узгоджене KV (etcd / ZooKeeper / Chubby усередині).
// КОЖЕН його виклик коштує раунд до живої більшості — тож у гарячий шлях воно НЕ лізе.
type Core interface {
	Get(ctx context.Context, key string) (val string, rev int64, err error)
	// CAS: записати val, лише якщо поточна ревізія ключа == expect (0 = «ключа ще нема»).
	CAS(ctx context.Context, key, val string, expect int64, ttl time.Duration) (rev int64, ok bool, err error)
	Watch(ctx context.Context, key string) <-chan Event // потік змін ключа
}
type Event struct{ Val string; Rev int64 }

// ── DATA PLANE — гарячий шлях. Маршрут читаємо з ЛОКАЛЬНОГО кешу: 0 раундів у ядро. ──
type ShardMap struct {
	mu    sync.RWMutex
	epoch int64    // ревізія ядра, з якої знято мапу — fencing проти застарілого кешу
	hi    []uint64 // верхні межі діапазонів home_id, відсортовані
	shard []string // shard[i] обслуговує діапазон, що кінчається на hi[i]
}

// Route — чистий локальний пошук: жодної мережі, жодного консенсусу. Наносекунди.
func (m *ShardMap) Route(homeID uint64) (shard string, epoch int64) {
	m.mu.RLock()
	defer m.mu.RUnlock()
	i := sort.Search(len(m.hi), func(i int) bool { return m.hi[i] >= homeID })
	return m.shard[i], m.epoch
}

// Refresh — рідкісний фон: оновлюємо кеш, ЛИШЕ коли ядро повідомить про зміну мапи.
func (m *ShardMap) Refresh(ctx context.Context, core Core) {
	for ev := range core.Watch(ctx, "/dh/shard-map") { // трапляється при ребалансі, не на запит
		hi, shard := parseMap(ev.Val) // парсер мапи — тривіальний, тіло опущено
		m.mu.Lock()
		m.hi, m.shard, m.epoch = hi, shard, ev.Rev
		m.mu.Unlock()
	}
}

// ── CONTROL PLANE — лідер нічних джоб. Раунд на здобуття лізи + рідкі поновлення. ──
func RunAsLeader(ctx context.Context, core Core, me string, job func(context.Context)) {
	const ttl = 10 * time.Second
	const key = "/dh/leader/night-jobs"
	for ctx.Err() == nil {
		if _, rev, _ := core.Get(ctx, key); rev == 0 { // вакансія — пробуємо зайняти
			if newRev, ok, _ := core.CAS(ctx, key, me, 0, ttl); ok {
				lead(ctx, core, key, me, newRev, ttl, job) // ми лідер
			}
		}
		time.Sleep(ttl / 3) // не лідер — зазираємо зрідка, не жаримо ядро
	}
}

// lead поновлює лізу CAS-ом «я → я» і крутить job, поки тримаємо ключ.
func lead(ctx context.Context, core Core, key, me string, rev int64, ttl time.Duration, job func(context.Context)) {
	jobCtx, stop := context.WithCancel(ctx)
	defer stop()
	go job(jobCtx) // РОБОТА лідера (ребаланс шардів) — локальна, ядро її не бачить
	tick := time.NewTicker(ttl / 3) // поновлюємо втричі частіше за строк
	defer tick.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-tick.C:
			newRev, ok, err := core.CAS(ctx, key, me, rev, ttl) // «я досі я»
			if err != nil || !ok {
				return // втратили лізу (пауза/мережа) — job спиниться разом зі stop()
			}
			rev = newRev
		}
	}
}
```

```py
import asyncio, bisect
from dataclasses import dataclass, field

# Core — крихітне сильно-узгоджене KV (etcd / ZooKeeper / Chubby усередині).
# КОЖЕН його виклик = раунд до живої більшості, тож у гарячий шлях воно НЕ лізе.
class Core:                                        # інтерфейс: get / cas / watch
    async def get(self, key: str) -> tuple[str | None, int]: ...
    async def cas(self, key: str, val: str, expect_rev: int, ttl: float = 0) -> tuple[int, bool]: ...
    async def watch(self, key: str): ...           # async-генератор подій (val, rev)

# ── DATA PLANE — гарячий шлях. Локальний кеш shard-map → 0 раундів у ядро. ──
@dataclass
class ShardMap:
    hi: list[int] = field(default_factory=list)    # верхні межі діапазонів home_id
    shard: list[str] = field(default_factory=list) # shard[i] тримає діапазон, що кінчається на hi[i]
    epoch: int = 0                                  # ревізія ядра — fencing проти застарілого кешу

    def route(self, home_id: int) -> tuple[str, int]:
        i = bisect.bisect_left(self.hi, home_id)   # двійковий пошук у пам'яті: наносекунди
        return self.shard[i], self.epoch           # жодної мережі, жодного консенсусу

    async def refresh(self, core: Core):
        async for ev in core.watch("/dh/shard-map"):   # рідко: лише при ребалансі, не на запит
            self.hi, self.shard = parse_map(ev.val)    # парсер мапи опущено: тривіальний
            self.epoch = ev.rev

# ── CONTROL PLANE — ліза лідера нічних джоб. Раунд на здобуття + рідкі поновлення. ──
async def run_as_leader(core: Core, me: str, job, ttl: float = 10.0):
    key = "/dh/leader/night-jobs"
    while True:
        _, rev = await core.get(key)
        if rev == 0:                               # вакансія — пробуємо зайняти CAS-ом
            new_rev, ok = await core.cas(key, me, expect_rev=0, ttl=ttl)
            if ok:
                await _lead(core, key, me, new_rev, ttl, job)  # ми лідер
        await asyncio.sleep(ttl / 3)               # не лідер — зазираємо зрідка, не жаримо ядро

async def _lead(core, key, me, rev, ttl, job):
    task = asyncio.create_task(job())              # РОБОТА лідера (ребаланс) — локальна
    try:
        while True:
            await asyncio.sleep(ttl / 3)           # поновлюємо втричі частіше за строк
            rev, ok = await core.cas(key, me, expect_rev=rev, ttl=ttl)  # «я досі я»
            if not ok:
                return                             # втратили лізу — job спиниться у finally
    finally:
        task.cancel()
```
:::

Тепер найважливіше — **перелічити, коли код узагалі торкається ядра**, бо саме тут ховається вся економія. Гарячий шлях запиту DH — «прийшло показання від дому `H`» — робить рівно два кроки: `Route(H)` бере адресу шарда **з локального кешу** (двійковий пошук у пам'яті, нуль раундів) і, якщо це наш дім, застосовує операцію локально на шарді. Ядро в цьому шляху **не з'являється жодного разу**. А коли ж воно з'являється?

```
дотики до консенсус-ядра (щабель 2) — і як рідко:
  Refresh    watch спрацьовує         → лише коли міняється shard-map (ребаланс) — одиниці/год
  RunAsLeader ліза лідера              → 1 здобуття + поновлення що ~⅓ TTL — десятки/с на групу
  замок прошивки                       → 1 CAS на пристрій за кампанію оновлення
  ────────────────────────────────────────────────────────────────────────────────
  гарячий шлях (Route + локальна робота) → ЖОДНОГО дотику, мільйони разів/с
```

Ось та сама форма, тепер підтверджена кодом: 99% роботи — це `Route` + локальне застосування, обидва без ядра; а те, що ядро таки бачить, — це watch-події при рідкісному ребалансі й поновлення лізи, розмазані на секунди. Кеш shard-map означає, що навіть питання «де живе дім `H`?» гарячий шлях не ставить ядру — він відповідає сам, зі знімка, який фоново оновлюється лише коли мапа справді змінилась.

> 🔧 **Навіщо це.** Головна архітектурна дисципліна тут — **кешувати відповіді ядра локально й читати кеш на гарячому шляху**, а не ходити в ядро на кожен запит. Наївна реалізація «спитаю etcd, де мій дім» на кожне показання перетворила б щабель-0-операцію на щабель-2-операцію й з'їла б увесь виграш — ти б платив раунд там, де його можна не платити. Правило просте: ядро — джерело правди, але гарячий шлях говорить із його **локальною копією**, а копію освіжає рідкісний watch. І тримай у копії `epoch` (ревізію): він знадобиться, щойно мапа зміниться під тобою, — про це в пастках.

## 3. Серветка: податок раундів

Лишилося показати ціну на числах — бо саме число робить вибір із рамки не смаком, а розрахунком. Порахуймо на серветці дві речі: скільки коштує одна операція на щаблі 0 проти щабля 2, і чому додати вузлів у консенсус-групу не робить її швидшою.

Візьмімо реалістичний за формою дата-центр: вузли рознесені по стійках, час туди-й-назад між ними (RTT) — близько **1 мс**. Тоді ціна однієї операції розкладається так:

```
── ціна ОДНІЄЇ операції (RTT у ДЦ ≈ 1 мс) ──
щабель 0 · локально на шарді:
   0 мережевих раундів · маршрут із кешу (нс) + локальний запис (SSD)
   ≈ 0.2 мс   і жодної залежності від «а хтось інший живий?»
щабель 2 · рішення консенсусом:
   ≥ 1 раунд до живої більшості     = 1 · RTT       ≈ 1.0 мс
   + fsync лога лідера й фоловерів   ≈ 0.5 … кілька мс
   ─────────────────────────────────────────────────────
   ≈ кілька мс на КОЖНЕ рішення   і воно не ухвалиться без більшості
```

Різниця — не у відсотках, а в порядках, і не лише в латентності. Локальна операція коштує стільки, скільки коштує локальна операція, і їй байдуже, чи живий сусідній вузол. Рішення консенсусом несе щонайменше один раунд у живу більшість плюс запис лога на диск — а якщо тієї більшості нема, воно просто **не ухвалюється**: система радше застигне, ніж дозволить двом розійтися.

![Часова смуга. Угорі щабель 0: коротюсінький зелений відрізок від нуля до ≈0.2 мс з підписом «0 мережевих раундів». Нижче щабель 2: довгий складений відрізок від нуля до ≈2.4 мс із трьох сегментів — fsync лідера, один RTT до живої більшості, коміт — з підписом «≈ кілька мс». Локальна операція фінішує там, де консенсус лише починає. Нижче — окрема панель «чому +вузли не швидші»: три ряди вузлів N=3, N=5, N=7, у кожному лідер L і кворум підсвічені зеленим, а червоний пунктирний поріг «останній потрібний акк» зсувається дедалі правіше зі зростанням N](/guide/progarch/time-order-consensus/sharding-consensus-choice/img/round-tax.svg)
*Локальна операція фінішує там, де консенсус лише починає роздавати пропозицію. А нижня панель відповідає на головне питання: чому не можна «докинути вузлів» і прискоритися. Кворум групи з N вузлів — це ⌊N/2⌋+1, тож із ростом N лідерові треба **більше** підтверджень, а не менше, і поріг «останнього потрібного акка» зсувається лише правіше.*

Тепер найпоширеніша хиба інтуїції, яку варто вбити числом: «додамо в консенсус-групу вузлів — стане швидше». Ні. Подивімося, чому саме:

```
── чому +вузли НЕ пришвидшують консенсус ──
кворум групи з N = ⌊N/2⌋ + 1   (лідер рахує й себе)
   N=3 → лідеру треба   1 акк фоловера  → чекає на 1-го найшвидшого з 2
   N=5 → лідеру треба   2 акки          → чекає на 2-го найшвидшого з 4
   N=7 → лідеру треба   3 акки          → чекає на 3-го найшвидшого з 6
латентність рішення = RTT до (⌊N/2⌋)-го за швидкістю фоловера
   → більше вузлів → поріг «останнього потрібного» лише ВІДСУВАЄТЬСЯ далі
   → +вузли купують ВИТРИВАЛІСТЬ (переживеш більше падінь), а НЕ швидкість
   → а лідер із логом лишається ОДИН → стеля пропускної здатності теж пласка
```

Ось два незалежні аргументи, чому докидання вузлів не рятує. Перший — латентність: рішення комітиться, коли його підтвердила більшість, тобто лідер мусить дочекатися ⌊N/2⌋-го за швидкістю фоловера; що більше вузлів, то далі відсунутий цей поріг, тож латентність у найкращому разі стоїть на місці, а зазвичай трохи росте. Другий, важчий — пропускна здатність: усі записи однаково течуть крізь **одного** лідера й лягають в **один** упорядкований лог, і додаткові вузли лідера не розвантажують, а лише додають йому адресатів для розсилки. Тому одна консенсус-група має **стелю**, і докидання вузлів її не піднімає — воно піднімає лише те, скільки падінь група переживе.

І ось тут аудит замикається сам на себе. Порахуймо бюджет рішень DH — скільки роботи насправді припадає на кожен щабель:

```
── бюджет рішень DH (прикидка на серветці) ──
щабель 0 — гаряча пожежна кишка (локально на шардах):
   телеметрія + читання твіна + правила ≈ 10⁶ … 10⁷ оп/с
   росте ЛІНІЙНО: тісно → додав шардів, і кожен новий шард додає пропускної
щабель 2 — тонка цівка в консенсус-ядро:
   зміна shard-map (ребаланс)      ≈ одиниці / год
   поновлення лізи лідера          ≈ 3 / TTL на джоб-групу  → десятки/с усього
   зміна конфігу                   ≈ одиниці / день
   замок прошивки (fencing)        ≈ 1 на пристрій за кампанію оновлення
   ─────────────────────────────────────────────────────────────────
   разом ядру                      ≈ десятки … сотні записів/с у піку
одна мала Raft-група тримає тисячі записів/с
   → ядро НЕ вузьке місце, бо аудит СВІДОМО зігнав щабель 2 до цівки
```

Оце і є пуант усього артефакту. Ми не боремося зі стелею консенсусу — ми **тікаємо** від неї заздалегідь. Мільйони операцій за секунду, що складають фактичну роботу DH, аудит розклав на щабель 0, де вони течуть локально й масштабуються лінійно з числом шардів. А на щабель 2 лишилися тільки ті кілька глобальних фактів, потік змін яких — десятки-сотні на секунду, — і це з запасом влазить в одну крихітну Raft-групу з трьох-п'яти вузлів. Стеля консенсусу нікуди не поділася; ми просто зробили так, щоб робота ніколи в неї не впиралася.

> 🔧 **Навіщо це.** Серветку роби **перед** тим, як обрати щабель, а не після аварії. Дві цифри вирішують майже все: скільки операцій цього класу за секунду в піку — і скільки з них справді вимагають глобального «рівно один». Якщо перша велика, а друга мала (майже завжди так), відповідь — площина даних на щаблі 0 плюс цівка в ядро; якщо хтось пропонує «проженімо все через etcd, щоб надійно», покажи йому рядок бюджету: одна група має стелю в тисячі записів/с, і мільйони показань DH її просто розчавлять. Консенсус масштабують **не** докиданням вузлів у групу (це лише витривалість), а тим, що тримають потік рішень крізь нього маленьким — власне те, заради чого й потрібен аудит.

## Складність і пастки

Артефакт готовий — але кожен його елемент легко перетворити на граблі, якщо переказати неточно. Пройдімося по найгостріших.

**Застарілий кеш shard-map — потрібен epoch/fencing.** Кеш маршрутів дає нам нуль раундів на гарячому шляху, але має зворотний бік: вузол, що проґавив ребаланс, маршрутизуватиме за **старою** мапою й відповідатиме за дім, який уже переїхав. Саме тому в кеші живе `epoch` (ревізія ядра): відповідь маршрутизації несе його з собою, а шард-власник відкидає запити зі старшим epoch — той самий fencing, що й у замку прошивки. Без epoch кеш тихо бреше рівно у вікні між ребалансом і освіженням watch.

**Ліза — це теж трафік у ядро; TTL треба бюджетувати.** Спокусливо поставити крихітний TTL, щоб швидко ловити падіння лідера. Але поновлення йде що ⅓ TTL, тож TTL = 1 с означає ~3 CAS/с на **кожну** лізу — а лідерів і замків можуть бути тисячі, і раптом «цівка» в ядро стає струменем. Зворотна крайність — TTL = хвилина — економить трафік, але лишає нічні джоби без лідера на цілу хвилину після падіння. Це прямий компроміс, і його рахують, а не вгадують: TTL добирають так, щоб сумарний потік поновлень лишався в бюджеті ядра, а час до відновлення був стерпним.

**Рефлекс «про всяк випадок через консенсус» отруює гарячий шлях.** Найтихіша й найдорожча пастка — не помилка в коді, а звичка. Кожне «а зробімо це через etcd, щоб напевно» додає раунд туди, де його можна було не додавати, і непомітно тягне операцію на щабель угору. Аудит існує саме як протиотрута цьому рефлексу: він змушує назвати, **про що конкретно** потрібна згода, — і майже завжди виявляється, що не про те, на що показувала рука.

**Багатошардова операція мовчки лізе вгору драбиною.** Уся економія тримається на тому, що операція живе в **одному** домі, а отже на одному шарді. Щойно з'являється дія, що зачіпає два доми одразу (перенесення пристрою між домами, зведений атомарний перерахунок по кількох), вона перестає бути щаблем 0: щоб зшити два шарди атомарно, доводиться повертати координацію — двофазний коміт чи сагу — з усім її податком. Тому такі операції або уникають дизайном ключа, або платять за них свідомо; а перекласти живі дані на інший ключ — це не прапорець, а [тижнева міграція під навантаженням, як у розборі Discord](guide:progarch/rozbir-discord-storage).

**Ліза блоку ID лишає діри — і це нормально, доки ID непрозорі.** Трюк із діапазоном (пастка 1) має тонкість: якщо вузол упав, не роздавши всі номери свого блока `[8000, 9000)`, решта з `8000…8999` просто зникає — у послідовності буде діра. Для унікального ідентифікатора це байдуже (він має бути унікальним, а не суцільним). Але щойно бізнес вимагає **бездіркової** нумерації (юридично — рахунки-фактури поспіль, без пропусків), трюк ламається, і ти повертаєшся на щабель 2 на кожен номер — бо «суцільно й поспіль» це і є строгий порядок. Тож перше питання до будь-якого «унікального номера»: він має бути лише унікальний — чи ще й без дір? Відповідь визначає щабель.
