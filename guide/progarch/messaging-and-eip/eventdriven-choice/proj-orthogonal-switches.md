# ⚙️ Один замок, дві осі — чотири системи з тих самих деталей

Тезу вже названо: тумблери незалежні. Але теза в прозі — річ дешева; повірити в неї легко й забути легко. Дорожчий доказ — той, що лягає на диск і запускається. Тож візьмімо **один** маленький агрегат дому — дверний замок — і напишімо його по **двох незалежних осях** так, щоб незалежність не декларувалася словом, а трималася самою формою коду. Якщо осі справді ортогональні, то з двох реалізацій на кожній осі впадуть **чотири** робочі системи — і впадуть без жодної спільної проводки між осями, просто зі складання.

Дві осі беремо найглибші й найпростіші для дотику:

- **Вісь джерела правди.** Що ми зберігаємо як істину? Або поточний стан замка, перезаписуючи клітинку (CRUD у чистому вигляді), або append-only журнал подій, а стан **рахуємо** згорткою ([event sourcing](book:programming/event-sourcing)).
- **Вісь читання.** Хто відповідає на запит панелі? Або та сама модель, з якої й пишемо, або окрема читацька проєкція, яку ми тримаємо збоку ([CQRS](book:programming/cqrs)).

Третій тумблер модуля — комунікацію, віяло подій між сервісами — ми навмисне лишаємо осторонь: він ортогональний так само, і саме тому його можна не чіпати, доводячи незалежність перших двох. І одразу межа задачі, щоб не збудувати зайвого: ми **не** будуємо тут повний твін дому й не обираємо, яку з чотирьох систем поставити в бій, — це зважать пізніші кроки. Наша єдина ціль — показати руками, що чотири комбінації складаються вільно, і назвати, **чим кожна платить**.

## Задача

Замок — навмисне дрібний агрегат, щоб уся увага лишилась на осях, а не на домені. У нього два переходи: `lock` і `unlock`, кожен від когось (`actor`) і в якийсь час (`at`). Стан замка — трійка: зачинено чи ні, хто торкнувся востаннє, коли.

А тепер важлива тонкість, без якої вісь читання виродилась би в порожнє слово: **читацька форма інша, ніж форма запису.** Панель безпеки дому не хоче «поле `locked: true`» — вона хоче рядок для ока чергового: «Вхідні: ЗАЧИНЕНО, останній — гість, за сьогодні відмикали 3 рази». Оте «відмикали 3 рази за сьогодні» — не поле стану, а **підсумок над історією**; саме такі похідні величини й виправдовують окрему читацьку модель ([матеріалізовану в'ю](book:programming/materialized-views) над потоком змін). Тримаймо цю різницю форм у голові — вона зробить вісь читання відчутною.

Від кожної з чотирьох систем хочемо дві операції: `send(cmd)` — виконати команду над замком; `view()` — віддати рядок панелі. І один-єдиний критерій успіху: щоб **будь-яку** реалізацію осі правди можна було зіткнути з **будь-якою** реалізацією осі читання, не міняючи жодного рядка ні там, ні там. Якщо це вдасться — осі ортогональні не на словах, а в системі типів.

## Ідея: дві осі — два інтерфейси, що не знають одне про одного

Уся хитрість — в одному рішенні на початку: зробити кожну вісь **окремим інтерфейсом**. Тоді «скласти систему» — це не написати новий клас на кожну комбінацію (їх було б чотири, потім вісім, потім не злічити), а просто **підставити** одну реалізацію правди й одну реалізацію читання в спільний каркас. Незалежність осей перестає бути обіцянкою в коментарі — вона стає тим фактом, що два інтерфейси в коді жодного разу не згадують одне одного.

Почнімо зі спільного домену — він однаковий для всіх чотирьох систем, бо домен про **замок**, а не про спосіб його зберігати:

:::tabs
```ts
// ── Спільний домен: команда → факт, і згортка факту в стан ──
type LockState = { locked: boolean; lastActor: string | null; at: number };
const INITIAL: LockState = { locked: false, lastActor: null, at: 0 };

type Command =
  | { kind: "lock";   actor: string; at: number }
  | { kind: "unlock"; actor: string; at: number };

// подія — доконаний ФАКТ (те, що вже сталося), а не наказ
type DoorEvent =
  | { type: "DoorLocked";   actor: string; at: number }
  | { type: "DoorUnlocked"; actor: string; at: number };

// доменне правило: команда обертається на факт (або відкидається)
function decide(s: LockState, c: Command): DoorEvent {
  if (c.kind === "lock"   && s.locked)  throw new Error("вже зачинено");
  if (c.kind === "unlock" && !s.locked) throw new Error("вже відчинено");
  return c.kind === "lock"
    ? { type: "DoorLocked",   actor: c.actor, at: c.at }
    : { type: "DoorUnlocked", actor: c.actor, at: c.at };
}

// згортка: факт зсуває стан на один крок
function apply(s: LockState, e: DoorEvent): LockState {
  return e.type === "DoorLocked"
    ? { locked: true,  lastActor: e.actor, at: e.at }
    : { locked: false, lastActor: e.actor, at: e.at };
}
```
```py
from dataclasses import dataclass, replace
from functools import reduce

# ── Спільний домен: команда → факт, і згортка факту в стан ──
@dataclass(frozen=True)
class LockState:
    locked: bool = False
    last_actor: str | None = None
    at: int = 0

INITIAL = LockState()

@dataclass(frozen=True)
class Command:               # kind: "lock" | "unlock"
    kind: str; actor: str; at: int

@dataclass(frozen=True)
class DoorEvent:             # доконаний ФАКТ, а не наказ
    type: str; actor: str; at: int   # type: "DoorLocked" | "DoorUnlocked"

def decide(s: LockState, c: Command) -> DoorEvent:
    if c.kind == "lock"   and s.locked:      raise ValueError("вже зачинено")
    if c.kind == "unlock" and not s.locked:  raise ValueError("вже відчинено")
    typ = "DoorLocked" if c.kind == "lock" else "DoorUnlocked"
    return DoorEvent(typ, c.actor, c.at)

def apply(s: LockState, e: DoorEvent) -> LockState:   # згортка на один крок
    return replace(s, locked=(e.type == "DoorLocked"), last_actor=e.actor, at=e.at)
```
:::

Зверни увагу, що `decide` і `apply` — чисті функції домену, і жодна з них ще нічого не «зберігає». Це навмисне: питання «де взяти правду» і питання «як показати читання» ми зараз винесемо в два різні інтерфейси, а домен лишиться спільним підмурком під усіма чотирма кутами.

### Вісь перша — джерело правди

Інтерфейс правди знає рівно дві речі: як виконати команду (і повернути породжений факт) і як віддати поточний стан. Дві реалізації — два положення тумблера.

:::tabs
```ts
// ── Вісь 1: ДЖЕРЕЛО ПРАВДИ ──
interface Truth {
  handle(cmd: Command): DoorEvent;   // виконати команду, повернути факт
  state(): LockState;                // поточний стан замка
}

// ВИМК — CRUD: одна клітинка, перезапис; минуле стерто
class CrudTruth implements Truth {
  private s: LockState = INITIAL;
  handle(cmd: Command): DoorEvent {
    const e = decide(this.s, cmd);
    this.s = apply(this.s, e);        // ← стан перезаписано, що було — забуто
    return e;
  }
  state(): LockState { return this.s; }
}

// УВІМК — event sourcing: append-only журнал; стан = згортка журналу
class EventTruth implements Truth {
  private log: DoorEvent[] = [];
  handle(cmd: Command): DoorEvent {
    const e = decide(this.state(), cmd);
    this.log.push(e);                 // ← лише дописуємо; нічого не стираємо
    return e;
  }
  state(): LockState { return this.log.reduce(apply, INITIAL); }  // згортка щоразу
}
```
```py
from typing import Protocol

# ── Вісь 1: ДЖЕРЕЛО ПРАВДИ ──
class Truth(Protocol):
    def handle(self, cmd: Command) -> DoorEvent: ...
    def state(self) -> LockState: ...

class CrudTruth:                       # ВИМК — перезапис клітинки
    def __init__(self): self._s = INITIAL
    def handle(self, cmd: Command) -> DoorEvent:
        e = decide(self._s, cmd)
        self._s = apply(self._s, e)     # ← минуле стерто
        return e
    def state(self) -> LockState: return self._s

class EventTruth:                      # УВІМК — append-only журнал
    def __init__(self): self._log: list[DoorEvent] = []
    def handle(self, cmd: Command) -> DoorEvent:
        e = decide(self.state(), cmd)
        self._log.append(e)             # ← лише дописуємо
        return e
    def state(self) -> LockState:
        return reduce(apply, self._log, INITIAL)   # згортка щоразу
```
:::

Дві реалізації відрізняються **тільки** тим, що вони пам'ятають. `CrudTruth` тримає єдину клітинку `s` й перезаписує її — те, що було до `lock`, зникає безслідно. `EventTruth` не тримає стану зовсім: він тримає список фактів і **рахує** стан згорткою на кожен запит. Той самий замок, той самий намір — різне джерело правди, і більше нічого. Оця пара, зведена в два класи, і є перший тумблер, узятий у руки.

### Вісь друга — читацький бік

Другий інтерфейс — про читання. Він знає, як почути про зміну (`notify`) і як віддати рядок панелі (`dashboard`). І — ключове — він приймає `Truth` як аргумент читання, а не як свою нутрощ: так читацький бік може або спертися на правду (згорнути її на місці), або зовсім її проігнорувати й повернути власний, наперед зібраний рядок.

:::tabs
```ts
// читацька форма — рядок панелі; інша, ніж форма запису
type DashRow = { status: string; lastActor: string; unlockedToday: number };

// ── Вісь 2: ЧИТАЦЬКИЙ БІК ──
interface Read {
  notify(e: DoorEvent): void;         // як читання дізнається про зміну
  dashboard(truth: Truth): DashRow;   // читацька відповідь
}

// ВИМК — та сама модель: рахуємо форму з правди на кожному читанні
class FoldOnRead implements Read {
  notify(_e: DoorEvent): void { /* нічого не тримаємо */ }
  dashboard(truth: Truth): DashRow {
    const s = truth.state();
    return {
      status: s.locked ? "ЗАЧИНЕНО" : "ВІДЧИНЕНО",
      lastActor: s.lastActor ?? "—",
      unlockedToday: -1,              // ← без історії підсумку не порахувати
    };
  }
}

// УВІМК — окрема проєкція (CQRS): тримаємо готовий рядок, оновлюємо подіями
class Projection implements Read {
  private row: DashRow = { status: "ВІДЧИНЕНО", lastActor: "—", unlockedToday: 0 };
  notify(e: DoorEvent): void {
    this.row.status    = e.type === "DoorLocked" ? "ЗАЧИНЕНО" : "ВІДЧИНЕНО";
    this.row.lastActor = e.actor;
    if (e.type === "DoorUnlocked") this.row.unlockedToday += 1;   // підсумок
  }
  dashboard(_truth: Truth): DashRow { return this.row; }  // готове, без обчислень
}
```
```py
@dataclass
class DashRow:
    status: str = "ВІДЧИНЕНО"
    last_actor: str = "—"
    unlocked_today: int = 0

# ── Вісь 2: ЧИТАЦЬКИЙ БІК ──
class Read(Protocol):
    def notify(self, e: DoorEvent) -> None: ...
    def dashboard(self, truth: Truth) -> DashRow: ...

class FoldOnRead:                       # ВИМК — та сама модель
    def notify(self, e: DoorEvent) -> None: pass          # нічого не тримаємо
    def dashboard(self, truth: Truth) -> DashRow:
        s = truth.state()
        return DashRow(status="ЗАЧИНЕНО" if s.locked else "ВІДЧИНЕНО",
                       last_actor=s.last_actor or "—",
                       unlocked_today=-1)                  # без історії не порахувати

class Projection:                       # УВІМК — окрема проєкція (CQRS)
    def __init__(self): self._row = DashRow()
    def notify(self, e: DoorEvent) -> None:
        self._row.status = "ЗАЧИНЕНО" if e.type == "DoorLocked" else "ВІДЧИНЕНО"
        self._row.last_actor = e.actor
        if e.type == "DoorUnlocked":
            self._row.unlocked_today += 1                 # ⚠ див. пастку нижче
    def dashboard(self, truth: Truth) -> DashRow:
        return self._row                                  # готове, без обчислень
```
:::

Тут проступає та сама різниця форм, задля якої ми й городили окрему читацьку модель. `FoldOnRead` уміє віддати статус і останнього актора — бо це є в стані, — але на `unlockedToday` чесно ставить `-1`: підсумок за день над стертою історією не візьмеш. `Projection` же **накопичує** цей підсумок подіями і тому віддає готовий рядок за нуль обчислень. Різні форми, різна ціна — рівно те, про що казала лінійка.

### Складання: чотири системи по одному рядку

І ось нагорода за те, що осі — окремі інтерфейси. Каркас, який їх зшиває, дрібний до непристойності:

:::tabs
```ts
class System {
  constructor(private truth: Truth, private read: Read) {}
  send(cmd: Command): void {
    const e = this.truth.handle(cmd);   // 1. записали правду
    this.read.notify(e);                // 2. повідомили читацький бік
  }
  view(): DashRow { return this.read.dashboard(this.truth); }
}

// ── ЧОТИРИ системи — вільна композиція двох осей, по рядку на кут ──
const plainCrud = new System(new CrudTruth(),  new FoldOnRead());  // ✗ ✗  дефолт
const crudCqrs  = new System(new CrudTruth(),  new Projection());  // ✗ ✓  CRUD + CQRS
const esSingle  = new System(new EventTruth(), new FoldOnRead());  // ✓ ✗  ES, одна модель
const esCqrs    = new System(new EventTruth(), new Projection());  // ✓ ✓  ES + CQRS
```
```py
class System:
    def __init__(self, truth: Truth, read: Read):
        self.truth, self.read = truth, read
    def send(self, cmd: Command) -> None:
        e = self.truth.handle(cmd)     # 1. записали правду
        self.read.notify(e)            # 2. повідомили читацький бік
    def view(self) -> DashRow:
        return self.read.dashboard(self.truth)

# ── ЧОТИРИ системи — вільна композиція двох осей ──
plain_crud = System(CrudTruth(),  FoldOnRead())   # ✗ ✗  дефолт
crud_cqrs  = System(CrudTruth(),  Projection())   # ✗ ✓  CRUD + CQRS
es_single  = System(EventTruth(), FoldOnRead())   # ✓ ✗  ES, одна модель
es_cqrs    = System(EventTruth(), Projection())   # ✓ ✓  ES + CQRS
```
:::

Ось і весь доказ ортогональності — чотири рядки. `CrudTruth` і `EventTruth` нічого не знають про `FoldOnRead` чи `Projection`, і навпаки; жоден з чотирьох інтерфейсних методів не згадує сусідню вісь. Тому будь-яка правда стикається з будь-яким читанням — компілятор пропускає всі чотири комбінації, бо в типах вони й справді незалежні. Незалежність не написана в коментарі — вона в тому, що ці два інтерфейси **не мають між собою жодного шва**.

Проженімо крізь усі чотири однакову коротку історію й погляньмо, де вони збігаються, а де розходяться:

```ts
for (const sys of [plainCrud, crudCqrs, esSingle, esCqrs]) {
  sys.send({ kind: "lock",   actor: "Аня",   at: 900 });
  sys.send({ kind: "unlock", actor: "гість", at: 1500 });
  sys.send({ kind: "lock",   actor: "Аня",   at: 1800 });
  console.log(sys.view());
}
// plainCrud → { status: "ЗАЧИНЕНО", lastActor: "Аня", unlockedToday: -1 }
// crudCqrs  → { status: "ЗАЧИНЕНО", lastActor: "Аня", unlockedToday:  1 }
// esSingle  → { status: "ЗАЧИНЕНО", lastActor: "Аня", unlockedToday: -1 }
// esCqrs    → { status: "ЗАЧИНЕНО", lastActor: "Аня", unlockedToday:  1 }
```

Придивись до цих чотирьох рядків — у них уся суть. **Статус** усюди однаковий: замок зачинено, останньою була Аня. А от у двох питаннях системи мовчки розійшлися. По колонці читання: хто носить окрему `Projection` (`crudCqrs`, `esCqrs`), той знає `unlockedToday: 1`; хто читає згорткою (`plainCrud`, `esSingle`), той чесно каже `-1` — підсумок за день йому нізвідки взяти. А по колонці правди різниця в цьому запуску **не видна очам зовсім** — і саме це найцікавіше: `plainCrud` і `esSingle` віддали ідентичний рядок, але `esSingle` під капотом лишив увесь журнал і тому мовчки зберіг здатність, якої в `plainCrud` нема назавжди: відповісти пізніше на «а хто відмикав о 15:00», переграти історію новим правилом, підняти аудит. За джерело правди платять не виглядом читання, а **опцією на майбутнє**, за яку тихо йде місце на диску.

## Чотири кути, чотири рахунки

Тепер, коли всі чотири системи існують у коді, розкладімо їхні рахунки поряд. Осі незалежні — тож і платня складається покомпонентно: свій рядок від осі правди, свій від осі читання, і в кутку `✓ ✓` вони просто підсумовуються.

![Матриця два на два: по горизонталі вісь джерела правди (ліворуч CRUD — перезапис стану, праворуч журнал подій — append і згортка), по вертикалі вісь читання (згори та сама модель зі згорткою на читанні, знизу окрема проєкція CQRS). Чотири клітини. Лівий-верхній кут «✗✗ Звичайний CRUD — дефолт»: сховище O(1) на замок, лаг читання 0, аудиту й переграти нема, схема подій ні до чого. Правий-верхній «✓✗ ES, одна модель»: сховище — журнал росте, лаг 0 але згортка O(n), аудит і переграти Є, схема подій замкнена. Лівий-нижній «✗✓ CRUD + CQRS»: додається читацька модель, лаг читання є, аудиту нема, пастка подвійного запису. Правий-нижній «✓✓ ES + CQRS — дует»: сховище журнал плюс проєкція, лаг є, аудит Є, схема подій замкнена. Що більше увімкнених тумблерів, то зеленіша й «дорожча машинерією» клітина](/guide/progarch/messaging-and-eip/eventdriven-choice/img/four-systems.svg)
*Ціна складається по осях: рядок від правди (аудит проти незворотної схеми) плюс рядок від читання (готовий рядок панелі проти лагу й другої моделі). Кут «✓ ✓» не має власної, окремої ціни — він просто носить обидва рахунки разом, і тому машинерії в ньому найбільше.*

Читається матриця по осях, не по клітинах. **Вісь правди** торгує одне на одне: увімкнеш журнал — купиш аудит, запити в минуле й перегравання, а заплатиш місцем, що росте без стелі, і — найважче — тим, що схема подій стає незворотною (про це нижче окремо). Лишиш CRUD — сховище копійчане й нічого не замкнеш, зате історія стерта назавжди. **Вісь читання** торгує інше: увімкнеш проєкцію — читання стане миттєвим і зможе носити підсумки на кшталт `unlockedToday`, а заплатиш другою моделлю, її синхронізацією і [лагом читання](book:programming/eventual-consistency); лишиш згортку на читанні — жодного лагу й жодної другої моделі, зате кожне читання рахує форму з нуля, і підсумків над історією тобі не бачити (а в парі з CRUD — і поготів, бо історії просто нема).

> 🔧 **Навіщо це.** Коли на рев'ю хтось малює «переходимо на event-driven», проведи його по цій матриці пальцем і спитай про кожну вісь окремо: «журнал чи перезапис? одна модель чи дві?» Дев'ять разів із десяти виявиться, що людині потрібен рівно **один** кут — скажімо, `✗ ✓` заради швидкої панелі, — а мимоволі вона підписувала команду на кут `✓ ✓` з усією його машинерією. Дві осі, чотири кути; називай кут, а не гасло.

## Складність і пастки

Осі незалежні — а от граблі під ними, навпаки, ростуть із того ж кореня, що й вигоди, і кілька з них уже причаїлися в коді вище.

**Подвійний запит стан+подія — головна пастка, і вона у `send`.** Придивись до двох рядків усередині `System.send`: спершу `truth.handle`, потім `read.notify`. Поки все живе в одній купі пам'яті одного процесу — байдуже. Але щойно читацький бік з'їде в **окреме** сховище (а проєкція CQRS у бою — це майже завжди окрема таблиця чи інший вузол), ці два рядки перетворюються на **два незалежні записи в дві різні системи без спільної транзакції**. Та сама пастка вилазить і коли до CRUD доточують віяло подій: змінити свій стан і розіслати подію.

```ts
async function send(cmd: Command) {
  await db.update("locks", cmd.id, nextState(cmd));  // 1. сховище стану
  await bus.publish(toEvent(cmd));                    // 2. окрема шина
  // ← упади процес ТУТ, між рядками: стан пішов уперед, подія не пішла НІКОЛИ
}
```

Крапка між рядками — це трюм, у якому тонуть системи. Стан оновлено, подію не розіслано (або навпаки) — і два сховища тихо розійшлися, без жодного винятку, який би це помітив. Лік канонічний і зветься [transactional outbox](book:programming/outbox-pattern): не публікувати назовні окремим кроком, а в **тій самій** локальній транзакції, що й запис правди, дописати рядок у таблицю-outbox; окремий relay потім вичитує outbox і публікує, скільки завгодно разів безпечно.

![Дві половини. Ліворуч, під червоним заголовком «подвійний запис — два сховища, одна надія»: блок handler зі стрілками до двох окремих сховищ — БД зі станом (зелена, записано) і шини з подією (червона, впала); знизу червоним — процес упав між кроками, стан пішов уперед, подія загубилась, два сховища розійшлися. Праворуч, під зеленим заголовком «один запис плюс outbox — одна транзакція»: handler веде в один блок «ОДНА локальна транзакція: journal += подія і outbox += подія», а з нього окремий relay вичитує outbox і публікує в шину ідемпотентно](/guide/progarch/messaging-and-eip/eventdriven-choice/img/dual-write-outbox.svg)
*Зліва — два записи в дві системи без спільної транзакції: падіння між ними лишає сховища в різних правдах. Справа — єдиний атомарний запис (правда + намір опублікувати в одній транзакції) плюс окрема, безпечна на повтори публікація. Правило: назовні не пишемо другим кроком — лишаємо слід у власній транзакції.*

**Проєкцію треба переграти — і `+= 1` цього не переживе.** Ось пастка, яку ми навмисне лишили в коді `Projection.notify`. Рано чи пізно читацьку модель доведеться **перебудувати** — новий звіт, зіпсутий рядок, зміна форми панелі, — і будувати її ми будемо, програючи журнал подій з початку:

```ts
const read = new Projection();
for (const e of journal) read.notify(e);   // перебудова з нуля
```

І тут `unlockedToday += 1` стає бомбою: кожне перегравання **додає** зверху, і після другого прогону лічильник подвоївся. Перебудова, яка мала відновити правду, її спотворює. Це загальний закон читацьких моделей: `notify` мусить бути [ідемпотентним](book:programming/idempotency) — застосувати ту саму подію двічі має давати той самий рядок. Надійний спосіб — не тримати лічильник як інкремент, а зробити його **чистою функцією журналу** (`unlockedToday = journal.filter(e => e.type === "DoorUnlocked").length`), або запам'ятовувати позицію в журналі, до якої проєкцію вже докрутили, і ніколи не застосовувати одну подію двічі. Той самий запобіжник, до речі, рятує проєкцію й від дублів, які приносить шина.

**Згортка на читанні росте O(n) — і колись з'їсть читання.** `EventTruth.state()` згортає **весь** журнал на кожен запит. На замку з десятком подій — дрібниця; на агрегаті з мільйоном записів кожне читання перемелює мільйон. Класичний лік — **знімок** (snapshot): раз-на-скількись згорнути журнал до позиції K, зберегти згорнутий стан і далі згортати лише короткий хвіст після знімка.

```ts
// замість згортати ввесь журнал — знімок на позиції K + тільки хвіст після нього
const s = journal.slice(snapshot.pos).reduce(apply, snapshot.state);
```

Ціною за це — ще трохи машинерії (знімки треба робити, зберігати, інколи перебудовувати) і те саме, що вже стоїть у матриці: місце під журнал росте без стелі, і його доводиться архівувати.

**Схема подій — однобічні двері.** І остання пастка не технічна, а часова, і стосується лише правого стовпця. Щойно `DoorEvent` полетів у журнал і на нього сперлися проєкції та звіти, його **форма стає опублікованим контрактом**. Ти вже не перепишеш стару подію заднім числом — на неї спираються читачі, і будь-яка зміна ризикує зламати кожного з них. Це [закон Гайрама впритул](guide:progarch/what-makes-irreversible/math-hyrum-law.md): за достатньої кількості читачів кожна помітна властивість твоєї події вже комусь потрібна. Далі схему можна тільки **доповнювати** — нові типи подій, версії старих, — але не переграти минуле начисто. Вісь правди тому й найглибша з двох: `FoldOnRead` проти `Projection` завжди можна переставити назад за спринт роботи, а `EventTruth` замість `CrudTruth` — це рішення, що живе рівно стільки, скільки живуть накопичені дані.

## Що лишається в руках

Ми взяли один дрібний замок і написали його по двох осях так, що незалежність осей стала не обіцянкою, а фактом системи типів: два інтерфейси, `Truth` і `Read`, жодного разу не згадують одне одного, тому будь-яка правда стикається з будь-яким читанням, і чотири робочі системи впали з чотирьох рядків складання. Це і є весь доказ ортогональності — не абзац переконування, а те, що компілятор пропустив усі чотири комбінації без жодної спільної проводки.

І поряд із доказом — чотири рахунки, які тепер лежать на долоні. Вісь читання торгує лагом і другою моделлю за миттєве, багате читання; вісь правди торгує місцем і незворотною схемою за аудит і перегравання. Кут `✓ ✓` не має власної ціни — він просто носить обидва рахунки разом. А найгостріші граблі — подвійний запис у `send`, неідемпотентний `+= 1` під перегравання, O(n)-згортка без знімків — не десь у теорії, а рівно в тих рядках, які ми написали; кожна з них має ім'я й лік, і кожну видно наперед, щойно знаєш, куди дивитись.

Чого ми тут свідомо **не** робили — то не обирали, який із цих чотирьох кутів поставити в бій під твін дому. Це окрема, більша робота: зважити конкретні вимоги дзеркала стану проти цих чотирьох рахунків і скроїти під них композицію. Її беруть наступні кроки. Цей проєкт дав під той вибір найпотрібніше — тверде, руками промацане знання, що вибирати доведеться **не «підхід», а положення двох незалежних тумблерів**, і що кожне з чотирьох положень має свій, наперед відомий рахунок.
