# Історія еволюції механізмів оновлення даних: від Maintenance Windows до Kappa-архітектури

Проблема безпечної обробки історичних даних та повторного обчислення доменних станів супроводжує індустрію програмної інженерії з моменту виникнення перших комерційних систем керування базами даних (СУБД) наприкінці 1970-х років. Спосіб, у який інженери розв'язували задачу «застосування нового коду до минулих даних», постійно змінювався під тиском двох факторів: зростання обсягів збереженої історії та вимог щодо безперервної доступності сервісів (SLA/SLO).

---

## 1. Ера технічних вікон обслуговування (1980–1990-ті)

У перші десятиліття розвитку корпоративних СУБД (IBM DB2, Oracle 7, Sybase, Microsoft SQL Server 6.5) панівною парадигмою була концепція **Maintenance Window (вікна технічного обслуговування)**. 

Оскільки бізнес більшості підприємств був строго локальним і прив'язаним до робочих годин (з 9:00 до 18:00 у конкретному часовому поясі), системні адміністратори мали у своєму розпорядженні 8–10 годин нічного часу та повні вихідні дні для проведення будь-які маніпуляцій з даними.

### Технічна механіка того часу:

1. **Повна зупинка додатка (Cold Maintenance):**
   О 22:00 веб-сервери або термінали OLTP відключалися від бази даних. Пул користувачів обнулявся, блоки СУБД ставали повністю статичними.
2. **Пряме виконання скриптів PL/SQL або T-SQL:**
   Інженери запускали монолітні курсори або процедури, які в єдиному монолітному циклі оновлювали мільйони рядків:
   ```sql
   -- Типовий підхід 1990-х років у нічному вікні
   DECLARE
       CURSOR c_orders IS SELECT id, total_amount FROM orders FOR UPDATE;
   BEGIN
       FOR r IN c_orders LOOP
           UPDATE orders 
           SET tax_v2 = r.total_amount * 0.20 
           WHERE CURRENT OF c_orders;
       END LOOP;
       COMMIT;
   END;
   ```
3. **Резервне копіювання на магнітні стрічки (Tape Backups):**
   Захистом від помилок у бекфіл-скриптах слугував повний знімок бази даних (Full Dump), збережений на магнітну стрічку перед початком робіт. Якщо процедура зазнавала невдачі або виходила за межі часового вікна (наприклад, перевищувала 6 годин), базу відкочували назад шляхом повного відновлення зі стрічки, а реліз нової версії коду відкладали на наступні вихідні.

### Занепад парадигми:
З появою глобального інтернету, транскордонної електронної комерції та цілодобових сервісів (24/7/365) поняття «нічного вікна» остаточно зникло. Зупинка продакшну навіть на одну годину означала мільйонні збитки та пряме порушення контракту SLA.

## 2. Ера батчевих ETL та Hadoop (2000–2010-ті)

Із вибуховим зростанням обсягів даних (Big Data) на початку 2000-х років реляційні СУБД перестали вміщати історичні масиви. Для аналітики та бекфілу почали використовувати виділені ETL-комплекси (Extract, Transform, Load) та розподілену екосистему Apache Hadoop (MapReduce, Hive, Pig).

### Парадигма Lambda-архітектури (Nathan Marz, 2011)

Для поєднання живої обробки та повторного обчислення історії Натан Марц (створювач Apache Storm) запропонував **Lambda-архітектуру (Lambda Architecture)**.

Система ділилася на три шари:
1. **Speed Layer (Шаровий потік):** обробляв лише свіжі дані за останні декілька годин з низькою затримкою (Real-time Stream Processing), компенсуючи затримку батч-шару.
2. **Batch Layer (Батчевий шар):** зберігав незмінні первинні дані (Immutable Master Dataset) у HDFS і щоночі перераховував усю історію за допомогою MapReduce-завдань.
3. **Serving Layer (Шаровий шар):** об'єднував результати з Speed та Batch шарів для надання кінцевим користувачам узгодженої вітрини.

```
                           +---> Speed Layer (Apache Storm) ----+
                           |     (Low latency, eventual)         |
[ Потік подій (Events) ] --+                                     +--> Serving Layer
                           |                                     |    (Merged View)
                           +---> Batch Layer (Hadoop MapReduce) -+
                                 (High latency, accurate)
```

### Драматичні недоліки Lambda-архітектури:
Головним болем інженерів стала **подвійна кодова база (Dual Codebase Problem)**. Бізнес-логіку обчислення (наприклад, розрахунок скорингу клієнта) доводилося писати двічі: один раз мовою Java/C++ для потокового двигуна Storm, і другий раз мовою MapReduce/Hive SQL для батчевого двигуна Hadoop.

Будь-яка зміна бізнес-правила вимагала синхронного правлення двох різних кодових баз. Найменша розбіжність між ними викликала фантомні розходження у даних, а проведення бекфілу в Batch Layer вимагало величезних обчислювальних ресурсів кластера.

## 3. Революція Kappa-архітектури та CDC (2014 — дотепер)

У 2014 році Джей Клепс (Jay Kreps, один із соавторів Apache Kafka та співзасновник Confluent) опублікував маніфест «Questioning the Lambda Architecture», запропонувавши **Kappa-архітектуру (Kappa Architecture)**.

Головна ідея Kappa-архітектури: **усунути Batch Layer повністю і обробляти як живий трафік, так і всю історію єдиним потоковим рушієм (Stream Processor)**.

```
[ Immutable Log (Kafka) ] ===> [ Single Stream Engine (Flink/Kafka Streams) ] ===> [ Serving Store ]
```

### Механізм бекфілу в Kappa-архітектурі:
1. **Єдине джерело правди:** вся історія системних подій зберігається у розподіленому журналі подій (Log Retention = Infinite або Long-term Storage у S3/Iceberg).
2. **Перезапуск через Shadow Consumer:** для репроцесингу чи бекфілу створюється новий екземпляр того самого потокового коду (v2).
3. **Скидання оффсета:** новий споживач зчитує топік Kafka з першого збереженого оффсета (`offset = 0`).
4. **Паралельне перемикання:** після того як споживач v2 вичитає весь лог і наздожене поточний час, трафік читання API перемикається на нову вітрину, а екземпляр v1 утилізується.

## 4. Сучасний стан: CDC (Change Data Capture) та безблокувальні міграції

Сучасний етап розвитку (2020-ті роки) характеризується поєднанням транзакційних СУБД із потоковими платформами через **Change Data Capture (CDC)** (наприклад, Debezium).

Замість того щоб сканувати реляційну базу важелезними SQL-вибірками, CDC-агент вичитає журнал передзапису СУБД (PostgreSQL WAL або MySQL Binlog) безпосередньо з диска СУБД без створення жодних locks на рівні SQL. Зміни перетворюються на потік подій Kafka, де бекфіл-worker'и обробляють їх у режимі сліпого теневого повтору (Shadow Replay).

Еволюція механізмів обробки даних остаточно довела: спроби оновити дані «на місці» у транзакційній СУБД під живим трафіком не масштабуються. Безпечне майбутнє спирається на незмінні журнали подій, адитивні розширення схем (Dual-Write) та асинхронні потокові репроцесори.
