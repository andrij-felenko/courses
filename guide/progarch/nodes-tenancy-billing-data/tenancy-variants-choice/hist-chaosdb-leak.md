# 📜 Історія ChaosDB: провал мультиарендності у найглибшому шарі

У серпні 2021 року дослідники з компанії Wiz виявили в хмарній БД Microsoft Azure Cosmos DB критичну вразливість, яка отримала назву **ChaosDB**. Цей інцидент увійшов до підручників з системної архітектури як один із найяскравіших прикладів того, как одна дрібна помилка в допоміжному мультиарендному сервісі здатна повністю зруйнувати ізоляцію даних між тисячами клієнтів на найглибшому інфраструктурному рівні.

Cosmos DB — це розподілена NoSQL-база даних Azure, якою користуються найбільші світові компанії для збереження фінансових записів, персональних даних та бізнес-критичної інформації. На папері платформа гарантувала сувору ізоляцію орендарів: кожен клієнт мав власні ключі доступу (Primary Keys), а дані ізолювалися за допомогою криптографічних меж та моделей доступу на рівні облікових записів. Проте вразливість виникла не в самому ядрі бази даних, а в новій функції, доданій для зручності розробників — вбудованій інтеграції з Jupyter Notebooks.

## Передумови: впровадження спільного середовища виконання

У 2019 році команда Azure Cosmos DB вирішила інтегрувати середовище Jupyter Notebooks прямо в консоль Azure Portal. Ідея виглядала привабливо: розробник міг відкрити браузер, написати декілька рядків коду мовою Python чи SQL і одразу візуалізувати аналітику над даними своєї бази без встановлення локальних утиліт.

З архітектурної точки зору інтеграція Jupyter Notebooks вимагала запуску контейнерів із середовищем виконання коду Python. Щоб не створювати повноцінну виділену віртуальну машину для кожного невеликого облікового запису (що зробило б функцію занадто дорогою для компанії), розробники Azure використали **спільну мультиарендну інфраструктуру (Pool model)** для обчислювальних контейнерів. 

Контейнери різних орендарів запускалися на спільних вузлах Kubernetes, а допуск до бази даних здійснювався за допомогою спеціального внутрішнього сервісу-проксі (Jupyter Service Wrapper). Кожен вузол обробляв контейнери кількох десятків різних клієнтів Azure.

У цій схемі було зроблено фатальне припущення: передбачалося, що межі контейнерів Docker та внутрішні токени автентифікації надійно відокремлюють право робити запити одного користувача від іншого.

## Анатомія провалу: від незахищеного порту до чужих ключів

У серпні 2021 року дослідники безпеки Нір Охфельд (Nir Ohfeld) та Сагі Цадік (Sagi Tzadik) з Wiz вирішили протестувати межі ізоляції цієї мультиарендної інтеграції. Вони виявили послідовність із трьох архітектурних помилок, яка перетворила теоретичний ризик на повну компрометацію бази даних:

### 1. Незахищений внутрішній сервіс (Late Binding Authentication)

У контейнері Jupyter працював фоновий процес `cdb-init`, який відповідав за первинну конфігурацію та підключення до Cosmos DB. Цей процес слухав локальний мережевий порт і приймав параметри підключення від внутрішнього сервісу Azure. 

Дослідники виявили, що процес не перевіряв автентичність запитів, які надходили на цей порт із внутрішньої мережі контейнера. Будь-який процес усередині контейнера міг відправляти команди керування для `cdb-init` без проходження перевірки прав.

### 2. Ескалація привілеїв у спільному обчислювальному середовищі

Оскільки користувач мав повний контроль над кодом усередині свого Jupyter Notebook (робоче середовище надавало root-доступ всередині Docker-контейнера), дослідники змогли встановити власний мережевий сканер і проаналізувати роботу внутрішньої мережі Kubernetes-вузла. 

Вони виявили, що внутрішній проксі-сервіс `JupyterHubWrapper`, який працював на тому самому вузлі, зберігав у пам'яті тимчасові токени доступу до керуючого сервісу Cosmos DB для всіх контейнерів, запущенних на цьому вузлі.

### 3. Витік первинних ключів (Primary Key Leakage)

Найгірше чекало попереду. Використовуючи отримані тимчасові токени та локальну ескалацію привілеїв, дослідники змогли звернутися до внутрішнього REST API управління інстансами Jupyter. Відповідь сервісу містила не просто тимчасовий токен читання, а **первинні ключі доступу (Primary Master Keys)** до інших облікових записів Cosmos DB, що працювали на тому ж інфраструктурному вузлі!

Первинний ключ у Cosmos DB дає абсолютні права на читання, запис та видалення всіх даних в обліковому записі бази даних. Маючи лише первинний ключ, зловмисник міг підключитися до бази даних будь-якого іншого орендаря через стандартний REST API з будь-якої точки світу, оминаючи всі налаштовані брандмауери, IP-whitelists та ролі доступу до бази даних.

Дослідники демонстративно отримали повний доступ до баз даних сотень великих компаній (включаючи транснаціональні корпорації, банківський сектор та медичні установи), не зробивши жодного злому самої бази даних — їм знадобився лише один клік для активації Jupyter Notebook у власному тестовому акаунті Azure.

## Архітектурний розбір: чому провалилася ізоляція

Вразливість ChaosDB виникла не через банальну одрукарку в коді, а через **системний компроміс при проєктуванні мультиарендної інфраструктури**:

### Помилка 1. Плутанина меж безпеки (Security Boundaries)

Розробники вважали межею ізоляції веб-інтерфейс Azure Portal. Насправді ж справжньою межею став користувацький код Python, якому дозволили виконуватися на спільній інфраструктурі. 

У момент, коли ви дозволяєте користувачеві запускати довільний код (Arbitrary Code Execution) у спільному басейні (Pool), ізоляція на рівні стандартних процесів ОС чи контейнерів Docker стає недостатньою. Необхідне використання апаратних мікро-ВМ (наприклад, AWS Firecracker чи gVisor), які створюють жорстку гіпервізорну перегородку.

### Помилка 2. Централізація Master-секретів у спільному процесі

У внутрішньому проксі-сервісі зберігалися первинні ключі різних орендарів. Вбудована архітектура не дотримувалася принципу найменших привілеїв (Least Privilege): замість генерації короткоживучих обмежених токенів доступу (Scoped Short-lived Tokens) для кожної сесії середовище оперувало Master-ключем, який дає повний доступ до всього акаунта.

Якби Jupyter Notebook отримував токен доступу лише до конкретного ресурсу й лише на читання протягом 15 хвилин, витік цього токена не дозволив би зловмиснику перехопити управління всією базою даних.

### Помилка 3. Відсутність Bulkhead (ізоляції вибуху)

Усі орендарі, які вмикали додаткову функцію аналітики, потрапляли в один спільний басейн обчислень. Збій або компрометація одного орендаря миттєво поширювалися на всіх сусідів по басейну. Повна відсутність мережевих перегородок між контейнерами різних орендарів усередині одного вузла Kubernetes дозволила провести атаку горизонтального переміщення (Lateral Movement).

Microsoft відреагувала миттєво: після закритого звіту Wiz компанія відключила функцію Jupyter Notebooks протягом кількох годин, а пізніше примусово відкликала та перевидала первинні ключі для тисяч клієнтів.

## Наслідки ChaosDB для індустрії хмарних обчислень

До виявлення ChaosDB більшість розробників хмарних застосунків вважали, що мультиарендні послуги Tier-1 хмарних провайдерів (AWS, Azure, GCP) гарантують абсолютну ізоляцію за замовчуванням. ChaosDB розвіяв цю ілюзію і спровокував масштасну переоцінку ризиків використання спільних сервісних шарів:

* **Модель спільної відповідальності (Shared Responsibility Model):** Хмарний провайдер відповідає за фізичну ізоляцію баз даних, але допоміжні сервіси візуалізації, аналітики чи генерації звітів часто створюються з нижчими вимогами до безпеки.
* **Перехід на Zero-Trust всередині хмари:** Внутрішні мережі між мікросервісами провайдера більше не вважаються безпечними. Кожен внутрішній REST-запит зобов'язаний вимагати строго підписаний Mutual TLS (mTLS) та JWT-токен із контекстом конкретного орендаря.
* **Відмова від довговічних Master-ключів:** Більшість сучасних хмарних баз даних (AWS DynamoDB, Azure Cosmos DB, Google Cloud Spanner) після 2021 року почали переводити клієнтів із систем статичних ключів доступу на динамічну IAM-автентифікацію (Identity and Access Management) з короткоживучими токенами.

## Уроки для архітектора мультиарендних систем

Історія ChaosDB дає п'ять критичних висновків для будь-якої команди, яка будує SaaS-платформу або multi-tenant систему:

1. **Ізоляція орендарів визначається найслабшим ланцюгом.** Не має значення, наскільки надійно захищена ваша основна PostgreSQL чи Cosmos DB, якщо допоміжний сервіс генерації PDF-звітів, аналітичний дашборд чи черга фонових задач використовує спільний сервісний акаунт із доступом до даних усіх орендарів.
2. **Ніколи не передавайте Master-ключі в мультиарендне середовище.** Якщо компонент системи працює в контексті конкретного орендаря (наприклад, обробляє його запит або виконує його фоновий скрипт), він мусить володіти лише тимчасовими credentials, обмеженими суворо цим `tenant_id`.
3. **Уникайте спільного виконання користувацького коду в Pool-моделі.** Якщо ваша платформа дозволяє користувачам завантажувати скрипти, плагіни або складні вирази, це середовище виконання має бути ізольоване на рівні віртуальних машин, а не простих процесів чи підмереж.
4. **Спільні внутрішні проксі — це магніт для атак cross-tenant.** Будь-яка централізована точка, яка знає секрети багатьох орендарів, стає мішенню №1. Сплануйте її так, щоб вона взагалі не мала доступу до відкритих ключів або даних.
5. **Тестуйте не лише автентифікацію, а й горизонтальну ескалацію.** Головний тест для мультиарендної системи — це не «чи можу я увійти без пароля», а «що станеться, якщо орендар A підставить ідентифікатор орендаря B у внутрішній мережевий запит».

ChaosDB довів: ізоляція орендарів — це не прапорець у конфігураторі і не один рядок `WHERE tenant_id = ...`. Це скнара дисципліна, яка вимагає перевірки меж доступу на кожному шарі системи — від HTTP-маршрутизатора до внутрішньої черги та тимчасових файлів на диску.
