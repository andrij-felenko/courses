# 🧮 Криптографічне запечатування реєстру: математика хеш-ланцюжків

Реляційна база даних або файл на диску гарантують атомарність і логічну цілісність, але не захищають від прямого втручання адміністратора з привілеями `root` або модифікацій на рівні накопичувача. Для доведення того, що жоден запис у хронології проводжень не був підроблений, відредагований чи видалений за останні роки, застосовується математична модель **криптографічного запечатування** (Tamper-evident Hash Chain).

В основі цього підходу лежить перетворення послідовності незалежних дій на рекурсивно зв'язаний інформаційний граф, де кожне наступне значення жорстко залежить від криптографічного дайджесту всієї попередньої історії.

### 1. Фундаментальні криптографічні припущення

Математична безпека запечатаного реєстру спирається на три властивості криптографічно стійких односпрямованих хеш-функцій (таких як SHA-256 чи BLAKE3):

1. **Стійкість до первинного образу (Pre-image resistance)**. За заданим значенням хешу `H` обчислювально неможливо знайти вхідне повідомлення `M` таке, що `Hash(M) = H`. Це означає, що зловмисник не може «підігнати» вміст фіктивної транзакції під вже існуючий хеш.
2. **Стійкість до колізій (Collision resistance)**. Обчислювально неможливо знайти два різних вхідних повідомлення `M₁ ≠ M₂` таких, що `Hash(M₁) = Hash(M₂)`. Для SHA-256 складність пошуку колізії становить `O(2¹²⁸)` операцій завдяки парадоксу днів народження, що робить практичний підбір колізії нереалізованим на наявному обчислювальному залізі.
3. **Лавинний ефект (Avalanche effect)**. Зміна хоча б одного біта у вхідному повідомленні `M` призводить до непередбачуваної зміни в середньому 50% бітів у підсумковому хеші `H`. Неможливо змінити один цент у сумі транзакції так, щоб підсумковий хеш зазнав лише дрібних локальних змін.

### 2. Формальна модель послідовного хешування (Hash Chain)

Нехай `E₀, E₁, E₂, ..., Eₙ` — це послідовність записів фінансових проводжень (ledger entries), впорядкована за часом створення. Кожен запис `Eᵢ` являє собою структурований кортеж даних, який включає унікальний ідентифікатор проведення, ID транзакції, ID дебетового та кредитового рахунків, суму в центах та часову мітку ISO-8601.

Для кожного запису `Eᵢ` розраховується криптографічний дайджест `Hᵢ` за допомогою рецепта послідовного зв'язування:

```
H₀ = SHA256(Genesis_Seed ∥ E₀)
H₁ = SHA256(H₀ ∥ E₁ ∥ Timestamp₁)
H₂ = SHA256(H₁ ∥ E₂ ∥ Timestamp₂)
...
Hᵢ = SHA256(Hᵢ₋₁ ∥ Eᵢ ∥ Timestampᵢ)    [для будь-якого i ≥ 1]
```

Значення `Hᵢ` функціонально залежить від вмісту поточного запису `Eᵢ` та **усієї попередньої історії** `E₀ ... Eᵢ₋₁`. Це утворює односпрямований рекурсивний математичний ланцюжок. Жоден запис не існує изолировано: він несе в собі криптографічний «відбиток» усіх минулих подій від моменту ініціалізації системи.

### 3. Формальне доведення виявлення фальсифікацій

Доведемо за допомогою математичної індукції, що будь-яка модифікація минулого запису спричиняє повну руйнацію ланцюжка хешів до самого верху.

**База індукції**: Припустимо, що зловмисник намагається непомітно змінити суму проведення у минулому записі `Eₖ` (де `0 ≤ k < n`), підмінивши значення `Eₖ` на `Eₖ'`.

За властивістю стійкості до колізій хеш-функції:

```
Hₖ' = SHA256(Hₖ₋₁ ∥ Eₖ' ∥ Timestampₖ) ≠ Hₖ
```

**Крок індукції**: Розглянемо розрахунок хешу наступного запису `Hₖ₊₁`. У неушкодженому реєстрі збережений хеш дорівнює `Hₖ₊₁ = SHA256(Hₖ ∥ Eₖ₊₁ ∥ Timestampₖ₊₁)`. При спробі перевірити цілісність з урахуванням зміненого запису `Eₖ'` перевірочний алгоритм обчислить:

```
Розрахований Hₖ₊₁' = SHA256(Hₖ' ∥ Eₖ₊₁ ∥ Timestampₖ₊₁)
```

Оскільки `Hₖ' ≠ Hₖ`, а хеш-функція стійка до колізій, отримуємо `Hₖ₊₁' ≠ Hₖ₊₁`. За індукцією для будь-якого `j > k`:

```
Hⱼ' ≠ Hⱼ
```

Отже, зміна хоча б одного цента в записі `Eₖ` робить невалідними **всі без винятку** наступні хеші в базі даних від `k` до `n`.

Для того, щоб непомітно фальсифікувати один минулий запис `Eₖ`, зловмиснику довелося б заново переобчислити всі хеші `Hₖ, Hₖ₊₁, ..., H♙`. Щоб заблокувати можливість заднього переобчислення, верхівка хеш-ланцюжка (Head Hash `H♙`) періодично підписується асиметричним цифровим підписом (RSA-4096 або Ed25519) із використанням закритого ключа, який зберігається у приватному апаратному модулі безпеки (HSM), та публікується у зовнішнє незмінне сховище (WORM / AWS QLDB). Підробка стає обчислювально неможливою без зламу криптографічного ключа.

### 4. Ієрархічні дерева Меркла (Merkle Tree Seal)

У масштабних фінансових системах з мільйонами проводжень за день послідовна перевірка хеш-ланцюжка `O(N)` стає надто повільною для оперативних аудитів. Для досягнення логарифмічної швидкості перевірки `O(log N)` проводження групуються у часові блоки (наприклад, за кожну годину) і для них будується бинарне Дерево Меркла.

```
                  Корінь (Merkle Root R)
                       /          \
              H₀₁ = H(H₀∥H₁)      H₂₃ = H(H₂∥H₃)
               /       \          /        \
             H₀         H₁       H₂         H₃
             |          |        |          |
             E₀         E₁       E₂         E₃
```

Кожен листовий вузол дерева являє собою хеш окремого проведення `Hᵢ = SHA256(Eᵢ)`. Батьківські вузли утворюються як хеш конкатенації двох дочірніх вузлів `Hᵢⱼ = SHA256(Hᵢ ∥ Hⱼ)`. Процес повторюється до утворення єдиного верхівкового значення — Коріння Меркла (Merkle Root `R`).

Висота дерева для `N` проводжень у блоці обчислюється як `h = ⌈log₂ N⌉`. Для блоку з 1 000 000 проводжень висота дерева становить лише 20 рівнів.

#### Логарифмічний доказ входження (Merkle Proof)

Якщо клієнт або аудитор бажає довести, що конкретна транзакція `E₂` дійсно була зафіксована в базі даних і не змінювалася, серверу не потрібно передавати весь мільйон записів блоку. Сервер надає лише доказ входження (Merkle Proof), що складається з логарифмічного набору сусідніх хешів `[H₃, H₀₁]`.

Алгоритм перевірки на боці аудитора виконується за логарифмічний час:

```
Крок 1: Обчислити хеш досліджуваного запису: H₂ = SHA256(E₂)
Крок 2: Обчислити батьківський хеш гілки:    H₂₃' = SHA256(H₂ ∥ H₃)         [H₃ надається у доказі]
Крок 3: Обчислити перевірочний корінь:      Root' = SHA256(H₀₁ ∥ H₂₃')      [H₀₁ надається у доказі]
Крок 4: Перевірка інваріанту цілісності:   Root' == Signed_Merkle_Root
```

Якщо `Root' == Signed_Merkle_Root`, математично доведено, що запис `E₂` існував у реєстрі у момент формування підпису і його вміст не зазнав жодного редагування.

### 5. Захист від підміни підпису, HMAC та процедура автоматичного аудиту

Дві додаткові математичні аномалії, які мусить блокувати запечатаний лог:

1. **Атака обрізанням (Truncation Attack)**. Зловмисник не редагує записи, але видаляє останні `K` проводжень із бази даних. Для захисту від обрізання кожен хеш `Hᵢ` містить монотонно зростаючий порядковий номер `Sequence_ID` та мітку часу `Timestamp`. Зникнення останніх записів призводить до розходження із раніше опублікованим підписаним коренем.
2. **Атака підміною ключа (HMAC-Authentication)**. Якщо хеш-ланцюжок будується без використання ключа, будь-хто з доступом до БД може створити альтернативний валідний ланцюжок. Для запобігання цьому хешування виконується через алгоритм HMAC-SHA256 із секретним аудит-ключем `K_audit`:

```
H_i = HMAC-SHA256(K_audit, H_{i-1} ∥ E_i ∥ Sequence_ID_i)
```

Завдяки цьому несанкціоноване переобчислення хеш-ланцюжка вимагає знання секретного ключа `K_audit`, доступ до якого обмежений на рівні апаратного модуля безпеки.

#### Алгоритм автоматизованої перевірки аудиту (Audit Verification Loop)

У продакшен-середовищі фоновий процес аудиту (Audit Watchdog) кожні 5 хвилин пробігає по нових блоках проводжень і виконує три операції:

```
1. Для кожного нового запису E_i обчислити HMAC-SHA256(K_audit, H_{i-1} || E_i).
2. Звірити обчислений хеш із записаним у колонку hash таблиці ledger_entries.
3. При виявленні найменшої розбіжності:
   - Негайно перевести білінг у режим Read-Only (Safety Lock);
   - Згенерувати критичний алерт SecurityIncident;
   - Фіксувати точний ID першого ушкодженого запису E_k для розслідування.
```

Цей математичний бар'єр гарантує, що жодне несанкціоноване втручання в базу даних не лишиться непоміченим.
