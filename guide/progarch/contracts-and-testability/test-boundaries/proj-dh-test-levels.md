# ⚙️ Прогін трьох рівнів у Digital Homes: одна грілка, три радіуси

Ми домовилися, що рівень тесту — це радіус кола навколо справжнього коду, і що радіус обирають під ризик. Домовитися легко; повірити — лише коли побачиш це на робочому коді, який запускається. Тож візьмімо ту саму грілку Digital Homes, яку вже знаємо напам'ять, і покриймо **одну** її поведінку — «у холодній кімнаті грій має ввімкнутися» — трьома різними радіусами. А щоб перевірка не була показною, підкладемо під неї три різні баги й подивимося чесно: кожен із них проскакує повз одні кола й гине на іншому. Не тому, що менші тести кепські, а тому, що баг живе поза їхнім колом — там, де дублер уже підмінив собою реальність.

Задача проста до банальності, і саме тому добра для досліду. Один вхід — температура. Один вихід — реле ввімкнене чи ні. Одне правило між ними. Якщо навіть на цьому мікроскопічному прикладі три рівні ловлять три різні класи помилок, то в справжній системі різниця між ними — не педантизм, а те, впіймаєш ти аварію до продакшену чи після.

## Спільний код під тестом

Головна умова досліду: **усі три рівні перевіряють один і той самий код**. Не три різні реалізації — одну. Змінюється лише радіус: скільки цього коду лишається справжнім усередині кола, а скільки відсунуто за дублер. Ось та система, яку ми несемо крізь курс, — той самий `thermostat`, у якому ми колись [відкрили шов на давачі](guide:progarch/seams-and-boundaries), доповнений вендоровим адаптером і тонкою збіркою-хабом.

:::tabs
```ts
// thermostat.ts — СИСТЕМА (те, що поїде в прод). Один код на всі три рівні.
export interface Sensor { read(): number; }        // контракт: завжди віддає °C
export interface Heater { on(): void; off(): void; }

// політика + проводка: читає крізь шов, керує грілкою
export function decide(sensor: Sensor, heater: Heater, threshold: number): void {
  if (sensor.read() < threshold) heater.on();
  else heater.off();
}

export interface Device { tempF(): number; }        // вендорів пристрій говорить у °F

// адаптер: вендорові °F → наші °C. Тут — правильна версія.
export class VendorSensorAdapter implements Sensor {
  constructor(private device: Device) {}
  read(): number {
    return (this.device.tempF() - 32) * 5 / 9;
  }
}

export type Config = { threshold: number };

// хаб: те, що прод збирає й крутить — справжній давач, справжня грілка, оберти
export class Hub {
  constructor(private sensor: Sensor, private heater: Heater,
              private threshold: number) {}
  tick(): void { decide(this.sensor, this.heater, this.threshold); }
  run(everyMs: number): void { setInterval(() => this.tick(), everyMs); }
}

// збірка: розв'язує конфіг у зібраний хаб (те саме, що кличе прод на старті)
export function buildHub(sensor: Sensor, heater: Heater, cfg: Config): Hub {
  return new Hub(sensor, heater, cfg.threshold);
}
```
```py
# thermostat.py — СИСТЕМА (те, що поїде в прод). Один код на всі три рівні.
from dataclasses import dataclass
from typing import Protocol


class Sensor(Protocol):
    def read(self) -> float: ...          # контракт: завжди віддає °C

class Heater(Protocol):
    def on(self) -> None: ...
    def off(self) -> None: ...


# політика + проводка: читає крізь шов, керує грілкою
def decide(sensor: Sensor, heater: Heater, threshold: float) -> None:
    if sensor.read() < threshold:
        heater.on()
    else:
        heater.off()


class Device(Protocol):
    def temp_f(self) -> float: ...        # вендорів пристрій говорить у °F


class VendorSensorAdapter:                # адаптер: вендорові °F → наші °C (правильна версія)
    def __init__(self, device: Device) -> None:
        self._device = device
    def read(self) -> float:
        return (self._device.temp_f() - 32) * 5 / 9


@dataclass
class Config:
    threshold: float


class Hub:                                # те, що прод збирає й крутить
    def __init__(self, sensor: Sensor, heater: Heater, threshold: float) -> None:
        self._sensor, self._heater, self._threshold = sensor, heater, threshold
    def tick(self) -> None:
        decide(self._sensor, self._heater, self._threshold)


def build_hub(sensor: Sensor, heater: Heater, cfg: Config) -> Hub:
    return Hub(sensor, heater, cfg.threshold)
```
:::

І дублери — рівно ті, що [заслуговують місця на справжньому шві](guide:progarch/test-doubles-when): фейк давача, що віддає задане число, шпигун грілки, що нічого не гріє, лише пам'ятає стан, і фейк вендорового пристрою, що говорить у Фаренгейтах.

:::tabs
```ts
// doubles.ts — те, що вішаємо ЗОВНІ розрізу
export class FakeSensor implements Sensor {          // фейк: віддає задане число (у °C)
  constructor(private celsius: number) {}
  read(): number { return this.celsius; }
}
export class SpyHeater implements Heater {           // шпигун: не гріє, лише пам'ятає стан
  isOn = false;
  on()  { this.isOn = true; }
  off() { this.isOn = false; }
}
export class FakeDevice implements Device {          // фейк вендорового пристрою — у °F
  constructor(private opts: { tempF: number }) {}
  tempF(): number { return this.opts.tempF; }
}
```
```py
# doubles.py — те, що вішаємо ЗОВНІ розрізу
class FakeSensor:                         # фейк: віддає задане число (у °C)
    def __init__(self, celsius: float) -> None:
        self._c = celsius
    def read(self) -> float:
        return self._c

class SpyHeater:                          # шпигун: не гріє, лише пам'ятає стан
    def __init__(self) -> None:
        self.is_on = False
    def on(self) -> None:  self.is_on = True
    def off(self) -> None: self.is_on = False

class FakeDevice:                         # фейк вендорового пристрою — у °F
    def __init__(self, temp_f: float) -> None:
        self._f = temp_f
    def temp_f(self) -> float:
        return self._f
```
:::

Усе. Далі не з'явиться жодного нового рядка системи — лише три способи обвести її колом.

## Рівень 1 — модульний: коло на `decide`

Найменший радіус лишає всередині саму `decide`. Усе довкола — дублери: у шов давача стає `FakeSensor`, у шов грілки — `SpyHeater`. Пишемо дві перевірки: холодно — грій вмикається; рівно на порозі — не вмикається.

:::tabs
```ts
test('модульний: нижче порога → грій вмикається', () => {
  const heater = new SpyHeater();
  decide(new FakeSensor(18), heater, 20);   // «давач дає 18 °C» — це НАШЕ припущення
  expect(heater.isOn).toBe(true);
});

test('модульний: рівно на порозі → грій не вмикається', () => {
  const heater = new SpyHeater();
  decide(new FakeSensor(20), heater, 20);   // 20 < 20 — хибно
  expect(heater.isOn).toBe(false);          // ловить «<=» замість «<»
});
```
```py
def test_unit_below_threshold_heats():
    heater = SpyHeater()
    decide(FakeSensor(18), heater, threshold=20)   # «давач дає 18 °C» — НАШЕ припущення
    assert heater.is_on is True

def test_unit_at_threshold_stays_off():
    heater = SpyHeater()
    decide(FakeSensor(20), heater, threshold=20)   # 20 < 20 — хибно
    assert heater.is_on is False                   # ловить «<=» замість «<»
```
:::

**Що воно ловить.** Усе, що живе в самій політиці. Переплутав `<` на `>` — і перший тест почервоніє: холодна кімната замість грітися застигне. Написав `<=` замість `<` — другий тест упіймає це на самісінькому порозі, де різниця між «грій» і «спокій» вирішується одним знаком. Ця перевірка летить за мікросекунди, ніколи не мерехтить, і якщо впала — винна рівно `decide`, більше нема на кого думати. Це дно піраміди: таких тестів можна мати сотні й ганяти на кожне збереження файлу.

**Що воно пропускає — і то по побудові, а не через недогляд.** Придивись до `FakeSensor(18)`. Цим числом ми не спитали реальність — ми **вклали в неї своє припущення**: що давач говорить у Цельсіях. Модульне коло не може це припущення перевірити, бо справжнього давача в ньому немає — там сидить наша ж підробка, яка слухняно підтверджує те, у що ми віримо. Усе, що станеться між вендоровим залізом і числом `18`, для цього кола не існує. І ось туди ми зараз і підкладемо першу справжню помилку.

## Рівень 2 — інтеграційний: справжній адаптер у колі

Приходить давач нового вендора, його драйвер віддає температуру у Фаренгейтах, і хтось пише адаптер. Пише — і плутає одиниці: віддає вендорове число як є, наче воно вже в Цельсіях.

:::tabs
```ts
// БАГ у справжньому коді: адаптер переплутав шкали
export class VendorSensorAdapter implements Sensor {
  constructor(private device: Device) {}
  read(): number {
    return this.device.tempF();   // ← забув перевести: віддав °F як °C
  }
}
```
```py
class VendorSensorAdapter:                # БАГ: адаптер переплутав шкали
    def __init__(self, device: Device) -> None:
        self._device = device
    def read(self) -> float:
        return self._device.temp_f()      # ← забув перевести: віддав °F як °C
```
:::

Тепер найважливіший момент усього прогону. Ця помилка **вже в проді**, а модульний тест із попереднього розділу — **усе ще зелений**. Він і не міг почервоніти: у його колі немає адаптера, там `FakeSensor(18)` віддає чесні 18, `decide` слухняно вмикає грій, `isOn` дорівнює `true`. Тест доводить, що `decide` правильна, — і це правда. Він просто нічого не знає про те, що число до `decide` тепер приходить спотворене. Помилка одиниць живе у шві між вендором і правилом; модульне коло туди не сягає, тож помилка проходить повз нього, не залишивши й сліду.

Щоб її впіймати, розширмо радіус так, аби всередину потрапив **справжній** адаптер. Дублер відсувається на крок глибше — до самого пристрою, який чесно говорить у Фаренгейтах:

:::tabs
```ts
test('інтеграційний: справжній адаптер віддає правилу коректний °C', () => {
  const device = new FakeDevice({ tempF: 64.4 });   // сам пристрій — у °F
  const sensor = new VendorSensorAdapter(device);   // СПРАВЖНІЙ адаптер — усередині кола
  const heater = new SpyHeater();
  decide(sensor, heater, 20);
  expect(heater.isOn).toBe(true);   // 64.4 °F = 18 °C < 20 → мало ввімкнутися
});
```
```py
def test_integration_real_adapter_feeds_celsius():
    device = FakeDevice(temp_f=64.4)          # сам пристрій — у °F
    sensor = VendorSensorAdapter(device)      # СПРАВЖНІЙ адаптер — усередині кола
    heater = SpyHeater()
    decide(sensor, heater, threshold=20)
    assert heater.is_on is True               # 64.4 °F = 18 °C < 20 → мало ввімкнутися
```
:::

Пройдімо арифметику, якою тест ловить помилку. Правильний адаптер мав би порахувати

```
(64.4 − 32) · 5 / 9 = 32.4 · 5 / 9 = 162 / 9 = 18.0 °C
```

18 °C нижче за поріг 20 — грій вмикається, `isOn` стає `true`, тест зелений **по-справжньому**. Але наш багнутий адаптер повертає `read()` = 64.4, і `decide` бачить `64.4 < 20` — хибно, отже вимикає грій у холодній кімнаті. `isOn` лишається `false`, `expect(true)` не збігається — тест **червоніє**. Той самий баг, що безслідно проскочив крізь модульне коло, тут валить перевірку до продакшену. Ось за що інтеграційні тести їдять свій хліб: вони перевіряють ті шви, які модульні дублери заклеїли собою.

**Що воно ловить.** Помилки в склейці — сплутані одиниці, забуте перетворення, зсув на множник. Усе, що модульний дублер підмінив своїм чесним числом, тут перевіряється справжнім кодом.

**Що воно пропускає.** `FakeDevice({ tempF: 64.4 })` — теж дублер, а отже, теж **твердження**: «справжній вендорів пристрій говорить у Фаренгейтах і віддає рівно таке число». Якщо реальний драйвер насправді віддає десяті частки градуса рядком чи має інакше названий виклик — цей тест того не побачить, бо звіряється з нашим здогадом про пристрій, а не з ним самим. Саме тому кожен фейк [винен контрактний тест](book:programming/contract-testing): один набір перевірок, прогнаний і на фейку, і на справжньому драйвері, не дасть підробці тихо розійтися з боєм. Ми вже [бачили цю пастку живцем](guide:progarch/seams-and-boundaries/proj-dh-sensor-seam.md), коли `FakeSensor` віддавав `19.0`, а реальний 1-Wire — цілими мілі-градусами. Дубль чесний рівно настільки, наскільки чесний контракт, який ти на нього поклав.

## Рівень 3 — тонкий наскрізний: увесь хаб

Лишилося коло, яке нічого не пропускає повз межі системи. Підкладемо третій баг — цього разу не в політику й не в адаптер, а в **збірку**. `buildHub` під час якоїсь правки загубив поріг із конфігу й прибив на його місце нуль:

:::tabs
```ts
// БАГ у збірці: поріг із конфігу загублено
export function buildHub(sensor: Sensor, heater: Heater, cfg: Config): Hub {
  return new Hub(sensor, heater, 0);   // ← мало бути cfg.threshold
}
```
```py
def build_hub(sensor: Sensor, heater: Heater, cfg: Config) -> Hub:
    return Hub(sensor, heater, 0)        # ← мало бути cfg.threshold
```
:::

Тепер послухаймо, що кажуть менші кола. Модульний тест кличе `decide` **напряму**, передаючи поріг сам, — він `buildHub` навіть не торкається, отже зелений. Інтеграційний тест сам новує `VendorSensorAdapter` і кличе `decide` — теж повз збірку, теж зелений. Обидва менші кола прорізали `buildHub` дублером власних рук: вони вставляли шматки самотужки, а не брали їх зі збірки. Помилка проводки живе рівно там, куди жоден із них не заглядає.

Найбільший радіус засуває всередину **весь зібраний хаб** — той самий шлях, яким прод стартує систему: конфіг → `buildHub` → `tick`. Дублери лишаються тільки на двох фізичних краях, які в тесті інакше не мати: пристрій знизу (справжнього термометра в пам'яті не тримати) і реле згори (справжньої розетки не смикати). Усе між ними — справжнє.

:::tabs
```ts
test('наскрізь: холодна кімната крізь зібраний хаб → грій увімкнено', () => {
  const device = new FakeDevice({ tempF: 64.4 });        // єдиний дубль знизу — залізо термометра
  const heater = new SpyHeater();                        // єдиний дубль згори — фізичне реле
  const hub = buildHub(new VendorSensorAdapter(device),
                       heater, { threshold: 20 });        // конфіг → збірка
  hub.tick();                                             // один справжній оберт зібраного хаба
  expect(heater.isOn).toBe(true);
});
```
```py
def test_e2e_cold_room_through_hub_heats():
    device = FakeDevice(temp_f=64.4)                      # єдиний дубль знизу — залізо термометра
    heater = SpyHeater()                                 # єдиний дубль згори — фізичне реле
    hub = build_hub(VendorSensorAdapter(device),
                    heater, Config(threshold=20))         # конфіг → збірка
    hub.tick()                                            # один справжній оберт зібраного хаба
    assert heater.is_on is True
```
:::

Зі справжнім `buildHub` цей тест зелений: 64.4 °F стають 18 °C, поріг 20 доїжджає зі збірки цілим, 18 < 20 — грій вмикається. З багнутим — поріг усередині хаба дорівнює 0, `decide` бачить `18 < 0` — хибно, грій не вмикається, тест **червоніє**. І впіймав його **тільки** цей рівень: жодне менше коло не проходило крізь `buildHub`, а помилка сиділа саме там.

Зверни увагу, чому це «тонкий» наскрізний, а не «повний». Ми ганяємо один `tick`, а не `run` із цоканням годинника — розклад тестові не потрібен, ніхто не чекатиме тридцять секунд на кожен оберт. Один шлях, одне ствердження, зібрана система замість розібраних шматків. Наскрізних тримають одиниці саме тому, що кожен дорогий; марнувати їх на десять варіантів того, що чудово ловиться нижче, — витрата без нового знання.

**Що воно пропускає навіть тут.** Два дублери на краях — не випадковість, а стеля офлайн-тесту. Справжнє реле, що почало залипати, справжній термометр, що дрейфує на півградуса за місяць, — це не мешкає в пам'яті тестового процесу, і жодне коло їх не впіймає. Чесна відповідь — не вдавати покриття, а винести цю перевірку [в прод зондом спостережності](guide:progarch/observability-as-testability) і записати непокрите [рядком свідомого боргу](guide:progarch/debt-as-decision): «дрейф і залипання реального заліза офлайн не тестуємо; підстраховано прод-тривогою». Діра, яку назвали й оцінили, — уже не діра.

## Три баги, три кола

Складімо весь дослід в одну картину. Три помилки, три радіуси — і кожна помилка гине рівно на найдешевшому колі, усередині якого вона опинилася справжньою.

Баг логіки ловить уже модульний; баг одиниць сліпий для модульного, але ловить інтеграційний; баг проводки сліпий для двох менших, ловить лише наскрізний. Сходинка «★» іде по діагоналі, під нею — сліпі зони, де дублер закрив саме те місце, де живе баг](/guide/progarch/contracts-and-testability/test-boundaries/img/bug-level-matrix.svg)
*Кожен баг гине на найдешевшому колі, що його містить; менші кола сліпі до нього не через недбальство, а тому, що дублер усередині них замінив собою саме те місце, де помилка живе.*

Прочитай сходинку зверху вниз. Баг логіки не має де сховатися — він у центрі кожного кола, тож дешевше й точніше за все його бере модульний. Баг одиниць живе у шві, куди модульний дублер не пускає, — перший, хто його бачить, це інтеграційний. Баг проводки живе у збірці, повз яку менші кола проходять власними руками, — його бачить лише наскрізний. Сірі клітини — не поразка тестів, а прямий наслідок їхнього устрою: там, де коло сліпе, воно сліпе тому, що на місці баги стоїть **твоя підробка**, яка каже те, у що ти віриш.

## Ціна кожного рівня

Тепер про те, за що платять, обираючи радіус. Той самий торг із чотирьох гаманців — швидкість, мерехтіння, локалізація, — але вже з конкретними числами нашого досліду:

```
рівень          швидкість     мерехтіння   куди тицяє при падінні
модульний       мкс           ніколи        «винна decide»
інтеграційний   мс            рідко         «адаптер або decide»
наскрізний      десятки мс+   інколи        «кімната не грілась — десь у хабі»
```

Дивись, як псується локалізація, коли росте радіус. Червоний модульний тест називає винуватця одним словом. Червоний інтеграційний звужує до двох підозрюваних. А червоний наскрізний каже лише «холодна кімната не нагрілася» — і далі копай сам: адаптер, поріг, збірка, проводка? Що більше справжнього коду всередині кола, то більше місць, де воно могло зламатися, і то довша дорога від червоного до причини. За ширше коло певності платиш гіршим пальцем.

Звідси й пастки, у які легко впасти. Перша — **надлишок дублерів у малому колі**: якщо в модульному тесті ти підмінив і `decide`, замінивши її на перевірку «спершу покликав read, потім on», тест стереже проводку, а не результат, і червоніє від будь-якого чесного рефакторингу. Друга — **наскрізний там, де стало б юніта**: покривати логіку порогів кліком крізь весь хаб означає купувати найдорожчою й найкрихкішою монетою те, що дно піраміди дає за мікросекунду. Третя — **фейк без прив'язі**: `FakeDevice`, що дрейфує геть від справжнього драйвера, одного дня зробить зелену збірку зеленим брехуном. Кожна з трьох — це той самий гріх під різними масками: коло стоїть не там, де живе ризик.

Тож весь прогін зводиться до одного руху думки, яким ми й закінчимо. Не питай абстрактно «юніт це чи наскрізний». Візьми конкретний клас помилок — сплутані одиниці, зсунутий поріг, загублений конфіг — і спитай, **де він живе**; тоді постав найменше коло, усередині якого те місце опиняється справжнім. Три баги нашої грілки показали це наочно: радіус, обраний під ризик, ловить його дешево й точно, а радіус, обраний за звичкою, або сліпий до баги, або платить за неї вчетверо. Рівень тесту — це рішення про те, де провести межу, і воно варте тієї ж уваги, що й межі в самому коді.
