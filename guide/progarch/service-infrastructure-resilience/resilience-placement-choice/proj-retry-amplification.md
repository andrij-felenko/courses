# ⚙️ Шторм повторів на числах: від ×81 назад до ×3

Страшну історію ми вже почули: увімкни повтор на кожному шарі — і один клік користувача добіжить до залежності не одним запитом, а двадцятьма сімома, а з четвертим шаром і всіма вісімдесятьма одним. Але історія — це ще не інженерія. Інженерія починається тоді, коли ти можеш **полічити** вибух наперед, **побачити** його в конфігу, який хтось написав не думаючи, і **згорнути** назад двома правками — одна в сітці, одна в коді. Саме це ми тут і зробимо: спершу змоделюємо навантаження числами, які можна крутити, тоді випишемо точний конфіг і код, що зводить множник з kᴺ назад до k, і насамкінець поставимо в сітці запобіжник, який не дасть шторму піднятися, навіть якщо хтось знову все увімкне.

Сюжет — знайомий шлях команди DH: **застосунок → шлюз → сайдкар сітки → сервіс команд**, а в глибині — сам пристрій, який від зайвого `toggle()` перемикається туди-сюди. Три перших шари вміють повторювати; питання лише в тому, скільки з них це справді робить.

## Задача: полічити шторм, а не боятися його

Перше, що варто зрозуміти про kᴺ, — це не одне число, а **дві** дуже різні величини, і плутати їх небезпечно.

Перша — **стеля**: найгірший випадок, коли кожна спроба провалюється й кожен шар вичерпує всі свої повтори. Вона й дає чистий добуток: три спроби на шарі, три шари — 3³ = 27, чотири — 3⁴ = 81. Друга — **очікуваний фан-аут** у звичайну хвилину, коли лише частка p запитів збоїть: тоді шар шле не рівно k запитів, а в середньому 1 + p + p² + … Ці дві величини розходяться драматично, і в цьому вся підступність шторму: у здоровій системі множник майже непомітний, а рівно в аварії, коли p злітає до одиниці, він стрибає до самої стелі. Повтори — це **латентний** множник: він спить, поки все добре, і прокидається точно тоді, коли залежності найгірше.

Змоделюймо обидві величини. Код тут — звичайний застосунковий, не системний гарячий шлях, тож беремо мови стеку; той самий розрахунок двома:

:::tabs
```ts
type Layer = { name: string; tries: number }; // tries: скільки спроб робить шар (1 = без повтору)

// СТЕЛЯ: кожен шар множить на свою кількість спроб. Найгірший випадок —
// кожна спроба провалюється, кожен шар вичерпує всі повтори.
const worstCase = (layers: Layer[]): number =>
  layers.reduce((acc, l) => acc * l.tries, 1);

// ОЧІКУВАНИЙ фан-аут за ймовірності збою p на спробу: шар, що робить t спроб,
// шле в середньому 1 + p + p² + … + p^(t−1) запитів (повторює лише ПІСЛЯ збою).
const expectedPerLayer = (tries: number, p: number): number => {
  let sum = 0, term = 1;
  for (let i = 0; i < tries; i++) { sum += term; term *= p; }
  return sum; // = (1 − p^tries) / (1 − p) при p < 1
};
const expectedFanout = (layers: Layer[], p: number): number =>
  layers.reduce((acc, l) => acc * expectedPerLayer(l.tries, p), 1);

// Шлях команди DH: три шари повторюють по 3 спроби, далі — залежність.
const path: Layer[] = [
  { name: "застосунок", tries: 3 },
  { name: "шлюз",       tries: 3 },
  { name: "сайдкар",    tries: 3 },
];
const RPS = 500; // клік/с на ранковому піку

for (const p of [0.0, 0.3, 0.7, 1.0]) {
  const f = expectedFanout(path, p);
  console.log(`p=${p}: фан-аут ${f.toFixed(2)}× → ${Math.round(f * RPS)} req/s`);
}
console.log(`стеля: ${worstCase(path)}× → ${worstCase(path) * RPS} req/s`);
```
```py
from dataclasses import dataclass

@dataclass
class Layer:
    name: str
    tries: int                     # скільки спроб робить шар (1 = без повтору)

# СТЕЛЯ: добуток спроб усіх шарів — кожна спроба провалюється, кожен шар вичерпує повтори.
def worst_case(layers):
    acc = 1
    for l in layers:
        acc *= l.tries
    return acc

# ОЧІКУВАНИЙ фан-аут за ймовірності збою p: шар на t спроб шле в середньому
# 1 + p + p² + … + p^(t−1) запитів (повторює лише ПІСЛЯ збою).
def expected_per_layer(tries, p):
    s, term = 0.0, 1.0
    for _ in range(tries):
        s += term
        term *= p
    return s                       # = (1 − p**tries) / (1 − p) при p < 1

def expected_fanout(layers, p):
    acc = 1.0
    for l in layers:
        acc *= expected_per_layer(l.tries, p)
    return acc

path = [Layer("застосунок", 3), Layer("шлюз", 3), Layer("сайдкар", 3)]
RPS = 500                          # клік/с на ранковому піку

for p in (0.0, 0.3, 0.7, 1.0):
    f = expected_fanout(path, p)
    print(f"p={p}: фан-аут {f:.2f}× → {round(f * RPS)} req/s")
print(f"стеля: {worst_case(path)}× → {worst_case(path) * RPS} req/s")
```
:::

Прогін друкує рівно те, що робить шторм таким підступним:

```
p=0.0: фан-аут 1.00× →   500 req/s     ← здорова хвилина: множника наче й немає
p=0.3: фан-аут 2.69× →  1343 req/s     ← дрібні збої вже майже потроїли трафік
p=0.7: фан-аут 10.50× → 5252 req/s     ← півсервіса збоїть — навантаження вдесятеро
p=1.0: фан-аут 27.00× → 13500 req/s    ← аварія: множник дострибнув до стелі
стеля: 27× → 13500 req/s
```

Прочитай перший і останній рядки поспіль. У добру хвилину повтори на трьох шарах додають майже нічого — 1.00×; система виглядає здоровою, конфіг «пояс і підтяжки» здається безкоштовним. Та щойно залежність просідає й p повзе до одиниці, той самий конфіг розганяє 500 клік/с до 13 500 — і саме тоді, коли сервіс команд уже задихається. Додай глибший міжсервісний хоп (четвертий шар) — і стеля стане 3⁴ = 81, тобто 40 500 req/s на одну залежність з півтисячі кліків. Множник не «трохи надійніше»; це закладена в конфіг бомба, ґніт якої підпалює сама аварія.

```
шарів N (k=3)   стеля kᴺ    на 500 клік/с
     0              1          500 req/s
     1              3         1500 req/s
     2              9         4500 req/s
     3             27        13500 req/s
     4             81        40500 req/s
```

> 🔧 **Навіщо це.** Перш ніж сперечатися про backoff чи джитер, **полічи показник степеня**. Небезпека шторму — не в тому, скільки повторів на одному шарі, а в тому, **скільки шарів** повторюють: kᴺ росте від N, а не від k. Два повтори (k=2) на п'ятьох шарах — це вже 2⁵ = 32. І дивись саме на стелю: очікуваний фан-аут у здорову хвилину тебе заколише близькою до одиниці цифрою — а платити доведеться в аварію, коли p піде вгору.

## Ідея: власник один, решта пропускає

Лік випливає з розвилки цього кроку одним реченням: **рівно один шар повторює, і це застосунок — бо лише він знає ключ ідемпотентності.** Решта шарів на маршруті команди мають пропускати збій далі, не додаючи від себе жодного повтору. Сайдкар бачить лише байти POST, що не відповів; повторити його наосліп — означає ризикнути другим `toggle()`. [Повтор безпечний тільки там, де хтось знає ключ ідемпотентності](book:programming/idempotency) — короткий рядок, за яким сервіс команд упізнає, що дві спроби це одна дія; сітка цього рядка не читає, а застосунок його сам і кладе.

Отже, лагодження — дві дії у двох домах: **у сітці** вимкнути повтор на маршруті команди (щоб множник тут став ×1), а **в застосунку** повторювати самому за незмінним ключем (єдиний ×k на всьому шляху). Порахуймо наперед, що це дасть. Було 3·3·3 = 27 (а з четвертим шаром 81). Стане 3·1·1 = **3**. Множник схлопується з kᴺ до k — не на відсотки, а на цілий степінь.

![Два рядки того самого шляху команди DH — застосунок → шлюз → сайдкар сітки → сервіс команд (залежність). Угорі «ДО: повтор на кожному шарі» — на кожній стрілці червоний бейдж ×3, праворуч підсумок «= ×27 → 13 500 req/s». Унизу «ПІСЛЯ: власник один, решта пропускає» — застосунок підсвічено бурштином як власника з бейджем «×3 власник», а на шлюзі й сайдкарі сірі бейджі «×1 off»; праворуч зелений підсумок «= ×3 → 1 500 req/s».](/guide/progarch/service-infrastructure-resilience/resilience-placement-choice/img/path-retry-switches.svg)
*Той самий шлях, два конфіги. Повтор нікуди не зник — він лишився рівно в застосунку, який знає ключ; на сітці й шлюзі його явно занулено. Множник упав з ×27 до ×3, бо перемножуватися тепер нема чому.*

Тепер випишемо обидві дії робочим кодом.

## Крок 1: сітка не повторює команду

Тут чигає перша, зовсім не очевидна пастка: **мовчання в конфігу — це не «нуль повторів»**. [Istio](book:programming/service-mesh) за замовчуванням вшиває у проксі політику на **дві** спроби повтору (тобто 3 запити на 1 — саме той k=3 з нашої моделі), і ця політика не порожня. Її задокументоване `retryOn` містить `connect-failure,refused-stream,unavailable,retriable-status-codes`, а серед `retriable-status-codes` — **503**. Тобто «з коробки» сітка повторює навіть відповідь 503, яку неідемпотентний сервіс міг повернути **вже змінивши стан**. Саме цю ваду спільнота роками кликала небезпечною, і у версії 1.24 Istio нарешті прибрав 503 зі стандартної політики (за прапорцем `EXCLUDE_UNSAFE_503_FROM_DEFAULT_RETRY`), бо повтор на 503 «потенційно небезпечний для неідемпотентних запитів». *(Джерела: Istio 1.24 change notes; обговорення istio/istio #20547, #38180 — статус: задокументована зміна дефолту.)*

Висновок для нас практичний: щоб сітка **точно** не повторювала команду, замовчування недостатньо перекрити надією — його треба **явно занулити** на маршруті. В Istio це `retries.attempts: 0`:

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: command-service
  namespace: dh
spec:
  hosts:
    - command-service.dh.svc.cluster.local
  http:
    - name: device-command
      match:
        - uri: { prefix: /v1/devices/ }        # маршрут команди пристрою
          method: { exact: POST }
      route:
        - destination: { host: command-service.dh.svc.cluster.local }
      retries:
        attempts: 0        # ← ЯВНО вимикаємо. Мовчання тут = 2 повтори за замовчуванням.
      timeout: 5s          # стеля часу лишається — це труба, дім сітки
```

Корисно бачити, що Istio зрештою програмує в самому Envoy, бо там правда без абстракцій. На рівні проксі «не повторювати» означає просто **відсутній** `retry_policy` на маршруті; а небезпечна стандартна політика, яку ми прибираємо, виглядає так:

```yaml
# Маршрут команди в Envoy: retry_policy ВІДСУТНЯ → num_retries = 0, проксі не повторює.
routes:
  - match: { prefix: "/v1/devices/" }
    route:
      cluster: command-service
      # без retry_policy — жодного повтору від сітки

# Для порівняння — НЕБЕЗПЕЧНА стандартна політика (те, що вмикається саме):
# retry_policy:
#   retry_on: "connect-failure,refused-stream,unavailable,retriable-status-codes"
#   num_retries: 2
#   retriable_status_codes: [503]   # ← саме цей рядок Istio 1.24 викинув зі стандарту
```

Зверни увагу, що ми не викинули **все** — таймаут з'єднання, mTLS, балансування між репліками лишаються в сітці, бо це труба. Ми занулили рівно **повтор** на рівно **цьому** маршруті: сітка більше не додає свого множника до команди, але й далі робить усе, для чого їй не треба знати змісту виклику.

## Крок 2: застосунок повторює за ключем

Тепер єдиний дозволений ×k — у коді застосунку. Дисципліна тут проста, але легко зламати одним недбалим рядком: **ключ ідемпотентності генерується один раз на логічну команду й носиться незмінним крізь усі повтори.** Якщо на кожну спробу згенерувати новий ключ, сервіс команд побачить три різні команди й чесно виконає `toggle()` тричі — той самий подвійний вимикач, лише вже з нашої вини. Паузу між спробами нарощуємо [повним джитером](book:programming/retries-backoff), щоб не бити синхронно; це саме той рукописний повтор, який ми вперше склали [на поганому Wi-Fi хаба](guide:progarch/dh-bad-network), тільки тепер він тут — **єдиний** на шляху.

:::tabs
```ts
import { randomUUID } from "node:crypto";

// Повний джитер: пауза рівномірно у вікні [0, min(cap, base·2^спроба)) мс.
const fullJitter = (attempt: number, base = 100, cap = 2000): number =>
  Math.random() * Math.min(cap, base * 2 ** attempt);
const sleep = (ms: number) => new Promise(r => setTimeout(r, ms));

async function sendCommand(deviceId: string, action: string): Promise<boolean> {
  // КЛЮЧ ГЕНЕРУЄМО ОДИН РАЗ на логічну команду — і носимо крізь УСІ повтори.
  // Той самий ключ → сервіс команд упізнає дубль і виконає дію рівно раз.
  const idempotencyKey = randomUUID();
  const maxTries = 3;                       // єдиний ×k на всьому шляху — тут і лише тут

  for (let attempt = 0; attempt < maxTries; attempt++) {
    if (attempt > 0) await sleep(fullJitter(attempt - 1));
    const res = await fetch(`/v1/devices/${deviceId}/commands`, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "Idempotency-Key": idempotencyKey,  // ← той самий рядок на кожній спробі
      },
      body: JSON.stringify({ action }),
    });
    if (res.ok) return true;
    // 5xx / мережа — минуще, варте повтору; 4xx (крім 429) — назавжди, не повторюємо.
    if (res.status < 500 && res.status !== 429) return false;
  }
  return false;                             // бюджет спроб вичерпано
}
```
```py
import asyncio, random, uuid
import httpx

def full_jitter(attempt, base=0.1, cap=2.0):            # секунди
    return random.uniform(0, min(cap, base * 2 ** attempt))

async def send_command(client: httpx.AsyncClient, device_id: str, action: str) -> bool:
    # Ключ — ОДИН на логічну команду, незмінний крізь усі повтори.
    idempotency_key = str(uuid.uuid4())
    max_tries = 3                                       # єдиний ×k на шляху

    for attempt in range(max_tries):
        if attempt > 0:
            await asyncio.sleep(full_jitter(attempt - 1))
        r = await client.post(
            f"/v1/devices/{device_id}/commands",
            headers={"Idempotency-Key": idempotency_key},   # той самий рядок щоразу
            json={"action": action},
        )
        if r.is_success:
            return True
        if r.status_code < 500 and r.status_code != 429:    # 4xx (крім 429) — не повторюємо
            return False
    return False                                        # спроби вичерпано
```
:::

Ключове тут — не цикл і не джитер (їх ми вже вміємо), а один незмінний `idempotencyKey` на всі спроби. Він і є те знання, якого сітці бракує: застосунок каже сервісу команд «це та сама команда, що й мить тому», і той згортає три спроби в одну дію. Три запити по мережі — але **один** `toggle()` на пристрої. Ось чому цей ×3 безпечний, а ×3 сітки — ні: різниця не в числі, а в тому, хто несе ключ.

## Крок 3: порахувати, як спало

Повернімо в модель нові числа — застосунок ×3, шлюз і сайдкар ×1 — і прожене той самий прогін:

```
                           стеля       на 500 клік/с
ДО (усі ×3, N=3):           27×          13500 req/s
   (+ 4-й шар → 3⁴):        81×          40500 req/s
ПІСЛЯ (власник один, ×3):    3×           1500 req/s
```

Множник упав з 27 (чи 81) до 3 — рівно в kᴺ⁻¹ разів, тобто на весь зайвий степінь. Причому впав саме там, де боліло: очікуваний фан-аут в аварії тепер прямує до 3, а не до 27, бо решта шарів більше не множать. Пристрій дістає щонайбільше три спроби однієї команди — і, завдяки ключу, виконує її раз.

> 🔧 **Навіщо це.** «Власник один» — це не гасло, а **інваріант конфігу**, який можна перевірити скриптом: пройдися маршрутом і додай `tries > 1` по шарах; якщо таких шарів більше одного — у тебе прихований множник. Тримай цей інваріант у рев'ю поряд із «полічи шари»: спершу порахуй N, тоді впевнись, що повторює рівно один із них — і що це той, хто тримає ключ.

## Запобіжник у сітці: бюджет, а не число

Зануливши повтор на маршруті, ми поклалися на дисципліну: доти доки ніхто не впише знову `attempts: 3` «щоб надійніше», множник тримається на трьох. Але дисципліна ламається, а конфігів багато. Тому розумні сітки додають запобіжник, що не залежить від того, чи хтось десь помилився, — **бюджет повторів**.

Ідея належить Linkerd і б'є точно в корінь шторму. Замість питати «скільки разів повторити один запит» (фіксоване число, яке множиться на шарах), бюджет питає інакше: «яку **частку** живого трафіку взагалі дозволити повторам». Це стеля не на запит, а на весь потік. Інженери Linkerd прямо назвали причину такого вибору: з фіксованим числом повторів навантаження компаундиться мультиплікативно й здатне обернути жменю помилок на самозаподіяну відмову в обслуговуванні. Бюджет цю петлю рве — хай скільки запитів збоїть, сумарні повтори не переростуть заданої частки. *(Джерело: Linkerd, «How we designed retries in Linkerd 2.2», 2019 — первинний опис механізму.)*

```yaml
apiVersion: linkerd.io/v1alpha2
kind: ServiceProfile
metadata:
  name: command-service.dh.svc.cluster.local
  namespace: dh
spec:
  routes:
    - name: "POST /v1/devices/{id}/commands"
      condition:
        method: POST
        pathRegex: /v1/devices/[^/]+/commands
      isRetryable: false          # семантику повтору лишаємо власнику — застосунку
  retryBudget:
    retryRatio: 0.2               # повтори — не більш ніж +20% до живого трафіку
    minRetriesPerSecond: 10       # дрібний «безкоштовний» запас на низькому RPS
    ttl: 10s                      # вікно, за яким рахуємо частку
```

Числа тут — стандартні для Linkerd і читаються як token bucket: за секунди трафіку 100 req/s повтори дістають стелю 0.2·100 + 10 = 30 req/s, а все понад — сітка відкидає. Порівняй із фіксованим ×3 на кожному шарі, який під час аварії хотів би сотні зайвих запитів: бюджет просто не пускає їх у залежність.

![Три стовпчики на спільній осі. Ліворуч синій «живий трафік» — 100 req/s. Посередині високий червоний «чого просить шторм» — 300 req/s, фіксовані повтори на шарах. Праворуч низенький зелений «бюджет пускає» — 30 req/s (0.2·100 + 10), обведений угорі червоним пунктиром до самого рівня 300 зі стрілкою вниз і підписом «сітка відкидає решту». Унизу параметри: retryRatio 0.2 · minRetriesPerSecond 10 · ttl 10s.](/guide/progarch/service-infrastructure-resilience/resilience-placement-choice/img/retry-budget-cap.svg)
*Бюджет міряє повтори як частку живого трафіку, а не числом на запит. Хай шторм хоче хоч 300 req/s — сітка пропускає лише стелю 0.2·100 + 10 = 30 і відкидає решту, тож самозаподіяна петля просто не роздувається.*

Дві тонкощі, щоб не сплутати запобіжник із лагодженням. По-перше, у цьому ж профілі маршрут команди позначено `isRetryable: false` — бюджет не скасовує правила «власник один»: він стеля для тих маршрутів, які **справді** віддані сітці (ідемпотентні читання, GET), а команду й далі повторює застосунок. По-друге, бюджет обмежує **розмір** шторму, але не вирішує, **хто** володіє семантикою: два власники повтору, кожен у межах свого бюджету, все одно подвоять дію. Тому бюджет — сітка безпеки під дисципліною, а не заміна їй: спершу «власник один», і лише тоді бюджет як страховка на випадок чужої помилки.

## Складність і пастки

**Мовчання ≠ нуль.** Головна пастка вже названа, але варта повтору: порожній `retries` у Istio — це **2 повтори за замовчуванням**, а не жоден. Перевіряй ефективну політику на самому проксі (`istioctl proxy-config route`), а не припускай її з відсутності рядка. І пам'ятай, що зміна дефолту 503 приїхала лише у 1.24 — на старших кластерах стандарт усе ще повторює 503, тож версію припущення варто прибити цвяхом.

**Час теж множиться, не лише кількість.** Кожен повтор має свій `perTryTimeout`; три спроби по 5 с — це до 15 с латентності на один виклик, ще й помножені на шари. Шторм повторів — це водночас **шторм затримки**: навіть якщо запити не завалять залежність, сумарний дедлайн роздується й з'їсть [бюджет часу](book:programming/timeouts-deadlines), який ти дав користувачеві. Зануляючи повтор у сітці, ти лагодиш і кількість, і час.

**Повтор іде на інший хост.** Envoy за замовчуванням при повторі вибирає **іншу** репліку (аж до `HostSelectionRetryMaxAttempts` спроб). Для однієї хворої репліки це рятунок — повтор омине її. Але під час загальної аварії це означає, що множник розмазується по **всьому** флоту реплік, а не по одній: 27× б'є не в один процес, а в кластер. Бюджет і тут доречний, бо рахує частку від усього трафіку.

**Ключ мусить пережити вікно повторів.** Незмінний ключ ідемпотентності рятує лише доти, доки сервіс команд його **пам'ятає**. Повний джитер із backoff може розтягнути три спроби на секунди; якщо вікно дедуплікації коротше за цей розкид, третя спроба прийде вже після того, як ключ забули, — і дубль просочиться. Дедуп-вікно на боці залежності має бути **ширшим** за найдовший можливий розкид повторів клієнта, інакше вся дисципліна ключа марна.

**Хеджування — теж повтор.** Якщо десь на шляху ввімкнено hedged requests (превентивний другий запит, не чекаючи збою першого), він додає свій множник **до** всякої аварії, бо шле дублікати завжди. У модель його треба класти як шар, що повторює з ймовірністю 1, а не p, — і тоді видно, що хеджування без ключа ідемпотентності небезпечне так само, як сліпий повтор.

**Коли залежність справді лягла — не повторюй узагалі.** Повтор має сенс проти **минущого** збою. Якщо сервіс команд лежить, три спроби кожного клієнта — це і є шторм; тут вступає [запобіжник](book:programming/circuit-breaker-pattern), який розмикає ланцюг і **припиняє** повтори, поки залежність не оживе. Бюджет обмежує шторм, запобіжник його **вимикає**; у парі вони закривають і «трохи зле», і «зовсім лягло».

Підсумок робочий, не гаслом: шторм повторів — це kᴺ, і воює з ним не хоробрість, а арифметика. Полічи N (скільки шарів повторюють), зведи власника до одного (застосунок, бо він знає ключ), явно занулюй решту (бо мовчання = дефолт), і підклади бюджет із запобіжником як страховку. Тоді 81 назад стає 3 — і то не тому, що ти прибрав надійність, а тому, що поставив її рівно один раз.
