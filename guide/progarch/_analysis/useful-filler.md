# Скептичний аудит користі плану `progarch` v3 (530 кроків)

Роль: скептик-мінімаліст, планка Staff/Principal. Гіпотеза за замовчуванням: «половина кроків тут для об'єму». Оцінка — КОРИСТЬ для практика-архітектора, не академічна повнота. Обіцянка курсу: **репертуар рішень/прийомів/вузлів**, НЕ енциклопедія суміжних фахів.

Легенда позначок: **БАЛАСТ** = не вчить архітектурного рішення (довідка/банальність/дубль/для-об'єму); **РОЗДУТО** = тему можна вдвічі коротше; **СПАДОК** = вижив від вирізаних доменних підручників.

## Модуль 1 — principles (22) — вердикт: ЯДРО, але роздутий хвіст

Це фундамент, більшість виправдана. Але для практика з планкою Staff тут забагато лікнепу, поданого крок-на-поняття.

- **1.6 abstraction-principle / 1.7 information-hiding / 1.8 coupling-cohesion** — три окремі кроки на те, що Staff-архітектор знає рефлекторно. Це не «як архітектори думають», це вступ до ІФ. Злити 1.6+1.7 в один; coupling/cohesion лишити.
- **1.11 error-handling / 1.12 assert-panic / 1.13 defensive-programming** — три ref-кроки поспіль про базову гігієну коду. Для курсу РІШЕНЬ це передумова, не крок. Лишити один вузол «контракт помилки» (1.10 design-by-contract + 1.14 own errors-through-layers його вже несуть). 1.11–1.13 → ref-передумови, не кроки-власники.
- **1.15–1.19 SOLID** п'ятьма кроками — класика роздування. SOLID як «інструменти з межами» можна дати 2–3 кроками (SRP+OCP разом, LSP/ISP разом ref, DIP окремо бо він несе інверсію залежностей). Зараз 5 кроків там, де рішення-цінності два.
- Банальність-ризик: **1.4 essential-accidental-complexity** (Брукс «срібної кулі нема») — це епіграф, не прийом. Тримати як 1 абзац у 1.1, не окремим кроком.

Оцінка: ~14 з 22 несуть прийом/рішення. Хвіст SOLID+гігієна роздутий на ~6 кроків.

## Модуль 3 — patterns (32) — вердикт: РОЗДУТО (каталог заради каталогу)

Тут гіпотеза «для об'єму» підтверджується найсильніше. GoF 23/23 — це вимога замовника (в самоперевірці зазначено), але «репертуар архітектора» ≠ «завчити 23 картки». Архітектурно-значущі патерни (adapter, facade, strategy, observer, command, state, proxy, composite, decorator, DI, repository) — так, вони «виростають у системи». Мікродизайнові — ні.

- **РОЗДУТО, розділ 4 «каталог до кінця» (3.19–3.26): bridge, flyweight, prototype, iterator, template-method, memento, visitor, interpreter** — 8 кроків мікро-ідіом рівня класу. Це чиста довідка GoF, не архітектурні розвилки. Практик-архітектор не ухвалює рішень «застосувати flyweight». Стиснути весь розділ у 2–3 кроки-огляди («решта GoF одним проходом»), решту — book-полиця. Економія ~5–6 кроків.
- **3.20 proj-particle-flyweight.md (частинки гри)** — **СПАДОК** ігрового підручника; вставка про gamedev-пам'ять. У курсі РІШЕНЬ зайва.
- **3.21 prototype «спавн сутностей, шаблони сцен»** — теж **СПАДОК** ігрової лексики.
- **3.26 interpreter + proj-rules-dsl** — DSL правил доречний для DH, але сам «інтерпретатор як GoF» — мікродизайн; ok лишити 1 крок бо DH-rules його реюзає.
- **3.17 finite-automata** ref — доречний (state machine далі скрізь).

Оцінка: ~22 з 32 несуть користь. ~8 мікро-GoF — каталог заради 23/23; мінус 5–6 кроків без втрати.

Практику-архітектору потрібен ВИСНОВОК (хвіст множиться, кеш працює бо Ципф), не теорія черг. Littles-law (17.4) + percentiles (17.2) достатньо; heavy-tail/queue-theory/zipf — секції/ref, не кроки-власники. Мінус ~1.
- **17.12 http-caching / 17.13 cdn / 17.14 distributed-cache / 17.15 cache-invalidation / 17.16 cache-tactics** — п'ять кроків кешу. Кеш — так, вузол; але 5 кроків + М5.26 (patterns) + М16.6 (server-state-cache) = кеш розмазано на 7+ кроків по курсу. Тут можна злити http-caching у cdn-секцію. Мінус пів-кроку.
- **17.19–17.25 «казати ні»** (queue-leveling, rate-limit-for-peak, admission, fairness, adaptive-concurrency, load-shedding, hedged) — 7 кроків backpressure/shedding. Це реальний репертуар обходів (v3-крило mitigations), тримати — але це щільний блок на межі «скільки способів сказати ні треба». adaptive-concurrency+admission+fairness+shedding — усі різні, ok.

Оцінка: ~24 з 28. Math-теорія (~1–2 кроки) — довідка; кеш злегка розмазаний.

Оцінка: ~13 з 20. Найбільша концентрація дублів-під-доменом і спадків. Реально ріжеться на ~14–15 без втрати.

## Чи витримує курс обіцянку «репертуар, не енциклопедія»

**Здебільшого ТАК.** Модулі 2, 5, 15, 18 — еталон щільного репертуару; М10/12/14/16 — сильні вузлові. Крила v3 (дисципліна, безпека, вузли, обходи) реально замінили вирізані домени змістовним матеріалом. Це вже НЕ «дві книги в обкладинці».

**АЛЕ обіцянка тріщить у трьох місцях:**
1. **GoF 23/23 (М3)** — свідомо енциклопедичний острів («вимога користувача»), суперечить «не завчати назви». Це найбільший компроміс проти власного маніфесту.
2. **М20–21 (40 кроків флоту)** — тримаються на одному наскрізному домені (розумний дім). Для не-IoT-архітектора це нішева енциклопедія пристроїв; переносність патернів заявлена, але щільність доменних DH-кроків висока. М21 — найслабша ланка.
3. **Рекап-тактики** (М2/11/13/17/19 — 5 кроків «тактика називає зроблене») + math-теорія (М17) — м'який академічний наповнювач.

**Вердикт:** курс НЕ «половина для об'єму». Це щільний (~80%) репертуарний курс із трьома зонами торгу: обрізати мікро-GoF, здути М21, зняти гігієну/OWASP-дроблення. Прицільна чистка ~50–60 кроків (до ~470–480) прибрала б майже весь баласт БЕЗ втрати жодного архітектурного рішення — і тоді обіцянка трималася б бездоганно. Цільові «~500» досяжні саме через це обрізання, а не через дотягування об'єму.
