# 📜 Еволюція вихідних взаємодій: від синхронного RPC до асинхронних Egress-вузлів

Ця історична вставка розкриває, як інженерна думка від 1970-х років до сьогодення долала невідворотні збої мережі на межі між автономними системами. Читач дізнається, чому наївні прямі HTTP-виклики 1990-х років спричиняли каскадні аварії, як пакетні файлові обміни EDI/FTP перетворилися на вебхуки й пуші, та чому створення виділеного Outbound Egress-вузла стало стандартом розподілених систем.

## Ера EDI та пакетних файлів (1970–1990-ті)

На світанку міжкорпоративних обчислень у 1970-х роках ідея про те, що один сервер може викликати процедуру на іншому сервері чужого підприємства в реальному часі, вважалася неприпустимим ризиком. Мережі були повільними, нестабільними й критично дорогими. Коли авіакомпанії, банки або логістичні гіганти мусили обмінюватися даними про квитки, фінансові транзакції чи вантажні декларації, вони використовували **Electronic Data Interchange (EDI)** — стандартизовані текстові формати (ANSI X12 у США, EDIFACT у Європі).

Типовий EDI-документ (наприклад, замовлення `ANSI X12 850` або повідомлення про відвантаження `856`) не надсилався миттєво. Зв'язок був строго асинхронним і пакетним (англ. *batch processing*). Раз на добу або щогодини система-відправник вивантажувала накопичені записи у файл, підписувала його контрольною сумою й завантажувала через FTP або SFTP на каталоговий сервер партнера. На боці отримувача демон вичитував файл, обробляв його у фоні та повертав квитанцію про прийом (наприклад, квитанцію `ANSI 997 Functional Acknowledgment`).

Ця модель мала дві величезні переваги, які на десятиліття закарбувалися в архітектурній думці:

1. **Абсолютна ізоляція транзакцій:** Жодне падіння чужого сервера чи мережевого кабелю не могло зупинити локальну базу даних. Системи працювали в незалежних темпах.
2. **Відсутність каскадних затримок:** Внутрішні оператори та користувачі системи не чекали на відповідь зовнішнього світу, бо вся робота з файлами діялася у фоні.

Проте вартість такого спокою була високою — **величезний лаг (high latency)**. Зміни стану ставали відомі партнерові лише через години чи дні, що унеможливлювало побудову інтерактивних сервісів реального часу.

## Корпоративні шини повідомлень (MOM) та стандарти X.400 (1980–1990-ті)

Паралельно з файловим EDI у великих банках та телекомах розвивалися системи орієнтованого на повідомлення проміжного програмного забезпечення (англ. *Message-Oriented Middleware, MOM*). Виникли стандарти X.400 та перші комерційні брокери — IBM MQ (IBM MQSeries, 1993) та TIBCO Rendezvous.

Брокери повідомлень запровадили поняття **черги з надійним збереженням (Store-and-Forward)**. Програма-відправник не зв'язувалася з отримувачем напряму, а клала повідомлення в локальну чергу. Брокер брав на себе гарантію доставки крізь нестабільну мережу. Проте в ті часи IBM MQ вимагала складних бінарних протоколів, виділених каналів зв'язку та дорогих ліцензій, що робило її недоступною для масового вебу.

## Пастка віддаленого виклику процедур (RPC) та помилкові припущення (1980–1990-ті)

У середині 1980-х років з'явилися перші технології віддаленого виклику процедур (RPC): Sun RPC (1984), DCE/RPC (1990), агодом CORBA (1991) та Java RMI (1995). Виробники програмного забезпечення намагалися створити ілюзію «прозорості мережі» (network transparency) — зробити так, щоб виклик функції на віддаленому сервері виглядав у коді точно так само, як звичайний виклик локальної функції в пам'яті:

```cpp
// Ілюзія 1990-х: віддалений виклик виглядає як локальний
OrderResult result = remote_payment_service.processOrder(order);
```

У 1994–1997 роках Пітер Дойч (Peter Deutsch), Джеймс Ґослінг (James Gosling) та їхні колеги з Sun Microsystems сформулювали фундаментальні **Вісім помилкових припущень про розподілені обчислення** (Fallacies of Distributed Computing). Вони довели, що намагання приховати мережу за фасадом звичайного виклику функції — це катастрофічний концептуальний дефект, бо мережа приватно має вісім непереборних властивостей:

1. Мережа надійна (The network is reliable).
2. Затримка дорівнює нулю (Latency is zero).
3. Пропускна здатність безкінечна (Bandwidth is infinite).
4. Мережа безпечна (The network is secure).
5. Топологія не змінюється (Topology doesn't change).
6. Є один адміністратор (There is one administrator).
7. Вартість транспорту дорівнює нулю (Transport cost is zero).
8. Мережа однорідна (The network is homogeneous).

Спроби застосувати CORBA чи Java RMI між автономними підприємствами провалилися саме тому, що вони ігнорували ці припущення, застрягаючи на мережевих таймаутах і рвучи транзакційні блоки.

## Перша хвиля Web API та каскадні аварії (2000-ні)

Наприкінці 1990-х із розквітом протоколу HTTP та появою корпоративних веб-сервісів (XML-RPC, SOAP, агодом і REST) індустрію охопила нова хвиля ейфорії. Інженерам здалося, що відкриті веб-стандарти нарешті розв'язали проблему міжсистемної взаємодії.

Розробники почали масово вбудовувати HTTP-виклики до зовнішніх платіжних шлюзів, SMS-провайдерів та партнерських API безпосередньо в синхронний потік обробки веб-запиту клієнта:

```
Запит клієнта → Потік веб-сервера → BEGIN SQL → HTTP-виклик платіжного шлюзу → COMMIT SQL → Відповідь 200
```

У 2000-х роках, коли електронна комерція переживала вибухове зростання, ця схема почала масово валитися. Достатньо було зовнішньому платіжному шлюзу або SMS-центру сповільнити відповідь із 200 мілісекунд до 15 секунд (або просто зависнути без закриття сокета), як усередині первинної системи діяв паніка-доміно:

1. **Вичерпання пулу потоків (Thread Pool Exhaustion):** Усі веб-потоки підключень застрягали в очікуванні сокетів зовнішніх викликів. За секунди веб-сервер припиняв приймати нові запити від будь-яких користувачів.
2. **Пастка подвійного списання (Double Spend / Duplicate Issue):** Користувачі, не дочекавшись відповіді браузера, натискали кнопку «Оплатити» або «Надіслати» вдруге. Перший HTTP-запит до платіжного шлюзу фактично проходив на том боці, але локальний веб-сервер рвав з'єднання за таймаутом і робив `ROLLBACK` місцевої БД. Друге натискання списувало гроші вдруге.
3. **Шторм повторів (Retry Storm):** Якщо розробники додавали наївний цикл `for i in 1..5 { http_post() }`, то під час тимчасового перевантаження зовнішнього API цей цикл помножував навантаження на зламаний сервіс у 5 разів, остаточно вбиваючи його.

Аналіз великих аварій 2003–2006 років у ритейлі та фінансовому секторі довів: **зовнішній мережевий виклик усередині синхронного контексту — це міна сповільненої дії**.

## Виникнення Webhooks та Push-мереж (2007–2012)

Реакцією на каскадні аварії стало повернення асинхронності, але вже на новій технічній основі.

У 2007 році хакер Джефф Ліндсей (Jeff Lindsay) запропонував концепцію **Webhooks** («веб-гачків»). Замість того щоб споживач постійно опитував API провайдера в синхронних циклах, провайдер реєстрував URL-адресу споживача й **штовхав** `POST`-запит із даними події лише тоді, коли подія реально ставалася. Stripe, GitHub, Twilio та Shopify зробили вебхуки стандартом де-факто для міжсерверної взаємодії.

Початкові вебхуки (Webhooks 1.0) були простими й незахищеними: провайдер просто надсилав сирий JSON `POST` без підписів. Зловмисники швидко навчилися сканувати IP-діапазони й надсилати фальшиві `POST`-запити на приймальні ендпоінти партнерів. Це спричинило появу **Webhooks 2.0**: обов'язкові HMAC-SHA256 підписи тіла, ротація ключів, часові мітки `t` для захисту від повторів (replay attacks) та публікація офіційних діапазонів IP-адрес відправника.

Майже одночасно у сфері взаємодії «машина-людина» виникли централізовані **Push Services**. До 2009 року кожен мобільний застосунок на смартфоні намагався тримати власний відкритий TCP-сокет до свого сервера, що розряджало батарею за 2 години й валило стільникові вежі. У 2009 році Apple випустила **APNs** (Apple Push Notification service), а Google у 2010 році — **C2DM** (попередник FCM). Вони змусили мобільні пристрої тримати **один** зашифрований системний сокет до хмари ОС, а розробників — надсилати сповіщення через вихідні API Apple та Google.

Однак вихідний потік (і вебхуків, і пушів) зіткнувся з новою пасткою — **проблемою подвійного запису (Dual-Write Problem)**. Якщо бізнес-логіка виконувала:

```
1. db.save(order)
2. webhook_client.send(order_created_event)
```

...то при падінні процесу між рядком 1 і 2 подія втрачалася назавжди, а при зворотній послідовності — зовнішній світ дізнавався про замовлення, збереження якого в БД впало.

## Формування паттерну Outbound Egress Node (2014–донині)

У 2014 році Кріс Річардсон (Chris Richardson) та спільнота мікросервісних архітекторів формалізували патерн **Transactional Outbox**. Його суть полягала в тому, що намір вихідного виклику записувався в спеціальну таблицю `outbox` **у тій самій SQL-транзакції**, що й локальні зміни стану.

Окремий процес-воркер (Outbox Processor) вичитав таблицю й передавав повідомлення до **виділеного вихідного вузла (Outbound Egress Gateway / Node)**.

Паралельно Майкл Нігард (Michael Nygard) у своїй фундаментальній праці «Release It!» (2007) запропонував патерн **Circuit Breaker** (автоматичний вимикач), який у поєднанні з експоненційним відступом (Exponential Backoff) і рандомізацією (Jitter) довершив анатомію вихідного вузла.

У сучасних хмарних архітектурах виділення вихідного вузла вилилося у створення спеціалізованих **Egress Proxies** (таких як Envoy Egress Gateway або Istio Egress Gateway), а також хмарних сервісів маршрутизації подій (AWS EventBridge, Azure Event Grid). Вони дозволяють повністю перенести задачі TLS-термінації, ротації секретів, перевірки Rate Limit, Circuit Breaking, метрик простежуваності (OpenTelemetry) та логування вихідного трафіку з коду додатків на спеціалізовану інфраструктуру.

Сучасна архітектура розподілених систем остаточно розділила внутрішній світ сервісів і вихідну мережу. Вихід назовні став не просто викликом бібліотеки `http.post()`, а **окремим інфраструктурним вузлом**, який володіє власною чергою, правилами стійкості, дедуп-ключами, автоматичними вимикачами, преференсами користувачів та мертвими чергами (DLQ).
