# 📋 Специфікація заголовків та статусів Idempotency-Key

Нижче наведено вичерпний технічний довідник контракту вихідної та вхідної ідемпотентності. Специфікація спирається на чернетку стандарту IETF `draft-ietf-httpapi-idempotency-key-header`, специфікацію Stripe API, а також практичні реалізації в платіжних системах Adyen, PayPal та хмарних платформах AWS і Google Cloud.

## 1. HTTP Заголовки запиту та відповіді

Для забезпечення детермінованої вихідної розмови специфікація визначає спеціальні заголовки на межі протоколу HTTP. Головним інструментом ідентифікації є заголовок `Idempotency-Key`, який клієнт прикріплює до вихідного HTTP POST запиту.

Коли клієнт надсилає запит із заголовком `Idempotency-Key: 7b9e81a2-3f1d-4e9a-8b12-9012345678ab`, серверний шлюз інтерпретує це як унікальну вимогу на проведення мутації. Якщо сервер отримує цей самий ключ у майбутньому, він розпізнає повторну спробу і не виконує бізнес-операцію вдруге.

У відповіді провайдер використовує заголовок `Idempotent-Replay: true`. Наявність цього заголовка повідомляє клієнтському шлюзу, що відповідь була повернута з персистентного кешу ідемпотентності без повторного списання коштів або створення нових ресурсів. Для цілей аудиту та моніторингу лагів сервер може також повертати `Idempotency-Key-First-Seen` із точним часом першого прибуття запиту.

При виникненні тимчасових затримок або обмежень швидкості сервер надає заголовок `Retry-After: 5`, який чітко каже клієнту, яку саме затримку в секундах необхідно витримати перед наступним повтором запиту.

Додатково клієнт або сервер можуть передавати заголовок `X-Payload-Fingerprint`, у якому міститься SHA-256 хеш канонічного JSON-тіла. Це дозволяє швидко перевірити, чи не було змінено параметри запиту під час ретраїв.

## 2. Порівняння заголовків між провідними платформами

Різні хмарні та платіжні платформи використовують власні назви заголовків, хоча їхня внутрішня семантика залишається абсолютно ідентичною.

У платіжній системі Stripe та провайдері Adyen використовується стандартний заголовок `Idempotency-Key`. Платіжна система PayPal у своєму REST API v2 застосовує заголовок `PayPal-Request-Id`. У хмарній інфраструктурі Amazon Web Services (DynamoDB, EC2 Auto Scaling) цей механізм реалізовано через параметр `ClientRequestToken`. У платформах Google Cloud (gRPC/REST API) аналогічний контроль здійснюється через атрибут `request_id`.

Попри відмінності у назвах, усі ці сервіси вимагають однакової поведінки від клієнтського шлюзу: повторний запит мусить передавати точно такий самий ключ та ідентичне корисне навантаження.

## 3. Формат та синтаксичні вимоги до ключа (BNF Grammar)

Специфікація висуває суворі синтаксичні обмеження до значення заголовка `Idempotency-Key` для забезпечення сумісності з HTTP-проксі та балансувальниками.

Заголовок повинен містити лише видимі ASCII-символи у діапазоні `0x21`–`0x7E` (букви латиниці, цифри, дефіс, підкреслення, крапка, двокрапка). Пробели та специфічні керуючі символи суворо заборонені.

Мінімальна довжина рядка становить 16 символів, а максимальна — 255 символів. Якщо клієнт передає ключ довжиною понад 255 символів, серверний API-шлюз негайно відхиляє запит із кодом `HTTP 400 Bad Request`, навіть не намагаючись розібрати тіло запиту.

Основними рекомендованими форматами ключів є:
- Стандартний UUIDv4: `9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d`
- Префіксний доменний ключ: `dh_charge_ord_8812_v1`
- Хеш бізнес-контексту: `idemp_sha256_e3b0c44298fc1c149afbf4`

## 4. Канонізація та обчислення відбитка тіла (Payload Fingerprinting)

Щоб виявити помилку **Payload Mismatch** (ситуацію, коли розробник помилково використав той самий ключ ідемпотентності для іншої операції або змінив суму платежу при ретраї), сервер обчислює канонічний хеш запиту відповідно до стандарту RFC 8785 (JSON Canonicalization Scheme — JCS).

Алгоритм канонізації складається з трьох послідовних кроків. Спершу формується базовий рядок, який об'єднує HTTP-метод, шлях запиту та канонічний JSON:
`StringFingerprint = HTTP_METHOD + "\n" + REQUEST_PATH + "\n" + CANONICAL_JSON_BODY`

Канонізація JSON-тіла вимагає, щоб усі ключі в об'єктах були впорядковані строго за алфавітом (UTF-8 code point order). Усі непотрібні пробели, переноси рядків та табуляції вилучаються. Числові значення відображаються у стандартній десятковій формі без форматування з плаваючою крапкою. Кодування рядків проводиться виключно в UTF-8.

Після формування канонічного рядка сервер обчислює криптографічний хеш `SHA-256`. Якщо при отриманні повторного запиту з тим самим `Idempotency-Key` новий хеш відрізняється від збереженого в кеші, сервер зупиняє обробку й повертає помилку `HTTP 422 Unprocessable Entity`.

## 5. Формат помилки конфлікту (RFC 7807 Problem Details)

При виникненні помилок ідемпотентності (`HTTP 409 Conflict` або `HTTP 422 Payload Mismatch`) сервер повертає структуру деталізації помилки у стандарті RFC 7807 (Problem Details for HTTP APIs).

Коли сервер виявляє розходження тіла запиту при однаковому ключі, він повертає відповідь зі статусом `422 Unprocessable Entity`. Тіло відповіді містить машинний код `idempotency_payload_mismatch`, пояснення для розробника у полі `detail` та посилання на документацію.

У разі, коли повторний запит потрапляє на сервер у мить, коли перший виклик ще виконується паралельно (стан `IN_FLIGHT`), сервер повертає статус `HTTP 409 Conflict`. У відповіді обов'язково додається заголовок `Retry-After: 3` та JSON-структура з кодом `idempotency_request_in_flight`. Це сигналізує клієнтському шлюзу про необхідність зачекати вказаний термін і повторити спробу з тим самим ключем.

## 6. Класифікація статус-кодів та зобов'язання клієнтського шлюзу

Для забезпечення коректної роботи вихідного шлюзу всі HTTP статус-коди відповіді діляться на чотири чіткі категорії.

Перша категорія — **Остаточний успіх (`200 OK`, `201 Created`, `202 Accepted`)**. Отримавши такий статус, клієнтський шлюз вважає вихідний виклик повністю виконаним. Він зберігає результат у локальній базі даних і переводить стан доменного завдання у `COMPLETED`.

Друга категорія — **Фатальні помилки клієнта (`400 Bad Request`, `401 Unauthorized`)**. Вони вказують на синтаксичні помилки в запиті або недійсні облікові дані. Клієнтський шлюз **не повинен повторювати** такі запити, оскільки повтор із тими самими параметрами дасть тотожний збій. Завдання позначається як `FAILED_FATAL`.

Третя категорія — **Тимчасові конфлікти та обмеження (`409 Conflict`, `429 Too Many Requests`)**. Вони повідомляють, що сервер зайнятий або обробляє попередній виклик. Клієнтський шлюз **зобов'язаний зробити паузу** (відповідно до заголовка `Retry-After`) і повторити запит **із тим самим заголовком `Idempotency-Key`**.

Четверта категорія — **Тимчасові збої сервера та таймаути (`500`, `502`, `503`, `504`)**. Це випадки, коли сервер провайдера зазнав внутрішньої аварії або не встиг повернути відповідь. Оскільки стан виконання невідомий, клієнтський шлюз **зобов'язаний повторити запит із тим самим ключем** за алгоритмом Exponential Backoff.

## 7. Ізоляція ключів та безпека (Scope & Security Boundaries)

Забезпечення ідемпотентності вимагає суворого дотримання меж безпеки. Ключ ідемпотентності ніколи не є глобальним у межах усієї бази провайдера. Він обов'язково зв'язується з ідентифікатором аутентифікованого клієнта.

Серверний шлюз обчислює підсумковий композитний ключ за формулою:
`UniqueKey = HMAC_SHA256(Client_API_Key, Idempotency_Key)`

Це унеможливлює атаки типу Cross-Tenant Key Hijacking, коли зловмисник намагається піддивитися або вгадати чужий UUID і отримати збережену відповідь іншого користувача. Два різні клієнти системи можуть використовувати однакові UUID без жодного ризику витоку даних чи конфлікту станів.

Крім того, проміжні інфраструктурні елементи (балансувальники Nginx, Envoy, Cloudflare) зобов'язані транслювати заголовок `Idempotency-Key` на бекенд-сервіси в незмінному вигляді.

## 8. Час життя ключів та політика очищення (TTL & Eviction)

Зберігання кешованих відповідей та станів ключів вимагає оперативності й дискових ресурсів. Тому специфікація визначає чіткі правила управління часом життя ключів (TTL).

Для платіжних та фінансових транзакцій стандартний TTL становить від 24 до 72 годин. Для оперативних сповіщень та push-повідомлень TTL може становити 12–24 години. Для інфраструктурних дій TTL може продовжуватися до 30 діб.

Якщо клієнт надсилає запит із ключем, термін дії якого в кеші провайдера вже закінчився, провайдер сприймає цей виклик як **новий початковий запит** і виконує бізнес-логіку з нуля. Звідси випливає важливе правило для клієнтського шлюзу: вікно повторних спроб клієнта мусить бути значно коротшим за TTL ключа на боці провайдера. Якщо клієнт робить повтори впродовж 6 годин, TTL на боці провайдера повинен становити не менше 24 годин.
