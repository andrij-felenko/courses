# 📜 Як Stripe ввів Idempotency-Key і врятував вихідні платежі

У 2017 році інженерна команда фінансової платформи Stripe опублікувала архітектуру забезпечення ідемпотентності вихідних та вхідних HTTP-викликів, яка згодом змінила підхід до проєктування Web API у всій індустрії програмного забезпечення. До цього моменту будь-який мережевий збій під час списання коштів чи обробки транзакцій у Web API ставив розробників перед болісним вибором: ризикнути й повторити HTTP-запит (і потенційно списати гроші з клієнта двічі) або відмовитися від повтору (і залишити замовлення неоплаченим, а користувача — без послуги).

## Історичне коріння: Механічні та банківські мережі проти протоколу HTTP

Проблема подвійного списання не була новою для фінансового світу. У традиційних банківських мейнфреймах і міжбанківських мережах (зокрема в межах стандарту ISO 8583, який використовується в платіжних терміналах POS та банкоматах ATM) поняття унікального номеру транзакції — **STAN** (англ. *System Trace Audit Number*) та **RRN** (англ. *Retrieval Reference Number*) — існувало ще з 1980-х років. Кожна операція по картці отримувала унікальний номер, і якщо банк-еквайр не отримував підтвердження від банку-емітента, він надсилав спеціальний запит скасування (Reversal) або повтор (Repeat) із тим самим STAN. Bank-side мейнфрейми знали, що запит із позначкою `Repeat` не повинен списувати кошти з рахунку вдруге.

Однак із вибуховим зростанням веб-сервісів у 2000-х роках та появою архітектурного стилю REST над протоколом HTTP, ця банківська дисципліна була значною мірою втрачена. Мережевий протокол HTTP/1.1 розроблявся для передачі документів, а не для фінансових транзакцій. Методи `GET`, `PUT` та `DELETE` за специфікацією RFC 7231 вважалися ідемпотентними, тоді як метод `POST` свідомо визначався як **неідемпотентний** (англ. *non-idempotent*).

Коли розробники почали будувати фінансові API поверх HTTP POST (наприклад, `POST /v1/charges`), будь-який виклик вважався новим бізнес-запитом кожного разу, коли сервер отримував новий TCP-пакет. 

З масовим переходом користувачів на мобільний інтернет (3G та 4G LTE у 2010–2015 роках) ситуація загострилася до межі. Мобільні мережі характеризуються частими короткочасними обривами зв'язку, високим показником втрати пакетів (packet loss) та різкими стрибками таймаутів. Мільйони покупців по всьому світу стикалися з ситуацією, коли під час оплати в мобільному застосунку екран зависав на 5 секунд, після чого вивалювалася помилка «Мережа недоступна». Натиснувши кнопку «Спробувати знову», покупець отримував два банківських SMS про списання однієї й тієї самої суми. 

Еквайри та торговельні майданчики платили за це величезні гроші: витрати на обробку чарджбеків (англ. *chargebacks*), штрафи від платіжних систем Visa та Mastercard і втрачену довіру клієнтів.

## Брандур Ліч та інженерне рішення Stripe (2017)

У 2017 році інженер Stripe Брандур Ліч (Brandur Leach) опублікував фундаментальну працю «Handling Overlaps and Retries with Idempotency Keys», у якій детально описав внутрішньослужбовий шар (middleware) платіжного шлюзу Stripe.

Інженери Stripe поставили собі за мету зробити так, щоб **будь-який вихідний HTTP POST запит міг бути безпечно повторений клієнтом довільну кількість разів** без ризику подвійного списання коштів чи дублювання об'єктів у базі даних.

Для цього Stripe запровадив обов'язковий (або рекомендований для мутацій) HTTP-заголовок `Idempotency-Key`.

### Внутрішня архітектура шлюзу Stripe

Шлюз Stripe був реалізований як прозорий шар перед основними доменними сервісами. Його робота спиралася на двоярусне сховище даних:
1. **Швидке сховище блокувань (Redis)**: Використовувалося для збереження короткоживучих атомних ключів зі станом `IN_FLIGHT`. Коли HTTP POST запит приходив на шлюз, шлюз виконував команду `SET key value NX EX 60`. Якщо команда повертала 0 (ключ уже існує і перебуває в процесі обробки), шлюз миттєво повертав відповідь `HTTP 409 Conflict`.
2. **Персистентне сховище відповідей (PostgreSQL)**: Після того, як доменна бізнес-логіка успішно проводила платіж, шлюз записував у PostgreSQL таблицю `idempotency_keys` точний злімок HTTP-відповіді: HTTP-статус (`200 OK`), усе JSON-тіло відповіді та ключові заголовки.

При отриманні повторного запиту з тим самим `Idempotency-Key` (наприклад, через 10 секунд після мережевого таймауту), шлюз взагалі НЕ викликав доменні сервіси обробки платежів і НЕ звертався до банківського процесингу. Замість цього він зчитував збережений злімок із PostgreSQL і повертав його клієнту, додаючи заголовок `Idempotent-Replay: true`.

### Відкриття та розв'язання пастки Payload Mismatch

У ході тестування системи Stripe виявив важливий крайовий випадок: що робити, якщо клієнт надсилає той самий `Idempotency-Key`, але змінює корисне навантаження (наприклад, у першому запиті було `amount: 100`, а в другому — `amount: 500`)?

Якщо просто повернути кешовану відповідь від першого запиту на $100, клієнт буде введено в оману, адже він вважатиме, що успішно провів платіж на $500. Якщо ж виконати запит як новий, руйнується ідемпотентність.

Інженери Stripe знайшли елегантне рішення: **Payload Fingerprinting** (обчислення відбитка корисного навантаження). При першому виклику шлюз обчислював `SHA-256` хеш від канонічного JSON-рядка тіла запиту й зберігав його поруч із ключем. При повторному виклику шлюз порівнював хеш нового тіла із збереженим. Якщо хеші не збігалися, шлюз відхиляв запит із кодом `HTTP 422 Unprocessable Entity` або `HTTP 400 Bad Request`, сповіщаючи про конфлікт параметрів.

## Розповсюдження стандарту в індустрії та IETF

Ідея Stripe виявилася настільки практичною й ефективною, що впродовж 2018–2021 років аналогічні заголовки й механізми запровадили майже всі провідні технологічні гіганти:

- **PayPal**: запровадив заголовок `PayPal-Request-Id` для своїх REST API v2.
- **Adyen**: додав заголовок `Idempotency-Key` у свої вихідні та вхідні платіжні інтерфейси.
- **AWS (Amazon Web Services)**: запровадив параметр `ClientRequestToken` в API DynamoDB, EC2 та EC2 Auto Scaling для запобігання дублюванню ресурсів при ретраях.
- **Google Cloud**: додав механізм `request_id` у свої gRPC та REST API управління інфраструктурою.

У 2020 році робоча група IETF (Internet Engineering Task Force) розпочала офіційний процес стандартизації специфікації під назвою `draft-ietf-httpapi-idempotency-key-header`. Стандарт закріпив заголовок `Idempotency-Key` як офіційне розширення протоколу HTTP для забезпечення ідемпотентних мутацій над неідемпотентними HTTP-методами (`POST`, `PATCH`).

Сьогодні ключ ідемпотентності є фундаментальним стандартом побудови вихідних та вхідних розмов у розподілених системах, без якого не будується жоден надійний платіжний чи інтеграційний шлюз.
