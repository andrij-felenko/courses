# 🔌 Класи систем авторизації: порівняння рушіїв політик та графів

Про проєктуванні сучасних програмних систем інженер стикається з десятками готових інструментів контролю доступу — від простих ORM-бібліотек до планетарних графових кластерів. Ця вставка класифікує наявні рішення авторизації, систематизує їх за архітектурними категоріями та дає матрицю порівняння для свідомого вибору під конкретний масштаб системи.

## 1. Таксономія систем авторизації

Усі сучасні засоби перевірки допусків поділяються на чотири великі архітектурні класи за тим, **де зберігаються правила**, **як обчислюється рішення** та **як передається контекст**.

```
                           Системи авторизації
                                    │
     ┌──────────────────┬───────────┴──────────────┬──────────────────┐
     ▼                  ▼                          ▼                  ▼
1. Вбудовані       2. Політики як код        3. Графові ReBAC    4. Комплексні IAM
   бібліотеки         (Policy Engines)          (Relationship)      (Identity & Access)
(Casbin, CASL)     (OPA/Rego, AWS Cedar)    (OpenFGA, SpiceDB)  (Keycloak, Keto)
```

---

## 2. Клас 1: Вбудовані бібліотеки та фреймворки (Embedded Application AuthZ)

Цей клас реалізує перевірку прав безпосередньо в процесі застосунку. Таблиці ролей і прав лежать у загальній БД сервісу, а кодовий хендлер викликає локальну бібліотеку.

- **Представники**: `Casbin` (Go/Java/Node/Python), `Spring Security` (Java), `CanCanCan` (Ruby), `CASL` (TypeScript), `Django Rules` (Python).
- **Механіка**: Застосунок сам дістає з бази даних роль чи атрибути користувача й передає їх у локальну функцію `can(user, 'read', 'camera')`.
- **Сильні боки**:
  - Нульова мережева затримка: перевірка відбувається в пам'яті процесу за мікросекунди.
  - Простий старт: не потрібно розгортати й обслуговувати окремі інфраструктурні сервіси.
  - Повний доступ до ORM і доменного контексту без додаткових мережевих запитів.
- **Слабкі боки**:
  - Прив'язка до мови/стеку: якщо систему розбито на Go, Node.js та Python, авторизаційну логіку доведеться дублювати трьома мовами.
  - Дрейф правил (Policy Drift): кожен мікросервіс починає трактувати ролі по-своєму.
  - Централізований аудит «хто до чого має доступ у всій системі» стає неможливим.

---

## 3. Клас 2: Рушії політик як код (Policy-as-Code / ABAC Engines)

Політики доступу відокремлюються від бізнес-коду й записуються спеціалізованою декларативною мовою. Рушій приймає JSON-контекст і повертає рішення `allow`/`deny`.

- **Представники**: `Open Policy Agent (OPA)` (мова Rego), `AWS Cedar` (мова Cedar), `Topaz`.
- **Механіка**: Сервіс або API Gateway передає в OPA документ із даними запиту (`input = {subject, action, resource, env}`). OPA виконує декларативні правила та віддає результат.
- **Сильні боки**:
  - Декларативна мова політик підходить для версіонування у Git, CI-тестування та автоматичного статичного аналізу.
  - Повна мовна незалежність: PDP працює як sidecar-процес або окремий мікросервіс.
  - Ідеально для інфраструктурної авторизації: Kubernetes Admission Control, правила API Gateway, Envoy proxy filter.
- **Слабкі боки**:
  - **Пастка PIP (Policy Information Point)**: Якщо політика потребує атрибутів, яких немає в початковому запиті (наприклад, прапорець бана користувача з іншої БД), OPA мусить або ротилювати ці дані до себе у пам'ять, або робити зовнішні HTTP-запити під час оцінки політики, що знищує продуктивність.

## 4. Клас 3: Графові ReBAC-рушії (Relationship-Based AuthZ Engines)

Втілення концепції Google Zanzibar. Замість обчислення абстрактних скриптів система зберігає мільярди кортежів стосунків та оцінює допуск як досяжність вузла у реляційному графі.

- **Представники**: `OpenFGA` (CNCF sandbox), `SpiceDB` (Authzed), `Permify`.
- **Механіка**: Доступ перевіряється викликом `check(user:alice, relation:viewer, object:camera:704)`. Рушій самостійно виконує оптимальний обхід графа по своєму оптимізованому сховищу.
- **Сильні боки**:
  - Універсальна підтримка складних доменних моделей: спільне володіння, вкладені папки, успадкування прав через групи.
  - Висока масштабованість: затримки `O(log N)` або `O(1)` завдяки розгортанню вкладених графів та індексуванню.
  - Чітка стандартизація схеми (DSL) та єдина правда про стосунки між сутностями системи.
- **Слабкі боки**:
  - Висока операційна складність: вимагає розгортання окремого кластера та власного високопродуктивного сховища (PostgreSQL/CockroachDB/Spanner).
  - Потребує синхронізації стосунків: при створенні чи видаленні сутностей бізнес-сервіси мусять асинхронно або транзакційно надсилати кортежі у ReBAC-рушій.

## 5. Клас 4: Комплексні IAM та SSO платформи (Identity & Access Management)

Системи, що закривають повний цикл від первинного входу користувача (AuthN) до видачі OAuth2-токенів та перевірки високорівневих прав.

- **Представники**: `Keycloak`, `Auth0`, `Ory Suite` (Kratos + Keto), `Ping Identity`.
- **Механіка**: Центральний сервер автентифікації керує обліковими записами, сесіями, 2FA/MFA і видає підписані JWT-токени з розширеними ролями та scopes.
- **Сильні боки**:
  - Готові протоколи «з коробки»: OpenID Connect, OAuth 2.0, SAML 2.0, FIDO2/WebAuthn.
  - Повністю закриває задачу автентифікації користувачів, відновлення паролів, соціальних входів (Google, GitHub).
- **Слабкі боки**:
  - Непридатні для тонкої доменної авторизації на рівні окремих ресурсів (Fine-grained Authorization). Намагання запхати всі доменні права об'єктів у токени Keycloak призводить до вибуху розміру JWT та падіння системи.

## 6. Зведена матриця порівняння

| Критерій порівняння | 1. Вбудована AuthZ | 2. OPA / Cedar (ABAC) | 3. ReBAC (Zanzibar) | 4. IAM / SSO |
| :--- | :--- | :--- | :--- | :--- |
| **Основна модель** | RBAC / Custom Code | ABAC / Policy-as-Code | ReBAC (Граф стосунків) | RBAC / OAuth Scopes |
| **Де лежать дані** | База даних сервісу | Вхідний JSON / Пам'ять OPA | Спеціалізоване сховище кортежів | База даних IAM |
| **Середня затримка** | < 0.1 мс | 0.5 – 3 мс | 1 – 5 мс | 10 – 50 мс (не для RPC) |
| **Вибух ролей / графів** | Страждає від ролей | Вирішує атрибутами | Вирішує графами | Страждає від ролей |
| **Обхід вкладеності** | Важкі SQL JOIN | Важко (потрібен preload) | Нативно вбудовано | Відсутній |
| **Операційна ціна** | Нульова | Низька (Sidecar) | Висока (Окремий кластер) | Середня/Висока |
| **Мовна незалежність** | Ні | Так | Так | Так |

## 7. Архітектурний висновок

Обирати клас авторизаційної системи слід за масштабом доменної моделі та операційними спроможностями команди:

1. **Моноліт або 2-3 мікросервіси з простою моделлю**: Вбудована бібліотека (Casbin / CASL) надає найшвидший результат без інфраструктурних витрат.
2. **Динамічні правила регуляторики та конфігурований захист API**: OPA або Cedar забезпечують гнучке декларування політик у вигляді коду під Git-контролем.
3. **Складні домени зі спільним доступом, орендою та вкладеними об'єктами (SaaS / Smart Home)**: ReBAC (OpenFGA / SpiceDB) є єдиним архітектурно стійким рішенням, яке не ламається при зростанні зв'язків між ресурсами.
