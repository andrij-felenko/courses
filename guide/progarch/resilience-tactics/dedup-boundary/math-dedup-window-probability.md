# 🧮 Математична модель дедуплікаційних вікна, ймовірності колізій та фільтрів Блума

Ця математична вставка формалізує розрахунок ймовірностей колізій ідентифікаторів дедуплікації, обсягу пам'яті для фільтрів Блума (Bloom Filter) та оцінку оптимуму TTL вікна для відсікання повторних повідомлень.

## Інженерна математика дедуплікації

При проєктуванні високонавантажених шлюзів (API Gateway / Ingest Proxy) інженер змушений шукати математичний баланс між трьома величинами:
1. **Обсягом оперативної пам'яті (Memory Footprint):** Скільки бітів пам'яті виділяється на кожен ключ.
2. **Ймовірністю помилкового відсікання (False Positive Rate):** Який відсоток унікальних запитів буде помилково прийнято за дублікати й відхилено.
3. **Часовим вікном збереження (TTL Window):** Протягом якого часу система пам'ятає раніше оброблені запити.

Невдало обрані математичні параметри призводять до двох крайностей: або шлюз вичерпує всю оперативну пам'ять сервера Redis і падає за OOM (Out-Of-Memory), або починає помилково відсікати валідні унікальні запити користувачів як дублікати.

Нижче наведено вичерпні математичні виведення, що дозволяють розраховувати ці параметри без гадання на кавовій гущі.

## 1. Ймовірність колізії ключів ідепотентості (Birthday Paradox)

Якщо клієнт або gateway генерує ідентифікатор запиту випадковим чином (наприклад, UUIDv4 або хеш), виникає ризик колізії: коли два *різні* запити отримують однаковий ID і другий унікальний запит відсікається як дублікат.

Для послідовності з `N` запитів та простору можливих ключів обсягом `M` (для UUIDv4 кількість вибіркових бітів становить 122 біти, тобто `M = 2¹²² ≈ 5.3 × 10³⁶`), ймовірність принаймні однієї колізії `P(collision)` обчислюється за формулою:

```
P(collision) ≈ 1 - exp( -N² / (2·M) )      [наближення парадоксу днів народження]
```

Виведемо необхідну кількість запитів `N` для досягнення заданого порогу ймовірності колізії `P`:

```
ln(1 - P) ≈ -N² / (2·M)                    [логарифмування обох частин]
= N² ≈ -2·M · ln(1 - P)                    [виділення квадратного значення N²]
= N ≈ √( -2·M · ln(1 - P) )                [добування квадратного кореня]
```

Для невеликих ймовірностей `P ≪ 1` застосовуємо розклад `ln(1 - P) ≈ -P`:

```
N ≈ √( 2 · M · P )                         [остаточна формула розрахунку ліміту N]
```

### Покроковий приклад обчислення для високонавантаженого сервісу

Нехай системний потік становить 100 000 запитів на секунду (`10⁵ req/sec`). Розрахуємо кількість запитів за 1 рік безупинної роботи:

```
N = 10⁵ req/sec · 86400 sec/day · 365 days  [річна кількість секунд]
  = 3.15 × 10¹² запитів на рік              [обчислений річний потік запитів]
```

При використанні випадкового UUIDv4 (`M = 2¹²² ≈ 5.3 × 10³⁶`):

```
P(collision) ≈ (3.15 × 10¹²)² / (2 · 5.3 × 10³⁶) [підстановка річної кількості N у формулу]
             = 9.9 × 10²⁴ / 1.06 × 10³⁷          [обчислення чисельника й знаменника]
             = 9.3 × 10⁻¹³                       [фінальна ймовірність колізії]
```

Ймовірність колізії становить менше `10⁻¹²`, що робить унікальність UUIDv4 математично достатньою. Проте якщо ідентифікатор скорочується до 64-бітного хешу (`M = 2⁶⁴ ≈ 1.84 × 10¹⁹`):

```
P(collision) ≈ (3.15 × 10¹²)² / (2 · 1.84 × 10¹⁹) [підстановка N та M для 64 бітів]
             = 9.9 × 10²⁴ / 3.68 × 10¹⁹          [ділення чисельника на знаменник]
             = 2.68 × 10⁵ ≫ 1                    [результат перевищує одиницю]
```

Висновок: 64-бітний ключ дедуплікації дасть гарантовані хибні відсікання унікальних запитів уже при обробці 10 мільйонів запитів!

## 2. Розрахунок параметрів фільтра Блума для дедуплікації на межі

Для високонавантажених шлюзів (Edge Gateway) збереження мільйонів повних рядкових ключів у пам'яті є надто дорогим. Для компактного відсікання застосовують фільтр Блума (Bloom Filter).

Фільтр Блума має фундаментальну математичну властивість:
- Якщо фільтр відповідає `NO`, запит **гарантовано унікальний** (відсутні False Negatives, ймовірність пропустити дублікат 0%).
- Якщо фільтр відповідає `YES`, запит **можливо є дублікатом** з ймовірністю хибного спрацювання `p` (False Positive Probability).

Нехай `n` — очікувана кількість унікальних ключів у вікні дедуплікації, `p` — припустима ймовірність ложнопозитивного спрацювання (наприклад, `p = 0.001`, тобто 0.1%).

Необхідний розмір бітового масиву `m` (у бітах) обчислюється як:

```
m = - (n · ln(p)) / (ln(2)²)               [оптимальний розмір масиву в бітах]
```

Оптимальна кількість хеш-функцій `k`:

```
k = (m / n) · ln(2)                        [оптимальна кількість хеш-функцій]
```

### Обчислення розміру пам'яті для вікна 10 000 000 ключів

Нехай `n = 10 000 000` (10 мільйонів ключів у TTL-вікні), `p = 0.001` (0.1% хибних дублів):

```
m = - (10⁷ · ln(0.001)) / (0.69315)²       [підстановка значення n та p]
  = - (10⁷ · (-6.9077)) / 0.48045          [обчислення натурального логарифма]
  = 69 077 000 / 0.48045                   [множення елементів у чисельнику]
  = 143 775 627 бітів                      [фінальний обсяг масиву в бітах]
```

Обчислення розміру в мегабайтах:

```
m_bytes = 143 775 627 / 8                  [переведення бітів у байти]
        = 17 971 953 байтів                [підсумок у байтах]
        ≈ 17.97 Мегабайтів                 [округлення до мегабайтів]
```

Оптимальне число хеш-функцій `k`:

```
k = (143 775 627 / 10 000 000) · 0.69315    [підстановка розміру m та кількості n]
  = 14.37 · 0.69315                        [обчислення відношення m до n]
  = 9.96 ≈ 10 хеш-функцій                  [округлення до цілого числа]
```

Висновок: Фільтр Блума дозволяє тримати 10 мільйонів ключів дедуплікації всього в **18 МБ оперативної пам'яті** шлюзу з точністю відсікання 99.9%.

## 3. Математична модель оптимального TTL вікна

Вибір тривалості збереження ключа `TTL` регулюється розподілом затримок мережевих повторів (Retry Delays).

Нехай затримка між первинним запитом та його повтором (Retry) описується випадковою величиною `T_retry` з функцією розподілу ймовірностей `F(t) = P(T_retry ≤ t)`.

Якщо клієнт реалізує експоненційну паузу (Exponential Backoff) з максимальним числом спроб `R_max` та максимальним запізненням `T_max`, імовірність того, що дублікат прийде через час `t > TTL`, становить:

```
P(missed_duplicate) = 1 - F(TTL)           [ймовірність пропуску дубліката поза вікном]
```

Для гарантії того, що не більше ніж `ε` (наприклад, `ε = 10⁻⁶`) дублікатів проскочать повз дедуплікаційне вікно межі, TTL обчислюється з умови:

```
F(TTL) ≥ 1 - ε                             [нижня межа функції розподілу]
= TTL = F⁻¹(1 - ε)                         [обчислення квантиля через обернену функцію]
```

Якщо `T_max` клієнтського повтору становить 1 годину, вибір `TTL = 24 години` дає `P(missed_duplicate) ≈ 0`, що повністю покриває мережеві затримки повторів.

## 4. Порівняння Bloom Filter та Cuckoo Filter за ефективністю пам'яті

Окрім класичного фільтра Блума, в сучасних високопродуктивних шлюзах застосовується Cuckoo Filter (зозулиний фільтр).

Математична порівняльна характеристика двох фільтрів:

```
Характеристика                 Bloom Filter                        Cuckoo Filter
-------------------------------------------------------------------------------------------------
Підтримка видалення ключів     Ні (потребує Counting Bloom)        Так (підтримує видалення)
Локальність кешу CPU (L1/L2)   Погана (k хешів по всьому масиву)   Відмінна (перевірка 2 бакетів)
Витрати пам'яті при p = 0.1%   1.44 log2(1/p) ≈ 14.4 біта/ключ    1.08 log2(1/p) ≈ 10.8 біта/ключ
Складність вставки (Insert)    O(k)                                 O(1) середнє
```

Cuckoo Filter будується на базі зозулиного хешування (Cuckoo Hashing). Він зберігає не повні хеші ключів, а короткі відбитки (fingerprints) фіксованої довжини (наприклад, 8 або 12 бітів). Завдяки тому що відбитки зберігаються в таблиці з двома альтернативними бакетами, Cuckoo Filter підтримує видалення ключів після закінчення їх TTL без необхідності перебудови всього масиву.

Висновок: Cuckoo Filter дозволяє зменшити витрати оперативної пам'яті ще на 25% порівняно з фільтром Блума при збереженні того самого рівня False Positive Rate.

## 5. Математична модель вичерпання пулу з'єднань бази даних при відсутності дедуп на межі

Оцінимо математичне навантаження на базу даних під час Retry Storm, якщо дедуплікатор на межі вимкнено.

Нехай сервіс обробляє потік унікальних запитів `λ = 1000 req/sec`. Час обробки одного запиту у БД становить `T_db = 50 ms = 0.05 sec`. За законом Літтла (Little's Law), середня кількість активних з'єднань у базі даних дорівнює:

```
L_normal = λ · T_db                        [закон Літтла для штатного режиму]
         = 1000 · 0.05                     [підстановка параметрів]
         = 50 активних з'єднань            [штатне навантаження на DB]
```

Якщо в мережі стається короткочасна затримка на 2 секунди, кожен з 2000 активних клієнтів робить 5 повторних спроб (Retry). Вхідний потік зростає до `λ_storm = 1000 + 5000 = 6000 req/sec`.

Нова кількість активних з'єднань без дедуп на межі:

```
L_storm = λ_storm · T_db                   [навантаження під час шторму повторів]
        = 6000 · 0.05                      [підстановка збільшеного потоку]
        = 300 активних з'єднань            [перевищення пулу DB connection pool]
```

Якщо максимальний розмір пулу з'єднань бази даних обмежено значенням `max_connections = 100`, система миттєво вичерпає пул і почне відхиляти нові транзакції з помилкою `Connection pool exhausted`.

При наявності Edge Filter, який відсікає 5000 повторних запитів за 0.1 мілісекунди на межі, навантаження на базу даних лишається на рівні `L_normal = 50`, що математично доводить критичність межі для стійкості всієї інфраструктури.
