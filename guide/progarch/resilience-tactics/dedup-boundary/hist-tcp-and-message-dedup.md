# 📜 Від мережевого кадру до брокера: історія боротьби з дублями

Витоки дедуплікації повідомлень простежуються від перших протоколів надійного зв'язку в мережах ARPANET і TCP до сучасних розподілених брокерів черг. Фізична ненадійність мережевих каналів змусила інженерів вигадати послідовні номери (sequence numbers), вікна повторів та ідемпотентні проксі, що пояснює, чому сучасний бекенд стикається з тими самими фундаментальними обмеженнями на межі систем.

## Проблема надійного зв'язку на ненадійному медіумі

Коли в 1970-х роках розроблялися перші розподілені мережі (ARPANET, ALOHANET), ключовою вимогою була надійність передачі даних через фізично нестабільні телефонні лінії та радіоканали. В умовах високого рівня завад, втрати пакетів та змін маршрутизації єдиним способом гарантувати доставку було впровадження автоматичного повтору запиту (Automatic Repeat-reQuest, ARQ).

Проте повтор запиту неминуче спричиняв появу дублікатів. Якщо одержувач приймав пакет, але його підтвердження (ACK) губилося в мережі або затримувалося через затори на роутерах, відправник за таймаутом надсилав той самий пакет вдруге. Без спеціального механізму розпізнавання одержувач обробляв би той самий блок даних двічі.

Першим фундаментальним рішенням стало впровадження **послідовних номерів (Sequence Numbers)** та **вікон очікування (Sliding Window)**. У протоколі TCP (RFC 793, 1981 рік, авторства Вінтона Серфа та Роберта Еллісона) кожен байт або сегмент даних отримує унікальний порядковий номер у межах з'єднання. Одержувач зберігає стан у пам'яті — поточно очікуваний номер сегмента. Якщо приходить сегмент із номером, який уже було прийнято й підтверджено, мережевий стек просто скидає цей дублікат і повторно надсилає ACK.

```
Відправник                           Одержувач
    │                                    │
    ├─── Segment (Seq=100) ─────────────►│ (Отримано 100, чекаємо 200)
    │                                    │
    │◄── ACK (Next=200) ── [ВТРАЧЕНО] ───┤ (ACK не дійшов!)
    │                                    │
    │ (Таймаут вичерпано, Retry!)        │
    ├─── Segment (Seq=100) ─────────────►│ (Дублікат Seq=100!)
    │                                    │ -> Скидаємо дубль
    │◄── ACK (Next=200) ─────────────────┤ -> Повторюємо ACK 200
```

Ця схема працювала бездоганно на рівні одного TCP-з'єднання, але мала два суттєвих обмеження:
1. **Збереження стану в пам'яті (Stateful Connection):** Вікно дедуплікації прив'язане до конкретного TCP-сокета й скидається при розриві з'єднання або перезавантаженні вузла.
2. **Локальний контекст:** Сегмент TCP не знає нічого про бізнес-зміст додатка.

## Ера бізнес-повідомлень: Enterprise Integration Patterns

З появою в 1990-х і 2000-х роках корпоративних сервісних шин (Enterprise Service Bus, ESB) та орієнтованих на повідомлення систем (Message-Oriented Middleware, MOM, таких як IBM MQ, MSMQ, TIBCO) проблему дедуплікації довелося підняти з мережевого рівня на рівень прикладних повідомлень.

У 2003 році Грегор Хопе (Gregor Hohpe) та Боб Вулф (Bobby Woolf) у своїй фундаментальній праці *Enterprise Integration Patterns (EIP)* систематизували паттерн **Idempotent Receiver (Ідемпотентний споживач)** та **Resequencer / De-duplicator**. Вони формалізували принципову різницю між двома концепціями:
- **Transport-level Deduplication (Дедуплікація транспорту):** Здійснюється на рівні протоколу (наприклад, JMS MessageID або WS-ReliableMessaging). Брокер або проксі перевіряє заголовок повідомлення й відсікає дублі до передачі додаткам.
- **Application-level Deduplication (Дедуплікація додатка):** Здійснюється всередині бізнес-компонента за допомогою бізнес-ключів (наприклад, Номер Замовлення + Ідентифікатор Транзакції).

Спроба зробити дедуплікацію універсальною на рівні WS-ReliableMessaging (стандарт W3C для SOAP-вебсервісів середини 2000-х) виявилася надто громіздкою: збереження стану всіх отриманих GUID у базі даних проксі-сервера створювало величезне вузьке місце для продуктивності (bottleneck) і вимагало складних алгоритмів очищення (garbage collection) старих ключів.

## Сучасні брокери: SQS FIFO та Apache Kafka

З розвитком хмарних систем та високонавантаженого потоку даних (event streaming) підхід до дедуплікації розділився на дві школи:

1. **Amazon SQS FIFO (MessageDeduplicationId):**
   Amazon Web Services впровадив дедуплікацію на межі черги. При відправці повідомлення в SQS FIFO можна вказати `MessageDeduplicationId` або увімкнути автоматичне хешування тіла повідомлення (`ContentBasedDeduplication`). SQS гарантує дедуплікацію протягом **5-хвилинного вікна**. Якщо те саме повідомлення надсилається впродовж 5 хвилин, SQS приймає його, але не доставляє споживачам повторно, повертаючи успішний статус відправнику.
   *Урок історії:* 5-хвилинне вікно — це свідомий компроміс між витратами на збереження стану (пам'ять і розподілені індекси SQS) та захистом від частих повторів через мережеві таймаути.

2. **Apache Kafka (Idempotent Producer та Exact-Once Semantics):**
   У версії Kafka 0.11 (2017 рік) було представлено механізм `enable.idempotence=true` та підтримку семантики Exactly-Once Semantics (EOS). Кожен продюсер отримує унікальний `PID` (Producer ID), а кожне повідомлення — зростальний порядковий номер `Sequence Number` для кожної партиції (`TopicPartition`). Брокер Kafka перевіряє, чи є новий `Sequence Number` рівно на 1 більшим за останній збережений для цього `PID`. Якщо приходить той самий номер — брокер відсікає дубль і повертає успіх.
   *Урок історії:* Схема Kafka майже ідентична протоколу TCP 1981 року, але перенесена на рівень розподіленого реплікованого логу. Вона працює виключно в межах сесії продюсера й не захищає від дублів, створених новими процес-екземплярами продюсера без збереження `PID`.

```
Рівень           Механізм                        Вікно стану          Витрати / Точність
-----------------------------------------------------------------------------------------
TCP Layer        Seq Numbers (RFC 793)           TCP Socket lifetime  Мінімальні / Низька
Queue Edge       SQS MessageDeduplicationId     5 хвилин (TTL)       Середні / Середня
Kafka Broker     Producer ID + Seq Num           Producer Session     Низькі / Локальна
Domain DB        UNIQUE Index + ACID Transaction Нескінченне (DB)     Високі / Абсолютна
```

Історія розвитку показала: що ближче дедуплікація до мережевої межі, то вона дешевша та простіша, але то коротшим є її вікно пам'яті й то поверхневішим є її розуміння бізнес-контексту.
