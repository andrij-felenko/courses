# 📋 Інтерфейси спостереження та трасування мережевого стека

Коли в мережевому стеку операційної системи виникає деградація пропускної здатності, непередбачувані сплески затримок або аномальні втрати пакетів, системному інженеру потрібні точні числові метрики ядра, а не здогадки. Ядро Linux містить багаторівневий каркас спостереження, який фіксує проходження кадрів від моменту замикання контактів мережевого адаптера до запису даних у буфер процесу. Цей інструментарій охоплює структури псевдофайлової системи `/proc`, статичні трасувальні точки ядра, лічильники апаратних буферів контролера та типізовані коди причин скидання пакетів.

Розуміння цих інтерфейсів дозволяє локалізувати місце виникнення проблеми з точністю до конкретної функції ядра або апаратного регістра мережевого адаптера.

### 1. Поциклова статистика черг ядра: `/proc/net/softnet_stat`

Файл `/proc/net/softnet_stat` надає низькорівневу статистику роботи обробника м'яких переривань мережі `NET_RX_SOFTIRQ` окремо для кожного логічного ядра процесора. У ядрі кожне процесорне ядро має власну незалежну структуру даних `struct softnet_data` (визначену в заголовковому файлі `include/linux/netdevice.h`). Щоб уникнути міжпроцесорних блокувань і взаємного витіснення рядків процесорного кешу, ці структури вирівняні за межею кеш-лінії процесора (`____cacheline_aligned_in_smp`).

При читанні файлу `/proc/net/softnet_stat` ядро виводить по одному рядку для кожного активного CPU. Кожен рядок складається з одинадцяти шістнадцяткових чисел, розділених пробілами, що відображають стан лічильників відповідної структури `softnet_data`.

```
0038a4f1 00000000 00000014 00000000 00000000 00000000 00000000 00000000 00000000 00000000 00000000
```

#### Детальний розбір стовпчиків та їхнього фізичного змісту

1. **Перший стовпчик (`processed`):** Загальна кількість мережевих пакетів, успішно опрацьованих цим процесорним ядром через функцію `net_rx_action()`. Цей лічильник інкрементується щоразу, коли ядро забирає черговий `struct sk_buff` з кільцевого буфера або з черги backlog.
2. **Другий стовпчик (`dropped`):** Кількість пакетів, які ядро було змушене безповоротно скинути через переповнення вхідної черги процесора `input_pkt_queue` (черга `backlog`). Коли на систему надходить трафік від інтерфейсу без апаратної підтримки NAPI або задіяно механізм програмного розподілу пакетів RPS, вхідний потік кладеться в чергу ядра. Якщо довжина цієї черги досягає ліміту, заданого параметром `net.core.netdev_max_backlog`, функція `enqueue_to_backlog()` негайно звільняє пам'ять пакета та інкрементує цей лічильник. Зростання цього числа однозначно свідчить про те, що м'які переривання не встигають забирати пакети з черги ядра.
3. **Третій стовпчик (`time_squeeze`):** Кількість випадків, коли функція опитування драйвера `napi->poll()` була примусово перервана ядром до того, як вона встигла спустошити кільцевий буфер мережевої карти. Таке переривання стається з двох причин: або було вичерпано квоту пакетів (параметр `net.core.netdev_budget`, за замовчуванням 300 пакетів), або сплив часовий ліміт безперервного виконання SoftIRQ (параметр `net.core.netdev_budget_usecs`, зазвичай 2 мілісекунди). Зростання значення `time_squeeze` сигналізує про високе навантаження на процесор і необхідність збільшення квоти опитування або оптимізації фонових обчислень.
4. **Четвертий стовпчик (`cpu_collision`):** Лічильник колізій при спробі захоплення спінового замка черги передачі адаптера (`txq->_xmit_lock`). У старих одночергових мережевих картах кілька процесорів могли одночасно намагатися надіслати пакет через один інтерфейс. У сучасних контролерах із множинними чергами передачі (Multi-Queue TX) цей лічильник зазвичай залишається нульовим.
5. **П'ятий стовпчик (`received_rps`):** Кількість міжпроцесорних переривань IPI, отриманих цим ядром від інших процесорів для пробудження обробника черги RPS. Це число показує, наскільки активно інші ядра перенаправляють мережеву роботу на це ядро.
6. **Шостий стовпчик (`flow_limit_count`):** Кількість пакетів, скинутих механізмом Flow Limit. Цей механізм захищає чергу `backlog` процесора від монополізації одним занадто інтенсивним мережевим потоком (наприклад, спрямованою DoS-атакою за одним UDP-портом), відсікаючи пакети конкретного хешу потоку, якщо вони займають понад половину черги ядра.
7. **Сьомий стовпчик (`backlog`):** Поточна довжина черги `input_pkt_queue` процесора. Введена в ядрах версії 5.18 для миттєвої оцінки заповнення черги без очікування переповнення.
8. **Восьмий стовпчик (`cpu_offline`):** Кількість пакетів, які довелося терміново перенести на сусідні ядра під час динамічного відключення поточного процесорного ядра з конфігурації системи.
9. **Дев'ятий — одинадцятий стовпчики:** Зарезервовані поля внутрішньої діагностики апаратних платформ та розширень драйверів.

### 2. Параметри конфігурації буферів ядра (Підсистема Sysctl)

Керування розмірами буферів, поведінкою алгоритмів TCP та квотами опитування здійснюється через механізм `sysctl`. Значення цих параметрів змінюють поведінку функцій ядра в реальному часі без необхідності перезавантаження операційної системи.

```
/proc/sys/net/
├── core/
│   ├── netdev_max_backlog     # Максимальна глибина вхідної черги на ядро CPU
│   ├── netdev_budget          # Ліміт пакетів за один цикл виклику napi->poll()
│   ├── netdev_budget_usecs    # Часовий ліміт роботи SoftIRQ на процесорі (мкс)
│   ├── dev_weight             # Вагова частка мережевого інтерфейсу в планувальнику
│   ├── rmem_max               # Абсолютна верхня межа буфера прийому сокета
│   └── wmem_max               # Абсолютна верхня межа буфера передачі сокета
└── ipv4/
    ├── tcp_rmem               # Вектор автоналаштування пам'яті прийому TCP
    ├── tcp_wmem               # Вектор автоналаштування пам'яті відправки TCP
    ├── tcp_max_syn_backlog    # Максимальна довжина черги напіввідкритих з'єднань
    └── tcp_moderate_rcvbuf    # Динамічне підлаштування вікна під швидкість мережі
```

#### Семантика та взаємозв'язок параметрів керування пам'яттю

Підсистема сокетів ядра Linux використовує дворівневу модель обмеження пам'яті: загальносистемні ліміти `rmem_max`/`wmem_max` та динамічні протокольні вектори `tcp_rmem`/`tcp_wmem`.

Параметр `net.core.netdev_max_backlog` визначає максимальну кількість структур `sk_buff`, які можуть одночасно перебувати у черзі `input_pkt_queue` процесорного ядра до моменту їхньої передачі в протокольний стек. Якщо на сервері активні віртуальні інтерфейси або програмна маршрутизація RPS, за замовчуванням встановлене значення 1000 є занадто малим. Під час короткочасних сплесків трафіку на швидкості 10 Гбіт/с черга на 1000 пакетів переповнюється за 67 мікросекунд. Для високошвидкісних систем цей параметр збільшують до 10000–65536.

Параметр `net.core.netdev_budget` задає максимальну кількість пакетів, яку драйвер мережевої карти має право вичитати з кільця дескрипторів за один виклик функції `napi->poll()`. Збільшення цього значення до 600–1000 дозволяє обробляти великі пачки трафіку з меншою кількістю перемикань контексту, але дещо збільшує затримку виконання користувацьких процесів на цьому ж ядрі CPU.

Параметр `net.core.netdev_budget_usecs` встановлює жорсткий часовий поріг (у мікросекундах) безперервної роботи обробника `net_rx_action()`. Навіть якщо ліміт пакетів `netdev_budget` ще не вичерпано, спливання цього таймера змушує SoftIRQ віддати процесор іншим задачам ядра, запобігаючи монополізації системи.

Вектори `net.ipv4.tcp_rmem` та `net.ipv4.tcp_wmem` складаються з трьох цілих чисел:
1. **Мінімальний розмір (`min`):** Гарантований обсяг пам'яті в байтах, який виділяється для буфера кожного сокета навіть під час сильного дефіциту оперативної пам'яті в системі (зазвичай 4096 байтів).
2. **Початковий розмір (`default`):** Розмір буфера за замовчуванням, який призначається новоствореному сокету при його відкритті.
3. **Максимальний розмір (`max`):** Верхня межа, до якої алгоритм автоматичного підлаштування буферів TCP (*TCP Buffer Auto-tuning*) має право збільшувати буфер з'єднання при зростанні добутку пропускної здатності на затримку каналу (*Bandwidth-Delay Product, BDP*).

Для каналу 10 Гбіт/с із затримкою RTT 20 мілісекунд теоретичний розмір BDP становить приблизно 25 мегабайтів. Якщо параметр `tcp_rmem[2]` обмежений стандартними 6 мегабайтами, протокол TCP не зможе розширити ковзне вікно передачі до повної місткості каналу, що штучно обмежить швидкість передачі даних на рівні близько 2,4 Гбіт/с незалежно від фізичної швидкості лінії.

### 3. Специфікація ядерних трасувальних точок (Tracepoints)

Статичні трасувальні точки ядра Linux інтегровані безпосередньо у вихідний код мережевих підсистем через макрос `TRACE_EVENT`. Вони мають нульовий накладний розхід у вимкненому стані (використовують інструкцію заміни коду `nop` через механізм `static_key`) та генерують структуровані події при активації через `ftrace`, `perf` або програми `eBPF`.

#### Головні трасувальні точки конвеєра прийому та передачі

* `net:netif_receive_skb`: Спрацьовує в момент виходу пакета з драйвера мережевої карти та його передачі в ядро через функцію `__netif_receive_skb()`. Дозволяє зафіксувати точний час надходження кадру, мережевий інтерфейс та адресу структури `sk_buff` у пам'яті.
* `net:net_dev_queue`: Фіксує постановку вихідного пакета в чергу планувальника трафіку (Qdisc) всередині функції `dev_queue_xmit()`.
* `net:net_dev_xmit`: Спрацьовує безпосередньо перед передачею пакета апаратному драйверу через виклик методу `ndo_start_xmit()`. Різниця в часі між `net_dev_queue` та `net_dev_xmit` показує точну затримку перебування пакета в чергах планувальника Qdisc.
* `skb:kfree_skb`: Критична точка спостереження, яка спрацьовує щоразу, коли пакет скидається ядром через будь-яку помилку (некоректна контрольна сума, відсутність маршруту, блокування файрволом, переповнення буфера).
* `skb:consume_skb`: Подія штатного та успішного вивільнення пам'яті пакета після того, як його корисні дані були скопійовані процесу або успішно передані в мережевий дріт.
* `sock:sock_rcvqueue_full`: Сигналізує про переповнення черги сокета `sk_receive_queue`, коли процес не встигає зчитувати дані системними викликами `recv()` або `read()`.
* `tcp:tcp_probe`: Регулярно фіксує параметри внутрішнього стану протоколу TCP для активного з'єднання: розмір вікна перевантаження `snd_cwnd`, поріг повільного старту `snd_ssthresh`, поточний розрахунок затримки `srtt` та довжину черги непідтверджених сегментів.

Формат бінарних даних, які передаються в кільцевий буфер трасування для кожної точки, описано у відповідних файлах псевдофайлової системи `/sys/kernel/debug/tracing/events/`.

```text
/* Формат події /sys/kernel/debug/tracing/events/net/netif_receive_skb/format */
name: netif_receive_skb
ID: 1420
format:
    field:unsigned short common_type;         offset:0;  size:2; signed:0;
    field:unsigned char common_flags;         offset:2;  size:1; signed:0;
    field:unsigned char common_preempt_count; offset:3;  size:1; signed:0;
    field:int common_pid;                     offset:4;  size:4; signed:1;

    field:void * skbaddr;                     offset:8;  size:8; signed:0;
    field:unsigned int len;                   offset:16; size:4; signed:0;
    field:char name[16];                      offset:20; size:16; signed:1;
```

### 4. Типізовані причини скидання пакетів (`SKB_DROP_REASON_*`)

До версії ядра Linux 5.17 скидання пакета в будь-якому місці ядра викликало універсальну функцію `kfree_skb()`. Це перетворювало діагностику втрат на складне розслідування: утиліти фіксували факт знищення пакета, але не могли повідомити, яка саме підсистема (драйвер, файрвол, таблиця маршрутів чи сокет) ініціювала скидання.

Починаючи з версії 5.17, ядро перейшло на функцію `kfree_skb_reason(skb, reason)`. Код причини передається у формі константи перечислення `enum skb_drop_reason` (визначеного в `include/net/dropreason-core.h`).

```text
/* Структура події /sys/kernel/debug/tracing/events/skb/kfree_skb/format */
name: kfree_skb
ID: 1455
format:
    field:void * skbaddr;                     offset:8;  size:8; signed:0;
    field:void * location;                    offset:16; size:8; signed:0;
    field:unsigned short protocol;            offset:24; size:2; signed:0;
    field:enum skb_drop_reason reason;        offset:28; size:4; signed:0;
```

#### Специфікація основних кодів причин скидання

* `SKB_DROP_REASON_NOT_SPECIFIED` (код 1): Скидання викликано ділянкою коду ядра, яку ще не оновлено до нової системи типізованих причин.
* `SKB_DROP_REASON_NO_SOCKET` (код 2): Пакет надійшов на локальну IP-адресу, але для вказаної пари портів призначення немає відкритого сокета ні в таблиці прослуховування, ні в таблиці встановлених з'єднань. Ядро генерує TCP RST або ICMP Port Unreachable.
* `SKB_DROP_REASON_PKT_TOO_SMALL` (код 3): Довжина отриманого кадру менша за мінімальний розмір заголовка відповідного протоколу (пошкодження даних або некоректна інкапсуляція).
* `SKB_DROP_REASON_TCP_CSUM` (код 4): Апаратна або програмна перевірка контрольної суми заголовка чи корисних даних TCP завершилася помилкою. Пакет відкидається без надсилання сповіщень відправнику.
* `SKB_DROP_REASON_SOCKET_RCVBUFF` (код 5): Буфер прийому сокета `sk_receive_queue` вичерпав ліміт пам'яті, встановлений параметрами `SO_RCVBUF` або `tcp_rmem`. Застосунок користувача не встигає вичитувати дані.
* `SKB_DROP_REASON_NETFILTER_DROP` (код 8): Пакет був заблокований правилом міжмережевого екрана iptables, nftables або модулем conntrack із вердиктом `NF_DROP`.
* `SKB_DROP_REASON_IP_INADDRERRORS` (код 10): IP-адреса призначення в заголовку пакета є неприпустимою (наприклад, адреса підмережі `0.0.0.0` або адреса зворотного зв'язку, отримана з зовнішнього фізичного інтерфейсу).
* `SKB_DROP_REASON_IP_NOPROTO` (код 14): Поле протоколу в IP-заголовку (`iph->protocol`) вказує на номер протоколу, для якого в ядрі не зареєстровано жодного обробника в масиві `inet_protos`.
* `SKB_DROP_REASON_TCP_FLAGS` (код 19): Отримано TCP-сегмент із неприпустимою комбінацією прапорців (наприклад, одночасно встановлені прапорці SYN та FIN, або відсутність будь-яких прапорців).
* `SKB_DROP_REASON_TCP_OLD_ACK` (код 24): Отримано дублюючий або застарілий номер підтвердження ACK, який вказує на вже підтверджені дані поза лівою межею поточного ковзного вікна.
* `SKB_DROP_REASON_XDP` (код 32): Пакет скинуто на рівні драйвера програмою eBPF XDP, що повернула дію `XDP_DROP`.
* `SKB_DROP_REASON_TC_INGRESS` (код 36): Пакет відкинуто фільтром підсистеми Traffic Control на вході інтерфейсу з вердиктом `TC_ACT_SHOT`.

### 5. Інтерфейс телеметрії контролера `ethtool`

Утиліта `ethtool` здійснює взаємодію з мережевим драйвером через системний виклик `ioctl` за допомогою керуючих кодів `SIOCETHTOOL` або через сучасний інтерфейс Netlink (`GENL_ID_GENERATE` для сімейства `ethtool`). Вона дозволяє безпосередньо опитувати стан кремнієвих регістрів контролера та конфігурувати кільцеві буфери DMA.

#### 5.1. Керування розміром кільцевого буфера дескрипторів

```bash
$ ethtool -g eth0
Ring parameters for eth0:
Pre-set maximums:
RX:             4096
TX:             4096
Current hardware settings:
RX:             1024
TX:             1024
```

Секція `Pre-set maximums` відображає апаратну місткість кремнієвого блоку контролера — максимальну кількість DMA-дескрипторів, яку підтримує логіка чипа.

Секція `Current hardware settings` показує фактичну кількість виділених сторінок оперативної пам'яті для кільця дескрипторів на цей момент. Якщо мережевий адаптер фіксує переповнення буфера через короткі інтенсивні сплески трафіку, адміністратор може розширити розмір кільця до апаратного максимуму командою:

```bash
# Збільшення розміру кілець прийому та передачі до максимуму
$ sudo ethtool -G eth0 rx 4096 tx 4096
```

Ця операція змушує драйвер переаллокувати таблицю DMA-дескрипторів та перезапустити чергу інтерфейсу.

#### 5.2. Адаптивне злиття переривань (Interrupt Moderation)

Генерація апаратного переривання для кожного окремого кадру призводить до непродуктивної витрати процесорного часу. Підсистема адаптивного злиття переривань (*Adaptive Interrupt Moderation / Coalescing*) змушує мережеву карту накопичувати пакети в апаратному буфері FIFO перед відправкою сигналу переривання на шину PCIe.

```bash
$ ethtool -c eth0
Coalesce parameters for eth0:
Adaptive RX: on
rx-usecs: 62
rx-frames: 32
```

Параметр `Adaptive RX: on` активує динамічний алгоритм ядра (*Dynamic Interrupt Moderation, DIM*), який автоматично аналізує частоту надходження пакетів. При низькій інтенсивності трафіку ядро зменшує затримку переривань майже до нуля, забезпечуючи мінімальний час відгуку для поодиноких запитів. При зростанні навантаження алгоритм автоматично піднімає затримку до кількох десятків мікросекунд, групуючи сотні пакетів в одне переривання та кардинально знижуючи завантаження CPU.

#### 5.3. Апаратні лічильники помилок та втрат

Опитування внутрішніх лічильників мережевого адаптера виконується командою `ethtool -S <interface>`. На відміну від стандартних лічильників утиліти `ip -s link`, `ethtool` виводить деталізовану діагностику специфічних апаратних блоків конкретної моделі мережевої карти.

```bash
$ ethtool -S eth0 | grep -E "drop|miss|err|fifo|alloc"
     rx_dropped: 0
     tx_dropped: 0
     rx_missed_errors: 18420
     rx_fifo_errors: 0
     rx_no_buffer_count: 18420
     alloc_rx_page_failed: 0
```

Лічильники `rx_missed_errors` та `rx_no_buffer_count` інкрементуються апаратним блоком мережевого контролера в той момент, коли вхідний кадр прибуває з фізичного кабелю, але адаптер не знаходить жодного вільного DMA-дескриптора в кільці RX Ring. Кадр відкидається на рівні кремнію ще до того, як операційна система дізнається про його існування. Поява ненульових значень у цих полях свідчить про необхідність збільшення розміру кільця RX (`ethtool -G`), перевірки закріплення переривань за ядрами CPU (*IRQ Affinity*) або налаштування енергозберігаючих станів процесора (*C-states*), вихід із яких може затримувати реакцію процесора на переривання.
