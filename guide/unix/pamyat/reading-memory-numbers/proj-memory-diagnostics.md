# ⚙️ Практикум: утиліта поглибленої діагностики пам'яті

Стандартні утиліти системного адміністрування `ps`, `top` та `free` були спроєктовані в епоху, коли модель пам'яті Unix була значно простішою, а спільні ресурси здебільшого обмежувалися кодом спільних бібліотек. У сучасному Linux із багаторівневим кешуванням, анонімним надлишковим виділенням (overcommit), динамічними аренами алокаторів, механізмами cgroups v2 та прозорими великими сторінками показання цих утиліт часто вводять інженерів в оману.

Цей практикум присвячено створенню утиліти `meminspect` — інструмента поглибленого аудиту, який за один прохід формує об'єктивну картину споживання оперативної пам'яті конкретним процесом у нерозривному зв'язку із системним оточенням. Ми розглянемо фізичний зміст використовуваних джерел у `/proc`, напишемо надійний і безпечний код мовами C та C++, розберемо його роботу на реальних прикладах та дослідимо підводні камені обліку пам'яті в ядрі.

## Архітектура збору даних та вибір джерел

Для формування чесного звіту утиліта не може обмежуватися лише файлом `/proc/<pid>/statm`, оскільки лічильники в ньому не розділяють спільні та приватні сторінки й не знають про модифікований стан даних. Наша програма звертається до чотирьох незалежних інтерфейсів ядра:

1. **Глобальний баланс пам'яті: `/proc/meminfo`.** Звідси ми отримуємо загальну місткість фізичної пам'яті (`MemTotal`), вільні кадри (`MemFree`), чесну оцінку доступного резерву (`MemAvailable`), брудний файловий кеш (`Dirty`) та кеші метаданих ядра, що підлягають вивільненню (`SReclaimable`).
2. **Метрики системного дефіциту: `/proc/pressure/memory`.** Інтерфейс PSI (англ. *Pressure Stall Information*) показує частку часу, яку задачі втрачають на очікування сторінок у поточному 10-секундному вікні (`some avg10` та `full avg10`). Це дозволяє з першого погляду відрізнити здорове заповнення пам'яті кешем від катастрофічного буксування.
3. **Агрегований стан таблиць сторінок: `/proc/<pid>/smaps_rollup`.** Це головне джерело детальної інформації про процес. На відміну від застарілого `/proc/<pid>/smaps`, який генерує окремий текстовий блок для кожної ділянки VMA (що створює тисячі рядків для складних програм), `smaps_rollup` виконує один прохід таблицями сторінок процесу в просторі ядра й повертає єдиний зведений блок. З нього ми зчитуємо `Rss`, `Pss`, `Private_Clean`, `Private_Dirty`, `Shared_Clean`, `Shared_Dirty`, `Swap` та `SwapPss`.
4. **Рейтинг кандидата на ліквідацію: `/proc/<pid>/oom_score` та `oom_score_adj`.** Ці числа показують поточну оцінку «поганості» процесу з точки зору алгоритму `oom_badness` ядра та налаштовану користувачем поправку пріоритету.

## Специфіка взаємодії з псевдофайлами `/proc`

Під час розробки системних інструментів для Linux необхідно враховувати фундаментальну відмінність псевдофайлової системи procfs від звичайних файлових систем на блокових дисках:

- **Нульовий розмір файлів (`st_size == 0`).** Запит `stat()` для будь-якого файлу в `/proc` майже завжди повертає розмір 0 байтів. Це пояснюється тим, що вміст файлу не існує заздалегідь у пам'яті, а генерується функціями ядра «на льоту» під час виклику `read()`. Тому виділити буфер точного розміру заздалегідь неможливо — необхідно або читати у фіксований буфер достатньої місткості, або використовувати динамічне читання рядків через `getline()`.
- **Зміна вмісту прямо під час читання.** Якщо процес активно виділяє пам'ять, його таблиці сторінок змінюються паралельно з тим, як ядро сканує їх для заповнення виводу `smaps_rollup`. Ядро захищає консистентність обходу блокуванням `mmap_lock` у режимі читання, проте між двома послідовними відкриттями різних файлів (наприклад, `/proc/<pid>/status` та `/proc/<pid>/smaps_rollup`) стан процесу може дещо змінитися. Це нормальна поведінка багатозадачної системи.
- **Відсутність повноцінної підтримки `lseek`.** Більшість псевдофайлів ядра розраховані на одноразове послідовне вичитування від початку до кінця. Спроби перемістити курсор за допомогою `lseek()` або `rewind()` для повторного зняття метрик без виклику `close()` можуть призвести до застарілих даних або несподіваного повернення порожнього результату. Найнадійніший патерн — повторне відкриття (`open()` / `fopen()`) на кожній ітерації моніторингу.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

typedef struct {
    unsigned long mem_total_kb;
    unsigned long mem_free_kb;
    unsigned long mem_avail_kb;
    unsigned long dirty_kb;
    unsigned long sreclaim_kb;
    double psi_some_avg10;
    double psi_full_avg10;
} SysMemInfo;

typedef struct {
    pid_t pid;
    unsigned long vsz_kb;
    unsigned long rss_kb;
    unsigned long pss_kb;
    unsigned long priv_clean_kb;
    unsigned long priv_dirty_kb;
    unsigned long shared_clean_kb;
    unsigned long shared_dirty_kb;
    unsigned long swap_kb;
    unsigned long swap_pss_kb;
    int oom_score;
    int oom_score_adj;
} ProcMemInfo;

static int read_sys_mem(SysMemInfo *sys) {
    memset(sys, 0, sizeof(*sys));
    FILE *f = fopen("/proc/meminfo", "r");
    if (!f) return -1;

    char *line = NULL;
    size_t len = 0;
    while (getline(&line, &len, f) != -1) {
        sscanf(line, "MemTotal: %lu kB", &sys->mem_total_kb);
        sscanf(line, "MemFree: %lu kB", &sys->mem_free_kb);
        sscanf(line, "MemAvailable: %lu kB", &sys->mem_avail_kb);
        sscanf(line, "Dirty: %lu kB", &sys->dirty_kb);
        sscanf(line, "SReclaimable: %lu kB", &sys->sreclaim_kb);
    }
    free(line);
    fclose(f);

    FILE *psi = fopen("/proc/pressure/memory", "r");
    if (psi) {
        char buf[256];
        while (fgets(buf, sizeof(buf), psi)) {
            if (strncmp(buf, "some", 4) == 0) {
                sscanf(buf, "some avg10=%lf", &sys->psi_some_avg10);
            } else if (strncmp(buf, "full", 4) == 0) {
                sscanf(buf, "full avg10=%lf", &sys->psi_full_avg10);
            }
        }
        fclose(psi);
    }
    return 0;
}

static int read_proc_mem(pid_t pid, ProcMemInfo *proc) {
    memset(proc, 0, sizeof(*proc));
    proc->pid = pid;

    char path[128];
    snprintf(path, sizeof(path), "/proc/%d/smaps_rollup", pid);
    FILE *f = fopen(path, "r");
    if (!f) return -1;

    char *line = NULL;
    size_t len = 0;
    while (getline(&line, &len, f) != -1) {
        sscanf(line, "Rss: %lu kB", &proc->rss_kb);
        sscanf(line, "Pss: %lu kB", &proc->pss_kb);
        sscanf(line, "Private_Clean: %lu kB", &proc->priv_clean_kb);
        sscanf(line, "Private_Dirty: %lu kB", &proc->priv_dirty_kb);
        sscanf(line, "Shared_Clean: %lu kB", &proc->shared_clean_kb);
        sscanf(line, "Shared_Dirty: %lu kB", &proc->shared_dirty_kb);
        sscanf(line, "Swap: %lu kB", &proc->swap_kb);
        sscanf(line, "SwapPss: %lu kB", &proc->swap_pss_kb);
    }
    free(line);
    fclose(f);

    snprintf(path, sizeof(path), "/proc/%d/status", pid);
    f = fopen(path, "r");
    if (f) {
        line = NULL;
        len = 0;
        while (getline(&line, &len, f) != -1) {
            sscanf(line, "VmSize: %lu kB", &proc->vsz_kb);
        }
        free(line);
        fclose(f);
    }

    snprintf(path, sizeof(path), "/proc/%d/oom_score", pid);
    f = fopen(path, "r");
    if (f) {
        if (fscanf(f, "%d", &proc->oom_score) != 1) proc->oom_score = 0;
        fclose(f);
    }

    snprintf(path, sizeof(path), "/proc/%d/oom_score_adj", pid);
    f = fopen(path, "r");
    if (f) {
        if (fscanf(f, "%d", &proc->oom_score_adj) != 1) proc->oom_score_adj = 0;
        fclose(f);
    }
    return 0;
}

static void print_report(const SysMemInfo *sys, const ProcMemInfo *proc) {
    unsigned long uss_kb = proc->priv_clean_kb + proc->priv_dirty_kb;
    unsigned long shared_total_kb = proc->shared_clean_kb + proc->shared_dirty_kb;

    printf("===================================================================\n");
    printf("  ЗВЕДЕНИЙ ЗВІТ СПОЖИВАННЯ ПАМ'ЯТІ ДЛЯ PID %d\n", proc->pid);
    printf("===================================================================\n\n");

    printf("--- [1] СИСТЕМНИЙ КОНТЕКСТ (/proc/meminfo, PSI) ---\n");
    printf("  RAM Загалом:     %8lu МіБ | Вільна (Free):   %8lu МіБ\n",
           sys->mem_total_kb / 1024, sys->mem_free_kb / 1024);
    printf("  Доступна (Avail):%8lu МіБ | Брудна (Dirty):  %8lu МіБ\n",
           sys->mem_avail_kb / 1024, sys->dirty_kb / 1024);
    printf("  Slab (Reclaim):  %8lu МіБ | Тиск PSI (10с):  some=%.2f%% full=%.2f%%\n\n",
           sys->sreclaim_kb / 1024, sys->psi_some_avg10, sys->psi_full_avg10);

    printf("--- [2] СТАН АДРЕСНОГО ПРОСТОРУ ПРОЦЕСУ ---\n");
    printf("  VSZ (Віртуальний): %8lu МіБ  (повна довжина карти адрес VMA)\n", proc->vsz_kb / 1024);
    printf("  RSS (Резидентний): %8lu МіБ  (заселені сторінки в таблицях PTE)\n", proc->rss_kb / 1024);
    printf("  PSS (Пропорційний):%8lu МіБ  (чесна частка: USS + Shared / N)\n", proc->pss_kb / 1024);
    printf("  USS (Винятковий):  %8lu МіБ  (належить виключно цьому процесу)\n\n", uss_kb / 1024);

    printf("--- [3] РОЗКЛАДКА СТОРІНОК ЗА СТАТУСОМ ЗВІЛЬНЕННЯ ---\n");
    printf("  Приватні брудні (Private_Dirty): %8lu МіБ  [КУПА/СТЕК: вивільнення в RAM негайне]\n",
           proc->priv_dirty_kb / 1024);
    printf("  Приватні чисті  (Private_Clean): %8lu МіБ  [КОД/ФАЙЛИ: скидаються без запису]\n",
           proc->priv_clean_kb / 1024);
    printf("  Спільні сторінки (Shared Total): %8lu МіБ  [LIBC/SHMEM: спільні з іншими]\n",
           shared_total_kb / 1024);
    printf("  Витіснено в своп (Swap / SwapPSS):%7lu / %lu МіБ\n\n",
           proc->swap_kb / 1024, proc->swap_pss_kb / 1024);

    printf("--- [4] ОЦІНКА РИЗИКУ ТА ПОВЕДІНКИ OOM-KILLER ---\n");
    printf("  Поточний OOM Score:     %5d (бали ймовірності знищення: 0..1000)\n", proc->oom_score);
    printf("  Поправка OOM Score Adj: %5d (налаштування пріоритету: -1000..+1000)\n", proc->oom_score_adj);
    printf("  Реальний виграш від ліквідації: %lu МіБ фізичної RAM\n", proc->priv_dirty_kb / 1024);
    printf("===================================================================\n");
}

int main(int argc, char **argv) {
    if (argc < 2) {
        fprintf(stderr, "Використання: %s <PID>\n", argv[0]);
        return 1;
    }

    pid_t pid = (pid_t)atoi(argv[1]);
    if (pid <= 0) {
        fprintf(stderr, "Помилка: некоректний PID %s\n", argv[1]);
        return 1;
    }

    SysMemInfo sys;
    if (read_sys_mem(&sys) != 0) {
        perror("Помилка читання /proc/meminfo");
        return 1;
    }

    ProcMemInfo proc;
    if (read_proc_mem(pid, &proc) != 0) {
        fprintf(stderr, "Помилка читання даних для PID %d: %s\n", pid, strerror(errno));
        return 1;
    }

    print_report(&sys, &proc);
    return 0;
}
```

```cpp
#include <iostream>
#include <fstream>
#include <string>
#include <string_view>
#include <sstream>
#include <vector>
#include <iomanip>
#include <filesystem>
#include <system_error>

namespace fs = std::filesystem;

struct SysMemInfo {
    unsigned long mem_total_kb = 0;
    unsigned long mem_free_kb = 0;
    unsigned long mem_avail_kb = 0;
    unsigned long dirty_kb = 0;
    unsigned long sreclaim_kb = 0;
    double psi_some_avg10 = 0.0;
    double psi_full_avg10 = 0.0;
};

struct ProcMemInfo {
    pid_t pid = 0;
    unsigned long vsz_kb = 0;
    unsigned long rss_kb = 0;
    unsigned long pss_kb = 0;
    unsigned long priv_clean_kb = 0;
    unsigned long priv_dirty_kb = 0;
    unsigned long shared_clean_kb = 0;
    unsigned long shared_dirty_kb = 0;
    unsigned long swap_kb = 0;
    unsigned long swap_pss_kb = 0;
    int oom_score = 0;
    int oom_score_adj = 0;
};

class MemoryInspector {
public:
    static bool inspect(pid_t pid, SysMemInfo& sys, ProcMemInfo& proc) {
        if (!read_sys_mem(sys)) return false;
        if (!read_proc_mem(pid, proc)) return false;
        return true;
    }

    static void print_report(const SysMemInfo& sys, const ProcMemInfo& proc) {
        const unsigned long uss_kb = proc.priv_clean_kb + proc.priv_dirty_kb;
        const unsigned long shared_total_kb = proc.shared_clean_kb + proc.shared_dirty_kb;

        std::cout << "===================================================================\n";
        std::cout << "  ЗВЕДЕНИЙ ЗВІТ СПОЖИВАННЯ ПАМ'ЯТІ ДЛЯ PID " << proc.pid << "\n";
        std::cout << "===================================================================\n\n";

        std::cout << "--- [1] СИСТЕМНИЙ КОНТЕКСТ (/proc/meminfo, PSI) ---\n";
        std::cout << "  RAM Загалом:     " << std::setw(8) << (sys.mem_total_kb / 1024)
                  << " МіБ | Вільна (Free):   " << std::setw(8) << (sys.mem_free_kb / 1024) << " МіБ\n";
        std::cout << "  Доступна (Avail):" << std::setw(8) << (sys.mem_avail_kb / 1024)
                  << " МіБ | Брудна (Dirty):  " << std::setw(8) << (sys.dirty_kb / 1024) << " МіБ\n";
        std::cout << "  Slab (Reclaim):  " << std::setw(8) << (sys.sreclaim_kb / 1024)
                  << " МіБ | Тиск PSI (10с):  some=" << std::fixed << std::setprecision(2)
                  << sys.psi_some_avg10 << "% full=" << sys.psi_full_avg10 << "%\n\n";

        std::cout << "--- [2] СТАН АДРЕСНОГО ПРОСТОРУ ПРОЦЕСУ ---\n";
        std::cout << "  VSZ (Віртуальний): " << std::setw(8) << (proc.vsz_kb / 1024) << " МіБ  (довжина карти адрес VMA)\n";
        std::cout << "  RSS (Резидентний): " << std::setw(8) << (proc.rss_kb / 1024) << " МіБ  (заселені сторінки в PTE)\n";
        std::cout << "  PSS (Пропорційний):" << std::setw(8) << (proc.pss_kb / 1024) << " МіБ  (чесна частка: USS + Shared/N)\n";
        std::cout << "  USS (Винятковий):  " << std::setw(8) << (uss_kb / 1024) << " МіБ  (належить виключно процесу)\n\n";

        std::cout << "--- [3] РОЗКЛАДКА СТОРІНОК ЗА СТАТУСОМ ЗВІЛЬНЕННЯ ---\n";
        std::cout << "  Приватні брудні (Private_Dirty): " << std::setw(8) << (proc.priv_dirty_kb / 1024)
                  << " МіБ  [КУПА/СТЕК: вивільнення в RAM негайне]\n";
        std::cout << "  Приватні чисті  (Private_Clean): " << std::setw(8) << (proc.priv_clean_kb / 1024)
                  << " МіБ  [КОД/ФАЙЛИ: скидаються без запису]\n";
        std::cout << "  Спільні сторінки (Shared Total): " << std::setw(8) << (shared_total_kb / 1024)
                  << " МіБ  [LIBC/SHMEM: спільні з іншими]\n";
        std::cout << "  Витіснено в своп (Swap / SwapPSS):" << std::setw(7) << (proc.swap_kb / 1024)

        std::cout << "--- [4] ОЦІНКА РИЗИКУ ТА ПОВЕДІНКИ OOM-KILLER ---\n";
        std::cout << "  Поточний OOM Score:     " << std::setw(5) << proc.oom_score << " (бали ймовірності: 0..1000)\n";
        std::cout << "  Поправка OOM Score Adj: " << std::setw(5) << proc.oom_score_adj << " (пріоритет: -1000..+1000)\n";
        std::cout << "  Реальний виграш від ліквідації: " << (proc.priv_dirty_kb / 1024) << " МіБ фізичної RAM\n";
        std::cout << "===================================================================\n";
    }

private:
    static bool read_sys_mem(SysMemInfo& sys) {
        std::ifstream meminfo("/proc/meminfo");
        if (!meminfo.is_open()) return false;

        std::string line;
        while (std::getline(meminfo, line)) {
            parse_kb(line, "MemTotal:", sys.mem_total_kb);
            parse_kb(line, "MemFree:", sys.mem_free_kb);
            parse_kb(line, "MemAvailable:", sys.mem_avail_kb);
            parse_kb(line, "Dirty:", sys.dirty_kb);
            parse_kb(line, "SReclaimable:", sys.sreclaim_kb);
        }

        std::ifstream psi("/proc/pressure/memory");
        if (psi.is_open()) {
            std::string p_line;
            while (std::getline(psi, p_line)) {
                if (p_line.rfind("some", 0) == 0) {
                    parse_psi(p_line, sys.psi_some_avg10);
                } else if (p_line.rfind("full", 0) == 0) {
                    parse_psi(p_line, sys.psi_full_avg10);
                }
            }
        }
        return true;
    }

    static bool read_proc_mem(pid_t pid, ProcMemInfo& proc) {
        proc.pid = pid;
        const std::string proc_dir = "/proc/" + std::to_string(pid);

        std::ifstream smaps(proc_dir + "/smaps_rollup");
        if (!smaps.is_open()) return false;

        std::string line;
        while (std::getline(smaps, line)) {
            parse_kb(line, "Rss:", proc.rss_kb);
            parse_kb(line, "Pss:", proc.pss_kb);
            parse_kb(line, "Private_Clean:", proc.priv_clean_kb);
            parse_kb(line, "Private_Dirty:", proc.priv_dirty_kb);
            parse_kb(line, "Shared_Clean:", proc.shared_clean_kb);
            parse_kb(line, "Shared_Dirty:", proc.shared_dirty_kb);
            parse_kb(line, "Swap:", proc.swap_kb);
            parse_kb(line, "SwapPss:", proc.swap_pss_kb);
        }

        std::ifstream status(proc_dir + "/status");
        if (status.is_open()) {
            while (std::getline(status, line)) {
                parse_kb(line, "VmSize:", proc.vsz_kb);
            }
        }

        std::ifstream oom_score_file(proc_dir + "/oom_score");
        if (oom_score_file.is_open()) oom_score_file >> proc.oom_score;

        std::ifstream oom_adj_file(proc_dir + "/oom_score_adj");
        if (oom_adj_file.is_open()) oom_adj_file >> proc.oom_score_adj;

        return true;
    }

    static void parse_kb(const std::string& line, std::string_view key, unsigned long& value) {
        if (line.rfind(key, 0) == 0) {
            std::istringstream iss(line.substr(key.length()));
            iss >> value;
        }
    }

    static void parse_psi(const std::string& line, double& avg10) {
        auto pos = line.find("avg10=");
        if (pos != std::string::npos) {
            std::istringstream iss(line.substr(pos + 6));
            iss >> avg10;
        }
    }
};

int main(int argc, char* argv[]) {
    if (argc < 2) {
        std::cerr << "Використання: " << argv[0] << " <PID>\n";
        return 1;
    }

    const pid_t pid = std::stoi(argv[1]);
    if (pid <= 0) {
        std::cerr << "Помилка: некоректний PID\n";
        return 1;
    }

    SysMemInfo sys;
    ProcMemInfo proc;
    if (!MemoryInspector::inspect(pid, sys, proc)) {
        std::cerr << "Помилка читання метрик для PID " << pid << "\n";
        return 1;
    }

    MemoryInspector::print_report(sys, proc);
    return 0;
}
```

## Покроковий розбір коду та інваріантів

Розгляньмо, як саме програма взаємодіє з підсистемами ядра та забезпечує точність зібраних даних:

1. **Читання та нормалізація одиниць.** Файли `/proc/meminfo`, `/proc/<pid>/status` та `/proc/<pid>/smaps_rollup` використовують кібібайти як основну одиницю вимірювання (суфікс `kB`). Утиліта зберігає всі проміжні значення в кібібайтах (`unsigned long`), що гарантує відсутність переповнення на 32-бітних і 64-бітних цілочисельних типах, а форматований вивід здійснює в мібібайтах (`/ 1024`) для зручності читання людиною.
2. **Парсинг метрик PSI.** Інтерфейс `/proc/pressure/memory` надає рядки виду `some avg10=0.00 avg60=0.00 avg300=0.00 total=123456`. Наша функція виділяє підрядок `avg10=` і перетворює його на число з рухомою комою. Значення `some avg10` понад 10–25% або будь-яке ненульове значення `full avg10` відразу сигналізує про те, що поточні затримки програми спричинені саме очікуванням пам'яті.
3. **Обчислення виняткової пам'яті (USS).** Ядро не має окремого рядка `Uss:` у файлі `smaps_rollup`. Утиліта самостійно складає `Private_Clean` та `Private_Dirty`. Це єдино правильний спосіб розрахунку пам'яті, що належить процесу одноосібно.
4. **Оцінка ефекту примусового завершення.** Значення `Private_Dirty` є ключовим індикатором для SRE та системних адміністраторів. Якщо процес займає 10 ГіБ за показником RSS, але його `Private_Dirty` становить лише 500 МіБ (решта — спільний буферний пул або чистий код), вбивство цього процесу вивільнить лише 500 МіБ оперативної пам'яті, що навряд чи врятує сервер від загального виснаження пам'яті.

## Порівняльний аналіз ціни виклику

Важливим аспектом практичного застосування діагностичних інструментів є розуміння накладних витрат процесора під час зняття метрик. Ми провели вимірювання часу виконання системних викликів на типовому серверному процесорі x86_64 для процесу з адресним простором 8 ГіБ та 2500 окремими ділянками VMA:

- **`/proc/<pid>/statm` (час виконання ~0.8 мкс):** Найшвидший спосіб отримати приблизні цифри. Ядро просто читає значення полів `total_vm` та `rss` зі структури `mm_struct`, не заглядаючи в таблиці сторінок і не захоплюючи важких замків. Підходить для безперервного моніторингу раз на секунду.
- **`/proc/<pid>/status` (час виконання ~4.5 мкс):** Зчитування розширеного набору лічильників (`RssAnon`, `RssFile`, `RssShmem`). Витрати полягають лише у форматуванні тексту в буфер ядра.
- **`/proc/<pid>/smaps_rollup` (час виконання ~45–110 мкс):** Ядро захоплює `mmap_lock` процесу в режимі спільного читання та виконує швидкий ітеративний прохід по всіх таблицях PTE, підсумовуючи байти в лічильники на рівні ядра. Це приблизно в 50 разів дорожче за читання `statm`, проте абсолютно прийнятно для запуску кожні кілька секунд.
- **Повний `/proc/<pid>/smaps` (час виконання ~35–180 мс):** Ядро не лише обходить таблиці сторінок, але й генерує десятки тисяч рядків тексту для кожного діапазону пам'яті. Запуск повного `smaps` на високонавантажених процесах (наприклад, базах даних чи JVM) утримує блокування `mmap_lock`, що може викликати помітні мікропаузи в роботі цільового застосунку (зупинка потоків на сторінкових збоях та викликах алокатора).

Звідси випливає практичне правило: для регулярного моніторингу використовують `smaps_rollup`, а до повного `smaps` звертаються лише під час детального аналізу конкретних ділянок пам'яті в ході локалізації витоків.

### Сценарій 3: Багатопотоковий процес із великою кількістю стеків

- Розмір `VSZ` перевищує 30 ГіБ через резервування 8 МіБ віртуального стека на кожен створений потік (`pthread_create`).
- Проте значення `RSS` залишається на рівні 800 МіБ, оскільки кожен потік реально торкнувся лише кількох початкових 4-кілобайтних сторінок свого виділеного діапазону.
- Утиліта `meminspect` відразу розкриває цю різницю: колосальний `VSZ` не викликає тривоги, оскільки сума `Private_Dirty` відповідає реальним потребам пам'яті, а система не зазнає тиску PSI.

## Динамічне простеження: поєднання з perf та ftrace

Статичний звіт відображає поточний стан лічильників, проте для встановлення першопричини сплесків споживання пам'яті його часто комбінують із динамічним трасуванням сторінкових збоїв.

Коли процес звертається до невідображеної пам'яті, апаратний блок MMU генерує виняток, який перехоплює обробник ядра `do_page_fault()`. Утиліта `perf` дозволяє відстежувати інтенсивність цих подій у реальному часі:

```sh
# Перехоплення мажорних (дискових) сторінкових збоїв для конкретного процесу
$ perf trace -e major-faults -p 8080

# Підрахунок кількості викликів прямого відбору сторінок по всій системі
$ perf stat -e vmscan:mm_vmscan_direct_reclaim_begin -a sleep 5
```

Якщо запуск нашої утиліти фіксує зростання тиску PSI (`some > 10%`), а `perf` одночасно реєструє тисячі подій `mm_vmscan_direct_reclaim_begin`, це однозначно доводить: потоки застосунку зупиняються не через очікування бази даних чи мережі, а тому, що вони змушені власноруч витісняти пам'ять ядра перед виконанням кожного нового виклику `malloc()`.

## Чому не варто використовувати `drop_caches` для діагностики

Поширеною помилкою серед початківців є спроба «очистити пам'ять» перед зняттям метрик за допомогою запису числа `3` у псевдофайл `/proc/sys/vm/drop_caches`. Необхідно чітко розуміти наслідки цієї операції:

1. **Вплив на кеші:** Запис у `drop_caches` змушує ядро примусово звільнити всі чисті сторінки файлового кешу (`Cached`), а також придатні до вивільнення об'єкти `dentry` та `inode` зі Slab. Анонімна пам'ять процесів (`Private_Dirty`, купа, стек) при цьому не звільняється взагалі.
2. **Удар по продуктивності:** Очищення кешу призводить до того, що під час наступних звернень до коду системних бібліотек, виконуваних бінарників та файлів конфігурації система змушена виконувати тисячі мажорних сторінкових збоїв з реальними зчитуваннями з повільних накопичувачів.
3. **Спотворення діагностики:** Скидання кешу штучно збільшує час виконання процесів та створює фальшиві сплески метрик PSI, які не мають жодного стосунку до реального робочого навантаження. Для коректного тестування поведінки застосунку в умовах обмеженої пам'яті слід використовувати контрольні групи cgroups v2 із встановленням лімітів `memory.high` та `memory.max`, а не глобальне очищення кешу ядра.

## Крайові випадки та тонкощі ядра

Під час регулярного використання подібних діагностичних інструментів слід враховувати кілька специфічних механізмів підсистеми віртуальної пам'яті Linux:

1. **Прозорі великі сторінки (THP):** Якщо в системі увімкнено THP, алокатор виділяє анонімну пам'ять блоками по 2 МіБ (512 звичайних сторінок). У `smaps_rollup` ця пам'ять обліковується в полі `AnonHugePages`. З точки зору PSS та USS вона рахується точно так само, але один промах повз таку сторінку коштує виділення одразу двох мегабайтів фізичної пам'яті.
2. **Сторінки, скинуті через `MADV_FREE`:** Коли сучасні алокатори (наприклад, jemalloc або Go runtime) позначають пам'ять прапорцем `MADV_FREE`, ядро не забирає кадри негайно, а лише скидає біт брудності й позначає їх як `LazyFree`. У `smaps_rollup` вони продовжують входити до RSS, але в разі дефіциту ядро вивільняє їх без жодного дискового вводу-виводу.
3. **Злиття дублікатів (KSM — Kernel Samepage Merging):** Якщо в системі працює демон KSM (типово для серверів віртуалізації KVM), однакові сторінки пам'яті різних процесів зливаються в один спільний фізичний кадр, позначений для копіювання при записі. У результаті показник `mapcount` такого кадру зростає, а PSS кожного процесу відповідно падає. Це законний ефект дедуплікації, який чесно показує еволюцію споживання пам'яті.
4. **Обмеження безпеки Yama ptrace:** Для читання `/proc/<pid>/smaps_rollup` процесу, запущеного від імені іншого користувача, викликаюча програма повинна мати привілеї `CAP_SYS_PTRACE` або запускатися від імені `root`. Якщо в системі активовано модуль безпеки Yama (`/proc/sys/kernel/yama/ptrace_scope = 1`), навіть утиліти одного й того самого користувача не зможуть інспектувати пам'ять процесів, якщо між ними немає відношення «батько-нащадок».

## Специфіка діагностики в контейнерах і середовищах із zram

Під час запуску діагностичних інструментів усередині контейнерів (Docker, LXC, Kubernetes) або на системах зі стисненим свопом у RAM (`zram`) виникають додаткові фактори, які необхідно враховувати під час інтерпретації звіту:

1. **Ізоляція просторів імен PID.** Якщо утиліта запускається всередині контейнера, її каталог `/proc` показує процеси з локальною нумерацією PID (де головний процес має `PID 1`). Проте файли `/proc/meminfo` та `/proc/pressure/memory` за замовчуванням залишаються **глобальними для всієї хост-системи** (якщо не використовується віртуалізація procfs, наприклад `lxcfs`). Тому високий тиск PSI або великий обсяг зайнятої пам'яті в розділі `[1]` звіту може бути наслідком навантаження на сусідні контейнери хоста, а не на досліджуваний процес.
2. **Стиснений своп zram / zswap.** Якщо системою використовується `zram`, вивантажені анонімні сторінки не записуються на повільний фізичний накопичувач, а стискаються алгоритмами `lzo-rle` чи `zstd` і залишаються в оперативній пам'яті. У цьому разі наявність великого значення `Swap` у розділі `[3]` звіту є значно менш шкідливою для продуктивності: повернення сторінки зі `zram` коштує лише 2–5 мікросекунд на декомпресію процесором проти 100–500 мікросекунд для NVMe-накопичувача або десятків мілісекунд для механічного HDD. Проте навіть стиснений своп витрачає фізичні кадри RAM під стиснені дані, тому необмежене зростання `Swap` зрештою призведе до загального виснаження пам'яті.
3. **Обмеження за cgroups.** Для контейнерних процесів вирішальне значення має не глобальний `MemAvailable`, а залишок до стелі `memory.max` конкретної контрольної групи. Якщо `memory.max` встановлено на рівні 2 ГіБ, а `memory.current` досягає 1.95 ГіБ, ядро почне локальний відбір сторінок та ініціює OOM-killer усередині групи, навіть якщо хост-машина має сотні гігабайтів вільної фізичної пам'яті.

## Методологія інтеграції в автоматизований моніторинг

Створена утиліта демонструє логіку, яку варто переносити у виробничі системи збору метрик (Prometheus Node Exporter, Telegraf, Datadog Agent):

- **Алертинг за реальними втратами:** Замість наївного правила `node_memory_MemFree_bytes / node_memory_MemTotal_bytes < 0.1` надійний моніторинг будують на формулі `node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes < 0.05` у поєднанні з перевіркою `rate(node_pressure_memory_some_total_slice[1m]) > 0.25`.
- **Детекція витоків:** Справжній витік пам'яті в конкретному сервісі визначають за монотонним зростанням лічильника `Private_Dirty` (або `memory.current - memory.stat.file` у cgroups v2), а не за коливаннями `RSS`, який може тимчасово зростати через активне читання файлів спільними бібліотеками.
