# 📋 Довідник системних інтерфейсів контролю привілеїв: prctl, capabilities, seccomp

Цей довідник містить повний опис низькорівневих системних інтерфейсів ядра Linux, призначених для зменшення поверхні атаки процесу та примусового обмеження його повноважень. Тут зібрано точні сигнатури викликів, внутрішні структури даних ядра, правила модифікації масок ідентичності (UID/GID), механізм збереження та перерахунку capabilities, синтаксис інструкцій віртуальної машини Seccomp-BPF, новітній інтерфейс пісочниць Landlock LSM, протокол міжпроцесної передачі дескрипторів `SCM_RIGHTS`, синтаксис профілів AppArmor та SELinux, а також параметри ізоляції служб у підсистемі `systemd`.

## 1. Системні виклики зміни креденшелів (UID / GID / Groups)

У ядрі Linux кожен процес описується структурою `task_struct`, яка містить вказівники на структури облікових даних `struct cred` (`real_cred` — об'єктивні права процесу та `cred` — суб'єктивні права, що застосовуються під час виконання конкретної операції). Усі операції зміни ідентифікаторів створюють новий екземпляр `struct cred` через механізм копіювання при записі (*copy-on-write*) та атомарно замінюють вказівник у дескрипторі задачі за допомогою внутрішньої функції `commit_creds()`.

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <grp.h>
#include <sys/types.h>

int setresuid(uid_t ruid, uid_t euid, uid_t suid);
int setresgid(gid_t rgid, gid_t egid, gid_t sgid);
int setgroups(size_t size, const gid_t *list);
int initgroups(const char *user, gid_t group);
```

### 1.1. Семантика та інваріанти `setresuid()` і `setresgid()`

Системні виклики `setresuid()` та `setresgid()` дозволяють процесу явно й незалежно встановити реальний (*Real*), ефективний (*Effective*) та збережений (*Saved*) ідентифікатори користувача чи групи. Значення `(uid_t)-1` або `(gid_t)-1` наказує ядру зберегти поточне значення відповідного поля без змін.

| Ідентифікатор | Роль у перевірках ядра | Правила зміни для непривілейованого процесу |
| :--- | :--- | :--- |
| **Real UID / GID (`ruid`, `rgid`)** | Визначає власника процесу в системі. Використовується ядром для перевірки прав на надсилання сигналів через `kill()`, керування пріоритетами планувальника через `setpriority()` та обліку лімітів ресурсів `RLIMIT_NPROC`. | Непривілейований процес може змінити `ruid` виключно на поточне значення свого `ruid`, `euid` або `suid`. |
| **Effective UID / GID (`euid`, `egid`)** | Визначає поточні права процесу при взаємодії з VFS. Використовується підсистемами ядра для перевірки доступу до файлів, сокетів, каталогів, IPC-об'єктів та перевірки наявності capabilities. | Непривілейований процес може встановити `euid` лише рівним поточному `ruid`, `euid` або `suid`. |
| **Saved UID / GID (`suid`, `sgid`)** | Зберігає попередній стан прав при запуску програм із бітами `setuid`/`setgid`. Дозволяє тимчасово перемикатися між привілейованим і непривілейованим режимами. | Непривілейований процес може встановити `suid` лише рівним поточному `ruid`, `euid` або `suid`. |

#### Інваріант безпечного незворотного скидання привілеїв:
Для гарантованого та безповоротного скидання привілеїв суперкористувача процес зобов'язаний встановити однаковий цільовий непривілейований ідентифікатор у всі три позиції:

:::tabs
```c
uid_t target_uid = 65534; /* nobody */
if (setresuid(target_uid, target_uid, target_uid) != 0) {
    /* Фатальна помилка: процес зобов'язаний негайно припинити виконання */
    perror("FATAL: setresuid failed");
    abort();
}
```
```cpp
constexpr uid_t target_uid = 65534; // nobody
if (::setresuid(target_uid, target_uid, target_uid) != 0) {
    throw std::system_error(errno, std::generic_category(), "FATAL: setresuid failed");
}
```
:::

Якщо програма викликає застарілу функцію `seteuid(target_uid)`, ядро змінює лише `euid`, залишаючи збережений `suid = 0`. Якщо у процесі виникне вразливість переповнення буфера або зловмисник зможе виконати довільний код через ROP-ланцюжок, він зможе викликати `setresuid(-1, 0, -1)` і миттєво відновити повні права `root`.

### 1.2. Очищення та ініціалізація додаткових груп (`setgroups`, `initgroups`)

Додаткові групи процесу зберігаються в динамічному масиві `struct group_info`. Навіть якщо процес успішно змінив свій основний UID та GID на непривілейовані, він продовжує володіти всіма додатковими групами, успадкованими від батьківського процесу (наприклад, групами з привілейованим доступом `wheel`, `sudo`, `docker`, `disk` або `adm`).

:::tabs
```c
/* 1. Повне очищення списку додаткових груп */
if (setgroups(0, NULL) != 0) {
    perror("FATAL: setgroups(0, NULL) failed");
    abort();
}

/* 2. АБО завантаження груп виділеного облікового запису з бази /etc/group */
if (initgroups("daemon_user", target_gid) != 0) {
    perror("FATAL: initgroups failed");
    abort();
}
```
```cpp
// 1. Повне очищення списку додаткових груп
if (::setgroups(0, nullptr) != 0) {
    throw std::system_error(errno, std::generic_category(), "FATAL: setgroups failed");
}

// 2. АБО завантаження груп користувача
if (::initgroups("daemon_user", target_gid) != 0) {
    throw std::system_error(errno, std::generic_category(), "FATAL: initgroups failed");
}
```
:::

#### Критичне правило черговості викликів:
Виклики `setgroups()` та `initgroups()` вимагають наявності привілею `CAP_SETGID` або нульового ефективного ідентифікатора (`euid == 0`). Якщо розробник спочатку викличе `setresuid()`, процес миттєво втратить право змінювати членство в групах. Наступний виклик `setgroups()` зазнає невдачі з помилкою `EPERM`, і процес залишиться працювати від непривілейованого користувача, але зі збереженими привілейованими групами адміністратора.

#### Таблиця кодів помилок для системних викликів креденшелів:

| Код помилки | Системні виклики | Причина виникнення в ядрі |
| :--- | :--- | :--- |
| `EPERM` | `setresuid`, `setresgid`, `setgroups` | Процес не має необхідного привілею `CAP_SETUID` або `CAP_SETGID` у своєму просторі користувача і намагається встановити ідентифікатор, відмінний від поточних значень `ruid`, `euid` чи `suid`. |
| `EINVAL` | `setgroups` | Значення параметра `size` перевищує системне обмеження ядра `NGROUPS_MAX` (за замовчуванням 65536 записів у Linux). |
| `EFAULT` | `setresuid`, `setgroups` | Вказівник на масив ідентифікаторів груп `list` або параметри виклику вказують на недійсну чи недоступну область пам'яті. |

## 2. Системний виклик `prctl()`: операції маніпуляції безпекою

Системний виклик `prctl()` (англ. *process control*) є основним інтерфейсом ядра Linux для тонкого налаштування характеристик та прапорців безпеки поточного потоку або процесу.

```c
#include <sys/prctl.h>

int prctl(int option, unsigned long arg2, unsigned long arg3,
          unsigned long arg4, unsigned long arg5);
```

### 2.1. Реєстр операцій безпеки `prctl`

| Опція (`option`) | Константи аргументів | Дія на рівні ядра та наслідки для процесу |
| :--- | :--- | :--- |
| `PR_SET_NO_NEW_PRIVS` | `arg2 = 1`, `arg3..5 = 0` | Встановлює прапорець `no_new_privs` у `task_struct`. Ця дія є **незворотною** для поточного процесу та всіх його майбутніх нащадків. Ядро блокує будь-яке підвищення привілеїв під час системного виклику `execve()`, ігноруючи файлові біти `setuid`/`setgid` та розширені атрибути capabilities (`security.capability`). Встановлення цього прапорця є обов'язковою вимогою ядра для завантаження фільтрів Seccomp-BPF непривілейованим процесом. |
| `PR_GET_NO_NEW_PRIVS` | `arg2..5 = 0` | Повертає `1`, якщо прапорець `no_new_privs` встановлено, або `0`, якщо процес може підвищувати привілеї через `execve()`. |
| `PR_SET_KEEPCAPS` | `arg2 = 1` або `0` | Встановлює стан прапорця `keep_capabilities`. За замовчуванням ядро Linux автоматично обнуляє маски Permitted та Effective capabilities при переході `euid` з `0` на ненульове значення. Встановлення `PR_SET_KEEPCAPS` у `1` змушує ядро зберегти набір Permitted capabilities після скидання UID. |
| `PR_GET_KEEPCAPS` | `arg2..5 = 0` | Повертає поточне значення прапорця `keep_capabilities` (`1` або `0`). |
| `PR_CAP_AMBIENT` | `arg2 = PR_CAP_AMBIENT_RAISE`<br>`arg2 = PR_CAP_AMBIENT_LOWER`<br>`arg2 = PR_CAP_AMBIENT_CLEAR_ALL`<br>`arg2 = PR_CAP_AMBIENT_IS_SET` | Керує набором *Ambient Capabilities* (введено в Linux 4.3). Дозволяє непривілейованому процесу підняти конкретний дозвіл (`arg3 = CAP_*`), який автоматично передається дочірнім процесам крізь `execve()` без потреби наявності суперкористувача чи файлових атрибутів `setcap`. |
| `PR_SET_DUMPABLE` | `arg2 = SUID_DUMP_DISABLE (0)`<br>`arg2 = SUID_DUMP_USER (1)` | Забороняє генерацію дампу пам'яті (*core dump*) та блокує підключення налагоджувачів через `ptrace` іншими процесами того ж користувача. Значення `0` блокує читання пам'яті процесу через вузол `/proc/[pid]/mem`, захищаючи збережені в пам'яті криптографічні ключі та конфіденційні сесії. |
| `PR_SET_CHILD_SUBREAPER` | `arg2 = 1` або `0` | Оголошує поточний процес локальним суб-ріпером (*subreaper*). Якщо дочірні процеси-воркери створюють власні нащадки й раптово завершують роботу, процеси-сироти перепідпорядковуються цьому процесу, а не системному `PID 1`. |

#### Коди помилок системного виклику `prctl`:

* `EINVAL`: Невідома опція `option`, або передано некоректне значення додаткових аргументів (наприклад, спроба передати прапорець `PR_SET_NO_NEW_PRIVS` зі значенням, відмінним від `1`).
* `EPERM`: Спроба підняти ambient capability, якого немає в поточному наборі Permitted, або спроба маніпуляції capabilities за наявності активного прапорця `PR_SET_NO_NEW_PRIVS` без відповідних прав.

## 3. Модель Linux Capabilities та бінарний інтерфейс

Підсистема Linux Capabilities замінює бінарну модель всемогутнього користувача `root` на набір із 41 атомарного дозволу (станом на сучасні версії ядра Linux). Контекст безпеки процесу включає п'ять 64-бітних бітових векторів.

### 3.1. П'ять наборів Capabilities процесу

```
+-------------------------------------------------------------------+
|                        task_struct->cred                          |
|                                                                   |
|   Permitted (pP)    : Максимальний резерв дозволених прав        |
|   Effective (pE)    : Права, що перевіряються під час виклику     |
|   Inheritable (pI)  : Права, які можна передати через execve()    |
|   Bounding (pB)     : Верхня абсолютна межа доступних прав       |
|   Ambient (pA)      : Автоматично успадковані права для non-root  |
+-------------------------------------------------------------------+
```

1. **Permitted (`pP`):** Абсолютний пул привілеїв, які процес має право ввімкнути у свій робочий набір `pE` або передати в набір `pA`.
2. **Effective (`pE`):** Набір привілеїв, які ядро безпосередньо перевіряє в момент виконання кожного чутливого системного виклику.
3. **Inheritable (`pI`):** Маска привілеїв, які можуть бути успадковані новою програмою під час виконання `execve()`, якщо відповідний бінарний файл має встановлені файлові атрибути `fI`.
4. **Bounding Set (`pB`):** Глобальний обмежувач процесу. Жоден процес не може отримати привілей у свій `pP`, якщо цей привілей відсутній у його `pB` (навіть якщо програма запускається під `root` або має встановлені файлові capabilities).
5. **Ambient Set (`pA`):** Набір привілеїв, які автоматично зберігаються в `pP` та `pE` при виклику `execve()` звичайного непривілейованого бінарного файлу без файлових розширених атрибутів.

#### Математична модель перерахунку capabilities при виконанні `execve()`:
```
pP' = (pI & fI) | (fP & pB) | pA'
pE' = (fE ? pP' : pA')
pI' = pI
pA' = (no_new_privs || root) ? 0 : (pA & pI & pP)
```
*де `fP`, `fI`, `fE` — це Permitted, Inheritable та Effective маски, зчитані з файлового атрибута `security.capability` бінарного файлу.*

### 3.2. Таблиця критичних констант Capabilities

| Константа | Номер біта | Опис дозволених дій та системних викликів |
| :--- | :--- | :--- |
| `CAP_NET_BIND_SERVICE` | `10` | Дозволяє прив'язку мережевих сокетів інтернет-домену (AF_INET, AF_INET6) до привілейованих портів з номерами менше `1024` через виклик `bind()`. |
| `CAP_NET_ADMIN` | `12` | Дозволяє конфігурацію мережевих інтерфейсів, маніпуляцію таблицями маршрутизації, додавання правил міжмережевого екрана (iptables/nftables), налаштування параметрів TOS/QoS та створення тунелів. |
| `CAP_NET_RAW` | `13` | Дозволяє відкриття сирих сокетів типу `SOCK_RAW` та `SOCK_PACKET`, маніпуляцію заголовками пакетів та надсилання довільного ICMP/IGMP трафіку. |

| `CAP_SYS_PTRACE` | `19` | Дозволяє трасування довільних процесів за допомогою `ptrace()`, а також читання й запис адресного простору інших процесів через `/proc/[pid]/mem`. |
| `CAP_SYS_ADMIN` | `21` | Перевантажений суперпривілей («фактичний еквівалент root»): монтування файлових систем (`mount`, `umount`), конфігурація просторів імен (`clone`, `unshare`), завантаження eBPF-програм, виклик `quotactl()`. |
| `CAP_DAC_OVERRIDE` | `1` | Повний обхід усіх перевірок дозволів читання, запису та виконання файлів у VFS. |
| `CAP_DAC_READ_SEARCH` | `2` | Обхід перевірок прав на читання файлів та прав на виконання каталогів (пошук файлів усередині дерева VFS). |
| `CAP_SETUID` | `7` | Довільна зміна UID процесу та підробка облікових даних при передачі через Unix Domain сокети. |
| `CAP_SETGID` | `6` | Довільна зміна GID процесу та маніпуляція масивом додаткових груп. |
| `CAP_SETPCAP` | `8` | Зміна набору Bounding Set та маніпуляція прапорцями Ambient capabilities. |
| `CAP_KILL` | `5` | Обхід перевірок прав при надсиланні сигналів процесам інших користувачів через виклик `kill()`. |
| `CAP_CHOWN` | `0` | Довільна зміна власника та групи файлів і каталогів (`chown()`, `fchownat()`). |
| `CAP_SYS_CHROOT` | `18` | Дозвіл на використання системного виклику зміни кореневого каталогу `chroot()`. |

## 4. Системний виклик `seccomp()` та віртуальна машина cBPF

Системний виклик `seccomp()` підключає програми на базі класичного Berkeley Packet Filter (cBPF) до шлюзу системних викликів ядра Linux. Фільтр виконується для кожного системного виклику перед його безпосередньою передачею до обробника підсистеми ядра.

```c
#include <linux/seccomp.h>
#include <linux/filter.h>
#include <linux/audit.h>
#include <sys/syscall.h>
#include <unistd.h>

int seccomp(unsigned int operation, unsigned int flags, void *args);
```

### 4.1. Специфікація структури вхідного контексту `seccomp_data`

Перед виконанням першої інструкції BPF-програми ядро формує структуру `struct seccomp_data`, заповнюючи її інформацією про поточний системний виклик:

```c
struct seccomp_data {
    int   nr;                    /* Номер системного виклику (константи __NR_*) */
    __u32 arch;                  /* Архітектура процесора (константи AUDIT_ARCH_*) */
    __u64 instruction_pointer;   /* Адреса інструкції CPU, яка виконала виклик */
    __u64 args[6];               /* Шість 64-бітних аргументів системного виклику */
};
```

### 4.2. Таблиця дій повернення фільтра (`SECCOMP_RET_*`)

Фільтр BPF повертає 32-бітне значення. Старші 16 біт визначають дію ядра, а молодші 16 біт несуть додаткові дані (наприклад, номер помилки `errno`):

| Константа дії | Шістнадцятковий код | Поведінка ядра Linux |
| :--- | :--- | :--- |
| `SECCOMP_RET_KILL_PROCESS` | `0x80000000U` | Ядро негайно знищує весь процес разом із усіма потоками. Сигнали не надсилаються, дампи пам'яті можуть не створюватися. |
| `SECCOMP_RET_KILL_THREAD` | `0x00000000U` | Ядро аварійно завершує лише той потік виконання, який ініціював заборонений виклик. |
| `SECCOMP_RET_TRAP` | `0x00030000U` | Ядро блокує виклик та надсилає потоку сигнал `SIGSYS`. Структура `siginfo_t` містить номер виклику, архітектуру та адресу інструкції CPU. |
| `SECCOMP_RET_ERRNO` | `0x00050000U` | Системний виклик **блокується** без виконання. Ядро повертає процесу значення помилки, вказане в молодших 16 бітах (наприклад, `SECCOMP_RET_ERRNO | (EPERM & 0xFFFF)`). |
| `SECCOMP_RET_USER_NOTIF` | `0x7fc00000U` | Системний виклик зупиняється, а його виконання делегується зовнішньому процесу-супервізору через спеціальний дескриптор `seccomp_unotify`. |
| `SECCOMP_RET_LOG` | `0x7ffc0000U` | Системний виклик виконується безперешкодно, але факт його виклику обов'язково записується в журнал системного аудиту. |
| `SECCOMP_RET_ALLOW` | `0x7fff0000U` | Системний виклик виконується ядром у звичайному штатному режимі. |

#### Важливість прапорця `SECCOMP_FILTER_FLAG_TSYNC`:
Якщо процес має кілька активних потоків виконання (*pthreads*), виклик `seccomp()` без додаткових прапорців застосовує BPF-фільтр лише до поточного потоку. Встановлення прапорця `SECCOMP_FILTER_FLAG_TSYNC` синхронізує та примусово встановлює даний фільтр на всі наявні потоки процесу. Якщо хоча б один потік не може прийняти фільтр (наприклад, має конфліктний фільтр вищого рівня), виклик завершується з помилкою, і жоден потік не змінює свій стан.

## 5. Обмеження доступу до файлової системи через Landlock LSM

Landlock (введено в ядро Linux 5.13) — це підсистема мандатного контролю доступу (LSM), яка дозволяє непривілейованому процесу динамічно створювати власні правила обмеження доступу до VFS без потреби прав суперкористувача.

```c
#include <linux/landlock.h>
#include <sys/prctl.h>
#include <sys/syscall.h>

int landlock_create_ruleset(const struct landlock_ruleset_attr *attr,
                            size_t size, __u32 flags);
int landlock_add_rule(int ruleset_fd, enum landlock_rule_type rule_type,
                      const void *rule_attr, __u32 flags);
int landlock_restrict_self(int ruleset_fd, __u32 flags);
```

### 5.1. Прапорці прав доступу до файлової системи (`handled_access_fs`)

| Прапорець Landlock | Дозволена операція над файлом чи каталогом |
| :--- | :--- |
| `LANDLOCK_ACCESS_FS_EXECUTE` | Дозвіл на запуск файлу як виконуваної програми (`execve()`). |
| `LANDLOCK_ACCESS_FS_WRITE_FILE` | Дозвіл на відкриття файлу для запису або перезапису (`O_WRONLY`, `O_RDWR`, `truncate`). |
| `LANDLOCK_ACCESS_FS_READ_FILE` | Дозвіл на читання вмісту файлу (`O_RDONLY`, `O_RDWR`). |
| `LANDLOCK_ACCESS_FS_READ_DIR` | Дозвіл на отримання списку файлів усередині каталогу (`getdents64()`, `opendir()`). |
| `LANDLOCK_ACCESS_FS_REMOVE_DIR` | Дозвіл на видалення порожнього каталогу (`rmdir()`, `unlinkat()`). |
| `LANDLOCK_ACCESS_FS_REMOVE_FILE` | Дозвіл на видалення звичайного файлу чи символьного посилання (`unlink()`, `unlinkat()`). |
| `LANDLOCK_ACCESS_FS_MAKE_CHAR` | Дозвіл на створення спеціального файлу символьного пристрою (`mknod()`). |
| `LANDLOCK_ACCESS_FS_MAKE_DIR` | Дозвіл на створення нового підкаталогу (`mkdir()`). |

| `LANDLOCK_ACCESS_FS_TRUNCATE` | Дозвіл на зміну розміру файлу (`truncate()`, `ftruncate()`, `open()` з `O_TRUNC`). |

## 6. Протокол передачі дескрипторів між процесами (`SCM_RIGHTS`)

У моделі розподілу привілеїв (*Privilege Separation*) привілейований процес відкриває захищений ресурс (наприклад, файл приватного ключа сертифіката або мережевий сокет порту 80) і передає відкритий файловий дескриптор непривілейованому воркеру через локальний Unix Domain сокет (`AF_UNIX`).

```c
#include <sys/socket.h>
#include <sys/un.h>

struct msghdr {
    void         *msg_name;       /* Адреса сокета (NULL для підключених потокових сокетів) */
    socklen_t     msg_namelen;    /* Розмір адреси */
    struct iovec *msg_iov;        /* Масив буферів корисних даних */
    size_t        msg_iovlen;     /* Кількість буферів у масиві msg_iov */
    void         *msg_control;    /* Буфер допоміжних службових повідомлень */
    size_t        msg_controllen; /* Розмір буфера msg_control */
    int           msg_flags;      /* Прапорці отриманого повідомлення */
};

struct cmsghdr {
    size_t cmsg_len;   /* Розмір службового блоку разом із заголовком */
    int    cmsg_level; /* SOL_SOCKET */
    int    cmsg_type;  /* SCM_RIGHTS */
    /* unsigned char cmsg_data[] — масив дескрипторів слідує безпосередньо за структурою */
};
```

### 6.1. Макроси маніпуляції допоміжними даними `cmsghdr`

```c
/* Повертає вказівник на перший заголовок cmsghdr у структурі msghdr */
struct cmsghdr *CMSG_FIRSTHDR(struct msghdr *msgh);

/* Повертає вказівник на наступний cmsghdr або NULL, якщо досягнуто кінця буфера */
struct cmsghdr *CMSG_NXTHDR(struct msghdr *msgh, struct cmsghdr *cmsg);

/* Повертає вказівник на перший байт корисних даних дескрипторів */
unsigned char *CMSG_DATA(struct cmsghdr *cmsg);

/* Обчислює сумарний розмір буфера з урахуванням вирівнювання пам'яті ядра */
size_t CMSG_SPACE(size_t length);
size_t CMSG_LEN(size_t length);
```

#### Механізм дублювання дескрипторів у ядрі:
Під час виклику `sendmsg()` ядро перевіряє переданий дескриптор у таблиці дескрипторів відправника, збільшує лічильник посилань на відповідну структуру `struct file` у VFS і розміщує посилання у черзі сокета. Коли процес-отримувач виконує виклик `recvmsg()`, ядро виділяє новий найменший вільний номер дескриптора в таблиці отримувача та прив'язує його до тієї самої структури `struct file`. Номери дескрипторів у відправника та отримувача можуть відрізнятися (наприклад, дескриптор `3` у майстра може стати дескриптором `7` у воркера), але вони вказують на один і той самий відкритий файл або сокет.

## 7. Синтаксис політик мандатного контролю (AppArmor та SELinux)

Мандатний контроль доступу (MAC) діє на рівні LSM-хуків ядра і перевіряє дозволи навіть у тому випадку, якщо класична модель дискреційного доступу (DAC) та перевірки capabilities дали згоду на виконання операції.

### 7.1. Профілі AppArmor: конфігурація шляхів та дозволів

Профілі AppArmor оперують шляхами файлової системи та зв'язуються з виконуваними файлами:

```apparmor
# Профіль для веб-демона /usr/sbin/mydaemon
#include <tunables/global>

/usr/sbin/mydaemon {
  #include <abstractions/base>
  #include <abstractions/nameservice>

  # Дозволені можливості (Capabilities)
  capability net_bind_service,
  capability setuid,
  capability setgid,

  # Доступ до файлів конфігурації (тільки читання)
  /etc/mydaemon/** r,
  /etc/ssl/certs/** r,

  # Доступ до каталогів даних та веб-кореня
  /var/www/html/** r,
  /var/log/mydaemon/*.log w,
  /run/mydaemon/mydaemon.pid rw,

  # Заборона виконання командних оболонок та бінарників
  deny /bin/** x,
  deny /usr/bin/** x,
  deny /tmp/** rwklx,
}
```

Прапорці доступу AppArmor:
* `r`: читання файлу (*read*).
* `w`: запис або зміна вмісту файлу (*write*).
* `a`: дописування в кінець файлу (*append*).
* `l`: створення жорстких посилань (*link*).
* `k`: блокування файлу через `fcntl` (*file locking*).
* `x`: виконання файлу (*execute*).
* `ix`: успадковане виконання в тому самому профілі (*inherit execute*).
* `px`: перехід у спеціальний профіль виконання (*profile execute*).

### 7.2. Правила SELinux Type Enforcement (TE)

SELinux маркує кожен об'єкт системи (процеси, файли, сокети, порти) контекстом безпеки у форматі `користувач:роль:тип:рівень` (наприклад, `system_u:system_r:httpd_t:s0`). Правила безпеки визначають дозволені взаємодії між типами:

```selinux
# Дозвіл типу процесу httpd_t зв'язуватися з мережевим портом типу http_port_t
allow httpd_t http_port_t:tcp_socket name_bind;

# Дозвіл читання файлів з міткою httpd_sys_content_t
allow httpd_t httpd_sys_content_t:file { read getattr open };
allow httpd_t httpd_sys_content_t:dir { read search open getattr };

# Дозвіл запису в лог-файли з міткою httpd_log_t
allow httpd_t httpd_log_t:file { create open append getattr write };
allow httpd_t httpd_log_t:dir { write add_name search };

# Заборона переходу в домен командної оболонки shell_exec_t
# (відсутність правила allow автоматично блокує операцію)
```

## 8. Декларативні параметри безпеки служб у `systemd`

Підсистема ініціалізації `systemd` дозволяє налаштовувати багаторівневу пісочницю безпосередньо в юніт-файлі служби (`.service`), автоматично викликаючи відповідні системні виклики перед запуском бінарного файлу демона.

```ini
[Unit]
Description=Isolated High-Security Network Service
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/mydaemon

# 1. Ідентичність та скидання привілеїв
User=daemon_user
Group=daemon_group
SupplementaryGroups=

# 2. Обмеження Capabilities
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE

# 3. Блокування підвищення прав та Seccomp
NoNewPrivileges=yes
SystemCallArchitectures=native
SystemCallFilter=@system-service @network-io
SystemCallFilter=~@privileged @resources @mount @reboot @swap @debug

# 4. Ізоляція файлової системи VFS
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
ReadWritePaths=/var/log/mydaemon /run/mydaemon

# 5. Захист пам'яті та мережевих протоколів
MemoryDenyWriteExecute=yes
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
RestrictRealtime=yes
LockPersonality=yes

[Install]
WantedBy=multi-user.target
```

### 8.1. Аудит безпеки служби утилітою `systemd-analyze`

Утиліта `systemd-analyze security` виконує статичний аналіз налаштувань безпеки активних служб та присвоює кожній числову оцінку експозиції загрозам (*exposure score* від `0.0` — максимальний захист до `10.0` — повна відсутність захисту):

```bash
systemd-analyze security mydaemon.service
```

## 9. Журнал системного аудиту Linux (Audit framework)

При спрацьовуванні фільтрів Seccomp з дією `SECCOMP_RET_LOG`, `SECCOMP_RET_KILL` або порушенні правил мандатного контролю (AppArmor / SELinux) ядро генерує записи аудиту через підсистему `kauditd`.

### 9.1. Структура запису блокування системного виклику в `/var/log/audit/audit.log`

```
type=SECCOMP msg=audit(1692361200.421:108): auid=1000 uid=65534 gid=65534 ses=2 
subj=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023 pid=4812 comm="worker" 
exe="/usr/local/bin/worker" sig=31 arch=c000003e syscall=165 compat=0 
hpid=4812 code=0x00000000
```

#### Розшифровка критичних полів запису аудиту:

| Поле | Значення в прикладі | Пояснення значення поля |
| :--- | :--- | :--- |
| `type` | `SECCOMP` | Підсистема безпеки ядра, що згенерувала запис аудиту. |
| `uid` | `65534` | Ефективний UID процесу в момент здійснення системного виклику (`nobody`). |
| `comm` | `worker` | Коротке ім'я процесу в таблиці задач ядра. |
| `arch` | `c000003e` | Шістнадцятковий код архітектури процесора (`AUDIT_ARCH_X86_64`). |
| `syscall` | `165` | Номер системного виклику в таблиці ядра (`165` на x86_64 відповідає `mount()`). |
| `code` | `0x00000000` | Дія фільтра Seccomp, яка призвела до події (`SECCOMP_RET_KILL_THREAD`). |
| `sig` | `31` | Номер сигналу, надісланого процесу (`31` відповідає сигналу `SIGSYS`). |
