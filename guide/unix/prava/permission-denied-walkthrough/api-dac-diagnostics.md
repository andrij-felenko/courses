# 📋 Інтерфейси перевірки прав DAC та коди помилок VFS

Коли системний виклик до файлової системи завершується невдачею, ядро Linux повертає у простір користувача від'ємний числовий код, який стандартна бібліотека мови C (`libc`) записує в потоко-локальну змінну `errno`. Для прикладного розробника та системного адміністратора ця відмова найчастіше виглядає як стандартне повідомлення «Permission denied» або «Operation not permitted». Проте за цими двома фразами стоїть багаторівневий апарат ядра: структури облікових даних процесу (`struct cred`), дескриптори файлових записів (`struct inode`), таблиці трансляції імен (`struct dentry`), ядрові хуки безпеки та спеціалізовані прапорці системних викликів.

У цьому довіднику зібрано повний програмний контракт перевірки прав: структури ядра, внутрішні функції VFS, розширені прапорці сучасного API розбору шляхів `openat2()`, взаємодію з POSIX ACLs та файловими атрибутами `chattr`, системну матрицю діагностики типових відмов, прапорці безпеки процесу `securebits`, матрицю кодів помилок, сигнатури системних викликів діагностики, параметри безпеки ядра `sysctl` та правила інтерпретації інтерфейсів `/proc`.

---

## 1. Внутрішні структури даних ядра Linux

Перевірка дискреційного контролю доступу (DAC, від англ. *Discretionary Access Control*) в ядрі Linux є операцією зіставлення атрибутів суб'єкта (процесу) з атрибутами об'єкта (файлу чи каталогу).

### Структура облікових даних: `struct cred`

Кожне завдання в ядрі (представлене структурою `task_struct`) володіє посиланням на об'єкт `struct cred` (файл `<linux/cred.h>`). Управління пам'яттю цієї структури здійснюється за допомогою атомарного підрахунку посилань (`usage`) та механізму RCU (Read-Copy-Update). Процес не має права змінювати власну структуру `cred` «на місці» — замість цього ядро створює копію через функцію `prepare_creds()`, модифікує необхідні поля та публікує нову структуру викликом `commit_creds()`.

Нижче наведено основні поля структури `cred`:

```c
struct cred {
    atomic_t        usage;
    kuid_t          uid;            /* Реальний ідентифікатор користувача (ruid) */
    kgid_t          gid;            /* Реальний ідентифікатор групи (rgid) */
    kuid_t          suid;           /* Збережений ідентифікатор користувача (suid) */
    kgid_t          sgid;           /* Збережений ідентифікатор групи (sgid) */
    kuid_t          euid;           /* Ефективний ідентифікатор користувача (euid) */
    kgid_t          egid;           /* Ефективний ідентифікатор групи (egid) */
    kuid_t          fsuid;          /* Ідентифікатор користувача для файлової системи (fsuid) */
    kgid_t          fsgid;          /* Ідентифікатор групи для файлової системи (fsgid) */
    unsigned        securebits;     /* Прапорці фіксації привілеїв (SECURE_* прапорці) */
    kernel_cap_t    cap_inheritable;/* Capabilities, що успадковуються через execve */
    kernel_cap_t    cap_permitted;  /* Дозволені capabilities (максимальний набір) */
    kernel_cap_t    cap_effective;  /* Активні capabilities, що перевіряються ядром */
    kernel_cap_t    cap_bset;       /* Обмежувальний набір (bounding set) */
    kernel_cap_t    cap_ambient;    /* Амбієнтні capabilities для не-привілейованих бінарників */
    struct group_info *group_info;  /* Масив додаткових числових GID (Supplementary Groups) */
    struct user_struct *user;       /* Статистика споживання ресурсів користувачем */
    struct user_namespace *user_ns; /* Простір імен користувачів (User Namespace) */
};
```

Поля `kuid_t` та `kgid_t` є спеціальними безпечними типами ядра (структурами з одним числовим полем `val`), що запобігають випадковому прямому змішуванню внутрішніх ідентифікаторів просторів імен з числовими значеннями простору користувача.

### Структура файлового вузла: `struct inode`

Об'єкт `struct inode` (файл `<linux/fs.h>`) представляє метадані файлу на рівні VFS:

```c
struct inode {
    umode_t         i_mode;         /* Тип файлу (4 біти) + Права доступу (12 бітів) */
    kuid_t          i_uid;          /* Числовий UID власника об'єкта */
    kgid_t          i_gid;          /* Числовий GID групи об'єкта */
    const struct inode_operations *i_op; /* Таблиця методів inode (зокрема i_op->permission) */
    struct super_block *i_sb;       /* Вказівник на суперблок файлової системи */
    unsigned long   i_flags;        /* Системні прапорці файлу (S_IMMUTABLE, S_APPEND тощо) */
    atomic_t        i_count;        /* Лічильник посилань на структуру в пам'яті */
    unsigned int    i_nlink;        /* Кількість жорстких посилань на диску */
};
```

Поле `i_mode` кодує як формат об'єкта (звичайний файл `S_IFREG`, каталог `S_IFDIR`, сокет `S_IFSOCK`, символьне посилання `S_IFLNK`), так і дванадцять бітів прав: три спеціальні біти (`S_ISUID`, `S_ISGID`, `S_ISVTX`) та дев'ять бітів матриці `rwx` (`S_IRWXU`, `S_IRWXG`, `S_IRWXO`).

## 2. Алгоритмічний ланцюг функцій ядра для перевірки прав

Підсистема VFS використовує стандартизований каскад функцій для ухвалення рішення про допуск до операції.

### Функція `generic_permission()`

Функція `generic_permission()` реалізує класичний стандарт перевірки прав POSIX DAC:

```c
int generic_permission(struct mnt_idmap *idmap, struct inode *inode, int mask);
```

* **Вхідні параметри:**
  * `idmap` — структура контексту відображення ідентифікаторів точки монтування (idmapped mounts). Для звичайних монтувань передається `&nop_mnt_idmap`.
  * `inode` — дескриптор цільового об'єкта файлової системи.
  * `mask` — бітова маска запитуваних прав, складена з прапорців ядра:
    * `MAY_EXEC` (`0x0001`) — виконання файлу або пошук у каталозі.
    * `MAY_WRITE` (`0x0002`) — модифікація вмісту файлу чи зміна записів у каталозі.
    * `MAY_READ` (`0x0004`) — читання даних файлу чи перегляд списку імен каталогу.
    * `MAY_NOT_BLOCK` (`0x0080`) — вимога виконати перевірку лише в кеші пам'яті (RCU-walk), не звертаючись до блокуючих дискових операцій.
* **Внутрішній алгоритм:**
  1. Отримує `fsuid` поточного процесу через макрос `current_fsuid()`.
  2. Порівнює `fsuid` із `inode->i_uid`. Якщо вони рівні — обчислює бітову маску дозволів класу власника: `(inode->i_mode & S_IRWXU) >> 6`.
  3. Якщо `fsuid` не збігся, перевіряє `fsgid` через `current_fsgid()` та викликає функцію `in_group_p(inode->i_gid)`. Якщо процес належить до групи файлу — обчислює маску класу групи: `(inode->i_mode & S_IRWXG) >> 3`.
  4. Якщо немає збігу за власником та групою — бере маску класу інших: `inode->i_mode & S_IRWXO`.
  5. Якщо обрана маска містить усі біти, що вимагаються в аргументі `mask`, функція повертає `0` (дозвіл надано).
  6. Якщо бітів бракує, перевіряються capabilities процесу (`capable_wrt_inode_uidgid`):
     * Для читання й запису перевіряється `CAP_DAC_OVERRIDE`.
     * Для пошуку в каталозі перевіряється `CAP_DAC_READ_SEARCH`.
     * Для виконання двійкового файлу перевіряється `CAP_DAC_OVERRIDE`, але з додатковою вимогою: хоча б один біт виконання (`S_IXUSR | S_IXGRP | S_IXOTH`) обов'язково має бути встановлений у `i_mode`.
  7. Якщо привілеї відсутні — повертається `-EACCES`.

### Функція `inode_permission()`

Функція `inode_permission()` є центральним шлюзом для будь-якої дії над дескриптором файлу:

```c
int inode_permission(struct mnt_idmap *idmap, struct inode *inode, int mask);
```

Вона виконує попередні системні перевірки:
* Якщо запитується запис (`mask & MAY_WRITE`):
  * Перевіряє, чи не змонтована файлова система в режимі тільки для читання: `sb_rdonly(inode->i_sb)`. У разі збігу повертає `-EROFS`.
  * Перевіряє наявність системного прапорця незмінності: `IS_IMMUTABLE(inode)`. У разі наявності повертає `-EPERM`.
* Викликає специфічний для конкретної файлової системи метод `inode->i_op->permission()` або базовий `generic_permission()`.
* Якщо перевірка DAC успішна, викликає хуки активних модулів безпеки LSM: `security_inode_permission(inode, mask)` (SELinux, AppArmor, Landlock).

### Функція `may_delete()`

Функція `may_delete()` викликається під час системних викликів `unlink()`, `rmdir()` та `rename()`:

```c
int may_delete(struct mnt_idmap *idmap, struct inode *dir, struct dentry *victim, bool isdir);
```

* **Перевірка:**
  1. Перевіряє право запису та пошуку на батьківському каталозі: `inode_permission(idmap, dir, MAY_WRITE | MAY_EXEC)`.
  2. Перевіряє наявність прапорця Sticky Bit на каталозі (`dir->i_mode & S_ISVTX`).
  3. Якщо Sticky Bit встановлено, видалення дозволяється лише за умови:
     * `current_fsuid() == victim->d_inode->i_uid` (процес є власником об'єкта);
     * АБО `current_fsuid() == dir->i_uid` (процес є власником каталогу);
     * АБО процес має `CAP_FOWNER` у поточному просторі імен користувачів.
  4. Якщо жодна з умов не виконана — повертає `-EACCES` (або `-EPERM`).

## 3. Сучасний інтерфейс розбору шляхів: `openat2()` та `struct open_how`

Починаючи з версії Linux 5.6, підсистема VFS підтримує системний виклик `openat2()`, який дозволяє процесу жорстко контролювати правила обходу шляхів для захисту від атак гонитви (TOCTOU) та підміни каталогів.

```c
#include <fcntl.h>
#include <linux/openat2.h>
#include <sys/syscall.h>

struct open_how {
    __u64 flags;        /* Прапорці відкриття (O_RDONLY, O_CREAT, O_CLOEXEC тощо) */
    __u64 mode;         /* Права створення файлу (0644) */
    __u64 resolve;      /* Прапорці поведінки розбору шляху (RESOLVE_*) */
};

int openat2(int dirfd, const char *pathname, struct open_how *how, size_t size);
```

### Прапорці керування розбором шляху (`how->resolve`)

* **`RESOLVE_NO_XDEV` (`0x01`):** забороняє перетин точок монтування під час обходу шляху. Якщо шлях веде на інший змонтований розділ, виклик завершується помилкою `EXDEV`.
* **`RESOLVE_NO_MAGICLINKS` (`0x02`):** забороняє перехід за спеціальними "магічними" посиланнями procfs (наприклад, `/proc/self/fd/N`). За спроби переходу повертається `ELOOP`.
* **`RESOLVE_NO_SYMLINKS` (`0x04`):** повністю забороняє будь-які символьні посилання на всьому шляху. Якщо будь-який компонент є symlink, повертається `ELOOP`.
* **`RESOLVE_BENEATH` (`0x08`):** гарантує, що розбір шляху ні за яких обставин не вийде за межі піддерева каталогу `dirfd` (блокує використання `..` для виходу вище або абсолютних символьних посилань). У разі спроби виходу повертається `EXDEV`.
* **`RESOLVE_IN_ROOT` (`0x10`):** розглядає каталог `dirfd` як тимчасовий корінь файлової системи (еквівалентно ізольованому `chroot` на час одного виклику). Будь-які абсолютні шляхи або переходи `..` затискаються всередині цього каталогу.

## 4. Взаємодія моделі DAC зі списками контролю доступу (POSIX ACLs)

Коли на файлі або каталозі встановлено розширені списки контролю доступу (POSIX ACLs), дескриптор `inode` зв'язується зі структурою `struct posix_acl`, яка зберігається в розширеному атрибуті `system.posix_acl_access`.

Утиліта `ls -l` сигналізує про наявність розширеного ACL символом `+` наприкінці рядка прав (`-rw-r-----+`).

### Структура записів ACL та алгоритм перевірки

Запис POSIX ACL складається з кількох обов'язкових та додаткових полів:
* `user::rwx` — права власника файлу (відповідає `S_IRWXU`).
* `user:<uid>:rwx` — права для конкретного іменованого користувача.
* `group::rwx` — права основної групи файлу.
* `group:<gid>:rwx` — права для конкретної іменованої групи.
* `mask::rwx` — маска максимальних прав для всіх іменованих користувачів та груп.
* `other::rwx` — права для решти користувачів (відповідає `S_IRWXO`).

**Алгоритм оцінки:**
1. Якщо `fsuid == inode->i_uid`, застосовується запис `user::` (маска `mask` на власника не діє).
2. Якщо `fsuid` збігається з іменованим записом `user:<uid>:`, права обчислюються як побітове `AND` прав користувача та запису `mask::`.
3. Якщо `fsgid` або будь-яка додаткова група збігається з `group::` або `group:<gid>:`, права обчислюються як побітове `AND` відповідного групового запису та запису `mask::`. Якщо користувач входить до кількох груп, їхні права **об'єднуються** (на відміну від класичного DAC).
4. Якщо жоден запис не підійшов, застосовується запис `other::`.

Важливий побічний ефект: системний виклик `chmod()` на файлі, що має ACL, змінює значення поля `mask::`, а не базові права групи власника.

## 5. Системні атрибути файлових систем (`chattr` / `lsattr`)

Окрім моделі DAC та списків ACL, ядро Linux підтримує системні прапорці файлових систем (`ext4`, `xfs`, `btrfs`), які зберігаються в полі `inode->i_flags` і мають вищий пріоритет над класичними правами:

| Прапорець | Назва прапорця ядра | Поведінка підсистеми VFS | Код помилки при порушенні |
| :--- | :--- | :--- | :--- |
| `i` | `FS_IMMUTABLE_FL` | Файл повністю захищений від модифікації, скорочення, видалення, перейменування чи створення жорстких посилань. Навіть користувач `root` не може змінити файл без попереднього зняття прапорця командою `chattr -i`. | `EPERM` |
| `a` | `FS_APPEND_FL` | Файл може бути відкритий на запис виключно з прапорцем `O_APPEND` (тільки дописування нових даних у кінець). Скорочення (`truncate`) та перезапис існуючих блоків суворо заборонені. | `EPERM` |
| `d` | `FS_NODUMP_FL` | Файл ігнорується резервним копіюванням утилітою `dump`. Не впливає на права доступу. | Не застосовується |
| `s` | `FS_SECRM_FL` | Безпечне видалення: під час виклику `unlink()` дискові блоки файлу перезаписуються нулями перед звільненням. | Не застосовується |

## 6. Прапорці фіксації привілеїв процесу (`securebits` та `PR_SET_NO_NEW_PRIVS`)

Ядро Linux містить механізми обмеження поведінки привілейованих процесів:

1. **`PR_SET_NO_NEW_PRIVS`:** системний виклик `prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)` гарантує, що процес та всі його нащадки ніколи не зможуть отримати додаткові привілеї через біти `setuid`/`setgid` на двійкових файлах або файлові capabilities. Будь-який подальший запуск `sudo` чи `su` виконається зі звичайними правами викликаючого процесу.
2. **Маска `securebits`:** керує тим, як UID 0 обробляється ядром. Наприклад, біт `SECBIT_NOROOT` забороняє автоматичне надання Capabilities при переході в `UID 0`, а `SECBIT_NO_SETUID_FIXUP` забороняє зміну capabilities при зміні UID.

## 7. Параметри безпеки ядра `sysctl` для файлових систем

Сучасне ядро Linux має набір глобальних параметрів `/proc/sys/fs/protected_*`, які блокують класичні вектори атак через спільні каталоги (`/tmp`):

| Параметр sysctl | Значення | Логіка блокування ядром Linux | Код помилки |
| :--- | :--- | :--- | :--- |
| `fs.protected_symlinks` | `1` (за замовчуванням) | Забороняє перехід за символьним посиланням у каталозі зі Sticky Bit (`+t`), якщо власник symlink не збігається з власником каталогу або користувачем, який здійснює виклик. | `EACCES` |
| `fs.protected_hardlinks` | `1` (за замовчуванням) | Забороняє створення жорсткого посилання `link()` на файл, власником якого процес не є, крім випадків, коли процес має права на читання та запис у цільовий файл. | `EPERM` |
| `fs.protected_fifos` | `1` / `2` | Значення `1` забороняє відкриття іменованих каналів (FIFO) у каталогах `+t`, створених іншими користувачами, якщо відкриття відбувається з прапорцем `O_CREAT`. Значення `2` розширює цю заборону на всі каталоги з правом запису для групи/інших. | `EACCES` |
| `fs.protected_regular` | `1` / `2` | Забороняє виклик `open()` з прапорцями `O_CREAT | O_EXCL` або `O_CREAT` для звичайних файлів у спільних каталогах, якщо файл належить іншому користувачеві. | `EACCES` |

## 8. Матриця діагностики типових відмов доступу для системного інженера

Нижче наведено практичну матрицю швидкої діагностики помилок файлового доступу:

| Симптом у терміналі | Найімовірніша причина | Команда швидкої перевірки | Спосіб виправлення |
| :--- | :--- | :--- | :--- |
| `open()` повертає `EACCES`, хоча на файлі стоїть `0777` | Відсутній біт `+x` на одному з проміжних каталогів шляху | `namei -ln /повний/шлях/до/файлу` | Встановити `chmod +x` на каталозі, що блокує прохід |
| `open()` на читання повертає `EACCES` для власника файлу | Файл має режим `0064` (`----rw-r--`); власник не має `r`, а права групи не діють | `stat -c "%a %u:%g" /шлях` | Встановити права читання для класу власника: `chmod u+r` |
| `open()` з `O_CREAT` повертає `EROFS` | Файлова система змонтована в режимі `ro` | `findmnt -T /шлях` | Перемонтувати файлову систему в режимі `rw` (`mount -o remount,rw`) |
| Скрипт падає з `Permission denied` при запуску `./run.sh` | На скрипті стоїть `+x`, але відсутній `+r` (інтерпретатор не може прочитати тіло) | `ls -l ./run.sh` | Встановити біт читання: `chmod +r ./run.sh` |
| Користувач не може видалити файл у `/tmp` | На каталозі стоїть Sticky Bit (`+t`), а користувач не є власником файлу чи каталогу | `stat -c "%a %u" /tmp/файл` | Видалення можливе лише власником файлу або користувачем `root` |
| Команда `rm -f` відмовляє користувачеві `root` з `EPERM` | На файлі встановлено прапорець незмінності `immutable` (`+i`) | `lsattr /шлях/до/файлу` | Зняти системний атрибут: `chattr -i /шлях/до/файлу` |
| Відкриття на запис виконуваного файлу повертає `ETXTBSY` | Двійковий файл прямо зараз завантажений у пам'ять і виконується | `fuser -v /шлях/до/бінарника` | Зупинити всі запущені екземпляри програми перед оновленням |

## 9. Матриця кодів помилок системних викликів

Коли системний виклик повертає помилку доступу, ядро використовує строго диференційовані числові коди.

| Макрос C | Код | Назва за POSIX | Семантика в ядрі Linux та типові причини |
| :--- | :--- | :--- | :--- |
| `EACCES` | `13` | Permission denied | Відмова в доступі за моделлю прав DAC. Брак бітів `r`, `w` або `x` у визначеному класі; відсутність біта `+x` на будь-якому каталозі шляху; порушення Sticky Bit у `/tmp`; заборона виконання через прапорець монтування `noexec`; блокування хуком LSM (AppArmor/SELinux). |
| `EPERM` | `1` | Operation not permitted | Брак прав власності або адміністративних Capabilities. Спроба виклику `chown()` не-привілейованим користувачем (без `CAP_CHOWN`); спроба виклику `chmod()` користувачем, який не є власником файлу (без `CAP_FOWNER`); спроба зміни файлу з атрибутом `immutable` (`chattr +i`); спроба надіслати сигнал чужому процесу через `kill()`. |
| `EROFS` | `30` | Read-only file system | Спроба будь-якої модифікації файлу (`MAY_WRITE`), створення або видалення запису на файловій системі, змонтованій із прапорцем `MS_RDONLY` (`ro`), або на фізично захищеному носії. |
| `ETXTBSY` | `26` | Text file busy | Спроба відкрити на запис (`O_WRONLY`, `O_RDWR`, `truncate`) виконуваний двійковий файл, який у даний момент завантажений у пам'ять і виконується процесом. |
| `ENOENT` | `2` | No such file or directory | Компонент шляху не існує; або шлях вказує на розірване символьне посилання (dangling symlink); або ядро навмисно повертає помилку відсутності для приховування існування захищеного об'єкта. |
| `EISDIR` | `21` | Is a directory | Спроба відкрити каталог на запис викликом `open(..., O_WRONLY)` або `open(..., O_RDWR)`. Зміна записів каталогу дозволена лише через спеціалізовані виклики VFS. |
| `ENOTDIR` | `20` | Not a directory | Компонент шляху вказано як каталог (наприклад, `/var/log/file.txt/sub`), але відповідний inode є звичайним файлом. |
| `EXDEV` | `18` | Invalid cross-device link | Спроба створення жорсткого посилання `link()` або атомарного перейменування `rename()` між різними точками монтування або різними файловими системами; або порушення правила `RESOLVE_BENEATH` у виклику `openat2()`. |
| `ELOOP` | `40` | Too many levels of symbolic links | Перевищено ліміт вкладеності символьних посилань (максимум 40 переходів у ядрі Linux) або виявлено циклічне зациклення посилань; або передано прапорець `O_NOFOLLOW` / `RESOLVE_NO_SYMLINKS`. |

## 10. Системні виклики простору користувача для роботи з правами

У просторі користувача взаємодія з правами та перевірками здійснюється через сімейство викликів POSIX та розширень Linux.

### Перевірка доступності: `access()`, `faccessat()` та `faccessat2()`

```c
#include <unistd.h>
#include <fcntl.h>

int access(const char *pathname, int mode);
int faccessat(int dirfd, const char *pathname, int mode, int flags);
int faccessat2(int dirfd, const char *pathname, int mode, int flags);
```

* **Маски перевірки (`mode`):**
  * `F_OK` (`0`) — перевірка існування файлу та можливості розбору шляху до нього.
  * `R_OK` (`4`) — перевірка дозволу на читання.
  * `W_OK` (`2`) — перевірка дозволу на запис.
  * `X_OK` (`1`) — перевірка дозволу на виконання або пошук.
* **Прапорці (`flags` у `faccessat2`):**
  * `AT_EACCESS` (`0x200`) — виконувати перевірку за **ефективними** ідентифікаторами (`euid`/`egid`), а не за реальними. Класичний виклик `access()` завжди використовує реальний UID/GID процесу, що робить його непридатним для перевірки прав утилітами з прапорцем `setuid`.
  * `AT_SYMLINK_NOFOLLOW` (`0x100`) — не переходити за символьними посиланнями.
  * `AT_EMPTY_PATH` (`0x1000`) — якщо `pathname` є порожнім рядком, виконати перевірку безпосередньо для файлу, на який вказує дескриптор `dirfd`.

### Керування ідентифікаторами: `getresuid()`, `setresuid()`, `setfsuid()`

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <sys/fsuid.h>

int getresuid(uid_t *ruid, uid_t *euid, uid_t *suid);
int setresuid(uid_t ruid, uid_t euid, uid_t suid);
int setfsuid(uid_t fsuid);
```

* **Особливість виклику `setfsuid()`:** Виклик `setfsuid()` ніколи не завершується помилкою через `-1` та `errno`. Функція повертає **попередній** числовий `fsuid`. Якщо передане значення є неприпустимим (процес не має `CAP_SETUID` і вказаний UID не збігається з його `ruid`, `euid` чи `suid`), виклик ігнорується, а повернуте значення залишається незмінним.

## 11. Практичний програмний приклад діагностики (C та C++)

Нижче наведено закінчений програмний приклад, який отримує всі ідентифікатори активного процесу та виконує перевірку прав доступу до вказаного файлу за моделлю ефективних привілеїв (`AT_EACCESS`).

```c
/* dac_inspect.c — Діагностика ідентичності та перевірка прав доступу на C */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <errno.h>
#include <string.h>
#include <sys/types.h>
#include <sys/stat.h>

void print_credentials(void) {
    uid_t ruid, euid, suid;
    gid_t rgid, egid, sgid;

    if (getresuid(&ruid, &euid, &suid) != 0 || getresgid(&rgid, &egid, &sgid) != 0) {
        perror("getresuid/getresgid");
        return;
    }

    int ngroups = getgroups(0, NULL);
    gid_t *groups = NULL;
    if (ngroups > 0) {
        groups = malloc(sizeof(gid_t) * ngroups);
        if (groups && getgroups(ngroups, groups) < 0) {
            free(groups);
            groups = NULL;
            ngroups = 0;
        }
    }

    printf("Ідентичність процесу [PID %d]:\n", getpid());
    printf("  UID: real=%u, effective=%u, saved=%u\n", ruid, euid, suid);
    printf("  GID: real=%u, effective=%u, saved=%u\n", rgid, egid, sgid);
    printf("  Додаткові групи (%d): ", ngroups);
    for (int i = 0; i < ngroups; ++i) {
        printf("%u ", groups[i]);
    }
    printf("\n");
    free(groups);
}

int check_access_effective(const char *path, int mode) {
    if (faccessat(AT_FDCWD, path, mode, AT_EACCESS) == 0) {
        return 0;
    }
    return errno;
}

int main(int argc, char **argv) {
    if (argc < 2) {
        fprintf(stderr, "Використання: %s <шлях_до_файлу>\n", argv[0]);
        return 1;
    }

    print_credentials();

    const char *target = argv[1];
    printf("\nПеревірка доступу до '%s' (faccessat з AT_EACCESS):\n", target);

    int err_r = check_access_effective(target, R_OK);
    int err_w = check_access_effective(target, W_OK);
    int err_x = check_access_effective(target, X_OK);

    printf("  Читання (R_OK):   %s\n", err_r == 0 ? "ДОЗВОЛЕНО" : strerror(err_r));
    printf("  Запис (W_OK):     %s\n", err_w == 0 ? "ДОЗВОЛЕНО" : strerror(err_w));
    printf("  Виконання (X_OK): %s\n", err_x == 0 ? "ДОЗВОЛЕНО" : strerror(err_x));

    return 0;
}
```

```cpp
// dac_inspect.cpp — Діагностика ідентичності та перевірка прав доступу на C++20
#include <iostream>
#include <vector>
#include <string>
#include <string_view>
#include <system_error>
#include <unistd.h>
#include <fcntl.h>
#include <sys/types.h>

struct Credentials {
    uid_t ruid{}, euid{}, suid{};
    gid_t rgid{}, egid{}, sgid{};
    std::vector<gid_t> groups;
};

Credentials get_current_credentials() {
    Credentials cred;
    if (getresuid(&cred.ruid, &cred.euid, &cred.suid) != 0 ||
        getresgid(&cred.rgid, &cred.egid, &cred.sgid) != 0) {
        throw std::system_error(errno, std::generic_category(), "Не вдалося отримати UID/GID");
    }

    int count = getgroups(0, nullptr);
    if (count > 0) {
        cred.groups.resize(count);
        if (getgroups(count, cred.groups.data()) < 0) {
            cred.groups.clear();
        }
    }
    return cred;
}

std::string check_permission(std::string_view path, int mode) {
    if (faccessat(AT_FDCWD, path.data(), mode, AT_EACCESS) == 0) {
        return "ДОЗВОЛЕНО";
    }
    return std::generic_category().message(errno);
}

int main(int argc, char** argv) {
    if (argc < 2) {
        std::cerr << "Використання: " << argv[0] << " <шлях_до_файлу>\n";
        return 1;
    }

    try {
        const auto cred = get_current_credentials();
        std::cout << "Ідентичність процесу [PID " << getpid() << "]:\n"
                  << "  UID: real=" << cred.ruid << ", effective=" << cred.euid << ", saved=" << cred.suid << "\n"
                  << "  GID: real=" << cred.rgid << ", effective=" << cred.egid << ", saved=" << cred.sgid << "\n"
                  << "  Додаткові групи (" << cred.groups.size() << "): ";
        for (gid_t g : cred.groups) {
            std::cout << g << " ";
        }
        std::cout << "\n\n";

        const std::string target = argv[1];
        std::cout << "Перевірка доступу до '" << target << "':\n"
                  << "  Читання (R_OK):   " << check_permission(target, R_OK) << "\n"
                  << "  Запис (W_OK):     " << check_permission(target, W_OK) << "\n"
                  << "  Виконання (X_OK): " << check_permission(target, X_OK) << "\n";
    } catch (const std::exception& ex) {
        std::cerr << "Помилка: " << ex.what() << "\n";
        return 1;
    }

    return 0;
}
```

## 12. Формат системних інтерфейсів `/proc` та інструментів адміністрування

### Декодування `/proc/[pid]/status`

Файл `/proc/[pid]/status` надає текстовий зліпок структури `cred`:

```sh
$ grep -E '^(Uid|Gid|Groups|Cap)' /proc/$$/status
Uid:    1000    1000    1000    1000
Gid:    1000    1000    1000    1000
Groups: 4 24 27 30 46 100 1000
CapInh: 0000000000000000
CapPrm: 0000000000000000
CapEff: 0000000000000000
CapBnd: 000001ffffffffff
CapAmb: 0000000000000000
```

* **Рядки `Uid` та `Gid`:** містять чотири стовпчики: `Real`, `Effective`, `Saved set`, `Filesystem`.
* **Рядок `Groups`:** перелік додаткових числових GID, які використовуються функцією `generic_permission()` для перевірки класу групи.
* **Рядки `Cap*`:** 64-бітові шістнадцяткові бітові маски набору capabilities (Inheritable, Permitted, Effective, Bounding, Ambient). Значення `CapEff: 0000000000000002` свідчить про наявність `CAP_DAC_OVERRIDE` (біт 1).

### Аналіз точок монтування через `/proc/[pid]/mountinfo`

Файл `/proc/[pid]/mountinfo` дозволяє детально перевірити стан прапорців кожної файлової системи:

```sh
$ grep ' /var ' /proc/self/mountinfo
28 1 8:2 / /var rw,nosuid,nodev,relatime - ext4 /dev/sda2 rw,data=ordered
```

* **Ключові параметри безпеки:**
  * `ro` — суперблок змонтований у режимі тільки для читання (будь-який запис повертає `EROFS`).
  * `noexec` — ядро блокує виклик `execve()` для двійкових файлів на цьому розділі (повертає `EACCES`).
  * `nosuid` — ядро ігнорує біти `setuid` та `setgid` на виконуваних файлах (програми запускаються зі звичайними правами поточного користувача).
  * `nodev` — ядро забороняє відкриття спеціальних файлів пристроїв (device nodes).

### Формат діагностики утиліти `namei`

Утиліта `namei -ln <шлях>` покроково емулює функцію `link_path_walk()` VFS, виводячи права та числові ідентифікатори кожного вузла:

```sh
$ namei -ln /var/log/app/service.log
f: /var/log/app/service.log
drwxr-xr-x     0     0 /
drwxr-xr-x     0     0 var
drwxr-xr-x     0     0 log
drwxr-x---  1000  1000 app
-rwxrwxrwx  1001  1001 service.log
```

* **Символи типу на початку:**
  * `d` — каталог (потрібен біт `+x` у стовпчику вашого класу).
  * `l` — символьне посилання (ядро автоматично розгортає шлях).
  * `-` — цільовий файл (перевіряється за матрицею запитуваних прав `rwx`).
