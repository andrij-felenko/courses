# 📋 Інтерфейс системних викликів epoll у ядрі Linux

Підсистема `epoll` є спеціалізованим засобом синхронного масштабованого мультиплексування дескрипторів у ядрі Linux. На відміну від застарілих POSIX-викликів `select()` та `poll()`, які є функціями без збереження стану (англ. *stateless*), `epoll` керує виділеним об'єктом ядра (екземпляром `struct eventpoll`), що зберігає таблицю зареєстрованих інтересів між системними викликами та асинхронно накопичує події готовності дескрипторів.

Цей довідник описує повний контракт викликів сімейства `epoll`, структури даних ядра, бітові маски подій, семантику модифікаторів тригерів, коди помилок, поведінку вкладених екземплярів (Cascading epoll), внутрішнє блокування в багатопотоковому середовищі та діагностику через псевдофайлову систему `procfs`.

---

## 1. Системні виклики та їхні сигнатури

Інтерфейс `epoll` складається з трьох основних системних викликів та їхніх розширених варіантів, оголошених у заголовному файлі `<sys/epoll.h>`.

### `epoll_create1()` — створення екземпляра epoll

Створює новий опис об'єкта `eventpoll` у пам'яті ядра та повертає файловий дескриптор, пов'язаний із цим екземпляром.

```c
#include <sys/epoll.h>

int epoll_create1(int flags);
```

#### Параметри:
* `flags` — бітова маска модифікаторів створення. Допустимі значення:
  * `0` — поведінка за замовчуванням (еквівалент застарілого виклику `epoll_create(int size)`);
  * `EPOLL_CLOEXEC` — атомарно встановлює прапорець `FD_CLOEXEC` (Close-on-exec) на створений дескриптор. Запобігає витоку дескриптора `epoll` у дочірні процеси під час виклику `execve()`.

#### Значення, що повертаються:
* У разі успіху повертає невід'ємне ціле число — файловий дескриптор екземпляра `epoll`;
* У разі помилки повертає `-1`, а глобальна змінна `errno` встановлюється у відповідний код помилки (`EINVAL`, `EMFILE`, `ENFILE`, `ENOMEM`).

> ⚠️ **Історична довідка щодо `epoll_create()`:** Застарілий системний виклик `int epoll_create(int size)` вимагав передачі аргументу `size > 0`, який спочатку використовувався як підказка ядру щодо очікуваної кількості дескрипторів для виділення хеш-таблиці. Починаючи з ядра Linux 2.6.8, внутрішню структуру було переведено на динамічне червоно-чорне дерево, аргумент `size` повністю ігнорується (перевіряється лише умова `size > 0`), а використання `epoll_create1(EPOLL_CLOEXEC)` є обов'язковим сучасним стандартом.

---

### `epoll_ctl()` — керування інтересами дескрипторів

Виконує операції реєстрації, модифікації маски подій або видалення дескриптора цільового ресурсу з червоно-чорного дерева інтересів екземпляра `epoll`.

```c
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
```

#### Параметри:
* `epfd` — файловий дескриптор екземпляра `epoll`, повернутий `epoll_create1()`;
* `op` — дія, яку необхідно виконати над цільовим дескриптором `fd`:
  * `EPOLL_CTL_ADD` — зареєструвати цільовий дескриптор `fd` в екземплярі `epoll` та пов'язати з ним налаштування зі структури `event`;
  * `EPOLL_CTL_MOD` — змінити налаштування подій або передані дані `event` для вже зареєстрованого дескриптора `fd`;
  * `EPOLL_CTL_DEL` — видалити дескриптор `fd` з екземпляра `epoll`. Спостереження за подіями припиняється. (У ядрах Linux до версії 2.6.9 аргумент `event` не міг бути `NULL`, навіть при видаленні; у сучасних ядрах при `EPOLL_CTL_DEL` покажчик `event` ігнорується і може бути переданий як `NULL`).
* `fd` — дескриптор цільового об'єкта VFS (сокет, канал, таймер, сигнал тощо), стан якого необхідно відстежувати;
* `event` — покажчик на структуру `struct epoll_event`, що описує бажану маску подій та асоційовані дані користувача.

#### Помилки `epoll_ctl()`:
* `EBADF` — `epfd` або `fd` не є дійсними дескрипторами;
* `EEXIST` — спроба `EPOLL_CTL_ADD` для дескриптора, який вже додано;
* `ENOENT` — спроба `EPOLL_CTL_MOD` або `EPOLL_CTL_DEL` для незареєстрованого дескриптора;
* `EINVAL` — спроба додати `epfd` до самого себе (`epfd == fd`);
* `ELOOP` — виявлено циклічну залежність або перевищено граничну глибину вкладеності;
* `ENOSPC` — вичерпано ліміт `max_user_watches`;
* `EPERM` — цільовий файл `fd` не підтримує `poll` (наприклад, регулярний дисковий файл).

### `epoll_wait()` — очікування подій готовності

Блокує потік виконання до моменту, поки хоча б один зареєстрований дескриптор не перейде в стан готовності, не вичерпається заданий таймаут або виклик не буде перервано сигналом.

```c
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);
```

#### Параметри:
* `epfd` — дескриптор екземпляра `epoll`;
* `events` — покажчик на попередньо виділений масив структур `struct epoll_event` у просторі користувача, куди ядро записує готові події;
* `maxevents` — місткість переданого масиву `events` (максимальна кількість подій, яку ядро може повернути за один виклик). Значення повинно бути строго більшим за 0;
* `timeout` — інтервал максимального очікування в мілісекундах:
  * `-1` — нескінченне блокування (потік спить у черзі очікування ядра, доки не з'явиться хоча б одна подія або не надійде системний сигнал);
  * `0` — негайне повернення без сну (неблокуюче опитування стану списку готових подій);
  * `> 0` — потік спить максимум зазначену кількість мілісекунд.

#### Значення, що повертаються:
* `> 0` — кількість структур у масиві `events`, заповнених ядром;
* `0` — минув таймаут очікування, жоден дескриптор не став готовим;
* `-1` — сталася помилка, деталі збережено в `errno` (зокрема код `EINTR`, якщо очікування перервав системний сигнал).

---

### `epoll_pwait()` та `epoll_pwait2()` — розширені варіанти очікування

Дозволяють атомарно встановити маску сигналів на час очікування подій, що усуває стан гонитви (race condition) між надходженням сигналів і переходом у стан сну.

```c
#define _GNU_SOURCE
#include <sys/epoll.h>
#include <signal.h>

int epoll_pwait(int epfd, struct epoll_event *events, int maxevents,
                int timeout, const sigset_t *sigmask);

int epoll_pwait2(int epfd, struct epoll_event *events, int maxevents,
                 const struct timespec *timeout, const sigset_t *sigmask);
```

* `sigmask` — покажчик на маску сигналів `sigset_t`. Ядро атомарно підміняє поточну маску сигналів потоку на передану, виконує очікування подій, а перед поверненням відновлює початкову маску;
* `epoll_pwait2()` (доступний починаючи з ядра Linux 5.11) приймає таймаут у форматі структури `struct timespec`, забезпечуючи роздільну здатність таймауту до **наносекунд** замість мілісекунд у класичному виклику. Якщо покажчик `timeout == NULL`, виклик блокується нескінченно.

## 2. Структури даних ядра та простору користувача

### Структура події `struct epoll_event`

Структура `struct epoll_event` передається у виклики `epoll_ctl()` для налаштування спостереження та заповнюється ядром під час виклику `epoll_wait()`.

```c
#include <stdint.h>

typedef union epoll_data {
    void        *ptr;      /* Покажчик на структуру користувацького контексту / сесії */
    int          fd;       /* Файловий дескриптор */
    uint32_t     u32;      /* 32-розрядне число */
    uint64_t     u64;      /* 64-розрядне число (ідентифікатор, таймстемп тощо) */
} epoll_data_t;

struct epoll_event {
    uint32_t      events;  /* Бітова маска подій epoll (вхідні / вихідні / прапорці) */
    epoll_data_t  data;    /* Користувацькі дані, що повертаються без змін */
};
```

> ⚠️ **Важлива особливість об'єднання `epoll_data_t`:** Поле `data` є об'єднанням (`union`). Програма може використовувати лише **одне** з полів одночасно. Якщо ви записуєте `event.data.ptr = &session;`, поле `event.data.fd` буде перезаписане значенням покажчика. У промислових подієвих циклах у `event.data.ptr` зберігають покажчик на структуру об'єкта підключення (яка вже всередині себе містить дескриптор `fd`, буфери прийому/передачі та стан протокольного автомата).

## 3. Внутрішні структури ядра Linux (`fs/eventpoll.c`)

Щоб розуміти швидкодію та поведінку `epoll` під час високих навантажень, важливо знати, як саме він представлений у просторі ядра:

```c
/* Концептуальна схема ключових структур ядра (fs/eventpoll.c) */

struct eventpoll {
    struct mutex            mtx;          /* М'ютекс для операцій epoll_ctl */
    rwlock_t                lock;         /* Блокування для списку готових подій */
    wait_queue_head_t       wq;           /* Черга очікування для epoll_wait() */
    wait_queue_head_t       poll_wait;    /* Черга очікування, якщо сам epoll вкладений в інший epoll */
    struct list_head        rdllist;      /* Двозв'язний список готових дескрипторів */
    struct rb_root_cached   rbr;          /* Червоно-чорне дерево зареєстрованих дескрипторів */
    struct epitem          *ovflist;      /* Тимчасовий список переповнення при копіюванні в userspace */
    struct user_struct     *user;         /* Облік ліміту max_user_watches для UID */
    struct file            *file;         /* Опис файлу самого екземпляра epoll */
};

struct epitem {
    struct rb_node          rb;           /* Вузол червоно-чорного дерева */
    struct list_head        rdllink;      /* Елемент двозв'язного списку rdllist */
    struct epoll_filefd     ffd;          /* Пара: struct file* та номер fd */
    struct eventpoll       *ep;           /* Покажчик на батьківський екземпляр eventpoll */
    struct epoll_event      event;        /* Поточна маска подій та дані користувача */
    struct list_head        pwqlist;      /* Список точок очікування в чергах драйверів */
};
```

### Механіка асинхронного сповіщення:
1. Під час виклику `epoll_ctl(EPOLL_CTL_ADD)` ядро виділяє структуру `struct epitem` зі спеціального кешу алокатора SLAB (`epitem_cache`);
2. Елемент додається в червоно-чорне дерево `rbr`. Ключем пошуку є комбінація покажчика на `struct file` та номера дескриптора `fd`;
3. Ядро викликає метод цільового файлу `file->f_op->poll` зі спеціальною таблицею зворотних викликів `ep_ptable_queue_proc()`. Це зв'язує сокет із функцією зворотного виклику ядра **`ep_poll_callback()`**;
4. Коли мережева карта доставляє пакет, драйвер сокета будить свою чергу очікування, що викликає `ep_poll_callback()`;
5. Функція `ep_poll_callback()` без блокувань додає `epitem` у список `rdllist` та будить потік у черзі `eventpoll->wq`.

## 4. Таблиця бітових прапорців подій та модифікаторів (`events`)

Поле `events` структури `struct epoll_event` є 32-розрядною бітовою маскою, утвореною побітовим «АБО» (`|`) із констант двох категорій: типів подій та модифікаторів поведінки тригера.

### Категорія 1: Події готовності дескриптора

| Прапорець | Опис та семантика готовності | Напрямок |
| :--- | :--- | :--- |
| **`EPOLLIN`** | Дескриптор готовий для операцій читання без блокування. Для сокетів — у буфері прийому з'явилися дані, або для слухаючого сокета прибуло нове з'єднання (можна викликати `accept()`). | Вхідний / Вихідний |
| **`EPOLLOUT`** | Дескриптор готовий для операцій запису без блокування. У буфері відправки сокета звільнилося місце для нових байтів. | Вхідний / Вихідний |
| **`EPOLLRDHUP`** | Віддалений вузол потокового TCP-сокета закрив з'єднання для запису (надіслав TCP FIN) або виконав виклик `shutdown(SHUT_WR)`. Дозволяє виявити закриття з'єднання без виконання зайвого виклику `read()`. (З ядра Linux 2.6.17). | Вхідний / Вихідний |
| **`EPOLLPRI`** | На дескрипторі доступні виняткові або термінові дані (Out-of-Band дані для TCP-сокетів або події стану файлів `/sys`). | Вхідний / Вихідний |
| **`EPOLLERR`** | На дескрипторі сталася помилка апаратного каналу або мережевого протоколу (наприклад, скидання TCP RST). Встановлюється ядром **автоматично**, навіть якщо прапорець не передавався в `epoll_ctl()`. | Вихідний (ядро) |
| **`EPOLLHUP`** | Відбулося відключення каналу (Hangup). Для каналів (pipe) — закриття останнього дескриптора запису; для сокетів — повне двостороннє розірвання зв'язку. Встановлюється ядром **автоматично**. | Вихідний (ядро) |

### Категорія 2: Модифікатори поведінки тригера та планування

| Прапорець | Опис та механізм дії |
| :--- | :--- |
| **`EPOLLET`** | **Edge-Triggered (фронтовий режим)**. Ядро генерує сповіщення про готовність виключно в момент **зміни стану** (прибуття нових пакетів у порожній буфер або перехід буфера відправки зі стану переповнення). Вимагає, щоб дескриптор був у неблокуючому режимі (`O_NONBLOCK`), а ввід-вивід виконувався в циклі до отримання помилки `EAGAIN`. Без цього прапорця `epoll` працює у стандартному режимі **Level-Triggered (рівневий режим)**. |
| **`EPOLLONESHOT`** | Встановлює одноразовий режим спостереження. Після того, як подія готовності для дескриптора була повернута викликом `epoll_wait()`, ядро автоматично вимикає спостереження за цим дескриптором. Щоб отримати наступні сповіщення, програма мусить явно переактивувати дескриптор через `epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &ev)`. Запобігає гонитвам у пулах робочих потоків. (З ядра Linux 2.6.2). |
| **`EPOLLEXCLUSIVE`** | **Ексклюзивне пробудження проти проблеми «здичавілого стада» (Thundering Herd)**. Коли кілька процесів або робочих потоків додають один і той самий дескриптор (типово, слухаючий TCP-сокет) у власні екземпляри `epoll`, надходження нового з'єднання без цього прапорця розбудить **усі** процеси одночасно. Кожен процес прокинеться, викличе `accept4()`, але лише один успішно забере клієнта, тоді як решта марно витратять такт CPU і отримають `EAGAIN`. Прапорець `EPOLLEXCLUSIVE` встановлює біт `WQ_FLAG_EXCLUSIVE` у структурі черги очікування ядра `wait_queue_entry`. Під час надходження події ядро розбудить **рівно один** екземпляр `epoll` зі списку очікування, розподіляючи нові з'єднання між робочими процесами. Прапорець підтримується лише для операції `EPOLL_CTL_ADD` і не може комбінуватися з `EPOLLET`. (З ядра Linux 4.5). |
| **`EPOLLWAKEUP`** | Запобігає переходу системи в режим сну (System Suspend), якщо в черзі `epoll` є необроблені події. Вимагає привілею `CAP_BLOCK_SUSPEND`. (З ядра Linux 3.5). |

## 5. Вкладені екземпляри: Cascading epoll

Екземпляр `epoll` сам є файловим дескриптором VFS, що реалізує метод операцій `.poll`. Це означає, що один дескриптор `epoll` може бути зареєстрований всередині іншого екземпляра `epoll` через `epoll_ctl(epfd_master, EPOLL_CTL_ADD, epfd_worker, &ev)`.

Цей патерн називають **каскадним epoll** (Cascading epoll). Він використовується у високонавантажених серверах для побудови ієрархічних циклів подій: головний потік моніторить готовність кількох підпорядкованих екземплярів `epoll`.

### Правила та обмеження вкладеності:
1. **Захист від циклів (`ELOOP`):** Ядро Linux виконує перевірку графа залежностей за допомогою функції `ep_loop_check()`. Спроба зареєструвати `epfd_A` в `epfd_B`, якщо `epfd_B` вже входить в `epfd_A`, негайно завершується помилкою `ELOOP`.
2. **Максимальна глибина вкладеності:** Максимальна глибина каскаду обмежена константою ядра `EP_MAX_NESTS` (зазвичай не більше 5 рівнів вкладеності), щоб запобігти вичерпанню стека ядра під час рекурсивного опитування.
3. **Особливості готовності вкладеного epoll:** Дескриптор `epfd_worker` вважається готовим до читання (`EPOLLIN`) всередині `epfd_master` тоді й лише тоді, коли у його власному списку `rdllist` є хоча б одна готова подія.

## 6. Багатопотокова синхронізація та внутрішні блокування ядра

Підсистема `epoll` спроєктована для безпечного багатопотокового використання. Кілька потоків можуть одночасно викликати системні виклики над одним екземпляром `epoll`:

1. **Одночасний `epoll_wait` з кількох потоків:**
   Кілька робочих потоків можуть одночасно спати у виклику `epoll_wait(epfd, ...)` на спільному екземплярі. Коли надходить подія готовності, ядро захоплює спінлок `ep->lock`, атомарно вилучає один або кілька елементів зі списку `rdllist` і будить рівно стільки потоків, скільки потрібно для обробки повернених подій.
2. **Модифікація `epoll_ctl` під час активного `epoll_wait`:**
   Якщо потік A спить усередині `epoll_wait()`, потік B може безпечно викликати `epoll_ctl(epfd, EPOLL_CTL_ADD, new_fd, &ev)` або `EPOLL_CTL_DEL`. Ядро захищає модифікацію дерева інтересів `rbr` м'ютексом `ep->mtx`. Доданий сокет миттєво підключається до системи сповіщень: якщо дані на ньому вже доступні, функція зворотного виклику розбудить потік A без затримок.
3. **Список переповнення (`ovflist`):**
   Під час копіювання списку готових подій у пам'ять простору користувача ядро звільняє спінлок `ep->lock`, щоб не блокувати апаратні переривання. Якщо в цей мікроскопічний проміжок часу на інших сокетах з'являються нові дані, функція зворотного виклику `ep_poll_callback()` додає їх у спеціальний список переповнення `ovflist`. Після завершення копіювання ядро переносить елементи з `ovflist` назад у `rdllist`, гарантуючи, що жодна подія не буде втрачена.

## 7. Підтримка типів дескрипторів: що підтримує epoll, а що ні

`epoll` працює не з усіма об'єктами віртуальної файлової системи VFS. Головна вимога: відповідний драйвер у ядрі повинен реалізовувати метод операцій `.poll` у структурі `struct file_operations`.

### Об'єкти, які підтримують epoll:
* **Мережеві сокети:** TCP, UDP, UNIX domain, raw sockets, Netlink, Bluetooth;
* **Канали:** Анонімні канали `pipe()`, іменовані канали FIFO;
* **Термінали та послідовні порти:** TTY, PTY, UART (`/dev/ttyS0`, `/dev/pts/*`);
* **Спеціальні системні дескриптори Linux:**
  * `timerfd_create()` — таймери ядра;
  * `signalfd()` — черги системних сигналів;
  * `eventfd()` — міжпотокові 64-розрядні лічильники;
  * `inotify_init1()` / `fanotify_init()` — події файлової системи;
  * `pidfd_open()` — відстеження життєвого циклу процесів;
  * `userfaultfd()` — обробка сторінкових збоїв віртуальної пам'яті у просторі користувача.

### Об'єкти, які НЕ підтримують epoll:
* **Звичайні файли на файлових системах (Ext4, XFS, Btrfs, FAT32):**
  Спроба викликати `epoll_ctl(epfd, EPOLL_CTL_ADD, file_fd, &ev)` для звичайного дискового файлу завжди негайно повертає помилку **`EPERM`** («Operation not permitted»). Дискові файли у традиційній моделі POSIX вважаються завжди готовими до читання або запису, навіть якщо операція блокує потік на час звернення до NVMe/SATA контролера. Для справжнього асинхронного вводу-виводу на файлах у Linux використовують підсистему `io_uring`.
* **Каталоги (Directory descriptors):** Виклик `open(path, O_DIRECTORY)` повертає дескриптор, який не підтримує додавання в `epoll` і повертає `EPERM`.

## 9. Внутрішня модель пам'яті: поведінка при `fork()`, `dup()` та закритті дескрипторів

Механіка `epoll` у ядрі базується на принциповій різниці між **файловим дескриптором процесу** (індексом у таблиці дескрипторів) та **описом відкритого файлу** (структурою ядра `struct file`, Open File Description):

1. **`epoll` відстежує `struct file`, а не число `fd`:**
   Коли ви реєструєте дескриптор за допомогою `epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev)`, ядро зв'язує точку спостереження безпосередньо зі структурою `struct file`, на яку вказує дескриптор у момент виклику.
2. **Поведінка при дублюванні (`dup()`, `dup2()`):**
   Якщо створити копію дескриптора через `fd2 = dup(fd)`, обидва числа (`fd` і `fd2`) посилатимуться на один і той самий опис `struct file`. Події на цьому сокеті генеруватимуть одне спільне сповіщення. Спроба додати `fd2` в той самий `epoll` завершиться помилкою `EEXIST`.
3. **Автоматичне припинення спостереження при `close()`:**
   Дескриптор автоматично видаляється з червоно-чорного дерева `epoll` **лише тоді, коли закрито останній дескриптор у системі, що посилався на відповідну структуру `struct file`**. Якщо дескриптор було дубльовано (`dup`) або скопійовано у дочірній процес через `fork()`, закриття `close(fd)` у батьківському процесі **НЕ видалить** об'єкт із `epoll`, оскільки лічильник посилань `file->f_count` залишається більшим за нуль. Рекомендовано явно викликати `epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL)` перед викликом `close(fd)`.

## 10. Системні ліміти ядра та конфігурація

Керування ресурсами підсистеми `epoll` здійснюється через файли віртуальної файлової системи `/proc/sys/fs/epoll/`:

* **/proc/sys/fs/epoll/max_user_watches** — визначає максимальну сумарну кількість файлових дескрипторів, яку один реальний користувач (UID) може зареєструвати у всіх своїх екземплярах `epoll` у системі.
  * У 64-розрядних системах кожне спостереження споживає близько 160 байтів пам'яті ядра (`struct epitem` + `struct eppoll_entry`).
  * Для сервера, що обслуговує 1 000 000 одночасних підключень, структури `epoll` потребують приблизно:
    ```
    1 000 000 × 160 байтів ≈ 160 000 000 байтів ≈ 152.6 МБ оперативної пам'яті ядра
    ```
  * Для налаштування сервера під навантаження мільйонів з'єднань ліміти збільшують у файлі конфігурації `/etc/sysctl.conf`:
    ```ini
    # Збільшення ліміту точок спостереження epoll
    fs.epoll.max_user_watches = 4194304

    # Збільшення загальносистемного ліміту відкритих дескрипторів
    fs.file-max = 2097152
    ```
  * Після редагування зміни застосовують командою `sysctl -p`.

## 11. Діагностика стану epoll через procfs

Стан будь-якого екземпляра `epoll` у працюючому процесі можна переглянути через віртуальну файлову систему `/proc`:

```bash
# Знайти всі дескриптори epoll процесу з PID 1234
ls -l /proc/1234/fd/ | grep anon_inode:\[eventpoll\]

# Переглянути список зареєстрованих дескрипторів та маски подій
cat /proc/1234/fdinfo/3
```

Файл `fdinfo` містить інформацію про кожен зареєстрований дескриптор:
```
pos:    0
flags:  02000002
mnt_id: 15
ino:    11422
tfd:        4 events:       19 data:                4 pos:0 ino:14251 sdev:8
tfd:        5 events:       19 data:  7ffd823410a0 pos:0 ino:14252 sdev:8
```
* `tfd` — номер цільового файлового дескриптора (Target File Descriptor);
* `events` — шістнадцяткова маска зареєстрованих подій (`0x19` = `EPOLLIN | EPOLLERR | EPOLLHUP`);
* `data` — збережене значення `epoll_data_t` (число дескриптора або 64-розрядна адреса покажчика).

## 12. Еволюційний перехід: від моделі готовності epoll до моделі завершення io_uring

Підсистема `epoll` залишається золотим промисловим стандартом синхронного мультиплексування дескрипторів у Linux понад два десятиліття. Проте фундаментальна модель `epoll` базується на **сповіщенні про готовність (Readiness Notification)**:
1. `epoll_wait()` сповіщає: «сокет готовий до читання»;
2. Програма виконує окремий системний виклик `read()`, копіюючи байти з ядра в простір користувача.

Ця двокрокова схема вимагає щонайменше двох системних викликів на кожну транзакцію даних. При переході до швидкостей 100 Гбіт/с та мільйонів операцій на секунду накладні витрати переходів ядра через Spectre/Meltdown бар'єри (Retpoline) спонукали до появи підсистеми `io_uring` (автор — Єнс Аксбо, 2019 рік). 

На відміну від `epoll`, `io_uring` реалізує **модель завершення (Completion-based I/O)** на основі двох кільцевих буферів у спільній пам'яті (Submission Queue та Completion Queue). Програма відправляє запит на читання без системного виклику, а ядро самостійно копіює дані та повертає готовий результат. Розуміння контракту та механізмів `epoll` є обов'язковим фундаментом перед вивченням `io_uring`, оскільки обидва інструменти доповнюють один одного в архітектурі сучасного Linux.
