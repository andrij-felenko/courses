# 📋 Довідник системних інтерфейсів Zero-Copy та io_uring

Цей довідник містить точні сигнатури системних викликів, структуру керуючих дескрипторів, бітові маски прапорців, правила узгодження пам'яті та коди помилок для технологій прямої передачі даних у ядрі Linux. Без точного знання цих низькорівневих контрактів неможливо коректно налаштувати безкопійні конвеєри через `sendfile`, `splice`, векторний ввід-вивід `readv`/`writev` та кільцеві структури спільної пам'яті `io_uring`.

## 1. Системний виклик `sendfile`

Виконує пряму передачу даних між файловим дескриптором джерела та дескриптором приймача (зазвичай мережевим сокетом) без проходження байтів крізь адресний простір користувача.

```c
#include <sys/sendfile.h>

ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
```

### Параметри та семантика аргументів

| Параметр | Тип | Опис та правила використання |
| :--- | :--- | :--- |
| `out_fd` | `int` | Дескриптор призначення. До версії ядра Linux 2.6.33 мав обов'язково бути мережевим сокетом. Починаючи з 2.6.33, може бути будь-яким файлом, відкритим на запис. |
| `in_fd` | `int` | Дескриптор джерела. Мусить підтримувати операцію позиціонування (`mmap`-сумісний регулярний файл або блоковий пристрій). Не може бути сокетом або каналом `pipe`. |
| `offset` | `off_t*` | Покажчик на змінну зміщення у файлі джерела. Якщо `NULL`, читання починається з поточного файлового зміщення `f_pos` дескриптора `in_fd`, і після виклику `f_pos` автоматично збільшується. Якщо передано адресу, читання починається зі значення `*offset`, після виклику `*offset` оновлюється, а позиція `in_fd` залишається незмінною. |
| `count` | `size_t` | Максимальна кількість байтів для передачі за один виклик. Ядро обмежує розмір одного виклику значенням `0x7ffff000` (2 ГБ мінус 4 КіБ). |

### Значення, що повертаються, та коди помилок

* **Успіх:** Кількість фактично записаних байтів (`> 0`). Значення `0` означає досягнення кінця файлу (EOF) у джерелі `in_fd`.
* **Помилка:** Повертається `-1`, а глобальна змінна `errno` встановлюється у відповідний код:
  * `EAGAIN` / `EWOULDBLOCK` — дескриптор `out_fd` позначено як неблокуючий (`O_NONBLOCK`), і буфер передачі сокета заповнений.
  * `EBADF` — дескриптор `in_fd` не відкритий на читання або `out_fd` не відкритий на запис.
  * `EINVAL` — дескриптор `in_fd` не підтримує операції типу `sendfile` (наприклад, є сокетом), або `out_fd` відкрито з прапорцем `O_APPEND`.
  * `EIO` — сталася низькорівнева апаратна помилка читання з файлової системи.
  * `ENOMEM` — недостатньо оперативної пам'яті ядра для створення структур мережевих пакетів `sk_buff`.

### Механізм роботи з мережевими сокетами та прапорець `TCP_CORK`

При передачі файлу через TCP-сокет за допомогою `sendfile` виникає проблема розділення службового HTTP-заголовка та тіла файлу. Якщо спочатку викликати `write()` для відправки заголовків, а потім `sendfile()` для передачі тіла, стек TCP надішле два окремі мережеві сегменти, створюючи зайві накладні витрати на заголовки IP/TCP.

Для об'єднання заголовків і тіла файлу в один повнорозмірний TCP-кадр (MTU 1500) використовують прапорець сокета `TCP_CORK`:
1. Перед відправкою програма встановлює опцію `setsockopt(sock, IPPROTO_TCP, TCP_CORK, &val, sizeof(val))` зі значенням `val = 1`. Це змушує ядро накопичувати всі вихідні байти в буфері сокета без негайної відправки.
2. Програма викликає звичайний `write()` або `writev()` для запису текстових заголовків відповіді.
3. Програма викликає `sendfile()` для передачі файлових блоків безпосередньо з кешу сторінок ядра.
4. Програма скидає стан затору, вимикаючи опцію `TCP_CORK` (`val = 0`), після чого ядро миттєво відправляє сформований повнорозмірний мережевий кадр.

## 2. Системні виклики сімейства `splice`: `splice`, `vmsplice`, `tee`

Сімейство системних викликів `splice` забезпечує універсальну інфраструктуру маршрутизації даних у просторі ядра між довільними дескрипторами без залучення буферів користувача.

### Сигнатура системного виклику `splice`

Переміщує дані між двома файловими дескрипторами через переприв'язку фізичних сторінок пам'яті (`struct page*`) у ядрі. Хоча б один із двох дескрипторів **зобов'язаний бути каналом (`pipe`)**.

```c
#include <fcntl.h>
#include <unistd.h>

ssize_t splice(int fd_in, loff_t *off_in, int fd_out, loff_t *off_out,
               size_t len, unsigned int flags);
```

### Прапорці керування поведінкою `flags`

| Прапорець | Числове значення | Семантика в ядрі Linux |
| :--- | :--- | :--- |
| `SPLICE_F_MOVE` | `0x01` | Спроба перемістити фізичні сторінки пам'яті замість копіювання посилань. Історичний оптимізаційний прапорець (у сучасних ядрах є підказкою). |
| `SPLICE_F_NONBLOCK` | `0x02` | Не блокувати виконання при відсутності даних у `fd_in` або відсутності вільного місця у `fd_out`. Виклик завершується з помилкою `EAGAIN`. |
| `SPLICE_F_MORE` | `0x04` | Підказка ядру, що невдовзі надійде наступна порція даних. Для сокетів транслюється у прапорець `MSG_MORE` протоколу TCP, затримуючи відправку дрібних пакетів (алгоритм Нейгла). |
| `SPLICE_F_GIFT` | `0x08` | Повідомляє ядру, що сторінки пам'яті користувача передаються у власність ядра безповоротно (використовується спільно з `vmsplice`). |

### Системний виклик `vmsplice` — відображення пам'яті користувача в канал

```c
#include <fcntl.h>
#include <sys/uio.h>

ssize_t vmsplice(int fd, const struct iovec *iov, unsigned long nr_segs,
                 unsigned int flags);
```

* **Призначення:** Якщо `fd` відкрито на запис у канал, виклик фіксує фізичні сторінки користувача, вказані масивом векторів `iov`, і підставляє їх у кільцевий буфер `pipe_buffer` без копіювання байтів. Якщо `fd` відкрито на читання з каналу, виклик вивантажує дані з каналу у буфери користувача.
* **Семантика володіння пам'яттю:** За замовчуванням пам'ять користувача захищена семантикою Copy-on-Write (COW). Якщо застосунок змінює дані в буфері після виклику `vmsplice` без прапорця `SPLICE_F_GIFT`, ядро автоматично створює дублікат сторінки. Якщо встановлено `SPLICE_F_GIFT`, користувацький процес зобов'язується ніколи не модифікувати сторінки, передані у конвеєр.

### Системний виклик `tee` — дублювання потоків у ядрі

```c
#include <fcntl.h>

ssize_t tee(int fd_in, int fd_out, size_t len, unsigned int flags);
```

* **Призначення:** Дублює до `len` байтів даних з каналу `fd_in` у канал `fd_out` без вилучення їх із вхідного каналу і без копіювання в простір користувача. Обидва дескриптори мають бути каналами (`pipe`). Операція збільшує лічильники посилань сторінок `page_ref_inc()` у кільцевих буферах обох каналів.

## 3. Векторний ввід-вивід: `readv`, `writev`, `preadv2`, `pwritev2`

Векторний ввід-вивід (Scatter-Gather I/O) дозволяє зчитувати дані у кілька розрізнених буферів пам'яті або відправляти дані з кількох буферів за один атомарний системний виклик, гарантуючи збереження порядку та цілісності передачі.

```c
#include <sys/uio.h>

struct iovec {
    void  *iov_base;    /* Початкова адреса буфера в пам'яті */
    size_t iov_len;     /* Довжина буфера в байтах */
};

ssize_t readv(int fd, const struct iovec *iov, int iovcnt);
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);

ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                 off_t offset, int flags);
```

### Обмеження ядра на розмір масиву `iovec`

Ядро Linux накладає суворе обмеження на максимальну кількість елементів у масиві векторів — константу `UIO_MAXIOV`, яка визначена у файлі `<linux/uio.h>` і за замовчуванням дорівнює `1024`.

Якщо застосунок передає значення `iovcnt > UIO_MAXIOV` або `iovcnt < 0`, виклики миттєво повертають помилку `-1` зі значенням `errno = EINVAL`. Крім того, сума довжин усіх сегментів `iov[i].iov_len` не може перевищувати максимальне значення типу `ssize_t` (`SSIZE_MAX`), інакше виклик також завершується з помилкою `EINVAL`.

### Прапорці розширеного інтерфейсу `flags` (для `preadv2` / `pwritev2`)

| Прапорець | Опис дії в підсистемі ядра |
| :--- | :--- |
| `RWF_HIPRI` | Запит на високопріоритетне асинхронне опитування (High-priority polling). Використовується для накопичувачів NVMe з підтримкою опитування черг без апаратних переривань. |
| `RWF_DSYNC` | Еквівалент відкриття файлу з прапорцем `O_DSYNC`. Запис завершується лише після скидання даних на постійний носій. |
| `RWF_SYNC` | Еквівалент відкриття з `O_SYNC`. Запис скидає як дані, так і оновлені метадані вузла `inode`. |
| `RWF_NOWAIT` | Не переходити в блокування, якщо дані відсутні в кеші сторінок або для запису потрібне виділення нових дискових блоків. Миттєво повертає помилку `EAGAIN`. |
| `RWF_APPEND` | Встановлює позицію запису в кінець файлу незалежно від значення аргументу `offset`. |

## 4. Системний інтерфейс `io_uring`

Архітектура `io_uring` базується на двох спільних кільцевих буферах пам'яті: черзі надсилання завдань (Submission Queue, SQ) та черзі фіксації результатів (Completion Queue, CQ).

### Первинні системні виклики ядра

```c
#include <linux/io_uring.h>
#include <sys/syscall.h>
#include <unistd.h>

int io_uring_setup(u32 entries, struct io_uring_params *p);
int io_uring_enter(unsigned int fd, unsigned int to_submit,
                   unsigned int min_complete, unsigned int flags,
                   sigset_t *sig);
int io_uring_register(unsigned int fd, unsigned int opcode,
                      void *arg, unsigned int nr_args);
```

### Структура параметрів ініціалізації `struct io_uring_params`

```c
struct io_uring_params {
    __u32 sq_entries;         /* Розмір черги надсилання (повертає ядро) */
    __u32 cq_entries;         /* Розмір черги завершення (зазвичай 2 * sq_entries) */
    __u32 flags;              /* Прапорці конфігурації рушія (IORING_SETUP_*) */
    __u32 sq_thread_cpu;      /* Номер процесорного ядра для потоку SQPOLL */
    __u32 sq_thread_idle;     /* Час простою потоку ядра в мс до засинання */
    __u32 features;           /* Бітова маска підтримуваних функцій ядра */
    __u32 wq_fd;              /* Дескриптор існуючого екземпляра для об'єднання пулу */
    __u32 resv[3];            /* Зарезервовані поля */
    struct io_sqring_offsets sq_off; /* Зміщення полів SQ для виклику mmap */
    struct io_cqring_offsets cq_off; /* Зміщення полів CQ для виклику mmap */
};
```

### Основні прапорці налаштування `io_uring_setup`

* `IORING_SETUP_IOPOLL` — Використовувати апаратне опитування стану драйвера замість переривань (IO Polling). Знижує затримку доступу до NVMe до субмікросекундного рівня.
* `IORING_SETUP_SQPOLL` — Створити виділений потік ядра (`io_uring-sq`), який самостійно опитує чергу SQ в пам'яті. Дозволяє відправляти операції вводу-виводу взагалі **без системних викликів `io_uring_enter`**.
* `IORING_SETUP_SQ_AFF` — Прив'язати ядерний потік `SQPOLL` до конкретного процесорного ядра, вказаного в полі `sq_thread_cpu`.
* `IORING_SETUP_CQSIZE` — Встановити спеціальний розмір черги CQ (передається в полі `cq_entries`).
* `IORING_SETUP_CLAMP` — Автоматично зменшити розмір черги до допустимого максимуму ядра замість помилки `EINVAL`.

## 5. Формат записів черг: `io_uring_sqe` та `io_uring_cqe`

### Елемент черги надсилання (Submission Queue Entry, SQE)

Кожен елемент SQE має фіксований розмір 64 байти та описує окрему операцію вводу-виводу:

```c
struct io_uring_sqe {
    __u8   opcode;        /* Код операції (IORING_OP_*) */
    __u8   flags;         /* Прапорці поведінки операції (IOSQE_*) */
    __u16  ioprio;        /* Пріоритет вводу-виводу (IOPRIO_PRIO_VALUE) */
    __s32  fd;            /* Файловий дескриптор або індекс фіксованого файлу */
    union {
        __u64  off;       /* Зміщення у файлі (offset) */
        __u64  addr2;     /* Додаткова адреса для операцій типу splice */
    };
    union {
        __u64  addr;      /* Покажчик на буфер або масив struct iovec */
        __u64  splice_off_in;
    };
    __u32  len;           /* Довжина буфера або кількість векторів iovec */
    union {
        __kernel_rwf_t  rw_flags;     /* Прапорці RWF_* для читання/запису */
        __u32           fsync_flags;  /* Прапорці IORING_FSYNC_* */
        __u16           buf_index;    /* Індекс зареєстрованого буфера */
        __u16           buf_group;    /* Група автоматично виділених буферів */
    };
    __u64  user_data;     /* 64-бітний ідентифікатор запиту користувача */
    union {
        struct {
            __u16  buf_index;  /* Індекс буфера */
            __u16  personality;/* Ідентифікатор прав доступу credentials */
            __s32  splice_fd_in;
        };
        __u8   pad2[24];  /* Доповнення структури до 64 байтів */
    };
};
```

### Найважливіші коди операцій `opcode` (IORING_OP_*)

| Опкод | Число | Призначення операції |
| :--- | :--- | :--- |
| `IORING_OP_READV` | 1 | Векторне читання з дескриптора (аналог `preadv`) |
| `IORING_OP_WRITEV` | 2 | Векторний запис у дескриптор (аналог `pwritev`) |
| `IORING_OP_FSYNC` | 3 | Скидання кешів файлу на носій (аналог `fsync`) |
| `IORING_OP_READ_FIXED` | 4 | Читання у попередньо зафіксований буфер без трансляції GUP |
| `IORING_OP_WRITE_FIXED` | 5 | Запис із попередньо зафіксованого буфера ядра |
| `IORING_OP_POLL_ADD` | 6 | Реєстрація подій готовності сокета (аналог `epoll_ctl`) |
| `IORING_OP_SENDMSG` | 9 | Відправка мережевого повідомлення (аналог `sendmsg`) |
| `IORING_OP_RECVMSG` | 10 | Прийом мережевого повідомлення (аналог `recvmsg`) |
| `IORING_OP_SPLICE` | 14 | Нуль-копійне переміщення даних між дескрипторами |
| `IORING_OP_PROVIDE_BUFFERS` | 31 | Надання пулу готових буферів для автоматичного вибору ядром |
| `IORING_OP_SEND_ZC` | 47 | Асинхронна безкопійна мережева відправка (Zero-Copy Send) |

### Прапорці зв'язування та поведінки SQE (`flags`)

* `IOSQE_IO_LINK` — Створює жорсткий зв'язок між поточним SQE та наступним у черзі. Наступна операція почне виконуватися **лише після успішного завершення поточної**. Якщо поточна операція завершується з помилкою, весь ланцюжок переривається з кодом `-ECANCELED`.
* `IOSQE_IO_DRAIN` — Затримує виконання цього SQE доти, доки **всі попередні операції** у черзі не будуть повністю завершені.
* `IOSQE_ASYNC` — Примусово передати виконання операції асинхронному пулу воркерів ядра (`io-wq`), навіть якщо ядро вважає операцію неблокуючою.
* `IOSQE_FIXED_FILE` — Вказує, що поле `fd` містить не системний дескриптор, а індекс у внутрішній таблиці файлів, зареєстрованій через `io_uring_register`.

### Елемент черги завершення (Completion Queue Entry, CQE)

Кожен елемент CQE має розмір 16 байтів та повертає результат виконаної операції:

```c
struct io_uring_cqe {
    __u64  user_data; /* Значення user_data, передане у відповідному SQE */
    __s32  res;       /* Результат операції (байти або від'ємний код помилки -errno) */
    __u32  flags;     /* Прапорці результату (наприклад, IORING_CQE_F_MORE) */
};
```

## 6. Механіка узгодження пам'яті в кільцях: Head, Tail та Memory Barriers

Кільця SQ та CQ є lock-free структурами даних формату Single-Producer Single-Consumer (SPSC).
* Для черги SQ: простір користувача є єдиним виробником (Producer), який пересуває покажчик `sq_ring->tail`, а ядро є споживачем (Consumer), який пересуває покажчик `sq_ring->head`.
* Для черги CQ: ядро є виробником, який пересуває `cq_ring->tail`, а простір користувача є споживачем, який оновлює `cq_ring->head`.

### Розрахунок індексу та маскування

Розмір кільця `entries` завжди є степенем двійки (наприклад, 64, 128, 512). Щоб знайти позицію елемента в масиві без виконання дорогої операції ділення або взяття залишку, використовують порозрядне маскування:

```
ring_mask = entries - 1
index = tail & ring_mask
```

Покажчики `head` та `tail` монотонно зростають і можуть вільно переповнюватися в межах 32-бітного типу без втрати коректності обчислень.

### Бар'єри пам'яті (Memory Barriers)

Оскільки процесор може перевпорядковувати інструкції запису в пам'ять (Out-of-Order Execution), обов'язковим є дотримання семантики Acquire/Release:

1. **Запис у SQE:** Програма заповнює поля структури `io_uring_sqe`, після чого виконує запис індексу в масив індирекції `sqring->array[index]`.
2. **Публікація покажчика:** Збільшення `sq_ring->tail` виконується виключно через операцію `smp_store_release` (або `atomic_store_explicit(..., memory_order_release)`), щоб гарантувати, що всі дані самого SQE фізично видимі в кеші процесора до того, як ядро побачить оновлений `tail`.
3. **Читання з CQE:** Програма перевіряє умову наявності готових подій `head != tail`, зчитуючи `cq_ring->tail` через операцію `smp_load_acquire` (або `atomic_load_explicit(..., memory_order_acquire)`).

## 7. Операції реєстрації ресурсів `io_uring_register`

Дозволяють усунути повторювані накладні витрати ядра на валідацію дескрипторів та трансляцію віртуальних адрес.

### Реєстрація фіксованих буферів (`IORING_REGISTER_BUFFERS`)

Програма одноразово блокує фізичні сторінки пам'яті в RAM (`pin_user_pages`), передаючи масив структур `iovec`:

```c
struct iovec iov[4];
/* Ініціалізація буферів */
int ret = io_uring_register(ring_fd, IORING_REGISTER_BUFFERS, iov, 4);
```

Після цього операції `IORING_OP_READ_FIXED` та `IORING_OP_WRITE_FIXED` посилаються на номер буфера через поле `sqe->buf_index`, повністю усуваючи роботу підсистеми MMU при кожному запиті.

### Реєстрація фіксованих файлів (`IORING_REGISTER_FILES`)

Ядро створює внутрішній масив вказівників `struct file*`, оминаючи звернення до таблиці дескрипторів процесу (`files_struct`) та захоплення блокувань списку відкритих файлів при кожному зверненні.

## 8. Високорівнева бібліотека `liburing`

Для усунення необхідності ручного виклику `mmap` та обчислення зміщень використовують бібліотеку `liburing` авторства Єнса Аксбо (Jens Axboe).

### Ключові функції життєвого циклу `liburing`

```c
#include <liburing.h>

/* Ініціалізація та знищення кільця */
int io_uring_queue_init(unsigned entries, struct io_uring *ring, unsigned flags);
void io_uring_queue_exit(struct io_uring *ring);

/* Отримання вільного слота в SQ */
struct io_uring_sqe *io_uring_get_sqe(struct io_uring *ring);

/* Підготовка операцій (хелпери ініціалізації полів SQE) */
void io_uring_prep_readv(struct io_uring_sqe *sqe, int fd,
                         const struct iovec *iovecs, unsigned nr_vecs, off_t offset);
void io_uring_prep_writev(struct io_uring_sqe *sqe, int fd,
                          const struct iovec *iovecs, unsigned nr_vecs, off_t offset);
void io_uring_prep_send(struct io_uring_sqe *sqe, int sockfd,
                        const void *buf, size_t len, int flags);
void io_uring_prep_recv(struct io_uring_sqe *sqe, int sockfd,
                        void *buf, size_t len, int flags);
void io_uring_prep_splice(struct io_uring_sqe *sqe, int fd_in, int64_t off_in,
                          int fd_out, int64_t off_out, unsigned int nbytes,
                          unsigned int splice_flags);

/* Відправка завдань ядру */
int io_uring_submit(struct io_uring *ring);
int io_uring_submit_and_wait(struct io_uring *ring, unsigned wait_nr);

/* Обробка результатів CQE */
int io_uring_peek_cqe(struct io_uring *ring, struct io_uring_cqe **cqe_ptr);
int io_uring_wait_cqe(struct io_uring *ring, struct io_uring_cqe **cqe_ptr);
void io_uring_cqe_seen(struct io_uring *ring, struct io_uring_cqe *cqe);
```

### Правила роботи з CQE у циклі подій

1. Програма отримує завершену подію через `io_uring_peek_cqe` (неблокуюче опитування) або `io_uring_wait_cqe` (очікування прибуття події).
2. Застосунок перевіряє код повернення у полі `cqe->res`. Якщо `cqe->res < 0`, сталася помилка, і значення є від'ємним кодом помилки системи (наприклад, `-EAGAIN`, `-EPIPE`). Якщо `cqe->res >= 0`, значення показує кількість фактично прочитаних або записаних байтів.
3. Застосунок знаходить контекст операції через поле `cqe->user_data`, яке було передано в момент створення SQE.
4. **Обов'язковий фінальний крок:** Програма зобов'язана викликати `io_uring_cqe_seen(ring, cqe)`, щоб сповістити ядро про звільнення слота в кільці CQ. Пропуск цього виклику призведе до переповнення кільця CQ та зупинки надходження нових подій.

## 9. Діагностика, крайові випадки та системні обмеження

### Обмеження пам'яті `RLIMIT_MEMLOCK`

При ініціалізації великих кілець або виклику `IORING_REGISTER_BUFFERS` ядро виділяє зафіксовану пам'ять, яка не може бути вивантажена у файл підкачки (swap). Ця пам'ять підлягає жорсткому ліміту `RLIMIT_MEMLOCK`. Якщо ліміт перевищено, системні виклики завершуються з помилкою `ENOMEM` або `EPERM`.

Для налаштування системного ліміту у файлі `/etc/security/limits.conf` додають запис:
```
* soft memlock unlimited
* hard memlock unlimited
```

### Фільтрація системних викликів через Seccomp

У контейнерних середовищах (Docker, Kubernetes) старі профілі безпеки Seccomp блокують виклики `io_uring_setup` з кодом `EPERM` або `EACCES` з міркувань ізоляції ядра. Будь-яка надійна системна бібліотека зобов'язана реалізовувати механізм автоматичного повернення (Graceful Fallback) на класичні виклики `epoll` та `preadv`/`pwritev`, якщо `io_uring_setup` повертає помилку заборони доступу.

### Крайові випадки при роботі з каналами та мережею

* **Обробка `EPIPE` та `SIGPIPE`:** При використанні `splice` або `sendfile` у мережевий сокет, якщо віддалений клієнт раптово закриває TCP-з'єднання під час передачі, ядро генерує сигнал `SIGPIPE`. За замовчуванням це призводить до аварійного завершення процесу. Серверні застосунки зобов'язані або блокувати цей сигнал через `signal(SIGPIPE, SIG_IGN)`, або передавати прапорець `MSG_NOSIGNAL`.
* **Короткий запис (Short Write):** Виклики `sendfile`, `splice` та `io_uring_prep_send` не гарантують передачу всього запитаного обсягу байтів за один крок, якщо вихідний буфер сокета частково заповнений. Програма зобов'язана зберігати поточне зміщення і повторювати передачу залишку даних у наступних ітераціях.

## 10. Простеження та діагностика вводу-виводу: ftrace, bpftrace та perf

Для точного вимірювання накладних витрат у просторі ядра та спостереження за поведінкою черг використовують динамічні інструменти трасування Linux.

### Точки трасування ядра (Static Tracepoints)

Підсистема ядра надає готові точки трасування для моніторингу подій життєвого циклу запитів:

| Точка трасування (Tracepoint) | Призначення | Ключові параметри події |
| :--- | :--- | :--- |
| `syscalls:sys_enter_sendfile64` | Фіксація входу у виклик `sendfile` | `out_fd`, `in_fd`, `count`, `offset` |
| `syscalls:sys_enter_splice` | Фіксація початку переміщення через `splice` | `fd_in`, `fd_out`, `len`, `flags` |
| `io_uring:io_uring_submit_req` | Додавання запиту SQE у чергу виконання | `ctx`, `opcode`, `user_data`, `flags` |
| `io_uring:io_uring_complete` | Завершення операції та формування CQE | `ctx`, `user_data`, `res`, `cflags` |
| `io_uring:io_uring_poll_arm` | Постановка сокета на асинхронне опитування | `ctx`, `req`, `mask`, `events` |

### Практичні однорядкові скрипти bpftrace для діагностики

1. **Побудова гістограми розмірів батчу при викликах `io_uring_enter`:**
   Дозволяє перевірити, чи ефективно застосунок пакетує операції перед зверненням до ядра:
   ```sh
   bpftrace -e 'tracepoint:syscalls:sys_enter_io_uring_enter { @batch_size = hist(args->to_submit); }'
   ```

2. **Вимірювання затримки виконання операцій `sendfile` у мікросекундах:**
   ```sh
   bpftrace -e '
     tracepoint:syscalls:sys_enter_sendfile64 { @start[tid] = nsecs; }
     tracepoint:syscalls:sys_exit_sendfile64 /@start[tid]/ {
       @latency_us = hist((nsecs - @start[tid]) / 1000);
       delete(@start[tid]);
     }'
   ```

3. **Підрахунок кількості виконаних операцій за опкодами в `io_uring`:**
   ```sh
   bpftrace -e 'tracepoint:io_uring:io_uring_submit_req { @opcodes[args->opcode] = count(); }'
   ```

## 11. Еволюція функціональності та динамічна перевірка можливостей ядра

Підсистема `io_uring` розвивається з кожним релізом ядра Linux. Щоб програма зберігала переносимість і стабільно працювала як на старіших дистрибутивах (наприклад, Ubuntu 20.04 LTS з ядром 5.4), так і на сучасних серверах (ядра 6.x), архітектура передбачає динамічну перевірку підтримуваних функцій через поле `params.features`.

### Бітові маски підтримки функцій ядра (`IORING_FEAT_*`)

Після успішного виклику `io_uring_setup()` ядро заповнює поле `params.features` набором прапорців:

| Прапорець можливості | Версія ядра | Значення та архітектурний вплив |
| :--- | :--- | :--- |
| `IORING_FEAT_SINGLE_MMAP` | Linux 5.4+ | Черги SQ та CQ відображаються одним спільним викликом `mmap` замість двох окремих, знижуючи накладні витрати на ініціалізацію. |
| `IORING_FEAT_NODROP` | Linux 5.5+ | Ядро гарантує, що події завершення CQE ніколи не будуть відкинуті при переповненні черги, а тимчасово затримані у внутрішньому беклозі. |
| `IORING_FEAT_SUBMIT_STABLE` | Linux 5.5+ | Буфери даних, передані у виклики запису, копіюються ядром у стабільний стан, що дозволяє безпечно перезаписувати буфер користувача одразу після відправки. |
| `IORING_FEAT_FAST_POLL` | Linux 5.7+ | Автоматична інтеграція неблокуючого вводу-виводу: ядро спочатку пробує виконати операцію негайно, і лише при поверненні `EAGAIN` автоматично вішає внутрішній поллінг. |
| `IORING_FEAT_POLL_32BITS` | Linux 5.9+ | Повна 32-бітна підтримка масок подій `epoll` у внутрішньому механізмі опитування. |
| `IORING_FEAT_SQPOLL_NONFIXED` | Linux 5.11+ | Дозволяє потоку `SQPOLL` працювати зі звичайними дескрипторами без обов'язкової попередньої реєстрації через `IORING_REGISTER_FILES`. |

## 12. Шаблони побудови нуль-копійних проксі-серверів на базі splice

Класичний двонаправлений проксі-сервер (наприклад, TCP-балансувальник навантаження) пересилає трафік між сокетом клієнта `client_fd` та сокетом сервера `backend_fd`.

Замість читання байтів у проміжний буфер процесу через `read()` і наступного виклику `write()`, проксі створює два анонімні канали `pipe_c2b` (клієнт → бекенд) та `pipe_b2c` (бекенд → клієнт) і виконує передачу виключно через виклики `splice`:

1. **Читання з сокета клієнта в канал:** `splice(client_fd, NULL, pipe_c2b[1], NULL, 65536, SPLICE_F_NONBLOCK | SPLICE_F_MOVE)`
2. **Скидання з каналу в сокет бекенда:** `splice(pipe_c2b[0], NULL, backend_fd, NULL, len, SPLICE_F_NONBLOCK | SPLICE_F_MORE)`

Для оптимізації пропускної здатності розмір проміжного каналу налаштовують за допомогою виклику `fcntl(pipe_fd, F_SETPIPE_SZ, size)`. За замовчуванням місткість каналу становить 64 КіБ (16 сторінок по 4 КіБ). Збільшення місткості до 1 Мегабайта (256 сторінок) дозволяє конвеєру поглинати великі сплески трафіку від високошвидкісних мережевих інтерфейсів без переходу в стан блокування `EAGAIN` та скорочує кількість системних викликів `splice` у 16 разів при передачі об'ємних потоків.

Така схема дозволяє процесу проксі працювати з нульовим навантаженням на кеш процесора (L1/L3 Cache Pollution Free), повністю передаючи відповідальність за доставку пакетів апаратному контролеру мережевої карти та механізму передачі дескрипторів сторінок ядра.
