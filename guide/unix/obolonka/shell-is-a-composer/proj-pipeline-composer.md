# ⚙️ Складання багатоступеневого конвеєра: повноцінний рушій виконання

Коли командна оболонка виконує рядок на зразок `cat /var/log/nginx/access.log | grep " 500 " | cut -d' ' -f1 | sort | uniq -c | sort -nr | head -n 10`, вона розв'язує задачу синхронізації кількох незалежних процесів, об'єднаних у спрямований граф передачі даних. Якщо хоча б один системний дескриптор буде закрито невчасно або пропущено налаштування групи процесів, конвеєр або зависне назавжди в стані взаємного блокування (deadlock), або залишить зомбі-процеси в системній таблиці, або проігнорує аварійне завершення проміжних команд.

Нижче розібрано повну інженерну реалізацію рушія конвеєрів довільної довжини, що підтримує правильне розгалуження, атомарне перепідключення потоків, ізоляцію груп процесів для керування терміналом, коректне закриття дескрипторів, обчислення статусів виходу з підтримкою семантики `pipefail`, оптимізацію пропускної здатності, коректну обробку часткових збоїв, порівняння з високорівневими мовами та автоматичне тестування на відсутність витоків ресурсів.

## Постановка задачі та інженерні вимоги

Необхідно створити універсальну системну функцію виконання конвеєра `run_pipeline()`, яка приймає масив із `N` команд, де кожна команда представлена списком аргументів (`argv`).

Рушій повинен задовольняти такі вимоги:
1. **Паралельність виконання**: усі `N` процесів мають запуститися одночасно й працювати паралельно, використовуючи природний механізм саморегуляції швидкості (backpressure) буферів каналів ядра.
2. **Відсутність витоків дескрипторів (No FD Leaks)**: усі невикористовувані дескриптори каналів повинні гарантовано закриватися як у батьківському процесі, так і в кожній дитині до виклику `execvp()`.
3. **Керування групами процесів (Job Control)**: усі процеси конвеєра повинні належати до однієї спільної групи процесів (`PGID`), лідером якої стає перший дочірній процес. Оболонка повинна безпечно передавати передній план термінала цій групі й повертати його собі після завершення.
4. **Утилізація зомбі-процесів**: батьківський процес зобов'язаний дочекатися завершення **кожного** з `N` дочірніх процесів через `waitpid()`.
5. **Збирання статусів виходу та pipefail**: функція має повертати як класичний статус виходу останньої команди конвеєра, так і статус за правилом `pipefail` (останній ненульовий код або 0, якщо всі завершилися успішно).

## Архітектурний план виконання

Процедура складання конвеєра з `N` команд розбивається на п'ять послідовних кроків:

```
Хронологічний план виконання конвеєра:
1. Виділення N-1 каналів:
   pipe2(pipes[0], O_CLOEXEC) ... pipe2(pipes[N-2], O_CLOEXEC)
2. Цикл розгалуження (i = 0 .. N-1):
   • fork()
   • Дитина i:
       setpgid(0, pgid)
       підключення stdin: якщо i > 0 -> dup2(pipes[i-1][0], 0)
       підключення stdout: якщо i < N-1 -> dup2(pipes[i][1], 1)
       закриття всіх інших дескрипторів каналів
       execvp(cmd[i].argv[0], cmd[i].argv)
   • Батько:
       фіксація pgid = child_pid для i=0
       setpgid(child_pid, pgid)
3. Закриття всіх N-1 каналів у батьківському процесі (КРИТИЧНО для EOF!)
4. Передача термінала групі конвеєра: tcsetpgrp(tty, pgid)
5. Збирання результатів waitpid() та обчислення pipefail
6. Повернення термінала оболонці: tcsetpgrp(tty, shell_pgid)
```

## Реалізація рушія конвеєрів

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <signal.h>
#include <termios.h>
#include <errno.h>

typedef struct {
    char *const *argv;
} Command;

typedef struct {
    int last_status;
    int pipefail_status;
    int *all_statuses;
    size_t count;
} PipelineResult;

PipelineResult run_pipeline(const Command *cmds, size_t num_cmds) {
    PipelineResult res = { .last_status = -1, .pipefail_status = 0, .all_statuses = NULL, .count = num_cmds };
    if (num_cmds == 0) return res;

    res.all_statuses = malloc(sizeof(int) * num_cmds);
    if (!res.all_statuses) {
        perror("malloc");
        return res;
    }

    int (*pipes)[2] = NULL;
    if (num_cmds > 1) {
        pipes = malloc(sizeof(int[2]) * (num_cmds - 1));
        if (!pipes) {
            perror("malloc pipes");
            free(res.all_statuses);
            res.all_statuses = NULL;
            return res;
        }
        for (size_t i = 0; i < num_cmds - 1; ++i) {
            if (pipe2(pipes[i], O_CLOEXEC) == -1) {
                perror("pipe2");
                for (size_t j = 0; j < i; ++j) {
                    close(pipes[j][0]);
                    close(pipes[j][1]);
                }
                free(pipes);
                free(res.all_statuses);
                res.all_statuses = NULL;
                return res;
            }
        }
    }

    pid_t *pids = malloc(sizeof(pid_t) * num_cmds);
    pid_t pgid = 0;
    int is_interactive = isatty(STDIN_FILENO);
    pid_t shell_pgid = getpgrp();

    for (size_t i = 0; i < num_cmds; ++i) {
        pid_t pid = fork();
        if (pid < 0) {
            perror("fork");
            break;
        }

        if (pid == 0) {
            // === ТІЛО ДОЧІРНЬОГО ПРОЦЕСУ ===
            pid_t cur_pid = getpid();
            pid_t target_pgid = (i == 0) ? cur_pid : pgid;
            setpgid(0, target_pgid);

            if (i > 0) {
                if (dup2(pipes[i - 1][0], STDIN_FILENO) == -1) {
                    perror("dup2 stdin");
                    _exit(127);
                }
            }

            if (i < num_cmds - 1) {
                if (dup2(pipes[i][1], STDOUT_FILENO) == -1) {
                    perror("dup2 stdout");
                    _exit(127);
                }
            }

            if (num_cmds > 1) {
                for (size_t j = 0; j < num_cmds - 1; ++j) {
                    close(pipes[j][0]);
                    close(pipes[j][1]);
                }
            }

            execvp(cmds[i].argv[0], cmds[i].argv);
            perror("execvp");
            _exit(127);
        }

        // === ТІЛО БАТЬКІВСЬКОГО ПРОЦЕСУ ===
        pids[i] = pid;
        if (i == 0) {
            pgid = pid;
        }
        setpgid(pid, pgid);
    }

    if (num_cmds > 1) {
        for (size_t i = 0; i < num_cmds - 1; ++i) {
            close(pipes[i][0]);
            close(pipes[i][1]);
        }
        free(pipes);
    }

    if (is_interactive && pgid > 0) {
        tcsetpgrp(STDIN_FILENO, pgid);
    }

    int pipefail_code = 0;
    for (size_t i = 0; i < num_cmds; ++i) {
        int wstatus = 0;
        while (waitpid(pids[i], &wstatus, 0) == -1) {
            if (errno == EINTR) continue;
            perror("waitpid");
            break;
        }

        int exit_code = 0;
        if (WIFEXITED(wstatus)) {
            exit_code = WEXITSTATUS(wstatus);
        } else if (WIFSIGNALED(wstatus)) {
            exit_code = 128 + WTERMSIG(wstatus);
        }

        res.all_statuses[i] = exit_code;
        if (exit_code != 0) {
            pipefail_code = exit_code;
        }
    }

    if (is_interactive) {
        tcsetpgrp(STDIN_FILENO, shell_pgid);
    }

    res.last_status = res.all_statuses[num_cmds - 1];
    res.pipefail_status = pipefail_code;

    free(pids);
    return res;
}

#include <iostream>
#include <vector>
#include <string>
#include <memory>
#include <span>
#include <system_error>
#include <unistd.h>
#include <fcntl.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <termios.h>

// Безпечна RAII-обгортка над системним файловим дескриптором
class UniqueFd {
    int fd_ = -1;
public:
    UniqueFd() noexcept = default;
    explicit UniqueFd(int fd) noexcept : fd_(fd) {}
    ~UniqueFd() noexcept { reset(); }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;

    UniqueFd(UniqueFd&& other) noexcept : fd_(other.release()) {}
    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            reset(other.release());
        }
        return *this;
    }

    [[nodiscard]] int get() const noexcept { return fd_; }
    [[nodiscard]] bool valid() const noexcept { return fd_ >= 0; }

    int release() noexcept {
        int old = fd_;
        fd_ = -1;
        return old;
    }

    void reset(int new_fd = -1) noexcept {
        if (fd_ >= 0) {
            ::close(fd_);
        }
        fd_ = new_fd;
    }
};

struct PipePair {
    UniqueFd read_end;
    UniqueFd write_end;

    static std::expected<PipePair, std::error_code> create() {
        int fds[2];
        if (::pipe2(fds, O_CLOEXEC) == -1) {
            return std::unexpected(std::error_code(errno, std::generic_category()));
        }
        return PipePair{UniqueFd(fds[0]), UniqueFd(fds[1])};
    }
};

struct Command {
    std::vector<std::string> args;
};

struct PipelineResult {
    int last_status{0};
    int pipefail_status{0};
    std::vector<int> all_statuses;
};

class PipelineComposer {
public:
    static std::expected<PipelineResult, std::error_code> execute(std::span<const Command> commands) {
        if (commands.empty()) {
            return PipelineResult{};
        }

        const size_t n = commands.size();
        std::vector<PipePair> pipes;
        pipes.reserve(n > 1 ? n - 1 : 0);

        for (size_t i = 0; i + 1 < n; ++i) {
            auto pipe_res = PipePair::create();
            if (!pipe_res) {
                return std::unexpected(pipe_res.error());
            }
            pipes.push_back(std::move(*pipe_res));
        }

        std::vector<pid_t> pids(n, 0);
        pid_t pgid = 0;
        const bool interactive = ::isatty(STDIN_FILENO) != 0;
        const pid_t shell_pgid = ::getpgrp();

        for (size_t i = 0; i < n; ++i) {
            pid_t pid = ::fork();
            if (pid < 0) {
                return std::unexpected(std::error_code(errno, std::generic_category()));
            }

            if (pid == 0) {
                pid_t cur_pid = ::getpid();
                pid_t target_pgid = (i == 0) ? cur_pid : pgid;
                ::setpgid(0, target_pgid);

                if (i > 0) {
                    if (::dup2(pipes[i - 1].read_end.get(), STDIN_FILENO) == -1) {
                        ::_exit(127);
                    }
                }

                if (i + 1 < n) {
                    if (::dup2(pipes[i].write_end.get(), STDOUT_FILENO) == -1) {
                        ::_exit(127);
                    }
                }

                for (auto& p : pipes) {
                    p.read_end.reset();
                    p.write_end.reset();
                }

                std::vector<char*> raw_args;
                raw_args.reserve(commands[i].args.size() + 1);
                for (const auto& arg : commands[i].args) {
                    raw_args.push_back(const_cast<char*>(arg.c_str()));
                }
                raw_args.push_back(nullptr);

                ::execvp(raw_args[0], raw_args.data());
                ::_exit(127);
            }

            pids[i] = pid;
            if (i == 0) {
                pgid = pid;
            }
            ::setpgid(pid, pgid);
        }

        pipes.clear();

        if (interactive && pgid > 0) {
            ::tcsetpgrp(STDIN_FILENO, pgid);
        }

        PipelineResult result;
        result.all_statuses.resize(n, 0);
        int pipefail_code = 0;

        for (size_t i = 0; i < n; ++i) {
            int wstatus = 0;
            while (::waitpid(pids[i], &wstatus, 0) == -1) {
                if (errno == EINTR) continue;
                break;
            }

            int code = 0;
            if (WIFEXITED(wstatus)) {
                code = WEXITSTATUS(wstatus);
            } else if (WIFSIGNALED(wstatus)) {
                code = 128 + WTERMSIG(wstatus);
            }

            result.all_statuses[i] = code;
            if (code != 0) {
                pipefail_code = code;
            }
        }

        if (interactive) {
            ::tcsetpgrp(STDIN_FILENO, shell_pgid);
        }

        result.last_status = result.all_statuses.back();
        result.pipefail_status = pipefail_code;
        return result;
    }
};

## Покрокове простеження життєвого циклу дескрипторів у ядрі

Щоб чітко зрозуміти, чому рушій працює надійно, простежимо стан системних таблиць ядра під час виконання триступеневого конвеєра `cmd0 | cmd1 | cmd2`.

### 1. Стан після виклику pipe2() для двох каналів

Батьківська оболонка виділяє два канали `p0` та `p1`. У просторі ядра створюються два екземпляри `struct file` для запису та два для зчитування. У таблиці дескрипторів оболонки з'являються індекси `3, 4` (канал 0) та `5, 6` (канал 1):

```
Таблиця дескрипторів батька:
FD 0: stdin (термінал)
FD 1: stdout (термінал)
FD 2: stderr (термінал)
FD 3: p0[0] (читач Pipe 0, refcount = 1)
FD 4: p0[1] (записувач Pipe 0, refcount = 1)
FD 5: p1[0] (читач Pipe 1, refcount = 1)
FD 6: p1[1] (записувач Pipe 1, refcount = 1)
```

### 2. Стан після розгалуження fork() для першої дитини (cmd0)

Дитина `cmd0` отримує повну копію таблиці дескрипторів. У результаті лічильники посилань `struct file` для кожного дескриптора збільшуються з 1 до 2:

```
Таблиця дескрипторів cmd0 (до очищення):
FD 0..2: успадковано від батька
FD 3: p0[0] (refcount = 2)
FD 4: p0[1] (refcount = 2)
FD 5: p1[0] (refcount = 2)
FD 6: p1[1] (refcount = 2)
```

Дитина виконує `dup2(4, STDOUT_FILENO)` — тепер її дескриптор 1 вказує на записувач Pipe 0 (лічильник записувачів стає 3). Далі дитина викликає цикл `close()` для дескрипторів 3, 4, 5, 6. Лічильники зменшуються:

```
Таблиця дескрипторів cmd0 (перед execvp):
FD 0: stdin (термінал)
FD 1: p0[1] (записувач Pipe 0, refcount = 2: один у cmd0, один у батька)
FD 2: stderr (термінал)
(дескриптори 3..6 закриті)
```

### 3. Стан після fork() для проміжної дитини (cmd1)

Дитина `cmd1` робить `dup2(3, STDIN_FILENO)` (підключення читача Pipe 0) та `dup2(6, STDOUT_FILENO)` (підключення записувача Pipe 1), після чого закриває дескриптори 3, 4, 5, 6.

### 4. Стан після завершення циклу fork() та закриття каналів у батькові

Коли всі три процеси створено, батьківська оболонка викликає `close()` для всіх кінців `pipes[0]` та `pipes[1]`. Тепер батько не має жодного відкритого дескриптора в ці канали!

У системі залишаються тільки ті дескриптори, які реально потрібні:
- **Pipe 0**: єдиний записувач — FD 1 процесу `cmd0` (refcount = 1); єдиний читач — FD 0 процесу `cmd1` (refcount = 1).
- **Pipe 1**: єдиний записувач — FD 1 процесу `cmd1` (refcount = 1); єдиний читач — FD 0 процесу `cmd2` (refcount = 1).

Ця рівновага забезпечує математичну точність передачі сигналів EOF: щойно `cmd0` завершує роботу, лічильник записувачів Pipe 0 стає 0, і `cmd1` гарантовано отримує EOF під час вичерпання буфера.

## Розбір критичних системних пасток

### 1. Дедлок через незакриті дескриптори запису

Найпоширеніша помилка реалізації конвеєрів — збереження відкритих дескрипторів запису `pipes[i][1]` у батьківському процесі або в дочірніх процесах наступних етапів.

Якщо оболонка створила канал між `cmd1` та `cmd2`, але забула викликати `close(pipes[0][1])` у власному процесі:
1. `cmd1` успішно зчитує вхідні дані, записує результат у канал і завершується через `exit(0)`.
2. Ядро автоматично закриває дескриптор `stdout` процесу `cmd1`.
3. `cmd2` зчитує всі байти з кільцевого буфера ядра і робить черговий системний виклик `read(0, buf, size)`.
4. Оскільки батьківська оболонка все ще тримає відкритий дескриптор запису в цей канал, ядро вважає, що запис нових даних теоретично можливий.
5. Замість повернення `0` (EOF), системний виклик `read()` у `cmd2` **блокується назавжди**.
6. Батьківський процес викликає `waitpid()` і також блокується назавжди. Виникає нерозв'язний дедлок.

### 2. Стан гонитви при призначенні групи процесів (PGID Race)

Коли оболонка створює перший дочірній процес (`PID 2001`), цей процес повинен стати лідером нової групи `PGID 2001`. Якщо виклик `setpgid()` розмістити лише в тілі дочірнього процесу:
- Планувальник ядра може перемкнути процесор на другий дочірній процес (`PID 2002`) до того, як перший процес встигне викликати `setpgid(0, 2001)`.
- Другий процес спробує виконати `setpgid(0, 2001)`, але оскільки групи `2001` у ядрі ще не існує, виклик завершиться системною помилкою `EPERM` або `ESRCH`.
- Якщо ж викликати `setpgid()` лише в батьківському процесі, перший процес може встигнути викликати `execve()`, після чого ядро заборонить зміну PGID з кодом `EACCES`.

**Єдине коректне рішення**: викликати `setpgid(pid, pgid)` **двічі** — і в батькові, і в дитині. Той процес, який дістанеться системного виклику першим, ініціалізує групу, а другий виклик або повторить дію безпомилково, або поверне безпечний код `0`.

### 3. Небезпека ігнорування SIGPIPE у багатопотокових серверах

Якщо конвеєр запускається всередині багатопотокового демона, де обробник `SIGPIPE` було вимкнено через `signal(SIGPIPE, SIG_IGN)`, дочірні процеси успадковують стан ігнорування через `execve()`. У такому разі утиліти, які покладаються на автоматичне завершення сигналом (наприклад, `yes`, `cat` або `tail -f`), почнуть нескінченно крутити процесор у циклі з помилкою `EPIPE` замість швидкої зупинки. Перед викликом `execvp()` дочірній процес повинен явно скинути диспозицію `SIGPIPE` на типову дію `SIG_DFL`.

### 4. Збирання всіх дітей та захист від зомбі

Якщо оболонка чекатиме лише завершення останнього процесу `pids[num_cmds - 1]` і негайно вийде з функції, усі попередні дочірні процеси залишаться в стані `Zombie` (Z), доки батьківський процес не завершиться або не викличе `waitpid(-1, NULL, 0)`.

У довгоживучих серверах або інтерактивних оболонках накопичення зомбі призводить до вичерпання таблиці процесів ядра (`PID exhaustion`). Наш рушій гарантовано ітерує по масиву всіх `N` процесів і вичищає таблицю записів ядра без залишку.

### 5. Обробка переривання EINTR у циклах waitpid

Системний виклик `waitpid()` може бути перерваний будь-яким сигналом операційної системи (наприклад, `SIGCHLD`, `SIGWINCH` при зміні розміру вікна термінала). У такому разі функція повертає `-1` і виставляє `errno = EINTR`. Рушій містить явний цикл `while (waitpid(...) == -1 && errno == EINTR);`, що гарантує надійне очікування результатів навіть в умовах інтенсивного потоку зовнішніх сигналів.

## Обробка збоїв розгалуження та часткове очищення

Якщо системний виклик `fork()` завершується помилкою (наприклад, система досягла ліміту процесів `EAGAIN` на етапі `i = 3` з 5 команд), рушій не може просто вийти: у системі вже працюють процеси `cmd0`, `cmd1`, `cmd2`.

Коректна процедура відновлення вимагає:
1. Закрити всі кінці виділених каналів у батьківському процесі, щоб читачі отримали EOF.
2. Надіслати сигнал примусового завершення `SIGTERM` або `SIGKILL` усім уже народженим дочірнім процесам (`pids[0..i-1]`).
3. Виконати цикл `waitpid()` для збирання статусів завершення народжених дітей, щоб уникнути витоку зомбі.
4. Звільнити виділені динамічні масиви та повернути помилку викликаючому коду.

## Інтеграція з файловими перенаправленнями

У реальних сценаріях кінці конвеєра часто з'єднуються не з терміналом, а з файлами на диску: `cmd0 < input.txt | cmd1 | cmd2 > output.txt`.

У цій моделі рушій виконує додаткові кроки у вікні між `fork()` та `execvp()`:
- Для першого процесу (`i == 0`): якщо задано вхідний файл, викликається `open("input.txt", O_RDONLY)`, результат перенаправляється на дескриптор 0 через `dup2(in_fd, STDIN_FILENO)`, після чого `in_fd` закривається.
- Для останнього процесу (`i == N-1`): якщо задано вихідний файл, викликається `open("output.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644)`, результат підключається до дескриптора 1 через `dup2(out_fd, STDOUT_FILENO)` і `out_fd` закривається.
- Якщо користувач вказав перенаправлення потоку помилок `2>&1`, дитина викликає `dup2(STDOUT_FILENO, STDERR_FILENO)` **після** налаштування дескриптора 1.

## Керування пропускною здатністю та розміром буфера каналу

За замовчуванням ядро Linux виділяє 64 КіБ (16 сторінок по 4096 байтів) на кожен неіменований канал. Для більшості потокових задач цього розміру достатньо, щоб згладжувати мікроколивання швидкості між процесами без зайвого споживання пам'яті.

Проте для високопродуктивних обчислювальних ланцюжків (наприклад, стиснення великих архівів або фільтрація мультимедійних потоків) розмір буфера можна динамічно збільшити через системний виклик `fcntl()` із командою `F_SETPIPE_SZ`:

:::tabs
```c
// Збільшення буфера каналу до 1 МіБ (256 сторінок)
int new_size = 1024 * 1024;
if (fcntl(pipefd[1], F_SETPIPE_SZ, new_size) == -1) {
    perror("fcntl F_SETPIPE_SZ");
}
```
```cpp
// Збільшення буфера каналу до 1 МіБ у C++ з обробкою винятків
const int new_size = 1024 * 1024;
if (::fcntl(pipe_fd.get(), F_SETPIPE_SZ, new_size) == -1) {
    throw std::system_error(errno, std::generic_category(), "fcntl F_SETPIPE_SZ failed");
}
```
:::

### Вплив розміру буфера на продуктивність:
- **Зменшення перемикань контексту**: при передачі гігабайтів даних буфер 1 МіБ дозволяє процесу-записувачу виконувати на порядок менше переходів у простір ядра, що підвищує загальну пропускну здатність конвеєра на 15–30% на сучасних багатоядерних процесорах.
- **Ціна латентності**: збільшення буфера збільшує затримку доставки першого байта до споживача. Для інтерактивних утиліт (де важлива миттєва реакція на ввід користувача) буфер слід залишати стандартним (64 КіБ).

### Порівняння класичного копіювання з технологією splice

У класичній моделі конвеєра кожен байт даних копіюється двічі: спочатку з пам'яті процесу-записувача в сторінки ядра (`copy_from_user`), а потім з ядра в пам'ять процесу-читача (`copy_to_user`). Для процесора це створює суттєве навантаження на L1/L2 кеші та шину пам'яті.

Якщо проміжна програма є простим перенаправлювачем або фільтром пакетів, використання системного виклику `splice()` дозволяє передавати сторінки між двома каналами або дескрипторами файлів без виходу в простір користувача:

:::tabs
```c
// Передача даних без копіювання між двома каналами
ssize_t n = splice(pipe_in, NULL, pipe_out, NULL, 65536, SPLICE_F_MOVE | SPLICE_F_MORE);
if (n == -1) {
    perror("splice");
}
```
```cpp
// Передача даних без копіювання у C++
const ssize_t n = ::splice(pipe_in.get(), nullptr, pipe_out.get(), nullptr, 65536, SPLICE_F_MOVE | SPLICE_F_MORE);
if (n == -1) {
    throw std::system_error(errno, std::generic_category(), "splice failed");
}
```
:::

Завдяки цьому пропускна здатність на швидких NVMe-накопичувачах або 100-гігабітних мережевих інтерфейсах зростає у 2–3 рази, а навантаження на процесор падає до мінімуму.

## Практичний тестовий набір та валідація на витоки дескрипторів

Щоб перевірити коректність роботи рушія в реальних умовах експлуатації, розробимо набір автоматичних перевірок, що покривають граничні випадки та контролюють збереження інваріантів системи.

```
Сценарії автоматичного тестування:
1. Тест лінійного конвеєра:
   printf "банан\nяблуко\nвишня\n" | sort | tr "a-z" "A-Z"
   Перевірка: коректність сортування, перетворення регістру та код виходу 0.
2. Тест раннього завершення (Broken Pipe):
   yes "дані" | head -n 5
   Перевірка: процес yes гине від SIGPIPE, статус head == 0, тривалість < 0.1 с.
3. Тест проміжного збою (pipefail):
   cat /неіснуючий_файл | grep "патерн" | wc -l
   Перевірка: стандартний статус == 0 (успіх wc), pipefail статус == 1 (помилка cat).
4. Тест відсутності витоку дескрипторів:
   Перевірка кількості записів у каталозі /proc/self/fd до і після 1000 запусків.
```

### Простеження стабільності ресурсів через procfs

Надійна перевірка відсутності дескрипторних витоків базується на порівнянні кількості файлів у `/proc/self/fd/`:

1. Перед викликом `run_pipeline()` програма зчитує список елементів каталогу `/proc/self/fd/` і фіксує базове число дескрипторів (типово 3 або 4 — дескриптори `stdin`, `stdout`, `stderr` та дескриптор відкритого каталогу `opendir`).
2. Виконується цикл із 1000 послідовних запусків конвеєра з 5 команд.
3. Після завершення циклу кількість файлових дескрипторів у `/proc/self/fd/` повторно вимірюється. Якщо число збільшилося хоча б на 1, це сигналізує про дефект звільнення ресурсів (`FD Leak`).
4. Наш рушій гарантує строгу константність кількості дескрипторів незалежно від кількості виконаних конвеєрів.

## Фоновий режим та взаємодія з терміналом: SIGTTIN та SIGTTOU

Коли конвеєр запускається у фоновому режимі (оператор `&` в оболонці), оболонка **не викликає** `tcsetpgrp(STDIN_FILENO, pgid)`. Замість цього передній план термінала залишається у самої оболонки.

У цій конфігурації вступають у дію правила керування завданнями POSIX:
- Якщо фоновий процес конвеєра намагається зчитати дані з термінала (`read(STDIN_FILENO, ...)`), драйвер термінала негайно надсилає всій фоновій групі сигнал `SIGTTIN` (Terminal Input). За замовчуванням цей сигнал зупиняє всі процеси конвеєра.
- Якщо увімкнено прапорець термінала `TOSTOP` (`stty tostop`), спроба фонового процесу записати байти в термінал (`write(STDOUT_FILENO, ...)`) спричиняє надсилання сигналу `SIGTTOU` (Terminal Output) і зупинку конвеєра до моменту переведення на передній план командою `fg`.

## Як конвеєри реалізовано у високорівневих мовах

Сучасні системні мови програмування надають власні абстракції над конвеєрами, проте всі вони під капотом зводяться до описаних примітивів ядра:

- **Python (`subprocess.Popen`)**: створює канали через `os.pipe()`, призначає `stdin=p1.stdout` і за замовчуванням виставляє `close_fds=True` (що еквівалентно циклу закриття дескрипторів у дитині).
- **Go (`os/exec`)**: метод `cmd.StdoutPipe()` створює системний канал з прапорцем `O_CLOEXEC`, а метод `cmd.Start()` запускає горутину для спостереження за закриттям читача та автоматичного виклику `wait()`.
- **Rust (`std::process::Stdio::piped()`)**: реалізує строге RAII-володіння кінцями каналу за допомогою типів `ChildStdin` та `ChildStdout`. Дескриптор автоматично закривається в момент видалення об'єкта зі стеку, запобігаючи дедлокам на рівні системи типів компілятора.

## Порівняльний аналіз підходів: C проти C++

Порівнюючи наведені реалізації на C та C++, звернемо увагу на архітектурні відмінності:

1. **Керування ресурсами**: у версії на C дескриптори каналів та масиви динамічної пам'яті вимагають ретельного ручного звільнення в усіх точках можливих помилок (обробка збою `pipe2` вимагає закриття попередніх каналів через вкладений цикл). У C++ клас `UniqueFd` та вектор `std::vector<PipePair>` автоматично закривають усі відкриті дескриптори у деструкторах при виході зі скоупу (зокрема при виникненні винятків чи ранньому поверненні через `std::unexpected`).
2. **Типобезпека результатів**: C++ повертає типізований об'єкт `std::expected<PipelineResult, std::error_code>`, який на рівні компілятора змушує викликаючий код перевірити наявність системної помилки до звернення до результатів статусів.
3. **Робота з рядками**: у C++ аргументи команд інкапсульовані в `std::vector<std::string>`, що усуває небезпеку некоректного звільнення буферів рядків, а перетворення на масив покажчиків `char*` для `execvp` виконується безпосередньо перед викликом.
4. **Витрати на виконання (Zero Overhead)**: сучасний компілятор C++ оптимізує виклики `UniqueFd` у прямі інструкції виклику `close()`, усуваючи будь-які накладні витрати порівняно з рукописним кодом на C, але надаючи повну безпеку щодо винятків та ранніх повернень.

## Висновок: надійність через строгі інваріанти

Наведений рушій доводить, що надійність виконання конвеєрів у просторі користувача не потребує введення складних додаткових протоколів чи надлишкових демонів. Достатньо суворо дотримуватися системних інваріантів Unix: виділяти всі канали до початку розгалуження, своєчасно закривати дескриптори запису для передачі сигналів EOF, синхронізувати призначення груп процесів з обох боків `fork` та вичищати статус кожного дочірнього процесу в таблиці ядра через `waitpid`.
