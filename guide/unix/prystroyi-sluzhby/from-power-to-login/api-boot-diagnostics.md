# 📋 Інтерфейси діагностики та параметри завантаження Linux

Коли операційна система не доходить до запрошення входу або завантажується неприпустимо довго, єдиним способом відновити контроль є передача спеціальних параметрів ядру та виклик діагностичних утиліт системного менеджера. Цей довідник містить вичерпну специфікацію параметрів командного рядка ядра (англ. *Kernel Command-Line Parameters*), інтерфейсів утиліти `systemd-analyze`, контрактів аварійних цілей завантаження, параметрів утиліт `journalctl` та `bootctl`, а також протоколу роботи системних генераторів.

## Параметри командного рядка ядра (Kernel Command Line)

Параметри передаються ядру завантажувачем у вигляді єдиного ASCII-рядка. Ядро Linux та системні генератори `systemd` розбирають цей рядок на ключі та пари `ключ=значення`. Значення, що починаються з префікса `rd.`, обробляються виключно всередині раннього простору користувача (англ. *initramfs*), тоді як параметри з префіксом `systemd.` керують поведінкою основного процесу PID 1.

| Параметр | Середовище | Тип значення | Опис призначення та системний ефект |
| :--- | :--- | :--- | :--- |
| `root=` | Kernel / initramfs | `UUID=...`, `PARTUUID=...`, `/dev/...` | Вказує блоковий пристрій або розділ, що містить справжню кореневу файлову систему. Рекомендовано передавати стійкі ідентифікатори `UUID` або `PARTUUID`. |
| `rootfstype=` | Kernel / initramfs | Рядок (`ext4`, `xfs`, `btrfs`) | Явно задає тип файлової системи кореня. Запобігає помилкам автоматичного визначення типу драйвером ядра. |
| `rootflags=` | Kernel / initramfs | Рядок опцій (`subvol=...`, `noatime`) | Опції монтування, що передаються прапорцями у системний виклик `mount()` для кореневого розділу. |
| `ro` / `rw` | Kernel / initramfs | Прапорець без значення | Початковий режим монтування кореня. `ro` змушує змонтувати корінь лише для читання для безпечної перевірки `fsck` перед переведенням у `rw`. |
| `init=` | Kernel | Шлях (`/bin/sh`, `/lib/systemd/systemd`) | Перевизначає абсолютний шлях до першої користувацької програми, яку запускає ядро. За замовчуванням `/sbin/init`. |
| `systemd.unit=` | PID 1 | Назва юніта (`rescue.target`, `emergency.target`) | Примусово встановлює цільовий юніт завантаження замість стандартного `default.target`. |
| `systemd.debug-shell` | PID 1 | `1` або `0` | Активує налагоджувальний root-шелл на віртуальному терміналі `/dev/tty9` без потреби автентифікації на ранніх фазах старту. |
| `systemd.log_level=` | PID 1 / initramfs | `debug`, `info`, `warning`, `err` | Встановлює рівень деталізації системного логу PID 1 та ранніх служб. |
| `systemd.log_target=` | PID 1 | `journal`, `kmsg`, `console`, `null` | Визначає приймач журнальних повідомлень до моменту готовності демона `systemd-journald`. |
| `rd.break=` | initramfs (dracut) | `cmdline`, `pre-udev`, `pre-mount`, `mount`, `pre-pivot` | Зупиняє виконання initramfs у вказаній точці перехоплення (hook) та викидає аварійний командний рядок у RAM. |
| `rd.shell` | initramfs (dracut) | `1` або `0` | Дозволяє або забороняє виклик аварійної оболонки у разі фатальної помилки розгортання initramfs. |
| `rd.emergency=` | initramfs | `reboot`, `poweroff`, `halt` | Поведінка initramfs при критичному збої монтування (перезавантаження, вимкнення або зависання). |
| `fsck.mode=` | initramfs / PID 1 | `auto`, `force`, `skip` | Режим перевірки цілісності файлових систем: примусова перевірка (`force`) або повне ігнорування (`skip`). |
| `fsck.repair=` | initramfs / PID 1 | `preen`, `yes`, `no` | Політика автоматичного виправлення пошкоджень: безпечні правки (`preen`), автоматична згода на всі виправлення (`yes`). |
| `panic=` | Kernel | Ціле число (секунди) | Кількість секунд затримки перед автоматичним перезавантаженням при паніці ядра (*Kernel Panic*). `0` — вічне зависання. |
| `earlyprintk=` | Kernel | `vga`, `serial,ttyS0,115200`, `efi` | Вмикає прямий вивід повідомлень ядра на екран або послідовний порт до ініціалізації стандартних TTY-драйверів. |
| `console=` | Kernel / PID 1 | `tty0`, `ttyS0,115200n8` | Задає первинний пристрій консольного вводу-виводу для повідомлень ядра, journald та екземплярів getty. |
| `crashkernel=` | Kernel | Діапазон пам'яті (`256M`, `512M@2G`) | Резервує виділену область фізичної пам'яті для завантаження аварійного ядра kdump у разі збою основного ядра. |

### Детальний механізм дії ключових параметрів ядра

Параметр `root=` є головним аргументом, від якого залежить здатність операційної системи знайти власні файли. Сучасне ядро підтримує кілька форматів адресації накопичувачів:
* `root=UUID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`: Адресація за універсальним унікальним ідентифікатором файлової системи. Цей метод є найнадійнішим, оскільки UUID генерується під час форматування розділу (наприклад командою `mkfs.ext4`) і зберігається безпосередньо в суперблоці. Порядок підключення дисків чи зміна номерів портів SATA/NVMe не впливають на ідентифікатор.
* `root=PARTUUID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`: Адресація за ідентифікатором розділу в таблиці розділів GPT (GUID Partition Table). Працює ще до того, як ядро розпізнає тип файлової системи всередині розділу, що критично для шифрованих або сирих блокових пристроїв.
* `root=/dev/nvme0n1p2` або `root=/dev/sda1`: Застарілий прямий шлях до ноди пристрою. Вразливий до зміни порядку ініціалізації контролерів: при додаванні другого накопичувача колишній `/dev/sda` може стати `/dev/sdb`, що призведе до паніки ядра.

Параметр `init=` дозволяє повністю обійти стандартну систему ініціалізації. Якщо передати `init=/bin/bash` або `init=/bin/sh`, ядро після монтування кореневої файлової системи не запускає `systemd`, а негайно виконує командну оболонку від імені суперкористувача root з PID 1. У цьому режимі не працює жодна системна служба, файлова система змонтована лише для читання (`ro`), а завершення роботи оболонки командою `exit` негайно викликає паніку ядра (*Kernel Panic — Attempted to kill init!*), оскільки процес PID 1 не має права завершуватися.

Параметри `systemd.log_level=` та `systemd.log_target=` керують діагностичним виводом системного менеджера. Встановлення `systemd.log_level=debug` змушує PID 1 друкувати повний протокол створення задач транзакцій, виконання кожного виклику `fork()`, застосування правил безпеки Seccomp та обмежень cgroups. За замовчуванням повідомлення надсилаються до демона `journald`, але до його готовності або в разі аварії параметр `systemd.log_target=kmsg` спрямовує вивід у кільцевий буфер ядра `/dev/kmsg`, звідки його можна прочитати утилітою `dmesg`.

### Точки зупинки initramfs: хуки `rd.break`

Опція `rd.break` приймає аргументом назву стадії ранньої ініціалізації всередині генератора `dracut` або `initramfs-tools`. Це дає змогу зупинити виконання скриптів раннього простору та отримати інтерактивну командну оболонку BusyBox:

1. `rd.break=cmdline`: Зупинка одразу після зчитування аргументів ядра з `/proc/cmdline`, до запуску демона `systemd-udevd`. Використовується для перевірки коректності переданих параметрів завантажувача.
2. `rd.break=pre-udev`: Зупинка перед завантаженням модулів ядра та скануванням апаратних шин. Дозволяє вручну завантажити експериментальний модуль через `modprobe` або налаштувати параметри модулів у `/etc/modprobe.d/`.
3. `rd.break=pre-trigger`: Демон `udevd` вже активний, але події апаратного виявлення (`udevadm trigger`) ще не відправлені. Корисно для налагодження правил udev у `/lib/udev/rules.d/`.
4. `rd.break=initqueue`: Фаза очікування готовності апаратних блокових пристроїв. Саме тут виконуються скрипти створення RAID-масивів `mdadm`, сканування томів LVM та розблокування ключів LUKS.
5. `rd.break=pre-mount`: Пристрій кореня розпізнано, створено ноду в `/dev/`, але системний виклик `mount()` до каталогу `/sysroot` ще не виконано. Дозволяє вручну перевірити диск утилітою `fsck` або перевірити таблицю розділів через `fdisk -l`.
6. `rd.break=mount`: Справжній корінь успішно змонтовано в `/sysroot`, але перенесення віртуальних файлових систем ще не почалося. Дозволяє перевірити цілісність вмісту фізичного диска хоста.
7. `rd.break=pre-pivot`: Усі підготовчі дії завершено, каталоги `/dev`, `/proc`, `/sys`, `/run` перенесені під `/sysroot`, пам'ять tmpfs очищена. Наступний крок — системний виклик `switch_root`.

Після завершення діагностики в аварійній оболонці initramfs вихід командою `exit` або `Ctrl+D` змушує скрипт продовжити штатне завантаження з точки зупинки.

## Команди утиліти `systemd-analyze`

Утиліта `systemd-analyze` є головним інструментом профілювання процесу завантаження в просторі користувача. Вона звертається через D-Bus до інтерфейсу `org.freedesktop.systemd1.Manager`, зчитуючи внутрішні часові мітки монотонного годинника `CLOCK_MONOTONIC`, які PID 1 фіксує під час проходження кожного етапу.

### Базові команди часової діагностики

```
Команда: systemd-analyze time
Призначення: Виводить інтегральний розподіл часу між основними етапами завантаження.
Приклад виводу:
Startup finished in 1.423s (firmware) + 2.112s (loader) + 1.845s (kernel) + 3.120s (initrd) + 4.230s (userspace) = 12.730s
graphical.target reached after 4.215s in userspace
```

Розподіл часу між шарами системи обчислюється за чіткими межами подій:
* `firmware`: Час виконання коду прошивки UEFI (від скидання процесора до виклику завантажувача). Зчитується з ACPI-таблиці BGRT/FPDT або змінних UEFI `LoaderTimeFirmwareUSec`.
* `loader`: Час роботи завантажувача (GRUB2 або systemd-boot). Зчитується зі змінної `LoaderTimeExecUSec`.
* `kernel`: Інтервал від точки входу ядра `startup_64` до виклику першого користувацького процесу `kernel_init()`.
* `initrd`: Час роботи раннього простору користувача initramfs до виклику `switch_root`.
* `userspace`: Час виконання PID 1 від старту основного менеджера до моменту переходу цільового юніта `default.target` у стан готовності.

### Виявлення «вузьких місць»: `blame` та `critical-chain`

Команда `systemd-analyze blame` виводить список усіх юнітів, що завершили ініціалізацію, впорядкований за спаданням часу, витраченого на їхній запуск:

```
          2.105s docker.service
          1.093s NetworkManager-wait-online.service
           520ms systemd-udevd.service
           235ms NetworkManager.service
           180ms lvm2-monitor.service
           145ms systemd-journald.service
            58ms systemd-modules-load.service
```

Головна особливість аналізу `blame` полягає в тому, що він відображає локальну тривалість виконання конкретної служби, але не враховує паралелізм. Служба `docker.service`, яка виконувалася 2.1 секунди, могла працювати повністю асинхронно у фоні й не затримувати появу вікна входу чи доступність терміналів.

Для визначення реальних затримок використовують команду `systemd-analyze critical-chain`:

```
graphical.target @4.215s
└─multi-user.target @4.215s
  └─docker.service @2.110s +2.105s
    └─network-online.target @2.108s
      └─NetworkManager-wait-online.service @1.015s +1.093s
        └─NetworkManager.service @780ms +235ms
          └─dbus.service @750ms
            └─basic.target @745ms
              └─sockets.target @740ms
                └─dbus.socket @738ms
                  └─sysinit.target @730ms
                    └─systemd-udevd.service @210ms +520ms
                      └─systemd-sysctl.service @180ms +25ms
                        └─systemd-modules-load.service @120ms +58ms
                          └─local-fs.target @118ms
                            └─run-user-1000.mount @115ms
```

Формат відміток часу у критичному ланцюгу містить дві компоненти:
* `@<time>`: Абсолютний час старту юніта відносно точки відліку простору користувача (userspace).
* `+<time>`: Чистий час, витрачений на виконання директиви `ExecStart=` до переходу служби в активний стан.

Критичний ланцюг показує найдовшу послідовність суворо синхронізованих залежностей (`After=` / `Requires=`). Скорочення часу завантаження будь-якого юніта поза критичним ланцюгом не прискорить готовність системи.

### Графічний та структурний аналіз

* `systemd-analyze plot > boot.svg`: Генерує детальну векторну часову діаграму завантаження у форматі SVG. Кожен юніт відображається окремою смугою на часовій шкалі з точним виділенням фаз очікування, запуску та активної роботи.
* `systemd-analyze dot 'multi-user.target' | dot -Tsvg > dependencies.svg`: Будує повний граф залежностей між юнітами у форматі Graphviz DOT. Дозволяє виявити неявні та надлишкові ребра залежностей.
* `systemd-analyze verify /etc/systemd/system/*.service`: Виконує статичну синтаксичну валідацію unit-файлів. Перевіряє існування вказаних бінарних шляхів, валідність директив безпеки Seccomp/cgroups та знаходить циклічні залежності (*Deadlocks*).
* `systemd-analyze cat-config systemd/system.conf`: Збирає й виводить єдину підсумкову конфігурацію з урахуванням пріоритетів каталогів `/usr/lib/`, `/run/` та `/etc/`.

## Робота з системним журналом `journalctl` та прошивкою `bootctl`

Для розслідування інцидентів, що сталися під час попередніх завантажень або до моменту доступності графічного інтерфейсу, системний адміністратор використовує спеціалізовані запити до `journalctl` та інтерфейс взаємодії з завантажувачем `bootctl`.

### Запити журналювання попередніх завантажень

Служба `systemd-journald` структурує записи за унікальними 128-бітними ідентифікаторами завантажень (Boot ID), які генеруються ядром у псевдофайлі `/proc/sys/kernel/random/boot_id`.

* `journalctl --list-boots`: Виводить таблицю всіх збережених сеансів завантаження з їхніми порядковими індексами, ідентифікаторами Boot ID та часовими межами першого й останнього запису:
  ```
  -2 9a4b8f3e... Sun 2026-08-16 10:15:02 EEST — Sun 2026-08-16 22:30:14 EEST
  -1 c7d21a90... Mon 2026-08-17 08:00:11 EEST — Mon 2026-08-17 18:45:50 EEST
   0 e3f412bc... Tue 2026-08-18 09:00:00 EEST — Tue 2026-08-18 14:30:22 EEST
  ```
* `journalctl -b 0`: Виводить журнал виключно поточного активного сеансу (індекс `0`).
* `journalctl -b -1 -p err..alert`: Показує лише критичні помилки та збої попереднього невдалого завантаження (індекс `-1`), що дозволяє розслідувати причину аварійного перезавантаження.
* `journalctl -b -u systemd-udevd.service`: Фільтрує повідомлення конкретної служби від початку її старту в поточному сеансі.
* `journalctl -k -b 0`: Виводить кільцевий буфер повідомлень ядра (*Kernel Ring Buffer*, еквівалент `dmesg`), зафіксований від моменту старту `startup_64`.

### Керування завантажувачем через `bootctl`

Утиліта `bootctl` взаємодіє зі специфікацією Boot Loader Specification (BLS) та змінними UEFI в каталозі `/sys/firmware/efi/efivars/`:

* `bootctl status`: Виводить повний звіт про стан прошивки: режим завантаження (UEFI чи BIOS), активність Secure Boot, точку монтування ESP (зазвичай `/efi` або `/boot/efi`), поточний активний завантажувач та список доступних конфігураційних записів BLS.
* `bootctl list`: Перелічує всі знайдені образи ядер, їхні версії, шляхи до `vmlinuz` та `initramfs`, а також параметри `cmdline`, що будуть передані під час вибору відповідного пункту.
* `bootctl set-default <entry-id>`: Встановлює запис за замовчуванням у конфігурації завантажувача без необхідності ручного редагування файлів.
* `bootctl set-oneshot <entry-id>`: Вказує прошивці завантажити вказане ядро рівно один раз під час наступного перезавантаження (використовує змінну UEFI `BootNext`), автоматично повертаючись до основного ядра у разі наступного старту.

## Контракти аварійних цілей завантаження

У разі виникнення критичних помилок монтування дисків або порушення цілісності графа юнітів `systemd` переводить систему в аварійні режими.

| Критерій порівняння | `emergency.target` | `rescue.target` | `default.target` (`multi-user`) |
| :--- | :--- | :--- | :--- |
| **Системний стан** | Критична аварія (Minimalistic Shell) | Однокористувацький режим (Single-User) | Повнофункціональна система |
| **Файлова система `/`** | Змонтована лише для читання (`ro`) | Переведена в режим запису (`rw`) | Повністю змонтована (`rw`) |
| **Локальні диски `/etc/fstab`** | **Не змонтовані** | **Змонтовані** (`local-fs.target` досягнуто) | Всі диски та мережеві ресурси активні |
| **Мережевий стек** | Повністю вимкнений | Повністю вимкнений | Активний (`network.target`) |
| **Системні служби** | Запущено лише `systemd-journald` | Базові служби (`sysinit.target`, `basic.target`) | Усі фонові демони та таймери |
| **Автентифікація** | Запит пароля root через `sulogin` | Запит пароля root через `sulogin` | Повноцінний вхід `login` / PAM |
| **Термінал запуску** | Прямий доступ до фізичної консолі | Фізична консоль (`/dev/console`) | Віртуальні термінали `tty1`..`tty6` |
| **Запуск по cmdline** | `systemd.unit=emergency.target` або `emergency` | `systemd.unit=rescue.target` або `single` / `1` | Стандартне завантаження |

У режимі `emergency.target` системний менеджер не запускає жодних генераторів монтування і не чіпає диски хоста. Це єдиний безпечний режим для виправлення пошкоджених файлових систем через `e2fsck` або відновлення конфігурації `/etc/fstab` після некоректного редагування.

У режимі `rescue.target` система успішно пройшла фазу `sysinit.target`: усі локальні диски перевірено й змонтовано, активовано розділи підкачки Swap, налаштовано параметри sysctl, але мережевий стек і прикладні демони залишаються вимкненими.

## Практичні сценарії відновлення та діагностичні рецепти

Коли система перестає завантажуватися у штатному режимі, інженер використовує перевірені діагностичні рецепти:

### Сценарій 1: Пошкодження суперблоку або помилка UUID у параметрі `root=`

Якщо ядро зависає на стадії `dracut-initqueue timeout` через неможливість знайти вказаний UUID накопичувача:
1. Під час старту в меню завантажувача натискають клавішу `e` для редагування параметрів.
2. Дописують параметр `rd.break=pre-mount` у кінець рядка `linux`.
3. Натискають `Ctrl+X` або `F10` для старту.
4. Після появи командного рядка initramfs виконують команду `blkid`, щоб знайти справжні ідентифікатори всіх підключених розділів.
5. Перевіряють наявність ноди пристрою у каталозі `/dev/disk/by-uuid/`. Якщо нода відсутня, запускають сканування томів `lvm vgscan --mknodes` або розблоковують LUKS через `cryptsetup luksOpen /dev/nvme0n1p3 root`.
6. Монтують корінь вручну командою `mount /dev/mapper/root /sysroot` і виходять з оболонки командою `exit` для продовження штатного старту.

### Сценарій 2: Відновлення пароля суперкористувача root

Якщо доступ до облікового запису адміністратора втрачено:
1. У рядку параметрів завантажувача замінюють виклик системи ініціалізації параметром `init=/bin/bash` або `init=/bin/sh`.
2. Після завантаження ядро надає root-шелл з PID 1. Оскільки корінь змонтовано в режимі лише для читання, виконують команду перемотування в режим запису: `mount -o remount,rw /`.
3. Змінюють пароль root командою `passwd root`.
4. Якщо в системі увімкнено SELinux, створюють сигнальний файл автоматичного перемаркування контекстів безпеки під час наступного старту: `touch /.autorelabel`.
5. Скидають кеш сторінок на диск командою `sync` та примусово перезавантажують комп'ютер через інтерфейс SysRq: `echo b > /proc/sysrq-trigger`.

### Сценарій 3: Діагностика циклічних блокувань у юнітах systemd

Якщо під час завантаження система зависає на стадії `basic.target` через взаємне блокування служб:
1. Передають ядру параметри `systemd.log_level=debug systemd.log_target=console systemd.default_timeout_start_sec=10s`.
2. PID 1 друкує детальний список знайдених ребер графа та вказує на точний рядок циклу, наприклад: `systemd[1]: app.service: Found ordering cycle on dbus.service/start`.
3. Використовують аварійний налагоджувальний шелл на віртуальній консолі `/dev/tty9`, активувавши параметр `systemd.debug-shell=1`, для інспекції стану служб командою `systemctl list-jobs` без зупинки системи.

## Директиви unit-файлів для керування стадіями старту

Кожен unit-файл `systemd` містить директиви, що визначають його поведінку під час побудови транзакційного графа запуску:

* `DefaultDependencies=no`: За замовчуванням `systemd` автоматично додає до кожної служби неявні залежності `Requires=basic.target` та `After=basic.target`. Для ранніх служб (наприклад демонів `udevd`, `systemd-journald` або служб монтування), які зобов'язані стартувати *до* `basic.target`, ця директива вимикає автоматичні ребра, запобігаючи виникненню циклічних блокувань (*Dependency Loops*).
* `TimeoutStartSec=90s`: Встановлює максимальний час очікування переходу служби в активний стан (виклик `sd_notify("READY=1")` або завершення скрипта `ExecStart`). Якщо таймаут вичерпано, служба вважається аварійною, переривається сигналом `SIGTERM` (і далі `SIGKILL`), а `systemd` активує обробники помилок.
* `OnFailure=emergency.target`: Визначає юніт, який повинен бути доданий у транзакцію завантаження, якщо поточна служба перейшла у стан `failed`. Використовується для критичних служб монтування кореня або налаштування криптографічних дисків.
* `JobTimeoutSec=300s` та `JobTimeoutAction=reboot-force`: Визначає глобальний ліміт часу на виконання всієї транзакції завантаження або досягнення цільового юніта, захищаючи сервер від вічного зависання в автономному датацентрі.

## Інтерфейс та протокол системних генераторів

Генератори `systemd` — це скомпільовані двійкові програми або виконувані скрипти, які розміщуються у виділених системних каталогах. Їхнє завдання — транслювати сторонні конфігураційні формати (наприклад `/etc/fstab`, конфігурацію crypttab, розмітку дисків GPT, налаштування мережі) у стандартні unit-файли `systemd` безпосередньо під час завантаження.

### Ієрархія каталогів генераторів

Генератори викликаються за таким порядком пріоритетів (від найвищого до найнижчого):
1. `/run/systemd/system-generators/`: Генератори, створені динамічно в пам'яті (наприклад процесом initramfs перед `switch_root`).
2. `/etc/systemd/system-generators/`: Генератори, встановлені системним адміністратором конкретного хоста.
3. `/usr/lib/systemd/system-generators/` або `/lib/systemd/system-generators/`: Стандартні генератори, що постачаються дистрибутивом Linux.

Якщо в кількох каталогах знайдено виконувані файли з однаковими іменами, виконується лише генератор із каталогу з вищим пріоритетом.

### Протокол виклику та каталоги призначення

Системний менеджер запускає кожен генератор синхронно, передаючи йому три позиційні аргументи командного рядка:

```
/usr/lib/systemd/system-generators/custom-gen <normal-dir> <early-dir> <late-dir>
```

Кожен аргумент вказує шлях до тимчасового каталогу в оперативній пам'яті (`tmpfs`), куди генератор може записувати створені unit-файли та символьні посилання залежностей:
* `$1` (`normal-dir`): Типово `/run/systemd/generator`. Створені тут юніти мають пріоритет над стандартними пакетами дистрибутиву в `/usr/lib/systemd/system/`, але поступаються локальним налаштуванням адміністратора в `/etc/systemd/system/`.
* `$2` (`early-dir`): Типово `/run/systemd/generator.early`. Юніти з цього каталогу перекривають **будь-які** файли конфігурації, включно з каталогом `/etc/`. Використовується для примусового перехоплення управління в критичних ситуаціях.
* `$3` (`late-dir`): Типово `/run/systemd/generator.late`. Має найнижчий пріоритет. Використовується для створення запасних правил (fallback rules), які застосовуються лише у разі повної відсутності юніта в інших джерелах.

### Інваріанти та вимоги до коду генераторів

При створенні власних генераторів необхідно суворо дотримуватися таких системних правил:
* **Синхронність та швидкодія:** Генератори виконуються послідовно на найранішому етапі ініціалізації PID 1. Будь-яка затримка чи зависання в коді генератора блокує весь процес завантаження комп'ютера.
* **Відсутність зовнішніх залежностей:** На момент виконання генераторів файлові системи ще не змонтовані, мережа відсутня, а демон `dbus-daemon` ще не запущений. Генератор не має права робити мережеві виклики чи D-Bus запити.
* **Атомарність створення файлів:** Unit-файли мають записуватися через тимчасові файли з наступним атомарним перейменуванням `rename()`, щоб унеможливити зчитування напівзаписаного файлу системним менеджером.
* **Створення зв'язків залежностей:** Щоб підключити динамічно створений юніт до стандартного графа, генератор створює підкаталог вигляду `<target>.wants/` або `<target>.requires/` і розміщує всередині символьне посилання на створений `.service` або `.mount` файл.
* **Коди виходу:** Генератор зобов'язаний повертати код `0` при успішному завершенні. Ненульовий код виходу фіксується у системному журналі, але не зупиняє роботу інших генераторів.
