# 📋 Контракти та важелі керування довговічністю запису

Ця довідка містить вичерпний опис інтерфейсів, системних викликів, прапорців відкриття файлів, параметрів ядра, атрибутів блокових пристроїв, налаштувань асинхронного вводу-виводу io_uring та апаратних команд накопичувача, що визначають поведінку та гарантії збереження даних на кожному поверсі операційної системи Linux.

## Системні виклики синхронізації

У просторі користувача програма ініціює збереження даних через стандартизовані виклики ядра POSIX та розширення Linux.

### `fsync` та `fdatasync`

:::tabs
```c
#include <unistd.h>

int fsync(int fd);
int fdatasync(int fd);
```
```cpp
#include <unistd.h>
#include <system_error>

// POSIX інтерфейси доступні безпосередньо у глобальному просторі або ::fsync
int ::fsync(int fd);
int ::fdatasync(int fd);
```
:::

* **Призначення:** Примусове винесення всіх модифікованих сторінок файлу з кешу сторінок ядра на блоковий пристрій та надсилання команди скидання апаратного кешу накопичувача.
* **Відмінність поведінки:**
  * `fsync()`: гарантує запис усіх змінених сторінок даних файлу, а також **усіх** метаданих `struct inode` (включно з розміром файлу `i_size`, картою блоків/екстентів, міткою часу зміни `mtime`, міткою зміни статусу `ctime`, правами доступу). У журнальних файлових системах (Ext4/XFS) це призводить до створення та фіксації повної транзакції журналу.
  * `fdatasync()`: записує всі сторінки даних і лише ті метадані, які є **критично необхідними для коректного зчитування цих даних у майбутньому** (наприклад, новий розмір файлу `i_size` та виділені дискові екстенти). Якщо було змінено лише вміст наявних блоків без зміни довжини файлу, оновлення `mtime`/`ctime` не скидається на диск, що усуває потребу у важкій транзакції журналу файлової системи.
* **Повертане значення:** `0` у разі успішного завершення; `-1` при виникненні помилки з встановленням `errno`.
* **Коди помилок:**
  * `EIO` — апаратна помилка блокового накопичувача під час винесення сторінок або збою контролера;
  * `ENOSPC` — вичерпано вільний простір на носії (актуально для розріджених файлів або тонкого виділення `thin-provisioning`);
  * `EROFS`, `EINVAL` — дескриптор вказує на об'єкт, що не підтримує синхронізацію (наприклад, спеціальний іменований канал або сокет);
  * `EBADF` — передано недійсний дескриптор або файл, не відкритий на запис.

### `pwritev2` з прапорцями довговічності

:::tabs
```c
#include <sys/uio.h>

ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                 off_t offset, int flags);
```
```cpp
#include <sys/uio.h>
#include <span>

ssize_t ::pwritev2(int fd, const struct iovec *iov, int iovcnt,
                   off_t offset, int flags);
```
:::

* **Призначення:** Векторний атомарний запис за фіксованим зсувом із можливістю вказати поведінку довговічності безпосередньо для окремої операції вводу-виводу через аргумент `flags`.
* **Прапорці `flags`:**
  * `RWF_SYNC`: еквівалент відкриття файлу з прапорцем `O_SYNC`. Операція повертається лише після того, як дані та всі метадані перенесені на енергонезалежний носій.
  * `RWF_DSYNC`: еквівалент `O_DSYNC`. Операція завершується після фіксації даних та необхідних метаданих (аналог поєднання `pwritev` + `fdatasync`). На NVMe-накопичувачах ядро транслює цей прапорець безпосередньо в біт `FUA` (Force Unit Access) блокового запиту `REQ_FUA`.
  * `RWF_NOWAIT`: забороняє блокування процесу, якщо для виконання запису потрібно очікувати вивільнення пам'яті, злиття брудних сторінок або блокування журналу. У разі затримки повертає помилку `EAGAIN`.

### `sync`, `syncfs` та `msync`

:::tabs
```c
#include <unistd.h>
#include <sys/mman.h>

void sync(void);
int syncfs(int fd);
int msync(void *addr, size_t length, int flags);
```
```cpp
#include <unistd.h>
#include <sys/mman.h>
#include <span>

void ::sync(void);
int ::syncfs(int fd);
int ::msync(void *addr, size_t length, int flags);
```
:::

* **`sync(void)`:** Асинхронно ініціює винесення **всіх** брудних сторінок і метаданих усіх змонтованих файлових систем у системі. Не повертає помилок і не гарантує очікування завершення запису на накопичувачах у старих стандартах (у сучасному Linux очікує підтвердження черг).
* **`syncfs(int fd)`:** Синхронізує виключно ту файлову систему, якій належить відкритий дескриптор `fd`. Повертає `0` або `-1` (передаючи помилки вводу-виводу, зафіксовані суперблоком).
* **`msync(addr, length, flags)`:** Застосовується для пам'яті, відображеної через `mmap()`.
  * `MS_SYNC`: синхронний запис брудних сторінок діапазону з блокуванням до завершення апаратного винесення;
  * `MS_ASYNC`: планує винесення сторінок диспетчером ядра й негайно повертає керування;
  * `MS_INVALIDATE`: робить недійсними інші копії кешу для повторного читання з носія.

### Асинхронна синхронізація через `io_uring`

Сучасний інтерфейс асинхронного вводу-виводу Linux `io_uring` надає пряму підтримку операцій синхронізації без блокування потоку процесу:

* **`IORING_OP_FSYNC`:** Код операції у дескрипторі черги подання (SQE). Виконує асинхронний аналог `fsync()` або `fdatasync()`.
* **Прапорець `IORING_FSYNC_DATASYNC`:** Якщо встановлено у полі `sqe->fsync_flags`, операція виконується за семантикою `fdatasync()`.
* **Прапорець ланцюжка `IOSQE_IO_DRAIN`:** Змушує `io_uring` виконати операцію синхронізації строго після завершення всіх попередніх запитів у черзі, забезпечуючи впорядкований транзакційний бар'єр без зупинки процесорного потоку.

### Пастка виклику `sync_file_range`

:::tabs
```c
#define _GNU_SOURCE
#include <fcntl.h>

int sync_file_range(int fd, off64_t offset, off64_t nbytes,
                    unsigned int flags);
```
```cpp
#define _GNU_SOURCE
#include <fcntl.h>
#include <cstdint>

int ::sync_file_range(int fd, off64_t offset, off64_t nbytes,
                      unsigned int flags);
```
:::

* **Прапорці:**
  * `SYNC_FILE_RANGE_WAIT_BEFORE`: очікування завершення вже розпочатого запису для вказаного діапазону;
  * `SYNC_FILE_RANGE_WRITE`: ініціація запису брудних сторінок діапазону у чергу блокового рівня;
  * `SYNC_FILE_RANGE_WAIT_AFTER`: очікування завершення запису сторінок, поставлених у чергу.
* ⚠️ **Критичне застереження:** Цей системний виклик **не є засобом забезпечення довговічності даних**. Він:
  1. Не викликає фіксації транзакції в журналі файлової системи (метадані екстентів залишаються несинхронізованими);
  2. Не надсилає команду скидання апаратного кешу накопичувача (`FLUSH` / `FUA`).
  Його єдине призначення — рівномірне фонове виштовхування сторінок для запобігання переповненню кешу пам'яті великими потоками запису.

## Прапорці відкриття файлів (`open`, `openat`)

Поведінка буферизації та синхронізації може бути задана на рівні опису відкритого файлу (`struct file`).

| Прапорець | Семантика на рівні VFS | Вплив на Page Cache | Вплив на метадані | Поведінка кожного виклику `write()` |
| :--- | :--- | :--- | :--- | :--- |
| **`O_SYNC`** | Повна синхронізація | Дані пишуться через кеш | Оновлює всі метадані (`mtime`, `ctime`, розмір) | Блокується до запису даних, метаданих і виконання Flush |
| **`O_DSYNC`** | Синхронізація цілісності даних | Дані пишуться через кеш | Оновлює лише метадані, потрібні для читання | Блокується до запису даних і виконання Flush/FUA |
| **`O_RSYNC`** | Синхронізація читання | Діє у парі з `O_SYNC` / `O_DSYNC` | Очікує завершення активних записів | Читання очікує фіксації паралельних змін на диску |
| **`O_DIRECT`** | Прямий ввід-вивід | **Повний обхід Page Cache** | Звичайне виділення блоків ФС | Запит передається безпосередньо контролеру через DMA |

### Вимоги до вирівнювання при використанні `O_DIRECT`

При відкритті дескриптора з `O_DIRECT` ядро Linux вимагає суворого вирівнювання за межами фізичного або логічного сектора блокового пристрою (типово 512 або 4096 байтів):
1. **Покажчик буфера в пам'яті** (`void *buf`): адреса повинна бути кратна розміру сектора (виділяється через `posix_memalign()` або `aligned_alloc()`).
2. **Зсув у файлі** (`off_t offset`): повинен бути строго кратний розміру сектора.
3. **Розмір порції запису** (`size_t count`): довжина повинна бути кратна розміру сектора.

Порушення будь-якої з цих трьох умов призводить до негайного повернення помилки `-EINVAL`.

> 🔧 **Навіщо це.** `O_DIRECT` усуває подвійне копіювання пам'яті між буфером процесу та сторінковим кешем ядра, а також знімає навантаження з алгоритмів витіснення сторінок пам'яті (reclaim). Проте `O_DIRECT` **не замінює `fsync`**: контролер накопичувача все одно може зберегти надіслані через DMA дані у своєму летючому DRAM-кеші, тому для довговічності комбінують `O_DIRECT | O_DSYNC` або явно викликають `fdatasync()`.

## Параметри ядра Linux для керування брудними сторінками (`/proc/sys/vm/`)

Ядро Linux балансує між продуктивністю відкладеного запису та ризиком втрати даних за допомогою підсистеми зворотного запису (*writeback*). Налаштування здійснюються через віртуальну файлову систему `procfs`.

```
/proc/sys/vm/
├── dirty_background_ratio       # Відсоток пам'яті для фонового старту flusher-потоків
├── dirty_background_bytes       # Альтернатива в байтах (0, якщо активний ratio)
├── dirty_ratio                  # Відсоток пам'яті, при якому процес блокується (throttle)
├── dirty_bytes                  # Альтернатива dirty_ratio в байтах
├── dirty_expire_centisecs       # Максимальний вік брудної сторінки перед винесенням
├── dirty_writeback_centisecs    # Інтервал пробудження фонових потоків ядра
└── dirtytime_expire_seconds     # Інтервал скидання «ледачих» міток часу inodes
```

### Детальний опис параметрів

* **`vm.dirty_background_ratio` (типово: `10` %):**
  Частка оперативної пам'яті (від доступної пам'яті `MemAvailable`), зайнята брудними сторінками, досягнення якої змушує фонові потоки ядра `wb_workfn` (kworker) розпочати асинхронне виштовхування даних на накопичувач. Процеси-письменники при цьому не блокуються.
* **`vm.dirty_background_bytes` (типово: `0`):**
  Абсолютний ліміт у байтах. Якщо встановлено ненульове значення, параметр `dirty_background_ratio` ігнорується. Рекомендується для серверів із великим обсягом оперативної пам'яті (128–512 ГіБ), де 10 % означало б накопичення десятків гігабайтів нескинутих даних.
* **`vm.dirty_ratio` (типово: `20` %):**
  Жорсткий ліміт брудної пам'яті. Якщо інтенсивність генерації даних перевищує пропускну здатність диска і частка брудних сторінок сягає цього значення, функція `balance_dirty_pages()` переводить сам процес-письменник у стан синхронного очікування: кожен наступний виклик `write()` заморожується, поки процес власноруч не скине порцію даних на диск.
* **`vm.dirty_bytes` (типово: `0`):**
  Абсолютний ліміт жорсткого дроселювання в байтах.
* **`vm.dirty_expire_centisecs` (типово: `3000`, тобто 30 секунд):**
  Час у сотих долях секунди (сантисекундах). Сторінка, позначена прапорцем `PG_dirty`, яка перебуває в пам'яті довше за цей інтервал, вважається протермінованою і підлягає обов'язковому винесенню під час наступного циклу flusher-потоку.
* **`vm.dirty_writeback_centisecs` (типово: `500`, тобто 5 секунд):**
  Період пробудження фонової черги завдань зворотного запису для перевірки наявності протермінованих сторінок. Якщо встановити в `0`, періодичний фоновий виклик вимикається повністю (скидання відбуватиметься лише за лімітом обсягу або явним `sync`).
* **`vm.dirtytime_expire_seconds` (типово: `43200`, тобто 12 годин):**
  Керує прапорцем монтування `lazytime`. Оновлення часу доступу та модифікації тримаються виключно в пам'яті `struct inode` і скидаються на диск або через 12 годин, або попутно з винесенням блоків даних файлу.

## Атрибути черги блокових пристроїв (`/sys/block/<dev>/queue/`)

Ядро надає інтерфейс діагностики та конфігурації кешування контролера конкретного накопичувача через `sysfs`.

```
/sys/block/nvme0n1/queue/
├── write_cache        # Режим кешу запису: "write back" або "write through"
├── fua                # Підтримка Force Unit Access апаратурою (1 або 0)
├── rotational         # Ознака магнітного накопичувача HDD (1) чи SSD/NVMe (0)
├── nr_requests        # Глибина черги запитів блокового планувальника
├── dax                # Прямий доступ до енергонезалежної NVDIMM-пам'яті (1 або 0)
└── max_sectors_kb     # Максимальний розмір одного блокового запиту
```

### Значення та діагностичне використання

* **`write_cache` (`cat /sys/block/sda/queue/write_cache`):**
  * `write back`: накопичувач повідомив ядру про наявність власного летючого DRAM/SRAM кешу запису. У цьому режимі блоковий шар ядра зобов'язаний генерувати та надсилати запити `REQ_PREFLUSH` / `REQ_FUA` під час кожного виклику `fsync()`.
  * `write through`: кеш накопичувача або вимкнено, або він працює в наскрізному режимі. Ядро оптимізує тракт і **не надсилає команди скидання кешу**.
  * ⚠️ *Небезпека:* Якщо вручну записати `write through` у цей файл для пристрою, який фактично має увімкнений летючий кеш без захисту живлення (PLP), ядро перестане штовхати бар'єри, і раптове знеструмлення гарантовано призведе до пошкодження файлової системи.
* **`fua` (`cat /sys/block/nvme0n1/queue/fua`):**
  * `1` — контролер підтримує апаратний біт FUA у командах запису. Ядро може надсилати одиничні критичні транзакції прямо в енергонезалежні комірки без необхідності скидати весь обсяг DRAM-кешу.
  * `0` — FUA не підтримується; замість нього ядро емулює бар'єр послідовністю «Запис блоків + окрема команда `FLUSH CACHE`».
* **`rotational` (`cat /sys/block/sda/queue/rotational`):**
  * `1` — пристрій має рухомі пластини та магнітні голівки (HDD). Блоковий шар застосовує агресивне злиття та сортування секторів.
  * `0` — твердотільний носій (SSD/NVMe). Увімкнено режим швидкої паралельної диспетчеризації `blk-mq`.

## Опції монтування файлових систем (Ext4, XFS)

Режим забезпечення довговічності та журналювання встановлюється під час монтування розділу утилітою `mount`.

### Ext4: Режими журналювання (`data=`)

1. **`data=journal`:**
   Найвищий рівень надійності. Усі зміни — як метадані файлової системи, так і самі сторінки даних користувача — спочатку повністю записуються в кільцевий журнал JBD2, фіксуються бар'єром коміту, і лише потім переносяться на свої постійні місця у файловій системі.
   * *Ціна:* Кожен байт записується на фізичний носій двічі. Пропускна здатність падає у 2–3 рази.
2. **`data=ordered` (типовий стандарт Linux):**
   Журналюються лише метадані. Проте ядро гарантує суворий порядок: усі змінені блоки даних файлу записуються на диск **до того**, як відповідна транзакція метаданих (розмір файлу, екстенти) отримає запис про фіксацію в журналі.
   * *Перевага:* Запобігає появі «сміття» та фрагментів чужих видалених файлів у хвості нового файлу після збою живлення.
3. **`data=writeback`:**
   Журналюються лише метадані, але порядок між винесенням блоків даних і фіксацією транзакції журналу не контролюється. Блоки даних можуть опинитися на носії значно пізніше за запис метаданих.
   * *Ризик:* Після аварійного перезавантаження розширений файл може містити неініціалізовані старі дискові сектори.

### Додаткові опції Ext4 та XFS

* **`barrier=1` / `barrier=0` (або `nobarrier` у XFS/Ext4):**
  Вмикає або вимикає надсилання апаратних бар'єрів запису (`FLUSH`/`FUA`) контролеру накопичувача під час фіксації транзакцій журналу.
  * ⚠️ *Вимкнення `barrier=0` є неприпустимим на споживчих SSD без конденсаторів PLP: це призводить до руйнування дерева екстентів при першому ж стрибку напруги.*
* **`commit=N` (Ext4, типово `commit=5` секунд):**
  Максимальний інтервал між автоматичними синхронізаціями транзакцій журналу JBD2. Збільшення до `commit=60` зменшує навантаження на диск, але збільшує часове вікно втрати даних до 60 секунд.
* **`lazytime` (Ext4/XFS):**
  Оновлює поля `atime`, `mtime`, `ctime` виключно в оперативній пам'яті структури `struct inode`. На диск вони потрапляють або при модифікації самого вмісту файлу, або за таймером `dirtytime_expire_seconds`.
* **`wsync` (XFS):**
  Змушує всі операції модифікації простору імен і метаданих (створення файлу, видалення, перейменування) виконуватися синхронно, очікуючи запису в лог.

## Апаратні команди керування кешем накопичувачів

На найнижчому рівні блоковий драйвер операційної системи взаємодіє з мікропрограмою накопичувача через стандартизовані протоколи інтерфейсів.

### 1. Протокол NVMe (Non-Volatile Memory Express)

* **Команда `Flush` (Код операції `0x00`):**
  Надсилається у Submission Queue контролера NVMe. Змушує контролер перенести весь вміст свого внутрішнього летючого кешу запису (Volatile Write Cache) у масиви енергонезалежної пам'яті NAND Flash для всіх просторів імен (Namespaces). Команда завершується записом у Completion Queue лише після фізичного запису на флеш.
* **Біт `FUA` (Force Unit Access, Біт 30 у Command Dword 12 команди Write `0x01`):**
  Якщо цей біт встановлено в `1`, контролер зобов'язаний записати корисне навантаження саме цієї конкретної команди `Write` безпосередньо в енергонезалежний носій, оминаючи DRAM-кеш або фіксуючи його в захищеному конденсаторами секторі, перш ніж надіслати повідомлення про завершення.
* **Керування летючим кешем (Set Features, Feature ID `0x06`):**
  Дозволяє програмно увімкнути (біт 0 = 1) або вимкнути (біт 0 = 0) використання летючого буфера запису накопичувача.

### 2. Протокол SATA / ATA (Advanced Technology Attachment)

* **`FLUSH CACHE` (Код команди `0xE7`, 28-бітне LBA):**
  Змушує накопичувач скинути буфер DRAM на магнітні пластини або NAND-комірки.
* **`FLUSH CACHE EXT` (Код команди `0xEA`, 48-бітне LBA):**
  Розширена версія для дисків великої ємності. Застосовується ядром Linux при кожному виклику `fsync()` на SATA-накопичувачах.
* **Керування через утиліту `hdparm`:**
  * Перевірка стану кешу: `hdparm -W /dev/sda`
  * Вимкнення летючого кешу накопичувача: `hdparm -W0 /dev/sda`

### 3. Протокол SCSI / SAS (Small Computer System Interface)

* **`SYNCHRONIZE CACHE (10)` (Код операції `0x35`):**
  Синхронізація діапазону логічних блоків кешу SCSI-пристрою. Якщо довжина та початковий блок встановлені в 0 — скидається весь кеш.
* **`SYNCHRONIZE CACHE (16)` (Код операції `0x91`):**
  64-бітна версія для великих масивів і LUN.
* **Біт `FUA` (Force Unit Access) у командах `WRITE (10)` / `WRITE (16)`:**
  Забезпечує прямий запис зазначених секторів на фізичний носій без скидання решти кешу.

## Інструменти трасування та перевірки бар'єрів у реальному часі

Для підтвердження того, що команди синхронізації дійсно проходять усі шари системи й доходять до фізичного накопичувача, утиліти ядра використовують точки трасування (tracepoints).

### Трасування через `bpftrace`

Перевірка перехоплення системних викликів `fsync` та виходу команд на блоковий рівень:

```bash
# Підрахунок кількості викликів fsync/fdatasync за процесами
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_fsync,tracepoint:syscalls:sys_enter_fdatasync { @[comm, probe] = count(); }'

# Фіксація блокових запитів із прапорцями PREFLUSH та FUA
sudo bpftrace -e '
tracepoint:block:block_rq_issue {
    $is_flush = args->rwbs & 1; // бітовий прапорець FLUSH/FUA
    if ($is_flush) {
        printf("PID %d (%s) -> Пристрій %s: Операція %s, Сектор %llu, Розмір %u байтів\n",
               pid, comm, args->dev, args->rwbs, args->sector, args->nr_bytes);
    }
}'
```

Ці механізми дають змогу розробнику точно оцінити ціну надійності та побудувати правильний баланс між продуктивністю операцій уводу-виводу та гарантіями цілісності даних.
