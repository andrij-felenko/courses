# 📋 Матриця метрик діагностики за методом USE

Матриця діагностики за методом USE (Utilization, Saturation, Errors — утилізація, насичення, помилки) є системним довідником для локалізації вузьких місць продуктивності та апаратних збоїв на рівні операційної системи Linux. Метод розробив провідний інженер із продуктивності Брендан Грегг (Brendan Gregg) як детерміновану стратегію інспекції всіх апаратних і віртуальних ресурсів системи для швидкого пошуку першопричини інцидентів без хаотичного перебору налаштувань.

Для кожного фізичного або абстрактного ресурсу операційної системи послідовно аналізуються три ортогональні виміри:
* **Utilization (Утилізація):** середня частка часу або місткості, протягом якої ресурс зайнятий виконанням корисної роботи.
* **Saturation (Насичення / переповнення):** міра наявності відкладеної роботи, яка не може бути виконана негайно і накопичується в чергах очікування.
* **Errors (Помилки):** кількість та частота апаратних збоїв, відкинутих запитів, втрачених пакетів чи аварійних подій.

## 1. Підсистема процесора (CPU)

Процесорний ресурс охоплює фізичні ядра, логічні апаратні потоки (SMT/Hyper-Threading), черги готовності планувальника завдань (`runqueue`) та механізми перемикання контексту.

### Механізм обліку та метрики ядра

Облік процесорного часу в Linux базується на періодичних перериваннях системного таймера (Timer Jiffies) або високоточних апаратних лічильниках (TSC, Time Stamp Counter). Ядро підсумовує кількість тактів, проведених кожним логічним ядром у різних станах виконання, та експортує їх у першому рядку файлу `/proc/stat`.

* **Час користувача (`%usr`):** виконання інструкцій у непривілейованому режимі Ring 3 (прикладний код, бібліотеки, середовища виконання).
* **Час ядра (`%sys`):** виконання коду ядра в режимі Ring 0 від імені користувацького процесу (обслуговування системних викликів, перемикання таблиць сторінок MMU, незначні сторінкові збої `minflt`).
* **Час програмних переривань (`%softirq`):** відкладена обробка мережевих пакетів у підсистемі NAPI та демонах `ksoftirqd/N`.
* **Час очікування диска (`%iowait`):** частка часу, коли ядро CPU простоювало (Idle), але щонайменше один потік перебував у стані неперериваного сну `TASK_UNINTERRUPTIBLE` через дискову операцію.

### Насичення черг та тиск на процесор

Коли кількість готових до виконання потоків перевищує кількість фізичних процесорів, задачі шикуються в чергу `runqueue` відповідного ядра. У сучасному планувальнику EEVDF (Earliest Eligible Virtual Deadline First) кожна задача має віртуальний дедлайн. Якщо черга переповнена, затримка між моментом пробудження задачі (`try_to_wake_up`) і фізичним наданням процесора (Runqueue Latency) може зростати від мікросекунд до сотень мілісекунд.

Об'єктивною мірою насичення є підсистема **PSI (Pressure Stall Information)**. Метрика `some avg10` у файлі `/proc/pressure/cpu` обчислює частку часу, протягом якої готові задачі втрачали продуктивність через очікування вільного процесора.

### Тюнінг та параметри sysfs/procfs для процесора

* `/proc/sys/kernel/sched_latency_ns`: цільовий період планування, протягом якого всі готові задачі повинні отримати хоча б один квант часу.
* `/proc/sys/kernel/sched_migration_cost_ns`: мінімальний час після останнього виконання, протягом якого планувальник вважає пам'ять задачі «гарячою» в кеші поточного ядра і уникає міграції на інше ядро.
* `/sys/devices/system/cpu/cpu*/cpufreq/scaling_governor`: режим енергозбереження ядер (`performance` для усунення затримок перемикання тактової частоти P-states, `powersave` або `schedutil` для адаптивного регулювання).

## 2. Підсистема оперативної пам'яті (Memory & Swap)

Пам'ять охоплює фізичну оперативну пам'ять (RAM), дискові розділи та файли підкачки (Swap), кеш сторінок (Page Cache), буфери структур ядра (Slab/Slub) та анонімні області пам'яті застосунків.

### Механізм алокації, витіснення та фрагментації

Ядро Linux керує пам'яттю сторінками розміром 4 КіБ через систему зон (ZONE_NORMAL, ZONE_DMA32). Коли пам'ять виділяється за допомогою `malloc()`, алокатор розширює адресний простір через `brk()` або `mmap()`, але фізичні сторінки виділяються ядром ліниво — лише при першому зверненні (Minor Page Fault).

Коли рівень вільної пам'яті опускається нижче водяного знака `watermark[WMARK_LOW]`, ядро активує фоновий демон `kswapd`, який починає асинхронно скидати «холодні» анонімні сторінки у Swap та очищати кеш сторінок. Якщо темп виділення пам'яті процесами перевищує швидкість `kswapd`, ядро переводить виділяючі процеси в режим прямого відбору (**Direct Reclaim**). У цьому стані будь-який виклик алокації блокується на десятки мілісекунд, доки сам потік не звільнить потрібну кількість сторінок.

### Показники насичення пам'яті

Головним показником насичення пам'яті є не відсоток зайнятої пам'яті (оскільки Linux навмисно заповнює всю вільну RAM кешем сторінок), а показники `MemAvailable`, частота значних сторінкових збоїв `majflt` та метрика `PSI memory`. Значення `full avg10` у `/proc/pressure/memory` показує частку часу, коли всі процеси були повністю зупинені через брак RAM.

### Тюнінг та параметри sysfs/procfs для пам'яті

* `/proc/sys/vm/swappiness`: коефіцієнт агресивності витіснення анонімних сторінок у Swap відносно очищення кешу файлових сторінок (типове значення 60; для серверів баз даних часто знижують до 1–10).
* `/proc/sys/vm/dirty_ratio`: максимальний відсоток оперативної пам'яті, який можуть займати «брудні» (модифіковані, але не записані на диск) сторінки, перш ніж процеси почнуть примусово синхронізувати їх на диск.
* `/proc/sys/vm/dirty_background_ratio`: відсоток брудної пам'яті, при досягненні якого ядро у фоновому режимі активує скидання даних потоками `kworker/flush`.
* `/proc/sys/vm/min_free_kbytes`: мінімальний резерв фізичної пам'яті, який ядро ніколи не віддає під кеш сторінок, захищаючи критичні алокації переривань ядра.

## 3. Підсистема блокового вводу-виводу (Storage & Block Devices)

Блокова підсистема охоплює фізичні накопичувачі (NVMe, SATA SSD, HDD), шари багаточергових планувальників ядра (blk-mq), драйвери контролерів, журнали файлових систем та сторінковий кеш VFS.

### Черги blk-mq та час очікування операцій

Сучасні ядра Linux взаємодіють з накопичувачами через шар `blk-mq` (Block Multi-Queue), який підтримує апаратні черги для кожного процесорного ядра. Час обробки дискового запиту складається з двох частин:
1. **Час у черзі ядра (Queue Time):** тривалість перебування запиту в черзі планувальника до передачі драйверу.
2. **Час обслуговування контролером (Service Time):** фізичний час запису або зчитування комірок Flash/магнітного диска.

Метрика `r_await` в утиліті `iostat` відображає сумарний час (`Queue + Service`) для операцій читання. Оскільки читання зазвичай є блокуючим для прикладного процесу, будь-яке зростання `r_await` понад 5–10 мс призводить до накопичення процесів у неперериваному стані сну `D` (`TASK_UNINTERRUPTIBLE`).

| Вимір | Метрика | Інструмент CLI | Шлях у /proc або /sys | Інтерпретація та порогові значення |
| :--- | :--- | :--- | :--- | :--- |
| **Utilization** | `%util` (Device Bandwidth) | `iostat -xz 1` | `/proc/diskstats`<br>`/sys/block/[dev]/stat` | `%util > 90%` для традиційних дисків або одиночних SSD означає повне завантаження шини пристрою запитами. |
| **Utilization** | `r/s`, `w/s`, `rMB/s`, `wMB/s` | `iostat -xz 1`<br>`sar -d 1` | `/proc/diskstats` | Порівняння досягнутої швидкості з паспортом обладнання (наприклад, ліміт IOPS для NVMe або 250 МБ/с для SATA SSD). |
| **Saturation** | `aqu-sz` (Average Queue Size) | `iostat -xz 1` | `/sys/block/[dev]/stat` | Довжина черги `aqu-sz > 4` на один накопичувач призводить до експоненційного зростання затримки обслуговування запитів. |
| **Saturation** | `r_await`, `w_await` (Latency) | `iostat -xz 1`<br>`biolatency` (eBPF) | `/proc/diskstats` | Середній час очікування операції: для швидких NVMe норма `< 1 мс`; значення `r_await > 10 мс` є ознакою глибокого перевантаження. |
| **Saturation** | `D-state Tasks` (неперериваний сон) | `vmstat 1` (стовпчик `b`)<br>`ps aux \| grep ' D '` | `/proc/loadavg` (2-ге число)<br>`/proc/[pid]/status` | `b > 0` свідчить про наявність процесів, які зависли на очікуванні фізичного дискового вводу-виводу або блокуваннях файлової системи. |
| **Saturation** | `PSI I/O Pressure` | `cat /proc/pressure/io` | `/proc/pressure/io` | `some avg10 > 15.0` свідчить про те, що дискова підсистема є головним гальмом системи. |
| **Errors** | `I/O Failures & Timeouts` | `dmesg -T \| grep -E 'I/O\|error\|reset'` | `/sys/block/[dev]/device/` | Помилки секторів (Bad Blocks), скидання черги команд NVMe (`Controller Reset`), скидання SATA лінків, збої файлової системи. |

### Порівняння планувальників вводу-виводу (I/O Schedulers)

Сучасне ядро Linux підтримує кілька планувальників підсистеми `blk-mq`:
* **none:** Пряма передача черги запитів безпосередньо у контролер накопичувача без перевпорядкування в ядрі. Оптимальний вибір для NVMe SSD з високою внутрішньою паралельністю.
* **mq-deadline:** Забезпечує жорсткі часові дедлайни для операцій читання (500 мс) та запису (5000 мс), запобігаючи нескінченному голодуванню операцій читання при інтенсивному потоці запису.
* **bfq (Budget Fair Queueing):** Пропорційний розподіл пропускної здатності диска між процесами з урахуванням ваг cgroups та інтерактивності задач. Рекомендовано для настільних систем або змішаних середовищ.
* **kyber:** Планувальник на основі цільової затримки, який динамічно обмежує глибину черги для підтримання латентності читання нижче 2 мс.

### Тюнінг та параметри sysfs для блокових пристроїв

* `/sys/block/[dev]/queue/scheduler`: активний планувальник вводу-виводу (`none` для швидких NVMe, `mq-deadline` або `bfq` для SATA/HDD).
* `/sys/block/[dev]/queue/nr_requests`: максимальна глибина черги команд, виділених для даного блокового пристрою в пам'яті ядра.
* `/sys/block/[dev]/queue/read_ahead_kb`: обсяг пам'яті для випереджального читання файлів VFS.

## 4. Мережевий стек та інтерфейси (Network)

Мережевий ресурс включає фізичні мережеві карти (NIC), кільцеві буфери прийому та передачі (RX/TX Rings), підсистеми фільтрації пакетів (Netfilter/iptables), буфери сокетів TCP/UDP та ліміти відкритих з'єднань.

### Механізм прийому пакетів: від переривання до сокета

Коли мережева карта отримує пакет, контролер записує його в пам'ять через DMA (Direct Memory Access) у вільний слот кільцевого буфера RX Ring і генерує апаратне переривання. Драйвер вимикає апаратні переривання і передає керування підсистемі NAPI, яка вичитує пакети в контексті програмного переривання `NET_RX_SOFTIRQ`.

Якщо процесор не встигає вичитувати кільцевий буфер через високе навантаження або блокування ядер, вільні слоти в RX Ring вичерпуються, і мережева карта апаратно відкидає нові пакети. Це фіксується лічильниками `rx_dropped` або `rx_missed_errors`. На вищому рівні протоколу TCP відкинуті пакети спричиняють таймаути `RTO` (Retransmission Timeout), різке падіння розміру вікна перевантаження `cwnd` та колапс пропускної здатності з'єднання.

| Вимір | Метрика | Інструмент CLI | Шлях у /proc або /sys | Інтерпретація та порогові значення |
| :--- | :--- | :--- | :--- | :--- |
| **Utilization** | `rxpck/s`, `txpck/s`, `rxkB/s`, `txkB/s` | `sar -n DEV 1`<br>`nicstat 1`, `iftop` | `/proc/net/dev`<br>`/sys/class/net/[if]/statistics` | Відсоток використання фізичної пропускної здатності лінку (наприклад, 9.2 Гбіт/с на інтерфейсі 10 GbE становить 92% утилізації). |
| **Saturation** | `rxdrop`, `txdrop`, `overruns` | `ip -s link show [if]`<br>`ethtool -S [if]` | `/proc/net/dev`<br>`/sys/class/net/[if]/statistics/rx_dropped` | Ненульові значення `rx_dropped` або `overruns` означають, що мережева карта чи ядро відкидають пакети через переповнення буферів RX ring. |
| **Saturation** | `Recv-Q`, `Send-Q` (черги сокетів) | `ss -tulpn`<br>`netstat -s` | `/proc/net/tcp`<br>`/proc/net/sockstat` | Постійно заповнена черга `Recv-Q` сокета свідчить про те, що прикладний процес не встигає викликати `read()`/`recv()`. |
| **Saturation** | `Listen Queue Overflows` | `netstat -s \| grep -i listen`<br>`nstat -az TcpExtListenOverflows` | `/proc/net/netstat`<br>(`ListenOverflows`) | Зростання лічильника вказує на переповнення черги незавершених з'єднань (SYN/Accept Backlog) через затримки в обробці `accept()`. |
| **Saturation** | `TCP Retransmits` | `sar -n ETCP 1`<br>`tcpretrans` (eBPF) | `/proc/net/snmp`<br>(`RetransSegs`) | Відсоток повторних передач сегментів TCP `> 0.5%` свідчить про втрати пакетів у локальній мережі або переповнення проміжних маршрутизаторів. |
| **Errors** | `CRC, Frame, FIFO Errors` | `ethtool -S [if]`<br>`ip -s link` | `/sys/class/net/[if]/statistics/` | Помилки контрольних сум CRC сигналізують про пошкодження кабелю, проблеми трансивера SFP+ або апаратні дефекти порту комутатора. |

### Життєвий цикл пам'яті TCP-сокетів та стан перевантаження

Мережевий стек Linux динамічно регулює використання оперативної пам'яті для буферів TCP-з'єднань через параметр `/proc/sys/net/ipv4/tcp_mem` (три числа у сторінках розміром 4 КіБ: min, pressure, max):
* **Штатний режим (< min):** Ядро автоматично збільшує розміри буферів сокетів (`SO_RCVBUF`, `SO_SNDBUF`) для максимізації пропускної здатності згідно з правилом Bandwidth-Delay Product (BDP).
* **Режим тиску (pressure):** Коли сумарна пам'ять усіх TCP-сокетів перевищує друге число, ядро переходить у режим примусового стиснення буферів: відкидаються випереджальні сегменти out-of-order, заморожується розширення вікна прийому, а в логах ядра з'являються попередження TCP: out of memory.
* **Критичний ліміт (max):** Досягнення третього порогу призводить до скидання нових вхідних з'єднань та генерації помилок `ENOBUFS`.

### Тюнінг та параметри sysctl для мережевого стека

* `/proc/sys/net/core/somaxconn`: максимальна довжина черги очікуючих з'єднань для виклику `listen()` (за замовчуванням 4096; для навантажених веб-серверів піднімають до 65535).
* `/proc/sys/net/ipv4/tcp_max_syn_backlog`: місткість черги напіввідкритих з'єднань (SYN queue) під час встановлення TCP 3-way handshake.
* `/proc/sys/net/ipv4/tcp_rmem` та `/proc/sys/net/ipv4/tcp_wmem`: мінімальний, типовий та максимальний розміри буферів прийому та передачі для кожного TCP-сокета.
* `/proc/sys/net/core/netdev_max_backlog`: максимальна кількість пакетів у черзі вхідної обробки ядра до передачі протокольному стеку.

## 5. Системні ресурси ядра, блокування та IPC

Ресурси ядра охоплюють глобальні таблиці дескрипторів, ліміти відкритих файлів, внутрішні блокування ядра (spinlocks, rwsem), користувацькі примітиви міжпроцесної синхронізації (futex), черги повідомлень, семафори та сокети домену Unix.

### Міжпроцесна взаємодія (IPC) та черги VFS

* **Сокети домену Unix (Unix Domain Sockets):** Використовують буфери сокетів у пам'яті ядра (`/proc/net/unix`). Насичення виникає, коли черга `Recv-Q` локального сокета заповнюється, змушуючи клієнтські процеси блокуватися на виклику `send()` або `write()`.
* **Анонімні канали (Pipes) та FIFO:** Обмежені розміром буфера (за замовчуванням 64 КіБ, налаштовується через `fcntl(F_SETPIPE_SZ)`). Якщо читач не вичитує дані, записуючий процес блокується у стані сну `S`.
* **Спільна пам'ять (POSIX Shared Memory):** Обмежується файловою системою `tmpfs` у каталозі `/dev/shm`. Вичерпання простору генерує помилки `ENOSPC`.

| Вимір | Метрика | Інструмент CLI | Шлях у /proc або /sys | Інтерпретація та порогові значення |
| :--- | :--- | :--- | :--- | :--- |
| **Utilization** | `Allocated File Handles` | `cat /proc/sys/fs/file-nr` | `/proc/sys/fs/file-nr`<br>`/proc/sys/fs/file-max` | Перше число показує виділені дескриптори, третє — системний максимум. Наближення до ліміту блокує системні виклики `open`/`socket`. |
| **Utilization** | `Process Descriptor Usage` | `sysctl kernel.pid_max` | `/proc/sys/kernel/pid_max` | Загальна кількість живих процесів та ниток у системі відносно глобального ліміту `pid_max`. |
| **Saturation** | `Futex Waiters & Contention` | `perf top -e futex:futex_wait`<br>`futexlatency` (eBPF) | `/proc/[pid]/wchan`<br>`/proc/[pid]/stack` | Висока частота викликів `futex` або тисячі добровільних перемикань контексту свідчать про внутрішню боротьбу за спільні блокування. |
| **Saturation** | `Epoll Event Backlog` | `cat /proc/sys/fs/epoll/max_user_watches` | `/proc/sys/fs/epoll/max_user_watches` | Вичерпання ліміту дескрипторів, що перебувають під наглядом екземплярів `epoll`. |
| **Errors** | `EMFILE` / `ENFILE` Errors | `strace -e openat,socket` | Стандартні коди помилок системних викликів | `EMFILE (Too many open files)` означає вичерпання ліміту процесу (`ulimit -n`); `ENFILE` — вичерпання загальносистемного ліміту. |

### Динаміка кешу VFS та витоки Dentry/Inode

Кеш віртуальної файлової системи (VFS Dentry & Inode Cache) зберігає структури каталогів та метаданих файлів в оперативній пам'яті для усунення повторних звернень до накопичувача. Якщо застосунок створює мільйони тимчасових унікальних файлів або сканує великі дерева каталогів, структури dentry та inode_cache займають гігабайти пам'яті всередині незвільнюваного слябу (SUnreclaim у /proc/meminfo).

* **Метрика тиску VFS:** `/proc/sys/vm/vfs_cache_pressure` (типове значення 100). Збільшення значення до 200–500 змушує ядро агресивніше звільняти кеш dentry та inode при дефіциті пам'яті.
* **Діагностика слябів ядра:** Запуск `slabtop -s c` або аналіз `/proc/slabinfo` дозволяє миттєво локалізувати витоки внутрішніх об'єктів ядра (наприклад, переповнення `radix_tree_node` або `buffer_head`).

## 6. Зіставлення методів: USE проти RED

У практичній інженерній роботі метод USE застосовується в тандемі з методом **RED** (Rate, Errors, Duration), розробленим Томом Вілкі (Tom Wilkie). Їхня принципова відмінність полягає в фокусі спостереження:

* **Метод USE орієнтований на ресурси (Resource-Centric):** Він відповідає на запитання: *«Як почувається серверне обладнання та операційна система?»*. Його застосовують системні адміністратори, інженери інфраструктури та SRE під час аналізу серверів, вузлів кластера та віртуальних машин.
* **Метод RED орієнтований на сервіси (Service-Centric):** Він відповідає на запитання: *«Яку якість обслуговування отримує кінцевий користувач або клієнтська програма?»*. Його використовують розробники бекенду та мікросервісів для оцінки прикладних інтерфейсів API.

Зв'язок між цими двома методами є прямолінійним: **погіршення метрик RED (зростання Duration або поява помилок Errors у сервісі) є зовнішнім симптомом, який вимагає негайного запуску перевірки за методом USE для локалізації внутрішнього насиченого ресурсу (Saturation у залізі)**.

| Критерій | Метод USE (Utilization, Saturation, Errors) | Метод RED (Rate, Errors, Duration) |
| :--- | :--- | :--- |
| **Об'єкт аналізу** | Фізичні та віртуальні **ресурси** системи (залізо, ядра, диски, пам'ять, стек ОС). | Прикладні **запити та сервіси** (HTTP-запити, RPC-виклики, транзакції БД). |
| **Основне питання** | «Чи не перевантажене залізо, чи немає черг і чи справні компоненти?» | «Яку пропускну здатність має сервіс, чи не падають помилки і яка латентність?» |
| **Rate / Utilization** | Утилізація ресурсу (наприклад, 85% CPU або 700 МБ/с диска). | Частота вхідних запитів (наприклад, 15 000 HTTP запитів на секунду, RPS). |
| **Errors** | Апаратні помилки, збої пам'яті ECC, відкинуті пакети RX drop. | Коди помилок прикладного рівня (HTTP 500, 502, 504, таймаути клієнтів gRPC). |
| **Saturation / Duration** | Довжина черги планувальника, блокування в стані D, PSI pressure. | Розподіл тривалості виконання запитів: медіана p50, квантилі p95, p99. |
| **Взаємозв'язок** | Насичення ресурсів (USE) є головною **причиною** зростання латентності (RED). | Зростання тривалості (Duration у RED) є **симптомом**, що спонукає запустити аналіз USE. |

## 7. 60-секундний протокол системного скринінгу

Коли інженер підключається до термінала сервера під час аварії, перша хвилина присвячується послідовному виконанню фіксованого списку команд, що покривають усю матрицю USE:

```sh
# 1. Загальний стан, черги планувальника та пам'ять (аналіз колонок r, b, si, so, us, sy, wa)
vmstat 1 5

# 2. Розподіл процесорного часу по всіх логічних ядрах (пошук перекосу на softirq або одне ядро)
mpstat -P ALL 1 3

# 3. Дефіцит ресурсів та об'єктивний тиск на систему (PSI для CPU, Memory, I/O)
grep -H . /proc/pressure/{cpu,memory,io}

# 4. Стан блокових накопичувачів (аналіз %util, aqu-sz, r_await, w_await)
iostat -xz 1 3

# 5. Вільна, доступна та буферизована пам'ять (перевірка MemAvailable та Swap)
free -m

# 6. Мережева активність та переповнення черг інтерфейсів (rx_dropped, overruns)
sar -n DEV,EDEV 1 3

# 7. Стан сокетів, заповнення черг Send-Q та Recv-Q
ss -s; ss -tulpn | grep -E 'Recv-Q|Send-Q' | head -n 20

# 8. Топ процесів за процесорним часом, пам'яттю та станом виконання
top -b -n 1 | head -n 25

# 9. Системні логи, апаратні помилки ядра, скидання контролерів або спрацьовування OOM
dmesg -T --level=err,warn | tail -n 30
```

Виконання цього скринінгового протоколу гарантує повне охоплення всіх апаратних доменів системи і дає змогу за одну хвилину звузити поле пошуку несправності від сотень потенційних гіпотез до одного конкретного фізичного ресурсу.
