# Конвеєр книг: як це працює

Це **операційні** правила (вантажаться самі). Пояснення «чому саме так» і повна таблиця
перевірок — `agents/antigravity/pipeline.md`. Канон письма — `AUTHORING.md`. Тут механіка.

## Три ролі, які не суміщаються

| роль | агент | що робить |
|---|---|---|
| автор | `write-topic` | пише статті, вставки, `figs.py` |
| дописувач | `grow-file` | доводить ОДИН `.md` до підлоги його рівня. Нічого не переписує наново |
| суддя | `check-all` | проганяє гейт, читає теку ОДИН раз, кладе вироки під усіма номерами. **Інструментів запису не має** |
| ремонтник | `repair-topic` | переписує рівно те, що завалили перевірки |

Хто пише — не судить, хто судить — не править: у суддів немає інструментів запису, в решти —
доступу до `verdict.js`.

## Виклик сабагента

`invoke_subagent`, один спек на агента; кілька спеків — паралельний запуск.

* `TypeName` — ім'я з `.agents/agents/<name>/agent.md` (`write-topic`, `grow-file`, `check-all`,
  `repair-topic`);
* `Role` — коротко, чия це робота;
* `Prompt` — **шлях теки теми** (абсолютний або від кореня репо) плюс, для ремонтника, дефекти
  з доказами дослівно. Сабагент стартує з чистим контекстом — усе потрібне має бути в промпті;
* `Workspace` — **завжди `inherit`**: `branch` кладе вироки й правки в іншу копію репо.

**Суддя на тему ОДИН** — шість суддів × чотири кола = 24 спавни по ~20k вхідних за читання ТІЄЇ
САМОЇ статті. **Розводити перевірки по окремих агентах заборонено.** Забути щось він не може:
вирок кладеться під СВОЇМ номером, і гейт червоний, доки номер порожній. Непорушний порядок —
**11-та ПЕРША, до читання файлу**. **Гейт суддя не переганяє** — бере пункти `verdict.js --list`.

## Правила книги — `_canon.md`

Є **`<вид>/<книга>/_canon.md`** — його читає **ПЕРШОЮ дією КОЖЕН агент**: автор, дописувач,
суддя, ремонтник. Це додаткові правила саме цієї книги (наскрізний приклад, єдині терміни, мова
прикладів); де він уточнює загальне — перевага за ним, де мовчить — `AUTHORING.md`. Судді це
потрібно не менше: не знаючи домовленостей книги, він визнає дефектом свідоме рішення.

## Цикл теми

```
write-topic пише тему (або grow-file дописує файл)
     ↓
node scripts/checks/gate.js "<тека теми>"     0 = ГОТОВО · 4 = ЗАСТІЙ, до людини · 1 = далі
     ↓
ОДИН check-all на тему: 11-та сліпо, тоді читання теки, тоді вироки під усіма номерами
     код 1 — дефекти вже перелічив скрипт, вироку не треба
     код 2 — вирок на кожен пункт: ok (закрито) | defect (у ремонт)
     ВСІ дефекти кола йдуть в ОДИН repair-topic, а не по одному
     ↓
repair-topic переписує рівно те, що завалилось   (дефект 13-ї — назад до write-topic)
     ↓
знову gate.js
```

**Чому це закінчується.** Вирок прив'язаний до хеша тексту пункту: переписаний текст його
протухає. **Стеля — 2 кола НА НЕЗМІННОМУ ТЕКСТІ** (`CHECKS_MAX_ROUNDS`), далі `4` — до людини.
**Коло — це зміна, а не запуск:** гейт рахує коло, лише коли підпис теми змінився.

## Команди

```
node scripts/checks/gate.js "<тека>"                    # стан теми: 0 / 1 / 4
node scripts/checks/gate.js --topics "<тека>" …         # по кількох; --batch <файл> — по черзі
node scripts/checks/NN-*.js "<тека>"                    # одна перевірка
node scripts/checks/verdict.js NN "<тека>" --item <N> --status ok|defect --proof "<доказ>"
   кілька --item поспіль в ОДНОМУ виклику — серія вироків;  --list — пункти й наявні вироки
node scripts/antigravity/newtopic.js --book … --kind … --section … --slug … --title … --why … --meets <ознаки через кому>   (--book може бути ІНШОЮ книгою, ніж стаття)
node scripts/antigravity/update-queue.js --book … [--status update] [--limit N] [--write]
node scripts/antigravity/assess-gate.js --batch <файл>   # 0 прийнято · 1 оцінювати НАНОВО
node scripts/antigravity/finish-batch.js --book … --kind … [--batch <файл>] [--apply]
node scripts/audit-layout.js                            # диск ↔ маніфест: розлади розкладки
```

Команди — з кореня репо; шлях теки приймається і відносний, і абсолютний.

## Сімнадцять перевірок, один суддя

`01` формули · `02` мова · `03` фігури · `04` текст у фігурах · `05` лінки й вставки · `06` обсяг ·
`07` числа · `08` арифметика · `09` терміни · `10` факти (вебпошук) · `11` вступ (СЛІПО, перша) ·
`12` нитка · `13` гейт базової · `14` пояснення чи підручник · `15` обґрунтованість тверджень ·
`16` зобов'язання теми · `17` де є C — має бути й C++.

Усі сімнадцять судить `check-all` за одне читання теки. **03, 04, 05 вироку не потребують** —
там його дає скрипт. **13 і 16** повертаються АВТОРОВІ, а не ремонтникові: це нова робота
(написати базову, дописати обіцяну вставку), а не правка наявного.

Судять **читанням**, ніколи списком слів: скрипт лише витягає місце рішення. Виняток один —
заборонені каноном ФОРМИ (сирий LaTeX, «у цій статті ми розглянемо»): там ідеться про наявність
конструкції. Вирок без конкретного доказу `verdict.js` відкидає сам; «усе гаразд» вироком не є.

## Обсяг: рівень розкриття підіймає підлогу

**Спільного орієнтиру немає** — показане моделі число стає ціллю (двічі заміряно, в обидва боки:
довідник §4). Число тут **своє на кожну тему**: смуга виду ділиться на п'ять зон, рівень підіймає
**нижній** край на початок своєї.

    підлога(вид, рівень) = lo + (рівень − 1) × (hi − lo) / 5

| вид | смуга | Р1 | Р2 | Р3 | Р4 | Р5 |
|---|---|--:|--:|--:|--:|--:|
| детальна `<slug>-d.md` | 1400–9100 | 1400 | 2950 | 4500 | 6000 | 7550 |
| `hist-` / `comp-` | 500–6500 | 500 | 1700 | 2900 | 4100 | 5300 |
| `math-` / `proj-` | 650–6500 | 650 | 1800 | 3000 | 4150 | 5350 |
| `api-` | 700–8000 | 700 | 2150 | 3600 | 5100 | 6550 |

**Верхній край спільний для всіх рівнів:** рівень задає низ, а не ціль. Переріс зону й лишився
під стелею — рівень недооцінили, текст правильний; двостороннє вікно зіштовхнулося б із залізним
«скорочувати заборонено». **Базова рівня не має** — її тримає §3 «≤ ½ детальної», смуга 650–1550.

Нижче підлоги свого рівня — дефект. Понад виняткову стелю — дефект (ділити тему). На дві зони
вище своєї — пункт на вирок «рівень занижено чи текст роздутий», судиться **читанням**.
**Скорочувати заради гейта заборонено.** Недобір лікується дописуванням, перебір — поділом.

### Рівень: хто ставить і де лежить

Ставить **окрема фаза оцінки на старті батчу**, і **не той, хто писатиме**. Оцінювач бачить теми
батчу (назва + `scope`) і розкладає їх **одну проти одної**: спершу найслабша й найсильніша, тоді
решта між ними. Абсолютне «наскільки ця тема важлива» сповзає в середину.

| Р1 | дотична — читач її мине без утрати |
|---|---|
| **Р2** | звичайна — своє місце в розділі, але на неї ніхто не спирається |
| **Р3** | робоча — на неї спираються сусідні теми |
| **Р4** | несуча — без неї розділ не читається |
| **Р5** | наріжна — книга стоїть на ній |

Ознаки: скільки тем книги назвали її в `<preknowlist>` · чи вона ціль `ref` у курсі · скільки
механізмів треба показати (1 · 2–3 · 4–6 · >6) · скільки в неї вставок.

**Розкладку приймає гейт, а не оцінювач:** `assess-gate.js` дивиться на батч як ціле й відхиляє
той, де майже все названо дотичним. Відхилив — крок оцінки НАНОВО: той самий промпт, свіжий агент.
⛔ **Порогів оцінювачеві не показують ніколи** — ні числом, ні натяком, ні «минулого разу вийшло
замало»: інакше рівні означатимуть арифметику, а не важливість тем. Переоцінка ТИХА. Третє
відхилення — до людини.

Живе **у батч-файлі прогону** (`scripts/_finish/_batch-<книга>.json`) поруч зі списком тем:
`{ "dir": …, "level": 3, "inserts": { "proj-x.md": 2 } }`. Файлу в теці теми немає: рівень —
параметр прогону, а не властивість статті. Письменник дістає число в завданні — **свій рівень
собі не ставить**. Рівень вставки він оголошує у звіті (наперед її не існує), у батч-файл
переносить оркестратор; рівню теми він **не дорівнює**.

**Рівень не міняється посеред письма.** Не вліз — це привід дописати, а не понизити оцінку.
Єдиний законний вихід із-під підлоги — звіт «ПІДЛОГА НЕДОСЯЖНА» з доказом і пропозицією рівня;
рішення ухвалює людина.

## Гейт базової (перевірка 13)

Детальну пишемо завжди, базову — за потреби, і потреба рідкісна. Рішення ухвалюють **за готовою
детальною**: `< 3150` слів прози — базової не пишемо · `3150–5600` — вирішує зміст (ознаки §3,
вагання → ні) · `> 5600` — базова потрібна, дефолт «ні» тут не діє. Дефект 13-ї — авторська
робота, не ремонтна.

## Що означає «тема закрита» (перевірка 16)

Тема закрита, коли справджуються всі:

1. **детальна** написана; **рішення про базову** ухвалене (13-та);
2. **кожна вставка** — обіцяна в прозі `root:`-лінком і записана в маніфесті `pending` — написана;
3. **кожне вагоме поняття**, на яке стаття спирається, має тему або стоїть у черзі нових;
4. усі 17 перевірок дали `0`.

Аж тоді `finish-batch.js` ставить `detailed: recheck`, `basic: recheck|empty`, вставки `recheck`
— і **щойно тоді ж** реєструє нові теми з черги як `basic:empty` + `detailed:pending`.

**Чому `recheck`, а не `done`:** сімнадцять перевірок означають «конвеєр свою частину зробив», а
не «людина це читала». У `done` переводить людина, не батч.

### Вставка чи нова тема — рішення свідоме (§6)

**Вставка** — матеріал ЦІЄЇ теми: історія цього механізму, виведення цієї формули, проект на
цьому предметі. Файл у теці теми. Ознака: поза статтею матеріал не має власного читача.

**Тема** — самостійне поняття, на яке стаття лише **спирається**: про нього можна написати
статтю, яку читатимуть, не читавши цієї. Планка — рахунок: чотири ознаки (`too-big`, `key`,
`eases`, `searchable`), вистачає ДВОХ, перелічуєш їх у `--meets`. Поняття чужої галузі йде в
ІНШУ книгу (`--book math`), а не відкидається. Заводиться `newtopic.js` — у чергу, не в роботу;
стеля — дві на статтю. Лінк ставиться одразу й битим не вважається: 05-та знає про чергу.

Перед заведенням перевір, чи це не синонім наявної: вужче й ширше про те саме
(`aslr` ↔ `rop-and-aslr`), абревіатура й розшифровка (`ksm` ↔ `ksm-page-merging`). Знайшов
близьке — ref-ни наявну. Помилка коштує в обидва боки: поняття, заховане у вставку, читач не
знайде пошуком; роздута до теми вставка розриває нитку.

## Батч і маніфест

```
перед:  node scripts/audit-layout.js <вид>/<книга> — тека ≠ секція ламає запис маніфесту
старт:  список тем батчу → scripts/_finish/_batch-<книга>.json
оцінка: ОДИН агент розкладає теми одна проти одної → рівень 1–5 кожній, назад у той самий
        файл: [{"dir": …, "level": N}, …] → assess-gate.js: код 1 = оцінювати НАНОВО
письмо: теми своїми циклами, ≤4 одночасно; рівень іде письменникові в завданні
нове:   помітив залежну тему → newtopic.js (У ЧЕРГУ, не в роботу й не в маніфест)
кінець: усі теми дали gate = 0 → finish-batch.js --apply
```

**Маніфест чіпаємо один раз — останнім рядком.** `finish-batch.js` сам ганяє гейт і не пише
нічого, якщо хоч одна тема не готова.

## Дописування вже написаного — `/update-batch`

Файл у статусі `update`, коротший за підлогу свого рівня, — свій цикл, не письмо й не ремонт.
Робота **файлова** (статус має кожна версія і кожна вставка окремо), суд — темний. Чергу дає
`update-queue.js`, дописує `grow-file`, далі гейт, суд, ремонт, `finish-batch`.

Дописувач, який не дійде до підлоги без води, **зупиняється й пише «ПІДЛОГА НЕДОСЯЖНА»** з
доказом і пропонованим рівнем; рівня не міняє, рішення за людиною. Це єдиний законний вихід
з-під підлоги — без нього «підлога обов'язкова» + «скорочувати заборонено» були б пасткою.

## Заборонено

Ставити `done` за власною заявою · правити `manifest.json` будь-чим, крім `finish-batch.js` ·
зводити в одного агента перевірки поза таблицею вище (і розводити зведені) · спавнити сабагента
з `Workspace: branch` · судити текст, який сам написав, і правити текст, який сам судив ·
**ставити рівень темі, яку сам писатимеш, і міняти свій рівень посеред роботи** · лікувати обсяг
чи ясність скороченням · починати нову тему посеред батчу · чіпати щось поза текою своєї теми ·
запускати наступний пакет, доки поточний не дав `gate = 0` · робити `git commit`.
