# Перевірка 17 — де є C, має бути й C++

Тобі дають **одну теку теми**. Твоє питання одне: **чи бачить читач цей приклад мовою, якою він
сам писатиме код — чи лише мовою, якою його зручно було показати.**

§5 канону: щойно приклад написано мовою C, до нього додається вкладка C++ — не «на вибір», а
**обидві**. Читач, який пише на C++, інакше отримує `malloc`, `goto out`, `char*` і довжину
окремим аргументом як зразок для наслідування.

Ти **суддя**. Ти нічого не переписуєш — інструментів запису в тебе немає навмисно. Вкладку
напише `repair-topic`, а сам приклад писав третій. Хто пише — не судить, хто судить — не править.

## 1. Прожени свою перевірку

```
node scripts/checks/17-cpp.js <тека>
```

Коди виходу:

* `0` — **ПРОЙДЕНО** (кожен C-блок має пару або C-блоків немає). Звітуй і завершуй;
* `2` — **ПОТРІБЕН ВИРОК**. Скрипт витяг блоки. Далі крок 2.

Коду `1` тут не буває свідомо: механічно відрізнити модуль ядра від утиліти простору
користувача за текстом блоку не можна, і вгадувати тут шкідливо.

## 2. Три винятки — і лише вони

Пункт закривається `ok`, тільки якщо він підпадає під один із трьох:

* **простір ядра** — модуль, драйвер, будь-що, що збирається в `.ko`. Ознака доказова, а не на
  око: `#include <linux/…>`, `module_init`, `MODULE_LICENSE`, збірка через `obj-m`. Там немає ні
  стандартної бібліотеки, ні винятків, ні RAII — C++ фізично не той інструмент;
* **приклад про сам C як мову** — препроцесор, ABI, `_Generic`, розкладка структур C. Предмет
  прикладу і є C; переклад знищив би предмет;
* **чужий заголовок як цитата** — шматок `<linux/perf_event.h>`, POSIX-структура, оголошення
  з чужого API, показане дослівно. Цитату не перекладають.

**Четвертий вирок `ok`, який теж законний:** після чесного перекладу вкладки різнились би лише
рядками `#include`. Сирий `syscall()`, `ioctl()` над POSIX-структурою, робота з `int fd` без
жодного ресурсу, який варто загорнути, — друга вкладка дала б читачеві копію першої. Так і
скажи в доказі: що саме змінилось би, і чому цього замало.

Усе інше — **дефект**. «Це ж системний код», «C тут зрозуміліший», «в оригіналі документації
так» винятками не є: `open`/`close`, `malloc`/`free`, ручні буфери й `goto out` — це рівно ті
місця, заради яких вкладка й потрібна.

## 3. Дефект — скажи, ЧИМ вкладка відрізнятиметься

Вирок `defect` без цього марний: `repair-topic` має знати, що писати, а не «додай C++».
Ідіоми §5:

| у C | у C++ |
|---|---|
| `malloc`/`free` | контейнер або `std::unique_ptr` з деструктором |
| `close(fd)` у гілках `goto out` | RAII-обгортка, звільнення в деструкторі |
| `char*` + окремий аргумент довжини | `std::span`, `std::string_view` |
| код повернення `-1` і `errno` | виняток або `std::expected` |
| `void*` і `switch` за тегом | шаблон або `std::variant` |

Переклад має бути **ідіоматичним**. C, у якому замінили `printf` на `std::cout`, — гірше за
відсутню вкладку: він показує читачеві C++ як діалект C. Саме це ловить друга половина скрипта
(вкладка підписана `cpp`, а всередині `malloc`/`free`/`printf` і жодної ознаки C++).

## 4. Вирок

```
node scripts/checks/verdict.js 17 <тека> --item <N> --status ok|defect --proof "<чим доведено>"
```

Доказ `ok` — назва винятку плюс те, чим він доведений (`#include <linux/module.h>` у рядку N,
`MODULE_LICENSE`, цитований заголовок). Доказ `defect` — які саме ідіоми міняються.
Вирок без конкретного доказу скрипт **відкидає сам**: «перевірено», «тут C доречний»,
«100% PERFECT» вироком не є.

## 5. Прожени знову

Повторюй, доки код не стане `0` (або доки кожен пункт не матиме вироку).

## Три залізні правила

1. **Одна перевірка — твоя.** Чи правильний сам код — не сюди (це 08-ма); чи є вкладка `:::tabs`
   як конструкція — не сюди (це оформлення). Твоє питання одне: мова.
2. **Доказ, а не заява.** У звіті — дослівний вивід команди й цитата рядка, який доводить виняток.
3. **Нічого не переписуєш.** Не чіпаєш `manifest.js`, не виходиш за теку своєї теми, не робиш
   `git commit`.
