# ⚙️ Знімок на microSD: камера + картка в коді

**Задача.** Плата вже на столі, живлення міцне, картка вставлена. Тепер треба, щоб код зробив просту й дуже практичну річ: **розбудити сенсор, клацнути один кадр і покласти його файлом `.jpg` на microSD** — так, щоб потім вийняти картку й побачити на комп'ютері нормальну картинку. Звучить як три рядки, а насправді тут сходяться три різні світи: драйвер камери зі своєю купою пінів, псевдостатична пам'ять під кадр і файлова система на картці, яка ділить виводи зі спалахом. Розберімо повний робочий цикл від першого `#include` до готового файлу — і всі місця, де новачок втрачає вечір на «камера мовчить» чи «картка не монтується».

Код нижче — справжній Arduino-скетч під ESP32 (той самий, що збирається в Arduino IDE чи PlatformIO), а не псевдокод: його можна вставити, залити й одразу отримати файл на картці.

## Ідея: сенсор пише кадр у PSRAM, а ви лише переливаєте байти на картку

Найважливіше зрозуміти одразу — **процесор кадр не малює й навіть не стискає**. Уся важка робота лежить на двох чужих плечах.

Перше плече — сам сенсор OV2640. Він знімає картинку, стискає її [у JPEG](book:algorithms/jpeg-intra) власним залізом і віддає ESP32 уже готовий потік стиснених байтів. Друге плече — **PSRAM** (*pseudo-static RAM* — псевдостатична зовнішня пам'ять): драйвер камери складає цей готовий JPEG у буфер саме там, бо внутрішньої SRAM мікроконтролера на кадр не вистачить. Один кадр UXGA (1600×1200) навіть у стисненому вигляді — це близько 150 кілобайтів, а розпакований був би близько 3.7 мегабайта; внутрішніх 520 кілобайтів ESP32 не вистачило б у принципі.

> 🔧 **Навіщо це.** З цього випливає весь дизайн коду. Ваша програма не «фотографує» — вона просить драйвер: «дай покажчик на останній готовий кадр». Драйвер повертає структуру з двома полями: `buf` (адреса стиснених байтів у PSRAM) і `len` (скільки їх). Усе, що лишається зробити, — **записати ці `len` байтів у файл** і **повернути буфер драйверу**, щоб він міг знімати далі. Ви — лише кур'єр між PSRAM і карткою, і саме тому дешевий процесор тягне камеру: найтяжче за нього роблять інші.

Звідси й порядок дій, який ми складемо: **(1)** розповісти драйверу, до яких саме пінів під'єднаний сенсор на цій платі, і що кадр класти в PSRAM у форматі JPEG; **(2)** підняти картку в однобітному режимі, щоб не будити спалах; **(3)** узяти кадр, злити його у файл, повернути буфер.

## Крок 1: піни камери — те, що не можна вгадати

Драйвер `esp_camera` універсальний: він працює з десятком різних плат, а плати розводять сенсор на різні виводи. Тому першим ділом ви віддаєте йому **карту пінів саме вашої плати**. Для AI-Thinker ESP32-CAM ця карта фіксована й перевірена — її не вигадують, а беруть як є:

```c
// Розводка сенсора OV2640 на платі AI-Thinker ESP32-CAM.
// Ці номери НЕ вигадують — вони визначені розводкою плати.
#define PWDN_GPIO_NUM  32   // power-down сенсора
#define RESET_GPIO_NUM -1   // апаратного reset немає (−1 = не використовується)
#define XCLK_GPIO_NUM   0   // тактовий сигнал для сенсора
#define SIOD_GPIO_NUM  26   // SCCB data (керування сенсором, як I2C)
#define SIOC_GPIO_NUM  27   // SCCB clock
#define Y9_GPIO_NUM    35   // D7  ─┐
#define Y8_GPIO_NUM    34   // D6   │
#define Y7_GPIO_NUM    39   // D5   │
#define Y6_GPIO_NUM    36   // D4   │ вісім ліній даних
#define Y5_GPIO_NUM    21   // D3   │ паралельного порту DVP
#define Y4_GPIO_NUM    19   // D2   │
#define Y3_GPIO_NUM    18   // D1   │
#define Y2_GPIO_NUM     5   // D0  ─┘
#define VSYNC_GPIO_NUM 25   // синхронізація кадру
#define HREF_GPIO_NUM  23   // синхронізація рядка
#define PCLK_GPIO_NUM  22   // тактовий сигнал пікселів
```

Тут корисно бачити, звідки береться теза «камера з'їдає майже всі виводи». Вісім ліній даних `Y2..Y9` — це і є ті вісім бітів пікселя, які сенсор виставляє паралельно щотакту `PCLK`. Плюс дві синхронізації (`VSYNC` каже «почався новий кадр», `HREF` — «іде видимий рядок»), плюс `XCLK`, яким процесор задає серце сенсору, плюс дві лінії `SIOD`/`SIOC` — це маленька шина керування (SCCB, майже точний клон I2C), через яку в сенсор пишуть налаштування яскравості, балансу білого, роздільності. Ось звідки набігає півтора десятка виводів на саму лише камеру.

Далі ці піни разом із режимом роботи складають у структуру `camera_config_t`. Це найгустіше місце всього коду, тож пройдімо його полями, а не гуртом:

```c
#include "esp_camera.h"

static camera_config_t make_camera_config(void) {
    camera_config_t config = {};        // важливо занулити всю структуру

    // канал і таймер LEDC — драйвер ними формує XCLK для сенсора
    config.ledc_channel = LEDC_CHANNEL_0;
    config.ledc_timer   = LEDC_TIMER_0;

    // вісім ліній даних
    config.pin_d0 = Y2_GPIO_NUM;  config.pin_d1 = Y3_GPIO_NUM;
    config.pin_d2 = Y4_GPIO_NUM;  config.pin_d3 = Y5_GPIO_NUM;
    config.pin_d4 = Y6_GPIO_NUM;  config.pin_d5 = Y7_GPIO_NUM;
    config.pin_d6 = Y8_GPIO_NUM;  config.pin_d7 = Y9_GPIO_NUM;

    // тактові й синхронізація
    config.pin_xclk  = XCLK_GPIO_NUM;
    config.pin_pclk  = PCLK_GPIO_NUM;
    config.pin_vsync = VSYNC_GPIO_NUM;
    config.pin_href  = HREF_GPIO_NUM;

    // шина керування сенсором (SCCB ≈ I2C)
    config.pin_sccb_sda = SIOD_GPIO_NUM;
    config.pin_sccb_scl = SIOC_GPIO_NUM;

    config.pin_pwdn  = PWDN_GPIO_NUM;
    config.pin_reset = RESET_GPIO_NUM;

    config.xclk_freq_hz = 20000000;          // 20 МГц на сенсор
    config.pixel_format = PIXFORMAT_JPEG;    // просимо готовий JPEG, не сирі пікселі

    // Розмір кадру, якість і кількість буферів — залежать від наявності PSRAM.
    if (psramFound()) {
        config.frame_size   = FRAMESIZE_UXGA; // 1600×1200 — на повну
        config.jpeg_quality = 10;             // менше число = краща якість
        config.fb_count     = 2;              // подвійний буфер
        config.fb_location  = CAMERA_FB_IN_PSRAM;
        config.grab_mode    = CAMERA_GRAB_LATEST;
    } else {
        // без PSRAM тягнемо лише скромний кадр в один буфер
        config.frame_size   = FRAMESIZE_SVGA; // 800×600
        config.jpeg_quality = 12;
        config.fb_count     = 1;
        config.fb_location  = CAMERA_FB_IN_DRAM;
        config.grab_mode    = CAMERA_GRAB_WHEN_EMPTY;
    }
    return config;
}
```

Три поля тут вирішують долю проєкту, і кожне варто зрозуміти.

**`pixel_format = PIXFORMAT_JPEG`** — це прохання «віддавай уже стиснене». Якби ви попросили `PIXFORMAT_RGB565` (сирі пікселі), сенсор віддавав би по два байти на кожен піксель, і буфер під UXGA роздувся б до тих самих небезпечних мегабайтів. JPEG знімає цю проблему в зародку.

**`fb_location`** — де жити буферу кадру. `CAMERA_FB_IN_PSRAM` кладе його в зовнішню псевдостатичну пам'ять; саме тому попередньо перевіряють `psramFound()`. **Це та сама пастка, про яку попереджають скрізь:** якщо в проєкті випадково вимкнено підтримку PSRAM (у налаштуваннях збірки чи вибором «не тієї» плати без PSRAM в Arduino IDE), то `psramFound()` поверне `false`, і код тихо впаде в куций режим SVGA — або, якщо жорстко просити UXGA без PSRAM, ініціалізація взагалі не вдасться. Класичне «камера мовчить» родом саме звідси.

**`grab_mode = CAMERA_GRAB_LATEST`** — тонкість, через яку люди годинами ловлять «камера віддає вчорашній кадр». Драйвер тримає чергу з `fb_count` буферів і за замовчуванням віддає **найстаріший** готовий, а не найсвіжіший. Для стріму це нормально, але для поодинокого знімка «зроби фото зараз» це означає, що ви отримаєте кадр, знятий кілька моментів тому. `CAMERA_GRAB_LATEST` каже драйверу тримати найновіший — і знімок стає справді знімком «тепер», а не «щойно було».

Тепер сама ініціалізація — і одразу гасимо спалах, поки він не встиг блимнути:

```c
static bool camera_start(void) {
    // Спалах сидить на GPIO4. Заганяємо його в нуль ЩЕ ДО init камери й картки,
    // щоб світлодіод не спалахнув навіть на мить.
    pinMode(4, OUTPUT);
    digitalWrite(4, LOW);

    camera_config_t config = make_camera_config();
    esp_err_t err = esp_camera_init(&config);
    if (err != ESP_OK) {
        Serial.printf("Камера не піднялася, помилка 0x%x\n", err);
        return false;   // далі йти немає сенсу
    }
    return true;
}
```

Зверніть увагу на порядок: **`GPIO4` у нуль — першим ділом**. Причина в наступному кроці.

## Крок 2: картка в однобітному режимі — і спалах замовкає

Гніздо microSD на цій платі під'єднане не по простій шині SPI, а по рідному інтерфейсу карток [SD-MMC](book:boards/microsd-card) (*SD Multi-Media Card*). Він уміє гнати дані чотирма лініями паралельно — швидко, але тоді займає шість виводів: `CLK`, `CMD` і чотири лінії даних `DATA0..DATA3`. І серед цих чотирьох ліній даних сидить біда: **`DATA1` — це той самий GPIO4, на якому висить білий світлодіод-спалах.** Тому в повному, чотирибітному режимі щоразу, коли картка передає дані, спалах моргає в такт запису — уночі камера сама себе засліплює.

Вихід елегантний і задається одним прапорцем. Функція `SD_MMC.begin()` бере другим аргументом ознаку однобітного режиму:

```c
#include "SD_MMC.h"

static bool sdcard_start(void) {
    //                         точка монтування,  1-біт-режим
    if (!SD_MMC.begin("/sdcard", true)) {
        Serial.println("microSD не змонтувалася");
        return false;
    }
    // Перевіримо, що картка справді вставлена, а не «просто змонтувалося».
    uint8_t type = SD_MMC.cardType();
    if (type == CARD_NONE) {
        Serial.println("Картки в гнізді немає");
        return false;
    }
    return true;
}
```

Той самий `true` другим аргументом робить одразу три корисні речі. По-перше, картка тепер тримає **одну** лінію даних (`DATA0`) замість чотирьох — і `DATA1`/`GPIO4` більше не смикається карткою, спалах перестає моргати. По-друге, звільняються **GPIO12 і GPIO13** (це були `DATA2` і `DATA3`) — два живі виводи повертаються у ваше розпорядження, і саме на них потім часто вішають давач по I2C. Платня — нижча швидкість запису, але для поодиноких знімків чи журналу її з головою.

> 🔧 **Навіщо це.** Ось чому на кроці 1 ми загнали GPIO4 у нуль **до** старту картки. Порядок тонкий: спершу `digitalWrite(4, LOW)` фіксує «спалах вимкнено», і лише потім піднімається картка в однобітному режимі, де GPIO4 узагалі не її лінія. Разом це дає **абсолютно тихий запис**: світлодіод не блимає ні під час монтування, ні під час зливання файлу. Якщо ж змонтувати картку в чотирибітному режимі (`SD_MMC.begin()` без другого аргументу або з `false`), то жодне гасіння GPIO4 не допоможе — картка перехопить цю лінію собі, і моргання повернеться.

Маленька, але важлива деталь: `SD_MMC.begin()` може повернути `true`, навіть якщо картка кепська або погано вставлена, тому окрема перевірка `cardType() == CARD_NONE` відсіює випадок «гніздо є, картки нема». Без неї запис у неіснуючу картку провалиться пізніше й глухо.

## Крок 3: знімок і файл — власне те, заради чого все

Тепер найкоротша частина, бо вся підготовка вже позаду. Беремо кадр, відкриваємо файл, ллємо байти, повертаємо буфер:

```c
static bool save_photo(const char *path) {
    // 1. Просимо драйвер камери віддати готовий кадр.
    camera_fb_t *fb = esp_camera_fb_get();
    if (!fb) {
        Serial.println("Не вдалося зняти кадр");
        return false;
    }

    // 2. Відкриваємо файл на картці для запису.
    File file = SD_MMC.open(path, FILE_WRITE);
    if (!file) {
        Serial.printf("Не відкрити файл %s\n", path);
        esp_camera_fb_return(fb);   // буфер усе одно ПОВЕРНУТИ
        return false;
    }

    // 3. Ллємо стиснені байти JPEG у файл одним махом.
    file.write(fb->buf, fb->len);   // fb->buf — адреса, fb->len — довжина
    file.close();

    Serial.printf("Збережено %s  (%u байт)\n", path, (unsigned)fb->len);

    // 4. ОБОВ'ЯЗКОВО повертаємо буфер драйверу.
    esp_camera_fb_return(fb);
    return true;
}
```

Тут кожен рядок несе сенс, і два з них — критичні.

`esp_camera_fb_get()` повертає покажчик на структуру `camera_fb_t`. Нам із неї потрібні лише два поля: `fb->buf` — адреса стиснених байтів JPEG у PSRAM, і `fb->len` — скільки цих байтів. Оскільки формат уже JPEG, ці `len` байтів — це **готовий файл**: не треба ні заголовків, ні кодування, просто виливаєш їх у файл — і на картці лежить справжній `.jpg`, який відкриє будь-який переглядач.

`esp_camera_fb_return(fb)` — рядок, який найлегше забути й найдорожче забувати. Драйвер має скінченну кількість буферів (`fb_count`). Поки ви тримаєте кадр, цей буфер зайнятий вами; якщо не повернути його — на наступному `esp_camera_fb_get()` вільного буфера не лишиться, і камера **зависне на другому знімку**. Тому повертати треба **на всіх шляхах виходу**, зокрема й тоді, коли файл не відкрився (гляньте: у гілці помилки `esp_camera_fb_return(fb)` стоїть перед `return`). Це той самий принцип, що «взяв ресурс — віддай», лише плата за забудькуватість тут особливо швидка й наочна.

Лишається зібрати все докупи. У прошивці для ESP32 точка входу — `setup()` (один раз при старті) і `loop()` (по колу); зробимо один знімок у `setup()`:

```c
void setup() {
    Serial.begin(115200);

    if (!camera_start())  return;   // камера не піднялася — далі немає сенсу
    if (!sdcard_start())  return;   // картка не змонтувалася — так само

    // Ім'я файлу зі зростаючим лічильником, щоб не затирати попередні.
    static int n = 0;
    char path[32];
    snprintf(path, sizeof(path), "/photo_%04d.jpg", n++);

    save_photo(path);
}

void loop() {
    // порожньо: один знімок зробили в setup(); тут можна спати або чекати кнопки
}
```

Оце і є повний робочий цикл. Ім'я `"/photo_0004.jpg"` формуємо зі зростаючим лічильником — інакше кожен новий знімок затирав би попередній під тим самим іменем. Файлова система на картці — [FAT](book:programming/flash-filesystems), тож картку виймають і читають на комп'ютері напряму, без жодних драйверів.

## Складність і пастки

Головна складність цього коду не в довжині, а в тому, що він мовчазний до помилок: майже кожна пастка проявляється не там, де причина, а деінде, і виглядає як «плата бракована». Ось повний список того, на чому губляться вечори.

- **PSRAM вимкнено — камера мовчить або дає лише крихітні кадри.** Найчастіша біда. Якщо в налаштуваннях збірки не ввімкнено PSRAM (в Arduino IDE це вибір плати з підписом «Huge APP» / правильної ESP32-CAM зі ввімкненою PSRAM), то `psramFound()` поверне `false`. У нашому коді це тихо переведе камеру в SVGA замість UXGA; а якщо жорстко просити `FRAMESIZE_UXGA` з `CAMERA_FB_IN_PSRAM` без PSRAM — `esp_camera_init()` поверне помилку, і плата «не запускається». Лікування: увімкнути PSRAM у налаштуваннях і **не** ігнорувати результат `psramFound()`.

- **GPIO4 зайнятий — спалах моргає при кожному записі.** Якщо змонтувати картку в чотирибітному режимі (`SD_MMC.begin()` без `true`), картка перехопить GPIO4 як лінію `DATA1`, і жодне `digitalWrite(4, LOW)` не втримає світлодіод — він блиматиме в такт запису. Лікування — саме `SD_MMC.begin("/sdcard", true)`. Побічний бонус — вільні GPIO12 і GPIO13.

- **Забули `esp_camera_fb_return()` — камера зависає на другому кадрі.** Перший знімок вдається, другий `esp_camera_fb_get()` не має вільного буфера й повертає `NULL` (або блокується). Ззовні — «камера зробила одне фото й померла». Лікування: повертати буфер на **всіх** шляхах виходу, зокрема в гілках помилок.

- **Малий буфер / брак пам'яті — кадр обрізається або не знімається.** Якщо на кадр не вистачає місця (наприклад, `fb_count = 2` під UXGA з'їдає помітний шматок PSRAM, а її ще ділять з іншими буферами), `esp_camera_fb_get()` може повернути `NULL`. Для поодиноких знімків досить `fb_count = 1`: другий буфер потрібен здебільшого для плавного стріму, а не для одного фото. Зменшивши `fb_count` до 1, ви вивільняєте PSRAM під власні дані.

- **Кадр «вчорашній» — забули `CAMERA_GRAB_LATEST`.** Драйвер за замовчуванням віддає найстаріший буфер у черзі. Для «зроби фото зараз» це видає кадр, знятий кілька моментів тому — особливо помітно, коли перед зйомкою щойно змінилася сцена. Лікування: `config.grab_mode = CAMERA_GRAB_LATEST`. Радикальний варіант, коли треба гарантовано найсвіжіший кадр, — узяти й одразу повернути один кадр, а тоді взяти наступний: `esp_camera_fb_return(esp_camera_fb_get());` перед справжнім `esp_camera_fb_get()` викидає той, що вже в черзі.

- **Картка «змонтувалася», але запис провалюється.** `SD_MMC.begin()` іноді повертає `true` навіть з кепською чи погано вставленою карткою. Без перевірки `cardType() == CARD_NONE` та без перевірки `if (!file)` після `open()` запис у нікуди мовчки провалиться. Обидві перевірки — дешева страховка від глухого «файлу на картці чомусь нема».

- **Живлення просідає під час зйомки — плата перезавантажується.** Це не про код, а про струм: одночасний старт сенсора з'їдає ривок струму, і на кволому живленні спрацьовує сторож напруги (*brownout detector*). Знадвору — «код доходить до `esp_camera_init()` і плата ребутиться». Якщо всі перевірки в коді проходять, а плата все одно циклиться на старті камери, причина майже напевно не в програмі — товстіші дроти, чесний 5-вольтовий блок і конденсатор на живленні лікують це надійніше за будь-яку правку скетчу.

Складіть ці сім осторог докупи — і «капризна» плата поводиться передбачувано: тихий однобітний запис, свіжий кадр UXGA у PSRAM, готовий `.jpg` на картці, жодного моргання й жодного загадкового ребуту. Уся хитрість була не в тому, щоб написати багато коду, а в тому, щоб у трьох рядках підготовки не наступити на жодну з мін.
