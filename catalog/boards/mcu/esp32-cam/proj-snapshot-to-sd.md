# ⚙️ Знімок на microSD: від кадру до файлу .jpg

**Задача.** Плата вже на столі, живлення міцне, картка вставлена, а сенсор і гніздо картки вже підняті в коді. Тепер треба зробити просту й дуже практичну річ: **клацнути один кадр і покласти його файлом `.jpg` на microSD** — так, щоб потім вийняти картку й побачити на комп'ютері нормальну картинку. Уся марудна підготовка (карта пінів сенсора, поля `camera_config_t`, режими картки) зібрана окремо в [довіднику підключення](book:boards/esp32-cam/api-esp32-cam-camera-sd-io.md); тут ми спираємось на неї й зосереджуємось на самому знімку.

Код нижче — справжній Arduino-скетч під ESP32 (той самий, що збирається в Arduino IDE чи PlatformIO), а не псевдокод: разом із функціями підняття з довідника його можна вставити, залити й одразу отримати файл на картці.

## Ідея: сенсор пише кадр у PSRAM, а ви лише переливаєте байти на картку

Найважливіше зрозуміти одразу — **процесор кадр не малює й навіть не стискає**. Уся важка робота лежить на двох чужих плечах.

Перше плече — сам сенсор OV2640. Він знімає картинку, стискає її [у JPEG](book:algorithms/jpeg-intra) власним залізом і віддає ESP32 уже готовий потік стиснених байтів. Друге плече — **PSRAM** (*pseudo-static RAM* — псевдостатична зовнішня пам'ять): драйвер камери складає цей готовий JPEG у буфер саме там, бо внутрішньої SRAM мікроконтролера на кадр не вистачить. Один кадр UXGA (1600×1200) навіть у стисненому вигляді — це близько 150 кілобайтів, а розпакований був би близько 3.7 мегабайта; внутрішніх 520 кілобайтів ESP32 не вистачило б у принципі.

> 🔧 **Навіщо це.** З цього випливає весь дизайн коду. Ваша програма не «фотографує» — вона просить драйвер: «дай покажчик на останній готовий кадр». Драйвер повертає структуру з двома полями: `buf` (адреса стиснених байтів у PSRAM) і `len` (скільки їх). Усе, що лишається зробити, — **записати ці `len` байтів у файл** і **повернути буфер драйверу**, щоб він міг знімати далі. Ви — лише кур'єр між PSRAM і карткою, і саме тому дешевий процесор тягне камеру: найтяжче за нього роблять інші.

Отже, увесь знімок зводиться до трьох рухів: узяти кадр із PSRAM, злити його байти у файл на картці, повернути буфер драйверу. Перш ніж це запрацює, сенсор і картку треба підняти — обидві функції підняття, `camera_start()` (сенсор плюс гасіння спалаху на GPIO4) і `sdcard_start()` (картка в однобітному режимі), беремо готовими з [довідника підключення](book:boards/esp32-cam/api-esp32-cam-camera-sd-io.md), щоб не повторювати тут карту пінів.

## Знімок і файл — власне те, заради чого все

Беремо кадр, відкриваємо файл, ллємо байти, повертаємо буфер:

```c
static bool save_photo(const char *path) {
    // 1. Просимо драйвер камери віддати готовий кадр.
    camera_fb_t *fb = esp_camera_fb_get();
    if (!fb) {
        Serial.println("Не вдалося зняти кадр");
        return false;
    }

    // 2. Відкриваємо файл на картці для запису.
    File file = SD_MMC.open(path, FILE_WRITE);
    if (!file) {
        Serial.printf("Не відкрити файл %s\n", path);
        esp_camera_fb_return(fb);   // буфер усе одно ПОВЕРНУТИ
        return false;
    }

    // 3. Ллємо стиснені байти JPEG у файл одним махом.
    file.write(fb->buf, fb->len);   // fb->buf — адреса, fb->len — довжина
    file.close();

    Serial.printf("Збережено %s  (%u байт)\n", path, (unsigned)fb->len);

    // 4. ОБОВ'ЯЗКОВО повертаємо буфер драйверу.
    esp_camera_fb_return(fb);
    return true;
}
```

Тут кожен рядок несе сенс, і два з них — критичні.

`esp_camera_fb_get()` повертає покажчик на структуру `camera_fb_t`. Нам із неї потрібні лише два поля: `fb->buf` — адреса стиснених байтів JPEG у PSRAM, і `fb->len` — скільки цих байтів. Оскільки формат уже JPEG, ці `len` байтів — це **готовий файл**: не треба ні заголовків, ні кодування, просто виливаєш їх у файл — і на картці лежить справжній `.jpg`, який відкриє будь-який переглядач.

`esp_camera_fb_return(fb)` — рядок, який найлегше забути й найдорожче забувати. Драйвер має скінченну кількість буферів (`fb_count`). Поки ви тримаєте кадр, цей буфер зайнятий вами; якщо не повернути його — на наступному `esp_camera_fb_get()` вільного буфера не лишиться, і камера **зависне на другому знімку**. Тому повертати треба **на всіх шляхах виходу**, зокрема й тоді, коли файл не відкрився (гляньте: у гілці помилки `esp_camera_fb_return(fb)` стоїть перед `return`). Це той самий принцип, що «взяв ресурс — віддай», лише плата за забудькуватість тут особливо швидка й наочна.

## Зібрати все докупи: setup і loop

У прошивці для ESP32 точка входу — `setup()` (один раз при старті) і `loop()` (по колу); зробимо один знімок у `setup()`:

```c
void setup() {
    Serial.begin(115200);

    if (!camera_start())  return;   // камера не піднялася — далі немає сенсу
    if (!sdcard_start())  return;   // картка не змонтувалася — так само

    // Ім'я файлу зі зростаючим лічильником, щоб не затирати попередні.
    static int n = 0;
    char path[32];
    snprintf(path, sizeof(path), "/photo_%04d.jpg", n++);

    save_photo(path);
}

void loop() {
    // порожньо: один знімок зробили в setup(); тут можна спати або чекати кнопки
}
```

Оце і є повний робочий цикл. Функції `camera_start()` і `sdcard_start()` — підняття сенсора та картки — визначені в [довіднику підключення](book:boards/esp32-cam/api-esp32-cam-camera-sd-io.md); саме там живе карта пінів та однобітний режим. Ім'я `"/photo_0004.jpg"` формуємо зі зростаючим лічильником — інакше кожен новий знімок затирав би попередній під тим самим іменем. Файлова система на картці — [FAT](book:programming/flash-filesystems), тож картку виймають і читають на комп'ютері напряму, без жодних драйверів.

## Складність і пастки

Головна складність цього коду не в довжині, а в тому, що він мовчазний до помилок: майже кожна пастка проявляється не там, де причина, а деінде, і виглядає як «плата бракована». Ось повний список того, на чому губляться вечори.

- **PSRAM вимкнено — камера мовчить або дає лише крихітні кадри.** Найчастіша біда. Якщо в налаштуваннях збірки не ввімкнено PSRAM (в Arduino IDE це вибір плати з підписом «Huge APP» / правильної ESP32-CAM зі ввімкненою PSRAM), то `psramFound()` поверне `false`. У нашому коді це тихо переведе камеру в SVGA замість UXGA; а якщо жорстко просити `FRAMESIZE_UXGA` з `CAMERA_FB_IN_PSRAM` без PSRAM — `esp_camera_init()` поверне помилку, і плата «не запускається». Лікування: увімкнути PSRAM у налаштуваннях і **не** ігнорувати результат `psramFound()`.

- **GPIO4 зайнятий — спалах моргає при кожному записі.** Якщо змонтувати картку в чотирибітному режимі (`SD_MMC.begin()` без `true`), картка перехопить GPIO4 як лінію `DATA1`, і жодне `digitalWrite(4, LOW)` не втримає світлодіод — він блиматиме в такт запису. Лікування — саме `SD_MMC.begin("/sdcard", true)`. Побічний бонус — вільні GPIO12 і GPIO13.

- **Забули `esp_camera_fb_return()` — камера зависає на другому кадрі.** Перший знімок вдається, другий `esp_camera_fb_get()` не має вільного буфера й повертає `NULL` (або блокується). Ззовні — «камера зробила одне фото й померла». Лікування: повертати буфер на **всіх** шляхах виходу, зокрема в гілках помилок.

- **Малий буфер / брак пам'яті — кадр обрізається або не знімається.** Якщо на кадр не вистачає місця (наприклад, `fb_count = 2` під UXGA з'їдає помітний шматок PSRAM, а її ще ділять з іншими буферами), `esp_camera_fb_get()` може повернути `NULL`. Для поодиноких знімків досить `fb_count = 1`: другий буфер потрібен здебільшого для плавного стріму, а не для одного фото. Зменшивши `fb_count` до 1, ви вивільняєте PSRAM під власні дані.

- **Кадр «вчорашній» — забули `CAMERA_GRAB_LATEST`.** Драйвер за замовчуванням віддає найстаріший буфер у черзі. Для «зроби фото зараз» це видає кадр, знятий кілька моментів тому — особливо помітно, коли перед зйомкою щойно змінилася сцена. Лікування: `config.grab_mode = CAMERA_GRAB_LATEST`. Радикальний варіант, коли треба гарантовано найсвіжіший кадр, — узяти й одразу повернути один кадр, а тоді взяти наступний: `esp_camera_fb_return(esp_camera_fb_get());` перед справжнім `esp_camera_fb_get()` викидає той, що вже в черзі.

- **Картка «змонтувалася», але запис провалюється.** `SD_MMC.begin()` іноді повертає `true` навіть з кепською чи погано вставленою карткою. Без перевірки `cardType() == CARD_NONE` та без перевірки `if (!file)` після `open()` запис у нікуди мовчки провалиться. Обидві перевірки — дешева страховка від глухого «файлу на картці чомусь нема».

- **Живлення просідає під час зйомки — плата перезавантажується.** Це не про код, а про струм: одночасний старт сенсора з'їдає ривок струму, і на кволому живленні спрацьовує сторож напруги (*brownout detector*). Знадвору — «код доходить до `esp_camera_init()` і плата ребутиться». Якщо всі перевірки в коді проходять, а плата все одно циклиться на старті камери, причина майже напевно не в програмі — товстіші дроти, чесний 5-вольтовий блок і конденсатор на живленні лікують це надійніше за будь-яку правку скетчу.

Складіть ці сім осторог докупи — і «капризна» плата поводиться передбачувано: тихий однобітний запис, свіжий кадр UXGA у PSRAM, готовий `.jpg` на картці, жодного моргання й жодного загадкового ребуту. Уся хитрість була не в тому, щоб написати багато коду, а в тому, щоб у трьох рядках підготовки не наступити на жодну з мін.
