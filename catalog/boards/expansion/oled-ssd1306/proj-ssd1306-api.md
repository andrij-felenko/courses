# ⚙️ Оживлюємо SSD1306 у коді: від сканера I2C до живого HUD

Плата лежить на столі, чотири дроти під'єднані, живлення є — а екран чорний. Це нормальний старт: OLED не показує нічого, доки контролеру не сказали прокинутися, увімкнути високу напругу й дати першу картинку. Уся практична робота з цим модулем зводиться до трьох дій, які варто виконати саме в цьому порядку: **знайти дисплей на шині** (переконатися, що він озивається й за якою адресою), **ініціалізувати контролер** (зокрема ввімкнути зарядний насос, інакше все марно), і далі щокадру **намалювати у буфер та штовхнути буфер** на екран. Розберімо кожну дію до дна — на реальному, скомпільованому коді, а не на псевдокоді, — і збудуймо наприкінці живий HUD: у верхньому рядку стан скінченного автомата пристрою, посередині велика цифра з давача, унизу — рядок меню з курсором, що бігає по пунктах.

Мета не в тому, щоб «мати шаблон, куди підставити свій текст». Мета — щоб кожен рядок був зрозумілий: чому саме `SSD1306_SWITCHCAPVCC`, чому обов'язково `display()`, чому на STM32 адреса раптом `0x78`, а не `0x3C`, і що робити, коли зв'язок є, а скло мертве. Тоді будь-яка чужа бібліотека для цього дисплея читатиметься як відкрита книга.

## Крок нуль: знайти дисплей на шині

Перше, що варто зробити з будь-яким I2C-пристроєм, — не писати під нього код, а **спитати шину, хто на ній є**. Це заощаджує години: якщо дисплей не озивається, то жодна ідеальна ініціалізація його не оживить, і копатися треба в дротах, а не в коді. Сканер I2C — це коротка петля, що по черзі «стукає» за кожною адресою від 1 до 126 й дивиться, чи хтось відповів підтвердженням (*ACK*).

Механіка стуку проста. Ведучий починає транзакцію на адресу, і якщо за цією адресою хтось живий, він **притягує лінію SDA до нуля** в дев'ятому такті — це і є ACK. Немає нікого — лінія лишається високою (*NACK*). Бібліотека `Wire` ховає це за парою `beginTransmission()` / `endTransmission()`: остання повертає `0`, якщо дістала ACK, і ненульовий код помилки — якщо ні. Тобто «просканувати шину» — це «спробувати почати й одразу закінчити порожню транзакцію на кожну адресу й подивитися на код повернення».

> 🔧 **Навіщо це.** Сканер відповідає на найважливіше питання діагностики цього модуля: **дисплей узагалі на шині чи ні?** Якщо він озвався на `0x3C` — проводка ціла, живлення є, і чорний екран далі — це вже проблема ініціалізації (майже завжди насос). Якщо не озвався ніхто — проблема фізична: переплутані SDA/SCL, немає живлення, немає підтяжок, задерта до 5 В шина на 3.3-вольтовому МК. Сканер розрізняє ці два світи одним запуском, і саме тому його роблять першим, ще до будь-якого малювання. Докладніше про сам механізм адрес і ACK — у [адресації I2C](book:communications/i2c-addressing).

Ось повний сканер для Arduino/ESP32. Його можна залити окремим скетчем — він нічого не малює, лише друкує в монітор порту знайдені адреси.

```cpp
#include <Wire.h>

void setup() {
  Serial.begin(115200);
  while (!Serial) { }            // на ESP32/native USB — дочекатися монітора
  Wire.begin();                  // SDA=GPIO21, SCL=GPIO22 на ESP32 за замовчуванням
  Serial.println("Скануємо шину I2C...");

  int found = 0;
  for (uint8_t addr = 1; addr < 127; addr++) {
    Wire.beginTransmission(addr);
    uint8_t err = Wire.endTransmission();   // 0 == дістали ACK, пристрій живий
    if (err == 0) {
      Serial.printf("  пристрій за адресою 0x%02X\n", addr);
      found++;
    }
  }
  if (found == 0)
    Serial.println("Ніхто не озвався — перевір дроти, живлення, підтяжки.");
}

void loop() { }
```

Запустивши це на справному модулі, ви побачите рівно один рядок: `пристрій за адресою 0x3C`. Зрідка — `0x3D` (якщо на платі перепаяно площадку SA0). Побачили `0x3D` — запам'ятайте це число: саме його треба буде передати в ініціалізацію замість типового `0x3C`, інакше бібліотека стукатиме не туди й вважатиме, що дисплея немає.

Перевірити адресу можна й точково, не скануючи всю шину, — коли ви вже знаєте кандидата й хочете лише пересвідчитися, що дисплей за ним відповідає:

```cpp
bool ping(uint8_t addr) {          // чи живий пристрій за цією адресою
  Wire.beginTransmission(addr);
  return Wire.endTransmission() == 0;
}

// у setup():
if      (ping(0x3C)) Serial.println("є на 0x3C");
else if (ping(0x3D)) Serial.println("є на 0x3D — не забудь передати цю адресу в begin()");
else                 Serial.println("дисплей мовчить");
```

На «голому» STM32 без Arduino та сама ідея виглядає інакше, бо там немає `Wire` — є **HAL**, і в ньому вже вбудований готовий сканер-примітив `HAL_I2C_IsDeviceReady()`. Він шле саму лише адресну фазу й повертає `HAL_OK`, якщо дістав ACK. Тут спливає перша каверза сімейства STM32, про яку варто знати заздалегідь: **HAL хоче 8-бітну адресу**, тобто 7-бітну `0x3C`, зсунуту ліворуч на один біт, — виходить `0x78`. Молодший біт у HAL — це напрям читання/запису, і ви віддаєте адресу вже «зсунутою під нього».

```c
// STM32 HAL: пройтися по шині й знайти OLED. hi2c1 уже налаштований у CubeMX.
// Увага: HAL адресує 8-бітно — 7-бітна 0x3C перетворюється на (0x3C << 1) = 0x78.
for (uint8_t a7 = 1; a7 < 127; a7++) {
    if (HAL_I2C_IsDeviceReady(&hi2c1, a7 << 1, 2, 10) == HAL_OK) {
        // a7 — «людська» 7-бітна адреса; для OLED тут буде 0x3C
        printf("пристрій за адресою 0x%02X\r\n", a7);
    }
}
```

> 🔧 **Навіщо це.** Зсув адреси на один біт — джерело половини головного болю саме на STM32. У даташитах, у сканерах і в усіх бібліотеках Arduino фігурує 7-бітна `0x3C`; а HAL-функції (`HAL_I2C_Master_Transmit`, `HAL_I2C_IsDeviceReady`) очікують її вже зсунутою — `0x78`. Передасте в HAL `0x3C` — він адресує зовсім інший пристрій, дисплей мовчить, і код виглядає правильним. Правило: **у HAL завжди `7-бітна << 1`.** Драйвери U8g2, які ми викличемо далі, ховають цей зсув усередині свого I2C-колбека — але коли пишете HAL руками, тримайте його в голові. Про сам поділ адрес на 7 біт і біт напряму — [адресація I2C](book:communications/i2c-addressing).

## Крок один: ініціалізація — і той рядок, який усі забувають

Дисплей озвався. Тепер його треба **розбудити**. Сира ініціалізація SSD1306 — це десятків зо два команд поспіль: задати режим адресації пам'яті, множник розгортки, зсув, полярність рядків і стовпців (від неї залежить, чи не буде картинка дзеркальна), контраст, частоту генератора — і, найголовніше для нас, **увімкнути зарядний насос**. Цей рядок — `0x8D, 0x14` — і є той самий, що вирішує, світитиметься скло чи ні.

Розкладімо ці два байти, бо в них уся суть «чорного екрана при живому I2C». Команда `0x8D` — це «зараз надійде налаштування зарядного насоса». Наступний байт — саме налаштування: `0x14` означає «увімкнути насос від внутрішнього перетворювача», а `0x10` — «вимкнути, живитимусь від зовнішньої високої напруги». На платі 0.96″ зовнішньої високої напруги нізвідки взятися — її робить сам насос, тож потрібне саме `0x14`. Лишите типове `0x10` (або взагалі не пошлете цю пару) — контролер працює, GDDRAM наповнюється вашою картинкою, драйвер стовпців силкується світити, **але живити піксель нічим**: органічному світлодіоду потрібні його 7–9 В, а їх немає. Зовні це виглядає як повністю справний, але мертвий екран.

> 🔧 **Навіщо це.** Ось чому в бібліотеці Adafruit параметр ініціалізації зветься `SSD1306_SWITCHCAPVCC` — це прямо «switched-capacitor VCC», тобто «живлення від насоса на перемикних конденсаторах, увімкни його». Передавши цей параметр, ви кажете бібліотеці послати за вас ту саму пару `0x8D, 0x14`. Є парний варіант `SSD1306_EXTERNALVCC` — «висока напруга ззовні»; для модуля 0.96″ він **неправильний** і дасть чорний екран. Запам'ятайте це як єдине: для цієї плати завжди `SWITCHCAPVCC`. Природа самого насоса — конденсатори, що «накачують» напругу, — розібрана в [зарядному насосі](book:electronics/charge-pump).

На щастя, руками цю пару команд шлють лише ті, хто пише свій драйвер. У звичайному коді беруть бібліотеку, яка знає всю послідовність напам'ять. У світі Arduino/ESP32 канонічна пара — **Adafruit_SSD1306** (драйвер саме цього контролера) поверх **Adafruit_GFX** (спільна графіка: шрифти, лінії, фігури — те саме API, що й для інших дисплеїв Adafruit). Ініціалізація зводиться до одного рядка:

```cpp
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>

#define SCREEN_W    128
#define SCREEN_H     64
#define OLED_ADDR  0x3C     // те, що показав сканер; зрідка 0x3D
#define OLED_RESET   -1     // I2C-модуль 0.96" не має окремої ніжки RESET

// Буфер 128*64/8 = 1024 байти живе всередині цього об'єкта, у RAM МК.
Adafruit_SSD1306 display(SCREEN_W, SCREEN_H, &Wire, OLED_RESET);

void setup() {
  Serial.begin(115200);
  Wire.begin();

  // SWITCHCAPVCC — увімкнути внутрішній зарядний насос (та сама пара 0x8D,0x14).
  // begin() ще й ВИДІЛЯЄ 1024 байти під буфер і повертає false, якщо RAM не стало.
  if (!display.begin(SSD1306_SWITCHCAPVCC, OLED_ADDR)) {
    Serial.println("SSD1306: begin() не вдався — адреса або брак RAM");
    for (;;) { }            // далі йти немає сенсу
  }

  display.clearDisplay();   // очистити буфер (у RAM; на склі ще старе/сміття)
  display.setTextColor(SSD1306_WHITE);
  display.setTextSize(2);
  display.setCursor(0, 20);
  display.println("Привіт!");
  display.display();        // ← ОЦЕ штовхає буфер на скло. Без нього — порожньо.
}

void loop() { }
```

Два рядки тут варто зупинити окремо. По-перше, `display.begin(...)` **повертає `bool`**, і це не формальність: усередині він намагається виділити 1024 байти під кадровий буфер, і на чипі з обмаллю RAM це може не вдатися. Тому перевірку `if (!display.begin(...))` не викидають — вона розрізняє «не та адреса / бракує пам'яті» від «усе гаразд». По-друге — і це найважливіше в усьому прикладі — останній рядок `display.display()`. До нього всі `println`, `setCursor`, майбутні лінії й прямокутники малюються **лише в буфер у RAM**; на склі не змінюється ані піксель. `display()` бере ці 1024 байти й жене їх на контролер. **Забули `display()` — екран лишається порожнім, і здається, що дисплей завис.**

> 🔧 **Навіщо це.** Ця відкладеність — не примха Adafruit, а прямий наслідок того, як улаштована пам'ять SSD1306: щоб змінити один піксель, треба переписати цілий байт-стовпчик, а вичитувати назад по I2C незручно. Тому бібліотека тримає **повну копію картинки в RAM МК**, дає вам малювати в ній скільки завгодно дешево, і виштовхує все однією пачкою по `display()`. Ті самі 1024 байти — причина, чому дисплей не заводиться на зовсім крихітних чипах: повному буферу нема де поміститися. Модель «картинка в пам'яті, яку цілком женуть на екран» — це і є [кадровий буфер](book:electronics/framebuffer); тут ви бачите його наживо.

### Той самий крок на STM32 через U8g2

На «голому» STM32 (без Arduino) Adafruit-бібліотека не підходить — вона зшита з `Wire`. Тут беруть **U8g2** — універсальний драйвер, що вміє десятки контролерів (зокрема й SH1106 з сусідніх 1.3″-модулів) і працює як в Arduino, так і в чистому C поверх HAL. Ціна універсальності — трохи більше ручної роботи: U8g2 не знає вашого конкретного мікроконтролера, тож ви даєте йому **два колбеки** — «як послати байти по I2C» і «як зачекати мілісекунди». Усередині цих колбеків і живе HAL зі своїм зсунутим `0x78`.

```c
#include "u8g2.h"

static u8g2_t u8g2;                 // структура дисплея; буфер 1024 Б — усередині
extern I2C_HandleTypeDef hi2c1;     // налаштований у CubeMX

// Колбек №1: віддати байти по I2C. U8g2 накопичує їх, а на END — шле пачку.
static uint8_t u8x8_byte_stm32_hw_i2c(u8x8_t *u8x8, uint8_t msg,
                                      uint8_t arg_int, void *arg_ptr) {
  static uint8_t buf[32];
  static uint8_t idx;
  uint8_t *data;
  switch (msg) {
    case U8X8_MSG_BYTE_START_TRANSFER: idx = 0; break;
    case U8X8_MSG_BYTE_SEND:
      data = (uint8_t *)arg_ptr;
      while (arg_int-- > 0) buf[idx++] = *data++;   // збираємо у свій буфер
      break;
    case U8X8_MSG_BYTE_END_TRANSFER:
      // 0x3C << 1 = 0x78 — HAL хоче 8-бітну адресу! (та сама каверза, що й у сканері)
      HAL_I2C_Master_Transmit(&hi2c1, 0x78, buf, idx, HAL_MAX_DELAY);
      break;
  }
  return 1;
}

// Колбек №2: затримки. Для I2C потрібні лише мілісекунди.
static uint8_t u8x8_gpio_and_delay_stm32(u8x8_t *u8x8, uint8_t msg,
                                         uint8_t arg_int, void *arg_ptr) {
  if (msg == U8X8_MSG_DELAY_MILLI) HAL_Delay(arg_int);
  return 1;
}

void oled_init(void) {
  // Конструктор «повнобуферного» (_f) драйвера саме SSD1306 128x64 noname.
  u8g2_Setup_ssd1306_i2c_128x64_noname_f(
      &u8g2, U8G2_R0,                       // R0 — без повороту
      u8x8_byte_stm32_hw_i2c, u8x8_gpio_and_delay_stm32);

  u8g2_InitDisplay(&u8g2);      // шле всю послідовність ініціалізації (насос теж!)
  u8g2_SetPowerSave(&u8g2, 0);  // 0 — прокинутися; 1 — приспати екран
  u8g2_ClearBuffer(&u8g2);

  u8g2_SetFont(&u8g2, u8g2_font_ncenB14_tr);
  u8g2_DrawStr(&u8g2, 0, 30, "Привіт!");
  u8g2_SendBuffer(&u8g2);       // ← аналог display(): без нього скло порожнє
}
```

Структурно це **той самий обряд**, лише іншими словами. `u8g2_InitDisplay()` шле всю послідовність команд, зокрема й увімкнення насоса, — вам не треба знати про `0x8D, 0x14`, U8g2 знає її для «noname» SSD1306. Суфікс `_f` у назві конструктора (`..._noname_f`) означає **full-buffer** — повний кадровий буфер у RAM, як у Adafruit; є ще режими з частковим буфером (`_1`, `_2`) для зовсім тісних чипів, але вони складніші в користуванні. І, звісно, `u8g2_SendBuffer()` — точний аналог `display()`: доки не покликали, скло не змінюється.

> 🔧 **Навіщо це.** Побачивши обидва приклади поруч, легко вивести інваріант, спільний для будь-якої бібліотеки й будь-якого МК: **(1) ініціалізація вмикає насос, (2) малюєш у буфер у RAM, (3) один раз штовхаєш буфер на скло.** Назви різняться — `begin` / `InitDisplay`, `display` / `SendBuffer`, — суть незмінна. Хто тримає цей інваріант у голові, того не спантеличить чужий код і не заскочить чорний екран. А хто чекає, що піксель загориться одразу після `drawPixel`, той шукатиме неіснуючу поломку.

## Крок два: збираємо живий HUD

Тепер зберемо щось, заради чого цей дисплей і ставлять на прилад, — **HUD** (*Head-Up Display*), що показує стан пристрою, не відриваючи оператора від справи. Три зони: зверху рядок зі **станом скінченного автомата** (у якому режимі зараз прилад), посередині — **велике число з давача** (щоб читалося здалеку й краєм ока), унизу — **рядок меню** з курсором, що бігає по пунктах. Це типова компоновка для дрібного приладу, і на ній добре видно, як три різні за характером речі — текст-стан, велика цифра, інтерактивний список — уживаються в одному кадрі 128×64.

Спочатку домовмося про модель того, що показуємо. Прилад живе як [скінченний автомат](book:electronics/finite-state-machines): у кожен момент він рівно в одному зі станів, і HUD показує, у якому саме. Візьмімо чотири стани, як у типового вимірювального приладу:

```
enum HudState {
  ST_IDLE,        // чекаємо
  ST_MEASURE,     // міряємо
  ST_ALARM,       // вихід за межу
  ST_CONFIG       // налаштування
};
```

Головна пастка великої цифри — **не тягти float заради краси**. Давач часто дає ціле в якихось сотих (наприклад, температуру як `int` у сотих градуса: `2537` = 25.37 °C). Виводити її через дробові числа на мікроконтролері марнотратно й повільно; куди дешевше й точніше **лишити ціле й самому поставити кому**: ціла частина — `value / 100`, дробова — `value % 100`. Це та сама ідея, що [фіксована кома](book:programming/fixed-point) — тримати «дробове» число як звичайне ціле в обраному масштабі; тут вона економить і час, і пам'ять.

Ось повний HUD для Arduino/ESP32. Логіку датчика й кнопок зведено до мінімуму (у справжньому приладі тут читання давача й опитування кнопок), щоб не затуляти саме **малювання кадру** — те, заради чого ця вставка.

```cpp
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>

#define SCREEN_W 128
#define SCREEN_H  64
Adafruit_SSD1306 display(SCREEN_W, SCREEN_H, &Wire, -1);

enum HudState { ST_IDLE, ST_MEASURE, ST_ALARM, ST_CONFIG };

// Людські назви станів для верхнього рядка.
const char* stateName(HudState s) {
  switch (s) {
    case ST_IDLE:    return "IDLE";
    case ST_MEASURE: return "MEASURE";
    case ST_ALARM:   return "ALARM";
    case ST_CONFIG:  return "CONFIG";
  }
  return "?";
}

const char* MENU[] = { "Start", "Zero", "Range", "Save" };
const int   MENU_N = 4;

// Намалювати ВЕСЬ кадр за поточним станом. Викликається щоразу, коли щось змінилось.
void drawHud(HudState st, int32_t centi, int cursor) {
  display.clearDisplay();                 // чистимо буфер, малюємо кадр з нуля

  // — Зона 1: рядок стану вгорі, у рамці-плашці ————————————————
  display.drawRect(0, 0, SCREEN_W, 14, SSD1306_WHITE);
  display.setTextSize(1);
  display.setTextColor(SSD1306_WHITE);
  display.setCursor(4, 3);
  display.print("St: ");
  display.print(stateName(st));

  // — Зона 2: велике число посередині, ціле «з комою вручну» ————————
  int32_t whole = centi / 100;            // ціла частина
  int32_t frac  = centi % 100;            // дві цифри після коми
  if (frac < 0) frac = -frac;             // модуль, щоб «-1.05» не став «-1.-5»
  char big[16];
  snprintf(big, sizeof(big), "%ld.%02ld", (long)whole, (long)frac);
  display.setTextSize(3);                 // розмір 3 ≈ 18x24 пікселі на символ
  display.setCursor(6, 20);
  display.print(big);
  display.setTextSize(1);                 // одиниці — дрібним, у куточку
  display.setCursor(104, 30);
  display.print("C");

  // — Зона 3: рядок меню внизу, курсор «>» перед активним пунктом ——————
  display.drawFastHLine(0, 50, SCREEN_W, SSD1306_WHITE);  // відділити меню лінією
  int x = 2;
  for (int i = 0; i < MENU_N; i++) {
    display.setCursor(x, 54);
    display.print(i == cursor ? ">" : " ");   // курсор перед активним пунктом
    display.print(MENU[i]);
    x += (strlen(MENU[i]) + 2) * 6;           // 6 пікселів на символ у розмірі 1
  }

  display.display();                      // ← штовхаємо весь кадр на скло
}

void setup() {
  Wire.begin();
  if (!display.begin(SSD1306_SWITCHCAPVCC, 0x3C)) { for (;;) {} }
}

void loop() {
  // Демонстрація: ганяємо стани й число, курсор повзе по меню.
  static int32_t t = 2500;                // 25.00 °C у сотих
  static int cursor = 0;
  static HudState st = ST_MEASURE;

  t += 7;                                 // «давач» поволі росте
  if (t > 8000) { st = ST_ALARM; }        // перейшли в тривогу за межею
  else          { st = ST_MEASURE; }

  drawHud(st, t, cursor);                 // перемалювали кадр
  cursor = (cursor + 1) % MENU_N;         // курсор на наступний пункт
  delay(400);
}
```

Придивімося, чому кадр збудовано саме так. **Увесь HUD малюється однією функцією `drawHud()`, що починається з `clearDisplay()` і закінчується `display()`.** Це не випадковість, а найздоровіший спосіб працювати з кадровим буфером: не «підтирати» окремі ділянки старого кадру (звідки беруться «привиди» недочищених пікселів), а щоразу малювати весь екран з чистого аркуша. 1024 байти на кадр — копійки; зате не треба стежити, що там лишилося від попереднього стану.

Далі — компоновка під **тісні 128×64**. Розмір тексту `3` в Adafruit_GFX — це базовий шрифт 6×8, помножений утричі, тобто приблизно 18×24 пікселі на символ. П'ять таких символів (`25.00`) з'їдають майже всю ширину — тому одиниці («C») ставлять дрібним шрифтом у куточок, а не поруч тим самим кеглем. Верхня плашка стану — 14 пікселів заввишки (рамка плюс рядок висотою 8), лінія меню — на `y=50`, велика цифра між ними. Це не єдина можлива розкладка, але вона показує головне: на такому екрані **місце рахують у пікселях**, і великий шрифт треба «бюджетувати» під ширину 128.

І курсор меню. Тут він елементарний — символ `>` перед активним пунктом і пробіл перед рештою; курсор рухається, змінюючи змінну `cursor`, а весь рядок перемальовується. У справжньому приладі `cursor` рухали б кнопки «вниз/вгору», а `Start`/`Save` запускали б перехід автомата — але механіка кадру та сама: змінилося щось у стані → перемалювали весь HUD → штовхнули буфер.

> 🔧 **Навіщо це.** Зверніть увагу, що `drawHud()` **нічого не знає про те, коли її кличуть**. Вона — чиста функція «дано стан → намалюй кадр». Це правильний поділ: логіка (автомат, читання давача, кнопки) окремо змінює `st`, `centi`, `cursor`, а `drawHud()` лише відбиває їх на склі. Тоді дисплей ніколи не бреше — він завжди показує поточний стан, — і код не плутається у «що вже намальовано, а що ні». Такий поділ «модель окремо, малювання кадру окремо» масштабується від цього HUD до будь-якого інтерфейсу.

Наостанок — велике число без float на «голому» STM32 з U8g2. Логіка та сама, лише виклики U8g2-ні; головна відмінність у тому, що в U8g2 **шрифт задає й розмір, і накреслення** (окремого множника розміру, як `setTextSize`, немає — ви обираєте готовий шрифт потрібної величини). Тому «велику цифру» дає вибір великого шрифту, а не множник.

```c
// STM32 / U8g2: велике число посередині, ціле «з комою вручну», без float.
void draw_big_value(int32_t centi) {
  int32_t whole = centi / 100;
  int32_t frac  = centi % 100;
  if (frac < 0) frac = -frac;
  char s[16];
  snprintf(s, sizeof(s), "%ld.%02ld", (long)whole, (long)frac);

  u8g2_ClearBuffer(&u8g2);
  u8g2_SetFont(&u8g2, u8g2_font_logisoso24_tn);  // великий шрифт, лише цифри й «.»
  u8g2_DrawStr(&u8g2, 4, 44, s);                 // (x, baseline_y, текст)
  u8g2_SendBuffer(&u8g2);
}
```

Зверніть увагу на суфікс шрифту `_tn` (*text, numbers*): він містить лише цифри, крапку й мінус — саме те, що треба великій цифрі, і при цьому не тягне у флеш увесь набір літер. У U8g2 координата `y` в `DrawStr` — це **базова лінія** (низ літер), а не верх рядка, як звик той, хто прийшов з Adafruit_GFX; переплутавши, дістанете текст, зрізаний за верхнім краєм. Дрібна різниця, але саме такі дрібниці й коштують півгодини, коли переходиш між бібліотеками.

## Складність і пастки

Уся практична складність цього дисплея — не в графіці, а в кількох місцях, де «код правильний, а екран не той». Зберімо їх в одне, з коротким «як упізнати» біля кожного, бо саме на цьому губиться найбільше часу.

**Забутий `display()` / `SendBuffer()` — картинка «застигла».** Наймасовіша пастка. Ви малюєте `println`, `drawRect`, `DrawStr` — на склі нічого. Причина не в дисплеї: усе намальоване сидить у буфері в RAM і чекає на виштовхування. Ознака: перший кадр (той, після якого `display()` таки покликали) є, а дальші зміни «не доходять» — бо в циклі забули повторний `display()`. **Правило:** перемалював кадр — того ж моменту штовхнув буфер. Якщо на екрані взагалі нічого й ви певні, що `display()` є, — це вже не ця пастка, дивіться насос.

**Не ввімкнений насос — I2C живий, скло чорне.** Найпідступніша, бо все «працює»: сканер бачить `0x3C`, `begin()` повертає `true`, дані йдуть — а екран мертвий. Причина: контролеру не послано `0x8D, 0x14`, високої напруги на OLED немає, світитися нічим. У бібліотеці це означає, що ви передали `SSD1306_EXTERNALVCC` замість `SSD1306_SWITCHCAPVCC` (або пишете ініціалізацію руками й проґавили цей рядок). **Ознака, що відрізняє від забутого `display()`:** тут навіть найперший кадр чорний, хоча зв'язок стовідсотково є. **Лік:** для модуля 0.96″ завжди `SWITCHCAPVCC`.

**Не та адреса — «дисплея немає», хоч він на шині.** `begin(SSD1306_SWITCHCAPVCC, 0x3C)` на платі, перепаяній під `0x3D`, повертає `false` — бібліотека стукає не туди. **Ознака:** сканер показує `0x3D` (або взагалі інше число), а код передає `0x3C`. **Лік:** передавати в ініціалізацію ту адресу, яку назвав сканер. На STM32 додайте до цього каверзу зсуву: у HAL адреса **завжди `7-бітна << 1`**, тобто `0x78` для `0x3C`; передасте `0x3C` — HAL адресує чужий пристрій, і дисплей «мовчить» при цілій проводці.

**Буфер 1024 Б у RAM — не влазить на дрібному чипі.** Повний кадровий буфер SSD1306 128×64 — це рівно `128 × 64 / 8 = 1024` байти, і вони мусять поміститися в RAM мікроконтролера **на додачу** до всього іншого. На ESP32 чи STM32 це дрібниця; на восьмибітному AVR з 2 КБ RAM повний буфер з'їдає половину пам'яті, а на зовсім крихітних чипах `begin()` чесно поверне `false` — RAM не стало. **Ознака:** `begin()` повертає `false`, хоча адреса правильна й дисплей на шині. **Лік:** або чип із більшою RAM, або бібліотека з посторінковим (частковим) буфером — U8g2 у режимах `_1`/`_2` тримає лише одну-дві сторінки замість усіх восьми, ціною складнішого малювання й повільнішого повного оновлення.

**Картинка зсунута на два пікселі — це не SSD1306.** Якщо код правильний, насос увімкнено, а зображення з'їхало ліворуч на пару стовпців і праворуч сміття — майже напевно під бібліотекою не той контролер: **SH1106** (типовий для 1.3″-модулів) має 132 стовпці пам'яті проти видимих 128 і показує центральні. **Лік:** узяти в U8g2 конструктор саме під SH1106 (`u8g2_Setup_sh1106_...`) — там перехід між чипами зводиться до одного рядка. Плутанина суто «каталожна»: зовні модулі близнюки, усередині — різна адресація.

Зведімо тепер усе в одну коротку схему-діагноста: почавши з симптому, за два-три питання дійти до причини.

```
Екран порожній / не той?
│
├─ Сканер БАЧИТЬ дисплей на шині?
│   │
│   ├─ НІ ─► фізика: дроти (SDA/SCL не переплутані?), живлення (VCC/GND),
│   │         підтяжки, рівень шини (не задерта до 5 В на 3.3-В МК),
│   │         на STM32 — адреса в HAL зсунута? (0x3C → 0x78)
│   │
│   └─ ТАК ─► зв'язок є, копаємо в коді:
│        │
│        ├─ begin()/InitDisplay повернув помилку? ─► не та адреса, або брак RAM (1024 Б)
│        │
│        ├─ перший кадр чорний, хоч зв'язок є? ─► НАСОС: SWITCHCAPVCC, не EXTERNALVCC
│        │
│        ├─ перший кадр є, дальші зміни «не доходять»? ─► забутий display()/SendBuffer у циклі
│        │
│        └─ картинка з'їхала на ~2 пікселі? ─► це SH1106 (1.3"), не SSD1306: інший конструктор
```

Ця драбинка «спершу спитай шину, тоді копай у коді» економить найбільше часу саме тому, що першим кроком **розводить фізику й програму**. Половина «непрацюючих дисплеїв» — переплутані дроти або задерта шина, і жодні правки коду їх не оживлять; друга половина — насос, забутий `display()` чи адреса, і тут дроти чіпати марно. Сканер I2C стоїть на розвилці цих двох світів — тому його й роблять нульовим кроком, ще до першої намальованої лінії.
