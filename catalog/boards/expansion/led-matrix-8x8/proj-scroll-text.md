# ⚙️ Проєкт: біжучий рядок на матриці 8×8

Найпопулярніша задача 8×8-матриці — **біжучий рядок**: текст, що плавно повзе екраном. Вона стоїть на готовому [керуванні матрицею](book:boards/led-matrix-8x8/api-driver.md): десь унизу вже крутиться драйвер, який вісім байтів **буфера кадру** (`uint8_t frame[8]`, по біту на цятку) невпинно перекладає на світлодіоди — чи то пряме мультиплексування таймером, чи драйвер MAX7219. Нам лишається тільки **писати в цей буфер** потрібну картинку. Щоб текст побіг, над драйвером треба надбудувати дві нові речі: **шрифт** (як виглядає кожна літера цятками) і **зсув** (як рухати текст уздовж екрана).

Код — справжній C++ під Arduino (ATmega328P на 16 МГц), той самий діалект, що й у драйвері: типи, `PROGMEM`, оголошення — усе як у реальному скетчі, що компілюється й заливається.

## Шрифт у пам'яті програм (PROGMEM)

Шрифт — це таблиця: для кожного символу вісім байтів, що малюють його на решітці 8×8, точнісінько як малюють усмішку в буфері кадру. Але таблиця чимала: навіть куций набір із сотні символів — це вже 800 байтів. А в ATmega328P лише **2 кілобайти** оперативної пам'яті (SRAM) на всі змінні й буфери разом. Покласти туди шрифт — означає з'їсти майже половину дефіцитної пам'яті ще до першої корисної змінної.

Рятунок — **тримати шрифт у пам'яті програм (Flash)**, якої на порядок більше (32 КБ), а не в SRAM. В Arduino це робить модифікатор `PROGMEM`: позначений ним масив лишається у Flash і не копіюється в оперативну пам'ять. За це доводиться платити дрібною незручністю — до таких даних **не можна звертатися напряму** (звичайний `font[i]` дасть сміття), їх дістають окремою функцією `pgm_read_byte`.

Ось шматок шрифту — по вісім байтів-стовпців на символ. Тут зручніше зберігати літери **колонками** (кожен байт — вертикальний стовпчик із восьми цяток), бо тоді біжучий рядок зсувається природно, стовпець за стовпцем:

```cpp
#include <avr/pgmspace.h>

// Шрифт 8×8, ПО СТОВПЦЯХ: для кожного символу — 8 байтів,
// кожен байт = вертикальний стовпчик (біт 0 згори). Лежить у Flash.
const uint8_t FONT[][8] PROGMEM = {
    { 0x00,0x00,0x00,0x00,0x00,0x00,0x00,0x00 },  // ' ' (пробіл)
    { 0x7E,0x11,0x11,0x11,0x7E,0x00,0x00,0x00 },  // 'A'
    { 0x7F,0x49,0x49,0x49,0x36,0x00,0x00,0x00 },  // 'B'
    { 0x3E,0x41,0x41,0x41,0x22,0x00,0x00,0x00 },  // 'C'
    // … решта літер і цифр …
};

// Дістати стовпець col символу з індексом idx у таблиці FONT.
uint8_t fontColumn(uint8_t idx, uint8_t col) {
    return pgm_read_byte(&FONT[idx][col]);   // читання саме з Flash, не напряму
}
```

Кожен рядок таблиці — намальована літера. Візьми, скажімо, `'A'`: перший байт `0x7E` — це майже повний вертикальний стовпчик (ліва стійка літери), далі три однакові `0x11` — поперечка з двома точками (перекладина й вершечок), і замикає все `0x7E` — права стійка. Дивишся на числа під кутом — і бачиш обриси літери. А `pgm_read_byte(&FONT[idx][col])` — єдиний правильний спосіб це число дістати: подаєш **адресу** елемента, функція лізе саме у Flash і повертає байт.

> 🔧 **Навіщо це.** Пропустиш `PROGMEM` — і шрифт із сотні символів (800 байтів) сяде в SRAM. Разом із буферами, стеком і рештою змінних два кілобайти вичерпаються, стек наповзе на дані, і плата почне збоїти без видимої причини: підвисати, перезавантажуватись, показувати абракадабру. Це найпідступніша пастка ATmega328P — не помилка логіки, а **тиха нестача пам'яті**. Тримай усі великі сталі таблиці (шрифти, криві, мелодії) у `PROGMEM`, звертайся через `pgm_read_byte` — і SRAM лишиться під те, що справді мусить бути змінним.

## Зсув: як рухати текст

Тепер механіка руху. Уяви весь текст як довгу стрічку цяток: усі літери, поставлені поряд, стовпчик до стовпчика. Екран 8×8 — це вузьке **віконце** шириною вісім стовпців, крізь яке видно лише шматок стрічки. Щоб текст «побіг», віконце повільно зсувається вздовж стрічки: показали стовпці 0–7, потім 1–8, потім 2–9 — і око бачить, як літери пливуть.

Тримати всю стрічку в пам'яті не треба — досить **на кожен крок вирахувати вісім видимих стовпців** прямо зі шрифту. Стрічка ділиться на символи по вісім стовпців (плюс, як правило, один порожній між літерами — щоб не злипались). За номером глобального стовпця `x` легко сказати, який це символ і котрий його стовпчик:

```cpp
const char* message = "HELLO ";     // що біжить
uint8_t colBuf[8];                  // вісім видимих стовпців (буфер по стовпцях)

// Індекс символу в таблиці FONT за його кодом (тут — латиниця й пробіл).
uint8_t glyphIndex(char ch) {
    if (ch == ' ') return 0;
    if (ch >= 'A' && ch <= 'Z') return 1 + (ch - 'A');   // 'A' → 1, 'B' → 2, …
    return 0;                                            // невідоме → пробіл
}

// Обчислити вісім видимих стовпців, коли віконце зсунуте на offset стовпців.
void renderWindow(uint16_t offset) {
    uint8_t len = strlen(message);
    const uint8_t GLYPH_W = 8;                 // ширина символу в стовпцях
    for (uint8_t screenCol = 0; screenCol < 8; screenCol++) {
        uint16_t x = offset + screenCol;       // глобальний номер стовпця стрічки
        uint8_t  charPos = x / GLYPH_W;        // котрий це символ повідомлення
        uint8_t  inChar  = x % GLYPH_W;        // котрий стовпчик усередині символу
        if (charPos >= len) {                  // за кінцем тексту — порожньо
            colBuf[screenCol] = 0x00;
            continue;
        }
        uint8_t idx = glyphIndex(message[charPos]);
        colBuf[screenCol] = fontColumn(idx, inChar);   // стовпець зі шрифту (Flash)
    }
}
```

`renderWindow(offset)` — це і є суть біжучого рядка. Він не зберігає стрічку цілком; для кожного з восьми екранних стовпців він на льоту рахує, який глобальний стовпець стрічки туди потрапив (`offset + screenCol`), розкладає це на «символ і стовпчик у ньому» діленням і остачею, і бере готовий стовпчик зі шрифту. Збільшуєш `offset` на одиницю — і вся картинка з'їжджає на стовпець ліворуч.

## Зшиваємо все докупи

Лишилось крутити `offset` і показувати кадр. Тут спливає одна тонкість формату: шрифт ми зберігали **по стовпцях**, а обидва виводи драйвера (і прямий, і MAX7219) чекають буфер **по рядках** (`frame[r]` — узор рядка). Тож перед показом стовпцевий буфер треба **перекласти на рядковий** — це маленька транспозиція вісім на вісім:

```cpp
// Перекласти вісім стовпців (colBuf) у вісім рядків (frame): транспозиція 8×8.
void columnsToRows() {
    for (uint8_t r = 0; r < 8; r++) {
        uint8_t rowBits = 0;
        for (uint8_t c = 0; c < 8; c++) {
            if (colBuf[c] & (1 << r))       // цятка (рядок r, стовпець c) горить?
                rowBits |= (1 << c);        // тоді ставимо біт c у рядку r
        }
        frame[r] = rowBits;
    }
}

void loop() {
    static uint16_t offset = 0;
    uint16_t total = strlen(message) * 8;   // повна довжина стрічки в стовпцях

    renderWindow(offset);     // порахувати вісім видимих стовпців
    columnsToRows();          // перекласти на рядки для виводу
    max7219show();            // показати (для прямого способу — нічого, крутить таймер)

    offset++;
    if (offset >= total) offset = 0;   // добіг кінця — почати спочатку

    delay(90);                // швидкість бігу: більше число — повільніше
}
```

І ось воно біжить. Кожні 90 мілісекунд віконце з'їжджає на стовпець, `renderWindow` бере зі шрифту нові вісім стовпців, транспозиція кладе їх у `frame[]` рядками, а `max7219show` (або, для прямого способу, невпинний таймер розгортки) виводить кадр на цятки. `delay(90)` тут припустимий саме тому, що з MAX7219 картинку між зсувами тримає сам чип — мікроконтролеру нема чого робити, поки віконце стоїть. При прямому способі замість `delay` краще рухати `offset` по `millis()`, щоб не глушити нічого іншого, — але механіка зсуву та сама.

## Пастки біжучого рядка

Драйвер має свій список пасток; біжучий рядок додає до нього власну, суто програмну — плутанину формату даних.

**Плутанина формату «рядки проти стовпців».** Ми зберігали шрифт по стовпцях, а виводили по рядках — і між ними стоїть транспозиція `columnsToRows()`. Забудеш її або переплутаєш, який буфер чого — і замість літер побачиш їхні «дзеркала по діагоналі». Тримай у голові чітко: шрифт для біжучого рядка зручний **колонками** (бо зсув іде стовпцями), а обидва виводи хочуть буфер **рядками** (`frame[r]`); місток між ними — одна транспозиція вісім на вісім.

**Порожнеча між літерами й порядок символів.** `renderWindow` розкладає глобальний стовпець на символ і стовпчик у ньому діленням `x / 8` та остачею `x % 8`. Якщо у шрифті літера займає не всі вісім стовпців (у прикладі `'A'` реально малюється п'ятьма, решта — нулі), проміжок між сусідніми літерами вийде природний. Але щойно захочеш вужчі букви або змінний інтервал — доведеться відмовитися від сталого `GLYPH_W = 8` і вести окрему таблицю ширин; інакше текст «дихатиме» нерівномірно. Для першого біжучого рядка стала ширина вісім — найпростіший і найнадійніший вибір.

Найважливіше, що весь цей код — шрифт у Flash, розрахунок віконця, транспозиція — **не залежить від способу керування матрицею**. Він лише пише у буфер кадру; а як ті вісім байтів долетять до світлодіодів — пряме мультиплексування чи MAX7219 — біжучому рядку байдуже. Зміниться лише остання ланка, [сам драйвер](book:boards/led-matrix-8x8/api-driver.md), а логіка тексту лишиться та сама.
