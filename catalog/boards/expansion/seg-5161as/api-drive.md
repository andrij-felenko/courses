# ⚙️ Бібліотека керування 5161AS: маски, яскравість, кілька розрядів

Засвітити одну цифру на 5161AS — три рядки коду й масив із десяти байтів. Але щойно проєкт виростає з «блимнути `8`» у щось живе — годинник, лічильник, вольтметр на макетці, — з'являються запитання, на які «три рядки» не відповідають. Як показати `A`, `F`, `−` чи знак градуса? Як притлумити цифру вночі, щоб не сліпила? І головне — що робити, коли одного розряду мало, а восьми вільних ніг мікроконтролера вже немає? Ці питання й розв'язує невеличка бібліотека: не «фреймворк», а кількадесят рядків, які один раз пишеш чесно й далі не переписуєш у кожному скетчі.

Тут ми зберемо таку бібліотеку крок за кроком: спершу таблицю масок (і чому вона саме така), тоді єдиний вимикач між спільним катодом і анодом, далі керування яскравістю двома різними способами, і врешті — вихід за межу одного розряду через зсувний регістр [74HC595](book:electronics/74hc595) та через мультиплексування. Кожен шматок — робоча прошивка, яку можна залити й побачити результат, а не псевдокод «для ілюстрації»; код скрізь показано трьома вкладками — Arduino, ESP-IDF і STM32 HAL, — бо сама задача на будь-якому мікроконтролері та сама, різняться лише назви функцій.

> 🔧 **Навіщо це.** Різниця між «працює в мене на столі» і «працює» — це рівно ті деталі, які нижче: порядок бітів, що збігається з розводкою; рівні, інвертовані під анод; струм, що не перевищує стелю ні виводу, ні зовнішньої мікросхеми. Кожну з них програміст, який знає лише «виставити рівень на виводі» (`digitalWrite`, `gpio_set_level`, `HAL_GPIO_WritePin` — назва різна, дія та сама), відкриває боляче — коли цифра виходить дзеркальна, дисплей ледь тліє або 74HC595 гріється й гине. Один раз розкласти їх «чому» — і код керування дисплеєм перестає бути джерелом сюрпризів.

## Задача: одна таблиця замість купи `digitalWrite`

Керувати сегментами напряму, окремим записом рівня на кожен вивід, — можна, але код швидко перетворюється на кашу з дев'яти викликів, повторених у кожному місці, де треба щось показати. Природний хід — **відділити «яка цифра» від «які ноги смикати»**. Проміжною мовою між ними стає **байт-маска**: одне 8-бітне число, де кожен біт — стан одного сегмента. Біт `a` — молодший (розряд 0), далі `b, c, d, e, f, g`, а восьмий (розряд 7) — крапка `DP`.

Чому саме байт, і чому такий порядок? Тому що сегментів рівно вісім, і вони чудово лягають у один байт — жодного біта не пропадає. А порядок `a…g, DP` від молодшого до старшого — це не закон природи, а **домовленість**, яку ми обираємо раз і тримаємо всюди: у таблиці, у масиві ніг, у зсувному регістрі. Щойно домовленість «поплила» бодай в одному місці — цифри виходять покручені. Тому першим ділом фіксуємо її як коментар, який видно завжди:

```c
//  біт:  7    6   5   4   3   2   1   0
//        DP   g   f   e   d   c   b   a
//        ↑ старший                  ↑ молодший
```

Тепер цифру `3` — сегменти `a, b, c, d, g` — можна записати як число, поставивши одиниці в потрібних розрядах: біти 0,1,2,3,6 → `0b01001111`. Це й є суть: **таблиця масок перекладає символ у набір рисок**, а вивід масок на ноги — окрема, дурна й однакова для всіх символів операція.

## Ідея: таблиця з 0-9, HEX і крапкою, зібрана з масок сегментів

Замість того щоб виписувати кожне число вручну (і помилятися в бітах), маску зручніше **зібрати з іменованих сегментів** — тоді запис читається як сама цифра. Оголосимо константи-біти й складемо їх операцією «або»:

```c
#include <stdint.h>

// Кожен сегмент — окремий біт у масці (порядок a..g, DP)
#define SA  (1 << 0)
#define SB  (1 << 1)
#define SC  (1 << 2)
#define SD  (1 << 3)
#define SE  (1 << 4)
#define SF  (1 << 5)
#define SG  (1 << 6)
#define SDP (1 << 7)

// Таблиця символів: 0..9, потім A b C d E F (для HEX).
// Маска зібрана з сегментів — видно, які риски світяться.
const uint8_t FONT[16] = {
  SA|SB|SC|SD|SE|SF,       // 0
        SB|SC,             // 1
  SA|SB|   SD|SE|   SG,    // 2
  SA|SB|SC|SD|      SG,    // 3
        SB|SC|   SF|SG,    // 4
  SA|   SC|SD|SF|SG,       // 5
  SA|   SC|SD|SE|SF|SG,    // 6
  SA|SB|SC,                // 7
  SA|SB|SC|SD|SE|SF|SG,    // 8
  SA|SB|SC|SD|   SF|SG,    // 9
  SA|SB|SC|   SE|SF|SG,    // A
        SC|SD|SE|SF|SG,    // b (мала, бо велика «B» = «8»)
  SA|      SD|SE|SF,       // C
     SB|SC|SD|SE|   SG,    // d (мала, бо велика «D» = «0»)
  SA|      SD|SE|SF|SG,    // E
  SA|         SE|SF|SG,    // F
};
```

Зверніть увагу на дрібницю, яка щоразу спантеличує новачків: у HEX-режимі `B` і `D` пишуть **малими** (`b`, `d`). Причина фізична, а не примхлива — велика `B`, засвічена всіма рисками, збіглася б з `8`, а велика `D` — з `0`; читач би їх не розрізнив. Тому семисегментний «алфавіт» для `b` і `d` завжди малий: `b` — це `c, d, e, f, g` (без верху й правого-верхнього), `d` — `b, c, d, e, g`. Це стала конвенція всіх HEX-дисплеїв.

Кілька корисних не-цифрових символів, які варто мати напохваті:

```c
#define GLYPH_MINUS   SG                       // «−» лише поперечка
#define GLYPH_DEGREE  (SA|SB|SF|SG)            // «°» верхнє кільце
#define GLYPH_BLANK   0                        // порожньо (усе згашено)
#define GLYPH_E       (SA|SD|SE|SF|SG)         // «E» — напр. для «Err»
```

Крапка `DP` у таблицю не входить навмисно: вона **ортогональна** до символу — будь-яку цифру можна показати з крапкою або без, тож її додають окремим бітом уже під час виводу, не плодячи другої таблиці на 32 рядки.

## Робочий C++: структура-драйвер під один розряд

Тепер зберемо таблицю, ноги й операцію виводу в один охайний об'єкт. Структура тримає масив із восьми ніг (у порядку `a…g, DP`) і прапорець полярності — про нього нижче. Метод `show` бере символ, домішує крапку й розкладає біти по ногах. Від платформи тут потрібні рівно дві речі: перевести вісім виводів у режим виходу й уміти виставити на виводі рівень — усе інше однакове, тож нижче та сама конструкція в трьох середовищах.

:::tabs
```arduino
#include <Arduino.h>

class Seg5161 {
public:
  // pins[8] у порядку a,b,c,d,e,f,g,DP.
  // commonAnode = false для 5161AS (спільний катод), true для 5161BS.
  Seg5161(const uint8_t (&pins)[8], bool commonAnode = false)
    : _anode(commonAnode) {
    for (uint8_t i = 0; i < 8; i++) _pin[i] = pins[i];
  }

  void begin() {
    for (uint8_t i = 0; i < 8; i++) {
      pinMode(_pin[i], OUTPUT);
      writeSeg(i, false);            // старт із погашеного
    }
  }

  // Показати вже готову маску (біт=сегмент, порядок a..g,DP)
  void showMask(uint8_t mask) {
    for (uint8_t i = 0; i < 8; i++)
      writeSeg(i, (mask >> i) & 1);
  }

  // Показати символ 0..15 (0-9,A,b,C,d,E,F), опційно з крапкою
  void showHex(uint8_t v, bool dot = false) {
    uint8_t m = FONT[v & 0x0F];
    if (dot) m |= SDP;
    showMask(m);
  }

  void clear() { showMask(0); }

private:
  uint8_t _pin[8];
  bool    _anode;

  // Один сегмент: on=true → світиться. Полярність вирішує рівень.
  void writeSeg(uint8_t i, bool on) {
    // Спільний катод: сегмент світиться від HIGH.
    // Спільний анод:  усе навпаки — світиться від LOW.
    bool level = _anode ? !on : on;
    digitalWrite(_pin[i], level);
  }
};

// --- використання ---
const uint8_t SEG_PINS[8] = { 2, 3, 4, 5, 6, 7, 8, 9 }; // a b c d e f g DP
Seg5161 disp(SEG_PINS, /*commonAnode=*/false);          // 5161AS

void setup() { disp.begin(); }

void loop() {
  for (uint8_t v = 0; v < 16; v++) {   // прокрутити 0..F
    disp.showHex(v, /*dot=*/(v == 10)); // крапку лише на «A» — для прикладу
    delay(500);
  }
}
```
```esp-idf
#include "driver/gpio.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

// Виводи в тому самому порядку a,b,c,d,e,f,g,DP — тут це номери GPIO.
static const gpio_num_t SEG_PIN[8] = {
  GPIO_NUM_4,  GPIO_NUM_5,  GPIO_NUM_6,  GPIO_NUM_7,
  GPIO_NUM_15, GPIO_NUM_16, GPIO_NUM_17, GPIO_NUM_18,
};
static const bool COMMON_ANODE = false;   // 5161AS — спільний катод

// Замість pinMode у циклі — один опис одразу на всі вісім ніг.
static void seg_begin(void) {
  uint64_t pins = 0;
  for (int i = 0; i < 8; i++) pins |= 1ULL << SEG_PIN[i];
  gpio_config_t cfg = {
    .pin_bit_mask = pins,
    .mode         = GPIO_MODE_OUTPUT,
    .pull_up_en   = GPIO_PULLUP_DISABLE,
    .pull_down_en = GPIO_PULLDOWN_DISABLE,
    .intr_type    = GPIO_INTR_DISABLE,
  };
  ESP_ERROR_CHECK(gpio_config(&cfg));
  for (int i = 0; i < 8; i++) gpio_set_level(SEG_PIN[i], COMMON_ANODE);
}

// Той самий єдиний рядок фізики: полярність вирішує рівень.
static void seg_show_mask(uint8_t mask) {
  for (int i = 0; i < 8; i++) {
    bool on = (mask >> i) & 1;
    gpio_set_level(SEG_PIN[i], COMMON_ANODE ? !on : on);
  }
}

static void seg_show_hex(uint8_t v, bool dot) {
  uint8_t m = FONT[v & 0x0F];
  if (dot) m |= SDP;
  seg_show_mask(m);
}

void app_main(void) {
  seg_begin();
  while (true) {
    for (uint8_t v = 0; v < 16; v++) {
      seg_show_hex(v, v == 10);
      vTaskDelay(pdMS_TO_TICKS(500));
    }
  }
}
```

```stm32
typedef struct { GPIO_TypeDef *port; uint16_t pin; } SegPin;

static const SegPin SEG[8] = {
  {GPIOA, GPIO_PIN_0}, {GPIOA, GPIO_PIN_1}, {GPIOA, GPIO_PIN_2}, {GPIOA, GPIO_PIN_3},
  {GPIOA, GPIO_PIN_4}, {GPIOA, GPIO_PIN_5}, {GPIOA, GPIO_PIN_6}, {GPIOA, GPIO_PIN_7},
};
static const bool COMMON_ANODE = false;   // 5161AS — спільний катод

// Окремого begin() немає: усі вісім ніг позначені GPIO_Output у CubeMX,
// і режим виходу виставляє згенерований MX_GPIO_Init().
static void seg_show_mask(uint8_t mask) {
  for (int i = 0; i < 8; i++) {
    bool on = (mask >> i) & 1;
    if (COMMON_ANODE) on = !on;
    HAL_GPIO_WritePin(SEG[i].port, SEG[i].pin, on ? GPIO_PIN_SET : GPIO_PIN_RESET);

  uint8_t m = FONT[v & 0x0F];
  if (dot) m |= SDP;
  seg_show_mask(m);
}

int main(void) {
  HAL_Init();
  SystemClock_Config();
  MX_GPIO_Init();
  while (1) {
    for (uint8_t v = 0; v < 16; v++) {
      seg_show_hex(v, v == 10);
      HAL_Delay(500);
    }
  }
```

Уся конструкція тримається на одному місці — там, де логічне `on` перетворюється на рівень (`writeSeg` у першій вкладці, той самий один рядок у решті). Воно єдине у всій бібліотеці знає про фізику: чи від «1», чи від «0» світиться сегмент. Решта коду оперує **логічним** `on/off`, і їй байдуже, який індикатор під нею. Це і є та межа, за якою «яка цифра» відділена від «які рівні на ногах».

### Один вимикач для спільного анода

Зверніть увагу, як мало коду забирає підтримка **обох** типів індикатора. Уся відмінність між [спільним катодом і спільним анодом](book:electronics/led) зведена до одного рядка в `writeSeg`:

```cpp
bool level = _anode ? !on : on;
```

Для 5161AS (`AS` — *common cathode*, спільний катод) спільна точка сидить на землі, і сегмент запалюється рівнем `HIGH`: `on` іде на вивід як є. Для дзеркального 5161BS (`BS` — *common anode*, спільний анод) спільна точка на «плюсі», струм тече з живлення в вивід, тож сегмент світиться, коли вивід тягне **`LOW`** — і `on` доводиться інвертувати. Одна булева змінна `_anode`, задана в конструкторі, розводить ці два світи, і жодна таблиця масок не міняється: інверсія живе рівно в одному місці, а не розповзається по коду.

> 🔧 **Навіщо це.** Спокуса «просто інвертувати таблицю FONT під анод» — пастка, що аукнеться пізніше. Тоді маски перестають означати «які сегменти світяться» й починають означати «які рівні на ногах», а це різні речі: крапку вже так просто не домішаєш операцією «або», і код `GLYPH_MINUS = SG` зламається. Правильна межа — **таблиця завжди в логіці «біт=світиться», а полярність застосовується в останню мить**, коли біт уже перетворюється на напругу. Тоді той самий FONT обслуговує обидва індикатори без жодної правки.

## Яскравість: два різні важелі — струм і час

«Притлумити» цифру можна двома принципово різними способами, і плутати їх — типова помилка. Перший важіль — **скільки струму** тече крізь сегмент; другий — **яку частку часу** він узагалі світиться. Обидва змінюють видиму яскравість, але працюють на різних рівнях і мають різну ціну.

**Струмом.** Яскравість світлодіода майже пропорційна струму крізь нього, а струм задає гасильний резистор: більший опір — менший струм — тьмяніше. Це найчесніший спосіб, бо світло стале, без мерехтіння. Мінус — він **апаратний**: щоб змінити яскравість, треба змінити резистор, а це не робиться з коду. Тому струмом задають **базовий рівень** яскравості під конкретне живлення, розрахований [законом Ома](book:electronics/ohms-law) з [прямого падіння](book:electronics/diode-forward-voltage) на світлодіоді. Для точного, керованого струму, що не «пливе» від живлення й температури, ставлять окрему мікросхему — [драйвер світлодіода зі стабілізацією струму](book:electronics/led-driver); для одного індикатора на макетці це надмір, але у виробі саме так тримають однакову яскравість усіх сегментів.

**Часом (ШІМ).** А от із коду яскравість регулюють **широтно-імпульсною модуляцією**: сегмент дуже швидко вмикають і вимикають, і око бачить середню яскравість, пропорційну **шпаруватості** — частці часу «увімкнено». Ганяємо цикл на кількасот герц (щоб не було видимого мерехтіння), і в кожному періоді тримаємо сегменти ввімкненими лише потрібну частку. Ось той самий важіль у трьох середовищах: спершу «програмний ШІМ» руками поверх нашого драйвера, далі — той самий сигнал, відданий апаратному каналу таймера:

:::tabs
```arduino
// Яскравість 0..255 через програмний ШІМ на спільному виводі.
// Тут COM_PIN — це спільний катод індикатора, заведений НЕ на землю
// напряму, а на вивід МК (через транзистор, якщо струм великий).
const uint8_t COM_PIN = 10;
uint8_t brightness = 255;      // 0 = згашено, 255 = повна

void setup() {
  disp.begin();
  pinMode(COM_PIN, OUTPUT);
}

// Викликати часто; тримає задану цифру із заданою яскравістю.
void refresh(uint8_t hex, bool dot) {
  disp.showHex(hex, dot);                // виставити сегменти
  // ── один період ШІМ (≈ сотні Гц при таких паузах) ──
  digitalWrite(COM_PIN, LOW);            // катод на землю → сегменти світять
  delayMicroseconds(1 + brightness * 6); // «увімкнено» пропорційно яскравості
  digitalWrite(COM_PIN, HIGH);           // катод підняти → усе гасне
  delayMicroseconds(1 + (255 - brightness) * 6); // решта періоду — темрява
}

void loop() {
  refresh(0x3, false);                   // показуємо «3»
  // brightness можна плавно міняти десь у програмі
}
```
```esp-idf
#include "driver/ledc.h"

// Спільний катод заведено на вивід МК (через транзистор, якщо струм великий).
// Шпаруватість тримає периферія LEDC — ядро в цьому не бере участі зовсім.
#define COM_PIN  GPIO_NUM_10

static void brightness_begin(void) {
  ledc_timer_config_t t = {
    .speed_mode      = LEDC_LOW_SPEED_MODE,
    .duty_resolution = LEDC_TIMER_8_BIT,   // шпаруватість 0..255
    .timer_num       = LEDC_TIMER_0,
```

Ключ тут — **де** ми рвемо струм. Ми смикаємо не вісім сегментних ніг по черзі (це вісім разів більше роботи), а **один спільний вивід**: піднімаємо катод — і разом гаснуть усі сегменти, опускаємо — усі світять. Шпаруватість цього одного сигналу й задає яскравість усієї цифри одразу. І ще одне: ручний цикл із паузами — найпростіший, але не найкращий спосіб. Майже в кожного МК є **апаратний ШІМ** — канал таймера, який сам смикає вивід із заданою шпаруватістю (LEDC на ESP32, канал таймера в режимі PWM на STM32, `analogWrite` на частині ніг Arduino). Тоді яскравість тримається сама, без участі ядра, і не мерехтить навіть коли процесор зайнятий.

> 🔧 **Навіщо це.** Важлива тонкість струму: коли ви заводите спільний катод на вивід МК (а не прямо на землю), через цей **один** вивід тече сума струмів усіх засвічених сегментів. Вісім сегментів по 10 мА — це 80 мА крізь одну ногу, а [навантажувальна здатність](book:electronics/pin-drive-limits) виводу — лише 20-40 мА. Нога не витримає. Тому спільний вивід під ШІМ або веде **транзистор** (нога керує базою, а струм сегментів тече крізь транзистор у землю), або струм на сегмент навмисно тримають маленьким. Регулювати яскравість, забувши про цей сумарний струм, — вірний спосіб спалити вивід, який досі чесно тягнув один сегмент.

## Кілька розрядів: 74HC595 — три ноги замість восьми

Один розряд з'їдає вісім ніг. Двозначне число «в лоб» — уже шістнадцять, а стільки вільних виводів немає навіть у щедрої плати. Порятунок — не додавати ніг, а **розкладати біти зовнішньою мікросхемою**. Класичний вибір — [зсувний регістр](book:electronics/shift-register) 74HC595: ви жене в нього байт **послідовно**, по одному біту, лише трьома лініями, а він виставляє всі вісім бітів на своїх восьми виходах паралельно — рівно на наші вісім сегментів.

Три лінії керування — це:
- **DS** (він же SER, `data`) — сам біт даних;
- **SHCP** (SRCLK, `clock`) — тактовий імпульс: на кожному фронті регістр «засмоктує» черговий біт з DS і зсуває решту;
- **STCP** (RCLK, `latch`, «засувка») — коли всі вісім бітів усередині, імпульс на цю ногу разом виштовхує їх на виходи.

Поділ на «зсувний» і «засувковий» регістри всередині 74HC595 — не примха: він дає засунути новий байт **непомітно**, поки на виходах ще стоїть старий, і показати його миттєво одним клацанням STCP, без проблиску проміжних станів. Гнати байт у регістр можна двома шляхами: смикати три ноги руками (в Arduino для цього є готова `shiftOut`) або віддати роботу **апаратному SPI** — 74HC595 і є найпростіший SPI-приймач, де DS це MOSI, SHCP — SCLK, а STCP чудово лягає на лінію вибору CS, яка сама підскакує вгору після останнього біта. Код короткий в обох випадках:

:::tabs
```arduino
// 5161AS через один 74HC595: 3 ноги МК замість 8.
// Виходи регістра Q0..Q7 розведені на сегменти a..g,DP відповідно.
const uint8_t PIN_DATA  = 2;   // DS   (SER)   → пін 14 регістра
const uint8_t PIN_CLOCK = 3;   // SHCP (SRCLK) → пін 11 регістра
const uint8_t PIN_LATCH = 4;   // STCP (RCLK)  → пін 12 регістра

void setup() {
  pinMode(PIN_DATA, OUTPUT);
  pinMode(PIN_CLOCK, OUTPUT);
  pinMode(PIN_LATCH, OUTPUT);
}

void showMask595(uint8_t mask) {
  digitalWrite(PIN_LATCH, LOW);                  // закрити засувку на час засування
  shiftOut(PIN_DATA, PIN_CLOCK, MSBFIRST, mask); // 8 бітів у регістр
  digitalWrite(PIN_LATCH, HIGH);                 // клац → усі 8 виходів разом
}

void loop() {
  static const uint8_t THREE = SA|SB|SC|SD|SG;   // «3»
  showMask595(THREE);
  delay(500);
}
```

Три ноги замість восьми — уже виграш, але справжня сила 74HC595 в іншому: регістри **ставляться ланцюжком**. Вихід переповнення `Q7'` (пін 9) одного регістра йде на `DS` наступного; тоді два байти підряд (два `shiftOut`, або одна SPI-передача на два байти) заповнюють два розряди, три — три, і так далі, а ліній керування лишається **ті самі три** на скільки завгодно цифр. Восьмирозрядне табло — це вісім 595 у ряд і три ноги мікроконтролера. Саме так побудовані готові багаторозрядні модулі; якщо потрібне табло без паяння регістрів руками, дивіться в бік [чотирирозрядного 5641AS](book:boards/seg-5641as), де ця логіка вже на платі.

> 🔧 **Навіщо це.** Найпідступніша пастка 74HC595 — **порядок бітів проти розводки**. Передача «старшим бітом уперед» (`MSBFIRST` у `shiftOut`, звичне MSB First у SPI) відправляє старший біт першим, і він осідає на виході **Q0** (пін 15), а молодший — на **Q7** (пін 7). Тобто фізичний порядок виходів **дзеркальний** до порядку бітів у байті. Якщо ви розвели `Q0→a, Q1→b, …` в надії, що біт 0 (`a`) потрапить на Q0, — вийде навпаки, і цифри будуть покручені. Три виходи: або жени молодшим бітом уперед (`LSBFIRST` у `shiftOut`, `SPI_FIRSTBIT_LSB` у налаштуваннях SPI), або розведи виходи у дзеркальному порядку, або (найчистіше) один раз склади таблицю FONT під фактичну розводку й забудь. Головне — **звірити напрямок один раз тестовим байтом** (напр. засвітити лише сегмент `a` маскою `0b00000001` і подивитися, яка риска спалахнула), а не гадати.

## Кілька розрядів без регістра: мультиплексування

Є й інший шлях показати багато цифр, коли зайвих ніг немає, — **мультиплексування** (лат. *multiplex* — багатоскладовий). Ідея зухвала: фізично **всі розряди ділять ті самі вісім сегментних ліній**, з'єднані паралельно (усі `a` разом, усі `b` разом…), а розрізняє їх лише **спільний вивід**: у кожну мить живиться лише **один** розряд, решта згашені. Мозок бачить одне ціле число, бо ми **дуже швидко** перебираємо розряди по черзі — засвітили перший на мілісекунду, згасили, засвітили другий, і так по колу сотні разів на секунду. Око не встигає за перемиканням і зливає окремі спалахи в суцільну картинку — те саме [явище інерції зору](book:electronics/led-photodiode/proj-charlieplexing.md), на якому тримаються всі динамічні дисплеї.

Рахунок ніг разюче кращий: чотири розряди — це вісім сегментних ліній плюс чотири спільних (по одній на розряд), разом **дванадцять** ніг замість тридцяти двох при прямому керуванні. Ось скелет мультиплексного виводу чотирьох цифр (припускаємо чотири окремі 5161AS або готовий 5641AS, у якого сегменти вже зведені всередині). Перша вкладка крутить перемальовування просто в головному циклі — так найвидніше, що відбувається; дві інші одразу вішають той самий крок на апаратний таймер, як і роблять у реальному проєкті:

:::tabs
```arduino
// 4 розряди: 8 сегментних ліній спільні, 4 «цифрові» вибирають розряд.
const uint8_t SEG[8]   = { 2, 3, 4, 5, 6, 7, 8, 9 };   // a..g,DP (спільні!)
const uint8_t DIGIT[4] = { 10, 11, 12, 13 };           // катоди 4 розрядів

uint8_t frame[4] = { 0, 0, 0, 0 };   // що показувати в кожному розряді (маски)

void setup() {
  for (uint8_t i = 0; i < 8; i++) pinMode(SEG[i], OUTPUT);
  for (uint8_t d = 0; d < 4; d++) { pinMode(DIGIT[d], OUTPUT);
                                    digitalWrite(DIGIT[d], HIGH); } // усі згашені
}

// Один прохід: швидко «промалювати» всі 4 розряди по черзі.
void multiplex() {
  for (uint8_t d = 0; d < 4; d++) {
    // 1) згасити все, щоб не було «привидів» від попереднього розряду
    for (uint8_t i = 0; i < 4; i++) digitalWrite(DIGIT[i], HIGH);
    // 2) виставити маску поточного розряду на спільні сегменти
    uint8_t m = frame[d];
    for (uint8_t i = 0; i < 8; i++) digitalWrite(SEG[i], (m >> i) & 1);
    // 3) увімкнути ЛИШЕ цей розряд (катод на землю)
    digitalWrite(DIGIT[d], LOW);
    delayMicroseconds(2000);          // ~2 мс на розряд → ~125 Гц на всі 4
  }
}

void setNumber(int n) {              // розкласти число на 4 цифри
  for (int d = 3; d >= 0; d--) { frame[d] = FONT[n % 10]; n /= 10; }
}

void loop() {
  setNumber(1234);
  multiplex();                        // кликати безперервно
}
```

```esp-idf
#include "esp_timer.h"

// 4 розряди: спільні сегменти вже налаштовані в seg_begin(), тут — вибір розряду.
static const gpio_num_t DIGIT[4] = { GPIO_NUM_1, GPIO_NUM_2, GPIO_NUM_3, GPIO_NUM_8 };
static uint8_t frame[4] = { 0, 0, 0, 0 };

// Один розряд за виклик; таймер кличе кожні 2 мс → ~125 Гц на всі 4.
static void multiplex_step(void *arg) {
  static int d = 0;
  for (int i = 0; i < 4; i++) gpio_set_level(DIGIT[i], 1);   // згасити все
  seg_show_mask(frame[d]);                                   // маска розряду
  gpio_set_level(DIGIT[d], 0);                               // катод на землю
  d = (d + 1) & 3;
}

static void multiplex_begin(void) {
  gpio_config_t cfg = {
    .pin_bit_mask = (1ULL << DIGIT[0]) | (1ULL << DIGIT[1])
                  | (1ULL << DIGIT[2]) | (1ULL << DIGIT[3]),
    .mode = GPIO_MODE_OUTPUT, .pull_up_en = GPIO_PULLUP_DISABLE,
    .pull_down_en = GPIO_PULLDOWN_DISABLE, .intr_type = GPIO_INTR_DISABLE,
  };
  ESP_ERROR_CHECK(gpio_config(&cfg));
  for (int i = 0; i < 4; i++) gpio_set_level(DIGIT[i], 1);   // усі згашені

  const esp_timer_create_args_t a = { .callback = multiplex_step, .name = "mux" };
  esp_timer_handle_t h;
  ESP_ERROR_CHECK(esp_timer_create(&a, &h));
  ESP_ERROR_CHECK(esp_timer_start_periodic(h, 2000));        // період у мкс
}

static void set_number(int n) {
  for (int d = 3; d >= 0; d--) { frame[d] = FONT[n % 10]; n /= 10; }
}

void app_main(void) {
  seg_begin();
  multiplex_begin();
  set_number(1234);                   // далі перемальовує таймер
}
```

Логіка вся у `multiplex`: згасити → виставити сегменти → засвітити один розряд → крихітна пауза → наступний. Порядок кроків **не випадковий**: спершу гасимо всі розряди, лише тоді міняємо сегменти, і аж потім вмикаємо потрібну цифру. Інакше під час зміни масок на спільних лініях на долю мілісекунди спалахнув би «привид» — шматок сусідньої цифри на цьому розряді (англ. *ghosting*).

За мультиплексування, однак, платять — і ця плата пояснює, чому для **одного** розряду він недоречний. По-перше, кожен розряд світить лише чверть часу (при чотирьох цифрах), тож середня яскравість падає вчетверо; щоб компенсувати, крізь сегменти в момент їхнього спалаху пускають **більший** імпульсний струм. По-друге, дисплей доводиться **безперервно перемальовувати** — варто циклу `multiplex` спинитися (застрягли в довгій паузі, у важкому обчисленні, у мережевому виклику), і цифри або згаснуть, або застигнуть на одному розряді. Тому мультиплексування в серйозних проєктах вішають на **апаратний таймер із перериванням**, щоб перемальовування йшло само, незалежно від головної програми. Для одного 5161AS усього цього не треба зовсім: розряд один, ділити нема що — вмикай його статично й забудь.

## Складність і пастки: де це ламається

Зберемо в одному місці граблі саме програмної частини — те, на чому губиться час уже після того, як залізо спаяне правильно.

**Порядок бітів не збігається з розводкою.** Головна й найчастіша. Байдуже, прямий вивід, 595 чи мультиплекс, — якщо домовленість «біт `i` → сегмент → фізична нога» розійшлася бодай в одному місці, цифри виходять покручені й нечитабельні. З 74HC595 це загострюється тим, що `shiftOut(MSBFIRST)` кладе біти у **дзеркальному** до виходів порядку (старший біт → Q0). Ліки одні: **звірити напрямок тестовим байтом** — засвітити рівно один сегмент відомою маскою й подивитися, який спалахнув, — а далі тримати одну домовленість по всьому проєкту. Не гадати, а поміряти.

**Переплутана полярність (катод/анод) у коді.** Схема під спільний анод, а в конструкторі лишили `commonAnode=false` (або навпаки) — і дисплей або мовчить, або показує «фотонегатив»: світиться те, що мало б бути темним. Уся полярність зведена в один рядок `writeSeg` саме щоб її було легко перевірити першою. 5161AS — спільний **катод**, тож `commonAnode=false`; переплутали з `BS`-версією — інвертуйте прапорець, а не таблицю.

**Сумарний струм спільного виводу.** Коли спільний вивід заходить на ногу МК (заради ШІМ-яскравості чи мультиплексування), крізь неї тече **сума** струмів усіх засвічених сегментів. `8` — це вісім сегментів; при 10 мА на кожен — 80 мА крізь одну ногу, а її [стеля](book:electronics/pin-drive-limits) — 20-40 мА. Нога перегрівається й деградує. Спільну лінію під навантаженням веде **транзистор**, а не сама нога.

**Ліміт струму 74HC595.** Окрема, менш очевидна межа. У регістра теж є стеля — і не лише на вивід. За даташитом Texas Instruments на SN74HC595 абсолютний максимум — **±35 мА на один вихід**, але **±70 мА сумарно** крізь вивід живлення VCC чи землі GND. Вісім сегментів по 10 мА дають 80 мА — уже **над** сумарною межею, хоча кожен окремий вихід ще в нормі. Регістр гріється й з часом гине, а причину шукають деінде. Тому струм на сегмент від 595 беруть **меншим** (резистори більші, ~5-7 мА на сегмент), щоб сума восьми лишалася під 70 мА; або ставлять регістр, розрахований на більший струм (напр. TPIC6B595 зі стоками-ключами), коли треба яскраво. *(Статус: підтверджено даташитом TI SN74HC595, абсолютні максимуми I_O = ±35 мА, I через VCC/GND = ±70 мА.)*

**Живлення 3.3 проти 5 В.** Той самий код на 3.3-вольтовому МК (ESP32, STM32, RP2040) світить помітно тьмяніше, ніж на 5-вольтовому (Arduino UNO), при однакових резисторах — бо при нижчій напрузі різниця «живлення мінус падіння світлодіода» менша, отже й струм менший. Це не баг коду, а фізика: резистори, пораховані під 5 В, для 3.3 В завеликі. Перерахуйте опір під фактичне живлення (для червоного при 3.3 В — близько 150 Ом замість 330). І пам'ятайте про [логічні рівні](book:electronics/logic-levels-as-ranges): 5-вольтову логіку не можна прямо чіпляти до 3.3-вольтового входу ESP32.

**Забутий `latch` / `refresh`.** У 74HC595 без імпульсу STCP (`latch`) засунуті біти лишаються **всередині** й на виходи не потрапляють — дисплей не міняється, хоча байт уже пішов у регістр і передача відпрацювала. У мультиплексуванні аналог — забути **безперервно** кликати перемальовування: один виклик покаже спалах і згасне. Обидві помилки виглядають як «код правильний, а екран мертвий»: дані готові, але останній крок, що виштовхує їх у світло, не зроблено.

**Числа поза таблицею.** `FONT[v]` для `v > 15` вилізе за масив — сміття на дисплеї або й падіння. Тому в `showHex` стоїть `v & 0x0F`, що затискає індекс у 0-15; для десяткового виводу окремо стежте, щоб цифра була 0-9. Дрібниця, але саме такі виходи за межу масиву дають «випадкові» глюки, які важко впіймати.

Отака вся «складність» керування семисегментним індикатором: не в алгоритмах, а в трьох речах, які треба тримати в голові одночасно — щоб **порядок бітів** збігався з розводкою, щоб **полярність** відповідала типу індикатора, і щоб **струм** ніде не перевищив стелю — ні виводу МК, ні зовнішнього регістра. Тримайте ці три межі, і та сама таблиця з шістнадцяти байтів однаково чесно світить хоч на одному розряді напряму, хоч на восьми через ланцюг регістрів.
