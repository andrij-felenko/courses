# ⚙️ Проєкт: драйвер KY-023 у прошивці — від сирих чисел до керма

Три `analogRead` і один `digitalRead` — це весь діалог із залізом джойстика, і на цьому фізика скінчилася. Далі починається інженерія: сирі числа з АЦП майже нікуди не годяться напряму. Центр гуляє, біля нуля все дрижить, «вгору» чомусь дає менше число, кнопка спрацьовує сама. Кожну з цих бід лікують кількома рядками коду — і, що важливо, **одними й тими самими рядками для будь-якої задачі**. Тому спершу зберемо один невеликий драйвер, який перетворює джойстик на чесний орган керування, а тоді на ньому складемо чотири готові речі: вести курсор, кермувати двома моторами танковим способом, читати вісім напрямків замість двох осей і ловити чистий натиск кнопки без брязкоту. Наприкінці — два повні скетчі, під Arduino (10-бітний АЦП) і під ESP32 (12-бітний), бо різниця між ними не косметична, і саме там ховається пара пасток.

Код усюди справжній — C++ під Arduino-фреймворк, той, що компілюється й заливається на ATmega328P чи на ESP32. Не псевдокод: типи, оголошення, імена — усе таке, як воно в реальному скетчі.

## Задача: чого ми хочемо від осі

Сформулюймо чесно, що має віддавати «правильна» вісь, бо з цього списку виросте весь драйвер. Від однієї осі джойстика ми хочемо число, яке:

- **дорівнює нулю, коли ручку відпущено** — навіть якщо конкретний екземпляр у спокої показує не 512, а 498 чи 531;
- **не дрижить у спокої** — дрібний шум АЦП і механічний люфт ручки не мають ворушити кермо;
- **лежить у зручному, передбачуваному діапазоні** — скажімо, від −100 до +100, а не в сирих 0…1023, які ще й різні для 10- і 12-бітного АЦП;
- **росте в той бік, у який ми очікуємо** — «вправо» дає плюс, «вгору» дає плюс, а не навпаки через те, як модуль лежить на столі.

Жодна з цих чотирьох вимог не виконується сама собою. Кожна — це наслідок того, що всередині KY-023 [два звичайні потенціометри-дільники](book:electronics/potentiometer): їхній центр неточний, їхній вихід шумить, їхній розмах прив'язаний до живлення, а напрямок росту залежить від того, який кінець смужки опору сидить на плюсі. Отже, драйвер осі — це рівно чотири кроки, кожен закриває одну вимогу: **виміряй центр → відніми його → відкинь мертву зону → домасштабуй і, якщо треба, інвертуй**. Зберемо їх у код так, щоб цей ланцюжок було видно очима.

## Ідея: одна структура на вісь, решта — поверх неї

Спокуса писати `analogRead` і магічні числа розкидано по всьому скетчу велика, і саме вона робить джойстик-код нечитабельним. Натомість замкнімо все знання про одну вісь у маленьку структуру: де її пін, який у неї виміряний центр, яка мертва зона, чи інвертувати. Тоді будь-яка задача — курсор, мотори, напрямки — працює з двома такими структурами й більше нічого про потенціометри не знає.

:::tabs
```cpp
struct Axis {
    uint8_t pin;        // аналоговий пін цієї осі (VRx або VRy)
    int     center;     // виміряний центр (заповнюємо на старті)
    int     lo, hi;     // сирі краї ходу: 0 і (ADC_MAX) — залежить від плати
    int     deadzone;   // напівширина мертвої зони, в одиницях АЦП
    bool    invert;     // true → міняємо знак виходу
};
```
```micropython
class Axis:
    def __init__(self, pin, center, lo, hi, deadzone, invert=False):
        self.pin = pin           # об'єкт ADC цієї осі (VRx або VRy)
        self.center = center     # виміряний центр (заповнюємо на старті)
        self.lo = lo             # сирий нижній край ходу: 0
        self.hi = hi             # сирий верхній край ходу: ADC_MAX — залежить від плати
        self.deadzone = deadzone # напівширина мертвої зони, в одиницях АЦП
        self.invert = invert     # True → міняємо знак виходу
```
:::

Поле `hi` тут не випадкове й не косметичне — це те єдине місце, де 10-бітна Arduino відрізняється від 12-бітного ESP32. На Arduino `analogRead` віддає 0…1023, тож `hi = 1023`; на ESP32 — 0…4095, тож `hi = 4095`. Заведемо цю межу однією константою на весь скетч, і тоді ту саму логіку осі можна залити на обидві плати, змінивши один рядок:

```cpp
// Стеля АЦП: Arduino Uno/Nano — 1023 (10 біт); ESP32 — 4095 (12 біт).
#if defined(ESP32)
  const int ADC_MAX = 4095;
#else
  const int ADC_MAX = 1023;
#endif
```

> 🔧 **Навіщо це.** `#if defined(ESP32)` — не мода, а страховка від найтихішої з пасток джойстика. Якщо взяти скетч, писаний під Arduino з жорстко зашитим 1023, і залити на ESP32, він **скомпілюється й запуститься**, але поводитиметься дивно: центр опиниться не 2048, а десь коло 2048, тоді як код чекає 512, і вся математика осі поповзе. Помилки не буде — буде «якось не так їде», а це найгірший різновид біди, бо його довго шукаєш не там. Одна константа `ADC_MAX`, виведена з макроса плати, прибирає цілий клас таких загадок: логіка осі однакова, змінюється лише число розмаху.

## Крок за кроком: чотири поправки в коді

Тепер напишемо саме перетворення — з сирого `analogRead` у чесне число −100…+100. Розкладемо його на ті самі чотири кроки, які вивели із задачі, і кожен прокоментуємо на місці.

### Калібрування центру на старті

Центр міряємо один раз, поки ручка гарантовано відпущена, — у `setup()`. Не беремо одне значення (воно шумить), а усереднюємо кілька десятків: сума ділена на кількість дає стабільний «нуль» саме цього екземпляра. Заразом можна перевірити, що ручку справді не чіпають: якщо розкид вимірів завеликий, хтось тримає джойстик, і центр вийде кривий.

:::tabs
```cpp
// Виміряти центр осі: N разів прочитати нерухому ручку й усереднити.
void calibrateCenter(Axis &a, uint8_t samples = 64) {
    long acc = 0;
    for (uint8_t i = 0; i < samples; i++) {
        acc += analogRead(a.pin);
        delay(3);                       // дати АЦП і напрузі влягтися між вимірами
    }
    a.center = acc / samples;           // справжній «нуль» саме цього екземпляра
}
```
```micropython
import time

# Виміряти центр осі: N разів прочитати нерухому ручку й усереднити.
def calibrate_center(a, samples=64):
    acc = 0
    for _ in range(samples):
        acc += a.pin.read()             # ADC.read() → сире число
        time.sleep_ms(3)                # дати АЦП і напрузі влягтися між вимірами
    a.center = acc // samples           # справжній «нуль» саме цього екземпляра
```
:::

Чому усереднення, а не одне читання? Бо АЦП на кожному вимірі додає ±кілька одиниць шуму, і якщо схопити «нуль» одним пострілом, можна невдало влучити в піковий викид — і весь подальший відлік поїде на цю похибку. Тридцять-шістдесят вимірів, усереднені, гасять шум у корінь-із-N разів: із ±4 одиниць розкиду одного відліку виходить менш ніж ±1 на усередненому. Дешево і надійно.

### Відняти центр і відкинути мертву зону

Маючи центр, віднімаємо його від поточного відліку — дістаємо **відхилення** `d`, знакове число: додатне в один бік, від'ємне в інший, нуль у спокої. Але «нуль у спокої» — це теорія; на практиці навіть після калібрування `d` дрібно скаче на ±2…5 через шум і люфт. Тому смужку навколо нуля — **мертву зону** (англ. *deadzone*) — оголошуємо суцільним нулем: усе, що ближче до центру за поріг, вважаємо спокоєм.

### Домасштабувати решту ходу й інвертувати

За межами мертвої зони лишається корисний хід — від краю мертвої зони до фізичного краю відліку. Його треба лінійно розтягнути в наш зручний діапазон −100…+100. Тонкість, яку часто ламають: масштабувати треба **від краю мертвої зони, а не від центру**. Інакше на самому виході з мертвої зони число стрибне з 0 одразу на кілька відсотків — керма смикнеться. Правильно ж, щоб на межі мертвої зони вихід був рівно 0 і далі плавно ріс.

Зберемо все в одну функцію. Вона й є серце драйвера:

:::tabs
```cpp
// Сире число осі → −100..+100 із мертвою зоною біля нуля.
int readAxis(const Axis &a) {
    int raw = analogRead(a.pin);
    int d   = raw - a.center;                  // відхилення від центру, знакове

    // 1) мертва зона: близько до центру — це строгий нуль
    if (d > -a.deadzone && d < a.deadzone) return 0;

    int out;
    if (d > 0) {
        // додатний бік: від краю мертвої зони до верхнього краю ходу
        out = map(d, a.deadzone, a.hi - a.center, 0, 100);
    } else {
        // від'ємний бік: від краю мертвої зони до нижнього краю ходу
        out = map(d, -a.deadzone, a.lo - a.center, 0, -100);
    }

    out = constrain(out, -100, 100);           // не вилазити за діапазон
    return a.invert ? -out : out;              // 3) інверсія осі, якщо треба
}
```
```micropython
# Лінійна пропорція цілими числами, як Arduino map().
def _map(v, from_lo, from_hi, to_lo, to_hi):
    return (v - from_lo) * (to_hi - to_lo) // (from_hi - from_lo) + to_lo

# Сире число осі → −100..+100 із мертвою зоною біля нуля.
def read_axis(a):
    raw = a.pin.read()                         # ADC.read() → сире число
    d = raw - a.center                         # відхилення від центру, знакове

    # 1) мертва зона: близько до центру — це строгий нуль
    if -a.deadzone < d < a.deadzone:
        return 0

    if d > 0:
        # додатний бік: від краю мертвої зони до верхнього краю ходу
        out = _map(d, a.deadzone, a.hi - a.center, 0, 100)
    else:
        # від'ємний бік: від краю мертвої зони до нижнього краю ходу
        out = _map(d, -a.deadzone, a.lo - a.center, 0, -100)

    out = max(-100, min(100, out))             # не вилазити за діапазон
    return -out if a.invert else out           # 3) інверсія осі, якщо треба
```
:::

Тут `map(value, fromLo, fromHi, toLo, toHi)` — стандартна Arduino-функція, що лінійно перекладає число з одного діапазону в інший; вона робить пропорцію, ту саму `(value − fromLo)·(toHi − toLo)/(fromHi − fromLo) + toLo`, тільки цілими числами. А `constrain` затискає результат у межі: без нього, якщо конкретний потенціометр дотягує трохи далі за розрахунковий край, вихід міг би вискочити за ±100 і зіпсувати логіку, що на нього спирається.

> 🔧 **Навіщо це.** Зверни увагу, що обидва краї ходу — `a.hi − a.center` угору й `a.lo − a.center` униз — рахуються **окремо**, а не як симетричні ±щось. Це не педантизм. Реальний потенціометр майже ніколи не дає рівно однаковий хід у обидва боки від виміряного центру: вгору може лишатися 500 одиниць, а вниз 512. Якби ми масштабували обидва боки на одне число, одна половина осі не дотягувала б до 100, а друга впиралась у стелю раніше за край — керма поводилося б асиметрично, і це відчутно рукою. Роздільний масштаб на кожен бік робить хід чесно симетричним на виході, хоч і кривим на вході.

Тепер про **обмін осей**. Інверсію ми сховали в поле `invert`, але буває, що джойстик стоїть боком, і рух «вправо» рукою крутить насправді вісь Y, а не X. Це не властивість осі — це властивість того, яку структуру ми питаємо для «горизонталі». Тому обмін робимо не в `readAxis`, а зовні, у тому, як задаємо осі. Досить завести дві іменовані ролі й прив'язати їх до потрібних структур:

:::tabs
```cpp
Axis vrx = { .pin = A0, .center = 512, .lo = 0, .hi = ADC_MAX,
             .deadzone = 24, .invert = false };
Axis vry = { .pin = A1, .center = 512, .lo = 0, .hi = ADC_MAX,
             .deadzone = 24, .invert = false };

// Логічні ролі керування. Джойстик стоїть боком? — поміняй місцями тут.
Axis &horizontal = vrx;   // якщо боком — постав vry
Axis &vertical   = vry;   // ... і сюди vrx
```
```micropython
from machine import ADC, Pin

vrx = Axis(pin=ADC(Pin(36)), center=2048, lo=0, hi=ADC_MAX, deadzone=90, invert=False)
vry = Axis(pin=ADC(Pin(39)), center=2048, lo=0, hi=ADC_MAX, deadzone=90, invert=False)

# Логічні ролі керування. Джойстик стоїть боком? — поміняй місцями тут.
horizontal = vrx          # якщо боком — постав vry
vertical   = vry          # ... і сюди vrx
```
:::

Отак усі три види «орієнтаційних» поправок — інверсія кожної осі, обмін осей, роздільний масштаб країв — лишаються даними (`invert`, яка структура куди прив'язана), а не розсипаним по коду `if`-лабіринтом. Змінив монтаж — правиш чотири рядки конфігурації, логіка керування не ворушиться.

## Рецепт 1: вести курсор чи об'єкт

Найпряміше застосування двох осей — рухати щось по екрану: пункт меню на дисплеї, приціл, точку на графіку. Ідея проста, але має один поворот, який відрізняє приємне керування від дратівливого. **Джойстик задає не позицію курсора, а його швидкість.** Нахилив трохи — курсор поповз повільно; нахилив до кінця — помчав. Відпустив — курсор стоїть там, де був. Це те саме, що важіль газу, а не кермо: важіль не каже «де бути», він каже «як швидко рухатися».

Чому саме так, а не «нахил = координата»? Бо хід джойстика короткий — пара сантиметрів, — а екран великий. Якби нахил задавав абсолютну позицію, увесь екран мусив би вміститися в ті два сантиметри ходу, і навести на дрібну ціль стало б неможливо: найменший дрож руки перестрибував би півекрана. А «нахил = швидкість» дає обидва режими одразу: ледь торкнувся — повзеш по пікселю, вихилив — летиш через увесь екран.

:::tabs
```cpp
int cursorX = 64, cursorY = 32;         // поточна позиція (напр. пікселі дисплея)

void moveCursor() {
    int vx = readAxis(horizontal);      // −100..+100
    int vy = readAxis(vertical);

    // швидкість у «пікселів за крок»: 100 на осі → 5 пікселів за виклик
    cursorX += vx / 20;
    cursorY += vy / 20;

    // не давати курсору втекти за межі екрана 128×64
    cursorX = constrain(cursorX, 0, 127);
    cursorY = constrain(cursorY,  0,  63);
}
```
```micropython
cursor_x, cursor_y = 64, 32             # поточна позиція (напр. пікселі дисплея)

def move_cursor():
    global cursor_x, cursor_y
    vx = read_axis(horizontal)          # −100..+100
    vy = read_axis(vertical)

    # швидкість у «пікселів за крок»: 100 на осі → 5 пікселів за виклик
    cursor_x += int(vx / 20)
    cursor_y += int(vy / 20)

    # не давати курсору втекти за межі екрана 128×64
    cursor_x = max(0, min(127, cursor_x))
    cursor_y = max(0, min(63,  cursor_y))
```
:::

Ділення `vx / 20` — це і є «чутливість»: більший дільник робить курсор повільнішим і точнішим, менший — швидшим і нервовішим. Оскільки `readAxis` уже віддає чесний нуль у спокої (завдяки мертвій зоні), відпущений джойстик додає рівно нуль, і курсор стоїть як укопаний — без «повзання», яким славляться наївні реалізації без калібрування.

Одна практична дрібниця: `moveCursor` треба викликати з **рівним темпом**, бо швидкість тут — це «пікселів за виклик». Якщо в одному циклі `loop()` встромити довгу затримку (перемалювати весь екран), курсор за той цикл стрибне на стільки ж, скільки за короткий, — вийде ривок. Тому або тримай цикл рівним, або, якщо хочеш строгості, рахуй швидкість «пікселів за мілісекунду» й множ на реальний час кроку.

## Рецепт 2: танкове керування двома моторами

Класика радіокерованих машинок і гусеничних роботів — **танкове керування** (англ. *tank drive*, або *differential drive*, диференціальний привід). Ідея: у робота два незалежні мотори, лівий і правий, і напрямок задається не кермом, а **різницею їхніх швидкостей**. Обидва вперед однаково — робот їде прямо. Лівий швидше за правий — робот завертає праворуч. Один вперед, другий назад — робот крутиться на місці. Жодного керма, жодних сервоприводів повороту: сама лише різниця обертів двох коліс.

Питання лише в тому, як дві осі джойстика лягають на дві швидкості. Найінтуїтивніший спосіб — **керування однією ручкою через змішування**: вісь Y (вперед-назад) задає спільний хід, вісь X (вліво-вправо) додає різницю. Змішуємо їх арифметично:

:::tabs
```cpp
// Танкове змішування: одна ручка → дві швидкості моторів (−100..+100 кожна).
struct Motors { int left, right; };

Motors tankMix() {
    int drive = readAxis(vertical);     // вперед/назад: спільна складова
    int turn  = readAxis(horizontal);   // ліворуч/праворуч: різницева складова

    int left  = drive + turn;           // праворуч → лівий мотор швидше
    int right = drive - turn;           // ... а правий повільніше

    left  = constrain(left,  -100, 100);
    right = constrain(right, -100, 100);
    return { left, right };
}
```
```micropython
# Танкове змішування: одна ручка → дві швидкості моторів (−100..+100 кожна).
def tank_mix():
    drive = read_axis(vertical)         # вперед/назад: спільна складова
    turn  = read_axis(horizontal)       # ліворуч/праворуч: різницева складова

    left  = drive + turn                # праворуч → лівий мотор швидше
    right = drive - turn                # ... а правий повільніше

    left  = max(-100, min(100, left))
    right = max(-100, min(100, right))
    return left, right
```
:::

Чому `left = drive + turn`, а не навпаки? Проведімо це руками, бо тут легко наплутати знак і потім довго дивуватися, чому робот крутить не туди. Хай `drive = 0` (стоїмо), а `turn = +100` (ручка вправо до кінця). Тоді `left = +100`, `right = −100`: ліве колесо крутиться вперед, праве назад — робот розвертається **праворуч** на місці. Саме те, що очікуєш від «ручка вправо». Якщо на твоєму залізі виходить дзеркально — не переписуй формулу, а інвертуй потрібний мотор у полі `invert` відповідної осі; логіка змішування має лишатися чистою.

Тонкий момент — **насичення на діагоналі**. Даймо повний газ уперед і повний поворот: `drive = 100`, `turn = 100`, тоді `left = 200` — а `constrain` зріже його до 100. Що це означає фізично? На повному ходу поворот стає слабшим, бо один мотор уже вперся у стелю й не може крутитися ще швидше, аби додати різницю. Для більшості машинок це прийнятно й навіть природно (на повній швидкості й справді важче завернути). Але якщо потрібен строго однаковий поворот на будь-якій швидкості, застосовують масштабоване змішування — заздалегідь тиснуть обидві складові так, щоб сума ніколи не вилазила за 100. Для більшості аматорських роботів простого змішування з `constrain` цілком досить.

> 🔧 **Навіщо це.** Число −100…+100, яке віддає `readAxis`, лягає на мотор не напряму — його ще треба перетворити на [ШІМ-сигнал](book:programming/pwm-on-mcu) і на напрямок обертання (два піни драйвера мотора: швидкість — модуляцією, напрямок — рівнем). Знак результату (`left < 0`) вмикає задній хід, модуль `abs(left)` після масштабу в 0…255 задає шпаруватість. Тобто танкове змішування дає дві знакові швидкості, а вже драйвер мотора (L298N, DRV8833 чи подібний) перетворює кожну на «крутитися туди-то з такою-то потугою». Тримай ці два шари окремо: джойстик рахує *чого хоче оператор*, драйвер мотора виконує *як саме крутити колесо*.

## Рецепт 3: вісім напрямків із двох осей

Іноді дві плавні осі — це занадто, а треба навпаки: **дискретні напрямки**, як на хрестовині старого геймпада. Вгору, вниз, вліво, вправо й чотири діагоналі — вісім команд плюс «спокій». Це зручно там, де плавність ні до чого: гортати меню, ходити персонажем по клітинках, слати команди «поверни на 45°».

Ідея переходу від осей до напрямків — розбити площину навколо центру на сектори. Але робити це через кути (арктангенс, вимірювання градусів) — і повільно на дрібному мікроконтролері, і зайво. Значно простіше й надійніше — **звести кожну вісь до трьох станів** (−1, 0, +1) з тим самим порогом мертвої зони, а тоді з двох таких «трійкових» осей скласти напрямок. Двовимірна решітка 3×3 дає рівно дев'ять клітин: центральна — спокій, чотири бічні — прямі напрямки, чотири кутові — діагоналі.

:::tabs
```cpp
enum Dir { DIR_NONE, DIR_N, DIR_NE, DIR_E, DIR_SE,
           DIR_S, DIR_SW, DIR_W, DIR_NW };

// Звести вісь до знака −1/0/+1 за порогом (частка від повного ходу).
int sign3(int v, int threshold = 40) {
    if (v >  threshold) return  1;
    if (v < -threshold) return -1;
    return 0;
}

Dir readDir() {
    int hx = sign3(readAxis(horizontal));   // −1, 0, +1  (захід … схід)
    int hy = sign3(readAxis(vertical));     // −1, 0, +1  (південь … північ)

    if (hx == 0 && hy == 0) return DIR_NONE;

    // 3×3 → напрямок; вважаємо +Y = північ (вгору), +X = схід (вправо)
    if (hy ==  1) return (hx == -1) ? DIR_NW : (hx == 1) ? DIR_NE : DIR_N;
    if (hy == -1) return (hx == -1) ? DIR_SW : (hx == 1) ? DIR_SE : DIR_S;
    return (hx == -1) ? DIR_W : DIR_E;      // hy == 0, hx ≠ 0
}
```

```micropython
DIR_S, DIR_SW, DIR_W, DIR_NW = 5, 6, 7, 8

    if v < -threshold: return -1
    return 0

def read_dir():
    hx = sign3(read_axis(horizontal))       # −1, 0, +1  (захід … схід)
    hy = sign3(read_axis(vertical))         # −1, 0, +1  (південь … північ)

    if hx == 0 and hy == 0:
        return DIR_NONE

    # 3×3 → напрямок; вважаємо +Y = північ (вгору), +X = схід (вправо)
    if hy ==  1:
        return DIR_NW if hx == -1 else DIR_NE if hx == 1 else DIR_N
    if hy == -1:
        return DIR_SW if hx == -1 else DIR_SE if hx == 1 else DIR_S
    return DIR_W if hx == -1 else DIR_E     # hy == 0, hx ≠ 0
```
:::

Поріг `threshold = 40` тут важливіший, ніж здається, і задає **розмір «мертвого хреста»** між напрямками. Візьми його замалим — і напрямки перемикатимуться від найменшого дотику, а на межі секторів команда тремтітиме між, скажімо, «північ» і «північний схід». Візьми завеликим — і доведеться хилити ручку майже до упору, щоб узагалі спрацювало. Сорок відсотків повного ходу — розумний початок: спокійна зона широка, а до країв усе однозначно.

Тонкість, спільна з кнопкою: `readDir` віддає напрямок **щомиті, поки ручка нахилена**. Якщо тобі треба «один нахил — один крок меню», а не «поки тримаю — меню летить», лови саме *зміну* напрямку — так само, як ловитимемо натиск кнопки в наступному рецепті. Порівнюй поточний `readDir()` із попереднім і дій лише коли він змінився з `DIR_NONE` на щось або з одного напрямку на інший.

## Рецепт 4: чистий натиск кнопки SW із гасінням брязкоту

Кнопка SW ставить перед прошивкою дві окремі задачі, і плутати їх не варто. Перша — **прочитати її взагалі**, попри те, що на модулі [немає підтяжки](book:electronics/floating-pullups) і в спокої пін висить у повітрі. Це лікується оголошенням входу `INPUT_PULLUP`: вбудований у мікроконтролер різистор сам тримає пін у стані «1», поки кнопку не натиснуто, а натиск садить його на землю в «0». Звідси перше правило коду кнопки: **натиск — це `LOW`, а не `HIGH`** (підтяжка все інвертує).

Друга задача тонша — зловити **один** натиск як одну подію. Механічний контакт при замиканні не стуляється чисто: пружні пластини всередині кнопки кілька мілісекунд деренчать, даючи чергу швидких «0↔1» замість одного переходу. Це [брязкіт контактів](book:electronics/contact-debounce). Для «поки тримаю — стріляю» він байдужий: ну поблимало на початку, потім рівний нуль. Але щойно треба порахувати кліки або перемкнути режим по натиску — один фізичний тик обертається на три-п'ять спрацювань, і лічильник біжить, а режим блимає.

Ідея гасіння (англ. *debounce*) проста: **не вір миттєвому рівню — вір рівню, що протримався сталим досить довго**. Запам'ятовуємо, коли рівень востаннє змінився; приймаємо нове значення лише коли після зміни минуло, скажімо, 25 мс без нових коливань. Деренчання коротше за це вікно — тож воно тоне, а справжній натиск (який триває сотні мілісекунд) проходить.

Загорнемо кнопку в маленьку структуру, як робили з віссю, і винесемо з неї дві корисні події: `pressed` (рівно один імпульс у мить натискання) і `held` (рівний рівень «тримають зараз»). Саме `pressed` — те, що потрібне для лічби кліків і перемикання режимів.

:::tabs
```cpp
struct Button {
    uint8_t  pin;
    bool     stable;        // останній сталий (гашений) рівень: true = відпущено
    bool     lastRead;      // останній миттєвий відлік — для лічби вікна
    uint32_t lastChange;    // коли миттєвий рівень востаннє змінився, мс
    bool     pressedEvent;  // виставляється на один цикл у мить натиску
};

const uint32_t DEBOUNCE_MS = 25;

void buttonSetup(Button &b, uint8_t pin) {
    b.pin = pin;
    pinMode(pin, INPUT_PULLUP);         // на модулі підтяжки немає!
    b.stable = b.lastRead = true;       // спокій = HIGH (відпущено)
    b.lastChange = millis();
    b.pressedEvent = false;
}

// Викликати щоцикл. Оновлює стан; pressedEvent — один імпульс на натиск.
void buttonUpdate(Button &b) {
    b.pressedEvent = false;
    bool now = digitalRead(b.pin);      // HIGH = відпущено, LOW = натиснуто

    if (now != b.lastRead) {            // рівень смикнувся — перезапустити вікно
        b.lastChange = millis();
        b.lastRead   = now;
    }

    // рівень протримався сталим досить довго — приймаємо його
    if (millis() - b.lastChange >= DEBOUNCE_MS && now != b.stable) {
        b.stable = now;
        if (b.stable == LOW)            // перехід HIGH→LOW = справжній натиск
            b.pressedEvent = true;
    }
}

bool buttonPressed(Button &b) { return b.pressedEvent; }         // один імпульс
bool buttonHeld(Button &b)    { return b.stable == LOW; }        // тримають зараз
```
```micropython
import time
from machine import Pin

DEBOUNCE_MS = 25

class Button:
    def __init__(self, pin_num):
        self.pin = Pin(pin_num, Pin.IN, Pin.PULL_UP)  # на модулі підтяжки немає!
        self.stable = True                   # спокій = HIGH (відпущено)
        self.last_read = True                # останній миттєвий відлік
        self.last_change = time.ticks_ms()   # коли рівень востаннє змінився, мс
        self.pressed_event = False           # один імпульс у мить натиску

    # Викликати щоцикл. Оновлює стан; pressed_event — один імпульс на натиск.
    def update(self):
        self.pressed_event = False
        now = bool(self.pin.value())         # 1 = відпущено, 0 = натиснуто

        if now != self.last_read:            # рівень смикнувся — перезапустити вікно
            self.last_change = time.ticks_ms()
            self.last_read = now

        # рівень протримався сталим досить довго — приймаємо його
        if time.ticks_diff(time.ticks_ms(), self.last_change) >= DEBOUNCE_MS \
                and now != self.stable:
            self.stable = now
            if not self.stable:              # перехід HIGH→LOW = справжній натиск
                self.pressed_event = True

    def pressed(self):  return self.pressed_event   # один імпульс
    def held(self):     return not self.stable      # тримають зараз
```
:::

Прочитаймо логіку, бо вона хитріша за вигляд. Змінна `lastRead` стежить за **миттєвим** рівнем: щойно він відрізнився від попереднього — ми не робимо нічого, крім як заводимо годинник `lastChange` наново. Поки контакт деренчить, цей годинник раз у раз скидається й ніколи не встигає добігти до 25 мс — тож `stable` не рухається, брязкіт мовчить. Аж коли рівень нарешті вгамувався й протримався 25 мс без смикань, ми приймаємо його в `stable`; і саме в мить, коли `stable` уперше стало `LOW`, виставляємо `pressedEvent` на один цикл. Наступний виклик його погасить. Отак із брудної черги імпульсів народжується рівно одна чиста подія «натиснуто».

> 🔧 **Навіщо це.** Це гасіння **без жодної затримки** — воно не спиняє програму на 25 мс, лише дивиться на годинник `millis()`. Різниця критична для джойстика: поки кнопка гаситься, осі мусять читатися далі й керма не має завмирати. Якби ми гасили брязкіт через `delay(25)`, увесь робот на ці 25 мс глух і сліпий — мотори крутяться наосліп, курсор застигає. Тому в живому коді керування гасіння завжди неблокуюче: запам'ятав час, порівняв, поїхав далі. Той самий підхід «дивись на годинник, не спи» лежить в основі будь-якої відзивчивої прошивки — і кнопки, і мигалки, і опитування давачів.

## Повний скетч під Arduino (10-бітний АЦП)

Складімо драйвер і всі рецепти в один робочий скетч під Arduino Uno чи Nano. Осі на A0/A1, кнопка на D2. Скетч показує все відразу: калібрує центр на старті, читає обидві осі в −100…+100, рахує танкове змішування й ловить чисті натиски кнопки, друкуючи їх у монітор порту.

```cpp
// ── KY-023 повний драйвер — Arduino Uno/Nano (10-бітний АЦП, 0..1023) ──
const int ADC_MAX = 1023;               // 10 біт

struct Axis {
    uint8_t pin; int center, lo, hi, deadzone; bool invert;
};
Axis vrx = { A0, 512, 0, ADC_MAX, 24, false };
Axis vry = { A1, 512, 0, ADC_MAX, 24, false };
Axis &horizontal = vrx;
Axis &vertical   = vry;

void calibrateCenter(Axis &a, uint8_t samples = 64) {
    long acc = 0;
    for (uint8_t i = 0; i < samples; i++) { acc += analogRead(a.pin); delay(3); }
    a.center = acc / samples;
}

int readAxis(const Axis &a) {
    int d = analogRead(a.pin) - a.center;
    if (d > -a.deadzone && d < a.deadzone) return 0;
    int out = (d > 0) ? map(d, a.deadzone, a.hi - a.center, 0,  100)
                      : map(d, -a.deadzone, a.lo - a.center, 0, -100);
    out = constrain(out, -100, 100);
    return a.invert ? -out : out;
}

// ── кнопка з неблокуючим гасінням ──
struct Button { uint8_t pin; bool stable, lastRead; uint32_t lastChange; bool ev; };
const uint32_t DEBOUNCE_MS = 25;
Button sw;

void buttonSetup(Button &b, uint8_t pin) {
    b.pin = pin; pinMode(pin, INPUT_PULLUP);
    b.stable = b.lastRead = true; b.lastChange = millis(); b.ev = false;
}
void buttonUpdate(Button &b) {
    b.ev = false;
    bool now = digitalRead(b.pin);
    if (now != b.lastRead) { b.lastChange = millis(); b.lastRead = now; }
    if (millis() - b.lastChange >= DEBOUNCE_MS && now != b.stable) {
        b.stable = now;
        if (b.stable == LOW) b.ev = true;
    }
}

long clicks = 0;

void setup() {
    Serial.begin(9600);
    calibrateCenter(vrx);               // ручку НЕ чіпати під час старту!
    calibrateCenter(vry);
    buttonSetup(sw, 2);
    Serial.print("Центр: X="); Serial.print(vrx.center);
    Serial.print(" Y=");       Serial.println(vry.center);
}

void loop() {
    buttonUpdate(sw);
    if (sw.ev) { clicks++; Serial.print("клік #"); Serial.println(clicks); }

    int vx = readAxis(horizontal);
    int vy = readAxis(vertical);

    // танкове змішування — приклад використання осей
    int left  = constrain(vy + vx, -100, 100);
    int right = constrain(vy - vx, -100, 100);

    Serial.print("X="); Serial.print(vx);
    Serial.print(" Y="); Serial.print(vy);
    Serial.print("  L="); Serial.print(left);
    Serial.print(" R=");  Serial.print(right);
    Serial.print(sw.stable == LOW ? "  [тримають]" : "");
    Serial.println();
    delay(30);                          // рівний темп циклу
}
```

Залий, відкрий монітор порту на 9600 — і в рядку побачиш обидві осі коло нуля в спокої, змішані швидкості моторів і лічильник кліків, що росте рівно на одиницю за натиск, попри брязкіт. Одне залізне правило старту: **під час `setup()` ручку не чіпай**, бо саме тоді міряється центр; торкнешся — «нуль» поповзе, і в роботі відпущений джойстик даватиме ненульове число.

## Повний скетч під ESP32 (12-бітний АЦП): що змінюється

На ESP32 логіка драйвера — та сама, майже дослівно. Змінюються три речі, і кожна варта уваги, бо на ній легко спіткнутися.

**Перше — розмах АЦП.** ESP32 має 12-бітний АЦП, тож `analogRead` віддає 0…4095, а не 0…1023, і центр у спокої — коло **2048**, а не 512. Достатньо однієї константи: `const int ADC_MAX = 4095;`. Уся решта коду осі спирається на `ADC_MAX` і `a.center`, тож більше нічого правити не треба — саме заради цього ми й винесли межу в константу.

**Друге, і найважливіше, — живлення й напруга осей.** ESP32 — [3.3-вольтова плата](book:electronics/logic-levels-as-ranges), і його аналогові входи не терплять на собі 5 В. А розмах напруги на осях KY-023 [дорівнює напрузі живлення](book:electronics/potentiometer): нагодуєш модуль п'ятьма вольтами — у крайніх положеннях ручки на VRx/VRy буде 5 В, і ти подаси 5 В на ногу, розраховану на 3.3. Наслідок — зіпсоване число (АЦП упреться в стелю задовго до краю ходу) у кращому разі й ушкоджений вхід у гіршому. **Живи KY-023 від піна 3V3 ESP32, а не від 5V.** Тоді осі гуляють у безпечних 0…3.3 В, і весь 12-бітний діапазон використовується чесно.

**Третє — який пін вибрати під вісь.** Тут ховається пастка, якої на Arduino не буває зовсім. У ESP32 два аналого-цифрові блоки, ADC1 і ADC2, і **ADC2 конфліктує з Wi-Fi**: щойно радіо ввімкнене, входи ADC2 віддають випадкове сміття замість напруги. Перевірено за документацією Espressif і трекером Arduino-ESP32: піни ADC2 не можна читати як аналогові, поки працює Wi-Fi. Тому осі джойстика вішай на входи **ADC1** — це GPIO 32, 33, 34, 35, 36, 37, 38, 39. Якщо радіо тобі не потрібне, ADC2 теж спрацює; але поставити осі на ADC1 нічого не коштує й одразу знімає цілий клас загадкових «джойстик дуріє, відколи ввімкнув Wi-Fi».

```cpp
// ── KY-023 під ESP32 (12-бітний АЦП, 0..4095) — відмінності від Arduino ──
const int ADC_MAX = 4095;               // 12 біт: центр у спокої ≈ 2048

// Осі — на входах ADC1 (безпечні з Wi-Fi). Живлення модуля — 3V3, НЕ 5V!
Axis vrx = { 34, 2048, 0, ADC_MAX, 90, false };   // GPIO34 = ADC1
Axis vry = { 35, 2048, 0, ADC_MAX, 90, false };   // GPIO35 = ADC1
Axis &horizontal = vrx;
Axis &vertical   = vry;
// кнопку — на будь-який звичайний GPIO зі входом і підтяжкою, напр. GPIO25
// (GPIO34/35/36/39 — «тільки вхід» і БЕЗ внутрішньої підтяжки, для кнопки не годяться!)
```

Дві дрібніші, але дошкульні відмінності на закуску. **Мертву зону масштабуй разом із розмахом**: 24 одиниці на 10-бітній Arduino — це той самий поріг, що ≈90 на 12-бітному ESP32 (розмах учетверо ширший, тож і смужка вчетверо ширша в одиницях). Візьмеш ту саму цифру 24 на ESP32 — мертва зона вийде вчетверо вужчою, і біля центру знову з'явиться дрож. І про **піни кнопки**: частина ніжок ESP32 (GPIO 34, 35, 36, 39) — «тільки вхід» і не мають внутрішньої підтяжки взагалі, тож `INPUT_PULLUP` на них нічого не тримає, і гола кнопка SW знову висітиме. Вішай кнопку на пін зі справжньою підтяжкою (майже будь-який інший GPIO), а «тільки-вхідні» бережи для осей, яким підтяжка ні до чого.

> 🔧 **Навіщо це.** ESP32-шний АЦП має ще й окрему тиху ваду, про яку варто знати наперед: він **нелінійний** біля країв діапазону, надто у стандартному режимі послаблення на повні 3.3 В — «12 біт» на практиці ближчі до 9–10 корисних. Для джойстика це майже байдуже, бо ми не міряємо точну напругу, а лише напрямок і грубу величину нахилу, та й мертва зона з калібруванням центру ховають дрібну кривизну. Але саме тому не варто будувати на осях KY-023 щось, що вимагає лінійного вимірювання (наприклад, точний кутовий давач) — джойстик для цього й не призначений, а АЦП ESP32 тим паче. Керма — так; метрологія — ні.

## Складність і пастки

Драйвер джойстика оманливо простий: чотири арифметичні дії на вісь плюс кнопка з таймером. Уся складність не в математиці, а в тому, що фізичний бік раз у раз порушує тихі припущення коду. Зберемо ці пастки в одне місце — кожну з причиною й лаконічним ліком, бо саме на них іде більшість згаяного часу.

- **Плаваючий SW → кнопка «спрацьовує сама».** На модулі немає підтяжки; у спокої пін ловить наводки. Лік: `INPUT_PULLUP`, натиск читай як `LOW`. На «тільки-вхідних» пінах ESP32 (34/35/36/39) внутрішньої підтяжки немає — кнопку туди не вішай.
- **Центр не 512 (не 2048) → відпущений джойстик «повзе».** Кожен екземпляр має свій нуль. Лік: `calibrateCenter` на старті, і ручку під час старту не чіпати.
- **Шум біля центру → курсор/кермо дрижить у спокої.** АЦП і люфт ручки дають ±кілька одиниць. Лік: мертва зона; і не забудь **масштабувати її поріг** під розмах АЦП (≈×4 з 10 на 12 біт).
- **Розмах = живлення → 5 В на 3.3-вольтовий вхід.** На ESP32 подати 5 В на осі — зіпсувати число й ушкодити ногу. Лік: живи модуль напругою логіки плати (ESP32 — від 3V3).
- **Плутанина 10/12 біт → математика осі повзе на чужій платі.** Скетч під 1023, залитий на ESP32, мовчки бреше. Лік: `ADC_MAX` через `#if defined(ESP32)`, а не магічне число.
- **ADC2 + Wi-Fi → осі віддають сміття, щойно вмикається радіо.** Лік: осі на входи ADC1 (GPIO 32–39).
- **Брязкіт кнопки → один натиск рахується як кілька.** Механічний контакт деренчить. Лік: неблокуюче гасіння (сталий рівень ≥ 25 мс), і **ніколи через `delay`** — керма не має глухнути.
- **Орієнтація монтажу → джойстик «їде не туди», осі переплутані.** Це не поломка, а геометрія. Лік: інвертуй потрібну вісь полем `invert` і, якщо стоїть боком, поміняй прив'язку `horizontal`/`vertical` — не переписуючи логіку рецептів.
- **Масштаб від центру, а не від краю мертвої зони → ривок на виході з мертвої зони.** Число стрибає з 0 одразу на кілька відсотків. Лік: масштабуй саме від краю мертвої зони, щоб на її межі вихід був рівно 0.

Красива думка на прощання: усі ці пастки, крім орієнтації, — це наслідок того, що KY-023 усередині гранично простий, [дві крутилки й контакт](book:electronics/voltage-divider), без жодної мікросхеми, яка згладила б за нас центр, шум чи розмах. Дорожчі джойстики з вбудованим контролером віддають уже готове каліброване число по цифровій шині — але й коштують інше, і не навчають нічого. KY-023 натомість чесно кладе всю чорнову роботу на прошивку — і саме тому на ньому так добре видно, з чого взагалі складається «прочитати аналоговий орган керування»: виміряти свій нуль, відкинути тремтіння, домасштабувати під задачу, підтягнути й погасити кнопку. Раз написавши цей драйвер, ти пишеш його для будь-якого потенціометра-осі на світі — бо всередині вони всі одна порода.
