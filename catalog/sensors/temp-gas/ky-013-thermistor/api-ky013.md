# ⚙️ KY-013 у прошивці: від сирого відліку АЦП до чесних градусів

Задача звучить наївно: «прочитати температуру з KY-013». Але між пласким `analogRead` і числом, яке не соромно показати людині, лежить чотири окремі кроки, і на кожному є місце спіткнутися. Треба перевести відлік АЦП у напругу, напругу — в опір термістора через рівняння дільника, опір — у градуси через формулу термістора, а тоді ще й приборкати шум і не спалити вхід. Тут я проведу цей шлях до кінця робочим кодом прошивки — так, щоб скетч можна було залити й дивитися на градуси, а не переписувати його по чужих форумах.

Скетчі нижче — справжній C++ під Arduino/ESP32, той, що компілюється й крутиться на залізі. Формула термістора (B-параметр і Стейнгарт–Гарт) виводиться від першопричини в статті про [NTC-термістор](book:electronics/ntc-thermistor); саме рівняння дільника — у статті про [дільник напруги](book:electronics/voltage-divider); що АЦП узагалі робить із напругою — у статті про [АЦП](book:electronics/adc). Я на них спираюся, а не переказую: тут увага на код і на пастки саме цифрового читання.

## Ідея: чотири перетворення, кожне зі своєю пасткою

Перш ніж писати, варто побачити весь конвеєр цілком — тоді кожен рядок коду стане на своє місце, а не з'явиться «бо так у прикладі».

```
крок 1:  analogRead  →  raw   (ціле 0..1023 або 0..4095)
крок 2:  raw         →  ratio = U_S / Vcc        (частка шкали, 0..1)
крок 3:  ratio       →  R_ntc  (опір термістора через рівняння дільника)
крок 4:  R_ntc       →  T °C   (через B-формулу або таблицю)
```

Дві тонкощі ховаються між кроками, і саме вони псують чужі скетчі. Перша: **крок 3 залежить від того, у якому плечі стоїть термістор** — угорі (між + і S) чи внизу (між S і −). Партії KY-013 розводять дільник по-різному, і формула опору в цих випадках обернена одна до одної. Друга: **крок 2 працює лише тоді, коли опорна напруга АЦП дорівнює живленню дільника** — інакше `Vcc` не скорочується і у формулу лізе абсолютний вольтаж, який ще й гуляє. Обидві тонкощі ми закриємо кодом явно, а не «на щастя».

Ще один наскрізний зиск від того, що весь конвеєр — це відношення. Придивись: на кроці 2 ми ділимо `raw` на повну шкалу, на кроці 3 у формулі стоїть `1/ratio − 1`. Живлення `Vcc` у цьому ланцюгу **ніде не фігурує як число** — воно скорочується само, бо і напруга на S, і опорна АЦП пропорційні тому самому `Vcc`. Це і є та сама ratiometric-магія: поки одне джерело живить і дільник, і АЦП, точне значення вольтажу нам байдуже. Тому в жодному зі скетчів нижче ти не побачиш рядка на кшталт `voltage = raw * 5.0 / 1023` — він зайвий і лише впустив би у формулу число, яке дрейфує.

> 🔧 **Навіщо це.** Тримай ці чотири кроки в голові як каркас. Коли термометр «бреше», ти не тикаєшся навмання, а питаєш по черзі: сирий `raw` узагалі ворушиться від тепла? (крок 1–2) у правильний бік? (плече, крок 3) опір виходить схожий на кілоомний? (крок 3) градуси близькі до кімнатних? (крок 4). Майже завжди помилка — на кроці 3, у плечі дільника.

## Мінімальний робочий скетч: B-параметр, термістор угорі

Почнімо з найпоширенішої плати — тієї, де термістор у верхньому плечі, тож нагрів **піднімає** напругу на S. Це той самий каркас, що в базовій статті, але тут я доведу його до придатного до життя стану: винесу перетворення у функцію, дам іменовані сталі й поясню кожен підводний рядок.

**Умова.** KY-013 сигналом S на A0 Arduino Uno. АЦП 10-бітний (0…1023), живлення й опорна — спільні 5 В (ratiometric виходить сам собою). Термістор 10 кОм / B = 3950, сталий резистор 10 кОм. Термістор у **верхньому** плечі.

```cpp
#include <math.h>

const uint8_t  PIN_NTC  = A0;        // сигнал S давача
const uint16_t ADC_MAX  = 1023;      // 10-біт АЦП: повна шкала (2^10 − 1)
const float    R_FIXED  = 10000.0f;  // сталий резистор на модулі, Ом
const float    R25      = 10000.0f;  // опір термістора за 25 °C, Ом
const float    BETA     = 3950.0f;   // B-параметр термістора, K
const float    T25_K    = 298.15f;   // 25 °C у кельвінах (25 + 273.15)

void setup() {
  Serial.begin(9600);                // пін аналоговий → pinMode НЕ потрібен
}

// відлік АЦП → опір термістора (термістор у ВЕРХНЬОМУ плечі)
float rawToResistance(uint16_t raw) {
  float ratio = (float)raw / ADC_MAX;             // U_S / Vcc, у межах 0..1
  // U_S/Vcc = R_fixed / (R_ntc + R_fixed)
  //        →  R_ntc = R_fixed * (1/ratio − 1)
  return R_FIXED * (1.0f / ratio - 1.0f);
}

// опір термістора → температура, °C (B-параметр)
float resistanceToTempC(float r_ntc) {
  // 1/T = 1/T25 + (1/B)·ln(R/R25)
  float invT = 1.0f / T25_K + logf(r_ntc / R25) / BETA;
  return 1.0f / invT - 273.15f;                   // K → °C
}

void loop() {
  uint16_t raw   = analogRead(PIN_NTC);
  float    r     = rawToResistance(raw);
  float    tempC = resistanceToTempC(r);

  Serial.print(tempC, 1);
  Serial.println(" C");
  delay(500);
}
```

Кілька рядків заслуговують уваги, бо на них ламаються.

Приведення `(float)raw / ADC_MAX` — не косметика. Якщо забути `(float)` і написати `raw / ADC_MAX` цілими, C поділить два `uint16_t` **націло**: при `raw < 1023` вийде рівно `0`, і далі `1/0` дасть нескінченність, а температура — сміття (`nan`). Це класична пастка новачка в C: «формула правильна, а число безглузде». Одне приведення до `float` на самому вході рятує весь ланцюг.

`logf`, а не `log`. На 8-бітному AVR обидві існують, але `log` — це `double`, а `double` на Arduino Uno **той самий** `float` (double там 32-бітний), тож `logf` нічого не гірше й чесніше показує намір. На ESP32, де `double` справді 64-бітний, `logf` ще й помітно швидший. Дрібниця, але безкоштовна.

Порядок аргументів у `logf(r_ntc / R25)`. Легко переплутати й написати `R25 / r_ntc` — і тоді знак усього виправлення перевернеться: тепле стане холодним. Запам'ятовувати не треба, треба **вивести**: коли термістор гарячий, його `r_ntc < R25`, відношення `r_ntc/R25 < 1`, логарифм від'ємний, він **зменшує** `1/T`, тобто **збільшує** T — усе сходиться. Якщо переплутати, температура поповзе не туди, і це відразу видно на моніторі.

> 🔧 **Навіщо це.** Винесення двох перетворень в окремі функції `rawToResistance` і `resistanceToTempC` — не заради краси. Саме `rawToResistance` — це той єдиний шматок, що залежить від плеча дільника й від конкретної плати. Тримаючи його окремо, ти правиш KY-013 під свою партію в **одному** місці, не чіпаючи решту, і легко підставляєш таблицю замість формули (нижче). Друга функція — суто фізика термістора — не змінюється ніколи.

## Друга орієнтація: термістор унизу — обертається один рядок

Тепер найважливіша для KY-013 варіація. Візьмеш плату іншої партії, де термістор у **нижньому** плечі (між S і −), — і нагрів тепер **опускає** напругу на S. Рівняння дільника обертається, і у формулі опору міняється **рівно один рядок**. Ось нова версія `rawToResistance`; уся решта скетча — байт у байт та сама:

```cpp
// відлік АЦП → опір термістора (термістор у НИЖНЬОМУ плечі)
float rawToResistance(uint16_t raw) {
  float ratio = (float)raw / ADC_MAX;             // U_S / Vcc
  // U_S/Vcc = R_ntc / (R_ntc + R_fixed)
  //        →  R_ntc = R_fixed * ratio / (1 − ratio)
  return R_FIXED * ratio / (1.0f - ratio);
}
```

Порівняй дві формули поряд — вони дзеркальні:

```
термістор УГОРІ  (між + і S):   R_ntc = R_fixed · (1/ratio − 1)
термістор УНИЗУ  (між S і −):   R_ntc = R_fixed · ratio / (1 − ratio)
```

Як **не гадати**, а точно знати, який рядок твій, — це той самий дослід із базової статті, тільки тепер він каже конкретну річ про код. Залий на хвилину сирий вивід і затисни намистинку пальцями:

```cpp
void loop() {
  Serial.println(analogRead(PIN_NTC));   // просто сире число
  delay(200);
}
```

Дивишся на монітор і грієш термістор рукою. Число **росте** від тепла → термістор угорі → бери формулу `(1/ratio − 1)`. Число **падає** → термістор унизу → бери `ratio/(1 − ratio)`. Одна ця хвилина економить годину блукань, бо жоден даташит не скаже, яку саме партію тобі поклали в пакет.

> 🔧 **Навіщо це.** Ось чому в конвеєрі саме крок 3 — головне джерело брехні. Візьмеш чужий скетч під протилежну орієнтацію — і код скомпілюється, `raw` ворушитиметься, опір рахуватиметься… але в неправильний бік, і термометр покаже дзеркальну маячню (гарячіше → «холодніше»). Компілятор тут безпорадний: обидві формули синтаксично бездоганні. Ловить помилку лише фізика — знак реакції на тепло руки.

## Усереднення: приборкати шум за майже нуль коштів

Один `analogRead` завжди трохи тремтить — молодші біти АЦП стрибають від наведень, від пульсацій живлення, від самого квантування. На градуснику це видно як останню цифру, що не стоїть на місці. Дешевий і чесний спосіб її заспокоїти — **усереднити кілька відліків**. Шум випадковий у обидва боки, тож середнє з N вимірів має приблизно в √N разів менший розкид: 16 відліків — учетверо спокійніше число.

Важлива тонкість **де** усереднювати: у сирих відліках АЦП, до всякої нелінійної формули. Якщо спершу порахувати температуру з кожного шумного відліку, а тоді усереднити температури, логарифм устигне спотворити симетрію шуму, і середнє трохи зміститься. Усереднюй `raw` — воно лінійне, і середнє чесне.

```cpp
// середній сирий відлік із N вимірів (шум давиться як √N)
uint16_t readRawAveraged(uint8_t samples = 16) {
  uint32_t acc = 0;                       // 32 біти: 16×1023 не переповнить
  for (uint8_t i = 0; i < samples; i++) {
    acc += analogRead(PIN_NTC);
    delayMicroseconds(200);               // дати входу АЦП «устоятися»
  }
  return (uint16_t)(acc / samples);
}
```

Три деталі, які роблять цю функцію правильною, а не просто «циклом навколо analogRead».

Акумулятор `uint32_t`, а не `uint16_t`. Сума шістнадцяти відліків по 1023 — це до 16368, що ще влізло б у 16 біт; але на ESP32 із 12-бітним АЦП (до 4095) і 64 відліками сума сягне 262080 — за межу `uint16_t` (65535). `uint32_t` знімає це питання назавжди, а коштує чотири байти. Не економ на розрядності акумулятора — це та економія, що виходить боком мовчазним переповненням.

`delayMicroseconds(200)` між відліками. Вхід АЦП — це конденсатор, який заряджається через опір джерела; якщо смикати `analogRead` впритул, сусідні виміри «злипаються» (ефект зветься crosstalk на мультиплексорі АЦП). Двісті мікросекунд дають входу устоятися між пробами, і виміри стають незалежними — саме тоді усереднення й працює як обіцяно. Для дільника з кілоомними опорами цього з запасом.

Параметр за замовчуванням `samples = 16` — розумний компроміс. Мало (4) — ще тремтить; багато (256) — повільно й уже без користі, бо в справу вступають систематичні похибки, які усередненням не прибрати. Для кімнатного термометра 16–32 — золота середина.

Тепер `loop` викликає усереднений відлік замість голого:

```cpp
void loop() {
  uint16_t raw   = readRawAveraged(16);
  float    tempC = resistanceToTempC(rawToResistance(raw));
  Serial.print(tempC, 1);
  Serial.println(" C");
  delay(500);
}
```

> 🔧 **Навіщо це.** Усереднення — найдешевше поліпшення точності на весь скетч: кілька рядків, і остання цифра перестає танцювати. Але воно давить лише **випадковий** шум; систематичну похибку (розкид сталого резистора, неточні R₂₅/B, зсув АЦП) воно не чіпає — з нею бореться калібрування, про яке нижче. Плутати ці дві речі — типова помилка: людина усереднює 500 відліків і дивується, чому термометр усе одно стабільно бреше на два градуси.

## Без log() зовсім: таблиця й лінійна інтерполяція

Формула з `logf` гарна, але на маленькому 8-бітному мікроконтролері вона недешева. ATmega328P (серце Arduino Uno) **не має апаратного блока з рухомою комою** — усі операції з `float`, а надто `logf`, виконуються програмно, десятками-сотнями тактів на дію, і тягнуть у прошивку майже два кілобайти бібліотечного коду (усталений факт: додавання найпростішої `float`-арифметики роздуває бінарник на ~1900 байтів). Коли пам'яті обмаль, коли треба міряти часто, або коли просто немає бажання тягати всю бібліотеку `math` — температуру дістають **таблицею**.

Ідея пряма. Заздалегідь, на комп'ютері, рахуємо: для кількох опорних відліків АЦП — яка це температура. Кладемо ці пари у масив у flash. У прошивці для живого відліку знаходимо два сусідні рядки таблиці, між якими він лежить, і **лінійно інтерполюємо** — проводимо пряму між їхніми температурами й беремо точку на ній. Жодного логарифма в реальному часі: увесь `logf` уже «згорів» на етапі підготовки таблиці.

![Таблиця відлік→°C у flash: живий відлік лежить між двома рядками, температуру беремо з прямої, проведеної між їхніми градусами — лінійна інтерполяція без логарифма](/catalog/sensors/temp-gas/ky-013-thermistor/img/ky013-lut-interp.svg)

*Живий відлік (тут 517) не збігається з жодним рядком таблиці, а лежить між рядками 548→25° і 486→30°. Замість формули проводимо між цими двома точками пряму й беремо на ній значення для 517 — виходить ~27.5°. Таблиця мала (десяток-другий рядків), крок між точками невеликий, тож пряма-хорда майже збігається зі справжньою кривою, а вся арифметика — лише додавання, віднімання й одне ділення в цілих числах.*

Спершу — як **зробити таблицю**. Це разовий скрипт (тут на C для наочності, але зазвичай його ганяють раз на комп'ютері й вставляють готовий масив у скетч). Для обраної орієнтації дільника беремо ряд температур із зручним кроком, для кожної рахуємо опір термістора, тоді відлік АЦП, який цьому опору відповідає:

```cpp
// РАЗОВО на комп'ютері: надрукувати рядки таблиці для вставки у скетч.
// Термістор УНИЗУ; крок 5 °C від −10 до +45.
#include <stdio.h>
#include <math.h>
int main() {
  const double R_FIXED = 10000, R25 = 10000, BETA = 3950, T25 = 298.15;
  const double ADC_MAX = 1023;
  for (int tC = -10; tC <= 45; tC += 5) {
    double T   = tC + 273.15;
    // T → опір термістора (обернена B-формула)
    double R   = R25 * exp(BETA * (1.0/T - 1.0/T25));
    // опір → відлік (термістор унизу): ratio = R/(R+R_fixed)
    double adc = ADC_MAX * (R / (R + R_FIXED));
    printf("  {%4d, %3d},\n", (int)(adc + 0.5), tC * 10);  // t×10 → десяті
  }
  return 0;
}
```

Вивід цього скрипта — готові рядки, які просто вставляють у скетч. А ось сам **скетч із таблицею й інтерполяцією**, той, що вже крутиться на мікроконтролері й не тягне ні `logf`, ні `float` узагалі:

```cpp
#include <avr/pgmspace.h>       // тримати таблицю у flash, не в дефіцитній RAM

const uint8_t  PIN_NTC = A0;

// Таблиця «відлік АЦП → температура×10 (десяті °C)», відліки СПАДАЮТЬ
// з нагрівом. °C×10, щоб не втратити десяті на цілій арифметиці.
// Термістор УНИЗУ (між S і −): гарячіше → напруга на S нижча → відлік менший.
struct Point { int16_t adc; int16_t t10; };
const Point TABLE[] PROGMEM = {
  {873, -100}, {834,  -50}, {788,    0}, {738,   50},
  {684,  100}, {627,  150}, {569,  200}, {512,  250},
  {456,  300}, {403,  350}, {354,  400}, {310,  450},
};
const uint8_t N = sizeof(TABLE) / sizeof(TABLE[0]);

void setup() { Serial.begin(9600); }

// відлік → температура×10, лінійна інтерполяція по таблиці (без float!)
int16_t lookupT10(int16_t raw) {
  int16_t a0 = pgm_read_word(&TABLE[0].adc);
  int16_t aN = pgm_read_word(&TABLE[N - 1].adc);
  if (raw >= a0) return pgm_read_word(&TABLE[0].t10);        // за краєм — обрізаємо
  if (raw <= aN) return pgm_read_word(&TABLE[N - 1].t10);

  // знайти сегмент [i, i+1], де adc спадає від >raw до <=raw
  for (uint8_t i = 0; i < N - 1; i++) {
    int16_t aHi = pgm_read_word(&TABLE[i].adc);       // більший відлік
    int16_t aLo = pgm_read_word(&TABLE[i + 1].adc);   // менший відлік
    if (raw <= aHi && raw >= aLo) {
      int16_t tHi = pgm_read_word(&TABLE[i].t10);
      int16_t tLo = pgm_read_word(&TABLE[i + 1].t10);
      // лінійна інтерполяція, уся арифметика ціла (32 біти проти переповнення):
      // t = tHi + (tLo − tHi)·(aHi − raw)/(aHi − aLo)
      int32_t num = (int32_t)(tLo - tHi) * (aHi - raw);
      return tHi + (int16_t)(num / (aHi - aLo));
    }
  }
  return pgm_read_word(&TABLE[N - 1].t10);            // сюди не дійде, для повноти
}

void loop() {
  int16_t raw = analogRead(PIN_NTC);
  int16_t t10 = lookupT10(raw);
  Serial.print(t10 / 10);       // ціла частина градусів
  Serial.print('.');
  Serial.println(abs(t10 % 10)); // десята
  delay(500);
}
```

Розберімо, чому воно саме таке.

`PROGMEM` і `pgm_read_word`. Масив живе у flash-пам'яті, а не в дефіцитній RAM (на Uno її лише 2 кБ). `PROGMEM` кладе таблицю у flash, а `pgm_read_word` дістає звідти 16-бітне слово. Забудеш `pgm_read_word` і звернешся до `TABLE[i].adc` напряму — на AVR прочитаєш **сміття** з RAM за тією ж адресою, бо там таблиці немає. Це специфіка гарвардської архітектури AVR: код і дані в різних просторах пам'яті.

Температура як `int16_t` у **десятих градуса** (`t10`), а не `float`. Множимо все на 10 — і десята частка градуса живе в цілому числі. Так ми зберігаємо роздільність без жодної рухомої коми: `255` означає 25.5 °C. Виводимо, розкладаючи на цілу частину (`t10/10`) і десяту (`t10%10`).

Ціла інтерполяція через `int32_t`. Формула прямої — `tHi + (tLo−tHi)·(aHi−raw)/(aHi−aLo)`. Чисельник `(tLo−tHi)·(aHi−raw)` може дійти до кількох тисяч на кількадесят — це десятки тисяч, що вже тисне на межу `int16_t`. Тому проміжок рахуємо в `int32_t`, а ділимо в кінці. Порядок дій критичний: **спершу множення, потім ділення**. Поділиш раніше цілими — втратиш усе на округленні (мала різниця відліків дасть `0`).

Обрізання країв. Якщо відлік вискочив за таблицю (давач відключився, коротке — АЦП дає 0 чи максимум), ми не інтерполюємо в порожнечу, а віддаємо крайню температуру таблиці. Це чесніше, ніж повернути випадкове число: видно, що впираємось у межу.

> 🔧 **Навіщо це.** Таблиця — це компроміс «пам'ять під код проти пам'яті під дані й швидкість». Формула з `logf` точна в кожній точці, але тягне бібліотеку `float` і рахує повільно. Таблиця миттєва, суто ціла, крихітна за кодом — ціною того, що між рядками ти зрізаєш кут прямою. Для KY-013 це не втрата: візьми крок 5 °C, і хорда відступає від справжньої кривої на соті градуса — куди дрібніше за похибку самої дешевої намистинки. На восьмибітнику без FPU це часто **єдиний** розумний шлях.

## ESP32: 12 біт, нелінійність і смертельні 5 вольтів

Перенесеш той самий KY-013 на [ESP32](book:boards/esp32-family) — і майже все лишиться, крім трьох речей, кожна з яких колись комусь коштувала вечора.

**Повна шкала — 4095, а не 1023.** АЦП ESP32 12-бітний, тож `raw` іде від 0 до 4095. Єдина правка у ratiometric-коді — константа шкали:

```cpp
const uint16_t ADC_MAX = 4095;    // 12-біт АЦП ESP32: 2^12 − 1
```

Уся решта конвеєра не змінюється: `ratio = raw/ADC_MAX` знову дає частку 0…1, і формули опору ті самі. Ось де окупається те, що ми з самого початку рахували через **відношення**, а не через абсолютні вольти: перехід 10-біт → 12-біт — це одне число, а не переписування математики. Якби ми десь зашили `raw*5.0/1023`, довелося б полювати за всіма такими місцями.

**Нелінійність АЦП ESP32.** Це головна прикрість платформи, і про неї треба знати чесно. АЦП ESP32 **помітно нелінійний**: реальна залежність «вольти → відлік» не пряма, надто на краях діапазону. За вимірами спільноти й самого Espressif, приблизно перші ~0.1–0.15 В входу «мертві» (відлік стоїть коло нуля), а вище ~3.1 В АЦП насичується в максимум — тобто крайні куски шкали брешуть, і паспортні «12 біт» на практиці ближчі до 9–10 корисних біт плюс шум. Наслідок для термометра прямий: **тримай робочу напругу на S у середині діапазону**, приблизно 0.3…2.7 В, де характеристика найрівніша. Для KY-013 це виходить майже само собою коло кімнатних температур (напруга на S близька до половини живлення), але на краях діапазону покази поповзуть не тільки через криву термістора, а й через криву самого АЦП.

Що з цим роблять на практиці. Espressif дає **заводську калібровку** АЦП: у частину чипів на виробництві прошито поправкові коефіцієнти в eFuse, і функції калібрувального API (в IDF — `esp_adc_cal_raw_to_voltage`, у новішому — `adc_cali_raw_to_voltage`) повертають уже виправлену напругу в мілівольтах. Це прибирає більшу частину **лінійного** зсуву й масштабу, але не всю нелінійність — двоточкова калібровка не випрямляє криву. Тому найнадійніше для KY-013 на ESP32 — узагалі не покладатися на абсолютний вольтаж, а працювати в ratiometric-відношенні (де `Vcc` скорочується) **і** тримати напругу подалі від країв. А коли потрібні чесні мілівольти — брати їх через калібрувальне API, а не через голе множення `raw` на опорну.

**Смертельні 5 вольтів на 3.3-вольтовому вході.** Це вже не про точність, а про життя плати, і сказати треба прямо. Виводи ESP32 **не толерантні до 5 В**: подаси на аналоговий вхід більше ~3.3 В — і ризикуєш пробити вхід назавжди. А напруга на S у KY-013 дорівнює живленню, помноженому на плече дільника, і **не перевищує напруги живлення модуля**. Тому арифметика проста й безжальна: живиш KY-013 від 5 В — S може підійматися до ~5 В — вхід ESP32 підсмажується. Висновок один: на ESP32 **живи модуль від 3.3 В**, тими самими 3.3 В, що й плату (це заразом і робить схему ratiometric відносно опорної АЦП). Якщо з якоїсь причини потрібне саме 5-вольтове живлення давача — став дільник напруги або обмежувач на вході, але простіше й безпечніше просто взяти 3.3 В.

> 🔧 **Навіщо це.** Три правки для ESP32 легко тримати списком. Перше — `ADC_MAX = 4095` (одна константа). Друге — **не вір краям**: працюй у середині діапазону напруги, а за абсолютними мілівольтами йди в калібрувальне API, не в голе множення. Третє, найважливіше — **3.3 В на живлення давача, ніколи 5 В**, бо S піде до живлення й спалить вхід. Перше — про правильність, друге — про точність, третє — про те, щоб плата взагалі лишилася жива.

## Калібрування: підрівняти покази до доброго термометра

Усе досі давало число, яке *схоже* на температуру. Щоб воно **збігалося** з правдою, KY-013 треба звірити з еталоном — добрим термометром — і підправити. Без цього чекай кількох градусів систематичної похибки: сталий резистор на платі звичайний (розкид ±1…5 %), паспортні R₂₅ і B дешевої намистинки гуляють від штуки до штуки. Це не випадковий шум (його давить усереднення) — це стабільний зсув, і лікується він калібруванням.

Найпростіше й найдієвіше — **однією точкою**. Дай давачу вилежатися поряд із добрим термометром до спільної температури, зчитай, що показує KY-013, і додай сталу поправку, щоб зійшлося. Це прибирає весь постійний зсув — головну частину похибки коло тієї точки:

```cpp
float T_OFFSET = 0.0f;   // поправка з калібрування, °C (спершу 0)

float readTempCalibrated() {
  float t = resistanceToTempC(rawToResistance(readRawAveraged(16)));
  return t + T_OFFSET;
}

// РАЗОВО: поклади поряд добрий термометр, дай зрівнятися, зчитай обидва.
// Скажімо, еталон показує 23.0, а KY-013 (з T_OFFSET=0) видає 25.4.
// Тоді  T_OFFSET = 23.0 − 25.4 = −2.4;  вписуєш це число у код.
```

Точніше — **двома точками**, бо один зсув не бере до уваги, що похибка різна на різних температурах (крива термістора й розкид B цього не дозволяють). Візьми дві температури якнайдалі одна від одної в робочому діапазоні: холодну (лід із водою — стабільні ~0 °C) і теплу (кімната або тепла вода). Для кожної запиши, що показує KY-013 (`m`, measured) проти еталона (`r`, real). Тоді проведи через дві пари `(m, r)` пряму й нею виправляй усі покази:

```cpp
// Дві калібрувальні пари (виміряне KY-013 → справжнє з еталона):
const float M1 =  1.5f, R1 =  0.0f;    // крижана вода: KY-013 дав 1.5, правда 0.0
const float M2 = 24.8f, R2 = 23.0f;    // кімната:      KY-013 дав 24.8, правда 23.0

float applyTwoPoint(float m) {
  // пряма r = a·m + b через дві точки (M1,R1) і (M2,R2)
  float a = (R2 - R1) / (M2 - M1);     // нахил
  float b = R1 - a * M1;               // зсув
  return a * m + b;
}

float readTempCalibrated2() {
  float m = resistanceToTempC(rawToResistance(readRawAveraged(16)));
  return applyTwoPoint(m);
}
```

Дві поради, що роблять калібровку чесною. Перша: **дай давачу зрівнятися**. Намистинка мала, але теплову інерцію має; клади її впритул до еталона й чекай кілька десятків секунд, поки покази перестануть повзти, — інакше калібруєш не температуру, а перехідний процес. Друга: **бери точки далеко одна від одної**. Дві близькі температури дадуть ненадійний нахил прямої (мала різниця в знаменнику `M2 − M1` роздуває будь-яку похибку зчитування). Лід і кімната — гарна пара: близько 20 градусів між ними.

Куди дівати самі коефіцієнти. У навчальному скетчі їх просто вписують у код, як вище. У серйознішому — кладуть у [EEPROM](book:programming/eeprom) плати (на Arduino — бібліотека `EEPROM`, на ESP32 — розділ NVS чи емуляція EEPROM), щоб калібровку не втратити при перепрошивці й щоб кожен екземпляр давача носив свою. Але це вже деталь зберігання; суть калібрування — саме дві виміряні пари й пряма через них.

> 🔧 **Навіщо це.** Калібрування — це та межа, за якою KY-013 із «приблизно теплого» стає справжнім термометром на кілька десятих у своєму вікні. Одна точка прибирає постійний зсув (найбільшу частину похибки), дві — ще й перекіс нахилу. Далі закон спадної віддачі: трьома-чотирма точками й кубічним Стейнгартом–Гартом можна вичавити ще трохи, але для копійчаної намистинки це вже переінвестування — розкид самого термістора з'їсть виграш. Дві точки — практичний максимум сенсу для KY-013.

## Складність і пастки: короткий підсумок для рук

Зберемо все, на чому реально спотикаються, у список — щоб перед заливкою пробігтися очима.

**Ділення цілих замість дробових.** `raw / ADC_MAX` без `(float)` дасть `0`, далі `1/0` → сміття. Приводь до `float` на самому вході — або, у табличному варіанті, тримай усе свідомо в цілих і множ **перед** діленням.

**Неправильне плече дільника.** Найчастіша й найпідступніша: код компілюється, `raw` ворушиться, а термометр показує дзеркально (тепло → «холодно»). Лікується не даташитом, а дослідом: грій намистинку рукою й дивись, `raw` росте (термістор угорі) чи падає (унизу), тоді бери відповідний рядок опору.

**10 біт проти 12 біт.** Перенесення Uno → ESP32 без правки `ADC_MAX` (1023 → 4095) зсуне всю шкалу вдвічі. Одна константа — але забути її легко.

**Нелінійність АЦП ESP32.** Краї діапазону (нижче ~0.1 В і вище ~3.1 В) брешуть; тримай робочу напругу в середині, а за абсолютними вольтами йди в калібрувальне API, не в голе множення на опорну.

**5 В на 3.3-вольтовий вхід.** Найдорожча пастка: живлення 5 В → S до ~5 В → пробитий вхід ESP32. На 3.3-вольтовій платі живи давач **тільки** від 3.3 В.

**Переповнення акумулятора усереднення.** `uint16_t` під суму багатьох 12-бітних відліків переллється; бери `uint32_t`.

**Плутанина шуму й зсуву.** Усереднення давить випадковий шум, калібрування — систематичний зсув. Усереднювати 500 відліків проти стабільної похибки на два градуси — марно; тут потрібна калібровка.

**PROGMEM без pgm_read_word.** На AVR пряме звернення до `PROGMEM`-масиву читає сміття з RAM. Діставай слова тільки через `pgm_read_word` (чи `pgm_read_*` за розміром).

Цих восьми пунктів вистачає, щоб KY-013 із «чому воно бреше» перетворився на надійну копійчану доріжку температури — рівно в тому вікні коло кімнатних значень, де ця намистинка й сильна.
