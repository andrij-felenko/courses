BMP180 не віддає нічого прямо. За фіксованою I2C-адресою `0x77` лежить набір регістрів, а число, яке з них читається, — сире: воно набуває сенсу лише після того, як його прогнати через рецепт Bosch разом з одинадцятьма коефіцієнтами, зашитими в пам'ять саме цього екземпляра давача на заводі. Цей довідник збирає **контракт** давача в одному місці: які регістри є і що в них лежить, що за калібрувальні коефіцієнти й якого вони типу, як влаштований протокол одного виміру (команда → пауза → читання) і сам цілочисловий рецепт компенсації — з перевіреними числами з документації, на яких видно, як `27898` перетворюється на рівно `15.0 °C`. Це структурний довідник, а не робочий код: готовий скетч, який усе це втілює, — в окремій [збірці коду для BMP180](book:sensors/gy-bmp180/proj-bmp180.md).

## Мапа регістрів: що де лежить у давачі

Перш ніж стукати в давач, треба знати куди. BMP180 — це набір **регістрів** (комірок пам'яті з адресами), до яких ведучий дотягується по I2C. Нас цікавлять лише кілька.

```
0xD0            — ідентифікатор чипа: завжди читається як 0x55
0xAA … 0xBF     — 22 байти калібрування: 11 коефіцієнтів по 2 байти
0xF4            — керівний регістр: сюди ПИШУТЬ командний байт виміру
0xF6, 0xF7      — старший і молодший байти результату
0xF8            — третій (найдрібніший) байт результату — лише для тиску
```

Регістр `0xD0` — дрібниця, але корисна: у ньому завжди лежить число `0x55`, однакове для BMP180 і його попередника BMP085. Прочитавши його на старті й переконавшись, що там `0x55`, ви одним запитом відрізняєте «давач на місці й це справді BMP180» від «на шині щось інше або взагалі тиша». Це найдешевша діагностика, яка є.

> Статус фактів: адреси регістрів, ідентифікатор `0x55` у `0xD0`, командні байти `0x2E`/`0x34` у `0xF4`, розкладка калібрування з `0xAA` та повний цілочисловий алгоритм компенсації — усе взято з офіційної документації BMP180 (Bosch Sensortec, BST-BMP180-DS000) і звірено з еталонним кодом Bosch «BMP180 API»; усталено.

## Одинадцять калібрувальних коефіцієнтів: адреси й знаковість

Коефіцієнти зашиті в давач намертво й не міняються, тож читають їх **один раз при старті**. Вони лежать поспіль, починаючи з адреси `0xAA`: одинадцять чисел по два байти, разом 22 байти. Кожне число — 16-бітне, старший байт іде першим (big-endian).

Ось де ховається перша пастка, і вона груба. **Не всі коефіцієнти однакового типу.** Вісім із них — **знакові** (можуть бути від'ємні), а три — **беззнакові** (лише додатні). Ось повна таблиця з їхніми адресами й типами:

```
адреса  коеф.  тип             адреса  коеф.  тип
0xAA    AC1    int16_t (знак)   0xB6    B1     int16_t (знак)
0xAC    AC2    int16_t (знак)   0xB8    B2     int16_t (знак)
0xAE    AC3    int16_t (знак)   0xBA    MB     int16_t (знак)
0xB0    AC4    uint16_t (без)   0xBC    MC     int16_t (знак)
0xB2    AC5    uint16_t (без)   0xBE    MD     int16_t (знак)
0xB4    AC6    uint16_t (без)
```

Чому це критично. Уявіть коефіцієнт `AC3`, що дорівнює `−14383`. У двох байтах це записано в доповняльному коді як `0xC7D1`. Якщо ви прочитаєте ці байти **як беззнакове** число, дістанете `51153` замість `−14383` — і вся подальша арифметика поїде в нікуди. Так само навпаки: `AC4` буває більший за 32767 (наприклад, `32741`), і прочитати його **як знакове** теж було б помилкою (для цього конкретного значення обійшлося б, але не для інших). Отже, читаючи, ви маєте **знати наперед**, який коефіцієнт якого типу, і покласти його у змінну правильного типу.

## Протокол виміру: команда → пауза → читання

Логіка виміру завжди однакова, чи міряємо температуру, чи тиск: **записати командний байт у керівний регістр `0xF4`, зачекати, поки давач зробить вимір, прочитати результат.** Різниця лише в командному байті й у тривалості паузи.

Для **температури** команда — `0x2E`. Для **тиску** — `0x34`, до якого в старших бітах додано **номер режиму передискретизації** (OSS): `0x34 + (OSS << 6)`. Тобто OSS зсувають на 6 бітів уліво й додають; пауза залежить від OSS.

```
вимір         команда у 0xF4   час давача   пауза (мс, із запасом)
температура   0x2E             ~4.5 мс      5
тиск OSS=0    0x34             ~4.5 мс      5
тиск OSS=1    0x74             ~7.5 мс      8
тиск OSS=2    0xB4             ~13.5 мс     14
тиск OSS=3    0xF4             ~25.5 мс     26
```

![Дві доріжки — для температури й для тиску; кожна складається з трьох кроків: запис командного байта в керівний регістр 0xF4, пауза потрібної тривалості, читання результату з регістрів даних; для температури це 2 байти й пауза ~5 мс, для тиску — 3 байти й пауза 5–26 мс залежно від OSS](img/measure-dance.svg)
*Однакова послідовність для обох вимірів: спершу запис команди в `0xF4` (для тиску до неї додано номер OSS), тоді обов'язкова пауза, поки давач готує результат, і лише потім читання — 2 байти для температури, 3 для тиску. Давач готує число на замовлення; читати до кінця паузи — значить читати недороблений вимір.*

Результат читають із регістрів даних: `0xF6` (старший) і `0xF7` (молодший) — для температури це два байти; для тиску додається ще `0xF8`, бо в режимах з високим OSS тиск має до 19 значущих бітів, а це більше, ніж влазить у два байти. Зібране з трьох байтів сире значення тиску зсувають праворуч на `8 − OSS` — цей зсув викидає молодші біти, яких при малому OSS давач не наповнив.

Тут ховаються дві класичні пастки протоколу. **Перша — забути паузу:** якщо прочитати результат одразу після команди, давач ще не домірив, і з регістра лізе старе значення або сміття. BMP180 — не «регістр, що завжди тримає свіже число», а машина на замовлення: ви замовляєте вимір, вона його готує, і послідовність «команда → пауза → читання» тут не рекомендація, а частина протоколу. **Друга, підступніша — неузгоджений OSS:** номер передискретизації входить у логіку тиску **двічі** — раз у командному байті (`0x34 + (OSS<<6)`) і вдруге у зсуві сирого числа (`>> (8 − OSS)`). Обидва OSS мусять бути **одним і тим самим** числом; скомандуєте OSS=3, а зсунете як OSS=0 — тиск систематично збреше, і зловити це важко, бо число виглядатиме майже правдоподібним.

Читання регістра по I2C робиться «повторним стартом»: ведучий пише адресу потрібного регістра, **не відпускаючи шину** (I2C repeated start), і одразу читає з неї потрібне число байтів. Якщо відпустити шину між записом і читанням, між ними встиг би влізти інший ведучий і зіпсувати обмін.

## Рецепт компенсації Bosch: від сирих чисел до °C і Па

На руках — два сирі числа: `UT` (uncompensated temperature) і `UP` (uncompensated pressure). Треба перетворити їх на справжні °C і Па. Bosch дає для цього **точний цілочисловий рецепт** — не формулу з плаваючою комою, а саме послідовність операцій над цілими числами, у визначеному порядку, з визначеними зсувами. Її треба відтворити **буквально**: це не «математично еквівалентний вираз», а конкретна арифметика, узгоджена з тим, як влаштований АЦП давача. Нижче — рецепт по частинах, і одразу прогнаний через **справжні числа з документації Bosch**, щоб видно було кожен проміжний результат.

### Температура: від UT до °C

Спершу температура — вона коротша й потрібна для тиску теж. Рецепт такий:

```
X1 = (UT − AC6) · AC5 / 2¹⁵
X2 = MC · 2¹¹ / (X1 + MD)
B5 = X1 + X2
T  = (B5 + 8) / 2⁴          ← у десятих градуса Цельсія
```

Ділення на `2¹⁵` — це зсув `>> 15`, множення на `2¹¹` — зсув `<< 11`; так у коді й пишуть, бо зсув швидший за ділення й саме його мав на увазі Bosch. Проміжна величина `B5` тут ключова: вона несе в собі «температурний стан» давача й потім знадобиться у формулі тиску. А `T` виходить **у десятих градуса** — тобто число `150` означає `15.0 °C`.

Візьмемо документаційний приклад. Bosch наводить конкретний давач із такими коефіцієнтами й таким сирим виміром:

```
AC5 = 32757    AC6 = 23153    MC = −8711    MD = 2868
UT  = 27898
```

Проженемо:

**Приклад: сирий вимір UT = 27898 → температура.**
```
X1 = (27898 − 23153) · 32757 / 2¹⁵
   = 4745 · 32757 / 32768
   = 155432565 / 32768
   = 4743              (цілочислово, дробову частину відкидаємо)

X2 = −8711 · 2¹¹ / (4743 + 2868)
   = −8711 · 2048 / 7611
   = −17840128 / 7611
   = −2344

B5 = 4743 + (−2344) = 2399

T  = (2399 + 8) / 2⁴ = 2407 / 16 = 150
```

Результат — `150`, тобто рівно **15.0 °C**. Число `150` збігається з тим, що дає документація для цих вхідних даних, — отже, ланцюжок відтворено правильно. Зверніть увагу, як тут працює знак: `X2` вийшов **від'ємним**, бо `MC` від'ємний, і без знакової арифметики цей крок дав би нісенітницю.

### Тиск: від UP до паскалів

Тепер тиск — довший ланцюжок, і саме тут `B5` з температурного розрахунку входить у гру (ось чому тиск не порахувати без температури). Рецепт:

```
B6 = B5 − 4000
X1 = (B2 · (B6 · B6 / 2¹²)) / 2¹¹
X2 = AC2 · B6 / 2¹¹
X3 = X1 + X2
B3 = ((AC1 · 4 + X3) << OSS + 2) / 4

X1 = AC3 · B6 / 2¹³
X2 = (B1 · (B6 · B6 / 2¹²)) / 2¹⁶
X3 = ((X1 + X2) + 2) / 2²
B4 = AC4 · (беззнак)(X3 + 32768) / 2¹⁵
B7 = ((беззнак)UP − B3) · (50000 >> OSS)

p  = (B7 < 0x80000000) ?  (B7 · 2) / B4  :  (B7 / B4) · 2

X1 = (p / 2⁸) · (p / 2⁸)
X1 = (X1 · 3038) / 2¹⁶
X2 = (−7357 · p) / 2¹⁶
p  = p + (X1 + X2 + 3791) / 2⁴          ← у паскалях
```

Так, це виглядає страхітливо. Але кожен рядок — проста ціла операція, і магічні числа (`4000`, `3038`, `−7357`, `3791`, зсуви) — це підігнані Bosch константи їхньої фізичної моделі мембрани; їх не виводять, а беруть як є з документації. Що справді треба зробити правильно — це **типи**. Дивіться на `B4` і `B7`: там стоїть **(беззнак)** — вони мають бути `uint32_t`, і `UP` у формулі `B7` теж тлумачиться беззнаково. `B7` легко переростає межу знакового 32-бітного числа (звідси й перевірка `B7 < 0x80000000` — це порівняння, чи «поміщається у половину діапазону»). Переплутаєте знакове з беззнаковим тут — і при високому тиску отримаєте від'ємну дурню.

Догоримо той самий документаційний приклад — тепер із тиском. Bosch дає:

```
AC1 = 408   AC2 = −72   AC3 = −14383   AC4 = 32741
B1  = 6190  B2  = 4     UP = 23843     OSS = 0
```

(і `B5 = 2399` з температурного кроку вище).

**Приклад: сирий вимір UP = 23843, B5 = 2399, OSS = 0 → тиск.**
```
B6 = 2399 − 4000 = −1601

X1 = (4 · (−1601·−1601 / 2¹²)) / 2¹¹ = (4 · (2563201/4096)) / 2048
   = (4 · 625) / 2048 = 2500 / 2048 = 1
X2 = −72 · −1601 / 2¹¹ = 115272 / 2048 = 56
X3 = 1 + 56 = 57
B3 = ((408·4 + 57) << 0 + 2) / 4 = (1632 + 57 + 2) / 4 = 1691 / 4 = 422

X1 = −14383 · −1601 / 2¹³ = 23027183 / 8192 = 2811
X2 = (6190 · (2563201/4096)) / 2¹⁶ = (6190 · 625) / 65536 = 3868750/65536 = 59
X3 = ((2811 + 59) + 2) / 4 = 2872 / 4 = 718
B4 = 32741 · (718 + 32768) / 2¹⁵ = 32741 · 33486 / 32768 = 1096375926/32768 = 33457
B7 = (23843 − 422) · (50000 >> 0) = 23421 · 50000 = 1171050000

B7 < 0x80000000 (=2147483648)?  так → p = (1171050000 · 2) / 33457 = 2342100000/33457 = 70003

X1 = (70003 >> 8) · (70003 >> 8) = 273 · 273 = 74529
X1 = (74529 · 3038) / 2¹⁶ = 226419102/65536 = 3454
X2 = (−7357 · 70003) / 2¹⁶ = −515012071/65536 = −7859
p  = 70003 + (3454 + (−7859) + 3791) >> 2⁴ = 70003 + (−614 >> 4) = 70003 + (−39) = 69964
```

Виходить рівно `69964 Па` — те саме число, що дає еталонний код Bosch для цих вхідних даних. Тобто **699.6 гПа** — приблизно тиск на висоті близько 3 км, що узгоджується з тестовими даними документації. Один нюанс у передостанньому рядку: там **зсув** `>> 4`, а не ділення `/ 16`, і для від'ємного `−614` це важить — арифметичний зсув округлює **вниз** (`−614 >> 4 = −39`), а не до нуля (`−614 / 16` дало б `−38`). Саме тому Bosch у рецепті всюди пише `>>`, і відтворювати треба буквально зсув. Головне ж: увесь ланцюжок відтворюється точно, і `B5` з температури справді проліз усередину через `B6 = B5 − 4000`.

Це і є весь контракт: регістри, типи коефіцієнтів, протокол виміру й точний рецепт компенсації. Як воно збирається в робочий скетч — з читанням калібрування, вимірами, обчисленням висоти й тим самим у три рядки готовою бібліотекою — показано в [збірці коду для BMP180](book:sensors/gy-bmp180/proj-bmp180.md).
