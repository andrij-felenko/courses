# ⚙️ KY-021 у коді: від «горить лампочка» до давача, що спить рік

Геркон на платі KY-021 не має ні мозку, ні пам'яті — він тупо замикає й розмикає два дроти. Уся кмітливість, яка перетворює це замикання на щось корисне, живе **у прошивці**. І тут ховається розрив, через який спотикаються майже всі: `digitalRead` виглядає так просто, що здається, ніби писати нема чого — а насправді той самий геркон, залежно від того, як ти його читаєш, буде або надійним лічильником обертів колеса, або джерелом випадкових цифр; або дверним давачем, що живе рік від «таблетки», або тим, що з'їдає батарею за тиждень.

Розберемо чотири задачі, які покривають майже все, для чого KY-021 узагалі беруть. Вони йдуть **сходами, від простого до хитрого**: спершу просто прочитати стан, тоді — навчитися чесно лічити (це вже не тривіально), тоді — ловити саму **мить** події, і врешті — вижати з давача головну його перевагу: майже нульове споживання уві сні. Код — реальний, під Arduino й ESP32; його можна взяти й залити.

## Пастка нульова, з якої все починається: перевернута логіка

Перш ніж писати бодай рядок, треба вкласти в голову одну річ, бо вона отруює всі чотири задачі одразу. На KY-021 резистор-[підтяжка](book:electronics/floating-pullups) тягне сигнал до плюса, а геркон стоїть між сигналом і землею. Звідси:

```
магніту немає  →  геркон розімкнений  →  підтяжка тримає S = HIGH  (1)
магніт поряд   →  геркон замкнув S на землю  →  S = LOW   (0)
```

Це **активно-низький** вихід: подія позначається **падінням** у нуль, а не підйомом. Дев'ять із десяти новачків пишуть `if (digitalRead(pin) == HIGH)`, думаючи «HIGH = спрацювало», і отримують давач, що «реагує весь час» — бо HIGH тут означає рівно протилежне, «магніту немає». Тому перше, що ми зробимо в коді, — заведемо чесне ім'я, щоб більше ніколи про це не думати:

:::tabs
```cpp
// одне місце правди на весь скетч:
// геркон замкнений (магніт поряд) == вхід у LOW
inline bool magnetPresent(uint8_t pin) {
  return digitalRead(pin) == LOW;
}
```
```micropython
from machine import Pin

# одне місце правди на весь скетч:
# геркон замкнений (магніт поряд) == вхід у LOW
def magnet_present(pin: Pin) -> bool:
    return pin.value() == 0
```
:::

Далі в усьому коді ми питаємо `magnetPresent(...)`, а не сирий `digitalRead`, і перевернута логіка більше нас не турбує — вона замкнена в одному рядку.

> 🔧 **Навіщо це.** Магічні `HIGH`/`LOW` розсипані по коду — головна причина «давач працює навпаки». Один `inline`-предикат коштує нуль тактів (компілятор його вбудує), але прибирає цілий клас помилок: логіка давача сформульована **раз**, словами предметної області («магніт поряд?»), а не електрики («пін у нулі?»). Коли за півроку ти повернешся до коду, ти читатимеш наміри, а не рахуватимеш інверсії в голові.

## Задача 1. Просто прочитати: є магніт чи ні

Найпростіший режим: у кожен момент хочемо знати поточний стан. Двері відчинені чи зачинені? Кришка закрита? Тут не треба нічого лічити й ловити — досить опитати пін і діяти за станом.

**Умова.** Сигнал S KY-021 — на D2 Arduino Uno; поки поряд магніт, світить вбудований світлодіод (D13) і в монітор порту летить стан. Плата 5-вольтова, модуль живимо 5 В.

:::tabs
```cpp
const uint8_t PIN_REED = 2;    // S давача KY-021
const uint8_t PIN_LED  = 13;   // вбудований світлодіод

inline bool magnetPresent(uint8_t pin) { return digitalRead(pin) == LOW; }

void setup() {
  pinMode(PIN_REED, INPUT);    // підтяжка вже на платі — INPUT достатньо
  pinMode(PIN_LED,  OUTPUT);
  Serial.begin(9600);
}

void loop() {
  bool magnet = magnetPresent(PIN_REED);
  digitalWrite(PIN_LED, magnet ? HIGH : LOW);
  Serial.println(magnet ? "магніт поряд" : "магніту немає");
  delay(100);
}
```
```micropython
from machine import Pin
import time

PIN_REED = 4                       # S давача KY-021 (GPIO 4)
PIN_LED  = 2                        # вбудований світлодіод (GPIO 2)

reed = Pin(PIN_REED, Pin.IN)       # підтяжка вже на платі — Pin.IN достатньо
led  = Pin(PIN_LED, Pin.OUT)

def magnet_present(pin: Pin) -> bool:
    return pin.value() == 0

while True:
    magnet = magnet_present(reed)
    led.value(1 if magnet else 0)
    print("магніт поряд" if magnet else "магніту немає")
    time.sleep_ms(100)
```
:::

Це працює й нічого хитрого не потребує — саме тому, що ми **не лічимо** й нам байдужий брязкіт. Якщо в мить замикання язички геркона кілька разів клацнуть між дотиком і розривом, світлодіод на ці мілісекунди легенько моргне — і ніхто цього не побачить. Для «показувати поточний стан» брязкіт нешкідливий; ми його просто ігноруємо.

Одразу закриємо дрібну, але часту пастку `INPUT` проти `INPUT_PULLUP`. На KY-021 підтяжка вже стоїть **на платі**, тож голого `INPUT` досить. Якби ти чіпляв **голий геркон** без модуля (два дроти прямо на пін і на землю), то `INPUT` дав би **плаваючий** вхід — розімкнений геркон лишив би пін ні до чого не підтягнутим, і той ловив би наведене сміття, показуючи то 0, то 1 без жодного магніту. Тоді рятує `INPUT_PULLUP`: він умикає **внутрішню** підтяжку чипа, і логіка стає такою ж активно-низькою. Правило просте: **модуль KY-021 → `INPUT` (можна й `INPUT_PULLUP`, не зашкодить); голий геркон → обов'язково `INPUT_PULLUP`**.

## Задача 2. Лічити чесно: брязкіт і дебаунс

А ось тут закінчується казка. Щойно ти захочеш не «показати стан», а **порахувати події** — скільки разів магніт пройшов повз, скільки обертів зробило колесо, скільки літрів протекло через лічильник води, — наївний код почне брехати, і брехати сильно.

Причина — той самий брязкіт, але тепер він фатальний. Геркон — механічний контакт; коли язички змикаються, вони не «залипають» миттєво, а кілька разів пружно **відскакують** і знову торкаються, перш ніж заспокоїтись. Для реального геркона це вкладається приблизно в **0.5–1 мс**, а на повільному підході магніту (коли поле наростає плавно) серія «клац» може розтягтися й на кілька мілісекунд. Мікроконтролер, що опитує пін тисячі разів на секунду, **бачить кожен цей відскок як окрему подію**. Один реальний прохід магніту перетворюється на три-п'ять зарахованих імпульсів.

![Часова діаграма: сирий сигнал геркона брязкає чотирма зайвими клацаннями, а після таймерного дебаунсу лишається один чесний імпульс](/catalog/sensors/motion/ky-021-reed/img/debounce-timeline.svg)

*Що бачить лічильник без дебаунсу і з ним. Угорі — сирий сигнал S: у мить замикання геркон встиг кілька разів клацнути (червоні позначки), і наївний лічильник зарахував би їх усі. Унизу — після дебаунсу: зафіксувавши перший край, код на ~10 мс перестає слухати пін, брязкіт вщухає всередині цього вікна, і лишається рівно один чесний імпульс на прохід.*

> 🔧 **Навіщо це.** Це не хиба саме KY-021, а властивість будь-якого механічного контакту, і лікується вона так само, як для звичайної кнопки — [усуненням брязкоту](book:electronics/contact-debounce): зафіксувати зміну рівня й **повірити їй лише тоді, коли вона встоялась**. Різниця в наслідках драматична. Для «увімкни світло, поки двері відчинені» зайві клацання непомітні. Для «полічи, скільки води пройшло через лічильник» вони роздувають показ **у рази** — уяви рахунок за воду, помножений на чотири. Тому щойно з'явилося слово «лічити», дебаунс перестає бути опційним.

### Дебаунс на `millis()`: чекаємо, доки заспокоїться

Найпростіший і найнадійніший спосіб — **не спати, а дивитися на годинник**. Ідея: зарахуємо подію на першому падінні в LOW, запам'ятаємо **коли** це сталося, і потім певний час (вікно дебаунсу) просто не звертаємо уваги на пін — хай брязкіт вигасне всередині цього вікна. Функція `millis()` повертає, скільки мілісекунд минуло від старту плати, і ми питаємо «а чи минуло вже 10 мс від зарахованого імпульсу?».

**Умова.** На колесі — магніт, повз нього стоїть KY-021 (S на D2). Рахуємо оберти й раз на секунду друкуємо лічбу. Магніт замикає геркон один раз за оберт.

:::tabs
```cpp
const uint8_t PIN_REED = 2;
const unsigned long DEBOUNCE_MS = 10;   // вікно тиші після події (мс)

inline bool magnetPresent(uint8_t pin) { return digitalRead(pin) == LOW; }

unsigned long revolutions = 0;
bool          lastState   = false;      // магніт був поряд минулого разу?
unsigned long lastEdgeMs  = 0;          // коли востаннє зарахували край
unsigned long lastReport  = 0;

void setup() {
  pinMode(PIN_REED, INPUT);
  Serial.begin(9600);
}

void loop() {
  unsigned long now = millis();
  bool state = magnetPresent(PIN_REED);

  // цікавить перехід «не було → з'явився» (край HIGH→LOW),
  // і лише якщо від минулого зарахованого краю минуло вікно тиші
  if (state && !lastState && (now - lastEdgeMs) >= DEBOUNCE_MS) {
    revolutions++;
    lastEdgeMs = now;
  }
  lastState = state;

  if (now - lastReport >= 1000) {
    lastReport = now;
    Serial.print("обертів: ");
    Serial.println(revolutions);
  }
}
```
```micropython
from machine import Pin
import time

PIN_REED    = 4
DEBOUNCE_MS = 10                  # вікно тиші після події (мс)

reed = Pin(PIN_REED, Pin.IN)

def magnet_present(pin: Pin) -> bool:
    return pin.value() == 0

revolutions  = 0
last_state   = False              # магніт був поряд минулого разу?
last_edge_ms = 0                  # коли востаннє зарахували край
last_report  = 0

while True:
    now   = time.ticks_ms()
    state = magnet_present(reed)

    # цікавить перехід «не було → з'явився» (край HIGH→LOW),
    # і лише якщо від минулого зарахованого краю минуло вікно тиші
    if state and not last_state and time.ticks_diff(now, last_edge_ms) >= DEBOUNCE_MS:
        revolutions += 1
        last_edge_ms = now
    last_state = state

    if time.ticks_diff(now, last_report) >= 1000:
        last_report = now
        print("обертів:", revolutions)
```
:::

Простежмо логіку, бо кожен рядок тут навмисний. Ми ловимо **край**, а не рівень: `state && !lastState` спрацьовує лише в **той цикл**, коли магніт щойно з'явився (був `false`, став `true`) — тож один прохід дає максимум одне зарахування, а не купу, поки магніт стоїть навпроти. Але край сам по собі ще не рятує від брязкоту: перший відскок теж дасть край HIGH→LOW. Тому додано `(now - lastEdgeMs) >= DEBOUNCE_MS` — **після зарахованого краю ми на 10 мс глухнемо**. Другий, третій, четвертий відскоки прилітають усередині цього вікна й ігноруються; на момент, коли вікно спливе, геркон уже давно заспокоївся. `lastState = state` наприкінці — щоб наступний цикл знав, який стан був «минулого разу».

Чому саме `unsigned long` для часу, а не `int`? Бо `millis()` рахує мілісекунди й через 49 діб безперервної роботи **переповнюється** (обнуляється). Хитрість `now - lastEdgeMs` на **беззнаковій** арифметиці переживає цей момент коректно: різниця лишиться правильною навіть у мить переповнення. Візьмеш `int` (на Uno він 16-бітний, стеля 32767) — зламається вже за 33 секунди.

Скільки ставити у `DEBOUNCE_MS`? Тут є вилка, і її треба відчувати. Вікно має бути **довшим за брязкіт**, але **коротшим за проміжок між двома справжніми подіями**, інакше ти проґавиш реальні імпульси. Прикинемо межу.

**Приклад: чи не задовгий дебаунс для швидкого колеса.**
```
Колесо: 1 магніт, 3000 обертів за хвилину (об/хв).
За секунду:   3000 / 60 = 50 обертів
Проміжок між обертами:  1000 мс / 50 = 20 мс
Вікно дебаунсу:         10 мс

10 мс < 20 мс  →  вікно вміщується між подіями, усе гаразд.
Але на 6000 об/хв проміжок = 10 мс — вікно з'їдає половину,
ризик пропуску росте. Тоді дебаунс зменшуй (до 3–5 мс)
або переходь на давач Голла — механічний геркон на таких
частотах усе одно не жилець.
```

Висновок: **10 мс — безпечний старт для дверей, лічильників води, повільних коліс**. Для швидкого обертання зменшуй вікно — але тоді насувається межа самого геркона, і про неї нижче.

> 🔧 **Навіщо це.** Дебаунс через `millis()` кращий за примітивний `delay(10)` після кожного краю з простої причини: `delay` **зупиняє весь чип** на ці 10 мс, і поки він спить, плата глуха до всього іншого — інших давачів, кнопок, шини. У лічильнику з одним герконом це ще стерпно, але щойно в проєкті друге діло — `delay`-дебаунс усе ламає. Підхід «дивитися на годинник» лишає `loop()` вільним: він пролітає тисячі разів на секунду, лише зрідка зараховуючи імпульс, а весь інший час доступний для решти роботи.

### Коли брязкіт зникає сам: лічба на апаратному перериванні

Опитувати пін у `loop()` добре, поки `loop()` короткий. Але якщо в проєкті багато роботи й один прохід циклу тягнеться довго, можна **проґавити** швидкий імпульс — магніт майне повз геркон між двома опитуваннями. Надійніше доручити ловлю самому чипу через [апаратне переривання](book:programming/interrupts): пін налаштовуємо так, що падіння в LOW **саме** смикає короткий обробник, хоч би що робив основний код.

:::tabs
```cpp
const uint8_t PIN_REED = 2;              // на Uno INT-входи — D2 і D3
const unsigned long DEBOUNCE_MS = 10;

volatile unsigned long revolutions = 0;  // змінюється в перериванні → volatile
volatile unsigned long lastEdgeMs  = 0;

void onReedFall() {                       // обробник переривання (ISR)
  unsigned long now = millis();           // millis() всередині ISR читати можна
  if (now - lastEdgeMs >= DEBOUNCE_MS) {  // той самий таймерний дебаунс
    revolutions++;
    lastEdgeMs = now;
  }
}

void setup() {
  pinMode(PIN_REED, INPUT);
  // край HIGH→LOW (магніт з'явився) смикає onReedFall()
  attachInterrupt(digitalPinToInterrupt(PIN_REED), onReedFall, FALLING);
  Serial.begin(9600);
}

void loop() {
  static unsigned long lastReport = 0;
  if (millis() - lastReport >= 1000) {
    lastReport = millis();
    noInterrupts();                        // читаємо 32-бітну лічбу атомарно
    unsigned long snapshot = revolutions;
    interrupts();
    Serial.print("обертів: ");
    Serial.println(snapshot);
  }
}
```
```micropython
from machine import Pin, disable_irq, enable_irq
import time

PIN_REED    = 4
DEBOUNCE_MS = 10

revolutions  = 0                  # змінюється в обробнику переривання
last_edge_ms = 0

def on_reed_fall(pin):            # обробник переривання (ISR)
    global revolutions, last_edge_ms
    now = time.ticks_ms()         # ticks_ms() усередині ISR читати можна
    if time.ticks_diff(now, last_edge_ms) >= DEBOUNCE_MS:  # той самий таймерний дебаунс
        revolutions += 1
        last_edge_ms = now

reed = Pin(PIN_REED, Pin.IN)
# край HIGH→LOW (магніт з'явився) смикає on_reed_fall()
reed.irq(trigger=Pin.IRQ_FALLING, handler=on_reed_fall)

last_report = 0
while True:
    if time.ticks_diff(time.ticks_ms(), last_report) >= 1000:
        last_report = time.ticks_ms()
        state = disable_irq()     # читаємо лічбу атомарно
        snapshot = revolutions
        enable_irq(state)
        print("обертів:", snapshot)
```
:::

Тут з'являються дві речі, повз які пройти не можна, бо їх забувають — і код починає збоїти рідко й незрозуміло. Перша: змінні, які чіпає переривання (`revolutions`, `lastEdgeMs`), позначені `volatile`. Без цього компілятор має право вирішити, що між ітераціями `loop()` вони не міняються (адже в `loop()` їх ніхто не пише), і закешувати старе значення в регістрі — лічба «замерзне». `volatile` наказує щоразу читати з пам'яті. Друга: `revolutions` — 32-бітна, а Uno 8-бітний, тож читання цих чотирьох байтів **не атомарне**: переривання може вклинитися посеред читання й лишити тобі напівоновлене число-химеру. Тому на час зчитування ми глушимо переривання (`noInterrupts()`), копіюємо значення й одразу вмикаємо назад. Обробник тримаємо **коротким** — жодних `Serial.print` усередині ISR: друк повільний, а переривання має влетіти й вилетіти за мікросекунди.

## Задача 3. Спіймати мить: одна дія на один прохід

Часто нам не потрібна лічба взагалі — потрібна **подія**. Не «поки магніт поряд, роби X», а «**у момент**, коли магніт з'явився, зроби X **один раз**»: клацнув замок — надіслав повідомлення; кришку закрили — приспав екран; двері відчинили — увімкнув світло. Якщо тут по-наївному написати `if (magnetPresent(...)) doAction();` у `loop()`, то дія повториться **тисячі разів на секунду**, поки магніт стоїть навпроти — бо умова весь цей час істинна.

Ключ — ловити не **рівень**, а **перехід**: дію запускати лише в той цикл, коли стан **змінився** з «немає» на «є». Для цього пам'ятаємо попередній стан і порівнюємо.

**Умова.** KY-021 на дверях (S на D3). Хочемо: коли двері **зачинили** (магніт наблизився, HIGH→LOW) — надрукувати «зачинено» один раз; коли **відчинили** (LOW→HIGH) — «відчинено» один раз. Жодних повторів, поки стан тримається.

:::tabs
```cpp
const uint8_t PIN_REED = 3;
const unsigned long DEBOUNCE_MS = 20;   // двері — не поспішають, вікно можна більше

inline bool magnetPresent(uint8_t pin) { return digitalRead(pin) == LOW; }

bool          doorClosed  = false;      // стійкий (уже підтверджений) стан
bool          reading     = false;      // останнє миттєве читання
unsigned long lastChange  = 0;

void setup() {
  pinMode(PIN_REED, INPUT);
  Serial.begin(9600);
  doorClosed = magnetPresent(PIN_REED); // початковий стан при вмиканні
}

void loop() {
  unsigned long now = millis();
  bool now_reading = magnetPresent(PIN_REED);

  // щойно миттєве читання відрізнилось від попереднього — перезапускаємо таймер
  if (now_reading != reading) {
    reading = now_reading;
    lastChange = now;
  }

  // читання протрималось незмінним довше за вікно → це справжня зміна, не брязкіт
  if ((now - lastChange) >= DEBOUNCE_MS && now_reading != doorClosed) {
    doorClosed = now_reading;             // фіксуємо новий стійкий стан
    Serial.println(doorClosed ? "зачинено" : "відчинено");
    // сюди — одноразова дія на перехід (надіслати, приспати, увімкнути…)
  }
}
```
```micropython
from machine import Pin

PIN_REED    = 5
```

Це вже **повноцінний антибрязкотний скінченний автомат**, і він елегантніший за попередній: він давить брязкіт **на обох краях** (і на замиканні, і на розмиканні) і водночас гарантує рівно одну реакцію на перехід. Логіка така: будь-яка зміна миттєвого читання перезапускає таймер `lastChange`; **справжньою** зміну визнаємо лише коли нове читання **протрималось незмінним** довше за вікно (`now - lastChange >= DEBOUNCE_MS`) і при цьому воно **відрізняється** від поточного стійкого стану. Брязкіт — це якраз швидкі перемикання, коротші за вікно; вони весь час скидають таймер і ніколи не «дозрівають» до зміни стійкого стану. А `doorClosed != now_reading` у кінці — запобіжник від повтору: коли стан уже зафіксовано, повторно ту саму дію не запустимо, доки не буде реального переходу назад.

> 🔧 **Навіщо це.** Різницю між «рівнем» і «переходом» варто закарбувати: **рівень** відповідає на «який стан **зараз**», **перехід** — на «що щойно **сталося**». Плутанина між ними — друга за поширеністю (після перевернутої логіки) причина дивної поведінки давача. Симптом упізнаваний: «моє повідомлення про відчинені двері шле сотні копій на секунду» — це рівень там, де мав бути перехід. Запам'ятав попередній стан, реагуєш лише на відмінність — і одна подія дає рівно одну дію.

## Задача 4. Спати роками: пробудження зі сну по замиканню геркона

Тепер — головна причина, чому в дверних сигналізаціях досі стоїть саме геркон, а не щось розумніше. **Сам геркон струму не споживає взагалі** — він просто шматок дроту з розривом, поки нема магніту. Це відчиняє двері до режиму, недосяжного для активних напівпровідникових давачів: мікроконтролер майже весь час **спить у глибокому сні**, з'їдаючи мікроампери, а замикання геркона його **будить**. Дверний давач у такому режимі живе рік і більше від однієї «таблетки» CR2032.

Але щоб це справді працювало, треба знати одну неочевидну апаратну деталь, і без неї нічого не вийде.

![Схема стану: мікроконтролер спить у power-down при мікроамперах, замикання геркона будить його рівневим перериванням, зробив діло — і назад у сон](/catalog/sensors/motion/ky-021-reed/img/wake-on-pin.svg)

*Життєвий цикл автономного давача. Майже весь час мікроконтролер у найглибшому сні (power-down): тактовий генератор стоїть, споживання ≈ 0.1 мкА. Замикання геркона роняє пін у LOW; рівневе переривання на INT0/INT1 будить чип, той робить діло (шле тривогу, інкрементує лічбу) — і знову лягає спати. Струм тече лише ті мілісекунди, поки чип не спить.*

### AVR (Arduino Uno/Nano): будити вміє тільки **рівень**, не край

Ось та деталь. У найглибшому сні ATmega328P (`SLEEP_MODE_PWR_DOWN`) **зупиняється тактовий генератор** — саме тому споживання падає до десятих часток мікроампера. Але апаратне визначення **краю** сигналу потребує **робочого тактового генератора**, щоб порівняти поточний рівень із попереднім. Раз генератор стоїть — визначати край **нема чим**. Тому з power-down чип можна розбудити зовнішнім сигналом **лише через реакцію на РІВЕНЬ**: коли на INT0 (D2) чи INT1 (D3) утримується **низький рівень**. Не падіння, а саме утримуваний нуль.

Для KY-021 це складається природно — треба лише тримати в голові напрямок. Будити з power-down вміє **низький рівень**, а низький рівень геркон дає, коли **замкнений** (магніт поряд). Отже, спати чип має в стані, де магніту нема (пін HIGH), а прокидатися — коли магніт **під'їхав** і замкнув пін у LOW. Саме так, до речі, влаштоване й пробудження ESP32 нижче. Розберемо цей — найприродніший для геркона — сценарій: **чип спить, доки магніту нема, і прокидається на замиканні.**

**Умова.** У спокої магніту біля геркона **нема**: підтяжка тримає пін у HIGH — саме в цьому стані чип спить у мікроамперах. Прокинутись треба, **щойно геркон замкнеться** (магніт під'їхав → пін упав у LOW): зачинили кришку з магнітом, під'їхав рухомий вузол, піднесли магніт-«ключ». ATmega328P (Uno/Nano), геркон на D2 (INT0).

```cpp
#include <avr/sleep.h>
#include <avr/interrupt.h>

const uint8_t PIN_REED = 2;              // INT0

inline bool magnetPresent(uint8_t pin) { return digitalRead(pin) == LOW; }

void onWake() {
  // порожньо: сам факт переривання будить чип; діло робимо в loop()
}

void goToSleep() {
  ADCSRA &= ~(1 << ADEN);                // вимкнути АЦП — інакше він їсть струм і уві сні
  set_sleep_mode(SLEEP_MODE_PWR_DOWN);   // найглибший сон, тактовий генератор стане
  cli();                                  // без переривань, поки готуємось (без гонки)
  sleep_enable();
  // у power-down доступний лише РІВЕНЬ. Озброюємось на НИЗЬКИЙ (пін LOW).
  // зараз магніту нема → пін HIGH → умова не виконана, тож чип спокійно засне;
  // переривання вистрелить згодом, коли геркон замкне пін у LOW.
  attachInterrupt(digitalPinToInterrupt(PIN_REED), onWake, LOW);
  sei();                                  // тепер переривання дозволені
  sleep_cpu();                            // ← ЧИП ЗАСИНАЄ ТУТ

  // ---- прокинулись (геркон замкнув пін у LOW): продовжуємо звідси ----
  sleep_disable();
  detachInterrupt(digitalPinToInterrupt(PIN_REED));
}

void setup() {
  pinMode(PIN_REED, INPUT);              // підтяжка на платі тримає рівні чіткими
  Serial.begin(9600);
  Serial.println("старт: засинаю, чекаю на замикання геркона");
  Serial.flush();
  goToSleep();                           // одразу в сон — до першого замикання
}

void loop() {
  // сюди виконання потрапляє ЩОЙНО прокинулись: геркон замкнувся
  Serial.println("прокинувся: геркон замкнувся (магніт поряд)!");
  Serial.flush();                        // дочекатись, поки байти підуть у порт
  // ... тут корисне діло: тривога по радіо, інкремент лічби, запис часу ...

  // поки магніт біля геркона (пін LOW), у power-down лягати НЕ МОЖНА:
  // рівневе переривання підняло б нас миттєво. Чекаємо, доки магніт поїде.
  while (magnetPresent(PIN_REED)) delay(20);

  goToSleep();                           // магніт поїхав (пін HIGH) — спимо далі
}
```

Простежмо, чому це справді спить, а не будиться щомиті. У мить `goToSleep()` магніту нема, пін у HIGH — а озброїли ми переривання на **LOW**. Умова не виконана, тож `sleep_cpu()` спокійно занурює чип у power-down: тактовий генератор стає, споживання падає в десяті частки мікроампера — і так, доки хтось не піднесе магніт. Щойно геркон замкнув пін у нуль, асинхронна ловля рівня (їй генератор не потрібен) будить чип, і виконання йде далі, у `loop()`.

Одна тонкість ховається в **поверненні** до сну. Рівневе переривання на LOW «тримається», поки пін у нулі. Якщо після пробудження магніт **ще поряд** (пін усе ще LOW), а ми одразу гукнемо `goToSleep()`, переривання спрацює **миттєво** — чип не засне, а закрутиться вхолосту, палячи струм і засипаючи порт. Тому перед сном ми **чекаємо, доки магніт поїде** (`while (magnetPresent(...))`) і пін підніметься в HIGH. Рік життя це не з'їдає: «магніт поряд» — це коротка мить самої події (кришку зачинили, ключ піднесли), а весь довгий спокій магніту нема — і чип спить.

А якщо треба навпаки — прокидатися, коли магніт **зникає** (класична тривога «двері відчинили», де в спокої двері зачинені й магніт навпроти геркона)? У power-down це так просто не зробити: зникнення магніту дає край LOW→HIGH, а високим рівнем ATmega з power-down **не будиться**. Виходів три: узяти **нормально-замкнений** геркон (замкнений, коли магніту нема, — тоді відчинення знову дає LOW); поставити апаратний **інвертор** сигналу; або спати не в найглибшому power-down, а в легшому режимі, де ловля краю ще жива, ціною більшого струму спокою. KY-021 — нормально-**розімкнений** модуль, тож на ньому природний варіант саме той, що вище: **будити замиканням**.

І ще дві дрібниці, без яких «мікроампери» лишаться на папері. Щоб струм справді впав, перед сном треба **вимкнути зайве**: АЦП (`ADCSRA &= ~(1 << ADEN)`) і, за потреби, детектор просідання живлення (BOD) — недоглянутий BOD сам їсть 20–25 мкА, з'їдаючи весь виграш. І пам'ятай, що на **готовій платі Arduino Uno** решта споживання йде не на сам чип, а на регулятор напруги й USB-міст — вони з'їдають міліампери незалежно від сну МК. Реальний наднизький струм отримують на **голому ATmega328P** (або спеціально «обрізаних» платах), де крім чипа нема кого годувати; тоді 0.1 мкА у power-down — досяжна цифра.

> 🔧 **Навіщо це.** Ось де геркон нищівно виграє в напівпровідникового родича. [Давач Голла](book:sensors/ky-003-hall) чи будь-який активний давач **сам постійно тягне струм** — його треба живити, щоб він хоч щось відчував; у сплячій системі він або їсть батарею, або мусить періодично прокидатись, щоб «озирнутись», і все одно щось витрачає. Геркон не відчуває — він **замикає коло**, а замкнене коло можна прочитати рівнем-перериванням, не витративши в спокої **нічого**. Саме тому герконовий давач живе роками від крихітної батареї, а на Голлі — тижні. Коли ключова вимога звучить «нуль струму спокою» — геркон поза конкуренцією.

### ESP32: глибокий сон і пробудження по RTC-піну

На [ESP32](book:boards/esp32-family) той самий фокус робиться інакше й, чесно кажучи, зручніше — але зі своєю парою пасток. У ESP32 є **глибокий сон** (`deep sleep`), у якому чип гасить майже все й тягне близько **10 мкА**, а прокидається за наперед заданою умовою. Для геркона нам потрібне джерело пробудження **ext0** — «прокинутись, коли на конкретному піні заданий рівень».

**Умова.** KY-021 на ESP32, S на GPIO 25. Хочемо спати в глибокому сні й прокидатися, щойно геркон замкнеться (магніт наблизиться → пін у LOW).

:::tabs
```cpp
#include "driver/rtc_io.h"

const gpio_num_t PIN_REED = GPIO_NUM_25;  // ОБОВ'ЯЗКОВО RTC-здатний GPIO!

void setup() {
  Serial.begin(115200);
  delay(200);

  // чому прокинулись цього разу?
  esp_sleep_wakeup_cause_t cause = esp_sleep_get_wakeup_cause();
  if (cause == ESP_SLEEP_WAKEUP_EXT0)
    Serial.println("прокинувся: геркон замкнувся (магніт поряд)");
  else
    Serial.println("холодний старт / скидання");

  // тут — корисне діло: надіслати тривогу по Wi-Fi, інкрементувати лічбу тощо

  // готуємось спати: будити, коли PIN_REED впаде в 0 (геркон замкнений)
  esp_sleep_enable_ext0_wakeup(PIN_REED, 0);   // 0 == прокинутись на LOW

  // на час сну лишити внутрішню підтяжку, щоб пін не «плавав»
  rtc_gpio_pullup_en(PIN_REED);
  rtc_gpio_pulldown_dis(PIN_REED);

  Serial.println("засинаю…");
  Serial.flush();
  esp_deep_sleep_start();                        // ← далі виконання НЕ ЙДЕ
}

void loop() {
  // недосяжно: після deep sleep чип перезавантажується й починає із setup()
}
```
```micropython
import machine
import esp32
from machine import Pin

PIN_REED = 25                     # ОБОВ'ЯЗКОВО RTC-здатний GPIO!

# після deep sleep чип стартує заново — уся логіка виконується «на вході»

# чому прокинулись цього разу?
if machine.wake_reason() == machine.EXT0_WAKE:
    print("прокинувся: геркон замкнувся (магніт поряд)")
else:
    print("холодний старт / скидання")

# тут — корисне діло: надіслати тривогу по Wi-Fi, інкрементувати лічбу тощо

reed = Pin(PIN_REED, Pin.IN, Pin.PULL_UP)  # внутрішня підтяжка, щоб пін не «плавав»

# готуємось спати: будити, коли PIN_REED впаде в 0 (геркон замкнений)
esp32.wake_on_ext0(pin=reed, level=esp32.WAKEUP_ALL_LOW)  # прокинутись на LOW

print("засинаю…")
machine.deepsleep()               # ← далі виконання НЕ ЙДЕ
```
:::

Тут відразу впадають в око дві відмінності від AVR, і обидві — типові пастки саме ESP32. Перша: **не будь-який GPIO вміє будити з глибокого сну**. Ловля рівня уві сні лежить на окремому «завжди живому» блоці RTC, тож пін мусить бути **RTC-здатним** — на класичному ESP32 це GPIO 0, 2, 4, 12–15, 25–27, 32–39. Причепиш геркон до GPIO 16 — код скомпілюється, але з deep sleep не прокинеться ніколи, і шукатимеш причину годинами. Друга: після глибокого сну ESP32 **не продовжує з місця засинання, а перезавантажується** — виконання щоразу починається з `setup()`, як після скидання. Тому вся логіка «прокинувся → зробив діло → знову спати» живе **в `setup()`**, а `loop()` лишається порожнім і недосяжним. Причину пробудження питаємо в `esp_sleep_get_wakeup_cause()`, щоб відрізнити «розбудив геркон» від «холодний старт».

І тут же — **пастка узгодження рівнів**, спільна для всіх 3.3-вольтових плат, включно з ESP32. KY-021 усеїдний по живленню, але **рівень на його виході S дорівнює напрузі живлення**. Нагодуєш модуль 5 вольтами, а сигнал заведеш на 3.3-вольтовий GPIO ESP32 — і «одиниця» з виходу (5 В) прикладеться до входу, розрахованого щонайбільше на 3.3 В, і з часом його пошкодить. Тому на ESP32 (як і на будь-якій 3.3-вольтовій платі) **живи модуль від 3.3 В**, а не від 5 В — тоді і «1» на S буде 3.3 В, безпечні для входу. Правило універсальне: [рівні читай як діапазони](book:electronics/logic-levels-as-ranges), а живлення давача бери **під логіку своєї плати**.

## Складність і пастки: короткий підсумок

Пройдений шлях склав чотири рівні майстерності з KY-021, і кожен додав рівно одну ідею поверх попереднього. Зберемо їх разом — і поруч головні пастки, кожна з яких колись комусь коштувала вечора.

**Що вміємо, за наростанням складності:**

```
1. digitalRead           → знати стан «є / нема магніту».  Брязкіт байдужий.
2. край + millis-дебаунс  → чесно ЛІЧИТИ проходи.           Брязкіт давимо.
3. пам'ять стану          → одна дія на один ПЕРЕХІД.        Рівень ≠ подія.
4. sleep + wake-on-pin    → давач, що спить роками.          Нуль струму спокою.
```

**Пастки, зібрані в одному місці:**

- **Перевернута логіка.** Магніт = **LOW**, не HIGH. `if (digitalRead(pin) == HIGH)` «спрацьовує весь час» саме тому, що HIGH тут — це «магніту немає». Лік: один предикат `magnetPresent()` на весь код.
- **`INPUT` vs `INPUT_PULLUP`.** Модуль KY-021 має підтяжку на платі → `INPUT` досить. **Голий** геркон без модуля → обов'язково `INPUT_PULLUP`, інакше вхід плаває й показує сміття.
- **Брязкіт при лічбі.** Один прохід без дебаунсу = 3–5 зарахованих імпульсів. Для «показати стан» — байдуже; для лічильника — **обов'язково** таймерний дебаунс (≈10 мс).
- **Рівень замість переходу.** «Моя дія повторюється сотні разів на секунду» = реагуєш на рівень там, де треба перехід. Лік: пам'ятай попередній стан, дій лише на відмінності.
- **Пробудження краєм на AVR.** У power-down тактовий стоїть → край **не будить**, лише низький **рівень** на INT0/INT1. Монтаж і логіку планують під це.
- **Не-RTC пін на ESP32.** З deep sleep будить лише **RTC-здатний** GPIO; звичайний пін мовчатиме назавжди. І `setup()`, не `loop()`, — бо після сну чип стартує заново.
- **Рівні на 3.3 В.** Модуль на 5 В + сигнал на 3.3-вольтовий вхід = поступове вбивання входу. На ESP32 та іншій 3.3-вольтовій платі **живи KY-021 від 3.3 В**.
- **Межа геркона.** Механічний контакт зношується за 10⁶–10⁹ спрацювань і брязкає; для дуже частих і швидких подій (сотні на секунду) бери давач Голла — там і зносу немає, і брязкоту.

Головне, що варто винести: KY-021 у коді **простий рівно настільки, наскільки проста твоя задача**. «Горить лампочка, поки магніт поряд» — це справді п'ять рядків. Але щойно ти переходиш до чесної лічби, до одноразових подій чи до автономного живлення — з'являється по одній новій ідеї на кожному кроці (дебаунс, пам'ять переходу, рівневе пробудження), і кожну треба зрозуміти, а не скопіювати наосліп. Зате коли всі чотири складено — з копійчаної скляної трубочки виходить давач промислової надійності, що чесно рахує, точно реагує й живе роками від батарейки.
