# ⚙️ MPU-9250 у коді: від WHO_AM_I до всіх 9 осей одним читанням

Тримати плату в руках — це ще нічого. Уся користь GY-91 починається, коли мікроконтролер уміє **сказати чипу**, що робити, і **розчути** його відповідь. А відповідь MPU-9250 дає з підступом: акселерометр і гіроскоп він віддає радо, а магнетометр ховає за власним внутрішнім контролером — і поки не знаєш, як його виманити, компас лишається німим. Тут — весь шлях у робочому C: під'єднати, розбудити, вибрати діапазони, дістати магнетометр обома способами (легким і правильним), прочитати заводські поправки, зняти висоту з BMP280 і зробити те саме на SPI. І пастки, на яких горить найбільше.

Скрізь нижче — реальна прошивка на C для 32-бітного мікроконтролера з 3.3-вольтовою логікою (ESP32, STM32, RP2040). Функції шини (`i2c_write_reg`, `i2c_read_regs`) — тонка обгортка над периферією конкретної плати; їхні тіла залежать від SDK, тож логіку побудовано на них, а не на конкретному HAL. Одна така обгортка виглядає так:

```c
#include <stdint.h>

#define MPU_ADDR   0x68      // AD0 до землі → 0x68 (до живлення → 0x69)
#define AK_ADDR    0x0C      // магнетометр AK8963, коли він на зовнішній шині
#define BMP_ADDR   0x76      // барометр BMP280 (на деяких платах 0x77)

// Записати один байт у регістр пристрою dev.
int  i2c_write_reg(uint8_t dev, uint8_t reg, uint8_t val);
// Прочитати n байтів поспіль, починаючи з регістра reg, у буфер buf.
int  i2c_read_regs(uint8_t dev, uint8_t reg, uint8_t *buf, uint8_t n);

// Зручні похідні:
static uint8_t read_u8(uint8_t dev, uint8_t reg) {
    uint8_t b; i2c_read_regs(dev, reg, &b, 1); return b;
}
```

## Крок нуль: хто на шині? WHO_AM_I

Перш ніж щось налаштовувати, треба переконатися, що плата взагалі відповідає і що це справді MPU-9250, а не самозванець. Кожен MPU має регістр-«паспорт» `WHO_AM_I` за адресою `0x75`, і в ньому зашите незмінне число — для MPU-9250 це **0x71** (усталено за офіційним datasheet InvenSense/TDK).

```c
#define REG_WHO_AM_I   0x75

int mpu_present(void) {
    uint8_t id = read_u8(MPU_ADDR, REG_WHO_AM_I);
    // 0x71 — MPU-9250; 0x73 — MPU-9255 (близький родич, теж працює);
    // 0x00 або 0xFF — плата мовчить (живлення / SDA-SCL / підтяжки).
    return (id == 0x71 || id == 0x73);
}
```

Ця чотирирядкова перевірка економить години. Прочитали `0x71` — плата жива, живлення й шина в нормі, далі шукайте помилку в *своєму* коді. Прочитали `0x00` чи `0xFF` — до чипа взагалі нічого не доходить: нема підтяжок на `SDA`/`SCL`, переплутані лінії, не те живлення або хибна адреса. Прочитали `0x73` — у вас MPU-9255, не MPU-9250; він майже сумісний, але це варто знати. Прочитали щось геть інше — під виглядом MPU продали перемаркований чип.

> 🔧 **Навіщо це.** `WHO_AM_I` — єдиний спосіб *програмно* відрізнити «неправильно спаяв» від «баг у логіці». Без нього ви годинами дивитеся на нулі в даних, не знаючи, чи це чип не бачить руху, чи ви читаєте не той регістр. З ним перше ж число дає діагноз. Тому будь-який серйозний драйвер починає саме тут і без успішного `WHO_AM_I` далі не йде.

## Розбудити й налаштувати ядро

Після скиду MPU-9250 спить (біт `SLEEP` у регістрі керування живленням піднятий). Треба його розбудити й — корисна звичка — вибрати добре джерело такту. У чипі є грубий внутрішній генератор на 20 МГц, але точніший опорний сигнал бере від самого гіроскопа (PLL, прив'язаний до осі гіроскопа). Тому канонічна послідовність: скид → пауза → вибір такту від гіроскопа → вибір діапазонів.

```c
#define REG_PWR_MGMT_1   0x6B
#define REG_GYRO_CONFIG   0x1B
#define REG_ACCEL_CONFIG  0x1C
#define REG_CONFIG        0x1A
#define REG_SMPLRT_DIV    0x19

void delay_ms(uint32_t ms);   // пауза платформи

void mpu_init(void) {
    // 1. Повний скид: біт 7 (DEVICE_RESET) → чип перезавантажує регістри.
    i2c_write_reg(MPU_ADDR, REG_PWR_MGMT_1, 0x80);
    delay_ms(100);                       // чекаємо, поки скид завершиться

    // 2. Прокинутися й узяти такт від PLL гіроскопа (значення 0x01),
    //    а не від грубого внутрішнього генератора (0x00).
    i2c_write_reg(MPU_ADDR, REG_PWR_MGMT_1, 0x01);
    delay_ms(10);

    // 3. Цифровий ФНЧ: смуга ~41 Гц (значення 0x03) — прибирає високочастотний
    //    шум і вібрацію; для дрона зазвичай беруть 20–40 Гц.
    i2c_write_reg(MPU_ADDR, REG_CONFIG, 0x03);

    // 4. Дільник частоти вибірки: 1 кГц / (1 + div). div=0 → 1 кГц.
    i2c_write_reg(MPU_ADDR, REG_SMPLRT_DIV, 0x00);

    // 5. Діапазони — див. нижче окремою функцією.
}
```

Пауза після скиду — не забобон. Скид перемикає внутрішні джерела живлення й такту; якщо одразу писати наступні регістри, частина запису загубиться, і чип лишиться в напівстані. Сто мілісекунд — з запасом.

### Діапазони: чим ширший, тим грубіша поділка

Діапазон (англ. *full-scale range*) — це компроміс між **розмахом** і **роздільністю**. 16-бітне число завжди те саме (−32768…+32767); ширший діапазон розтягує ці числа на більший фізичний інтервал, тож на одиницю припадає більше фізичної величини — поділка грубішає. Вибір роблять двома бітами в кожному конфіг-регістрі (біти 4:3).

```c
// Діапазони акселерометра: біти 4:3 регістра ACCEL_CONFIG.
#define ACCEL_FS_2G   (0 << 3)   // ±2 g,  16384 LSB/g  (найточніше)
#define ACCEL_FS_4G   (1 << 3)   // ±4 g,   8192 LSB/g
#define ACCEL_FS_8G   (2 << 3)   // ±8 g,   4096 LSB/g
#define ACCEL_FS_16G  (3 << 3)   // ±16 g,  2048 LSB/g  (найгрубіше)

// Діапазони гіроскопа: біти 4:3 регістра GYRO_CONFIG.
#define GYRO_FS_250   (0 << 3)   // ±250 °/с, 131.0 LSB/(°/с)
#define GYRO_FS_500   (1 << 3)   // ±500 °/с,  65.5 LSB/(°/с)
#define GYRO_FS_1000  (2 << 3)   // ±1000 °/с, 32.8 LSB/(°/с)
#define GYRO_FS_2000  (3 << 3)   // ±2000 °/с, 16.4 LSB/(°/с)

void mpu_set_ranges(uint8_t accel_fs, uint8_t gyro_fs) {
    i2c_write_reg(MPU_ADDR, REG_ACCEL_CONFIG, accel_fs);
    i2c_write_reg(MPU_ADDR, REG_GYRO_CONFIG,  gyro_fs);
}
```

Як обирати. Для **дрона** беруть широкий гіроскоп (±2000 °/с — швидкі перевороти) і середній акселерометр (±8 g — удари при посадці не зашкалюють). Для **вимірювання нахилу нерухомого об'єкта** — навпаки, найвужчі діапазони (±2 g, ±250 °/с), бо там важлива кожна дрібна поділка, а великих швидкостей нема. Правило просте: бери найвужчий діапазон, у який ще влазить твій найбільший очікуваний рух, — так дістанеш найтоншу поділку.

Коефіцієнти перерахунку в фізичні одиниці випливають прямо з таблиці вище:

```c
// Приклад: діапазони ±8 g і ±2000 °/с. Ціна поділки з коментарів вище.
float accel_g   = raw_accel / 4096.0f;    // сире → g
float gyro_dps  = raw_gyro  / 16.4f;      // сире → °/с
```

## Читання сирих даних акселерометра й гіроскопа

Дані обох давачів лежать поспіль, починаючи з `ACCEL_XOUT_H` (`0x3B`): шість байтів акселерометра, два байти температури, шість байтів гіроскопа — **чотирнадцять байтів одним махом**. Кожна вісь — старший байт, потім молодший (big-endian, на відміну від магнетометра — про це нижче окрема пастка).

```c
#define REG_ACCEL_XOUT_H  0x3B

typedef struct {
    int16_t ax, ay, az;      // акселерометр, сирі
    int16_t temp;            // температура, сира
    int16_t gx, gy, gz;      // гіроскоп, сирі
} mpu_raw_t;

void mpu_read_raw(mpu_raw_t *r) {
    uint8_t b[14];
    i2c_read_regs(MPU_ADDR, REG_ACCEL_XOUT_H, b, 14);   // одне читання — усе

    // MPU віддає старший байт першим (big-endian):
    r->ax   = (int16_t)((b[0]  << 8) | b[1]);
    r->ay   = (int16_t)((b[2]  << 8) | b[3]);
    r->az   = (int16_t)((b[4]  << 8) | b[5]);
    r->temp = (int16_t)((b[6]  << 8) | b[7]);
    r->gx   = (int16_t)((b[8]  << 8) | b[9]);
    r->gy   = (int16_t)((b[10] << 8) | b[11]);
    r->gz   = (int16_t)((b[12] << 8) | b[13]);
}
```

Одне читання на 14 байтів замість семи окремих — не тільки швидше. Воно бере всі осі з **одного й того ж моменту**: між байтами чип не встигає взяти нову вибірку, тож ax, ay, az узгоджені в часі. Якби ви читали осі поодинці, між ними міг би вклинитися рух — і вектор прискорення «розсипався» б.

**Worked-приклад: сире число температури в градуси.** Температура — приємний спосіб перевірити, що читання взагалі коректне, бо кімнатні 20–30 °C легко впізнати. Формула з datasheet:

```c
// TEMP_degC = (raw - roomOffset) / 333.87 + 21.0   (усталено за datasheet)
// roomOffset для MPU-9250 = 0.
float temp_c = r->temp / 333.87f + 21.0f;
// напр. raw = 1336 → 1336/333.87 + 21 = 4.0 + 21 = 25.0 °C
```

Якщо тут виходить розумне число близько кімнатного — шина, адреса й порядок байтів у вас правильні. Якщо −273 чи +900 — щось із читанням (переплутані байти, зсунута адреса регістра).

## Магнетометр: два шляхи до поля

Ось де починається справжня специфіка MPU-9250. Магнетометр AK8963 — окремий кристал усередині корпусу, і **напряму на адресі 0x0C зовнішній мікроконтролер його за замовчуванням не бачить**. Причина в архітектурі: MPU-9250 має власний внутрішній I²C-майстер (англ. *auxiliary I²C master*), і при старті лінії магнетометра підключені саме до нього, а не до зовнішньої шини.

Є два шляхи дістатися поля. Легкий (bypass) і правильний (slave-режим). Обидва наведено повністю.

![Два шляхи до магнетометра AK8963: bypass відкриває наскрізний прохід із зовнішньої шини на адресу 0x0C, і майстер читає магнетометр окремо; slave-режим лишає AK8963 за внутрішнім I²C-майстром MPU, який сам опитує його й складає поле в регістри EXT_SENS_DATA поряд з акселерометром і гіроскопом.](img/mag-paths.svg)
*Bypass дає простий, але окремий доступ до магнетометра. Slave-режим тримає AK8963 усередині MPU, тож усі 9 осей забираються одним синхронним читанням.*

### Шлях 1: bypass — наскрізний прохід

Найпростіший спосіб. У регістрі `INT_PIN_CFG` (`0x37`) є біт `BYPASS_EN` (біт 1, значення `0x02`), який фізично з'єднує внутрішні лінії магнетометра із зовнішньою шиною. Але є умова: bypass працює, лише коли внутрішній I²C-майстер MPU **вимкнено** (біт `I2C_MST_EN` у `USER_CTRL` опущено). Інакше майстер тримає лінії собі.

```c
#define REG_USER_CTRL     0x6A
#define REG_INT_PIN_CFG   0x37

// Регістри самого AK8963 (адресуються за AK_ADDR = 0x0C):
#define AK_WIA    0x00       // паспорт, має віддати 0x48
#define AK_ST1    0x02       // біт 0 (DRDY) = дані готові
#define AK_HXL    0x03       // перший байт даних (X, МОЛОДШИЙ — little-endian!)
#define AK_ST2    0x09       // читання ЗАВЕРШУЄ цикл; біт 3 (HOFL) = перевантаження
#define AK_CNTL1  0x0A       // режим роботи
#define AK_ASAX   0x10       // заводські поправки чутливості X/Y/Z (0x10..0x12)

// Режими AK8963 (біти 3:0 регістра CNTL1; біт 4 = роздільність):
#define AK_MODE_POWERDOWN  0x00
#define AK_MODE_FUSEROM    0x0F           // доступ до заводських поправок
#define AK_MODE_CONT2_16B  0x16           // безперервно 100 Гц, 16 біт
//  0x16 = 0001 0110: біт4=1 → 16 біт; біти3:0=0110 → безперервний режим 2 (100 Гц)

void ak_enable_bypass(void) {
    // 1. Вимкнути внутрішній майстер MPU — інакше bypass не пустить.
    i2c_write_reg(MPU_ADDR, REG_USER_CTRL, 0x00);
    delay_ms(3);
    // 2. Увімкнути наскрізний прохід: BYPASS_EN (біт 1).
    i2c_write_reg(MPU_ADDR, REG_INT_PIN_CFG, 0x02);
    delay_ms(3);
    // Тепер AK8963 доступний напряму на адресі 0x0C.
}
```

Далі магнетометр налаштовують уже як окремий давач за адресою `0x0C`. Обов'язковий крок перед вимірами — прочитати заводські поправки (докладно нижче), бо без них компас буде викривлений.

```c
float asa[3];   // заводські множники осей, заповнить ak_read_asa()

void ak_init_bypass(void) {
    if (read_u8(AK_ADDR, AK_WIA) != 0x48) return;   // паспорт магнетометра

    // Читаємо ASA (потрібно зайти в режим Fuse ROM), потім вмикаємо вимір.
    ak_read_asa();                                  // див. наступний розділ
    i2c_write_reg(AK_ADDR, AK_CNTL1, AK_MODE_CONT2_16B);
    delay_ms(10);
}
```

Bypass добрий для першого запуску й для повільних задач: код прозорий, магнетометр читається окремою функцією. Мінус — дані магнетометра не синхронізовані з акселерометром і гіроскопом (кожен читаєте своїм викликом, у різні моменти), а магнетометр і так повільний (100 Гц проти 1000 Гц у гіроскопа). Для стабілізації дрона це не найкраще.

### Шлях 2: slave-режим — усі 9 осей одним читанням

Правильний спосіб для серйозних застосунків. Тут внутрішній I²C-майстер MPU **сам**, за розкладом, опитує AK8963 і **складає його дані у власні регістри** `EXT_SENS_DATA` поряд з акселерометром і гіроскопом. Тоді зовнішній мікроконтролер одним читанням забирає **всі 9 осей** — і вони синхронні, бо MPU збирає їх узгоджено.

Ідея така. Треба навчити внутрішній майстер: «Ходи до пристрою 0x0C, читай з нього 7 байтів, починаючи з регістра ST1, і клади їх у EXT_SENS_DATA». Це задають чотири регістри слейва (`I2C_SLV0_*`):

```c
#define REG_I2C_MST_CTRL    0x24
#define REG_I2C_SLV0_ADDR   0x25       // адреса слейва (+ біт READ = 0x80)
#define REG_I2C_SLV0_REG    0x26       // з якого регістра слейва починати
#define REG_I2C_SLV0_CTRL   0x27       // біт EN (0x80) + кількість байтів
#define REG_EXT_SENS_DATA_00 0x49      // сюди майстер складає прочитане

// Спершу магнетометр треба ОДИН РАЗ налаштувати. Для цього — короткочасно
// підняти bypass, увімкнути безперервний режим AK, прочитати ASA, і лише
// потім віддати AK8963 внутрішньому майстрові.
void ak_init_slave(void) {
    ak_enable_bypass();                             // тимчасово відкриваємо прохід
    if (read_u8(AK_ADDR, AK_WIA) != 0x48) return;
    ak_read_asa();                                  // заводські поправки
    i2c_write_reg(AK_ADDR, AK_CNTL1, AK_MODE_CONT2_16B);
    delay_ms(10);

    // Тепер закриваємо bypass і піднімаємо внутрішній майстер MPU.
    i2c_write_reg(MPU_ADDR, REG_INT_PIN_CFG, 0x00); // BYPASS_EN → 0
    i2c_write_reg(MPU_ADDR, REG_USER_CTRL,   0x20); // I2C_MST_EN (біт 5)
    i2c_write_reg(MPU_ADDR, REG_I2C_MST_CTRL, 0x0D);// такт внутр. шини ~400 кГц
    delay_ms(3);

    // Навчаємо слейв 0: читати AK8963, 7 байтів, з регістра ST1.
    i2c_write_reg(MPU_ADDR, REG_I2C_SLV0_ADDR, AK_ADDR | 0x80); // 0x80 = READ
    i2c_write_reg(MPU_ADDR, REG_I2C_SLV0_REG,  AK_ST1);
    i2c_write_reg(MPU_ADDR, REG_I2C_SLV0_CTRL, 0x80 | 7);       // EN + 7 байтів
    delay_ms(3);
}
```

Чому саме 7 байтів від `ST1`? Дані магнетометра — це `ST1` (1 байт статусу) + шість байтів поля (HXL…HZH) + `ST2` (1 байт). Разом вісім, але майстер читає **сім** від ST1: статус, шість даних. А ось `ST2` — окрема тонкість: **читання ST2 обов'язкове**, воно сигналить магнетометру «цикл завершено, можеш готувати наступний вимір». Якщо ST2 не читати, AK8963 «застигне» на першому вимірі. Тому в slave-конфігурації часто читають усі 8 байтів (ST1 + 6 + ST2), щоб майстер сам чіпав ST2. Наведений варіант із 7 байтами покладається на те, що наступний цикл слейва зачепить ST1 наново; надійніше — читати 8, і нижче в повному читанні ми беремо саме 8, щоб не залишити ST2 незачепленим:

```c
// НАДІЙНІШИЙ варіант: слейв читає 8 байтів (ST1 + 6 даних + ST2).
// Тоді ST2 читається щоцикла, і магнетометр не зависає.
i2c_write_reg(MPU_ADDR, REG_I2C_SLV0_CTRL, 0x80 | 8);
```

Тепер головне читання. Один виклик — 14 байтів акселерометра/температури/гіроскопа плюс 8 байтів магнетометра з `EXT_SENS_DATA`. Оскільки останні лежать окремим блоком (`0x49`), беремо їх другим читанням, але за один цикл опитування:

```c
typedef struct {
    int16_t ax, ay, az, temp, gx, gy, gz;   // сирі акселерометр/темп/гіро
    int16_t mx, my, mz;                     // сирий магнетометр
    uint8_t mag_ovf;                        // прапорець перевантаження поля
} imu9_t;

void imu_read_9(imu9_t *d) {
    uint8_t a[14], m[8];
    i2c_read_regs(MPU_ADDR, REG_ACCEL_XOUT_H,    a, 14);  // акс/темп/гіро
    i2c_read_regs(MPU_ADDR, REG_EXT_SENS_DATA_00, m, 8);  // магнетометр

    // Акселерометр/гіроскоп — старший байт першим (big-endian):
    d->ax = (int16_t)((a[0] << 8)|a[1]);   d->ay = (int16_t)((a[2] << 8)|a[3]);
    d->az = (int16_t)((a[4] << 8)|a[5]);   d->temp=(int16_t)((a[6] << 8)|a[7]);
    d->gx = (int16_t)((a[8] << 8)|a[9]);   d->gy = (int16_t)((a[10]<<8)|a[11]);
    d->gz = (int16_t)((a[12]<<8)|a[13]);

    // m[0] = ST1; далі шість байтів поля МОЛОДШИМ першим (little-endian!);
    // m[7] = ST2. Порядок байтів у магнетометра ПРОТИЛЕЖНИЙ до MPU:
    d->mx = (int16_t)((m[2] << 8)|m[1]);   // HXH<<8 | HXL
    d->my = (int16_t)((m[4] << 8)|m[3]);
    d->mz = (int16_t)((m[6] << 8)|m[5]);
    d->mag_ovf = (m[7] & 0x08) ? 1 : 0;    // ST2 біт 3 = HOFL (перевантаження)
}
```

Дивіться на порядок байтів магнетометра: `(m[2] << 8) | m[1]` — старший байт із **більшого** індексу. Це не помилка, а найкапосніша пастка MPU-9250: **AK8963 віддає дані молодшим байтом першим (little-endian), а сам MPU — старшим (big-endian)**. Хто механічно копіює формулу акселерометра на магнетометр, отримує безглузді стрибучі числа й тижнями шукає причину. Порядок байтів у двох давачів **протилежний**, бо це два різні кристали різних виробників.

> 🔧 **Навіщо це.** Синхронність — не педантизм. Алгоритм злиття (фільтр Маджвіка чи Калмана) припускає, що всі три давачі виміряли **той самий момент орієнтації**. Якщо магнетометр відстав на кілька мілісекунд, а дрон у цей час крутнувся, фільтр отримує суперечливі вектори й «смикає» оцінку курсу. Slave-режим гарантує єдиний момент: MPU збирає всі 9 осей в узгоджений кадр. Тому польотні контролери йдуть саме цим складнішим шляхом.

## Заводські поправки магнетометра (ASA) і формула поля

У кожного екземпляра AK8963 три осі трохи різняться за підсиленням — виробничий розкид. Щоб компас не був викривлений, на заводі в незмінну пам'ять кожного чипа (fuse ROM — «пропалена» ПЗП) зашивають три поправкові числа `ASA` (X, Y, Z). Їх треба прочитати **один раз** при старті — але тільки в спеціальному режимі доступу до fuse ROM.

```c
void ak_read_asa(void) {
    uint8_t raw[3];
    // 1. Спершу — power-down (перемикати режими можна лише через нього).
    i2c_write_reg(AK_ADDR, AK_CNTL1, AK_MODE_POWERDOWN);
    delay_ms(10);
    // 2. Режим доступу до заводської пам'яті.
    i2c_write_reg(AK_ADDR, AK_CNTL1, AK_MODE_FUSEROM);
    delay_ms(10);
    // 3. Три байти поправок поспіль (ASAX, ASAY, ASAZ = 0x10..0x12).
    i2c_read_regs(AK_ADDR, AK_ASAX, raw, 3);
    // 4. Назад у power-down (перед вмиканням вимірювального режиму).
    i2c_write_reg(AK_ADDR, AK_CNTL1, AK_MODE_POWERDOWN);
    delay_ms(10);

    // Перерахунок у множник. Формула з datasheet AK8963:
    //   adj = ((ASA - 128) * 0.5 / 128) + 1  =  ((ASA - 128) / 256) + 1
    for (int i = 0; i < 3; i++)
        asa[i] = ((float)(raw[i] - 128) / 256.0f) + 1.0f;
}
```

Звідки саме така формула. `ASA` — восьмибітне число навколо середини діапазону, 128 (тобто `0x80`). Значення рівно 128 означає «ця вісь ідеальна, множник 1». Відхилення від 128 масштабується як `(ASA − 128)/256`: datasheet визначає крок як половину відсотка на одиницю, тож повний розкид ±128 одиниць дає множник у межах приблизно від 0.5 до 1.5. Це і є `((ASA − 128) × 0.5 / 128) + 1`, що алгебраїчно те саме, що `((ASA − 128)/256) + 1`.

Тепер повна формула поля. Сире 16-бітне число множать на ціну поділки (0.15 мкТ/LSB у 16-бітному режимі, усталено за datasheet AK8963) і на заводський множник осі:

```
поле[мкТ]_вісь = сире_вісь · 0.15 · asa[вісь]
```

```c
// Повний перерахунок з поправками. Одиниці — мікротесла (мкТ).
void ak_field_uT(const imu9_t *d, float out[3]) {
    const float scale = 0.15f;              // мкТ на LSB, 16-бітний режим
    out[0] = d->mx * scale * asa[0];
    out[1] = d->my * scale * asa[1];
    out[2] = d->mz * scale * asa[2];
}
```

**Worked-приклад: сире поле в мікротесла.** Хай сире `mx = 200`, а заводська поправка осі X дала `ASA = 180`:

```
adj_x = ((180 - 128) / 256) + 1 = (52/256) + 1 = 0.203 + 1 = 1.203
Bx    = 200 · 0.15 · 1.203 = 30.0 · 1.203 = 36.1 мкТ
```

Поле Землі біля поверхні — приблизно 25–65 мкТ, тож 36 мкТ — цілком розумне число. Якщо після поправок величина вектора поля (√(Bx²+By²+Bz²)) тримається в цьому діапазоні й не «дихає» при повороті плати — магнетометр читається правильно. Якщо `mag_ovf` підняте, поле зашкалило (поряд сильний магніт або двигун) — такий вимір відкидають.

> 🔧 **Навіщо це.** Без ASA компас не бракований — просто його осі різномасштабні, і при повороті плати кінець вектора поля описує не сферу, а еліпсоїд. Алгоритм визначення курсу очікує сферу; еліпсоїд дає систематичну похибку курсу, яка гуляє з напрямком. ASA — перший, заводський рівень калібрування; поверх нього ще накладають калібрування від «твердого» й «м'якого» заліза самого пристрою, але без ASA навіть ідеальне польове калібрування стартує з викривлених осей.

## BMP280: тиск і висота

Барометр BMP280 — четвертий, зовсім окремий давач на тій самій шині (адреса `0x76`, на деяких платах `0x77`). Свій паспорт він тримає в регістрі `0xD0` і віддає `0x58` (усталено). Його цінність — **другий канал висоти**: тиск падає з підйомом, і з нього рахують висоту навіть там, де GPS не бачить неба.

BMP280 непростий тим, що віддає **сирий** тиск і температуру, які треба скомпенсувати заводськими коефіцієнтами калібрування (їх 12, лежать від `0x88`). Bosch дає в datasheet готову цілочислову процедуру компенсації — її беруть як є, не переписуючи, бо вона враховує нелінійність давача. Тут — скелет ініціалізації й перерахунок тиску у висоту (сама компенсація — окрема довга функція `bmp280_compensate` з datasheet):

```c
#define BMP_ID      0xD0     // паспорт, віддає 0x58
#define BMP_RESET   0xE0
#define BMP_CTRL    0xF4     // керування вимірами (oversampling + режим)
#define BMP_CONFIG  0xF5
#define BMP_PRESS   0xF7     // 0xF7..0xF9 тиск, 0xFA..0xFC температура
#define BMP_CALIB   0x88     // 24 байти калібрування (12 коефіцієнтів)

int bmp280_init(void) {
    if (read_u8(BMP_ADDR, BMP_ID) != 0x58) return 0;   // не BMP280
    i2c_write_reg(BMP_ADDR, BMP_RESET, 0xB6);          // м'який скид
    delay_ms(10);
    // Читаємо 24 байти калібрування у структуру (порядок — little-endian):
    uint8_t cal[24];
    i2c_read_regs(BMP_ADDR, BMP_CALIB, cal, 24);
    bmp280_store_calib(cal);                           // розкласти по dig_T*/dig_P*
    // Oversampling ×16 по тиску й ×2 по температурі, безперервний режим:
    i2c_write_reg(BMP_ADDR, BMP_CTRL, 0x57);
    i2c_write_reg(BMP_ADDR, BMP_CONFIG, 0x10);         // фільтр IIR
    delay_ms(10);
    return 1;
}
```

Перерахунок тиску у висоту — це **барометрична формула** (спрощена, для тропосфери). Її фізичний зміст: тиск падає з висотою приблизно за степеневим законом, бо стовп повітря над тобою легшає.

```
h[м] = 44330 · (1 − (P / P₀)^(1/5.255))
```

Тут `P` — виміряний тиск, `P₀` — тиск на рівні моря (стандартно 101325 Па, але реально він гуляє з погодою), 44330 і 5.255 — сталі, що вбирають температурний градієнт атмосфери й газову сталу (усталено — стандартна атмосфера ISA).

```c
#include <math.h>

// Тиск у паскалях → висота в метрах над рівнем, де тиск = P0.
float bmp280_altitude(float pressure_pa, float p0_pa) {
    return 44330.0f * (1.0f - powf(pressure_pa / p0_pa, 1.0f / 5.255f));
}
```

**Worked-приклад: тиск у висоту.** Хай давач показав 95460 Па, а на рівні моря сьогодні 101325 Па:

```
відношення = 95460 / 101325 = 0.9421
степінь    = 0.9421 ^ (1/5.255) = 0.9421 ^ 0.1903 ≈ 0.98866
h          = 44330 · (1 − 0.98866) = 44330 · 0.01134 ≈ 503 м
```

Це висота близько 500 метрів — типово для передгір'я. Але зверніть увагу на `P₀`: якщо взяти стандартні 101325 замість справжнього сьогоднішнього тиску, похибка легко сягне десятків метрів, бо погода зсуває весь стовп. Тому барометр дає чудову **відносну** висоту (зміну від старту), а для абсолютної його калібрують за відомою точкою або зливають із GPS.

> 🔧 **Навіщо це.** GPS дає висоту рідко (кілька разів за секунду) і кепсько по вертикалі (похибка метрів десять). Барометр — швидко (сотні разів за секунду) і з роздільністю близько метра на короткому інтервалі, але «пливе» з погодою. У польотному контролері їх зливають: GPS ловить довгий дрейф барометра, барометр дає швидку й гладку вертикальну швидкість для утримання висоти. Саме тому квадрокоптер із барометром висить рівніше, ніж на самому GPS.

## SPI-варіант: та сама логіка, інша шина

Коли треба сотні чи тисячі вибірок за секунду (стабілізація коптера, аналіз вібрації), 400 кГц I²C стають вузьким місцем — і плату перемикають на SPI. Логіка регістрів **не змінюється**: ті самі адреси, ті самі значення. Змінюється лише транспорт і один нюанс тактової частоти.

Ключова асиметрія, прямо прописана в datasheet MPU-9250: **регістри читаються й пишуться на SPI лише до 1 МГц, а дані давачів можна забирати до 20 МГц** (усталено за офіційним datasheet). Тобто конфігуруєте чип повільно, а викачуєте виміри швидко. Друга відмінність — адресація регістра: замість I²C-адреси пристрою старший біт номера регістра слугує прапорцем напрямку (1 = читання, 0 = запис).

```c
uint8_t spi_transfer(uint8_t out);        // один байт туди-назад по SPI
void    spi_set_hz(uint32_t hz);          // змінити частоту такту
void    cs_low(void);  void cs_high(void);// смикнути лінію вибору чипа (NCS)

// Запис регістра: старший біт = 0. Завжди на 1 МГц.
void spi_write_reg(uint8_t reg, uint8_t val) {
    spi_set_hz(1000000);                  // конфіг — не швидше 1 МГц!
    cs_low();
    spi_transfer(reg & 0x7F);             // біт 7 = 0 → запис
    spi_transfer(val);
    cs_high();
}

// Читання n регістрів: старший біт = 1. Дані можна на 20 МГц.
void spi_read_regs(uint8_t reg, uint8_t *buf, uint8_t n) {
    spi_set_hz(20000000);                 // дані — до 20 МГц
    cs_low();
    spi_transfer(reg | 0x80);             // біт 7 = 1 → читання
    for (uint8_t i = 0; i < n; i++)
        buf[i] = spi_transfer(0x00);      // тактуємо нулями, приймаємо байти
    cs_high();
}
```

І практичний нюанс, який ламає читання цілком: **саме тому конфіг і дані розводять по частоті**. Якщо помилково писати конфіг-регістри на 20 МГц, чип іноді приймає їх спотворено — і потім годинами дивишся, чому «те саме читання» дає то правильні, то безглузді числа. Розділіть частоти, як вище, і проблема зникає.

Магнетометр на SPI дістають **тільки slave-режимом** — bypass на SPI недоступний (наскрізний прохід — це I²C-міст). Тому налаштування AK8963 через внутрішній майстер (розділ вище) — єдиний шлях до 9 осей на SPI, і воно ще й природніше лягає: усе читається з регістрів MPU одним потоком.

## Пастки, на яких горить найбільше

Зберемо докупи місця, де застрягають найчастіше — від найбільш смертельних до дрібних.

**Живлення й рівні 3.3 В.** Головна причина спаленої плати. Мікросхеми всередині — суто 3.3-вольтові; регулятор захищає лише лінію `VIN`, **а не лінії шини**. Підключили `SDA`/`SCL` напряму до 5-вольтового Arduino Uno — на входи чипа пішло 5 В, понад допустиме, і давач деградує (одразу або поступово). З 5-вольтовою логікою обов'язковий перетворювач рівнів, а `VIN` — від 3.3 В. З 3.3-вольтовим мікроконтролером (ESP32, STM32, RP2040) — напряму.

**Підтяжки на I²C.** Без підтягувальних резисторів на `SDA`/`SCL` (типово 4.7 кОм до 3.3 В) шина «мовчить» — `WHO_AM_I` віддає `0xFF`. На частині плат вони вже стоять; якщо ні або якщо лінії довгі — потрібні зовнішні. Перше, що перевіряють при німій шині.

**NCS і CSB.** Ці дві лінії вибору чипа (для MPU і для BMP280 відповідно) в режимі I²C **мусять лишатися на високому рівні**. Низький рівень на `NCS` перемикає MPU в SPI — і чип раптом ігнорує I²C. На GY-91 вони підтягнуті високо на платі, тож у чистому I²C їх не чіпають; але якщо випадково притягнути `NCS` до землі — I²C замовкне без видимої причини.

**Протилежний порядок байтів магнетометра.** AK8963 — little-endian (молодший байт першим), MPU — big-endian (старший першим). Механічне копіювання формули акселерометра на магнетометр дає стрибучі безглузді числа. Це не апаратна поломка, а найкапосніша тиха пастка коду.

**Незачеплений ST2.** Якщо в slave-режимі не читати регістр `ST2` магнетометра щоцикла, AK8963 застигає на першому вимірі — поле «замерзає» й не оновлюється. Тому слейв конфігурують на 8 байтів (ST1 + 6 + ST2), а не на 6 чи 7.

**Забутий ASA.** Пропустили заводські поправки — компас працює, але викривлений, і курс гуляє з напрямком. Пастка тим підступніша, що «майже працює».

**Конфіг на 20 МГц по SPI.** Писати регістри треба на 1 МГц; на 20 МГц вони приймаються нестабільно. Симптом — то правильні, то безглузді дані «без причини».

**Підміна чипа.** Під виглядом MPU-9250 інколи продають **MPU-9255** (`WHO_AM_I` = 0x73, майже сумісний) або перемарковані старіші чипи. А для *нового* виробу пам'ятайте: MPU-9250 знято з виробництва (EoL), наступник — ICM-20948, але він **не** код-сумісний (інша карта регістрів, драйвер треба переписувати; усталено за офіційним повідомленням про міграцію TDK/InvenSense). Тому `WHO_AM_I` на старті — не формальність, а спосіб дізнатися, що саме у вас на платі.

Проведіть код через ці вісім пунктів — і 9 осей поля разом із висотою потечуть стабільно й синхронно, готові до злиття в орієнтацію.
