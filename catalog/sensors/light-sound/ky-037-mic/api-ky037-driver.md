# 📋 Читання виходів KY-037: полярність DO, вікно для AO, піни ESP32

Голе читання KY-037 обманює простотою. `digitalRead` цифрового виходу — один рядок; `analogRead` аналогового — теж один. І майже кожен перший проєкт із цим давачем виходить дивним: аналоговий вихід «показує однакове» і в тиші, і під музику; на сусідній платі цифрова логіка перевернута; ESP32 з увімкненим Wi-Fi раптом читає з мікрофона суцільні `4095`. Жодна з цих бід — не баг у давачі. Усі вони — наслідки того, **що насправді стоїть на кожному з двох виходів**, і того, як по-різному ці виходи читаються. Ця довідка збирає докупи, як читати кожен вихід KY-037 правильно: полярність і автовизначення спокою на DO, вимірювання вікном (розмах і RMS) на AO, поріг та згладжування, а насамкінець — особливості АЦП на ESP32, що ламають наївний код. Приклади — робочим кодом, а не псевдокодом, і кожен у трьох виглядах: Arduino, ESP-IDF і STM32 HAL. Задача всюди та сама — цифровий вхід, канал АЦП, лічильник часу; різняться лише назви функцій.

Одну думку варто прийняти відразу, бо на ній тримається все інше: **KY-037 — це два різні давачі в одному корпусі**. Цифровий вихід (DO) — уже готове рішення заліза: компаратор LM393 сам порівняв звук із порогом-гвинтиком і віддав чистий біт «гучно / тихо». Аналоговий вихід (AO) — сирий, миттєвий голос мікрофона, що прудко гойдається навколо половини живлення; з нього гучність треба **видобути самому**. Плутати їх — і буде та сама «дивна поведінка». Розрізниш — і код стане простим.

## Цифровий вихід DO: контракт і полярність

DO — готовий біт: компаратор уже зробив головну роботу, порівнявши звук із поставленим гвинтиком порогом, і твій код лише читає результат. Робота проста рівно доти, доки не спіткнешся об одну пастку — **полярність**.

### Не зашивай «0» чи «1» намертво

Перша пастка чигає ще до першого корисного рядка. Питання просте: **який рівень на DO означає «голосно»** — «1» чи «0»? І чесна відповідь: залежить від плати.

Причина — у природі виходу LM393. Це **відкритий колектор** (англ. *open collector*): сама мікросхема вміє лише притягувати вихід до землі, а «вгору» його тягне підтяжковий резистор на платі. Через це на різних партіях DO у спокої може стояти або у «1», або у «0», і подія — це або падіння, або зростання. За офіційним даташитом самого модуля (Joy-IT) DO **зростає в «1»**, коли звук перевищує поріг. Це підтверджує і їхній приклад: код перевіряє `if (digital_value == 1)`. Але дешеві безіменні клони часто розведені інакше, і в них усе перевернуто. (Статус факту: усталено для оригіналу Joy-IT — з їхнього даташита; інверсія клонів — поширене, багаторазово підтверджене спостереження спільноти, а не окремий стандарт.)

Висновок для коду залізний: **ніколи не зашивай `HIGH` чи `LOW` як «подію» намертво**. Замість цього на старті визнач, який рівень плата тримає в тиші, запам'ятай його — і вважай подією будь-яке **відхилення від спокою**. Тоді той самий скетч працює і на оригіналі, і на дзеркальному клоні, без жодної правки.

:::tabs
```arduino
const uint8_t SOUND = 3;        // DO давача — на цифровий вхід

int idleLevel;                  // рівень, який плата тримає в ТИШІ (визначаємо на старті)

void setup() {
    pinMode(SOUND, INPUT);
    Serial.begin(9600);
    delay(50);                  // дати входу усталитися
    idleLevel = digitalRead(SOUND);   // у тиші — це «спокій» цієї конкретної плати
    Serial.print("Рівень спокою DO = ");
    Serial.println(idleLevel == HIGH ? "HIGH (подія — падіння в LOW)"
                                     : "LOW (подія — зростання в HIGH)");
}

// true — коли DO відійшов від спокою, тобто звук ПЕРЕВИЩИВ поріг.
inline bool isLoud() {
    return digitalRead(SOUND) != idleLevel;
}

void loop() {
    Serial.println(isLoud() ? "гучно" : "тихо");
    delay(100);
}
```
```esp-idf
#include "driver/gpio.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_log.h"

#define SOUND_GPIO  GPIO_NUM_4          // DO давача — на будь-який вхідний GPIO
static const char *TAG = "ky037";

static int idle_level;                  // рівень, який плата тримає в ТИШІ

static void sound_begin(void) {
    gpio_config_t io = {
        .pin_bit_mask = 1ULL << SOUND_GPIO,
        .mode         = GPIO_MODE_INPUT,
        .pull_up_en   = GPIO_PULLUP_DISABLE,   // підтяжка вже стоїть на модулі
        .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type    = GPIO_INTR_DISABLE,
    };
    ESP_ERROR_CHECK(gpio_config(&io));
    vTaskDelay(pdMS_TO_TICKS(50));             // дати входу усталитися
    idle_level = gpio_get_level(SOUND_GPIO);   // у тиші — «спокій» цієї плати
    ESP_LOGI(TAG, "рівень спокою DO = %d (подія — відхилення від нього)", idle_level);
}

// true — коли DO відійшов від спокою, тобто звук ПЕРЕВИЩИВ поріг.
static inline bool is_loud(void) {
    return gpio_get_level(SOUND_GPIO) != idle_level;
}

void app_main(void) {
    sound_begin();
    while (1) {
        ESP_LOGI(TAG, "%s", is_loud() ? "гучно" : "тихо");
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}
```
```stm32
#include "stm32f4xx_hal.h"
#include <stdbool.h>
#include <stdio.h>

#define SOUND_PORT  GPIOA
#define SOUND_PIN   GPIO_PIN_1          // DO давача — на будь-який вхідний вивід

static GPIO_PinState idle_level;        // рівень, який плата тримає в ТИШІ

void sound_begin(void) {
    __HAL_RCC_GPIOA_CLK_ENABLE();
    GPIO_InitTypeDef io = {0};
    io.Pin  = SOUND_PIN;
    io.Mode = GPIO_MODE_INPUT;
    io.Pull = GPIO_NOPULL;              // підтяжка вже стоїть на модулі
    HAL_GPIO_Init(SOUND_PORT, &io);

    HAL_Delay(50);                      // дати входу усталитися
    idle_level = HAL_GPIO_ReadPin(SOUND_PORT, SOUND_PIN);   // у тиші — «спокій» плати
    printf("Рівень спокою DO = %s\r\n",
           idle_level == GPIO_PIN_SET ? "SET (подія — падіння в RESET)"
                                      : "RESET (подія — зростання в SET)");
}

// true — коли DO відійшов від спокою, тобто звук ПЕРЕВИЩИВ поріг.
bool is_loud(void) {
    return HAL_GPIO_ReadPin(SOUND_PORT, SOUND_PIN) != idle_level;
}

int main(void) {
    HAL_Init();
    SystemClock_Config();
    sound_begin();
    while (1) {
        printf("%s\r\n", is_loud() ? "гучно" : "тихо");
        HAL_Delay(100);
    }
}
```
:::

Уся інверсія тепер живе в одному місці — у порівнянні `!= idleLevel` всередині `isLoud()`. Решта програми оперує чесним булевим «гучно чи ні», не знаючи й не переймаючись, «1» це чи «0» на конкретній платі.

> 🔧 **Навіщо це.** Обгортка `isLoud()` коштує один рядок, а прибирає цілий клас найпідступніших багів — «на моїй платі працює, у товариша навпаки». Поки логіка розповзається по коду десятком `== HIGH` / `== LOW`, кожен новий `if` — шанс поставити не той бік. Зібрана в одну функцію з автовизначенням спокою, полярність стає невидимою: пишеш `if (isLoud())` і читаєш це як просте «якщо голосно». Це та сама дисципліна, що рятує з будь-яким компараторним давачем на LM393 — [огляд цього класу](book:sensors/sound-lm393) показує, що всі вони мають однакову ваду відкритого колектора.

### Рівень тримається, поки звук голосний

Ще одна риса DO, від якої залежить спосіб читання: поки звук залишається гучнішим за поріг, вихід **тримається в стані події безперервно**, а не «пікає» один раз. Крикнув на секунду — DO цілу секунду в «події». Для задачі «світи, поки шумно» це саме те, що треба, — читаєш рівень прямо:

:::tabs
```arduino
const uint8_t LED = 13;         // вбудований світлодіод

void loop() {
    digitalWrite(LED, isLoud());   // світло тримається рівно поки звук над порогом
}
```

```esp-idf
        vTaskDelay(pdMS_TO_TICKS(10));        // віддати такт іншим задачам
    }
}
```

Але якщо треба ловити **окремі події** — порахувати оплески, перемкнути світло одним оплеском, — самого рівня замало: один затяжний звук зарахується як безліч. Тоді читають не рівень, а **момент його появи** (фронт) і гасять хвіст гістерезисом у часі. Це вже прикладна логіка поверх контракту DO — її повністю розібрано в [проєкті «оплеск-перемикач»](book:sensors/ky-037-mic/proj-ky037-driver.md), з фронтом, «глухим» вікном і готовими скетчами.

## Аналоговий вихід AO: чому крапка бреше, і як міряти вікном

Спокуса очевидна: «хочу число гучності — прочитаю аналоговий вихід одним `analogRead`». І тут майже всі спотикаються, бо **один відлік AO не каже про гучність нічого**. Це не тонкість, а фундамент; поки він не в голові, весь аналоговий код буде «показувати сміття».

Причина — у **зсуві**, з якого зроблено аналоговий вихід. Звук — знакозмінна величина: тиск то більший за атмосферний, то менший, тож чистий сигнал мікрофона гойдається навколо нуля, і в плюс, і в мінус. Але АЦП мікроконтролера не вміє читати від'ємну напругу — нижче нуля для нього не існує. Тому схема штучно піднімає всю хвилю на **половину живлення**: у тиші вихід стоїть не на нулі, а приблизно на ½·+V (близько 1.65 В при 3.3 В або 2.5 В при 5 В), і звук хитає сигнал уже навколо цієї робочої точки — угору й униз від неї.

Звідси й пастка. На AO — не «рівень гучності», а **миттєве значення звукової хвилі**, що прудко гойдається навколо ½·+V. Прочитавши його один раз, ти впіймаєш **випадкову точку синусоїди**: сигнал якраз міг бути на гребені, у западині чи на середині. І в глибокій тиші, і під час крику одиничний `analogRead` однаково легко поверне значення, близьке до половини живлення, — бо саме там хвиля проходить двічі за період. Тому «тихо / гучно» за одним відліком **не відрізниш**: обидва дають плюс-мінус те саме число.

Правильний спосіб випливає прямо з цього розуміння: щоб дістати гучність, треба зміряти **розмах хвилі за коротке вікно**. Береш багато відліків підряд за кілька мілісекунд — і дивишся, наскільки широко сигнал розгойдався навколо зсуву. У тиші розгойд крихітний, при голосному звуці — великий. Є два способи виразити цей розгойд числом, і варто знати обидва.

![Одне вікно вимірювання з хвилею, що свербить навколо ½·+V; горизонтальні лінії max і min охоплюють розмах хвилі, подвійна стрілка показує max−min; праворуч дві картки — спосіб розмаху та спосіб RMS](/catalog/sensors/light-sound/ky-037-mic/img/loudness-window.svg)
*Дві міри розгойду за одне вікно. Набравши пачку відліків за 30–50 мс, гучність оцінюють двома способами. Спосіб 1 — **розмах**: різниця найбільшого й найменшого значень (max−min); простий і швидкий, але чутливий до одного випадкового виплеску. Спосіб 2 — **середньоквадратичне відхилення (RMS)** від середнього: рівніше число, стійкіше до одиничного викиду й ближче до того, як гучність чує вухо. Обидва беруть багато точок за вікно — саме тому один `analogRead` тут безсилий.*

Розберімо обидві міри окремо, бо вони дають різні числа й різну поведінку.

### Спосіб перший — розмах (max−min)

Найпростіша міра: за вікно запам'ятовуємо найбільше й найменше значення АЦП, повертаємо різницю.

**Умова.** AO під'єднано до входу АЦП (на Arduino це A0, на ESP32 — нога блока АЦП1, на STM32 — канал ADC1). Треба за кожні ~50 мс оцінити гучність як розмах сигналу й вивести число, зручне для порівняння.

:::tabs
```arduino
const uint8_t MIC = A0;              // AO давача
const unsigned long WINDOW = 50;     // вікно вимірювання, мс

int measurePeakToPeak() {
    unsigned long t0 = millis();
    int hi = 0, lo = 1023;           // межі 10-бітного АЦП Arduino
    while (millis() - t0 < WINDOW) {
        int v = analogRead(MIC);     // миттєва точка хвилі
        if (v > hi) hi = v;
        if (v < lo) lo = v;
    }
    return hi - lo;                  // РОЗМАХ: тиша ≈ мало, гучно ≈ багато
}

void setup() { Serial.begin(9600); }

void loop() {
    Serial.println(measurePeakToPeak());   // спробуй у тиші й під оплеск — числа різні
}
```
```esp-idf
#include "esp_adc/adc_oneshot.h"
#include "esp_timer.h"
#include "esp_log.h"

#define MIC_CHAN   ADC_CHANNEL_6         // ADC1_CH6 = GPIO34 — блок АЦП1, дружній до Wi-Fi
#define WINDOW_US  50000                 // вікно вимірювання, 50 мс

static adc_oneshot_unit_handle_t adc1;

static void mic_begin(void) {
    adc_oneshot_unit_init_cfg_t unit = { .unit_id = ADC_UNIT_1 };
    ESP_ERROR_CHECK(adc_oneshot_new_unit(&unit, &adc1));
    adc_oneshot_chan_cfg_t chan = {
        .bitwidth = ADC_BITWIDTH_DEFAULT,   // 12 біт → 0…4095
        .atten    = ADC_ATTEN_DB_12,        // повний вхідний діапазон
    };
    ESP_ERROR_CHECK(adc_oneshot_config_channel(adc1, MIC_CHAN, &chan));
}

static int measure_peak_to_peak(void) {
    int64_t t0 = esp_timer_get_time();
    int hi = 0, lo = 4095, v;             // межі 12-бітного АЦП ESP32
    while (esp_timer_get_time() - t0 < WINDOW_US) {
        adc_oneshot_read(adc1, MIC_CHAN, &v);   // миттєва точка хвилі
        if (v > hi) hi = v;
        if (v < lo) lo = v;
    }
    return hi - lo;                       // РОЗМАХ: тиша ≈ мало, гучно ≈ багато
}

void app_main(void) {
    mic_begin();
    while (1) ESP_LOGI("ky037", "%d", measure_peak_to_peak());
}
```
```stm32
#include "stm32f4xx_hal.h"
#include <stdio.h>

#define WINDOW_MS  50                    // вікно вимірювання, мс

extern ADC_HandleTypeDef hadc1;          // AO — на канал ADC1 (напр. PA0 = IN0)

static uint16_t adc_sample(void) {
    HAL_ADC_Start(&hadc1);
    HAL_ADC_PollForConversion(&hadc1, 1);   // одне перетворення, чекати до 1 мс
    uint16_t v = HAL_ADC_GetValue(&hadc1);
    HAL_ADC_Stop(&hadc1);
    return v;
}

int measure_peak_to_peak(void) {
    uint32_t t0 = HAL_GetTick();
    int hi = 0, lo = 4095;               // межі 12-бітного АЦП STM32
    while (HAL_GetTick() - t0 < WINDOW_MS) {
        int v = adc_sample();            // миттєва точка хвилі
        if (v > hi) hi = v;
        if (v < lo) lo = v;
    }
    return hi - lo;                      // РОЗМАХ: тиша ≈ мало, гучно ≈ багато
}

int main(void) {
    HAL_Init();
    SystemClock_Config();
    MX_ADC1_Init();                      // канал, час вибірки — з генератора CubeMX
    while (1) printf("%d\r\n", measure_peak_to_peak());
}
```

Розмах — це той самий метод, що згадано в описі самого модуля, і його цілком досить, щоб відрізнити тишу від звуку. Але в нього є вада: він тримається на **двох крайніх** відліках з усього вікна. Один випадковий сплеск-наводка, що влучив у вікно, роздує `hi` — і число підскочить, хоч звуку не було. Розмах смиканий: реагує на піки, зокрема хибні.

### Спосіб другий — середньоквадратичне відхилення (RMS)

Рівніша міра дивиться не на дві крайні точки, а на **всі** відліки вікна: наскільки в середньому сигнал відхиляється від своєї середини. Це і є середньоквадратичне відхилення (англ. *RMS — root mean square*, «корінь із середнього квадрата»). Ідея: знайти середину сигналу за вікно, для кожного відліку взяти відхилення від неї, піднести до квадрата (щоб плюс і мінус не гасили одне одного), усереднити й узяти корінь.

```
σ = √( Σ(vᵢ − серед)² / N )
```

де `серед` — середнє значення за вікно (робоча точка ½·+V, знайдена з самих даних), `vᵢ` — відліки, `N` — їхня кількість. Це число росте з гучністю рівніше за розмах і не смикається від одного викиду, бо кожен відлік вносить лише свою частку в суму. Воно й ближче до того, як гучність відчуває вухо (звідси споріднений із ним «RMS-рівень» у справжніх шумомірах).

**Умова.** Той самий AO на тому самому вході АЦП. За вікно 50 мс порахувати RMS-відхилення й вивести його. Проходимо вікно **двічі**: спершу знаходимо середнє, тоді — суму квадратів відхилень від нього.

:::tabs
```arduino
const uint8_t MIC = A0;
const unsigned long WINDOW = 50;

float measureRMS() {
    // --- прохід 1: середнє (робоча точка) за вікно ---
    unsigned long t0 = millis();
    long sum = 0;
    int  n = 0;
    while (millis() - t0 < WINDOW) {
        sum += analogRead(MIC);
        n++;
    }
    float mean = (float)sum / n;

    // --- прохід 2: сума квадратів відхилень від середнього ---
    t0 = millis();
    float sumSq = 0;
    int  n2 = 0;
    while (millis() - t0 < WINDOW) {
        float d = analogRead(MIC) - mean;
        sumSq += d * d;
        n2++;
    }
    return sqrt(sumSq / n2);          // RMS-відхилення в одиницях АЦП
}

void setup() { Serial.begin(9600); }

void loop() {
    Serial.println(measureRMS(), 1);  // одна цифра після коми
}
```

Для навчального й практичного застосування два коротких проходи по 50 мс — цілком нормально; загальна затримка ~100 мс, оновлення десять разів на секунду — більш ніж досить для індикатора гучності.

### Поріг і згладжування в коді

Двох речей бракує, щоб зробити з числа гучності корисну поведінку: **порога** (від якого значення вважати «шумно») і **згладжування** (щоб число не тремтіло).

Поріг у коді потрібен тоді, коли ти хочеш ловити подію не залізним гвинтиком, а програмно — гнучкіше, з кількома рівнями чи з логікою. Це просто: порівнюєш виміряну гучність зі своїм числом.

:::tabs
```arduino

void loop() {
    int loud = measurePeakToPeak();
    if (loud > NOISE_THRESHOLD) {
        Serial.print("ШУМНО: ");
        Serial.println(loud);
    }
}
```

Число порога не універсальне — його визначають експериментально: подивись, яке значення дає `measurePeakToPeak()` у тиші твоєї кімнати, і постав поріг помітно вище фонового рівня. Це те саме, що виставити гвинтик за LED2, тільки в коді й із можливістю мати кілька порогів («тихо / розмова / крик»).

Згладжування прибирає тремтіння показника. Навіть RMS від вікна до вікна трохи гуляє; якщо гнати його прямо на стовпчик-індикатор, той дриґатиметься. Класичний дешевий фільтр — **експоненційне згладжування** (він же однополюсний ІІР-фільтр): нове згладжене значення — це переважно старе плюс дрібка нового.

:::tabs
```arduino
float g_smooth = 0;                  // згладжений рівень (зберігається між викликами)
const float ALPHA = 0.2;             // 0..1: менше = плавніше, але млявіше

void loop() {
    float now = measureRMS();
    g_smooth = ALPHA * now + (1 - ALPHA) * g_smooth;   // ковзне середнє
    Serial.println(g_smooth, 1);
}
```

Коефіцієнт `ALPHA` керує інерцією: `0.2` означає «новий вимір важить 20 %, накопичене минуле — 80 %», тож стрибки згладжуються, але й реакція трохи запізнюється. Менше значення — плавніше й повільніше; більше — жвавіше й смиканіше. Для індикатора шуму `0.1–0.3` — добрий діапазон.

> 🔧 **Навіщо це.** Три речі роблять з AO корисне число: вимірювати **вікном** (а не крапкою), поставити **поріг** над фоном свого приміщення й **згладити** результат. Пропусти перше — і тиша не відрізнятиметься від крику (класична біда «аналоговий давач звуку показує однакове»). Пропусти поріг — і не буде рішення «шумно / ні». Пропусти згладжування — і будь-який індикатор дриґатиметься від власного шуму вимірювання. Разом ці три прийоми перетворюють сирий гойдливий сигнал на стабільний рівень гучності, яким можна керувати підсвіткою, будити пристрій від шуму чи будувати грубий шумомір.

## АЦП на ESP32: розрядність і піни під Wi-Fi

На ESP32 вся логіка вище — автополярність DO, вимір AO вікном, поріг, згладжування — та сама, **байт у байт**, бо вона не прив'язана до конкретного числа розрядів. Але сам АЦП тут інший, і кілька його рис здатні зіпсувати весь аналоговий тракт, якщо їх не знати. Розберімо їх, бо вони важливіші за самі рядки коду.

**Ширший АЦП — 12 біт замість 10.** АЦП ESP32 за замовчуванням дає **12-бітне** число: відлік — 0…4095, а не 0…1023, як на 10-бітному АЦП AVR (Arduino Uno/Nano). Практично це означає рівно одне: усі «магічні числа» діапазону змінюються. Верхня межа розмаху — 4095, а не 1023; пороги, підібрані на Arduino, треба перерахувати (грубо — помножити на чотири). Сама логіка вимірювання (розмах, RMS, поріг, згладжування) — байт у байт та сама, бо вона не прив'язана до конкретного числа розрядів.

**Ширший діапазон і швидше читання — краще для звуку.** Ширше число дає тонший розмах: слабкі звуки, що на 10 бітах ледь ворушили б розмах, на 12 бітах видно чіткіше. До того ж одне перетворення на ESP32 швидше, тож за те саме вікно 50 мс встигаєш набрати більше відліків — вимір рівніший. Для звукового давача це відчутний плюс.

**Головна пастка ESP32 — конфлікт АЦП2 з Wi-Fi.** Ось про що спотикаються найчастіше, і симптом лякає: щойно вмикаєш Wi-Fi, аналоговий вихід починає читатися як суцільні `4095` (або сміття). Причина — архітектурна. У ESP32 два блоки АЦП: **АЦП1** обслуговує піни GPIO 32–39, **АЦП2** — GPIO 0, 2, 4, 12, 13, 14, 15, 25, 26, 27. І блок **АЦП2 радіомодуль забирає собі, коли працює Wi-Fi**; поки радіо активне, читати з піна АЦП2 не можна — `analogRead` віддає непотріб. (Статус: усталено, задокументовано Espressif і незліченно підтверджено спільнотою.)

Висновок практичний і жорсткий: **якщо на ESP32 буде Wi-Fi, саджай AO KY-037 лише на пін АЦП1 — GPIO 32…39**. Наприклад, GPIO 34 або 35 (вони заодно тільки входи, що для давача якраз доречно). Тоді аналоговий вихід читатиметься надійно й з увімкненим радіо. Цифровий вихід DO цим не переймається — його читає звичайний цифровий вхід, а не АЦП, тож для DO будь-який зручний GPIO годиться.

**Точність ESP32-АЦП, чесно.** Його АЦП **нелінійний біля країв діапазону**: дуже низькі й дуже високі напруги він розрізняє погано (0 В і 0.1 В обидва дадуть 0; 3.2 В і 3.3 В обидва — 4095). Для абсолютного вимірювання напруги це біда, і її лікують калібруванням. Але для **розмаху** сигналу навколо середини це майже не заважає: робоча точка ½·+V сидить у центрі діапазону, де АЦП найлінійніший, а розмах симетричний навколо неї. Тож для гучності KY-037 нелінійність країв — не проблема; згадати про неї варто лише якщо колись читатимеш із AO абсолютний рівень.

## Діагностика: симптом → причина → лік

Код для KY-037 короткий, але навколо нього — щільний вінок пасток читання, і майже кожна маскується під «баг у програмі», хоча причина в залізі чи фізиці сигналу. Ось найчастіші, з механізмом кожної.

**Один `analogRead` для звуку — тиша не відрізняється від крику.** Найчастіша аналогова біда. Одиничний відлік ловить випадкову точку хвилі, що гойдається навколо ½·+V, тож і в тиші, і під крик віддає плюс-мінус половину живлення. Лік — вимірювати **розмах** (max−min) або **RMS** за коротке вікно з багатьох відліків, як у прикладах вище. Один відлік для звуку непридатний у принципі, а не «недостатньо точний».

**У тиші на AO ~1.6 В (або ~2.5 В) «нізвідки».** Це не поломка, а навмисний **зсув ½·+V** — робоча точка, навколо якої гойдається звук (звук знакозмінний, а АЦП від'ємного не читає, тож усю хвилю підняли на середину). Так і має бути; гучність — у розмаху навколо цієї половини, а не в самому рівні.

**Цифровий вихід «навпаки»: у спокої тривога, від звуку тиша.** У тебе **інвертований DO** — варіант плати чи клон із іншим розведенням відкритого колектора LM393. Лік — не зашивати «0»/«1» намертво, а на старті прочитати рівень спокою й вважати подією відхилення від нього (`isLoud()` з `idleLevel`). Тоді код байдужий до полярності конкретної партії.

**DO спрацьовує від найменшого шурхоту або мовчить на все.** Поріг **не налаштований гвинтиком**. Вистав його за світлодіодом LED2: у тиші крути, поки LED2 щойно згасне (перестане реагувати на фон), тоді перевір, що потрібний звук його впевнено запалює. Код тут ні до чого — це фізичне налаштування компаратора.

**ESP32 з Wi-Fi читає з AO суцільні `4095`.** Ти посадив AO на пін **АЦП2** (GPIO 0, 2, 4, 12, 13, 14, 15, 25, 26, 27), а Wi-Fi забрав АЦП2 собі. Лік — саджати AO **тільки на АЦП1** (GPIO 32…39, напр. 34 чи 35). DO цим не переймається (він іде через цифровий вхід). Це найпідступніша ESP32-пастка: без Wi-Fi усе працює, а з ним аналог «ламається».

**Пороги з Arduino не працюють на ESP32.** АЦП ESP32 — **12-бітний** (0…4095), AVR-Arduino (Uno/Nano) — **10-бітний** (0…1023). Число порога, підібране на одному, на іншому промахнеться вчетверо. Перераховуй пороги під розрядність своєї плати (грубо ×4 з Arduino на ESP32); логіка вимірювання лишається та сама.

**Довгі дроти до AO — «фонить», хибні спрацювання.** Аналоговий сигнал слабкий і високоомний; довгий дріт до AO ловить наведення (мережа 50 Гц, радіо, сусідні лінії), і вони підмішуються в розмах. Тримай дріт до AO **коротким**, за змоги веди його окремо від силових ліній, живи модуль від чистого джерела. Для DO це менш критично — поріг компаратора відсікає дрібні коливання, тож цифровий вихід стійкіший до наводок і дроту.

**Живлення не під логіку плати.** Модуль всеїдний (3.3–5 В), але рівень на його виходах іде **під його живлення**. Даси модулю 5 В, а читатимеш 3.3-вольтовою платою — на DO/AO прилетить до 5 В, а це понад дозволене для входу 3.3-вольтового МК, і вхід можна пошкодити. Живи модуль **під логіку своєї плати**: 3.3 В на 3.3-вольтовій, 5 В на 5-вольтовій Arduino (там заодно ширший розмах на AO). Що таке рівні як діапазони напруги — в основах [логічних рівнів](book:electronics/logic-levels-as-ranges).

**Очікування точних децибелів.** KY-037 віддає **сирі одиниці АЦП**, а не калібрований рівень звуку: підсилення на модулі не нормоване, електретні капсулі різняться між собою. Давач добрий для **відносних** суджень (голосніше / тихіше, є звук / нема, перевищено поріг / ні); для абсолютних децибелів потрібне калібрування за еталонним шумоміром або спеціалізований мікрофонний модуль із нормованим трактом. Не будуй на «сирому» числі логіку, що вимагає справжніх дБ.

Уся довідка тримається на одному розрізненні. **DO — це готове «гучно / тихо» від компаратора**: простий біт, поріг гвинтиком; читати його правильно означає не зашивати полярність намертво, а визначати спокій на старті. **AO — сирий, миттєвий голос мікрофона навколо ½·+V**: одним відліком з нього гучності не дістати, її міряють **вікном** — розмахом чи RMS, — з порогом і згладжуванням. На AVR-Arduino це 10-бітний АЦП, на ESP32 — 12-бітний і вужчий вибір ніг під Wi-Fi (AO тільки на АЦП1). Читатимеш кожен вихід його способом — і давач, який доти «показував сміття», стане простим і передбачуваним.
