# ⚙️ Керуємо реле з коду: один вивід, нуль бібліотек, три пастки

Задача звучить оманливо просто: «увімкни реле, за п'ять секунд вимкни». Здавалося б, два рядки — `digitalWrite(pin, HIGH)` і `digitalWrite(pin, LOW)` між ними затримка. Насправді ж рівно на цих двох рядках новачок збирає три класичні граблі, кожні з яких коштують вечора: реле **клацає саме собою** в мить увімкнення плати; воно вмикається **не тим рівнем** («пишу HIGH — а воно вимикається»); а якщо перемикати його в циклі — контакти **вигорають за тиждень** замість роками. Ця стаття — робочий код, у якому всі три граблі вже прибрано, і розбір, **чому** кожен рядок стоїть саме там, де стоїть.

Гарна новина спершу: **жодної бібліотеки для реле не існує й не потрібно**. Для мікроконтролера реле-модуль — це звичайний цифровий вихід, той самий, яким блимають світлодіодом. Уся «спеціальність» реле — не в програмному інтерфейсі, а в двох фізичних фактах, які код зобов'язаний поважати: вхід модуля часто **активний нулем**, і всередині сидить механіка з обмеженим ресурсом. Розберемося з обома, і код перестане підкидати сюрпризи.

> 🔧 **Навіщо це.** Спокуса взяти «бібліотеку для реле» веде в глухий кут: її нема, бо нема чого абстрагувати — це один біт у регістрі порту. Зате є конкретні звички, без яких «простий» код псує залізо: правильний **порядок ініціалізації**, поправка на **полярність** і **обмеження частоти** перемикань. Ці три звички важать більше за будь-яку бібліотеку.

## Ідея: реле — це вихід, але вихід із пам'яттю про безпечний стан

Перш ніж писати рядок коду, тримаймо в голові головну відмінність реле від світлодіода. Світлодіод байдужий до того, у якому стані він застав старт плати: мигнув на мілісекунду при завантаженні — ніхто й не помітив. А реле керує **справжнім навантаженням** — помпою, нагрівачем, замком. Випадкове клацання при старті — це помпа, що штовхнула воду, замок, що клацнув уночі, нагрівач, що дав імпульс струму. Тому перше правило коду для реле інше, ніж для світлодіода: **вивід мусить опинитися у вимкненому стані ще до того, як стане виходом.**

Звучить парадоксально — як задати стан виводу, який ще не вихід? Але саме тут ховається розв'язок першої граблі. У мить подання живлення вивід будь-якого мікроконтролера — **вхід** (так його лишає скидання), і поки код не переналаштував ніжку на вихід (`pinMode` в Arduino, `gpio_config()` в ESP-IDF, `HAL_GPIO_Init()` на STM32), лінія `IN` ні до чого не притягнута: вона «висить у повітрі» й може випадково просісти до нуля. А на active-low модулі нуль — це **увімкнено**. Ось і клац.

Порядок, що прибирає цю граблю, — вивести на ніжку вимкнений рівень (для active-low це `HIGH`) **перед** перемиканням у режим виходу, а не після. Тоді щойно вивід стає виходом, він одразу тримає безпечний рівень, і між «висів входом» та «став виходом» нема вікна, у якому реле могло б клацнути.

*Дві часові діаграми в часі зліва направо. Наївний порядок (`pinMode` першим): доки код не дійшов до `setup()`, ніжка `IN` висить і просідає в `LOW` — на active-low модулі це «увімкнено», і реле дає небажаний `КЛАЦ`. Безпечний порядок: рівень `HIGH` (вимкнено) тримаємо від самого початку, тож коли ніжка стає виходом, реле навіть не сіпається.*

## Крок 1: правильна ініціалізація — вимкнено ще до `OUTPUT`

Ось мінімальний скелет — тими самими двома діями на трьох платформах, — який робить рівно те, що треба на старті: спершу оголошує вимкнений рівень, тоді перемикає ніжку у вихід. Зверніть увагу на порядок цих двох дій в ініціалізації — він і є вся суть.

:::tabs
```arduino
// Реле-модуль на ніжці; ТИПОВИЙ модуль — active-low (LOW = увімкнено).
const uint8_t PIN_RELAY = 7;

// Явні імена станів, щоб у коді не думати щоразу про інверсію.
const uint8_t RELAY_ON  = LOW;    // active-low: нуль вмикає
const uint8_t RELAY_OFF = HIGH;   // одиниця вимикає

void setup() {
    // 1) СПЕРШУ виставити безпечний (вимкнений) рівень на ніжку.
    digitalWrite(PIN_RELAY, RELAY_OFF);
    // 2) ТІЛЬКИ ТЕПЕР зробити ніжку виходом — вона вже тримає OFF.
    pinMode(PIN_RELAY, OUTPUT);
    // Тепер реле гарантовано вимкнене, старт тихий.
}

void loop() {
}
```
```esp-idf
// Те саме на ESP-IDF: рівень у засувку виходу СПЕРШУ, драйвер виходу — ПОТІМ.
#include "driver/gpio.h"

#define PIN_RELAY   GPIO_NUM_25   // не завантажувальна ніжка (чому — див. нижче)
#define RELAY_ON    0             // active-low: нуль вмикає
#define RELAY_OFF   1             // одиниця вимикає

void app_main(void) {
    // 1) СПЕРШУ покласти вимкнений рівень у засувку виходу. Ніжка ще не вихід,
    //    тож назовні нічого не йде — рівень просто чекає в регістрі.
    gpio_set_level(PIN_RELAY, RELAY_OFF);

    gpio_config_t cfg = {
        .pin_bit_mask = 1ULL << PIN_RELAY,
        .mode         = GPIO_MODE_OUTPUT,      // 2) ТІЛЬКИ ТЕПЕР — вихід
        .pull_up_en   = GPIO_PULLUP_ENABLE,    // підтяжка тримає IN у HIGH
        .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type    = GPIO_INTR_DISABLE,
    };
    ESP_ERROR_CHECK(gpio_config(&cfg));
    // Драйвер вмикається вже з рівнем OFF — старт тихий.
}
```
```stm32
// Те саме на STM32 HAL: запис в ODR СПЕРШУ, HAL_GPIO_Init — ПОТІМ.
#include "stm32f4xx_hal.h"

#define RELAY_PORT  GPIOB
#define RELAY_PIN   GPIO_PIN_5
#define RELAY_ON    GPIO_PIN_RESET   // active-low: нуль вмикає
#define RELAY_OFF   GPIO_PIN_SET     // одиниця вимикає

void relay_init(void) {
    __HAL_RCC_GPIOB_CLK_ENABLE();

    // 1) СПЕРШУ рівень OFF у засувку ODR — ніжка ще вхід, назовні нічого не йде.
    HAL_GPIO_WritePin(RELAY_PORT, RELAY_PIN, RELAY_OFF);

    GPIO_InitTypeDef gpio = {0};
    gpio.Pin   = RELAY_PIN;
    gpio.Mode  = GPIO_MODE_OUTPUT_PP;   // 2) ТІЛЬКИ ТЕПЕР — вихід
    gpio.Pull  = GPIO_NOPULL;           // вікно до цього рядка закриває
    gpio.Speed = GPIO_SPEED_FREQ_LOW;   // ЗОВНІШНЯ підтяжка на IN (див. нижче)
    HAL_GPIO_Init(RELAY_PORT, &gpio);
    // Драйвер вмикається вже з рівнем OFF — старт тихий.
}
```
:::

Ключ — у тому, що рівень записується **перед** тим, як ніжка стає виходом. Поки вона ще вхід, цей запис не видає напругу «в навантаження»: на AVR (а отже й у скетчі) `digitalWrite(HIGH)` на вході вмикає **вбудовану підтяжку** до живлення, на ESP32 і STM32 рівень лягає в **засувку виходу** й чекає там, а лінію тим часом тримає підтяжка — внутрішня чи зовнішня. Так чи так, `IN` не провалюється в нуль. А коли наступний рядок робить ніжку виходом, драйвер вмикається вже **з того самого рівня** `HIGH`. Клацнути нема коли.

Якби ми написали навпаки — спершу зробили ніжку виходом, потім виставили рівень OFF, — між цими двома діями ніжка-вихід на коротку мить тримала б **дефолтний нуль** (свіжий вихід стартує в `LOW`), і на active-low модулі реле встигло б клацнути. Різниця в один переставлений рядок — різниця між тихим стартом і замком, що клацає при кожному ввімкненні плати.

> 🔧 **Навіщо це.** Іменовані сталі `RELAY_ON`/`RELAY_OFF` — не косметика. Коли по всьому коду розкидані голі `digitalWrite(pin, LOW)`, через півроку неможливо згадати, вмикає той `LOW` чи вимикає, і рефакторинг під active-high модуль перетворюється на полювання по всіх файлах. З двома сталими зверху весь код читається людською мовою (`digitalWrite(PIN_RELAY, RELAY_ON)` — очевидно вмикає), а перехід на модуль іншої полярності — це правка **двох рядків** визначень, і решта коду не змінюється зовсім.

## Крок 2: чому `HIGH` вимикає — інкапсулюймо полярність у дві функції

Друга грабля — сам «активний нуль». Її природа фізична (щоб засвітився світлодіод оптопари, струм має **витікати** з ніжки в модуль, а це стан `LOW`), і боротися з нею в кожному рядку виснажливо. Куди чистіше — заховати інверсію **один раз** у дві крихітні функції й далі говорити з реле людськими словами `relayOn()` / `relayOff()`, не згадуючи про `HIGH`/`LOW` взагалі.

:::tabs
```arduino
const uint8_t PIN_RELAY = 7;

// Уся полярність модуля живе ТУТ, в одному місці.
// active-low: увімкнути = притягнути ніжку в LOW.
const bool ACTIVE_LOW = true;

inline void relayWrite(bool on) {
    // on==true  → реле УВІМКНЕНЕ; on==false → вимкнене.
    // XOR з ACTIVE_LOW інвертує рівень лише коли модуль active-low.
    digitalWrite(PIN_RELAY, (on ^ ACTIVE_LOW) ? HIGH : LOW);
}

inline void relayOn()  { relayWrite(true);  }
inline void relayOff() { relayWrite(false); }

void setup() {
    relayOff();                     // безпечний рівень СПЕРШУ (див. крок 1)
    pinMode(PIN_RELAY, OUTPUT);
}

void loop() {
    relayOn();
    delay(1000);
    relayOff();
    delay(1000);
}
```
```esp-idf
#include <stdbool.h>
#include "driver/gpio.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

#define PIN_RELAY  GPIO_NUM_25

// Уся полярність модуля живе ТУТ, в одному місці.
static const bool ACTIVE_LOW = true;

static inline void relay_write(bool on) {
    // XOR з ACTIVE_LOW інвертує рівень лише коли модуль active-low.
    gpio_set_level(PIN_RELAY, (on ^ ACTIVE_LOW) ? 1 : 0);
}

static inline void relay_on(void)  { relay_write(true);  }
static inline void relay_off(void) { relay_write(false); }

void app_main(void) {
    relay_off();                     // безпечний рівень СПЕРШУ (див. крок 1)
    gpio_config_t cfg = {
        .pin_bit_mask = 1ULL << PIN_RELAY, .mode = GPIO_MODE_OUTPUT,
        .pull_up_en = GPIO_PULLUP_ENABLE, .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type = GPIO_INTR_DISABLE,
    };
    ESP_ERROR_CHECK(gpio_config(&cfg));

    while (1) {
        relay_on();
        vTaskDelay(pdMS_TO_TICKS(1000));
        relay_off();
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```
```stm32
#include <stdbool.h>
#include "stm32f4xx_hal.h"

#define RELAY_PORT  GPIOB
#define RELAY_PIN   GPIO_PIN_5

// Уся полярність модуля живе ТУТ, в одному місці.
static const bool ACTIVE_LOW = true;

static inline void relay_write(bool on) {
    // XOR з ACTIVE_LOW інвертує рівень лише коли модуль active-low.
    HAL_GPIO_WritePin(RELAY_PORT, RELAY_PIN,
                      (on ^ ACTIVE_LOW) ? GPIO_PIN_SET : GPIO_PIN_RESET);
}

static inline void relay_on(void)  { relay_write(true);  }
static inline void relay_off(void) { relay_write(false); }

int main(void) {
    HAL_Init();
    SystemClock_Config();
    __HAL_RCC_GPIOB_CLK_ENABLE();

    relay_off();                     // безпечний рівень СПЕРШУ (див. крок 1)
    GPIO_InitTypeDef gpio = { .Pin = RELAY_PIN, .Mode = GPIO_MODE_OUTPUT_PP,
                              .Pull = GPIO_NOPULL, .Speed = GPIO_SPEED_FREQ_LOW };
    HAL_GPIO_Init(RELAY_PORT, &gpio);

    while (1) {
        relay_on();
        HAL_Delay(1000);
        relay_off();
        HAL_Delay(1000);
    }
}
```
:::

Уся хитрість — у рядку `(on ^ ACTIVE_LOW)`. Це виключне «або» (XOR): воно перевертає логічне значення `on` лише тоді, коли `ACTIVE_LOW == true`. Розпишемо всі чотири випадки, бо саме тут вся магія полярності:

```
on=true  (хочемо увімкнути), ACTIVE_LOW=true  → true ^ true  = false → LOW  → увімкнено ✓
on=false (хочемо вимкнути),  ACTIVE_LOW=true  → false ^ true = true  → HIGH → вимкнено  ✓
on=true  (хочемо увімкнути), ACTIVE_LOW=false → true ^ false = true  → HIGH → увімкнено ✓
on=false (хочемо вимкнути),  ACTIVE_LOW=false → false ^ false= false → LOW  → вимкнено  ✓
```

Одна змінна `ACTIVE_LOW` — і той самий код коректно керує обома типами модулів. Трапився вам голий транзисторний модуль, активний одиницею (стилю KY-019)? Міняєте `ACTIVE_LOW = false` — і решта програми не помічає різниці, бо про `HIGH`/`LOW` вона більше не знає нічого: тільки `relayOn()` і `relayOff()`.

Порівняно з підходом «сира ніжка як GPIO-вихід» (детально про самі функції `digitalWrite`/`pinMode` і що вони роблять із регістром порту — в [API виводів Arduino](topic:boards/arduino-uno/api-blink-io.md)) ми не додали жодного нового вміння; ми лише **назвали** інверсію так, щоб вона перестала плутати.

> 🔧 **Навіщо це.** Найдорожча помилка новачка з реле — не спалена ніжка, а **години на пошук неіснуючого багу**: «код правильний, а реле вмикається навпаки». Причина майже завжди одна — active-low, про який забули. Заховавши полярність у `relayWrite`, ви не просто економите на друкуванні `LOW`; ви **вилучаєте цілий клас помилок** — більше ніде в коді нема голого рівня, який можна переплутати. Один правильний рядок з XOR коштує дешевше за одну сесію налагодження «чому воно навпаки».

## Крок 3: таймер «увімкнути на N секунд» — без `delay`, щоб плата не глухла

Тепер сама задача: увімкнути реле й вимкнути через N секунд. Найочевидніше рішення — «увімкнути, поспати п'ять секунд, вимкнути» (`delay(5000)` в Arduino, `HAL_Delay(5000)` на STM32, `vTaskDelay` в ESP-IDF) — працює, але має вбудовану ваду: блокуюча пауза **вимикає всю плату на п'ять секунд** (на RTOS — принаймні всю цю задачу). Ці п'ять секунд контролер не читає кнопки, не опитує давачі, не блимає індикатором, не відповідає по шині — він тупо крутить порожній цикл, рахуючи час. Для іграшкового скетчу байдуже; для будь-якого реального пристрою це смерть: поки реле «відлічує», плата глуха до всього іншого.

Правильний спосіб робити щось «за таймером» і не глухнути — **не спати, а дивитися на годинник**. Годинник є на кожній платформі: лічильник мілісекунд від старту (`millis()` в Arduino, `HAL_GetTick()` на STM32, `esp_timer_get_time()` в мікросекундах в ESP-IDF). Замість «поспати 5000 мс» ми запам'ятовуємо мить увімкнення й у кожному проході циклу питаємо: «а чи вже минуло 5000 мс?».

:::tabs
```arduino
const uint8_t PIN_RELAY = 7;
const uint8_t RELAY_ON  = LOW;
const uint8_t RELAY_OFF = HIGH;

// Стан таймера реле.
bool          relayActive = false;   // чи реле зараз увімкнене таймером
unsigned long relayOffAt  = 0;       // МИТЬ (за millis), коли треба вимкнути

// Увімкнути реле рівно на durationMs мілісекунд.
void relayOnFor(unsigned long durationMs) {
    digitalWrite(PIN_RELAY, RELAY_ON);
    relayActive = true;
    relayOffAt  = millis() + durationMs;   // коли гасити
}

// Викликати В КОЖНОМУ проході loop(): сам вимкне, коли час вийде.
void relayTick() {
    if (relayActive && (long)(millis() - relayOffAt) >= 0) {
        digitalWrite(PIN_RELAY, RELAY_OFF);
        relayActive = false;
    }
}

void setup() {
    digitalWrite(PIN_RELAY, RELAY_OFF);
    pinMode(PIN_RELAY, OUTPUT);
    relayOnFor(5000);                 // клацнули увімкнене на 5 секунд
}

void loop() {
    relayTick();                      // стежить за часом, не блокуючи
    // ...сюди можна дописати будь-що: кнопки, давачі, індикатор —
    //    усе працює, поки реле відлічує свої 5 секунд.
}
```
```esp-idf
#include <stdbool.h>
#include "driver/gpio.h"
#include "esp_timer.h"
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

#define PIN_RELAY  GPIO_NUM_25
#define RELAY_ON   0
#define RELAY_OFF  1

// Стан таймера реле.
static bool    relay_active = false;   // чи реле зараз увімкнене таймером
static int64_t relay_off_at = 0;       // МИТЬ (мс від старту), коли треба вимкнути

// 64-бітні мікросекунди → мілісекунди; такий лічильник не переповниться ніколи.
static int64_t now_ms(void) { return esp_timer_get_time() / 1000; }

// Увімкнути реле рівно на duration_ms мілісекунд.
void relay_on_for(int64_t duration_ms) {
    gpio_set_level(PIN_RELAY, RELAY_ON);
    relay_active = true;
    relay_off_at = now_ms() + duration_ms;   // коли гасити
}

// Викликати В КОЖНОМУ проході циклу: сам вимкне, коли час вийде.
void relay_tick(void) {
    if (relay_active && now_ms() >= relay_off_at) {
        gpio_set_level(PIN_RELAY, RELAY_OFF);
        relay_active = false;
    }
}

void app_main(void) {
    gpio_set_level(PIN_RELAY, RELAY_OFF);
    gpio_config_t cfg = {
        .pin_bit_mask = 1ULL << PIN_RELAY, .mode = GPIO_MODE_OUTPUT,
        .pull_up_en = GPIO_PULLUP_ENABLE, .pull_down_en = GPIO_PULLDOWN_DISABLE,
        .intr_type = GPIO_INTR_DISABLE,
    };
    ESP_ERROR_CHECK(gpio_config(&cfg));
    relay_on_for(5000);               // клацнули увімкнене на 5 секунд

    while (1) {
        relay_tick();                 // стежить за часом, не блокуючи
        vTaskDelay(pdMS_TO_TICKS(10));   // віддаємо процесор іншим задачам
    }
}
```
```stm32
#include <stdbool.h>
#include "stm32f4xx_hal.h"

#define RELAY_PORT  GPIOB
#define RELAY_PIN   GPIO_PIN_5
#define RELAY_ON    GPIO_PIN_RESET
#define RELAY_OFF   GPIO_PIN_SET

// Стан таймера реле.
static bool     relay_active = false;  // чи реле зараз увімкнене таймером
static uint32_t relay_off_at = 0;      // МИТЬ (за HAL_GetTick), коли треба вимкнути

// Увімкнути реле рівно на duration_ms мілісекунд.
void relay_on_for(uint32_t duration_ms) {
    HAL_GPIO_WritePin(RELAY_PORT, RELAY_PIN, RELAY_ON);
    relay_active = true;
    relay_off_at = HAL_GetTick() + duration_ms;   // коли гасити
}

// Викликати В КОЖНОМУ проході циклу: сам вимкне, коли час вийде.
void relay_tick(void) {
    // HAL_GetTick() — 32 біти, тож та сама поправка на переповнення, що й нижче.
    if (relay_active && (int32_t)(HAL_GetTick() - relay_off_at) >= 0) {
        HAL_GPIO_WritePin(RELAY_PORT, RELAY_PIN, RELAY_OFF);
        relay_active = false;
    }
}

int main(void) {
    HAL_Init();
    SystemClock_Config();
    __HAL_RCC_GPIOB_CLK_ENABLE();

    HAL_GPIO_WritePin(RELAY_PORT, RELAY_PIN, RELAY_OFF);
    GPIO_InitTypeDef gpio = { .Pin = RELAY_PIN, .Mode = GPIO_MODE_OUTPUT_PP,
                              .Pull = GPIO_NOPULL, .Speed = GPIO_SPEED_FREQ_LOW };
    HAL_GPIO_Init(RELAY_PORT, &gpio);
    relay_on_for(5000);               // клацнули увімкнене на 5 секунд

    while (1) {
        relay_tick();                 // стежить за часом, не блокуючи
        // ...сюди можна дописати будь-що: кнопки, давачі, індикатор —
        //    усе працює, поки реле відлічує свої 5 секунд.
```

Різниця з `delay` принципова. У блокуючому варіанті плата **спала** й була глухою всі п'ять секунд. Тут головний цикл (`loop()` у скетчі, `while (1)` в `app_main`/`main`) пролітає тисячі разів на секунду; `relayTick()` щоразу лише кидає погляд на годинник — і майже завжди нічого не робить, поки не настане мить `relayOffAt`. Увесь інший час цикл вільний для решти справ. Це фундамент будь-якого неіграшкового скетчу: не «зробити й заснути», а «завести й перевіряти».

Один тонкий момент вартий уваги — порівняння `(long)(millis() - relayOffAt) >= 0`. Будь-який 32-бітний лічильник мілісекунд — і `millis()`, і `HAL_GetTick()` — беззнаковий і **переповнюється** (обнуляється) приблизно за 49 діб безперервної роботи. Наївне `millis() >= relayOffAt` зламалося б у мить переповнення. А різниця `millis() - relayOffAt`, зведена до знакового типу тієї ж ширини, лишається коректною **навіть через переповнення**: доки різниця від'ємна — час не настав, стала невід'ємною — пора гасити. Це стандартний прийом беззнакової арифметики часу; той самий, на якому тримається все планування за лічильником тиків. (64-бітному лічильнику ESP-IDF ця поправка не потрібна взагалі — він не переповниться за час життя пристрою.)

> 🔧 **Навіщо це.** «Увімкнути на N секунд» — найчастіша задача реле (полити N секунд, продути N секунд, тримати замок відчиненим N секунд). І майже кожен новачок пише її через `delay`, а потім дивується, чому кнопка «стоп» не працює під час поливу — та ж плата спить. Виносьте час у `millis()`-таймер від самого початку: коштує це кількох зайвих рядків, зате пристрій лишається живим і керованим, поки реле робить своє. Глибше про неблокуючий стиль і чому `delay` — ворог живого пристрою: [точний час на millis()](topic:programming/millis-micros).

## Крок 4: захист від деренчання — не дати реле клацати надто часто

Третя грабля найпідступніша, бо код при ній виглядає бездоганно. Уявіть, що реле вмикається за подією — натиском кнопки, порогом давача, командою по мережі. І уявіть, що подія «тремтить»: кнопка деренчить контактами, давач балансує на самому порозі (то трохи вище, то трохи нижче), команди сиплються пачкою. Наївний код слухняно перемикає реле на кожну зміну — і реле починає **тарахкотіти**, клацаючи десятки разів на секунду. Це чути (реле трясе), це шкодить (механіка зношується), а на межевому навантаженні це ще й **іскрить контакти в порох**.

Тут стикаються два різні захисти, і їх легко сплутати. Перший — **усунення деренчання входу** (debounce): фільтруємо тремтіння самого сигналу, щоб один фізичний натиск дав рівно одну команду. Другий — **обмеження частоти перемикань реле** (rate-limit): навіть якщо команди легітимні, не даємо реле клацати частіше, ніж, скажімо, раз на пів секунди, бережучи механіку. Потрібні обидва, і вони працюють на різних кінцях: debounce чистить **вхід**, rate-limit береже **вихід**.

Почнімо з debounce для кнопки. Механічна кнопка не замикається чисто — пружні пластинки в мить контакту кілька мілісекунд деренчать, замикаючись і розмикаючись десятки разів. Контролер на десятки МГц бачить кожне тремтіння як окремий натиск. Фільтр простий: помітивши зміну сирого читання, **перезапускаємо таймер тиші**, і віримо новому стану лише коли він протримався незмінним довше за поріг деренчання.

:::tabs
```arduino
const uint8_t PIN_BTN   = 2;      // кнопка між ніжкою і землею
const uint8_t PIN_RELAY = 7;

const bool ACTIVE_LOW = true;
inline void relayWrite(bool on) {
    digitalWrite(PIN_RELAY, (on ^ ACTIVE_LOW) ? HIGH : LOW);
}

bool          relayState  = false;    // логічний стан реле, який перемикаємо
bool          lastReading = HIGH;     // попереднє СИРЕ читання кнопки (спокій = HIGH)
bool          btnStable   = HIGH;     // стан, у який кнопка вже устоялась
unsigned long lastEdge    = 0;        // коли сире читання востаннє смикнулось
const unsigned long DEBOUNCE_MS = 25; // «тиша» довша за деренчання (кілька мс)

void setup() {
    relayWrite(false);
    pinMode(PIN_RELAY, OUTPUT);
    pinMode(PIN_BTN, INPUT_PULLUP);   // спокій = HIGH, натиск замикає в LOW
}

void loop() {
    bool reading = digitalRead(PIN_BTN);

    if (reading != lastReading) {     // сире читання смикнулось — перезапуск відліку
        lastEdge = millis();
        lastReading = reading;
    }

    // Читання протрималось довше за DEBOUNCE і це НОВИЙ устояний стан?
    if ((millis() - lastEdge) > DEBOUNCE_MS && reading != btnStable) {
        btnStable = reading;
        if (btnStable == LOW) {       // саме натиск (не відпускання)
            relayState = !relayState; // один клац кнопки = одне перемикання реле
            relayWrite(relayState);
        }
    }
}
```

Ідея: сире читання може деренчати скільки завгодно — щоразу, як воно смикнулось, ми скидаємо таймер. Лише коли читання встояло довше за `DEBOUNCE_MS` (25 мс — з добрим запасом над типовими кількома мілісекундами деренчання), ми віримо, що стан справжній, ловимо перехід у `LOW` (реальний натиск) і аж тоді перемикаємо реле. Один фізичний клац кнопки дає рівно одне клацання реле — не вісім.

Але debounce чистить лише вхід-кнопку. А що, як реле керується давачем, який балансує на порозі, — або кнопкою, яку тиснуть по-справжньому швидко, — і реле все одно ризикує тарахкотіти? Тоді додаємо **другий бар'єр на самому виході**: не даємо реле перемкнутися, якщо від минулого перемикання не минув мінімальний інтервал. Це rate-limit, і він захищає механіку незалежно від того, наскільки «чистий» вхід.

:::tabs
```arduino
unsigned long lastSwitch = 0;              // мить минулого РЕАЛЬНОГО перемикання реле
const unsigned long MIN_INTERVAL_MS = 500; // реле не клацає частіше ніж раз на 0.5 с

// Безпечне перемикання: пропустить, лише якщо минув мінімальний інтервал.
// Повертає true, якщо перемикання відбулося.
bool relaySwitch(bool on) {
    if (on == relayState) return false;               // уже в цьому стані — нічого не робимо
    if ((millis() - lastSwitch) < MIN_INTERVAL_MS)    // ще рано перемикати
        return false;
    relayState = on;
    relayWrite(on);
    lastSwitch = millis();
    return true;
}
```

Тепер, замість смикати `relayWrite` напряму, весь код проходить крізь `relaySwitch`. Два ефекти зразу: по-перше, повторна команда «увімкнути», коли реле вже увімкнене, нічого не коштує (перший `return` відсікає зайве клацання); по-друге, навіть шквал легітимних команд не змусить реле перемикатися частіше ніж раз на пів секунди — механіка захищена. Давач, що тремтить на порозі, більше не вводить реле в тарахкотіння: між клацаннями фізично мусить минути `MIN_INTERVAL_MS`.

> 🔧 **Навіщо це.** `DEBOUNCE_MS = 25` і `MIN_INTERVAL_MS = 500` — числа з різних світів, і плутати їх не можна. Перше — **мілісекунди**, бо деренчання контактів триває одиниці мілісекунд; візьмеш 2–3 мс — деренчання подекуди проскочить, візьмеш 300 мс — швидкі натиски губитимуться. Друге — **пів секунди й більше**, бо береже не логіку, а метал: реле фізично встигає перемкнутися за ~15 мс, але клацати його частіше кількох разів на секунду означає стрімко палити ресурс контактів (чому саме — нижче). Debounce робить один натиск одним; rate-limit не дає навіть правильним натискам вбити реле поспіхом.

## Складність і пастки: де цей «простий» код підводить

Код вище робочий, але за ним стоять кілька суворих обмежень заліза, яких жоден рядок не скасує. Розберемо три головні пастки — саме на них перетворюється «просто увімкни реле» в реальному пристрої.

### Пастка перша: механічний ресурс — чому не можна смикати реле в циклі

Найспокусливіша помилка — керувати реле так, ніби це світлодіод: вмикати-вимикати в кожному проході головного циклу, або гнати на нього ШІМ для «плавного» керування потужністю. Реле цього **не переживе**, і причина суто механічна: усередині фізичний якір фізично б'ється об осердя щоразу, коли реле спрацьовує. Це метал об метал, і він зношується.

Порахуймо ресурс чесно, за даташитом Songle SRD-05VDC. Виробник дає дві різні цифри, і різниця між ними — ключова:

```
механічний ресурс (без навантаження):  ~10 000 000 спрацювань  (10⁷)
електричний ресурс (під повним струмом): ~100 000 спрацювань     (10⁵)
```

Різниця у **сто разів** не випадкова. Механічна межа 10⁷ — це коли контакти просто перекидаються «на холосту», без струму: зношується лише шарнір і пружина. А електрична межа 10⁵ — це коли контакти розмикають **реальний струм під напругою**: у мить розриву між ними спалахує мікродуга, яка щоразу випалює крихту металу з контакту. Сто тисяч розривів під струмом — і контакти вигоряють, починають залипати або не проводити.

Тепер відчуйте масштаб на прикладі. Уявіть код, який помилково перемикає реле під навантаженням раз на секунду:

**Умова:** реле клацає раз на секунду під струмом; електричний ресурс 100 000 циклів.

```
циклів на добу = 60 · 60 · 24 = 86 400 клацань/добу
ресурс         = 100 000 циклів
строк служби   = 100 000 / 86 400 ≈ 1.16 доби
```

**Висновок:** трохи більше **доби** — і реле мертве. Не роки, не місяці — доба. А та сама помилка з ШІМ (сотні перемикань на секунду) вбиває реле за **хвилини**. Ось чому реле категорично не для ШІМ і не для швидкого мигтіння: його стихія — вмикати й вимикати **надовго**, годинами й днями, а не деренчати в циклі. Для швидкого перемикання потужності беруть **напівпровідниковий ключ** — MOSFET або твердотільне реле (SSR), де перемикає не метал, а електрони, і ресурс практично безмежний.

Саме заради цієї пастки в кроці 4 стоїть `MIN_INTERVAL_MS`: він — не косметика, а буквально різниця між реле, що служить роками, і реле, що згоряє за добу через випадкове тарахкотіння в коді.

> 🔧 **Навіщо це.** Порахуйте бюджет клацань для СВОГО застосування, перш ніж писати логіку. Термостат, що вмикає нагрівач кілька разів на годину, — це ~30–50 клацань на добу, і навіть електричні 100 000 циклів дадуть роки служби. А ось «стежити за рівнем і клацати помпу щоразу, як давач перетнув поріг» без rate-limit — це шлях до реле, вбитого за тиждень тремтінням на порозі. Правило: **реле любить рідкісні, свідомі, тривалі перемикання**; усе, що частіше кількох разів на хвилину під навантаженням, — привід або поставити гістерезис у код, або взяти SSR/MOSFET замість електромеханіки.

### Пастка друга: старт мікроконтролера — ESP32 і його «стрибучі» ніжки

Крок 1 прибирає клац на старті **на боці нашого коду** — але на ESP32 є ще одна, апаратна причина клацання, якої `pinMode`-порядком не побороти. Деякі ніжки ESP32 — так звані **завантажувальні** (strapping) виводи — у мить подання живлення чип **сам** протягує в певний рівень, ще до того як виконається перший рядок вашого скетчу. І гірше: під час завантаження окремі ніжки на коротку мить **стрибають** з 0 на 3.3 В, бо чип читає ними режим старту.

Це підтверджена, добре задокументована поведінка: на ESP32 деякі GPIO при старті чи скиданні коротко змінюють рівень або навіть видають імпульси ШІМ, і реле, почеплене на таку ніжку, **тимчасово вмикається** незалежно від вашого коду ([Random Nerd Tutorials](https://randomnerdtutorials.com/esp32-pinout-reference-gpios/), [ESP32 strapping pins guide](https://www.espboards.dev/blog/esp32-strapping-pins/)). Найвідоміші проблемні — GPIO0, GPIO2, GPIO12, GPIO15 (і на різних варіантах — свій набір). Наш безпечний порядок ініціалізації тут безсилий, бо стрибок стається **до** `setup()`.

Лікується це двома способами, і найкраще — обома разом:

```cpp
// 1) НЕ вішати реле на завантажувальні ніжки ESP32.
//    Безпечні для реле виводи: 13, 14, 16, 17, 25, 26, 27, 32, 33.
const uint8_t PIN_RELAY = 25;    // а НЕ 0/2/12/15

// 2) Зовнішня підтяжка у ВИМКНЕНИЙ рівень прямо на платі:
//    для active-low модуля — резистор 10 кОм від IN до 3.3 В.
//    Тоді навіть коли ніжка «висить» під час старту чипа,
//    IN фізично тримається у HIGH (вимкнено), і реле не клацає.
```

Перший захід — вибір ніжки — прибирає саму причину: на «спокійних» виводах (13, 14, 25, 26, 27, 32, 33) чип нічим не стрибає при старті, і реле поводиться передбачувано. Другий — зовнішній резистор-підтяжка 10 кОм від `IN` до живлення силового боку — страхує на випадок, коли вибору нема: він фізично тримає лінію у вимкненому рівні весь час, поки ніжка контролера ще не взяла її під контроль. Разом вони закривають ту частку клацань, до якої код просто не встигає.

> 🔧 **Навіщо це.** Це та пастка, що змушує людей писати «ESP32 випадково вмикає реле при кожному ввімкненні, хоча код правильний». Код і справді правильний — винен вибір ніжки. На Arduino UNO/Nano ця проблема майже не проявляється (там ніжки при старті просто входи), а на ESP32 вона типова саме на популярних GPIO0/2. Перше, що треба зробити на ESP32 з реле, — **свідомо вибрати вивід зі списку безпечних**, а не хапати перший-ліпший; це дешевше за будь-який резистор і прибирає більшість клацань одразу.

### Пастка третя: active-high варіанти й розводка живлення при знятій перемичці

Дві менші, але дошкульні пастки наостанок.

**Не кожен модуль active-low.** Ми будували код навколо `ACTIVE_LOW = true`, бо такий типовий модуль з оптопарою. Але трапляються модулі **активні одиницею**: голі транзисторні плати без оптопари (стилю KY-019), деякі релейні шилди, окремі модулі з перемичкою вибору полярності. Симптом невідповідності однозначний: реле вмикається, **коли ви його вимикаєте**, і навпаки. Не шукайте помилку в паянні — просто змініть `ACTIVE_LOW` на `false`, і завдяки інкапсуляції з кроку 2 весь код одразу почне поводитися правильно. Золоте правило: **перевірте полярність на столі перед написанням логіки** — подайте на `IN` нуль і послухайте, чи клацнуло. Клацнуло при нулі — active-low; при одиниці — active-high.

**Знята перемичка `JD-VCC` живить силовий бік окремо — і код мусить це враховувати.** Коли ви знімаєте перемичку `JD-VCC` заради справжньої гальванічної розв'язки, силовий бік (котушки реле) починає живитися **від окремого 5-вольтового блока**, а не від контролера. Це нічого не змінює в самому коді керування (ніжка `IN` так само притягує лінію в нуль чи одиницю), але додає фізичну умову, про яку код мовчки покладається: **окреме живлення силового боку мусить бути подане**. Розводка при знятій перемичці така:

```
Логічний бік (керування):
  VCC модуля   ──── 5V контролера   (або 3.3V — світлодіод оптопари засвітиться й від 3.3 В)
  IN           ──── GPIO
  GND (логіки) ──── GND контролера

Силовий бік (котушки), ОКРЕМЕ джерело:
  JD-VCC       ──── +5V окремого блока живлення
  GND (сили)   ──── GND того ж окремого блока
  ⚠ земля логіки й земля сили НЕ з'єднані — у цьому й суть розв'язки
```

Пастка тут програмно-фізична: якщо код вважає, що «виставив LOW — реле увімкнулось», а окремий блок на `JD-VCC` не поданий (забули ввімкнути, просів, відвалився), — реле **не спрацює взагалі**, хоч логіка бездоганна. Оптопара засвітиться, а котушці нема від чого живитися. Тому в пристрої з розв'язаним живленням варто або **контролювати наявність силового живлення** окремою лінією, або принаймні тримати в голові, що «команда пішла» і «реле спрацювало» — тепер дві різні події, між якими стоїть окреме джерело. За накинутої перемички ця пастка зникає (обидва боки живляться разом), але зникає й справжня ізоляція — і це вже свідомий компроміс, а не дрібниця.

> 🔧 **Навіщо це.** Найковарніший баг розв'язаної схеми — «вчора працювало, сьогодні ні, код не чіпав». Часто це просто непідключений або просілий блок `JD-VCC`: логіка шле команди, оптопара кліпає світлодіодом, а реле мовчить, бо котушці нема струму. Коли знімаєте перемичку заради ізоляції — закладайте в голову (а краще в код, окремою лінією контролю), що силове живлення тепер **незалежне** й може відпасти окремо від логіки. Розв'язка захищає контролер від шуму реле, але ціна — ще одна точка відмови, за якою треба стежити.

## Що забрати з собою

Керування реле-модулем у коді не потребує жодної бібліотеки — це звичайний цифровий вихід. Уся складність — не в програмному інтерфейсі, а в трьох звичках, без яких «простий» код псує залізо або підкидає примарні баги.

Перше — **порядок ініціалізації**: виставте вимкнений рівень (`HIGH` для active-low) на ніжку **до** того, як вона стане виходом (`pinMode(OUTPUT)`, `gpio_config()`, `HAL_GPIO_Init()` — назва різна, правило одне), інакше реле клацне саме собою в мить старту плати. Друге — **полярність**: типовий модуль активний нулем, тож заховайте інверсію в дві функції `relayOn()`/`relayOff()` через одну сталу `ACTIVE_LOW`, і код перестане плутати `HIGH` з увімкненням, а перехід на active-high модуль стане правкою одного рядка. Третє — **бережіть механіку**: реле має скінченний ресурс (~100 000 перемикань під навантаженням — це доба клацань раз на секунду), тому таймер робіть на лічильнику мілісекунд, а не на блокуючій паузі (щоб плата не глухла), кнопку фільтруйте від деренчання, а сам вихід обмежуйте частотою (`MIN_INTERVAL_MS`), щоб тремтіння на вході не спалило контакти.

Складіть ці три звички — і той самий код, що вмикав світлодіод, надійно керуватиме помпою, нагрівачем чи замком роками, а не тижнями. А коли задача вимагає швидкого перемикання потужності — пам'ятайте головну межу реле: воно для рідкісних, свідомих, тривалих клацань; усе швидше віддавайте напівпровіднику.
