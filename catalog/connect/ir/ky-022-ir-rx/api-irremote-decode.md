# 📋 api: бібліотека IRremote 4.x — контракт читання ІЧ-пульта

Приймач на платі віддає на вивід S чисту, але «сиру» обвідну: спокій тримається на «1», а кожна 38-кілогерцова пачка від пульта притискає лінію в «0». Перетворити ці довжини нулів і одиниць на осмислене «яку кнопку натиснули» руками — марудно й крихко: пультів багато, форматів пачок (NEC, Sony SIRC, RC5, Samsung, Panasonic…) — ще більше, у кожного своя таблиця. Для Arduino цим займається бібліотека **IRremote**. Тут — **контракт її сучасної гілки 4.x**: які виклики, які поля, які прапорці вона виставляє і які граблі ховає її будова. Не переказ статті про плату, а довідник, куди заглядають, коли пишуть код.

Увесь контракт стоїть на трьох викликах, решта — деталі навколо них:

```cpp
IrReceiver.begin(pin, ENABLE_LED_FEEDBACK);   // 1. увімкнути приймач на піні
IrReceiver.decode()                           // 2. чи прийшов і розпізнався кадр?
IrReceiver.decodedIRData                      //    ← сюди складено результат
IrReceiver.resume();                          // 3. звільнити приймач під наступний
```

## Підключення заголовка

```cpp
#include <IRremote.hpp>          // саме .hpp, не .h — і лише в ОДНОМУ файлі
```

У 4.x підключають заголовок з розширенням **`.hpp`** (не старий `.h`), і **лише в одному** `.cpp`-файлі проєкту. Через `.hpp` бібліотека тягне з собою реалізацію, тож якщо вписати цей `include` у два файли — лінкувальник посвариться на дубльовані символи. У простому одно-файловому скетчі це неважливо; у багатофайловому проєкті `#include <IRremote.hpp>` разом із конфігурацією тримають в одному модулі, решта користується оголошеннями.

## `begin()` — запуск приймача

```cpp
void IrReceiver.begin(uint8_t pin, bool enableLEDfeedback);
```

| Аргумент | Що це |
|---|---|
| `pin` | цифровий пін, на якому висить вивід S приймача |
| `enableLEDfeedback` | `ENABLE_LED_FEEDBACK` — на кожен спійманий кадр коротко світити вбудованим світлодіодом плати (на Uno — LED на D13), як «ознака життя»; `DISABLE_LED_FEEDBACK` — вимкнути це |

Службовий блимавчик `ENABLE_LED_FEEDBACK` — це вбудований LED **плати-мікроконтролера**, а не світлодіод на самій платі KY-022 (той керується апаратно, самим приймачем, і блимає незалежно від коду).

## Цикл читання: `decode()` → поля → `resume()`

Контракт приймання — три дії за оборот циклу:

```cpp
if (IrReceiver.decode()) {           // є готовий кадр?
  // … читаємо IrReceiver.decodedIRData …
  IrReceiver.resume();               // звільнити буфер під наступний кадр
}
```

**`bool IrReceiver.decode()`** повертає `true` рівно тоді, коли у фоновому буфері зібрався цілий кадр (і його або розпізнано, або визнано `UNKNOWN` — але кадр цілий). Поки пульт мовчить — `false`, і цикл біжить далі без затримок. Приймач не опитують байт за байтом: при `begin()` бібліотека вішається на пін через переривання, у фоні заміряє тривалості пачок і пауз, а `decode()` лише забирає готове.

**`void IrReceiver.resume()`** — обов'язковий виклик після кожного `decode() == true`. Доки ти його не викликав, бібліотека вважає, що ти ще не дочитав поточний кадр, і **не звільняє буфер** під новий — `decode()` повертатиме `false` вічно, приймач ніби «оглухне» після першого ж натиску. Правило: **на кожен `decode()`, що дав `true`, — рівно один `resume()`**, у кінці обробки, після всіх звертань до `decodedIRData`.

> 🔧 **Навіщо це.** Розділення на `decode()` і `resume()` — не примха, а захист від гонки. Поки ти читаєш поля `decodedIRData` (а це може бути кілька повільних рядків друку), у фоні вже може прилетіти наступна пачка. Якби буфер звільнявся автоматично одразу після `decode()`, нова пачка затерла б дані, які ти ще не дочитав. `resume()` — це твоє явне «я забрав усе потрібне, тепер можна писати новий кадр». Тому його ставлять **після** всіх звертань до `decodedIRData`, а не перед ними.

## `decodedIRData` — результат кадру

Результат у 4.x лежить у полях структури `IrReceiver.decodedIRData` (а **не** в окремому `results`-об'єкті, як у старих версіях):

| Поле | Тип | Що містить |
|---|---|---|
| `.protocol` | enum | розпізнаний протокол: `NEC`, `SONY`, `RC5`, `SAMSUNG`, `PANASONIC`… або `UNKNOWN` |
| `.address` | `uint16_t` | адреса **пристрою** (яка апаратура — щоб чужий пульт не керував твоєю саморобкою) |
| `.command` | `uint16_t` | номер натиснутої **кнопки** |
| `.flags` | бітова маска | прапорці кадру (див. нижче `IRDATA_FLAGS_IS_REPEAT`) |
| `.decodedRawData` | `uint32_t` | «відбиток» кадру — стійке число з сирих тривалостей; заповнене й тоді, коли протокол `UNKNOWN` |

У більшості пультів `.address` стала (це «пристрій такої-то фірми»), а `.command` змінюється від кнопки до кнопки. Допоміжна `IrReceiver.getProtocolString()` віддає людську назву протоколу рядком (напр. `"NEC"`) — зручно для друку.

Важлива приємність: та перевернутість виходу приймача (активний «0», спокій «1») **повністю схована в бібліотеці** — вона знає, що спокій це HIGH, і рахує від цього. Пишеш логіку кнопок, не логіку рівнів.

## Прапорець повтору: `IRDATA_FLAGS_IS_REPEAT`

Коли кнопку **тримають**, пульт не шле повний кадр знову і знову — він шле повний кадр один раз, а далі випускає куций **кадр-повтор** (repeat frame): «та сама кнопка ще тримається», без повторної передачі номера. Бібліотека це розпізнає й піднімає прапорець:

```cpp
if (IrReceiver.decodedIRData.flags & IRDATA_FLAGS_IS_REPEAT) {
  // це кадр-повтор: кнопку тримають, нового натиску НЕ було
}
```

Приємна деталь 4.x: **на кадрі-повторі бібліотека сама відновлює `.address` і `.command` з попереднього кадру** — навіть коли фізично номера в куцому повторі нема, поля містять ту саму кнопку, що й на першому натиску. Тобі не треба пам'ятати «а що там тримали». (Звірено з декодером NEC самої IRremote — статус: підтверджено.)

Часовий бік повтору диктує сам протокол: у NEC перший повтор приходить приблизно через **40 мс** після кінця першого кадру, а далі повтори йдуть із періодом близько **110 мс** (звірено з хронометражем NEC — статус: підтверджено). Що з цим прапорцем робити — відрізняти утримання від натиску, будувати власний автоповтор — це вже застосунок; робочий приклад меню з утриманням — в [окремому проєкті](book:connect/ky-022-ir-rx/proj-irremote-menu.md).

## Невідомий протокол: `protocol == UNKNOWN` і `decodedRawData`

Не всі пульти лягають у відомі протоколи (дешевий пульт із набору, кондиціонер, старий японський апарат). Тоді `decode()` усе одно поверне `true`, але `decodedIRData.protocol` дорівнюватиме **`UNKNOWN`** — і поля `.command` та `.address` **не мають сенсу** (не заповнені осмислено). Перевіряти цей стан обов'язково, інакше `switch (command)` ловитиме шум і «привидів»:

```cpp
if (IrReceiver.decodedIRData.protocol == UNKNOWN) {
  Serial.println("протокол не впізнано");
  IrReceiver.printIRResultRawFormatted(&Serial, true);   // дамп сирих тривалостей
}
```

Для нерозпізнаних кадрів усе одно доступне поле **`.decodedRawData`** — стійкий відбиток форми кадру. Різні кнопки дають різні відбитки, тож навіть без розбору протоколу можна **відрізнити кнопку А від кнопки Б** за цим числом (метод грубий — відбиток чутливий до шуму, повтори можуть давати інший хеш, — але для «увімкнути з будь-якого пульта під рукою» часто досить). Функція `printIRResultRawFormatted(&Serial, true)` вивалює в монітор сирий портрет кадру — послідовність тривалостей «мітка/пробіл» у мікросекундах — головний інструмент діагностики незнайомого пульта.

## Мінімальний робочий приклад

Кістяк, що ловить будь-який натиск і друкує його в монітор порту, — від нього відштовхуються всі складніші версії:

```cpp
#include <IRremote.hpp>          // IRremote 4.x

const uint8_t IR_PIN = 2;        // вивід S модуля KY-022 → D2

void setup() {
  Serial.begin(115200);
  IrReceiver.begin(IR_PIN, ENABLE_LED_FEEDBACK);   // старт приймача
}

void loop() {
  if (IrReceiver.decode()) {                        // прийшов і розпізнався кадр?
    Serial.print("протокол: ");
    Serial.print(IrReceiver.getProtocolString());   // напр. "NEC"
    Serial.print("  адреса: 0x");
    Serial.print(IrReceiver.decodedIRData.address, HEX);
    Serial.print("  команда: 0x");
    Serial.println(IrReceiver.decodedIRData.command, HEX);
    IrReceiver.resume();                            // ГОТОВІ приймати наступний
  }
}
```

## Сумісність версій: 4.x проти 2.x/3.x

Половина старих туторіалів в інтернеті написана під IRremote 2.x/3.x, і їхній код у 4.x **не компілюється**. Головні відмінності:

| Старе (2.x/3.x) | 4.x |
|---|---|
| `IRrecv irrecv(RECV_PIN)` + `irrecv.enableIRIn()` | `IrReceiver.begin(pin, …)` |
| `decode(&results)` | `IrReceiver.decode()` (без аргументу) |
| результат у `results.value` | поля `IrReceiver.decodedIRData.command` / `.address` |
| `#include <IRremote.h>` | `#include <IRremote.hpp>` |

Побачив у чужому коді `results`, `decode(&results)`, `RECV_PIN`, `enableIRIn()` — це давня гілка; перекладай на 4.x, не змішуй версії.

## Апаратний таймер і конфлікти

За фонові виміри пульта відповідає **апаратний таймер**, який бібліотека забирає собі й ні з ким не ділить — звідси головний клас «магічних» багів.

- **AVR (Uno, Nano, ATmega328).** Виміри йдуть через апаратний таймер (типово Timer 2), а сам пін сигналу — будь-який цифровий.
- **ESP32** ([родина ESP32/ESP8266](book:boards/esp32-family)). Приймання веде апаратний таймер (`hw_timer_t`), тому вивід приймача можна повісити майже на **будь-який GPIO** — обмеження ставить розводка плати (уникай пінів «тільки вхід» без підтяжки й службових пінів завантаження), а не бібліотека. (Звірено з README IRremote — статус: підтверджено; конкретний таймер залежить від версії ядра ESP32.)

**Конфлікт таймерів — тиха біда.** Будь-яка інша бібліотека, що претендує на той самий таймер, увійде в конфлікт **без явної помилки** — просто щось із двох перестане працювати. Класичні суперники на AVR:

- **`Servo`** — теж любить Timer 1/2: серво починає смикатися або приймач глухне;
- **`tone()`** — генерує звук через таймер: поки грає нота, приймання «сліпне»;
- **`analogWrite()` (ШІМ)** на певних пінах — ті самі таймери керують ШІМ.

Симптом характерний: **усе працює, поки не задіяв другу периферію** — увімкнув серво, і пульт перестав читатися; заграв `tone()`, і кадри почали губитися. Ліки: рознось периферію по різних таймерах (у README IRremote є таблиця «таймер на плату»), або, якщо таймерів не вистачає, бери плату, де їх більше (ESP32, Teensy).

> 🔧 **Навіщо це.** Головна причина «магічних» багів IRremote — саме невидимий конфлікт таймерів, а не сам приймач. Приймач простий: три дроти, і фізику видно по блимавчику. Але щойно в проєкті з'являється другий претендент на таймер (серво, ШІМ-мотор, звук), поведінка стає плаваючою й ніби безпричинною. Плануючи проєкт із пультом, **першою думкою** тримай: який таймер забере IRremote на моїй платі й з ким він за нього битиметься.

## Пастки API-рівня — коротко

- **Забутий `resume()`** — приймач оглухне після першого кадру (`decode()` вічно `false`). На кожен `decode() == true` — рівно один `resume()`, у тому числі коли свідомо викидаєш чужий кадр перед `return`.
- **`switch (command)` без перевірки `UNKNOWN`** — ловить незаповнені поля й шум; спершу відсій `protocol == UNKNOWN`.
- **Старий API** (`results`, `decode(&results)`, `RECV_PIN`, `enableIRIn()`) — це 2.x/3.x; переклади на 4.x.
- **`.h` замість `.hpp`** або `include` у двох файлах — дубльовані символи в лінкувальника.
- **Конфлікт таймерів** — невидимий; плануючи проєкт із пультом, тримай у голові, який таймер забере IRremote й з ким битиметься.
