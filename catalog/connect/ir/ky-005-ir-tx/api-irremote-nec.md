# 📋 IRremote для KY-005: підключення, виклики send*, карта пасток

<preknowlist>
- [Модуляція несучої 38 кГц](book:communications/carrier-ir-modulation) — біт «одиниця» — це не постійне світло, а пачка мигання на 38 кГц; приймач ловить лише цю частоту.
- [GPIO — цифровий вивід](book:electronics/gpio) — бібліотека керує світлодіодом, смикаючи один цифровий вивід у нулі й одиниці десятки тисяч разів на секунду.
</preknowlist>

Керувати KY-005 напряму, вручну виставляючи вивід у високий і низький рівень за таймінгами протоколу, теоретично можна — але це те саме, що писати драйвер відеокарти, коли треба лише намалювати вікно. Пачку несучої 38 кГц довелося б формувати вручну з точністю до мікросекунд, рахувати довжини бітів NEC, вставляти інверсні байти для перевірки. Усе це вже написано, вилизано за півтора десятиліття й лежить в одній бібліотеці — **IRremote**. Автор — Кен Шеріфф (Ken Shirriff), який виклав першу версію 2009 року й донині веде дуже читаний блог про реверс-інжиніринг заліза; статус авторства — усталений, бібліотека є фактичним стандартом ІЧ на Arduino. Ця довідка — про інтерфейс бібліотеки з боку передавача: які виклики є, що означають їхні аргументи й де на них найчастіше спотикаються.

Розберемо те, чого не видно з короткого прикладу «шлемо NEC раз на секунду»: **як бібліотека взагалі мусить бути підключена в актуальній четвертій версії** (тут ламаються найчастіше), **чому саме вивід 3 на Arduino Uno** (це не примха, а прямий наслідок того, як влаштований апаратний таймер), **як виглядають виклики `send*`** для NEC та інших протоколів і **де найчастіше гальмує передача**. А закінчений сценарій, заради якого KY-005 і беруть найчастіше, — зняти код рідного пульта й повторити його, зробивши плату точним клоном, — винесено в окремий проєкт: [клон пульта на KY-005](book:connect/ky-005-ir-tx/proj-clone-remote.md).

## Підключити бібліотеку: `.hpp`, а не `.h` — і чому це не одруківка

Перше, на чому спотикаються майже всі, хто вчився за старими прикладами з інтернету: у сучасній IRremote (гілка **4.x**) підключати треба саме заголовок з розширенням `.hpp`, а не звичний `.h`:

```arduino
#include <IRremote.hpp>   // ПРАВИЛЬНО у 4.x — саме .hpp
// #include <IRremote.h>  // старий стиль 2.x — у 4.x так робити НЕ можна
```

Це не косметична дрібниця, і варто розуміти, звідки вона. Бібліотека, щоб працювати швидко на слабких восьмибітних мікроконтролерах, компілює свій код прямо у ваш скетч, а не лежить окремим заздалегідь зібраним модулем. Файл `.hpp` містить і оголошення, і саму реалізацію. Тому **`IRremote.hpp` можна підключати рівно в одному файлі проєкту** — тому, де ви налаштовуєте відправлення чи приймання. Якщо підключити його у двох файлах, лінкувальник поскаржиться, що ті самі функції визначені двічі. Старий `IRremote.h` у четвертій версії лишили тільки як заглушку, яка видасть попередження й спрямує вас на `.hpp`.

Звідси ж — головна причина, чому чужий приклад з мережі «не збирається»: він написаний під версію 2.x або 3.x, де і заголовок інший, і виклики звалися по-іншому. Перш ніж копіювати код, гляньте на дату й на те, що там підключають.

> 🔧 **Навіщо знати про версії, а не просто ставити «найновішу».** Бо API між великими версіями змінювався **несумісно**, і саме на цьому губиться найбільше часу. Показова пастка приймання: у 2.x приймали кадр через `irrecv.decode(&results)` і читали `results.value`; у 4.x це `IrReceiver.decode()` без аргументу, а дані лежать у полях `IrReceiver.decodedIRData.address` і `.command`. Скопіюєте половину прикладу зі старої версії, половину з нової — і воно не збереться або тихо поверне сміття. Правило просте: **весь приклад — з однієї версії**, і бажано з офіційного `README` актуальної гілки, а не з випадкового блогу трирічної давнини.

Хай яке залізо під рукою, далі йдуть дві однакові справи: сказати, **на якому виводі** висить сигнальний пін вашого KY-005 (той самий S, підключений **через резистор**), і завести на цьому виводі **несучу 38 кГц** силами апаратури. Сама IRremote живе в Arduino-середовищі; поза ним ту саму роботу роблять штатні вузли чипа — у ESP-IDF це RMT, у STM32 канал ШІМ таймера:

:::tabs
```arduino
void setup() {
    IrSender.begin(3);   // вивід 3 — сюди через резистор іде пін S модуля
}
```
```esp-idf
#include "driver/rmt_tx.h"

static rmt_channel_handle_t chan;              // канал RMT — «магнітофон» таймінгів

void ir_begin(int gpio) {                      // вивід будь-який вільний
    rmt_tx_channel_config_t cfg = {
        .clk_src = RMT_CLK_SRC_DEFAULT,
        .gpio_num = gpio,
        .resolution_hz = 1000000,              // 1 тік = 1 мкс
        .mem_block_symbols = 64,
        .trans_queue_depth = 4,
    };
    ESP_ERROR_CHECK(rmt_new_tx_channel(&cfg, &chan));

    rmt_carrier_config_t carrier = {           // несучу домішує сама апаратура
        .frequency_hz = 38000,
        .duty_cycle = 0.33,
    };
    ESP_ERROR_CHECK(rmt_apply_carrier(chan, &carrier));
    ESP_ERROR_CHECK(rmt_enable(chan));
}
```
```stm32
#include "stm32f4xx_hal.h"

TIM_HandleTypeDef htim3;                       // TIM3_CH1 виведений на PA6

void ir_begin(void) {                          // несуча — канал ШІМ таймера
    __HAL_RCC_TIM3_CLK_ENABLE();
    htim3.Instance = TIM3;
    htim3.Init.Prescaler = 0;                          // таймер тактується 84 МГц
    htim3.Init.Period = 84000000 / 38000 - 1;          // ≈ 2210 → 38 кГц
    htim3.Init.CounterMode = TIM_COUNTERMODE_UP;
    HAL_TIM_PWM_Init(&htim3);

    TIM_OC_InitTypeDef oc = {0};
    oc.OCMode = TIM_OCMODE_PWM1;
    oc.Pulse = (htim3.Init.Period + 1) / 3;            // ≈ 1/3 — як світить пульт
    HAL_TIM_PWM_ConfigChannel(&htim3, &oc, TIM_CHANNEL_1);
}
```
:::

`IrSender` — це вже готовий глобальний об'єкт, який бібліотека створює за вас; свій заводити не треба, лише покликати в нього `begin(pin)` з номером виводу. Один цей виклик робить велику роботу: він налаштовує апаратний таймер мікроконтролера так, щоб той сам, без участі процесора, генерував на цьому виводі меандр 38 кГц, коли треба світити. Ось чому номер виводу тут не довільний.

## Чому на Arduino Uno саме вивід 3

Це найчастіше «магічне число» у всій темі, і воно перестає бути магією, щойно зрозуміти, звідки береться несуча.

Пригадаймо суть: щоб приймач нас почув, світлодіод має не горіти рівно, а **мигати на 38 кГц** увесь час, поки триває «одиничний» імпульс коду. Мигати 38 тисяч разів на секунду, смикаючи вивід із програми в циклі, восьмибітний AVR на 16 МГц фізично не встигав би робити стабільно — між іншими справами таймінг «плив» би. Тому цю роботу віддають **апаратному таймеру**: спеціальному лічильнику всередині мікроконтролера, який уміє сам перемикати конкретний вивід із заданою частотою, поки процесор зайнятий чимось іншим.

Але апаратний таймер жорстко прив'язаний до конкретних ніжок. На чипі ATmega328, що стоїть в Arduino Uno й Nano, бібліотека за замовчуванням бере **Timer2**, а Timer2 своїм каналом виведення (у документації AVR він зветься **OC2B**) фізично підключений до **виводу 3** плати. Не до довільного — до цього конкретного. Тому вивід 3 на Uno «зашитий» під передавання не примхою автора, а розводкою кремнію: саме туди таймер уміє видавати меандр сам.

```
Arduino Uno / Nano (ATmega328):
  таймер несучої → Timer2
  канал Timer2   → OC2B → фізично це вивід 3
  ⇒ передавач сидить на виводі 3
```

Є й побічний наслідок, про який корисно знати заздалегідь: коли Timer2 забраний під ІЧ, **функція `analogWrite()` на виводах 3 і 11 перестає працювати як завжди**, бо ті виводи тримає той самий таймер. Якщо у вашому проєкті на піні 11 висить, скажімо, ШІМ-регулювання яскравості світлодіода через `analogWrite`, — після `IrSender.begin(3)` воно зламається. Це не баг, а плата за апаратну несучу: один таймер — на одну справу.

На інших платах вивід передавання інший, бо там інша прив'язка таймерів до ніжок:

```
Плата                 Чип            Вивід передавання (за замовч.)
Arduino Uno / Nano    ATmega328      3
Arduino Mega          ATmega2560     9
ESP32                 ESP32          будь-який (несучу дає канал LEDC)
Raspberry Pi Pico     RP2040         будь-який
```

Різниця між AVR і новішими платами (ESP32, Pico) тут принципова. У маленького ATmega несуча жорстко прив'язана до однієї ніжки, бо її дає конкретний таймер. А ESP32 має гнучкий блок ШІМ (LEDC), який можна причепити до **будь-якого** виводу, тож там ви передаєте KY-005 на тому піні, який зручний. Тому «вивід 3» — це правда **лише про Arduino Uno/Nano**; переносячи проєкт на ESP32, номер сміливо міняйте.

> 🔧 **Навіщо це в реальному проєкті.** Знання «несуча = апаратний таймер = конкретний вивід» рятує в двох випадках. Перший: щось на платі раптом перестало ШІМити після додавання ІЧ — ви одразу знаєте винного (таймер), а не годину шукаєте примару. Другий: переносите код з Uno на ESP32 і дивуєтесь, що передавач мовчить на піні 3, — а тепер розумієте, що на ESP32 пін довільний, і просто вказуєте свій у `begin()`.

## Передати команду: `sendNEC` і що таке адреса й команда

Найкоротший робочий передавач шле одну команду й нічого більше. Робота скрізь та сама — завести несучу на виводі, видати кадр, зачекати; різниться лише те, чим кадр складають — готовим викликом бібліотеки чи власним переліком таймінгів:

:::tabs
```arduino
#include <IRremote.hpp>

void setup() {
    IrSender.begin(3);
}

void loop() {
    IrSender.sendNEC(0x00, 0x34, 0);   // адреса 0x00, команда 0x34, 0 повторів
    delay(1000);
}
```
```esp-idf
#include "driver/rmt_tx.h"
#include "freertos/FreeRTOS.h"

static rmt_encoder_handle_t enc;                 // «копія» — шле символи як є
static rmt_symbol_word_t frame[34];

static rmt_symbol_word_t sym(uint16_t on, uint16_t off) {   // пачка / тиша, мкс
    return (rmt_symbol_word_t){ .duration0 = on,  .level0 = 1,
                                .duration1 = off, .level1 = 0 };
}

static void nec_send(uint8_t addr, uint8_t cmd) {
    uint32_t w = addr | (uint32_t)(uint8_t)~addr << 8
               | (uint32_t)cmd << 16 | (uint32_t)(uint8_t)~cmd << 24;
    int n = 0;
    frame[n++] = sym(9000, 4500);                     // преамбула
    for (int i = 0; i < 32; i++, w >>= 1)
        frame[n++] = sym(560, (w & 1) ? 1690 : 560);  // «1» — довша пауза
    frame[n++] = sym(560, 0);                         // стоп-імпульс
    rmt_transmit_config_t tc = { .loop_count = 0 };
    ESP_ERROR_CHECK(rmt_transmit(chan, enc, frame, n * sizeof(frame[0]), &tc));
}

void app_main(void) {
    ir_begin(18);
    rmt_copy_encoder_config_t cc = {};
    ESP_ERROR_CHECK(rmt_new_copy_encoder(&cc, &enc));

    while (1) {
        nec_send(0x00, 0x34);                         // адреса 0x00, команда 0x34
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```
```stm32
// htim3 налаштовано в ir_begin(): TIM3_CH1 = 38 кГц, шпаруватість ≈ 1/3
static void mark(uint16_t us) {                  // пачка несучої
    HAL_TIM_PWM_Start(&htim3, TIM_CHANNEL_1);
    delay_us(us);                                // мікросекундна пауза (DWT або окремий TIM)
    HAL_TIM_PWM_Stop(&htim3, TIM_CHANNEL_1);
}
static void space(uint16_t us) { delay_us(us); } // тиша тієї ж довжини

static void send_nec(uint8_t addr, uint8_t cmd) {
    uint32_t w = addr | (uint32_t)(uint8_t)~addr << 8
               | (uint32_t)cmd << 16 | (uint32_t)(uint8_t)~cmd << 24;
    mark(9000); space(4500);                     // преамбула
    for (int i = 0; i < 32; i++, w >>= 1) { mark(560); space((w & 1) ? 1690 : 560); }
    mark(560);                                   // стоп-імпульс
}

int main(void) {
    HAL_Init();
    ir_begin();
    while (1) { send_nec(0x00, 0x34); HAL_Delay(1000); }
}
```
:::

Розберемо три числа в `sendNEC`, бо саме тут виникає плутанина «а що вписувати».

**Адреса** (перший аргумент) — це «кому». У протоколі NEC кожен тип пристрою має свій ідентифікатор: телевізор певної марки відповідає, скажімо, на адресу `0x04`, а програвач тієї ж марки — на `0x08`. Приймач, який слухає ефір, спершу дивиться на адресу: «це мені?» — і ігнорує кадри з чужою адресою. Тому один пульт може лежати поряд із двома пристроями й не плутати їх: команди йдуть з різними адресами.

**Команда** (другий аргумент) — це «що зробити»: яку кнопку натиснуто. `0x34` — умовно «гучність +», `0x35` — «гучність −», і так далі. Таблиця «кнопка → код» своя в кожного виробника, і саме її ви або шукаєте в довідниках, або [знімаєте з живого пульта](book:connect/ky-005-ir-tx/proj-clone-remote.md).

**Повтори** (третій аргумент) — скільки разів дослати кадр поспіль. Нуль означає «один раз і все». Навіщо взагалі повтори — окрема тонкість, і в ній ховається смішна пастка.

Числа пишуть у шістнадцятковому вигляді (`0x` спереду) не з любові до складності, а тому що так їх видає й показує сам приймач, коли ви знімаєте код, — і так їх наводять у всіх довідниках. Ніщо не заважає написати `sendNEC(0, 52, 0)` десятковими, вийде те саме, але звіряти з таблицями зручніше в hex.

## Утримання кнопки: чому повтор — не просто «слати ще раз»

Здавалося б, щоб «затиснути» кнопку гучності, треба просто слати `sendNEC` у циклі якнайчастіше. Так теж працює, але правильний спосіб інший, і різниця не косметична.

Реальний пульт, коли ви тримаєте кнопку, **не шле повний кадр знову і знову**. Він шле повний кадр **один раз**, а далі, поки кнопка натиснута, випускає короткі **кадри-повтори** — куценькі службові посилки «те саме, що щойно, ще тримаю», без адреси й команди всередині. Так задумано в самому протоколі NEC: повний кадр довгий, гнати його потоком марно, коротка «крапка-повтор» дешевша й швидша. Приймач, отримавши таку крапку, розуміє «попередня команда триває».

Саме для цього — третій аргумент `sendNEC`. Він каже бібліотеці: «пошли повний кадр, а тоді ще стільки-то правильних коротких повторів». Там, де бібліотеки нема, ту крапку-повтор видають самі — і добре видно, з чого вона складається: пачка 9 мс, пауза 2.25 мс, коротка крапка 560 мкс, і жодного біта даних усередині:

:::tabs
```arduino
// затиснути «гучність +» на приблизно пів секунди правильними повторами NEC
IrSender.sendNEC(0x04, 0x34, 4);   // 1 повний кадр + 4 фірмові короткі повтори
```
```esp-idf
static const rmt_symbol_word_t nec_repeat[2] = {
    { .duration0 = 9000, .level0 = 1, .duration1 = 2250, .level1 = 0 },
    { .duration0 = 560,  .level0 = 1, .duration1 = 0,    .level1 = 0 },
};

rmt_transmit_config_t tc = { .loop_count = 0 };
nec_send(0x04, 0x34);                             // 1 повний кадр…
for (int i = 0; i < 4; i++) {                     // …і 4 короткі повтори
    vTaskDelay(pdMS_TO_TICKS(40));                // повтор — кожні 110 мс від початку кадру
    ESP_ERROR_CHECK(rmt_transmit(chan, enc, nec_repeat, sizeof(nec_repeat), &tc));
}
```
```stm32
static void nec_repeat(void) {                    // кадр-повтор: без адреси й команди
    mark(9000); space(2250); mark(560);
}

send_nec(0x04, 0x34);                             // 1 повний кадр…
for (int i = 0; i < 4; i++) {                     // …і 4 короткі повтори
    HAL_Delay(40);                                // повтор — кожні 110 мс від початку кадру
    nec_repeat();
}
```
:::

Пастка ж ось у чім. Якщо замість цього тупо крутити повний кадр у циклі —

```arduino
// ТАК ЗАЗВИЧАЙ НЕ ТРЕБА: кожен раз повний кадр
for (int i = 0; i < 5; i++) { IrSender.sendNEC(0x04, 0x34, 0); delay(40); }
```

— то багато телевізорів сприймуть це не як «утримую гучність», а як **п'ять окремих натискань**: гучність підскочить на п'ять поділок ривком замість плавного наростання. Бо пристрій розрізняє «одне довге натискання» і «серію коротких» саме за тим, ідуть після кадру фірмові короткі повтори чи щоразу приходить новий повний кадр. Тому для утримання — третій аргумент, а не цикл.

Тонкість на завершення теми: є різновид **NEC2**, у якому пульт на утримання шле не короткі крапки, а щоразу повний кадр. Такі пристрої трапляються; якщо приймач уперто не розуміє ваше «утримання» правильними повторами — можливо, він з тих, хто чекає саме повторюваних повних кадрів. Але це виняток; типова NEC-техніка хоче короткі повтори.

## Інші протоколи: NEC — не єдиний у світі

NEC — найпоширеніший, але далеко не єдиний. Sony, Philips, Samsung, багато кондиціонерів — усі говорять по-своєму, і бібліотека вміє більшість. Виклик такий самий за формою, міняється лише назва:

```arduino
IrSender.sendSony(0x1, 0x12, 2, 12);   // Sony SIRC: адреса, команда, повтори, к-сть біт (12/15/20)
IrSender.sendSamsung(0x0707, 0x02, 0);  // Samsung
IrSender.sendRC5(0x00, 0x0B, 0);        // Philips RC5
IrSender.sendNEC(0x04, 0x34, 0);        // NEC — те, що ми вже бачили
```

Sony вимагає ще й четвертий аргумент — **скільки біт** у кадрі (12, 15 чи 20): у SIRC є три різновиди різної довжини, і треба сказати, який саме. Це типовий приклад того, що кожен протокол має свої примхи, і механічно підставляти аргументи від NEC у Sony не можна.

Тут ховається одна з двох найчастіших причин «світлодіод блимає, а приймач глухий», і про неї варто сказати різко: **різні протоколи їздять на різній несучій частоті**. Це не деталь для педантів, це те, що ламає передачу мовчки й без жодної помилки в коді.

```
Протокол        Несуча       Приймач має бути на
NEC             ≈ 38 кГц     38 кГц
Philips RC5/6   ≈ 36 кГц     36 кГц
Sony SIRC       ≈ 40 кГц     40 кГц
```

Тепер згадаймо, як влаштований приймач: усередині нього — вузькосмуговий фільтр, налаштований на **одну** частоту. Приймач на 38 кГц — це фактично «вухо», глухе до всього, крім мигання близько 38 кГц. Пошлете йому Sony на 40 кГц — сигнал промине повз смугу фільтра, і приймач нічого не почує, хоч світлодіод чесно блимав. Практичне правило з вимірів: **розбіжність усього в 2 кГц зрізає дальність приблизно вдвічі**; на 4 кГц дешевий трипіновий приймач часто вже глухне зовсім.

Звідси висновок, який економить години. Коли передаєте на **свій** KY-022/VS1838B, беріть протокол під його частоту (VS1838B — 38 кГц, тобто NEC лягає ідеально). А коли керуєте **справжньою** технікою, підбирайте протокол не навмання: телевізор чекає своєї несучої, і NEC на 38 кГц він або зрозуміє (якщо він NEC-пристрій), або проігнорує (якщо він Sony на 40 кГц). Не вгадуєте протокол — знімаєте його з рідного пульта, і тоді все стає на місця само.

> Чому вузькосмуговий фільтр приймача відсіює все, крім своєї несучої, і чому саме тому передавач і приймач мусять «домовитися» про частоту — розібрано окремо: [модуляція несучої для відсіву перешкод](book:communications/carrier-ir-modulation). Коротко: приймач — це смуговий фільтр на одну частоту, і мимо смуги для нього не існує сигналу.

## Складність і пастки: коротка карта, де гальмує найчастіше

Зберемо в одному місці те, на чому губиться час, — від найчастішого до рідкісного, з механізмом, а не просто «спробуйте те».

**«Не збирається / незнайомі імена».** Майже завжди — мішанина версій. Приклад під 2.x (`IRremote.h`, `irrecv`, `results.value`) не збереться в 4.x. Лік один: увесь код — з `README` актуальної гілки, підключення — `#include <IRremote.hpp>`, і рівно в одному файлі проєкту.

**«Компілюється, світлодіод блимає (перевірили камерою), а приймач мовчить».** Тут два підозрювані, обидва — про несучу й протокол, і жоден не видно в коді:
- *Не та несуча.* Шлете Sony (40 кГц) на приймач 38 кГц — мимо смуги фільтра. Правило: приймач і протокол мусять збігтися по частоті (NEC↔38, RC5↔36, SIRC↔40); 2 кГц різниці — мінус пів дальності.
- *Не той протокол.* Керуєте живою технікою навмання? Вона чекає свого протоколу. Не вгадуєте — знімаєте з рідного пульта ([клон пульта](book:connect/ky-005-ir-tx/proj-clone-remote.md)) і шлете рівно те, що зняли.

**«Світлодіод не блимає навіть на камеру».** Це вже залізо, не код. Найчастіше — **забутий або не туди поставлений резистор**, або переплутані живлення й земля на модулі, або сигнал заведено не на вивід 3 (на Uno). Камера телефону — головний діагност: наведіть її на купол світлодіода під час передачі; блідо-фіолетові спалахи означають «світить, шукай проблему далі по лінії», темрява — «не світить, винне підключення чи резистор». Нагадаю з фізики модуля: KY-005 бере струм світлодіода **прямо з сигнальної ноги**, і без резистора в її розриві вивід або йде в захист (сигнал просідає, кадр псується), або поступово вигорає.

**«Утримання кнопки поводиться як черга натискань».** Ви шлете повний кадр у циклі замість фірмових повторів. Лік — третій аргумент `sendNEC(addr, cmd, N)`, який дошле правильні короткі NEC-повтори; техніка тоді зрозуміє це як одне довге натискання, а не N окремих.

**«Свій приймач розуміє, а телевізор — ні (або навпаки)».** Різні цілі — різні очікування. Ваш VS1838B — 38 кГц і радо їсть NEC; конкретний телевізор може бути Sony на 40 кГц. Не існує одного «універсального» виклику на всі пристрої: під кожну ціль — її протокол і несуча, зняті або відомі, а не вгадані.

**«Дальність — метр, далі не бере».** Це не помилка коду, а межа голого модуля: струм світлодіода обмежений і резистором, і кволим виводом мікроконтролера. IRremote тут ні до чого — вона вже мигає оптимально; більше струму дає лише апаратура (транзисторний ключ і кілька світлодіодів у ряд, як радить і сам `README` бібліотеки: 2–3 діоди послідовно піднімають потужність «задарма»). Софтом дальність не наростити.

Підсумок карти простий. Спершу переконайтеся, що **світить** (камера). Тоді — що несуча й протокол **збігаються** з приймачем (найкраще: зняти з рідного пульта й повторити один-в-один). І лише коли й це є, а бракує **дальності**, — лізьте в залізо. У цьому порядку більшість «нічого не працює» розсипається за хвилини.
