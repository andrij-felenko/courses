# ⚙️ Керуємо KY-008 з коду: промінь, блимання, лазерний бар'єр

Керувати лазерним модулем із коду — це насправді керувати **одним цифровим виводом**. «1» на ньому — промінь горить, «0» — темно. Уся хитрість не в самому вмиканні (це один рядок), а в тому, **як** його вмикати, щоб діод не помер, вивід мікроконтролера не перегорів, а блимання виходило рівним, без випадкових збоїв. Розберімо це від найпростішого світіння до робочого лазерного бар'єра, що ловить момент перетину променя, — і по дорозі знімемо три пастки, на яких люди гублять вечори.

Мова тут одна — **C/C++**. Ми працюємо просто з ніжкою мікроконтролера (`digitalWrite`, таймери, читання АЦП), а це доменно-замкнена робота із залізом: жодна «мова стеку» тут не лягає, писати регістри GPIO Python-ом чи Go немає сенсу. Приклади — під Arduino-каркас (він однаковий для Uno/Nano на AVR і для ESP32), а специфіку кожної плати відзначаємо окремо.

## Крок 0: надійне підключення трьох пінів

Перш ніж писати код, треба, щоб залізо було під'єднане так, аби код узагалі мав із чим працювати. Три дроти:

- **S** (сигнал) → будь-який цифровий вивід плати;
- **середній пін** → **5 В**;
- **−** → **GND**.

Чому саме «живи середній пін на 5 В, навіть не знаючи ревізії» — розписано в статті про модуль; коротко: у частішій ревізії середній пін — це живлення (+), і без нього діод просто не засвітиться, а в іншій ревізії він ні до чого не під'єднаний, і зайві 5 В на ньому нічому не шкодять. Тому правило «під'єднуй усі три за призначенням» робить обидві ревізії робочими, і **код виходить той самий**: підняв S у «1» — промінь є.

Один вибір піна треба зробити свідомо. На платах ESP32 частина виводів **особливі**: деякі при старті мусять мати певний рівень (strapping-піни GPIO0, GPIO2, GPIO12, GPIO15), інші — тільки вхід (GPIO34–39, без внутрішніх підтяжок і без виходу взагалі). Якщо повісити S на такий пін, у найкращому разі лазер не вмикатиметься, у гіршому — плата не завантажиться. Тому на ESP32 бери **звичайний вивід** — наприклад, GPIO4, GPIO16, GPIO17, GPIO18, GPIO23; на Arduino Uno/Nano підійде будь-який із D2–D13 (D0/D1 зайняті послідовним портом).

> 🔧 **Навіщо це.** Половина скарг «залив приклад, а лазер мертвий» — це не код і не битий модуль, а невдалий пін на ESP32 або незалитий середній пін. Спершу переконайся, що на середньому піні є 5 В, а S сидить на нормальному GPIO, — і лише потім винувать прошивку.

## Крок 1: увімкнути, вимкнути, блимати

Найпростіша програма — світлофор для лазера: секунду горить, секунду темно. Оскільки KY-008 керується одним рівнем, будь-який приклад «блимання світлодіодом» працює для нього дослівно, лише замість світлодіода на виводі — лазер.

```cpp
const uint8_t LASER = 4;   // пін S модуля -> GPIO4 (ESP32) або D4 (Arduino)

void setup() {
    pinMode(LASER, OUTPUT);
    digitalWrite(LASER, LOW);   // старт з вимкненим променем — гарна звичка
}

void loop() {
    digitalWrite(LASER, HIGH);  // промінь увімкнено
    delay(1000);
    digitalWrite(LASER, LOW);   // промінь вимкнено
    delay(1000);
}
```

Два рядки в `setup` варто розуміти, а не просто копіювати. `pinMode(LASER, OUTPUT)` перемикає вивід у режим виходу — без цього `digitalWrite` нічого не робить (вивід лишається входом з високим опором, і на S «висить» невизначений рівень). А `digitalWrite(LASER, LOW)` **першим ділом гасить промінь** — це не косметика: поки вивід ще не налаштований (частки мілісекунди між подачею живлення й виконанням `setup`), рівень на S не визначений, і в деяких ревізіях лазер може коротко блимнути. Виставивши LOW одразу, ти скорочуєш цей неконтрольований спалах. Звичка **починати з вимкненого променя** — перше правило безпечної роботи з лазером у коді.

Загорнімо ввімкнення/вимкнення в маленькі функції — далі буде читабельніше:

```cpp
inline void laserOn()  { digitalWrite(LASER, HIGH); }
inline void laserOff() { digitalWrite(LASER, LOW);  }
```

Оце — уся «бібліотека» для KY-008. Ніякого драйвера, ніяких залежностей: модуль настільки простий, що готова бібліотека для нього була б надлишком. Усе цікаве починається, коли ми хочемо блимати **швидко**, **не блокуючи** решту програми, або **щось із цим приймати** на тому боці.

## Крок 2: блимати, не зупиняючи програму — і пастка delay

`delay(1000)` має ваду: поки він триває, мікроконтролер **не робить нічого іншого**. Для одного лазера це терпимо, але щойно поряд з'явиться друга справа (опитати кнопку, прийняти байт, крутнути серво), блимання на `delay` усе заморозить. Правильний спосіб — блимати **за годинником**, звіряючись із `millis()` (лічильник мілісекунд від старту), і між перевірками віддавати час іншим справам.

```cpp
const uint8_t  LASER    = 4;
const uint32_t PERIOD   = 500;   // півсекунди на кожен стан (2 Гц миготіння)

uint32_t lastToggle = 0;
bool      beamOn     = false;

void setup() {
    pinMode(LASER, OUTPUT);
    digitalWrite(LASER, LOW);
}

void loop() {
    uint32_t now = millis();
    if (now - lastToggle >= PERIOD) {
        lastToggle = now;
        beamOn = !beamOn;
        digitalWrite(LASER, beamOn ? HIGH : LOW);
    }

    // тут програма вільна робити будь-що інше —
    // блимання йде «саме собою», без пауз
}
```

Ключовий момент — вираз `now - lastToggle`. Він **правильно поводиться навіть тоді, коли `millis()` переповнюється** (через ~49.7 доби лічильник `uint32_t` мілісекунд обнуляється й починає рахунок наново). Здавалося б, після переповнення `now` стане маленьким, а `lastToggle` лишиться великим, і різниця «зламається». Але в беззнаковій арифметиці C++ віднімання рахується за модулем 2³², тож `now - lastToggle` дає правильний **проміжок**, а не від'ємне сміття. Тому ніколи не пишіть умову як `now >= lastToggle + PERIOD` (ось **ця** форма ламається на переповненні) — тільки `now - lastToggle >= PERIOD`.

> 🔧 **Навіщо це.** Різниця між `delay` і `millis` — це різниця між іграшкою й пристроєм. Охоронна розтяжка мусить водночас **світити променем і стежити за приймачем**; сигнальний маяк — блимати й слухати команди. Тільки-но лазер стає частиною чогось більшого, `delay` доведеться викинути, тож звикай писати неблокувально одразу.

## Крок 3: швидка модуляція — і чому «просто блимати швидко» ламається

Повільне миготіння оком видно як миготіння. Але якщо блимати **швидко** — кілограни разів на секунду, — промінь стає носієм: ним можна передати біт даних, або (найкорисніше) **промодулювати його несучою частотою**, щоб приймач на тому боці впевнено відрізняв «наш» промінь від сонця, ламп і випадкового світла. Це той самий прийом, що в інфрачервоних пультах: там світлодіод не просто світить, а мерехтить на 38 кГц, і приймач реагує лише на цю частоту.

Наївна спроба зробити несучу «в лоб» — блимати через `delayMicroseconds`:

```cpp
// НАЇВНО й КРИХКО: несуча ~38 кГц через зайнятий цикл
void carrierNaive(uint16_t cycles) {
    for (uint16_t i = 0; i < cycles; i++) {
        digitalWrite(LASER, HIGH);
        delayMicroseconds(13);   // ~13 мкс зверху
        digitalWrite(LASER, LOW);
        delayMicroseconds(13);   // ~13 мкс знизу -> період ~26 мкс -> ~38 кГц
    }
}
```

Виглядає розумно, а працює погано — і тут криється **третя пастка: на високій частоті сам `digitalWrite` уже не безкоштовний**. На Arduino Uno один `digitalWrite` — це не запис у регістр, а виклик функції, що всередині розбирає номер піна в порт і маску, перевіряє, чи не зайнятий пін таймером ШІМ, і аж тоді змінює біт. Це коштує **кілька мікросекунд** — сумірно з тими 13 мкс, які ти намагаєшся відміряти. У підсумку реальний період «попливе», частота вийде не 38, а, скажімо, 32 кГц, і від плати до плати по-різному. Для повільного миготіння ця похибка невидима; для несучої, куди приймач налаштований вузько, — фатальна.

Є два надійні виходи, і обидва прибирають `digitalWrite` із гарячого шляху.

**Спосіб 1 (портативний): прямий доступ до порту.** Замість `digitalWrite` смикаємо потрібний біт порту напряму — це одна машинна інструкція замість функції.

```cpp
// Arduino Uno/Nano (AVR): пін D4 -> біт 4 порту D
// перемикання за ~0.1 мкс замість кількох мкс digitalWrite
void carrierFast(uint16_t cycles) {
    for (uint16_t i = 0; i < cycles; i++) {
        PORTD |=  (1 << PD4);      // S у «1»
        delayMicroseconds(11);     // трохи менше 13 — компенсуємо накладні
        PORTD &= ~(1 << PD4);      // S у «0»
        delayMicroseconds(11);
    }
}
```

Тут `PORTD |= (1 << PD4)` піднімає рівень на D4 миттєво, тож усю затримку задає `delayMicroseconds`, і її можна точно підібрати. Ціна портативності: цей код прив'язаний до конкретного порту й піна саме цієї плати (на іншому виводі номер порту й біта інші), тому такі рядки завжди коментують.

**Спосіб 2 (правильний на ESP32): апаратний ШІМ-генератор.** Найкраще взагалі **не крутити несучу програмно**. У мікроконтролера є апаратний блок ШІМ, який видає задану частоту сам, без участі процесора, — а програма лише вмикає й вимикає цей потік. На ESP32 це модуль LEDC:

```cpp
// ESP32: несуча 38 кГц робиться апаратно (LEDC), процесор вільний
const uint8_t  LASER    = 4;
const uint32_t CARRIER  = 38000;   // Гц
const uint8_t  RES_BITS = 8;       // 8-бітна роздільність шпаруватості

void carrierBegin() {
    ledcAttach(LASER, CARRIER, RES_BITS);   // core 3.x: пін, частота, біти
    ledcWrite(LASER, 0);                     // 0 = несучої нема (промінь темний)
}

void carrierMark()  { ledcWrite(LASER, 128); }  // ~50% -> несуча в ефірі («мітка»)
void carrierSpace() { ledcWrite(LASER, 0);   }   // 0% -> тиша («пауза»)
```

Тут `ledcAttach` прив'язує до піна апаратний канал, налаштований на 38 кГц; далі `ledcWrite(pin, 128)` при 8 бітах — це шпаруватість близько 50%, тобто рівна несуча, а `ledcWrite(pin, 0)` її глушить. Процесор при цьому вільний повністю: несучу тримає залізо. Щоб передати біт чи символ, ти **вмикаєш/вимикаєш несучу** (мітка/пауза) на потрібні проміжки — це і є амплітудна маніпуляція, той самий принцип, що в ІЧ-протоколах.

> 🔧 **Навіщо це.** Ось чому «зроблю несучу через delay» майже завжди розчаровує: на потрібних десятках кілогерц накладні `digitalWrite` того ж порядку, що й корисна затримка, і частота розпливається. Пряма робота з портом (AVR) або апаратний ШІМ (ESP32) прибирає процесор із гарячого циклу — і несуча стає точною й стабільною, як того вимагає приймач.

## Крок 4: лазерний бар'єр — ловимо перетин променя

Тепер найцікавіше, заради чого KY-008 і беруть у проєкти: **лазерний бар'єр**. Ідея проста, як стіна. Лазер світить рівним променем на давач світла навпроти. Поки промінь долітає — давач «бачить світло», бар'єр цілий. Щойно між ними щось проходить (рука, коробка на конвеєрі, зловмисник у розтяжці) — промінь перекрито, давач різко темніє, і код розуміє: **перетин**.

Сам KY-008 тут — лише половина системи, **випромінювач**. Друга половина — приймач. Найпростіший і найдешевший приймач — [фоторезистор KY-018](book:sensors/ky-018-photoresistor): це той самий формат KY-плати, тільки з давачем-фоторезистором (LDR), опір якого падає на світлі й росте в темряві. Ставимо його навпроти лазера, читаємо АЦП — і маємо готову пару.

*Промінь від KY-008 (ліворуч) б'є на фоторезистор KY-018 (праворуч). Поки промінь долітає, давач яскраво освітлений і АЦП дає високе число; предмет, перетнувши промінь, різко затінює давач — число падає нижче порога, і код фіксує «перетин». Лазер — джерело, давач і код — усе інше.*

Схему з'єднань беремо таку: лазер — на своєму виводі, як вище; фоторезистор — на **аналоговий** вхід (на Arduino Uno це A0–A5; на ESP32 — будь-який ADC1-пін, наприклад GPIO34/35, які саме тут доречні, бо вони тільки-вхід і для читання АЦП створені).

### Найпростіший бар'єр: фіксований поріг

```cpp
const uint8_t  LASER  = 4;    // KY-008 S
const uint8_t  LDR    = A0;   // KY-018 сигнал -> аналоговий вхід (Arduino)
const int      THRESH = 400;  // поріг «світло/темно», підбирається під місце

void setup() {
    pinMode(LASER, OUTPUT);
    digitalWrite(LASER, HIGH);   // промінь горить постійно — тримає бар'єр
    Serial.begin(115200);
}

void loop() {
    int light = analogRead(LDR);          // 0..1023 на Arduino Uno
    bool broken = (light < THRESH);       // темно -> промінь перекрито

    if (broken) {
        Serial.println("ПЕРЕТИН!");
    }
    delay(20);
}
```

Це працює — і одразу показує свою слабкість. **Число `THRESH` — з пальця.** Освітленість «цілого» бар'єра залежить від відстані, від того, наскрізь чи вбік дивиться лазер на давач, від фонового світла в кімнаті, від того, чи ввімкнена люстра. Поріг 400 підійде в одному місці й геть не підійде в іншому: удень від сонця число «цілого» бар'єра може виявитися нижчим за нічне число «перекритого». Тому фіксований поріг годиться лише для швидкої перевірки на столі.

### Робочий бар'єр: калібрування + гістерезис + антидребезг

Щоб бар'єр працював у реальному місці, три речі треба зробити по-дорослому.

**Перше — калібрування.** На старті, коли ми впевнені, що промінь долітає (нічого не перетинає), заміряймо реальну освітленість «цілого» бар'єра й порахуймо поріг **від неї**, а не з голови. Скажімо, «перекрито» — це коли світло впало більш ніж на чверть від опорного рівня.

**Друге — гістерезис.** Якщо поріг один, то на самій його межі (предмет заходить у промінь скраю, освітленість тремтить біля порога) стан «цілий/перекритий» почне **деренчати** — десятки хибних спрацювань за секунду. Ліки — **два пороги**: щоб оголосити «перекрито», світло має впасти нижче нижнього; щоб повернутися в «цілий», — піднятися вище верхнього, трохи вищого. Між ними — «мертва зона», у якій стан не міняється. Це той самий гістерезис, що рятує від дребезгу скрізь, від термостата до кнопки.

**Третє — антидребезг за часом.** Навіть із гістерезисом варто вимагати, щоб новий стан **протримався кілька мілісекунд**, перш ніж ми йому повіримо, — це відсіює поодинокі сплески АЦП (шум, наведення). Ідея та сама, що при боротьбі з [брязкотом контактів](book:electronics/contact-debounce): не реагуй на перший-ліпший відлік, дочекайся, поки сигнал устоявся.

Складімо це разом:

```cpp
const uint8_t  LASER      = 4;     // KY-008 S
const uint8_t  LDR        = A0;    // KY-018 -> аналоговий вхід
const uint32_t STABLE_MS  = 8;     // скільки стан має протриматись, щоб повірити

int  baseLight = 0;                // опорна освітленість «цілого» бар'єра
int  loThresh  = 0;                // нижче -> точно перекрито
int  hiThresh  = 0;                // вище  -> точно цілий

bool broken       = false;         // поточний підтверджений стан
bool candidate    = false;         // куди стан «хоче» перейти
uint32_t sinceChange = 0;          // відколи кандидат тримається

void calibrate() {
    // промінь уже горить; беремо середнє з кількох відліків як опору
    long sum = 0;
    const int N = 32;
    for (int i = 0; i < N; i++) { sum += analogRead(LDR); delay(3); }
    baseLight = sum / N;

    // пороги: перекрито, якщо світло впало >25%; повернення — при >85% опори
    loThresh = (baseLight * 3) / 4;    // 75% опори
    hiThresh = (baseLight * 85) / 100; // 85% опори (вище -> знову цілий)
}

void setup() {
    pinMode(LASER, OUTPUT);
    digitalWrite(LASER, HIGH);   // промінь тримає бар'єр
    Serial.begin(115200);
    delay(50);                   // дати променю й давачу вгамуватися
    calibrate();
    Serial.print("опора="); Serial.print(baseLight);
    Serial.print("  lo=");   Serial.print(loThresh);
    Serial.print("  hi=");   Serial.println(hiThresh);
}

void loop() {
    int light = analogRead(LDR);

    // 1) гістерезис: куди сигнал показує ПРЯМО ЗАРАЗ
    bool wantBroken = broken;                 // за замовчуванням не міняємо
    if (light < loThresh) wantBroken = true;  // впало глибоко -> перекрито
    if (light > hiThresh) wantBroken = false; // піднялось -> цілий
    // між lo і hi (мертва зона) стан лишається як був

    // 2) антидребезг: віримо новому стану, лише коли він протримався STABLE_MS
    uint32_t now = millis();
    if (wantBroken != candidate) {            // кандидат щойно змінився
        candidate   = wantBroken;
        sinceChange = now;
    } else if (candidate != broken && now - sinceChange >= STABLE_MS) {
        broken = candidate;                   // підтверджуємо перехід
        Serial.println(broken ? "ПЕРЕТИН!" : "бар'єр цілий");
    }
}
```

Розберімо, що тут відбувається, бо ця структура — стандартний кістяк для будь-якого «надійного давача-порога».

Спершу **гістерезис** вирішує, куди сигнал показує *миттєво*: провалився нижче `loThresh` — «хоче перекрито», піднявся вище `hiThresh` — «хоче цілий», а між ними стан не чіпаємо (`wantBroken` лишається рівним поточному `broken`). Це прибирає деренчання на межі.

Далі **антидребезг за часом** не дає повірити навіть узгодженому сигналу одразу. Ми стежимо за `candidate` — станом, у який сигнал хоче перейти. Щойно кандидат змінюється, ми запам'ятовуємо момент (`sinceChange`) і починаємо відлік. Якщо кандидат протримався незмінним `STABLE_MS` мілісекунд і він досі відрізняється від підтвердженого `broken` — аж тоді робимо перехід офіційним. Один випадковий сплеск АЦП зіб'є `candidate` на мить, але не встигне «дожити» до підтвердження й тихо згасне.

Зверни увагу: тут **немає жодного `delay`** у циклі. Бар'єр можна поставити поряд з іншою роботою — сигналізацією, дисплеєм, лічильником спрацювань, — і він не заважатиме. Це той самий неблокувальний підхід за `millis()`, що й у блиманні; він же лежить в основі надійного антидребезгу.

> 🔧 **Навіщо це.** Різниця між «фіксований поріг 400» і цим кістяком — це різниця між демо, що працює лише на твоєму столі при твоєму світлі, і бар'єром, який переживе ранок, вечір і ввімкнену люстру. Калібрування прив'язує поріг до реального місця; гістерезис прибирає деренчання на межі; антидребезг відсіює шум. Три речі, три причини — і жодна не зайва.

### Бар'єр із модуляцією: бачити тільки «свій» промінь

У найпростішому бар'єрі є вроджена слабкість: давач реагує на **будь-яке** світло. Спрямуй на нього ліхтарик — і код вирішить, що промінь цілий, хоча лазер ти давно перекрив. Проти цього і працює несуча з кроку 3: якщо лазер не світить рівно, а **мерехтить на відомій частоті**, приймач може ловити саме це мерехтіння й ігнорувати постійне фонове світло.

Найчистіше це роблять готовим ІЧ-приймачем на 38 кГц (як TSOP), але його ставлять на інфрачервоний діапазон, а наш лазер видимий-червоний — тож така пара «в лоб» не завжди сходиться за довжиною хвилі. З фоторезистором KY-018 несучу теж не спіймаєш: він **надто повільний**, його опір міняється за десятки мілісекунд і 38 кГц просто «розмаже» в постійне середнє. Тому для модульованого бар'єра фоторезистор не годиться — потрібен швидкий давач (фотодіод чи фототранзистор), який устигає за несучою.

Сам приймальний бік модульованого бар'єра — це вже окрема інженерія (смуговий фільтр, детектор обвідної, поріг за амплітудою несучої), і вона виходить за межі керування самим KY-008. Тут важливо знати межу: **KY-008 уміє видати модульований промінь** (крок 3 показав, як), а от «побачити» цю модуляцію — задача приймача, і простий фоторезистор її не тягне. Для порогового бар'єра «є світло / нема світла» пари KY-008 + KY-018 цілком досить; для завадостійкого, що бачить лише свій промінь, приймач треба будувати під несучу окремо.

## Пастка, яку не можна проминути: струм сигнального виводу на ESP32

Тепер найважливіше застереження цього розділу — те, через що робочий на Arduino Uno код може **тихо вбити вивід ESP32**. Корінь — у ревізіях плати, з яких ми почали.

Згадаймо: у **варіанті Б** (середній пін не з'єднаний) весь струм лазерного діода тече **прямо із сигнального виводу** — через резистор на платі та діод на землю. А це, як ми рахували в статті про модуль, близько **28 мА** (з паспортної межі «менше 40 мА»). Тепер питання: чи витримає це вивід мікроконтролера?

**На Arduino Uno (ATmega328P) — на межі, але терпимо.** Абсолютний максимум виводу AVR — 40 мА, і 28 мА в нього вкладаються. Щоправда, рекомендований тривалий струм — **20 мА**, тож 28 мА — це вже понад комфорт: для короткого світіння чи миготіння виводу нічого не буде, але тримати так вивід під навантаженням цілодобово роками — потроху виснажувати його ресурс. (Ці цифри — з даташита Atmel/Microchip на ATmega328P: 40 мА абсолютний максимум на вивід, ~20 мА як розумна робоча межа, 200 мА сумарно на весь чип.)

**На ESP32 — так робити не можна.** І ось де підступ. Формально в даташиті ESP32 абсолютний максимум на GPIO теж стоїть 40 мА, і, здавалося б, 28 мА проходять. Але за цією цифрою — кілька «але». По-перше, 40 мА — це **абсолютний максимум**, межа руйнування, а не робоча точка; тривалий струм має бути помітно нижчим. По-друге, історично в ранніх редакціях документації ESP32 фігурувала консервативна цифра **~12 мА** на вивід (вона «переїхала» з ESP8266, поки Espressif доводила остаточні числа), і саме на неї спільнота досі орієнтується як на безпечну. По-третє, драйвер виходу ESP32 має налаштовну «силу» (drive strength) з рівнями приблизно 5 / 10 / 20 / 40 мА, і за замовчуванням він не на максимумі. Підсумок практичний: **гнати ~28 мА безперервно крізь один GPIO ESP32 — за межею здорового глузду**, навіть якщо абсолютний максимум формально вищий; вивід гріється, деградує, а сусідні лінії ловлять просадки живлення.

Виходів **два**, обидва прибирають струм діода з ніжки мікроконтролера.

**Вихід 1 — узяти варіант А (найпростіше).** У ревізії А струм діода тече з **живлення (+)** на середньому піні, а сигнальний вивід лише **керує** (притягує гілку до потрібного рівня), сам майже не проводячи струму. Тому «живи середній пін на 5 В» — це не лише про те, щоб діод світив: у ревізії А це знімає навантаження з GPIO взагалі. Якщо твоя плата виявилася варіанта А — на ESP32 проблеми немає, вивід у безпеці. Клопіт лишається тільки якщо плата варіанта Б.

**Вихід 2 — поставити транзисторний ключ (надійно завжди).** Щоб не залежати від ревізії, увімкни між виводом ESP32 і модулем [BJT-ключ](book:electronics/bjt-switch): маленький npn-транзистор (як 2N2222, BC337, S8050) керує струмом лазера, а сам вивід лише **відмикає базу** через резистор і проводить якийсь міліампер. Уся сила струму йде тоді крізь транзистор від 5-вольтового живлення, повз ніжку мікроконтролера.

```cpp
// Лазер через npn-ключ: GPIO лише керує базою, струм діода йде повз вивід
//
//   5V ──[ модуль KY-008: + і S на живлення/резистор+діод ]── колектор
//   GPIO ──[ 1 кОм ]── база npn (2N2222/BC337)
//   емітер ── GND
//
// (для варіанта Б: S модуля -> колектор ключа, а не прямо на GPIO)

const uint8_t LASER_GATE = 4;   // GPIO -> резистор -> база транзистора

void setup() {
    pinMode(LASER_GATE, OUTPUT);
    digitalWrite(LASER_GATE, LOW);   // база закрита -> лазер темний
}

void laserOn()  { digitalWrite(LASER_GATE, HIGH); } // відмикаємо базу -> струм тече
void laserOff() { digitalWrite(LASER_GATE, LOW);  }
```

Логіка коду **не змінюється** — так само `HIGH`/`LOW` на одному GPIO. Різниця лише в тому, що тепер `HIGH` відмикає транзистор, а не тягне струм діода сам. Резистор бази ~1 кОм обмежує струм у базу до безпечних одиниць міліампер (цього з запасом досить, щоб транзистор увійшов у насичення й пропустив ті ~28 мА крізь колектор). База закрита на старті (`LOW`) — знову ж таки, промінь стартує вимкненим.

> 🔧 **Навіщо це.** Це найпідступніша пастка проєкту, бо код при ній **не падає й не свариться** — він працює, а вивід ESP32 тихо деградує тижнями, поки одного дня не «висне» на постійному рівні. Правило коротке: **на 5-вольтовому Arduino Uno варіант Б терпимий, на ESP32 — ні.** На ESP32 або переконайся, що плата варіанта А (струм іде з живлення, вивід лише керує), або став npn-ключ — і струм лазера ніколи не піде крізь ніжку мікроконтролера.

## Складність і пастки: коротко про все

Зведімо докупи те, на чому спотикаються з KY-008 у коді, — щоб мати перед очима повний список.

- **Невдалий пін на ESP32.** Strapping-піни (GPIO0/2/12/15) заважають завантаженню, вхідні-тільки (GPIO34–39) не вміють виходу. Для сигналу S бери звичайний GPIO; для аналогового приймача, навпаки, GPIO34/35 доречні.
- **`delay` заморожує все.** Для чогось складнішого за один лазер блимай за `millis()`, а не `delay`; умову пиши як `now - lastToggle >= PERIOD`, щоб пережити переповнення `millis` кожні ~49.7 доби.
- **`digitalWrite` надто повільний для несучої.** На десятках кілогерц накладні виклику того ж порядку, що й корисна затримка. Пряма робота з портом (AVR) або апаратний ШІМ LEDC (ESP32) роблять частоту точною.
- **Фіксований поріг бар'єра — крихкий.** Калібруй від реальної освітленості «цілого» бар'єра; додай гістерезис (два пороги) проти деренчання на межі й антидребезг за часом проти шуму АЦП.
- **Фоторезистор повільний.** Для порогового бар'єра «є світло / нема» KY-018 годиться; для модульованого (бачити лише свій промінь) — ні, бо не встигає за несучою; там потрібен швидкий давач.
- **Струм виводу на ESP32.** У варіанті Б ~28 мА діода течуть крізь GPIO — на Uno на межі терпимого, на ESP32 зась. Рятує варіант А (струм із живлення) або npn-ключ.
- **Промінь стартує до налаштування виводу.** Перший рядок у `setup` — `digitalWrite(LASER, LOW)`; звичка починати з темряви скорочує неконтрольований спалах і привчає не тримати головку на рівні очей.

І наскрізна думка про весь код KY-008: сам модуль **лишається дурним джерелом світла**. Уся «розумність» — блимання без пауз, точна несуча, надійний бар'єр із калібруванням і гістерезисом — живе **не в лазері, а в коді навколо нього й у приймачі навпроти**. KY-008 робить рівно одне: вмикає й вимикає промінь за рівнем на одному піні. Усе інше — твоє.
