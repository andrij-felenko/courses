# 📋 Довідник інструментів аналізу, перевірки та контролю ABI у C++

Цей довідник містить систематизований опис командних утиліт, компіляторних прапорців, скриптів компонувальника та систем автоматизованого аудиту, призначених для діагностики, перевірки та фіксації стабільності двійкового інтерфейсу (англ. Application Binary Interface, ABI) у програмах на C/C++.

Матеріал охоплює як засоби низькорівневої інспекції скомпільованих артефактів (ELF на Linux/Unix, PE/COFF на Windows), так і компіляторні діагностичні засоби аналізу геометрії пам'яті класів, інструменти аналізу налагоджувальних дерев DWARF та промислові системи автоматичного виявлення двійкових розривів під час безперервної інтеграції (CI/CD).

## 1. Утиліти низькорівневої інспекції двійкових файлів

Аналіз скомпільованих об'єктних модулів (`.o`, `.obj`), статичних архівів (`.a`, `.lib`) та динамічних бібліотек (`.so`, `.dylib`, `.dll`) виконується за допомогою системних утиліт пакетів GNU Binutils, LLVM та Microsoft Windows SDK. Ці інструменти дозволяють заглянути всередину скомпільованого машинного коду та таблиць метаданих без наявності вихідних текстів програми.

### 1.1. Демоніфікація манглених імен: `c++filt` та `llvm-cxxfilt`

Утиліта перетворює внутрішні декоровані (манглені) двійкові ідентифікатори Itanium ABI або MSVC ABI у зрозумілі людині сигнатури функцій та типів C++. Манглінг є необхідним механізмом лінкера, оскільки класичні компонувальники оперують пласкими текстовими іменами і не підтримують перевантаження функцій, шаблони та простори імен безпосередньо.

```bash
# Синтаксис виклику:
c++filt [опції] [манглені_символи...]
```

| Параметр | Призначення та поведінка |
| :--- | :--- |
| `_Z...` | Пряме декодування символу Itanium C++ ABI, що застосовується у GCC та Clang на платформах Linux, macOS та Android. |
| `-t`, `--types` | Декодувати назви низькорівневих типів даних (RTTI дескриптори, аргументи шаблонів, базові типи). |
| `-p`, `--no-params` | Не виводити типи аргументів функцій, показуючи лише повне кваліфіковане ім'я з просторами імен. |
| `-s`, `--format=FORMAT` | Примусово встановити схему манглінгу: `gnu-v3` (Itanium ABI), `msvc` (Microsoft), `arm`, `auto`. |
| `--strip-underscore` | Видалити початковий символ підкреслення (характерно для символьних таблиць macOS Mach-O). |

**Анатомія кодування Itanium C++ ABI:**

У схемі Itanium ABI усі імена починаються з префікса `_Z`. Якщо функція розташована всередині простору імен або класу, додається префікс `N`, після якого чергуються довжина ідентифікатора та його назва, а завершується блок літерою `E`. Типи параметрів кодуються скороченими одно- або двобуквеними позначеннями:
- `v` — `void`, `b` — `bool`, `c` — `char`, `i` — `int`, `l` — `long`, `d` — `double`;
- `P` — вказівник (`Pointer`), `R` — lvalue-посилання (`Reference`), `O` — rvalue-посилання;
- `K` — кваліфікатор `const`, `V` — кваліфікатор `volatile`;
- `S_`, `S0_`, `S1_` — механізм стиснення імен (Substitution), що замінює вже раніше згадані простори імен або типи для зменшення розміру бінарника.

```bash
# Декодування мангленого символу функції:
$ c++filt _ZN6Widget6renderERKNS_8SettingsE
Widget::render(Widget::Settings const&)

# Декодування типу даних через конвеєр:
$ echo "_ZTI6Widget" | c++filt -t
typeinfo for Widget
```

**Анатомія кодування Microsoft Visual C++ ABI:**

На платформі Windows компілятор MSVC використовує іншу схему, де всі символи починаються зі знака питання `?`. Наприклад, функція `Widget::draw(int)` транслюється у символ `?draw@Widget@@QEAAXH@Z`. У цій схемі префікс `QEAA` шифрує модифікатор доступу (public), константність покажчика `this` (non-const) та конвенцію виклику (`__cdecl` або x64 FastCall), літера `X` позначає тип повернення `void`, а літера `H` — параметр типу `int`.

### 1.2. Інспекція таблиці символів: `nm` та `llvm-nm`

Утиліта `nm` зчитує таблиці символів із двійкових файлів ELF або Mach-O, відображаючи ім'я кожного символу, його адресу в пам'яті, тип прив'язки (локальний, глобальний, слабкий) та секцію, у якій він розміщений.

```bash
# Синтаксис виклику:
nm [опції] <двійковий_файл>
```

| Параметр | Опис дії |
| :--- | :--- |
| `-C`, `--demangle` | Автоматично декодувати манглені імена C++ у читабельний вигляд. |
| `-D`, `--dynamic` | Читати символи динамічної таблиці `.dynsym`, яка завантажується в пам'ять під час запуску програми. Обов'язковий прапорець для бібліотек без налагоджувальної інформації. |
| `-g`, `--extern-only` | Відображати виключно глобальні (експортовані або імпортовані) символи, ігноруючи внутрішні для одиниці трансляції. |
| `-u`, `--undefined-only` | Вивести лише невизначені символи, які бібліотека очікує отримати від інших модулів або операційної системи. |
| `--defined-only` | Вивести символи, що мають конкретну реалізацію безпосередньо в цьому файлі. |

Кожен символ у звіті `nm` позначається однобуквеним кодом, що розкриває його внутрішню природу в двійковому форматі:

- **`T` / `t`**: Символ розміщений у секції виконуваного коду (`.text`). Велика літера позначає глобальний експорт, доступний іншим модулям, мала — локальну статичну функцію.
- **`U`**: Невизначений символ (Undefined) — викликається кодом поточної бібліотеки, але його адреса має бути заповнена динамічним лінкером під час завантаження.
- **`W` / `w`**: Слабкий символ (Weak) — створений для `inline`-функцій, шаблонів або таблиць `vtable`. Компонувальник об'єднує всі дублікати слабкого символу в один екземпляр згідно з правилом ODR (One Definition Rule).
- **`D` / `d`**: Ініціалізовані глобальні або статичні змінні, розміщені в секції даних (`.data`).
- **`B` / `b`**: Неініціалізовані глобальні змінні, розташовані в секції `.bss` (Block Started by Symbol), які занулюються ядром ОС під час створення процесу.
- **`R` / `r`**: Дані тільки для читання (`.rodata`), включаючи рядкові константи, константні таблиці та дескриптори RTTI.
- **`V` / `v`**: Слабкий об'єкт даних (наприклад, екземпляри `std::type_info` для поліморфних класів).

Практичний приклад виявлення витоку приватних символів та перевірки коректності експорту публічного API бібліотеки:

```bash
# Перевірка всіх глобально експортованих функцій спільної бібліотеки:
$ nm -gDC libengine.so | grep " T "
0000000000002140 T engine_init
0000000000002190 T engine_shutdown
0000000000002200 T Engine::Core::internal_allocator(unsigned long) # Помилка! Внутрішній метод експортовано назовні
```

### 1.3. Повний аналіз структури ELF: `readelf` та `objdump`

Утиліти `readelf` та `objdump` забезпечують детальний аналіз заголовків, секцій, сегментів завантаження, залежностей та асемблерного коду скомпільованих програм.

```bash
# Синтаксис виклику:
readelf [опції] <elf_файл>
objdump [опції] <двійковий_файл>
```

| Опція `readelf` | Результат роботи |
| :--- | :--- |
| `-h`, `--file-header` | Заголовок ELF: архітектура процесора (x86_64, ARM), розрядність, порядок байтів (Endianness), тип файлу (`EXEC`, `DYN`). |
| `-l`, `--program-headers` | Таблиця програмних заголовків: сегменти завантаження в пам'ять (`LOAD`), динамічні теги (`DYNAMIC`), секція винятків (`GNU_EH_FRAME`). |
| `-S`, `--section-headers` | Повний список секцій файлу із зазначенням прапорців пам'яті (`ALLOC`, `EXECINSTR`, `WRITE`). |
| `-s`, `--symbols` | Повна таблиця символів із точним розміром кожного об'єкта та функції в байтах. |
| `--dyn-syms` | Таблиця символів динамічного лінкування для завантажувача ОС (`ld.so`). |
| `-d`, `--dynamic` | Теги динамічної секції: ідентифікатор бібліотеки (`SONAME`), список прямих залежностей (`NEEDED`), шляхи пошуку (`RUNPATH`, `RPATH`). |
| `-V`, `--version-info` | Інформація про версіонування символів (GNU Versioning Scheme). |

Для детального аналізу асемблерного коду та перевірки конвенцій виклику функцій використовується дизасемблер `objdump`:

```bash
# Дизасемблювання з синтаксисом Intel та декодуванням імен:
$ objdump -d -M intel -C libengine.so > disassembly.txt
```

Аналіз асемблерного виклику дає можливість точно визначити, чи викликається віртуальний метод через правильне зміщення у `vtable`, та чи передаються аргументи через регістри (`rdi`, `rsi`, `rdx`), чи записуються на стек процесу.

### 1.4. Інспекція налагоджувальних дерев DWARF: `llvm-dwarfdump`

Інформація про типи, ієрархію успадкування та зміщення полів зберігається у спеціальних секціях DWARF (`.debug_info`, `.debug_types`). Утиліта `llvm-dwarfdump` дозволяє безпосередньо перевірити, як компілятор зафіксував геометрію структур у двійковому файлі.

```bash
# Пошук конкретної структури в налагоджувальних деревах:
$ llvm-dwarfdump --name=Widget libengine.so
```

Кожен запис DWARF містить вузли DIE (Debugging Information Entry):
- `DW_TAG_structure_type` або `DW_TAG_class_type` — описує ім'я класу, його розмір у байтах (`DW_AT_byte_size`) та файл оголошення;
- `DW_TAG_member` — описує окреме поле, його тип та зміщення в байтах від початку структури (`DW_AT_data_member_location`);
- `DW_TAG_inheritance` — фіксує базові класи та зміщення під'об'єкта базового класу.

Саме ці секції DWARF зчитуються інструментами автоматизованого аудиту (зокрема Libabigail) для виявлення розривів ABI між версіями бібліотек.

### 1.5. Аналіз залежностей та шляхів завантаження: `ldd` та `patchelf`

Динамічний завантажувач операційної системи Linux (`ld.so`) розв'язує залежності спільних бібліотек на основі службових тегів у двійковому файлі. Для інспекції та модифікації цих зв'язків застосовують утиліти `ldd` та `patchelf`.

```bash
# Перегляд дерева завантаження спільних бібліотек для виконуваного файлу:
$ ldd ./my_application
    libengine.so.1 => /usr/local/lib/libengine.so.1 (0x00007ffff7fa0000)
    libstdc++.so.6 => /lib/x86_64-linux-gnu/libstdc++.so.6 (0x00007ffff7d70000)
    libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007ffff7b50000)
```

Якщо під час запуску програми завантажується застаріла або несумісна версія бібліотеки з системного каталогу замість локальної збірки, утиліта `patchelf` дозволяє примусово модифікувати вбудований шлях пошуку (`RUNPATH` або `RPATH`) без повторної перекомпіляції коду:

```bash
# Встановлення пріоритетного локального шляху пошуку бібліотек:
$ patchelf --set-rpath '$ORIGIN/../lib' ./my_application

# Зміна SONAME у скомпільованому бінарнику:
$ patchelf --set-soname libengine.so.2 build/libengine.so
```

## 2. Прапорці компіляторів для інспекції розкладки пам'яті класів

Для гарантії стабільності ABI розробнику необхідно точно знати, як компілятор розташовує поля в пам'яті, де виникають байти заповнення (padding) для збереження вирівнювання та як структурована таблиця віртуальних функцій (`vtable`).

### 2.1. Діагностичні прапорці Clang / LLVM

Компілятор Clang надає прямий доступ до внутрішнього представлення AST та генератора коду через спеціальні прапорці фронтенду (`-Xclang`).

| Прапорець | Призначення |
| :--- | :--- |
| `-Xclang -fdump-record-layouts` | Виводить у термінал повну схему розміщення полів усіх структур і класів, включаючи розмір (`sizeof`), вирівнювання (`alignof`), розмір без віртуальних баз (`nvsize`) та зміщення кожного поля в байтах. |
| `-Xclang -fdump-record-layouts-simple` | Скорочений формат виводу, зручний для швидкого парсингу скриптами. |
| `-Xclang -fdump-vtable-layouts` | Повний дамп усіх віртуальних таблиць: зміщення Offset-to-top, RTTI дескриптор `typeinfo`, таблиця покажчиків на віртуальні методи та зміщення Thunk-функцій для множинного успадкування. |

Приклад аналізу виводу розкладки пам'яті в Clang:

```text
*** Layout: Struct 'Widget'
   0 | struct Widget
   0 |   (Widget vtable pointer)
   8 |   int id_
  12 |   int priority_
  16 |   double scale_
     | [sizeof=24, dsize=24, align=8,
     |  nvsize=24, nvalign=8]
```

У наведеному прикладі перші 8 байтів займає покажчик на віртуальну таблицю (`vptr`), за зміщенням +8 розташоване поле `id_`, за зміщенням +12 — поле `priority_`, а за зміщенням +16 — 8-байтне число з рухомою комою `scale_`, що вимагає вирівнювання за 8-байтною межею. Параметр `nvsize=24` позначає розмір об'єкта без урахування віртуальних базових класів.

### 2.2. Діагностичні засоби GCC (GNU Compiler Collection)

У компіляторі GCC структура класів аналізується через генерацію спеціальних файлів дампів або увімкнення попереджень компілятора щодо заповнення пам'яті.

| Прапорець | Опис результату |
| :--- | :--- |
| `-fdump-lang-class` | Створює текстовий файл `<файл>.class`, який містить повний опис геометрії класів, таблиць `vtable` та вторинних таблиць `VTT` для віртуального успадкування. |
| `-Wpadded` | Генерує попередження компілятора щоразу, коли компілятор змушений вставити невикористані байти заповнення між полями або в кінці структури для вирівнювання. |
| `-Wpacked` | Попереджає, якщо атрибут `__attribute__((packed))` не впливає на вирівнювання структури. |

Аналіз попереджень `-Wpadded` дозволяє проєктувати структури з мінімальним розміром і фіксованими межами, що запобігає несподіваним змінам зміщень полів:

```cpp
struct UnalignedConfig {
    char active;      // 1 байт
    // Попередження: padding of 3 bytes added after 'active' [-Wpadded]
    int timeout_ms;   // 4 байти (зміщення +4)
    char debug_level; // 1 байт (зміщення +8)
    // Попередження: padding of 7 bytes added after 'debug_level' [-Wpadded]
    double threshold; // 8 байтів (зміщення +16)
}; // Загальний розмір: 24 байти замість оптимальних 16 при перевпорядкуванні полів
```

### 2.3. Засоби інспекції Microsoft Visual C++ (MSVC)

Компілятор MSVC містить діагностичні прапорці серії `/d1report`, які виводять детальну карту пам'яті класів безпосередньо під час складання проєкту.

| Прапорець | Дія |
| :--- | :--- |
| `/d1reportSingleClassLayout<ClassName>` | Виводить у вивід компіляції точну розкладку зазначеного класу, показуючи зміщення `vfptr` (покажчик віртуальних функцій), `vbtable` (покажчик таблиці віртуальних баз) та користувацьких даних. |
| `/d1reportAllClassLayout` | Виводить розкладку всіх без винятку класів, згаданих під час компіляції одиниці трансляції. |

Приклад звіту MSVC для класу з віртуальним методом:

```text
class Widget	size(24):
	+---
 0	| {vfptr}
 8	| int id_
12	| int priority_
16	| double scale_
	+---
Widget::$vftable@:
	| &Widget_meta
	|  0
 0	| &Widget::draw
 1	| &Widget::update
```

### 2.4. Компіляторні статичні перевірки розкладки (ABI Static Assertions)

Найпростішим і найнадійнішим способом гарантувати незмінність розкладки полів у критичних структурах є вбудовування статичних перевірок `static_assert` безпосередньо у вихідний код публічних заголовків:

```cpp
#include <cstddef>
#include <type_traits>

struct PacketHeader {
    uint32_t magic;
    uint16_t version;
    uint16_t payload_size;
    uint64_t sequence_id;
};

// Статичні інваріанти ABI: гарантують падіння збірки при спробі змінити структуру
static_assert(sizeof(PacketHeader) == 16, "Критична помилка: розмір PacketHeader змінився!");
static_assert(alignof(PacketHeader) == 8, "Критична помилка: вирівнювання PacketHeader змінилося!");
static_assert(offsetof(PacketHeader, magic) == 0, "Зсув поля magic порушено!");
static_assert(offsetof(PacketHeader, version) == 4, "Зсув поля version порушено!");
static_assert(offsetof(PacketHeader, payload_size) == 6, "Зсув поля payload_size порушено!");
static_assert(offsetof(PacketHeader, sequence_id) == 8, "Зсув поля sequence_id порушено!");
static_assert(std::is_standard_layout_v<PacketHeader>, "PacketHeader повинен мати стандартну розкладку!");
```

## 3. Автоматизований аудит двійкової сумісності (Libabigail)

Набір інструментів **Libabigail** (Application Binary Interface Generic Analysis and Instrumentation Library), створений інженерами Red Hat, є загальновизнаним промисловим інструментом для автоматичного моніторингу сумісності C/C++ ABI в операційних системах Linux та конвеєрах неперервної інтеграції.

На відміну від поверхневого аналізу заголовків або простих перевірок текстових імен символів, Libabigail зчитує секції налагоджувальної інформації у форматі DWARF (`DW_TAG_structure_type`, `DW_TAG_member`, `DW_TAG_subprogram`, `DW_AT_data_member_location`), реконструює повну об'єктну модель типів і математично порівнює двійкові графи двох версій бібліотеки.

### 3.1. Склад пакету Libabigail

```bash
# 1. Екстракція та збереження двійкового зліпка ABI у форматі XML
abidw [опції] <бібліотека.so> --out-file <зліпок.abi>

# 2. Порівняння двох спільних бібліотек або збережених зліпків ABI
abidiff [опції] <стара_версія.so> <нова_версія.so>

# 3. Перевірка сумісності клієнтської програми зі спільною бібліотекою
abicompat [опції] <програма_клієнт> <нова_бібліотека.so>

# 4. Перевірка синтаксичної та семантичної коректності ABI XML файлу
abilint [опції] <зліпок.abi>
```

### 3.2. Ключові прапорці утиліти `abidiff`

| Прапорець | Призначення та застосування |
| :--- | :--- |
| `--suppressions <файл.suppr>` | Підключити файл правил ігнорування дозволених змін (наприклад, дозволених модифікацій приватних полів або внутрішніх просторів імен). |
| `--leaf-changes-only` | Виводити лише безпосередні першопричини змін типів без розгортання всього дерева залежних функцій. |
| `--impacted-interfaces` | Сформувати список усіх публічних функцій і методів, поведінка або бінарний виклик яких порушилися внаслідок зміни типу. |
| `--no-added-syms` | Не фіксувати додавання нових символів як зміну (додавання нових функцій у кінець бібліотеки зазвичай є зворотно-сумісним). |
| `--drop-private-types` | Ігнорувати типи даних, які не фігурують у публічних експортованих сигнатурах функцій. |
| `--dump-diff-tree` | Вивести повне дерево розбіжностей у форматі графу для детального налагодження. |

Приклад реального звіту `abidiff`, який зупиняє розгортання бібліотеки через виявлений зсув поля:

```text
$ abidiff --leaf-changes-only libengine-1.0.so libengine-1.1.so
Functions changes summary: 0 Removed, 1 Changed, 0 Added function
Variables changes summary: 0 Removed, 0 Changed, 0 Added variable

1 function with some sub-type change:

  [C]'function void process_event(Event*)' at engine.cpp:50:1 has some sub-type changes:
    parameter 1 of type 'Event*' has sub-type changes:
      in pointed to type 'struct Event' at event.h:18:1:
        type size changed from 128 to 192 (in bits)
        1 data member insertion:
          'uint64_t timestamp', at offset 64 (in bits) at event.h:20:1
        1 data member change:
          'int payload' offset changed from 64 to 128 (in bits) (by +64 bits)
```

### 3.3. Файли правил придушення (Suppression Files)

Для виключення хибнопозитивних спрацьовувань під час аналізу приватних компонентів бібліотеки створюють конфігураційний файл у форматі INI (`abi-rules.suppr`):

```ini
[suppress_type]
  # Ігнорувати зміни у внутрішніх деталях реалізації PImpl
  name = EngineImpl
  type_kind = class

[suppress_function]
  # Дозволити зміну сигнатури внутрішніх допоміжних функцій
  namespace_name_regex = ^Engine::detail::
```

Запуск аудиту з файлом правил:

```bash
abidiff --suppressions abi-rules.suppr libengine-v1.so libengine-v2.so
```

### 3.4. Автоматизація в конвеєрах CI/CD

Типовий крок перевірки стабільності двійкового інтерфейсу в конвеєрах автоматичного тестування (GitHub Actions, GitLab CI) виглядає наступним чином:

```bash
# 1. Завантаження еталонного зліпка попереднього стабільного релізу
curl -sO https://releases.example.com/abi/libengine-v1.0.abi

# 2. Генерація поточного зліпка щойно скомпільованої бібліотеки
abidw --drop-private-types build/libengine.so --out-file current.abi

# 3. Виконання диференційного аналізу з перевіркою коду завершення
abidiff --suppressions config/abi.suppr libengine-v1.0.abi current.abi
if [ $? -ne 0 ]; then
    echo "CRITICAL: Виявлено розрив ABI! Злиття заборонено."
    exit 1
fi
```

### 3.5. Альтернативний генератор звітів: `abi-compliance-checker`

Поряд із Libabigail у дистрибутивах Linux та системних проектах широко застосовується інструмент `abi-compliance-checker`. Він зчитує сирцеві заголовки C/C++ разом із двійковими бібліотеками і формує наочний інтерактивний HTML-звіт про рівень зворотної сумісності (Binary and Source Compatibility).

```bash
# Синтаксис генерації двійкового дескриптора через abi-dumper:
abi-dumper libengine.so.1.0 -o libengine_v1.dump -lver 1.0

# Порівняння двох версій бібліотеки з генерацією звіту:
abi-compliance-checker -l libengine -old libengine_v1.dump -new libengine_v2.dump -html
```

Утиліта розраховує відсоток сумісності (наприклад, `99.4% Binary Compatibility`) і класифікує знайдені проблеми за трьома рівнями серйозності:
- **High Severity (Критичні)**: зміна розміру експортованого класу, зміщення публічних полів, видалення віртуального методу або зміна його індексу у `vtable`, зміна типу або кількості аргументів експортованої функції;
- **Medium Severity (Середні)**: зміна константності аргументу, зміна значень елементів переліку `enum`, зміна умов розгортання винятків у блоці `noexcept`;
- **Low Severity (Низькі)**: додавання нових невіртуальних методів у кінець класу або введення нових типів переліків.

## 4. Засоби контролю видимості та версіонування символів

Для побудови захищеного двійкового інтерфейсу використовують комбінацію прапорців компілятора для приховування символів та версійних скриптів компонувальника для формування структурованої таблиці динамічних символів.

### 4.1. Атрибути видимості GCC/Clang та макроси експорту

За замовчуванням у компіляторах GCC та Clang на Unix-системах усі символи отримують видимість `default` і потрапляють у динамічну таблицю `.dynsym`. Це сповільнює завантаження програми через велику кількість зайвих релокацій і відкриває внутрішні класи бібліотеки для випадкового зовнішнього зв'язування. Промисловим стандартом є примусове приховування всіх символів через прапорці компілятора:

```bash
# Прапорці закриття внутрішнього інтерфейсу бібліотеки:
CXXFLAGS += -fvisibility=hidden -fvisibility-inlines-hidden
```

Для вибіркового відкриття публічного API у вихідному коді використовують платформонезалежні макроси експорту:

```cpp
#if defined(_WIN32) || defined(__CYGWIN__)
  #if defined(ENGINE_BUILDING_DLL)
    #define ENGINE_API __declspec(dllexport)
  #else
    #define ENGINE_API __declspec(dllimport)
  #endif
#else
  #if defined(__GNUC__) && __GNUC__ >= 4
    #define ENGINE_API __attribute__((visibility("default")))
    #define ENGINE_LOCAL __attribute__((visibility("hidden")))
  #else
    #define ENGINE_API
    #define ENGINE_LOCAL
  #endif
#endif

// Використання у публічних заголовках:
class ENGINE_API PublicEngine {
public:
    void start();  // Символ експортується у .dynsym
private:
    void step();   // Символ залишається локальним і прихованим
};
```

---

### 4.2. Скрипти версіонування символів компонувальника (GNU Symbol Versioning)

Компонувальник GNU `ld` та LLVM `lld` дозволяють прив'язувати символи спільної бібліотеки до версійних вузлів за допомогою спеціального версійного скрипта (`libengine.map`). Це гарантує, що стара програма, яка вимагає версії символу `ENGINE_1.0`, не виконає несумісну реалізацію з `ENGINE_2.0`.

**Синтаксис файлу `libengine.map`:**

```text
ENGINE_1.0 {
    global:
        engine_create;
        engine_destroy;
        engine_execute;
        extern "C++" {
            Engine::Widget::*;
        };
    local:
        *;  # Приховати абсолютно всі інші символи
};

ENGINE_2.0 {
    global:
        engine_execute_async;
} ENGINE_1.0;  # Успадковує всі символи вузла ENGINE_1.0
```

**Підключення версійного скрипта під час збірки бібліотеки:**

```bash
g++ -shared -fPIC -o libengine.so.1.0 engine.o \
    -Wl,--version-script=libengine.map \
    -Wl,-soname,libengine.so.1
```

Якщо в новій версії бібліотеки необхідно одночасно підтримувати стару реалізацію функції для старих клієнтів і нову реалізацію для нових, у вихідному коді застосовують директиву `.symver`:

```cpp
// Стара версія функції для клієнтів, зібраних під ENGINE_1.0
int engine_compute_v1(int x) {
    return x * 2;
}
__asm__(".symver engine_compute_v1, engine_compute@ENGINE_1.0");

// Нова версія функції для нових клієнтів (ENGINE_2.0 за замовчуванням)
int engine_compute_v2(int x, int flags) {
    return x * 3 + flags;
}
__asm__(".symver engine_compute_v2, engine_compute@@ENGINE_2.0");
```

Завдяки цьому старі скомпільовані програми безшовно продовжують викликати `engine_compute_v1`, тоді як нові програми під час лінкування автоматично зв'язуються з `engine_compute_v2`.

---

### 4.3. Експорт символів на Windows через модуль визначення DEF-файлів

На платформі Windows альтернативою розстановці директив `__declspec(dllexport)` у заголовках є використання файлів визначення модуля (`.def`). Цей механізм дозволяє фіксувати порядкові номери експорту (Ordinals) та приховувати внутрішні імена C++:

```text
LIBRARY libengine.dll
EXPORTS
    engine_init        @1
    engine_shutdown    @2
    engine_process     @3
    ?render@Widget@@QEAAXXZ @4 NONAME  ; Експорт суто за порядковим номером
```

Використання ключового слова `NONAME` вилучає текстове ім'я функції з таблиці експорту DLL, зменшуючи розмір двійкового файлу та унеможливлюючи несанкціоноване зв'язування за іменем.

## 5. Практичні сценарії налагодження помилок ABI у GDB та ASan

Коли розрив ABI все ж таки стався і програма падає під час виконання, застосовують системні налагоджувачі та динамічні санітайзери для локалізації невідповідності розкладки пам'яті.

### 5.1. Діагностика через GDB

Під час зупинки процесу в точці краху в GDB можна перевірити стан таблиці віртуальних методів та точні адреси полів структури:

```gdb
# 1. Вивід повної таблиці віртуальних функцій об'єкта:
(gdb) info vtbl object_ptr
vtable for 'Widget' @ 0x7ffff7fb8d40 (subobject @ 0x55555556b2c0):
[0]: 0x7ffff7fa4180 <Widget::render()>
[1]: 0x7ffff7fa4210 <Widget::update()>

# 2. Перевірка фактичної адреси поля в пам'яті:
(gdb) print &(((Widget*)0)->scale_)
$1 = (double *) 0x10

# 3. Шістнадцятковий дамп сирих байтів об'єкта:
(gdb) x/6gx object_ptr
0x55555556b2c0: 0x00007ffff7fb8d40  0x0000000100000002
0x55555556b2d0: 0x4058c00000000000  0x0000000000000000
```

Якщо індекс у виклику `call [rax + offset]` вказує на слот таблиці, де розміщено деструктор замість очікуваного методу `update()`, це слугує беззаперечним доказом зсуву віртуальної таблиці внаслідок несумісної версії бібліотеки.

### 5.2. Виявлення порушень ODR за допомогою AddressSanitizer

Компілятори GCC та Clang підтримують виявлення порушень One Definition Rule (ODR) між різними одиницями трансляції за допомогою AddressSanitizer:

```bash
# Компіляція з прапорцем виявлення невідповідності розмірів глобальних змінних:
g++ -fsanitize=address -O1 -g main.cpp lib.cpp -o app
ASAN_OPTIONS=detect_odr_violation=2 ./app
```

При виявленні глобального об'єкта або таблиці, які мають різний розмір у різних модулях програми, AddressSanitizer формує детальний звіт із зазначенням імен вихідних файлів та номерів рядків, де було оголошено несумісні типи.

### 5.3. Аналіз пошкодження фрейму стеку через Core Dump

Якщо функція була викликана з невідповідною конвенцією виклику (наприклад, викликач передавав структуру в регістрах, а функція очікувала її на стеку і виштовхнула зайві байти інструкцією `ret N`), стек процесора розбалансовується, а адреса повернення замінюється випадковим числом. У журналі `dmesg` або під час відкриття аварійного дампу (`core dump`) у GDB це проявляється як пошкоджений стек:

```gdb
$ gdb ./app core.12345
(gdb) bt
#0  0x00000000deadbeef in ?? ()
#1  0x00007fffffffe100 in ?? ()
Backtrace stopped: Cannot access memory at address 0xdeadbeef
```

У такій ситуації налагоджувач не може відновити ланцюг викликів через те, що збережений покажчик бази кадру (`%rbp`) або адреса повернення були перезаписані. Локалізація такої помилки вимагає покрокового аналізу інструкцій виклику `call` та повернення `ret` у точці виклику бібліотечної функції.
