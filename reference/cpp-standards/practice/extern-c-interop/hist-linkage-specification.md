# 📜 Історія специфікації зв'язування: як Cfront породив extern "C"

Специфікатор зв'язування `extern "C"` виник не як естетичне доповнення синтаксису C++, а як відповідь на кризу двійкової сумісності під час переходу від транслятора Cfront до повноцінних компіляторів наприкінці 1980-х років. Без цього механізму щойно народжена мова C++ була б ізольована від усієї накопиченої екосистеми системних бібліотек мови C і Unix API.

## Епоха "C with Classes" і перші транслятори Cfront

На початку 1980-х років Б'ярн Страуструп (Bjarne Stroustrup) у дослідницькому центрі Bell Labs працював над розширенням мови C, яке спочатку отримало назву "C with Classes", а в 1983 році було перейменовано на C++. Оскільки створення повноцінного компілятора під десятки апаратних архітектур вимагало колосальних інженерних ресурсів, Страуструп обрав прагматичний шлях: створив препроцесор-транслятор Cfront (спочатку відомий під робочою назвою `cpre`).

Cfront читав вихідний код мовою C++, перевіряв типи, обробляв класи й перетворював об'єктні конструкції на проміжний чистий код мовою C. Цей згенерований C-код згодом передавався стандартному системному C-компілятору (переважно Portable C Compiler, PCC на комп'ютерах VAX-11/780 під керуванням Unix Research Edition).

У проміжному коді класи C++ перетворювалися на звичайні C-структури, покажчик `this` передавався першим явним параметром кожної функції, а віртуальні таблиці формувалися як масиви покажчиків на функції всередині структур `struct __vtbl`.

У ранніх версіях Cfront (1.0 та 1.1) концепція спотворення імен (name mangling) була мінімалістичною. Методи класів перетворювалися на звичайні глобальні C-функції шляхом механічного з'єднання імені класу, розділювача та імені методу: метод `Task::display()` ставав C-функцією `display_4Task()`. Звичайні глобальні функції не модифікувалися взагалі.

Доки глобальні функції C++ не підтримували перевантаження (overloading), жодного двійкового конфлікту імен із базовою бібліотекою мови C (`libc`) не виникало: виклик `printf`, `malloc` або системного виклику `open` у вихідному коді на C++ безпосередньо транслювався в ідентичний C-виклик `printf`, `malloc` або `open` у результуючому C-файлі.

## Криза перевантаження функцій і типобезпечного зв'язування (1986–1988)

У 1986–1987 роках під час проектування Cfront 2.0 Страуструп упровадив повноцінне перевантаження функцій як фундаментальну властивість мови. Можливість визначати в одній області видимості кілька функцій із однаковим іменем, але різними типами аргументів (наприклад, `sqrt(double)` та `sqrt(complex)`), вимагала закодувати повну сигнатуру типів параметрів безпосередньо в рядок символу об'єктного файлу. Без цього системний компонувальник Unix (`ld`) не міг би розрізнити їх у таблиці символів і зупинявся б із помилкою множинного визначення однакових символів.

Цей підхід отримав назву **типобезпечного зв'язування** (англ. *Type-Safe Linkage*). Глобальна математична функція `sqrt(double)` почала транслюватися у внутрішній двійковий символ `sqrt__Fd` (де `F` означало функцію, а `d` — тип параметра `double`).

Але це нововведення негайно зруйнувало двійкову сумісність із існуючими бібліотеками операційної системи. Коли програміст підключав стандартний заголовок і викликав функцію:

```cpp
#include <math.h>

double val = sqrt(2.0);
```

Транслятор Cfront 2.0 генерував асемблерний виклик декорованого символу `sqrt__Fd`. Проте вже скомпільована системна бібліотека математики Unix (`libm.a`), написана мовою C, містила в таблиці символів виключно плоский ASCII-запис `sqrt`. Під час фази зшивання компонувальник зупиняв процес із фатальною помилкою:

```text
ld: undefined symbol sqrt__Fd referenced in main.o
```

Першою спробою вийти з глухого кута в Cfront 1.2 стало введення спеціального ключового слова `overload`. Розробник був зобов'язаний явно вказувати компілятору, які саме імена функцій підлягають перевантаженню та спотворенню:

```cpp
overload sqrt;
double sqrt(double);
double sqrt(complex);
```

Якщо функція не мала попереднього оголошення `overload`, Cfront залишав її ім'я незмінним. Проте таке рішення виявилося надзвичайно крихким і небезпечним: випадковий пропуск директиви в одному заголовку призводив до мовчазної підміни символів, а системні заголовки Unix вимагали постійних ручних модифікацій під кожну нову версію компілятора. Крім того, ключове слово `overload` вирішувало лише проблему імен, але не враховувало можливих розбіжностей у конвенціях виклику.

## Розробка концепції Language Linkage (1988–1989)

Б'ярн Страуструп усвідомив, що проблема полягає не просто в текстовому кодуванні назв, а у фундаментальній взаємодії двох різних мовних моделей. Різні мови програмування мають власні угоди про виклики (calling conventions), специфічні правила вирівнювання стекових кадрів, розподіл регістрів під передачу аргументів та механізми повернення структур із функцій.

У 1988 році Страуструп опублікував програмну статтю *"Type-Safe Linkage for C++"* у журналі *Computing Systems*, де вперше сформулював концепцію **специфікації мовного зв'язування** (Language Linkage Specification). Головна ідея полягала в тому, щоб надати програмісту явний і декларативний інструмент, який повідомляє компілятору, за правилами якої мови слід формувати двійковий інтерфейс конкретної сутності.

Синтаксис отримав форму:

```cpp
extern "C" double sqrt(double);
```

Цей запис давав компілятору дві обов'язкові вказівки:
1. Застосувати до функції системну угоду про виклики та розміщення аргументів мови C для поточної цільової архітектури.
2. Експортувати або імпортувати символ без спотворення імен (name mangling), тобто під незмінним рядком `sqrt`.

Для забезпечення зручності роботи з великими сторонніми бібліотеками Страуструп додав блокову форму специфікації:

```cpp
extern "C" {
    int open(const char* path, int oflag, ...);
    int close(int fd);
    long read(int fd, void* buf, unsigned long nbyte);
}
```

Такий підхід дозволив підключати стандартні заголовки мови C без необхідності редагувати кожне окреме оголошення функції в системних файлах `/usr/include`.

## Розмежування класу пам'яті та мовного зв'язування

Важливим теоретичним досягненням періоду 1988–1990 років стало чітке розділення понять **класу пам'яті** (Storage Class Specifier) та **мовного зв'язування** (Language Linkage Specification). Ключове слово `extern` у мові C традиційно означало зовнішню видимість символу (External Linkage). Проте конструкція `extern "C"` у C++ визначає саме мовну конвенцію, а не область видимості.

Це уможливило оголошення локальних для одиниці трансляції функцій із конвенцією мови C:

```cpp
extern "C" static void internal_helper(int code) {
    // Внутрішня функція з внутрішнім зв'язуванням (internal linkage),
    // але з C calling convention, придатною для реєстрації в C-бібліотеках
}
```

Така функція не експортується в глобальну таблицю символів компонувача, проте має двійкову конвенцію виклику мови C, що дозволяє передавати її покажчик як callback у сторонні C-драйвери.

## Типізація покажчиків на функції та простори імен

Одним із найскладніших питань під час стандартизації стало визначення типу покажчика на функцію. Чи має покажчик на C-функцію відрізнятися за типом від покажчика на C++ функцію з аналогічними аргументами?

У роботах комітету стандартизації було зафіксовано, що мовне зв'язування є повноправною частиною типу функції. Оголошення:

```cpp
extern "C" typedef void (*c_callback_t)(int);
typedef void (*cpp_callback_t)(int);
```

породжують два принципово різні типи в системі типів C++. На апаратних архітектурах, де конвенції викликів C та C++ відрізняються (наприклад, за використанням спеціалізованих регістрів або очищенням стека викликачем vs викликаною функцією), пряме присвоєння покажчика одного типу іншому без явного перехідника порушує цілісність виконання машинного коду.

Також запеклі дискусії точилися навколо взаємодії `extern "C"` із просторами імен (namespaces), доданими в C++ на початку 1990-х років. Комітет ухвалив принципове правило: навіть якщо функція `extern "C"` оголошена всередині простору імен:

```cpp
namespace drivers::net {
    extern "C" void init_socket(int port);
}
```

вона все одно отримує глобальне плоске ім'я `init_socket` у результуючому об'єктному файлі. Оголошення іншої функції `extern "C" void init_socket(int)` у будь-якому іншому просторі імен є грубою помилкою ODR, оскільки простір імен не змінює експортоване ім'я C-символу.

## Канонізація в ARM (1990) та першому стандарті ISO C++98

У 1990 році Маргарет Елліс (Margaret Ellis) та Б'ярн Страуструп опублікували фундаментальну працю *"The Annotated C++ Reference Manual"* (відому як **ARM**), яка стала офіційною базою для роботи комітету зі стандартизації ANSI/ISO C++ (WG21).

В ARM специфікація зв'язування була остаточно формалізована в граматиці мови (розділ 7.4). Стандарт закріпив дві базові специфікації, обов'язкові для абсолютно кожної відповідної реалізації:
- `extern "C++"` — стандартні правила мови C++ (зі спотворенням імен, підтримкою перевантаження та повноцінною системою типів), які активні за замовчуванням для всього коду.
- `extern "C"` — правила взаємодії з мовою C (відключення манглінгу, заборона повторного оголошення функцій із однаковим ім'ям у межах одного зв'язування).

Стандарт також залишив відкриту можливість для компіляторів підтримувати інші мовні зв'язування залежно від операційного середовища. У 1990-х роках на мейнфреймах і спеціалізованих серверах зустрічалися реалізації з підтримкою `extern "FORTRAN"`, `extern "Pascal"` та `extern "Ada"`. Проте в міру стандартизації архітектур x86, SPARC, MIPS та ARM саме двійковий інтерфейс мови C (C ABI) закріпився як універсальна спільна мова двійкового зв'язування для всієї комп'ютерної індустрії.

## Перехід від Cfront до сучасних компіляторів і FFI

На початку 1990-х років індустрія відмовилася від проміжної трансляції через Cfront на користь прямих нативних компіляторів (GCC g++, Clang, MSVC, Sun Studio, IBM XL). З появою окремих оптимізуючих бекендів важливість чіткого розмежування мовних меж лише зросла.

Сьогодні механізм `extern "C"` є фундаментальною основою Foreign Function Interface (FFI) усього сучасного стеку технологій:
- **Rust** використовує блок `extern "C"` для експорту функцій у зовнішні динамічні бібліотеки та виклику C-коду.
- **Python** завантажує двійкові модулі та розширення через `ctypes` і CFFI, спираючись на плоскі C-символи у таблицях `.dynsym` (ELF) та експортних таблицях DLL (PE/COFF).
- **Go** використовує підсистему `cgo` для безшовного виклику C-бібліотек через стандартний C ABI.
- **Java** взаємодіє з нативним простором операційної системи через Java Native Interface (JNI), де кожен експортований метод позначається як `extern "C"`.

Інженерне рішення, розроблене Страуструпом у 1988 році для зшивання Cfront із системною бібліотекою `libc`, стало головним сполучним елементом глобальної інфраструктури системного програмування.
