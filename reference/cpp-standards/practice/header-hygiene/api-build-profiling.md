# 📋 Довідник: прапорці профілювання компілятора та прагми IWYU

Цей довідник містить повну специфікацію прапорців командного рядка компіляторів Clang, GCC та MSVC для діагностики часу збірки, синтаксис аналізатора ClangBuildAnalyzer, а також вичерпний опис спеціальних коментарів-директив (прагм) інструменту Include What You Use (IWYU) і схему конфігураційних файлів мапінгу `.imp`.

---

## 1. Прапорці профілювання та діагностики Clang і GCC

Сучасні компілятори сімейства Clang та GCC надають набір вбудованих діагностичних інструментів для вимірювання часу, який компілятор витрачає на кожен етап трансляції: лексичний аналіз, парсинг заголовків, інстанціювання шаблонів, оптимізацію AST та генерацію машинного коду.

### Механізм трасування Clang `-ftime-trace`

Прапорець `-ftime-trace` активує вбудований у компіляторний фронтенд Clang таймер високої точності на базі системного лічильника процесора (`std::chrono::high_resolution_clock` або інструкції `rdtsc`). Для кожної окремої операції парсингу файлу, розбору класу, інстанціювання шаблону чи оптимізації функції компілятор фіксує мітку початку та тривалість.

Після завершення трансляції цільового файлу `UserSession.cpp` компілятор записує поруч файл `UserSession.json` у стандартному форматі Google Chrome Tracing Event (Catapult). Цей JSON-файл можна безпосередньо завантажити у веб-інтерфейс `chrome://tracing`, `edge://tracing` або сучасний аналізатор профілів `speedscope.app` для візуального дослідження ієрархічного флеймграфа (Flame Graph) компіляції.

Усередині згенерованого JSON-файлу містяться події двох основних фаз:

1. **Фаза фронтенду (`Frontend`)**:
   - `Source`: відкриття, читання та препроцесинг конкретного заголовкового файлу.
   - `ParseDeclarationOrFunctionDefinition`: синтаксичний розбір оголошень функцій, класів та методів.
   - `InstantiateClass` / `InstantiateFunction`: генерація конкретного коду зі спільних шаблонів C++.
2. **Фаза бекенду (`Backend`)**:
   - `OptFunction`: оптимізаційні проходи LLVM над внутрішнім представленням (LLVM IR) конкретної функції.
   - `CodeGenFunction`: перетворення проміжного представлення у машинний ассемблер цільової архітектури.

| Прапорець Clang | Опис та семантика | Приклад використання |
| :--- | :--- | :--- |
| **`-ftime-trace`** | Вмикає детальне ієрархічне трасування всіх операцій фронтенду та бекенду. Для кожного вихідного файлу `file.cpp` компілятор записує поруч файл `file.json` у форматі Chrome Tracing Event. | `clang++ -ftime-trace -c main.cpp` |
| **`-ftime-trace-granularity=N`** | Встановлює мінімальний поріг тривалості операції в мікросекундах (за замовчуванням `500` мкс = 0.5 мс). Операції, які тривають менше ніж `N` мкс, відсікаються для зменшення розміру JSON-файлу. | `clang++ -ftime-trace -ftime-trace-granularity=1000 -c main.cpp` |
| **`-ftime-report`** | Виводить у `stderr` підсумкову таблицю часу виконання фаз компілятора (Parsing, Semantic Analysis, LLVM IR Optimization, Code Generation). | `clang++ -ftime-report -c main.cpp` |
| **`-ftime-report=structure-passed-in-json`** | Виводить структурований звіт про час виконання фаз компілятора у форматі JSON безпосередньо у стандартний потік. | `clang++ -ftime-report=structure-passed-in-json -c main.cpp` |
| **`-H`** | Виводить у `stderr` повне дерево включень заголовкових файлів у процесі препроцесингу. Кожен рівень вкладеності позначається додатковою крапкою (наприклад, `. /usr/include/vector`, `.. /usr/include/bits/stl_vector.h`). | `clang++ -H -c main.cpp` |
| **`-Winvalid-pch`** | Генерує попередження компілятора, якщо вказаний файл попередньо скомпільованого заголовка (PCH) не вдалося використати через невідповідність прапорців або зміну контексту. | `clang++ -Winvalid-pch -include-pch pch.h.pch -c main.cpp` |
| **`-Xclang -print-stats`** | Виводить низькорівневу статистику виділення пам'яті компілятора: кількість створених вузлів AST, ідентифікаторів, типів та розмір таблиць символів. | `clang++ -Xclang -print-stats -c main.cpp` |

### Прапорці генерації залежностей для систем збірки (Clang / GCC)

Системи збірки (Make, Ninja, CMake) не можуть знати про внутрішні залежності C++ файлів без допомоги компілятора. Компілятор аналізує всі директиви `#include` і записує їх у форматі правил Makefile (так звані `.d` depfiles).

- **`-M`**: повністю зупиняє генерацію об'єктного коду і виводить у стандартний потік перелік усіх залежностей (включно із системними заголовками типу `<stdio.h>`).
- **`-MM`**: аналогічно до `-M`, проте ігнорує заголовки, розташовані у системних системних каталогах `/usr/include` або каталогах тулчейна.
- **`-MD`**: виконує повну компіляцію вихідного коду і паралельно записує файл `.d` із повним графом залежностей.
- **`-MMD`**: виконує повну компіляцію вихідного коду і записує файл `.d`, який містить лише користувацькі файли проєкту. Саме цей прапорець використовується генератором Ninja у зв'язці з CMake для швидкої інкрементальної збірки.
- **`-MF <шлях>`**: перевизначає вихідне ім'я файлу залежностей (за замовчуванням `<ім'я_файлу>.d`).
- **`-MP`**: додає до кожного заголовка у згенерованому правилі порожню фіктивну ціль без залежностей. Це запобігає фатальним помилкам систем збірки, коли заголовок було видалено з диска, а старий Makefile продовжує його шукати.
- **`-MT <ціль>`**: змінює ім'я об'єктної цілі в згенерованому файлі залежностей.

## 2. Прапорці профілювання та діагностики MSVC (Microsoft Visual C++)

Компілятор `cl.exe` платформи Windows побудований за класичною двофазною модульною схемою: фронтенд мови C++ (`c1xx.dll`) відповідає за парсинг та семантичний аналіз, після чого передає проміжне бінарне представлення (CIL) бекенду оптимізатора та кодогенератора (`c2.dll`).

Для точного хронометражу кожної з цих бібліотек MSVC надає спеціалізовані службові прапорці.

### Прапорець `/Bt`: розділення часу фронтенду та бекенду

Прапорець `/Bt` наказує компілятору `cl.exe` вимірювати та виводити в мілісекундах час роботи кожного динамічного модуля:

```
time(C:\Program Files\Microsoft Visual Studio\2022\Enterprise\VC\Tools\MSVC\14.38.33130\bin\HostX64\x64\c1xx.dll)=1.248s
time(C:\Program Files\Microsoft Visual Studio\2022\Enterprise\VC\Tools\MSVC\14.38.33130\bin\HostX64\x64\c2.dll)=0.412s
```

Якщо час `c1xx.dll` становить понад 75% загального часу файлу, головною проблемою є роздуті заголовкові файли та шаблони (проблема фронтенду). Якщо ж домінує `c2.dll`, вузьким місцем є важкі оптимізаційні проходи, складні цикли та агресивне вбудовування функцій (проблема бекенду).

### Прапорець `/d2cgsummary`: аудит проходів генератора коду

Недокументований, але широко використовуваний прапорець оптимізатора `/d2cgsummary` друкує структурований звіт про роботу бекенда `c2.dll`:

- `Total Function Count`: загальна кількість функцій, переданих на кодогенерацію (включно з інстанційованими inline-методами із заголовків).
- `Inliner Time`: час, витрачений евристичним аналізатором на оцінку бюджету вбудовування функцій.
- `Optimizer Time`: час виконання класичних оптимізацій (усунення спільних підвиразів, векторизація, розгортання циклів).
- `Global Register Allocator Time`: час розфарбовування графа інтерференції регістрів процесора.

### Прапорець `/showIncludes`: трасування графа включень

Прапорець `/showIncludes` виводить у потік `stdout` повне дерево включень. Для кожного файлу виводиться рядок виду:

```
Note: including file: E:\Engine\include\UserSession.h
Note: including file:  E:\Engine\include\Database.h
Note: including file:   C:\Program Files\Microsoft Visual Studio\...\include\vector
```

Кількість початкових пробілів після двокрапки точно відповідає глибині вкладеності директиви `#include`. IDE Visual Studio та генератор Ninja використовують цей вивід для побудови графа залежностей на платформі Windows.

### Прапорці аналізу пам'яті: `/d1reportAllClassLayout`

Для перевірки вирівнювання даних та виявлення прихованого заповнення (padding) у класах використовують прапорець `/d1reportAllClassLayout` або його точкову версію `/d1reportSingleClassLayout<Ім'яКласу>`. Компілятор виводить детальну карту пам'яті із зазначенням зсуву (`offset`) кожного поля та розміру віртуальних таблиць (`vftable`).

## 3. Інструмент ClangBuildAnalyzer

`ClangBuildAnalyzer` — це автономна кросплатформна утиліта з відкритим вихідним кодом, розроблена Арвідом Норбергом (Arvid Norberg). Вона призначена для агрегації сотень окремих JSON-файлів, згенерованих компілятором Clang з прапорцем `-ftime-trace`, та формування зведеного аналітичного звіту про фактори, які найбільше сповільнюють збірку проєкту.

### Повний синтаксис командного рядка

```bash
# 1. Початковий збір та агрегація всіх JSON-файлів у бінарний архів
ClangBuildAnalyzer --all <шлях_до_каталогу_збірки> <вихідний_архів.bin>

# 2. Формування та вивід текстового аналітичного звіту
ClangBuildAnalyzer --analyze <вихідний_архів.bin>

# 3. Очищення всіх .json файлів трасування з каталогу збірки
ClangBuildAnalyzer --clean <шлях_до_каталогу_збірки>
```

### Алгоритм розрахунку метрик

Під час роботи `ClangBuildAnalyzer` виконує складний топологічний аналіз:

1. **Власна тривалість (Self-Time) проти кумулятивної (Cumulative Time)**: якщо заголовок `A.h` включає `B.h`, загальний час `A.h` включає в себе час `B.h`. Аналізатор віднімає вкладені інтервали, показуючи чистий час парсингу безпосереднього тіла файлу.
2. **Множник реплікації (Inclusion Count Multiplier)**: заголовок, парсинг якого триває лише 50 мс, але який включений у 600 файлів проєкту, створює сумарне навантаження у 30 секунд процесорного часу, опиняючись на перших місцях у списку найдорожчих заголовків (`Top expensive headers`).

## 4. Повний довідник прагм Include What You Use (IWYU)

Інструмент IWYU керується спеціальними коментарями, які вставляються безпосередньо у вихідний код C або C++. Усі прагми починаються з обов'язкового рядка `// IWYU pragma:`.

### Детальний опис та приклади директив

#### `// IWYU pragma: keep`
Наказує аналізатору безумовно зберегти цей рядок `#include`, навіть якщо прямих звернень до символів файлу не знайдено.
```cpp
#include <gtest/gtest.h> // IWYU pragma: keep — необхідний для реєстрації макросів TEST
#include "TypeTraits.h"  // IWYU pragma: keep — містить спеціалізації шаблонів
```

#### `// IWYU pragma: export`
Повідомляє, що поточний файл експортує зазначений заголовок. Будь-який зовнішній файл, який включає поточний, має право звертатися до символів експортованого заголовка без додавання прямого `#include`.
```cpp
#include "Core/Types.h" // IWYU pragma: export
```

#### `// IWYU pragma: begin_exports` та `// IWYU pragma: end_exports`
Блокова версія прагми `export`, яка застосовується до групи заголовків (типово для фасадів бібліотек).
```cpp
// IWYU pragma: begin_exports
#include "Math/Vector3.h"
#include "Math/Matrix4.h"
#include "Math/Quaternion.h"
// IWYU pragma: end_exports
```

#### `// IWYU pragma: private, include "public.h"`
Позначає поточний файл як приватну деталь реалізації. Якщо сторонній код звертається до типів із цього файлу, IWYU вимагатиме включити вказаний публічний заголовок `"public.h"`.
```cpp
// Detail/ConnectionImpl.h
#pragma once
// IWYU pragma: private, include "Network/Connection.h"
```

#### `// IWYU pragma: no_include "header.h"`
Забороняє інструменту IWYU пропонувати підключення зазначеного файлу для поточної трансляційної одиниці.
```cpp
// IWYU pragma: no_include "HeavyLegacyFramework.h"
```

#### `// IWYU pragma: no_forward_declare ClassName`
Забороняє IWYU генерувати неповне оголошення (`forward declaration`) для класу `ClassName`, примушуючи включати повноцінний заголовковий файл.
```cpp
// IWYU pragma: no_forward_declare MyComplexType
```

#### `// IWYU pragma: associated_include "header.h"`
Явно вказує парний заголовковий файл реалізації для поточного `.cpp`, якщо їхні назви або розташування в каталогах відрізняються від стандартної схеми.
```cpp
// src/network_posix_socket.cpp
// IWYU pragma: associated_include "Network/Socket.h"
#include "Network/Socket.h"
```

## 5. Специфікація конфігураційних файлів мапінгу IWYU (.imp)

Файли мапінгу IWYU мають формат JSON і описують глобальні правила перетворення внутрішніх файлів, синонімів та символів на канонічні заголовки публічного API.

### Структура елементів конфігурації

Кожен елемент списку конфігурації є JSON-об'єктом, який реалізує одну з трьох схем:

1. **Мапінг файлів (`include`)**:
   `{ "include": ["<приватний_шлях>", "private", "<публічний_шлях>", "public"] }`
2. **Мапінг символів (`symbol`)**:
   `{ "symbol": ["повне_ім'я_символу", "private", "<публічний_шлях>", "public"] }`
3. **Підключення зовнішніх файлів правил (`ref`)**:
   `{ "ref": "шлях_до_іншого_файлу.imp" }`

### Підтримка регулярних виразів

Якщо рядок шляху починається зі символу `@`, IWYU інтерпретує решту рядка як регулярний вираз формату POSIX Extended Regular Expression. Це дозволяє одним правилом спрямувати всі внутрішні файли бібліотеки на головний заголовок:

```json
[
  {
    "include": [
      "@<boost/asio/detail/.*>",
      "private",
      "<boost/asio.hpp>",
      "public"
    ]
  },
  {
    "include": [
      "@<QtWidgets/private/.*>",
      "private",
      "<QtWidgets/QtWidgets>",
      "public"
    ]
  }
]
```

## 6. Аналіз профілів збірки у Speedscope та Chrome Tracing

Згенеровані компілятором Clang файли `-ftime-trace` у форматі JSON містять сирий потік подій, який складно аналізувати вручну. Для інтерактивного дослідження застосовують візуалізатори трасування.

### Робота з візуалізатором Speedscope

Утиліта `speedscope` (доступна локально як CLI-інструмент або через веб-інтерфейс `speedscope.app`) надає три взаємодоповнюючі режими дослідження часових шкалів:

1. **Режим часової шкали (Time Order)**: відображає хронологічний порядок виконання операцій зліва направо. Дозволяє побачити точний момент, коли компілятор перейшов від синтаксичного аналізу конкретного заголовка до оптимізації функцій бекендом.
2. **Режим узагальненого дерева (Left Heavy)**: групує всі однакові операції та сортує їх за сумарною тривалістю. У цьому режимі одразу видно, які шаблони (наприклад, `std::unordered_map` чи `nlohmann::json`) сумарно забрали найбільше мілісекунд у рамках поточної трансляційної одиниці.
3. **Режим сендвіча (Sandwich View)**: показує для обраної функції список усіх її викликачів (Callers) та викликаних нею внутрішніх підпрограм (Callees) із точним розділенням власного часу виконання (Self Time) та загального часу стека.

## 7. Діагностика часу компонування та Link-Time Code Generation (LTCG / LTO)

Гігієна заголовків безпосередньо впливає не лише на компілятор, а й на лінкер. Коли заголовковий файл містить неоптимальні `inline`-функції або масово розгортає шаблони в сотнях трансляційних одиниць, кожен об'єктний файл `.obj` / `.o` роздувається копіями однакових секцій коду (`.text$mn`, `.pdata`, `.xdata`).

### Прапорці діагностики лінкера MSVC (`link.exe`)

| Прапорець лінкера | Призначення та діагностичний вивід |
| :--- | :--- |
| **`/TIME+`** | Виводить докладний звіт про час виконання кожної фази лінкування: читання об'єктних файлів, побудова таблиці символів, усунення дублікатів (COMDAT folding), створення файлу PDB. |
| **`/VERBOSE:INCR`** | Виводить причини, чому інкрементальне лінкування було скасовано і лінкер перейшов до повної перебудови бінарного файлу. |
| **`/VERBOSE:UNUSEDLIBS`** | Виводить список статичних бібліотек `.lib`, підключених через аргументи лінкера, з яких не було використано жодного символу. |
| **`/OPT:REF` та `/OPT:ICF`** | Вмикає агресивне видалення несилкуваних функцій (`REF`) та злиття ідентичних функцій і шаблонів (`ICF` — Identical COMDAT Folding). |

### Прапорці діагностики лінкера LLD (LLVM) та GNU Gold

- **`-Wl,--time-trace`**: лінкер LLD записує власний JSON-файл трасування часу лінкування (читання секцій, резолв символів, генерація налагоджувальної інформації DWARF).
- **`-Wl,--print-gc-sections`**: виводить у консоль перелік усіх функцій та глобальних змінних, які лінкер видалив як мертвий код.
- **`-Wl,--stats`**: друкує фінальну статистику кількості оброблених символів, релокацій та розміру результуючого бінарного образу.

## 8. Автоматичний аудит чистоти включень через Clang-Tidy

Окрім утиліти IWYU, сучасний тулчейн LLVM включає модуль перевірки `misc-include-cleaner` у складі статичного аналізатора `clang-tidy`.

### Ключові діагностичні правила `clang-tidy`

| Правило clang-tidy | Опис перевірки |
| :--- | :--- |
| **`misc-include-cleaner`** | Перевіряє код на відповідність принципу IWYU: виявляє невикористовувані заголовки (Unused Includes) та використання символів без прямого включення (Missing Includes). Працює на базі сучасного рушія Clang AST. |
| **`llvm-include-order`** | Перевіряє дотримання канонічного порядку директив `#include` (парний заголовок -> заголовки проєкту -> сторонні бібліотеки -> STL -> системні C-заголовки). |
| **`readability-duplicate-include`** | Знаходить дубльовані директиви `#include` в межах одного файлу. |
| **`modernize-deprecated-headers`** | Пропонує заміну застарілих C-заголовків на їхні C++ аналоги (наприклад, `<stdlib.h>` -> `<cstdlib>`, `<math.h>` -> `<cmath>`). |

### Приклад конфігураційного файлу `.clang-tidy`

```yaml
---
Checks: >
  -*,
  misc-include-cleaner,
  llvm-include-order,
  readability-duplicate-include,
  modernize-deprecated-headers

CheckOptions:
  misc-include-cleaner.DeduplicateFindings: true

WarningsAsErrors: 'misc-include-cleaner'
...
```

Запуск аудиту виконується однією командою над базою компіляції:

```bash
clang-tidy -p build/compile_commands.json src/UserSession.cpp
```

## 9. Вбудовані діагностичні інструменти Ninja

Система швидкої збірки Ninja надає набір низькорівневих службових прапорців для аналізу черги задач, критичного шляху збірки та пошуку причин неочікуваних перекомпіляцій.

### Діагностичні режими Ninja (`-d`)

| Прапорець | Опис та семантика |
| :--- | :--- |
| **`ninja -d stats`** | Друкує фінальну статистику продуктивності внутрішніх структур Ninja: час розбору `build.ninja`, кількість запитів до системного кешу `stat()`, час оновлення файлу історії `.ninja_log`. |
| **`ninja -d explain`** | Виводить у консоль детальне пояснення для кожного скомпільованого файлу, чому саме Ninja вирішив його перезібрати (наприклад: `ninja explain: include/Database.h is newer than obj/UserSession.o`). Допомагає миттєво знаходити причини нескінченних перезбірок. |
| **`ninja -d keeprsp`** | Зберігає на диску тимчасові файли відповідей (`@response.rsp`), які містять повні списки прапорців компілятора та шляхів до файлів. |

### Службові інструменти Ninja (`-t`)

- **`ninja -t deps <ціль>`**: виводить точний список усіх транзитивних заголовків, які компілятор зберіг у бінарній базі `.ninja_deps` під час останньої збірки.
- **`ninja -t commands <ціль>`**: друкує точні рядки команд компілятора без їх фактичного запуску.
- **`ninja -t recompact`**: оптимізує та стискає внутрішні бази даних `.ninja_log` та `.ninja_deps`, видаляючи застарілі записи.

## 10. Керуючі цільові властивості CMake для гігієни заголовків

| Властивість CMake | Тип | Опис та вплив на компіляцію |
| :--- | :--- | :--- |
| **`EXPORT_COMPILE_COMMANDS`** | Глобальна змінна | Генерує файл `compile_commands.json`, необхідний для роботи IWYU, Clang-Tidy, ClangBuildAnalyzer та LSP-сервера `clangd`. |
| **`VERIFY_INTERFACE_HEADER_SETS`** | Цільова властивість | Вмикає автоматичну генерацію та компіляцію синтетичних файлів `.cxx` для перевірки самодостатності кожного заголовка у `FILE_SET HEADERS`. |
| **`PCH_INSTANTIATE_TEMPLATES`** | Цільова властивість | Наказує компіляторам Clang та MSVC інстанціювати спільні шаблони під час збірки PCH, зменшуючи час інстанціювання у клієнтських `.cpp`. |
| **`PCH_WARN_INVALID`** | Цільова властивість | Примусово перетворює відмову від використання PCH на помилку або попередження збірки, запобігаючи «тихому» уповільненню компіляції. |

## 11. Специфіка обробки шаблонів та концептів в IWYU

Під час аналізу сучасного C++ коду (C++17/20) розробники стикаються з чотирма складними крайовими випадками IWYU:

1. **Спеціалізації `std::hash<T>` та `std::formatter<T>`**: оскільки структура спеціалізується за межами визначення типу `T`, IWYU вимагає розміщувати повний `#include` файлу зі спеціалізацією або захищати його прагмою `// IWYU pragma: keep`.
2. **Шаблони виразів (Expression Templates у бібліотеках типу Eigen чи Boost.Spirit)**: проміжні типи виразів не мають власних публічних заголовків. Для них обов'язково налаштовують регулярні вирази у файлі `.iwyu.imp`.
3. **Концепти C++20 (`concepts`)**: перевірка концепту `std::integral<T>` вимагає лише заголовка `<concepts>`, тоді як сам тип `T` може залишатися неповним, якщо концепт перевіряє виключно властивості категорій типів.
4. **Пошук імен, залежний від аргументів (Argument-Dependent Lookup, ADL)**: коли виклик вільної функції типу `swap(a, b)` або `serialize(stream, obj)` спирається на ADL у просторі імен аргументу, аналізатор AST може не розпізнати зв'язок безпосереднього виклику, якщо заголовок функції не був підключений явно. У таких сценаріях поруч із викликом обов'язково встановлюють прагму `// IWYU pragma: keep` на рівні заголовка операцій.
5. **Генерація коду через макроси препроцесора**: якщо тип використовується виключно всередині макросу конкатенації токенів чи макросу налагодження (наприклад, `LOG_DEBUG(obj)`), компілятор бачить тип лише після розкриття препроцесора. Для таких конструкцій використовують прагму `// IWYU pragma: associated_include` або додають макрос у таблицю винятків аналізатора.

## 12. Локальні хуки розробника (Git Pre-commit Hooks)

Для того щоб дефекти включень виявлялися безпосередньо в момент створення коміту, а не на стадії відхилення Pull Request у CI, інженерні команди налаштовують локальні Git-хуки (`.git/hooks/pre-commit`):

- **Швидка перевірка форматування та порядку включень**: утиліта `clang-format` з параметром `SortIncludes: CaseSensitive` перевіряє тільки змінені рядки (`git-clang-format`).
- **Інкрементальний запуск IWYU для змінених файлів**: скрипт отримує список змінених `.cpp` через `git diff --cached --name-only` і передає їх у `iwyu_tool.py`, блокуючи коміт у разі виявлення забутих або зайвих заголовків.

Така багаторівнева стратегія — від локального pre-commit хука до компіляторного трасування у CI — перетворює гігієну заголовків на надійний автоматизований конвеєр.
