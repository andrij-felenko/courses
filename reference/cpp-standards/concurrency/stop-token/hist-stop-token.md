# 📜 Еволюція скасування потоків: від POSIX-сигналів до std::stop_token

Коли в паралельній системі фонове обчислення стає непотрібним — через таймаут мережевого запиту, скасування операції користувачем або знайдення шуканого результату сусіднім потоком — виникає фундаментальна інженерна вимога: безпечно та вчасно перервати потік виконання. Протягом трьох десятиліть мови системного програмування C та C++ шукали відповідь на запитання, як поєднати асинхронне переривання потоку з детермінованим управлінням ресурсами та гарантіями безпеки пам'яті.

Шлях до появи заголовка `<stop_token>` у стандарті C++20 проліг крізь невдалі експерименти з примусовим убивством системних потоків, небезпечне розгортання стеку за допомогою винятків та роки гострих дискусій у комітеті стандартизації ISO C++.

---

## 1. Епоха POSIX: ілюзія асинхронного скасування та крах інваріантів

У 1995 році стандарт IEEE POSIX 1003.1c закріпив базовий інтерфейс багатопоточності для UNIX-подібних систем — бібліотеку `pthreads` (POSIX Threads). Серед іншого, стандарт надав функцію `pthread_cancel(pthread_t thread)`, яка надсилала запит на скасування цільовому потоку. POSIX передбачав два фундаментальні режими реакції:

1. **Асинхронне скасування (`PTHREAD_CANCEL_ASYNCHRONOUS`)**: Ядро операційної системи переривало потік у будь-який довільний момент часу — буквально на довільній машинній інструкції процесора.
2. **Відкладене скасування (`PTHREAD_CANCEL_DEFERRED`)**: Потік переривався лише тоді, коли досягав однієї зі стандартизованих «точок скасування» (cancellation points), таких як системні виклики `read()`, `write()`, `sleep()` або `pthread_cond_wait()`.

### Катастрофа асинхронного переривання для пам'яті C++

У мові C для ручного звільнення ресурсів при скасуванні пропонувався макросний механізм `pthread_cleanup_push()` та `pthread_cleanup_pop()`, які реєстрували функції очищення у спеціальному стеку обробників. Проте для C++ асинхронне переривання стало джерелом непереборного невизначеного поводження (Undefined Behavior):

- **Порушення інваріантів динамічної пам'яті**: Якщо апаратне переривання заставало потік посеред виклику оператора `new`, внутрішні таблиці алокатора купи (`ptmalloc` або `jemalloc`) залишалися з розірваними бінарними деревами вільних блоків. Наступна спроба виділення пам'яті в будь-якому іншому потоці призводила до негайного падіння з помилкою `Segmentation fault`.
- **Блокування м'ютексів назавжди**: Якщо потік переривався в критичній секції між захопленням м'ютекса та його звільненням, м'ютекс залишався назавжди замкненим. Будь-який інший потік процесу, що намагався отримати доступ до цих даних, потрапляв у вічний дедлок (deadlock).
- **Відсутність розгортання стеку**: Операційна система просто скидала стек або завершувала виконання потоку без виклику деструкторів локальних C++ об'єктів. Файлові дескриптори, мережеві сокети та блоки пам'яті витікали безповоротно.

Аналогічна проблема існувала у Win32 API з функцією `TerminateThread()`. Виклик `TerminateThread()` миттєво зупиняв потік, не звільняючи його стек, не очищаючи блок TEB (Thread Environment Block) і залишаючи захоплені критичні секції (`CRITICAL_SECTION`) у заблокованому стані на рівні ядра Windows.

### Пастка примусового розгортання стеку: __forced_unwind

Спроба інтегрувати відкладене скасування (`PTHREAD_CANCEL_DEFERRED`) у середовище Linux та GCC NPTL (Native POSIX Thread Library) породила ще одну небезпечну проблему. Розробники компіляторів спробували емулювати скасування через спеціальний внутрішній псевдовиняток `abi::__forced_unwind`.

Коли потік досягав точки скасування, середовище виконання генерувало цей прихований виняток, що змушувало стек розгортатися та викликати деструктори C++. Проте якщо в коді траплявся блок перехоплення `catch (...)`, розробник якого не підозрював про внутрішню кухню бібліотеки `pthreads` і не викликав повторний викид `throw;`, runtime GCC фіксував переривання ланцюжка розгортання та аварійно завершував увесь процес викликом `std::terminate()`. Тисячі надійних бібліотек раптово падали лише тому, що логували невідомі помилки через універсальний блок перехоплення.

## 2. Експеримент Boost.Thread: скасування на основі винятків

У середині 2000-х років Ентоні Вільямс (Anthony Williams) та спільнота розробників бібліотеки Boost.Thread запропонували кооперативну модель переривання, засновану на стандартних винятках мови C++.

У цій моделі об'єкт `boost::thread` мав метод `interrupt()`. Усередині коду потоку розробник міг викликати функцію `boost::this_thread::interruption_point()` або використовувати стандартні блокуючі функції бібліотеки Boost (наприклад, очікування на умовній змінній). Коли потік натрапляв на точку переривання за активного прапорця, бібліотека генерувала звичайний C++ виняток `boost::thread_interrupted`.

```cpp
// Історичний підхід Boost.Thread (2007)
void worker_boost() {
    try {
        while (true) {
            boost::this_thread::interruption_point(); // Точка перевірки
            do_work();
        }
    } catch (const boost::thread_interrupted&) {
        // Чисте переривання та звільнення ресурсів
    }
}
```

Незважаючи на значний прогрес порівняно з POSIX, модель винятків виявила суттєві недоліки у великих архітектурних проектах:

1. **Невидиме поглинання винятків**: Сторонній код або алгоритми часто містили блоки `catch (const std::exception&)` або `catch (...)`. Якщо такий блок перехоплював `boost::thread_interrupted`, сигнал скасування безслідно зникав, і потік продовжував нескінченно працювати.
2. **Небезпека у деструкторах**: Якщо переривання ставалося під час виконання коду всередині деструктора (який сам по собі міг викликати якусь функцію з точкою переривання), виліт винятку з деструктора під час уже наявного розгортання стеку спричиняв негайний `std::terminate()`.
3. **Накладні витрати на таблиці винятків**: Організація точок переривання через механізм Zero-Cost Exceptions вимагала постійної готовності середовища до генерації виняткових станів і створювала додаткове навантаження на таблиці розгортання DWARF.

## 3. Чому C++11 залишив std::thread без механізму скасування

Під час підготовки стандарту C++11 робоча група WG21 під керівництвом Ганса Бема (Hans Boehm) та Лоуренса Краула (Lawrence Crowl) стандартизувала модель пам'яті C++ та базовий клас `std::thread`.

Комітет свідомо відмовився включати в C++11 будь-який механізм скасування. Головна причина полягала у відсутності консенсусу щодо безпечної моделі:
- Асинхронне скасування в стилі POSIX було категорично відкинуто як несумісне з моделлю пам'яті C++ та RAII.
- Модель винятків у стилі Boost.Thread викликала занепокоєння через неконтрольоване поглинання винятків у користувацьких фреймворках та деструкторах.
- Простий атомарний прапорець не міг пробуджувати потоки, заблоковані на системних викликах введення-виведення або умовних змінних.

У результаті стандарт C++11 залишив розробників сам на сам із ручним керуванням: створення пари `std::atomic<bool>` та `std::condition_variable` для кожного окремого потоку стало виснажливою та схильною до помилок рутиною.

## 4. Вплив C# CancellationToken та Go Context

На початку 2010-х років в інших сучасних мовах системного та прикладного програмування кристалізувалася принципово нова концепція: **розділення джерела сигналу та спостерігача через неволодіючі токени**.

- **C# та платформа .NET 4.0 (2010)**: Корпорація Microsoft представила структуру `CancellationToken` та клас `CancellationTokenSource`. Замість зупинки самого потоку, сигнал передавався безпосередньо в асинхронні завдання через неволодіючий токен. Токен дозволяв як регулярне опитування статусу (`IsCancellationRequested`), так і реєстрацію функцій зворотного виклику (`Register(Action)`).
- **Мова Go (2014)**: Пакет `context` запровадив тип `context.Context`, який транслював сигнал зупинки крізь дерево викликів за допомогою закриття спеціального каналу `<-ctx.Done()`.

Ці промислові системи довели дві фундаментальні істини:
1. Скасування має бути виключно **кооперативним**: потік або корутина повинні самі контролювати точки виходу зі свого алгоритму.
2. Необхідний механізм **зворотного виклику (callback)**: коли потік блокується на вводі-виводі або умовній змінній, зовнішній сигнал скасування має автоматично виконати зареєстровану функцію для закриття дескриптора сокета або сповіщення черги.

## 5. Пропозиції P0660 та стандартизація в C++20

У 2017 році Ніколаї Йосутіс (Nicolai Josuttis), Льюїс Бейкер (Lewis Baker) та Ентоні Вільямс (Anthony Williams) представили робочій групі WG21 серію пропозицій, що завершилися документом **P0660: Stop Token and Joining Thread**.

Протягом трьох років обговорень автори та комітет вирішували складні інваріанти синхронізації та продуктивності:
- **Семантика пам'яті (Memory Ordering)**: Було погоджено, що успішний виклик `request_stop()` виконує атомарний запис із семантикою `std::memory_order_release` або `std::memory_order_acq_rel`, тоді як перевірка `stop_requested()` синхронізується з цим записом за допомогою `std::memory_order_acquire`. Це гарантує, що всі операції запису в пам'ять, здійснені ініціатором до сигналу скасування, стають повністю видимими для робочого потоку.
- **Синхронне виконання зворотних викликів**: Комітет категорично відхилив ідею створення окремих фонових потоків-обробників для колбеків. Усі зареєстровані об'єкти `std::stop_callback` зобов'язані виконуватися синхронно в контексті того самого системного потоку, який викликав `request_stop()`.
- **Гарантія безпечної деструкції**: Якщо деструктор `~stop_callback()` викликається в момент, коли інший потік прямо зараз виконує відповідну функцію зворотного виклику, деструктор блокується до повного завершення цієї функції. Це фундаментальне рішення усунуло будь-яку можливість появи невизначеного поводження через вимивання захоплених посилань на локальний стек.
- **Оптимізація нульових витрат (`std::nostopstate`)**: Для випадків, коли потік або бібліотечний компонент гарантовано не потребує скасування, комітет додав тег `std::nostopstate`. Це дозволило конструювати об'єкти джерела та токена без виділення динамічної пам'яті в купі під спільний блок керування.

Фінальний дизайн закріпив триєдину архітектуру:
1. `std::stop_source`: Об'єкт, що володіє ексклюзивним правом ініціювати зупинку через метод `request_stop()`.
2. `std::stop_token`: Легковажний об'єкт для опитування (`stop_requested()`), який можна безпечно копіювати та передавати в потоки за значенням.
3. `std::stop_callback`: RAII-об'єкт підписки на сигнал скасування.

У лютому 2020 року на пленарному засіданні комітету ISO C++ у Празі специфікація `<stop_token>` була одноголосно затверджена та офіційно увійшла до фінального міжнародного стандарту ISO/IEC 14882:2020 (C++20). Це поклало край чвертьстолітнім пошукам безпечного, елегантного та масштабованого механізму скасування в C++.
