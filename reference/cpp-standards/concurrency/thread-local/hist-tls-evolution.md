# 📜 Еволюція локальної пам'яті потоку: від ручних ключів до thread_local

У 1990-х роках із появою багатоядерних архітектур та стандартизацією системних потоків POSIX (IEEE Std 1003.1c-1995 `pthreads`) розробники зіткнулися з фундаментальною дилемою: як надати паралельним потокам незалежний робочий стан без використання блокувань м'ютекса і без передачі службового контексту крізь усі рівні викликів функцій. Звичайні глобальні змінні (`static` або зовнішні `extern`) створювали критичні гонки даних (data races), а захист кожного звернення м'ютексом уповільнював паралельні алгоритми у десятки разів через постійний кеш-контеншн (cache contention) між процесорними ядрами.

Першою офіційною відповіддю індустрії став механізм потоково-специфічних даних (Thread-Specific Data — TSD). У стандарті POSIX для цього запровадили API на основі ключів: `pthread_key_create()`, `pthread_setspecific()` та `pthread_getspecific()`. У середовищі Win32 для операційної системи Windows NT 3.1 корпорація Microsoft запропонувала аналогічний набір викликів: `TlsAlloc()`, `TlsSetValue()` та `TlsGetValue()`. Цей підхід розв'язував задачу функціонально, проте ціною колосальних накладних витрат під час виконання.

Найяскравішим прикладом системної кризи стала глобальна змінна `errno` у стандартній бібліотеці мови C. В однопотокових системах `errno` була простим скалярним цілим числом у сегменті даних (`.data`). Щойно програми почали виконувати паралельні системні виклики (наприклад, одночасне читання з сокетів), один потік перезаписував код помилки іншого до того, як той встигав його перевірити. Щоб зберегти працездатність API без зміни сигнатур тисяч системних функцій, розробники бібліотек libc пішли на вимушений трюк: перетворили `errno` на макрос препроцесора, який розгортався у виклик внутрішньої функції:

:::tabs
```c
/* Традиційна трансформація errno в системних C-бібліотеках */
#define errno (*__errno_location())  /* glibc (Linux) */
#define errno (*_errno())            /* MSVC CRT (Windows) */
```
```cpp
// Сучасна C++ альтернатива локального стану помилки
#include <system_error>

thread_local std::error_code last_thread_error{};
```
:::

Кожне звернення до `errno` тепер вимагало непрямого виклику функції, вилучення ідентифікатора потоку та пошуку в масиві TSD. На операціях введення-виведення з високою частотою перевірок це створювало помітне падіння пропускної здатності процесора.

## 1. Епоха ручних ключів: ціна динамічного пошуку TSD

Механізм TSD спирався на глобальну таблицю дескрипторів та масив покажчиків, прив'язаний до структури управління потоком. Щоб зберегти значення, потік мусив спочатку створити спільний ключ `pthread_key_t`, а потім під час кожної операції читання або запису виконувати системний або бібліотечний виклик, що витягував значення за індексом у масиві потоку.

Головними вадами підходу були:
1. **Накладні витрати на виклик функцій**: Замість однієї інструкції читання з пам'яті процесор мусив виконувати повноцінний виклик функції `pthread_getspecific()`, що скидало регістровий контекст і ламало конвеєр інструкцій CPU.
2. **Втрата типізації**: API приймало та повертало виключно нетипізовані покажчики `void*`. Будь-яка робота зі скалярними значеннями (`int`, `double`) вимагала або динамічного виділення пам'яті в купі (`malloc`/`free`), або небезпечного приведення цілих чисел до покажчиків.
3. **Ручне управління пам'яттю**: Розробник мав власноруч писати функцію-деструктор для очищення пам'яті під час завершення потоку, що часто призводило до витоків пам'яті (memory leaks) або помилок використання після звільнення (use-after-free).

:::tabs
```c
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

static pthread_key_t thread_log_key;
static pthread_once_t key_once = PTHREAD_ONCE_INIT;

static void destroy_log_buffer(void* buf) {
    free(buf);
}

static void init_log_key(void) {
    pthread_key_create(&thread_log_key, destroy_log_buffer);
}

void append_log(const char* msg) {
    pthread_once(&key_once, init_log_key);
    char* buf = (char*)pthread_getspecific(thread_log_key);
    if (!buf) {
        buf = (char*)malloc(1024);
        pthread_setspecific(thread_log_key, buf);
    }
    snprintf(buf, 1024, "Log: %s\n", msg);
}
```
```cpp
#include <pthread.h>
#include <memory>
#include <string>
#include <mutex>

namespace legacy_tls {
    static pthread_key_t thread_log_key;
    static std::once_flag key_init_flag;

    static void destroy_cpp_buffer(void* ptr) {
        delete static_cast<std::string*>(ptr);
    }

    void append_log(const std::string& msg) {
        std::call_once(key_init_flag, []() {
            pthread_key_create(&thread_log_key, destroy_cpp_buffer);
        });

        auto* buf = static_cast<std::string*>(pthread_getspecific(thread_log_key));
        if (!buf) {
            buf = new std::string();
            pthread_setspecific(thread_log_key, buf);
        }
        *buf = "Log: " + msg + "\n";
    }
}
```
:::

У високочастотних операціях — таких як генерація випадкових чисел у гарячому циклі, виділення дрібних об'єктів у локальній арені чи оновлення системної змінної `errno` — постійні виклики `pthread_getspecific()` сповільнювали код у 20–40 разів порівняно зі звичайним доступом до пам'яті.

## 2. Компіляторні розширення: __thread та __declspec(thread)

На межі 1990-х та 2000-х років розробники компіляторів зрозуміли: підтримка локального стану потоку має бути вбудована безпосередньо у мову та апаратно підтримана процесором. Якщо операційна система виділяє кожному потоку власний базовий регістр сегментації (регістр `FS` або `GS` на архітектурі x86/x86-64), компілятор може генерувати звернення до локальних змінних як пряме асемблерне зміщення відносно цього регістра.

Так з'явилися пропрієтарні розширення:
- **`__declspec(thread)`** у Microsoft Visual C++ (введено для Windows NT ще у 1993 році).
- **`__thread`** у GNU C/C++ Compiler (GCC 3.1, 2001–2002 роки).

Ці розширення перетворили доступ до локальних даних на одну швидку апаратну інструкцію виду `movq %fs:offset, %rax`. Час доступу зрівнявся зі звичайними глобальними змінними.

Однак обидва розширення мали серйозні обмеження:
- **Лише тривіальні типи (POD)**: Підтримувалися тільки примітивні типи або C-подібні структури без користувацьких конструкторів і деструкторів. Оголосити `__thread std::string` або `__thread std::vector<int>` було неможливо: компілятор не знав, коли викликати конструктор для нового потоку і де реєструвати деструктор.
- **Відсутність єдиного стандарту**: Код, написаний під GCC з `__thread`, не компілювався під MSVC, а код з `__declspec(thread)` ламався при динамічному завантаженні бібліотек через `LoadLibrary()` у старих версіях Windows XP.

## 3. Специфікація ELF TLS Ульріха Дреппера (2001–2002)

Справжній інженерний прорив у реалізації локальної пам'яті потоку відбувся у 2001–2002 роках, коли Ульріх Дреппер (Ulrich Drepper) із компанії Red Hat разом із Якубом Єлінеком (Jakub Jelinek) та інженерами Sun Microsystems опублікували фундаментальний документ: *«ELF Handling For Thread-Local Storage»*.

Дреппер сформулював уніфіковану модель компонування для бінарного формату ELF (Executable and Linkable Format), яка лягла в основу стандартних бібліотек C (`glibc`), динамічних лінкерів (`ld.so`) та операційних систем Linux, FreeBSD і Solaris.

Специфікація запровадила чотири ключові концепти:
1. **Секції бінарного образу `.tdata` та `.tbss`**: Спеціальні секції, які містять шаблон для ініціалізованих та нульових локальних даних потоку. Під час створення кожного нового потоку ядро або рантайм копіює секцію `.tdata` у виділену сторінку пам'яті та занулює діапазон `.tbss`.
2. **Блок керування потоком (Thread Control Block — TCB)**: Системна структура, на яку вказує сегментний регістр `FS` (на x86-64) або `GS`. Зсуви відносно покажчика потоку (Thread Pointer — TP) визначають фізичну адресу змінної в пам'яті.
3. **Динамічний вектор потоків (Dynamic Thread Vector — DTV)**: Таблиця покажчиків, яка дозволяє потоку ліниво адресувати локальні змінні у бібліотеках, завантажених під час роботи програми через системний виклик `dlopen()`.
4. **Чотири моделі доступу до TLS**: Formalized models (Local Exec, Initial Exec, Local Dynamic, General Dynamic), які дозволили компіляторам і лінкерам оптимізувати доступ до змінних залежно від того, де змінна оголошена та де вона використовується.

Завдяки специфікації Дреппера апаратна підтримка TLS стала стандартом де-факто для операційних систем POSIX.

## 4. Шлях до стандарту C++11: пропозиції Лоуренса Кроула

Після стандартизації механізму в ELF та системних C-бібліотеках виникла нагальна потреба ввести повноцінну підтримку локального стану в ядро мови C++. На відміну від мови C, у C++ об'єкти мають нетривіальні життєві цикли: конструктори, деструктори, семантику копіювання та переміщення, а також поліморфізм.

У період з 2005 по 2008 рік робоча група комітету стандартизації C++ (WG21) під керівництвом Лоуренса Кроула (Lawrence Crowl) із компанії Google підготувала серію пропозицій:
- **N1966 (2006)**: *«Thread-Local Storage»* — перший системний аналіз синтаксису та семантики.
- **N2280 (2007)**: *«Thread-Local Storage (Revision 2)»* — уточнення правил зв'язування (linkage) та ініціалізації.
- **N2659 (2008)**: *«Thread-Local Storage»* — фінальний документ, затверджений комітетом для включення у робочий проєкт майбутнього стандарту C++11.

Головні дискусії в комітеті точилися довкола трьох архітектурних питань:
1. **Вибір ключового слова**: Пропонувалися варіанти `__thread`, `__thread_local`, `threadlocal` та `thread_local`. Комітет обрав `thread_local` як повноцінний специфікатор тривалості зберігання (storage class specifier), поставивши його в один ряд із `static`, `extern` та `auto`.
2. **Момент динамічної ініціалізації**: Якщо об'єкт `thread_local` вимагає виклику конструктора з параметрами, коли саме він має конструюватися? Було вирішено: глобальні об'єкти `thread_local` можуть ініціалізуватися або при запуску потоку, або ліниво (lazy initialization) при першому зверненні до будь-якої змінної з даної одиниці трансляції. Локальні блочні змінні ініціалізуються суворо при першому переході виконання через їхнє оголошення.
3. **Механізм деструкції об'єктів**: Для коректного знищення нетривіальних C++ об'єктів при завершенні потоку консорціум Itanium C++ ABI розробив функцію `__cxa_thread_atexit()`. Вона реєструє виклики деструкторів для кожного потоку окремо, забезпечуючи виконання деструкторів у порядку, суворо зворотному до завершення їхніх конструкторів.

## 5. Розвиток у C++20: подолання динамічних пасток через constinit

У стандарті C++11 специфікатор `thread_local` став потужним інструментом, проте розробники високопродуктивних систем зіткнулися з проблемою прихованого оверхеду. Якщо об'єкт `thread_local` ініціалізувався динамічно, компілятор був змушений огортати кожне звернення до змінної перевіркою службового прапорця ініціалізації (`guard variable`). Це перетворювало 1 такт читання пам'яті на умовне розгалуження та виклик прихованої функції-обгортки.

Крім того, виникала загроза так званого *Static Initialization Order Fiasco*: якщо `thread_local` змінна в одному файлі намагалася звернутися до іншої `thread_local` змінної з іншого файлу до її ініціалізації, програма отримувала невизначену поведінку (UB).

У стандарті C++20 цю проблему остаточно розв'язали введенням специфікатора `constinit` (пропозиція P0886 / P2116). Специфікатор `constinit thread_local` вимагає від компілятора гарантувати константну ініціалізацію під час компіляції:
- Компілятор розміщує початкове значення безпосередньо в секції `.tdata`.
- Під час створення потоку пам'ять уже готова до використання.
- Повністю усуваються приховані функції-обгортки, перевірки guard-прапорців та небезпека міжмодульних гонок ініціалізації.

Таким чином, еволюція локального стану потоку пройшла повний тридцятирічний шлях: від повільних нетипізованих функціональних викликів POSIX TSD до безнакладного, строго типізованого та безпечного системного примітиву `thread_local` у сучасному C++.
