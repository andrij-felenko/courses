# 📋 Довідник нововведень C++11 та C++14: ядро, STL, макроси та депрекації

Систематизований реєстр синтаксичних конструкцій ядра, підсистем бібліотеки STL, макросів інспекції компілятора та застарілих елементів мови, стандартизованих у специфікаціях ISO/IEC 14882:2011 (C++11) та ISO/IEC 14882:2014 (C++14).

## 1. Специфікація нововведень ядра мови

У цьому розділі наведено архітектурний опис та нормативні вимоги до синтаксичних конструкцій ядра, введених у стандартах C++11 та C++14.

| **Автовиведення `auto`** | C++11 | `auto var = expr;` | Виводить тип змінної на етапі статичного аналізу AST за правилами виведення типів аргументів шаблонів функцій, відкидаючи посилання та модифікатори `const` верхнього рівня. |
| **Оператор `decltype`** | C++11 | `decltype(expr) var;` | Обчислює точний тип виразу без його виконання під час роботи програми, зберігаючи всі посилання, константність та специфікатори типу. |
| **Лямбда-вирази** | C++11 | `[cap](params) -> ret { body }` | Компілятор генерує унікальний анонімний клас-функтор із полями для захоплених змінних та константним перевантаженням оператора виклику функції `operator()`. |
| **Константні функції `constexpr`** | C++11 | `constexpr ret func(params);` | Вимагає можливості виконання функції під час компіляції за умови передачі константних аргументів; у C++11 тіло обмежене рівно одним оператором `return`. |
| **Уніфікована ініціалізація** | C++11 | `Type var{arg1, arg2};` | Забезпечує уніфікований синтаксис прямої ініціалізації агрегатів і класів, блокуючи неявні перетворення зі звуженням розрядності (Narrowing Conversions). |

| **Типізований нуль `nullptr`** | C++11 | `nullptr` | Літерал окремого фундаментального типу `std::nullptr_t`, який неявно приводиться до будь-якого вказівника на об'єкт або функцію, але не приводиться до цілих типів. |
| **Строгі переліки `enum class`** | C++11 | `enum class Name : BaseType` | Ізолює імена елементів у власному просторі імен переліку, усуває неявне перетворення до типу `int` та дозволяє фіксувати точний розмір підкладного цілого типу. |

| **Специфікатор `final`** | C++11 | `class C final;` / `f() final;` | Забороняє подальше спадкування від класу або перевизначення віртуального методу в похідних класах, що дозволяє оптимізатору застосовувати девіртуалізацію викликів. |
| **Керування генерацією методів** | C++11 | `= default;` / `= delete;` | `= default` вимагає від компілятора згенерувати стандартну реалізацію спеціального члена класу; `= delete` повністю забороняє виклик і бере участь у розв'язанні перевантажень. |
| **Варіативні шаблони** | C++11 | `template<typename... Args>` | Дозволяє шаблонам приймати довільну кількість типів або значень; розпакування здійснюється через синтаксис `Args...` або оператор розміру `sizeof...(Args)`. |
| **Цикл по діапазону (range-for)** | C++11 | `for (auto&& x : range)` | Транслюється компілятором у класичний цикл по ітераторах `auto __begin = begin(range)`, `auto __end = end(range)` із перевіркою `__begin != __end` та інкрементом `++__begin`. |
| **Псевдоніми типів `using`** | C++11 | `template<class T> using P = ...` | Повноцінна заміна застарілого `typedef`, яка на відміну від останнього підтримує параметризацію шаблонами (Template Aliases). |
| **Узагальнені лямбди** | C++14 | `[](auto x, auto y) { ... }` | Компілятор генерує анонімну структуру, де оператор виклику `operator()` є шаблонним методом `template<typename T1, typename T2> auto operator()(T1 x, T2 y) const`. |
| **Захоплення з ініціалізацією** | C++14 | `[var = expr]() { ... }` | Дозволяє вводити нові іменовані змінні в замикання безпосередньо у списку захоплення, відкриваючи можливість захоплення об'єктів за семантикою переміщення `[p = std::move(ptr)]`. |
| **Імперативний `constexpr`** | C++14 | `constexpr` з циклами й змінами | Дозволяє використання локальних змінних, циклів `for`/`while`, розгалужень `if`/`switch` та неконстантних функцій-членів, якщо об'єкт створюється в межах константного виразу. |
| **Виведення результату функцій** | C++14 | `auto func() { return val; }` | Компілятор автоматично виводить тип повернення звичайної функції з виразу в операторі `return` за правилами шаблонів, або за правилами `decltype`, якщо вказано `decltype(auto)`. |
| **Шаблонні змінні** | C++14 | `template<class T> constexpr T var` | Дозволяє параметризувати константи та глобальні змінні типами без необхідності загортати їх у фіктивні статичні структури-обгортки. |
| **Двійкові літерали й роздільники** | C++14 | `0b1010'0101`, `1'000'000` | Префікс `0b` або `0B` задає двійкове числове представлення; одинарний апостроф `'` слугує візуальним роздільником розрядів і повністю ігнорується транслятором. |

### Механізм роботи rvalue-посилань і переміщення

Введення rvalue-посилань зажадало формального розділення операцій копіювання та переміщення. Коли компілятор зустрічає передачу аргументу, він аналізує його категорію значення:
1. Якщо вираз є `lvalue` (іменована змінна), вибирається перевантаження, що приймає `const T&`. Виконується глибоке копіювання з виділенням нової пам'яті.
2. Якщо вираз є `prvalue` (безпосередній результат обчислення виразу) або `xvalue` (об'єкт, явно обгорнутий у `std::move`), вибирається перевантаження з `T&&`. Викликається конструктор або оператор переміщення, який забирає покажчики на динамічні ресурси.

Стан об'єкта після переміщення (стан *moved-from*) за стандартом ISO повинен залишатися валідним, але не специфікованим (англ. *valid but unspecified state*). Це означає, що для такого об'єкта гарантовано можна викликати деструктор або присвоїти йому нове значення, але читання його внутрішніх даних без попередньої ініціалізації є логічною помилкою.

### Механіка компіляції лямбда-виразів

Лямбда-вираз не є функціональним вказівником. Це синтаксичний цукор над генерацією строго типізованого функціонального об'єкта (замикання, англ. *closure*).

Якщо лямбда має порожній список захоплення `[]`, стандарт C++11 вимагає наявності неявного оператора перетворення до звичайного вказівника на функцію `typedef ret (*func_ptr)(params)`. Це забезпечує повну сумісність лямбд із класичними C-бібліотеками, які приймають зворотні виклики (callbacks) у вигляді вказівників `void (*cb)(void*)`.

Якщо ж список захоплення містить змінні, розмір згенерованої структури стає рівним сумарному розміру захоплених посилань і копій значень з урахуванням правил вирівнювання структури в пам'яті (структурного паддингу).

## 2. Каталог підсистем стандартної бібліотеки (STL)

### Оптимізації пам'яті: `std::make_shared` проти `std::make_unique`

Конструкція `std::make_shared<T>(args...)` виконує одне суцільне виділення пам'яті в купі (Single Heap Allocation), розміщуючи контрольний блок лічильників і сам об'єкт `T` поруч. Це мінімізує фрагментацію оперативної пам'яті та підвищує швидкодію за рахунок локальності кешу ЦП. Проте розробник повинен пам'ятати про крайовий випадок: пам'ять під сам об'єкт `T` не може бути звільнена доти, доки існує хоча б один живий екземпляр `std::weak_ptr`, оскільки контрольний блок і тіло об'єкта виділені в одному суцільному шматку пам'яті.

На відміну від неї, `std::make_unique<T>(args...)` у C++14 принципово не має контрольного блоку. Його завдання полягає у забезпеченні суворої виняткобезпеки під час обчислення складних виразів виклику функцій. Якщо вираз передає кілька розумних вказівників у функцію, порядок обчислення аргументів у C++11 не був зафіксований, що створювало ризик незворотного витоку пам'яті при виникненні винятку у сусідньому виразі.

```cpp
// Небезпечно у C++11 (можливий витік пам'яті, якщо другий new кине виняток до виклику конструктора unique_ptr):
process(std::unique_ptr<A>(new A()), std::unique_ptr<B>(new B()));

// Безпечно у C++14 (гарантований захист від витоків на рівні стандарту):
process(std::make_unique<A>(), std::make_unique<B>());
```

## 3. Детальний аналіз моделі синхронізації та порядків пам'яті `<atomic>`

Заголовок `<atomic>` у C++11 визначає шість різних режимів упорядкування пам'яті (Memory Orders), які дають змогу програмісту обирати точний баланс між суворістю узгодженості даних та швидкодією на процесорних архітектурах зі слабким порядком пам'яті (ARM, PowerPC, RISC-V):

1. **`std::memory_order_relaxed`:**
   Гарантує лише атомарність самої операції читання або запису. Жодних обмежень на перестановку навколишніх операцій читання або запису компілятором чи процесором не накладається. Використовується виключно для простих лічильників (наприклад, лічильників переглядів або метрик), де порядок подій не впливає на коректність програми.

2. **`std::memory_order_consume`:**
   Спеціалізований слабкий режим для операцій читання. Встановлює порядок тільки для тих наступних інструкцій, які мають пряму залежність за даними від завантаженого значення (Data Dependency). У практиці компіляторів цей режим часто неявно транслюється в сильніший `memory_order_acquire` через складність підтримки ланцюжків залежностей оптимізаторами AST.

3. **`std::memory_order_acquire`:**
   Застосовується для операцій читання (Load). Гарантує, що жодне читання чи запис пам'яті в поточному потоці, розташоване в тексті програми після операції з `acquire`, не може бути переставлене компілятором чи процесором перед цією операцією. Усі записи, виконані іншим потоком до парного `release`, стають гарантовано видимими в поточному потоці.

4. **`std::memory_order_release`:**
   Застосовується для операцій запису (Store). Гарантує, що жодне читання чи запис пам'яті в поточному потоці, розташоване до операції з `release`, не може бути переставлене після цієї операції. Усі попередні модифікації пам'яті «скидаються» і стають видимими для будь-якого іншого потоку, який виконає `acquire` над тим самим атомарним прапорцем.

5. **`std::memory_order_acq_rel`:**
   Поєднує властивості `acquire` та `release`. Застосовується виключно для операцій типу «читання-модифікація-запис» (Read-Modify-Write), таких як `fetch_add`, `fetch_sub` або `compare_exchange_strong`.

6. **`std::memory_order_seq_cst` (Sequential Consistency):**
   Режим послідовної узгодженості, який діє за замовчуванням для всіх атомарних операцій у C++. На додаток до семантики `acquire-release` встановлює глобальний єдиний тотальний порядок виконання всіх атомарних операцій для всієї системи, що спостерігається однаково всіма ядрами процесора.

На апаратній платформі x86-64 через дію вбудованої моделі TSO (Total Store Order) апаратні операції запису ніколи не обганяють інші записи, а читання не обганяють читання. Тому `acquire` та `release` транслюються компілятором у звичайні інструкції `MOV` без накладних витрат. На архітектурах ARMv7/ARMv8 компілятор змушений генерувати спеціальні апаратні бар'єри пам'яті `DMB ISHLD` та `DMB ISHST`.

## 4. Фізичний час, випадкові числа та системні помилки

Окрім паралелізму, стандарт C++11 докорінно оновив три критичні системні підсистеми:

### Підсистема вимірювання часу `<chrono>`

Бібліотека `<chrono>` побудована на концепції розмірностей фізичних величин, що виключає поширені помилки передачі мілісекунд у функції, які очікують секунди або мікросекунди:
- **Тривалість (`std::chrono::duration`):** представляє проміжок часу як кількість тіків заданого періоду (наприклад, `std::chrono::milliseconds`). Операції додавання та віднімання різних тривалостей виконуються з автоматичним приведенням до найменшого спільного знаменника.
- **Часова точка (`std::chrono::time_point`):** представляє конкретний момент часу відносно епохи годинника (Epoch).
- **Типи годинників:** `std::chrono::system_clock` (системний настінний час, може стрибати назад при корекції NTP), `std::chrono::steady_clock` (монотонний таймер, який ніколи не зменшується і гарантує точність вимірювання інтервалів виконання коду) та `std::chrono::high_resolution_clock` (годинник із найменшим доступним періодом тіку).

У C++14 роботу з часом спростили за допомогою стандартних суфіксів літералів у просторі імен `std::chrono_literals`, що дозволило писати `auto timeout = 100ms;` замість `std::chrono::milliseconds(100)`.

### Підсистема генерації випадкових чисел `<random>`

Застаріла C-функція `rand()` мала суттєві вади: малий період генерації (зазвичай `2^32`), нерівномірність розподілу молодших бітів та залежність від глобального стану процесу.

Заголовок `<random>` розділив генерацію на дві незалежні ортогональні сутності:
1. **Генератори псевдовипадкових послідовностей (Engines):** наприклад, вихровий генератор Мерсенна `std::mt19937` із гігантським періодом `2^19937 - 1`, а також апаратне джерело ентропії `std::random_device` для генерації випадкових початкових зерен (Seed).
2. **Статистичні розподіли (Distributions):** класи, які перетворюють рівномірний бітовий потік від генератора у математично точні розподіли: `std::uniform_int_distribution` (рівномірний цілочисельний), `std::normal_distribution` (нормальний гауссівський), `std::bernoulli_distribution` (розподіл Бернуллі) тощо.

### Кросплатформна обробка помилок `<system_error>`

Заголовок `<system_error>` стандартизував структуру передачі та класифікації системних помилок ядра ОС, сокетів та файлових дескрипторів:
- `std::error_code`: зберігає числове значення помилки (платформний код, наприклад `errno` або код Win32 `GetLastError()`) та покажчик на категорію `const std::error_category&`.
- `std::error_condition`: абстрактна переносима помилка (наприклад, помилка відмови у доступі `permission_denied`), з якою можна порівнювати платформозалежні коди через перевантажений оператор `==`.
- `std::system_error`: стандартний виняток, який інкапсулює `std::error_code` та автоматично формує інформативне повідомлення методом `what()`.

## 5. Макроси перевірки можливостей транслятора

Для організації умовної компіляції у великих проєктах, що збираються під різними версіями компіляторів (GCC, Clang, MSVC, Apple Clang), стандарт C++14 нормалізував макроси перевірки можливостей (англ. *Feature Testing Macros*). 

Значення макроса кодується у форматі цілого числа `YYYYMML`, яке позначає рік і місяць прийняття відповідного нормативного документа робочою групою WG21:

```cpp
#include <iostream>

// Перевірка підтримки узагальнених лямбд стандарту C++14
#if defined(__cpp_generic_lambdas) && __cpp_generic_lambdas >= 201304L
    #define HAS_GENERIC_LAMBDAS 1
#else
    #define HAS_GENERIC_LAMBDAS 0
#endif

// Перевірка наявності розширеного constexpr C++14
#if defined(__cpp_constexpr) && __cpp_constexpr >= 201304L
    #define HAS_RELAXED_CONSTEXPR 1
#else
    #define HAS_RELAXED_CONSTEXPR 0
#endif

// Перевірка двійкових літералів
#if defined(__cpp_binary_literals) && __cpp_binary_literals >= 201304L
    constexpr auto bitmask = 0b1010'1111;
#else
    constexpr auto bitmask = 0xAF;
#endif
```

Повний нормативний перелік макросів ядра наведено нижче:
- `__cpp_rvalue_references` (`200610L`) — підтримка rvalue-посилань і семантики переміщення.
- `__cpp_variadic_templates` (`200704L`) — варіативні шаблони зі змінною кількістю аргументів.
- `__cpp_initializer_lists` (`200806L`) — уніфікована ініціалізація та `std::initializer_list`.
- `__cpp_lambdas` (`200907L`) — базові лямбда-вирази C++11.
- `__cpp_constexpr` (`200704L` для C++11, `201304L` для C++14) — константні вирази часу компіляції.
- `__cpp_decltype` (`200707L`) — базовий оператор отримання типу `decltype`.
- `__cpp_decltype_auto` (`201304L`) — автоматичне виведення типу за правилами decltype у C++14.
- `__cpp_generic_lambdas` (`201304L`) — поліморфні узагальнені лямбда-вирази з параметрами `auto`.
- `__cpp_init_captures` (`201304L`) — захоплення з ініціалізацією та переміщенням у лямбдах C++14.
- `__cpp_variable_templates` (`201304L`) — шаблонні змінні та константи C++14.
- `__cpp_binary_literals` (`201304L`) — двійкові числові літерали `0b...`.
- `__cpp_return_type_deduction` (`201304L`) — виведення типу повернення функцій за оператором return.

## 6. Метапрограмування та бібліотека `<type_traits>`

Бібліотека метафункцій `<type_traits>` дозволяє досліджувати характеристики типів під час трансляції та умовно активувати перевантаження функцій за допомогою правила SFINAE (англ. *Substitution Failure Is Not An Error* — невдача підстановки не є помилкою).

### Інспекція та порівняння типів

Кожна метафункція інспекції у C++11 є структурою, яка успадковує `std::integral_constant<bool, Value>`. Отримання логічного результату здійснюється через звернення до статичного поля `::value`:

```cpp
#include <type_traits>

template<typename T>
void analyze_type() {
    // Перевірка категорії типу
    constexpr bool is_int = std::is_integral<T>::value;
    constexpr bool is_float = std::is_floating_point<T>::value;
    constexpr bool is_ptr = std::is_pointer<T>::value;

    // Перевірка можливостей життєвого циклу
    constexpr bool is_trivially_copyable = std::is_trivially_copyable<T>::value;
    constexpr bool is_nothrow_move = std::is_nothrow_move_constructible<T>::value;
}
```

### Трансформація типів та спрощення C++14

У C++11 метафункції модифікації типів повертали результат через внутрішній тип `::type`. Це вимагало постійного використання ключового слова `typename` у шаблонному коді. Стандарт C++14 запровадив зручні шаблонні псевдоніми з суфіксом `_t`:

```cpp
// Порівняння синтаксису C++11 та C++14 під час обмеження SFINAE:

// C++11: багатослівний синтаксис із typename та ::type
template<typename T, 
         typename = typename std::enable_if<std::is_integral<T>::value>::type>
void process_number_c11(T val) {
    typedef typename std::remove_reference<T>::type CleanType;
    typedef typename std::decay<T>::type DecayedType;
}

// C++14: компактний синтаксис через псевдоніми _t
template<typename T, 
         typename = std::enable_if_t<std::is_integral<T>::value>>
void process_number_c14(T val) {
    using CleanType   = std::remove_reference_t<T>;
    using DecayedType = std::decay_t<T>;
}
```

Важливою метафункцією трансформації є `std::decay<T>`. Вона емулює правила неявного приведення типів під час передачі аргументів у функції за значенням:
1. Видаляє посилання `&` та специфікатори константності `const`/`volatile`.
2. Перетворює типи масивів `U[]` або `U[N]` на покажчики `U*`.
3. Перетворює типи функцій `Ret(Args...)` на вказівники на функції `Ret(*)(Args...)`.

## 7. Засуджені та вилучені елементи стандарту

З метою очищення мови від небезпечних спадкових конструкцій C та раннього C++98 комітет WG21 встановив чітку політику життєвого циклу застарілих елементів. Елемент спочатку оголошується засудженим (*deprecated*), що змушує компілятори видавати попередження, а через один-два стандарти остаточно вилучається з тексту нормативного документа (*removed*).

### Таблиця депрекацій і вилучень у C++11 та C++14

| Конструкція / Клас | Версія депрекації | Версія вилучення | Причина усунення та безпечна альтернатива |
|---|---|---|---|
| `std::auto_ptr<T>` | C++11 | C++17 | Небезпечна семантика неявного перехоплення володіння при копіюванні; замінено на `std::unique_ptr<T>`. |
| Ключове слово `register` | C++11 | C++17 | Застаріла підказка компілятору щодо розміщення в регістрах ЦП; сучасні оптимізатори розподіляють регістри значно ефективніше самостійно. |
| Динамічні специфікації винятків `throw(T1, T2)` | C++11 | C++17 / C++20 | Спричиняли непередбачувані виклики `std::unexpected` під час виконання програми та блокували компіляторні оптимізації; замінено на специфікатор `noexcept`. |
| Функція `std::bind1st` та `std::bind2nd` | C++11 | C++17 | Громіздкий застарілий синтаксис зв'язування аргументів функторів; замінено на прості та наочні лямбда-вирази або `std::bind`. |
| Функція `std::random_shuffle` | C++14 | C++17 | Використовувала глобальний небезпечний генератор `std::rand()`; замінено на `std::shuffle` із зазначенням якісного генератора з `<random>`. |
| Небезпечна функція `gets()` у `<cstdio>` | C++11 | C++14 | Принципово вразлива функція читання рядка без обмеження розміру буфера (постійне джерело переповнення буфера); замінено на `std::fgets` або `std::getline`. |
| Операція постфіксного інкременту `bool++` | C++14 | C++17 | Небезпечний рудимент C, що приводив логічну змінну до значення `true`; замінено на пряме присвоєння `b = true;`. |

## 8. Конфігурація середовища збірки

Для переведення інструментів компіляції в режим підтримки стандартів C++11 та C++14 використовуються прапорці командного рядка та налаштування сучасних систем автоматизації збірки.

### Прапорці компіляторів GCC, Clang та MSVC

```bash
# Компіляція за стандартом C++11 із максимальним рівнем попереджень
g++ -std=c++11 -Wall -Wextra -Wpedantic main.cpp -o app_c11
clang++ -std=c++11 -Wall -Wextra -Wpedantic main.cpp -o app_c11

# Компіляція за стандартом C++14
g++ -std=c++14 -Wall -Wextra -Wpedantic main.cpp -o app_c14
clang++ -std=c++14 -Wall -Wextra -Wpedantic main.cpp -o app_c14

# Компілятор Microsoft Visual C++ (MSVC):
# Починаючи з VS 2015 Update 3 стандарт C++14 увімкнено за замовчуванням
cl.exe /std:c++14 /W4 /EHsc main.cpp /Fe:app_c14.exe
```

### Декларативна конфігурація у сучасній системі CMake

У сучасній практиці збірки програм на C++ не рекомендується встановлювати прапорці компілятора вручну через змінну `CMAKE_CXX_FLAGS`. Замість цього використовується цільовий (Target-based) підхід, який ізолює вимоги до стандарту для кожної конкретної бібліотеки або виконуваного файлу:

```cmake
cmake_minimum_required(VERSION 3.1)
project(ModernCppApp LANGUAGES CXX)

add_executable(my_service
    src/main.cpp
    src/network.cpp
    src/dispatcher.cpp
)

# Встановлення стандарту C++14 для цільового бінарника
set_target_properties(my_service PROPERTIES
    CXX_STANDARD 14
    CXX_STANDARD_REQUIRED ON
    CXX_EXTENSIONS OFF
)

# Додавання системних багатопотокових бібліотек
find_package(Threads REQUIRED)
target_link_libraries(my_service PRIVATE Threads::Threads)
```
