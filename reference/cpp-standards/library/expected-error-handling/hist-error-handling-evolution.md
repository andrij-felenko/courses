# 📜 Еволюція оброблення помилок у C++: від errno до std::expected

Історія оброблення помилок у мові C++ — це тривала еволюція компромісів між апаратною продуктивністю, детермінізмом системного програмування та математичною виразністю високорівневих абстракцій. Від перших днів розробки мови C функція, яка потенційно може зазнати невдачі, поставала перед фундаментальною суперечністю: канал повернення значення у мові програмування зазвичай один, тоді як можливих результатів виконання завжди два — або успішно згенероване корисне значення, або діагностична інформація про причину збою.

У класичній мові C рішенням цієї суперечності стала домовленість про виділення «магічних» значень з діапазону повернення. Якщо функція повертає вказівник, значення `NULL` сигналізує про помилку (як у виклику `malloc`). Якщо функція повертає ціле число, значення `-1` або від'ємний код вказує на збій (як у системних викликах POSIX `read` чи `write`). Конкретизація ж причини збою виносилася у глобальну або попотокову змінну `errno`.

:::tabs
```c
// Класичний підхід мови C з виділеним магічним значенням та errno
int fd = open("/etc/config.json", O_RDONLY);
if (fd == -1) {
    // Деталі помилки зберігаються окремо в попотоковій змінній errno
    if (errno == ENOENT) {
        // Файл не знайдено в файловій системі
    } else if (errno == EACCES) {
        // Відсутні права доступу для даного процесу
    }
}
```
```cpp
// Еквівалентний C++23 підхід без errno з використанням std::expected
#include <expected>
#include <system_error>
#include <fcntl.h>

std::expected<int, std::error_code> safe_posix_open(const char* path, int flags) {
    int fd = ::open(path, flags);
    if (fd == -1) {
        return std::unexpected(std::error_code(errno, std::generic_category()));
    }
    return fd;
}
```
:::

Цей підхід мав фундаментальні недоліки, які гостро проявилися з розвитку багатопотоковості, паралельних обчислень та складних програмних архітектур:
- **Забруднення сигналу**: якщо функція обчислює математичну величину (наприклад, повертає значення типу `double`), узяти окреме магічне значення для помилки без спотворення числового діапазону неможливо. Спроби повертати `NaN` втрачають будь-яку інформативність про причину збою.
- **Втрата глобального стану та багаторазові race conditions**: змінна `errno` у перших реалізаціях була глобальною, що призводило до стану ґонки при паралельному виконанні потоків. Пізніше її зробили потоково-локальною (`thread_local`), проте фундаментальна проблема залишилася: `errno` легко перезаписати наступним системним викликом, якщо розробник не зберіг її значення локально одразу після збою.
- **Відсутність контролю з боку компілятора**: мова C не змушує розробника перевіряти повернутий код помилки. Ігнорування результату `read()` або `scanf()` призводить до використання неініціалізованої пам'яті та критичних уразливостей у системній безпеці.
- **Використання вихідних параметрів (out-parameters)**: аби відокремити код помилки від результату, розробники змушені передавати вказівники на вихідні змінні: `int parse_int(const char* str, int* out_val)`. Це руйнує чистий виразний стиль написання коду, робить неможливим вкладення викликів та унеможливлює використання об'єктів без конструктора за замовчуванням.

З появою C++98 Б'ярн Страуструп та комітет зі стандартизації запропонували альтернативну парадигму — механізм винятків (`try`, `catch`, `throw`). Ідея полягала у повному відокремленні «щасливого шляху» (happy path) від шляху оброблення помилок. Згідно з цією концепцією, функція має повертати лише чисте корисне значення, а при виникненні позаштатної ситуації керування автоматично передається вгору за стеком викликів до найближчого відповідного блоку `catch`.

Модель винятків у C++ була реалізована за принципом Zero-Cost Exceptions (зокрема у специфікації Itanium C++ ABI). Термін «нульова вартість» означає відсутність накладних витрат у процесі нормального виконання програми: у щасливому шляху немає жодних перевірок прапорців чи умовних переходів `if (error)`. Проте ця назва виявилася оманою щодо загальної системної продуктивності:
- **Роздування розміру бінарного файлу**: компілятор мусить генерувати розлогі таблиці розгортання стеку (`.eh_frame` та `.gcc_except_table` у форматі DWARF), які описують порядок виклику деструкторів для кожного інструкційного блоку. Для систем із обмеженою пам'яттю (embedded-пристрої, мікроконтролери, польотні контролери) це призводить до збільшення розміру прошивки на 15–35%.
- **Надетермінована затримка (Non-deterministic latency)**: у момент виклику `throw` операційна система та runtime C++ починають динамічно сканувати таблиці винятків, розгортати стек і шукати відповідний блок `catch`. Час виконання цього процесу коливається у широкому діапазоні і залежить від глибини стеку, наповнення кекшів CPU та виділення пам'яті під об'єкт винятку, що робить винятки категорично неприйнятними для систем реального часу (Real-Time OS), ігрових рушіїв, високочастотного трейдингу (HFT) та ядра операційних систем.
- **Прихований канал керування**: сигнатура функції `double compute(double x)` не дає жодної інформації про те, чи може ця функція кинути виняток і які саме типи винятків очікувати. Спроба ввести специфікації винятків у C++98 (`throw(std::bad_alloc)`) виявилася невдалою через накладні витрати на перевірку в runtime і була остаточно видалена в C++17, залишивши лише `noexcept`.

У результаті цілі високонавантажені галузі розробки — від ядра Linux та розробки драйверів до ігрових рушіїв Unreal Engine, автомобільної промисловості (стандарт AUTOSAR C++) та систем робототехніки — повністю заборонили використання винятків прапорцем компілятора `-fno-exceptions`.

Це вимушене відключення винятків повернуло спільноту розробників до вихідної проблеми: як передавати помилки без винятків, зберігши високу типобезпеку, чистоту коду та можливість композиції?

Першою спробою компромісу в стандартній бібліотеці стало використання `std::pair<T, bool>` або `std::pair<T, std::error_code>` (C++11). Проте `std::pair` мав суттєвий недолік: він вимагав конструювання об'єкта `T` навіть у випадку виникнення помилки. Якщо тип `T` не мав конструктора за замовчуванням або його створення вимагало виділення дорогих ресурсів (наприклад, відкриття мережевого сокета або виділення буфера пам'яті), використання `std::pair` ставало вкрай неефективним або взагалі неможливим.

У C++17 з'явився шаблон `std::optional<T>`. Він вирішив проблему неефективного використання пам'яті: об'єкт містив неініціалізований буфер під `T` і прапорець `bool`, не виділяючи пам'ять у купі і не створюючи `T` при відсутності значення. Проте `std::optional` мав інший обмежений спектр застосування — він фіксував лише факт відсутності значення (`std::nullopt`), але був недатним повідомити причину цієї відсутності. Для логування, аналізу та специфічної обробки помилок у складних розподілених системах `std::optional` виявився недостатньо інформативним.

Паралельно у спільноті Boost та робочих групах ISO C++ розвивалася альтернативна концепція. Натхненням стали мови функційного програмування та мова Rust, у якій тип `Result<T, E>` з перших днів став основною моделлю оброблення помилок. У C++ спільноті ключову роль відіграли такі розробки:
- **Boost.Outcome**: бібліотека Нелла Вайта (Niall Douglas), яка надавала типи `outcome<T, EC, EP>` для складного комбінування коду помилки та об'єкта винятку.
- **Boost.Expected / P0323 proposal**: серія пропозицій від Вісенте Ботет Ескріба (Vicente J. Botet Escribá) та Рохана Дрейпа / Сая Бранда (Sy Brand). Авторський проект `tl::expected` від Sy Brand став де-факто стандартом девелоперського досвіду до офіційної стандартизації.

Розробка специфікації `std::expected` тривала понад сім років (від першої пропозиції P0323R0 у 2016 році до остаточного схвалення P0323R12 у C++23). Основними предметами дискусій у комітеті ISO C++ були:
1. **Семантика доступу**: чи має оператор `operator*()` перевіряти наявність значення в runtime (throw/assert), чи забезпечувати найшвидший доступ без перевірок як у `std::optional`. Було прийнято рішення: `operator*()` дає незахищений доступ (undefined behavior при відсутності значення), а метод `value()` виконує перевірку та кидає виняток `std::bad_expected_access<E>`.
2. **Тип-маркер для помилки**: як уникнути амбівалентності при конструюванні, коли `T` та `E` мають однаковий тип (наприклад, `std::expected<std::string, std::string>`). Для цього було створено допоміжний шаблон `std::unexpected<E>`, який чітко сигналізує компілятору, що значення, що передається, є саме помилкою.
3. **Монадичний інтерфейс**: додання методів `.and_then()`, `.transform()`, `.or_else()`, `.transform_error()`, які дозволили будувати безперервні конвеєри трансформацій даних без явного написання розлогих каскадів `if (!res.has_value())`.
4. **Спеціалізація std::expected<void, E>**: окремий пласт обговорень стосувався процедур, які не повертають значення при успіху (повертають `void`), але можуть завершитися помилкою. Спеціалізація `std::expected<void, E>` дозволила уникнути створення фіктивних типів на кшталт `std::monostate` або `std::expected<std::monostate, E>`, зберігши нульовий розмір для успішного корисного навантаження.

Паралельно з прийняттям `std::expected` у комітеті обговорювалася також пропозиція Герба Саттера (Herb Sutter) P0709 "Zero-overhead deterministic exceptions" (відома як static exceptions чи `std::error`). Саттер пропонував кардинальну реформу мови: винятки повинні були стати легковаговими значеннями типу `std::error`, що повертаються через окремий регістр CPU на рівні ABI без використання таблиць розгортання стеку. Проте пропозиція P0709 вимагала глибоких змін у самих компіляторах та розриву сумісності ABI, тому її реалізація відклалася на невизначений термін. 

Тим часом `std::expected` пропонував готове рішення в рамках існуючої системи типів бібліотеки без необхідності змінювати архітектуру компіляторів. Починаючи з версій GCC 12, Clang 16 та MSVC 2022 (v19.33), шаблон `std::expected` увійшов до складу стандартних бібліотек `libstdc++`, `libc++` та MSVC STL, ставши головним інструментом детермінованого оброблення помилок у сучасному C++.

Важливо відзначити внесок робочої групи WG21 (включно із субгрупами LEWG та EWG), яка провела десятки рев'ю для узгодження конструкторів `explicit` та концептів виведення типів. Завдяки цій ретельній роботі `std::expected` отримав бездоганну інтеграцію з існуючою екосистемою C++20/C++23 (включно з `std::concepts` та `std::format`).

Практичний досвід впровадження `std::expected` у великих відкритих проектах (зокрема у середовищі LLVM та низці ігрових двигунів) довів, що перехід на монадичне оброблення помилок знижує кількість прихованих багів на 20–30% завдяки атрибуту `[[nodiscard]]`, що вбудований у шаблон.

Отже, еволюційний шлях оброблення помилок пройшов повний цикл: від хаотичних C-кодів через неявні C++ винятків до явних, детермінованих та типобезпечних монадичних контейнерів на стеку. Шаблон `std::expected` органічно об'єднав найкращі риси обох світів — детермінізм класичного мовного рівня C та математичну виразність сучасної мови C++.
