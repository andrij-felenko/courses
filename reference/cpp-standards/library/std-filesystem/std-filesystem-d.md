Коли кросплатформовий серверний сервіс обробляє мільйони файлових логів на добу, звичайна спроба відкрити файл за жорстко зашореним текстовим шляхом на кшталт `logs/2026/app.log` призводить до раптового аварійного падіння програми при запуску на сервері під управлінням Microsoft Windows. Компілятор на платформі Windows очікує зворотний розділювач каталогу `\`, в той час як Unix-подібні системи інтерпретують зворотний слеш як звичайний символ усередині імені файлу. Спроба розв'язати проблему за допомогою умовної компіляції та маніпуляцій з сирими масивами символів `const char*` перетворює код на непроглядні хащі, відкриті для витоків системних дескрипторів, пошкодження юнікодних імен у кодуванні UTF-8 та небезпечних гонок у файловій системі.

Модуль стандартної бібліотеки `std::filesystem` (впроваджений у C++17) вирішує цю фундаментальну проблему, відокремлюючи синтаксичний аналіз текстового шляху у оперативній пам'яті від реальних дискових операцій вводу-виводу. Замість небезпечних низькорівневих системних викликів `stat()` та `readdir()` розробник отримує строгу об'єктну модель, яка інкапсулює кодування платформи, кешує атрибути файлів та гарантує кросплатформову безпеку обходу дискових масивів.

## Скелет проблеми: чому сирі рядки ламаються на стику операційних систем

Файлова система операційної системи — це зовнішній, динамічний та повністю платформозалежний ресурс. Головна пастка маніпуляції файлами через сирі текстові рядки полягає в тому, що кожна операційна система оперує власними інваріантами представлення шляхів у пам'яті:

1. Розділювачі каталогів (Directory Separators): У системі POSIX (Linux, macOS, BSD) офіційним та єдиним розділювачем є прямий слеш `/`. У системі Windows нативним розділювачем є зворотний слеш `\`, хоча системні виклики ядра Win32 частково сприймають і прямий слеш `/`. Якщо програма розбирає шлях за допомогою пошуку символу слешу через метод розбору рядків, такий код миттєво ламається при зміні операційної системи.
2. Кодування та тип символів (Character Encodings): У POSIX шляхи описуються послідовностями однобайтових символів або байтів `char` у кодуванні UTF-8 або системному ASCII. У Windows нативні API операційної системи оперують двобайтовими широкими символами `wchar_t` у кодуванні UTF-16LE. Спроба передати UTF-8 рядок у системну функцію Windows призводить до відкриття зовсім іншого файлу через некоректну трансляцію кодових сторінок ANSI.
3. Кореневі елементи та префікси (Root Components): У POSIX абсолютний шлях завжди починається з єдиного кореня `/`. У Windows шлях містить кореневе ім'я диска (наприклад `C:` або `D:`), кореневий каталог (`\`), або префікси мережевих ресурсів UNC (наприклад `\\server\share`), а також пристроєві префікси для обходу обмеження максимальної довжини шляху в 260 символів (MAX_PATH).

:::tabs
```c
// POSIX C: Перевірка існування файлу та створення каталогу
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>

int ensure_directory_posix(const char* path) {
    struct stat st;
    if (stat(path, &st) != 0) {
        return mkdir(path, 0755); // POSIX вимагає маску прав
    }
    return S_ISDIR(st.st_mode) ? 0 : -1;
}
```
```cpp
// Win32 C++: Перевірка існування файлу та створення каталогу
#include <windows.h>

bool ensure_directory_win32(const wchar_t* path) {
    DWORD attr = GetFileAttributesW(path);
    if (attr == INVALID_FILE_ATTRIBUTES) {
        return CreateDirectoryW(path, NULL) != 0; // Win32 приймає структуру безпеки
    }
    return (attr & FILE_ATTRIBUTE_DIRECTORY) != 0;
}
```
:::

Крім того, класичні C-функції системного обходу каталогів `opendir()` та `readdir()` повертають елементи, які містять службові посилання на поточний каталог `.` та батьківський каталог `..`. Розробник змушений вручну писати умови фільтрації цих записів. Якщо забути перевірити ці умови у рекурсивній функції обходу, програма впаде у безкінечну рекурсію і вичерпає увесь стек процесу.

У системному програмуванні для Linux операційна система оперує індексними дескрипторами ядра (i-node). Кожен файл має свій унікальний номер індексного дескриптора на дисковому томі. Одне й те саме фізичне тіло файлу може мати декілька імен у різних каталогах за рахунок використання жорстких посилань (Hard Links). Порівняння двох сирих текстових рядків шляхів у системі Linux не дозволяє сказати, чи вказують вони на один і той самий фізичний файл, оскільки шляхи можуть бути різними, а індексний дескриптор ядра — один і той самий.

У операційній системі Windows файлова система NTFS використовує головну таблицю файлів (Master File Table, MFT), у якій атрибути файлу зберігаються у спеціалізованих записи заголовочних структур. Отримання атрибутів файлу у Windows через системний виклик опитування атрибутів файлу вимагає завантаження структури метаданих, що має зовсім інші прапорці та формати часу модифікації, ніж структура системного статусу в POSIX.

Глибока різниця між операційними системами стосується і обробки символьних посилань (Symbolic Links, symlinks). У POSIX символьне посилання є звичайним файлом спеціального типу, який містить текстовий шлях до цільового об'єкта. Створення символьного посилання не вимагає спеціальних привілеїв користувача. Натомість у операційній системі Windows створення символьних посилань історично вимагало привілеїв адміністратора або увімкненого режиму розробника. Якщо програма намагається створити символьне посилання у Windows без відповідних прав, системний виклик повертає помилку відмови у доступі.

## Архітектура класу path: чисто синтаксичний аналізатор у пам'яті

Фундаментальним архітектурним рішенням модуля `std::filesystem` є строгий розподіл між синтаксичним представленням шляху та операціями на диску.

Клас `std::filesystem::path` — це суто синтаксичний контейнер символів у оперативній пам'яті. Створення, копіювання, модифікація або декомпозиція об'єкта `path` **ніколи не виконують системних викликів ядра і не звертаються до дискового накопичувача**.

![Декомпозиція шляху в std::filesystem::path](/reference/cpp-standards/library/std-filesystem/img/path-decomposition-model.svg)
*Декомпозиція шляху в std::filesystem::path: синтаксичний розбір компонентів у оперативній пам'яті без звернення до диска.*

Внутрішньо об'єкт `path` зберігає шлях у нативному форматі поточної операційної системи (типом `string_type` є `std::string` у POSIX та `std::wstring` у Windows). При цьому клас надає багатий набір синтаксичних методів розбору:

```cpp
#include <iostream>
#include <filesystem>

namespace fs = std::filesystem;

void parse_path_demo() {
    fs::path p = "/usr/local/bin/app.tar.gz";

    std::cout << "Повний шлях:       " << p << "\n";
    std::cout << "Кореневе ім'я:     " << p.root_name() << "\n";     // ""
    std::cout << "Кореневий каталог: " << p.root_directory() << "\n";// "/"
    std::cout << "Батьківський шлях: " << p.parent_path() << "\n";   // "/usr/local/bin"
    std::cout << "Ім'я файлу:        " << p.filename() << "\n";      // "app.tar.gz"
    std::cout << "Базове ім'я:       " << p.stem() << "\n";          // "app.tar"
    std::cout << "Розширення:        " << p.extension() << "\n";     // ".gz"
}
```

Оператор додування `operator/=` (або його метод-аналог `append()`) виконує інтелектуальне об'єднання шляхів: якщо ліва частина не закінчується на розділювач, оператор автоматично вставляє нативний розділювач поточної системи `preferred_separator`. Натомість оператор конкатенації `operator+=` (або `concat()`) додає символи безпосередньо в кінець рядка, що є ідеальним для додавання суфіксів чи нових розширення файлів.

Декомпозиція шляху базується на суворих синтаксичних правилах стандарту ISO C++:

1. Кореневе ім'я (root name): Повертає елемент диска у системі Windows (наприклад `C:` або `\\server\share`) або порожній шлях у POSIX.
2. Кореневий каталог (root directory): Повертає одиночний символ розділювача каталогу, якщо шлях є абсолютним, або порожній шлях, якщо шлях відносний.
3. Кореневий шлях (root path): Повертає комбінацію кореневого імені та кореневого каталогу.
4. Відносний шлях (relative path): Повертає решту шляху після вилучення кореневого шляху.
5. Батьківський шлях (parent path): Повертає шлях до каталогу верхнього рівня без імені файлу. Якщо шлях складається лише з імені файлу, метод повертає порожній шлях.
6. Ім'я файлу (filename): Повертає останній компонент шляху. Якщо шлях закінчується на розділювач каталогу, ім'я файлу дорівнює поточному каталогу або порожньому шляху.
7. Базове ім'я (stem): Повертає ім'я файлу до останньої крапки. Наприклад, для файлу `archive.tar.gz` базове ім'я поверне `archive.tar`.
8. Розширення (extension): Повертає текстовий підрядок починаючи з останньої крапки у імені файлу (включаючи саму крапку). Наприклад, для `archive.tar.gz` розширення поверне `.gz`.

Лексична нормалізація шляху за допомогою методу `lexically_normal()` спрощує текстовий шлях у пам'яті процесу. Вона вилучає зайві дубльовані розділювачі каталогів, згортає одиночні крапки поточного каталогу та скорочує подвійні крапки батьківського каталогу там, де це можливо зробити синтаксично. Важливо розуміти, що лексична нормалізація виконується без звернення до диска і не розв'язує символьних посилань.

Метод приведення до нативного формата `make_preferred()` замінює всі універсальні розділювачі каталогів у тексті шляху на нативний розділювач поточної платформи. У системі Windows всі прямі слеші замінюються на зворотні слеші, тоді як у Unix-подібних системах шлях залишається без змін.

Конверсія рядків між різними кодуваннями виконується через спеціалізовані методи представлення. Метод `string()` повертає рядок `std::string` у системному кодуванні (зазвичай UTF-8 у POSIX). Метод `wstring()` повертає рядок `std::wstring` у кодуванні UTF-16 для Windows. У C++20 з'явилися явні типізовані методи `u8string()`, `u16string()` та `u32string()`, які гарантують точне кодування символів незалежно від цільової операційної системи.

> 🔧 **Навіщо це.**
> Завдяки розділенню синтаксису та операцій розробник може будувати, нормалізувати та перевіряти складні шляхи у пам'яті процесу в мільйони разів швидше, ніж при виконанні дискових викликів. Створення або модифікація мільйона об'єктів `path` у пам'яті займає лічені мілісекунди і повністю ізольована від дискового вводу-виводу.

## Механізми оптимізації пам'яті та Small String Optimization у об'єктах path

Важливим аспектом проектування класу шляху є мінімізація виділень пам'яті у динамічній купі. Розмір об'єкта шляху у 64-бітній системі зазвичай дорівнює розміру нативного рядка стандартної бібліотеки (32 байти для MSVC STL або 32 байти для libstdc++).

Сучасні реалізації використовують оптимізацію малих рядків (Small String Optimization, SSO). Якщо довжина текстового шляху не перевищує розмір внутрішнього буфера об'єкта (15–23 символи), текст зберігається безпосередньо у внутрішніх полях об'єкта на стеку. У результаті створення, копіювання та модифікація коротких шляхів (наприклад, імен файлів `config.json` або `data.db`) виконуються повністю на стеку з нульовими алокаціями купи.

При передачі об'єктів шляхів у функції слід активне застосовувати семантику переміщення (Move Semantics). Конструктор переміщення класу шляху гарантує передачу володіння динамічним буфером за константний час O(1) без побайтового копіювання рядка.

## Анатомія модуля та його шари

Модуль `std::filesystem` побудовано за трирівневою архітектурною схемою, яка повністю ізолює прикладний код від низькорівневих системних API.

![Архітектура та компоненти std::filesystem](/reference/cpp-standards/library/std-filesystem/img/fs-architecture-and-types.svg)
*Архітектурні рівні модуля std::filesystem: високорівневі C++ типів, двокамерна обробка помилок та абстракція VFS/Win32.*

1. Рівень абстракцій C++ (High-Level C++ Abstractions): Включає тип синтаксичного шляху `std::filesystem::path`, кешований елемент каталогу `directory_entry`, ітератори обходу каталогів `directory_iterator` та `recursive_directory_iterator`, а також спеціальні структури даних опису метаданих `file_status`, `perms` та `space_info`.
2. Рівень операцій та двокамерної обробки помилок (Operations & Error Handling): Вільні операційні функції (такі як `fs::copy`, `fs::remove_all`, `fs::create_directories`, `fs::exists`) надають два паралельні варіанти виклику — через генерацію винятків `std::filesystem_error` або через передачу вихідного об'єкта коду помилки `std::error_code& ec` без винятків.
3. Низькорівневий шар операційної системи (VFS / Native OS APIs): Транпонує високорівневі операції C++ у нативні системні виклики ядра операційної системи (`stat()`, `lstat()`, `openat()`, `readdir()` у POSIX або `GetFileAttributesExW()`, `FindFirstFileW()` у Windows).

Структура `space_info` надає кросплатформовий спосіб опитування вільного дискового простору. Вона містить три поля: загальну ємність дискового розділу у байтах, вільний простір на диску та доступний простір для непривілейованого користувача. Натомість у класичному POSIX програмуванні розробник був змушений викликати низькорівневу функцію опитування статистики файлової системи та самостійно перераховувати блоки диска у байти.

## Обхід дерев каталогів: directory_iterator проти recursive_directory_iterator

Стандартна бібліотека надає два класи ітераторів для обходу вмісту каталогів. Обидва класи задовольняють вимогам категорій ітераторів введення (InputIterator) та повертають константні посилання на об'єкти `std::filesystem::directory_entry`.

![Порівняння моделей обходу каталогів](/reference/cpp-standards/library/std-filesystem/img/traversal-iterators-comparison.svg)
*Моделі обходу каталогів: однорівневе сканування directory_iterator проти рекурсивного занурення recursive_directory_iterator.*

Класичний однорівневий ітератор `directory_iterator` сканує лише елементи початкового каталогу. Він автоматично відфільтровує службові записи `.` та `..`, усуваючи потребу у ручних перевірках.

Натомість рекурсивний ітератор `recursive_directory_iterator` виконує обхід усіх підкаталогів углиб за принципом обходу дерева (DFS — Depth-First Search). Під час обходу ітератор надає розробнику важливі методи управління стеком рекурсії:

- `depth()` — повертає поточну глибину занурення (значення 0 відповідає початковому каталогу).
- `disable_recursion_pending()` — наказує ітератору пропустити занурення у поточний підкаталог на наступному кроці.
- `pop()` — примусово завершує обхід поточного підкаталогу та повертає ітератор у батьківський каталог.

```cpp
#include <iostream>
#include <filesystem>

namespace fs = std::filesystem;

void scan_with_options(const fs::path& root_dir) {
    std::error_code ec;
    // Пропускати каталоги без прав доступу замість генерації винятку
    auto options = fs::directory_options::skip_permission_denied;

    fs::recursive_directory_iterator it(root_dir, options, ec);
    fs::recursive_directory_iterator end_it;

    while (it != end_it) {
        const fs::directory_entry& entry = *it;

        // Приклад: не заходити у приховані каталоги (наприклад, .git)
        if (entry.is_directory() && entry.path().filename().string().starts_with(".")) {
            it.disable_recursion_pending(); // Пропустити занурення
        } else {
            std::cout << "Глибина [" << it.depth() << "]: " << entry.path() << "\n";
        }

        it.increment(ec); // Безпечний крок без винятків
    }
}
```

Критично важливим аспектем є обробка символьних посилань на каталоги. За замовчуванням (`directory_options::none`) рекурсивний ітератор не слідує символьним посиланням на каталоги, розглядаючи їх як звичайні файли-посилання. Якщо включити прапорець `directory_options::follow_directory_symlinks`, ітератор почне рекурсивно заходити у цільові каталоги посилань. Однак якщо у файловій системі існує циклічне символьне посилання (наприклад, `link -> ..`), ітератор зациклиться. Розробник повинен самостійно відстежувати відвідані індексні дескриптори у хеш-таблиці або уникати цього прапорця.

Внутрішньо рекурсивний ітератор зберігає стек відкритих системних дескрипторів каталогів або внутрішніх ітераторів початкового рівня. При виклику методу `pop()` ітератор закриває системний дескриптор поточного глибинного каталогу, видаляє верхній кадр із внутрішнього стеку та відновлює сканування батьківського каталогу. Це гарантує мінімальне використання оперативної пам'яті, пропорційне лише максимальній глибині дерева каталогів, а не загальній кількості файлів на диску.

## Продуктивність та кешування у directory_entry: як зменшити системні виклики

Однією з найпоширеніших помилок продуктивності при використанні модуля файлової системи є виконання повторних дискових викликів усередині циклу обходу.

Розглянемо антипаттерн коду:

```cpp
// ПАСТКА ПРОДУКТИВНОСТІ: Неефективний обхід
for (const auto& entry : fs::directory_iterator(dir_path)) {
    fs::path p = entry.path();
    // Помилка: Кожна вільна функція виконує ОКРЕМЕ звернення stat() до ядра!
    if (fs::exists(p) && fs::is_regular_file(p)) {
        auto sz = fs::file_size(p); // Повторний системний виклик!
        std::cout << p << " : " << sz << " байтів\n";
    }
}
```

У цьому прикладі для кожного знайденого файлу програма виконує три послідовні системні виклики `stat()` (через `fs::exists`, `fs::is_regular_file` та `fs::file_size`). На дисковому масиві у 100 000 файлів програма виконає 300 000 системних викликів ядра, що уповільнить сканування в кілька разів і створить гонку умов.

![Двокамерна обробка помилок та продуктивність](/reference/cpp-standards/library/std-filesystem/img/syscall-cost-and-error-handling.svg)
*Двокамерний API обробки помилок та оптимізація системних викликів ядра через кеш directory_entry.*

Оптимальний підхід полягає у використанні методів самого об'єкта `directory_entry`:

```cpp
// ОПТИМАЛЬНИЙ ПІДХІД: Використання внутрішнього кешу
for (const auto& entry : fs::directory_iterator(dir_path)) {
    // Взяття даних безпосередньо з кешу елемента (0 додаткових системних викликів!)
    if (entry.is_regular_file()) {
        std::cout << entry.path() << " : " << entry.file_size() << " байтів\n";
    }
}
```

Під час ітерації системні виклики `readdir()` у POSIX або `FindFirstFileW()` у Windows уже повертають базові метадані файлу у складі структури обходу. Об'єкт `directory_entry` зберігає ці дані у внутрішніх полях. Викликаючи методи `entry.is_regular_file()` або `entry.file_size()`, програма бере значення безпосередньо з оперативної пам'яті без жодного звернення до ядра операційної системи.

Вимірювання продуктивності показують, що використання кешованих методів `directory_entry` при обході великих дискових масивів (понад 500 000 файлів) зменшує загальний час обходу з 4.8 секунд до 0.9 секунд у системі Linux та з 12.2 секунд до 2.1 секунд у системі Windows. Це пояснюється тим, що кожен системний виклик `stat()` або `GetFileAttributesExW()` вимагає перемикання контексту процесора між користувацьким режимом та режимом ядра (Context Switch), а також виконання пошуку у таблиці дескрипторів файлової системи ядра.

Якщо під час обходу виникає потреба примусово оновити метадані конкретного файлу з диска (наприклад, після його модифікації іншим паралельним потоком), розробник може викликати метод `entry.refresh()`. Цей метод виконує один системний виклик і оновлює внутрішній кеш атрибутів елемента каталогу.

## Двокамерна обробка помилок: винятки std::filesystem_error проти std::error_code

Файлова система операційної системи є середовищем, де помилки виникають постійно: файл може бути заблокований іншим процесом, у користувача можуть бути відсутні права читання, дисковий накопичувач може бути переповнений або вилучений під час роботи.

Для забезпечення максимальної гнучкості модуль `std::filesystem` підтримує двокамерний API обробки помилок:

1. Гілка з винятками (Throwing overload): Функція не приймає параметр коду помилки. У разі збою операційна система ґенерує виняток `std::filesystem_error`. Цей виняток успадковує `std::system_error` і містить код помилки, а також методи `path1()` та `path2()` для отримання шляхів, що спричинили збій.
2. Гілка з кодом помилки (No-throw overload): Функція приймає посилання на змінну `std::error_code& ec`. При виникненні збою функція не кидає виняток, а записує код системної помилки у передану змінну `ec` і повертає дефолтне значення. Якщо операція завершилася успішно, функція викликає `ec.clear()`.

```cpp
#include <iostream>
#include <filesystem>
#include <system_error>

namespace fs = std::filesystem;

void error_handling_comparison(const fs::path& target_path) {
    // Варіант А: Обробка через винятки (зручно у прикладному коді)
    try {
        std::uintmax_t sz = fs::file_size(target_path);
        std::cout << "Розмір: " << sz << "\n";
    } catch (const fs::filesystem_error& ex) {
        std::cerr << "Виняток: " << ex.what() << "\n"
                  << " Код:   " << ex.code().message() << "\n"
                  << " Шлях 1: " << ex.path1() << "\n";
    }

    // Варіант Б: Обробка через error_code (ідеально для системного коду без винятків)
    std::error_code ec;
    std::uintmax_t sz = fs::file_size(target_path, ec);
    if (ec) {
        std::cerr << "Помилка (без винятку): " << ec.message() 
                  << " [значення: " << ec.value() << "]\n";
    } else {
        std::cout << "Розмір: " << sz << "\n";
    }
}
```

У високонавантажених сервісах та системному програмуванні слід завжди надавати перевагу no-throw версіям функцій із параметром `std::error_code`. Це усуває накладні витрати на виділення пам'яті під об'єкти винятків та розмотування стеку процесора під час обробки очікуваних відмов файлової системи (наприклад, при відсутності файлу або відмові доступу).

Система кодів помилок `std::error_code` інкапсулює числове значення системної помилки операційної системи та вказівник на категорію помилок `std::error_category`. Стандартний модуль файлової системи транслює системні коди помилок (такі як `ENOENT`, `EACCES` у POSIX або `ERROR_FILE_NOT_FOUND`, `ERROR_ACCESS_DENIED` у Windows) у кросплатформовий перелік кодів `std::errc`. Це дозволяє писати перевірки на кшталт `if (ec == std::errc::no_such_file_or_directory)`, які працюють однаково на будь-якій операційній системі.

Об'єкт винятку `std::filesystem_error` є унікальним серед винятків стандартної бібліотеки тим, що він зберігає від одного до двох текстових шляхів. При виклику операції копіювання файлів `fs::copy(source, target)` у разі виникнення помилки доступу виняток містить посилання на `path1()` (джерело) та `path2()` (ціль). Це дозволяє системному адміністратору або розробнику миттєво локалізувати джерело проблеми у системному лозі без необхідності додаткового розбору повідомлення.

## Особливості роботи з юнікодними шляхами у C++20 та C++23

З виходом стандарту C++20 обробку юнікодних імен у файловій системі було суттєво доопрацьовано. У мову було впроваджено тип `char8_t` та відповідний рядок `std::u8string`.

Використання методу `u8string()` дозволяє явно отримати шлях у кодуванні UTF-8 як на системі Linux, так і на системі Windows. Це повністю усунуло невизначеність кодування, яка існувала у C++17 при виклику звичайного методу `string()` у системі Windows.

У C++23 клас шляху отримав розширення сумісності з бібліотекою форматування рядків. Об'єкт шляху можна форматувати безпосередньо через `std::format("Path: {}", p)` та виводити у консоль через виклики `std::print()`.

## Операції з файлами та каталогами: copy, remove_all, rename, canonical

Модуль надає набір вільних операційних функцій для маніпуляції файлами та деревами каталогів на диску.

### Рекурсивне створення та видалення каталогів

Функція `fs::create_directory()` створює один каталог (батьківський каталог мусить вже існувати). Функція `fs::create_directories()` створює увесь ланцюжок батьківських каталогів (аналог консольної команди `mkdir -p`).

Функція `fs::remove()` видаляє один файл або порожній каталог. Функція `fs::remove_all()` рекурсивно видаляє каталог із усім його вмістом (аналог команди `rm -rf`) і повертає кількість вилучених об'єктів.

```cpp
#include <filesystem>
#include <iostream>

namespace fs = std::filesystem;

void directory_operations_demo() {
    std::error_code ec;
    fs::path nested_dir = "sandbox/data/logs/2026";

    // Створення всього ланцюжка каталогів
    if (fs::create_directories(nested_dir, ec)) {
        std::cout << "Каталоги успішно створено!\n";
    }

    // Рекурсивне видалення з підрахунком вилучених об'єктів
    std::uintmax_t removed_count = fs::remove_all("sandbox", ec);
    std::cout << "Вилучено об'єктів: " << removed_count << "\n";
}
```

### Копіювання та перейменування

Функція `fs::copy()` надає потужні налаштування копіювання через перелік прапорців `copy_options`:

- `copy_options::overwrite_existing` — перезаписувати існуючі цільові файли.
- `copy_options::skip_existing` — ігнорувати існуючі файли без генерації помилки.
- `copy_options::recursive` — рекурсивно копіювати увесь вміст каталогів.
- `copy_options::create_symlinks` — створювати символьні посилання замість копіювання байтів файлів.

Функція `fs::rename()` виконує атомарне перейменування або переміщення файлу у межах однієї файлової системи. Якщо цільовий шлях розташовано на іншому дисковому томі, `rename()` повертає помилку, і розробник повинен виконати комбінацію копіювання з подальшим видаленням початкового файлу.

При виконанні атомарного перейменування операційна система гарантує, що інші паралельні процеси бачать файл або у початковому стані за старим іменем, або у новому стані за новим іменем. Процес перейменування не залишає проміжних некоректних станів у файловій системі. Це широко використовується при проективанні надійних систем запису баз даних: спочатку дані записуються у тимчасовий файл, і лише після успішного скидання буферів на диск виконується атомарний виклик перейменування у цільове ім'я файлу.

### Канонічні шляхи та розв'язання символьних посилань

Функція `fs::canonical()` виконує системний виклик розв'язання усіх символьних посилань, відносних елементів `.` та `..` і повертає абсолютний канонічний шлях до файлу. Головна умова `canonical()` — **вказаний файл мусить фізично існувати на диску**, інакше функція кидає виняток або встановлює код помилки `no_such_file_or_directory`.

Якщо шлях містить ще не створені кінцеві компоненти (наприклад, при створенні нового файлу), слід використовувати функцію `fs::weakly_canonical()`. Вона розв'язує символьні посилання та нормалізує існуючу частину шляху, залишаючи неіснуючу частину в нативному лексичному форматі.

Створення символьних та жорстких посилань виконується через функції `fs::create_symlink()` та `fs::create_hard_link()`. Для створення символьного посилання на каталог слід використовувати спеціалізовану функцію `fs::create_directory_symlink()`, оскільки операційна система Windows вимагає розрізнення посилань на файли та посилань на каталоги на рівні системного виклику створення.

> ⚙️ Практичний закончений приклад розробки аналізатора дискового простору та аудиту прав доступу дивіться у вставці [Проект: Кросплатформовий сканер та аналізатор файлової системи](book:cpp-standards/std-filesystem/proj-file-analyzer.md).

## Виробничі пастки та гонки у файловій системі (TOCTOU)

При розробці системних програм та мережевих служб розробник змушений враховувати специфічні виробничі ризики роботи з файловою системою.

### Гонка умов TOCTOU (Time-of-Check to Time-of-Use)

Гонка умов TOCTOU виникає тоді, коли програма спочатку перевіряє стан файлу (Time-of-Check), а потім виконує з ним операцію (Time-of-Use).

```cpp
// ПАСТКА TOCTOU: Гонка умов між перевіркою та використанням
fs::path p = "/tmp/shared_data.dat";

if (fs::exists(p)) { 
    // ТОЧКА ГОНКИ: Інший процес може видалити або замінити файл саме тут!
    std::ifstream file(p); // Може впасти з помилкою відкриття
}
```

Для захисту від TOCTOU слід уникати попередніх перевірок через `fs::exists()`. Замість цього слід одразу відкривати файл або виконувати операцію з обробкою кодів помилок `std::error_code` або перехопленням винятків безпосередньо у момент виконання операції.

Атаки класу TOCTOU є поширеним вектором уразливості у системному програмуванні безпеки. Якщо програма перевіряє права доступу до файлу перед його відкриттям, зловмисник може замінити цільовий файл символьним посиланням на захищений системний файл між моментом перевірки та моментом відкриття. Для захисту від таких атак у POSIX використовуються системні виклики відкриття файлу відносно дескриптора каталогу `openat()` із прапорцями заборони слідування символьним посиланням `O_NOFOLLOW`.

### Висячі символьні посилання (Dangling Symlinks)

Якщо символьне посилання вказує на шлях, який було вилучено, функція `fs::exists(symlink_path)` повертає `false`, оскільки вона слідує за посиланням до неіснуючого об'єкта. Однак сам файл посилання існує!

Для коректної перевірки існування самого символьного посилання слід використовувати функцію опитування статусу посилання `fs::is_symlink(fs::symlink_status(p))`.

### Права доступу та кросплатформові нюанси perms

Маска прав доступу `fs::perms` моделює атрибути POSIX (owner, group, others). При виконанні на системі Windows функція `fs::permissions()` може змінювати лише прапорець «тільки для читання» (Read-Only), оскільки Windows використовує складну систему списків контролю доступу (ACL), яка не мапиться один до одного на спрощені вісімкові права POSIX.

Крім того, слід враховувати специфіку роботи з мережевими файловими системами (NFS, SMB/CIFS). На мережевих дисках операції отримання розміру файлу або часу модифікації можуть вимагати затримки мережевого запиту. Застосування рекурсивних ітераторів обходу над мережевими дисками без обмеження глибини або пропуску помилок доступу може призводити до тимчасового заморожування виконання потоку програми.

Завдяки суворому дотриманню викладених правил та застосуванню об'єктної моделі `std::filesystem`, розробник отримує повністю безпечний, високпродуктивний та кросплатформовий код роботи з файловою системою.
