# 📋 Інтерфейс трейтів, концептів та категорій ітераторів

Ця довідкова вставка містить вичерпний технічний контракт механізмів обходу в мові C++: від класичних типів-трейтів (C++98/C++17) до концептів та вартівників C++20. Опис охоплює п'ять асоційованих типів, теги категорій, концепти вимог та вільні допоміжні функції для роботи з ітераторами.

## Анатомія std::iterator_traits

Шаблон `std::iterator_traits<It>` у заголовковому файлі `<iterator>` слугує єдиною точкою запиту властивостей будь-якого типу `It`, що використовується як ітератор. Головна мета цього шаблону — забезпечити єдиний метапрограмувальний інтерфейс для отримання асоційованих типів як для користувацьких класів-ітераторів, так і для звичайних вказівників мови C.

```cpp
namespace std {
    template<typename It>
    struct iterator_traits {
        using difference_type   = typename It::difference_type;
        using value_type        = typename It::value_type;
        using pointer           = typename It::pointer;
        using reference         = typename It::reference;
        using iterator_category = typename It::iterator_category;
    };
}
```

### Детальний розбір п'яти асоційованих типів

1. **`difference_type`**: Знаковий цілочисельний тип (зазвичай `std::ptrdiff_t`), що виражає відстань між двома ітераторами (результат операції `it2 - it1`). Цей тип використовується для підрахунку кількості кроків між елементами контейнера, зсуву ітераторів у функціях `std::advance` та обчислення розмірів діапазонів. Для стандартних контейнерів `difference_type` збігається з типом різниці адрес у пам'яті. Якщо тип не підтримує віднімання ітераторів, `difference_type` все одно визначається для позначення максимальної теоретичної кількості кроків.

2. **`value_type`**: Тип елемента, на який вказує ітератор (без кваліфікаторів `const` та посилань `&`). Цей тип використовується шаблонними алгоритмами для створення тимчасових змінних або буферів зберігання значення (наприклад, під час виклику `std::swap` або створення локальних копій). Для ітераторів виводу (англ. *output iterators*), які призначені виключно для запису в потік або контейнер і не підтримують операцію читання, цей тип може визначатися як `void`.

3. **`pointer`**: Тип вказівника на елемент (зазвичай `T*` або `typename It::pointer`). Він виражає тип результату, який повертає оператор стрілочного доступу `operator->()`. У більшості випадків цей тип дорівнює `value_type*` або `const value_type*`. Якщо ітератор не реалізує оператор `->`, цей тип визначається як `void` або спеціальний тип-обгортка.

4. **`reference`**: Тип, що повертається при розіменуванні оператора `*it`. Для більшості класичних контейнерів `reference` є справжнім посиланням на об'єкт у пам'яті — `T&` або `const T&`. Проте для проксі-ітераторів (таких як `std::vector<bool>::iterator` або розріджених views) тип `reference` може бути тимчасовим об'єктом-проксі, що імітує поведінку посилання через перевантаження оператора присвоєння.

5. **`iterator_category`**: Один із шести класичних тегів категорій, за яким компілятор визначає алгоритмічні можливості ітератора під час компіляції. Завдяки цьому типу шаблони алгоритмів можуть обирати оптимальну реалізацію обходу (наприклад, зсув за `O(1)` замість покрокового проходу).

### Спеціалізації для сирих вказівників C-стилю

Оскільки сирі вказівники `T*` та `const T*` є вбудованими типами мови C, вони не можуть мати внутрішніх вкладених синонімів типів (типу `T*::value_type`). Щоб сирі вказівники могли використовуватися у стандартних шаблонах STL нарівні з об'єктами класів, у стандартній бібліотеці передбачено часткові спеціалізації `std::iterator_traits`:

```cpp
namespace std {
    // Спеціалізація для неконстантного вказівника
    template<typename T>
    struct iterator_traits<T*> {
        using difference_type   = std::ptrdiff_t;
        using value_type        = T;
        using pointer           = T*;
        using reference         = T&;
        using iterator_category = std::random_access_iterator_tag; // у C++20: std::contiguous_iterator_tag
    };

    // Спеціалізація для константного вказівника
    template<typename T>
    struct iterator_traits<const T*> {
        using difference_type   = std::ptrdiff_t;
        using value_type        = T; // Зверніть увагу: value_type очищається від const
        using pointer           = const T*;
        using reference         = const T&;
        using iterator_category = std::random_access_iterator_tag; // у C++20: std::contiguous_iterator_tag
    };
}
```

Важлива деталь спеціалізації `iterator_traits<const T*>` полягає у тому, що тип `value_type` визначається як `T`, а не `const T`. Це зроблено свідомо: якби `value_type` залишався константним, алгоритми (такі як `std::sort` або `std::vector::iterator`) не змогли б створювати тимчасові змінній для обміну значень `T temp = *it`. Крім того, створення контейнерів типів `std::vector<const T>` є невалідним у C++.

## Теги категорій ітераторів (Iterator Category Tags)

Теги категорій — це порожні структури, впорядковані у закриту ієрархію успадкування. Вони не містять жодних даних або методів під час виконання (англ. *runtime*), а використовуються виключно під час компіляції для техніки **Tag Dispatching**:

```cpp
namespace std {
    struct input_iterator_tag {};
    struct output_iterator_tag {};
    struct forward_iterator_tag : public input_iterator_tag {};
    struct bidirectional_iterator_tag : public forward_iterator_tag {};
    struct random_access_iterator_tag : public bidirectional_iterator_tag {};
    
    // Додано у C++20 для формалізації суцільної пам'яті
    struct contiguous_iterator_tag : public random_access_iterator_tag {};
}
```

Завдяки успадкуванню тегів перевантаження функцій працює за правилами оприявнення типів: якщо алгоритм розрахований на `input_iterator_tag`, йому можна безпечно передати `forward_iterator_tag` або `random_access_iterator_tag`, оскільки похідний тег неявно перетворюється на посилання на свій базовий клас.

### Механізм Tag Dispatching проти if constexpr у C++17/C++20

У класичному C++98 вибір реалізації алгоритму залежно від категорії ітератора відбувався через допоміжні перевантажені функції. Компілятор аналізував тип тегу і обирав потрібний варіант:

```cpp
// Класичний Tag Dispatching у C++98/C++11
namespace detail {
    template<typename InputIt, typename Distance>
    void advance_impl(InputIt& it, Distance n, std::input_iterator_tag) {
        while (n > 0) { ++it; --n; }
    }

    template<typename RandomIt, typename Distance>
    void advance_impl(RandomIt& it, Distance n, std::random_access_iterator_tag) {
        it += n;
    }
}

template<typename It, typename Distance>
void advance(It& it, Distance n) {
    using category = typename std::iterator_traits<It>::iterator_category();
    detail::advance_impl(it, n, category{});
}
```

З появою C++17 та константних умовних виразів `if constexpr` цей код можна переписати в межах однієї функції без створення допоміжних приватних перевантажень у просторі імен `detail`:

```cpp
// Сучасна реалізація через if constexpr у C++17
template<typename It, typename Distance>
void advance(It& it, Distance n) {
    using category = typename std::iterator_traits<It>::iterator_category;
    
    if constexpr (std::is_base_of_v<std::random_access_iterator_tag, category>) {
        it += n;
    } else if constexpr (std::is_base_of_v<std::bidirectional_iterator_tag, category>) {
        if (n < 0) {
            while (n < 0) { --it; ++n; }
        } else {
            while (n > 0) { ++it; --n; }
        }
    } else {
        while (n > 0) { ++it; --n; }
    }
}
```

Версія з `if constexpr` забезпечує таку ж нульову ціну під час виконання, як і Tag Dispatching, оскільки гілки умов, які не відповідають типу ітератора, відтинаються компілятором ще на етапі синтаксичного аналізу шаблону.

## Концепти ітераторів C++20

У C++20 у заголовковому файлі `<iterator>` введено фундаментальні концепти, які замінюють перевірку неявних вимог документації на строгу компіляційну перевірку типів прямо у підписі шаблонних функцій.

### Базові мовні концепти обходу

1. **`std::input_or_output_iterator<I>`**: Найпростіший тип, який можна розіменувати через оператор `*i` та просунути вперед через префіксний або постфіксний інкремент `++i`. Цей концепт є базовою точкою входу для всіх ітераторів.

2. **`std::sentinel_for<S, I>`**: Перевіряє, що тип вартового `S` та тип ітератора `I` можна порівнювати між собою через оператори рівності `i == s` та `i != s`. При цьому вартовий `S` не зобов'язаний бути ітератором і може бути порожньою структурою-прапорцем.

3. **`std::sized_sentinel_for<S, I>`**: Розширює вимагання `sentinel_for`, додатково вимагаючи, щоб операція віднімання `s - i` або `i - s` була виражена за `O(1)` і повертала тип різниці `std::iter_difference_t<I>`.

### Розрізнення iterator_category та iterator_concept у C++20

У C++20 для забезпечення зворотної сумісності зі старими алгоритмами C++98 було введено розрізнення двох моделей тегів:

- **`iterator_category`**: Визначає категорію за класичною моделлю C++98 (для коду, що покладається на `std::iterator_traits`).
- **`iterator_concept`**: Новий вкладений синонім типу у C++20, який дозволяє ітераторові оголосити більш точну категорію для алгоритмів `std::ranges` (наприклад, `std::contiguous_iterator_tag`), навіть якщо для старих алгоритмів він оголошує `std::random_access_iterator_tag`.

Це дозволило стандартній бібліотеці додати категорію `ContiguousIterator` без ламання існуючого коду C++98/11/14/17, який не знав про існування нового тегу.

### Категоріальні концепти C++20

Концепти C++20 визначають алгоритмічні вимоги до типів через семантичні вирази:

```cpp
namespace std {
    // Ітератор вводу (читання однопрохідного потоку)
    template<typename I>
    concept input_iterator =
        std::input_or_output_iterator<I> &&
        std::indirectly_readable<I> &&
        requires(I i) {
            typename std::iter_concept_t<I>;
        };

    // Ітератор виводу (однопрохідний запис у потік або контейнер)
    template<typename I, typename T>
    concept output_iterator =
        std::input_or_output_iterator<I> &&
        std::indirectly_writable<I, T> &&
        requires(I i, T&& val) {
            *i++ = std::forward<T>(val);
        };

    // Однонапрямлений ітератор (багаторазовий прохід multi-pass)
    template<typename I>
    concept forward_iterator =
        std::input_iterator<I> &&
        std::derived_from<std::iter_concept_t<I>, std::forward_iterator_tag> &&
        std::incrementable<I> &&
        std::sentinel_for<I, I>;

    // Двонапрямлений ітератор (підтримка оператора декременту)
    template<typename I>
    concept bidirectional_iterator =
        std::forward_iterator<I> &&
        std::derived_from<std::iter_concept_t<I>, std::bidirectional_iterator_tag> &&
        requires(I i) {
            { --i } -> std::same_as<I&>;
            { i-- } -> std::same_as<I>;
        };

    // Ітератор довільного доступу (зсув та арифметичні оператори за O(1))
    template<typename I>
    concept random_access_iterator =
        std::bidirectional_iterator<I> &&
        std::derived_from<std::iter_concept_t<I>, std::random_access_iterator_tag> &&
        std::totally_ordered<I> &&
        std::sized_sentinel_for<I, I> &&
        requires(I i, const I j, const std::iter_difference_t<I> n) {
            { i += n } -> std::same_as<I&>;
            { i -= n } -> std::same_as<I&>;
            { j +  n } -> std::same_as<I>;
            { n +  j } -> std::same_as<I>;
            { j -  n } -> std::same_as<I>;
            { j[n]   } -> std::same_as<std::iter_reference_t<I>>;
        };

    // Ітератор суцільної пам'яті (гарантія розташування елементів у RAM)
    template<typename I>
    concept contiguous_iterator =
        std::random_access_iterator<I> &&
        std::derived_from<std::iter_concept_t<I>, std::contiguous_iterator_tag> &&
        std::is_lvalue_reference_v<std::iter_reference_t<I>> &&
        std::same_as<std::iter_value_t<I>, std::remove_cvref_t<std::iter_reference_t<I>>> &&
        requires(const I& i) {
            { std::to_address(i) } -> std::same_as<std::add_pointer_t<std::iter_reference_t<I>>>;
        };
}
```

Головна перевага концептів над класичними тегами полягає у тому, що концепт перевіряє не лише наявність синоніма `iterator_category`, а й фактичну спроможність типу виконувати потрібні операції (такі як наявність оператора `+=` або сумісність повертаного типу розіменування).

### Спеціальні вартівники та зв'язувальні адаптери C++20

Стандарт C++20 надає додаткові узагальнюючі типи у заголовку `<iterator>`:

- `std::unreachable_sentinel_t`: Вартовий, порівняння з яким `it == std::unreachable_sentinel` завжди обчислюється як `false` під час компіляції. Це дозволяє створювати нескінченні діапазони або передавати компіляторові інформацію для векторної оптимізації, вказуючи, що умова виходу з циклу буде досягнута через внутрішній `break`. Використання цієї позначки сигналізує оптимізатору про відсутність потреби перевіряти вихід за межі буфера на кожній ітерації.
- `std::default_sentinel_t`: Порожній вартовий за замовчуванням, що використовується для генераторів та ледачих потоків даних.
- `std::counted_iterator<I>`: Обгортає ітератор `I` та лічильник `n`. Робить ітератор зупинюваним рівно через `n` кроків, перетворюючи довільний ітератор на об'єкт з вартовим лічильником.
- `std::common_iterator<I, S>`: Приводить асиметричну пару `Iterator` та `Sentinel` до єдиного спільного типу (англ. *common type*) через `std::variant`. Це дозволяє передавати нові діапазони C++20 Ranges у застарілі алгоритми C++98, які вимагають симетричних типів `begin` та `end`.

### Контракт std::ranges::subrange

У C++20 шаблон `std::ranges::subrange<I, S>` об'єднує ітератор `I` та вартовий `S` в єдиний об'єкт діапазону (англ. *view*). Він задовольняє концепт `std::ranges::view` і надає класичні методи `begin()` та `end()`, повертаючи відповідні типи `I` та `S`. Якщо `S` задовольняє `std::sized_sentinel_for<S, I>`, `subrange` також надає метод `size()` з часовою складністю `O(1)`. Це робить `subrange` ідеальним мостом між новими асиметричними вартівниками та алгоритмами C++20.

## Проксі-ітератори та проблема свідка доступності (Proxy Iterators)

Окремою вимогою в ієрархії концептів є підтримка справжнього посилання `T&` для категорії `ContiguousIterator` та `RandomAccessIterator` у C++98.

Коли тип ітератора розіменовується не у справжній `T&`, а у тимчасовий об'єкт-проксі (англ. *proxy object*), такий ітератор називається **проксі-ітератором**. Класичним прикладом у стандартній бібліотеці є `std::vector<bool>::iterator`. Оскільки `std::vector<bool>` пакує кожен біт у бітову маску (8 біт на один байт), отримати пряму адресу окремого біта у пам'яті (`bool&`) неможливо на апаратному рівні процесора x86/ARM.

Тому розіменування `*it` повертає тимчасовий об'єкт `std::vector<bool>::reference`, який перевизначає `operator=` для модифікації біта у байті. Наслідки для контракту C++:
- `std::vector<bool>::iterator` не задовольняє концепт `std::contiguous_iterator` і навіть `std::random_access_iterator` у суворому розумінні C++20 (оскільки `reference` не є справжнім `bool&`).
- Шаблонні алгоритми, які вимагають прив'язки авто-посилання `auto& val = *it;`, зазнають помилки компіляції або виклику прив'язки до тимчасового об'єкта (англ. *rvalue reference*).
- У C++20 концепт `std::indirectly_readable` та CPO `std::ranges::iter_move` вирішують цю проблему, дозволяючи алгоритмам правильно працювати з проксі-об'єктами через семантику витягування значення.

Також подібні проксі-об'єкти використовуються у нових адаптерах діапазонів C++20, таких як `std::views::zip` та `std::views::enumerate`, де оператор розіменування повертає кортеж тимчасових посилань `std::tuple<T1&, T2&>`.

## Допоміжні псевдоніми типів C++20 (Associated Type Helpers)

У C++20 замість громіздкого виклику `typename std::iterator_traits<It>::value_type` введено короткі шаблони псевдонімів типів у простір імен `std`. Вони автоматично працюють як для класичних ітераторів із `iterator_traits`, так і для нових концептуальних ітераторів та типів з асиметричними вартовими:

| Псевдонім типу у C++20 | Опис та семантика |
| :--- | :--- |
| `std::iter_value_t<I>` | Тип елемента (аналог `value_type`), витягнутий з `iterator_traits` або концептів. |
| `std::iter_reference_t<I>` | Тип результату розіменування `decltype(*std::declval<I&>())`. |
| `std::iter_difference_t<I>` | Тип різниці між ітераторами (знаковий цілочисельний тип). |
| `std::iter_rvalue_reference_t<I>` | Тип rvalue-посилання `decltype(std::ranges::iter_move(std::declval<I&>()))`. |
| `std::iter_concept_t<I>` | Найбільш специфічний концептуальний тег ітератора. |

Використання цих хелперів дозволяє уникнути помилок синтаксису C++98, коли забуте слово `typename` перед метафункцією призводило до важкочитаних помилок компіляції.

## Кастомізаційні точки доступу: ranges::iter_move та ranges::iter_swap

У C++20 з'явилися нові об'єкти CPO (англ. *Customization Point Objects*), призначені для узагальненої маніпуляції вмістом ітераторів без жорсткої прив'язки до операторів `*it` та `std::swap`:

1. **`std::ranges::iter_move(it)`**: Дозволяє витягнути rvalue-посилання з ітератора `it`. Якщо для типу ітератора реалізовано ADL-функцію `iter_move`, викликається вона; інакше виконується `std::move(*it)`. Це робить роботу з проксі-ітераторами безпечною під час переміщення елементів.
2. **`std::ranges::iter_swap(it1, it2)`**: Обмінює значення, на які вказують ітератори `it1` та `it2`. Якщо тип надає спеціалізовану ADL-функцію `iter_swap`, алгоритми сортування використовують її за `O(1)` без проміжного копіювання (наприклад, для обміну вузлів у зв'язаних списках).

## Вільні функції обходу та навігації

Стандарт надає п'ять основних безшаблонерних/шаблонних вільних функцій для безпечного маніпулювання ітераторами залежно від їхньої категорії у заголовку `<iterator>`:

### 1. `std::advance(it, n)`
Зсуває ітератор `it` на `n` елементів. Перевірка категорії відбувається під час компіляції:
- Для `RandomAccessIterator`: виконує `it += n` за один крок `O(1)`.
- Для `BidirectionalIterator`: якщо `n < 0`, виконує `--it` `|n|` разів, дозволяючи зворотний зсув.
- Для `InputIterator` та `ForwardIterator`: виконує `++it` `n` разів у циклі (`O(n)`). Передача від'ємного `n` для не-двонапрямленого ітератора викликає невизначену поведінку (UB).

### 2. `std::distance(first, last)`
Обчислює кількість елементів між `first` та `last`.
- Для `RandomAccessIterator`: повертає результат виразу `last - first` за `O(1)`.
- Для решти категорій: послідовно інкрементує копію ітератора `first` до досягнення `last`, повертаючи лічильник знайдених кроків за `O(n)`. При цьому `last` має бути досяжним з `first`.

### 3. `std::next(it, n = 1)` та `std::prev(it, n = 1)`
Повертають **новий ітератор**, зсунутий на `n` позицій вперед або назад, залишаючи оригінальний ітератор `it` без змін. Це дозволяє використовувати їх безпосередньо у виразах передачі аргументів у функції без модифікації вихідної змінної.

### 4. `std::ranges::advance` та `std::ranges::distance` (C++20)
Нові версії функцій із простору імен `std::ranges`, які підтримують асиметричні вартівники (sentinels), вміють приймати верхню межу обходу для запобігання виходу за межі діапазону та повертають залишок недосягнутого кроку.

## Стандартні адаптери ітераторів

Адаптери ітераторів — це шаблонні обгортки, які перетворюють поведінку вихідного ітератора, адаптуючи його під інші алгоритмічні задачі:

| Адаптер | Заголовковий файл | Опис контракту та механіки |
| :--- | :--- | :--- |
| `std::reverse_iterator<It>` | `<iterator>` | Інвертує напрямок обходу двонапрямленого ітератора. `*rIt` повертає `*std::prev(base)`, зберігаючи напіввідкритий інтервал `[begin, end)`. |
| `std::move_iterator<It>` | `<iterator>` | Перетворює оператор розіменування `operator*` на повернення rvalue-посилання `T&&` через `std::move`, дозволяючи переміщувати елементи під час обходу. |
| `std::back_insert_iterator<C>` | `<iterator>` | Адаптер виводу. Присвоєння `*it = val` внутрішньо викликає метод контейнера `container.push_back(val)`. |
| `std::front_insert_iterator<C>` | `<iterator>` | Адаптер виводу. Присвоєння `*it = val` внутрішньо викликає метод контейнера `container.push_front(val)`. |
| `std::insert_iterator<C>` | `<iterator>` | Адаптер виводу з вказанням позиції. Присвоєння `*it = val` викликає `container.insert(pos, val)`. |
| `std::istream_iterator<T>` | `<iterator>` | Читає послідовні значення типу `T` зі стандартного потоку вводу `std::istream` через `operator>>`. |
| `std::ostream_iterator<T>` | `<iterator>` | Записує послідовні значення типу `T` у потік виводу `std::ostream` через `operator<<` з можливим додатковим текстовим розділювачем. |

## Матриця інвалідації ітераторів у контейнерах STL

При модифікації контейнерів у пам'яті ітератори можуть втрачати дійсність (англ. *iterator invalidation*). Використання інвалідованого ітератора призводить до невизначеної поведінки (UB) або пошкодження пам'яті.

| Контейнер | Операція вставки (Insert / Push) | Операція видалення (Erase / Pop) |
| :--- | :--- | :--- |
| `std::vector` | Інвалідує **всі** ітератори при реалокації пам'яті (`capacity` перевищено). Без реалокації — інвалідує ітератори від позиції вставки до кінця. | Інвалідує ітератори від позиції видалення до кінця масиву. |
| `std::deque` | Інвалідує **всі** ітератори при вставці всередину. Вставка в початок чи кінець інвалідує ітератори, але зберігає посилання на об'єкти. | Видалення всередині інвалідує всі ітератори. Видалення з початку/кінця інвалідує лише вказаний елемент. |
| `std::list` / `std::forward_list` | **Ніколи** не інвалідує ітератори інших елементів. | Інвалідує **лише** ітератор видаленого елемента. |
| `std::set` / `std::map` | **Ніколи** не інвалідує ітератори інших вузлів дерева. | Інвалідує **лише** ітератор видаленого вузла. |
| `std::unordered_map` | При `rehashing` (перевищено `max_load_factor`) інвалідує **всі** ітератори. Без `rehashing` — зберігає ітератори на інші елементи. | Інвалідує **лише** ітератор видаленого елемента у бакеті. |

Знання цієї матриці є обов'язковою умовою для вибору правильних алгоритмів видалення (таких як `std::erase_if` у C++20).

## Чеклист вимог для створення власного ітератора (C++20)

Щоб компілятор і стандартні алгоритми C++20 визнали клас `MyIterator` повноцінним ітератором (наприклад, що задовольняє концепт `std::forward_iterator`), розробник має забезпечити дотримання такого технічного контракту:

1. **Визначення вкладених синонімів типів**:
   - `using value_type = T;`
   - `using difference_type = std::ptrdiff_t;`
   - `using iterator_concept = std::forward_iterator_tag;` (або `iterator_category`)
   - `using pointer = T*;`
   - `using reference = T&;`

2. **Обов'язкові конструктори та присвоєння**:
   - Конструктор за замовчуванням `MyIterator() = default;` (необхідний для задоволення вимог концепту `std::regular`).
   - Конструктор копіювання та оператор присвоєння.

3. **Оператори розіменування та стрілочного доступу**:
   - `reference operator*() const;`
   - `pointer operator->() const;`

4. **Оператори навігації та переходу**:
   - `MyIterator& operator++();` (префіксний інкремент, що повертає посилання на себе).
   - `MyIterator operator++(int);` (постфіксний інкремент, що повертає копію попереднього стану).

5. **Оператори порівняння**:
   - `bool operator==(const MyIterator& other) const;`
   - `bool operator!=(const MyIterator& other) const;` (у C++20 генерується компілятором автоматично, якщо визначено `operator==`).

Дотримання цього контракту гарантує, що власний ітератор буде повністю прозорим для усіх стандартних алгоритмів `std::ranges` та класичних алгоритмів STL.
