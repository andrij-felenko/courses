# 📜 Історія форматування у C++: від sprintf до std::format та std::print

Текстове форматування у системному програмуванні тривалий час залишалося ареною жорстких компромісів між швидкодією, типобезпекою, безпекою пам'яті та зручністю використання. Історія еволюції засобів виводу в мовах C та C++ показує, як мовне середовище поступово відмовлялося від небезпечної спадщини C-varargs та громіздкої станової архітектури `iostream`, намагаючись досягти ідеалу Python-подібного синтаксису без жодних накладних витрат у runtime.

## Ера мови C: швидкість ціною арифметики, випадкових аварій та CVE-вразливостей

Уперше концепція рядка формату з масками замінників була запропонована в лабораторіях Bell Labs під час створення операційної системи Unix на машинах PDP-11. У мові C головними інструментами побудови рядків та консольного виводу стали функції сімейства `printf`, `fprintf`, `sprintf` та `vsprintf`.

:::tabs
```c
/* C: Традиційне використання sprintf та snprintf */
#include <stdio.h>

void log_connection(const char* host, int port) {
    char buffer[128];

    /* Потенційне переповнення буфера у sprintf при занадто довгому host */
    sprintf(buffer, "Connecting to %s:%d", host, port);

    /* Безпечніша альтернатива C99 snprintf з явним обмеженням розміру */
    snprintf(buffer, sizeof(buffer), "Connecting to %s:%d", host, port);
}
```
```cpp
// C++: Ідіоматична обгортка з std::string_view та std::span
#include <format>
#include <string_view>
#include <span>

void log_connection_cpp(std::span<char> buffer, std::string_view host, int port) {
    // Безалокаційний типобезпечний вивід
    std::format_to_n(buffer.data(), buffer.size() - 1, "Connecting to {}:{}", host, port);
}
```
:::

Дизайн `printf` був орієнтований на граничну простоту реалізації на асемблері: рядок формату містив символи-специфікатори (`%d` для цілих чисел, `%f` для чисел із плаваючою крапкою, `%s` для нуль-термінованих рядків), а сам виклик спирався на функціонал C-varargs (`va_list`, `va_start`, `va_arg`).

Проте механізм C-varargs приховував у собі фундаментальну небезпеку: **повну відсутність контролю типів на рівні компілятора**. На стек або у регістри ABI передавалися сирі байти аргументів. За угодами викликів того часу (наприклад, на PDP-11 або VAX), типи `char` та `short` примусово розширювалися до `int`, а `float` перетворювався на `double`. 

Компілятор C сприймав рядок формату як звичайну послідовність символів і ніяк не перевіряв його під час збірки. Якщо розробник припускався помилки й передавав `double` замість специфікатора цілого числа `%d` або передавав ціле число `42` замість вказівника на рядок `%s`, програма під час виконання зчитувала довільну адресу зі стека. Це призводило до невизначеної поведінки (Undefined Behavior), пошкодження пам'яті або фатального аварійного завершення процесів (Segmentation Fault).

У наприкінці 1990-х років вибухнув цілий клас вразливостей під назвою **Format String Vulnerabilities (CVE-2000-0573)**. Якщо програма виводила рядок, отриманий від користувача, у виклик вида `printf(user_input)`, зловмисник міг передати специфікатор `%n` (який записує кількість виведених байтів за адресою з аргументу) та переписати адреси повернення функцій на стеку, отримуючи повний контроль над виконанням коду на сервері.

Крім того, C-функції форматування не мали жодної системи розширення для типів користувача. Створити власну структуру `struct Point { int x; int y; }` і передати її безпосередньо у `printf("%s", pt)` було неможливо — доводилося вручну розпаковувати кожне поле структури у місці виклику.

## Спадщина C++98: потоки iostream та станова катастрофа

З появою мови C++ Б'ярн Страуструп запропонував альтернативну концепцію форматування та виводу, побудовану на об'єктно-орієнтованих потоках `std::ostream`, `std::stringstream` та операторах перевантаження `operator<<`.

Головною перевагою `iostream` стала повна **типобезпека**. Диспетчеризація виклику відбувалася на рівні перевантажень функцій під час компіляції. Передати некоректний тип було неможливо: для кожного стандартного чи призначеного для користувача типу викликався відповідний `operator<<`.

```cpp
// C++98/C++03: Потоковий вивід через std::ostringstream
#include <iostream>
#include <sstream>
#include <iomanip>

std::string format_log_legacy(const std::string& host, int port) {
    std::ostringstream ss;
    ss << "Connecting to " << host << ":" << std::dec << port 
       << " (HEX: 0x" << std::hex << std::uppercase << std::setw(4) << std::setfill('0') << port << ")";
    return ss.str();
}
```

Незважаючи на типобезпеку та підтримку власних типів, `iostream` викликав хвилю критики в інженерній спільноті через чотири фундаментальні вади:

1. **Багатослівність та розрив візуальної суцільності.** Замість єдиного рядка формату код перетворився на ланцюжки лапок, операторів `<<` та маніпуляторів. Зрозуміти підсумкову структуру рядка при складному форматуванні стало надзвичайно важко.
2. **Становий характер маніпуляторів (Stateful I/O).** Маніпулятори типу `std::hex`, `std::setprecision` або `std::setw` змінювали внутрішній прапорець стану самого об'єкта потоку (`std::ios_base::fmtflags`). Якщо розробник переключав потік у шістнадцятковий режим `std::hex` у глибині функції і забував відновити `std::dec`, усі подальші числа у всьому застосунку виводилися у hex-форматі.
3. **Низька швидкодія та конкуренція за локалі.** Класи `std::ostream` були побудовані на віртуальних функціях буфера `std::streambuf`, вимагали створення проміжних об'єктів у купі (`std::stringbuf`), проводили періодичне захоплення м'ютексів для синхронізації з C-stdio та виконували розбір локалей (Locale parsing) при кожній операції виводу.
4. **Неможливість інтернаціоналізації (i18n).** При перекладі програм на інші мови порядок слів у реченні змінюється. Наприклад, англійське `"File %s created by %s"` німецькою або японською вимагає зміни місцями першого та другого аргументів. Потоковий вивід `os << "File " << a << " created by " << b` жорстко зафіксовував порядок аргументів у коді, унеможливлюючи винесення рядків у зовнішні файли перекладу.

## Епоха бібліотек Boost.Format та fmtlib

Бажання поєднати зручність синтаксису рядків форматування C з типобезпекою C++ привело до появі бібліотеки **Boost.Format** у 2002 році. Вона дозволяла використовувати специфікатори позицій вида `%1%` та `%2%`:

```cpp
// Використання Boost.Format (2002 рік)
#include <boost/format.hpp>
#include <string>

std::string s = boost::str(boost::format("Connecting to %1%:%2%") % "localhost" % 8080);
```

Проте Boost.Format був занадто важким: перевантаження оператора `%` викликало значне уповільнення компіляції та додавало помітні накладні витрати під час виконання через побудову складного дерева об'єктів для кожного аргументу.

Справжній прорив стався у 2012 році, коли Віктор Зверович (Victor Zverovich) відкрив розробку відкритої бібліотеки **fmt** (відомої як `fmtlib`). Віктор відмовився від застарілої синтаксичної традиції `%` і взяв за основу розширену граматику форматування мови Python (PEP 3101).

Бібліотека `fmtlib` продемонструвала вражаючі результати:
- Вона працювала **швидше за `printf`** за рахунок безалокаційного внутрішнього стекового буфера та оптимізованого алгоритму конвертації чисел у текст (Dragonbox / Grisu).
- Забезпечувала повну типобезпеку на етапі компіляції.
- Надавала компактний синтаксис `{}` та позиційні аргументи `{0}`, `{1}`.
- Підтримувала швидке розширення для користувацьких типів через спеціалізацію шаблонів.

`fmtlib` моментально здобула визнання і стала стандартом de facto у великих C++ проєктах (LLVM, CMake, Redis, MongoDB, FlightGear).

## Стандартизація: C++20 std::format та C++23 std::print

Успіх `fmtlib` став підґрунтям для офіційної пропозиції до Комітету зі стандартизації C++. Папір **P0645 (Text Formatting)**, створений Віктором Зверовичем, Говардом Хіннантом (Howard Hinnant) та іншими авторами, був офіційно прийнятий до стандарту **C++20** під назвою `<format>`.

Ключовим досягненням `std::format` у C++20 стала поява підсистеми компіляційної перевірки рядка формату. Завдяки механізму `consteval` компілятор аналізує рядок формату під час збірки програми. Якщо розробник напише `std::format("{:d}", "hello")`, компіляція зупиниться з описовою помилкою типу: `"format specifier 'd' is invalid for string types"`.

Однак у C++20 стандартизували лише форматування у рядок (`std::format`, `std::format_to`). Прямий вивід у консоль все ще вимагав написання `std::cout << std::format(...)`, що призводило до подвійного копіювання даних та збереження згаданих проблем iostream з локами та локалями.

Щоб закрити цю прогалину, у стандарту **C++23** було прийнято документ **P2093 (Formatted output)**, який додав функції `std::print` та `std::println` у заголовочний файл `<print>`.

`std::print` вирішив задавнену проблему виводу Юнікоду (UTF-8) у системних консолях Windows (де `printf` та `std::cout` виводили "кракозябри" через незбіг кодових сторінок). `std::print` визначає, чи є вихідний потік консоллю, і на операційних системах Windows автоматично виконує виклик нативного Unicode API (`WriteConsoleW`), оминаючи шар сумісності C-runtime.

Таким чином, за тридцять років еволюції C++ пройшов шлях від небезпечних C-аргументів зі випадковими аваріями до найшвидшої в індустрії, повністю типобезпечної системи форматування під час компіляції.
