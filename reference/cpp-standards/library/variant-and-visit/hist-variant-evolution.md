# 📜 Історія еволюції типів-сум у мові C++: від C-union до std::variant

Вираження неоднорідних даних, де один об'єкт може містити лише один стан із фіксованого набору типів у будь-який момент часу, пройшло довгий шлях розвитку у мовах програмування системного рівня.

Еволюція типів-сум відображає постійну боротьбу між трьома критичними інженерними вимогами:
1. **Продуктивність пам'яті:** розміщення об'єктів у суцільному блоці на стеку без використання динамічної купи.
2. **Безпека типів (Type Safety):** статичний контроль за відповідністю типу під час доступів та викликів методів.
3. **Автоматичне керування життєвим циклом:** коректне конструювання та знищення об'єктів зі складними деструкторами.

## 1. Об'єднання в мові C (1970-ті роки)

У мові C об'єднання `union` було створене для максимально ефективного використання оперативної пам'яті: усі члени `union` починаються з однієї базової адреси, а розмір об'єднання дорівнює розміру його найбільшого члена.

:::tabs
```c
/* Мова C: розмічене об'єднання з тегом типу */
struct CTaggedUnion {
    int type_tag; // 0 = int, 1 = double
    union {
        int i_val;
        double d_val;
    } data;
};
```
```cpp
// Мова C++: аналогічна структура C-style з тегом
struct CppTaggedUnion {
    int type_tag; // 0 = int, 1 = double
    union {
        int i_val;
        double d_val;
    } data;
};
```
:::

Головним дефектом C-union є відсутність автоматичного зв'язку між полем `type_tag` та вмістом `union`. Програміст змушений писати ручні оператори `switch` або `if`, перевіряючи тег перед кожним доступом.

Якщо розробник допускає помилку в логіці та зчитує поле `d_val` у момент, коли активним є `i_val`, програма інтерпретує біти цілого числа за правилами числа з плаваючою крапкою. Це створює непередбачувані помилки (Undefined Behavior) та порушує суворе правила вирівнювання типів (Strict Aliasing).

## 2. Необмежені об'єднання у C++11 (Unrestricted Unions)

У стандарту C++98/03 об'єднання `union` мало жорстке обмеження: членами `union` могли бути лише типи з тривіальними конструкторами та деструкторами (POD-типи, Plain Old Data). Спроба помістити `std::string` чи `std::vector` у `union` викликала помилку компіляції.

Стандарт C++11 зняв це обмеження, запровадивши **необмежені об'єднання** (Unrestricted Unions, папір N2248). C++11 дозволив розміщувати в `union` будь-які типи із нетривіальними конструкторами та деструкторами, але поклав усю відповідальність за керування життєвим циклом на розробника:

```cpp
union UnrestrictedUnion {
    int i_val;
    std::string s_val;

    // Компілятор вимагає від розробника самостійно визначити конструктори та деструктор!
    UnrestrictedUnion() : i_val(0) {}
    ~UnrestrictedUnion() {} // Не знає, чи треба викликати ~string()!
};
```

Для зміни типу всередині C++11 `union` розробник мусив вручну викликати деструктор `s_val.~basic_string()` та застосовувати оператор placement `new`. Це вирішило проблему зберігання складних об'єктів у пам'яті, але зберегло всі ризики небезпечного доступу до бітів.

## 3. Бібліотека Boost.Variant (2003–2015 роки)

Побачивши обмеження мови, автори бібліотеки Boost (Кевлін Хенні, Ерік Фрідріхсен та Олексій Гуртовий) створили шаблонний клас `boost::variant`.

`boost::variant` став першою реалізацією безпечного типу-суми у C++. Він вирішив дві ключові задачі:
- **Автоматичний контроль деструкторів:** `boost::variant` запам'ятовував активний тип і автоматично викликав деструктор відповідного об'єкта під час знищення чи присвоєння.
- **Статичний відвідувач (Static Visitor):** Запровадження функції `boost::apply_visitor` дозволило реалізувати статичний поліморфізм без виділення пам'яті у купі.

Однак `boost::variant` мав суттєві недоліки, зумовлені обмеженнями мови C++03:
1. **Необхідність пустих станів через винятки:** При спробі присвоїти нове значення `boost::variant` міг виділити пам'ять у купі (fallback allocation) або використати внутрішнє обгортання, щоб зберегти гарантію безпеки винятків.
2. **Тривалий час компіляції:** Через відсутність варіативних шаблонів у C++03 `boost::variant` імітував варіативність за допомогою складного метапрограмування препроцесора (`BOOST_VARIANT_LIMIT_TYPES = 20`).

## 4. Дискусія в комітеті WG21 та пропозиція P0088 (2015–2017 роки)

У 2015 році Аксель Науманн (Axel Naumann) подав пропозицію P0088 щодо включення `std::variant` до складу стандарту C++17.

Найбільш гостра дискусія в комітеті WG21 розгорнулася навколо так званої **проблеми невалідного стану під час винятків** (The Empty State Problem / Never-Empty Guarantee).

### Суть конфлікту у комітеті:
Коли ви виконуєте `variant_A = value_B`, об'єкт повинен знищити значення типу `A` і сконструювати значення типу `B`. Якщо конструктор типу `B` кидає виняток посередині операції, старий об'єкт `A` вже знищено, а новий `B` не створено!

Комітет розділився на дві групи:

1. **Прибічники обгортання у порожній стан (Nullable Variant):** Пропонували дозволити `std::variant` автоматично ставати порожнім (аналог `std::optional` чи `nullptr`), якщо конструктор кинув виняток.
2. **Прибічники принципу строгої суми (Never-Empty Guarantee):** Математики та автори мови (зокрема Б'ярн Страуструп та Степан Лававей) категорично заперечували проти неявного порожнього стану. Вони аргументували це тим, що алгебраїчний тип-сума A + B не повинен перетворюватися на 1 + A + B. Якщо дозволити порожній стан за замовчуванням, `std::variant` перетвориться на ще один аналог вказівника `nullptr` чи `null` у мовах Java/C#. Це змусило б розробників додавати перевірки на порожнечу перед кожним зверненням до об'єкта, порушуючи статичну типізацію та створюючи нові ризики для надійності коду.

### Компромісне рішення: стан valueless_by_exception
У результаті комітет прийняв компроміс: `std::variant` гарантує, що він **завжди** містить валідне значення (Never-Empty Guarantee при нормальному виконанні).

Проте якщо операція присвоєння переривається винятком, об'єкт не намагається підробити порожній стан через `nullptr`, а переходить у явний стан `valueless_by_exception`. Це вказує на те, що стан варіанта зламано внаслідок винятку під час конструювання.

## 5. Стандартизація C++20 та C++23

- **C++20:** Механізми `std::variant` та `std::visit` отримали повну підтримку `constexpr`. Це дозволило виконувати патерн-матчинг та оцінку типів-сум безпосередньо під час компіляції програми.
- **C++23:** Запроваджено функцію `std::visit<R>`, яка дозволяє явно вказувати тип повернення відвідувача. Також запроваджено фічу Deducing `this`, яка спростила створення рекурсивних відвідувачів та роботу з відносними посиланнями на об'єкти.
