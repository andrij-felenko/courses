# 📜 Історія текстових типів у C++: від C-рядків до std::string_view

Цей історичний нарис відстежує еволюцію представлення тексту в мовах C та C++ протягом чотирьох десятиліть: від небезпечних C-рядків з нульовим термінатором до розвалу епохи Copy-On-Write та стандартизації типу `std::string_view` у C++17.

## 1970-ті: Спадщина мови C та небезпечний нульовий термінатор

У мові C, створеній Деннісом Рітчі в Bell Labs, рядок не був окремим типом даних. Він репрезентувався як неперервний масив байтів `char[]`, закінчення якого позначалося нульовим символом `\0` (ASCII 0x00).

Такий вибір був диктовний вкрай обмеженими ресурсами комп'ютерів PDP-11: збереження довжини рядка в окремому полі вимагало б додаткових 2 або 4 байтів пам'яті на кожен рядок. Позначення кінця рядка спеціальним символом `\0` дозволило зберігати лише сам текст.

Проте ця економія створила дві фундаментальні проблеми, які супроводжували програмування десятиліттями:

1. **Складність `O(N)` для обчислення довжини**: Функція `strlen(s)` змушена побайтово сканувати увесь масив у пам'яті до першого `\0`. Обчислення довжини мільйонного рядка вимагає мільйона зчитувань з пам'яті.
2. **Вразливості переповнення буфера (Buffer Overflow)**: Якщо функція `strcpy` або `strcat` зустрічає рядок без `\0`, вона продовжує перезаписувати пам'ять за межами масиву, руйнуючи стек та відкриваючи шляхи для мережевих атак.

Крім того, C-рядки не мали семантики володіння пам'яттю. Програміст змушений був вручну стежити за тим, хто виділив масив через `malloc()`, хто відповідає за його звільнення через `free()`, і чи не було масив звільнено достроково (помилки Double Free та Use-After-Free).

## C++98: Клас std::string та створення володаря

Коли у 1998 році було прийнято перший стандарт C++98, Комітет із стандартизації намагався розв'язати проблеми C-рядків, створивши шаблонний клас `std::basic_string<char>` (псевдонім `std::string`).

`std::string` об'єднав масив символів у купі з двома додатковими полями: поточним розміром (`size`) та виділеною ємністю (`capacity`). Це зробило виклик `s.size()` миттєвим (`O(1)`), а автоматичне виділення пам'яті у деструкторі за принципом RAII усунуло витоки пам'яті.

Проте `std::string` розроблявся як **монопольний володар** пам'яті. Намагаючись захистити розробника від висячих вказівників, стандарт вимагав, щоб кожен об'єкт `std::string` володів власним буфером. Будь-яке виділення підрядка `s.substr()` або передача C-рядка у функцію з `const std::string&` змушували програму копіювати байти й звертатися до динамічного алокатора пам'яті.

Комітет стандартизації орієнтувався на парадигму безпечного коду, де кожен об'єкт контролює свій час життя. Проте для розробників системного програмного забезпечення (веб-сервери, СУБД, компилятори) ця безпека вилилася у величезні втрати швидкості через нескінченне копіювання текстових буферів.

## Епоха Copy-On-Write (COW) та її розвал у C++11

Щоб уникнути дорогих копіювань при передачі та поверненні `std::string`, розробники компиляторів у 2000-х роках (зокрема GCC у бібліотеці `libstdc++` версій 3.x та 4.x) впровадили оптимізацію **Copy-On-Write (COW)**.

При COW-підході декілька об'єктів `std::string` вказували на один і той самий буфер у купі, який містив лічильник посилань. Копіювання рядка лише збільшувало лічильник на 1 (`O(1)`). Справжнє дублювання буфера виконувалося лише тоді, коли один із рядків намагався змінити свій вміст (записати символ).

```cpp
// Концепція Copy-On-Write (GCC 3.4 / 4.8)
std::string a = "Very Long Text Payload...";
std::string b = a; // Обидва вказують на один буфер! ref_count = 2

b[0] = 'v'; // Справжнє копіювання відбувається ЛИШЕ ТУТ!
```

Однак вихід на арену багатоядерних процесорів виявив фатальний недолік COW:

1. **Атомарні операції уповільнювали програму**: Збільшення та зменшення лічильника посилань вимагало атомарних інструкцій процесора (`LOCK XADD` на x86). При передачі рядків між потоками атомарні операції спричиняли скидання кеш-ліній процесора (Cache Line Bouncing), роблячи COW повільнішим за звичайне копіювання.
2. **Помилки потокобезпечності**: Неконстантні оператори `operator[]` змушені були виконувати дублювання буфера, навіть якщо розробник викликав їх лише для читання символу.

У C++11 Комітет стандартизації **офіційно заборонив Copy-On-Write** для `std::string`. Стандарт C++11 зажадав, щоб елементи рядка зберігалися суцільним масивом і щоб оператор читання не збурював інші об'єкти. Реалізації перейшли на оптимізацію малих рядків (SSO), що повернуло проблему дорогих копіювань для великих рядків.

## Пошуки рішення: StringPiece та Boost.StringRef

З забороною COW у C++11 розробники великих систем опинилися перед проблемою: кожна токенізація файлу чи розбір JSON створювали мільйони алокацій у купі.

Великі IT-компанії почали створювати власні внутрішні рішення:
- **Google**: створив клас `StringPiece` у своїх відкритих бібліотеках (Google Abseil / Chromium) для розбору HTTP-запитів у високоінтенсивних серверах Search та AdSense.
- **LLVM / Clang**: створили `llvm::StringRef` для швидкої роботи компілятора з вихідним кодом, що дозволило прискорити компіляцію C++ кодів на 20-30%.
- **Boost**: випустив бібліотеку `Boost.Utility/StringRef` (`boost::string_ref` у Boost 1.53, згодом `boost::string_view`).

Всі ці типи мали однакову структуру: легковажна пара `(const char* data, size_t size)`, яка передавалася за значенням і надавала сумісний з `std::string` read-only інтерфейс.

Проте відсутність єдиного стандарту спричиняла фрагментацію екосистеми: бібліотека від Google вимагала `StringPiece`, бібліотека LLVM очікувала `StringRef`, а стандартні функції C++ вимагали `const std::string&`. Розробники змушені були писати перехідники та конвертори між різними типами поглядів.

## Стандартизація в C++17: народження std::string_view

Бачачи фрагментацію екосистеми та успіх `Boost.StringRef`, розробники Джеффрі Їлкін (Jeffrey Yasskin) та Маршалл Клов (Marshall Clow) подали пропозицію до Комітету C++ (папери N3685 та N3921).

Після тривалих дискусій у робочих групах Library Working Group (LWG) та обкатки у специфікації `Library Fundamentals TS` (`std::experimental::string_view`), клас було офіційно включено до стандарту **C++17** під ім'ям `std::basic_string_view`.

Стандартизація `std::string_view` принесла в C++ тріаду текстових типів:

1. `const char*` — C-сумісний нуль-термінований масив (мінімальні гарантії, без знання розміру).
2. `std::string` — засіб володіння та модифікації динамічного тексту (RAII, безпека, але ціна алокацій).
3. `std::string_view` — універсальний безволодісний інструмент спостереження та аналізу (O(1) передача, O(1) substr, нульові алокації).

Еволюцію C++ рядків підсумовує хронологічна веха: від небезпеки повернення вказівників у C до створення нуль-алокаційних поглядів у сучасному C++.

У C++20 та C++23 розробка текстових типів продовжилася впровадженням модулів `std::format`, `constexpr std::string` та діапазонів `std::ranges`, де `std::string_view` виступає як базовий елемент текстових абстракцій мови.
