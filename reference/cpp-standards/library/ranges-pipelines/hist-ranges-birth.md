# 📜 Історія Ranges: від палуби STL Олександра Степанова до ISO C++20

Тридцятирічна еволюція абстракцій обробки послідовностей у мові C++ пройшла шлях від початкового відкриття ітераторних пар Олександром Степановичем Степановим у 1990-х роках через експерименти бібліотеки Boost.Range та фундаментальну революцію Range-v3 Еріка Ніблера до остаточної стандартизації конвеєрів діапазонів у стандартах ISO C++20 та ISO C++23. Механізм обробки даних розвинувся від імперативного управління парами вказівників до декларативної композиції лінивих виглядів через оператор конвеєра `|`.

## 1. Спадщина 1994 року: Елегантність та обмеження ітераторних пар STL

У 1993–1994 роках Олександр Степанов (Alexander Stepanov) разом із Менг Лі (Meng Lee) в лабораторіях Hewlett-Packard розробили Standard Template Library (STL). Фундаментальною ідеєю Степанова було розділення контейнерів (структур збереження даних) та алгоритмів (процедур обробки) через узагальнену проміжну абстракцію — ітератор (англ. *iterator*, від латинського *iterare* — повторювати).

Ітератор імітував поведінку звичайного вказівника мови C. Алгоритм не знав, де саме лежать дані — у безперервному масиві, зв'язаному списку чи збалансованому дереві. Все, що вимагалося від алгоритму, — це оперувати парою ітераторів `[first, last)`, де `first` вказував на перший елемент послідовності, а `last` слугував напіввідкритою межею (англ. *half-open range*), яка показувала кінець послідовності, але не посилалася на реальний об'єкт.

Схема `[first, last)` виявилася неймовірно успішною та революційною для свого часу. Вона дозволила реалізувати `O(N)` алгоритмів над `O(M)` контейнерами з використанням лише `O(N + M)` коду замість `O(N · M)`. Проте з появою складніших систем виявилися фундаментальні архітектурні обмеження концепції пар ітераторів:

1. **Багатослівність та дублювання синтаксису.** Будь-який виклик алгоритму вимагав дворазового передавання імені контейнера: `std::sort(vec.begin(), vec.end())`. При передаванні укладених виразів синтаксис ставав громіздким та важкочитаним.
2. **Ризик неузгоджених пар (Mismatched Iterators).** Передача `std::sort(vec1.begin(), vec2.end())` була синтаксично коректним кодом C++, але призводила до невизначеної поведінки (undefined behavior) та краху програми у рантаймі.
3. **Жадібність та неможливість прямої композиції.** Виклики алгоритмів не складали елегантних ланцюжків. Щоб відфільтрувати вектор і потім піднести його елементи до квадрата, програміст мусив або виділяти тимчасові проміжні контейнери `std::vector`, або писати ручні цикли `for`, руйнуючи концепцію узагальненого програмування.

## 2. Перші спроби композиції: Boost.Range (2003–2009)

Зі зростанням популярності C++98 спільнота прагнула обгортати пари ітераторів у єдиний об'єкт. У 2003–2005 роках Ніл Ґровс (Neil Groves) та Торстен Оттосен (Thorsten Ottosen) розробили бібліотеку **Boost.Range**.

Головною інновацією Boost.Range стало введення концепції `Single Pass Range` та перевантаження базових алгоритмів: `boost::sort(vec)` замість `boost::sort(vec.begin(), vec.end())`. Бібліотека пропонувала перші адаптери діапазонів, такі як `boost::adaptors::filtered` та `boost::adaptors::transformed`. Програмісти вперше отримали можливість застосовувати оператор `|` для поєднання операцій:

```cpp
// Ранній синтаксис Boost.Range (середина 2000-х років)
using namespace boost::adaptors;
for (int x : vec | filtered(is_even) | transformed(square)) {
    // Обробка елементів
}
```

Проте Boost.Range мала суттєві обмеження:
- Вона спиралася на шаблони C++03 без підтримки семантики переміщення (move semantics) та виведення типів `auto`.
- Відсутність концептів (Concepts) у мові призводила до гігантських та нечитабельних помилок компіляції при найменшій помилці в типах.
- Концепція кінечного ітератора вимагала, щоб тип кінця послідовності `last` був строго ідентичний типу початку `first`. Це унеможливлювало роботу з нескінченними послідовностями або рядками з нульовим термінатором (`null-terminated strings`) без попереднього обчислення довжини.

## 3. Революція Range-v3 та концепція Sentinel Еріка Ніблера (2013–2019)

У 2013 році комитет стандартизації ISO C++ розпочав активне проєктування майбутнього C++17 та C++20. Розробник **Ерік Ніблер (Eric Niebler)** запропонував фундаментальний перегляд підходів Степанова у своїй практичній бібліотеці **Range-v3**.

Ніблер сформулював три ключові ідеї, які лягли в основу сучасного ISO C++ Ranges:

### Ідея 1: Розділення типу ітератора та вартівника (Sentinel)
У класичному STL діапазони вимагали однакового типу для початку та кінця: `Iterator first, Iterator last`. Ніблер довів, що для зупинки циклу кінцевому об'єкту непотрібно бути ітератором! Йому достатньо бути **вартівником (Sentinel)** — об'єктом типу `Sentinel`, для якого визначено оператор порівняння з ітератором: `it != sentinel`.

Це відкрило шлях до:
- **Нескінченних послідовностей**: вартівник `std::unreachable_sentinel` завжди повертає `false` при порівнянні `it != sentinel`, дозволяючи генерувати нескінченні числа `views::iota(0)`.
- **Лінивих лексичних вартівників**: для рядка C-style `const char* str` вартівник перевіряє `*it == '\0'`, не роблячи попереднього проходу `strlen()` для пошуку кінця.

### Ідея 2: Концепція View (Вигляд) та неволодіюча семантика
Ніблер чітко розмежував дві категорії діапазонів:
- **Range (Контейнер/Діапазон):** володіє елементами (наприклад, `std::vector`, `std::string`). Копіювання контейнера виконує глибоке копіювання пам'яті за `O(N)`.
- **View (Вигляд):** легка неволодіюча обгортка над діапазоном, копіювання, переміщення та знищення якої завжди виконуються за сталий час `O(1)`.

### Ідея 3: Каррування та Замикання адаптерів (Range Adaptor Closure Objects)
Ніблер впровадив механізм часткового застосування функцій (каррування) для операцій над діапазонами. Вираз `views::filter(pred)` не виконує фільтрацію негайно. Він повертає спеціальний об'єкт замикання (closure object), який перевантажує `operator|`. Коли до цього замикання зліва застосовується діапазон `r`, вираз `r | views::filter(pred)` обчислює `views::filter(r, pred)`, повертаючи новий обгортаючий `View`.

## 4. Драматичні дискусії в комітеті: проксі-ітератори, vector<bool> та borrowed_range

Шлях Ranges TS до стандартного C++20 виявився насиченим гострими архітектурними дискусіями у комітеті WG21, оскільки нова модель зачіпала самі основи теорії ітераторів Степанова.

### Проблема проксі-ітераторів та `std::vector<bool>`
У класичному C++98 вимагалося, щоб поверчуваний тип `operator*()` для `ForwardIterator` був справжнім посиланням `T&`. Це створило відому заувагу з `std::vector<bool>`, де `operator*()` повертає тимчасовий об'єкт-проксі `std::vector<bool>::reference`, через що `std::vector<bool>` не відповідав вимогам справжнього контейнера C++ STL!

При розробці `std::ranges` Ерік Ніблер та Ендрю Саттон (Andrew Sutton) повністю переписали ієрархію концептів ітераторів. Вони ввели поняття `std::indirectly_readable` та відокремили тип посилання `iter_reference_t<I>` від типу значення `iter_value_t<I>`. Модель C++20 Ranges офіційно дозволила ітераторам повертати проксі-значення через операції `iter_move` та `iter_swap`. Це дало змогу бездоганно інтегрувати проксі-контейнери, трансформуючі вигляди `views::transform` та стиснуті бітові послідовності у загальний конвеєр.

### Проблема «висячих» посилань та `std::ranges::dangling`
Найсерйознішою небезпекою неволодіючих виглядів була робота з тимчасовими об'єктами (rvalues). Розглянемо код:
```cpp
auto get_temp_vector() { return std::vector{1, 2, 3, 4}; }
auto it = std::ranges::find(get_temp_vector(), 3);
// Якщо it збереже ітератор на знищений vector, розіменування призведе до краху!
```
Щоб запобігти цій катастрофі, комітет впровадив концепт `std::ranges::borrowed_range`. Контейнери, які володіють своєю пам'яттю (як-от `std::vector`), НЕ є `borrowed_range`. Якщо алгоритм повертає ітератор із тимчасового контейнера, що не є `borrowed_range`, C++20 повертає спеціальний маркерний тип `std::ranges::dangling`. Спроба розіменувати `std::ranges::dangling` викликає помилку компіляції ще на етапі збирання проєкту, унеможливлюючи витоки висячих вказівників.

## 5. Шлях до стандарту ISO: від Ranges TS до C++20 та C++23

У 2014 році комитет ISO затвердив створення технічної специфікації Ranges TS (N4128). Розробка тривала понад 5 років і вимагала паралельного впровадження мовної фічі **Concepts (Концепти)** у C++20. Без концептів `std::ranges::range`, `std::ranges::view` та `std::input_iterator` реалізація перевантажень оператора `|` була б схильна до неоднозначностей під час інстанціювання шаблонів.

У 2019 році пропозиція P0896R4 (*The One Ranges Proposal*) була офіційно прийнята до складу стандарту **ISO C++20**. Стандарт отримав простір імен `std::ranges` для алгоритмів та `std::views` (аліас для `std::ranges::views`) для адаптерів конвеєра.

Еволюція не зупинилася на C++20. У той час як C++20 надав фундаментальну базу (`filter`, `transform`, `take`, `drop`, `join`, `split`), стандарт **C++23** значно розширив набір адаптерів діапазонів завдяки пропозиціям Еріка Ніблера, Баррі Ревізіна (Barry Revzin) та Тіма Сонга (Tim Song):
- **P2164R9 (`views::enumerate`):** додавання індексу до кожного елемента послідовності.
- **P2374R4 (`views::cartesian_product`):** декартів добуток довільної кількості діапазонів.
- **P2432R1 (`views::chunk`) та P2433R1 (`views::slide`):** розбиття на блоки та ковзні вікна.
- **P2441R2 (`views::repeat`):** безкінечне повторення елемента або значення.
- **P2281R1 (`std::ranges::to`):** пряме матеріалізування лінивих конвеєрів у контейнери (`std::vector`, `std::unordered_map`).

Завдяки тридцятирічному розвитку абстракції C++ пройшли шлях від ручних вказівників C до високоефективних, безпечних відносно типів та лінивих конвеєрів обробки даних із нульовою вартістю абстракції (zero-cost abstractions).
