# 📋 Інтерфейс та специфікація стандартних адаптерів діапазонів (C++20/C++23)

Цей довідник містить повну технічну специфікацію концептів діапазонів, стандартних адаптерів виглядів (Range Adaptors) у просторі імен `std::views` мов C++20 та C++23, детальний аналіз вимог до типів, збереження категорій ітераторів, складність обчислень, специфіку кешування та синтаксис об'єктів замикання адаптерів.

## 1. Фундаментальні концепти діапазонів у `std::ranges`

Для забезпечення безпеки типів під час компіляції мова C++20 вводить вбудовану систему концептів у заголовковому файлі `<ranges>`. На відміну від класичного STL C++98, де помилки невідповідності типів ітераторів виникали глибинно в надрах шаблонів і призводили до багатометрових повідомлень промислових компіляторів, концепти перевіряють анатомію типів ще на етапі оцінки виклику.

### Деталізація концептів діапазонів

1. **`std::ranges::range<T>`** — базовий концепт фундаментального рівня. Клас або тип `T` задовольняє `range`, якщо для його об'єктів визначено вирази `std::ranges::begin(t)` та `std::ranges::end(t)`. Важливо зауважити, що `ranges::begin` та `ranges::end` не є просто викликами методів `.begin()` та `.end()`. Це спеціальні Customization Point Objects (CPO), які послідовно шукають:
   - Методи класу `t.begin()` / `t.end()`.
   - Вільні функції `begin(t)` / `end(t)` через механізм ADL (Argument Dependent Lookup).
   - Фізичні межі масиву для сирих масивів C (`T[N]`).

2. **`std::ranges::borrowed_range<T>`** — спеціальний концепт, що вирішує проблему «висячих» посилань. Він гарантує, що ітератори, отримані з об'єкта типу `T`, зберігають свою дійсність (validity) навіть після того, як самий об'єкт `T` припинив свій час життя (був знищений у стеку). Концепт виконується для:
   - Всіх lvalue-посилань (`T&`).
   - Типів виглядів, які не володіють даними (`std::string_view`, `std::span`).
   - Спеціалізованих виглядів `std::ranges::ref_view<R>`.

3. **`std::ranges::sized_range<T>`** — концепт, що вимагає виконання виразу `std::ranges::size(t)` за сталий час `O(1)`. Якщо для контейнера `T` обчислення кількості елементів вимагає лінійного проходу `O(N)` (як для `std::forward_list`), такий контейнер НЕ є `sized_range`.

4. **`std::ranges::view<T>`** — формальний концепт для виглядів. Вимагає виконання `range<T>`, мобільності `std::movable<T>`, а також гарантії того, що конструктор копіювання, конструктор переміщення, оператори присвоєння та деструктор мають часову складність `O(1)`. Об'єкт типу `view` не повинен володіти елементами монопольно.

5. **`std::ranges::viewable_range<T>`** — концепт, який використовується адаптерами для перевірки того, чи можна передати даний діапазон у конвеєр pipe. Перевірка повертає `true`, якщо:
   - Тип `T` вже є `view` (`std::ranges::view<remove_cvref_t<T>>`).
   - Тип `T` передано за lvalue-посиланням (`T&` є `range`).
   - Тип `T` передано за rvalue-посиланням, і при цьому `T` є `borrowed_range`.

6. **`std::ranges::common_range<T>`** — концепт, який вимагає, щоб тип ітератора початку `iterator_t<T>` та тип вартівника кінця `sentinel_t<T>` були строго ідентичними. Багато класичних алгоритмів STL C++98 вимагають саме `common_range`. Перетворити довільний діапазон з вартівником на `common_range` дозволяє адаптер `std::views::common`.

### Категорії ітераторів діапазонів та правила успадкування
Категорія ітератора результуючого вигляду визначається за принципом найслабшої ланки між можливостями базового діапазону `R` та внутрішніми обмеженнями самого адаптера. Наприклад, якщо базовий контейнер `std::vector` надає `random_access_range`, але ви застосовуєте `std::views::filter`, підсумковий вигляд втрачає доступ за індексом `operator[]` і стає лише `bidirectional_range`, оскільки неможливо вирахувати точну зміщення елемента після фільтрації за `O(1)`.

Стандарт C++20 визначає наступну ієрархію концептів ітераторів:
- `std::ranges::input_range` — однопрохідний доступ на читання (наприклад, потік `std::cin`).
- `std::ranges::output_range` — однопрохідний доступ на запис.
- `std::ranges::forward_range` — багатопрохідний доступ (ітератори можна повторно розіменовувати та копіювати, наприклад `std::forward_list`).
- `std::ranges::bidirectional_range` — підтримка зворотного ходу `operator--()` (наприклад `std::list`).
- `std::ranges::random_access_range` — доступ за довільним індексом `operator[]` та арифметика ітераторів `it + n` за `O(1)` (наприклад `std::deque`).
- `std::ranges::contiguous_range` — гарантія фізичної безперервності елементів у пам'яті (наприклад `std::vector`, `std::array`, `std::span`).

## 2. Повний реєстр стандартних адаптерів `std::views`

Усі адаптери розділено за категоріями функціонального призначення. Позначення у таблицях:
- `R` — вхідний діапазон (`range`).
- `V` — результуючий вигляд (`view`).
- `Cat(R)` — категорія ітератора вхідного діапазону `R`.
- `Cat(V)` — підсумкова категорія ітератора вигляду `V`.

## 3. Детальний аналіз алгоритмів складності та кешування

Різні типи виглядів володіють різною асимптотичною складністю та особливостями поведінки під час виконання першого проходу.

### Механіка `cached_begin` та розіменування
Для адаптерів `filter_view`, `drop_view`, `join_view` та `split_view` операція знаходження першого елемента не є `O(1)`. Розглянемо детально, що відбувається всередині `std::ranges::filter_view::begin()`:

1. Метод перевіряє optional-поле `cached_begin_`.
2. Якщо значення відсутнє, запускається внутрішній алгоритм `std::ranges::find_if(base_, std::ref(pred_))`.
3. У найгіршому випадку (якщо жоден елемент не задовольняє предикат або шуканий елемент знаходиться в кінці) виклик `begin()` проходить весь масив розміром `N` за час `O(N)`.
4. Знайдена позиція ітератора зберігається у `cached_begin_`.
5. Подальші виклики `begin()` відразу повертають збережений ітератор за `O(1)`.

Внаслідок цього мутаційного кешування об'єкти виглядів з `cached_begin_` втрачають можливість викликати метод `begin()` для константних екземплярів `const view`. 

Якщо вам необхідно ітерувати `const filter_view`, використовуйте вигляд `std::ranges::ref_view` або передавайте сам вигляд за значенням у дочірні функції, оскільки копіювання будь-якого вигляду за стандартом є дешевою операцією `O(1)`.

### Поведінка складних адаптерів C++23 (`zip`, `cartesian_product`, `join_with`)

- **`std::views::zip`**: Поєднує кілька діапазонів. Його ітератор зберігає кортеж базових ітераторів `std::tuple<iterator_t<Views>...>`. При виконанні `operator++()` інкремент застосовується до кожного ітератора у кортежі. Розмір `zip` визначається мінімальним розміром серед усіх вхідних `sized_range`.
- **`std::views::cartesian_product`**: Реалізує вкладені цикли за допомогою єдиної плоскої абстракції ітератора. Ітератор зберігає поточні індекси/ітератори для кожного з `N` діапазонів. Коли внутрішній ітератор досягає вартівника `end()`, він скидається у `begin()`, а попередній (зовнішній) ітератор інкрементується. Часова складність повного обходу дорівнює `O(N₁ · N₂ · ... · Nₖ)`.
- **`std::views::join_with`**: Дозволяє об'єднувати послідовності рядків чи діапазонів через роздільник (наприклад, об'єднання `std::vector<std::string>` через кому `", "`). Ітератор всередині переключає свій стан між читанням з поточного елемента-послідовності та читанням з діапазону-роздільника.

## 4. Синтаксис замикань, каррування та `std::ranges::range_adaptor_closure`

Стандарт C++23 офіційно затвердив механізм для створення власних адаптерів виглядів через базовий клас `std::ranges::range_adaptor_closure`.

### Шаблонний механізм обгортання замикань

Об'єкт замикання адаптера — це функтор, який зв'язує аргументи адаптера (наприклад предикат для `filter` або кількість для `take`) і чекає на передачу самого діапазону.

```cpp
// Концептуальна реалізація базового класу C++23 range_adaptor_closure:
namespace std::ranges {

template <typename D>
struct range_adaptor_closure {
    // Оператор pipe для зв'язування: range | closure
    template <range R>
    requires can_apply<D, R>
    [[nodiscard]] constexpr auto operator|(R&& r, const D& self) const {
        return self(std::forward<R>(r));
    }

    // Оператор pipe для композиції двох замикань: closure1 | closure2
    template <typename C2>
    [[nodiscard]] constexpr auto operator|(const D& self, const C2& c2) const {
        return views::pipeline(self, c2);
    }
};

} // namespace std::ranges
```

Завдяки цьому механізму будь-яка лямбда або структурований функтор, успадкований від `range_adaptor_closure`, бездоганно інтегрується в ланцюжки `operator|` разом зі стандартними адаптерами `std::views`.

## 3. Оцінка кешування та const-коректності у виглядах

Особливою архітектурною рисою стандартних адаптерів C++20 є специфіка їхньої const-коректності, яка випливає з необхідності зберігати або кешувати внутрішній стан ітератора.

### Проблема кешування першого елемента (`cached_begin`)
Для адаптерів, таких як `std::ranges::filter_view`, `std::ranges::drop_view`, `std::ranges::join_view` та `std::ranges::split_view`, обчислення позиції першого елемента не є операцією зі сталим часом `O(1)`. Наприклад, для `filter_view` предикат повинен послідовно перевіряти елементи базового діапазону від `begin()` доти, доки не знайде перший елемент, що відповідає умові.

Щоб уникнути повторного виконання проходу `O(N)` при кожному наступному виклику `begin()`, реалізація адаптера мусить зберегти (закешувати) знайдений ітератор всередині об'єкта вигляду. Проте запис у кеш вимагає мутації внутрішніх полів об'єкта!

З цієї причини метода `begin()` для таких виглядів не може бути оголошено як `const`:
```cpp
// filter_view містить модифікований кеш, тому begin() є non-const:
constexpr auto begin() requires (!simple_view<V>) {
    if (!cached_begin_.has_value()) {
        cached_begin_ = std::ranges::find_if(base_, std::ref(pred_));
    }
    return iterator{this, *cached_begin_};
}
```

Якщо об'єкт `filter_view` передати за константним посиланням `const auto&`, спроба викликати `std::ranges::begin(v)` або ітерувати його у циклі `for (auto x : const_view)` спричинить помилку компіляції, якщо тільки вхідний вигляд не є `simple_view` (тобто коли константний і неконстантний ітератори збігаються і кешування не потрібне).

## 4. Синтаксис замикань та оператора `|`

Адаптери виглядів можуть використовуватися у двох еквівалентних формах:

1. **Функціональна форма (прямий виклик конструктора):**
   ```cpp
   std::ranges::transform_view v2(std::ranges::filter_view(vec, pred), func);
   ```

2. **Форма конвеєра (Pipe syntax):**
   ```cpp
   auto v2 = vec | std::views::filter(pred) | std::views::transform(func);
   ```

### Механізм `std::ranges::range_adaptor_closure` (C++23)
У C++23 було стандартизовано базовий клас для створення власних об'єктів замикання. Якщо тип `Closure` успадковує `std::ranges::range_adaptor_closure<Closure>`, компілятор автоматично згенерує перевантаження `operator|`:

```cpp
template <typename Range, typename Closure>
requires std::ranges::range_adaptor_closure<Closure> &&
         std::ranges::range<std::remove_cvref_t<Range>>
constexpr decltype(auto) operator|(Range&& r, Closure&& c) {
    return std::forward<Closure>(c)(std::forward<Range>(r));
}
```

Також підтримується композиція самих об'єктів замикання без вхідного діапазону:
```cpp
// Створення нового об'єднаного адаптера через pipe:
auto filter_and_square = std::views::filter(is_even) | std::views::transform(square);

// Застосування до контейнера:
auto result = vec | filter_and_square;
```
