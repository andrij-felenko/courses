# ⚙️ Проєкт: Нуль-копіювальний бінарний парсер мережевих пакетів

У системному та мережевому програмуванні розбір пакетів даних (наприклад, заголовків мережевих протоколів Ethernet, IP, TCP або бінарних кадрів серіалізації) вимагає високої швидкодії. Традиційний підхід із виділенням тимчасових буферів у купі або копіюванням байтів у окремі структури створює величезні накладні витрати на процес алокації та копіювання пам'яті.

У цьому проєкті ми побудуємо нуль-копіювальний (англ. *zero-copy*) декодер бінарного мережевого кадру, який аналізує вхідний сирий буфер байтів без єдиного копіювання чи виділення пам'яті, порівнюючи низькорівневий підхід мовою C із сучасним підходом C++20 на основі `std::span`.

## Архітектура та бінарна специфікація кадру

Мережевий кадр має чітку бінарну специфікацію розміщення полів у пам'яті. Заголовки мережевих протоколів традиційно передаються у мережевому порядку байтів (англ. *network byte order*, big-endian), що вимагає перетворення байтів на архітектурах із малоендіанним порядком (little-endian, таких як x86-64 та ARM64).

Кадр складається з трьох послідовних бінарних секцій:

1. **Заголовок кадру (Frame Header, фіксовано 8 байтів)**:
   - `uint16_t magic` — магічне число кадру `0x4850` (символи "HP");
   - `uint8_t  version` — версія протоколу (очікується `1`);
   - `uint8_t  flags` — системні прапорці кадру;
   - `uint32_t payload_len` — оголошена довжина корисного навантаження у байтах (big-endian).
2. **Корисне навантаження (Payload, динамічна довжина N байтів)**:
   - Довільний суцільний бінарний буфер даних, що слідує безпосередньо за заголовком.
3. **Контрольна сума кадру (Trailer, фіксовано 4 байти)**:
   - `uint32_t crc32` — контрольна сума кадру для перевірки цілісності даних.

Головна проблема при розборі таких пакетів у системному програмуванні — гарантувати, що зміщення вказівників не вийдуть за межі виділеного сокетного буфера, а також забезпечити захист від невирівняного доступу до пам'яті (англ. *unaligned memory access*).

На багатьох архітектурах (наприклад, ARMv7 або деяких DSP-процесорах) спроба розіменувати 32-бітний вказівник `uint32_t*`, розташований за непарною адресою, призводить до апаратного виключення процесора (англ. *alignment fault*). Тому безпечне розпакування бінарних полів вимагає використання `std::memcpy` або байтових зрізів, що оптимізуються компілятором у ефективні інструкції читання.

## Порівняльна реалізація розбору кадру

Нижче наведено дві повноцінні, ідіоматичні реалізації розбору бінарного кадру: у стилі класичного C (із сирими вказівниками та лічильниками байтів) та у стилі сучасного C++20 (із використанням `std::span`, `subspan` та байтових зрізів `std::byte`).

```c
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define FRAME_MAGIC 0x4850
#define HEADER_SIZE 8
#define TRAILER_SIZE 4

typedef struct {
    uint16_t magic;
    uint8_t  version;
    uint8_t  flags;
    uint32_t payload_len;
} FrameHeaderC;

typedef struct {
    FrameHeaderC header;
    const uint8_t* payload_ptr;
    size_t payload_len;
    uint32_t crc32;
} ParsedFrameC;

// Допоміжна функція перетворення endianness (network to host)
static uint32_t ntohl_custom(uint32_t val) {
    return ((val & 0xFF000000) >> 24) |
           ((val & 0x00FF0000) >> 8)  |
           ((val & 0x0000FF00) << 8)  |
           ((val & 0x000000FF) << 24);
}

static uint16_t ntohs_custom(uint16_t val) {
    return (uint16_t)((val >> 8) | (val << 8));
}

// Парсер у стилі C: вимагає сирого вказівника та розрахунку зміщень
bool parse_frame_c(const uint8_t* buffer, size_t buffer_len, ParsedFrameC* out_frame) {
    if (buffer == NULL || out_frame == NULL) {
        return false;
    }

    // 1. Перевірка мінімального розміру для заголовка та трейлера
    if (buffer_len < HEADER_SIZE + TRAILER_SIZE) {
        return false;
    }

    // 2. Безпечне зчитування заголовка через memcpy (уникнення unaligned access)
    FrameHeaderC hdr;
    memcpy(&hdr, buffer, sizeof(FrameHeaderC));
    hdr.magic = ntohs_custom(hdr.magic);
    hdr.payload_len = ntohl_custom(hdr.payload_len);

    if (hdr.magic != FRAME_MAGIC || hdr.version != 1) {
        return false;
    }

    // 3. Перевірка чи достатньо байтів у буфері для оголошеного payload_len
    size_t total_expected = HEADER_SIZE + hdr.payload_len + TRAILER_SIZE;
    if (buffer_len < total_expected) {
        return false;
    }

    // 4. Виділення вказівника на payload упевнившись у межах
    out_frame->header = hdr;
    out_frame->payload_ptr = buffer + HEADER_SIZE;
    out_frame->payload_len = hdr.payload_len;

    // 5. Зчитування контрольної суми
    const uint8_t* trailer_ptr = buffer + HEADER_SIZE + hdr.payload_len;
    uint32_t raw_crc;
    memcpy(&raw_crc, trailer_ptr, sizeof(uint32_t));
    out_frame->crc32 = ntohl_custom(raw_crc);

    return true;
}
```
```cpp
#include <span>
#include <cstdint>
#include <bit>
#include <optional>
#include <cstring>

constexpr uint16_t FRAME_MAGIC = 0x4850;
constexpr std::size_t HEADER_SIZE = 8;
constexpr std::size_t TRAILER_SIZE = 4;

struct FrameHeader {
    uint16_t magic;
    uint8_t  version;
    uint8_t  flags;
    uint32_t payload_len;
};

struct ParsedFrame {
    FrameHeader header;
    std::span<const std::byte> payload; // Безволодісний зріз корисного навантаження
    uint32_t crc32;
};

// Ідіоматичний парсер C++20: нуль-копіювання через std::span
std::optional<ParsedFrame> parse_frame_cpp(std::span<const std::byte> buffer) noexcept {
    // 1. Перевірка мінімальної довжини для заголовка та контрольної суми
    if (buffer.size() < HEADER_SIZE + TRAILER_SIZE) {
        return std::nullopt;
    }

    // 2. Вирізаємо статичний зріз заголовка 8 байтів за O(1)
    auto header_bytes = buffer.first<HEADER_SIZE>();
    
    FrameHeader hdr;
    std::memcpy(&hdr, header_bytes.data(), sizeof(FrameHeader));
    
    // Свап байтів для мережевого порядку (big-endian)
    if constexpr (std::endian::native == std::endian::little) {
        hdr.magic = std::byteswap(hdr.magic);
        hdr.payload_len = std::byteswap(hdr.payload_len);
    }

    if (hdr.magic != FRAME_MAGIC || hdr.version != 1) {
        return std::nullopt;
    }

    // 3. Перевірка загального розміру пакета
    const std::size_t total_expected = HEADER_SIZE + hdr.payload_len + TRAILER_SIZE;
    if (buffer.size() < total_expected) {
        return std::nullopt;
    }

    // 4. Відокремлюємо payload та trailer за допомогою subspan
    std::span<const std::byte> payload_span = buffer.subspan(HEADER_SIZE, hdr.payload_len);
    std::span<const std::byte> trailer_span = buffer.subspan(HEADER_SIZE + hdr.payload_len, TRAILER_SIZE);

    uint32_t raw_crc;
    std::memcpy(&raw_crc, trailer_span.data(), sizeof(uint32_t));
    if constexpr (std::endian::native == std::endian::little) {
        raw_crc = std::byteswap(raw_crc);
    }

    return ParsedFrame{
        .header = hdr,
        .payload = payload_span,
        .crc32 = raw_crc
    };
}
```

## Покроковий морфологічний розбір двох підходів

Щоб глибше зрозуміти різницю між традиційним програмуванням мовою C та сучасним C++20, розберемо виконання кожного кроку розбору детально.

### Крок 1: Вхідна перевірка та передача буфера

У реалізації мовою C функція розбору `parse_frame_c` приймає два окремих параметри: сирий вказівник `const uint8_t* buffer` та числове значення `size_t buffer_len`. На самому початку функція змушена виконати перевірку вказівника на `NULL`. Якщо викликач помилково передасть вказівник `buffer` з масиву `A`, а значення `buffer_len` з масиву `B`, розробник C-функції не має жодного механізму виявити цю помилку до моменту псування пам'яті.

У реалізації C++20 функція `parse_frame_cpp` приймає єдиний аргумент `std::span<const std::byte> buffer`. Оскільки `std::span` є єдиним об'єктом, що об'єднує адресовий вказівник `data()` та кількість елементів `size()`, можливість передачі розсинхронізованих аргументів виключається ще на етапі створення зрізу. Перевірка на `NULL` не потрібна, оскільки порожній `std::span` просто має `size() == 0` та `data() == nullptr`, що безпечно обробляється викликом `buffer.size() < HEADER_SIZE + TRAILER_SIZE`.

### Крок 2: Декодування заголовка та небезпека Strict Aliasing

Для зчитування полів заголовка C-програмісти часто намагаються приводити сирий вказівник безпосередньо до типу структури: `const FrameHeaderC* hdr = (const FrameHeaderC*)buffer`. Проте це створює дві критичні небезпеки:
1. **Порушення Strict Aliasing**: Компілятор розглядає вказівник на `uint8_t` та вказівник на `FrameHeaderC` як несумісні типи. Оптимізатор GCC чи Clang може перевпорядкувати операції запису у буфер та читання зі структури, спричинивши важкодоступні баги при оптимізації `-O3`.
2. **Невирівняний доступ (Unaligned Access)**: Якщо буфер байтів розташований за адресою `0x1001`, розіменування `hdr->payload_len` змусить процесор прочитати 32-бітне число з непарної адреси. На багатьох RISC-архітектурах це викликає апаратне виключення (Hardware Trap).

Обидві реалізації у нашому проєкті розв'язують цю проблему через `memcpy` / `std::memcpy`. Оскільки `memcpy` має спеціальний статус у стандартах C та C++, компілятор розглядає копіювання байтів як безпечний доступ до сирої пам'яті і оптимізує його у поодинокі інструкції читання без реального виклику функції.

### Крок 3: Перевірка переповнення розміру (Integer Overflow)

Критичним крайовим випадком при обробці мережевих даних є захист від шкідливо згенерованого поля `payload_len`. Якщо зловмисник надішле кадр, у якому `hdr.payload_len` дорівнює `0xFFFFFFFF` (тобто `SIZE_MAX`), додавання `HEADER_SIZE + hdr.payload_len + TRAILER_SIZE` у 32-бітній арифметиці переповниться (integer wrap-around) і дасть маленьке число. В результаті перевірка `buffer_len < total_expected` буде пройдена, але подальша робота з буфером призведе до виходу за межі пам'яті.

Для запобігання цьому у 64-бітних системах обчислення `total_expected` виконується у 64-бітному типі `std::size_t`, де `0xFFFFFFFF` не спричиняє переповнення. Додатково функція `subspan` у C++20 генерує асерти налагодження при спробі вирізати зріз, що виходить за межі вихідного `buffer.size()`.

### Крок 4: Забезпечення нерозривності часу життя (Lifetime Bounds)

Результат роботи C++20 парсера — структура `ParsedFrame`, яка містить поле `std::span<const std::byte> payload`. Оскільки `payload` є безволодісним зрізом, його створення не вимагає виділення динамічної пам'яті у купі (`malloc`/`new`).

Проте розробник, який викликає `parse_frame_cpp`, має пам'ятати про правила часу життя: вказівник всередині `payload` залишається валидним лише доти, доки існує вхідний мережевий буфер `buffer`. Якщо вхідний буфер перебуває у тимчасовій пам'яті сокета і знищується після обробки, поле `payload` має бути оброблено негайно або скопійовано у володіючий контейнер `std::vector<std::byte>`.

## Глибокий аналіз безпеки та продуктивності

Порівняння двох підходів розкриває фундаментальні переваги використання `std::span` у системних архітектурах високого навантаження.

### 1. Запобігання помилкам арифметики вказівників

У реалізації мовою C розробник змушений вручну обчислювати адреси зміщення: `buffer + HEADER_SIZE` та `buffer + HEADER_SIZE + hdr.payload_len`. Навіть незначна помилка у знаку або порядок додавання змінних призводить до виходу за межі пам'яті. 

Натомість у реалізації C++20 метод `buffer.subspan(HEADER_SIZE, hdr.payload_len)` самостійно виконує перевірки та повертає новий об'єкт `std::span`. Вказівник `data()` та розмір `size()` нового зрізу коригуються атомарно в одному конструкторі, що робить розсинхронізацію адреси та довжини фізично неможливою.

### 2. Захист від помилок інвалідації через std::optional

Функція розбору мовою C повертає прапорець `bool` і приймає вихідний вказівник `out_frame`. Якщо викликач забуде перевірити повернуте значення `false` і продовжить читати `out_frame`, він звернеться до несміттєвих даних або нульових вказівників.

У C++20 функція повертає `std::optional<ParsedFrame>`. Якщо аналіз пакета провалюється (наприклад, через невірне магічне число чи недостатню довжину буфера), функція повертає `std::nullopt`. Спроба дістати значення з порожнього `std::optional` без перевірки гарантовано викликає асерт або виняток, захищаючи програму від невизначеної поведінки.

### 3. Оптимізація компілятором та відсутність накладних витрат

Сгенерований машинний код для обидвох функцій при оптимізації `-O2` або `-O3` є практично ідентичним. Виклики `buffer.first<HEADER_SIZE>()` повністю інлайняться компілятором. Компілятори GCC та Clang розпізнають шаблон `std::memcpy` і замінюють його на поодинокі інструкції завантаження регістрів `mov` (на x86-64) або `ldr` (на ARM), усуваючи реальний виклик функції `memcpy`.

Використання `std::endian::native` та `std::byteswap` (C++23) дозволяє компілятору згенерувати одну інструкцію `bswap` для розпакування мережевого порядку байтів без виклику застарілих макросів `ntohl`/`ntohs`.

### 4. Вплив на кеш-пам'ять та векторизацію (SIMD)

Оскільки `std::span` зберігає корисне навантаження у вигляді суцільного зрізу `std::span<const std::byte>`, подальша обробка корисного навантаження (наприклад, розрахунок CRC32 або векторизоване декодування протоколу Protobuf/FlatBuffers) виконується максимально ефективно.

Процесор завантажує дані з оперативної пам'яті у кеш L1/L2 цілими кеш-лініями по 64 байти. Оскільки `std::span` гарантує суцільне розташування елементів, апаратний предвибірник процесора (англ. *hardware prefetcher*) автоматично виявляє лінійний паттерн читання і завчасно завантажує наступні кеш-лінії, що запобігає затримкам промахів кешу (англ. *cache misses*).
