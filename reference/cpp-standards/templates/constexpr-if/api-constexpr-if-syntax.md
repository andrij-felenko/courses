# 📋 Специфікація та правила відкидання гілок if constexpr

У цьому довіднику наведено повну формальну граматику, семантичні інваріанти стандарту ISO C++ та специфікацію поведінки інструкції `if constexpr`.

## Формальна граматика стандарту ISO C++

У міжнародному стандарті ISO/IEC 14882 (розділи [stmt.if] та [stmt.select]) інструкція `if constexpr` визначається як спеціалізована форма інструкції вибору (Selection Statement).

### Синтаксичні конструкції

```text
if constexpr ( init-statement(opt) condition ) statement
if constexpr ( init-statement(opt) condition ) statement else statement
```

де елементи граматичної структури мають такі нормативні визначення:
- **`init-statement` (необов'язковий):** інструкція ініціалізації. Може бути або інструкцією-виразом (Expression Statement), або простим оголошенням змінної (Simple Declaration), наприклад `auto val = get_data();` чи `constexpr int threshold = 100;`. Введена в стандарті C++17 для обмеження області видимості службових змінних.
- **`condition` (обов'язковий):** вираз, який контекстуально перетворюється до типу `bool`, або оголошення однієї змінної з обов'язковою прямою чи копіювальною ініціалізацією (`constexpr bool is_valid = ...`).
- **`statement`:** цільова інструкція або блок інструкцій у фігурних дужках `{ ... }`, що утворює тіло гілки `then` або гілки `else`.

### Область видимості та час життя сутностей init-statement

1. Якщо в конструкції присутній `init-statement`, усі оголошені в ньому змінні, типи та псевдоніми потрапляють в область видимості, яка охоплює як сам вираз умови `condition`, так і обидві гілки (`then` та `else`).
2. Час життя (Lifetime) об'єктів автоматичної пам'яті, створених у `init-statement`, триває до моменту повного завершення виконання інструкції `if constexpr` (тобто до виходу за межі фігурних дужок активної гілки).
3. Змінні, оголошені в `init-statement`, є доступними у виразі `condition` під час обчислення `constexpr` лише за умови, що вони самі оголошені зі специфікатором `constexpr` або є константними значеннями інтегрального чи перелічуваного типу.

## Вимоги до виразу умови condition

Вираз умови `condition` у конструкції `if constexpr` підпорядковується суворим нормативним обмеженням розділу [expr.const] стандарту C++:

1. **Константний вираз (Constant Expression):** умова зобов'язана бути виразом часу компіляції, придатним для використання в контекстах оцінки констант. Вона не може залежати від стану регістрів процесора, динамічного виділення пам'яті в купі (до C++20) або вхідних аргументів програми.
2. **Контекстуальне перетворення до типу bool:** тип результуючого значення виразу умови повинен неявно або явно перетворюватися на булеве значення (`bool`). Будь-яке цілочислове значення або перелік перетворюється за правилом: ненульове значення трактується як `true`, нуль — як `false`.
3. **Помилка часу компіляції при неконстантності:** якщо умова містить значення, відомі лише під час виконання (Runtime Values), або неконстантні виклики функцій, компілятор зобов'язаний негайно зупинити процес збірки з діагностичним повідомленням про неможливість обчислення виразу під час трансляції.
4. **Особливості оголошення змінної в condition:** якщо в умові оголошується змінна (`if constexpr (constexpr auto flag = check())`), вона зобов'язана мати тип, що перетворюється на `bool`. Спроба оголосити змінну неконстантного типу в умові `if constexpr` є синтаксичною помилкою.

```cpp
template<typename T>
void validate(T x) {
    // ВАЛІДНО: константний предикат метаінформації про тип
    if constexpr (std::is_integral_v<T>) { /* ... */ }

    // ВАЛІДНО: вираз оператора sizeof є константою компіляції
    if constexpr (sizeof(T) > 8) { /* ... */ }

    // ПОМИЛКА: значення параметра x відоме лише у runtime!
    if constexpr (x > 0) { /* ... */ } 
}
```

## Нормативна семантика відкинутих інструкцій (Discarded Statements [stmt.if]/2)

Головною інновацією `if constexpr` є механізм перетворення невибраної гілки на **відкинуту інструкцію** (Discarded Statement). Поведінка компілятора строго розмежовується залежно від того, чи знаходиться інструкція всередині шаблону (Templated Entity), чи у звичайній функції.

### Випадок 1: if constexpr усередині шаблонного контексту

Якщо конструкція `if constexpr` розташована всередині шаблону функції, шаблону методу класу, шаблону класу або узагальненого лямбда-виразу (`auto` лямбда):

1. **Оцінка умови під час інстанціювання:** компілятор обчислює значення `condition` індивідуально для кожної конкретної спеціалізації під час підстановки аргументів шаблону (Фаза 2 двоетапного пошуку імен).
2. **Селективне інстанціювання (Selective Instantiation):**
   - Якщо умова дорівнює `true`, гілка `then` стає активною інструкцією (Active Statement), а гілка `else` (якщо вона присутня) перетворюється на відкинуту інструкцію (Discarded Statement).
   - Якщо умова дорівнює `false`, гілка `then` стає відкинутою інструкцією, а гілка `else` (якщо вона присутня) стає активною.
3. **Правила трансляції відкинутої гілки:**
   - Усі синтаксичні конструкції, виклики методів, звернення до полів та типи даних, які прямо чи опосередковано залежать від параметрів шаблону (Dependent Entities), у відкинутій інструкції **не інстанціюються** (Not Instantiated).
   - Звернення до неіснуючих методів класу (`obj.non_existent_method()`), некоректні операції над залежними типами (розіменування скалярного числа `*val`) або спроби використання некоректних типів не піддаються семантичному аналізу й не генерують помилок компіляції.
   - Оголошення локальних класів, шаблонних спеціалізацій та лямбда-виразів усередині відкинутої гілки ігноруються й не породжують символів у таблиці трансляції.
   - Генератор коду бекенду компілятора повністю виключає відкинуту гілку: для неї не створюються вузли внутрішнього представлення (LLVM IR / GIMPLE) та не генеруються машинні інструкції.

### Випадок 2: if constexpr у нешаблонному контексті

Якщо `if constexpr` використовується всередині звичайної нешаблонної функції глобального простору імен або звичайного класу:

1. Умова все одно зобов'язана бути константним виразом `constexpr`.
2. Оптимізувальний компілятор використовує константність умови для відсікання мертвого коду, гарантуючи, що невибрана гілка не потрапить до бінарного файлу.
3. **Фундаментальна відмінність від шаблонів:** оскільки в нешаблонній функції відсутня фаза інстанціювання (немає параметрів-типів), компілятор зобов'язаний повністю перевірити семантику, типи та валідність викликів **для обох гілок**. Увесь код у невибраній гілці зобов'язаний бути на 100% коректним C++ щодо наявних типів програми.

```cpp
void regular_function() {
    constexpr bool feature_enabled = false;
    
    if constexpr (feature_enabled) {
        // Компілятор повністю перевіряє цей виклик! Якщо функція do_work()
        // не оголошена в коді, виникне помилка, незважаючи на if constexpr!
        do_work(); 
    }
}
```

## Вимоги синтаксичної коректності та двоетапний пошук імен [temp.res]

Відкинута інструкція у мові C++ **не є еквівалентом препроцесорної текстової вирізки `#ifdef`**. Вона підпорядковується загальним правилам двоетапного пошуку імен (Two-Phase Name Lookup) та аналізу шаблонів відповідно до розділу стандарту [temp.res]:

### Фаза 1: Синтаксичний аналіз визначення шаблону (Template Definition Parsing)

Під час першого проходу компілятор аналізує вихідний текст шаблону, коли аргументи типів ще не підставлені:

1. **Граматична цілісність:** весь текст усередині обох гілок `if constexpr` зобов'язаний відповідати формальній граматиці C++. Незбалансовані дужки, пропущені крапки з комою або лексичні помилки призводять до негайної зупинки компіляції.
2. **Перевірка незалежних імен (Non-dependent Names):** будь-який ідентифікатор, який не залежить від параметрів шаблону (наприклад, ім'я глобальної функції, назва стандартного типу `std::vector` чи константа), шукається в точці визначення шаблону. Якщо незалежне ім'я не знайдено — компілятор видає фатальну помилку на Фазі 1.
3. **Безумовно некоректні конструкції (Ill-formed, No Diagnostic Required):** якщо конструкція всередині відкинутої гілки не містить залежних від шаблону імен і є принципово некоректною для будь-якої можливої майбутньої спеціалізації шаблону, компілятор згідно зі стандартом має право визнати програму некоректною негайно.

### Механізм ODR-use для сутностей у відкинутих інструкціях

Згідно з правилом одного визначення (One Definition Rule [basic.def.odr]):
- Якщо функція або змінна з зовнішнім зв'язуванням використовується (ODR-used) всередині відкинутої гілки, але це використання залежить від параметра шаблону, сутність **не вважається використаною** (Not ODR-used), і лінкер не вимагатиме наявності її визначення.
- Якщо ж сутність не залежить від параметрів шаблону, факт її виклику в тілі відкинутої гілки може спричинити вимогу щодо наявності визначення символу під час компонування.

## Проблема static_assert(false) та специфікація dependent_false

Одним із найпоширеніших патернів у метапрограмуванні є перевірка повноти гілок: якщо жодна з очікуваних умов не виконана, компілятор має зупинити збірку зі зрозумілим повідомленням.

### Причина збою static_assert(false) у стандартах C++17 та C++20

```cpp
template<typename T>
void handle(T val) {
    if constexpr (std::is_integral_v<T>) {
        // обробка
    } else {
        // ПОМИЛКА C++17/C++20: літерал false не залежить від T!
        static_assert(false, "Непідтримуваний тип T!"); 
    }
}
```

Чому цей код не компілювався у C++17/C++20?
1. Вираз `false` є логічним літералом і синтаксично не містить жодного параметра шаблону `T`.
2. Компілятор класифікує вираз як незалежний від шаблону (Non-dependent Expression).
3. Відповідно до пункту [temp.res], твердження `static_assert` з незалежною хибною умовою оцінюється на **Фазі 1** (парсинг шаблону).
4. Оскільки `false` завжди є хибним, компілятор видає помилку негайно під час першого читання файлу, навіть якщо функція `handle()` ніде в програмі не викликається!

### Специфікація та реалізація ідіоми dependent_false

Щоб обійти це обмеження стандарту C++17, розробники використовують ідіому залежної константи (Dependent False Idiom). Створюється допоміжний шаблон змінної, значення якого завжди дорівнює `false`, проте його обчислення синтаксично прив'язане до типу `T`:

```cpp
template<typename...>
inline constexpr bool dependent_false = false;

template<typename T>
void handle_valid(T val) {
    if constexpr (std::is_integral_v<T>) {
        // обробка цілих чисел
    } else {
        // ВАЛІДНО: вираз dependent_false<T> залежить від T
        // Компілятор відкладає оцінку на Фазу 2 (інстанціювання)
        static_assert(dependent_false<T>, "Непідтримуваний тип T!");
    }
}
```

Оскільки `dependent_false<T>` залежить від `T`, компілятор ігнорує вираз на Фазі 1. На Фазі 2, якщо гілка `else` стає відкинутою інструкцією, шаблон `dependent_false<T>` у ній взагалі не інстанціюється. Помилка виникає виключно тоді, коли функція реально викликається з типом, для якого умова `is_integral_v<T>` дорівнює `false`.

### Зміни у стандарті C++23 (P2593R1)

У стандарті C++23 комітет ISO C++ ухвалив документ **P2593R1: «Making static_assert(false) dependent on template parameters»**. Нова редакція стандарту прямо гарантує: якщо `static_assert` знаходиться всередині відкинутої інструкції шаблонного контексту, він не оцінюється доти, доки ця гілка не стане активною під час фактичного інстанціювання шаблону.

## Виведення типу повернення (Return Type Deduction [dcl.spec.auto])

При використанні специфікаторів автоматичного виведення типу повернення `auto` або `decltype(auto)` конструкція `if constexpr` підпорядковується спеціальним правилам розділу [dcl.spec.auto]:

1. **Повне виключення відкинутих return:** усі інструкції `return`, які знаходяться всередині відкинутих гілок `if constexpr`, **повністю ігноруються** механізмом виведення типу функції.
2. **Узгодженість активних інструкцій:** якщо всередині активної гілки (або поза межами `if constexpr`) знаходиться декілька інструкцій `return`, усі вони зобов'язані виводити в точності один і той самий тип даних відповідно до стандартних правил виведення `auto`.
3. **Поліморфізм повертаного типу (Polymorphic Return Type):** функція з умовним компілюванням може повертати принципово різні типи даних для різних аргументів інстанціювання, що замінює складні метапрограмні структури вибору типу повернення на базі `std::conditional_t` або SFINAE.

```cpp
template<typename T>
auto extract_data(T obj) {
    if constexpr (std::is_pointer_v<T>) {
        return *obj;          // Якщо T = double*, результуючий тип: double
    } else if constexpr (std::is_integral_v<T>) {
        return obj * 2;        // Якщо T = int, результуючий тип: int
    } else {
        return std::string(obj); // Якщо T = const char*, результуючий тип: std::string
    }
}
```

У наведеному прикладі під час виклику `extract_data(5)` активною є друга гілка, яка повертає `int`. Перша та третя гілки позначаються як відкинуті інструкції, тому несумісність між типами `double`, `int` та `std::string` не викликає жодних помилок трансляції.

## Зведена матриця відмінностей механізмів статичного вибору

Нижче наведено порівняльну характеристику інструментів розгалуження в системному програмуванні на C++:

| Характеристика | Звичайний `if (runtime)` | Конструкція `if constexpr` (C++17) | Механізм SFINAE (`enable_if`) | Обмеження Concepts (C++20) |
| :--- | :--- | :--- | :--- | :--- |
| **Етап вибору гілки** | Час виконання (Runtime) | Інстанціювання шаблону (Compile-time) | Вибір перевантаження (Compile-time) | Вибір перевантаження (Compile-time) |
| **Інстанціювання невибраної гілки** | Завжди інстанціюється повністю | Не інстанціюється (Discarded) | Кандидат вилучається з множини | Кандидат вилучається з множини |
| **Вимога валідності методів у невибраній гілці** | Обов'язкова для всіх типів | Не потрібна для залежних типів | Не потрібна (вилучається сигнатура) | Не потрібна (вилучається сигнатура) |
| **Участь у виборі перевантажень (Overload Resolution)** | Ні (розгалуження всередині тіла) | Ні (розгалуження всередині тіла) | Так (керує множиною перевантажень) | Так (визначає найбільш обмежений шаблон) |
| **Вплив на виведення типу auto** | Усі return мають бути однакового типу | Відкинуті return ігноруються | Кожен шаблон має власну сигнатуру | Кожен шаблон має власну сигнатуру |
| **Вплив на розмір бінарного коду** | Може генерувати зайві переходи та код | Нульовий (невибраний код відсікається) | Нульовий (генерується лише обрана функція) | Нульовий (генерується лише обрана функція) |
| **Складність повідомлень про помилки** | Низька (локальні помилки типів) | Низька (локальні помилки в гілці) | Вкрай висока (каскади substitution failure) | Дуже низька (чітке повідомлення про невиконаний концепт) |

## Типові помилки використання та діагностика компіляторів

Нижче наведено перелік типових помилок використання інструкції `if constexpr` та форми їхньої діагностики провідними рушіями компіляції (Clang, GCC, MSVC):

1. **Використання неконстантної умови:**
   - *Код:* `if constexpr (x > 0)` для параметра функції `int x`.
   - *Діагностика Clang:* `error: constexpr if condition is not a constant expression`.
   - *Діагностика GCC:* `error: the value of 'x' is not usable in a constant expression`.
   - *Причина:* аргумент функції є значенням часу виконання, яке не може бути оцінене на етапі компіляції.
2. **Передчасний збій static_assert у C++17/20:**
   - *Код:* `static_assert(false, "err")` у гілці `else`.
   - *Діагностика Clang:* `error: static_assert failed "err"`.
   - *Причина:* літерал `false` не залежить від шаблону і викликає помилку на Фазі 1 (вимагає заміни на `dependent_false<T>`).
3. **Хибне коротке замикання в складених умовах:**
   - *Код:* `if constexpr (std::is_class_v<T> && has_nested<typename T::nested_type>::value)`.
   - *Діагностика GCC:* `error: 'typename T::nested_type' is not a class, struct, or union type`.
   - *Причина:* парсер розбирає типи у виразі умови до обчислення логічного оператора `&&` (вимагає вкладених блоків `if constexpr`).
4. **Неузгоджені типи повернення в межах однієї активної гілки:**
   - *Код:* `if constexpr (flag) { if (runtime_cond) return 1; return 2.0; }` для функції з повертаним типом `auto`.
   - *Діагностика Clang:* `error: deduced return type 'double' when previous return type was 'int'`.
   - *Причина:* якщо всередині активної гілки розташовано кілька інструкцій `return`, вони зобов'язані повертати строго один і той самий тип даних.

## Практичні інваріанти та інженерні рекомендації

1. **Розділення відповідальності між API та реалізацією:**
   - Якщо дві функції з однаковим ім'ям призначені для участі в зовнішньому виборі перевантажень (наприклад, через механізм пошуку Кеніґа ADL або для створення перевантажених операторів), розгалуження слід здійснювати в сигнатурі за допомогою концептів C++20 (`requires`) або SFINAE.
   - Якщо інтерфейс функції єдиний, а внутрішня реалізація містить альтернативні алгоритмічні шляхи (швидкий шлях для POD-типів або оптимізація під категорії ітераторів), вибір слід робити всередині тіла функції за допомогою `if constexpr`.
2. **Захист від передчасного синтаксичного збою (Short-circuiting Protection):** якщо умова перевіряє наявність внутрішнього типу чи складного методу в класі, перевірку слід розділяти на вкладені блоки `if constexpr`, щоб уникнути помилок парсингу складених виразів оператора `&&` на типах, що не є класами.
3. **Перевірка повноти покриття типів:** у поліморфних диспетчерах (наприклад, при обробці `std::variant`) завжди завершуйте ланцюжок умов блоком `else { static_assert(dependent_false<T>, "..."); }`, що гарантує захист від пропуску нових типів під час еволюції кодової бази.
4. **Контроль захоплення змінних у лямбда-виразах:** змінні зовнішнього контексту, що використовуються виключно всередині відкинутих гілок узагальнених лямбд, не збільшують розмір замикання, якщо вони не мають ODR-використання в активній гілці.
