# 📜 Історія появи if constexpr: від static if до C++17

Еволюція умовного компілювання в мові C++ пройшла довгий і драматичний шлях від наївного текстового маніпулювання препроцесором до повноцінної інтеграції в систему синтаксичного аналізу й інстанціювання компілятора. Ця трансформація відображає фундаментальний інженерний конфлікт: як надати розробникам узагальнених бібліотек максимальну виразність і контроль над кодогенерацією, не зруйнувавши при цьому строгі правила статичної типізації, блокової видимості та двоетапного пошуку імен.

## Ера препроцесора та глухий кут статичного розгалуження

На початкових етапах розвитку мов C та C++ єдиним інструментом для умовного вилучення фрагментів коду з процесу компіляції був препроцесор із його директивами `#if`, `#ifdef`, `#elif` та `#endif`. Препроцесор виконував обробку вихідного тексту на найпершій фазі трансляції — задовго до того, як компілятор будував абстрактне синтаксичне дерево (AST), перевіряв типи та заповнював таблицю символів.

```cpp
#if ARCHITECTURE_BITS == 64
    using word_t = unsigned long long;
#else
    using word_t = unsigned int;
#endif
```

У контексті низькорівневого програмування на C цього було достатньо для вибору системних заголовків чи конфігурації платформи. Проте з появою стандарту C++98 та стрімким розвитком узагальненого програмування на базі шаблонів виявилася повна безпорадність препроцесора перед завданнями інтроспекції типів:

1. **Сліпота до системи типів:** препроцесор нічого не знав про типи даних C++, структури, класи, вирівнювання пам'яті чи оператори `sizeof` та `alignof`. Усі його вирази оперували виключно цілочисловими літералами та попередньо визначеними макросами.
2. **Неможливість взаємодії з параметрами шаблонів:** якщо функція параметризована типом `template<typename T>`, препроцесор не мав жодної змоги дізнатися, чи є `T` вказівником, чи має він метод `.size()`, чи підтримує арифметичні операції або тривіальне копіювання байтів.
3. **Руйнування структури програми:** макроси діяли глобально, ігнорували простори імен, не підпорядковувалися правилам блокової інкапсуляції та спричиняли важковловимі конфлікти імен у великих кодових базах.

Щоб обирати різні шляхи виконання залежно від типу `T`, творцям бібліотек (зокрема розробникам стандартної бібліотеки STL та Boost) довелося винаходити складні обхідні механізми. Першим із них стала **диспетчеризація за тегами** (Tag Dispatching), де логіка розбивалася на кілька окремих перевантажених функцій, а вибір потрібної здійснювався через передачу фіктивного порожнього об'єкта-тегу (`std::input_iterator_tag{}`, `std::random_access_iterator_tag{}`). Другим став механізм **SFINAE** (Substitution Failure Is Not An Error) та утиліта `std::enable_if`, які дозволяли умовно вилучати функції з набору кандидатів перевантаження під час підстановки типів.

Обидва підходи були вимушеними «милицями»: замість природного лінійного розгалуження всередині однієї функції розробники мусили розривати алгоритм на множину фрагментів, створювати допоміжні структури й писати захаращені сигнатури, які генерували нечитабельні багатосторінкові повідомлення про помилки компіляції.

## Досвід мови D: тріумф і компроміси конструкції static if

На початку 2000-х років Волтер Брайт (Walter Bright), засновник мови програмування D, у тісній співпраці з відомим дослідником метапрограмування C++ Андреєм Александреску (Andrei Alexandrescu) реалізував революційну конструкцію — `static if`.

На відміну від звичайного виконання `if`, `static if` у мові D оцінював константний вираз на етапі компіляції. Якщо вираз був істинним, компілятор вбудовував тіло блоку в навколишній код; якщо хибним — весь блок безслідно відкидався, ніби його ніколи не існувало в тексті файлу.

Найрадикальнішою особливістю реалізації в мові D було **розширення області видимості** (Scope Injection або Scope Leaking). Оголошення нових типів, змінних чи функцій усередині `static if` ставали видимими у зовнішньому блоці, що охоплював цю конструкцію:

```d
// Концептуальна модель static if у мові D
static if (is(T == int)) {
    int local_counter = 0; // local_counter стає доступним у всій зовнішній функції!
}
```

Така поведінка надала розробникам небачену виразність: можна було умовно додавати поля до структури даних, динамічно генерувати методи класу або створювати нові псевдоніми типів. Проте це породжувало серйозні проблеми для архітектури компілятора:

- **Нелінійність синтаксичного аналізу:** щоб зрозуміти, чи є певний ідентифікатор типом чи змінною в наступних рядках файлу, аналізатор мусив спочатку повністю обчислити всі попередні умови `static if`.
- **Крах традиційних інструментів розробки (IDE):** системи автодоповнення, індексатори коду та статичні аналізатори не могли побудувати модель коду без повного запуску рушія інстанціювання для кожного можливого варіанта типів.

## Спроба перенесення в C++: документ N3329 та великі дебати 2012 року

У 2011–2012 роках інженери Герб Саттер (*Herb Sutter*), Волтер Брайт (*Walter Bright*) та Андрей Александреску (*Andrei Alexandrescu*) запропонували адаптувати підхід мови D до синтаксису C++, опублікувавши документ **N3329: «Proposal: static if declaration»** (розвиваючи ранню концептуальну розвідку Волтера Брауна N3322).

Пропонувалося ключове слово `static_if (condition) { ... } else { ... }`, яке могло використовуватися як усередині функцій, так і на рівні визначення класів чи просторів імен.

Документ спричинив одну з найзапекліших дискусій у новітній історії комітету ISO C++. Провідні експерти з теорії мов та архітектури компіляторів — зокрема Б'ярне Страуструп (*Bjarne Stroustrup*), Габріель Дос Рейс (*Gabriel Dos Reis*) та Ендрю Саттон (*Andrew Sutton*) у фундаментальній відповіді **N3613: «"Static If" Considered»** (2013) — виступили з ґрунтовною критикою концепції `static_if`. Їхня позиція спиралася на кілька непохитних принципів:

1. **Руйнування двоетапного пошуку імен (Two-Phase Name Lookup):** фундаментальний інваріант мови C++ стверджує, що будь-який шаблон аналізується у два етапи:
   - *Фаза 1 (визначення шаблону):* перевірка базового синтаксису, побудова AST та прив'язка незалежних імен до того, як стануть відомі конкретні типи.
   - *Фаза 2 (інстанціювання):* підстановка типів-аргументів і перевірка виразів, що залежать від параметрів шаблону.
   Якщо `static_if` дозволяв умовно додавати оголошення імен у зовнішній контекст, компілятор на першій фазі втрачав можливість побудувати коректне дерево AST, бо не знав структури оточення.
2. **Порушення семантики блокових дужок:** у мові C++ кожна пара фігурних дужок `{}` створює ізольовану лексичну область видимості (Block Scope). Можливість змінних «витікати» з дужок `static_if` грубо порушувала просторову локальність коду та збивала з пантелику розробників.
3. **Неможливість локального аналізу шаблонів:** без конкретних параметрів інстанціювання файл перетворювався на нерозбірливу послідовність символів, що паралізувало роботу парсерів у середовищах розробки (CLion, Visual Studio тощо).

На засіданні комітету в Портленді восени 2012 року пропозицію `static_if` було остаточно відхилено. Більшість робочої групи дійшла висновку: C++ потребує умовного компілювання, але воно не повинно руйнувати лексичну структуру мови.

## Пошук компромісу: народження constexpr if (2015–2016)

Відхилення N3322 не зменшило тиску з боку індустрії. Поява стандарту C++14 суттєво розширила можливості функцій `constexpr` (дозволивши всередині них локальні змінні, цикли та звичайні інструкції розгалуження `if`), проте всередині шаблонів звичайний `if` залишався безпорадним: обидві його гілки мусили бути коректно типізованими для будь-якого аргументу шаблону.

У 2015–2016 роках група авторів — Вілле Воутілайнен (Ville Voutilainen), Фейсал Валі (Faisal Vali), Єнс Маурер (Jens Maurer), Девід Вандевурд (David Vandevoorde) та Річард Сміт (Richard Smith) — запропонувала кардинально переосмислену концепцію у документах **P0128: «constexpr if-statements»** та **P0292: «constexpr if: A slightly different take on static if»**.

Ключем до успіху нової пропозиції стала відмова від ідеї розширення видимості (Scope Injection) та формулювання концепції **відкинутих інструкцій (Discarded Statements)**:

1. **Строга блокова видимість:** кожна гілка конструкції створює свій власний повноцінний блок видимості. Жодна сутність не просочується назовні.
2. **Збереження двоетапного пошуку імен:** на Фазі 1 компілятор зобов'язаний синтаксично проаналізувати обидві гілки (і `then`, і `else`). Граматичні помилки та некоректні незалежні імена відловлюються негайно, що гарантує цілісність синтаксичного дерева AST.
3. **Селективне інстанціювання (Фаза 2):** відкидання гілки відбувається виключно під час підстановки конкретних типів-параметрів. Усі вирази, які залежать від шаблону, у відкинутій гілці просто не піддаються інстанціюванню.
4. **Синтаксична спадкоємність:** замість створення штучного оператора `static_if` розробники взяли звичний `if` і додали кваліфікатор `constexpr`, що підкреслило його роль у сімействі компіляційних обчислень C++.

У червні 2016 року на засіданні комітету стандартизації в місті Оулу (Фінляндія) документ P0292R2 було схвалено переважною більшістю голосів і офіційно включено до проєкту стандарту **C++17 (ISO/IEC 14882:2017)**.

## Виклики реалізації у компіляторах та проблема static_assert(false)

Впровадження `if constexpr` вимагало глибокої перебудови внутрішніх механізмів компіляторів. Рушії GCC та Clang, які з самого початку розроблялися з підтримкою чистого двоетапного пошуку імен, адаптували новий стандарт відносно швидко. Натомість команді Microsoft Visual C++ довелося повністю переписати свій застарілий однофазний синтаксичний аналізатор шаблонів (що привело до створення прапорця сумісності `/permissive-` у MSVC).

У процесі практичного використання розробники зіткнулися з відомою підступною пасткою: спробою розмістити `static_assert(false, "Помилка")` у гілці `else` для перехоплення непідтримуваних типів. Оскільки вираз `false` не містив залежних від шаблону імен, компілятори відповідно до пункту [temp.res] діагностували помилку ще на Фазі 1, руйнуючи збірку. Спільноті довелося кілька років використовувати допоміжний шаблон `dependent_false<T>`, доки в стандарті **C++23** пропозиція **P2593R1** («Making static_assert(false) dependent on template parameters») остаточно не легалізувала прямий запис `static_assert(false)`.

Завдяки конструкції `if constexpr` мова C++ здобула інструмент, який поєднав простоту звичайного процедурного розгалуження з потужністю статичного метапрограмування, відкривши шлях до сучасних архітектурних патернів обробки типів.
