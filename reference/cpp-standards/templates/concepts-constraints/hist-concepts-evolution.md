# 📜 Еволюція концептів у C++: від ConceptGCC до C++20

Коли в середині 1990-х років Олександр Степанов (Alexander Stepanov) разом із Менґ Лі (Meng Lee) та Девідом Мюссером (David Musser) створював Standard Template Library (STL), узагальнене програмування (англ. *generic programming*) будувалося навколо чіткої математичної ідеї: алгоритми повинні оперувати не конкретними типами у пам'яті, а абстрактними алгебраїчними структурами та сімействами вимог до поведінки. У документації до STL з'явилися формальні описи: `InputIterator`, `ForwardIterator`, `LessThanComparable`, `EqualityComparable`. Проте мова C++ стандарту C++98 не мала жодного синтаксичного інструменту для прямого вираження цих сутностей. Для компілятора заголовок `template<typename T>` означав абсолютно довільний тип, а відповідність вимогам алгоритму з'ясовувалася лише в момент спроби скомпілювати згенероване тіло функції.

Ця розбіжність між математичною строгістю проєктування та повною відсутністю перевірки меж інтерфейсу в компіляторі породила понад двадцять років запеклих дискусій, експериментів, скасованих стандартів та наукових досліджень.

---

## Концептуальний фундамент: Степанов, Страуструп та аксіоми

Слово «концепт» походить від латинського *conceptus* (поняття, уявлення, від дієслова *concipere* — охоплювати, зачинати, збирати разом). В узагальненому програмуванні концепт позначає сукупність синтаксичних вимог (наявність методів, операторів, вкладених типів), семантичних вимог (що саме роблять ці методи) та часових і просторових гарантій складності алгоритмів.

Б'ярне Страуструп (Bjarne Stroustrup) у книзі *The Design and Evolution of C++* згадував, що мріяв про систему обмежень параметрів шаблонів ще наприкінці 1980-х, коли шаблони тільки проєктувалися. Проте тоді не існувало зрозумілого механізму, який би поєднував строгу типізацію з нульовими накладними витратами під час виконання (англ. *zero-overhead principle*).

У класичному об'єктно-орієнтованому програмуванні поліморфізм реалізується через успадкування від абстрактних базових класів з віртуальними функціями. Для узагальнених алгоритмів такий підхід був неприйнятним із трьох причин:
1. **Накладні витрати часу виконання**: кожен виклик оператора чи ітератора вимагав би непрямого переходу через таблицю віртуальних методів (`vtable`), що унеможливлювало б інлайнінг дрібних операцій і сповільнювало б роботу критичних циклів у десятки разів.
2. **Неможливість оптимізації вбудованих типів**: фундаментальні типи процесора на кшталт `int`, `double` або сирих вказівників `T*` не мають базових класів і не можуть успадковувати жодні інтерфейси.
3. **Бінарні операції над одним типом**: вирази на кшталт `a + b` вимагають гарантії, що обидва операнди належать до абсолютно однакового типу, тоді як класичний динамічний підтипізаційний поліморфізм дозволяє змішувати різні похідні класи в ієрархії.

Тому шаблони C++ пішли шляхом статичного «качиного типізування» на етапі компіляції. Якщо тип `T` підтримує `*it` та `++it`, він підходить для алгоритму `std::find`. Проте якщо тип не підтримував потрібної операції, компілятор видавав багатосторінкові повідомлення про помилки з глибин внутрішніх реалізацій бібліотеки, а перевантаження функцій на основі властивостей типів перетворювалося на складні трюки через SFINAE.

## Епоха C++0x: зліт і криза ConceptGCC

На початку 2000-х років робоча група комітету ISO C++ розпочала підготовку нового великого стандарту, відомого тоді як C++0x (майбутній C++11). Концепти вважалися центральною та найважливішою функцією цього релізу.

Головними архітекторами першої моделі концептів стали Дуглас Ґреґор (Douglas Gregor), Джеремі Сік (Jeremy Siek), Ендрю Ламсдейн (Andrew Lumsdaine) та Б'ярне Страуструп. Вони поставили амбітну мету: створити повноцінну модульну систему типізації шаблонів, яка перевіряла б тіло шаблону ізольовано від його викликів.

У моделі C++0x концепт оголошувався спеціальним блоком, який описував сигнатури, вкладені типи та навіть математичні аксіоми:

```cpp
// Історичний синтаксис C++0x ConceptGCC (2006-2009 роки):
concept LessThanComparable<typename T> {
    bool operator<(T a, T b);
    
    // Спроба формалізації математичних аксіом у мові:
    axiom Irreflexivity(T a) {
        (a < a) == false;
    }
    axiom Asymmetry(T a, T b) {
        if (a < b) (b < a) == false;
    }
};
```

Найрадикальнішим елементом моделі C++0x була ідея **відображення концептів** (англ. *concept maps*). Якщо тип структурно не задовольняв вимоги концепту (наприклад, метод називався `length()` замість `size()`, або замість глобального оператора порівняння був метод класу), розробник міг явно написати адаптер прямо в коді:

```cpp
// Історичний синтаксис: адаптація стороннього класу до концепту
concept_map Stack<MyLegacyQueue> {
    void push(MyLegacyQueue& q, int val) { q.enqueue(val); }
    int pop(MyLegacyQueue& q) { return q.dequeue(); }
};
```

Для експериментів із цією моделлю Дуглас Ґреґор розробив експериментальний форк компілятора GCC — **ConceptGCC**. Університет Індіани та група авторів провели тисячі годин, реалізуючи повну підтримку моделі та портуючи STL на концепти.

Проте що глибше розвивалася реалізація, то більша кількість фундаментальних проблем виринала на поверхню:

1. **Роздільна перевірка типу (Type Checking of Template Definitions)**: у C++0x компілятор повинен був перевіряти тіло шаблону взагалі без підстановки конкретних типів. Якщо у тілі функції викликався метод, явно не задекларований у концепті, компілятор видавав помилку. Це вимагало переписування практично кожної строчки стандартної бібліотеки.
2. **Конфлікт явних та автоконцептів (Explicit vs Auto Concepts)**: концепт за замовчуванням вимагав явного оголошення `concept_map`, що руйнувало сумісність з існуючим кодом. Додавання `auto concept` (автоматичного визначення відповідності за структурою) створювало жахливі граматичні неоднозначності з пошуком імен через ADL.
3. **Експоненційне зростання складності компіляторів**: специфікація концептів у чернетці стандарту перевищила 100 сторінок надзвичайно складного математичного тексту. Жоден комерційний постачальник компіляторів (ні Microsoft, ні EDG, ні IBM) не бачив можливості реалізувати цю специфікацію у розумні терміни.

## Липнева драма у Франкфурті (2009 рік)

У липні 2009 року комітет ISO C++ зібрався на історичне засідання у Франкфурті (Німеччина). Стандарт C++0x уже запізнювався на кілька років. На порядку денному стояло питання готовності концептів до фінальної стандартизації.

Б'ярне Страуструп та Дуглас Ґреґор наполягали, що концепти можна доопрацювати та спростити в процесі впровадження. Проте представники великих індустріальних компаній та розробники фронтендів компіляторів виступили категорично проти. Головним аргументом було те, що поточний проєкт концептів був занадто важким, нестійким і створював нерозв'язні крайові випадки у правилах пошуку імен та перевантаження.

Відбулося драматичне голосування. Більшістю голосів комітет вирішив **повністю видалити концепти з робочого проєкту C++0x**. Це стало шоком для академічної спільноти. Дуглас Ґреґор незабаром залишив активну роботу над цією частиною стандарту і перейшов до команди розробників Clang/LLVM.

Стандарт було терміново очищено від усіх згадок концептів, і в 2011 році він вийшов під назвою C++11, залишивши розробників зі старим інструментарієм: SFINAE, `std::enable_if` та нововведеними варіативними шаблонами.

Страуструп пізніше назвав події у Франкфурті «найбільшим розчаруванням у своїй роботі над C++», проте визнав, що ухвалене рішення врятувало C++11 від нескінченної затримки.

## Відродження: Concepts Lite та Технічна специфікація TS 19217

Незважаючи на фіаско у Франкфурті, проблема перевірки інтерфейсів шаблонів нікуди не зникла. Б'ярне Страуструп спільно з Ендрю Саттоном (Andrew Sutton) та Габріелем Дос Рейсом (Gabriel Dos Reis) розпочали роботу з чистого аркуша.

Вони сформулювали новий підхід під назвою **Concepts Lite** (документ N3580, 2013 рік). Філософія нової моделі базувалася на радикальному спрощенні:

1. **Відмова від роздільної компіляції тіла**: компілятор більше не намагається валідувати тіло шаблону без підстановки типів. Перевіряються лише аргументи на вході в шаблон.
2. **Відмова від `concept_map`**: типи відповідають концепту виключно на основі того, чи є валідними операції над ними (структурна відповідність).
3. **Концепт як булевий предикат часу компіляції**: концепт — це іменований константний вираз типу `bool`, який обчислюється під час збірки і може використовуватися як обмеження.
4. **Вираз `requires`**: введено спеціальний синтаксичний блок, що перевіряє валідність довільних виразів, наявність типів та сигнатур без необхідності генерації коду.

У 2015 році модель Concepts Lite була опублікована як офіційна технічна специфікація **ISO/IEC TS 19217:2015**. Ендрю Саттон реалізував її у спеціальній гілці GCC, що дозволило сотням розробників протестувати новий синтаксис на реальних кодових базах.

## Тріумф C++20: злиття та оновлена стандартна бібліотека

Упродовж циклу розробки C++17 та C++20 модель Concepts Lite зазнала кількох важливих покращень:
- Додано формальні правила **поглинання концептів** (англ. *subsumption*), які дозволили компілятору автоматично визначати більш спеціалізовані перевантаження без конфліктів.
- Узгоджено чотири рівноправні синтаксичні форми обмежень: від речень `requires` до лаконічних скорочених шаблонів функцій із типом `auto`.
- Було створено фундаментальну бібліотеку стандартних концептів у заголовному файлі `<concepts>`, а також повністю переписано алгоритми та ітератори у новій бібліотеці Ranges (`<ranges>`).

На засіданні комітету ISO у Сан-Дієго (2018 рік) та фінальному затвердженні у Празі (2020 рік) концепти були одноголосно включені до ядра стандарту C++20.

Через двадцять п'ять років після появи STL мова C++ нарешті отримала офіційний, швидкий у компіляції та надійний інструмент, який матеріалізував початкове бачення Олександра Степанова. Концепти перестали бути просто коментарями в документації, перетворившись на повноправних вартових архітектури коду.
