# 📜 Еволюція SFINAE: від зауваження до мовного стандарту

Історія механізму SFINAE (*Substitution Failure Is Not An Error* — невдача підстановки не є помилкою) демонструє, як технічний виняток у правилах зіставлення сигнатур перетворився на головний фундамент шаблонного метапрограмування мови C++ на понад два десятиліття. Без розуміння цієї еволюції неможливо збагнути, чому сучасні стандартні бібліотеки містять стільки шарів `enable_if`, як з'явилася ідіома виявлення та чому комітет ISO врешті-решт створив концепції у C++20.

## Зауваження Девіда Вандевурда та народження C++98

Наприкінці 1990-х років, коли комітет ISO C++ завершував роботу над першим міжнародним стандартом ISO/IEC 14882:1998, шаблони функцій розглядалися переважно як зручний спосіб параметризації алгоритмів над довільними типами. Творець мови Баджарн Страуструп (*Bjarne Stroustrup*) та автор стандартної бібліотеки шаблонів STL Александр Степанов (*Alexander Stepanov*) прагнули створити систему узагальнених контейнерів та ітераторів без втрати швидкості виконання на рівні асемблера.

Проте практична взаємодія шаблонів зі звичайним механізмом перевантаження функцій виявила серйозну математичну суперечність у правилах мови.

Уявімо типову ситуацію узагальненої бібліотеки: розробник створює перевантажену функцію для обробки стандартних контейнерів, яка приймає вкладений тип `typename T::value_type`, а поруч оголошує звичайну функцію для простих скалярних чисел `int`:

```cpp
template<typename T>
void process(typename T::value_type x);

void process(int x);
```

Коли компілятор обробляє виклик `process(10)`, він зобов'язаний сформувати повний список усіх доступних кандидатів перед тим, як обрати найкращу функцію. Для шаблонної версії компілятор мусить вивести параметр `T` та підставити тип переданого аргументу `T = int`. Проте фундаментальний тип `int` не є структурою чи класом і за своєю природою не містить жодних вкладених типів `value_type`.

За загальними правилами типізації C++ будь-яка спроба звернутися до неіснуючого члена типу `int::value_type` є грубою синтаксичною помилкою (Ill-formed program), яка вимагає негайного переривання трансляції з аварійним завершенням збірки. Якби це правило застосовувалося абсолютно до всіх фаз компіляції, жодне шаблонне перевантаження із залежними типами не змогло б мирно співіснувати з іншими функціями. Будь-який виклик із несумісним типом призводив би до миттєвого краху проєкту.

Бельгійський інженер і активний член комітету стандартизації Девід Вандевурд (*David Vandevoorde*) звернув увагу робочої групи на цю проблему. Він запропонував фундаментальне розмежування: помилка, що виникає безпосередньо під час підстановки виведених параметрів у сигнатуру шаблону функції, не повинна вважатися фатальною помилкою трансляції. Компілятор має просто мовчки викреслити цей шаблон зі списку кандидатів і продовжити розгляд решти перевантажень.

Цей принцип увійшов до стандарту C++98 у розділі [temp.deduct]. Згодом у 2002 році Девід Вандевурд та Ніколаї Йосуттіс (*Nicolai M. Josuttis*) у своїй фундаментальній книзі *«C++ Templates: The Complete Guide»* вперше зафіксували та популяризували абревіатуру **SFINAE**.

## Ера C++03: трюки з sizeof та виникнення Boost.EnableIf

У стандарті C++98/C++03 правило SFINAE було суворо обмежене: воно діяло лише для типів у сигнатурі (наприклад, типів параметрів чи типу повернення), але не поширювалося на довільні вирази всередині коду. Проте розробники швидко зрозуміли: якщо невдала підстановка тихо відкидає шаблон, цим механізмом можна керувати штучно для перевірки властивостей типів.

У 2000–2003 роках дослідники з Університету Індіани — Яакко Ярві (*Jaakko Järvi*), Джеремія Вілкок (*Jeremiah Willcock*) та Ендрю Ламсдейн (*Andrew Lumsdaine*) — опублікували серію праць про параметричний поліморфізм та створили бібліотеку `Boost.EnableIf`.

До появи `enable_if` розробники використовували громіздку ідіому на базі оператора `sizeof`. Оскільки оператор `sizeof` у C++ ніколи не виконує обчислень у runtime, а лише оцінює тип виразу під час компіляції, перевірку наявності властивостей робили через розміри штучних масивів:

```cpp
// Трюк епохи C++03 для перевірки наявності внутрішнього типу iterator
typedef char YesType[1];
typedef char NoType[2];

template<typename C>
static YesType& check(typename C::iterator*);

template<typename C>
static NoType& check(...);

// Якщо C має iterator, перевантаження 1 є валідним, і sizeof(YesType) == 1
const bool has_iterator = (sizeof(check<MyType>(0)) == sizeof(YesType));
```

Яарві та його колеги зрозуміли, що цю логіку можна уніфікувати в одну просту структуру:

```cpp
template<bool B, class T = void>
struct enable_if_c {
    typedef T type;
};

template<class T>
struct enable_if_c<false, T> {};
```

Якщо булева умова істинна, структура містить `typedef T type`. Якщо хибна — вкладений псевдонім `type` просто відсутній. Спроба розіменувати `typename enable_if_c<Cond, Ret>::type` генерує саме ту помилку підстановки, яка змушує SFINAE відкинути кандидат без аварійного завершення компіляції.

Бібліотека увійшла до складу Boost 1.31 у 2003 році й на десятиліття стала стандартом де-факто для вибіркового перевантаження функцій у таких масштабних бібліотеках, як `Boost.Spirit`, `Boost.Serialization` та `Boost.Graph`.

## C++11 та Expression SFINAE (N2242)

З розвитком узагальненого програмування можливостей C++03 стало недостатньо. Розробники хотіли перевіряти не лише наявність вкладених `typedef`, але й валідність довільних математичних виразів: «Чи можна скласти два об'єкти оператором `a + b`?», «Чи має об'єкт метод `serialize()` з відповідними аргументами?».

У C++03 спроба підставити невалідний вираз викликала жорстку помилку компіляції. Щоб розширити SFINAE на будь-які синтаксичні вирази, Говард Гіннант (*Howard Hinnant*), Джастін Рошангіас (*Justin Rochanghiaz*) та Баджарн Страуструп (*Bjarne Stroustrup*) запропонували документ **N2242** (*«Expression SFINAE»*), який було прийнято до стандарту C++11.

Одночасно з цим стандарт C++11 ввів оператор виведення типу `decltype` та допоміжну функцію `std::declval`. Це уможливило перевірку будь-яких методів у сигнатурі повернення:

```cpp
template<typename T>
auto serialize(T& obj) -> decltype(obj.serialize(), void()) {
    obj.serialize();
}
```

У C++11 `enable_if` також отримав офіційне місце у стандартному заголовку `<type_traits>` як `std::enable_if`. Проте реалізація Expression SFINAE у трансляторах виявилася настільки складною, що повна підтримка цього стандарту в комерційних компіляторах затягнулася на роки: наприклад, компілятор MSVC досяг повної відповідності стандарту щодо Expression SFINAE лише у випусках Visual Studio 2017.

## C++14 та прорив Walter Brown: std::void_t (N3928)

Попри всю міць Expression SFINAE у C++11, написання предикатів інтроспекції вимагало складної шаблонної магії та обтяжливого коду. Для кожної нової перевірки доводилося виписувати десятки рядків коду з допоміжними перевантаженнями `decltype` та `std::declval`.

На засіданні комітету стандартизації в Іссакуа (штат Вашингтон) у лютому 2014 року професор Волтер Браун (*Walter E. Brown*) подав короткий документ **N3928** (*«Making Non-modifying Sequence Operations More Flexible»*), у якому запропонував надзвичайно лаконічний псевдонім:

```cpp
template<typename...>
using void_t = void;
```

Цей шаблон із трьох рядків приймає довільну кількість типів та завжди перетворює їх на `void`. Проте якщо всередині списку параметрів будь-який із виразів є невалідним (наприклад, звернення до неіснуючого методу чи типу), `void_t` зазнає помилки підстановки SFINAE.

Завдяки `void_t` народилася знаменита **ідіома виявлення** (Detection Idiom), яка дозволила писати перевірки наявності методів та типів усього у дві спеціалізації структури без жодних макросів чи ручних таблиць перевантажень.

## Чому C++20 відмовився від панування SFINAE

Попри свою гнучкість, SFINAE мав дві фатальні вади, які перетворили компіляцію великих проектів C++ на важке випробування:
1. **Катастрофічне роздування повідомлень про помилки (Diagnostics Bloat):** Якщо розробник припускався помилки в одному аргументі виклику, компілятор відкидав усі перевантаження за правилом SFINAE. У результаті він видавав десятки сторінок тексту з діагностикою: `candidate template ignored: substitution failure`, показуючи нутрощі десятків стандартних заголовків замість короткого пояснення проблеми.
2. **Низька швидкість збірки:** Компілятор був змушений інстанціювати десятки структур `enable_if` та обчислювати AST виразів для кожного кандидата у списку перевантажень.

У стандарті C++20 комітет під керівництвом Баджарна Страуструпа, Ґабріеля Дос Рейса (*Gabriel Dos Reis*) та Ендрю Саттона (*Andrew Sutton*) стандартизував **Концепції та Обмеження** (*Concepts and Constraints*, P0784 та супутні документи).

Концепції зробили обмеження сигнатур першокласними громадянами мови. Замість трюків із навмисним провокуванням синтаксичних збоїв `std::enable_if`, розробники отримали пряме ключове слово `requires`. SFINAE залишився у стандарті для зворотної сумісності з мільйонами рядків коду C++98–C++17, але в сучасному дизайні поступився місцем чистій декларативній системі концепцій.
