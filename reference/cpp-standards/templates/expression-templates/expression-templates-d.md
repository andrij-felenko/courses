# Шаблони виразів: коли вираз стає деревом типів

<preknowlist>
- [Шаблони: параметризація типом](book:cpp-standards/templates-basics) — інстанціювання класів-шаблонів та виведення типів аргументів.
- [Спеціалізація й перевантаження шаблонів](book:cpp-standards/specialization-overload) — як C++ добирає функції для шаблонних операндів.
- [CRTP: статичний поліморфізм](book:cpp-standards/crtp) — передавання похідного класу як параметра базового шаблону для виклику методів без `vtable`.
- [Категорії значень: lvalue, prvalue, xvalue](book:cpp-standards/value-categories) — чому тимчасові об'єкти та посилання впливають на час життя у складених виразах.
</preknowlist>

Обчислення математичного виразу `Vector result = A + B + C + D;` у традиційній бібліотеці лінійної алгебри на C++ з звичайним перевантаженням операторів спричиняє приховану катастрофу продуктивності. Кожен оператор `+` обчислює результат негайно, повертаючи новий тимчасовий об'єкт вектора. За розміру векторів `N = 10 000 000` елементів типу `double` (по 80 мегабайтів кожний) вираз `A + B` виділяє у динамічній пам'яті перші 80 мегабайтів і виконує перший прохід циклом додавання. Проміжний результат `(A + B) + C` виділяє другі 80 мегабайтів і виконує другий цикл. Операція `+ D` виділяє треті 80 мегабайтів і здійснює третій цикл. Загалом програма виконує 3 виділення пам'яті в купі на суму 240 мегабайтів, 6 повних читань із оперативної пам'яті та 3 записи на елемент, перетворюючи потужний обчислювальний процесор на пасивного очікувальника повільної шини RAM.

Ручний код на мові C або Fortran у подібній ситуації не виділяє жодного тимчасового буфера: розробник пише один цикл `for (size_t i = 0; i < N; ++i) result[i] = A[i] + B[i] + C[i] + D[i];`, який завантажує дані в регістри процесора, робить 4 читання та 1 запис на елемент і миттєво векторизується інструкціями SIMD. 

Шаблони виразів (Expression Templates) — це ідіома метапрограмування C++, яка усуває цей розрив між виразним математичним синтаксисом високого рівня та ефективністю низькорівневого машинного коду. Вона перетворює арифметичні оператори з інструментів безпосереднього обчислення на інструменти побудови статичного дерева типів під час компіляції.

![Порівняння обчислення виразу: наївне проти шаблонів виразів](/reference/cpp-standards/templates/expression-templates/img/et-evaluation.svg)
*Порівняння обчислення виразу: наївні перевантажені оператори виділяють три тимчасових масиви в пам'яті, тоді як шаблони виразів будують дерево типів під час компіляції та обчислюють весь вираз в одному циклі.*

## 1. Проблема наївного перевантаження: чому прості оператори нищать кеш

Для глибшого розуміння фізичної природи проблеми розглянемо взаємодію сучасної мікроархітектури процесора з оперативною пам'яттю під час обчислення векторних виразів.

Сучасний процесор обробляє дані на частоті 4–5 ГГц. Векторні модулі SIMD (наприклад, AVX-512) здатні виконувати по дві 512-бітні інструкції за такт, опрацьовуючи до 16 чисел з плаваючою крапкою подвійної точності (`double`) за один такт. Проте час доступу до оперативної пам'яті (DRAM) становить приблизно 200–300 тактів процесора. Щоб згладити цю прірву, процесор спирається на ієрархію кеш-пам'яті (L1, L2, L3) та апаратний предвибігач (Hardware Prefetcher), який заздалегідь завантажує послідовні блоки даних розміром 64 байти (кеш-лінії).

Коли обчислення виконується в один цикл:

```cpp
for (size_t i = 0; i < N; ++i) {
    result[i] = A[i] + B[i] + C[i] + D[i];
}
```

процесор зчитує 4 масиви паралельно. Кеш-лінії для `A`, `B`, `C`, `D` ідеально пакуються в кеш L1/L2, а проміжні результати додавання утримуються у векторних регістрах процесора (`YMM0`–`YMM15`). В оперативну пам'ять вирушає лише один підсумковий потік запису `result`.

Розглянемо тепер, що відбувається при наївному перевантаженні операторів для трьох послідовних операцій `A + B + C + D`:

### Крок 1: Обчислення `T1 = A + B`
1. Викликається `operator+`, який виділяє у купі масив `T1` розміром 80 МБ через `malloc`/`operator new`.
2. Процесор читає `A` (80 МБ) та `B` (80 МБ) із RAM.
3. Процесор записує `T1` (80 МБ) у RAM.
4. Оскільки масив 80 МБ не вміщується в кеш L3 (який зазвичай має розмір 16–32 МБ), усі витіснені кеш-лінії скидаються в оперативну пам'ять.

### Крок 2: Обчислення `T2 = T1 + C`
1. Викликається другий `operator+`, який виділяє ще один масив `T2` розміром 80 МБ.
2. Процесор знову читає щойно записаний `T1` (80 МБ) та масив `C` (80 МБ) із RAM.
3. Процесор записує `T2` (80 МБ) у RAM.

### Крок 3: Обчислення `T3 = T2 + D`
1. Викликається третій `operator+`, виділяючи `T3` на 80 МБ.
2. Процесор читає `T2` (80 МБ) та `D` (80 МБ).
3. Процесор записує `T3` (80 МБ) у RAM.

### Підсумковий баланс трафіку пам'яті
- **Наївне перевантаження**: 6 читань + 3 записи = **9 проходів по 80 МБ (720 МБ трафіку RAM)** та 3 виділення пам'яті у купі.
- **Оптимальний злитий цикл**: 4 читання + 1 запис = **5 проходів по 80 МБ (400 МБ трафіку RAM)** та 0 додаткових виділень пам'яті.

Наївний підхід генерує майже вдвічі більше трафіку пам'яті та здійснює три дорогі звернення до менеджера кулі пам'яті (`heap allocator`), що призводить до падіння продуктивності у 4–10 разів.

## 2. Задум шаблонів виразів: відкладені обчислення та AST типів

Щоб ліквідувати ці витрати, не відмовляючись від природного синтаксису `A + B + C + D`, шаблони виразів змінюють саму роль арифметичних операторів у C++.

У звичайній програмі арифметичний оператор означає **виконати дію**. У шаблонах виразів арифметичний оператор означає **побудувати вузол дерева обчислень**.

Замість повернення нового контейнера з даними, оператор повертає об'єкт-посередник, тип якого описує структуру виразу. Обчислення стає **відкладеним (lazy evaluation)**: жодне число не додається доти, доки дерево не буде приєднано до цільового контейнера через оператор присвоєння `=`.

### Перетворення виразу на дерево типів

Розглянемо вираз:

```cpp
Vector R = A + B * 2.5 + C;
```

Коли компілятор бачить цей вираз, він застосовує стандартні правила пріоритету та асоціативності операторів:
1. Спочатку конструюється вузол множення вектора `B` на скаляр `2.5`: `VecScale<Vector>`.
2. Потім конструюється лівий вузол додавання вектора `A` до результату множення: `VecAdd<Vector, VecScale<Vector>>`.
3. Нарешті конструюється правий вузол додавання результату до вектора `C`: `VecAdd<VecAdd<Vector, VecScale<Vector>>, Vector>`.

Отриманий об'єкт не містить масивів елементів. Він складається лише з двох константних посилань на підвирази та одного скалярного значення `double`. 

Зображення типу у пам'яті під час компіляції можна уявити як дерево абстрактного синтаксису (AST):

```
                   VecAdd (корінь дерева)
                  /      \
            VecAdd        Vector C (листок)
           /      \
   Vector A        VecScale
  (листок)         /      \
           Vector B        double (2.5)
           (листок)
```

Детальний розбір того, як Тодд Велдхейзен у 1995 році придумав цей механізм для обходу швидкісних обмежень C++ і як він еволюціонував до сучасних `std::ranges` у C++20, викладено в [історії виникнення шаблонів виразів](book:cpp-standards/expression-templates/hist-expression-templates.md).

## 3. Анатомія побудови шаблонів виразів через CRTP

Для уніфікації інтерфейсу всіх можливих вузлів дерева (векторів, операцій додавання, множення, транспонування) без використання повільних віртуальних функцій застосовується шаблонний паттерн **CRTP (Curiously Recurring Template Pattern)**.

### 3.1. Базовий клас CRTP: `VecExpr`

Базовий клас параметризується типом самого похідного класу `Derived`:

```cpp
template <typename Derived>
struct VecExpr {
    // Доступ до елемента за індексом через статичне приведення
    [[nodiscard]] decltype(auto) operator[](std::size_t i) const {
        return static_cast<const Derived&>(*this)[i];
    }

    // Повертає загальну кількість елементів у виразі
    [[nodiscard]] std::size_t size() const {
        return static_cast<const Derived&>(*this).size();
    }
};
```

Приведення `static_cast<const Derived&>(*this)` виконується під час компіляції. Компілятор знає точний тип `Derived`, тому виклик `operator[]` прямує безпосередньо у відповідний метод похідного класу без таблиці віртуальних функцій (`vtable`).

### 3.2. Листовий вузол: контейнер `Vector`

Клас `Vector` володіє реальними даними у пам'яті та успадковує `VecExpr<Vector>`:

```cpp
class Vector : public VecExpr<Vector> {
private:
    std::vector<double> data_;

public:
    explicit Vector(std::size_t size, double val = 0.0) : data_(size, val) {}

    // Конструктор ініціалізації з довільного виразу
    template <typename E>
    Vector(const VecExpr<E>& expr) : data_(expr.size()) {
        *this = expr;
    }

    // Оператор присвоєння — ДРАЙВЕР ОБЧИСЛЕННЯ ВЕСЬОГО ДЕРЕВА
    template <typename E>
    Vector& operator=(const VecExpr<E>& expr) {
        const E& e = static_cast<const E&>(expr);
        const std::size_t n = e.size();
        
        if (data_.size() != n) {
            data_.resize(n);
        }
        
        // Єдиний цикл усього виразу!
        for (std::size_t i = 0; i < n; ++i) {
            data_[i] = e[i];
        }
        return *this;
    }

    double operator[](std::size_t i) const { return data_[i]; }
    double& operator[](std::size_t i) { return data_[i]; }
    std::size_t size() const { return data_.size(); }
};
```

### 3.3. Вузол бінарної операції: `VecAdd`

Вузол додавання успадковує `VecExpr<VecAdd<LHS, RHS>>` та зберігає посилання на лівий і правий операнди:

```cpp
template <typename LHS, typename RHS>
class VecAdd : public VecExpr<VecAdd<LHS, RHS>> {
private:
    const LHS& lhs_;
    const RHS& rhs_;

public:
    VecAdd(const LHS& lhs, const RHS& rhs) : lhs_(lhs), rhs_(rhs) {}

    // Метод доступу обчислює суму для i-го елемента «льоту»
    double operator[](std::size_t i) const {
        return lhs_[i] + rhs_[i];
    }

    std::size_t size() const {
        return lhs_.size();
    }
};
```

### 3.4. Вузол скалярного множення: `VecScale`

Вузол скалярного множення зберігає посилання на вираз та числове значення скаляра:

```cpp
template <typename E>
class VecScale : public VecExpr<VecScale<E>> {
private:
    const E& expr_;
    double alpha_;

public:
    VecScale(const E& expr, double alpha) : expr_(expr), alpha_(alpha) {}

    double operator[](std::size_t i) const {
        return expr_[i] * alpha_;
    }

    std::size_t size() const {
        return expr_.size();
    }
};
```

### 3.5. Оператори-генератори

Оператори `+` та `*` створюють відповідні вузли дерев:

```cpp
template <typename LHS, typename RHS>
VecAdd<LHS, RHS> operator+(const VecExpr<LHS>& lhs, const VecExpr<RHS>& rhs) {
    return VecAdd<LHS, RHS>(
        static_cast<const LHS&>(lhs),
        static_cast<const RHS&>(rhs)
    );
}

template <typename E>
VecScale<E> operator*(const VecExpr<E>& expr, double alpha) {
    return VecScale<E>(static_cast<const E&>(expr), alpha);
}

template <typename E>
VecScale<E> operator*(double alpha, const VecExpr<E>& expr) {
    return VecScale<E>(static_cast<const E&>(expr), alpha);
}
```

Повний приклад працюючого рушія з реалізацією скалярного множення, віднімання та порівнянням із C-підходом міститься у [практичній реалізації DSL для векторної алгебри](book:cpp-standards/expression-templates/proj-expression-vector.md).

## 4. Каскадне розгортання та інлінінг: як це виглядає в ассемблері

Ключовим моментом продуктивності шаблонів виразів є те, як компілятор опрацьовує виклик `data_[i] = e[i]` у циклі оператора присвоєння `=`.

Розглянемо покрокове розгортання виклику `e[i]` для об'єкта типу `VecAdd<VecAdd<Vector, VecScale<Vector>>, Vector>`:

```
e[i]
= VecAdd<...>::operator[](i)
= lhs_[i] + rhs_[i]
= (VecAdd<Vector, VecScale<Vector>>)[i] + C[i]
= (A[i] + (VecScale<Vector>)[i]) + C[i]
= (A[i] + (B[i] * 2.5)) + C[i]
```

Завдяки тому, що кожен метод `operator[]` позначений як вбудований (inline) або легко піддається інлінінгу за допомогою оптимізацій GCC/Clang (`-O2`/`-O3`), компілятор розгортає весь цей каскад викликів функцій у єдиний арифметичний вираз:

```cpp
for (std::size_t i = 0; i < n; ++i) {
    R.data_[i] = A.data_[i] + B.data_[i] * 2.5 + C.data_[i];
}
```

### Доказ тотожності згенерованого коду

Сучасні компілятори розпізнають цей прямий цикл і автоматично векторизують його інструкціями SIMD (AVX2 або AVX-512 на x86-64, NEON на ARM). 

Подивіться на асемблерний вихід для GCC 13 (`-O3 -mavx2`):

```assembly
.L3:
    vmovupd (%rsi,%rax), %ymm0        ; Завантажити 4 елементи B[i..i+3] у регістр YMM0
    vmulpd  %ymm2, %ymm0, %ymm0       ; Поелементне множення на alpha (ymm2)
    vaddpd  (%rdx,%rax), %ymm0, %ymm0 ; Додати 4 елементи A[i..i+3] у регістр YMM0
    vaddpd  (%rcx,%rax), %ymm0, %ymm0 ; Додати 4 елементи C[i..i+3] у регістр YMM0
    vmovupd %ymm0, (%rdi,%rax)        ; Записати 4 результати в R[i..i+3]
    addq    $32, %rax                 ; Зсув індексу на 32 байти (4 * double)
    cmpq    %r8, %rax
    jne     .L3
```

Якщо ввімкнути прапор розширеного набору інструкцій `-mfma`, компілятор об'єднує множення та додавання в єдину процесорну інструкцію FMA (**Fused Multiply-Add**):

```assembly
.L3:
    vmovupd (%rsi,%rax), %ymm0            ; YMM0 = B[i..i+3]
    vfmadd213pd (%rdx,%rax), %ymm2, %ymm0 ; YMM0 = YMM0 * alpha + A[i..i+3]
    vaddpd  (%rcx,%rax), %ymm0, %ymm0     ; YMM0 = YMM0 + C[i..i+3]
    vmovupd %ymm0, (%rdi,%rax)            ; R[i..i+3] = YMM0
    addq    $32, %rax
    cmpq    %r8, %rax
    jne     .L3
```

Жодної проміжної функції, жодного тимчасового буфера, жодної втрати тактів. Складне дерево типів C++ повністю розчинилося під час компіляції, залишивши після себе ідеальний машинний код. Це чистий приклад абстракції з нульовою вартістю (**Zero-Cost Abstraction**).

## 5. Простеження через профілювальник (Perf & Valgrind)

Щоб переконатися у відсутності алокацій на практиці, скористаємося системними профілювальниками Linux: `Valgrind` (інструмент `Massif`) та `perf`.

### 5.1. Аналіз профілю пам'яті через Massif

При профілюванні наївного додавання `Valgrind Massif` показує три чітких піки виділення пам'яті у купі:

```
    MB
80^                                          :#
  |                                          :#
  |                                   :: : : :#
  |                            :: : : :: : : :#
  |                     :: : : :: : : :: : : :#
0 +-------------------------------------------------> time
   (Алокація T1)        (Алокація T2)       (Алокація T3)
```

При використанні шаблонів виразів профайл пам'яті залишається абсолютно пласким. Під час оцінки виразу `R = A + B + C + D` інструмент `Massif` фіксує **0 додаткових виділень пам'яті у купі** (`0 bytes allocated in 0 blocks`).

### 5.2. Аналіз подій CPU через `perf stat`

Запуск `perf stat` демонструє разичу в ефективності роботи з кеш-пам'яттю та процесорними інструкціями:

```
# 1. Наївний підхід
perf stat ./naive_vector_app
       1,450,210,040      cycles                    #    3.821 GHz
       2,120,405,100      instructions              #    1.46  insn per cycle
          18,402,110      L1-dcache-load-misses     #    4.12% of all L1-dcache hits

# 2. Шаблони виразів (Expression Templates)
perf stat ./expression_templates_app
         310,105,400      cycles                    #    3.850 GHz
       1,050,112,000      instructions              #    3.38  insn per cycle
           1,205,010      L1-dcache-load-misses     #    0.28% of all L1-dcache hits
```

Ключові показники:
1. **Кількість циклів процесора**: зменшилася майже в 5 разів (з 1.45 млрд до 310 млн).
2. **L1 D-Cache Misses**: кількість кеш-промахів першого рівня впала з 18.4 млн до 1.2 млн, що підтверджує ідеальну роботу предвибігача (Hardware Prefetcher) при злитому однопрохідному циклі.

## 6. Підводні камені та складні випадки

Попри свою ефективність, шаблони виразів мають кілька небезпечних крайових випадків, які необхідно враховувати під час проєктування виробничих бібліотек.

### 6.1. Небезпека аліасингу пам'яті (Memory Aliasing)

Розглянемо вираз додавання вектора до самого себе:

```cpp
A = A + B;
```

У цьому випадку в циклі `A[i] = A[i] + B[i]` читання з `A[i]` здійснюється до запису в `A[i]`. Оскільки елементи обчислюються незалежно за індексами `i`, така операція є абсолютно безпечною.

Проте для матричного множення ліниве обчислення створює важку помилку! Якщо спробувати обчислити матричне множення `A = A * B` через лінивий вираз:

```cpp
A[i][j] = sum_k (A[i][k] * B[k][j]);
```

то при обчисленні елемента `A[0][1]` будуть прочитані елементи `A[0][0]`, які вже були перезаписані на попередньому кроці `i=0, j=0`!

#### Рішення: Примусова оцінка `.eval()`

Бібліотеки лінійної алгебри (зокрема Eigen) розрізняють **поелементні операції** (де аліасинг нешкідливий) та **структурні операції** (матричне множення, транспонування, LU-розклад). Для структурних операцій реалізують метод примусової оцінки `.eval()`, який спочатку записує результат у тимчасовий буфер, і лише потім присвоює його цілі:

```cpp
A = (A * B).eval(); // Спочатку обчислює в temporary, потім копіює в A
```

### 6.2. Проблема висячих посилань (Dangling References) на тимчасові об'єкти

Розглянемо небезпечний сценарій використання ключового слова `auto`:

```cpp
Vector make_vector() { return Vector(100, 1.0); }

// НЕБЕЗПЕКА: висяче посилання!
auto expr = A + make_vector();
double val = expr[0]; // НЕВИЗНАЧЕНА ПОВЕДІНКА (Undefined Behavior)!
```

Що тут сталося?
1. Функція `make_vector()` повертає тимчасовий об'єкт `Vector` (prvalue).
2. Оператор `+` створює об'єкт `VecAdd`, який зберігає посилання `const Vector&` на цей тимчасовий об'єкт.
3. У кінці рядка `auto expr = ...` тимчасовий об'єкт знищується (його час життя закінчився).
4. Змінна `expr` залишається жити з висячим посиланням всередині. Спроба прочитати `expr[0]` призводить до звернення до звільненої пам'яті.

#### Рішення через Type Traits та Стратегії Зберігання

Щоб захиститися від цієї проблеми, сучасні реалізації перевіряють категорію значення операнда. Якщо операнд є lvalue (іменована змінна), вузол зберігає посилання `const T&`. Якщо операнд є rvalue (тимчасовий об'єкт), вузол зберігає об'єкт **за значенням** `T`:

```cpp
template <typename T>
struct storage_traits {
    // Якщо T це lvalue-посилання — зберігаємо const T&, інакше зберігаємо за значенням T
    using type = std::conditional_t<
        std::is_lvalue_reference_v<T>,
        const std::remove_reference_t<T>&,
        const std::remove_reference_t<T>
    >;
};
```

Повний опис типів рис, уніфікованих концептів та стратегій зберігання наведено в [довідці за інтерфейсом та рисами вузлів виразів](book:cpp-standards/expression-templates/api-expression-interface.md).

### 6.3. Роздування коду (Binary Bloat) та час компіляції

Кожен новий математичний вираз із унікальною комбінацією операторів створює новий шаблонний тип. Вираз із 10 операцій додавання та множення породжує глибоко вкладений тип завдовжки у кілька кілобайтів символьного імені (mangled name).

Це має два негативні наслідки:
1. **Зростання часу компіляції**: Компілятор витрачає значні ресурси на побудову, перевірку та інстанціювання складних дерев типів. На великих проєктах це може збільшити час збірки в рази.
2. **Символьний шлак у бінарнику**: Якщо не використовувати прапорці приховування символів (`-fvisibility=hidden`), закодовані імена сотень складних виразів потрапляють у таблицю символів об'єктних файлів, збільшуючи розмір підсумкового бінарника.

## 7. Додавання власних математичних функцій (Унарні операції)

Архітектура шаблонів виразів є легкорозширюваною. Додамо підтримку унарних математичних функцій, наприклад `sin(A)` чи `exp(A)`.

### 7.1. Вузол унарної функції `VecUnary`

```cpp
template <typename Op, typename E>
class VecUnary : public VecExpr<VecUnary<Op, E>> {
private:
    const E& expr_;
    Op op_;

public:
    VecUnary(const E& expr, Op op = Op{}) : expr_(expr), op_(op) {}

    double operator[](std::size_t i) const {
        return op_(expr_[i]);
    }

    std::size_t size() const {
        return expr_.size();
    }
};
```

### 7.2. Функція-генератор `sin`

Оголосимо функтор та операційну функцію `sin`:

```cpp
struct SinOp {
    double operator()(double x) const { return std::sin(x); }
};

template <typename E>
VecUnary<SinOp, E> sin(const VecExpr<E>& expr) {
    return VecUnary<SinOp, E>(static_cast<const E&>(expr));
}
```

Тепер розробник може писати вирази вигляду `R = sin(A) + B * 2.0;`. Вони будуть обчислені в один злитий цикл, де виклик `std::sin` підставиться безпосередньо у SIMD-інструкцію `vsinpd` (при використанні `-ffast-math`).

## 8. Сучасний C++20: Концепти замість CRTP і SFINAE

У ранньому C++ для обмеження операторів виразів доводилося використовувати SFINAE та `std::enable_if_t`, щоб оператор `+` не перехоплював додавання сторонніх типів.

З появою C++20 кодові бази шаблонів виразів стали значно лаконічнішими завдяки **концептам (Concepts)**. Замість вимогати успадкування від CRTP-бази `VecExpr`, ми можемо описати вимоги до вузла виразу безпосередньо:

```cpp
template <typename T>
concept VectorExpression = requires(const T& expr, std::size_t i) {
    { expr.size() } -> std::convertible_to<std::size_t>;
    { expr[i] }     -> std::convertible_to<double>;
};

// Простий і чистий оператор додавання без CRTP і без SFINAE
template <VectorExpression LHS, VectorExpression RHS>
auto operator+(const LHS& lhs, const RHS& rhs) {
    return VecAdd<LHS, RHS>(lhs, rhs);
}
```

Якщо припуститися помилки й спробувати додати вектор до невідповідного типу, компілятор C++20 не вивалить три сторінки непрохідних нутрощів шаблону, а чітко вкаже: `type 'int' does not satisfy concept 'VectorExpression'`.

## 9. Практичне значення в інженерії

> 🔧 **Навіщо це.**
> Шаблони виразів — це фундамент, на якому стоять усі сучасні високопродуктивні обчислювальні бібліотеки мови C++:
> - **Eigen** — провідна бібліотека лінійної алгебри, що використовується в ROS (Robot Operating System), OpenCV, TensorFlow та PyTorch C++ Frontend.
> - **Blaze** — одна з найшвидших бібліотек для матричних обчислень із високим рівнем векторизації.
> - **Ceres Solver** — бібліотека Google для вирішення задач найменших квадратів та оптимізації у тривимірній реконструкції.
> - **std::ranges (C++20)** — стандартна бібліотека конвеєрів діапазонів, що застосовує ідіому відкладеного обчислення для обробки послідовностей.
> 
> Розуміння шаблонів виразів дозволяє не лише писати власні швидкодійні DSL-обгортки, а й упевнено читати повідомлення про помилки та профілювати кодові бази, що спираються на Eigen чи `std::ranges`.

Шаблони виразів довели важливий принцип дизайну C++: **елегантний математичний синтаксис і гранична продуктивність нативного коду не є протилежностями**. Завдяки статичному аналізу типів компілятор бере на себе рутинну роботу з об'єднання циклів та усунення буферів пам'яті, звільняючи розробника для вирішення задач вищого рівня.
