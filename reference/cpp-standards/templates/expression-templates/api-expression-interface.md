# 📋 Інтерфейс та риси вузлів виразів

Дана вставка містить повний довідник типів, концептів, рис типів (type traits) та правил зберігання операндів, які утворюють публічний та внутрішній контракт бібліотек шаблонів виразів (Expression Templates).

## 1. Контракт інтерфейсу вузла виразу

Усі вузли абстрактного синтаксичного дерева (AST), що беруть участь у шаблонах виразів, повинні дотримуватися суворого контракту інтерфейсу. На відміну від класичного об'єктно-орієнтованого програмування, де контракт задається чисто віртуальними функціями базового класу, у шаблонах виразів контракт задається **статично** — через паттерн CRTP або концепти C++20.

Вузол виразу зобов'язаний надавати наступні публічні методи та типи:

1. `size()` — повертає кількість елементів у виразі (типу `std::size_t`).
2. `operator[](std::size_t i)` — повертає `i`-й елемент виразу "льоту", обчислюючи його без збереження у пам'яті.
3. `value_type` — тип елементів, які повертаються виразом (наприклад, `double`, `float` або `std::complex<double>`).

Вимоги до уніфікованого вузла виразу у C++20 формалізуються за допомогою концептів. Концепти дозволяють перевірити наявність усіх методів ще на етапі комбінування типів:

```cpp
#include <type_traits>
#include <cstddef>
#include <concepts>

// Концепт C++20, що формалізує вимоги до векторного виразу
template <typename T>
concept VectorExpression = requires(const T& expr, std::size_t i) {
    typename T::value_type;
    { expr.size() } -> std::same_as<std::size_t>;
    { expr[i] }     -> std::convertible_to<typename T::value_type>;
};
```

## 2. Довідникова таблиця вузлів та їхня складність

Нижче наведено класифікацію основних вузлів виразів, які реалізуються у промислових бібліотеках лінійної алгебри (Eigen, Blaze, Boost.uBLAS).

| Вузол виразу | Опис операції | Внутрішній стан (Поля) | Складність `operator[]` | Необхідна пам'ять |
| :--- | :--- | :--- | :--- | :--- |
| **`Vector`** | Листовий вузол (реальні дані) | `double* data_`, `size_t size_` | `O(1)` (прямий доступ) | `O(N)` |
| **`Scalar`** | Скалярний листок (число) | `double val_` | `O(1)` (повертає константу) | `O(1)` |
| **`VecAdd<LHS, RHS>`** | Поелементне додавання | `const LHS& lhs_`, `const RHS& rhs_` | `O(1)` (`lhs[i] + rhs[i]`) | 0 байтів (`O(1)`) |
| **`VecSub<LHS, RHS>`** | Поелементне віднімання | `const LHS& lhs_`, `const RHS& rhs_` | `O(1)` (`lhs[i] - rhs[i]`) | 0 байтів (`O(1)`) |
| **`VecScale<E>`** | Множення на скаляр | `const E& expr_`, `double alpha_` | `O(1)` (`expr[i] * alpha`) | 0 байтів (`O(1)`) |
| **`VecNegate<E>`** | Заперечення знаку (`-A`) | `const E& expr_` | `O(1)` (`-expr[i]`) | 0 байтів (`O(1)`) |
| **`MatMul<LHS, RHS>`**| Матричне множення | `const LHS& lhs_`, `const RHS& rhs_` | `O(K)` (скалярний добуток) | 0 байтів (ліниве) / `O(N²)` (`.eval()`) |

## 3. Риси типів (Type Traits) та Політики Зберігання

Одним із найскладніших питань при конструюванні вузлів виразів є вибір правильної політики зберігання операндів (**Storage Policy**).

### 3.1. Проблема висячих посилань (Dangling References)

Якщо вузол виразу завжди зберігає операнди за посиланням `const T&`, це працює ідеально для lvalue (іменованих змінних, на кшталт `Vector A, B;`). Проте, якщо операндом виступає тимчасовий rvalue-об'єкт (наприклад, результат фабричної функції `Vector(10, 1.0)` або проміжний скалярний вираз), тимчасовий об'єкт знищується в кінці повного виразу. Збереження посилання на нього призводить до висячого посилання та невизначеної поведінки (**Undefined Behavior**).

Розглянемо приклад помилки:

```cpp
auto make_temp() { return Vector(100, 2.0); }

// Збереження const Vector& на результат make_temp() фатальне!
auto expr = A + make_temp(); 
double v = expr[0]; // Dangling reference: пам'ять усередині make_temp() знищено!
```

### 3.2. Селектор типів зберігання `storage_traits`

Щоб уникнути цього підводного каменя, виробничі бібліотеки використовують метафункції для визначення типу поля. Якщо операнд є lvalue, зберігається константне посилання (`const T&`). Якщо операнд є rvalue, об'єкт зберігається **за значенням** (`T`):

```cpp
template <typename T>
struct expression_storage_traits {
    // Якщо T є lvalue-посиланням (наприклад, Vector&), зберігаємо const Vector&.
    // Якщо T є значенням (тимчасовим rvalue, наприклад Vector), зберігаємо за значенням Vector.
    using type = std::conditional_t<
        std::is_lvalue_reference_v<T>,
        const std::remove_reference_t<T>&,
        const std::remove_reference_t<T>
    >;
};

template <typename T>
using storage_type_t = typename expression_storage_traits<T>::type;
```

### 3.3. Приклад застосування політики у вузлі виразу

Завдяки цьому селектору вузол виразу захищений від висячих посилань незалежно від того, як його було сконструйовано:

```cpp
template <typename LHS, typename RHS>
class VecAdd {
private:
    // Автоматичний вибір: посилання для lvalue, значення для rvalue
    storage_type_t<LHS> lhs_;
    storage_type_t<RHS> rhs_;

public:
    VecAdd(LHS&& lhs, RHS&& rhs)
        : lhs_(std::forward<LHS>(lhs)), rhs_(std::forward<RHS>(rhs)) {}

    double operator[](std::size_t i) const {
        return lhs_[i] + rhs_[i];
    }

    std::size_t size() const {
        return lhs_.size();
    }
};
```

## 4. Метод примусової оцінки `.eval()` та контроль аліасингу

У деяких математичних операціях (наприклад, матричне множення `C = A·B` або транспонування `A = Aᵀ`) поелементне ліниве обчислення є неприпустимим через **аліасинг пам'яті** (Memory Aliasing), оскільки запис у `A[i][j]` модифікує вхідні дані, які ще знадобляться для обчислення наступних елементів `A[i][k]`.

### 4.1. Метод `.eval()`

Для вирішення цієї проблеми надається публічний метод `.eval()` та специфічні риси оцінки, які примусово обчислюють проміжний вираз у новий буфер:

```cpp
template <typename Derived>
class ExpressionBase {
public:
    // Примусова оцінка виразу у тимчасовий конкретний контейнер
    template <typename ConcreteContainer>
    [[nodiscard]] ConcreteContainer eval() const {
        ConcreteContainer temp(static_cast<const Derived&>(*this).size());
        temp = static_cast<const Derived&>(*this); // Викликає злитий цикл
        return temp;
    }
};
```

### 4.2. Метаінспекція аліасингу у виразах

Бібліотеки на кшталт Eigen та Blaze визначають спеціальні риси типів, що аналізують дерево типів під час компіляції та автоматично вставляють виклики `.eval()`, якщо у правій та лівій частинах оператора `=` виявлено той самий об'єкт:

```cpp
template <typename Expr>
struct needs_eval : std::false_type {};

// Матричне множення вимагає створення тимчасового буфера за замовчуванням
template <typename LHS, typename RHS>
struct needs_eval<MatMul<LHS, RHS>> : std::true_type {};

template <typename Expr>
inline constexpr bool needs_eval_v = needs_eval<Expr>::value;
```

## 5. Артефакти та типи у промисловій бібліотеці Eigen

Промислова бібліотека **Eigen** реалізує розширений варіант контракту типів. Вона будує ієрархію базових класів та спеціальних типів-обгортки для роботи з пам'яттю:

1. `Eigen::DenseBase<Derived>` — загальний базовий клас для всіх щільних матриць, векторів та виразів.
2. `Eigen::MatrixBase<Derived>` — базовий клас для двовимірних матричних виразів (підтримує `operator*` як матричне множення).
3. `Eigen::ArrayBase<Derived>` — базовий клас для поелементних масивів (підтримує `operator*` як поелементне множення).
4. `Eigen::Map<PlainObjectType>` — вузол виразу, що перетворює сирий вказівник на C-масив (`double*`) у повноцінний матричний об'єкт без копіювання пам'яті.
5. `Eigen::Ref<PlainObjectType>` — обгортка-посередник для передавання матричних виразів у функції без інстанціювання нових шаблонів (зменшує розмір бінарника).

## 6. Зв'язок з інтерфейсом C++20 Ranges та Views

Ідіома шаблонів виразів знайшла своє пряме продовження у стандартній бібліотеці C++20 у формі діапазонів (**Ranges**) та видів (**Views**).

Коли у C++20 розробник пише комбінований конвеєр опрацювання даних:

```cpp
auto result = vec | std::views::filter([](int x) { return x % 2 == 0; })
                  | std::views::transform([](int x) { return x * 2; });
```

компілятор генерує тип вида:

```cpp
std::ranges::transform_view<
    std::ranges::filter_view<
        std::ranges::ref_view<std::vector<int>>,
        Z1FilterLambda
    >,
    Z2TransformLambda
>
```

Цей об'єкт виду за своєю внутрішньою будовою є точним аналогом вузла `VecAdd` у шаблонах виразів. Він зберігає посилання на початковий контейнер та лямбда-функції, не виділяючи жодного елемента у купі. Обчислення кожної лямбди виконується тільки під час розіменування ітератора при проходженні циклом `for (auto val : result)`.

## 7. Просування типів при змішаній точності (Mixed Precision Promotion)

У математичних бібліотеках часто виникають вирази зі змішаними типами операндів, наприклад додавання вектора `float` до вектора `double` або множення вектора комплексних чисел `std::complex<double>` на скаляр `double`.

Для підтримки таких виразів вузол виразу обчислює підсумковий тип елемента за допомогою метафункції `std::common_type_t`:

```cpp
template <typename LHS, typename RHS>
class MixedVecAdd {
public:
    // Тип результату визначається як спільний тип операндів
    using value_type = std::common_type_t<
        typename LHS::value_type,
        typename RHS::value_type
    >;

private:
    const LHS& lhs_;
    const RHS& rhs_;

public:
    MixedVecAdd(const LHS& lhs, const RHS& rhs) : lhs_(lhs), rhs_(rhs) {}

    value_type operator[](std::size_t i) const {
        return static_cast<value_type>(lhs_[i]) + static_cast<value_type>(rhs_[i]);
    }

    std::size_t size() const { return lhs_.size(); }
};
```

Завдяки цьому компілятор автоматично виконує розширення типів (`float` -> `double`) безпосередньо у SIMD-регістрах під час виконання єдиного злитого циклу.

## 8. Повна класифікація рис типів (Type Traits Reference)

Нижче наведено підсумкову таблицю метафункцій, необхідних для побудови безпечного рушія виразів:

| Риса (Trait) | Значення за замовчуванням | Призначення та поведінка |
| :--- | :--- | :--- |
| `is_expression<T>::value` | `false` | Повертає `true` тільки для класів, що успадковують `VecExpr` |
| `storage_type_t<T>` | `const T&` або `T` | Обирає безпечний тип поля (посилання або значення) |
| `has_aliasing<T>::value` | `false` | Повертає `true` для матричного множення та транспонування |
| `is_pure_elementwise<T>::value` | `true` | Повертає `true` для операцій `+`, `-`, `*` (скаляр) |
| `eval_result_type<T>::type` | `T` | Тип тимчасового буфера, що створюється при виклику `.eval()` |

## 9. Порівняльна характеристика продуктів обчислень

Нижче наведено порівняльний аналіз трьох основних режимів опрацювання виразів у програмах на C++:

```
+--------------------------+-------------------+---------------------+-----------------------+
| Режим опрацювання        | Алокації пам'яті  | Кількість циклів    | Ефективність SIMD     |
+--------------------------+-------------------+---------------------+-----------------------+
| 1. Naive Overloading     | O(K · N) (Купа)   | K окремих циклів    | Низька (RAM bottleneck)|
| 2. Expression Templates  | 0 байтів (О(1))   | 1 злитий цикл       | Максимальна (AVX/FMA) |
| 3. Forced .eval()        | O(N) (1 буфер)    | 2 цикли (eval+copy) | Висока                |
+--------------------------+-------------------+---------------------+-----------------------+
```

Застосування описуваного контракту інтерфейсу та типів рис дозволяє будувати масштабовані, безпечні та високопродуктивні бібліотеки лінійної алгебри, які повністю усувають накладні витрати на абстракцію.
