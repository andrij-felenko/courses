# 📜 Історія виникнення CRTP: від трюку Бартона-Некмана до C++23

<preknowlist>
- [Шаблони: параметризація типом](topic:cpp-standards/templates-basics) — базовий синтаксис інстанціювання шаблонних класів.
- [Розв'язання перевантажень](topic:cpp-standards/overload-resolution) — правила вибору функцій компілятором під час ADL.
- [Явний параметр об'єкта](topic:cpp-standards/deducing-this) — механізм C++23, який модернізує статичний поліморфізм.
</preknowlist>

Ця історія описує, як спроба обійти обмеження розв'язання перевантажень у C++98 привела до відкриття шаблону CRTP та його тридцятилітньої еволюції в стандартній бібліотеці C++.

Виклик віртуальних методів у мові C++ завжди мав високу ціну на рівні виконання. Наприкінці 1980-х та на початку 1990-х років, коли Б'ярне Страуструп створював перші версії мови C++ (C з класичними розширеннями, а згодом компілятор Cfront), віртуальні функції були єдиним вбудованим механізмом побудови поліморфних інтерфейсів. Проте кожна віртуальна функція вимагала непрямого адресного переходу через вказівник на таблицю віртуальних функцій (`vptr` → `vtable`), не дозволяла компілятору виконувати інлайнінг у гарячих циклах обчислень та додавала додаткові 8 байтів витрат пам'яті на кожен екземпляр об'єкта для тримання адреси таблиці. У ті роки для наукових обчислень, лінійної алгебри, тривимірної графіки та системного програмування ця ціна вважалася неприйнятною. Розробники шукали спосіб винести визначення інтерфейсу й спільної поведінки в базовий клас, але зберегти прямі виклики функцій та інлайнінг, який забезпечує звичайний невіртуальний код.

Перший вирішальний крок у цьому напрямку зробили Джон Бартон (John Barton) та Лі Некман (Lee Nackman), які працювали в дослідному центрі IBM T.J. Watson Research Center над розробкою високопродуктивних числових бібліотек C++ для фізичного та математичного моделювання. У 1994 році вони випустили фундаментальну праця *«Scientific and Engineering C++: An Introduction with Advanced Techniques and Applications»*. У цій книзі автори описували складнощі розробки математичних типів (комплексних чисел, матриць, тензорів, векторів) та масове дублювання коду при реалізації операторів порівняння й арифметики.

Для вирішення проблеми генерації математичних операторів (таких як `operator!=` через вже визначений `operator==`, або `operator>` через `operator<`) вони запропонували техніку, яка пізніше увійшла до історії під назвою **трюк Бартона-Некмана** (англ. *Barton-Nackman trick*).

Ідея Бартона й Некмана полягала у використанні шаблонного базового класу, який приймав похідний клас як параметр шаблону, і всередині себе оголошував нешаблонні дружні (`friend`) функції:

```cpp
template <typename Derived>
class EqualComparable {
public:
    friend bool operator!=(const Derived& lhs, const Derived& rhs) {
        return !(lhs == rhs);
    }
};

class Complex : public EqualComparable<Complex> {
public:
    bool operator==(const Complex& rhs) const {
        return re == rhs.re && im == rhs.im;
    }
private:
    double re{0.0};
    double im{0.0};
};
```

У C++98 це вирішувало одразу дві серйозні проблеми мови того часу. По-перше, функція `operator!=` з'являлася в глобальному просторі імен тільки в момент інстанціювання `EqualComparable<Complex>`, не засмічуючи таблицю перевантажень для інших типів і не спотворюючи пошук імен. По-друге, пошук залежно від аргументів (Argument-Dependent Lookup, ADL, або пошук Кеніґа) миттєво знаходив цей оператор при порівнянні двох об'єктів `Complex`. При цьому жодного віртуального виклику не відбувалося: компілятор підставляв оператор `==` безпосередньо за місцем використання, повністю усуваючи будь-які накладні витрати пам'яті чи процесорних тактів.

У 1995 році Джим Коплієн (Jim Coplien) опублікував у часописі *C++ Report* статтю під назвою *«Curiously Recurring Template Pattern»* («Дивовижно повторюваний шаблонний візерунок»). Коплієн звернув увагу на те, що рекурсивне визначення виду `class Derived : public Base<Derived>` є не просто точковим трюком для операторів порівняння, а самостійним, надзвичайно потужним ідіоматичним візерунком, який виходить далеко за межі ідеї Бартона-Некмана. 

Джим Коплієн уперше проаналізував перенесення класичних об'єктно-орієнтованих паттернів проектування банди чотирьох (GoF — Gang of Four) у статичний вимір під час компіляції. Він довів, що такі класичні паттерни, як «Стратегія» (Strategy), «Відвідувач» (Visitor), «Команда» (Command) та «Шаблонний метод» (Template Method), можуть бути переписані через CRTP без жодної віртуальної функції. Замість збереження вказівника на інтерфейс стратегії, об'єкт отримує точний тип стратегії як параметр шаблону, а базовий CRTP-клас викликає її методи через `static_cast<Derived*>(this)`.

Коплієн систематизував застосування цієї ідіоми для чотирьох ключових інженерних завдань:

1. **Статичний поліморфізм**: виклик методів похідного класу з базового за допомогою касту `static_cast<Derived*>(this)` без використання віртуальних таблиць.
2. **Композиція міксинів**: підключення готовій функціональності до класів без збільшення розміру об'єктів у пам'яті (завдяки оптимізації порожньої бази EBO).
3. **Безинерційне видалення**: захист від непланованого поліморфного видалення об'єктів через базовий вказівник за допомогою приватностей конструкторів чи захищених деструкторів замість коштовного віртуального деструктора.
4. **Плавні інтерфейси**: побудова конфігураторів (Fluent Interfaces) зі збереженням точного типу похідного класу `Derived&` у ланцюжку викликів методів.

Саме Джим Коплієн надав цій техніці сакраментальну назву **CRTP**, яка назавжди стала загальноприйнятим терміном у всій міжнародній спільноті розробників C++.

На початку 2000-х років, із виходом праці Андрія Александреску *«Modern C++ Design: Generic Programming and Design Patterns Applied»* (2001) та бурхливим розвитком бібліотеки Boost, CRTP перетворився на один із головних інструментів шаблонного метапрограмування. Александреску поєднав CRTP із концепцією орієнтованого на політики проектування (Policy-Based Design). У цьому підході базовий клас збирається з кількох CRTP-міксинів, кожен з яких реалізує окрему політику (політику виділення пам'яті, політику синхронізації, політику серіалізації).

У бібліотеці `Boost.Operators` ідіома CRTP використовувалася для того, щоб автоматично згенерувати повну групу з кількох десятків операторів порівняння та арифметики лише на основі двох базових операторів, визначених у похідному класі. Бібліотека `Boost.Iterator` застосовувала CRTP для автоматичного проектування стандартних ітераторів (кваліфікованих за категоріями Input, Forward, Bidirectional, Random Access) через клас `boost::iterator_facade`. Без CRTP створення власного сумісного зі стандартом STL ітератора вимагало написання понад 15 ручних операторів і типів-псевдонімів; з `iterator_facade` розробникові достатньо було реалізувати лише чотири методи: `dereference()`, `equal()`, `increment()` та `decrement()`.

Бібліотека `Boost.Python` використовувала CRTP для автоматичної обгортки типів C++ у класи інтерпретатора Python без втрати продуктивності. Бібліотека `Boost.Statechart` застосовувала CRTP для побудови скінченних автоматів високої швидкодії (Finite State Machines), де кожний стан автомата представляв собою CRTP-клас. Бібліотека `Boost.Spirit` будувала високоефективні парсери контекстно-вільних граматик безпосередньо у коді C++, комбінуючи сотні CRTP-вузлів у єдиний вираз без жодного віртуального виклику.

У 2005 році Комітет зі стандартизації C++ включив CRTP у перший технічний звіт TR1 (Technical Report 1), а згодом у офіційний стандарт C++11 у формі класу `std::enable_shared_from_this<T>`. Проблема, яку вирішував цей клас, полягала в безпечному створенні `std::shared_ptr` на самого себе зсередини методу об'єкта. Якщо об'єкт просто обгортав `this` у новий `shared_ptr`, створювався другий незалежний лічильник посилань, що неодмінно призводило до подвійного звільнення пам'яті (англ. *double free*). Завдяки успадкуванню від `std::enable_shared_from_this<Derived>` базовий клас отримував можливість звертатися до існуючого блоку керування пам'яттю й повертати правильний `shared_ptr<Derived>`.

У C++20 CRTP знайшов нове дихання в бібліотеці діапазонів (Ranges), розробленій на основі праць Еріка Ніблера (Eric Niebler) та Трістана Бріндла (Tristan Brindle). Клас `std::ranges::view_interface<Derived>` використовує CRTP для того, щоб надати похідному виду (англ. *view*) багатий інтерфейс: оператори доступу за індексом `operator[]`, методи `front()`, `back()`, `empty()`, `size()` та приведення до `bool`, вимагаючи від авторів нового діапазону реалізації лише двох базових методів — `begin()` та `end()`.

Попри свою високу ефективність, класичний CRTP упродовж майже тридцяти років мав кілька суттєвих вад:
- **Важкий та громіздкий синтаксис**: написання `class Derived : public Base<Derived>` вимагало дублювання імені класу й робило ієрархії складними для читання.
- **Відсутність чіткої перевірки контрактів**: якщо програміст припускався помилки в друку й писав `class DerivedB : public Base<DerivedA>`, компілятор видавав багатоекрани про простирадла помилок інстанціювання лише всередині методів базового класу.
- **Проблема константних та тимчасових об'єктів**: для підтримки `const` і `non-const` методів доводилося або дублювати методи базового класу, або застосовувати складні шаблонні касти.

Еволюційним розв'язанням цих проблем став стандарт C++23, у якому було прийнято папір P0847R7 під назвою *«Deducing this»* (Явний параметр об'єкта) авторів P.X. Garcia, Ville Voutilainen, Sy Brand, Barry Revzin та інших. Можливість передавати сам об'єкт `this` як перший параметр функції `void foo(this Self&& self)` дозволила створювати класи-міксини без використання шаблонного успадкування й без `static_cast`. Дослідники та розробники стандартних бібліотек оцінили `deducing this` як остаточну відповідь на тридцятилітній синтаксичний борг CRTP.

Значення CRTP для всієї історії розвитку мови C++ важко переоцінити: він фундаментально довів усім розробникам системного програмного забезпечення можливість створення високорівневих модульних абстракцій без жодної плати за швидкість виконання під час роботи програми. Хоча CRTP залишається фундаментальною частиною мільйонів рядків існуючого коду C++98–C++20, у новому коді C++23 явний параметр об'єкта поступово заступає класичний CRTP у завданнях розширення інтерфейсів, стаючи новим сучасним стандартом розробки міксинів у C++.
