# 📜 Еволюція точок налаштування: від std::swap до CPO та tag_invoke

Історія розширюваності алгоритмів у C++ — це тридцятилітній пошук балансу між двома протилежними вимогами: дати користувачеві змогу підмінити алгоритм для власного типу і не дозволити випадковому коду підмінити алгоритм там, де про це ніхто не просив.

## Обобщене програмування та виклики STL у C++98

Коли Олександр Степанов (Alexander Stepanov) та Менґ Лі (Meng Lee) розробляли стандартну бібліотеку шаблонів (STL) у Hewlett-Packard Laboratories на початку 1990-х років, головною архітектурною ідеєю була фундаментальна розв'язка алгоритмів і структур даних. Алгоритм `std::sort` або `std::reverse` не мав знати внутрішньої будови конкретного контейнера чи масиву — він оперував лише концепцією ітераторів та обміном елементів.

Для обміну двох значень STL надавала базову шаблонну функцію `std::swap`, а для ітераторів — `std::iter_swap`:

```cpp
template<typename T>
void swap(T& a, T& b) {
    T temp = a;
    a = b;
    b = temp;
}
```

У мові C++98, де ще не існувало семантики переміщення (`std::move`), цей базовий шаблон виконував три повні копіювання об'єкта через конструктор копіювання та оператор присвоювання. Для простих типів на кшталт `int` або фундаментальних структур цей код працював ідеально. Проте для складних контейнерів — наприклад, `std::vector` або `std::list` з мільйоном елементів — така реалізація була катастрофою. Кожне копіювання вектора вимагало нового виділення динамічної пам'яті в купі (heap) та копіювання всіх його елементів.

Для вектора обмін мав зводитися до простого обміну трьох внутрішніх вказівників (буфер, розмір, місткість). Це операція зі складністю `O(1)`, яка виконується за кілька тактів процесора та ніколи не кидає винятків. Заради цього у `std::vector` з'явився метод-член `v1.swap(v2)`.

Але виникла глибока архітектурна проблема: як обобщений алгоритм `std::sort`, працюючи з абстрактними ітераторами, мав дізнатися, що для конкретного типу `T` існує ефективніший спосіб обміну, ніж стандартний трикроковий шаблон `std::swap`?

Першим рішенням у C++98 було створення перевантаження функції `swap` у тому ж просторі імен, де визначено тип користувача. Це сформувало найпершу точку налаштування (Customization Point) у історії C++.

## Пастка ADL та двокрокова ідіома `using std::swap`

Щоб обобщений алгоритм міг автоматично знайти та викликати користувацьку функцію `swap`, мова C++ покладалася на механізм пошуку імен, залежного від аргументів (Argument-Dependent Lookup, ADL, також відомий як пошук Кенона на честь Деніела Кенона).

Суть ADL полягає в тому, що якщо виклик функції є неповнокваліфікованим (написаним без префікса `std::`), компілятор шукає відповідне перевантаження не лише в поточному просторі імен, а й у просторах імен, до яких належать типи аргументів виклику.

Це породило знамениту двокрокову ідіому обміну (ADL swap idiom):

```cpp
template<typename T>
void my_generic_algorithm(T& a, T& b) {
    using std::swap; // 1. Вводимо std::swap у поточну область дій як фолбек
    swap(a, b);      // 2. Неповнокваліфікований виклик шукає користувацьку swap через ADL
}
```

Механізм працював за чітким сценарієм:
- Якщо для типу `T` у його власному просторі імен було оголошено функцію `swap(T&, T&)`, ADL знаходив її й компілятор обирав її як більш специфічне перевантаження.
- Якщо ж такої функції у просторі імен аргументу не існувало, ADL не знаходив кандидатів, і компілятор обирав `std::swap`, доступну завдяки директиві `using`.

Ця схема активно використовувалася понад п'ятнадцять років, але містила три фундаментальні підводні камені, які регулярно призводили до важких системних помилок:

1. **Людський фактор та випадкова відмова від ADL.** Якщо автор обобщеного алгоритму припустився найменшої описки й написав `std::swap(a, b);` замість двокрокової ідіоми, ADL вимикався повністю. Компілятор мовчки викликав загальний шаблон `std::swap`, ігноруючи високоефективну користувацьку реалізацію `a.swap(b)`. Код залишався повністю робочим, але мовчки втрачав продуктивність у сотні разів.
2. **Викрадення пошуку (ADL Hijacking).** Якщо користувач або стороння бібліотека оголошувала шаблонну функцію `swap` у своєму просторі імен з занадто широкими шаблонами (наприклад, `template<typename T> void swap(T&, T&)`), вона могла ненавмисно збігатися з аргументами з інших просторів імен. ADL знаходив чужу, непридатну функцію, що призводило до фатальних помилок компіляції або виконання зовсім іншого коду.
3. **Каскадні помилки компіляції.** Якщо тип `T` не підтримував операцію обміну (наприклад, мав видалений конструктор переміщення), помилка компіляції виникала не у місці виклику `my_generic_algorithm`, а глибоко в надрах реалізації `std::swap`, генеруючи десяток сторінок нечитабельного виводу компілятора (template instantiation cascade).

## Спеціалізація шаблонів у просторі `std`: тупиковий альтернативний шлях

У спробі уникнути примх ADL комітет C++ у стандартах C++98 та C++11 запропонував альтернативний механізм точок налаштування: явну спеціалізацію шаблонів у просторі імен `std`. Найвідомішим прикладом цієї моделі є `std::hash` та `std::numeric_limits`:

```cpp
namespace std {
    template<>
    struct hash<MyType> {
        std::size_t operator()(const MyType& obj) const noexcept {
            return std::hash<int>{}(obj.id);
        }
    };
}
```

У цій системі розробник розширював стандартну бібліотеку, відкриваючи простір імен `std` та додаючи туди явну спеціалізацію структури для свого типу. Оскільки спеціалізація структурально прив'язана до типу `std::hash<T>`, вона не потребує ADL і завжди викликається кваліфіковано: `std::hash<T>{}(val)`.

Проте спроба застосувати цю модель до функцій або операторів зазнала поразки через фундаментальні обмеження мови:

- **Заборона часткової спеціалізації функцій.** Мова C++ дозволяє часткову спеціалізацію лише для шаблонів класів та структур, але категорично забороняє її для шаблонних функцій. Спеціалізувати шаблонну функцію можна лише повністю для конкретного типу, що робить неможливим створення узагальнених спеціалізацій для шаблонів типів на кшталт `MyContainer<T>`.
- **Бруднення простору імен `std`.** Стандарт C++ встановлює жорстке правило: користувачам дозволено додавати в `std` лише спеціалізації існуючих шаблонів для своїх типів. Додавання нових функцій, методів або перевантажень у `std` вважається невизначеною поведінкою (Undefined Behavior).
- **Високе навантаження на компілятор.** Інстанціювання шаблонів класів для кожної спеціалізації створює суттєвий оверхед під час компіляції та збільшує розмір відлагоджувальної інформації.

## Пошук гармонії у C++17: від `std::size` до концепції NIEBLO

З появою C++11 та C++14 стандартна бібліотека поповнилася функціями `std::begin`, `std::end`, а у C++17 — `std::size`, `std::empty` та `std::data` (папір N4280 під авторством Ріккардо Маркандело). Вони дозволяли однотипно працювати як зі стандартними контейнерами, так і зі звичайними C-масивами:

```cpp
int arr[5] = {1, 2, 3, 4, 5};
auto sz = std::size(arr); // повертає 5
```

Проте для користувацьких типів ці функції все ще вимагали ADL і зберігали всі вразливості класичної двокрокової ідіоми.

Під час розробки експериментальної бібліотеки `range-v3` Ерік Ніблер (Eric Niebler) та Кейсі Картер (Casey Carter) усвідомили, що для бібліотеки діапазонів (Ranges TS) класична модель ADL є неприйнятною. Діапазони вимагали десятків точок налаштування (`begin`, `end`, `size`, `data`, `empty`, `rbegin` тощо), і вимога писати `using std::begin; begin(r);` для кожного виклику усередині конвеєрів виразів (pipe expressions) робила код громіздким та вразливим.

Ніблер запропонував концептуальний прорив, який отримав назву **NIEBLO** (Naming Is Essential Beside Logical Overloads або Naming Inhibiting Expressive Bad Lookup Overloads).

Фундаментальне відкриття полягало в специфіці мовного правила пошуку імен в C++: **якщо назва в кваліфікованому виклику ідентифікує об'єкт або змінну, компілятор НЕ проводить ADL для функцій з такою ж назвою**.

Замість шаблонної функції `std::begin(x)` автори створили глобальний константний об'єкт-функтор (функціональний об'єкт):

```cpp
namespace std::ranges {
    namespace __detail {
        struct __begin_fn {
            template<typename T>
            constexpr auto operator()(T&& t) const {
                // Внутрішньо контрольовано перевіряються:
                // 1. Метод t.begin()
                // 2. ADL виклик begin(t) у закритому контексті
                // 3. Запасні варіанти для C-масивів
            }
        };
    }

    inline constexpr __detail::__begin_fn begin{};
}
```

Тепер розробник описував виклик абсолютно прямо й кваліфіковано:

```cpp
auto it = std::ranges::begin(container);
```

Це прямий виклик `operator()` глобального об'єкта `std::ranges::begin`. Оскільки виклик є кваліфікованим (`std::ranges::`), компілятор не шукає функцію `begin` через ADL на рівні цього виклику. Натомість сам об'єкт `std::ranges::begin` всередині свого `operator()` проводить безпечний, ізольований і контрольований пошук потрібної реалізації.

У C++20 ця архітектурна модель була офіційно прийнята до стандарту під назвою **Customization Point Objects (CPO)** і зафіксована у розділі `[custom.mana]`.

## Революція `tag_invoke` та майбутнє точок налаштування у C++23/C++26

Незважаючи на те, що CPO у C++20 повністю вирішили проблему безпеки ADL і надали точні помилки компіляції завдяки концептам C++20, створення кожного нового CPO вимагало колосальної кількості дубльованого шаблонного коду (boilerplate).

Для кожного CPO авторам бібліотек доводилося описувати окремий тип функтора, створювати унікальну таблицю пріоритетів викликів, заводити ізольовані простори імен та прописувати власні концептуальні обмеження. Коли у C++23 розпочалася розробка стандарту асинхронного програмування `std::execution` (Sender/Receiver model, папір P2300), з'ясувалося, що архітектура вимагає понад п'ятдесят різних точок налаштування (`connect`, `start`, `set_value`, `set_error`, `set_stopped`, `get_env`, `get_scheduler` тощо).

Створення 50 окремих CPO призводило до вибухового зростання розміру коду заголовкових файлів та суттєвого уповільнення компіляції.

Льюїс Бейкер (Lewis Baker), Ерік Ніблер та Керк Шуп у папері P1895 запропонували наступний крок еволюції — патерн **`tag_invoke`**.

Ідея `tag_invoke` полягає у згортці всіх точок налаштування в **ЄДИНУ ADL-функцію**:

```cpp
// Замість пошуку десятків різних імен (connect, start, set_value...)
// ADL шукає ЛИШЕ ОДНЕ єдине ім'я: tag_invoke

template<typename Tag, typename... Args>
constexpr decltype(auto) tag_invoke(Tag&& tag, Args&&... args) noexcept;
```

У цій схемі сама точка налаштування (тег) передається як перший аргумент функції. Оскільки тип тегу є унікальним (наприклад, `std::execution::connect_t`), ADL шукає функцію `tag_invoke` у просторі імен користувацького типу, передаючи тег як маркер наміру.

У мовах C++23 та C++26 патерн `tag_invoke` розвинувся далі в напрямку використання статичних операторів виклику `static operator()` (C++23) та пропозицій уніфікованого мовного синтаксису точок налаштування (P2544 / P3055). Це завершило тридцятилітню еволюцію від простих небезпечних макросоподібних підстановок до строго типованізованих, безпечних та ефективних мовних конструкцій.
