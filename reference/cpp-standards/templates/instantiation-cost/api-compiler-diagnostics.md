# 📋 Довідник прапорців та інструментів діагностики інстанціації компіляторів GCC, Clang і MSVC

Цей довідник містить систематизований перелік прапорців компіляції, діагностичних опцій, прагм та макросів препроцесора для керування неявною та явною інстанціацією шаблонів, лімітами рекурсії, обмеженнями SFINAE й виводом профілю компіляції в компіляторах GCC, Clang та Microsoft Visual C++ (MSVC).

## 1. Прапорці контролю інстанціації та згортання коду

У даному розділі деталізовано системні прапорці компіляції, які регулюють глибину синтаксичного розгортання шаблонів, правила неявної компіляції та ліміти діагностичних повідомлень при виявленні помилок у шаблонах.

| Прапорець компілятора | Компілятор | Призначення та діапазон значень | Замовчуване значення |
| :--- | :--- | :--- | :--- |
| `-ftemplate-depth=N` | GCC, Clang | Задає максимальну глибину рекурсивного розгортання шаблонів класів та функцій. | `1024` (Clang/GCC) |
| `/ftemplate-depth=N` | MSVC | Задає максимальну глибину рекурсивної інстанціації шаблонів у MSVC (починаючи з VS 2019). | `1024` |
| `-fno-implicit-templates` | GCC, Clang | Відключає неявну інстанціацію шаблонів. Вимагає явного `template class` для кожної спеціалізації. | Відключено (неявна дозволена) |
| `-fno-implicit-inline-templates` | GCC | Забороняє випромінювати неявні інстанціації inline-функцій шаблонів, якщо вони не викликаються у файлі. | Відключено |
| `-ftemplate-backtrace-limit=N` | GCC, Clang | Задає максимальну кількість рівнів каскаду шаблонів у повідомленнях про помилки SFINAE/Concepts (`0` — без обмежень). | `10` (Clang) / `10` (GCC) |
| `/diagnostics:caret` | MSVC | Вмикає покажчик рядка та розширену ієрархію інстанціації у виводі помилок MSVC. | Ввімкнено початково |
| `-fconcepts-diagnostics-depth=N` | GCC, Clang | Глибина деталізації під час невдалої перевірки обмежень C++20 Concepts. | `1` |

### Деталізований опис поведінки прапорців інстанціації

Прапорець `-ftemplate-depth=N` контролює граничну глибину рекурсії при інстанціації шаблонів типів і функцій. Якщо рекурсивний метаалгоритм (наприклад, обчислення числа Фібоначчі або розгортання `std::tuple`) перевищує вказаний поріг `N`, компілятор зупиняє роботу із зазначенням помилки `template instantiation depth exceeds maximum`. У ранніх версіях GCC за замовчуванням використовувалося значення 17, у C++11 його було збільшено до 256, а в сучасних компіляторах Clang та GCC стандартним є поріг 1024. Збільшення цього значення до 2048 чи 4096 виправдане лише для складної метаматематики, але при цьому суттєво зростає ризик вичерпання стеку компілятора.

Прапорець `-fno-implicit-templates` переводить компілятор у режим суворого контролю інстанціацій. У цьому режимі компілятор повністю відключає неявне розгортання шаблонів при їх використанні. Якщо розробник забуде вказати явну інстанціацію `template class my_container<int>;` у якомусь об'єктному модулі, компонувальник поверне помилку незадоволеного зовнішнього символу (`undefined reference`). Цей прапорець активно використовується в строго контрольованих вбудованих системах (embedded C++) для запобігання випадковому розростанню бінарного коду.

Прапорець `-ftemplate-backtrace-limit=N` вирішує проблему надмірного обсягу консольного виводу при помилках підстановки. За замовчуванням при помилці в глибоко вкладеному шаблоні (наприклад, у бібліотеці `std::ranges` або `Boost.Spirit`) компілятор генерує до 10 рівнів деталізації того, як саме створювався кожен тип. Встановлення значення `0` дозволяє побачити повне дерево інстанціації без зрізання, а встановлення значення `1` або `3` лишає лише найважливіші верхівкові виклики.

Прапорець `-fno-implicit-inline-templates` використовується у компіляторі GCC для запобігання генерації коду шаблоних inline-функцій у випадках, коли вони лише оголошені, але не викликаються безпосередньо в даній одиниці компіляції. Це дозволяє зекономити час генератора коду та зменшити обсяг об'єктних файлів у великих проектах.

Опція `/diagnostics:caret` компілятора MSVC вмикає візуальний індикатор (символ `^`), який показує точне місце виникнення помилки підстановки типів всередині складної шаблоної конструкції. У поєднанні з прапорцем `/diagnostics:column` це значно прискорює пошук помилок у метакоді.

Параметр `/Zc:twoPhase-` у MSVC вимикає суворий двофазний пошук імен (Two-Phase Name Lookup), повертаючи застарілий режим обробки шаблонів. Використання цього прапорця не рекомендується у сучасному коді, оскільки воно порушує сумісність зі стандартом ISO C++ і маскує помилки розпізнавання типів на першій фазі.

Опція `-Wtemplates` у компіляторі GCC вмикає додаткові попередження щодо невизначених або неявних інстанціацій, допомагаючи інженерам виявляти відсутні `extern template` у бібліотечному коді.

Додатково прапорець `-Wno-template-id-cdtor` дозволяє відключити застарілі застереження про синтаксис конструкторів шаблонів у застарілих стандартних кодових базах C++98.

## 2. Прапорці хронометражу та профілювання компіляції

Інструменти вимірювання часу інстанціації надають дані про витрати ресурсів процесора та оперативної пам'яті на етапах препроцесингу, синтаксичного розбору та кодогенерації.

| Прапорець / Опція | Компілятор | Формат виводу | Опис і застосування |
| :--- | :--- | :--- | :--- |
| `-ftime-trace` | Clang 9+, GCC 14+ | JSON (Chrome Tracing) | Створює файл `.time-trace` із мікросекундним профілем фаз FrontEnd, BackEnd, `InstantiateClass` та `InstantiateFunction`. |
| `-ftime-trace-granularity=N` | Clang | Число (мікросекунди) | Мінімальний поріг тривалості події (у мкс), що потрапляє у JSON-трасування. За замовчуванням `500` мкс. |
| `-ftime-report` | GCC, Clang | Текстовий звіт (stderr) | Виводить консольну таблицю з розбивкою часу за фазами компіляції (Passes), синтаксичним аналізом та інстанціацією. |
| `/ftime` | MSVC | Текстовий лог (stdout) | Виводить деталізований час виконання кожної фази компілятора MSVC (`c1xx.dll` та `c2.dll`). |
| `/bt` | MSVC | Консольний вивід | Виводить час компіляції кожного заголовочного файлу та шаблону (C++ Build Timing). |
| `/d2cgsummary` | MSVC | Консольний вивід | Виводить підсумкову статистику генератора коду MSVC (BackEnd code generation summary). |

### Механіка функціонування трасування `-ftime-trace`

Опція `-ftime-trace` у компіляторі Clang викликає вбудований хронометр для кожної внутрішньої функції синтаксичного аналізатора та генератора коду. Під час виконання компілятор формує в пам'яті хронологічну магістраль подій, де кожна інстанціація шаблону реєструється як інтервал часу з мікросекундною точністю.

Параметр `-ftime-trace-granularity=N` дозволяє відфільтрувати надто дрібні події. За замовчуванням поргом є 500 мікросекунд (0.5 мс). Якщо інстанціація шаблону тривала 120 мікросекунд, вона не потрапить до підсумкового JSON-файлу, щоб запобігти розростанню самого файлу трасування до багатьох гігабайт на великих проектах. Налаштування даного параметра на `100` мкс корисне для пошуку точкових затримок у легких шаблонах.

Прапорець `-ftime-report` у GCC та Clang друкує підсумкову текстової таблицю у потік помилок `stderr`. У цій таблиці відображається відсотковий розподіл часу між препроцесором, виведенням типів `template instantiation`, оптимізаціями на рівні проміжних представлень (SSA/LLVM IR) та генерацією інструкцій для цільового процесора.

Опція `/ftime` у MSVC виводить статистику внутрішніх фаз компілятора Microsoft. Фаза `c1xx.dll` відповідає за C++ FrontEnd (розбір заголовочних файлів, підстановка шаблонів, перевірка типів), а фаза `c2.dll` — за BackEnd генерацію машинного коду та оптимізації. Якщо левова частка часу витрачається у `c1xx.dll`, це прямо вказує на навантаження від шаблонів та заголовочних файлів.

Опція `/d2cgsummary` у MSVC надає поглиблену статистику оптимізатора коду BackEnd. Вона показує кількість згенерованих байт машинного коду для кожного інстанційованого методу класу, що дозволяє швидко виявляти шаблони, які створюють найбільший `Code Bloat`.

Крім того, прапорець `-Rmodule-build` у Clang виводить сповіщення препроцесора під час первинної збірки та інстанціації модульних інтерфейсів C++20, що дозволяє контролювати перезбірку кешованих бінарних модулів (BMI).

Прапорець `-fdiagnostics-format=json` у компіляторі GCC 10+ виводить усі повідомлення про помилки та деталі інстанціації у форматованому структурованому вигляді JSON, що дозволяє інтегрувати їх у середовища розробки (IDE) та аналітичні приладові панелі.

Також у системі MSVC доступна внутрішня опція `/d1reportAllClassLayout`, яка виводить у консоль точну геометрію полів та байтове зміщення (offsets) для всіх розгорнутих спеціалізацій шаблонних класів, допомагаючи діагностувати проблеми вирівнювання пам'яті.

## 3. Прагми компілятора для локального контролю інстанціації

Для вибіркового відключення сповіщень про розростання шаблонів або керування експортом інстанціацій у заголовочних файлах використовуються директиви препроцесора.

### Clang та GCC Pragmas

```cpp
// Тимчасове збільшення або зменшення межі глибини шаблонів (Clang)
#pragma clang diagnostic push
#pragma clang diagnostic ignored "-Wundefined-func-template"

// Приглушення попереджень про відсутність явної інстанціації
#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wtemplate-id-cdtor"

// Повернення попередніх налаштувань
#pragma clang diagnostic pop
#pragma GCC diagnostic pop
```

Директиви `#pragma clang diagnostic` та `#pragma GCC diagnostic` дозволяють локально локалізувати попередження компілятора, викликані шаблонами. Це особливо важливо при розробці бібліотек, які включають треті заголовочні файли з глибокими інстанціаціями, де неможливо змінити вихідний код.

### MSVC Pragmas

```cpp
// Приглушення попереджень MSVC щодо експорту шаблонних класів у DLL (C4251)
#pragma warning(push)
#pragma warning(disable: 4251) // class 'A<T>' needs to have dll-interface

template <typename T>
class __declspec(dllexport) DllExportedBuffer {
    // ...
};

#pragma warning(pop)
```

Директива `#pragma warning(disable: 4251)` у компіляторі MSVC приглушує відоме попередження про експорт екземплярів шаблонних класів через межі динамічних бібліотек (`DLL`). Оскільки кожна DLL у Windows має власну CRT-зону пам'яті, неявна інстанціація шаблонів між DLL вимагає обережного використання `extern template` та прагм експорту.

Також у MSVC використовується директива `#pragma component(mintypeinfo, on/off)`, яка локально регулює обсяг генерованої метаінформації RTTI для шаблонних класів, зменшуючи підсумковий розмір таблиць типів у бінарному файлі.

## 4. Системні макроси перевірки можливостей компілятора (Feature Testing)

Стандартні макроси перевірки можливостей дозволяють писати кросплатформений код з урахуванням підтримки концептів, `extern template` та модулів C++20:

```cpp
// Перевірка підтримки явного контролю інстанціації (C++11 extern template)
#if __cplusplus >= 201103L
    #define HAS_EXTERN_TEMPLATE 1
#endif

// Перевірка підтримки C++20 Concepts для скорочення вартості SFINAE
#if defined(__cpp_concepts) && __cpp_concepts >= 201907L
    #define HAS_CPP20_CONCEPTS 1
#endif

// Перевірка підтримки модулів C++20
#if defined(__cpp_modules) && __cpp_modules >= 201907L
    #define HAS_CPP20_MODULES 1
#endif
```

Використання цих макросів дозволяє розробникам будувати умовні конфігурації компіляції. Якщо компілятор підтримує C++20 Concepts (`__cpp_concepts`), бібліотека обирає перевірку обмежень через `requires`-clauses, яка виконується миттєво. Якщо ж код збирається застарілим компілятором C++14, виконується резервний перехід на `std::enable_if_t`, що гарантує сумісність ціною тривалішої збірки.

## 5. Довідник виклику Clang Build Analyzer та інтерпретації помилок

Інструмент `clang-build-analyzer` обробляє трасування `-ftime-trace` і генерує звіт зі структурованими секціями.

### Детальний опис аналітичних секцій звіту

1. **Expensive Headers:** Заголовочні файли, які сумарно вимагали найбільше часу для сканування та розбору між усіма файлами проекту. Цей список показує, які заголовки мають найбільший коефіцієнт повторного включення й потребують рефакторингу або переведення на `Pimpl` чи C++20 Modules.
2. **Expensive Templates:** Шаблони класів/функцій із найбільшою сумарною тривалістю `InstantiateClass` / `InstantiateFunction`. Вони є першочерговими кандидатами на застосування `extern template` або нешаблонної основи (Non-template Base Idiom).
3. **Template Instantiations:** Конкретні інстанціації типів (наприклад, `std::unordered_map<std::string, std::variant<...>>`), чий час інстанціації перевищив порівняльні ліміти. Зазвичай це надто складні класи метапрограмування з глибокою вкладеністю типів.
4. **Global Variables & Initializers:** Час, витрачений на генерацію конструкторів глобальних шаблонних об'єктів під час старт-апу та компіляції.

### Статичний аналіз та правила Clang-Tidy для шаблонів

Для автоматизованого пошуку неоптимальних шаблонних конструкцій доцільно застосовувати статичний аналізатор `clang-tidy` з наступним набором перевірок:

- `modernize-use-constraints`: пропонує автоматичну заміну старих виразів `std::enable_if_t` на концептуальні обмеження C++20 Concepts, що суттєво прискорює фазу підстановки типів.
- `performance-move-const-arg`: знаходить випадки, коли у шаблонну функцію передається `const T&`, який неможливо перемістити, запобігаючи генерації марних шаблонних обгорткових функцій.
- `readability-redundant-smartptr-get`: виявляє дубльовані виклики `get()` у шаблонних розумних вказівниках, зменшуючи складність синтаксичного дерева AST.

### Типові діагностичні повідомлення компілятора та методи розв'язання

#### Помилка: Перевищення межі глибини рекурсії шаблону

- **GCC/Clang:** `error: template instantiation depth exceeds maximum of 1024 (use '-ftemplate-depth=' to increase)`
- **MSVC:** `fatal error C1202: recursive type or function dependency context too complex`
- **Причина виникнення:** Рекурсивна інстанціація метафункції (наприклад, `TupleSearch<N-1>`) не знайшла базового випадку спеціалізації або утворила нескінченний цикл у типах під час спроби обчислити виразовий тип.
- **Спосіб розв'язання:** Перевірити наявність базової спеціалізації для `N=0`, переписати рекурсію на згортання виразів (`fold expressions` у C++17) або тимчасово збільшити ліміт прапорцем `-ftemplate-depth=2048`.

#### Помилка: Розростання списку помилок SFINAE (Backtrace Explosion)

- **GCC/Clang:** `note: in instantiation of function template specialization ... required from here` (і далі десятки рядків стеку)
- **Причина виникнення:** Невдале перевантаження функції серед десятків кандидатів із заплутаними виразами `std::enable_if`. Компілятор виводить увесь ланцюг спроб підстановки для кожного відкинутого кандидата.
- **Спосіб розв'язання:** Обмежити глибину виводу прапорцем `-ftemplate-backtrace-limit=5` або замінити SFINAE на `requires`-clause у C++20 Concepts, яка відсікає невідповідних кандидатів на самому початку перевірки підпису.

#### Помилка: Вичерпання оперативної пам'яті компілятора (OOM during compilation)

- **GCC/Clang:** `fatal error: out of memory allocating ... bytes` / `Killed (signal 9)`
- **MSVC:** `fatal error C1060: compiler is out of heap space`
- **Причина виникнення:** Генерація колосального абстрактного синтаксичного дерева (AST) через одночасну інстанціацію тисяч складних шаблонів у великій одиниці компіляції.
- **Спосіб розв'язання:** Розбити великий файл `.cpp` на кілька менших одиниць компіляції, розділити заголовочні файли на дрібніші модулі або застосувати `extern template` для винесення інстанціацій у окремі об'єктні файли.

## 6. Протоколи порівняльного моніторингу часу збірки

Для побудови системи моніторингу часу компіляції на серверах CI/CD рекомендується використовувати наступний сценарій опитування прапорців компіляції:

```bash
#!/usr/bin/env bash
# Скрипт автоматичної перевірки відхилень часу компіляції
set -euo pipefail

BUILD_DIR="build_ci"
REPORT_FILE="time_report.txt"

# 1. Збірка з трасуванням
cmake -B "${BUILD_DIR}" -G Ninja -DCMAKE_CXX_FLAGS="-ftime-trace"
clang-build-analyzer --start "${BUILD_DIR}"
ninja -C "${BUILD_DIR}"
clang-build-analyzer --stop "${BUILD_DIR}" "${REPORT_FILE}"

# 2. Перевірка наявності важких інстанціацій
if grep -q "Expensive Templates" "${REPORT_FILE}"; then
    echo "[CI WARNING] Found heavy template instantiations in build report!"
    head -n 30 "${REPORT_FILE}"
fi
```

Даний протокол дозволяє команді розробників отримувати сповіщення в автоматичному режимі, запобігаючи неконтрольованому зростанню часу збірки проекту.

### Порівняльна таблиця засобів аналізу інстанціації

| Інструмент аналізу | Організація розробки | Переваги | Обмеження |
| :--- | :--- | :--- | :--- |
| `Clang Build Analyzer` | Open Source (C++) | Швидкий звіт, групування за шаблонами | Працює лише з Clang `-ftime-trace` |
| `Speedscope` | Web / JS | Гнучкі Flame-graphs, деталізація викликів | Потребує завантаження JSON вручну |
| `Build Insights` | Microsoft (VS 2019+) | Глибока інтеграція з MSVC, C++ Event Tracing | Працює виключно у Windows / MSVC |
| `Ninja -t browse` | Open Source | Показує граф залежностей файлів | Не показує час інстанціації шаблонів |

### Архітектурні прапорці прискорення інстанціації у великих проектах

Впровадження сучасних прапорців оптимізації компілятора дозволяє системно зменшити навантаження на підсистему інстанціації у великих кодових базах:

- `-fno-elide-type`: у компіляторі Clang скасовує скорочення імен типів у діагностичних повідомленнях, що необхідно для глибокого вивчення канонічних спеціалізацій шаблонів.
- `-fvisibility-inlines-hidden`: ховає символи шаблонів та inline-функцій із таблиці динамічного експорту shared-бібліотек, знижуючи час завантаження динамічних модулів у Linux/macOS.
- `/Gy` (Enable Function-Level Linking) у MSVC: змушує компілятор упаковувати кожну шаблонну функцію в окрему COMDAT-секцію, що дозволяє компонувальник видаляти невикористовувані спеціалізації під час збірки з прапорцем `/OPT:REF`.

Використання цих прапорців у комбінації із заголовочною гігієною дозволяє отримати максимальну швидкість збірки проекту без втрати продуктивності виконання під час запуску програми.

### Додаткові діагностичні прапорці MSVC та GCC для детального аудиту

Для інженерів, які працюють над оптимізацією збірки комерційних систем у MSVC, корисним є прапорець `/d1PP` (Preprocess to File with Line Numbers), який дозволяє візуалізувати розгорнутий препроцесором текстовий потік шаблонного класу з відновленими номерами рядків вихідних заголовочних файлів.

У компіляторі GCC прапорець `-fmem-report` друкує вичерпний звіт про споживання оперативної пам'яті купи (Heap Allocation Report) для кожного внутрішнього класу AST, дозволяючи точно встановити, скільки мегабайт витрачено на спеціалізації конкретного шаблону. Крім того, опція `-Wuseless-cast` допомагає знаходити нерелевантні перетворення типів усередині шаблонних функцій.

Своєчасна інтеграція цих діагностичних засобів у робочий процес команди дозволяє уникнути деградації компіляційної швидкості на всіх стадіях розробки C++ систем, забезпечуючи швидкий зворотний зв'язок при розробці складних програмних продуктів. Система автоматизованого моніторингу за допомогою `clang-build-analyzer` надає інженерам об'єктивні метрики для обґрунтованого прийняття рішень щодо проведення рефакторингу шаблонів. Регулярний аналіз логів профілювання гарантує підтримку стабільно високого темпу розробки. Систематичне дотримання цих рекомендацій мінімізує витрати на підтримку шаблонів у великих програмних комплексах, роблячи процес розгортання метакоду прозорим та повністю керованим. Комплексне застосування прапорців діагностики дає розробникам повний контроль над тривалістю збірки, якістю метапрограмування та стабільністю проектного коду.
