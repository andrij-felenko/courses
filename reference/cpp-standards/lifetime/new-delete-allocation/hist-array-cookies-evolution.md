# 📜 Історія еволюції операторів виділення масивів та array cookies

Однією з найбільш повчальних історій еволюції мови C++ є шлях розвитку операторів виділення та знищення масивів об'єктів. Від перших експериментів Б'ярна Страуструпа у трансляторі Cfront до сучасних стандартів C++14 та C++20 механізм керування пам'яттю масивів пройшов шлях від небезпечного ручного вказування розміру до стандартизованих префіксних заголовків (Array Cookies), спеціалізованих деструкторів компілятора та автоматизованого розмірного видалення (Sized Deallocation).

Ця історія демонструє фундаментальний принцип розвитку системного програмування: будь-яка відповідальність, покладена на пам'ять розробника, рано чи пізно перетворюється на критичну вразливість, тому компілятор і ABI мають брати облік розмірів на себе.

## 1. Ранні роки Cfront: синтаксис `delete[size] ptr`

Наприкінці 1980-х років у мові «C with Classes» та перших версіях Cfront (1.0–1.2) не існувало окремих операторів `new[]` та `delete[]`. Усі динамічні виділення виконувалися через єдиний оператор `new`.

Коли виділявся масив складних об'єктів із нетривіальними деструкторами, виникала принципова проблема: транслятор генерував код для послідовного виклику конструкторів кожного елемента, але як деструктор мав дізнатися, скільки саме ітерацій потрібно виконати під час звільнення?

У Cfront 1.0 розробники вирішили цю проблему найпростішим для компілятора, але найнебезпечнішим для програміста шляхом — вимагаючи **явно передавати кількість елементів у квадратних дужках оператора delete**:

```cpp
// Синтаксис Cfront 1.0 (застарілий)
String* names = new String[10];

// Розробник був зобов'язаний вручну повторити кількість елементів:
delete[10] names;
```

### Чому ручний розмір призвів до катастрофи надійності

Покладання підрахунку кількості елементів на людину спричинило хвилю важковиправних багів у реальних кодових базах:

1. **Помилка розсинхронізації розмірів (Size Mismatch):** якщо розробник змінював виділення з `new String[10]` на `new String[20]`, але забував оновити вираз `delete[10] names`, останні 10 об'єктів залишалися живими, а їхні деструктори не викликалися ніколи, викликаючи тихі витоки файлових дескрипторів, сокетів та пам'яті.
2. **Розпад пам'яті через завищений лічильник (Destruction of Garbage):** якщо у виразі `delete[100] names` передавалося число, більше за реальний розмір масиву, компілятор намагався викликати деструктори над неініціалізованими байтами сусідніх блоків пам'яті, що призводило до негайного падіння програми (Segmentation Fault).
3. **Втрата інформації про розмір у функціях:** якщо покажчик передавався у допоміжну функцію очищення `void cleanup(String* arr)`, ця функція не мала жодного способу дізнатися оригінальну довжину масиву без передачі додаткового лічильника окремим параметром.

## 2. Поява Array Cookies у Cfront 2.0 та ARM

У 1990 році Б'ярн Страуструп разом із Марґарет Елліс опублікували фундаментальну працю *The Annotated C++ Reference Manual* (ARM), яка заклала основу майбутнього стандарту ISO/IEC 14882:1998.

У Cfront 2.0 синтаксис було спрощено: квадратні дужки стали порожніми `delete[] ptr;`. Компілятор узяв на себе обов'язок самостійно зберігати лічильник виділених елементів.

Щоб реалізувати це без змін у форматі покажчиків (зберігаючи розмір `sizeof(T*)` рівним точно одному машинному слову), творці C++ винайшли концепцію **Array Cookie** (заголовка масиву):

* Під час виконання виразу `new T[N]` компілятор замовляє у системного алокатора блок розміром `sizeof(size_t) + N * sizeof(T)`.
* У перші байти виділеної ділянки записується число `N`.
* Клієнту повертається адреса, зміщена на розмір службового заголовка: `return raw_ptr + sizeof(size_t)`.
* Під час виконання виразу `delete[] ptr` компілятор зчитує лічильник зі зміщенням `ptr - sizeof(size_t)`, викликає `N` деструкторів у зворотному порядку та передає оригінальну адресу `raw_ptr` у системну функцію `operator delete[]`.

## 3. Стандартизація в Itanium C++ ABI

На початку 2000-х років консорціум провідних розробників компіляторів (HP, Intel, IBM, SGI, GNU) створив *Itanium C++ ABI*, який згодом став де-факто стандартом для систем Linux, macOS, FreeBSD, Android та iOS на всіх архітектурах (x86-64, ARM64, RISC-V, MIPS).

Itanium ABI чітко зафіксував правила розташування та формату Array Cookie:

1. **Розмір кукі:** для 64-бітних архітектур заголовок масиву займає рівно 8 байтів (`std::size_t`).
2. **Вирівнювання корисного навантаження:** якщо тип `T` має вимогу до вирівнювання, що перевищує `sizeof(size_t)` (наприклад, `alignas(16)` або `alignas(32)`), компілятор додає вирівнювальне заповнення (padding) між кукі та першим елементом масиву:

```
┌────────────────────────┬─────────────────────┬────────────────────────────────────┐
│ Array Cookie (8B)      │ Padding (до кратності│ Масив об'єктів T[0], T[1]...      │
│ [елементів = N]        │ alignof(T))         │ (адреса, що повертається у код)    │
└────────────────────────┴─────────────────────┴────────────────────────────────────┘
▲                                              ▲
│                                              │
Початок виділення (raw_ptr)                    Користувацька адреса (user_ptr)
```

## 4. Підхід Microsoft Visual C++ ABI: Vector Deleting Destructor

Компілятор Microsoft Visual C++ (MSVC) пішов власним шляхом реалізації деструкції масивів. Замість генерації зовнішнього циклу знищення у місці виклику `delete[]`, MSVC вбудовує спеціальну допоміжну функцію безпосередньо у таблицю віртуальних методів (vtable) або генерує синтетичний метод — **Vector Deleting Destructor**:

* У MSVC vtable деструктор приймає прихований цілочисельний прапорець (наприклад, `void* T::`scalar deleting destructor`(unsigned int flags)`).
* Якщо прапорець містить біт `0x01`, деструктор після знищення полів викликає `operator delete(this)`.
* Якщо виставляється біт `0x02`, метод розуміє, що покажчик вказує на масив об'єктів (`vector deleting destructor`). Він зчитує Array Cookie за адресою `this - 4` (на 32-бітних) або `this - 8` (на 64-бітних), виконує цикл викликів деструкторів для всіх елементів масиву у зворотному порядку, а потім звільняє весь вихідний блок через `operator delete[]`.

Ця архітектурна відмінність між Itanium ABI та MSVC ABI є однією з головних причин бінарної несумісності C++ бібліотек між різними компіляторами.

## 5. Чому поліморфні масиви лишилися невирішеною проблемою

Попри автоматизацію підрахунку елементів через Array Cookies, динамічні масиви зберегли фундаментальну проблему безпеки типів: **поліморфне видалення масивів похідних класів через покажчик на базовий клас**.

Якщо розробник виконує:

```cpp
struct Base { virtual ~Base() = default; int b; };
struct Derived : Base { int extra_data[10]; };

Base* array = new Derived[10];
delete[] array; // Невизначена поведінка (Undefined Behavior)!
```

Навіть за наявності віртуального деструктора `delete[]` призводить до фатальної помилки розпаду пам'яті. Причина криється у тому, що Array Cookie зберігає лише **кількість елементів** `N`, але **не зберігає крок індексації** (stride / element size).

Компілятор, генеруючи цикл за покажчиком типу `Base*`, обчислює адресу `i`-го елемента як `array + i * sizeof(Base)`. Але оскільки реальні об'єкти мають розмір `sizeof(Derived)`, починаючи з другого елемента покажчик потрапляє у середину об'єкта `Derived[0]`, руйнуючи vptr та пам'ять процесу. Комітет зі стандартизації C++ свідомо відмовився від збереження розміру елемента у заголовку масиву, оскільки це подвоїло б оверхед Array Cookie для кожного масиву у програмі.

## 6. Оптимізація нульових витрат: виняток для тривіальних типів

Одним із головних наріжних каменів філософії C++ є принцип нульових накладних витрат (Zero-overhead Principle): те, чим ви не користуєтесь, не повинно коштувати вам жодного такту процесора чи байта пам'яті.

Якщо тип `T` є **тривіально деструктованим** (англ. *trivially destructible*), тобто є вбудованим скалярним типом (`int`, `double`, `char*`) або структурою C-стилю без явного деструктора (`std::is_trivially_destructible_v<T> == true`), операція `delete[]` взагалі не потребує виклику жодних деструкторів.

Тому стандарти C++ та Itanium ABI дозволяють компілятору повністю усувати Array Cookie для тривіальних типів:

```cpp
// Trivially destructible: Cookie НЕ створюється!
// Виділяється рівно 4000 байтів, адреса повертається без зміщення
int* numbers = new int[1000];
delete[] numbers;

// Non-trivial destructor: Cookie ОБОВ'ЯЗКОВЕ!
// Виділяється 8 (cookie) + 1000 * sizeof(std::string) байтів
std::string* strings = new std::string[1000];
delete[] strings;
```

Ця оптимізація забезпечує повну двійкову сумісність масивів примітивних типів між кодом на мовах C та C++: масив `new int[N]` виділяє точно такий самий неперервний блок байтів, як і виклик `malloc(N * sizeof(int))`.

## 7. Повернення розміру: Sized Deallocation у C++14

Через двадцять п'ять років після скасування синтаксису `delete[size]` концепція передачі розміру об'єкта під час видалення повернулася у мову — але вже на абсолютно новому якісному рівні надійності.

У C++14 пропозиція Лорана Сансонетті та фахівців Google стандартизувала розмірне звільнення **Sized Deallocation**:

```cpp
void operator delete(void* ptr, std::size_t size) noexcept;
void operator delete[](void* ptr, std::size_t size) noexcept;
```

На відміну від застарілого підходу Cfront 1.0, розробнику більше не потрібно писати розмір вручну у сирцевому коді. Компілятор сам обчислює точний розмір під час компіляції виразу `delete ptr` і автоматично передає його другим аргументом у функцію `operator delete`.

Сучасні розподільники пам'яті (tcmalloc, jemalloc, mimalloc) використовують цей переданий розмір для миттєвого пошуку потрібного розмірного класу (Size Class Bin) без необхідності зчитувати службові заголовки з пам'яті, що дає прискорення операцій деалокації до 15–20% у масштабі високонавантажених серверів.

## 8. Занепад сирих масивів у сучасному C++

У сучасному C++ (C++11/14/20) пряме використання виразів `new T[N]` та `delete[] arr` вважається застарілою практикою (code smell). На зміну їм прийшли безпечні абстракції:

* **`std::vector<T>`:** динамічний масив із динамічним масштабуванням, де розмір і місткість зберігаються явно в об'єкті вектора на стеку, а не у прихованих префіксах купи.
* **`std::make_unique<T[]>(N)`:** створює динамічний масив фіксованого розміру під керуванням RAII-обгортки `std::unique_ptr<T[]>`, яка автоматично генерує коректний виклик `delete[]`, повністю виключаючи витоки пам'яті при виникненні винятків.
* **`std::span<T>` (C++20):** надає неволодіюче вікно перегляду неперервної послідовності елементів без накладних витрат і без виділення пам'яті.

Завдяки цим типам сучасний прикладний розробник практично ніколи не стикається з сирими Array Cookies безпосередньо, залишаючи цей механізм внутрішньою деталлю реалізації компіляторів та низькорівневих системних бібліотек.

## Підсумкова хронологія еволюції

| Рік / Етап | Синтаксис | Механізм збереження розміру | Наслідки та ризики |
| :--- | :--- | :--- | :--- |
| **1985 (Cfront 1.0)** | `delete[N] ptr;` | Ручний ввід розробником | Масові розпади пам'яті через розсинхронізацію `N` |
| **1989 (Cfront 2.0 / ARM)** | `delete[] ptr;` | Автоматичний заголовок Array Cookie | Безпечне автоматичне очищення, накладні 4–8 байтів |
| **2001 (Itanium ABI)** | `delete[] ptr;` | Стандартизація 8-байтового кукі з padding | Уніфікація компонування на Linux, macOS, Unix |
| **2014 (C++14)** | `delete ptr;` | Автоматичний Sized Delete | Оптимізація алокаторів без ручного втручання |
| **2020 (C++20)** | `std::make_unique<T[]>` / `std::span` | Повний перехід на RAII та spans | Занепад сирих масивів у прикладному коді |

Еволюція операторів виділення масивів у C++ демонструє, як мова поступово трансформувала низькорівневі небезпечні конструкції у надійні, стандартизовані механізми, які зберігають максимальну швидкодію без компромісів щодо безпеки пам'яті. Розуміння структури Array Cookies та історії їх виникнення дозволяє системним інженерам глибше розуміти поведінку двійкового інтерфейсу прикладних програм (ABI) та уникати підступних пасток під час взаємодії з низькорівневим кодом.
