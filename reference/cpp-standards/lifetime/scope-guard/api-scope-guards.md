# 📋 Інтерфейс std::scope_exit, std::scope_fail та std::scope_success

Технічна специфікація C++ Extensions for Library Fundamentals (P0052R10) визначає три узагальнені класи-обгортки для гарантованого виконання коду під час виходу з області видимості, формалізуючи семантику відкату дій, зняття блокувань та компенсації помилок на рівні стандартної бібліотеки.

## Загальний огляд заголовка `<scope>`

Класи охоронців розташовані в заголовку `<scope>` (або `<experimental/scope>` у межах Technical Specification) у просторі імен `std` (або `std::experimental`). Вони інкапсулюють викликаний функціональний об'єкт (англ. *invocable*) та керують його викликом у деструкторі залежно від способу виходу з поточної області видимості.

Три класи відрізняються виключно умовою активації деструктора:

1. `std::scope_exit` — виконує збережену дію **завжди** при знищенні об'єкта (як при нормальному виході через `return`/завершення блоку, так і при розгортанні стека винятком), якщо охоронець не був попередньо деактивований.
2. `std::scope_fail` — виконує збережену дію **лише у разі аварійного виходу** з області видимості через виняток (коли кількість активних винятків `std::uncaught_exceptions()` на момент виходу перевищує кількість на момент конструювання).
3. `std::scope_success` — виконує збережену дію **лише у разі успішного (безаварійного) виходу** з області видимості (коли розгортання стека через новий виняток не відбувається).

## Синопсис шаблонів класів

Нижче наведено повні декларації інтерфейсів трьох класів стандарту:

```cpp
namespace std {

// ── 1. std::scope_exit ───────────────────────────────────────────────────────
template <class EF>
class scope_exit {
public:
    // Тип збереженого функціонального об'єкта
    using exit_function = EF;

    // Конструктори
    template <class E>
    explicit scope_exit(E&& fn) noexcept(
        std::is_nothrow_constructible_v<EF, E> ||
        std::is_nothrow_constructible_v<EF, E&>
    );

    scope_exit(scope_exit&& rhs) noexcept(
        std::is_nothrow_move_constructible_v<EF> ||
        std::is_nothrow_copy_constructible_v<EF>
    );

    // Заборона копіювання
    scope_exit(const scope_exit&) = delete;
    scope_exit& operator=(const scope_exit&) = delete;
    scope_exit& operator=(scope_exit&&) = delete;

    // Деструктор
    ~scope_exit() noexcept;

    // Скасування виконання
    void release() noexcept;
};

// Deduction Guide (автоматичне виведення типів аргументів шаблону C++17)
template <class EF>
scope_exit(EF) -> scope_exit<EF>;


// ── 2. std::scope_fail ───────────────────────────────────────────────────────
template <class EF>
class scope_fail {
public:
    using exit_function = EF;

    template <class E>
    explicit scope_fail(E&& fn) noexcept(
        std::is_nothrow_constructible_v<EF, E> ||
        std::is_nothrow_constructible_v<EF, E&>
    );

    scope_fail(scope_fail&& rhs) noexcept(
        std::is_nothrow_move_constructible_v<EF> ||
        std::is_nothrow_copy_constructible_v<EF>
    );

    scope_fail(const scope_fail&) = delete;
    scope_fail& operator=(const scope_fail&) = delete;
    scope_fail& operator=(scope_fail&&) = delete;

    ~scope_fail() noexcept;

    void release() noexcept;
};

template <class EF>
scope_fail(EF) -> scope_fail<EF>;


// ── 3. std::scope_success ────────────────────────────────────────────────────
template <class EF>
class scope_success {
public:
    using exit_function = EF;

    template <class E>
    explicit scope_success(E&& fn) noexcept(
        std::is_nothrow_constructible_v<EF, E> ||
        std::is_nothrow_constructible_v<EF, E&>
    );

    scope_success(scope_success&& rhs) noexcept(
        std::is_nothrow_move_constructible_v<EF> ||
        std::is_nothrow_copy_constructible_v<EF>
    );

    scope_success(const scope_success&) = delete;
    scope_success& operator=(const scope_success&) = delete;
    scope_success& operator=(scope_success&&) = delete;

    ~scope_success() noexcept(noexcept(std::declval<EF&>()()));

    void release() noexcept;
};

template <class EF>
scope_success(EF) -> scope_success<EF>;

} // namespace std
```

## Вимоги до типу параметра `EF` (Exit Function)

Тип `EF` (функціональний об'єкт очищення) повинен відповідати суворим вимогам мови C++:

1. **Вимога викликаності (Invocable):** Вираз `std::is_invocable_v<EF&>` повинен повертати `true`. Тип `EF` повинен бути об'єктом функції, лямбда-виразом, покажчиком на функцію або екземпляром класу з перевантаженим оператором `operator()()`, який можна викликати без аргументів. У C++20 це формулюється концептом `requires std::invocable<EF&>`.
2. **Вимога знищуваності (Destructible):** Тип `EF` повинен бути коректно знищуваним (`std::is_destructible_v<EF> == true`). Деструктор типу `EF` не повинен викидати винятків (`std::is_nothrow_destructible_v<EF> == true`).
3. **Семантика збереження (Decay):** Якщо користувач передає функцію за посиланням або тимчасову лямбду, внутрішній тип зберігається як `std::decay_t<EF>`. Це забезпечує повноцінне володіння копією або переміщеним замиканням усередині стекового об'єкта.

## Детальний опис методів, передмов та післямов

### Конструктор ініціалізації

```cpp
template <class E>
explicit scope_exit(E&& fn) noexcept(...);
```

- **Призначення:** Ініціалізує охоронець переданою дією `fn`. Встановлює внутрішній стан активності у значення `true`.
- **Передмови (Preconditions):** Тип `std::remove_cvref_t<E>` повинен бути конструктивним у `EF`. Вираз `fn()` повинен бути допустимим для виклику без параметрів.
- **Післямови (Postconditions):** Об'єкт вважається активним (`active_ == true`).
- **Специфікація винятків конструктора:**
  У виразі `noexcept` використовується диз'юнкція:
  `noexcept(std::is_nothrow_constructible_v<EF, E> || std::is_nothrow_constructible_v<EF, E&>)`.
  Це правило гарантує, що якщо ініціалізація внутрішнього об'єкта `EF` із прямого rvalue або lvalue-посилання не може кинути виняток, конструктор охоронця також позначається як `noexcept`.
- **Особливості `scope_fail` та `scope_success`:** Під час конструювання ці класи додатково фіксують поточне значення активних винятків у потоці шляхом виклику `uncaught_on_creation_ = std::uncaught_exceptions()`.
- **Безпека винятків:** Якщо під час конструювання об'єкта `EF` із `fn` виникає виняток (наприклад, збій алокації пам'яті всередині захоплених змінних лямбди), охоронець **не вважається сконструйованим**.
  - Для `scope_exit` та `scope_fail`: якщо конструктор `EF` викидає виняток, і `fn()` є викликаною сутністю, стандарт гарантує виконання `fn()`, щоб не допустити витоку ресурсу, який передавався для очищення.
  - Для `scope_success`: якщо конструктор кидає виняток, дія `fn()` **не викликається**.
- **Складність:** `O(1)`.

### Конструктор переміщення

```cpp
scope_exit(scope_exit&& rhs) noexcept(...);
```

- **Призначення:** Передає володіння збереженою дією новому екземпляру охоронця.
- **Передмови:** `rhs` повинен бути валідним об'єктом.
- **Післямови:** Створений об'єкт переймає стан активності `rhs.active_` та лічильник винятків `rhs.uncaught_on_creation_`. Об'єкт-джерело `rhs` стає неактивним (`rhs.active_ == false`).
- **Знеструмлення джерела:** Конструктор викликає `rhs.release()`. Подальший деструктор `rhs` завершиться як порожня операція (англ. *no-op*), що унеможливлює подвійне виконання відкату.
- **Складність:** `O(1)`.

### Заборона копіювання та операторів присвоєння

```cpp
scope_exit(const scope_exit&) = delete;
scope_exit& operator=(const scope_exit&) = delete;
scope_exit& operator=(scope_exit&&) = delete;
```

Охоронці області видимості моделюють суворе одноосібне право на виконання відкладеної дії:
- **Заборона копіювання:** Дублювання об'єкта призвело б до роздвоєння відповідальності та неминучого подвійного виклику компенсаційної дії (наприклад, подвійного виклику `free` або повторного закриття одного дескриптора файлу).
- **Заборона переміщувального присвоєння:** Видалення `operator=(scope_exit&&)` запобігає виникненню логічної неоднозначності: чи повинен лівий операнд виконувати свою поточну дію перед заміщенням новим значенням з правого операнда, чи стара дія має бути анульована. Замість присвоєння розробник повинен явно керувати областями видимості або створювати новий вкладений блок.

### Метод скасування `release()`

```cpp
void release() noexcept;
```

- **Призначення:** Безповоротно деактивує охоронець.
- **Ефект:** Встановлює внутрішній прапорець виконання в стан `false`. Подальший виклик деструктора об'єкта не призведе до жодних дій.
- **Специфікація винятків:** Метод гарантовано є `noexcept`.
- **Складність:** `O(1)`.

### Деструктори: логіка та умови виконання

```cpp
~scope_exit() noexcept;
~scope_fail() noexcept;
~scope_success() noexcept(noexcept(std::declval<EF&>()()));
```

Поведінка деструктора визначається типом охоронця:

1. **`~scope_exit()`:**
   - Якщо `active_ == true`, викликає збережену функцію `callback_()`.
   - Виконується завжди, незалежно від способу виходу з області видимості.

2. **`~scope_fail()`:**
   - Якщо `active_ == true` **ТА** `std::uncaught_exceptions() > uncaught_on_creation_`, викликає `callback_()`.
   - Тобто спрацьовує виключно тоді, коли область залишається через розгортання стека новим винятком, викинутим після конструювання цього охоронця.

3. **`~scope_success()`:**
   - Якщо `active_ == true` **ТА** `std::uncaught_exceptions() <= uncaught_on_creation_`, викликає `callback_()`.
   - Тобто спрацьовує виключно тоді, коли вихід з області є нормальним (безаварійним).

## Правила виведення типів аргументів шаблону (CTAD)

Завдяки впровадженню CTAD (англ. *Class Template Argument Deduction*) у стандарті C++17 розробникам більше не потрібні громіздкі фабричні функції на зразок `make_scope_exit`.

Спеціальне керівництво виведення (англ. *deduction guide*):

```cpp
template <class EF>
scope_exit(EF) -> scope_exit<EF>;
```

дозволяє компілятору автоматично виводити унікальний анонімний тип замикання, створеного лямбда-виразом:

```cpp
// Автоматичне виведення типу EF як анонімної лямбди
std::scope_exit guard = [&] {
    std::cout << "Clean exit\n";
};
```

Якщо передається покажчик на функцію або екземпляр класу функтора, CTAD розгортає його у відповідний конкретний тип. Якщо потрібно зберегти посилання на існуючий функціональний об'єкт без його копіювання, використовують обгортку `std::ref`:

```cpp
auto external_action = [&] { cleanup(); };
std::scope_exit guard_ref(std::ref(external_action));
```

## Різновиди функціональних об'єктів: продуктивність та оверхед

Тип об'єкта, що передається в охоронець, безпосередньо впливає на машинний код та продуктивність:

1. **Прямі лямбда-вирази (найшвидший варіант):**
   Лямбда-вираз безпосередньо стає типом параметра шаблону `EF`. Компілятор бачить тіло оператора `operator()()` і виконує стовідсотковий інлайнінг коду в деструктор. Накладні витрати на виклик дорівнюють нулю (zero runtime overhead).
2. **Вказівники на функції (`void (*)()`):**
   Розмір охоронця збільшується на розмір одного покажчика (8 байтів на x86-64). Виклик відбувається як непрямий перехід (англ. *indirect call*), якщо компілятор не зміг провести міжпроцедурну оптимізацію (LTO).
3. **`std::bind_front` або функтори з полями:**
   Копіюють або переміщують зв'язані аргументи всередину функціонального об'єкта. Пам'ять залишається на стеку, а виклик зазвичай повністю інлайниться.
4. **`std::function<void()>` (не рекомендовано для гарячих шляхів):**
   Застосування `std::function` як `EF` створює накладні витрати на стирання типу (англ. *type erasure*), віртуальний виклик через таблицю покажчиків і потенційне динамічне виділення пам'яті в купі, якщо замикання перевищує розмір буфера малої оптимізації (SBO). Використовувати `std::function` зі `scope_exit` слід лише тоді, коли охоронці різних типів треба скласти в єдиний поліморфний масив.

## Розкладка в пам'яті та оптимізація розміру (Layout)

Розмір екземпляра охоронця області залежить від типу збереженого функціонального об'єкта `EF`:

1. **Безстатусна лямбда (Stateless Lambda):** Безстатусна лямбда `[] { ... }` не має власних полів і є порожнім класом (`sizeof == 1` у C++ за правилами унікальності адрес). Завдяки оптимізації порожньої бази (EBO) або атрибуту `[[no_unique_address]]` для внутрішнього поля, розмір `std::scope_exit` для такої лямбди становить:
   - `sizeof(std::scope_exit<Stateless>) == 1` байт (лише булевий прапорець `active_`);
   - `sizeof(std::scope_fail<Stateless>) == sizeof(int) + align` (прапорець `active_` + ціле число `uncaught_on_creation_`, зазвичай 8 байтів із вирівнюванням).
2. **Лямбда із захопленням за посиланням (`[&]`):** Зберігає адреси захоплених змінних на стеку. Розмір дорівнює сумі розмірів покажчиків плюс поле стану активності.
3. **Лямбда із захопленням за значенням (`[=]`):** Розмір дорівнює сумі розмірів скопійованих об'єктів плюс поля охоронця.

Охоронці ніколи не виділяють динамічну пам'ять у купі (heap), що робить їх повністю придатними для систем реального часу, вбудованих мікроконтролерів та високочастотних торгових платформ.

## Потокова безпека та багатопоточність

Охоронці області видимості розраховані на суто локальне використання:

- **Прив'язка до потоку:** Екземпляр охоронця створюється на стеку конкретного потоку виконання. Механізм `std::uncaught_exceptions()` повертає кількість винятків виключно для *поточного потоку*. Передавати активний екземпляр `std::scope_fail` між різними потоками заборонено, оскільки стан розгортання стека є локальним для кожного потоку (англ. *thread-local*).
- **Конкурентний доступ:** Якщо кілька потоків звертаються до спільних змінних усередині тіла лямбди охоронця, розробник зобов'язаний забезпечити належну синхронізацію за допомогою м'ютексів або атомарних операцій (`std::atomic`).

## Статичний аналіз та попередження компіляторів

Оскільки створення безіменного тимчасового охоронця `std::scope_exit([&]{ ... });` є поширеною помилкою (об'єкт знищується в тому ж рядку, де був створений), сучасні компілятори та лінтери надають спеціальні діагностичні перевірки:

- **Атрибут `[[nodiscard]]`:** Стандартні реалізації позначають класи охоронців атрибутом `[[nodiscard]]`, що змушує компілятор видавати попередження `warning: ignoring temporary created by a constructor declared with 'nodiscard' attribute`.
- **Clang-Tidy:** Правило `bugprone-unused-raii` ловить будь-які спроби створити анонімний стековий об'єкт охоронця без присвоєння його імені змінної.
- **GCC / MSVC:** Попередження `-Wunused-variable` може спрацьовувати на іменовану змінну охоронця, якщо до неї явно не звертаються у тілі функції. Для придушення такого хибного попередження використовують атрибут `[[maybe_unused]]`:

```cpp
[[maybe_unused]] std::scope_exit cleanup = [&] { release_lock(); };
```

## Зберігання в опціональних типах (std::optional) та відкладена ініціалізація

Іноді виникає потреба створити охоронець не на початку функції, а лише після виконання певних попередніх умов, зберігаючи при цьому дію до кінця зовнішнього блоку. Оскільки `std::scope_exit` не має конструктора за замовчуванням і оператора присвоєння, таку відкладену ініціалізацію реалізують через `std::optional`:

```cpp
#include <optional>
#include <scope>

void conditional_guarded_operation(bool need_lock, Mutex& mtx) {
    // Відкладений охоронець: на початку порожній
    auto lock_guard = [&]() -> auto {
        if (need_lock) {
            mtx.lock();
            return std::optional(std::scope_exit([&mtx] noexcept { mtx.unlock(); }));
        }
        return std::optional<std::scope_exit<void(*)()>>{std::nullopt};
    }();

    // Виконання роботи...
    // Наприкінці блоку деструктор std::optional автоматично знищить scope_exit, якщо він був створений
}
```

## Обчислення під час компіляції (constexpr contexts)

У сучасних версіях стандарту (C++20 та C++23) вимоги до constexpr-обчислень були значно розширені: деструктори класів можуть бути оголошені як `constexpr`.

Якщо функціональний об'єкт `EF` є придатним для виклику у час компіляції, охоронець `std::scope_exit` може використовуватися всередині `constexpr` та `consteval` функцій:

```cpp
constexpr int compute_compile_time_val() {
    int state = 10;
    {
        std::scope_exit guard = [&state] { state *= 2; };
        state += 5;
    } // guard виконується тут під час компіляції, state стає 30
    return state;
}

static_assert(compute_compile_time_val() == 30);
```

Ця можливість дозволяє будувати надійні алгоритми генерації метаданих та таблиць пошуку під час компіляції з гарантією коректного очищення проміжних станів.

## Макроси тестування можливостей та інтеграція зі збирачами

Для забезпечення кросплатформної сумісності та перевірки наявності підтримки заголовка `<scope>` у стандартній бібліотеці використовують макроси тестування властивостей (англ. *feature test macros*), стандартизовані в документі SD-6:

```cpp
#if defined(__cpp_lib_scope) && __cpp_lib_scope >= 201902L
    #include <scope>
    namespace my_scope = std;
#elif defined(__cpp_lib_experimental_scope)
    #include <experimental/scope>
    namespace my_scope = std::experimental;
#else
    // Fallback: використання власної або бібліотечної реалізації
#endif
```

У системах автоматизації збирання (CMake) перевірку наявності заголовка `<scope>` здійснюють за допомогою модуля `CheckIncludeFileCXX` або механізму `target_compile_features(app PRIVATE cxx_std_20)`, що гарантує сумісність кодової бази при портуванні між різними версіями стандартних бібліотек libstdc++, libc++ та MSVC STL.

## Порівняльна матриця специфікації класів

У таблиці нижче зведено ключові технічні характеристики трьох типів охоронців:

| Характеристика / Клас | `std::scope_exit` | `std::scope_fail` | `std::scope_success` |
| :--- | :--- | :--- | :--- |
| **Умова виконання дії** | `active_ == true` | `active_ && (uncaught > initial)` | `active_ && (uncaught <= initial)` |
| **Нормальний вихід (`return`)** | Виконується | **Не виконується** | Виконується |
| **Розгортання через `throw`** | Виконується | Виконується | **Не виконується** |
| **Збереження лічильника винятків** | Ні (не потрібно) | Так (`int uncaught_on_creation_`) | Так (`int uncaught_on_creation_`) |
| **Специфікація `~dtor()`** | Завжди `noexcept` | Завжди `noexcept` | `noexcept(noexcept(EF()))` |
| **Типове призначення** | Звільнення ресурсів, закриття дескрипторів | Відкат транзакцій, компенсація аварій | Фіксація змін (commit), сповіщення |

## Поведінка у разі викидання винятку з тіла `exit_function`

Одним із найсуворіших інваріантів C++ є вимога: **деструктори не повинні випускати винятків назовні**.

1. **Для `scope_exit` та `scope_fail`:** деструктори мають безумовну специфікацію `noexcept` (або `noexcept(true)`). Якщо збережена функція `EF` викине виняток під час виконання деструктора, середовище виконання C++ негайно викличе `std::terminate()`, що призведе до миттєвого аварійного зупинення процесу без розгортання стека.
2. **Для `scope_success`:** деструктор має умовну специфікацію `noexcept(noexcept(std::declval<EF&>()()))`. Якщо функція `EF` потенційно може кинути виняток, деструктор `scope_success` може бути викликаний під час нормального повернення з функції. Якщо він кидає виняток, цей виняток поширюється далі вгору стеком (оскільки розгортання стека ще не відбувалося). Проте якщо `scope_success` викликається у вкладеному контексті (наприклад, всередині деструктора іншого об'єкта під час розкручування), будь-який вторинний виняток також негайно призведе до виклику `std::terminate()`.

Тому в промислових кодових базах діє непорушне правило: усі функціональні об'єкти, що передаються в охоронці області, повинні проектуватися з гарантією `noexcept` і перехоплювати власні винятки всередині лямбди.

## Порівняння з іншими стандартними RAII-інструментами

Стандартна бібліотека C++ пропонує кілька споріднених інструментів керування життєвим циклом:

1. **`std::unique_ptr<T, Deleter>`:** Спеціалізований розумний покажчик. Призначений для володіння конкретною адресою динамічного об'єкта або дискретним числовим дескриптором. Викликає делітер лише тоді, коли внутрішній покажчик не є `nullptr`.
2. **`std::lock_guard` / `std::scoped_lock`:** Спеціалізовані охоронці блокувань. Працюють виключно з типами, що задовольняють вимогам `BasicLockable` (мають методи `lock()` та `unlock()`).
3. **`std::scope_exit`:** Абсолютно узагальнений охоронець керування потоком виконання. Не вимагає наявності покажчика, ресурсу чи методу `unlock()`. Загортає будь-яку довільну послідовність інструкцій мови, перетворюючи її на деструктор.

## Керівництво з міграції з legacy-бібліотек

Для проектів, які використовують застарілі сторонні бібліотеки, перехід на стандартні класи є простим і прозорим:

- **З бібліотеки Loki (`Loki::ScopeGuard`, `MakeGuard`):**
  - Старий код: `ScopeGuard g = MakeGuard(&cleanup_fn, arg1);`
  - Стандартний C++: `std::scope_exit g = [&] { cleanup_fn(arg1); };`
- **З бібліотеки Boost (`Boost.ScopeExit`):**
  - Старий код: `BOOST_SCOPE_EXIT(&x) { x.rollback(); } BOOST_SCOPE_EXIT_END`
  - Стандартний C++: `std::scope_exit g = [&x] { x.rollback(); };`
- **З бібліотеки Folly (`folly::makeGuard`, `SCOPE_FAIL`):**
  - Старий код: `SCOPE_FAIL { db.rollback(); };`
  - Стандартний C++: `std::scope_fail g = [&] { db.rollback(); };`

Стандартизовані класи P0052 надають максимальну швидкість виконання, повну сумісність із семантикою переміщення C++17/20 та кришталеву чистоту синтаксису.
