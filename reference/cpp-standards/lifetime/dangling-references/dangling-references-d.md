Ось функція, яка повертає рядок привітання, і рядок коду, який намагається зберегти його для подальшого друку:

```cpp
#include <iostream>
#include <string>
#include <string_view>

std::string_view make_greeting(const std::string& name) {
    std::string text = "Вітаємо, " + name + "!";
    return text; // Компілятор попереджає, але код успішно транслюється
}

int main() {
    std::string_view greeting = make_greeting("Марія");
    std::cout << greeting << '\n'; // ← що саме з'явиться в терміналі?
}
```

У більшості випадків на екрані з'явиться очікуваний текст `Вітаємо, Марія!`. Але варто вставити перед викликом `std::cout` звичайний виклик сторонньої функції або виділити тимчасовий масив, як замість привітання надрукується набір випадкових символів або програма завершиться аварійно через сигнал помилки сегментації.

Причина нестабільності полягає в тому, що після повернення з функції `make_greeting` об'єкт `text` перестав існувати: його деструктор відпрацював, а кадровий вказівник стека змістився вгору. Проте фізичні байти в оперативній пам'яті ще не були затерті іншими даними. Пам'ять залишилася доступною, але вказівник усередині `std::string_view` перетворився на **висяче посилання** (англ. *dangling reference*), а будь-яке читання крізь нього стало **зверненням після звільнення** (англ. *use-after-free*, скорочено *UAF*).

## Анатомія висячого стану: чому пам'ять є, а звернення — злочин

Щоб розібратися, чому звернення до щойно знищеного об'єкта руйнує логіку програми, необхідно розділити апаратну організацію пам'яті та семантичну модель мови C++.

На рівні апаратури процес взаємодіє з віртуальним адресним простором, розбитим на сторінки розміром 4 КіБ. Якщо адреса належить виділеній сторінці стека або купи, процесор успішно читає байти за цією адресою. Апаратний блок керування пам'яттю (англ. *Memory Management Unit*, MMU) не знає, де пролягають межі окремих змінних чи об'єктів мови C++: для нього існують лише права доступу до сторінки.

У мові C++ ситуація протилежна. Стандарт визначає два незалежні інтервали існування: **тривалість зберігання** (англ. *storage duration*, від лат. *duratio* — тривалість) та **час життя** (англ. *lifetime*). Тривалість зберігання — це період, протягом якого під об'єкт зарезервовано ділянку пам'яті відповідного розміру та вирівнювання. Час життя — це суворий інтервал між моментом завершення конструктора і початком виклику деструктора.

Коли деструктор об'єкта завершує роботу:
1. Час життя об'єкта незворотно закінчується.
2. Вказівники та посилання, що дивилися на цей об'єкт чи його підоб'єкти, стають висячими (англ. *dangling*).
3. Пам'ять переходить у недійсний для читання стан, навіть якщо адреса все ще входить до поточної сторінки процесу.

![Руйнування стекового кадру та перезапис пам'яті новим викликом](/reference/cpp-standards/lifetime/dangling-references/img/stack-frame-dangling.svg)
*При виході з make_widget() вказівник стека RSP звільняє кадровий простір. Наступний виклик compute() розміщує власні змінні на тому самому місці, перетворюючи збережену адресу ptr на джерело пошкодження даних.*

Звернення до пам'яті за межами часу життя об'єкта є прямим порушенням фундаментального контракту мови, тобто класичною [невизначеною поведінкою (UB)](book:programming/undefined-behavior). Наслідки такого звернення набагато небезпечніші за звичайне читання застарілих байтів:

1. **Припущення оптимізатора про аліасинг (Type-Based Alias Analysis, TBAA)**: Компілятор оптимізує код на основі аксіоми, що через дійсне посилання типу `T&` можна отримати доступ лише до живого об'єкта типу `T`. Якщо пам'ять уже віддана під об'єкт іншого типу, оптимізатор вважає ці дві адреси несумісними й має право переставити запис і читання місцями або повністю викинути синхронізацію.
2. **Видалення мертвого коду (Dead Code Elimination)**: Оскільки стандарти C++ гарантують, що коректна програма ніколи не виконує невизначеної поведінки, оптимізатор може вважати шлях виконання, що містить звернення до висячого посилання, недосяжним. У результаті компілятор має право повністю вирізати навколишні перевірки та умовні блоки `if`.
3. **Зміщення вказівників при множинному успадкуванні (Pointer Adjustment)**: Якщо клас використовує множинне або віртуальне успадкування, приведення вказівника на базовий клас вимагає додавання зсуву до адреси. Якщо об'єкт знищено, читання таблиці зміщень (vbtable/vtable) призводить до стрибка за довільною адресою пам'яті.
4. **Вразливості безпеки (Use-After-Free CVE)**: Якщо звільнений об'єкт містив віртуальну таблицю (`vptr`) або покажчики на функції зворотного виклику, зловмисник може алокувати в купі підконтрольний блок на тій самій адресі та змусити процес виконати довільний машинний код.

> 🔧 **Навіщо це.** У практичному системному програмуванні висячі вказівники — головна причина плаваючих помилок пам'яті та критичних вразливостей (клас CWE-416). Помилка ніколи не проявляється в момент створення висячого посилання: вона чекає, поки пам'ять буде перезаписана іншим модулем через десятки функцій. Тому надійний захист будується не на відлагодженні симптомів, а на розумінні правил часу життя.

## Повернення посилань і вказівників на локальні змінні

Найбільш прямолінійний спосіб отримати висяче посилання — повернути адресу локальної змінної або параметр за посиланням із функції.

Кожна функція під час виклику виділяє на апаратному [стеку](book:programming/stack-lifo) власний кадр активації (англ. *stack frame*). Усі локальні змінні з автоматичною тривалістю зберігання розміщуються всередині цього кадру. На виході з функції виконуються деструктори в порядку, зворотному до оголошення, після чого інструкція процесора `ret` (на архітектурі x86) відновлює регістр покажчика інструкцій `RIP`, а регістр стека `RSP` повертається до стану зухвалого кадру.

```cpp
struct DataPacket {
    int header;
    double payload[8];
};

const DataPacket& parse_packet(const char* raw_bytes) {
    DataPacket packet;
    packet.header = static_cast<int>(raw_bytes[0]);
    // Заповнення пакету...
    return packet; // Помилка: повернення посилання на локальну змінну!
}
```

У момент повернення з `parse_packet` об'єкт `packet` знищується. Той, хто викликав функцію, отримує посилання на пам'ять нижче поточного вказівника стека `RSP`. 

На архітектурі x86-64 System V ABI ділянка пам'яті розміром 128 байтів нижче `RSP` називається червоною зоною (англ. *red zone*): компілятор має право тимчасово використовувати її для зберігання проміжних обчислень без зміщення `RSP`. Проте перший же виклик будь-якої іншої функції чи обробка апаратного переривання негайно запише поверх кадру `parse_packet` адресу повернення та нові локальні змінні.

Починаючи зі стандарту C++26, пряме повернення посилання на локальну автоматичну змінну заборонено на рівні граматики мови як некоректний вираз (англ. *ill-formed*, згідно з резолюцією робочої групи CWG 1696). Проте якщо посилання повертається опосередковано (через допоміжну структуру, кортеж або сторонню функцію), компілятор не завжди здатен виявити це без глибинного аналізу потоку даних.

### Повернення за значенням та конвенції ABI

Поширена помилка початківців — спроба «зекономити на копіюванні», повертаючи посилання замість об'єкта. У сучасному C++ повернення за значенням є не лише абсолютно безпечним, але й максимально ефективним завдяки обов'язковому усуненню копіювання (англ. *Guaranteed Copy Elision* / *RVO*):

```cpp
// Правильно та ефективно: об'єкт конструюється безпосередньо в кадрі викликача
DataPacket create_packet(int id) {
    DataPacket packet;
    packet.header = id;
    return packet; // Оптимізація Named Return Value Optimization (NRVO)
}
```

На рівні двійкового інтерфейсу (ABI) для структур, розмір яких перевищує два регістри процесора (16 байтів) або які мають нетривіальний конструктор копіювання, викликач виділяє пам'ять у власному стековому кадрі перед інструкцією `call` і передає неявний вказівник на цей буфер у першому службовому регістрі (регістр `RDI` у System V AMD64 або `RCX` у Microsoft x64). Функція `create_packet` записує дані безпосередньо в пам'ять викликача. Жодного копіювання чи переміщення не відбувається, а час життя створеного об'єкта повністю контролюється кадром функції, яка його отримала.

## Тимчасові об'єкти: правила подовження життя та місця розриву

Окремий і найпідступніший клас висячих посилань виникає при роботі з **тимчасовими об'єктами** (англ. *temporary objects*).

Тимчасовий об'єкт виникає щоразу, коли вираз [prvalue](book:cpp-standards/value-categories) (чисте значення без власного імені, як-от результат виклику функції, що повертає значення за копією, результат конкатенації рядків чи явне створення `std::string("abc")`) матеріалізується для ініціалізації посилання або виконання операції.

Базове правило стандарту стверджує: **тимчасовий об'єкт знищується наприкінці повного виразу** (англ. *end of full-expression*), тобто в точці найближчої крапки з комою `;` або закриваючої дужки керуючої конструкції.

```cpp
std::string get_token() { return "token_98765"; }

// Приклад 1: Тимчасовий об'єкт живе лише всередині виразу
const char* ptr = get_token().c_str(); 
// На крапці з комою ';' тимчасовий рядок знищено!
std::cout << ptr << '\n'; // Use-After-Free: ptr вказує на мертвий буфер
```

У прикладі вище метод `.c_str()` повернув вказівник на внутрішній масив символів тимчасового об'єкта `std::string`. На крапці з комою деструктор рядка звільнив пам'ять, а вказівник `ptr` залишився висячим.

### Механізм подовження життя через const&

Щоб уможливити роботу з тимчасовими результатами без зайвого копіювання, у мові C++ діє фундаментальне виняткове правило: **якщо посилання `const T&` або rvalue-посилання `T&&` зв'язується безпосередньо з тимчасовим об'єктом, час життя цього тимчасового об'єкта подовжується до часу життя самого посилання**.

```cpp
// Подовження життя діє: тимчасовий рядок житиме весь час, поки живе ref
const std::string& ref = get_token();
std::cout << ref << '\n'; // Безпечно: об'єкт живий
```

Деструктор тимчасового рядка викличеться не на крапці з комою, а лише тоді, коли змінна `ref` вийде зі своєї області видимості. Правило поширюється також на підоб'єкти агрегатів (доступ через оператор крапки `.`): `const auto& field = make_struct().data_member;` утримує живим увесь складений об'єкт `make_struct()`.

![Подовження життя тимчасового об'єкта та точки, де ланцюг рветься](/reference/cpp-standards/lifetime/dangling-references/img/temporary-lifetime-break.svg)
*При прямому зв'язуванні з prvalue час життя подовжується. Але виклик допоміжної функції або методу повертає glvalue, перериваючи подовження: тимчасовий об'єкт знищується на крапці з комою, а посилання стає висячим.*

### Сім критичних пасток, де подовження життя НЕ спрацьовує

Подовження життя здається магічним інструментом, але воно діє за надзвичайно вузьким формальним правилом ([class.temporary] стандарту ISO C++). Будь-який відхил від форми ламає ланцюг подовження, не викликаючи помилки компіляції:

#### 1. Опосередковане повернення через функцію або метод

Якщо посилання зв'язується не з самим результатом prvalue, а з результатом виклику функції, що повертає посилання (glvalue), компілятор не виконує подовження життя. Компілятор не заглядає всередину тіла функції під час аналізу виразу й не знає, на який саме аргумент вказує повернене посилання:

```cpp
const std::string& a = "перший";
// std::min повертає const T& на один із параметрів
const std::string& result = std::min(a, std::string("другий"));
// Тимчасовий рядок "другий" помер на ';'!
std::cout << result << '\n'; // Якщо std::min обрав другий рядок — це Use-After-Free
```

Ця сама пастка виникає при виклику методів доступу до контейнерів: `const auto& elem = make_vector().front();` або `const auto& val = make_map()["key"];` залишають `elem` та `val` висячими.

#### 2. Посилання-члени класу в списку ініціалізації конструктора

Якщо клас містить поле посилального типу, ініціалізація цього поля тимчасовим об'єктом у списку ініціалізації конструктора **не подовжує** життя тимчасового об'єкта поза межі виконання самого конструктора:

```cpp
struct Viewer {
    const std::string& bound_ref;
    explicit Viewer(const std::string& s) : bound_ref(s) {}
};

Viewer v(std::string("тимчасовий текст")); 
// Тимчасовий рядок гине після завершення виразу створення v!
// Поле v.bound_ref стає висячим посиланням.
```

#### 3. Агрегати, ініціалізовані круглими дужками (C++20)

У C++20 з'явилася можливість ініціалізувати агрегати через круглі дужки `Aggregate(arg1, arg2)`. Проте подовження життя для посилань-членів агрегату гарантується **виключно** при використанні фігурних дужок `Aggregate{arg1, arg2}`. Круглі дужки розглядаються як звичайний виклик псевдоконструктора, де тимчасові аргументи вмирають на крапці з комою.

#### 4. Повернення посилання на тимчасовий об'єкт із функції

```cpp
const std::string& bad_generator() {
    return std::string("новий рядок"); // Тимчасовий об'єкт знищується на return!
}
```

Посилання `const&` у сигнатурі функції не здатне затримати знищення об'єкта, створеного у виразі `return`.

#### 5. Захоплення тимчасових об'єктів лямбда-виразами

```cpp
auto make_callback() {
    // Ініціалізуюче захоплення за посиланням тимчасового об'єкта
    auto lambda = [&ref = std::string("тимчасовий")]() {
        std::cout << ref << '\n';
    };
    return lambda; // Тимчасовий рядок помер на крапці з комою оголошення лямбди!
}
```

#### 6. Динамічне виділення об'єктів у купі через `new`

```cpp
struct Holder {
    const std::string& text;
};

// Об'єкт Holder у купі живе до виклику delete,
// а тимчасовий рядок гине негайно на крапці з комою
Holder* h = new Holder{std::string("дані")};
// h->text — висяче посилання
```

#### 7. Небезпека списків ініціалізації `std::initializer_list`

Клас `std::initializer_list<T>` спроектований як легковажний невласницький тип-обгортка, що містить пару вказівників на початок і кінець масиву. Коли програма створює список `{1, 2, 3}`, компілятор виділяє на стеку прихований масив `const T[N]`, на який і посилається `std::initializer_list`.

```cpp
std::initializer_list<int> get_numbers() {
    return {10, 20, 30}; // Помилка: прихований масив знищується на виході з функції!
}

void use_list() {
    auto list = get_numbers();
    for (int x : list) { // Use-After-Free: читання мертвого стекового масиву
        std::cout << x << ' ';
    }
}
```

Повний звід контрактів і перевірок компілятора розібрано в окремому довіднику: [атрибути часу життя та прапорці діагностики компілятора](book:cpp-standards/dangling-references/api-lifetime-attributes.md).

## Інвалідація ітераторів і посилань при мутації контейнерів

Ще одне поширене джерело звернень після звільнення — модифікація динамічних контейнерів (`std::vector`, `std::string`, `std::deque`, `std::unordered_map`), у той час як код зберігає прямі посилання або ітератори на їхні внутрішні елементи.

Розгляньмо механіку роботи послідовного контейнера `std::vector`. Вектор володіє неперервним буфером у купі, розмір якого визначається місткістю (англ. *capacity*).

```cpp
#include <vector>
#include <iostream>

int main() {
    std::vector<int> numbers = {10, 20}; // size = 2, capacity = 2
    
    // Отримуємо пряме посилання на нульовий елемент
    const int& first = numbers[0];

    // Додаємо новий елемент: size (3) перевищує capacity (2)
    numbers.push_back(30);

    // Що відбувається всередині push_back:
    // 1. Алокується новий буфер у купі місткістю 4 елементи.
    // 2. Старі елементи [10, 20] копіюються/переміщуються в новий буфер.
    // 3. Старий буфер знищується через operator delete[].
    // 4. Посилання first продовжує вказувати на адресу старого звільненого буфера!

    std::cout << first << '\n'; // Невизначена поведінка (Use-After-Free)
}
```

![Інвалідація посилань при зростанні буфера std::vector](/reference/cpp-standards/lifetime/dangling-references/img/vector-reallocation-invalidation.svg)
*При нестачі capacity метод push_back виділяє новий масив і знищує старий. Усі зовнішні посилання, вказівники та ітератори, що вказували на елементи старого буфера, стають висячими.*

### Пастка малої оптимізації рядків (SSO)

Для рядків `std::string` ситуація ще складніша через **оптимізацію малих рядків** (англ. *Small String Optimization*, SSO). Якщо довжина рядка не перевищує 15 байтів (для 64-бітних реалізацій `libc++` та `libstdc++`), рядок не виділяє пам'ять у купі, а зберігає символи безпосередньо всередині власного тіла на стеку.

Це призводить до двох небезпечних ефектів:
1. **Інвалідація при додаванні символів**: Щойно довжина рядка перетинає межу SSO (15 символів), рядок переїжджає в купу, а всі старі покажчики на `data()` стають висячими.
2. **Інвалідація при переміщенні (Move)**: Переміщення звичайного рядка з купи копіює лише вказівник на буфер, зберігаючи валідність покажчиків на символи. Але переміщення SSO-рядка копіює символи всередину нового стекового кадру, миттєво інвалідуючи всі покажчики на старий рядок!

### Зведена таблиця інвалідації стандартних контейнерів

| Тип контейнера | Операція модифікації | Стан ітераторів | Стан посилань на елементи |
|---|---|---|---|
| `std::vector` | `push_back` (із релокацією) | **Інвалідуються всі** | **Інвалідуються всі** |
| `std::vector` | `push_back` (без релокації) | Інвалідується лише `end()` | **Зберігаються всі** |
| `std::vector` | `erase`, `insert` | Інвалідуються від точки вставки до кінця | Інвалідуються від точки вставки до кінця |
| `std::deque` | `push_front` / `push_back` | Інвалідуються всі ітератори | **Зберігаються всі посилання!** |
| `std::deque` | Вставка/видалення всередині | Інвалідуються всі | Інвалідуються всі |
| `std::list`, `std::set`, `std::map` | `insert`, `erase` (інших вузлів) | **Зберігаються всі**, крім видаленого | **Зберігаються всі**, крім видаленого |
| `std::unordered_map` | `insert` (із рехешуванням) | Інвалідуються всі ітератори | **Зберігаються всі посилання на пари!** |

Вузлові контейнери (`std::list`, `std::map`, `std::set`) зберігають кожен елемент в окремому вузлі купи. Тому вставка чи видалення інших елементів ніколи не інвалідує посилання на сусідні вузли.

### Пастки C++20 Ranges, Optional та Structured Bindings

Сучасні засоби C++20 додають нові контексти виникнення висячих посилань:

1. **Тимчасові контейнери в конвеєрах Views (C++20 Ranges)**:
   ```cpp
   std::vector<std::string> get_words();

   // Помилка: get_words() створює тимчасовий вектор, який знищується на ';'
   auto view = get_words() | std::views::filter([](const auto& s) { return s.size() > 3; });

   for (const auto& word : view) { // Use-After-Free: ітерація по мертвому вектору!
       std::cout << word << '\n';
   }
   ```
   Конвеєри `std::views` ніколи не володіють даними: вони зберігають лише ітератори або посилання на вихідний контейнер. Щоб уникнути помилки, контейнер-власник слід обов'язково зберегти в іменованій локальній змінній перед створенням представлення.

2. **Отримання значень із тимчасових `std::optional` та `std::variant`**:
   ```cpp
   std::optional<std::string> find_entry();

   // Помилка: метод value() викликано на тимчасовому об'єкті optional
   const std::string& val = find_entry().value(); 
   // Об'єкт optional знищується на ';', посилання val стає висячим!
   ```
   Якщо функція повертає `std::optional<T>` за значенням, викликати `.value()` чи оператор `*` для збереження посилання заборонено: результат необхідно копіювати або зберігати сам контейнер `auto opt = find_entry();`.

3. **Структуровані зв'язування (Structured Bindings, C++17)**:
   Синтаксис `auto&& [a, b] = get_pair();` створює невидимий прихований об'єкт `__e = get_pair()`, з яким зв'язуються ідентифікатори `a` та `b`. Якщо `get_pair()` повертає пару за значенням, подовження життя діє на весь фіктивний об'єкт `__e`. Проте якщо сама пара містила посилання всередині (наприклад, `std::pair<const std::string&, int>`), розпаковані змінні стануть висячими відразу після виходу з ладу цільового рядка.

4. **Тернарний оператор і приведення типів**:
   ```cpp
   std::string true_val = "активно";
   // Тернарний оператор зводить обидві гілки до спільного типу (std::string)
   // Якщо вибрано рядок "вимкнено", створюється тимчасовий об'єкт!
   const std::string& res = condition ? true_val : "вимкнено";
   ```
   Якщо тип літерала `"вимкнено"` не збігається з типом `true_val`, компілятор неявно конструює тимчасовий `std::string`, час життя якого прив'язується до посилання `res`. Проте якщо такий вираз обгорнуто у функцію, посилання на тимчасовий об'єкт вислизає назовні.

## Лямбда-замикання за посиланням: пастка асинхронності

Лямбда-вираз у C++ не є звичайною функцією: це синтаксичний цукор для створення анонімного функціонального об'єкта (англ. *closure type*). 

Коли лямбда захоплює змінну за посиланням `[&x]`, компілятор генерує структуру, всередині якої оголошено нестатичне поле посилального типу `Type& x_ref;`. Якщо використовується неявне захоплення за замовчуванням `[&]`, усі використані всередині лямбди змінні захоплюються за посиланням на поточний кадр стека.

```cpp
#include <functional>
#include <iostream>
#include <string>

std::function<void()> create_task() {
    std::string secret = "X99-PRO-AUTH";
    
    // Небезпека: лямбда захоплює secret за посиланням на локальний стек
    return [&secret]() {
        std::cout << "Авторизація: " << secret << '\n';
    };
}

int main() {
    auto task = create_task();
    // Локальна змінна secret знищена!
    task(); // Use-After-Free: читання мертвого стека
}
```

Ця проблема стає критичною в асинхронному програмуванні, обробці графічного інтерфейсу (GUI), роботі з пулами потоків (`std::thread`, `boost::asio`) та корутинах C++20:

1. **Асинхронні зворотні виклики (Callbacks)**: Функція запускає мережевий запит і передає лямбду з `[&]`. Функція завершується негайно, а мережева відповідь приходить через 100 мс, коли кадру функції вже давно немає в пам'яті.
2. **Неявне захоплення `this`**: До стандарту C++20 запис `[=]` неявно захоплював вказівник `this` за значенням. Це створювало ілюзію копіювання стану, хоча лямбда зберігала голий вказівник на об'єкт. Якщо об'єкт-власник знищувався раніше, ніж спрацьовував таймер чи потік, метод читав поля мертвого об'єкта.
3. **Корутини C++20 (`co_await`, `co_yield`)**: Коли корутина призупиняється через `co_await`, керування повертається викликачу, і його локальний стек розкручується. Якщо корутина приймала аргументи за посиланням `const T&`, після відновлення вона намагатиметься прочитати знищені змінні стека викликача. Стан корутини (coroutine frame) живе в купі, а посилання вказує на мертвий кадр стека. Тому корутини зобов'язані приймати всі параметри виключно за значенням або через `std::shared_ptr`.
4. **Багатопотоковість і стан гонки на Use-After-Free (Data Race UAF)**: Якщо один потік викликає `delete ptr` або модифікує вектор, а інший потік паралельно читає дані за адресою без використання м'ютексів або атомарних операцій, виникає стан гонки за даними, обтяжений знищенням об'єкта. Це класичне подвійне порушення моделі пам'яті C++11.

### Пастки розумних вказівників при розіменуванні

Навіть використання `std::unique_ptr` та `std::shared_ptr` не гарантує абсолютного захисту від висячих посилань, якщо код утримує пряме розіменоване посилання:

```cpp
#include <memory>

struct SensorNode {
    int value{0};
    void poll() { value++; }
};

void process_node() {
    auto node = std::make_shared<SensorNode>();
    
    // Отримуємо сире посилання на керований об'єкт
    SensorNode& ref = *node;

    // Скидаємо розумний вказівник (або передаємо його в інший потік, де він знищується)
    node.reset(); 

    // Use-After-Free: об'єкт SensorNode знищено методом reset()!
    ref.poll(); 
}
```

Інша підступна помилка пов'язана з методом `std::weak_ptr::lock()`. Метод повертає тимчасовий `std::shared_ptr`. Якщо зберегти сирий вказівник на результат без збереження самого `shared_ptr`, об'єкт знову стає висячим:

```cpp
std::weak_ptr<SensorNode> weak_node;

// Помилка: тимчасовий shared_ptr знищується на крапці з комою ';'
SensorNode* raw = weak_node.lock().get(); 
// raw вже є висячим вказівником, якщо лічильник сильних посилань дорівнював 0!
```

### Безпечні патерни захоплення лямбд

1. **Явне захоплення за значенням**: Завжди перелічуйте змінні явно `[x, id]`, уникаючи магічного `[&]`.
2. **Ініціалізуюче переміщення (Init-capture, C++14)**: Передавайте право володіння всередину замикання через `[ptr = std::move(ptr)]`.
3. **Захоплення копії об'єкта `[*this]` (C++17)**: Для гарантії існування стану копіюйте поточний об'єкт у лямбду замість збереження вказівника на нього.
4. **Слабкі посилання `std::weak_ptr` для довгоживучих обробників**:

```cpp
#include <memory>
#include <iostream>

class NetworkManager : public std::enable_shared_from_this<NetworkManager> {
public:
    void send_request() {
        // Захоплюємо std::weak_ptr, щоб уникнути висячого this
        auto callback = [weak_self = weak_from_this()](std::string response) {
            if (auto self = weak_self.lock()) {
                self->handle_response(response);
            } else {
                std::cout << "Об'єкт NetworkManager уже знищено, ігноруємо відповідь\n";
            }
        };
        // Реєстрація callback у мережевому циклі...
    }

    void handle_response(const std::string& r) {
        std::cout << "Отримано: " << r << '\n';
    }
};
```

## Діагностика: статичний аналіз і AddressSanitizer

Боротьба з висячими посиланнями ведеться на двох взаємодоповнюючих рівнях: під час компіляції (статичний аналіз) та під час виконання (динамічні санітайзери).

### Прапорці статичного аналізу

Сучасні компілятори мають розширені діагностичні модулі, які відстежують рух посилань у межах функції:
- `-Wdangling` та `-Wreturn-stack-address` (GCC/Clang): попереджають про очевидні спроби повернення локальних адрес.
- `-Wdangling-gsl` (Clang): аналізує типи-в'ювери (`std::string_view`, `std::span`) та видає помилку при зв'язуванні з тимчасовими об'єктами.
- `/analyze` (MSVC): активує C++ Core Guidelines Lifetime Checker.

### Динамічний аналіз: AddressSanitizer (ASan)

Для виявлення помилок, які проходять крізь межі компіляції різних файлів, застосовується інструмент **AddressSanitizer** (`-fsanitize=address`). Він відображає кожні 8 байтів звичайної пам'яті програми в 1 байт спеціальної тіньової пам'яті (коефіцієнт стиснення 8:1), де кодує статус валідності адрес.

![Архітектура Shadow Memory в AddressSanitizer](/reference/cpp-standards/lifetime/dangling-references/img/asan-shadow-memory.svg)
*AddressSanitizer проектує кожні 8 байтів оперативної пам'яті в 1 тіньовий байт. При звільненні пам'яті купи вона позначається як 0xFD, а при знищенні стекового кадру — як 0xF5, викликаючи миттєву аварію при несанкціонованому зверненні.*

Практичний розбір архітектури тіньової пам'яті, конфігурації режиму перевірки висячого стека (`ASAN_OPTIONS=detect_stack_use_after_return=1`) та читання звітів розібрано в окремому матеріалі: [практичний розбір механізму тіньової пам'яті та аналізу звітів ASan](book:cpp-standards/dangling-references/proj-asan-shadow-memory.md).

### Апаратний захист: Memory Tagging Extension (ARM MTE)

У сучасних апаратних архітектурах (зокрема ARMv8.5-A MTE у мобільних процесорах та серверах) реалізовано апаратний захист від Use-After-Free. Технологія використовує невикористовувані верхні 4 біти 64-розрядного вказівника (англ. *Top-Byte Ignore*, TBI) для збереження тегу кольору (значення від 0 до 15).

Кожна 16-байтна гранула фізичної пам'яті має відповідний 4-бітний апаратний тег. Коли алокатор звільняє блок пам'яті через `free()`, він перезаписує апаратний тег пам'яті новим випадковим числом. Якщо старий висячий вказівник спробує звернутися до пам'яті, процесор виявить невідповідність тегу вказівника та тегу пам'яті на апаратному рівні за один такт і миттєво згенерує апаратне переривання `SIGSEGV` із кодом `SEGV_MTESERR`.

## Архітектурні інваріанти безпечного володіння

Повне усунення дефектів висячих посилань досягається дотриманням чотирьох фундаментальних архітектурних правил:

1. **Семантика значень за замовчуванням (Value Semantics)**: Передавайте та повертайте невеликі типи (`int`, `double`, дрібні структури) та важкі типи з підтримкою дешевого переміщення (`std::string`, `std::vector`) за значенням. Не намагайтеся оптимізувати сигнатуру посиланням, якщо в цьому немає явної необхідності.
2. **Суворе розмежування володіння та запозичення**:
   - Об'єкти-власники (`std::string`, `std::vector`, `std::unique_ptr`) керують часом життя.
   - Невласницькі типи (`T&`, `const T*`, `std::string_view`, `std::span`) існують **тільки як короткоживучі аргументи функцій** і ніколи не зберігаються в довгоживучих структурах або полях класів без явної синхронізації життєвого циклу.
3. **Ієрархія часу життя зверху вниз**: Посилання має право вказувати лише на об'єкт, який створений раніше за нього і буде знищений пізніше за нього. Якщо зв'язок спрямований вгору або вбік — володіння має передаватися явно через значення або `std::shared_ptr`.
4. **Обов'язкова перевірка в CI/CD**: Автоматичне складання з прапорцями `-Wall -Wextra -Wdangling` та регулярний запуск тестів під AddressSanitizer усувають людський фактор з процесу розробки.
