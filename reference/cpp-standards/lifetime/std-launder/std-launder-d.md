Розглянемо коротку функцію, у якій об'єкт із константним полем знищується й створюється заново в тій самій ділянці пам'яті:

```cpp
#include <new>
#include <iostream>

struct Config {
    const int timeout_ms;
};

void run() {
    auto* cfg = new Config{100};
    std::cout << cfg->timeout_ms << '\n'; // друкує 100

    cfg->~Config();                       // явне завершення часу життя
    new (cfg) Config{500};                // створення нового об'єкта в тому самому сховищі

    std::cout << cfg->timeout_ms << '\n'; // що надрукує оптимізована програма?
    delete cfg;
}
```

У режимі без оптимізацій (`-O0`) компілятор чесно записує число `500` в пам'ять за адресою `cfg`, а потім зчитує його звідти й виводить `500`. Але варто ввімкнути оптимізатор GCC або Clang (`-O2` чи `-O3`), як другий вивід раптово друкує `100`.

Фізично в комірці оперативної пам'яті вже лежить двійкове число `500` — розміщувальний `new` добросовісно його туди записав. Проте асемблерний код другого виклику взагалі не містить інструкції читання з пам'яті: компілятор зашив константу `100` безпосередньо в машинну команду як літерал. Оптимізатор не помилився у власній логіці й не зламався: він діяв за формальними правилами мови C++, згідно з якими значення поля `const int` за адресою `cfg` не має права змінюватися протягом усього виконання програми. Звернення `cfg->timeout_ms` після повторного створення об'єкта стало невизначеною поведінкою, а порятунком від неї виступає функція `std::launder`.

## Чому оптимізатор не читає пам'ять удруге

Щоб зрозуміти, чому компілятор ігнорує реальний вміст оперативної пам'яті, потрібно подивитися на програму очима її абстрактної машини (англ. *abstract machine*). Головне завдання оптимізатора — видалити зайві звернення до повільної пам'яті та замінити змінні константами або регістрами процесора.

Коли компілятор транслює вираз `cfg->timeout_ms`, він бачить тип структури `Config`, у якій поле `timeout_ms` оголошене як `const`. За правилами C++ модифікатор `const` для нестатичного поля означає абсолютний інваріант: від моменту завершення конструктора й до початку деструктора значення цього поля не може змінитися за жодних обставин. Будь-яка спроба модифікувати таку пам'ять через зняття константності (`const_cast`) є невизначеною поведінкою.

Перетворюючи вихідний код у проміжне представлення зі статичним одиночним присвоєнням (англ. *Static Single Assignment*, SSA), оптимізатор позначає операцію завантаження константного поля спеціальним атрибутом інваріантності (у бекенді LLVM це метадані `!invariant.load` або група `!invariant.group`). Якщо компілятор один раз зчитав `cfg->timeout_ms` і отримав значення `100`, він записує це число у віртуальний SSA-регістр.

Усі наступні читання `cfg->timeout_ms` за тим самим базовим вказівником `cfg` замінюються на вже відоме значення з регістра. Ця трансформація відома як розповсюдження констант (англ. *Constant Propagation*) та усунення спільних підвиразів (англ. *Common Subexpression Elimination*, CSE). Навіть якщо між двома читаннями викликаються сторонні функції чи виконується запис байтів у пам'ять, оптимізатор знає: жоден легальний код не здатен змінити константне поле живого об'єкта, тому перевіряти комірку пам'яті вдруге немає сенсу.

![Повторне використання пам'яті й оптимізація Constant Propagation](/reference/cpp-standards/lifetime/std-launder/img/storage-reuse-invariant.svg)
*Зіткнення оптимізатора з повторним використанням пам'яті: без бар'єра інваріантів процесор бере закешоване значення з регістра, ігноруючи реальний запис у комірку.*

Коли викликається деструктор `cfg->~Config()`, старий об'єкт припиняє своє існування. Наступний розміщувальний `new (cfg) Config{500}` створює новий екземпляр у тому самому сховищі. Але змінна `cfg` у вихідному тексті — це той самий вказівник, через який читався перший об'єкт. Для оптимізатора ланцюжок походження (англ. *provenance*) вказівника `cfg` не перервався: він вважає, що звернення йде до старого об'єкта з уже закешованим інваріантом `100`.

## Прозоре заміщення об'єктів і межі [basic.life]

Стандарт C++ містить спеціальний розділ `[basic.life]`, який регулює повторне використання виділеної пам'яті (англ. *storage reuse*). Коли в буфері, де щойно жив один об'єкт, створюється новий, виникає фундаментальне запитання: чи мають право наявні вказівники, посилання та імена змінних автоматично вказувати на новий об'єкт?

Цей механізм у стандарті називається **прозорим заміщенням** (англ. *transparently replaceable*). Якщо старий об'єкт замінюється новим прозоро, програмісту не потрібно оновлювати вказівники: старий вказівник `p` автоматично набуває значення адреси нового об'єкта й стає повністю легальним для використання.

Проте стандарт висуває жорсткий перелік вимог, за яких прозоре заміщення є дійсним. Новий об'єкт `Y` прозоро заміщує старий об'єкт `X`, якщо одночасно виконуються всі наступні умови:

1. Сховище для `Y` займає точно те саме місце в пам'яті, що й сховище `X` (той самий розмір і вирівнювання).
2. Тип `Y` збігається з типом `X` (ігноруючи `cv`-кваліфікатори верхнього рівня).
3. `X` не є повним константним об'єктом зі статичною чи автоматичною тривалістю зберігання.
4. `X` і `Y` є або обидва повними об'єктами (англ. *complete objects*), або обидва підоб'єктами одного й того самого базового класу чи масиву.
5. **Тип `X` не містить нестатичних даних-членів із типом `const` або типом посилання (`T&`) — ані безпосередньо, ані рекурсивно всередині своїх полів чи базових класів.**
6. Якщо `X` є об'єктом поліморфного класу, новий об'єкт `Y` має належати до того самого динамічного типу (не змінюється таблиця віртуальних методів).

![Умови прозорого заміщення об'єктів у C++](/reference/cpp-standards/lifetime/std-launder/img/transparent-replacement-decision.svg)
*Дерево рішень стандарту C++: якщо тип містить const-поля або посилання, автоматичне прозоре заміщення блокується, перетворюючи старий вказівник на недійсний.*

Пункт 5 є критичним. Якщо структура містить хоча б одне поле `const` або посилання `&`, автоматичне прозоре заміщення **не відбувається ніколи**. 

Після виклику деструктора старий об'єкт помер, а разом із ним померли всі його вказівники та посилання. Хоча за тією самою числовою адресою народився новий об'єкт `Config{500}`, старий вказівник `cfg` формально продовжує вказувати на *неіснуючий* старий об'єкт. Звернення до полів через `cfg` є розіменуванням мертвого вказівника (невизначеною поведінкою).

Чому комітет стандартизації ввів саме таке обмеження? Якби стандарт дозволив автоматичне прозоре заміщення для типів із `const`-полями, компілятори втратили б право оптимізувати доступ до константних даних. Їм довелося б припускати, що між будь-якими двома операціями читання константи хтось міг знищити об'єкт через деструктор і створити новий із іншим значенням. Це зруйнувало б оптимізацію `Constant Propagation` у всьому коді C++.

Детальний аналіз суперечок у робочій групі WG21 та розбору дефекту Core 1776 наведено у вставці [Історія появи std::launder](book:cpp-standards/std-launder/hist-p0137-p0532.md).

## Концепція походження вказівників (Pointer Provenance)

Щоб до кінця зрозуміти, чому фізичної рівності адрес недостатньо для легального доступу до пам'яті, потрібно розібратися з концепцією **походження вказівників** (англ. *pointer provenance*).

У машинній мові процесора вказівник — це просто 64-бітне чи 32-бітне беззнакове ціле число, яке вказує на зміщення в байтовому просторі пам'яті. Для процесора адреса `0x7ffee400` є однаковою незалежно від того, як ми її отримали.

Проте для абстрактної машини C++ і компіляторного оптимізатора вказівник — це складна сутність, яка несе із собою приховану історію свого створення. Кожен вказівник прив'язаний до конкретного об'єкта або виділеного блоку пам'яті, з якого його було отримано:

1. Якщо вказівник створено виразом `&var`, його походження пов'язане з локальною змінною `var`.
2. Якщо вказівник повернено функцією `malloc` або оператором `new`, його походження пов'язане з новим виділеним динамічним блоком.
3. Якщо виконано перетворення `reinterpret_cast<T*>(buffer)`, отриманий вказівник несе походження масиву `buffer`.

Коли об'єкт `A` знищується, а на його місці створюється об'єкт `B`, їхня числова адреса збігається. Але старий вказівник `p_A` прив'язаний до життєвого циклу об'єкта `A`. Оптимізатор будує граф залежностей даних, у якому властивості `A` (його константи, таблиці функцій, тип) асоційовані саме з вузлом `p_A`.

Якщо ми намагаємося звернутися до об'єкта `B` через вказівник `p_A`, оптимізатор продовжує використовувати граф залежностей об'єкта `A`. З точки зору компілятора, наявність запису за адресою `0x7ffee400` була операцією над стороннім буфером, яка не повинна впливати на незмінні властивості `A`.

Саме тому мові C++ був необхідний явний оператор переприв'язки походження. Функція `std::launder` бере числове значення адреси старого вказівника і створює в оптимізаторі абсолютно новий вузол походження, прив'язаний до актуального об'єкта, що зараз живе за цією адресою.

## Проблема відмивання вказівника (Pointer Laundering)

Розміщувальний оператор `new` повертає чистий, свіжий вказівник на новостворений об'єкт:

```cpp
Config* fresh_ptr = new (cfg) Config{500};
```

Вказівник `fresh_ptr` є абсолютно валідним: він отриманий безпосередньо з виразу створення, має новий ланцюжок походження в оптимізаторі й не несе за собою закешованих констант старого об'єкта. Якщо звернутися до `fresh_ptr->timeout_ms`, компілятор згенерує чесну інструкцію читання з пам'яті й надрукує `500`.

Але в реальних програмах зберегти та передати далі значення `fresh_ptr` вдається далеко не завжди. Типовий приклад — узагальнені контейнери на кшталт `std::optional<T>`, `std::variant<Ts...>`, `std::any` або власні пули пам'яті (англ. *memory arenas*).

Усередині такого контейнера пам'ять виділяється у вигляді сирого вирівняного масиву байтів:

```cpp
template <typename T>
class OptionalStorage {
    alignas(T) std::byte buffer_[sizeof(T)];
    bool engaged_ = false;

public:
    template <typename... Args>
    void emplace(Args&&... args) {
        if (engaged_) {
            get_ptr()->~T();
        }
        ::new (static_cast<void*>(buffer_)) T(std::forward<Args>(args)...);
        engaged_ = true;
    }

    T* get_ptr() noexcept {
        return reinterpret_cast<T*>(buffer_); // ← ПОМИЛКА: ланцюжок походження розірвано
    }
};
```

Погляньмо на метод `get_ptr()`. Вираз `reinterpret_cast<T*>(buffer_)` бере адресу масиву байтів `buffer_`. Оскільки масив `buffer_` існував від самого створення екземпляра `OptionalStorage`, з точки зору моделі пам'яті перетворення його адреси в `T*` створює вказівник, походження якого веде до байтового масиву, а не до щойно створеного всередині нього об'єкта типу `T`.

Якщо тип `T` містить `const`-поля або посилання, а метод `emplace()` викликається повторно, виклик `get_ptr()` повертає вказівник, який не пройшов прозоре заміщення. Будь-яке читання членів класу через такий вказівник знову призводить до невизначеної поведінки та некоректної оптимізації.

Виникла патова ситуація:
1. Новий об'єкт у пам'яті реально існує.
2. Програміст знає точну адресу цього об'єкта (`buffer_`).
3. Мова C++ забороняє використовувати вказівник `reinterpret_cast<T*>(buffer_)`, бо він має старе походження і не заміщує об'єкт автоматично.

Потрібен був легальний спосіб сказати компілятору: «Забудь усе, що ти знав про історію та інваріанти цих байтів. За цією адресою зараз живе повноцінний об'єкт типу `T`, дай мені чистий вказівник на нього».

Ця операція очищення історії отримала назву «відмивання вказівника» (англ. *pointer laundering*), а в стандарті C++17 для неї було введено функцію `std::launder`.

## Семантика й механізм роботи std::launder

Функція `std::launder` оголошена в заголовковому файлі `<new>`:

```cpp
namespace std {
    template <class T>
    [[nodiscard]] constexpr T* launder(T* p) noexcept;
}
```

Слово `launder` перекладається як «прати», «відмивати» (від латинського *lavare* — мити).

Семантика функції полягає в наступному: вона приймає вказівник `p` і повертає новий вказівник на той самий об'єкт типу `T`, що знаходиться за вказаною адресою, але розриває зв'язок з оптимізаційними припущеннями минулого.

Повний перелік формальних вимог стандарту, обмежень шаблону та діагностичну матрицю зібрано у вставці [Семантика й контракт std::launder](book:cpp-standards/std-launder/api-launder-contract.md).

З точки зору компілятора, `std::launder` є спеціальним інтринсиком (наприклад, `__builtin_launder` у GCC та Clang). Він діє як оптимізаційний бар'єр для аналізу псевдонімів (англ. *alias analysis*) та інваріантних завантажень.

У проміжному поданні компілятора `std::launder` генерує новий вузол у графі потоку даних (SSA), який не успадковує атрибути константності старого вказівника:

```text
Без std::launder:
  %ptr1 = getelementptr (старий об'єкт)
  %val1 = load %ptr1 [invariant]          ; %val1 = 100
  ... (placement new за тією ж адресою) ...
  %val2 = %val1                           ; оптимізатор використовує 100

Із застосуванням std::launder:
  %ptr1 = getelementptr (старий об'єкт)
  %val1 = load %ptr1 [invariant]          ; %val1 = 100
  ... (placement new за тією ж адресою) ...
  %ptr2 = call @llvm.launder(%ptr1)       ; бар'єр походження!
  %val2 = load %ptr2                      ; чесне читання з пам'яті: %val2 = 500
```

![Граф походження та бар'єр оптимізації std::launder](/reference/cpp-standards/lifetime/std-launder/img/launder-provenance-barrier.svg)
*Розрив графа походження: std::launder змушує бекенд компілятора створити новий SSA-вузол адреси та згенерувати інструкцію читання з оперативної пам'яті.*

Найважливіша властивість `std::launder` — **нульова вартість у рантаймі** (англ. *zero-overhead abstraction*). Функція не генерує жодної машинної інструкції процесора: в асемблерному лістингу немає ані викликів `call`, ані інструкцій синхронізації шини, ані бар'єрів пам'яті (`mfence` чи `dmb`). Це суто внутрішня вказівка для аналізатора компілятора під час трансляції.

Виправимо реалізацію нашого контейнера `OptionalStorage` за допомогою `std::launder`:

```cpp
T* get_ptr() noexcept {
    return std::launder(reinterpret_cast<T*>(buffer_));
}

const T* get_ptr() const noexcept {
    return std::launder(reinterpret_cast<const T*>(buffer_));
}
```

Тепер код є на 100% коректним за стандартом C++17/C++20/C++23: компілятор не має права застосовувати закешовані значення константних полів, і програма працюватиме надійно за будь-яких рівнів оптимізації.

> 🔧 **Навіщо це.** Практичне правило: якщо ви пишете низькорівневий контейнер (`variant`, `optional`, `any`, `small_vector`) або алокатор пулу пам'яті, який перетворює `std::byte[]` чи `char[]` на об'єкти з потенційно константними чи посилальними членами, будь-яке отримання вказівника на об'єкт із сирої пам'яті **повинно** огортатися в `std::launder`. Без цього оптимізатор має законне право підставити застарілі дані.

## Девіртуалізація й поліморфне перевтілення

Константні поля та посилання — не єдина причина, чому компілятор покладається на незмінність об'єкта. Другим класичним джерелом оптимізацій є **девіртуалізація** (англ. *devirtualization*).

Коли метод викликається через вказівник на базовий клас `Base*`, компілятор за замовчуванням генерує непрямий виклик через таблицю віртуальних методів (`vtable`). Проте якщо компілятор бачить створення конкретного похідного класу `DerivedA` у локальній області видимості, він знає точний динамічний тип об'єкта. У такому разі непрямий виклик замінюється прямим переходом на функцію `DerivedA::method()`, оминаючи звернення до `vtable`.

Що станеться, якщо в сховищі `DerivedA` створити інший похідний клас `DerivedB`?

```cpp
#include <new>
#include <iostream>

struct Base {
    virtual void speak() const { std::cout << "Base\n"; }
    virtual ~Base() = default;
};

struct Dog : Base {
    void speak() const override { std::cout << "Гав!\n"; }
};

struct Cat : Base {
    void speak() const override { std::cout << "Няв!\n"; }
};

void test_animals() {
    alignas(Dog) alignas(Cat) std::byte storage[sizeof(Dog)];
    
    // Створюємо перший об'єкт Dog
    Base* animal = new (storage) Dog();
    animal->speak(); // Оптимізатор девіртуалізує це у прямий виклик Dog::speak() -> "Гав!"

    animal->~Base();

    // Створюємо Cat у тому самому місці
    new (storage) Cat();

    // Звернення через старий вказівник animal:
    animal->speak(); // ДЕВІРТУАЛІЗАЦІЯ: оптимізатор може знову викликати Dog::speak()!
}
```

У цьому прикладі тип нового об'єкта (`Cat`) не збігається з типом старого (`Dog`). Згідно з пунктом 2 правил `[basic.life]`, прозоре заміщення не відбувається.

Оптимізатор Clang або GCC під час міжпроцедурного аналізу може зберегти інформацію: «за вказівником `animal` знаходиться об'єкт типу `Dog`». Відповідно, другий виклик `animal->speak()` буде скомпільований не як читання нового `vptr` з пам'яті, а як прямий виклик `Dog::speak()`. Замість очікуваного «Няв!» програма надрукує «Гав!», або впаде з помилкою сегментації, якщо розміщення методів чи зміщення полів класів не збігаються.

Правильне вирішення цієї проблеми вимагає використання `std::launder`:

```cpp
// Отримуємо новий вказівник на Base через відмивання пам'яті
Base* new_animal = std::launder(reinterpret_cast<Base*>(storage));
new_animal->speak(); // Гарантовано прочитає новий vptr об'єкта Cat і надрукує "Няв!"
```

Виклик `std::launder` повідомляє підсистемі девіртуалізації, що таблиця віртуальних методів за цією адресою могла змінитися, змушуючи оптимізатор чесно витягти адресу віртуального методу з нового `vptr`.

## Поведінка на рівні асемблера для посилань і констант

Подивимося, як поводиться оптимізатор на рівні асемблерних інструкцій під час роботи з класами, що містять поля-посилання.

Посилання в C++ є незмінними за своєю природою: зв'язавши посилання один раз під час ініціалізації об'єкта, його неможливо переприв'язати до іншої змінної. Тому компілятор оптимізує доступ через поля-посилання ще агресивніше, ніж через константні поля.

```cpp
struct Binding {
    int& target;
};

int inspect(Binding* b, int* next_val) {
    int first = b->target;
    
    b->~Binding();
    new (b) Binding{*next_val}; // нове посилання на іншу змінну
    
    // Помилка: використання старого вказівника b без launder
    int second = b->target;
    return first + second;
}
```

Погляньмо на згенерований асемблер для x86-64 (GCC 13, `-O3`):

```nasm
inspect(Binding*, int*):
    mov   rax, QWORD PTR [rdi]    ; завантажуємо адресу b->target у rax
    mov   edx, DWORD PTR [rax]    ; first = *target
    mov   QWORD PTR [rdi], rsi    ; записуємо нову адресу next_val у пам'ять (new)
    lea   eax, [rdx + rdx]        ; РЕЗУЛЬТАТ: first + first (оптимізатор продублював first!)
    ret
```

Зверніть увагу на рядок `lea eax, [rdx + rdx]`. Оптимізатор порахував значення `first + first` (тобто `first * 2`), повністю проігнорувавши той факт, що поле-посилання тепер вказує на іншу адресу `rsi` (`next_val`). Компілятор вирішив: «поле `target` є посиланням, його адреса не могла змінитися, отже `second == first`».

Додамо `std::launder`:

```cpp
int inspect_correct(Binding* b, int* next_val) {
    int first = b->target;
    
    b->~Binding();
    new (b) Binding{*next_val};
    
    Binding* lb = std::launder(b); // очищення інваріантів
    int second = lb->target;
    return first + second;
}
```

Асемблерний лістинг кардинально змінюється:

```nasm
inspect_correct(Binding*, int*):
    mov   rax, QWORD PTR [rdi]    ; rax = стара адреса b->target
    mov   eax, DWORD PTR [rax]    ; first = *target (старе значення)
    mov   QWORD PTR [rdi], rsi    ; запис нової адреси next_val у пам'ять
    mov   edx, DWORD PTR [rsi]    ; ЧЕСНЕ ЧИТАННЯ: second = *next_val
    add   eax, edx                ; результат = first + second
    ret
```

Оптимізатор виконав реальне завантаження `mov edx, DWORD PTR [rsi]`, зберігши правильну семантику обчислення.

Покрокову реалізацію повноцінного контейнера `InPlaceOptional<T>`, що коректно працює з константними даними, посиланнями та поліморфізмом, дивіться у вставці [Реалізація InPlaceOptional та аналіз асемблера](book:cpp-standards/std-launder/proj-inplace-storage.md).

## Складні випадки: множинне успадкування та зміщення покажчиків

У складних ієрархіях класів із множинним успадкуванням адреса повного об'єкта може не збігатися з адресою його базових підкласів. Розглянемо випадок, коли об'єкт створюється в буфері, а доступ до нього здійснюється через вказівник на другий базовий клас:

```cpp
struct Base1 {
    int a;
    virtual void f() {}
};

struct Base2 {
    int b;
    virtual void g() {}
};

struct Derived : Base1, Base2 {
    int c;
};
```

У типовому ABI (наприклад, Itanium C++ ABI) розміщення структури `Derived` виглядає так: спочатку йде `Base1` (зі своїм `vptr`), а за ним зі зміщенням у `sizeof(Base1)` розташовується `Base2` (зі своїм окремим `vptr`).

Якщо ми знищуємо екземпляр `Derived` і створюємо новий у тому самому буфері:

```cpp
void test_multiple_inheritance() {
    alignas(Derived) std::byte storage[sizeof(Derived)];
    
    auto* d1 = new (storage) Derived();
    Base2* b2 = d1; // b2 вказує на середину буфера storage (storage + offset)

    d1->~Derived();
    auto* d2 = new (storage) Derived();

    // Чи дійсний b2?
    // Ні! Тип Derived має нетривіальну структуру, а d2 замінив увесь об'єкт.
    // Звернення b2->g() без оновлення адреси або без std::launder є UB.
    
    Base2* valid_b2 = std::launder(reinterpret_cast<Base2*>(
        reinterpret_cast<std::byte*>(storage) + sizeof(Base1)
    ));
    valid_b2->g();
}
```

Без `std::launder` вказівник `b2` розглядається оптимізатором як старий підоб'єкт першого екземпляра `Derived`. Оскільки час життя першого екземпляра скінчився, `b2` втратив валідність. Відмивання покажчика на точну адресу зміщення відновлює легітимність доступу до підоб'єкта.

## Взаємодія з оптимізаціями LTO та міжпроцедурним аналізом

Особлива небезпека ігнорування `std::launder` проявляється при увімкненні оптимізації на етапі компонування (англ. *Link-Time Optimization*, LTO / LTCG).

Коли код скомпільовано без LTO у вигляді окремих одиниць трансляції (`.cpp` файлів), виклик сторонньої функції в іншому файлі часто діє як неявний бар'єр для оптимізатора. Оскільки компілятор не знає, що саме робить функція `external_func()`, він змушений перезавантажувати значення полів із пам'яті на випадок, якщо ця функція змінила глобальний стан. Завдяки цьому помилки з відсутністю `std::launder` можуть роками маскуватися й не призводити до збоїв у звичайних збірках.

Проте варто ввімкнути `-flto` або `-O3 -fipa-cp` (міжпроцедурне розповсюдження констант), як оптимізатор аналізує весь проект цілком. Він бачить, що жодна функція не здійснює легальної модифікації константних полів, і агресивно видаляє перезавантаження пам'яті між функціями різних модулів. Програма, яка ідеально проходила всі модульні тести, несподівано ламається в релізному білді.

## Передумови та межі застосування: коли std::launder є безсилим

Функція `std::launder` — це прецизійний інструмент низькорівневого коду, а не універсальний засіб маскування будь-яких помилок пам'яті. Стандарт C++ накладає суворі передумови (англ. *preconditions*) на виклик `std::launder(p)`:

1. **Об'єкт повинен реально існувати.** Вказівник `p` має вказувати на ділянку пам'яті, у якій на момент виклику *вже почався і ще не закінчився* час життя об'єкта типу `T`. Виклик `std::launder` для неініціалізованої сирої пам'яті або пам'яті після деструктора (до виклику розміщувального `new`) є **невизначеною поведінкою**.
2. **Неможливість порушення правил псевдонімів (Strict Aliasing).** `std::launder` не дозволяє звертатися до об'єкта одного типу через вказівник іншого несумісного типу. Спроба зробити `std::launder(reinterpret_cast<float*>(int_ptr))` не рятує від UB, якщо в пам'яті реально лежить `int`.
3. **Об'єкт не повинен бути `void` або функцією.** Шаблон `std::launder` заборонено інстанціювати для `void*` або вказівників на функції — такий код просто не скомпілюється.
4. **Межі байтового сховища.** Усі байти розміром `sizeof(T)`, починаючи з адреси `p`, повинні належати одному виділеному сховищу.

Зведена таблиця ситуацій демонструє, коли використання `std::launder` є обов'язковим, коли воно є зайвим, а коли призводить до помилки:

| Сценарій у коді | Необхідність `std::launder` | Наслідки без `std::launder` |
| :--- | :--- | :--- |
| Повторне створення об'єкта з `const`-полями через placement `new` у тому самому буфері | **Обов'язково** (якщо доступ через старий вказівник чи `reinterpret_cast`) | UB: `Constant Propagation` повертає старе значення |
| Повторне створення об'єкта з полями-посиланнями (`T&`) | **Обов'язково** | UB: оптимізатор вважає, що адреса посилання незмінна |
| Зміна динамічного типу поліморфного об'єкта за фіксованою адресою | **Обов'язково** | UB: помилкова девіртуалізація старих методів |
| Використання безпосереднього результату placement `new`: `auto* p = new (buf) T()` | **Зайве** | Помилки немає, але `std::launder` надлишковий (результат `new` уже валідний) |
| Звичайні типи без `const`, посилань і віртуальних функцій (просте прозоре заміщення) | **Зайве** | Автоматичне прозоре заміщення за `[basic.life]` |
| Виклик на сирій неініціалізованій пам'яті до створення об'єкта | **Заборонено (UB)** | `std::launder` вимагає живого об'єкта в пам'яті |
| Спроба обійти Strict Aliasing (читання `int` як `float`) | **Заборонено (UB)** | Порушення системи типів C++ |

## Помилкові уявлення та підводні камені

Навколо `std::launder` виникло чимало міфів серед розробників C++. Розглянемо найпоширеніші помилки:

### Міф 1: «std::launder потрібен після кожного placement new»

Це хибне твердження. Якщо результат виразу `new (buf) T(...)` зберігається у змінну й використовується безпосередньо, `std::launder` не потрібен взагалі:

```cpp
void correct_usage() {
    alignas(Config) std::byte buf[sizeof(Config)];
    Config* p1 = new (buf) Config{10};
    std::cout << p1->timeout_ms << '\n'; // 100% легально

    p1->~Config();
    Config* p2 = new (buf) Config{20};   // p2 повернено з new
    std::cout << p2->timeout_ms << '\n'; // 100% легально, std::launder НЕ потрібен!
}
```

Потреба у `std::launder` виникає лише тоді, коли ви втратили прямий вказівник `p2` і змушені відновлювати його через `reinterpret_cast<Config*>(buf)` або використовувати старий вказівник `p1`.

### Міф 2: «std::launder ініціалізує байти пам'яті або створює об'єкт»

`std::launder` не виконує жодних операцій запису в пам'ять. Якщо виділити сирий буфер через `malloc` або `std::byte buf[16]` і одразу викликати `std::launder(reinterpret_cast<int*>(buf))`, програма отримає невизначену поведінку, оскільки в буфері немає створеного об'єкта `int`.

### Міф 3: «std::launder дозволяє безпечно читати union не за активним полем»

У C++ (на відміну від C) читання неактивного члена об'єднання (`type punning` через `union`) є невизначеною поведінкою. Виклик `std::launder` над неактивним членом `union` не робить його активним і не рятує від UB.

## Еволюція в C++20 і C++23: std::construct_at та створення часу життя

У стандартах C++20 та C++23 модель пам'яті отримала важливі уточнення, які полегшили роботу зі сховищем об'єктів.

### 1. `std::construct_at` (C++20)

У C++20 з'явилася стандартна функція `std::construct_at` (заголовковий файл `<memory>`), яка замінює прямий синтаксис розміщувального `new`:

```cpp
#include <memory>

template <class T, class... Args>
constexpr T* construct_at(T* p, Args&&... args);
```

Ключова перевага `std::construct_at` полягає в тому, що вона:
- Працює у `constexpr`-виразах під час компіляції;
- Гарантовано повертає валідний вказівник на новостворений об'єкт.

Якщо ви зберігаєте результат `std::construct_at` і звертаєтеся до полів виключно через нього, потреба у ручному виклику `std::launder` відпадає:

```cpp
auto* fresh = std::construct_at(reinterpret_cast<Config*>(buffer), 500);
std::cout << fresh->timeout_ms << '\n'; // Коректно: fresh повертає новий об'єкт
```

Проте якщо через деякий час в іншій функції вам знову знадобиться витягти `Config*` із сирого `buffer`, виклик `std::launder(reinterpret_cast<Config*>(buffer))` залишається обов'язковим.

### 2. Неявне створення часу життя та `std::start_lifetime_as` (C++23)

Для типів із тривіальним часом життя (англ. *implicit-lifetime types*) операції копіювання байтів на кшталт `std::memcpy`, `malloc` або зчитування з сокета в буфер `std::byte[]` у C++20/C++23 неявно створюють об'єкти.

Але якщо тип є нетривіальним або містить `const`-члени, операція `memcpy` не розпочинає його час життя автоматично. Для вирішення цієї проблеми у C++23 було додано сімейство функцій `std::start_lifetime_as` (P2590R2):

```cpp
#include <memory>

// C++23: явний старт часу життя у байтовому сховищі
auto* obj = std::start_lifetime_as<Config>(buffer);
```

Функція `std::start_lifetime_as<T>` не лише створює об'єкт у сховищі без виклику конструктора (якщо байти вже заповнені, наприклад, з файлу), а й неявно виконує семантику `std::launder`, повертаючи абсолютно валідний вказівник для компілятора.

## Підсумкова картина інваріантів

Модель пам'яті C++ тримається на балансі двох протилежних сил:
1. **Свобода оптимізатора**: можливість агресивно кешувати константи, розгортати цикли та девіртуалізувати виклики, спираючись на `const`, посилання та типи;
2. **Гнучкість програміста**: можливість перевикористовувати виділені сторінки пам'яті, створювати гетерогенні контейнери та власні механізми розміщення.

`std::launder` є мостом між цими двома світами. Він не сповільнює виконання жодною інструкцією, але дає оптимізатору чіткий сигнал: старі припущення про інваріанти за цією адресою анульовано. Розуміння його семантики перетворює низькорівневу роботу з пам'яттю з лотереї оптимізацій на суворий і надійний інженерний процес.
