# 📋 Правила та синтаксис constinit: формальний довідник

Специфікатор `constinit` уведений міжнародним стандартом C++20 у розділі `[dcl.constinit]` як мовний механізм прямого контролю фази ініціалізації об'єктів. Його головна мета — примусово закріпити ініціалізацію змінної виключно у фазі константної ініціалізації (англ. *constant initialization*), що виконується під час збірки програми або безпосередньо при завантаженні бінарного файлу операційною системою. Якщо ініціалізатор неможливо обчислити на етапі компіляції, компілятор відмовляється збирати програму і генерує детальне повідомлення про помилку.

## Граматика та правила розміщення в тексті програми

У синтаксичній структурі мови C++20 специфікатор `constinit` належить до групи специфікаторів оголошення (англ. *declaration specifiers*). Він застосовується виключно до оголошень змінних і може комбінуватися з іншими специфікаторами у довільному порядку, хоча усталена ідіоматична практика ставить його на самий початок оголошення перед специфікаторами тривалості зберігання та типом.

```cpp
// Ідіоматичний порядок розміщення специфікаторів:
constinit static int global_device_counter = 0;
constinit thread_local unsigned long current_thread_epoch = 1;
constinit inline double global_sampling_ratio = 0.05;
constinit const char* const firmware_version_tag = "v2.4.1";
```

### Дозволені контексти застосування

Згідно з пунктом стандарту `[dcl.constinit]`, специфікатор `constinit` дозволено застосовувати лише до тих змінних, які володіють **статичною тривалістю зберігання** (англ. *static storage duration*) або **потоковою тривалістю зберігання** (англ. *thread storage duration*). Усі такі об'єкти існують протягом усього часу роботи програми або всього часу життя окремого операційного потоку.

До дозволених контекстів належать чотири категорії сутностей:

1. **Глобальні змінні.** Змінні, оголошені на рівні файлу в глобальному просторі імен, а також змінні всередині явно іменованих або безіменних (`anonymous namespace`) просторів імен.
2. **Статичні змінні-члени класів та структур.** Поля класів, оголошені зі специфікатором `static`. Вони належать не окремому екземпляру класу, а самому типу, і мають статичну тривалість зберігання.
3. **Локальні статичні змінні.** Змінні, оголошені всередині тіла функцій, методів, блоків коду або лямбда-виразів із ключовим словом `static`. За замовчуванням локальні статичні змінні ініціалізуються при першому вході керування у функцію, однак наявність `constinit` змушує компілятор виконати ініціалізацію заздалегідь, до старту виконання програми.
4. **Потоково-локальні змінні (`thread_local`).** Змінні, оголошені з ключовим словом `thread_local` на рівні простору імен, класу або локального блоку функції. Для кожного новоствореного потоку операційна система виділяє окремий екземпляр такої змінної.

### Заборонені контексти та некоректні конструкції

Застосування `constinit` до сутностей з автоматичною або динамічною тривалістю зберігання є грубою синтаксичною помилкою, яку компілятор зобов'язаний діагностувати на етапі синтаксичного аналізу.

Нижче наведено вичерпний перелік заборонених контекстів із детальним поясненням причини заборони:

- **Автоматичні змінні на стеку:** Змінні, що створюються всередині функцій без специфікатора `static`, розміщуються в кадрі стека під час виконання. Їхнє життя прив'язане до моменту виклику функції, тому концепція статичної константної ініціалізації до них не застосовна в принципі.
- **Параметри функцій:** Аргументи, що передаються у функцію, обчислюються у місці виклику і формуються в регістрах процесора або на стеку безпосередньо перед передачею керування.
- **Нестатичні поля класів і структур:** Нестатичні змінні-члени є складовими частинами екземпляра об'єкта. Їхній розподіл у пам'яті відбувається в момент конструювання конкретного екземпляра (на стеку, у купі через `new` або всередині іншого об'єкта).
- **Оголошення функцій і методів:** `constinit` контролює стан пам'яті для даних, а не машинний код функцій. Для примусового обчислення функцій під час компіляції існує окремий специфікатор `consteval`.
- **Псевдоніми типів (`typedef` та `using`):** Специфікатор `constinit` не є модифікатором типу і не входить до сигнатури типу (на відміну від `const` або `volatile`). Спроба включити його у визначення псевдоніма типу є синтаксично некоректною.
- **Структуровані зв'язування (`structured bindings`):** Стандарт C++20 явно забороняє застосування `constinit` до синтаксису `auto [x, y]`, оскільки структуроване зв'язування розкладає тимчасовий об'єкт або посилання, що має власні специфічні правила ініціалізації полів.

```cpp
// ПОМИЛКА 1: Автоматична змінна в тілі функції
void calculate_hash() {
    constinit int seed_value = 0x9e3779b9; // Помилка: автоматична тривалість зберігання
}

// ПОМИЛКА 2: Параметр функції
void set_timeout(constinit int milliseconds); // Помилка: параметри не мають статичної тривалості

// ПОМИЛКА 3: Нестатичне поле структури
struct PacketHeader {
    constinit uint16_t magic_number = 0x55AA; // Помилка: нестатичне поле екземпляра
};

// ПОМИЛКА 4: Оголошення функції
constinit int compute_initial_capacity(); // Помилка: constinit не застосовується до функцій

// ПОМИЛКА 5: Структуроване зв'язування
struct Coordinates { int latitude; int longitude; };
constinit auto [lat, lon] = Coordinates{50, 30}; // Помилка: заборонено стандартом
```

## Матриця взаємодії з іншими специфікаторами мови

Специфікатор `constinit` займає унікальну позицію в системі типів C++, оскільки він впливає виключно на часовий момент ініціалізації об'єкта, не накладаючи обмежень на його подальшу модифікацію під час виконання.

Розглянемо детально правила його поєднання з іншими специфікаторами та ключовими словами:

### Взаємодія зі специфікатором static

Комбінація `constinit static` є повністю коректною і широко використовується. Для глобальних змінних та змінних у просторах імен ключове слово `static` задає внутрішнє зв'язування (англ. *internal linkage*), обмежуючи видимість символу поточною одиницею трансляції. Для змінних усередині функцій `static` перетворює автоматичну змінну на локальну статичну, надаючи їй необхідну статичну тривалість зберігання.

### Взаємодія зі специфікатором thread_local

Поєднання `constinit thread_local` дозволяє кардинально оптимізувати роботу зі змінними, що створюються для кожного потоку виконання. Без `constinit` компілятор змушений генерувати приховану функцію-обгортку та прапорець ініціалізації для кожного потоку, перевіряючи цей прапорець при кожному зверненні до змінної. Застосування `constinit` гарантує, що початковий образ змінної формується на етапі компіляції і розміщується безпосередньо в секції даних локальної пам'яті потоку (`.tdata`), усуваючи накладні витрати під час виконання.

### Взаємодія зі специфікатором inline

Поєднання `constinit inline` є ключовим інструментом для розробників бібліотек, що складаються виключно із заголовкових файлів (англ. *header-only libraries*). Специфікатор `inline` дозволяє розміщувати визначення глобальної змінної безпосередньо в `.hpp` файлі, гарантуючи виконання правила одного визначення (англ. *One Definition Rule*, ODR): компонувальник об'єднує всі екземпляри змінної з різних одиниць трансляції в один спільний об'єкт. Специфікатор `constinit` додатково гарантує, що цей об'єкт ініціалізується статично до старту будь-якого динамічного коду.

### Взаємодія зі специфікатором const

Комбінація `constinit const` є синтаксично коректною і означає, що змінна зобов'язана пройти константну ініціалізацію під час збірки, а також є повністю незмінною (read-only) під час виконання програми. На відміну від звичайного `const`, який дозволяє мовчазне перемикання на динамічну ініціалізацію при виклику звичайної функції, `constinit const` видає помилку компіляції, якщо ініціалізатор не є константним виразом.

### Взаємне виключення з constexpr та consteval

Одночасне використання `constinit` та `constexpr` в одному оголошенні суворо заборонене стандартом мови. Причина полягає в тому, що специфікатор `constexpr` на змінній уже включає в себе вимогу константної ініціалізації та автоматично робить тип змінної константним (`const`). Дублювання цих вимог через `constinit` визнано надлишковим і заборонено синтаксисом.

Специфікатор `consteval` застосовується виключно до функцій, вимагаючи, щоб кожен виклик такої функції відбувався під час компіляції. Оскільки `constinit` застосовується виключно до змінних, їхнє поєднання неможливе.

### Посилання та constinit

Специфікатор `constinit` можна застосовувати до оголошень посилань (`constinit T& ref = target;`), якщо посилання прив'язується до об'єкта зі статичною тривалістю зберігання. У цьому випадку адреса цільового об'єкта повинна бути відома на етапі компонування, а саме посилання стає статично ініціалізованим покажчиком у бінарному файлі.

## Низькорівневе розміщення у двійкових секціях (ELF та PE/COFF)

Розуміння роботи `constinit` вимагає погляду на те, як операційна система та компонувальник розміщують змінні у пам'яті виконуваного файлу:

1. **Секція `.data` (Ініціалізовані мутабельні дані):** Глобальні та статичні змінні з `constinit`, які не є `const`, потрапляють безпосередньо у секцію `.data`. Двійковий образ їхніх початкових байтів записується компілятором у файл на диску. При завантаженні програми ядро операційної системи відображає (через `mmap` або завантажувач PE) ці сторінки пам'яті в адресний простір процесу з правами читання та запису (Read-Write). Значення вже присутні в пам'яті в момент створення процесу, до виконання будь-якої інструкції машинного коду.
2. **Секція `.rodata` або `.rdata` (Дані лише для читання):** Якщо змінна оголошена як `constinit const`, вона розміщується в захищеній секції константних даних. Операційна система позначає відповідні сторінки віртуальної пам'яті правами лише для читання (Read-Only), що викликає апаратний захист від модифікації процесором.
3. **Секції `.tdata` та `.tbss` (Локальні дані потоків TLS):** Для `constinit thread_local` змінних початковий шаблон формується в секції `.tdata` (якщо є ненульовий ініціалізатор) або `.tbss` (якщо значення нульове). При створенні нового потоку операційна система або бібліотека `pthreads` виділяє блок пам'яті для потоку і копіює туди готовий образ секції `.tdata`. Звернення до змінної згенерованим машинним кодом виконується через прямий зсув від регістра базової адреси сегмента потоку (регістр `%fs` на архітектурі x86-64 Linux або `%gs` на Windows x64), що не вимагає виклику жодних функцій перевірки.

## Порівняльний аналіз чотирьох специфікаторів стану

Для точного проектування архітектури програми стандарт C++20 надає чотири специфікатори, які часто плутають між собою. Їхня поведінка та призначення суттєво відрізняються за фундаментальними характеристиками:

| Критерій порівняння | constinit | constexpr (змінна) | const | consteval |
| :--- | :--- | :--- | :--- | :--- |
| **До чого застосовується** | Тільки змінні | Змінні або функції | Змінні або методи | Тільки функції |
| **Етап ініціалізації** | Компіляція / завантаження | Компіляція | Компіляція або виконання | Компіляція (при виклику) |
| **Мутабельність значення** | **Змінне (Read-Write)** | Завжди незмінне (Read-Only) | Завжди незмінне (Read-Only) | Не застосовується |
| **Тривалість зберігання** | Тільки `static` / `thread_local` | Будь-яка (включно зі стеком) | Будь-яка (стек, купа, статика) | Не застосовується |
| **Використання у static_assert** | Ні (якщо без `const`) | **Так, завжди** | Лише для цілих / enum | Результат виклику — так |
| **Вимоги до деструктора** | Будь-який деструктор | Тільки тривіальний (у статиці) | Будь-який деструктор | Не застосовується |
| **Реакція на неконстантний вираз** | **Помилка компілятора** | **Помилка компілятора** | Мовчазний перехід у рантайм | **Помилка компілятора** |
| **Захист від проблеми SIOF** | **100% гарантований** | **100% гарантований** | Відсутній (залежить від виразу) | Не застосовується |

## Фази ініціалізації та виконання деструкторів

Специфікатор `constinit` чітко розмежовує фази життєвого циклу об'єкта зі статичною тривалістю зберігання:

1. **Фаза нульової ініціалізації (Zero-initialization):** До початку виконання будь-яких інструкцій програми операційна система виділяє сторінки пам'яті для сегментів `.bss` та `.data`, занулюючи всі байти неініціалізованих статичних змінних.
2. **Фаза константної ініціалізації (Constant initialization):** Компілятор під час збірки обчислює початковий стан `constinit`-об'єкта і записує його двійковий образ безпосередньо у бінарний файл. При завантаженні програми ці дані негайно стають доступними в сегменті пам'яті `.data`. Ця фаза завершується абсолютно для всіх константних об'єктів до того, як розпочнеться перший крок динамічної ініціалізації.
3. **Фаза динамічної ініціалізації (Dynamic initialization):** Середовище виконання C++ послідовно викликає конструктори глобальних об'єктів, які потребують обчислень під час виконання. Будь-який такий конструктор може безпечно зчитувати стан `constinit`-змінних або записувати в них дані: стан `constinit`-об'єктів гарантовано готовий і валідний.
4. **Фаза знищення (Destruction):** Після виходу з функції `main()` або при виклику системної функції `std::exit()` середовище виконання починає викликати деструктори глобальних об'єктів у порядку, зворотному до завершення їхньої динамічної ініціалізації. Для `constinit`-об'єктів деструктори реєструються через системний механізм `__cxa_atexit` і виконуються коректно. Це критична перевага `constinit` над `constexpr`: `constexpr`-об'єкти зі статичною тривалістю зберігання зобов'язані мати тривіальний деструктор, тоді як `constinit` дозволяє використовувати класи з повноцінними користувацькими деструкторами (наприклад, для коректного закриття дескрипторів файлів або скидання буферів пам'яті на диск перед завершенням процесу).

## Детальний аналіз діагностичних повідомлень компіляторів

Коли вираз ініціалізації для `constinit`-змінної порушує правила обчислення константних виразів (англ. *core constant expressions*), компілятор генерує дерево діагностики, що вказує на точну причину відмови. Розглянемо чотири найтиповіші сценарії помилок та реакцію провідних компіляторів (GCC, Clang, MSVC).

### Сценарій 1: Виклик функції без специфікатора constexpr

```cpp
int generate_unique_seed() {
    return 42;
}

constinit int app_seed = generate_unique_seed();
```

Причина відмови полягає в тому, що функція `generate_unique_seed` не має специфікатора `constexpr`. Навіть якщо її тіло складається лише з повернення літерала `42`, компілятор не має права викликати її в контексті інтерпретатора сталих виразів:

- **GCC:**
  ```text
  error: 'constinit' variable 'app_seed' does not have a constant initializer
  note: call to non-'constexpr' function 'int generate_unique_seed()'
  ```
- **Clang:**
  ```text
  error: variable does not have a constant initializer
  note: required by 'constinit' specifier here
  note: non-constexpr function 'generate_unique_seed' cannot be used in a constant expression
  ```
- **MSVC:**
  ```text
  error C2127: 'app_seed': illegal initialization of 'constinit' entity with a non-constant expression
  note: a non-constexpr function 'generate_unique_seed' cannot be used in a constant expression
  ```

### Сценарій 2: Звернення до змінної з динамічним значенням

```cpp
int system_page_size = 4096;

constinit int default_buffer_size = system_page_size * 2;
```

Змінна `system_page_size` не оголошена як `const` або `constexpr`, тому її значення може бути змінене будь-яким потоком у будь-який момент часу виконання. Інтерпретатор сталих виразів компілятора не може гарантувати сталість цієї величини під час збірки:

- **GCC:**
  ```text
  error: 'constinit' variable 'default_buffer_size' does not have a constant initializer
  note: the value of 'system_page_size' is not usable in a constant expression
  ```
- **Clang:**
  ```text
  error: variable does not have a constant initializer
  note: read of non-const variable 'system_page_size' is not allowed in a constant expression
  ```
- **MSVC:**
  ```text
  error C2127: 'default_buffer_size': illegal initialization of 'constinit' entity with a non-constant expression
  note: the value of variable 'system_page_size' cannot be used in a constant expression
  ```

### Сценарій 3: Витік динамічної пам'яті всередині constexpr-конструктора

Стандарт C++20 дозволяє виділяти динамічну пам'ять за допомогою оператора `new` всередині `constexpr`-виразів. Проте стандарт висуває суворий інваріант: уся пам'ять, виділена під час сталого обчислення, повинна бути повністю звільнена оператором `delete` до завершення обчислення цього виразу. Пам'ять із купи не може пережити етап компіляції і потрапити в бінарний файл.

```cpp
struct DynamicArray {
    int* data;
    constexpr DynamicArray(int size) {
        data = new int[size]{}; // Виділення динамічної пам'яті
        // Оператор delete не викликано — витік пам'яті!
    }
};

constinit DynamicArray g_array{16};
```

- **GCC:**
  ```text
  error: 'constinit' variable 'g_array' does not have a constant initializer
  note: dynamic memory allocated by 'new' is not deallocated before the end of the constant expression
  ```
- **Clang:**
  ```text
  error: variable does not have a constant initializer
  note: pointer to subobject of heap-allocated object is not a constant expression
  ```
- **MSVC:**
  ```text
  error C2127: 'g_array': illegal initialization of 'constinit' entity with a non-constant expression
  note: memory allocated during evaluation was not freed before completion
  ```

### Сценарій 4: Вихід за межі масиву та невизначена поведінка

Обчислювач сталих виразів усередині компілятора працює в режимі суворої перевірки на невизначену поведінку (UB). Будь-яка спроба виходу за межі масиву, розіменування нульового покажчика чи знакового переповнення негайно перериває обчислення і генерує помилку `constinit`:

```cpp
constexpr int get_lookup_entry(int index) {
    constexpr int table[3] = {10, 20, 30};
    return table[index]; // Якщо index >= 3, виникає UB
}

constinit int bad_lookup = get_lookup_entry(5);
```

- **GCC:**
  ```text
  error: 'constinit' variable 'bad_lookup' does not have a constant initializer
  note: array subscript value '5' is outside the bounds of array 'table' of type 'const int [3]'
  ```
- **Clang:**
  ```text
  error: variable does not have a constant initializer
  note: array subscript 5 is outside the bounds of array type 'const int[3]'
  ```
- **MSVC:**
  ```text
  error C2127: 'bad_lookup': illegal initialization of 'constinit' entity with a non-constant expression
  note: out of bounds array access in constant evaluation
  ```

## Взаємодія з модулями C++20 (Modules)

При переході на модульну систему C++20 (`import` / `export`) специфікатор `constinit` поводиться безшовно:

```cpp
// telemetry_module.ixx
export module telemetry;

export struct SessionMetrics {
    unsigned long requests_count;
    unsigned long errors_count;
    constexpr SessionMetrics() : requests_count(0), errors_count(0) {}
};

export constinit SessionMetrics g_session_metrics{};
```

Експортована змінна `g_session_metrics` стає видимою для всіх модулів, що імпортують `telemetry`. Компілятор та компонувальник гарантують, що змінна буде розміщена в секції ініціалізованих даних і підготовлена до використання до запуску будь-якого коду клієнтських модулів.

## Інженерні рекомендації щодо використання

Для забезпечення максимальної надійності масштабних програмних комплексів рекомендується дотримуватися таких правил:

1. **Захист усіх мутабельних глобальних об'єктів:** Якщо об'єкт зі статичною тривалістю зберігання є змінюваним (`std::atomic`, м'ютекс, буфер подій), його оголошення повинно супроводжуватися специфікатором `constinit`. Це на 100% захищає архітектуру програми від випадкової появи SIOF.
2. **Використання в заголовкових файлах разом з inline:** Усі спільні глобальні об'єкти конфігурації чи реєстрів у бібліотеках повинні оголошуватися як `inline constinit`, що забезпечує коректне об'єднання символів компонувальником без накладних витрат у часі виконання.
3. **Оптимізація потокового стану:** Для високонавантажених потокових обробників слід замінювати динамічні змінні `thread_local` на `constinit thread_local`, перетворюючи доступ до змінних потоку на пряму адресацію пам'яті без системних функцій-обгорток.
