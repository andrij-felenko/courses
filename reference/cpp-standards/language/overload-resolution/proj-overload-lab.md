# 🧪 Лабораторія добору: програма, що сама каже, кого обрано

Читати правила добору й бачити їхню роботу — різні речі, і звичний спосіб побачити тут не працює. Покласти друк усередину кожного перевантаження можна, але найповчальніші випадки до запуску не доходять зовсім: вони закінчуються помилкою компіляції. Тому лабораторія нижче дістає відповідь «кого обрано» двічі — під час запуску й **до** нього, з того самого набору перевантажень, — а потім цей набір навмисно ламається, щоб побачити, якими словами про кожну поломку говорить компілятор. Усе — один файл на C++20 без жодної зовнішньої залежності.

## Ідея: хай відповідь буде типом результату

Тип повернення в доборі не бере участі — саме тому `int g(); double g();` це не перевантаження, а помилка повторного оголошення. Для нас це вільний канал зв'язку: віддамо кожному перевантаженню **власний тип результату**, який не робить нічого, крім того, що називає себе. Один і той самий виклик тоді відповідає двома способами: при запуску — полем `who` у мітці, а при компіляції — через [`decltype`](topic:cpp-standards/decltype), бо `decltype(f(x))` дає тип результату, не викликаючи функції взагалі.

## Драбина на живому наборі

```cpp
// lab.cpp — g++ -std=c++20 lab.cpp   |   clang++ -std=c++20 lab.cpp
#include <cstdio>

// Мітки: за типом результату впізнаємо переможця.
struct AsInt    { static constexpr const char* who = "f(int)";    };
struct AsDouble { static constexpr const char* who = "f(double)"; };
struct AsBool   { static constexpr const char* who = "f(bool)";   };
struct AsMeters { static constexpr const char* who = "f(Meters)"; };
struct AsAny    { static constexpr const char* who = "f(...)";    };

struct Meters { double v; };
struct Feet   { double v; operator Meters() const { return { v * 0.3048 }; } };
struct Blob   { };                    // ні в що не перетворюється

AsInt    f(int)    { return {}; }
AsDouble f(double) { return {}; }
AsBool   f(bool)   { return {}; }
AsMeters f(Meters) { return {}; }
AsAny    f(...)    { return {}; }

#define SHOW(expr) std::printf("%-14s → %s\n", #expr, (expr).who)

int main() {
    short s = 7;
    float x = 1.5f;
    const char* text = "мс";

    SHOW( f(42)        );   // точний збіг
    SHOW( f(s)         );   // підвищення   short → int
    SHOW( f(x)         );   // підвищення   float → double
    SHOW( f('a')       );   // підвищення   char  → int
    SHOW( f(text)      );   // перетворення const char* → bool
    SHOW( f(Feet{1.0}) );   // користувацьке перетворення
    SHOW( f(Blob{})    );   // нікуди більше — багатокрапка
}
```

```
f(42)          → f(int)
f(s)           → f(int)
f(x)           → f(double)
f('a')         → f(int)
f(text)        → f(bool)
f(Feet{1.0})   → f(Meters)
f(Blob{})      → f(...)
```

Середина виводу — це і є драбина. `short` придатний для трьох іменованих кандидатів, але до `int` він іде підвищенням, а до `double` і `bool` — перетворенням, тож `f(int)` виграє одноосібно; `char` дає точнісінько таку саму картину. З `float` дзеркально: підвищення веде в `double`, а решта шляхів — перетворення. А от `const char*` не має підвищення нікуди; єдиний іменований кандидат, до якого веде хоч якийсь шлях, — це `f(bool)` через булеве перетворення, і воно перемагає багатокрапку. Саме тому рядок мовчки перетворився на `true`, і це не збій, а штатна робота правил.

Два останні рядки перевіряють кінці драбини. `Feet` не має жодної стандартної дороги до параметрів набору, зате має оператор приведення до `Meters` — один користувацький крок, який бере верх лише над багатокрапкою. `Blob` не має й цього, тому лишається останній щабель. Порожня структура з тривіальним копіюванням проходить крізь `...` законно; тип із власним копіювальним конструктором чи деструктором туди передавати вже не можна.

## Нульова позиція: об'єкт перед крапкою

Той самий прилад працює й на методах, бо для добору вираз ліворуч від крапки — просто ще один аргумент, нульовий:

```cpp
struct AsMut   { static constexpr const char* who = "data()";       };
struct AsConst { static constexpr const char* who = "data() const"; };

struct Buf {
    AsMut   data()       { return {}; }   // неявний параметр: Buf&
    AsConst data() const { return {}; }   // неявний параметр: const Buf&
};

Buf b;
const Buf& cb = b;

SHOW( b.data()  );
SHOW( cb.data() );
```

```
b.data()       → data()
cb.data()      → data() const
```

Окремого «вибору за константністю» не існує: неконстантний об'єкт бере перший метод точним збігом, а для константного першого кандидата просто немає — до `Buf&` з `const Buf&` дороги нема. Практична вигода та сама, що й раніше: `static_assert(std::is_same_v<decltype(cb.data()), AsConst>)` прибиває цвяхом, що дорога тільки читає, і зловить день, коли хтось випадково зніме `const` десь по колії виклику.

## Спитати компілятор, не запускаючи програми

Мітка працює й тоді, коли програма не запускається — бо `decltype` нічого не викликає. Допишемо у той самий файл:

```cpp
#include <type_traits>

short       probe_s{};
float       probe_x{};
const char* probe_p{};

static_assert(std::is_same_v<decltype(f(42)),        AsInt>);
static_assert(std::is_same_v<decltype(f(probe_s)),   AsInt>);
static_assert(std::is_same_v<decltype(f(probe_x)),   AsDouble>);
static_assert(std::is_same_v<decltype(f(probe_p)),   AsBool>);
static_assert(std::is_same_v<decltype(f(Feet{1.0})), AsMeters>);
static_assert(std::is_same_v<decltype(f(Blob{})),    AsAny>);
```

Цей блок не додає до програми ані байта й не потребує навіть визначень функцій — самих оголошень досить, бо виклик не відбувається ([риси типів](topic:cpp-standards/type-traits) тут лише порівнюють два типи). І в цьому головна практична користь усього прийому: такий `static_assert` у тесті прибиває цвяхом, куди саме йде конкретний виклик у вашій кодовій базі. Коли завтра хтось додасть у бібліотеку ще одне перевантаження й добір поїде, ви дізнаєтеся про це помилкою компіляції, а не зміною поведінки програми.

Незручність одна: `static_assert` каже «не збіглося», але не каже, з чим саме. Ім'я переможця витягується сусіднім прийомом — оголосити шаблон без тіла й змусити компілятор його інстанціювати:

```cpp
template <class...> struct Show;      // лише оголошення, визначення немає
Show<decltype(f(probe_p))> tell;      // навмисна помилка
```

```
g++:     error: aggregate 'Show<AsBool> tell' has incomplete type and cannot be defined
clang++: error: implicit instantiation of undefined template 'Show<AsBool>'
```

Тип названо у самому тексті помилки — це найдешевший спосіб побачити будь-який виведений тип, не лише переможця добору.

## Поломка перша: усі на одному щаблі

```cpp
SHOW( f(7L) );
```

```
g++ (скорочено):
lab.cpp: error: call of overloaded 'f(long int)' is ambiguous
lab.cpp: note: candidate: 'AsInt f(int)'
lab.cpp: note: candidate: 'AsDouble f(double)'
lab.cpp: note: candidate: 'AsBool f(bool)'
```

`long` не має підвищення до жодного з цих типів: усі три шляхи — перетворення, усі три на одному щаблі, жоден не кращий. Список кандидатів тут читається не як «хтось із них правильніший», а як «ось усі, хто набрав однаково». Полагодити можна з боку виклику — `f(static_cast<int>(7L))` — або додавши перевантаження `f(long)`, яке візьме аргумент точним збігом.

Другий досвід показує нічию складнішого роду — коли розряди не однакові, а просто непорівнянні:

```cpp
struct AsIntDbl { static constexpr const char* who = "p(int, double)"; };
struct AsDblInt { static constexpr const char* who = "p(double, int)"; };

AsIntDbl p(int, double) { return {}; }
AsDblInt p(double, int) { return {}; }

SHOW( p(1, 2.5) );      // друкує p(int, double)
SHOW( p(1, 2)   );      // error: call of overloaded 'p(int, int)' is ambiguous
```

У першому виклику перший кандидат точний на обох позиціях — виграв за всіма й не програв ніде. У другому кожен точний на своїй позиції й гірший на чужій, а поступка на одній позиції не купує переваги на іншій. Прикметно, чим це **не** лікується: додати третього кандидата `p(long, long)`, гіршого за обох, — і неоднозначність лишиться, бо переможець мусить бути кращим за всіх, а не за когось. Лікує лише кандидат, строго кращий за обох: `p(int, int)` бере обидва аргументи точним збігом і забирає виклик собі.

## Поломка друга: імені немає в списку

```cpp
struct Device {
    void send(int code)        { std::puts("Device::send(int)"); }
    void send(const char* msg) { std::puts("Device::send(const char*)"); }
};
struct Radio : Device {
    void send(double hz)       { std::puts("Radio::send(double)"); }
};

Radio r;
r.send("ping");
```

```
clang++ (скорочено):
lab.cpp: error: no matching member function for call to 'send'
lab.cpp: note: candidate function not viable: no known conversion
               from 'const char[5]' to 'double' for 1st argument
```

У списку **один** кандидат. Це і є діагноз: `Device::send` не програв — його там немає, бо пошук імені зупинився на `Radio`. Правило читання просте: якщо в переліку кандидатів бракує функції, яку ви точно писали, помилка сталася ще до порівняння. Лікується одним рядком у похідному класі:

```cpp
struct Radio : Device {
    using Device::send;                 // утягнути базові оголошення
    void send(double hz)       { std::puts("Radio::send(double)"); }
};
```

```
Device::send(const char*)
```

Тепер усі три оголошення в одній області видимості й змагаються нормально; докладніше про сам механізм — у [затулянні імен і using-оголошеннях](topic:cpp-standards/using-and-name-hiding).

## Поломка третя: шаблон, що з'їв копіювальний конструктор

```cpp
#include <utility>                      // std::as_const

struct Person {
    template <class S>
    explicit Person(S&&) { std::printf("шаблон: %s\n", __PRETTY_FUNCTION__); }
    Person(const Person&) { std::puts("копіювальний конструктор"); }
};

Person a{"Ада"};
Person b{a};                    // копія?
Person c{std::as_const(a)};     // теж копія?
```

```
шаблон: Person::Person(S&&) [with S = const char (&)[7]]
шаблон: Person::Person(S&&) [with S = Person&]
копіювальний конструктор
```

Другий рядок — та сама поломка, через яку копії тихо перестають бути копіями. `a` — неконстантне lvalue, шаблон виводить `S = Person&`, параметр стає `Person&` і бере аргумент точним збігом; копіювальному ж треба додати `const`, а це вже гірший розряд. Розряди різні — отже, до правила «шаблон програє звичайній функції» справа не доходить, воно вмикається лише за рівних. Третій рядок це підтверджує: для константного lvalue обидва кандидати точні, рахунок рівний — і перемагає нешаблонний.

`__PRETTY_FUNCTION__` тут другий прилад лабораторії: він друкує сигнатуру разом із виведеними аргументами шаблона, тож видно не лише «спрацював шаблон», а й з чим саме (Clang друкує те саме трохи інакше: `[S = Person &]`). Ліки — не пускати шаблон до власного типу:

```cpp
#include <concepts>
#include <type_traits>

// той самий конструктор усередині Person, лише з обмеженням
template <class S>
    requires (!std::same_as<std::remove_cvref_t<S>, Person>)
explicit Person(S&&) { std::printf("шаблон: %s\n", __PRETTY_FUNCTION__); }
```

Тепер `Person b{a}` друкує «копіювальний конструктор»: обмеження ([концепти](topic:cpp-standards/concepts-constraints)) прибирає шаблон із кандидатів ще до порівняння, а не робить його гіршим. Це стандартна плата за передавальне посилання — те саме обмеження носить із собою кожна фабрика на [ідеальному передаванні](topic:cpp-standards/perfect-forwarding).

## Поломка четверта: перевантаження як заборона

Додамо в набір лабораторії один рядок:

```cpp
AsInt f(char) = delete;
```

```
g++:     error: use of deleted function 'AsInt f(char)'
clang++: error: call to deleted function 'f'
         note: candidate function has been explicitly deleted
```

Рядок `SHOW( f('a') )`, який щойно друкував `f(int)`, тепер не компілюється — і це саме те, чого хотіли. Видалене перевантаження бере символ точним збігом, виграє в усіх, і перемога видаленої функції є помилкою. Якби `= delete` означало «мене не видно», виклик тихо пішов би туди ж, куди й раніше, і заборона нічого не заборонила б. Так само закривають від функції випадкові `nullptr`, вужчі цілі типи чи тимчасові об'єкти — не приховуючи перевантаження, а навпаки, підставляючи його під перемогу.

## Читати список кандидатів

Перелік `note: candidate…` — це не рейтинг. Компілятор друкує кандидатів у порядку оголошення, і найперший у списку рівно так само програв, як останній. Корисне в кожному рядку інше: у придатних дивляться на позицію, де вектор розійшовся, а в непридатних — на фразу `no known conversion for argument N`, яка називає точну позицію аргументу, що вибив кандидата зі змагання.

Окремо варто впізнавати рядки про шаблони. Clang пише `candidate template ignored: substitution failure` — це шаблон, який вибув при підстановці й кандидатом так і не став; `candidate template ignored: constraints not satisfied` — шаблон, відсіяний обмеженням. Саме другий рядок з'явиться в діагностиці полагодженого `Person`: обмежений конструктор більше не змагається з копіювальним, і в цьому можна переконатися, не читаючи код.

Список буває підрізаним. Clang має прапорець `-fshow-overloads=all|best`: типове значення — `all`, а `best` навмисно тримає повний перелік лише для першого набору й скорочує подальші, тож урізаний список у великому шаблонному коді часто означає саме цю настройку. GCC від 14-ї версії має зустрічний прапорець `-fdiagnostics-all-candidates` — «note all candidates during overload resolution failure»; без нього частина кандидатів у деяких помилках лишається неназваною.

## Ціна й гачки

Уся лабораторія коштує нуль часу виконання: мітки — порожні типи, `decltype` і `static_assert` живуть до генерації коду, а функції з `return {}` зникають при першому ж інлайні. Гачків три, і всі про межі методу.

Мітка каже, **хто** переміг, і ніколи не каже, **чому**. Причину доводиться шукати звуженням: закоментувати одного кандидата й повторити — щойно відповідь змінилася, знайдено суперника, який усе вирішував.

Прилад міняє те, що вимірює. Перевантаження з багатокрапкою робить набір усеїдним: помилка «немає придатної функції» перетворюється на тихий виклик `f(...)`. У навчальному наборі це зручно, у робочому — небезпечно, тож `f(...)` лишається в лабораторії.

І останнє: перевіряти треба ту саму множину, що в бою. Кандидатів дає не лише ваш файл — їх додає ADL із просторів імен аргументів, тому набір, зібраний із самих локальних оголошень, може дати відповідь, якої в справжньому виклику не буде.
