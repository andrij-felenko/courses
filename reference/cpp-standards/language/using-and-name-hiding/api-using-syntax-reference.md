# 📋 Довідник синтаксису using та правил пошуку імен

Цей довідник містить вичерпну класифікацію граматичних форм ключового слова `using`, правила їхньої дії в різних областях видимості (простір імен, клас, функціональний блок), взаємодію зі специфікаторами доступу, алгоритми пошуку імен, роботу з модулями C++20 та перелік діагностичних повідомлень компіляторів для стандартів C++98, C++11, C++14, C++17, C++20 та C++23.

---

## 1. Using-оголошення (Using-Declarations)

Using-оголошення вводить іменовані сутності з іншого простору імен або базового класу безпосередньо в ту декларативну область (англ. *declarative region*), у якій розміщено це оголошення.

### Формальний синтаксис та граматика (ISO C++ [namespace.udecl])

```cpp
using typename(opt) nested-name-specifier unqualified-id ;
using nested-name-specifier unqualified-id , ... ; // (C++17 розширення зі списком)
```

Ключове слово `typename` є обов'язковим, якщо using-оголошення розміщене всередині шаблонного класу і звертається до залежного типу в базовому класі (`using typename Base<T>::NestedType;`).

### Правила застосування за контекстами

#### У просторах імен та глобальній області
Коли using-оголошення записане на рівні простору імен (`namespace MyLib { using std::swap; }`), воно вводить зазначений символ у простір `MyLib`. Якщо символ експортується в заголовному файлі, він стає частиною публічного інтерфейсу цього простору. Будь-який зовнішній код може викликати `MyLib::swap(...)`. Це затуляє однойменні символи з охопних (зовнішніх) просторів імен, але не конфліктує з локальними перевантаженнями, якщо їхні сигнатури відрізняються.

При цьому компілятор формує множину кандидатів, об'єднуючи всі перевантаження з однаковим ідентифікатором, які існували в цільовому просторі імен на момент оголошення. Якщо в цільовий простір пізніше додаються нові перевантаження після рядка `using`, вони також стають видимими, оскільки using-оголошення зв'язується з іменем у просторі, а не з фіксованим списком сигнатур.

#### Усередині функціональних блоків та локальних областей
Using-оголошення всередині тіла функції вводить символ локально. Локальний символ повністю затуляє будь-які однойменні функції чи змінні в охопних просторах імен і класах. Розв'язання перевантажень (Overload Resolution) розглядає лише введені символи та локальні перевантаження, ігноруючи зовнішні сутності.

Якщо всередині функції оголошено локальну змінну або функцію з тим самим ім'ям і сигнатурою, що й імпортований символ, виникає помилка повторного оголошення (redefinition error). Проте якщо імпортуються функції з іншими типами аргументів, вони утворюють локальний набір перевантажень разом із локальними функціями.

#### Усередині тіла класу (Class Scope)
Using-оголошення всередині класу дозволено використовувати **виключно** для членів прямого або непрямого базового класу (`using BaseClass::member_name;`). Спроба написати `using namespace_name::symbol;` усередині тіла класу є синтаксичною помилкою (порушення пункту [class.mem] стандарту).

Коли using-оголошення стосується методу базового класу, воно переносить усі перевантаження цього методу в похідний клас. Похідний клас може перевизначити окремі перевантаження; ті перевантаження, які не були явно перевизначені, залишаються доступними з базового класу без затуляння.

## 2. Using-директиви (Using-Directives)

Using-директива робить усі ідентифікатори зазначеного простору імен доступними для некваліфікованого пошуку імен без необхідності явного префікса.

### Формальний синтаксис (ISO C++ [namespace.udir])

```cpp
using namespace nested-name-specifier(opt) namespace-name ;
[[attribute-list]] using namespace nested-name-specifier(opt) namespace-name ;
```

### Механізм видимості в найближчому спільному предку

На відміну від using-оголошення, using-директива **не переносить** символи в поточну область видимості. Відповідно до пункту [namespace.udir] стандарту C++, імена з імпортованого простору стають видимими так, ніби вони були оголошені в **найближчому спільному просторі імен, що охоплює як поточну область, так і імпортований простір**.

Якщо у глобальній області оголошено функцію `void display(int)`, а простір `Graphics` містить функцію `void display(double)`, то написання `using namespace Graphics;` усередині локальної функції призведе до того, що обидві функції `display` вважатимуться оголошеними в глобальному просторі (найближчому спільному предку). Виклик `display(10)` спричинить помилку компіляції через неоднозначність (англ. *ambiguous call*), оскільки жодна з функцій не затуляє іншу.

Цей механізм спеціально розроблено для того, щоб підключення простору імен не могло випадково затулити локальні функції або змінні програми. Замість мовчазного перехоплення викликів компілятор генерує діагностичне повідомлення про неоднозначність, змушуючи розробника явно кваліфікувати виклик.

### Транзитивність using-директив
Using-директиви є транзитивними. Якщо простір імен `Alpha` містить рядок `using namespace Beta;`, а в коді написано `using namespace Alpha;`, то всі ідентифікатори простору `Beta` також стають видимими для пошуку імен. Це створює серйозні ризики неконтрольованого експорту сторонніх залежностей, якщо директиви розміщуються у відкритих заголовних файлах.

### Заборона в класах
Стандарт C++ суворо забороняє використання using-директив (`using namespace ...;`) всередині тіла класів та структур. Using-директиви дозволені лише в просторах імен, глобальній області та всередині тіл функцій і локальних блоків.

## 3. Псевдоніми типів та шаблонні псевдоніми (Type Aliases & Alias Templates)

Псевдоніми типів визначають нове ім'я для вже існуючого типу без створення нової сутності в системі типів.

### Граматика (ISO C++ [dcl.typedef])

```cpp
using identifier = type-id ;
template < template-parameter-list >
using identifier = type-id ;
```

### Порівняльний аналіз із typedef

1. **Порядок читання**: Синтаксис `using Name = Type;` чітко відокремлює нове ім'я (ліворуч від знака рівності) від складного типу (праворуч). У `typedef` для складних покажчиків на функції чи масивів ім'я розташовувалося всередині структури типу:
   - `typedef int (*FunctionPointerArray[10])(double);` (неінтуїтивно)
   - `using FunctionPointerArray = int (*[10])(double);` (лінійне читання)
2. **Шаблонізація**: Ключове слово `typedef` синтаксично неможливо параметризувати шаблоном. Конструкція `template<typename T> typedef ...;` є забороненою. Шаблонні псевдоніми `template<typename T> using Name = ...;` підтримують довільні параметри типів, шаблонів та нетипові параметри (non-type template parameters).
3. **Еквівалентність типів**: Псевдонім не створює нового унікального типу під час компіляції. Для компілятора та системи манглінгу імен (Name Mangling) `MyAlias` і `TargetType` є повністю тотожними сутностями. Вони мають однаковий розмір, однакове розташування в пам'яті й не можуть використовуватись для перевантаження функцій як різні типи.
4. **Шаблонні параметри шаблонів (Template Template Parameters)**: Шаблонний псевдонім може передаватися як аргумент у шаблони, що приймають інші шаблони:
   ```cpp
   template <template <typename> class Container, typename T>
   struct Wrapper { Container<T> storage; };

   template <typename T>
   using FastVector = std::vector<T, CustomFastAlloc<T>>;

   Wrapper<FastVector, int> my_wrapper; // Повністю валідно в C++11 і новіших
   ```

## 4. Успадкування конструкторів (Inheriting Constructors)

Успадкування конструкторів дозволяє похідному класу отримати всі конструктори базового класу без ручного написання проміжних функцій ініціалізації.

### Граматика (ISO C++ [class.inhctor.init])

```cpp
using BaseClass::BaseClass ;
```

### Правила та семантика від C++11 до C++17

У стандарті C++11 успадкування конструкторів розглядалося як генерація синтетичних функцій-делегатів. Це спричиняло проблеми при роботі з параметрами за замовчуванням та досконалою передачею (Perfect Forwarding).

У стандарті C++17 (пропозиція P0136R1) модель було фундаментально змінено:
- Компілятор більше не генерує реальних функцій-конструкторів у похідному класі.
- Під час розв'язання перевантажень для ініціалізації об'єкта `Derived(arg1, arg2)` компілятор розглядає конструктори `Base(arg1, arg2)` як безпосередні кандидати ініціалізації базового підкласу.
- Якщо похідний клас оголошує власний конструктор із точно такою самою сигнатурою, що й базовий клас, конструктор похідного класу має перевагу й затуляє базовий.
- Спеціальні функції-члени — конструктор за замовчуванням, конструктор копіювання та конструктор переміщення — **ніколи не успадковуються** через `using Base::Base;`. Вони завжди створюються за загальними правилами синтезу функцій-членів самого похідного класу.
- Якщо базовий клас містить конструктор із параметрами за замовчуванням (`Base(int a, double b = 0.0)`), у C++17 успадковується як версія з двома параметрами, так і версія з одним параметром.

## 5. Варіативні using-оголошення (Pack Expansion in Using-Declarations)

Починаючи зі стандарту C++17 (пропозиція P0195R2), символ трикрапки `...` дозволено використовувати безпосередньо в using-оголошеннях для розгортання пакетів параметрів шаблону.

### Граматика

```cpp
template <typename... Bases>
struct Derived : Bases... {
    using Bases::member_name... ; // розгортає using для кожного типу з Bases
};
```

### Правила об'єднання операторів
Якщо кілька базових класів містять однакові оператори або методи (наприклад, `operator()`), розгортання `using Bases::operator()...;` утворює в похідному класі єдину цілісну множину кандидатів на перевантаження. Якщо для конкретного виклику існує точний збіг сигнатури в одному з базових типів, розв'язання перевантажень проходить успішно. Якщо один і той самий метод із тотожною сигнатурою наявний у кількох базах одночасно, виклик залишається неоднозначним і вимагає кваліфікації.

Цей механізм усунув необхідність складного рекурсивного успадкування в метапрограмуванні: замість створення ланцюжків успадкування `struct Overload<Head, Tail...>` достатньо одного простого вариативного класу.

## 6. Using-оголошення для переліків (Using-Enum Declarations)

Стандарт C++20 (пропозиція P1099R5) ввів можливість прямого імпорту ідентифікаторів переліків у поточну область видимості.

### Граматика (ISO C++ [enum.udecl])

```cpp
using enum nested-name-specifier(opt) enum-name ;
using nested-name-specifier enum-name :: enumerator ;
```

### Правила застосування
- Конструкція `using enum Color;` імпортує всі елементи переліку `Color` (наприклад, `Red`, `Green`, `Blue`) у поточний простір імен, клас або функціональний блок.
- Це дозволяє звертатися до них як до некваліфікованих імен `Red` замість `Color::Red`.
- Сама строга типізація `enum class` не порушується: неявні приведення до цілих чисел (`int`) залишаються забороненими.
- Дозволено використовувати всередині класів як член класу, що експортує імена переліку для клієнтів цього класу.
- Може застосовуватися до залежних типів переліків у шаблонах: `using enum T::Status;`.

## 7. Взаємодія using зі специфікаторами доступу (Access Control)

Права доступу до членів, імпортованих через `using`, повністю визначаються тією секцією похідного класу, де записано це using-оголошення.

### Порядок перевірки прав та фаз трансляції

Дуже важливо розуміти, що контроль доступу перевіряється на двох незалежних етапах:
1. **Під час трансляції самого using-оголошення**: компілятор перевіряє, чи має похідний клас право звертатися до зазначеного члена базового класу. Якщо член оголошено як `private` в `Base`, виникає негайна помилка компіляції.
2. **Під час виклику методу через об'єкт похідного класу**: зовнішній код перевіряється на відповідність специфікатору доступу (`public`, `protected`, `private`), під яким using-оголошення розміщено в похідному класі.

### Детальна матриця прав доступу:

| Рівень члена в базовому класі | Секція `using` у похідному класі | Підсумкова доступність для зовнішніх користувачів | Підсумкова доступність для спадкоємців похідного класу | Дозволено стандартом? |
| :--- | :--- | :--- | :--- | :--- |
| `public` | `public:` | Відкрито (`public`) | Відкрито (`public`) | Так |
| `public` | `protected:` | Заборонено | Захищено (`protected`) | Так (звуження доступу) |
| `public` | `private:` | Заборонено | Заборонено (приховано) | Так (повна інкапсуляція) |
| `protected` | `public:` | Відкрито (`public`) | Відкрито (`public`) | Так (розширення доступу) |
| `protected` | `protected:` | Заборонено | Захищено (`protected`) | Так |
| `protected` | `private:` | Заборонено | Заборонено (приховано) | Так |
| `private` | Будь-яка | Недоступно | Недоступно | **Ні (помилка компіляції)** |

## 8. Алгоритми пошуку імен у C++

Стандарт C++ розрізняє кілька спеціалізованих алгоритмів пошуку імені, кожен із яких взаємодіє з using-оголошеннями за власними правилами:

### Некваліфікований пошук (Unqualified Name Lookup)
Використовується, коли ім'я записано без префіксів (`action(x)`). Пошук іде послідовно:
1. Локальний блок та вкладені блоки функції.
2. Тіло поточного класу та його базових класів (включаючи всі імена, внесені через `using Base::name;`).
3. Тіла охопних класів (для вкладених типів).
4. Простір імен, що містить поточний контекст, та всі охопні простори імен аж до глобального.
5. На кожному рівні просторів імен переглядаються також усі простори, підключені через `using namespace`.
Пошук зупиняється на найпершому рівні, де знайдено хоча б одне оголошення.

### Кваліфікований пошук (Qualified Name Lookup)
Використовується, коли ім'я містить префікс простору чи класу (`Scope::action(x)`). Пошук здійснюється виключно всередині зазначеної області `Scope`. Охопні області не переглядаються. Якщо `Scope` є класом, переглядаються всі його базові класи.

### Пошук, залежний від аргументів (Argument-Dependent Lookup / ADL)
Застосовується для некваліфікованих викликів функцій. Додатково до звичайного некваліфікованого пошуку компілятор переглядає простори імен, пов'язані з типами переданих аргументів. Using-оголошення в просторах імен типів аргументів беруть участь в ADL, розширюючи набір доступних кандидатів.

## 9. Взаємодія з модулями C++20 (C++20 Modules)

У модулях C++20 ключове слово `using` може поєднуватися зі специфікатором `export` для експорту сутностей з інтерфейсу модуля:

```cpp
export module MyMathModule;

namespace internal_detail {
    export struct Matrix { /* ... */ };
    export void fast_inverse(Matrix& m);
}

// Експортуємо конкретні сутності в інтерфейс модуля:
export using internal_detail::Matrix;
export using internal_detail::fast_inverse;

// Експорт переліку:
export enum class Status { Ok, Fail };
export using enum Status;
```

Коли клієнтський файл виконує `import MyMathModule;`, усі символи, оголошені з `export using`, стають доступними у відповідних просторах імен клієнтського коду без необхідності включати внутрішні деталі реалізації модуля.

## 10. Дружні функції (Friend Declarations) та приховані друзі

Особливе місце в пошуку імен займає патерн «прихованого друга» (англ. *Hidden Friend*):

```cpp
class Fraction {
private:
    int num_, den_;
public:
    Fraction(int n, int d) : num_(n), den_(d) {}

    // Прихований друг: оголошено й визначено всередині класу
    friend Fraction operator+(const Fraction& a, const Fraction& b) {
        return Fraction(a.num_ * b.den_ + b.num_ * a.den_, a.den_ * b.den_);
    }
};
```

Функція `operator+` не є членом класу `Fraction` і не є видимою для звичайного некваліфікованого пошуку чи using-оголошень у просторі імен. Вона стає доступною **виключно через ADL**, коли хоча б один з аргументів виклику має тип `Fraction`. Це усуває конфлікти імен і запобігає небажаним неявним перетворенням з інших типів.

Спроба імпортувати прихованого друга через `using Fraction::operator+;` призведе до помилки компіляції, оскільки `friend`-функція не є членом класу.

## 11. Типові помилки компілятора та їхня діагностика

Нижче наведено зразки типових повідомлень популярних компіляторів (GCC, Clang, MSVC), спричинених некоректним використанням using або затулянням імен:

### 1. Спроба відкрити приватний член базового класу
- **Код:** `using Base::private_data;`
- **Clang:** `error: 'private_data' is a private member of 'Base'`
- **GCC:** `error: 'int Base::private_data' is private within this context`
- **MSVC:** `error C2248: 'Base::private_data': cannot access private member declared in class 'Base'`
- **Причина:** Using-оголошення не може підвищувати рівень доступу до членів, які є закритими в самому базовому класі.

### 2. Неоднозначність через using-директиву
- **Код:** `using namespace A; using namespace B; func(10);` (де `A::func(int)` та `B::func(int)`)
- **Clang:** `error: call to 'func' is ambiguous; candidate found in namespace 'A'; candidate found in namespace 'B'`
- **GCC:** `error: call of overloaded 'func(int)' is ambiguous`
- **MSVC:** `error C2668: 'func': ambiguous call to overloaded function`
- **Причина:** Using-директива винесла символи обох просторів на рівень спільного предка, створивши нерозв'язний конфлікт перевантаження.

### 3. Пропущене typename для залежного типу
- **Код:** `using Base<T>::NestedType;` всередині `template<typename T> struct Derived : Base<T>`
- **Clang:** `error: missing 'typename' prior to dependent type name 'Base<T>::NestedType'`
- **GCC:** `error: need 'typename' before 'Base<T>::NestedType' because 'Base<T>' is a dependent scope`
- **Причина:** До інстанціювання шаблону компілятор не знає, чи є `NestedType` типом чи статичним полем. Необхідно писати `using typename Base<T>::NestedType;`.

### 4. Використання using-директиви всередині класу
- **Код:** `class MyClass { using namespace std; };`
- **Clang:** `error: expected member name or ';' after declaration specifiers`
- **GCC:** `error: using-directive cannot appear in class scope`
- **MSVC:** `error C2871: 'std': a namespace with this name does not exist / error C2059: syntax error: 'namespace'`
- **Причина:** Стандарт C++ забороняє using-директиви всередині тіла класу; дозволені лише using-оголошення окремих членів базових класів.
