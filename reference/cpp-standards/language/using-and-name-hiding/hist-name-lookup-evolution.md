# 📜 Історія затуляння імен і еволюція using у C++

Правило, за яким компілятор C++ шукає ідентифікатор спочатку виключно за назвою й негайно зупиняється на першій же знайденій області видимості, не зважаючи на типи аргументів чи повернення, було свідомим і фундаментальним архітектурним вибором, ухваленим творцями мови на зламі 1980-х і 1990-х років. Без цього суворого правила будь-яке невинне розширення інтерфейсу базового класу в глибині сторонньої бібліотеки могло б непомітно перехопити виклики в похідних класах користувачів, повністю зруйнувавши модульність і надійність програм. Ключове слово `using` пройшло шлях від засобу розв'язання конфліктів у перших просторах імен C++98 до універсального механізму маніпуляції типами, конструкторами та наборами перевантажень у C++11, C++17 і C++20.

## Від мови C до «C з класами»: виникнення ієрархій областей видимості

У класичній мові C існувала дуже проста модель іменування: глобальний простір функцій та глобальних змінних, простір тегів структур і локальні області видимості блоків функцій. Будь-яка локальна змінна всередині фігурних дужок `{ ... }` автоматично затуляла глобальну змінну з таким самим ім'ям. Це було природно й інтуїтивно: локальний контекст завжди вважався ближчим і пріоритетнішим за зовнішній.

Коли Б'ярн Страуструп (англ. *Bjarne Stroustrup*) у 1979 році в лабораторіях Bell Labs розпочав розробку мови «C з класами» (англ. *C with Classes*), натхненної мовою Simula 67, він увів концепцію класів як окремих областей видимості. Члени класу належали власному простору імен цього типу. З появою одиничного успадкування виникла природна ієрархія: область видимості похідного класу вважалася вкладеною в область видимості базового класу, подібно до того, як внутрішній блок коду вкладений у зовнішній.

У середині 1980-х років у C++ 1.0 та C++ 2.0 (1989) з'явилося множинне успадкування та повноцінне перевантаження функцій (англ. *function overloading*). Саме тоді виникло принципове архітектурне питання: як має працювати перевантаження, коли однойменні функції оголошені на різних поверхах ієрархії класів або в різних областях видимості?

## Спокуса об'єднання областей та проблема «викрадення викликів»

На етапі проєктування транслятора `cfront` 2.0 розглядалася спокуслива альтернатива: дозволити компілятору одночасно переглядати всі доступні області видимості — локальний блок, поточний похідний клас, усі його базові класи та глобальний контекст — і збирати всі однойменні функції в єдину спільну множину кандидатів для перевантаження.

Здавалося, що це дасть максимальну зручність: якщо базовий клас має метод `void log(int)`, а похідний клас додає `void log(std::string_view)`, то об'єкт похідного класу міг би приймати як цілі числа, так і рядки без жодного додаткового коду.

Проте практичні експерименти швидко виявили катастрофічну вразливість такого підходу, яка в теорії мов програмування отримала назву проблеми «викрадення функцій» (англ. *function hijacking*) та стала частиною ширшої проблеми «крихкого базового класу» (англ. *fragile base class problem*).

Уявімо реальну ситуацію в комерційній розробці. Бібліотека графічного інтерфейсу надає базовий клас `Widget`, у якому є метод малювання: `void draw(int flags)`. Розробник програми створює похідний клас `CustomButton` і реалізує в ньому власну допоміжну функцію для рендерингу з масштабуванням: `void draw(double scale)`. Усередині коду кнопки викликається `draw(1.0)`.

Якщо компілятор об'єднує всі області видимості разом, то при виклику `draw(1.0)` обирається метод кнопки `CustomButton::draw(double)`. Але через рік автор базової бібліотеки `Widget` випускає оновлення, де додає новий метод для підтримки високої точності: `void draw(double zoom, bool high_dpi = false)`.

У момент перекомпіляції програми з новим заголовком бібліотеки виклик `draw(1.0)` у класі `CustomButton` раптом неявно й мовчки зв'язується з новим методом базового класу `Widget::draw(double, bool)`, тому що він має відповідний тип аргументу за замовчуванням! Програма змінила свою логіку виконання без жодного попередження компілятора. Що глибшою була ієрархія класів, то непередбачуванішим ставало додавання будь-якого нового методу в базовий клас: воно могло зламати або непомітно перехопити виклики в сотнях похідних класів по всьому світу.

## Рішення в ARM (1990): Розділення пошуку та перевантаження

У фундаментальній книзі *«The Annotated C++ Reference Manual»* (ARM, 1990) Б'ярн Страуструп та Маргарет Елліс (англ. *Margaret A. Ellis*) остаточно зафіксували канонічне правило, яке діє в стандарті C++ донині:

> **Пошук імені (Name Lookup) завжди виконується повністю до початку перевірки типів і розв'язання перевантажень (Overload Resolution).**

Компілятор шукає лише назву ідентифікатора. Знайшовши ім'я в найближчому похідному класі, він негайно зупиняє пошук. Усі перевантаження з базових класів стають невидимими (затуленими).

Страуструп пояснював це рішення так: локальний захист коду від непередбачуваних змін у далеких предках є значно важливішим, ніж автоматичне злиття перевантажень. Якщо розробник похідного класу справді хоче використовувати методи базового класу разом зі своїми новими методами, він повинен заявити про цей намір **явно**.

У період розробки ARM для явного відкриття затуленого імені використовувалися так звані «оголошення доступу» (англ. *access declarations*):

```cpp
// Застарілий синтаксис кінця 1980-х (ARM 10.1.1):
class Derived : public Base {
public:
    Base::display; // оголошення доступу без ключового слова using
    void display(double);
};
```

Цей механізм був обмеженим: він дозволяв лише повертати оригінальні права доступу до членів базового класу, не працював із конструкторами та не міг масштабуватися на нові концепції мови.

## Стандарт C++98: Простори імен і народження ключового слова using

На початку 1990-х років C++ зіткнувся з новою кризою: стрімким розростанням глобального простору імен через об'єднання багатьох сторонніх бібліотек в одному проєкті. Щоб вирішити цю проблему, робоча група ANSI/ISO WG21 схвалила пропозицію просторів імен (англ. *namespaces*).

Щоб дати розробникам інструмент гнучкого імпорту імен, було введено ключове слово `using` у двох взаємодоповнювальних формах:
1. **`using`-оголошення (Using-declaration):** `using std::vector;` — явно вносить зазначений символ у поточну область видимості так, ніби він оголошений локально.
2. **`using`-директива (Using-directive):** `using namespace std;` — робить усі імена простору доступними на рівні найближчого спільного простору-предка.

Комітет стандартизації одночасно уніфікував роботу з класами: старий синтаксис `Base::member;` було оголошено застарілим, а на його місце прийшов уніфікований запис `using Base::member;`. Відтепер одне ключове слово `using` відповідало за явне керування видимістю як у просторах імен, так і в ієрархіях успадкування.

## C++11: Псевдоніми типів, шаблони та конструктори

Наступний великий еволюційний стрибок ключового слова `using` відбувся під час розробки стандарту C++11 (відомого на етапі підготовки як C++0x).

### Відмова від обмежень typedef на користь Alias Templates

Успадковане від мови C ключове слово `typedef` десятиліттями викликало нарікання через незручний синтаксис оголошення покажчиків на функції та масивів (`typedef void (*Callback)(int);`), де нове ім'я губилося всередині складного оголошення.

Але критичним недоліком `typedef` була принципова неможливість його параметризації шаблонами. Програмісти не могли оголосити шаблонний синонім типу. Доводилося використовувати громіздкі обхідні шляхи зі структурами-обгортками:

```cpp
// Обхідний шлях у C++98:
template <typename T>
struct VectorWrapper {
    typedef std::vector<T, CustomAllocator<T>> type;
};

// Використання вимагало 'typename' і '::type':
typename VectorWrapper<int>::type my_vec;
```

У 2003–2007 роках Б'ярн Страуструп та Габріель Дос Рейс (англ. *Gabriel Dos Reis*) підготували низку пропозицій для комітету WG21 (документи N1489 та N2258). Спочатку обговорювався синтаксис `template<typename T> typedef ...`, але він виявився граматично неоднозначним для синтаксичних аналізаторів через традиційний зворотний порядок запису `typedef`.

Було ухвалено нове елегантне формулювання на основі `using`:

```cpp
template <typename T>
using Vector = std::vector<T, CustomAllocator<T>>;

Vector<int> my_vec; // чистий і прямий синтаксис
```

Синтаксис `using Name = Type;` не лише розв'язав проблему шаблонів, а й зробив звичайні псевдоніми типів лінійними та зрозумілими, наслідуючи синтаксис оператора присвоєння.

### Успадкування конструкторів (Inheriting Constructors)

У C++11 комітет також вирішив проблему монотонного коду під час створення класів-обгорток. До C++11, якщо базовий клас мав десяток перевантажених конструкторів, похідний клас мусив вручну продублювати кожен із них, передаючи аргументи вгору.

Пропозиція N2540 ввела конструкцію `using Base::Base;`. Вона наказала компілятору неявно згенерувати для похідного класу всі конструктори предка.

## C++17: Переосмислення конструкторів та пакетні using-оголошення

Стандарт C++17 приніс два важливі вдосконалення механізмів `using`:

1. **Реформа успадкування конструкторів (P0136R1)**. До C++17 успадкування конструкторів працювало шляхом генерації синтетичних функцій-делегатів. Це спричиняло проблеми з перевантаженнями, аргументами за замовчуванням, `constexpr` та категоріями значень аргументів. Річард Сміт (англ. *Richard Smith*, провідний розробник Clang) запропонував змінити модель: замість генерації функцій компілятор тепер розглядає успадкований конструктор як пряму ініціалізацію підкласу базового об'єкта під час розв'язання перевантажень. Це усунуло всі вади старої моделі та зробило успадкування конструкторів абсолютно безкоштовним і точним.
2. **Варіативні using-оголошення (P0195R2)**. Роланд Бок (англ. *Roland Bock*) запропонував дозволити розгортання пакетів параметрів усередині `using`: `using Ts::operator()...;`. Це стало ключем до створення компактного патерну `Overload` для обробки `std::variant` через `std::visit`, замінивши складні метапрограмні рекурсивні структури попередніх стандартів одним рядком коду.

## C++20: Останній штрих — using enum

З моменту появи строго типізованих переліків `enum class` у C++11 розробники цінували їх за безпеку та захист від колізій імен, але часто скаржилися на надмірну багатослівність у конструкціях `switch` та оголошеннях станів.

У C++20 пропозиція P1099R5 (автори Gašper Ažman та John Spicer) ввела конструкцію `using enum`:

```cpp
switch (status) {
    using enum ConnectionStatus;
    case Connecting:   break;
    case Connected:    break;
    case Disconnected: break;
}
```

Це нововведення гармонійно завершило еволюцію `using`, надавши інструмент локального імпорту для всіх іменованих сутностей мови — просторів імен, класів, шаблонів, типів, конструкторів та переліків.

| Період | Стандарт | Архітектурне нововведення | Ключова мотивація |
| :--- | :--- | :--- | :--- |
| **1990** | ARM | Правило «Lookup before Overload» | Захист від викрадення викликів при еволюції базових класів |
| **1998** | C++98 | `using`-оголошення та директиви | Керування просторами імен та заміна застарілого синтаксису ARM |

Історія розвитку механізмів пошуку імен та ключового слова `using` свідчить про послідовний рух мови C++ до максимального контролю, строгої типізації та виразності без втрати принципу нульових накладних витрат під час виконання.
