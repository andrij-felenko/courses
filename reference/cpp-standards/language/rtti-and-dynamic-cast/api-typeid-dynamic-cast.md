# 📋 Довідка: `typeid`, `dynamic_cast`, `<typeinfo>` і прапорці збірки

Це точний контракт обох операторів: коли операнд обчислюється, а коли ні; що саме є помилкою компіляції, а що — нулем чи винятком у час виконання; повний склад `std::type_info` і `std::type_index` із версіями стандарту; імена, які видно в дизасемблері й лінкувальнику; прапорці, якими механізм вмикають і вимикають. Заглядають сюди, коли треба говорити не поняттями, а сигнатурами: `dynamic_cast` мовчки віддав нуль, `typeid` порівняв не те, збірка з `-fno-rtti` не злінкувалася.

<preknowlist>
- [Оператори приведення](book:cpp-standards/cast-operators) — `static_cast`, `reinterpret_cast`, `const_cast` і те, що жоден із них не звіряється з дійсністю в час виконання.
- [Множинне й віртуальне спадкування](book:cpp-standards/multiple-and-virtual-inheritance) — підоб'єкти баз лежать за різними зсувами, і зсув віртуальної бази не є сталою типу.
- [Динамічне лінкування](book:programming/dynamic-linking) — символ може прийти з бібліотеки, приєднаної під час роботи програми, і тоді його видимість вирішує все.
</preknowlist>

## Заголовки

| заголовок | що дає | доступність |
|---|---|---|
| `<typeinfo>` | `std::type_info`, `std::bad_cast`, `std::bad_typeid` | стандарт, C++98 |
| `<typeindex>` | `std::type_index`, спеціалізація `std::hash<std::type_index>` | стандарт, C++11 |
| `<cxxabi.h>` | `abi::__cxa_demangle`, класи `abi::__*_type_info` | GCC, Clang, будь-яка реалізація Itanium ABI |

Без оголошення `std::type_info` перед `typeid` програма некоректна: `<typeinfo>` треба включити явно, навіть якщо вона «і так підтягується» через інший заголовок.

## `typeid`: дві форми й правило обчислення

```cpp
typeid ( type-id )     // питаємо про тип
typeid ( expression )  // питаємо про вираз
```

Результат — lvalue статичного типу `const std::type_info`; його динамічний тип реалізація має право зробити похіднішим. Об'єкт живе до кінця програми, тож посилання на нього можна зберігати.

Вирішує все те, чи операнд **обчислюється**:

| операнд | обчислюється | результат описує |
|---|---|---|
| `typeid(T)`, `typeid(T&)`, `typeid(const T)` | — | `T` без верхніх `const`/`volatile` і без посилання |
| glvalue поліморфного класу: `*p`, `ref`, `arr[i]` | **так** | динамічний тип найпохіднішого об'єкта |
| prvalue поліморфного класу: `f()`, `Shape{}` | ні | статичний тип виразу |
| будь-що інше: `p`, `i++`, `Point{}` | ні | статичний тип виразу |

Перетворення lvalue→rvalue, масив→вказівник і функція→вказівник до необчислюваного операнда не застосовуються, тож `typeid(arr)` для `int arr[10]` дає `int[10]`, а не `int*`.

**Помилки й винятки:**

| ситуація | що буде |
|---|---|
| `<typeinfo>` не включено | помилка компіляції |
| клас операнда оголошено, але не визначено | помилка компіляції |
| `typeid(*p)` при `p == nullptr`, тип поліморфний | `std::bad_typeid` у час виконання |
| `typeid(*p)` при `p == nullptr`, тип неполіморфний | нічого: операнд не обчислюється |
| `typeid` у конструкторі чи деструкторі | тип **цього** конструктора/деструктора; якщо статичний тип операнда не цей клас і не його база — невизначена поведінка |
| збірка з `-fno-rtti` і поліморфний glvalue | помилка компіляції |

**Сталі вирази.** З C++20 `dynamic_cast` і `typeid` над поліморфним glvalue дозволені в сталих виразах — папір P1327R1 (Пітер Дімов, Васіл Васілєв, Річард Сміт): обмеження зняли, бо компілятор і так зобов'язаний стежити за динамічним типом під час сталого обчислення. З C++23 `operator==` став `constexpr` (P1328R1), і лише відтоді результат придатний до вжитку; ознака — `__cpp_lib_constexpr_typeinfo == 202106L`, реалізовано в GCC 12, Clang 17, MSVC 19.33.

```cpp
static_assert(typeid(int) == typeid(const int));      // C++23: cv відкидається

struct B { virtual ~B() = default; };
struct D : B { int v = 7; };
constexpr int probe() { D d; B& b = d; return dynamic_cast<D&>(b).v; }
static_assert(probe() == 7);                          // C++20
```

Обидві операції лишаються забороненими в сталому виразі, коли динамічний тип об'єкта компіляторові невідомий або коли операція мала б кинути виняток.

## `std::type_info`

```cpp
namespace std {
  class type_info {
  public:
    virtual ~type_info();
    constexpr bool operator==(const type_info& rhs) const noexcept;  // constexpr з C++23
    bool           before(const type_info& rhs) const noexcept;
    size_t         hash_code() const noexcept;                       // C++11
    const char*    name() const noexcept;
    type_info(const type_info&)            = delete;
    type_info& operator=(const type_info&) = delete;
  };
}
```

| член | контракт |
|---|---|
| `operator==` | тотожність **типів**, а не адрес об'єктів опису |
| `operator!=` | прибрано в C++20: компілятор переписує його через `operator==` |
| `before` | довільний, але сталий у межах одного запуску порядок; між запусками не гарантований — тому не ключ для файлу чи мережі |
| `hash_code` | рівні типи дають рівне значення; різні типи **можуть** збігтися, реалізація лише «має намагатися» цього уникати |
| `name` | рядок, що завершується нулем; вміст визначає реалізація |

Копіювання заборонено, деструктор віртуальний — `type_info` сам поліморфний, і саме тому реалізація вільна класти під нього похідні класи.

**Що повертає `name()`:**

| компілятор | `typeid(Polygon).name()` | як прочитати людською |
|---|---|---|
| GCC, Clang (Itanium ABI) | `7Polygon` | `abi::__cxa_demangle`, `c++filt -t` |
| MSVC | `class Polygon` | вже читне; `raw_name()` (розширення MSVC) дає внутрішнє `.?AVPolygon@@` |

```c
char* abi::__cxa_demangle(const char* mangled_name, char* output_buffer,
                          size_t* length, int* status);
```

Повертає буфер, виділений `malloc`; звільняти зобов'язаний той, хто кликав. Передавши `output_buffer == nullptr`, буфер віддають функції на відкуп. Коди в `*status`: `0` — успіх, `-1` — не вистачило пам'яті, `-2` — рядок не є коректним спотвореним іменем, `-3` — хибні аргументи. Правила самого спотворення — у темі про [спотворення імен](book:cpp-standards/name-mangling).

## `std::type_index`

Обгортка навколо посилання на `type_info`, яка додає копіювання й порядок — рівно те, чого бракує для ролі ключа контейнера.

```cpp
namespace std {
  class type_index {
  public:
    type_index(const type_info& rhs) noexcept;          // неявний, навмисно
    bool             operator==(const type_index&) const noexcept;
    strong_ordering  operator<=>(const type_index&) const noexcept;  // C++20
    bool             operator<(const type_index&) const noexcept;    // і >, <=, >=
    size_t           hash_code() const noexcept;
    const char*      name() const noexcept;
  };
  template<> struct hash<type_index>;   // повертає rhs.hash_code()
}
```

Порядок `operator<` збудовано на `type_info::before`, тож `std::map<std::type_index, …>` працює, але порядок обходу між запусками може відрізнятися.

## `dynamic_cast`: що перевіряється, а що ні

```cpp
dynamic_cast < T > ( v )
```

| `T` | яким має бути `v` |
|---|---|
| `X*` (повний тип класу) | prvalue типу «вказівник на повний тип класу» |
| `X&` | lvalue повного типу класу |
| `X&&` | glvalue повного типу класу |
| `cv void*` | вказівник на **поліморфний** тип |

Далі — перебір випадків у порядку, у якому їх розглядає мова:

| випадок | перевірка в час виконання | результат |
|---|---|---|
| тип `v` збігається з `T` (з точністю до cv) | ні | `v` |
| `T` — доступна й однозначна база типу `v` (приведення вгору) | **ні** | адреса підоб'єкта бази; зсув компілятор додає сам |
| `v` — нульовий вказівник | ні | нульовий вказівник типу `T` |
| `T` — `cv void*` | так | адреса найпохіднішого об'єкта |
| вниз до похідного або навскіс між базами | так | адреса підоб'єкта `T` або невдача |

Перевірка вдається лише тоді, коли підоб'єкт, на який дивиться `v`, є **публічною** базою єдиного об'єкта типу `T`, або коли найпохідніший об'єкт має однозначну публічну базу `T`. Слово «публічна» тут не формальність: непублічна база `dynamic_cast`ові не видна, і приведення чесно провалюється, хоча спорідненість типів існує.

**Куди дівається невдача:**

| форма | невдача |
|---|---|
| вказівник | `nullptr` — передбачена нормальна відповідь |
| посилання (`X&` або `X&&`) | виняток типу, який ловить `catch (const std::bad_cast&)` |

**Що ловиться ще під час компіляції:**

| ситуація | коли виявиться |
|---|---|
| потрібна перевірка, а статичний тип операнда неполіморфний | помилка компіляції |
| `T` — неповний тип класу | помилка компіляції |
| база при приведенні вгору недоступна або неоднозначна | помилка компіляції |
| база непублічна, а приведення — вниз чи навскіс | **нуль у час виконання** |
| базу успадковано двічі не віртуально | **нуль у час виконання** |

Окремо — конструктори й деструктори. Поки працює конструктор класу `C`, об'єкт вважається найпохіднішим об'єктом типу `C`. Але якщо статичний тип операнда не `C` і не його база, це вже не «інша відповідь», а невизначена поведінка — те саме правило, що й для `typeid`.

## Рівень ABI: імена, які видно назовні

Ці символи не пишуть руками, але за ними впізнають, що саме поклав компілятор і чого не вистачило лінкувальникові.

| символ для класу `Shape` | що це |
|---|---|
| `_ZTV5Shape` | таблиця віртуальних функцій |
| `_ZTI5Shape` | сам об'єкт `type_info` |
| `_ZTS5Shape` | рядок імені, на який указує `name()` |

Реалізація кладе під `std::type_info` похідні класи — по одному на різновид типу, і саме від цього залежить, чи буде перевірка швидкою:

| ABI-клас | для чого | додаткові поля |
|---|---|---|
| `__fundamental_type_info` | `int`, `void`, `std::nullptr_t`… | — |
| `__array_type_info`, `__function_type_info`, `__enum_type_info` | масиви, функції, перелічення | — |
| `__class_type_info` | клас без баз | — |
| `__si_class_type_info` | одна публічна невіртуальна база | `__base_type` — швидкий шлях |
| `__vmi_class_type_info` | усе решта: кілька баз, віртуальні, непублічні | `__flags`, `__base_count`, масив `__base_info[]` |
| `__pointer_type_info`, `__pointer_to_member_type_info` | вказівники (спільна база `__pbase_type_info`) | `__flags` із cv-бітами, `__pointee` |

```cpp
struct __base_class_type_info {
    const __class_type_info *__base_type;
    long                     __offset_flags;   // (зсув << 8) | прапорці
    enum __offset_flags_masks {
        __virtual_mask = 0x1,   // база віртуальна: у полі не зсув, а індекс у таблиці
        __public_mask  = 0x2,   // база публічна
        __offset_shift = 8
    };
};
```

Біт `__public_mask` — це і є та сама «публічність» із правил мови, записана одним бітом: обхід графа просто не спускається в базу без нього.

Сама перевірка — виклик функції рантайму:

```cpp
extern "C" void* __dynamic_cast(const void *sub,
                                const abi::__class_type_info *src,
                                const abi::__class_type_info *dst,
                                std::ptrdiff_t src2dst_offset);
```

Останній аргумент — підказка, яку компілятор обчислює статично, щоб зрізати обхід:

| значення | сенс |
|---|---|
| `≥ 0` | `src` — єдина публічна невіртуальна база `dst` за цим зсувом |
| `-1` | підказки немає |
| `-2` | `src` не є публічною базою `dst` |
| `-3` | `src` — публічна база `dst`, але не єдина; віртуальною не буває |

Невдалі приведення й `typeid` кличуть `__cxa_bad_cast()` і `__cxa_bad_typeid()`, які й кидають відповідні винятки. У Clang є ще й окремий шлях (зміна D154658, липень 2023): приведення до класу, поміченого `final`, він розгортає у пряме порівняння вказівника на таблицю замість виклику `__dynamic_cast`; GCC і MSVC цього не роблять.

## Прапорці й макроси

| компілятор | увімкнено | вимкнено | ознака в препроцесорі |
|---|---|---|---|
| GCC | `-frtti` (типово) | `-fno-rtti` | `__cpp_rtti == 199711`, `__GXX_RTTI` |
| Clang | `-frtti` (типово) | `-fno-rtti` | `__cpp_rtti`, `__has_feature(cxx_rtti)` |
| MSVC | `/GR` (типово) | `/GR-` | `_CPPRTTI` |

Що саме прибирає вимкнення, документація GCC формулює точно: зникає «генерація відомостей про кожен клас із віртуальними функціями», а `dynamic_cast` лишається придатним для приведень, яким ці відомості не потрібні, — до `void*` і до однозначних баз. Винятки при цьому працюють: описи типів для них компілятор випускає окремо, за потребою. MSVC поводиться інакше й м'якше: `/GR-` не забороняє операторів, а видає попередження рівня 1 **C4541** «used on polymorphic type … with /GR-; unpredictable behavior may result» — тобто зламається воно вже в час виконання.

Змішувати одиниці трансляції, зібрані з увімкненим і вимкненим механізмом, не можна: клас, скомпільований двічі по-різному, дає різні таблиці, і лінкувальник мовчки лишить одну.

**Коли опис типу подвоївся** (`dynamic_cast` віддає нуль через межу модуля, `catch` не ловить):

| засіб | де застосувати |
|---|---|
| ключова функція — невбудований нечистий віртуальний метод, визначений в **одній** одиниці трансляції | у коді класу |
| `__attribute__((visibility("default")))` на класі | у коді класу |
| `-fvisibility=default` замість `hidden` | збірка одиниці |
| `dlopen(…, RTLD_NOW \| RTLD_GLOBAL)` | завантаження модуля |
| `-Wl,--export-dynamic` | лінкування головного файлу |

## Мінімальний робочий приклад

Обидва оператори поруч — і видно, чим саме вони відрізняються: реєстр знаходить **точний** тип, приведення питає про **спорідненість**.

```cpp
#include <typeinfo>
#include <typeindex>
#include <unordered_map>
#include <functional>
#include <memory>
#include <string>
#include <cstdio>
#include <cstdlib>
#include <cxxabi.h>

struct Shape   { virtual ~Shape() = default; };
struct Circle  : Shape { double r = 2.5; };
struct Polygon : Shape { int n = 5; };
struct Regular : Polygon {};

std::string human(const std::type_info& t) {
    int status = 0;
    char* raw = abi::__cxa_demangle(t.name(), nullptr, nullptr, &status);
    std::string out = (status == 0 && raw) ? raw : t.name();
    std::free(raw);
    return out;
}

int main() {
    using Dump = std::function<void(const Shape&)>;
    std::unordered_map<std::type_index, Dump> registry;

    // ключ — точний тип, тому в обробнику static_cast уже безпечний
    registry[typeid(Circle)]  = [](const Shape& s) {
        std::printf("коло r=%g\n", static_cast<const Circle&>(s).r); };
    registry[typeid(Polygon)] = [](const Shape& s) {
        std::printf("многокутник n=%d\n", static_cast<const Polygon&>(s).n); };

    std::unique_ptr<Shape> s = std::make_unique<Regular>();

    std::printf("динамічний тип:  %s\n", human(typeid(*s)).c_str());   // Regular
    std::printf("тип виразу `s`:  %s\n", human(typeid(s)).c_str());    // unique_ptr<Shape,…>

    auto it = registry.find(typeid(*s));
    std::printf("у реєстрі: %s\n", it == registry.end() ? "не знайдено" : "знайдено");

    if (auto* p = dynamic_cast<Polygon*>(s.get()))   // спрацює: Regular — різновид Polygon
        std::printf("сторін: %d\n", p->n);

    try { (void)dynamic_cast<Circle&>(*s); }
    catch (const std::bad_cast& e) { std::printf("bad_cast: %s\n", e.what()); }
}
```

Збирається як `g++ -std=c++17 -Wall demo.cpp`. `std::type_index` тут будується неявно з `typeid(...)`, тож писати його ім'я не доводиться.

## Як подивитися це в бінарнику

| завдання | команда |
|---|---|
| які типи взагалі описано у файлі | `nm -C a.out \| grep "typeinfo for"` |
| чи експортує бібліотека опис типу назовні | `nm -D --defined-only lib.so \| grep _ZTI` |
| розшифрувати рядок із `name()` вручну | `c++filt -t 7Polygon` |
| скільки місця з'їли описи й таблиці | `size -A a.out` — розділи `.rodata` і `.data.rel.ro` |
| зловити приведення `static_cast` до неправильного типу | зібрати з `-fsanitize=vptr` (входить у `-fsanitize=undefined`); потрібне ввімкнене RTTI — див. [санітайзери](book:programming/static-analysis/proj-sanitizers.md) |
| перевірити, чи вимкнено механізм у цій одиниці | `g++ -dM -E -x c++ /dev/null \| grep -i rtti` з тими самими прапорцями |
