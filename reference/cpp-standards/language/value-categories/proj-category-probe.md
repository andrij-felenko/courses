# ⚙️ Вимірювач категорій: як спитати компілятор, чим є ваш вираз

Категорію виразу можна не вгадувати, а **виміряти** — зібрати маленький інструмент, який просто на етапі компіляції каже, чим є `obj.field[i]`, `std::move(cfg)` чи `cond ? x : y`. Будувати його варто власноруч, бо кожна проміжна версія бреше в новому місці, і саме ці брехні пояснюють правила мови краще за будь-яку таблицю: готовий інструмент займає пів сторінки, а дорога до нього проходить рівно через ті місця, де в живому коді тихо зникає переміщення.

## Що ми хочемо від приладу

Вимог рівно чотири, і кожна далі щось у конструкції визначить.

**Приймає будь-який вираз, а не значення.** Не «змінну типу `X`», а буквально текст виразу: `v.at(3)`, `f().name`, `arr[i + 1]`. Прилад для вимірювання категорій, який не бере половини виразів, ні на що не годиться.

**Нічого не виконує.** Вимірювання не має права кинути виняток, змінити лічильник чи виділити пам'ять. Інакше ним не можна користуватися там, де найцікавіше, — у гарячому коді й у виразах, що падають.

**Відповідає на етапі компіляції.** Категорія — властивість тексту програми, її знає компілятор і не знає процесор. Питати про неї в рантаймі — те саме, що вимірювати рулеткою креслення замість деталі.

**Відповідь придатна не лише для друку.** Надрукувати «xvalue» — добре для налагодження; закріпити «тут мусить бути xvalue» у тесті, який ламає збірку при регресії, — набагато краще.

## Наївна спроба, яка бреше двічі

Перше, що спадає на думку: категорія якось пов'язана з посиланнями, а про посилання є готова риса типу. Риси типів (type traits) — це шаблони-запитання про тип, які компілятор обчислює під час компіляції й віддає `true`/`false` або інший тип; ціла їхня родина лежить у заголовку `<type_traits>`, і `std::is_reference_v<T>` серед них найпростіша ([риси типів](book:cpp-standards/type-traits)). Спробуймо:

```cpp
#include <cstdio>
#include <string>
#include <type_traits>
#include <utility>

std::string make();

#define NAIVE(expr) (std::is_reference_v<decltype(expr)> ? "rvalue" : "prvalue")

int main() {
    std::string s = "text";
    std::string&& r = make();

    std::puts(NAIVE(s));             // "prvalue" — а насправді lvalue
    std::puts(NAIVE(r));             // "rvalue"  — а насправді теж lvalue
    std::puts(NAIVE(std::move(s)));  // "rvalue"  — правда, але випадкова
}
```

Три рядки — і два з них хибні. Помилок теж дві, і вони незалежні.

Перша: `decltype(s)` без зайвих дужок віддає **оголошений тип сутності** — той, який стоїть у визначенні змінної, — а не тип виразу з його категорією. Для `s` це `std::string`, посилання там немає, і прилад упевнено каже «prvalue» про звичайнісіньку змінну. Для `r` оголошений тип якраз `std::string&&`, тож відповідь виходить «rvalue» — і це найдорожча брехня з усіх, бо вираз `r` є lvalue: у нього є ім'я.

Друга: навіть коли тип таки виявиться посиланням, `is_reference` не розрізняє, яке саме. Посилання на lvalue й посилання на rvalue для неї однакові, а це рівно та відмінність, заради якої ми все й затіяли.

## Перша поправка: дужки, які вмикають потрібний режим

`decltype` навмисне має дві поведінки, і перемикають їх дужки:

- `decltype(вираз)`, де вираз — **просте ім'я або звертання до члена без дужок**: віддає оголошений тип названої сутності, категорію ігнорує повністю;
- `decltype((вираз))` — тобто будь-що інше, зокрема те саме ім'я, взяте в зайві дужки: віддає тип, **у формі якого закодовано категорію**: `T&` для lvalue, `T&&` для xvalue, просто `T` для prvalue.

Друга поведінка — не курйоз, а основне правило; перша — спеціальний виняток, доданий, щоб можна було спитати «якого типу оголошено оцю сутність» для оголошень і повернень. Зайві дужки вимикають виняток, бо `(s)` — це вже не «просте ім'я», а звичайний вираз, і в дію вступає загальне правило. Тонкощі самого `decltype` — окрема тема ([decltype](book:cpp-standards/decltype)); нам вистачить того, що друга форма перекладає категорію в **тип**, а з типами вже вміють працювати шаблони.

## Друга поправка: посилання бувають двох сортів

Замінімо одну грубу рису на дві точні. Гілки, які не мають виконуватися, приберімо з коду ще на етапі компіляції — це вміє `if constexpr`: компілятор обчислює умову й **викидає** невибрану гілку разом із її помилками, замість генерувати обидві ([if constexpr](book:cpp-standards/constexpr-if)).

```cpp
template <typename T>
constexpr const char* name_of() {
    if constexpr (std::is_lvalue_reference_v<T>)      return "lvalue";
    else if constexpr (std::is_rvalue_reference_v<T>) return "xvalue";
    else                                              return "prvalue";
}

#define VALUE_CATEGORY(expr) (name_of<decltype((expr))>())
```

Це вже працює: `VALUE_CATEGORY(s)` каже «lvalue», `VALUE_CATEGORY(r)` — теж «lvalue», `VALUE_CATEGORY(make())` — «prvalue». Здавалося б, кінець.

Кінця немає, бо відповідь — рядок. Рядок можна надрукувати, і на цьому все: за ним не вибрати перевантаження, ним не параметризувати шаблон, його незручно порівнювати там, де працює компілятор. Ми відповіли людині й нічого не сказали компіляторові. А четверта вимога з нашого списку — саме про це.

## Категорія як тип, а не як рядок

Зробімо категорію повноцінним типом. Три порожні структури-мітки й три часткові спеціалізації:

```cpp
struct lvalue_t  {};
struct xvalue_t  {};
struct prvalue_t {};

template <typename T> struct category      { using tag = prvalue_t; };
template <typename T> struct category<T&>  { using tag = lvalue_t;  };
template <typename T> struct category<T&&> { using tag = xvalue_t;  };

template <typename T> using category_t = typename category<T>::tag;
```

Працює це так: компілятор дивиться на тип, який йому дав `decltype((expr))`, і шукає найточніший зразок. `std::string&` збігається зі зразком `T&` (при `T = std::string`), `std::string&&` — зі зразком `T&&`, а `std::string` не збігається з жодним частковим і потрапляє в загальний шаблон. Часткова спеціалізація тут не прикраса, а точний інструмент: її вибір відбувається за формою типу й цілком на етапі компіляції, без жодної гілки в машинному коді ([спеціалізація шаблонів](book:cpp-standards/specialization-overload)).

Виграш у тому, що `category_t<decltype((expr))>` — **тип**. Типи можна порівнювати (`std::is_same_v`), передавати в шаблони й ставити в перевантаження. Категорія перестала бути повідомленням для людини й стала фактом, з яким може працювати програма.

## Чому це неминуче макрос

Макросів у C++ уникають, і небезпідставно: препроцесор працює до компілятора, простою заміною тексту, тож макрос не бачить просторів імен, не поважає областей видимості й псує повідомлення про помилки ([препроцесор і заголовки](root:embedded/c-preprocessor-headers)). Тому спокуса написати замість нього чесну функцію нормальна. Але тут функція не просто незручна — вона **фізично не може** виконати роботу, і причин дві.

Перша: функція обчислює аргумент. `probe(v.at(9))` кине виняток раніше, ніж щось виміряється; `probe(make())` справді збудує рядок; `probe(i++)` змінить `i`. Операнд `decltype` натомість не обчислюється взагалі — це невиконуваний операнд, від нього потрібен лише тип. Наскільки це буквально, видно з приємного наслідку: демонстраційна програма нижче лінкується, хоча жодну з оголошених у ній функцій ніде не визначено. Їх ніхто не викликає.

Друга причина остаточна: **категорія не переживає передавання аргументу**. Спробуймо найгнучкіший вид параметра — універсальне посилання `T&&` у шаблоні, куди прив'язується будь-що:

```cpp
template <typename T>
const char* probe(T&& p) {
    // p — ім'я параметра, отже завжди lvalue, хай яким був аргумент.
    // Лишається дивитися на виведений T:
    if constexpr (std::is_lvalue_reference_v<T>) return "lvalue";
    else                                         return "xvalue або prvalue — не знаю";
}
```

Виведення типу для такого параметра має рівно два можливі результати: якщо аргумент був lvalue, виводиться `T = X&`; якщо аргумент був будь-яким rvalue — виводиться `T = X`. Прив'язування зберігає лише те, що потрібне механізмові: чи вільно грабувати. Тонша різниця «уже існує об'єкт» проти «об'єкта ще немає» на цьому кроці зникає, бо жодному правилу зв'язування вона не потрібна ([виведення аргументів шаблону](book:cpp-standards/template-argument-deduction)). Саме на цій половинчастій пам'яті й стоїть ідеальне передавання: `std::forward<T>` уміє відтворити «lvalue чи rvalue» і принципово не вміє відтворити «xvalue чи prvalue» ([ідеальне передавання](book:cpp-standards/perfect-forwarding)).

![Три виклики з аргументами різних категорій ліворуч, шаблон із параметром T&& у центрі, праворуч два результати виведення: T = std::string& для lvalue і T = std::string, куди злилися xvalue і prvalue](/reference/cpp-standards/language/value-categories/img/function-collapse.svg)

*Виклик функції — це вже перетворення: те, що по цей бік дужок було трьома різними категоріями, по той стає двома типами.*

Макрос обходить обидві перепони одним рухом, бо він не приймає аргументу. Він **підставляє текст виразу** туди, де компілятор подивиться на нього напряму — у точці, де категорія ще ціла.

> 🔧 **Навіщо це.** Вимірювання не коштує нічого й нічим не ризикує: `VALUE_CATEGORY(v.at(999))` спокійно скаже «lvalue» на порожньому векторі, а `VALUE_CATEGORY(*p)` — «lvalue» для нульового покажчика, бо розіменування не відбудеться. Спірний вираз можна міряти прямо там, де він стоїть, а не відтворювати ситуацію в окремій пісочниці.

## Кома, яка ламає макрос

Один макропараметр — це пастка, і натрапляють на неї одразу:

```cpp
VALUE_CATEGORY(std::pair<int, int>{});   // помилка: макрос дістав ДВА аргументи
VALUE_CATEGORY((0, s));                  // а тут кома всередині дужок — усе гаразд
```

Препроцесор рахує дужки й не знає нічого про кутові: кома між `int` та `int` для нього — межа аргументів. Лікується це змінною арністю: макрос оголошують із трьома крапками й підставляють увесь «хвіст» цілком.

```cpp
#define VALUE_CATEGORY(...) (::probe::describe<decltype((__VA_ARGS__))>())
```

Дужок у цьому рядку три пари, і кожна за щось відповідає. Зовнішня — щоб макрос лишався одним виразом у будь-якому оточенні. Далі йде пара, якої вимагає синтаксис `decltype`. І нарешті внутрішня — та сама, що вмикає режим категорії; саме її найлегше загубити, і саме її втрата дає ту першу брехню, з якої ми починали.

## Константність, яку не можна не показувати

Прилад із трьох міток чесно скаже «xvalue» про `std::move(cs)`, де `cs` оголошено як `const std::string`. Формально це правда — і водночас найгірша можлива підказка, бо переміщення тут не станеться: переміщувальний конструктор бере `std::string&&` без `const`, під константу він не підходить, і перевантаження мовчки з'їжджає на копіювання ([коректність за const](book:cpp-standards/const-correctness)). Людина, яка щойно прочитала на екрані «xvalue», піде шукати причину копій деінде.

Тому вимірювач мусить показувати й константність. Технічно це один рядок: зняти посилання й спитати `std::is_const_v`.

## Готовий прилад

```cpp
// value_category_probe.hpp — вимірювач категорії виразу
#pragma once
#include <type_traits>

namespace probe {

struct lvalue_t  {};
struct xvalue_t  {};
struct prvalue_t {};

// Категорію закодовано ФОРМОЮ типу, який віддає decltype((expr))
template <typename T> struct category      { using tag = prvalue_t; };
template <typename T> struct category<T&>  { using tag = lvalue_t;  };
template <typename T> struct category<T&&> { using tag = xvalue_t;  };

// Псевдонім рятує від typename у шаблонному коді
template <typename T> using category_t = typename category<T>::tag;

constexpr const char* plain(lvalue_t)  { return "lvalue";  }
constexpr const char* plain(xvalue_t)  { return "xvalue";  }
constexpr const char* plain(prvalue_t) { return "prvalue"; }

constexpr const char* qualified(lvalue_t)  { return "const lvalue";  }
constexpr const char* qualified(xvalue_t)  { return "const xvalue";  }
constexpr const char* qualified(prvalue_t) { return "const prvalue"; }

template <typename T>
constexpr const char* describe() {
    if constexpr (std::is_const_v<std::remove_reference_t<T>>)
        return qualified(category_t<T>{});
    else
        return plain(category_t<T>{});
}

}  // namespace probe

// Для людини: рядок, який можна надрукувати
#define VALUE_CATEGORY(...) (::probe::describe<decltype((__VA_ARGS__))>())

// Для збірки: перевірка, яка ламає компіляцію при регресії
#define STATIC_CATEGORY(expected, ...)                                    \
    static_assert(                                                        \
        std::is_same_v<::probe::category_t<decltype((__VA_ARGS__))>,      \
                       ::probe::expected>,                                \
        "не та категорія виразу: " #__VA_ARGS__)
```

Мітка навмисне не знає про `const`: «яка це категорія» і «чи константне» — два різні питання, і змішувати їх у тесті було б незручно. Рядок для людини їх поєднує, бо людині потрібна повна картина одразу; перевірка для збірки — розділяє, бо перевіряти хочеться щось одне за раз.

Користуються ним так:

```cpp
#include <cstdio>
#include <string>
#include <utility>
#include "value_category_probe.hpp"

// Нічого з цього не треба ВИЗНАЧАТИ: жоден вираз нижче не виконується
std::string          make();
extern std::string   s;
extern std::string&& r;

int main() {
    std::puts(VALUE_CATEGORY(s));             // lvalue
    std::puts(VALUE_CATEGORY(r));             // lvalue  ← має ім'я
    std::puts(VALUE_CATEGORY(std::move(s)));  // xvalue
    std::puts(VALUE_CATEGORY(make()));        // prvalue
}
```

Ця програма компілюється й лінкується — попри те, що ні `make`, ні `s`, ні `r` ніде не визначені. Визначення потрібні тому, хто збирається щось виконувати; вимірювачеві досить оголошень.

## Прогін по виразах, де чуття промахується

Далі — те, заради чого прилад і будували. Оголошення для всіх рядків такі:

```cpp
std::string        make();
const std::string  make_const();     // так писати не варто — але подивімося
std::string&       shared();
std::string&&      expiring();

struct Buf { int cells[4]; };
Buf make_buf();

struct Node {
    std::string  name;
    std::string& alias;              // посилальний член
    unsigned     flag : 1;           // бітове поле
    static std::string kind;         // статичний член
};

extern Node n;
extern std::string s, s2;
extern const std::string cs;
extern std::string&& r;              // іменоване посилання на rvalue
extern int arr[4], i;
extern bool cond;
```

Спершу очікуване — щоб було з чим порівнювати:

| вираз | вимірювач каже | чому |
|---|---|---|
| `s` | `lvalue` | у виразу є ім'я |
| `cs` | `const lvalue` | те саме плюс константність |
| `42` | `prvalue` | у числа немає місця |
| `make()` | `prvalue` | результат ще нікому не належить |
| `shared()` | `lvalue` | функція повернула `T&` |
| `expiring()` | `xvalue` | функція повернула `T&&` |
| `std::move(s)` | `xvalue` | зведення до `std::string&&` |
| `s + "!"` | `prvalue` | новий рядок нікому не належить |
| `s += "!"` | `lvalue` | оператор повернув `std::string&` |

А тепер те, де чуття промахується майже завжди:

| вираз | вимірювач каже | чому |
|---|---|---|
| `r` (оголошено як `std::string&&`) | `lvalue` | категорія виразу — не оголошений тип змінної |
| `std::move(cs)` | `const xvalue` | переміщення не буде, буде копія |
| `make_const()` | `const prvalue` | `const` на поверненні вбиває переміщення |
| `"text"` | `const lvalue` | це масив `const char[5]` зі своєю адресою |
| `this` | `prvalue` | це не змінна, у нього немає адреси |
| `[]{}` | `prvalue` | замикання будується на місці (з C++20) |
| `arr[0]` | `lvalue` | індексують lvalue-масив |
| `std::move(arr)[0]` | `xvalue` | індексують rvalue-масив |
| `make_buf().cells[0]` | `xvalue` | масив усередині тимчасового |
| `std::move(n).name` | `xvalue` | приреченість передається членові |
| `std::move(n).alias` | `lvalue` | посилальний член — завжди lvalue |
| `std::move(n).kind` | `lvalue` | статичний член об'єктові не належить |
| `n.flag` (бітове поле) | `lvalue` | адреси немає, а категорія звичайна |
| `std::move(n.flag)` | не компілюється | посилання до бітового поля не прив'язати |
| `cond ? s : s2` | `lvalue` | обидві гілки — lvalue того самого типу |
| `cond ? s : std::move(s)` | `prvalue` | категорії різні — народжується новий об'єкт |
| `(0, s)` | `lvalue` | кома віддає праву гілку як є |
| `++i` | `lvalue` | префікс повертає саму змінну |
| `i++` | `prvalue` | постфікс повертає стару копію |
| `typeid(s)` | `const lvalue` | результат — `const std::type_info` |

Шість місць у цій таблиці варті окремої розмови.

**Іменоване rvalue-посилання.** Змінну оголошено як `std::string&&` — а вираз `r` є lvalue. Причина одна: у нього є ім'я, отже до нього повернуться, отже грабувати не можна. «Посилання на rvalue» — це властивість **змінної**, а не виразів із її іменем. Уся потреба в `std::forward` виростає звідси: параметр, оголошений як `T&&`, усередині функції поводиться як звичайна змінна, і без явного зведення передати приреченість далі неможливо.

**Посилальний і статичний члени.** Ці два рядки — готова тиха помилка. Ви пишете `std::move(wrapper).field`, певні, що забираєте нутрощі, а поле оголошене як `std::string&` — і вираз лишається lvalue, бо посилальний член об'єктові не належить: він лише позначає щось стороннє. Те саме зі статичним членом — приреченість `n` до нього не має жодного стосунку. Переміщення тихо не станеться, і жодного попередження не буде.

**Тернарний оператор.** Коли обидві гілки мають тотожність (тобто є lvalue або xvalue), той самий тип **і ту саму категорію**, результат успадковує її. Щойно категорії розійшлися — правило не спрацьовує, і результатом стає prvalue: компілятор змушений збудувати новий об'єкт із тієї гілки, яку обрали. Тому `cond ? big : std::move(big)` не «інколи переміщує, інколи ні», а завжди створює третій об'єкт — з лівої гілки копіюванням, з правої переміщенням. Вираз, що виглядає як вибір між двома посиланнями на той самий об'єкт, насправді робить копію.

**Масиви.** Індексація масиву-lvalue дає lvalue, індексація масиву-rvalue — xvalue, і саме тому `make_buf().cells[0]` виявляється приреченим. Правило дописали не одразу: у C++11 вираз індексації завжди був lvalue, і лише правка комітету CWG 1213 «Array subscripting and xvalues» (ухвалена 2013 року як виправлення дефекту, тобто чинна й для старішого коду) дала теперішнє формулювання — результат є lvalue, коли операнд-масив є lvalue, і xvalue в усіх інших випадках.

**Бітове поле.** Тут прилад упирається в межу самої мови. Саме поле він міряє без пригод: `n.flag` — звичайне lvalue, як і будь-який інший член. А от `std::move(n.flag)` не скомпілюється взагалі. `std::move` виводить свій параметр як `unsigned&`, тобто неконстантне lvalue-посилання, а прив'язати таке до бітового поля мова забороняє: у поля немає власної адреси, воно вужче за байт. Константне посилання й посилання на rvalue прив'язати можна — але зв'яжуться вони **не з полем**: стандарт наказує створити тимчасову копію значення й прив'язати посилання вже до неї. Тому `const unsigned& c = n.flag;` дає вид не на поле, а на його знімок, а перемістити бітове поле вдасться хіба через явну копію — `std::move(+n.flag)`, де унарний плюс спершу зчитує значення й народжує prvalue. Урок ширший за бітові поля: прилад міряє категорію виразу, а не тотожність об'єкта за ним ([бітові поля](book:programming/c-bitfields)).

**`this`.** Вираз `this` — prvalue, а не змінна: йому не можна присвоїти й не можна взяти адресу. Це не примха, а точний опис: `this` — обчислена адреса поточного об'єкта, і жодного місця, де вона лежить, мова не обіцяє. Контраст добре видно з нововведення C++23: коли явний параметр оголошено як `this auto&& self`, `self` — уже звичайний параметр, а отже його ім'я є lvalue, як і в будь-якого іншого ([що приніс C++23](book:cpp-standards/cpp23-features)).

## Що вимірювач бачить, а що ні

Обмежень у приладу небагато, і кожне пояснює щось про мову.

**Перевантажене ім'я не візьмеш.** Коли під іменем ховається кілька функцій, компілятор не знає, яку саме ви маєте на увазі, а вгадувати не має права. Обхід — назвати сигнатуру явно й повернутися від неї до lvalue:

```cpp
int f(int);
double f(double);

VALUE_CATEGORY(f);                             // помилка: яка саме f?
VALUE_CATEGORY(*static_cast<int(*)(int)>(f));  // lvalue — функція, узята за адресою й розіменована
```

**Лямбда — лише з C++20.** У C++11 лямбдам заборонили з'являтися в невиконуваних операндах, щоб не морочитися з їхніми унікальними типами в перевантаженнях і в іменах символів. Заборону зняв папір P0315R4 «Wording for lambdas in unevaluated contexts», що ввійшов у C++20; GCC вміє це з версії 9, Clang — з версії 17. Отже, рядок `VALUE_CATEGORY([]{})` — не універсальний тест, а перевірка на сучасність збірки.

**Неповні типи, навпаки, не заважають.** Здавалося б, `category<T>` мусить знати про `T` бодай розмір — але ні: параметром шаблону тип може бути й неповним, а нічого, що вимагає повноти, ми з ним не робимо. Більше того, стандарт спеціально це передбачив: від результату виклику функції він вимагає повного типу — і одразу робить виняток для `decltype`. Тобто виміряти категорію виклику функції, яка повертає лише оголошений, але ще не визначений тип, цілком законно.

**Прилад міряє намір, а не наслідок.** Він скаже, що `sink(std::move(x))` передає xvalue, — і промовчить про те, чи спрацював переміщувальний конструктор, чи копіювальний, чи взагалі жодного не було через усунення копій ([усунення копій](book:cpp-standards/copy-elision)). Категорія — це те, що вираз **дозволяє**; що з дозволу вийшло, вирішує вже перевантаження. Для другої половини питання потрібен другий прилад.

## Той самий макрос у тестах збірки

Найцінніше застосування вимірювача — не друк, а сторожа в CI. `static_assert` перевіряє умову під час компіляції й, коли вона хибна, ламає збірку з вашим текстом помилки — тобто регресія помирає до того, як хтось її запустить ([перевірки на етапі компіляції](book:programming/static-assert)).

```cpp
class Config {
    std::string text_;
public:
    const std::string& text() const& { return text_; }   // з живого об'єкта — дивимося
    std::string        text() &&     { return std::move(text_); }  // з тимчасового — забираємо
};

extern Config cfg;

STATIC_CATEGORY(lvalue_t,  cfg.text());        // вид на чуже, без копії
STATIC_CATEGORY(prvalue_t, Config{}.text());   // нутрощі забрано

static_assert(!std::is_const_v<std::remove_reference_t<decltype((Config{}.text()))>>,
              "повернення const-значення вимикає переміщення");
```

Цінність цих трьох рядків стає видно через півроку. Хтось «спрощує» клас і прибирає перевантаження з `&&` — другий рядок ламає збірку з поясненням, замість того щоб профіль через місяць показав зайві копії в гарячому шляху. Хтось дописує `const` до типу повернення «для надійності» — падає третій рядок, бо цей `const` тихо вимикає переміщення для всіх користувачів методу. Такі самі сторожі варто ставити на власні контейнери: `STATIC_CATEGORY(xvalue_t, std::move(v)[0])` фіксує, що ваш `operator[]` із `&&`-кваліфікатором справді віддає приречений елемент, а не звичайне посилання.

Коштує це нуль: `static_assert` не лишає в бінарнику жодного байта, а `describe()` — `constexpr`-функція, яка згортається в покажчик на літерал ще під час компіляції.

## Друга оптика: датчик конструкторів

Питання «яка це категорія» і «що компілятор із нею зробив» — різні, і другий прилад робиться так само просто: тип, який голосно повідомляє про кожен свій конструктор.

```cpp
#include <cstdio>

struct Loud {
    Loud()                { std::puts("будую"); }
    Loud(const Loud&)     { std::puts("копіюю"); }
    Loud(Loud&&) noexcept { std::puts("переміщую"); }
    ~Loud()               { std::puts("гину"); }
};
```

Поставте `Loud` замість справжнього типу в сумнівному місці, запустіть — і побачите, що сталося насправді: скільки разів скопійовано, чи спрацювало переміщення, чи об'єкт узагалі не будувався, бо його усунули. Разом два прилади закривають питання цілком.

## Підводні камені

**Макрос лишається макросом.** Він не бачить просторів імен і не поважає областей видимості, тож ім'я має бути кричущим і рідкісним. У публічному заголовку бібліотеки таким макросам не місце: тримайте їх у налагоджувальному чи тестовому заголовку, а якщо вже винесли назовні — знімайте `#undef`-ом наприкінці файлу.

**Препроцесор MSVC.** Наш макрос підставляє `__VA_ARGS__` напряму в код, а не передає в інший макрос, тож навіть давній препроцесор Visual C++ обробляє його правильно. Щойно почнете будувати з нього шари макросів — умикайте `/Zc:preprocessor`, інакше кома всередині аргументу знову поводитиметься не за стандартом.

**Шаблонний контекст.** Усередині шаблону `category<decltype((expr))>::tag` — залежне ім'я, і компілятор вимагатиме `typename` перед ним. Псевдонім `category_t` у заголовку існує саме тому: він ховає `typename` усередині себе, і код виклику лишається однаковим і в шаблоні, і поза ним.

**Найчастіша помилка — виміряти не той вираз.** Прилад відповідає рівно про той текст, який ви йому дали. Якщо суперечка про рядок `sink(builder.take())`, то міряти треба `builder.take()`, а не `builder` і не змінну, у яку результат потім лягає: категорія живе у виразі, а не в його учасниках. Найдешевший спосіб не помилитися — скопіювати спірний вираз із коду буквально, разом з усіма викликами, і вставити в дужки макроса.
