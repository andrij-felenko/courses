# ⚙️ Проєкт: обгортка, яка сама себе зважує

Про ідеальне передавання легко сперечатися словами — а можна порахувати. Тут ми збираємо невелику програму, у якій кожне копіювання й кожне переміщення друкує рядок про себе, і проганяємо крізь неї три версії однієї обгортки, маленьку фабрику на кшталт `make_unique`, `emplace` власного контейнера і дві пастки, у які передавальне посилання заводить найчастіше. Наприкінці буде не переконання, а таблиця чисел — і кілька з них виявляться не такими, як підказує здоровий глузд.

Усе нижче — **один файл** `forward-lab.cpp`. Шматки наведено в тому порядку, у якому вони мають стояти; разом вони збираються командою:

```
g++ -std=c++20 -Wall forward-lab.cpp -o forward-lab
```

## Піддослідний, який усе рахує

Щоб міряти, потрібен тип, чиї конструктори видно. Заводимо `Probe`: він тримає рядок-мітку, рахує події в глобальному лічильнику й друкує кожну.

```cpp
#include <concepts>
#include <cstddef>
#include <cstdio>
#include <memory>
#include <new>
#include <stdexcept>
#include <string>
#include <type_traits>
#include <utility>

struct Tally { int made = 0, copied = 0, moved = 0; };
Tally tally;
bool verbose = true;

// printf міряє ширину в байтах, а не в літерах, тож вирівнюємо самі
std::string pad(const char* s, std::size_t width) {
    std::string out = s;
    std::size_t letters = 0;
    for (unsigned char ch : out)
        if ((ch & 0xC0) != 0x80) ++letters;      // байти-продовження не рахуємо
    while (letters < width) { out += ' '; ++letters; }
    return out;
}

void reset() { tally = Tally{}; }

void numbers() {
    std::printf("      = конструктори %d, копії %d, переміщення %d\n",
                tally.made, tally.copied, tally.moved);
}
```

Тепер сам піддослідний.

```cpp
class Probe {
public:
    explicit Probe(std::string name) : name_(std::move(name)) {
        ++tally.made;
        note("конструктор");
    }
    Probe(const Probe& other) : name_(other.name_), hollow_(other.hollow_) {
        ++tally.copied;
        note("КОПІЮВАННЯ");
    }
    Probe(Probe&& other) noexcept
        : name_(std::move(other.name_)), hollow_(other.hollow_) {
        other.hollow_ = true;                    // джерело віддало вміст
        ++tally.moved;
        note("переміщення");
    }
    Probe& operator=(const Probe&) = delete;
    Probe& operator=(Probe&&) = delete;

    const char* text() const { return hollow_ ? "<порожньо>" : name_.c_str(); }

private:
    void note(const char* what) const {
        if (verbose) std::printf("      %s%s\n", pad(what, 14).c_str(), text());
    }
    std::string name_;
    bool hollow_ = false;
};
```

Три рішення в цьому класі варті пояснення, бо без них вимірювання брехало б.

**Присвоєння видалено.** Не тому, що воно шкідливе, а тому, що інакше частина подій пройшла б повз лічильник: об'єкт міг би змінитися присвоєнням, а ми рахуємо тільки конструктори. Після `= delete` компілятор гарантує: кожен `Probe` у програмі з'явився через один із трьох перелічених входів, і жодна подія не заховалася.

**Прапорець `hollow_` успадковується.** Найспокусливіше було б написати в конструкторі переміщення просто `other.hollow_ = true` і на цьому спинитися. Тоді об'єкт, зроблений із уже спустошеного джерела, вважав би себе цілим — його власне поле `hollow_` дорівнювало б `false` за замовчуванням, а `name_` містив би те, що лишилося від чужого рядка. Тому прапорець їде разом із вмістом: `hollow_(other.hollow_)`. Тільки завдяки цьому пастка з циклом далі покаже чесне `<порожньо>` замість того, щоб покладатися на випадковість реалізації.

Це не дрібниця. Стандарт каже, що переміщений `std::string` лишається у **дійсному, але невизначеному** стані — див. [семантику переміщення](book:cpp-standards/move-semantics). На поширених реалізаціях він виявляється порожнім, і саме тому такий баг легко «побачити» в одному компіляторі й проґавити в іншому. Власний прапорець робить спостереження незалежним від бібліотеки.

**Вирівнювання рахуємо руками.** `printf("%-14s")` міряє ширину поля в байтах, а кожна кирилична літера в UTF-8 займає два. Функція `pad` рахує байти, у яких два старші біти не дорівнюють `10` — тобто початкові байти символів, а не продовження. Дрібниця, але без неї весь журнал з'їхав би, а журнал тут і є результатом.

## Три обгортки, шість вимірів

Кінцевий споживач — функція з параметром за значенням. Так поводиться будь-хто, кому потрібна власна копія: конструктор, що зберігає поле, контейнер, що кладе елемент собі.

```cpp
void consume(Probe kept) { (void)kept; }   // кінцева зупинка

template <class T> void wrapByValue(T x)           { consume(std::move(x)); }
template <class T> void wrapByConstRef(const T& x)  { consume(x); }
template <class T> void wrapByForward(T&& x)        { consume(std::forward<T>(x)); }
```

Три обгортки роблять одне й те саме — беруть аргумент і віддають його `consume`. Різняться лише оголошенням параметра. Проганяємо кожну двічі: з іменованою змінною й з тимчасовим об'єктом.

```cpp
void demoWrappers() {
    std::puts("\n=== 1. Три обгортки під навантаженням ===");

    verbose = false;
    Probe left("лівий");
    verbose = true;

    std::puts("\n-- аргумент lvalue: іменована змінна --");
    std::puts("   за значенням:");     reset(); wrapByValue(left);      numbers();
    std::puts("   за const&:");        reset(); wrapByConstRef(left);   numbers();
    std::puts("   передавальне T&&:"); reset(); wrapByForward(left);    numbers();

    std::puts("\n-- аргумент rvalue: тимчасовий об'єкт --");
    std::puts("   за значенням:");     reset(); wrapByValue(Probe("правий"));    numbers();
    std::puts("   за const&:");        reset(); wrapByConstRef(Probe("правий")); numbers();
    std::puts("   передавальне T&&:"); reset(); wrapByForward(Probe("правий"));  numbers();
}
```

Ось що друкує ця частина:

```text
=== 1. Три обгортки під навантаженням ===

-- аргумент lvalue: іменована змінна --
   за значенням:
      КОПІЮВАННЯ    лівий
      переміщення   лівий
      = конструктори 0, копії 1, переміщення 1
   за const&:
      КОПІЮВАННЯ    лівий
      = конструктори 0, копії 1, переміщення 0
   передавальне T&&:
      КОПІЮВАННЯ    лівий
      = конструктори 0, копії 1, переміщення 0

-- аргумент rvalue: тимчасовий об'єкт --
   за значенням:
      конструктор   правий
      переміщення   правий
      = конструктори 1, копії 0, переміщення 1
   за const&:
      конструктор   правий
      КОПІЮВАННЯ    правий
      = конструктори 1, копії 1, переміщення 0
   передавальне T&&:
      конструктор   правий
      переміщення   правий
      = конструктори 1, копії 0, переміщення 1
```

Зведімо це в таблицю. Рядок «конструктор» у правій половині — це поява самого тимчасового об'єкта; вона однакова в усіх трьох випадках, тож у порівнянні не важить.

| оголошення параметра | lvalue-аргумент | rvalue-аргумент |
|---|---|---|
| `T x` — за значенням | 1 копія + 1 переміщення | 1 переміщення |
| `const T& x` | 1 копія | **1 копія** |
| `T&& x` + `std::forward` | 1 копія | 1 переміщення |

Перше, що видно: **для lvalue-аргументу передавальне посилання не дає нічого.** Рядок `const T&` і рядок `T&&` в лівій колонці збігаються, і збігаються на одній копії: споживач хоче власний примірник, а іменована змінна лишається жити в викликача, тож хтось мусить цю копію зробити. Уся вигода передавання зосереджена в правій колонці, у єдиній клітинці, виділеній жирним: коли викликач віддає тимчасовий об'єкт, версія з `const&` робить повне копіювання приреченого вмісту. Не помилка, не падіння — просто виділення пам'яті й побайтове копіювання там, де мало бути присвоєння вказівника.

Друге, менш очікуване: **версія за значенням програє лише одне переміщення.** На lvalue-шляху вона робить зайвий рух, на rvalue-шляху не програє нічого. Причина другого — у правилі мови, а не в оптимізації: prvalue-аргумент від C++17 ініціалізує сам параметр, тож проміжного об'єкта, який треба було б переміщувати, просто не існує. Папір, що це закріпив, називається [P0135R1 «Wording for guaranteed copy elision through simplified value categories»](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0135r1.html) (Річард Сміт, 2016), і назва його трохи оманлива — копію тут не усувають, її від початку немає; докладніше — [усунення копій](book:cpp-standards/copy-elision).

Звідси практичний висновок. Для типів із дешевим переміщенням — рядок, вектор, `unique_ptr` — прийом «беремо за значенням і переміщуємо далі» лишається цілком розумним вибором: одне зайве переміщення в обмін на звичайну функцію без шаблона й без виносу тіла в заголовок. Ламається він там, де переміщення не дешеве або його немає взагалі: `std::array<char, 4096>` переміщується копіюванням, і те «одне зайве переміщення» коштує повних чотири кілобайти.

> 🔧 **Навіщо це.** Коли постає питання «як оголосити цей параметр», відповідь не треба вгадувати. Підставте свій тип замість `std::string` у `Probe` — і таблиця для нього збереться сама, за півгодини. Особливо корисно там, де конструктор копіювання власний і ціна копії неочевидна.

## Фабрика: їдуть аргументи, а не об'єкт

Тепер найпоширеніша роль передавального посилання — фабрика, що конструює об'єкт із чужих аргументів. Пакет параметрів (`Args&&...`) робить її незалежною від їхньої кількості; про сам механізм пакетів — [шаблони змінної арності](book:cpp-standards/variadic-and-folds).

```cpp
template <class T, class... Args>
std::unique_ptr<T> makeOne(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}
```

Це майже дослівно `std::make_unique` — функція, яку Стефан Т. Лававей (Microsoft) подав папером [N3656](https://isocpp.org/files/papers/N3656.txt) від 18 квітня 2013 року (переробка ранішого N3588 за відгуками бібліотечної підгрупи) і яку того ж місяця на зустрічі в Бристолі ухвалили до чернетки C++14; окремі перевантаження там додано ще для масивів. Повертає вона одноосібне володіння — [unique_ptr](book:cpp-standards/unique-ptr).

Зверніть увагу на **круглі дужки** в `new T(...)`. Це не стилістичний вибір: із фігурними дужками `new T{...}` виклик `makeOne<std::vector<int>>(3, 7)` дав би вектор із двох елементів `{3, 7}`, а з круглими дає три сімки. Стандартний `make_unique` теж вживає круглі — і саме тому не вміє конструювати агрегати списком ініціалізації. Ще одне: `std::forward` пишеться **на кожен аргумент окремо**, а не на пакет цілком; `...` після виразу розкриває його по одному разу для кожного елемента.

```cpp
void demoFactory() {
    std::puts("\n=== 2. Фабрика: їдуть аргументи, а не об'єкт ===");

    verbose = false;
    Probe source("джерело");
    verbose = true;

    std::puts("\n   makeOne<Probe>(\"з літерала\"):");
    reset();
    { auto p = makeOne<Probe>("з літерала"); std::printf("      у купі: %s\n", p->text()); }
    numbers();

    std::puts("\n   makeOne<Probe>(source):");
    reset();
    { auto p = makeOne<Probe>(source); std::printf("      у купі: %s\n", p->text()); }
    numbers();

    std::puts("\n   makeOne<Probe>(std::move(source)):");
    reset();
    { auto p = makeOne<Probe>(std::move(source)); std::printf("      у купі: %s\n", p->text()); }
    numbers();

    std::printf("\n   а source після цього: %s\n", source.text());
}
```

```text
=== 2. Фабрика: їдуть аргументи, а не об'єкт ===

   makeOne<Probe>("з літерала"):
      конструктор   з літерала
      у купі: з літерала
      = конструктори 1, копії 0, переміщення 0

   makeOne<Probe>(source):
      КОПІЮВАННЯ    джерело
      у купі: джерело
      = конструктори 0, копії 1, переміщення 0

   makeOne<Probe>(std::move(source)):
      переміщення   джерело
      у купі: джерело
      = конструктори 0, копії 0, переміщення 1

   а source після цього: <порожньо>
```

Перший випадок — головний. Нуль копій і нуль переміщень: об'єкт узагалі не подорожував, бо його ще не існувало. Крізь фабрику проїхав рядковий літерал, а `Probe` народився вже в купі, там, де й лишиться. Це і є сенс фрази «конструювати на місці»: передавати треба **матеріал**, а не готовий виріб.

Два наступні випадки показують, що буває, коли виріб уже готовий. Фабрика чесно донесла категорію: з lvalue — копія, з rvalue — переміщення, і після третього виклику `source` порожній, як і має бути. Але жоден із цих двох не досягає нуля з першого. Обгортка вміє не псувати — скасувати вже зроблене вона не вміє.

## emplace і сирі байти

Той самий прийом усередині контейнера виглядає цікавіше, бо там нема куди «повертати» об'єкт — його треба збудувати за адресою, яку контейнер сам порахував. Пишемо мінімальне сховище: воно бере сирий шматок пам'яті й конструює в ньому елементи розміщувальним `new`. Механіка вирівнювання, `::operator new` з `align_val_t` і `std::launder` — окрема тема, [вирівнювання й розміщувальний new](book:cpp-standards/alignment-placement-new); тут вона потрібна як тло.

```cpp
template <class T>
class Bin {
public:
    explicit Bin(std::size_t capacity)
        : raw_(static_cast<std::byte*>(
              ::operator new(capacity * sizeof(T), std::align_val_t{alignof(T)}))),
          cap_(capacity) {}

    ~Bin() {
        while (size_ > 0) { --size_; (*this)[size_].~T(); }
        ::operator delete(raw_, std::align_val_t{alignof(T)});
    }

    Bin(const Bin&) = delete;
    Bin& operator=(const Bin&) = delete;

    template <class... Args>
    T& emplace(Args&&... args) {
        if (size_ == cap_) throw std::length_error("Bin: місця немає");
        void* slot = raw_ + size_ * sizeof(T);
        T* made = ::new (slot) T(std::forward<Args>(args)...);
        ++size_;
        return *made;
    }

    T& operator[](std::size_t i) {
        return *std::launder(reinterpret_cast<T*>(raw_ + i * sizeof(T)));
    }

    std::size_t size() const { return size_; }

private:
    std::byte* raw_;
    std::size_t cap_;
    std::size_t size_ = 0;
};
```

Ключовий рядок один: `::new (slot) T(std::forward<Args>(args)...)`. У перших дужках — адреса, куди класти; у других — аргументи, що дожили сюди зі своїми категоріями. Між ними немає жодного проміжного `T`. Саме цим `emplace_back` відрізняється від `push_back`: перший приймає матеріал, другий — готовий об'єкт.

```cpp
void demoEmplace() {
    std::puts("\n=== 3. Власний контейнер: emplace, а не push ===");

    verbose = false;
    Probe ready("готовий");
    verbose = true;

    Bin<Probe> bin(4);

    std::puts("\n   bin.emplace(\"зроблений на місці\"):");
    reset(); bin.emplace("зроблений на місці"); numbers();

    std::puts("\n   bin.emplace(ready):");
    reset(); bin.emplace(ready); numbers();

    std::puts("\n   bin.emplace(std::move(ready)):");
    reset(); bin.emplace(std::move(ready)); numbers();

    std::printf("\n   вміст сховища (%zu):", bin.size());
    for (std::size_t i = 0; i < bin.size(); ++i)
        std::printf(" [%s]", bin[i].text());
    std::putchar('\n');
}
```

```text
=== 3. Власний контейнер: emplace, а не push ===

   bin.emplace("зроблений на місці"):
      конструктор   зроблений на місці
      = конструктори 1, копії 0, переміщення 0

   bin.emplace(ready):
      КОПІЮВАННЯ    готовий
      = конструктори 0, копії 1, переміщення 0

   bin.emplace(std::move(ready)):
      переміщення   готовий
      = конструктори 0, копії 0, переміщення 1

   вміст сховища (3): [зроблений на місці] [готовий] [готовий]
```

Числа ті самі, що у фабрики, — і це головний висновок: чарівництва в `emplace` немає. Він не робить копію дешевшою; він дає **можливість її не робити**, якщо викликач передасть аргументи замість об'єкта. Напишіть `bin.emplace(ready)` — і матимете рівно те саме копіювання, що дав би `push(ready)`. Виграє тільки перший виклик, де об'єкта до входу в контейнер взагалі не існувало.

Ще одна дрібниця, яку видно в останньому рядку виводу: третій елемент друкує «готовий», а не «порожньо». У джерела перед переміщенням прапорець `hollow_` дорівнював `false`, тож ціль дістала `false` — а спорожнів після цього сам `ready`. Так і має бути: вміст не зник, він змінив адресу.

## Пастка перша: forward у циклі

Тепер найдорожча помилка. `std::forward` може обернутися переміщенням — отже, аргумент після нього спожито, і скористатися ним удруге не можна. У циклі це правило порушується непомітно.

```cpp
class Receiver {
public:
    explicit Receiver(const char* tag) : tag_(tag) {}
    void add(Probe p) { std::printf("      %s отримав: %s\n", tag_, p.text()); }
private:
    const char* tag_;
};

template <class T>
void broadcastBroken(Receiver* rs, std::size_t n, T&& value) {
    for (std::size_t i = 0; i < n; ++i)
        rs[i].add(std::forward<T>(value));          // ← forward на кожній ітерації
}

template <class T>
void broadcastFixed(Receiver* rs, std::size_t n, T&& value) {
    if (n == 0) return;
    for (std::size_t i = 0; i + 1 < n; ++i)
        rs[i].add(value);                           // усім, крім останнього, — копія
    rs[n - 1].add(std::forward<T>(value));          // останньому можна віддати
}

void demoLoop() {
    std::puts("\n=== 4. Пастка: forward у циклі ===");
    Receiver rs[3] = { Receiver{"A"}, Receiver{"B"}, Receiver{"C"} };

    verbose = false;
    Probe named("вітання");
    verbose = true;

    std::puts("\n   зламана версія, аргумент lvalue — усе гаразд:");
    reset(); broadcastBroken(rs, 3, named); numbers();

    std::puts("\n   зламана версія, аргумент rvalue — вміст зникає:");
    reset(); broadcastBroken(rs, 3, Probe("вітання")); numbers();

    std::puts("\n   полагоджена версія, аргумент rvalue:");
    reset(); broadcastFixed(rs, 3, Probe("вітання")); numbers();
}
```

*Той самий об'єкт `value` у три моменти часу. Угорі кожної колонки — стан аргументу перед ітерацією, унизу — що дістав приймач.*

Перший блок виводу пояснює, чому така помилка спокійно доживає до робочої системи. З іменованою змінною зламана функція працює **бездоганно**: `T` виводиться як `Probe&`, `std::forward<Probe&>` віддає lvalue, ніхто нічого не забирає, усі три приймачі отримують свої копії. Тести, у яких аргумент — локальна змінна, зелені. Ламається воно рівно тоді, коли хтось напише `broadcastBroken(rs, 3, Probe("вітання"))` — і навіть тоді не впаде, а тихо роздасть порожнечу.

Але найцікавіше — у самих числах. Зламана версія: **3 переміщення, 0 копій**. Полагоджена: **2 копії, 1 переміщення**. За наївною метрикою «менше копій — краще» зламаний код виглядає кращим. Лічильник копій — не показник якості; він показник того, скільки разів вміст роздвоївся, а не скільки разів дійшов за призначенням. Тому єдина надійна перевірка тут — не профайлер, а те, що надрукували приймачі.

Правило, яке з цього випливає, коротке: **на один аргумент — один `std::forward`, і той на останньому використанні**. У циклі це означає «всім копія, останньому оригінал». Автоматично таке ловить перевірка `bugprone-use-after-move` у clang-tidy — вона розуміє й `std::move`, і `std::forward`, і саме її варто ввімкнути там, де передавальних посилань багато.

## Пастка друга: шаблон, який хапає своє

Передавальне посилання прив'язується до всього — зокрема й до типу, у чиєму класі його оголошено. Конструктор `template <class S> Guest(S&&)` стає конкурентом власного конструктора копіювання, і в одному конкретному випадку виграє. Побачити це на самих конструкторах не вийде: код, який демонструє помилку, не компілюється. Тож розіграємо той самий відбір на двох звичайних функціях із такими самими сигнатурами — і роздрукуємо переможця.

```cpp
struct Person { std::string name; };
struct Student : Person {};

const char* pick(const Person&)          { return "нешаблон  (const Person&)"; }
template <class S> const char* pick(S&&) { return "ШАБЛОН    (S&&)"; }

void demoGreedy() {
    std::puts("\n=== 5. Ненажерливий шаблон: хто виграє відбір ===");

    Person p{"Леся"};
    const Person cp{"Леся"};
    Student st{};
    const Student cst{};

    std::printf("   %s%s\n", pad("Person, неконстантний lvalue", 32).c_str(),  pick(p));
    std::printf("   %s%s\n", pad("Person, константний lvalue", 32).c_str(),    pick(cp));
    std::printf("   %s%s\n", pad("Person, тимчасовий об'єкт", 32).c_str(),     pick(Person{"Леся"}));
    std::printf("   %s%s\n", pad("Student, неконстантний lvalue", 32).c_str(), pick(st));
    std::printf("   %s%s\n", pad("Student, константний lvalue", 32).c_str(),   pick(cst));
}
```

```text
=== 5. Ненажерливий шаблон: хто виграє відбір ===
   Person, неконстантний lvalue    ШАБЛОН    (S&&)
   Person, константний lvalue      нешаблон  (const Person&)
   Person, тимчасовий об'єкт       ШАБЛОН    (S&&)
   Student, неконстантний lvalue   ШАБЛОН    (S&&)
   Student, константний lvalue     ШАБЛОН    (S&&)
```

Чотири рядки з п'яти виграє шаблон. Перший рядок — та сама смерть конструктора копіювання: обидва кандидати дають точний збіг, але шаблон прив'язується до `Person`, а нешаблон — до `const Person`, і менш кваліфікована ціль краща. Другий рядок показує, чому баг такий підступний: для константного аргументу прив'язки зрівнюються, спрацьовує тай-брейк «нешаблон кращий за шаблон» — і копіювання константного об'єкта працює. Читач бачить, що `const Person c = p;` компілюється, і не чекає, що `Person q{p};` не скомпілюється.

А два останні рядки додають те, чого на самому `Person` не побачити: для спадкоємця **константність не рятує**. Нешаблонний кандидат мусить перетворити `Student` на базу — це вже не точний збіг, а перетворення; шаблон виводить `S = const Student&` і збігається точно. Конструктор копіювання бази не викличеться ніколи, ні для константного об'єкта, ні для звичайного. Чому саме так порівнюються ці кандидати — [розв'язання перевантажень](book:cpp-standards/overload-resolution).

Лікування — не давати шаблонові претендувати на власний тип і його нащадків. У C++20 це пишеться прямо, через [концепти й обмеження](book:cpp-standards/concepts-constraints):

```cpp
class Guest {
public:
    template <class S>
        requires (!std::is_base_of_v<Guest, std::remove_cvref_t<S>>)
              && std::constructible_from<std::string, S>
    explicit Guest(S&& src) : name_(std::forward<S>(src)) { say("шаблонний конструктор"); }

    Guest(const Guest& other) : name_(other.name_) { say("конструктор копіювання"); }
    Guest(Guest&& other) noexcept : name_(std::move(other.name_)) { say("конструктор переміщення"); }

    const std::string& name() const { return name_; }

private:
    static void say(const char* what) { std::printf("      %s\n", what); }
    std::string name_;
};

struct Vip : Guest {
    Vip() : Guest("вельможа") {}
};
```

Перша умова прибирає з розгляду сам `Guest` і все, що від нього походить: `std::is_base_of_v<Guest, Guest>` дорівнює `true`, бо клас вважається базою самого себе, — саме це нам і потрібно. `std::remove_cvref_t` знімає посилання й `const`, бо `S` цілком може бути `Guest&`, і без цього перевірка нічого не знайшла б. Друга умова, `constructible_from`, не менш важлива за першу: без неї шаблон лишався б у списку кандидатів для типів, із яких рядка не збудувати, і помилка вивалювалася б із нутрощів конструктора замість чесного «немає відповідного конструктора».

До C++20 те саме роблять через [SFINAE й enable_if](book:cpp-standards/sfinae-and-enable-if):

```cpp
class GuestCpp17 {
public:
    template <class S,
              class = std::enable_if_t<
                  !std::is_base_of_v<GuestCpp17, std::decay_t<S>> &&
                   std::is_constructible_v<std::string, S>>>
    explicit GuestCpp17(S&& src) : name_(std::forward<S>(src)) {}

    GuestCpp17(const GuestCpp17&) = default;
    GuestCpp17(GuestCpp17&&) noexcept = default;

    const std::string& name() const { return name_; }
private:
    std::string name_;
};
```

Тут `std::decay_t` замість `std::remove_cvref_t`, бо друга риса з'явилася лише в C++20; для наших цілей вони рівноцінні — див. [риси типів](book:cpp-standards/type-traits). Але цей запис має ваду, про яку варто знати: аргумент шаблону за замовчуванням **не входить у сигнатуру**, тож двох перевантажень, що різняться тільки цим `enable_if`, оголосити не можна — компілятор вважатиме їх повторним оголошенням однієї функції. Для одного конструктора це не заважає; щойно умов стане дві, доведеться переносити `enable_if` у тип повернення або в додатковий параметр-вказівник.

```cpp
void demoGuard() {
    std::puts("\n   із запобіжником requires — шаблон більше не претендує на свій тип:");

    std::puts("   Guest g1{\"Леся\"};");
    Guest g1{"Леся"};
    std::puts("   Guest g2{g1};");
    Guest g2{g1};
    std::puts("   Guest g3{std::move(g2)};");
    Guest g3{std::move(g2)};
    std::puts("   Vip vip;");
    Vip vip;
    std::puts("   Guest g4{vip};");
    Guest g4{vip};

    std::printf("      цілі: %s, %s, %s\n",
                g1.name().c_str(), g3.name().c_str(), g4.name().c_str());

    GuestCpp17 old{"той самий запобіжник через enable_if"};
    GuestCpp17 copy{old};
    std::printf("      C++17-версія: %s\n", copy.name().c_str());
}

int main() {
    demoWrappers();
    demoFactory();
    demoEmplace();
    demoLoop();
    demoGreedy();
    demoGuard();
}
```

Кожен рядок тут — окрема перевірка. `g1` з рядкового літерала йде через шаблон, як і задумано. `g2` з `Guest`-lvalue і `g3` з `Guest`-rvalue тепер потрапляють до справжніх конструкторів копіювання й переміщення. `g4` із `Vip` — до конструктора копіювання бази, чого без обмеження не сталося б ніколи. І сам `vip` конструюється тим самим шаблонним конструктором, бо масив символів `Guest`-ові не нащадок.

## Ціна й межі

Передавальне посилання не безкоштовне, і рахунок йому виставляють не в тактах.

**Тіло переїжджає в заголовок.** Обгортка мусить бути шаблоном, а шаблон інстанціюється в місці виклику — отже, його визначення видно всім, хто його вживає. Кожен новий тип аргументу породжує окреме тіло; за цим тягнеться час компіляції, розмір бінарника й довжина повідомлень про помилки. Коли ціна копії мала, а типів багато, звичайний нешаблонний параметр за значенням або `const&` виграє за сукупністю — про це є окрема тема, [ціна інстанціювання](book:cpp-standards/instantiation-cost).

**Помилка приходить пізно.** Нешаблонна функція перевіряє аргумент на межі; шаблонна пропускає все й падає всередині, вже після підстановки. Обмеження `requires` — це не косметика, а спосіб повернути перевірку на межу, де вона й має бути.

**Спожити можна один раз.** Це не властивість `std::forward`, а властивість переміщення, але саме через `forward` вона проникає в код непомітно: те саме місце поводиться по-різному залежно від того, що передав викликач. Тому й пастка з циклом мовчить у половині випадків.

**Прапорець мусить їхати з вантажем.** Якби `Probe` не переносив `hollow_` у ціль, блок про цикл показав би «вітання» там, де насправді порожньо, — або порожньо там, де все гаразд, залежно від реалізації рядка. Коли пишете власний вимірювальний тип, перевірте це першим: інструмент, що бреше, гірший за відсутність інструмента.

Винести `Probe` окремим заголовком у тести варто одразу — далі він знадобиться щоразу, коли сигнатура спірна. Одне доповнення, яке в бойових тестах виправдовує себе відразу: додайте до нього лічильник деструкторів і звіряйте його з сумою `made + copied + moved`. Рівність означає, що жоден об'єкт не загубився й не з'явився з нізвідки; розбіжність — що є ще один шлях створення, якого ви не помітили, і всі попередні числа треба перечитати спочатку.
