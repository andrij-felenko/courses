# 📋 Інтерфейс підтримки контрактів: <contracts> і семантика обробки

Цей довідник надає вичерпну специфікацію програмного інтерфейсу стандартного заголовного файлу `<contracts>`, структури метаданих порушення `std::contracts::contract_violation`, правил розміщення контрактних специфікаторів `pre`, `post`, `contract_assert` у граматиці мови C++26, поведінки контрактів у константних виразах, лямбда-виразах, корутинах, віртуальних ієрархіях та шаблонах, а також вимог до бінарного інтерфейсу (ABI) та механізмів конфігурації семантик оцінки на рівні компілятора та компонувальника.

## Стандартний заголовок `<contracts>`

Заголовок `<contracts>` надає типи даних, службові переліки та точки інтеграції середовища виконання, необхідні для реєстрації, інспекції та обробки порушень контрактів. Він входить до складу вільного від залежностей ядра стандартної бібліотеки C++26 і доступний як у звичайних середовищах виконання, так і в автономних середовищах розробки для вбудованих систем (freestanding implementations).

```cpp
namespace std::contracts {

    // Класифікація контрактного специфікатора за його синтаксичною роллю
    enum class contract_kind : unsigned char {
        pre,        // Преумова функції (pre)
        post,       // Постумова функції (post)
        assert      // Внутрішнє твердження в тілі блоку (contract_assert)
    };

    // Спосіб ідентифікації та реєстрації порушення під час оцінки
    enum class detection_mode : unsigned char {
        predicate_false,      // Вираз предиката успішно обчислився і повернув false
        evaluation_exception  // Під час обчислення предиката виник необроблений виняток
    };

    // Клас метаданих порушення контракту
    class contract_violation {
    public:
        // Конструктори копіювання та переміщення видалені для збереження цілісності рантайму
        contract_violation(const contract_violation&) = delete;
        contract_violation(contract_violation&&) = delete;
        contract_violation& operator=(const contract_violation&) = delete;
        contract_violation& operator=(contract_violation&&) = delete;

        // Номер рядка вихідного коду, де оголошено відповідний контракт
        [[nodiscard]] constexpr uint_least32_t line_number() const noexcept;

        // Ім'я або повний шлях до файлу вихідного коду (UTF-8 рядок із нульовим байтом)
        [[nodiscard]] constexpr const char* file_name() const noexcept;

        // Сигнатура або ім'я функції, до якої прив'язано контракт
        [[nodiscard]] constexpr const char* function_name() const noexcept;

        // Текст або мітка контракту, зазначена в квадратних дужках [name]
        [[nodiscard]] constexpr const char* comment() const noexcept;

        // Текстовий запис виразу предиката мовою C++
        [[nodiscard]] constexpr const char* predicate() const noexcept;

        // Вид контракту: pre, post або assert
        [[nodiscard]] constexpr contract_kind kind() const noexcept;

        // Причина спрацювання механізму порушення
        [[nodiscard]] constexpr detection_mode detection_mode() const noexcept;
    };

} // namespace std::contracts
```

## Детальний опис методів класу `std::contracts::contract_violation`

Об'єкт класу `contract_violation` інстанціюється внутрішнім середовищем виконання C++ у точці виявлення хибного або аварійного предиката. Посилання на цей об'єкт передається як єдиний аргумент до функції зворотного виклику `handle_contract_violation`.

### 1. `line_number()`
```cpp
[[nodiscard]] constexpr uint_least32_t line_number() const noexcept;
```
- **Призначення:** Повертає номер фізичного або логічного рядка вихідного файлу, де знаходиться відповідний специфікатор контракту.
- **Тип повернення:** Ціле беззнакове число `std::uint_least32_t` (щонайменше 32 біти).
- **Гарантії та особливості:** Якщо інформацію про рядки було усунуто компілятором під час збирання для мінімізації розміру бінарного образу (наприклад, за наявності специфічних опцій стиснення метаданих або у вбудованих прошивках), метод повертає значення `0`.

### 2. `file_name()`
```cpp
[[nodiscard]] constexpr const char* file_name() const noexcept;
```
- **Призначення:** Повертає вказівник на рядок шляху до файлу вихідного коду.
- **Тип повернення:** Вказівник на константний C-рядок `const char*` із нульовим завершенням.
- **Час життя пам'яті:** Рядок зберігається в сегменті статичних даних виконуваного файлу (`.rodata`). Вказівник залишається повністю валідним протягом усього часу функціонування операційної системи або процесу.

### 3. `function_name()`
```cpp
[[nodiscard]] constexpr const char* function_name() const noexcept;
```
- **Призначення:** Повертає читабельну назву функції, яка містить або контролює цей контракт.
- **Тип повернення:** `const char*` із нульовим завершенням.
- **Формат рядка:** Формується компілятором аналогічно до вбудованих макросів `__PRETTY_FUNCTION__` або `__func__`, включаючи простір імен, ім'я класу та типи параметрів. Якщо контракт оголошено поза тілом функції (наприклад, глобальне твердження модуля), метод повертає вказівник на порожній рядок `""`.

### 4. `comment()`
```cpp
[[nodiscard]] constexpr const char* comment() const noexcept;
```
- **Призначення:** Надає доступ до символічної мітки або описового коментаря контракту.
- **Тип повернення:** `const char*` із нульовим завершенням.
- **Поведінка:** Якщо в коді використано синтаксис міток виду `pre [index_in_range]: idx < size()`, метод повертає рядок `"index_in_range"`. Якщо контракт задекларовано без мітки (`pre: idx < size()`), метод гарантовано повертає порожній рядок `""`, ніколи не повертаючи нульовий покажчик `nullptr`.

### 5. `predicate()`
```cpp
[[nodiscard]] constexpr const char* predicate() const noexcept;
```
- **Призначення:** Повертає вихідний текст виразу мови C++, що використовувався як предикат.
- **Тип повернення:** `const char*` із нульовим завершенням.
- **Приклад:** Для умови `post(r): r > 0 && r <= capacity()` метод повертає точний символьний запис `"r > 0 && r <= capacity()"`.

### 6. `kind()`
```cpp
[[nodiscard]] constexpr contract_kind kind() const noexcept;
```
- **Призначення:** Повідомляє про синтаксичну категорію контракту, що дозволяє обробнику розрізняти помилки на боці викликача, помилки в алгоритмі функції або порушення внутрішніх інваріантів.
- **Значення переліку:**
  - `std::contracts::contract_kind::pre` — преумова на вході у функцію;
  - `std::contracts::contract_kind::post` — постумова при виході з функції;
  - `std::contracts::contract_kind::assert` — твердження `contract_assert` усередині блоку коду.

### 7. `detection_mode()`
```cpp
[[nodiscard]] constexpr detection_mode detection_mode() const noexcept;
```
- **Призначення:** Ідентифікує причину, через яку умова вважається порушеною.
- **Значення переліку:**
  - `std::contracts::detection_mode::predicate_false` — вираз було обчислено без системних помилок, і він повернув логічний результат `false`;
  - `std::contracts::detection_mode::evaluation_exception` — під час обчислення коду предиката виник виняток C++, який не було перехоплено всередині самого виразу.

## Синтаксис специфікаторів контрактів у граматиці C++26

Контракти в C++26 є повноправними синтаксичними конструкціями ядра мови. Вони вбудовуються безпосередньо в декларатори функцій та послідовності інструкцій.

### 1. Преумови: специфікатор `pre`

Преумова формулює контрактні вимоги до аргументів функції та зовнішнього стану системи, які зобов'язаний забезпечити викликач.

```
pre-clause:
    pre : conditional-expression
    pre [ contract-label ] : conditional-expression
```

#### Правила розміщення та області видимості:
- Преумова записується після списку формальних параметрів і всіх кваліфікаторів сигнатури (`const`, `volatile`, посилання `&`/`&&`, специфікатор винятків `noexcept`).
- У виразі преумови дозволено звертатися до всіх іменованих параметрів функції.
- Для функцій-членів класу у виразі доступні всі поля, типи та методи класу (включно з `private` та `protected`), оскільки перевірка виконується в контексті класу через неявний покажчик `this`.
- Якщо функція оголошується з кількома преумовами, вони перевіряються послідовно в порядку їхнього фізичного декларування. Якщо будь-яка попередня умова повертає `false`, подальші преумови **не обчислюються**, що захищає від розіменування невалідних покажчиків у наступних перевірках:

```cpp
// Друга умова безпечна, бо перша гарантує валідність покажчика
void process_packet(const Header* hdr, std::size_t payload_len)
    noexcept
    pre [valid_pointer]: hdr != nullptr
    pre [valid_length]: hdr->length == payload_len;
```

---

### 2. Постумови: специфікатор `post`

Постумова формулює гарантії, які функція надає викликачеві в разі свого успішного завершення.

```
post-clause:
    post : conditional-expression
    post ( result-identifier ) : conditional-expression
    post [ contract-label ] : conditional-expression
    post [ contract-label ] ( result-identifier ) : conditional-expression
```

#### Правила роботи з результатом та параметрами:
- Ідентифікатор у круглих дужках `(result-identifier)` вводить нове ім'я в область видимості виразу постумови, яке прив'язується до константного посилання на обчислене значення функції.
- Для функцій, що повертають тип `void`, синтаксис із круглими дужками результату заборонений; використовується форма `post: cond`.
- Якщо функція завершує своє виконання генерацією винятку (stack unwinding), звичайні постумови `post` не викликаються.
- Якщо параметри функції були передані за значенням і модифіковані всередині тіла функції, у постумові вони обчислюються у своєму **фінальному стані** на момент завершення тіла. Для порівняння зі значенням на вході використовують збереження в локальні константи або майбутні розширення захоплення старих значень (`old`).

```cpp
int transfer_funds(Account& from, Account& to, int amount)
    pre: amount > 0 && from.balance() >= amount
    post(actual_transferred): actual_transferred == amount && from.balance() >= 0;
```

---

### 3. Твердження в коді: специфікатор `contract_assert`

Специфікатор `contract_assert` перевіряє довільні логічні інваріанти безпосередньо у внутрішніх точках виконання алгоритму.

```
contract-assert-statement:
    contract_assert : conditional-expression ;
    contract_assert [ contract-label ] : conditional-expression ;
```

- Використовується на рівні звичайних інструкцій мови всередині блоків `{ ... }`.
- На відміну від макроса `assert()`, `contract_assert` не є препроцесорною директивою, повністю підпорядковується правилам просторів імен, бере участь у шаблонах та інтегрується зі стандартизованим рантаймом обробки порушень.

```cpp
template <typename T>
void custom_sort(std::span<T> view) {
    // ... логіка сортування ...
    contract_assert [partition_valid]: std::is_partitioned(view.begin(), view.end(), [](const auto& x) {
        return x >= 0;
    });
}
```

## Контракти в лямбда-виразах та корутинах

Сучасний C++ широко використовує анонімні замикання (лямбди) та асинхронні корутини (Coroutines). Стандарт C++26 уніфікує застосування контрактів для цих мовних конструкцій.

### 1. Лямбда-вирази
Лямбда-вираз може мати власні преумови та постумови, які розміщуються після списку параметрів замикання:

```cpp
auto safe_divider = [](double a, double b)
    pre [non_zero_denom]: b != 0.0
    post(res): res * b == a
{
    return a / b;
};
```
У виразах контрактів лямбди доступні як параметри замикання, так і всі змінні, явно або неявно захоплені в `[captures]`.

### 2. Корутини (`co_await`, `co_yield`, `co_return`)
Для функцій-корутин діють чіткі межі оцінки:
- **Преумови (`pre`):** Обчислюються рівно один раз — у момент первинного виклику корутини до виділення фрейму корутини на купі (coroutine frame allocation) та створення об'єкта обіцянки (`promise_type`). Якщо преумова порушена, фрейм корутини взагалі не створюється.
- **Постумови (`post`):** Обчислюються в момент остаточного повернення результату через інструкцію `co_return`. Вирази постумови мають доступ до значення, переданого в `co_return`, але не викликаються під час проміжних призупинень потоку через `co_yield` або `co_await`.

## Контракти в константних виразах (`constexpr` та `consteval`)

Стандарт C++26 гарантує однакову поведінку контрактів як під час звичайного виконання в пам'яті процесу, так і під час інтерпретації коду компілятором на етапі компіляції (`constexpr` / `consteval` контекст).

### Правила компіляції константних виразів:
1. Якщо функція з контрактами викликається в константному контексті, предикати преумов та постумов обчислюються як невіддільна частина константного виразу.
2. Якщо контракт порушується під час константного обчислення:
   - Обробник порушень `handle_contract_violation` **не викликається** (оскільки він є функцією середовища виконання).
   - Порушення контракту трактується компілятором як помилка константного обчислення (вираз перестає бути `constant expression`).
   - Компілятор зупиняє збирання з діагностичним повідомленням про помилку компіляції, вказуючи вихідний рядок контракту, предикат та значення вхідних параметрів.
3. Режим `ignore` під час константного обчислення не перевіряє предикат, що дозволяє виконувати constexpr-функції без додаткових витрат часу трансляції.

```cpp
constexpr int compute_factorial(int n)
    pre: n >= 0 && n <= 12
    post(r): r >= 1
{
    int res = 1;
    for (int i = 2; i <= n; ++i) {
        res *= i;
    }
    return res;
}

// Успішна компіляція: преумова n >= 0 виконується
constexpr int f5 = compute_factorial(5);

// Помилка компіляції: порушення преумови pre: n >= 0 && n <= 12
// static_assert вимагає коректного константного виразу
constexpr int f_bad = compute_factorial(-3); // Помилка: -3 не в діапазоні [0, 12]
```

## Контракти у віртуальних функціях та спадкуванні

Успадкування класів із віртуальними функціями підпорядковується фундаментальному принципу підстановки Лісков (Liskov Substitution Principle, LSP): нащадок зобов'язаний бути придатним для використання скрізь, де очікується базовий клас.

### Семантичні правила для віртуальних контрактів:
1. **Перевизначення преумов (Contravariance):** Перевизначена функція-член у похідному класі не має права посилювати преумови базового класу (вимагати від клієнта більше). Вона може лише послаблювати їх або зберігати незмінними.
2. **Перевизначення постумов (Covariance):** Перевизначена функція-член не має права послаблювати постумови базового класу (гарантувати клієнту менше). Вона може лише посилювати свої гарантії або залишати їх ідентичними.
3. **Правило перенесення контрактів у C++26:** Якщо віртуальна функція перевизначається в похідному класі без повторного явного написання контрактів, вона автоматично успадковує преумови та постумови базової віртуальної функції. Якщо нащадок вказує додаткові контракти, середовище виконання комбінує перевірки відповідно до правил LSP (преумови через логічне «АБО», постумови через логічне «ТА»).

```cpp
class BaseStream {
public:
    virtual ~BaseStream() = default;

    virtual std::size_t read_bytes(std::span<std::byte> dst)
        pre [valid_buffer]: !dst.empty()
        post(bytes_read): bytes_read <= dst.size() = 0;
};

class NonBlockingStream : public BaseStream {
public:
    // Автоматично успадковує pre [valid_buffer] та post(bytes_read)
    // Може повертати 0 байтів, якщо даних ще немає, що цілком відповідає bytes_read <= dst.size()
    std::size_t read_bytes(std::span<std::byte> dst) override;
};
```

## Контракти та шаблони функцій

У шаблонах C++26 контракти інтегруються з механізмами виведення типів, концептами (Concepts) та метапрограмуванням.

### Взаємодія з концептами (`requires`):
- **Концепти (`requires`-вирази)** перевіряють синтаксичну валідність типів на етапі компіляції (чи має тип метод `.size()`, чи є тип копійованим).
- **Контракти (`pre` / `post`)** перевіряють семантичні значення даних під час виконання (чи є `.size() > 0`, чи не є покажчик нульовим).
- Концепти та контракти не конкурують, а доповнюють один одного: концепт відсікає некоректні типи на етапі інстанціювання шаблону, а контракт контролює коректність аргументів під час виклику.

```cpp
template <typename T>
    requires std::integral<T> // Концепт: перевірка типу під час компіляції
T fast_gcd(T a, T b)
    pre: a > 0 && b > 0     // Контракт: перевірка числових значень
    post(g): g > 0 && (a % g == 0) && (b % g == 0)
{
    while (b != 0) {
        T t = b;
        b = a % b;
        a = t;
    }
    return a;
}
```

## Бінарний інтерфейс (ABI) та міжмодульна сумісність

Важливою перевагою дизайну P2900 у C++26 є стабільність двійкового інтерфейсу (Application Binary Interface, ABI) при зміні семантик оцінки контрактів.

### 1. Розміщення коду перевірки преумов
Компілятори реалізують преумови через механізм **перевірки на стороні викликача (caller-side check)** або через **внутрішній пролог функції (callee-side prologue)**:
- Для звичайних функцій із зовнішнім зв'язуванням (external linkage) перевірка преумови вбудовується безпосередньо в початок тіла функції (callee-side), що гарантує виконання контракту навіть у разі динамічного виклику через вказівник на функцію або виклику з динамічної бібліотеки (`.so` / `.dll`).
- Для inline-функцій та шаблонів оптимізатор може переносити перевірку в точку виклику (caller-side) для усунення дублювання перевірок.

### 2. Незалежність сигнатури від семантики контрактів
Наявність контрактів або зміна режиму оцінки (`ignore` → `enforce`) **не змінює манглування імен** (name mangling) функції. Завдяки цьому бібліотека, скомпільована з режимом `enforce`, може безперешкодно лінкуватися з клієнтським кодом, зібраним у режимі `ignore`, і навпаки.

## Механізм обробки порушень: `handle_contract_violation`

Коли предикат контракту в режимах `observe` або `enforce` повертає `false` або породжує необроблений виняток, рантайм передає керування глобальній функції обробки.

### Заміна стандартного обробника (Custom Violation Handler)

Програма має право визначити власний глобальний обробник у глобальному просторі імен:

```cpp
void handle_contract_violation(const std::contracts::contract_violation& violation) noexcept;
```

### Залізні правила та гарантії безпеки обробника:
1. **Абсолютна вимога `noexcept`:** Функція `handle_contract_violation` зобов'язана мати специфікацію `noexcept`. Спроба викинути виняток зсередини обробника негайно активує `std::terminate()`.
2. **Захист від нескінченної рекурсії:** Якщо код всередині самого обробника порушить інший контракт або викличе функцію з порушеною преумовою, система виконання виявляє повторний рекурсивний вхід і миттєво аварійно зупиняє процес без повторного виклику обробника.
3. **Семантика повернення:**
   - Якщо контракт працював у режимі `observe`: завершення функції обробника повертає керування в точку виклику, дозволяючи програмі продовжити виконання (ідеально для збору статистики помилок у тестовому середовищі).
   - Якщо контракт працював у режимі `enforce`: після повернення керування з обробника система виконання негайно і безумовно викликає `std::terminate()`.

### Зразок реалізації надійного обробника з телеметрією:

```cpp
#include <contracts>
#include <cstdio>
#include <cstdlib>

void handle_contract_violation(const std::contracts::contract_violation& v) noexcept {
    static thread_local bool in_violation_handler = false;
    if (in_violation_handler) {
        // Запобігання повторному входу у разі рекурсивного збою
        return;
    }
    in_violation_handler = true;

    const char* kind_str = "невідомий";
    switch (v.kind()) {
        case std::contracts::contract_kind::pre:    kind_str = "преумова (pre)"; break;
        case std::contracts::contract_kind::post:   kind_str = "постумова (post)"; break;
        case std::contracts::contract_kind::assert: kind_str = "твердження (assert)"; break;
    }

    const char* mode_str = (v.detection_mode() == std::contracts::detection_mode::predicate_false)
        ? "предикат хибний"
        : "виник виняток під час оцінки";

    std::fprintf(stderr,
        "[CRITICAL CONTRACT VIOLATION]\n"
        "  Файл:        %s:%u\n"
        "  Функція:     %s\n"
        "  Тип:         %s\n"
        "  Мітка:       %s\n"
        "  Предикат:    %s\n"
        "  Причина:     %s\n",
        v.file_name(),
        static_cast<unsigned int>(v.line_number()),
        v.function_name(),
        kind_str,
        v.comment()[0] != '\0' ? v.comment() : "<немає>",
        v.predicate(),
        mode_str
    );

    in_violation_handler = false;
}
```

## Режими оцінки та керування компілятором

Стандарт C++26 визначає три фундаментальні семантики оцінки контрактів, які призначаються на етапі збирання проєкту:

1. **`ignore` (ігнорування):**
   - Умови контрактів не генерують жодних інструкцій у машинному коді.
   - Нульовий накладний вплив на розмір бінарного образу та швидкість виконання.
   - **Захист від UB:** Компілятору **заборонено** припускати, що невиконаний предикат у режимі `ignore` є істинним, якщо це не дозволено окремим прапорцем агресивних аксіом.

2. **`observe` (спостереження):**
   - Предикати обчислюються під час виконання.
   - При порушенні викликається `handle_contract_violation`, після чого потік виконання продовжується далі.
   - Використовується для тестування, моніторингу та пошуку дефектів на живих тестових стендах без зупинки процесу.

3. **`enforce` (примусове дотримання):**
   - Предикати обчислюються під час виконання.
   - При порушенні викликається `handle_contract_violation`, після чого рантайм викликає `std::terminate()`.
   - Застосовується в критичних до надійності системах для запобігання поширенню пошкодженого стану.

### Прапорці командного рядка компіляторів

#### GCC / G++ (експериментальна підтримка C++26):
- `-fcontracts` — увімкнення розпізнавання контрактів;
- `-fcontract-semantic=enforce` — глобальний вибір семантики `enforce`;
- `-fcontract-semantic=observe` — глобальний вибір семантики `observe`;
- `-fcontract-semantic=ignore` — глобальне відключення перевірок;
- `-fcontract-build-level=audit` — увімкнення обчислювально важких аудит-контрактів.

#### Clang:
- `-fcontracts` — активує синтаксичний аналізатор контрактів;
- `-fcontract-evaluation-semantic=enforce`
- `-fcontract-evaluation-semantic=observe`
- `-fcontract-evaluation-semantic=ignore`

#### MSVC (Visual C++):
- `/std:c++latest` — підтримка стандарту C++26;
- `/contracts:semantic=enforce`
- `/contracts:semantic=observe`
- `/contracts:semantic=ignore`
