## Чому покажчика виявилося замало

У C, щоб функція працювала з чужим об'єктом і не копіювала його, є рівно один прийом: передати адресу. Прийом працює, але залишає слід у кожному рядку, який цю адресу вживає. Автор C++ Б'ярне Страуструп ілюструє це двома функціями, які роблять одне й те саме:

```cpp
void f1(const complex* x, const complex* y)   // без посилань
{
    complex z = *x + *y;                      // потворно
}

void f2(const complex& x, const complex& y)   // з посиланнями
{
    complex z = x + y;                        // краще
}
```

Зірочка перед кожним операндом — не просто негарно. Вона робить неможливим те, заради чого перевантаження операторів узагалі затівалося. Оператор `+` для комплексних чисел мусить приймати щось, що пишеться як `x`, а не як `*x`, — інакше вираз `a = b - c` доведеться писати як `a = *(operator-(&b, &c))`, і вся ідея «свій тип виглядає як вбудований» помирає. Сам Страуструп формулює прямо: пряма причина, з якої посилання потрапили в мову, — підтримати перевантаження операторів. [Як саме посилання з'явилися в C++ і як через двадцять років до них додали rvalue-різновид](book:cpp-standards/references-binding/hist-references-birth.md) — окрема історія з паперами комітету й одним виправленням, яке врятувало мову від тихого крадіжництва.

Але річ не лише в косметиці. Покажчик — сам по собі об'єкт: у нього є власна адреса, його можна перепризначити, зсунути арифметикою, зробити нульовим. Для аргументу оператора кожна з цих можливостей — зайва свобода, за яку хтось заплатить. Потрібне було щось інше: **друге ім'я для об'єкта, який уже існує деінде**. Не новий об'єкт, не адреса, яку можна крутити, — саме ім'я.

## Зв'язування — єдина мить, коли посилання щось вирішує

Ось воно:

```cpp
int  x = 7;
int& r = x;      // ← зв'язування
```

Другий рядок — не присвоєння і не копіювання. Це **зв'язування** (англ. *binding*): відтепер і назавжди `r` означає той самий об'єкт, що й `x`. Не «показує на нього», а *є* ним під іншим іменем. Тому `r = 9` записує дев'ятку в `x`, `++r` збільшує `x`, а `&r` дає ту саму адресу, що й `&x`. Синтаксису, який перенацілив би `r` на інший об'єкт, у мові просто немає — будь-яке подальше `r = щось` це присвоєння **в** `x`.

З цього єдиного факту випливає решта. Посилання **мусить** бути ініціалізоване: `int& r;` — помилка компіляції, бо оголосити друге ім'я, не сказавши чого воно ім'я, безглуздо. (Винятки — параметр функції, який зв'яжеться при виклику, і `extern`-оголошення, де ініціалізатор стоїть в іншій одиниці трансляції.) Нульового посилання не буває: `int& r = *p;` при `p == nullptr` — це вже невизначена поведінка, а не «посилання, що ні на що не вказує».

Далі: **посилання не є об'єктом**. Стандарт не вимагає для нього ані байта пам'яті. Тому не існує масиву посилань, покажчика на посилання й посилання на посилання, записаного прямо в коді, а `sizeof(int&)` дорівнює `sizeof(int)` — питання «скільки важить саме посилання» стандарт не має чим відповісти.

![Ліворуч одна комірка з двома іменами x і r; праворуч дві комірки, друга містить адресу першої](/reference/cpp-standards/language/references-binding/img/alias-vs-pointer.svg)

*Посилання — це друге ім'я вже наявної комірки: власної адреси в нього немає. Покажчик — самостійна комірка, що зберігає адресу іншої, і саме тому його можна перенацілити або занулити.*

На практиці компілятор часто взагалі нічого не генерує для локального посилання на локальний об'єкт — після оптимізації від `r` не лишається сліду, всі звертання йдуть прямо до `x`. Коли ж посилання перетинає межу функції, компілятор передає адресу — рівно те, що передав би покажчик. Це і є звичайна відповідь на питання «скільки коштує `const T&`»: у машинному коді — стільки ж, скільки покажчик, ні на такт більше.

> 🔧 **Навіщо це.** З цього випливає перше правило гігієни інтерфейсів: параметр-посилання не безкоштовний для маленьких типів. Передати `int` за значенням — це одне число в регістрі; передати `const int&` — це адреса в регістрі плюс читання з пам'яті на кожне звертання, і компілятор часто не має права цього прибрати, бо не знає, чи не змінить об'єкт хтось інший. Тому `const T&` беруть для типів, дорожчих за пару машинних слів, а не «на всяк випадок».

## До чого можна прив'язатися: три роди посилань

Компілятор перевіряє зв'язування за одним питанням: **що це за вираз праворуч** — наявний іменований об'єкт чи щось безіменне й тимчасове. Кожен рід посилань відповідає на це питання по-своєму, і в кожної відповіді є причина.

**`T&` — змінне lvalue-посилання.** Прив'язується лише до змінного lvalue того самого типу (або до об'єкта похідного класу). До тимчасового — ні:

```cpp
void grow(std::string& s);

std::string name = "Ада";
grow(name);            // добре
grow(name + "!");      // помилка компіляції
```

Заборона не примхлива. `grow` існує, щоб **змінити** переданий об'єкт; результат `name + "!"` — тимчасовий рядок, який зникне наприкінці цього ж виразу. Робота, яку `grow` над ним зробить, згине разом із ним, а той, хто писав виклик, майже напевно мав на увазі щось інше. Мова відмовляє замість того, щоб мовчки виконати безглуздя. (Компілятор Microsoft історично дозволяв таке зв'язування як власне розширення; вимикається прапорцем `/Zc:referenceBinding`, і код, що на нього спирався, не збирається більше ніде.)

**`const T&` — універсальний читач.** Прив'язується практично до всього: до змінного lvalue, до `const`-lvalue, до тимчасового. Причина знову проста: ми пообіцяли не писати. Якщо об'єкт помре відразу після виразу — нам байдуже, ми його лише прочитали; а якщо ми захочемо потримати посилання довше, мова спеціально подовжить життя тимчасовому (про це нижче). Саме звідси всюдисущість `const T&` у сигнатурах: це єдиний вид параметра, що приймає геть усе й нічого не копіює.

**`T&&` — rvalue-посилання.** Прив'язується лише до rvalue: до безіменного тимчасового або до того, що явно позначили як «більше не потрібне». Це не «посилання на посилання» й не «посилання швидше» — це **інший канал перевантаження**, який говорить: об'єкт нікому далі не знадобиться, можна забрати з нього нутрощі. До іменованої змінної воно не прив'яжеться:

```cpp
std::string name = "Ада";
std::string&& a = name;              // помилка: name — це lvalue
std::string&& b = name + "!";        // добре: тимчасовий
std::string&& c = std::move(name);   // добре: явний дозвіл
```

Тут варто зупинитися на `std::move`, бо назва обманює: він **нічого не переміщує**. Це приведення типу, яке з lvalue робить xvalue, тобто рівно та дія, що дозволяє зв'язатися з `T&&`. Переміщення (якщо воно взагалі станеться) виконає той, хто потім вибере перевантаження з `T&&`, — [конструктор чи оператор переміщення](book:cpp-standards/move-semantics).

**`const T&&`** теж існує й теж законний, хоч на перший погляд позбавлений сенсу: прив'язатися можна, а забрати нутрощі — ні, бо `const`. Його справжня роль — заборонна. Стандартна бібліотека оголошує такі перевантаження видаленими, щоб відрізати небезпечний виклик: `template <class T> void ref(const T&&) = delete;` у `std::ref` не дає загорнути тимчасовий у посилання-обгортку, яка його переживе. Так само влаштований `std::as_const`.

![Таблиця: рядки — рід ініціалізатора, стовпці — рід посилання, у клітинках галочки й хрестики](/reference/cpp-standards/language/references-binding/img/binding-matrix.svg)

*Уся механіка зв'язування вміщається в одну решітку. Змінне lvalue-посилання найвибагливіше, `const T&` приймає все, `T&&` — тільки безіменне. Стовпець `const T&&` порожній не тому, що зв'язування рідкісне, а тому, що така сигнатура майже завжди пишеться, щоб бути видаленою.*

Прочитати решітку варто в один бік: **чим більше посилання обіцяє не чіпати об'єкт, тим до ширшого кола об'єктів воно допускається**. `T&` збирається писати — його пускають лише до того, що має ім'я й не `const`. `T&&` збирається обібрати — його пускають лише до того, чого нікому не шкода. `const T&` не збирається робити нічого — його пускають усюди.

## Коли типи не збігаються: тихо народжений тимчасовий

Досі ми мовчки припускали, що тип посилання і тип ініціалізатора однакові. Коли ні — компілятор не здається одразу. Якщо з ініціалізатора можна зробити об'єкт потрібного типу, він **матеріалізує тимчасовий** (створює безіменну копію потрібного типу) і прив'язує посилання до неї. Для `const T&` і `T&&` це дозволено; для `T&` — ні, і саме тому `T&` тут просто відмовляє.

```cpp
int         n = 5;
const long& r = n;   // компілюється: створено тимчасовий long зі значенням 5
n = 100;
// r досі 5 — це посилання на копію, а не на n
```

Виглядає як дрібниця, доки та сама механіка не спрацьовує там, де очікуєш нульову ціну:

```cpp
std::map<std::string, int> counts;

for (const std::pair<std::string, int>& kv : counts)   // копія на кожній ітерації!
    use(kv);
```

Тип елемента `std::map` — `std::pair<const std::string, int>`, а не `std::pair<std::string, int>`. Типи різні, посилання `const&`, отже компілятор чесно робить те, що йому дозволено: на кожній ітерації конструює тимчасову пару, копіюючи рядок разом із виділенням пам'яті, прив'язує до неї `kv` і наприкінці ітерації знищує. Жодного попередження: код правильний, просто в рази повільніший, ніж здається з тексту. Ліки — `const auto&`, який виведе точний тип елемента й нічого не скопіює.

Те саме пастка ловить у сигнатурах: `void log(const std::string& msg)`, викликаний як `log("готово")`, будує тимчасовий `std::string` із виділенням пам'яті на купі — щоб функція, яка лише читає символи, могла взяти параметр за посиланням. Саме для цього випадку існує [`std::string_view`](book:cpp-standards/string-and-string-view), який приймає і літерал, і `std::string`, не створюючи нічого.

> 🔧 **Навіщо це.** Матеріалізація тимчасового — головне джерело копій, яких немає в тексті програми. Профайлер покаже час у конструкторі копіювання, а рядок, який його спричинив, виглядатиме як звичайна передача за посиланням. Практичне правило: якщо в циклі або в гарячій функції стоїть `const T&` з явно виписаним `T`, звірте `T` із фактичним типом виразу; розбіжність у `const`, у знаковості чи в аргументі шаблону коштує копію на кожен прохід.

## Продовження життя тимчасового — і чотири місця, де воно не діє

Тимчасовий об'єкт за звичайним правилом знищується наприкінці **повного виразу** — того, що закінчується крапкою з комою. Якби правило працювало без винятків, `const T&` був би марним поза параметрами:

```cpp
const Matrix& m = compute();   // тимчасовий помер би тут же
use(m);                        // ...і це вже було б UB
```

Тому мова робить виняток: **тимчасовий, прив'язаний прямо до посилання, живе стільки, скільки живе саме посилання**. Для `const Matrix& m` вище це означає до кінця блоку. Те саме працює для `Matrix&& m = compute();`. Подовження стосується цілого об'єкта, а не шматка: у `const int& n = makePoint().x;` живою лишається вся точка, бо `n` дивиться в її поле.

Але виняток вузький, і всі місця, де він **не** діє, стандарт перелічує поіменно. Вони й дають найпоширеніші висячі посилання:

**Повернення з функції.** Тимчасовий помирає наприкінці виразу в `return`, і посилання повертається вже мертвим:

```cpp
const std::string& bad() {
    return std::string("ой");   // тимчасовий гине тут
}
```

**Параметр функції.** Тимчасовий, прив'язаний до параметра-посилання, живе до кінця повного виразу з викликом — не довше. Тому зберегти цей параметр у полі об'єкта означає покласти в поле посилання, яке протухне на наступному рядку.

**Ініціалізатор у `new`.** Якщо створюваний об'єкт має поле-посилання, тимчасовий, прив'язаний до нього, гине наприкінці повного виразу з `new`, тоді як сам об'єкт живе далі в купі.

**Список ініціалізації конструктора.** Тимчасовий, прив'язаний до поля-посилання, живе до кінця конструктора. Об'єкт щойно збудовано — а його поле вже висить.

До цього додається два наслідки, які варто пам'ятати окремо. Подовження **не транзитивне**: якщо посилання вже дивиться на тимчасовий, прив'язка до нього ще одного `const&` нічого не продовжує — саме це показує друга смуга на схемі. І подовження **розривається розіменуванням**: `const int& r = *make().ptr;` не подовжує нічого, бо посилання зв'язується не з тимчасовим, а з тим, куди дивився його покажчик.

![Дві часові смуги: у першій тимчасовий живий до кінця блоку, у другій зелена ділянка обривається на крапці з комою й далі йде червона](/reference/cpp-standards/language/references-binding/img/lifetime-extension.svg)

*Пряме зв'язування з тимчасовим подовжує його життя до життя посилання. Щойно між тимчасовим і посиланням з'являється посередник — виклик функції, повернення, розіменування — правило вимикається, і посилання переживає об'єкт.*

Один давній випадок цієї пастки виправили лише в C++23. Цикл `for (auto x : getVector().items())` до того працював так: тимчасовий вектор, породжений `getVector()`, гинув до першої ітерації, і цикл обходив уламки. Папір P2718R0, ухвалений на листопадовій зустрічі комітету 2022 року, продовжив життя **всім** тимчасовим із діапазонного виразу на весь цикл. Компілятори підтягнулися пізніше, тому в коді, що має збиратися старішим стандартом, безпечніше й досі спершу зберегти діапазон в іменованій змінній.

## Згортання посилань

Написати `int& &` у коді не можна. Але компілятор може дійти до такої конструкції сам — через параметр шаблону, `typedef`, `using` чи `decltype`, — і тоді діє правило **згортання** (англ. *reference collapsing*):

```
T&  &   → T&
T&  &&  → T&
T&& &   → T&
T&& &&  → T&&
```

Правило легко запам'ятати одним реченням: **lvalue перемагає**. Лише коли обидві половини rvalue-посилання, результат лишається rvalue-посиланням.

Вибір саме такий тому, що lvalue-посилання — обережніша заява. `T&` каже «об'єкт існує й має ім'я», `T&&` каже «об'єкт нічий, беріть». Якщо хоча б одна половина стверджує перше, підсумок не має права стверджувати друге: інакше з іменованої змінної можна було б забрати нутрощі, ні про що не спитавши.

```cpp
using Lref = int&;
using Rref = int&&;

int n = 1;
Lref&& a = n;             // int&  — прив'язується до змінної
Rref&& b = std::move(n);  // int&& — лишається rvalue-посиланням
```

У парі з правилом виведення типу для `T&&` у шаблоні (коли аргумент — lvalue типу `U`, параметр `T` виводиться як `U&`) згортання дає конструкцію, що приймає й lvalue, й rvalue, зберігаючи їхню категорію, — [універсальне посилання й ідеальне передавання](book:cpp-standards/perfect-forwarding).

## Зв'язування вирішує, яке перевантаження виграє

Правила зв'язування працюють не тільки як заборона. Вони ж визначають, **яку з кількох функцій обере компілятор**. Спершу відсіюються ті, чиї параметри взагалі не можуть зв'язатися з аргументом, а серед решти виграє те зв'язування, яке ближче до точного збігу.

```cpp
void take(const std::string&);   // 1
void take(std::string&&);        // 2

std::string name = "Ада";
const std::string frozen = "Грейс";

take(name);                  // 1 — 2 не бере lvalue
take(frozen);                // 1 — 2 не бере lvalue
take(std::string("тимч"));   // 2 — обидві підходять, rvalue краще лягає на T&&
take(std::move(name));       // 2
```

Третій рядок — найцікавіший: тимчасовий може зв'язатися і з `const std::string&`, і з `std::string&&`, тобто кандидати обидва. Стандарт розв'язує нічию окремим правилом: коли аргумент — rvalue, зв'язування з rvalue-посиланням вважається кращим. Саме на цьому тримається вся семантика переміщення: щойно ви дописали перевантаження з `T&&`, тимчасові автоматично поїхали в нього, а іменовані змінні лишилися в `const T&`.

Тепер два наслідки, на яких спотикаються найчастіше. Перший: **не змішуйте передачу за значенням і за посиланням для того самого параметра**.

```cpp
void put(std::string);          // 3
void put(const std::string&);   // 1

put(name);   // помилка: неоднозначність
```

Для компілятора ініціалізація параметра-значення копією і зв'язування `const&` мають однаковий ранг — обидві «точний збіг». Розв'язати нічию нема чим, і виклик відхиляється.

Другий: **точність зв'язування важить більше за спорідненість класів**.

```cpp
struct Base {};
struct Derived : Base {};

void h(Base&);
void h(Derived&);

Derived d;
h(d);        // → h(Derived&)
```

Зв'язати `Derived&` з `d` — це тотожність, найвищий ранг. Зв'язати `Base&` з `d` — перетворення до бази, ранг нижчий. Так само `const`: додавання `const` при зв'язуванні трохи гірше за точний збіг, тому за наявності обох `h(Derived&)` і `h(const Derived&)` змінний аргумент піде в перший. Ці ранги — частина загального механізму [вибору перевантаження](book:programming/function-overloading), у якому зв'язування посилань складає лише один, хоч і найчастіший, крок.

Побачити всі ці правила в дії за один прогін допомагає [маленька лабораторія: програма, що друкує, яке саме перевантаження спрацювало й коли живе тимчасовий](book:cpp-standards/references-binding/proj-binding-lab.md) — з передбачуваними висновками там, де інтуїція підводить.

## Посилання на базовий клас: чому немає зрізання

Спорідненість класів дає зв'язуванню ще одну властивість, заради якої посилання й пробралися в кожну поліморфну сигнатуру. Порівняйте два рядки:

```cpp
void byValue(Base b);
void byRef(const Base& b);

Derived d;
byValue(d);   // скопійовано ЛИШЕ підоб'єкт Base — «зрізання»
byRef(d);     // b зв'язано з тим самим об'єктом d
```

У першому випадку конструктор копіювання `Base` бере з `d` тільки ту частину, яку розуміє, і будує з неї повноцінний окремий `Base`. Динамічний тип нового об'єкта — саме `Base`, тому віртуальні виклики підуть у базові реалізації, а поля похідного класу просто зникнуть. Це і є **зрізання об'єкта** (англ. *object slicing*), і воно тихе: код компілюється, програма працює, просто робить не те.

У другому випадку нічого не копіюється. `b` — друге ім'я того самого `d`, його динамічний тип лишився `Derived`, і виклик `b.virtualMethod()` піде в реалізацію `Derived`. Ось чому в C++ поліморфізм існує тільки через посилання й покажчики: параметр за значенням фізично не може зберегти похідну частину, бо його розмір відомий компіляторові наперед.

Це працює і з тимчасовими: у `const Base& b = makeDerived();` подовження життя стосується **цілого** об'єкта, тобто повного `Derived`, а не зрізаної бази, — і віртуальний виклик крізь `b` знайде похідну реалізацію.

## Ціна: посилання нічого не обіцяє про час життя

Тепер варто назвати те, чого правила зв'язування **не** роблять. Вони перевіряють, **що** з чим можна зв'язати, і жодного разу — **як довго** зв'язок лишатиметься правдою. Посилання стверджує рівно одне: «тут є об'єкт». Хто гарантує, що він переживе посилання, стандарт не питає й компілятор не перевіряє.

Звідси весь клас помилок, у якому синтаксично бездоганний код читає звільнену пам'ять:

```cpp
std::string_view sv = makeName();   // тимчасовий рядок гине наприкінці рядка
use(sv);                            // UB: sv дивиться в звільнений буфер
```

`string_view` — не посилання, тому правило подовження на нього не поширюється: воно рятує лише справжні посилання. Так само висять посилання, збережені в полі об'єкта, захоплені лямбдою за `&` й пережиті кадром стека, або повернені з функції на локальний об'єкт. Механіка кожного випадку та сама й розібрана окремо — [висячі посилання й звертання після звільнення](book:cpp-standards/dangling-references).

> 🔧 **Навіщо це.** Оскільки компілятор мовчить, домовленість про час життя мусить бути в сигнатурі, і читати її треба буквально. `const T&` у параметрі означає «я подивлюся й забуду до кінця виклику»; якщо функція насправді зберігає аргумент, її параметр має бути `T` за значенням, `std::shared_ptr<T>` або хоча б `T*` — тип, який своїм виглядом попереджає виклик. Цю відповідність типу параметра й наміру розібрано в темі [володіння в сигнатурі](book:cpp-standards/ownership-semantics); тут важливо інше: тип параметра — єдине місце, де намір узагалі можна записати.

## Посилання-член і посилання, яке можна перекласти

Поле-посилання виглядає природно, поки не спробуєш ним скористатися:

```cpp
struct View {
    const Table& t_;
    explicit View(const Table& t) : t_(t) {}   // лише через список ініціалізації
};
```

Оскільки перезв'язати посилання неможливо, компілятор не може згенерувати оператор присвоєння — він і не генерує, а видаляє. Клас із таким полем не присвоюється, а отже, не сортується у векторі, не перезаписується в мапі, не бере участі в половині алгоритмів. Плюс сам об'єкт відповідає за те, щоб `t_` не пережив таблиці, — а нагадати про це нема кому.

Коли треба саме «посилання, але як значення», є `std::reference_wrapper<T>`: усередині — покажчик, зовні — неявне перетворення в `T&`. Його можна копіювати, присвоювати й класти в контейнери:

```cpp
std::vector<std::reference_wrapper<Sensor>> active;
active.push_back(std::ref(temperature));
active[0].get().reset();
```

Другий, менш очевидний привід — функції, які **копіюють** свої аргументи, хоч сигнатура цього не показує: `std::thread`, `std::bind`, `std::make_tuple` роблять із аргументів незалежні копії. Щоб передати туди саме зв'язок, а не копію, аргумент загортають:

```cpp
std::thread worker(collect, std::ref(counter));   // без ref потік дістав би копію
```

І тут спрацьовує та сама заборонна роль `const T&&`, з якої почалася розмова про роди посилань: `std::ref` має видалене перевантаження для `const T&&`, тож обгорнути тимчасовий не вдасться. Обгортка пережила б його — і мова відрубує цю можливість на етапі компіляції.

## Зв'язування самого об'єкта виклику

Останнє місце, куди дотягнулися ті самі правила, — неявний аргумент методу. Метод можна позначити `&` або `&&` після списку параметрів, і це вимога до того, **як зв'язується сам об'єкт**, на якому метод викликають:

```cpp
class Buffer {
    std::vector<char> data_;
public:
    const std::vector<char>& data() const&  { return data_; }              // об'єкт має ім'я
    std::vector<char>        data() &&      { return std::move(data_); }   // об'єкт тимчасовий
};

Buffer b;
auto& live = b.data();          // перший: посилання всередину живого b
auto  taken = makeBuffer().data();   // другий: вміст забрано з тимчасового
```

Без другого перевантаження рядок `makeBuffer().data()` повернув би посилання всередину об'єкта, що гине тієї ж миті, — класичне висяче посилання, породжене цілком безневинним викликом. Ref-кваліфікатор дає єдиний спосіб це помітити на етапі компіляції й повернути з тимчасового значення замість посилання. Тим самим прийомом закривають ще одну прикрість — присвоєння тимчасовому: `operator=`, позначений `&`, робить вираз `getVector() = other;` помилкою, хоча для вбудованих типів мова відкидає його й без жодних оголошень.

Посилання виявилося найдешевшою конструкцією C++ і водночас найвимогливішою: у машинному коді воно не коштує нічого й не гарантує нічого. Правила зв'язування — це вся та частка контракту, яку компілятор здатний узяти на себе: відмовити змінному посиланню в тимчасовому, подовжити тимчасовому життя під `const&`, згорнути `&& &` у `&`, віддати rvalue тому перевантаженню, що готове його розібрати. Кожне з них зроблено так, щоб типовий безпечний випадок писався сам собою, а небезпечний вимагав окремого слова — `std::move`, `std::ref`, `&&`-кваліфікатора. Там, де правила закінчуються — у збереженому полі, у захопленні лямбди, у поверненому посиланні, — залишається тільки домовленість, записана типом параметра; і читає її людина, не компілятор.
