# 📋 Довідник операторів приведення: правила, вартість та обмеження

Цей технічний довідник містить повну специфікацію механізмів приведення типів у C++, включаючи контракти компілятора, часову вартість виконання, правила збереження розкладки пам'яті, інваріанти безпеки, стандарти ISO C++ та формальний п'ятиступеневий алгоритм розгортання застарілого C-style cast.

## Зведена таблиця характеристик операторів

У таблиці нижче наведено порівняння чотирьох іменованих операторів C++, сучасного `std::bit_cast` та C-style cast:

| Оператор | Стандарт ISO C++ | Перевірка | Вартість у runtime | Допустимі операнди | Поведінка при помилці | Головний ризик UB |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `static_cast<T>(v)` | [expr.static.cast] | Compile-time | 0 тактів (компіляторний зсув адреси) | Числа, споріднені класи, `void*`, explicit ctor/op, rvalue | Помилка компіляції | Некоректний unchecked downcast |
| `dynamic_cast<T>(v)` | [expr.dynamic.cast] | Run-time (RTTI) | O(h) до O(N) операцій (обхід vtable/дерева) | Поліморфні класи (з хоча б однією virtual-функцією) | `nullptr` (для вказівників) або `std::bad_cast` (для посилань) | Відсутній (захищений дизайном) |
| `const_cast<T>(v)` | [expr.const.cast] | Compile-time | 0 тактів (лише кваліфікатор типу) | Вказівники та посилання однакового базового типу | Помилка компіляції | Модифікація справжнього `const`-об'єкта у `.rodata` |
| `reinterpret_cast<T>(v)` | [expr.reinterpret.cast] | Compile-time | 0 тактів (чисте копіювання бітів) | Вказівники, посилання, цілі числа `uintptr_t` | Помилка компіляції | Порушення Strict Aliasing Rule, втрата зсуву адреси |
| `std::bit_cast<To>(v)` | [bit.cast] (C++20) | Compile-time (`constexpr`) | 0 тактів (регістровий move / memcpy) | Trivially copyable типи однакового `sizeof` | Помилка компіляції | Порушення інваріантів цільового типу (trap representations) |
| `(T)v` (C-style cast) | [expr.cast] | Змішана | 0 тактів (або аварія в runtime) | Будь-які типи (перебирає 5 спроб за пріоритетом) | Помилка компіляції (лише якщо всі 5 спроб не підійшли) | Приховане побітове переосмислення при рефакторингу |

## 1. `static_cast<Target>(expression)`

Оператор `static_cast` виконує явні, добре визначені та повністю статичні перетворення, які мають зворотний семантичний зміст або відомі компілятору на етапі аналізу вихідного коду. Він регулюється пунктом стандарту ISO C++ [expr.static.cast].

### Дозволені категорії перетворень

1. **Числові конверсії (Numeric Conversions):**
   - **Звуження та розширення цілих чисел:** перетворення між типами різної розрядності (`int` ↔ `long long`, `int` ↔ `int8_t`). При звуженні старші байти відкидаються за правилами модульної арифметики (для unsigned) або реалізації (для signed).
   - **Конверсії з рухомою комою:** приведення між `float`, `double` та `long double`.
   - **Перетворення між цілими та дійсними числами:** дробова частина відкидається (truncation toward zero). Якщо значення виходить за межі діапазону цілого типу, поведінка є невизначеною.
   - **Зміна знаковості:** перетворення між `signed` та `unsigned` однакового розміру.

2. **Перетворення користувацьких типів (Ініціалізація):**
   - Вираз `static_cast<Target>(expr)` семантично еквівалентний прямій ініціалізації тимчасового об'єкта: `Target temp(expr);`.
   - Викликає конструктори з одним аргументом, включаючи ті, що оголошені з ключовим словом `explicit`.
   - Викликає явні та неявні оператори перетворення типу: `operator Target() const`.

3. **Переліки (Enumerations):**
   - Перетворення значення `enum class` у базовий цілий тип (`underlying_type`) і навпаки.
   - Перетворення цілого числа у звичайний `enum` або `enum class`. Якщо число виходить за діапазон допустимих значень переліку, результат є коректним, якщо вміщується в мінімальну бітову маску, здатну представити всі елементи переліку.

4. **Ієрархії спадкування (Static Class Navigation):**
   - **Upcast (вгору по ієрархії):** перетворення `Derived*` → `Base*` або `Derived&` → `Base&`. Повністю безпечне приведення, що виконує корекцію адреси на етапі компіляції.
   - **Unchecked Downcast (вниз по ієрархії):** перетворення `Base*` → `Derived*` або `Base&` → `Derived&`. Компілятор статично обчислює зсув підоб'єкта і віднімає його від базової адреси. **Перевірка фактичного типу під час виконання не здійснюється.** Якщо об'єкт насправді не є екземпляром `Derived`, виникає невизначена поведінка (UB) при першому зверненні до специфічних полів чи методів.
   - **Заборона віртуальних баз:** `static_cast` не може виконати downcast від віртуального базового класу (`virtual base class`), оскільки зміщення віртуальної бази визначається лише в runtime через таблицю віртуальних зсувів (vbtable). Для таких випадків обов'язковим є `dynamic_cast`.

5. **Зворотні перетворення через `void*` (Void Pointer Round-trip):**
   - Вказівник на будь-який тип об'єкта `T*` може бути неявно або через `static_cast` приведений до `void*` (збереження адреси).
   - Вказівник `void*` може бути приведений назад до `T*` лише через `static_cast<T*>`.
   - **Гарантія стандарту:** якщо вказівник `void*` приводиться точно до того самого типу `T*`, з якого він був отриманий, отриманий вказівник повністю валідний і дорівнює вихідному.

6. **Категорії значень (Value Categories & Move Semantics):**
   - Перетворення `lvalue` у `rvalue` (зокрема `xvalue`): `static_cast<T&&>(var)`.
   - Це фундаментальний механізм роботи `std::move`: він не генерує апаратного коду, а лише змінює категорію значення для перевантаження функцій.

7. **Приведення вказівників на члени класів (Pointers to Members):**
   - `static_cast` підтримує інвертовану навігацію вказівників на члени класу: перетворення вказівника на член базового класу `MemberType Base::*` у вказівник на член похідного класу `MemberType Derived::*`.
   - **Інверсія напрямку:** якщо `Derived` успадковує `Base`, то будь-який член `Base` гарантовано існує всередині `Derived`. Тому приведення `Base::*` → `Derived::*` є безпечним і дозволеним у `static_cast`.
   - Зворотне перетворення `Derived::*` → `Base::*` заборонене на етапі компіляції, оскільки член класу `Derived` може бути відсутній у базовому класі `Base`.

8. **Роздільна здатність операторів приведення та явних конструкторів:**
   - Якщо клас визначає як конструктор перетворення `explicit T(U)`, так і оператор перетворення `explicit operator T() const`, вираз `static_cast<T>(u)` ініціює повну процедуру перевантаження за правилами прямої ініціалізації ([over.match.copy]).
   - Компілятор розглядає обидва кандидати та видає помилку неоднозначності (ambiguity error), якщо обидва шляхи перетворення мають однаковий ранг у системі типів.

## 2. `const_cast<Target>(expression)`

Оператор `const_cast` призначений виключно для маніпуляції кваліфікаторами `const` та `volatile` (cv-кваліфікатори). Він регулюється пунктом стандарту ISO C++ [expr.const.cast].

### Сигнатура та правила валідації

- Цільовий тип `Target` і вихідний тип виразу `expression` повинні посилатися на **ідентичний базовий тип**.
- Дозволяє додавати або знімати `const`, `volatile` або обидва кваліфікатори одночасно.
- Застосовується виключно до вказівників, посилань або вказівників на члени класу (`pointer-to-member`).
- Не може змінювати розрядність, знаковість або структуру типу (наприклад, не можна одночасно зняти `const` і перетворити `int*` на `double*`).

### Багаторівневі покажчики (Multi-level Pointers)

При роботі з вказівниками на вказівники (`T**`) зняття константності вимагає суворого дотримання правил кваліфікації. Наприклад:
- Приведення `const char**` до `char**` через `const_cast<char**>` знімає константність із внутрішнього покажчика.
- Неявне приведення `char**` до `const char**` у C++ заборонено (на відміну від `char*` → `const char*`), оскільки це створило б діру в системі типів, дозволивши записати константний вказівник у змінний масив. `const_cast` дозволяє обійти це обмеження, коли програміст гарантує інваріант незмінності.

### Контракт пам'яті: легальний доступ проти апаратного UB

1. **Легальне використання (Safe Const Casting):**
   Об'єкт спочатку створено як неконстантний (`int x = 10;`). Посилання на нього передано в функцію як `const int& ref`. Функція знімає `const` через `const_cast<int&>(ref)` і змінює значення. Оскільки пам'ять змінної `x` виділена в стеку або динамічній пам'яті (RW — Read/Write), запис є на 100% стандарто-сумісним і безпечним.

2. **Невизначена поведінка (Undefined Behavior & Hard Fault):**
   Об'єкт створено як константний (`const int x = 10;`). Компілятор має право розмістити змінну `x` у секції пам'яті лише для читання (`.rodata`, Flash-пам'ять мікроконтролера) або агресивно підставити константу `10` у всі місця використання. Якщо програміст зніме `const` через `const_cast<int*>(&x)` і спробує виконати запис `*p = 20;`, стандарт оголошує таку дію невизначеною поведінкою. На практиці це призводить до системного винятку процесора `SIGSEGV` (Page Access Violation) або до ситуації, коли пам'ять змінюється, але оптимізований код продовжує читати старе значення `10`.

## 3. `reinterpret_cast<Target>(expression)`

Оператор `reinterpret_cast` виконує низькорівневе побітове переосмислення пам'яті та адрес без зміни бітових шаблонів. Він регулюється пунктом стандарту ISO C++ [expr.reinterpret.cast].

### Дозволені категорії низькорівневих перетворень

1. **Вказівник ↔ Ціле число:**
   - Перетворення будь-якого вказівника на об'єкт або функцію `T*` у цілий тип, достатній для збереження адреси (`uintptr_t` або `intptr_t`), і назад.
   - **Інваріант оборотності:** `reinterpret_cast<T*>(reinterpret_cast<uintptr_t>(p)) == p`.
2. **Вказівник ↔ Вказівник:**
   - Перетворення між вказівниками на довільні типи об'єктів (`Foo*` ↔ `Bar*`).
   - Числове значення адреси залишається **незмінним**. Компілятор не застосовує жодних зміщень підоб'єктів, навіть якщо класи знаходяться в одній ієрархії спадкування.
3. **Посилання ↔ Посилання:**
   - `reinterpret_cast<Target&>(expr)` інтерпретує байти існуючого об'єкта як екземпляр `Target`.

### Суворе правило сумісності типів: Strict Aliasing Rule (ISO C++ [basic.lval])

Отримання вказівника іншого типу через `reinterpret_cast` саме по собі є валідним. Однак **розіменування** такого вказівника (читання або запис значення через чужий тип) є **невизначеною поведінкою (UB)**, за винятком точно визначеного переліку типів-аліасів:

- Типи символьного представлення: `char`, `unsigned char`, `std::byte`.
- Типи, що відрізняються лише наявністю або відсутністю cv-кваліфікаторів (`const`, `volatile`).
- Базові класи вихідного динамічного типу об'єкта.
- Типи з підписами знаковості: `signed int` ↔ `unsigned int`.

Будь-яка спроба читання `float` через `int*` або структури `Header` через `uint32_t*` порушує Strict Aliasing Rule, дозволяючи оптимізатору викинути збереження в пам'ять або змінити порядок виконання інструкцій.

## 4. `dynamic_cast<Target>(expression)`

Оператор `dynamic_cast` реалізує динамічну навігацію складними поліморфними ієрархіями на основі метаданих RTTI під час виконання програми. Регулюється пунктом ISO C++ [expr.dynamic.cast].

### Вимоги до типів та середовища виконання

- Вихідний тип `expression` повинен бути **поліморфним**, тобто клас зобов'язаний мати хоча б одну віртуальну функцію (найчастіше це віртуальний деструктор `virtual ~Base() = default;`).
- Компілятор повинен мати ввімкнену генерацію RTTI (Run-Time Type Information). При компіляції з прапорцем `-fno-rtti` використання `dynamic_cast` для downcast призводить до помилки компіляції.

### Варіанти навігації по ієрархії

1. **Upcast (Вгору):** безпечне приведення до базового типу. Працює як на етапі компіляції, так і в runtime (фактично оптимізується до звичайного зміщення адреси).
2. **Downcast (Вниз):** перевірка, чи належить об'єкт базового класу `Base*` конкретному похідному типу `Derived*`.
3. **Cross-cast (Вбік / Side-cast):** приведення між двома незалежними базовими гілками об'єкта при множинному спадкуванні (наприклад, перетворення `InterfaceA*` у `InterfaceB*`, якщо реальний об'єкт реалізує обидва інтерфейси).
4. **Cast to void\* (Пошук бази):** вираз `dynamic_cast<void*>(pBase)` знаходить і повертає точну адресу початку найбільш похідного об'єкта (Most Derived Object) у пам'яті, використовуючи спеціальний запис Complete Object Locator у таблиці vtable.

### Семантика обробки невдач

- **Для вказівників (`Target*`):** якщо об'єкт не належить до цільового типу, оператор повертає нульовий вказівник `nullptr`. Перевірка виконується простим умовним виразом `if (auto* d = dynamic_cast<Derived*>(b))`.
- **Для посилань (`Target&`):** оскільки концепція «нульового посилання» суперечить семантиці мови, у разі невідповідності типу оператор викидає стандартний виняток `std::bad_cast` (оголошений у заголовковому файлі `<typeinfo>`).

### Продуктивність та часова складність

Вартість виклику `dynamic_cast` варіюється від одного читання пам'яті (для простого одиночного спадкування) до рекурсивного обходу графа типів DAG (Directed Acyclic Graph) з порівнянням рядків імен типів (`strcmp` у випадках динамічного завантаження бібліотек через `dlopen` у Linux). Часова складність може досягати `O(N)`, де `N` — загальна кількість класів у складному графі множинного спадкування.

## 5. Алгоритм розгортання C-style cast (ISO C++ [expr.cast])

Синтаксис явного приведення мови C `(Target)expression` або функціональна форма `Target(expression)` є не єдиною операцією, а п'ятиступеневим каскадом. Компілятор зобов'язаний по черзі перевірити п'ять можливих комбінацій і вибрати першу, яка є синтаксично валідною:

1. `const_cast<Target>(expression)`
2. `static_cast<Target>(expression)`
3. `static_cast<Target>(expression)`, за яким слідує `const_cast<Target>` (одночасна семантична конверсія та зняття константності)
4. `reinterpret_cast<Target>(expression)`
5. `reinterpret_cast<Target>(expression)`, за яким слідує `const_cast<Target>`

Якщо жодна з п'яти спроб не підходить, виникає помилка компіляції. Через те, що крок 4 (`reinterpret_cast`) автоматично слідує за кроком 2 (`static_cast`), будь-яка зміна ієрархії класів (наприклад, перетворення відкритого спадкування на закрите або розрив зв'язку спадкування) перетворює раніше безпечний код на мовчазний `reinterpret_cast`, що породжує важкі приховані дефекти пам'яті.

## 6. Порівняльний аналіз низькорівневого копіювання: `reinterpret_cast`, `std::memcpy`, `std::bit_cast`

При роботі з низькорівневими двійковими представленнями (десеріалізація мережевих пакетів, робота з регістрами апаратури MMIO, оптимізація обчислень Fast Inverse Square Root) інженери часто стикаються з вибором між трьома інструментами:

| Критерій | `reinterpret_cast<T*>` | `std::memcpy` | `std::bit_cast<To>` (C++20) |
| :--- | :--- | :--- | :--- |
| **Відповідність стандарту (Strict Aliasing)** | Порушує (UB при читанні через чужий тип) | Повністю легально ([basic.types]) | Повністю легально ([bit.cast]) |
| **Можливість обчислень у `constexpr`** | Ні (заборонено стандартом у сталих виразах) | Ні (до C++20 / обмежено в C++23) | Так (повна підтримка `constexpr`) |
| **Вимоги до типів** | Будь-які типи вказівників | Будь-які trivially copyable типи | Trivially copyable типи однакового `sizeof` |
| **Апаратний оверхед (-O2 / -O3)** | 0 інструкцій (але ламає оптимізатор) | 0 інструкцій (інтринсик підставляє регістровий `mov`) | 0 інструкцій (чисте переміщення між регістрами) |
| **Безпека вирівнювання (Alignment)** | Ризик падіння на ARM/SPARC при некратному вирівнюванні | Безпечно (копіює побайтово, оптимізатор зливає в MOV) | Безпечно (цільовий об'єкт створюється з коректним вирівнюванням) |

---

## 7. Прапорці компілятора та діагностика дефектів приведення

Сучасні компілятори Clang та GCC надають набір діагностичних ключів для виявлення сумнівних та небезпечних операцій приведення типів під час статичного аналізу:

| Прапорець | Компілятори | Опис та призначення |
| :--- | :--- | :--- |
| `-Wold-style-cast` | GCC, Clang | Генерує попередження на будь-яке використання C-style cast `(Type)val` у коді C++, вимагаючи заміни на іменовані оператори |
| `-Wcast-align` | GCC, Clang | Попереджає про приведення вказівника до типу з більшими вимогами до вирівнювання (наприклад, `char*` → `int*`), що може спричинити апаратне виключення на ARM |
| `-Wcast-qual` | GCC, Clang | Попереджає про неявне або явне зняття кваліфікаторів типу (`const`, `volatile`) |
| `-Wstrict-aliasing=2` | GCC, Clang | Активує суворий аналіз порушень правила Strict Aliasing при перетворенні та розіменуванні вказівників |
| `-Wnon-virtual-dtor` | GCC, Clang | Попереджає про знищення об'єкта через вказівник на базовий клас без віртуального деструктора (що робить некоректним і `dynamic_cast`) |

---

## 8. Типові сценарії невизначеної поведінки при приведенні типів

Для запобігання критичним дефектам пам'яті архітектори системного ПЗ виділяють п'ять головних пасток приведення:

1. **Модифікація справжнього константного літерала:** створення вказівника через `const_cast` на рядковий літерал або глобальну змінну `const` і запис у неї. Призводить до негайного падіння процесу через апаратний захист сторінок пам'яті.
2. **Невідповідний unchecked downcast через `static_cast`:** приведення `Base*` до `Derived*`, коли реальний об'єкт у купі є іншим підтипом `OtherDerived`. Звернення до полів класу викликає читання сміття або пошкодження сусідніх блоків пам'яті.
3. **Побітове переосмислення при множинному спадкуванні через `reinterpret_cast`:** замість зміщення вказівника на розмір попереднього базового підоб'єкта адреса залишається незмінною, через що виклики методів другого інтерфейсу отримують невірний `this`.
4. **Розіменування неаліасованого вказівника через `reinterpret_cast`:** читання `float` через `uint32_t*`, через що компілятор вважає, що запис у `uint32_t*` не впливає на кешоване у регістрі FPU/SSE значення `float`.
5. **Приведення вказівника на об'єкт, час життя якого завершено (Lifetime Violation):** використання `static_cast` або `reinterpret_cast` над адресою об'єкта після виклику його деструктора або звільнення пам'яті (`use-after-free`).
6. **Виклик віртуальних функцій або `dynamic_cast` у конструкторі чи деструкторі:** під час конструювання базового класу вказівник на таблицю vtable вказує на vtable базового типу, тому `dynamic_cast` до похідного типу повертає `nullptr` або кидає `std::bad_cast`.
7. **Знищення похідного об'єкта через базовий вказівник без віртуального деструктора:** якщо базовий клас не має віртуального деструктора, виклик `delete pBase` є невизначеною поведінкою, оскільки деструктор похідного класу ніколи не буде викликаний, а виділена пам'ять звільниться некоректно.

> [!IMPORTANT]
> При проектуванні систем критичної надійності вибір між операторами приведення повинен спиратися на принцип найменших привілеїв: якщо задачу можна вирішити за допомогою `static_cast`, неприпустимо використовувати `reinterpret_cast` або C-style cast. Будь-яке зняття `const` через `const_cast` або реінтерпретація пам'яті через `reinterpret_cast` вимагає обов'язкового супровідного коментаря з обґрунтуванням інваріантів безпеки.
