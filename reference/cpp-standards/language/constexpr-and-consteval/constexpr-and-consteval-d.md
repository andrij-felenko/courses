## Місця, які не вміють чекати

```cpp
int table[N];
switch (c) { case N: break; }
static_assert(N > 0);
alignas(N) char storage[64];
std::array<int, N> buf;
```

Жоден із цих рядків компілятор не може відкласти на потім. Розмір масиву визначає, скільки байтів зарезервувати в кадрі стека або в секції даних; мітка `case` потрібна, щоб побудувати таблицю переходів; аргумент шаблону — щоб узагалі породити тип. Тут немає варіанту «дізнаємося під час роботи»: якщо числа немає зараз, немає й програми.

Отже мова зобов'язана відповісти на питання, які саме вирази компілятор мусить уміти порахувати сам. До C++11 відповідь була вузька: літерал, арифметика над літералами і `const`-змінна цілого типу, ініціалізована таким виразом. Виклику функції в цьому переліку не було — навіть найпростішого.

Наслідок відчувався щодня. Функція `pow2` працювала бездоганно, але поставити `pow2(10)` у розмір масиву не дозволялося, і те саме число доводилося здобувати іншим способом — рекурсією за цілим параметром шаблону:

```cpp
template <int N> struct Pow2 { static const int value = 2 * Pow2<N - 1>::value; };
template <>      struct Pow2<0> { static const int value = 1; };

int table[Pow2<10>::value];   // 1024
```

Це працює, але це друга мова всередині C++: інший синтаксис, інші правила, нечитні повідомлення про помилки — і жодного зв'язку з тією самою арифметикою, записаною звичайно. Одну логіку доводилося тримати у двох несумісних записах і стежити, щоб вони не розійшлися. Те, що така мова взагалі знайшлася в шаблонах, було не задумом, а знахідкою: [Як обчислення до запуску потрапило в C++](book:cpp-standards/constexpr-and-consteval/hist-constexpr-birth.md) розповідає про випадковий шаблонний обчислювач, знайдений на початку 1990-х, і про низку пропозицій Ґабріеля Дос Реїса, Бʼярне Струструпа і Єнса Маурера, з якої виросло `constexpr`.

Задум був простий: дозволити одну звичайну функцію, яку можна покликати і в розмірі масиву, і в звичайному коді.

## Слово на функції — це дозвіл, а не наказ

```cpp
constexpr int square(int x) { return x * x; }

static_assert(square(7) == 49);     // контекст вимагає сталої — рахує компілятор

int n = std::atoi(argv[1]);
int m = square(n);                  // звичайний виклик у час виконання
```

`constexpr` перед функцією не наказує рахувати її під час компіляції. Воно стверджує слабше: цю функцію **можна** порахувати під час компіляції, якщо аргументи це дозволять. Хто цим скористається — вирішує місце виклику.

Правило таке. Якщо вираз стоїть там, де мова **вимагає** сталої, компілятор запускає власний обчислювач сталих — вбудований у нього інтерпретатор C++ — і або дістає значення, або видає помилку. Якщо ж контекст звичайний, `constexpr`-функція викликається так само, як будь-яка інша.

![Один і той самий constexpr обчислюється або компілятором, або процесором](/reference/cpp-standards/language/constexpr-and-consteval/img/two-paths.svg)

*Ключове слово лише відчиняє двері; у які саме двері піде виклик, визначає контекст, у якому він написаний.*

Тут легко переплутати дві різні речі. Оптимізатор і без жодного `constexpr` радо згорне `square(7)` у сімдесятку — це його звичайна робота за правилом «ніби». Але то оптимізація, а не гарантія: вона залежить від рівня оптимізації, від того, чи видно тіло функції, від настрою конкретної збірки. `constexpr` натомість описує **правило мови**: у контексті, що вимагає сталої, обчислення або відбудеться, або програма не збереться. Різниця між «швидше за все порахує» і «зобов'язаний порахувати» — це вся різниця між оптимізацією й типом.

Наскільки далеко може заходити дозвіл, який ніколи не спрацює? До C++23 стандарт вимагав, щоб `constexpr`-функція була придатна для сталого обчислення хоч за якихось аргументів — інакше програма вважалася хибною, хоч і без обов'язку діагностувати це. Вимога виявилася шкідливою: перевірити її означає перебрати всі можливі входи, тож компілятори мовчали, а автор шаблонної бібліотеки не міг знати, чи його код формально коректний для типів, яких він ще не бачив. C++23 вимогу прибрав: `constexpr` на функції тепер означає рівно «в сталому контексті ця функція не заборонена», і не більше. Заразом `constexpr`-функція неявно `inline` — інакше визначення в заголовку, яке мусить бути видиме кожному, хто хоче її порахувати, порушувало б [правило одного визначення](book:cpp-standards/odr-and-linkage).

## На змінній те саме слово означає протилежне

```cpp
constexpr int limit = square(7);    // вимога: порахуй мене зараз
```

Тут `constexpr` уже нічого не дозволяє — воно вимагає. Якщо ініціалізатор не вдасться порахувати, це помилка компіляції, а не тихий відкат до звичайного присвоєння.

Суперечності немає: правило одне, змінилося лише місце. Слово завжди означає «тут працює обчислювач сталих», і на змінній воно стоїть перед ініціалізатором — тобто перед позицією, яка сталої вимагає. Тому наслідок для змінної жорсткий, а для функції м'який.

Із цієї вимоги випливають два побічні наслідки. По-перше, `constexpr`-змінна автоматично `const`: значення повністю відоме до запуску, змінювати його нічим і ніде. По-друге, змінна зі статичним часом зберігання не потребує коду ініціалізації взагалі — її вміст лягає в незмінну секцію готового бінарника ще на етапі збірки.

## Чому обчислювач сталих такий вибагливий

Перша редакція правил, C++11, дозволяла в тілі `constexpr`-функції фактично один-єдиний `return`. Ні циклу, ні локальної змінної, ні `if` — лише умовний вираз і рекурсія. Обмеження було не принциповим, а бюджетним: обчислювач сталих — це другий, окремий виконавець C++, написаний усередині компілятора, і кожна підтримана конструкція коштувала його авторам роботи. Комітет узяв мінімум, який розв'язував початкову задачу.

Уже в C++14 (папір N3652 Річарда Сміта) стало можна майже все звичне: локальні змінні, цикли, розгалуження, зміна об'єктів, створених у ході самого обчислення. Ця остання дозволеність показує, де насправді пролягає межа. Змінювати щось усередині сталого обчислення можна, і це нікому не шкодить, бо змінене ніде за межами обчислення не існує.

Ось справжній інваріант усього механізму: **стале обчислення замкнене в собі**. Його результат залежить тільки від аргументів і від того, що створене всередині нього самого; жодного стану ззовні воно ні читає, ні лишає.

![Стале обчислення замкнене: усе, чого воно торкається, або аргумент, або створене всередині](/reference/cpp-standards/language/constexpr-and-consteval/img/sealed-box.svg)

*Усі заборони всередині сталого обчислення — наслідки однієї вимоги: воно не має ні зовнішнього стану, ні світу навколо.*

З цієї замкненості виводяться всі заборони, і кожну можна не запам'ятовувати, а вивести самому:

- **Читати змінну, що живе лише в час виконання, не можна** — під час компіляції такої змінної ще фізично немає, її значення нізвідки взяти.
- **Ввід-вивід і системні виклики не можна** — операційної системи в цій точці немає, а компілятор не має права підмінити її вигаданою відповіддю.
- **Пам'ять із `new` (дозволена з C++20) мусить бути звільнена до кінця того самого обчислення** — купа не переживає компіляції: у бінарник не існує способу покласти живий блок, виділений під час збірки.
- **Невизначеної поведінки не може бути взагалі** — обчислювач мусить дати конкретну відповідь, а UB відповіді не має.

Останній пункт вартий окремого погляду, бо він дає C++ те, чого в ньому більше ніде немає:

```cpp
constexpr int grow(int x) { return x + 1; }

constexpr int ok  = grow(41);            // 42
constexpr int bad = grow(2147483647);    // помилка компіляції: знакове переповнення
```

У звичайному коді той самий `grow(2147483647)` — це невизначена поведінка: компілятор має право вважати переповнення неможливим і викинути перевірку, що на ньому трималася. У сталому обчисленні виходу «як пощастить» немає: обчислювач зобов'язаний або дати число, або визнати вираз несталим, і другий варіант у контексті `constexpr`-змінної означає діагностику. Помилку видно на екрані замість того, щоб ловити її в проді.

> 🔧 **Навіщо це.** Стале обчислення — єдине місце в C++, де стандарт обіцяє впіймати невизначену поведінку, а не залишити її на волю оптимізатора. Звідси практичний прийом: перевіряти арифметику й розбір даних `static_assert`-ами на модельних входах. Такий «тест» не запускається — він або зібрався, або збірка впала з вказівкою на конкретний рядок, і жодного коду в бінарник не додає.

Замкненість пояснює й те, що спантеличує найчастіше: чому `std::vector` можна вживати всередині `constexpr`-функції, але `constexpr std::vector` як змінну оголосити не можна. Усередині обчислення вектор поводиться нормально — виділяє пам'ять, росте, звільняє її у своєму деструкторі до кінця обчислення. А `constexpr`-змінна мусить **пережити** обчислення й лягти в бінарник готовою; вказівник на купу, якої після компіляції не існує, покласти туди неможливо. Звідси й формальна умова, яку стандарт ставить типам таких змінних: пережити межу обчислення може лише **літеральний тип** — той, чиє значення цілком складається з полів, придатних до сталого обчислення, і чий деструктор тривіальний. `int`, `std::array<int, 8>`, власна структура з таких полів — так; будь-що з власною купою — ні.

Пізніші випуски стандарту рухалися в одному напрямку — розширювати, що дозволено всередині замкненої коробки: віртуальні виклики, `try`/`catch`, зміну активного члена об'єднання, роботу з `std::vector` і `std::string`. Точний перелік того, що дозволяє кожна редакція мови, зібрано окремо: [Що дозволено в сталому обчисленні за редакціями стандарту](book:cpp-standards/constexpr-and-consteval/api-constexpr-by-version.md).

## Прогалина, яку лишає слово «можна»

М'якість `constexpr` на функції — не завжди перевага. Є задачі, де відкат до звичайного виклику означає мовчазний провал усього задуму.

Класика — таблиця замін, яку рахують один раз і назавжди: якщо вона з якоїсь причини не обчислилася під час збірки, програма просто тихо витрачає час на старті. Ще гірше з перевірками: функція, що звіряє рядок формату з переліком аргументів, має сенс лише як помилка компіляції. Якщо ту саму перевірку виконати в час виконання, вона перетвориться на витрату процесорного часу і на помилку, яка вилізе в користувача. І нарешті — код, породжений заради самої компіляції, взагалі не повинен потрапляти в бінарник.

У всіх трьох випадках потрібне не «можна», а «мусить». C++20 дав для цього окреме слово — `consteval` (папір P1073R3 Річарда Сміта, Ендрю Саттона й Давида Вандевоорда; у першій редакції його пропонували писати як `constexpr!`). Функцію з `consteval` називають **негайною** (immediate): кожен її виклик зобов'язаний сам бути сталим виразом.

```cpp
consteval int checked_port(int p) {
    if (p <= 0 || p >= 65536) throw "порт поза допустимим діапазоном";
    return p;
}

constexpr int http = checked_port(8080);   // добре

int r = std::atoi(argv[1]);
int bad = checked_port(r);                 // помилка: аргумент не сталий
```

`throw` тут — не обробка помилок, а спосіб зупинити обчислювач: викинутий виняток робить вираз несталим, а для негайної функції несталий виклик і є діагностикою. Ніякого винятку в час виконання не буде, бо в час виконання цієї функції не існує.

Саме це — головний наслідок. Негайна функція не має тіла в готовому бінарнику: у неї немає адреси, її не можна передати як зворотний виклик, не можна взяти вказівник на неї у звичайному коді. Вона живе рівно стільки, скільки триває компіляція.

![constexpr, consteval і constinit: що кожне слово вимагає](/reference/cpp-standards/language/constexpr-and-consteval/img/four-words.svg)

*З чотирьох записів лише `constexpr` на функції є дозволом — три інші є вимогами, і при невдачі падає збірка.*

Четвертий запис на цій схемі, `constinit`, стосується не обчислення, а моменту ініціалізації: він вимагає, щоб змінна зі статичним часом зберігання дістала значення до запуску, але не робить її незмінною. Це рятує від [фіаско порядку статичної ініціалізації](book:programming/cpp-static-init-order) там, де об'єкт мусить змінюватися далі; докладніше — у [constinit: ініціалізація до запуску без обіцянки незмінності](book:cpp-standards/constinit).

## Дві реалізації в одному тілі

Часто та сама операція має різні найкращі втілення до запуску й під час роботи. Порахувати кількість значущих бітів на процесорі — одна інструкція; але тієї інструкції не існує в світі обчислювача сталих, там потрібен переносний цикл. Писати дві функції означає знову розділити одну логіку надвоє — рівно те, від чого `constexpr` мав рятувати.

C++20 дав функції спосіб спитати, де вона зараз виконується. `std::is_constant_evaluated()` з `<type_traits>` (папір P0595 Давида Вандевоорда, у пізніших редакціях разом із Річардом Смітом і Ендрю Саттоном) повертає `true`, коли виклик відбувається всередині сталого обчислення:

```cpp
constexpr int bit_width(unsigned v) {
    if (std::is_constant_evaluated()) {
        int n = 0;
        while (v) { ++n; v >>= 1; }
        return n;                                  // переносно, для компілятора
    }
    return v ? 32 - __builtin_clz(v) : 0;          // одна інструкція, для процесора
}
```

Ця функція має пастку, на яку натрапляли настільки часто, що компілятори завели про неї окреме попередження. Записати перевірку через `if constexpr` не можна:

```cpp
if constexpr (std::is_constant_evaluated()) { … }   // завжди true
```

Причина проста, коли її побачити: умова `if constexpr` сама зобов'язана бути сталим виразом, отже сама обчислюється всередині сталого обчислення. Питання «чи я зараз у сталому обчисленні?» задається в місці, де відповідь наперед відома, — і завжди повертає `true`, скільки б разів функцію не викликали в час виконання.

C++23 прибрав цю пастку конструкцією, якою неможливо скористатися неправильно, — `if consteval` (папір P1938R3 Баррі Ревзіна, Річарда Сміта, Ендрю Саттона й Давида Вандевоорда). Дужки в ній обов'язкові, тож переплутати форми ніде:

```cpp
constexpr int bit_width(unsigned v) {
    if consteval { int n = 0; while (v) { ++n; v >>= 1; } return n; }
    else         { return v ? 32 - __builtin_clz(v) : 0; }
}
```

Крім захисту від помилки, гілка `if consteval` дає ще одне: всередині неї дозволено викликати негайні функції. Це той самий висновок, що й раніше, лише доведений до кінця — якщо ми точно знаємо, що виконуємось під час компіляції, то й обмеження на `consteval` тут ні до чого.

## Коли негайність підіймається вгору

У C++20 лишалася діра, яка ламала складання коду з частин. `constexpr`-функція мусить бути придатною і як звичайна, а всередині неї параметр — не стала. Тому будь-яка обгортка над негайною функцією не збиралася взагалі, навіть якщо її саму завжди кликали в сталому контексті. Обгортати не вдавалося нічого: ані передавальний шар, ані конструктор, який хотів перевірити свій аргумент негайною функцією.

C++23 (папір P2564R3 Баррі Ревзіна) розв'язав це передаванням негайності вгору: функція, яка не може обійтися без негайного виклику, сама стає негайною.

```cpp
consteval int id(int x) { return x; }

template <class T>
constexpr int wrap(T x) { return id(x); }   // C++20: помилка; C++23: wrap стає негайною

static_assert(wrap(5) == 5);                // добре
int z = wrap(std::atoi(argv[1]));           // помилка — і саме на цьому рядку
```

Важлива подробиця: підвищується не будь-що. Перетворитися на негайну може лише інстанціювання шаблону, лямбда або згенерований компілятором особливий метод — тобто сутність, яка й так народжується під конкретне вживання. Звичайна нешаблонна `constexpr`-функція так не робить, і це навмисно: вона є справжнім символом у бінарнику, на неї можуть покликатися з інших одиниць трансляції, і тихо позбавити її життя в час виконання означало б зламати чужий код без жодного попередження.

## Що це коштує

Обчислювач сталих — інтерпретатор, який працює всередині компілятора й не має ні оптимізацій, ні машинного коду. Обчислення, яке процесор виконує за мікросекунду, у ньому може тривати на порядки довше, і платить за це кожна збірка. Це реальний важіль: одна велика таблиця, порахована під час компіляції, обмінює секунди старту програми на секунди складання проєкту — і чи вигідний цей обмін, залежить від того, скільки разів на день перезбирають код.

Друга частина ціни — розмір. Результат сталого обчислення не зникає: він лягає в бінарник як дані. Таблиця на шістдесят чотири тисячі елементів по чотири байти — це чверть мегабайта у файлі прошивки незалежно від того, чи знадобиться вона взагалі.

Як це виглядає на живому коді — від таблиці CRC-32, порахованої до запуску, до перевірки рядка формату негайною функцією, і що з усього цього справді потрапляє в об'єктний файл: [Таблиця й перевірка, зроблені компілятором](book:cpp-standards/constexpr-and-consteval/proj-compile-time-table.md).
