Ти читаєш чужий код і натрапляєш на виклик:

```cpp
render(scene, camera);
```

Найперше питання, яке треба закрити, щоб читати далі: чи повернеться `scene` з цього виклику такою самою? Щоб відповісти, доводиться відкрити `render`. А там ще п'ять викликів, і в кожен `scene` іде далі. Відповідь на одне просте питання коштує обходу півдерева викликів — і так щоразу, для кожної змінної, у кожному місці.

Коментар «функція не змінює сцену» цю ціну не знімає, бо коментар ніхто не звіряє з кодом: він старіє мовчки, і за півроку — це просто напис, під яким уже може бути що завгодно. Потрібна не обіцянка на словах, а обіцянка, яку **перевіряє машина** і яку видно **прямо в підписі функції**, без читання тіла. У C++ місце для таких обіцянок одне — тип. Тому й з'явилося слово `const` (лат. *constans* — сталий): не приписка до змінної, не побажання компіляторові, а **частина типу**.

## const описує двері, а не кімнату

Ось два рядки, у яких немає жодного `const`-об'єкта:

```cpp
int x = 1;
const int& r = x;      // ✓ дозволено: звужуємо права доступу
r = 2;                 // ✗ помилка компіляції
x = 2;                 // ✓ той самий об'єкт, інший шлях — можна
```

Об'єкт один. Комірка одна. Але через `r` писати не можна, а через `x` — можна. Тобто `const` тут характеризує не комірку, а **дорогу до неї**: посилання `r` — це вид на об'єкт із правом лише читати. Кімната не змінилася; замок висить на дверях.

![Одна прямокутна комірка пам'яті «x = 1» посередині. Ліворуч до неї веде стрілка з підписом «int& — двері з правом писати», праворуч — стрілка «const int& — двері лише для читання», перекреслена стрілка «запис» на ній. Унизу підпис: об'єкт один, прав доступу два](/reference/cpp-standards/language/const-correctness/img/const-view.svg)

*Один і той самий об'єкт можна бачити крізь двоє різних дверей: одні дають писати, другі — лише читати. `const` живе на дверях, а не в кімнаті, і саме тому обмеження можна додати по дорозі, а зняти — ні.*

З цієї картинки одразу випливає перше практичне правило конверсій. Звузити права можна завжди: `int&` перетворюється на `const int&`, `T*` — на `const T*`, мовчки й безкоштовно. Розширити — не можна: із `const int&` не зробити `int&` жодним неявним перетворенням, бо це означало б відібрати назад обіцянку, яку хтось уже комусь дав.

Тепер підпис функції читається без відкривання тіла:

```cpp
void render(const Scene& s, Camera& c);
```

`Scene` заходить крізь двері лише для читання — компілятор не пропустить жодного запису в неї всередині `render`, і так само не пропустить передавання її далі кудись, де писати дозволено. `Camera` заходить крізь звичайні двері, отже цілком може повернутися іншою. Одне слово в підписі замінило обхід дерева викликів.

> 🔧 **Навіщо це.** Головна вигода `const` — не «захист від себе», а **локальність міркувань**. Побачивши `const Scene&`, ти закриваєш питання про сцену назавжди й читаєш далі, не тримаючи в голові гілку «а раптом там усе-таки запис». У великому проєкті це різниця між кодом, який можна читати шматками, і кодом, який доводиться тримати в голові цілком. І це ж робить `const` частиною [дизайну API](book:programming/api-design): підпис функції — місце, де читач шукає контракт, і `const` там дешевший за будь-яку документацію, бо не бреше.

## Дві сторони одного вказівника

Посилання просте: воно саме по собі незмінне — прив'язалося раз і назавжди, тож для нього питання «що заморожено» не стоїть. З вказівником інакше: у ньому дві сутності — сама стрілка й мішень, у яку вона показує. Заморозити можна кожну окремо, тому й записів три:

```cpp
char buf[] = "abc";
char other[] = "xyz";

const char* p = buf;        // мішень незмінна, стрілку можна перевести
p = other;                  // ✓
*p = 'X';                   // ✗

char* const q = buf;        // стрілка прибита, мішень мінлива
q = other;                  // ✗
*q = 'X';                   // ✓

const char* const s = buf;  // прибито обидва
```

![Три горизонтальні смуги. У кожній ліворуч рамка «вказівник», стрілка до правої рамки «дані». Перша смуга: підпис const char* p, замок на правій рамці, стрілка помічена «можна перевести». Друга: char* const q, замок на лівій рамці, права помічена «можна писати». Третя: const char* const s, замки на обох. Праворуч від кожної — короткий вислід](/reference/cpp-standards/language/const-correctness/img/pointer-const-sides.svg)

*У вказівнику дві незалежні речі: стрілка й мішень. `const` ліворуч від зірочки замикає мішень, `const` праворуч — саму стрілку. Читати оголошення треба справа наліво від імені: `char* const q` — «q є сталим вказівником на char».*

Правило читання й справді просте: іди від імені змінної вліво, вимовляючи слова. `const char* p` — «p є вказівником на char, який сталий». `char* const q` — «q є сталим вказівником на char». Розташування `const` до чи після `char` (`const char*` проти `char const*`) нічого не змінює — це той самий тип, лише два стилі запису; варіант `char const*` тим і зручний, що дає читати послідовно справа наліво без винятків.

Ці дві сторони мають назви, і вони не косметичні. `const` **верхнього рівня** — той, що замикає сам об'єкт (`char* const`, `const int n`). `const` **нижнього рівня** — той, що замикає те, на що об'єкт дивиться (`const char*`). Різниця між ними визначає, що взагалі бачить решта програми.

**const верхнього рівня на параметрі нікого не обходить.** Ось наслідок, який дивує, поки не подумати:

```cpp
void f(int n);
void f(const int n);   // ✗ це НЕ перевантаження — це та сама функція
```

Компілятор відкидає `const` верхнього рівня з параметрів, коли визначає тип функції. І це не примха, а необхідність: параметр `int n` — **копія**, вона живе всередині виклику й помирає з ним. Чи змінює функція власну копію — справа її кухні, а не контракту з тим, хто викликає; той, хто викликає, взагалі не має способу помітити різницю. Тому в **оголошенні** такий `const` — шум (його прибирають), а в **означенні** він законний і корисний: обіцянка самому собі не крутити параметр усередині тіла.

```cpp
void f(int n);            // оголошення в заголовку — без const
void f(const int n) {     // означення: усередині n не змінюємо
    // ...
}
```

А от `const` **нижнього рівня** — повноцінна частина типу функції, і саме на ньому будуються перевантаження: `f(char*)` і `f(const char*)` — дві різні функції.

**Чому `char**` не перетворюється на `const char**`.** Класичне місце, де інтуїція «додати `const` завжди безпечно» ламається. Здається, що додавання `const` углиб — таке саме звуження прав, як і всюди. Але подивись, що воно відкрило б:

```cpp
const char kSecret = 'S';
char* p = nullptr;

const char** pp = &p;   // ✗ заборонено — і ось чому
*pp = &kSecret;         // законно: у const char* кладемо const char*
*p = 'X';               // запис у kSecret — крізь звичайний char*!
```

Кожен окремий крок після першого рядка виглядає бездоганно, тож дірку мусить закрити саме перший. Тому конверсія `T**` → `const T**` заборонена. Дозволена інша: `char**` → `const char* const*` — коли додаєш `const` углиб, треба додати його **й на всіх проміжних рівнях**, і тоді підміни зсередини не станеться.

## const-метод — це const-вид на сам об'єкт

Функція-член не має явного параметра для об'єкта, на якому її викликають, — той приходить прихованим вказівником `this`. Отже, питання «чи змінює метод об'єкт» — це те саме питання про двері, тільки для `this`. Слово `const` після списку параметрів і означає: `this` тут має тип «вказівник на сталий об'єкт».

```cpp
class Buffer {
    std::vector<std::byte> data_;
public:
    std::size_t size() const { return data_.size(); }  // this: const Buffer*
    void clear()             { data_.clear(); }        // this: Buffer*
};
```

Далі працює звичайний [добір перевантаження](book:cpp-standards/overload-resolution): на `const`-об'єкті доступні лише `const`-методи, на звичайному — всі, і за наявності пари компілятор бере точнішу за константністю. На цьому тримається один із найпоширеніших візерунків стандартної бібліотеки — **пара доступових методів**:

```cpp
class Buffer {
    std::vector<std::byte> data_;
public:
    std::byte&       operator[](std::size_t i)       { return data_[i]; }
    const std::byte& operator[](std::size_t i) const { return data_[i]; }
};
```

Той самий вираз `b[i]` дає право писати, якщо `b` звичайний, і лише читати, якщо `b` сталий. Так само влаштовані `begin()`/`end()` у контейнерах, а `cbegin()`/`cend()` (з C++11) існують окремо для випадку, коли об'єкт не `const`, а `const_iterator` тобі потрібен явно.

Пара доступових методів має незручність: тіло дублюється, і з часом дві копії розходяться. Історичний вихід — написати `const`-версію, а неконстантну виразити через неї:

```cpp
std::byte& Buffer::operator[](std::size_t i) {
    return const_cast<std::byte&>(std::as_const(*this)[i]);
}
```

Це законно, доки сам об'єкт не оголошений `const`, — але потворно. C++23 дав пряме рішення — **явний параметр об'єкта**: метод оголошує `this` як звичайний шаблонний параметр, і одне тіло обслуговує обидві константності, [зберігаючи категорію значення](book:cpp-standards/deducing-this) виклику:

```cpp
template <class Self>
auto&& operator[](this Self&& self, std::size_t i) {
    return std::forward<Self>(self).data_[i];
}
```

## Де const зупиняється

Тут ховається найдорожча помилка розуміння. Питання просте: `const`-метод заморожує об'єкт — а наскільки глибоко?

Відповідь випливає з того самого принципу: `const` — це властивість **шляху**, і застосовується він до **самих полів**, а не до всього, що з них досяжно. Усередині `const`-методу кожне поле бачиться зі своїм `const` верхнього рівня. Для поля-значення це заморожує все:

```cpp
class Widget {
    std::vector<int> v_;   // у const-методі бачиться як const std::vector<int>
    Impl* impl_;           // у const-методі бачиться як Impl* const
public:
    void touch() const {
        v_.push_back(1);   // ✗ вектор став сталим — жодних змін
        impl_->mutate();   // ✓ КОМПІЛЮЄТЬСЯ — і об'єкт таки міняється
    }
};
```

Другий рядок компілюється не через дірку в мові, а точно за правилом: поле `impl_` — це стрілка, і сталою стала **стрілка**, а не мішень. Метод не може перевести `impl_` кудись інде, зате все, що лежить за ним, лишається повністю мінливим. Константність не проходить крізь вказівник.

![Рамка «const-метод» з написом this: const Widget*. Усередині два поля. Поле v_ (значення) охоплене замком «застигло цілком». Поле impl_ — рамка із замком лише на самій рамці, з неї стрілка виходить за межі великої рамки в окрему рамку «Impl — мінливий», стрілка підписана «const тут закінчується»](/reference/cpp-standards/language/const-correctness/img/const-method-depth.svg)

*У `const`-методі застигають самі поля. Поле-значення застигає разом із вмістом, а поле-вказівник застигає лише як стрілка: за нею починається територія, куди `const` не дістає. Це та сама поверхнева незмінність, тільки записана правилами C++.*

Це поверхнева, а не глибока константність — та сама пастка, що й у будь-якій мові з посиланнями, докладно розібрана в статті про [незмінність як прийом дизайну](book:programming/immutability); там же видно, чому «глибина» гарантії дорівнює найслабшій ланці на дорозі вглиб. У C++ вона має конкретні наслідки. Перший — [PIMPL](book:cpp-standards/pimpl): якщо реалізація схована за `Impl*`, то `const`-методи класу **не захищають** її від змін, і компілятор мовчить. Ліки — `std::experimental::propagate_const` з бібліотечного TS: обгортка над вказівником, яка проштовхує константність власника всередину. Другий наслідок стосується невласницьких видів: `const std::span<int>` — це сталий **вид** (не переставити на інший масив), а не сталі **дані**, тоді як «дивитися й не чіпати» пишеться як `std::span<const int>`; те саме розрізнення живе в [span](book:cpp-standards/span-contiguous) і в [string_view](book:cpp-standards/string-and-string-view). Плутанина між цими двома записами — постійне джерело «але ж я поставив const».

## Побітова константність проти логічної

Дотепер `const`-метод виглядав як «нічого в об'єкті не міняти». Але візьмімо реальну потребу: клас `Document` уміє віддати кількість слів, рахувати її дорого, а текст після створення не змінюється. Природно порахувати раз при першому запиті й запам'ятати. `word_count()` — очевидно, метод для читання, отже `const`. Але він **пише** в поле кешу.

Тут доводиться вибрати, що означає `const` насправді. **Побітова константність** — жоден біт об'єкта не змінюється. **Логічна константність** — назовні об'єкт не змінився: жодна послідовність викликів не поверне двох різних відповідей на те саме питання. Кеш пише біти, але не змінює жодної відповіді: `word_count()` завжди віддає те саме число, просто вдруге швидше.

C++ обрав логічну, і дав для неї спеціальне слово — `mutable` (лат. *mutabilis* — змінний). Поле, позначене `mutable`, дозволено змінювати навіть у `const`-методі:

```cpp
class Document {
    std::string text_;
    mutable std::optional<std::size_t> words_;   // кеш, а не стан
public:
    std::size_t word_count() const {
        if (!words_) words_ = count_words(text_);
        return *words_;
    }
};
```

Межа тут не технічна, а сенсова, і провести її мусиш ти: `mutable` законний тільки для того, що **не видно назовні** — кеші, лічильники звернень, ліниво обчислені значення, м'ютекси. Щойно `mutable`-поле починає впливати на відповіді методів, `const` перетворюється на брехню, і всі, хто на нього спирався, отримали хибну гарантію. Компілятор цю межу не стереже — він перевіряє лише те, що записано в типах.

## C++11 додав до const обіцянку про потоки

До C++11 сказаного вище вистачало. Потім у мову прийшла модель пам'яті — і разом із нею з'ясувалося, що «логічна константність» замало.

Розсудьмо, чому. Два потоки одночасно викликають `word_count()` на тому самому документі. Обидва бачать порожній кеш, обидва пишуть у `words_`. Це [гонка даних](book:programming/atomicity-races) — невизначена поведінка, попри те що обидва потоки, з погляду програміста, «лише читали». Тим часом увесь звичний спосіб працювати з даними між потоками саме на цьому й тримається: спільний об'єкт роздають усім лише для читання й вважають, що синхронізація не потрібна.

Тому стандарт C++11 закріпив вимогу до стандартної бібліотеки: одночасні виклики `const`-методів того самого об'єкта **мусять бути безпечними**. Це піднімає планку для `mutable`: логічної константності вже недостатньо, потрібна ще й відсутність гонок. Герб Саттер сформулював новий зміст стисло — `const` тепер означає «незмінний **або** внутрішньо синхронізований»; Б'ярне Страуструп цю саму тезу підтверджує словами, що `const` означає незмінність і відсутність гонок. Тобто `mutable`-поле, яке справді пишеться, зобов'язане бути або атомарним, або накритим [м'ютексом](book:cpp-standards/mutex-and-raii-locks):

```cpp
class Document {
    std::string text_;
    mutable std::mutex m_;
    mutable std::optional<std::size_t> words_;
public:
    std::size_t word_count() const {
        std::lock_guard lock(m_);
        if (!words_) words_ = count_words(text_);
        return *words_;
    }
};
```

Зверни увагу, що м'ютекс теж `mutable`: захоплення замка змінює його стан, а робиться воно з `const`-методу. Повний розбір такого класу — від наївної версії до тієї, що витримує і потоки, і копіювання, з переліком пасток на кожному кроці — винесено в окремий [проєкт про логічну константність](book:cpp-standards/const-correctness/proj-logical-const-cache.md).

> 🔧 **Навіщо це.** Ця вимога перетворює `const` із зручності на **інструмент потокової безпеки**. Побачивши, що об'єкт роздано кільком потокам лише як `const&`, ти маєш право не шукати синхронізацію — за умови, що автор класу дотримав правила. І навпаки: якщо ти пишеш клас із `mutable`-кешем без замка, ти ламаєш обіцянку, на яку спирається кожен користувач твого типу, причому ламаєш тихо — у тестах на одному потоці все зелене. Це основна причина, чому [потокова безпека](book:programming/thread-safety) типу починається з чесного `const`.

## Зняти const: де закон, а де невизначена поведінка

`const_cast` існує, бо реальність буває не константо-коректною: стара бібліотека бере `char*` там, де читає, і переписати її ти не можеш. Питання лише в тому, коли зняття `const` — законна операція, а коли — вихід за межі мови.

Відповідь знову випливає зі спини всієї теми. `const` — властивість шляху, тож зняти його — це просто взяти інший шлях до того самого об'єкта. Якщо **сам об'єкт** не константний, інший шлях цілком законний:

```cpp
int x = 1;
const int& r = x;
const_cast<int&>(r) = 2;    // ✓ законно: об'єкт x не const, ми лише обійшли двері
```

А якщо об'єкт **оголошений** `const`, писати в нього через будь-який шлях — невизначена поведінка:

```cpp
const int y = 1;
const_cast<int&>(y) = 2;    // ✗ UB, хоч би що показав запуск
```

Це не формальність заради формальності — за нею стоїть конкретна свобода [компілятора](book:programming/compiler-optimizations). Побачивши `const int y = 1`, він має право не заводити комірку взагалі, а підставити одиницю в усі місця, де `y` читається; має право покласти об'єкт у секцію пам'яті лише для читання, і тоді запис — апаратна помилка. Одна й та сама програма надрукує `1` в одній збірці й `2` в іншій, і обидві будуть праві, бо контракт порушив ти. Про цей клас помилок — стаття про [невизначену поведінку](book:programming/undefined-behavior); тут важливо тільки правило: `const_cast` знімає **позначку зі шляху**, а не константність із об'єкта, і чинний він лише тоді, коли об'єкт від початку був мінливим.

Зворотна операція — додати `const` — потреби в касті не має взагалі, а з C++17 має зручну назву: `std::as_const(obj)` повертає `const`-посилання й нічого не копіює. Це найкоротший спосіб змусити компілятор вибрати `const`-перевантаження, коли об'єкт під рукою звичайний. Повний перелік мовних і бібліотечних засобів, що працюють із константністю — від `const_cast` і `std::as_const` до рис `std::is_const_v`, `std::remove_const_t` і `propagate_const`, — зібрано в окремому [довіднику інструментів](book:cpp-standards/const-correctness/api-const-toolbox.md).

## const — не про час компіляції

Дві речі постійно злипаються в одну: «значення не зміниться» і «значення відоме компіляторові». `const` каже лише перше.

```cpp
const int a = 5;                  // ініціалізатор — константний вираз
int arr[a];                       // ✓ можна: a годиться як константний вираз

const int b = std::atoi(argv[1]); // теж const — але значення з'явиться в рантаймі
int arr2[b];                      // ✗ не можна
```

Обидві змінні однаково незмінні. Але тільки перша придатна там, де мові потрібне значення на етапі компіляції. Ця напівпридатність — історична: `const` у C++ успадкував роль «типізованої заміни макросу `#define`», тому цілочислові сталі з константним ініціалізатором працюють як константні вирази, а решта — ні. Слово, яке каже саме «обчислюється на компіляції», — це `constexpr` (див. [обчислення на етапі компіляції](book:programming/constexpr)); застосований до змінної, він до того ж робить її `const`. Зворотне неправда: `const` про час обчислення не каже нічого.

Із тим самим спадком пов'язана ще одна тонкість, яка щодня рятує заголовки. У C++ (на відміну від C) змінна рівня простору імен, оголошена `const`, за замовчуванням має **внутрішнє зв'язування** — тобто в кожній одиниці трансляції своя окрема копія, і [правило одного означення](book:cpp-standards/odr-and-linkage) не порушується:

```cpp
// у заголовку
const int kMax = 1024;                // своя копія в кожній .cpp — ODR цілий
inline constexpr int kMax2 = 1024;    // C++17: одна сутність на всю програму
extern const int kShared;             // явно зовнішнє зв'язування; означення — в одній .cpp
```

Побічний ефект у першого варіанта є: якщо взяти адресу `kMax` у двох різних файлах, адреси будуть різні. Коли це важливо — `inline constexpr` (з C++17) дає одну сутність на програму.

Ще одна дрібниця з тієї самої опери: `constexpr`-метод у C++11 був **неявно `const`**, і багато хто досі так думає. C++14 це прибрав (папір N3652, який заодно дозволив у `constexpr`-функціях цикли й розгалуження). Відтоді, якщо `constexpr`-метод має бути ще й `const`, це треба написати руками.

## const і переміщення: тиха ціна

Є місце, де надмірний `const` коштує швидкодії, і побачити це важко, бо код компілюється й працює правильно.

[Переміщення](book:cpp-standards/move-semantics) забирає нутрощі з об'єкта-джерела, тобто **змінює** його. А в сталий об'єкт писати не можна. Отже, сталий об'єкт не переміщується — і замість помилки ти отримуєш мовчазне копіювання:

```cpp
const std::string s = make_name();
std::vector<std::string> v;
v.push_back(std::move(s));   // копія, а не переміщення
```

`std::move(s)` дає тип `const std::string&&`. Перевантаження `push_back(std::string&&)` таке не приймає — [категорія значення](book:cpp-standards/value-categories) підходить, а константність ні. Зате підходить `push_back(const std::string&)`, і компілятор мовчки бере його. Звідси — два практичні висновки.

Перший: **не повертай значення за `const`**. Запис `const std::string name() const;` колись радили, щоб ніхто не написав `obj.name() = "x"`; ціна виявилася вищою за користь — такий результат неможливо перемістити, тож кожен виклик тягне копію.

Другий: **`const`-поле вимикає присвоєння класу**. Присвоїти сталому полю нічого не можна, тому неявний оператор присвоєння оголошується вилученим:

```cpp
struct Config {
    const std::string name;   // виглядає «правильно» й безпечно
    int retries;
};
Config a{"a", 3}, b{"b", 5};
a = b;                        // ✗ оператор присвоєння вилучено
std::vector<Config> v;
std::sort(v.begin(), v.end(), by_retries);   // ✗ sort вимагає присвоюваності
```

Тому незмінність поля майже завжди краще виражати приватним полем без сетера, ніж `const`-полем: гарантія та сама, а тип лишається повноцінним значенням (докладніше про те, які операції треба тримати живими — у [правилі п'яти й правилі нуля](book:cpp-standards/rule-of-five-zero)).

## const вірусний — і це його спосіб працювати

Остання властивість, з якою стикається кожен, хто пробує додати `const` у наявний проєкт. Щоб зробити метод `const`, треба, щоб усе, що він викликає, теж було `const`. Ті методи тягнуть наступні. Одна нижня функція, яка бере `T*` замість `const T*`, блокує весь ланцюг угору.

Це неминучий наслідок того, що `const` — обіцянка, яку перевіряють: обіцяти можна лише те, що спираєшся на такі самі обіцянки. Практичний висновок звідси один і жорсткий: **константну коректність або закладають із першого дня, або доводиться робити суцільним проходом знизу вгору**. Дописування `const` шматками зазвичай застрягає на першій же старій функції й закінчується `const_cast`-ом, який гасить симптом і зберігає хворобу.

І є ще одна ціна, про яку згадують запізно. `const` нижнього рівня в підписі входить у **манґлене ім'я** функції, тому додавання `const` до параметра-посилання в опублікованій бібліотеці — це [зламаний ABI](book:cpp-standards/abi-stability-cpp): старі об'єктні файли шукають символ, якого більше немає. Усередині проєкту, що збирається цілком, це коштує перезбірки; для бібліотеки з сумісністю — це зміна версії.

Історія самого слова пояснює, чому воно вийшло саме таким компромісом — типізованою заміною макроса і водночас позначкою «сюди не писати»; вона ж пояснює, звідки взялася різниця між C і C++ у зв'язуванні й константних виразах. Це окрема розповідь: [як народився const](book:cpp-standards/const-correctness/hist-const-origin.md).

## Що зрештою дає const

`const` слабший, ніж незмінність, і плутати їх — головна причина розчарувань. Незмінний об'єкт не змінюється **ніколи й ні для кого**. `const`-посилання каже лише, що **крізь нього** писати не можна: той самий об'єкт в іншому місці програми може бути звичайним, і його там законно міняють, поки ти дивишся на нього крізь свої двері. Гарантія тримається не тому, що комірка захищена, а тому, що всі шляхи до неї описані в типах і компілятор ці описи звіряє.

Саме звідси й береться вся практика. Ставити `const` там, де він описує **контракт** — параметри-посилання, методи для читання, вказівники на чужі дані. Не ставити там, де він нічого нікому не обіцяє — на параметрах за значенням в оголошеннях, на результатах функцій. Пам'ятати, що він поверхневий, і тому вважати `const`-метод захистом нутрощів за вказівником не можна. І тримати в голові, що з C++11 у нього вбудована ще й обіцянка про потоки, яку клас із `mutable`-полем зобов'язаний виконати сам.
