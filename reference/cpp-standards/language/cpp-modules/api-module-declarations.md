# 📋 Синтаксис та декларації модульної системи C++20

Модульна система C++20 вводить до граматики мови набір нових ключових слів та контекстних інструкцій (`module`, `import`, `export`), які замінюють лексичну вставку препроцесора типізованою семантичною структурою. Замість неконтрольованого текстового копіювання файлів через `#include`, модулі формують строгі межі видимості символів, ізолюють макроси та встановлюють чіткі правила взаємодії між одиницями трансляції.

Нижче наведено повний формальний довідник синтаксичних конструкцій, правил експорту, видів компонування (linkage), інстанціації шаблонів, взаємодії з мовними зв'язками `extern "C"`, трансформації правила єдиного визначення (ODR), стандартних модулів C++23 та матриці видимості й досяжності типів.

## 1. Структурні форми модульних одиниць

Будь-який джерельний файл модульної програми належить до однієї з шести категорій одиниць трансляції (Translation Units). Тип одиниці визначається її початковими деклараціями та наявністю ключового слова `export`:

| Вид одиниці трансляції | Оголошення на початку файлу | Наявність `export` | Призначення |
| :--- | :--- | :--- | :--- |
| **Головний інтерфейс (Primary Interface Unit)** | `export module <name>;` | Так | Визначає ім'я модуля, експортує публічне API, породжує головний BMI |
| **Інтерфейсний розділ (Interface Partition)** | `export module <name>:<part>;` | Так | Частина інтерфейсу модуля, обов'язково реекспортується головним інтерфейсом |
| **Розділ реалізації (Internal Partition)** | `module <name>:<part>;` | Ні | Внутрішній допоміжний код модуля, доступний лише іншим розділам цього ж модуля |
| **Одиниця реалізації (Implementation Unit)** | `module <name>;` | Ні | Реалізація функцій і методів модуля без зміни бінарного інтерфейсу |
| **Глобальний фрагмент (Global Module Fragment)** | `module;` перед `export module` | Ні | Ізольоване підключення застарілих C-заголовків без витоку макросів |
| **Приватний фрагмент (Private Module Fragment)** | `module :private;` у хвості інтерфейсу | Ні | Локалізація коду реалізації в єдиному файлі інтерфейсу без зміни BMI |

### Правила іменування модулів та розділів

Ім'я модуля (`<name>`) складається з одного або кількох валідних C++ ідентифікаторів, розділених символом крапки. Крапка не несе жодного семантичного навантаження для компілятора — вона слугує візуальним маркером логічної ієрархії для людини:

```cpp
export module engine.graphics.vulkan;
```

З точки зору компілятора та компонувальника `engine.graphics.vulkan` — це єдиний плоский ідентифікатор. Він не створює простору імен `engine::graphics::vulkan`, не відображається на каталоги файлової системи й не надає автоматичного доступу до символів гіпотетичного модуля `engine.graphics`.

Розділ модуля позначається двокрапкою після імені модуля (`<module_name>:<partition_name>`):

```cpp
export module engine:render_core; // Інтерфейсний розділ render_core модуля engine
module engine:memory_pool;        // Внутрішній розділ пам'яті модуля engine
```

Ім'я розділу належить виключно своєму модулю. За межами модуля `engine` розділ `:render_core` імпортувати неможливо — клієнти завжди підключають весь модуль директивою `import engine;`.

## 2. Специфікатор експорту `export`

Специфікатор `export` повідомляє компілятору, що оголошена сутність стає частиною публічного інтерфейсу модуля і потрапляє до скомпільованого бінарного дерева інтерфейсу (BMI). 

Специфікатор `export` дозволено застосовувати виключно в інтерфейсних одиницях модулів (головному інтерфейсі або інтерфейсних розділах) і лише у глобальній області видимості або всередині просторів імен. Заборонено ставити `export` всередині тіл функцій, методів, класів або блоків локальних змінних.

### Дозволені форми та синтаксичні конструкції експорту

#### 1. Окреме експортне оголошення:
Ключове слово `export` ставиться безпосередньо перед оголошенням функції, класу, структури, перечислення, псевдоніма типу або константи:
```cpp
export void compute_hash(std::span<const std::byte> data);
export class Matrix;
export enum class StatusCode { Ok, Error, Timeout };
export using ByteVector = std::vector<std::byte>;
export constexpr double PI = 3.141592653589793;
```

#### 2. Блоковий експорт:
Коли потрібно експортувати групу споріднених функцій чи типів, їх можна об'єднати у фігурні дужки після ключового слова `export`. Це не створює нової області видимості:
```cpp
export {
    void system_init();
    void system_shutdown();
    struct ConfigOptions {
        int worker_threads{4};
        bool verbose{false};
    };
}
```

#### 3. Експорт простору імен:
Якщо `export` розміщено перед декларацією простору імен, усі сутності, оголошені всередині цього блоку, автоматично стають експортованими:
```cpp
export namespace math::linear {
    struct Vector2 { double x, y; };
    double dot_product(Vector2 a, Vector2 b);
}
```
Якщо простір імен уже був відкритий без `export`, а згодом відкривається з `export`, експортуються лише ті оголошення, що з'явилися в експортованому блоці.

#### 4. Експорт шаблонів і концептів:
Усі параметризовані конструкції та концепти C++20 експортуються разом зі своїми визначеннями, оскільки компілятору споживача потрібне повне синтаксичне дерево для інстанціації:
```cpp
export template <typename T>
concept Serializable = requires(T a) {
    { a.serialize() } -> std::same_as<std::string>;
};

export template <Serializable T>
class MessageQueue {
public:
    void push(T msg);
    T pop();
};
```

### Заборони та обмеження експорту

Стандарт C++20 накладає строгі заборони на використання `export` з сутностями, які мають локальну або внутрішню природу:

1. **Сутності з внутрішнім компонуванням (Internal Linkage)**:
   - Заборонено експортувати змінні та функції, оголошені зі специфікатором `static`.
   - Заборонено експортувати типи та функції, розміщені в анонімних просторах імен (`namespace { ... }`).
   - Спроба написати `export static void helper();` або `export namespace { class Hidden; }` викликає помилку компіляції.
2. **Директиви використання просторів імен (Using Directives)**:
   - Заборонено експортувати анонімне втягування цілих просторів імен: `export using namespace std;` є синтаксичною помилкою.
   - Дозволено експортувати конкретні псевдоніми та using-оголошення: `export using std::string;` або `export using MyInt = int;`.
3. **Визначення спеціалізацій для неекспортованих первинних шаблонів**.

## 3. Інструкції імпорту `import`

Директива `import` завантажує попередньо згенерований бінарний інтерфейс модуля (BMI) у поточну одиницю трансляції без виконання текстового препроцесингу.

```cpp
import <module-name>;
```

### Семантичні форми імпорту

| Конструкція | Де дозволена | Семантика для поточної одиниці та споживачів |
| :--- | :--- | :--- |
| `import A;` | Будь-яка одиниця | Імпортує модуль `A` для використання лише в поточному файлі |
| `export import A;` | Інтерфейсні одиниці | **Транзитивний реекспорт**: будь-хто, хто підключає поточний модуль, автоматично отримує весь інтерфейс `A` |
| `import :part;` | Всередині модуля | Імпортує розділ `:part` цього ж модуля за відносним ідентифікатором |
| `export import :part;` | Головний інтерфейс | Реекспортує інтерфейсний розділ як частину публічного API модуля |
| `import <header>;` | Будь-яка одиниця | **Header Unit**: підключає системний заголовок як бінарний модуль з експортом макросів |
| `import "header.h";` | Будь-яка одиниця | **Header Unit**: підключає локальний заголовок як бінарний модуль з експортом макросів |

### Правила розташування інструкцій `import`

- Усі директиви `import` мають бути розміщені на початку одиниці трансляції, безпосередньо після декларації `module;` або `export module / module`.
- Заборонено розміщувати `import` всередині тіл функцій, блоків `namespace` або описів класів.
- Циклічні залежності заборонені: модуль `A` не може імпортувати модуль `B`, якщо `B` прямо чи опосередковано імпортує `A`. Аналогічно, розділи одного модуля не можуть утворювати циклічні кільця імпорту.

## 4. Види компонування в C++20 (Linkage Model)

Модулі додають до системи типів новий рівень зв'язування символів — **модульне компонування (Module Linkage)**. Тепер мова розрізняє чотири види компонування:

| Вид компонування (Linkage) | Де оголошено сутність | Видимість у межах поточного файлу | Видимість в інших файлах того ж модуля | Доступність за межами модуля (у клієнтів) |
| :--- | :--- | :--- | :--- | :--- |
| **No Linkage (Без компонування)** | Локальні змінні та типи всередині функцій | Так | Ні | Ні |
| **Internal Linkage (Внутрішнє)** | `static`-функції, змінні, анонімні `namespace` | Так | Ні | Ні |
| **Module Linkage (Модульне)** | Неекспортовані сутності глобального простору або просторів імен модуля | Так | **Так** (через спільну сферу модуля або внутрішні розділи) | **Ні** (повна ізоляція від клієнтів) |
| **External Linkage (Зовнішнє)** | Сутності, позначені ключовим словом `export` | Так | Так | **Так** (через `import`) |

```cpp
export module cryptography;

// 1. Internal Linkage: унікальна для цього файлу, не конфліктує з іншими static-функціями
static void mix_entropy(uint64_t* state);

// 2. Module Linkage: доступна всім файлам модуля cryptography, але невидима для імпортерів
void generate_prime_candidate(mpz_t out);

// 3. External Linkage: публічний контракт модуля для зовнішніх споживачів
export void generate_rsa_keypair(PublicKey* pub, PrivateKey* priv);
```

### Взаємодія з `extern "C"` та зв'язками інших мов

Сутності, оголошені всередині блоків зв'язку `extern "C"`, за замовчуванням мають зовнішнє компонування C. Проте для того, щоб вони стали видимими клієнтам модуля, їх необхідно явно супроводити ключовим словом `export`:

```cpp
export module c_api_wrapper;

export extern "C" {
    void legacy_driver_init(int channel);
    int legacy_driver_read(void* buffer, size_t max_len);
}
```

## 5. Трансформація ODR та вбудованих функцій (Inline Functions)

У класичному C++ із заголовковими файлами правило єдиного визначення (ODR) спиралося на слабкі символи (weak symbols / COMDAT sections). Якщо функція або метод класу були позначені як `inline`, або якщо шаблон інстанціювався в десяти різних файлах `.cpp`, компілятор дублював машинний код у кожному об'єктному файлі. На етапі лінкування компонувальник вибирав одну довільну копію та викидав решту (COMDAT folding).

У модулях C++20 семантика ODR зазнала кардинальної оптимізації:

1. **Функції в інтерфейсі без `inline`**: якщо функція експортується з інтерфейсу модуля і має тіло без специфікатора `inline`, вона має сильне зовнішнє компонування. Компілятор зобов'язаний згенерувати машинний код рівно в одному об'єктному файлі інтерфейсу. Споживачі модуля отримують лише виклик символу без дублювання тіла.
2. **Функції зі специфікатором `inline`**: залишаються доступними для вбудовування компілятором у місці виклику (inlining). Тіло такої функції серіалізується в BMI, щоб оптимізатор зміг підставити його безпосередньо в код клієнта.
3. **Ізоляція внутрішніх визначень**: дві різні бібліотеки можуть мати неекспортовані функції з абсолютно однаковими іменами та сигнатурами у своїх модулях. Завдяки модульному компонуванню (Module Linkage) ці символи спотворюються компілятором (Name Mangling) з додаванням ідентифікатора модуля, що на 100% унеможливлює ODR-конфлікти на етапі компонування.

## 6. Матриця: Видимість (Visibility) проти Досяжності (Reachability)

Розділення понять видимості та досяжності є ключовим семантичним фундаментом модулів C++20:

- **Видимість імені (Name Visibility)** — властивість ідентифікатора бути знайденим під час лексичного пошуку імен (Name Lookup), як-от пряме написання `TypeName var;`.
- **Досяжність типу (Type Reachability)** — наявність у транслятора повної семантичної інформації про тип (розмір, вирівнювання полів, таблиці віртуальних методів, визначення конструкторів і деструкторів), що дозволяє компілятору безпечно виділяти пам'ять, генерувати виклики методів або інстанціювати шаблони над цим типом.

| Операція над сутністю | Неекспортований тип із модуля | Експортований тип через звичайний `import` | Експортований тип через `export import` |
| :--- | :--- | :--- | :--- |
| Оголошення змінної за іменем: `MyType x;` | ❌ Невидимий (Помилка компіляції) | ✅ Видимий | ✅ Видимий |
| Отримання через фабрику: `auto x = make_obj();` | ✅ **Досяжний** | ✅ Досяжний | ✅ Досяжний |
| Виклик методів: `x.process();` | ✅ **Досяжний** | ✅ Досяжний | ✅ Досяжний |
| Визначення розміру: `sizeof(x)` | ✅ **Досяжний** | ✅ Досяжний | ✅ Досяжний |
| Інстанціація контейнера: `std::vector<decltype(x)>` | ✅ **Досяжний** | ✅ Досяжний | ✅ Досяжний |
| Пошук функцій через ADL в асоційованому просторі | ✅ **Працює** | ✅ Працює | ✅ Працює |

### Розбір поведінки компілятора на прикладі

Розглянемо модуль бази даних, який навмисно приховує назву внутрішнього дескриптора транзакції, але дозволяє повноцінно працювати з ним через фабричний інтерфейс:

```cpp
// --- Файл transaction_engine.cppm ---
export module transaction_engine;

// Тип НЕ експортується: його назва TransactionContext відсутня в таблиці імен споживача
struct TransactionContext {
    uint64_t tx_id{0};
    bool is_active{true};

    void commit() { is_active = false; }
    void rollback() { is_active = false; }
};

// Експортована функція повертає тип за значенням
export TransactionContext begin_transaction(uint64_t id) {
    return TransactionContext{id, true};
}
```

У клієнтському коді споживач взаємодіє з типом через механізм виведення типів `auto`:

```cpp
// --- Файл client.cpp ---
import transaction_engine;

void run_client() {
    // TransactionContext ctx; // ❌ ПОМИЛКА: ідентифікатор TransactionContext невидимий (Not Visible)

    auto ctx = begin_transaction(1001); // ✅ ДОЗВОЛЕНО: тип TransactionContext досяжний (Reachable)
    ctx.commit();                       // ✅ ДОЗВОЛЕНО: компілятор знає макет класу та зміщення методу commit
    
    constexpr size_t ctx_sz = sizeof(ctx); // ✅ ДОЗВОЛЕНО: повний розмір структури відомий із BMI
}
```

## 7. Модулі стандартної бібліотеки C++23: `std` та `std.compat`

Стандарт C++23 остаточно завершив перехід стандартної бібліотеки на модульну архітектуру, запропонувавши два стандартні іменовані модулі:

### 1. Модуль `std` (`import std;`)
Імпортує абсолютно всі типи, функції, шаблони та класи стандартної бібліотеки C++ (від `<vector>`, `<string>`, `<algorithm>` до `<ranges>`, `<chrono>`, `<thread>` та `<print>`) виключно в межах простору імен `std`. Жодні C-символи у глобальний простір імен не експортуються.

```cpp
import std;

int main() {
    std::vector<std::string> names{"Alice", "Bob", "Charlie"};
    for (const auto& name : names) {
        std::println("Hello, {}!", name);
    }
}
```

### 2. Модуль сумісності `std.compat` (`import std.compat;`)
Імпортує весь вміст модуля `std`, а також додатково експортує глобальні C-функції та типи стандартної бібліотеки C у глобальний простір імен (`::printf`, `::size_t`, `::memcpy`, `::sin`, `::uint32_t`).

```cpp
import std.compat;

int main() {
    printf("Сумісність зі старим кодом C без префікса std::\n");
}
```

### Правило спільного вживання з `#include`
Якщо в одній одиниці трансляції необхідно одночасно використовувати старий заголовок (через `#include`) та модуль `import std;`, інструкція `import std;` обов'язково повинна стояти перед підключенням заголовка, щоб запобігти спотворенню синтаксичного дерева модуля локальними препроцесорними макросами цього заголовка.

## 8. Приватний фрагмент модуля (`module :private;`)

Приватний фрагмент модуля — це спеціальна мовна конструкція, яка дозволяє розмістити реалізацію функцій та закритих деталей класу в одному фізичному файлі з інтерфейсом, повністю виключаючи цей код із генерованого бінарного інтерфейсу (BMI):

```cpp
export module secure_enclave;

export class Enclave {
public:
    Enclave();
    ~Enclave();
    void execute_secure(int command);
private:
    void decrypt_hardware_keys();
};

// Початок приватного фрагмента
module :private;

Enclave::Enclave() = default;
Enclave::~Enclave() = default;

void Enclave::execute_secure(int command) {
    decrypt_hardware_keys();
    // Виконання команди
}

void Enclave::decrypt_hardware_keys() {
    // Складні асемблерні інструкції та взаємодія з криптопроцесором
}
```

### Інженерні наслідки використання приватного фрагмента

- Будь-які правки алгоритмів, розташованих нижче маркера `module :private;`, **не змінюють бінарний інтерфейс (BMI)** модуля. Клієнти, які імпортують модуль, не вимагають перекомпіляції під час зміни реалізації у приватному фрагменті.
- Модуль, що містить приватний фрагмент, зобов'язаний бути **єдиною** одиницею трансляції цього модуля. Він не може мати розділів (partitions) чи окремих допоміжних `.cpp` файлів реалізації.
