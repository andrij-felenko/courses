# 📋 Специфікація розкладки пам'яті: Itanium C++ ABI та MSVC

Стандарт ISO C++ навмисно не визначає точного двійкового розташування полів, віртуальних покажчиків та підоб'єктів у пам'яті, залишаючи це на розсуд двійкового інтерфейсу прикладних програм (англ. *Application Binary Interface*, ABI). У сучасній індустрії програмного забезпечення закріпилися дві основні моделі розкладки:

1. **Itanium C++ ABI:** промисловий стандарт, розроблений консорціумом виробників (Intel, HP, SGI, Red Hat). Прийнятий компіляторами GCC, Clang, Intel oneAPI на платформах Linux, macOS, iOS, Android, FreeBSD та сучасних вбудованих POSIX-системах.
2. **Microsoft Visual C++ ABI (MSVC ABI):** стандарт компілятора MSVC для операційної системи Microsoft Windows (архітектури x86, x64, ARM64).

Нижче наведено формальну довідкову специфікацію правил обчислення розмірів, вирівнювання, зміщень підоб'єктів, структури віртуальних таблиць (vtable), таблиць таблиць конструювання (VTT), покажчиків на члени (pointers-to-members), обробки винятків та таблиць віртуальних баз (vbtbl).

---

## 1. Термінологія та базові величини

Під час розрахунку геометрії класу компіляторний бекенд ABI оперує такими формальними метриками:

| Величина ABI | Опис | Формула / Правило |
| :--- | :--- | :--- |
| `sizeof(T)` | Повний розмір типу в байтах, включно з вирівнюванням і віртуальними базами | Кратний `alignof(T)` |
| `alignof(T)` | Вирівнювання типу в байтах | `max(alignof(B_i), alignof(m_j))` |
| `nvsize(T)` | Невіртуальний розмір (розмір без віртуальних баз) | Обчислюється до додавання віртуальних баз |
| `nvalign(T)` | Невіртуальне вирівнювання | `max(alignof(DirectNonVirtualBases), alignof(Members))` |
| `dsize(T)` | Розмір даних (без завершального padding) | `nvsize(T) - tail_padding(T)` |
| `offset_to_top` | Зсув від поточного `vptr` до початку найбільш похідного об'єкта | Від'ємне або нульове число (`<= 0`) |
| `vbase_offset` | Зсув від поточного `vptr` до підоб'єкта віртуальної бази | Додатне або від'ємне число |

## 2. Алгоритм розкладки в Itanium C++ ABI

Специфікація Itanium C++ ABI будує об'єкт у два послідовні проходи:
- **Фаза I:** розміщення невіртуальної частини об'єкта (Direct Non-Virtual Bases та нестатичні члени класу).
- **Фаза II:** розміщення віртуальних баз (Virtual Base Subobjects).

```
Схема фаз компонування Itanium C++ ABI:
┌─────────────────────────────────────────────────────────────┐
│ 1. Вибір Primary Base Class (первинної бази)                │
│    └─ Успадковує offset 0, ділить vptr із Derived           │
├─────────────────────────────────────────────────────────────┤
│ 2. Розміщення вторинних невіртуальних баз                   │
│    └─ Зсув = roundup(поточний_зсув, alignof(Base))          │
├─────────────────────────────────────────────────────────────┤
│ 3. Розміщення власних нестатичних членів даних              │
│    └─ Можливе повторне використання tail padding баз        │
├─────────────────────────────────────────────────────────────┤
│ 4. Фіксація nvsize(T) та nvalign(T)                         │
├─────────────────────────────────────────────────────────────┤
│ 5. Розміщення спільних віртуальних баз (Virtual Bases)      │
│    └─ Порядок: pre-order depth-first обхід графа            │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. Вибір первинної бази (Primary Base Class)

Первинна база — це базовий клас, чий покажчик на віртуальну таблицю (`vptr`) стає спільним `vptr` для похідного класу за нульовим зміщенням (offset 0).

**Правила вибору первинної бази:**
1. Якщо клас має одну або більше прямих невіртуальних поліморфних баз (баз із віртуальними функціями), перша з них за порядком оголошення обирається як **Primary Base**.
2. Якщо клас не має невіртуальних поліморфних баз, але успадковує **віртуальну поліморфну базу**, компілятор може призначити її віртуальною первинною базою (Virtual Primary Base), якщо це не призводить до колізій адрес підоб'єктів одного типу.
3. Якщо поліморфних баз немає, але клас сам оголошує нову віртуальну функцію, клас стає поліморфним і виділяє власний новий `vptr` за зміщенням 0.
4. Якщо поліморфізму немає взагалі, перша невіртуальна база розміщується за зміщенням 0 (з урахуванням оптимізації порожньої бази EBO).

### 2.2. Повторне використання завершального padding (Tail Padding Reuse)

Якщо базовий клас має невіртуальний розмір `nvsize(Base) = 12` байтів, але через вимогу вирівнювання `alignof(Base) = 8` його повний `sizeof(Base) = 16` байтів, останні 4 байти є «завершальним доповненням» (англ. *tail padding*).

В Itanium ABI власні поля похідного класу або наступні порожні бази **можуть бути розміщені всередині tail padding попередньої бази**, за умови, що це не порушує правила унікальності адрес. Це дозволяє суттєво зекономити пам'ять:

```cpp
struct Base {
    virtual ~Base() = default; // vptr: 8 байтів (зсув 0..7)
    int32_t val;               // 4 байти (зсув 8..11)
    // 4 байти tail padding (зсув 12..15)
};

struct Derived : public Base {
    int32_t extra; // Розміщується за зсувом 12 всередині tail padding Base!
    // sizeof(Derived) залишається 16 байтів замість 24!
};
```

### 2.3. Майже порожні віртуальні бази (Nearly Empty Virtual Bases)

Клас вважається **майже порожнім** (англ. *nearly empty*), якщо він задовольняє такі умови:
- Не містить нестатичних членів даних (окрім нульових бітових полів).
- Має віртуальний деструктор або віртуальні методи (тобто містить рівно один `vptr`).
- Не має невіртуальних баз або має лише порожні невіртуальні бази.
- Не має віртуальних баз або має лише порожні віртуальні бази.

Такі класи в Itanium C++ ABI оптимізуються спеціальним чином: якщо майже порожній клас є віртуальною базою, компілятор може сумістити його `vptr` із первинною базою нащадка, мінімізуючи накладні витрати пам'яті.

## 3. Анатомія віртуальної таблиці (vtable) за Itanium C++ ABI

У системі з множинним та віртуальним спадкуванням віртуальна таблиця є не просто масивом покажчиків на функції, а складним композитним масивом із **від'ємними префіксами**.

Вказівник `vptr` усередині об'єкта завжди вказує на **точку прив'язки** (Address Point) — нульовий індекс, де починається перший віртуальний метод.

```
Структура префіксів та слотів vtable у пам'яті:
                   ┌──────────────────────────────────────────────┐
  vptr - 32 байтів │ [-4] vbase_offset для 2-ї віртуальної бази   │
                   ├──────────────────────────────────────────────┤
  vptr - 24 байти  │ [-3] vbase_offset для 1-ї віртуальної бази   │
                   ├──────────────────────────────────────────────┤
  vptr - 16 байтів │ [-2] offset_to_top (зсув до початку об'єкта) │
                   ├──────────────────────────────────────────────┤
  vptr - 8 байтів  │ [-1] RTTI typeinfo pointer (&typeinfo)       │
 ══════════════════╪══════════════════════════════════════════════╡ <── ТОЧКА ПРИВ'ЯЗКИ (vptr)
  vptr + 0 байтів  │ [ 0] virtual void f() (вхідна точка)         │
                   ├──────────────────────────────────────────────┤
  vptr + 8 байтів  │ [ 1] virtual void g()                        │
                   ├──────────────────────────────────────────────┤
  vptr + 16 байтів │ [ 2] virtual ~Destructor() (complete)        │
                   ├──────────────────────────────────────────────┤
  vptr + 24 байти  │ [ 3] virtual ~Destructor() (deleting)        │
                   └──────────────────────────────────────────────┘
```

### 3.1. Опис полів префікса

- **`vbase_offset` (Virtual Base Offset):** зміщення в байтах від поточного `vptr` до початку відповідного підоб'єкта віртуальної бази. Якщо клас має три віртуальні бази, у префіксі таблиці виділяються три окремі слоти (`[-5]`, `[-4]`, `[-3]`).
- **`offset_to_top`:** відстань у байтах від адреси поточного `vptr` до абсолютного початку найбільш похідного об'єкта (`Most Derived Object`). Для первинної бази це завжди `0`. Для вторинних баз це від'ємне число (наприклад, `-16`), яке використовується оператором `dynamic_cast` для знаходження кореня об'єкта.
- **`RTTI typeinfo pointer`:** адреса глобального константного дескриптора `std::type_info`, що описує динамічний тип об'єкта.
- **Деструктори (Complete vs Deleting):** Itanium ABI генерує дві версії віртуального деструктора:
  1. *Complete object destructor (`D1`):* знищує поля та підоб'єкти без виклику `operator delete`.
  2. *Deleting destructor (`D0`):* знищує об'єкт і автоматично викликає `operator delete(this)`.

## 4. Таблиця таблиць віртуальних методів (VTT)

При віртуальному спадкуванні виникає фундаментальна проблема конструювання:
- Під час роботи конструктора проміжної бази `VirtualAudioIn` віртуальні виклики повинні резолвитися у версії методів `VirtualAudioIn`.
- Проте зсув до спільної віртуальної бази `VDevice` має відповідати геометричній розкладці кінцевого об'єкта `AudioDuplexV`.
- Звичайна статична `vtable` класу `VirtualAudioIn` розрахована на випадок, коли `VirtualAudioIn` є самостійним об'єктом, де `VDevice` лежить за іншим зсувом.

Для розв'язання цієї проблеми компілятор генерує **Construction Virtual Tables** (таблиці конструювання), а адреси цих таблиць передаються через спеціальний масив — **VTT** (Virtual Table Table).

```
Структура VTT для AudioDuplexV:
┌──────────┬────────────────────────────────────────────────────────────────────────┐
│ Індекс   │ Вміст покажчика                                                        │
├──────────┼────────────────────────────────────────────────────────────────────────┤
│ VTT[0]   │ Головна vtable повного об'єкта AudioDuplexV                            │
├──────────┼────────────────────────────────────────────────────────────────────────┤
│ VTT[1]   │ Construction vtable для підоб'єкта VirtualAudioIn усередині AudioDuplexV│
├──────────┼────────────────────────────────────────────────────────────────────────┤
│ VTT[2]   │ Вторинна Construction vtable для віртуальної бази VirtualAudioIn       │
├──────────┼────────────────────────────────────────────────────────────────────────┤
│ VTT[3]   │ Construction vtable для підоб'єкта VirtualAudioOut усередині AudioDuplexV│
├──────────┼────────────────────────────────────────────────────────────────────────┤
│ VTT[4]   │ Вторинна Construction vtable для віртуальної бази VirtualAudioOut      │
└──────────┴────────────────────────────────────────────────────────────────────────┘
```

### 4.1. Вкладені під-VTT (Sub-VTTs)

Якщо ієрархія має кілька рівнів віртуального спадкування (наприклад, `Base` -> `Mid1 : virtual Base` -> `Mid2 : virtual Mid1` -> `Derived`), структура VTT стає ієрархічною. Для кожного проміжного класу, що сам містить віртуальні бази, у головному масиві VTT виділяється послідовний блок покажчиків — **sub-VTT**, адреса початку якого передається конструктору відповідного рівня.

**Сигнатури згенерованих конструкторів:**
1. `AudioDuplexV::AudioDuplexV(AudioDuplexV* this)` — конструктор повного об'єкта (ініціалізує віртуальні бази та передає вказівник на свій VTT усім вкладеним базам).
2. `VirtualAudioIn::VirtualAudioIn(VirtualAudioIn* this, const void* const* vtt)` — конструктор підоб'єкта (отримує VTT від батька і не ініціалізує віртуальні бази самостійно).

## 5. Алгоритм виконання runtime dynamic_cast (__dynamic_cast)

У стандартній бібліотеці C++ (libcxxabi для Clang, libsupc++ для GCC) операція `dynamic_cast` для поліморфних об'єктів транслюється у виклик низькорівневої C-функції середовища виконання:

```cpp
extern "C" void* __dynamic_cast(
    const void* sub,                  // Вказівник на вихідний підоб'єкт
    const __class_type_info* src,     // Статичний тип вихідного покажчика
    const __class_type_info* dst,     // Цільовий тип приведення
    std::ptrdiff_t src2dst_offset     // Статична підказка зсуву (-1, якщо невідомо)
);
```

### 5.1. Покроковий алгоритм роботи __dynamic_cast:

1. **Перевірка на nullptr:** Якщо `sub == nullptr`, функція негайно повертає `nullptr`.
2. **Отримання повного об'єкта:** За допомогою `vptr` вихідного об'єкта `sub` читається поле `offset_to_top` (`vtable[-2]`). Обчислюється адреса найбільш похідного об'єкта:
   ```cpp
   const void* complete_object = static_cast<const char*>(sub) + offset_to_top;
   ```
3. **Отримання RTTI повного типу:** За адресою `vtable[-1]` зчитується `typeinfo` найбільш похідного об'єкта (`complete_typeinfo`).
4. **Співпадіння типів:** Якщо `complete_typeinfo == dst`, приведення є простим downcast до повного типу; функція повертає `complete_object`.
5. **Обхід графа успадкування:** Середовище виконання рекурсивно обходить дерево підоб'єктів `complete_typeinfo`:
   - Знаходить усі входження підоб'єкта типу `dst`.
   - Перевіряє права доступу (`public` vs `private`/`protected`).
   - Перевіряє неоднозначність (якщо цільовий тип `dst` досяжний кількома різними шляхами і не є віртуальною базою, виникає неоднозначність, і функція повертає `nullptr`).
6. **Повернення адреси:** Якщо знайдено рівно один валідний публічний шлях до `dst`, повертається скоригована адреса знайденого підоб'єкта.

## 6. Двійковий інтерфейс покажчиків на члени (Pointers-to-Members)

Одним із найскладніших аспектів ABI є двійкове представлення покажчиків на члени класів (`void (T::*method)()`), розмір яких суттєво різниться залежно від моделі спадкування.

### 6.1. Itanium C++ ABI

В Itanium ABI покажчик на метод класу завжди має фіксований розмір **16 байтів** (на 64-бітній платформі) і складається зі структури з двох 64-бітних слів:

```cpp
struct ItaniumMemberFunctionPointer {
    std::uintptr_t ptr;  // Адреса невіртуальної функції АБО зсув у vtable + 1
    std::ptrdiff_t adj;  // Статичний зсув вказівника this
};
```

- Якщо молодший біт `ptr` дорівнює `0`: метод невіртуальний; `ptr` містить пряму адресу функції в пам'яті.
- Якщо молодший біт `ptr` дорівнює `1`: метод віртуальний; `ptr - 1` містить байтовий зсув у віртуальній таблиці.
- Поле `adj` містить зміщення, яке процесор додає до вказівника `this` перед викликом (pointer adjustment).

### 6.2. MSVC ABI

У компіляторі MSVC розмір покажчика на член класу динамічно змінюється залежно від складності ієрархії:
- **Одиночне спадкування (Single Inheritance):** 8 байтів (лише адреса функції).
- **Множинне спадкування (Multiple Inheritance):** 16 байтів (адреса функції + зсув `this`).
- **Віртуальне спадкування (Virtual Inheritance):** 24 байти (адреса функції + зсув `this` + зсув у таблиці `vbtbl`).
- **Невідоме спадкування (Unspecified Inheritance, прапорець `/vmg`):** 32 байти.

Ця різниця розмірів робить неможливим прямий обмін покажчиками на методи між модулями з різними налаштуваннями моделі спадкування в MSVC.

## 7. Взаємодія з механізмом обробки винятків (Exceptions ABI)

Коли в C++ викидається виняток (`throw Derived()`), обробник `catch` може перехоплювати його за посиланням на одну з базових структур (`catch (const Base& b)`).

У множинному та віртуальному спадкуванні адреса `Derived*` не обов'язково збігається з адресою `Base*`. Двійковий інтерфейс розмотування стека (Personality Routine за стандартом Itanium ABI) розв'язує цю задачу через дескриптор типів:

1. Метадані RTTI кожного класу містять масив структур `__base_class_type_info`:
   ```cpp
   struct __base_class_type_info {
       const __class_type_info* base_type; // Дескриптор базового типу
       long offset_flags;                  // Прапорці доступу та зміщення
   };
   ```
2. Поле `offset_flags` кодує:
   - Молодші 8 бітів: прапорці публічності та віртуальності (`is_virtual`, `is_public`).
   - Старші 56 бітів: статичний зсув підоб'єкта (для невіртуальних баз) або зсув до відповідного запису у `vtable` (для віртуальних баз).
3. Під час пошуку відповідного блоку `catch` функція `__gxx_personality_v0` зчитує ці зміщення, динамічно коригує адресу винятку і передає у блок `catch` правильний вказівник на підоб'єкт `Base`.

## 8. Специфікація розкладки Microsoft Visual C++ (MSVC ABI)

Компілятор Microsoft Visual C++ використовує принципово іншу модель для віртуального спадкування:
- **`vfptr` (Virtual Function Table Pointer):** вказівник на таблицю віртуальних функцій (`vftable`).
- **`vbptr` (Virtual Base Table Pointer):** окремий додатковий вказівник на таблицю зміщень віртуальних баз (`vbtbl`).

Замість розміщення `vbase_offset` у префіксі віртуальної таблиці, MSVC виділяє під `vbptr` окремі 8 байтів у кожному підоб'єкті, що має віртуальні бази.

```
Структура пам'яті за MSVC ABI:
┌─────────────────────────────────────────────────────────────┐
│ 1. vfptr (8 B) -> vftable (таблиця віртуальних функцій)     │
├─────────────────────────────────────────────────────────────┤
│ 2. vbptr (8 B) -> vbtbl (таблиця зсувів до віртуальних баз) │
├─────────────────────────────────────────────────────────────┤
│ 3. Власні поля даних невіртуального підоб'єкта              │
├─────────────────────────────────────────────────────────────┤
│ 4. Спільний підоб'єкт віртуальної бази (Virtual Base)       │
│    └─ Містить власний vfptr та поля даних                   │
└─────────────────────────────────────────────────────────────┘
```

### 8.1. Структура таблиці віртуальних баз (vbtbl) у MSVC

Таблиця `vbtbl` являє собою масив 32-бітних цілих чисел зі знаком (`int32_t`):
- `vbtbl[0]` = зміщення від адреси `vbptr` до початку підоб'єкта, що містить цей `vbptr` (зазвичай `0` або від'ємне число).
- `vbtbl[1]` = зміщення від адреси `vbptr` до 1-ї віртуальної бази.
- `vbtbl[2]` = зміщення від адреси `vbptr` до 2-ї віртуальної бази.

**Механізм доступу до віртуальної бази в MSVC (x64):**
```cpp
// Псевдокод згенерованого доступу до віртуальної бази в MSVC:
char* vbptr_addr = reinterpret_cast<char*>(this) + vbptr_offset;
int32_t* vbtbl = *reinterpret_cast<int32_t**>(vbptr_addr);
int32_t offset_to_vbase = vbtbl[1];
Base* vbase = reinterpret_cast<Base*>(vbptr_addr + offset_to_vbase);
```

### 8.2. Прапорець is_most_derived у конструкторах MSVC

На відміну від Itanium ABI, де використовується масив VTT, MSVC передає в конструктори додатковий прихований цілочисельний аргумент `int is_most_derived`:
- `is_most_derived == 1` — конструктор викликається для створення повного об'єкта. Він безпосередньо ініціалізує всі віртуальні бази та встановлює всі `vbptr`.
- `is_most_derived == 0` — конструктор викликається як проміжний підоб'єкт. Виклики конструкторів віртуальних баз пропускаються через умовний перехід (`if (!is_most_derived) skip;`).

## 9. Практичний розрахунок розкладки: комплексний приклад

Розглянемо покроковий розрахунок пам'яті для складної ієрархії, що поєднує невіртуальне та віртуальне спадкування:

```cpp
struct CommonBase {
    virtual void base_fn();
    int32_t base_id; // 4 байти
};

struct InterfaceA : virtual public CommonBase {
    virtual void fn_a();
    int32_t a_val;   // 4 байти
};

struct InterfaceB : virtual public CommonBase {
    virtual void fn_b();
    int32_t b_val;   // 4 байти
};

struct ConcreteCombined : public InterfaceA, public InterfaceB {
    int64_t combined_id; // 8 байтів
};
```

### 9.1. Покроковий розрахунок зміщень за Itanium ABI:

1. **Невіртуальна частина InterfaceA:**
   - Зсув `0..7`: `vptr` для `InterfaceA` (Primary Base для `ConcreteCombined`).
   - Зсув `8..11`: поле `a_val` (4 байти).
   - Зсув `12..15`: `tail padding` (4 байти для вирівнювання до 8 байтів).
   - `nvsize(InterfaceA) = 16`, `nvalign(InterfaceA) = 8`.

2. **Невіртуальна частина InterfaceB (Secondary Base):**
   - Розміщується з вирівнюванням `nvalign(InterfaceB) = 8` за зсувом `16`.
   - Зсув `16..23`: власний `vptr` для `InterfaceB`.
   - Зсув `24..27`: поле `b_val` (4 байти).
   - Зсув `28..31`: `tail padding` (4 байти).
   - `nvsize` об'єднання зріс до `32` байтів.

3. **Власні поля ConcreteCombined:**
   - Поле `combined_id` (8 байтів) вимагає вирівнювання на 8 байтів.
   - Розміщується за зсувом `32..39`.
   - Поточний `nvsize(ConcreteCombined) = 40` байтів.

4. **Розміщення спільної віртуальної бази CommonBase:**
   - Розміщується після невіртуальної частини за зсувом `40`.
   - Зсув `40..47`: `vptr` для `CommonBase`.
   - Зсув `48..51`: поле `base_id` (4 байти).
   - Зсув `52..55`: `tail padding` (4 байти для вирівнювання всього типу до `alignof = 8`).

**Підсумок розкладки:**
- Повний розмір `sizeof(ConcreteCombined) = 56` байтів.
- Об'єкт містить **три окремі `vptr`**: за зсувами `0`, `16` та `40`.
- У віртуальній таблиці `InterfaceA` запис `vbase_offset` для `CommonBase` дорівнює `+40`.
- У віртуальній таблиці `InterfaceB` запис `vbase_offset` для `CommonBase` дорівнює `+24` (бо `40 - 16 = 24`).

## 10. Зведена таблиця порівняння Itanium ABI та MSVC ABI

| Властивість | Itanium C++ ABI (GCC, Clang) | MSVC ABI (Microsoft Visual C++) |
| :--- | :--- | :--- |
| **Розміщення `vbase_offset`** | За від'ємними індексами у `vtable` | В окремій таблиці `vbtbl` |
| **Додаткові вказівники в об'єкті** | Лише один `vptr` на поліморфну базу | Окремий `vfptr` + окремий `vbptr` |
| **Розмір об'єкта з віртуальною базою** | Менший (без додаткових покажчиків) | Більший (через наявність `vbptr`) |
| **Розмір Pointer-to-Member Function** | Завжди фіксований (16 байтів) | Змінний (8 / 16 / 24 / 32 байти) |
| **Конструювання віртуальних баз** | Механізм VTT (Virtual Table Table) | Параметр `is_most_derived` (цілий прапорець) |
| **Tail Padding Reuse** | Дозволено для невіртуальних баз | Заборонено (або обмежено для POD) |
| **Деструктори у vtable** | 2 слоти: Complete (`D1`) та Deleting (`D0`) | 1 слот: метод `scalar deleting destructor` з прапорцем |
| **Коригувальні перехідники** | Adjustor Thunks (асемблерні мікрофункції) | Thunks або `[thunk]`-адаптери у vftable |

## 11. Прапорці компіляторів для діагностики розкладки

Для детального аналізу компонування класів у конкретних проектах рекомендується використовувати спеціалізовані прапорці інтроспекції компіляторів:

### 11.1. Clang / LLVM
```bash
# Дамп розкладки всіх структур і підоб'єктів
clang++ -Xclang -fdump-record-layouts -std=c++20 -c source.cpp

# Дамп структури віртуальних таблиць та VTT
clang++ -Xclang -fdump-vtable-layouts -std=c++20 -c source.cpp
```
Прапорець `-fdump-record-layouts` виводить повну ієрархічну розкладку кожного класу: невіртуальні бази, зсуви `vptr`, позиції кожного члена даних, хвостові проміжки (tail padding) та зсуви спільних віртуальних баз. Прапорець `-fdump-vtable-layouts` розкриває вміст усіх створених таблиць віртуальних методів, включно з префіксами `offset-to-top`, дескрипторами `RTTI` та масивами `VTT`.

### 11.2. GCC
```bash
# Створення текстового файлу .class з повним описом розкладки та vtable
g++ -fdump-lang-class -std=c++20 -c source.cpp
```
GCC записує структурований звіт у файл із розширенням `.class` у поточній директорії збірки. У звіті міститься повний опис порядку віртуальних баз, зсуви таблиць конструювання та кодовані імена функцій-перехідників (thunks).

### 11.3. MSVC
```cmd
# Виведення розкладки конкретного класу в консоль
cl /d1reportSingleClassLayoutAudioDuplexV /std:c++20 /c source.cpp

# Виведення розкладки всіх класів у файлі
cl /d1reportAllClassLayout /std:c++20 /c source.cpp
```
Недокументований, але широко використовуваний прапорець `/d1reportSingleClassLayout<ClassName>` виводить у консоль точне текстове дерево з позиціями `vfptr`, `vbptr`, розмірами структур і зміщеннями віртуальних баз за стандартом Microsoft C++ ABI.
