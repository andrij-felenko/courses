# ⚙️ Свій тип під `auto [a, b]`: tuple_size, tuple_element і get

Протокол `tuple_size`/`tuple_element`/`get` — єдиний спосіб віддати власний клас на розбирання тоді, коли його частини не збігаються з його полями: поля закриті, або потрібної частини взагалі немає в пам'яті і її треба обчислити. Далі — робочий приклад від початку до кінця, обидва способи написати `get`, і перелік місць, де це мовчки ламається.

## Задача

Знімок з АЦП: усередині лежить шістнадцятибітний код перетворення і мітка каналу.

```cpp
#include <cstdint>
#include <string>
#include <tuple>
#include <type_traits>
#include <utility>

namespace hw {

class Sample {
public:
    Sample(std::uint16_t code, std::string tag)
        : code_(code), tag_(std::move(tag)) {}

    double voltage() const { return code_ * (3.3 / 65535.0); }

private:
    std::uint16_t code_;
    std::string   tag_;
};

}  // namespace hw
```

Той, хто читає знімки, оперує вольтами, а не кодами: код перетворення й опорна напруга — внутрішня справа класу. Хочеться писати

```cpp
auto [u, tag] = read_sample();
```

і мати `u` одразу у вольтах. Розбирання за полями тут не годиться двічі: поля закриті (а якби й були відкриті, першим ім'ям стало б `code_`, а не напруга), і вольтів як окремого об'єкта в пам'яті просто немає — їх нізвідки взяти, крім множення. Лишається протокол.

## Три питання, три джерела відповідей

Щоб розібрати об'єкт типу `E`, компілятор мусить дізнатися три речі, і кожна має власне джерело:

- **скільки частин** — `std::tuple_size<E>::value`;
- **якого типу i-та частина** — `std::tuple_element<i, E>::type`;
- **звідки її взяти** — виклик `e.get<i>()` або `get<i>(e)`.

Перші дві відповіді — шаблони зі стандартної бібліотеки, тож їх спеціалізують у просторі `std`. Додавати до `std` нові сутності заборонено, а спеціалізувати наявний шаблон для власного типу — можна й саме так і задумано. З C++17 для цього не обов'язково відкривати сам простір: досить кваліфікованого імені.

```cpp
template <>
struct std::tuple_size<hw::Sample>
    : std::integral_constant<std::size_t, 2> {};

template <std::size_t I>
struct std::tuple_element<I, hw::Sample> {
    static_assert(I < 2, "у hw::Sample дві частини");
    using type = std::conditional_t<I == 0, double, std::string>;
};
```

Дві дрібниці тут визначають усе подальше. Перша: `tuple_element` написано **однією** частковою спеціалізацією з `conditional_t`, а не ланцюгом повних спеціалізацій на кожен індекс. Ланцюг із двох виглядає невинно, ланцюг із п'яти вже розповзається файлом, і кожна ланка може розійтися з відповідною гілкою `get` окремо від інших.

Друга: типи в `tuple_element` — **значення**, без `const` і без `&`. Варіанти для `const hw::Sample` бібліотека виводить сама: у неї є часткові спеціалізації для cv-кваліфікованих типів, які беруть `value` з некваліфікованої і навішують `const` на тип частини. Тому після цих десяти рядків `const auto& [u, tag] = s;` дасть частини типів `const double` і `const std::string` — писати для цього нічого не треба.

## Спосіб перший: шаблонний член `get`

`get` — уже не бібліотека, а ваш код, і в нього рівно одне зобов'язання: віддати те, що пообіцяв `tuple_element`. Для першої частини обіцяно `double` — отже, значення. Для другої обіцяно `std::string`, і віддати треба **посилання** на справжнє поле, інакше зв'язування дивитиметься в копію.

```cpp
// у публічній частині класу hw::Sample:

template <std::size_t I>
decltype(auto) get() & {
    static_assert(I < 2, "у hw::Sample дві частини");
    if constexpr      (I == 0) return voltage();   // double: обчислене значення
    else if constexpr (I == 1) return (tag_);      // std::string&
}

template <std::size_t I>
decltype(auto) get() const& {
    static_assert(I < 2, "у hw::Sample дві частини");
    if constexpr      (I == 0) return voltage();
    else if constexpr (I == 1) return (tag_);      // const std::string&
}

template <std::size_t I>
decltype(auto) get() && {
    static_assert(I < 2, "у hw::Sample дві частини");
    if constexpr      (I == 0) return voltage();
    else if constexpr (I == 1) return std::move(tag_);   // std::string&&
}
```

[Гілки `if constexpr`](book:cpp-standards/constexpr-if), які не спрацювали, не інстанціюються, тож `decltype(auto)` виводиться з єдиної живої гілки — і різні частини спокійно мають різні типи повернення в одному тілі. Альтернативи цьому немає: функцію-шаблон [не можна частково спеціалізувати](book:cpp-standards/specialization-overload), тож «по функції на індекс» означало б 3×N функцій замість трьох. А так кожне тіло читається як таблиця «індекс → частина», і рядок навпроти `I == 0` стоїть на відстані ока від рядка `I == 0` у `tuple_element`.

Дужки в `return (tag_);` — не оформлення. Без них `decltype(auto)` виводить **оголошений тип поля**, тобто `std::string`, і функція мовчки повертає копію. З ними виводиться тип виразу — `std::string&`. Помилки компіляції не буде в жодному разі: у першому випадку зв'язування просто прив'яжеться до тимчасового рядка, запис у нього нікуди не потрапить, а кожен обхід контейнера почне копіювати мітку.

## Яке з трьох перевантажень візьметься

Ref-кваліфікацій три, бо викликаються вони на прихованій змінній `e`, а її категорія залежить від того, що написано перед дужками. Правило коротке й не збігається з інтуїцією: `e` — lvalue лише тоді, коли **тип** `e` є lvalue-посиланням; у всіх інших випадках `e` віддається як [xvalue](book:cpp-standards/value-categories), тобто як те, з чого дозволено забирати нутрощі.

![Таблиця: форма оголошення, тип прихованої e, категорія e у виклику get і вибране перевантаження](/reference/cpp-standards/language/structured-bindings/img/get-overloads.svg)

*Найнесподіваніший рядок — перший: звичайне `auto [u, tag] = s;` бере саме `&&`-перевантаження.*

Перший рядок таблиці варто перечитати. `auto [u, tag] = s;` копіює `s` у власну `e`, і далі частини забираються з цієї копії переміщенням — бо копія все одно нічия, вона зникне наприкінці області. Тому `&&`-перевантаження потрібне навіть тому, хто ніде не пише `std::move`.

## Член чи вільна функція

Компілятор шукає `get` як член у межах класу `E`, і бере членний шлях, **якщо знайшов шаблон функції, чий перший параметр шаблону — не тип, а значення**. Не знайшов такого — переходить до `get<i>(e)`, який шукається [лише пошуком за аргументом](book:cpp-standards/namespaces-and-adl). Ніякого змагання між членом і вільною функцією немає: рішення ухвалюється на етапі пошуку, ще до розгляду того, чи виклик узагалі скомпілюється, і навіть без огляду на доступність знайденого члена.

Вимогу «саме шаблон із нетиповим першим параметром» додав папір **P0961R1** (Вілле Воутілайнен, 14 березня 2018 року), і додав як виправлення дефекту, тобто заднім числом і до C++17. Доти будь-який член на ім'я `get` — включно з успадкованим звичайним `get()` без параметрів — перекривав шлях до вільної функції. Через це не можна було зробити придатними до розбирання цілі родини типів: обгортки над розумними вказівниками, надбудови над `future`, узагалі все, що успадкувало чужий `get()`.

Вільний `get` пишеться тим самим ланцюгом `if constexpr`, але мусить лежати **в просторі імен свого класу** — глобальний `get` чи `using`-оголошення не допоможуть, бо ніякого іншого пошуку тут не виконують.

```cpp
namespace hw {

// у класі додано публічні методи доступу:
//     std::string&       tag()       { return tag_; }
//     const std::string& tag() const { return tag_; }

template <std::size_t I> decltype(auto) get(Sample& s) {
    static_assert(I < 2, "у hw::Sample дві частини");
    if constexpr      (I == 0) return s.voltage();
    else if constexpr (I == 1) return s.tag();     // std::string&
}

template <std::size_t I> decltype(auto) get(const Sample& s) {
    static_assert(I < 2, "у hw::Sample дві частини");
    if constexpr      (I == 0) return s.voltage();
    else if constexpr (I == 1) return s.tag();     // const std::string&
}

template <std::size_t I> decltype(auto) get(Sample&& s) {
    static_assert(I < 2, "у hw::Sample дві частини");
    if constexpr      (I == 0) return s.voltage();
    else if constexpr (I == 1) return std::move(s.tag());
}

}  // namespace hw
```

Тут дужки навколо `s.tag()` не потрібні: це виклик, а не ім'я, і `decltype` від нього одразу дає оголошений тип повернення. Зате видно ціну вільного шляху — він бачить лише публічний інтерфейс, тож або клас віддає частини методами, або всі три функції треба оголосити `friend`. Членний `get` цієї турботи не має, і для власного класу він майже завжди простіший. Вільний потрібен там, де клас чужий і чіпати його не можна, — з тим застереженням, що дописати функцію в чужий простір імен вийде тільки якщо цей простір не `std`.

> 🔧 **Навіщо це.** Обіцянку протоколу варто читати вузько: ви домовляєтеся з мовою, а не з усією бібліотекою. `auto [u, tag] = s;` працюватиме будь-де, а от `std::apply` і `std::tuple_cat` викликають **кваліфіковану** `std::get` — вашої функції вони не побачать, а з C++23 ще й формально звужені до кортежоподібних типів самої бібліотеки. Зате код, який навмисно пише `using std::get; get<I>(x);`, підхопить ваш тип автоматично: саме через це `get` і зветься точкою налаштування, і саме так варто писати власні узагальнені алгоритми.

## Частина, якої немає в об'єкті

`get<0>` повертає щойно обчислений `double` — тобто prvalue, тимчасове значення. Розбирання від цього не ламається, і причина того варта окремого рядка. Компілятор оголошує приховане посилання на тип частини й прив'язує до нього результат `get`; для значення це виходить `double&& r = e.get<0>();`. Спрацьовує звичайне правило: посилання подовжує життя тимчасовому до кінця своєї області. Обчислена частина живе рівно стільки, скільки ім'я, яке на неї вказує.

Наслідок практичний: запис у таку частину компілюється, але потрапляє в тимчасове значення, а не в об'єкт. Якщо це небажано, скажіть про це в типі:

```cpp
using type = std::conditional_t<I == 0, const double, std::string>;
```

Тепер `decltype(u)` — `const double`, і `u = 0.0` не збереться.

## Пастки

**`tuple_element`, що розійшовся з `get`.** Найнебезпечніша, бо не завжди помилка. Приховане посилання має тип «посилання на `tuple_element_t<i, E>`», і якщо `get` повернув інше, але перетворне, прив'язка все одно вдасться — через тимчасовий. Пообіцяйте `float`, поверніть `double` — збереться, `decltype(u)` буде `float`, точність тихо зникне. Пообіцяйте `std::string_view`, поверніть `std::string` — теж збереться: до кінця області проживе вид, а рядок, у який він дивиться, помре наприкінці виразу, і ви отримаєте [висяче посилання](book:cpp-standards/dangling-references) там, де в коді жодного посилання не написано.

**Забуте перевантаження.** Без `const&` не збереться найпоширеніша форма `const auto& [u, tag] = s;`. Без `&&` не збереться нічого гіршого за мовчазну втрату переміщення: xvalue прив'яжеться до `const&`, і замість переїзду мітки станеться її копіювання.

**Посилання на локальне.** Спокуса «не копіювати ж обчислене» дає `const double& get() const { double v = voltage(); return v; }` — і висяче посилання на кожному виклику. Обчислені частини повертають **значенням**; приховане посилання зроблене саме для цього.

**Забутий `static_assert` на індекс.** Без нього зайве ім'я в дужках дає або порожній `decltype(auto)` (тобто `void`), або помилку десь глибоко в інстанціюванні. Один рядок нагорі кожної гілки перетворює це на людське повідомлення.

Три майже однакові тіла `get` — те, що в C++23 згортається в одне за допомогою [явного об'єктного параметра](book:cpp-standards/deducing-this): `template <std::size_t I, class Self> decltype(auto) get(this Self&& self)` лишається шаблоном із нетиповим першим параметром, тож протокол його впізнає.

## Перевірка

Останній крок — переконатися не в тому, що код збирається, а в тому, що типи вийшли ті, які задумано.

```cpp
hw::Sample s{40000, "ch0"};
static_assert(std::tuple_size_v<hw::Sample> == 2);

auto& [u, tag] = s;                    // e — Sample&, працює get() &
static_assert(std::is_same_v<decltype(u),   double>);
static_assert(std::is_same_v<decltype(tag), std::string>);

const auto& [cu, ctag] = s;            // e — const Sample&, працює get() const&
static_assert(std::is_same_v<decltype(cu),   const double>);
static_assert(std::is_same_v<decltype(ctag), const std::string>);

tag = "ch0-rev2";                      // пише в поле s: tag — ім'я підоб'єкта
u   = 0.0;                             // пише в тимчасовий double: s не змінився
```

Два зв'язування виглядають однаково, а поводяться по-різному — і це не дефект, а точний портрет того, що написано в `get`: мітка існує в об'єкті, напруга існує лише в момент запитання. Пара `const double`/`const std::string` у другому наборі перевірок з'явилася сама — її дала бібліотечна спеціалізація `tuple_element` для `const`-типів, якої ви не писали.
