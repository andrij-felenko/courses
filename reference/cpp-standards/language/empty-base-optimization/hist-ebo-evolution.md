# 📜 Від заборони нульового розміру до [[no_unique_address]]

Історія оптимізації порожніх типів у C++ розкриває фундаментальний компроміс між моделлю пам'яті C, об'єктно-орієнтованою ідентичністю та прагненням до нульових накладних витрат (*zero-overhead principle*). Цей шлях тривав понад тридцять років — від перших трансляторів Б'ярна Страуструпа (*Bjarne Stroustrup*) до стандарту C++20.

### Витоки: чому об'єкт зобов'язаний мати адресу

Наприкінці 1970-х років, створюючи мову «C з класами» (*C with Classes*), Б'ярн Страуструп спирався на фізичну модель пам'яті мови C. У C кожен об'єкт займає конкретну неперервну послідовність байтів, а покажчик на об'єкт — це числова адреса його першого байта.

Коли в мові з'явилися класи без полів даних (наприклад, типи, що містять лише методи, переліки або визначення типів), постало логічне запитання: скільки пам'яті має займати екземпляр такого класу?

Математично інтуїтивна відповідь — нуль байтів: якщо об'єкт не зберігає стану, він не потребує комірок у фізичній пам'яті. Проте Страуструп швидко виявив, що нульовий розмір руйнує фундаментальні аксіоми адресної арифметики C та семантики об'єктів:

1. **Унікальність ідентичності**: якщо два незалежні об'єкти `Empty a;` та `Empty b;` розташовані поспіль у стеку або статичній пам'яті і мають розмір 0, то вираз `&a == &b` поверне `true`. Два різні об'єкти з різними іменами та незалежним часом життя отримають однакову адресу. Це унеможливлює однозначну ідентифікацію об'єктів у контейнерах, асоціативних таблицях чи алгоритмах пошуку за адресою.
2. **Адресна арифметика масивів**: у C та C++ вираз `arr + 1` означає зсув покажчика на `sizeof(*arr)` байтів. Якби `sizeof(Empty)` дорівнював нулю, додавання одиниці не змінювало б числове значення адреси. Відтак елементи `arr[0]`, `arr[1]` та `arr[2]` вказували б на одну й ту саму точку пам'яті. Будь-який цикл проходу масивом або алгоритм `std::distance` перетворився б на нескінченне зациклення на місці.
3. **Оператор виділення пам'яті `new`**: виклик `new Empty[100]` повинен повертати 100 розрізнюваних покажчиків. При нульовому розмірі функція виділення пам'яті мусила б або повертати `nullptr`, або повертати однаковий покажчик для кожного елемента, що зробило б неможливим їх коректне індивідуальне знищення через деструктори.

У фундаментальній праці *The Annotated C++ Reference Manual* (ARM, 1990) Б'ярн Страуструп та Марґарет Елліс (*Margaret Ellis*) зафіксували канонічне правило: розмір будь-якого повного об'єкта (*complete object*) або типу структури має бути щонайменше 1 байт. Якщо клас не містить полів даних, компілятор Cfront неявно резервував під нього 1 байт (так званий «байт-заповнювач» або *dummy byte*).

### Відкриття винятку: народження EBO в C++98

Правило `sizeof >= 1` бездоганно працювало для простих змінних і масивів, але на початку 1990-х років із розвитком узагальненого програмування та появою бібліотеки STL (*Standard Template Library*) Алекса Степанова (*Alexander Stepanov*) мова зіткнулася з серйозним архітектурним викликом.

STL масово впроваджувала класи без власного стану (*stateless classes*):
- алокатори пам'яті за замовчуванням (`std::allocator<T>`);
- функціональні об'єкти та предикати порівняння (`std::less<T>`, `std::equal_to<T>`);
- теги категорій ітераторів (`std::random_access_iterator_tag`);
- класи характеристик типів (*traits*).

Коли розробники контейнерів намагалися зберегти такий функціональний об'єкт або алокатор як звичайне поле класу:

```cpp
template <typename T, typename Alloc>
class vector {
    T* data_;
    size_t size_;
    size_t capacity_;
    Alloc alloc_; // Порожній алокатор пам'яті
};
```

Через вимоги до вирівнювання покажчиків на 64-бітній платформі 1-байтове поле `alloc_` спричиняло додавання 7 байтів порожнього заповнення (*tail padding*). Розмір об'єкта `vector` зростав з 24 байтів до 32 байтів — на 33% більше пам'яті на кожен екземпляр вектора в системі виключно заради збереження порожнього службового типу! Для таких класів, як `std::unique_ptr`, де розмір критично мав збігатися з розміром одного машинного слова (8 байтів), збереження порожнього делітера роздувало структуру до 16 байтів.

Розв'язання знайшов комітет зі стандартизації під час підготовки першого міжнародного стандарту ISO/IEC 14882:1998 (C++98). Комітет проаналізував вимогу унікальності адрес і зробив важливе розмежування: правило обов'язкової унікальності адреси стосується **повних об'єктів** і **полів-членів**, але **не є обов'язковим для базових підоб'єктів** (*base class subobjects*).

Оскільки базовий клас не існує окремо від похідного класу, а становить його складову частину, компілятору офіційно дозволили розміщувати базовий підоб'єкт за тим самим зміщенням, що й перше поле похідного класу (зміщення 0). Цей механізм отримав назву **Оптимізація порожньої бази** (*Empty Base Optimization*, скорочено EBO).

### Епоха хаків: `boost::compressed_pair` та Policy-Based Design

Термін *Empty Base Optimization* остаточно закріпився в літературі завдяки публікації Натана Маєрса (*Nathan Myers*) 1997 року *The Empty Base C++ Optimization*. Маєрс показав інженерній спільноті, як за допомогою приватного спадкування можна створювати узагальнені структури, що не витрачають жодного зайвого байта на порожні класи.

У 2001 році Андрей Александреску (*Andrei Alexandrescu*) у монографії *Modern C++ Design* перетворив EBO на наріжний камінь проектування на основі політик (*Policy-Based Class Design*). Замість того, щоб передавати конфігураційні класи та стратегії поведінки як поля, Александреску запропонував спадкувати їх:

```cpp
template <typename T, typename ThreadingModel, typename CheckingPolicy>
class SmartPtr : private ThreadingModel, private CheckingPolicy {
    T* pointee_;
};
```

Якщо `ThreadingModel` та `CheckingPolicy` є порожніми класами (що типово для однопотокових конфігурацій без динамічних перевірок), `SmartPtr` має фізичний розмір рівно одного звичайного машинного покажчика.

Бібліотека Boost канонізувала цей підхід у шаблоні `boost::compressed_pair`. За допомогою засобів інтроспекції типів `boost::is_empty<T>` клас `compressed_pair<T1, T2>` аналізував параметри шаблона під час компіляції та автоматично обирав: спадкувати тип чи зберігати його як поле. Саме на фундаменті EBO та спеціалізованих стиснених пар були побудовані реалізації `std::unique_ptr`, `std::vector` та `std::function` у стандартних бібліотеках libstdc++ (GNU GCC) та libc++ (LLVM Clang).

### Архітектурні обмеження спадкування

Попри свою ефективність, спадкування заради оптимізації розміру залишалося вимушеним обхідним шляхом і породжувало серйозні проблеми проектування:

1. **Неможливість оптимізації `final`-типів**: у стандарті C++11 з'явився специфікатор `final`. Якщо користувацький stateless-алокатор чи функтор оголошено як `struct MyDeleter final { ... };`, спроба застосувати EBO через спадкування викликає жорстку помилку компіляції.
2. **Несумісність із базовими типами**: від вказівників на функції (`void(*)(int*)`), числових типів, посилань чи масивів неможливо успадкуватися синтаксично, що змушувало авторів бібліотек писати складні розгалуження в метапрограмах.
3. **Витік інтерфейсу та колізії імен**: навіть приватне спадкування впливає на таблиці символів, пошук імен (*name lookup*) та правила перевантаження операторів. Якщо порожня база містить метод або тип з тим самим ім'ям, що й похідний клас, звернення до члена стає неоднозначним (*ambiguous*).
4. **Ризик небезпечного зрізання**: механізм спадкування в об'єктно-орієнтованому проектуванні моделює відношення «є різновидом» (*is-a*). Використання його суто для оптимізації розкладки пам'яті спотворювало семантику коду та створювало ризики випадкового приведення типів.

У спільноті визріло чітке розуміння: C++ потребує прямого, декларативного способу вказати компілятору «це поле не містить стану, оптимізуй його розмір без зміни структури класів».

### Шлях до C++20: пропозиція P0840 та атрибут `[[no_unique_address]]`

У жовтні 2017 року Річард Сміт (*Richard Smith*) опублікував пропозицію **P0840R0** (*Language support for empty objects*).

Автори запропонували ввести новий стандартний атрибут `[[no_unique_address]]`, призначений для застосування до нестатичних полів класів. Семантика атрибута прямо наказує компілятору: поле-член класу не вимагає виділення унікальної адреси пам'яті, якщо воно не містить корисного стану, і може ділити адресу з іншими полями або підоб'єктами.

Комітет WG21 зустрів пропозицію з великим схваленням. Документ швидко пройшов етапи рецензування робочою групою з еволюції мови (EWG) і на літньому засіданні в Рапперсвілі (*Rapperswil*, Швейцарія, червень 2018 року) був офіційно включений до робочого проекту C++20 у редакції **P0840R2**.

Атрибут розв'язав усі накопичені десятиліттями проблеми:
- повна підтримка `final`-типів без спеціальних умов;
- прозора композиція полів без залучення ієрархій спадкування;
- відсутність впливу на пошук імен, віртуальні таблиці чи права доступу;
- спрощення коду стандартних утиліт `std::tuple`, `std::unique_ptr` та `std::expected`.

### Двійкова розбіжність: історія з MSVC ABI

Впровадження `[[no_unique_address]]` виявило несподівану двійкову проблему в екосистемі Microsoft Visual C++ (MSVC).

Компілятори GCC та Clang на платформах Linux і macOS використовують Itanium C++ ABI, правила якого вже містили концепцію зміщення підоб'єктів нульового розміру. Однак компілятор MSVC на платформі Windows історично використовував власну двійкову модель розміщення структур, зафіксовану ще на початку 1990-х років.

Зміна правил розташування полів у структурах при переході на новий стандарт автоматично призвела б до порушення бінарної сумісності (*ABI breakage*) між динамічними бібліотеками (DLL), зібраними в режимах C++14/17 та C++20. Оскільки атрибути в C++ за визначенням вважаються оптимізаційними підказками, які компілятор має право ігнорувати, команда розробників MSVC вирішила зробити стандартний атрибут `[[no_unique_address]]` **пустою операцією** (*no-op*) без попередження.

Щоб надати розробникам можливість увімкнути оптимізацію розміру явно, Microsoft запровадила спеціальний специфічний атрибут **`[[msvc::no_unique_address]]`** (доступний починаючи з Visual Studio 2019 версії 16.9). Це спричинило тимчасове роздвоєння синтаксису в індустрії: кросплатформні проекти C++20 використовують препроцесорні макроси, які розгортаються у `[[msvc::no_unique_address]]` під компілятор MSVC та у `[[no_unique_address]]` під Clang і GCC.
