# 📜 Історія спотворення імен: від cfront і ARM до Itanium ABI

Коли Б'ярн Страуструп на початку 1980-х років в лабораторіях Bell Labs розробляв першу версію C++ («C з класами», а згодом мову C++), перед ним стояла фундаментальна інженерна дилема: написати власний повноцінний компілятор під кожну апаратну архітектуру (VAX, PDP-11, Motorola 68000) або створити високорівневий транслятор, який перетворюватиме новий об'єктний синтаксис у стандартний код мови C. Страуструп обрав другий шлях, створивши транслятор `cfront` (C Front-end). Це дозволило мові миттєво поширитися на десятки систем, де вже існував зрілий C-компілятор.

Проте трансляція об'єктно-орієнтованих конструкцій у класичний процедурний C одразу зіткнулася з жорстким обмеженням двійкового формату об'єктних файлів. У мові C імена функцій утворювали плаский глобальний простір. Системний компонувальник Unix оперував виключно плоскими таблицями символів a.out або COFF, де кожне ім'я було неструктурованим рядком байтів. Якщо програміст оголошував дві однойменні функції для друку різних типів даних (`print(int)` та `print(double)`), трансляція їх як `print` у C-код призводила до фатальної помилки компіляції та компонування: два глобальні символи мали однаковий ідентифікатор.

Щоб зберегти перевантаження функцій і методи класів без зміни системних компонувальників, `cfront` мусив вирішувати конфлікт на етапі трансляції. Компілятор брав на себе обов'язок самостійно генерувати штучні унікальні імена для кожної сутності, вшиваючи інформацію про типи параметрів безпосередньо в текстовий рядок символу. Цей механізм отримав назву спотворення імен (англ. *name mangling* або *name decoration*).

## Перша схема cfront та стандарт ARM (1980-ті)

У найперших версіях `cfront` 1.0 та 2.0 схема кодування була навмисно спрощеною. Компілятор брав вихідне ім'я функції, додавав спеціальний розділювач із двох символів підкреслення `__`, після якого ставив літеру `F` (що позначала *Function*), а далі — послідовність однолітерних або дволітерних кодів базових типів аргументів.

Символи підкреслення були обрані не випадково: згідно з традицією системного програмування на C подвійне підкреслення не використовувалося у звичайному прикладному коді і вважалося службовим маркером компілятора.

```text
// Вихідний синтаксис C++:
void print(int x);
void print(double x);
void print(const char* s);

// Результуючий вивід cfront для C-компілятора:
void print__Fi(int x);
void print__Fd(double x);
void print__FPCc(const char* s);
```

Для методів класів перед розділювачем додавалася назва класу, до якого належить метод:
```text
class Screen {
public:
    void clear();
    void resize(int w, int h);
};

// Згенеровані C-функції:
void Screen__clear__Fv(Screen* this);
void Screen__resize__Fii(Screen* this, int w, int h);
```

Прихований перший аргумент `this` явно передавався у згенеровану функцію як перший параметр типу `Screen*`. Код типу `v` позначав порожній список параметрів (`void`), `i` — `int`, `d` — `double`, а `PCc` розшифровувався з кінця наперед: `c` — `char`, `C` — `const`, `P` — `Pointer` (вказівник на константний символ).

Цю систему формалізували Маргарет Елліс та Б'ярн Страуструп у 1990 році в книзі *«The Annotated C++ Reference Manual»* (відомій у спільноті за абревіатурою **ARM**). На той час здавалося, що схема ARM закриває всі потреби мови. Вона була зрозумілою для інженера під час читання асемблерних лістингів, не вимагала складних алгоритмів декодування і надійно розрізняла функції в межах невеликих проєктів.

Проте схема ARM мала серйозну системну ваду: вона спиралася на те, що граматика мови залишиться відносно простою та фіксованою. Вона не передбачала появи глибоких просторів імен, узагальненого програмування та складних шаблонів.

## Криза 1990-х: революція мови та хаос несумісних компіляторів

Між 1992 та 1998 роками, під час підготовки першого міжнародного стандарту ISO/IEC 14882:1998 (C++98), мова зазнала вибухового розвитку. До неї було додано три фундаментальні механізми, які остаточно зруйнували схему ARM:

1. **Простори імен (Namespaces)**, стандартизовані в 1993–1994 роках, запровадили довільно вкладені області видимості. Простий розділювач `__` уже не дозволяв зрозуміти, де закінчується назва зовнішнього простору імен, де починається вкладений простір, де ім'я класу, а де безпосередньо назва методу.
2. **Шаблони (Templates)** та поява стандартної бібліотеки шаблонів (STL) Олександра Степанова. Тип аргументу тепер міг бути складним деревом: функція могла приймати `std::map<std::string, std::vector<double>>`. Кодування такого типу вимагало опису всього дерева інстанціації шаблону разом з усіма аргументами за замовчуванням та алокаторами.
3. **Кваліфікатори посилань, вказівники на члени класів та оператори користувацького приведення типів**.

Оскільки стандарт ISO свідомо регламентував лише синтаксис та семантику мови, повністю оминаючи питання двійкового інтерфейсу (ABI), кожен виробник компіляторів почав рятувати ситуацію власними силами. Почалася епоха «компіляторних війн», яка породила повну фрагментацію індустрії:

- **Microsoft Visual C++** (починаючи з версій 1.0 та 4.0 для Win32) створив власну складну систему декорації. Імена починалися зі знака питання `?`, як розділювач компонентів використовувався символ `@`, а подвійний символ `@@` позначав завершення списку областей видимості. Microsoft вирішила кодувати в символі не лише аргументи, а й конвенцію виклику (`__cdecl`, `__stdcall`, `__thiscall`), рівень доступу методу (`public`, `protected`, `private`) та тип повернення функції.
- **Borland C++** (основний конкурент Microsoft на платформі DOS/Windows у 1990-х) створив несумісну систему, де символи починалися з `@`, а типи аргументів кодувалися за власною однолітерною таблицею.
- **GNU Project (g++)** пройшов через низку болісних ітерацій. Версії GCC 2.7, GCC 2.8 та GCC 2.95 мали різні реалізації манглінгу. Кожне мажорне оновлення компілятора GCC у дистрибутивах Linux ламало бінарну сумісність: усі сторонні динамічні бібліотеки `.so` доводилося перекомпілювати з нуля, оскільки компонувальник шукав функції під новими іменами.
- **IBM VisualAge**, **SunPro CC** для Solaris, **Metrowerks CodeWarrior** для Mac OS та **Watcom C++** використовували власні незалежні схеми.

Ця роздробленість перетворилася на катастрофу для комерційної розробки. Розробник, який купував пропрієтарну графічну бібліотеку чи рушій бази даних у скомпільованому вигляді (без надання вихідного коду), ставав довічним заручником одного конкретного компілятора і навіть його конкретної версії. Зібрати проєкт компілятором GCC з об'єктним файлом від Borland чи Microsoft було абсолютно неможливо: компонувальник сипав сотнями помилок `undefined symbol`, оскільки одна й та сама функція `Vector::normalize()` у різних файлах мала абсолютно різні спотворені імена.

Додатково виникла проблема **вибухового роздування таблиць символів**. Нестиснені шаблонні імена у ранніх версіях STL займали по 2000–5000 байтів на один символ. Якщо функція використовувала кілька стандартних контейнерів, її ім'я багаторазово дублювало довгі службові назви на кшталт `std::basic_string<char, std::char_traits<char>, std::allocator<char>>`. Розміри об'єктних файлів вимірювалися сотнями мегабайтів, а системний компонувальник витрачав хвилини на звичайне текстове зіставлення символів під час лінкування.

## Робоча група Itanium C++ ABI (1999–2001)

Наприкінці 1990-х років компанії Intel та Hewlett-Packard завершували проектування нової 64-бітної мікропроцесорної архітектури IA-64, яка отримала ринкову назву **Itanium**.

Перехід на 64-бітну платформу відкривав унікальне вікно можливостей. Провідні виробники системного програмного забезпечення усвідомили: перенесення старого хаосу 32-бітних несумісних ABI на нову архітектуру призведе до того, що Unix-системи втратять міжплатформну сумісність.

У 1999 році було сформовано консорціум **Itanium C++ ABI Consortium**. До робочої групи увійшли провідні інженери та архітектори компіляторів із компаній Intel, Hewlett-Packard, Silicon Graphics (SGI), Sun Microsystems, IBM, Compaq, а також ключові розробники GNU Toolchain із компаній Cygnus Solutions та Red Hat (зокрема Джейсон Меррілл і Марк Мітчелл).

Консорціум поставив перед собою мету розробити вичерпний, відкритий і математично строгий стандарт двійкового інтерфейсу мови C++, який покривав би:
- розміщення структур і класів у пам'яті (включно зі складним віртуальним успадкуванням);
- розміщення та заповнення таблиць віртуальних методів (`vtable`);
- генерацію метаданих динамічної типізації (RTTI);
- системні таблиці розгортання стеку для винятків (`.eh_frame` та формат DWARF);
- системну бібліотеку часу виконання (C++ Runtime з префіксом функцій `__cxa_`);
- уніфікований алгоритм спотворення імен.

Специфікація спотворення імен у стандарті Itanium C++ ABI була побудована на кількох фундаментальних принципах:

1. **Строга формальна граматика BNF:** Стандарт дав однозначний опис правил формування символів. Усі C++ символи починаються з глобального префікса `_Z` (у мові C цей префікс зарезервовано за системною реалізацією компілятора, що виключає колізії з іменами звичайного коду).
2. **Префікси довжини замість розділювачів:** Замість використання спеціальних символів-розділювачів, які могли конфліктувати з системними обмеженнями асемблерів, кожному ідентифікатору передує точна десяткова кількість його символів. Наприклад, `namespace graphics` кодується як `8graphics`, а метод `render` як `6render`. Це дозволило парсеру деманґлера однозначно зчитувати межі слів без потреби в розділювальних знаках.
3. **Складені імена в дужках `N...E`:** Для вкладених просторів імен, класів і методів було запроваджено префікс `N` (від *Nested*) та термінатор `E` (від *End*). Конструкція `graphics::Renderer::draw` отримала вигляд `_ZN8graphics8Renderer4drawE...`.
4. **Алгоритм компресії через підстановки (Substitutions):** Щоб подолати проблему гігантських імен у шаблонах, було створено механізм підстановок. Компілятор, проходячи сигнатуру зліва направо, записує кожен новий тип, простір імен чи шаблон у внутрішню таблицю індексів. Повторна поява цього ж типу замінюється коротким кодом: перше повторення — `S_`, друге — `S0_`, третє — `S1_` і так далі. Крім того, найпоширеніші типи стандартної бібліотеки отримали фіксовані глобальні скорочення: `St` для простору `std::`, `Sa` для `std::allocator`, `Sb` для `std::basic_string` та `Ss` для `std::string`. Завдяки цьому розмір спотворених символів складних STL-типів зменшився в 5–10 разів.

## Доля стандарту: тріумф програмної специфікації

Сам мікропроцесор Intel Itanium (IA-64) через складність архітектури VLIW та проблеми з продуктивністю на невирівняному коді виявився комерційно невдалим і з часом повністю поступився архітектурі AMD64 (x86-64).

Однак програмна специфікація Itanium C++ ABI виявилася настільки технічно досконалою, чистою та масштабованою, що індустрія миттєво адаптувала її для інших процесорів.

У 2001 році розробники GNU проекту інтегрували Itanium ABI у компілятор GCC 3.0 для архітектури x86. Коли на початку 2000-х з'явилася компанія Apple з архітектурою LLVM/Clang, вона обрала Itanium ABI як рідний бінарний стандарт для всіх операційних систем родини Darwin (macOS, iOS, watchOS, tvOS). Згодом стандарт без змін перейшов на платформу Android (у складі Android NDK), операційні системи FreeBSD, OpenBSD, NetBSD, а також на архітектури ARM, AArch64 та RISC-V.

Сьогодні Itanium C++ ABI є універсальним відкритим двійковим стандартом майже всього світового комп'ютерного простору поза операційною системою Windows. Microsoft вирішила зберегти свій історичний формат MSVC ABI заради забезпечення зворотної сумісності мільйонів рядків коду у Windows API та системних DLL.

Таким чином, сучасний світ C++ функціонує в умовах стабільного двополюсного балансу: відкритий світ Unix спирається на стандарт Itanium C++ ABI з префіксом `_Z`, а екосистема Microsoft Windows використовує стандарт MSVC ABI з префіксом `?`.
