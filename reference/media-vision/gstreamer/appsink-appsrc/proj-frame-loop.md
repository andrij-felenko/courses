# ⚙️ Кадр із конвеєра в OpenCV і назад: робочий цикл

Зберімо повну програму, яка бере кадри з камери або відеофайлу, малює по них засобами OpenCV і пише результат у придатний до відтворення mp4, — і порахуймо на ній кожен скопійований байт. Цінність тут не в тому, що вона працює: працює й той десяток рядків, що ходить по форумах. Цінність у тому, що на цьому лістингу видно, де така програма зазвичай тихо бреше — про крок рядка, про час і про кінець потоку — і скільки пам'яті вона перекладає з місця на місце там, де в коді немає жодного натяку на копію.

## Задача

Вхід — або камера через `v4l2src`, або будь-який файл через `filesrc` і `decodebin`. Обробка — довільна робота OpenCV над кадром: тут це вимірювання яскравості й напис поверх картинки, але на цьому місці однаково добре стоїть детектор, трекер чи інференс. Вихід — H.264 у файл `out.mp4` (або, тим самим кодом, RTP через `udpsink`).

Вимоги, які й роблять задачу задачею, а не вправою:

- кадр не копіюється жодного разу, коли копію можна не робити, і копіюється рівно там, де без неї не можна;
- час у записаному файлі відповідає реальному часу зйомки, навіть якщо частину кадрів довелося викинути;
- Ctrl+C дає файл, який відкривається програвачем, а не сорок мегабайтів сміття;
- обробка, яка не встигає, псує картинку, а не вішає камеру.

## Ідея: два конвеєри, один ваш потік

Перший конвеєр закінчується на `appsink`, другий починається з `appsrc`, а між ними — звичайний цикл `while` у вашому власному потоці. Три рішення в цій схемі неочевидні, і кожне далі окупається.

**Забирати кадр самим, а не чекати виклику.** `gst_app_sink_try_pull_sample()` блокує **ваш** потік, а не потік передавання конвеєра. Це коштує одного контекстного перемикання на кадр і одразу знімає цілий клас помилок: усе, що ви робите з кадром, відбувається поза конвеєром, тож ані довга обробка, ані зупинка, ані блокування на виході не чіпають декодер напряму.

**Замовляти формат фільтром caps, а не сподіватися на нього.** Рядок `videoconvert ! video/x-raw,format=BGR ! appsink` — це не опис того, що прийде, а вимога. Без фільтра `appsink` погодиться на будь-що, і `cv::Mat` типу `CV_8UC3` рано чи пізно отримає NV12 з половинною колірністю. Про те, як конвеєр перебирає варіанти, домовляючись про формат, — у [темі про узгодження caps](book:media-vision/caps-negotiation).

**Будувати другий конвеєр після першого кадру, а не разом із першим.** Роздільність і частота стають відомі лише з caps семпла. Вгадана роздільність — це в кращому разі помилка `not-negotiated` на кодері, у гіршому — правильно зібраний конвеєр, який читає пам'ять за межами буфера. Тому `appsrc` створюється тоді, коли є що йому сказати.

## Збірка

```
g++ -O2 -std=c++17 frame_loop.cpp -o frame_loop \
    $(pkg-config --cflags --libs gstreamer-1.0 gstreamer-app-1.0 \
                                 gstreamer-video-1.0 opencv4)
```

Три пакети GStreamer, і жоден не зайвий: `gstreamer-1.0` — ядро, `gstreamer-app-1.0` — власне `appsink` і `appsrc` із бібліотеки `libgstapp`, `gstreamer-video-1.0` — `GstVideoInfo` і `GstVideoFrame`, без яких не буде правильного кроку рядка. Ім'я `opencv4` — це `.pc`-файл OpenCV 4.x; за часів OpenCV 3 воно звалося просто `opencv`.

`x264enc` живе в наборі gst-plugins-ugly — його може не бути в мінімальній збірці. Заміни: `openh264enc` (gst-plugins-bad), `vaapih264enc`, `nvh264enc`, `v4l2h264enc` — усе, що дає [апаратне кодування](book:media-vision/hardware-decode-elements); рядок конвеєра при цьому міняється в одному слові.

## Код

```cpp
// frame_loop.cpp — кадр із конвеєра → OpenCV → назад у конвеєр.

#include <gst/gst.h>
#include <gst/app/gstappsink.h>
#include <gst/app/gstappsrc.h>
#include <gst/video/video.h>

#include <opencv2/imgproc.hpp>

#include <csignal>
#include <cstdio>
#include <string>

static volatile sig_atomic_t g_stop = 0;
static void on_sigint (int) { g_stop = 1; }

/* Обробка. Малюємо ВЖЕ у власній пам'яті: frame — заголовок над
   вихідним буфером, який ми самі щойно виділили.
   putText уміє лише латиницю, тому напис англійський. */
static void process (cv::Mat &frame, guint64 n)
{
  cv::Mat gray;
  cv::cvtColor (frame, gray, cv::COLOR_BGR2GRAY);
  double lum = cv::mean (gray)[0];

  char label[64];
  std::snprintf (label, sizeof label, "frame %llu   mean %.1f",
                 (unsigned long long) n, lum);
  cv::rectangle (frame, cv::Rect (8, 8, 330, 34),
                 cv::Scalar (0, 0, 0), cv::FILLED);
  cv::putText (frame, label, cv::Point (16, 32), cv::FONT_HERSHEY_SIMPLEX,
               0.6, cv::Scalar (255, 255, 255), 1, cv::LINE_AA);
}

/* Помилку на шині забираємо НЕ блокуючись — інакше цикл кадрів стане. */
static bool bus_ok (GstElement *pipeline, const char *who)
{
  GstBus *bus = gst_element_get_bus (pipeline);
  GstMessage *msg = gst_bus_pop_filtered (bus, GST_MESSAGE_ERROR);
  bool ok = true;
  if (msg) {
    GError *e = NULL; gchar *dbg = NULL;
    gst_message_parse_error (msg, &e, &dbg);
    g_printerr ("[%s] %s (%s)\n", who, e->message, dbg ? dbg : "-");
    g_clear_error (&e); g_free (dbg);
    gst_message_unref (msg);
    ok = false;
  }
  gst_object_unref (bus);
  return ok;
}

/* Другий конвеєр будуємо ТІЛЬКИ тоді, коли з першого кадру відомі
   справжні роздільність і частота. */
static GstElement *build_output (GstVideoInfo *info, GstAppSrc **src_out)
{
  const char *desc =
      "appsrc name=in format=time ! videoconvert ! "
      "x264enc tune=zerolatency speed-preset=veryfast bitrate=4000 "
      "         key-int-max=30 ! "
      "h264parse ! mp4mux ! filesink location=out.mp4";

  GError *e = NULL;
  GstElement *p = gst_parse_launch (desc, &e);
  if (!p) { g_printerr ("вихід: %s\n", e->message); g_clear_error (&e); return NULL; }

  GstAppSrc *src = GST_APP_SRC (gst_bin_get_by_name (GST_BIN (p), "in"));

  /* Caps будуємо з того самого GstVideoInfo, з якого потім беремо
     розмір буфера й крок рядка — тож розійтися вони не можуть. */
  GstCaps *caps = gst_video_info_to_caps (info);
  gst_app_src_set_caps (src, caps);
  gst_caps_unref (caps);

  /* block=TRUE безпечний РІВНО ТОМУ, що штовхаємо зі свого потоку:
     тут блокування гальмує наш цикл, а не потік передавання камери. */
  g_object_set (src, "block", TRUE,
                "max-bytes", (guint64) (4 * GST_VIDEO_INFO_SIZE (info)), NULL);

  gst_element_set_state (p, GST_STATE_PLAYING);
  *src_out = src;
  return p;
}

int main (int argc, char *argv[])
{
  gst_init (&argc, &argv);
  std::signal (SIGINT, on_sigint);

  /* Фільтр caps після videoconvert — це замовлення формату: саме ним ми
     змушуємо конвеєр віддати BGR, якого чекає cv::Mat. decodebin віддає
     пад не одразу, але відкладене з'єднання gst_parse_launch ставить сам. */
  std::string in_desc = (argc > 1)
      ? std::string ("filesrc location=\"") + argv[1] + "\" ! decodebin ! "
        "videoconvert ! video/x-raw,format=BGR ! appsink name=out"
      : std::string ("v4l2src device=/dev/video0 ! videoconvert ! "
                     "video/x-raw,format=BGR ! appsink name=out");

  GError *e = NULL;
  GstElement *pin = gst_parse_launch (in_desc.c_str (), &e);
  if (!pin) { g_printerr ("вхід: %s\n", e->message); return 1; }

  GstAppSink *sink = GST_APP_SINK (gst_bin_get_by_name (GST_BIN (pin), "out"));
  g_object_set (sink,
                "sync",        FALSE,      /* кадр потрібен, щойно він є */
                "max-buffers", (guint) 2,  /* дві миті затримки, не більше */
                "drop",        TRUE,       /* з 1.28 — leaky-type=downstream */
                NULL);
  gst_element_set_state (pin, GST_STATE_PLAYING);

  GstElement   *pout   = NULL;
  GstAppSrc    *src    = NULL;
  GstCaps      *known  = NULL;              /* caps, під які зібрано вихід */
  GstVideoInfo  info;
  GstClockTime  base   = GST_CLOCK_TIME_NONE;   /* PTS першого кадру */
  guint64       frames = 0;

  while (!g_stop) {
    GstSample *sample = gst_app_sink_try_pull_sample (sink, 200 * GST_MSECOND);
    if (!sample) {                       /* таймаут, кінець або біда */
      if (gst_app_sink_is_eos (sink)) break;
      if (!bus_ok (pin, "вхід")) break;
      continue;
    }

    GstCaps *caps = gst_sample_get_caps (sample);   /* належить семплу */
    if (!known) {
      if (!gst_video_info_from_caps (&info, caps)) {
        g_printerr ("незрозумілі caps\n"); gst_sample_unref (sample); break;
      }
      known = gst_caps_ref (caps);
      pout  = build_output (&info, &src);
      if (!pout) { gst_sample_unref (sample); break; }
    } else if (!gst_caps_is_equal (caps, known)) {
      /* Формат змінився посеред потоку — камера перемкнула роздільність.
         Зупиняємось чесно: перебудова гілки кодування на льоту — окрема
         задача, а мовчки різати кадр під старий розмір не можна. */
      g_printerr ("формат змінився посеред потоку\n");
      gst_sample_unref (sample);
      break;
    }

    GstBuffer *inbuf = gst_sample_get_buffer (sample);   /* теж належить семплу */

    GstVideoFrame in_f;
    if (!gst_video_frame_map (&in_f, &info, inbuf, GST_MAP_READ)) {
      gst_sample_unref (sample);
      continue;
    }

    /* Заголовок поверх ЧУЖОЇ пам'яті — жодного скопійованого байта.
       П'ятий аргумент — КРОК РЯДКА; без нього OpenCV вважає рядок
       щільним і на вирівняному кадрі малює косі смуги. */
    cv::Mat view (GST_VIDEO_FRAME_HEIGHT (&in_f),
                  GST_VIDEO_FRAME_WIDTH  (&in_f), CV_8UC3,
                  GST_VIDEO_FRAME_PLANE_DATA   (&in_f, 0),
                  GST_VIDEO_FRAME_PLANE_STRIDE (&in_f, 0));

    /* Вихідний буфер — наш власний і писабельний. Розмір бере
       GstVideoInfo, тож кроки збігаються з тим, чого чекає кодер. */
    GstBuffer *outbuf =
        gst_buffer_new_allocate (NULL, GST_VIDEO_INFO_SIZE (&info), NULL);
    GstVideoFrame out_f;
    gst_video_frame_map (&out_f, &info, outbuf, GST_MAP_WRITE);
    cv::Mat dst (GST_VIDEO_FRAME_HEIGHT (&out_f),
                 GST_VIDEO_FRAME_WIDTH  (&out_f), CV_8UC3,
                 GST_VIDEO_FRAME_PLANE_DATA   (&out_f, 0),
                 GST_VIDEO_FRAME_PLANE_STRIDE (&out_f, 0));

    view.copyTo (dst);        /* ЄДИНА повна копія кадру в цьому циклі */
    process (dst, frames);    /* малюємо вже у своїй пам'яті */

    gst_video_frame_unmap (&out_f);
    gst_video_frame_unmap (&in_f);

    /* Час беремо з ВХІДНОГО кадру, а не з лічильника: якщо appsink щось
       викинув, справжні мітки збережуть реальний темп, а нумерація
       кадрів мовчки пришвидшила б запис. */
    GstClockTime pts = GST_BUFFER_PTS (inbuf);
    GstClockTime dur = GST_BUFFER_DURATION (inbuf);
    if (!GST_CLOCK_TIME_IS_VALID (dur))
      dur = (GST_VIDEO_INFO_FPS_N (&info) > 0)
          ? gst_util_uint64_scale_int (GST_SECOND,
                                       GST_VIDEO_INFO_FPS_D (&info),
                                       GST_VIDEO_INFO_FPS_N (&info))
          : 33 * GST_MSECOND;
    if (!GST_CLOCK_TIME_IS_VALID (pts))  pts  = frames * dur;
    if (!GST_CLOCK_TIME_IS_VALID (base)) base = pts;

    GST_BUFFER_PTS      (outbuf) = (pts > base) ? pts - base : 0;
    GST_BUFFER_DTS      (outbuf) = GST_CLOCK_TIME_NONE;   /* поставить кодер */
    GST_BUFFER_DURATION (outbuf) = dur;

    gst_sample_unref (sample);   /* пам'ять — назад у пул, якомога раніше */

    GstFlowReturn ret = gst_app_src_push_buffer (src, outbuf);
    if (ret != GST_FLOW_OK) {    /* outbuf уже НЕ наш — за будь-якого ret */
      g_printerr ("вихід зупинився: %s\n", gst_flow_get_name (ret));
      break;
    }
    if (!bus_ok (pout, "вихід")) break;
    ++frames;
  }

  /* Порядок згортання: перестати штовхати → EOS → ДОЧЕКАТИСЯ його на
     шині → лише тоді NULL. Без очікування mp4mux не допише moov. */
  if (src) {
    gst_app_src_end_of_stream (src);
    GstBus *bus = gst_element_get_bus (pout);
    GstMessage *msg = gst_bus_timed_pop_filtered (
        bus, 10 * GST_SECOND,
        (GstMessageType) (GST_MESSAGE_EOS | GST_MESSAGE_ERROR));
    if (!msg) g_printerr ("EOS не дійшов за 10 с — файл може бути битий\n");
    else      gst_message_unref (msg);
    gst_object_unref (bus);
  }

  gst_element_set_state (pin, GST_STATE_NULL);
  if (pout) gst_element_set_state (pout, GST_STATE_NULL);

  if (known) gst_caps_unref (known);
  if (src)   gst_object_unref (src);
  if (pout)  gst_object_unref (pout);
  gst_object_unref (sink);
  gst_object_unref (pin);

  g_printerr ("кадрів: %" G_GUINT64_FORMAT "\n", frames);
  return 0;
}
```

Щоб віддавати картинку в мережу замість файлу, змінюється один хвіст рядка:

```
appsrc name=in format=time is-live=true ! videoconvert !
x264enc tune=zerolatency speed-preset=ultrafast bitrate=2000 key-int-max=30 !
rtph264pay config-interval=1 pt=96 ! udpsink host=192.168.1.50 port=5000
```

`config-interval=1` тут не косметика: він повторює SPS і PPS раз на секунду, інакше приймач, який під'єднався посеред трансляції, не зможе почати декодувати — [заголовки потоку H.264](book:algorithms/h264-nal-structure) прийшли й пішли до його появи.

## Три місця, де така програма зазвичай бреше

### Крок рядка приходить із буфера, а не з арифметики

Найдорожча помилка в усьому циклі — рахувати адресу пікселя як `data + y * width * 3`. Пам'ять під відео вирівняна: кожен рядок починається з адреси, кратної 16, 32 чи 64 байтам, бо так люблять векторні інструкції й апаратні блоки.

**Умова: кадр 1366×768 у форматі BGR, вирівнювання рядка на 64 байти.**

```
щільний рядок  = 1366 × 3            = 4098 байтів
крок рядка     = ⌈4098 / 64⌉ × 64    = 65 × 64 = 4160 байтів
доповнення     = 4160 − 4098         = 62 байти на рядок
зсув на рядку 100 = 100 × 62         = 6200 байтів ≈ 1.5 рядка
```

Код, що вважає рядок щільним, на сотому рядку читає вже на півтора рядка вбік — звідси знамениті косі смуги замість картинки. І це не той випадок, коли можна один раз обчислити крок і забути: `gst_video_frame_map()` спочатку шукає на буфері `GstVideoMeta` і, якщо вона є, бере кроки й зсуви площин **з неї**, а не з `GstVideoInfo`. Саме так апаратний декодер повідомляє свій нестандартний крок. Обчислити крок із caps самотужки означає проігнорувати це повідомлення — і саме тому в коді немає `gst_buffer_map()`, хоча він коротший.

Різних розкладок пікселів та їхніх площин — окрема тема: [формати пікселів і буферів зображення](book:algorithms/pixel-formats).

### Час приходить із кадру, а не з лічильника

Спокуса написати `PTS = frames * (GST_SECOND / 30)` величезна, і на ідеальному потоці вона нічим себе не видає. Видає — на реальному. У нас `appsink` налаштований викидати старі кадри: коли обробка не встигає, частина кадрів зникає. Із власною нумерацією записаний файл цього не помічає — тридцять кадрів, що насправді розтягнулися на півтори секунди, лягають у секунду, і відео стає пришвидшеним ривками. Перенесені з вхідного буфера мітки зберігають правду: дірка в часі просто означає, що попередній кадр висить на екрані довше.

Друга половина цього рішення — віднімання `base`. Мітки з камери відлічуються від запуску конвеєра, і перший кадр цілком може мати PTS у кілька сотень мілісекунд. Не віднявши його, ви отримаєте mp4 із порожньою паузою на початку.

`DTS` навмисно лишається невизначеним: порядок декодування визначає кодер, коли розставляє B-кадри, і ставити цю мітку зі свого боку не потрібно й шкідливо.

### Кінець — це подія, а не вихід із циклу

`gst_app_src_end_of_stream()` пускає конвеєром подію EOS, але функція повертається **одразу**, задовго до того, як подія дійде до `filesink`. Між цими двома митями `mp4mux` дописує атом `moov` — таблицю, без якої програвач не знає, де в файлі які кадри. Викликати EOS і одразу перевести конвеєр у NULL — це зупинити мультиплексор посередині роботи й отримати файл із правильними даними, який не відкривається.

Тому після EOS програма чекає повідомлення на шині — механіку цього очікування описує [тема про шину повідомлень](book:media-vision/bus-and-messages). Ту саму пастку знають і з командного рядка: `gst-launch-1.0` має для цього ключ `-e`, який на Ctrl+C шле EOS замість негайного виходу. Обробник `SIGINT` у програмі — рівно той самий ключ, зроблений руками: він лише виставляє прапорець, а весь коректний фінал відбувається в звичайному коді після циклу.

## Скільки байтів справді рухається

У коді видно одну копію — `view.copyTo (dst)`. Порахуймо, скільки їх насправді.

![Таблиця кроків циклу з обсягом записаних байтів на кожному](/reference/media-vision/gstreamer/appsink-appsrc/img/copy-map.svg)

*Копія, через яку заведено переживати, — трохи більш ніж половина всього запису; решти не видно в коді взагалі.*

**Умова: кадр 1280×720 BGR, 30 кадрів за секунду, конвеєр із лістингу.**

```
пікселів у кадрі  = 1280 × 720            = 921 600
кадр BGR          = 921600 × 3            = 2 764 800 байтів ≈ 2.76 МБ
кадр I420         = 921600 × 1.5          = 1 382 400 байтів ≈ 1.38 МБ
кадр H.264        = 4000000 / 8 / 30      =    16 667 байтів ≈ 0.017 МБ

записано на кадр:
  view.copyTo(dst)                          2.76 МБ
  cv::cvtColor у process()                  0.92 МБ
  рамка й напис                           ≈ 0.04 МБ
  videoconvert: BGR → I420                  1.38 МБ
  x264enc при 4000 кбіт/с                 ≈ 0.017 МБ
                                          ──────────
  разом                                   ≈ 5.12 МБ

при 30 к/с       = 5.12 × 30              ≈ 153 МБ/с
стиснення        = 2764800 / 16667        ≈ 166 разів
```

Висновок неприємний для інтуїції: свідома копія — це 54 % записаних байтів, а решта 46 % робиться там, де в тексті програми немає ані слова про пам'ять. `cvtColor` виглядає як «просто аналіз», хоча щоразу виділяє новий мегабайт і заповнює його. `videoconvert` виглядає як службовий елемент, хоча перекладає кожен кадр цілком.

**Копія в `copyTo` обов'язкова.** Пам'ять вхідного буфера прийшла з [пулу декодера](book:media-vision/buffers-and-memory), позначена лише для читання й повертається в пул, щойно ви відпустите семпл. Малювати по ній заборонено, тримати її довше — означає посадити конвеєр на голодування. Обійти `make_writable()` теж не вийде: доки живий семпл, він тримає своє посилання на буфер, лічильник більший за одиницю, і `gst_buffer_make_writable()` чесно зробить ту саму копію, тільки непомітно.

**А от решта прибирається по-справжньому.** Якщо аналізові потрібна яскравість, а не колір — замовляйте в `appsink` не BGR, а NV12 і кладіть `cv::Mat` просто поверх першої площини:

```cpp
/* appsink: video/x-raw,format=NV12 — площина 0 це вже готова яскравість */
cv::Mat luma (GST_VIDEO_FRAME_HEIGHT (&in_f),
              GST_VIDEO_FRAME_WIDTH  (&in_f), CV_8UC1,
              GST_VIDEO_FRAME_PLANE_DATA   (&in_f, 0),
              GST_VIDEO_FRAME_PLANE_STRIDE (&in_f, 0));
```

`cvtColor` зникає — яскравість уже обчислена декодером, вона й лежить у площині 0. Копія кадру меншає вдвічі: NV12 — це 1.5 байта на піксель проти трьох. `videoconvert` стає прохідним, бо `x264enc` приймає NV12 напряму (як і I420, Y42B, Y444 та GRAY8). Разом виходить 1.38 + 0.04 + 0.017 ≈ 1.44 МБ запису на кадр замість 5.12 — утричі з половиною менше при тій самій роботі. Ціна — колір лежить в окремій площині з половинною роздільністю й переплетеними U та V, тож малювати кольорову рамку доведеться в дві площини, а не в одну.

Гранична економія — не копіювати взагалі: якщо ваш код лише **дивиться** на кадр і нічого не малює, вихідний буфер не потрібен, і в `appsrc` можна віддати той самий вхідний через `gst_buffer_ref (inbuf)`. Тоді на кадр не припадає жодної копії. Плата чесна й помітна: буфер із пулу декодера тепер живе ще й у черзі `appsrc`, а пул скінченний, тож `max-bytes` на `appsrc` доводиться тримати маленьким — інакше рівно та сама економія обертається зупинкою першого конвеєра.

## Пастки, які видно лише в біді

### `copyTo`, що тихо перевиділяє пам'ять

`cv::Mat::copyTo` не пише в приймач наосліп: він спершу викликає `create()`, і якщо розмір або тип не збігаються — **перевиділяє** приймач власною пам'яттю OpenCV. У нашому циклі `dst` — заголовок над буфером GStreamer, і збіг тримається на тому, що `GstVideoInfo` один і той самий для обох боків. Помиліться на піксель — і `copyTo` мовчки відв'яже `dst` від буфера, намалює все у своїй пам'яті, а в конвеєр піде щойно виділений, ніколи не заповнений буфер: рівний сірий кадр без жодної помилки в журналі. Це не гіпотетична вигадка, а стандартна поведінка [моделі пам'яті `cv::Mat`](book:media-vision/mat-memory-model), і саме тому розмір вихідного буфера в лістингу береться з того самого `info`, що й розміри `dst`.

### Незакопійований `Mat`, відданий в інший потік

`cv::Mat`, збудований поверх пам'яті буфера, не володіє нею й не рахує на неї посилань — він лише вказівник із розмірами й кроком. Чинний він рівно доти, доки живий і відображений семпл.

![Часова діаграма: перший потік відпускає семпл, декодер переписує пам'ять, другий потік читає вже чужий кадр](/reference/media-vision/gstreamer/appsink-appsrc/img/dangling-mat.svg)

*Пам'ять не зникає — її просто заповнює наступний кадр, тому падіння не буде: буде тихо неправильний результат.*

Найгірше в цій помилці — що вона не падає. Пам'ять із пулу залишається доступною, змінюється лише її вміст, тож детектор працює й повертає координати — іноді навіть правдоподібні. На порожньому стенді все чудово: обробник устигає прочитати кадр раніше, ніж декодер дійде до того самого буфера. Під навантаженням результати починають «плисти» без жодної закономірності.

Правило просте й без винятків: **через межу потоку передається лише те, що ви скопіювали**, тобто `Mat`, який володіє власною пам'яттю. Або `view.clone()`, або — як у лістингу — копія в буфер, яким володієте ви. Про те, які взагалі бувають безпечні види поверх чужої пам'яті, — [окрема тема](book:media-vision/mat-views-no-copy); загальні вимоги до коду, що ходить між потоками, — у [темі про потокову безпеку](book:programming/thread-safety).

### Зупинка конвеєра зсередини `new_sample`

Наш цикл витягує кадри сам, і саме тому в ньому немає найпоширенішого зависання. Якби ми взяли зворотний виклик `new_sample`, спокуса написала б у ньому щось на кшталт «побачив останній кадр — зупиняю конвеєр»:

```cpp
/* ТАК НЕ МОЖНА: new_sample виконується В ПОТОЦІ ПЕРЕДАВАННЯ */
static GstFlowReturn new_sample (GstAppSink *s, gpointer user)
{
  if (enough ())
    gst_element_set_state (pipeline, GST_STATE_NULL);   /* зависне назавжди */
  return GST_FLOW_OK;
}
```

`gst_element_set_state (…, NULL)` зупиняє потоки передавання й **чекає**, поки вони справді зупиняться. Але ви **і є** потік передавання: він не завершиться, доки не повернеться ваш зворотний виклик, а ваш зворотний виклик не повернеться, доки не завершиться перехід. Це підручниковий [глухий кут](book:programming/deadlock) із двох учасників, де другий учасник — ви самі.

Правильно зі зворотного виклику лише **повідомити**: виставити прапорець, покласти щось у свою чергу — і зупинити конвеєр із головного потоку або з обробника шини. Той самий зворотний виклик має власний спосіб сказати «мені досить» без зупинки: повернути `GST_FLOW_EOS` замість `GST_FLOW_OK` — і потік вище за течією згорнеться сам, штатно.

### `block=true`, увімкнений не з того потоку

У `build_output()` на `appsrc` стоїть `block=TRUE`, і це рішення тримається на одному факті: штовхаємо ми зі свого циклу. Тоді блокування дає рівно те, чого від нього хочуть, — цикл сам вирівнюється за темпом кодера, черга не росте, пам'ять не тече.

Перенесіть той самий рядок у програму, де кадр штовхають прямо із `new_sample`, — і властивість поміняє знак. Блокуватися почне потік передавання **першого** конвеєра, тобто той, у якому працює декодер. Затримка кодера миттєво стане затримкою камери, з усіма наслідками: переповненими DMA-буферами драйвера й кадрами, втраченими там, де ви цього не бачите. У такій топології `appsrc` мусить мати `block=false` плюс політику викидання, а вирівнювати темп треба своєю чергою між двома потоками, а не властивістю елемента.

Симетричне зауваження стосується `max-bytes`. Типове значення — 200 000 байтів, тобто 7 % одного кадру 1280×720: із ним `appsrc` вважає себе переповненим ще до того, як прийме перший кадр. У лістингу воно виставлене в чотири розміри кадру — не з любові до круглих чисел, а тому що чотири кадри при 30 к/с — це 133 мс запасу, приблизно стільки, скільки кодер може затриматися на важкому ключовому кадрі, не змушуючи цикл чекати.
