# 📋 Мова рядка-конвеєра: `gst-launch-1.0` і `gst_parse_launch`

Увесь конвеєр GStreamer записують одним текстовим рядком — і це не спрощена «демонстраційна форма», а повноцінна мова опису з власною граматикою, типами значень і правилами екранування; тут зібрано її цілком: кожен знак, кожен тип поля, кожен прапорець утиліти й кожен код помилки розбору.

Один парсер обслуговує два входи. Утиліта `gst-launch-1.0` склеює свої аргументи пробілами й віддає готовий рядок у `gst_parse_launchv()`; програма на C передає такий самий рядок у `gst_parse_launch()`. Тому все, що написано нижче, однаково дійсне для команди в терміналі, для рядка в конфігураційному файлі й для рядка, зашитого в код.

## Граматика на одній сторінці

```
ОПИС         := ФРАГМЕНТ [ФРАГМЕНТ ...]
ФРАГМЕНТ     := ЕЛЕМЕНТ | ЗВ'ЯЗОК | CAPS | БІН
ЕЛЕМЕНТ      := тип [ВЛАСТИВІСТЬ ...] [@preset=назва]
ВЛАСТИВІСТЬ  := ім'я=значення
ЗВ'ЯЗОК      := [елемент][.пад[,пад ...]]  !  [елемент][.пад[,пад ...]]
              | [елемент][.пад[,пад ...]]  :  [елемент][.пад[,пад ...]]
CAPS         := тип-медіа [(ознака)] [, поле=[(тип)]значення ...] [; CAPS ...]
БІН          := [тип-біна].( ОПИС )
```

Ключове слово тут — **фрагмент**. Опис не є ланцюгом зліва направо; це набір фрагментів, які парсер зводить докупи за іменами. Тому рядок із трьома гілками виглядає як три окремі ланцюжки, зшиті посиланнями на одне ім'я, — і порядок цих ланцюжків у рядку значення не має.

## Елемент і його властивості

Перше слово фрагмента — **тип елемента**, тобто те ім'я, за яким фабрику шукають у реєстрі плагінів: `filesrc`, `avdec_h264`, `autovideosink`. Далі йдуть властивості у вигляді `ім'я=значення`, розділені пробілами.

Що можна писати як значення, залежить від типу властивості в системі об'єктів GObject, на якій стоїть уся бібліотека ([GObject під GStreamer](topic:media-vision/gobject-basics)). Перелік типів і допустимих значень для конкретного елемента показує `gst-inspect-1.0 <тип>` — це єдине надійне джерело, бо імена властивостей у різних елементів не уніфіковані.

| Тип властивості | Як записують | Приклад |
|---|---|---|
| ціле, ціле без знака | десяткове число | `num-buffers=300`, `port=5000` |
| дробове | крапка як роздільник | `volume=0.8` |
| булеве | `true` / `false` (регістр не важить), `1` / `0` | `sync=false` |
| рядок | без лапок, доки нема пробілів і спецзнаків | `location=/tmp/out.mp4` |
| перелік (enum) | повна назва, коротке прізвисько (nick) або число | `tune=zerolatency` |
| набір прапорців (flags) | прізвиська через `+` або число | `flags=video+audio` |
| дріб (fraction) | `чисельник/знаменник` | `aspect-ratio=16/9` |
| caps | опис caps як значення | `caps=video/x-raw,format=I420` |
| елемент | опис конвеєра в лапках — парсер збере з нього бін | `video-sink="videoconvert ! autovideosink"` |

Остання строчка таблиці — не екзотика, а щоденний прийом: властивість типу «елемент» приймає цілий опис, і `playbin video-filter="mfxvpp rotation=90" video-sink="mfxsink display=egl fullscreen=true"` збирає два вкладені біни просто з тексту.

Окремо стоїть `@preset=назва` — не властивість, а готовий набір значень, збережений для цього типу елемента; його застосовують перед рештою властивостей у фрагменті.

> 🔧 **Навіщо це.** Дві помилки у властивостях поводяться **по-різному**, і це найпідступніша асиметрія всієї мови. Неіснуюче **ім'я** властивості валить розбір із виразною помилкою `no such property`. А значення **неправильного типу** мовчить: функція, що присвоює аргумент із рядка, за документацією «тихо повертається, коли значення не вдається перетворити до типу властивості». Елемент лишається зі старим значенням, конвеєр запускається, поводиться не так, як написано, — і в рядку немає жодної підказки. Тому властивість, яка «не подіяла», перевіряють не переписуванням рядка, а ключем `-v`: він друкує фактичні значення.

## Знак `!` — з'єднання, а не передача даних

Знак оклику з'єднує елемент ліворуч від себе з елементом праворуч. Це не оператор потоку й не труба: під час розбору він виконує звичайне з'єднання падів, тобто те саме, що робить `gst_element_link()` у коді. Уся передача даних починається пізніше, коли конвеєр перейде в робочий стан.

Якщо пади не названо, парсер перебирає всі можливі пари й бере першу сумісну. Якщо названо — з'єднує саме їх.

| Запис | Що робить |
|---|---|
| `a ! b` | з'єднати `a` з `b`, пади дібрати самому |
| `a.src ! b.sink` | з'єднати названі пади явно |
| `overlay.video_sink` | приєднатися до конкретного пада названого елемента |
| `a.src_0,src_1 ! b.sink_0,sink_1` | кілька з'єднань за один раз, по порядку; кількість імен з обох боків має збігатися |
| `a : b` | з'єднати **всі** можливі пари падів між елементами |

Двокрапка — інструмент для багатопадових елементів: там, де `!` дає одне з'єднання, `:` з'єднує все, що зійшлося. Її описує чинна граматика; на давніших складаннях парсера її може не бути, і тоді рядок падає із синтаксичною помилкою.

Порожній бік теж дозволено: `a !` без правого сусіда — це не з'єднання, а помилка `link without sink element`, тож зайвий знак оклику наприкінці рядка ловиться одразу.

## Caps-фільтр — обмеження стику

Фрагмент між двома знаками оклику, який не схожий на елемент, парсер читає як **caps** і мовчки перетворює на елемент `capsfilter` із виставленою властивістю `caps`. Тобто ці два рядки тотожні:

```sh
gst-launch-1.0 videotestsrc ! video/x-raw,format=GRAY8 ! videoconvert ! autovideosink
gst-launch-1.0 videotestsrc ! capsfilter caps=video/x-raw,format=GRAY8 ! videoconvert ! autovideosink
```

`capsfilter` не чіпає дані — він пропускає їх наскрізь і лише **звужує множину форматів**, про які дозволено домовитися сусідам ([узгодження caps](topic:media-vision/caps-negotiation)). Звідси головна пастка: caps-фільтр нічого не перетворює. Рядок `videotestsrc ! video/x-raw,format=I420 ! autovideosink` не «переведе» формат — він або змусить `videotestsrc` віддавати саме `I420` (бо той уміє), або зупинить конвеєр помилкою `not-negotiated`. Перетворення робить елемент — `videoconvert`, `audioconvert`, `videoscale`, — а фільтр лише каже йому, що саме віддавати на виході.

**Поля caps типізовані**, і тип пишуть у дужках перед значенням. Без дужок парсер вгадує в порядку: ціле → дробове → булеве → рядок.

| Позначка типу | Що приймає | Приклад поля |
|---|---|---|
| `i`, `int` | ціле або діапазон | `width=(int)1280` |
| `f`, `float` | дробове або діапазон | `quality=(float)0.9` |
| `b`, `bool`, `boolean` | булеве | `interlaced=(boolean)false` |
| `s`, `str`, `string` | рядок | `format=(string)NV12` |
| `fraction` | дріб | `framerate=(fraction)30/1` |
| `l`, `list` | список значень | `format=(string){ NV12, I420 }` |

Значення буває не одиничним, і саме на цьому мова caps виграє в звичайного «формат=такий»:

| Форма | Значення | Приклад |
|---|---|---|
| `значення` | точно це | `width=1280` |
| `[ min, max ]` | будь-що в межах | `rate=[32000,64000]` |
| `{ a, b, c }` | будь-що зі списку | `format={S16LE,S24LE,S32LE}` |
| `CAPS; CAPS` | будь-яка з альтернатив цілком | `video/x-raw,format=YUY2;video/x-raw,format=YV12` |

Крапка з комою розділяє **цілі структури**, а не поля: `'video/x-raw,format=YUY2;video/x-raw,format=YV12'` каже «або перше цілком, або друге цілком».

Ще одна деталь, помітна на апаратних конвеєрах: у дужках одразу після типу медіа стоїть **ознака пам'яті** — `video/x-raw(memory:NVMM)`, `video/x-raw(memory:GLMemory)`. Це не поле, а вимога до того, **де** лежить кадр; caps із різними ознаками несумісні, навіть коли всі поля збігаються, і саме тому рядок із апаратним декодером не стикується з програмним стоком без явного елемента-завантажувача.

## Ім'я елемента й крапка

Властивість `name=` є в кожного елемента, і вона перетворює його на точку, до якої можна звернутися з будь-якого місця рядка. Звертання — ім'я з крапкою.

```sh
# розгалуження: один потік у вікно і у файл
gst-launch-1.0 -e videotestsrc ! videoconvert ! tee name=t \
  t. ! queue ! autovideosink \
  t. ! queue ! x264enc tune=zerolatency ! mp4mux ! filesink location=out.mp4
```

`t.` праворуч від оклику означає «сюди, у цей елемент», ліворуч — «звідси, з цього елемента». Кожне звертання до `tee` просить у нього **новий вихідний пад**: такі пади створюють на вимогу, а не мають заздалегідь ([пади і з'єднання](topic:media-vision/pads-and-linking)). Черга на кожній гілці після `tee` — не прикраса: без неї обидві гілки крутить одна нитка й вони починають чекати одна одну.

Крапка з іменем пада після неї вибирає **конкретний** пад, коли їх кілька й вони не рівноправні:

```sh
gst-launch-1.0 textoverlay name=overlay ! videoconvert ! autovideosink \
  filesrc location=movie.avi ! decodebin ! videoconvert ! overlay.video_sink \
  filesrc location=movie.srt ! subparse ! overlay.text_sink
```

Тут добре видно природу опису як набору фрагментів: три незалежні ланцюжки, зшиті двома звертаннями до `overlay`.

Окремий випадок — пади, яких на момент розбору **ще не існує**. Демультиплексор чи `decodebin` створює вихідні пади лише тоді, коли розбере заголовки й побачить, що всередині. Парсер це передбачає: він запам'ятовує намір і виконує **відкладене з'єднання**, щойно потрібний пад з'явиться.

```sh
gst-launch-1.0 filesrc location=movie.mkv ! decodebin name=d \
  d. ! queue ! videoconvert ! autovideosink \
  d. ! queue ! audioconvert ! audioresample ! autoaudiosink
```

Якщо пад так і не з'явиться — у файлі просто немає звуку, — розбір це не завалить, але помилка `delayed link` у журналі буде.

## Дужки: бін як один фрагмент

Круглі дужки складають кілька елементів в один **бін**, який назовні поводиться як один елемент.

| Запис | Що дає |
|---|---|
| `( a ! b ! c )` | звичайний бін із трьох елементів |
| `тип.( ... )` | бін заданого типу замість типового |
| `bin.( ... )` | явно `GstBin` |

Дужки потрібні там, де фрагмент має бути одним цілим: як значення властивості типу «елемент» або як лівий бік `:`-з'єднання. У простому лінійному рядку вони зайві.

Всередину вкладеного біна дістаються **подвійною двокрапкою**: `дитина::властивість`. Схема рекурсивна — `дитина1::дитина2::властивість` теж дійсне, доки кожен рівень уміє віддавати своїх дітей за іменем.

## Лапки й екранування: два рівні, а не один

Найчастіша причина того, що «рядок із інтернету не працює», — не GStreamer. Текст проходить **дві** обробки: спершу його ріже оболонка, і лише те, що вціліло, бачить парсер ([розкриття й лапки](topic:unix-linux/expansion-and-quoting)).

| Знак | Що з ним робить оболонка | Що він означає для парсера |
|---|---|---|
| `!` | в **інтерактивному** bash розкриває історію команд | з'єднання |
| пробіл | ділить на аргументи | розділяє фрагменти й властивості |
| `{ }` | bash розкриває дужки: `{a,b}` → два слова | список значень у caps |
| `( )` | підоболонка | бін |
| `;` `&` | розділювач команд, фон | альтернатива caps |
| `"` `'` | знімає одну пару лапок | групує токен |
| `\` | екранує наступний знак | екранує наступний знак |

Практичні правила виводяться звідси механічно:

- **Caps завжди в одинарних лапках.** Через `{ }` і `;`: незахищене `format={S16LE,S24LE}` bash перетворить на два окремі слова `format=S16LE` і `format=S24LE`, і парсер побачить безглуздя. Саме тому в офіційних прикладах caps зі списками стоять у лапках: `'audio/x-raw,rate=[32000,64000],format={S16LE,S24LE,S32LE}'`.
- **Шлях із пробілом — у лапках:** `location="/home/user/my video.mp4"`.
- **Опис як значення властивості — у подвійних лапках:** `video-sink="videoconvert ! autovideosink"`. Тут лапки знімає оболонка, а парсер бачить властивість, значення якої сам розбирає як опис.
- **Знак оклику в інтерактивній оболонці.** У скрипті проблеми немає; у живій сесії bash `!` у подвійних лапках усе ще розкриває історію, а в одинарних — ні.

Пробіли між фрагментами вільні: `gst-launch-1.0` склеює свої аргументи пробілом, тож рядок можна ламати на кілька рядків зворотним слешем і розставляти пробіли для читабельності як завгодно.

## Прапорці утиліти

```
gst-launch-1.0 [ПРАПОРЦІ] ОПИС-КОНВЕЄРА
```

| Прапорець | Дія |
|---|---|
| `-v`, `--verbose` | друкувати стан і сповіщення про властивості — зокрема **фактично узгоджені caps на кожному паді** |
| `-m`, `--messages` | друкувати повідомлення, що надходять на шину конвеєра |
| `-t`, `--tags` | друкувати теги (метадані потоку) |
| `-e`, `--eos-on-shutdown` | надіслати джерелам EOS **перед** зупинкою |
| `-q`, `--quiet` | нічого не друкувати про поступ |
| `-f`, `--no-fault` | не ставити обробник збою |
| `--no-position` | не друкувати поточну позицію |
| `--force-position` | друкувати позицію, навіть коли вивід не термінал |

Два з них варті окремого слова.

`-v` — головний діагностичний прапорець мови. Він друкує рядки на кшталт `…/GstVideoTestSrc:videotestsrc0.GstPad:src: caps = video/x-raw, format=(string)I420, width=(int)320…`, тобто показує, **про що насправді домовилися** пади, а не про що ви просили. Різниця між написаним у рядку й надрукованим у виводі — це відповідь на більшість питань «чому картинка не така».

`-e` рятує файли. Без нього Ctrl+C гасить конвеєр негайно: мультиплексор не отримує кінця потоку, не дописує таблицю зміщень, і `out.mp4` лишається нечитабельним огризком, хоча всі кадри в ньому є. З `-e` джерела спершу отримують EOS, він доходить ланцюгом до мультиплексора, той закриває файл — і аж тоді конвеєр гаситься ([стани конвеєра](topic:media-vision/states-lifecycle)). Правило просте: **пишете у файл — ставте `-e`**.

`-m` показує сирі повідомлення шини — саме той канал, яким конвеєр говорить із програмою ([шина повідомлень](topic:media-vision/bus-and-messages)).

Крім власних прапорців утиліта приймає спільні ключі бібліотеки й читає змінні оточення:

| Ключ або змінна | Дія |
|---|---|
| `--gst-debug-level=N` | поріг журналу: 0 нічого · 1 ERROR · 2 WARNING · 3 FIXME · 4 INFO · 5 DEBUG · 6 LOG · 7 TRACE · 9 MEMDUMP |
| `--gst-debug=категорія:N` | рівень для окремих категорій, через кому |
| `--gst-debug-help` | показати всі категорії |
| `--gst-plugin-path=ШЛЯХ` | додаткові теки з плагінами |
| `GST_DEBUG=…` | те саме, що `--gst-debug`, через оточення |
| `GST_DEBUG_FILE=…` | скерувати журнал у файл замість терміналу |
| `GST_DEBUG_DUMP_DOT_DIR=…` | скидати граф конвеєра у `.dot` |
| `GST_PLUGIN_PATH=…` | те саме, що `--gst-plugin-path` |
| `GST_REGISTRY_UPDATE=no` | не перебудовувати реєстр плагінів |

`GST_DEBUG_DUMP_DOT_DIR` заслуговує на окремий рядок саме в довіднику мови: `gst-launch-1.0` сам скидає граф на **кожній зміні стану**, тож ви отримуєте набір файлів `…NULL_READY.dot`, `…READY_PAUSED.dot`, `…PAUSED_PLAYING.dot`. Це готова картинка того, що парсер справді зібрав із вашого рядка, — з усіма вставленими `capsfilter` і узгодженими форматами на ланках ([діагностика конвеєра](topic:media-vision/pipeline-debugging)). Теку GStreamer не створює — вона має існувати заздалегідь.

## Той самий рядок у коді

```c
#include <gst/gst.h>

int main (int argc, char *argv[])
{
  gst_init (&argc, &argv);

  GError *err = NULL;
  GstElement *pipeline = gst_parse_launch (
      "videotestsrc num-buffers=300 name=src "
      "! video/x-raw,width=1280,height=720,framerate=30/1 "
      "! videoconvert ! autovideosink",
      &err);

  /* УВАГА: err може бути виставлено й тоді, коли конвеєр повернувся —
     це «часткова» помилка, конвеєр зібрано не цілком. */
  if (err != NULL) {
    g_printerr ("розбір: %s\n", err->message);
    g_clear_error (&err);
  }
  if (pipeline == NULL)
    return 1;

  /* саме заради цього рядка елементам дають name= */
  GstElement *src = gst_bin_get_by_name (GST_BIN (pipeline), "src");
  g_object_set (src, "pattern", 18, NULL);   /* ball */
  gst_object_unref (src);

  gst_element_set_state (pipeline, GST_STATE_PLAYING);
  /* ... тут програма слухає шину ... */
  gst_element_set_state (pipeline, GST_STATE_NULL);
  gst_object_unref (pipeline);
  return 0;
}
```

| Функція | Що робить |
|---|---|
| `GstElement *gst_parse_launch (const gchar *опис, GError **err)` | зібрати конвеєр із рядка |
| `GstElement *gst_parse_launchv (const gchar **argv, GError **err)` | те саме з масиву аргументів (ним і користується утиліта) |
| `GstElement *gst_parse_launch_full (const gchar *опис, GstParseContext *ctx, GstParseFlags flags, GError **err)` | плюс прапорці розбору й контекст із переліком відсутніх елементів |
| `GstElement *gst_parse_bin_from_description (const gchar *опис, gboolean ghost_unlinked_pads, GError **err)` | зібрати **бін** для вставляння у вже наявний конвеєр |

`GstParseFlags` міняють поведінку на помилках і на формі результату:

| Прапорець | Дія |
|---|---|
| `GST_PARSE_FLAG_NONE` | типова поведінка |
| `GST_PARSE_FLAG_FATAL_ERRORS` | на будь-якій помилці повертати `NULL`, а не половину конвеєра |
| `GST_PARSE_FLAG_NO_SINGLE_ELEMENT_BINS` | опис з одного елемента повертати самим елементом, без обгортки-біна |
| `GST_PARSE_FLAG_PLACE_IN_BIN` | покласти результат у `GstBin`, а не в `GstPipeline` |

Перший із них варто ставити майже завжди: типова поведінка «повернути частково зібране» зручна для інтерактивного інструмента, але в програмі дає конвеєр, який існує, запускається й мовчки не робить половини роботи.

## Помилки розбору й що вони означають

Парсер повертає їх у домені `GST_PARSE_ERROR`; утиліта друкує їх рядком `WARNING: erroneous pipeline: …`.

| Код | Текст, який видно | Причина й куди дивитися |
|---|---|---|
| `SYNTAX` | `syntax error` | рядок покалічила оболонка — лапки, `{ }`, `!`, зайвий пробіл |
| `NO_SUCH_ELEMENT` | `no element "xyz"` | плагіна немає в реєстрі; перевіряти `gst-inspect-1.0 xyz` ([модель плагінів](topic:media-vision/plugin-model)) |
| `NO_SUCH_PROPERTY` | `no property "x" in element "y"` | описка в імені або властивість іншої версії елемента |
| `COULD_NOT_SET_PROPERTY` | `could not set property` | значення не лягло в тип |
| `LINK` | `could not link a to b` | статичні caps сусідів не перетинаються — бракує перетворювача |
| `DELAYED_LINK` | `failed delayed linking` | очікуваний пад так і не з'явився: у потоці немає такої доріжки |
| `EMPTY_BIN` | `empty bin` | порожні дужки |
| `EMPTY` | `empty pipeline not allowed` | порожній опис |

Межа між цими помилками й помилками виконання проходить чітко. Усе з таблиці стається **до** запуску: конвеєра ще нема, дані не текли. Помилки на кшталт `not-negotiated` чи `Internal data stream error` — уже інша порода: рядок розібрано правильно, елементи створено, і зупинилися вони на домовленості про формат або на самих даних. Якщо утиліта надрукувала `erroneous pipeline` — виправляти треба текст; якщо надрукувала `ERROR: from element …` — текст правильний, а не сходиться зміст.

## Чого ця мова не вміє

Рядок описує **топологію й початкові значення** — і нічого більше. У ньому немає місця для реакції на подію, для розгалуження за умовою, для перебудови конвеєра на льоту, для доступу до кадрів із власного коду й для обробки помилок інакше, ніж «надрукувати й зупинитися». Обробники сигналів, підписка на шину, зміна властивостей у відповідь на стан — усе це живе лише в коді.

Звідси й межа застосування: рядок — це інструмент **перевірки й діагностики**. Ним за хвилину з'ясовують, чи взагалі камера віддає потік, чи є в системі потрібний декодер і які формати узгодилися насправді. Готова програма потім повторює ту саму топологію — часто тим самим `gst_parse_launch()`, але вже з іменами на елементах, підпискою на шину й власною реакцією на кожну біду.
