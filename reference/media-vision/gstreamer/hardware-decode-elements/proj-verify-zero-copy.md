# ⚙️ Довести, що копії немає: програма-вимірювач

Ця програма на C бере довільний конвеєр із апаратним декодером і відповідає числом на питання, на яке назва елемента не відповідає ніколи: чи залишився кадр у пам'яті пристрою, чи його вже переписали до вас. Вона друкує узгоджену ознаку пам'яті на вході `appsink`, розбирає буфер на шматки й називає тип кожного, а тоді окремо міряє, скільки коштує подивитися на пікселі — щоб «нуль копій» перестало бути вірою й стало вимірюванням.

## Три питання, які треба рознести

Спокуса — запустити конвеєр, глянути на завантаження процесора й зробити висновок. Так не вийде: одне число змішує розбір контейнера, декодування, копіювання кадру, перетворення формату й показ. Коли воно високе, ви знаєте, що щось не так, але не знаєте що. Потрібні три окремі відповіді, і кожна вимірюється по-різному.

**На чому домовилися сусіди.** [Узгодження caps](book:media-vision/caps-negotiation) закінчується конкретним набором можливостей на кожному з'єднанні, і саме там записано, у якому представленні прийде кадр. Ознака пам'яті — частина цього набору, тож питати треба не елемент, а **пад**: узяти sink-пад `appsink` і прочитати з нього поточні caps. Це дешева перевірка, яка коштує нуль на кадр і відсіює половину помилок одразу.

**З чого насправді зроблений буфер.** Caps — це домовленість, буфер — факт, і вони розходяться частіше, ніж хочеться. Елемент може узгодити `memory:DMABuf`, а віддати буфер, у якому один шматок дескрипторний, а другий — звичайна пам'ять, дозбирана в обхід. [Буфер у GStreamer](book:media-vision/buffers-and-memory) — не масив байтів, а список шматків `GstMemory`, кожен зі своїм алокатором; отже, треба пройти список і назвати кожен шматок.

**Скільки коштує подивитися.** Це найважливіше і найтонше. Апаратне декодування має сенс доти, доки процесор кадру не чіпає; щойно ви викликали `gst_video_frame_map` з наміром читати, ви або платите за перетин межі, або не платите — і це залежить не від вашого коду, а від того, як пам'ять відображена. Здогадатися не можна. Можна тільки виміряти.

## Чому вимірювання самого мапування бреше

Тут закопана пастка, через яку більшість саморобних вимірювань показують неправду.

Коли буфер зроблений із дескриптора спільного буфера, `gst_video_frame_map` під капотом робить `mmap` цього дескриптора. [Відображення файлу в пам'ять](book:unix-linux/mmap-model) — операція майже безкоштовна: ядро лише робить запис у таблиці областей процесу, жодна фізична сторінка при цьому не під'єднується. Сторінки під'єднуються потім, поштучно, [сторінковими збоями](book:unix-linux/page-fault) — у мить, коли програма вперше торкається адреси.

Наслідок прямий: секундомір навколо самого `map` покаже десятки мікросекунд і дозволить радісно оголосити мапування безкоштовним. Насправді на цю мить не заплачено нічого — рахунок прийде пізніше й піде на інший рядок, розмазаний по вашому власному циклу обробки. Тому секундомірів має бути два: перший — на виклик мапування, другий — на **дотик** до всіх пікселів. Перший каже, скільки коштує домовитися; другий — скільки коштує подивитися.

Дотикатися треба з кроком у [кеш-лінію](book:programming/cache), а не по одному байту на сторінку. Читання одного байта підтягує з пам'яті всю лінію цілком, тож крок 64 байти дає чесний рахунок: приїжджає весь кадр, а ми не витрачаємо час на арифметику. Проходити ж усе поспіль теж не варто — ми міряємо шлях байтів через шину, а не швидкість власного циклу.

## Програма

Мова тут не обирається: увесь відповідний інтерфейс GStreamer — це C, поля `GstMemory` й `GstAllocator` читаються прямо зі структур, а вимірювання в десятки мікросекунд не переживе жодного проміжного шару.

```c
/* zerocopy.c — чи справді кадр лишився в пристрої.
 *
 * gcc -O2 -Wall zerocopy.c -o zerocopy $(pkg-config --cflags --libs \
 *     gstreamer-1.0 gstreamer-app-1.0 gstreamer-video-1.0 gstreamer-allocators-1.0)
 */
#include <gst/gst.h>
#include <gst/app/gstappsink.h>
#include <gst/video/video.h>
#include <gst/allocators/gstdmabuf.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

#define MAX_HOLD 256

/* ---------- дрібна статистика ---------- */

typedef struct { gint64 *v; guint n, cap; } Series;

static void
series_add (Series * s, gint64 x)
{
  if (s->n == s->cap) {
    s->cap = s->cap ? s->cap * 2 : 256;
    s->v = g_renew (gint64, s->v, s->cap);
  }
  s->v[s->n++] = x;
}

static int
cmp_i64 (const void *a, const void *b)
{
  gint64 x = *(const gint64 *) a, y = *(const gint64 *) b;
  return (x > y) - (x < y);
}

/* Середнє тут не годиться: кілька витіснень планувальника тягнуть його вгору
   й ховають справжню ціну. Мінімум показує цю ціну без завад, медіана —
   типовий кадр, p95 — те, від чого захлинається показ. */
static gint64
series_report (Series * s, const char *what, guint skip)
{
  guint n;
  gint64 *v, med;

  if (s->n <= skip) {
    g_print ("%-24s замало вимірів\n", what);
    return 0;
  }
  n = s->n - skip;
  v = g_malloc (n * sizeof (gint64));
  memcpy (v, s->v + skip, n * sizeof (gint64));
  qsort (v, n, sizeof (gint64), cmp_i64);
  med = v[n / 2];
  g_print ("%-24s мін %8" G_GINT64_FORMAT "  медіана %8" G_GINT64_FORMAT
      "  p95 %8" G_GINT64_FORMAT "  макс %8" G_GINT64_FORMAT "  мкс\n",
      what, v[0], med, v[n * 95 / 100], v[n - 1]);
  g_free (v);
  return med;
}

/* ---------- який це шматок пам'яті ---------- */

/* «Тип» шматка живе не в самому GstMemory, а в його алокаторі, і то рядком.
   gst_memory_is_type() порівнює цей рядок з еталонним, не заглядаючи всередину;
   для друку беремо саме ім'я — так видно навіть типи, про які ми не знали. */
static const char *
memory_kind (GstMemory * mem, int *fd_out)
{
  *fd_out = -1;
  if (gst_is_dmabuf_memory (mem)) {
    *fd_out = gst_dmabuf_memory_get_fd (mem);
    return "DMABuf";
  }
  if (gst_memory_is_type (mem, GST_ALLOCATOR_SYSMEM))
    return "SystemMemory";
  /* VAMemory, CUDAMemory, GLMemory, NVMM… — усе, що плагін завів собі сам */
  return mem->allocator ? mem->allocator->mem_type : "(без алокатора)";
}

static void
dump_memories (GstBuffer * buf)
{
  guint i, n = gst_buffer_n_memory (buf);

  g_print ("буфер: %u шматок(ів), разом %" G_GSIZE_FORMAT " Б\n",
      n, gst_buffer_get_size (buf));
  for (i = 0; i < n; i++) {
    GstMemory *m = gst_buffer_peek_memory (buf, i);
    int fd;
    const char *kind = memory_kind (m, &fd);

    if (fd >= 0)
      g_print ("  [%u] %-14s %9" G_GSIZE_FORMAT " Б  fd=%d\n",
          i, kind, m->size, fd);
    else
      g_print ("  [%u] %-14s %9" G_GSIZE_FORMAT " Б\n", i, kind, m->size);
  }
}

/* ---------- дотик до пікселів ---------- */

static volatile guint64 keep_alive;    /* щоб оптимізатор не викинув цикл */

/* Один байт на кеш-лінію: сторінки таки під'єднуються, і з пам'яті реально
   приїжджає кожна лінія — тобто ми платимо за весь кадр, а не за 1/64 його. */
static gsize
touch_frame (GstVideoFrame * f)
{
  guint p;
  guint64 acc = 0;
  gsize bytes = 0;

  for (p = 0; p < GST_VIDEO_FRAME_N_PLANES (f); p++) {
    const guint8 *base = GST_VIDEO_FRAME_PLANE_DATA (f, p);
    gint stride = GST_VIDEO_FRAME_PLANE_STRIDE (f, p);
    gint h = GST_VIDEO_FRAME_COMP_HEIGHT (f, p);   /* NV12/I420: площина p ↔ компонента p */
    gint x, y;

    if (stride <= 0)                   /* перевернутий кадр — не наш випадок */
      continue;
    for (y = 0; y < h; y++) {
      const guint8 *row = base + (gsize) y * stride;

      for (x = 0; x < stride; x += 64)
        acc += row[x];
    }
    bytes += (gsize) h * stride;
  }
  keep_alive += acc;
  return bytes;
}

/* ---------- GstVideoInfo з caps, з поправкою на DMA_DRM ---------- */

static gboolean
video_info_from_caps (GstVideoInfo * info, GstCaps * caps)
{
  if (gst_video_info_from_caps (info, caps))
    return TRUE;
#if GST_CHECK_VERSION (1, 24, 0)
  {
    /* На caps із format=DMA_DRM звичайний розбір падає: колірний формат
       схований у полі drm-format разом із модифікатором розкладки. */
    GstVideoInfoDmaDrm drm;

    gst_video_info_dma_drm_init (&drm);
    if (gst_video_info_dma_drm_from_caps (&drm, caps)
        && gst_video_info_dma_drm_to_video_info (&drm, info))
      return TRUE;
  }
#endif
  return FALSE;
}

/* ---------- допоміжне ---------- */

static void
drain_errors (GstElement * pipeline)
{
  GstBus *bus = gst_element_get_bus (pipeline);
  GstMessage *msg;

  while ((msg = gst_bus_pop_filtered (bus, GST_MESSAGE_ERROR))) {
    GError *e = NULL;
    gchar *dbg = NULL;

    gst_message_parse_error (msg, &e, &dbg);
    g_printerr ("помилка від %s: %s\n", GST_OBJECT_NAME (msg->src), e->message);
    if (dbg)
      g_printerr ("  подробиці: %s\n", dbg);
    g_clear_error (&e);
    g_free (dbg);
    gst_message_unref (msg);
  }
  gst_object_unref (bus);
}

static gint64
cpu_time_us (void)
{
  struct timespec ts;

  if (clock_gettime (CLOCK_PROCESS_CPUTIME_ID, &ts) != 0)
    return 0;
  return (gint64) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
}

/* ---------- головне ---------- */

int
main (int argc, char **argv)
{
  const char *desc = NULL;
  gboolean do_map = FALSE, have_info = FALSE;
  guint want = 300, hold = 0, skip = 8, got = 0, i;
  GError *err = NULL;
  GstElement *pipeline, *probe;
  GstPad *pad;
  GstCaps *caps;
  GstCapsFeatures *feat;
  GstVideoInfo vinfo;
  GstSample *held[MAX_HOLD];
  Series t_map = { NULL, 0, 0 }, t_touch = { NULL, 0, 0 }, t_unmap = { NULL, 0, 0 };
  gsize frame_bytes = 0;
  gint64 wall0, wall1, cpu0, cpu1;
  gchar *str;

  gst_init (&argc, &argv);
  memset (held, 0, sizeof (held));

  for (i = 1; i < (guint) argc; i++) {
    if (!g_strcmp0 (argv[i], "--map"))
      do_map = TRUE;
    else if (!g_strcmp0 (argv[i], "--frames") && i + 1 < (guint) argc)
      want = atoi (argv[++i]);
    else if (!g_strcmp0 (argv[i], "--hold") && i + 1 < (guint) argc)
      hold = MIN (atoi (argv[++i]), MAX_HOLD);
    else if (!desc)
      desc = argv[i];
  }
  if (!desc) {
    g_printerr ("вжиток: %s \"<конвеєр з appsink name=probe>\""
        " [--map] [--frames N] [--hold N]\n", argv[0]);
    return 2;
  }

  pipeline = gst_parse_launch (desc, &err);
  if (!pipeline) {
    g_printerr ("конвеєр не зібрався: %s\n", err->message);
    return 1;
  }
  probe = gst_bin_get_by_name (GST_BIN (pipeline), "probe");
  if (!probe) {
    g_printerr ("у конвеєрі має бути appsink name=probe\n");
    return 1;
  }

  gst_element_set_state (pipeline, GST_STATE_PLAYING);
  /* Чекаємо не на команду, а на факт: доки перехід не завершився,
     узгоджених caps на паді ще немає, і питати нема про що. */
  if (gst_element_get_state (pipeline, NULL, NULL, 10 * GST_SECOND)
      != GST_STATE_CHANGE_SUCCESS) {
    drain_errors (pipeline);
    g_printerr ("конвеєр не дійшов до PLAYING\n");
    return 1;
  }

  pad = gst_element_get_static_pad (probe, "sink");
  caps = gst_pad_get_current_caps (pad);
  if (!caps) {
    g_printerr ("на паді немає узгоджених caps\n");
    return 1;
  }
  str = gst_caps_to_string (caps);
  g_print ("узгоджені caps : %s\n", str);
  g_free (str);

  feat = gst_caps_get_features (caps, 0);
  str = gst_caps_features_to_string (feat);
  g_print ("ознака пам'яті : %s\n", str);
  g_free (str);

  /* Порожній набір ознак рівносильний memory:SystemMemory — це той самий
     звичайний video/x-raw, тобто кадр уже в пам'яті процесу. */
  if (gst_caps_features_get_size (feat) == 0
      || gst_caps_features_contains (feat, GST_CAPS_FEATURE_MEMORY_SYSTEM_MEMORY))
    g_print ("вирок          : кадр у пам'яті процесу — копія вже сталася\n");
  else
    g_print ("вирок          : кадр лишився в чужій пам'яті\n");

  have_info = video_info_from_caps (&vinfo, caps);
  if (do_map && !have_info)
    g_printerr ("з цих caps GstVideoInfo не збирається — мапувати не будемо\n");

  wall0 = g_get_monotonic_time ();
  cpu0 = cpu_time_us ();

  while (got < want) {
    GstSample *smp =
        gst_app_sink_try_pull_sample (GST_APP_SINK (probe), 5 * GST_SECOND);
    GstBuffer *buf;

    if (!smp) {
      if (gst_app_sink_is_eos (GST_APP_SINK (probe)))
        g_print ("потік скінчився на %u-му кадрі\n", got);
      else
        g_print ("ЗАТИК: 5 с без кадру на %u-му (утримано зразків: %u)\n",
            got, MIN (got, hold));
      break;
    }
    buf = gst_sample_get_buffer (smp);

    if (got == 0)
      dump_memories (buf);

    if (do_map && have_info) {
      GstVideoFrame f;
      gint64 a = g_get_monotonic_time (), b, c, d;

      if (gst_video_frame_map (&f, &vinfo, buf, GST_MAP_READ)) {
        b = g_get_monotonic_time ();
        frame_bytes = touch_frame (&f);
        c = g_get_monotonic_time ();
        gst_video_frame_unmap (&f);
        d = g_get_monotonic_time ();
        series_add (&t_map, b - a);
        series_add (&t_touch, c - b);
        series_add (&t_unmap, d - c);
      } else if (got == 0) {
        g_printerr ("кадр не мапується на читання — пам'ять непрозора\n");
      }
    }

    if (hold) {
      guint slot = got % hold;

      if (held[slot])
        gst_sample_unref (held[slot]);
      held[slot] = smp;             /* зразок лишається нашим — і поверхня теж */
    } else {
      gst_sample_unref (smp);       /* поверхня повертається в пул саме тут */
    }
    got++;
  }

  wall1 = g_get_monotonic_time ();
  cpu1 = cpu_time_us ();

  g_print ("\nкадрів %u   час за годинником %.2f с (%.1f к/с)"
      "   процесорний час %.2f с (%.2f мс на кадр)\n",
      got, (wall1 - wall0) / 1e6,
      got ? got / ((wall1 - wall0) / 1e6) : 0.0,
      (cpu1 - cpu0) / 1e6, got ? (cpu1 - cpu0) / 1000.0 / got : 0.0);

  if (t_touch.n > skip) {
    gint64 med;

    series_report (&t_map, "gst_video_frame_map", skip);
    med = series_report (&t_touch, "читання кадру", skip);
    series_report (&t_unmap, "gst_video_frame_unmap", skip);
    if (med > 0)
      g_print ("%-24s %" G_GSIZE_FORMAT " Б за %" G_GINT64_FORMAT
          " мкс → %.0f МБ/с\n", "пропускна здатність",
          frame_bytes, med, frame_bytes / (double) med);
  }

  for (i = 0; i < MAX_HOLD; i++)
    if (held[i])
      gst_sample_unref (held[i]);
  gst_caps_unref (caps);
  gst_object_unref (pad);
  gst_object_unref (probe);
  gst_element_set_state (pipeline, GST_STATE_NULL);
  gst_object_unref (pipeline);
  g_free (t_map.v);
  g_free (t_touch.v);
  g_free (t_unmap.v);
  return 0;
}
```

Кілька рішень у коді варті пояснення. Виклик `gst_element_get_state` після `set_state` — не перестраховка: `set_state` лише замовляє перехід, [а завершується він асинхронно](book:media-vision/states-lifecycle), і до цієї миті на паді нема узгоджених caps. Далі — `gst_app_sink_try_pull_sample` замість `pull_sample`: [appsink віддає кадри на запит](book:media-vision/appsink-appsrc), і запит без часового обмеження заблокується назавжди, а нам потрібно саме побачити, що кадри перестали приходити, і назвати причину. І нарешті `skip = 8`: перші кадри завжди дорожчі — виділяється пул, гріється кеш перекладу адрес, елементи дороблюють ліниву ініціалізацію, — тож у статистику вони не йдуть.

## Два прогони, один конвеєр

Уся сила цієї програми в порівнянні двох запусків, які відрізняються однією річчю — тим, чи дозволено `appsink` брати чужу пам'ять.

Перший прогін: `appsink` без властивості `caps`. Його шаблон паду — «будь-що», тому узгодження знайде найдешевший для декодера варіант і кадр лишиться в пристрої.

```sh
./zerocopy "filesrc location=in.mp4 ! qtdemux ! h264parse ! vah264dec \
   ! queue max-size-buffers=2 ! appsink name=probe sync=false max-buffers=2 drop=true" \
   --frames 300
```

Другий прогін: та сама стрічка, той самий декодер, але `appsink` вимагає простий `video/x-raw` — і цим змушує декодер витягти кадр у пам'ять процесу.

```sh
./zerocopy "filesrc location=in.mp4 ! qtdemux ! h264parse ! vah264dec \
   ! queue max-size-buffers=2 \
   ! appsink name=probe caps=video/x-raw sync=false max-buffers=2 drop=true" \
   --frames 300
```

`sync=false` тут обов'язковий: інакше `appsink` віддаватиме кадри за годинником конвеєра, і ви виміряєте частоту показу замість швидкості шляху. Ось приблизно як виглядає вивід (числа — з ноутбука з вбудованою графікою Intel; ваші будуть інші, важить порядок і різниця між прогонами).

```
    ПЕРШИЙ ПРОГІН (без --map)
    узгоджені caps : video/x-raw(memory:DMABuf), format=NV12, width=1920, height=1080…
    ознака пам'яті : memory:DMABuf
    вирок          : кадр лишився в чужій пам'яті
    буфер: 1 шматок(ів), разом 3110400 Б
      [0] DMABuf          3110400 Б  fd=17
    кадрів 300  час за годинником 3.11 с (96.5 к/с)  процесорний час 0.09 с (0.31 мс на кадр)

    ДРУГИЙ ПРОГІН (без --map)
    узгоджені caps : video/x-raw, format=NV12, width=1920, height=1080…
    ознака пам'яті : memory:SystemMemory
    вирок          : кадр у пам'яті процесу — копія вже сталася
    буфер: 1 шматок(ів), разом 3110400 Б
      [0] SystemMemory    3110400 Б
    кадрів 300  час за годинником 3.44 с (87.2 к/с)  процесорний час 0.44 с (1.48 мс на кадр)
```

Ось воно, шукане число. Ми в обох прогонах нічого з кадром не робили — тільки взяли зразок і відпустили його. Різниця в процесорному часі — **1.17 мс на кадр** — це рівно та копія, яку декодер зробив усередині себе, бо ми змусили його віддати байти. Перевірмо, чи вона правдоподібна:

```
кадр NV12 1080p        = 1920 · 1080 · 1.5 = 3 110 400 Б ≈ 3.11 МБ
різниця на кадр        = 1.48 − 0.31 = 1.17 мс
швидкість копіювання   = 3.11 МБ / 1.17 мс ≈ 2.66 ГБ/с
```

Два з половиною гігабайти на секунду — саме те, чого чекаєш від читання з некешованої поверхні з наступним записом у звичайну пам'ять. Число сходиться, отже, ми справді виміряли копію, а не шум.

Для одного потоку 1080p30 це 3.6 % ядра — непомітно. Для відеостіни з шістнадцяти камер це вже понад половину ядра, ще до того, як ви щось із кадрами зробили.

## Найважливіше число — те, що ламає очікування

Тепер увімкнімо `--map` і виміряймо, скільки коштує подивитися на пікселі.

```
    ПЕРШИЙ ПРОГІН (--map, memory:DMABuf)
    gst_video_frame_map      мін       18  медіана       24  p95       41  макс      180  мкс
    читання кадру            мін     9420  медіана     9910  p95    11200  макс    14300  мкс
    gst_video_frame_unmap    мін        6  медіана        9  p95       17  макс       52  мкс
    пропускна здатність      3110400 Б за 9910 мкс → 314 МБ/с

    ДРУГИЙ ПРОГІН (--map, memory:SystemMemory)
    gst_video_frame_map      мін        0  медіана        1  p95        2  макс       15  мкс
    читання кадру            мін      380  медіана      410  p95      470  макс      910  мкс
    gst_video_frame_unmap    мін        0  медіана        0  p95        1  макс        4  мкс
    пропускна здатність      3110400 Б за 410 мкс → 7586 МБ/с
```

Мапування в першому прогоні коштує двадцять чотири мікросекунди — і саме через це число хочеться зробити хибний висновок. А читання того самого кадру коштує **десять мілісекунд**: у двадцять чотири рази більше, ніж у другому прогоні, де кадр лежить у звичайній кешованій пам'яті. Триста мегабайтів на секунду проти семи з половиною гігабайтів — це різниця між читанням з пам'яті пристрою, яку процесор не кешує, і читанням із власного ОЗП.

Висновок з цього виходить неприємний для гасла «нуль копій». Якщо ваш споживач — кодер, композитор чи перетворювач, який говорить тією ж мовою пам'яті, перший прогін безкоштовний: ви ніколи не читаєте, тож ніколи не платите. Але якщо ви збиралися передати кадр у власний код на процесорі й бігати по пікселях, то «нуль копій» коштує вам десять мілісекунд на кадр замість однієї, — бо оптимізований копіювальник усередині драйвера читає некешовану пам'ять потоковими інструкціями, а ваш цикл на це не здатен. При 60 к/с десять мілісекунд на кадр — це не «трохи повільніше», це неробочий конвеєр.

> 🔧 **Навіщо це.** Правило звучить так: **нуль копій виграє лише тоді, коли процесор кадру не торкається взагалі**. Якщо далі йде обробка на процесорі, чесніше попросити в декодера звичайний `video/x-raw` і дати драйверові скопіювати кадр його швидким шляхом. Куди саме віддавати кадр і в якому форматі — питання [стику з обробником](book:media-vision/frame-interop), і починається воно з цих двох чисел.

Крива мапування ще й підкаже, як алокатор поводиться з відображенням. [Спільний буфер ядра](book:unix-linux/dma-buf) відображається на вимогу й типово знімається з відображення, коли останній охочий відпустив пам'ять; але елемент може попросити тримати відображення постійно. Якщо в стовпчику «мін» ви бачите одиниці мікросекунд, а в «p95» — десятки, і поріг припадає приблизно на розмір пулу — відображення тримають і ви бачите чергування холодних і теплих кадрів. Якщо ж усі кадри однаково дорогі, кожен `map` — це новий `mmap`.

## Пастка пулу: що буває, якщо не відпускати зразок

Тепер найкорисніша перевірка. Запустімо перший прогін із `--hold 12`:

```sh
./zerocopy "… ! vah264dec ! queue max-size-buffers=2 \
   ! appsink name=probe sync=false max-buffers=2 drop=true" --frames 300 --hold 12
```

```
    узгоджені caps : video/x-raw(memory:DMABuf), format=NV12, …
    буфер: 1 шматок(ів), разом 3110400 Б
      [0] DMABuf          3110400 Б  fd=17
    ЗАТИК: 5 с без кадру на 9-му (утримано зразків: 9)
    кадрів 9   час за годинником 5.06 с (1.8 к/с)   процесорний час 0.01 с (1.11 мс на кадр)
```

Дев'ять кадрів — і тиша. Жодної помилки на шині, жодного попередження, конвеєр формально в стані PLAYING. Причина видна саме з тих двох рядків, які програма надрукувала на початку: буфер складається з одного шматка `DMABuf`, а це поверхня з пулу декодера. Зразок володіє буфером, буфер володіє шматком, шматок — поверхнею. Доки ми тримаємо `GstSample`, поверхня зайнята. На дев'ятому кадрі вільних поверхонь у пулі не лишилося, і декодер став чекати — назавжди.

Найкоштовніше тут те, що симптом ззовні виглядає як завислий декодер, а причина в нашому коді, за два виклики звідси. Числа роблять діагноз миттєвим: змініть `--hold 12` на `--hold 4` — і затик або зникне, або переїде на пізніший кадр. Кадр, на якому все стало, і є розмір пулу мінус те, що тримають черги. Це вимірювання розміру пулу без жодної документації.

Звідси й правило користування: зразок треба відпускати одразу після того, як ви з нього все взяли. А якщо кадр справді потрібен надовго — його доведеться скопіювати `gst_buffer_copy_deep`, тобто заплатити ту саму копію, від якої ви тікали. Іншого виходу немає: дефіцитний ресурс пристрою не можна тримати «про запас».

## Ціна й пастки

Ціна самого вимірювання проста. Без `--map` програма робить на кадр сталу роботу: один зразок, кілька читань полів, одне звільнення — одиниці мікросекунд, тобто вимірювач не спотворює того, що міряє. З `--map` робота стає пропорційною площі кадру: сторінкових збоїв близько `W·H·1.5 / 4096`, а прочитаних кеш-ліній — `W·H·1.5 / 64`. Для 1080p це 760 сторінок і 48 600 ліній на кадр.

Далі — те, на чому вимірювання ламається найчастіше.

**Властивість `caps` на `appsink` — найпоширеніша самопастка.** Її ставлять «щоб напевно знати формат», а вона мовчки викидає з узгодження всі ознаки пам'яті, крім системної. Конвеєр працює, елемент апаратний, копія на кожному кадрі. Якщо ви не задаєте `caps`, формат усе одно доступний — із зразка через `gst_sample_get_caps`.

**Перші кадри брешуть.** Пул виділяється при першому кадрі, відображення холодні, елементи дороблюють ініціалізацію. Тому в статистику йдуть кадри починаючи з дев'ятого; на коротких прогонах у сто кадрів це помітно зсуває медіану.

**Журнал змінює те, що міряє.** `GST_DEBUG` вище другого рівня додає форматування рядків у кожному виклику й може легко подвоїти час на кадр. Міряти треба з вимкненим журналом, а вмикати його вже для пояснення того, що виміряли.

**`format=DMA_DRM` ламає звичайний розбір caps.** Починаючи з 1.24 конвеєр узгоджує розкладку явно, і колірний формат переїжджає в поле `drm-format`; `gst_video_info_from_caps` на таких caps повертає невдачу. Обхід у коді є, але він допомагає лише для лінійної розкладки: якщо поверхня тайлова, читати її як лінійну не можна взагалі — ви отримаєте картинку з переставленими квадратами й вирішите, що зламався декодер.

**Не всяка пам'ять мапується.** Поверхня VA часто мапується, поверхня CUDA з боку процесора — ні, `memory:NVMM` на Jetson — теж ні. `gst_video_frame_map` тоді просто поверне невдачу, і це не помилка програми, а чесна відповідь: цей кадр процесор побачити не може. Саме тому програма друкує тип пам'яті **до** того, як пробує мапувати.

**Середнє обманює, мінімум — ні.** Планувальник, міграція між ядрами й зміна частоти дають поодинокі викиди в десятки разів. Мінімум показує фізичну ціну шляху, медіана — типовий кадр, p95 — те, від чого захлинається показ. Середнє не показує нічого й тому в звіті його немає.

**Той самий бінарник — інший бекенд.** Замініть `vah264dec` на `nvh264dec` — і в рядку типу пам'яті з'явиться `CUDAMemory`; на SoC із `v4l2h264dec` — знову `DMABuf`, але вже з іншого драйвера. Програма нічого про ці плагіни не знає: вона читає ім'я з алокатора, тому працює з бекендом, якого на момент її написання не існувало.
