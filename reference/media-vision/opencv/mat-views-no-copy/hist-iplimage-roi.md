# 📜 Ділянка, що жила в самому зображенні: від cvSetImageROI до cv::Mat

Десять років OpenCV позначала прямокутник для обробки не окремим значенням, а **перемикачем усередині зображення**: виклик `cvSetImageROI` міняв саме зображення, і всі, хто його тримав, відтоді бачили лише вирізаний шматок. Цей розділ — про те, звідки такий підхід узявся, чому він мусив був померти й що саме змінилося у версії 2.0.

## Ipl — три літери з чужої бібліотеки

Структура, з якої починалося будь-яке зображення в OpenCV, зветься `IplImage`, а не `CvImage`, і це не примха. Документація бібліотеки каже прямо: `IplImage` узято з Intel Image Processing Library — там цей формат рідний, а OpenCV підтримує лише частину його можливостей *(підтверджено первинним джерелом: довідка модуля core про старі структури)*. Літери «Ipl» — це скорочення назви тієї бібліотеки.

Контекст такий. OpenCV почалася як дослідницька ініціатива Intel 1999 року; перша публічна альфа з'явилася 2000-го на конференції CVPR, а розголосу їй додала стаття Ґері Брадскі (Gary Bradski) «The OpenCV Library» у Dr. Dobb's Journal того ж року. Стабільна версія 1.0 вийшла 2006-го *(документовано)*. Брадскі — американський дослідник комп'ютерного зору, який ініціював і просував проєкт; сама ж реалізація й оптимізації робилися командами бібліотек продуктивності Intel, зокрема інженерами російського підрозділу компанії — тож приписувати бібліотеку одній людині було б неточно в обидва боки: ані «її написав Брадскі», ані «її написали в Нижньому Новгороді» окремо не є правдою.

Головне для нашої теми: OpenCV не проєктувала формат зображення з нуля. Вона взяла готову структуру сусідньої комерційної бібліотеки — разом із її рішеннями. І два з них виявилися доленосними.

Перше рішення — **`widthStep`**: байтова довжина рядка зберігається окремо від ширини в пікселях. У полях `IplImage` навіть лишилося поле `align` (4 або 8), яке OpenCV ігнорує, покладаючись натомість саме на `widthStep`. Це рішення пережило все інше й дожило до сьогодні, бо без нього немає ані вирівнювання рядків під [вимоги пам'яті й інструкцій](book:programming/memory-alignment) — доступ за «круглою» адресою дешевший, а деякі [векторні інструкції](book:programming/simd-vectorization) взагалі люблять кратні адреси, — ані будь-якого виду на частину растра.

Друге рішення — **поле `roi`** просто в тілі зображення:

```c
typedef struct _IplROI {
    int coi;                 /* 0 — усі канали, 1 — нульовий, ... */
    int xOffset, yOffset;
    int width, height;
} IplROI;

typedef struct _IplImage {
    int   nChannels, depth;
    int   width, height;
    struct _IplROI *roi;     /* NULL — вибрано все зображення */
    char *imageData;
    int   widthStep;         /* байтів на вирівняний рядок */
    /* ... і ще з десяток полів, частину яких OpenCV просто ігнорує ... */
} IplImage;
```

Зверни увагу на `coi` — «channel of interest». Разом із прямокутником зображення могло тримати ще й **увімкнений канал**: обробляй лише синій. Одна структура несла два різні перемикачі режиму.

![Ліворуч: IplImage із полем roi всередині; праворуч: три незалежні заголовки cv::Mat над одним блоком пікселів](/reference/media-vision/opencv/mat-views-no-copy/img/roi-state-vs-value.svg)

*Та сама задача — «працювати з частиною» — у двох різних моделях: перемикач у самому об'єкті проти окремого значення поруч.*

## Ділянка як увімкнений режим

Робочий цикл виглядав так:

```c
IplImage* img = cvLoadImage("shot.png", CV_LOAD_IMAGE_COLOR);

cvSetImageROI(img, cvRect(100, 100, 64, 64));   /* увімкнули ділянку */
cvSmooth(img, img, CV_GAUSSIAN, 31, 31, 0, 0);  /* згладили ТІЛЬКИ її */
cvResetImageROI(img);                           /* вимкнули назад */

cvReleaseImage(&img);                           /* звільнили вручну */
```

Ніякого нового об'єкта тут не з'являється. `cvSetImageROI` за документацією виділяє структуру `IplROI`, якщо її ще не було, і чіпляє до зображення; `cvResetImageROI` повертає ділянку на все зображення **і звільняє цю структуру**; `cvGetImageROI` віддає поточний прямокутник, а для зображення без ділянки — його повні розміри *(підтверджено первинним джерелом: довідка API старих структур)*. Функції обробки при вході дивилися на `img->roi` і самі звужували роботу.

З погляду 1999 року це навіть елегантно: жодна сигнатура не змінюється, у C немає ані перевантажень, ані значень із деструкторами, а «обробити частину» працює для всіх функцій одразу.

## Чому стан у зображенні не витримав

Проблема не в тому, що підхід повільний — він якраз нічого не копіює. Проблема в тому, що ділянка стала **прихованим станом об'єкта**, який усі бачать спільно.

**Ділянка — не властивість виклику, а властивість зображення.** Функція, якій передали `IplImage*`, не може знати, чи це «весь кадр», чи «шматок 64×64, який хтось увімкнув три виклики тому». Вона отримує вказівник на об'єкт, а сенс цього об'єкта залежить від історії. Це класичний випадок [глобального стану](book:programming/global-state) — стану, доступного здалеку й змінюваного здалеку, від якого поведінка коду залежить невидимо в місці виклику. Найгірший різновид помилки, який із цього виростає, — **забутий `cvResetImageROI`**: увімкнули ділянку, вийшли по `return` чи по помилці, і наступні кадри мовчки обробляються по прямокутнику 64×64. Нічого не падає, ніде не порожньо — просто результат неправильний.

**Дві ділянки одночасно неможливі.** Поле `roi` одне. Порівняти лівий і правий фрагмент одного кадру двома видами не можна: доведеться або копіювати обидва в окремі зображення, або перемикати ROI туди-сюди між викликами. А коли з'явилися багатоядерні процесори й бажання роздати смуги кадру різним потокам, підхід уперся в стіну остаточно: спільний змінюваний стан і паралельність не поєднуються без блокувань, а зображення не мало ані блокувань, ані [потокової безпеки](book:programming/thread-safety) як обіцянки. Це, мабуть, головна причина смерті моделі: не естетика, а те, що в 2000-х паралелізм із розряду екзотики перейшов у розряд типового.

**Час життя треба вести руками.** `cvCreateImage` виділяв заголовок і дані разом, `cvReleaseImage` звільняв їх разом, а між ними код мусив сам не загубити вказівник. Коли ж хотілося саме виду — заголовка над чужим буфером, — конструкція розсипалася на кроки: `cvCreateImageHeader`, потім `cvSetData` на чужу пам'ять, потім обов'язкове звільнення **лише заголовка**, бо дані належать комусь іншому. Помилися в останньому кроці — і ти або звільнив чуже, або втратив своє. Ніякого [зв'язування ресурсу з часом життя об'єкта](book:programming/raii) тут бути не могло: у C немає деструкторів.

**Копіювання поводилося несиметрично.** `cvCloneImage` документовано копіює заголовок, дані **і ROI** — тобто клон успадковує ще й увімкнений режим. Присвоєння ж `IplImage*` іншій змінній не копіювало нічого: два вказівники на один об'єкт, і зміна ділянки крізь один із них миттєво видна крізь другий. Різниця між [глибокою й поверхневою копією](book:programming/deep-shallow-copy) залежала від того, яким саме викликом ти скористався, і жодна з двох поведінок не була очевидною з коду.

## Значення-заголовок було поруч увесь час

Тут важливо не спростити історію до «спершу було погано, потім придумали види». Ідея «заголовок як окреме значення над спільними даними» існувала в OpenCV **ще в C-шному API** — паралельно з `IplImage`.

По-перше, поруч жила структура `CvMat`, і в ній були поля `refcount` (вказівник на лічильник посилань блоку даних) та `hdr_refcount` — тобто [підрахунок посилань](book:programming/reference-counting) уже був реалізований *(підтверджено первинним джерелом: заголовок `types_c.h`, який і сьогодні лишається в дереві OpenCV)*.

По-друге, була функція `cvGetSubRect`, яка **повертала заголовок матриці** на прямокутну підобласть вхідного зображення чи матриці — без копіювання даних:

```c
CvMat sub;                                   /* заголовок на стеку */
cvGetSubRect(img, &sub, cvRect(100, 100, 64, 64));
cvSmooth(&sub, &sub, CV_GAUSSIAN, 31, 31, 0, 0);
```

Це вже вид у сучасному сенсі: два незалежні описи, одні пікселі, жодного перемикача в батьківському об'єкті. Поруч жили `cvGetRow`, `cvGetCol`, `cvGetDiag` — ті самі майбутні `row`, `col`, `diag`.

Отже, розрізняймо чесно: **ідея** й **реалізація** видів були в бібліотеці задовго до 2.0. Чого не було — так це того, щоб вид став **типовим і безпечним способом роботи**. Заголовки треба було оголошувати й передавати вручну, лічильник посилань крутити викликами, а функції приймали безтиповий `CvArr*`, за яким могло ховатися що завгодно з трьох різних структур. Тому в реальному коді люди й далі писали `cvSetImageROI` — воно було коротшим.

## Жовтень 2009: вид стає типовим випадком

Версія 2.0 принесла інтерфейс C++ поряд зі старим C-шним API. Дата: пакет `OpenCV-2.0.0` викладено на SourceForge **1 жовтня 2009 року** *(підтверджено датою файлу в первинному сховищі релізів; енциклопедичні джерела теж пишуть «жовтень 2009» — зустрічна дата «вересень 2009» трапляється, але первинним джерелом не підтверджується)*.

Що змінилося по суті — не синтаксис, а **кому належить ділянка**:

```cpp
cv::Mat frame = cv::imread("shot.png");
cv::Mat roi   = frame(cv::Rect(100, 100, 64, 64));   // нове ЗНАЧЕННЯ
cv::GaussianBlur(roi, roi, cv::Size(31, 31), 0);
```

Три наслідки, і кожен закриває один із пунктів попереднього розділу. Ділянка більше не стан: `frame` після другого рядка точнісінько такий самий, як був, і жодна функція, що отримає `frame`, не потрапить у чужий увімкнений режим. Ділянок може бути скільки завгодно й одночасно — вони просто окремі значення, тож смугу кадру можна віддати кожному потоку свою. Час життя веде лічильник посилань у блоці пікселів: деструктор зменшує його, а пам'ять звільняється тоді й тільки тоді, коли він дійшов нуля — тож `cvReleaseImage` і питання «хто тут власник» зникають разом.

Заразом зник і `coi`. Канал у C++ API став окремою операцією над даними (`split`, `extractChannel`, `mixChannels`), а не режимом, увімкненим у зображенні. Обидва перемикачі, що жили в `IplROI`, перетворилися на звичайні значення й виклики.

## Що з цього лишилося в коді

`IplImage` нікуди не подівся: структура й досі оголошена в `types_c.h`, а старий C API довго лишався в дереві заради сумісності. Успадковані ним поля, які OpenCV ніколи не використовувала — `colorModel`, `channelSeq`, `BorderMode`, `alphaChannel`, — так і стоять із коментарем «ігнорується», як археологічний шар чужої бібліотеки в чинному заголовку. Місток між світами теж лишився: `cv::cvarrToMat` будує `Mat`-заголовок над старою структурою, і, до речі, за домовчанням він **враховує** `roi` старого зображення — тобто прихований стан живий рівно доти, доки в системі є хоч один `IplImage`.

Урок з усієї цієї історії ширший за OpenCV. Обидві моделі не копіюють пікселів і за швидкістю рівні. Різниця виключно в тому, **де записано «яка саме частина нас цікавить»**: у спільному об'єкті, що бачать усі, — чи у значенні, яке тримає той, кому воно потрібне. Перше коротше пишеться, друге не дозволяє тихо помилитися. Коли з'явилися багатоядерні процесори, вибір між цими двома перестав бути питанням смаку.
