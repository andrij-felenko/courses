# 📋 Ворота внеску в QGroundControl: гачки, рецепти, процеси, мітки

Це реєстр усього, що автоматично оглядає зміну на шляху в апстрим QGroundControl: які гачки `pre-commit` спрацьовують локально й що саме кожен забороняє, чим замінити заборонений виклик, за що відповідає кожен рецепт `just`, які робочі процеси на серверах GitHub запускаються на запит і що перевіряє кожен із них, які мітки навішуються самі й на що впливають, які типи повідомлення коміту дозволені й котрі з них спричиняють випуск. Довідка потрібна тому, що межі перевірок не виводяться з їхніх назв: `check-no-fixed-qwait` дивиться **тільки** в теку `test/`, а `check-no-qassert` — навпаки, всюди, **крім** неї; `just format` і `just lint` перевіряють різні речі; мітка `size/XL` не блокує нічого, а мітка `RN:` вирішує, чи побачить вашу роботу пілот у нотатках випуску.

**Усе звірено з гілкою `master` станом на серпень 2026 року.** Версії інструментів у `.pre-commit-config.yaml` закріплені поіменно (`rev:`) і оновлюються щотижневим запитом від Renovate, тож числа старіють швидко. Що змінюється значно повільніше — набір гачків, їхні межі за файлами й точні шаблони заборон; саме це тут і зафіксовано. Перед звіркою заглядайте в `.pre-commit-config.yaml`, `justfile`, `.github/release.yml` і `.releaserc.json` тієї гілки, з якої збираєте.

## Як увімкнути й запускати гачки в себе

Гачок сам себе не встановлює: клонування репозиторію дає конфігурацію, але не запис у `.git/hooks`. Механіка того, як git взагалі викликає скрипт у момент коміту, описана окремо — [гачки git](book:programming/git-hooks): це виконуваний файл у теці репозиторію, який git запускає перед створенням коміту, і ненульовий код виходу скасовує коміт.

```bash
pre-commit install                       # прописати гачок у .git/hooks/pre-commit
pre-commit run --all-files               # повний прогін; те саме, що just lint
pre-commit run clang-format --all-files  # один гачок за id
pre-commit run --from-ref origin/master --to-ref HEAD   # лише файли гілки
pre-commit autoupdate                    # підняти закріплені rev
SKIP=clang-tidy,clazy git commit -m "fix: ..."          # пропустити повільні
git commit --no-verify                                  # обійти всі гачки
```

Дві межі, про які варто знати наперед. По-перше, у самому кінці конфігурації стоїть загальне `exclude: ^build/` — тека збірки невидима для **всіх** гачків, і жодне попадання туди перевірки не спричинить. По-друге, без `--all-files` гачки бачать лише **проіндексовані** файли, тому зміна, збережена в редакторі, але не додана через `git add`, крізь локальні ворота проходить непоміченою й червоніє вже на сервері.

| `uv-lock` | `uv-pre-commit` | `tools/uv.lock` відповідає `tools/pyproject.toml` |
| `shellcheck` | `shellcheck-py` | скрипти оболонки; вимкнено `SC1091` — не заходить у підключені через `source` файли |
| `hadolint` | `hadolint-py` | лише `deploy/docker/Dockerfile-*` |
| `cmake-format`, `cmake-lint` | `cmakelang` | `CMakeLists.txt` і `*.cmake`, у режимі перевірки; поза увагою `build/`, `libs/` |
| `qmllint` | `tools/analyze.py --tool qmllint` | усі `.qml` |
| `clang-tidy` | `tools/analyze.py --tool clang-tidy` | C++ поза `build/`, `libs/`, `test/` |
| `clazy` | `tools/analyze.py --tool clazy` | C++ поза `build/`, `libs/`, `test/` |

Три останні мають спільну властивість, через яку прогін триває довго: у їхньому описі стоїть `pass_filenames: false`, тобто вони **не отримують списку змінених файлів** і щоразу обходять своє дерево цілком. `clang-tidy` і `clazy` — це [статичний аналіз](book:programming/static-analysis), тобто пошук помилок за структурою коду без його запуску; `clazy` знає ще й окремі хиби, характерні саме для Qt. Саме ці три варто відкладати через `SKIP=` під час частих проміжних комітів і давати їм відпрацювати перед надсиланням.

## Шість проєктних заборон

Це власні гачки QGroundControl — саме та частина, якої немає в жодному стандартному наборі. Чотири з них — звичайний `grep` із точним шаблоном, два — скрипти Python у `tools/analyzers/`. Точні межі важать більше за формулювання правила: те саме написання в сусідній теці може бути дозволене.

| Гачок | Шукає | Де діє | Чим замінити |
|---|---|---|---|
| `check-no-qassert` | підрядок `Q_ASSERT` | C++ **поза** `test/` | захисна перевірка з раннім поверненням |
| `check-categorized-logging` | `qDebug(…Log)` та так само `qInfo`, `qWarning`, `qCritical` | увесь C++ | `qCDebug`, `qCInfo`, `qCWarning`, `qCCritical` |
| `check-no-qtest-ignore-message` | `QTest::ignoreMessage` | лише `test/` | `expectLogMessage` + `verifyExpectedLogMessage` або `ignoreLogMessage` |
| `check-no-fixed-qwait` | `qWait(<число ≠ 0>)` | лише `test/` | `QTRY_VERIFY_WITH_TIMEOUT`, `QTRY_COMPARE_WITH_TIMEOUT`, `QSignalSpy::wait` зі сталою `TestTimeout::*` |
| `vehicle-null-check` | `activeVehicle()->…` без перевірки; результат `getParameter()` без перевірки | C++ поза `build/`, `libs/`, `test/` | перевірка на нуль перед розіменуванням |
| `qt-translate-noop-check` | `QT_TRANSLATE_NOOP` і `QT_TR_NOOP` як **значення** | C++ поза `build/`, `libs/`, `test/` | `QCoreApplication::translate("контекст", "рядок")` |

Три уточнення, без яких шаблони поводяться несподівано.

**`check-no-qassert` — це буквальний пошук підрядка.** Він спрацює й на `Q_ASSERT_X`, і на згадку слова в коментарі, і на власне ім'я на кшталт `MY_Q_ASSERTION`. Це не хиба реалізації: дешевий гачок навмисно ловить із запасом, а рідкісний хибний спрацьовок автор знімає перейменуванням або `SKIP=`.

**`check-categorized-logging` ловить рівно одну помилку — категорію, передану в некатегоризований макрос.** Тобто `qDebug(VehicleLog) << …` не пройде, бо `qDebug` у такій формі трактує аргумент зовсім не як категорію. А от голий `qDebug() << …` цим гачком **не** ловиться: вимога тримати кожне повідомлення в категорії лишається правилом стилю, яке стежиться на рев'ю.

```cpp
// не пройде гачок: категорія передана в некатегоризований макрос
qDebug(VehicleLog) << "armed" << vehicle->armed();

// правильно: категоризований макрос
qCDebug(VehicleLog) << "armed" << vehicle->armed();
```

**`check-no-fixed-qwait` дивиться на буквальне число.** Шаблон `qWait\([1-9][0-9]*\)` не спрацює ані на `qWait(0)`, ані на `qWait(kSettleMs)`, ані на запис із пробілами всередині дужок. Обійти його тривіально — і це нормально: гачок ставлять проти неуважності, а не проти зловмисності.

Останній із шести варто показати кодом, бо помилка тут не видима на око. `QT_TRANSLATE_NOOP` — макрос-**позначка**: він розгортається в той самий рядковий літерал і нічого не перекладає під час виконання. Його призначення — щоб `lupdate` витягнув рядок у список для перекладачів; сам переклад мусить статися в місці вживання.

```cpp
// не пройде гачок: назва режиму повернеться англійською попри переклад
QString modeName() { return QT_TRANSLATE_NOOP("Mode", "Return to Launch"); }

// правильно: позначка витягне рядок, translate() підставить перекладений
QString modeName() { return QCoreApplication::translate("Mode", "Return to Launch"); }
```

Скрипт `vehicle_null_check.py` шукає перевірку на нуль у **десяти попередніх рядках** тієї самої функції; якщо ваша перевірка стоїть далі або схована за допоміжним викликом, гачок поскаржиться на цілком коректний код — тоді перевірку простіше присунути ближче, ніж сперечатися зі скриптом.

## Рецепти `just`

`justfile` у корені — єдине джерело команд; саме ці рядки згадані в документі про внесок, і саме їх повторює неперервна інтеграція. Потрібна версія `just` не нижча за 1.30 (через `home_directory()`); пакет `just` в Ubuntu постачає 1.21 і не годиться — ставте через `python tools/setup/install_python.py dev`, `pipx install rust-just` або `cargo install just`.

| Рецепт | Що виконує | Роль |
|---|---|---|
| `just deps` | `tools/setup/install_dependencies --platform debian` | системні залежності (Debian/Ubuntu) |
| `just submodules` | `git submodule update --init --recursive` | підмодулі |
| `just configure` | `tools/configure.py -B build -t $BUILD_TYPE --testing --qt-root $QT_DIR` | конфігурація **з тестами**; сама тягне `submodules` |
| `just build` | `cmake --build build --config $BUILD_TYPE --parallel $JOBS` | складання |
| `just release` | конфігурація `--release` + складання `Release` | релізна збірка однією командою |
| `just rebuild` | `clean` → `configure` → `build` | після зміни опцій CMake |
| `just setup` | `deps` → `submodules` → `configure` → `build` | перший запуск на чистій машині |
| `just test` | `ctest --output-on-failure -L "$LABELS" -LE "$EXCLUDE"` у теці `build` | тести з тими самими мітками, що в CI |
| `just lint` | `pre-commit run --all-files` | усі гачки |
| `just format` | `tools/analyze.py --tool clang-format` | **лише перевірка** форматування |
| `just format-fix` | те саме з `--fix` | виправлення форматування |
| `just analyze` | `tools/analyze.py` | статичний аналіз повністю |
| `just coverage` | `tools/coverage.py` | звіт покриття |
| `just check` | `lint` + `test` | ворота, які треба пройти перед запитом |
| `just run` | `./build/$BUILD_TYPE/QGroundControl` | запуск зібраного застосунку |
| `just info` | друкує зведені версії | чим саме збираєте |
| `just check-deps` | `tools/check_deps.py` | звірка версій залежностей |
| `just clean *ARGS`, `just distclean` | `tools/clean.py` | очищення (`--cache`, `--all`, `--dry-run`) |

Змінні оточення, якими рецепти керуються, і їхні типові значення:

```
QT_DIR      ~/Qt/<версія з build-config.json>/gcc_64
BUILD_TYPE  Debug
JOBS        кількість ядер машини
LABELS      Unit|Integration      мітки ctest, які ЗАПУСКАЮТЬСЯ
EXCLUDE     Flaky|Network         мітки ctest, які ПРОПУСКАЮТЬСЯ
```

Пара `-L` / `-LE` — це відбір за [мітками ctest](book:build-systems/ctest): кожен тест реєструється з переліком міток, а запуск бере одні й відкидає інші. Значення за замовчуванням дібрані так, щоб локальний прогін збігався з тим, що робить сервер; окремий тест ганяють через `ctest -R <ім'я>` без участі `just`.

## Робочі процеси на запит

| Процес | Коли запускається | Що перевіряє |
|---|---|---|
| `linux.yml` | push у `master`/`Stable*`, запит, черга злиття, вручну | релізна збірка за архітектурами + **єдине місце, де ганяються тести** |
| `windows.yml` | те саме | збірка `msvc2022_64`, `arm64` і крос-збірка + запуск-перевірка двійника |
| `macos.yml` | те саме | збірка `clang_64` + запуск-перевірка |
| `android.yml` | те саме | збірка APK; матриця хостів; димова перевірка запуску на емуляторі |
| `ios.yml` | те саме | збірка під iOS |
| `_detect-changes.yml` | викликається з кожного платформного процесу | за списком змінених файлів вирішує `should_build`; на не-запитних подіях завжди `true` |
| `pre-commit.yml` | push і запит, **окрім** змін лише в `docs/` чи `translations/` | ті самі гачки, що локально, повним прогоном |
| `pr-checks.yml` | відкриття, редагування, оновлення запиту | заголовок запиту, мітка розміру, мітки за шляхами |
| `ci-scripts.yml` | зміни в `.github/` або `tools/` | `actionlint` плюс `pytest` для `tools/tests` і `.github/scripts/tests` |
| `codeql.yml` | push, запит, черга злиття, вручну | сканування безпеки для `c-cpp`, `actions`, `java-kotlin`, `python` |
| `check-links.yml` | зміни в `*.md` | биті посилання (`lychee`) |
| `analysis.yml` | **тільки вручну** | на вибір: `clazy`, `iwyu`, `asan`, `ubsan`, `tsan` |
| `build-results.yml` | після завершення `Linux`, `Windows`, `MacOS`, `Android`, `pre-commit` | зводить їхні підсумки в **один** коментар до запиту |

Дві речі з цієї таблиці найлегше зрозуміти неправильно.

**`analysis.yml` не є частиною воріт запиту.** Він запускається лише вручну, з вибором інструмента, і потрібен для розслідування, а не для щоденної перевірки. Санітайзери при цьому в CI все-таки працюють — але в іншому місці, див. нижче.

**`build-results.yml` не перевіряє нічого.** Це складач звіту: він чекає завершення чотирьох платформних процесів і `pre-commit`, збирає їхні артефакти й пише один коментар. iOS у цьому переліку немає — його стан видно лише на вкладці перевірок.

Тести й санітайзери живуть у `linux.yml`, у завданні `debug-validation`, і воно розкладається рівно на два прогони:

| Прогін | Опції конфігурації | Мітки, які пропускаються | Стеля часу |
|---|---|---|---|
| `Test + Coverage` | звичайний `Debug` з тестами | `Flaky`, `Network` | 60 хв |
| `Sanitizers (ASan+UBSan)` | `-DQGC_ENABLE_ASAN=ON -DQGC_ENABLE_UBSAN=ON -DQGC_TEST_DETECT_LEAKS=ON` | `Flaky`, `Network`, `NoSanitizer` | 120 хв |

Другий прогін вмикає [санітайзер адрес](book:programming/address-sanitizer) — інструментування, яке під час виконання ловить вихід за межі буфера, звернення до звільненої пам'яті й витоки; `QGC_TEST_DETECT_LEAKS=ON` окремо вмикає пошук витоків, який у звичайних прогонах приглушено, бо Qt лишає по собі очікувані нерозв'язані об'єкти. Мітка `NoSanitizer` існує саме для тестів, які під інструментуванням не мають сенсу.

Перший прогін дає ще й пороги [покриття коду](book:programming/code-coverage): результат звіряється з кеш-змінними CMake `QGC_COVERAGE_LINE_THRESHOLD` і `QGC_COVERAGE_BRANCH_THRESHOLD`, чиї значення за замовчуванням — **30 % за рядками** і **20 % за гілками**. Це підлога, що не дає покриттю сповзати, а не мета.

## Мітки: три незалежні набори

**Мітки нотаток випуску.** Ставить їх людина; вони визначають розділ, у який зміна потрапить у згенерованих нотатках (`.github/release.yml`).

| Розділ нотаток | Мітки |
|---|---|
| Features | `RN: MAJOR FEATURE`, `RN: MINOR FEATURE`, `RN: MAJOR FEATURE - CUSTOM BUILD`, `RN: MINOR FEATURE - CUSTOM BUILD` |
| Improvements | `RN: IMPROVEMENT`, `RN: IMPROVEMENT - CUSTOM BUILD`, `RN: REFACTORING` |
| Fixes | `RN: BUGFIX`, `RN: BUGFIX - CUSTOM BUILD` |
| Targets | `RN: NEW BOARD SUPPORT` |

Варіанти з хвостом `- CUSTOM BUILD` стосуються механізму власних збірок: зміна цікава тим, хто робить свою накладку, а не пілотові стандартної станції, — і потрапляє в окремий рядок того самого розділу.

**Мітка розміру.** Навішується автоматично за кількістю змінених рядків; файли `package-lock.json`, будь-які `*.lock` і `translations/*` до рахунку не входять.

`size/XL` **не валить перевірку** — бот лише додає коментар із порадою розділити запит. Стара мітка розміру знімається окремим кроком, тож на запиті завжди рівно одна.

## Типи комітів і що кожен спричиняє

Правила беруться з `.releaserc.json`, звідки їх читає `semantic-release`.

| Тип | Підняття версії | Розділ нотаток |
|---|---|---|
| `feat` | мінорна | Features |
| `fix` | патчева | Bug Fixes |
| `perf` | патчева | Performance |
| `revert` | патчева | Reverts |
| `docs` | немає | приховано |
| `style` | немає | приховано |
| `chore` | немає | приховано |
| `refactor` | немає | приховано |
| `test` | немає | приховано |
| `build` | немає | приховано |
| `ci` | немає | приховано |

Перші чотири спричиняють випуск, решта сім — ні. Яку саме обіцянку споживачеві дає кожна цифра, розібрано в [семантичному версіонуванні](book:programming/semantic-versioning): мінорна означає нову сумісну можливість, патчева — виправлення без зміни поведінки. Тому `feat` замість `fix` — не питання смаку, а зміщення номера версії на цілу позицію.

Формат заголовка запиту перевіряється тим самим переліком типів, з такими подробицями:

```
<тип>(<область>): <опис>

область   необов'язкова
опис      1–80 символів
wip       заголовок, що починається з "WIP", пропускається
```

Ключова властивість цієї перевірки: вона позначена `continue-on-error`, тобто **не блокує** запит. Замість падіння бот залишає коментар із таблицею «поточний заголовок / запропонований», де другий складено мовною моделлю за дифом і описом; щойно заголовок стає правильним, коментар згортається як розв'язаний.

## Чекліст перед надсиланням

З документа про внесок, у порядку виконання:

1. Перенести гілку на свіжий стан: `git fetch upstream && git rebase upstream/master`.
2. Прогнати `just check` — гачки плюс тести.
3. Оновити документацію, якщо зміна її стосується.
4. Написати опис запиту, що відповідає на чотири питання: яку проблему розв'язує, як перевірено, чи є зламані сумісності, знімок екрана для змін інтерфейсу.

Вимоги, за якими запит приймають:

- усі перевірки CI зелені;
- код відповідає стилю проєкту;
- нова функціональність приходить із тестами в `test/`, що дзеркалить структуру `src/`;
- у дифі немає нічого, що не стосується теми;
- повідомлення комітів — за угодою вище.

Окремо про рев'ю: зауваження виправляють **новими комітами**, примусове надсилання під час рев'ю не застосовують. Ліцензійна вимога перевіряється не автоматикою, а вами: код має бути власним або взятим з BSD, MIT чи Apache 2.0 — копілефтне джерело несумісне з дозвільною гілкою подвійної ліцензії.

Звіт про помилку — окремий вхід із власним переліком: версія застосунку, операційна система з версією, кроки відтворення, файли журналу з теки даних застосунку (на Linux це `~/.local/share/QGroundControl/`) і знімок екрана або відео для проблем інтерфейсу.
