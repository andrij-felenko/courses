# 🗂 Файл налаштувань станції: шляхи, секції, ключі

Це довідник місць і імен: де саме на кожній операційній системі лежить `QGroundControl.ini`, за яким правилом його ключі складаються в секції, які службові ключі там варто вміти впізнати з першого погляду, у яких теках осідають кеші й документи — і що саме стирає кожен із двох аргументів чистки. Потрібен він тоді, коли конфігурацію треба прочитати очима, перенести на іншу машину або знищити прицільно, а не «знести все».

Числа й імена звірено з апстримом `mavlink/qgroundcontrol`, гілка `master` (лінія 5.x, серпень 2026). Там, де стабільна лінія `Stable_V4.4` відрізняється, це названо окремо — питання «а в якій версії?» тут не риторичне: між 4.4 та 5.0 змінилося саме ім'я теки.

## Три рядки, з яких виростає шлях

Ім'я теки й файла станція не вигадує: вона віддає сховищу (`QSettings`) три рядки, зашиті в збірку, і примусово вмикає ini-формат. Рядки задано опціями CMake у `cmake/CustomOptions.cmake`.

| Константа збірки | `master` (5.x) | `Stable_V4.4` |
|------------------|----------------|---------------|
| `QGC_ORG_NAME` — тека | `QGroundControl` | `QGroundControl.org` |
| `QGC_ORG_DOMAIN` | `qgroundcontrol.com` | `org.qgroundcontrol` |
| `QGC_APP_NAME` — файл | `QGroundControl` | `QGroundControl` |
| `QGC_PACKAGE_NAME` — пакунок Android/macOS | `org.mavlink.qgroundcontrol` | не опція збірки |
| `QGC_SETTINGS_VERSION` | `9` | `9` (у `QGCConfig.h`) |

Перейменування організації в лінії 5.x означає нову теку налаштувань: свіжа станція не побачить конфігурації, залишеної четвіркою, і почне з типових значень. Це не помилка й не міграція — просто інша адреса.

**Ім'я застосунку ще й домальовується суфіксом** залежно від того, що це за прогін:

| Прогін | `applicationName` | Файл |
|--------|-------------------|------|
| Звичайний запуск | `QGroundControl` | `QGroundControl.ini` |
| Денна збірка (`QGC_DAILY_BUILD`) | `QGroundControl Daily` | `QGroundControl Daily.ini` |
| Юніт-тест із назвою | `QGroundControl_unittest_<назва>` | `QGroundControl_unittest_<назва>.ini` |
| Юніт-тести без фільтра | `QGroundControl_unittest_<pid>` | те саме з номером процесу |
| Вендорська збірка | своє з `QGC_APP_NAME` | своє |

Тестовий прогін не лише бере окремий файл, а й **прибирає його за собою при виході** — разом зі своєю текою кеша параметрів і своєю текою збереження.

## Де саме лежить файл

Ini-формат прив'язує розташування до конфігураційної теки користувача, а не до реєстру Windows чи `plist` на macOS. Шляхи нижче — для `master`; для лінії 4.4 підставте `QGroundControl.org` замість першого `QGroundControl`.

| ОС | Файл налаштувань |
|----|------------------|
| Linux | `$XDG_CONFIG_HOME/QGroundControl/QGroundControl.ini`; типово `~/.config/QGroundControl/QGroundControl.ini` |
| Windows | `%APPDATA%\QGroundControl\QGroundControl.ini` — тобто `C:\Users\<user>\AppData\Roaming\QGroundControl\QGroundControl.ini` |
| macOS | `~/.config/QGroundControl/QGroundControl.ini` — саме `.config`, а не `~/Library/Preferences`: в ini-режимі сховище лишається на юніксовому шляху |
| Android | `<APPROOT>/files/settings/QGroundControl/QGroundControl.ini`, де `<APPROOT>` = `/data/user/0/org.mavlink.qgroundcontrol`; якщо на пристрої вже існує старіший `<APPROOT>/files/.config/…`, береться він |

Розкид цих шляхів — не примха: операційні системи домовилися розводити конфіг, дані й кеш застосунку по різних коренях саме тому, що ці три речі мають різні права на видалення ([теки застосунку в ОС](topic:programming/app-data-directories)). Тому нижче тека кеша й тека документів матимуть **інші** корені, а не підтеки цього самого.

Перевірити, який файл узяв конкретний запуск, найдешевше з журналу: у першому ж рядку категорії `API.QGCApplication` станція пише і повний шлях, і відповідь на питання, чи вдалося в цей файл записати.

## Як ключ перетворюється на секцію

Усередині застосунку ключ виглядає як шлях через похилу риску: `LinkConfigurations/Link0/portName`. Записувач ini розкладає його за одним правилом.

- **Перша** похила риска ділить ключ на секцію й решту: `LinkConfigurations` → `[LinkConfigurations]`.
- Усі **наступні** похилі риски в решті стають зворотними: `Link0/portName` → `Link0\portName`.
- Ключ **без** похилої риски потрапляє в секцію `[General]`.
- Група, названа `general` у будь-якому регістрі, пишеться як `[%General]` — щоб її не сплутати з попереднім випадком.
- Символи поза набором `A–Z a–z 0–9 _ - .` в **іменах** ключів і секцій кодуються як `%XX`, а ті, що не вміщаються в байт, — як `%Uxxxx`. Тому імена ключів у файлі завжди латиничні.

Значення пишуться інакше, ніж імена, і тут є пастки, через які файл іноді виглядає «дивно»:

| Що у значенні | Як лягає у файл |
|---------------|-----------------|
| Текст | у кодуванні UTF-8, як є — кирилиця в назві каналу читається очима |
| `;`, `,` або `=` усередині | усе значення береться в подвійні лапки |
| Пробіл на початку чи в кінці | те саме — лапки |
| `"` або `\` | екранується зворотною рискою: `\"`, `\\` |
| Керівний символ (код < 0x20) | `\xNN` |
| `bool` | `true` / `false` |
| Список рядків | елементи через `, `; порожній список — `@Invalid()` |
| Двійкові дані | `@ByteArray(…)`, `@Variant(…)` |

Звідси, наприклад, лапки навколо `firstRunPromptIdsShown`: усередині коми, отже — лапки. Ніякої окремої логіки для цього ключа немає.

Ось як це виглядає в живому файлі:

```ini
[General]
SettingsVersion=9
savePath=C:/Users/olena/Documents/QGroundControl
audioMuted=false
qLocaleLanguage=0
firstRunPromptIdsShown="1,2,5"

[Units]
horizontalDistanceUnits=1

[LinkConfigurations]
count=2
Link0\name=Радіомодем
Link0\type=0
Link0\auto=true
Link0\high_latency=false
Link0\portName=COM7
Link0\baud=57600
```

## Групи налаштувань і їхні префікси

Кожна група налаштувань отримує при створенні два імені: перше вказує на JSON-ресурс метаданих (`:/json/<Ім'я>.SettingsGroup.json`), друге стає префіксом у сховищі — тобто **назвою секції ini**. Для більшості груп це просто ім'я класу без слова `Settings`.

| Клас групи | Префікс / секція | Клас групи | Префікс / секція |
|------------|------------------|------------|------------------|
| `AppSettings` | `""` → `[General]` | `MavlinkSettings` | `""` → `[General]` |
| `UnitsSettings` | `Units` | `AutoConnectSettings` | `AutoConnect` |
| `BatteryIndicatorSettings` | `BatteryIndicator` | `MavlinkActionsSettings` | `MavlinkActions` |
| `FirmwareUpgradeSettings` | `FirmwareUpgrade` | `FlightMapSettings` | `FlightMap` |
| `FlightModeSettings` | `FlightMode` | `FlyViewSettings` | `FlyView` |
| `GimbalControllerSettings` | `GimbalController` | `MapsSettings` | `Maps` |
| `OfflineMapsSettings` | `OfflineMaps` | `PlanViewSettings` | `PlanView` |
| `RemoteIDSettings` | `RemoteID` | `RTKSettings` | `RTK` |
| `NTRIPSettings` | `NTRIP` | `VideoSettings` | `Video` |
| `JoystickManagerSettings` | `JoystickManager` | `LogManagerSettings` | `LogManager` |
| `LogViewerSettings` | `LogViewer` | `Viewer3DSettings` | `Viewer3D` |
| `ADSBVehicleManagerSettings` | `ADSBVehicleManager` | `APMMavlinkStreamRateSettings` | `APMMavlinkStreamRate` |

**Дві групи мають порожній префікс** — застосунку й MAVLink. Отже, у `[General]` лежать вперемішку ключі обох, тож однойменних ключів у цих двох групах бути не може. Решта відділені одна від одної секціями.

## Службові ключі в `[General]`

Більшість ключів — звичайні налаштування зі свого JSON-опису. Кілька — службові: вони керують поведінкою самого механізму збереження, і саме їх варто впізнавати у чужому файлі.

| Ключ | Тип | Типове | Що це |
|------|-----|--------|-------|
| `SettingsVersion` | int | — | Версія **формату** сховища, не застосунку. Пише її сам застосунок, а не система фактів. Розбіжність зі своїм числом (`QGC_SETTINGS_VERSION`, зараз `9`) при старті стирає всі налаштування |
| `savePath` | string | `""` у метаданих | Корінь теки документів. Порожнє типове значення — маркер «ще не обрано»: реальний шлях підставляється при першому створенні факту |
| `clearSettingsNextBoot` | bool | `false` | Галочка «скинути все при наступному старті». Читається **напряму** з файла на самому початку запуску, до підняття менеджера налаштувань |
| `disableAllPersistence` | bool | `false` | Вимикає необов'язковий запис: телеметрію не починають писати й не зберігають після польоту, завантажені тайли карти не осідають у кеші |
| `firstRunPromptIdsShown` | string | `""` | Перелік ідентифікаторів уже показаних одноразових вікон, через кому — тому у файлі в лапках |
| `qLocaleLanguage` | uint32 | `0` | Мова інтерфейсу як число `QLocale::Language`; `0` означає «як у системи». Читається окремим раннім шляхом, ще до завантаження JSON-ресурсів |
| `favoriteParameters` | string | `""` | Обрані параметри апарата — імена через кому |

`disableAllPersistence` — прапорець із дірою за визначенням: щоб завтра нічого не писалося, сьогодні у файл лягає хоча б він сам.

Решта ключів у `[General]` — звичайні налаштування. Ось ті, за якими найчастіше лізуть у файл руками:

| Ключ | Тип | Типове | Що це |
|------|-----|--------|-------|
| `audioMuted` | bool | `false` | Глушить озвучення повністю, гучності при цьому не змінює |
| `audioVolume` | double | `100` | Гучність озвучення у відсотках |
| `indoorPalette` | uint32 | `0` | Схема кольорів. `0` — Outdoor (світла), `1` — Indoor (темна). Ім'я ключа згадує лише один із двох варіантів, і саме той, що не є типовим |
| `uiScalePercent` | uint32 | `100` | Масштаб інтерфейсу у відсотках, від `50` до `200` |
| `batteryPercentRemainingAnnounce` | uint32 | `30` | Заряд у відсотках, від якого починається голосове попередження |
| `defaultMissionItemAltitude` | double | `50` | Висота нового пункту місії в метрах |
| `mapboxToken`, `esriToken`, `vworldToken`, `openaipToken`, `tiandituToken` | string | `""` | Ключі доступу до постачальників карт |

Останній рядок вартий окремої уваги при передачі файла комусь: ключі доступу лежать у ньому **відкритим текстом**, як і будь-яке інше рядкове значення.

## Секція `[LinkConfigurations]`

Перелік каналів записано пласким списком: лічильник плюс пронумеровані групи. Читання починається з перевірки, чи є взагалі ключ `count`.

```ini
[LinkConfigurations]
count=3
Link0\name=…
Link1\name=…
Link2\name=…
```

Спільні поля є в кожного каналу незалежно від типу:

| Ключ | Тип | Зміст |
|------|-----|-------|
| `Link<n>\name` | string | Ім'я в списку. Порожнє ім'я — запис відкидається при читанні |
| `Link<n>\type` | int | Номер типу з переліку (таблиця нижче). Відсутній або завеликий — запис відкидається |
| `Link<n>\auto` | bool | Під'єднуватися автоматично при старті |
| `Link<n>\high_latency` | bool | Ознака повільного каналу (супутник, дальній зв'язок) |

**Номер типу — крихке місце.** Елементи переліку компонуються умовно, тож нумерація залежить від прапорців збірки:

| Тип | Звичайна релізна збірка | Без серійного каналу (`QGC_NO_SERIAL_LINK`) | Зневаджувальна (`QT_DEBUG`) |
|-----|:---:|:---:|:---:|
| Серійний | 0 | — | 0 |
| UDP | 1 | 0 | 1 |
| TCP | 2 | 1 | 2 |
| Bluetooth | 3 | 2 | 3 |
| Mock (тестовий) | — | — | 4 |
| Відтворення логу | 4 | 3 | 5 |

Отже, файл, перенесений між збірками різної конфігурації, може дати канали не того типу. Це один із доводів на користь того, що версія формату існує, а скидання не вважається бідою. Що саме означає кожен тип — у [типах каналів](topic:qgroundcontrol/link-types).

### Типозалежні ключі

Далі кожен тип конфігурації дописує своє в ту саму групу `Link<n>`.

**Серійний канал:**

| Ключ | Тип | Типове | Значення |
|------|-----|--------|----------|
| `portName` | string | — | Системне ім'я порту: `COM7`, `/dev/ttyUSB0` |
| `portDisplayName` | string | — | Показуване ім'я; при читанні заново обчислюється, якщо пристрій на місці |
| `baud` | int | `57600` | Швидкість порту |
| `dataBits` | int | `8` | `5` · `6` · `7` · `8` — число дорівнює кількості бітів даних |
| `parity` | int | `0` | `0` немає · `2` парна · `3` непарна · `4` біт завжди 0 · `5` біт завжди 1 |
| `stopBits` | int | `1` | `1` один · `2` два · `3` півтора |
| `flowControl` | int | `0` | `0` немає · `1` апаратне · `2` програмне |
| `dtrForceLow` | bool | `false` | Тримати DTR притиснутим (щоб плата не пішла в перезавантаження) |

Зверніть увагу на `parity` і `stopBits`: числа взято з переліків `QSerialPort`, і вони **не** послідовні — `2` в `stopBits` означає два стоп-біти, а `3` — півтора.

**UDP:**

| Ключ | Тип | Значення |
|------|-----|----------|
| `port` | uint | Локальний порт прослуховування; типове береться з `AutoConnect/udpListenPort` |
| `hostCount` | int | Скільки цілей записано |
| `host<i>` | string | Ім'я або адреса `i`-ї цілі |
| `port<i>` | uint | Порт `i`-ї цілі |

**TCP:** `host` (рядок) і `port` (число).

**Bluetooth:** `mode` (`0` класичний, `1` Low Energy), `deviceName`, `address`, а для LE ще `serviceUuid`, `readCharUuid`, `writeCharUuid` — усі три як рядки з фігурними дужками.

**Відтворення логу:** єдиний ключ `logFilename` — повний шлях до файла телеметрії.

### Два правила запису переліку

- **Секція щоразу переписується цілком:** перед записом вона вичищається, і лише потім наповнюється наново. Інакше ключі видаленого `Link2\…` залишалися б у файлі й ламали читання за лічильником.
- **Динамічні конфігурації пропускаються:** канал, створений автопід'єднанням або переданий аргументом командного рядка, у файл не потрапляє, і нумерація `Link<n>` рахує лише збережувані. Тому номер у файлі може не збігатися з порядком у списку на екрані.

Запис відбувається не за таймером, а в моменти зміни складу переліку — створення, редагування, видалення конфігурації.

## Теки кеша

Кеші — окремий світ від налаштувань, і лежать вони в двох різних місцях: те, що прив'язане до конкретного апарата, живе поруч із ini, а те, що система має право прибрати сама, — у системній теці кеша.

**Поруч із файлом налаштувань** (тобто в теці організації):

| Що | Шлях | Зміст |
|----|------|-------|
| Кеш параметрів | `<тека ini>/<ім'я ini без розширення>/ParamCache/<sysid>_<compid>.v2` | Двійковий знімок «ім'я параметра → тип і значення» для одного компонента одного апарата |
| Кеш метаданих параметрів | `<тека ini>/ParameterFactMetaData.json` | Успадкований одиничний файл |
| Кеш описів конфігурацій PX4 | `<тека ini>/PX4AirframeFactMetaData.xml` | Те саме, для переліку конфігурацій апарата (airframe) |

Приклад для Linux: `~/.config/QGroundControl/QGroundControl/ParamCache/1_1.v2`. Вкладена підтека з іменем збірки ізолює кеші стабільної, денної та паралельних тестових збірок одну від одної. У лінії 4.4 цієї підтеки немає — там шлях коротший, `~/.config/QGroundControl.org/ParamCache/`, і збірки ділять один кеш.

Суфікс `.v2` у назві файла — версія формату **в імені**, а не всередині: зміниться формат — зміниться суфікс, і старі файли просто ніхто не відкриє. Як цей кеш звіряється зі станом апарата, описано в [менеджері параметрів](topic:qgroundcontrol/parameter-manager).

**У системній теці кеша:**

| Що | Шлях |
|----|------|
| Версійований кеш метаданих | `<CacheLocation>/ParameterMetaData/ParameterFactMetaData_<N>.<major>.<minor>.json`, де `N` — номер автопілота з `MAV_AUTOPILOT`. Береться найсвіжіший файл із тим самим `major`, що й вбудований опис |
| База тайлів карти | `<CacheLocation>/QGCMapCache/qgcMapCache.db` |
| Те саме на Android та iOS | `<AppDataLocation>/QGCMapCache/qgcMapCache.db` |
| Запасний варіант, якщо теку не створити | `~/.qgcmapscache/qgcMapCache.db` |

Сам `<CacheLocation>` розкривається так:

| ОС | Шлях |
|----|------|
| Linux | `~/.cache/QGroundControl/QGroundControl` |
| Windows | `C:\Users\<user>\AppData\Local\QGroundControl\QGroundControl\cache` |
| macOS | `~/Library/Caches/QGroundControl/QGroundControl` |
| Android | `<APPROOT>/cache` (для бази тайлів натомість береться `<APPROOT>/files`) |

Межі росту бази тайлів задають звичайні налаштування `Maps/maxCacheDiskSize` і `Maps/maxCacheMemorySize`; влаштування самої бази — в [офлайн-картах](topic:qgroundcontrol/offline-maps).

## Тека збереження й що в ній

Ключ `savePath` тримає лише корінь. Типове значення підставляється при першому створенні факту й залежить від платформи:

| Платформа | Типовий корінь |
|-----------|----------------|
| Linux, Windows, macOS | `<Документи>/<ім'я застосунку>` — наприклад `~/Documents/QGroundControl`, а для денної збірки `~/Documents/QGroundControl Daily` |
| Android | Тека на SD-карті, якщо вона є, доступна на запис і не заборонена ключем `androidDontSaveToSDCard`; інакше `<GenericDataLocation>/<ім'я застосунку>`. Поле сховане від користувача |
| iOS | Корінь `<Документи>` — щоб теки було видно у файловому застосунку |

Підтеки станція створює сама при кожній зміні кореня:

| Підтека | Що в ній | Розширення |
|---------|----------|:----------:|
| `Missions` | Плани польоту | `plan`, а також `waypoints` для успадкованого формату |
| `Parameters` | Збережені набори параметрів | `params` |
| `Telemetry` | Записана телеметрія | `tlog` |
| `Logs` | Вивантажені журнали польоту | `ulg` |
| `Video` | Записане відео | — |
| `Photo` | Знімки | — |
| `CrashLogs` | Звіти про аварійні завершення | — |
| `MavlinkActions` | Описи власних дій MAVLink | — |
| `Settings` | Файли перекриття налаштувань | `settings` |

Власної підтеки не мають ще три розширення, які застосунок знає: `kml` і `shp` (імпорт-експорт геометрії) та `qgctiledb` (експортований набір тайлів).

Практичний висновок про переїзд: файл налаштувань і ця тека — дві незалежні речі, і копіювати треба обидві. Чистка налаштувань до теки документів **не дотягується взагалі**.

## Файли перекриття `*.settings`

Підтека `Settings` — не сміттєзвалище, а точка розширення: усе, що там лежить із розширенням `.settings`, при старті читається як **перекриття метаданих**. Це спосіб змінити типові значення або сховати налаштування, не збираючи [власну збірку](topic:qgroundcontrol/custom-build).

Файли читаються один раз при запуску, в алфавітному порядку імен без урахування регістру; якщо те саме налаштування перекрито кількома файлами, виграє останній.

```json
{
    "version": 1,
    "fileType": "Settings",
    "groups": {
        "Video": {
            "forceVideoDecoder": { "forceRawValue": 0 }
        },
        "": {
            "virtualJoystick": { "visible": false }
        },
        "FlyView": {
            "guidedMinimumAltitude": { "default": 5 }
        }
    }
}
```

Ключ групи — той самий префікс сховища, що й у таблиці секцій вище; для налаштувань застосунку та MAVLink це порожній рядок `""`. Ім'я налаштування — ім'я факту з відповідного `<Ім'я>.SettingsGroup.json`.

| Ключ перекриття | Дія |
|-----------------|-----|
| `forceRawValue` | Закріплює значення намертво **і** ховає налаштування з очей |
| `visible` | `false` ховає налаштування, лишаючи значення чинним |
| `default` | Змінює типове значення; користувач і далі може його змінити |
| `min`, `max`, `decimalPlaces` | Змінюють межі й точність |
| `shortDesc`, `longDesc` | Змінюють підпис і підказку |
| `enumStrings` / `enumValues` | Замінюють **увесь** список варіантів; задаються лише разом і однакової довжини |
| `bitmask` | Замінює весь набір бітових варіантів; `index` — номер біта, не маска |

`forceRawValue` і `visible` разом задавати не можна — вони суперечать одне одному, і пара мовчки відкидається. Писати `name` і `type` немає сенсу: станція підставляє їх сама з наявного опису факту, хоч би що там стояло. Будь-який **невідомий** ключ валить перевірку опису й скасовує перекриття цього налаштування цілком, лишаючи попередження в журналі категорії `Utilities.SettingsManager`.

Наслідок, який плутає найчастіше: **у схованого налаштування збережене значення ігнорується**, і береться типове. Тобто перекриття перемагає вміст ini. Те саме вміє [ядрове розширення](topic:qgroundcontrol/core-plugin) — і перекриття з файлів застосовуються **першими**, а розширення править метадані після них.

## Аргументи чистки

Два аргументи командного рядка чистять різні світи, і розділені вони саме тому, що кеш і налаштування — різні роди стану.

| Аргумент | Що робить |
|----------|-----------|
| `--clear-settings` | Стирає **весь** вміст файла налаштувань, потім видаляє теку `ParamCache` і одразу створює її порожньою |
| `--clear-cache` | Файла налаштувань не чіпає. Видаляє теку `ParamCache`, файли `ParameterFactMetaData.json` і `PX4AirframeFactMetaData.xml` поруч із ini та теку `<CacheLocation>/ParameterMetaData` |

Жоден із двох **не чіпає ані теку документів, ані базу тайлів карти**. Кеш карти прибирають окремо — з розділу офлайн-карт, де набори тайлів видаляють поштучно; місій і логів не чіпає жоден із аргументів.

Скидання налаштувань має три входи, і всі три сходяться в одну й ту саму дію:

1. аргумент `--clear-settings`;
2. збережена галочка `clearSettingsNextBoot` — її значення підмішується до аргументу логічним «або»;
3. розбіжність `SettingsVersion` із `QGC_SETTINGS_VERSION` — тоді ще й піднімається ознака, за якою користувач побачить повідомлення про зміну формату. Звіряють лише тоді, коли ключ у файлі **є**: у зовсім свіжому файлі його немає, і стирати там нічого — число просто дописується.

Третій вхід відрізняється від перших двох однією деталлю: якщо аргумент або галочка вже спрацювали, звірка версії **не виконується взагалі** — файл уже порожній, звіряти нічого.

Порядок дій на самому початку запуску фіксований, і кожен крок стоїть там не випадково:

```
1. скласти імена: applicationName (+ Daily / _unittest_…), organizationName
2. увімкнути ini-формат → шлях до файла визначено
3. записати в журнал шлях і відповідь isWritable()
4. прочитати clearSettingsNextBoot напряму з файла
5. якщо аргумент або галочка → settings.clear() + перестворити ParamCache
   інакше → звірити SettingsVersion, при розбіжності settings.clear()
6. записати SettingsVersion = 9
7. якщо --clear-cache → видалити кеші параметрів і метаданих
8. і лише потім піднімати підсистеми
```

Крок 8 стоїть останнім із конкретної причини: факт налаштування пише у файл у ту саму мить, коли змінюється його значення, а частина фактів набуває значення просто від підйому своєї підсистеми. Найпростіший приклад — `savePath`: при створенні він бачить порожнє типове значення, обчислює шлях до теки документів і одразу присвоює його собі, тобто пише рядок у файл. Якби чистка йшла після підняття підсистем, вона стирала б файл, у якому вже лежить дописане.
