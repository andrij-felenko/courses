# ⚙️ Своя група налаштувань: від JSON-опису до перемикача в інтерфейсі

Ця вставка проводить одну робочу задачу від початку до кінця: додати до станції власну групу налаштувань і скористатися нею з коду й з інтерфейсу — щоб було видно, де в цій підсистемі закінчуються дані й починається код, і чому саме там.

**Задача.** До станції додано власну підсистему — планувальник корисного навантаження, що керує підвісом і знімає за розкладом. Їй потрібні чотири величини, які мусять пережити перезапуск: інтервал спрацювання, профіль навантаження, прапорець автозапуску й тека, куди складати вивантажені файли. Кожна має показуватися в інтерфейсі з підписом і одиницями, перевірятися на межі при введенні й бути доступною і з C++, і з QML.

**Ідея розв'язку.** Не писати нічого з переліченого. Опис величини — це дані, а не код: із них станція сама зробить редактор, перевірку й читання-запис, бо вона робить це для [фактів](book:qgroundcontrol/fact-system) з першого дня. Ваша частина зводиться до класу-порожняка з чотирма рядками-оголошеннями, а весь зміст лягає у JSON. Разом виходить чотири артефакти: файл метаданих, заголовок, реалізація й один рядок реєстрації в менеджері налаштувань.

![Дві половини одного оголошення групи: перше ім'я вказує, який JSON-ресурс із метаданими читати при створенні групи, друге стає секцією у файлі налаштувань на диску; факти народжуються при першому доступі, а звертатися до них можна і з C++, і з QML](/reference/qgroundcontrol/architecture/settings-persistence/img/settings-group-anatomy.svg)
*Уся конструкція тримається на одному рядку макроса, у якому два імені роблять різні речі. Ліве живе тільки під час збірки: за ним будується шлях до ресурсу з метаданими. Праве живе тільки під час роботи: воно стає секцією у файлі налаштувань. Плутанина між ними — найчастіша помилка при додаванні своєї групи, і найнеприємніша, бо помиляється вона тихо.*

## Крок 1. Метадані як дані

Файл `Payload.SettingsGroup.json` описує всі чотири величини й більше нічого:

```json
{
    "version":  1,
    "fileType": "FactMetaData",
    "QGC.MetaData.Facts": [
{
    "name":          "triggerInterval",
    "label":         "Інтервал спрацювання",
    "shortDesc":     "Пауза між знімками під час автоматичного знімання",
    "type":          "double",
    "units":         "s",
    "min":           0.5,
    "max":           60.0,
    "decimalPlaces": 1,
    "default":       2.0
},
{
    "name":        "payloadProfile",
    "label":       "Профіль навантаження",
    "shortDesc":   "Який набір команд слати на підвіс",
    "type":        "uint32",
    "enumStrings": "Фотокамера,Мультиспектр,Лідар",
    "enumValues":  "0,1,2",
    "default":     0
},
{
    "name":      "autoStart",
    "label":     "Починати автоматично",
    "shortDesc": "Запускати знімання при вході в перший галс",
    "type":      "bool",
    "default":   false
},
{
    "name":      "dumpDirectory",
    "label":     "Тека вивантаження",
    "shortDesc": "Куди складати вивантажені з підвісу файли",
    "type":      "string",
    "default":   ""
}
    ]
}
```

Кілька речей тут не очевидні, поки не вдаришся об них.

Ключ типового значення зветься `default`, а не `defaultValue` — метадані параметрів автопілота пишуться іншим набором ключів, і пам'ять раз по раз підсовує чужий. `type` береться зі списку, який розуміє система фактів: цілі різної ширини й знаковості, `float`, `double`, `string`, `bool` і кілька службових; довільного типу тут бути не може, бо саме з нього виводиться і перевірка, і редактор.

`label` — короткий підпис для інтерфейсу, `shortDesc` — пояснення до нього. Порожній `label` не валить застосунок, але лишає критичний запис у журналі: підпис вважається обов'язковим, бо без нього редактор нічим підписати.

Перелічення задають **двома** паралельними рядками: `enumStrings` — те, що бачить людина, `enumValues` — те, що лягає у файл. Розділені комами, однакової довжини. У самій станції ці рядки пишуть англійською й перекладають окремим механізмом; у власній збірці вибір мови вже ваш.

Файл перевіряють за схемою (`factmetadata.schema.json`), тож одрук у назві ключа не мовчить.

## Крок 2. Клас групи: тридцять рядків, з них двадцять — макроси

```cpp
#pragma once

#include <QtQmlIntegration/QtQmlIntegration>
#include "SettingsGroup.h"

class PayloadSettings : public SettingsGroup
{
    Q_OBJECT
    QML_ELEMENT
    QML_UNCREATABLE("")

public:
    PayloadSettings(QObject *parent = nullptr);

    DEFINE_SETTING_NAME_GROUP()

    DEFINE_SETTINGFACT(triggerInterval)
    DEFINE_SETTINGFACT(payloadProfile)
    DEFINE_SETTINGFACT(autoStart)
    DEFINE_SETTINGFACT(dumpDirectory)
};
```

Тіла в класі немає взагалі — усе згенерують макроси. `DEFINE_SETTING_NAME_GROUP()` додає два статичні рядки, `name` і `settingsGroup`; вони й будуть тими двома іменами, про які йшлося. `DEFINE_SETTINGFACT(triggerInterval)` розгортається приблизно в таке:

```cpp
private:
    SettingsFact *_triggerIntervalFact = nullptr;

public:
    Q_PROPERTY(Fact *triggerInterval READ triggerInterval CONSTANT)
    Fact *triggerInterval();
    static const char *triggerIntervalName;
```

Тобто одне слово породжує чотири речі: сховок для вказівника, властивість для QML, метод для C++ і константу з іменем, за яким факт шукатимуть у метаданих. Ім'я в макросі мусить збігатися з полем `name` у JSON **посимвольно** — це єдиний зв'язок між двома файлами, і компілятор його не перевіряє.

## Крок 3. Ліниві факти й місце, куди чіпляти реакцію

```cpp
#include "PayloadSettings.h"

DECLARE_SETTINGGROUP(Payload, "PayloadPlanner")
{
    // тіло конструктора: сюди йде лише те, чого не описати в JSON —
    // наприклад, перелік, що залежить від наявного обладнання
}

DECLARE_SETTINGSFACT(PayloadSettings, triggerInterval)
DECLARE_SETTINGSFACT(PayloadSettings, autoStart)
DECLARE_SETTINGSFACT(PayloadSettings, dumpDirectory)

DECLARE_SETTINGSFACT_NO_FUNC(PayloadSettings, payloadProfile)
{
    if (!_payloadProfileFact) {
        _payloadProfileFact = _createSettingsFact(payloadProfileName);
        connect(_payloadProfileFact, &Fact::rawValueChanged,
                this, &PayloadSettings::_profileChanged);
    }
    return _payloadProfileFact;
}
```

`DECLARE_SETTINGGROUP(Payload, "PayloadPlanner")` — це водночас визначення двох статичних рядків і **заголовок конструктора**, тіло якого ви дописуєте у фігурних дужках одразу за макросом. Конструктор бази при цьому вже зробив головне: прочитав `:/json/Payload.SettingsGroup.json` і склав із нього відображення «ім'я → метадані».

`DECLARE_SETTINGSFACT(PayloadSettings, triggerInterval)` дописує тіло методу — приблизно таке:

```cpp
const char *PayloadSettings::triggerIntervalName = "triggerInterval";

Fact *PayloadSettings::triggerInterval()
{
    if (!_triggerIntervalFact) {
        _triggerIntervalFact = _createSettingsFact(triggerIntervalName);
    }
    return _triggerIntervalFact;
}
```

Ось воно, [ліниве створення](book:programming/lazy-loading): факт народжується при першому звертанні й у цю саму мить читає своє значення з диска. Варіант `_NO_FUNC` існує рівно для випадку, коли до народження треба щось додати — приєднати обробник, перерахувати похідні величини. Обробник чіпляють **усередині** гілки створення, а не в конструкторі групи: у конструкторі факту ще немає, і звертання до нього там зруйнувало б усю лінивість.

> 🔧 **Навіщо це.** Лінивість тут не про мікросекунди старту, а про вміст файлу на диску. Група, до якої ніхто не звертався, не створює жодного факту — отже, не пише жодного ключа. Файл налаштувань лишається переліком того, чого людина торкалася, а не знімком усієї конфігурації. Це видно й у зворотний бік: якщо ваш код читає налаштування на старті «про всяк випадок», ви цим-таки прописуєте його в файл усім користувачам — і наступна версія станції вже не зможе змінити для них типове значення.

## Крок 4. Збірка й реєстрація

Два рядки в `CMakeLists.txt` теки, де лежить ваш клас:

```cmake
target_sources(${CMAKE_PROJECT_NAME}
    PRIVATE
        PayloadSettings.cc
        PayloadSettings.h
)

qgc_add_json_resources(json_payload_settings)
```

Друга функція — власна допоміжна станції: вона збирає всі `*.json` поточної теки й додає їх у ресурси під префіксом `/json`. Оскільки це збирання за взірцем, новий файл підхоплюється лише після перезапуску конфігурації складання; якщо ви кладете JSON поруч із рештою груп, де така стрічка вже є, дописувати нічого не треба. Подробиці налаштування збірки — у [збірці станції](book:qgroundcontrol/building-qgc).

Далі — менеджер налаштувань. У заголовку:

```cpp
    Q_PROPERTY(QObject *payloadSettings READ payloadSettings CONSTANT)
    Q_MOC_INCLUDE("PayloadSettings.h")
    // ...
    PayloadSettings *payloadSettings() const;

private:
    PayloadSettings *_payloadSettings = nullptr;
```

У реалізації — один рядок у `init()`, серед решти груп:

```cpp
void SettingsManager::init()
{
    _unitsSettings = new UnitsSettings(this);   // мусить бути першою
    _appSettings   = new AppSettings(this);
    // ...
    _payloadSettings = new PayloadSettings(this);
}
```

Порядок тут не косметичний: група одиниць створюється першою, бо на неї спирається група застосунку, а через перерахунок величин — і метадані решти фактів. Свою групу дописуйте в кінець, і питання не постане.

Зверніть увагу: **групи створюються всі одразу**, ліниві тільки факти. Тобто JSON вашої групи читається при кожному старті станції, навіть якщо в розділ ніхто не зайде. Ціна — розбір кількох кілобайтів; але якщо описів у вас сотні, це вже помітно, і думати про це варто заздалегідь.

Сам менеджер — [сінглтон](book:programming/singleton) з методом `instance()`, тож ніякої передачі посилань крізь півзастосунку не потрібно.

## Крок 5. Читання й запис із C++

```cpp
#include "SettingsManager.h"
#include "PayloadSettings.h"

void PayloadPlanner::start()
{
    PayloadSettings *payload = SettingsManager::instance()->payloadSettings();

    const double interval = payload->triggerInterval()->rawValue().toDouble();
    const uint32_t profile = payload->payloadProfile()->rawValue().toUInt();

    if (payload->autoStart()->rawValue().toBool()) {
        _beginCapture(profile, interval);
    }

    connect(payload->triggerInterval(), &Fact::rawValueChanged,
            this, [this](const QVariant &value) {
        _retimeCapture(value.toDouble());
    });
}

void PayloadPlanner::setDumpDirectory(const QString &path)
{
    // запис на диск відбувається тут-таки, окремої дії «зберегти» немає
    SettingsManager::instance()->payloadSettings()->dumpDirectory()->setRawValue(path);
}
```

Два зауваження, які варті окремої уваги.

Факт віддає значення у двох виглядах: `rawValue()` — те, що зберігається й іде в протокол, `cookedValue()` — те саме після перерахунку в одиниці, обрані користувачем. Для інтервалу в секундах різниці немає, для відстані чи швидкості — величезна. Правило просте: усе, що йде до заліза або у файл, бере `rawValue()`; `cookedValue()` існує для показу.

Підписка на `rawValueChanged` — не дрібниця зручності. Налаштування може змінитися будь-якої миті з інтерфейсу, і код, який прочитав його один раз на старті, працюватиме зі старим числом до перезапуску. Це найтиповіша скарга «змінив, а нічого не сталося».

## Крок 6. Той самий факт у QML

```qml
import QtQuick
import QtQuick.Layouts
import QGroundControl
import QGroundControl.Controls
import QGroundControl.FactControls

ColumnLayout {
    property var payload: QGroundControl.settingsManager.payloadSettings

    GridLayout {
        columns: 2

        QGCLabel      { text: payload.triggerInterval.shortDescription }
        FactTextField { fact: payload.triggerInterval; Layout.fillWidth: true }

        QGCLabel     { text: payload.payloadProfile.shortDescription }
        FactComboBox { fact: payload.payloadProfile; indexModel: false }
    }

    FactCheckBox {
        fact: payload.autoStart
        text: payload.autoStart.shortDescription
    }
}
```

Тут не написано ані меж, ані одиниць, ані типу — редактори дістають усе це з метаданих факту. `FactTextField` сам не пустить `70` у поле з максимумом `60`, `FactComboBox` сам візьме назви з `enumStrings`, а `FactCheckBox` знає, що факт логічний. Це і є та вигода, заради якої налаштування взагалі зробили фактами: описавши величину один раз даними, ви більше ніде її не описуєте.

## Пастки

**Два імені — не одне.** `DECLARE_SETTINGGROUP(Payload, "PayloadPlanner")`: перше — ім'я класу-заготовки, з якого будується шлях до ресурсу `:/json/Payload.SettingsGroup.json`; друге — префікс у сховищі, тобто секція `[PayloadPlanner]` у файлі налаштувань. Вони незалежні. Помиляються здебільшого в другому: скопіювали сусідню групу, забули змінити рядок — і ваші ключі осіли в чужій секції поверх чужих однойменних. Група застосунку, до речі, має **порожній** другий рядок, тож її ключі лежать просто в корені файлу.

**Немає метаданих — застосунок падає.** Одрук в імені факту (`triggerIntervall` у макросі проти `triggerInterval` у JSON) або забутий у ресурсах JSON — і при першому звертанні до факту застосунок пише в журнал шлях, якого не знайшов, і завершується з `exit(-1)`. Різкість навмисна: факт без метаданих не має ні типу, ні меж, і працювати з ним було б небезпечніше, ніж не працювати взагалі. Наслідок для вас — помилка спливає **не при збірці, а при першому відкритті вашого розділу**, тож пройдіться по всіх нових налаштуваннях руками, перш ніж віддавати збірку.

**Перейменування ключа лишає сироту.** Сховище нічого не прибирає саме. Перейменували `triggerInterval` на `captureInterval` — старий запис назавжди лишиться у файлі, а новий ключ читатиме типове значення, ніби людина ніколи його не чіпала. Штатний спосіб один: підняти число версії формату (`QGC_SETTINGS_VERSION`), і тоді при наступному старті станція **зітре весь файл** налаштувань і покаже повідомлення, що значення повернуто до типових. Ціна така сама, як у [міграцій схеми](book:programming/database-migrations), тільки навпаки: замість писати й тестувати код переносу, платять гучною разовою втратою в усіх користувачів. Тому версію піднімають на релізному циклі й гуртом, а не на кожен свій рефакторинг — а до релізу простіше пожити зі старою назвою ключа.

**Перелік у пронумерованих ключах треба чистити перед записом.** Якщо ваша підсистема зберігає не одну величину, а список — скажімо, кілька профілів навантаження, — плоске сховище «ключ — значення» саме по собі списків не має, і список розкладають на `Profile0`, `Profile1`, … з лічильником. Ключі, які колись з'явилися, самі не зникають, тож запис **мусить** починатися з видалення всієї гілки:

```cpp
void PayloadPlanner::saveProfiles(const QList<PayloadProfile> &profiles)
{
    QSettings settings;

    settings.remove(kProfilesRoot);          // без цього лишиться хвіст
    settings.beginGroup(kProfilesRoot);
    settings.setValue("count", profiles.count());

    for (int i = 0; i < profiles.count(); i++) {
        settings.beginGroup(QStringLiteral("Profile%1").arg(i));
        settings.setValue("name",     profiles[i].name);
        settings.setValue("interval", profiles[i].interval);
        settings.endGroup();
    }

    settings.endGroup();
}
```

Приберіть перший рядок — і при переході з трьох профілів на два у файлі лишиться `Profile2\name` з видаленого. Читання за лічильником його не помітить, але будь-який обхід гілки — помітить, і в списку з'явиться привид. Саме так станція зберігає конфігурації каналів: секцію спершу вичищають цілком, а потім пишуть наново, пропускаючи створені автоматично. Альтернатива — записувати список через `beginWriteArray()`, який робить це прибирання сам; вибирайте одну форму й тримайтеся її, бо на диску вони виглядають по-різному.

**Невидиме налаштування не торкається диска.** Група має ознаку видимості, а метадані окремого факту може виправити [ядрове розширення](book:qgroundcontrol/core-plugin) або файл-перекриття. Якщо факт визнано невидимим, він **не читає** збережене значення й **не пише** змін: береться типове з метаданих. Логіка правильна — сховане налаштування не має воскресати з давнього запису у файлі, — але вона ж і дає найзагадковіший баг вендорських збірок: «значення не запам'ятовується». Перше, що варто перевірити, — чи не сховане воно.

Той самий механізм дає й корисний прийом. Файл із розширенням `.settings` у підтеці `Settings` теки збереження може перекрити метадані будь-якої групи, зокрема примусово задати значення:

```json
{
    "version":  1,
    "fileType": "Settings",
    "groups": {
        "PayloadPlanner": {
            "triggerInterval": { "forceRawValue": 5.0 }
        }
    }
}
```

Так інтервал фіксують на весь парк машин без правки коду. Одночасно задавати примусове значення й лишати налаштування видимим не можна: видиме читається зі сховища й тим-таки переб'є примусове, тому такий запис станція визнає суперечливим і пропускає.

**У юніт-тестах значення завжди типове.** Читання зі сховища при тестовому прогоні пропускається — інакше налаштування машини розробника впливали б на результат тестів. Тест, якому потрібне інше значення, ставить його явно через `setRawValue()`.

**Кожна зміна — окремий запис у файл.** Прив'язувати факт налаштувань до величини, що змінюється безперервно (позиція повзунка під час тягання), — марна робота диску. Прив'язуйте до завершеної дії.

## Що це коштувало

Ваш внесок — чотири артефакти й близько п'ятдесяти рядків, із яких сорок описують дані, а не поведінку. Задарма при цьому дістається розбір типу, перевірка меж, підпис і одиниці, готовий редактор для кожного типу, читання при народженні й запис при кожній зміні, доступ із QML, можливість вендорської збірки перекрити типове значення й можливість зафіксувати значення файлом на парк машин.

Головна властивість цієї схеми в тому, що межа між даними й кодом проведена в правильному місці: усе, що можна описати, описано в даних, а код лишається тільки там, де без нього не обійтися. Тому нове налаштування коштує один запис у JSON плюс один рядок у класі — і це саме той рівень витрат, за якого люди перестають зберігати конфігурацію «десь у себе». Що, власне, і є справжня мета такої підсистеми, а не сама по собі зручність оголошення.
