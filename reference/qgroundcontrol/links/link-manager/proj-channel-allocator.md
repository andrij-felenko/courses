# ⚙️ Видача каналів MAVLink бітовою маскою

Номер каналу MAVLink — не ярлик і не ідентифікатор з'єднання, а індекс у статичному масиві станів розбирача, і на настільній збірці таких індексів рівно шістнадцять. Отже, це справжній обмежений ресурс: його треба вміти видати, повернути й чесно сказати «більше нема» — і все це коштує рівно одне 32-бітове число.

## Що саме роздають

Розбирач MAVLink написаний на C і тримає свій проміжний стан там, де його не треба нікому передавати, — у статичному масиві всередині функції:

```c
MAVLINK_HELPER mavlink_status_t* mavlink_get_channel_status(uint8_t chan)
{
    static mavlink_status_t m_mavlink_status[MAVLINK_COMM_NUM_BUFFERS];
    return &m_mavlink_status[chan];
}
```

Довжина масиву — константа етапу збірки:

```c
#ifndef MAVLINK_COMM_NUM_BUFFERS
#if (defined linux) | (defined __linux) | (defined  __MACH__) | (defined _WIN32)
# define MAVLINK_COMM_NUM_BUFFERS 16
#else
# define MAVLINK_COMM_NUM_BUFFERS 4
#endif
#endif
```

Звідси все й випливає. Ресурс, який видає станція, — це не об'єкти, не дескриптори й не вказівники, а **малі цілі числа від 0 до 15**. Числа взаємозамінні: жодне з них нічим не краще за інше, важливо лише, щоб два з'єднання одночасно не тримали одне й те саме. QGroundControl додатково резервує нульовий номер за собою, тож насправді роздати можна п'ятнадцять.

Те, що ресурс — це підмножина невеликої фіксованої множини номерів, і визначає структуру даних. Далі це просто впізнати.

## Чому маска, а не лічильник і не список

Три очевидні варіанти варто зважити до кінця, бо кожен виглядає розумно, поки не спитати про повернення.

**Лічильник, що росте.** `return _next++;` — найдешевше з можливого. Ламається на першому ж від'єднанні: номер, який повернули, лічильник видати вже не може, а масив у бібліотеці має рівно шістнадцять комірок. Оператор шістнадцять разів утикає й висмикує USB — і станція більше ні з ким не з'єднається. Монотонний лічильник придатний тільки там, де номери **не мусять** повертатися, — скажімо, для наскрізних номерів повідомлень чи для [людських ідентифікаторів](book:programming/sequences-counters). Тут — ні.

**Список вільних номерів.** `std::vector<uint8_t>` або `std::set<uint8_t>`, наповнений на старті числами 0…15; узяти — зняти з кінця, повернути — покласти назад. Працює. Але за цю правильність платять невідповідно до задачі: динамічна пам'ять там, де потрібно лише 16 бітів інформації; окремий момент ініціалізації, який має відбутися раніше за перше з'єднання; питання «а чи зайнято номер 5?» — це прохід списком; і, головне, сам список не заважає покласти в нього той самий номер двічі.

**Бітова маска.** Кожному номеру відповідає біт одного слова; одиниця означає «зайнято». Стан усього розподільника — чотири байти без купи й без ініціалізації в рантаймі: `uint32_t` із початковим значенням просто лежить у полі об'єкта. Перевірка, взяття й повернення — по одній машинній операції. Ще й приємна дрібниця: увесь стан пишеться в журнал одним шістнадцятковим числом, і `0x0007` відразу читається як «зайняті нульовий, перший і другий».

Загальне правило звучить так: **список — це подання множини наперед невідомого розміру, а маска — подання підмножини відомого малого всесвіту**. Коли всесвіт — шістнадцять номерів, а слово процесора має тридцять два біти, вся множина влазить у регістр, і будь-яка інша структура буде дорожчою обгорткою над тією самою ідеєю. Про самі біти в числі — у темі [біти й порядок байтів](book:programming/bits-bytes-endianness); про загальну схему «видали з обмеженого набору, попрацював — поверни» — у [пулі об'єктів](book:programming/object-pool).

## Код видачі

Маска живе в менеджері й стартує не з нуля:

```cpp
uint32_t _mavlinkChannelsUsedBitMask = 1;   // нульовий канал зайнято ще до старту
```

Сама видача — лінійний перебір у пошуку першого нуля:

```cpp
uint8_t LinkManager::allocateMavlinkChannel()
{
    for (uint8_t mavlinkChannel = 0; mavlinkChannel < MAVLINK_COMM_NUM_BUFFERS; mavlinkChannel++) {
        if (_mavlinkChannelsUsedBitMask & (1 << mavlinkChannel)) {
            continue;                                   // біт стоїть — номер уже в когось
        }

        mavlink_reset_channel_status(mavlinkChannel);    // прибрати за попереднім орендарем
        mavlink_status_t* const mavlinkStatus = mavlink_get_channel_status(mavlinkChannel);
        mavlinkStatus->flags |= MAVLINK_STATUS_FLAG_OUT_MAVLINK1;

        _mavlinkChannelsUsedBitMask |= (1 << mavlinkChannel);   // і аж тепер — зайняти
        return mavlinkChannel;
    }

    qCWarning(LinkManagerLog) << "allocateMavlinkChannel: all channels reserved!";
    return invalidMavlinkChannel();
}
```

![Перебір бітів маски знизу вгору: перший нуль стає номером каналу; три бітові операції — перевірити, взяти, повернути](/reference/qgroundcontrol/links/link-manager/img/alloc-scan.svg)

*Три операції над маскою вичерпують увесь розподільник. Якщо жодного нуля не знайшлося, повертається не «якийсь поганий номер», а окреме значення 0xFF.*

Дві дрібниці в цьому циклі варті окремої уваги.

Перебір іде **від молодшого біта**, а не від останнього звільненого. Номери рівноправні, тож будь-який порядок дав би робочий код; вибір найменшого тримає маску щільною, і за журналом видно не хаотичну розсипку, а «скільки з'єднань, стільки й молодших бітів».

Стан каналу прибирають **до** того, як біт стає одиницею. Порядок безкоштовний, а сенс у нього прямий: номер оголошують зайнятим лише тоді, коли за ним уже чисто. Зворотний порядок лишив би — нехай і мікроскопічний — проміжок, у якому маска каже «канал видано», а стан за ним іще чужий.

## Що саме віддають разом із номером

Тут ховається найнеочевидніше. Функція з назвою `mavlink_reset_channel_status` виглядає так, ніби вона обнуляє запис стану. Насправді:

```c
MAVLINK_HELPER void mavlink_reset_channel_status(uint8_t chan)
{
	mavlink_status_t *status = mavlink_get_channel_status(chan);
	status->parse_state = MAVLINK_PARSE_STATE_IDLE;
}
```

Одне поле. «Забудь, де ти зупинився посеред пакета» — і не більше. Решта запису переживає скидання:

```c
typedef struct __mavlink_status {
    uint8_t msg_received;
    uint8_t buffer_overrun;
    uint8_t parse_error;
    mavlink_parse_state_t parse_state;
    uint8_t packet_idx;
    uint8_t current_rx_seq;
    uint8_t current_tx_seq;
    uint16_t packet_rx_success_count;
    uint16_t packet_rx_drop_count;
    uint8_t flags;
    uint8_t signature_wait;
    struct __mavlink_signing *signing;
    struct __mavlink_signing_streams *signing_streams;
} mavlink_status_t;
```

Саме тому два рядки після скидання не декоративні. `flags` тримає, у якій версії протоколу канал **говорить** і в якій **чує**; менеджер виставляє консервативне «на вихід — перша версія», а `LinkInterface`, отримавши номер, одразу перевизначає:

```cpp
mavlink_set_proto_version(_mavlinkChannel, MAVLINK_VERSION);
```

Цей рядок легко прочитати неправильно. `MAVLINK_VERSION` — це **не** двійка й не номер версії дротового протоколу: у згенерованих заголовках це номер версії самого діалекту, узятий із XML (у поточних заголовках бібліотеки — трійка). Працює воно тому, що помічник перевіряє не рівність, а порівняння:

```c
MAVLINK_HELPER void mavlink_set_proto_version(uint8_t chan, unsigned int version)
{
	mavlink_status_t *status = mavlink_get_channel_status(chan);
	if (version > 1) {
		status->flags &= ~(MAVLINK_STATUS_FLAG_OUT_MAVLINK1);
	} else {
		status->flags |= MAVLINK_STATUS_FLAG_OUT_MAVLINK1;
	}
}
```

Тобто «будь-що більше за одиницю» означає «виходь другою версією». Менеджер поставив прапорець, з'єднання його зняло — два записи в одне поле з різних шарів, і кожен окремо виглядає осмислено. Знати про цей шов варто: якщо колись доведеться розбиратися, чому станція шле пакети не тієї версії, шукати треба в **обох** місцях.

Третє, що йде з номером, — підпис. Поля `signing` і `signing_streams` — це **вказівники** на структури, якими володіє викликач:

```c
typedef struct __mavlink_signing {
    uint8_t flags;
    uint8_t link_id;
    uint64_t timestamp;
    uint8_t secret_key[32];
    mavlink_accept_unsigned_t accept_unsigned_callback;
    mavlink_signing_status_t last_status;
} mavlink_signing_t;
```

Секретний ключ лежить у пам'яті застосунку, а бібліотека лише дивиться на нього через вказівник у записі каналу. Тому разом із номером створюють нового власника цього ключа й одразу приводять підпис у визначений стан:

```cpp
_signingController = std::make_unique<SigningController>(
    static_cast<mavlink_channel_t>(_mavlinkChannel));
_signingController->clearSigning();
```

Пропустити цей крок означало б, що нове з'єднання підписуватиме пакети ключем попереднього орендаря каналу — а якщо той орендар уже помер, то й узагалі вказівником у звільнену пам'ять. Що таке підпис і навіщо він потрібен — у темі [підпис повідомлень MAVLink 2](book:communications/mavlink-v2-signing).

![Запис стану каналу: скидання чіпає лише parse_state, версію й підпис доводять руками, а лічильники не чистить ніхто](/reference/qgroundcontrol/links/link-manager/img/handover.svg)

*Видача каналу — це не «дати число», а «дати число й прибрати за попереднім». Лічильники наскрізних номерів і втрат переходять новому орендарю у спадок, і цього ніхто не виправляє.*

## Код повернення

Повернення живе у двох місцях, і поділ між ними точний: з'єднання прибирає **стан**, менеджер прибирає **біт**.

```cpp
void LinkInterface::_freeMavlinkChannel()
{
    if (!mavlinkChannelIsSet()) {
        return;                                    // нема чого повертати
    }

    _signingController.reset();                    // обʼєкт із ключем помирає...

    mavlink_status_t* const status = mavlink_get_channel_status(_mavlinkChannel);
    status->signing = nullptr;                     // ...тож вказівники на нього
    status->signing_streams = nullptr;             //    мусять зникнути тут-таки
    mavlink_reset_channel_status(_mavlinkChannel);

    LinkManager::instance()->freeMavlinkChannel(_mavlinkChannel);
    _mavlinkChannel = LinkManager::invalidMavlinkChannel();   // і забути свій номер
}
```

```cpp
void LinkManager::freeMavlinkChannel(uint8_t channel)
{
    if (invalidMavlinkChannel() == channel) {
        return;
    }
    _mavlinkChannelsUsedBitMask &= ~(1 << channel);
}
```

Два рядки з `nullptr` стоять упритул до `reset()` не випадково: між знищенням контролера й обнуленням вказівників запис каналу кілька операторів указує в звільнену пам'ять. Вставити між ними будь-що — і з'явиться вікно, у якому чужий код може зазирнути в цей вказівник.

Останній рядок першої функції — головна лінія оборони всієї схеми, і чому саме він, видно з наступного розділу.

## Чому 0xFF, а не 0

«Каналу нема» — теж стан, і його треба якось записати. QGroundControl бере вартове значення:

```cpp
static constexpr uint8_t invalidMavlinkChannel() { return std::numeric_limits<uint8_t>::max(); }
```

```cpp
uint8_t _mavlinkChannel = std::numeric_limits<uint8_t>::max();
bool mavlinkChannelIsSet() const { return (invalidMavlinkChannel() != _mavlinkChannel); }
```

Нуль на цю роль не годиться з трьох різних причин, і кожна самостійна.

**Нуль — законний індекс.** У бібліотеці канал 0 нічим не гірший за решту: це перша комірка масиву. «Нема каналу» і «канал нульовий» — різні факти, і одне значення не може означати обидва.

**Резервування нуля — це політика, а не кодування.** QGC справді ніколи не видає нульовий номер, тож сьогодні нуль і був би вільний під вартове значення. Але «які номери ми роздаємо» і «як ми пишемо слово *нічого*» — два незалежні рішення, і зшивати їх в одне небезпечно: досить комусь звільнити біт 0 під використання, і кожна перевірка `if (channel)` почне тихо брехати, не змінившись жодним символом. Значення поза діапазоном таких зв'язків не створює: 255 не стане валідним номером за жодного `MAVLINK_COMM_NUM_BUFFERS`, бо індекс і так `uint8_t`, а 255 — остання його сходинка.

**Вартове значення стає типовим.** Поле оголошене одразу з ним, тож щойно збудований `LinkInterface` уже правильно каже «каналу не маю» — без коду в конструкторі й без сусіднього `bool _hasChannel`. Два поля можуть розійтися між собою; одне — ні. А `mavlinkChannelIsSet()` після цього не веде жодного окремого обліку: усе питання «чи тримаю я канал» — це порівняння одного байта.

Ціна такого рішення теж є: вартове значення живе в домовленості, а не в типі. Компілятор не змусить перевірити `mavlinkChannelIsSet()` перед використанням, як змусив би [optional](book:cpp-standards/optional). Але номер каналу переходить у C-функції, де він мусить бути голим `uint8_t`, — а на цій межі обгортка все одно розпалася б на те саме число плюс окремий прапорець. Про загальний вибір між вартовим значенням і типом, що вміє порожнечу, — у [вартових значеннях](book:programming/sentinel-values).

## Скільки це коштує

Перебір — не більше шістнадцяти повторів із однією операцією «І» та однією умовою всередині; навіть за тридцяти двох каналів це кілька наносекунд, і трапляється воно раз на з'єднання, тобто кілька разів за годину. Оптимізувати тут нема чого. Але варіант за одну операцію пишеться в один рядок і має приємну властивість:

```cpp
#include <bit>

uint8_t LinkManager::allocateMavlinkChannel()
{
    const uint32_t freeBits = ~_mavlinkChannelsUsedBitMask;   // одиниця = вільно
    const int i = std::countr_zero(freeBits);                 // молодший вільний номер

    if (i >= MAVLINK_COMM_NUM_BUFFERS) {
        return invalidMavlinkChannel();                       // сюди ж падає і «все зайнято»
    }
    // ... прибрати стан каналу i, виставити біт, повернути i
}
```

Окремої гілки «маска повна» тут не потрібно: `std::countr_zero` для нуля за визначенням віддає розрядність типу, тобто 32, а якщо зайняті всі шістнадцять молодших бітів — 16. Обидва числа не менші за `MAVLINK_COMM_NUM_BUFFERS`, і та сама умова ловить обидва випадки.

Пам'яті розподільник з'їдає рівно чотири байти. Дорого коштує не він, а те, що за номерами: кожен канал тягне свій запис `mavlink_status_t` у кілька десятків байтів, і ці записи існують завжди, незалежно від того, скільки каналів реально видано.

## Пастки

**Зсув одиниці зі знаком.** `1 << mavlinkChannel` — це зсув `int`, а не `unsigned`. За шістнадцяти каналів усе гаразд, але збірка, що підніме `MAVLINK_COMM_NUM_BUFFERS` до 32, перетворить останній канал на невизначену поведінку: `1 << 31` для знакового типу переповнює його. Звичка писати `1u <<` не коштує нічого й забирає пастку назовсім.

**Подвійне звільнення.** Саме по собі `mask &= ~bit` ідемпотентне: двічі зняти той самий біт — те саме, що зняти один раз. Ні падіння, ні запису в журнал. Небезпечне тут інше: між двома звільненнями номер може вже належати комусь іншому. Послідовність виглядає так — з'єднання A віддає номер 3; з'єднання B під'єднується й отримує 3; спізніла копія коду A віддає 3 ще раз; з'єднання C під'єднується й теж отримує 3. Тепер B і C сидять на одному записі стану, обидва бачать переплетені напівпакети й помилки контрольної суми. Маска нічим не могла цьому зарадити: вона зберігає «зайнято», але не зберігає **ким**.

Оборона тому стоїть не в масці, а в об'єкті: рання перевірка `if (!mavlinkChannelIsSet()) return;` і рядок `_mavlinkChannel = invalidMavlinkChannel();` наприкінці. Інваріант простий — номер звільняє тільки його власник, і тим самим рухом перестає бути власником. Прямий виклик `LinkManager::freeMavlinkChannel(3)` звідкись іще обходить цю оборону повністю; тому в коді він не трапляється ніде, крім `LinkInterface::_freeMavlinkChannel`.

Того ж роду й обережність на вході:

```cpp
Q_ASSERT(!mavlinkChannelIsSet());

if (mavlinkChannelIsSet()) {
    qCWarning(LinkInterfaceLog) << "already have" << _mavlinkChannel;
    return true;
}
```

Перевірка стоїть двічі навмисно. У зневаджувальній збірці твердження падає голосно й показує, хто просить канал удруге; у робочій воно зникає, і залишається `if`, який просто не дає повторно взяти другий номер поверх наявного.

**Витік каналу.** Маска не скидається сама ніколи й ніким не звіряється. Якщо канал видали, а `_connect()` не вдався й відкат виявився неповним, біт залишиться одиницею до кінця роботи застосунку. П'ятнадцять невдалих спроб на мертвому порту — і станція більше не з'єднається ні з чим, причому провал вилізе зовсім в іншому місці й без жодного пояснення. Саме тому відкат у `createConnectedLink` обов'язково викликає `_freeMavlinkChannel()`, а не просто забуває про об'єкт.

> 🔧 **Навіщо це.** Витік каналів має чіткий відбиток у журналі. Увімкніть категорію `LinkManagerLog` і порахуйте рядки: кожному `allocateMavlinkChannel N` має відповідати свій `freeMavlinkChannel N`. Якщо номери, що видаються, повзуть угору й ніколи не повторюються, а з'єднань на екрані менше — біти течуть. Симптом із боку користувача той самий, що й у вичерпання: кнопка «З'єднати» просто нічого не робить.

**Вичерпання.** Коли вільних бітів не лишилося, `allocateMavlinkChannel` повертає `0xFF`, `LinkInterface::_allocateMavlinkChannel` бачить, що канал не виставлено, і повертає `false`, а `createConnectedLink` через це повертає `false` — з'єднання не народжується. Інтерфейс скаже «не вдалося під'єднатися», і єдиний слід справжньої причини — попередження `all channels reserved!` у журналі. П'ятнадцяти каналів людині-оператору вистачає з великим запасом, але станція з кількома апаратами, каналом пересилання, відтворенням логу й парою UDP-точок підбирається до стелі відчутно. А на збірці не для настільної системи стеля — чотири канали, з яких видати можна три.

**Ніякого замка на масці.** `_mavlinkChannelsUsedBitMask` — звичайний `uint32_t`, а `|=` і `&=` над ним — це «прочитати, змінити, записати». Тримається все на тому, що обидві функції викликають лише з головного потоку: видачу — з `createConnectedLink`, повернення — з обробника відкладеного сигналу про розрив. Додайте виклик із власного потоку з'єднання — і два канали тихо отримають однаковий номер, бо одне з двох читань побачить застарілу маску. Полагодити це м'ютексом було б надміру: природний засіб — `std::atomic<uint32_t>` із циклом `compare_exchange`, тим паче що перебір і так читає маску заново. Чому саме читання-зміна-запис ламається без синхронізації — у [потоковій безпеці](book:programming/thread-safety).

**Номер єдиний рівно настільки, наскільки єдиний масив за ним.** Запис стану — це статична змінна всередині функції, а сама функція оголошена як `MAVLINK_HELPER`, тобто `static inline`. У C++ `static` дає внутрішнє зв'язування, і кожна одиниця трансляції, яка викликає `mavlink_get_channel_status`, дістає **власну** копію масиву — питання зв'язування, а не оптимізації ([ODR і зв'язування](book:cpp-standards/odr-and-linkage)). Бібліотека тримає для цього окремий макрос `MAVLINK_EXTERNAL_RX_STATUS`, який виносить масив назовні, в одне-єдине визначення; у заголовку-обгортці QGroundControl (`src/MAVLink/MAVLinkLib.h`) його не визначено. Практичний висновок для будь-якої власної збірки: номер каналу — це ключ до масиву того, хто його тримає, тож розбір і прибирання стану варто тримати там, де вони справді дивляться в один масив.

## Перевірити руками

Уся механіка розподільника вміщається в самодостатню програму, на якій видно і перевикористання номера, і крадіжку каналу подвійним звільненням, і вичерпання:

```cpp
// c++ -std=c++20 -O2 chan.cpp && ./a.out
#include <bit>
#include <cstdint>
#include <cstdio>
#include <limits>

constexpr uint8_t kChannels = 16;
constexpr uint8_t kInvalid  = std::numeric_limits<uint8_t>::max();

static uint32_t g_used = 1;                     // біт 0 зарезервовано

static uint8_t take()
{
    for (uint8_t i = 0; i < kChannels; ++i) {
        if (g_used & (1u << i)) { continue; }
        g_used |= (1u << i);
        return i;
    }
    return kInvalid;
}

static void give(uint8_t ch)
{
    if (ch == kInvalid) { return; }
    g_used &= ~(1u << ch);
}

static int freeCount() { return std::popcount(~g_used & 0xFFFFu); }

int main()
{
    const uint8_t a = take();            // 1
    const uint8_t b = take();            // 2
    give(a);
    const uint8_t c = take();            // знову 1 — номер перевикористано
    printf("a=%u b=%u c=%u  маска=0x%04X  вільних=%d\n",
           (unsigned)a, (unsigned)b, (unsigned)c, (unsigned)g_used, freeCount());

    give(c);                             // власник повернув свій номер
    const uint8_t d = take();            // сусід узяв той самий номер
    give(c);                             // спізніла копія власника віддає його ВДРУГЕ
    const uint8_t e = take();            // і номер видають ще раз
    printf("d=%u e=%u  → два зʼєднання на каналі %u\n",
           (unsigned)d, (unsigned)e, (unsigned)d);

    for (int i = 0; i < 13; ++i) { (void)take(); }   // беремо й «забуваємо» повернути
    printf("після витоку маска=0x%04X  вільних=%d\n", (unsigned)g_used, freeCount());
    printf("наступна видача дає %u — це 0xFF, каналів більше нема\n", (unsigned)take());
    return 0;
}
```

Вивід:

```
a=1 b=2 c=1  маска=0x0007  вільних=13
d=1 e=1  → два зʼєднання на каналі 1
після витоку маска=0xFFFF  вільних=0
наступна видача дає 255 — це 0xFF, каналів більше нема
```

Другий рядок і є та сама аварія, якої не помітить ніхто: маска в цю мить абсолютно коректна, біт стоїть, ніякої суперечності в ній нема. Помилка сталася не в розподільнику, а в тому, хто вважав себе власником номера, уже ним не бувши. Тому справжній захист від подвійного звільнення в QGroundControl стоїть не в масці, а в одному рядку, який стирає номер із того, хто його щойно віддав.
