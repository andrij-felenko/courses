У проєкті на двадцять вихідних файлів компіляція та лінкування вимагають виконання приблизно тридцяти окремих команд. Якщо записати їх у звичайний лінійний скрипт оболонки, вони виконуватимуться одна за одною строго в зазначеному порядку. Проте на восьмиядерному процесорі послідовне виконання триватиме сорок секунд замість п'яти, бо сім ядер простоюватимуть. Якщо ж запустити всі тридцять команд одночасно у фоновому режимі, процес лінкування негайно завершиться аварією з помилкою «файл не знайдено», оскільки спробує зібрати фінальний бінарник до того, як компілятори встигнуть створити хоча б один об'єктний файл.

Лінійний список приховує справжню структуру взаємозв'язків між файлами. Він нав'язує штучний строгий порядок там, де його немає (компіляція `math.cpp` та `network.cpp` ніяк не залежать одна від одної), і водночас не фіксує суттєвих обмежень, які не можна порушувати (компіляція `parser.cpp` не може початися до завершення генерації `parser.h` утилітою Bison).

Щоб ефективно завантажити всі наявні процесорні ядра і водночас гарантувати цілісність результату, системі збірки потрібна модель, яка виражає причинно-наслідкові зв'язки у чистому вигляді. Такою моделлю є орієнтований ациклічний граф.

## Від локальних декларацій до орієнтованого графа

Система збірки не вимагає від розробника будувати глобальну карту всього проєкту вручну. Натомість вона збирає її з множини локальних правил виду: «артефакт `A` створюється з файлів `B` і `C` командою `K`».

Кожен файл у такій системі стає вершиною, а кожна вимога передування — напрямленим зв'язком. Якщо зобразити цей зв'язок стрілкою від вхідного ресурсу до кінцевого продукту (`B → A` та `C → A`), ми отримуємо орієнтований граф (гр. *gráphō* — пишу, креслю). Орієнтованим його називають тому, що залежність принципово асиметрична: виконуваний файл програми потребує наявності скомпільованого модуля, але модуль не залежить від того, куди саме його згодом приєднає лінкер.

У такому графі відсутність шляху між двома вершинами означає повну незалежність. Якщо між вершиною `math.o` та вершиною `network.o` немає ланцюжка стрілок у жодному напрямку, система збірки отримує математичний доказ: ці дві задачі можна виконувати в будь-якій послідовності або одночасно на різних обчислювальних ядрах. Паралелізм збірки виникає не зі спеціальних прапорців, а безпосередньо з топологічної структури зв'язків.

Водночас наявність стрілки `A → B` накладає жорстке часове обмеження: момент завершення задачі `A` повинен строго передувати моменту запуску задачі `B`:

```
t_start(B) ≥ t_finish(A)      [інваріант коректності виконання залежності]
```

Якщо це правило виконується для кожного ребра графа, то порядок виконання гарантовано приведе до коректного результату без гонок за ресурси чи передчасних звернень до нестворених файлів.

## Анатомія графа збірки: природа вузлів

У реальних системах збірки вершини графа представляють не просто абстрактні імена, а фізичні або логічні сутності з чітко розмежованими обов'язками.

```
       [ config.h.in ]              [ engine.cpp ]    [ engine.h ]    [ main.cpp ]
              │                            │               │               │
       (конфігурація)                      │         ┌─────┴──────┐        │
              ▼                            ▼         ▼            ▼        ▼
        [ config.h ] ──────────────► [ engine.o ] ◄──┘            └──► [ main.o ]
     (згенерований файл)                   │                               │
                                           └───────────────┬───────────────┘
                                                           ▼
                                                        [ app ]  (бінарник)
                                                           │
                                                           ▼ (phony)
                                                        [ all ]
```

![Анатомія графа збірки: типи вузлів та характер залежностей](/reference/build-systems/fundamentals/dependency-graph/img/dag-structure.svg)
*Анатомія графа збірки: джерела утворюють вхідні листки, команди породжують проміжні об'єкти та бінарники, а фіктивні вузли агрегують підграфи цілей.*

За своєю поведінкою та життєвим циклом вузли поділяються на чотири виразні класи:

1. **Первинні джерела (Source Leaves):** вихідні тексти програм (`.cpp`, `.c`), рукописні заголовки (`.h`), конфігураційні шаблони (`config.h.in`), ресурси та графічні файли. Це вхідні вершини графа. У них немає вхідних ребер від інших задач збірки (`in-degree = 0` у термінах потоку даних). Їхній вміст змінює виключно людина або система контролю версій.
2. **Згенеровані проміжні файли (Generated Intermediate Artifacts):** файли вихідного коду, утворені парсерами (Bison, Flex), генераторами серіалізації (Protobuf, FlatBuffers) або утилітами конфігурації. Такий вузол є одночасно і результатом попереднього кроку, і входом для наступного: він має вхідні ребра від генератора та вихідні ребра до транслятора.
3. **Кінцеві бінарні артефакти (Sink Targets):** об'єктні файли (`.o`), статичні бібліотеки (`.a`), динамічні бібліотеки (`.so`, `.dll`) та виконувані файли. Вони утворюють проміжні або фінальні шари збірки.
4. **Фіктивні вузли (Phony / Pseudo-targets):** логічні цілі, яким не відповідає жоден реальний файл на диску (`all`, `clean`, `test`, `install`, `check`). Їхнє єдине призначення — об'єднувати інші цілі під зручним іменем або запускати команди з побічними ефектами.

Фіктивні вузли несуть у собі підступну пастку, пов'язану з перевіркою актуальності. Класичні системи збірки на зразок Make визначають необхідність роботи за наявністю файлу та його часовою позначкою. Якщо розробник оголосить ціль `clean` у Make-файлі, але забуде помітити її спеціальною директивою `.PHONY: clean`, то збірка працюватиме справно рівно доти, доки хтось випадково не створить у кореневому каталозі проєкту файл або теку з назвою `clean`. Щойно такий файл з'явиться на диску, Make виявить, що ціль `clean` уже існує і не має вхідних залежностей, а отже, видасть повідомлення `make: 'clean' is up to date.` і відмовиться видаляти скомпільовані об'єкти.

У сучасних низькорівневих рушіях на зразок Ninja фіктивність виражається явно через вбудоване правило `phony`:

```ninja
build clean: phony
build all: phony app unit_tests
```

У такій моделі рушій знає на рівні графа, що вузол не виробляє фізичного артефакту, і не намагається шукати його часову позначку у файловій системі.

## Анатомія ребер: типи залежностей

Зв'язки між вузлами в системі збірки несуть різне смислове навантаження. Залежно від того, як саме один файл впливає на інший, системи збірки виділяють три принципово різні категорії ребер.

### 1. Явні залежності за даними (Explicit Dependencies)

Це прямі вхідні файли, шляхи до яких явно передаються в командному рядку компілятора чи лінкера. Наприклад, у правилі `cc -c main.c -o main.o` файл `main.c` є явним входом. Якщо змінити ім'я чи вміст `main.c`, команда трансляції мусить виконатися повторно, а старий `main.o` вважається недійсним.

### 2. Неявні заголовочні залежності (Implicit Dependencies)

Під час компіляції `main.c` препроцесор розгортає директиви `#include "config.h"` та `#include "engine.h"`. Сам рядок команди компіляції не містить згадки про ці заголовки, але їхній байтовий вміст стає невіддільною частиною одиниці трансляції.

Якщо розробник виправляє сигнатуру функції в `engine.h`, об'єктний файл `main.o` повинен бути повністю перекомпільований, хоча сам `main.c` не змінювався. Неявні залежності утворюють ребра в графі, які безпосередньо впливають на актуальність цілі, але не передаються як позиційні аргументи в командний рядок збірки.

### 3. Залежності за порядком (Order-Only Dependencies)

Це специфічний вид ребер, у якому зв'язок визначає виключно черговість запуску задач, але не впливає на актуальність артефакту за часовими позначками.

Класичний приклад — створення каталогу для вихідних файлів перед початком збірки. Команда компіляції `cc -c src/a.c -o build/obj/a.o` завершиться аварією, якщо тека `build/obj/` ще не створена операційною системою. Якщо зв'язати `a.o` зі створенням теки `build/obj/` звичайним ребром даних, виникне неприємний побічний ефект: операційні системи оновлюють часову позначку каталогу щоразу, коли всередині нього створюється або видаляється будь-який файл. Отже, щойно перший потік скомпілює `a.o` всередині `build/obj/`, каталог оновить свій час модифікації, ставши новішим за всі інші заплановані об'єктні файли, що призведе до повторного безперервного перезбирання всього проєкту.

Залежність за порядком (у Make позначається вертикальною рискою `|`, у Ninja — подвійною рискою `||`) гарантує, що каталог буде створений до старту компіляції, але зміна часової позначки каталогу ніколи не зробить залежні об'єктні файли застарілими:

```ninja
rule compile_cpp
  command = clang++ -c $in -o $out

build build/obj: mkdir_rule

# build/obj буде створено до компіляції, але зміна часу каталогу не чіпає util.o
build build/obj/util.o: compile_cpp src/util.cpp || build/obj
```

Аналогічно залежності за порядком застосовують при генерації глобальних заголовків, коли десяткам модулів достатньо знати факт існування файлу на момент старту парсингу, а його змістовні зміни відстежуються через персональні dep-файли.

## Топологічне впорядкування: алгоритми планування

Щоб виконати роботи, описані графом, система збірки мусить знайти такий лінійний порядок вершин `v₁, v₂, ..., vₙ`, у якому для будь-якого орієнтованого ребра `(u, v)` вершина `u` стоїть строго раніше за `v`. Ця операція називається **топологічним сортуванням** (гр. *tópos* — місце + *lógos* — вчення).

```
Вхідний граф:            [A.c] ────► [A.o] ───┐
                         [B.c] ────► [B.o] ───┼──► [app]
                         [C.h] ────► [A.o]    │
                               └────► [B.o] ───┘

Можливий лінійний порядок (послідовний):
  1. C.h  ──►  2. A.c  ──►  3. B.c  ──►  4. A.o  ──►  5. B.o  ──►  6. app

Шари для паралельного виконання (хвилі):
  Хвиля 0: { C.h, A.c, B.c }       (3 задачі паралельно)
  Хвиля 1: { A.o, B.o }            (2 задачі паралельно після завершення хвилі 0)
  Хвиля 2: { app }                 (1 задача після завершення хвилі 1)
```

В інженерній практиці систем збірки використовуються два класичних алгоритми з принципово різною логікою обходу.

### 1. Алгоритм Кана (Arthur B. Kahn, 1962) — основа паралельних диспетчерів

Алгоритм Кана працює за принципом відстеження вхідних степенів (`in-degree` — кількість невиконаних передумов, на які очікує вершина).

Механізм складається з чотирьох кроків:
1. Для кожного вузла графа обчислюється початковий лічильник `in_degree[u]`.
2. Усі вершини з `in_degree[u] == 0` (джерела даних, які ні на кого не чекають) поміщаються в чергу готових до виконання задач (`Ready Queue`).
3. Поки черга не порожня, планувальник вилучає задачу `u`, призначає її вільному процесорному потоку, а після її завершення зменшує `in_degree[v]` на одиницю для всіх прямих нащадків `v`.
4. Якщо після декременту в якогось нащадка `in_degree[v]` стає рівним нулю, це означає, що всі його передумови готові: вузол `v` негайно додається в `Ready Queue`.

![Алгоритм Кана як двигун планувальника паралельної збірки](/reference/build-systems/fundamentals/dependency-graph/img/topological-kahn.svg)
*Алгоритм Кана у динаміці: лічильники передумов зменшуються в міру завершення робіт, відкриваючи доступ до нових паралельних шарів графа.*

Перевага алгоритму Кана полягає в тому, що він природно трансформується в багатопотоковий планувальник реального часу. Черга `Ready Queue` не потребує повного попереднього розгортання всього графа: вона наповнюється задачами у процесі збірки в міру того, як воркери завершують попередні етапи.

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>

#define MAX_NODES 64

typedef struct {
    int count;
    int edges[MAX_NODES][MAX_NODES];
    int in_degree[MAX_NODES];
} BuildGraph;

void graph_init(BuildGraph* g, int count) {
    g->count = count;
    for (int i = 0; i < count; i++) {
        g->in_degree[i] = 0;
        for (int j = 0; j < count; j++) {
            g->edges[i][j] = 0;
        }
    }
}

void graph_add_edge(BuildGraph* g, int from, int to) {
    g->edges[from][to] = 1;
    g->in_degree[to]++;
}

bool run_kahn_schedule(const BuildGraph* g, int* order_out) {
    int temp_in_degree[MAX_NODES];
    int queue[MAX_NODES];
    int head = 0, tail = 0;
    int processed = 0;

    for (int i = 0; i < g->count; i++) {
        temp_in_degree[i] = g->in_degree[i];
        if (temp_in_degree[i] == 0) {
            queue[tail++] = i;
        }
    }

    while (head < tail) {
        int curr = queue[head++];
        order_out[processed++] = curr;

        for (int next = 0; next < g->count; next++) {
            if (g->edges[curr][next]) {
                temp_in_degree[next]--;
                if (temp_in_degree[next] == 0) {
                    queue[tail++] = next;
                }
            }
        }
    }

    return processed == g->count;
}
```
```cpp
#include <vector>
#include <queue>
#include <optional>
#include <cstddef>

class BuildGraph {
public:
    explicit BuildGraph(std::size_t node_count)
        : adj_(node_count), in_degree_(node_count, 0) {}

    void add_dependency(std::size_t from_prereq, std::size_t to_target) {
        adj_[from_prereq].push_back(to_target);
        ++in_degree_[to_target];
    }

    [[nodiscard]] std::optional<std::vector<std::size_t>> compute_schedule() const {
        std::vector<std::size_t> degrees = in_degree_;
        std::queue<std::size_t> ready_queue;
        std::vector<std::size_t> linear_order;
        linear_order.reserve(adj_.size());

        for (std::size_t i = 0; i < degrees.size(); ++i) {
            if (degrees[i] == 0) {
                ready_queue.push(i);
            }
        }

        while (!ready_queue.empty()) {
            std::size_t current = ready_queue.front();
            ready_queue.pop();
            linear_order.push_back(current);

            for (std::size_t dependent : adj_[current]) {
                if (--degrees[dependent] == 0) {
                    ready_queue.push(dependent);
                }
            }
        }

        if (linear_order.size() != adj_.size()) {
            return std::nullopt; // Виявлено цикл
        }

        return linear_order;
    }

private:
    std::vector<std::vector<std::size_t>> adj_;
    std::vector<std::size_t> in_degree_;
};
```

### 2. Пошук у глибину (DFS) з трьома кольорами — модель зворотного запиту

Класичний Make реалізує іншу філософію — *pull-модель* (запит від кінцевої цілі). Коли користувач викликає `make app`, система починає обхід від цілі `app`, рекурсивно вимагаючи актуалізації всіх її передумов через пошук у глибину (DFS).

Щоб правильно побудувати порядок і не зациклитися, DFS використовує розфарбування вершин у три кольори:
- **Білий (White / 0):** вершина ще не розглядалася.
- **Сірий (Gray / 1):** вершина знаходиться в поточному стеку викликів (триває обробка її передумов).
- **Чорний (Black / 2):** усі передумови вершини успішно перевірені та виконані, вершину додано у вихідний список.

Під час обходу порядок додавання у вихідний список є *post-order* (додавання на зворотному ході рекурсії). Обернений post-order або пряме виконання на виході з рекурсії якраз і дає валідну топологічну послідовність дій.

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>

#define MAX_DFS_NODES 64
#define COLOR_WHITE 0
#define COLOR_GRAY  1
#define COLOR_BLACK 2

typedef struct {
    int count;
    int edges[MAX_DFS_NODES][MAX_DFS_NODES];
    int color[MAX_DFS_NODES];
} DfsGraph;

void dfs_graph_init(DfsGraph* g, int count) {
    g->count = count;
    for (int i = 0; i < count; i++) {
        g->color[i] = COLOR_WHITE;
        for (int j = 0; j < count; j++) {
            g->edges[i][j] = 0;
        }
    }
}

void dfs_add_edge(DfsGraph* g, int from, int to) {
    g->edges[from][to] = 1;
}

static bool dfs_visit(DfsGraph* g, int u, int* order_out, int* order_idx) {
    g->color[u] = COLOR_GRAY;

    for (int v = 0; v < g->count; v++) {
        if (g->edges[u][v]) {
            if (g->color[v] == COLOR_GRAY) {
                return false; // Знайдено back-edge (цикл)
            }
            if (g->color[v] == COLOR_WHITE) {
                if (!dfs_visit(g, v, order_out, order_idx)) {
                    return false;
                }
            }
        }
    }

    g->color[u] = COLOR_BLACK;
    order_out[(*order_idx)++] = u; // Додавання на зворотному ході (post-order)
    return true;
}

bool run_dfs_toposort(DfsGraph* g, int* order_out) {
    int order_idx = 0;
    for (int i = 0; i < g->count; i++) {
        if (g->color[i] == COLOR_WHITE) {
            if (!dfs_visit(g, i, order_out, &order_idx)) {
                return false; // Виявлено цикл
            }
        }
    }
    return true;
}
```
```cpp
#include <vector>
#include <optional>
#include <cstddef>
#include <cstdint>

enum class NodeColor : std::uint8_t {
    White,
    Gray,
    Black
};

class DfsBuildGraph {
public:
    explicit DfsBuildGraph(std::size_t node_count)
        : adj_(node_count) {}

    void add_dependency(std::size_t from_prereq, std::size_t to_target) {
        adj_[from_prereq].push_back(to_target);
    }

    [[nodiscard]] std::optional<std::vector<std::size_t>> compute_toposort() const {
        std::vector<NodeColor> colors(adj_.size(), NodeColor::White);
        std::vector<std::size_t> post_order;
        post_order.reserve(adj_.size());

        for (std::size_t i = 0; i < adj_.size(); ++i) {
            if (colors[i] == NodeColor::White) {
                if (!visit_node(i, colors, post_order)) {
                    return std::nullopt; // Знайдено цикл
                }
            }
        }

        return post_order;
    }

private:
    bool visit_node(std::size_t u, std::vector<NodeColor>& colors,
                    std::vector<std::size_t>& post_order) const {
        colors[u] = NodeColor::Gray;

        for (std::size_t v : adj_[u]) {
            if (colors[v] == NodeColor::Gray) {
                return false; // Ребро веде на предка в стеку — цикл
            }
            if (colors[v] == NodeColor::White) {
                if (!visit_node(v, colors, post_order)) {
                    return false;
                }
            }
        }

        colors[u] = NodeColor::Black;
        post_order.push_back(u);
        return true;
    }

    std::vector<std::vector<std::size_t>> adj_;
};
```

| **Паралелізм** | Ідеально підходить для динамічного диспетчера | Вимагає додаткової синхронізації піддерев |
| **Використання** | Ninja, Bazel, сучасні паралельні рушії | Класичний GNU Make |

## Дворівнева ієрархія графів: від високорівневих цілей до файлового DAG

Сучасна розробка майже ніколи не описує низькорівневі файлові правила безпосередньо в термінах окремих об'єктних файлів. Замість цього такі мета-системи, як CMake, Meson або Premake, вводять абстракцію **графа цілей (Target Graph)**.

```
1. Високорівневий граф цілей (CMake / Meson):
   [ target: core_lib ] ──(PUBLIC залежність)──► [ target: app_binary ]
   Властивості: include_directories, compile_definitions, compile_options

2. Трансляція та розгортання властивостей:
   app_binary автоматично успадковує -Iinclude/core та -DUSE_CORE_V2

3. Низькорівневий файловий DAG збірки (Ninja / Make):
   src/core.cpp ──► build/core.o ──┐
   src/main.cpp ──► build/main.o ──┼──► build/app_binary
   include/core.h ─(неявно)────────┘
```

У цій моделі існують два різних шари абстракції:
- **Граф цілей (Target-Level Graph):** вузлами є логічні модулі (бібліотеки, плагіни, програми), а ребрами — вимоги вжитку (`target_link_libraries`, `PUBLIC`, `PRIVATE`, `INTERFACE`). Цей граф задає поширення транзитивних властивостей: прапорців компілятора, шляхів до заголовочних файлів і макросів компілятора.
- **Файловий граф виконання (Action/File DAG):** плоский низькорівневий граф, де вузлами є виключно конкретні файли на диску, а ребрами — команди трансформації.

Генератор збірки (наприклад, CMake) виконує операцію *сплощення* (lowering): він аналізує граф цілей, протягує всі успадковані властивості вздовж стрілок і транслює одну логічну бібліотеку на десятки конкретних правил компіляції файлів у форматі `build.ninja`. Користувацькі команди генерації (`add_custom_command`) утворюють містки між цими двома світами, зв'язуючи файлові входи та виходи з високорівневими таргетами.

## Циклічні залежності: неможливість розв'язку та діагностика

Граф залежностей має право називатися системою збірки лише доти, доки він залишається **ациклічним** (гр. *a-* — без, *kýklos* — коло, круг). Якщо у графі виникає циклічний шлях `A → B → C → A`, задача впорядкування перестає мати фізичний і математичний зміст.

У циклі жодна вершина не може бути скомпільована першою, бо кожна вимагає попереднього завершення свого попередника:

```
t_start(A) ≥ t_finish(C) ≥ t_finish(B) ≥ t_finish(A)
⟹ t_start(A) ≥ t_start(A) + duration(A) + duration(B) + duration(C)
```

Оскільки тривалість кожної реальної команди `duration > 0`, ця нерівність є строгою суперечністю (`t ≥ t + Δt`, де `Δt > 0`).

### Звідки беруться цикли у реальних проєктах

Розробники рідко створюють циклічні залежності між файлами свідомо. Найчастіше цикли виникають як результат складних взаємодій між кодогенерацією та бібліотеками:

1. **Зациклена кодогенерація:** допоміжна утиліта генерації коду `codegen` зібрана з використанням внутрішньої бібліотеки `libcore.a`. Згодом один із модулів `libcore.a` починає використовувати структуру даних, яку повинен генерувати інструмент `codegen`. Утворюється замкнене коло: щоб скомпілювати `codegen`, потрібна готова `libcore.a`, а щоб скомпілювати `libcore.a`, потрібно запустити `codegen`.
2. **Кругові залежності заголовків:** файл `user.h` включає `account.h`, а `account.h` включає `user.h`. Якщо система збірки генерує ці заголовки автоматично або сканує їх як окремі вузли графа, рушій фіксує цикл передування.
3. **Кругові статичні бібліотеки на етапі лінкування:** модуль `libA.a` звертається до функцій із `libB.a`, а `libB.a` викликає зворотні виклики (callbacks) із `libA.a`. Однопрохідні лінкери утиліти `ld` вимагають або повторення бібліотек у рядку виклику (`-lA -lB -lA`), або явного використання маркерів групи (`--start-group -lA -lB --end-group`), що знімає вимогу ациклічності на рівні самого компонувальника.

### Механізм виявлення та формування діагностики

Система збірки повинна не просто виявити цикл і аварійно зупинитися, а надати розробнику вичерпний ланцюжок, який утворив зациклення.

В алгоритмі Кана виявлення циклу відбувається за лічильником: якщо після повного спустошення `Ready Queue` кількість оброблених вершин `processed < total_nodes`, це слугує неспростовним доказом того, що серед решти вершин є щонайменше один цикл (усі вони мають залишковий `in_degree > 0` і вічно очікують одна на одну).

У DFS-обході цикл виявляється ще простіше і точніше: якщо під час аналізу ребер вершини `u` знайдено ребро `(u, v)`, де вершина `v` уже пофарбована в **сірий колір**, це означає, що ми натрапили на зворотне ребро (*back-edge*), яке веде на предка в поточному стеку викликів.

Відновлення шляху циклу здійснюється розгортанням стека викликів від поточної вершини до знайденого сірого предка:

```
ninja: error: dependency cycle:
  src/core/parser.cpp.o ->
  include/generated/tokens.h ->
  tools/token_gen ->
  lib/libcore.a ->
  src/core/parser.cpp.o
```

Таке повідомлення точно вказує архітектурний дефект: зв'язок `tools/token_gen` із бібліотекою `libcore.a` був помилковим і вимагає розділення монолітної бібліотеки на дві незалежні частини.

## Паралелізм збірки, критичний шлях та планування робіт

Можливість розпаралелювання робіт обмежується не лише кількістю ядер процесора, але й формою самого графа.

Для математичного аналізу часу збірки використовують дві фундаментальні величини:
1. **Обсяг роботи (Work, `T₁`):** сумарний час, необхідний для виконання всіх задач графа на одному обчислювальному ядрі (сума ваг усіх вершин `∑ duration(v)`).
2. **Критичний шлях / Довжина спану (Span, `T∞`):** найдовший за часом зважений шлях від будь-якого вхідного джерела до фінального артефакту. Навіть якщо надати системі збірки нескінченну кількість процесорів (`p = ∞`), збірка не зможе завершитися швидше, ніж за час `T∞`, оскільки операції на критичному шляху принципово неможливо виконувати одночасно через прямі залежності між ними.

```
Критичний шлях (Span = 8 + 16 + 6 = 30 с):
  [ gen_tables.py (8 с) ] ──► [ heavy_parser.cpp (16 с) ] ──► [ link app (6 с) ]

Паралельні другорядні гілки:
  [ gen_tables.py (8 с) ] ──► [ util_math.cpp (3 с) ] ──► [ net_client.cpp (4 с) ] ──► [ link app ]
```

![Критичний шлях зваженого графа та вплив евристик черги на хвіст збірки](/reference/build-systems/fundamentals/dependency-graph/img/critical-path-span.svg)
*Критичний шлях задає абсолютну нижню межу тривалості збірки: запізнілий старт найважчої задачі утворює однопотоковий хвіст, тоді як пріоритизація глибини насичує ядра.*

Згідно з лемою Брента (Richard P. Brent, 1974) та оцінками Грема, час виконання графа на `p` паралельних потоках за жадібного планування затиснутий у строгі рамки:

```
T_p ≥ max(T₁ ÷ p, T∞)                 [теоретична нижня межа]
T_p ≤ T∞ + (T₁ − T∞) ÷ p              [верхня межа жадібного планувальника]
```

### Проблема «хвоста збірки» (Build Tail) та пріоритетне планування

Якщо планувальник вибирає задачі з `Ready Queue` за звичайним правилом FIFO (First-In, First-Out), виникає дефект під назвою **хвіст збірки**.

Уявімо проєкт, де є сто дрібних файлів по 0.5 секунди компіляції і один гігантський модуль із шаблонами на 30 секунд компіляції. Якщо планувальник спочатку розбере сотню дрібних файлів, то перші 10 секунд усі 16 ядер працюватимуть на повну потужність. Потім дрібні задачі вичерпаються, і система почне компілювати гігантський модуль. Наступні 30 секунд п'ятнадцять ядер повністю байдикуватимуть, очікуючи на завершення одного важкого потоку перед фінальним лінкуванням.

Щоб запобігти цьому, планувальники (зокрема Ninja) використовують **пріоритезацію за критичною глибиною**:
- Для кожного вузла графа обчислюється його *вага піддерева* — сумарний час або максимальна кількість залежних нащадків, що чекають на результат цього вузла.
- Черга готових задач стає чергою з пріоритетом (`Priority Queue`).
- Важкі задачі, які стоять на початку довгих ланцюжків залежностей, запускаються першими в черзі, щоб дати змогу паралельним процесорам розігнати довгі гілки заздалегідь.

### Обмеження матеріальних ресурсів: пули пам'яті (Resource Pools)

Граф залежностей виражає лише залежності за даними. Проте операційна система має обмежені апаратні ресурси, найкритичнішим із яких є оперативна пам'ять (RAM).

Якщо запустити збірку великого C++ проєкту на машині з 32 ядрами і 32 ГБ пам'яті з прапорцем `-j32`, компіляція легких файлів пройде миттєво. Але якщо в проєкті є чотири важких виконуваних бінарники, які збираються з генерацією повної відлагоджувальної інформації та увімкненою оптимізацією часу лінкування (LTO), кожен процес `clang++` під час компонування може спожити по 12–16 ГБ пам'яті. Запуск 4 таких лінкувань паралельно потребуватиме понад 50 ГБ RAM, що негайно зіб'є систему в дисковий swap storm або викличе аварійне завершення через механізм ядра Linux OOM-Killer.

Для вирішення цієї проблеми Ninja ввів концепцію **пулів ресурсів (Pools)**:

```ninja
# Оголошуємо пул із максимальною глибиною 2 слоти
pool link_pool
  depth = 2

rule link_heavy
  command = clang++ -flto $in -o $out
  pool = link_pool

# Усі інші задачі можуть виконуватися з -j32, але link_heavy — не більше 2 одночасно
build app1: link_heavy obj1.o
build app2: link_heavy obj2.o
build app3: link_heavy obj3.o
```

Пули створюють додаткові штучні семафорні обмеження в планувальнику, запобігаючи перевантаженню апаратних ресурсів машини.

### Make Jobserver: координація потоків між підпроцесами

У складних ієрархічних проєктах головний процес `make` нерідко викликає вкладені процеси `make -C subdir`. Якщо кожен із них спробує самостійно запустити `make -j8`, загальна кількість паралельних процесів у системі почне лавиноподібно множитися, паралізуючи операційну систему.

Для глобального контролю паралелізму GNU Make розробив механізм **Jobserver**:
- Головний процес створює неіменований UNIX-пайп (pipe) і записує туди `N - 1` однобайтових токенів (де `N` — аргумент прапорця `-jN`).
- Номери файлових дескрипторів передаються всім дочірнім процесам через змінну оточення `MAKEFLAGS=--jobserver-auth=3,4` (або через іменовані канали `fifo` у GNU Make 4.4+).
- Будь-який підпроцес `make`, перш ніж запустити чергову команду збірки, зобов'язаний прочитати один байт із пайпу. Якщо пайп порожній, процес блокується операційною системою у системному виклику `read()`, очікуючи звільнення слота.
- Щойно команда завершується, процес записує токен назад у пайп, розблоковуючи іншого охочого воркера.

У середовищі Windows аналогічний контроль реалізується за допомогою іменованих семафорів (`Semaphore Objects`) або `Job Objects`, що забезпечує централізований динамічний ліміт паралелізму для довільно глибокого дерева вкладених збірок.

## Динамічне розширення графа: вирішення проблеми «курки й яйця»

Найскладніша практична проблема графа збірки полягає в тому, що повний статичний граф неможливо знати заздалегідь до початку збірки.

Для компіляції файлу `main.cpp` необхідно знати список усіх включених до нього заголовків (`config.h`, `engine.h`, `math.h`), щоб побудувати ребра графа і стежити за їхніми змінами. Але щоб дізнатися цей список, необхідно запустити C-препроцесор над файлом `main.cpp`. А щоб знати, чи треба взагалі запускати препроцесор та компілятор, система збірки спочатку повинна з'ясувати, чи не застаріли якісь із включених файлів.

Утворюється класичне замкнене коло: залежності невідомі без запуску компіляції, а компіляція не може бути коректно запланована без знання залежностей.

```
1. Статичний опис (CMake / Ninja):
   [ engine.cpp ] ─────────────────────────► [ engine.o ]

2. Компілятор під час трансляції вивантажує файл залежностей (engine.d):
   engine.o: engine.cpp engine.h config.h /usr/include/math.h

3. Рушій збірки зчитує depfile і динамічно мутує граф:
   [ engine.cpp ] ─────────────────────────► [ engine.o ]
   [ engine.h ]   ────── (динамічне ребро) ──► [ engine.o ]
   [ config.h ]   ────── (динамічне ребро) ──► [ engine.o ]
```

![Динамічне збагачення графа залежностей через вивантаження depfile](/reference/build-systems/fundamentals/dependency-graph/img/depfile-dynamic-mutation.svg)
*Двоетапне життя залежностей: компілятор фіксує включені заголовки побічним ефектом трансляції, а рушій збірки динамічно добудовує граф для наступних прогонів.*

Цю проблему вирішує технологія **динамічних файлів залежностей (Depfiles)**.

### Технологія Depfile (`-MD -MF`, `-MP` та `.ninja_deps`)

Сучасні компілятори (GCC, Clang, MSVC) уміють генерувати список реально розгорнутих заголовків одночасно з генерацією машинного коду за один прохід:

```sh
clang++ -MD -MF build/engine.d -MP -c src/engine.cpp -o build/engine.o
```

У результаті на диску поруч із `engine.o` з'являється текстовий файл `engine.d` у синтаксисі Make-правила:

```makefile
build/engine.o: src/engine.cpp include/engine.h include/config.h \
  /usr/include/stdio.h /usr/include/stdlib.h

include/engine.h:
include/config.h:
/usr/include/stdio.h:
/usr/include/stdlib.h:
```

Прапорець `-MP` розв'язує підступну класичну проблему систем збірки: якщо розробник видаляє або перейменовує заголовок `old.h` і прибирає `#include "old.h"` із вихідного коду, старий файл `engine.d` все ще містить ребро `old.h → engine.o`. Під час наступного запуску система збірки намагається знайти передумову `old.h`, бачить, що файлу на диску більше немає і жодне правило не вміє його створювати, і перериває роботу з фатальною помилкою `No rule to make target 'old.h', needed by 'engine.o'`. Додавання порожніх фіктивних правил для кожного заголовка (що й робить `-MP`) дозволяє системі збірки вважати видалений файл застарілою передумовою, спокійно запустити компіляцію і перезаписати свіжий `engine.d`.

Рушій збірки працює за двоетапною моделлю:
1. **Перший запуск (чиста збірка):** граф містить лише базові явні ребра (`engine.cpp → engine.o`). Компілятор виконує трансляцію і паралельно створює `engine.d`.
2. **Наступні запуски (інкрементальна збірка):** рушій збірки перед формуванням топологічного порядку зчитує збережені `engine.d` файли і **динамічно вбудовує нові ребра** в існуючий граф у пам'яті.

Ранні системи збірки зберігали тисячі окремих файлів `.d` на диску, що створювало колосальне навантаження на файлову систему під час стартового опитування. Ninja зробив технологічний стрибок: він зчитує `.d`-файли одразу після завершення кожної команди, записує їхній розібраний бінарний вміст у єдиний монолітний лог-файл `.ninja_deps` і миттєво видаляє текстовий `.d`-файл із диска. На старті наступної збірки Ninja за мілісекунди відображає `.ninja_deps` у пам'ять через системний виклик `mmap()`, відновлюючи мільйони динамічних ребер графа майже без затримок.

### Динамічні залежності нового покоління: Ninja Dyndep (C++20 Modules та Fortran)

З появою модулів C++20 (`import foo;` замість `#include "foo.h"`) проблема курки й яйця вийшла на новий рівень.

У модульній системі модуль `A` не просто використовує інтерфейс модуля `B` — він вимагає, щоб компілятор попередньо скомпілював модуль `B` у бінарний інтерфейсний файл (BMI — *Binary Module Interface*, наприклад `.pcm` або `.ifc`). Тобто порядок компіляції самих `.cpp` файлів більше не довільний: якщо `a.cpp` імпортує `b.cpp`, то `b.cpp` зобов'язаний скомпілюватися раніше за `a.cpp`.

Оскільки сканувати весь код проєкту на етапі запуску генератора CMake занадто довго, Ninja реалізував механізм **Dyndep (Dynamic Dependencies)**:

```ninja
rule scan_cpp_modules
  command = clang-scan-deps -format=p1689 -- $in -o $out

rule compile_module
  command = clang++ -c $in -o $out

# 1. Скануємо залежності модуля
build build/main.dd: scan_cpp_modules src/main.cpp

# 2. Компілюємо з підключенням динамічного опису
build build/main.o: compile_module src/main.cpp || build/main.dd
  dyndep = build/main.dd
```

Під час збірки Ninja запускає швидку фазу сканування `scan_cpp_modules`. Згенерований файл `main.dd` містить вказівку: «для збірки `main.o` потрібен бінарний артефакт `math.pcm`». Ninja зупиняє просування по цій гілці, динамічно врізає нові ребра у робочий граф і перераховує топологічний порядок просто під час виконання, без повного перезапуску системи збірки.

## Порівняння моделей графа у сучасних інструментах

Різні системи збірки обирають різний рівень деталізації та методи управління графом.

| Система | Гранулярність вузла | Модель побудови графа | Механізм паралелізму | Робота з заголовками |
| :--- | :--- | :--- | :--- | :--- |
| **GNU Make** | Окремий файл / ціль | Декларативний текст (DFS обхід при запиті цілі) | Jobserver (токенізація через пайп) | Зовнішні `.d` файли через директиву `-include` |
| **Ninja** | Окремий файл / дія | Низькорівневий статичний DAG (Алгоритм Кана з пріоритетом) | Черга готових задач + Resource Pools | Бінарний лог `.ninja_deps` + механізм `dyndep` |
| **CMake** | Логічна ціль (Target: бібліотека/бінарник) | Мета-система: генерує DAG для Ninja/Make/VS | Делегується бекенду збірки | Генерує правила відстеження для бекенда |
| **Bazel** | Пакет / Дія (Hermetic Action) | Суворий герметичний DAG у пам'яті сервера | Вбудований асинхронний пул потоків | Сканування включень + ізоляція у sandbox |

Розуміння будови графа залежностей перетворює роботу інженера зі сліпого налаштування конфігураційних файлів на точний розрахунок. Правильно побудований ациклічний граф із чесно оголошеними явними та неявними ребрами гарантує максимальну швидкість паралельної збірки, відсутність паразитного перезбирання та повну повторюваність результату на будь-якій кількості обчислювальних ядер.
