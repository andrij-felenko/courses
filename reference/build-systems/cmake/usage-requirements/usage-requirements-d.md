Уявімо три модулі в типовому інженерному проєкті: бібліотеку цифрової обробки сигналів `dsp_math`, мережевий протокол `audio_stream` і кінцеву програму `player_app`. Бібліотека `dsp_math` містить складні векторні алгоритми, реалізовані у файлах `fft.cpp` та `filter.cpp`. Для внутрішніх потреб їй потрібні специфічні заголовки асемблерних оптимізацій з теки `src/internal/` та визначення макросу `-DFFT_ACCELERATION_AVX2`. Назовні ж вона віддає лаконічний заголовок `include/dsp/fft.h` із єдиною функцією `transform()`. Бібліотека `audio_stream` використовує цю функцію у своєму коді, але у власному відкритому заголовку `include/stream/receiver.h` оперує виключно стандартним потоком байтів, не згадуючи жодного математичного типу. Програма `player_app` викликає лише `audio_stream`.

Якщо налаштувати таку систему за старим звичаєм через команди каталогу на зразок `include_directories(src/internal)` та `add_definitions(-DFFT_ACCELERATION_AVX2)`, виникає системний збій. Шляхи до закритих заголовків і специфічні прапорці компілятора розливаються по всьому дереву збірки. Програма `player_app` раптом отримує доступ до `fft_internal.h`, випадково починає залежати від деталей реалізації чужого модуля, а зміна одного внутрішнього коментаря в математичній бібліотеці спричиняє повну перекомпіляцію сотень файлів клієнтського застосунку. Що гірше: прапорець `-DFFT_ACCELERATION_AVX2` змінює вирівнювання структур у сторонніх заголовках, призводячи до розбіжності бінарного інтерфейсу (ABI — англ. *Application Binary Interface*) та падінь під час виконання, які неможливо відстежити на етапі компіляції.

Якщо ж навпаки спробувати ізолювати все вручну й забути передати шлях до публічного `include/dsp/`, модуль `audio_stream` взагалі не збереться, бо компілятор не знайде оголошення `transform()`. Постає потреба в точній, автоматизованій межі. Будь-який програмний компонент — це не просто набір вихідних файлів, що перетворюються на об'єктний архів. Це асиметричний двосторонній контракт: одна його частина описує те, що потрібно для створення самого компонента, а друга — те, що компонент вимагає від будь-кого, хто збирається ним скористатися. Ця друга частина в сучасній моделі збірки називається **вимогами вжитку** (англ. *usage requirements*).

## Анатомія вимог: внутрішня збірка та експортний інтерфейс

Щоб реалізувати цей контракт без використання глобальних змінних, CMake розділяє простір налаштувань кожної цілі на два незалежні набори властивостей. Перший набір керує компіляцією вихідних файлів самої цілі. Другий набір — властивості з префіксом `INTERFACE_` — ніяк не впливає на власну компіляцію, а натомість автоматично приєднується до параметрів компілятора кожного споживача, який приєднає цю ціль через команду `target_link_libraries`.

Для кожного аспекту процесу збірки існує пара властивостей:

* Каталоги пошуку заголовків: `INCLUDE_DIRECTORIES` для себе та `INTERFACE_INCLUDE_DIRECTORIES` для споживачів.
* Системні каталоги заголовків (без попереджень компілятора): `SYSTEM_INCLUDE_DIRECTORIES` та `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES`.
* Визначення макросів препроцесора: `COMPILE_DEFINITIONS` та `INTERFACE_COMPILE_DEFINITIONS`.
* Прапорці компілятора: `COMPILE_OPTIONS` та `INTERFACE_COMPILE_OPTIONS`.
* Вимоги до стандарту й можливостей мови: `COMPILE_FEATURES` та `INTERFACE_COMPILE_FEATURES`.
* Попередньо скомпільовані заголовки: `PRECOMPILE_HEADERS` та `INTERFACE_PRECOMPILE_HEADERS`.
* Вихідні файли, що передаються для компіляції: `SOURCES` та `INTERFACE_SOURCES`.
* Прапорці лінкера: `LINK_OPTIONS` та `INTERFACE_LINK_OPTIONS`.
* Каталоги пошуку бібліотек: `LINK_DIRECTORIES` та `INTERFACE_LINK_DIRECTORIES`.
* Ребра графа залежностей: `LINK_LIBRARIES` та `INTERFACE_LINK_LIBRARIES`.

Коли ми викликаємо команди налаштування цілі (`target_include_directories`, `target_compile_definitions`, `target_compile_options`, `target_compile_features`, `target_sources`, `target_link_options`, `target_link_directories`, `target_precompile_headers`), ми вказуємо одне з трьох ключових слів: `PRIVATE`, `INTERFACE` або `PUBLIC`. Ці слова не мають стосунку до модифікаторів доступу класів у C++, а виконують роль перемикача між двома половинами сховища властивостей.

![Розподіл властивостей цілі між власною збіркою та інтерфейсом споживача](/reference/build-systems/cmake/usage-requirements/img/public-private-interface.svg)
*Ключове слово визначає цільову властивість: PRIVATE пише лише у внутрішній список, INTERFACE — лише у зовнішній інтерфейс споживача, а PUBLIC наповнює обидва списки одночасно.*

Механізм розподілу діє суворо детерміновано:

1. **`PRIVATE`** спрямовує значення виключно до внутрішньої властивості (наприклад, `INCLUDE_DIRECTORIES`). Значення бере участь у компіляції файлів вихідного коду поточної цілі, але повністю невидиме для зовнішнього світу.
2. **`INTERFACE`** спрямовує значення виключно до властивості з префіксом `INTERFACE_` (наприклад, `INTERFACE_INCLUDE_DIRECTORIES`). Власні файли цілі не отримують цього параметра під час збірки; він зберігається як вимога для тих, хто підключатиме цю бібліотеку.
3. **`PUBLIC`** записує значення одночасно в обидві властивості. Параметр використовується для збірки самої цілі і автоматично експортується її споживачам.

Детальний перелік усіх сигнатур команд налаштування цілей і відповідних їм пар властивостей зібрано в окремому довіднику: [довідка команд вимог вжитку](book:build-systems/usage-requirements/api-usage-requirements.md).

## Семантика трьох рівнів на реальних прикладах

Розглянемо практичну поведінку кожного рівня на прикладі побудови бібліотеки обробки зображень `image_processor`.

### Рівень PRIVATE: деталі реалізації за зачиненими дверима

Бібліотеці `image_processor` для внутрішньої роботи потрібні допоміжні алгоритми з каталогу `src/simd_internal/` та стороння бібліотека розпакування `libpng`, до якої звертаються виключно файли реалізації `png_loader.cpp`. Відкритий заголовок `include/image.h` оперує виключно власним типом `ImageBuffer` і не містить жодного входження `#include <png.h>`.

```cmake
add_library(image_processor STATIC
    src/image.cpp
    src/png_loader.cpp
    src/simd_internal/sse_kernels.cpp
)

# Каталог із закритими заголовками бачить лише сама бібліотека
target_include_directories(image_processor PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/src/simd_internal
)

# Прапорець компілятора діє лише на файли image.cpp, png_loader.cpp тощо
target_compile_options(image_processor PRIVATE
    -Werror=uninitialized
)

# libpng лінкується всередину, але її заголовки не експортуються назовні
target_link_libraries(image_processor PRIVATE
    PNG::PNG
)
```

:::tabs
```c
/* include/image.h — чистий публічний інтерфейс (C) */
#ifndef IMAGE_H
#define IMAGE_H

#include <stddef.h>
#include <stdint.h>

typedef struct {
    uint32_t width;
    uint32_t height;
    uint8_t* pixels;
} ImageBuffer;

ImageBuffer* image_create(uint32_t w, uint32_t h);
void image_free(ImageBuffer* img);
int image_load_from_file(const char* path, ImageBuffer* out_img);

#endif
```
```cpp
// include/image.hpp — чистий публічний інтерфейс (C++)
#pragma once
#include <vector>
#include <cstdint>
#include <string_view>
#include <expected>

namespace img {

struct ImageBuffer {
    uint32_t width{0};
    uint32_t height{0};
    std::vector<uint8_t> pixels;
};

class Processor {
public:
    static std::expected<ImageBuffer, std::string> load_from_file(std::string_view path);
};

} // namespace img
```
:::

Чому тут критично використати саме `PRIVATE`: якщо позначити `PNG::PNG` або `-Werror=uninitialized` як `PUBLIC`, будь-який зовнішній застосунок, який підключить `image_processor`, буде примусово скомпільований із прапорцем зупинки на неініціалізованих змінних і отримає каталог заголовків `libpng` у свій шлях пошуку `#include`. Це створює паразитний зв'язок (англ. *accidental coupling*): сторонній код може випадково скомпілюватися з заголовком `png.h`, навіть не підозрюючи, що бере його не з системного пакета, а транзитивно через бібліотеку обробки зображень.

### Рівень PUBLIC: публічний інтерфейс і спільний контракт

Тепер припустимо, що публічний заголовок `include/image.hpp` містить метод, який повертає об'єкт матриці перетворення, визначений у бібліотеці `linear_math`:

:::tabs
```c
/* include/image_transform.h — тип Matrix3x3 є частиною API (C) */
#ifndef IMAGE_TRANSFORM_H
#define IMAGE_TRANSFORM_H

#include "image.h"
#include <math/matrix3x3.h>

void image_apply_transform(ImageBuffer* img, const Matrix3x3* matrix);

#endif
```
```cpp
// include/image_transform.hpp — тип Matrix3x3 є частиною API (C++)
#pragma once
#include "image.hpp"
#include <math/matrix3x3.hpp>

namespace img {

void apply_transform(ImageBuffer& img, const math::Matrix3x3& matrix);

} // namespace img
```
:::

Тепер клієнт бібліотеки `image_processor` не зможе навіть скомпілювати рядок `#include <image_transform.hpp>`, якщо йому недоступні заголовки з `linear_math`. Більше того, обидва модулі мусять мати спільний макрос `-DIMG_COLOR_DEPTH_16BIT`, який змінює розмір полів структури `ImageBuffer`.

```cmake
# Публічні заголовки потрібні і файлам реалізації, і споживачам
target_include_directories(image_processor PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>
)

# Макрос змінює ABI структури ImageBuffer — він має бути ідентичним скрізь
target_compile_definitions(image_processor PUBLIC
    IMG_COLOR_DEPTH_16BIT=1
)

# Оскільки тип Matrix3x3 присутній у відкритому заголовку, залежність має бути PUBLIC
target_link_libraries(image_processor PUBLIC
    linear_math
)
```

Завдяки `PUBLIC` відбуваються дві паралельні дії:
1. Під час збірки файлу `src/image.cpp` компілятор отримує прапорці `-I.../include`, `-DIMG_COLOR_DEPTH_16BIT=1` та шляхи до заголовків `linear_math`.
2. Коли виконуваний файл `app` пише `target_link_libraries(app PRIVATE image_processor)`, компілятор під час збірки `app/main.cpp` автоматично отримує ті самі прапорці `-I.../include`, `-DIMG_COLOR_DEPTH_16BIT=1` і заголовки `linear_math`.

### Рівень INTERFACE: чисті вимоги до споживача

Рівень `INTERFACE` використовується тоді, коли самій цілі параметр не потрібен (або коли в цілі взагалі немає власних скомпільованих бінарних файлів), але споживач зобов'язаний його мати.

Класичний приклад — бібліотека, що складається виключно із заголовків (англ. *header-only library*), або ціль-конфігурація, яка слугує носієм стандарту мови:

```cmake
# Створення інтерфейсної бібліотеки (не збирає жодного .o/.obj файлу)
add_library(fast_json INTERFACE)

# Споживач отримує шлях до заголовків
target_include_directories(fast_json INTERFACE
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>
)

# Споживач зобов'язаний збиратися у режимі C++20 або новішому
target_compile_features(fast_json INTERFACE
    cxx_std_20
)
```

Спроба викликати `target_include_directories(fast_json PRIVATE ...)` для інтерфейсної цілі спричинить фатальну помилку конфігурації CMake:
```
CMake Error at CMakeLists.txt:10 (target_include_directories):
  INTERFACE library can only be used with the INTERFACE keyword of
  target_include_directories
```
Ця помилка логічна: в інтерфейсної цілі немає файлів для компіляції, тому для неї не існує властивості `INCLUDE_DIRECTORIES`, куди ключове слово `PRIVATE` могло б записати значення.

## Транзитивність у графі залежностей (DAG)

Сучасний процес збірки формує напрямлений ациклічний граф (DAG — англ. *Directed Acyclic Graph*, від латинського *transitivus* — перехідний), у якому вершинами є цілі, а напрямленими ребрами — зв'язки, встановлені командою `target_link_libraries`.

Коли проєкт складається з довгого ланцюжка модулів, властивості поширюються цим графом відповідно до правил транзитивності:

```
[GUI App] ---> [Rendering Engine] ---> [Vulkan Wrapper] ---> [Vulkan SDK (Interface)]
```

Розглянемо поширення на формальному ланцюжку `A → B → C`, де ціль `A` лінкує ціль `B`, а ціль `B` лінкує ціль `C`.

![Транзитивність вимог вжитку в ланцюжку цілей](/reference/build-systems/cmake/usage-requirements/img/dag-propagation.svg)
*При лінкуванні PRIVATE вимоги цілі C зупиняються на рівні B. При лінкуванні PUBLIC вимоги C проходять крізь B і потрапляють до A.*

### Сценарій 1: Ізоляція реалізації (`B` лінкує `C` через `PRIVATE`)

Нехай `C` визначає:
* `INTERFACE_INCLUDE_DIRECTORIES = /opt/c_lib/include`
* `INTERFACE_COMPILE_DEFINITIONS = C_FAST_MATH`

Ціль `B` викликає `target_link_libraries(B PRIVATE C)`.
* Внутрішні властивості `B` поповнюються: під час компіляції файлів цілі `B` компілятор отримає `-I/opt/c_lib/include` та `-DC_FAST_MATH`.
* Але у властивість `INTERFACE_LINK_LIBRARIES` цілі `B` ціль `C` не додається як відкритий інтерфейс.

Коли ціль `A` викликає `target_link_libraries(A PRIVATE B)`:
* `A` отримує параметри з `INTERFACE_INCLUDE_DIRECTORIES` цілі `B`.
* `A` **не отримує** ні `/opt/c_lib/include`, ні `-DC_FAST_MATH`. Граф заблокував витік параметрів `C` на рівні `B`.

Це запобігає витоку абстракцій та надлишковому зв'язуванню (англ. *overlinking*): якщо завтра бібліотека `B` замінить внутрішній рушій `C` на інший аналог `D`, код модуля `A` навіть не помітить змін і не вимагатиме повторної компіляції своїх вихідних файлів.

### Сценарій 2: Відкритий тип у контракті (`B` лінкує `C` через `PUBLIC`)

Якщо ж відкритий інтерфейс `B` вимагає `C`, розробник пише `target_link_libraries(B PUBLIC C)`.
* Ціль `C` записується у властивість `INTERFACE_LINK_LIBRARIES` цілі `B`.
* Коли `A` лінкує `B`, генератор CMake під час аналізу залежностей бачить запис `C` в інтерфейсі `B` і рекурсивно обходить граф далі.
* Ціль `A` автоматично отримує у свій командний рядок компіляції і заголовки `B`, і заголовки `C`, а також усі макровизначення обох модулів.

### Сценарій 3: Інтерфейсне делегування (`B` лінкує `C` через `INTERFACE`)

Якщо `B` є інтерфейсною бібліотекою (наприклад, мета-пакетом SDK) і пише `target_link_libraries(B INTERFACE C)`:
* Сама ціль `B` нічого не компілює.
* Будь-який споживач `A`, що підключить `B`, отримає всі вимоги вжитку від `C` так, ніби підключив `C` безпосередньо.

## Механізм обчислення транзитивного замикання під час генерації

Усі операції зі збору властивостей виконуються не в момент виклику команди `target_link_libraries`, а на стадії генерації низових збіркових файлів (для Ninja, Make, Visual Studio чи Xcode).

Цей механізм має чотири фундаментальні властивості:

1. **Порядок команд `target_*` у межах файлу не має значення для транзитивності.** Ви можете спочатку викликати `target_link_libraries(app PRIVATE engine)`, а вже трьома рядками нижче додати `target_include_directories(engine PUBLIC include)`. Під час конфігурації CMake лише записує ребра графа та властивості до словників у пам'яті. Повне транзитивне замикання (англ. *transitive closure*) будується пізніше, коли всі файли `CMakeLists.txt` завершили роботу.
2. **Алгоритм обходу графа усуває дублікати.** Якщо ціль `A` лінкує бібліотеку `B` і бібліотеку `D`, і обидві вони підключають `common_types` як `PUBLIC`, каталог заголовків `common_types` з'явиться в командному рядку компілятора `A` рівно один раз. При цьому CMake зберігає порядок першого входження для каталогів заголовків і детермінований топологічний порядок для бібліотек лінкера.
3. **Захист від зациклень.** Якщо в проєкті випадково створюється взаємна залежність або довга петля, генератор виявляє цикл під час топологічного сортування DAG і зупиняє роботу зі зрозумілою діагностикою ланцюжка помилки.
4. **Ієрархія пріоритетів включення.** Шляхи з власної властивості `INCLUDE_DIRECTORIES` завжди передаються компілятору раніше, ніж шляхи, отримані транзитивно через `INTERFACE_INCLUDE_DIRECTORIES` від залежностей. Це гарантує, що локальні файли поточної цілі мають пріоритет над однойменними заголовками сторонніх бібліотек.

## Вимоги до стандарту мови: автоматичне узгодження cxx_std

Один із найяскравіших прикладів роботи вимог вжитку — властивість `COMPILE_FEATURES` та команда `target_compile_features`.

Замість жорсткого прописування прапорців на зразок `-std=c++20` чи `/std:c++latest`, які специфічні для конкретного компілятора і ламають кросплатформність, розробник описує мінімальну вимогу до мови:

```cmake
# Бібліотека template_helpers використовує концептуальні обмеження C++20 у відкритих заголовках
add_library(template_helpers INTERFACE)
target_compile_features(template_helpers INTERFACE cxx_std_20)

# Бібліотека legacy_engine використовує можливості C++17 у власних .cpp файлах
add_library(legacy_engine STATIC engine.cpp)
target_compile_features(legacy_engine PRIVATE cxx_std_17)

# Підключаємо template_helpers до legacy_engine
target_link_libraries(legacy_engine PUBLIC template_helpers)
```

Що відбувається під час генерації для `legacy_engine`:
* Власна вимога `legacy_engine` — щонайменше `cxx_std_17`.
* Транзитивна вимога від `template_helpers` — щонайменше `cxx_std_20`.
* Генератор CMake порівнює всі вимоги вздовж графа залежностей, обчислює верхню межу (максимальний необхідний стандарт) і автоматично виставляє для компіляції `legacy_engine` прапорець `C++20`!

Якщо до проєкту додається інший застосунок `app`, який сам по собі вимагає `cxx_std_23`, CMake підніме стандарт для `app` до `C++23`, гарантуючи, що жодна ціль у графі не буде скомпільована з версією мови, нижчою за вимоги будь-якої з її транзитивних бібліотек.

## Системні заголовки та придушення шуму стороннього коду

Коли проєкт підключає зовнішню або успадковану бібліотеку, її заголовні файли нерідко містять код, який викликає масу зауважень компілятора під час збірки з суворими прапорцями (`-Wall -Wextra -Wpedantic`). Якщо підключити таку бібліотеку звичайним шляхом, розробники поточного проєкту потонуть у сотнях чужих попереджень.

CMake вирішує цю проблему за допомогою модифікатора `SYSTEM`:

```cmake
# Позначаємо заголовки сторонньої бібліотеки як системні для споживачів
target_include_directories(legacy_vendor_sdk SYSTEM INTERFACE
    ${CMAKE_CURRENT_SOURCE_DIR}/vendor/include
)
```

Механізм дії модифікатора `SYSTEM`:
1. Замість звичайної властивості `INTERFACE_INCLUDE_DIRECTORIES`, шлях записується у властивість `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES`.
2. Під час генерації команди компіляції для споживачів CMake підставляє спеціальний прапорець компілятора замість стандартного `-I`:
   * Для GCC та Clang генерується прапорець `-isystem /path/to/vendor/include`.
   * Для Microsoft Visual C++ (MSVC) генерується прапорець `/external:I /path/to/vendor/include` (починаючи з версії MSVC 2017/2019 за підтримки відповідних політик CMake).
3. Компілятор шукає файли за вказаним шляхом точно так само, але повністю вимикає генерацію будь-яких діагностичних попереджень для коду всередині цих заголовків.

Це дозволяє утримувати режим нульової толерантності до попереджень (`-Werror`) у власному коді, не змінюючи вихідні файли сторонніх бібліотек.

## Попередньо скомпільовані заголовки: target_precompile_headers

Починаючи з версії CMake 3.16, вимоги вжитку охоплюють механізм попередньої компіляції заголовків (PCH — англ. *Precompiled Headers*). Команда `target_precompile_headers` повністю інтегрована в модель рівнів видимості:

```cmake
add_library(core_framework STATIC core.cpp utils.cpp)

# Внутрішній PCH прискорює лише збірку файлів самої бібліотеки
target_precompile_headers(core_framework PRIVATE
    <vector>
    <string>
    <memory>
    "src/internal_pch.h"
)

# Публічний PCH примусово підключається до кожного споживача
target_precompile_headers(core_framework PUBLIC
    <algorithm>
    <chrono>
)
```

Розподіл дій за рівнями:
* **`PRIVATE`**: заголовок додається у властивість `PRECOMPILE_HEADERS`. Компілятор збирає бінарний файл заголовка (`.gch` або `.pch`) і автоматично додає його через прапорець включення (`-include` або `/Yu`) лише під час компіляції вихідних файлів `core_framework`.
* **`PUBLIC` / `INTERFACE`**: заголовок потрапляє у властивість `INTERFACE_PRECOMPILE_HEADERS`. Будь-яка інша ціль, що лінкує `core_framework`, автоматично отримає цей PCH у свій процес компіляції.

Експорт PCH через `PUBLIC` вимагає обережності: він дійсно прискорює компіляцію клієнтських файлів, але водночас неявно впроваджує важкі заголовки у простір імен клієнта, що може призвести до неочікуваних колізій макросів або типів.

## Опції та каталоги лінкування: target_link_options

Починаючи з версії CMake 3.13, команди `target_link_options` та `target_link_directories` замінили застарілі глобальні каталожні команди, перевівши налаштування лінкера на цільово-орієнтовані рейки.

```cmake
add_library(secure_core STATIC secure.cpp)

# Прапорці лінкера потрібні будь-кому, хто створює фінальний бінарник із цією бібліотекою
target_link_options(secure_core INTERFACE
    $<$<CXX_COMPILER_ID:GNU,Clang>:
        -Wl,-z,relro
        -Wl,-z,now
    >
)
```

Властивість `INTERFACE_LINK_OPTIONS` автоматично передається вгору по дереву залежностей аж до кінцевого виконуваного файлу чи спільної бібліотеки, яка виконує фінальне зв'язування. Це дозволяє налаштовувати захисні механізми операційної системи (ASLR, стек без виконання, таблиці безпечного зв'язування) безпосередньо у файлі конфігурації бібліотеки, яка їх вимагає.

## Об'єктні бібліотеки (OBJECT) та вимоги вжитку

Особливе місце в сучасній моделі посідають об'єктні бібліотеки (`add_library(foo OBJECT ...)`). Вони компілюють вихідні файли у набір `.o` / `.obj` файлів, але не склеюють їх у статичний архів і не лінкують у спільну бібліотеку.

До CMake 3.12 об'єктні бібліотеки не могли повноцінно брати участь у графі вимог. Починаючи з версії CMake 3.12:
* Об'єктна бібліотека може споживати вимоги інших цілей через `target_link_libraries(obj_lib PRIVATE external_dep)`.
* Інші цілі можуть підключати об'єктну бібліотеку через `target_link_libraries(final_app PRIVATE obj_lib)`. При цьому споживач `final_app` не лише отримує всі вимоги з `INTERFACE_*`, а й автоматично додає скомпільовані об'єктні файли цілі `obj_lib` безпосередньо до власного рядка лінкування, позбавляючи потреби у ручному розгортанні генераторного виразу `$<TARGET_OBJECTS:obj_lib>`.

## Компіляція проти лінкування: тонка поведінка статичних бібліотек

Один із найбільш підступних моментів у практиці систем збірки стосується різниці між поширенням **вимог компіляції** та поширенням **бінарних залежностей лінкування** для статичних бібліотек.

Розглянемо приклад:
```cmake
add_library(math_engine STATIC math.cpp)

add_library(renderer STATIC renderer.cpp)
target_link_libraries(renderer PRIVATE math_engine)

add_executable(game_app main.cpp)
target_link_libraries(game_app PRIVATE renderer)
```

Погляньмо на виклик `target_link_libraries(renderer PRIVATE math_engine)`. Оскільки вказано `PRIVATE`, вимоги компіляції `math_engine` (каталоги включення, макроси) **не потрапляють** до `game_app`. Якщо `main.cpp` спробує написати `#include <math.h>`, компілятор видасть помилку.

Але що відбувається на фінальному етапі лінкування виконуваного файлу `game_app`?
У командному рядку лінкера ми несподівано бачимо обидва архіви:
```bash
gcc main.o librenderer.a libmath_engine.a -o game_app
```

Чому `libmath_engine.a` з'явилася в команді лінкування `game_app`, якщо зв'язок між `renderer` та `math_engine` був оголошений як `PRIVATE`?

Ця поведінка зумовлена фізичною природою статичного лінкування в системних мовах (C, C++):

1. Створення статичної бібліотеки `librenderer.a` — це всього лише пакування скомпільованих об'єктних файлів `renderer.o` в один архів за допомогою утиліти `ar` (або `llvm-ar` / `lib.exe`). На цьому етапі **не відбувається розв'язання зовнішніх символів** і не генерується бінарний зв'язок.
2. Файли `renderer.o` містять невирішені звернення до функцій `math_engine`.
3. Коли створюється фінальний бінарний файл `game_app`, системний лінкер зобов'язаний мати доступ до коду всіх невирішених символів, інакше збірка впаде з помилкою `undefined reference to math_function()`.

CMake розв'язує цю дилему елегантно, розділяючи транзитивність на два рівні:

* **Вимоги вжитку для компілятора** (`INTERFACE_INCLUDE_DIRECTORIES`, `INTERFACE_COMPILE_DEFINITIONS` тощо) підкоряються ключовим словам строго: якщо вказано `PRIVATE`, споживач `game_app` їх **не бачить**. Заголовки надійно ізольовані.
* **Бінарні вимоги для лінкера** (`LINK_LIBRARIES`): для статичних бібліотек CMake автоматично просуває бінарний файл `libmath_engine.a` до фінального лінкера, навіть якщо зв'язок був `PRIVATE`.

Якби `renderer` був динамічною (спільною) бібліотекою (`SHARED`):
```cmake
add_library(renderer SHARED renderer.cpp)
target_link_libraries(renderer PRIVATE math_engine)
```
Тоді під час створення `librenderer.so` системний лінкер повністю розв'язав би всі символи з `libmath_engine.a` і включив їхній код усередину спільного об'єкта. У такому разі `game_app` лінкувався б лише з `librenderer.so`, а `libmath_engine.a` взагалі не фігурувала б у команді створення `game_app` (якщо платформа або експорт символів цього не вимагають).

## Перевірка несумісності в графі: COMPATIBLE_INTERFACE

У складних архітектурах трапляється ситуація, коли різні бібліотеки вимагають взаємовиключних параметрів середовища. Наприклад, одна бібліотека зібрана для роботи з однопотоковим пулом пам'яті (`USE_THREAD_SAFE=0`), а інша вимагає глобального блокування потоків (`USE_THREAD_SAFE=1`). Якщо обидві підключити до однієї програми, виникне важковловима помилка пам'яті під час виконання.

CMake містить вбудований механізм валідації сумісності вимог вжитку: властивості `COMPATIBLE_INTERFACE_BOOL` та `COMPATIBLE_INTERFACE_STRING`.

```cmake
add_library(driver_legacy STATIC legacy.cpp)
set_target_properties(driver_legacy PROPERTIES
    INTERFACE_USE_64BIT_ADDR "OFF"
    COMPATIBLE_INTERFACE_BOOL USE_64BIT_ADDR
)

add_library(driver_modern STATIC modern.cpp)
set_target_properties(driver_modern PROPERTIES
    INTERFACE_USE_64BIT_ADDR "ON"
    COMPATIBLE_INTERFACE_BOOL USE_64BIT_ADDR
)

add_executable(controller main.cpp)
# ПОМИЛКА під час генерації: несумісні вимоги інтерфейсу!
target_link_libraries(controller PRIVATE driver_legacy driver_modern)
```

Коли ціль `controller` намагається злінкувати обидві бібліотеки, генератор CMake аналізує граф вимог і виявляє конфлікт у значенні логічної властивості `USE_64BIT_ADDR`. Процес генерації миттєво зупиняється зі звітом:
```
CMake Error: The INTERFACE_USE_64BIT_ADDR property of "driver_modern" does
not agree with the value of "USE_64BIT_ADDR" already evaluated for target "controller"
from target "driver_legacy".
```

Цей механізм дозволяє авторам бібліотек створювати контракти безпеки, які гарантують цілісність архітектурних конфігурацій на рівні всієї збірки.

## Інтерфейсні бібліотеки як носії налаштувань

Інтерфейсні бібліотеки в сучасній архітектурі CMake застосовуються не лише для коду без компіляції (header-only), а й як потужний шаблон проєктування: **цілі-конфігурації** (англ. *tooling / configuration targets*).

У застарілих проєктах прапорці компілятора та попередження часто додавали глобально через змінні:
```cmake
# АНТИПАТЕРН: бруднить прапорцями абсолютно всі цілі, включно з підтягнутими сторонніми бібліотеками
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Wall -Wextra -Wpedantic -Werror")
```
Якщо проєкт підключає сторонню бібліотеку через [FetchContent](book:build-systems/fetchcontent-subprojects) або `add_subdirectory`, цей глобальний прапорець `-Werror` призведе до падіння збірки через незначне попередження в чужому коді, на який розробники проєкту не мають впливу.

Правильне вирішення — створити інтерфейсну ціль із набором прапорців і підключати її лише до власних модулів:

```cmake
add_library(project_warnings INTERFACE)

target_compile_options(project_warnings INTERFACE
    $<$<CXX_COMPILER_ID:GNU,Clang>:
        -Wall
        -Wextra
        -Wpedantic
        -Wconversion
        -Wshadow
    >
    $<$<CXX_COMPILER_ID:MSVC>:
        /W4
        /permissive-
    >
)

# Застосовуємо прапорці лише до власних цілей
add_library(core_engine STATIC engine.cpp)
target_link_libraries(core_engine PRIVATE project_warnings)

add_executable(game_server main.cpp)
target_link_libraries(game_server PRIVATE project_warnings)
```

![Структура та поширення вимог інтерфейсної бібліотеки](/reference/build-systems/cmake/usage-requirements/img/header-only-interface.svg)
*Інтерфейсна ціль існує в графі збірки як самостійний вузол і безпечно роздає свої вимоги підключеним споживачам.*

Такий підхід забезпечує абсолютну ізоляцію:
* Сторонні залежності збираються зі своїми власними налаштуваннями за замовчуванням.
* Усі власні модулі проєкту мають єдине, централізоване джерело прапорців якості коду.
* Зміна або додавання нового діагностичного прапорця здійснюється в одному місці й автоматично поширюється на всі потрібні цілі.

Більше того, починаючи з версії CMake 3.19, інтерфейсні бібліотеки можуть мати навіть власні вихідні файли (`target_sources`), які приєднуються до списку компіляції будь-якого споживача. А починаючи з версії 3.23, механізм `FILE_SET` дозволяє інтерфейсним цілям публікувати структуровані набори модулів C++20 та заголовків, які автоматично встановлюються командою `install(TARGETS ... FILE_SET HEADERS)`.

## Розділення середовищ: BUILD_INTERFACE проти INSTALL_INTERFACE

Коли бібліотека розробляється для подальшого встановлення в систему через команду `install(TARGETS ... EXPORT ...)`, виникає просторовий парадокс шляхів пошуку заголовків.

Під час розробки всередині репозиторію публічні заголовки розташовані за абсолютною адресою вихідного коду:
`${CMAKE_CURRENT_SOURCE_DIR}/include` (наприклад, `/home/dev/projects/engine/include`).

Але після встановлення бібліотеки в операційну систему (через `cmake --install`) заголовки опиняються у системному каталозі (наприклад, `/usr/local/include` або `C:/Program Files/Engine/include`).

Якщо наївно вказати абсолютний шлях:
```cmake
# ПОМИЛКА під час подальшого експорту цілі
target_include_directories(engine PUBLIC
    ${CMAKE_CURRENT_SOURCE_DIR}/include
)
```
То під час генерації експортного файлу для зовнішніх споживачів (`engine-config.cmake` або `engine-targets.cmake`) CMake виявить, що ціль намагається експортувати абсолютний шлях файлової системи розробника. Команда `install(EXPORT ...)` негайно зупинить процес із фатальною помилкою:
```
CMake Error in CMakeLists.txt:
  Target "engine" INTERFACE_INCLUDE_DIRECTORIES property contains path:
    "/home/dev/projects/engine/include"
  which is prefixed in the source directory.
```

Це захисний механізм: CMake не дозволяє жорстко зашити локальні шляхи однієї машини в поширюваний дистрибутив пакета.

Для розв'язання цієї проблеми використовуються [генераторні вирази](book:build-systems/generator-expressions) простору вжитку:
`$<BUILD_INTERFACE:...>` та `$<INSTALL_INTERFACE:...>`.

```cmake
target_include_directories(engine PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>
)
```

![Розділення шляхів включення для етапів збірки та встановлення](/reference/build-systems/cmake/usage-requirements/img/build-vs-install-interface.svg)
*Генераторні вирази дозволяють точно розділити шляхи: внутрішні тести бачать дерево вихідного коду, а зовнішні клієнти — шлях відносно префікса інсталяції.*

Як це працює:
* Під час збірки цілей у поточному дереві (включно з внутрішніми модульними тестами та прикладами) вираз `$<BUILD_INTERFACE:...>` розгортається у фактичний шлях до початкового коду, а `$<INSTALL_INTERFACE:...>` перетворюється на порожній рядок.
* Коли виконується команда експорту для інсталяції ([install і export](book:build-systems/install-and-export)), CMake генерує файл опису цілі для зовнішнього споживача, де залишає лише значення з виразу `$<INSTALL_INTERFACE:include>`, автоматично прив'язуючи його до динамічного префікса інсталяції `_IMPORT_PREFIX`.

Цей самий підхід застосовується і до прапорців компілятора чи опцій лінкування, які можуть відрізнятися для внутрішньої розробки та зовнішнього використання.

## Діагностика розповсюдження вимог

Коли проєкт розростається до десятків бібліотек, відстежити очима, чому той чи інший прапорець опинився в командному рядку компілятора (або чому заголовок не знайдено), стає важко. Для діагностики графа вимог вжитку в CMake існує кілька ефективних інструментів.

### 1. Перевірка реального командного рядка компілятора

Найбільш прямий спосіб перевірити, що саме отримав компілятор після обходу всіх вузлів графа, — запустити збірку в докладному режимі:

```bash
# Для генератора Ninja
cmake --build build --verbose

# Або напряму через Ninja / Make
ninja -v -C build
make VERBOSE=1 -C build
```

У виводі ви побачите точну команду компіляції для кожного об'єктного файлу, де будуть перелічені всі зібрані прапорці `-I`, `-D` та опції стандарту.

Інший спосіб — генерація бази команд компіляції:
```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```
Це створить у теці збірки файл `compile_commands.json`, який можна переглянути будь-яким текстовим редактором або використати в аналізаторах коду (Clang-Tidy, Clangd, VS Code, CLion).

### 2. Інспектування властивостей під час конфігурації

Якщо потрібно дізнатися, що записано безпосередньо у властивостях цілі, використовують команду `get_target_property`:

```cmake
get_target_property(inc_dirs core_engine INCLUDE_DIRECTORIES)
message(STATUS "Власні каталоги core_engine: ${inc_dirs}")

get_target_property(iface_inc core_engine INTERFACE_INCLUDE_DIRECTORIES)
message(STATUS "Експортні каталоги core_engine: ${iface_inc}")

get_target_property(libs game_app LINK_LIBRARIES)
message(STATUS "Залежності game_app: ${libs}")
```

> ⚠️ **Важливе застереження:** властивість `INCLUDE_DIRECTORIES` на споживачі `game_app` покаже лише ті шляхи, які були задані для `game_app` безпосередньо. Шляхи, що приходять транзитивно від підключених бібліотек через `INTERFACE_INCLUDE_DIRECTORIES`, **не записуються** у властивість `INCLUDE_DIRECTORIES` споживача! Їх обчислює генератор CMake на етапі генерації збіркових файлів.

### 3. Візуалізація графа через Graphviz

CMake має вбудовану можливість експортувати повний граф залежностей у форматі Graphviz DOT:

```bash
# Генерація графа залежностей у файл dependencies.dot
cmake --graphviz=build/dependencies.dot -B build

# Перетворення у векторне зображення (потрібен встановлений Graphviz)
dot -Tsvg build/dependencies.dot -o build/graph.svg
```

Згенерований файл покаже не лише всі вузли проєкту, а й типи зв'язків між ними:
* Суцільні лінії позначають `PUBLIC` залежності.
* Пунктирні лінії позначають `PRIVATE` залежності.
* Штрихпунктирні лінії позначають `INTERFACE` залежності.

Це дозволяє миттєво виявити небажані циклічні залежності або випадкові транзитивні протікання внутрішніх бібліотек у публічний контур проєкту.

## Історичний розвиток та політики CMake

Сучасна строга модель вимог вжитку сформувалася не одразу. До версії CMake 2.8.11 розробники були змушені вручну підтримувати пари змінних на зразок `FOO_INCLUDE_DIRS` та `FOO_LIBRARIES`, що робило будь-яку збірку вразливою до людських помилок.

Перехід до системи `PUBLIC`/`PRIVATE`/`INTERFACE` регулюється низкою фундаментальних політик:

* **`CMP0022`** (CMake 2.8.12): визначила, що саме властивість `INTERFACE_LINK_LIBRARIES` відповідає за транзитивні залежності лінкування, скасувавши старе автоматичне дублювання списку `LINK_LIBRARIES`.
* **`CMP0023`** (CMake 2.8.12): заборонила змішувати виклики команди `target_link_libraries` із ключовими словами (`PUBLIC`/`PRIVATE`/`INTERFACE`) та старі виклики без ключових слів у межах однієї цілі.
* **`CMP0079`** (CMake 3.13): дозволила викликати `target_link_libraries` над цілями, створеними в інших підкаталогах проєкту, остаточно усунувши необхідність піднімати налаштування на рівень батьківських каталогів через глобальні змінні.

Ці політики гарантують, що проєкти, написані за сучасними стандартами CMake, зберігають передбачувану, детерміновану та ізольовану поведінку на будь-якій підтримуваній платформі.

## Правила проєктування: як уникати пасток

Підсумуємо практичні принципи керування вимогами вжитку, перевірені практикою великих виробничих проєктів:

| Тип ресурсу | Коли використовувати `PRIVATE` | Коли використовувати `PUBLIC` | Коли використовувати `INTERFACE` |
|---|---|---|---|
| **Каталоги заголовків** | Внутрішні теки `src/`, закриті деталі реалізації | Каталог `include/` із відкритим API бібліотеки | Каталоги header-only бібліотеки |
| **Системні заголовки** | Сторонні внутрішні бібліотеки з зауваженнями | Заголовки зовнішніх залежностей, що входять у публічне API | Системні SDK для клієнтів (через `SYSTEM INTERFACE`) |
| **Макроси препроцесора** | Макроси оптимізації, локальні прапорці налагодження | Макроси конфігурації типів і структур у публічних `.h` | Макроси для шаблонного заголовкового коду |
| **Прапорці компілятора** | Попередження (`-Wall`), прапорці оптимізації поточної збірки | Тільки якщо прапорець критично змінює ABI (вкрай рідко) | Ціль-пакет налаштувань для проєкту (`project_warnings`) |
| **Попередньо скомпільовані заголовки** | Внутрішній PCH для прискорення власної збірки | Стандартні заголовки для всієї підсистеми | Спільний набір PCH для клієнтів SDK |
| **Прапорці лінкера** | Прапорці оптимізації лінкування власного бінарника | Прапорці експорту символів, специфічні для API | Глобальні прапорці безпеки (ASLR, RELRO) |
| **Залежності (бібліотеки)** | Бібліотека використовується тільки у внутрішніх `.cpp` | Типи бібліотеки передаються через відкриті заголовки | Залежності header-only модуля або мета-пакета |

Головний орієнтир: **що вужча видимість, то стабільніша архітектура**. Усе, що може бути зроблено `PRIVATE`, має бути зроблено `PRIVATE`. Будь-яке підвищення до `PUBLIC` повинно мати чітке обґрунтування: наявність типу або символу залежності у відкритому заголовному файлі.

Дотримання цієї дисципліни перетворює систему збірки з джерела випадкових помилок компіляції на строгий інструмент контролю модульності та архітектурних меж проєкту.
