# 📜 Історія появи та еволюції CPack

Розробка компільованого програмного забезпечення на рубежі 1990-х і 2000-х років спиралася на розірваний технологічний ланцюг: система збірки відповідала виключно за компіляцію сирців у бінарні файли, тоді як створення дистрибутивів залишалося сферою ізольованих сторонніх утиліт. У світі Unix стандартом де-факто був набір GNU Autotools, де команда `make dist` створювала вихідний архів `.tar.gz`, а формування бінарних пакетів `.rpm` чи `.deb` вимагало окремого написання складних файлів специфікацій (`spec`-файлів для RPM або каталогів `debian/` для dpkg). У середовищі Microsoft Windows розробники вручну писали сценарії для інсталяторів NSIS (Nullsoft Scriptable Install System) або Inno Setup, дублюючи переліки файлів та шляхи їхнього розташування.

Кожен новий бінарний файл, динамічна бібліотека чи конфігураційний файл вимагали одночасного оновлення у кількох незалежних конфігураціях. Якщо розробник додавав новий заголовочний файл у `Makefile.am`, але забував додати його до секції `%files` у `package.spec` або до секції інсталяції в NSIS, пакунок збирався без помилок, проте кінцевий користувач отримував некомплектний дистрибутив.

## Поява CPack у складі CMake 2.4

Проблема стала критичною для кросплатформних проєктів із відкритим вихідним кодом, зокрема системи візуалізації VTK (Visualization Toolkit) та медичного інструментарію ITK (Insight Segmentation and Registration Toolkit), якими опікувалася компанія Kitware. Створення CMake на початку 2000-х років розв'язало задачу уніфікації генерації файлів збірки під Make, Ninja чи Visual Studio, однак останній крок — дистрибуція артефактів — залишався ручним і вразливим до людських помилок.

У 2006 році разом із релізом CMake 2.4 компанія Kitware представила CPack — генератор пакетів, вбудований безпосередньо в екосистему CMake. Головна ідея Білла Гоффмана (Bill Hoffman) та команди Kitware полягала у повторному використанні інформації, яку CMake вже мав про проєкт. Якщо розробник уже описав правила інсталяції за допомогою команд `install(TARGETS ...)` та `install(FILES ...)`, системі відомо все необхідне: точний перелік цілей, їхні типи (виконувані файли, динамічні бібліотеки, статичні архіви), шляхи призначення відносно префікса та права доступу.

Замість написання окремих сценаріїв пакування CPack запровадив проміжний рівень абстракції: під час конфігурації CMake генерував службовий файл `CPackConfig.cmake`, а окрема утиліта `cpack` зчитувала ці інструкції, монтувала тимчасове дерево інсталяції у відокремленому каталозі (*staging directory*) і передавала його на вхід обраному бекенду генератора.

## Еволюція від монолітних архівів до компонентів

Перші версії CPack створювали виключно монолітні архіви: весь вміст, описаний правилами `install()`, потрапляв в один єдиний пакунок (`.tar.gz`, `.zip` чи `.exe` інсталятор NSIS). Проте для корпоративних бібліотек і системних сервісів монолітний підхід був неприйнятним. Розробникам потрібно було розділяти кінцевий продукт на ізольовані частини:
1. Виконувані файли та динамічні бібліотеки для кінцевих користувачів (*Runtime*).
2. Заголовки, статичні бібліотеки та конфігураційні файли CMake для програмістів (*Development*).
3. Довідкові матеріали та документацію API (*Documentation*).

У релізі CMake 2.6 (2008 рік) з'явилася підсистема компонентного пакування (*Component-Based Packaging*). CMake розширив команду `install()` обов'язковим аргументом `COMPONENT`, а CPack отримав модуль `CPackComponent`, який дозволив декларувати метадані компонентів, зв'язувати їх графом залежностей і пакувати кожен компонент в окремий файл `.deb`, `.rpm` чи zip-архів без повторної перекомпіляції проєкту.

## Перехід до нативних пакетів Linux та сучасного WiX

На початковому етапі генератори DEB та RPM всередині CPack були простими обгортками, які викликали системні утиліти `dpkg-deb` та `rpmbuild`. Вони вимагали від розробника самостійно вказувати всі системні залежності у змінних CMake. Це породжувало проблеми сумісності між різними версіями дистрибутивів Linux (наприклад, Ubuntu та Fedora використовували різні імена базових бібліотек OpenSSL чи zlib).

Починаючи з CMake 3.x, підсистема CPack для Linux отримала глибоку інтеграцію з аналізатором виконуваних файлів ELF. Генератор DEB навчився автоматично викликати `dpkg-shlibdeps`, аналізувати динамічні секції `DT_NEEDED` у скомпільованих бінарниках і генерувати точний список залежностей `Depends:` на основі системних файлів `shlibs`. Для формату RPM було реалізовано автоматичне генерування секцій `%provides` та `%requires` на базі внутрішніх макросів `rpmbuild`.

Паралельно у світі Windows застарілий підхід із генерацією MSI-інсталяторів через сторонні утиліти замінили на повноцінний генератор WiX (Windows Installer XML Toolset). Це дозволило створювати декларативні, транзакційні інсталятори для корпоративного розгортання через групові політики Active Directory, де кожен файл відстежується унікальним GUID.

Сьогодні CPack перетворився на індустріальний стандарт кросплатформного пакування у світі C та C++, поєднуючи простоту єдиного файлу `CMakeLists.txt` із можливістю генерувати готові до публікації системні пакети для будь-якої цільової операційної системи.
