# 📋 Довідник змінних тулчейна та крос-компіляції CMake

Цей довідник містить вичерпний опис усіх системних змінних CMake, що керують вибором цільової платформи, налаштуванням компіляторів і бінарних утиліт, маршрутизацією системного кореня (sysroot), перевизначенням поведінки пошукових команд `find_*`, конфігурацією емуляторів виконання та режимами перевірки компілятора `try_compile`. Його відкривають, коли потрібно створити або відлагодити файл тулчейна для вбудованих систем, мобільних платформ, bare-metal мікроконтролерів чи крос-дистрибутивів Linux.

---

## 1. Змінні ідентифікації та конфігурації платформи

Встановлення змінних цільової системи є першим і головним завданням файлу тулчейна. Саме вони переводять внутрішній рушій CMake у режим крос-компіляції, змінюючи базові припущення про середовище виконання та файлову структуру.

Коли CMake обробляє команду `project()` або `enable_language()`, він насамперед перевіряє значення змінної `CMAKE_SYSTEM_NAME`. Якщо ця змінна не визначена, CMake вважає збірку нативною (хостовою) та автоматично копіює значення змінної `CMAKE_HOST_SYSTEM_NAME` (наприклад `Linux`, `Windows` або `Darwin`) у цільову `CMAKE_SYSTEM_NAME`. Якщо ж змінну `CMAKE_SYSTEM_NAME` задано явно у файлі тулчейна, CMake активує механізм крос-компіляції, встановлюючи прапорець `CMAKE_CROSSCOMPILING = TRUE`.

| Змінна | Тип | Опис та допустимі значення |
| :--- | :--- | :--- |
| `CMAKE_SYSTEM_NAME` | `STRING` | Назва цільової операційної системи. Встановлення цієї змінної активує прапорець `CMAKE_CROSSCOMPILING = TRUE`. Типові значення: `Linux`, `Generic` (для bare-metal/RTOS без стандартної ОС), `Android`, `Windows`, `Darwin`, `FreeBSD`, `QNX`, `iOS`. |
| `CMAKE_SYSTEM_PROCESSOR` | `STRING` | Архітектура цільового мікропроцесора. Використовується внутрішніми модулями CMake та сторонніми бібліотеками для вибору асемблерного коду. Приклади: `arm`, `aarch64`, `riscv32`, `riscv64`, `x86_64`, `mips`. |
| `CMAKE_SYSTEM_VERSION` | `STRING` | Версія цільової ОС або рівень API. Для Embedded Linux — версія ядра; для Android — числовий рівень API (наприклад `29`); для Windows — версія WinSDK (наприклад `10.0.19041.0`). |
| `CMAKE_CROSSCOMPILING` | `BOOL` | Прапорець тільки для читання (Read-Only). Автоматично отримує значення `TRUE`, якщо `CMAKE_SYSTEM_NAME` явно встановлено і воно відрізняється від `CMAKE_HOST_SYSTEM_NAME` (або для `Generic`). |
| `CMAKE_HOST_SYSTEM_NAME` | `STRING` | Назва операційної системи хост-машини, на якій запущено сам процес `cmake` (наприклад `Linux`, `Windows`, `Darwin`). Задається автоматично. |
| `CMAKE_HOST_SYSTEM_PROCESSOR` | `STRING` | Архітектура процесора хост-машини (наприклад `x86_64`, `AMD64`, `arm64`). Задається автоматично. |

### Особливості значення Generic

Значення `Generic` має спеціальний статус у внутрішній системі типів CMake. Воно сигналізує генератору, що цільове середовище позбавлене стандартних системних викликів POSIX, динамічного завантажувача бібліотек та файлової системи. Під час використання `Generic` CMake вимикає автоматичне додавання системних прапорців динамічного лінкування (наприклад `-rdynamic` чи `-ldl`), які є обов'язковими для повноцінних дистрибутивів Linux, але спричиняють фатальні помилки компіляції на мікроконтролерах.

## 2. Змінні компіляторів, утиліт та ABI

Ці змінні визначають, які саме бінарні файли крос-тулчейна запускатимуться на стадіях трансляції вихідного коду, архівації об'єктних файлів, оптимізації секцій і фінального компонування бінарного образу.

Під час призначення шляхів до компіляторів у файлі тулчейна важливо враховувати, що CMake кешує ці значення після першого успішного прогону. Якщо шлях до компілятора зміниться, каталог збірки вимагатиме повного очищення або повторного виклику з перестворенням кешу.

| Змінна | Призначення | Приклад значення |
| :--- | :--- | :--- |
| `CMAKE_C_COMPILER` | Шлях або назва виконуваного файла компілятора мови C. | `arm-none-eabi-gcc` або `/opt/toolchain/bin/aarch64-linux-gnu-gcc` |
| `CMAKE_CXX_COMPILER` | Шлях або назва компілятора мови C++. | `arm-none-eabi-g++` або `/opt/toolchain/bin/aarch64-linux-gnu-g++` |
| `CMAKE_ASM_COMPILER` | Компілятор/асемблер для файлів `.s` та `.S`. | `arm-none-eabi-gcc` або `arm-none-eabi-as` |
| `CMAKE_AR` | Утиліта створення статичних бібліотек (архіватор). | `arm-none-eabi-ar` |
| `CMAKE_RANLIB` | Генератор індексу таблиці символів для архівів `.a`. | `arm-none-eabi-ranlib` |
| `CMAKE_STRIP` | Утиліта видалення налагоджувальних символів із бінарників. | `aarch64-linux-gnu-strip` |
| `CMAKE_OBJCOPY` | Утиліта конвертації бінарних форматів (ELF у HEX/BIN). | `arm-none-eabi-objcopy` |
| `CMAKE_OBJDUMP` | Дизасемблер та аналізатор секцій ELF-файлів. | `arm-none-eabi-objdump` |
| `CMAKE_C_COMPILER_TARGET` | Цільовий тріплет для уніфікованого компілятора Clang (передається як прапорець `--target=<triple>`). | `arm-none-eabi` або `aarch64-linux-gnu` |
| `CMAKE_CXX_COMPILER_TARGET`| Цільовий тріплет мови C++ для Clang. | `arm-none-eabi` або `aarch64-linux-gnu` |
| `CMAKE_ASM_COMPILER_TARGET`| Цільовий тріплет асемблера для Clang. | `arm-none-eabi` |

### Взаємодія з Clang та LLVM

На відміну від GCC, де для кожної цільової платформи збирається окремий двійковий файл (наприклад `aarch64-linux-gnu-gcc`), компілятор Clang використовує єдиний двійковий файл `clang`. Розрізнення архітектур виконується передачею прапорця `--target=<triple>`. Коли у файлі тулчейна встановлено змінну `CMAKE_<LANG>_COMPILER_TARGET`, CMake автоматично додає цей прапорець не лише до фінальної компіляції проєктних файлів, але й до всіх внутрішніх викликів перевірки працездатності компілятора та визначення ABI.

## 3. Змінні Sysroot та ізоляції файлової системи

Змінні цієї групи вказують компілятору та лінкеру логічний каталог розташування цільових заголовкових файлів і системних бібліотек. Вони гарантують, що під час включення системних заголовків або зв'язування з бібліотеками рушій збірки не звертатиметься до кореневої файлової системи хостової машини.

Системний корінь (Sysroot) відтворює структуру стандартного дерева Unix (`/usr/include`, `/usr/lib`, `/lib`), але містить файли, згенеровані під цільову архітектуру.

| Змінна | Прапорець компілятора | Опис семантики |
| :--- | :--- | :--- |
| `CMAKE_SYSROOT` | `--sysroot=<dir>` | Абсолютний шлях до кореневого каталогу цільової файлової системи. Застосовується одночасно до компілятора та лінкера на всіх стадіях складання. |
| `CMAKE_SYSROOT_COMPILE` | `--sysroot=<dir>` | Окремий системний корінь виключно для етапу компіляції. Дозволяє відокремити заголовкові файли від бінарних бібліотек у нестандартних структурах SDK. |
| `CMAKE_SYSROOT_LINK` | `--sysroot=<dir>` | Окремий системний корінь виключно для етапу лінкування. Використовується для зазначення каталогу розміщення цільових бібліотек та системних об'єктів запуску (`crt1.o`, `crti.o`). |
| `CMAKE_STAGING_PREFIX` | — | Шлях на машині хоста, куди команда `cmake --install` копіюватиме скомпільовані артефакти замість спроби запису у захищений системний каталог `CMAKE_INSTALL_PREFIX`. |

### Механізм заміщення шляхів інсталяції через CMAKE_STAGING_PREFIX

Під час крос-збірки змінна `CMAKE_INSTALL_PREFIX` часто встановлюється у значення `/usr` або `/opt/app`, оскільки саме за цими шляхами програма розташовуватиметься всередині цільової файлової системи пристрою. Якщо виконати інсталяцію безпосередньо, CMake спробує записати бінарні файли у системні каталоги хоста, що призведе до помилки доступу або пошкодження хостового середовища. 

Встановлення `CMAKE_STAGING_PREFIX` у файлі тулчейна розв'язує цю проблему: бінарні файли компілюються з префіксом `CMAKE_INSTALL_PREFIX` (що важливо для зашитих шляхів RPATH), але фактично копіюються у тимчасовий каталог хоста `CMAKE_STAGING_PREFIX` для подальшого пакування в образ системи.

## 4. Керування режимами команд пошуку find_*

Змінна `CMAKE_FIND_ROOT_PATH` містить список префіксів, які додаються на початок шляхів у командах `find_file()`, `find_path()`, `find_library()`, `find_package()`, `find_program()`.

Це дозволяє перенаправляти всі пошукові запити проєкту в ізольоване середовище sysroot або додаткових SDK без необхідності змінювати вихідні тексти `CMakeLists.txt`.

```cmake
# Приклад конфігурації префіксів пошуку у файлі тулчейна
set(CMAKE_FIND_ROOT_PATH "/opt/sysroot-arm64" "/opt/vendor-sdk")

set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

### Детальна семантика режимів фільтрації

Кожна команда родини `find_*` підпорядковується відповідній режимній змінній, яка може приймати одне з трьох значень:

- **`NEVER`**: Префікси з `CMAKE_FIND_ROOT_PATH` повністю ігноруються. Пошук виконується виключно за стандартними хостовими каталогами. Цей режим є критично обов'язковим для програм-інструментів (`find_program`), оскільки виконувані файли генераторів (компілятори схем, перетворювачі ресурсів) повинні виконуватися процесором робочої станції під час самого процесу збірки.
- **`ONLY`**: Пошук виконується виключно всередині префіксів, зазначених у `CMAKE_FIND_ROOT_PATH` або `CMAKE_SYSROOT`. Усі системні каталоги хоста (`/usr/include`, `/usr/lib`, `/lib`) повністю виключаються зі списку перевірки. Це унеможливлює випадкове включення хостових заголовків або лінкування несумісних динамічних бібліотек.
- **`BOTH`**: Двоетапний пошук. Спочатку перевіряються шляхи всередині `CMAKE_FIND_ROOT_PATH`, а якщо цільовий артефакт не знайдено — виконується повторний пошук за стандартними незміненими шляхами хоста. Цей режим використовують з обережністю, переважно для змішаних SDK.

### Алгоритм підстановки шляхів

Коли викликається команда `find_library(MY_LIB NAMES ssl PATHS /usr/lib)`, CMake виконує трансформацію шляху. Якщо активний режим `ONLY`, шлях `/usr/lib` замінюється послідовністю перевірок:

```text
/opt/sysroot-arm64/usr/lib/libssl.so
/opt/vendor-sdk/usr/lib/libssl.so
```

Прямий шлях `/usr/lib/libssl.so` на хості навіть не опитується операційною системою. Якщо ж конкретний виклик у коді проєкту містить прапорець `NO_CMAKE_FIND_ROOT_PATH`, CMake ігнорує глобальне правило файлу тулчейна для цього окремого виклику, що іноді потрібно для виявлення специфічних утиліт хоста.

### Режимні змінні та сфери їхнього впливу

| Змінна | Команди, на які вона впливає | Рекомендоване значення для крос-компіляції |
| :--- | :--- | :--- |
| `CMAKE_FIND_ROOT_PATH_MODE_PROGRAM` | `find_program()` | `NEVER` (інструменти збірки повинні виконуватися на хості) |
| `CMAKE_FIND_ROOT_PATH_MODE_LIBRARY` | `find_library()` | `ONLY` (цільові бінарні бібліотеки беруться виключно з sysroot) |
| `CMAKE_FIND_ROOT_PATH_MODE_INCLUDE` | `find_path()`, `find_file()` | `ONLY` (заголовки беруться виключно з цільового дерева) |
| `CMAKE_FIND_ROOT_PATH_MODE_PACKAGE` | `find_package()` | `ONLY` (пакети `*Config.cmake` шукаються лише у цільових каталогах) |

## 5. Спеціальні прапорці Bare-Metal та емуляції

Під час розробки для контролерів без операційних систем або тестування цільових бінарників на хостовій машині використовуються спеціалізовані керуючі змінні.

| Змінна | Тип та значення | Детальний опис поведінки |
| :--- | :--- | :--- |
| `CMAKE_TRY_COMPILE_TARGET_TYPE` | `STRING` (`EXECUTABLE` або `STATIC_LIBRARY`) | Визначає тип вихідного артефакту під час внутрішніх тестів працездатності компілятора в команді `project()`. Якщо встановлено `STATIC_LIBRARY`, CMake перевіряє компілятор шляхом створення статичного архіву утилітою `CMAKE_AR`, повністю виключаючи виклик компонувальника. Це запобігає збоям ініціалізації на платформах, де скрипт лінкера надається користувачем пізніше. |
| `CMAKE_CROSSCOMPILING_EMULATOR` | `STRING` або `LIST` (наприклад `qemu-aarch64;-L;/opt/sysroot`) | Шлях до двійкового файла емулятора та його аргументів. Дозволяє CMake прозоро запускати цільові двійкові файли на хості під час виконання команди `try_run()` та прогону тестових наборів `ctest`. |
| `CMAKE_TRY_COMPILE_PLATFORM_VARIABLES` | `LIST` назв змінних | Список додаткових змінних CMake, значення яких обов'язково повинні транслюватися у тимчасові ізольовані каталоги внутрішніх проєктів команди `try_compile()`. |

### Застосування емулятора у тестах

Якщо змінну `CMAKE_CROSSCOMPILING_EMULATOR` налаштовано у файлі тулчейна, команди створення тестів у CTest (`add_test()`) автоматично огортають виклик цільового бінарника у зазначений емулятор:

```text
/usr/bin/qemu-aarch64 -L /opt/sysroot-arm64 ./build/test_binary
```

Це дозволяє запускати повний тестовий набір проєкту командою `ctest` безпосередньо на робочій станції розробника або в конвеєрах неперервної інтеграції (CI) без доступу до реального фізичного обладнання.

## 6. Змінні мобільних систем: Android та iOS

Для розробки під мобільні операційні системи файл тулчейна містить специфічні змінні SDK виробника.

### Android NDK

Під час збірки для Android зазвичай використовується файл тулчейна, наданий безпосередньо Google у складі Android NDK (`build/cmake/android.toolchain.cmake`), або власний файл тулчейна, що налаштовує такі змінні:

- `CMAKE_ANDROID_NDK` — абсолютний шлях до розпакованого Android NDK.
- `CMAKE_ANDROID_ARCH_ABI` — цільовий двійковий інтерфейс (`arm64-v8a`, `armeabi-v7a`, `x86_64`, `x86`).
- `CMAKE_ANDROID_ARM_NEON` — прапорець активації векторних інструкцій NEON для 32-розрядних процесорів ARM.
- `CMAKE_ANDROID_STL_TYPE` — тип стандартної бібліотеки C++ (`c++_shared`, `c++_static` або `none`).
- `CMAKE_SYSTEM_VERSION` — цільовий рівень Android API (наприклад `21` для Android 5.0 або `33` для Android 13).

### Apple iOS та macOS

Під час крос-компіляції під iOS, tvOS чи watchOS у середовищі macOS використовують такі налаштування:

- `CMAKE_OSX_SYSROOT` — ім'я SDK (наприклад `iphoneos` для реального пристрою або `iphonesimulator` для емулятора) або абсолютний шлях до каталогу `.sdk` всередині Xcode.
- `CMAKE_OSX_ARCHITECTURES` — список цільових архітектур процесора (наприклад `arm64` для нових пристроїв Apple Silicon або `arm64;x86_64` для універсальних бінарників).

## 7. Зразкові конфігурації файлів тулчейнів

Нижче наведено два еталонні файли тулчейнів: перший — для 64-розрядного вбудованого Linux (AArch64), другий — для крос-компіляції під Windows за допомогою MinGW-w64.

### 7.1. Тулчейн для Embedded Linux (AArch64)

```cmake
# toolchain-aarch64-linux-gnu.cmake
cmake_minimum_required(VERSION 3.20)

# Ідентифікація платформи
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

# Префікс інструментів тулчейна
set(TOOLCHAIN_PREFIX "/opt/toolchains/aarch64-linux-gnu/bin/aarch64-linux-gnu-")
set(CMAKE_C_COMPILER   "${TOOLCHAIN_PREFIX}gcc")
set(CMAKE_CXX_COMPILER "${TOOLCHAIN_PREFIX}g++")
set(CMAKE_ASM_COMPILER "${TOOLCHAIN_PREFIX}gcc")

set(CMAKE_AR     "${TOOLCHAIN_PREFIX}ar"     CACHE FILEPATH "Archiver")
set(CMAKE_RANLIB "${TOOLCHAIN_PREFIX}ranlib" CACHE FILEPATH "Ranlib")
set(CMAKE_STRIP  "${TOOLCHAIN_PREFIX}strip"  CACHE FILEPATH "Strip")

# Системний корінь цільової ОС
set(CMAKE_SYSROOT "/opt/sysroots/aarch64-buildroot-linux-gnu")
set(CMAKE_FIND_ROOT_PATH "${CMAKE_SYSROOT}")

# Ізоляція пошуку
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

# Емулятор для прогону тестів CTest
set(CMAKE_CROSSCOMPILING_EMULATOR "qemu-aarch64" "-L" "${CMAKE_SYSROOT}")
```
