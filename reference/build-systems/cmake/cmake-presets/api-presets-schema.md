# 📋 Схема CMakePresets.json: структура, поля та макроси

Файли `CMakePresets.json` та `CMakeUserPresets.json` мають ідентичну внутрішню структуру та підпорядковуються єдиній специфікації JSON Schema, яка постачається разом із дистрибутивом CMake або завантажується за посиланням зі схеми. Принципова різниця між двома файлами полягає виключно у призначенні та політиці версіонування. Файл `CMakePresets.json` описує загальні командні конфігурації проєкту, фіксує обов'язкові параметри збірки та підлягає обов'язковому коміту до репозиторію Git. Натомість файл `CMakeUserPresets.json` містить індивідуальні налаштування окремого розробника, локальні шляхи до встановлених бібліотек і сторонніх тулчейнів, а тому обов'язково додається до файлу ігнорування `.gitignore`.

Будь-який коректний файл пресетів верхнього рівня є об'єктом JSON, що починається з обов'язкового оголошення версії схеми та мінімальних вимог до версії рушія:

```json
{
  "version": 8,
  "cmakeMinimumRequired": {
    "major": 3,
    "minor": 28,
    "patch": 0
  },
  "configurePresets": [],
  "buildPresets": [],
  "testPresets": [],
  "packagePresets": [],
  "workflowPresets": []
}
```

Коли утиліта `cmake` завантажує файл конфігурації, вона виконує сувору валідацію документа відповідно до оголошеної версії схеми. Якщо у файлі присутні невідомі поля, які не належать до зарезервованого словника метаданих `vendor`, або якщо типи полів не відповідають специфікації, синтаксичний аналізатор негайно перериває роботу з помилкою. Нижче наведено детальний опис усіх кореневих об'єктів, внутрішніх полів специфікації, правил успадкування та таблиць макросів.

## Кореневі поля документа та версіонування схеми

Кожен файл пресетів верхнього рівня складається з метаданих та п'яти функціональних масивів, що відповідають окремим етапам життєвого циклу програмного комплексу.

Поле `version` є обов'язковим цілим числом у діапазоні від 1 до 8. Воно повідомляє синтаксичному аналізатору, яку саме версію специфікації використано для складання конфігурації. Якщо версія документа перевищує максимальну версію схеми, яку підтримує поточний встановлений бінарний файл `cmake`, виконання негайно зупиняється. Це захищає розробника від тихих помилок ігнорування нових полів, запроваджених у новіших випусках системи.

Поле `cmakeMinimumRequired` є структурованим об'єктом із трьома цілими полями: `major`, `minor` та `patch`. Цей блок задає строгу межу сумісності. Навіть якщо версія схеми формально підтримується старим CMake, але версія самого інструмента менша за оголошену в `cmakeMinimumRequired`, робота переривається. Це дозволяє гарантувати, що проєкт не почне конфігуруватися застарілою версією рушія, в якій відсутні критично важливі команди у `CMakeLists.txt`.

Поле `include` з'явилося у схемі версії 4 і приймає масив рядків зі шляхами до додаткових файлів пресетів. Шляхи можуть бути відносними щодо каталогу поточного файлу або абсолютними. Завдяки директиві підключення великі монорепозиторії можуть розділяти монолітні конфігураційні файли на окремі логічні модулі (наприклад, окремий файл для платформних тулчейнів і окремий для тестових сценаріїв). Підключені файли обробляються рекурсивно до того, як рушій почне розв'язувати зв'язки успадкування між пресетами.

Поле `vendor` є довільним об'єктом JSON, призначеним для збереження метаданих інтегрованих середовищ розробки та сторонніх інструментів. Сам CMake повністю ігнорує вміст цього словника, однак наявність цього поля дозволяє плагінам для VS Code, Visual Studio чи CLion зберігати власні параметри (наприклад, кольорові теми чи налаштування графічного інтерфейсу) без порушення валідації суворої схеми.

Масиви `configurePresets`, `buildPresets`, `testPresets`, `packagePresets` та `workflowPresets` містять списки іменованих пресетів відповідного типу. Кожен пресет у масиві повинен мати унікальний ідентифікатор у межах свого функціонального розділу.

## Загальні поля та механіка успадкування

Усі типи пресетів у всіх п'яти категоріях спираються на однаковий базовий набір атрибутів, що визначають ідентифікацію, відображення у графічних інтерфейсах та зв'язки успадкування.

```json
{
  "name": "linux-x64-debug",
  "displayName": "Linux x64 Debug (Clang)",
  "description": "Локальна налагоджувальна збірка з адресною санітизацією",
  "hidden": false,
  "inherits": ["base-ninja", "clang-flags"],
  "condition": {
    "type": "equals",
    "lhs": "${hostSystemName}",
    "rhs": "Linux"
  }
}
```

Поле `name` є обов'язковим рядком, що слугує унікальним системним ідентифікатором пресета. Назва може містити літери латинського алфавіту, цифри, знаки дефіса та підкреслення. Саме це ім'я передається як аргумент у командному рядку під час виклику утиліт, наприклад `cmake --preset linux-x64-debug` або `ctest --preset linux-x64-debug`.

Поля `displayName` та `description` є необов'язковими інформаційними рядками. Перше містить лаконічну назву для показу у випадаючих списках та селекторах графічних середовищ розробки, а друге — розгорнутий опис для документації та контекстних підказок.

Поле `hidden` є булевим прапорцем. Якщо воно встановлене у `true`, пресет стає абстрактним шаблоном. Такий пресет приховується зі списку доступних команд утиліти командного рядка та випадаючих меню IDE, а його прямий запуск блокується. Абстрактні пресети створюються виключно для того, щоб виступати базою для поля `inherits` інших конкретних пресетів, концентруючи в собі спільні налаштування генератора, каталогів або базових змінних середовища.

Поле `inherits` визначає одне ім'я або масив імен батьківських пресетів того самого типу. Під час завантаження пресета CMake формує спрямований ациклічний граф залежностей та обчислює підсумкові властивості за чіткими правилами злиття:

1. **Скалярні значення** (наприклад, `generator`, `binaryDir`, `jobs`, `installDir`): дочірній пресет повністю перекриває значення, успадковане від батьківських пресетів. Якщо пресет успадковує кілька батьківських об'єктів одночасно, пріоритет має батько, вказаний останнім у масиві `inherits`.
2. **Словникові структури** (наприклад, `cacheVariables`, `environment`, `variables`): ключі словників поєднуються. Якщо один і той самий ключ визначено у кількох батьках, його значення береться з останнього батька в списку. Якщо ключ перевизначено у дочірньому пресеті, діє дочірнє значення. Значення `null` у дочірньому пресеті повністю вилучає відповідну змінну з підсумкового оточення.
3. **Спискові масиви** (наприклад, `targets`, `nativeToolOptions`, `generators`): дочірній список цілком замінює батьківський, якщо специфікацією поля не передбачено явного об'єднання.

Поле `condition` дозволяє вмикати або вимикати пресет залежно від динамічних умов оточення (наприклад, перевірки поточної операційної системи чи наявності змінних середовища). Якщо вираз умови обчислюється як хибний, пресет стає неактивним і поводиться так, ніби його не існує в документі.

## Пресети конфігурації (configurePresets)

Пресет конфігурації є центральним елементом усієї системи, оскільки саме він керує виконанням файлів `CMakeLists.txt` та формує модель проєкту в каталозі збірки.

```json
{
  "name": "base-ninja-release",
  "displayName": "Base Ninja Release",
  "generator": "Ninja",
  "binaryDir": "${sourceDir}/build/${presetName}",
  "installDir": "${sourceDir}/install/${presetName}",
  "toolchainFile": "${sourceDir}/cmake/toolchains/linux-clang.cmake",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "Release",
    "CMAKE_EXPORT_COMPILE_COMMANDS": {
      "type": "BOOL",
      "value": "ON"
    },
    "ENABLE_TESTING": true
  },
  "environment": {
    "CC": "clang",
    "CXX": "clang++",
    "CFLAGS": "-fcolor-diagnostics",
    "PATH": "/opt/llvm/bin:$penv{PATH}"
  },
  "warnings": {
    "dev": true,
    "deprecated": false,
    "uninitialized": true,
    "unusedCli": true
  },
  "errors": {
    "dev": false,
    "deprecated": true
  }
}
```

### Каталоги, генератор та керування тулчейнами

Поле `generator` містить рядок із точною назвою генератора CMake (наприклад, `"Ninja"`, `"Unix Makefiles"`, `"Visual Studio 17 2022"` або `"Ninja Multi-Config"`). Це поле є обов'язковим для будь-якого конкретного пресета конфігурації.

Поле `binaryDir` задає абсолютний або відносний шлях до цільового каталогу збірки, куди записуються згенеровані файли рідного збирача, проміжний кеш `CMakeCache.txt` та скомпільовані об'єктні модулі. Найкращою практикою є формування цього шляху за допомогою вбудованих макросів: `"${sourceDir}/build/${presetName}"`.

Поле `sourceDir` визначає шлях до каталогу з вихідним кодом проєкту, що містить кореневий `CMakeLists.txt`. Якщо це поле відсутнє, за замовчуванням береться каталог розташування самого файлу `CMakePresets.json`.

Поле `installDir` (запроваджене у схемі 3) задає цільовий каталог для встановлення зібраних бінарних файлів, бібліотек та заголовків. Це поле автоматично ініціалізує системну змінну `CMAKE_INSTALL_PREFIX` під час запуску конфігурації.

Поле `toolchainFile` містить шлях до файлу кросплатформного або системного тулчейна. Воно повністю замінює прапорець командного рядка `-DCMAKE_TOOLCHAIN_FILE=...` і гарантує, що тулчейн завантажується на найпершому кроці ініціалізації середовища до першого виклику команди `project()`.

Поля `architecture` та `toolset` призначені для багатоцільових генераторів Visual Studio та Xcode. Вони керують передачею прапорців `-A` (вибір архітектури, наприклад `"x64"`, `"Win32"`, `"ARM64"`) та `-T` (вибір версії набору компіляторів, наприклад `"v143"`, `"ClangCL"`). Кожне з цих полів може бути як простим рядком, так і об'єктом із полями `"value"` та `"strategy"` (де стратегія `"set"` самостійно виставляє змінні, а `"external"` очікує ініціалізації від інтегрованого середовища).

### Керування кешем та системним оточенням

Словник `cacheVariables` містить перелік змінних, які записуються до кешу проєкту `CMakeCache.txt`. Ключем запису є ім'я змінної. Значення може задаватися двома способами:
- **Скорочений запис:** простий рядок, число або булеве значення. При цьому булеве `true` автоматично перетворюється на рядок `"ON"`, а `false` — на рядок `"OFF"`.
- **Розгорнутий типізований запис:** об'єкт із полями `"type"` та `"value"`. Допустимі типи відповідають внутрішній типізації кешу CMake: `"BOOL"`, `"STRING"`, `"PATH"`, `"FILEPATH"` та `"INTERNAL"`.

Словник `environment` виставляє змінні середовища операційної системи перед запуском дочірнього процесу конфігурації. На відміну від глобальних змінних оболонки, ці значення діють локально в межах поточного запуску. Всередині рядків підтримуються макроси `$penv{<ІМ'Я>}`, що дозволяють прочитати значення батьківської змінної до того, як її модифікував поточний пресет, що є критично важливим для коректного дописування шляхів до системного `PATH`.

### Діагностика, попередження та налагодження

Блок `warnings` керує діагностичними повідомленнями під час синтаксичного розбору `CMakeLists.txt`:
- `dev`: вмикає або вимикає попередження для авторів проєктів (`-Wdev`, `-Wno-dev`).
- `deprecated`: вмикає попередження про використання застарілих команд (`-Wdeprecated`, `-Wno-deprecated`).
- `uninitialized`: попереджає про звернення до неініціалізованих змінних (`--warn-uninitialized`).
- `unusedCli`: попереджає про передані в командному рядку змінні, які не були використані у проєкті (`--warn-unused-cli`).
- `systemVars`: повідомляє про використання системних змінних (`--check-system-vars`).

Блок `errors` дозволяє трактувати певні категорії попереджень як фатальні помилки, що переривають конфігурацію:
- `dev`: зупиняє роботу при виникненні авторських попереджень (`-Werror=dev`).
- `deprecated`: перериває роботу при виявленні застарілих конструкцій (`-Werror=deprecated`).

Блок `debug` налаштовує режими глибокої діагностики: `output` друкує додаткову інформацію про розбір файлів (`--debug-output`), `tryCompile` зберігає тимчасові каталоги тестових компіляцій (`--debug-trycompile`), а `find` виводить трасування роботи команди `find_package` (`--debug-find`).

Блок `trace` (версія 5+) активує трасування виконання скриптів (`--trace`) із можливістю налаштування формату виводу (`--trace-format=json-v1`) та перенаправлення журналу у файл (`--trace-redirect`).

## Пресети збірки (buildPresets)

Пресет збірки інкапсулює параметри виклику компіляторів та лінкерів через інтерфейс `cmake --build`.

```json
{
  "name": "linux-build-app",
  "displayName": "Build Application Only",
  "configurePreset": "linux-x64-debug",
  "configuration": "Debug",
  "targets": ["app", "network_engine"],
  "jobs": 16,
  "cleanFirst": false,
  "verbose": true,
  "nativeToolOptions": ["-k", "0"],
  "environment": {
    "MAKEFLAGS": "-j16"
  }
}
```

Поле `configurePreset` є обов'язковим рядком для будь-якого неконкретного пресета збірки. Воно пов'язує пресет збірки з відповідним пресетом конфігурації. Звідти збирач отримує каталог `binaryDir`, де розташовані скомпільовані файли проєкту.

Поле `inheritConfigureEnvironment` є булевим прапорцем (за замовчуванням `true`). Воно визначає, чи повинен процес компіляції успадковувати змінні середовища, оголошені у пов'язаному `configurePreset`.

Поле `configuration` вказує ім'я цільової конфігурації для багатоконфігураційних генераторів (Visual Studio, Xcode, Ninja Multi-Config). У випадку одноконфігураційних генераторів (таких як звичайний Ninja чи Make) це поле ігнорується, оскільки тип збірки жорстко зафіксовано на фазі конфігурації через змінну `CMAKE_BUILD_TYPE`.

Поле `targets` містить одне ім'я цілі або масив рядків із назвами конкретних цілей для збірки. Якщо поле пропущено, CMake збирає псевдоціль за замовчуванням (`all` для Make/Ninja або `ALL_BUILD` для Visual Studio).

Поле `jobs` визначає граничну кількість одночасних процесів компіляції (еквівалент прапорця `--parallel` або `-j`). Якщо вказано число `0`, система автоматично обирає кількість потоків відповідно до кількості апаратних ядер процесора.

Поле `cleanFirst` при значенні `true` змушує рідний збирач виконати повне очищення дерева артефактів перед початком поточної збірки (`--clean-first`).

Поле `verbose` при значенні `true` вмикає докладний вивід командного рядка компіляторів та лінкерів у термінал (`--verbose`).

Поле `nativeToolOptions` містить масив додаткових аргументів, які без змін передаються безпосередньо утиліті збірки (Ninja, Make, MSBuild) після розділювача `--`.

## Пресети тестування (testPresets)

Пресет тестування налаштовує параметри автоматичного прогону тестів за допомогою утиліти `ctest --preset <name>`.

```json
{
  "name": "quick-unit-tests",
  "displayName": "Run Fast Unit Tests",
  "configurePreset": "linux-x64-debug",
  "configuration": "Debug",
  "filter": {
    "include": {
      "label": "unit"
    },
    "exclude": {
      "name": "slow_network_test"
    }
  },
  "execution": {
    "stopOnFailure": true,
    "jobs": 8,
    "timeout": 30,
    "repeat": {
      "mode": "until-pass",
      "count": 3
    }
  },
  "output": {
    "outputOnFailure": true,
    "verbosity": "default"
  }
}
```

### Фільтрація тестів (filter)

Блок `filter` керує складом тестової вибірки. Він підтримує дві симетричні секції: `include` (вибірка тестів, які слід виконати) та `exclude` (вибірка тестів, які необхідно виключити з прогону):
- `name`: регулярний вираз для зіставлення з назвами тестів (еквівалент прапорців `-R` та `-E` у CTest).
- `label`: регулярний вираз для фільтрації за користувацькими мітками тестів, встановленими властивістю цілі `LABELS` (еквівалент `-L` та `-LE`).
- `useRegEx`: булевий прапорець, що визначає, чи слід інтерпретувати рядкові патерни як регулярні вирази.
- `index`: фільтрація за порядковими номерами тестів із можливістю задавати початковий індекс `start`, кінцевий `end`, крок `stride` або явний список номерів `specificTests`.

### Режими виконання (execution)

Блок `execution` визначає правила прогону та обмеження ресурсів:
- `jobs`: кількість паралельних потоків виконання тестів (`-j`).
- `stopOnFailure`: негайне припинення всього прогону після першого падіння тесту (`--stop-on-failure`).
- `timeout`: індивідуальний таймаут для кожного тесту у секундах. Якщо тест не завершується за цей час, CTest примусово завершує його процес.
- `repeat`: об'єкт повторного запуску флакаючих тестів. Поле `mode` приймає значення `"until-fail"` (повторювати, доки не впаде), `"until-pass"` (повторювати, доки не пройде успішно) або `"after-timeout"` (повторювати лише у разі перевищення ліміту часу); поле `count` задає максимальну кількість спроб.
- `resourceSpecFile`: шлях до файлу специфікації апаратних ресурсів для ізоляції доступу тестів до конкретних ядер чи графічних прискорювачів GPU.
- `noTestsAction`: поведінка CTest у ситуації, коли жоден тест не підійшов під фільтри (`"default"`, `"error"` або `"ignore"`).

### Журналювання та вивід (output)

Блок `output` налаштовує деталізацію консольних звітів:
- `outputOnFailure`: автоматично друкує повний стандартний вивід та потік помилок тесту, якщо він завершився аварійно (`--output-on-failure`).
- `verbosity`: встановлює ступінь деталізації виводу: `"default"`, `"verbose"` (`-V`) або `"extra"` (`-VV`).
- `outputJUnitFile`: генерує звіт про проходження тестового набору у стандартному форматі XML JUnit (версія 6+), що забезпечує пряму інтеграцію з панелями моніторингу серверів CI.

## Пресети пакування (packagePresets)

Пресет пакування керує створенням релізних дистрибутивів проєкту за допомогою утиліти `cpack --preset <name>`.

```json
{
  "name": "release-deb-package",
  "displayName": "Debian Package for Release",
  "configurePreset": "linux-x64-release",
  "generators": ["DEB", "TGZ"],
  "configurations": ["Release"],
  "packageDirectory": "${sourceDir}/dist",
  "packageName": "my-project-linux-x64",
  "packageVersion": "1.4.0",
  "variables": {
    "CPACK_DEBIAN_PACKAGE_MAINTAINER": "DevOps Team <devops@example.com>",
    "CPACK_DEBIAN_PACKAGE_SECTION": "devel"
  }
}
```

Поле `configurePreset` обов'язково пов'язує пресет пакування з вихідним пресетом конфігурації.

Поле `generators` містить масив імен генераторів пакувальника CPack, наприклад `["TGZ", "ZIP", "DEB", "RPM", "NSIS", "WIX", "DragNDrop"]`.

Поле `packageDirectory` задає цільовий каталог на файловій системі, куди складаються сформовані інсталятори та архіви.

Поля `packageName` та `packageVersion` перевизначають базову назву та версію створюваного пакета без необхідності змінювати глобальні змінні у файлах `CMakeLists.txt`.

Словник `variables` дозволяє декларативно виставити внутрішні змінні CPack (наприклад, `CPACK_DEBIAN_PACKAGE_MAINTAINER` чи `CPACK_RESOURCE_FILE_LICENSE`).

## Пресети робочих процесів (workflowPresets)

Пресет робочого процесу об'єднує повний життєвий цикл розробки в один атомарний сценарій, який виконується командою `cmake --workflow --preset <name>`.

```json
{
  "name": "ci-pipeline",
  "displayName": "Full CI Validation Pipeline",
  "steps": [
    {
      "type": "configure",
      "name": "linux-x64-release"
    },
    {
      "type": "build",
      "name": "linux-build-app"
    },
    {
      "type": "test",
      "name": "quick-unit-tests"
    },
    {
      "type": "package",
      "name": "release-deb-package"
    }
  ]
}
```

Масив `steps` визначає послідовність кроків. Першим елементом масиву обов'язково має бути крок із типом `"configure"`. Наступні кроки мають тип `"build"`, `"test"` або `"package"` і виконуються строго у порядку їхнього слідування в списку. Кожен крок посилається на ім'я відповідного пресета через поле `name`. Якщо будь-який крок конвеєра зазнає невдачі, виконання ланцюжка негайно припиняється, а утиліта повертає ненульовий код статусу аварійного кроку.

## Таблиця макросів заміни

Усі рядкові поля документа підтримують набір динамічних макросів, що обчислюються під час розбору файлу:

| Макрос | Контекст розкриття | Приклад обчисленого значення |
| :--- | :--- | :--- |
| `${sourceDir}` | Абсолютний шлях до каталогу з головним `CMakeLists.txt`. | `/home/developer/projects/app` |
| `${sourceParentDir}` | Абсолютний шлях до батьківського каталогу вихідного дерева. | `/home/developer/projects` |
| `${sourceDirName}` | Ім'я каталогу вихідного дерева без шляху. | `app` |
| `${presetName}` | Назва пресета, який зараз обробляється синтаксичним аналізатором. | `linux-x64-debug` |
| `${generator}` | Назва генератора, зазначена у поточному або успадкованому пресеті. | `Ninja` |
| `${hostSystemName}` | Назва хостової операційної системи (`Linux`, `Windows`, `Darwin`). | `Linux` |
| `${fileDir}` | Каталог, у якому фізично розташований поточний JSON-файл (версія 4+). | `/home/developer/projects/app` |
| `${dollar}` | Літеральний символ долара `$`. Використовується для екранування від підстановки. | `$` |
| `$env{<ІМ'Я>}` | Значення змінної середовища поточної сесії операційної системи. | `/usr/local/bin` |
| `$penv{<ІМ'Я>}` | Значення батьківської змінної середовища до будь-яких змін полем `environment`. | `/usr/bin:/bin` |

## Синтаксис логічних умов (condition)

У схемі версії 8 активація будь-якого пресета може обмежуватися структурованими логічними умовами:

```json
{
  "condition": {
    "type": "allOf",
    "conditions": [
      {
        "type": "equals",
        "lhs": "${hostSystemName}",
        "rhs": "Linux"
      },
      {
        "type": "notEquals",
        "lhs": "$env{CI}",
        "rhs": ""
      }
    ]
  }
}
```

Доступні такі типи логічних блоків:
- `equals` / `notEquals`: перевірка двох рядків `lhs` та `rhs` на точний збіг або відмінність.
- `inList` / `notInList`: перевірка входження рядка `string` до масиву рядків `list`.
- `matches` / `notMatches`: перевірка відповідності рядка `string` регулярному виразу `regex`.
- `anyOf`: логічна диз'юнкція (АБО) над списком вкладених умов у масиві `conditions`.
- `allOf`: логічна кон'юнкція (І) над списком вкладених умов у масиві `conditions`.
- `not`: логічне інвертування (НІ) вкладеної умови в полі `condition`.
- `hostOperatingSystem`: спрощена перевірка хостової платформи через список назв операційних систем у масиві `values` (наприклад, `["Windows", "Linux"]`).

## Матриця версій схем CMakePresets
