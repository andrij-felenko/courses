# 📋 Сигнатури та параметри власних команд і цілей CMake

Команди `add_custom_command` та `add_custom_target` складають ядро розширення декларативного графа збірки CMake довільними зовнішніми інструментами, генераторами джерел, компіляторами мов специфікацій та утилітами пакування бінарників. Без них неможливо підключити жоден сторонній інструмент — від транслятора Protocol Buffers до утиліти підпису коду чи розрахунку контрольних сум. Ця довідка містить вичерпний опис інтерфейсу, сигнатур, параметрів і властивостей, що керують поведінкою власних команд у всіх підтримуваних генераторах CMake.

---

## 1. Генерація файлів: add_custom_command(OUTPUT ...)

Ця форма команди створює файловий вузол у графі залежностей. Вона не є окремою іменованою ціллю; це низькорівневе декларативне правило, яке вказує системі збірки, як із набору вхідних файлів або цілей отримати один чи кілька вихідних дискових файлів.

```cmake
add_custom_command(
    OUTPUT output1 [output2 ...]
    COMMAND command1 [ARGS] [args1...]
    [COMMAND command2 [ARGS] [args2...]]
    [MAIN_DEPENDENCY depend]
    [DEPENDS [depends...]]
    [BYPRODUCTS [files...]]
    [IMPLICIT_DEPENDS <lang1> <file1> [<lang2> <file2>...]]
    [WORKING_DIRECTORY dir]
    [COMMENT comment]
    [DEPFILE depfile]
    [JOB_POOL pool]
    [VERBATIM]
    [APPEND]
    [USES_TERMINAL]
    [COMMAND_EXPAND_LISTS]
)
```

### Детальний опис параметрів

#### OUTPUT output1 [output2 ...]
Обов'язковий список файлів, які гарантовано створюються або оновлюються внаслідок виконання вказаних команд. Шляхи можуть бути абсолютними або відносними. Якщо вказано відносний шлях, CMake автоматично розгортає його відносно поточного каталогу збірки `CMAKE_CURRENT_BINARY_DIR`.

Кожен файл, зазначений у секції `OUTPUT`, автоматично маркується внутрішньою властивістю джерела `GENERATED = 1`. Завдяки цьому CMake дозволяє додавати ці файли до списків джерел цілей (`target_sources`), навіть якщо на момент конфігурації файлів ще немає на диску.

Якщо вказано кілька вихідних файлів (`OUTPUT a.cpp a.hpp`), CMake створює єдине правило збірки з множинним виходом. У генераторі Ninja це перетворюється на правило з кількома вихідними вузлами, що гарантує виконання команди рівно один раз для всієї групи файлів.

#### COMMAND command1 [ARGS] [args1...]
Виконувана програма та її позиційні аргументи. Якщо вказано кілька блоків `COMMAND`, вони виконуються послідовно в тому порядку, у якому вони записані. Якщо хоча б одна команда завершується з ненульовим кодом повернення, весь ланцюг негайно переривається, а система збірки фіксує помилку.

Значенням `command` може бути:
- Ім'я виконуваної цілі CMake, створеної через `add_executable()` у цьому ж проєкті або підпроєкті. CMake автоматично підставить правильний шлях до скомпільованого бінарника.
- Генераторний вираз, наприклад `$<TARGET_FILE:my_tool>`.
- Абсолютний шлях до системної утиліти або скрипту, отриманий через `find_program()`.
- Назва системної утиліти з системного шляху `PATH` (наприклад, `python3`, `git`, `bison`).

#### MAIN_DEPENDENCY depend
Спеціальний параметр для інтеграції з IDE. Він визначає головний вхідний файл, який відображається у дереві рішень Visual Studio (Solution Explorer). У генераторах Makefile та Ninja цей параметр трактується як звичайний перший елемент списку `DEPENDS`.

#### DEPENDS [depends...]
Список дискових файлів або іменованих цілей CMake, від яких залежить виконання команди:
- **Якщо елемент є файлом**: система збірки порівнює його мітку часу модифікації `mtime` із міткою найстарішого файлу з `OUTPUT`. Якщо будь-який файл із `DEPENDS` новіший за `OUTPUT`, або якщо файли `OUTPUT` відсутні, команда запускається.
- **Якщо елемент є CMake-ціллю**: команда виконується лише після того, як вказана ціль буде повністю скомпільована та злінкована. Більше того, якщо змінюється будь-який вихідний файл цієї цілі, кастомна команда автоматично перевиконується.

#### BYPRODUCTS [files...]
Список допоміжних або побічних файлів, які створюються командою під час виконання, але не є її основними виходами. Цей параметр додано для генератора Ninja.

Ninja вимагає, щоб усі файли, які з'являються на диску внаслідок роботи правил, були задекларовані. Якщо команда створює неоголошений файл, це може призвести до проблем із паралелізмом, помилок виявлення застарілих файлів та залишків сміття при очищенні проєкту. Файли з `BYPRODUCTS` автоматично очищаються командою `ninja clean`.

#### DEPFILE depfile
Шлях до файлу залежностей у форматі Makefile syntax (`output.cpp: input.dsl type.dsl`). Призначений для підтримки динамічних неявних залежностей, коли кодогенератор сам виявляє вкладені директиви імпорту під час обробки схеми. Підтримується в Ninja з CMake 3.7+ та у генераторах Makefile з CMake 3.20+.

#### JOB_POOL pool
Призначає виконання кастомної команди до конкретного іменованого пулу обмеження паралелізму Ninja. Якщо утиліта кодогенерації споживає гігабайти оперативної пам'яті, призначення її до пулу з `JOB_POOLS memory_heavy_pool=2` запобігає вичерпанню пам'яті комп'ютера при паралельній збірці `ninja -j32`.

#### VERBATIM
Критично важливий прапорець безпеки. Наказує CMake коректно та автоматично екранувати всі аргументи командного рядка під синтаксис поточної операційної системи та командного інтерпретатора (`cmd.exe`, `/bin/sh` або прямий виклик API створення процесів). Без цього прапорця лапки, пробіли у шляхах та спеціальні символи не екрануються, викликаючи помилки збірки на інших платформах.

#### COMMAND_EXPAND_LISTS
Вмикає коректне розгортання списків CMake (значень із роздільником `;`) всередині генераторних виразів. Наприклад, вираз `$<TARGET_PROPERTY:tgt,INCLUDE_DIRECTORIES>` за замовчуванням підставляється як один суцільний рядок із крапками з комою. Із цим прапорцем CMake перетворює кожен елемент списку на окремий аргумент командного рядка.

#### WORKING_DIRECTORY dir
Каталог, який встановлюється поточним робочим каталогом на час виконання процесу. Якщо параметр не задано, за замовчуванням використовується `CMAKE_CURRENT_BINARY_DIR`.

## 2. Хуки цілей: add_custom_command(TARGET ...)

Ця сигнатура прив'язує команду до життєвого циклу вже наявної цілі. Вона не створює нових файлових вузлів у дереві залежностей і спрацьовує на фіксованих фазах компіляції цієї цілі.

```cmake
add_custom_command(
    TARGET target
    PRE_BUILD | PRE_LINK | POST_BUILD
    COMMAND command1 [ARGS] [args1...]
    [COMMAND command2 [ARGS] [args2...]]
    [BYPRODUCTS [files...]]
    [WORKING_DIRECTORY dir]
    [COMMENT comment]
    [VERBATIM]
    [USES_TERMINAL]
    [COMMAND_EXPAND_LISTS]
)
```

### Стадії прив'язки

1. **`PRE_BUILD`**:
   - Має виконуватися до того, як скомпілюється будь-який об'єктний файл цілі.
   - Повноцінно працює лише у генераторі Visual Studio.
   - У генераторах Ninja та Makefiles через обмеження моделей рушіїв трактується як `PRE_LINK`. Не придатна для створення заголовків або джерел.

2. **`PRE_LINK`**:
   - Виконується після компіляції всіх `.cpp`/`.c` файлів цілі в об'єктні файли `.o`/`.obj`, але безпосередньо перед викликом лінкера.
   - Застосовується для генерації файлів таблиць експорту, валідації об'єктних секцій та вбудовування ресурсів.

3. **`POST_BUILD`**:
   - Виконується після успішного лінкування та запису фінального бінарного файлу на диск.
   - Застосовується для конвертації форматів (`objcopy` у `.bin`/`.hex`), цифрового підпису виконуваних файлів, аналізу розмірів секцій та копіювання динамічних бібліотек.

## 3. Фіктивні цілі: add_custom_target()

Створює іменовану службову ціль найвищого рівня. Така ціль не виробляє дискового артефакту з тим самим іменем, тому вважається завжди застарілою і виконує свої команди при кожному запуску.

```cmake
add_custom_target(
    Name [ALL]
    [COMMAND command1 [ARGS] [args1...]]
    [COMMAND command2 [ARGS] [args2...]]
    [DEPENDS depend1 [depend2 ...]]
    [BYPRODUCTS [files...]]
    [WORKING_DIRECTORY dir]
    [COMMENT comment]
    [VERBATIM]
    [USES_TERMINAL]
    [COMMAND_EXPAND_LISTS]
    [SOURCES src1 [src2...]]
)
```

### Параметри add_custom_target

- `Name`: унікальне глобальне ім'я цілі в усьому дереві CMake. Дозволяє викликати ціль напряму через `cmake --build . --target Name` або `ninja Name`.
- `ALL`: якщо вказано, ціль автоматично додається до цілі за замовчуванням і виконується при кожному звичайному запуску збірки. Якщо прапорець відсутній, ціль запускається лише за явної вимоги розробника або залежності іншої цілі.
- `DEPENDS`: список файлів або інших цілей. Якщо елемент списку є файлом, створеним через `add_custom_command(OUTPUT ...)`, виклик кастомної цілі змусить CMake перевірити актуальність і виконати відповідну команду генерації файлу.
- `SOURCES`: список допоміжних вихідних файлів, які не беруть участі у збірці, але повинні відображатися в ієрархічному дереві файлів усередині IDE (Visual Studio Solution Explorer, Xcode, CLion).

## 4. Властивості файлів джерел (Source File Properties)

CMake надає механізм керування файлами через їхні властивості:

### GENERATED
Булева властивість джерела. Повідомляє CMake, що файл створюється під час збірки і його відсутність на диску під час фази конфігурації не є помилкою. Усі файли з секції `OUTPUT` команди `add_custom_command` отримують цю властивість автоматично. Встановлення вручну:
```cmake
set_source_files_properties(generated.cpp PROPERTIES GENERATED TRUE)
```

### OBJECT_DEPENDS
Дозволяє вказати список додаткових файлів, від яких залежить компіляція конкретного об'єктного файлу. Якщо будь-який із цих файлів змінюється, об'єктний файл компілюється заново, навіть якщо сам вихідний файл `.cpp` не містить прямого включення `#include`.

## 5. Зведена матриця сумісності генераторів

| Можливість / Генератор | Ninja | Unix Makefiles | Visual Studio (MSVC) | Xcode |
| :--- | :---: | :---: | :---: | :---: |
| `OUTPUT` + `DEPENDS` | Так | Так | Так | Так |
| `VERBATIM` | Так | Так | Так | Так |
| `DEPFILE` | Так (3.7+) | Так (3.20+) | Ні | Ні |
| `BYPRODUCTS` | Обов'язково | Ігнорується | Ігнорується | Ігнорується |
| `JOB_POOL` | Так (3.0+) | Ігнорується | Ігнорується | Ігнорується |
| `USES_TERMINAL` | Так | Ігнорується | Ігнорується | Ігнорується |
| `COMMAND_EXPAND_LISTS` | Так (3.12+) | Так (3.12+) | Так (3.12+) | Так (3.12+) |
| `PRE_BUILD` у TARGET | Як `PRE_LINK` | Як `PRE_LINK` | До компіляції | Як `PRE_LINK` |
