# 📜 Еволюція Conan: від скриптів збірки до суворої моделі 2.0

Світ мов програмування C та C++ понад три десятиліття розвивався без загальноприйнятого, стандартизованого менеджера пакетів. У той час як екосистеми Java (Maven, Gradle), JavaScript (npm), Rust (Cargo) та Python (pip/PyPI) оперували централізованими реєстрами з єдиним стандартизованим рантаймом, розробники на C++ були змушені керувати стороннім кодом вручну.

Основними інструментами інтеграції чужого коду довгий час залишалися завантаження архівів вихідного коду безпосередньо в дерево проєкту, підключення сторонніх сховищ через механізм Git Submodules або спроби використовувати системні пакувальники дистрибутивів Linux (APT, RPM, Pacman).

Проте системні пакувальники операційних систем принципово не розв'язували задачу управління C++-залежностями: вони постачали рівно одну версію бібліотеки, скомпільовану рівно одним системним компілятором із фіксованим набором прапорців дистрибутива. Будь-яка спроба зібрати застосунок новішою версією GCC, увімкнути прапорці санітайзерів пам'яті AddressSanitizer, змінити рівень оптимізації або скомпілювати проєкт під платформу Windows компілятором MSVC призводила до несумісності двійкового інтерфейсу прикладних програм (ABI) та фатальних збоїв компонування.

## Поява Conan та перші роки (2015–2018)

У 2014–2015 роках у C++-спільноті виникло кілька незалежних ініціатив: проєкт Biicode намагався будувати керування залежностями на рівні окремих файлів вихідного коду (але збанкрутував через надмірну централізацію сервісу), з'явився проєкт Hunter на базі чистих скриптів CMake, а компанія Microsoft розпочала розробку власного каталогу портів vcpkg.

У 2015 році іспанські інженери Дієго Родрігес-Лосада (Diego Rodriguez-Losada) та Луїс Мартінес де Бартоломе (Luis Martínez de Bartolomé) заснували проєкт Conan. Їхня ключова архітектурна ідея базувалася на двох принципах:
1. Рецепт пакета є повноцінною програмою мовою Python, що дозволяє виконувати будь-яку довільну логіку конфігурації платформи та викликати будь-які наявні системи збірки (CMake, Visual Studio, Autotools, Makefiles, Meson).
2. Кожен скомпільований бінарний артефакт однозначно ідентифікується детермінованим хешем (`package_id`), що обчислюється на основі операційної системи, архітектури процесора, версії компілятора, стандарту мови C++ та прапорців оптимізації.

Уперше концепцію було публічно представлено на міжнародній конференції CppCon 2015. Демонстрація можливості встановити важку графічну бібліотеку з усіма залежностями за кілька секунд без компіляції викликала значний резонанс в індустрії.

У 2016 році стартап придбала компанія JFrog. Завдяки значним інвестиціям та прямій інтеграції з корпоративним репозиторієм артефактів JFrog Artifactory Conan швидко перетворився на стандарт де-факто для великих інженерних корпорацій у галузях автомобільної електроніки (Automotive: BMW, Continental, Mercedes-Benz), робототехніки, ігрової індустрії (Sony PlayStation, Electronic Arts, Ubisoft) та аерокосмічних систем.

У 2018 році відбувся реліз версії Conan 1.0. Менеджер пакетів довів практичну життєздатність концепції децентралізованого бінарного кешування, проте перший мажорний реліз ніс у собі суттєвий тягар архітектурних компромісів раннього етапу розвитку.

## Архітектурний борг версії 1.x

Широка експлуатація Conan 1.x у масштабних виробничих конвеєрах виявила системні обмеження, закладені в початковий дизайн:

1. **Однопрофільна модель за замовчуванням.** У Conan 1.x за замовчуванням використовувався один профіль збірки. Під час крос-компіляції інструменти кодогенерації (наприклад, генератор коду протобуферів `protoc`, компілятор асемблера `nasm` або генератор парсерів `bison`) помилково компілювалися під цільову архітектуру (ARM), через що хост-машина компіляції (x86_64) не могла їх запустити. Інженери були змушені писати заплутані скрипти-милиці або вручну перевизначати системні змінні.
2. **Забруднення файлів `CMakeLists.txt`.** Перші версії вимагали явного включення спеціальних макросів Conan безпосередньо у вихідний код збірки проєкту: `include(${CMAKE_BINARY_DIR}/conanbuildinfo.cmake)` та виклику `conan_basic_setup()`. Це порушувало принцип чистоти системи збірки: проєкт ставав нездатним скомпілюватися без попереднього запуску клієнта Conan, що створювало бар'єр для контриб'юторів відкритого коду.
3. **Глобальні мутації стану.** Рецепти версії 1.x могли довільно змінювати глобальні змінні оточення операційної системи під час виконання своїх методів. Це призводило до непередбачуваної поведінки та плаваючих помилок збірки залежно від випадкового порядку обходу вузлів графа залежностей.
4. **Відсутність концепції Layout.** Рецепти вручну вгадували відносні шляхи до каталогів вихідного коду та проміжної збірки, через що використання пакетів у режимі прямої паралельної розробки (editable mode) було надзвичайно крихким і часто вимагало ручного копіювання заголовків.

## Переосмислення: реліз Conan 2.0 (2023)

У 2019 році команда розробників Conan спільно з інженерною спільнотою (Conan 2.0 Tribe) розпочала масштабну роботу над повною перебудовою внутрішньої архітектури. Цей процес тривав майже чотири роки і завершився офіційним випуском Conan 2.0 у лютому 2023 року.

Реліз 2.0 став рішучим розривом зі зворотною сумісністю заради досягнення суворої математичної чистоти графа:
- **Обов'язкова двопрофільна модель:** розділення контекстів `--profile:build` (інструменти збірки) та `--profile:host` (цільові бібліотеки) стало непорушним правилом для абсолютно всіх операцій збірки та інсталяції.
- **Стандартизована просторова розмітка Layout:** метод `layout()` та помічник `cmake_layout()` чітко розмежували простори джерел, проміжної компіляції, згенерованих конфігурацій та кінцевих артефактів, забезпечивши прозору роботу механізму `conan editable`.
- **Безшовна інтеграція з Modern CMake:** інструменти `CMakeToolchain` та `CMakeDeps` повністю прибрали будь-який код Conan із файлів `CMakeLists.txt`, зробивши стандартом офіційні імпортовані цілі `find_package(Pkg CONFIG)` та декларативні файли `CMakePresets.json`.
- **Криптографічна незмінність артефактів:** кожна модифікація рецепта (Recipe Revision, RREV) та кожного бінарного пакета (Package Revision, PREV) отримала унікальний SHA-1 хеш, що разом із механізмом `conan.lock` унеможливило випадковий дрейф залежностей у виробничих конвеєрах неперервної інтеграції.
