Веб-сервер під час раптового сплеску відвідувачів починає масово відхиляти нові TCP-з'єднання з помилкою `Connection refused`, хоча навантаження на процесор та оперативну пам'ять не перевищує і десяти відсотків. Причина полягає у тому, що черга незведених сокетів `net.core.somaxconn` у ядрі за замовчуванням обмежена числом 4096. Якщо програма не встигає підхопити нові з'єднання з черги accept, ядро Linux просто відкидає нові пакети SYN. Зміна цього єдиного числа у працюючому ядрі без перезавантаження всієї машини вирішує проблему за частку секунди.

Ця ситуація ілюструє фундаментальну потребу системного програмування: ядро операційної системи містить тисячі внутрішніх змінних, що контролюють розміри буферів, ліміти ресурсів, алгоритми планивальника та рівні безпеки. Перекомпіляція ядра чи навіть його перезавантаження із новими параметрами командного рядка (*kernel boot command line*) для зміни одного числа є надто дорогою операцією. Операційній системі потрібен спеціальний інтерфейс динамічної конфігурації, який дозволяє читати та модифікувати змінні ядра «на ходу» — без зупинки системних процесів. У Linux цим механізмом є підсистема `sysctl` та її віртуальне файлове дерево `/proc/sys`.

## Проблема динамічного керування ядром

Звичайні програми отримують налаштування через файли конфігурації або аргументи командного рядка під час запуску. Для ядра Linux ситуація значно складніша, оскільки воно працює в окремому привілейованому режимі процесора (*ring 0*) і його пам'ять повністю захищена від прямого доступу з простору користувача (*userspace*). Усі таблиці сторінок пам'яті (*page tables*) позначено прапорцем захисту від запису для невідокремленого коду, тому жоден процес у просторі користувача не може напряму змінити змінну в RAM ядра через звичайні вказівники.

Історично в системному програмуванні існувало три рівні конфігурації ядра:

1. **Статична конфігурація при компіляції (`.config`).** Визначає, які підсистеми взагалі вбудовуються у бінарний образ ядра `vmlinuz`, а які збираються у вигляді динамічних модулів (`.ko`). Зміна цих параметрів вимагає повної перекомпіляції ядра та повторного монтування підсистем.
2. **Параметри завантаження (`kernel command line`).** Передаються завантажувачем (наприклад, GRUB, U-Boot або systemd-boot) під час старту системи. Вони ідеальні для конфігурації ранніх етапів ініціалізації (наприклад, `root=`, `init=`, `console=`, `mem=`), але зміна будь-якого параметра вимагає перезавантаження всієї машини.
3. **Динамічний тюнінг під час виконання (*runtime tuning*).** Дозволяє модифікувати параметри працюючого ядра у будь-який момент через оголошені системні інтерфейси без зупинки системних процесів.

Для забезпечення динамічного тюнінгу ядро Linux експортує внутрішні змінні через інтерфейс `sysctl` (від англ. *system control* — керування системою).

## Розподіл ролей між /proc/sys, /proc та /sys

У сучасних дистрибутивах Linux простір користувача взаємодіє з ядром через кілька віртуальних файлових систем (*pseudo-filesystems*). Оскільки всі вони монтуються як звичайні каталоги, їх нерідко плутають.

![Розподіл ролей між /proc/sys, /proc та /sys](/reference/unix-linux/proc/sysctl-kernel-tuning-interface/img/proc-vs-sysfs.svg)
*Призначення та формат даних трьох віртуальних файлових систем Linux.*

Кожна з цих псевдо-ФС має свою чітку спеціалізацію у структурі операційної системи:

- **`procfs` (`/proc` без піддерева `/proc/sys`):** Історично виникла у 8-й редакції Research Unix для відображення процесів у вигляді файлів (`/proc/[pid]/`). Згодом розрослася статистикою системи: файли `/proc/meminfo`, `/proc/cpuinfo`, `/proc/stat`, `/proc/interrupts` генерують багаторадкові текстові звіти про стан ресурсів. Драйвер `procfs` породжує вміст цих файлів динамічно під час виклику `read()` за допомогою внутрішнього механізму `seq_file`.
- **`sysfs` (`/sys`):** З'явилася у Linux 2.6 для відображення об'єктної моделі пристроїв ядра (*kernel device model*). Вона має суворий канон ієрархії `kobject`: кожен файл містить лише один атрибут пристрою, драйвера чи шини (наприклад, `/sys/block/sda/size` або `/sys/class/net/eth0/mtu`). Файли в `sysfs` відображають топологію шин PCI, USB, пристроїв та контролерів cgroups v2.
- **`sysctl` (`/proc/sys`):** Спеціалізоване піддерево всередині `procfs`, яке слугує виключно для читання та запису налаштовних параметрів ядра. На відміну від решти `/proc`, файли у `/proc/sys` майже завжди відкриті як для читання, так і для запису (`0644` або `0600`), а кожному файлу відповідає конкретна змінна або масив змінних у пам'яті ядра.

## Внутрішня архітектура sysctl та реєстрація в VFS

З точки зору простору користувача, параметр `sysctl` — це звичайний файл у файловій системі. Проте за цим файлом не стоїть жодного дискового блоку чи inode на фізичному носії.

Коли програма викликає системний виклик `open("/proc/sys/net/ipv4/ip_forward", O_WRONLY)`, віртуальна файлова система VFS (*Virtual File System*) звертається до обробника файлової системи `procfs`. Драйвер `procfs` шукає відповідний вузол у внутрішньому дереві реєстрації `sysctl`.

![Архітектура sysctl](/reference/unix-linux/proc/sysctl-kernel-tuning-interface/img/sysctl-architecture.svg)
*Проходження запиту від простору користувача крізь VFS до обробника ctl_table та змінної ядра.*

Кожна підсистема ядра розкриває свої параметри через масив структур `struct ctl_table`. У цій структурі вказується:
- Ім'я файлу в VFS (`procname`).
- Указник на змінну в RAM ядра (`data`).
- Максимальний розмір даних у байтах (`maxlen`).
- Права доступу VFS (`mode`).
- Спеціальна функція-обробник (`proc_handler`), яка викликається при читанні або записі.

Коли програма записує рядок `"1"` у файл `/proc/sys/net/ipv4/ip_forward`, VFS виконує наступну послідовність дій:

1. Системний виклик `write()` переходить у функцію VFS `vfs_write()`.
2. VFS перевіряє права доступу користувача за прапорцями POSIX та структурою `struct cred` поточного процесу.
3. Управління передається обробнику `proc_sys_write()`, який знаходить відповідний вузол у структурі `ctl_table_header`.
4. Обробник `proc_sys_write()` викликає конкретну функцію `proc_handler` (у даному випадку стандартну функцію ядра `proc_dointvec`).
5. Функція `proc_dointvec` копіює рядок з буфера користувача через `copy_from_user()`, перетворює ASCII-рядок `"1"` у ціле число `1`, перевіряє межі значення та атомарно оновлює змінну `sysctl_net_ipv4_ipv4_forward` у пам'яті ядра.

Детальний аналіз того, як виникала ця архітектура і чому Linux відмовився від старого двійкового системного виклику `sysctl(2)` з BSD, розкрито в [історії переходу від системного виклику sysctl(2) до рядкового інтерфейсу /proc/sys](book:unix-linux/sysctl-kernel-tuning-interface/hist-sysctl-evolution.md).

## Ієрархія каталогів /proc/sys

Піддерево `/proc/sys` впорядковане за функціональними підсистемами ядра. Кожен каталог відображає окрему частину ядра Linux.

### 1. `/proc/sys/kernel/` — загальносистемні параметри ядра

Цей каталог містить важелі керування базовими механізмами ядра: планувальником задач, сигналами, механізмами IPC, логуванням та безпекою.

- `kernel.pid_max`: Максимальне значення PID процесів у системі. На 64-бітних системах за замовчуванням дорівнює `4194304` (2²²), але на старих 32-бітних системах обмежувалося значенням `32768`. При досягненні цього ліміту ядро закочує лічильник PID назад до малого числа, пропускаючи вже зайняті ідентифікатори.
- `kernel.threads-max`: Загальносистемна стеля кількості потоків виконання (*kernel threads*), яку ядро здатне створити з урахуванням обсягу фізичної оперативної пам'яті.
- `kernel.sysrq`: Керує доступними комбінаціями Magic SysRq для екстреного відновлення ядра при збоях. Значення `0` повністю вимикає SysRq, `1` дозволяє всі команди, а бітова маска (наприклад, `176`) відкриває лише безпечні операції (скидання дискового кешу, перемонтування у read-only, завершення процесів).
- `kernel.random.entropy_avail`: Зчитує поточний рівень ентропії у пулі генератора випадкових чисел ядра (в оцінці біт).
- `kernel.random.boot_id`: Видає унікальний псевдовипадковий UUID, який генерується ядром один раз під час завантаження системи і залишається незмінним до перезавантаження.
- `kernel.unprivileged_bpf_disabled`: Забороняє непривілейованим користувачам завантажувати eBPF-програми у ядро (значення `1` або `2`). Це один із найважливіших важелів безпеки сучасного ядра для запобігання атак типу Spectre та побочних каналів пам'яті.
- `kernel.kptr_restrict`: Захисний важіль, що приховує реальні вказівники на адреси ядра у `/proc/kallsyms` та файлах простеження від звичайних користувачів. Значення `1` приховує адреси для всіх користувачів без `CAP_SYSLOG`, а значення `2` повністю зануляє адреси незалежно від привілеїв.
- `kernel.core_pattern`: Шаблон форми іменування та шляху для дампів пам'яті (*core dumps*). Якщо рядок починається із символу пайпа `|`, ядро не створює файл на диску, а запускає вказану програму (наприклад, `systemd-coredump`) і передає їй вміст пам'яті падаючого процесу через `stdin`.
- `kernel.tainted`: Бітова маска плям ядра (*kernel taint flags*). Показує десятковим числом, чи завантажувалися у ядро закриті пропрієтарні драйвери, чи відбувалися апаратні помилки CPU/RAM, або чи ставив мітку адміністратор вручну.

### 2. `/proc/sys/vm/` — керування віртуальною пам'яттю

Розділ `vm` (*Virtual Memory*) відповідає за роботу підсистеми підкачки, кешування сторінок, виділення пам'яті та скидання даних на фізичні носії.

- `vm.swappiness`: Визначає відносну вагу витіснення анонімних сторінок пам'яті у поділ swap порівняно зі звільненням файлового кешу. Значення варіюється від `0` (максимальне утримання сторінок у RAM) до `200` (агресивний swap). Значення `100` означає рівну вагу файлового та анонімного витіснення.
- `vm.dirty_ratio` та `vm.dirty_background_ratio`: Процентний ліміт оперативної пам'яті, зайнятої «брудними» сторінками (*dirty pages* — сторінки з файлового кешу, змінені в RAM, але ще не записані на диск). При досягненні `dirty_background_ratio` (наприклад, 10%) ядро фоново запускає фонові потоки `kworker` для вимивання даних на диск. При досягненні `dirty_ratio` (наприклад, 20%) ядро блокує процеси, що виконують запис `write()`, примушуючи їх чекати фізичного закінчення скидання блоків на носій.
- `vm.dirty_expire_centisecs` та `vm.dirty_writeback_centisecs`: Часові інтервали у сотнях часток секунди (1/100 с). Перший параметр задає максимальний вік брудної сторінки, після якого вона підлягає обов'язковому скиданню, а другий — частоту пробудження фонового потоку вимивання.
- `vm.overcommit_memory`: Режим виділення пам'яті ядра:
  - `0` (попереджувальний аналіз heuristic overcommit): ядро оцінює обсяг вільної RAM та дозволяє виділяти більше пам'яті, ніж є в наявності, сподіваючись, що програми не використають усе одразу.
  - `1` (завжди дозволяти overcommit): ядро схвалює будь-які запити `malloc()`/`mmap()`, що корисно для наукових обчислень із великими розрідженими масивами.
  - `2` (сувора заборона overcommit): виділення пам'яті обмежується суворою стелею: `swap_size + (RAM_size * overcommit_ratio / 100)`. Запит, що перевищує цю межу, повертає помилку `ENOMEM`.
- `vm.drop_caches`: Запис чисел у цей файл викликає негайне очищення чистих кешів ядра:
  - `echo 1 > /proc/sys/vm/drop_caches` — звільняє кеш сторінок (*pagecache*).
  - `echo 2 > /proc/sys/vm/drop_caches` — звільняє dentry та inode кеші.
  - `echo 3 > /proc/sys/vm/drop_caches` — звільняє pagecache, dentries та inodes.
- `vm.vfs_cache_pressure`: Контролює схильність ядра регенерації пам'яті шляхом витіснення dentry та inode кешів порівняно з pagecache. Значення за замовчуванням `100` зберігає баланс, значення вище `100` змушує ядро агресивніше викидати структури каталогів та файлів з RAM.
- `vm.min_free_kbytes`: Задає мінімальний запас оперативної пам'яті в кілобайтах, який ядро тримає вільним завжди для критично важливих атомарних розподілів пам'яті у перериваннях та мережевих драйверах.

### 3. `/proc/sys/net/` — мережевий стек

Найбільший та найскладніший розділ `sysctl`, що керує протоколами IPv4, IPv6, сокетами, чергами пакетів та фільтрацією пакетів (netfilter).

- `net.core.somaxconn`: Длина черги незведених з'єднань (*listen backlog*) для TCP-сокетів. Визначений у програмі аргумент виклику `listen(fd, backlog)` мовчки обрізається ядром до значення цього параметра.
- `net.core.netdev_max_backlog`: Максимальна кількість мережевих пакетів, які додаються у чергу обробки CPU, коли мережевий інтерфейс отримує пакети швидше, ніж ядро встигає їх розібрати.
- `net.ipv4.ip_forward`: Прапорець дозволу маршрутизації пакетів між мережевими інтерфейсами (`0` — вимкнено, `1` — увімкнено). Використовується на роутерах, шлюзах та вузлах Kubernetes/Docker.
- `net.ipv4.tcp_rmem`: Три числа у байтах (мінімум, за замовчуванням, максимум), що контролюють автоматичне масштабування вікна прийому TCP (*receive buffer autotuning*).
- `net.ipv4.tcp_wmem`: Три числа у байтах, що визначають розрахунок буфера передачі TCP.
- `net.ipv4.tcp_tw_reuse`: Дозволяє безпечне повторне використання сокетів у стані `TIME_WAIT` для нових вихідних з'єднань, якщо це дозволяють метки часу TCP (*timestamps*). Це критично для високонавантажених проксі-серверів (HAProxy, Nginx), які швидко вичерпують діапазон ефемерних портів.
- `net.ipv4.tcp_syncookies`: Вмикає захист від атаки SYN-flood шляхом надсилання кодованих SYN-кукі замість виділення пам'яті під напіввідкриті з'єднання при переповненні черги.

### 4. `/proc/sys/fs/` — файлові системи та ліміти VFS

- `fs.file-max`: Загальносистемна стеля на кількість одночасно відкритих файлових дескрипторів для всіх процесів у системі.
- `fs.file-nr`: Файл лише для читання, який віддає три числа: кількість відкритих файлових дескрипторів у даний момент, кількість виділених але вільних дескрипторів та максимальну стелю `file-max`.
- `fs.nr_open`: Максимальна кількість файлових дескрипторів, яку один окремий процес може відкрити (верхня межа для `RLIMIT_NOFILE`).
- `fs.protected_symlinks` та `fs.protected_hardlinks`: Механізми безпеки, що забороняють перехід по символьних посиланнях у загальнодоступних каталогах з прапорцем sticky bit (наприклад, `/tmp`), якщо власник посилання не збігається з власником каталогу чи файлу.
- `fs.inotify.max_user_watches`: Стеля кількості каталогів та файлів, за якими один користувач може стежити через системний виклик `inotify`. При вичерпанні цього ліміту `inotify_add_watch()` повертає помилку `ENOSPC`.

Повний контракт реєстрації та створення власних параметрів у коді ядра розібрано у довіднику [інтерфейс реєстрації таблиць ctl_table та обробників ядра](book:unix-linux/sysctl-kernel-tuning-interface/api-sysctl-handlers.md).

## Конфігураційні файли та утиліта sysctl(8)

Зміни, внесені шляхом прямого запису у `/proc/sys/`, діють миттєво, але зберігаються лише до першого перезавантаження системи. Для збереження параметрів між перезавантаженнями використовується системна утиліта `sysctl(8)` та конфігураційні файли.

### Нотації та трансляція імен

Утиліта `sysctl(8)` підтримує дві еквівалентні нотації назв параметрів:
- **Крапкова нотація:** `net.ipv4.ip_forward` (використовується в CLI та `.conf` файлах).
- **Слішева нотація:** `net/ipv4/ip_forward` або повний шлях `/proc/sys/net/ipv4/ip_forward`.

Утиліта під час виконання автоматично перетворює всі крапки у символи слішу і додає префікс `/proc/sys/`.

### Команди CLI sysctl(8)

```bash
# Перегляд усіх доступних параметрів ядра
sysctl -a

# Перегляд конкретного параметра
sysctl net.ipv4.ip_forward

# Тимчасова зміна параметра в пам'яті ядра
sysctl -w net.ipv4.ip_forward=1

# Перезавантаження налаштувань із конкретного файлу
sysctl -p /etc/sysctl.d/99-custom.conf

# Завантаження параметрів з усіх системних каталогів
sysctl --system
```

### Порядок застосування конфігурації у systemd

Під час завантаження системи служба `systemd-sysctl.service` виконує утиліту `sysctl --system`. Вона зчитує файли конфігурації з розширенням `.conf` у наступних каталогах (у порядку зростання пріоритету):

1. `/usr/lib/sysctl.d/*.conf` — замовчувані налаштування дистрибутиву та встановлених пакунків.
2. `/run/sysctl.d/*.conf` — тимчасові налаштування, згенеровані під час роботи (наприклад, мережевими демонами).
3. `/etc/sysctl.d/*.conf` — конфігураційні файли адміністратора системи.
4. `/etc/sysctl.conf` — традиційний глобальний файл конфігурації.

Якщо параметр з однаковим іменем зустрічається у кількох файлах, перемагає файл із каталогу з вищим пріоритетом. Якщо кілька файлів лежать увому тому ж каталозі, вони застосовуються у лексикографічному (алфавітному) порядку за іменем файлу.

Практичну реалізацію аналога утиліти `sysctl` мовами C та C++ з показом системних викликів розібрано у проєкті [практичний приклад написання консольної утиліти читання й запису параметрів /proc/sys](book:unix-linux/sysctl-kernel-tuning-interface/proj-sysctl-tool.md).

## Ізоляція у просторах імен (Namespaces) та безпека

З появою ізоляції процесів та контейнеризації (Docker, LXC, Podman, Kubernetes) виникла проблема: якщо контейнер змінює параметр `net.core.somaxconn` або `net.ipv4.ip_forward`, чи повинна ця зміна впливати на весь фізичний хост та сусідні контейнери?

Відповідь ядра Linux полягає у поділі параметрів `sysctl` на дві категорії:

1. **Глобальні параметри (Un-namespaced sysctls):** Належать всій операційній системі глобально. До них належать `fs.file-max`, `vm.swappiness`, `kernel.pid_max`, `kernel.shmmax`. Зміна цих параметрів впливає на всі процеси системи і вимагає привілею `CAP_SYS_ADMIN` у початковому просторі імен користувачів (*initial user namespace*).
2. **Ізольовані параметри (Namespaced sysctls):** Прив'язані до конкретного екземпляра простору імен (найчастіше мережевого `netns` або мижпроцесного `ipcns`). До них належать більшість параметрів `net.ipv4.*` та `net.core.*`.

![Ізоляція sysctl у просторах імен](/reference/unix-linux/proc/sysctl-kernel-tuning-interface/img/sysctl-namespace-isolation.svg)
*Розмежування глобальних параметрів sysctl та ізольованих параметрів контейнерів.*

Усередині мережевого простору імен контейнера процеси з привілеєм `CAP_NET_ADMIN` у своєму просторі мають право безпечно модифікувати параметри `net.*`. Зміна параметрів усередині Контейнера А не впливає на мережевий стек Контейнера Б чи фізичного хоста.

Спроба змінити глобальний параметр (наприклад, `fs.file-max`) зсередини контейнера без привілеїв у початковому просторі імен повертає відмову VFS із кодом помилки `EACCES` або `EPERM`.

У контексті безпеки Kubernetes розділяє `sysctls` на дві групи:
- **Safe sysctls:** Ізольовані у под-namespace і перевірені на відсутність впливу на сусідні поди (наприклад, `net.ipv4.ping_group_range`). Для їх увімкнення не потрібні додаткові привілеї ноди.
- **Unsafe sysctls:** Глобальні або потенційно небезпечні параметри, які вимагають явного дозволу адміністратора кластера у конфігурації Kubelet (`--allowed-unsafe-sysctls`).

> 🔧 **Навіщо це у реальній розробці.**
> Під час проектування систем високонавантажених веб-серверів та баз даних тюнінг `sysctl` є обов'язковим етапом оптимізації продуктивності та захисту від відмов.
>
> 1. **Оптимізація мережевого стеку для веб-сервера (Nginx/HAProxy):**
>    ```ini
>    # Збільшення черги прийому незведених сокетів
>    net.core.somaxconn = 8192
>    net.ipv4.tcp_max_syn_backlog = 8192
>    # Повторне використання TIME_WAIT сокетів
>    net.ipv4.tcp_tw_reuse = 1
>    # Збільшення діапазону ефемерних портів
>    net.ipv4.ip_local_port_range = 1024 65535
>    ```
> 2. **Усунення затримок запису I/O для баз даних (PostgreSQL/ClickHouse):**
>    Зниження `vm.dirty_background_ratio` до `5` і `vm.dirty_ratio` до `10` змушує ядро скидати брудні сторінки невеликими порціями, запобігаючи «тривалим паузам диска» під час вимивання великих обсягів кешу на повільні накопичувачі.
> 3. **Захист від вичерпання дескрипторів у високонавантажених сервісах:**
>    Підняття `fs.file-max = 2097152` гарантує, що сервіси обробки файлів чи сокетів не впруться у загальносистемну стелю відкритих файлів.
> 4. **Зміцнення безпеки сервера (Hardening):**
>    ```ini
>    kernel.kptr_restrict = 2
>    kernel.unprivileged_bpf_disabled = 1
>    fs.protected_symlinks = 1
>    fs.protected_hardlinks = 1
>    ```

Підсумовуючи, інтерфейс `sysctl` та `/proc/sys` забезпечує гнучкий міст між привілейованою пам'яттю ядра Linux та простором користувача, поєднуючи швидкість виконання з безпечним контролем доступу через VFS та простори імен.
