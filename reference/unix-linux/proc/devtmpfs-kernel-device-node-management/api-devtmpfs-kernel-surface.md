# 📋 Інтерфейс ядра та конфігураційні параметри devtmpfs

Керувати `devtmpfs` доводиться з чотирьох різних місць, і кожне має власний словник імен: прапори `Kconfig` при збірці ядра, параметр `devtmpfs.mount=` у командному рядку завантажувача, внутрішній C API підсистеми `driver core` та звичайні опції `mount -o` у просторі користувача. Що з цього вийшло, видно потім у `procfs` та `sysfs`.

## Конфігурація збірки ядра (Kconfig)

Параметри файлової системи `devtmpfs` визначаються під час конфігурації ядра Linux у розділі `Device Drivers -> Generic Driver Options`. Вони контролюють ввімкнення коду підсистеми та автоматичне монтування під час завантаження.

### Прапори конфігуратора Kconfig:

1. **`CONFIG_DEVTMPFS`**
   - **Тип:** `bool` (`y` / `n`) — окремим модулем не збирається, лише всередину ядра.
   - **Опис:** Вмикає компіляцію `drivers/base/devtmpfs.c`. Реєструє внутрішній тип файлової системи `devtmpfs_fs_type` у VFS та запускає фоновий потік ядра `kdevtmpfs`. Без цього прапора ядро позбавлене можливості автоматично створювати вузли у пам'яті.
   - **Залежності:** Формальних `depends on` не має. За наявності `CONFIG_TMPFS` примірник будується на `shmem`; якщо `CONFIG_TMPFS` вимкнено, ядро тихо бере простішу `ramfs` — саме про це попереджає довідка Kconfig.

2. **`CONFIG_DEVTMPFS_MOUNT`**
   - **Тип:** `bool` (`y` / `n`), `depends on DEVTMPFS`.
   - **Опис:** Передає ядру вказівку автоматично змонтувати примірник `devtmpfs` у каталог `/dev` одразу після того, як ядро змонтувало кореневу файлову систему (виклик `devtmpfs_mount()` у `prepare_namespace()`), але **до** моменту запуску першого користувацького бінарного файлу (`/sbin/init` чи `/lib/systemd/systemd`).
   - **⚠️ Межа дії:** на завантаження через `initramfs` цей прапор **не впливає** — так прямо сказано в довідці Kconfig. Там `/dev` монтує сам скрипт `/init`, а мінімальний `/dev/console` усе одно має лежати в образі статично.
   - **Системні наслідки:** Дає підняти систему в рятівному режимі `init=/bin/sh` навіть тоді, коли каталог `/dev` на кореневій ФС цілком порожній.

3. **`CONFIG_DEVTMPFS_SAFE`**
   - **Тип:** `bool` (`y` / `n`), `depends on DEVTMPFS`. З'явився у ядрі 5.17 — у старіших деревах цього прапора немає взагалі.
   - **Опис:** Додає до прапорів монтажу `devtmpfs` (`DEVTMPFS_MFLAGS`) біти `MS_NOEXEC` та `MS_NOSUID` — без нього діє лише `MS_SILENT`. Тобто з файлів у `/dev` не можна ні виконувати код, ні підвищувати привілеї через setuid-біт.
   - **Ціна:** `/dev/mem` більше не відображається в пам'ять із прапором `PROT_EXEC`, що ламає, зокрема, відеодрайвери без KMS.

## Параметри командного рядка ядра (BootCmdline)

Поведінку автомонтажу можна змінити без перекомпіляції ядра — просто на завантаженні. Для цього системний завантажувач (GRUB, systemd-boot, U-Boot) передає ядру такі аргументи:

- **`devtmpfs.mount=1`**: Примусово вмикає автоматичний монтаж `devtmpfs` у точку `/dev` при старті ядра. Перевизначає значення `CONFIG_DEVTMPFS_MOUNT=n`.
- **`devtmpfs.mount=0`**: Примусово вимикає автоматичний монтаж `devtmpfs` ядром. Застосовується у спеціалізованих середовищах розробки, при налагодженні власних образів `initramfs` або у контейнерних архітектурах, де простір користувача повинен самостійно контролювати вміст `/dev`.

Розбирає обидва значення функція `mount_param()`, зареєстрована через `__setup("devtmpfs.mount=", …)`, — це саме параметр командного рядка ядра, а не запис у `/sys/module/`.

## Внутрішній C API ядра

Функціональний інтерфейс `devtmpfs` використовується підсистемою `driver core` та не експортується для сторонніх модулів через `EXPORT_SYMBOL` (виклики є внутрішньоядровими). Оголошення розкидані по двох заголовках, і плутати їх не варто:

```c
/* include/linux/devtmpfs.h — видимий коду ініціалізації ядра */
int devtmpfs_init(void);
int devtmpfs_mount(void);

/* drivers/base/base.h — приватний заголовок driver core */
int devtmpfs_create_node(struct device *dev);
int devtmpfs_delete_node(struct device *dev);
```

Зверніть увагу: у сучасних ядрах `devtmpfs_mount()` **не приймає аргументів** — точка монтажу зашита в саму функцію. Історична сигнатура `devtmpfs_mount(const char *mntdir)` жила в деревах до середини серії 5.x (тоді монтаж робив ще `ksys_mount()`, а не `init_mount()`); трапляється вона й у статтях, писаних за тими деревами.

### Детальний контракт та сигнатури методів:

#### 1. `int devtmpfs_create_node(struct device *dev)`

- **Параметри:** `dev` — вказівник на структуру пристрою ядра `struct device`, яка повинна містити дійсний номер пристрою `dev->devt` та сформоване ім'я `dev_name(dev)`.
- **Контекст виконання:** ⚠️ **Лише там, де дозволено спати.** Функція не просто ставить завдання в чергу — вона чекає на `wait_for_completion(&req.done)`, доки `kdevtmpfs` не завершить VFS-операцію. Виклик з атомарного контексту чи з-під спін-блокування — помилка. Обмеження не штучне: `device_add()`, єдиний законний викликач, сама спить на виділенні пам'яті `GFP_KERNEL` і на мутексах sysfs.
- **Що функція вирішує за драйвера:** ім'я вузла бере з `device_get_devnode()`; якщо драйвер не задав власного режиму доступу, ставить `0600`; тип файлу домішує сама — `S_IFBLK` для блокового пристрою, `S_IFCHR` для символьного. Пам'ять під запит не виділяється взагалі: `struct req` живе на стеку викликача, і саме тому виклик мусить дочекатися відповіді.
- **Коди повернення:**
  - `0`: Вузол створено, `/dev/<name>` уже існує на момент повернення.
  - `-ENOMEM`: Не вдалося сформувати ім'я вузла (`device_get_devnode()` повернув `NULL`).
  - Інший від'ємний код: помилка VFS, яку записав у поле `req.err` потік `kdevtmpfs`.
- **Гарантія порядку:** `device_add()` викликає `devtmpfs_create_node()` **до** `kobject_uevent(&dev->kobj, KOBJ_ADD)`. Тому будь-який слухач uevent у просторі користувача бачить подію лише тоді, коли вузол у `/dev` уже на місці.

#### 2. `int devtmpfs_delete_node(struct device *dev)`

- **Параметри:** `dev` — вказівник на вилучений пристрій.
- **Контекст виконання:** Викликається з функції `device_del()` під час відключення обладнання або розвантаження модуля драйвера.
- **Внутрішня механіка:** Той самий `devtmpfs_submit_req()`, але з `mode = 0` — саме нуль у полі режиму є домовленим маркером вилучення (у структурі немає окремого поля «операція»). Прибирання батьківських каталогів, що спорожніли, бере на себе `delete_path()`.
- **Коди повернення:** `0` при успішному вилученні або від'ємний код помилки VFS (наприклад, `-ENOENT`).

#### 3. `int devtmpfs_mount(void)`

- **Параметри:** відсутні. Точка монтажу (`/dev`) зашита у тілі функції.
- **Контекст виконання:** Викликається виключно під час ранньої ініціалізації ядра — з `prepare_namespace()` (`init/do_mounts.c`), одразу після `mount_root()` і перед `init_mount(".", "/", NULL, MS_MOVE, NULL)`. Нічого не робить, якщо `CONFIG_DEVTMPFS_MOUNT=n` і в командному рядку немає `devtmpfs.mount=1`, а також завжди, коли систему піднято через `initramfs`.
- **Коди повернення:** `0` при успішному монтажі або код помилки VFS.

## Системний виклик монтування у просторі користувача

Файлову систему `devtmpfs` можна змонтувати й із простору користувача — утилітою `mount` або системним викликом `mount()` — у довільний каталог. Одного тільки не буде: нового примірника. `devtmpfs` існує в системі в єдиному екземплярі, і кожне таке монтування показує ту саму файлову систему, переналаштовуючи її за переданими опціями. Тобто `-o` тут задає параметри не «свого» монтажу, а спільної для всіх `devtmpfs`:

```bash
mount -t devtmpfs devtmpfs /dev -o mode=0755,nr_inodes=262144
```

### Доступні опції монтування (`-o`):

- **`mode=octal`**: Встановлює вісімковий режим доступу для кореневого індексу змонтованого каталогу. За замовчуванням значення становить `0755` (`rwxr-xr-x`).
- **`uid=N`**: Числовий ідентифікатор користувача, який стає власником кореневого каталогу `/dev` (за замовчуванням `0` — `root`).
- **`gid=N`**: Числовий ідентифікатор групи-власника кореневого каталогу `/dev` (за замовчуванням `0` — `root`).
- **`nr_inodes=N`**: Задає граничне обмеження на максимальну кількість індексних дескрипторів (об'єктів файлів та каталогів), які дозволено створити у цьому примірнику `devtmpfs`. Запобігає вичерпанню пам'яті ядра при масовій генерації вузлів.
- **`size=N`**: Стеля пам'яті під вміст файлів, записана звичними одиницями (`16M`, `512K`) або відсотком від RAM (`50%`). Саме це значення видно в `/proc/self/mountinfo` як `size=…k`. Типово ядро бере половину сторінок оперативної пам'яті.
- **`nr_blocks=N`**: Та сама стеля, але лічена просто в сторінках пам'яті (на x86-64 сторінка — 4 КіБ, на інших архітектурах буває більша).

## Точки діагностики у віртуальних файлових системах

Стан та конфігурація `devtmpfs` відображаються у псевдо-файлових системах `procfs` та `sysfs`:

### 1. Перелік файлових систем (`/proc/filesystems`)

Містить рядок реєстрації `devtmpfs`, і рядок цей — з префіксом `nodev`. Позначка означає рівно одне: файловій системі не потрібен блоковий пристрій-носій, її монтують без реального диска. До того, чи вміє `devtmpfs` створювати вузли пристроїв, ця позначка стосунку не має:

```
nodev   sysfs
nodev   tmpfs
nodev   devtmpfs
```

### 2. Таблиця змонтованих систем (`/proc/self/mountinfo`)

Відображає повний стан змонтованої файлової системи `devtmpfs`, включаючи ідентифікатор пристрою VFS, прапори монтування та обмеження ресурсів:

```
20 26 0:6 / /dev rw,nosuid,relatime shared:2 - devtmpfs devtmpfs rw,size=4042856k,nr_inodes=1010714,mode=0755
```

Числа тут не довільні: типово `devtmpfs` бере половину сторінок RAM, тож `size` (у КіБ) рівно вчетверо більший за `nr_inodes` (у сторінках по 4 КіБ). У наведеному рядку 4 042 856 КіБ ≈ 3,86 ГіБ — це половина від приблизно 7,7 ГіБ доступної пам'яті.

### 3. Індекси пристроїв у sysfs (`/sys/dev/char/` та `/sys/dev/block/`)

Кожному мажорному й мінорному номеру, що обробляється у `devtmpfs`, відповідає символічне посилання у `sysfs`:

- `/sys/dev/char/<major>:<minor>` — посилання на об'єкт `kobject` символьного пристрою у дереві `/sys/devices/`.
- `/sys/dev/block/<major>:<minor>` — посилання на об'єкт `kobject` блокового пристрою у дереві `/sys/devices/`.
