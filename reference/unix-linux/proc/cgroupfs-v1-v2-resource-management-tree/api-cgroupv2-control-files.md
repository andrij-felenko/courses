# 📋 Довідник файлів керування та параметрів cgroup v2

Цей довідник містить повну специфікацію файлів керування cgroup v2 у `/sys/fs/cgroup`, включаючи синтаксис налаштування контролерів CPU, пам'яті, I/O та PIDs, а також метрики Pressure Stall Information (PSI).

## Принципи побудови інтерфейсу файлів cgroup v2

Усі файли керування у файловій системі cgroup v2 дотримуються єдиного домовленого синтаксису, що розроблений для легкого розбору у просторі користувача та надійної перевірки вхідних даних у ядрі.

Кожен файл керування використовує один із трьох форматів:
1. **Просте скалярне значення**: Текстове представлення одного цілого числа (наприклад, кількість байтів у `memory.max` або кількість процесів у `pids.max`).
2. **Пара значень «квота період»**: Два числа, розділені пробілом (наприклад, `50000 100000` у `cpu.max`), де перше значення означає виділений ресурс, а друге — часове вікно.
3. **Параметр із позначкою пристрою**: Ідентифікатор блокового пристрою у форматі `major:minor`, за яким слідує ключ із значенням (наприклад, `8:0 rbps=104857600` у `io.max`).

Спеціальне значення `max` використовується у всіх контролерах для позначення відсутності будь-якого обмеження.

## 1. Системні файли керування дерева cgroup v2

Кожен каталог (вузол) файлового дерева `/sys/fs/cgroup` автоматично створює базовий набір універсальних файлів керування. Цей набір керує ієрархічним розгалуженням, прапорцями станів та переліком делегованих ресурсів.

Файл `cgroup.events` надає асинхронний моніторинг станів через прапорці `populated` (значення `1` показує присутність хоча б одного живого процесу у цій cgroup чи її піддереві) та `frozen` (значення `1` вказує на заморожений стан виконання процесів). Зміна цих прапорців активує системну подію `POLLPRI` на відкритих файлових дескрипторах цього файла.

| Файл | Режим | Опис та синтаксис |
| :--- | :--- | :--- |
| `cgroup.procs` | R/W | Список PIDs усіх процесів, прив'язаних до даної cgroup (по одному PID на рядок). Запис PID переносить увесь процес у цю cgroup. |
| `cgroup.threads` | R/W | Список TID (ідентифікаторів потоків) для використання у режимі Thread Mode (`cgroup.type = threaded`). |
| `cgroup.controllers` | Read-only | Список доступних контролерів, делегованих від батьківського вузла (наприклад, `cpu memory io pids`). |
| `cgroup.subtree_control` | R/W | Контролери, активовані для безпосередніх дочірніх вузлів. Запис: `+cpu -memory +io`. |
| `cgroup.events` | Read-only | Ключ-значення підключених подій. Містить `populated 0/1` (наявність процесів) та `frozen 0/1`. |
| `cgroup.type` | R/W | Тип cgroup: `domain` (стандартний), `domain threaded`, `domain invalid` або `threaded`. |
| `cgroup.freeze` | R/W | Запис `1` заморожує виконання всіх процесів у cgroup та її піддереві; запис `0` відновлює виконання. На відміну від `SIGSTOP`, стан не видно самому процесу і його не можна скасувати сигналом `SIGCONT`. |
| `cgroup.kill` | Write-only | Запис `1` надсилає сигнал SIGKILL всім процесам у cgroup та її дочірніх вузлах (атомарне знищення). |
| `cgroup.max.depth` | R/W | Максимальна припустима глибина вкладеності дочірніх каталогів піддерева. |
| `cgroup.max.descendants` | R/W | Максимальна кількість дочірніх каталогів (нащадків), які дозволено створити під цим вузлом. |

## 2. Контролер процесорних ресурсів (CPU Controller)

Контролер CPU оперує механізмами розподілу квантів часу CFS (Completely Fair Scheduler) та регулює доступ до обчислювальних ядер. Загальний опис роботи планувальника включає підтримку як пропорційного поділу процесорного часу між сусідніми вузлами, так і встановлення абсолютних меж часу виконання за допомогою фіксованих періодів.

Налаштування `cpu.max` оперує мікросекундами. Запис `200000 100000` дозволяє cgroup використовувати сумарно 200 мс процесорного часу за кожні 100 мс реального часу (еквівалент використання 2 повних процесорних ядер). Якщо навантаження перевищує цей поріг, лічильник `nr_throttled` у `cpu.stat` збільшується, а потоки блокуються.

| Файл | Формат запису / зчитування | Опис |
| :--- | :--- | :--- |
| `cpu.max` | `$quota $period` (наприклад, `50000 100000`) | Абсолютний ліміт часу CPU у мікросекундах. Значення `max 100000` означає відсутність обмежень. |
| `cpu.weight` | Число від `1` до `10000` (за замовчуванням `100`) | Пропорційна частка процесорного часу відносно сусідніх вузлів (відповідник `cpu.shares` із cgroup v1). |
| `cpu.weight.nice` | Число від `-20` до `19` | Альтернативний інтерфейс налаштування вагового коефіцієнта у шкалі значення `nice`. |
| `cpu.stat` | `usage_usec $val`, `user_usec $val`, `system_usec $val` | Статистика використання CPU: загальний час, час у просторі користувача та ядра, лічильники тротлінгу. |
| `cpu.pressure` | PSI метрика (`some avg10=0.00 ...`) | Затримки очікування процесів через дефіцит процесорного часу. |

## 3. Контролер оперативної пам'яті (Memory Controller)

Контролер memory надає чотирирівневу каскадну модель захисту та обмежень оперативної пам'яті, підкачки (swap) та ядерних структур даних. Кожен рівень захисту виконує власну функцію у ланцюжку витіснення сторінок пам'яті.

Детальна статистика у файлі `memory.stat` включає розподіл споживання за типами:
- `anon`: Обсяг анонімної оперативної пам'яті (купа, стек, виділення через `malloc`/`mmap`).
- `file`: Обсяг кешу сторінок пам'яті (page cache) при роботі з дисковими файлами.
- `kernel_stack`: Пам'ять, виділена під стеки системних викликів процесів у ядрі.
- `pagetables`: Пам'ять під таблиці сторінок віртуальної пам'яті процесу.
- `sec_pagetables`: Пам'ять під таблиці сторінок підсистеми віртуалізації (EPT/NPT).
- `slab`: Пам'ять під внутрішні структури даних ядра (об'єкти `struct task_struct`, `struct inode` тощо).

| Файл | Одиниці виміру | Опис та логіка спрацювання |
| :--- | :--- | :--- |
| `memory.current` | Байти | Поточний обсяг пам'яті, спожитий cgroup (анонімна пам'ять, кеш сторінок, пам'ять ядра). |
| `memory.min` | Байти або `max` | Жорсткий захист (Hard Protection). Пам'ять у межах порогу не витісняється ядром за жодних умов. |
| `memory.low` | Байти або `max` | М'який захист (Soft Protection). Пам'ять у межах порогу витісняється лише тоді, коли витісняти більше нема чого у незахищених cgroups. |
| `memory.high` | Байти або `max` | Поріг тротлінгу. Перевищення викликає примусовий reclaim та затримки виконання потоків. |
| `memory.max` | Байти або `max` | Жорсткий верхній ліміт. Перевищення запускає OOM Killer у cgroup. |
| `memory.oom.group` | `0` або `1` | Якщо `1`, при спрацюванні OOM вбиваються ВСІ процеси cgroup атомарно. |
| `memory.stat` | Поля ключ-значення | Детальна статистика: `anon`, `file`, `kernel_stack`, `pagetables`, `sec_pagetables`, `pgfault`, `pgmajfault`. |
| `memory.events` | Лічильники подій | Кількість подій `low`, `high`, `max`, `oom`, `oom_kill`, `oom_group_kill`. |
| `memory.pressure` | PSI метрика | Метрики затримок процесу при витісненні пам'яті на диск (`some` та `full`). |

## 4. Контролер блокового введення-виведення (I/O Controller)

Забезпечує обмеження пропускної здатності дискових операцій у байтах за секунду (BPS) та кількості операцій введення-виведення за секунду (IOPS) для конкретних блокових пристроїв.

Файл `io.stat` надає поточні значення зчитаних та записаних даних у байтах для кожного блокового пристрою (`rbytes`, `wbytes`), а також відповідні лічильники операцій (`rios`, `wios`). Зверніть увагу на несиметричність назв: обмеження в `io.max` задаються ключами `riops`/`wiops`, а вже виконані операції рахуються в `io.stat` ключами `rios`/`wios`.

| Файл | Синтаксис | Опис |
| :--- | :--- | :--- |
| `io.max` | `$major:$minor rbps=$v wbps=$v riops=$v wiops=$v` | Абсолютні межі для пристрою (наприклад, `8:0 rbps=104857600` означає 100 МіБ/с читання). |
| `io.weight` | `default $weight` або `$major:$minor $weight` (від `1` до `10000`, типово `100`) | Пропорційний розподіл пропускної здатності дискового накопичувача між cgroups. |
| `io.stat` | `$major:$minor rbytes=$v wbytes=$v rios=$v wios=$v dbytes=$v dios=$v` | Лічильники зчитаних, записаних та відкинутих (discard) байтів і операцій для кожного пристрою. |
| `io.pressure` | PSI метрика | Очікування процесів при затримках дискового блокового I/O. |

## 5. Контролер кількості процесів (PID Controller)

Призначений для захисту системних ресурсів від аварійного породження процесів та захисту від атак типу fork bomb. Контролер відстежує загальну кількість потоків виконання та процесів у піддереві.

При вичерпанні ліміту `pids.max` будь-який наступний системний виклик `fork()`, `clone()` або `clone3()` повертає помилку `EAGAIN`, а лічильник `max` у `pids.events` інкрементується.

| Файл | Значення | Опис |
| :--- | :--- | :--- |
| `pids.max` | Число або `max` | Максимальна дозволена кількість процесів та потоків у цій cgroup та її нащадках. |
| `pids.current` | Число | Поточна сумарна кількість активних PIDs у cgroup. |
| `pids.events` | `max $count` | Лічильник випадків блокування виклику `fork()`/`clone()` через досягнення `pids.max`. |

## 6. Метрики Pressure Stall Information (PSI)

Усі параметри `*.pressure` мають єдиний стандартний синтаксис виводу, що описує частку часу, змарновану через дефіцит ресурсу:

```
some avg10=0.00 avg60=0.00 avg300=0.00 total=0
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

Значення метрик мають наступну логічну інтерпретацію:
- **`some`**: Відсоток часу у 10, 60 та 300-секундних вікнах усереднення, коли принаймні один потік cgroup очікував на виділення ресурсу (CPU, memory, I/O).
- **`full`**: Відсоток часу, коли всі активні потоки cgroup були одночасно заблоковані у стані очікування даного ресурсу (повне простоювання корисної роботи).
- **`total`**: Загальний накопичений час очікування ресурсів у мікросекундах з моменту створення cgroup.

## 7. Інспекція належності процесів через procfs та системні файли

Для перевірки того, до яких cgroups належить конкретний процес, у ядрі Linux надається псевдофайл `/proc/[pid]/cgroup`.

У режимі cgroup v2 вміст `/proc/[pid]/cgroup` має лаконічний вигляд з однієї стрічки:
```
0::/user.slice/user-1000.slice/user@1000.service/app.slice/demo.service
```

Цифра `0` у першому полі вказує на використання єдиної ієрархії cgroup v2 (у cgroup v1 перше поле містило номер ієрархії контролера). Друге поле — список контролерів — у v2-рядку завжди порожнє, бо контролери не прив'язані до окремих дерев; третє поле описує абсолютний шлях до cgroup відносно кореня `/sys/fs/cgroup`.

Загальний перелік доступних підсистем cgroup у ядрі та їхній поточний стан можна перевірити через системний файл `/proc/cgroups`:
```
#subsys_name    hierarchy       num_cgroups     enabled
cpuset          0               125             1
cpu             0               125             1
memory          0               125             1
```
Значення `0` у стовпчику `hierarchy` означає, що підсистема не змонтована в жодній ієрархії cgroup v1, — тобто працює у складі єдиного дерева cgroup v2.

## 8. Коди помилок при записі у файли керування

Запис некоректних параметрів або порушення системних правил cgroup v2 повертає стандартні помилки POSIX:
- **`EBUSY`**: Спроба увімкнути контролер у `cgroup.subtree_control`, коли батьківська cgroup містить власні процеси у `cgroup.procs` (порушення правила відсутності внутрішніх процесів).
- **`EINVAL`**: Передано некоректний формат синтаксису, від'ємне значення або перевищено припустимий діапазон (наприклад, значення `cpu.weight` поза межами 1..10000).
- **`ESRCH`**: Передано у `cgroup.procs` ідентифікатор PID, якого немає у системному списку процесів.
- **`ENOENT`**: Спроба увімкнути в `cgroup.subtree_control` контролер, якого немає у списку `cgroup.controllers` цього вузла, — його не зібрано в ядрі, вимкнено параметром завантаження `cgroup_disable` або не делеговано батьківським вузлом. Невідому назву контролера ядро відкидає з `EINVAL`.
