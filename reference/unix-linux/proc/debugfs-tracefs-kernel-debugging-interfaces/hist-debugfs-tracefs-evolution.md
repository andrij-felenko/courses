# 📜 Еволюція налагодових ВФС: від хаосу procfs до ізоляції tracefs

Історія виникнення та відокремлення спеціалізованих налагодових віртуальних файлових систем у ядрі Linux відображає понад тридцятирічний шлях еволюції системної архітектури. Вона демонструє, як розробники ядра поступово шукали баланс між трьома суперечливими вимогами: зручністю розробки драйверів, суворістю гарантій зворотної сумісності (ABI) та безпекою виробничих середовищ.

## Ранній період: витоки procfs та захаращення простору назв (1991–2003)

Концепція файлової системи процесів `procfs` (/proc) була початково розроблена в дослідній операційній системі Plan 9 у Bell Labs і згодом адаптована в UNIX System V Release 4. Її головною метою було надання інструментам спостереження за процесами (таким як `ps` або `gdb`) зручного текстового інтерфейсу до пам'яті та стану структур `task_struct` через стандартні системні виклики POSIX (`open`, `read`, `close`).

Линус Торвальдс імплементував базову підтримку `procfs` на ранніх етапах розвитку ядра Linux (серія 0.99/1.0). Проте через відсутність у ранньому Linux інших віртуальних систем експорту даних ядра, розробники пристроїв почали використовувати `/proc` для будь-яких завдань:
- Драйвери мережевих карт, мережеві стеки (IPX, AppleTalk, IPv4), контролери SCSI та звукові карти реєстрували власні довільні каталоги у корені `/proc`.
- Формат виводу генерувався вручну через виклики `sprintf()`, що регулярно призводило до переповнення буферів у просторі ядра та непередбачуваних падінь системи (Kernel Panic) при зчитуванні великих обсягів даних.
- Скрипти та утиліти користувацького простору опиралися на текстовий формат виводу конкретної версії драйвера. Будь-яка спроба розробників ядра виправити друкарську помилку або змінити порядок колонок у файлі `/proc/net/dev` або `/proc/scsi/scsi` спричиняла поломку системного програмного забезпечення, створюючи де-факто неофіційні зобов'язання щодо збереження зворотної сумісності (ABI).

До моменту виходу серії ядер 2.4 каталог `/proc` перетворився на некоординований хаос, у якому статистика системних процесів перемішувалася з внутрішніми налагоджувальними дампними регістрами периферійного заліза.

## Поява sysfs та криза налагодження драйверів (2003)

Під час підготовки ядра Linux 2.6 розробники Патрік Мочел (Patrick Mochel) та Ґреґ Кроа-Гартман (Greg Kroah-Hartman) здійснили масштабну реформацію, створивши файлову систему `sysfs` (користувацька точка монтування `/sys`). 

Головним завданням `sysfs` було строге відображення ієрархії об'єктів ядра (`kobject`), пристроїв, шин (PCI, USB, I2C) та відповідних їм драйверів. Для запобігання хаосу, аналогічного `/proc`, для `sysfs` було встановлено фундаментальні правила:
1. **Суворий зв'язок із стабільним ABI:** формат атрибута у `/sys` фіксується в документації ядра (`Documentation/ABI/`). Його зміна або видалення вимагає тривалого періоду оголошення застарілим (deprecation cycle), що розтягується на роки.
2. **Правило «один атрибут — одне значення» (one value per file):** кожен файл у `sysfs` мусить містити лише один рядковий або числовий показник (наприклад, прапор живлення пристрою `1`/`0` або температуру в міліградусах).

Ці обмеження виявилися ідеальними для системних демонів (`udev`, `systemd`), проте вони поставили в безвихідь розробників складних драйверів (наприклад, відеокарт, мережевих адаптерів 100GbE або підсистеми віртуальної пам'яті). Для аналізу збоїв інженеру необхідно вивантажувати складні багатосторінкові таблиці станів, структури дескрипторів DMA, графічні конвеєри та лічильники блокувань. Експортувати такі дані через тисячі окремих файлів `sysfs` з дотриманням правил ABI було неможливо.

## Народження debugfs як зони без правил (2004)

У грудні 2004 року Ґреґ Кроа-Гартман запропонував радикальне рішення — створити спеціалізовану віртуальну файлову систему **debugfs** (включена у реліз ядра Linux 2.6.11-rc1).

Основна ідея `debugfs` полягала у створенні «пісочниці» для розробників з повним скасуванням будь-яких правил та обмежень:
- **Забороно гарантії ABI (NO_ABI):** у документації ядра чітко зафіксовано, що користувацькі утиліти не мають права розраховувати на наявність або стабільність формату файлів у `debugfs`. Розробник має право перейменовувати, змінювати або повністю видаляти файли в будь-якому релізі ядра.
- **Довільні формати:** дозволено двонаправлені дампам оперативної пам'яті, бінарні структури, багаторазові текстові звіти та довільні двійкові блоги.
- **Мигцем створений API:** для створення вузлів у ядрі було додано лаконічні виклики `debugfs_create_u32()`, `debugfs_create_bool()` та `debugfs_create_file()`, що скоротило обсяг коду налагодження у драйверах на сотні рядків.

Точкою монтування `debugfs` за замовчуванням став каталог `/sys/kernel/debug`.

## Проект PREEMPT_RT, поява ftrace та криза безпеки (2008–2014)

У 2005–2008 роках під час роботи над проектом адаптації Linux до систем реального часу (PREEMPT_RT patchset) Стівен Ростедт (Steven Rostedt) та Інґо Молнар (Ingo Molnar) розробили підсистему трасування ядра **ftrace** (Function Tracer). ftrace дозволила перехоплювати вхід та вихід із будь-якої функції ядра з мінімальними накладними витратами.

Оскільки на той момент єдиною ВФС для налагодження була `debugfs`, усі керувальні файли ftrace (кільцеві буфери, вимикачі, фільтри) розмістили всередині `debugfs` за шляхом `/sys/kernel/debug/tracing`.

Це рішення чудово працювало на робочих станціях розробників, але у 2010-х роках інструменти трасування (`perf`, `trace-cmd`, а згодом і `eBPF`) стали критично необхідними на виробничих серверах (production) для відстеження затримок та аналізу продуктивності під навантаженням. 

Тут виникла нова системна проблема безпеки:
- Каталог `/sys/kernel/debug` містив не лише трасувальник ftrace, а й небезпечні вузли драйверів, які дозволяли пряме читання фізичної пам'яті або перезапис регістрів обладнання. З цієї причини доступ до `/sys/kernel/debug` закривали правами `0700` лише для суперкористувача `root`.
- Надавати інженерам з аналізу продуктивності або автоматизованим моніторинговим агентам повні права `root` до небезпечних драйверів у `debugfs` було категорично неприпустимо з міркувань безпеки.

## Виокремлення tracefs та епоха Kernel Lockdown (2015 — наш час)

У грудні 2014 року Стівен Ростедт подав серію патчів для виокремлення трасувальної інфраструктури у власну віртуальну файлову систему — **tracefs**. 

Офіційна інтеграція `tracefs` відбулася у червні 2015 року в ядрі Linux 4.1. Нова файлова система отримала власну точку монтування `/sys/kernel/tracing`. Для збереження працездатності існуючого інструментарію каталог `/sys/kernel/debug/tracing` перетворили на автоматичне зв'язування (bind mount) на точку `/sys/kernel/tracing`.

Виокремлення `tracefs` дозволило системним адміністраторам застосовувати гнучкі правила прав доступу: надавати групі аналітиків (`tracing`) права читання та запису до файлів трасування, залишаючи небезпечні вузли `debugfs` повністю ізольованими.

Останнім етапом формування безпекової моделі стало впровадження у ядрі Linux 5.4 (2019 рік) підсистеми **Kernel Lockdown** (автор Меттью Гарретт). При завантаженні системи в режимі UEFI Secure Boot підсистема Lockdown у режимі `confidentiality` повністю блокує доступ до `debugfs` навіть для користувача `root`, запобігаючи витоку конфіденційних даних через налагоджувальні файли драйверів. Водночас `tracefs` залишається працездатною у межах безпечних статичних точок трасування (tracepoints).
