# 📋 Специфікація API debugfs та керувальних інтерфейсів tracefs

Цей довідник описує повну специфікацію функцій C API ядра Linux для реєстрації вузлів у віртуальній файловій системі `debugfs`, а також синтаксис налаштувань, керувальних файлів та динамічних зондів у файловій системі `tracefs`.

---

## 1. C API ядра Linux для debugfs (<linux/debugfs.h>)

Інтерфейс програмування `debugfs` призначений для швидкого експорту внутрішніх змінних ядра та реєстрації користувацьких точок читання і запису. Усі функціональні виклики створення вузлів приймають текстове ім'я елемента, маску прав доступу POSIX, вказівник на батьківську структуру `dentry` та адреси експортованих даних. Якщо параметр батьківського каталогу дорівнює `NULL`, ядро автоматично створює новий вузол у кореневому каталозі файлової системи `/sys/kernel/debug`.

### Механізми обробки помилок та повертаних значень

На відміну от більшості традиційних підсистем ядра, де невдалий виклик повертає вказівник `NULL`, функції `debugfs` повертають спеціальний маскований вказівник на помилку `ERR_PTR`. Це зроблено для того, щоб розробник міг відрізнити випадок, коли файлова система `debugfs` взагалі вимкнена в ядрі на етапі конфігурації (параметр `CONFIG_DEBUG_FS=n`), від випадку, коли не вдалося виділити пам'ять під новий елемент каталогу.

Для перевірки результату виконання виклику у коді драйвера застосовуються спеціалізовані макроси ядра:
- `IS_ERR(dentry)` — повертає `true`, якщо повернене значення містить код помилки (наприклад, `-ENOMEM` або `-EEXIST`).
- `PTR_ERR(dentry)` — вилучає числовий код помилки зі структури вказівника для подальшого повернення в обробнику ініціалізації модуля.

Забезпечення безпечного зчитування скалярних величин у багатопроцесорних системах (SMP) досягається за допомогою викликів `debugfs_create_atomic_t()`, які виконують атомарне зчитування `atomic_read()` без використання блокуючих м'ютексів.

### Повний довідник функцій створення та видалення вузлів

| Сигнатура функції / Макрос | Параметри та призначення | Повертане значення та обробка помилок |
| :--- | :--- | :--- |
| `debugfs_create_dir(name, parent)` | **name:** ім'я каталогу.<br>**parent:** батьківський `struct dentry*` (якщо `NULL`, створюється в корені `/sys/kernel/debug`). | Повертає `struct dentry*`. При помилці повертає `ERR_PTR` або `NULL` (якщо debugfs вимкнено в ядрі). Перевіряється макросом `IS_ERR()`. |
| `debugfs_create_file(name, mode, parent, data, fops)` | **name:** ім'я файлу.<br>**mode:** права POSIX (наприклад `0644`).<br>**parent:** батьківський каталог.<br>**data:** приватний вказівник `void*` (доступний через `inode->i_private`).<br>**fops:** вказівник на `struct file_operations`. | Повертає `struct dentry*`. При помилці повертає `ERR_PTR`. Використовується для підключення `seq_file` обробників. |
| `debugfs_create_u8(name, mode, parent, value)` | Експорт 8-бітного цілого числа (`u8*`). | Повертає `struct dentry*`. Атомарний експорт скалярної змінної. |
| `debugfs_create_u16(name, mode, parent, value)` | Експорт 16-бітного цілого числа (`u16*`). | Повертає `struct dentry*`. Атомарний експорт скалярної змінної. |
| `debugfs_create_u32(name, mode, parent, value)` | Експорт 32-бітного цілого числа (`u32*`). | Повертає `struct dentry*`. Атомарний експорт скалярної змінної. |
| `debugfs_create_u64(name, mode, parent, value)` | Експорт 64-бітного цілого числа (`u64*`). | Повертає `struct dentry*`. Атомарний експорт скалярної змінної. |
| `debugfs_create_bool(name, mode, parent, value)` | Експорт прапорця `bool*`. У ВФС відображається як рядок `Y` або `N` при зчитуванні. | Повертає `struct dentry*`. При запису приймає `1`/`0`, `y`/`n`, `Y`/`N`. |
| `debugfs_create_atomic_t(name, mode, parent, value)` | Експорт атомарного лічильника ядра `atomic_t*`. | Повертає `struct dentry*`. Забезпечує безпечне зчитування лічильника в ядрах SMP. |
| `debugfs_create_blob(name, mode, parent, blob)` | Експорт бінарного масиву через структуру `struct debugfs_blob_wrapper { void *data; unsigned long size; }`. | Повертає `struct dentry*`. Створює файл лише для читання двонаправленого дампу пам'яті. |
| `debugfs_remove(dentry)` | Вилучення одного конкретного файлу або порожнього каталогу. | `void`. Безпечно приймає `NULL` або `ERR_PTR` (нічого не робить). |
| `debugfs_remove_recursive(dentry)` | Рекурсивне вилучення каталогу та всіх його підкаталогів і файлів. | `void`. Викликається в обробнику `module_exit()` при розвантаженні драйвера. |

### Послідовний вивід великих структур даних через seq_file

Коли обсяг експортованого тексту перевищує розмір однієї системної сторінки пам'яті (зазвичай 4096 байтів), стандартні обробники `read` стають схильними до помилок через складність розрахунку поточного зміщення `loff_t *ppos`. Для вирішення цієї задачі застосовується підсистема `seq_file`.

При реєстрації користувацького файлу викликом `debugfs_create_file()` у структуру `struct file_operations` підключаються готові системні обробники:

```c
static const struct file_operations my_debugfs_fops = {
    .owner   = THIS_MODULE,
    .open    = my_driver_single_open,
    .read    = seq_read,
    .llseek  = seq_lseek,
    .release = single_release,
};
```

Функція `single_open()` зв'язує відкритий файловий дескриптор із конкретною користувацькою функцією відображення `single_show`. Вона автоматично керує виділенням та розширенням внутрішнього буфера `seq_file`, запобігаючи обрізанню даних та випадковим витокам пам'яті ядра.

## 2. Керувальні файли та налаштування tracefs (/sys/kernel/tracing/)

Віртуальна файлова система `tracefs` експортує файли конфігурації та зчитування для трасувальника `ftrace`. Кожен файл представляє конкретний вузол управління кільцевим буфером або фільтрацією подій.

### Механіка керування пам'яттю кільцевих буферів

Кільцевий буфер ftrace виділяється окремо для кожного процесорного ядра системи (per-CPU buffer). Розмір одного буфера регулюється через файл `buffer_size_kb`. За замовчуванням ядро виділяє по 1408 КБ на кожне процесорне ядро. На багатоядерних серверах зі 128 потоками це може вимагати понад 180 МБ оперативної пам'яті.

При виникненні переповнення кільцевого буфера ядро за замовчуванням працює в режимі перезапису (overwrite mode): найновіші події заміщують найстаріші. Цю поведінку можна змінити через файл `options/overwrite`, встановивши `0`, що змусить ядро відкидати нові події при заповненні буфера.

Запис власних логів із простору користувача у трасувальний потік здійснюється через спеціальний файл `trace_marker`. Наприклад, системний демон може виконати системний виклик `write()` у `/sys/kernel/tracing/trace_marker`, що дозволяє точна синхронізувати події користувацького додатка з подіями ядра за спільними часовими мітками.

### Специфікація основних управляючих файлів tracefs

| Файл у tracefs | Тип / Права | Синтаксис використання та опис |
| :--- | :--- | :--- |
| `available_tracers` | RO (0444) | Перелік підтримуваних трасувальників у поточному ядрі.<br>Приклад виводу: `hwlat blk mmiotrace function_graph wakeup_dl wakeup_rt wakeup function nop` |
| `current_tracer` | RW (0644) | Активний двигун трасування.<br>Приклад увімкнення: `echo function_graph > current_tracer`<br>Скидання в пасивний режим: `echo nop > current_tracer` |
| `tracing_on` | RW (0644) | Глобальний вимикач запису в кільцевий буфер.<br>`1` — запис дозволено.<br>`0` — запис призупинено (накопичений вміст буфера зберігається). |
| `trace` | RW (0644) | Статичний зріз вмісту per-CPU кільцевих буферів.<br>Зчитування: `cat trace` (не видаляє дані).<br>Очищення буфера: `echo > trace` |
| `trace_pipe` | RO (0444) | Потоковий блокуючий інтерфейс зчитування.<br>Зчитування `cat trace_pipe` видаляє опрацьовані дані з буфера в реальному часі. |
| `trace_marker` | WO (0220) | Інтерфейс запису користувацьких міток у трасувальний лог ядра.<br>Приклад: `echo "Start benchmark" > trace_marker` |
| `set_ftrace_filter` | RW (0644) | Фільтрація функцій для трасувальника `function`.<br>Приклад: `echo 'vfs_*' > set_ftrace_filter` (трасувати лише функції VFS). |
| `set_ftrace_notrace` | RW (0644) | Виключення функцій із трасування (чорний список).<br>Приклад: `echo 'spin_*' > set_ftrace_notrace` |
| `set_ftrace_pid` | RW (0644) | Фільтрація трасування за PID процесів.<br>Приклад: `echo 1234 > set_ftrace_pid` |
| `buffer_size_kb` | RW (0644) | Розмір кільцевого буфера в кілобайтах **на кожен CPU core**.<br>Приклад: `echo 4096 > buffer_size_kb` (виділити по 4 МБ на ядро). |

## 3. Ієрархія підсистеми подій та динамічних зондів

Статичні точки трасування (tracepoints) організовано в ієрархічні каталоги підсистем у `/sys/kernel/tracing/events/`. Вони розробляються авторами ядра і розміщуються в критичних місцях підсистем керування пам'яттю, мережевого стека, планировщика та системних викликів.

### Структура керування подібними точками (events/<subsystem>/<event>/)

Для кожної конкретної події (наприклад, `events/sched/sched_switch`) доступні такі файли керування:

1. **enable** — бінарний вимикач події. Запис `1` вмикає трасування події, `0` — вимикає.
2. **filter** — вираз фільтрації події за значеннями її полів. Підтримує логічні оператори `&&`, `||`, `!`, а також порівняння чисел та рядків.
   - Синтаксис: `echo 'common_pid == 1024 || common_pid == 2048' > filter`
   - Скидання фільтра: `echo 0 > filter`
3. **format** — файл лише для читання, який описує бінарний макет (layout) структури події. У ньому вказуються зміщення полів у байтах, їхні розміри та знаковість. Опис використовується інструментами `perf`, `trace-cmd` та eBPF для автоматичної десеріалізації полів.
4. **trigger** — налаштування автоматичних дій при настанні події (наприклад, увімкнення іншого трасувальника, запис трасування стеку викликів `stacktrace` або створення зрізу буфера).

### Специфікація динамічних зондів kprobe_events

Файл `/sys/kernel/tracing/kprobe_events` дозволяє створювати динамічні точки перехоплення у будь-якому місці ядра Linux без перекомпіляції його вихідного коду. Механізм `kprobe` підміняє інструкцію за вказаною адресою на точки зупинки (break instruction), перехоплює виконання, витягує значення регістрів і повертає контроль ядру.

#### Формат запису kprobe_events:

```text
p[:[GRP/]EVENT] [MODULE:]SYM[+OFFS]|MEMADDR [FETCHARGS]  # Вхід у функцію (kprobe)
r[:[GRP/]EVENT] [MODULE:]SYM[+OFFS]|MEMADDR [FETCHARGS]  # Повернення з функції (kretprobe)
```

#### Пояснення полів та аргументів витягування:

- **p / r** — тип зонду (`p` — kprobe при вході у функцію, `r` — kretprobe при поверненні з функції).
- **GRP/EVENT** — ім'я групи та події у `/sys/kernel/tracing/events/kprobes/`. Якщо ім'я не вказано, ядро створює ім'я автоматично.
- **SYM+OFFS** — ім'я символу ядра з таблиці `kallsyms` та зміщення в байтах від початку функції (наприклад, `do_sys_open+0x0`).
- **FETCHARGS** — аргументи для витягування значень з регістрів або пам'яті:
  - `%ax`, `%di`, `%si`, `%dx` — зчитування значення архітектурного регістра процесора.
  - `+0(%sp)` — зчитування даних зі зміщенням від вказівника стеку.
  - `+0(%di):string` — розіменування вказівника та зчитування рядочка з пам'яті.
  - `:s32`, `:u64`, `:x32` — примусове приведення типу аргументу.

#### Покроковий приклад створення та вилучення kprobe у терміналі:

```bash
# 1. Створення kprobe на функцію do_sys_open із витягуванням першого аргументу (dfd)
$ echo 'p:my_open_probe do_sys_open dfd=+0(%di):s32' | sudo tee /sys/kernel/tracing/kprobe_events

# 2. Перевірка створення події в ієрархії events
$ ls -l /sys/kernel/tracing/events/kprobes/my_open_probe/

# 3. Увімкнення створеного динамічного зонду
$ echo 1 | sudo tee /sys/kernel/tracing/events/kprobes/my_open_probe/enable

# 4. Перегляд згенерованих подій
$ sudo cat /sys/kernel/tracing/trace_pipe

# 5. Вимкнення та вилучення створеного зонду
$ echo 0 | sudo tee /sys/kernel/tracing/events/kprobes/my_open_probe/enable
$ echo '-:kprobes/my_open_probe' | sudo tee /sys/kernel/tracing/kprobe_events
```

### Специфікація динамічних зондів uprobe_events

Файл `/sys/kernel/tracing/uprobe_events` використовується для динамічного трасування функцій у виконуваних бінарних файлах ELF та спільних бібліотеках простору користувача. На відміну від kprobes, для uprobes вказується шлях до файла у файловій системі та зміщення вхідної точки інструкції в байтах від початку файлу.

#### Формат запису uprobe_events:

```text
p[:[GRP/]EVENT] PATH:OFFSET [FETCHARGS]  # Вхід у функцію простору користувача
r[:[GRP/]EVENT] PATH:OFFSET [FETCHARGS]  # Повернення з функції
```

#### Приклад створення uprobe для моніторингу викликів malloc у бінарному файлі libc:

```bash
# 1. Знаходження зміщення функції malloc у системній бібліотеці libc
$ nm -D /lib/x86_64-linux-gnu/libc.so.6 | grep ' malloc$'
00000000000982d0 T malloc

# 2. Встановлення зонду на зміщення 0x982d0 із витягуванням першого аргументу (%di)
$ echo 'p:user_malloc /lib/x86_64-linux-gnu/libc.so.6:0x982d0 bytes=%di:u64' | sudo tee /sys/kernel/tracing/uprobe_events

# 3. Увімкнення uprobe зонду
$ echo 1 | sudo tee /sys/kernel/tracing/events/uprobes/user_malloc/enable
```
