Користувач висмикує USB-флешку в ту саму мить, коли інша програма тримає відкритим файл із відомостями про цей пристрій. У ядрі 2.4 такий збіг клав машину: єдиного обліку часу життя об'єктів не було, драйвер звільняв свої структури одразу після від'єднання, а відкритий файл у `/proc` лишався з посиланням на вже звільнену пам'ять — наступний `read()` наривався на звернення за недійсним вказівником. Розробники драйверів хаотично записували неструктурований текстовий потік у каталог `/proc/driver/`, а підсистема керування живленням багаторівневих апаратних шин не мала жодної інформації про те, який контролер живить дочірній пристрій і в якому порядку слід зупиняти шини при переході системи у режим сну. Спроба вимкнути живлення материнського контролера до того, як засне підпорядкований периферійний диск, призводила до зависання шини або пошкодження даних на носіях.

Для подолання цієї кризової ситуації у серії ядер Linux 2.5 та 2.6 було розроблено уніфіковану модель пристроїв (англ. *Unified Device Model*) та віртуальну файлову систему `sysfs` (змонтовану в точці `/sys`). В основі sysfs лежить не фізичний дисковий накопичувач, а живий граф об'єктів ядра, побудований на атомарній структурі `kobject`.

## Базовий атом ядра: `struct kobject` та підрахунок посилань

Структура `kobject` (від англ. *kernel object*) є фундаментальним будівельним блоком моделі пристроїв Linux. Вона рідко використовується як самостійна автономна змінна; замість цього її вбудовують (англ. *embed*) всередину більших структур підсистем — `struct device`, `struct module`, `struct bus_type` або `struct device_driver`.

```c
struct kobject {
    const char          *name;
    struct list_head    entry;
    struct kobject      *parent;
    struct kset         *kset;
    const struct kobj_type *ktype;
    struct kernfs_node  *sd;
    struct kref         kref;
    unsigned int state_initialized:1;
    unsigned int state_in_sysfs:1;
    unsigned int state_add_uevent_sent:1;
    unsigned int state_remove_uevent_sent:1;
    unsigned int uevent_suppress:1;
};
```

Кожне поле структури `kobject` виконує строго визначену функцію у побудові графа та керуванні пам'яттю:
- **`name`**: текстовий ідентифікатор об'єкта, який стає ім'ям відповідного каталогу у файловій системі sysfs.
- **`kref`**: атомарний лічильник посилань (`refcount_t`). Узгоджене, парне застосування функцій `kobject_get()` та `kobject_put()` гарантує, що пам'ять структури не буде звільнена доти, доки хоча б один компонент ядра або процес простору користувача тримає посилання на неї.
- **`parent`**: вказівник на батьківський `kobject`. Зв'язки батько-дитина формують точну деревну ієрархію каталогів у `/sys`.
- **`kset`**: вказівник на групу об'єктів або підсистему, до якої належить даний об'єкт.
- **`ktype`**: вказівник на структуру `kobj_type`, яка визначає таблицю операцій та метод звільнення пам'яті.
- **`sd`**: вказівник на легковаговий вузол файлової системи (`kernfs_node`, історично `sysfs_dirent`).
- **Прапори стану (`state_*`)**: набір бітових прапорів, які контролюють внутрішні фази життя об'єкта. Прапор `state_initialized` гарантує, що структура пройшла первинне обнулення. Прапор `state_in_sysfs` вказує на наявність зареєстрованого каталогу у sysfs, а прапори `state_add_uevent_sent` та `state_remove_uevent_sent` захищають ядро від повторного або некоректного відправлення подій гарячого підключення. Прапор `uevent_suppress` дозволяє тимчасово маскувати сповіщення під час масового створення об'єктів.

Ініціалізація та реєстрація `kobject` складається з двох послідовних етапів. На першому етапі функція `kobject_init()` обнуляє структуру, встановлює лічильник `kref` у значення 1 та призначає тип `ktype`. На другому етапі функція `kobject_add()` підв'язує об'єкт до батьківського каталогу, перевіряє унікальність імені та створює записи у файловій системі sysfs. Зручна функція `kobject_create_and_add()` об'єднує динамічне виділення пам'яті зі SLUB-кешу та обидва етапи ініціалізації в один виклик.

Головне правило безпеки ядра полягає у суворій забороні прямого виклику `kfree()` для структури, яка містить `kobject`. Фізичне звільнення пам'яті має відбуватися виключно у зворотному виклику `release`, що входить до складу `struct kobj_type`.

Послідовність зменшення лічильника посилань та звільнення ресурсів має такий вигляд:

```
kobject_put(kobj) ──► kref_put() ──► kref == 0? ──► ktype->release(kobj) ──► kfree(container)
```

Тут важливо не сплутати два різні часи життя: пам'яті самої структури й запису про неї в `/sys`. Пам'ять береже `kref`: доки будь-хто в ядрі тримає посилання, `release` не викличеться, і «використання після звільнення» (англ. *use-after-free*) не станеться. А ось запис у `/sys` спершу був прив'язаний до першого намертво. До Linux 2.6.22 включно відкриття файла атрибута брало `kobject_get()`, а `close()` віддавав посилання назад — отже, забутий у терміналі `cat` тримав об'єкт пристрою живим і не давав прибрати каталог із `/sys` після фізичного від'єднання.

Від 2.6.23 цю прив'язку розрізали: вузол дістав окремий лічильник активних посилань (`s_active`, у сучасному `kernfs` — просто `active`), який утримується лише на час виконання самих `show()` та `store()`. Видалення (`kobject_del()`, `sysfs_remove_group()`) чекає, поки вже запущені обробники повернуться, і після цього вузол мертвий: наступний `read()` на тому самому, ще відкритому дескрипторі поверне `-ENODEV`. Тож висмикнутий пристрій зникає з `/sys` одразу, а програма, що не встигла закрити файл, дістає чесну помилку замість аварії ядра.

Докладніше про історію виникнення цієї інфраструктури та внесок розробників у розв'язання проблеми гарячого відключення обладнання можна дізнатися у вставці [📜 Історія створення sysfs та еволюція від dentry до kernfs](book:unix-linux/sysfs-kobject-sysfs-dirent/hist-sysfs-birth.md).

## Групування та поведінка: `kset` і `kobj_type`

Для керування множинами об'єктів та визначення їхньої поведінки ядро строго розділяє поняття контейнера (`kset`) та таблиці методів (`kobj_type`).

`struct kset` є впорядкованим набором об'єктів `kobject`. Вона містить у собі двозв'язний список (`struct list_head list`), у який за допомогою поля `entry` включено всі дочірні об'єкти даної підсистеми. Ядро використовує цей список для обходу всіх зареєстрованих пристроїв класу або шини. Перебір елементів здійснюється за допомогою макросів списку, таких як `list_for_each_entry()`. Крім того, `kset` сам містить у собі вкладений `kobject`, завдяки чому кожен `kset` відображається у sysfs як окремий каталог високого рівня.

У корені файлової системи `/sys` розташовано стандартний набір каталогів `kset`:
- `/sys/devices/`: глобальне апаратне дерево всіх пристроїв, впорядковане за фізичними шинами підключення.
- `/sys/bus/`: каталоги шин ядра (PCI, USB, I2C, SPI), що містять підкаталоги `devices` та `drivers`.
- `/sys/class/`: логічне групування пристроїв за функціональними класами (мережеві інтерфейси `net`, звукові карти `sound`, блоки накопичувачів `block`, датчики `hwmon`).
- `/sys/block/`: символічні посилання на всі блокові пристрої системи (диски, розділи).
- `/sys/module/`: список усіх завантажених модулів ядра та їхніх параметрів.
- `/sys/kernel/`: глобальні параметри самого ядра та точки входу його діагностичних підсистем.
- `/sys/firmware/`: інтерфейси взаємодії з прошивками платформи (UEFI, ACPI, Device Tree).

Крім організації каталогів, `kset` слугує центром обробки подій гарячого підключення (uevent). Коли будь-який вкладений `kobject` змінює свій стан, саме `kset` перехоплює подію, фільтрує її за допомогою власної таблиці `kset_uevent_ops`, доповнює змінними оточення та транслює у простір користувача.

`struct kobj_type` (`ktype`) описує спільні властивості та операції для об'єктів одного класу:

```c
struct kobj_type {
    void (*release)(struct kobject *kobj);
    const struct sysfs_ops *sysfs_ops;
    const struct attribute_group **default_groups;
};
```

Таблиця `sysfs_ops` містить два фундаментальних методи обробки файлових операцій:
- **`show(kobj, attr, buf)`**: викликається при зчитуванні файла в sysfs. Драйвер знаходить свою батьківську структуру за допомогою макросу `container_of(kobj, struct my_device, kobj)`, форматує значення атрибута і записує його у буфер `buf`.
- **`store(kobj, attr, buf, count)`**: викликається при записі у файл sysfs. Метод зчитує дані з `buf`, валідує їх та оновлює внутрішні параметри драйвера.

Макрос `container_of` виконує арифметичний зсув вказівника на основі макросу `offsetof`, повертаючи вказівник на початок зовнішньої структури пристрою:

```c
struct my_device *dev = container_of(kobj, struct my_device, kobj);
```

Це дозволяє драйверу прозоро переходити від уніфікованого ядерного об'єкта `kobject` до власної специфічної структури даних зі збереженням строгої типізації.

*Структура об'єктів kobject у пам'яті ядра та їх пряме відображення у дерево каталогів і файлів sysfs.*

Повний список методів, сигнатур та макросів для роботи з цими структурами наведено у довіднику [📋 Контракт API: макроси та функції kobject і sysfs](book:unix-linux/sysfs-kobject-sysfs-dirent/api-sysfs-kobject.md).

## Проблема пам'яті та еволюція: `sysfs_dirent` і `kernfs`

У перших випусках серії ядер Linux 2.6 файлова система sysfs будувалася безпосередньо над класичними об'єктами VFS (англ. *Virtual Filesystem*). При реєстрації кожного `kobject` та кожного його атрибута sysfs одразу виділяла у пам'яті ядра об'єкти `struct dentry` (запис каталогу VFS, ~192 байти) та `struct inode` (індексний вузол VFS, ~600 байтів).

На великих серверах із багатьма процесорними ядрами, контролерами накопичувачів, мережевими інтерфейсами та датчиками загальна кількість атрибутів у `/sys` досягала 500 000 і більше. 

Обчислення витрат пам'яті у цій старій схемі демонструвало катастрофічний результат:

```
500 000 атрибутів × (192 B dentry + 600 B inode) ≈ 4·10⁸ байтів ≈ 400 МБ (380 МіБ)
```

Майже 400 мегабайтів оперативної пам'яті ядра витрачалося лише на підтримку файлової структури `/sys` — несвапованої пам'яті SLAB, навіть якщо жоден процес у просторі користувача ніколи не читав ці файли й не заглядав у каталог `/sys`.

Вихід шукали у два кроки. Спершу sysfs дістала власне «сховище» — компактну структуру `struct sysfs_dirent` на кілька десятків байтів замість майже восьмисот на пару `dentry` + `inode`; ці патчі влилися в Linux 2.6.10. Далі структуру зробили первинною: у 2.6.23 у ній з'явився лічильник активних посилань `s_active`, а в 2.6.24 зникло останнє поле `s_dentry` — відтоді важкі об'єкти VFS перестали бути обов'язковою підпорою, і sysfs будувала власне компактне дерево у пам'яті. Хто саме це зробив і чому саме так — у вставці [📜 Історія створення sysfs та еволюція від dentry до kernfs](book:unix-linux/sysfs-kobject-sysfs-dirent/hist-sysfs-birth.md).

Кожен вузол `sysfs_dirent` зберігає лише найнеобхідніші метадані: ім'я вузла, вказівник на батьківський та дочірні вузли, режим доступу POSIX та вказівник на цільовий `kobject` або `attribute`. Спершу дочірні вузли просто нанизувалися у список `s_sibling`, упорядкований за номером `ino`, тож пошук імені в каталозі був лінійним; від Linux 3.5 їх тримає червоно-чорне дерево (англ. *red-black tree*, поле `s_rb`, у сучасному `kernfs_node` — `rb`). Це дає логарифмічний час пошуку `O(log N)` навіть у каталогах із десятками тисяч пристроїв.

Індексний номер вузла `ino` у `sysfs_dirent` виділяється динамічно за допомогою легковагового ядерного розподілювача ідентифікаторів IDA (англ. *ID Allocator*, окремий лічильник `sysfs_ino_ida`), що усуває потребу у створенні повноцінного `struct inode` VFS під час первинної реєстрації об'єкта.

Об'єкти VFS (`dentry` та `inode`) відтепер створюються динамічно за запитом (англ. *on-demand*) — тільки тоді, коли програма викликає системні виклики `open()`, `ls` або `stat()`. Як тільки програма закриває файл, підсистема підчищення VFS (англ. *dentry shrinker*) під тиском пам'яті вільно звільняє об'єкти `dentry`, а внутрішнє дерево продовжує зберігати ієрархію ядра з мінімальними витратами RAM у власному кеші SLUB — тоді він звався `sysfs_dir_cache`, сьогодні це `kernfs_node_cache`.

![Відокремлення внутрішнього дерева kernfs від важких об'єктів VFS](/reference/unix-linux/proc/sysfs-kobject-sysfs-dirent/img/sysfs-dirent-kernfs-vfs.svg)
*Динамічне створення VFS-об'єктів поверх компактного дерева kernfs_node та економія пам'яті ядра.*

У Linux 3.14 кодову базу `sysfs_dirent` виділили у незалежну підсистему [kernfs](book:unix-linux/kernfs-vfs-abstraction-layer): структуру перейменували на `struct kernfs_node`, а sysfs перетворилася на тонку декларативну обгортку над нею. Сьогодні на `kernfs` стоять sysfs і cgroupfs (обидві версії cgroups) — саме вони обирають `CONFIG_KERNFS`; сусідні псевдо-ФС `debugfs` і `tracefs` побудовані окремо, простими засобами VFS, і до `kernfs` не належать.

Сам вузол за роки підріс: до полів епохи `sysfs_dirent` додалися тег простору імен `ns`, вузол червоно-чорного дерева, кешований хеш імені, 64-бітний ідентифікатор `id` та вказівник на `kernfs_iattrs`. Порядок співвідношення від того не змінився — вузол лишається приблизно на порядок меншим за пару `dentry` + `inode`, тобто десятки байтів проти майже восьмисот.

## Покроковий шлях виклику `read()` та `write()` у sysfs

Для глибокого розуміння роботи sysfs розглянемо шлях виконання системного виклику `read()` при зчитуванні атрибута (наприклад, `cat /sys/kernel/demo_kobj/status`):

1. **Звернення у VFS**: Програма у просторі користувача викликає `open()` та `read()`. VFS шукає відповідний `dentry`. Якщо `dentry` відсутній у dcache, VFS інстанціює тимчасовий `dentry` та `inode` на основі метаданих відповідного `kernfs_node`.
2. **Вхід у `kernfs`**: VFS передає виклик операціям файлу — `kernfs_fop_read_iter()` (до Linux 5.11 kernfs мала звичайний `->read`, і функція звалася `kernfs_fop_read()`). Мутекс `of->mutex` конкретного відкритого файла (`struct kernfs_open_file`) упорядковує паралельні звернення й не дає виникнути гонкам (англ. *race conditions*).
3. **Отримання буфера**: Ядро готує тимчасовий буфер розміром щонайбільше `PAGE_SIZE` (4096 байтів): історично sysfs брала цілу сторінку через `get_zeroed_page(GFP_KERNEL)`, сучасний `kernfs` користується заздалегідь виділеним `of->prealloc_buf` або разовим `kmalloc()`.
4. **Делегування драйверу**: `kernfs` дістає `kobject` із поля `priv` батьківського вузла-каталогу, а сам атрибут — із поля `priv` вузла-файла, після чого викликає метод `kobj_type->sysfs_ops->show(kobj, attr, buf)`.
5. **Форматування**: Функція обробника драйвера заповнює буфер за допомогою `sysfs_emit()` та повертає кількість байтів.
6. **Копіювання у простір користувача**: `kernfs` копіює дані у буфер процесу користувача, після чого тимчасовий буфер ядра звільняється.

Аналогічним чином системний виклик `write()` передає дані через `kernfs_fop_write_iter()`. Спочатку VFS перевіряє POSIX-прапори доступу (для запису — `S_IWUSR`), після чого ядро копіює у ядерний буфер не більш ніж одну сторінку (`PAGE_SIZE`) і викликає `sysfs_ops->store(kobj, attr, buf, count)`.

## Ізоляція просторів імен та блокування у kernfs

Сучасна реалізація `kernfs` підтримує віртуалізацію та простори імен (англ. *namespaces*). Для об'єктів, прив'язаних до мережевих просторів імен (network namespaces), один і той самий шлях у sysfs (наприклад, `/sys/class/net/eth0`) відображає різні пристрої залежно від того, у якому контейнері чи просторі імен виконується процес простору користувача.

Внутрішньо `kernfs_node` містить вказівник на простір імен `ns`, а пошук у червоно-чорному дереві враховує як ім'я вузла, так і тег простору імен. Публічна точка входу — `kernfs_find_and_get_ns()`, яка повертає вузол уже з піднятим лічильником посилань:

```c
struct kernfs_node *kernfs_find_and_get_ns(struct kernfs_node *parent,
                                           const char *name, const void *ns);
```

Завдяки цьому контейнери Docker та systemd-nspawn отримують ізольоване представлення пристроїв у sysfs без дублювання самого дерева вузлів у пам'яті ядра.

Дерево `kernfs` захищено семафором читання/запису `kernfs_rwsem` (`struct rw_semaphore`). Операції пошуку та зчитування атрибутів ідуть паралельно під блокуванням на читання (`down_read`), тоді як створення або видалення вузлів вимагають ексклюзивного блокування на запис (`down_write`). Межа тут проходить по версіях: до Linux 5.14 включно дерево захищав один глобальний мутекс `kernfs_mutex`, у 5.15 його замінив глобальний `kernfs_rwsem`, а від 5.17 семафор став окремим для кожного кореня `kernfs` — `root->kernfs_rwsem`, тож sysfs і cgroupfs більше не штовхаються за спільне блокування.

## Динамічна видимість та керування групами: `is_visible`

Під час реєстрації групи атрибутів через `sysfs_create_group()` розробник може керувати динамічним відображенням файлів залежно від можливостей апаратного забезпечення. Для цього у структурі `struct attribute_group` передбачено калбек `is_visible()`:

```c
struct attribute_group {
    const char *name;
    umode_t (*is_visible)(struct kobject *kobj, struct attribute *attr, int index);
    struct attribute **attrs;
    struct bin_attribute **bin_attrs;
};
```

Функція `is_visible()` опитується ядром для кожного атрибута групи при його створенні у sysfs. Вона може повернути:
- Прапори доступу (`0644` або `0444`) — файл створюється у sysfs із вказаними правами.
- Значення `0` — ядро пропускає створення цього атрибута. Це дозволяє розробнику драйвера створювати єдиний статичний масив атрибутів, але автоматично приховувати ті з них, які не підтримуються ревізією поточного чипа.

## Символічні посилання у sysfs (`sysfs_create_link`)

Особливою можливістю sysfs є масове використання символічних посилань. Наприклад, каталог `/sys/class/net/eth0` не є автономним об'єктом, а являє собою символічне посилання на реальний фізичний пристрій у глобальному дереві `/sys/devices/pci0000:00/0000:00:1f.6/net/eth0`.

Це дає операційній системі змогу підтримувати дві паралельні ієрархії:
- Фізичну ієрархію підключення апаратних шин у `/sys/devices/`.
- Логічну класифікацію за типами пристроїв у `/sys/class/` та `/sys/bus/`.

Створення символічного посилання здійснюється функцією `sysfs_create_link(kobj, target_kobj, name)`. Важливо, що символічне посилання у sysfs не створює об'єкта VFS symlink inode на диску. Воно реалізується як той самий легковаговий вузол `kernfs_node` — лише з прапорцем типу `KERNFS_LINK` і вказівником `target_kn` на цільовий вузол у пам'яті; жодного зайвого об'єкта VFS посилання не коштує.

## Порівняльний аналіз псевдофайлових систем ядра

Для чіткої орієнтації у системному програмуванні Linux слід відрізняти призначення трьох головних віртуальних файлових систем ядра:

| Файлова система | Точка монтування | Основне призначення | Гарантії ABI простору користувача |
| :--- | :--- | :--- | :--- |
| **procfs** | `/proc` | Відомості про процеси (`/proc/<pid>/`) та загальний стан ядра (`meminfo`, `cpuinfo`) | Часткові (історичні файли стабільні, розширення змінюються) |
| **sysfs** | `/sys` | Модель пристроїв, об'єкти `kobject`, параметри драйверів, шини та класи | Строгі (стабільний ABI, формат «1 файл = 1 параметр») |
| **debugfs** | `/sys/kernel/debug` | Внутрішнє налагодження ядра, дампи стану та діагностика драйверів | Відсутні (внутрішній інструмент розробників ядра, ABI може змінюватися) |

## Контракт атрибутів sysfs: «Один файл — одне значення»

Файлова система sysfs встановлює суворі правила щодо оформлення файлів атрибутів. На відміну від `/proc`, де дозволено виводити довільні текстові звіти та багатосторінкові таблиці, атрибут sysfs підпорядковується суворому кодексу розробників ядра: «один файл — один параметр».

Атрибути поділяються на два види:
1. **Текстові атрибути (`struct attribute`, `struct kobj_attribute`)**: відображають скалярні числа, розпізнані прапори або короткі рядки стану (наприклад, `4096`, `enabled`, `online`).
2. **Бінарні атрибути (`struct bin_attribute`)**: використовуються для передачі сирих двійкових даних без форматування (наприклад, вміст NVRAM, таблиці ACPI або прошивки мікроконтролерів).

Спеціальна структура `struct bin_attribute` містить розширені методи `read` та `write`, які приймають додатковий аргумент зсуву `loff_t off` та розміру `size_t count`. Це дає змогу простору користувача зчитувати великі масиви бінарних даних за допомогою системних викликів `pread()` та `pwrite()` частинами, наприклад при завантаженні бінарних прошивок у мікроконтролери мережевих адаптерів через `/sys/class/firmware/`.

Основні вимоги до текстових атрибутів:
- **Обмеження буфера `PAGE_SIZE`**: розмір виводу функції `show` не повинен перевищувати одну сторінку пам'яті (зазвичай 4096 байтів). Спроба записати більше даних призводить до обрізання або помилок пам'яті.
- **Символ нового рядка `\n`**: кожен атрибут при читанні має завершуватися символом `\n`. Це забезпечує коректну роботу утиліт shell (`cat`, `grep`, `awk`).
- **Безпечні функції форматування**: у сучасних ядрах обов'язково застосовується `sysfs_emit(buf, fmt, ...)` замість `sprintf`, оскільки `sysfs_emit` перевіряє межі буфера `PAGE_SIZE`. Для послідовного дописування у декілька етапів застосовується функція `sysfs_emit_at(buf, at, fmt, ...)`.

Для реєстрації атрибутів розробники модулів можуть використовувати одиночний виклик `sysfs_create_file()` або груповий виклик `sysfs_create_group()`. Груповий спосіб є кращим, оскільки він гарантує атомарне створення всіх файлів атрибутів і виключає стани, коли процес у просторі користувача намагається прочитати атрибут, який ще не встиг зареєструватися у VFS.

З практичним прикладом написання модуля ядра, який створює власні атрибути у `/sys/kernel/demo_kobj`, можна ознайомитися у вставці [⚙️ Практикум: створення власних kobject та атрибутів у ядрі](book:unix-linux/sysfs-kobject-sysfs-dirent/proj-kobject-custom.md).

## Події гарячого підключення: `uevent` та `netlink`

Коли новий пристрій підключається до шини PCI або USB, ядро має сповістити про це менеджер пристроїв у просторі користувача (`systemd-udevd`). Цей механізм реалізовано через функцію `kobject_uevent()`.

При виклику `kobject_uevent(kobj, KOBJ_ADD)` ядро виконує такі дії:
1. Перевіряє прапори придушення подій `uevent_suppress`. Якщо сповіщення дозволено, ядро формує текстовий масив змінних оточення: `ACTION=add`, `DEVPATH=/devices/pci0000:00/...`, `SUBSYSTEM=usb`, `DEVTYPE=usb_device`, `SEQNUM=1234` і — для пристроїв, що мають вузол у `/dev`, — пару `MAJOR`/`MINOR` та `DEVNAME`. Для самих USB-пристроїв старший номер сталий: `USB_DEVICE_MAJOR` дорівнює 189, а молодший ядро рахує з номерів шини й пристрою, тож п'ятий пристрій на першій шині дає `MAJOR=189`, `MINOR=4`, `DEVNAME=bus/usb/001/005`.
2. Атомарно інкрементує глобальний лічильник послідовності подій ядра `uevent_seqnum`.
3. Транслює повідомлення у простір користувача через сокет Netlink спеціалізованого протоколу `NETLINK_KOBJECT_UEVENT`.
4. Демон `systemd-udevd` зчитує повідомлення із сокета й зіставляє його з правилами у каталогах `/usr/lib/udev/rules.d/` та `/etc/udev/rules.d/`: довантажує потрібні модулі (`modprobe`), доводить права, власника й символічні назви у `/dev/`. Сам вузол пристрою за цією ж парою `MAJOR`/`MINOR` створює ядро — через `devtmpfs`, а не udev.

Послідовне порядкове число `SEQNUM` дає змогу менеджеру `udevd` відновлювати точний порядок виникнення подій навіть у разі паралельної асинхронної ініціалізації багатьох пристроїв на багатоядерних системах.

Програма у просторі користувача може зчитувати події uevent безпосередньо через сокет Netlink.

:::tabs
```c
/* Зчитування подій uevent через Netlink сокет у C */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <linux/netlink.h>

int main(void) {
    int fd = socket(PF_NETLINK, SOCK_RAW, NETLINK_KOBJECT_UEVENT);
    if (fd < 0) return 1;

    struct sockaddr_nl nls;
    memset(&nls, 0, sizeof(nls));
    nls.nl_family = AF_NETLINK;
    nls.nl_pid = getpid();
    nls.nl_groups = -1; /* Слухати всі групи uevent */

    if (bind(fd, (struct sockaddr *)&nls, sizeof(nls)) < 0) {
        close(fd);
        return 1;
    }

    char buf[4096];
    while (1) {
        ssize_t len = recv(fd, buf, sizeof(buf) - 1, 0);
        if (len > 0) {
            buf[len] = '\0';
            printf("Uevent: %s\n", buf);
        }
    }

    close(fd);
    return 0;
}
```

```cpp
// Зчитування подій uevent через Netlink сокет у C++ (RAII, виняток замість -1)
#include <iostream>
#include <vector>
#include <string_view>
#include <system_error>
#include <cerrno>
#include <unistd.h>
#include <sys/socket.h>
#include <linux/netlink.h>

class UeventSocket {
    int fd_ = -1;
public:
    UeventSocket() {
        fd_ = socket(PF_NETLINK, SOCK_RAW, NETLINK_KOBJECT_UEVENT);
        if (fd_ < 0) throw std::system_error(errno, std::generic_category());

        sockaddr_nl nls{};
        nls.nl_family = AF_NETLINK;
        nls.nl_pid = getpid();
        nls.nl_groups = -1;

        if (bind(fd_, reinterpret_cast<sockaddr*>(&nls), sizeof(nls)) < 0) {
            int err = errno;
            close(fd_);
            fd_ = -1;
            throw std::system_error(err, std::generic_category());
        }
    }

    UeventSocket(const UeventSocket&) = delete;
    UeventSocket& operator=(const UeventSocket&) = delete;

    ~UeventSocket() {
        if (fd_ >= 0) close(fd_);
    }

    void listen_events() {
        std::vector<char> buffer(4096);
        while (true) {
            ssize_t len = recv(fd_, buffer.data(), buffer.size(), 0);
            if (len > 0) {
                std::cout << "Uevent: "
                          << std::string_view(buffer.data(), static_cast<size_t>(len)) << "\n";
            }
        }
    }
};

int main() {
    try {
        UeventSocket uevent;
        uevent.listen_events();
    } catch (const std::exception& e) {
        std::cerr << "Помилка uevent сокета: " << e.what() << "\n";
        return 1;
    }
    return 0;
}
```

> 🔧 **Навіщо це.**
> Архітектура `kobject` та `sysfs` дає розробникам системного програмного забезпечення гарантію безпеки при роботі з обладнанням. Завдяки атомарному лічильнику `kref` утиліти простору користувача можуть безпечно опитувати параметри пристроїв у `/sys`, не ризикуючи обвалити ядро при висмикуванні кабелю. Легковагове дерево `kernfs` дозволяє операційній системі підтримувати мільйони апаратних атрибутів із мізерними витратами RAM, а сокети uevent забезпечують миттєву реакцію демонів автоматизації (`udevd`) на будь-які зміни в обладнанні.
