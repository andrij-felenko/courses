# 📜 Еволюція RAM-дисків у Linux: від /dev/ram до tmpfs

Вставка пояснює історичні причини відмови ядра Linux від фіксованих блокових пристроїв оперативної пам'яті (`ramdisk`) та легковагової файлової системи `ramfs` на користь динамічної підсистеми `shmem` і ВФС `tmpfs`.

## Ера блокових пристроїв ramdisk (/dev/ram)

У перших версіях ядра Linux (серії 0.9x та 1.x/2.0) єдиним способом тримати файлову систему в оперативній пам'яті був драйвер блокового пристрою RAM-диска (`drivers/block/brd.c` або псевдопристрої `/dev/ram0` ... `/dev/ram15`).

Ідея здавалася простою: ядро резервувало статичний неперервний шматок фізичної пам'яті (розмір задавався параметром завантаження ядра `ramdisk_size=8192`), форматувало його звичайною дисковою файловою системою (наприклад, ext2 за допомогою `mke2fs /dev/ram0`) та монтувало в потрібну точку файлового дерева.

Однак ця концепція мала два фундаментальні архітектурні недоліки:

1. **Марнотратство пам'яті через подвійне кешування (Double Caching):**
   Коли процес зчитував файл з екземпляра ext2, змонтованого на `/dev/ram0`, шар VFS сприймав `/dev/ram0` як звичайний блоковий пристрій. В результаті байти з блоків пам'яті ramdisk копіювалися в [кеш сторінок VFS](book:unix-linux/page-cache-durability). Один і той самий вміст файла дублювався в оперативній пам'яті двічі: один раз у зоні пам'яті блокового пристрою ramdisk, і вдруге — у сторінковому кеші ядра.

2. **Жорстке негнучке резервування:**
   Виділений під `/dev/ram` обсяг пам'яті віднімався від загального фонду RAM системи намолодо під час завантаження ядра. Навіть якщо на ramdisk лежав один файл розміром у 4 КБ, зарезервовані 64 МБ були недоступні для інших процесів та кешування дискового вводу-виводу.

```
Схема подвійного кешування у старій схемі /dev/ram:

Пам'ять RAM:  [ Пам'ять пристрою /dev/ram0 ]  ──копіювання VFS──>  [ Page Cache ядра ]  ──>  Процес
                 (ext2 блоки даних)                               (struct page)
```

## Виникнення ramfs як простішого розв'язку

Наприкінці 1990-х років Лінус Торвальдс (Linus Torvalds) та Аль Віро (Al Viro) переписали підсистему VFS і [кеш сторінок](book:unix-linux/page-cache-durability). Під час розробки ядра Linux 2.4 Торвальдс продемонстрував, що сам Page Cache уже є повноцінною файловою системою в пам'яті.

Так з'явилася псевдофайлова система `ramfs`. Її реалізація займала менше ніж кілька сотень рядків C-коду в файлі `fs/ramfs/inode.c`. Вона не мала власного блокового пристрою і працювала прямо над Page Cache: коли процес робив виклик `write()`, ядро виділяло сторінку пам'яті `struct page`, асоціювало її з `inode` та клало у кеш сторінок. Ніякого подвійного копіювання чи блокового пристрою більше не було.

Проте `ramfs` створила нову критичну проблему безпеки: у ній відсутні будь-які обмеження на максимальний обсяг пам'яті або кількість інодів. Будь-який звичайний користувач міг записати у змонтовану `ramfs` файл розміром у весь обсяг фізичної RAM і спровокувати аварійну зупинку операційної системи через вичерпання пам'яті (Out-Of-Memory, OOM-killer). Крім того, сторінки `ramfs` принципово не вміли витискатися у swap-простір.

## Народження tmpfs та уніфікація shmem у ядрі Linux 2.4.4

Для вирішення проблем безпеки та надання можливості витискання даних у swap розробник Крістоф Рохланд (Christoph Rohland) запропонував нову підсистему під назвою `shm fs` (пізніше перейменовану в `tmpfs`), яка була офіційно включена до складу ядра Linux 2.4.4 у травні 2001 року.

Головною інновацією Рохланда стала уніфікація двох досі незалежних підсистем ядра:
* Розділюваної пам'яті System V (`shmget`, `shmat`);
* Тимчасової файлової системи в оперативній пам'яті (`tmpfs`).

Рохланд створив підсистему `shmem` (`mm/shmem.c`), яка виступає універсальним двигуном анонімної оперативності. `tmpfs` стала публічним файловим інтерфейсом над `shmem`, отримавши підтримку:
1. Лімітів обсягу пам'яті (`size=`) та кількості інодів (`nr_inodes=`);
2. Інтеграції з фоновим демон-деструктором пам'яті `kswapd`, що дозволило виносити невикористовувані сторінки `tmpfs` на диск у swap;
3. Динамічного повернення пам'яті операційній системі при викликах `unlink()` та `truncate()`.

### Еволюція в ядрі 2.6 та сучасний розвиток

З виходом ядра Linux 2.6 підсистема `shmem` отримала повну підтримку POSIX Shared Memory (`/dev/shm`), а у версії Linux 3.17 розробник Девід Геррманн (David Herrmann) додав системний виклик `memfd_create()`.

Паралельно з розвитком контейнеризації (Docker, Podman, LXC/LXD) та ініціалізатора `systemd`, `tmpfs` стала основою ізоляції процесів:
* Каталоги `/run` та `/sys/fs/cgroup` монтуються як `tmpfs` для забезпечення швидкого доступу до службових підошв без зносу накопичувача.
* Застосунки у пісочницях (Flatpak, Snap) отримують власні приватні монтування `tmpfs` для ізоляції файлового середовища.

Відтоді `tmpfs` повністю замінила застарілі `ramdisk` та `ramfs` у роль основного середовища для тимчасових даних `/tmp`, каталогу рантайм-станцій `/run` та об'єктів IPC у Unix/Linux.
