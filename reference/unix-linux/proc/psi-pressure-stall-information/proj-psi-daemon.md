# ⚙️ Практична реалізація демона моніторингу голодування ресурсу пам'яті

Для проактивного захисту системи від зависань у стані пробуксовування (thrashing) системні сервіси та демони моніторингу налаштовують тригери PSI й очікують на події через асинхронні системні виклики `epoll()`. Отримавши сповіщення про перевищення допустимого тиску пам'яті, демон може вжити запобіжних заходів: вивантажити тимчасові кеші додатка, відхилити нові вхідні з'єднання або надіслати сигнал завершення `SIGKILL` ресурсомісткій контрольно-групі.

Цей проєктний довідник містить повну практичну реалізацію демона моніторингу голодування пам'яті, який реєструє тригер `some 150000 1000000` (150 мс голодування у 1-секундному вікні), обробляє події `EPOLLPRI` та здійснює проактивне реагування на ресурсові кризи.

## Архітектурний дизайн демона моніторингу

Розробка системних демонів реального часу для ядра Linux вимагає виконання послідовних етапів підготовки середовища та обробки подій:

1. **Ініціалізація та відкриття вузла PSI:** Файл `/proc/pressure/memory` (або `<cgroup>/memory.pressure`) відкривається у режимі читання-запису з прапорами `O_RDWR | O_NONBLOCK`. Запис потрібен для реєстрації тригера, читання — щоб після події дізнатися числа; неблокуючий режим — конвенція, успадкована від `lmkd` і прикладу в документації ядра (про те, від чого він захищає насправді, а від чого ні, — нижче, у розборі пасток).
2. **Конфігурація тригера в ядрі:** Запис рядка формату `"some 150000 1000000"` ініціалізує у ядрі динамічне вікно відстеження тривалістю 1 секунда (1 000 000 мікросекунд) із порогом допустимої затримки 150 000 мікросекунд (150 мс). Приріст затримки ядро звіряє з порогом десять разів за вікно — тобто раз на 100 мс для цього тригера.
3. **Реєстрація у мультиплексорі подій (epoll):** Файловий дескриптор додається до системного мультиплексора `epoll` із прапором `EPOLLPRI` (Priority Data). Використання `epoll` замість опитування у циклі дозволяє повністю звільнити процесорний час: демон перебуває у стані сну, і ядро будить його лише при виникненні аномального тиску.
4. **Обробка подій та позиціонування lseek:** Після повернення керування з виклику `epoll_wait()` демон обов'язково викликає `lseek(psi_fd, 0, SEEK_SET)`. Це необхідно тому, що файли у procfs є віртуальними: після надходження події позиція читача не скидається автоматично на початок файлу. Потім демон зчитує актуальні рядки `some` та `full`, витягуючи значення `avg10` та `total`.
5. **Виконання проактивного реагування (OOM Remediation):** Отримавши підтвердження високого тиску пам'яті, демон приймає рішення про ліквідацію джерела тиску. Сучасні демони спираються на механізм атомарного завершення cgroup через файл `cgroup.kill` (доступний у cgroups v2 починаючи з ядра Linux 5.14). Запис значення `1` у файл `<cgroup_path>/cgroup.kill` надсилає незахоплюваний сигнал `SIGKILL` усім процесам даної контрольної групи одночасно, запобігаючи гонкам процесів (race conditions).

### Захист пам'яті та системне налаштування пріоритету

Щоб демон моніторингу сам не став жертвою вичерпання пам'яті під час критичного тиску, високонадійні сервіси застосовують системні виклики захисту:
- **Блокування пам'яті `mlockall(MCL_CURRENT | MCL_FUTURE)`:** Запобігає вивантаженню виконуваного коду та стека демона в swap або direct reclaim.
- **Призначення реального часу `sched_setscheduler()`:** Налаштування класу `SCHED_FIFO` з помірним пріоритетом гарантує, що демон отримає процесорний квант миттєво після розбудження з `epoll_wait()`.
- **Захист від OOM `oom_score_adj`:** Запис значення `-1000` у файл `/proc/self/oom_score_adj` унеможливлює знищення самого демона ядерним OOM Killer.

## Повна реалізація у просторі користувача: C та C++

Нижче наведено паралельні ідіоматичні реалізації демона моніторингу. Реалізація мовою C спирається на прямі POSIX системні виклики та стандартні файлові дескриптори, тоді як реалізація на C++ корисна для інтеграції у сучасні сервіси завдяки використанню патерну RAII, автоматичному управлінню ресурсами та безпечній обробці помилок.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/epoll.h>
#include <signal.h>
#include <errno.h>

#define PSI_MEMORY_PATH "/proc/pressure/memory"
#define TRIGGER_CMD "some 150000 1000000"
#define BUFFER_SIZE 512

static volatile sig_atomic_t g_running = 1;

static void handle_signal(int sig) {
    (void)sig;
    g_running = 0;
}

static void parse_and_log_psi(const char *buffer) {
    float avg10 = 0.0f, avg60 = 0.0f, avg300 = 0.0f;
    unsigned long long total = 0;

    if (sscanf(buffer, "some avg10=%f avg60=%f avg300=%f total=%llu",
               &avg10, &avg60, &avg300, &total) == 4) {
        printf("[PSI MONITOR C] КРИТИЧНИЙ ТИСК! avg10=%.2f%% avg60=%.2f%% total=%llu us\n",
               avg10, avg60, total);
    } else {
        printf("[PSI MONITOR C] Сирий вивід PSI:\n%s\n", buffer);
    }
}

static void handle_psi_event(int psi_fd) {
    char buf[BUFFER_SIZE];
    
    /* Переміщення вказівника на початок файлу перед читанням */
    if (lseek(psi_fd, 0, SEEK_SET) < 0) {
        perror("Помилка lseek на psi_fd");
        return;
    }

    ssize_t bytes_read = read(psi_fd, buf, sizeof(buf) - 1);
    if (bytes_read > 0) {
        buf[bytes_read] = '\0';
        parse_and_log_psi(buf);
        // Тут здійснюються дії OOM Remediation (наприклад, запис '1' у cgroup.kill)
    } else if (bytes_read < 0) {
        if (errno != EAGAIN && errno != EWOULDBLOCK) {
            perror("Помилка читання даних PSI");
        }
    }
}

int main(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = handle_signal;
    sigaction(SIGINT, &sa, NULL);
    sigaction(SIGTERM, &sa, NULL);

    int psi_fd = open(PSI_MEMORY_PATH, O_RDWR | O_NONBLOCK);
    if (psi_fd < 0) {
        perror("Не вдалося відкрити " PSI_MEMORY_PATH);
        return EXIT_FAILURE;
    }

    /* Запис тригера: some 150ms / 1000ms */
    ssize_t written = write(psi_fd, TRIGGER_CMD, strlen(TRIGGER_CMD));
    if (written < 0) {
        perror("Не вдалося записати тригер PSI");
        close(psi_fd);
        return EXIT_FAILURE;
    }

    int epoll_fd = epoll_create1(0);
    if (epoll_fd < 0) {
        perror("Не вдалося створити epoll instance");
        close(psi_fd);
        return EXIT_FAILURE;
    }

    struct epoll_event ev;
    memset(&ev, 0, sizeof(ev));
    ev.events = EPOLLPRI;
    ev.data.fd = psi_fd;

    if (epoll_ctl(epoll_fd, EPOLL_CTL_ADD, psi_fd, &ev) < 0) {
        perror("Не вдалося додати psi_fd до epoll");
        close(epoll_fd);
        close(psi_fd);
        return EXIT_FAILURE;
    }

    printf("Демон PSI (C) запущений. Очікування на події тиску пам'яті...\n");

    struct epoll_event events[1];
    while (g_running) {
        int nfds = epoll_wait(epoll_fd, events, 1, 1000);
        if (nfds < 0) {
            if (errno == EINTR) continue;
            perror("Помилка в epoll_wait");
            break;
        }

        if (nfds > 0 && (events[0].events & EPOLLPRI)) {
            handle_psi_event(psi_fd);
        }
    }

    printf("Завершення роботи демона PSI (C)...\n");
    close(epoll_fd);
    close(psi_fd);
    return EXIT_SUCCESS;
}
```

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <array>
#include <system_error>
#include <utility>
#include <cerrno>
#include <csignal>
#include <cstdio>
#include <unistd.h>
#include <fcntl.h>
#include <sys/epoll.h>

namespace sys {

// RAII обгортка для безпечного володіння файловими дескрипторами
class UniqueFd {
    int fd_{-1};
public:
    constexpr UniqueFd() noexcept = default;
    explicit UniqueFd(int fd) noexcept : fd_(fd) {}
    ~UniqueFd() { reset(); }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;

    UniqueFd(UniqueFd&& other) noexcept : fd_(other.release()) {}
    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            reset(other.release());
        }
        return *this;
    }

    [[nodiscard]] int get() const noexcept { return fd_; }
    [[nodiscard]] bool valid() const noexcept { return fd_ >= 0; }

    int release() noexcept {
        int old = fd_;
        fd_ = -1;
        return old;
    }

    void reset(int new_fd = -1) noexcept {
        if (fd_ >= 0) {
            ::close(fd_);
        }
        fd_ = new_fd;
    }
};

} // namespace sys

class PsiMonitor {
    static constexpr std::string_view kMemoryPath = "/proc/pressure/memory";
    static constexpr std::string_view kTriggerSpec = "some 150000 1000000";

    sys::UniqueFd psi_fd_;
    sys::UniqueFd epoll_fd_;
    bool running_{true};

public:
    void init() {
        int raw_psi = ::open(kMemoryPath.data(), O_RDWR | O_NONBLOCK);
        if (raw_psi < 0) {
            throw std::system_error(errno, std::generic_category(), "open " + std::string(kMemoryPath));
        }
        psi_fd_.reset(raw_psi);

        ssize_t written = ::write(psi_fd_.get(), kTriggerSpec.data(), kTriggerSpec.size());
        if (written < 0) {
            throw std::system_error(errno, std::generic_category(), "write PSI trigger");
        }

        int raw_epoll = ::epoll_create1(0);
        if (raw_epoll < 0) {
            throw std::system_error(errno, std::generic_category(), "epoll_create1");
        }
        epoll_fd_.reset(raw_epoll);

        epoll_event ev{};
        ev.events = EPOLLPRI;
        ev.data.fd = psi_fd_.get();

        if (::epoll_ctl(epoll_fd_.get(), EPOLL_CTL_ADD, psi_fd_.get(), &ev) < 0) {
            throw std::system_error(errno, std::generic_category(), "epoll_ctl ADD");
        }
    }

    void stop() noexcept {
        running_ = false;
    }

    void run_loop() {
        std::cout << "Демон PSI (C++) запущений. Очікування подій...\n";
        std::array<epoll_event, 1> events{};

        while (running_) {
            int nfds = ::epoll_wait(epoll_fd_.get(), events.data(), static_cast<int>(events.size()), 1000);
            if (nfds < 0) {
                if (errno == EINTR) continue;
                throw std::system_error(errno, std::generic_category(), "epoll_wait failure");
            }

            if (nfds > 0 && (events[0].events & EPOLLPRI)) {
                on_pressure_event();
            }
        }
        std::cout << "Демон PSI (C++) успішно зупинений.\n";
    }

private:
    void on_pressure_event() {
        std::array<char, 512> buffer{};
        if (::lseek(psi_fd_.get(), 0, SEEK_SET) < 0) {
            std::cerr << "Помилка lseek на psi_fd\n";
            return;
        }

        ssize_t count = ::read(psi_fd_.get(), buffer.data(), buffer.size() - 1);
        if (count > 0) {
            buffer[count] = '\0';
            log_event_details(buffer.data());
        } else if (count < 0 && errno != EAGAIN && errno != EWOULDBLOCK) {
            std::cerr << "Помилка читання даних PSI в C++\n";
        }
    }

    void log_event_details(const char* raw_text) {
        float avg10 = 0.0f, avg60 = 0.0f, avg300 = 0.0f;
        unsigned long long total = 0;

        if (std::sscanf(raw_text, "some avg10=%f avg60=%f avg300=%f total=%llu",
                        &avg10, &avg60, &avg300, &total) == 4) {
            std::cout << "[УВАГА C++] Виявлено тиск пам'яті! avg10=" << avg10 
                      << "% avg60=" << avg60 << "% total=" << total << " us\n";
        } else {
            std::cout << "[УВАГА C++] Сирий вивід PSI:\n" << raw_text;
        }
    }
};

static PsiMonitor* g_monitor_ptr = nullptr;

static void signal_handler(int sig) {
    (void)sig;
    if (g_monitor_ptr) {
        g_monitor_ptr->stop();
    }
}

int main() {
    try {
        PsiMonitor monitor;
        g_monitor_ptr = &monitor;

        struct sigaction sa{};
        sa.sa_handler = signal_handler;
        ::sigaction(SIGINT, &sa, nullptr);
        ::sigaction(SIGTERM, &sa, nullptr);

        monitor.init();
        monitor.run_loop();
    } catch (const std::exception& ex) {
        std::cerr << "Помилка демона: " << ex.what() << '\n';
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

## Детальний розбір алгоритмів та патернів реалізації

Розглянемо ключові відмінності між реалізаціями та інженерні рішення, закладені в код.

### 1. Використання патерну RAII у C++ (UniqueFd)

У реалізації мовою C++ управління файловими дескрипторами винесено у клас `sys::UniqueFd`. Завдяки цьому при виникненні будь-якого винятку (наприклад, винятку `std::system_error` при відсутності файлу procfs) конструктори гарантують автоматичний виклик `close()` для всіх вже відкритих дескрипторів. Це унеможливлює витоки файлових дескрипторів у тривало працюючих сервісах без необхідності писати громіздкі блоки `goto out`, характерні для коду C.

### 2. Атомарне завершення через cgroup.kill

При виявленні критичного голодування пам'яті застарілі демони знаходили PID найжадібнішого процесу та надсилали йому `kill(pid, SIGKILL)`. Проте в багатопотокових середовищах та контейнерах цей підхід є вразливим до гонок PID (PID reuse race): процес міг завершитися сам до моменту надсилання сигналу, а його PID міг бути повторно виділений іншому, цілком критичному системному процесу.

Використання файлу `cgroup.kill` у cgroups v2 усуває цю проблему. Демон відкриває файл `<cgroup_path>/cgroup.kill` і записує туди рядок `"1"`. Ядро атомарно надсилає `SIGKILL` усім потокам даної cgroup в одному контексті, гарантуючи повне та безпечне очищення ресурсів групи.

### 3. Безпечна обробка сигналів завершення та прапори sig_atomic_t

Для коректної інтеграції з системним менеджером `systemd` демон повинен підтримувати асинхронні сигнали `SIGTERM` та `SIGINT`. У C-реалізації використовується змінна `volatile sig_atomic_t g_running`, що гарантує атомарний запис прапора при приході сигналу без ризику виникнення станів гонки (data race) між обробником сигналу та головним циклом `epoll_wait()`. Встановлений таймаут 1000 мс у виклику `epoll_wait()` дозволяє періодично перевіряти стан прапора та завершувати роботу демона із закриттям ресурсів.

## Особливості роботи з epoll у режимах Level-Triggered та Edge-Triggered

Тригер PSI поводиться не так, як звичайне джерело даних. Ядро тримає для нього однобітовий прапор `event` і скидає його вже під час опитування, тож навіть у типовому режимі контролю рівня (level-triggered) `EPOLLPRI` приходить по разу на подію, а не безперервно, доки тиск високий. Понад це ядро саме обмежує частоту: у межах одного вікна тригер сповіщає лише один раз. Тому демон не має права рахувати кількість подій як міру тяжкості кризи — про тяжкість каже тільки прочитане з файлу число `avg10`. Прапор `EPOLLET` при такій семантиці нічого не додає, і стандартний level-triggered лишається правильним вибором.

## Мульти-ресурсний моніторинг у єдиному реакторі epoll

У складному виробничому середовищі демон моніторингу часто повинен відстежувати голодування не лише пам'яті, а й дискового вводу/виводу та процесорного часу одночасно. Архітектура `epoll` дозволяє реалізувати це без створення додаткових операційних потоків.

Демон відкриває три окремих файлових дескриптори:
- `fd_cpu = open("/proc/pressure/cpu", O_RDWR | O_NONBLOCK);`
- `fd_mem = open("/proc/pressure/memory", O_RDWR | O_NONBLOCK);`
- `fd_io  = open("/proc/pressure/io", O_RDWR | O_NONBLOCK);`

Після запису відповідних порогів у кожен із них (`"some 200000 1000000"` для CPU, `"some 150000 1000000"` для Memory, `"full 100000 1000000"` для I/O), усі три дескриптори реєструються у єдиному екземплярі `epoll` за допомогою викликів `epoll_ctl(..., EPOLL_CTL_ADD, fd, &ev)`.

Поле `ev.data.fd` або користувацька структура в `ev.data.ptr` дозволяє обробнику циклу точно ідентифікувати, який саме ресурс спричинив спрацювання тригера, та вжити точкових заходів реагування (наприклад, зменшити I/O weight для дискових подій або завершити cgroup при критичному тиску пам'яті).

## Динамічний обхід дерев cgroups v2 у контейнерних кластерах

У високонавантажених Kubernetes-вузлах демони моніторингу (на кшталт `node-problem-detector` чи локальних OOM-вартів) виконують динамічний моніторинг ієрархії cgroups v2.

Демон відкриває каталог `/sys/fs/cgroup/kubepods.slice/` і через `inotify` або регулярний обхід дерев знаходить нові файли `memory.pressure` для новостворених Pod-ів. Відкривши дескриптор `memory.pressure` підпорядкованого контейнера, демон реєструє тригер у ядрі та додає `fd` до загального реактора `epoll`.

Якщо конкретний Pod починає створювати тиск `memory full` вище порога, заданого політикою вузла, демон ідентифікує відповідний cgroup path і здійснює проактивне вивантаження контейнера через `cgroup.kill`, не чекаючи, поки тиск розповсюдиться на увесь хост-вузол і призведе до зупинки сусідніх системних служб.

## Особливості поведінки при використанні стисненої підкачки zRAM

Коли операційна система Linux використовує блок-пристрій стисненої оперативної пам'яті zRAM як основний простір підкачки (swap device), динаміка виникнення подій PSI має важливі відмінності:
- **Тиск лягає на `memory`, а не на `io`:** шлях підкачки й тут проходить через блоковий пристрій — zRAM саме ним і є, — але вміст нікуди не їде: запит обслуговується стисненням чи розпакуванням просто в контексті процесу, що його подав, і на момент повернення з `submit_bio()` операція вже завершена. Задачі просто нема на чому заснути, тож звичайного для дискового swap очікування в `io_schedule()` не виникає, а `TSK_IOWAIT` не вмикається. Саму затримку ядро при цьому рахує: шлях читання сторінки з swap обгорнуто в `psi_memstall_enter()`, тому зростає `memory`. Читати це як «`io` при zRAM завжди нуль» усе-таки не варто: у zRAM є режим витіснення холодних сторінок на справжній накопичувач (`backing_dev`), і тоді ввід/вивід повертається — разом із затримками, які метрика `io` чесно покаже.
- **Вплив на швидкодію CPU:** стиснення сторінок у zRAM виконує той самий процесор, тож обмін пам'яті на диск перетворюється на обмін пам'яті на такти CPU й дає короткочасні сплески `cpu some`. Демон, який дивиться лише на `memory`, побачить половину картини: на вузлі з zRAM пам'ять і процесор перестають бути незалежними ресурсами.

## Інтеграція з трасуванням eBPF та вимірювання затримок у ядрі

Для систем високої точності моніторингу користувацький демон може доповнюватися програмою трасування eBPF. Власних tracepoint-ів PSI не має, тож чіплятися доводиться до самих функцій обліку — `kprobe:psi_memstall_enter` і `kprobe:psi_memstall_leave`. У той час як тригер PSI у procfs сповіщає про сам факт перевищення порогу затримки у вікні, програма eBPF дозволяє зібрати на вході в `psi_memstall_enter()` точний стек викликів ядра (kernel stack trace) — тобто побачити, хто саме завів процес у затримку.

Завдяки цьому інженери отримують не лише сповіщення про факт дефіциту пам'яті, а й чітку причину: наприклад, конкретний системний виклик `mmap()`, виклики allocation у драйвері відеокарти або масоване сканування каталогів у файловій системі ext4.

Окрім цього, інтеграція zRAM з eBPF розширеннями дозволяє будувати теплові карти (heatmaps) розподілу часу стиснення та розпакування сторінок у контексті окремих cgroups, даючи інженерам вичерпний інструментарій для проектування високонавантажених серверних систем.

## Інтеграція у виробничі конфігурації systemd та Kubernetes

Для розгортання демона PSI в операційному середовищі створюється системний unit-файл `/etc/systemd/system/psi-guardian.service`:

```ini
[Unit]
Description=PSI Memory Stall Monitoring Daemon
After=syslog.target network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/psi_daemon
Restart=always
RestartSec=3s
OOMScoreAdjust=-1000
CPUSchedulingPolicy=fifo
CPUSchedulingPriority=50
ProtectSystem=strict
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

Використання `OOMScoreAdjust=-1000` виключає демон зі списку потенційних жертв OOM Killer, а пара `CPUSchedulingPolicy=fifo` / `CPUSchedulingPriority=50` переводить демон у клас реального часу — так він витісняє звичайні задачі одразу після пробудження, не чекаючи своєї черги нарівні з навантаженням, яке саме й спричинило кризу.

## Повна діагностика пасток реалізації та крайових випадків

Під час розробки високонадійних системних демонів на основі тригерів PSI необхідно враховувати шість фундаментальних інженерних пасток.

### 1. Необхідність позиціонування lseek при читанні procfs
У звичайних файлах системний виклик `read()` переміщує файловий вказівник уперед на кількість прочитаних байтів — і тут поводиться так само. Уся відмінність у тому, що подія `EPOLLPRI` вказівника не чіпає: він лишається там, де його покинуло попереднє читання, тобто в кінці вмісту. Другий `read()` без перемотування впирається в цей кінець і повертає 0 байтів (EOF), тож демон не побачить ані `avg10`, ані `total`. Тому `lseek(fd, 0, SEEK_SET)` перед кожним читанням обов'язковий: він змушує `seq_file` заново згенерувати вміст — уже зі свіжими числами.

### 2. Прапор O_NONBLOCK і те, чого він насправді не рятує
Файли PSI відкривають із `O_RDWR | O_NONBLOCK` — так роблять і `lmkd`, і приклад у документації ядра. Варто, однак, розуміти межу цієї обачності. Саме читання `/proc/pressure/*` не блокує: `psi_show()` друкує готові числа з накопичувачів і повертається. Небезпека інша й тихіша: `read()` на файлі `seq_file` виділяє під вивід буфер у ядрі, а виділення пам'яті на вузлі, який уже пробуксовує, саме може завести викликача в direct reclaim — тобто демон затримається рівно там, де мав діяти. `O_NONBLOCK` цього не скасовує; його скасовує `mlockall()` плюс резервування буферів наперед, до першої кризи. Прапор лишається як дешевий запобіжник проти блокування у сценаріях, де той самий цикл `epoll` обслуговує ще й сокети та канали.

### 3. Хто скидає прапор події EPOLLPRI
Прапор події скидає саме ядро, і робить це в момент опитування: `psi_trigger_poll()` забирає його операцією `cmpxchg(&t->event, 1, 0)`. Тому пропущений `read()` не заганяє демона в нескінченний цикл — наступний `epoll_wait()` просто засне далі. Пастка тут інша й тихіша: не прочитавши файл, демон приймає рішення про вбивство cgroup, не побачивши жодного числа, — він знає лише «поріг перевищено», але не знає, наскільки й за яким ресурсом. Читати `fd` після події потрібно не заради ядра, а заради власного рішення.

### 4. Права доступу та сумісність із cgroups v2
До ядра 6.5 створення глобального тригера у `/proc/pressure/memory` вимагало прав `root` або привілею `CAP_SYS_RESOURCE`, і без них уже `open()` на запис повертав `EPERM`. Від 6.5 перевірку перенесли в `psi_trigger_create()`: безпривілейований процес теж може створити монітор, але лише з вікном, кратним 2 секундам, — інакше дістане `EINVAL`. Наш приклад просить вікно 1 секунда, тобто короткі вікна лишаються привілейованими. Демон у безпривілейованому контейнері має або погодитися на вікно `2000000`, або створювати тригер у делегованому файлі контрольної групи `<cgroup_path>/memory.pressure`, де права доступу належать користувачеві контейнера.

### 5. Обробка переривань системних викликів (EINTR)
Кожен сигнал, для якого демон поставив власний обробник, перериває `epoll_wait()` — у нашому прикладі це `SIGTERM` і `SIGINT`, у реальному сервісі додається ще `SIGHUP` для перечитування конфігурації. Виклик повертає `-1` з `errno == EINTR`, і це не помилка: цикл має перевірити прапор завершення й заснути далі. Демон, який трактує будь-яке від'ємне значення `epoll_wait()` як фатальну помилку, помре від першої ж спроби перечитати конфіг.

### 6. Відсутність ядерної підтримки (Linux < 4.20)
У разі запуску на застарілих ядрах Linux (версії 4.19 і нижче) або при збірці ядра з вимкненим параметром `CONFIG_PSI=n`, відкриття файлу `/proc/pressure/memory` завершиться помилкою `ENOENT` (No such file or directory). Системні демони повинні передбачати безпечний фолбек (graceful degradation), логуючи попередження та переходячи на резервні метрики (наприклад, на лічильник `oom_kill` у файлі `memory.events` відповідної cgroup).

## Навантажувальне тестування та верифікація демона

Для верифікації правильності роботи розробленого демона моніторингу виконується синтетична генерація тиску пам'яті за допомогою інструменту `stress-ng`:

```bash
stress-ng --vm 4 --vm-bytes 85% --vm-method all --verify -t 30s
```

Ця команда створює 4 потоки, які інтенсивно виділяють та модифікують 85% оперативної пам'яті системи. При досягненні позначки direct reclaim ядро згенерує подію PSI, і демон отримає `EPOLLPRI` у межах одного кроку перевірки вікна — для тригера з вікном 1 секунда це до 100 мс.

## Порівняльний аналіз накладних витрат та продуктивності

Демони моніторингу на основі тригерів PSI демонструють кардинально вищу ефективність порівняно з традиційними демонами опитування (такими як `earlyoom` або `nohang` перших версій):

- **Використання CPU:** у стані очікування — практично нуль незалежно від тривалості спостереження, бо потік повністю заблокований у ядрі на `epoll_wait()` і не виконує жодної інструкції, доки ядро його не розбудить. Демон опитування натомість платить фіксовану ціну за кожен цикл: розбудитися, відкрити чи перемотати файл, розібрати рядок — і так хоч раз на секунду, хоч сто разів на секунду, увесь час роботи системи. Різниця тут не у відсотках, а в самій природі витрат.
- **Використання пам'яті (RSS):** порядок — одиниці мегабайтів; точне число сильно залежить від libc й способу збірки (статичний бінарник проти динамічного, glibc проти musl), тож наводити його без опису стенда безглуздо. Важливіше інше: цей RSS має бути зафіксований у пам'яті через `mlockall()`, інакше демон, покликаний рятувати систему від пробуксовування, сам чекатиме на свої сторінки з диска саме в ту хвилину, коли він потрібен.
- **Час реакції на кризу:** згори цю затримку обмежує не демон, а крок перевірки вікна тригера — десята частина `window_us`, тобто від 50 мс для мінімального 500-мілісекундного вікна до 1 с для максимального десятисекундного. Усе, що демон додає понад це, — час на пробудження та планування, і саме заради нього ставлять `SCHED_FIFO`.
