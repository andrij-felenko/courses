# 📋 Специфікація інтерфейсу PSI: файли /proc/pressure та контроль cgroups v2

Підсистема Pressure Stall Information (PSI) надає дворівневий програмний інтерфейс для моніторингу голодування ресурсів у просторі користувача: загальносистемний рівень через віртуальну файлову систему `procfs` (`/proc/pressure/`) та ізольований рівень контрольних груп через `cgroups v2` (`/sys/fs/cgroup/.../*.pressure`). Цей довідник описує точну структуру експортованих полів, алгоритми їх обчислення, правила налаштування подієвих тригерів, семантику системних викликів, обробку помилок та моніторинг дельт.

## Структура файлів /proc/pressure/

Для трьох основних видів апаратних ресурсів ядро створює окремі віртуальні вузли у файловій системі procfs:
- `/proc/pressure/cpu` — голодування за процесорним часом.
- `/proc/pressure/memory` — голодування за оперативною пам'яттю.
- `/proc/pressure/io` — голодування за вводом/виводом блокових пристроїв та файлових систем.

Кожен із трьох файлів містить два рядки статистичних даних — для рівнів `some` та `full`. Для `memory` та `io` змістовні обидва. У файлі `cpu` рядок `full` теж друкується (з ядра 5.13, заради сумісності зі споживачами формату), але на рівні всієї системи він завжди заповнений нулями: повного голодування процесора у працюючій системі концептуально не існує. Змістовним `cpu full` буває лише у файлі `cpu.pressure` окремої cgroup.

```text
$ cat /proc/pressure/memory
some avg10=1.25 avg60=0.84 avg300=0.12 total=45210984
full avg10=0.00 avg60=0.00 avg300=0.00 total=1204890
```

### Синтаксис і детальний розбір полів

Кожен рядок даних у файлі PSI розбивається на дві частини: трійку експоненційно згладжених середніх та один кумулятивний лічильник часу.

1. **`avg10`**: Експоненційно згладжене середнє значення відсотка часу голодування за останні **10 секунд**. Метрика швидко реагує на короткочасні сплески ресурсного тиску і слугує основним індикатором для оперативного сповіщення інженерних служб.
2. **`avg60`**: Експоненційно згладжене середнє значення відсотка часу за останні **60 секунд** (1 хвилина). Відображає середньострокові тренди навантаження та дозволяє оцінити стійкість ресурсного дефіциту під час виконання періодичних завдань.
3. **`avg300`**: Експоненційно згладжене середнє значення відсотка часу за останні **300 секунд** (5 хвилин). Показує довгостроковий стан ресурсного дефіциту і використовується для планування ємності серверного обладнання та оцінки якості обслуговування (SLA).
4. **`total`**: Абсолютний кумулятивний лічильник часу в **мікросекундах (us)**, проведеного системою у відповідному стані голодування з моменту завантаження ядра (або створення відповідної cgroup).

### Математичний розрахунок EWMA та вимірювання дельт

Значення `avg10`, `avg60` та `avg300` обчислюються в ядрі за допомогою формули експоненційно зваженого ковзного середнього (EWMA):

```text
avg_new = avg_old · e^(-dt / T) + stall_pct · (1 - e^(-dt / T))
```

Де:
- `dt = 2` секунди (період відкладеної роботи `psi_avgs_work()`, константа `PSI_FREQ`).
- `T` — часове вікно згладжування (10, 60 або 300 секунд).
- `stall_pct` — фактична частка часу голодування у поточному 2-секундному інтервалі.

Оскільки ковзні середні загладжують короткі сплески, системи високоточного моніторингу (Prometheus node_exporter, Datadog agent, Telegraf) спираються на кумулятивний лічильник `total`. Поле `total` є монотонно зростаючим. Для розрахунку точного відсотка голодування між двома моментовими замірами `t1` та `t2` використовується наступна формула:

```text
Stall_Percentage = (total(t2) - total(t1)) / ((t2 - t1) в мікросекундах) · 100%
```

#### Покроковий приклад обчислення дельти:

Припустимо, програма моніторингу прочитала поле `total` з `/proc/pressure/memory` у момент часу `t1`, а потім повторно у момент `t2` через 5 секунд:
- `t1 = 10.0` с, `total(t1) = 1 000 000` us.
- `t2 = 15.0` с, `total(t2) = 1 500 000` us.
- Інтервал часу: `t2 - t1 = 5.0` с = `5 000 000` us.
- Дельта затримки: `total(t2) - total(t1) = 500 000` us.
- Розраховане голодування: `500 000 us / 5 000 000 us = 0.10` (або **10.0%** часу).

Це означає, що протягом 5-секундного інтервалу вимірювання процеси чекали на виділення пам'яті рівно 10% астрономічного часу.

## Деталізація файлів /proc/pressure/io та /proc/pressure/cpu

Файл `/proc/pressure/io` відображає затримки, пов'язані з очікуванням блокового вводу/виводу. Метрика `io some` враховує будь-які процеси, заблоковані на зчитуванні або записі диска, тоді як `io full` реєструє моменти, коли всі активні процеси застрягли в очікуванні дискових операцій.

Файл `/proc/pressure/cpu` розраховує час, протягом якого процеси перебували у стані готовності до виконання (`TASK_RUNNING`), але не могли отримати процесорний квант через заповненість черги `runqueue`. Нульовий рядок `full` у цьому файлі зумовлений тим, що при наявності виконання на CPU принаймні один потік завжди виконує інструкції, унеможливлюючи стан повного паралічу CPU на рівні вузла.

## Інтеграція з Control Groups (cgroups v2)

У cgroups v2 кожен вузол ієрархії містить власні файли моніторингу PSI, які дозволяють отримувати ізольовану картину навантаження для окремих контейнерів або системних служб:
- `<cgroup_path>/cpu.pressure`
- `<cgroup_path>/memory.pressure`
- `<cgroup_path>/io.pressure`

На відміну від глобальних файлів у `/proc/pressure/`, файли в cgroup відображають голодування лише тих процесів, які належать до цієї конкретної контрольної групи та її підпорядкованих нащадків.

| Файл cgroups v2 | Контролер cgroup | Наявність `some` | Наявність `full` | Опис контрольованого голодування |
| :--- | :--- | :--- | :--- | :--- |
| `cpu.pressure` | `cpu` | Так | Так (з ядра 5.13) | `some` — процеси групи чекають на вільний квант CPU через конкуренцію з іншими cgroups; `full` — жодна не-idle задача групи не рахує (витіснили чужі процеси або зупинив ліміт `cpu.max`). |
| `memory.pressure` | `memory` | Так | Так | Затримки через direct reclaim, page faults, swapping або очікування memory limit групи. |
| `io.pressure` | `io` | Так | Так | Процеси групи чекають на виконання блокового вводу/виводу. |

Дворівнева модель дозволяє розділити відповідальність: глобальний `/proc/pressure/` моніторить здоров'я всього вузла (bare-metal чи VM), а `cgroup.pressure` надає метрики для контейнерів (Docker, Podman, LXC, Kubernetes pods).

### Налаштування контролю cgroups v2 та делегування

Файли `*.pressure` не належать жодному контролеру: ядро створює їх у кожному вузлі уніфікованої ієрархії разом із рештою базових файлів, тож увімкнення `+memory +io +cpu` у `cgroup.subtree_control` для читання тиску не потрібне. Керує обліком інший вимикач — файл `cgroup.pressure` (з ядра 6.1): запис `0` вимикає облік PSI саме для цієї групи, `1` вмикає назад. Він навмисно не ієрархічний, бо існує заради економії: PSI рахує затримки для кожної групи окремо й підсумовує їх на кожному рівні дерева, тому в глибоких ієрархіях облік у проміжних вузлах коштує помітно, а користі не дає. Делегування ж у rootless-режимі зводиться до прав на самі файли: власник делегованої піддиректорії може і читати `*.pressure`, і заводити в них тригери без прав root.

Системний менеджер `systemd` дозволяє керувати реакцією на тиск PSI безпосередньо у unit-файлах служб:

```ini
[Service]
MemoryAccounting=true
ManagedOOMMemoryPressure=kill
ManagedOOMMemoryPressureLimit=80%
```

Ці параметри інструктують `systemd-oomd` моніторити `memory.pressure` цього сервісу та завершувати його cgroup, коли тиск `full` (поле `avg10`) тримається вище 80% достатньо довго. Саме «достатньо довго» задає не unit, а загальний конфіг демона: `DefaultMemoryPressureDurationSec=` у `oomd.conf(5)`, типово 30 секунд (там же живе й типовий поріг `DefaultMemoryPressureLimit=60%`, який рядок `ManagedOOMMemoryPressureLimit=` перекриває для цієї групи). Окремо на unit тривалість можна перекрити директивою `ManagedOOMMemoryPressureDurationSec=`, але вона з'явилася лише в systemd 257 і типово порожня — тобто на старіших системах єдиний важіль тривалості загальний, на всі групи одразу.

## Прапор завантаження ядра та параметри конфігурації

Підтримка підсистеми PSI в ядрі Linux регулюється наступними параметрами збірки та параметрами командного рядка завантажника:
- `CONFIG_PSI=y`: Вмикає підсистему PSI під час компіляції ядра.
- `CONFIG_PSI_DEFAULT_DISABLED=y`: Вимикає підсистему за замовчуванням для зменшення накладних витрат на старіших системах.
- `psi=1` або `psi=0`: Параметр завантаження ядра у `grub` або `cmdline`, який примусово вмикає або вимикає розрахунок PSI при старті системи.

Якщо підсистему вимкнено через `psi=0`, каталог `/proc/pressure/` узагалі не створюється, і відкриття його файлів дає `ENOENT`; читання `*.pressure` у cgroup у цьому режимі повертає `EOPNOTSUPP`.

## Ізоляція у просторах імен та файлові системи procfs / sysfs

У контексті контейнеризації важливим аспектом є поведінка віртуальних файлів при монтуванні cgroup namespace. Коли контейнер запускається у власному cgroup namespace, шлях `/sys/fs/cgroup/` монтується так, що корінь контейнера бачить власний файл `memory.pressure` як кореневий для цього середовища.

Однак глобальний файл `/proc/pressure/memory` відображає стан усього хост-вузла. Тому для надання контейнерам ізольованої картини системні агенти монтують поверх `/proc/pressure/` файли з відповідної cgroup цього контейнера.

Така підміна тримає принцип найменших привілеїв у багатокористувацьких кластерах: контейнер не повинен бачити затримки сусідніх процесів на хост-вузлі. Вона закриває саме цей канал витоку — знання про завантаженість сусідів, — а не робить середовище захищеним загалом.

## Подієвий інтерфейс тригерів (Triggers & Epoll)

Постійне опитування (polling) файлів PSI через відкриття та читання рядків створює непотрібні накладні витрати CPU. Для реального часу PSI підтримує підписку на події перевищення порогу через системні виклики `poll()`, `epoll()` або `select()`.

### Синтаксис реєстрації тригера

Щоб налаштувати сповіщення, процес відкриває відповідний файл PSI у режимі читання-запису (`O_RDWR` або `O_WRONLY`) і записує в нього конфігураційний рядок наступного формату:

```text
<some|full> <threshold_us> <window_us>
```

- **`some` / `full`**: тип стану голодування, який відстежується.
- **`threshold_us`**: поріг сумарного часу затримки в мікросекундах.
- **`window_us`**: довжина рухомого часового вікна в мікросекундах (від 500 000 us [0.5с] до 10 000 000 us [10с]).

#### Приклади тригерів:

1. `some 150000 1000000` — розбудити процес, якщо протягом 1-секундного вікна (`1 000 000 us`) хоча б одна задача чекала на ресурс сумарно **150 мс** (`150 000 us`, або 15% часу).
2. `full 50000 1000000` — розбудити процес, якщо протягом 1-секундного вікна ВСІ задачі були заблоковані сумарно протягом **50 мс** (`50 000 us`, або 5% часу).

### Алгоритм роботи ядерного вікна тригера

Коли тригер зареєстровано на відкритому файловому дескрипторі:
1. Ядро створює внутрішню структуру `psi_trigger` і прив'язує її до цього `struct file`.
2. Ядро стежить за приростом сигналу десять разів за вікно (`UPDATES_PER_WINDOW = 10`), тобто крок перевірки — десята частина `window_us`: для 1-секундного вікна це 100 мс, для мінімального 500-мілісекундного — 50 мс. Саме цей крок і задає найменшу можливу затримку сповіщення.
3. Коли сумарна дельта затримок у межах вікна `window_us` перевищує `threshold_us`, ядро надсилає подію `POLLPRI` (Priority Data) на відповідний файловий дескриптор.
4. Опитувальний виклик `epoll_wait()` повертає прапор `EPOLLPRI`, сповіщаючи процес про критичний тиск.

```
Структура реєстрації тригера PSI:

   Простір користувача                      Ядро Linux (PSI Engine)
+-----------------------+               +----------------------------------+
| open("/proc/pressure/ |               |                                  |
|       memory",O_RDWR) | --- fd ---->  | psi_trigger_create()             |
| write(fd, "some ...") |               | Створення tracking window        |
+-----------------------+               +----------------------------------+
            |                                            |
            v                                            v
+-----------------------+               +----------------------------------+
| epoll_wait(...,       | <--- POLLPRI -| Перевищено threshold_us          |
|            EPOLLPRI)  |               | у вікні window_us!               |
+-----------------------+               +----------------------------------+
```

### Обробка помилок та коди повернення системних викликів

При записі рядка конфігурації у файли PSI системний виклик `write()` може повертати стандартні коди помилок POSIX, які необхідно обробляти у користувацькому коді:

| Константа | Текст `strerror()` | Причина виникнення помилки | Спосіб усунення |
| :--- | :--- | :--- | :--- |
| `EINVAL` | Invalid argument | `threshold_us` перевищує `window_us`; `window_us` виходить за межі [500 мс … 10 с]; або процес без `CAP_SYS_RESOURCE` просить вікно, не кратне 2 с (ядра 6.5+). | Скоригувати значення у рядку запису — безпривілейованому процесу підійде `window_us`, кратне 2 000 000. |
| `EBUSY` | Device or resource busy | Тригер вже зареєстровано на цьому файловому дескрипторі `fd`. | Відкрити новий `fd` через `open()` для другого тригера. |
| `EPERM` | Operation not permitted | Ядра до 6.5: відкриття `/proc/pressure/*` на запис без `CAP_SYS_RESOURCE`. | Запустити з привілеями або використати `<cgroup>/memory.pressure`. |
| `ENOENT` / `EOPNOTSUPP` | No such file / Not supported | Ядро зібрано без підтримки `CONFIG_PSI=y`, або параметр завантаження `psi=0`. | Увімкнути `CONFIG_PSI=y` або додати `psi=1` у bootcmdline. |

### Внутрішні заголовочні структури ядра (`include/linux/psi_types.h`)

Для розробників ядерних модулів та розширень трасування eBPF нижче наведено фрагменти ключових структур даних ядра, які керують обліком затримок:

```c
struct psi_trigger {
	/* Стан, за яким стежить тригер: PSI_MEM_SOME, PSI_IO_FULL, … */
	enum psi_states state;
	/* Поріг у наносекундах */
	u64 threshold;
	/* Вузол у списку тригерів групи */
	struct list_head node;
	struct psi_group *group;
	/* Черга очікування для poll()/epoll() */
	wait_queue_head_t event_wait;
	/* Прапор нової події (скидається при опитуванні) */
	int event;
	/* Рухоме вікно відстеження */
	struct psi_window win;
	u64 last_event_time;
	/* Який агрегатор обслуговує тригер: PSI_AVGS чи PSI_POLL */
	enum psi_aggregators aggregator;
};

struct psi_group {
	struct psi_group *parent;
	bool enabled;
	/* Per-CPU масив накопичувачів */
	struct psi_group_cpu __percpu *pcpu;
	/* Відкладена робота оновлення EWMA (раз на 2 с) */
	struct delayed_work avgs_work;
	/* Тригери на повільному агрегаторі (безпривілейовані, вікно N·2 с) */
	struct list_head avg_triggers;
	/* Тригери на швидкому RT-опитуванні та його потік */
	struct list_head rtpoll_triggers;
	struct task_struct __rcu *rtpoll_task;
	u64 rtpoll_min_period;
	/* Накопичений час за станами та готові середні */
	u64 total[NR_PSI_AGGREGATORS][NR_PSI_STATES - 1];
	unsigned long avg[NR_PSI_STATES - 1][3];
};
```

Два списки тригерів — не випадковість: безпривілейовані тригери з вікном, кратним 2 с, обслуговує та сама відкладена робота, що рахує середні, тоді як короткі вікна вимагають окремого потоку реального часу `rtpoll_task` із періодом `rtpoll_min_period`. Ці структури забезпечують збереження стану між викликами планувальника та гарантують високу точність обчислення затримок при мінімальних накладних витратах.

### Особливості, права доступу та обмеження тригерів

- **Один файловий дескриптор — один тригер:** На одному відкритому `fd` можна зареєструвати лише один тригер. Якщо потрібно відстежувати і `some`, і `full`, програма повинна відкрити файл двічі й отримати два окремих `fd`.
- **Життєвий цикл тригера:** Тригер існує лише доти, доки відкрито відповідний файловий дескриптор `fd`. Закриття `fd` через `close()` автоматично видаляє тригер із ядерного списку відстеження та звільняє виділені ресурси пам'яті.
- **Права доступу:** самі файли `/proc/pressure/*` створено з режимом `0666`, але тригер на них довго був привілейованою операцією: до ядра 6.5 відкриття на запис вимагало `CAP_SYS_RESOURCE`. Від 6.5 перевірку перенесли в `psi_trigger_create()` і пом'якшили: безпривілейований процес теж може створити монітор, якщо розмір вікна кратний 2 с — такий тригер обслуговує звичайний агрегатор середніх і окремого потоку реального часу не потребує. У cgroups v2 запис у `<cgroup>/memory.pressure` дозволений власникові файлу в межах делегованого середовища без root-прав.
- **Читання після події:** прапор події ядро скидає саме при опитуванні — `psi_trigger_poll()` забирає його операцією `cmpxchg(&t->event, 1, 0)`, тож наступний `epoll_wait()` уже не поверне `EPOLLPRI` і зациклення не буде. А от щоб прочитати свіжі числа, `lseek(fd, 0, SEEK_SET)` перед `read()` обов'язковий: файл procfs віддає вміст через `seq_file`, і без перемотування на початок повторний `read()` дасть 0 байтів.
