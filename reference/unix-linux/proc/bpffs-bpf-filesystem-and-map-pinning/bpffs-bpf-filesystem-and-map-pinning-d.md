Коли мережевий або аналітичний демон у просторі користувача створює eBPF-мапу або завантажує програму трасування, ядро Linux повертає йому стандартний файловий дескриптор. У рамках POSIX-моделі ресурсів цей дескриптор існує лише у таблиці `files_struct` даного процесу. При аварійному завершенні процесу, перезапуску служб під час оновлення програмного забезпечення або виклику `exit()` ядро автоматично закриває файловий дескриптор, знижуючи внутрішній лічильник посилань об'єкта `refcnt` до нуля. Це призводить до миттєвого знищення накопиченого стану в пам'яті (таблиць маршрутизації, лічильників метрик, сесій) та вивантаження обробників трафіка з точок монтування ядра.

Потреба забезпечити життєвий цикл об'єктів eBPF незалежно від процесів у просторі користувача призвела до створення псевдофайлової системи `bpffs` (англ. *BPF file system*). Вона надає механізм фіксації (англ. *pinning*), який перетворює анонімні об'єкти ядра у стійкі записи віртуальної файлової системи VFS.

## Негарантована тривалість файлових дескрипторів та модель ресурсів BPF

У системному виклику `bpf()` кожен створений ресурс (програма `struct bpf_prog`, таблиця `struct bpf_map` або зв'язок `struct bpf_link`) розглядається як анонімний об'єкт ядра. Доступ до цього об'єкта з простору користувача здійснюється виключно через файловий дескриптор, який вказує на анонімний інод VFS (створений за допомогою `anon_inode_getfd()`).

Усі об'єкти eBPF підтримують атомарний лічильник посилань `refcnt` (тип `atomic64_t`). Збільшення та зменшення цього лічильника контролює повернення пам'яті ядра:

1. **При створенні:** Функція `bpf_map_alloc()` або `bpf_prog_load()` виділяє пам'ять у heap ядра та ініціалізує `refcnt = 1`. Ядро виділяє елемент у таблиці `files_struct` процесу і повертає `fd`.
2. **При дублюванні:** Виклики `dup()`, `fork()` або передача `fd` через Unix-сокет збільшують `refcnt` на 1 для кожного нового дескриптора.
3. **При прикріпленні до хуків:** Завантаження XDP-програми на мережевий інтерфейс або прив'язка kprobe додає внутрішнє посилання ядра від драйвера мережевої карти або підсистеми трасування, що знову збільшує `refcnt`.

Однак, якщо процес у просторі користувача створив мапу для збереження стану (наприклад, мапу типу `BPF_MAP_TYPE_HASH` для відстеження IP-з'єднань), ця мапа не прив'язана до системних хуків. Якщо демон закриває свій `fd` або помирає через помилку `OOM-killer`, таблиця `files_struct` очищається. Внутрішній лічильник `refcnt` досягає значення `0`, і підсистема BPF негайно викликає деструктор `bpf_map_free_deferred()`, знищуючи всі накопичені записи.

Фундаментальне обмеження POSIX-дескрипторів полягає у тому, що файловий дескриптор є локальною сутністю конкретного процесу. Він не має ідентифікатора у глобальному простір імен файлової системи. Якщо два автономні демони бажають працювати з однією мапою, вони не можуть просто передати ціле число `fd = 3` через конфігураційний файл, оскільки у контексті другого процесу дескриптор `3` може вказувати на зовсім інший сокет або файл.

Детальний перебіг розробки та альтернативні шляхи вирішення цієї проблеми описано у вставці [Еволюція фіксації об'єктів BPF](book:unix-linux/bpffs-bpf-filesystem-and-map-pinning/hist-bpffs-evolution.md).

## Архітектура та внутрішня організація bpffs

Файлова система `bpffs` є спеціалізованою віртуальною файловою системою VFS (тип `bpf`), реалізованою у модулі ядра `kernel/bpf/inode.c`. Вона не вимагає блокового пристрою зберігання і монтується за стандартним шляхом `/sys/fs/bpf`:

```bash
mount -t bpf none /sys/fs/bpf
```

Головне призначення `bpffs` — надати простір імен VFS, де кожен фіксований файл (англ. *pinned file*) є віртуальним покажчиком на відповідну структуру ядра `bpf_map`, `bpf_prog` або `bpf_link`.

![Життєвий цикл об'єкта eBPF та лічильник посилань refcnt під час пінінгу](/reference/unix-linux/proc/bpffs-bpf-filesystem-and-map-pinning/img/bpffs-lifecycle.svg)
*Життєвий цикл об'єкта eBPF та зміна лічильника посилань refcnt при пінінгу та розфіксації*

### Ініціалізація суперблоку та драйвера bpf_fs_type

При виконанні команди монтування шар VFS викликає функцію драйвера `bpf_mount()`. Ядро створює екземпляр `struct super_block` у пам'яті з магічним числом `BPF_FS_MAGIC` (`0xcafe4a11`).

Драйвер `bpffs` реєструє власну структуру типу файлової системи:

```c
static struct file_system_type bpf_fs_type = {
    .owner   = THIS_MODULE,
    .name    = "bpf",
    .mount   = bpf_mount,
    .kill_sb = kill_litter_super,
};
```

Функція `bpf_fill_super()` налаштовує кореневий інод файлової системи (`root inode`), призначаючи йому режим доступу `S_IFDIR | mode` (за замовчуванням `0700`) та прив'язуючи оператори каталогу `bpf_dir_iops` та `bpf_dir_fops`.

### Внутрішня структура інода у bpffs

При фіксації об'єкта ядро створює об'єкт `struct inode` у пам'яті `bpffs`. Оскільки `bpffs` не є дисковою файловою системою, уся метаінформація зберігається у оперативній пам'яті:

```c
struct inode {
    umode_t         i_mode;       /* Права доступу (S_IFREG | mode) */
    kuid_t          i_uid;        /* UID власника */
    kgid_t          i_gid;        /* GID групи */
    const struct inode_operations *i_op;  /* Операції над інодом bpf_file_iops */
    const struct file_operations  *i_fop; /* Операції над файлом bpf_bpffs_fops */
    void           *i_private;    /* Покажчик на об'єкт bpf_map, bpf_prog або bpf_link */
};
```

Ключовим є поле `i_private`. У ньому ядро зберігає сирий покажчик на структуру об'єкта eBPF. Тип об'єкта визначається через внутрішній заголовок або перелічення `enum bpf_type`:
- `BPF_TYPE_MAP` — вказує на структуру `struct bpf_map`.
- `BPF_TYPE_PROG` — вказує на структуру `struct bpf_prog`.
- `BPF_TYPE_LINK` — вказує на структуру `struct bpf_link`.

Для каталогів у `bpffs` поле `i_op` вказує на масив `bpf_dir_iops`, який дозволяє створювати піддерева за допомогою виклику `mkdir()`, але забороняє створення звичайних файлів через `open(..., O_CREAT)`. Створення файл-об'єктів у `bpffs` дозволено виключно через інтерфейс системного виклику `bpf()`.

## Механізм пінінгу: виконання BPF_OBJ_PIN та BPF_OBJ_GET

Взаємодія простору користувача з `bpffs` здійснюється через дві спеціалізовані команди системного виклику `bpf()`: `BPF_OBJ_PIN` та `BPF_OBJ_GET`.

*Архітектура ядра: взаємодія шару VFS, драйвера bpffs та об'єктів підсистеми BPF*

### Алгоритм фіксації BPF_OBJ_PIN

Коли застосунок викликає `bpf(BPF_OBJ_PIN, &attr, sizeof(attr))`, ядро виконує такі кроки у функції `bpf_obj_pin()`:

1. **Валідація шляху:** Ядро перевіряє переданий у `attr.pathname` рядок шляху та резолвить його через VFS-функцію `user_path_create()`.
2. **Перевірка файлової системи:** Ядро переконується, що цільова директорія належить суперблоку `bpffs` (`sb->s_type == &bpf_fs_type`). Спроба зафіксувати об'єкт на ext4 або tmpfs повертає помилку `EINVAL`.
3. **Отримання об'єкта за FD:** За переданим `attr.bpf_fd` ядро знаходить відповідну структуру `bpf_map` або `bpf_prog` у таблиці відкритих файлів поточного процесу.
4. **Створення інода (bpf_mkobj):** Ядро виділяє новий `struct inode` у пам'яті `bpffs`, записує покажчик на об'єкт у `inode->i_private` та ініціалізує атрибути файлу (права доступу `0600` або модифіковані відповідно до `umask`).
5. **Збільшення refcnt:** Ядро викликає `bpf_map_inc()` або `bpf_prog_inc()`, атомарно збільшуючи `refcnt` об'єкта на 1.
6. **Прив'язка dentry:** Новий інод зв'язується з об'єктом `struct dentry` у VFS-кеші і стає видимим при виклику `ls` або `stat`.

Після успішного завершення `BPF_OBJ_PIN` процес користувача може безпечно закрити свій `bpf_fd`. Оскільки інод у `bpffs` утримує власне посилання у `refcnt`, об'єкт залишається повністю функціональним у пам'яті ядра.

### Алгоритм відновлення доступу BPF_OBJ_GET

Для отримання файлового дескриптора зафіксованого об'єкта процес користувача викликає `bpf(BPF_OBJ_GET, &attr, sizeof(attr))`. Обробка у ядрі (`bpf_obj_get_user()`) відбувається за такою послідовністю:

1. **Резолюція шляху VFS:** Функція `user_path_at()` знаходить об'єкт `struct path` у дереві файлів `bpffs`.
2. **Перевірка прав доступу VFS:** Ядро виконує `inode_permission()`, перевіряючи, чи має поточний процес (за його `euid`/`egid` та сабітом `capabilities`) права на читання чи запис даного файлу.
3. **Витяг покажчика з i_private:** З інода `path.dentry->d_inode` зчитується покажчик `i_private`.
4. **Перевірка сумісності режимів:** Якщо передано прапори `BPF_F_RDONLY` або `BPF_F_WRONLY`, ядро перевіряє, чи дозволяє тип мапи відкриття у цьому режимі.
5. **Збільшення refcnt:** Ядро викликає `bpf_map_inc()` або `bpf_prog_inc()`, збільшуючи лічильник посилань для нового дескриптора.
6. **Виділення анонімного FD:** За допомогою `anon_inode_getfd()` ядро створює новий файловий дескриптор у таблиці `files_struct` викликаючого процесу і повертає його значення.

Детальні структури даних, атрибути системного виклику та функції бібліотеки `libbpf` наведено у вставці [Системний виклик bpf() та параметри bpffs](book:unix-linux/bpffs-bpf-filesystem-and-map-pinning/api-bpffs-syscall-and-ops.md).

## Обернені мапи (Map-in-Map) та ієрархічний пінінг

У складних мережевих підсистемах (наприклад, реалізації NAT або розмежування ресурсів для мультитенантних контейнерів) використовується механізм вкладених мап (англ. *map-in-map*). Типи мап `BPF_MAP_TYPE_ARRAY_OF_MAPS` та `BPF_MAP_TYPE_HASH_OF_MAPS` містять як елементи значення покажчиків на інші мапи.

При роботі з вкладеними мапами механізм пінінгу має такі особливості:

- **Фіксація зовнішньої мапи:** При фіксації зовнішньої мапи за шляхом `/sys/fs/bpf/outer_map` ядро збільшує `refcnt` лише зовнішньої мапи. Внутрішні мапи, розміщені у її комірках, утримуються через внутрішні покажчики ядра `outer_map->element[i]`.
- **Автономна фіксація внутрішніх мап:** Якщо розробник бажає надати прямої доступ до конкретної внутрішньої мапи для окремого процес-споживача, внутрішня мапа повинна бути зафіксована за власним шляхом (наприклад, `/sys/fs/bpf/inner_maps/tenant_42`). Це збільшує `refcnt` внутрішньої мапи на 1 і дозволяє викликати `BPF_OBJ_GET` безпосередньо для неї.

## Особливості фіксації об'єктів bpf_link та bpf_iter

З появою об'єкта `struct bpf_link` (який представляє зв'язок між завантаженою eBPF-програмою та точки її прикріплення у ядрі) механізм фіксації в `bpffs` став основним інструментом гарантування безперервності роботи хуків.

Коли програма трасування або XDP-фільтр прив'язуються через `bpf_link`, фіксація файлу за шляхом `/sys/fs/bpf/links/xdp_eth0` призводить до таких наслідків:

1. Інод `bpffs` утримує посилання на `struct bpf_link`.
2. Об'єкт `bpf_link` у свою чергу утримує позитивне посилання у `refcnt` прив'язаної програми `struct bpf_prog`.
3. Навіть якщо процес закриває дескриптор зв'язку, хук ядра залишається активним, а програма виконується при кожному вхідному пакеті мережевої карти.

Видалення зафіксованого файлу `xdp_eth0` через `unlink()` викликає функцію `bpf_link_put()`. Якщо інших посилань немає, зв'язок автоматично від'єднується від хука (детач) та знищується.

Крім того, підсистема `bpf_iter` дозволяє створювати зафіксовані ітератори ядра. Коли BPF-програма типу `iter` фіксується у `bpffs` (наприклад, `/sys/fs/bpf/bpf_iter_netstat`), звичайне читання файла через VFS (`cat` або `open()`) запускає виконання eBPF-коду для динамічної генерації тексту прямо в буфер читача.

## Розмежування прав доступу, безпека та підсистема LSM

Оскільки зафіксовані у `bpffs` об'єкти проникають у простір імен VFS, до них застосовуються класичні механізми контролю доступу Linux Discretionary Access Control (DAC) та Mandatory Access Control (MAC).

### Права доступу Unix (DAC) та атрибути монтування

Кожен інод у `bpffs` підпорядковується стандартним правилам прав доступу POSIX (`rwx`). За замовчуванням при створенні файлу функцією `BPF_OBJ_PIN` йому призначаються права `0600` (читання та запис лише для власника, яким зазвичай є `root`).

Утиліти адміністрування можуть змінювати власника та маску прав фіксованих об'єктів за допомогою стандартних системних викликів `chmod()` та `chown()` або CLI-команд:

```bash
# Надання прав читання мапи групі monitoring
chown root:monitoring /sys/fs/bpf/network_stats
chmod 0640 /sys/fs/bpf/network_stats
```

При виконанні `BPF_OBJ_GET` ядро перевіряє права доступу VFS:
- Якщо процес запитує дескриптор мапи без прапора `BPF_F_RDONLY`, йому потрібні права на запис (`w`) до інода у `bpffs`.
- Якщо процес відкриває мапу з прапором `BPF_F_RDONLY`, достатньо прав на читання (`r`).

Служба `systemd` забезпечує автоматичне монтування точки `/sys/fs/bpf` при завантаженні ОС через юніт `sys-fs-bpf.mount`. Конфігурація за замовчуванням обмежує доступ лише для привілейованих користувачів (`mode=0700`, `uid=0`, `gid=0`).

### Ізоляція у контейнерних середовищах та Mount Namespaces

У сучасних хмарних інфраструктурах (Kubernetes, Docker) ізоляція процесів базується на просторах імен (namespaces). Оскільки `bpffs` є файловою системою, вона підпорядковується правилам Mount Namespace:

- Кожен контейнер може мати власну приватну точку монтування `/sys/fs/bpf`, ізольовану від хоста.
- У разі використання спільного монтування (shared mount flag `MS_SHARED`), файли у `/sys/fs/bpf/cilium/` стають видимими як для хоста, так і для мережевих агентів усередині контейнерів.

Це дозволяє будувати багаторівневі політики безпеки, де мережевий плагін CNI (Cilium або Calico) керує центральними мапами маршрутизації хоста, надаючи окремим подам доступ лише до прочитання конкретних статистичних файлів.

### Системні привілеї Capabilities та BPF LSM

До версії ядра Linux 5.8 створення та маніпулювання об'єктами eBPF вимагало глобальних привілеїв суперкористувача `CAP_SYS_ADMIN`. З виходом Linux 5.8 ядро запровадило спеціалізовану сабкапабіліті `CAP_BPF`, а також `CAP_NET_ADMIN` (для мережевих програм) та `CAP_PERFMON` (для трасування).

При виклику `BPF_OBJ_GET` перевіряються дві незалежні умови:
1. **Шар VFS:** Перевірка `inode_permission()` за UID/GID та прапорами доступу інода `bpffs`.
2. **Шар підсистеми BPF:** Перевірка наявності `CAP_BPF` у процесу та значення системного прапора `sysctl kernel.unprivileged_bpf_disabled`. Якщо unprivileged BPF вимкнено у ядрі (`value = 1` або `2`), виклик `BPF_OBJ_GET` повернуто помилку `EPERM` навіть при наявності повних VFS-прав `0666` на файл у `bpffs`.

У підсистемі Linux Security Modules (LSM) файли у `bpffs` отримують відповідний контекст безпеки SELinux/AppArmor (наприклад, `system_u:object_r:bpffs_t:s0`). Це дозволяє настроювати мандатні політики, що обмежують конкретним контейнерам або сервісам доступ лише до їхніх власних піддерев у `/sys/fs/bpf/docker/` або `/sys/fs/bpf/cilium/`.

## Спільний доступ та гаряче оновлення (Live Upgrades) без втрати стану

Можливість фіксації об'єктів у `bpffs` відкриває два ключові патерни побудови високонавантажених системних сервісів: міжпроцесний обмін даними та безперервне оновлення програмного забезпечення без зупинки обробки трафіка.

### Патерн спільних мап (Shared Maps)

У мікросервісній архітектурі або при розділенні привілеїв демон-генератор (наприклад, мережевий агент Cilium) створює BPF-мапу, заповнює її правилами фільтрації та фіксує у `/sys/fs/bpf/pipeline/ingress_map`.

Інші автономні процеси у системі (наприклад, CLI-утиліта моніторингу або експортер Prometheus метрик) не потребують родинних зв'язків `fork()` чи IPC-сокетів. Вони виконують `bpf_obj_get("/sys/fs/bpf/pipeline/ingress_map")`, отримують власний дескриптор мапи і читають значення лічильників паралельно з роботою основного демона.

Практичну реалізацію створення та спільного використання мапи між двома мовами програмування (C та C++) наведено у вставці [Спільне використання eBPF-мапи через bpffs між незалежними процесами](book:unix-linux/bpffs-bpf-filesystem-and-map-pinning/proj-pinned-map-sharing.md).

### Атомарне гаряче оновлення eBPF-програм через bpf_link

До появи об'єктів `bpf_link` при оновленні мережевого обробника виникав стан гонки: потрібно було відв'язати стару програму від мережевої карти, завантажити нову та прив'язати її знову. Протягом кількох мілісекунд між цими операціями пакети могли проходити повз фільтр або губитися.

Сучасний підхід базується на фіксації об'єктів `bpf_link` у `bpffs`:

1. Демон завантажує нову версію програми eBPF.
2. Демон створює об'єкт `bpf_link`, що з'єднує нову програму з мережевим інтерфейсом або kprobe.
3. За допомогою виклику `bpf_link_update()` демон атомарно перемикає виконання на нову програму всередині ядра за одну інструкцію.
4. Демон фіксує новий `bpf_link` у `/sys/fs/bpf/links/my_link`, замінюючи старий файл у `bpffs`.

Завдяки цьому оновлення відбувається безперервно для мережевого стеку, а накопичені у зафіксованих мапах дані зберігаються у повному обсязі.

## Крайові випадки, розфіксація (unpinning) та очищення пам'яті

Неминучим наслідком використання `bpffs` є проблема "витоку" зафіксованих об'єктів у пам'яті ядра. Оскільки інод `bpffs` утримує позитивний `refcnt`, мапа або програма буде висіти в оперативній пам'яті нескінченно — навіть якщо всі процеси користувача завершилися, а самі дані більше нікому не потрібні.

### Механізм розфіксації (Unpinning)

Видалення фіксованого об'єкта з `bpffs` здійснюється за допомогою стандартного системного виклику `unlink()` або POSIX-функції `remove()` (команда `rm` у командному рядку):

```bash
rm /sys/fs/bpf/my_map
```

Під час виконання `unlink()` ядро виконує такі дії:

1. **Видалення з VFS:** Запис `dentry` вилучається з каталогу `bpffs`.
2. **Виклик bpf_evict_inode:** Драйвер `bpffs` викликає функцію очищення інода `bpf_evict_inode()`.
3. **Зменшення refcnt:** Функція зчитує покажчик `i_private` і викликає `bpf_map_put()` або `bpf_prog_put()`, декрементуючи атомарний лічильник `refcnt` на 1.

Якщо на даний момент жоден процес не має відкритого `fd` для цієї мапи і вона не прив'язана до системних хуків ядра, її `refcnt` стає рівним `0`.

### Звільнення пам'яті через RCU (Read-Copy Update)

Зменшення `refcnt` до нуля не означає негайного виклику `kfree()` у контексті системного виклику `unlink()`. Оскільки eBPF-програми або мапи можуть паралельно зчитуватися ядрами ЦП у контексті переривань (NAPI або ksoftirqd), пряме виділення пам'яті створило б катастрофічні умови гонки (use-after-free).

Ядро Linux застосовує механізм RCU (англ. *Read-Copy Update*):
- Об'єкт позначається як видалений і поміщається у чергу RCU-звільнення.
- Ядро чекає завершення так званого "спокійного періоду" (англ. *grace period*), протягом якого всі ЦП гарантовано здійснюють контекстне перемикання і завершують поточні виконання eBPF-коду.
- Одночасно запускається фоновий воркер `bpf_map_free_deferred()`, який остаточно звільняє сторінки оперативної пам'яті ядра через `vfree()` або `kfree()`.

### Типові пастки та підводні камені

На практиці під час роботи з `bpffs` виникають такі типові проблеми:

- **Залишені файли після аварій (Dangling Pins):** Якщо застосунок фіксує мапи у `/sys/fs/bpf/app_map`, а потім падає без виклику `unlink()`, при повторному запуску виклик `BPF_OBJ_PIN` поверне помилку `EEXIST` (файл вже існує). Корректний алгоритм завантаження повинен спочатку перевіряти наявність файлу через `BPF_OBJ_GET` або видаляти застарілий файл перед фіксацією.
- **Невідповідність типів мап:** Якщо новий реліз застосунку змінює розмір ключа або значення мапи (наприклад, з `uint32_t` на `uint64_t`), спроба відкрити зафіксовану у `bpffs` стару мапу через `BPF_OBJ_GET` поверне файловий дескриптор старої мапи з невідповідною схемою даних, що призведе до збоїв при зчитуванні.
- **Розмонтування bpffs:** Виконанна `umount /sys/fs/bpf` видаляє всі VFS-іноди з псевдофайлової системи. Це призводить до декременту `refcnt` для всіх зафіксованих об'єктів. Якщо об'єкти не утримуються файловими дескрипторами процесів, вони будуть остаточно знищені ядрами.

Організація чіткої структури піддерев у `/sys/fs/bpf/<subsystem>/` та дотримання правил розграничення прав є обов'язковою умовою для побудови надійних та безпечних систем на базі eBPF у Linux.
