# 📜 Історія KVM: від програмної емуляції до апаратної віртуалізації

Поява KVM у 2006 році стала поворотною точкою в історії системного програмування Linux, перетворивши звичайне ядро операційної системи на високопродуктивний гіпервізор. До цього віртуалізація на архітектурі x86 розривалася між двома компромісними підходами: повільною програмною емуляцією інструкцій та складною паравіртуалізацією, яка вимагала глибокої модифікації ядер гостьових систем. Поява апаратних розширень віртуалізації від Intel та AMD створила можливість для створення нового класу гіпервізорів, але саме концепція KVM — перетворення самого Linux на гіпервізор — кардинально змінила архітектуру хмарних обчислень.

## Ера програмної емуляції та двійкової трансляції

Наприкінці 1990-х років архітектура x86 (IA-32) вважалася неефективною та непридатною для класичної віртуалізації за критеріями Попека і Гольдберга. Згідно з їхньою теоремою, архітектура піддається віртуалізації за умови, що всі чутливі інструкції (що читають або змінюють стан системного апаратного забезпечення) є привілейованими — тобто викликають апаратне перехоплення (trap) під час спроби виконання у неконфіденційному режимі (Ring 1, 2 або 3).

В архітектурі x86 існувала ціла низка чутливих, але непривілейованих інструкцій. Наприклад, інструкція `POPF` змінювала прапор переривань `IF`, але при виконанні у Ring 1 не викликала виключення, а просто мовчки ігнорувала зміну прапора. Інструкції `SGDT` та `SIDT` дозволяли користувацькому коду читати адреси глобальних таблиць дескрипторів, розкриваючи наявність гіпервізора.

Щоб обійти цю проблему, ранні системи віртуалізації використовували два різні підходи:

1. **Повна інтерпретація (Bochs):** Програмно моделювала кожен регістр, кожне декодування інструкції та кожну зміну прапорів. Це гарантувало точність, але знижувало швидкість виконання у 50–100 разів порівняно з фізичним залізом.
2. **Динамічна двійкова трансляція (VMware, QEMU):** Французький програміст Фабріс Беллар (Fabrice Bellard) у 2003 році випустив QEMU, використавши генератор коду dyngen (витягування й зшивання мікрооперацій з об'єктних файлів GCC). Лише у 2008 році з'явився TCG (Tiny Code Generator), який замінив dyngen у QEMU 0.10.0 (2009 р.). QEMU аналізував блок гостьових інструкцій безпосередньо перед виконанням, замінював чутливі інструкції безпечними викликами емулятора та кешував згенерований машинний код хоста. VMware застосовувала схожий підхід на промисловому рівні. Швидкість зросла, але накладні витрати на аналіз та трансляцію коду залишалися високими.

## Паравіртуалізація та підхід Xen

У 2003 році дослідники з Кембриджського університету на чолі з Ієном Праттом (Ian Pratt) представили проєкт Xen. Вони сформулювали іншу філософію: якщо архітектура x86 заважає віртуалізації, потрібно змінити саме ядро гостя.

Цей підхід отримав назву **паравіртуалізація** (paravirtualization). Гостьова операційна система «знала», що вона працює у віртуальному середовищі. Виклики привілейованих інструкцій, маніпуляції з таблицями сторінок та робота з таймерами замінювалися прямими викликами гіпервізора — **гіпервикликами** (hypercalls), за аналогією із системними викликами (syscalls).

Xen працював як тонкий мікроядерний гіпервізор (Domain 0) безпосередньо на залізі в Ring 0, а ядро Linux гостя (Domain U) виконувалося в Ring 1. Паравіртуалізація демонструвала вражаючу продуктивність, близьку до голого заліза, проте мала суттєвий недолік: вона вимагала глибокої модифікації вихідного коду гостьової ОС. Запустити пропрієтарні системи на кшталт Microsoft Windows у середовищі Xen без апаратної підтримки було неможливо.

## Апаратне переосмислення: Intel VT-x та AMD-V

У 2005–2006 роках виробники процесорів вирішили проблему на рівні кремнію:

- **Intel VT-x (Vanderpool, 2005):** Ввів новий режим роботи процесора, ортогональний до кільцевого захисту (Rings 0–3). Процесор отримав два класи операцій: **VMX Root Operation** (де працює гіпервізор хоста) та **VMX Non-Root Operation** (де працює гість). У режимі VMX Non-Root спроба виконання чутливих інструкцій викликає апаратний перехід — **VMExit** — назад у VMX Root mode.
- **AMD-V (Pacifica, 2006):** Реалізувала аналогічну концепцію під назвою Secure Virtual Machine (SVM) з інструкціями `VMRUN` та апаратною структурою VMCB.

Тепер процесор самостійно виконував безпечні інструкції гостя на повній швидкості заліза, а привілейовані операції автоматично перехоплювалися апаратурою.

## Радикальна ідея Аві Ківіті

У 2006 році ізраїльський розробник Аві Ківіті (Avi Kivity), працюючи в стартапі Qumranet, аналізував нові апаратні інструкції Intel VT-x. Більшість існуючих гіпервізорів на той час намагалися побудувати довкола VT-x власну складну інфраструктуру: власні планувальники потоків, власні менеджери пам'яті, власні драйвери блокових пристроїв та мережевих карт.

Ківіті поставив фундаментальне питання: **навіщо писати ще одну операційну систему всередині гіпервізора, якщо ядро Linux вже містить один із найдосконаліших у світі планувальників, зрілу систему керування пам'яттю, підтримку NUMA та тисячі готових драйверів?**

Замість побудови автономного гіпервізора, Ківіті створив невеликий модуль ядра Linux — **KVM (Kernel-based Virtual Machine)**. Задум полягав у тому, щоб перетворити сам процес Linux на віртуальну машину:

- Кожна віртуальна машина — це звичайний процес Linux (`struct task_struct`).
- Кожен віртуальний процесор (vCPU) — це звичайний потік POSIX (`pthread`), який планується стандартним планувальником ядра (CFS / EEVDF).
- Управління пам'яттю віртуальної машини — це просто виділення анонімної пам'яті через `mmap()`.
- Доступ до апаратної віртуалізації надається через символьний пристрій `/dev/kvm`.

Для емуляції периферійних пристроїв (материнської плати, мережевих карт, контролерів дисків) Ківіті використав існуючий проєкт QEMU, викинувши з нього модуль динамічної двійкової трансляції і замінивши його викликами `ioctl` до `/dev/kvm`.

## Злиття з ядром та спадщина

У жовтні 2006 року Аві Ківіті опублікував патч із KVM у списку розсилки Linux Kernel Mailing List (LKML). Завдяки лаконічності коду (початковий патч містив усього близько 10 000 рядків C) та природній інтеграції з архітектурою ядра, Лінус Торвальдс прийняв KVM до основного стовбура ядра вже у грудні 2006 року. У лютому 2007 року вийшов реліз Linux 2.6.20, який офіційно включив KVM.

У вересні 2008 року компанія Red Hat придбала Qumranet за \$107 мільйонів, зробивши KVM своєю основною технологією віртуалізації замість Xen.

Інтеграція KVM в ядро Linux змінила ландшафт обчислювальних систем:
- KVM автоматично успадковує всі вдосконалення ядра Linux: нові планувальники, покращення підсистеми cgroups, захист від атак на пам'ять та нові мережеві стеки.
- Сучасні хмарні гіганти (Google Cloud Platform, Amazon Web Services з гіпервізором Nitro/Firecracker, OpenStack) використовують KVM як фундаментальну основу для запуску мільйонів віртуальних машин щодня.
- На базі KVM виникло нове покоління лаконічних гіпервізорів для мікросервісів та бессерверних обчислень, таких як AWS Firecracker, Google crosvm та Cloud Hypervisor, які використовують той самий контракт `/dev/kvm` замість QEMU.

Створення KVM довело, що розширення існуючого ядра операційної системи новими апаратними режимами може бути значно ефективнішим, ніж побудова спеціалізованих монолітних гіпервізорів з нуля.
