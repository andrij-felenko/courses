# 📋 Інтерфейс системних викликів KVM: ioctl, структури та режими

Інтерфейс `ioctl` ядра KVM є єдиним низькорівневим контрактом між користувацьким простором (QEMU, Firecracker, crosvm) та підсистемою апаратної віртуалізації Linux. Без розуміння трирівневої ієрархії файлових дескрипторів та машинних структур даних у спільній пам'яті неможливо збагнути, як саме процес користувача контролює регістри процесора, виділяє фізичну пам'ять гостя та обробляє перехоплені події введення-виведення.

Цей довідник описує повний контракт викликів `ioctl`, структури даних спільної пам'яті та механізми обробки подій між ядром Linux і програмою управління віртуальними машинами.

## 1. Трирівнева ієрархія файлових дескрипторів

Взаємодія з KVM побудована на чіткій деревоподібній структурі дескрипторів файлів POSIX. Кожен наступний рівень створюється шляхом виконання виклику `ioctl` на файловому дескрипторі попереднього рівня. Така ієрархічна модель гарантує безпечне ізолювання ресурсів: закриття дескриптора вищого рівня автоматично звільняє або деактивує всі пов'язані з ним дочірні ресурси.

```
/dev/kvm (System FD)
   │
   └── KVM_CREATE_VM ──> VM FD
                            │
                            ├── KVM_SET_USER_MEMORY_REGION (Слоти пам'яті)
                            ├── KVM_CREATE_IRQCHIP         (Вбудований APIC)
                            ├── KVM_IRQFD / KVM_IOEVENTFD  (Подійні канали)
                            │
                            └── KVM_CREATE_VCPU ──> vCPU FD
                                                     │
                                                     ├── mmap() ──> struct kvm_run
                                                     └── ioctl(KVM_RUN)
```

### Рівень 1: Системний дескриптор (System FD)

Системний дескриптор відкривається безпосередньо через файлову систему шляхом виклику `open("/dev/kvm", O_RDWR | O_CLOEXEC)`. Він не прив'язаний до жодної конкретної віртуальної машини, а відповідає за глобальний стан модуля KVM у ядрі Linux.

Основні виклики `ioctl` на системному дескрипторі:

- `KVM_GET_API_VERSION`: Повертає версію API KVM. Від Linux 2.6.22 ABI оголошено стабільним, і це значення дорівнює `12` та більше не змінюватиметься. Ядра 2.6.20 і 2.6.21, у яких KVM щойно з'явився, звітують менші числа — ці ранні версії ніколи не документували й не підтримували. Якщо виклик повертає не `12`, користувацький простір мусить негайно зупинити роботу через несумісність контракту.
- `KVM_CHECK_EXTENSION`: Перевіряє наявність апаратних або програмних розширень ядра. Приймає як аргумент константу розширення (наприклад, `KVM_CAP_USER_MEMORY`, `KVM_CAP_IRQCHIP`, `KVM_CAP_SIGNAL_MSI`). Повертає `0` або `1` (для деяких розширень — числовий ліміт, наприклад, максимальну кількість vCPU).
- `KVM_CREATE_VM`: Створює новий глобальний контекст віртуальної машини в ядрі та повертає новий дескриптор файлу `vm_fd`. Аргумент `machine_type` зазвичай дорівнює `0`, але на архітектурах ARM64 або s390x може задавати тип адресації.
- `KVM_GET_VCPU_MMAP_SIZE`: Повертає розмір у байтах буфера спільної пам'яті, який необхідно відобразити через `mmap()` для кожного vCPU, щоб отримати доступ до структури `struct kvm_run`.

### Рівень 2: Дескриптор віртуальної машини (VM FD)

Дескриптор `vm_fd` керує спільними ресурсами віртуальної машини: її фізичним адресним простором (Guest Physical Address, GPA), слотами пам'яті, вбудованими контролерами переривань та маршрутизацією подій.

Основні виклики `ioctl` на рівні VM:

- `KVM_SET_USER_MEMORY_REGION`: Прив'язує діапазон користувацької пам'яті хоста (Host Virtual Address, HVA) до фізичного адресного простору гостя (GPA). Передає вказівник на структуру `struct kvm_userspace_memory_region`.
- `KVM_CREATE_VCPU`: Створює новий віртуальний процесор з ідентифікатором `vcpu_id` (ціле число від 0 до системного ліміту) і повертає новий дескриптор `vcpu_fd`.
- `KVM_CREATE_IRQCHIP`: Доручає ядру KVM створити та симулювати всередині ядра контролери переривань (vLAPIC для кожного vCPU, vIOAPIC та vPIC). Це усуває потребу повертатися в QEMU при кожному перериванні.
- `KVM_IRQFD`: Прив'язує дескриптор `eventfd` користувацького простору до конкретного вектора переривання гостя. Запис у `eventfd` з боку будь-якого потоку хоста викликає миттєву інжекцію переривання у віртуальний процесор без участі vCPU-потоку QEMU.
- `KVM_IOEVENTFD`: Прив'язує запис гостя за певною адресою MMIO або порту I/O до дескриптора `eventfd`. Коли гість пише за цією адресою, ядро KVM не повертає контроль у QEMU через `KVM_EXIT_MMIO`, а просто сигналізує `eventfd` і негайно відновлює виконання гостя.

### Рівень 3: Дескриптор віртуального процесора (vCPU FD)

Дескриптор `vcpu_fd` відповідає за стан та виконання одного конкретного віртуального процесорного ядра. 

Основні виклики `ioctl` на рівні vCPU:

- `KVM_RUN`: Головна команда циклу виконання. Переводить потік хоста у гостьовий режим (VMX Non-Root Operation). Потік блокується всередині ядра до виникнення події `VMExit`. При поверненні повертає `0` у разі успішного перехоплення події або `-1` при системній помилці.
- `KVM_GET_REGS` / `KVM_SET_REGS`: Зчитує або перезаписує регістри загального призначення `struct kvm_regs` (RAX, RBX, RCX, RDX, RSI, RDI, RSP, RBP, R8–R15, RIP, RFLAGS).
- `KVM_GET_SREGS` / `KVM_SET_SREGS`: Зчитує або перезаписує сегментні регістри, керуючі регістри (CR0, CR2, CR3, CR4, CR8), регістр розширених можливостей EFER та таблиці дескрипторів GDT/IDT (`struct kvm_sregs`).
- `KVM_SET_CPUID2`: Передає віртуальному процесору конфігурацію функцій інструкції `CPUID`. Це дозволяє QEMU приховати від гостя частину можливостей процесора хоста або сформувати віртуальний процесор із заданим набором векторних розширень (SSE4.2, AVX2, AVX-512).

## 2. Структури даних спільної пам'яті

### Конфігурація пам'яті: `struct kvm_userspace_memory_region`

Для надання гостю фізичної пам'яті QEMU спочатку виділяє звичайну анонімну ділянку пам'яті в просторі користувача за допомогою системного виклику `mmap()`, а потім реєструє її в KVM через `struct kvm_userspace_memory_region`:

```c
struct kvm_userspace_memory_region {
    __u32 slot;            // Унікальний індекс слота пам'яті (0..KVM_MEM_SLOTS_NUM)
    __u32 flags;           // Прапори конфігурації регіону
    __u64 guest_phys_addr; // Початкова фізична адреса в гості (GPA)
    __u64 memory_size;     // Розмір регіону в байтах (мусить бути кратним 4 КіБ)
    __u64 userspace_addr;  // Вказівник на пам'ять у хості (HVA, повернутий mmap)
};
```

Допустимі значення поля `flags`:
- `KVM_MEM_LOG_DIRTY_PAGES`: Вмикає відстеження модифікованих сторінок (Dirty Page Tracking). Ядро KVM веде бітову карту сторінок, у які гість виконував запис. Використовується QEMU під час живої міграції (Live Migration) для копіювання лише тих сторінок, які змінилися.
- `KVM_MEM_READONLY`: Позначає слот як доступний лише для читання з боку гостя (прапор приймається, лише якщо `KVM_CHECK_EXTENSION` підтвердив `KVM_CAP_READONLY_MEM`). Будь-яка спроба запису викликає `EPT Violation`, який віддається користувацькому простору як `KVM_EXIT_MMIO`. Використовується для емуляції віртуальних мікросхем ROM та BIOS/UEFI прошивок.

Для конфіденційних гостей (Intel TDX, AMD SEV-SNP) поруч живе новіший `KVM_SET_USER_MEMORY_REGION2` зі структурою `kvm_userspace_memory_region2`: та сама п'ятірка полів плюс `guest_memfd` і `guest_memfd_offset`, які прив'язують слот до приватної пам'яті, створеної через `KVM_CREATE_GUEST_MEMFD`. Для звичайної віртуальної машини достатньо старого виклику.

### Буфер зв'язку: `struct kvm_run`

Структура `struct kvm_run` відображається в пам'ять користувацького простору через виклик `mmap()` на файловому дескрипторі `vcpu_fd`. Вона містить поточний стан виконання vCPU та детальні параметри події `VMExit`:

```c
struct kvm_run {
    /* Вхідні прапори користувацького простору */
    __u8 request_interrupt_window; // 1 = вийти з KVM_RUN, щойно гість буде готовий прийняти переривання
    __u8 immediate_exit;           // 1 = негайно перервати KVM_RUN
    __u8 padding1[6];

    /* Вихідні дані ядра */
    __u32 exit_reason;             // Код причини виходу з гостьового режиму
    __u8 ready_for_interrupt_injection;
    __u8 if_flag;                  // Стан прапора IF гостя
    __u16 flags;
    __u64 cr8;
    __u64 apic_base;

    /* Об'єднання (union) параметрів залежно від exit_reason */
    union {
        /* KVM_EXIT_IO: Емуляція портів введення-виведення (IN / OUT) */
        struct {
            __u8 direction;    // KVM_EXIT_IO_IN (0) або KVM_EXIT_IO_OUT (1)
            __u8 size;         // Розмір операції в байтах (1, 2, 4)
            __u16 port;        // Номер порту I/O (наприклад, 0x3F8)
            __u32 count;       // Кількість елементів для рядкових інструкцій (INS/OUTS)
            __u64 data_offset; // Зсув в байтах від початку структури kvm_run до буфера даних
        } io;

        /* KVM_EXIT_MMIO: Емуляція пам'яті пристроїв */
        struct {
            __u64 phys_addr;   // GPA адреса, до якої звернувся гість
            __u8  data[8];     // Буфер для прочитаних або записаних байтів
            __u32 len;         // Довжина операції (1..8 байтів)
            __u8  is_write;    // 1 = запис у пристрій, 0 = читання з пристрою
        } mmio;

        /* KVM_EXIT_FAIL_ENTRY: Апаратний збій інструкції VMLAUNCH/VMRESUME */
        struct {
            __u64 hardware_entry_failure_reason; // Апаратний код помилки Intel/AMD
            __u32 cpu;
        } fail_entry;

        /* KVM_EXIT_INTERNAL_ERROR: Внутрішній збій ядра KVM */
        struct {
            __u32 suberror;
            __u32 ndata;
            __u64 data[16];
        } internal;

        /* KVM_EXIT_SYSTEM_EVENT: Запит на перезавантаження або вимкнення */
        struct {
            __u32 type;        // KVM_SYSTEM_EVENT_SHUTDOWN, RESET, CRASH
            __u64 flags;
        } system_event;
    };
};
```

Це скорочений зріз: справжнє об'єднання має кілька десятків варіантів, по одному на клас причин виходу. Одна межа версій варта згадки окремо: до ядра 5.18 `system_event` виглядав саме так, як вище, а від 5.18 поле `flags` увійшло до об'єднання з масивом `data[16]`, і поруч з'явилося `ndata` з кількістю дійсних елементів. Старе ім'я `flags` лишили заради сумісності, тож код, який читає тільки його, працює й далі.

## 3. Деталізація причин виходу (Exit Reasons)

Після завершення системного виклику `ioctl(vcpu_fd, KVM_RUN, 0)` поле `exit_reason` містить код події, яка змусила ядро повернути контроль у QEMU:

1. `KVM_EXIT_IO` (2): Гість виконав порт-орієнтовану інструкцію `IN` або `OUT`. QEMU читає або записує байти за адресою `((char *)run + run->io.data_offset)` і негайно викликає `KVM_RUN` знову.
2. `KVM_EXIT_MMIO` (6): Гість виконав читання або запис за адресою GPA, яка не має відображення в EPT (наприклад, BAR-регістр PCI пристрою). Для операції читання (`is_write == 0`) QEMU повинен записати результат у масив `mmio.data` і знову викликати `KVM_RUN`.
3. `KVM_EXIT_HLT` (5): Гість виконав інструкцію `HLT`. Віртуальний процесор зупиняється. QEMU переводить потік vCPU у стан сну до приходу наступного апаратного або таймерного переривання.
4. `KVM_EXIT_INTR` (10): Виконання KVM було перервано доставкою звичайного POSIX-сигналу Linux (наприклад, `SIGALRM` або `SIGINT`), надісланого потоку vCPU. QEMU обробляє сигнал і поновлює цикл.
5. `KVM_EXIT_FAIL_ENTRY` (9): Критичний апаратний збій процесора Intel/AMD під час спроби виконати `VMLAUNCH` або `VMRESUME`. Свідчить про невалідні параметри у структурах VMCS/VMCB (наприклад, неправильно налаштовані сегментні межі або прапори `CR0`/`CR4`).
6. `KVM_EXIT_SHUTDOWN` (8): Гість зазнав критичної помилки ядра (Triple Fault). QEMU трактує це як перезавантаження або зупинку віртуальної машини.

## 4. Стан регістрів процесора

Структура `struct kvm_regs` описує стан регістрів загального призначення процесора x86-64:

```c
struct kvm_regs {
    __u64 rax, rbx, rcx, rdx;
    __u64 rsi, rdi, rsp, rbp;
    __u64 r8,  r9,  r10, r11, r12, r13, r14, r15;
    __u64 rip, rflags;
};
```

Структура `struct kvm_sregs` описує системний стан процесора, зокрема перемикачі режимів (Real Mode, Protected Mode, Long Mode):

```c
struct kvm_segment {
    __u64 base;        // Базова адреса сегмента
    __u32 limit;       // Межа сегмента
    __u16 selector;    // Селектор сегмента
    __u8  type;        // Тип сегмента (Code, Data, System)
    __u8  present;     // Прапор наявності (P)
    __u8  dpl;         // Рівень привілеїв (Descriptor Privilege Level, 0..3)
    __u8  db;          // Default size (0 = 16-bit, 1 = 32-bit)
    __u8  s;           // Descriptor type (0 = system, 1 = code/data)
    __u8  l;           // Long mode прапор (1 = 64-bit code)
    __u8  g;           // Granularity (0 = byte, 1 = сторінка 4 КіБ)
    __u8  avl;
    __u8  unusable;
    __u8  padding;
};

struct kvm_sregs {
    struct kvm_segment cs, ds, es, fs, gs, ss;
    struct kvm_segment tr, ldt;
    struct kvm_dtable gdt, idt;
    __u64 cr0, cr2, cr3, cr4, cr8;
    __u64 efer;        // Extended Feature Enable Register (вмикає Long Mode)
    __u64 apic_base;   // Фізична адреса Local APIC
    __u64 interrupt_bitmap[(KVM_NR_INTERRUPTS + 63) / 64];
};
```

Правильне заповнення полів `cs`, `rip`, `cr0` та `efer` дозволяє користувацькому простору точно визначити стартовий стан віртуального процесора — від 16-бітного режиму Real Mode при симуляції старту BIOS до прямого стрибка у 64-бітний Long Mode у схемах прямого завантаження ядра на кшталт PVH чи машини `microvm`.
