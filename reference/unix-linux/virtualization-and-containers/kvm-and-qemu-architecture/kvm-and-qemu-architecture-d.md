Уявіть, що ви намагаєтеся запустити повноцінну операційну систему в ізольованому середовищі (віртуальній машині), використовуючи лише програмну емуляцію всіх інструкцій процесора та звернень до пам'яті. Цей підхід, відомий як повна програмна емуляція, працює настільки повільно, що завантаження звичайного ядра може зайняти хвилини або навіть години, а виконання повсякденних задач стає нестерпним. Справжня проблема полягає в тому, що більшість інструкцій гостьової ОС (наприклад, математичні операції або маніпуляції з регістрами) є абсолютно безпечними для виконання безпосередньо на фізичному процесорі, проте гіпервізор повинен мати змогу перехопити так звані «привілейовані» інструкції (наприклад, звернення до апаратного забезпечення або зміну таблиць сторінок), не дозволяючи гостю зруйнувати хост-систему. Як організувати цей «прозорий» і безпечний прямий доступ до процесора без колосальних втрат продуктивності? Відповіддю є апаратно-асистентна віртуалізація.

KVM (Kernel-based Virtual Machine) — це інфраструктура віртуалізації в ядрі Linux, яка перетворює ядро на гіпервізор типу 1 (або 1.5, враховуючи його гібридну природу). Завдяки апаратній підтримці (Intel VT-x та AMD-V), KVM дозволяє гостьовим операційним системам виконувати не-привілейований код зі швидкістю, майже еквівалентною «голому залізу» (bare metal).

## Вступ до KVM: Архітектурний огляд

До появи KVM, гіпервізори часто розроблялися як окремі, спеціалізовані міні-ОС (наприклад, ранні версії Xen), що вимагало дублювання функціоналу (планування завдань, управління пам'яттю, драйвери пристроїв). Філософія KVM кардинально інша: **навіщо писати новий гіпервізор з нуля, якщо ядро Linux вже має все необхідне?** Linux вміє планувати процеси, керувати пам'яттю, працювати з NUMA, має драйвери для будь-якого обладнання. KVM просто додає до Linux новий режим виконання — *гостьовий режим* (guest mode).

### Три режими виконання

Замість традиційних двох режимів (User Mode та Kernel Mode), KVM-система оперує трьома:
1. **User Mode:** Виконується звичайний користувацький код хоста (наприклад, емулятор QEMU, який керує VM).
2. **Kernel Mode:** Виконується код ядра Linux. Сюди хост повертається для обробки переривань, системних викликів, або коли KVM потрібно емулювати специфічні операції для гостя.
3. **Guest Mode:** Виконується код гостьової ОС (як її ядро, так і користувацький простір гостя). У цьому режимі фізичний процесор напряму виконує гостьові інструкції.

### Роль `/dev/kvm` та користувацького простору (QEMU)

KVM сам по собі не емулює пристрої (диски, мережеві карти, відеокарти) і не створює віртуальні машини в класичному розумінні. KVM надає лише механізм доступу до апаратної віртуалізації через символьний пристрій `/dev/kvm`.

Будь-яка програма користувацького простору, що має відповідні права, може відкрити `/dev/kvm` і використовувати `ioctl` для створення та запуску VM. Найпопулярнішим користувацьким компонентом є QEMU (часто разом з libvirt).
Розподіл обов'язків такий:
- **KVM (у ядрі):** Забезпечує виконання процесорних інструкцій, керує віртуальним MMU (доступом до пам'яті), інжектує переривання в гостя, керує розширеннями Intel VT-x/AMD-V.
- **QEMU (у користувацькому просторі):** Виділяє пам'ять для гостя, емулює апаратні пристрої (PCI, IDE/SCSI, мережу), керує життєвим циклом VM, взаємодіє з користувачем або системою управління (libvirt).

## API KVM: ioctl інтерфейс

Інтерфейс KVM базується на послідовних викликах `ioctl` до дескрипторів, отриманих з `/dev/kvm`. Процес ініціалізації віртуальної машини виглядає наступним чином:

:::tabs
== C
```c
// 1. Відкриття /dev/kvm
int kvm_fd = open("/dev/kvm", O_RDWR | O_CLOEXEC);

// 2. Створення VM (KVM_CREATE_VM)
int vm_fd = ioctl(kvm_fd, KVM_CREATE_VM, 0);

// 3. Налаштування пам'яті (KVM_SET_USER_MEMORY_REGION)
struct kvm_userspace_memory_region region = {
    .slot = 0,
    .guest_phys_addr = 0x100000,
    .memory_size = 512 * 1024 * 1024, // 512 MB
    .userspace_addr = (uint64_t)qemu_mmap_ptr,
};
ioctl(vm_fd, KVM_SET_USER_MEMORY_REGION, &region);

// 4. Створення vCPU (KVM_CREATE_VCPU)
int vcpu_fd = ioctl(vm_fd, KVM_CREATE_VCPU, vcpu_id);
```
== Rust
```rust
// Приклад використання через крейт kvm_ioctls
use kvm_ioctls::{Kvm, VmFd};
use kvm_bindings::kvm_userspace_memory_region;

let kvm = Kvm::new().unwrap();
let vm = kvm.create_vm().unwrap();

let mem_region = kvm_userspace_memory_region {
    slot: 0,
    guest_phys_addr: 0x100000,
    memory_size: 512 * 1024 * 1024,
    userspace_addr: qemu_mmap_ptr as u64,
    flags: 0,
};
unsafe { vm.set_user_memory_region(mem_region).unwrap(); }

let vcpu = vm.create_vcpu(0).unwrap();
```
:::

5. **Пам'ять комунікації (`kvm_run`):**
KVM та користувацький простір ділять спільну структуру `kvm_run` для обміну інформацією про стан vCPU. QEMU отримує її адресу через `mmap(vcpu_fd, ...)`.

6. **Цикл виконання vCPU (`KVM_RUN`):**
Це серце віртуалізації. Потік vCPU у QEMU входить у безкінечний цикл:

```c
while (1) {
    // Передаємо управління гостьовій ОС
    ioctl(vcpu_fd, KVM_RUN, 0);
    
    // Якщо ioctl повернувся, значить гість виконав дію, яку 
    // KVM не зміг обробити в ядрі і потребує допомоги QEMU.
    switch (run->exit_reason) {
        case KVM_EXIT_IO:
            handle_pio(run->io); // Емуляція PIO (in/out)
            break;
        case KVM_EXIT_MMIO:
            handle_mmio(run->mmio); // Емуляція Memory-Mapped IO
            break;
        case KVM_EXIT_HLT:
            wait_for_interrupt(); // Гість виконав інструкцію hlt (idle)
            break;
        // ... інші причини
    }
}
```

## Апаратна підтримка: Intel VT-x та AMD-V

Щоб зрозуміти, що відбувається під час виклику `KVM_RUN`, потрібно заглибитися в апаратні розширення процесорів. У 2005-2006 роках Intel та AMD майже одночасно представили свої розширення для віртуалізації (VT-x та AMD-V відповідно). Вони вирішували ключову проблему: архітектура x86 не була «класично віртуалізовною» через певні інструкції, які вели себе по-різному залежно від режиму привілеїв, але не генерували виключень (traps), якщо виконувалися в непривілейованому режимі.

### VMX та режими Root / Non-Root (Intel VT-x)

Intel VT-x (Virtual Machine Extensions, VMX) вводить два нові режими роботи процесора:
- **VMX Root Operation:** Повністю привілейований режим. Тут працює гіпервізор (KVM). Цей режим майже ідентичний звичайному захищеному режиму x86, але з додаванням нових інструкцій VMX.
- **VMX Non-Root Operation:** Режим, у якому працює гостьова ОС. У цьому режимі, навіть якщо гостьове ядро виконується в кільці 0 (Ring 0), воно не має повного контролю над фізичним апаратним забезпеченням.

### VMCS (Virtual-Machine Control Structure)

VMCS — це спеціальна структура в оперативній пам'яті, керована апаратно, яка містить весь стан віртуальної машини. Для кожного vCPU KVM виділяє окрему VMCS (в AMD аналог називається VMCB - Virtual Machine Control Block).

VMCS містить кілька зон:
1. **Guest-state area:** Стан процесора (всі регістри, лічильник команд, сегменти) під час перебування в гостьовому режимі. При вході в гостя процесор автоматично завантажує ці значення.
2. **Host-state area:** Стан фізичного процесора (гіпервізора). Коли відбувається вихід з гостя (VM-Exit), процесор зберігає поточний стан у guest-state і завантажує стан хоста з host-state, щоб KVM міг коректно продовжити роботу.
3. **VM-execution control fields:** Визначають, які дії гостя повинні призводити до VM-Exit. Наприклад, KVM може налаштувати VMCS так, щоб будь-яке звернення до регістра CR3 (таблиці сторінок) спричиняло вихід.
4. **VM-exit information fields:** Після VM-Exit тут міститься детальна інформація про те, чому відбувся вихід (наприклад, адреса інструкції, що викликала fault, або номер порту вводу-виводу).

### Процес переходу: VMLAUNCH / VMRESUME та VM-Exit

Коли потік QEMU викликає `KVM_RUN`, ядро Linux готує VMCS, перевіряє стан і виконує спеціальну асамблерну інструкцію: `VMLAUNCH` (для першого запуску) або `VMRESUME` (для наступних).

Виконання цієї інструкції ініціює **VM-Entry**. Фізичний процесор миттєво перемикається в *VMX Non-Root mode*, завантажує регістри з VMCS і починає виконувати код гостя на повній фізичній швидкості.

Гість працює доти, доки не станеться подія, яка вимагає втручання гіпервізора. Це може бути:
- Апаратне переривання на хості (наприклад, прийшов мережевий пакет або закінчився таймер планувальника).
- Звернення гостя до емульованого пристрою (I/O порт, MMIO).
- Спроба гостя виконати привілейовану дію (наприклад, змінити налаштування віртуалізації).

Коли стається така подія, процесор апаратно виконує **VM-Exit**. Він зберігає стан гостя у VMCS, завантажує стан KVM, і потік виконання повертається до функції гіпервізора у ядрі. KVM аналізує причину виходу (читаючи VMCS).
- Якщо причиною було зовнішнє переривання, KVM передає його ядру Linux для обробки, а потім повертає гостя до роботи (VM-Entry).
- Якщо гість звернувся до внутрішньоядерного емулятора (наприклад, APIC), KVM обробляє це самостійно.
- Якщо гість звернувся до складного емульованого пристрою (наприклад, віртуального диска), KVM завершує ioctl `KVM_RUN` і повертає керування в QEMU. QEMU читає структуру `kvm_run`, емулює цю дію, змінює стан і знову викликає `KVM_RUN`.

## Управління пам'яттю: EPT та NPT

Віртуалізація пам'яті — одна з найскладніших задач. У віртуальній машині гість має власні таблиці сторінок. Він думає, що працює з фізичною пам'яттю, але насправді ця «фізична пам'ять» (Guest Physical Address, GPA) є просто віртуальною пам'яттю процесу QEMU на хості (Host Virtual Address, HVA), яка потім відображається на реальну фізичну пам'ять (Host Physical Address, HPA).

Отже, нам потрібна **двостадійна трансляція**:
1. GVA (Guest Virtual) -> GPA (Guest Physical): керується гостьовою ОС.
2. GPA (Guest Physical) -> HPA (Host Physical): керується KVM.

Ранні реалізації використовували метод *Shadow Page Tables (Тіньові таблиці сторінок)*, що вимагало колосальних накладних витрат. Сучасний підхід — апаратна підтримка **EPT (Intel)** або **NPT (AMD)** (загальна назва — Second Level Address Translation, SLAT).

З EPT процесор має два паралельних набори таблиць сторінок. Коли гість звертається до пам'яті, процесор (MMU) читає гостьові таблиці сторінок, щоб перекласти GVA в GPA. Але для кожного звернення до пам'яті під час цього процесу MMU використовує структуру EPT (якою керує KVM), щоб апаратно перекласти GPA в HPA. KVM лише підтримує таблиці EPT актуальними (відображаючи те, як QEMU виділив пам'ять).

### Емуляція MMIO (Memory-Mapped I/O)

Коли QEMU створює віртуальну мережеву карту, він резервує ділянку GPA для її регістрів. Проте QEMU **не** повідомляє KVM про те, що ця ділянка має мапитись на реальну пам'ять, тому в таблицях EPT немає записів.

Що відбувається, коли гостьовий драйвер записує дані в регістр?
1. Гість виконує запис за адресою регістра.
2. MMU гостя перетворює GVA на GPA.
3. Апаратний MMU звертається до таблиць EPT, щоб знайти HPA.
4. Запису в EPT немає! Відбувається EPT Violation, що спричиняє VM-Exit.
5. KVM бачить, що сталося EPT Violation, і розуміє, що це доступ до MMIO. KVM готує структуру `kvm_run->mmio` і повертає керування в QEMU.
6. QEMU читає `kvm_run`, ідентифікує пристрій, виконує логіку, і знову викликає `ioctl(KVM_RUN)`.

## Паравіртуалізація з Virtio

Незважаючи на апаратну допомогу (EPT, VT-x), повна емуляція пристроїв через перехоплення MMIO (VM-Exit -> KVM -> QEMU -> емуляція пристрою) є дуже повільною для інтенсивного вводу/виводу, такого як мережа чи диски. Щоб вирішиць цю проблему, використовується паравіртуалізація — **virtio**.

Філософія virtio полягає в тому, що гостьова ОС "знає", що вона працює у віртуальній машині. Замість емуляції реального "заліза" (як-от мережевої карти Intel e1000), хост надає гостю спеціальні паравіртуалізовані пристрої (virtio-net, virtio-blk). Гість має спеціальний драйвер, який взаємодіє з гіпервізором напряму через високоефективні кільцеві буфери у спільній пам'яті (virtqueues), мінімізуючи кількість дорогих операцій VM-Exit.

Це дозволяє досягати швидкостей дискових операцій і мережевої передачі, що майже дорівнюють швидкостям фізичної системи, оскільки KVM/QEMU можуть напряму читати дані з пам'яті гостя, не емулюючи кожен біт переміщення даних через порти введення/виведення.

## Висновок

KVM демонструє силу філософії ядра Linux — повторне використання існуючих компонентів. Замість монолітного гіпервізора, ми маємо елегантний драйвер (`/dev/kvm`), який відкриває двері до апаратних можливостей процесора. Разом з QEMU та апаратними розширеннями на кшталт EPT/VT-x та паравіртуалізацією virtio, KVM створює віртуальні машини, що працюють з мінімальними накладними витратами, залишаючись при цьому звичайними Linux-процесами.
