## Вступ до проблеми утилізації CPU

У сучасних ядрах Linux планувальник завдань виконує надзвичайно складну роботу, намагаючись збалансувати продуктивність, затримки (latency) та енергоспоживання. Зазвичай, для відстеження навантаження на процесор використовується механізм **PELT (Per-Entity Load Tracking)**. Він дозволяє ядру відстежувати, скільки часу кожне завдання (потік, процес або група cgroup) проводить у стані виконання або очікування на виконання, формуючи "сигнал утилізації" (utilization signal). На основі цього сигналу регулятор частоти процесора (наприклад, `schedutil`) приймає рішення про підвищення або зниження тактової частоти CPU (DVFS - Dynamic Voltage and Frequency Scaling).

Проте, сам по собі PELT має суттєвий недолік: він реагує на зміни навантаження поступово (за замовчуванням період напіврозпаду становить 32 мс). Якщо завдання несподівано прокидається і потребує максимальної продуктивності для забезпечення мінімальної затримки (наприклад, рендеринг кадру в грі або обробка аудіо), PELT знадобиться певний час, щоб "розігрітися" і повідомити регулятору про необхідність підвищення частоти. З іншого боку, фонові завдання можуть призводити до непотрібного підвищення частоти, що негативно позначається на часі автономної роботи пристрою.

Саме для вирішення цих проблем був розроблений механізм **Utilization Clamping (uclamp)**. Він дозволяє користувацькому простору (userspace) вказувати планувальнику мінімальні (`uclamp.min`) та максимальні (`uclamp.max`) межі утилізації для конкретних завдань або їх груп.

## Що таке uclamp?

**Utilization Clamping (uclamp)** — це механізм ядра Linux (доданий у версії 5.3), який дозволяє обмежувати або "затискати" (clamp) сигнал утилізації, який бачить планувальник і регулятор частоти.

- **`uclamp.min` (Гарантія частоти):** Вказує мінімальний рівень утилізації для завдання. Якщо фактична утилізація за PELT нижча за `uclamp.min`, планувальник діятиме так, ніби утилізація дорівнює `uclamp.min`. Це ефективно змушує регулятор `schedutil` підняти частоту CPU до певного мінімального рівня відразу, як тільки завдання починає виконуватися, не чекаючи "розігріву" PELT. Це критично для завдань, чутливих до затримок.
- **`uclamp.max` (Обмеження частоти):** Вказує максимальний рівень утилізації для завдання. Навіть якщо завдання повністю завантажує процесор (утилізація за PELT дорівнює 100%), планувальник обмежить цей сигнал значенням `uclamp.max`. Це не дозволить регулятору підвищувати частоту CPU вище певного рівня, заощаджуючи заряд батареї. Це ідеально для фонових процесів, які можуть виконуватися довше, але не повинні розряджати батарею.

Сигнал утилізації вимірюється в діапазоні від 0 до 1024 (де 1024 відповідає 100% утилізації найпродуктивнішого ядра в системі).

## Системний виклик `sched_setattr(2)`

Для управління параметрами uclamp на рівні окремих потоків використовується системний виклик `sched_setattr(2)`. Він дозволяє встановлювати різні атрибути планування, включаючи пріоритети, політику (наприклад, `SCHED_DEADLINE`, `SCHED_FIFO`, `SCHED_NORMAL`), а також параметри uclamp.

Щоб використовувати uclamp через `sched_setattr`, необхідно встановити прапор `SCHED_FLAG_UTIL_CLAMP`.

### Структура `sched_attr`

```c
#include <sched.h>
#include <linux/sched/types.h>

struct sched_attr {
    __u32 size;                 /* Розмір структури */
    __u32 sched_policy;         /* Політика планування (наприклад, SCHED_OTHER) */
    __u64 sched_flags;          /* Прапори, наприклад SCHED_FLAG_UTIL_CLAMP_MIN | SCHED_FLAG_UTIL_CLAMP_MAX */
    __s32 sched_nice;           /* Значення nice (для SCHED_OTHER, SCHED_BATCH) */
    __u32 sched_priority;       /* Статичний пріоритет (для SCHED_FIFO, SCHED_RR) */
    /* ... параметри для SCHED_DEADLINE ... */
    __u32 sched_util_min;       /* uclamp_min (0 - 1024) */
    __u32 sched_util_max;       /* uclamp_max (0 - 1024) */
};
```

### Прапори uclamp

- `SCHED_FLAG_UTIL_CLAMP_MIN`: Вказує, що поле `sched_util_min` містить валідне значення і має бути застосоване.
- `SCHED_FLAG_UTIL_CLAMP_MAX`: Вказує, що поле `sched_util_max` містить валідне значення і має бути застосоване.
- `SCHED_FLAG_UTIL_CLAMP`: Це комбінація обох вищевказаних прапорів (`SCHED_FLAG_UTIL_CLAMP_MIN | SCHED_FLAG_UTIL_CLAMP_MAX`).

### Приклад коду на C

Нижче наведено приклад програми, яка встановлює для себе `uclamp_min` на 512 (гарантує як мінімум 50% продуктивності) та `uclamp_max` на 768 (обмежує продуктивність до 75%).

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <linux/sched/types.h>
#include <sys/syscall.h>

/* Обертка для sched_setattr, оскільки glibc може не надавати її безпосередньо */
int sched_setattr(pid_t pid, const struct sched_attr *attr, unsigned int flags) {
    return syscall(SYS_sched_setattr, pid, attr, flags);
}

int main() {
    struct sched_attr attr = {0};
    attr.size = sizeof(attr);
    
    /* Ми змінюємо лише параметри uclamp, залишаючи інше без змін.
       Для цього краще спочатку викликати sched_getattr(), але для простоти
       встановимо політику SCHED_OTHER (звичайна політика). */
    attr.sched_policy = SCHED_OTHER;
    
    /* Встановлюємо прапори для оновлення обох значень uclamp */
    attr.sched_flags = SCHED_FLAG_UTIL_CLAMP;
    
    /* Встановлюємо значення uclamp (масштаб 0 - 1024) */
    attr.sched_util_min = 512; /* Гарантуємо ~50% продуктивності */
    attr.sched_util_max = 768; /* Обмежуємо до ~75% продуктивності */
    
    if (sched_setattr(0, &attr, 0) == -1) {
        perror("sched_setattr failed");
        exit(EXIT_FAILURE);
    }
    
    printf("uclamp_min and uclamp_max successfully applied!\n");
    
    /* Нескінченний цикл навантаження для тестування (обережно!) */
    while (1) {
        /* ... інтенсивні обчислення ... */
    }
    
    return 0;
}
```

## Інтеграція з Cgroups v2 (cpu.uclamp.min, cpu.uclamp.max)

Крім встановлення параметрів uclamp для окремих потоків (через `sched_setattr`), Linux дозволяє управляти uclamp на рівні груп процесів через Cgroups v2. Це особливо зручно для контейнерів або додатків в Android, де завдання групуються за їхньою роллю (наприклад, "top-app", "background").

У контролері `cpu` Cgroups v2 доступні два нові файли:
- `cpu.uclamp.min`
- `cpu.uclamp.max`

На відміну від `sched_setattr`, де значення вказуються в діапазоні 0-1024, у Cgroups v2 вони вказуються у відсотках з двома десятковими знаками (від `0.00` до `100.00`) або зі спеціальним значенням `max`.

### Приклад використання Cgroups

Створимо cgroup для фонових завдань і обмежимо їхню максимальну продуктивність до 20%:

```bash
# Створюємо cgroup
mkdir /sys/fs/cgroup/background_tasks

# Дозволяємо контроль CPU (якщо не увімкнено за замовчуванням)
# Впевніться, що контролер cpu доступний у cgroup.controllers і cgroup.subtree_control

# Обмежуємо uclamp.max до 20%
echo 20.00 > /sys/fs/cgroup/background_tasks/cpu.uclamp.max

# Перевіряємо значення
cat /sys/fs/cgroup/background_tasks/cpu.uclamp.max
# Вивід: 20.00

# Додаємо процес до цієї cgroup (де 1234 - PID процесу)
echo 1234 > /sys/fs/cgroup/background_tasks/cgroup.procs
```

Створимо cgroup для критичних до затримок завдань (наприклад, UI потік) і гарантуємо їм мінімум 60% продуктивності:

```bash
mkdir /sys/fs/cgroup/ui_critical
echo 60.00 > /sys/fs/cgroup/ui_critical/cpu.uclamp.min
```

### Як взаємодіють обмеження завдань та cgroup?

Коли завдання належить до cgroup із встановленими параметрами uclamp, і саме завдання має свої параметри uclamp (встановлені через `sched_setattr`), ядро застосовує політику **ефективних значень** (effective values).

Загальне правило полягає в тому, що обмеження cgroup діють як жорсткі межі (clamping) для запитів окремих завдань:
- Ефективний `uclamp.max` завдання не може перевищувати `uclamp.max` його cgroup.
- Ефективний `uclamp.min` завдання обмежується (clamped) значенням `uclamp.max` його cgroup (щоб завдання не могло вимагати більше мінімуму, ніж дозволяє максимум групи).

## Системні параметри (Sysctls)

Для глобального управління та налаштування uclamp доступні системні змінні через `/proc/sys/kernel/`:

1. **`/proc/sys/kernel/sched_util_clamp_min`**
   - Глобальний мінімум. Дозволяє системному адміністратору або фреймворку (наприклад, Android OS) підняти мінімальну продуктивність для всієї системи. Зазвичай встановлено на 0.

2. **`/proc/sys/kernel/sched_util_clamp_max`**
   - Глобальний максимум. Обмежує максимальну продуктивність системи. За замовчуванням 1024.

3. **`/proc/sys/kernel/sched_util_clamp_min_rt_default`**
   - Це дуже важливий параметр. За замовчуванням завдання з політиками реального часу (Real-Time, такі як `SCHED_FIFO` та `SCHED_RR`) завжди отримують максимальну частоту CPU (їхній умовний `uclamp.min` дорівнює 1024). Якщо цей sysctl змінити на менше значення, RT-завдання більше не змушуватимуть CPU працювати на максимальній частоті, якщо їх фактичне навантаження невелике, що значно покращує енергоефективність.

## Взаємодія з апаратним забезпеченням (EAS та CPPC)

Механізм uclamp відіграє ключову роль у сучасних архітектурах планування, таких як **EAS (Energy Aware Scheduling)**, яка широко використовується на архітектурі ARM (в смартфонах).

### EAS (Energy Aware Scheduling)
EAS використовує інформацію про утилізацію завдань та енергетичну модель (Energy Model) процесора для вибору найбільш енергоефективного ядра (наприклад, LITTLE, MID або BIG у конфігурації ARM big.LITTLE / DynamIQ) для виконання завдання.

`uclamp` безпосередньо впливає на цей вибір:
- Якщо завдання має високий `uclamp.min` (наприклад, 800), EAS розуміє, що цьому завданню потрібна висока продуктивність, і навіть якщо воно прокинулося після тривалого сну (його PELT низький), EAS відразу розмістить його на великому (BIG) ядрі.
- Якщо завдання має низький `uclamp.max` (наприклад, 200), EAS розмістить його на маленькому (LITTLE) ядрі, гарантуючи, що воно не розбудить енергоємне велике ядро, навіть якщо завдання виконуватиметься нескінченно довго.

### x86 та CPPC (Collaborative Processor Performance Control)
На платформі x86 технології на кшталт Intel Speed Shift (HWP) та AMD CPPC дозволяють апаратному забезпеченню самостійно керувати частотою, отримуючи "підказки" (hints) від операційної системи. Коли uclamp змінює сигнал утилізації, драйвери регуляторів частоти (наприклад, `intel_pstate` з `schedutil` або `amd-pstate`) конвертують ці сигнали в підказки продуктивності (Desired Performance, Minimum Performance, Maximum Performance) і передають їх процесору через MSR (Model-Specific Registers). Таким чином, обмеження, встановлені через uclamp у просторі користувача, безпосередньо транслюються в апаратні інструкції управління живленням.

## Висновки

Utilization Clamping (`uclamp`) — це потужний інструмент, що перекидає місток між простором користувача та підсистемами планування/управління частотою в ядрі Linux. Використовуючи `uclamp.min`, розробники додатків можуть гарантувати відсутність затримок (latency spikes) для критичних потоків під час їхнього раптового пробудження. Завдяки `uclamp.max`, фонові та низькопріоритетні процеси можуть бути жорстко обмежені в споживанні енергії, залишаючись на найповільніших ядрах і не розряджаючи батарею. Разом з Cgroups v2 та EAS, uclamp є фундаментальним компонентом сучасного управління продуктивністю та енергоефективністю в Linux та Android.
