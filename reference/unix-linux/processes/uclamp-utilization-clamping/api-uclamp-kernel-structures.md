# 📋 Внутрішні структури ядра Linux та системний ABI uclamp

Підсистема Utilization Clamping у ядрі Linux охоплює внутрішні структури даних планивальника `struct sched_entity`, чергу виконання `struct rq`, підсистему Cgroups v2 та системний ABI через системні виклики `sched_setattr(2)` і `sched_getattr(2)`.

Усі параметри uclamp всередині ядра нормалізовані до шкали від 0 до 1024 одиниць. Значення 1024 відповідає 100% обчислювальної спроможності найпотужнішого ядра системи (наприклад, BIG-ядра у процесорах ARM DynamIQ або турбо-ядра у процесорах x86).

## Структури даних ядра Linux

Кожен елемент планування `sched_entity` та кожна група контролера CPU у Cgroups v2 містить два екземпляри структури `struct uclamp_se` (один для `UCLAMP_MIN`, декілька для `UCLAMP_MAX`).

### 1. Структура `struct uclamp_se`

Структура `struct uclamp_se` зберігає інформацію про поточні налаштування утилізації для окремого завдання або цілої cgroup:

```c
struct uclamp_se {
    unsigned int value;       /* Запитуване значення uclamp у діапазоні 0..1024 */
    unsigned int bucket_id;   /* Індекс бакета (0..4) у масиві uclamp_buckets */
    unsigned int active : 1;  /* Прапор: чи знаходиться задача у черзі виконання (rq) */
    unsigned int user_defined : 1; /* Чи було значення встановлено явно через sched_setattr */
};
```

Індекс бакета обчислюється ядрами за допомогою цілочисельного ділення запитуваного значення на розмір діапазону:

```
bucket_id = value / (1024 / 5) = value / 205
```

Цей індекс прив'язує значення задачи до одного з п'яти фіксованих діапазонів, що дозволяє черзі виконання групувати задачі зі схожими вимогами до продуктивності.

### 2. Структура `struct uclamp_rq` та бакети черги

Черга виконання кожної CPU-ячейки `struct rq` відстежує активні обмеження uclamp усіх runnable-задач за допомогою масиву бакетів:

```c
struct uclamp_bucket {
    unsigned int value;  /* Точне максимальне значення uclamp серед задач цього бакета */
    unsigned int tasks;  /* Лічильник активних задач у цьому бакеті */
};

struct uclamp_rq {
    unsigned int value;  /* Ефективне значення uclamp для всієї черги rq */
    struct uclamp_bucket bucket[5]; /* 5 бакетів утилізації */
};
```

Під час активації задачи (`enqueue_task`) ядро визначає її `bucket_id` і виконує такі кроки:

1. Збільшує лічильник активних задач у даному бакеті: `rq->uclamp[UCLAMP_MIN].bucket[bucket_id].tasks++`.
2. Оновлює точне максимальне значення бакета: `bucket[bucket_id].value = max(bucket[bucket_id].value, task.value)`.
3. Оновлює загальне значення утилізації черги `uclamp_rq.value`.

При деактивації задачи (`dequeue_task`) лічильник декрементується. Якщо `tasks` стає рівним 0, бакет деактивується. Швидкий пошук максимуму `uclamp_rq` сканує бакети від індексу 4 до 0 за фіксований час O(1).

## Системні параметри Sysctl (`/proc/sys/kernel/`)

Ядро надає три глобальні системні змінні для керування поведінкою uclamp:

- `/proc/sys/kernel/sched_util_clamp_min`: Глобальний мінімум системної утилізації (за замовчуванням 0). Визначає найнижчу межу для всіх задач у системі.
- `/proc/sys/kernel/sched_util_clamp_max`: Глобальний максимум системної утилізації (за замовчуванням 1024). Дозволяє системному адміністратору глобально затиснути продуктивність усієї системи (наприклад, у режимі критичного збереження енергії).
- `/proc/sys/kernel/sched_util_clamp_min_rt_default`: Значення `uclamp_min` за замовчуванням для потоків реального часу (`SCHED_FIFO` та `SCHED_RR`). За замовчуванням ядро виставляє тут 1024 (максимальна частота для будь-якої RT-задачі). Зниження цього значення до 512 запобігає перевитраті енергії RT-потоками з низьким робочим циклом.

## Інтерфейс Cgroups v2 (`cpu.uclamp.min` та `cpu.uclamp.max`)

У контролері `cpu` ієрархії Cgroups v2 значення задаються у відсотках від `0.00` до `100.00` або ключовим словом `max`:

- `cpu.uclamp.min`: Нижня межа утилізації для всіх задач даної групи.
- `cpu.uclamp.max`: Верхня межа утилізації для всіх задач даної групи.

При обчисленні ефективного значення утилізації для конкретної задачи ядро застосовує внутрішню функцію `uclamp_eff_value()`, яка обчислює перетин параметрів задачи з усіма батьківськими cgroups:

```
effective_max = min(task.uclamp_max, cgroup.uclamp_max)
effective_min = clamp(task.uclamp_min, cgroup.uclamp_min, effective_max)
```

Такий підхід гарантує, що жоден потік користувача не зможе обійти обмеження своєї cgroup, навіть якщо він має привілеї виклику `sched_setattr(2)`. Обчислення ефективного значення відбувається динамічно під час зміни структури cgroups або оновлення атрибутів планувальника, гарантуючи ізоляцію ресурсів багатоорендних систем.

## Обробка помилок та перевірка привілеїв у системних викликах

Під час виконання системного виклику `sched_setattr(2)` ядро перевіряє права доступу процесу:

1. **Значення `sched_util_min` > 0:** Вимагає від процесу наявності системної капабіліті `CAP_SYS_NICE`. Без цієї капабіліті виклик поверне помилку `-EPERM`. Це запобігає ситуації, коли непривілейований процес намагається розігнати частоту CPU та підвищити власне споживання ресурсів.
2. **Значення `sched_util_max`:** Може знижуватися непривілейованим процесом для власного потоку без додаткових прав, оскільки зниження максимуму лише обмежує використання ресурсів і є безпечним для системи.

Оцінити стан помилок у просторі користувача можна через стандартну змінну `errno`, перевіряючи значення `-EINVAL` (невалідний діапазон понад 1024) або `-EPERM` (відсутність прав `CAP_SYS_NICE`).

## Трейспоінти ядра та інструменти розробника

Для моніторингу uclamp на рівні ядра передбачені наступні трасувальні інтерфейси:

- `/sys/kernel/tracing/events/sched/sched_util_clamp`: Подія ftrace, що фіксує зміну ефективного значення утилізації черги `rq`.
- `/proc/sys/kernel/sched_energy_aware`: Прапор активації підсистеми EAS, яка використовує uclamp для вибору енергоефективних ядер.
- `/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`: Поточна частота CPU, що відображає миттєвий ефект від роботи uclamp.

## Наслідки успадкування при виклику fork(2) та clone(2)

Під час створення нового дочірнього потоку або процесу викликами `fork(2)` та `clone(2)` ядро копіює значення uclamp з батьківської структури `task_struct`. Дочірній потік успадковує прапор `uclamp.user_defined`. Якщо батьківський потік мав `uclamp_min = 500`, дочірній потік автоматично запускається з тими самими параметрами, що дозволяє пулам воркерів зберігати заданий профіль продуктивності без додаткових викликів системних функцій.

## Спостереження за утилізацією через cgroup.stat

У середовищі Cgroups v2 розробники можуть моніторити поточний стан затискання утилізації для всієї групи за допомогою файла `cpu.stat`. Файл розкриває агреговані метрики часу утилізації, включно з інформацією про обмеження частоти процесора для даного контейнера.
