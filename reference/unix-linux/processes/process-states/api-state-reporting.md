# 📋 Де система показує стан задачі: літери, поля й ключі

Ця довідка збирає всі місця, якими Linux віддає стан задачі назовні: повний перелік літер і модифікаторів у виводі `ps`, точні поля `/proc`, звідки ці літери беруться, і ключі `sysctl`, що керують доглядачем за зависаннями. Потрібна вона в момент, коли треба не зрозуміти явище, а прочитати конкретний байт із конкретного файлу — і знати, що він означає, а чого в ньому немає взагалі.

## Два поля, у яких живе стан

Стан тримають **два** різні поля структури задачі, і плутати їх не можна: одне описує живу задачу, друге — ту, що вже вийшла.

| поле `task_struct` | що тримає | зауваги |
|---|---|---|
| `__state` | стан живої задачі: біжить, спить, зупинена, запаркована | так поле зветься з ядра 5.14; до того — просто `state` (перейменування Петера Зейлстри, червень 2021, разом зі зняттям `volatile`) |
| `exit_state` | стан задачі, що вже викликала `exit()`: `EXIT_ZOMBIE` або `EXIT_DEAD` | у живої задачі тут нуль |

Обидва поля — бітові маски, і саме тому стан не зводиться до одного значення з переліку: у полі можуть стояти кілька прапорців одночасно.

| значення | назва | де | що означає |
|---|---|---|---|
| `0x0000` | `TASK_RUNNING` | `__state` | нічого не бракує: задача в черзі готових або вже на ядрі |
| `0x0001` | `TASK_INTERRUPTIBLE` | `__state` | сон, який будить будь-який доправлений сигнал |
| `0x0002` | `TASK_UNINTERRUPTIBLE` | `__state` | сон, якого звичайний сигнал не чіпає |
| `0x0004` | `__TASK_STOPPED` | `__state` | зупинено сигналом зупинки |
| `0x0008` | `__TASK_TRACED` | `__state` | зупинено зневаджувачем |
| `0x0010` | `EXIT_DEAD` | `exit_state` | запис уже забирають, задача дорозбирається |
| `0x0020` | `EXIT_ZOMBIE` | `exit_state` | вийшла, код виходу ще ніхто не забрав |
| `0x0040` | `TASK_PARKED` | `__state` | потік ядра, знятий з роботи через `kthread_park()` |
| `0x0080` | `TASK_DEAD` | `__state` | остання мить перед зникненням задачі |
| `0x0100` | `TASK_WAKEKILL` | `__state` | «мене можна розбудити смертельним сигналом» |
| `0x0200` | `TASK_WAKING` | `__state` | задачу вже будять, перенесення між чергами триває |
| `0x0400` | `TASK_NOLOAD` | `__state` | «не рахувати мене в середньому навантаженні» |
| `0x0800` | `TASK_NEW` | `__state` | задача створена, але ще не пущена в чергу |
| `0x1000` | `TASK_RTLOCK_WAIT` | `__state` | чекання на блокуванні, перетвореному на rt-м'ютекс (режим `PREEMPT_RT`) |
| `0x2000` | `TASK_FREEZABLE` | `__state` | цей сон можна заморозити перед засинанням системи |
| `0x8000` | `TASK_FROZEN` | `__state` | задачу заморожено |

Складені значення, які трапляються в коді ядра частіше за окремі біти:

```c
#define TASK_KILLABLE   (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)   /* 0x0102 */
#define TASK_IDLE       (TASK_UNINTERRUPTIBLE | TASK_NOLOAD)     /* 0x0402 */
#define TASK_STOPPED    (TASK_WAKEKILL | __TASK_STOPPED)         /* 0x0104 */
#define TASK_NORMAL     (TASK_INTERRUPTIBLE | TASK_UNINTERRUPTIBLE)
#define TASK_REPORT     (TASK_RUNNING | TASK_INTERRUPTIBLE | TASK_UNINTERRUPTIBLE | \
                         __TASK_STOPPED | __TASK_TRACED | EXIT_DEAD | EXIT_ZOMBIE | \
                         TASK_PARKED)                            /* 0x007F */
```

## Як біти стають однією літерою

Назовні йде не маска, а один байт. Перетворення робить коротка функція з `include/linux/sched.h`, і в ній варто прочитати кожен рядок — саме вона визначає, чого ви ніколи не побачите:

```c
static inline unsigned int __task_state_index(unsigned int tsk_state,
                                              unsigned int tsk_exit_state)
{
    unsigned int state = (tsk_state | tsk_exit_state) & TASK_REPORT;

    if ((tsk_state & TASK_IDLE) == TASK_IDLE)
        state = TASK_REPORT_IDLE;          /* 0x80 — понад маску */

    if ((tsk_state & TASK_RTLOCK_WAIT) || (tsk_state & TASK_FROZEN))
        state = TASK_UNINTERRUPTIBLE;      /* свідома підміна: показати як D */

    return fls(state);                     /* номер старшого одиничного біта */
}
```

`fls()` (*find last set*) віддає позицію найстаршої одиниці, рахуючи від одиниці, і нуль для нульового аргументу. Отриманий номер — це індекс у масиві рядків із `fs/proc/array.c`:

```c
static const char * const task_state_array[] = {
    /* стани в масці TASK_REPORT: */
    "R (running)",      /* 0x00 */
    "S (sleeping)",     /* 0x01 */
    "D (disk sleep)",   /* 0x02 */
    "T (stopped)",      /* 0x04 */
    "t (tracing stop)", /* 0x08 */
    "X (dead)",         /* 0x10 */
    "Z (zombie)",       /* 0x20 */
    "P (parked)",       /* 0x40 */
    /* стан поза маскою: */
    "I (idle)",         /* 0x80 */
};
```

![Біти поля __state зводяться маскою TASK_REPORT, спецвипадки підмінюються, fls дає індекс у масиві літер](/reference/unix-linux/processes/process-states/img/state-letter-path.svg)

*Усе, що не потрапило в маску, назовні не існує: жодне з полів `/proc` і жоден стовпчик `ps` цих бітів не показують.*

**Умова: задача спить у `TASK_KILLABLE`, `exit_state` дорівнює нулю.**

```
__state       = 0x0102        (TASK_WAKEKILL | TASK_UNINTERRUPTIBLE)
& TASK_REPORT = 0x0102 & 0x007F = 0x0002
fls(0x0002)   = 2
масив[2]      = "D (disk sleep)"
```

Літера — `D`, точно така сама, як у сну, що не вбивається нічим. Те саме роблять спецвипадки: `TASK_RTLOCK_WAIT` і `TASK_FROZEN` показуються як `D` навмисно, щоб не заводити назовні нових станів.

> 🔧 **Навіщо це.** З цієї таблиці випливає межа будь-якої діагностики за літерою: `D` — це чотири різні речі (звичайний непереривний сон, сон із дозволом на смерть, чекання на блокуванні реальночасового ядра, заморожена задача), і жодним полем `/proc` вони не розрізняються. Тому питання «чи вб'ється цей процес» відповіді у виводі не має — його перевіряють лише дією.

Ще дві дрібниці, що випливають із того самого коду. Літеру `X` дає `EXIT_DEAD` із `exit_state`, а не `TASK_DEAD` — останній лежить поза маскою й дав би індекс нуль, тобто `R`. `TASK_NEW` і `TASK_WAKING` теж поза маскою, тому й вони показуються як `R`: задача, яку саме зараз переносять між чергами, назовні виглядає готовою.

## Повний перелік літер

| літера | рядок у `/proc/PID/status` | звідки | що означає |
|---|---|---|---|
| `R` | `R (running)` | індекс 0 | на процесорі **або** в черзі готових — розрізнити неможливо |
| `S` | `S (sleeping)` | `TASK_INTERRUPTIBLE` | сон, який перерве будь-який сигнал |
| `D` | `D (disk sleep)` | `TASK_UNINTERRUPTIBLE` | непереривний сон; сюди ж зведено сон із дозволом на смерть, чекання на rt-м'ютексі й заморожені задачі |
| `T` | `T (stopped)` | `__TASK_STOPPED` | зупинено `SIGSTOP`/`SIGTSTP`, чекає на `SIGCONT` |
| `t` | `t (tracing stop)` | `__TASK_TRACED` | зупинено зневаджувачем; хто саме — у `TracerPid` |
| `X` | `X (dead)` | `EXIT_DEAD` | запис дорозбирають; побачити майже неможливо |
| `Z` | `Z (zombie)` | `EXIT_ZOMBIE` | код виходу чекає на `wait()` від батька |
| `P` | `P (parked)` | `TASK_PARKED` | потік ядра, знятий з роботи; звичайні пробудження його не беруть |
| `I` | `I (idle)` | `TASK_IDLE` | непереривний сон із прапорцем «не рахувати в навантаженні» |

Історичні літери, які трапляються в старих статтях, старих ядрах і досі — у man-сторінці `proc(5)`:

| літера | коли існувала | що означала |
|---|---|---|
| `W` | до 2.6.0 | сторінкова підкачка (окремого стану більше немає) |
| `x` | 2.6.33 – 3.13 | мертва (нині лише `X`) |
| `K` | 2.6.33 – 3.13 | `TASK_WAKEKILL` показувався окремо |
| `W` | 2.6.33 – 3.13 | `TASK_WAKING` показувався окремо |
| `P` | 3.9 – 3.13 | запаркована |

Про `P` варто сказати точніше, бо тут man-сторінка відстала від ядра. У 4.13 масив станів мав рівно сім рядків, а запарковані задачі підмінялися на `TASK_INTERRUPTIBLE` і показувалися як `S` — це видно з коду `get_task_state()` тієї версії. У 4.14 масив уже містить і `P (parked)`, і `I (idle)`: перебудова виводу станів авторства Петера Зейлстри (Peter Zijlstra) внесла `TASK_PARKED` у маску `TASK_REPORT`, пересунувши задля цього номери бітів. Тобто `P` не «лише 3.9–3.13», як каже `proc(5)`, а «3.9–3.13 і знову з 4.14».

## Модифікатори `ps`: звідки береться кожен символ

Перший символ стовпчика `STAT` — це **байт із поля 3** `/proc/PID/stat`, скопійований без жодного перекладу: власного словника станів у `ps` немає, тож будь-яку нову літеру ядра вона покаже сама собою. Решта символів — надбудова самої `ps`, зібрана з інших полів:

```c
/* procps-ng, ps/output.c — уся логіка стовпчика STAT */
static int pr_stat(char *restrict const outbuf, const proc_t *restrict const pp){
    int end = 0;
    outbuf[end++] = pp->state;
    if(pp->nice < 0)            outbuf[end++] = '<';
    if(pp->nice > 0)            outbuf[end++] = 'N';
    if(pp->vm_lock)             outbuf[end++] = 'L';
    if(pp->session == pp->tgid) outbuf[end++] = 's';
    if(pp->nlwp > 1)            outbuf[end++] = 'l';
    if(pp->pgrp == pp->tpgid)   outbuf[end++] = '+';
    outbuf[end] = '\0';
    return end;
}
```

| символ | умова | звідки взято число |
|---|---|---|
| `<` | `nice < 0` — підвищений пріоритет | поле 19 `/proc/PID/stat` |
| `N` | `nice > 0` — знижений пріоритет | поле 19 |
| `L` | є сторінки, замкнені в пам'яті | `VmLck` у `/proc/PID/status` |
| `s` | лідер сеансу | поле 6 (`session`) дорівнює номеру процесу |
| `l` | багатопотоковий | поле 20 (`num_threads`) більше за одиницю |
| `+` | у групі переднього плану термінала | поле 5 (`pgrp`) дорівнює полю 8 (`tpgid`) |

Пастка тут одна, зате поширена: `<` **не означає реального часу**. Це виключно `nice`, тож задача з політикою `SCHED_FIFO` і нульовим `nice` не отримає жодного модифікатора. Клас планування показують окремі стовпчики `cls` і `rtprio`.

| що потрібно | команда |
|---|---|
| літера без модифікаторів | `ps -eo pid,s,comm` (`s` — синонім `state`) |
| літера з модифікаторами | `ps -eo pid,stat,comm` |
| літера, місце сну й команда | `ps -eo pid,stat,wchan:32,comm --sort=-stat` |
| рядок на кожен **потік** | `ps -eLo pid,tid,stat,wchan:24,comm` |
| потоки одного процесу | `ps -L -p 2431 -o tid,stat,wchan:24,comm` |
| те саме в `top` | стовпчик `S`; `top -H` — по потоках |

Швидкий перепис станів по всій системі — суфікс `=` прибирає заголовок стовпчика, `cut` лишає саму літеру без модифікаторів:

```sh
ps -eo stat= | cut -c1 | sort | uniq -c | sort -rn
```

Форми з `-L` і `-H` у цьому переліку не косметика: за замовчуванням `ps` дає один рядок на процес і зводить стани всіх потоків до одного, «найактивнішого». Процес, у якому один потік намертво стоїть у `D`, а решта сплять, показується як `S` ([потоки як задачі](book:unix-linux/threads-as-tasks) — стан лежить у задачі, і в процесу з двадцятьма потоками є двадцять станів, а не один).

## Поля `/proc/PID/stat`

Файл — один довгий рядок чисел, розділених пробілами. Нумерація полів нижче — та, якою користується `proc(5)`; наведено лише те, що стосується стану.

| № | поле | що з нього видно |
|---|---|---|
| 1 | `pid` | номер задачі (у теці `task/` — номер потоку) |
| 2 | `comm` | ім'я програми **в круглих дужках** |
| 3 | `state` | та сама літера, один байт |
| 4 | `ppid` | батько |
| 5 | `pgrp` | група процесів — потрібна для модифікатора `+` |
| 6 | `session` | сеанс — потрібен для модифікатора `s` |
| 8 | `tpgid` | група переднього плану термінала — друга половина `+` |
| 19 | `nice` | джерело `<` і `N` |
| 20 | `num_threads` | джерело `l`; нуль потоків тут не буває |
| 35 | `wchan` | **не адреса**, а прапорець 0/1 |
| 39 | `processor` | номер ядра, на якому задача виконувалася востаннє |
| 40, 41 | `rt_priority`, `policy` | реальночасовий пріоритет і клас планування |
| 42 | `delayacct_blkio_ticks` | скільки тиків задача сумарно простояла на блоковому вводі-виводі |
| 52 | `exit_code` | код виходу — для `Z` єдина причина, чому запис ще існує |

Три речі, на яких найчастіше спотикаються.

**Поле 35 більше не адреса.** Колись воно віддавало адресу функції ядра, у якій задача спить, але це витік розкладки ядра, тож у коді тепер стоїть коментар «ми показуємо прапорець 0/1, щоб просто сказати простору користувача, чи є що читати в `/proc/PID/wchan`». Ім'я функції беруть звідти, а не звідси.

**Поле 42 мовчить, поки вимкнено облік затримок.** Із ядра 5.14 підсистема обліку затримок вимкнена типово; вмикають її ключем `kernel.task_delayacct` або параметром завантаження `delayacct`. Причому лічильники заводяться в момент створення задачі — тож після ввімкнення на ходу цифри з'являться лише в тих задач, що народилися **після** нього.

**Розбирати рядок пробілами з початку не можна.** Поле 2 — це ім'я в дужках, і воно містить те, що процес собі виставив: там бувають і пробіли, і сама дужка. Єдиний надійний спосіб — знайти **останню** `)` у рядку; літера стану стоїть рівно через один пробіл після неї.

## Поля `/proc/PID/status`

Той самий стан у придатному для читання вигляді плюс сусідні поля, без яких літера часто нічого не пояснює.

| рядок | що показує |
|---|---|
| `State:` | повний рядок з масиву, наприклад `D (disk sleep)` |
| `Threads:` | скільки потоків у процесі |
| `TracerPid:` | хто трасує задачу; для стану `t` — єдина відповідь на «хто її тримає» ([ptrace](book:unix-linux/ptrace-model) — підсистема, крізь яку один процес дістає контроль над іншим) |
| `SigPnd:` | недоправлені сигнали **цього потоку**, шістнадцяткова маска |
| `ShdPnd:` | недоправлені сигнали, спільні для всього процесу |
| `SigBlk:`, `SigIgn:`, `SigCgt:` | заблоковані, зігноровані, перехоплені |
| `voluntary_ctxt_switches:` | скільки разів задача сходила з процесора сама |
| `nonvoluntary_ctxt_switches:` | скільки разів її зняли |

Маски сигналів читають побітово: сигнал із номером *N* займає біт *N−1* ([сигнал](book:unix-linux/signal-model) — асинхронне сповіщення; недоправлені лежать у процеса в окремому наборі, поки він їх не прийме).

**Умова: у `/proc/2431/status` стоїть `State: D (disk sleep)` і `ShdPnd: 0000000000000100`.**

```
маска         = 0x0000000000000100
номер біта    = log₂(0x100) = 8
номер сигналу = 8 + 1 = 9
сигнал 9      = SIGKILL
```

Отже, `kill -9` уже надіслано, він лежить недоправлений, а задача досі в `D` — рівно та картина, за якою впізнають застрягання, не пробуючи вбити процес удруге.

Остання пара лічильників — саме те, на що дивиться доглядач за зависаннями: якщо їхня сума за весь інтервал не змінилася, задача не сходила з процесора й не поверталася жодного разу, тобто справді простояла все це в одному сні.

## Де саме задача спить

| файл | що віддає | доступ |
|---|---|---|
| `/proc/PID/wchan` | символьне ім'я функції ядра, у якій задача викликала `schedule()`; `0` — якщо задача біжить, символ не знайдено **або** немає прав | режим `PTRACE_MODE_READ_FSCREDS` |
| `/proc/PID/stack` | стек ядра задачі — найточніша вказівка на підсистему, що не відпускає | лише привілейований; потрібне ядро з `CONFIG_STACKTRACE` |
| `/proc/PID/syscall` | номер поточного системного виклику, його аргументи, вказівники стека й інструкції; рядок `running`, якщо задача на процесорі | режим `PTRACE_MODE_ATTACH_FSCREDS` |
| `/proc/PID/task/TID/…` | те саме окремо для кожного потоку | так само |

Нуль у `wchan` неоднозначний навмисно: за ним не відрізнити «задача біжить» від «вам не дозволено читати». Тому там, де стан `D`, а стовпчик `wchan` порожній, першою перевіряють не підсистему, а власні права: під тим самим користувачем, під яким запущено процес, або під `root` те саме читання зазвичай дає ім'я функції.

## Лічильники по всій системі

| джерело | що рахує | чого **не** рахує |
|---|---|---|
| `/proc/stat`, рядок `procs_running` | скільки задач зараз готові (`nr_running()`) | нічого зі сплячих |
| `/proc/stat`, рядок `procs_blocked` | скільки задач заснуло саме через `io_schedule()` (`nr_iowait()`) | `D` на м'ютексі, на сторінці чи в драйвері сюди не потрапляє |
| `/proc/loadavg`, перші три числа | середні за 1, 5 і 15 хвилин від суми «готові + непереривний сон» | задачі з `TASK_NOLOAD`, тобто всі з літерою `I` |
| `/proc/loadavg`, четверте поле виду `2/1234` | ліворуч — скільки задач зараз готові, праворуч — скільки всього існує | ліва половина не містить `D`, на відміну від самих середніх |
| `/proc/pressure/io`, `/proc/pressure/cpu` | частку часу, коли на ресурс справді чекали | працює лише на ядрах із увімкненим PSI |

Різниця між третім і четвертим рядками цієї таблиці — джерело вічної плутанини: у тому самому файлі ліве число четвертого поля рахує лише `R`, а три середні — ще й `D` ([середнє навантаження й тиск на ресурси](book:unix-linux/load-and-pressure) — що саме входить у ці числа й на які питання вони відповідають).

## Ключі `sysctl`

Доглядач за зависаннями — окремий потік ядра `khungtaskd`, який періодично обходить задачі. Хто саме потрапляє під його погляд, видно з однієї умови в `kernel/hung_task.c`:

```c
/* пропустити переривний сон, «сон із дозволом на смерть»,
   простій і заморожені задачі */
if (!(state & TASK_UNINTERRUPTIBLE) ||
    (state & (TASK_WAKEKILL | TASK_NOLOAD | TASK_FROZEN)))
        return false;
```

Тобто сон із дозволом на смерть, попри ту саму літеру `D`, доглядач свідомо не рахує зависанням: така задача не безнадійна, бо `SIGKILL` її виведе.

| ключ | типове значення | що робить |
|---|---|---|
| `kernel.hung_task_timeout_secs` | `CONFIG_DEFAULT_HUNG_TASK_TIMEOUT`, у більшості дистрибутивів 120 | скільки секунд у непереривному сні без жодного перемикання контексту вважати зависанням; `0` вимикає перевірку |
| `kernel.hung_task_check_interval_secs` | `0` | як часто робити обхід; `0` означає «раз на `timeout`» |
| `kernel.hung_task_warnings` | `10` | скільки повідомлень надрукувати всього; `-1` — без обмеження |
| `kernel.hung_task_check_count` | `PID_MAX_LIMIT` | скільки задач перевіряти за один обхід |
| `kernel.hung_task_panic` | `0` | скільки зависань за один обхід валять ядро в паніку; `1` — класична поведінка «перше ж зависання» |
| `kernel.hung_task_all_cpu_backtrace` | `0` | `1` — розіслати немаскований переривник на всі ядра й зібрати стек із кожного |
| `kernel.hung_task_detect_count` | лічильник | скільки зависань виявлено від завантаження; запис `0` скидає |
| `kernel.task_delayacct` | `0` (з ядра 5.14) | вмикає облік затримок: без нього мовчать поле 42 і всі програми на кшталт `iotop` |
| `kernel.sysrq` | залежить від дистрибутива | бітова маска дозволів для клавіатурного SysRq (біт `0x8` — дампи процесів) |

Повідомлення доглядача виглядає так і завжди супроводжується стеком ядра:

```
INFO: task dd:2431 blocked for more than 120 seconds.
      Tainted: G           OE     6.8.0-generic #1
"echo 0 > /proc/sys/kernel/hung_task_timeout_secs" disables this message.
```

Ту саму вибірку можна взяти на вимогу, не чекаючи порога:

```sh
echo w > /proc/sysrq-trigger    # стеки всіх задач у непереривному сні
echo t > /proc/sysrq-trigger    # стеки геть усіх задач
dmesg -T | tail -40             # читати результат
```

Значення `kernel.sysrq` на це не впливає: маска обмежує лише виклик із клавіатури, а запис у `/proc/sysrq-trigger` привілейованому користувачеві дозволено завжди.

## Мінімальний робочий виклик

Прочитати літеру стану й місце сну для **кожного** потоку процесу — саме те, чого не дає типовий вивід `ps`. Ключова деталь обох варіантів однакова: поле 3 шукають від останньої дужки, а не з початку рядка ([procfs](book:unix-linux/proc-filesystem) — файли, що читаються як звичайні, але породжуються ядром у момент читання, тому жодного кешування тут немає).

:::tabs
```c
#define _GNU_SOURCE
#include <dirent.h>
#include <stdio.h>
#include <string.h>

/* Читає перший рядок файлу; повертає довжину або -1. */
static int read_line(const char *path, char *buf, size_t cap)
{
    FILE *f = fopen(path, "re");
    if (!f)
        return -1;
    size_t n = fread(buf, 1, cap - 1, f);
    fclose(f);
    buf[n] = '\0';
    buf[strcspn(buf, "\n")] = '\0';
    return (int)n;
}

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "вжиток: %s <pid>\n", argv[0]);
        return 2;
    }

    char dir[64], path[160], buf[4096], wchan[128];
    snprintf(dir, sizeof dir, "/proc/%s/task", argv[1]);

    DIR *d = opendir(dir);
    if (!d) {
        perror(dir);
        return 1;
    }

    for (struct dirent *e; (e = readdir(d)) != NULL; ) {
        if (e->d_name[0] == '.')
            continue;

        snprintf(path, sizeof path, "%s/%s/stat", dir, e->d_name);
        if (read_line(path, buf, sizeof buf) <= 0)
            continue;                      /* потік вийшов, поки ми читали */

        char *p = strrchr(buf, ')');       /* кінець поля 2 — ОСТАННЯ дужка */
        if (!p || p[1] != ' ')
            continue;
        char state = p[2];                 /* поле 3 — рівно один байт */

        snprintf(path, sizeof path, "%s/%s/wchan", dir, e->d_name);
        if (read_line(path, wchan, sizeof wchan) <= 0)
            strcpy(wchan, "0");            /* «0» = біжить або немає прав */

        printf("%-7s %c  %s\n", e->d_name, state, wchan);
    }

    closedir(d);
    return 0;
}
```
```python
#!/usr/bin/env python3
"""Літера стану й місце сну для кожного потоку процесу."""
import pathlib
import sys

pid = sys.argv[1]

for task in sorted(pathlib.Path(f"/proc/{pid}/task").iterdir(), key=lambda p: int(p.name)):
    try:
        stat = (task / "stat").read_text()
        # поле 2 — ім'я в дужках, у ньому бувають пробіли й ')',
        # тому відлік починаємо від ОСТАННЬОЇ дужки
        state = stat[stat.rindex(")") + 2]
        wchan = (task / "wchan").read_text().strip()   # «0» = біжить або немає прав
    except (FileNotFoundError, ProcessLookupError, PermissionError):
        continue                                        # потік уже вийшов
    print(f"{task.name:<7} {state}  {wchan}")
```
:::

Обидва варіанти віддають **знімок**, а не вимір: між двома читаннями стан міняється тисячі разів, і побачити в `D` задачу, яка проводить там частку відсотка часу, — звичайна річ. Питання «скільки часу задача насправді простояла» цими файлами не закривається взагалі: на нього відповідають поле 42 `/proc/PID/stat`, облік затримок і лічильники тиску на ресурси — і кожен із них треба спершу ввімкнути.
