# 📋 DBus-інтерфейс org.freedesktop.systemd1: специфікація контрактів

Цей довідник містить детальний опис системного контракту DBus, який надається менеджером `systemd` (PID 1) для динамічного управління cgroups, юнітами та обмеженнями ресурсів у системі Linux.

## Загальна архітектура та шина зв'язку

Менеджер системи `systemd` виступає в ролі активного сервера системної шини повідомлень DBus (System Bus). Обмін даними здійснюється через доменний сокет Unix `/run/dbus/system_bus_socket` або приватний сокет `/run/systemd/private`.

- **Сервіс призначення (Destination Service)**: `org.freedesktop.systemd1`
- **Головний шлях об'єкта (Object Path)**: `/org/freedesktop/systemd1`
- **Основний інтерфейс**: `org.freedesktop.systemd1.Manager`

Для кожного окремого юніта systemd створює динамічний об'єкт за шляхом `/org/freedesktop/systemd1/unit/<unit_id>`, де спеціальні символи в назві юніта кодуються шістнадцятковим кодом ASCII (наприклад, крапка перетворюється на `_2e`, дефіс у зрізах на `_2d`).

### Аутентифікація та авторизація (Polkit)

Кожен виклик методів через DBus проходить перевірку прав доступу на основі сокетних облікових даних Unix (`SO_PEERCRED` / `sd_bus_get_name_creds`). Якщо запит надходить від безпривілейованого користувача (UID ≠ 0), systemd ініціалізує запит до демона `Polkit` через дію `org.freedesktop.systemd1.manage-units`. Якщо авторизацію відхилено, метод повертає помилку `SD_BUS_ERROR_ACCESS_DENIED`.

## Маппінг типів DBus та упакування `a(sv)`

Система DBus використовує сувору статичну типізацію повідомлень. При передачі налаштувань ресурсів cgroups використовується складний тип **`a(sv)`** — масив (`a`) кортежів-структур (`(...)`), що складаються з двох елементів:
1. Рядка назви властивості (`s` — string);
2. Варіанта (`v` — variant), який містить внутрішній маркер типу DBus та безпосередньо значення.

Низькорівневе маршалювання (серіалізація) цього типу вимагає покрокового відкриття контейнерів структури `'r'` (struct) та варіанта `'v'` (variant) перед записом байтів значення.

### Символи типів даних DBus:
- `'s'` — string (рядок UTF-8 із завершальним нульовим байтом);
- `'u'` — uint32 (32-бітне ціле без знаку, 4 байти);
- `'t'` — uint64 (64-бітне ціле без знаку, 8 байт);
- `'b'` — boolean (булеве значення, 4 байти: 0 або 1);
- `'au'` — array of uint32 (масив 32-бітних цілих чисел, наприклад, список PID);
- `'as'` — array of strings (масив рядків UTF-8).

## Специфікація методів інтерфейсу `Manager`

### 1. `StartTransientUnit`

Створює та негайно запускає тимчасовий юніт (Transient Unit) — службу або область (Scope) — із заданими параметрами та лімітами cgroups без створення конфігураційного файлу `.service` чи `.scope` на фізичному диску.

**Сигнатура методу**:
```
StartTransientUnit(s name, s mode, a(sv) properties, a(sa(sv)) aux) -> (o job)
```

**Детальний розбір параметрів**:
- `name` (`s`): Унікальне ім'я юніта в системі. Повинне містити суфікс `.service` або `.scope` (наприклад, `my-worker.service` або `session-10.scope`).
- `mode` (`s`): Режим розв'язання конфліктів у черзі завдань systemd. Допустимі значення:
  - `"replace"` — зупинити поточні завдання для цього юніта та замінити їх новим;
  - `"fail"` — повернути помилку, якщо для юніта вже існує активне завдання;
  - `"isolate"` — зупинити всі інші служби в системі, крім вказаної (використовується для зміни цілей/target);
  - `"ignore-dependencies"` — ігнорувати оголошені залежності юніта при запуску;
  - `"ignore-requirements"` — ігнорувати вимоги `Requires=` та `Requisite=`.
- `properties` (`a(sv)`): Масив налаштувань юніта та лімітів cgroups v2 (див. таблицю нижче).
- `aux` (`a(sa(sv))`): Масив додаткових прихованих юнітів (структура `a(sa(sv))`, де `s` — назва юніта, `a(sv)` — масив його властивостей), які створюються менеджером systemd атомарно в єдиній транзакції разом із головним юнітом (якщо додаткових юнітів немає, передається порожній масив `[]`).

**Значення повернення**:
- `job` (`o`): Шлях до об'єкта завдання в DBus (наприклад, `/org/freedesktop/systemd1/job/412`), який дозволяє асинхронно відстежувати процес запуску.

### 2. `StopUnit`

Зупиняє активний юніт і примусово завершує всі процеси у його cgroup.

**Сигнатура методу**:
```
StopUnit(s name, s mode) -> (o job)
```

- `name` (`s`): Назва юніта для зупинки.
- `mode` (`s`): Режим заміни завдань (`"replace"` або `"fail"`).

### 3. `SetUnitProperties`

Динамічно змінює конфігураційні параметри та обмеження cgroups для вже запущеного юніта без його перезапуску чи зупинки процесів.

**Сигнатура методу**:
```
SetUnitProperties(s name, b runtime, a(sv) properties) -> ()
```

- `name` (`s`): Назва юніта.
- `runtime` (`b`): Прапор збереження змін:
  - `1` (`true`) — зміни лягають файлом-доповненням у тимчасову файлову систему (`/run/systemd/system.control/<юніт>.d/`) і діють до перезапуску системи;
  - `0` (`false`) — зміни записуються на диск у каталог `/etc/systemd/system.control/` і зберігаються між перезавантаженнями.
- `properties` (`a(sv)`): Масив нових властивостей для застосування.

### 4. `ResetFailedUnit`

Скидає аварійний стан юніта (стан `failed`), дозволяючи повторний запуск після системних збоїв або перевищення ліміту `MemoryMax`.

**Сигнатура методу**:
```
ResetFailedUnit(s name) -> ()
```

### 5. `AbandonScope`

Свідчить systemd про те, що процес-ініціатор більше не керує вказаним Scope. systemd залишає процеси у cgroup, але перестає вважати відсутність активності помилкою.

**Сигнатура методу**:
```
AbandonScope(s name) -> ()
```

## Таблиця властивостей масиву `properties` (`a(sv)`)

У таблиці нижче наведено повний перелік конфігураційних ключів, які транслюються systemd у відповідні атрибути файлової системи cgroups v2:

| Назва властивості | Тип DBus | Базове значення | Атрибут cgroups v2 | Повний опис механізму та поведінки |
| :--- | :--- | :--- | :--- | :--- |
| `PIDs` | `au` | порожній | `cgroup.procs` | Масив 32-бітних PID процесів, які прикріплюються до створюваного Scope (використовується лише для `.scope`). |
| `MemoryMax` | `t` | `UINT64_MAX` | `memory.max` | Жорсткий ліміт оперативної пам'яті в байтах. При перевищенні викликається OOM-killer. |
| `MemoryHigh` | `t` | `UINT64_MAX` | `memory.high` | М'який ліміт пам'яті в байтах. При перевищенні ядро примусово сповільнює процеси групи (throttling). |
| `MemoryLow` | `t` | `0` | `memory.low` | М'який захист пам'яті в байтах від вивантаження на диск (reclaim). |
| `MemoryMin` | `t` | `0` | `memory.min` | Жорстка гарантія пам'яті в байтах. Ядро ніколи не відбирає цю пам'ять. |
| `CPUWeight` | `t` | `100` | `cpu.weight` | Пропорційна вага розподілу процесорного часу від 1 до 10000. |
| `CPUQuotaPerSecUSec` | `t` | `UINT64_MAX` | `cpu.max` | Квота CPU в мікросекундах на секунду (100000 us = 100% = 1 CPU core). |
| `IOWeight` | `t` | `100` | `io.weight` | Пропорційна вага блокового вводу-виводу для планувальника BFQ (1..10000). |
| `TasksMax` | `t` | за замовч. | `pids.max` | Максимально дозволена кількість задач (процесів і потоків) у cgroup. |
| `Delegate` | `b` | `0` | `cgroup.subtree_control` | Прапор делегування cgroup (`1` дозволяє стороннім рушіям створювати підгрупи). |
| `DelegateControllers` | `as` | порожній | `cgroup.subtree_control` | Список назв дозволених делегованих контролерів (наприклад, `["cpu", "memory", "pids"]`). У unit-файлі той самий перелік записується як `Delegate=cpu memory pids`. |
| `OOMPolicy` | `s` | `"stop"` | `memory.oom.group` | Політика реакції на OOM: `"stop"` (зупинка юніта), `"kill"` (знищення всіх процесів групи), `"continue"`. |

## Специфікація сигналів Manager

### 1. `JobRemoved`

Менеджер systemd надсилає цей сигнал, коли завдання запуску або зупинки юніта завершує своє виконання.

**Сигнатура**:
```
JobRemoved(u id, o job, s unit, s result)
```

- `id` (`u`): Числовий ідентифікатор завдання;
- `job` (`o`): Шлях до об'єкта завдання DBus;
- `unit` (`s`): Текстова назва юніта;
- `result` (`s`): Текстовий результат виконання:
  - `"done"` — запуск або зупинку успішно завершено;
  - `"failed"` — під час запуску сталася помилка (наприклад, процес повернув ненульовий код);
  - `"canceled"` — завдання скасовано іншим викликом;
  - `"timeout"` — час виконання завдання перевищив `TimeoutStartSec`.

### 2. `UnitNew`

Надсилається в момент створення нового юніта в системі (включно зі створенням відповідної cgroup).

**Сигнатура**:
```
UnitNew(s id, o unit)
```

- `id` (`s`): Ідентифікатор юніта;
- `unit` (`o`): Об'єктний шлях юніта в DBus.

### 3. `UnitRemoved`

Надсилається при вилученні юніта з пам'яті systemd та видаленні його cgroup з VFS.

**Сигнатура**:
```
UnitRemoved(s id, o unit)
```

## Коди помилок `sd_bus_error`

При відхиленні викликів методів DBus повернута структура помилки містить наступні стандартні константи systemd:

- `org.freedesktop.systemd1.NoSuchUnit` — вказаний юніт не існує в пам'яті менеджера.
- `org.freedesktop.systemd1.UnitExists` — спроба створити transient unit із назвою, яка вже зайнята іншим юнітом.
- `org.freedesktop.systemd1.UnitMasked` — юніт замасковано (`masked`), його запуск заборонено.
- `org.freedesktop.systemd1.BadUnitSetting` — у масиві `properties` передано невідому назву властивості або неприпустиме для неї значення.
- `org.freedesktop.systemd1.JobTypeNotApplicable` — тип завдання не застосовний до цього юніта у його поточному стані.
- `org.freedesktop.systemd1.TransactionIsDestructive` — запуск завдання призведе до скасування критичних системних юнітів.
