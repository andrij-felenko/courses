# Послідовні замки: як читати без блокування письменників

- [Атомарні операції](book:unix-linux/atomic-ops) — операції, що виконуються як єдине ціле.
- [Бар'єри пам'яті](book:unix-linux/memory-barriers) — впорядкування доступу до пам'яті для багатоядерних систем.
</preknowlist>

Коли ми працюємо з даними, які дуже часто читаються, але рідко змінюються, використання звичайних блокувань (наприклад, спінлоків) може стати вузьким місцем. Якщо безліч читачів постійно захоплюють блокування для читання (`read_lock`), письменник може опинитися в стані голодування (starvation), не маючи змоги оновити дані. З іншого боку, якщо письменнику надати абсолютний пріоритет, це може призупинити всіх читачів, навіть якщо оновлення триватиме дуже короткий час. 

Саме для вирішення цієї проблеми в ядрі Linux було введено механізм **seqlock** (послідовний замок, від англ. *sequence lock*). Він дозволяє читачам читати дані без використання блокувань, перевіряючи лише спеціальний лічильник послідовності. Це означає, що читачі ніколи не блокують письменників.

## Проблема: голодування письменників

Уявіть собі системний годинник (наприклад, лічильник `jiffies`), який постійно оновлюється під час кожного переривання таймера, і водночас сотні або тисячі процесів постійно запитують поточний час. Якщо використовувати звичайний замок `rwlock` (read-write lock), кожен процес-читач буде брати замок на читання. Оскільки читачів дуже багато, замок майже ніколи не буде повністю вільним. Коли таймерному перериванню (письменнику) знадобиться оновити годинник, воно може довго чекати, поки всі читачі звільнять замок. Це призведе до затримки в оновленні часу та можливої розсинхронізації.

Seqlock розв'язує цю проблему радикально: письменник просто **нікого не чекає** (крім інших письменників). Він починає писати, коли йому потрібно. А от читач після прочитання перевіряє, чи не змінилися дані під час його читання.

## Як працює seqlock

Структура `seqlock_t` містить дві основні речі:
1. Звичайний **спінлок** для синхронізації між самими письменниками (щоб два письменники не писали одночасно).
2. **Лічильник послідовності** (sequence counter). 

Лічильник послідовності — це парне число, коли замок вільний від запису, і непарне, коли відбувається запис. 

### Алгоритм письменника

Коли письменник хоче оновити дані:
1. Він захоплює спінлок (щоб відсікти інших письменників).
2. Він збільшує лічильник послідовності на 1 (тепер він стає непарним).
3. Виконує запис даних.
4. Знову збільшує лічильник послідовності на 1 (тепер він знову парний).
5. Звільняє спінлок.

Ці кроки в ядрі реалізуються функціями `write_seqlock()` та `write_sequnlock()`. Оскільки лічильник стає непарним під час запису, читачі можуть легко дізнатися, що запис триває.

### Алгоритм читача

Читач ніколи не блокує нічого. Його дії виглядають так:
1. Прочитати поточне значення лічильника (це робить `read_seqbegin()`). Якщо лічильник непарний, значить запис уже йде — читач просто чекає (через цикл), поки він не стане парним.
2. Прочитати самі дані.
3. Прочитати лічильник ще раз (це робить `read_seqretry()`). Якщо поточне значення відрізняється від того, яке було на кроці 1, це означає, що письменник змінив дані прямо під час нашого читання. У такому разі прочитані дані можуть бути некоректними (пошкодженими), і читач мусить **повторити всю процедуру з кроку 1**.

Цей цикл називається оптимістичним читанням. Ми припускаємо (оптимістично), що встигнемо прочитати дані без втручання письменника. Оскільки запис відбувається рідко, у 99% випадків читач проходить цикл з першої спроби, взагалі не використовуючи атомарних інструкцій чи бар'єрів запису, що робить цей процес надзвичайно швидким на багатоядерних системах.

## Коли варто використовувати seqlock?

Seqlock — це не універсальний інструмент. Його використання виправдане лише тоді, коли збігаються кілька умов:
- **Дані малі та швидко читаються/пишуться.** Читач повинен встигати прочитати дані до того, як письменник встигне їх змінити, інакше він зависне в нескінченному циклі повторних читань.
- **Читань значно більше, ніж записів.** Якщо записів багато, читачі будуть постійно провалювати `read_seqretry()` і витрачати процесорний час на марні повтори.
- **Дані не містять вказівників, які можуть бути звільнені.** Це дуже важливе правило. Оскільки читач читає дані без блокування, письменник може оновити вказівник і звільнити стару пам'ять, тоді як читач якраз намагається перейти за цим старим вказівником. Це призведе до паніки ядра. Тому seqlocks ідеально підходять для структур із простими типами (цілі числа, масиви фіксованого розміру), наприклад, для представлення часу.

## Приклад: оновлення часу (jiffies)

Найвідоміший приклад використання seqlocks у ядрі Linux — це захист системного часу. Змінна `jiffies_64`, яка зберігає кількість тиків таймера з моменту завантаження, на 32-бітних системах потребує двох 32-бітних операцій для читання, тому читання може бути розірване записом. Seqlock (`jiffies_lock`) гарантує цілісність цього читання.

Розглянемо, як це виглядає в коді. Уявимо, що ми хочемо прочитати поточне значення 64-бітного лічильника тиків:

````
```c
/* Читання (Простір ядра, C) */
u64 get_jiffies_64(void)
{
    unsigned int seq;
    u64 ret;

    do {
        /* Початок спроби читання. Повертає поточний номер послідовності */
        seq = read_seqbegin(&jiffies_lock);
        
        /* Читаємо самі дані. Важливо, щоб тут не було ніяких вказівників */
        ret = jiffies_64;
        
        /* Перевіряємо, чи не змінилися дані під час нашого читання.
           Якщо змінилися (read_seqretry поверне true), цикл повториться. */
    } while (read_seqretry(&jiffies_lock, seq));

    return ret;
}
```
````

Зверніть увагу, як елегантно вирішується проблема: читач `get_jiffies_64()` просто крутиться в циклі `do-while`, поки не отримає консистентний зріз даних. Йому не треба блокувати письменника. А обробник переривання `do_timer()` просто оновлює час з мінімальними затримками, використовуючи `write_seqlock()`.

## Підводні камені та особливості

Хоча ідея виглядає простою, реалізація вимагає обережності, особливо на архітектурах із слабким впорядкуванням пам'яті (weak memory ordering), таких як ARM або PowerPC.
Функції `read_seqbegin()` та `read_seqretry()` містять спеціальні бар'єри пам'яті (`smp_rmb()`), які гарантують, що процесор не переупорядкує читання самих даних і читання лічильника послідовності. Якби бар'єрів не було, процесор міг би оптимізувати виконання і спочатку прочитати лічильник у `read_seqretry()`, а вже потім прочитати дані. Це повністю зламало б логіку перевірки.

Крім того, варто пам'ятати про переривання. Якщо читач перерветься надовго, він майже напевно змушений буде повторити цикл після повернення, оскільки за час його відсутності письменник, імовірно, встигне змінити дані. Проте це безпечно — дані завжди залишатимуться консистентними.

> 🔧 **Навіщо це.** Seqlocks використовуються в ядрі скрізь, де є короткі, часті читання і рідкісні записи простих структур даних (без вказівників). Найвідоміші місця — це системний час (jiffies_64, vDSO), кеш маршрутизації мережі та параметри файлових систем.
