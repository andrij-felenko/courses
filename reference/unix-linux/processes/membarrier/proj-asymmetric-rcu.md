# ⚙️ Асиметричний RCU на membarrier: сто рядків робочого коду

Тут зібрано маленьку бібліотеку, у якій читач заходить у критичну секцію двома звичайними записами в пам'ять — без жодної атомарної операції й без жодного апаратного бар'єра, — а всю ціну впорядкування платить письменник, по два системні виклики на кожну заміну структури. Задача класична для [read-copy-update](book:programming/read-copy-update): таблицю читають мільйони разів на секунду, підмінюють раз на секунду, і хтось мусить сказати письменникові, коли стара копія вже нікому не потрібна.

## Слово стану: чому число, а не біт

Почнімо з найпростішого, що спадає на думку: у кожного читача власний прапорець «я всередині». Письменник публікує нову таблицю, робить `membarrier`, а потім чекає, доки в кожного читача побачить нуль.

Це безпечно. Прапорець читача, виставлений до його точки впорядкування, письменник після повернення з виклику точно побачить — тож нуль означає, що на момент точки читач був зовні. А будь-яку секцію, яку той почне пізніше, він відкриє вже після своєї точки — і побачить нову таблицю, бо публікацію письменник зробив до виклику.

Небезпеки немає, а от чекати можна нескінченно. Потік, що входить і виходить десять мільйонів разів на секунду, поза секцією перебуває мізерну частку часу; письменник, опитуючи його ззовні, може мільйони разів поспіль натрапляти на одиницю, хоча читач за цей час устиг зайти й вийти безліч разів і давно тримає нову таблицю. Одного біта бракує не для правильності, а для завершення.

Полагодити це можна одним рухом: питати не «ти зараз усередині?», а «ти заходив уже після мене?». Друге питання потребує числа. Заводимо глобальний лічильник поколінь `gp`; читач на **зовнішньому** вході знімає з нього копію й кладе у власне слово. Глибина вкладеності живе в тому ж слові — у семи молодших бітах (`liburcu` теж бере сім, тобто до 127 рівнів; глибше не буває навіть у найзаплутанішому коді).

![Слово стану читача складається з покоління і глибини; письменник дивиться на обидва поля й вирішує, чи можна звільняти](/reference/unix-linux/processes/membarrier/img/reader-word.svg)

*Три випадки: не в секції — вільно; свіже покоління — вільно; старе покоління з ненульовою глибиною — чекаємо.*

## Гарячий бік

```c
#define NEST_MASK  0x7fUL              /* сім молодших бітів — глибина */
#define GEN_STEP   0x80UL              /* крок покоління — перший біт над нею */

struct reader {
    _Alignas(64) unsigned long ctr;    /* покоління | глибина */
    struct reader *next;
};

static unsigned long gp;               /* покоління; піднімає лише письменник */
static struct reader *registry;
static __thread struct reader *self;

static inline void rcu_read_lock(void)
{
    unsigned long v = self->ctr;                       /* слово своє — гонок нема */
    if ((v & NEST_MASK) == 0)
        v = __atomic_load_n(&gp, __ATOMIC_RELAXED) | 1;  /* зовнішній вхід */
    else
        v = v + 1;                                     /* вкладений — лише глибина */
    __atomic_store_n(&self->ctr, v, __ATOMIC_RELAXED);
    __atomic_signal_fence(__ATOMIC_SEQ_CST);           /* бар'єр компілятора */
}

static inline void rcu_read_unlock(void)
{
    unsigned long v = __atomic_load_n(&self->ctr, __ATOMIC_RELAXED);
    __atomic_signal_fence(__ATOMIC_SEQ_CST);
    __atomic_store_n(&self->ctr, v - 1, __ATOMIC_RELAXED);
}

#define rcu_dereference(p) __atomic_load_n(&(p), __ATOMIC_RELAXED)
```

У згенерованому машинному коді від `__atomic_signal_fence` не лишається жодної інструкції: це бар'єр між потоком і його ж обробником сигналу, тобто рівно заборона оптимізаторові переставляти доступи через цю точку. Дармовий — і водночас незамінний, бо це найтонше місце всієї схеми. Компілятор бачить три незалежні об'єкти (`gp`, `self->ctr`, `table`) і має цілковите право прочитати `table` до запису в `ctr`, а в циклі — ще й підняти читання `table` у регістр над усім циклом. Тоді читач мільйон ітерацій поспіль працюватиме зі вказівником, який давно звільнено, і жоден бар'єр у чужому потоці цього не виправить: потрібної інструкції просто немає в програмі. Апаратне переставляння письменник вибиває щоразу заново, а переставляння компілятора вкарбоване в код назавжди.

Розслаблене читання `rcu_dereference` теж не випадкове: `p->field` залежить від адреси, узятої з `p`, а таку залежність поважає будь-яка жива архітектура — на відміну від пари незалежних читань, яку ARM чи POWER переставлять без сорому. [Порядок доступів до пам'яті](book:programming/memory-ordering-barriers) тут не декоративна деталь, а те, на чому все тримається.

## Рідкісний бік

```c
static void barrier_all(void);         /* membarrier або запасний шлях */

static void synchronize_rcu(void)      /* викликається під замком письменників */
{
    struct reader *r;
    unsigned long now;

    barrier_all();                     /* (1) публікацію бачать усі читачі */
    now = __atomic_add_fetch(&gp, GEN_STEP, __ATOMIC_RELAXED);
    barrier_all();                     /* (2) нове покоління видиме; чужі слова читабельні */

    for (r = registry; r; r = r->next)
        for (;;) {
            unsigned long v = __atomic_load_n(&r->ctr, __ATOMIC_RELAXED);
            if ((v & NEST_MASK) == 0)          /* не в секції */
                break;
            if ((v & ~NEST_MASK) == (now & ~NEST_MASK))
                break;                         /* зайшов уже після (2) */
            usleep(20);
        }
}

void update_table(struct route *fresh)
{
    struct route *old = __atomic_exchange_n(&table, fresh, __ATOMIC_RELEASE);
    synchronize_rcu();
    free_table(old);
}
```

Викликів `membarrier` тут два, і кожен закриває свою діру. Другий очевидний: без нього письменник читав би чужі слова стану, які ще сидять у буферах записів своїх ядер, — і міг би не побачити читача, що вже зайшов у секцію.

Перший потрібен через хитрішу причину — саме він робить чинним висновок «свіже покоління ⇒ читач безпечний». Читач знімає копію `gp` і потім читає `table` двома незалежними читаннями; своїм порядком він їх не скріплює. Якби письменник підняв `gp` до виклику, читач міг би побачити нове покоління і при цьому старий вказівник — і письменник звільнив би таблицю в нього під руками. Викликавши `membarrier` **до** підняття лічильника, ми домагаємося іншого: нове значення `gp` з'являється у світі вже після того, як усі читачі пройшли свої точки. Тепер прочитати його можна лише після власної точки, а отже й `table` читач візьме після неї — тобто вже нову. Та сама послідовність «спершу бар'єр, потім зміна покоління» стоїть і в `synchronize_rcu()` бібліотеки `liburcu`.

Два виклики замість одного подвоюють ціну рідкісного боку — і це нічого не міняє: вісімдесят мікросекунд раз на секунду з'їдають вісім тисячних відсотка часу, тоді як прибраний з гарячого боку бар'єр повертав би п'яту частину ядра. Асиметрія така груба, що на цьому боці рахувати вже нема чого.

І окремо: `membarrier` нікого не зупиняє. Читачі як бігли, так і біжать — виклик лише робить достовірним те, що письменник про них прочитає. Логіку очікування ми пишемо самі, і вона в тілі циклу.

## Реєстрація і старе ядро

```c
static int mode;                        /* 1 — експедований, 2 — глобальний, 0 — трюк */
static char *helper;

static int membarrier(int cmd, unsigned int flags, int cpu)
{ return syscall(__NR_membarrier, cmd, flags, cpu); }

int rcu_init(void)
{
    int mask = membarrier(MEMBARRIER_CMD_QUERY, 0, 0);

    if (mask > 0 && (mask & MEMBARRIER_CMD_PRIVATE_EXPEDITED) &&
        membarrier(MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED, 0, 0) == 0)
        return mode = 1;                /* одиниці-десятки мікросекунд */
    if (mask > 0 && (mask & MEMBARRIER_CMD_GLOBAL))
        return mode = 2;                /* десятки мілісекунд, зате без реєстрації */

    helper = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                  MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (helper == MAP_FAILED) return -1;
    *helper = 0;
    mlock(helper, 4096);                /* сторінка мусить лишатися присутньою */
    return mode = 0;
}

static void barrier_all(void)
{
    switch (mode) {
    case 1: membarrier(MEMBARRIER_CMD_PRIVATE_EXPEDITED, 0, 0); break;
    case 2: membarrier(MEMBARRIER_CMD_GLOBAL, 0, 0);            break;
    default:
        mprotect(helper, 4096, PROT_READ | PROT_WRITE);
        *(volatile char *)helper = 0;
        mprotect(helper, 4096, PROT_NONE);   /* звуження прав тягне розсилку IPI */
    }
}
```

Опитування через `MEMBARRIER_CMD_QUERY` повертає бітову маску підтриманих команд; на ядрі, старішому за 4.3, самого виклику немає, і повернеться `-1` з `ENOSYS`. Тоді лишається трюк, яким довго жило середовище виконання .NET: звуження прав на присутню сторінку змушує ядро [розіслати скидання TLB](book:unix-linux/tlb-shootdown), а це переривання на кожне ядро, що виконує наш адресний простір, — і кожне таке переривання дає бар'єр. Сторінку тримають замкненою в пам'яті саме тому, що вивантажена між двома викликами `mprotect` сторінка переривань не породить. Це побічний ефект чужого механізму, а не обіцянка: розробники .NET самі відзначали, що припущення взяте з поведінки x86, і сумнівалися в ньому для ARM64. `membarrier` існує зокрема для того, щоб такі трюки стали непотрібні.

## Пастки

**Вкладеність.** Внутрішній `rcu_read_lock` не має права перезнімати покоління — інакше письменник вирішить, що читач «зайшов заново», і звільнить таблицю, вказівник на яку тримає зовнішня секція. Тому гілка з `gp` виконується лише за нульової глибини.

**Сон усередині секції.** Заблокований виклик у критичній секції перетворює пільговий період із сорока мікросекунд на секунди, а звільнення відкладених копій — на зростання пам'яті. Правило жорстке: у секції не блокуємося. Так само не можна скасовувати чи вбивати потік усередині секції — його слово застрягне ненульовим назавжди, і письменник крутитиметься довіку.

**Реєстрація потоків.** Кожен читач заводить свій `struct reader` і чіпляє у список до першої секції, а при виході — знімає; і те, і те під тим самим замком, що його тримає письменник, тож обхід списку безпечний.

**Сусідство в одному рядку кеша.** Без `_Alignas(64)` слова кількох читачів сядуть в один рядок, і опитування письменником одного з них вибиватиме рядок у сусідів. Гарячий шлях знову почне платити — тепер промахами кеша замість бар'єра, і рівно стільки ж. Механіка цієї пастки — [хибне спільне використання](book:programming/false-sharing).

**Детектори гонок.** [ThreadSanitizer](book:programming/thread-sanitizer) на цьому коді закричить: порядок тут забезпечує ядро системи, і жодна бібліотека інструментування про це не знає. Такі місця доводиться глушити анотаціями вручну.

## Мікробенчмарк

Перевірити варто рівно те, заради чого все затівалося, — ціну входу в секцію.

```c
static double loop(int fenced)
{
    struct timespec a, b;
    const long N = 50L * 1000 * 1000;
    volatile unsigned long sink = 0;

    clock_gettime(CLOCK_MONOTONIC, &a);
    for (long i = 0; i < N; i++) {
        rcu_read_lock();
        if (fenced)
            __atomic_thread_fence(__ATOMIC_SEQ_CST);   /* те, що ми прибрали */
        sink += rcu_dereference(table) != NULL;
        rcu_read_unlock();
    }
    clock_gettime(CLOCK_MONOTONIC, &b);
    return ((b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec)) / (double)N;
}
```

Обидва прогони роблять в одному процесі, по черзі й кілька разів, а потік прив'язують до ядра — інакше половину різниці з'їсть [прив'язка до процесора](book:unix-linux/cpu-affinity) з міграціями. Порядок величин, який має вийти на будь-якому сучасному x86: без бар'єра одиниці наносекунд на ітерацію, з бар'єром — вдесятеро більше. Цифру на своїй машині варто отримати самому: вона й буде тим множником, на який множиться десять мільйонів читань за секунду.
