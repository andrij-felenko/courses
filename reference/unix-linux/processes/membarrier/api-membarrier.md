# 📋 Набір команд membarrier: сигнатура, версії ядра, коди відмов

Це викличний контракт системного виклику `membarrier()` — сигнатура, усі команди з версіями ядра й парними командами реєстрації, значення прапорця й третього аргументу, кожен код відмови з його справжньою причиною та зразок опитування підтримки. Звірятися з ним доводиться двічі: коли пишеш код і коли розбираєшся, чому виклик повернув `EINVAL` там, де за описом мав спрацювати, — бо більшість відмов тут походить не з команди, а з `flags` або з того, як зібрано конкретне ядро.

## Виклик

Обгортки в glibc немає й ніколи не було, тож виклик роблять напряму:

```c
#include <linux/membarrier.h>
#include <sys/syscall.h>
#include <unistd.h>

static long membarrier(int cmd, unsigned int flags, int cpu_id)
{
    return syscall(__NR_membarrier, cmd, flags, cpu_id);
}
```

У ядрі це `SYSCALL_DEFINE3(membarrier, int cmd, unsigned int flags, int cpu_id)`. До версії 5.10 аргументів було два — `int membarrier(int cmd, int flags)`, — і третій просто не читався, тож писати його завжди безпечно: на старому ядрі зайвий регістр ігнорується. Небезпечне інше — заголовки: `__NR_membarrier` з'явився в `<sys/syscall.h>` не одразу, і збірка проти дуже старих заголовків падає ще до запуску. Надійний спосіб — власний `#ifndef __NR_membarrier` із числом для потрібних архітектур або `SYS_membarrier` через перевірку в системі збирання.

## Команди

Значення команд — не порядкові номери, а **окремі біти**: саме так `MEMBARRIER_CMD_QUERY` повертає їх усі однією маскою. Сама `QUERY` має значення `0` і в маску не входить ніколи, тож перевірка `mask & MEMBARRIER_CMD_QUERY` завжди хибна — на цьому спотикаються, коли пишуть цикл по всіх іменах підряд.

| Команда | Значення | Ядро | Що робить | Парна реєстрація |
|---|---:|---:|---|---|
| `MEMBARRIER_CMD_QUERY` | `0` | 4.3 | повертає бітову маску підтриманих команд | — |
| `MEMBARRIER_CMD_GLOBAL` | `1 << 0` | 4.3 | бар'єр на **всіх** ядрах системи; всередині — `synchronize_rcu()` | не потрібна |
| `MEMBARRIER_CMD_SHARED` | те саме | 4.3 | давнє ім'я `GLOBAL`; від 4.16 лишилося як `#define` заради сумісності | — |
| `MEMBARRIER_CMD_GLOBAL_EXPEDITED` | `1 << 1` | 4.16 | негайний бар'єр на ядрах, де крутяться потоки **зареєстрованих** процесів | `REGISTER_GLOBAL_EXPEDITED` — але її видає **ціль**, не викликач |
| `MEMBARRIER_CMD_REGISTER_GLOBAL_EXPEDITED` | `1 << 2` | 4.16 | оголошує: потоки цього процесу мають бути покриті глобальною розсилкою | — |
| `MEMBARRIER_CMD_PRIVATE_EXPEDITED` | `1 << 3` | 4.14 | негайний бар'єр на ядрах, де крутяться потоки того самого адресного простору | `REGISTER_PRIVATE_EXPEDITED` |
| `MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED` | `1 << 4` | 4.14 | дає процесові право видавати приватну експедовану команду | — |
| `MEMBARRIER_CMD_PRIVATE_EXPEDITED_SYNC_CORE` | `1 << 5` | 4.16 | те саме плюс серіалізація конвеєра перед поверненням у користувацький код | `REGISTER_PRIVATE_EXPEDITED_SYNC_CORE` |
| `MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED_SYNC_CORE` | `1 << 6` | 4.16 | реєстрація для попередньої | — |
| `MEMBARRIER_CMD_PRIVATE_EXPEDITED_RSEQ` | `1 << 7` | 5.10 | те саме плюс зрив критичних ділянок [rseq](book:unix-linux/rseq) у потоків-побратимів | `REGISTER_PRIVATE_EXPEDITED_RSEQ` |
| `MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED_RSEQ` | `1 << 8` | 5.10 | реєстрація для попередньої | — |
| `MEMBARRIER_CMD_GET_REGISTRATIONS` | `1 << 9` | 6.3 | повертає маску вже виданих команд реєстрації | — |

Дві дати в рядку `GLOBAL` — не помилка. Команда працює від 4.3 під іменем `MEMBARRIER_CMD_SHARED`; у 4.16, коли з'явився глобальний експедований варіант, її перейменували на `GLOBAL`, а старе ім'я лишили як псевдонім із тим самим значенням. Код, написаний під 4.3, компілюється й донині; код, написаний під `GLOBAL`, не збереться проти заголовків 4.3.

`GET_REGISTRATIONS` додали заради [контрольних точок процесу](book:unix-linux/checkpoint-restore): глобальна експедована команда успішно виконується й для незареєстрованого процесу, тож інакше немає способу дізнатися, чи реєстрація була, — а без цього відновлений процес утратив би її мовчки.

## Реєстрація має два різні сенси

Однакове слово в назвах приховує дві різні речі, і плутанина тут коштує неправильно збудованого запуску.

У **приватному** режимі реєстрація — це дозвіл **слати**. Без неї `PRIVATE_EXPEDITED` повертає `EPERM`. Кожен різновид має власний біт готовності: реєстрація звичайного приватного бар'єра не відкриває ні `SYNC_CORE`, ні `RSEQ` — потрібні свої команди, і саме на цьому найчастіше з'являється несподіваний `EPERM`.

У **глобальному** експедованому режимі реєстрація — це згода **бути покритим**. Викликач її не потребує взагалі; вона позначає ті процеси, чиї потоки ядро включить у розсилку. Тому глобальна експедована команда ніколи не повертає `EPERM`.

Стан реєстрації живе в описі адресного простору (`mm`), а не в задачі чи групі потоків, і успадковується разом із ним. Повторний виклик реєстрації нешкідливий: якщо потрібний біт уже стоїть, ядро одразу повертає нуль.

## flags і третій аргумент

Тут ховається найчастіша причина `EINVAL`, і правило вужче, ніж здається з опису.

```
flags = 0                        — обов'язково для ВСІХ команд, крім однієї
flags = MEMBARRIER_CMD_FLAG_CPU  — дозволено ЛИШЕ з PRIVATE_EXPEDITED_RSEQ
                                   (значення 1 << 0)
```

Будь-яке інше значення `flags` — миттєвий `EINVAL`, ще до розбору команди. А `cpu_id` ядро читає **тільки** тоді, коли прапорець виставлено; інакше воно примусово підставляє `-1`, і третій аргумент не має жодного значення. Отже, звузити дію до одного ядра можна лише в rseq-команді: спробувати `PRIVATE_EXPEDITED` з `FLAG_CPU` — це отримати `EINVAL`, а не адресну розсилку.

## Що повертається

`MEMBARRIER_CMD_QUERY` повертає маску підтримки (невід'ємне число), `GET_REGISTRATIONS` — маску реєстрацій, решта команд при успіху — нуль. Відмова — це `-1` і код у `errno`:

| Код | Коли саме |
|---|---|
| `ENOSYS` | виклику немає в цьому ядрі — старіше за 4.3 або зібране без нього |
| `EINVAL` | невідома команда · ненульовий `flags` там, де він мусить бути нулем · `SYNC_CORE` на архітектурі без `CONFIG_ARCH_HAS_MEMBARRIER_SYNC_CORE` · `RSEQ` при вимкненому `CONFIG_RSEQ` · `GLOBAL` при увімкненому `nohz_full` |
| `EPERM` | приватна експедована команда без **своєї** реєстрації |
| `ENOMEM` | не вдалося виділити маску ядер під розсилку — ситуація виняткова |

Два `EINVAL` з цього списку варті окремого слова.

**Архітектура.** `SYNC_CORE` існує лише там, де ядро вміє серіалізувати конвеєр перед поверненням у користувацький простір: у чинному дереві це x86, ARM, ARM64, PowerPC, RISC-V і s390. На решті архітектур команда відсутня, і біт не з'явиться в масці `QUERY` — тобто [JIT-компілятор](book:programming/jit-compilation) мусить мати власний шлях, а не покладатися на неї.

**nohz_full.** Якщо ядро завантажено з переліком ядер процесора без періодичних [тиків](book:unix-linux/kernel-timekeeping), команда `GLOBAL` вимикається цілком: біт зникає з маски `QUERY`, а сам виклик повертає `EINVAL`. Причина в механіці: `GLOBAL` спирається на те, що пільговий період RCU неминуче тягне за собою перемикання контексту на кожному ядрі, а перемикання містить повний бар'єр. Ядро в режимі без тиків, яке довго крутить користувацький код, звітує про свій спокійний стан іншим шляхом — жодного перемикання, жодного бар'єра. Гарантія б розсипалася, тому команду просто закрили. Експедовані команди від цього не залежать: вони б'ють [міжпроцесорними перериваннями](book:unix-linux/inter-processor-interrupts), а переривання дістає й таке ядро.

## Тихий нуль

Окремо варто знати випадки, коли виклик повертає **нуль, не зробивши нічого**, — і це правильно, бо гарантія й так виконана:

- у процесі один користувач адресного простору (`mm_users == 1`) або в системі одне онлайн-ядро — для всіх приватних команд, **крім** `SYNC_CORE`: серіалізація конвеєра потрібна навіть однопотоковій програмі, що сама собі згенерувала код;
- `cpu_id` поза межами можливих ядер, ядро вимкнене або на ньому крутиться чужий адресний простір — жодного переривання, нуль у відповідь.

Останній пункт означає, що адресний варіант **не повідомляє про промах**. Якщо потік поїхав на інше ядро між тим, як його там побачили, і викликом, — команда мовчки нічого не зробить. Розраховувати на «нуль означає, що переривання дійшло» не можна; нуль означає лише «гарантія тепер тримається».

## Опитування підтримки й запасний шлях

Правильний запуск робить це один раз і запам'ятовує режим:

```c
enum mb_mode { MB_PRIVATE, MB_GLOBAL, MB_NONE };
static enum mb_mode mode = MB_NONE;

void mb_setup(void)
{
    long mask = membarrier(MEMBARRIER_CMD_QUERY, 0, 0);
    if (mask < 0)                             /* ENOSYS: ядро старіше за 4.3 */
        return;                               /* лишається MB_NONE */

    if ((mask & MEMBARRIER_CMD_PRIVATE_EXPEDITED) &&
        membarrier(MEMBARRIER_CMD_REGISTER_PRIVATE_EXPEDITED, 0, 0) == 0) {
        mode = MB_PRIVATE;
        return;
    }
    if (mask & MEMBARRIER_CMD_GLOBAL)         /* при nohz_full біта немає */
        mode = MB_GLOBAL;
}
```

Далі рідкісний бік вибирає команду за режимом:

```c
void mb_heavy(void)
{
    switch (mode) {
    case MB_PRIVATE: membarrier(MEMBARRIER_CMD_PRIVATE_EXPEDITED, 0, 0); break;
    case MB_GLOBAL:  membarrier(MEMBARRIER_CMD_GLOBAL, 0, 0);            break;
    case MB_NONE:    __atomic_thread_fence(__ATOMIC_SEQ_CST);            break;
    }
}
```

І тут — головне, що зазвичай забувають. Гілка `MB_NONE` не є рівноцінною заміною: бар'єр на рідкісному боці не впорядковує чужих ядер. Тому запасний шлях змінює контракт **обох** боків, і гарячий мусить його бачити:

```c
static inline void mb_light(void)
{
    if (mode == MB_NONE)
        __atomic_thread_fence(__ATOMIC_SEQ_CST);   /* справжня інструкція */
    else
        __atomic_signal_fence(__ATOMIC_SEQ_CST);   /* лише бар'єр компілятора */
}
```

Одна перевірка добре передбачуваної змінної коштує майже нічого, а програма лишається коректною і на ядрі 4.2, і на ядрі з `nohz_full`.

## Ціна команд і формальна парність

`GLOBAL` не потребує ні реєстрації, ні підтримки чогось особливого — і саме тому блокує викликача на **десятки мілісекунд**: усередині це очікування пільгового періоду RCU. Експедовані команди не блокують: розсилка переривань і повернення вкладаються в **одиниці-десятки мікросекунд**. Різниця в три-чотири порядки визначає, де яка команда доречна: `GLOBAL` — для подій, що трапляються рідше, ніж раз на секунду, або як запасний шлях; експедовані — скрізь, де затримка рідкісного боку взагалі помітна.

Формальний бік контракту ядро записує таблицею парності — які два бар'єри впорядковують доступи один щодо одного (`O` — впорядковують, `X` — ні):

```
                    barrier()   smp_mb()   sys_membarrier()
  barrier()             X          X              O
  smp_mb()              X          O              O
  sys_membarrier()      O          O              O
```

Уся вигода механізму — у верхньому правому куті. Пара «бар'єр компілятора ↔ `membarrier()`» упорядкована, а пара «бар'єр компілятора ↔ бар'єр компілятора» — ні. Тобто прибрати справжню інструкцію з гарячого шляху можна рівно тоді, коли на рідкісному стоїть системний виклик, і ніколи інакше.
