# 📋 Змінні per-CPU: усі виклики й що кожен обіцяє

Це збірка контрактів: кожен спосіб оголосити дані per-CPU, дістати їхню адресу, змінити їх однією операцією чи під замком, а також готові конструкції `percpu_counter` і `percpu_ref` — із відповіддю на питання, яких компілятор не поставить ніколи. Від кого цей виклик захищає, звідки його законно кликати і як виглядає найчастіша помилка з ним. Сигнатури звірені з деревом Linux станом на 2026 рік; там, де інтерфейс з'явився недавно, версію названо окремо.

## Три питання до кожного рядка

Питання перше — **чи закриває міграцію**. Між обчисленням адреси своєї копії й дією над нею [планувальник](book:unix-linux/scheduler-model) може перенести задачу на інше ядро процесора. Тоді запис піде за старою адресою — тобто в чужу копію.

Питання друге — **чи закриває суперника на цьому ж ядрі процесора**. [Обробник переривання чи softirq](book:unix-linux/interrupts-bottom-halves) влізає між «прочитати» й «записати» і губить свій приріст. Для цього ворога не потрібен жоден інший процесор.

Питання третє — **чи є суперник з іншого процесора**. Якщо він є, жоден примітив із цієї сторінки не годиться: ані `this_cpu_*`, ані `local_lock` не бачать нікого поза своїм ядром процесора. Потрібен звичайний [спін-замок](book:programming/spinlock) — і разом із ним зникає весь виграш per-CPU.

![Чотири форми доступу до даних per-CPU і вікна, у які встигає влізти суперник: одна інструкція вікон не має, гола адреса має обидва, заборона витіснення закриває міграцію, local_lock_irqsave — обидва](/reference/unix-linux/processes/per-cpu-data/img/access-windows.svg)

*Червона смуга — проміжок, у який може встигнути чужий код. Вибір виклику — це рівно вибір того, які з цих проміжків ви заклеюєте.*

## Оголошення статичної змінної

```c
/* у заголовку — оголошення */
DECLARE_PER_CPU(unsigned long, rx_packets);

/* рівно в одному .c — визначення */
DEFINE_PER_CPU(unsigned long, rx_packets);
```

| макрос | у яку підсекцію кладе | коли брати саме його |
|---|---|---|
| `DEFINE_PER_CPU(type, name)` | `.data..percpu` | звичайний випадок |
| `DEFINE_PER_CPU_SHARED_ALIGNED(type, name)` | `..shared_aligned` | до змінної лізуть з інших ядер процесора через `per_cpu_ptr()` |
| `DEFINE_PER_CPU_ALIGNED(type, name)` | `..aligned` | те саме, але вирівнювання потрібне й у збірці без SMP |
| `DEFINE_PER_CPU_PAGE_ALIGNED(type, name)` | `..page_aligned` | структура, яку віддають апаратурі або відображають сторінкою |
| `DEFINE_PER_CPU_READ_MOSTLY(type, name)` | `..read_mostly` | пишуть раз при налаштуванні, читають постійно |
| `DEFINE_PER_CPU_CACHE_HOT(type, name)` | `..hot..name` | найгарячіші змінні ядра; з'явилося у свіжих ядрах (6.15) і призначене для самого ядра, не для модулів |

Вирівнювання тут потрібне не проти сусідніх ядер процесора — їхні копії й так рознесені на цілий блок. Воно потрібне проти **власних сусідів у блоці**: якщо чуже ядро процесора регулярно читає вашу змінну, вона тягне за собою в чужий кеш увесь свій рядок разом із гарячими локальними лічильниками, і [хибне спільне використання](book:programming/false-sharing) повертається всередині одного блоку.

Модулю, щоб дістатися до змінної ядра, потрібен явний вивіз символу — `EXPORT_PER_CPU_SYMBOL_GPL(name)` у файлі з визначенням. Звичайний `EXPORT_SYMBOL` тут не працює, бо вивозиться не адреса, а зсув.

> 🔧 **Навіщо це.** Найпоширеніша помилка на цьому рівні — вважати, що `DEFINE_PER_CPU` десь у `.h`. Тоді кожна одиниця трансляції заведе власну змінну з тим самим ім'ям, компонувальник поскаржиться на повторення символу, а якщо `static` — мовчки дасть кілька незалежних наборів копій.

## Виділення на ходу

| виклик | сигнатура | контекст | типова помилка |
|---|---|---|---|
| `alloc_percpu(type)` | повертає `type __percpu *` або `NULL` | спить (усередині `GFP_KERNEL`) — лише контекст задачі | кликати з-під замка чи з обробника |
| `alloc_percpu_gfp(type, gfp)` | те саме з вибором прапорців | з `GFP_ATOMIC` законно з атомарного контексту, але відмов помітно більше | вважати відмову неможливою |
| `__alloc_percpu(size, align)` | коли розмір не виводиться з типу | як вище | передати вирівнювання менше за природне |
| `free_percpu(ptr)` | `void` | можна з атомарного контексту; `free_percpu(NULL)` безпечний | звільнити, поки хтось тримає похідний вказівник |

Три властивості цього виділювача варто знати напам'ять.

**Пам'ять занулено** — і в усіх копіях одразу, тож окремо чистити не треба.

**Є стеля розміру.** Одне виділення не може перевищити `PCPU_MIN_UNIT_SIZE`, тобто `PFN_ALIGN(32 << 10)` — 32 КіБ. Спроба взяти більше повертає `NULL` завжди, скільки б пам'яті не було вільно. Структура з великим вбудованим масивом усередині — класичний спосіб напоротися на цю межу; масив тримають окремим звичайним виділенням, а в даних per-CPU лишають вказівник.

**Повернений вказівник — не адреса.** Він позначений `__percpu` і придатний лише як аргумент до макросів доступу. Розіменувати його безпосередньо — помилка, яку компілятор пропустить, а статичний аналізатор `sparse` (запуск `make C=1`) впіймає й назве.

```c
struct stats { u64 bytes, packets; };
static struct stats __percpu *st;

st = alloc_percpu(struct stats);
if (!st)
        return -ENOMEM;
...
free_percpu(st);
```

## Дістати адресу копії

| виклик | що повертає | що вимикає | типова помилка |
|---|---|---|---|
| `per_cpu_ptr(ptr, cpu)` | вказівник на копію заданого ядра процесора | нічого | вважати прочитане звідти узгодженим із чимось |
| `per_cpu(var, cpu)` | сама змінна як l-value (для статичних) | нічого | те саме |
| `this_cpu_ptr(ptr)` | вказівник на свою копію | нічого | зберегти вказівник і скористатися ним після сну |
| `raw_cpu_ptr(ptr)` | те саме без перевірки контексту | нічого | брати «щоб не сварилося» |
| `get_cpu_ptr(ptr)` / `put_cpu_ptr(ptr)` | вказівник на свою копію | витіснення | заснути між ними |
| `get_cpu_var(var)` / `put_cpu_var(var)` | сама змінна як l-value | витіснення | те саме |
| `get_cpu()` / `put_cpu()` | номер свого ядра процесора | витіснення | забути `put_cpu()` на шляху помилки |
| `smp_processor_id()` | номер свого ядра процесора | нічого | кликати там, де витіснення дозволене |
| `raw_smp_processor_id()` | те саме без перевірки | нічого | вживати відповідь як факт, а не як підказку |

Різниця між `this_cpu_ptr()` і `raw_cpu_ptr()` уся в налагоджувальній збірці: з `CONFIG_DEBUG_PREEMPT` перший бере зсув через `smp_processor_id()` і тому скаржиться, якщо витіснення в цю мить дозволене. Другий іде повз перевірку. Без цієї конфігурації обидва — той самий код, тому ціна перевірки в робочій збірці нульова, і брати `raw_` заради швидкості немає сенсу.

Пари `get_*`/`put_*` — це лише `preempt_disable()` та `preempt_enable()` навколо. Звідси два наслідки. Перший: усередині заборонено все, що спить, — виділення з `GFP_KERNEL`, `mutex_lock()`, копіювання в простір користувача. Другий: заборона витіснення **не спиняє переривань** і не спиняє softirq на цьому ж ядрі процесора, тож проти обробника ці пари не захищають зовсім.

## Операції над скаляром

```c
this_cpu_read(pcp)                    /* → значення            */
this_cpu_write(pcp, val)
this_cpu_add(pcp, val)                this_cpu_sub(pcp, val)
this_cpu_inc(pcp)                     this_cpu_dec(pcp)
this_cpu_and(pcp, val)                this_cpu_or(pcp, val)
this_cpu_add_return(pcp, val)         this_cpu_sub_return(pcp, val)
this_cpu_inc_return(pcp)              this_cpu_dec_return(pcp)
this_cpu_xchg(pcp, nval)              /* → старе значення      */
this_cpu_cmpxchg(pcp, oval, nval)     /* → старе значення      */
this_cpu_try_cmpxchg(pcp, &oval, nval) /* → bool; свіжі ядра   */
```

Аргументом іде **сама змінна**, не її адреса: `this_cpu_inc(rx_packets)`. Для динамічної пам'яті — розіменований вказівник: `this_cpu_inc(*p)` або поле `this_cpu_add(st->bytes, n)`.

Ширші за машинне слово пари змінюють `this_cpu_cmpxchg64()` і `this_cpu_cmpxchg128()` там, де архітектура це вміє; давніший `this_cpu_cmpxchg_double()` із ядра прибрано разом із загальним переходом на `cmpxchg128()` (робота Пітера Зейлстри, влита у 2023 році).

### Три родини й що між ними спільного

| родина | вимикає витіснення/переривання сама | перевірка в налагоджувальній збірці | коли брати |
|---|---|---|---|
| `this_cpu_*` | так, якщо архітектура не вміє однією інструкцією | не потрібна | коли не певні — це правильний вибір за замовчуванням |
| `__this_cpu_*` | ні | так: `CONFIG_DEBUG_PREEMPT` кричить, якщо витіснення дозволене | під уже взятою забороною — усередині `local_lock`, спін-замка, обробника |
| `raw_cpu_*` | ні | ні | коли неточність свідома: підказки, приблизна статистика, налагоджувальні лічильники |

На x86-64 `this_cpu_*` для простих дій компілюється в одну інструкцію з сегментним префіксом, і тоді всі три родини дають однаковий машинний код — різниця лише в тому, що перевіряється. На архітектурах без такої адресації `this_cpu_*` розгортається в заборону переривань, дію і відновлення, а `__this_cpu_*` та `raw_cpu_*` — ні; саме там ціна різниться по-справжньому.

### Від чого захищає і від чого ні

| загроза | `this_cpu_*` | `__this_cpu_*` і `raw_cpu_*` |
|---|---|---|
| міграція між обчисленням адреси і дією | **закрито** | не закрито |
| переривання цього ж ядра процесора всередині «прочитати — змінити — записати» | **закрито** | не закрито |
| інший процесор пише в цю саму копію через `per_cpu_ptr()` | не закрито | не закрито |
| перевпорядкування доступів компілятором чи процесором | не закрито | не закрито |
| дві операції поспіль як одне неподільне ціле | не закрито | не закрито |

Останні три рядки — саме ті, на яких найчастіше спотикаються.

Жодна операція `this_cpu_*` **не є бар'єром пам'яті**. Вона неподільна щодо свого ядра процесора — і все. Якщо інший процесор читає вашу копію й має побачити її узгодженою з якимось іншим записом, потрібні звичайні [бар'єри](book:programming/memory-ordering-barriers), як для будь-яких спільних даних.

`this_cpu_cmpxchg()` — теж не заміна атомарної операції. Вона порівнює й міняє неподільно **лише щодо цього ядра процесора**; інший процесор, що пише в ту саму копію, зруйнує її без жодного попередження. Документація ядра називає віддалений запис через `per_cpu_ptr()` украй небажаним саме тому: операції `this_cpu_*` не мають семантики замка й не бачать чужого втручання.

## Обійти всі ядра процесора

| ітератор | множина, яку обходить | коли саме він |
|---|---|---|
| `for_each_possible_cpu(cpu)` | усі ядра процесора, які **можуть** бути в системі | підсумовування лічильників: копії вимкнених ядер зберігають свої значення |
| `for_each_online_cpu(cpu)` | ті, що зараз працюють | коли треба щось **зробити** на ядрі: послати IPI, поставити роботу, розбудити нитку |
| `for_each_present_cpu(cpu)` | фізично присутні | рідко, здебільшого в коді [ввімкнення ядер на ходу](book:unix-linux/cpu-hotplug) |
| `for_each_cpu(cpu, mask)` | довільна маска | власні підмножини |
| `nr_cpu_ids` | верхня межа номерів (≤ `NR_CPUS`) | розмір допоміжних масивів |
| `num_possible_cpus()`, `num_online_cpus()` | кількості | арифметика, а не обхід |

Помилка, яка не проявляється на стенді: підсумувати лічильники через `for_each_online_cpu()`. Поки жодне ядро процесора не вимикали, відповідь правильна; після першого ж вимкнення сума мовчки губить усе, що те ядро встигло нарахувати.

Дзеркальна помилка на іншому боці: обійти `for_each_online_cpu()` і вважати результат узгодженим. Множина ввімкнених ядер змінюється паралельно з вашим циклом. Якщо результат має бути цілісним, обхід беруть під `cpus_read_lock()` / `cpus_read_unlock()`.

І третя, окремого сорту: тримати в даних per-CPU **запас** — вільні об'єкти, сторінки, буфери — і не віддавати його при вимкненні ядра процесора. Пам'ять лишиться замкненою в копії, до якої більше ніхто не зайде. Підсистеми із запасами реєструють гак на вимикання саме для цього.

## local_lock: назвати захист

```c
struct depot {
        local_lock_t     lock;
        struct list_head free;
};

/* статична ініціалізація */
static DEFINE_PER_CPU(struct depot, depot) = {
        .lock = INIT_LOCAL_LOCK(lock),
};

/* або на ходу */
local_lock_init(&depot.lock);
```

| виклик | що робить |
|---|---|
| `local_lock(&d.lock)` / `local_unlock(&d.lock)` | ділянка проти витіснення |
| `local_lock_irq(&d.lock)` / `local_unlock_irq(&d.lock)` | ділянка проти переривань, беззастережно |
| `local_lock_irqsave(&d.lock, flags)` / `local_unlock_irqrestore(&d.lock, flags)` | те саме зі збереженням попереднього стану |
| `local_trylock(&t)` / `local_trylock_irqsave(&t, flags)` | спроба без чекання; вимагає окремого типу `local_trylock_t` |
| `local_lock_nested_bh(&d.lock)` / `local_unlock_nested_bh(&d.lock)` | ділянка всередині softirq, де `bh` уже вимкнено |
| `lockdep_assert_held(this_cpu_ptr(&d.lock))` | твердження «замок узято», перевіряється лише з `CONFIG_LOCKDEP` |

Аргумент — **шлях до поля в кресленні**, а не адреса вашої копії: `&depot.lock`. Свою копію макрос знайде сам. Виняток — `lockdep_assert_held()`, який працює зі звичайним вказівником, тому там пишуть `this_cpu_ptr(&depot.lock)`.

### У що це розгортається

| виклик | звичайне ядро | ядро з `PREEMPT_RT` |
|---|---|---|
| `local_lock()` | `preempt_disable()` | `migrate_disable()` + `spin_lock()` на своїй копії |
| `local_unlock()` | `preempt_enable()` | `spin_unlock()` + `migrate_enable()` |
| `local_lock_irq()` | `local_irq_disable()` | те саме, що `local_lock()` — **переривання не вимикаються** |
| `local_lock_irqsave(&l, f)` | `local_irq_save(f)` | `f = 0`, далі як `local_lock()` — **переривання не вимикаються** |
| `local_trylock()` | `preempt_disable()` + перевірка поля `acquired` | `migrate_disable()` + `spin_trylock()`; у NMI та в обробнику переривання **завжди невдача** |
| `local_lock_nested_bh()` | лише позначка для перевіряльника | `spin_lock()` |

Розбіжність у рядках `_irq` — не хиба, а суть задуму. На ядрі реального часу обробники переривань виконуються в нитках і беруть той самий замок, тому взаємне виключення дає сам замок, а не заборона переривань. Код, який покладався на побічний ефект `local_irq_save()` — скажімо, використовував його як гарантію неподільності щодо апаратури, — під `PREEMPT_RT` зламається мовчки.

Розмір типу теж вартий рядка: без `CONFIG_DEBUG_LOCK_ALLOC` структура `local_lock_t` порожня, тобто займає нуль байтів. `local_trylock_t` додає один байт прапорця `acquired` — саме тому це окремий тип, а не режим того самого.

### Від чого захищає і від чого ні

| загроза | `local_lock()` | `local_lock_irq()` / `_irqsave()` |
|---|---|---|
| витіснення на цьому ядрі процесора | **закрито** | **закрито** |
| softirq на цьому ядрі процесора | не закрито | **закрито** (на `PREEMPT_RT` — самим замком) |
| обробник апаратного переривання на цьому ядрі процесора | не закрито | **закрито** (на `PREEMPT_RT` — самим замком) |
| код на іншому ядрі процесора | не закрито | не закрито |

Другий рядок — головна пастка. `preempt_disable()` не спиняє softirq: обробник переривання, що прийде посеред вашої ділянки, на виході цілком законно запустить відкладену половину прямо тут. Тому `local_lock()` там, де ті самі дані чіпає softirq, — це мовчазна перегона на звичайному ядрі.

Саме її й ловить перевіряльник замків, і в цьому головна практична цінність примітиву. Мапа замка запам'ятовує контекст кожного взяття, тож коли той самий `local_lock` беруть із задачі без `_irq` і з обробника, `CONFIG_PROVE_LOCKING` видає скаргу про неузгоджений стан. Голий `local_irq_save()` такої мапи не мав і мовчав.

Чого `local_lock` не робить у жодній конфігурації — не захищає від інших процесорів. Якщо сусіднє ядро дістанеться до вашої копії через `per_cpu_ptr(&depot, cpu)`, воно візьме **свій** замок і зайде безборонно. Це чесний сигнал, що дані такої форми не є даними per-CPU. Про решту сімейства замків ядра — окремо в [примітивах синхронізації](book:unix-linux/kernel-locking/api-locking-primitives.md).

Примітив влито в ядро 5.8; тип `local_trylock_t` разом із `local_trylock()` — значно пізніше, у 6.15.

## percpu_counter: лічильник із порогом

Готова конструкція для випадку «пишуть безперервно, читають часто й хочуть майже правду». Тримає малу дельту на кожному ядрі процесора і одне спільне число; коли дельта переростає поріг, її вливають у спільне під замком.

| виклик | що робить | контекст |
|---|---|---|
| `percpu_counter_init(fbc, amount, gfp)` | виділяє масив копій, ставить початкове значення; `0` або `-ENOMEM` | з `GFP_KERNEL` спить |
| `percpu_counter_destroy(fbc)` | звільняє масив і знімає з обліку hotplug | обов'язково, інакше витік |
| `percpu_counter_add(fbc, amount)` | додає у свою копію, при переповненні порога вливає у спільне | будь-який |
| `percpu_counter_add_batch(fbc, amount, batch)` | те саме зі своїм порогом | будь-який |
| `percpu_counter_add_local(fbc, amount)` | додає **лише** у свою копію, ніколи не вливає | будь-який |
| `percpu_counter_inc/dec/sub(fbc, …)` | зручні обгортки над `add` | будь-який |
| `percpu_counter_set(fbc, amount)` | перезаписує все значення | рідко, здебільшого при налаштуванні |
| `percpu_counter_read(fbc)` | читає **тільки** спільне число | одне читання, приблизно |
| `percpu_counter_read_positive(fbc)` | те саме, від'ємне віддає нулем | одне читання |
| `percpu_counter_sum(fbc)` | бере замок і обходить усі копії | дорого |
| `percpu_counter_sum_positive(fbc)` | те саме, від'ємне віддає нулем | дорого |
| `percpu_counter_compare(fbc, rhs)` | порівнює дешево, а біля межі — точно | саме це замість «прочитати й порівняти» |
| `percpu_counter_limited_add(fbc, limit, amount)` | додає, лише якщо не перевищить межу; повертає `bool` | будь-який |
| `percpu_counter_initialized(fbc)` | чи ініціалізовано | будь-який |

Поріг вливання — глобальна змінна `percpu_counter_batch`, і вона не стала. Спершу дорівнює 32, а далі ядро перераховує її при кожній зміні складу ввімкнених ядер процесора:

```
batch = max(32, кількість_ввімкнених_ядер × 2)
```

Звідси береться межа похибки дешевого читання. Кожна копія тримає менше за `batch` за модулем, отже:

**Умова.** Машина на 64 ядра процесора, усі ввімкнені.

```
batch                        = max(32, 64 × 2) = 128
найгірша розбіжність         = batch × кількість ядер
                             = 128 × 64
                             = 8192
```

Тобто `percpu_counter_read()` на такій машині може відставати від дійсності на вісім тисяч. Перевіряти межу цим викликом безглуздо — для цього є `percpu_counter_compare()`, який дешево відповідає, коли відповідь очевидна, і сам переходить на повний обхід, коли значення підійшло близько.

Дві тонкощі, яких не видно з назв.

`percpu_counter_add_local()` **ніколи** не вливає дельту у спільне число. Тому після нього `percpu_counter_read()` віддає застаріле значення назавжди, і читати такий лічильник законно лише через `percpu_counter_sum()`. Ця пара призначена для найгарячіших шляхів, де навіть рідкісний вихід на спільний замок неприйнятний.

Вимкнення ядер процесора конструкція розв'язує сама: при виході ядра її гак зливає його дельту у спільне число, а `percpu_counter_sum()` обходить ввімкнені й ті, що саме вмикаються чи вмирають. Тому — на відміну від голих лічильників per-CPU — тут `for_each_possible_cpu()` не потрібен і навіть шкідливий: копії вимкнених ядер уже враховано, і додавати їх ще раз означає порахувати двічі.

## percpu_ref: лічильник посилань у два життя

Звичайне підсумовування копій не годиться там, де питання завжди «чи вже нуль» — доки ви рахуєте суму, вона змінюється. Тому [підрахунок посилань](book:programming/reference-counting) тут живе у двох режимах, і перехід між ними робить `percpu_ref_kill()`.

```
percpu_ref_init   →  режим per-CPU: лічильник = 1, це початкове посилання власника
   get / put         звичайний приріст у свою копію; нуль не перевіряється взагалі

percpu_ref_kill   →  перемикання в атомарний режим (чекає період спокою RCU),
                     складання всіх копій, скидання початкового посилання
   tryget_live       від цієї миті повертає false
   put               атомарний; той, що дійде нуля, викличе release()

percpu_ref_exit   →  звільнити масив копій, коли все скінчилося
```

| виклик | сигнатура й повернення | контекст | типова помилка |
|---|---|---|---|
| `percpu_ref_init(ref, release, flags, gfp)` | `int`: `0` або `-ENOMEM` | спить | не перевірити результат |
| `percpu_ref_get(ref)`, `percpu_ref_get_many(ref, n)` | `void` | будь-який | брати посилання, не тримаючи жодного, — перегони з `kill` |
| `percpu_ref_tryget(ref)` | `bool`: вдається, поки лічильник не нуль | будь-який | вживати там, де треба «ще не вбитий» |
| `percpu_ref_tryget_live(ref)` | `bool`: не вдається після `kill` | будь-який, бере RCU сам | плутати з `tryget()` |
| `percpu_ref_tryget_live_rcu(ref)` | те саме, RCU має бути вже взято | під `rcu_read_lock()` | кликати без RCU |
| `percpu_ref_put(ref)`, `percpu_ref_put_many(ref, n)` | `void` | будь-який | забути, що останній `put` викличе `release()` прямо тут |
| `percpu_ref_kill(ref)` | `void` | контекст задачі, **рівно один раз** | покликати двічі |
| `percpu_ref_kill_and_confirm(ref, confirm)` | зі зворотним викликом на підтвердження | контекст задачі | те саме |
| `percpu_ref_is_zero(ref)`, `percpu_ref_is_dying(ref)` | `bool` | будь-який | приймати рішення за застарілою відповіддю |
| `percpu_ref_switch_to_atomic(ref, confirm)` | перевести в атомарний режим без убивства | контекст задачі | — |
| `percpu_ref_switch_to_atomic_sync(ref)` | те саме з очікуванням | спить | кликати з атомарного контексту |
| `percpu_ref_switch_to_percpu(ref)` | повернути дешевий режим | контекст задачі | — |
| `percpu_ref_resurrect(ref)` | оживити після `kill` | лише з `PERCPU_REF_ALLOW_REINIT` | без прапорця — попередження |
| `percpu_ref_exit(ref)` | звільнити пам'ять | коли вже ніхто не тримає | звільнити до того, як `release()` відпрацював |

Прапорці `percpu_ref_init()`:

| прапорець | що змінює |
|---|---|
| `PERCPU_REF_INIT_ATOMIC` | почати одразу в атомарному режимі; дешевий режим увімкнути потім |
| `PERCPU_REF_INIT_DEAD` | почати вже «вбитим» — для об'єктів, які вмикають згодом; має на увазі й атомарний режим |
| `PERCPU_REF_ALLOW_REINIT` | дозволити `percpu_ref_resurrect()` та повторну ініціалізацію |

Дві речі, які визначають, чи буде код правильним.

**`kill` не діє миттєво.** Перехід в атомарний режим чекає періоду спокою [RCU](book:unix-linux/rcu-mechanism), бо треба дати договорити всім, хто вже почав дешевий `get`. Отже, між викликом `kill()` і викликом `release()` минає невідомий наперед час — і жодного «звільнимо одразу після kill» бути не може.

**`release()` кличе останній `put`.** Не окрема нитка, не робоча черга — той самий контекст, у якому виконався останній `put`. Якщо `put` роблять із обробника переривання, то й зворотний виклик виконається в обробнику, де спати не можна. Коли `release()` мусить спати, він сам ставить роботу в чергу.

## Мінімальний робочий скелет

```c
struct depot {
        local_lock_t     lock;
        struct list_head free;
        unsigned int     count;
};

static DEFINE_PER_CPU(struct depot, depot) = {
        .lock = INIT_LOCAL_LOCK(lock),
};
static DEFINE_PER_CPU(unsigned long, hits);

static struct obj *depot_pop(void)
{
        struct depot *d;
        struct obj *o = NULL;

        local_lock(&depot.lock);        /* витіснення закрито   */
        d = this_cpu_ptr(&depot);       /* адреса дійсна тут    */
        lockdep_assert_held(this_cpu_ptr(&depot.lock));
        if (d->count) {
                o = list_first_entry(&d->free, struct obj, node);
                list_del(&o->node);
                d->count--;
                __this_cpu_inc(hits);   /* можна без гарантій:  */
        }                               /* витіснення вже нема  */
        local_unlock(&depot.lock);
        return o;
}

static unsigned long depot_hits(void)
{
        unsigned long total = 0;
        int cpu;

        for_each_possible_cpu(cpu)      /* possible, не online  */
                total += per_cpu(hits, cpu);
        return total;                   /* сума з різних митей  */
}
```

Якщо цей самий склад чіпав би ще й обробник переривання, `local_lock()` довелося б замінити на `local_lock_irqsave(&depot.lock, flags)` — і більше нічого.

## Що ядро скаже, коли ви помилилися

| повідомлення | що порушено | конфігурація, яка його вмикає |
|---|---|---|
| `BUG: using smp_processor_id() in preemptible [00000000] code:` | номер ядра процесора взято там, де витіснення дозволене | `CONFIG_DEBUG_PREEMPT` |
| `BUG: using __this_cpu_add() in preemptible [00000000] code:` | `__`-варіант ужито без обіцяної заборони | `CONFIG_DEBUG_PREEMPT` |
| `BUG: sleeping function called from invalid context` | сон під `local_lock`, `preempt_disable()` чи забороною переривань | `CONFIG_DEBUG_ATOMIC_SLEEP` |
| `inconsistent {SOFTIRQ-on-W} -> {IN-SOFTIRQ-W} usage` | той самий `local_lock` беруть із задачі без `_irq` і з обробника | `CONFIG_PROVE_LOCKING` |
| `WARNING: … at lib/percpu-refcount.c` | `percpu_ref_kill()` удруге або `resurrect` без прапорця | завжди |
| компонувальник: повторення символу | `DEFINE_PER_CPU` потрапило в заголовок | завжди |
| `sparse`: `incorrect type in initializer (different address spaces)` | вказівник `__percpu` ужито як звичайну адресу | `make C=1` |

Три перші рядки не з'являться в робочій збірці ніколи — не тому, що коду там немає помилки, а тому, що перевірок немає. Це й пояснює, чому налагоджувальну конфігурацію тримають на стенді постійно: [витісненість](book:unix-linux/kernel-preemption) і контекст — саме ті властивості, які не видно ані в коді, ані в поведінці, доки не зійдеться рідкісний збіг на завантаженій машині.
