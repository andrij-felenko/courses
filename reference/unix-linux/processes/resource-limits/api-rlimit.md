# 📋 Довідка по RLIMIT_*: константи, виклики, одиниці

Тут зібрано повний перелік ресурсів, у яких є пара «м'який–жорсткий»: що саме рахує кожен, у чому вимірюється, як виглядає спрацювання і з якої версії ядра він існує. Далі — підписи `getrlimit`/`setrlimit`/`prlimit` з повним списком помилок і таблиця відповідності між константою ядра, буквою `ulimit`, рядком у `/proc`, директивою systemd і полем `limits.conf`. Останню потрібно тримати перед очима найчастіше: одне й те саме число в цих п'яти місцях називають п'ятьма іменами й пишуть у трьох різних одиницях, а помиляються в ньому рівно в 1024 рази.

## Три виклики

```c
#include <sys/resource.h>

struct rlimit {
    rlim_t rlim_cur;    /* м'який: саме з ним ядро звіряє кожен запит */
    rlim_t rlim_max;    /* жорсткий: стеля для м'якого, не для ресурсу */
};

int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
```

```c
#define _GNU_SOURCE                     /* prlimit() — розширення GNU */
#include <sys/resource.h>

int prlimit(pid_t pid, int resource,
            const struct rlimit *new_limit,   /* NULL — нічого не міняти */
            struct rlimit *old_limit);        /* NULL — нічого не читати */
```

| виклик | кого стосується | читає | пише | доступність |
|---|---|---|---|---|
| `getrlimit()` | лише себе | так | ні | завжди |
| `setrlimit()` | лише себе | ні | так | завжди |
| `prlimit()` | себе (`pid == 0`) або чужий процес | так | так | ядро 2.6.36, обгортка glibc 2.13 |

Усі троє повертають `0` або `-1` з `errno`.

**`prlimit()` робить обидві дії за один вхід у ядро.** Передані разом `new_limit` і `old_limit` означають «постав нове й віддай попереднє» — старе значення повертається те, що було до заміни. Пара `getrlimit()` + `setrlimit()` дає те саме лише тоді, коли між ними ніхто не втрутився, а втрутитися є кому: той самий набір лімітів спільний для всіх потоків процесу ([потоки як задачі](book:unix-linux/threads-as-tasks) — планувальник бачить окремі задачі, а ліміти належать усій їх групі), та й чужий процес із правами може переставити ваші межі ззовні.

**Права на чужий процес.** Щоб чіпати межі не свого PID, потрібна або можливість `CAP_SYS_RESOURCE` у просторі імен користувачів адресата ([можливості замість всесильного root](book:unix-linux/capabilities) — окремо роздані шматки повноважень), або збіг ідентичностей: реальний, чинний і збережений UID адресата мусять дорівнювати реальному UID того, хто просить, і те саме для GID. Тобто «свої процеси» — це справді свої, а не будь-чиї з того самого сеансу.

**`rlim_t` — беззнаковий.** Від'ємних лімітів не буває, і саме тому «немає межі» позначають не мінус одиницею, а окремою константою `RLIM_INFINITY`. Її числове значення архітектурно залежне: зазвичай це всі одиниці (`~0UL`), але на 32-бітових MIPS вона дорівнює `0x7fffffffUL`, а на Alpha — `0x7ffffffffffffffful`, обидва рази заради сумісності зі старішими системами. Порівнювати треба з іменем константи, ніколи з `-1` чи `~0`.

Помилки — спільні для трьох викликів:

| помилка | коли |
|---|---|
| `EFAULT` | вказівник веде за межі доступного адресного простору |
| `EINVAL` | `resource` не є чинним номером; або `rlim_cur > rlim_max` у тому, що ставлять |
| `EPERM` | непривілейована спроба **підняти** жорсткий ліміт (потрібна `CAP_SYS_RESOURCE`) |
| `EPERM` | жорсткий `RLIMIT_NOFILE` вище за `/proc/sys/fs/nr_open` — це не обходить навіть привілейований |
| `EPERM` | `prlimit()`: немає прав на вказаний `pid` |
| `ESRCH` | `prlimit()`: процесу з таким `pid` не існує |

Опустити будь-який ліміт `EPERM` не дає ніколи: рух униз дозволений без прав, і саме тому він незворотний.

**Що насправді викликає glibc.** Обгортки `getrlimit()` і `setrlimit()` у сучасній glibc звертаються до системного виклику `prlimit64()`, а не до однойменних старих. Причина суто арифметична: на 32-бітових платформах старий інтерфейс носив 32-бітові значення й не міг виразити ліміт понад 4 ГіБ, а `prlimit64()` носить 64-бітові завжди. Через це поведінка виявляється кращою за букву старого ABI — наприклад, ліміт у 8 ГіБ на 32-бітовій системі читається правильно.

## Повний перелік ресурсів

Номер у першій колонці — це значення самої константи. Він важить не сам по собі, а тому, що в цьому порядку рядки йдуть у `/proc/<pid>/limits`.

| № | константа | що саме рахує | одиниця | що видно при спрацюванні | з якої версії |
|---|---|---|---|---|---|
| 0 | `RLIMIT_CPU` | накопичений процесорний час процесу | секунди | `SIGXCPU` на м'якій межі, `SIGKILL` на жорсткій | від початку |
| 1 | `RLIMIT_FSIZE` | розмір файлу, який процес створює або подовжує | байти | `SIGXFSZ` **і** `EFBIG` з `write()`/`truncate()` | від початку |
| 2 | `RLIMIT_DATA` | сегмент даних: `brk()`/`sbrk()`, від 4.7 ще й приватні записувані `mmap()` | байти | `ENOMEM` | розширено в 4.7 |
| 3 | `RLIMIT_STACK` | головний стек процесу | байти | `SIGSEGV`, коли стек не може вирости далі | від початку |
| 4 | `RLIMIT_CORE` | розмір аварійного дампа | байти | дамп обрізають; `0` — не пишуть узагалі | від початку |
| 5 | `RLIMIT_RSS` | **нічого** | байти | нічого: діяв лише до 2.4.30 | мертвий |
| 6 | `RLIMIT_NPROC` | задачі реального UID по всій системі | штуки | `EAGAIN` з `fork()`/`clone()` | від початку |
| 7 | `RLIMIT_NOFILE` | на одиницю більше за найбільший дозволений номер дескриптора | штуки | `EMFILE` | від початку |
| 8 | `RLIMIT_MEMLOCK` | заблоковані в оперативній пам'яті байти | байти, вниз до сторінки | `ENOMEM` з `mlock()`/`mlockall()`/`mmap(MAP_LOCKED)` | сенс змінено в 2.6.9 |
| 9 | `RLIMIT_AS` | сума розмірів усіх відображень адресного простору | байти | `ENOMEM` з `mmap`/`brk`/`mremap`; `SIGSEGV` при рості стека | від початку |
| 10 | `RLIMIT_LOCKS` | **нічого** | штуки | нічого: діяв лише 2.4.0–2.4.24 | мертвий |
| 11 | `RLIMIT_SIGPENDING` | сигнали в черзі до реального UID | штуки | `EAGAIN` з `sigqueue()` | 2.6.8 |
| 12 | `RLIMIT_MSGQUEUE` | байти під черги повідомлень реального UID | байти | `ENOMEM` з `mq_open()` | 2.6.8 |
| 13 | `RLIMIT_NICE` | стелю ввічливості, як `20 − rlim_cur` | зсунуте число | `EACCES`/`EPERM` з `setpriority()`/`nice()` | 2.6.12 |
| 14 | `RLIMIT_RTPRIO` | найвищий реальночасовий пріоритет | пріоритет | `EPERM` з `sched_setscheduler()` | 2.6.12 |
| 15 | `RLIMIT_RTTIME` | процесорний час реальночасової задачі без блокування | мікросекунди | `SIGXCPU` на м'якій межі, `SIGKILL` на жорсткій | 2.6.25 |

`RLIM_NLIMITS` дорівнює 16 — це кількість рядків у таблиці, а не найбільший чинний номер.

**Номери переносні не всюди.** Наведені значення чинні для більшості архітектур, але не для всіх: на MIPS `RLIMIT_NOFILE` дорівнює 5, `RLIMIT_AS` — 6, `RLIMIT_RSS` — 7, `RLIMIT_NPROC` — 8, `RLIMIT_MEMLOCK` — 9; на Alpha свій зсув. Число в коді писати не можна — тільки ім'я константи.

### Ті, у кого спрацювання має формулу

**`RLIMIT_NICE` — зсунута шкала.** Ліміт не може бути від'ємним, а ввічливість (nice) буває від −20 до 19, тож межу зберігають зсунутою. Стелю рахують так:

**Умова: `rlim_cur` дорівнює 30. Наскільки низько процес зможе опустити своє число ввічливості?**

```
стеля nice = 20 − rlim_cur = 20 − 30 = −10

rlim_cur = 40  →  nice ≥ −20   (найвищий можливий пріоритет)
rlim_cur = 30  →  nice ≥ −10
rlim_cur = 20  →  nice ≥   0   (звична поведінка: тільки вгору по числу)
rlim_cur =  1  →  nice ≥  19   (нижче нікуди)
```

Корисний проміжок значень ліміту — від 1 до 40; нуль нічого не додає до одиниці. Сам сенс числа ввічливості — у [пріоритетах і реальночасових класах](book:unix-linux/priority-nice-realtime).

**`RLIMIT_MSGQUEUE` — місце під чергу рахують наперед.** `mq_open()` не чекає, поки чергу наповнять: він одразу списує з бюджету реального UID усю можливу вагу черги разом зі службовими витратами ядра. Від Linux 3.5 формула така:

```
байти = mq_maxmsg · sizeof(struct msg_msg)
      + min(mq_maxmsg, MQ_PRIO_MAX) · sizeof(struct posix_msg_tree_node)
      + mq_maxmsg · mq_msgsize
```

Доданок зі службовими структурами існує рівно для того, щоб чергу з десятків тисяч нульових повідомлень не можна було створити «безкоштовно». До 3.4 включно формула була простіша — `mq_maxmsg · sizeof(struct msg_msg *) + mq_maxmsg · mq_msgsize`, — і саме цю дірку вона й лишала. Типовий бюджет — 819 200 байтів; що таке самі черги, описано в темі про [черги повідомлень](book:unix-linux/message-queues).

**`RLIMIT_CPU` і `RLIMIT_RTTIME` — межу відсувають на секунду.** Обидва впроваджують сигналом, і в обох є однакова тонкість реалізації: від Linux 2.6.12, якщо процес перехопив `SIGXCPU` і після обробника вижив, ядро **піднімає м'який ліміт на одну секунду** й надішле сигнал знову за секунду. Без цього обробник, який не завершує процес, отримував би сигнал безперервно й машина стояла б. Жорстка межа такої поблажки не має: там `SIGKILL`, і перехопити його нічим ([сигнал: асинхронне сповіщення](book:unix-linux/signal-model) — типова дія й межі того, що з нею можна зробити).

**`RLIMIT_MEMLOCK` — два окремі кошики.** Значення заокруглюють униз до сторінки, і воно обмежує дві незалежні суми: блокування, зроблені через `mlock()`/`mlockall()`/`mmap(MAP_LOCKED)`, та блокування сегментів спільної пам'яті через `shmctl(SHM_LOCK)`. Кожен кошик має свою повну межу — процес може вибрати ліміт двічі. Від Linux 2.6.9 привілейований процес під цю межу не підпадає взагалі, а сама вона стосується непривілейованих; до 2.6.9 було навпаки — вона обмежувала саме привілейованих.

Типове значення виросло вчетверо за сотню: до Linux 5.16 це були 64 КіБ, від 5.16 — 8 МіБ. Причина в тому, що ліміт з часом набрав нових споживачів: 64 КіБ вистачало, поки йшлося лише про ключі й паролі, які не хочуть віддавати у своп, і геть не вистачало для наперед закріплених буферів [io_uring](book:unix-linux/io-uring). Ще один колишній споживач із цієї межі пішов: до Linux 5.11 пам'ять під BPF-мапи списували з `RLIMIT_MEMLOCK`, тому рецепт «спершу `ulimit -l unlimited`» був у кожній інструкції з [eBPF](book:unix-linux/ebpf-extended-berkeley-packet-filter); від 5.11 її рахують через контролер пам'яті cgroup, і рецепт застарів.

**`RLIMIT_NOFILE` — стеля над стелею.** Значення означає «на одиницю більше за найбільший номер дескриптора», тобто `1024` дозволяє номери від 0 до 1023 ([файловий дескриптор](book:unix-linux/file-descriptor) — індекс у таблиці процесу, а не сам файл). Сам жорсткий ліміт має власну стелю — `/proc/sys/fs/nr_open`, типово 1 048 576; спроба перевищити її дає `EPERM` навіть привілейованому. Від Linux 4.5 цей самий ліміт рахує ще одне: скільки дескрипторів непривілейований процес має «в польоті», тобто вже відправленими через сокет домену Unix, але ще не прийнятими на тому кінці.

### Ті, у кого лічильник спільний

Три ліміти рахують не процес, а **реального користувача** — усі його задачі по всій системі, у якому б місці вони не жили:

- `RLIMIT_NPROC` — задачі (не процеси: потоки теж рахують окремо);
- `RLIMIT_SIGPENDING` — сигнали в черзі;
- `RLIMIT_MSGQUEUE` — байти під черги повідомлень.

Наслідок один і той самий для всіх трьох: межу, виставлену службі, може вичерпати щось геть інше, запущене від того самого імені ([користувачі, групи й ідентичність процесу](book:unix-linux/uid-gid-model) — чому саме реальний UID, а не чинний). Тому окремий системний користувач на службу — не косметика, а єдиний спосіб зробити цей бюджет справді її власним.

`RLIMIT_NPROC` має ще й дірку в перевірці: її не роблять зовсім, якщо процес має `CAP_SYS_ADMIN` чи `CAP_SYS_RESOURCE` або працює з реальним UID 0. Звідси відомий сюрприз у програм, що скидають привілеї: доки процес був привілейованим, ліміт його не стосувався, а перший же `fork()` після зміни UID може повернути `EAGAIN`, хоча в самій програмі нічого не змінилося.

`RLIMIT_SIGPENDING` впроваджують лише для `sigqueue()`. Звичайний `kill()` завжди має право поставити в чергу один примірник сигналу, якого там ще немає, — інакше вичерпаний бюджет зробив би процес нездоланним.

## Типові значення, з якими народжується система

Ядро видає перші межі процесу з номером 1, і далі вони йдуть у спадок ([fork: розмноження процесу](book:unix-linux/fork-semantics) — дитина починає копією батька).

| ресурс | м'який | жорсткий | звідки число |
|---|---|---|---|
| `RLIMIT_STACK` | 8 МіБ | без межі | `_STK_LIM` = 8·1024·1024 |
| `RLIMIT_CORE` | 0 | без межі | дампів типово не пишуть |
| `RLIMIT_NOFILE` | 1024 | 4096 | `INR_OPEN_CUR` / `INR_OPEN_MAX` |
| `RLIMIT_MEMLOCK` | 8 МіБ | 8 МіБ | `MLOCK_LIMIT`, від 5.16 (раніше 64 КіБ) |
| `RLIMIT_MSGQUEUE` | 819 200 | 819 200 | `MQ_BYTES_MAX` |
| `RLIMIT_NICE`, `RLIMIT_RTPRIO` | 0 | 0 | понижувати ввічливість типово не можна нікому |
| `RLIMIT_NPROC`, `RLIMIT_SIGPENDING` | половина `max_threads` | те саме | рахують від обсягу пам'яті на етапі старту |
| решта | без межі | без межі | |

Число для `NPROC` і `SIGPENDING` тому й не стале, що залежить від пам'яті машини: на різних серверах `ulimit -u` покаже різне, і це нормально.

Systemd, будучи процесом номер 1, цей набір переписує перед запуском кожної служби: `DefaultLimitNOFILE=` типово дорівнює `1024:524288`, тобто жорстка межа дескрипторів для служб — півмільйона, а м'яка лишається на 1024. Решта `DefaultLimit…=` типово не задані, і межі просто успадковуються від ядра або від середовища контейнера.

### Одиниці розходяться — і саме тут помиляються

Ядро оперує байтами, секундами й мікросекундами. Інші чотири записи це поважають не всі.

| ліміт | ядро й systemd | `ulimit` | `limits.conf` |
|---|---|---|---|
| `STACK`, `DATA`, `AS`, `MEMLOCK`, `RSS` | байти | **кілобайти** (× 1024) | **кілобайти** (× 1024) |
| `CORE`, `FSIZE` | байти | **блоки**: 1024 Б, а в POSIX-режимі 512 Б | кілобайти |
| `CPU` | секунди | секунди | **хвилини** |
| `RTTIME` | мікросекунди | мікросекунди | мікросекунди |
| `MSGQUEUE` | байти | байти | байти |
| `NOFILE`, `NPROC`, `SIGPENDING`, `LOCKS` | штуки | штуки | штуки |
| `NICE` | `20 − nice`, тобто 0…40 | те саме, 1…40 | сам nice, −20…19 |

**Умова: службі треба стек у 8 МіБ. Як це число виглядає в кожному записі?**

```
ядро, prlimit(2), /proc/<pid>/limits   8388608          байтів
ulimit -s                              8192             КіБ  (× 1024)
systemd  LimitSTACK=                   8M   або 8388608  байтів
limits.conf   stack                    8192             КіБ  (× 1024)
```

Тому `LimitSTACK=8192` у файлі юніта — це не «як `ulimit -s 8192`», а 8 кілобайтів: служба не переживе першого ж глибокого виклику. Помилка в тисячу двадцять чотири рази виглядає як довільне падіння в незрозумілому місці, і саме її дає механічне перенесення числа з оболонки в юніт.

Друга пастка того самого роду — процесорний час: `LimitCPU=600` і `ulimit -t 600` означають десять хвилин, а `cpu 600` у `limits.conf` — шістсот хвилин, тобто десять годин.

Третя — «блоки» в `ulimit -c` і `-f`. Слово в підказці `ulimit -a` є, а розміру блока в ньому немає, і він не сталий: bash множить на 1024, але в POSIX-режимі — на 512, бо сам стандарт описує з усіх меж лише `-f` і саме в блоках по 512 байтів. Тобто той самий рядок `ulimit -f 100` в одному режимі означає 102 400 байтів, а в іншому 51 200.

**Умова: `ulimit -f 100` у трьох різних місцях. Скільки це байтів?**

```
bash звичайний    100 · 1024 = 102400 Б
bash -o posix     100 ·  512 =  51200 Б
LimitFSIZE=100          100  =    100 Б  (systemd рахує байти)
```

### Дрібниці записів, які кусаються

- **Порожній `-H`/`-S` у `ulimit` означає різне для читання й запису.** Без ключів читання показує **м'який** ліміт, а присвоєння ставить **обидва** — і жорсткий теж, назавжди вниз. Тому `ulimit -n 4096` в одному рядку скрипту здатне зробити неможливим `ulimit -n 8192` у наступному.
- **Букв у `ulimit` більше, ніж лімітів у Linux.** `-b` (буфер сокета), `-k` (kqueue), `-P` (псевдотермінали), `-T` (потоки), `-w` (своп) відповідають межам BSD-систем; на Linux відповідних констант немає, і bash ці ключі просто не збирає.
- **systemd бере пару через двокрапку.** `LimitNOFILE=1024:524288` — м'яка й жорстка окремо, одне число — обидві однакові, слово `infinity` — без межі. Розміри приймають суфікси `K`, `M`, `G`, `T`, `P`, `E` за основою 1024, а часові — `ms`, `s`, `min`, `h`.
- **`LimitNICE=` розуміє обидві шкали.** Число зі знаком (`+5`, `-10`) — це звичайна ввічливість із проміжку −20…19, число без знака — сире значення ліміту з проміжку 0…40. `LimitNICE=10` і `LimitNICE=+10` означають протилежні речі.
- **`limits.conf` має тип рядка.** Третє поле `hard`, `soft` або `-` (обидва одразу). Слово `unlimited` у полі `nofile` перетворюється не на нескінченність, а на вміст `/proc/sys/fs/nr_open`, бо вище за нього ліміт дескрипторів не піднімається.
- **`rss` у `limits.conf` не робить нічого**, як і сам `RLIMIT_RSS`. Рядок приймається й ігнорується.

## Що показує `/proc/<pid>/limits`

Файл існує від Linux 2.6.24, а від 2.6.36 його читає будь-хто, не тільки власник процесу — це найкоротший спосіб дізнатися, з чим служба справді працює, замість здогадів про те, що мало б успадкуватися ([/proc: процеси як файли](book:unix-linux/proc-filesystem) — вікна у внутрішній стан, які не займають місця на диску).

```
Limit                     Soft Limit           Hard Limit           Units
Max cpu time              unlimited            unlimited            seconds
Max file size             unlimited            unlimited            bytes
Max stack size            8388608              unlimited            bytes
Max open files            1024                 524288               files
Max processes             31573                31573                processes
Max nice priority         0                    0
```

Три властивості формату варто знати наперед. Значення завжди в **одиницях ядра** — байти, а не кілобайти. Замість числа може стояти слово `unlimited`. Останній стовпчик у рядках `Max nice priority` і `Max realtime priority` **порожній**, бо одиниці в них немає; розбирач, який жорстко чекає чотири поля, спіткнеться саме тут. Рядки йдуть точно в порядку номерів констант, тож на архітектурі зі своїм порядком і файл виглядатиме інакше.

Утиліта `prlimit(1)` із util-linux показує й міняє те саме за номером процесу, а також уміє запустити програму з новими межами. Її аргументи — теж в одиницях ядра:

```sh
prlimit --pid 1234                        # усі межі процесу таблицею
prlimit --pid 1234 --nofile               # тільки дескриптори
prlimit --pid 1234 --nofile=8192:16384    # м'яка:жорстка вже запущеному
prlimit --pid 1234 --nproc=512:           # тільки м'яку, жорстку лишити
prlimit --pid $$ --nproc=unlimited        # зняти межу собі
prlimit --cpu=10 sort -u величезний.txt   # запустити програму з межею
```

Пропущена частина пари означає «лишити як є»: `512:` міняє тільки м'яку, `:512` — тільки жорстку. Один із ключів `--pid` або команда обов'язковий; без них утиліта покаже власні межі.

## Мінімальний робочий виклик

Прочитати всі шістнадцять меж будь-якого процесу — те саме, що показує `/proc/<pid>/limits`, але через інтерфейс і в тих одиницях, у яких їх зберігає ядро:

```c
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>

static const struct { int res; const char *name; const char *unit; } LIMITS[] = {
    { RLIMIT_CPU,        "RLIMIT_CPU",        "с"       },
    { RLIMIT_FSIZE,      "RLIMIT_FSIZE",      "Б"       },
    { RLIMIT_DATA,       "RLIMIT_DATA",       "Б"       },
    { RLIMIT_STACK,      "RLIMIT_STACK",      "Б"       },
    { RLIMIT_CORE,       "RLIMIT_CORE",       "Б"       },
    { RLIMIT_RSS,        "RLIMIT_RSS",        "(мертвий)"},
    { RLIMIT_NPROC,      "RLIMIT_NPROC",      "задач"   },
    { RLIMIT_NOFILE,     "RLIMIT_NOFILE",     "шт."     },
    { RLIMIT_MEMLOCK,    "RLIMIT_MEMLOCK",    "Б"       },
    { RLIMIT_AS,         "RLIMIT_AS",         "Б"       },
    { RLIMIT_LOCKS,      "RLIMIT_LOCKS",      "(мертвий)"},
    { RLIMIT_SIGPENDING, "RLIMIT_SIGPENDING", "шт."     },
    { RLIMIT_MSGQUEUE,   "RLIMIT_MSGQUEUE",   "Б"       },
    { RLIMIT_NICE,       "RLIMIT_NICE",       "20−nice" },
    { RLIMIT_RTPRIO,     "RLIMIT_RTPRIO",     "пріор."  },
    { RLIMIT_RTTIME,     "RLIMIT_RTTIME",     "мкс"     },
};

static void fmt(rlim_t v, char *buf, size_t n)
{
    if (v == RLIM_INFINITY)             /* НЕ порівнювати з -1 чи ~0 */
        snprintf(buf, n, "unlimited");
    else
        snprintf(buf, n, "%llu", (unsigned long long)v);
}

int main(int argc, char **argv)
{
    pid_t pid = (argc > 1) ? (pid_t)atoi(argv[1]) : 0;   /* 0 — я сам */

    for (size_t i = 0; i < sizeof LIMITS / sizeof *LIMITS; i++) {
        struct rlimit rl;
        char soft[32], hard[32];

        if (prlimit(pid, LIMITS[i].res, NULL, &rl) != 0) {
            printf("%-18s  %s\n", LIMITS[i].name, strerror(errno));
            continue;
        }
        fmt(rl.rlim_cur, soft, sizeof soft);
        fmt(rl.rlim_max, hard, sizeof hard);
        printf("%-18s %12s %12s  %s\n",
               LIMITS[i].name, soft, hard, LIMITS[i].unit);
    }
    return 0;
}
```

`prlimit(pid, res, NULL, &rl)` з нульовим `new_limit` — це чистий «прочитати», причому для чужого процесу теж; `prlimit(0, …)` без `--pid` в утиліті й без аргументу тут означає «сам себе».

Другий типовий виклик — підняти собі м'яку межу під потребу програми, не намагаючись зачепити жорстку (на що прав немає) і не падаючи, якщо стеля виявиться нижчою за бажане:

```c
/* Довести м'який ліміт щонайменше до `want`, не вище виданої стелі.
   Повертає 0, якщо після виклику межа не менша за want, 1 — якщо стеля нижча. */
static int raise_soft(int resource, rlim_t want)
{
    struct rlimit rl;

    if (prlimit(0, resource, NULL, &rl) != 0)
        return -1;
    if (rl.rlim_cur == RLIM_INFINITY || rl.rlim_cur >= want)
        return 0;                       /* уже досить, нічого не робимо */

    int capped = 0;
    if (rl.rlim_max != RLIM_INFINITY && rl.rlim_max < want) {
        want = rl.rlim_max;             /* вище жорсткого не стрибнемо */
        capped = 1;
    }
    rl.rlim_cur = want;
    if (prlimit(0, resource, &rl, NULL) != 0)
        return -1;
    return capped;
}
```

Тут немає жодної спроби підняти `rlim_max`, і саме тому виклик не потребує ніяких прав: рух м'якої межі всередині жорсткої дозволено всім. Розрізняти три результати варто окремо — «дали скільки просив», «дали скільки було» і «зламалося»: друге зазвичай не привід зупинятися, а привід написати в журнал справжнє число, з яким програма далі житиме.

І дзеркальний виклик — незворотно опустити обидві межі перед тим, як віддати керування менш надійному коду:

```c
/* Замкнути ресурс на `value` назавжди: жорстку межу назад не піднімає
   вже ніхто всередині цього процесу. */
static int lock_down(int resource, rlim_t value)
{
    struct rlimit rl = { .rlim_cur = value, .rlim_max = value };
    return prlimit(0, resource, &rl, NULL);
}
```

`EINVAL` тут означає лише одне — `rlim_cur` більший за `rlim_max` у переданій структурі (або хибний номер ресурсу); `EPERM` при русі вниз не буває взагалі. Це і є та властивість, заради якої ліміти вживають як засіб безпеки: обіцянка, яку не можна відкликати.
