# 📋 Контракт clone і clone3: слово прапорців, поля clone_args, обгортка проти сирого виклику

Тут зібрано все, що треба знати, щоб покликати ці два системні виклики руками: три різні підписи, які легко сплутати, повний перелік прапорців із номерами версій ядра й забороненими сполученнями, розкладка структури `clone_args` разом із правилом її версіювання та коди помилок. Довідка потрібна в мить, коли код уже пишеться і треба точно знати, що передати, у якому порядку і що перевірити на поверненні.

## Три підписи, які роблять різні речі

```c
/* 1. Обгортка glibc — це не системний виклик, а функція поверх нього */
#define _GNU_SOURCE
#include <sched.h>
int clone(int (*fn)(void *), void *stack, int flags, void *arg,
          ... /* pid_t *parent_tid, void *tls, pid_t *child_tid */ );

/* 2. Сирий clone — порядок аргументів залежить від архітектури (нижче x86-64) */
#include <sys/syscall.h>
long syscall(SYS_clone, unsigned long flags, void *stack,
             int *parent_tid, int *child_tid, unsigned long tls);

/* 3. clone3 — обгортки в glibc немає взагалі, лише сирий виклик */
long syscall(SYS_clone3, struct clone_args *cl_args, size_t size);
```

| | обгортка `clone()` | сирий `SYS_clone` | `SYS_clone3` |
|---|---|---|---|
| як триває дитина | викликає `fn(arg)`; коли `fn` повернула, дитина завершується, і повернуте число стає її кодом виходу | виклик повертається вдруге, нулем — так само, як у `fork` | так само, як у сирого `clone` |
| стек | покажчик на **верхівку** ділянки, бо стек росте вниз; `NULL` не приймається | те саме поле й той самий сенс, але `NULL` **приймається** | `stack` — **найнижчий** байт, плюс окреме `stack_size` |
| номер сигналу | молодший байт `flags` | молодший байт `flags` | окреме поле `exit_signal` |
| ширина маски прапорців | `int` | `unsigned long` | `__u64` |
| невдача | `−1` і `errno` | `−1` і `errno` (через `syscall()`) | те саме |
| окремий шлях | на ia64 замість неї `__clone2` із базою й розміром стека | — | — |

Три рядки цієї таблиці варто прочитати уважно, бо на них ламаються найчастіше.

**Обгортка не повертається двічі.** Вона й не може: із `CLONE_VM` обидві задачі опиняються в одному адресному просторі, а два повернення в один стек означали б дві рамки викликів на тій самій пам'яті. Тому дитина стартує не «поверненням», а викликом функції `fn` на стеку, який їй дали. Наслідок практичний: стек обгортці треба виділити самому (`malloc`, `mmap` — байдуже), і передати саме його верхівку.

**Сирий виклик приймає `stack == NULL`.** Тоді дитина продовжується з тим самим покажчиком стека, що й батько, а окремі сторінки під стек з'являються звичайним [копіюванням при записі](book:unix-linux/copy-on-write) — ядро копіює не сторінки, а таблиці сторінок, і справжня копія кадру виникає лише при першому записі. Це і є те, як реалізовано `fork`: `clone(SIGCHLD)` без стека.

**Поле `flags` в обгортці має тип `int`.** Отже прапорці, що лежать вище 31-го біта, крізь неї не проходять навіть на 64-бітній машині — для них є тільки `clone3`.

## Порядок аргументів залежить від архітектури

Сирий `clone` — один із небагатьох викликів, у якого аргументи розкладені по регістрах по-різному на різних сімействах машин. Якщо ти кличеш його через `syscall()`, ця таблиця — твоя відповідальність, бо обгортка тут уже не допомагає ([системний виклик](book:unix-linux/syscall-mechanics) — програма кладе номер послуги й аргументи в регістри й переходить у ядро, тож «порядок аргументів» тут означає буквально порядок регістрів).

| архітектура | аргументи сирого `clone` |
|---|---|
| x86-64, SuperH, Alpha | `flags, stack, parent_tid, child_tid, tls` |
| x86-32, ARM, ARM64, MIPS, PowerPC, PA-RISC, Xtensa, ARC | `flags, stack, parent_tid, tls, child_tid` — переставлено два **останні** |
| s390, CRIS | `stack, flags, parent_tid, child_tid, tls` — переставлено два **перші** |
| MicroBlaze | `flags, stack, stack_size, parent_tid, child_tid, tls` — шість аргументів |
| ia64 | окремий виклик `__clone2`: `flags, stack_base, stack_size, parent_tid, child_tid, tls` |

Ця таблиця й пояснює, чому `clone3` мусив з'явитися саме як новий виклик, а не як розширення старого: дописати шостий аргумент до інтерфейсу, у якого п'ять аргументів лежать у чотирьох різних порядках, неможливо — доведеться правити чотири різні угоди одночасно й зламати їх усі.

## Слово прапорців: чому біти скінчилися

![Розкладка 64 бітів: молодший байт зайнятий номером сигналу, біти 8–31 роздані класичним прапорцям, усе вище 32-го доступне лише через clone3](/reference/unix-linux/processes/spawn-alternatives/img/clone-flag-word.svg)

*Молодший байт і набір прапорців — дві незалежні речі, які старий виклик склав в одне машинне слово; звідси й стеля.*

Маска `CSIGNAL` — це `0x000000ff`, молодші вісім бітів, у яких `clone` передає номер сигналу про завершення дитини. Класичні прапорці починаються з `CLONE_VM = 0x00000100` і закінчуються `CLONE_IO = 0x80000000`: двадцять чотири біти, роздані до останнього. Усе, що вище, — це `1ULL << 32` і далі, тобто діапазон, куди старий виклик не дотягується взагалі.

Один прапорець опинився не на своєму місці саме через цю тісноту: `CLONE_NEWTIME` дістав значення `0x00000080` — усередині маски сигналу, — тому його приймають лише `clone3` і `unshare`. Подробиці по кожному типу простору імен зібрані окремо: [інтерфейси просторів імен](book:unix-linux/namespaces/api-namespace-interfaces.md).

## Прапорці: повний перелік

Полярність запам'ятовується одним реченням: **прапорець піднято — ресурс спільний, прапорець опущено — у дитини власна копія**. Виняток — родина `CLONE_NEW*`, де піднятий прапорець означає «новий, окремий»: простори імен за замовчуванням саме успадковуються, тож питання там ставиться навпаки.

### Що стає спільним

| прапорець | значення | у ядрі з | що це означає |
|---|---|---|---|
| `CLONE_VM` | `0x00000100` | 2.0 | спільний адресний простір: усі відображення й кожен наступний `mmap`, `munmap`, `brk` видно обом |
| `CLONE_FS` | `0x00000200` | 2.0 | спільні корінь, робочий каталог і `umask`: `chdir`, `chroot`, `umask` в одному видно в іншому |
| `CLONE_FILES` | `0x00000400` | 2.0 | спільна таблиця дескрипторів: `open` і `close` в одному змінюють номери в іншому |
| `CLONE_SIGHAND` | `0x00000800` | 2.0 | спільна таблиця диспозицій сигналів; маски при цьому лишаються власними в кожного |
| `CLONE_THREAD` | `0x00010000` | 2.4.0 | одна група потоків: спільний номер від `getpid()`, і про завершення такої задачі сигнал не надсилається нікому |
| `CLONE_SYSVSEM` | `0x00040000` | 2.5.10 | спільний список поправок `semadj` для семафорів System V |
| `CLONE_IO` | `0x80000000` | 2.6.25 | спільний контекст планувальника блокового вводу-виводу |
| `CLONE_VFORK` | `0x00004000` | 2.2 | не ресурс, а режим: той, хто кликав, спиняється до `execve` або `_exit` дитини |
| `CLONE_PARENT` | `0x00008000` | 2.3.12 | не ресурс, а родовід: батьком дитини стає батько того, хто кликав, — сигнал про завершення піде йому |

`CLONE_THREAD` тут головний за силою наслідків: він не «створює потік», а лише заносить нову задачу в наявну групу, і саме з цього беруться однаковий `getpid()` та спільна доля при сигналах ([одиниця планування в Linux одна](book:unix-linux/threads-as-tasks) — процес і потік різняться лише набором прапорців, а не механізмом).

### Записи в пам'ять і дескриптори

| прапорець | значення | у ядрі з | що це означає |
|---|---|---|---|
| `CLONE_SETTLS` | `0x00080000` | 2.5.32 | поставити дитині блок даних, локальних до потоку (аргумент `tls`) |
| `CLONE_PARENT_SETTID` | `0x00100000` | 2.5.49 | записати номер дитини за адресою `parent_tid` ще до повернення з виклику |
| `CLONE_CHILD_SETTID` | `0x01000000` | 2.5.49 | записати номер дитини за адресою `child_tid` у її власній пам'яті |
| `CLONE_CHILD_CLEARTID` | `0x00200000` | 2.5.49 | коли дитина завершиться — обнулити те слово й розбудити на ньому ф'ютекс |
| `CLONE_PIDFD` | `0x00001000` | 5.2 | покласти дескриптор на дитину: у `clone()` — за `parent_tid`, у `clone3()` — за `pidfd` |
| `CLONE_CLEAR_SIGHAND` | `1 << 32` | 5.5 | скинути всі перехоплені сигнали в `SIG_DFL`; лише `clone3` |
| `CLONE_INTO_CGROUP` | `1 << 33` | 5.7 | народити одразу в групі, дескриптор якої лежить у полі `cgroup`; лише `clone3` |

Останні три рядки — це та частина переліку, заради якої `clone3` і робили. `CLONE_INTO_CGROUP` знімає проміжок, у якому дитина вже виконується, а обмежень [контрольної групи](book:unix-linux/cgroups) на неї ще не наклали.

`CLONE_CHILD_CLEARTID` виглядає дрібницею, але на ньому стоїть увесь `pthread_join`: бібліотека дає ядру адресу слова, а сама лягає чекати на [ф'ютексі](book:unix-linux/eventfd-and-futex) за тією ж адресою — дешевому замку, який іде в ядро лише тоді, коли справді треба заснути. Ядро обнуляє слово й будить чекальника без жодного сигналу.

Про `CLONE_PIDFD` варто знати одну річ понад таблицю: у старому `clone()` дескриптор віддається через той самий аргумент `parent_tid`, тому з `CLONE_PARENT_SETTID` він несумісний. Решта інтерфейсу дескрипторів на процес — окремо: [довідка інтерфейсів іменування](book:unix-linux/pid-and-hierarchy/api-pid-interfaces.md).

### Трасування й вилучене

| прапорець | значення | у ядрі | що це означає |
|---|---|---|---|
| `CLONE_PTRACE` | `0x00002000` | з 2.2 | якщо того, хто кликав, трасують, — трасувати й дитину |
| `CLONE_UNTRACED` | `0x00800000` | з 2.5.46 | заборонити тому, хто трасує, нав'язати дитині `CLONE_PTRACE` |
| `CLONE_DETACHED` | `0x00400000` | ігнорується з 2.6.2 | нічого; у `clone3` дає `EINVAL` |
| `CLONE_STOPPED` | — | 2.6.0 … 2.6.38 | дитина стартувала спиненою; позначено застарілим у 2.6.25, вилучено в 2.6.38 |
| `CLONE_PID` | — | 2.0 … 2.5.15 | дитина з тим самим номером, що й батько; вилучено |

### Простори імен

| прапорець | значення | у ядрі з | власним стає |
|---|---|---|---|
| `CLONE_NEWNS` | `0x00020000` | 2.4.19 | дерево монтувань |
| `CLONE_NEWUTS` | `0x04000000` | 2.6.19 | ім'я вузла й ім'я домену |
| `CLONE_NEWIPC` | `0x08000000` | 2.6.19 | об'єкти System V і черги повідомлень POSIX |
| `CLONE_NEWUSER` | `0x10000000` | заготовка з 2.6.23, придатний з 3.8 | ідентифікатори користувачів і набір можливостей |
| `CLONE_NEWPID` | `0x20000000` | 2.6.24 | номери процесів |
| `CLONE_NEWNET` | `0x40000000` | 2.6.24 | інтерфейси, адреси, маршрути, порти |
| `CLONE_NEWCGROUP` | `0x02000000` | 4.6 | точка, від якої видно ієрархію обмежень |
| `CLONE_NEWTIME` | `0x00000080` | 5.6 | монотонні годинники; лише `clone3` і `unshare` |

Простір над 33-м бітом уже заповнюється далі: у поточному дереві ядра в заголовку `include/uapi/linux/sched.h` стоять `CLONE_AUTOREAP` (`1ULL << 34`), `CLONE_NNP` (`1ULL << 35`, ставить дитині `no_new_privs` — засув, після якого [фільтр системних викликів](book:unix-linux/seccomp-filtering) уже не обійти через `setuid`-програму), `CLONE_PIDFD_AUTOKILL` (`1ULL << 36`) і `CLONE_EMPTY_MNTNS` (`1ULL << 37`). Це найсвіжіший шар, тож номер ядра для кожного звіряй за самим заголовком, а не за пам'яттю.

## Заборонені сполучення

Кожен рядок нижче дає `EINVAL`.

| сполучення | чому саме так |
|---|---|
| `CLONE_SIGHAND` без `CLONE_VM` (з 2.6.0) | таблиця диспозицій зберігає адреси функцій; спільною вона має сенс лише там, де адреси в обох означають те саме |
| `CLONE_THREAD` без `CLONE_SIGHAND` (з 2.5.35) | потоки однієї групи мусять реагувати на сигнал як одне ціле |
| `CLONE_SIGHAND` разом із `CLONE_CLEAR_SIGHAND` | одна вимога каже «поділи таблицю», друга — «обнули її»; виконати обидві неможливо |
| `CLONE_FS` разом із `CLONE_NEWNS` | нове дерево монтувань і спільний із чужим процесом корінь суперечать одне одному |
| `CLONE_NEWUSER` разом із `CLONE_FS` (з 3.9) | спільний корінь дав би шлях повз межу нового простору |
| `CLONE_NEWIPC` разом із `CLONE_SYSVSEM` | поправки `semadj` посилаються на семафори реєстру, який щойно став іншим |
| `CLONE_NEWPID` разом із `CLONE_THREAD` або `CLONE_PARENT` | усі потоки групи мусять жити в одному просторі номерів |
| `CLONE_NEWUSER` разом із `CLONE_THREAD` | потоки одного процесу мусять мати спільну ідентичність |
| `CLONE_PIDFD` разом із `CLONE_PARENT_SETTID` у `clone()` | обидва повертають результат через той самий аргумент `parent_tid` |
| `CLONE_PIDFD` разом із `CLONE_DETACHED` у `clone()` | мертвий біт поруч із новим прапорцем — ознака випадкового значення, і ядро відмовляє замість того, щоб мовчки його проковтнути |
| `CLONE_DETACHED` у `clone3` | у новому виклику невідомих і мертвих бітів не приймають узагалі |

## struct clone_args: поля, зсуви, версії

![Одинадцять полів по вісім байтів кожне, зсуви від 0 до 80; праворуч три розміри-версії: 64 для ядра 5.3, 80 для 5.5, 88 для 5.7](/reference/unix-linux/processes/spawn-alternatives/img/clone-args-layout.svg)

*Структура росте лише в хвіст, і кожен приріст має власний розмір; аргумент `size` — це і є те, чим версії домовляються між собою.*

```c
struct clone_args {
    __aligned_u64 flags;
    __aligned_u64 pidfd;
    __aligned_u64 child_tid;      /* увага: спершу child, потім parent —    */
    __aligned_u64 parent_tid;     /* у сирому clone порядок саме зворотний  */
    __aligned_u64 exit_signal;
    __aligned_u64 stack;          /* найнижчий байт, а не верхівка          */
    __aligned_u64 stack_size;
    __aligned_u64 tls;
    __aligned_u64 set_tid;        /* з 5.5 */
    __aligned_u64 set_tid_size;   /* з 5.5 */
    __aligned_u64 cgroup;         /* з 5.7 */
};
```

Три речі тут ловлять навіть уважних.

**Усі поля — `__aligned_u64`, зокрема ті, що насправді є вказівниками.** Записувати треба через подвійне перетворення: `args.pidfd = (__u64)(uintptr_t)&pidfd`. Це не примха: розкладка структури мусить бути однакова для 32- і 64-бітної програми на одному ядрі, а вказівник такої гарантії не дає.

**`exit_signal` винесено в окреме поле.** Тому `flags` тут — чисті прапорці, без домішку номера сигналу, і саме тому в `clone3` поміщається все, що не влізло в старий виклик. Значення в цьому полі має ту саму умову, що й молодший байт у `clone`: якщо там не `SIGCHLD`, батько мусить чекати на дитину з `__WALL` або `__WCLONE` ([очікування й зомбі](book:unix-linux/exit-wait-zombies) — доки батько не забрав код виходу, запис про мертву дитину лишається в таблиці процесів).

**`set_tid` читається зсередини назовні.** `set_tid[0]` — бажаний номер у найглибшому просторі, тому, де дитина народжується; останній елемент — у найзовнішньому. Потрібен [`CAP_SYS_ADMIN`](book:unix-linux/capabilities) — або, з ядра 5.9, вужчий `CAP_CHECKPOINT_RESTORE` — у власницькому просторі користувачів кожного зі згаданих просторів номерів; можливість тут окрема від «бути root», а зайнятий номер дає `EEXIST`. Заради цього поля половина `clone3` і робилася: без нього відновити процес із контрольної точки під тим самим номером неможливо.

Розмір структури керується аргументом `size`, і правило читається так:

```
size < 64                     → EINVAL   (менше за CLONE_ARGS_SIZE_VER0)
size > розмір сторінки        → E2BIG
size < того, що знає ядро     → відсутні поля ядро вважає нулями
size > того, що знає ядро     → хвіст мусить бути нульовим, інакше E2BIG
```

Три опубліковані розміри: `CLONE_ARGS_SIZE_VER0 = 64` (ядро 5.3), `VER1 = 80` (5.5, поява `set_tid`), `VER2 = 88` (5.7, поява `cgroup`).

> 🔧 **Навіщо це.** Практичний висновок один: передавай `sizeof(struct clone_args)` із того заголовка, з яким збираєшся, і ніколи не зашивай число руками. Зібрана з новим заголовком програма працюватиме й на старому ядрі — бо хвіст, який те ядро не знає, у неї нульовий, а нуль означає «як було». І навпаки: старій програмі на новому ядрі бракуючі поля добиваються нулями. Це той самий [розширюваний двійковий контракт](book:unix-linux/userspace-abi-stability), на якому тримається сумісність між ядром і програмами в обидва боки; зашите `64` ламає його першим же оновленням заголовків.

## Коди помилок

| код | коли |
|---|---|
| `EINVAL` | заборонене сполучення прапорців (таблиця вище); `size` менший за 64; невалідні номери в `set_tid`; `set_tid_size` більший за глибину вкладення просторів номерів |
| `E2BIG` | `size` більший за розмір сторінки; або `size` більший за відомий ядру, а хвіст ненульовий — тобто «ядро не вміє того, що ти просиш» |
| `EEXIST` | один із номерів у `set_tid` уже зайнятий |
| `EPERM` | `set_tid_size` більший за нуль, а ні `CAP_SYS_ADMIN`, ні `CAP_CHECKPOINT_RESTORE` у відповідному просторі користувачів немає; або немає прав на простір імен |
| `EACCES` | `CLONE_INTO_CGROUP`: немає доступу до вказаної групи |
| `EBUSY` | `CLONE_INTO_CGROUP`: у цільовій групі увімкнено контролер домену |
| `EOPNOTSUPP` | `CLONE_INTO_CGROUP`: група в непридатному для цього стані |
| `ENOSPC` | вичерпано межу вкладеності просторів номерів або межу просторів користувачів |
| `EAGAIN` | забагато процесів: `RLIMIT_NPROC` або загальносистемна межа |
| `ENOMEM` | не вистачило пам'яті ядра на структури нової задачі |
| `ENOSYS` | `clone3` на ядрі, старішому за 5.3 |

## Мінімальний виклик, що працює і на старому ядрі

```c
/* spawn3.c — clone3 з відступом на clone, коли ядро надто старе.
 *   gcc -O2 -Wall -o spawn3 spawn3.c && ./spawn3
 * Підключаємо саме <linux/sched.h>: прапорці визначені і в ньому,
 * і в glibc-івському <sched.h>, тож обидва разом брати не варто.
 * P_PIDFD у waitid — це glibc 2.32 і ядро 5.4.
 */
#define _GNU_SOURCE
#include <errno.h>
#include <linux/sched.h>
#include <linux/types.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>

static long spawn_task(int *pidfd_out)
{
    struct clone_args args = {
        .flags       = CLONE_PIDFD | CLONE_CLEAR_SIGHAND,
        .pidfd       = (__u64)(uintptr_t)pidfd_out,
        .exit_signal = SIGCHLD,
    };
    long pid = syscall(SYS_clone3, &args, sizeof args);
    if (pid >= 0 || (errno != ENOSYS && errno != EINVAL && errno != E2BIG))
        return pid;                 /* або вийшло, або зламалося по суті */

    /* ENOSYS — ядро старіше за 5.3; EINVAL — воно не знає CLONE_CLEAR_SIGHAND;
       E2BIG — заголовок новіший за ядро. Відступаємо на старий виклик:
       CLONE_PIDFD там є з 5.2, але дескриптор віддається через parent_tid. */
    return syscall(SYS_clone, (unsigned long)(CLONE_PIDFD | SIGCHLD),
                   NULL, pidfd_out, NULL, 0UL);      /* порядок для x86-64 */
}

int main(void)
{
    int pidfd = -1;
    long pid = spawn_task(&pidfd);
    if (pid < 0) { perror("clone"); return 1; }

    if (pid == 0) {                 /* сирий виклик повертається двічі */
        execlp("id", "id", (char *)NULL);
        _exit(127);
    }

    siginfo_t info;
    if (waitid(P_PIDFD, (id_t)pidfd, &info, WEXITED) == 0)
        printf("дитина %d вийшла з кодом %d\n", info.si_pid, info.si_status);
    close(pidfd);
    return 0;
}
```

```cpp
#define _GNU_SOURCE
#include <errno.h>
#include <linux/sched.h>
#include <linux/types.h>
#include <signal.h>
#include <stdint.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>
#include <iostream>
#include <system_error>

class UniquePidFd {
    int fd_{-1};
public:
    constexpr UniquePidFd() noexcept = default;
    explicit UniquePidFd(int fd) noexcept : fd_(fd) {}
    ~UniquePidFd() { reset(); }

    UniquePidFd(const UniquePidFd&) = delete;
    UniquePidFd& operator=(const UniquePidFd&) = delete;

    UniquePidFd(UniquePidFd&& other) noexcept : fd_(other.release()) {}
    UniquePidFd& operator=(UniquePidFd&& other) noexcept {
        if (this != &other) reset(other.release());
        return *this;
    }

    void reset(int new_fd = -1) noexcept {
        if (fd_ >= 0) ::close(fd_);
        fd_ = new_fd;
    }
    [[nodiscard]] int release() noexcept {
        int old = fd_;
        fd_ = -1;
        return old;
    }
    [[nodiscard]] int get() const noexcept { return fd_; }
    [[nodiscard]] int* ptr() noexcept { return &fd_; }
};

static long spawn_task(int *pidfd_out) {
    struct clone_args args{};
    args.flags = CLONE_PIDFD | CLONE_CLEAR_SIGHAND;
    args.pidfd = static_cast<__u64>(reinterpret_cast<uintptr_t>(pidfd_out));
    args.exit_signal = SIGCHLD;

    long pid = ::syscall(SYS_clone3, &args, sizeof(args));
    if (pid >= 0 || (errno != ENOSYS && errno != EINVAL && errno != E2BIG)) {
        return pid;
    }

    return ::syscall(SYS_clone, static_cast<unsigned long>(CLONE_PIDFD | SIGCHLD),
                     nullptr, pidfd_out, nullptr, 0UL);
}

int main() {
    UniquePidFd pidfd;
    long pid = spawn_task(pidfd.ptr());
    if (pid < 0) {
        std::cerr << "clone помилка: " << std::generic_category().message(errno) << '\n';
        return 1;
    }

    if (pid == 0) {
        ::execlp("id", "id", static_cast<char*>(nullptr));
        ::_exit(127);
    }

    siginfo_t info{};
    if (::waitid(P_PIDFD, static_cast<id_t>(pidfd.get()), &info, WEXITED) == 0) {
        std::cout << "дитина " << info.si_pid << " вийшла з кодом " << info.si_status << '\n';
    }
    return 0;
}
```

Дві деталі в цьому коді неочевидні. По-перше, стек не виділяється зовсім: `stack` лишається нулем, `CLONE_VM` не піднято — отже дитина продовжується на дублі стека батька, як після `fork`. По-друге, `CLONE_CLEAR_SIGHAND` тут навмисний: сам по собі він зайвий, бо `execlp` і так скине обробники, — але він існує лише в `clone3`, тому саме на ньому й видно, як має виглядати відступ на старий виклик. У бойовому коді умову відступу треба звужувати до тих прапорців, які ти справді просиш: `EINVAL` від `clone3` означає не тільки «ядро старе», а й «ти передав заборонене сполучення», і відступати на `clone` у другому випадку — значить сховати власну помилку.

## Внутрішня анатомія ядра: як прапорці керують `task_struct`

Кожен прапорець `clone` має пряме втілення у структурі описувача задачі `task_struct` всередині ядра Linux (`kernel/fork.c`). Під час виконання системного виклику функція `copy_process()` перевіряє бітову маску й ухвалює рішення щодо кожного вказівника на внутрішні ресурси:

- `CLONE_VM`: якщо виставлено, `p->mm = current->mm`, і атомарний лічильник користувачів пам'яті `mm_users` збільшується. Якщо ні — кличеться `dup_mm()`, яка виділяє нову структуру `mm_struct`, переносить у неї опис кожної області пам'яті (`vm_area_struct`) і копіює таблиці сторінок.
- `CLONE_FILES`: якщо виставлено, `p->files = current->files`, і лічильник посилань `count` збільшується. Якщо ні — кличеться `dup_fd()`, яка робить глибоку копію масиву файлових дескрипторів.
- `CLONE_FS`: якщо виставлено, `p->fs = current->fs`, що робить спільними покажчики на кореневий каталог, робочий каталог і `umask`. Якщо ні — кличеться `copy_fs_struct()`.
- `CLONE_SIGHAND`: якщо виставлено, `p->sighand = current->sighand`. Якщо ні — виділяється нова структура `sighand_struct` із копією обробників сигналів.
- `CLONE_NEW*`: якщо виставлено хоча б один із просторів імен, кличеться `copy_namespaces()`, яка виділяє нову структуру `nsproxy` із новими екземплярами відповідних підсистем.

Простежити ці переходи на живій системі можна через інструменти трасування (`perf trace -e syscalls:sys_enter_clone,syscalls:sys_enter_clone3`) або огляд `/proc/<pid>/status`, де поля `Threads`, `NStid`, `VmPTE` відображають остаточний стан розгалуженої задачі.

### Відображення прапорців у /proc та системні виклики pidfd

Після виконання `clone` або `clone3` стан створеної задачі простежується через псевдофайлову систему `/proc`:

- `/proc/<pid>/status`:
  - `Threads` — кількість задач у даній групі потоків (зростає при `CLONE_THREAD`).
  - `NStid` — ієрархія ідентифікаторів задачі у всіх вкладених просторах номерів PID (заповнюється при `CLONE_NEWPID` та `set_tid`).
  - `Seccomp` — режим фільтрації системних викликів (передається дитині, якщо не скинуто).
- `/proc/<pid>/fd/` — показує відкриті дескриптори. Якщо піднято `CLONE_FILES`, масив inode у цій теці є спільним із батьківським процесом.

Отриманий при прапорці `CLONE_PIDFD` дескриптор процесу відкриває доступ до трьох системних викликів для безпечного керування дитиною без гонитви за номером, який ядро могло вже перевидати:

1. `pidfd_send_signal(int pidfd, int sig, siginfo_t *info, unsigned int flags)` — надсилає сигнал саме тій задачі, яка пов'язана з дескриптором, навіть якщо її оригінальний `pid_t` уже перевидано іншому процесу.
2. `pidfd_open(pid_t pid, unsigned int flags)` — отримує `pidfd` для вже наявного процесу.
3. `pidfd_getfd(int pidfd, int targetfd, unsigned int flags)` — дублює файловий дескриптор `targetfd` із цільового процесу у свій власний список. Операція вимагає привілеїв `PTRACE_MODE_ATTACH_REALCREDS` (перевірка прав на трасування цільового процесу).

Виклик `pidfd_getfd` особливо цінний для середовищ виконання контейнерів та системних демонів (як-от systemd): він дозволяє витягти відкритий сокет або файл із дитини без співпраці з її боку й без небезпечних проміжків гонитви за нове ім'я. Завдяки цим викликам системне програмування в Linux позбулося давньої проблеми точок гонитви при роботі з короткими процесами.
