Сервер баз даних високого навантаження виконує критичні транзакції користувачів, поки поруч у тій самій системі фоновий процес робить нічне резервне копіювання. Програма копіювання зчитує сотні гіробайтів файлів, заповнюючи сторінковий кеш ядра (page cache) модифікованими даними. Коли алгоритм згортання пам'яті вимагає скинути «брудні» сторінки на диск, ядро запускає фонові потоки запису `kworker`. Якщо у цей момент обмеження дискового вводу-виводу та ліміти оперативної пам'яті працюють як незалежні підсистеми, ядро втрачає зв'язок між тим, **хто** згенерував брудні сторінки, і тим, **хто** їх фізично пише на диск. Потоки `kworker` перевантажують чергу блокового пристрою від імені кореневої системи, спричиняючи важку інверсію пріоритетів: транзакції бази даних зависають в очікуванні диска, хоча сама база даних не перевищила жодного власного ліміту.

Ця масштабна інженерна проблема була неминучим наслідком першої версії підсистеми Control Groups (cgroups v1). У ній кожен ресурсний контролер — процесорний (`cpu`), пам'яті (`memory`), блокового вводу-виводу (`blkio`) — існував у вигляді окремого дерева файлової системи. Процес міг перебувати в одній групі для планувальника CPU і зовсім в іншій для обліку пам'яті. Неможливість надійної координації між контролерами ядра та важкі конфлікти блокувань при створенні процесів призвели до фундаментальної реформації підсистеми. [Історія виникнення та реформації cgroups](book:unix-linux/cgroups-v2-unified-hierarchy/hist-cgroups-v1-v2-evolution.md) детально показує шлях від ортогональних ієрархій 2006 року до створення єдиного дерева.

## 1. Концепція єдиної ієрархії (Unified Hierarchy)

У cgroups v2 розробники ядра Linux відмовилися від множинних незалежних дерев. У системі існує лише **одне єдине дерево ієрархії**, яке монтується як віртуальна файлова система типу `cgroup2` за стандартним шляхом `/sys/fs/cgroup`:

```bash
mount -t cgroup2 none /sys/fs/cgroup
```

Під час монтування файлової системи `cgroup2` ядро підтримує спеціальні прапорці монтування VFS. Прапорець `nsdelegate` вмикає безпечне делегування для просторів імен користувачів (user namespaces), автоматично захищаючи внутрішні контролерні файли від модифікації зсередини контейнера. Прапорець `memory_localevents` змушує файли `memory.events` відображати події лише конкретного вузла без агрегації статистики дочірніх піддерев. Додатковий параметр `memory_recursive_prot` активує рекурсивне успадкування порогів захисту `memory.min` та `memory.low` по всій глибині вкладеності дочірніх груп.

У цій моделі будь-який процес системи належить виключно до **однієї** cgroup у кожен момент часу. Не існує ситуації, коли процес перебуває у групі A для контролера пам'яті і в групі B для контролера диска.

![Порівняння розрізнених ієрархій v1 та єдиного дерева v2](/reference/unix-linux/processes/cgroups-v2-unified-hierarchy/img/v1-vs-v2.svg)
*У cgroups v1 кожен контролер будував власне дерево й не бачив сусідів; у v2 існує єдина ієрархія, де всі контролери об'єднані спільною структурою вузлів.*

### 1.1 Структури ядра та зв'язок із задачами

Всередині ядра Linux єдина ієрархія спирається на три фундаментальні структури даних:

1. `struct cgroup`: Представляє вузол у файловій системі `cgroup2`. Вона містить списки дочірніх груп, вказівник на батьківський вузол, лічильники синівських процесів та масив станів контролерів.
2. `struct cgroup_subsys_state` (css): Конкретний стан конкретного контролера (наприклад, `memory_cgroup` чи `task_group` для CPU), прив'язаний до вузла `cgroup`.
3. `struct css_set`: Об'єднувальна структура, на яку посилається кожен процес (`struct task_struct->cgroups`). У v2, завдяки єдиній ієрархії, кількість унікальних комбінацій `css_set` у системі кардинально зменшилася.

Коли процес викликає `fork()` або `clone()`, дочірня задача автоматично успадковує `css_set` батьківського процесу. Переміщення процесу у нову cgroup виконується шляхом атомарного запису його PID у керуючий файл `cgroup.procs` відповідної директорії. Ядро оновлює вказівник `task_struct->cgroups` під захистом RCU (Read-Copy-Update), що гарантує відсутність затримок при зчитуванні стану cgroup іншими ядрами CPU.

Під час переміщення процесів між групами ядро гарантує атомарність: якщо процес має сотні потоків (threads), запис PID у `cgroup.procs` атомарно переводить усю групу потоків (thread group) до нового `css_set`. Це виконується під захистом ядерного блокування `cgroup_threadgroup_change_lock`, запобігаючи ситуаціям, коли частину потоків переміщено, а частина залишилася у попередній cgroup.

Додатково ядро відстежує життєвий цикл зомбі-процесів та процесів, які знаходяться на стадії вилучення (`dying tasks`). Коли процес завершується викликом `exit()`, його `struct task_struct` тимчасово залишається у списку `cgroup.stat` у полі `nr_dying_descendants` до тих пір, поки батьківський процес не прочитає код повернення викликом `waitpid()`. Це гарантує точність статистичного обліку ресурсів до повного звільнення ядерних структур.

### 1.2 Принцип контролю згори донизу (Top-Down Constraint)

На відміну від v1, де контролер був доступний одразу після монтування усім вузлам свого дерева, у cgroups v2 діє строгий принцип розподілу ресурсів **згори донизу (Top-Down Control)**.

Будь-яка cgroup отримує доступ до ресурсного контролера лише у тому випадку, якщо цей контролер був послідовно активований у всіх її батьківських вузлах, починаючи від кореневого `/sys/fs/cgroup`.

Активація контролерів для дочірніх груп виконується через керуючий файл `cgroup.subtree_control`. Запис рядка з префіксом `+` вмикає контролер для дочірнього рівня, а префікс `-` вимикає його:

```bash
# Перевірка доступних контролерів у батьківському вузлі
cat /sys/fs/cgroup/production/cgroup.controllers
# Вивід: cpuset cpu io memory pids

# Активація контролерів пам'яті та диска для піддерева production
echo "+memory +io" > /sys/fs/cgroup/production/cgroup.subtree_control
```

Якщо контролер `memory` не активовано в `production/cgroup.subtree_control`, жодна дочірня група (наприклад, `/sys/fs/cgroup/production/backend`) не зможе скористатися файлами `memory.max` чи `memory.high`. Це гарантує цілісність адміністраторської політики: вищий рівень ієрархії повністю контролює межі повноважень своїх піддерев. [Повний довідник керуючих файлів cgroupv2](book:unix-linux/cgroups-v2-unified-hierarchy/api-cgroup2-control-surface.md) описує детальний перелік усіх інтерфейсних файлів для кожного контролера.

## 2. Правило відсутності внутрішніх процесів (No Internal Processes)

Найважливішим архітектурним обмеженням cgroups v2, яке гарантує математичну точність розподілу ресурсів, є правило **No Internal Processes**.

**Суть правила**: Некоренева cgroup не може одночасно розподіляти ресурси між дочірніми підгрупами (тобто мати увімкнені контролери у своєму `cgroup.subtree_control`) **і** містити процеси у своєму файлі `cgroup.procs`.

Таким чином, будь-який некореневий вузол у cgroups v2 належить до одного з двох чітко розмежованих типів:
- **Внутрішній вузол (Internal Node)**: Його файл `cgroup.subtree_control` непорожній (активовані контролери для дітей), але його файл `cgroup.procs` є порожнім. Внутрішній вузол оперує виключно як магістральний шлюз для розподілу ресурсів між своїми дочірніми групами.
- **Листовий вузол (Leaf Node)**: Його файл `cgroup.subtree_control` порожній, але файл `cgroup.procs` містить PID процесів. Листовий вузол виконує роль безпосереднього контейнера для виконання задач.

![Правило відсутності внутрішніх процесів у некореневих вузлах](/reference/unix-linux/processes/cgroups-v2-unified-hierarchy/img/no-internal-processes.svg)
*Некореневий вузол є або внутрішнім (розподіляє ресурси між дочірніми групами), або листовим (містить процеси). Суміщення процесів і активних дочірніх контролерів у cgroups v2 заборонено.*

### 2.1 Математичне обґрунтування правила

У cgroups v1 некоренева група могла одночасно містити і дочірні cgroups, і власні процеси. Коли контролер розраховував пропорційний розподіл CPU (наприклад, вагу CFS) або пропускну здатність диска, виникала неоднозначність: як зіставити процес, що лежить безпосередньо у батьківському вузлі, із цілою дочірньою групою?

Планувальнику доводилося розглядати процеси батьківського вузла як якусь уявну «неявну дочірню групу». Це призводило до викривлення математичних ваг: процеси у батьківській cgroup отримували невиправдану перевагу над процесами у дочірніх вузлах, або навпаки.

У cgroups v2 ця неоднозначність усунута на рівні ядра. Змагання за ресурси завжди відбувається **виключно між сусідніми вузлами одного рівня** (siblings):
- На верхньому рівні внутрішній вузол A змагається з внутрішнім вузлом B.
- Всередині вузла A листова група Leaf1 змагається з листовою групою Leaf2.

### 2.2 Дотримання правила ядром та винятки

Якщо спробувати записати PID у файл `cgroup.procs` внутрішнього вузла, у якого вже активовані контролери в `cgroup.subtree_control`, системний виклик `write()` поверне помилку `EBUSY` (Device or resource busy). Аналогічно, якщо у групі вже є процеси, спроба записати `+memory` у `cgroup.subtree_control` завершиться помилкою `EBUSY`.

```bash
# Спроба порушити правило No Internal Processes
mkdir /sys/fs/cgroup/app
echo "+memory" > /sys/fs/cgroup/app/cgroup.subtree_control

# Запис PID у батьківський вузол викликає помилку EBUSY!
echo $$ > /sys/fs/cgroup/app/cgroup.procs
# bash: echo: write error: Device or resource busy
```

**Офіційні винятки з правила**:
1. **Коренева cgroup (`/sys/fs/cgroup`)**: Кореневий вузол може одночасно містити процеси (наприклад, системні демони ядра) та розподіляти ресурси для дочірніх системних зрізів (`system.slice`, `user.slice`).
2. **Контролери без розподілу доменів**: Деякі контролери (наприклад, `pids`) вимірюють лише абсолютну кількість ресурсів і не виконують пропорційного вирівнювання дерев, однак для узгодженості інтерфейсу система оперує однаково для всіх.
3. **Threaded Mode (Потоковий режим)**: Для мов програмування з вираженою багатопотоковістю (Java, Go, Rust) cgroups v2 надає можливість переводити окремі піддерева у потоковий режим (`cgroup.type = threaded`). Це дозволяє розподіляти окремі потоки (`TID`) одного процесу по дочірніх листових вузлах для контролерів `cpu` та `cpuset`, зберігаючи при цьому спільні доменні контролери `memory` та `io` на рівні основного процесу.

Потоковий режим організує піддерева за схемою `domain threaded root`. Батьківський вузол виступає доменним коренем для ресурсів пам'яті та вводу-виводу, а дочірні потокові cgroups обробляють окремі `TID` через `cgroup.threads`, що дозволяє задавати індивідуальні ваги `cpu.weight` для різних робітників у межах одного процесу.

Для заморожування процесів піддерева cgroups v2 надає файл `cgroup.freeze`. Запис `1` у цей файл переводить внутрішню функцію ядра `cgroup_freeze_task()` у стан призупинення виконання. На відміну від сигналів `SIGSTOP`, які можуть бути перехоплені або виявлені програмою, ядерне заморожування є повністю прозорим: процеси зупиняються без зміни стану обробників сигналів і відновлюються атомарно при записі `0` у `cgroup.freeze`.

## 3. Детальний розбір ресурсних контролерів у cgroups v2

Контролери у v2 зазнали глибинної переробки для забезпечення прозорого обліку та усунення дублювання метрик.

### 3.1 Контролер процесора (`cpu`)

Контролер `cpu` у v2 об'єднав функціональність двох окремих v1-контролерів: `cpu` (планування часу) та `cpuacct` (облік використання).

Головні керуючі файли:
- **`cpu.weight`**: Замінює застаріле поле `cpu.shares`. Встановлює відносну вагу cgroup у діапазоні від `1` до `10000` (за замовчуванням `100`). Якщо група A має вагу `200`, а група B має вагу `100`, то при 100% завантаженні CPU група A отримає 66.6% процесорного часу, а група B — 33.3%.
- **`cpu.max`**: Замінює пару файлів `cpu.cfs_quota_us` та `cpu.cfs_period_us`. Формат запису: `$MAX $PERIOD`.
  - `$MAX` — дозволена квота процесорного часу в мікросекундах у межах періоду (або рядок `max` для скасування обмежень).
  - `$PERIOD` — тривалість самого періоду (за замовчуванням `100000` мкс, тобто 100 мілісекунд).
  - Приклад `200000 100000` надає cgroup еквівалент 2 повних ядер CPU.
- **`cpu.stat`**: Надає розширену статистику у мікросекундах: `usage_usec` (загальний час), `user_usec` (час у юзер-просторі), `system_usec` (час у ядрі), а також `nr_throttled` та `throttled_usec` (кількість та тривалість обмежень через вичерпання квоти).

Додатково у cgroups v2 реалізовано підтримку сплесків квотування (`cpu.max.burst`). Якщо cgroup протягом попередніх періодів не використовувала свою максимальну квоту, вона накопичує кредит часу, який дозволяє перевищити `$MAX` під час коротких сплесків обчислювального навантаження без переведення процесів у стан призупинення.

### 3.2 Контролер прив'язки процесорів та вузлів NUMA (`cpuset`)

Контролер `cpuset` обмежує виконання задач cgroup конкретними фізичними ядрами CPU та конкретними вузлами оперативно пам'яті у багатопроцесорних архітектурах NUMA (Non-Uniform Memory Access).

Основні керуючі файли `cpuset`:
- **`cpuset.cpus`**: Маска дозволених ядер CPU. Формат запису: діапазони або списки ядер (наприклад `0-3,8-11`).
- **`cpuset.mems`**: Маска дозволених вузлів пам'яті NUMA (наприклад `0,1`).
- **`cpuset.cpus.effective`** та **`cpuset.mems.effective`**: Файли лише для читання, які показують реальну результуючу маску ядер та вузлів NUMA з урахуванням гарячого підключення обладнання (hotplug) та обмежень батьківських cgroups.
- **`cpuset.cpus.partition`**: Спеціальний режим ізоляції ядер. Запис `root` створює ексклюзивне піддерево ізольованих ядер, відбираючи їх із глобального балансувальника CFS. Це дозволяє гарантувати відсутність плаваючих переривань та затримок для систем реального часу.

### 3.3 Контролер оперативної пам'яті (`memory`)

Контролер `memory` в v2 реалізує багаторівневу захисну ієрархію, яка прийшла на зміну єдиному жорсткому ліміту `memory.limit_in_bytes`.

```
Використання пам'яті cgroup
0 ──────────────── memory.min ────────── memory.low ────────── memory.high ────────── memory.max
     [Hard Guard]            [Soft Guard]           [Throttle Zone]          [OOM Zone]
  Ніколи не вивантажується   Вивантажується         Активне згортання       Виклик OOM
  навіть при оом системи     в останню чергу        пам'яті процесом        killer
```

Специфікація п'яти рівнів управління пам'яттю:
1. **`memory.min` (Hard Protection)**: Абсолютний захист. Пам'ять групи в межах цього значення **ніколи** не підлягає згортанню (reclaim) або вивантаженню в swap. Навіть якщо система входить у стан загального брак пам'яті, ядро скоріше знищить інші процеси через OOM killer, ніж відбере сторінки нижче `memory.min`.
2. **`memory.low` (Best-effort Protection)**: М'який захист. Ядро уникає вивантаження сторінок цієї cgroup доти, доки інші cgroups не вичерпають свою надлишкову пам'яті.
3. **`memory.high` (Throttle Limit)**: Поріг м'якого обмеження. При перевищенні `memory.high` ядро не викликає OOM killer. Замість цього воно переводить процеси цієї cgroup у режим синхронного згортання пам'яті (direct reclaim): кожен системний виклик виділення пам'яті (`malloc`/`mmap`) призупиняється, змушуючи самий процес очищати власні брудні сторінки, сповільнюючи його виконання.
4. **`memory.max` (Hard Limit)**: Жорсткий ліміт. Якщо використання пам'яті досягає `memory.max` і ядром не вдається звільнити сторінки у межах direct reclaim, викликається OOM killer.
5. **`memory.swap.max`**: Окреме жорстке обмеження на використання swap-простору. У v1 swap додавався до загального ліміту пам'яті (`memory.memsw.limit_in_bytes`), що ускладнювало тонке налаштування. У v2 swap контролюється незалежно.

Файл `memory.stat` надає вичерпну розкладку ядерних категорій використання пам'яті:
- `anon`: Обсяг анонімної пам'яті купи та стеку.
- `file`: Обсяг сторінкового кешу файлової системи.
- `kernel`: Пам'ять ядерних структур даних, влючаючи `kernel_stack`, `pagetables` та `percpu`.
- `slab`: Обсяг пам'яті, виділеної ядерним розподільником `slab` (`slab_reclaimable` та `slab_unreclaimable`).
- `sock`: Пам'ять буферів мережевих сокетів TCP/UDP.

У багатопроцесорних вузлах NUMA контролер пам'яті додатково експортує статистику `memory.numa_stat`, яка розбиває показники `anon`, `file` та `unevictable` по конкретних апаратних вузлах `N0`, `N1`. Це дозволяє виявляти міжвузлові затримки шини QPI/UPI, коли процес виконується на ядрі сокета 0, але його пам'ять виділена у фізичному модулі сокета 1.

**Керування OOM на рівні всієї групи (`memory.oom.group`)**:
За замовчуванням у Linux при досягненні OOM killer обирає та вбиває один найбільший процес у cgroup (`memory.oom.group = 0`). Однак для складних застосунків (наприклад, PostgreSQL або JVM із допоміжними процесами) смерть одного робітника робить усю групу непрацездатною. Запис `1` у `memory.oom.group` гарантує атомарність: при OOM ядро одночасно надсилає `SIGKILL` **усім** процесам цієї cgroup.

### 3.4 Контролер блокового вводу-виводу (`io`) та механізм Cgroup Writeback (cgwb)

Контролер `io` у v2 є фундаментальним досягненням єдиної ієрархії завдяки підтримці **cgroup writeback (cgwb)**.

У v2 кожна сторінка сторінкового кешу ядра при створенні маркується вказівником на cgroup, якій вона належить. Коли фонові потоки ядра виконують скидання асинхронних записів на диск, дисковий планивальник точно знає власнику файлових сторінок і застосовує відповідні ліміти пропускної здатності.

Всередині ядра для кожної пари `(cgroup, block_device)` створюється відповідний об'єкт `struct bdi_writeback` (cgwb). Коли процес пише у файл, сторінка реєструється у вирівняному списку даної `bdi_writeback`. Якщо cgroup вичерпує свою дискову квоту, підсистема VFS обмежує швидкість подальших системних викликів `write()`, запобігаючи неконтрольованому заповненню оперативної пам'яті брудними сторінками.

Підсистема контролера сокетів у cgroups v2 також інтегрована у загальний черговий механізм: структура `sock_cgroup_data` дозволяє підсистемі `net_cls` маркувати мережеві пакети належним тегом без створення окремої ієрархії файлової системи.

Налаштування файлу `io.max`:
```bash
# Обмеження для пристрою 8:0 (Major:Minor)
# rbps/wbps — байти на секунду для читання/запису
# riops/wiops — операції на секунду для читання/запису
echo "8:0 rbps=10485760 wbps=5242880" > /sys/fs/cgroup/app/leaf/io.max
```

### 3.5 Контролер кількості процесів (`pids`)

Контролер `pids` захищає систему від атак типу «fork bomb» та виснаження ядерної таблиці процесів.

Керуючі файли:
- `pids.max`: Максимально дозволена кількість задач (процесів та потоків) у межах cgroup та її піддерев (наприклад `echo 500 > pids.max`).
- `pids.current`: Поточна сумарна кількість задач.
- `pids.events`: Лічильник `max`, який фіксує кількість відхилених системних викликів `fork()`/`clone()` через досягнення стелі.

## 4. Pressure Stall Supervision (PSI)

Традиційні метрики системного моніторингу (load average, відсоток вільної пам'яті чи iostat) показують лише наслідки навантаження, але не дають відповіді на головне питання: **наскільки сильно процеси затримуються (stalled) через брак конкретного ресурсу**.

Впроваджений у ядрі Linux 4.20 механізм **Pressure Stall Information (PSI)** розроблений як безпосередній компаньйон cgroups v2. PSI вимірює реальні витрати часу процесів на очікування CPU, пам'яті та дискового вводу-виводу.

У кожній cgroup контролери створюють три спеціальних файли моніторингу:
- `cpu.pressure`
- `memory.pressure`
- `io.pressure`

### 4.1 Алгоритм розрахунку та показники `some` і `full`

PSI розраховує усереднені значення затримки за вікна 10, 60 та 300 секунд, а також фіксує сумарний час у мікросекундах (`total`).

Метрики поділяються на два класи:
- **`some`**: Відсоток часу, протягом якого **хоча б один** процес у cgroup перебував у стані очікування ресурсу (наприклад, чекав зчитування сторінки з диска), поки інші процеси могли продовжувати виконання.
- **`full`**: Відсоток часу, протягом якого **всі** активні (non-idle) процеси у cgroup були повністю заблоковані ресурсом. Для контролера `cpu` показник `full` відсутній, оскільки CPU не чекає сам на себе.

Вивід вмісту файлу `memory.pressure`:
```text
some avg10=0.04 avg60=0.01 avg300=0.00 total=84120
full avg10=0.01 avg60=0.00 avg300=0.00 total=12300
```
Значення `some avg10=0.04` означає, що за останні 10 секунд щонайменше один процес у цій cgroup витратив 0.04% часу на очікування пам'яті.

### 4.2 Проактивний OOM killer через epoll та PSI

Найпотужнішою можливістю PSI є підтримка системного виклику `epoll()` для створення проактивних демонів ресурсоуправління (таких як `systemd-oomd` або Meta `oomd`).

Замість того, щоб опитувати файли `.pressure` у циклі, програма відкриває `memory.pressure` у режимі `O_RDWR` і записує у нього поріг спрацьовування:

```c
/* Запит сповіщення: якщо 'some' затримка пам'яті перевищує 150мс (150000мкс) 
   універсального вікна в 1 секунду (1000000мкс) */
const char *trigger = "some 150000 1000000";
write(fd, trigger, strlen(trigger));
```

Після цього файл реєструється у селекторі `epoll()` з прапорцем `EPOLLPRI`. Коли ядро фіксує сплеск тиску пам'яті вище 150 мс, `epoll_wait()` негайно розблоковує демон моніторингу. Демон може проактивно зменшити квоту низькопріоритетного контейнера або м'яко перезапустити службу **до того**, як система увійде в стан глибокого swap-шторму або викликає ядерний OOM killer. [Практичну реалізацію менеджера cgroups мовами C та C++](book:unix-linux/cgroups-v2-unified-hierarchy/proj-cgroupv2-manager.md) наведено у проектній вставці, де проілюстровано повний цикл налаштування cgroup та підписки на PSI-події.

Поведінка `systemd-oomd` спирається на два рівні реагування: при зростанні `memory.pressure` демону надсилається сигнал тригера. Спершу демон надсилає сигнал примусового згортання swap у найменш пріоритетний зріз (`user.slice`), і лише якщо тиск не знижується протягом 20 секунд, здійснюється виклик аварійного вилучення всієї cgroup винуватця.

## 5. Інспекція стану ядра та системне середовище

Для аналізу приналежності процесів та трасування подій cgroups v2 ядро Linux надає набір інтерфейсів у `/proc` та підсистемі eBPF/tracepoints.

Для обмеження глибини дерева та захисту таблиці ядерних джерел VFS від виснаження cgroups v2 підтримує два керуючих файли обмеження ієрархії: `cgroup.max.depth` задає максимальну глибину вкладеності дочірніх каталогах, а `cgroup.max.descendants` обмежує абсолютну кількість нащадків. Додатково файл `cgroup.stat` надає глобальну статистику піддерева у полях `nr_descendants` (кількість живих дочірніх cgroups) та `nr_dying_descendants`. Для аналізу заморожених процесів файл `cgroup.events` містить поле `frozen`, яке набуває значення `1` під час повного призупинення задач.

### 5.1 Простеження приналежності через `/proc/[pid]/cgroup`

У cgroups v1 файл `/proc/[pid]/cgroup` містив десятки рядків — по одному для кожного змонтованого контролера. У cgroups v2 цей файл завжди містить **один-єдиний рядок** із префіксом `0::`:

```bash
$ cat /proc/self/cgroup
0::/user.slice/user-1000.slice/user@1000.service/app.slice/app-db.service
```

Це є прямим підтвердженням виконання єдиної ієрархії: номер ієрархії завжди дорівнює `0`, за ним ідуть два двокрапки та абсолютний шлях до cgroup від кореня `/sys/fs/cgroup`.

### 5.2 Ядерні події та Tracepoints

Підсистема cgroups v2 експортує серію стандартних ядерних точок трасування (tracepoints) у файловій системі `tracefs` (`/sys/kernel/tracing/events/cgroup/`):

- `cgroup:cgroup_mkdir`: Фіксує створення нового вузла в ієрархії (`ino`, `path`).
- `cgroup:cgroup_rmdir`: Фіксує вилучення вузла.
- `cgroup:cgroup_attach_task`: Фіксує переміщення процесів між cgroups (`dst_path`, `pid`, `comm`).
- `cgroup:cgroup_freeze`: Фіксує зміну стану заморожування групи.

Моніторинг цих подій через інструменти `bpftrace` або `perf` дозволяє відстежувати динаміку створення контейнерів у системі в реальному часі без опитування файлової системи.

```bash
# Трасування переміщення процесів між cgroups за допомогою bpftrace
bpftrace -e 'tracepoint:cgroup:cgroup_attach_task { printf("PID %d (%s) moved to %s\n", args->pid, args->comm, str(args->dst_path)); }'
```

## 6. Інтеграція з systemd та контейнерними рушіями

У сучасних дистрибутивах Linux пряма маніпуляція `/sys/fs/cgroup` вручну виконується вкрай рідко. Головним менеджером cgroups v2 у системі виступає `systemd`.

### 6.1 Архітектура зрізів systemd (Slices, Scopes, Services)

Systemd відображає свої системні концепції безпосередньо на дерева cgroups v2:
- **`Slice` (Зріз)**: Внутрішній вузол cgroups v2, призначений для групування інших зрізів та служб (`system.slice`, `user.slice`, `machine.slice`).
- **`Service` (Служба)**: Листовий вузол cgroups v2, який містить процеси, запущені відповідним unit-файлом.
- **`Scope` (Область)**: Листовий вузол для процесів, створених ззовні systemd (наприклад, сесії користувачів PAM або контейнери).

Директиви unit-файлу systemd автоматично транслюються у відповідні керуючі файли cgroups v2:

```ini
[Unit]
Description=Database Engine Service

[Service]
ExecStart=/usr/bin/db_engine
# Директиви cgroups v2:
MemoryMin=1G
MemoryHigh=3.5G
MemoryMax=4G
CPUWeight=200
TasksMax=1000
IOWeight=150
```

При запуск цієї служби `systemd` виконає наступні трансляції у `/sys/fs/cgroup/system.slice/db.service/`:
- `MemoryMin=1G` → `memory.min = 1073741824`
- `MemoryHigh=3.5G` → `memory.high = 3758096384`
- `MemoryMax=4G` → `memory.max = 4294967296`
- `CPUWeight=200` → `cpu.weight = 200`
- `TasksMax=1000` → `pids.max = 1000`

Окрім прямої трансляції файлів контролерів, systemd підтримує BPF-фільтрацію сокетів через директиви `IPAddressAllow=` та `IPAddressDeny=`. Для реалізації цих обмежень systemd завантажує програми eBPF типу `BPF_PROG_TYPE_CGROUP_SKB` безпосередньо у відповідний вузол `cgroup`, дозволяючи фільтрувати мережевий трафік служби без залучення важкого фаєрвола `iptables`.

### 6.2 Модель делегування (Delegation) та Rootless-контейнери

У cgroups v2 запроваджено безпечну модель **делегування піддерев**. Системний адміністратор або `systemd` може передати право керування конкретним піддеревом cgroups безпривілейованому користувачеві або контейнерному демону.

Для цього systemd надає директиву `Delegate=yes`. При її активації systemd змінює власника (`chown`) файлів `cgroup.procs` та `cgroup.subtree_control` піддерева на UID звичайного користувача.

Це створило фундамент для **Rootless-контейнерів** (Podman, Docker Rootless mode, containerd):
1. Непривілейований користувач запускає контейнерний демон всередині свого `user.slice`.
2. Демон створює дочірні cgroups всередині делегованого піддерева без залучення прав `root`.
3. ОСРВ-рушії (OCI Runtimes, такі як `crun` або `runc`) налаштовують ліміти `memory.max` та `cpu.max` для контейнерів, дотримуючись правила *No Internal Processes*.

Контейнерні рушії додатково перевіряють стан файлу `cgroup.controllers` для впевненості у доступності необхідних ядерних підсистем перед запуском робочого навантаження користувача. При проектуванні хмарних оркестраторів Kubernetes підсистема Kubelet взаємодіє з cgroups v2 через модуль `systemd cgroup driver`, збираючи PSI-статистику контейнерних Pod-файлів та керуючи динамічним виділенням ресурсів вузла.

Завдяки уніфікованому підходу системні адміністратори можуть будувати гнучкі та захищені середовища виконання. Ефективне розмежування прав та ресурсів підвищує передбачуваність навантаження за умови правильного вибору лімітів пам'яті та CPU. Єдина ієрархія усунула фундаментальні вади першої версії, надавши системним розробникам надійний інструментарій керування ресурсами операційної системи.

Усунення розрізненості контролерів та введення суворих правил математичної коректності зробили cgroups v2 надійною основою інфраструктури Linux. Відмова від ортогональних дерев на користь єдиного ієрархічного графа дозволила об'єднати управління пам'яттю, дисковим вводом-виводом та обчислювальним часом CPU під дахом прозорої псевдофайлової системи.

Завдяки єдиній ієрархії, суворому правилу відсутності внутрішніх процесів та прозорому механізму PSI, підсистема Cgroups v2 перетворилася на надійний, передбачуваний та високопродуктивний стандарт ізоляції та розподілу ресурсів у сучасному ядрі Linux.
