# 📋 Інтерфейс файлової системи cgroupv2: довідник керуючих файлів

Файлова система `cgroup2` (зазвичай змонтована за шляхом `/sys/fs/cgroup`) слугує єдиним віртуальним інтерфейсом простору користувача для конфігурування, моніторингу та делегування ресурсних обмежень ядра Linux. На відміну від звичайних файлових систем на блокових носіях, кожен файл у cgroups v2 є динамічним вікном до ядерних структур даних `struct cgroup` та `struct cgroup_subsys_state`.

Усі взаємодії з цими файлами виконуються за допомогою стандартних системних викликів POSIX (`open`, `read`, `write`, `close`). Під час зчитування ядро динамічно викликом `seq_file` генерує актуальну статистику, а під час запису аналізує текстовий рядок, конвертує числа та модифікує внутрішній стан відповідних підсистем ядра.

У цьому довіднику зведено повну розкладку інтерфейсних файлів cgroups v2, їхній формат, синтаксичні вимоги, діапазони допустимих значень та коди помилок системних викликів.

## 1. Базові файли керування ієрархією

Ці файли присутні у кожній директорії (вузлі) cgroups v2 незалежно від того, які контролери увімкнено для цієї групи. Вони визначають структуру дерева, список процесів та стан делегування.

### 1.1 `cgroup.procs` — Управління процесами

Файл `cgroup.procs` містить список ідентифікаторів процесів (PID), які належать до цієї конкретної cgroup. При зчитуванні ядро виводить список PID по одному на рядок. У cgroups v2 запис PID у цей файл переміщує процес та **всі** його потоки виконання (threads) до нової cgroup.

- **Режим доступу**: Read-Write (R/W).
- **Синтаксис запису**: Десятичне число PID процесу, наприклад `echo 1234 > cgroup.procs`.
- **Поведінка ядра**: Ядро перевіряє наявність процесу у таблиці задач, перевіряє права доступу користувача (`CAP_SYS_ADMIN` або права на запис у `cgroup.procs` цільової групи) та перевіряє дотримання правила *No Internal Processes*. Якщо цільова група є внутрішнім вузлом із активованими дочірніми контролерами, запис завершується помилкою `EBUSY`.

### 1.2 `cgroup.threads` — Управління окремими потоками

Використовується виключно у потоковому режимі (`threaded mode`) для переміщення окремих потоків (TID) одного й того самого процесу між дочірніми потоковими cgroups.

- **Режим доступу**: Read-Write (R/W).
- **Синтаксис запису**: Десятичне число TID потоку, наприклад `echo 1235 > cgroup.threads`.
- **Поведінка ядра**: Переміщує лише вказаний потік, залишаючи інші потоки групи у попередніх вузлах. Працює лише для контролерів `cpu`, `cpuset` та `pids`.

### 1.3 `cgroup.controllers` — Доступні контролери

Файл лише для читання, який показує перелік усіх ресурсних контролерів, які доступні для конфігурування у цьому вузлі.

- **Режим доступу**: Read-Only (RO).
- **Формат виводу**: Назви контролерів, розділені пробілами (наприклад `cpuset cpu io memory pids`).
- **Логіка формування**: Перелік є перетином контролерів, підтримуваних ядром, та контролерів, увімкнених у файлі `cgroup.subtree_control` батьківського вузла.

### 1.4 `cgroup.subtree_control` — Ввімкнення контролерів для дочірніх груп

Ключовий файл реалізації принципу Top-Down Control. Він визначає, які саме контролери будуть активовані для **дочірніх** вузлів цієї cgroup.

- **Режим доступу**: Read-Write (R/W).
- **Синтаксис запису**: Рядок із назвами контролерів, де префікс `+` означає активацію, а префікс `-` — деактивацію. Наприклад: `echo "+cpu +memory -io" > cgroup.subtree_control`.
- **Поведінка ядра**: Увімкнений контролер з'являється у файлах `cgroup.controllers` усіх безпосередніх дочірніх груп і створює контролерні файли (`memory.max`, `cpu.weight` тощо) у цих дочірніх групах. Якщо у поточній cgroup вже є процеси у `cgroup.procs`, запис повертає помилку `EBUSY`.

### 1.5 `cgroup.events` — Стан та прапорці подій

Надає інформацію про актуальний динамічний стан cgroup у вигляді пар `ключ значення`.

- **Режим доступу**: Read-Only (RO).
- **Ключові поля**:
  - `populated 0|1`: Значення `1` вказує, що ця cgroup або принаймні одна з її дочірніх підгруп містить хоча б один живий процес. Значення `0` означає, що піддерево порожнє.
  - `frozen 0|1`: Значення `1` вказує, що виконання всіх процесів у групі призупинено через механізм заморожування (`cgroup.freeze`).

### 1.6 `cgroup.freeze` — Механізм заморожування процесів

Дозволяє атомарно призупиняти та відновлювати виконання всіх процесів у cgroup та її піддеревах (аналог підсистеми `freezer` у cgroups v1).

- **Режим доступу**: Read-Write (R/W).
- **Синтаксис запису**: `1` для заморожування, `0` для розморожування.
- **Поведінка ядра**: При записі `1` ядро надсилає сигнал призупинення всім задачам у групі. Процеси переходять у стан `D` (uninterruptible sleep) або зупиняються на межі системних викликів. Стан заморожування відображається у `cgroup.events`.

### 1.7 `cgroup.type` — Доменний та потоковий типи

Визначає роль вузла в ієрархії: звичайний домен або потокова група.

- **Режим доступу**: Read-Write (R/W).
- **Можливі значення**: `domain` (звичайна cgroup), `threaded` (потоковий вузол), `domain threaded` (корінь потокового піддерева) або `domain invalid`.

### 1.8 `cgroup.stat` — Ієрархічна статистика

Містить інформацію про структуру піддерева.

- **Режим доступу**: Read-Only (RO).
- **Ключові поля**: `nr_descendants` (загальне число дочірніх вузлів на всіх рівнях глибини) та `nr_dying_descendants` (кількість вузлів, які знаходяться на стадії вилучення ядром).

### 1.9 `cgroup.max.depth` та `cgroup.max.descendants` — Обмеження обходу

Файли встановлення структурних меж піддерева для захисту від надмірного розростання ієрархії.

- **Режим доступу**: Read-Write (R/W).
- **Синтаксис**: Десятичне число або `max` (без обмежень).

## 2. Контролер процесора (`cpu`)

Контролер `cpu` регулює розподіл процесорного часу між cgroups за допомогою алгоритму CFS (Completely Fair Scheduler) та обмежень реального часу.

### 2.1 `cpu.weight` та `cpu.weight.nice` — Пропорційна вага

Визначають відносну частку CPU, яку отримує cgroup під час конкуренції за процесорні ядра.

- **Режим доступу**: Read-Write (R/W).
- **Діапазон значень `cpu.weight`**: Від `1` до `10000`. Значення за замовчуванням: `100`.
- **Синтаксис запису**: `echo 200 > cpu.weight`.
- **Математика розрахунку**: Якщо група A має вагу 200, а група B має вагу 100, то при змаганні за один процесор група A отримає `200 / (200 + 100) = 2/3` (66.6%) часу CPU, а група B — `1/3` (33.3%).
- **Файл `cpu.weight.nice`**: Транслює вагу у звичну шкалу `nice` від `-20` до `19`. Запис значення `0` встановлює вагу `100`.

### 2.2 `cpu.max` — Жорстка квота CPU (Bandwidth Control)

Встановлює жорсткі межі процесорного часу, які cgroup не може перевищити навіть за наявності вільних ядер у системі.

- **Режим доступу**: Read-Write (R/W).
- **Формат запису**: Рядок із двох значень `$MAX $PERIOD`, відокремлених пробілом.
  - `$MAX`: Дозволена квота часу CPU у мікросекундах у межах кожного періоду (або рядок `max` для скасування ліміту).
  - `$PERIOD`: Тривалість кванту часу у мікросекундах (за замовчуванням `100000` мкс, тобто 100 мс).
- **Приклади**:
  - `echo "50000 100000" > cpu.max` — обмеження у 0.5 ядра (50 мс за кожні 100 мс).
  - `echo "200000 100000" > cpu.max` — обмеження у 2 повних ядра (200 мс за кожні 100 мс).
  - `echo "max 100000" > cpu.max` — скасування квотування.

### 2.3 `cpu.stat` — Статистика виконання процесора

- **Режим доступу**: Read-Only (RO).
- **Поля виводу**:
  - `usage_usec`: Загальний процесорний час, спожитий усіма задачами групи (в мікросекундах).
  - `user_usec`: Час виконання у просторі користувача.
  - `system_usec`: Час виконання системних викликів у ядрі.
  - `nr_periods`: Кількість пройдених квантів часу `$PERIOD`.
  - `nr_throttled`: Кількість періодів, у яких cgroup вичерпала свою квоту `$MAX` і була призупинена (throttled).
  - `throttled_usec`: Сумарний час, протягом якого процеси групи перебували в призупиненому стані через вичерпання квоти.

## 3. Контролер оперативної пам'яті (`memory`)

Обмеження пам'яті у cgroups v2 охоплюють анонімну пам'ять (heap, stack), сторінковий кеш файлової системи (page cache), пам'ять ядра (slab, kernel stack) та мережеві сокети.

### 3.1 `memory.current` — Поточне споживання

Показує точний сумарний обсяг пам'яті у байтах, який використовується усіма процесами у цій cgroup та її піддеревах.

- **Режим доступу**: Read-Only (RO).

### 3.2 `memory.min` — Жорсткий захист пам'яті

- **Режим доступу**: Read-Write (R/W).
- **Формат**: Число у байтах або з суфіксами `K`, `M`, `G` (наприклад `1G`).
- **Поведінка ядра**: Ядро створює недоторканний резерв пам'яті. Якщо використання пам'яті cgroup знаходиться нижче `memory.min`, ядро **ніколи** не вивантажує сторінки цієї cgroup на диск чи у swap. Якщо системі бракує пам'яті, згортання проводиться виключно за рахунок інших cgroups.

### 3.3 `memory.low` — М'який захист пам'яті

- **Режим доступу**: Read-Write (R/W).
- **Поведінка ядра**: Захист за принципом «best-effort». Ядро намагається не вивантажувати сторінки цієї cgroup, доки інші cgroups не вичерпають свою пам'ять вище своїх порогів `memory.low`.

### 3.4 `memory.high` — М'яке обмеження та сповільнення (Throttling)

- **Режим доступу**: Read-Write (R/W).
- **Поведінка ядра**: Головний інструмент запобігання OOM. При перевищенні `memory.high` ядро переводить процеси групи у режим синхронного згортання пам'яті (direct reclaim). Виклики виділення пам'яті призупиняються, змушуючи процеси очищати власний кеш і сповільнюючи їхнє виконання без виклику OOM killer.

### 3.5 `memory.max` — Жорсткий ліміт пам'яті (Hard Limit)

- **Режим доступу**: Read-Write (R/W).
- **Поведінка ядра**: Абсолютна верхня межа. Якщо cgroup досягає `memory.max` і ядром не вдається звільнити сторінки у межах direct reclaim, викликається OOM killer.

### 3.6 `memory.swap.max` — Обмеження swap-простору

- **Режим доступу**: Read-Write (R/W).
- **Синтаксис**: Байти або `max`. Задає максимальний обсяг swap, який дозволено використовувати cgroup.

### 3.7 `memory.oom.group` — Поведінка OOM killer

- **Режим доступу**: Read-Write (R/W).
- **Значення**:
  - `0` (дефолт): OOM killer знищує лише один найбільший процес cgroup.
  - `1`: OOM killer одночасно надсилає `SIGKILL` усім процесам cgroup для збереження атомарності системи.

### 3.8 `memory.events` — Лічильники подій пам'яті

- **Режим доступу**: Read-Only (RO).
- **Поля**: `low`, `high`, `max`, `oom`, `oom_kill`, `oom_group_kill`. Показують кількість разів, коли cgroup перетинала відповідні межі.

## 4. Контролер блокового вводу-виводу (`io`)

Керує блоковими пристроями на основі номера пристрою Major:Minor.

### 4.1 `io.max` — Ограничення пропускної здатності та IOPS

- **Режим доступу**: Read-Write (R/W).
- **Формат запису**: `$MAJOR:$MINOR rbps=$B wbps=$B riops=$N wiops=$N`
  - `rbps`/`wbps`: Максимальні байти на секунду для читання/запису.
  - `riops`/`wiops`: Максимальні операції на секунду для читання/запису.
  - Приклад: `echo "8:0 rbps=10485760 wbps=5242880" > io.max` (10 MB/s читання, 5 MB/s запис на диск /dev/sda).

### 4.2 `io.weight` — Пропорційна вага диска

- **Режим доступу**: Read-Write (R/W).
- **Діапазон**: Від `1` до `10000` (дефолт `100`). Використовується дисковими планувальниками BFQ для пропорційного розподілу квантів дискового часу.

## 5. Контролер кількості процесів (`pids`)

### 5.1 `pids.max` та `pids.current`

- **`pids.max`** (R/W): Максимальна дозволена кількість процесів і потоків у cgroup (число або `max`).
- **`pids.current`** (RO): Поточна сумарна кількість задач.
- **`pids.events`** (RO): Містить лічильник `max` — кількість відхилених системних викликів `fork()`/`clone()` через досягнення межі `pids.max`.

## 6. Коди помилок системних викликів при роботі з cgroups v2

При виконанні системних викликів `write()`, `mkdir()`, `rmdir()` над файлами cgroups v2 ядро повертає чіткі коди помилок у змінній `errno`:

1. **`EBUSY` (Device or resource busy)**:
   - Спроба увімкнути контролер у `cgroup.subtree_control`, коли у цій cgroup вже є процеси у `cgroup.procs` (порушення правила *No Internal Processes*).
   - Спроба перемістити PID у `cgroup.procs` некореневого внутрішнього вузла, який вже має активовані дочірні контролери.
   - Спроба вилучити директорію cgroup за допомогою `rmdir()`, якщо у ній або її піддеревах залишаються живі процеси або дочірні каталоги.

2. **`EINVAL` (Invalid argument)**:
   - Синтаксична помилка при записі у керуючий файл (наприклад, невідома назва контролера в `cgroup.subtree_control`, від'ємне значення ваги в `cpu.weight` або неправильний формат $MAJOR:$MINOR в `io.max`).
   - Спроба записати дробове число у файли, які очікують цілі байти або мікросекунди.

3. **`ENOENT` (No such file or directory)**:
   - Запис PID у `cgroup.procs` для процесу, який не існує або вже завершив своє виконання у ядрі.
   - Спроба відкрити файл контролера, який не був активований у `cgroup.subtree_control` батьківського вузла.

4. **`E2BIG` (Argument list too long)**:
   - Спроба створити дочірній каталог `mkdir`, яка перевищує максимально дозволену глибину дерева, встановлену у файлі `cgroup.max.depth`.

5. **`EOPNOTSUPP` (Operation not supported)**:
   - Спроба налаштувати параметри контролера на пристрої або файловій системі, яка не підтримує відповідну операцію (наприклад, спроба виставити `io.max` для мережевої ФС або виртуального loop-пристрою без підтримки квотування).

6. **`EACCES` / `EPERM` (Permission denied / Operation not permitted)**:
   - Недостатньо прав для створення директорії або запису у файл cgroup. Для створення cgroups потрібні права `root` (`CAP_SYS_ADMIN`) або права власника на делеговане піддерево при використанні моделі `Delegate=yes`.
