У ядрі Linux є структури даних, які читають мільйони разів на секунду, а змінюють дуже рідко (наприклад, таблиця маршрутизації мережі). Захищати їх звичайними замками (навіть замками читач-письменник) занадто дорого: сам факт того, що читач має повідомити про свою присутність (збільшити лічильник), змушує ядра процесора битися за один рядок кеша.

RCU (Read-Copy Update) вирішує цю проблему радикально: **читач не залишає жодних слідів у спільній пам'яті**. Читання стає абсолютно безкоштовним, не потребує замків і чудово масштабується на будь-яку кількість ядер.

Але якщо читач нічого не пише, то як письменник (той, хто змінює структуру) дізнається, що читачів більше немає і можна звільнити стару пам'ять? Письменник цього не дізнається. Замість точного обліку RCU використовує **час і спостереження за станом системи**.

## Три кроки RCU

Механізм Read-Copy Update складається з трьох фаз, коли треба змінити або вилучити вузол:

1. **Від'єднання (Removal/Publish).** Письменник замінює вказівник у списку на новий вузол (або просто прибирає його). З цього моменту нові читачі перестають бачити старий вузол. Але старі читачі, які вже встигли зайти за вказівником до від'єднання, все ще можуть читати стару пам'ять.
2. **Період відстрочки (Grace Period).** Письменник чекає, поки всі такі старі читачі гарантовано завершать свою роботу.
3. **Звільнення (Reclamation).** Коли період відстрочки минає, ядро безпечно звільняє старий вузол.

## Період відстрочки (Grace Period)

Головний трюк RCU полягає в тому, як вимірюється цей період. На читача накладається одне суворе правило: **під час читання не можна засинати, блокуватися чи віддавати процесор**.

Завдяки цьому правилу, ядру достатньо дочекатися моменту, коли **кожне** ядро процесора хоча б один раз здійснить перемикання контексту, перейде в стан простою або вийде в простір користувача. Такі події називаються **спокійними станами** (quiescent states). Якщо на ядрі відбулося перемикання контексту, старий читач там уже завершив роботу: сам він процесора не віддає. (У витісненому ядрі задачу можуть зняти й посеред читання — тоді ядро окремо бере таку задачу на облік і не закриває період, доки вона не дочитає.)

Час, за який кожне ядро процесора проходить через спокійний стан, і є **періодом відстрочки**. Письменник чекає цей період, знаючи, що після нього старих читачів у системі фізично лишитися не могло.

## Інтерфейс у коді

Для роботи з RCU ядро Linux надає спеціальні примітиви; у Rust-частині з них наразі є позначення ділянки читання, а колекція в прикладі нижче — умовна.

:::tabs
== C
```c
/* Читач: лише позначає межі, жодних блокувань */
rcu_read_lock();
list_for_each_entry_rcu(d, &dev_list, node) {
    if (d->ifindex == idx) {
        found = d;
        break;
    }
}
/* Робота з found має завершитися до unlock */
rcu_read_unlock();

/* Письменник (вилучення) */
mutex_lock(&dev_mutex); /* RCU не захищає письменників один від одного */
list_del_rcu(&d->node);
mutex_unlock(&dev_mutex);

/* Асинхронне звільнення після Grace Period */
call_rcu(&d->rcu, dev_free);
```
== Rust
```rust
// У Rust читання під RCU оформлюється через RCU Guard
let rcu_guard = kernel::sync::rcu::read_lock();

// Пошук у колекції, захищеній RCU
if let Some(dev) = dev_list.iter(&rcu_guard).find(|d| d.ifindex == idx) {
    // Працюємо з dev...
}
// Guard автоматично звільняється при виході з області видимості
drop(rcu_guard);

// Письменник
let mut list = dev_list.lock(); // Захист письменників
let old_node = list.remove(idx);
// Звільнення буде автоматично відкладене завдяки Drop + RCU
```
:::

## Підсумок

RCU — це розмін точності обліку на швидкість. Замість того, щоб кожне ядро процесора постійно відмічалося в пам'яті («я тут», «я вийшов»), RCU покладається на спостереження за природними подіями в системі (перемикання контексту). Це робить оновлення повільним (через необхідність чекати), але робить мільйони читань абсолютно безкоштовними.
