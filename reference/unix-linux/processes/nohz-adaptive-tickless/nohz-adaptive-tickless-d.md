# Адаптивне ядро без тиків (NO_HZ_FULL)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Системний таймер в операційній системі Linux відіграє ключову роль у функціонуванні планувальника процесів, механізмів синхронізації та управління енергоспоживанням. Протягом десятиліть ядро Linux покладалося на періодичні переривання таймера (system ticks) для виконання регулярних завдань. Проте з розвитком багатоядерних архітектур та зростанням вимог до продуктивності з боку спеціалізованих галузей, таких як високопродуктивні обчислення (HPC) та високочастотний трейдинг (HFT), періодичний таймер став суттєвою перешкодою. 

У цій статті ми глибоко зануримося в еволюцію системного таймера в Linux, детально розберемо механізми роботи `CONFIG_NO_HZ_IDLE` та `CONFIG_NO_HZ_FULL`, а також розглянемо, як досягти ідеальної ізоляції процесорних ядер (CPU isolation) для задач, що вимагають нульової затримки.

## 1. Фундаментальні основи: HZ, Jiffies та системний тик

### 1.1 Роль системного таймера
В основі традиційного ядра лежить концепція періодичного переривання. Апаратний таймер (наприклад, Programmable Interval Timer - PIT, HPET або Local APIC Timer) програмується на генерацію переривань із заданою частотою. Ця частота визначається конфігураційним параметром ядра `CONFIG_HZ`.

Типові значення `CONFIG_HZ`:
- **100 Гц (10 мс):** Використовувалося в старих системах. Менше навантаження на процесор, але низька реактивність.
- **250 Гц (4 мс):** Компромісне значення, яке часто використовується за замовчуванням у багатьох серверних дистрибутивах.
- **1000 Гц (1 мс):** Використовується в десктопних системах для забезпечення плавності інтерфейсу та швидкої реакції на дії користувача.

Кожен раз, коли таймер генерує переривання, управління передається обробнику переривань ядра. Цей обробник виконує низку життєво важливих функцій:
1. Оновлення лічильника `jiffies`, який зберігає кількість тиків з моменту завантаження системи. Цей лічильник використовується для розрахунку часу (uptime) та вимірювання інтервалів.
2. Оновлення системного часу (wall clock).
3. Перевірка, чи не вичерпав поточний процес свій квант часу (time slice). Якщо квант вичерпано, встановлюється прапорець `TIF_NEED_RESCHED`, що змушує планувальник (scheduler) вибрати інший процес для виконання.
4. Обслуговування колбеків RCU (Read-Copy Update), перевірка станів спокою (quiescent states).
5. Виконання відкладених таймерів (software timers), зареєстрованих підсистемами ядра.
6. Збір статистики використання процесора (для утиліт на кшталт `top`, `vmstat`, `sar`).

### 1.2 Проблема періодичних переривань
Хоча періодичні тики роблять архітектуру ядра простою та передбачуваною, вони мають два серйозні недоліки:
1. **Енергоспоживання:** Коли система простоює, процесор переходить у стан сну (C-states), щоб заощадити енергію. Якщо `CONFIG_HZ` встановлено на 1000, процесор змушений прокидатися 1000 разів на секунду лише для того, щоб ядро переконалося, що робити нічого, і знову заснуло. Це розряджає батарею ноутбуків і збільшує тепловиділення на серверах.
2. **Латентність (Jitter):** Коли на ядрі працює критичний до затримок додаток (наприклад, HFT алгоритм), кожне переривання таймера відбирає в нього управління на кілька мікросекунд (так званий "OS jitter"). Ці мікросекунди можуть коштувати мільйони доларів у фінансовому трейдингу або руйнувати симуляції в HPC.

## 2. Епоха Dynamic Ticks: `CONFIG_NO_HZ_IDLE`

Щоб вирішити проблему енергоспоживання, у ядрі 2.6.21 було представлено технологію "Dynamic Ticks" (dynticks), також відому як `NO_HZ_IDLE`.

### 2.1 Як працює NO_HZ_IDLE
Ідея `NO_HZ_IDLE` полягає в тому, що періодичні тики потрібні лише тоді, коли процесор виконує корисну роботу або коли є кілька процесів, між якими потрібно перемикатися. Якщо черга виконання (runqueue) на певному логічному ядрі CPU порожня (тобто на ньому працює лише потік `idle`), періодичний таймер стає непотрібним.

Алгоритм роботи `NO_HZ_IDLE`:
1. Коли процесор збирається перейти в стан простою (виконується `idle` потік), ядро перевіряє, коли має спрацювати найближчий відкладений таймер або подія.
2. Ядро перепрограмує апаратний таймер (наприклад, LAPIC) так, щоб він спрацював не через 1 мілісекунду, а саме тоді, коли настане час наступної події (наприклад, через 500 мс).
3. Періодичний тик зупиняється.
4. Процесор переходить у глибокий сон (глибокий C-state).
5. Коли спрацьовує перепрограмований таймер або приходить апаратне переривання (наприклад, від мережевої карти або клавіатури), процесор прокидається, і періодичний тик відновлюється.

### 2.2 Переваги та обмеження
`NO_HZ_IDLE` є надзвичайно успішною інновацією. Цей режим включений за замовчуванням у всіх сучасних дистрибутивах Linux (Ubuntu, RHEL, Debian, Android). Він дозволяє сучасним мобільним пристроям працювати днями в режимі очікування.

Проте, `NO_HZ_IDLE` **не вирішує** проблему латентності для працюючих додатків. Щойно ви запускаєте ваш критичний додаток на процесорі, `NO_HZ_IDLE` знову вмикає періодичний тик. Додаток починає отримувати переривання кожну мілісекунду.

## 3. Адаптивне ядро без тиків: `CONFIG_NO_HZ_FULL`

Розробники систем реального часу та HPC не були задоволені `NO_HZ_IDLE`. Їм потрібно було рішення, яке б зупиняло системний таймер **навіть тоді, коли на процесорі виконується код користувача**.

Так з'явилася технологія Adaptive Tickless Kernel (`CONFIG_NO_HZ_FULL`), введена в гілку ядра 3.10.

### 3.1 Концепція NO_HZ_FULL
Логіка `NO_HZ_FULL` геніально проста: якщо на певному ядрі CPU виконується **рівно один** Runnable процес, планувальнику ядра не потрібно прокидатися 1000 разів на секунду, щоб перевірити, чи не пора віддати процесор комусь іншому — адже інших претендентів немає!

Коли `NO_HZ_FULL` активується, ядро зупиняє періодичний таймер на цьому CPU. Єдиний процес, що працює на цьому ядрі, отримує 100% циклів процесора (повна монополія). Жодних переривань від таймера, жодних скидань кешів L1/L2 через код ядра, жодного jitter-а.

### 3.2 Чому це так складно реалізувати?
Зупинити таймер під час виконання користувацького коду набагато складніше, ніж під час `idle`. Таймер відповідає не лише за планувальник. Без нього ядро сліпне: воно не знає, скільки часу витратив процес, воно не може оновлювати системний час, воно не може виконувати RCU колбеки.

Саме тому `NO_HZ_FULL` ніколи не включається для всіх ядер системи. Завжди має залишатися хоча б одне ядро (зазвичай CPU 0), яке бере на себе роль **Housekeeping CPU**. Це ядро продовжує тикати, оновлює загальносистемні лічильники часу (jiffies), обробляє системні таймери, виконує мережевий стек та інші фонові задачі ОС, дозволяючи ізольованим ядрам працювати без перешкод.

## 4. RCU (Read-Copy-Update) та `rcu_nocbs`

Одна з найбільших перешкод для `NO_HZ_FULL` — це RCU.
RCU — це потужний механізм синхронізації в Linux, який дозволяє читачам читати дані без блокувань (lock-free), тоді як письменники створюють копії даних і оновлюють вказівники. Стара версія даних може бути звільнена з пам'яті лише тоді, коли ядро гарантує, що жоден читач більше на неї не дивиться. Цей момент гарантії називається **Grace Period**.

### 4.1 Проблема RCU Grace Periods
Ядро визначає, що grace period закінчився, чекаючи, поки кожен CPU пройде через **Quiescent State** (стан спокою) — наприклад, перемикання контексту або перехід в userspace.
У традиційному ядрі саме системний таймер використовується для того, щоб перевіряти стан процесорів та сигналізувати підсистемі RCU про проходження quiescent states.

Якщо ми вимкнемо таймер на ізольованому CPU, підсистема RCU може зависнути (stall), чекаючи на відповідь від цього CPU, що призведе до паніки ядра (Kernel Panic) або вичерпання пам'яті (ОС не зможе звільняти старі структури).

### 4.2 RCU Offloading (`rcu_nocbs`)
Для вирішення цієї проблеми Пол Маккенні (автор RCU) розробив **RCU Offloading**.
У цьому режимі, замість того щоб ізольований CPU сам обробляв свої RCU колбеки під час тиків, ядро створює спеціальні потоки (kernel threads), такі як `rcuoX` та `rcucX`.
Ці потоки прив'язуються (pinned) до Housekeeping CPU (наприклад, CPU 0). Коли ізольований CPU створює RCU колбек, він просто додає його в чергу і продовжує свою роботу, а Housekeeping CPU виконує важку роботу з його обслуговування.

Щоб включити цю магію, необхідно передати параметру ядра список ізольованих ядер через аргумент `rcu_nocbs`. Наприклад: `rcu_nocbs=1-15`.

## 5. Практичне налаштування ізоляції ядер (CPU Isolation)

Простого включення `CONFIG_NO_HZ_FULL` у конфігу ядра недостатньо. Це лише фреймворк. Щоб реально отримати ізольовані ядра без тиків, необхідно налаштувати систему через параметри завантаження (GRUB).

Уявімо, що ми маємо 16-ядерний сервер. Ми хочемо залишити CPU 0 для ОС, а CPU 1-15 ізолювати для нашого HFT трейдера або DPDK додатку.

### 5.1 Параметри завантаження ядра
У `/etc/default/grub` (змінна `GRUB_CMDLINE_LINUX`) додаємо наступні параметри:

`isolcpus=1-15 nohz_full=1-15 rcu_nocbs=1-15 irqaffinity=0 intel_pstate=disable`

Розберемо кожен параметр:
- **`isolcpus=1-15`**: Вказує планувальнику не планувати жодні звичайні процеси на ядрах 1-15. Вони будуть порожніми, поки ми явно не прив'яжемо до них процес за допомогою `taskset`.
- **`nohz_full=1-15`**: Активує Adaptive Tickless на цих ядрах.
- **`rcu_nocbs=1-15`**: Переносить обробку RCU колбеків з ядер 1-15 на інші ядра (в нашому випадку на CPU 0).
- **`irqaffinity=0`**: Направляє всі апаратні переривання за замовчуванням на CPU 0. Якщо переривання від мережевої карти або диска прилетить на ізольоване ядро, воно перерве процес і викличе затримку.
- **`intel_pstate=disable`** (або `processor.max_cstate=0`): Відключає динамічну зміну частоти (Turbo Boost та енергозбереження), щоб уникнути затримок при пробудженні ядра з C-state (важливо для HFT).

Після редагування необхідно оновити GRUB (наприклад, `update-grub` в Debian/Ubuntu або `grub2-mkconfig` в RHEL) і перезавантажити сервер.

### 5.2 Служби, які потрібно вимкнути
Навіть з параметрами ядра деякі системні демони можуть порушити ізоляцію:
1. **`irqbalance`**: Цей демон сканує переривання і перерозподіляє їх між ядрами. Він проігнорує `irqaffinity` і направить IRQ на ваші ізольовані ядра. Його потрібно зупинити: `systemctl disable --now irqbalance`.
2. **`vmstat`**, **`sysstat`**: Ці інструменти можуть періодично опитувати статистику, викликаючи активність ядра.

### 5.3 Прив'язка процесу (Thread Pinning)
Тепер, коли система завантажена, ядра 1-15 порожні і чекають. Запускаємо наш критичний додаток:

```bash
taskset -c 1 ./hft_trading_bot
```
Або, якщо ми використовуємо cgroups (рекомендується сучасними стандартами замість `isolcpus`), ми створюємо cpuset з `cpuset.cpus = 1` і поміщаємо туди PID процесу.

## 6. Вороги NO_HZ_FULL: Що може повернути системний тик?

Найбільша омана щодо `NO_HZ_FULL` полягає в тому, що після його налаштування можна забути про ОС і просто писати код. Насправді, `NO_HZ_FULL` дуже крихкий. Якщо ваш потік зробить щось, що вимагає уваги ядра, системний тик негайно повернеться. Це називається **"порушенням ізоляції" (isolation break)**.

Що викликає повернення тиків?

### 6.1 Системні виклики (Syscalls)
Коли програма викликає системний виклик (наприклад, `read()`, `write()`, `send()`, `recv()`), контекст перемикається в ядро. ЯдроLinux не підтримує виконання тривалих системних викликів без тику. Більшість syscalls гарантовано активують таймер.
**Рішення:** 
- Уникайте системних викликів у гарячому циклі (hot path).
- Використовуйте технології Kernel Bypass. Для мережі це DPDK (Data Plane Development Kit), Solarflare OpenOnload або XDP/AF_XDP. Додаток отримує прямий доступ до пам'яті (DMA) мережевої карти (NIC), читаючи пакети без жодного звернення до ОС (без `recv()`).
- Для міжпроцесної взаємодії (IPC) використовуйте shared memory (`shmget`) замість пайпів чи сокетів, опитуючи пам'ять циклом (busy spin).

### 6.2 Сторінкові помилки (Page Faults)
Якщо ваш додаток намагається звернутися до пам'яті, яка була виділена (`malloc()`), але ще не прив'язана до фізичної RAM (lazy allocation), виникає Minor Page Fault. Ядро має зупинити процес, виділити фізичну сторінку, оновити Page Table і повернути управління. Це займає мікросекунди і включає тик.
**Рішення:**
- Виділяйте всю необхідну пам'ять під час ініціалізації (до входу в критичний цикл).
- Використовуйте системний виклик `mlockall(MCL_CURRENT | MCL_FUTURE)`, який змушує ядро одразу відобразити всі сторінки в фізичну RAM і запобігає їхньому свопінгу (swapping).
- Встановлюйте пам'ять (наприклад, через `memset`), щоб гарантувати її реальне виділення в пам'яті.

### 6.3 Більше одного процесу на ядрі
Пам'ятайте правило: `NO_HZ_FULL` працює лише тоді, коли на ядрі є **рівно один** Runnable процес. Якщо ви запустите два потоки на CPU 1, планувальник ядра негайно увімкне системний таймер (зазвичай на 1000 Гц), щоб квантувати час (time-slicing) між цими двома потоками.
**Рішення:** Жорстка прив'язка (affinity) — один потік на одне ядро.

### 6.4 SoftIRQs та Workqueues
Іноді ядро може запланувати виконання відкладених задач (softirqs) на ізольованому ядрі (наприклад, таймери мережевого стеку). 
**Рішення:** Ізоляція переривань (`irqaffinity=0`) і RCU offloading зазвичай мінімізують цю проблему.

## 7. Верифікація та налагодження (Debugging)

Як переконатися, що ваше налаштування дійсно працює і таймер вимкнено?

### 7.1 Перевірка /proc/interrupts
Ви можете перевірити кількість переривань таймера (Local APIC timer).
Запустіть ваш додаток на CPU 1, а потім виконайте команду кілька разів з інтервалом в 1 секунду:

```bash
watch -n 1 "cat /proc/interrupts | grep LOC"
```
Для CPU 0 (Housekeeping) ви побачите стрімке зростання лічильника (приблизно на 1000 щосекунди, залежно від `HZ`).
Для CPU 1 (Ізольоване ядро) лічильник має бути **статичним** або зростати надзвичайно повільно (1-2 тики на секунду, які є "залишковим шумом").

### 7.2 Використання ftrace та perf
Щоб глибоко проаналізувати, що саме перериває ваш потік (timer interrupts, page faults, syscalls), можна скористатися вбудованим в ядро інструментом трасування `ftrace`.

Увімкніть відстеження подій ОС на конкретному ядрі:
```bash
echo 1 > /sys/kernel/tracing/events/irq/enable
echo 1 > /sys/kernel/tracing/events/sched/enable
echo 1 > /sys/kernel/tracing/events/syscalls/enable
```
Або використовуйте `perf`:
```bash
perf record -C 1 -e irq_vectors:local_timer_entry sleep 10
perf report
```
Якщо ви бачите `local_timer_entry` під час роботи вашого трейдингового бота — ваша ізоляція порушена.

## 8. NO_HZ_FULL в сучасних архітектурах

Варто зазначити, що `NO_HZ_FULL` є потужним інструментом, але його використання є нішевим. Розробники ядра Linux (зокрема Ingo Molnar, Thomas Gleixner, Paul McKenney) витратили роки на доведення цієї підсистеми до стабільного стану.

**Вимоги до апаратного забезпечення:** 
Для ефективної роботи Adaptive Tickless процесор повинен підтримувати сучасні таймери високої роздільної здатності, а також інструкції `RDTSC` (Read Time-Stamp Counter). Додатки в userspace використовують `RDTSC` для вимірювання часу без системних викликів. Завдяки vDSO (virtual dynamically linked shared object), виклики на кшталт `clock_gettime()` також не викликають контекстних перемикань.

**Контейнеризація та Kubernetes:**
Сьогодні технології CPU Isolation активно використовуються в Kubernetes за допомогою **CPU Manager** та **Topology Manager**. Задавши політику `static` для CPU Manager, Kubernetes може виділяти ексклюзивні ядра для Pod-ів (наприклад, для NFV - Network Function Virtualization або 5G телекому). У поєднанні з налаштуваннями вузла (node) на базі `NO_HZ_FULL`, контейнеризовані програми отримують bare-metal продуктивність без джитера ОС.

## 9. Висновки

Адаптивне ядро без тиків (`NO_HZ_FULL`) — це вінець розвитку можливостей Linux у сфері реального часу. Перетворивши періодичні переривання з обов'язкового елемента системи на опціональний, ядро Linux здатне працювати в двох парадигмах одночасно: як багатофункціональна ОС загального призначення на Housekeeping ядрах та як ультралегка RTOS (операційна система реального часу) на ізольованих ядрах.

Хоча налаштування та підтримка ізоляції є складною задачею, що вимагає бездоганної архітектури користувацького додатку (без syscalls, з попереднім виділенням пам'яті), результати вражають. Можливість виконувати код із субмікросекундною передбачуваністю відкриває для Linux двері в індустрії, де кожна наносекунда має безпосередню фінансову цінність.

Рекомендації для інженерів:
1. Завжди використовуйте комбінацію `nohz_full`, `rcu_nocbs` та `irqaffinity`.
2. Відключайте системні демони, що втручаються в роботу ядер (напр., `irqbalance`).
3. Використовуйте `mlockall` для фіксації пам'яті.
4. Профілюйте ваші додатки за допомогою `perf` та `ftrace`, щоб виявляти несподівані системні виклики та переривання.
5. Для I/O використовуйте архітектури Kernel Bypass.
