# Адаптивне ядро без тиків (NO_HZ_FULL)

<preknowlist>
- [Модель процесів та планувальник CFS](book:unix-linux/scheduler-model) — принципи квантування часу та роботи черг виконання runqueue.
- [Високоточні таймери hrtimer](book:unix-linux/high-resolution-timers) — апаратна інфраструктура таймерів та обробка часових подій у ядрі.
</preknowlist>

У системі високочастотного трейдингу робочий потік опитує мережеву карту в очікуванні біржового пакета. Кожна наносекунда затримки означає втрату фінансової позиції. Раптово обробник апаратного таймера ядра перериває виконання коду користувача на 3 мікросекунди лише для того, щоб оновити системний лічильник `jiffies` та перевірити, чи не з'явилися інші процеси у порожній черзі виконання. Це явище називається тремтінням затримок операційної системи (*від англ. OS jitter — тремтіння, коливання*), і в традиційному ядрі Linux воно відбувається від 100 до 1000 разів на секунду на кожному процесорному ядрі.

Адаптивне ядро без тиків (`CONFIG_NO_HZ_FULL`) вирішує цю проблему, повністю вимикаючи періодичне переривання таймера на процесорних ядрах, які виконують один критичний потік користувача.

![Еволюція системного таймера](/reference/unix-linux/processes/nohz-adaptive-tickless/img/nohz-timeline.svg)
*Порівняння періодичного тику, динамічного тику у простої (NO_HZ_IDLE) та адаптивного ядра без тиків (NO_HZ_FULL).*

## 1. Механіка системного тику: HZ, Jiffies та накладні витрати

Традиційне ядро Linux базується на концепції періодичного системного переривання (*від англ. tick — цокання, мітка*). Апаратний таймер (Programmable Interval Timer i8254, High Precision Event Timer або Local APIC Timer) програмується на генерацію переривань з фіксованою частотою, яка визначається константою `CONFIG_HZ` під час компіляції ядра.

При частоті `CONFIG_HZ = 1000` переривання генерується кожну 1 мілісекунду (1000 мікросекунд). Обробник переривання таймера `tick_periodic()` або `tick_sched_timer()` виконує в контексті переривання серію обов'язкових процедур ядра:

1. **Інкремент лічильника `jiffies`:** Глобальна 64-бітна змінна `jiffies_64` зберігає кількість системних тиків, що минули з моменту завантаження системи. Вона слугує базовим джерелом часу для вимірювання системного uptime та розрахунку таймаутів у ядрі.
2. **Облік процесорного часу (Time Accounting):** Планувальник CFS (Completely Fair Scheduler) підраховує кількість циклів процесора, витрачених поточним потоком у режимі користувача (user space, Ring 3) та режимі ядра (kernel space, Ring 0), оновлюючи структури статистики `task_struct`.
3. **Квантування часу та витіснення:** Планувальник перевіряє, чи не вичерпав поточний процес свій динамічний квант часу (*time slice*). Якщо квант вичерпано і в черзі `runqueue` є інші активні процеси з рівним або вищим пріоритетом, обробник встановлює прапорець `TIF_NEED_RESCHED` у структурі `thread_info`, змушуючи ядро виконати функцію перемикання контексту `schedule()`.
4. **Обслуговування підсистеми RCU:** Підсистема Read-Copy Update використовує переривання таймера для перевірки проходження станів спокою (*quiescent states*) кожним процесором системи, щоб завершувати періоди очікування (*grace periods*).
5. **Виконання м'яких таймерів (Softirqs):** Запуск обробників таймерів високої роздільної здатності `hrtimer` та класичних таймерів ядра (`timer_list`), а також ініціація програмних переривань `TIMER_SOFTIRQ` та `SCHED_SOFTIRQ`.

Для універсального сервера загального призначення періодичний тик є природним і необхідним пульсом ОС. Проте для обчислювальних ядер з виключною монополією одного низькозатримкового процесу цей пульс перетворюється на паразитарний шум. 

Кожне переривання таймера викликає примусове збереження регістрів процесора на стек, вимивання гарячих даних із кешів першого та другого рівнів (L1d, L1i, L2), забруднення буфера асоціативної трансляції адреси (TLB) та затримку виконання коду користувача від 1 до 5 мікросекунд. При 1000 тиках на секунду процес втрачає до декількох мілісекунд чистого процесорного часу щосекунди, але головне — отримує непередбачуване тремтіння затримок (jitter).

Докладну хронологію розвитку підсистеми таймерів ядра Linux — від фіксованих 100 Гц у Linux 2.4 до виникнення dynticks та Adaptive Tickless — викладено у вставці [📜 Історія виникнення ядра без тиків](book:unix-linux/nohz-adaptive-tickless/hist-tickless-kernel.md).

## 2. Динамічний тик у простої: CONFIG_NO_HZ_IDLE

Коли черга виконання `runqueue` логічного CPU стає порожньою, ядро переходить до виконання спеціального потоку `idle` (PID 0). Генерація регулярних періодичних переривань у цьому стані є марною, оскільки витісняти процесор немає чим. Замість постійного цокання ядро під час входу в `idle` аналізує червоно-чорне дерево таймерів високої роздільної здатності `hrtimer` та обчислює точний момент часу `t_next`, коли має спрацювати найближчий запланований таймер. Апаратний Local APIC таймер перепрограмується на генерування єдиного одноразового переривання у момент `t_next`, що дозволяє повністю зупинити періодичний тик і перевести процесор у стан простою.

```
Вхід у idle → Пошук найближчого hrtimer → Перепрограмування LAPIC → Вимкнення тику → Вхід у C-state
```

Цей механізм вимкнення періодичних переривань під час простою був уперше реалізований як режим `CONFIG_NO_HZ_IDLE` (відомий як Dynamic Ticks або dynticks) у ядрі Linux 2.6.21.

Підсистема dynticks обчислює інтервал до `t_next` (наприклад, 300 мілісекунд), після чого апаратний Local APIC таймер генерує єдине переривання в обраний момент, а процесор переходить у глибокі стани енергозбереження (C-states від C1/C2 до C6/C10).

Алгоритм роботи `NO_HZ_IDLE` реалізовано у функції `tick_nohz_idle_enter()`. При виклику функція перевіряє стан черги `runqueue` і, переконавшись у відсутності активних задач, переводить локальний таймер у безтиковий режим `TICK_NOHZ_MODE_LOWRES` або `TICK_NOHZ_MODE_HIGHRES`.

Фундаментальні обмеження `NO_HZ_IDLE`:
- **Функціонування виключно у простої:** Щойно на ядрі з'являється хоча б один активний процес користувача, підсистема dynticks негайно відновлює періодичний тик з частотою `CONFIG_HZ`.
- **Відсутність захисту активних задач:** `NO_HZ_IDLE` блискуче вирішив проблему енергоспоживання мобільних пристроїв та серверів у простої, але залишив латентність активних робочих навантажень без жодних змін.

## 3. Принцип функціонування CONFIG_NO_HZ_FULL

Технологія Adaptive Tickless Kernel (`CONFIG_NO_HZ_FULL`) розширює концепцію dynticks на режим активного виконання коду користувача.

Логіка підсистеми базується на фундаментальній умові: **якщо на ізольованому процесорному ядрі виконується рівно один обчислювальний процес (Runnable task count = 1), ядру немає потреби проводити квантування часу**. Оскільки інших процесів у черзі виконання немає, витісняти поточний процес ніким, а отже, періодичний переривач виявляється надлишковим.

![Архітектура розділення ядер при NO_HZ_FULL](/reference/unix-linux/processes/nohz-adaptive-tickless/img/nohz-architecture.svg)
*Розподіл функцій між Housekeeping-ядром (CPU 0) та ізольованими ядрами (CPU 1..N) у режимі NO_HZ_FULL.*

### 3.1 Концепція розділення ядер: Housekeeping CPU

Зупинити системний таймер на ядрі, де виконується активний процес користувача, набагато складніше, ніж у стані `idle`. Без тиків ядро втрачає можливість оновлювати загальносистемний час, обробляти глобальні таймери, збирати статистику та обслуговувати мережевий стек.

З цієї причини `NO_HZ_FULL` вимагає жорсткого розділення ядер системи на дві категорії:

1. **Housekeeping CPU (зазвичай CPU 0):** Службові ядра, на яких `NO_HZ_FULL` вимкнено. Вони продовжують генерувати періодичний тик з частотою `CONFIG_HZ`, оновлюють лічильник `jiffies`, підтримують системний годинник (wall clock), обробляють апаратні переривання I/O та виконують системні служби.
2. **Adaptive Tickless / Isolated CPUs (наприклад, CPU 1..N):** Ізольовані ядра, призначені для виконання низькозатримкових задач. При переході користувацького потоку в режим виконання ядро вимикає системний тик на цих ядрах.

### 3.2 Внутрішня структура `struct tick_sched` та точки контролю

У внутрішній архітектурі ядра стан системного таймера для кожного CPU описується структурою `struct tick_sched`, що оголошена у `kernel/time/tick-sched.h`:

:::tabs
```c
struct tick_sched {
    struct hrtimer          sched_timer;
    enum tick_nohz_mode     nohz_mode;
    ktime_t                 last_tick;
    ktime_t                 next_tick;
    int                     inidle;
    int                     tick_stopped;
    unsigned long           idle_jiffies;
    unsigned long           idle_calls;
    unsigned long           idle_sleeps;
    ktime_t                 idle_entrytime;
    atomic_t                check_clocks;
};
```
```cpp
struct tick_sched {
    hrtimer                 sched_timer;
    tick_nohz_mode          nohz_mode;
    ktime_t                 last_tick;
    ktime_t                 next_tick;
    int                     inidle;
    int                     tick_stopped;
    unsigned long           idle_jiffies;
    unsigned long           idle_calls;
    unsigned long           idle_sleeps;
    ktime_t                 idle_entrytime;
    atomic_t                check_clocks;
};
```
:::

Перевірка можливості зупинки тику виконується функцією `tick_nohz_full_check()`, яка викликається під час переходу з режиму ядра у режим користувача (`user_enter_irqoff()`). Якщо прапорець `tick_nohz_full_running` встановлено в `true`, а кількість runnable-процесів у черзі дорівнює 1 (`rq->nr_running == 1`), ядро викликає `tick_nohz_stop_sched_tick()`, зупиняючи локальний таймер APIC.

### 3.3 Підсистема відстеження контексту (Context Tracking)

Режим `NO_HZ_FULL` критично залежить від підсистеми ядра Context Tracking (`CONFIG_CONTEXT_TRACKING`). Ця підсистема відстежує точний момент, коли процесор перетинає межу між режимом користувача (Ring 3) та режимом ядра (Ring 0).

Коли потік повертається з ядреного виклику або переривання у userspace, підсистема викликає `user_enter_irqoff()`, сигналізуючи ядру, що процесор більше не виконує ядрений код і переривання таймера можна безпечно зупинити. Навпаки, коли потік виконує системний виклик або зазнає переривання, викликається `user_exit_irqoff()`, який відновлює системну активність.

Ціна Context Tracking: на кожному переході Ring 3 ↔ Ring 0 ядро виконує додаткові інструкції відстеження контексту. Це викликає невелику додаткову затримку на системних викликах (slow path), але повністю окуповується відсутністю тиків під час тривалого обчислення в userspace.

## 4. Підсистема RCU та RCU Offloading (rcu_nocbs)

Найважчим бар'єром на шляху створення `NO_HZ_FULL` була залежність підсистеми RCU (Read-Copy Update) від переривань таймера.

В архітектурі RCU читачі отримують доступ до даних без блокувань, а письменники створюють копії структур, оновлюють вказівники та реєструють відкладені колбеки для звільнення старої пам'яті. Звільнити пам'ять можна лише після проходження періоду очікування (*grace period*), коли всі CPU системи пройдуть через стан спокою (*quiescent state*).

### 4.1 Проблема RCU Grace Period без тиків

У традиційному ядрі саме системний тик перевіряє, чи перебуває CPU у стані спокою (наприклад, у режимі користувача або під час перемикання контексту). Якщо вимкнути тик на ізольованому ядрі, це ядро перестане сигналізувати RCU про проходження станів спокою. Як наслідок, глобальний grace period RCU зависне (*RCU stall*), що призведе до вичерпання пам'яті ядра або виклику Kernel Panic.

### 4.2 Делегування RCU колбеків: `rcu_nocbs`

Коли потік на ізольованому CPU генерує RCU-колбек, локальне виконання цього колбеку вимагало б локальних тиків таймера для відстеження стану спокою та виклику процедури звільнення пам'яті `kfree()`. Щоб уникнути цього, потік лише додає новий колбек до безблокувальної черги і негайно повертається до обчислень користувача без зупинки та без тиків. Натомість спеціальний потік ядра `rcuo/X` (де `X` — номер ізольованого CPU), примусово прив'язаний до Housekeeping-ядра (CPU 0), витягає колбеки з цієї черги, відстежує проходження grace period та самостійно виконує звільнення пам'яті.

```
Ізольований CPU (CPU 1)         Housekeeping CPU (CPU 0)
-----------------------         ------------------------
Реєструє RCU колбек       →     Потік rcuo/1 отримує колбек
Продовжує обчислення            Перевіряє Grace Period
(Без зупинки та тиків)           Виконує kfree() пам'яті
```

Така схема винесення обробки відкладених викликів називається механізмом **RCU Offloading** (`rcu_nocbs` — *RCU no callbacks*). При активації прапорця `rcu_nocbs=<cpulist>` ядро створює системні нитки `rcuo/X` та `rcuc/X`, які прив'язуються (*pinned*) до Housekeeping-ядер (CPU 0) і повністю звільняють ізольовані ядра від обслуговування RCU-колбеків.

## 5. Практична конфігурація ізоляції ядер

Ввімкнення опції `CONFIG_NO_HZ_FULL=y` у конфігурації ядра під час компіляції надає лише інфраструктуру. Для досягнення режиму без тиків необхідно правильно сформувати параметри завантаження ядра в завантажувачі GRUB.

### 5.1 Аргументи командного рядка ядра (cmdline)

Розглянемо випадок 16-ядерної системи, де CPU 0 виділено для службово-господарських потреб ОС, а ядра CPU 1-15 ізолюються для низькозатримкового додатку.

Для забезпечення детермінованої роботи необхідно завчасно усунути два джерела затримок:
- **Затримки пробудження C-states:** При переході ядер у глибші стани сну (C-states) та динамічній зміні частоти (P-states) будь-яке нове завдання зазнає затримки на пробудження (від десятків до сотень мікросекунд), а нестабільна частота викликає коливання продуктивності. Заборонивши глибокі стани сну та динамічне керування частотою, ядро утримує процесор у постійній готовності.
- **Шторм таймерів (Timer Storm):** Коли кілька Housekeeping-ядер одночасно генерують переривання таймера на одній мілісекундній межі, виникає сплеск системного навантаження (*timer storm*). Синхронізовані переривання створюють колізії на системній шині. Зсув моментів спрацювання таймерів між Housekeeping-ядрами розмиває цей пік у часі.

З урахуванням цих механізмів у файлі `/etc/default/grub` параметр `GRUB_CMDLINE_LINUX` доповнюється наступним набором аргументів:

```bash
isolcpus=1-15 nohz_full=1-15 rcu_nocbs=1-15 irqaffinity=0 intel_pstate=disable processor.max_cstate=0 skew_tick=1
```

Призначення кожного параметра:

- **`isolcpus=1-15`:** Виключає ядра 1-15 з автоматичного розподілу задач планувальником CFS. Поточні звичайні процеси системи ніколи не потраплять на ці ядра.
- **`nohz_full=1-15`:** Вмикає режим Adaptive Tickless на ядрах 1-15.
- **`rcu_nocbs=1-15`:** Делегує обробку RCU-колбеків з ядер 1-15 на Housekeeping-ядра.
- **`irqaffinity=0`:** Встановлює маску приналежності апаратних переривань за замовчуванням на CPU 0. Жодне мережеве чи дискове переривання не потрапить на ядра 1-15, якщо воно явно туди не спрямоване.
- **`intel_pstate=disable processor.max_cstate=0`:** Вимикає регулювання частоти та перехід у стан C-states для запобігання затримкам пробудження та плаваючим частотам CPU.
- **`skew_tick=1`:** Зміщує за часом моменти генерування переривань таймера між службовими ядрами Housekeeping, запобігаючи одночасним сплескам системних переривань (*timer storm*).

### 5.2 Ураження апаратної топології SMT / Hyper-Threading

На процесорних архітектурах із підтримкою симетричної багатопотоковості SMT (Simultaneous Multithreading / Intel Hyper-Threading) кожне фізичне ядро ділиться на два логічних CPU. Вони спільно використовують конвеєр інструкцій, блок обчислень з плаваючою крапкою (FPU) та кеші L1/L2.

Якщо ізолювати лише логічний CPU 1, але залишити парний логічний CPU 17 (його SMT-брата) у загальному пулі планувальника CFS, процеси на CPU 17 викличуть вимивання кешів L1/L2 та конкуренцію за виконавчі блоки.

Існує два варіанти вирішення проблеми SMT:
1. **Повне вимкнення SMT в BIOS/UEFI або cmdline:** Передача параметра `nosmt` у командному рядку завантажувача.
2. **Парна ізоляція SMT-потоків:** Одночасна ізоляція обох логічних ядер одного фізичного ядра (наприклад, `nohz_full=1,17`).

### 5.3 Ізоляція фонових воркерів (Workqueues)

Окрім параметрів ядра, необхідно забезпечити, щоб незв'язані черги робіт ядра (Unbound Workqueues) не виконували потоки `kworker` на ізольованих ядрах. Для цього підсистема sysfs надає вузол маски приналежності CPU. Маска `1` є шістнадцятковим бітовим масивом, де встановлено лише біт 0 (що відповідає CPU 0). Запис цього значення звужує дозволений список ядер для всіх unbound workqueues виключно до Housekeeping-ядра CPU 0, витісняючи фонові воркери з ізольованих ядер.

Конфігурація здійснюється через системний файл sysfs:

```bash
echo 1 > /sys/devices/virtual/workqueue/cpumask
```

### 5.4 Управління системними демонами та обмеженнями RT

Навіть після застосування параметрів cmdline деякі системні служби можуть порушити ізоляцію:

1. **Демон `irqbalance`:** Автоматично перерозподіляє апаратні IRQ між ядрами системи. Демон необхідно примусово вимкнути:
   ```bash
   systemctl disable --now irqbalance
   ```
2. **Демони аудіту `auditd`:** Можуть фіксувати системні виклики та генерувати міжпроцесорні події.
3. **Обмеження RT Throttling:** За замовчуванням ядро обмежує потоки `SCHED_FIFO` до 95% часу процесора (`/proc/sys/kernel/sched_rt_runtime_us = 950000`). Для ізольованих ядер це обмеження вимикають:
   ```bash
   echo -1 > /proc/sys/kernel/sched_rt_runtime_us
   ```

### 5.5 Прив'язка процесів (Affinity) та Cgroups v2

Для запуску робочого навантаження на ізольованому ядрі використовується утиліта `taskset` або механізм Cgroups v2.

Запуск через `taskset`:
```bash
taskset -c 1 ./low_latency_app
```

В ієрархії cgroups v2 створюється контролер `cpuset`:
```bash
mkdir /sys/fs/cgroup/isolated
echo "1" > /sys/fs/cgroup/isolated/cpuset.cpus
echo "0" > /sys/fs/cgroup/isolated/cpuset.mems
echo "isolated" > /sys/fs/cgroup/isolated/cpuset.cpus.partition
echo $PID > /sys/fs/cgroup/isolated/cgroup.procs
```

## 6. Причини повернення системного тику (Isolation Breaks)

Режим `NO_HZ_FULL` є крихким станом ядра. Якщо при виконанні користувацького потоку виникає подія, яка вимагає втручання ядра або порушує умову монополії, ядро **негайно увімкне системний тик знову**.

Розглянемо основні джерела порушення ізоляції (isolation breaks):

### 6.1 Системні виклики (Syscalls)

При виконанні будь-якого системного виклику (наприклад, `read()`, `write()`, `sys_epoll_wait()`, `sched_yield()`) відбується перехід з користувацького режиму Ring 3 у режим ядра Ring 0 через інструкцію `syscall`. Ядро Linux активує таймер для відстеження часу виконання системного виклику.

**Шлях усунення:** 
Використання технологій **Kernel Bypass** (обхід ядра).
- **Мережевий I/O:** Застосування фреймворків DPDK (Data Plane Development Kit), Solarflare OpenOnload або AF_XDP. Додаток опитує кільцеві буфери мережевої карти (ring buffers) безпосередньо з userspace через DMA без системних викликів.
- **Міжпроцесна взаємодія (IPC):** Використання спільної пам'яті (`shmget`, `mmap`) з атомарними безблокувальними кільцевими буферами (Lock-free Ring Buffers) та циклічним опитуванням (*busy polling*) замість POSIX сокетів чи пайпів.

### 6.2 Сторінкові помилки (Page Faults)

Якщо програма звертається до пам'яті, виділеної через `malloc()` або `mmap()`, але ще не відображеної на фізичні сторінки DRAM (лінива алокація *lazy allocation*), виникає Minor Page Fault. Процесор генерує переривання, ядро зупиняє потік, алокує фізичний кадр пам'яті та оновлює таблиці сторінок (Page Tables). Цей процес активує системний тик.

**Шлях усунення:**
Виклик `mlockall(MCL_CURRENT | MCL_FUTURE)` під час ініціалізації та обов'язкове прогрівання пам'яті (`memset`) до входу в критичний цикл.

Повний працездатний приклад ініціалізації середовища низької затримки мовами C та C++ наведено у вставці [⚙️ Практична ізоляція ядра та вимірювання джитера](book:unix-linux/nohz-adaptive-tickless/proj-cpu-isolation.md).

### 6.3 Конфлікт процесів на ядрі

Якщо на ізольоване ядро випадково потрапляє другий Runnable потік (наприклад, потік ядра `kworker` або другий процес користувача), умова монополії `Runnable tasks = 1` порушується. Планувальник CFS негайно вмикає системний тик для квантування часу між процесами.

**Шлях усунення:**
Суворе дотримання правила «один процес — одне ізольоване ядро».

### 6.4 Системний таймер NMI Watchdog

Таймер NMI (Non-Maskable Interrupt) Watchdog періодично генерує немасковані переривання для виявлення зависань ядра. Ці переривання пробивають будь-яку ізоляцію.

**Шлях усунення:**
Вимкнення watchdog через sysctl:
```bash
sysctl -w kernel.watchdog=0
```

## 7. Методологія діагностики та верифікації

Для підтвердження того, що системний тик на ізольованому ядрі справді вимкнено, використовуються системні інструменти моніторингу та трасування.

### 7.1 Аналіз /proc/interrupts

Найпростішим способом верифікації є моніторинг лічильника переривань `LOC` (Local timer interrupts).

Виконайте команду опитування з інтервалом в 1 секунду:
```bash
watch -n 1 "cat /proc/interrupts | grep LOC"
```

Очікувана поведінка:
- **CPU 0 (Housekeeping):** Лічильник зростає на значення `CONFIG_HZ` щосекунди (наприклад, +1000 тиків/сек).
- **CPU 1 (Isolated `NO_HZ_FULL`):** Лічильник залишається **абсолютно статичним** під час виконання гарячого циклу користувача.

### 7.2 Трасування через ftrace

Для виявлення прихованих переривань ядро розміщує точкові монітори безпосередньо у викликах обробників векторів переривань. Під час входження в обробник підсистема трасування зберігає часову мітку, номер CPU та вектор переривання у кільцевий буфер (ring buffer) пам'яті ядра без зупинки роботи процесора. Аналіз цього кільцевого буфера дозволяє точно визначити частоту та причини генерації переривань.

Цей механізм реалізовано в системній інфраструктурі `ftrace`. Трасування події `local_timer_entry` фіксує у кільцевому буфері вектори переривань локального таймера APIC:

```bash
echo 0 > /sys/kernel/tracing/tracing_on
echo > /sys/kernel/tracing/trace
echo 1 > /sys/kernel/tracing/events/irq_vectors/local_timer_entry/enable
echo 1 > /sys/kernel/tracing/tracing_on
```

Якщо у виводі кільцевого буфера `/sys/kernel/tracing/trace` з'являються записи для ізольованого CPU 1, це сигналізує про порушення ізоляції.

Повний довідник sysfs-вузлів та tracepoints ядра наведено у вставці [📋 Інтерфейси опитування та конфігурації NO_HZ_FULL](book:unix-linux/nohz-adaptive-tickless/api-nohz-sysfs.md).

## 8. Проектування високопродуктивних систем без джитера

Адаптивне ядро без тиків створює унікальний дуалізм в операційній системі Linux. На Housekeeping-ядрах Linux функціонує як універсальна ОС загального призначення з повною підтримкою мережевого стеку, файлових систем та баз даних. На ізольованих ядрах Linux перетворюється на ультралегке середовище виконання з властивостями операційної системи реального часу (RTOS).

### 8.1 Порівняння PREEMPT_RT та NO_HZ_FULL

Для створення ультра-низькозатримкових систем часом поєднують патч детермінізму ядра `PREEMPT_RT` та механізм `NO_HZ_FULL`. Важливо розуміти відмінність їх фундаментальних задач:

- **PREEMPT_RT (Real-Time Patch):** Робить обробники переривань та критичні секції ядра витісняємими (*preemptible*). Мета PREEMPT_RT — мінімізувати найгірший час відповіді ядра (*worst-case execution time, WCET*) при виклику системних функцій чи реакції на апаратні переривання.
- **NO_HZ_FULL (Adaptive Tickless):** Усуває сам факт виникнення переривань таймера під час виконання користувацького коду. Мета NO_HZ_FULL — надати користувацькому потоку 100% циклів CPU без жодних втручань з боку ОС.

При поєднанні `PREEMPT_RT` та `NO_HZ_FULL` досягається синергетичний ефект: потік у userspace працює без тиків (NO_HZ_FULL), а якщо йому все ж доводиться виконати рідкісний системний виклик або обробити I/O, ядро виконує його з детермінованою низькою затримкою (PREEMPT_RT).

### 8.2 Чекліст інженера для zero-jitter архітектури

Побудова систем із нульовим джитером (zero-jitter) вимагає суворого дотримання послідовності етапів конфігурації. На першому етапі ізолюються фізичні та логічні ресурси процесора на рівні завантажувача ядра. На другому — вимикаються фонові сервіси, демони перерозподілу переривань та немасковані системні таймери. На третьому — прикладний процес налаштовує власну прив'язку до ядра, пріоритет реального часу та закріплює пам'ять у DRAM. На завершальному етапі програма входить у безблокувальний цикл опитування (busy-spin) з обходом системних викликів. Послідовність цих етапів підсумовано у наступному чеклісті:

```
[Параметри ядра]    isolcpus=1..N nohz_full=1..N rcu_nocbs=1..N irqaffinity=0
        ↓
[Налаштування ОС]   systemctl disable irqbalance; sysctl kernel.watchdog=0
        ↓
[Ініціалізація APP] pthread_setaffinity_np() → SCHED_FIFO 99 → mlockall()
        ↓
[Гарячий цикл]      Busy-spin loop + vDSO clock_gettime / RDTSC + Kernel Bypass
```

Завдяки інтеграції `NO_HZ_FULL` із сучасними інструментами оркестрації (такими як Kubernetes CPU Manager з політикою `static`), технологія адаптивного ядра без тиків стала стандартом для розгортання віртуалізованих мережевих функцій (NFV), телеком-вузлів 5G та фінансових торгових платформ із гарантованою субмікросекундною передбачуваністю затримок.
