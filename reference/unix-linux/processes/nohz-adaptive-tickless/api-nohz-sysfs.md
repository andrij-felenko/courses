# 📋 Інтерфейси опитування та конфігурації NO_HZ_FULL: sysfs, procfs, ftrace

Підсистема ядра Linux `NO_HZ_FULL` надає розширений комплекс системних інтерфейсів у псевдофайлових системах `sysfs`, `procfs` та `tracefs` для детальної верифікації стану системного тику, відстеження апаратних і програмних переривань та локалізації джерел порушення ізоляції ядер (*isolation breaks*).

### 1. Докладний розбір інтерфейсів sysfs та procfs

Псевдофайлова система `sysfs` відображає поточну конфігурацію ядра та підсистеми ізоляції CPU. Нижче наведено повний розбір ключових вузлів:

#### 1.1 Системні вузли sysfs
- `/sys/devices/system/cpu/nohz_full`
  Текстовий файл із діапазоном логічних ядер CPU, для яких активовано режим Adaptive Tickless при завантаженні ядра (наприклад, `1-15`) — ядро друкує сюди вміст внутрішньої маски `tick_nohz_full_mask` у людському записі cpulist. Якщо параметр `nohz_full=` не було передано в командному рядку завантажувача, файл залишається порожнім; якщо опцію `CONFIG_NO_HZ_FULL` вимкнено у конфігу ядра, файла немає взагалі. Програми у користувацькому просторі зчитують цей файл для автоматичного вибору вільних безтикових ядер.

- `/sys/devices/system/cpu/isolated`
  Містить маску логічних ядер, примусово виключених зі звичайного планування CFS за допомогою параметра завантаження `isolcpus=`. Ядра з цього списку не беруть участі у загальному балансуванні навантаження, збереженні енергії чи перерозподілі потоків.

- `/sys/devices/system/cpu/present` та `/sys/devices/system/cpu/online`
  Відображають фізично присутні та активні на даний момент ядра CPU. Порівняння цих файлів із `nohz_full` дозволяє переконатися, що всі ізольовані ядра перебувають в онлайн-стані та доступні для прив'язки потоків.

#### 1.2 Файли псевдофайлової системи procfs
- `/proc/cmdline`
  Текстовий файл, що містить точну копію параметрів завантаження ядра, переданих завантажувачем GRUB або systemd-boot. Дозволяє верифікувати наявність та коректність синтаксису параметрів `nohz_full=`, `rcu_nocbs=`, `irqaffinity=`, `isolcpus=`.

- `/proc/interrupts`
  Відображає таблицю лічильників апаратних та міжпроцесорних переривань у розрізі кожного логічного ядра з моменту завантаження ОС. Для аналізу ефективності `NO_HZ_FULL` ключове значення мають наступні рядки:
  - `LOC` (Local timer interrupts): Лічильник переривань локального апаратного таймера APIC. На ізольованому ядрі під час виконання користувацького коду цей лічильник зобов'язаний замирати і не зростати.
  - `RES` (Rescheduling interrupts): Міжпроцесорні переривання IPI, що надсилаються планувальником з інших ядер для виклику примусового перепланування.
  - `CAL` (Function call interrupts): Переривання IPI для виконання викликів функцій ядра на віддаленому CPU.
  - `TLB` (TLB shootdowns): Переривання скидання буферів асоціативної трансляції адреси при зміні таблиць сторінок у паралельних потоках.

- `/proc/softirqs`
  Статистика виконання м'яких програмних переривань (SoftIRQs) у розрізі ядер. Для `NO_HZ_FULL` критичними є рядки `TIMER` (обробка м'яких таймерів), `SCHED` (планувальник), `RCU` (колбеки RCU) та `NET_RX`/`NET_TX` (мережевий стек). Будь-яке зростання цих лічильників на ізольованому ядрі сигналізує про витік системної активності.

#### 1.3 Системні параметри sysctl для управління затримками
- `/proc/sys/kernel/watchdog` та `/proc/sys/kernel/nmi_watchdog`
  Контрольні параметри підсистеми NMI Watchdog. Значення `1` вказує на активний моніторинг зависань ядра через немасковані переривання NMI, які регулярно переривають ізольовані ядра. Для повного усунення jitter на ізольованих ядрах значення записується як `0`.

- `/proc/sys/kernel/sched_rt_runtime_us`
  Визначає кількість мікросекунд на секунду, доступних для потоків реального часу `SCHED_FIFO`/`SCHED_RR`. За замовчуванням встановлено значення `950000` (тобто 95% часу), залишаючи 5% для звичайних процесів. Для ізольованих ядер безтикового режиму це значення встановлюють у `-1`, що повністю вимикає притлумлення (*RT throttling*) і надає потоку 100% циклів процесора.

### 2. Ключові Tracepoints у tracefs / ftrace

Для точної локалізації причин відновлення системного тику використовується підсистема трасування ядра `ftrace`, яка доступна за шляхом `/sys/kernel/tracing/` (або `/sys/kernel/debug/tracing/`).

Система надає спеціальні точкові події (*tracepoints*):

1. `irq_vectors:local_timer_entry`
   Викликається при кожному вході в обробник локального таймера APIC. Якщо ця подія фіксується на ізольованому ядрі під час виконання обчислювального циклу користувача, це є беззаперечним доказом відновлення системного тику та порушення режиму без тиків.

2. `sched:sched_switch`
   Фіксує момент перемикання контексту між процесами. Дозволяє виявити появу другого runnable-процесу або фонового потоку ядра (`kworker`), що порушує монополію `NO_HZ_FULL`.

3. `raw_syscalls:sys_enter`
   Генерується при кожному виконанні системного виклику з користувацького простору (Ring 3 -> Ring 0). Відображає точний номер системного виклику (`NR`), який спричинив повернення тиків.

4. `workqueue:workqueue_execute_start`
   Фіксує запуск фонової задачі ядра з черги воркерів (workqueue) на даному CPU.

5. `rcu:rcu_utilization` та `rcu:rcu_grace_period`
   Відображають активність підсистеми RCU, дозволяючи перевірити, чи нормально функціонує віддалена обробка RCU-колбеків через `rcu_nocbs`.

### 3. Практичний сценарій діагностики ізоляції через ftrace

Щоб відфільтрувати трасування виключно для досліджуваного ядра, використовується бітова маска `tracing_cpumask`. У поєднанні з фіксацією таймера події `sys_enter` перехоплюють номери системних викликів користувача, а `workqueue_execute_start` виявляє запуск фонових воркерів `kworker`, дозволяючи точно ідентифікувати джерело кожного порушення.

Для детального аналізу причин виникнення jitter на ізольованому CPU 1 виконується наступний покроковий bash-скрипт від імені користувача `root`:

```bash
# 1. Зупиняємо поточне трасування та очищаємо буфер
echo 0 > /sys/kernel/tracing/tracing_on
echo > /sys/kernel/tracing/trace

# 2. Встановлюємо маску відстеження лише для CPU 1 (бітова маска: 2^1 = 2)
echo 2 > /sys/kernel/tracing/tracing_cpumask

# 3. Активуємо ключові точкові події
echo 1 > /sys/kernel/tracing/events/irq_vectors/local_timer_entry/enable
echo 1 > /sys/kernel/tracing/events/sched/sched_switch/enable
echo 1 > /sys/kernel/tracing/events/raw_syscalls/sys_enter/enable
echo 1 > /sys/kernel/tracing/events/workqueue/workqueue_execute_start/enable

# 4. Вмикаємо кільцевий буфер трасування
echo 1 > /sys/kernel/tracing/tracing_on

# 5. Виконуємо досліджуваний низькозатримковий додаток на CPU 1
taskset -c 1 ./low_latency_app

# 6. Зупиняємо трасування
echo 0 > /sys/kernel/tracing/tracing_on

# 7. Переглядаємо перші 40 подій трасування
cat /sys/kernel/tracing/trace | head -n 40
```

Якщо у виводі командної стрічки фіксуються події `local_timer_entry`, аналіз відповідних їм подій `sys_enter` або `workqueue_execute_start` дозволяє точно визначити файл, рядок коду чи системний процес, який порушив режим без тиків.

### 4. Використання інструменту perf для профілювання затримок

Окрім ftrace, для моніторингу затримок із побудовою стека викликів використовується системний профілювальник `perf`. Під час моніторингу затримок важливо відновити повний ланцюжок викликів, який призвів до переходу в ядро: прапорець `-g` змушує `perf` зчитувати вказівники стекових кадрів (frame pointers) при кожній зафіксованій події, формуючи повний стек викликів (call stack) від функції користувацького коду до обробника в ядрі.

```bash
# Запис подій локального таймера та системних викликів на CPU 1 протягом 10 секунд
perf record -C 1 -e irq_vectors:local_timer_entry,raw_syscalls:sys_enter -g -- sleep 10

# Формування звіту з деревом викликів
perf report --stdio
```

Завдяки цьому інженер отримує повне стекове трасування (stack trace) моментів входу в ядро, що дозволяє швидко усунути небажані системні виклики або звернення до системних ресурсів у низькозатримковому коді.
