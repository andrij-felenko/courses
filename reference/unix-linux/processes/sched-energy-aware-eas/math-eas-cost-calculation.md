# 🧮 Математика обчислення енергетичних витрат в EAS

Ця вставка надає точний математичний апарат, за допомогою якого функція `compute_energy()` у ядрі Linux обчислює прогнозоване енергоспоживання процесорних кластерів при прийнятті рішень про розміщення задач.

## 1. Нормалізація навантаження та ємності процесів

Для приведення всіх ядер гетерогенної системи до єдиного обчислювального знаменника ядро Linux використовує константу максимальної ємності `SCHED_CAPACITY_SCALE = 1024`.

Кожен процесор `c` у системі має константну вихідну місткість `capacity_orig(c)`, яка визначається його мікроархітектурою на максимальній робочій частоті. Якщо найпотужніше ядро системи (наприклад, Cortex-X4) прийнято за `capacity_orig = 1024`, то енергоефективне ядро (Cortex-A520) може мати `capacity_orig = 410`.

Поняття ємності дозволяє планувальнику порівнювати швидкість виконання задач на ядрах з різною обчислювальною потужністю. Задача, якій для виконання потрібна певна кількість інструкцій, виконається на ядрі з `capacity_orig = 1024` у 2.5 рази швидше, ніж на ядрі з `capacity_orig = 410`.

Навантаження окремої задачі `t` вимірюється підсистемою Per-Entity Load Tracking (PELT) і виражається величиною `util_avg(t) ∈ [0, 1024]`. Показник `util_avg(t)` є експоненціально зваженим ковзним середнім часу, протягом якого потік перебував у стані готовності до виконання.

Оскільки навантаження PELT відносне до часу виконання на поточному ядрі, при оцінці перенесення задачі на інше ядро з іншою місткістю `capacity_orig(c_target)`, ядро виконує нормалізацію навантаження. Це гарантує, що оцінка часу виконання залишається інваріантною відносно апаратної швидкості ядра.

Формула нормалізації навантаження задачі:

```
util_task_normalized = util_avg(t) · (1024 / capacity_orig(c_current))
```

Сумарне поточне навантаження ядра `c` обчислюється як сума сигналів PELT усіх процесів, що перебувають у його черзі виконання (runqueue):

```
util_cpu(c) = ∑ util_avg(t_i)    для всіх t_i ∈ runqueue(c)
```

## 2. Моделювання навантаження домену продуктивності

Процесорна система розбита на `M` доменів продуктивності `D_1, D_2, ..., D_M`. Усі ядра всередині одного домену `D_m` функціонують на спільній робочій частоті `f(D_m)`. Це означає, що підвищення частоти для одного ядра в домені автоматично піднімає частоту і споживання всіх інших ядер цього кластера.

При оцінці candidate-ядра `c_cand ∈ D_k` для розміщення задачі `t`, ядро обчислює гіпотетичне нове навантаження кожного ядра домену `D_m`. Для ядер, на які задача не призначається, навантаження залишається незмінним, а для candidate-ядра додається нормалізоване навантаження задачі.

Рівняння прогнозованого навантаження ядра:

```
util_new(c) = util_cpu(c) + util_task_normalized,    якщо c = c_cand
util_new(c) = util_cpu(c),                            якщо c ≠ c_cand
```

Оскільки частота всього домену продуктивності вимушена підлаштовуватися під найзавантаженіше ядро в кластері, необхідна обчислювальна спроможність домену `U(D_m)` визначається як максимум серед усіх його ядер. Якщо одне ядро завантажене на 70%, а інші три — на 10%, увесь домен працюватиме на частоті, необхідній для покриття 70% навантаження.

Формула визначення пікового навантаження домену:

```
U(D_m) = max( util_new(c) )    для всіх c ∈ D_m
```

З урахуванням 25-відсоткового запасу частоти (headroom), який вимагає регулятор `schedutil` для запобігання насиченню ядра на 100%, ефективний запит продуктивності домену вираховується за формулою:

```
U_request(D_m) = 1.25 · U(D_m)
```

Запит `U_request(D_m)` додатково обмежується верхньою стелею вихідної ємності домену `capacity_orig(D_m)`. Якщо підсумковий запит перевищує вихідну ємність ядра, це означає, що ядро не здатне обробити задачу без виникнення черг та затримок.

## 3. Пошук OPP та обчислення потужності домену

Кожен домен `D_m` має у фреймворку Energy Model таблицю станів продуктивності `em_perf_state`, яка складається з `N` впорядкованих записів:

```
OPP_0, OPP_1, ..., OPP_{N-1}
```

Кожен стан `OPP_i` містить такі величини:
- `frequency_i`: робоча частота в кілогерцах;
- `power_i`: споживана потужність у міліватах (мВт);
- `performance_i`: обчислювальна здатність домену на даній частоті, масштабована до 1024.

Планувальник виконує бінарний пошук по таблиці станів, знаходячи найменший індекс `k`, який задовольняє умову покриття навантаження:

```
performance_k ≥ (U_request(D_m) · 1024) / capacity_orig(D_m)
```

Пошук найменшого індексу `k` гарантує, що система обере мінімально можливу частоту, здатну виконати заданий обсяг роботи. Це мінімізує динамічні витрати потужності `P_dyn ∝ V² · f`.

Якщо такий стан знайдено, споживана потужність домену `P(D_m)` приймається рівною `power_k`. Якщо запит перевищує максимальну здатність домену (`U_request > capacity_orig`), обирається останній стан з максимальною потужністю `power_{N-1}`.

Сумарне прогнозоване енергоспоживання всієї процесорної системи `E_total` обчислюється як сума потужностей усіх доменів продуктивності:

```
E_total(c_cand) = ∑ P(D_m)    для всіх m від 1 до M
```

Ця формула враховує не лише ядро, на яке претендує задача, а й непрямий вплив на сусідні ядра кластера: якщо додавання задачі змушує весь кластер підняти частоту з 600 МГц до 1.2 ГГц, потужність `P(D_m)` зросте для всіх активних ядер цього домену.

## 4. Оцінка стану простою та штрафу за пробудження C-states

Якщо ядро `c` перебуває у стані простою (CPU Idle / C-state), його споживання в режимі `E_current` вважається близьким до нуля. Однак вихід з глибокого стану сну вимагає витрат енергії на відновлення живлення шини, синхронізацію шин та інвалідацію кеш-пам'яті.

Планувальник EAS враховує термальний та енергетичний штраф за пробудження. Якщо кандидатне ядро спить, до обчисленого споживання додається величина штрафу `E_wake_penalty`:

```
E_wake_penalty = exit_latency(C_state) · P_transition
```

Значення `exit_latency` береться з підсистеми `cpuidle` і опирається на характеристики поточного C-стану (наприклад, C1, C2 чи C6). Чим глибший стан сну ядра, тим вища затримка виходу і тим більший енергетичний штраф.

При розрахунку `E(c_cand)` для ядра, що спить, планувальник додає значення `E_wake_penalty` до підсумкового споживання домену. Це створює математичну перевагу для "пакування" задач на вже активні ядра, запобігаючи марному виведенню інших ядер зі стану простою.

## 5. Обчислення енергетичної дельти та правило вибору

Перед початком порівняння кандидатів алгоритм обчислює поточне енергоспоживання всієї системи `E_current` за початкового розподілу задач:

```
E_current = ∑ P_current(D_m)   для всіх m від 1 до M
```

Для кожного допустимого ядра-кандидата `c ∈ {c_1, c_2, ..., c_K}` обчислюється прогнозоване споживання `E(c)` та енергетична дельта `ΔE(c)`:

```
ΔE(c) = E(c) - E_current
```

Значення `ΔE(c)` відображає чистову зміну потужності всієї системи у міліватах. Якщо `ΔE(c) < 0`, додавання задачі дає оптимізацію споживання (наприклад, за рахунок перенесення з ненажерливого ядра big на завантажене LITTLE з нижчою питомою вартістю). Якщо `ΔE(c) > 0`, споживання системи зросте.

Остаточний вибір ядра `c_best` здійснюється за правилом мінімізації енергетичної дельти при суворому дотриманні обмеження поточної ємності:

```
c_best = arg min ( ΔE(c) )

за умов:
1. util_cpu(c) + util_task ≤ 0.80 · capacity_of(c)
2. ΔE(c) < 0  або  c = prev_cpu
```

Перша умова гарантує, що ядро не увійде в стан перевантаження (Over-Utilized). Поріг 80% запевняє 20-відсотковий запас емності, що запобігає виникненню черг виконання. Друга умова забезпечує, що задача змінить ядро лише тоді, коли міграція дає реальну економію енергії (`ΔE < 0`). Якщо жодне ядро не дає економії, задача повертається на своє попереднє ядро `prev_cpu`, що виключає витрати на міжядерну міграцію та перезапуск кешів.
