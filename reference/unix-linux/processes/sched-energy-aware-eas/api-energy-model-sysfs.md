# 📋 Інтерфейси sysfs та API Energy Model

Цей довідник описує програмні структури ядра Linux, C-функції реєстрації доменів енергоспоживання, а також файлові інтерфейси `sysfs`, `sysctl` та `debugfs` для налаштування й діагностики підсистеми Energy Model (EM) та Energy-Aware Scheduling (EAS).

## 1. Програмні структури ядра (`include/linux/energy_model.h`)

Підсистема Energy Model описує апаратні профілі енергоспоживання за допомогою двох основних структур даних: стани продуктивності `struct em_perf_state` та домени продуктивності `struct em_perf_domain`.

```c
struct em_perf_state {
    unsigned long frequency;   /* Робоча частота домену в кілогерцах (кГц) */
    unsigned long power;       /* Споживана потужність у міліватах (мВт) або мікроватах */
    unsigned long cost;        /* Обчислена вартість виконання = (power / performance) * 1024 */
    unsigned long flags;       /* Внутрішні прапорці стану (наприклад, EM_PERF_STATE_INEFFICIENT) */
};

struct em_perf_domain {
    struct em_perf_state *table; /* Масив станів OPP, відсортований за зростанням частоти */
    int nr_perf_states;          /* Кількість доступних станів OPP у масиві table */
    int flags;                   /* Прапорці домену (наприклад, EM_PERF_DOMAIN_MICROWATTS) */
    unsigned long cpus[1];       /* Бітова маска CPU, що входять до даного домену */
};
```

Поле `frequency` описує робочу частоту ядра в кілогерцах. Поле `power` містить споживану потужність кластера на цій частоті. Якщо прапорець `EM_PERF_DOMAIN_MICROWATTS` увімкнено, значення потужності подається в мікроватах (мкВт), інакше — у відносних абстрактних одиницях. 

Поле `cost` розраховується автоматично при реєстрації домену як відношення споживаної потужності до продуктивності, масштабоване до порогу 1024. Це поле дозволяє планувальнику EAS порівнювати відносну вартість обчислень на різних станах OPP за одну операцію бінарного пошуку.

Масив `table` усередині `struct em_perf_domain` виділяється як суцільна read-only ділянка пам'яті під час реєстрації домену і залишається незмінним протягом усього часу роботи системи. Це забезпечує мінімальні накладні витрати кешу при зверненні з гарячого шляху планувальника.

## 2. Kernel C API для реєстрації драйверів платформи

Драйвери процесорної платформи (наприклад, cpufreq, SCMI або ACPI CPPC) реєструють домени продуктивності у фреймворку Energy Model під час завантаження системи.

Основними функціями API є:

```c
int em_dev_register_perf_domain(
    struct device *dev,
    unsigned int nr_states,
    struct em_data_cb *cb,
    cpumask_t *span,
    bool microwatts
);
```

### Детальний опис параметрів виклику:

- `dev`: вказівник на пристрій процесора в ієрархії ядра (зазвичай отриманий через `get_cpu_device(cpu)`). Пристрій відповідає головному ядру домену продуктивності.
- `nr_states`: кількість доступних станів OPP (Operating Performance Points) для даного домену. Кількість станів має бути більшою за нуль.
- `cb`: структура зворотного виклику `struct em_data_cb`, що містить вказівник на функцію `active_power()`. Ядро викликає цю функцію послідовно для кожного стану від `0` до `nr_states - 1` з метою заповнення полів частоти та потужності.
- `span`: маска процесорів (`cpumask_t`), які належать до цього домену і ділять спільну частоту та напругу. Маска визначає межі домену продуктивності.
- `microwatts`: прапорець виміру потужності. Якщо встановлено `true`, одиницями виміру є мікровати (мкВт). Якщо `false`, потужність подається в абстрактних відносних одиницях.

### Звільнення ресурсів та обробка помилок:

Для скасування реєстрації домену при вивантаженні драйвера або деініціалізації платформи використовується функція:

```c
void em_dev_unregister_perf_domain(struct device *dev);
```

Під час реєстрації ядро перевіряє сувору монотонність зростання частоти у наданій таблиці станів. Якщо частоти не впорядковані за зростанням або одна з частот дорівнює нулю, функція реєстрації повертає помилку `-EINVAL`. Якщо не вдається виділити пам'ять під таблицю станів, повертається `-ENOMEM`. Якщо домен для даних CPU вже зареєстровано раніше, повертається `-EEXIST`.

## 3. Системні параметри `sysctl` та `sysfs`

Управління підсистемою EAS з простору користувача виконується через віртуальні інтерфейси файлової системи `sysctl` та `sysfs`.

### Параметри `sysctl` (`/proc/sys/kernel/`):

- `/proc/sys/kernel/sched_energy_aware`:
  - `1` (за замовчуванням): підсистему EAS активовано. Планувальник виконує енергетичні розрахунки у `find_energy_efficient_cpu()` при пробудженні задач.
  - `0`: примусове деактивування EAS. Планувальник повертається до класичного симетричного балансування навантаження CFS без оцінки енергетичних витрат.

Зміна цього параметра дозволяє системному адміністраторові або сервісам енергозбереження динамічно вмикати або вимикати енергоефективний режим у реальному часі без перезавантаження системи.

### Інтерфейси `sysfs` (`/sys/devices/system/cpu/`):

| Шлях до файлу | Права | Опис |
| :--- | :--- | :--- |
| `/sys/devices/system/cpu/cpu*/cpu_capacity` | RO | Максимальна вихідна ємність ядра `capacity_orig` (шкала від 0 до 1024). Описує відносну потужність ядра |
| `/sys/devices/system/cpu/cpu*/of_node/dynamic-power-coefficient` | RO | Коефіцієнт динамічної потужності з Device Tree у pW/MHz/V², який використовується драйвером cpufreq-dt |

Значення `cpu_capacity` зчитується підсистемою планувальника при розрахунку тривалості виконання задач. А от окремого файла для налаштування 20-відсоткового запасу ємності мейнлайн не дає: поріг 80% зашитий у `fits_capacity()` множником 1280/1024, тож змінити його можна лише перезбіркою ядра (вендорські ядра іноді додають власний параметр).

## 4. Дерево діагностики `debugfs`

Якщо в конфігурації ядра увімкнено підтримку `CONFIG_DEBUG_FS`, фреймворк Energy Model експортує повне дерево характеристик у каталог `/sys/kernel/debug/energy_model`. Це дозволяє інспектувати таблиці OPP, зчитані з прошивки SoC або Device Tree.

Структура каталогу:

```
/sys/kernel/debug/energy_model/
├── cpu0/                         # Домен продуктивності для кластера LITTLE (cpu0-cpu3)
│   ├── cpus                      # Маска ядер: "0-3"
│   ├── flags                     # Прапорці домену: "microwatts"
│   ├── ps:300000/                # Стан OPP 300 МГц
│   │   ├── cost                  # Обчислена вартість (miscellaneous cost scale)
│   │   ├── frequency             # 300000 кГц
│   │   └── power                 # 45000 мкВт
│   └── ps:1200000/               # Стан OPP 1.2 ГГц
│       ├── cost
│       ├── frequency
│       └── power
└── cpu4/                         # Домен продуктивності для кластера big (cpu4-cpu7)
    ├── cpus                      # Маска ядер: "4-7"
    └── ps:2000000/               # Стан OPP 2.0 ГГц
        ├── cost
        ├── frequency
        └── power
```

Перевірити глобальну готовність EAS у поточній конфігурації можна переглядом файла:

```bash
$ cat /sys/kernel/debug/sched/energy_aware
1
```

Якщо файл повертає `0`, це свідчить про те, що або Energy Model не ініціалізована драйверами пристрою, або процесор є симетричним (всі ядра мають однакову ємність), або EAS вимкнено через `sysctl kernel.sched_energy_aware=0`. Тимчасовий стан `overutilized` значення цього файла не змінює.

## 5. Формат подій трасування Tracepoints

Для інспекції рішень EAS у реальному часі вендорські (Android) ядра надають спеціалізовані ftrace-події в `/sys/kernel/debug/tracing/events/sched/`; у мейнлайні ті самі місця коду позначені «голими» tracepoints `sched_compute_energy_tp` і `sched_overutilized_tp`, які читає BPF-програма або модуль ядра. Обидва варіанти дозволяють аналізувати роботу алгоритму `find_energy_efficient_cpu()` під навантаженням.

### Подія `sched_energy_diff`

Викликається всередині `find_energy_efficient_cpu()` при порівнянні кандидатних ядер під час пробудження задачі:

```
field: char task[16];        offset: 0;   size: 16;  /* Назва потоку/процесу */
field: pid_t pid;            offset: 16;  size: 4;   /* PID процесу */
field: int src_cpu;          offset: 20;  size: 4;   /* Попереднє ядро виконання (prev_cpu) */
field: int dst_cpu;          offset: 24;  size: 4;   /* Обране ядро-кандидат (best_energy_cpu) */
field: int task_util;        offset: 28;  size: 4;   /* Нормалізоване навантаження PELT */
field: long nrg_diff;        offset: 32;  size: 8;   /* Обчислена дельта енергії ΔE */
```

Поле `nrg_diff` відображає різницю споживання системи у міліватах або абстрактних одиницях. Від'ємне значення `nrg_diff` означає, що обране ядро `dst_cpu` забезпечує економію енергії порівняно з початковим станом системи.

### Подія `sched_overutilized`

Сповіщає про перехід системи між режимом енергоефективного пакування та режимом аварійного bypass при перевищенні 80% ємності будь-якого ядра:

```
field: bool overutilized;    offset: 0;   size: 1;   /* true (1) — перевантаження, false (0) — норма */
field: unsigned int span;    offset: 4;   size: 4;   /* Маска ядер root-домену */
```

Аналіз цих точок трасування за допомогою інструментів `trace-cmd`, `perf` або eBPF дозволяє розробникам системного софту й драйверів верифікувати поведінку планувальника на реальних мобільних та вбудованих пристроях.
