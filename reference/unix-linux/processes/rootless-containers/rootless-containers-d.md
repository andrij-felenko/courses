# Безкорінна контейнеризація (Rootless Containers)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів.
- [User Namespaces](book:unix-linux/namespaces) — ізоляція ідентифікаторів користувачів і груп.
</preknowlist>

Концепція «безкорінної» (rootless) контейнеризації стала справжнім проривом у світі безпеки Linux. Протягом тривалого часу для запуску контейнерів за допомогою демона Docker вимагалися привілеї користувача `root`. Це створювало значні ризики для безпеки: якщо зловмиснику вдавалося вирватися з контейнера (container breakout), він міг отримати повний контроль над хостовою системою, оскільки демон контейнеризації та самі процеси контейнера працювали з правами суперкористувача.

Безкорінна контейнеризація (втілена в таких інструментах, як Podman, Rootless Docker та з використанням RootlessKit) дозволяє звичайному непривілейованому користувачеві створювати, запускати та керувати контейнерами. Вона використовує низку механізмів ядра Linux (зокрема, user namespaces), щоб ізолювати процеси, при цьому обманюючи контейнер, ніби він запущений користувачем `root`.

У цій статті ми глибоко зануримося в архітектуру безкорінної контейнеризації, розберемо механізми мапінгу ідентифікаторів, файлових систем та мереж, які роблять цю технологію можливою.

## Непривілейовані простори імен користувачів

Фундаментом безкорінної контейнеризації є функція ядра Linux, відома як User Namespaces. Простори імен дозволяють ізолювати глобальні системні ресурси так, що процеси всередині простору імен мають власне, незалежне бачення цих ресурсів.

User Namespaces дозволяють відображати (map) ідентифікатори користувачів (UID) і груп (GID) всередині простору імен на інші ідентифікатори поза ним. Найпоширеніший сценарій: користувач із UID 1000 на хост-системі стає користувачем `root` (UID 0) всередині простору імен контейнера. Це ключова ілюзія, яка дозволяє процесу всередині вважати, що він має повні права.

Для створення такого простору без `sudo` ядро має підтримувати непривілейовані простори імен (`kernel.unprivileged_userns_clone = 1` у деяких старих дистрибутивах, зараз це здебільшого стандарт).

````
```bash
# Створення простору імен через CLI
unshare --user --map-root-user /bin/sh
```
````

Коли процес створює новий user namespace, він визначає таблицю відображення. Якщо `alice` (UID 1000) запускає контейнер, мапінг виглядає так: UID 0 всередині -> UID 1000 назовні. Це означає, що процес всередині «вважає», що він працює від `root`. Однак для ядра він усе ще залишається процесом користувача `alice`.

## Механізми /etc/subuid та /etc/subgid

Сучасним контейнерам зазвичай потрібен не лише `root`. В образі (наприклад, Ubuntu або Alpine) можуть бути файли інших користувачів, які мають UID від 1 до 65535. Процес всередині контейнера може намагатися змінити власника файлу (через `chown`) на UID 1000 або інший. Щоб ядро дозволило це зробити, ці UID всередині контейнера повинні бути відображені на якісь реальні UID на хості, до яких користувач `alice` має доступ. Але звичайний користувач має доступ лише до свого єдиного UID 1000. Він не може привласнити собі інші ідентифікатори.

Тут у гру вступають файли `/etc/subuid` та `/etc/subgid`. Вони визначають пули "підпорядкованих" UID (subuid) і GID, які системний адміністратор делегує непривілейованим користувачам.

Формат цих файлів: `username:starting_uid:count`

Приклад рядка у файлі `/etc/subuid`: `alice:100000:65536`. Цей запис означає, що користувачу `alice` дозволено використовувати 65536 ідентифікаторів, починаючи з номера 100000.

Мапінг, який створює рушій контейнеризації (Podman або Docker), тоді виглядає так:
- Контейнер UID 0 -> Хост UID 1000 (сам користувач `alice`)
- Контейнер UID 1..65535 -> Хост UID 100000..165535 (з пулу `subuid`)

## Утиліти newuidmap та newgidmap

Проблема в тому, що звичайний процес `alice` не може самостійно встановити мапінг на кілька ідентифікаторів у файлі `/proc/[pid]/uid_map` без привілеїв. Ядро дозволяє процесу без привілеїв відобразити лише свій власний поточний UID.

Для обходу цього обмеження використовуються спеціальні системні утиліти `newuidmap` та `newgidmap`. Вони встановлюються в системі з бітом `setuid root`. Це означає, що коли їх запускає звичайний користувач, вони тимчасово отримують права суперкористувача.

Коли рушій створює контейнер і готує мапінг, він викликає `newuidmap`. Ця утиліта працює від `root`, перевіряє `/etc/subuid`, переконується, що `alice` справді має право на запитуваний діапазон ідентифікаторів, і лише тоді від імені ядра записує складний мапінг у `/proc/[pid]/uid_map`. Таким чином, користувач може безпечно використовувати виділені йому пули ідентифікаторів без ризику скомпрометувати інші UID у системі.

## RootlessKit та створення Fake Root

`RootlessKit` — це ключовий інструмент (зокрема в екосистемі Docker), що служить обгорткою для створення безкорінних середовищ. Він автоматизує процес створення user namespaces і мережевих просторів, створюючи "fake root" (штучний root) середовище. У Podman ця логіка значною мірою вбудована або використовує схожі бібліотечні рішення (наприклад, `containers/common`).

RootlessKit відповідає за оркестрацію: він викликає `newuidmap`/`newgidmap` для налаштування ідентифікаторів, монтує файлові системи та ініціалізує мережу через спеціальні драйвери, такі як `slirp4netns`. Це ядро Rootless Docker, що абстрагує всю складність роботи з просторами імен.

## Файлова система: fuse-overlayfs та VFS

Контейнери широко використовують об'єднані файлові системи (UnionFS), найпопулярнішою з яких є `overlayfs`. Вона дозволяє накладати шари образів один на одного (наприклад, шар бази даних поверх шару ОС), щоб економити місце і створювати нові шари для запису (Copy-on-Write).

Традиційна реалізація `overlayfs` у ядрі Linux тривалий час вимагала привілеїв `root` у початковому (init) просторі імен для монтування. Це було серйозною перешкодою для rootless контейнерів.

Для вирішення цього завдання була створена `fuse-overlayfs` — реалізація OverlayFS через механізм FUSE (Filesystem in Userspace). FUSE дозволяє монтувати файлові системи звичайним процесам у просторі користувача без привілеїв ядра.

`fuse-overlayfs` спеціально оптимізована для потреб rootless контейнерів. Вона дозволяє рушіям (як-от Podman) розпаковувати шари, при цьому коректно обробляючи зміну власників файлів (chown), записуючи файли на диск хоста з ідентифікаторами з пулу `/etc/subuid`. Це вирішує складну проблему роботи з файлами: файл, який всередині контейнерного образу належить root, на диску хоста повинен належати користувачу, а файл, який належить UID 1 (наприклад, daemon), на диску має належати UID 100000. Починаючи з ядра Linux 5.11, нативна підтримка непривілейованого монтування `overlayfs` у user namespaces була додана в ядро, що значно прискорило роботу і зменшило потребу у `fuse-overlayfs`.

## Мережева взаємодія: slirp4netns та pasta

Ще одним викликом є мережа. Налаштування мережевих інтерфейсів (створення veth, призначення IP-адрес, налаштування маршрутів та NAT) жорстко вимагає привілеїв `CAP_NET_ADMIN` у хостовому просторі імен. Звичайний користувач не може створювати інтерфейси на хості.

Тому для rootless контейнерів був розроблений підхід з використанням мережевого стека в просторі користувача. Одним із найвідоміших рішень є `slirp4netns` — програма, що базується на бібліотеці `libslirp`.

**Як працює slirp4netns:**
1. Рушій створює новий мережевий простір імен для контейнера.
2. Всередині цього простору створюється віртуальний TAP-інтерфейс (це можливо, оскільки в межах свого user/network namespace контейнер має "права root").
3. Процес `slirp4netns` запускається на хості і підключається до цього TAP-інтерфейсу через файловий дескриптор.
4. Трафік з контейнера (наприклад, TCP/IP пакети) потрапляє в TAP і перехоплюється процесом `slirp4netns`.
5. `slirp4netns` розбирає ці пакети, витягує дані і транслює їх через стандартні мережеві сокети простору користувача (`socket()`, `send()`, `recv()`) на хості.
6. Для зовнішнього світу (і для ядра хоста) це виглядає просто як трафік від звичайної програми, запущеної користувачем `alice`. Жодних спеціальних правил маршрутизації чи NAT у ядрі хоста не створюється.

Цей підхід безпечний і не вимагає привілеїв, але він має значні накладні витрати на трансляцію кожного пакета між простором ядра та простором користувача (context switches). 

Останнім часом набирають популярності сучасні альтернативи, такі як `pasta` (з проєкту `passt`). Вона працює ефективніше, мінімізуючи копіювання даних і використання ресурсів, і поступово стає де-факто стандартом замість `slirp4netns` у нових версіях Podman.

## Висновок

Архітектура безкорінних контейнерів не є єдиною технологією — це складне, але дуже елегантне поєднання багатьох механізмів: `user namespaces` для ізоляції, `/etc/subuid` і `newuidmap` для мапінгу ідентифікаторів, `fuse-overlayfs` (або нативна overlayfs) для керування файловими шарами та `slirp4netns`/`pasta` для мережі без `CAP_NET_ADMIN`. Разом ці технології дозволили створити безпечне середовище для запуску контейнерів без привілеїв демона, зробивши rootless контейнеризацію стандартом для сучасних хмарних і десктопних середовищ.
