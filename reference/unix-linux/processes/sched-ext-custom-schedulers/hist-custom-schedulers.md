# 📜 Історія та еволюція спеціалізованих планувальників у Linux

Шлях ядра Linux від статичних алгоритмів розподілу часу до динамічного підключення BPF-планувальників — це історія тридцятирічного протистояння між потребами серверів баз даних та вимогами мультимедійних систем реального часу. Стандартні планувальники ядра завжди створювалися як універсальні компроміси, проте специфічні робочі навантаження регулярно вимагали принципово інших підходів до черговленості.

---

## 1. Епоха O(1) та CFS: пошук універсального балансу

У ранніх версіях ядра Linux (до 2.4) використовувався простий планувальник з лінійним перебором задач `O(n)`, що робило систему неефективною на багатоядерних серверах із сотнями процесів. У версії Linux 2.6 Інго Мольнар (Ingo Molnar) представив **O(1) Scheduler**, який використовував бітові карти та дві черги задач (`active` і `expired`). Це забезпечило константний час вибору наступного процесу незалежно від їх кількості.

Проте механізм обчислення "інтерактивності" у планувальнику O(1) базувався на евристиках: ядро намагалося вгадати, чи є процес інтерактивним (наприклад, графічний текстовий редактор) чи обчислювальним (наприклад, компелятор C++), на основі часу сну процесу. Ці евристики регулярно хибили. Користувачі настільних систем стикалися з неприємним ефектом "desktop stuttering", коли курсор миші або відтворення відео замерзали під час фонової компіляції ядра.

У 2007 році у версії Linux 2.6.23 ядро перейшло на **Completely Fair Scheduler (CFS)**. Замість пріоритетних черг CFS запровадив концепцію віртуального часу (`vruntime`) та червоно-чорне дерево (`RB-tree`). CFS прагнув до математично ідеальної "справедливості": якщо на ядрі виконуються `N` процесів однаковими пріоритетами, кожен з них має отримати `1/N` частину обчислювальної потужності процесора.

Згодом, у версії Linux 6.6 (2023 рік), CFS поступається місцем планувальнику **EEVDF (Earliest Eligible Virtual Deadline First)** авторства Петера Зейльстри (Peter Zijlstra). EEVDF розв'язав давню проблему CFS із затримками, інтегрувавши точне управління дедлайнами (latency target) безпосередньо у розрахунок віртуального часу.

```
O(n) Linear Scan (Linux 2.2)
   │
   ▼
O(1) Priority Array (Linux 2.6)
   │
   ▼
CFS: Completely Fair Scheduler / RB-Tree (Linux 2.6.23)
   │
   ▼
EEVDF: Earliest Eligible Virtual Deadline First (Linux 6.6)
   │
   ▼
sched_ext: Extensible BPF Scheduling Class (Linux 6.11)
```

## 2. Альтернативний табір: Кон Колівас та альтернативні планувальники

Поки головні розробники ядра фокусувалися на масштабованості для тисяч ядер та серверних навантажень, спільнота настільних ПК та ігор відчувала недостатню чутливість систем. Анестезіолог і системний розробник Кон Колівас (Con Kolivas) висунув гіпотезу: серверна "справедливість" CFS шкодить інтерактивності настільних систем.

Колівас розробив серію альтернативних планувальників:
- **RSDL (Rotating Staircase DeadLine)** — планувальник, що запровадив суворі дедлайни замість обчислення складних евристик.
- **BFS (Brain Fuck Scheduler)** (2009 рік) — виклично простий планувальник з єдиною глобальною двобічною чергою для всіх CPU. BFS відмовився від складних алгоритмів балансування між ядрами, що усунуло мікрозатримки при перемиканні контексту на 2–8 ядерних процесорах.
- **MuQSS (Multiple Queue Skiplist Scheduler)** — еволюція BFS, яка замінила глобальну чергу на списки з пропусками (skiplists) для кожного процесора.

Паралельно Альфред Чен (Alfred Chen) створив планувальники **PDS (Priority Dynamic Slices)** та **BMQ (BitMap Queue)**, які активно використовувалися в спеціалізованих дистрибутивах (наприклад, XanMod, Liquorix, CachyOS).

Проте жоден із цих планувальників не мав шансів потрапити в основну гілку ядра (mainline). Спільнота ядра відхиляла патчі через відсутність масштабованості на NUMA-серверах із сотнями ядер, а підтримання позадеревних (out-of-tree) патчів вимагало колосальних зусиль при кожному релізі ядра.

## 3. Корпоративні виклики Meta та ігровий прорив Valve

До 2020 року проблема спеціалізованого планування вийшла за межі ентузіастів десктопів:

1. **Гіперскейлери (Meta, Google)** зіштовхнулися з тим, що веб-сервіси з мільйонами RPC-запитів вимагають оптимізації L3-кешу та локальності NUMA-вузлів. Модифікація CFS для експериментів вимагала місяців розробки та ризикованого оновлення ядра на сотнях тисяч серверів.
2. **Ігрова індустрія (Valve, SteamOS)** зіштовхнулася з проблемами продуктивності на портативній консолі Steam Deck. Звичайний CFS рівномірно розподіляв ресурси між ігровим рушієм та фоновим комбілюванням шейдерів, що спричиняло просідання кадрів (frametime spikes) та швидке розряджання акумулятора.

Інженери Meta Тежун Хео (Tejun Heo) та Девід Верне (David Vernet) запропонували радикальне рішення: замість того, щоб сперечатися про один "ідеальний" планувальник для всіх, ядро повинно надати абстракцію для безпечного завантаження користувацьких BPF-планувальників під час роботи системи.

Так народився проект **sched_ext** (Extensible Scheduler Class).

---

## 4. Від концепту до Linux 6.11

Розробка `sched_ext` тривала понад два роки. Головним викликом було забезпечення абсолютної безпеки: помилка у користувацькій програмі планування не повинна призводити до зависання системи (kernel lockup) або паніки ядра.

Завдяки можливостям eBPF верифікатора, ядро отримало змогу перевіряти безпеку пам'яті BPF-програм, а вбудований у `sched_ext` механізм тайм-аутів (watchdog) автоматично вивантажує збійний BPF-планувальник і повертає систему на стандартний EEVDF, якщо BPF-код припиняє передавати задачі процесору.

У вересні 2024 року підсистема `sched_ext` була офіційно злита в основну гілку ядра Linux 6.11. Це відкрило еру, коли планування в Linux стало повністю програмованим — від гібридних користувацьких демонів на Rust (`scx_rustland`) до спеціалізованих ігрових інновацій (`scx_lavd`).
