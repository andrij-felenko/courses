Ядро Linux історично відоме своєю монолітною природою, де ключові підсистеми, такі як планувальник завдань (CPU scheduler), жорстко закодовані. Від планувальника O(1) до Completely Fair Scheduler (CFS) і сучасного EEVDF, розробникам ядра доводилося шукати "золоту середину" — алгоритм, який би працював добре для більшості робочих навантажень: від мобільних пристроїв до суперкомп'ютерів.

Проте "універсальний" планувальник рідко є ідеальним для специфічних задач (наприклад, ігрових консолей, високочастотного трейдингу, або великих кластерів баз даних). Зміна планувальника раніше вимагала написання патчів для ядра, перекомпіляції та перезавантаження. 

Усе змінилося з появою **sched_ext** (Extensible Scheduler Class) — нового класу планування, який дозволяє реалізовувати планувальники у вигляді BPF (Berkeley Packet Filter) програм. Це дає змогу завантажувати, тестувати та гаряче замінювати алгоритми планування без перезавантаження системи і без ризику паніки ядра (kernel panic).

У цій статті ми детально розглянемо архітектуру `sched_ext`, ключові структури, такі як `struct sched_ext_ops`, та проаналізуємо реальні BPF-планувальники, такі як `scx_rustland` та `scx_lavd`.

---

## 1. Архітектура та місце sched_ext в ядрі Linux

`sched_ext` (скорочено SCX) — це новий клас планування (scheduling class), доданий до ядра Linux (інтегрований починаючи з версії 6.11). 

Щоб зрозуміти його місце, згадаймо ієрархію класів планування в Linux. Ядро опитує класи у строго визначеному порядку, щоб знайти наступне завдання для виконання на CPU:

1. `Stop` (найвищий пріоритет)
2. `Deadline` (`SCHED_DEADLINE`)
3. `Realtime` (`SCHED_FIFO`, `SCHED_RR`)
4. **`Extensible` (`sched_ext` / SCX)** — *тут підключаються BPF планувальники*
5. `Fair` (`CFS` / `EEVDF` — `SCHED_NORMAL`, `SCHED_BATCH`)
6. `Idle` (`SCHED_IDLE`)

Як бачимо, завдання, які керуються `sched_ext`, мають вищий пріоритет, ніж стандартні завдання класу `Fair`. Коли ви завантажуєте BPF-планувальник, ви можете перевести частину або всі звичайні процеси під управління `sched_ext`.

### 1.1. Як це працює під капотом?

![Архітектура sched_ext](/reference/unix-linux/processes/sched-ext-custom-schedulers/img/sched-ext-arch.svg)
*Рис. 1. Загальна схема взаємодії BPF-планувальника з ядром та User Space.*

Коли ядро (через `core.c`) потребує рішення щодо планування завдань у класі `sched_ext`, воно викликає набір BPF-хуків (гачків). BPF-програма виконується в контексті ядра (забезпечуючи мінімальні затримки), але безпечно, оскільки BPF-верифікатор гарантує, що програма не зациклиться і не звернеться до забороненої пам'яті.

## 2. Ключові концепції та `struct sched_ext_ops`

Ядром розробки SCX-планувальника є заповнення структури `struct sched_ext_ops`. Це набір callback-функцій, які ваша BPF-програма повинна реалізувати.

```c
struct sched_ext_ops {
    /* Викликається, коли завдання прокидається. Тут можна вибрати CPU для нього. */
    s32 (*select_cpu)(struct task_struct *p, s32 prev_cpu, u64 wake_flags);

    /* Завдання додається до черги планувальника. */
    void (*enqueue)(struct task_struct *p, u64 enq_flags);

    /* Завдання видаляється з черги. */
    void (*dequeue)(struct task_struct *p, u64 deq_flags);

    /* Викликається ядром, коли CPU готовий виконати нове завдання.
       BPF програма повинна відправити (dispatch) завдання на виконання. */
    void (*dispatch)(s32 cpu, struct task_struct *prev);

    /* Викликається під час таймерного переривання (scheduler tick) */
    void (*tick)(struct task_struct *p);
    
    // ... інші методи (init, exit, runnable, running, stopping тощо)
};
```

### 2.1. Життєвий цикл завдання в `sched_ext`

1. **Wakeup (Пробудження)**: Коли завдання прокидається (наприклад, дочекалося I/O), ядро викликає `select_cpu`. Ваш планувальник вирішує, на якому ядрі процесора (CPU) це завдання має виконуватися в ідеалі.
2. **Enqueue**: Завдання потрапляє до вашого планувальника. Зазвичай, тут ви зберігаєте вказівник на завдання у BPF-карті (map), наприклад, у локальній черзі, червоно-чорному дереві (RB-tree) або BPF-черзі.
3. **Dispatch**: Коли CPU стає вільним, ядро просить планувальник дати йому роботу через `dispatch`. Планувальник бере завдання зі своєї внутрішньої структури даних і викликає спеціальну BPF-хелпер функцію `scx_bpf_dispatch()`, передаючи його до **DSQ** (Dispatch Queue).
4. **Execute & Consume**: Ядро забирає завдання з DSQ і запускає його на CPU.

### 2.2. Dispatch Queues (DSQ)

DSQ (Dispatch Queues) — це вбудований у ядро механізм `sched_ext` для зберігання завдань, які вже готові до виконання і чекають на вільний CPU. 
Існує три типи DSQ:
- **Локальна DSQ (Local DSQ)**: Кожен CPU має свою локальну чергу (`SCX_DSQ_LOCAL`). Коли ви відправляєте завдання сюди, воно гарантовано виконається на цьому конкретному CPU.
- **Глобальна DSQ (Global DSQ)**: Спільна черга (`SCX_DSQ_GLOBAL`). Будь-який вільний CPU може взяти завдання звідси.
- **Власні DSQ (Custom DSQ)**: Ви можете створити власні DSQ за допомогою `scx_bpf_create_dsq()` для реалізації складних топологій (наприклад, одна черга на NUMA-вузол або на L3-кеш).

## 3. Анатомія розробки: Від C до Rust

Більшість складних `sched_ext` планувальників складаються з двох частин:
1. **BPF-програма (на C)**: Завантажується в ядро. Обробляє швидкі шляхи (fast paths), такі як `enqueue` та `dispatch`.
2. **Програма простору користувача (User-space, часто на Rust)**: Керує конфігурацією, збирає статистику, а в деяких випадках — виконує саме планування!

Бібліотека `scx` та набір інструментів (зокрема, фреймворк на Rust) роблять цей процес набагато простішим. Розглянемо два абсолютно різні підходи на прикладі реальних планувальників.

## 4. Аналіз scx_rustland: Планування у просторі користувача

`scx_rustland` — це один із найбільш революційних прикладів того, що дозволяє робити `sched_ext`. Основна ідея `scx_rustland`: **А що, якщо перенести логіку прийняття рішень щодо планування у простір користувача?**

### 4.1. Як працює rustland?
У типовому планувальнику BPF-код сам вирішує, яке завдання виконати наступним. У `scx_rustland`:
1. BPF-код в ядрі просто перехоплює події `enqueue` і відправляє повідомлення у простір користувача (через BPF Ring Buffer), повідомляючи: "Гей, завдання X готове до виконання".
2. Демон у просторі користувача (написаний на Rust) отримує ці повідомлення, оновлює свої внутрішні структури даних (які можуть бути настільки складними, наскільки дозволяє Rust) і вирішує, яке завдання має виконуватися наступним.
3. Коли ядро запитує `dispatch`, BPF-код звертається до простору користувача (або читає з BPF Map, куди демон Rust попередньо записав рішення), щоб дізнатися, що запускати.

### 4.2. Переваги та недоліки User-space планування
**Переваги:**
- **Безмежна складність**: Ви не обмежені BPF-верифікатором (який обмежує цикли, глибину стека та складність структур даних). Ви можете використовувати стандартні бібліотеки Rust, складні графи, звертатися до мережі, баз даних або навіть AI-моделей для прийняття рішень (хоча це було б повільно).
- **Зручність розробки**: Налагодження звичайного Rust-процесу за допомогою gdb/lldb, використання логів (printf/println) працює як для звичайної програми.
- **Стійкість**: Помилка в алгоритмі просто вб'є user-space процес (і `sched_ext` безпечно переключить систему назад на стандартний планувальник ядра), а не викличе kernel panic.

**Недоліки (і вони суттєві):**
- **Latency (Затримка)**: Перемикання контексту між ядром і простором користувача займає час (мікросекунди). Для мікросекундного планування це може бути катастрофою. Тому `scx_rustland` не підходить для HFT (High-Frequency Trading), але чудово працює для десктопів, де затримка в мілісекунди є непомітною, а "розумний" розподіл завдань між E-cores та P-cores дає більше користі.

## 5. Аналіз scx_lavd: Геймінг та управління затримками

Інший видатний приклад — `scx_lavd` (Latency-critical Advanced Virtual Deadline). Цей планувальник був розроблений компанією Valve спільно з Igalia спеціально для покращення продуктивності ігор на портативних пристроях на кшталт Steam Deck (SteamOS).

### 5.1. Цільова аудиторія
На портативних консолях (де обмежений тепловий пакет і батарея) часто виникає ситуація: важка гра (рендеринг, фізика) конкурує за CPU з фоновими процесами (завантаження шейдерів, оновлення). Стандартний CFS може розподіляти час надто справедливо, через що гра втрачає кадри (stuttering).

### 5.2. Алгоритм LAVD
`scx_lavd` написаний на BPF (логіка в ядрі для мінімальної затримки) і фокусується на **LAVD** (Latency-critical Advanced Virtual Deadline) — алгоритмі, який поєднує ідеї віртуального часу (vruntime з CFS) з жорсткими дедлайнами (deadline scheduling).

Ключові особливості `scx_lavd`:
1. **Ізоляція ігрових потоків**: Він вміє автоматично (або через підказки) визначати "критичні" потоки (наприклад, основний цикл рендерингу) і давати їм абсолютний пріоритет, гарантуючи мікросекундну затримку пробудження.
2. **Врахування топології**: Він жорстко прив'язує потоки, які спільно використовують дані, до одного CCX (Core Complex) у процесорах AMD, щоб уникнути дорогих промахів L3-кешу.
3. **Core Compaction (Ущільнення ядер)**: Замість того, щоб розмазувати фонові завдання по всіх ядрах (що змушує процесор споживати більше енергії), `scx_lavd` намагається групувати некритичні завдання на кількох ядрах, дозволяючи іншим ядрам перейти у стан глибокого сну (C-states), що критично важливо для батареї.

Код `scx_lavd` в BPF є надзвичайно складним і використовує кастомні DSQ для кожної групи пріоритетів і NUMA-вузлів. Це приклад того, як `sched_ext` дозволяє компаніям (наприклад, Valve) швидко впроваджувати глибокі оптимізації без необхідності чекати роками, поки зміни приймуть у головну гілку ядра Linux (mainline).

## 6. Як написати свій BPF-планувальник (Приклад scx_central)

Щоб зрозуміти, наскільки це може бути просто, поглянемо на ідею `scx_central` — найпростішого планувальника.

Уявіть планувальник, який ігнорує будь-яку топологію процесора (NUMA, L3) і просто складає всі завдання в одну глобальну чергу FIFO.

Ось як виглядає BPF-код для такого планувальника:

```c
#include <scx/common.bpf.h>

// Глобальна диспетчерська черга вже вбудована: SCX_DSQ_GLOBAL

s32 BPF_STRUCT_OPS(central_select_cpu, struct task_struct *p,
                   s32 prev_cpu, u64 wake_flags)
{
    // Завжди кажемо ядру використовувати поточний CPU як підказку,
    // але насправді завдання піде в глобальну чергу.
    return prev_cpu;
}

void BPF_STRUCT_OPS(central_enqueue, struct task_struct *p, u64 enq_flags)
{
    // Відправляємо завдання одразу в глобальну чергу
    scx_bpf_dispatch(p, SCX_DSQ_GLOBAL, SCX_SLICE_DFL, enq_flags);
}

void BPF_STRUCT_OPS(central_dispatch, s32 cpu, struct task_struct *prev)
{
    // Ядро просить завдання для `cpu`. 
    // Оскільки ми вже відправили все в SCX_DSQ_GLOBAL під час enqueue,
    // ядро саме автоматично забере його з глобальної черги.
    // Тут нам нічого не потрібно робити!
    scx_bpf_consume(SCX_DSQ_GLOBAL);
}

SEC(".struct_ops.link")
struct sched_ext_ops central_ops = {
    .select_cpu  = (void *)central_select_cpu,
    .enqueue     = (void *)central_enqueue,
    .dispatch    = (void *)central_dispatch,
    .name        = "central",
};
```

Цей код на 30 рядків замінює планувальник ядра Linux! Звісно, він буде страшенно неефективним на багатоядерних системах через конкуренцію за єдиний глобальний ресурс (lock contention), але він демонструє потужність абстракції `sched_ext`.

### 6.1. Гаряча заміна (Hot Swapping)
Найкраща частина `sched_ext` — це розгортання. Ви компілюєте BPF-програму, запускаєте loader (завантажувач) у просторі користувача (наприклад, `./scx_central`), і система миттєво переходить на новий планувальник.

Якщо ви натиснете `Ctrl+C` у терміналі, де працює `scx_central`, BPF-програма вивантажиться, і ядро безпечно, без зупинки роботи програм, переведе всі завдання назад на стандартний планувальник (наприклад, EEVDF). Жоден процес не впаде і не загубиться.

## 7. Підсумки та майбутнє планування

`sched_ext` руйнує монополію розробників ядра на планування. Він дозволяє:
- **Гіперскейлерам (Meta, Google)** створювати планувальники під специфіку їхніх веб-сервісів (наприклад, оптимізуючи під L3-кеш для RPC-серверів).
- **Ігровій індустрії (Valve)** усувати лаги та оптимізувати батарею.
- **Дослідникам** тестувати нові алгоритми на реальних навантаженнях без ризику зламати ядро.

Хоча `sched_ext` додає невеликі накладні витрати на виконання BPF (зазвичай менше 1%), вигоди від алгоритмів, адаптованих до конкретного навантаження, з лишком перекривають ці витрати, відкриваючи нову еру в системному програмуванні Linux.

> **Що далі?** Рекомендуємо вивчити репозиторій `sched-ext/scx` на GitHub, щоб побачити сирцевий код `scx_rustland`, `scx_lavd` та інших планувальників, написаних як на C, так і на Rust за допомогою макросів та фреймворку `scx_rust`.
