# 📋 Довідник інтерфейсів та фреймворку розробки BPF-планувальників (scx_rust та struct sched_ext_ops)

Цей довідник містить систематизований опис системних інтерфейсів ядра `sched_ext`, структури зворотних викликів `struct sched_ext_ops`, ядрових BPF-функцій (kfuncs), прапорців диспетчеризації та високорівневих модулів мови Rust з офіційного фреймворку `scx_utils`.

---

## 1. Специфікація `struct sched_ext_ops` та ядрові колбеки

Головним контрактом взаємодії між ядром Linux та користувацьким BPF-планувальником є структура `struct sched_ext_ops`, яка оголошується у BPF-програмі та реєструється в спеціальній секції `.struct_ops`. Ядро викликає ці функції під час ключових подій життєвого циклу процесів.

### 1.1. Таблиця зворотних викликів (Callbacks)

| Метод (Callback) | Сигнатура | Опис та фаза виконання |
| :--- | :--- | :--- |
| `select_cpu` | `s32 (*select_cpu)(struct task_struct *p, s32 prev_cpu, u64 wake_flags)` | Викликається під час пробудження задачі. Вибирає цільовий CPU або повертає підказку для ядра. |
| `enqueue` | `void (*enqueue)(struct task_struct *p, u64 enq_flags)` | Завдання переводиться в стан готовності та додається до черги планувальника. |
| `dequeue` | `void (*dequeue)(struct task_struct *p, u64 deq_flags)` | Завдання вилучається з черги готовності (перехід у стан сну, витіснення або завершення). |
| `dispatch` | `void (*dispatch)(s32 cpu, struct task_struct *prev)` | Ядро запитує нове завдання для виконання на вказаному процесорі `cpu`. |
| `runnable` | `void (*runnable)(struct task_struct *p, u64 enq_flags)` | Задача перейшла у стан готовності (викликається між `select_cpu` та `enqueue`). |
| `running` | `void (*running)(struct task_struct *p)` | Задача фізично розпочала виконання на процесорі (контекст відновлено). |
| `stopping` | `void (*stopping)(struct task_struct *p, bool runnable)` | Задача припинила виконання на процесорі (через вичерпання кванта або витіснення). |
| `tick` | `void (*tick)(struct task_struct *p)` | Періодичне таймерне переривання ядра (`scheduler tick`) на виконуючому CPU. |
| `init_task` | `s32 (*init_task)(struct task_struct *p, struct scx_init_task_args *args)` | Викликається при створенні нового процесу або потоку (`fork`/`clone`). |
| `exit_task` | `void (*exit_task)(struct task_struct *p, struct scx_exit_task_args *args)` | Викликається при знищенні процесу для очищення BPF-пам'яті та контексту. |
| `init` | `s32 (*init)()` | Викликається один раз під час завантаження та активації BPF-планувальника. |
| `exit` | `void (*exit)(struct scx_exit_info *info)` | Викликається при вивантаженні BPF-планувальника або переході в аварійний режим. |

### 1.2. Контекст та правила виконання колбеків

Кожен зворотний виклик виконується під відповідними ядровими блокуваннями та в чітко визначених контекстах:
- **`select_cpu`**: Виконується в контексті переривання або розблокування потоку під закритим блокуванням `pi_lock` задачі `p`. У цьому колбеку заборонено спати або здійснювати довготривалі обчислення. Повернене значення — це ідентифікатор CPU ($0 \dots N-1$) або негативний код помилки, який змушує ядро використати дефолтну евристику.
- **`enqueue` та `dequeue`**: Виконуються під локальним блокуванням черги `rq->lock`. BPF-код має гарантувати, що задача буде або відправлена у чергу диспетчеризації `DSQ` через `scx_bpf_dispatch()`, або збережена у BPF-карті для пізнішої обробки.
- **`dispatch`**: Викликається, коли процесор `cpu` стає вільним і потребує наступного процесу. Якщо функція `dispatch` не викликає `scx_bpf_consume()` або `scx_bpf_dispatch()`, ядро намагається витягнути задачу з глобальної черги `SCX_DSQ_GLOBAL`.

## 2. Системні BPF-функції ядра (`scx_bpf_*` kfuncs)

Для взаємодії з підсистемою `sched_ext` ядро надає спеціальний набір BPF kfuncs, які можна викликати з BPF-програм.

### 2.1. `scx_bpf_dispatch`
Відправляє завдання `p` у визначену чергу диспетчеризації `DSQ`.

```c
void scx_bpf_dispatch(struct task_struct *p, u64 dsq_id, u64 slice, u64 enq_flags);
```
- `p`: Вказівник на структуру `struct task_struct` процесу.
- `dsq_id`: Ідентифікатор черги диспетчеризації. Це може бути `SCX_DSQ_LOCAL` (локальна черга поточного CPU), `SCX_DSQ_GLOBAL` (спільна глобальна черга ядра) або кастомний 64-бітний ідентифікатор черги, створеної розробником.
- `slice`: Квант часу у наносекундах, який виділяється процесу на виконання. Якщо передано `SCX_SLICE_DFL`, ядро призначає стандартний квант, який у макросі ядра `SCX_SLICE_DFL` визначено як 20 000 000 нс (20 мілісекунд).
- `enq_flags`: Прапорці додавання у чергу (наприклад, `SCX_ENQ_HEAD` для поміщення в початок черги або `SCX_ENQ_PREEMPT` для запиту негайного витіснення).

### 2.2. `scx_bpf_consume`
Витягує задачу із зазначеної черги `DSQ` і переміщує її у локальну чергу виконуючого процесора.

```c
bool scx_bpf_consume(u64 dsq_id);
```
Повертає `true`, якщо із черги `dsq_id` вдалося успішно вилучити принаймні одну задачу і призначити її на поточний CPU.

### 2.3. `scx_bpf_select_cpu_dfl`
Викликає стандартну евристику ядра для вибору найменш завантаженого або спільного по кешу CPU.

```c
s32 scx_bpf_select_cpu_dfl(struct task_struct *p, s32 prev_cpu, u64 wake_flags, u64 is_idle);
```
Використовується як резервний варіант усередині колбеку `select_cpu`, якщо кастомний алгоритм вирішує не втручатися у розміщення конкретної задачі.

### 2.4. `scx_bpf_create_dsq` та `scx_bpf_destroy_dsq`
Створюють та знищують кастомну чергу диспетчеризації `DSQ`.

```c
s32 scx_bpf_create_dsq(u64 dsq_id, s32 node);
void scx_bpf_destroy_dsq(u64 dsq_id);
```
- `dsq_id`: Унікальний 64-бітний ідентифікатор користувацької черги.
- `node`: Ідентифікатор NUMA-вузла, на якому виділяється пам'ять під чергу (або `NUMA_NO_NODE`).

### 2.5. `scx_bpf_error`
Ініціює аварійну зупинку BPF-планувальника з записом причини у системний журнал `dmesg`.

```c
void scx_bpf_error(const char *fmt, ...);
```
При виклику цієї функції ядро негайно переходить у фазу аварійного вивантаження (panic recovery) і безпечно повертає всі процеси системи на класичний планувальник EEVDF.

## 3. Прапорці, константи та коди станів

### 3.1. Прапорці Enqueue (`enq_flags`)
- `SCX_ENQ_WAKEUP` (`1ULL << 0`): Задача прокинулася після очікування події вводу-виводу або таймера.
- `SCX_ENQ_HEAD` (`1ULL << 1`): Задача додається в початок черги `DSQ` (приорітетне виконання).
- `SCX_ENQ_PREEMPT` (`1ULL << 2`): Запит на витіснення поточного процесу, який виконується на CPU.
- `SCX_ENQ_REENQ` (`1ULL << 3`): Повторне розміщення задачі у черзі без зміни її стану готовності.

### 3.2. Прапорці Dequeue (`deq_flags`)
- `SCX_DEQ_SLEEP` (`1ULL << 0`): Задача добровільно віддає CPU та переходить у стан сну (`TASK_INTERRUPTIBLE` або `UNINTERRUPTIBLE`).
- `SCX_DEQ_SAVE` (`1ULL << 1`): Тимчасове вилучення задачі для оновлення її атрибутів або переміщення між чергами.

### 3.3. Ідентифікатори черг DSQ
- `SCX_DSQ_INVALID` (`0ULL`): Недійсний ідентифікатор черги.
- `SCX_DSQ_GLOBAL` (`1ULL`): Глобальна черга ядра, доступна для всіх вільних CPU.
- `SCX_DSQ_LOCAL` (`2ULL`): Локальна черга поточного виконуючого CPU.
- `SCX_DSQ_LOCAL_ON | cpu`: Локальна черга конкретного процесора з номером `cpu`.

## 4. Високорівневий API фреймворку Rust (`scx_utils`)

Для розробників, які створюють користувацькі демони планування мовою Rust, надається стандартний crate `scx_utils`. Він абстрагує роботу з `libbpf-rs`, надаючи безпечні обгортки над системними викликами та BPF maps.

### 4.1. Автоматичне очищення ресурсів `AutoExit`

Модуль `scx_utils::AutoExit` гарантує, що при отриманні сигналів `SIGINT`, `SIGTERM` або при виникненні необробленого виключення в Rust-програмі, BPF-планувальник буде коректно вивантажений із ядра.

```rust
use scx_utils::AutoExit;

fn main() -> anyhow::Result<()> {
    // Реєстрація обробника сигналів зупинки
    let _auto_exit = AutoExit::new()?;

    // Код ініціалізації BPF-планувальника
    Ok(())
}
```

### 4.2. Будівельник планувальника `SchedulerBuilder`

Структура `SchedulerBuilder` забезпечує відкриття, налаштування та завантаження BPF-скелета у ядро.

```rust
use scx_utils::SchedulerBuilder;

fn init_scheduler() -> anyhow::Result<()> {
    let mut builder = SchedulerBuilder::new();
    
    // Встановлення опцій завантаження
    builder.set_print_bpf_logs(true);
    
    // Відкриття та завантаження BPF-об'єкта
    let mut skel = builder.open_and_load()?;
    
    // Активація struct_ops у ядрі
    skel.attach()?;
    
    Ok(())
}
```

### 4.3. Асинхронний моніторинг Ring Buffer (`RingBuffer`)

Клас `RingBuffer` забезпечує високоефективне вичитання подій із BPF Ring Buffer без зайвого копіювання пам'яті.

```rust
use scx_utils::RingBuffer;
use std::time::Duration;

fn poll_events(map: &libbpf_rs::Map) -> anyhow::Result<()> {
    let mut ringbuf = RingBuffer::new(map)?;
    
    loop {
        // Опитування буфера з тайм-аутом 10 мілісекунд
        ringbuf.poll(Duration::from_millis(10), |data: &[u8]| {
            // Безпечна інтерпретація сирих байтів у структуру події
            if data.len() >= std::mem::size_of::<SchedEvent>() {
                let event = unsafe { &*(data.as_ptr() as *const SchedEvent) };
                println!("Отримано подію для PID: {}", event.pid);
            }
            0
        })?;
    }
}
```

Цей інтерфейс забезпечує повний контроль над життєвим циклом BPF-планувальника як зі сторони ядра на C, так і зі сторони простору користувача на Rust чи C++.
