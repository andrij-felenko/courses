# 📋 Довідник системного виклику `ptrace`: запити, прапорці та макроси

Системний виклик `ptrace(2)` є основним низькорівневим інтерфейсом ядра Linux для дослідження стану процесів у просторі користувача та керування ним. У цьому розділі наведено повний структурований довідник із сигнатури виклику, запитів та їхніх параметрів, прапорців розширених опцій, кодів подій, структур регістрів і допоміжних макросів аналізу стану.

## Сигнатура та заголовочні файли

Для використання системного виклику `ptrace` у програмі мовою C або C++ необхідно підключити відповідні системні заголовочні файли. Системна бібліотека `glibc` надає оголошення функції у `<sys/ptrace.h>`, а структури регістрів та макроси обробки стану знаходяться у заголовочних файлах `<sys/user.h>`, `<sys/types.h>` і `<sys/wait.h>`.

```c
#include <sys/ptrace.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <sys/user.h>

long ptrace(enum __ptrace_request request, pid_t pid, void *addr, void *data);
```

Системний виклик приймає чотири обов'язкові аргументи:
- `request`: Константа запиту з переліку `enum __ptrace_request`, яка визначає конкретну операцію (читання пам'яті, запис регістрів, покрокове виконання, конфігурація подій розгалуження).
- `pid`: Ідентифікатор цільового процесу або нитки (або `0` при використанні запиту `PTRACE_TRACEME`).
- `addr`: Віртуальна адреса у пам'яті цільового процесу або зміщення у структурі регістрів (залежить від значення параметра `request`).
- `data`: Вказівник на буфер у пам'яті трасувальника або числове значення параметра (залежить від значення параметра `request`).

У разі успішного виконання більшість запитів повертають `0`. Запити `PTRACE_PEEKTEXT` та `PTRACE_PEEKDATA` повертають зчитане машинне слово як значення повернення виклику. Оскільки прочитане значення пам'яті може дорівнювати `-1` (що збігається з кодом помилки), перед кожним викликом читання пам'яті необхідно обнуляти системну змінну `errno`, а після виклику перевіряти значення `errno` на наявність кодів помилок.

Основою безпеки системного виклику є перевірка прав доступу: за відсутності необхідних привілеїв ядро повертає помилку `EPERM`, якщо цільовий процес не існує — повертає `ESRCH`, при спробі читання некоректної віртуальної адреси — повертає `EFAULT` або `EIO`.

## Основні запити (request)

У таблиці нижче наведено всі ключові запити системного виклику `ptrace`, їхнє призначення та правила передачі аргументів `addr` і `data`:

| Запит | Опис та призначення | Значення `addr` | Значення `data` |
| :--- | :--- | :--- | :--- |
| `PTRACE_TRACEME` | Оголошує, що поточний процес буде трасуватися батьківським процесом. | Ігнорується (`0`) | Ігнорується (`0`) |
| `PTRACE_ATTACH` | Прикріплюється до процесу `pid`, надсилаючи йому `SIGSTOP`. | Ігнорується (`0`) | Ігнорується (`0`) |
| `PTRACE_SEIZE` | Прикріплюється до `pid` без зупинки процесу та без надсилання `SIGSTOP`. | Ігнорується (`0`) | Прапорці `PTRACE_O_*` |
| `PTRACE_DETACH` | Відкріплює трасувальник від процесу `pid`, відновлюючи його нормальне виконання. | Ігнорується (`0`) | Сигнал для доставки |
| `PTRACE_PEEKTEXT` / `PTRACE_PEEKDATA` | Читає одне машинне слово з адреси `addr` у простір пам'яті трасованого процесу. | Адреса в пам'яті | Вказівник або `NULL` |
| `PTRACE_POKETEXT` / `PTRACE_POKEDATA` | Записує слово `data` за адресою `addr` у простір пам'яті трасованого процесу. | Адреса в пам'яті | Значення для запису |
| `PTRACE_GETREGS` | Зчитує загальні регістри процесора у структуру `struct user_regs_struct`. | Ігнорується (`0`) | Вказівник на структуру |
| `PTRACE_SETREGS` | Записує нові значення регістрів процесора зі структури `struct user_regs_struct`. | Ігнорується (`0`) | Вказівник на структуру |
| `PTRACE_CONT` | Відновлює виконання призупиненого процесу. | Ігнорується (`0`) | Сигнал для доставки або `0` |
| `PTRACE_SINGLESTEP` | Виконує рівно одну машинну інструкцію процесу й знову його призупиняє. | Ігнорується (`0`) | Сигнал для доставки або `0` |
| `PTRACE_SYSCALL` | Відновлює виконання до наступного входу або виходу з системного виклику. | Ігнорується (`0`) | Сигнал для доставки або `0` |
| `PTRACE_SETOPTIONS` | Встановлює розширені налаштування трасування для процесу. | Ігнорується (`0`) | Бітова маска `PTRACE_O_*` |
| `PTRACE_GETEVENTMSG` | Отримує повідомлення про подію (наприклад, PID нового процесу при fork). | Ігнорується (`0`) | Вказівник на `unsigned long` |

## Прапорці опцій (`PTRACE_SETOPTIONS`)

Встановлюються через запит `PTRACE_SETOPTIONS` для керування розширеною поведінкою трасування:

- `PTRACE_O_TRACESYSGOOD`: Встановлює 7-й біт у номері сигналу (`SIGTRAP | 0x80` = 0x85) при зупинках на системних викликах. Це дозволяє трасувальнику легко відрізняти вхід/вихід із системного виклику від звичайних сигналів `SIGTRAP`.
- `PTRACE_O_TRACEFORK`: Автоматично зупиняє новий дочірній процес при виконанні `fork()` з подією `PTRACE_EVENT_FORK`.
- `PTRACE_O_TRACEVFORK`: Зупиняє процес при виконанні `vfork()` з подією `PTRACE_EVENT_VFORK`.
- `PTRACE_O_TRACECLONE`: Зупиняє процес при виконанні `clone()` з подією `PTRACE_EVENT_CLONE`.
- `PTRACE_O_TRACEEXEC`: Зупиняє процес перед завершенням системного виклику `execve()` з подією `PTRACE_EVENT_EXEC`.
- `PTRACE_O_TRACEEXIT`: Зупиняє процес на порозі власного завершення (коли ресурси ще не звільнено) з подією `PTRACE_EVENT_EXIT`.
- `PTRACE_O_TRACESECCOMP`: Зупиняє процес із подією `PTRACE_EVENT_SECCOMP`, коли спрацював фільтр `seccomp` із вироком `SECCOMP_RET_TRACE`.
- `PTRACE_O_EXITKILL`: Автоматично надсилає сигнал `SIGKILL` усім трасованим процесам, якщо трасувальник раптово помирає.
- `PTRACE_O_SUSPEND_SECCOMP`: Тимчасово вимикає фільтрацію `seccomp` для трасованого процесу; потребує привілею `CAP_SYS_ADMIN` у трасувальника.

Опції передаються як побітова маска через четвертий параметр виклику `ptrace(PTRACE_SETOPTIONS, pid, 0, options)`. Вони дозволяють налаштувати автоматичне трасування складних багатониткових та багатопроцесних систем без потреби вручну перехоплювати кожен виклик створення процесу.

## Події ptrace (`PTRACE_EVENT_*`)

Коли встановлено відповідні опції через `PTRACE_SETOPTIONS`, системний виклик `waitpid()` повертає `status`, у якому старші 16 бітів (`status >> 16`) містять код відповідної події розгалуження чи виконання. Трасувальник зчитує цей код для автоматичного відстеження ієрархії дочірніх процесів та завантаження нових файлів через `PTRACE_GETEVENTMSG`:

- `PTRACE_EVENT_FORK` (1): Породжено дочірній процес через `fork()`.
- `PTRACE_EVENT_VFORK` (2): Породжено процес через `vfork()`.
- `PTRACE_EVENT_CLONE` (3): Породжено процес або нитку через `clone()`.
- `PTRACE_EVENT_EXEC` (4): Процес успішно виконав `execve()`.
- `PTRACE_EVENT_VFORK_DONE` (5): Батьківський процес розблоковано після виконання `vfork()`.
- `PTRACE_EVENT_EXIT` (6): Процес починає процедуру завершення роботи.
- `PTRACE_EVENT_SECCOMP` (7): Спрацював фільтр `seccomp` із вироком `SECCOMP_RET_TRACE` на вході у системний виклик.
- `PTRACE_EVENT_STOP` (128): Зупинка, породжена самим `ptrace` після `PTRACE_SEIZE` чи `PTRACE_INTERRUPT` (а не сигналом).

Після отримання події `PTRACE_EVENT_FORK` або `PTRACE_EVENT_CLONE` трасувальник виконує виклик `ptrace(PTRACE_GETEVENTMSG, pid, 0, &new_pid)`, щоб отримати ідентифікатор `PID` нового дочірнього процесу або нитки й додати його до списку відстежуваних об'єктів.

## Макроси перевірки стану `waitpid`

При використанні `waitpid(pid, &status, options)` стан зупинки перевіряється стандартними макросами з заголовочного файла `<sys/wait.h>`:

```c
WIFSTOPPED(status)       /* Повертає true, якщо процес призупинено */
WSTOPSIG(status)         /* Повертає номер сигналу, що спричинив зупинку */
WIFEXITED(status)        /* Повертає true, якщо процес нормально завершився */
WEXITSTATUS(status)      /* Код повернення завершеного процесу */
WIFSIGNALED(status)      /* Повертає true, якщо процес вбито сигналом */
WTERMSIG(status)         /* Номер сигналу, що завершив процес */
```

Коли макрос `WIFSTOPPED(status)` повертає істину, трасувальник аналізує номер сигналу через `WSTOPSIG(status)`. Якщо встановлено опцію `PTRACE_O_TRACESYSGOOD`, значення `WSTOPSIG(status) == (SIGTRAP | 0x80)` гарантує, що зупинка відбулася на межі системного виклику.

## Структура регістрів `struct user_regs_struct` (x86_64)

На 64-бітній архітектурі x86_64 структура `struct user_regs_struct` з заголовочного файла `<sys/user.h>` описує зліпок усіх регістрів загального призначення процесора. Ця структура використовується при запитах `PTRACE_GETREGS` та `PTRACE_SETREGS` для читання й модифікації стану процесора:

```c
struct user_regs_struct {
    unsigned long long r15;
    unsigned long long r14;
    unsigned long long r13;
    unsigned long long r12;
    unsigned long long rbp;
    unsigned long long rbx;
    unsigned long long r11;
    unsigned long long r10;
    unsigned long long r9;
    unsigned long long r8;
    unsigned long long rax; /* На вході у виклик — заглушка -ENOSYS; на виході — код повернення */
    unsigned long long rcx;
    unsigned long long rdx; /* 3-й аргумент виклику */
    unsigned long long rsi; /* 2-й аргумент виклику */
    unsigned long long rdi; /* 1-й аргумент виклику */
    unsigned long long orig_rax; /* Номер системного виклику (єдине надійне джерело на вході) */
    unsigned long long rip; /* Instruction Pointer (лічильник інструкцій) */
    unsigned long long cs;
    unsigned long long eflags;
    unsigned long long rsp; /* Stack Pointer (вказівник стека) */
    unsigned long long ss;
    unsigned long long fs_base;
    unsigned long long gs_base;
    unsigned long long ds;
    unsigned long long es;
    unsigned long long fs;
    unsigned long long gs;
};
```

Регістри ABI System V AMD64 відповідають за наступні функції під час викликів: номер виклику програма кладе в `rax`, але ядро зберігає його копію в `orig_rax` і перезаписує `rax` спершу заглушкою `-ENOSYS`, а потім результатом — тому трасувальник читає номер саме з `orig_rax`, а результат з `rax`; `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` передають від 1-го до 6-го аргументу системного виклику відповідно; `rip` містить вказівник на наступну машинну інструкцію; `rsp` вказує на верхівку стека викликів.

## Опрацювання помилок та повернення значень

Кожен запит `ptrace` обробляється ядром із суворими перевірками безпеки. При відмові у доступі або відсутності прав `CAP_SYS_PTRACE` системний виклик повертає `-1`, а системна змінна `errno` набуває відповідного значення:
- `EPERM`: Заборонено трасування цільового процесу (діють обмеження Yama LSM `ptrace_scope`, або цільовий процес змінив UID через `setuid`).
- `ESRCH`: Вказаний процес з ідентифікатором `pid` не існує або наразі не трасується даним трасувальником.
- `EIO`: Передано некоректний номер запиту `request`, некоректний прапорець опції або вирівнювання адреси `addr` є неприпустимим для даної архітектури.
- `EFAULT`: Спроба читання або запису за адресою `addr`, яка не належить до дійсних відображених сторінок віртуальної пам'яті цільового процесу.

Для надійної обробки результатів у налагоджувачах код завжди перевіряє значення `errno` після кожного виклику `ptrace`, особливо при використанні запитів `PTRACE_PEEKDATA`, де повернуте значення `-1` може бути легітимним вмістом зчитаної комірки пам'яті.
