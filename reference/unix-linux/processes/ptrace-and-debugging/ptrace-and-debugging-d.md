# `ptrace`: повний контроль над чужим процесом

Системний виклик `ptrace(2)` — це механізм, за допомогою якого один процес (трасувальник) може взяти під повний контроль інший процес (трасований). Це серцевина роботи таких інструментів, як `gdb` (відладчик) та `strace` (трасувальник системних викликів). Коли ви підключаєтеся до програми, щоб переглянути її змінні, або коли дивитеся, які файли вона відкриває, ви використовуєте `ptrace`. 

Чому взагалі виникла потреба в `ptrace`? В операційних системах сімейства Unix процеси ізольовані один від одного. Процес A не може просто взяти й прочитати пам'ять процесу B або змінити його регістри процесора, інакше система перетворилася б на хаос. Але розробникам необхідно шукати помилки в програмах, ставити точки зупину (breakpoints), перевіряти стан пам'яті та крок за кроком виконувати інструкції. Для цього ядро надає спеціальну шпарину — `ptrace`, яка дозволяє порушити цю ізоляцію під суворим наглядом операційної системи.

## Як встановити контроль: ATTACH і TRACEME

Існує два основні способи, якими трасувальник може захопити контроль над процесом:

1. **`PTRACE_ATTACH`**: Трасувальник прикріплюється до вже запущеного процесу. Наприклад, коли ви виконуєте `gdb -p <pid>`, `gdb` викликає `ptrace(PTRACE_ATTACH, pid, ...)`. Ядро надсилає цільовому процесу сигнал `SIGSTOP`, і він призупиняє своє виконання. Тепер трасувальник може його досліджувати, і процес не зробить жодного кроку без дозволу.
2. **`PTRACE_TRACEME`**: Цей метод використовується, коли трасувальник сам породжує процес, який хоче досліджувати (наприклад, коли ви запускаєте програму зсередини `gdb`). Спочатку трасувальник викликає `fork()`. У дочірньому процесі (перед тим, як викликати `exec()`) виконується `ptrace(PTRACE_TRACEME, 0, ...)`. Це каже ядру: "Дозволь моєму батьківському процесу мене трасувати". Після цього дочірній процес викликає `exec()`, але ядро призупиняє його перед виконанням першої інструкції нової програми, даючи батькові змогу встановити точки зупину до того, як програма почне працювати.

:::tabs
== C
```c
#include <sys/ptrace.h>
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>
#include <stdlib.h>

int main() {
    pid_t pid = fork();
    if (pid == 0) {
        /* Дочірній процес: дозволяємо трасування */
        ptrace(PTRACE_TRACEME, 0, NULL, NULL);
        /* Після exec процес автоматично зупиниться */
        execl("/bin/ls", "ls", NULL);
        exit(1);
    } else {
        /* Батьківський процес: чекаємо зупинки дочірнього */
        int status;
        waitpid(pid, &status, 0);
        printf("Дочірній процес зупинився перед першою інструкцією.\\n");
        /* Відпускаємо його працювати далі */
        ptrace(PTRACE_CONT, pid, NULL, NULL);
    }
    return 0;
}
```
== Python
```python
import os
import ctypes
import sys

libc = ctypes.CDLL("libc.so.6")
PTRACE_TRACEME = 0
PTRACE_CONT = 7

pid = os.fork()

    # Дочірній процес

    os.execl("/bin/ls", "ls")
else:
    # Батьківський процес
    _, status = os.waitpid(pid, 0)
    print("Дочірній процес зупинився.")
    libc.ptrace(PTRACE_CONT, pid, 0, 0)
```

## Читання та запис: PEEKDATA і POKEDATA

Після того, як процес зупинено, трасувальник отримує можливість зазирати в його нутрощі. Це робиться за допомогою запитів `PTRACE_PEEKDATA` (прочитати слово з пам'яті трасованого) та `PTRACE_POKEDATA` (записати слово в пам'ять трасованого). 

Коли ви просите `gdb` показати значення змінної (наприклад, `print my_var`), відладчик визначає адресу цієї змінної в пам'яті (завдяки налагоджувальній інформації, як-от DWARF, що зберігається в бінарному файлі) і викликає `PTRACE_PEEKDATA` для цієї адреси. Ядро бере байти з пам'яті зупиненого процесу і передає їх `gdb`. З точки зору ОС, ядро мапує сторінку пам'яті цільового процесу, читає звідти значення і повертає його трасувальнику.

Щоб змінити значення змінної (`set var = 42`), `gdb` використовує `PTRACE_POKEDATA`. Ядро записує нове значення прямо в адресний простір цільового процесу. Це дозволяє вносити зміни на льоту, не зупиняючи програму назавжди.

Однак цей механізм має суттєвий недолік — він повільний. `ptrace` пересилає дані машинними словами (зазвичай 8 байтів на 64-бітних архітектурах). Якщо вам треба прочитати великий масив або структуру даних, `gdb` доведеться зробити тисячі системних викликів `PTRACE_PEEKDATA`. Кожен такий виклик пов'язаний із перемиканням контексту: від простору користувача в ядро і назад. Для вирішення цієї проблеми сучасні версії Linux пропонують системні виклики на кшталт `process_vm_readv` та `process_vm_writev`, які дозволяють копіювати великі блоки пам'яті за один раз. Але `ptrace` залишається універсальним фундаментом, який працює скрізь.

## Точки зупину (Breakpoints): як обдурити процесор

Найцікавіше в роботі відладчика — це точки зупину. Процесор сам по собі не має магічної інструкції "зупинися на рядку 45 вихідного коду". Щоб зупинити програму в потрібному місці, `gdb` вдається до трюку з модифікацією машинного коду:

1. **Читання оригіналу:** Відладчик обчислює адресу в пам'яті, що відповідає рядку коду, читає оригінальну інструкцію за цією адресою через `PTRACE_PEEKDATA` і запам'ятовує її.
2. **Впровадження пастки:** Він записує на це місце спеціальну інструкцію-переривання (через `PTRACE_POKEDATA`). В архітектурі x86 це один байт `0xCC`, який означає програмне переривання `int 3`. На інших архітектурах є свої аналоги (наприклад, `brk` в ARM).
3. **Відновлення виконання:** Трасувальник дозволяє процесу виконуватися далі за допомогою команди `PTRACE_CONT`.

Коли цільовий процес доходить до модифікованої адреси, він намагається виконати вставлену інструкцію. `int 3` викликає виняткову ситуацію на рівні апаратного забезпечення. Ядро перехоплює це переривання, розуміє, що процес трасується, і надсилає йому сигнал `SIGTRAP`. Оскільки процес знаходиться під контролем `ptrace`, він не обробляє сигнал сам, а просто зупиняється, а ядро сповіщає трасувальника (відладчик прокидається з `waitpid`).

Тепер програма зупинена, і `gdb` може показати вам командний рядок. Але щоб програма могла продовжити роботу, `gdb` мусить зробити ще кілька кроків:
1. Записати оригінальну інструкцію назад замість `0xCC` (через `PTRACE_POKEDATA`).
2. Повернути лічильник команд (Instruction Pointer, регістра `RIP` або `EIP`) на один байт назад, оскільки процесор уже встиг виконати `0xCC` і посунув лічильник уперед. Це робиться за допомогою `PTRACE_SETREGS`.
3. Виконати рівно один крок (одну інструкцію) через `PTRACE_SINGLESTEP`, щоб виконати ту саму оригінальну інструкцію.
4. Знову вставити `0xCC` на випадок, якщо це точка зупину в циклі.
5. Відпустити процес вільно виконуватися через `PTRACE_CONT`.

Цей танець відбувається щоразу, коли ви досягаєте точки зупину, і все це завдяки контролю через `ptrace`.

## Трасування системних викликів: магія strace

Інструмент `strace` дозволяє бачити кожен системний виклик, який робить програма, але він працює дещо інакше, ніж класичні точки зупину. Замість того, щоб вставляти переривання в код програми, він використовує опцію `PTRACE_SYSCALL`.

Ця опція каже ядру: "Віднови виконання процесу, але зупини його наступного разу, коли він спробує виконати системний виклик, АБО коли системний виклик завершиться". Таким чином `strace` прокидається двічі на кожен системний виклик:
- **На вході (Syscall Entry):** Процес переривається перед тим, як ядро почне обробляти запит. `strace` використовує `PTRACE_GETREGS`, щоб прочитати регістри процесора. У реєстрах лежить номер системного виклику (наприклад, 0 для `read`, 1 для `write` в x86_64) та його аргументи.
- **На виході (Syscall Exit):** Після того, як ядро виконало виклик, процес знову призупиняється. `strace` читає регістри, щоб отримати код повернення, який ядро повернуло програмі (наприклад, скільки байтів було прочитано).

Саме через це `strace` суттєво уповільнює роботу програми. Нормальний системний виклик вимагає одного перемикання контексту: програма → ядро → програма. Під час роботи `strace` кожен виклик до ядра перетворюється на складний ланцюжок: програма → ядро → зупинка → перемикання на `strace` → `strace` читає регістри → ядро → повернення в `strace` → `strace` каже продовжити → ядро виконує виклик → зупинка → перемикання на `strace`... Це уповільнює інтенсивні до I/O програми в десятки разів.

## Обмеження, безпека та патч Yama

`ptrace` дає абсолютну владу. Якщо ви можете підключитися до процесу, ви можете прочитати його пам'ять (включно з криптографічними ключами), змінити його логіку або змусити виконати будь-який код. Тому в Linux діють суворі правила:

1. Ви можете трасувати лише ті процеси, які належать вашому користувачу.
2. Ви не можете трасувати процеси, які мають підвищені привілеї через `setuid` або `setgid` (наприклад, програму `sudo`), якщо ви самі не є суперкористувачем `root`.
3. За замовчуванням не можна трасувати процес ядра (хоча для цього є інші інструменти).

Однак навіть цих обмежень виявилося недостатньо. Уявіть, що ви завантажили шкідливий скрипт. Оскільки він запущений від вашого імені, він може зробити `PTRACE_ATTACH` до вашого веббраузера, прочитати пам'ять і вкрасти паролі чи сесійні токени. Щоб цьому запобігти, розробники впровадили модуль безпеки **Yama**.

Сучасні дистрибутиви (наприклад, Ubuntu, Debian) постачаються з увімкненим патчем Yama (який можна налаштувати через `/proc/sys/kernel/yama/ptrace_scope`). Yama суттєво обмежує можливість підключення до запущених процесів. Якщо параметр `ptrace_scope` дорівнює 1 (типове значення), процес може трасувати лише своїх безпосередніх нащадків. Тобто ви можете запустити програму всередині `gdb` (тут використовується `fork` і `PTRACE_TRACEME`), але не можете зробити `gdb -p <pid>` до сторонньої програми, навіть якщо вона ваша. Щоб підключитися до довільного процесу, вам знадобляться права `root` або спеціальні `capabilities` (`CAP_SYS_PTRACE`).

Це ускладнює життя розробникам, яким іноді потрібно дослідити робочий процес, що завис у фоні, але значно підвищує безпеку звичайних користувачів, обмежуючи радіус ураження в разі компрометації одного застосунку.

## Трасування сигналів та ін'єкції коду

Окрім читання пам'яті та встановлення точок зупину, `ptrace` дозволяє повністю контролювати доставку сигналів до процесу. Коли трасований процес отримує будь-який сигнал (навіть такий, що мав би його вбити, наприклад `SIGSEGV`), процес зупиняється і ядро передає цей сигнал трасувальнику. Відладчик може вирішити:
1. Передати сигнал процесу, ніби нічого не сталося.
2. Проігнорувати сигнал і продовжити роботу.
3. Надіслати процесу інший сигнал.

Завдяки цьому `gdb` перехоплює помилки сегментації і дозволяє вам оглянути стан пам'яті до того, як процес "помре".

Більше того, оскільки ви можете змінювати регістри процесора через `PTRACE_SETREGS` і писати в пам'ять, ви можете створювати **ін'єкції коду**. Це процес, коли трасувальник виділяє шматок пам'яті у цільовому процесі (наприклад, через виклик `mmap`), записує туди свій машинний код, налаштовує `RIP` (лічильник команд) на цей код і змушує процес його виконати. Після цього можна повернути `RIP` назад. Саме так працюють складні системи динамічного патчингу та деякі види шкідливого програмного забезпечення.

## За межами `ptrace`

Хоча `ptrace` залишається стандартом де-факто, він морально застарів. Його дизайн, орієнтований на передачу даних по одному слову і надмірне використання сигналів (`SIGSTOP`/`SIGTRAP`), робить його повільним і складним у програмуванні. Сьогодні для спостереження за системою все частіше використовують технологію **eBPF**. Вона дозволяє завантажити безпечну програму прямо в ядро, яка буде збирати статистику системних викликів, обробляти події та збирати стеки викликів без постійного перемикання контексту, що робить її ідеальною для профілювання навантажених серверів без помітного падіння продуктивності. Але для інтерактивного налагодження `ptrace` все ще немає рівних.
