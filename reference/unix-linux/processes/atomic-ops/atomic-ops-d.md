Атомні операції є найнижчим і найшвидшим рівнем примітивів синхронізації в ядрі Linux. У багатоядерних і багатопотокових системах, де кілька процесорів можуть одночасно читати та модифікувати одну й ту саму комірку пам'яті, звичайні операції на зразок `counter++` розпадаються на три окремі кроки на рівні ассемблера: зчитування з пам'яті у регістр CPU, модифікація значення в регістрі та запис результату назад у RAM. Якщо два шинні цикли або два процесорні ядра виконують цю послідовність паралельно, виникає класичний стан перегонів (race condition), і один із записів буде мовчки втрачено.

Для розв'язання цієї проблеми ядро Linux надає спеціальні типи даних `atomic_t` та `atomic64_t`, а також набір атомарних функцій, які гарантують, що зчитування, зміна та запис відбуваються як єдина нероздільна операція на рівні апаратури.

## Апаратна суть атомарності: MESI та префікс LOCK

На системному рівні атомарність гарантується взаємодією кеш-контролера процесора та протоколів когерентності кешів (наприклад, MESI або MOESI).

Коли процесор виконує атомарну інструкцію (на архітектурі x86/x86_64 це зазвичай інструкції з префіксом `LOCK`, такі як `LOCK XADD` або `LOCK CMPXCHG`), кеш-контролер застосовує один із двох механізмів:
1. **Кеш-блокування (Cache Locking):** Якщо адреса пам'яті вже перебуває у кеші L1/L2 даного ядра у стані `Modified` або `Exclusive`, ядро процесора утримує лінію кешу (cache line) і заборгує іншим ядрам доступ до неї на час виконання інструкції. Протокол MESI гарантує, що жодне інше ядро не зможе зчитати чи модифікувати цю лінію, поки атомарний запис не завершиться.
2. **Шинне блокування (Bus Locking):** Якщо дані перетинають межу лінії кешу (unaligned memory access) або незакешовані, процесор виставляє апаратний сигнал на шині системної пам'яті (Bus Lock Signal), тимчасово блокуючи будь-який доступ до шини RAM для всіх інших процесорів і контролерів DMA.

```c
// Структурне визначення типом даних atomic_t у ядрі Linux (include/linux/types.h)
typedef struct {
    int counter;
} atomic_t;

typedef struct {
    s64 counter;
} atomic64_t;
```

Використання окремої структури `atomic_t` замість звичайного `int` є свідомим архітектурним рішенням розробників ядра Linux. Це забороняє розробникам драйверів застосовувати звичайний оператор присвоєння `=` або прямі арифметичні операції, примушуючи явно викликати атомарні функції API ядра.

## Основний API: Read-Modify-Write та Compare-And-Swap

Ядро надає багатий набір функцій для роботи з `atomic_t`:

```c
// Ініціалізація та базова робота
atomic_t v = ATOMIC_INIT(0);

int val = atomic_read(&v);       // Атомарне зчитування значення
atomic_set(&v, 10);              // Атомарний запис значення

// Арифметика без повернення значення
atomic_inc(&v);                  // v++
atomic_dec(&v);                  // v--
atomic_add(5, &v);               // v += 5
atomic_sub(2, &v);               // v -= 2

// Арифметика з поверненням нового або старого значення
int new_val = atomic_inc_return(&v); // Збільшує і повертає новий результат
int old_val = atomic_fetch_add(5, &v); // Додає 5 і повертає СТАРЕ значення

// Тестові операції (для реалізації флагів та локів)
if (atomic_dec_and_test(&v)) {
    // Повертає true, якщо після зменшення значення стало рівним 0
}
```

Найважливішою атомарною операцією для побудови безблокувальних структур даних (lock-free data structures) є **Compare-And-Swap (CAS)**, у ядрі представлена функцією `atomic_cmpxchg`:

```c
int atomic_cmpxchg(atomic_t *v, int old_val, int new_val);
```

Функція порівнює поточне значення `v` із `old_val`. Якщо вони збігаються, вона замінює значення `v` на `new_val` і повертає `old_val`. Якщо значення не збігаються, модифікація не відбувається, і повертається поточне дійсне значення `v`.

## Приклад у коді ядра: Лічильник посилань (Reference Counting)

Найпоширенішим застосуванням `atomic_t` у ядрі є керування життєвим циклом об'єктів за допомогою лічильника посилань:

```c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/slab.h>
#include <linux/atomic.h>

struct my_kernel_object {
    atomic_t refcount;
    char data[64];
};

struct my_kernel_object *obj_alloc(void)
{
    struct my_kernel_object *obj = kmalloc(sizeof(*obj), GFP_KERNEL);
    if (!obj)
        return NULL;

    // Початкове значення refcount = 1
    atomic_set(&obj->refcount, 1);
    return obj;
}

void obj_get(struct my_kernel_object *obj)
{
    // Збільшуємо лічильник посилань при передачі об'єкта іншому потоку
    atomic_inc(&obj->refcount);
}

void obj_put(struct my_kernel_object *obj)
{
    // Атомарно зменшуємо і перевіряємо, чи став refcount == 0
    if (atomic_dec_and_test(&obj->refcount)) {
        pr_info("my_object: refcount reached 0, freeing memory\n");
        kfree(obj);
    }
}
```

> 🔧 **Навіщо це.** Без атомарного `atomic_dec_and_test` два паралельних процеси, що одночасно звільняють посилання на об'єкт, могли б обидва вважати, що лічильник ще не нульовий (double free / memory leak) або що вони обидва мають право звільнити пам'ять (use-after-free).

## Оптимізації refcount_t у сучасному ядрі

У сучасних версіях ядра Linux для керування лічильниками посилань замість звичайного `atomic_t` наполегливо рекомендується використовувати спеціалізований тип `refcount_t` (`#include <linux/refcount.h>`).

Тип `refcount_t` реалізований як обгортка над `atomic_t`, але включає апаратний захист від двох небезпечних атак і помилок:
1. **Overflow Protection (Переповнення):** Якщо лічильник виходить за межі `INT_MAX`, `refcount_inc` насичує значення і викликає ядерний `WARN_ON`, не дозволяючи лічильнику згорнутися в 0 і спричинити передчасне звільнення пам'яті.
2. **Use-After-Free Protection:** Спроба збільшити лічильник, який вже досяг 0 (`refcount_inc` над звільненим об'єктом), блокується і викликає попередження ядра.
