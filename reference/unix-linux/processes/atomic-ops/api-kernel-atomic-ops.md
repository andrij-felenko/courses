# 🔌 Довідник API атомарних операцій ядра Linux

Цей довідник містить систематизовану специфікацію програмного інтерфейсу (API) атомарних операцій ядра Linux для типів `atomic_t`, `atomic64_t`, `atomic_long_t`, бітових масок `<linux/bitops.h>` та захищеного лічильника посилань `refcount_t`.

Усі функції оголошені в заголовкових файлах `<linux/atomic.h>`, `<linux/refcount.h>` та `<linux/bitops.h>` (останній сам підтягує архітектурну реалізацію з `<asm/bitops.h>` — саме `linux/`-варіант підключає код драйвера). Інтерфейс є уніфікованою абстракцією ядра Linux, яка пропонує однаковий C-синтаксис для всіх підтримуваних апаратних архітектур (x86_64, ARM64, RISC-V, PowerPC, MIPS).

## Структурні типи даних та вимоги до вирівнювання

Для забезпечення тип-безпечності ядро Linux відмовляється від використання звичайних типів `int` або `long` для атомарних змінних. Використання окремих обгорток-структур унеможливлює випадкові помилки розробника драйвера, коли замість виклику атомарної функції застосовується пряме C-присвоєння або звичайна неатомарна арифметика.

```c
// include/linux/types.h
typedef struct {
    int counter;
} atomic_t;

#ifdef CONFIG_64BIT
typedef struct {
    s64 counter;
} atomic64_t;
#endif

// include/linux/atomic/atomic-long.h — окремої структури немає, лише псевдонім
#ifdef CONFIG_64BIT
typedef atomic64_t atomic_long_t;
#else
typedef atomic_t   atomic_long_t;
#endif
```

Змінна `atomic_t` гарантує атомарність модифікації 32-бітного цілого числа зі знаком. Змінна `atomic64_t` працює з 64-бітними числами зі знаком. Змінна `atomic_long_t` адаптується під природну розрядність архітектури: на 64-бітних системах вона є прямим псевдонімом `atomic64_t`, а на 32-бітних системах вказує на `atomic_t`.

Фундаментальною вимогою для роботи атомарного API є суворе вирівнювання (Alignment) даних у пам'яті:
- Змінна `atomic_t` повинна бути вирівняна за межею 4 байтів (`alignof(int)`).
- Змінна `atomic64_t` повинна бути вирівняна за межею 8 байтів (`alignof(s64)`).

Якщо адреса атомарної змінної виявляється невирівняною (наприклад, у результаті пакування структури макросом `__attribute__((packed))`), поведінка системи різко деградує. На архітектурі x86 невирівняна атомарна операція провокує важке шинне блокування (Bus Lock) замість кеш-блокування, що заморожує процесорну шину на сотні тактів. На архітектурах ARM64 та RISC-V невирівняний виклик атомарних інструкцій `LDXR`/`STXR` (у 32-бітному режимі AArch32 — `LDREX`/`STREX`) або `lr.w`/`sc.w` викликає апаратне виключення ядра (Alignment Fault), яке призводить до миттєвого краху системи (Kernel Panic).

На 32-бітних архітектурах без нативної апаратної підтримки 64-бітних атомарних інструкцій ядро реалізує `atomic64_t` через емуляцію з використанням масиву з 16 внутрішніх спінлоків (`CONFIG_GENERIC_ATOMIC64`, `lib/atomic64.c`), де адреса змінної хешується для вибору замка.

Порядок розташування байтів у пам'яті (Endianness) не впливає на коректність атомарних інструкцій. На системах Little-Endian (x86_64, ARM64) та Big-Endian (s390x, PowerPC) атомарні операції працюють із цілісним значенням слова в регістрі CPU, зберігаючи математичну еквівалентність однакових викликів.

Особливою категорією є використання атомарних змінних у спільно використовуваній пам'яті (Shared Memory) між процесами користувацького простору та ядром. При відображенні сторінок через `mmap()` атомарні виклики `atomic_t` гарантують нероздільність навіть у разі, якщо один потік працює у режимі ядра, а інший — у режимі користувача.

## Ініціалізація та базовий доступ

Операції зчитування та запису гарантують атомарне читання або оновлення значення в пам'яті без проміжних станів.

| Сигнатура / Макрос | Повертане значення | Опис дії та механізм виконання |
| :--- | :--- | :--- |
| `ATOMIC_INIT(int i)` | `atomic_t` | Статична ініціалізація структури `atomic_t` початковим значенням `i` під час оголошення змінної. |
| `ATOMIC64_INIT(s64 i)` | `atomic64_t` | Статична ініціалізація структури `atomic64_t` початковим значенням `i`. |
| `atomic_read(const atomic_t *v)` | `int` | Зчитує поточне значення `v`. Реалізовано через `READ_ONCE()`, що забороняє компіляторові кешувати значення в регістрі. |
| `atomic_set(atomic_t *v, int i)` | `void` | Записує нове значення `i` за адресою `v`. Реалізовано через `WRITE_ONCE()`, забороняючи компілятору розбивати запис на частини. |
| `atomic64_read(const atomic64_t *v)` | `s64` | Атомарне 64-бітне зчитування значення `v`. |
| `atomic64_set(atomic64_t *v, s64 i)` | `void` | Атомарне 64-бітне встановлення значення `v = i`. |

Оскільки `atomic_read()` та `atomic_set()` є простими зчитуваннями та записами вирівняних слів у пам’яті, вони не генерують інструкцій з префіксом `LOCK` на x86 і працюють із мінімальними витратами CPU. Використання макросів `READ_ONCE` та `WRITE_ONCE` усередині цих функцій інформує компілятор C (GCC/Clang) про те, що значення може бути модифіковане паралельними потоками або апаратними перериваннями. Це гарантує, що компілятор не оптимізує повторні виклики `atomic_read()` у циклі, перетворюючи їх на нескінченне читання з процесорного регістра.

Окрім того, `READ_ONCE` захищає від дефекту розщеплення зчитувань (Read Tear), коли компілятор вирішує зчитати 32-бітне значення двома окремими 16-бітними командами. Для вирівняних типів `atomic_t` макрос примусово генерує одну 32-бітну або 64-бітну інструкцію `MOV`.

## Арифметичні та логічні операції без повернення значення

Ця група функцій виконує атомарні модифікації за схемою Read-Modify-Write (RMW). Вони не повертають отриманого результату, що дозволяє компілятору згенерувати максимально швидкий апаратний код (наприклад, `LOCK INC` на x86 без збереження прапорців чи регістрів).

| Сигнатура функції | Тип модифікації | Опис операції |
| :--- | :--- | :--- |
| `atomic_inc(atomic_t *v)` | `v++` | Збільшує значення `v` на 1. |
| `atomic_dec(atomic_t *v)` | `v--` | Зменшує значення `v` на 1. |
| `atomic_add(int i, atomic_t *v)` | `v += i` | Додає ціле значення `i` до лічильника `v`. |
| `atomic_sub(int i, atomic_t *v)` | `v -= i` | Віднімає ціле значення `i` від лічильника `v`. |
| `atomic_and(int i, atomic_t *v)` | `v &= i` | Виконує побітове і (AND) над `v` та маскою `i`. |
| `atomic_or(int i, atomic_t *v)` | `v \|= i` | Виконує побітове або (OR) над `v` та маскою `i`. |
| `atomic_xor(int i, atomic_t *v)` | `v ^= i` | Виконує побітове виключне або (XOR) над `v` та маскою `i`. |
| `atomic_andnot(int i, atomic_t *v)` | `v &= ~i` | Очищає біти за маскою `i` (`v AND NOT i`). |

Аналогічні функції виклику існують для `atomic64_t` із префіксом `atomic64_*` (наприклад, `atomic64_add(s64 i, atomic64_t *v)`).

Особливістю функцій без повернення значення є те, що вони не створюють суворих бар'єрів пам'яті (Memory Barriers). Операції читання й запису суміжних неатомарних змінних можуть вільно переставлятися компілятором або процесором до або після виклику `atomic_inc()`.

Це означає, що операції без повернення значення ідеально підходять для лічильників статистики або лічильників оброблених пакетів, де не потрібно синхронізувати стан інших даних, але катастрофічно не підходять для публікації вказівників чи прапорців готовності без використання додаткових бар'єрів пам'яті.

## Арифметика з поверненням значення

Коли алгоритму необхідно знати стан лічильника після додавання або значення, яке передувало оновленню, використовують функції RMW з поверненням.

| Сигнатура функції | Повертане значення | Опис дії та механізм |
| :--- | :--- | :--- |
| `atomic_inc_return(atomic_t *v)` | `int` (Нове) | Збільшує `v` на 1 та повертає **нове** значення `v + 1`. |
| `atomic_dec_return(atomic_t *v)` | `int` (Нове) | Зменшує `v` на 1 та повертає **нове** значення `v - 1`. |
| `atomic_add_return(int i, atomic_t *v)` | `int` (Нове) | Додає `i` та повертає **нове** значення `v + i`. |
| `atomic_sub_return(int i, atomic_t *v)` | `int` (Нове) | Віднімає `i` від `v` та повертає **нове** значення `v - i`. |
| `atomic_fetch_add(int i, atomic_t *v)` | `int` (Старе) | Додає `i` до `v` та повертає **старе** значення до модифікації. |
| `atomic_fetch_sub(int i, atomic_t *v)` | `int` (Старе) | Віднімає `i` від `v` та повертає **старе** значення до модифікації. |
| `atomic_fetch_and(int i, atomic_t *v)` | `int` (Старе) | Виконує побітове `v &= i` та повертає **старе** значення. |
| `atomic_fetch_or(int i, atomic_t *v)` | `int` (Старе) | Виконує побітове `v \|= i` та повертає **старе** значення. |
| `atomic_fetch_xor(int i, atomic_t *v)` | `int` (Старе) | Виконує побітове `v ^= i` та повертає **старе** значення. |
| `atomic_xchg(atomic_t *v, int new)` | `int` (Старе) | Безумовно записує `new` у `v` та повертає **старе** значення. |

Усі стандартні функції з поверненням значення (`*_return` та `fetch_*`) на відміну від операцій без повернення діють як повні бар'єри пам'яті (Full Memory Barriers). Вони гарантують суворе впорядкування: жодне зчитування чи запис, розташоване в коді після виклику, не може бути виконане раніше за атомарний запис.

Розглянемо практичний випадок використання `atomic_fetch_add()`. Якщо розробник реалізує розподіл унікальних порядкових номерів завдань (Task ID), функція `atomic_fetch_add(1, &global_id)` атомарно збільшить лічильник, але поверне унікальний попередній номер для поточного виклику, гарантуючи відсутність дубльованих ідентифікаторів у паралельних потоках.

## Тестові та умовні операції

Умовні операції використовуються для реалізації лічильників посилань, спінлоків та сигналів завершення дій.

| Сигнатура функції | Повертане значення | Умова повернення true |
| :--- | :--- | :--- |
| `atomic_dec_and_test(atomic_t *v)` | `bool` | Зменшує `v` на 1. Повертає `true`, якщо новий результат дорівнює **0**. |
| `atomic_inc_and_test(atomic_t *v)` | `bool` | Збільшує `v` на 1. Повертає `true`, якщо новий результат дорівнює **0**. |
| `atomic_add_negative(int i, atomic_t *v)` | `bool` | Додає `i` до `v`. Повертає `true`, якщо результат є **від'ємним** (`v < 0`). |
| `atomic_sub_and_test(int i, atomic_t *v)` | `bool` | Віднімає `i` від `v`. Повертає `true`, якщо результат дорівнює **0**. |

Макрос `atomic_dec_and_test()` є найбільш вживаним механізмом для деалокації ресурсів у ядрі. Якщо під час зменшення лічильника посилань функція повертає `true`, на цей момент об'єкт більше не має активних власників, і його пам'ять можна безпечно передати до `kfree()`.

Виклик `atomic_add_negative()` часто застосовується в кредитних алгоритмах обмеження швидкості (Rate Limiting). Коли потік «витрачає» ліміт квантів, додавання від'ємного значення повертає `true`, якщо кредит вичерпано і процес повинен перейти в стан очікування.

## Операції Compare-And-Swap (CAS)

Атомарні порівняння й заміни є фундаментом для побудови будь-яких безблокувальних структур даних (Lock-Free data structures).

### `atomic_cmpxchg`

Функція атомарно перевіряє, чи поточне значення `v` дорівнює порівнюваному старому значенню `old`, і лише при їх збігу замінює вміст `v` на `new`, повертаючи попередній стан:

```c
int atomic_cmpxchg(atomic_t *v, int old, int new);
```

Якщо значення не збігаються, модифікація скасовується, а функція повертає дійсне поточне значення `v`.

### `atomic_try_cmpxchg`

Сучасна оптимізована альтернатива CAS (з'явилася в ядрі Linux 4.12) приймає вказівник `old` по посиланню: при невідповідності вона автоматично оновлює значення за вказівником `*old` актуальним вмістом пам'яті і на x86 транслюється у використання прапорця нуля `ZF`:

```c
bool atomic_try_cmpxchg(atomic_t *v, int *old, int new);
```

Якщо `v == *old`, функція записує `new` у `v` і повертає `true`. Якщо `v != *old`, вона автоматично оновлює локальну змінну `*old` поточним значенням `v` і повертає `false`.

На архітектурі x86 `atomic_try_cmpxchg` генерує продуктивніший машинний код у циклах безблокувальних спроб, оскільки прямо транслюється в прапор нульового результату інструкції `CMPXCHG` (`EFLAGS.ZF`), усуваючи потребу в додатковому виклику порівняння:

```c
// Класичний цикл безблокувального оновлення за допомогою atomic_try_cmpxchg
int old = atomic_read(&v);
do {
    new_val = calculate_new_state(old);
} while (!atomic_try_cmpxchg(&v, &old, new_val));
```

При кожній невдалій спробі `atomic_try_cmpxchg` самостійно перезавантажує нове актуальне значення `v` у змінну `old`, звільняючи розробника від виклику повторного `atomic_read()` у тілі циклу.

Варто відзначити, що при побудові безблокувальних списків та черг операція `atomic_try_cmpxchg` виключає потребу у внесенні проміжних змінних для збереження старого стану, скорочуючи кількість зайнятих регістрів загального призначення у згенерованому GCC коді.

## Атомарні бітові операції (`<linux/bitops.h>`)

Підсистема бітових операцій ядра працює з довільними масивами бітів у пам'яті (Bitmaps). На відміну від `atomic_t`, бітові операції приймають номер біта `nr` та вказівник на `unsigned long`.

| Сигнатура функції | Повертане значення | Опис операції |
| :--- | :--- | :--- |
| `set_bit(long nr, volatile unsigned long *addr)` | `void` | Атомарно встановлює біт номер `nr` в 1. |
| `clear_bit(long nr, volatile unsigned long *addr)` | `void` | Атомарно скидає біт номер `nr` в 0. |
| `change_bit(long nr, volatile unsigned long *addr)` | `void` | Атомарно інвертує біт номер `nr` (0->1 або 1->0). |
| `test_and_set_bit(long nr, volatile unsigned long *addr)` | `bool` | Встановлює біт `nr` в 1 та повертає **старе** значення біта. |
| `test_and_clear_bit(long nr, volatile unsigned long *addr)` | `bool` | Скидає біт `nr` в 0 та повертає **старе** значення біта. |
| `test_and_change_bit(long nr, volatile unsigned long *addr)` | `bool` | Інвертує біт `nr` та повертає **старе** значення біта. |
| `test_and_set_bit_lock(long nr, volatile unsigned long *addr)` | `bool` | Встановлює біт `nr` із семантикою Acquire для реалізації бітових спінлоків (`bit_spin_lock`). |
| `clear_bit_unlock(long nr, volatile unsigned long *addr)` | `void` | Скидає біт `nr` із семантикою Release для звільнення бітових спінлоків (`bit_spin_unlock`). |

Усі бітові операції з префіксом `__` (наприклад, `__set_bit()`) є **неатомарними** варіантами. Вони виконуються швидше, але можуть застосовуватися лише під захистом спінлока або в локальному поточному контексті.

При обробці великих масивів прапорців (наприклад, таблиць сторінок пам'яті або бітмапів вільних inode у файлових системах) бітові операції є незамінними, оскільки дозволяють змінювати один біт у машинному слові без ризику перезаписати сусідні біти, редаговані паралельними процесорами.

Поруч із ними ядро надає швидкий пошук вільного біта — `find_first_zero_bit()` та `find_next_zero_bit()`. Вони самі **не атомарні**: це звичайний послівний перегляд масиву `unsigned long`, який може повернути номер біта, уже зайнятого сусіднім ядром. Штатний спосіб виділити слот — знайти кандидата цими функціями, а претензію на нього заявити атомарним `test_and_set_bit()` і повторити пошук, якщо той повернув `true`.

## Захищений лічильник посилань `refcount_t` (`<linux/refcount.h>`)

Тип `refcount_t` реалізовано над `atomic_t`, але він містить апаратний та програмний захист від переповнення (Overflow) та використання після звільнення (Use-After-Free).

| Сигнатура функції | Повертане значення | Захисний механізм |
| :--- | :--- | :--- |
| `REFCOUNT_INIT(int i)` | `refcount_t` | Статична ініціалізація лічильника посилань початковим значенням `i`. |
| `refcount_set(refcount_t *r, int n)` | `void` | Встановлює значення `r = n`. |
| `refcount_read(const refcount_t *r)` | `unsigned int` | Зчитує поточне значення лічильника посилань. |
| `refcount_inc(refcount_t *r)` | `void` | Збільшує `r` на 1. Захищає від переповнення: якщо приріст виводить за `REFCOUNT_MAX` (`INT_MAX`) або виконується над нулем, викликає `refcount_warn_saturate()` — `WARN_ONCE` плюс примусове насичення. |
| `refcount_inc_not_zero(refcount_t *r)` | `bool` | Атомарно збільшує `r` на 1 лише якщо `r != 0`. Повертає `true` при успіху, захищаючи від race conditions при повторному отриманні об'єкта. |
| `refcount_dec(refcount_t *r)` | `void` | Зменшує `r` на 1. Викликає `WARN_ON`, якщо після зменшення результат став від'ємним або дорівнював 0. |
| `refcount_dec_and_test(refcount_t *r)` | `bool` | Зменшує `r` на 1. Повертає `true`, якщо результат дорівнює **0** (безпечний сигнал для деалокації пам'яті). |

Обидва аварійні шляхи — і приріст над нулем (помилка Use-After-Free), і вихід за `REFCOUNT_MAX` (`INT_MAX`, 2 147 483 647) — ведуть в ту саму функцію `refcount_warn_saturate()`. Вона першою ж дією записує в лічильник константу `REFCOUNT_SATURATED`, що дорівнює `INT_MIN / 2`, і лише потім друкує `WARN_ONCE` у `dmesg`. Із цієї точки лічильник заморожено: жоден інкремент не доведе його до `INT_MAX`, жоден декремент — до нуля, тож `refcount_dec_and_test()` уже ніколи не поверне `true` і об'єкт не буде звільнено. Ціною свідомого витоку пам'яті знімається цілий клас атак на передчасну деалокацію.

Крім того, функції `refcount_inc_not_zero()` реалізують атомарний захист від перегонів при отриманні об'єктів з глобальних кешів (наприклад, `dentry` у VFS). Потік перевіряє, чи об'єкт не перебуває в стані деалокації, і якщо `refcount != 0`, атомарно збільшує його без ризику захопити «мертву» структуру.

Важливо враховувати, що при спробі деалокації об'єкта з `refcount_t` виклик `refcount_dec_and_test()` є остаточним: якщо результат став рівним 0, жоден інший потік системи більше не зможе успішно виконати `refcount_inc_not_zero()`, що забезпечує математичну строгість деструкції об'єкта.

## Суфікси впорядкування пам'яті

За замовчуванням усі RMW операції ядра з поверненням значення мають суворі гарантії впорядкування (Full Memory Barrier). Однак для високооптимізованого коду ядро надає варіанти атомарних функцій із суфіксами впорядкування:

- **`_relaxed`** (наприклад, `atomic_inc_return_relaxed`): Атомарність модифікації в пам'яті повністю гарантується, але апаратні бар'єри пам'яті відсутні. Дозволяється інструкційне переставляння довкола виклику для оптимізації конвеєра CPU.
- **`_acquire`** (наприклад, `atomic_read_acquire`): Гарантує, що жодна наступна операція читання або запису в програмі не буде переставлена компілятором або CPU раніше цієї атомарної інструкції (Acquire Semantics).
- **`_release`** (наприклад, `atomic_set_release`): Гарантує, що всі попередні операції читання або запису будуть завершені до виконання цієї атомарної інструкції (Release Semantics).

Використання семантики `acquire-release` дозволяє будувати високопродуктивні безблокувальні алгоритми із мінімальними накладними витратами на синхронізацію кешів процесора.

Особливе місце посідає виклик `smp_mb__before_atomic()` та `smp_mb__after_atomic()`. Вони використовуються для прив'язки бар'єрів пам'яті до атомарних операцій без повернення значення (таких як `atomic_inc()`), перетворюючи їх на повністю впорядковані виклики з мінімальними витратами на сумісність із застарілими архітектурами.

## Внутрішня перевірка ядра `CONFIG_ATOMIC64_SELFTEST`

Для валідації коректності виконання атомарного API на нових апаратних архітектурах у ядрі Linux реалізовано внутрішній тестовий модуль `lib/atomic64_test.c`. При включенні конфігурації `CONFIG_ATOMIC64_SELFTEST=y` під час завантаження ядра виконується вичерпне тестування всіх граничних значень `atomic64_t` (переходи через 0, `S64_MAX`, `S64_MIN`, від'ємна арифметика та коректність перевірок CAS).

Варто розуміти межі цієї перевірки: набір тестів однопотоковий і виконується як `__init`-функція на одному ядрі. Він судить **функціональну** правильність архітектурних макросів `atomic64` — чи те саме число повертає `atomic64_add_return()`, чи спрацьовує CAS на межі `S64_MIN` — а не поведінку під конкуренцією. Змагання ядер перевіряють іншими засобами, передусім KCSAN. Діагностичні повідомлення самотестування виводяться у `dmesg` під час ініціалізації ядра і дозволяють розробникові нового порту миттєво побачити дефект в асемблерних макросах.

Окремо варто застерегти від типової помилки: `/proc/sys/kernel/split_lock_mitigate` — це не лічильник, а перемикач `0`/`1` (типово `1`), який лише вмикає уповільнення процесів-порушників. Прочитати з нього кількість шинних блокувань неможливо; факти виявлення split lock ядро повідомляє рядками в `dmesg`.
