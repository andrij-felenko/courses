# 📋 Контракт rseq: один виклик, дві структури, п'ять кодів помилок

Це точний перелік того, чим програма й ядро обмінюються через механізм перезапускних послідовностей: сигнатура системного виклику, поле за полем обидві структури спільної пам'яті, чинні й виведені з ужитку прапорці, умови кожної помилки, правила успадкування через `fork`/`clone`/`exec` і символи glibc, через які до всього цього дістаються, коли табличку зареєструвала бібліотека. Потрібен він тоді, коли треба або звіритися з чинним ABI, або зрозуміти, чому виклик повернув саме цей код, — бо половина відмов тут походить не з того аргументу, на який думають.

## Системний виклик

Обгортки в glibc немає — виклик роблять через `syscall(2)`:

```c
#include <linux/rseq.h>
#include <sys/syscall.h>
#include <unistd.h>

long rc = syscall(SYS_rseq, struct rseq *rseq, uint32_t rseq_len,
                  int flags, uint32_t sig);
```

| Аргумент | Що це |
|---|---|
| `rseq` | адреса таблички потоку; при знятті реєстрації — та сама адреса, що при реєстрації |
| `rseq_len` | довжина таблички **в байтах**; ніколи не менша за 32 |
| `flags` | `0` — зареєструвати, `RSEQ_FLAG_UNREGISTER` — зняти реєстрацію; інших значень немає |
| `sig` | 32-бітний підпис, який ядро запам'ятовує для цієї задачі й звіряє при кожному зриві |

Успіх — `0`, відмова — `-1` і код у `errno`. Реєстрація суто індивідуальна: кожен потік реєструє власну табличку, і **більше однієї реєстрації на потік не буває**. Пам'ять під табличку не можна звільняти чи використовувати під щось інше, доки реєстрація жива, — ядро писатиме туди й далі.

## struct rseq: спільна табличка потоку

| Зсув | Поле | Тип | Хто пише | Що містить | З версії |
|---:|---|---|---|---|---|
| 0 | `cpu_id_start` | `__u32` | ядро | номер ядра процесора; **завжди** значення з діапазону можливих ядер, навіть коли реєстрації ще не було | 4.18 |
| 4 | `cpu_id` | `__u32` | ядро (програма кладе `-1` при ініціалізації) | той самий номер, але зі спеціальними значеннями стану | 4.18 |
| 8 | `rseq_cs` | `__u64` (об'єднання) | програма ставить, ядро занулює | адреса чинного дескриптора ділянки або `0` | 4.18 |
| 16 | `flags` | `__u32` | програма | виведено з ужитку; мусить бути `0` | 4.18 |
| 20 | `node_id` | `__u32` | ядро | номер вузла NUMA поточного ядра процесора | 6.3 |
| 24 | `mm_cid` | `__u32` | ядро | номер конкурентності, унікальний у межах адресного простору | 6.3 |
| 28 | `char end[]` | — | — | межа опису полів; далі доповнення до 32 байтів | 6.3 |

Структура вирівняна на 32 байти (`__attribute__((aligned(4 * sizeof(__u64))))`) — тобто вміщається в один рядок кеша й не перетинає його межі.

**Чому номерів ядра процесора два.** Вони відрізняються не значенням, а тим, що може в них потрапити. `cpu_id_start` ніколи не містить нічого, крім правдоподібного номера, — саме ним індексують масив, не питаючи попередньо, чи все гаразд. `cpu_id` натомість несе стани:

| Значення | Ім'я в заголовку | Що означає |
|---:|---|---|
| `-1` | `RSEQ_CPU_ID_UNINITIALIZED` | реєстрації ще не було (або її щойно знято) |
| `-2` | `RSEQ_CPU_ID_REGISTRATION_FAILED` | реєстрація не вдалася — механізму в цьому потоці немає |
| `≥ 0` | — | справжній номер ядра процесора |

Поле оголошене як `__u32`, тож щоб побачити від'ємні стани, його читають через `int32_t` або порівнюють із `(uint32_t)-1`. Читати обидва поля має право лише той потік, що зареєстрував табличку; читання з чужого потоку дає лише «якесь недавнє значення» — воно застаріває в ту саму мить.

Поле `rseq_cs` на 64-бітних платформах — звичайний `__u64`. На 32-бітних це об'єднання з парою `ptr32` + `padding`, розкладених за порядком байтів платформи: писати треба **всі вісім байтів** (доповнення — нулями), бо ядро читає ціле 64-бітне число.

## Правило розширення: rseq_len

Тут ховається найчастіше непорозуміння. Виклик міряє табличку в байтах, а не в полях, і мінімум — 32, хоча полів початково було на 20 байтів. Причина проста: структура від самого початку вирівняна на 32, тож `sizeof(struct rseq)` дорівнював 32 ще у версії 4.18, і саме це число зафіксували як «вихідний розмір».

Ядро приймає довжину за такою умовою (усе інше — `EINVAL`):

```
rseq_len < 32                                  → відмова
rseq_len = 32   і адреса не кратна 32          → відмова
rseq_len > 32   і (адреса не кратна вирівнюванню
                   struct rseq  або  rseq_len < 28) → відмова
```

Число 28 — це `offsetof(struct rseq, end)`, тобто «стільки байтів справді описано полями в цій версії ядра». Умова «більша довжина — не менша за 28» і є механізм розширення: коли ABI доросте до нових полів, ядро підніме цю межу, а старі програми з `rseq_len = 32` працюватимуть далі.

Скільки полів справді підтримує ядро, програма питає не у виклику, а в [допоміжного вектора](book:unix-linux/auxiliary-vector) — двох записів, які ядро кладе на стек під час запуску образу:

| Запис | Номер | Значення |
|---|---:|---|
| `AT_RSEQ_FEATURE_SIZE` | 27 | скільки байтів таблички описано полями (28 на 6.3+) |
| `AT_RSEQ_ALIGN` | 28 | якого вирівнювання вимагає ядро для таблички (32) |

Обидва записи з'явилися разом із `node_id` і `mm_cid` у версії 6.3. Якщо `getauxval(AT_RSEQ_FEATURE_SIZE)` повертає нуль — вектор таких записів не містить, тобто ядро старіше й описаних полів рівно 20 байтів. Читати `node_id` чи `mm_cid` на такому ядрі безглуздо: ядро туди не пише, і там лежатиме те, що поклала сама програма.

![Побайтова розкладка struct rseq: поля, ознака підтримуваних можливостей і вирівнювання](/reference/unix-linux/processes/rseq/img/rseq-layout.svg)

*Мінімум для `rseq_len` — 32 байти, бо стільки займає структура з доповненням; а скільки з них ядро справді заповнює, каже окреме число з допоміжного вектора.*

## struct rseq_cs: дескриптор ділянки

| Зсув | Поле | Тип | Що містить |
|---:|---|---|---|
| 0 | `version` | `__u32` | версія формату; наразі лише `0` |
| 4 | `flags` | `__u32` | виведено з ужитку; мусить бути `0` |
| 8 | `start_ip` | `__u64` | адреса першої команди ділянки |
| 16 | `post_commit_offset` | `__u64` | довжина ділянки в байтах: перша команда **за** ділянкою — це `start_ip + post_commit_offset` |
| 24 | `abort_ip` | `__u64` | адреса, на яку ядро переставить лічильник команд при зриві |

Розмір — рівно 32 байти, вирівнювання — теж 32. Структура незмінна: її кладуть у сталу секцію під час компонування й ніколи не правлять під час роботи. Змінюється тільки вказівник на неї в табличці.

Читаючи дескриптор, ядро перевіряє його на все відразу — і жодна з цих перевірок **не є кодом повернення виклику**, бо відбувається вона вже на шляху повернення в простір користувача:

| Умова | Навіщо перевірка |
|---|---|
| адреса дескриптора або будь-яка з трьох адрес — поза межами простору користувача | дескриптор під керуванням програми; ядро не піде за вказівником у власну пам'ять |
| `version > 0` | формат, якого це ядро не розуміє |
| `start_ip + post_commit_offset` переповнюється | інакше «діапазон» загорнувся б і покрив пів адресного простору |
| `abort_ip` лежить усередині діапазону ділянки | зрив усередину ділянки означав би нескінченний перезапуск |
| чотири байти безпосередньо перед `abort_ip` не збігаються з підписом реєстрації | стрибок готують не туди, куди дозволив автор програми |

## Прапорці

| Ім'я | Значення | Де | Стан |
|---|---:|---|---|
| `RSEQ_FLAG_UNREGISTER` | `1 << 0` | аргумент `flags` виклику | чинний, єдиний |
| `RSEQ_CS_FLAG_NO_RESTART_ON_PREEMPT` | `1 << 0` | поле `flags` в обох структурах | виведено з ужитку з 6.1 |
| `RSEQ_CS_FLAG_NO_RESTART_ON_SIGNAL` | `1 << 1` | те саме | виведено з ужитку з 6.1 |
| `RSEQ_CS_FLAG_NO_RESTART_ON_MIGRATE` | `1 << 2` | те саме | виведено з ужитку з 6.1 |

Три останні колись означали «не зривай мене на витісненні / на сигналі / на переносі» — вибіркове послаблення гарантії. З версії 6.1 їх не просто ігнорують: **будь-яке ненульове значення поля `flags`** — чи в табличці, чи в дескрипторі — під час обробки зриву стає внутрішньою помилкою, а вона перетворюється на сигнал (нижче). У журнал ядра при цьому один раз потрапляє `Deprecated flags (…) in rseq_cs ABI structure` для відомих прапорців або `Unknown flags (…)` для решти бітів. Обидва поля `flags` треба тримати нульовими — і в табличці, і в кожному дескрипторі.

## Коди помилок

Помилки тут двох різних родів, і плутати їх — головне джерело хибних діагнозів.

**Перший рід — те, що повертає сам виклик.**

| Код | Коли |
|---|---|
| `EINVAL` | `flags` має біт поза `RSEQ_FLAG_UNREGISTER`; адреса не вирівняна; `rseq_len` не проходить умову вище; при знятті — адреса чи довжина не ті, що при реєстрації, або реєстрації взагалі немає; при повторній реєстрації — **адреса або довжина відмінні** від чинних |
| `EPERM` | адреса й довжина збігаються з чинною реєстрацією, а `sig` — ні (і при знятті, і при повторній реєстрації) |
| `EBUSY` | реєстрація вже є, і **всі** аргументи збігаються з нею до єдиного біта |
| `EFAULT` | табличка недоступна за вказаною адресою на читання й запис |
| `ENOSYS` | виклику в ядрі немає: воно старіше за 4.18 або зібране без `CONFIG_RSEQ` |

Різниця між `EINVAL` і `EBUSY` при вже наявній реєстрації варта окремого рядка, бо саме її найчастіше читають навпаки. `EBUSY` — це не «зайнято, спробуй пізніше», а «ти вже зареєстрований рівно з цими аргументами»: код, який спокійно можна вважати успіхом. `EINVAL` натомість означає «місце зайняте **іншою** табличкою». Тому програма, що спробує зареєструвати власну табличку поверх глібсівської, дістане `EINVAL`, а бібліотека, що знайшла глібсівську адресу й повторно зареєструвала саме її, — `EBUSY`.

Коду `EOVERFLOW` серед відповідей `rseq(2)` **немає** — попри те, що він трапляється в переказах цього інтерфейсу. Єдина перевірка на переповнення (`start_ip + post_commit_offset`) належить до другого роду й дає `EINVAL` усередині ядра. Перевірено за джерелом `kernel/rseq.c` у гілці 6.12 і в поточному стані дерева; довідкова сторінка `rseq(2)` теж перелічує лише п'ять кодів вище.

**Другий рід — помилки, яких ніхто не повертає.** Вони виникають тоді, коли ядро вже повертає задачу в простір користувача й читає її табличку. Повертати код нікуди — виклику ж не було. Тому будь-яка з них закінчується `force_sigsegv()`: потік дістає `SIGSEGV`, і його не можна ані проігнорувати, ані перекрити власним обробником, що просто піде далі.

| Причина | Наслідок |
|---|---|
| табличка чи дескриптор недоступні для читання | `SIGSEGV` |
| дескриптор не проходить хоч одну з перевірок вище | `SIGSEGV` |
| підпис перед `abort_ip` не той — плюс запис у журнал `Possible attack attempt. Unexpected rseq signature …` | `SIGSEGV` |
| ненульові `flags` у табличці або дескрипторі (з 6.1) | `SIGSEGV` |
| системний виклик усередині ділянки — на ядрі з `CONFIG_DEBUG_RSEQ` | `SIGSEGV` |

Практичний висновок: раптовий `SIGSEGV` у програмі, що вживає перезапускні послідовності, — привід спершу заглянути в журнал ядра, а не в стек викликів.

## Успадкування

| Подія | Що стається з реєстрацією | Чому саме так |
|---|---|---|
| `fork()`, `clone()` **без** `CLONE_VM` | успадковується повністю: адреса, довжина, підпис | адресний простір дитини — копія батьківського, тож табличка лежить там само |
| `clone()` з `CLONE_VM` (створення потоку) | реєстрації немає, поля обнулено | простір спільний, а табличка мусить бути в кожного потоку своя |
| `execve()` | стирається | старого образу разом із його табличкою більше немає |
| завершення потоку | ядро знімає реєстрацію само | — |

Звідси й звичний порядок: `pthread_create()` іде через `CLONE_VM`, тому кожен новий потік реєструється сам, і саме це робить glibc у стартовому коді потоку.

Знімаючи реєстрацію, ядро ще й приводить табличку до вихідного стану: `cpu_id_start = 0`, `cpu_id = -1`, `node_id = 0`, `mm_cid = 0`. Якщо на цей запис не вдається (пам'ять уже недоступна) — виклик повертає `EFAULT`, а реєстрація лишається чинною.

## Символи glibc

З версії 2.35 glibc реєструє табличку для кожного потоку сама, включно з головним. Адреси таблички вона не оголошує — натомість дає три змінні, з яких її обчислюють:

| Символ | Тип | Що це |
|---|---|---|
| `__rseq_offset` | `ptrdiff_t` | зсув від [вказівника потоку](book:unix-linux/elf-tls) до таблички; однаковий у всіх потоках процесу, може бути від'ємним |
| `__rseq_size` | `unsigned int` | `0` — реєстрації немає (не вдалася або вимкнена); інакше розмір **діючої** частини таблички |
| `__rseq_flags` | `unsigned int` | прапорці, з якими зроблено реєстрацію; наразі завжди `0` |

Адреса таблички — `(char *)__builtin_thread_pointer() + __rseq_offset`.

Значення `__rseq_size` міняло зміст: у 2.35–2.39 воно дорівнювало 32 завжди, бо повідомляло розмір структури разом із доповненням; з 2.40 — розмір справді діючої частини таблички, тобто 20 на ядрі без розширень і 28 на 6.3 і новіших. Тому перевіряти наявність `mm_cid` через `__rseq_size` можна лише з glibc 2.40; на старіших бібліотеках правильне джерело — `AT_RSEQ_FEATURE_SIZE`.

**Правило спільного користування.** Реєстрація одна на потік, тож табличка теж одна — і всі, кому вона потрібна, працюють із глібсівською через ці символи. Так робить `librseq`, так робить розподільник tcmalloc. Спроба завести власну натомість дає `EINVAL`; єдиний законний спосіб забрати місце — вимкнути глібсівську реєстрацію змінною середовища `GLIBC_TUNABLES=glibc.pthread.rseq=0`, після чого `__rseq_size` дорівнює нулю, а `sched_getcpu()` повертається до звичайного, дорожчого шляху.

Спільною є й найважливіша комірка — `rseq_cs`. Це означає, що двох ділянок водночас у потоці бути не може: друга затерла б указівник першої. Вкладення ділянок неможливе й за побудовою — усередині ділянки не буває викликів функцій.

## RSEQ_SIG

Підпис вибирає програма, ядро лише порівнює. Але вибір не довільний: значення беруть таке, що є кодом команди-пастки для цієї архітектури.

| Архітектура | `RSEQ_SIG` | Яку команду кодує |
|---|---:|---|
| x86-32, x86-64 | `0x53053053` | `ud1 0x53053053(%rip),%edi` |
| arm64 | `0xd428bc00` | `brk #0x45e0` |
| powerpc | `0x0fe5000b` | `twui r5,11` |

Правила довкола нього такі:

- рівно чотири байти **безпосередньо перед** `abort_ip` мусять містити це число; ядро читає їх за адресою `abort_ip - 4` і звіряє з тим, що дістало при реєстрації;
- підпис у реєстрації один на потік — тож усі ділянки в потоці, з якої б бібліотеки вони не походили, мусять уживати те саме значення;
- розбіжність дає запис у журнал і `SIGSEGV`.

Чому це саме команда-пастка, видно з протилежного випадку: якби підпис був довільним числом, він лежав би в коді як безневинні чотири байти, на які теж можна стрибнути. Вибравши недійсну команду, автори зробили так, що потрапляння на сам підпис негайно валить потік замість того, щоб непомітно поїхати виконанням далі.

## Мінімальний робочий доступ

Найкоротший коректний шлях до таблички: спершу спитати glibc, і лише коли її реєстрації немає — зареєструвати власну.

```c
#define _GNU_SOURCE
#include <errno.h>
#include <linux/rseq.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/auxv.h>
#include <sys/syscall.h>
#include <unistd.h>

#ifndef AT_RSEQ_FEATURE_SIZE
#define AT_RSEQ_FEATURE_SIZE 27
#endif

#define RSEQ_SIG 0x53053053                       /* x86 */
#define OFFSETOFEND(t, f) (offsetof(t, f) + sizeof(((t *)0)->f))

/* Слабкі — щоб код лінкувався і з glibc без підтримки rseq. */
extern __attribute__((weak)) ptrdiff_t    __rseq_offset;
extern __attribute__((weak)) unsigned int __rseq_size;

/* Запасний варіант: власна табличка, якщо glibc своєї не зареєструвала. */
static __thread struct rseq own_area __attribute__((aligned(32))) = {
    .cpu_id = RSEQ_CPU_ID_UNINITIALIZED,
};
static __thread int own_state;                    /* 0 — не пробували, 1 — є, -1 — не вийшло */

static struct rseq *rseq_area(void)
{
    if (&__rseq_size != NULL && __rseq_size != 0)
        return (struct rseq *)((char *)__builtin_thread_pointer() + __rseq_offset);

    if (own_state == 0) {
        long rc = syscall(SYS_rseq, &own_area, sizeof(own_area), 0, RSEQ_SIG);
        own_state = (rc == 0) ? 1 : -1;           /* ENOSYS / EINVAL / EFAULT */
    }
    return own_state == 1 ? &own_area : NULL;
}

/* Нуль у допоміжному векторі означає ядро до 6.3: описано 20 байтів. */
static unsigned int feature_size(void)
{
    unsigned long v = getauxval(AT_RSEQ_FEATURE_SIZE);
    return v ? (unsigned int)v : 20u;
}

int main(void)
{
    struct rseq *r = rseq_area();
    if (r == NULL) {
        fprintf(stderr, "rseq недоступний\n");
        return 1;
    }

    printf("cpu_id_start = %u\n", r->cpu_id_start);
    printf("cpu_id       = %d\n", (int32_t)r->cpu_id);   /* -1 і -2 — стани, не номери */

    if (feature_size() >= OFFSETOFEND(struct rseq, mm_cid))
        printf("node_id = %u, mm_cid = %u\n", r->node_id, r->mm_cid);

    return 0;
}
```

Три подробиці цього коду не декоративні. Слабкі оголошення потрібні, щоб бінарник лінкувався й запускався зі старою бібліотекою, де цих символів немає, — тоді `&__rseq_size` дорівнює `NULL`. Вирівнювання власної таблички на 32 обов'язкове: без нього виклик поверне `EINVAL` ще до того, як гляне на решту аргументів. А `__builtin_thread_pointer()` доступний не скрізь — на архітектурах і компіляторах без нього те саме значення дістають коротким асемблерним рядком, і саме тому glibc віддає **зсув**, а не адресу: адреса в кожного потоку своя, а зсув один на весь процес.
