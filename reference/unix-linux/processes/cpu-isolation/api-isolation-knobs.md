# 📋 Довідка: ручки ізоляції — що задають при старті, що крутять на живій машині, чим перевіряють

Ізоляція ядра процесора складається не з одного вимикача, а з десятка окремих ручок, розкиданих між командним рядком ядра, cgroup v2, sysfs і sysctl. Тут вони зібрані в одному місці: формат значення, чи діє ручка на живій системі, і — найважливіше — чим перевірити, що вона прийнялася, бо мовчазна відмова тут звичніша за помилку.

## Форма запису списку ядер

```
4-7            діапазон, лише за зростанням
2,4,6          перелік
1,4-7,12       мішанина
N              останнє ядро машини (у параметрах командного рядка)
```

Один і той самий набір ядер має дві несумісні форми запису, і плутанина між ними — найчастіша дрібна помилка:

| Форма | Де вживається | Ядра 4–7 виглядають як |
|---|---|---|
| список | параметри командного рядка, `cpuset.cpus`, `*_cpumask` у sysctl, `smp_affinity_list` | `4-7` |
| шістнадцяткова маска | `/proc/irq/<n>/smp_affinity`, `/proc/irq/default_smp_affinity` | `f0` |

Безпечне правило: спершу прочитати файл, побачити, у якій формі він показує чинне значення, і писати в тій самій.

## Параметри командного рядка

Ці ручки [ядро дістає при старті](book:unix-linux/bootloader-and-cmdline) — рядок фіксується назавжди, тож змінити їх без перезавантаження не можна. Те, що ядро справді отримало, лежить у `/proc/cmdline`.

| Параметр | Значення | Що прибирає | Слід у системі |
|---|---|---|---|
| `isolcpus=[прапорці,]<список>` | прапорці `nohz`, `domain`, `managed_irq` через кому **перед** списком; без прапорців — `domain` | залежить від прапорців (нижче) | `/sys/devices/system/cpu/isolated`, журнал ядра |
| `nohz_full=<список>` | список | періодичний тік; заразом віддає на службові ядра зворотні виклики RCU, незв'язані таймери й робочі черги | `/sys/devices/system/cpu/nohz_full` |
| `rcu_nocbs=<список>` | список; ядра з `nohz_full=` потрапляють сюди самі, новіші ядра приймають і `all` | зворотні виклики [RCU](book:unix-linux/rcu-mechanism) — механізму, якому кожне ядро мусить звітувати про вихід із критичних ділянок читання — виконують окремі потоки, які вже можна пересунути | потоки `rcuop/<n>` у переліку процесів |
| `rcu_nocb_poll` | без значення | пробудження: потоки `rcuo*` самі опитують чергу замість того, щоб ізольоване ядро їх будило — менше перешкод тут ціною зайвої роботи на службових | лише `/proc/cmdline` |
| `irqaffinity=<список>` | список | усталену маску переривань, які зареєструються після цього моменту (уже наявних не чіпає) | `/proc/irq/default_smp_affinity` |
| `watchdog_cpumask=<список>` | список | потоки сторожового пса; коли задано `nohz_full=`, ядро виключає ці ядра само | `/proc/sys/kernel/watchdog_cpumask` |
| `skew_tick=1` | без значення | не перешкоду на ізольованому ядрі, а тиск на спільні замки: розводить тік різних ядер у часі, тож лікує **службову** половину машини | лише `/proc/cmdline` |
| `tsc=reliable` | без значення | періодичну звірку годинника з повільнішим джерелом; є й вужче `tsc=nowatchdog` — прибрати саму звірку, лишивши перевірки при старті | рядки про `clocksource` у журналі ядра |
| `nowatchdog` | без значення | обидва детектори блокувань одразу — і потік `watchdog/<n>`, і апаратний | `/proc/sys/kernel/watchdog` показує `0` |

Три прапорці `isolcpus=` вилучають різне: `domain` — з областей планування (балансувальник, незв'язані таймери й черги), `nohz` — те саме, що перелічити ядра в `nohz_full=`, `managed_irq` — не адресувати сюди переривання, чию прив'язку розподіляє саме ядро операційної системи.

Ядро повідомляє про відмову рядком у журналі, а не помилкою завантаження. Варто знати ці рядки в обличчя:

```
Housekeeping: nohz unsupported. Build with CONFIG_NO_HZ_FULL
Housekeeping: nohz_full= or isolcpus= incorrect CPU range
Housekeeping: nohz_full= must match isolcpus=
Housekeeping: must include one present CPU neither in nohz_full= nor in isolcpus=domain, ignoring setting …
isolcpus: Skipped unknown flag …
```

Останній рядок — про прапорець, якого ядро не знає: розбирач `isolcpus=` у ванільному ядрі приймає рівно три імені (`nohz`, `domain`, `managed_irq`), решту мовчки пропускає, а список ядер розбирає далі. Тому, зокрема, `isolcpus=io_queue,4-7` **не** обмежить черги блокового введення-виведення: прапорця з таким іменем у мейнлайні немає (пропозицію додати його обговорюють у списку розсилки; станом на серпень 2026 в дереві Торвальдса його нема), і рядок спрацює як звичайний `isolcpus=4-7`.

## Файли керування на живій машині

| Файл | Значення | Що робить |
|---|---|---|
| `<група>/cpuset.cpus` | список | які ядра дозволено задачам групи ([розділи cpuset](book:unix-linux/cpu-affinity) — той самий механізм, що й прив'язка, але на цілу групу) |
| `<група>/cpuset.cpus.exclusive` | список | ядра, віддані цій гілці назовсім; мусять не перетинатися з такими самими списками сестринських груп |
| `<група>/cpuset.cpus.exclusive.effective` | лише читання | скільки з попереднього справді дісталося цій групі |
| `<група>/cpuset.cpus.partition` | `member` · `root` · `isolated` | `isolated` — розділ **без балансування навантаження**: саме він замінює планувальну половину `isolcpus=` на живій машині |
| `/sys/fs/cgroup/cpuset.cpus.isolated` | лише читання | усі ядра, які зараз перебувають в ізольованих розділах |
| `/sys/devices/virtual/workqueue/cpumask` | маска | де виконуються **незв'язані** [робочі черги](book:unix-linux/interrupts-bottom-halves) — відкладена робота, яку ядро не прив'язало до конкретного процесора |
| `/sys/devices/virtual/workqueue/<черга>/cpumask`, `affinity_scope`, `affinity_strict` | маска, назва обсягу, `0`/`1` | те саме для окремої черги; строгий обсяг забороняє потокові виходити за межі свого набору |
| `/proc/irq/<n>/smp_affinity_list` | список | куди адресувати конкретне переривання |
| `/proc/sys/kernel/timer_migration` | `0`/`1`, усталено `1` | чи можна зносити таймери з ядер, що простоюють |
| `/proc/sys/kernel/watchdog_cpumask` | список | де сторожовий пес прокидається на перевірку |
| `/proc/sys/kernel/watchdog`, `watchdog_thresh` | `0`/`1`; секунди, усталено `10` | вимкнути детектори блокувань або зробити їхні перевірки рідшими |
| `/proc/sys/vm/stat_interval` | секунди, усталено `1` | як часто зводиться статистика сторінок; більше значення — рідші пробудження |

Останні чотири — звичайні [налаштування sysctl](book:unix-linux/sysctl-tunables): переживають читання-запис, але не перезавантаження, тож постійними їх роблять файлом у `/etc/sysctl.d/`.

Ізольований розділ створюють так:

```sh
# cgroup v2; контролер cpuset має бути ввімкнений у батька
echo '+cpuset' > /sys/fs/cgroup/cgroup.subtree_control
mkdir /sys/fs/cgroup/rt
echo '4-7'     > /sys/fs/cgroup/rt/cpuset.cpus
echo isolated  > /sys/fs/cgroup/rt/cpuset.cpus.partition

cat /sys/fs/cgroup/rt/cpuset.cpus.partition   # isolated                  ← прийнялося
                                              # isolated invalid (…)      ← ні, у дужках причина
cat /sys/fs/cgroup/cpuset.cpus.isolated       # 4-7
```

Запис у `cpuset.cpus.partition` майже ніколи не повертає помилки — розділ просто стає недійсним, і причина написана в дужках при читанні. Найчастіші: ядра не належать батьківському набору, ті самі ядра вже забрала сестринська група, або групу створено глибоко в ієрархії без того, щоб дорогою вниз проставити `cpuset.cpus.exclusive`. Загальну механіку [дерева контрольних груп](book:unix-linux/cgroups) варто мати в голові: розділ — це властивість вузла, а не окремого ядра.

Переривання розводять по одному:

```sh
grep -i nvme /proc/interrupts | cut -d: -f1        # номери потрібних переривань
echo 0-3 > /proc/irq/142/smp_affinity_list
cat /proc/irq/142/smp_affinity_list                # 0-3 — прийнялося
```

Відмова тут гучна: якщо прив'язку цього переривання розподіляє саме ядро операційної системи (черги багатозадачних мережевих і дискових контролерів), запис поверне `-EIO` — оболонка покаже «Input/output error». Такі переривання руками не пересуваються взагалі; єдиний важіль на них — `isolcpus=managed_irq` при старті.

## Файли для читання стану

| Файл | Що показує |
|---|---|
| `/sys/devices/system/cpu/isolated` | ядра, вилучені з планування — і завантажувальним параметром, і ізольованим розділом |
| `/sys/devices/system/cpu/nohz_full` | ядра, яким дозволено безтіковий режим; порожньо (на частині ядер — `(null)`) означає, що параметра не було |
| `/proc/interrupts` | лічильники за ядрами — головне мірило того, чи вийшло |
| `/proc/timer_list` | які таймери зараз озброєні на кожному ядрі; читає лише адміністратор |
| `/sys/kernel/debug/tracing` (сучасна назва — `/sys/kernel/tracing`) | трасувальники, що називають винуватця поіменно |

Чотири рядки `/proc/interrupts`, які варто читати разом:

```
LOC  локальний таймер            тік і одноразові таймери цього ядра
RES  перепланування              інше ядро попросило перевибрати задачу
CAL  виклик функції              спільна робота, надіслана сюди
TLB  скидання перекладів адрес   хтось змінив таблиці сторінок
```

Останні три — це [міжпроцесорні переривання](book:unix-linux/inter-processor-interrupts): прямі сигнали від сусідніх ядер, які не питають про жодні маски. Приріст `LOC` — головне число всієї теми:

```sh
CPU=5
col=$((CPU + 2))                                   # перше поле рядка — «LOC:»
a=$(awk -v c=$col '/^ *LOC/ {print $c}' /proc/interrupts); sleep 10
b=$(awk -v c=$col '/^ *LOC/ {print $c}' /proc/interrupts)
echo $(( (b - a) / 10 ))    # ~1 — безтіковий режим працює; ~1000 — тік іде як завжди
```

Коли число не сходиться, винуватця називають [трасувальники затримок](book:unix-linux/latency-tracers) — вони міряють украдений час і показують, хто його вкрав:

```sh
cd /sys/kernel/tracing
echo 5       > osnoise/cpus              # де шукати шум
echo 1000000 > osnoise/period_us         # вікно виміру
echo 900000  > osnoise/runtime_us        # скільки з вікна власне міряємо
echo 20      > osnoise/stop_tracing_us   # спинити трасування на першій паузі понад 20 мкс
echo osnoise > current_tracer
cat trace
```

Те саме зручніше подає утиліта `rtla`: `rtla osnoise top -c 5 -d 10s` показує джерела шуму на ядрі 5 за десять секунд, `rtla timerlat hist -c 5 -d 10s` — гістограму запізнення таймера, тобто відповідь на питання «наскільки пізніше за замовлений момент ядро справді прокинулося».

> 🔧 **Навіщо це.** У кожного шару свій спосіб сказати «ні», і всі троє тихі. Завантажувальні параметри скаржаться рядком у журналі ядра й вантажаться далі. Розділ cpuset не повертає помилки — він стає недійсним, і причина видна лише при читанні файлу назад. Переривання відмовляє кодом `-EIO`, який легко проґавити в скрипті. Тому порядок перевірки не «чи я правильно написав конфігурацію», а знизу вгору: `/proc/cmdline` → журнал ядра → читання назад кожного записаного файлу → приріст `LOC`. Останнє число вирішальне: доки воно тисяча, усе інше не має значення.
