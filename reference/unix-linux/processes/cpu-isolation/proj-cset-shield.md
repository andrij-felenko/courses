# ⚙️ Щит із `cset`: вирізати ядра й перевірити, що система справді переїхала

Розділи cpuset створюють і руками, але порядок дій там неочевидний і легко зробити його у зворотний бік — заборонити чуже там, де воно вже сидить. `cset` — тонка обгортка на Python над тією ж підсистемою, яка робить кроки в правильному порядку одним викликом.

Головне, заради чого сюди варто зазирнути, — не команди, а **перевірки після кожної**. Ізоляція мовчки не спрацьовує: конфігурація приймається, вивід виглядає переконливо, а ядро далі будять тисячу разів на секунду. Тому кожен крок нижче має пару «зробити» → «переконатися».

## Що робить `cset shield`

Дві контрольні групи замість одної:

```
system   ← сюди переїжджають УСІ наявні процеси, зокрема systemd з дітьми
user     ← сюди пускають лише те, що ви явно запустили
```

Ключовий тут перший рядок. Порожня група з ізольованими ядрами нічого не ізолює: процеси, що лишились у кореневій групі, зберігають право на всі ядра, і планувальник ним скористається. Ізоляція починається з того, що систему **заганяють у куток**, а не з того, що вам виділяють ядра.

## Крок 1. Поставити щит

Машина на 8 ядер; ядра 0–1 лишаємо системі, 2–7 забираємо:

```bash
sudo cset shield -c 2-7 -k on
```

`-k on` переносить ще й неприв'язані потоки ядра. Прив'язані за побудовою (`migration/N`, `ksoftirqd/N`, `rcuc/N`) не переїдуть ніколи — вони існують окремо на кожному ядрі й обслуговують саме його.

**Переконатися:**

```bash
sudo cset shield
```

У виводі має бути `"user" cpuset of CPUSPEC(2-7) with N tasks running` і мала кількість задач у `user`. Якщо в `user` уже сидять десятки задач до того, як ви щось запустили, — щит поставлено поверх процесів, а не навколо порожніх ядер.

## Крок 2. Перевірити, що корінь спорожнів

Це та перевірка, якої зазвичай не роблять, а вона вирішальна:

```bash
cat /sys/fs/cgroup/cpuset/tasks | wc -l        # cgroup v1, шлях cset
```

Нуль або кілька непереносних потоків — добре. Десятки — переїзд не завершився, і кожен з них має право прийти на ваші ядра.

## Крок 3. Запустити задачу під щитом

```bash
sudo cset shield --exec -- ./my-app --arg value
```

Уже запущений процес переносять за номером:

```bash
sudo cset shield --shield --pid 4242
```

**Переконатися, що задача справді там, де треба:**

```bash
taskset -pc 4242          # має показати 2-7, а не 0-7
```

## Крок 4. Виміряти, а не повірити

Щит прибирає **чужі задачі** — і на цьому його влада закінчується. Тік, зворотні виклики RCU й переривання пристроїв приходять не через планувальник, тому після кроку 3 ядро цілком може лишатися галасливим.

```bash
awk '/^ *LOC/ {print $4}' /proc/interrupts; sleep 10
awk '/^ *LOC/ {print $4}' /proc/interrupts     # стовпчик потрібного ядра
```

Читання результату:

```
приріст ≈ 10000 за 10 с   → безтіковий режим НЕ увімкнувся: або немає nohz_full=,
                            або на ядрі є друга готова задача
приріст ≈ 10 за 10 с      → періодичного тіка немає, це найкращий досяжний результат
```

Далі дивляться решту рядків того самого стовпчика — будь-який, що росте, це пристрій, чию прив'язку не переставили.

## Крок 5. Зняти щит

```bash
sudo cset shield --reset
```

Процеси повертаються в кореневу групу, обидві групи зникають. Параметри завантаження (`nohz_full=`, `rcu_nocbs=`) це не чіпає — вони діють до перезавантаження незалежно від розділів.

## Межі способу

`cset` працює через **cgroup v1**, і на системах з єдиною ієрархією v2 його або немає в пакунках, або він вимагає завантажити систему з `systemd.unified_cgroup_hierarchy=0`. На таких машинах ті самі кроки роблять напряму через файли v2 (`cpuset.cpus`, `cpuset.cpus.partition`), і саме цей шлях сьогодні основний.

Утиліта не має стосунку до тіка, RCU й переривань — усе це лишається на параметрах завантаження й ручній прив'язці. Щит без них дає ядро без чужих задач і з тисячею таймерних переривань на секунду, тобто рівно половину роботи.
