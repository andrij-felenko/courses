# Бар'єри пам'яті в ядрі Linux

<preknowlist>
- [Атомні операції в ядрі Linux](book:unix-linux/atomic-ops) — базові атомарні примітиви модифікації даних.
- [Конкурентність і блокування в ядрі](book:unix-linux/kernel-locking) — правила взаємодії паралельних потоків виконання.
</preknowlist>

Сучасні високопродуктивні процесори та компілятори оптимізують виконання коду шляхом зміни порядку інструкцій (out-of-order execution, спекулятивне виконання) та використання проміжних буферів запису (store buffers / write buffers). Для однопотокового коду ці оптимізації абсолютно прозорі: процесор гарантує дотримання принципу strictly sequential execution per-thread (ілюзія послідовності). Однак у багатопотокових ядерних системах та під час взаємодії з апаратурою (DMA, пам'ять пристроїв) реодеринг інструкцій читання та запису може призвести до важковиявлюваних і катастрофічних збоїв.

Бар'єри пам'яті (memory barriers) — це спеціальні примітиви компілятора та інструкції процесора, які примусово зупиняють перевпорядкування читань і записів крізь визначену межу у коді.

## Чому виникає реодеринг: Буфери запису та out-of-order execution

Щоб зрозуміти необхідність бар'єрів пам'яті, розглянемо апаратну архітектуру сучасного ядра процесора:

```
[ CPU Core 0 ]  ──> [ Store Buffer ] ──> [ L1 Data Cache ]
                                                │
                                        [ System Bus / RAM ]
                                                │
[ CPU Core 1 ]  ──> [ Store Buffer ] ──> [ L1 Data Cache ]
```

1. **Буфери запису (Store Buffers):** Коли ядро виконує інструкцію запису в пам'ять `MOV [address], val`, воно не чекає, поки дані пройдуть шину та кеш L1/L2. Запис негайно скидається у високошвидкісний локальний Store Buffer процесора, а ядро продовжує виконувати наступні інструкції. Інші ядра процесора не бачать вмісту цього Store Buffer, поки він не буде флешнутий у спільний кеш.
2. **Перевпорядкування компілятором (Compiler Reordering):** Компилятор C (GCC/Clang) під час агресивних оптимізацій (`-O2`, `-O3`) може переставити інструкції читання та запису місцями у згенерованому ассемблері, якщо між ними немає прямої дата-залежності (data dependency) у межах даної функції.

### Класична ілюстрація проблеми

Розглянемо двохпотоковий приклад без бар'єрів:

```c
// Початковий стан у RAM: flag = 0, data = 0

// CPU Core 0 (Producer)        // CPU Core 1 (Consumer)
data = 42;                      while (flag == 0); // чекаємо прапорець
flag = 1;                       print(data);
```

Інтуїтивно здається, що `print(data)` завжди виведе `42`. Проте на реальній суперскалярній системі можливі два сценарії збою:
- **Апаратний:** CPU Core 0 скинув `flag = 1` у кеш раніше ніж `data = 42` виплив із його Store Buffer. Core 1 побачив `flag == 1`, але зчитав застаріле значення `data == 0`.
- **Компіляторний:** Компілятор поміняв місцями інструкції `data = 42` та `flag = 1`, бо в межах коду Core 0 вони незалежні.

## Види бар'єрів пам'яті в ядрі Linux

Ядро Linux розділяє бар'єри на дві основні категорії: **бар'єри компілятора** та **апаратні бар'єри процесора**.

### 1. Бар'єр компілятора (`barrier()`)

Бар'єр компілятора забороняє GCC/Clang переставляти інструкції читання/запису крізь точку бар'єра під час генерації ассемблерного коду.

```c
#define barrier() __asm__ __volatile__("": : :"memory")
```

Вказуючи `"memory"` у списку clobber-регістрів, ми повідомляємо компілятору, що дана інструкція може змінити будь-яку комірку пам'яті. Компілятор змушений скинути всі локальні значення з регістрів у пам'ять до бар'єра та заново прочитати необхідні змінні після нього.

### 2. Апаратні бар'єри процесора (SMP barriers)

У багатопроцесорних системах (SMP) використовуються апаратні бар'єри, які примушують процес скидати Store Buffers та синхронізувати кеші:

| Функція ядра | Тип бар'єра | Опис поведінки | Інструкція x86_64 |
| :--- | :--- | :--- | :--- |
| `smp_wmb()` | Write Memory Barrier | Гарантує, що всі записи **ДО** бар'єра будуть видимі іншим ядрам раніше, ніж будь-який запис **ПІСЛЯ** бар'єра. | `barrier()` (на x86 записи впорядковані апаратно TSO) |
| `smp_rmb()` | Read Memory Barrier | Гарантує, що всі зчитування **ДО** бар'єра завершаться раніше, ніж будь-яке зчитування **ПІСЛЯ** бар'єра. | `barrier()` (на x86 зчитування впорядковані) |
| `smp_mb()` | Full Memory Barrier | Повний двосторонній бар'єр: і записи, і зчитування не можуть перетинати межу. | `MFENCE` або `LOCK ADD` |

Виправимо наш Producer-Consumer приклад за допомогою ядерних бар'єрів:

```c
// CPU Core 0 (Producer)        // CPU Core 1 (Consumer)
data = 42;                      while (flag == 0);
smp_wmb();                      smp_rmb();
flag = 1;                       print(data);
```

## Сучасний підхід: Acquire-Release семантика

У сучасному ядрі Linux примітивні бар'єри `smp_rmb()`/`smp_wmb()` все частіше замінюються на більш зрозумілу семантику **Acquire / Release**, яка вибудовує пару причинно-наслідкових зв'язків (happens-before ordering):

```c
#include <linux/compiler.h>

// Producer
smp_store_release(&flag, 1);    // Запис із семантикою Release (усі попередні записи фіксуються)

// Consumer
if (smp_load_acquire(&flag) == 1) { // Читання із семантикою Acquire (наступні читання бачать нові дані)
    print(data); // Гарантовано 42!
}
```

- **`smp_store_release(ptr, val)`:** Поміщає бар'єр запису *перед* збереженням значення. Гарантує, що жоден запис до цієї точки не випливе за неї.
- **`smp_load_acquire(ptr)`:** Поміщає бар'єр читання *після* зчитування значення. Гарантує, що жодне читання після цієї точки не притягнеться до неї.

> 🔧 **Навіщо це.** Acquire-Release семантика є основою для побудови безблокувальних кілець (lock-free ring buffers), алгоритму RCU (Read-Copy-Update) та передачі файлових дескрипторів без використання важких спінлоків.
