# 📋 Поверхня керування пам'яттю Cgroups v2

Ця вставка надає повну аналітичну специфікацію файлів керування підсистеми cgroups v2 memory. Вона необхідна розробникам системного програмного забезпечення, адміністраторам високонавантажених серверних комплексів та авторам контейнерних оркестраторів, яким потрібен детальний опис контрактів читання, запису, типів даних та очікуваних значень для кожного псевдофайлу у віртуальній файловій системі `cgroupfs` (зазвичай змонтованій у шляху `/sys/fs/cgroup`).

У cgroups v2 всі файли підсистеми пам'яті розташовані безпосередньо в каталозі відповідної cgroup. Керування доступністю контролера здійснюється рекурсивно через запис рядочка `+memory` у файл `cgroup.subtree_control` батьківського вузла. Доки контролер не активовано у батьківському каталозі, створення файлів пам'яті у дочірніх каталогах не відбувається, що забезпечує чітку ієрархічну дисципліну ресурсів.

## 1. Основні файли лімітів та гарантій RAM

Усі числові значення обсягу пам'яті у файлах cgroups v2 приймаються та повертаються у байтах. При записі у файли дозволяється використовувати стандартні суфікси згрупованого обсягу: `K` (кілобайти), `M` (мегабайти), `G` (гігабайти), `T` (терабайти). При зчитанні файл завжди повертає точний обсяг у байтах у вигляді десяткового цілого числа або спеціального рядка `"max"`, який символізує відсутність будь-якого обмеження (нескінченну межу).

Таблиця нижче підсумовує ключові файли керування оперативною пам'яттю:

| Файл | Режим | Опис та семантика ядра |
| :--- | :--- | :--- |
| `memory.current` | RO | Поточний загальний обсяг RAM, виділений групі та її дочірнім вузлам (анонімна пам'ять, page cache, kernel memory, socket buffers). |
| `memory.min` | RW | Тверда гарантія пам'яті. Витіснення (reclaim) ніколи не забирає пам'ять нижче цього рівня. При глобальному OOM сторінки групи захищені. |
| `memory.low` | RW | М'яка гарантія (best-effort). При витісненні ядро намагається не зачіпати пам'ять групи, якщо інші cgroups перевищують свої `memory.low`. |
| `memory.high` | RW | М'яке обмеження. При перевищенні ядро активує асинхронне витіснення та впроваджує штрафні затримки (throttling) для процесів групи. |
| `memory.max` | RW | Жорсткий ліміт. Перевищення запускає примусовий direct reclaim. Якщо пам'ять не звільнено — викликається cgroup OOM Killer. |
| `memory.peak` | RO/RW | Історичний максимум (High Watermark) споживання `memory.current`. Запис `"reset"` або поточного значення скидає лічильник (Linux 6.3+). |
| `memory.reclaim` | WO | Примусове витіснення пам'яті з простору користувача (Linux 5.19+). Запис обсягу (наприклад `echo 50M > memory.reclaim`) змушує ядро звільнити вказану кількість сторінок. |

Зчитування файлів лімітів виконується неблокуючим чином. Якщо записане значення перевищує фізичний обсяг пам'яті вузла чи наявні ліміти батьківських cgroups, ядро приймає запис без помилок, але ефективним обмеженням стає найсуворіша межа вздовж усього ланцюга від кореня до поточного вузла.

### Специфікація файлів лімітів

#### memory.current
- **Синтаксис зчитання:** Десяткове ціле число у байтах (наприклад, `104857600`).
- **Семантика:** Повертає суму всіх фізичних сторінок, розраховану підсистемою `rstat`. Включає анонімні сторінки, файловий кеш, пам'ять ядра (`slab`, `kernel_stack`, `pagetables`) та буфери сокетів.
- **Особливості:** Не можна модифікувати. Запис повертає помилку `EACCES` або `EROFS`.

#### memory.min
- **Синтаксис запису:** Ціле число або суфікси (`100M`, `2G`, `max`).
- **Синтаксис зчитання:** Десяткове ціле число або `0`.
- **Семантика:** Твердий захист від витіснення. Якщо споживання менше або дорівнює `memory.min`, підсистема reclaim ігнорує дану cgroup.
- **Коди помилок:** `EINVAL` при невідомому синтаксисі запису або від'ємному значенні.

#### memory.low
- **Синтаксис запису:** Ціле число або суфікси (`500M`, `4G`, `max`).
- **Синтаксис зчитання:** Десяткове ціле число або `0`.
- **Семантика:** М'який захист від витіснення. Сторінки скануються зі зниженим пріоритетом пропорційно до перевищення `(current - low) / current`.

#### memory.high
- **Синтаксис запису:** Ціле число або суфікси (`1G`, `max`).
- **Синтаксис зчитання:** Десяткове ціле число або `max`.
- **Семантика:** Робоча межа. Перевищення вмикає примусову затримку (throttling) потоків у `mem_cgroup_handle_over_high()`.

#### memory.max
- **Синтаксис запису:** Ціле число або суфікси (`2G`, `max`).
- **Синтаксис зчитання:** Десяткове ціле число або `max`.
- **Семантика:** Абсолютна стеля. При досягненні викликається синхронний direct reclaim, а при його неуспішності — cgroup OOM Killer.

#### memory.peak
- **Синтаксис зчитання:** Десяткове ціле число у байтах.
- **Синтаксис запису:** Рядок `"reset"` (у ядрах 6.3+).
- **Семантика:** Зчитування повертає High Watermark споживання RAM. Запис `"reset"` скидає значення до поточного `memory.current`.

#### memory.reclaim
- **Синтаксис запису:** Рядок обсягу пам'яті (наприклад `echo 100M > memory.reclaim`).
- **Синтаксис зчитання:** Заборонено. Запис у файл викликає негайне примусове витіснення сторінок з RAM.
- **Коди помилок:** `EAGAIN`, якщо ядро не змогло звільнити вказаний обсяг у межах доступних неактивних сторінок.

## 2. Файли керування простором підкачки (Swap)

Контроль простору підкачки доступний за умови, якщо ядро Linux зібрано з підтримкою конфігурації `CONFIG_MEMCG_SWAP` і в системі ввімкнено хоча б один пристрій підкачки (swap partition, swap file, або zswap/zram).

| Файл | Режим | Опис та семантика ядра |
| :--- | :--- | :--- |
| `memory.swap.current` | RO | Поточний обсяг анонімних сторінок цієї групи, скинутих у простір підкачки (swap або zswap/zram). |
| `memory.swap.high` | RW | М'який ліміт swap. При перевищенні сповільнюються процеси, що намагаються скидати пам'ять на диск, запобігаючи swap thrashing. |
| `memory.swap.max` | RW | Жорсткий ліміт swap. Значення `0` повністю забороняє використання swap даною групою. |
| `memory.swap.peak` | RO/RW | Пікове історичне значення використання swap цієї cgroup з моменту створення або останнього скидання (Linux 6.5+). |

Значення за замовчуванням для `memory.swap.max` виставляється як `"max"`. Якщо сервісу потрібно категорично заборонити скидання анонімних сторінок на диск (наприклад, для забезпечення захисту конфіденційних ключів шифрування у RAM від витоку на накопичувач), у файл `memory.swap.max` записується числовий нуль (`0`).

#### memory.swap.current
- **Синтаксис зчитання:** Десяткове ціле число у байтах.
- **Семантика:** Відображає кількість анонімних сторінок даної cgroup, які знаходяться у swap-просторі або у стисненому пулі Zswap.

#### memory.swap.high
- **Синтаксис запису:** Ціле число або суфікси (`100M`, `max`).
- **Семантика:** М'який ліміт swap. При перевищенні ядро активує затримки потоків витіснення `mem_cgroup_handle_over_swap_high()`, захищаючи накопичувач від I/O перенавантаження.

#### memory.swap.max
- **Синтаксис запису:** Ціле число або `0` чи `max`.
- **Семантика:** Жорсткий ліміт. Значення `0` забороняє свопінг для даної cgroup.

#### memory.swap.peak
- **Синтаксис зчитання:** Десяткове ціле число у байтах.
- **Синтаксис запису:** Рядок `"reset"` (у ядрах 6.5+).

## 3. Файли подій та сповіщень OOM

Файли подій надають механізм сповіщення про виникнення критичних умов виділення пам'яті. Зчитування файлу повертає поточні значення лічильників, а реєстрація файлового дескриптора у системному виклику `epoll()` або `select()` дозволяє отримувати асинхронні сповіщення без циклічного опитування.

| Файл | Режим | Опис та семантика ядра |
| :--- | :--- | :--- |
| `memory.events` | RO | Лічильники подій для групи та її піддерева. Підтримує сповіщення через `poll()` / `epoll()`. |
| `memory.events.local` | RO | Лічильники подій виключно для даного cgroup-вузла (без урахування дочірніх груп). |
| `memory.oom.group` | RW | Прапорець атомного OOM (`0` або `1`). При `1` OOM Killer вбиває всі процеси у cgroup та її підгрупах як єдине ціле. |

### Формат вмісту memory.events

Файл `memory.events` форматується як набір ключів та значень, розділених пробілами та символами нового рядка:

```
low 12
high 1450
max 3
oom 1
oom_kill 1
oom_group_kill 1
```

Семантика кожного лічильника описується так:
- **`low`**: Загальна кількість разів, коли ядро змушене було витісняти пам'ять із даної cgroup через те, що сусідні cgroups не могли задовольнити свої потреби у межах `memory.low`.
- **`high`**: Кількість випадків, коли споживання групи перевищило м'яку межу `memory.high`, внаслідок чого потік виконання зазнав примусової затримки (throttling).
- **`max`**: Лічильник спроб виділення пам'яті, які зазнали невдачі та змусили ядро увійти у режим прямого витіснення (direct reclaim) через досягнення стелі `memory.max`.
- **`oom`**: Кількість ініціалізацій процедури OOM Killer для цієї cgroup.
- **`oom_kill`**: Кількість фактів надсилання сигналу `SIGKILL` конкретним процесам за рішенням OOM Killer.
- **`oom_group_kill`**: Кількість подій, коли спрацювала атомна ліквідація всієї ієрархії cgroup завдяки увімкненому прапорцю `memory.oom.group=1`.

## 4. Детальна статистика споживання memory.stat

Файл `memory.stat` надає найповніше розбиття використання пам'яті підсистемою `rstat`. Зчитування файлу повертає текстові пари `ключ значення`, виражені у байтах або штуках сторінок.

Ключові метрики підсистеми пам'яті у `memory.stat`:

- **`anon`**: Обсяг оперативної пам'яті, зайнятий анонімними сторінками (динамічна купа `brk`/`sbrk`, аллокації `malloc`, стек процесів, анонімні ділянки `mmap`).
- **`file`**: Загальний обсяг дискового кешу сторінок (page cache), включаючи відображені через `mmap()` файли та файлові буфери.
- **`kernel`**: Сумарна пам'ять ядра, виділена для підтримки функціонування процесів даної cgroup.
- **`kernel_stack`**: Обсяг пам'яті, витрачений на виділення внутрішніх стеків викликів потоків виконання у просторі ядра.
- **`pagetables`**: Пам'ять, виділена під таблиці сторінок (Page Tables) архітектури MMU для процесів цієї групи.
- **`sec_pagetables`**: Пам'ять під вторинні таблиці сторінок у середовищах віртуалізації (EPT/NPT для KVM).
- **`percpu`**: Обсяг пам'яті ядра, виділений у пер-процесорних масивах (`alloc_percpu`) для потреб cgroup.
- **`sock`**: Мережеві буфери сокетів TCP, UDP та UNIX domain sockets, прив'язані до процесів групи.
- **`slab`**: Пам'ять підсистеми аллокаторів ядра SLAB/SLUB, яка додатково поділяється на `slab_reclaimable` (структури dentry, inode cache) та `slab_unreclaimable` (незвільнювані внутрішні структури ядра).
- **`file_mapped`**: Обсяг файлового кешу, який безпосередньо відображено у віртуальний простір адрес процесів через `mmap()`.
- **`file_dirty`**: Обсяг модифікованих сторінок файлового кешу ("брудні" сторінки), які чекають фонового скидання на диск підсистемою `flusher`.
- **`file_writeback`**: Обсяг сторінок, які наразі перебувають у стані фізичного запису на накопичувач.
- **`swapcached`**: Анонімні сторінки, які витіснені у swap, але одночасно зберігаються у RAM для прискорення повторного доступу.
- **`workingset_refault_anon` / `workingset_refault_file`**: Лічильники подій, коли витіснена сторінка знову запитується процесом незабаром після вилучення. Висока швидкість зростання цих показників свідчить про наявність важкого профілю дефіциту пам'яті (working set thrashing).

## 5. Порівняльна специфікація Cgroups v1 vs Cgroups v2

Для полегшення міграції існуючих систем у таблиці нижче наведено пряму відповідність імен файлів та концепцій між першою та другою версіями контролера пам'яті:

| Cgroups v1 (застарілий) | Cgroups v2 (сучасний) | Зміни у семантиці |
| :--- | :--- | :--- |
| `memory.usage_in_bytes` | `memory.current` | У v2 включає пам'ять ядра (`kernel`) за замовчуванням. |
| `memory.limit_in_bytes` | `memory.max` | Змінено ім'я; `max` замінив числове значення `-1`. |
| `memory.soft_limit_in_bytes` | `memory.high` | У v1 soft_limit діяв лише при загальному дефіциті; у v2 `high` вмикає локальний throttling. |
| `memory.memsw.limit_in_bytes` | `memory.swap.max` | У v1 ліміт задавав суму (RAM + Swap); у v2 `swap.max` регулює виключно обсяг swap. |
| `memory.max_usage_in_bytes` | `memory.peak` | У v2 додано можливість скидання вотермарки через `echo reset > memory.peak`. |
| `memory.kmem.limit_in_bytes` | *відсутній* | Пам'ять ядра у v2 інтегрована в загальний лічильник `memory.max` без окремих лімітів. |
| `memory.use_hierarchy` | *відсутній* | Ієрархічний облік у v2 є обов'язковим та єдиним режимом функціонування. |

## 6. Взаємодія з глобальними параметорами sysctl

Файли контролера пам'яті cgroups v2 працюють поверх глобальних налаштувань підсистеми віртуальної пам'яті ядра Linux, заданих через системні параметри `sysctl`:

- **`vm.swappiness`**: Визначає відносну схильність ядра до витіснення анонімної пам'яті у порівнянні з файловим кешем. Значення варіюється від 0 (агресивне утримання анонімних сторінок) до 200 (рівноцінне витіснення). Налаштування cgroups v2 `memory.swap.high` та `memory.swap.max` накладаються поверх глобального значення `vm.swappiness`.
- **`vm.dirty_background_ratio` / `vm.dirty_ratio`**: Задають відсоток RAM, при досягненні якого брудні сторінки починають скидатися на диск фоново або синхронно. У cgroups v2 підсистема `cgroup writeback` пропорційно розподіляє брудні сторінки між cgroups, запобігаючи ситуації, коли одна cgroup заповнює весь глобальний буфер `dirty_ratio`.

## 7. Права доступу, безпека та делегування cgroupfs

Файли керування у cgroupfs створюються ядром із правами доступу за замовчуванням `0644` (власник `root:root`). У системних середовищах із безпривілейованими контейнерами або користувацькими службами systemd (`systemd --user`) доступ до модифікації лімітів регулюється механізмом cgroup delegation.

Для безпечного делегування керування піддеревом cgroup невідомому користувачеві системний демон виконує такі операції:
1. Змінює власника каталогу cgroup та файлів `cgroup.procs` і `cgroup.threads` на відповідного UID/GID користувача (`chown user:user`).
2. Передає право запису у файли `cgroup.subtree_control` для активації додаткових контролерів у дочірніх cgroups.
3. Обмеження пам'яті `memory.max` та `memory.high` у батьківському каталозі залишаються під контролем суперкористувача, унеможливлюючи вихід безпривілейованого процесу за межі виділеної йому системної квоти.

Детальна поверхня керування cgroups v2 memory слугує низькорівневим фундаментом, на якому базується вся сучасна система контролю ресурсів у дистрибутивах Linux.
