# Управління піками та пропускною здатністю у Cgroups v2 memory

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У сучасних операційних системах сімейства Linux управління ресурсами є одним з найважливіших завдань для забезпечення стабільної та передбачуваної роботи системи. Серед усіх ресурсів оперативна пам'ять (RAM) є найбільш критичною, оскільки її нестача може призвести до катастрофічних наслідків, таких як зависання системи або примусове завершення важливих процесів механізмом OOM (Out-Of-Memory) Killer. 

Cgroups (Control Groups) версії 2 є сучасним механізмом ядра Linux для ієрархічного управління ресурсами. На відміну від cgroups v1, де кожен ресурс мав власну незалежну ієрархію, cgroups v2 запроваджує єдину уніфіковану ієрархію, що значно спрощує адміністрування та вирішує багато концептуальних проблем попередньої версії.

Контролер пам'яті (memory controller) у cgroups v2 надає багатий інструментарій для обмеження, гарантування та моніторингу використання пам'яті групами процесів. У цій статті ми детально розглянемо механізми управління пам'яттю, фокусуючись на лімітах, відстеженні пікового споживання та управлінні простором підкачки (swap).

## 1. Архітектура контролера пам'яті в Cgroups v2

У cgroups v2 контролер пам'яті активується шляхом запису `+memory` у файл `cgroup.subtree_control` батьківської групи. Це дозволяє дочірнім групам використовувати контролер пам'яті та встановлювати власні обмеження.

Основна концепція управління пам'яттю базується на розподілі доступної пам'яті між різними cgroups. Кожна група може мати власні ліміти та гарантії, що дозволяє створювати складні ієрархії розподілу ресурсів. Наприклад, ви можете виділити гарантований мінімум пам'яті для критичних системних сервісів, одночасно обмеживши максимальне споживання пам'яті для фонових завдань.

Пам'ять, яка обліковується контролером, включає:
- Анонімну пам'ять (anonymous memory) - пам'ять, що виділяється процесами (heap, stack).
- Файловий кеш (page cache) - пам'ять, яка використовується для кешування файлів на диску.
- Мережеві буфери (socket buffers).
- Структури даних ядра (kernel memory), специфічні для процесів групи.

## 2. Гарантії та ліміти: memory.min, memory.low, memory.high, memory.max

Cgroups v2 пропонує чотири основні параметри для управління кількістю пам'яті, доступної для групи. Ці параметри дозволяють реалізувати як жорсткі, так і м'які обмеження, а також надати гарантії.

### 2.1 memory.min (Жорстка гарантія)

`memory.min` встановлює жорстку гарантію на мінімальний обсяг пам'яті для групи. Якщо споживання пам'яті групою падає нижче цього значення, ядро ніколи не буде звільняти пам'ять цієї групи (reclaim) під час глобальної нестачі пам'яті, навіть якщо це призведе до OOM у системі загалом.

Цей параметр використовується для захисту критично важливих процесів, які повинні мати гарантований доступ до пам'яті за будь-яких умов. Однак слід бути обережним: сума значень `memory.min` для всіх груп не повинна перевищувати загальний обсяг фізичної пам'яті, інакше гарантії не зможуть бути виконані, і система стане нестабільною.

### 2.2 memory.low (М'яка гарантія)

`memory.low` діє як м'яка гарантія (best-effort). Коли система стикається з нестачею пам'яті, вона намагатиметься не звільняти пам'ять з груп, чиє споживання нижче `memory.low`, віддаючи перевагу групам, чиє споживання перевищує цей ліміт.

Однак, на відміну від `memory.min`, якщо ядро не зможе звільнити достатньо пам'яті з інших джерел, воно може почати звільняти пам'ять з груп, захищених `memory.low`. Це робить `memory.low` ідеальним для процесів, яким бажано надати пріоритет у доступі до пам'яті, але які не є абсолютно критичними для виживання системи. 

Ефективне використання `memory.low` вимагає розуміння поведінки page cache. Якщо процес активно використовує кеш файлів, `memory.low` допоможе запобігти витісненню цього кешу, що може значно покращити продуктивність.

### 2.3 memory.high (М'який ліміт)

`memory.high` встановлює м'який ліміт на споживання пам'яті. Коли група досягає цього значення, ядро починає агресивно звільняти пам'ять з цієї групи (throttling), намагаючись утримати споживання нижче встановленого рівня. 

Важлива особливість `memory.high` полягає в тому, що перевищення цього ліміту не призводить до негайного виклику OOM Killer. Натомість процеси в групі починають відчувати значне сповільнення через те, що ядро витрачає більше часу на звільнення сторінок пам'яті, ніж на виконання корисного навантаження. Це створює сильний зворотний тиск (backpressure), який змушує процеси сповільнити своє виконання і, відповідно, зменшити швидкість виділення пам'яті.

Цей параметр корисний для завдань, які можуть обробляти дані повільніше у випадку нестачі ресурсів, не вимагаючи примусового завершення.

### 2.4 memory.max (Жорсткий ліміт)

`memory.max` - це жорсткий ліміт, який група ніколи не може перевищити. Якщо споживання пам'яті досягає `memory.max` і ядро не може негайно звільнити сторінки (наприклад, через відсутність доступних для витіснення сторінок або через те, що вся пам'ять є анонімною і swap недоступний або переповнений), спрацьовує cgroup OOM Killer.

Використання `memory.max` є класичним способом ізоляції процесів (наприклад, у контейнерах), гарантуючи, що жодна група не зможе спожити більше пам'яті, ніж їй виділено, і тим самим вплинути на інші групи або ядро.

## 3. Відстеження пікового споживання: memory.peak

Оптимізація використання ресурсів вимагає точного розуміння того, скільки пам'яті насправді потребує робоче навантаження. Параметр `memory.current` показує поточне споживання, але для завдань з нестабільним профілем пам'яті (наприклад, java-застосунки або процеси, що мають періодичні сплески активності) поточного значення недостатньо.

Тут на допомогу приходить файл `memory.peak`. Він записує історичний максимум споживання пам'яті з моменту створення cgroup. Це значення ніколи не зменшується автоматично; воно зростає, коли `memory.current` досягає нового максимуму.

### Використання memory.peak для оптимізації (Rightsizing)

1. **Моніторинг:** Запустіть завдання з великим (або необмеженим) `memory.max`. Дочекайтеся завершення повного циклу роботи (наприклад, добу для веб-сервера, або повне виконання batch-завдання).
2. **Збір даних:** Зчитайте значення `memory.peak`.
3. **Аналіз:** Отримане значення є реальним максимумом. Додайте до нього невеликий запас (margin) і встановіть як нове значення `memory.max`. Це дозволить звільнити невикористану пам'ять для інших процесів, покращуючи загальну утилізацію кластера.
4. **Скидання:** У деяких версіях ядра ви можете скинути (reset) `memory.peak`, записавши в нього "max" або поточне значення `memory.current`, щоб почати вимірювання заново для нового інтервалу.

Відстеження `memory.peak` є критично важливим для контейнерних оркестраторів, таких як Kubernetes, для коректного налаштування requests/limits.

## 4. Управління простором підкачки (Swap): memory.swap.high та memory.swap.max

У середовищах, де увімкнено swap, контролер пам'яті cgroups v2 надає додаткові механізми для управління його використанням. Включення swap дозволяє витісняти анонімні сторінки з оперативної пам'яті на диск, що збільшує загальну ємність пам'яті системи, але за рахунок значного падіння продуктивності при активному використанні.

### 4.1 memory.swap.current
Цей файл показує обсяг swap, який наразі використовується цією групою.

### 4.2 memory.swap.max
Цей параметр встановлює жорсткий ліміт на обсяг swap, доступний для групи. Якщо група досягає свого `memory.max` і намагається виділити ще пам'ять, ядро почне витісняти сторінки у swap. Якщо споживання swap також досягає `memory.swap.max`, спрацює OOM Killer.

Значення `0` повністю відключає використання swap для групи, змушуючи її жити виключно в межах `memory.max` (або загального обсягу RAM, якщо `memory.max` не встановлено).

### 4.3 memory.swap.high
Аналогічно до `memory.high`, це м'який ліміт для swap. Коли використання swap досягає цього значення, процеси в групі починають піддаватися throttling'у. Це корисно для запобігання надмірному "свопінгу", який може призвести до високого навантаження на диск (I/O) і сповільнення всієї системи (явище thrashing).

## 5. Взаємодія з OOM Killer у Cgroups v2

OOM (Out-Of-Memory) Killer - це механізм ядра, який активується, коли система або конкретна cgroup вичерпує ліміти пам'яті. У cgroups v2 поведінка OOM Killer стала більш передбачуваною та керованою.

### 5.1 Коли спрацьовує OOM Killer
У контексті cgroup v2, OOM Killer викликається за таких умов:
- Споживання пам'яті досягає `memory.max`, і ядро не може звільнити сторінки (ні кеш, ні анонімні сторінки, якщо `memory.swap.max` досягнуто або swap відключений/відсутній).
- Сталася глобальна нестача пам'яті в системі, і дана cgroup була обрана жертвою.

### 5.2 Моніторинг OOM-подій (memory.events)
Файл `memory.events` є важливим інструментом для моніторингу стану групи. Він містить лічильники для різних подій:
- `low`: кількість разів, коли пам'ять звільнялася через перевищення `memory.low`.
- `high`: кількість разів, коли застосовувався throttling через перевищення `memory.high`.
- `max`: кількість разів, коли виділення пам'яті зазнало невдачі через `memory.max`.
- `oom`: кількість разів, коли межа пам'яті була досягнута, і це призвело до необхідності вбити процес (але сам процес ще міг не бути вбитий).
- `oom_kill`: кількість фактично вбитих процесів OOM Killer-ом у цій групі.

Відстеження `oom_kill` є основним способом дізнатися, що ваші процеси були примусово завершені через нестачу пам'яті.

### 5.3 memory.oom.group
Cgroups v2 вводить новий параметр `memory.oom.group`. Якщо записати `1` у цей файл, то у випадку, коли всередині цієї групи спрацьовує OOM, ядро вб'є *всі* процеси в цій групі (та її підгрупах), а не лише один процес-порушник.
Це вкрай корисно для багатопроцесних архітектур (наприклад, PostgreSQL або PHP-FPM), де вбивство лише одного процесу може залишити застосунок у неробочому або узгодженому стані. Вбиваючи всю групу, оркестратор (наприклад, systemd) може перезапустити весь сервіс цілком, відновлюючи стабільну роботу.

## 6. Взаємодія з systemd

В сучасних дистрибутивах Linux налаштування cgroups зазвичай здійснюється через systemd. Unit-файли надають директиви для управління пам'яттю, які прямо мапляться на параметри cgroups v2:

- `MemoryMin=` -> `memory.min`
- `MemoryLow=` -> `memory.low`
- `MemoryHigh=` -> `memory.high`
- `MemoryMax=` -> `memory.max`
- `MemorySwapMax=` -> `memory.swap.max`

Наприклад, конфігурація сервісу:
```ini
[Service]
MemoryMax=1G
MemoryHigh=800M
MemorySwapMax=0
```
Цей конфіг забороняє сервісу використовувати swap, обмежує споживання пам'яті 1 ГБ, і починає уповільнювати сервіс, якщо він перетинає позначку 800 МБ.

## 7. Тюнінг для різних навантажень

Різні типи застосунків вимагають різних підходів до налаштування лімітів пам'яті.

**Бази даних (PostgreSQL, MySQL):**
- Зазвичай вимагають багато page cache і великих buffer pools.
- Встановіть `memory.low`, щоб захистити кеш від витіснення іншими сервісами.
- Використовуйте `memory.oom.group=1`, щоб уникнути пошкодження структур даних, якщо OOM Killer вб'є один робочий процес.

**Веб-сервери та мікросервіси:**
- Використовуйте `memory.high` разом з `memory.max`. М'який ліміт дозволить системі сповільнити процес під час сплеску трафіку, даючи йому шанс звільнити пам'ять (наприклад, завершивши обробку запитів), уникнувши примусового рестарту.

**Фонові завдання (Batch jobs):**
- Встановіть жорсткі ліміти `memory.max` і забороніть або сильно обмежте swap, оскільки такі завдання зазвичай повинні виконуватися швидко або впасти з помилкою, а не "зависати" у свопі, сповільнюючи всю систему.

## Висновок

Cgroups v2 надає гнучку і потужну модель для управління пам'яттю в Linux. Використання багатошарової системи лімітів (`memory.min`, `low`, `high`, `max`) дозволяє адміністраторам тонко налаштовувати поведінку системи як у звичайному режимі, так і під час критичної нестачі ресурсів. Розуміння механізмів відстеження піків (`memory.peak`) та коректне управління swap є ключовими для побудови ефективних, стабільних і щільно упакованих серверних інфраструктур.
