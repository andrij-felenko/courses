Взаємодія декількох вимогливих служб на одному хості Linux без обмеження пам'яті неминуче призводить до розрастання файлового кешу або витоку пам'яті в одному з процесів, що спричиняє хаотичне спрацьовування OOM Killer і зупинку всієї системи. Традиційні ліміти `rlimit` (зокрема `RLIMIT_AS` та `RLIMIT_DATA`) оперують лише віртуальним простором адрес окремого процесу й не здатні ізолювати анонімну пам'ять чи дисковий кеш групи процесів. Контролер `memory` в cgroups v2 вирішує цю проблему, запроваджуючи чотирирівневу систему захисту та обмеження RAM, управління простором підкачки (swap), а також інструменти вимірювання пікового споживання й зворотного тиску (backpressure).

## 1. Архітектура підсистеми пам'яті ядра та лінивий облік rstat

Контролер пам'яті в cgroups v2 інтегрований безпосередньо у підсистему підрахунку, розподілу та витіснення сторінок ядра Linux (`mm/memcontrol.c`). Кожен об'єкт cgroup у ядрі описується внутрішньою структурою `struct mem_cgroup`. На відміну від першої версії cgroups, де керування пам'яттю ядра (kmalloc, slab) та анонімною пам'яттю відбувалося через окремі незалежні лічильники, у cgroups v2 вся пам'ять групи обліковується уніфіковано в межах єдиної ієрархії.

Під облік контролера потрапляють чотири основні категорії пам'яті:

1. **Анонімна пам'ять (anonymous memory):** сторінки динамічної кучі (heap), стека процесів, а також анонімні відображення `mmap(MAP_ANONYMOUS)`. Ці сторінки не мають прив'язки до файлів на диску і у випадку витіснення вимагають наявності пристрою підкачки (swap).
2. **Файловий кеш (page cache):** сторінки дискових файлів, прочитані або підготовлені до запису через системні виклики `read()`, `write()` або відображені у простір пам'яті через `mmap()`. Файловий кеш ділиться на чисті (clean) та брудні (dirty) сторінки.
3. **Пам'ять ядра (kernel memory):** структури даних ядра, виділені для забезпечення діяльності процесів групи. Сюди входять внутрішні стеки ниток у ядрі (`kernel_stack`), таблиці сторінок віртуальної пам'яті (`pagetables`), буфери мережевих сокетів (`sock`), а також аллокації підсистеми `slab/slub`.
4. **Простір підкачки (swap):** анонімні сторінки, витіснені з оперативної пам'яті на дисковий пристрій підкачки або у стиснений RAM-буфер підсистеми Zswap/Zram.

### Механізм заряджання сторінок (Charging Flow) та списки LRU

При кожній спробі виділення нової фізичної сторінки (наприклад, при обробці сторінкового збою page fault або при читанні файла у кеш) ядро викликає внутрішню функцію `mem_cgroup_charge()`. Цей процес відбувається у кілька етапів:

1. **Пакетне виділення з per-CPU stock:** Щоб не звертатися до блокувань структури `struct mem_cgroup` при кожній сторінці 4 КБ, ядро виділяє пам'ять пакетами по 32 сторінки (128 КБ) у локальний для даного CPU масив `memcg_stock_pcp`. Якщо локальний запас містить вільні одиниці, облік відбувається миттєво без жодного зв'язку з іншими ядрами.
2. **Поповнення запасу (try_charge):** Якщо локальний запас вичерпано, потік виконує функцію `try_charge()`, яка перевіряє ліміти `memory.max` та `memory.high` вздовж усієї ієрархії від поточного cgroup-вузла до кореня.
3. **Облік у LRU-списках:** Після успішного заряджання сторінка прив'язується до векторів `lruvec` даної cgroup, де вона класифікується за ступенем активності використання між п'ятьма основними списками LRU (Least Recently Used):
   - `LRU_INACTIVE_ANON`: неактивні анонімні сторінки (перші кандидати на swap);
   - `LRU_ACTIVE_ANON`: активно використовувані анонімні сторінки;
   - `LRU_INACTIVE_FILE`: неактивний файловий кеш (перші кандидати на скидання);
   - `LRU_ACTIVE_FILE`: активно використовуваний файловий кеш;
   - `LRU_UNEVICTABLE`: заблоковані сторінки (`mlock()`), вилучені з витіснення.

При звільненні сторінки або знищенні процесу викликається `mem_cgroup_uncharge()`, яка повертає одиниці обліку у локальний запас `percpu_stock`.

### Визначення повторних завантажень (Refault Detection)

Коли ядро витісняє сторінку з RAM, воно залишає у таблиці сторінок або файловому кеші так звану "тіньову" структуру (shadow entry). Якщо процес знову звертається до цієї сторінки незабаром після вилучення, ядро обчислює інтервал між вилученням та повторним зверненням (refault distance). Якщо цей інтервал менший за розмір активного робочого набору (working set), ядро фіксує події `workingset_refault_anon` або `workingset_refault_file` у `memory.stat` і негайно переміщує завантажену сторінку в активний список LRU, захищаючи її від повторного швидкого витіснення.

### Лінивий облік через rstat (per-CPU counters)

У сучасних багатоядерних системах з сотнями потоків виконання централізоване атомарне оновлення єдиного лічильника пам'яті в кореневі й проміжних cgroups спричиняло б важкий кеш-конфлікт (cacheline bouncing). Кожна операція `alloc_pages()` або `free_pages()` змушена була б блокувати кеш-лінію шини пам'яті між процесорами, руйнуючи масштабованість.

Щоб усунути цю перешкоду, ядро використовує підсистему `rstat` (read-side stat):

```
Процесор 0 (CPU 0)  --->  Per-CPU delta counter (без блокувань)
Процесор 1 (CPU 1)  --->  Per-CPU delta counter (без блокувань)
                                   |
                                   v  (ліниве зведення при читанні / тиску)
                        rstat_flush() -> struct mem_cgroup (глобальний підсумок)
```

При кожній зміні стану сторінки потік ядра оновлює локальний для даного CPU лічильник у масиві `percpu_charge`. Зведення локальних відхилень у глобальне дерево `struct mem_cgroup` відбувається ліниво (lazy aggregation) — лише тоді, коли процес простору користувача зчитує файл `memory.stat` або коли ядро приймає рішення про досягнення межі витіснення (reclaim boundary). Завдяки цьому плата за облік покладається на спостерігача, а не на робочий потік виділення пам'яті.

## 2. Гарантії та обмеження RAM: математика чотирьох позначок

Управління оперативною пам'яттю в cgroups v2 описується чотирма основними показниками, які формують ієрархічний діапазон дій ядра під час виділення та витіснення сторінок.

![Обмеження, гарантії та піки споживання пам'яті у Cgroups v2](/reference/unix-linux/processes/cgroup-v2-memory-peak-swap/img/cgroup-memory-limits.svg)
*Схема межових рівнів memory.min, memory.low, memory.high, memory.max та відстеження піка memory.peak у Cgroups v2*

### 2.1 memory.min (Тверда гарантія)

`memory.min` визначає абсолютний мінімальний обсяг RAM, який ядро за жодних умов не має права витісняти (reclaim) з цієї групи. Якщо поточне споживання cgroup падає нижче `memory.min`, сторінки цієї групи повністю виключаються зі списків кандидатів підсистеми `kswapd` та прямого витіснення (direct reclaim).

Якщо в системі виникає глобальний брак пам'яті, ядро скоріше викличе OOM Killer у незахищеній cgroup, ніж забере хоча б одну сторінку з групи, захищеної `memory.min`.

> 🔧 **Навіщо це.** `memory.min` використовується для захисту системно критичних демонів (таких як `systemd-journald`, `sshd` або контролер контейнерного рантайму), чия зупинка або затримка через витіснення кешу чи свопінг призведе до втрати керованості всією ОС.

При ієрархічному вкладенні дочірні групи ділять захищене значення батьківської групи пропорційно до власних налаштувань `memory.min`. Формула рекурсивного захисту `effective_min` для дочірньої групи `i` має вигляд:

```
effective_min[i] = min( memory.min[i], 
                        parent.effective_min * (memory.min[i] / sum(children.memory.min)) )
```

Наприклад, якщо батьківська cgroup має `effective_min = 10G`, а дві дочірні cgroup A та B мають `memory.min = 6G` кожна (сума 12 ГБ), то ефективний захист кожної з дочірніх cgroup буде розраховано як:

```
effective_min[A] = min( 6G, 10G * (6G / 12G) ) = 5G
```

Це унеможливлює ситуацію, коли дочірня група затребує більше захисту, ніж гарантовано її батьківському вузлу.

### 2.2 memory.low (М'яка гарантія та Best-Effort захист)

`memory.low` працює як м'яка гарантія. Якщо загальне споживання пам'яті групою `E` менше за встановлене значення `L` (`E <= L`), ядро утримується від витіснення її сторінок під час штатного тиску на пам'ять. Однак, якщо в системі не залишається інших незахищених джерел пам'яті, ядро може пропорційно забрати частину пам'яті з груп, захищених `memory.low`.

Математика витіснення при перевищенні `memory.low` базується на розрахунку коефіцієнта пропорційного тиску. Якщо група споживає `E` байтів при гарантії `L` (де `E > L`), частка пам'яті `P`, доступна для підсистеми reclaim, становить:

```
P = (E - L) / E
```

Якщо група споживає 4 ГБ при `memory.low = 3G`, то під витіснення потрапляє лише частка:

```
P = (4 - 3) / 4 = 0.25  (тобто лише 25% від її сторінок розглядаються як кандидати)
```

Завдяки цьому ядро сканує сторінки захищеної cgroup зі зниженою інтенсивністю, віддаючи перевагу витісненню ресурсів з тих cgroups, які взагалі не мають встановленого захисту або значно перевищують свої нормативні межі. Це дозволяє уникнути різкого "вибивання" дискового кешу баз даних чи веб-серверів під час короткочасних сплесків активності у сусідніх cgroups.

### 2.3 memory.high (М'яке обмеження та механізм затримок Throttling)

`memory.high` встановлює робочу межу споживання пам'яті. На відміну від жорсткого ліміту, перетин `memory.high` не викликає OOM Killer і не вбиває процеси. Натомість ядро активує асинхронне витіснення та застосовує **механізм зворотного тиску (backpressure throttling)**.

![Послідовність обробки memory.high та memory.max у ядрі](/reference/unix-linux/processes/cgroup-v2-memory-peak-swap/img/cgroup-throttling-flow.svg)
*Алгоритм обробки запитів пам'яті, асинхронного витіснення та виклику cgroup OOM Killer*

Коли потік виконання перетинає позначку `memory.high`, ядро примусово викликає функцію `mem_cgroup_handle_over_high()`. Цей механізм розраховує штрафний інтервал сну (penalty sleep) перед поверненням потоку з системного виклику назад у простір користувача.

Розрахунок затримки у ядрі базується на ступені перевищення ліміту:

```
overage = memory.current - memory.high
penalty_jiffies = (overage / memory.high) * BASE_PENALTY
```

Потік присипляється у функції `schedule_timeout_killable()`, де максимальна одноразова затримка обмежена значенням 2 секунди. Внаслідок цього процес, який активно виділяє пам'ять (наприклад, через `malloc()`), починає пропорційно сповільнюватися. Це знижує швидкість генерації нових запитів на виділення сторінок і дає фоновому потоку ядра `kswapd` час звільнити неактивний файловий кеш чи скинути анонімні сторінки у swap.

Детальний опис текстового формату файлів керування та подій подано у вставці [Поверхня керування пам'яттю Cgroups v2](book:unix-linux/cgroup-v2-memory-peak-swap/api-memory-control-surface.md).

### 2.4 memory.max (Жорсткий ліміт) та direct reclaim

`memory.max` є абсолютного стелею використання RAM. Якщо споживання групи досягає `memory.max`, ядро переходить у режим **прямого витіснення (direct reclaim)**: потік, що затребував пам'ять, зупиняється і виконує синхронне звільнення сторінок у контексті власного виклику через функцію `try_to_free_mem_cgroup_pages()`.

Витіснення відбувається за циклами пріоритету сканування від `DEF_PRIORITY` (12) до 0. На кожному ітераційному кроці ядро сканує LRU-списки cgroup, вилучає неактивні файлові сторінки та скидає брудні сторінки на диск. Додатково викликаються функції `shrink_slab()`, які вивільняють кэші метаданих файлових систем (`dentry`, `inode cache`).

Якщо direct reclaim на рівні пріоритету 0 не здатний звільнити жодної сторінки (наприклад, вся пам'ять є анонімною, а swap вимкнено або заповнено), ядро ініціює процедуру cgroup OOM Killer.

### 2.5 Проактивне витіснення через memory.reclaim (Linux 5.19+)

Починаючи з версії ядра Linux 5.19, cgroups v2 підтримує інтерфейс проактивного витіснення `memory.reclaim`. Запис у цей файл обсягу пам'яті змушує ядро негайно виконати цикл витіснення вказаного обсягу сторінок для даної cgroup без зміни лімітів `memory.high` або `memory.max`:

```bash
echo 100M > /sys/fs/cgroup/system.slice/my-app.service/memory.reclaim
```

Це дозволяє зовнішнім оркестраторам (таким як Kubernetes або власний daemon моніторингу) звільняти файловий кеш перед запуском важких обчислювальних задач, запобігаючи несподіваним затримкам direct reclaim у майбутньому.

## 3. Взаємодія з фоновим записом (Cgroup Writeback)

Однією з найбільших проблем першої версії cgroups була розсинхронізація підсистеми пам'яті та підсистеми блокового вводу-виводу (I/O). Коли процес у cgroups v1 модифікував файл у кеші, сторінка ставала "брудною" (dirty). Однак фізичний запис брудної сторінки на накопичувач виконувався асинхронно фоновими потоками ядра `kworker` або `flusher`. В результаті операції I/O списувалися на кореневу cgroup, а не на групу-винуватця.

У cgroups v2 впроваджено підсистему **cgroup writeback** (`mm/page-writeback.c`). Кожна брудна сторінка зберігає посилання на `struct mem_cgroup`, яка її модифікувала. Коли підсистема I/O починає скидати сторінки на диск, вона передає контекст cgroup до контролера `io`.

### Стримування брудних сторінок (Dirty Throttling)

Ядро Linux контролює частку брудних сторінок у cgroup за допомогою двох рівнів стримування:

1. **Фоновий поріг (dirty background limit):** При досягненні цього порогу ядро запускає фонові потоки запису `wb_domain` для цієї cgroup.
2. **Жорсткий поріг (dirty limit):** Якщо споживання брудних сторінок досягає жорсткої межі, системний виклик `write()` у процесі-винуватці блокується і переходить у стан синхронного скидання даних на диск.

Завдяки цьому cgroups v2 унеможливлює ситуацію, коли одна cgroup заповнює брудними сторінками весь доступний page cache системи й блокує дискові операції інших ізольованих сервісів.

## 4. Відстеження пікового споживання: memory.peak та правайзинг

Для точного підбору лімітів ресурсів (rightsizing) значення `memory.current` є недостатнім, оскільки воно показує лише миттєву зріз-картину. Для програм із періодичними сплесками активності (batch processing, збірка сміття у JVM) споживання між сплесками може бути низьким, але під час сплеску процес вимагає суттєво більше RAM.

Файл `memory.peak` фіксує максимальне історичне значення `memory.current` з моменту створення cgroup або від останнього скидання лічильника:

```
memory.peak = max( memory.peak, memory.current )
```

Оновлення значення `memory.peak` у ядрі відбувається атомарно під час кожної операції заряджання сторінок через інструкцію `cmpxchg()`. Це унеможливлює пропуск пікових сплесків навіть у тому випадку, якщо сплеск тривав декілька мікросекунд.

У ядрах Linux 6.3+ підтримується скидання вотермарки `memory.peak` шляхом запису у файл значення `"reset"` або поточного значення `memory.current`:

```bash
echo reset > /sys/fs/cgroup/my-app/memory.peak
```

### Методологія визначення лімітів (Rightsizing)

1. **Фаза спостереження:** Застосунок запускається з вимкненим або завищеним `memory.max`.
2. **Проходження навантаження:** Виконується повний тестовий цикл або добовий прогін у продакшені під піковим трафіком.
3. **Фіксація піка:** Програмно або через утиліти зчитується `memory.peak`.
4. **Розрахунок термінів:** Жорсткий ліміт `memory.max` виставляється за формулою:
   ```
   memory.max = memory.peak * 1.20  (запас 20% на непередбачені сплески)
   memory.high = memory.peak * 1.05 (початок гальмування при перевищенні нормального піка)
   ```
5. **Скидання метрики:** Для нового релізу чи фази тестування виконується `echo reset > memory.peak`.

## 5. Управління простором підкачки (Swap): memory.swap.high та memory.swap.max

Існує помилкова думка, що повне відключення swap (`swapoff -a` або `memory.swap.max = 0`) покращує продуктивність системи. Насправді відсутність swap позбавляє ядро можливості витіснити "мертву" анонімну пам'ять (сторінки конфігурації, ініціалізаційний код процесів, які виконуються один раз при старті), звільняючи місце для корисного файлового кешу.

Cgroups v2 надає ізольований контроль над утилізацією swap для кожної групи через параметри `memory.swap.high`, `memory.swap.max` та `memory.swap.peak`.

### 5.1 memory.swap.max

`memory.swap.max` встановлює жорстку стелю анонімних сторінок цієї групи, які можуть бути витіснені на дисковий пристрій підкачки або у Zswap.

Якщо cgroup вичерпала `memory.max` і намагається витіснити анонімні сторінки у swap, але досягла `memory.swap.max`, ядро блокує подальший свопінг. Наступний запит на виділення пам'яті призведе до OOM Killer. Значення `0` закриває доступ до swap для цієї групи, змушуючи її працювати виключно в межах RAM.

### 5.2 memory.swap.high та приборкання своп-штормів (Swap Thrashing)

Коли система активно скидає сторінки на повільний накопичувач (HDD/SSD), швидкість введення-виведення дискової підсистеми стає вузьким місцем. Процеси входять у стан `D` (uninterruptible sleep), чекаючи завершення сторінкового збою (page fault). Починається шторм підкачки (thrashing).

`memory.swap.high` дозволяє встановити м'яку межу на використання swap. Перетин цієї межі вмикає throttling для процесів цієї cgroup під час спроб витіснення анонімних сторінок у функції `mem_cgroup_handle_over_swap_high()`, сповільнюючи процес до того, як він заповнить увесь доступний swap і заблокує дисковий контролер.

### 5.3 Взаємодія з Zswap та Zram

У сучасних системах Linux витіснення анонімної пам'яті часто спрямовується не на фізичний диск, а у модуль `zswap` (стиснений кеш у RAM) або `zram` (стиснений пристрій у пам'яті). Коли cgroup витісняє анонімну сторінку, ядро стискає її за допомогою алгоритмів `lz4` чи `zstd` і зберігає у зарезервованому пулі RAM.

Контролер пам'яті cgroups v2 обліковує анонімні сторінки у `zswap` як частину `memory.swap.current`. Це дозволяє суворо контролювати обсяг стиснених сторінок і запобігати ситуаціям, коли стиснення пам'яті з'їдає весь доступний процесорний час хоста.

## 6. Анатомія cgroup OOM Killer та атомність groups

Коли прямий reclaim не може звільнити пам'ять при досягненні `memory.max` та `memory.swap.max`, підсистема пам'яті викликає функцію `mem_cgroup_out_of_memory()`.

### 6.1 Алгоритм вибору жертви

Cgroup OOM Killer обирає процес-жертву за допомогою обрахунку штрафного балу `oom_score`:

```
oom_score = (rss_pages + swap_pages + slab_pages) + oom_score_adj
```

Ядро шукає процес з наибольшим `oom_score` **всередині цієї cgroup та її піддерева**. Процеси в сусідніх cgroups не розглядаються й залишаються неушкодженими.

### 6.2 Атомна ліквідація групи через memory.oom.group

У складних багатопроцесних архітектурах (наприклад, база даних PostgreSQL із сотнями worker-процесів, або PHP-FPM) вбивство одного дочірнього процесу зазвичай є згубним: застосунок втрачає зв'язок зі своїми ресурсами, залишає незвільнені shared memory locks або входить у стан вічного панічного перезапуску.

Прапорець `memory.oom.group` вирішує цю проблему:

```bash
echo 1 > /sys/fs/cgroup/system.slice/postgresql.service/memory.oom.group
```

При `memory.oom.group = 1`, коли всередині cgroup спрацьовує OOM Killer, ядро перебирає всі задачі ієрархії через `css_task_iter_start()` та надсилає сигнал `SIGKILL` **усім процесам цієї cgroup та її дочірніх підгруп одночасно**. Це гарантує атомність знищення всієї групи й дозволяє супервізору (systemd чи Kubernetes) виконати чистий рестарт всієї служби з початкового стану.

## 7. Накладні витрати (Overhead) та продуктивність memcg

Використання cgroups v2 memory додає мінімальні накладні витрати на рівні ядра, однак при великій кількості короткоживучих cgroups необхідно враховувати такі фактори:

1. **Пам'ять під `struct mem_cgroup`:** Створення кожного вузла cgroup вимагає аллокації структури пам'яті розміром близько 4–8 КБ у ядрі, а також пер-процесорних масивів лічильників `percpu_charge`. При наявності десятків тисяч cgroups це може займати сотні мегабайтів RAM ядра.
2. **Проблема Dying Cgroups:** Коли cgroup видаляється, але деякі її сторінки залишаються в кеші або swap, ядро не може негайно звільнити структуру `struct mem_cgroup`. Вона переходить у стан `dying cgroup` до повного uncharge всіх сторінок.
3. **Lock contention у LRU-списках:** При використанні багатьох дочірніх cgroups підсистема витіснення витрачає час на перебір ієрархічного дерева cgroups (`mem_cgroup_iter()`). Для оптимальної продуктивності рекомендується уникати глибини вкладення cgroups більше 5–7 рівнів.

## 8. Аналіз подій та діагностика через memory.events та bpftrace

Для побудови системи моніторингу cgroups v2 надає текстовий файл `memory.events`, який містить атомарні лічильники критичних станів.

### Лічильники файлу memory.events

- `low`: кількість випадків, коли пам'ять групи витіснялася через захист сусідніх cgroups.
- `high`: кількість подій перевищення `memory.high` та активації throttling.
- `max`: кількість невдалих спроб аллокації через перетин `memory.max`.
- `oom`: кількість ініціалізацій логіки OOM Killer для цієї cgroup.
- `oom_kill`: кількість фактів знищення процесів OOM Killer-ом.
- `oom_group_kill`: кількість фактів повного атомного знищення cgroup через `memory.oom.group=1`.

Практична реалізація монітора подій пам'яті мовами C та C++ з використанням неблокуючого виклику `epoll()` наведена у вставці [Моніторинг лімітів та подій пам'яті на C та C++](book:unix-linux/cgroup-v2-memory-peak-swap/proj-cgroup-memory-monitor.md).

### Простеження через eBPF та bpftrace

Для глибокої діагностики затримок витіснення сторінок у ядрі використовується інструмент `bpftrace`. Однорядковий скрипт нижче відстежує всі випадки, коли ядро застосовує throttling при перевищенні `memory.high`, виводячи назву процесу, PID та назву cgroup:

```bash
bpftrace -e '
kprobe:mem_cgroup_handle_over_high {
    $memcg = (struct mem_cgroup *)arg0;
    printf("Throttling PID %d (%s) у cgroup %s\n", 
           pid, comm, $memcg->css.cgroup->kn->name);
}'
```

Цей спосіб дозволяє безпосередньо виміряти затримки виділення пам'яті без внесення додаткових накладних витрат у простір користувача.

## 9. Конфігурація в systemd та Kubernetes

У сучасних дистрибутивах Linux первинним менеджером cgroups v2 є `systemd`. Директиви юнітів systemd прямо мапяться на файли контролера пам'яті:

```ini
[Unit]
Description=High-Load Database Service
After=network.target

[Service]
ExecStart=/usr/bin/clickhouse-server --config-file=/etc/clickhouse-server/config.xml
User=clickhouse

# Гарантії та обмеження Cgroups v2 memory
MemoryMin=2G
MemoryLow=4G
MemoryHigh=14G
MemoryMax=16G
MemorySwapMax=1G

# Атомне вбивство всієї групи при OOM
MemoryAccounting=true
OpenFileHandlerLimit=100000

[Install]
WantedBy=multi-user.target
```

Відповідність параметрів systemd та файлів cgroupfs:

- `MemoryMin=2G` → `memory.min`
- `MemoryLow=4G` → `memory.low`
- `MemoryHigh=14G` → `memory.high`
- `MemoryMax=16G` → `memory.max`
- `MemorySwapMax=1G` → `memory.swap.max`

У середовищі Kubernetes при використанні cgroup v2 (Kubelet `cgroupDriver: systemd`):
- `resources.requests.memory` транслюється в `memory.low` (або `memory.min` залежно від конфігурації QOS).
- `resources.limits.memory` транслюється в `memory.max`.

## Висновок

Підсистема пам'яті в cgroups v2 перетворює ізоляцію оперативної пам'яті з грубого механізму примусового знищення процесів на точний інструмент управління пропускною здатністю та затримками. Використання чотирьох рівнів обмежень (`memory.min`, `low`, `high`, `max`), моніторинг вотермарок `memory.peak`, керування простором підкачки та атомна реакція на OOM дозволяють створювати стабільні multi-tenant системи із гарантованим рівнем обслуговування (SLA).
