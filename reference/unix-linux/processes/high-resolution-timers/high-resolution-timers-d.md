Запустіть процес обробки аудіо з розміром буфера 64 семпли при частоті дискретизації 48 кГц. Кожен такий буфер вимагає обробки й відправки у звукову карту строго кожні 1.33 мілісекунди. Якщо запросити у системи паузу в 1.33 мілісекунди через класичні системні виклики засинання у ядрі з частотою системного тику 250 Гц, процес засне не на 1.33 мс, а на цілих 4 мілісекунди, пропустивши два дедлайни поспіль і спричинивши тріск у динаміках.

```
частота дискретизації = 48000 Гц
розмір буфера        = 64 семпли
період кадру         = 64 / 48000
                     = 0.001333 с
                     = 1.333 мс
період тику HZ=250   = 1000 / 250
                     = 4.0 мс
фактичний сон        = 4.0 мс     [округлення вгору до наступного тику]
затримка прострочення = 4.0 - 1.333
                     = 2.667 мс   [спустошення буфера звукової карти]
```

Ця проблема виникає через дискретизацію часу в традиційних операційних системах. Протягом двох десятиліть ядро Linux покладалося на фіксовані переривання системного таймера, які квантували час із кроком від 1 до 10 мілісекунд. Підсистема **hrtimers** (High-Resolution Timers) замінила цю схему на наносекундне представлення часу, червоно-чорні дерева сортування подій та одноразові апаратні переривання, надавши Linux субмілісекундну точність.

## Квант у млинку: чому 100 Гц перестало вистачати

Історично ядро Linux використовувало підсистему таймерного колеса (англ. *Timer Wheel*). Алгоритм відмінно масштабувався для мільйонів мережевих таймаутів: вставка й видалення таймера виконувалися за постійний час `O(1)` завдяки поділу таймерів на кошики залежно від часу їхнього спрацьовування.

Однак точність колеса таймерів жорстко прив'язувалася до частоти системного переривання `HZ`. Якщо ядро зібрано з `HZ=100`, системний тик відбувається кожні 10 мілісекунд. Будь-який таймер із часом спрацьовування, що потрапляє всередину цього інтервалу, округляється вгору до наступного тику.

Просте збільшення частоти `HZ` до 10 000 Гц (з кроком 100 мікросекунд) проблему не розв'язує. При 10 000 перериваннях на секунду на кожному ядрі процесор витрачає до 20% робочого часу лише на обробку порожніх переривань таймера. Більше того, колесо таймерів має операцію перекаскадування: коли вичерпується поточний кошик найближчого рівня, ядро переносить таймери з віддаленого кошика у ближній. Ця операція має часову складність `O(N)` від кількості таймерів у даному кошику, що створює раптові затримки в обробці переривань.

```
кількість тиків на секунду = 10000
період між тиками          = 1000000 / 10000
                           = 100 мкс
накладні витрати на тик   = 2.5 мкс
витрати ядра за секунду   = 10000 · 2.5 мкс
                           = 25000 мкс
                           = 25 мс
частка втраченого часу    = 25 / 1000
                           = 2.5% на кожен процесорний потік
```

Для задач реального часу, профілювання коду, синхронізації відеокадрів та високочастотного мережевого опитування така схема виявилася непридатною. Детальніше еволюцію від колеса таймерів до нової архітектури розібрано в [Історія появи hrtimers у ядрі Linux](book:unix-linux/high-resolution-timers/hist-hrtimers-genesis.md).

## Архітектурний поділ: Timer Wheel проти Hrtimers

Щоб розв'язати проблему без руйнування продуктивності мережевого стека, підсистема `hrtimers` розділила облік часу в ядрі на дві незалежні паралельні підсистеми:

1. **Низькоточні затримки ядра (Timer Wheel)**: Таймаути сокетів, драйверів дисків, перевірки з'єднань TCP та інші операції, що не вимагають мікросекундної точності. Для них важливіше швидке долучення `O(1)` при мільйонах одночасних запитів.
2. **Високоточні таймери (Hrtimers)**: Засинання процесів (`nanosleep`), POSIX-таймери (`timer_create`), `timerfd`, виклики реального часу та внутрішні дедлайни планувальника.

Замість квантованого лічильника `jiffies` підсистема `hrtimers` використовує уніфікований тип **`ktime_t`**. У 64-бітних архітектурах `ktime_t` є 64-бітним цілим числом зі знаком (`s64`), яке зберігає абсолютний час у наносекундах. Це забезпечує діапазон вимірювання понад 292 роки без ризику переповнення.

У 32-бітних архітектурах `ktime_t` реалізується як структура з двох 32-бітних слів (секунди та наносекунди), а для запобігання гонкам при зчитанні застосовуються атомарні секції послідовного засуву `seqcount_t`.

Кожен таймер описується структурою `struct hrtimer`:

```c
struct hrtimer {
    struct timerqueue_node  node;
    ktime_t                 _softexpires;
    enum hrtimer_restart    (*function)(struct hrtimer *);
    struct hrtimer_clock_base *base;
    u8                      state;
    u8                      is_rel;
    u8                      is_soft;
    u8                      is_hard;
};
```

Таймери зберігаються не у масивах кошиків, а в сортованому червоно-чорному дереві (структура `timerqueue_node`, що загортає `struct rb_node`). Ключем сортування є абсолютний час спрацьовування `_softexpires`.

![Еволюція підсистеми таймерів у ядрі Linux](/reference/unix-linux/processes/high-resolution-timers/img/hrtimer-architecture.svg)

*Порівняння традиційного колеса таймерів та сортованого червоно-чорного дерева підсистеми hrtimers*

Вставка нового таймера у червоно-чорне дерево коштує `O(log N)`, де `N` — кількість активних високоточних таймерів на даному ядрі. Оскільки кількість одночасних високоточних таймерів рідко перевищує кілька десятків або сотень на ядро, `log N` не перевищує 7–10 ітерацій порівняння.

Для швидкого вибору наступної події підсистема кешує вказівник на найлівіший вузол дерева (`rb_leftmost`). Завдяки цьому пошук таймера, який має спрацювати найпершим, виконується за постійний час `O(1)`.

## Процесорні бази часу (hrtimer_clock_base)

Кожен процесорний потік (CPU core) у ядрі Linux має власний екземпляр структури `struct hrtimer_cpu_base`, який керує масивом баз часу `clock_base[HRTIMER_MAX_CLOCK_BASES]`.

Таймери прив'язані до конкретних баз часу `struct hrtimer_clock_base`. Ядро Linux підтримує кілька систем відліку часу на кожному процесорному ядрі:

| База часу | Поведінка при зміні системного годинника | Враховує час сну (suspend) | Основне призначення |
| :--- | :--- | :--- | :--- |
| `CLOCK_MONOTONIC` | Монотонна, не зазнає стрибків | Ні | Абсолютні інтервальні затримки |
| `CLOCK_REALTIME` | Може стрибати через NTP або `settimeofday` | Ні | Таймери будильників та календарних подій |
| `CLOCK_BOOTTIME` | Монотонна | Так | Таймери, що мають враховувати час сну пристрою |
| `CLOCK_TAI` | Атомний час (без вискокосних секунд) | Так | Синхронізація точного часу в мережах PTP |
| `CLOCK_MONOTONIC_RAW` | Апаратний час без коригування фази NTP | Ні | Точне профілювання hardware джиттера |

Кожна база часу тримає власне червоно-чорне дерево. При обробці таймерного переривання ядро сканує найлівіші вузли всіх баз часу на даному CPU і вибирає абсолютний мінімум серед них.

## Шлях виконання системного виклику clock_nanosleep

Щоб зрозуміти, як `hrtimers` працюють на практиці при зверненні з простору користувача, простежимо шлях системного виклику `clock_nanosleep()`:

1. **Вхід у ядро**: Процес викликає `clock_nanosleep(CLOCK_MONOTONIC, 0, &rqtp, &rmtp)`. Ядро переходить у режим супервізора і передає управління у функцію `sys_clock_nanosleep()`.
2. **Створення `struct hrtimer_sleeper`**: На стеку потоку ядро створює обгортку `struct hrtimer_sleeper`, яка містить вбудовану структуру `struct hrtimer` та посилання на задачу `task_struct`.
3. **Ініціалізація callback**: Функція зворотного виклику таймера виставляється у `hrtimer_wakeup()`. При спрацьовуванні ця функція переведе потік із стану `TASK_INTERRUPTIBLE` у стан `TASK_RUNNING` і розбудить його через `wake_up_process()`.
4. **Вставка в дерево та перепрограмування**: Викликається `hrtimer_start_range_ns()`. Таймер вставляється у червоно-чорне дерево відповідного ядра. Якщо його час спрацьовування є найближчим, ядро викликом `tick_program_event()` миттєво записує новий відлік у регістр апаратного таймера APIC.
5. **Засинання потоку**: Потік викликає `freezable_schedule()`. Планувальник вилучає потік із черги виконання і переключає контекст процесора на іншу задачу.
6. **Апаратне переривання**: Коли апаратний APIC досягає нуля, виникає переривання. Обробник `hrtimer_interrupt()` знаходить таймер, викликає `hrtimer_wakeup()`, і планувальник повертає потік у чергу готовності.

Цей ланцюг показує, що точність повернення у простір користувача складається з двох компонентів: точності спрацьовування самого `hrtimer` та затримки планувальника при виборі розбудженої задачі.

## Апаратний міст: one-shot clockevents та APIC

Неможливо забезпечити наносекундну точність на рівні програмного забезпечення, якщо апаратне забезпечення продовжує переривати процесор за фіксованим розкладом HZ. Для реалізації `hrtimers` ядро Linux впровадило абстракцію драйверів подій часу — **`clock_event_device`**.

Драйвер `clock_event_device` огортає апаратні таймери процесора:
- Локальний таймер APIC (Advanced Programmable Interrupt Controller) у процесорах x86 / x86-64.
- Апаратний таймер HPET (High Precision Event Timer).
- Архітектурний таймер ARM Generic Timer (System Timer).

Пристрої `clock_event_device` можуть працювати у двох режимах:
1. **`CLOCK_EVT_MODE_PERIODIC`**: Традиційний режим. Апаратний таймер налаштовується один раз при завантаженні й генерує переривання строго через однакові інтервали (наприклад, кожні 1 мс).
2. **`CLOCK_EVT_MODE_ONESHOT`**: Режим одноразового спрацьовування. Апаратний таймер програмується на відлік конкретної кількості тактів. Після спрацьовування таймер зупиняється і не генерує нових переривань, поки ядро явно не запрограмує його на наступну події.

Перехід підсистеми `hrtimers` у високоточний режим (**high-resolution mode**) відбувається під час завантаження системи або підключення апаратного пристрою, що підтримує режим `ONESHOT`. 

Коли додається новий `hrtimer`, ядро перевіряє, чи не є його час спрацьовування ранішим за поточний запланований апаратний тик. Якщо новий таймер стає найлівішим вузлом у червоно-чорному дереві, ядро викликає функцію `tick_program_event()`. Ця функція обчислює різницю між часом спрацьовування та поточним часом і записує це значення безпосередньо у регістр лічильника апаратного APIC-таймера.

```
поточний час ktime_get() = 1000000000 нс
найближчий hrtimer (T1)  = 1000050000 нс
дельта для апаратури      = 1000050000 - 1000000000
                         = 50000 нс (50 мкс)
запис у регістр APIC     = 50000 / тактовий_період_APIC
```

В результаті процесор не отримує жодного зайвого переривання між моментом `1000000000` та `1000050000`. Апаратне переривання виникає строго у момент `1000050000` нс.

## Анатомія спрацьовування: від переривання до зворотного виклику

Коли апаратний таймер досягає нуля, він генерує вектор апаратного переривання (hardirq). Обробник цього переривання передає управління у функцію підсистеми `hrtimer_interrupt()`.

![Цикл обробки переривання та перепрограмування clockevent](/reference/unix-linux/processes/high-resolution-timers/img/hrtimer-interrupt-flow.svg)

*Послідовність викликів та перепрограмування при спрацьовуванні hrtimer_interrupt()*

Покроковий процес обробки переривання виглядає так:

1. **Фіксація точного часу**: Ядро зчитує поточний час з апаратного джерела `clocksource` (наприклад, інструкцією `RDTSC` на x86) і зберігає його у змінну `now = ktime_get()`.
2. **Обхід застарілих вузлів**: Починаючи з найлівішого вузла червоно-чорного дерева `rb_leftmost`, ядро порівнює `timer->expires` із `now`. Усі таймери, час яких менший або дорівнює `now`, вилучаються з дерева.
3. **Виконання зворотних викликів (callbacks)**: Для кожного вилученого таймера ядро викликає функцію `timer->function(timer)`.
4. **Оновлення стану та повторний запуск**: Залежно від повернутого значення `timer->function()`:
   - Якщо повернуто `HRTIMER_NORESTART`, таймер переходить у стан неактивності.
   - Якщо повернуто `HRTIMER_RESTART`, ядро очікує, що функція викликала `hrtimer_forward()`, і знову вставляє таймер у червоно-чорне дерево на нову позицію.
5. **Перепрограмування апаратури**: Ядро знаходить новий найлівіший вузол `rb_leftmost` у дереві й через `tick_program_event()` програмує апаратний APIC-таймер на час спрацьовування цього наступного таймера.

Особливе значення має контекст виконання зворотного виклику. В звичайному ядрі Linux callback виконується безпосередньо в атомарному контексті апаратного переривання (hardirq). Це означає, що функція таймера має бути максимально короткою і не має права викликати операції, що засинають або блокуються (наприклад, виділення пам'яті з `GFP_KERNEL` або захоплення звичайного мутекса).

У ядрі з підтримкою реального часу (PREEMPT_RT) або при використанні прапорця `HRTIMER_MODE_SOFT` обробка розділяється: в атомарному контексті вилучаються лише вузли, а самі функції зворотного виклику передаються для виконання у контекст програмних переривань `HRTIMER_SOFTIRQ` (який виконується у нитках ядра `ksoftirqd/X`).

### Приклад створення ядерного hrtimer

Нижче наведено приклад модуля ядра Linux, який створює періодичний високоточний таймер із інтервалом 250 мікросекунд (4000 Гц):

```c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/hrtimer.h>
#include <linux/ktime.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Unix-Linux Reference");
MODULE_DESCRIPTION("High-Resolution Timer Kernel Module Example");

static struct hrtimer my_hrtimer;
static ktime_t period_ns;
static u64 fire_count = 0;

static enum hrtimer_restart hrtimer_callback(struct hrtimer *timer) {
    ktime_t now = ktime_get();
    fire_count++;

    /* Оновлюємо час наступного спрацьовування, уникаючи накопичення похибки */
    hrtimer_forward(timer, now, period_ns);

    if (fire_count % 4000 == 0) {
        pr_info("hrtimer_example: 4000 спрацьовувань зафіксовано\n");
    }

    /* Вказуємо підсистемі перезапустити таймер у дереві */
    return HRTIMER_RESTART;
}

static int __init hrtimer_example_init(void) {
    /* 250 мікросекунд = 250 000 наносекунд */
    period_ns = ktime_set(0, 250000);

    /* Ініціалізуємо hrtimer для монотонного годинника у відносному режимі */
    hrtimer_init(&my_hrtimer, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
    my_hrtimer.function = hrtimer_callback;

    pr_info("hrtimer_example: запуск hrtimer з періодом 250 мкс\n");
    hrtimer_start(&my_hrtimer, period_ns, HRTIMER_MODE_REL);

    return 0;
}

static void __exit hrtimer_example_exit(void) {
    int ret = hrtimer_cancel(&my_hrtimer);
    if (ret) {
        pr_info("hrtimer_example: активний таймер скасовано при вивантаженні\n");
    }
    pr_info("hrtimer_example: модуль вивантажено, всього спрацьовувань: %llu\n", fire_count);
}

module_init(hrtimer_example_init);
module_exit(hrtimer_example_exit);
```

Повний контракт системного та ядерного API з описом усіх режимів, прапорців та поверчуваних кодів зібрано у [Довідник системного та ядерного API hrtimers](book:unix-linux/high-resolution-timers/api-hrtimer-kernel-surface.md).

## Вплив C-states та управління живленням (PM QoS)

Окрім планувальника, найпотужнішим джерелом затримок при роботі з `hrtimers` є енергозберігаючі стани процесора (C-states). 

Коли ядро перебуває в режимі простою `idle`, процесор знижує споживання електроенергії, відключаючи окремі внутрішні блоки. Наприклад, у стані `C1` вимикається лише тактовий генератор ядра, а у станах `C6` або `C7` повністю скидається напруга з L1/L2 кешів та зупиняється внутрішній конвеєр інструкцій.

Вихід із глибоких станів C6/C7 вимагає часу на відновлення живлення та розігрів кешів:

```
стан C1  (Halt)           = 1 - 3 мкс затримки пробудження
стан C3  (Deep Sleep)     = 10 - 20 мкс затримки пробудження
стан C6/C7 (Power Gated)  = 50 - 150 мкс затримки пробудження
```

Якщо програма реального часу запросила високоточне засинання на 20 мікросекунд, а процесор у момент таймерного переривання знаходився у стані `C6`, реальна затримка пробудження становитиме 20 мкс (таймер) + 100 мкс (вихід із C-state) = 120 мікросекунд.

Для вирішення цієї проблеми ядро Linux надає інтерфейс управління якістю обслуговування **PM QoS** (Power Management Quality of Service).

Програма реального часу може відкрити файл `/dev/cpu_dma_latency` і записати туди максимальну допустиму затримку в мікросекундах (наприклад, `0` або `10` мкс):

```c
int fd = open("/dev/cpu_dma_latency", O_WRONLY);
int32_t latency = 0; /* 0 мікросекунд = заборона глибоких C-states */
write(fd, &latency, sizeof(latency));
```

Поки цей файловий дескриптор залишається відкритим, підсистема управління живленням ядра забороняє процесору переходити у стани сну глибше за вказаний ліміт, гарантуючи мікросекундний джиттер при спрацьовуванні `hrtimers`.

## Безтиковий режим (NOHZ) і збереження енергії

Поява підсистеми `hrtimers` та одноразових апаратних переривань уможливила реалізацію безтикового ядра — **NOHZ** (Tickless Kernel).

У традиційній системі з періодичними тиками, навіть коли процесор повністю простоює (стан idle), апаратний таймер продовжує генерувати 1000 переривань на секунду. Це перериває енергозберігаючі стани процесора (C-states), змушуючи його пробуджуватися, живити кеші й витрачати енергію акумулятора на перевірку порожніх черг задач.

Завдяки `hrtimers` у режимі `CONFIG_NO_HZ_IDLE` ядро при переході процесора в простій виконує такі кроки:
1. Перевіряє, чи є активні розклади у підсистемі `hrtimers` на цьому ядрі.
2. Якщо найближчий `hrtimer` має спрацювати через 2.5 секунди, ядро програмує локальний APIC-таймер на 2.5 секунди вперед і повністю вимикає періодичний системний тик.
3. Процесор переходить у глибокий стан сну (наприклад, C6/C7) на всі 2.5 секунди без жодного проміжного переривання.

В результаті енергоспоживання мобільних та серверних систем у режимі простою знижується у кілька разів. У режимі `CONFIG_NO_HZ_FULL` ядро може відключати періодичні тики навіть на працюючих ядрах, якщо на ядрі виконується лише одна задача з високим пріоритетом реального часу.

## Інтерфейси користувача: timerfd, clock_nanosleep та slack

У просторі користувача розробники мають доступ до точності `hrtimers` через кілька системних викликів:

1. **`clock_nanosleep()`**: Поліпшена версія `nanosleep`, яка дозволяє вказувати бажану базу часу (`CLOCK_MONOTONIC`, `CLOCK_REALTIME`) та використовувати абсолютний час спрацьовування (`TIMER_ABSTIME`).
2. **POSIX-таймери (`timer_create`, `timer_settime`)**: Дозволяють прив'язувати спрацьовування таймерів до доставки сигналів або виклику потоків у просторі користувача.
3. **`timerfd_create()`**: Найбільш ефективний сучасний інтерфейс, який загортає високоточний таймер у файловий дескриптор.

Виклик `timerfd` дозволяє інтегрувати високоточні таймери безпосередньо у неблокуючі цикли обробки подій (`epoll`, `select`, `poll`) поруч із мережевими сокетами та файловими дескрипторами.

### Концепція Timer Slack (згрупування таймерів)

Хоча `hrtimers` здатні пробуджувати процес із точністю до наносекунд, абсолютна точність для кожного некритичного таймера є шкідливою для енергоефективності. Якщо 50 фонових процесів запросять засинання на 10 мілісекунд із різницею в 50 мікросекунд один від одного, процесор муситиме прокинутися 50 разів поспіль.

Для вирішення цієї проблеми у ядрі Linux впроваджено концепцію **Timer Slack** (таймерний люфт).

Для кожного таймера ядро обчислює не лише точний час `_softexpires`, а й допустимий діапазон затримки `_expires` (діапазон slack):

```
_softexpires = бажаний_час_спрацьовування
_expires    = _softexpires + timer_slack
```

Коли ядро вставляє новий таймер, воно перевіряє, чи є в дерево вже існуючі таймери, чий час спрацьовування потрапляє у діапазон `[_softexpires; _expires]`. Якщо такий таймер існує, ядро групує новий таймер з існуючим, змушуючи їх спрацювати одночасно під час одного апаратного переривання.

Величина `timer_slack` за замовчуванням становить 50 мікросекунд і може налаштовуватися для кожного процесу окремо через системний виклик `prctl(PR_SET_TIMERSLACK, ...)` або через псевдофайл `/proc/<pid>/timerslack_ns`. Для систем реального часу `timer_slack` виставляють у 0, гарантуючи негайне спрацьовування.

### Приклад використання timerfd у просторі користувача

Нижче наведено приклад періодичного таймера з інтервалом 1 мілісекунда, інтегрованого у цикл `epoll`.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <unistd.h>
#include <sys/timerfd.h>
#include <sys/epoll.h>
#include <time.h>

int main(void) {
    int tfd = timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC);
    if (tfd == -1) {
        perror("timerfd_create");
        return EXIT_FAILURE;
    }

    struct itimerspec new_value = {0};
    /* Період 1 мілісекунда = 1 000 000 наносекунд */
    new_value.it_interval.tv_sec = 0;
    new_value.it_interval.tv_nsec = 1000000;
    new_value.it_value.tv_sec = 0;
    new_value.it_value.tv_nsec = 1000000;

    if (timerfd_settime(tfd, 0, &new_value, NULL) == -1) {
        perror("timerfd_settime");
        close(tfd);
        return EXIT_FAILURE;
    }

    int epfd = epoll_create1(EPOLL_CLOEXEC);
    if (epfd == -1) {
        perror("epoll_create1");
        close(tfd);
        return EXIT_FAILURE;
    }

    struct epoll_event ev;
    ev.events = EPOLLIN;
    ev.data.fd = tfd;
    if (epoll_ctl(epfd, EPOLL_CTL_ADD, tfd, &ev) == -1) {
        perror("epoll_ctl");
        close(epfd);
        close(tfd);
        return EXIT_FAILURE;
    }

    printf("Чекаємо 5 спрацьовувань timerfd...\n");
    for (int i = 0; i < 5; i++) {
        struct epoll_event events[1];
        int nfds = epoll_wait(epfd, events, 1, -1);
        if (nfds > 0) {
            uint64_t overruns = 0;
            ssize_t s = read(tfd, &overruns, sizeof(overruns));
            if (s == sizeof(overruns)) {
                printf("Тик %d: спрацьовувань за інтервал = %llu\n", i + 1, (unsigned long long)overruns);
            }
        }
    }

    close(epfd);
    close(tfd);
    return EXIT_SUCCESS;
}
```

```cpp
#include <iostream>
#include <chrono>
#include <system_error>
#include <cstdint>
#include <unistd.h>
#include <sys/timerfd.h>
#include <sys/epoll.h>

class HighResTimer {
    int m_tfd{-1};
public:
    explicit HighResTimer(std::chrono::nanoseconds period) {
        m_tfd = ::timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC);
        if (m_tfd == -1) {
            throw std::system_error(errno, std::generic_category(), "timerfd_create failed");
        }

        struct itimerspec new_val{};
        auto secs = std::chrono::duration_cast<std::chrono::seconds>(period);
        auto nsecs = period - secs;

        new_val.it_interval.tv_sec = secs.count();
        new_val.it_interval.tv_nsec = nsecs.count();
        new_val.it_value = new_val.it_interval;

        if (::timerfd_settime(m_tfd, 0, &new_val, nullptr) == -1) {
            ::close(m_tfd);
            throw std::system_error(errno, std::generic_category(), "timerfd_settime failed");
        }
    }

    ~HighResTimer() {
        if (m_tfd != -1) {
            ::close(m_tfd);
        }
    }

    int fd() const noexcept { return m_tfd; }

    std::uint64_t read_overruns() {
        std::uint64_t overruns{0};
        ssize_t s = ::read(m_tfd, &overruns, sizeof(overruns));
        if (s != sizeof(overruns)) {
            throw std::system_error(errno, std::generic_category(), "read failed");
        }
        return overruns;
    }
};

int main() {
    try {
        using namespace std::chrono_literals;
        HighResTimer timer(1ms);

        int epfd = ::epoll_create1(EPOLL_CLOEXEC);
        if (epfd == -1) {
            throw std::system_error(errno, std::generic_category(), "epoll_create1 failed");
        }

        struct epoll_event ev{};
        ev.events = EPOLLIN;
        ev.data.fd = timer.fd();
        ::epoll_ctl(epfd, EPOLL_CTL_ADD, timer.fd(), &ev);

        std::cout << "Чекаємо 5 спрацьовувань C++ timerfd...\n";
        for (int i = 0; i < 5; ++i) {
            struct epoll_event events[1];
            int nfds = ::epoll_wait(epfd, events, 1, -1);
            if (nfds > 0) {
                auto count = timer.read_overruns();
                std::cout << "C++ Тик " << (i + 1) << ": спрацьовувань = " << count << '\n';
            }
        }

        ::close(epfd);
    } catch (const std::exception& ex) {
        std::cerr << "Помилка: " << ex.what() << '\n';
        return EXIT_FAILURE;
    }

    return EXIT_SUCCESS;
}
```

## Особливості в PREEMPT_RT та реальний час

У ядрах із патчами реального часу PREEMPT_RT підсистема `hrtimers` зазнає додаткових адаптацій для усунення невизначеності в затримках:

1. **Розділення прапорців `HRTIMER_MODE_HARD` та `HRTIMER_MODE_SOFT`**: Таймери, задіяні в обробці переривань заліза або синхронізації планувальника (наприклад, дедлайни `SCHED_DEADLINE`), позначаються прапорцем `HRTIMER_MODE_HARD`. Вони виконуються безпосередньо у суворому контексті апаратного переривання з вимкненими перериваннями ядра. Усі інші користувацькі таймери виконуються у контексті потоків `ksoftirqd`.
2. **Міграція таймерів (`hrtimer_migrate`)**: При переході процесорного ядра у стан сну або при зміні маски приналежності процесу (CPU affinity) ядро переносить активні таймери на сусідні працюючі ядра, щоб уникнути втрати подій.

Завдяки цим адаптаціям у системах реального часу розсіювання затримки (джиттер) пробудження процесів вдається зменшити до менш ніж 5–10 мікросекунд навіть при 100% навантаженні процесора обчислювальними задачами.

## Діагностика та простеження: /proc/timer_list та tracepoints

Для аналізу стану підсистеми `hrtimers` у працюючій системі ядро надає кілька інструментів діагностики.

### 1. Інспекція через /proc/timer_list

Файл `/proc/timer_list` містить повний зріз стану всіх баз часу, пристроїв `clockevent` та списків активних таймерів на кожному процесорному ядрі:

```bash
cat /proc/timer_list | head -n 40
```

Типовий фрагмент виводу:

```text
Timer List Version: v0.9
now at 4589201248512 nsecs

cpu: 0
 clock 0:
  .base: ffff880157c0d000
  .index: 0
  .resolution: 1 nsecs
  .get_time: ktime_get_real
  active timers:
   #0: <ffff880152a3b780>, tick_sched_timer, S:01
   #1: <ffff880155b1f400>, hrtimer_wakeup, S:01
    #sys: 1542, posix_timer
```

У виводі можна перевірити параметри `.resolution` (наявність значення `1 nsecs` підтверджує активний високоточний режим), а також переглянути списки таймерів, прикриплених до кожної бази часу.

### 2. Простеження через tracepoints підсистеми hrtimer

Підсистема `hrtimers` містить вбудовані точки простеження (tracepoints) у Ftrace:

```bash
# Список доступних точок простеження hrtimer
sudo perf list 'hrtimer:*'
```

Основні події:
- `hrtimer:hrtimer_start`: Фіксує момент ініціалізації та вставки таймера у дерево.
- `hrtimer:hrtimer_expire_entry`: Фіксує початок виконання функції зворотного виклику.
- `hrtimer:hrtimer_expire_exit`: Фіксує завершення виконання callback.

Моніторинг затримок виконання зворотних викликів таймерів за допомогою `trace-cmd`:

```bash
sudo trace-cmd record -e "hrtimer:*" sleep 2
sudo trace-cmd report
```

Ці інструменти дозволяють інженерам миттєво виявляти "погані" callbacks, які виконуються занадто довго у контексті переривань і створюють затримки для решти підсистем ядра.
