Запустіть багатопотокову програму й подивіться на неї двома командами. `ps -p 1200` покаже один рядок. Але `ps -p 1200 -L` покаже кілька рядків із тим самим номером 1200 у першій колонці, але різними номерами в другій. Команда `kill 1200` завершить їх усі разом, а `taskset` може прив'язати окремий рядок до певного ядра.

Що з цього ядро вважає справжнім? Планувальник тримає список **задач** (`task_struct`). Потік у Linux — це не «полегшений процес», а звичайна задача, яку зв'язали з іншими задачами спільною ідентичністю. Процес — це група таких задач.

## Спільна пам'ять — це ще не потік

Виклик `clone()` із прапорцем `CLONE_VM` створює задачу, яка ділить той самий адресний простір із батьком. Але без інших прапорців це будуть дві різні програми з дивною спільною пам'яттю: у кожної свій PID, свої ліміти, своя таблиця файлових дескрипторів і свої лічильники часу.

Спільна пам'ять — необхідна властивість потоку, але не достатня.

## Ідентичність і CLONE_THREAD

Щоб задачі стали справжніми потоками однієї програми, потрібен прапорець `CLONE_THREAD`. Він заносить нову задачу в **групу задач**.

У групи є номер — **TGID** (ідентифікатор групи). Саме його повертає `getpid()`. А власний номер задачі видає `gettid()`. У лідера групи (першої задачі) ці номери збігаються.

````
```c
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/syscall.h>

static void *worker(void *arg) {
    printf("потік:   getpid()=%d  gettid()=%ld\n",
           getpid(), (long)syscall(SYS_gettid));
    return NULL;
}

int main(void) {
    pthread_t t;
    printf("головний: getpid()=%d  gettid()=%ld\n",
           getpid(), (long)syscall(SYS_gettid));
    pthread_create(&t, NULL, worker, NULL);
    pthread_join(t, NULL);
    return 0;
}
```
````

Спільна ідентичність приносить кілька наслідків:
- **Про смерть задачі не повідомляють.** Батьківський процес дізнається лише про завершення всієї групи.
- **Рахунки спільні.** Ліміти ресурсів і спожитий час лежать в одній структурі `signal_struct`.
- **Смерть спільна.** Смертельний сигнал чи `exit()` з будь-якого потоку завершує всю групу.

## Що в потоку лишається своїм

Хоча багато ресурсів є спільними (відображення пам'яті, таблиця дескрипторів, обробники сигналів), деякі речі кожна задача мусить мати власні:

- **Регістри й стек ядра**, оскільки кожна задача може виконувати власні інструкції й робити незалежні системні виклики.
- **Стек користувача.** Ядро не може ростити кілька стеків в одному адресному просторі, тому їх виділяє бібліотека потоків (через `mmap()`) фіксованого розміру зі сторінкою-вартовим унизу для захисту від переповнення.
- **Власні глобальні змінні.** Змінні на кшталт `errno` мусять бути окремими для кожного потоку, інакше виклики б затирали результати один одному (реалізується через механізм локальних даних потоку — TLS).
- **Маска сигналів.** Диспозиція (обробник) сигналів — спільна, а от які сигнали наразі заблоковано, вирішує кожна задача окремо.
- **Пріоритет планування.** Значення `nice` і маска дозволених ядер є властивістю конкретної задачі.

## Сигнали: одна диспозиція, багато масок

Сигнал може бути адресований **усій програмі** (групі) або **конкретній задачі** (`pthread_kill()`).
Якщо сигнал надходить до групи, ядро доправляє його будь-якій **одній** задачі, яка не тримає його заблокованим. Тому надійний спосіб працювати із сигналами в потоках — заблокувати їх скрізь, окрім одного виділеного потоку.

Якщо ж сигнал породжено інструкцією (наприклад, `SIGSEGV`), він приходить саме тій задачі, що схибила. Але оскільки типова дія — завершення, то гине вся група. Тому падіння одного потоку завжди валить усю програму.
