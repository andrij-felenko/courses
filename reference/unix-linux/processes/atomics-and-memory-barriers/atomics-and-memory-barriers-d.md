# Атомарні операції та бар'єри пам'яті в Linux

Ядро Linux — це багатонитеве середовище з істинним паралелізмом, де тисячі процесів, переривань та ядер процесора одночасно змагаються за спільні дані. Класичні блокування (спінлоки, м'ютекси) розв'язують проблему гонитви, але ціною зупинки або очікування. Коли потрібно змінити простий лічильник чи прапорець, блокування стають надто «важкими».

Тут на допомогу приходять **атомарні операції** — інструкції, які процесор виконує як єдине ціле, без можливості втручання з боку інших ядер. Проте самі лише атомарні операції не рятують від іншої проблеми сучасних архітектур — переупорядкування інструкцій (instruction reordering) процесором та компілятором. Для контролю над порядком видимості пам'яті використовуються **бар'єри пам'яті** (memory barriers).

## Атомарний тип `atomic_t`

В ядрі Linux атомарні змінні представлені спеціальним типом `atomic_t` (для 32-бітних значень) та `atomic64_t` (для 64-бітних). 

Ви не можете просто привласнити значення `atomic_t` через `=`, оскільки структура приховує реальне значення, щоб змусити розробника використовувати лише спеціальні атомарні API.

### Базові операції

Читання та запис:
```c
atomic_t counter = ATOMIC_INIT(0); // Ініціалізація під час компіляції

atomic_set(&counter, 5);           // Встановити значення
int val = atomic_read(&counter);   // Прочитати значення
```
Ці операції гарантують, що читання або запис не буде розірвано (torn read/write), але вони **не дають жодних гарантій** щодо порядку виконання відносно інших операцій з пам'яттю.

### Операції Read-Modify-Write (RMW)

Це операції, які читають старе значення, змінюють його і записують нове — усе це як одна неподільна дія.

```c
atomic_add(10, &counter); // Додати 10
atomic_sub(2, &counter);  // Відняти 2
atomic_inc(&counter);     // Інкремент
atomic_dec(&counter);     // Декремент
```

Окремою групою є операції, що повертають значення та дозволяють перевіряти умову. Це важливо для управління пам'яттю, наприклад, підрахунку посилань (reference counting):

```c
if (atomic_dec_and_test(&refcount)) {
    // Якщо після декременту значення стало 0 — звільняємо ресурс
    kfree(resource);
}
```

## Переупорядкування та чому потрібні бар'єри

Сучасні процесори не виконують інструкції строго в тому порядку, як вони написані в коді. Заради продуктивності вони змінюють порядок, завантажують дані наперед і кешують їх (Out-of-Order Execution). Компілятор робить те саме на етапі оптимізації.

Уявімо класичний сценарій з прапорцем готовності:

```c
// Початковий стан
int data = 0;
int ready = 0;

// Потік 1 (виробник)
data = 42;      // A
ready = 1;      // B

// Потік 2 (споживач)
if (ready == 1) // C
    print(data); // D
```

З погляду одного потоку логіка зберігається. Але для потоку 2 запис `ready = 1` може стати видимим **до** того, як стане видимим `data = 42`. Тоді потік 2 побачить `ready == 1`, але `data` все ще дорівнюватиме `0`. Це стається через слабку модель пам'яті процесора (як у ARM) або оптимізації компілятора.

## Бар'єри пам'яті (Memory Barriers)

Бар'єр пам'яті — це вказівка компілятору і процесору: «заверши всі операції з пам'яттю до цієї лінії, перш ніж починати операції після неї».

В ядрі Linux є кілька типів бар'єрів:

1. **`smp_mb()`** — Повний бар'єр (Full Barrier). Гарантує, що всі читання та записи до бар'єра будуть видимі перед будь-якими читаннями та записами після бар'єра.
2. **`smp_rmb()`** — Бар'єр читання (Read Barrier). Гарантує порядок лише для операцій читання.
3. **`smp_wmb()`** — Бар'єр запису (Write Barrier). Гарантує порядок лише для операцій запису.

Виправимо попередній приклад за допомогою бар'єрів:

:::tabs
== C (Linux Kernel)
```c
// Потік 1 (виробник)
data = 42;
smp_wmb();  // Гарантує, що data=42 буде видимим ДО ready=1
ready = 1;

// Потік 2 (споживач)
if (ready == 1) {
    smp_rmb(); // Гарантує, що data прочитається ПІСЛЯ перевірки ready
    print(data);
}
```
== C11 (Userspace)
```c
// Потік 1 (виробник)
data = 42;
atomic_store_explicit(&ready, 1, memory_order_release);

// Потік 2 (споживач)
if (atomic_load_explicit(&ready, memory_order_acquire) == 1) {
    print(data);
}
```
:::

## Семантика Acquire / Release

Класичні бар'єри `smp_mb()`, `smp_wmb()` — це важкий інструмент, що глобально впливає на конвеєр. Набагато елегантніше і швидше використовувати однобічні (one-way) бар'єри, відомі як **Acquire** та **Release** семантика.

- **Acquire** (отримання) — операція читання. Гарантує, що жодні подальші операції читання/запису не будуть переміщені **вгору** (до acquire). Використовується при захопленні блокування або перевірці прапорця.
- **Release** (звільнення) — операція запису. Гарантує, що жодні попередні операції читання/запису не будуть переміщені **вниз** (після release). Використовується при звільненні блокування або встановленні прапорця готовності.

В ядрі Linux для цього є спеціальні макроси:

```c
// Потік 1
data = 42;
smp_store_release(&ready, 1); // Всі попередні записи видимі

// Потік 2
if (smp_load_acquire(&ready) == 1) { // Наступні читання виконаються після
    print(data);
}
```

Це де-факто стандартний і рекомендований спосіб роботи з прапорцями готовності в сучасному ядрі.

## Резюме

- Використовуйте `atomic_t` для простих лічильників, де блокування (spinlock) надлишкові.
- Самі по собі `atomic_set` / `atomic_read` не гарантують порядку видимості для *інших* змінних.
- `smp_wmb()` та `smp_rmb()` захищають порядок виконання від оптимізацій компілятора та Out-of-Order виконання процесором.
- `smp_load_acquire()` та `smp_store_release()` — це сучасний, менш витратний спосіб синхронізувати продюсера і консьюмера без важких повних бар'єрів.
