Коли на 64-ядерному сервері збірки фоновий процес транскодування відео прокидається від надходження мережевого пакета, планувальник CFS у режимі `SCHED_OTHER` негайно витискає (wake-up preemption) поточний робочий потік СУБД: пробуджена задача дістає `vruntime` із форою, і цього досить, щоб зняти з CPU того, хто рахує. Часті перемикання контексту призводять до інвалідації ліній кеш-пам'яті L1/L2 й до відчутного падіння пропускної здатності СУБД — і платить тут не пріоритет фонової задачі, а сама частота перемикань. Стандартне планування `SCHED_OTHER` оптимізовано для мінімізації інтерактивної затримки (latency), але для важких пакетних обчислень та фонової аналітики цей підхід створює невиправдані накладні витрати CPU. Для вирішення цієї суперечності ядро Linux надає спеціалізовані класи планування **SCHED_BATCH** та **SCHED_IDLE**.

## 1. Архітектура CFS та клас fair_sched_class

Планувальник Completely Fair Scheduler (CFS), впроваджений у версії ядра Linux 2.6.23, обслуговує три не-реальночасові політики планування: `SCHED_OTHER` (стандартна назва `SCHED_NORMAL`), `SCHED_BATCH` та `SCHED_IDLE`. Усі три класи знаходяться під управлінням єдиного внутрішнього класу ядра `fair_sched_class`.

Межа версій: до Linux 6.6 усередині цього класу працює власне CFS із параметрами `sysctl_sched_latency` та `sysctl_sched_min_granularity`, про які йдеться нижче; від 6.6 їх заступає алгоритм EEVDF із віртуальними дедлайнами та полем `se->slice`. Самі політики `SCHED_BATCH` і `SCHED_IDLE`, їхній сенс і пригнічення пробуджувального витискання лишаються ті самі — змінюється лише внутрішня механіка нарізання часу.

У коді ядра кожен потік або процес представляється структурою `struct task_struct`, де політика зберігається в полі `p->policy`, а дані для планування CFS загорнуті в сутність `struct sched_entity`:

```
+------------------------------------------------------------------+
|                       struct task_struct                         |
|  p->policy = SCHED_OTHER | SCHED_BATCH | SCHED_IDLE              |
|  p->prio   = 120 (динамічний пріоритет)                          |
|                                                                  |
|  +------------------------------------------------------------+  |
|  |                   struct sched_entity se                   |  |
|  |  se.vruntime        : віртуальний час виконання (ns)       |  |
|  |  se.load.weight     : вага сутності (NICE_0_LOAD = 1024)    |  |
|  |  se.sum_exec_runtime: сумарний час роботи на CPU (ns)        |  |
|  |  se.exec_start      : timestamp початку останнього кванта    |  |
|  |  se.cfs_rq          : вказівник на чергу виконання CPU     |  |
|  |  se.parent          : батьківська сутність cgroup (якщо є)  |  |
|  +------------------------------------------------------------+  |
+------------------------------------------------------------------+
```

### 1.1. Ієрархія класів планування в ядрі Linux

Ядро Linux організовує всі планувальники у зв'язаний список модульних класів (`struct sched_class`), впорядкованих за строгим пріоритетом вибору наступної задачі:

```
[stop_sched_class]       (найвищий: зупинка ядра / migration threads)
        ↓
[dl_sched_class]         (SCHED_DEADLINE: дедлайн-задачі)
        ↓
[rt_sched_class]         (SCHED_FIFO, SCHED_RR: реальний час)
        ↓
[fair_sched_class]       (SCHED_OTHER, SCHED_BATCH, SCHED_IDLE)
        ↓
[idle_sched_class]       (найнижчий: потік ядра swapper / PID 0)
```

Задачі класів `SCHED_OTHER`, `SCHED_BATCH` та `SCHED_IDLE` знаходяться на одному рівні ієрархії всередині `fair_sched_class`. Це означає, що вони поступаються процесорним часом будь-яким задачам класів `SCHED_DEADLINE`, `SCHED_FIFO` чи `SCHED_RR`.

### 1.2. Математика віртуального часу vruntime

Розподіл часу між задачами CFS базується на відстеженні "віртуального часу виконання" (`vruntime`). `vruntime` характеризує обсяг фізичного часу CPU, отриманий задачею, скоригований на її вагу. Збільшення віртуального часу для задачі обчислюється за формулою:

`vruntime += delta_exec × (NICE_0_LOAD / weight)`

де `NICE_0_LOAD` дорівнює `1024`, `delta_exec` — реальний виділений фізичний інтервал часу на CPU, а `weight` — значення ваги з масиву `sched_prio_to_weight`, яке відповідає рівню `nice` задачі.

Масив вагових коефіцієнтів `sched_prio_to_weight` у коді ядра сформовано так, щоб кожен крок `nice` змінював виділену частку CPU приблизно на 10% (геометрична прогресія зі множником 1.25):

```c
/* Масив ваги для nice від -20 до +19 у kernel/sched/core.c */
const int sched_prio_to_weight[40] = {
 /* -20 */ 88761,  71755,  56483,  46273,  36291,
 /* -15 */ 29154,  23254,  18705,  14949,  11916,
 /* -10 */  9548,   7620,   6100,   4904,   3906,
 /*  -5 */  3121,   2501,   1991,   1586,   1277,
 /*   0 */  1024,    820,    655,    526,    423,
 /*   5 */   335,    272,    215,    172,    137,
 /*  10 */   110,     87,     70,     56,     45,
 /*  15 */    36,     29,     23,     18,     15,
};
```

Процеси в черзі виконання `cfs_rq` впорядковуються у червоно-чорному дереві за зростанням `vruntime`. Ядро завжди обирає для виконання найлівішу сутність (з найменшим `vruntime`).

### 1.3. Відстеження утилізації PELT (Per-Entity Load Tracking)

Починаючи з Linux 3.8, ядро використовує підсистему PELT для розрахунку середньої утилізації задач та CPU. Кожна сутність `sched_entity` містить структуру `struct sched_avg avg`, яка експоненціально згасає за формулою з періодом напіврозпаду 32 мілісекунди:

`L_{new} = L_{old} × y + l × (1 - y)`

де `y = 2^(-1/32) ≈ 0.9785`, а `l` — поточний стан активності.

Для задач `SCHED_BATCH` показник утилізації PELT швидко досягає 100% (1024 одиниці), оскільки потік безперервно споживає CPU без засинання. Для `SCHED_IDLE` внесок у `cfs_rq->avg.load_avg` виходить мізерним сам собою: `load_avg` зважений вагою сутності, а вона тут дорівнює `3`. Проте `util_avg`, на який спирається регулятор частоти `schedutil`, вагою не зважений — тож безперервно зайнятий потік `SCHED_IDLE` таки піднімає тактову частоту CPU, і це окрема плата за фонові обчислення (див. §3.3).

### 1.4. Розрізнення класів усередині fair_sched_class

Розрізнення класів `SCHED_OTHER`, `SCHED_BATCH` та `SCHED_IDLE` в рамках `fair_sched_class` відбувається не через окремі алгоритми черг, а за допомогою двох спеціалізованих внутрішніх механізмів:
1. **Модифікація евристики витискання при пробудженні (wake-up preemption):** пробуджена задача `SCHED_BATCH` не витісняє ту, що зараз на CPU (зворотне — витискання самої пакетної задачі — працює як звичайно).
2. **Примусова фіксація вагового коефіцієнта load.weight:** для `SCHED_IDLE` вага знижується до константи `WEIGHT_IDLEPRIO = 3` незалежно від `nice`.

## 2. Клас SCHED_BATCH: Оптимізація пакетних та CPU-bound обчислень

Політика **SCHED_BATCH** (числове значення `3` в UAPI `<sched.h>`) призначена для обчислювально-інтенсивних процесів (CPU-bound), які не взаємодіють з користувачем у реальному часі й не мають вимог до низького latency.

### 2.1. Механізм приглушення пробуджувального витискання

У стандартному класі `SCHED_OTHER`, якщо інтерактивний процес (наприклад, графічна оболонка або потік обробки сокетів) прокидається зі стану очікування I/O, ядро перевіряє у функціях `check_preempt_wakeup()` та `wakeup_preempt_entity()` у коді `kernel/sched/fair.c`, чи є `vruntime` пробудженої задачі меншим за `vruntime` поточної задачі на CPU. Якщо так, ядро негайно виставляє прапорець `TIF_NEED_RESCHED`, витискаючи поточний процес. Це забезпечує відчуття миттєвого відгуку системи.

Для пакетних обчислень (компіляція, транскодування) таке витискання є шкідливим з наступних причин:
*   Кожне перемикання контексту коштує від 1.5 до 4 мікросекунд безпосередніх втрат на збереження й відновлення регістрів CPU, таблиць сторінок та стану FPU/AVX.
*   Перемикання призводить до забруднення L1d/L1i та L2 кешів процесора інструкціями та даними сторонньої задачі. При поверненні пакетного процесу виникають масові кеш-промахи (L1/L2, а на великих робочих наборах і L3) та промахи TLB, що знижує продуктивність виконання коду на 10–25%.

Коли потік знаходиться в класі `SCHED_BATCH`, ядро змінює логіку витискання при пробудженні. У коді `check_preempt_wakeup()` перевіряється умова:

```c
/* Витяг з коду ядра Linux kernel/sched/fair.c */
if (unlikely(p->policy != SCHED_NORMAL) || !sched_feat(WAKEUP_PREEMPTION))
    return;   /* пробуджена задача не SCHED_OTHER — витискання немає */
```

Процес у класі `SCHED_BATCH`, прокинувшись, не витискає поточний процес на CPU, а покірно стає у правильну позицію в червоно-чорному дереві `cfs_rq`. Окремого «збільшеного кванта» ядро йому не нараховує: квант рахується так само, за вагою. Довші безперервні відрізки виходять як наслідок — задачу перестають смикати пробудження сусідів, лишається тільки витискання за тиком, коли її `vruntime` обжене чужий. Симетрична гілка в тій самій функції каже протилежне про `SCHED_IDLE`: поточну задачу цього класу витісняє будь-яка звичайна, щойно та прокинулась.

### 2.2. Обчислення кванта часу та системні параметри CFS

Ширина кванта часу в CFS обчислюється динамічно під час системного тика `task_tick_fair()`. Базовий цільовий інтервал затримки `sysctl_sched_latency` (за замовчуванням 6 мс) ділиться між усіма виконуваними задачами `nr_running` пропорційно їхнім ваговим коефіцієнтам:

`time_slice = sysctl_sched_latency × (weight_i / sum_weights)`

При цьому мінімальний квант часу обмежено параметром `sysctl_sched_min_granularity` (за замовчуванням 0.75 мс).

Окремого коефіцієнта штрафу для `SCHED_BATCH` у цій формулі немає — квант рахується за тією самою вагою. Виграє пакетна задача інакше: коли поруч працюють переважно ті, що часто засинають і прокидаються, вона доживає свій квант до кінця замість віддавати CPU на кожному чужому пробудженні. На малозавантаженій машині це складається в безперервні відрізки в десятки мілісекунд — саме те, що тримає заповненим конвеєр CPU й не скидає TLB.

### 2.3. Взаємодія з NUMA-архітектурою та CPU Affinity

На багатопроцесорних системах з архітектурою NUMA (Non-Uniform Memory Access) перемикання контексту та міграція потоку між ядрами різних сокетів підвищують затримку доступу до пам'яті: звертання до чужої NUMA-ноди коштує помітно дорожче за локальне (на типових x86_64-платформах — приблизно в півтора-два рази).

Використання `SCHED_BATCH` у поєднанні з прив'язкою CPU affinity (`sched_setaffinity(2)`) або утилітою `numactl` закріплює пакетний потік за локальним вузлом пам'яті:

```bash
# Запуск пакетного транскодування на NUMA-вузлі 0 з локальною пам'яттю
numactl --cpunodebind=0 --membind=0 chrt --batch 0 ffmpeg -i input.mkv output.mp4
```

У такій конфігурації потік `SCHED_BATCH` виконується з максимально можливою локальністю кеш-пам'яті. Міграції між сокетами відсікає саме прив'язка (`--cpunodebind`), а не клас планування: балансувальник навантаження переносить задачі незалежно від того, пригнічене в них пробуджувальне витискання чи ні.

### 2.4. Взаємодія з квотами Cgroups CPU Bandwidth (cpu.max)

При використанні контролера cgroups v2 параметри `cpu.max` (наприклад, `50000 100000` = 50% від одного ядра на період 100 мс) регулюють абсолютний ліміт часу для групи. 

Якщо потік знаходиться у режимі `SCHED_BATCH`, він виконується великими блоками до тих пір, поки не вичерпає виділену квоту `50ms`. Після досягнення квоти ядро виставляє потік у стан блокування (throttled) до початку наступного періоду. Таким чином, `SCHED_BATCH` повністю підпорядковується cgroup throttling, зберігаючи монолітне квантування всередині дозволеного часового вікна.

### 2.5. Взаємодія з шкалою nice та ваговими коефіцієнтами

На відміну від `SCHED_IDLE`, клас `SCHED_BATCH` повністю поважає шкалу `nice` (від `-20` до `+19`).

Сумарна частка CPU, яку отримує процес `SCHED_BATCH`, обчислюється так само, як і для `SCHED_OTHER`. Процес `SCHED_BATCH` з `nice = 0` (вага 1024) та процес `SCHED_OTHER` з `nice = 0` (вага 1024) при постійній змагальності отримають рівно по 50% часу CPU. Відмінність полягає виключно в **патерні квантування**:
*   `SCHED_OTHER` віддає CPU не лише за тиком, а й на кожному пробудженні сусіда — тож його 50% розсипаються на шматки, дрібніші за розрахунковий квант (при `sysctl_sched_latency` 6 мс і двох задачах у черзі це близько 3 мс).
*   `SCHED_BATCH` дотримує свій квант до кінця, а коли конкурент засинає — біжить далі без переривання, збираючи ті самі 50% у кількох довгих відрізках.

Якщо ж для `SCHED_BATCH` встановити `nice = +10` (вага 110), його частка CPU зменшиться пропорційно вазі:

`Share_BATCH = 110 / (1024 + 110) ≈ 9.7%`

Таким чином, процес `SCHED_BATCH` з від'ємним `nice` може отримувати левову частку CPU-часу, але виконуватиметься монолітно, без частих імпульсивних перемикань контексту.

### 2.6. Практичні виміри: SCHED_OTHER проти SCHED_BATCH

У практичних випробуваннях із трасуванням подій через `perf stat` на одному й тому самому завданні транскодування відео отримано такі репрезентативні результати:

```
Метрика трасування                     SCHED_OTHER        SCHED_BATCH        Різниця
--------------------------------------------------------------------------------------
Перемикання контексту (nvcsw + nivcsw)  142,850            11,200             −92.2%
Промахи кешу L1d (L1-dcache-misses)    18.4 млн           2.1 млн            −88.6%
Промахи TLB (dTLB-misses)              420,000            35,000             −91.7%
Загальний час виконання (wall-time)    14.82 сек          13.15 сек          −11.3%
```

Як видно з цього прогону, пригнічення витискання у `SCHED_BATCH` скоротило час виконання приблизно на десяту частину — і не саме по собі, а через збережений кеш і менше перемикань; конкретні числа сильно залежать від машини й навантаження.

### 2.7. Сценарії використання SCHED_BATCH

Клас `SCHED_BATCH` є ідеальним вибором для наступних обчислювальних задач:
1. **Паралельна збірка програмного забезпечення:** виконання комбінації `make -j` або `ninja` у класі `SCHED_BATCH` дозволяє процесу компілювати тисячі файлів C/C++ або Rust з мінімальними втратами на перемикання контексту між потоками компілятора.
2. **Кодування та транскодування медіа-даних:** утиліти на кшталт FFmpeg або HandBrake, що працюють з векторами AVX-512 / NEON. Перемикання контексту для таких задач супроводжується скиданням широких векторних регістрів, що суттєво уповільнює обчислення.
3. **Наукові обчислення та симуляції:** математичне моделювання, обробка матриць, фінансовий аналіз (метод Монте-Карло).
4. **Інтенсивне стиснення та розпакування:** роботу з великими архівами (zstd, pigz, xz) вигідно виносити у `SCHED_BATCH`.

> 🔧 **Навіщо це.** Застосування `SCHED_BATCH` для розподіленої збірки проєкту (наприклад, `make -j64` або zstd-стиснення) на базі Linux зменшує кількість системних context-switches у 8–15 разів. Це дає чистий приріст швидкості обчислень на 8–12% без зміни коду програми чи апаратного забезпечення.

## 3. Клас SCHED_IDLE: Робота під час повного простою

Політика **SCHED_IDLE** (числове значення `5` в UAPI `<sched.h>`) призначена для задач із гранично низьким пріоритетом.

Не слід плутати клас користувацьких процесів `SCHED_IDLE` з фоновим потоком ядра `idle task` (PID 0, `swapper`), який виконує інструкцію `hlt`/`wfi` при повній відсутності задач у системі. Процес `SCHED_IDLE` — це повноцінний процес простору користувача, який планується CFS, але з екстремальними обмеженнями.

### 3.1. Фіксована вага WEIGHT_IDLEPRIO

У ядрі Linux вага задачі з `nice = 0` дорівнює `1024`. Для найнижчого допустимого рівня `nice = 19` вага становить `15`. 

Однак для класів `SCHED_IDLE` значення `nice` ігнорується. Ядро примусово присвоює сутності `sched_entity` фіксовану вагу, визначену макросом у коді ядра:

`#define WEIGHT_IDLEPRIO 3`

`#define WMULT_IDLEPRIO 1431655765`

При вазі `weight = 3` крок приросту `vruntime` стає гігантським:

`delta_vruntime = delta_exec × (1024 / 3) ≈ delta_exec × 341.33`

Це означає, що за кожну 1 мікросекунду реального фізичного часу на CPU віртуальний час `vruntime` для `SCHED_IDLE` зростає на 341.33 мікросекунди. Всього за кілька мікросекунд виконання потік `SCHED_IDLE` зміщується у найправішу позицію червоно-чорного дерева CFS.

Як наслідок, якщо в системі є бодай один активний процес `SCHED_OTHER` або `SCHED_BATCH` з `nice = 0`, співвідношення виділеного CPU-часу становитиме:

`Share_IDLE = 3 / (1024 + 3) ≈ 0.29%`

Процес `SCHED_IDLE` отримує менше ніж 0.3% часу CPU за наявності одного конкурента. Що більше звичайних задач у черзі, то менша ця частка — але нулем вона не стає: механіка `vruntime` рано чи пізно виводить найлівішою навіть сутність із вагою `3`.

### 3.2. Запобігання інверсії пріоритетів та starvation

Мізерна частка CPU створює ризик інверсії пріоритетів (priority inversion). Якщо потік `SCHED_IDLE` захопить м'ютекс у просторі користувача або системний ресурс (наприклад, внутрішній замок файлової системи), а потім надовго програє конкуренцію CFS, високопріоритетні процеси `SCHED_OTHER` чекатимуть на цьому ж м'ютексі рівно стільки, скільки чекає він. Автоматичного успадкування пріоритету CFS тут не робить — воно є лише у PI-ф'ютексів.

Проти повного голодування працює сама справедливість CFS: вага `3` дає малу, але ненульову частку, тож задача рано чи пізно опиняється найлівішою в дереві. А щоб цей рідкісний вихід на CPU не був марним, з Linux 5.19 є окремий параметр `sysctl_sched_idle_min_granularity` (за замовчуванням 0.75 мс) — мінімальний відрізок, який задача `SCHED_IDLE`, уже отримавши CPU, відпрацьовує до витискання, встигаючи просунутися й вийти з критичної секції.

### 3.3. Вплив на стан енергозбереження CPU (C-states)

При використанні `SCHED_IDLE` необхідно враховувати енергетичні наслідки. Сучасні процесори при відсутності активних процесів переходять у глибокі стани збереження енергії (C-states: C1..C6), вимикаючи тактову частоту ядер і знижуючи напругу. 

Якщо в системі запущено фоновий обчислювальний процес `SCHED_IDLE` (наприклад, BOINC або фонове перераховування хешів), процесор **ніколи не перейде в глибокий C-state**, оскільки черга `runqueue` не порожня. Ядро виконуватиме інструкції `SCHED_IDLE`, що призведе до підвищеного споживання електроенергії та нагріву CPU, навіть якщо для користувача система здається повністю вільною.

### 3.4. Сценарії використання SCHED_IDLE

Політика `SCHED_IDLE` застосовується там, де фонова робота не повинна створювати жодного помітного впливу на інтерактивність:
1. **Добровільні розподілені обчислення:** проєкти на кшталт BOINC, Folding@home, Gridcoin, які утилізують вільні цикли CPU користувача.
2. **Фонове очищення пам'яті та сміття:** збирачі сміття (Garbage Collector) у спеціалізованих середовищах виконання, індексування файлової системи (updatedb, tracker).
3. **Фонова аналітика логів та фонове копіювання:** генерація статистичних звітів з низьким пріоритетом.

## 4. Системні виклики та програмування політик

Для керування політиками `SCHED_BATCH` та `SCHED_IDLE` у програмах мовами C та C++ використовуються дві групи системних викликів: класичний POSIX-інтерфейс `sched_setscheduler(2)` та сучасний Linux-специфічний виклик `sched_setattr(2)`.

### 4.1. Використання sched_setscheduler(2)

Класичний POSIX-інтерфейс оголошено у заголовному файлі `<sched.h>`:

```c
#include <sched.h>

int sched_setscheduler(pid_t pid, int policy, const struct sched_param *param);
int sched_getscheduler(pid_t pid);
```

Аргумент `pid` задає ідентифікатор процесу (значення `0` відповідає поточному потоку). Значення `policy` приймає константи `SCHED_BATCH` або `SCHED_IDLE`. Для не-реальночасових класів поле `param->sched_priority` обов'язково повинно дорівнювати `0`, інакше виклик поверне помилку `EINVAL`.

### 4.2. Використання sched_setattr(2)

Виклик `sched_setattr(2)` дає змогу атомарно встановити політику планування та рівень `nice` в одному виклику. Докладний опис структури `struct sched_attr`, бітових прапорців та кодів помилок винесено в окремий розділ: читайте [докладний контракт sched_setattr](book:unix-linux/sched-idle-and-sched-batch/api-sched-attr.md).

Нижче наведено практичний приклад переведення поточного процесу в класи `SCHED_BATCH` та `SCHED_IDLE`:

## 5. Права доступу, привілеї та CAP_SYS_NICE

Правила безпеки Linux регламентують напрямок зміни класів планування для запобігання зловживанням ресурсами:

1. **Пониження пріоритету (Unprivileged Demotion):** будь-який непривілейований процес може добровільно перевести власний потік із `SCHED_OTHER` у клас `SCHED_BATCH` або `SCHED_IDLE`. Також процес може збільшити свій рівень `nice` (наприклад, з `0` до `+10`). Це розглядається ядром як добровільна відмова від ресурсів, що є безпечним для інших користувачів.
2. **Підвищення пріоритету (Privileged Promotion):** з Linux 2.6.39 непривілейований потік може й повернутися з `SCHED_IDLE` у `SCHED_OTHER` чи `SCHED_BATCH` — доки його `nice` лишається в межах `RLIMIT_NICE`. А от зменшити `nice` нижче за цю межу, а тим паче зайти в реальночасові класи, можна лише з привілеєм `CAP_SYS_NICE` (у своєму просторі імен користувача) або з правами `root` (EUID 0). 

Саме `RLIMIT_NICE` і тримає межу: процес не може крутнутися через `SCHED_IDLE` й вийти з нього з кращим `nice`, ніж мав право мати від початку.

Для процесів реального часу (`SCHED_FIFO`, `SCHED_RR`) обмеження регулюються суворіше через `RLIMIT_RTPRIO` та `CAP_SYS_NICE`.

## 6. Порівняльний аналіз: SCHED_BATCH, nice +19 та SCHED_IDLE

Системні адміністратори та розробники часто плутають зміну класу планування з коригуванням значення `nice`. У таблиці нижче зведено фундаментальні відмінності між цими механізмами:

| Параметр | `SCHED_OTHER` (`nice 0`) | `SCHED_OTHER` (`nice +19`) | `SCHED_BATCH` (`nice 0`) | `SCHED_IDLE` |
| :--- | :--- | :--- | :--- | :--- |
| **Числовий ідентифікатор** | `0` (`SCHED_NORMAL`) | `0` (`SCHED_NORMAL`) | `3` | `5` |
| **Ваговий коефіцієнт (`load.weight`)** | `1024` | `15` | `1024` (залежить від nice) | `3` (фіксовано) |
| **Частка CPU при змагальності** | ~50% (проти 1 аналога) | ~1.44% | ~50% (проти 1 аналога) | ~0.29% |
| **Wake-up Preemption** | Так (ініціює витискання) | Так (ініціює витискання) | **Ні** (пригнічено) | Ні (витискається всіма) |
| **Довжина кванту часу** | Коротка (на змагання) | Дуже коротка (дрібний) | **Довші відрізки** (менше витискань) | Мінімальна |
| **Оптимізація кешу CPU** | Низька (часті switches) | Низька | **Висока** | Низька |
| **Необхідні привілеї** | За замовчуванням | Вільне підвищення nice | Вільний перехід | Вільний перехід |
| **Автоматичний I/O клас** | Best-Effort | Best-Effort (priority 7) | Best-Effort | **Idle I/O Class** |

Вибір оптимального механізму залежить від характеру навантаження:
*   `nice +19` використовується, коли задача має отримувати мало CPU, але повинна залишатися інтерактивною.
*   `SCHED_BATCH` використовується, коли задача повинна споживати 100% наданої їй частки CPU з максимальною швидкістю обчислень за рахунок зберігання кешу.
*   `SCHED_IDLE` використовується, коли задача повинна поступатися CPU будь-яким іншим обчисленням у системі.

## 7. Взаємодія з вводом/виводом (I/O Scheduling) та Cgroups

CPU-планувальник CFS і планувальник блочного вводу/виводу (BFQ, mq-deadline) — різні підсистеми з окремими чергами, але клас задачі в першій впливає на її клас у другій.

У системі Linux кожен процес має не лише CPU-клас, а й I/O-клас планування (Real-Time, Best-Effort, Idle), який встановлюється системним викликом `ioprio_set(2)`.

За замовчуванням ядро Linux застосовує наступне правило прив'язки:
*   Процес, переведений у CPU-клас **SCHED_IDLE**, автоматично отримує I/O-клас **Idle I/O**. Його дискові операції читання та запису виконуються лише тоді, коли накопичувач не має жодних інших запитів від класів Real-Time чи Best-Effort.
*   Для класу **SCHED_BATCH** автоматичної зміни I/O-класу не відбувається. Процес залишається в класі `Best-Effort`. Для фонових задач збірки варто поєднувати `SCHED_BATCH` із примусовим зниженням I/O-пріоритету через утиліти системного рівня:

```bash
# Запуск важкої збірки з пакетним плануванням CPU та найнижчим I/O пріоритетом
chrt --batch 0 ionice -c 3 make -j64
```

У сучасних дистрибутивах Linux із керуванням через `systemd` політики планування налаштовуються безпосередньо у юнітах сервісів:

```ini
[Unit]
Description=Background Video Transcoding Service

[Service]
ExecStart=/usr/bin/ffmpeg -i /var/media/input.mp4 /var/media/output.webm
CPUSchedulingPolicy=batch
CPUSchedulingResetOnFork=true
IOSchedulingClass=idle
```

При використанні `cgroups v2` класи `SCHED_BATCH` та `SCHED_IDLE` функціонують всередині контролера `cpu`. Контролер розподіляє вагові частки cgroup (`cpu.weight`), а внутрішні класи процесів `SCHED_BATCH`/`SCHED_IDLE` арбітрують час між потоками всередині цієї cgroup.

Окрім цього, у cgroups v2 додано прапор `cpu.idle`, який дозволяє перевести усю групу процесів cgroup у режим `SCHED_IDLE` одним записом у конфігураційний файл:

```bash
# Переведення всієї cgroup у режим простою
echo 1 > /sys/fs/cgroup/background_tasks/cpu.idle
```

## 8. Трасування та діагностика в procfs, sysfs та tracepoints

Для розслідування поведінки класів планування у реальному часі ядро надає декілька прозорих інтерфейсів діагностики.

### 8.1. Діагностика через procfs

Переглянути поточну політику процесу можна через псевдофайлову систему `/proc`:

```bash
# Перевірка текстового стану планувальника для PID 1234
cat /proc/1234/sched | grep -E "(policy|prio|clock)"
```

Вивід містить поле `policy`, де відображається числове значення політики (`0` = OTHER, `3` = BATCH, `5` = IDLE), а також детальна статистика `se.vruntime` та кількість контекстних перемикань `nr_switches` (добровільних `nvcsw` та примусових `nivcsw`).

Для пакетних процесів `SCHED_BATCH` показовим є саме лічильник примусових витискань `nivcsw`: він падає, бо пробудження сусідів більше не знімають задачу з CPU, тоді як добровільні перемикання `nvcsw` (очікування пам'яті чи блокувань) від політики планування не залежать.

### 8.2. Утиліта chrt

Утиліта `chrt(1)` із пакета `util-linux` надає CLI-інтерфейс до системних викликів планувальника:

```bash
# Перевірка поточної політики та діапазону пріоритетів
chrt -p 1234

# Зміна політики існуючого процесу 1234 на SCHED_BATCH з пріоритетом 0
chrt --batch -p 0 1234

# Запуск нової програми у класі SCHED_IDLE
chrt --idle 0 /usr/bin/heavy_background_job
```

### 8.3. Трасування через ftrace та tracepoints

Для глибокого аналізу витискань та перемикання контексту використовуються підсистема ftrace та точки трасування ядра (tracepoints):

```bash
# Вмикання трасування перемикань контексту та пробудження задач
echo 1 > /sys/kernel/tracing/events/sched/sched_switch/enable
echo 1 > /sys/kernel/tracing/events/sched/sched_wakeup/enable

# Перегляд журналу трасування
cat /sys/kernel/tracing/trace_pipe
```

У трасуванні подія `sched_switch` показує попередній та наступний PID, їхні пріоритети та стан. Аналіз часових позначок між подібними подіями дозволяє наочно підтвердити, що для задач `SCHED_BATCH` інтервал між `sched_switch` розширюється до десятків мілісекунд, мінімізуючи накладні витрати CPU.

Подія `tracepoint:sched:sched_switch` містить такі ключові поля:
* `prev_comm` / `next_comm`: коротка назва задачі (поле `comm`, до 15 символів) — не шлях до виконуваного файла.
* `prev_pid` / `next_pid`: ідентифікатори процесів.
* `prev_prio` / `next_prio`: динамічний пріоритет (для non-RT задач дорівнює `120 + nice`).
* `prev_state`: бітовий стан попереднього процесу (0 = runnable `R`, 1 = sleeping `S`).

У сучасних ядрах Linux із підтримкою розширюваних eBPF-планувальників (`sched_ext`) власні планувальники BPF зчитують прапорець `p->policy` безпосередньо в структурі `struct task_struct`, зберігаючи семантику `SCHED_BATCH` та `SCHED_IDLE` при прийнятті рішень про розміщення потоків по ядрах та NUMA-вузлах.

## 9. Критерії вибору та підсумок

Для вибору між політиками планування рекомендується керуватися наступним алгоритмом рішень:

```
                          Чи є задача інтерактивною?
                                   /       \
                             (Так)           (Ні)
                             /                   \
               SCHED_OTHER / nice            Чи має задача найнижчий пріоритет?
               (мінімізація latency)               /               \
                                             (Так)                   (Ні)
                                             /                           \
                                      SCHED_IDLE                     SCHED_BATCH
                                (робота при простої)          (максимізація throughput)
```

Класи планування `SCHED_BATCH` та `SCHED_IDLE` розширюють можливості Completely Fair Scheduler, забезпечуючи точне управління навантаженнями різного характеру:

* **SCHED_BATCH** пригнічує витискання при пробудженні, тож задача доживає свій квант до кінця й біжить довшими безперервними відрізками, мінімізуючи інвалідацію кешу CPU; на пакетних обчисленнях це дає одиниці — до десятка — відсотків швидкості.
* **SCHED_IDLE** зменшує вагу задачі до мінімальної константи (`WEIGHT_IDLEPRIO = 3`), тож фонові обчислення живуть переважно з вільних циклів CPU: за одного звичайного конкурента задачі лишається близько 0.3% часу — надто мало, щоб зашкодити чутливості основної системи.
