# 📋 Довідник інтерфейсів обліку процесорного часу

Процесорний час Linux віддає десятьма різними дверима, і жодні двоє не збігаються повністю: у них різна одиниця (сота частка секунди, мікросекунда, наносекунда), різне охоплення (потік, процес, дочекані нащадки, контрольна група, машина) і різна природа числа — точна сума планувальника або тикова вибірка, домасштабована до тієї суми. Тут зібрано контракт кожних дверей: підпис, одиниця, охоплення, джерело — і ті пастки перетворення, на яких найчастіше ламаються монітори.

## Зведення

| Інтерфейс | Одиниця | Охоплення | Джерело числа |
|---|---|---|---|
| `times()` | тик USER_HZ (10 мс) | процес; окремо — дочекані нащадки | масштабована вибірка |
| `getrusage(RUSAGE_SELF)` | мікросекунда | процес: усі потоки, разом із завершеними | масштабована вибірка |
| `getrusage(RUSAGE_CHILDREN)` | мікросекунда | лише дочекані нащадки | масштабована вибірка |
| `getrusage(RUSAGE_THREAD)` | мікросекунда | потік, що викликав | масштабована вибірка |
| `clock_gettime(CLOCK_PROCESS_CPUTIME_ID)` | наносекунда | процес: усі потоки | точна сума планувальника |
| `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` | наносекунда | потік, що викликав | точна сума планувальника |
| `/proc/<pid>/stat`, поля 14–17, 43–44 | тик USER_HZ | група потоків + дочекані нащадки | масштабована вибірка |
| `/proc/<pid>/schedstat` | наносекунда | **один** потік (для `<pid>` — головний) | точна сума планувальника |
| `/proc/stat`, рядки `cpu*` | тик USER_HZ | ядро процесора або вся машина | вибірка (окрім `steal` і, за опції, `irq`) |
| `cpu.stat` у cgroup v2 | мікросекунда | група разом з нащадками | сума точна, поділ вибірковий |

![Кожен інтерфейс покриває свій обсяг: від одного потоку до всієї машини](/reference/unix-linux/processes/cpu-time-accounting/img/scope-map.svg)

*Кожна наступна смуга ширша: обсяг обліку розширюється згори вниз. Дві найважливіші межі тут — між потоком і процесом (потоки підсумовуються завжди) і між процесом та його нащадками (нащадки додаються лише після `wait`).*

## Одиниця, з якої все починається

Три інтерфейси з десяти віддають час у «тиках», і цю одиницю треба здобути правильно, бо вона не константа мови й не константа ядра.

```c
long tck = sysconf(_SC_CLK_TCK);      /* канонічний спосіб */
```

Друге джерело того самого числа — запис `AT_CLKTCK` у [допоміжному векторі](book:unix-linux/auxiliary-vector), який ядро кладе на стек при запуску процесу; `sysconf()` у glibc саме звідти його й бере:

```c
#include <sys/auxv.h>
unsigned long tck = getauxval(AT_CLKTCK);
```

Величина зветься USER_HZ і на всіх поширених збірках Linux дорівнює 100. Вона **не** пов'язана з HZ, з яким зібране ядро: ядро може цокати 250 або 1000 разів на секунду, назовні воно однаково перераховує все в соті частки секунди. Зашивати `100` у код — найпоширеніша помилка в цьому довіднику: на збірці з іншим USER_HZ програма мовчки покаже час, помилковий рівно в `USER_HZ / 100` разів.

> 🔧 **Навіщо це.** Ділення на неправильну сталу не падає й не логується — воно просто дає інше число. Графік, на якому служба їсть удесятеро більше процесора, ніж насправді, виглядає рівно так само справно, як правильний, і причину потім шукають де завгодно, тільки не в одному зашитому літералі.

## `times()` — найстарші двері

```c
#include <sys/times.h>

clock_t times(struct tms *buf);

struct tms {
    clock_t tms_utime;   /* власний час у режимі користувача */
    clock_t tms_stime;   /* власний час у режимі ядра        */
    clock_t tms_cutime;  /* те саме для дочеканих нащадків   */
    clock_t tms_cstime;
};
```

Усі чотири поля — у тиках USER_HZ. Охоплення `tms_utime`/`tms_stime` — увесь процес, тобто сума по всіх [потоках](book:unix-linux/threads-as-tasks), включно з тими, що вже завершилися. `tms_cutime`/`tms_cstime` наповнюються лише в мить, коли `wait()` чи `waitpid()` повертає PID нащадка, і разом із власним часом дитини туди йде накопичений нею час її власних дітей — тож [збирання нащадків](book:unix-linux/exit-wait-zombies) є умовою, без якої піддерево не потрапить в облік узагалі.

Повернене значення — теж тики, але **не** процесорний час: це настінний час від довільної точки в минулому. У Linux 2.4 і раніше точкою було завантаження системи; починаючи з 2.6 її свідомо зсунули на `(2³²/HZ) − 300` секунд **до** завантаження — так, щоб лічильник переходив через межу свого типу невдовзі після старту машини, а не через сотні днів роботи, коли причину падіння вже ніхто не пов'яже з арифметикою часу. Практичне правило звідси одне: два таких значення можна відняти одне від одного, але саме значення не можна вважати ні малим, ні додатним, ні монотонним на всій довжині життя системи.

Звідси й головна пастка виклику: `(clock_t) −1` — це і код помилки, і цілком законне значення часу; на i386 є навіть вікно секунд на сорок невдовзі після завантаження, коли `times()` віддає саме його без жодної помилки. Єдиний правильний спосіб перевірки:

```c
errno = 0;
clock_t t = times(&tm);
if (t == (clock_t)-1 && errno != 0) { /* справді помилка */ }
```

## `getrusage()` — та сама вибірка, дрібніша решітка

```c
#include <sys/resource.h>

int getrusage(int who, struct rusage *usage);
```

| `who` | Що входить | Примітка |
|---|---|---|
| `RUSAGE_SELF` | процес: сума по всіх потоках | нащадки **не** входять |
| `RUSAGE_CHILDREN` | лише завершені й дочекані нащадки | разом із їхніми дочеканими нащадками |
| `RUSAGE_THREAD` | лише потік, що викликав | з Linux 2.6.26, потребує `_GNU_SOURCE` |

Час лежить у двох полях типу `struct timeval` — секунди плюс мікросекунди:

```c
double user = ru.ru_utime.tv_sec + ru.ru_utime.tv_usec / 1e6;
double sys  = ru.ru_stime.tv_sec + ru.ru_stime.tv_usec / 1e6;
```

Решта структури — не про час, але поруч і тому варта переліку, бо половина її полів на Linux мертва. Живі: `ru_maxrss` (пік резидентної пам'яті, **кібібайти**, з Linux 2.6.32), `ru_minflt`/`ru_majflt` (легкі та важкі сторінкові збої), `ru_inblock`/`ru_oublock` (блокові операції, з 2.6.22), `ru_nvcsw`/`ru_nivcsw` (добровільні та примусові перемикання контексту). Завжди нулі: `ru_ixrss`, `ru_idrss`, `ru_isrss`, `ru_nswap`, `ru_msgsnd`, `ru_msgrcv`, `ru_nsignals` — Linux їх не веде, і перевіряти на нуль тут нема сенсу.

Окрема тонкість `RUSAGE_CHILDREN`: `ru_maxrss` там — пік **найпрожерливішої** дитини, а не сума по дереву; складати ці числа не можна.

Потрібен облік не всіх нащадків разом, а кожного окремо — його дає четвертий аргумент `wait4()`:

```c
pid_t wait4(pid_t pid, int *wstatus, int options, struct rusage *rusage);
```

Сирий системний виклик `waitid()` теж має такий аргумент — п'ятим, — але обгортка glibc його не показує. Тож через glibc облік окремого нащадка дає лише `wait4()` або старіший `wait3()`.

## `clock_gettime()` — точна сума, без вибірки

```c
#include <time.h>

int clock_gettime(clockid_t clockid, struct timespec *tp);

struct timespec { time_t tv_sec; long tv_nsec; };
```

| `clockid` | Що міряє | З версії |
|---|---|---|
| `CLOCK_PROCESS_CPUTIME_ID` | процесорний час усього процесу | Linux 2.6.12 |
| `CLOCK_THREAD_CPUTIME_ID` | процесорний час потоку, що викликав | Linux 2.6.12 |

Це єдині двері в переліку, за якими лежить `sum_exec_runtime` — величина, яку [планувальник](book:unix-linux/scheduler-model) накопичує вимірюванням, а не опитуванням. Тому число тут одне: поділу на `user` і `sys` ці годинники не знають і дати не можуть. Обидва на Linux не встановлюються — `clock_settime()` на них поверне `EINVAL`.

Ці ж ідентифікатори приймає `timer_create()`, тож на процесорному часі можна звести [таймер](book:unix-linux/process-timers), який спрацює після заданої кількості спожитих наносекунд, а не за настінним годинником.

### Годинник чужого процесу або чужого потоку

```c
int clock_getcpuclockid(pid_t pid, clockid_t *clockid);          /* 0 / −1 і errno */
int pthread_getcpuclockid(pthread_t thread, clockid_t *clockid); /* повертає КОД помилки */
```

Помилки `clock_getcpuclockid()`: `ESRCH` — процесу з таким PID немає; `EPERM` — доступу до його годинника нема; `ENOSYS` — ядро не вміє віддавати годинник чужого процесу. У `pthread_getcpuclockid()` свої два: `ESRCH` — такого потоку немає, `ENOENT` — система не має потокових процесорних годинників. Друга функція, за звичаєм `pthread_*`, повертає номер помилки прямо, а `errno` не чіпає.

Отриманий `clockid` — не маленьке число з переліку, а закодована структура:

![Ідентифікатор процесорного годинника: інвертований PID у старших бітах, тип — у трьох молодших](/reference/unix-linux/processes/cpu-time-accounting/img/clockid-bits.svg)

*Три молодші біти кажуть, чий і який це годинник; решта — PID, інвертований побітово. Саме інверсія робить усі такі ідентифікатори від'ємними, і ядро відрізняє їх від звичайних годинників за самим знаком.*

```
clockid = ((~pid) << 3) | which          для годинника процесу
clockid = ((~tid) << 3) | which | 4      для годинника потоку

which:  0 — PROF (user+sys), 1 — VIRT (лише user), 2 — SCHED (точна сума)

pid = 1234, which = 2:
  ~1234                 = -1235
  -1235 << 3            = -9880
  -9880 | 2             = -9878     ← саме це поверне clock_getcpuclockid()
```

Практичний наслідок: `clockid` не можна ні використовувати як індекс, ні порівнювати з іменованими сталими — це число від'ємне й залежить від PID. Виклик `clock_getcpuclockid(0, &cid)` дає той самий годинник, що й стала `CLOCK_PROCESS_CPUTIME_ID`, — але позначений іншим числом: стала дорівнює 2, а закодований ідентифікатор власного процесу — −6.

## `/proc/<pid>/stat` — заморожений порядок полів

Файл — один рядок чисел, розділених пробілами. Порядок полів заморожений як частина ABI: нові поля дописують у кінець, наявні ніколи не переставляють.

| № | Поле | Формат | Одиниця | Що це |
|---|---|---|---|---|
| 14 | `utime` | `%lu` | тик USER_HZ | власний час у режимі користувача |
| 15 | `stime` | `%lu` | тик USER_HZ | власний час у режимі ядра |
| 16 | `cutime` | `%ld` | тик USER_HZ | те саме для дочеканих нащадків |
| 17 | `cstime` | `%ld` | тик USER_HZ | — |
| 22 | `starttime` | `%llu` | тик USER_HZ | мить старту процесу, від завантаження системи |
| 42 | `delayacct_blkio_ticks` | `%llu` | тик USER_HZ | сумарна затримка на блоковому вводі-виводі |
| 43 | `guest_time` | `%lu` | тик USER_HZ | час виконання віртуального процесора гостя |
| 44 | `cguest_time` | `%ld` | тик USER_HZ | те саме для дочеканих нащадків |

Чотири речі, які тут ламають наївний розбір.

**Поле 2 не можна пропустити пробілом.** Ім'я програми стоїть у круглих дужках і може містити і пробіли, і самі дужки — `(my )weird( prog)` цілком законне. Єдиний надійний спосіб — знайти **останню** закривну дужку в рядку й рахувати поля від неї:

:::tabs
```c
char *p = strrchr(line, ')');    /* далі: пробіл, потім поле 3 (state) */
```
```cpp
auto pos = line.rfind(')');      // далі: пробіл, потім поле 3 (state)
```
:::

**`starttime` — не процесорний час.** Це мить старту, виміряна в тих самих тиках від завантаження системи; щоб дістати вік процесу в секундах, беруть перше число з `/proc/uptime` й віднімають `starttime / tck`.

**`guest_time` уже сидить усередині `utime`.** Ядро додає тик гостя і в `p->utime`, і в `p->gtime` одночасно, тож `utime + guest_time` — це подвійний облік, а не «повний час».

**Файл групи й файл потоку — різні речі.** `/proc/<pid>/stat` віддає суму по всій групі потоків, `/proc/<pid>/task/<tid>/stat` — час одного потоку. А от `cutime`/`cstime` живуть у спільній структурі групи, тому у файлі окремого потоку вони показують те саме, що й у файлі процесу.

Про решту вмісту [файлової системи `/proc`](book:unix-linux/proc-filesystem) — окремо; тут важливо лише те, що цей конкретний файл читають за номером поля, а всі інші згадані нижче — за ключем.

## `/proc/<pid>/schedstat` — сирий лічильник планувальника

Три числа в один рядок, без назв:

```
15340238771 2274931883 41827
    │            │        └── скільки разів задача отримувала процесор
    │            └─────────── наносекунди очікування в черзі готових
    └──────────────────────── наносекунди на процесорі (sum_exec_runtime)
```

Файл існує за `CONFIG_SCHED_INFO`. Перше число планувальник веде завжди — воно потрібне йому для власної роботи; друге й третє наповнюються лише коли ввімкнена статистика планувальника (`CONFIG_SCHEDSTATS` плюс перемикач `kernel.sched_schedstats`), інакше там стоять нулі.

Пастка тут одна, зате велика: **це числа однієї задачі, а не групи**. `/proc/<pid>/schedstat` показує час головного потоку — і на програмі, де вся робота розкладена по пулу робітників, там буде майже нуль при цілком завантажених ядрах. Правильний спосіб — або підсумувати `/proc/<pid>/task/*/schedstat`, або взяти `CLOCK_PROCESS_CPUTIME_ID`, який зробить те саме підсумовування всередині ядра.

## `/proc/stat` — погляд згори

Рядок `cpu` — уся машина; рядки `cpu0`, `cpu1`, … — окремі ядра процесора. Десять граф, усі в тиках USER_HZ, порядок фіксований:

| № | Графа | З версії | Що це |
|---|---|---|---|
| 1 | `user` | — | режим користувача |
| 2 | `nice` | — | режим користувача зі зниженим [пріоритетом](book:unix-linux/priority-nice-realtime) |
| 3 | `system` | — | режим ядра |
| 4 | `idle` | — | простій |
| 5 | `iowait` | 2.5.41 | простій, коли хтось у черзі цього ядра чекав на ввід-вивід |
| 6 | `irq` | 2.6.0 | обробка апаратних переривань |
| 7 | `softirq` | 2.6.0 | обробка відкладених переривань |
| 8 | `steal` | 2.6.11 | час, забраний гіпервізором у цієї віртуальної машини |
| 9 | `guest` | 2.6.24 | виконання віртуального процесора гостя |
| 10 | `guest_nice` | 2.6.33 | те саме для гостя зі зниженим пріоритетом |

Завантаження рахують за двома зрізами з різницею приростів, і саме там ховаються три пастки.

**`guest` і `guest_nice` уже враховані.** Перша — всередині `user`, друга — всередині `nice`. Сума всіх десяти граф дає завищений результат, і на хазяїні з віртуальними машинами монітор покаже понад сто відсотків. Правильні формули:

```
total = user + nice + system + idle + iowait + irq + softirq + steal
busy  = total − idle − iowait
завантаження = Δbusy / Δtotal
```

**`iowait` може зменшитися.** Ця графа приписана конкретному ядру процесора, хоча задача, що чекає, не виконується на жодному; коли вона прокидається на іншому ядрі, число здатне піти вниз. Різниця двох зрізів тоді від'ємна — і код, який ділить її на `Δtotal`, видає безглуздя. Або обробляйте від'ємний приріст як нуль, або не використовуйте цю графу зовсім: реальний тиск від вводу-виводу видно з [обліку затримок і PSI](book:unix-linux/load-and-pressure), а не звідси.

**`steal` — не робота цієї машини.** Він показує час, коли віртуальний процесор був готовий, але фізичного ядра не отримав. У «зайнятий» час його включають, бо машина в ці миті хотіла працювати й не могла; у «спожитий процесор» — ні, бо процесора вона не бачила.

## `cpu.stat` у cgroup v2

Файл є в кожній [контрольній групі](book:unix-linux/cgroups), навіть коли контролер `cpu` не ввімкнений, і читається **за ключем**, а не за позицією — набір ключів росте від версії до версії.

```
usage_usec 48213904
user_usec  41003117
system_usec 7210787
nr_periods 1204
nr_throttled 37
throttled_usec 918233
```

| Ключ | Одиниця | Умова наявності |
|---|---|---|
| `usage_usec` | мкс | завжди |
| `user_usec` | мкс | завжди |
| `system_usec` | мкс | завжди |
| `nr_periods` | лічильник | контролер увімкнений |
| `nr_throttled` | лічильник | контролер увімкнений |
| `throttled_usec` | мкс | контролер увімкнений |
| `nr_bursts` | лічильник | контролер увімкнений |
| `burst_usec` | мкс | контролер увімкнений |

Три перші ключі рахують **усі** процеси групи разом з усіма її нащадками — облік у cgroup v2 рекурсивний, батько бачить піддерево цілком. П'ять інших стосуються лише задач звичайного класу планування й описують обмеження пропускної здатності, а не облік.

Природа чисел тут різна: `usage_usec` — точна сума, накопичена з тих самих приростів, що й `sum_exec_runtime`, а `user_usec` і `system_usec` — та сама пропорція від тиків, домасштабована до цієї суми. Для кореневої групи всі три беруться із загальносистемних лічильників, тобто описують машину так само, як рядок `cpu` у `/proc/stat`.

У cgroup v1 ту саму роль відігравали `cpuacct.usage` (наносекунди) і `cpuacct.stat` — і ось там одиниця знову тики USER_HZ, а не мікросекунди. Переносячи код між версіями, множник доводиться міняти.

## Перетворення в секунди — одним поглядом

```
тик USER_HZ  →  t / sysconf(_SC_CLK_TCK)        НЕ / 100
мікросекунда →  tv_sec + tv_usec / 1e6
наносекунда  →  tv_sec + tv_nsec / 1e9
```

Роздільність, з якою число доходить до вас, — це роздільність решета, а не вимірювання: усередині ядро скрізь рахує наносекундами. Тому `/proc/<pid>/stat` не відрізнить процес, що спожив 3 мс, від процесу, що спожив 9 мс — обидва там нулі, — тоді як `CLOCK_PROCESS_CPUTIME_ID` покаже і те, й те.

## Одна програма, яка читає всі двері

:::tabs
```c
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <unistd.h>
#include <sys/times.h>
#include <sys/resource.h>

static double cpu_seconds(clockid_t c)
{
    struct timespec t;
    if (clock_gettime(c, &t) != 0)
        return -1.0;
    return t.tv_sec + t.tv_nsec / 1e9;
}

int main(void)
{
    const double tck = (double)sysconf(_SC_CLK_TCK);   /* НЕ 100 напам'ять */

    /* 1. times() — тики USER_HZ; процес окремо, дочекані нащадки окремо */
    struct tms tm;
    errno = 0;
    if (times(&tm) == (clock_t)-1 && errno != 0) {
        perror("times");
        return 1;
    }
    printf("times    user %.2f  sys %.2f  нащадки %.2f\n",
           tm.tms_utime / tck, tm.tms_stime / tck,
           (tm.tms_cutime + tm.tms_cstime) / tck);

    /* 2. getrusage() — мікросекунди, той самий поділ, дрібніше решето */
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    printf("rusage   user %.6f  sys %.6f\n",
           ru.ru_utime.tv_sec + ru.ru_utime.tv_usec / 1e6,
           ru.ru_stime.tv_sec + ru.ru_stime.tv_usec / 1e6);

    /* 3. процесорні годинники — наносекунди, точна сума без поділу */
    printf("clock    процес %.9f  потік %.9f\n",
           cpu_seconds(CLOCK_PROCESS_CPUTIME_ID),
           cpu_seconds(CLOCK_THREAD_CPUTIME_ID));

    /* 4. schedstat — наносекунди, але ЛИШЕ цей потік */
    unsigned long long run = 0, wait = 0;
    unsigned long slices = 0;
    FILE *f = fopen("/proc/self/schedstat", "r");
    if (f) {
        if (fscanf(f, "%llu %llu %lu", &run, &wait, &slices) == 3)
            printf("sched    на процесорі %.9f  у черзі %.9f  вибрано %lu разів\n",
                   run / 1e9, wait / 1e9, slices);
        fclose(f);
    }

    /* 5. /proc/self/stat — тики USER_HZ; comm може містити дужки й пробіли */
    char buf[4096];
    size_t n = 0;
    f = fopen("/proc/self/stat", "r");
    if (f) {
        n = fread(buf, 1, sizeof buf - 1, f);
        fclose(f);
    }
    buf[n] = '\0';

    char *p = strrchr(buf, ')');          /* кінець поля 2 */
    if (p) {
        unsigned long ut = 0, st = 0;
        /* p+2 — поле 3 (state); далі 5 int, 1 unsigned, 4 lu, і аж тоді 14 і 15 */
        if (sscanf(p + 2, "%*c %*d %*d %*d %*d %*d %*u %*lu %*lu %*lu %*lu %lu %lu",
                   &ut, &st) == 2)
            printf("stat     user %.2f  sys %.2f\n", ut / tck, st / tck);
    }
    return 0;
}
```

```cpp
#include <iostream>
#include <fstream>
#include <sstream>
#include <string>
#include <iomanip>
#include <cerrno>
#include <ctime>
#include <unistd.h>
#include <sys/times.h>
#include <sys/resource.h>

static double cpu_seconds(clockid_t c) {
    timespec t{};
    if (clock_gettime(c, &t) != 0) return -1.0;
    return t.tv_sec + t.tv_nsec / 1e9;
}

int main() {
    const double tck = static_cast<double>(sysconf(_SC_CLK_TCK));

    // 1. times() — тики USER_HZ
    tms tm{};
    errno = 0;
    if (times(&tm) == static_cast<clock_t>(-1) && errno != 0) {
        std::perror("times");
        return 1;
    }
    std::cout << std::fixed << std::setprecision(2)
              << "times    user " << (tm.tms_utime / tck)
              << "  sys " << (tm.tms_stime / tck)
              << "  нащадки " << ((tm.tms_cutime + tm.tms_cstime) / tck) << "\n";

    // 2. getrusage() — мікросекунди
    rusage ru{};
    getrusage(RUSAGE_SELF, &ru);
    std::cout << std::setprecision(6)
              << "rusage   user " << (ru.ru_utime.tv_sec + ru.ru_utime.tv_usec / 1e6)
              << "  sys " << (ru.ru_stime.tv_sec + ru.ru_stime.tv_usec / 1e6) << "\n";

    // 3. процесорні годинники — наносекунди
    std::cout << std::setprecision(9)
              << "clock    процес " << cpu_seconds(CLOCK_PROCESS_CPUTIME_ID)
              << "  потік " << cpu_seconds(CLOCK_THREAD_CPUTIME_ID) << "\n";

    // 4. schedstat
    if (std::ifstream f{"/proc/self/schedstat"}; f.is_open()) {
        unsigned long long run = 0, wait = 0;
        unsigned long slices = 0;
        if (f >> run >> wait >> slices) {
            std::cout << "sched    на процесорі " << (run / 1e9)
                      << "  у черзі " << (wait / 1e9)
                      << "  вибрано " << slices << " разів\n";
        }
    }

    // 5. /proc/self/stat
    if (std::ifstream f{"/proc/self/stat"}; f.is_open()) {
        std::string line;
        if (std::getline(f, line)) {
            auto pos = line.rfind(')');
            if (pos != std::string::npos && pos + 2 < line.size()) {
                std::istringstream iss(line.substr(pos + 2));
                char state;
                int ppid, pgrp, session, tty, tpgid;
                unsigned flags;
                unsigned long minflt, cminflt, majflt, cmajflt, ut, st;
                if (iss >> state >> ppid >> pgrp >> session >> tty >> tpgid
                        >> flags >> minflt >> cminflt >> majflt >> cmajflt >> ut >> st) {
                    std::cout << std::setprecision(2)
                              << "stat     user " << (ut / tck) << "  sys " << (st / tck) << "\n";
                }
            }
        }
    }
    return 0;
}
```

## Що обирати під задачу

| Питання | Чим міряти | Чому саме ним |
|---|---|---|
| Чи стала функція швидшою | `CLOCK_THREAD_CPUTIME_ID` | точна сума, не залежить від сусіднього коду |
| Скільки процесора з'їв процес разом з потоками | `CLOCK_PROCESS_CPUTIME_ID` | те саме, підсумоване ядром |
| Скільки з'їла збірка з усіма компіляторами | `getrusage(RUSAGE_CHILDREN)` | єдиний, хто рахує дочеканих нащадків |
| Скільки з'їв кожен нащадок окремо | `wait4()` з `struct rusage` | облік приходить разом зі статусом виходу |
| Скільки з'їла служба разом з усім піддеревом | `cpu.stat` групи | рекурсивно й без вимоги збирати нащадків |
| Скільки часу задача чекала в черзі | `/proc/<pid>/task/*/schedstat` | єдине джерело часу очікування |
| Завантаження машини для графіка | `/proc/stat`, два зрізи | усі ядра й усі категорії разом |
| Чи не вперлася служба в квоту | `nr_throttled`, `throttled_usec` | облік тут ні до чого — це обмеження |

Спільне правило під усім переліком: поділ на `user` і `sys` — оцінка, а сума — вимір. Тому будь-яке рішення, що спирається саме на пропорцію режимів, потребує довгого прогону, а рішення про загальний час можна ухвалювати з мілісекундного відрізка. Тієї самої логіки тримається й ядро: ліміт процесорного часу [`RLIMIT_CPU`](book:unix-linux/resource-limits) перевіряють проти `user + sys` разом, а не проти жодної з половин окремо.
