# 📋 Контракт родини wait: підписи, прапорці, siginfo_t і помилки

П'ять викликів роблять ту саму справу — забирають у ядра результат дитини, — але беруть різні аргументи, приймають різні набори прапорців і віддають відповідь у двох несумісних формах. Нижче зібрано повний контракт: підписи, словник цілей, обидві маски `options`, поля `siginfo_t`, поля `struct rusage` і всі помилки — з поясненням, звідки кожне обмеження береться, бо більшість із них не сваволя, а прямий наслідок того, як виклики росли один з одного.

## П'ять підписів

```c
#include <sys/wait.h>

pid_t wait(int *_Nullable wstatus);
pid_t waitpid(pid_t pid, int *_Nullable wstatus, int options);
int   waitid(idtype_t idtype, id_t id, siginfo_t *infop, int options);

/* для wait3/wait4 у glibc потрібен _DEFAULT_SOURCE
   (до glibc 2.19 — _BSD_SOURCE), і додатковий заголовок */
#include <sys/resource.h>

pid_t wait3(int *_Nullable wstatus, int options,
            struct rusage *_Nullable rusage);
pid_t wait4(pid_t pid, int *_Nullable wstatus, int options,
            struct rusage *_Nullable rusage);
```

| виклик | стандарт | кого чекає | форма відповіді | облік | повертає |
|---|---|---|---|---|---|
| `wait` | POSIX | будь-яку дитину | слово `int` | — | pid > 0, або −1 |
| `waitpid` | POSIX | за словником `pid` | слово `int` | — | pid > 0, 0 при `WNOHANG`, −1 |
| `waitid` | POSIX | за парою (`idtype`, `id`) | `siginfo_t` | — | **0 в обох випадках**, −1 |
| `wait3` | 4.3BSD, зі SUSv3 прибрано | будь-яку дитину | слово `int` | `rusage` | як `waitpid` |
| `wait4` | 4.3BSD, поза стандартом | за словником `pid` | слово `int` | `rusage` | як `waitpid` |

Останній стовпчик — перша пастка. Три «слівні» виклики розрізняють «забрав дитину» і «нікого готового немає» самим поверненим числом: у першому випадку це номер, у другому — нуль. `waitid` повертає нуль **і** тоді, і тоді, бо номер він кладе не в повернене значення, а в `si_pid`. Тому перевірка успіху в нього інша, і саме на цьому найчастіше ламається код, переписаний із `waitpid` механічно.

Тотожності, з яких видно, що справді нову можливість додає лише `waitid`:

```
wait(&st)                 ≡  waitpid(-1, &st, 0)
waitpid(pid, &st, opts)   ≡  wait4(pid, &st, opts, NULL)
wait3(&st, opts, &ru)     ≡  wait4(-1, &st, opts, &ru)
```

Скільки з цього — справжні системні виклики? На x86-64 ядро має рівно два: `wait4` і `waitid`. Окремого `waitpid` у ядрі немає — він лишився номером 7 у 32-бітному i386 як спадок, і на 64-бітних архітектурах його не заводили. Тому всі чотири «слівні» форми glibc зводить до `wait4`; там, де архітектура успадкованих викликів не має, — до `waitid`. Вибір між `wait`, `waitpid` і `wait4` не коштує нічого: це три підписи над одним викликом, і різняться вони лише зручністю ([libc як шлюз до ядра](book:unix-linux/libc-as-gateway)).

## Кого чекати: перший аргумент

У `waitpid`, `wait4` і `kill` перший аргумент читають однаковим знаковим словником — і ця спільність не випадкова, а свідома: обидва звертаються до тієї самої цілі.

| `pid` | кого шукати |
|---|---|
| `> 0` | саме цю дитину |
| `0` | будь-яку дитину з групи процесів того, хто чекає (група береться на момент виклику) |
| `-1` | будь-яку дитину |
| `< -1` | будь-яку дитину з групи процесів `-pid` |

Окремий випадок: `pid == INT_MIN` дає `ESRCH`, бо це єдине число, яке не можна заперечити — `-INT_MIN` не поміщається в `int`.

`waitid` те саме злиття розводить на два аргументи: різновид цілі окремо, число окремо. Плата — багатослівність, виграш — місце під різновиди, яких у знаковому словнику просто немає куди вписати.

| `idtype` | значення | `id` | обмеження |
|---|---|---|---|
| `P_ALL` | 0 | ігнорується | — |
| `P_PID` | 1 | номер дитини | `id ≤ 0` → `EINVAL` |
| `P_PGID` | 2 | номер групи процесів | `id < 0` → `EINVAL`; `id == 0` означає власну групу того, хто чекає (від Linux 5.4) |
| `P_PIDFD` | 3 | дескриптор процесу | від Linux 5.4; `id < 0` → `EINVAL` |

`P_PIDFD` — те, заради чого `waitid` варто знати навіть тому, хто зі статусами працює через макроси. Дескриптор процесу вказує на конкретну дитину назавжди, і повторно використаний номер під нього не підставиться ([PID і дерево процесів](book:unix-linux/pid-and-hierarchy)). Прапорець `O_NONBLOCK` на такому дескрипторі діє й тут: якщо дитина ще жива, виклик віддасть `EAGAIN` замість того, щоб заблокуватися.

## Прапорці: одне слово, дві маски

`options` в усіх п'яти викликів — те саме 32-бітне слово з тими самими значеннями бітів. Але ядро перевіряє його **двома різними масками**, і зайвий біт не ігнорується, а відхиляється.

![Вісім прапорців із їхніми бітами; під кожним — що він вмикає, і два ряди: чи приймає його маска wait4 та маска waitid; WEXITED і WNOWAIT позначені як EINVAL для wait4](/reference/unix-linux/processes/exit-wait-zombies/img/wait-options-masks.svg)

*Дві маски — це два покоління інтерфейсу в одному аргументі: біти 0x4 і 0x1000000 з'явилися вже разом із `waitid`, і старий виклик про них нічого не знає.*

Перевірка в ядрі записана буквально так:

```c
/* kernel_wait4() — маска для wait, waitpid, wait3, wait4 */
if (options & ~(WNOHANG|WUNTRACED|WCONTINUED|__WNOTHREAD|__WCLONE|__WALL))
        return -EINVAL;

/* kernel_waitid() — маска для waitid, плюс вимога вибрати подію */
if (options & ~(WNOHANG|WNOWAIT|WEXITED|WSTOPPED|WCONTINUED|
                __WNOTHREAD|__WCLONE|__WALL))
        return -EINVAL;
if (!(options & (WEXITED|WSTOPPED|WCONTINUED)))
        return -EINVAL;
```

Звідси — усе, що варто знати про поєднання прапорців.

**`WEXITED` (0x4) і `WNOWAIT` (0x1000000) законні тільки в `waitid`.** Виклик `waitpid(pid, &st, WEXITED)` не «просить повідомити про мертвих», а просто не працює: біт 0x4 не входить у маску `wait4`, і замість статусу повернеться −1 з `EINVAL`. Помилка виглядає нешкідливо, бо назва прапорця описує саме те, чого ти хочеш.

**`WUNTRACED` і `WSTOPPED` — один і той самий біт 0x2 під двома іменами.** Перше ім'я прийшло з берклійського `waitpid`, друге — з `waitid`; у заголовку так і написано: `#define WSTOPPED WUNTRACED`. Плутанина безпечна — обидва працюють в обох викликах, — але тримати їх за різні речі не варто.

**`waitid` без жодного з `WEXITED`, `WSTOPPED`, `WCONTINUED` — це `EINVAL`.** Мовчазної домовленості «за замовчуванням чекаю на смерть» тут немає: подію треба вибрати явно. Найчастіший правильний набір — `WEXITED`, найчастіша помилка — передати самий `WNOHANG`.

**`__WALL` перекриває `__WCLONE`.** Ядро перевіряє їх у такому порядку:

```c
static int eligible_child(struct wait_opts *wo, bool ptrace, struct task_struct *p)
{
        if (!eligible_pid(wo, p))
                return 0;
        if (ptrace || (wo->wo_flags & __WALL))
                return 1;
        if ((p->exit_signal != SIGCHLD) ^ !!(wo->wo_flags & __WCLONE))
                return 0;
        return 1;
}
```

Останній рядок і є весь зміст `__WCLONE`: без нього беруть лише дітей, що шлють при смерті саме `SIGCHLD`, з ним — лише тих, що шлють щось інше або нічого. «Щось інше» задають при створенні через `clone` ([vfork, posix_spawn і clone](book:unix-linux/spawn-alternatives)). Коли ж стоїть `__WALL`, до цієї перевірки не доходить узагалі, і `__WCLONE` нічого не звужує.

**`__WNOTHREAD` звужує пошук до дітей самого потоку** замість усієї групи потоків — тобто вимикає поведінку, яка в Linux є типовою від версії 2.4 ([потоки як задачі ядра](book:unix-linux/threads-as-tasks)).

**`WNOHANG` і `WNOWAIT` сумісні** й разом дають рівно «подивитися, чи є готові, нічого не забираючи й не блокуючись» — єдиний спосіб опитати стан дитини, не втративши права забрати статус пізніше.

Ще одна асиметрія, якої в масках не видно: `WUNTRACED` керує лише **нетрасованими** дітьми. Зупинку дитини, яку трасують, повідомляють у будь-якому разі, хоч би що стояло в `options` — саме на цьому тримається робота налагоджувача ([ptrace: на чому тримається трасування](book:unix-linux/ptrace-model)).

## Макроси розбору статусу: коли який чинний

Макроси не взаємозамінні й не всі чинні одночасно: спершу питають розрізнювальний макрос, і лише тоді — той, що дістає число.

| макрос | що дає | чинний, коли | звідки береться |
|---|---|---|---|
| `WIFEXITED(st)` | вийшов сам | завжди можна питати | POSIX |
| `WEXITSTATUS(st)` | код виходу, 0…255 | `WIFEXITED` істинний | POSIX |
| `WIFSIGNALED(st)` | убито сигналом | завжди можна питати | POSIX |
| `WTERMSIG(st)` | номер сигналу-вбивці | `WIFSIGNALED` істинний | POSIX |
| `WCOREDUMP(st)` | чи робилася спроба дампа | `WIFSIGNALED` істинний | у glibc потрібен `_DEFAULT_SOURCE`; у POSIX лише з видання 2024 |
| `WIFSTOPPED(st)` | зупинено | завжди; істинний лише якщо просили `WUNTRACED` або дитину трасують | POSIX |
| `WSTOPSIG(st)` | номер сигналу зупинки | `WIFSTOPPED` істинний | POSIX |
| `WIFCONTINUED(st)` | відновлено `SIGCONT` | істинний лише якщо просили `WCONTINUED` | від Linux 2.6.10 |

Два рядки тут — про переносність, а не про семантику. `WCOREDUMP` десятиліттями лишався берклійським розширенням поза стандартом, і в glibc його ховає ознака `__USE_MISC`: без `_DEFAULT_SOURCE` код із ним просто не збереться ([POSIX: що саме стандартизовано](book:unix-linux/posix-standard)). Чи справді після сигналу лишився файл — питання окреме: макрос каже, що ядро спробувало, а не що вийшло ([аварійний дамп](book:unix-linux/core-dump)).

Рядок про `WIFCONTINUED` варто прочитати як застереження: якщо `WCONTINUED` не просили, дитина, відновлена `SIGCONT`, не спричинить повернення з `wait` узагалі, і макрос ніколи не стане істинним ([керування завданнями](book:unix-linux/job-control)).

## siginfo_t, який заповнює waitid

Ядро пише в структуру рівно **шість полів** і не чіпає решти:

| поле | що в ньому |
|---|---|
| `si_signo` | `SIGCHLD`; нуль, якщо при `WNOHANG` нікого готового не було |
| `si_errno` | завжди 0 |
| `si_code` | причина, один із `CLD_*` |
| `si_pid` | номер дитини |
| `si_uid` | справжній UID дитини, перекладений у простір імен користувачів того, хто чекає |
| `si_status` | число, зміст якого визначає `si_code` |

| `si_code` | значення | що сталося | що в `si_status` |
|---|---|---|---|
| `CLD_EXITED` | 1 | вийшла сама | код виходу, 0…255 |
| `CLD_KILLED` | 2 | убито сигналом | номер сигналу |
| `CLD_DUMPED` | 3 | убито, дамп записувався | номер сигналу |
| `CLD_TRAPPED` | 4 | трасована дитина спинилася на пастці | номер сигналу |
| `CLD_STOPPED` | 5 | зупинено сигналом | номер сигналу зупинки |
| `CLD_CONTINUED` | 6 | відновлено | `SIGCONT` |

Ось де видно виграш: те, що в слові `int` розкидано по двох байтах і дістається трьома парами макросів, тут лежить у двох звичайних цілих полях. `CLD_KILLED` і `CLD_DUMPED` розділені як окремі причини, а не як біт усередині числа. Питати `si_status` можна без попередньої перевірки — зіпсутого значення там не буває, лише інакше витлумачене.

Натомість непричесані поля — джерело двох тонкощів.

Перша: **структуру треба обнулити самому**. Ядро пише шість полів, і все, що лежить у `siginfo_t` поза ними, лишається сміттям зі стека. Зокрема `si_utime` й `si_stime`, які приходять заповненими в обробнику `SIGCHLD`, після `waitid` не означають нічого.

Друга: **як зрозуміти, що `WNOHANG` нікого не знайшов**. Повернене значення однакове в обох випадках, тож дивитися треба на `si_pid`. Linux у цьому разі чесно записує нулі в усі шість полів, але POSIX додав таку вимогу лише технічним виправленням 2013 року, і не всі системи їй відповідають. Переносний спосіб один: обнулити `si_pid` **перед** викликом і перевірити його після.

## rusage: що саме віддають wait3 і wait4

```c
struct rusage {
    struct timeval ru_utime;  /* час у власному коді          */
    struct timeval ru_stime;  /* час у ядрі                   */
    long   ru_maxrss;         /* пік резидентної пам'яті, КіБ */
    long   ru_minflt;         /* легкі промахи сторінок       */
    long   ru_majflt;         /* важкі промахи сторінок       */
    long   ru_inblock;        /* блокові читання              */
    long   ru_oublock;        /* блокові записи               */
    long   ru_nvcsw;          /* добровільні перемикання      */
    long   ru_nivcsw;         /* примусові перемикання        */
    /* нижче — поля, які Linux не веде: у них завжди нуль */
    long   ru_ixrss, ru_idrss, ru_isrss, ru_nswap;
    long   ru_msgsnd, ru_msgrcv, ru_nsignals;
};
```

Порядок полів у справжньому заголовку інший — тут вони перегруповані, щоб було видно межу між тими сімома, що завжди нульові, і рештою ([облік процесорного часу](book:unix-linux/cpu-time-accounting), [облік пам'яті](book:unix-linux/memory-accounting)).

Одна властивість цих чисел не очевидна з підпису. Забираючи зомбі, ядро кличе внутрішній облік із режимом `RUSAGE_BOTH` — тобто в структуру потрапляє час **самої дитини плюс тих онуків, яких вона встигла прибрати сама**. Дитина, що не кликала `wait` на своїх дітей, віддасть менше, ніж насправді з'їло її піддерево: непозбираний онук так і не додав свого рахунку нікому.

Ще одна асиметрія: раціон і статус разом віддають лише `wait3`/`wait4`, тобто у формі слова `int`. Справжній системний виклик `waitid` теж має п'ятий аргумент типу `struct rusage *`, але обгортка glibc передає туди `NULL` і назовні його не показує. Хто хоче водночас `siginfo_t` і облік, мусить кликати ядро прямо:

```c
#include <sys/syscall.h>
#include <unistd.h>

siginfo_t si = {0};
struct rusage ru = {0};
long r = syscall(SYS_waitid, P_ALL, 0, &si, WEXITED, &ru);
```

## Помилки

| помилка | коли |
|---|---|
| `ECHILD` | дітей немає взагалі; або немає саме тієї, про яку питали; або той, хто чекає, поставив `SIGCHLD` у `SIG_IGN` чи `SA_NOCLDWAIT` — тоді дітей прибирає ядро й статусу не лишається |
| `EINTR` | виклик перервано сигналом, обробник якого зареєстровано без `SA_RESTART`; результату немає |
| `EINVAL` | біт в `options` поза маскою виклику; `waitid` без жодної події; недозволене `idtype` або `id` |
| `EAGAIN` | `waitid` із `P_PIDFD` на неблокувальному дескрипторі, а дитина ще жива |
| `ESRCH` | `pid == INT_MIN` у `wait`/`waitpid` |

`ECHILD` — не аварія, а звичайний кінець циклу очікування: він означає «більше нема кого чекати». Плутати його з `EINTR` не можна, бо `EINTR` каже протилежне — чекати ще є на кого, просто виклик не встиг. Із прапорцем `SA_RESTART` ядро перезапускає очікування саме, і `EINTR` не з'являється зовсім; без нього повторний виклик — обов'язок програми ([перервані виклики й перезапуск](book:unix-linux/eintr-and-restart), [диспозиція сигналу](book:unix-linux/signal-disposition)).

Усі виклики родини — точки скасування потоку за POSIX: потік, що чекає в `wait`, скасовується тоді, коли на нього прийшов запит.

## Мінімальний робочий виклик

Класична форма — статус і облік одним рухом, з правильним повтором після `EINTR`:

```c
#define _DEFAULT_SOURCE        /* wait4() і WCOREDUMP() */
#include <errno.h>
#include <stdio.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    pid_t child = fork();
    if (child < 0) { perror("fork"); return 1; }
    if (child == 0) _exit(42);

    int status;
    struct rusage ru;
    pid_t got;
    do {
        got = wait4(child, &status, 0, &ru);
    } while (got < 0 && errno == EINTR);
    if (got < 0) { perror("wait4"); return 1; }

    if (WIFEXITED(status))
        printf("вийшов сам, код %d\n", WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("убито сигналом %d%s\n", WTERMSIG(status),
               WCOREDUMP(status) ? " (дамп)" : "");

    printf("user %ld.%06ld  sys %ld.%06ld  maxrss %ld КіБ\n",
           (long)ru.ru_utime.tv_sec, (long)ru.ru_utime.tv_usec,
           (long)ru.ru_stime.tv_sec, (long)ru.ru_stime.tv_usec,
           ru.ru_maxrss);
    return 0;
}
```

Те саме через `waitid`, у неблокувальному опитуванні — з обома перевірками, які тут інші:

```c
siginfo_t si;
si.si_pid = 0;                 /* переносний спосіб побачити «нікого» */

if (waitid(P_PID, child, &si, WEXITED | WNOHANG) < 0) {
    perror("waitid");          /* −1: справжня помилка */
} else if (si.si_pid == 0) {
    /* нуль і порожній si_pid: дитина ще жива, це не помилка */
} else if (si.si_code == CLD_EXITED) {
    printf("код %d\n", si.si_status);
} else {
    printf("сигнал %d, причина %d\n", si.si_status, si.si_code);
}
```

Різниця між двома фрагментами й є коротким підсумком усього контракту: `wait4` віддає одне число, яке треба розбирати, зате разом з обліком; `waitid` віддає розібрану відповідь і точнішу ціль, зате мовчить про час і вимагає перевіряти успіх не там, де звик той, хто прийшов від `waitpid`.
