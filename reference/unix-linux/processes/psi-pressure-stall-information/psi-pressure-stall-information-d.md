# Підсистема оцінки голодування ресурсів PSI (Pressure Stall Information)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Історично системні адміністратори оцінювали навантаження на систему через метрику Load Average (`loadavg`). Вона показує середню кількість процесів, що перебувають у черзі на виконання або в стані безперервного сну. Але цей показник має фатальний недолік: високий `loadavg` сам по собі не каже, *чого саме* не вистачає і чи є це проблемою. Load 50 на 64-ядерному сервері — норма; load 10 на 4-ядерному — теж норма, якщо процеси виконують короткі операції вводу/виводу. Гірше того, коли системі не вистачає пам'яті й вона починає "пробуксовувати" (thrashing), постійно скидаючи та витягуючи сторінки з диска, процесор може бути майже вільним, `loadavg` не показуватиме катастрофи, але система перетвориться на цеглину.

Виникла потреба в показнику, який відповідав би не на питання "скільки завдань працює", а на питання: **"Який відсоток часу мої програми НЕ могли працювати через нестачу ресурсів?"**

Саме цю проблему вирішує підсистема Pressure Stall Information (PSI). Вона дає канонічний, кількісний показник того, наскільки ресурсне голодування впливає на загальну продуктивність для трьох основних ресурсів: процесорного часу (CPU), пам'яті (Memory) та вводу/виводу (I/O).

## Концепції some та full stalls

Щоб оцінити втрати від нестачі ресурсів, PSI вводить дві фундаментальні метрики затримок (stalls), які вимірюються у відсотках часу.

### Деяке голодування (some)

Стан `some` означає, що протягом певного часу **хоча б одне завдання було готове до виконання, але не могло працювати через нестачу ресурсу**. 

Якщо показник `memory some` становить 10%, це означає, що протягом 10% часу принаймні один процес у системі був заблокований, чекаючи на виділення пам'яті (наприклад, через page fault). У цей час інші процеси могли продовжувати роботу, тому система в цілому не завмерла. Це ранній індикатор того, що ресурс стає вузьким місцем і система втрачає потенційну продуктивність.

### Повне голодування (full)

Стан `full` — це метрика повного паралічу. Вона показує відсоток часу, протягом якого **всі без винятку активні завдання були заблоковані через нестачу ресурсу**.

У цьому стані жоден процес не виконує корисну роботу в просторі користувача. Якщо `memory full` становить 20%, це означає, що п'яту частину всього часу комп'ютер простоював або виконував лише внутрішню роботу ядра (наприклад, тасував сторінки пам'яті на диск і назад), бо всі програми чекали на пам'ять. Це класичний симптом глибокого thrashing-у.

Для ресурсу CPU існує лише метрика `some`. "Повного" голодування процесора не буває: якщо всі завдання чекають на CPU, це означає, що процесор на 100% зайнятий їх виконанням, тому ситуація, коли всі чекають на CPU і при цьому CPU нічого не робить, концептуально неможлива.

## Інтерфейс у просторі користувача

Дані PSI експортуються через віртуальну файлову систему у теці `/proc/pressure/`, яка містить три файли: `cpu`, `memory` та `io`.

Вміст файлу `/proc/pressure/memory` виглядає так:

```text
some avg10=2.35 avg60=1.61 avg300=0.74 total=34567812
full avg10=0.00 avg60=0.00 avg300=0.00 total=123450
```

Кожен рядок відповідає за рівень голодування (`some` або `full`).
- **avg10, avg60, avg300:** експоненційно згладжені ковзні середні, що показують відсоток часу за останні 10, 60 та 300 секунд. Наприклад, `avg10=2.35` — за останні 10 секунд 2.35% часу принаймні одне завдання чекало на пам'ять.
- **total:** абсолютний лічильник часу (в мікросекундах), проведеного у цьому стані з моменту завантаження. Він монотонно зростає, що дозволяє системам моніторингу обчислювати точні дельти між будь-якими двома зчитуваннями.

Оскільки PSI повністю інтегрована з ієрархією Control Groups (cgroups v2), такі самі файли (`cpu.pressure`, `memory.pressure`, `io.pressure`) існують у кожній теці cgroup. Це дозволяє відслідковувати ресурсне голодування ізольовано для кожного контейнера чи сервісу.

## Як ядро обчислює затримки

Оскільки перемикання контексту завдань відбувається тисячі разів на секунду, збір такої статистики міг би створити величезне навантаження на процесор. Тому PSI реалізовано так, щоб не обчислювати відсотки при кожній зміні.

PSI інтегровано безпосередньо в планувальник завдань. Ядро відстежує кількість завдань у певних станах (`NR_IOWAIT`, `NR_MEMSTALL`, `NR_RUNNING`). Коли стан системи змінюється (наприклад, одне із заблокованих завдань починає виконуватися), ядро записує поточний timestamp. Наступного разу, коли стан знову змінюється, ядро обчислює дельту часу, що минув, і додає її до відповідних акумуляторів `total` для станів `some` або `full`. 

Періодичне оновлення згладжених середніх (avg10, avg60, avg300) виконується окремим таймером лише раз на дві секунди. Такий підхід зводить накладні витрати на відстеження голодування до часток відсотка від процесорного часу.

## Подійний моніторинг замість постійного зчитування

Для автоматизованого реагування на проблеми PSI надає механізм подієвих тригерів. Замість того, щоб постійно читати файли з `/proc` (polling) і марнувати ресурси, програма може налаштувати ядро розбудити її, коли тиск перевищить певний поріг.

Щоб встановити тригер, програма відкриває відповідний файл PSI, записує в нього конфігураційний рядок у форматі `<type> <threshold_us> <window_us>`, а потім викликає `poll` або `epoll` на цей файловий дескриптор.

```c
#include <fcntl.h>
#include <poll.h>
#include <stdio.h>
#include <unistd.h>
#include <string.h>

int main() {
    int fd = open("/proc/pressure/memory", O_RDWR | O_NONBLOCK);
    if (fd < 0) return 1;

    // Тригер: some stalls > 150мс протягом 1 секунди
    const char *trigger = "some 150000 1000000";
    write(fd, trigger, strlen(trigger));

    struct pollfd pfd = { .fd = fd, .events = POLLPRI };
    
    printf("Очікування на голодування пам'яті...\n");
    while (poll(&pfd, 1, -1) > 0) {
        if (pfd.revents & POLLPRI) {
            printf("Увага: виявлено високий тиск на пам'ять!\n");
            // Проактивні дії: скидання кешів, завершення фонових завдань
        }
    }
    close(fd);
    return 0;
}
```

Цей механізм став основою для проактивних демонів, таких як `systemd-oomd`. 

Ядерний OOM (Out-Of-Memory) Killer часто спрацьовує надто пізно: коли пам'ять вичерпано повністю, система вже давно могла увійти в стан глибокого thrashing-у. Система зависає на хвилини, формально ще маючи кілька мегабайтів вільної пам'яті, що стримує запуск ядерного OOM Killer. 

Демон `systemd-oomd` працює у просторі користувача і відстежує `memory.pressure`. Якщо тригер `full` показує, що система увійшла в стан паралічу через пам'ять (навіть якщо фізично пам'ять ще є), демон самостійно знаходить cgroup із найбільшим споживанням і надсилає їй `SIGKILL`. Це дозволяє вбити жадібний процес (наприклад, вкладку браузера) до того, як вся система втратить чуйність.
