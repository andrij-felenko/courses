# 📋 Довідка інтерфейсів іменування процесів

Тут зібрано все, чим у Linux називають процес, потік, групу й сеанс: підписи викликів, значення кожного аргументу, повний перелік помилок і версію ядра, з якої воно працює. Довідка потрібна в момент, коли код уже пишеться і треба точно знати, що передати й що перевірити на поверненні.

## Дізнатися власні номери

```c
#include <unistd.h>

pid_t getpid(void);      /* номер групи потоків — однаковий у всіх потоках */
pid_t getppid(void);     /* номер батька */

#define _GNU_SOURCE
pid_t gettid(void);      /* номер саме цього потоку */
```

| виклик | що повертає | помилки | доступність |
|---|---|---|---|
| `getpid()` | PID (він же TGID) процесу | немає — виклик не може провалитися | завжди |
| `getppid()` | PID батька, або **0**, якщо батько в іншому просторі імен процесів | немає | завжди |
| `gettid()` | TID потоку; у однопотоковому процесі дорівнює `getpid()` | немає | ядро 2.4.11; обгортка в glibc — з 2.30, раніше `syscall(SYS_gettid)` |

Три речі, які варто знати про ці три рядки.

**`errno` після них нічого не означає.** Обидва `get*pid` документовані як такі, що завжди успішні; перевіряти повернене значення на `-1` немає сенсу, а читати `errno` — тим паче, бо його ніхто не чіпав.

**`getppid()` може повернути 0.** Це не помилка й не «немає батька»: так ядро каже, що батько існує, але лежить у просторі імен, з якого ваш простір нічого не бачить ([простори імен](book:unix-linux/namespaces) — ізольовані «погляди» на систему, і видимість у них однобічна). Усередині контейнера це звичайна відповідь для головного процесу.

**Кешування PID у glibc прибрали в 2.25.** Раніше бібліотека запам'ятовувала номер, щоб не робити системний виклик щоразу, і програма, яка створювала процес не через обгортку glibc, а прямим `clone()`, отримувала з `getpid()` чуже, застаріле число. Тепер це завжди справжній системний виклик.

Різницю між `getpid()` і `gettid()` дає модель, у якій одиниця планування — задача, а «процес» — це група задач зі спільним адресним простором ([потоки як задачі](book:unix-linux/threads-as-tasks)). Тому в багатопотоковій програмі номер один на всіх, а номерів задач стільки, скільки потоків.

## Надіслати сигнал

```c
#include <signal.h>

int kill(pid_t pid, int sig);            /* 0 або -1 */
int killpg(int pgrp, int sig);           /* те саме, що kill(-pgrp, sig) */
int tgkill(pid_t tgid, pid_t tid, int sig);   /* конкретному потокові */
```

Аргумент `pid` у `kill()` — не просто номер: його знак перемикає сам різновид адресата.

![Таблиця: додатний pid — процес, нуль — своя група, мінус один — усі, менше −1 — група](/reference/unix-linux/processes/pid-and-hierarchy/img/pid-argument-sign.svg)

*Той самий `pid_t` в одному аргументі несе чотири різні змісти, і розрізняє їх знак. Та сама домовленість діє в `waitpid()`, але «усі» там означає «усі мої діти», а не «усі процеси системи».*

`sig == 0` не шле нічого, але виконує обидві перевірки — існування й прав. Це і є канонічний спосіб спитати «чи живий такий номер»:

```c
if (kill(pid, 0) == 0)           /* процес є і я маю право його сигналити */
    ;
else if (errno == EPERM)         /* процес Є, але він чужий */
    ;
else if (errno == ESRCH)         /* такого номера немає (або він зомбі, вже прибраний) */
    ;
```

Зверніть увагу на `EPERM`: він означає «існує», а не «немає». Код, який перевіряє лише на нуль, помилково вважає чужий живий процес мертвим.

**Права на сигнал.** Надсилач мусить або мати можливість `CAP_KILL` у просторі імен користувачів адресата ([можливості замість всесильного root](book:unix-linux/capabilities) — дрібно нарізані повноваження, які роздають окремо), або мати реальний чи чинний UID, що збігається з реальним або збереженим set-user-ID адресата. Виняток один: для `SIGCONT` достатньо спільного сеансу.

| помилка | коли |
|---|---|
| `EINVAL` | `sig` не є чинним номером сигналу |
| `EPERM` | процес (або хоч один процес групи) існує, але прав на нього немає |
| `ESRCH` | процесу чи групи не існує; зомбі при цьому вважається наявним, доки його не прибрали `wait` |

Дві поведінки `kill(-1, sig)`, які легко проґавити: процес 1 із розсилки виключено завжди, а на Linux надсилач не сигналить і сам себе (POSIX цього не вимагає, тому переносний код на це не спирається).

`tgkill()` цілиться в окремий потік і вимагає **обидва** номери: `tgid` — групи, `tid` — потоку. Другий аргумент без першого — це застарілий `tkill()`, і саме тому він застарілий: номер потоку так само перевикористовується, тож без перевірки «а чи той це ще потік тієї групи» сигнал міг прилетіти сторонньому. Обгортку `tgkill()` glibc дає з 2.30, у ядрі виклик є з 2.5.75.

| помилка `tgkill()` | коли |
|---|---|
| `EAGAIN` | вичерпано ліміт черги сигналів реального часу або пам'ять ядра |
| `EINVAL` | `tgid`, `tid` або `sig` недійсні |
| `EPERM` | немає прав |
| `ESRCH` | немає такого потоку або такої групи |

## Забрати результат дитини

```c
#include <sys/wait.h>

pid_t wait(int *wstatus);
pid_t waitpid(pid_t pid, int *wstatus, int options);
int   waitid(idtype_t idtype, id_t id, siginfo_t *infop, int options);
```

`waitpid()` читає той самий знаковий словник, що й `kill()`, тільки в межах власних дітей: `> 0` — конкретна дитина, `0` — будь-яка з групи процесів того, хто чекає, `-1` — будь-яка, `< -1` — будь-яка з групи `-pid`. Повертає номер дитини; `0` — якщо стояв `WNOHANG` і ніхто не змінив стану; `-1` — помилка.

`waitid()` розділяє те, що в `waitpid()` злите в одне число: різновид цілі окремо, сам номер окремо.

| `idtype` | що означає `id` | доступність |
|---|---|---|
| `P_ALL` | `id` ігнорується — будь-яка дитина | завжди |
| `P_PID` | PID конкретної дитини | завжди |
| `P_PGID` | номер групи процесів; `id == 0` — група того, хто чекає | `id == 0` — з ядра 5.4 |
| `P_PIDFD` | дескриптор процесу (pidfd), а не число | з ядра 5.4 |

`options` — прапорці через «або». Для `waitid()` **обов'язково** вказати щонайменше одну з трьох подій, інакше `EINVAL`:

| прапорець | подія | `waitpid()` | `waitid()` |
|---|---|---|---|
| `WEXITED` | дитина завершилася | мається на увазі завжди | треба вказати явно |
| `WSTOPPED` / `WUNTRACED` | дитину зупинено сигналом | `WUNTRACED` | `WSTOPPED` |
| `WCONTINUED` | зупинену дитину відновлено | є | є |
| `WNOHANG` | не блокуватися, якщо нічого не сталося | є | є |
| `WNOWAIT` | підглянути стан, **не** прибираючи запис | ні | є |

`WNOWAIT` — єдиний спосіб дізнатися код виходу, не звільнивши номер: запис про померлу дитину лишається, і забрати його можна пізніше ще раз. Це рівно те, що потрібно, коли результат читає один шматок програми, а прибирає інший.

Результат `waitid()` приходить не бітовим полем, а структурою:

```c
siginfo_t info = { 0 };
if (waitid(P_PID, (id_t)child, &info, WEXITED) == 0) {
    /* info.si_pid    — хто саме
       info.si_uid    — від чийого імені він виконувався
       info.si_status — код виходу або номер сигналу
       info.si_code   — CLD_EXITED | CLD_KILLED | CLD_DUMPED
                        | CLD_STOPPED | CLD_TRAPPED | CLD_CONTINUED */
}
```

Пастка `WNOHANG`: `waitid()` повертає **0** і тоді, коли нічого не сталося. Розрізняти треба за `si_pid` — виправлення до POSIX.1-2008 (Technical Corrigendum 1, 2013) вимагає, щоб у цьому разі реалізація сама обнулила `si_pid` і `si_signo`, тож перевірка `info.si_pid != 0` і є ознакою «щось справді відбулося». Дотримуються цього не всі, тому поле обнуляють самі перед викликом — саме тому в прикладі вище стоїть `siginfo_t info = { 0 }`.

Бітове поле `wstatus` зі старих викликів розбирають макросами: `WIFEXITED`/`WEXITSTATUS`, `WIFSIGNALED`/`WTERMSIG`/`WCOREDUMP`, `WIFSTOPPED`/`WSTOPSIG`, `WIFCONTINUED`.

| помилка | коли |
|---|---|
| `ECHILD` | дітей, що підходять під запит, немає — або вказаний процес не ваша дитина |
| `EINTR` | прийшов сигнал, а `WNOHANG` не стояв; виклик треба перезапускати ([EINTR і перезапуск](book:unix-linux/eintr-and-restart) — не всі перервані виклики ядро відновлює само) |
| `EINVAL` | недійсні `options` (зокрема `waitid()` без жодної з подій) |
| `EAGAIN` | `waitid(P_PIDFD, …)` на неблокуючому дескрипторі, а процес ще живий |
| `ESRCH` | `wait`/`waitpid` із `pid == INT_MIN` |

## Групи процесів і сеанси

```c
#include <unistd.h>

int   setpgid(pid_t pid, pid_t pgid);
pid_t getpgid(pid_t pid);
pid_t getpgrp(void);            /* == getpgid(0) */
pid_t setsid(void);
pid_t getsid(pid_t pid);
```

Нуль в аргументі всюди означає «я»: `setpgid(0, 0)` робить процес лідером власної нової групи, `getpgid(0)` віддає номер своєї групи, `getsid(0)` — свого сеансу.

`setpgid()` обставлено вузькими умовами, і кожна з них має причину.

| помилка | коли | чому саме так |
|---|---|---|
| `EACCES` | дитина вже зробила `execve()` | після заміни образу оболонка вже не має права переставляти дитину: та могла свідомо перебудувати своє оточення |
| `EINVAL` | `pgid < 0` | номер групи — це PID лідера, від'ємним він не буває |
| `EPERM` | перенесення в групу з іншого сеансу; спроба змінити групу дитині з іншого сеансу; спроба змінити групу лідерові сеансу; цільової групи не існує | сеанс — жорсткіша межа за групу; лідера сеансу зрушити не можна взагалі |
| `ESRCH` | `pid` — не ви й не ваша дитина | керувати можна лише своїм піддеревом на один рівень |

Звідси відома домовленість керування завданнями: `setpgid()` після розгалуження викликають **обидва** — і батько, і дитина, кожен на дитину. Це не надмірність, а усунення гонки: хто з них дістанеться процесора першим, наперед невідомо, а другий виклик просто нічого не змінить. Далі оболонка передає групу терміналові через `tcsetpgrp()` ([керування завданнями](book:unix-linux/job-control) — те, як `Ctrl+C` знаходить потрібні процеси).

`setsid()` повертає номер нового сеансу або `-1` з `EPERM`, якщо той, хто кличе, **вже є лідером групи**. Перевірка виглядає дивно, аж поки не поглянути на наслідок: якби лідер групи міг піти в новий сеанс, його стара група опинилася б розірваною між двома сеансами. Тому стандартний рецепт — розгалузитися, дати батькові вийти, а `setsid()` кликати з дитини, яка лідером групи бути не може за визначенням.

Новий сеанс не має керівного термінала — це, власне, і є той механізм, яким служба відв'язується від консолі.

## Хто підбирає сиріт

```c
#include <sys/prctl.h>

prctl(PR_SET_CHILD_SUBREAPER, 1L);      /* я підбираю своїх нащадків */
int on;
prctl(PR_GET_CHILD_SUBREAPER, &on);     /* прочитати поточний стан */
```

Процес із цим прапорцем стає новим батьком для будь-якого свого нащадка, який осиротів: замість підійматися до PID 1, дитина перечіпляється до **найближчого живого предка-підбирача**. Той отримує `SIGCHLD` і має право забрати код виходу ([сироти й перепідпорядкування](book:unix-linux/orphan-reparenting) — правила, за якими дерево не розривається).

Дві властивості прапорця, які визначають, де його ставити:

- **не успадковується** дітьми, створеними через `fork()`/`clone()` — кожен, хто хоче бути підбирачем, вмикає його собі сам;
- **переживає `execve()`** — тобто вмикати можна до заміни образу, і нова програма прапорець збереже.

Доступно з ядра 3.4.

## Посилання замість числа: pidfd

```c
#include <sys/syscall.h>
#include <unistd.h>

int pidfd_open(pid_t pid, unsigned int flags);
int pidfd_send_signal(int pidfd, int sig, siginfo_t *info, unsigned int flags);
int pidfd_getfd(int pidfd, int targetfd, unsigned int flags);
```

Обгорток у glibc історично не було, тому в коді ці виклики роблять напряму — така форма працює з будь-якою версією бібліотеки:

```c
static int pidfd_open(pid_t pid, unsigned int flags) {
    return (int)syscall(SYS_pidfd_open, pid, flags);
}
```

![Смуга версій ядра: 5.1 pidfd_send_signal, 5.2 CLONE_PIDFD, 5.3 pidfd_open, 5.4 waitid P_PIDFD, 5.6 pidfd_getfd, 5.10 PIDFD_NONBLOCK, 6.9 PIDFD_THREAD](/reference/unix-linux/processes/pid-and-hierarchy/img/pidfd-versions.svg)

*Інтерфейс складався сімома кроками впродовж кількох років, тому «pidfd є» — недостатньо точне твердження: у кожної частини свій поріг версії.*

### `pidfd_open()`

`pid` без прапорців має бути номером **групи потоків** (тобто тим, що повертає `getpid()`); номер окремого потоку тут дасть `EINVAL`.

| прапорець | дія | з версії |
|---|---|---|
| `0` | звичайний блокуючий дескриптор на процес | 5.3 |
| `PIDFD_NONBLOCK` | `waitid()` на цьому дескрипторі не блокується, а віддає `EAGAIN` | 5.10 |
| `PIDFD_THREAD` | дескриптор указує на **окремий потік**, а не на групу | 6.9 |

| помилка | коли |
|---|---|
| `EINVAL` | недійсні `flags`, або `pid` не є лідером групи потоків без `PIDFD_THREAD` |
| `EMFILE` / `ENFILE` | вичерпано ліміт дескрипторів процесу / системи |
| `ENODEV` | недоступна внутрішня ФС анонімних inode |
| `ENOMEM` | немає пам'яті ядра |
| `ESRCH` | процесу з таким номером немає |

### `pidfd_send_signal()`

`info == NULL` дає ту саму семантику, що й звичайний `kill()`. Заповнена структура дозволяє передати власні дані сигналу — але підробити `si_code` для чужого процесу не вийде, ядро відповість `EPERM`.

| прапорець | дія | з версії |
|---|---|---|
| `0` | адресата визначає сам дескриптор | 5.1 |
| `PIDFD_SIGNAL_THREAD` | точно в той потік, на який указує дескриптор | 6.9 |
| `PIDFD_SIGNAL_THREAD_GROUP` | у всю групу потоків, якщо дескриптор на лідера | 6.9 |
| `PIDFD_SIGNAL_PROCESS_GROUP` | у всю групу процесів, якщо дескриптор на лідера групи | 6.9 |

| помилка | коли |
|---|---|
| `EBADF` | це не pidfd |
| `EINVAL` | недійсний `sig`, недійсні `flags`, або немає прав щодо простору імен адресата |
| `EPERM` | немає прав на сигнал, або недійсний `info.si_code` для чужого процесу |
| `ESRCH` | процес завершився **і вже прибраний** через `wait` |

Останній рядок і є те, заради чого весь механізм: там, де `kill()` мовчки влучив би в чужу програму, що встигла отримати той самий номер, дескриптор повертає `ESRCH`.

### `pidfd_getfd()`

Витягує з чужого процесу його відкритий дескриптор `targetfd` і кладе копію собі. `flags` мусить бути `0`. Права перевіряються тим самим механізмом, що й приєднання налагоджувача — режимом `PTRACE_MODE_ATTACH_REALCREDS` ([ptrace](book:unix-linux/ptrace-model) — підсистема, крізь яку один процес дістає контроль над іншим). На поверненому дескрипторі одразу стоїть `FD_CLOEXEC`; зміщення й прапорці стану спільні з оригіналом.

Помилки: `EBADF` (не pidfd або в адресата такого дескриптора немає), `EINVAL` (`flags != 0`), `EMFILE`/`ENFILE`, `EPERM` (не пройшла ptrace-перевірка), `ESRCH`. Доступно з 5.6.

### Отримати дескриптор одночасно з дитиною

```c
int pidfd = -1;
struct clone_args a = {
    .flags = CLONE_PIDFD,
    .pidfd = (uint64_t)(uintptr_t)&pidfd,
    .exit_signal = SIGCHLD,
};
pid_t child = syscall(SYS_clone3, &a, sizeof a);
```

`CLONE_PIDFD` (з 5.2) кладе готовий дескриптор у пам'ять батька в ту саму мить, коли дитина з'являється, — вікна «дитина вже є, а посилання ще нема» просто не існує. У старого `clone()` дескриптор потрапляє за вказівником `parent_tid`, тому з `CLONE_PARENT_SETTID` цей прапорець несумісний; з `CLONE_DETACHED` — теж, а з `CLONE_THREAD` не можна було до 6.9.

Поле `set_tid` у `struct clone_args` (з ядра 5.5) — той рідкісний випадок, коли номер замовляють: масив просить конкретні номери по рівнях просторів імен, від внутрішнього до зовнішнього, і потрібен він механізмам збереження й відновлення стану. До 5.5 те саме робили записом бажаного числа в `/proc/sys/kernel/ns_last_pid` — підказкою, а не замовленням.

### Очікування на дескрипторі

pidfd можна класти в `poll`/`epoll` разом із сокетами й таймерами ([очікування на багато джерел](book:unix-linux/select-poll-epoll) — один цикл, що чекає на всі події одразу):

| подія | коли настає |
|---|---|
| `EPOLLIN` | задача завершилася й стала зомбі |
| `EPOLLHUP` | запис про задачу прибрано |

З `PIDFD_THREAD` дескриптор стає читабельним, щойно вийшов **саме цей** потік, навіть якщо група ще жива. Без нього — лише коли вийшов останній потік групи.

Окремо варто знати: дескриптор, отриманий звичайним `open("/proc/<pid>", O_RDONLY)`, теж вважається pidfd для частини викликів, але його **не можна** ні опитувати через `poll`, ні подавати в `waitid()`.

І чого pidfd не робить: він не резервує номер. Поки ви тримаєте дескриптор, система вільна видати те саме число наступному процесові — гарантія лише в тому, що ваш дескриптор до нього не має стосунку.

## Мінімальний робочий виклик

Запустити дитину, дочекатися її в одному циклі з іншими подіями й надіслати сигнал без ризику влучити в стороннього:

```c
#define _GNU_SOURCE
#include <linux/sched.h>
#include <poll.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int pidfd = -1;
    struct clone_args a = {
        .flags       = CLONE_PIDFD,
        .pidfd       = (uint64_t)(uintptr_t)&pidfd,
        .exit_signal = SIGCHLD,
    };

    pid_t child = syscall(SYS_clone3, &a, sizeof a);
    if (child == 0) {                       /* дитина */
        execl("/bin/sleep", "sleep", "30", (char *)NULL);
        _exit(127);
    }

    struct pollfd pf = { .fd = pidfd, .events = POLLIN };
    int ready = poll(&pf, 1, 2000);         /* чекаємо 2 с */

    if (ready == 0) {                       /* не дочекалися — просимо піти */
        syscall(SYS_pidfd_send_signal, pidfd, SIGTERM, NULL, 0);
        poll(&pf, 1, -1);
    }

    siginfo_t info = { 0 };
    waitid(P_PIDFD, (id_t)pidfd, &info, WEXITED);
    printf("pid=%d code=%d status=%d\n", info.si_pid, info.si_code, info.si_status);

    close(pidfd);
    return 0;
}
```

Тут немає жодного місця, де число `child` використовували б для дії: воно лишається тільки як підпис у виведенні. Усі дії йдуть крізь `pidfd`.

## Звідки система дає ці дані

Усе перелічене читається з `/proc` як зі звичайних файлів ([procfs](book:unix-linux/proc-filesystem) — каталоги-вікна у структури ядра, які не займають місця на диску).

| що | де | подробиці |
|---|---|---|
| PID батька | `/proc/<pid>/stat`, поле **4** (`ppid`) | те саме є в `status` як `PPid` |
| група процесів | `/proc/<pid>/stat`, поле **5** (`pgrp`) | |
| сеанс | `/proc/<pid>/stat`, поле **6** (`session`) | |
| керівний термінал | `/proc/<pid>/stat`, поля **7** (`tty_nr`) і **8** (`tpgid`) | `tpgid` — група, що зараз на передньому плані |
| час старту | `/proc/<pid>/stat`, поле **22** (`starttime`) | у тиках від завантаження системи; ділити на `sysconf(_SC_CLK_TCK)` |
| потоки | каталог `/proc/<pid>/task/<tid>/` | у кожного потоку своя копія тих самих файлів |
| номери в просторах імен | `/proc/<pid>/status`: `NStgid`, `NSpid`, `NSpgid`, `NSsid` | список від зовнішнього простору до внутрішнього; з ядра 4.1 |
| кількість потоків | `/proc/<pid>/status`: `Threads` | |
| хто трасує | `/proc/<pid>/status`: `TracerPid` | `0`, якщо ніхто |

**Пастка розбору `stat`.** Поле 2 — це ім'я програми **в дужках**, і воно може містити і пробіли, і саму дужку, бо береться з того, що процес собі виставив. Розбирати рядок пробілами з початку не можна: правильно шукати **останню** `)` і рахувати поля від неї. Довші за 15 символів імена мовчки обрізаються (`TASK_COMM_LEN` = 16 разом із нулем).

**Умова: `sysconf(_SC_CLK_TCK)` = 100, поле 22 у `/proc/4242/stat` дорівнює 918271, `uptime` системи — 12034.6 с.**

```
старт процесу = 918271 / 100 = 9182.71 c від завантаження
вік процесу   = 12034.6 − 9182.71 ≈ 2851.9 c ≈ 47.5 хв
```

Роздільність тут — одна сота секунди, тож пара «номер + час старту» майже напевно унікальна: два процеси з однаковим номером мали б народитися в один і той самий тик. Саме тому цю пару використовують як дешеву перевірку тотожності там, де pidfd недоступний.

## Межа простору номерів

| файл | що робить | значення |
|---|---|---|
| `/proc/sys/kernel/pid_max` | число, на якому нумерація обертається (на одиницю більше за найбільший можливий PID) | типово 32768; на 32-бітових системах це й максимум, на 64-бітових — до 2²² = 4194304 |
| `/proc/sys/kernel/threads-max` | скільки всього задач дозволено в системі | |
| `/proc/sys/kernel/ns_last_pid` | останній виданий номер у поточному просторі імен; запис у файл підказує ядру, з якого числа шукати наступне | з ядра 3.3 |

Коли вільних номерів не лишилося, це видно не окремою помилкою, а звичайним `EAGAIN` від `fork()`/`clone()`. Той самий код повертається ще в трьох випадках, і розрізнити їх за `errno` неможливо:

- вичерпано м'який ліміт `RLIMIT_NPROC` для цього користувача;
- уперлися в `threads-max`;
- уперлися в ліміт контролера `pids` тієї cgroup, у якій живе процес ([cgroups](book:unix-linux/cgroups) — механізм обліку й обмеження ресурсів для груп процесів).

Тому діагностика «чому не створюється процес» починається не з `errno`, а з перевірки всіх чотирьох меж по черзі — зазвичай першою спрацьовує cgroup-межа, а не глобальна.
