## 1. Ієрархія scheduler_class та місце sched_ext

У ядрі Linux немає єдиного монолітного алгоритму планування. Натомість використовується ієрархічний паттерн «Ланцюжок відповідальності» (Chain of Responsibility), сформований структурою `struct sched_class`. Кожен клас планування визначає свій спосіб вибору наступного завдання і має чіткий пріоритет відносно інших класів.

Коли ядро викликає головну функцію перепланування `__schedule()`, воно опитує класи планування у суворо визначеному порядку спадання пріоритету. Перший клас, який має ready-to-run завдання для даного CPU, отримує право призначити свій потік на виконання:

1. **`stop_sched_class`** — найвищий пріоритет у системі. Використовується для службових системних завдань ядра, які не можна переривати (наприклад, зупинка CPU при гарячому виключенні `cpu_down` або виконання процедур міграції `migration_cpu`).
2. **`dl_sched_class`** — клас `SCHED_DEADLINE`. Обслуговує завдання з жорсткими часовими гарантіями за алгоритмом Earliest Deadline First (EDF) та сервером постійної пропускної здатності (Constant Bandwidth Server).
3. **`rt_sched_class`** — класи реального часу `SCHED_FIFO` та `SCHED_RR`. Завдання виконуються доти, доки самі не віддадуть CPU або не з'явиться вищий RT-потік.
4. **`ext_sched_class` (`sched_ext`)** — розширювальний клас BPF. Знаходиться між класом реального часу та звичайними завданнями.
5. **`fair_sched_class`** — стандартний клас для звичайних процесів `SCHED_NORMAL` / `SCHED_BATCH` (алгоритм EEVDF або CFS).
6. **`idle_sched_class`** — найнижчий пріоритет. Виконується лише тоді, коли на CPU немає жодного готового завдання (`swapper` / `idle` thread).

```
+-------------------------------------------------------+  Пріоритет
| stop_sched_class (Міграція та зупинка CPU)            |  Найвищий
+-------------------------------------------------------+     |
| dl_sched_class   (SCHED_DEADLINE)                     |     |
+-------------------------------------------------------+     |
| rt_sched_class   (SCHED_FIFO / SCHED_RR)              |     v
+-------------------------------------------------------+
| ext_sched_class  (sched_ext — eBPF Планувальник)      |  <-- НОВИЙ КЛАС
+-------------------------------------------------------+     |
| fair_sched_class (SCHED_NORMAL — EEVDF / CFS)         |     |
+-------------------------------------------------------+     v
| idle_sched_class (Низькопріоритетний простій)         |  Найнижчий
+-------------------------------------------------------+
```

Розміщення `ext_sched_class` перед `fair_sched_class` є фундаментальним рішенням. Потоки, які переведені під управління `sched_ext`, отримують процесорний час раніше за звичайні завдання EEVDF, але ніколи не можуть порушити роботи потоків реального часу `SCHED_FIFO`/`SCHED_RR`. Це гарантує, що важливі системні драйвери та критичні RT-завдання залишаються повністю захищеними від можливих затримок у користувацькому BPF-планувальнику.

Усередині ядра `ext_sched_class` імплементує стандартний набір внутрішніх методів `sched_class`:
- `enqueue_task_scx()` — викликається під час додавання процесу до черги ядра. Перевіряє стан завдання і викликає BPF-хук `enqueue`.
- `dequeue_task_scx()` — викликається при вилученні процесу зі стану runnable (сон, блокування I/O). Викликає BPF-хук `dequeue`.
- `yield_task_scx()` — обробляє добровільну віддачу процесора через системний виклик `sched_yield()`.
- `pick_next_task_scx()` — викликає BPF-хук `dispatch` та повертає наступне завдання для виконання на вільному CPU.
- `put_prev_task_scx()` — зберігає стан попередньо виконуваного процесу, обчислює залишок кванту часу і викликає BPF-хук `stopping`.

Якщо у системі активовано `sched_ext`, ядро за замовчуванням переводить **усі** звичайні процеси класу `SCHED_NORMAL` під контроль `ext_sched_class`. Для ситуацій, коли потрібно ізолювати лише конкретну групу застосунків, передбачено режим `SCX_OPS_SWITCH_PARTIAL`: у цьому режимі `sched_ext` управляє лише тими процесами, для яких користувач явно викликав системний виклик `sched_setscheduler()` із політикою `SCHED_EXT`. Решта процесів системи продовжують плануватися через EEVDF. Детальніше про передумови створення цієї архітектури описано в [історії виникнення sched_ext](book:unix-linux/sched-ext-ebpf-scheduler/hist-sched-ext.md).

## 2. Внутрішній механізм BPF_PROG_TYPE_STRUCT_OPS

Фундаментом, який робить можливим виконання C-коду планувальника з низькими затримками у режимі ядра, є механізм BPF `struct_ops`.

У класичній системі eBPF програми приєднуються до заздалегідь визначених точек трасування (tracepoints, kprobes) або мережевих сокетів (XDP, tc). Механізм `struct_ops` пішов далі: він дозволяє замінювати цілі структури таблиць покажчиків на функції у ядрі Linux (Function Pointer Tables) на BPF-програми, зкомпільовані JIT-компілятором у сирий машиний код.

Коли BPF-планувальник завантажується в систему, користувацький завантажувач передає ядру структуру `struct sched_ext_ops`. Ядро перевіряє її за допомогою eBPF Verifier і підключає покажчики `ext_sched_class` безпосередньо до JIT-скомпільованих точок входу BPF-програми.

```
Користувацький завантажувач (libbpf)
        |
        | 1. bpf_map__attach_struct_ops()
        v
+---------------------------------------------------------------+
| Ядро Linux: eBPF Verifier                                     |
| • Перевірка безпеки пам'яті (BTF типи)                        |
| • Відсутність нескінченних циклів та заборона null-дереференсу|
+---------------------------------------------------------------+
        |
        | 2. JIT Компіляція у x86_64 / arm64 інструкції
        v
+---------------------------------------------------------------+
| ext_sched_class у пам'яті ядра                               |
| .enqueue   ---> JIT_Code_my_enqueue()                         |
| .dispatch  ---> JIT_Code_my_dispatch()                        |
| .select_cpu---> JIT_Code_my_select_cpu()                     |
+---------------------------------------------------------------+
```

### Гарантії безпеки eBPF Verifier для планування

На відміну від традиційних модулів ядра (Kernel Modules / `.ko`), збій у яких призводить до Kernel Panic і «синього екрану» сервера, BPF-планувальник проходить суворий аналіз верифікатором:

1. **Обмеження пам'яті та типів (BTF):** BPF-програма не може читати чи писати довільні адреси оперативної пам'яті. Усі доступи до полів `struct task_struct` перевіряються через BPF Type Format (BTF). Доступ дозволено лише до безпечних полів контексту процесу, таких як `p->pid`, `p->policy`, `p->nr_cpus_allowed`, `p->scx.dsq_flags`.
2. **Гарантія завершення:** Верифікатор гарантує, що будь-який хук (наприклад, `ops.enqueue`) виконається за обмежену кількість інструкцій і не увійде в нескінченний цикл. Усі цикли повинні мати статично перевірювану межу виходу.
3. **Атомарність та контексти блокування:** BPF-програма не може викликати функції ядра, які блокують потік (`msleep`, `mutex_lock`), усередині гарячих хуків планувальника, де заборонено перемикання контексту.
4. **Трампліни виклику (JIT Trampolines):** Для забезпечення мінімальних overhead ядро створює спеціалізовані JIT-трампліни. Виклик BPF-функції з C-коду ядра відбувається напряму через інструкцію `CALL` без додаткових перевірок чи шарів інтерпретації.

Завдяки JIT-компіляції прямий виклик JIT-коду BPF через `struct_ops` не створює накладних витрат на інтерпретацію. Швидкість виконання BPF-хука дорівнює швидкості звичайного C-коду ядра, зкомпільованого GCC або Clang.

## 3. Життєвий цикл завдання та ключові хуки

Робота `sched_ext` будується навколо набору подієвих хуків (callbacks), які викликаються ядром у відповідні моменти зміни стану процесів. Повний перелік полів та сигнатур містить [інтерфейс struct sched_ext_ops](book:unix-linux/sched-ext-ebpf-scheduler/api-sched-ext-ops.md).

Розглянемо шлях завдання від моменту його пробудження до виконання на CPU.

```
Завдання пробуджується (Task Wakes Up)
         |
         v
  [ops.select_cpu]  ---> Обирає цільовий CPU (балансування NUMA / L3)
         |
         v
  [ops.enqueue]     ---> Додає завдання до DSQ (Global / Local / Custom)
         |
         v
  [ops.dispatch]    ---> Обирає завдання з DSQ для вільного CPU
         |
         v
  [ops.running]     ---> Завдання починає виконуватися на CPU
         |
         v
  [ops.stopping]    ---> Квант вичерпано або відбулося блокування (I/O)
```

### 3.1. Вибір процесора: ops.select_cpu

Коли процес прокидається після очікування I/O або сигналу, ядро викликає хук `ops.select_cpu`. Його головне завдання — обрати процесор, на якому потік має бути розміщений.

Це рішення критично впливає на продуктивність:
- Якщо обрати той самий CPU (`prev_cpu`), на якому процес працював до засинання, гарячі дані залишаться в кешах L1 та L2 CPU.
- Якщо `prev_cpu` зайнятий, краще обрати сусіднє ядро, яке ділить з ним спільний L3-кеш, аніж мігрувати потік на інший сокет NUMA.

```c
s32 BPF_STRUCT_OPS(my_select_cpu, struct task_struct *p, s32 prev_cpu, u64 wake_flags)
{
    bool is_idle = false;
    s32 cpu;

    // Викликаємо стандартний хелпер ядра для пошуку вільного ядра
    cpu = scx_bpf_select_cpu_dfl(p, prev_cpu, wake_flags, &is_idle);

    if (is_idle) {
        // Якщо знайдено вільне ядро, відразу відправляємо завдання на нього
        scx_bpf_dispatch(p, SCX_DSQ_LOCAL, SCX_SLICE_DFL, 0);
    }

    return cpu;
}
```

Якщо BPF-програма повертає цільовий CPU і одночасно викликає `scx_bpf_dispatch()` усередині `select_cpu`, завдання оминає чергу `ops.enqueue` і потрапляє напряму в локальну чергу процесора (Direct Dispatch). Це знижує затримку пробудження (wakeup latency) до мінімуму.

### 3.2. Додавання до черги: ops.enqueue

Якщо `ops.select_cpu` не відправив завдання напряму на виконання, ядро викликає хук `ops.enqueue`. Завдання `p` офіційно стає `runnable` (готовим до виконання), і BPF-програма повинна розмістити його в одній із черг диспетчеризації (DSQ).

Усередині `ops.enqueue` розробник має повну свободу вибору алгоритму:
- Помістити завдання в глобальну FIFO чергу.
- Вставити завдання у BPF-мапу типу `BPF_MAP_TYPE_REUSEPORT_SOCKARRAY` або червоно-чорне дерево за пріоритетом.
- Відправити завдання в локальну чергу конкретного процесора за допомогою прапорця `SCX_DSQ_LOCAL_ON(target_cpu)`.

Параметр `enq_flags` передає важливі контекстні прапорці:
- `SCX_ENQ_WAKEUP` — завдання прокинулося після блокування.
- `SCX_ENQ_HEAD` — вимога помістити завдання у початок черги для прискореного виконання.
- `SCX_ENQ_REENQ` — повторне додавання у чергу після зміни параметрів розкладу.
- `SCX_ENQ_LAST` — завдання було останнім виконуваним потоком на даному CPU.

### 3.3. Видача на виконання: ops.dispatch

Коли процесор стає вільним (наприклад, поточне завдання заблокувалося або вичерпало свій квант часу `slice`), ядро викликає хук `ops.dispatch(cpu, prev)`.

Завдання цього хука — наповнити локальну чергу даного `cpu` новими завданнями. Для цього BPF-програма викликає хелпер `scx_bpf_consume(dsq_id)`. Функція `consume` атомарно вилучає завдання з черги `dsq_id` і переміщує його в локальну чергу процесора, готуючи до виконання.

Якщо BPF-планувальник бажає примусово розбудити або витіснити завдання на іншому ядрі, він викликає `scx_bpf_kick_cpu(cpu, flags)`. Цей хелпер посилає міжпроцесорне переривання (IPI) на вказаний CPU, примушуючи його миттєво увійти в хук `ops.dispatch`.

### 3.4. Створення та завершення процесів: ops.init_task та ops.exit_task

Під час створення нового процесу через системні виклики `fork()` або `clone()` ядро викликає хук `ops.init_task(p, args)`. Тут BPF-планувальник виділяє внутрішні структури даних для нового процесу, ініціалізує лічильники квоти часу та встановлює початкові прапорці.

Коли процес завершує свою роботу (`do_exit`), ядро викликає `ops.exit_task(p, args)`, дозволяючи BPF-програмі звільнити ресурси у BPF-мапах та оновити глобальну статистику виконаних завдань.

### 3.5. Моніторинг та кванти: ops.running та ops.stopping

- **`ops.running(p)`**: Викликається у контексті ядра безпосередньо перед перемиканням контексту на процес `p`. Тут оновлюється статистика часу старту та обчислюється віртуальний годинник.
- **`ops.stopping(p, runnable)`**: Викликається, коли процес `p` залишає CPU. Параметр `runnable` вказує, чи потік був витіснений вищим пріоритетом (залишився готовим), чи заснув в очікуванні системного виклику.

Усередині `ops.stopping` BPF-програма може виміряти точний час, проведений процесом на CPU, і зменшити його залишковий квант або оновити лічильники у BPF-мапі.

## 4. Ієрархія черг диспетчеризації (DSQ)

Черги диспетчеризації (Dispatch Queues - DSQ) є центральним механізмом абстракції в `sched_ext`. Вони слугують мостом між BPF-програмою та апаратними ядрами CPU.

![Ієрархія черг диспетчеризації (DSQ)](/reference/unix-linux/processes/sched-ext-ebpf-scheduler/img/sched-ext-dsq.svg)
*Схема руху завдань через глобальні, локальні та користувацькі черги DSQ.*

У `sched_ext` існує три категорії черг DSQ:

### 4.1. Глобальна черга (SCX_DSQ_GLOBAL)

Глобальна черга системного рівня, створена ядром за замовчуванням. Вона працює за принципом FIFO (First In, First Out). Будь-який процесор у системі, який стає idle, може автоматично забирати завдання з `SCX_DSQ_GLOBAL`, якщо його локальна черга порожня.

Глобальна черга чудово підходить для простих планувальників та симетричних багатопроцесорних систем (SMP), але створює контенцію замок-пам'ять при великій кількості ядер (понад 64 CPU).

### 4.2. Локальні черги CPU (SCX_DSQ_LOCAL)

Кожен процесор у системі має свою власну локальну чергу `SCX_DSQ_LOCAL`. Завдання, розміщене у `SCX_DSQ_LOCAL`, може бути виконане **тільки** цим конкретним CPU.

Використання локальних черг забезпечує максимальну локальність кешу L1/L2 та відсутність міжпроцесорних блокувань. BPF-програма може явно відправляти завдання в локальну чергу конкретного процесора за допомогою макроса:

```c
scx_bpf_dispatch(p, SCX_DSQ_LOCAL_ON(target_cpu), SCX_SLICE_DFL, enq_flags);
```

### 4.3. Користувацькі черги BPF (Custom DSQs)

Розробник BPF-планувальника може створити до `2^63 - 1` власних черг за допомогою системного виклику `scx_bpf_create_dsq(dsq_id, node)` під час ініціалізації (`ops.init`).

Власні черги дозволяють будувати складні багаторівневі ієрархії:
- Черга високого пріоритету для інтерактивних GUI-потоків.
- Черга низького пріоритету для фонових обчислень.
- Окремі черги для кожного NUMA-вузла або L3-кеш кластера.

Усі деталі реалізації такої черги продемонстровано у [реалізації FIFO-планувальника](book:unix-linux/sched-ext-ebpf-scheduler/proj-scx-simple-fifo.md).

## 5. Гібридне та User-Space планування

Одним із найпотужніших архітектурних проривів `sched_ext` є можливість створення **гібридних планувальників**, де прийняття складних рішень делегується фоновому демону у просторі користувача (User-Space Daemon).

Виконання коду у просторі ядра (навіть у BPF) завжди обмежене: у BPF заборонено обчислення з плаваючою комою (floating point / SIMD), використання складних графічних алгоритмів та виділення великих обсягів динамічної пам'яті. Гібридна архітектура долає ці обмеження.

```
  +-------------------------------------------------------------+
  | USER SPACE: Демон розкладу (Rust / C++ / Go)               |
  | • Математичні моделі, машийне навчання, аналіз тоології     |
  | • Обчислення оптимальних пріоритетів та квотування          |
  +-------------------------------------------------------------+
        ^                                               |
        | BPF Ringbuffer                                | BPF Array Maps
        | (Події: task_wake, task_exit)                 | (Оновлені масиви/пріоритети)
        |                                               v
  +-------------------------------------------------------------+
  | KERNEL SPACE: BPF_PROG_TYPE_STRUCT_OPS                      |
  | • ops.enqueue() / ops.dispatch()                            |
  | • Тонкий шар: читає рішення з BPF Map і робить dispatch     |
  +-------------------------------------------------------------+
```

### Модель взаємодії: BPF Ringbuffer та BPF Maps

1. **Ядро -> User-Space:** Коли в ядрі відбуваються події (поява нового процесу, засинання, зміна cgroup), BPF-програма відправляє коротке повідомлення через `BPF_MAP_TYPE_RINGBUF` до користувацького демона.
2. **User-Space Обчислення:** Демон (наприклад, написаний на Rust або C++) у окремому потоці обробляє потік подій. Він може враховувати дані про температуру CPU, рівень заряду батареї, мережеву активність або топологію контейнерів.
3. **User-Space -> Ядро:** Демон записує обчислені рішення (якому процесу надати який CPU і квант часу) у спільно використовувану мапу `BPF_MAP_TYPE_ARRAY` або `BPF_MAP_TYPE_HASH`.
4. **Виконання в ядрі:** При наступному виклику `ops.dispatch` BPF-програма в ядрі просто зчитує готовий результат із мапи за `O(1)` і миттєво передає завдання процесору.

### Область спільної пам'яті BPF Arena (Linux 6.9+)

Починаючи з ядра Linux 6.9, підсистема eBPF отримала підтримку `BPF_MAP_TYPE_ARENA`. Вона дозволяє виділяти спільний регіон віртуальної пам'яті, який доступний одночасно BPF-програмі у режимі ядра та завантажувачу у просторі користувача за одними й тими самими 64-бітними покажчиками.

Це усунуло необхідність копіювання даних через BPF ringbuffers. Демон у користувацькому просторі опитує або оновлює складні структури даних (наприклад, графік залежностей завдань чи черги пріоритетів), а BPF-хуки ядра зчитують покажчики напряму з Arena без додаткових системних викликів.

### Реальні приклади екосистеми SCX

Спільнота розробників `sched_ext` створила репозиторій відкритих планувальників `scx`, які демонструють різні підходи:

- **`scx_rustland`**: Планувальник, де вся логіка прийняття рішень винесена в демон на мові Rust. BPF-частина ядра слугує лише безперебійним виконавцем команд. Сбій у Rust-демоні не викликає падіння ядра — ядро просто безпечно вивантажує планувальник.
- **`scx_lavd` (Latency-critical Audio-Video & Gaming Scheduler)**: Спеціалізований планувальник для ігор та мультимедіа. Він аналізує критичність затримок кадрів (frame pacing) і гарантує, що ігрові потоки не зазнають мікрозависань від фонових завдань ОС.
- **`scx_bpfland`**: Високоефективний планувальник, який повністю виконується всередині BPF у ядрі, забезпечуючи мінімальні overhead на серверах баз даних.

## 6. Інтеграція з cgroups, NUMA та керуванням живленням (EAS)

У реальних виробничих середовищах планувальник не працює в ізоляції. Він повинен поважати обмеження cgroups v2, враховувати топологію пам'яті NUMA та інтегруватися з підсистемою керування живленням (CPUfreq / Energy-Aware Scheduling).

### 6.1. Підтримка cgroups v2 та регулювання ресурсів

`sched_ext` підтримує ієрархію cgroups v2 через хуки `ops.cgroup_init`, `ops.cgroup_exit` та `ops.cgroup_move`. BPF-програма отримує доступ до полів вагових коефіцієнтів `cgroup->weight` та лімітів квантів `cpu.max`.

Це дозволяє будувати планувальники, які гарантують суворий розподіл ресурсів між контейнерами: наприклад, надавати контейнерам баз даних 70% обчислювальної потужності сокета, а фоновим вебобробникам — залишок 30%. При цьому BPF-планувальник може реалізувати більш гнучку політику розподілу невикористаного кванту часу (bursting), аніж жорсткий токенний алгоритм CFS Bandwidth Control.

### 6.2. Врахування топології NUMA та L3-кешу

На сучасних серверних процесорах (наприклад, AMD EPYC або Intel Xeon) доступ до пам'яті сусіднього сокета через міжпроцесорну шину (UPI / Infinity Fabric) забирає в 2.5 рази більше часу, ніж доступ до локального вузла NUMA.

`sched_ext` дозволяє створювати окремі черги Custom DSQ для кожного NUMA-вузла (`scx_bpf_create_dsq(dsq_id, node_id)`). При пробудженні завдання BPF-хук `select_cpu` перевіряє вузол пам'яті потоку і направляє його виключно в DSQ відповідного сокета. Це усуває постійну міграцію потоків між вузлами та стабілізує затримки L3-кешу.

### 6.3. Підтримка SMT Core Scheduling (SCX_OPS_HAS_CORE)

У середовищах з підвищеними вимогами до безпеки (хмарні гіпервізори, мультиарендні контейнери) апаратні гіперпотоки (SMT / Hyper-Threading) створюють загрозу витоку даних через сторонні канали процесора (Side-Channel Attacks, такі як Spectre, MDS, L1TF).

Ввімкнення прапорця `SCX_OPS_HAS_CORE` активує в `sched_ext` підтримку SMT Core Scheduling. Ядро гарантує, що на двох апаратних потоках одного фізичного ядра можуть одночасно виконуватися лише потоки з однієї групи довіри (Core Tag). Якщо в BPF-черзі є завдання з іншої cgroup, `sched_ext` призупиняє сусідній гіперпотік, запобігаючи виконанню чужого коду на спільному L1-кеші.

### 6.4. Енергоефективність на ARM big.LITTLE (EAS)

На мобільних пристроях (Android) та процесорах з гетерогенними ядрами (Intel Alder Lake / ARM DynamIQ) ядра діляться на високопродуктивні (Performance Cores) та енергоефективні (Efficient Cores).

`sched_ext` отримує дані про емпіричну потужність ядер через хелпери ядра `arch_scale_cpu_capacity()`. BPF-планувальник може динамічно направляти інтерактивні GUI-потоки та ігрові обробники на P-ядра, а фонові демони синхронізації — на E-ядра, оптимізуючи споживання акумулятора та уникаючи перегріву SoC.

## 7. Безпека, Watchdog та механізм Fallback

Найважливішою вимогою при розробці `sched_ext` була абсолютна надійність системи. Якщо BPF-програма містить логічну помилку (наприклад, «забуває» помістити процес у чергу, створюючи starvation), система не повинна зависати.

Для захисту від таких ситуацій у `sched_ext` вбудовано підсистему **scx_watchdog**.

```
         +---------------------------------------------+
         | BPF Планувальник виконує ops.enqueue()      |
         +---------------------------------------------+
                                |
                                v
         +---------------------------------------------+
         | Завдання у стані RUNNABLE понад 3 секунди?  |
         +---------------------------------------------+
                   /                         \
                 Ні                           Так
                 /                             \
        v                                       v
[Нормальне виконання]                [Спрацьовує scx_watchdog]
                                                |
                                                v
                                     [Викликається ops.error()]
                                                |
                                                v
                                     [Аварійний Fallback:       ]
                                     [Вивантаження BPF         ]
                                     [Перехід усіх task на EEVDF]
```

### Принцип роботи Watchdog та Fallback

1. **Моніторинг таймаутів:** Ядро відстежує кожен процес у `ext_sched_class`. Якщо процес перебуває у стані `RUNNABLE`, але не отримує процесорного часу протягом заданого таймауту (за замовчуванням 3 секунди), сторожовий таймер `scx_watchdog` фіксує збій планувальника.
2. **Аварійний виклик `ops.error()`:** Ядро зупиняє виконання BPF-програми, фіксує стековий дамп і викликає callback `ops.exit()` із кодом помилки.
3. **Автоматичний Fallback на EEVDF:** Ядро атомарно переводить усі процеси з `ext_sched_class` назад під управління стандартного планувальника `fair_sched_class` (EEVDF/CFS).
4. **Збереження працездатності:** Операційна система продовжує роботу без жодної втрати даних чи перезавантаження. Адміністратор бачить детальну інформацію про причину вигрузки у системному журналі `dmesg`.

Таймаут сторожового таймера можна налаштувати у системному файлі `/sys/kernel/sched_ext/watchdog_duration_us`. На робочих серверах його значення зазвичай становить від 1 до 5 секунд.

## 8. Простеження, інспекція та діагностика

Для адміністрування та налагодження BPF-планувальників ядро Linux надає багатий інструментарій інспекції.

### 8.1. Псевдофайлова система sysfs

Стан підсистеми `sched_ext` експортується через директорію `/sys/kernel/sched_ext/`:

```bash
# Перевірка поточного стану планувальника
cat /sys/kernel/sched_ext/state
# Можливі значення: disabled, enabled, switching

# Перевірка назви активного BPF-планувальника
cat /sys/kernel/sched_ext/root/ops_name
# Вивід: simple_fifo_demo

# Налаштування таймауту сторожового таймера (у мікросекундах)
echo 5000000 > /sys/kernel/sched_ext/watchdog_duration_us
```

### 8.2. Трасування через tracepoints та bpftool

Ядро експортує спеціалізовані точки трасування `tracepoint:sched_ext:*`, які дозволяють моніторити роботу планувальника в реальному часі за допомогою `bpftool` або `bcc/bpftrace`:

```bash
# Відстеження подій переключення та помилок sched_ext
sudo bpftrace -e 'tracepoint:sched_ext:sched_ext_dump { printf("SCX Error: %s\n", args->reason); }'

# Перевірка завантажених BPF struct_ops у ядрі
sudo bpftool struct_ops list
```

У разі виникнення помилки у BPF-планувальнику BPF-хелпер `scx_bpf_dump()` дозволяє зберегти внутрішній стан черг DSQ у кільцевий буфер ядра, що спрощує пошук причин взаємних блокувань (deadlocks).

## 9. Практичне застосування та висновки

Технологія `sched_ext` радикально змінює парадигму розвитку системного планування у Linux. Замість спроб створити один універсальний планувальник, який одночасно задовольняв би протилежні вимоги баз даних, графічних ігор та енергоефективних смартфонів, ядро надає безпечний розширювальний шар.

Основні переваги використання `sched_ext`:
- **Безпечні експерименти:** Розробники можуть створювати та тестувати нові алгоритми планування у просторі користувача чи BPF без ризику викликати Kernel Panic.
- **Швидкість адаптації:** Спеціалізовані рішення для баз даних чи ігрових консолей впроваджуються за дні, а не чекають роками на прийняття патчів у mainline ядро.
- **Гарантована надійність:** Спрацювання `scx_watchdog` миттєво повертає систему під контроль перевіреного EEVDF, гарантуючи безперебійність сервісів.

> 🔧 **Навіщо це у реальній розробці.**
> `sched_ext` змінює підхід до оптимізації інфраструктури. Замість того щоб підлаштовувати архітектуру високопродуктивних застосунків під фіксовану логіку планувальника ядра, інженери можуть створити спеціалізований eBPF-планувальник для конкретного типу навантаження. Це дозволяє досягти мінімальних затримок обробки мережевих пакетів у HFT, виключити мікрофрізи в Linux-іграх та суттєво підвищити щільність упаковки контейнерів у хмарних дата-центрах.
