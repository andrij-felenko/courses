# 📋 Інтерфейс та хуки struct sched_ext_ops

Специфікація контракту `struct sched_ext_ops` визначає точну точку інтеграції між ядром Linux та користувацькою логікою BPF-планувальника. Об'єкт `sched_ext_ops` реєструється в ядрі за допомогою механізму BPF `struct_ops` (`SEC(".struct_ops.link")`). Коли BPF-планувальник завантажується у систему, ядро аналізує поля цієї структури, перевіряє безпеку кожного виклику через eBPF Verifier та підміняє таблицю покажчиків класу `ext_sched_class` на відповідні JIT-скомпільовані інструкції.

Нижче наведено докладну специфікацію функціональних хуків, бітових прапорців конфігурації та системних BPF-хелперів (`scx_bpf_*`), необхідних для розробки та діагностики розширень планувальника.

### 1. Основні хуки життєвого циклу (Callbacks)

Усі хуки приймають покажчик на структуру `struct task_struct *p` або контекст процесора. Таблиця нижче описує ключові функції, момент їх виклику ядром та контекст виконання.

| Назва хука | Сигнатура BPF-функції | Момент виклику ядра | Обов'язковість |
| :--- | :--- | :--- | :--- |
| `select_cpu` | `s32 (*select_cpu)(struct task_struct *p, s32 prev_cpu, u64 wake_flags)` | Викликається при пробудженні завдання для вибору цільового CPU. | Ні (опціональний) |
| `enqueue` | `void (*enqueue)(struct task_struct *p, u64 enq_flags)` | Завдання стає runnable. Повинно бути поміщено у DSQ. | **Так (обов'язковий)** |
| `dequeue` | `void (*dequeue)(struct task_struct *p, u64 deq_flags)` | Завдання перестає бути runnable (переходить у сон чи блокується). | Ні (опціональний) |
| `dispatch` | `void (*dispatch)(s32 cpu, struct task_struct *prev)` | Ядро шукає наступне завдання для виконання на `cpu`. | Ні (опціональний) |
| `running` | `void (*running)(struct task_struct *p)` | Завдання `p` призначено на CPU і воно починає виконання. | Ні (опціональний) |
| `stopping` | `void (*stopping)(struct task_struct *p, bool runnable)` | Завдання `p` знімається з CPU (вичерпано квант або заблоковано). | Ні (опціональний) |
| `yield` | `void (*yield)(struct task_struct *from, struct task_struct *to)` | Завдання викликає системний виклик `sched_yield()`. | Ні (опціональний) |
| `init_task` | `s32 (*init_task)(struct task_struct *p, struct scx_init_task_args *args)` | Створення нового завдання в системі (`fork` / `clone`). | Ні (опціональний) |
| `exit_task` | `void (*exit_task)(struct task_struct *p, struct scx_exit_task_args *args)` | Завершення роботи завдання (`do_exit`). | Ні (опціональний) |
| `init` | `s32 (*init)(void)` | Викликається при завантаженні BPF-планувальника в ядро. | Ні (опціональний) |
| `exit` | `void (*exit)(struct scx_exit_info *info)` | Викликається при вивантаженні планувальника або аварійному fallback. | Ні (опціональний) |

Хук `enqueue` є єдиним обов'язковим callback-методом. Якщо інші хуки не реалізовано, ядро підставляє власні стандартні обгортки за замовчуванням (Default Callbacks). Наприклад, відсутність `select_cpu` змушує ядро використовувати стандартний обхід топології CPU ядра Linux.

Під час виконання хуків `enqueue` та `dispatch` ядро утримує спинлок черги виконання процесора (`rq->lock`). З цієї причини всередині BPF-хуків заборонено виконувати системні операції, що можуть призвести до переключення контексту або блокування потоку. Порушення цього правила приведе до негайного відхилення програми на етапі перевірки eBPF Verifier.

### 2. Прапорці та параметри конфігурації (Ops Flags)

Поле `ops.flags` містить бітову маску конфігурації, яка визначає глобальну поведінку `sched_ext` ядра:

```c
struct sched_ext_ops my_ops = {
    .flags = SCX_OPS_HAS_CORE | SCX_OPS_SWITCH_PARTIAL,
    .name  = "my_custom_scheduler",
};
```

Значення бітових констант та їхній системний вплив:
- `SCX_OPS_HAS_CORE` — вмикає підтримку SMT Core Scheduling. Цей прапорець гарантує, що при виконанні завдань на апаратних гіперпотоках (Hyper-Threads) одного фізичного ядра `sched_ext` синхронізує їхній вибір, запобігаючи витоку даних через сторонні канали процесора (side-channel attacks, такі як Spectre або L1TF).
- `SCX_OPS_SWITCH_PARTIAL` — переводить у режим `sched_ext` лише ті процеси, для яких явно встановлено политику `SCHED_EXT` за допомогою системного виклику `sched_setscheduler()`. За замовчуванням (якщо прапорець відсутній) `sched_ext` перехоплює **усі** звичайні процеси `SCHED_NORMAL` у системі.
- `SCX_OPS_KEEP_BUILTIN_IDLE` — зберігає стандартну логіку пошуку вільних процесорів ядра Linux при виклику `scx_bpf_select_cpu_dfl()`. Це дозволяє уникнути потреби вручну аналізувати стани сну процесора (C-states).
- `SCX_OPS_ENQ_LAST` — налаштовує ядро передавати інформацію про те, чи був потік останнім виконуваним на процесорі перед зупинкою.

### 3. Основні BPF-хелпери ядра (scx_bpf_*)

Для управління чергами та станом завдань ядро надає спеціальний набір BPF helper-функцій, які можна викликати з контексту `sched_ext_ops`:

#### scx_bpf_dispatch()
Поміщає завдання `p` у вказану чергу диспетчеризації (DSQ).
```c
void scx_bpf_dispatch(struct task_struct *p, u64 dsq_id, u64 slice, u64 enq_flags);
```
- `p` — покажчик на структуру завдання.
- `dsq_id` — ідентифікатор черги (`SCX_DSQ_GLOBAL`, `SCX_DSQ_LOCAL` або власний ID, створений через `scx_bpf_create_dsq`).
- `slice` — квант часу виконання в наносекундах (наприклад, `SCX_SLICE_DFL` дорівнює 20 мс).
- `enq_flags` — прапорці входу (`SCX_ENQ_HEAD` для додавання в початок черги).

#### scx_bpf_consume()
Переміщує перше завдання з вказаної черги `dsq_id` у локальну чергу поточного CPU для негайного виконання.
```c
bool scx_bpf_consume(u64 dsq_id);
```
Повертає `true`, якщо завдання було успішно вилучено з черги і призначено на виконання, або `false`, якщо черга була порожньою.

#### scx_bpf_create_dsq()
Створює нову власну чергу диспетчеризації (Custom DSQ) з вказаним 64-бітним ID.
```c
s32 scx_bpf_create_dsq(u64 dsq_id, s32 node);
```
- `dsq_id` — унікальний ідентифікатор черги (значення від `1` до `2^63 - 1`).
- `node` — ідентифікатор NUMA-вузла (-1 для поточного вузла). Повертає `0` при успіху або від'ємний код помилки.

#### scx_bpf_kick_cpu()
Насилає міжпроцесорне переривання (IPI — Inter-Processor Interrupt) на вказаний `cpu`, примушуючи його викликати `ops.dispatch` та перепланувати виконання.
```c
void scx_bpf_kick_cpu(s32 cpu, u64 flags);
```
- `flags` — `SCX_KICK_IDLE` (викликати виключно якщо CPU зараз перебуває в стані idle) або `SCX_KICK_PREEMPT` (примусово витіснити поточне завдання).

#### scx_bpf_select_cpu_dfl()
Викликає стандартну логіку ядра Linux для пошуку найоптимальнішого вільного CPU для завдання `p`.
```c
s32 scx_bpf_select_cpu_dfl(struct task_struct *p, s32 prev_cpu, u64 wake_flags, bool *is_idle);
```
Використовується усередині хука `ops.select_cpu`, якщо BPF-програма не хоче самостійно обходити топологію кешів для простих завдань.

#### scx_bpf_dump()
Фіксує поточний стан BPF-планувальника та відправляє діагностичний дамп у журнал ядра у разі виявлення внутрішньої аномалії чи таймауту.
```c
void scx_bpf_dump(const char *fmt, ...);
```

### 4. Прапорці контексту входу (enq_flags)

Під час додавання завдання у чергу через `ops.enqueue(p, enq_flags)` параметр `enq_flags` передає стан процесу:
- `SCX_ENQ_WAKEUP` — завдання прокинулося після очікування події I/O або таймера.
- `SCX_ENQ_HEAD` — вимога помістити потік у початок черги DSQ для пріоритетного виконання.
- `SCX_ENQ_REENQ` — повторне вставлення завдання у чергу після зміни його конфігурації.
- `SCX_ENQ_LAST` — вказує, що завдання було останнім виконуваним потоком на даному процесорі.

Використання цих прапорців дозволяє BPF-планувальнику точніше адаптувати кванти часу та обирати відповідні черги для збереження максимальної чутливості інтерактивних застосунків.

### 5. Обробка помилок та аварійне вивантаження

При виникненні внутрішніх помилок (наприклад, спробі вставити завдання в неіснуючу чергу DSQ або перевищенні квот пам'яті) BPF-планувальник викликає хелпер `scx_bpf_error()`. Цей виклик негайно ініціює процедуру зупинки BPF-програми. Ядро фіксує номер лінії коду та текстовий опис помилки, після чого запускає механізм аварійного вивантаження `scx_watchdog` та повертає всі процеси системи під контроль EEVDF.
