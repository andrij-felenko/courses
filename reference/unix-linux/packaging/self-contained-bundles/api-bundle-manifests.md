# 📋 Специфікація маніфестів AppImage, Flatpak та Snap

Цей довідник містить повну технічну специфікацію структур файлів конфігурації, декларативних маніфестів та змінних середовища виконання для трьох основних форматів самодостатніх пакунків у Linux: AppImage, Flatpak та Snap. Опис охоплює внутрішню організацію файлових точок, специфікацію ключів маніфестів, параметри контролю доступу, формат файлів метаданих, конфігурацію заміщення шляхів (layout overrides) та системи інтерфейсів взаємодії з хост-системою.

## 1. Специфікація AppImage

Формат AppImage свідомо відмовляється від централізованого декларативного файлу конфігурації у форматі JSON або YAML на користь прозорої файлової структури. Замість цього розробник формує каталог `AppDir`, який містить бінарні файли, залежні бібліотеки, метадані Freedesktop та точку входу `AppRun`. Під час генерації кінцевого бандла утиліта `appimagetool` упаковує вміст `AppDir` у образ SquashFS і приєднує до його початку бінарний ELF-лаунчер.

### 1.1 Структура каталогу AppDir

Каталог `AppDir` являє собою сире дерево файлів, що повторює стандартну ієрархію каталогу розпакованого програмного забезпечення:

```
MyApp.AppDir/
├── AppRun                    [Обов'язковий: виконуваний файл або скрипт точки входу]
├── myapp.desktop             [Обов'язковий: Desktop-файл специфікації Freedesktop]
├── myapp.png                 [Обов'язковий: іконка застосунку або піктограма]
├── .DirIcon                  [Символічне посилання на myapp.png]
└── usr/                      [Стандартна файлова структура розпакованого ПЗ]
    ├── bin/                  [Головний бінарний файл застосунку]
    ├── lib/                  [Усі необхідні .so бібліотеки]
    └── share/                [Ресурси, локалі, графічні теми]
```

При старті AppImage бінарна частина `AppRun` монтує цей образ у тимчасовий каталог файлової системи за допомогою FUSE і виставляє системні змінні оточення.

### 1.2 Метадані специфікації Desktop Entry у AppImage

Файл `.desktop`, розміщений у корені `AppDir`, не лише додає ярлик у меню операційної системи, але й надає метадані для утиліти збірки `appimagetool`. Маніфест повинен відповідати специфікації Freedesktop та містити розширені ключі AppImage:

```ini
[Desktop Entry]
Name=MyApp
Exec=myapp %U
Icon=myapp
Type=Application
Categories=Utility;Development;
Terminal=false
StartupWMClass=myapp
X-AppImage-Version=1.2.4
X-AppImage-BuildId=bf738e4a-58bc
```

Ключ `X-AppImage-Version` визначає версійну мітку бандла, а `X-AppImage-BuildId` слугує унікальним криптографічним ідентифікатором для системи атомарних дельта-оновлень `appimageupdate`. Якщо бінарний файл `AppRun` не знаходить сумісного FUSE-драйвера в системі, він може використовувати цей ідентифікатор для виклику режиму аварійного розпакування.

### 1.3 Змінні середовища оточення AppRun

Під час запуску `.AppImage` лаунчер `AppRun` експортує низку важливих системних змінних оточення безпосередньо в процес цільового застосунку:

| Змінна | Тип | Опис та значення для процесів |
| :--- | :--- | :--- |
| `APPDIR` | `String (Path)` | Абсолютний шлях до тимчасової точки монтажу SquashFS (наприклад, `/tmp/.mount_AppXYZ123`). Використовується програмою для пошуку своїх ресурсів. |
| `APPIMAGE` | `String (Path)` | Абсолютний шлях до оригінального `.AppImage`-файлу на диску, який запустив користувач. |
| `OWD` | `String (Path)` | Оригінальний робочий каталог (Original Working Directory), з якого було здійснено виклик команди. |
| `ARGV0` | `String` | Початкове значення `argv[0]`, передане під час первинного виклику лаунчера. |
| `LD_LIBRARY_PATH` | `String (Colon list)` | Шляхи до бібліотек, модифіковані з додаванням `$APPDIR/usr/lib:$APPDIR/lib` на початок списку. |
| `PATH` | `String (Colon list)` | Шляхи до виконуваних файлів з додаванням `$APPDIR/usr/bin:$APPDIR/bin`. |
| `XDG_DATA_DIRS` | `String (Colon list)` | Модифікований список точок даних із додаванням `$APPDIR/usr/share` для знаходження іконок та пиктограм. |
| `APPIMAGE_EXTRACT_AND_RUN` | `Integer (0/1)` | При значенні `1` змушує лаунчер розпакувати SquashFS у тимчасову теку замість використання FUSE (корисно для Docker-контейнерів). |
| `APPIMAGE_SILENT` | `Integer (0/1)` | Придушує вивід інформаційних повідомлень лаунчера `AppRun` у стандартний потік помилок `stderr`. |

### 1.4 Утиліти збірки та валідації AppImage

Генерація AppImage здійснюється за допомогою утиліти `appimagetool`. Команда збірки перевіряє наявність `.desktop`-файла, іконки та бінарника `AppRun`, а потім створює файл пакунка:

```bash
# Валідація структури AppDir та створення кінцевого бінарника
appimagetool --verbose MyApp.AppDir/ MyApp-x86_64.AppImage
```

## 2. Специфікація маніфесту Flatpak

Складання та ізоляція пакунків Flatpak повністю керуються декларативним маніфестом у форматі JSON або YAML. Інструмент автоматизації збірки `flatpak-builder` аналізує цей файл, завантажує потрібні джерела коду, виконує компіляцію у середовищі SDK та формує фінальний бандл для публікації в OSTree-репозиторії.

### 2.1 Головні поля маніфесту Flatpak

Маніфест задає метадані застосунку, ідентифікатори рантаймів, командний рядок запуску та список модулів збірки:

| Поле | Тип | Обов'язкове | Опис призначення |
| :--- | :--- | :---: | :--- |
| `app-id` | `String` | Так | Унікальний ідентифікатор застосунку у форматі зворотного доменного імені (наприклад, `org.gimp.GIMP` або `com.spotify.Client`). |
| `runtime` | `String` | Так | Назва базового рантайму, який містить спільні бібліотеки (наприклад, `org.gnome.Platform` або `org.kde.Platform`). |
| `runtime-version` | `String` | Так | Конкретна версія базового рантайму (наприклад, `45` або `6.6`). |
| `sdk` | `String` | Так | Назва комплекту розробника (SDK), що містить заголовочні файли та компілятори (`org.gnome.Sdk`). |
| `command` | `String` | Так | Назва або відносний шлях виконуваного файла у `/app/bin`, який запускається при команді `flatpak run`. |
| `finish-args` | `Array[String]` | Так | Перелік прапорів пісочниці `bubblewrap`, що декларують потрібні дозволи до ресурсів операційної системи. |
| `modules` | `Array[Object]` | Так | Масив опису модулів для компіляції вихідного коду програми та її специфічних залежностей. |
| `sdk-extensions` | `Array[String]` | Ні | Список розширень SDK, необхідних під час компіляції (наприклад, `org.freedesktop.Sdk.Extension.rust-stable`). |
| `tags` | `Array[String]` | Ні | Теги категорії та стану готовності для відображення у каталогах ПЗ (`nightly`, `beta`). |

### 2.2 Аргументи завершення (finish-args) та дозволи пісочниці

Секція `finish-args` визначає межі безпеки пісочниці `bubblewrap`. Кожен прапор у цій секції транслюється у параметри створення просторів імен та монтування файлових точок:

```json
"finish-args": [
    "--share=network",             /* Дозвіл на використання мережевих сокетів хоста */
    "--share=ipc",                 /* Дозвіл на міжпроцесну взаємодію IPC */
    "--socket=fallback-x11",       /* Доступ до графічного сервера X11 */
    "--socket=wayland",            /* Доступ до графічного сервера Wayland */
    "--socket=pulseaudio",         /* Доступ до звукового сервера PulseAudio / PipeWire */
    "--device=dri",                /* Доступ до апаратного прискорення GPU (Direct Rendering Infrastructure) */
    "--filesystem=host",           /* Доступ до всієї файлової системи (не рекомендовано з міркувань безпеки) */
    "--filesystem=home",           /* Доступ до домашнього каталогу користувача */
    "--filesystem=~/.config/myapp:ro", /* Доступ лише для читання до конкретної конфігураційної теки */
    "--talk-name=org.freedesktop.secrets" /* Дозвіл на виклик специфічного D-Bus сервісу шифрування */
]
```

Прапор `--filesystem=host` слід використовувати з крайньою обережністю, оскільки він фактично нівелює ізоляцію пісочниці, надаючи бінарним файлам доступ до виконання та читання конфіденційних даних користувача.

### 2.3 Структура генеруваного файла metadata

Після компіляції `flatpak-builder` створює системний файл метаданих `metadata`, який розміщується всередині OSTree-комміту:

```ini
[Application]
name=org.example.MyApp
runtime=org.gnome.Platform/x86_64/45
sdk=org.gnome.Sdk/x86_64/45
command=myapp

[Context]
shared=network;ipc;
sockets=x11;wayland;pulseaudio;
filesystems=home;

[Session Bus Policy]
org.freedesktop.secrets=talk
```

### 2.4 Специфікація модуля збірки (Module Object)

Кожен елемент масиву `modules` описує окремий вихідний компонент або залежність, яку необхідно завантажити, зібрати та встановити у каталог `/app`:

```json
{
    "name": "libfoo",
    "buildsystem": "autotools",     /* Системи збірки: autotools, cmake, cmake-ninja, meson, simple */
    "config-opts": [
        "--enable-shared",
        "--disable-static"
    ],
    "build-options": {
        "cflags": "-O2 -g",
        "env": {
            "MY_VAR": "value"
        }
    },
    "cleanup": [
        "/include",
        "*.a",
        "/share/doc"
    ],
    "sources": [
        {
            "type": "archive",       /* Типи джерел: archive, git, file, script, dir */
            "url": "https://example.com/src/libfoo-1.0.tar.gz",
            "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
        }
    ]
}
```

### 2.5 Інструментарій збірки та публікації flatpak-builder

Утиліта `flatpak-builder` забезпечує локальну компіляцію у пісочниці та публікацію пакунків:

```bash
# Збірка програми та її локальна інсталяція для поточного користувача
flatpak-builder --user --install build-dir org.example.MyApp.json --force-clean
```

## 3. Специфікація маніфесту Snap (snapcraft.yaml)

Система Snap використовує єдиний декларативний конфігураційний файл `snap/snapcraft.yaml`. Цей файл описує як метадані публікації в Snap Store, так і інструкції збірки, рівні обмеження ізоляції (confinement) та інтерфейси зв'язку (plugs та slots).

### 3.1 Ключові метадані snapcraft.yaml

Таблиця описує основні глобальні параметри конфігурації Snap-пакунка:

| Поле | Тип | Опис призначення |
| :--- | :--- | :--- |
| `name` | `String` | Унікальна назва пакунка у магазині Snap Store (лише малі латинські літери, цифри та дефіс). |
| `version` | `String` | Версійний рядок застосунку (наприклад, `1.2.0` або `git`). |
| `summary` | `String` | Коротка анотація призначення програми (до 79 символів). |
| `description` | `String` | Детальний багаторядковий опис функціоналу та можливостей програми. |
| `base` | `String` | Базовий Snap-образ дистрибутива (наприклад, `core20`, `core22`, `core24`). |
| `confinement` | `Enum` | Рівень обмеження безпеки: `strict` (ізольований), `classic` (повний доступ), або `devmode`. |
| `grade` | `Enum` | Ступінь готовності до релізу: `stable` (для публікації) або `devel` (для розробників). |
| `architectures` | `Array` | Список цільових апаратних архітектур CPU (`amd64`, `arm64`, `armhf`). |
| `passthrough` | `Object` | Прямий доступ до розширених полів маніфесту snapd, не підтримуваних плагінами. |

### 3.2 Режими обмеження безпеки (confinement)

Snap підтримує три режими контролю доступу, які визначають поведінку AppArmor та seccomp:

* **strict:** Повна ізоляція на основі динамічних профілів AppArmor та seccomp. Програма не має доступу до ресурсів операційної системи, крім явно підключених інтерфейсів (plugs). Це основний стандарт для безпечного десктопного та серверного ПЗ.
* **classic:** Повний доступ до файлової системи та системних викликів без AppArmor-обмежень (подібно до звичайного `.deb` чи `.rpm` пакета). Використовується для IDE, компіляторів та системних інструментів. Публікація в Snap Store вимагає ручної перевірки модераторами.
* **devmode:** Режим розробки та налагодження. Спроби порушення AppArmor-профілю занотовуються у системний журнал `/var/log/syslog`, але виконання не блокується.

### 3.3 Опис застосунків (apps) та служб

Секція `apps` декларує виконувані точки входу, графічні ярлики, змінні оточення та фонові демони systemd:

```yaml
apps:
  myapp:
    command: bin/myapp-wrapper
    desktop: share/applications/myapp.desktop
    completer: share/bash-completion/completions/myapp
    environment:
      MY_APP_DATA: $SNAP_USER_DATA/custom
    plugs:
      - home
      - network
      - network-bind
      - desktop
      - wayland
      - removable-media
  
  myservice:
    command: bin/myserviced
    daemon: simple                  # Варіанти демонів: simple, forking, oneshot, notify
    restart-condition: on-failure
    plugs:
      - network-bind
```

### 3.4 Механізм перенаправлення шляхів (layout overrides)

Секція `layout` у `snapcraft.yaml` дозволяє перенаправляти абсолютні системні шляхи, жорстко зашиті в бінарний код програми, у внутрішні теки Snap без перекомпіляції:

```yaml
layout:
  /usr/share/myapp:
    bind: $SNAP/usr/share/myapp
  /etc/myapp.conf:
    bind-file: $SNAP_DATA/etc/myapp.conf
```

Це дозволяє задовольняти вимоги програм, які розраховують знайти свої конфігураційні файли за зафіксованими абсолютними шляхами FHS.

### 3.5 Стандартні інтерфейси (Plugs)

Інтерфейси зв'язують точки запиту пакунка (plugs) із системними ресурсами хоста (slots):

| Назва Plug | Цільовий ресурс хост-системи | Автоматичне підключення |
| :--- | :--- | :---: |
| `home` | Доступ до читання/запису у домашній теці користувача (`$HOME`). | Так |
| `network` | Створення клієнтських мережевих сокетів (TCP/UDP/Raw). | Так |
| `network-bind` | Відкриття мережевих портів для серверних служб та сокетів. | Так |
| `desktop` | Графічний вивід через X11 та базові сервіси Desktop Environment. | Так |
| `wayland` | Прямий сокет протоколу композитора Wayland. | Так |
| `removable-media` | Доступ до змонтованих зовнішніх накопичувачів у `/media` та `/run/media`. | Ні (потрібен `snap connect`) |
| `system-observe` | Читання метрик системи (`/proc`, `dmesg`, стан процесів). | Ні |
| `hardware-observe` | Читання інформації про пристрої та шини PCI/USB. | Ні |

### 3.6 Секція деталей збірки (parts)

Секція `parts` визначає правила завантаження вихідного коду, вибір компіляційних плагінів та перелік додаткових пакунків Ubuntu для пакування:

```yaml
parts:
  my-part:
    plugin: meson                   # Плагіни: cmake, meson, autotools, python, dump, go, rust
    source: https://github.com/user/project.git
    source-tag: 'v1.2.0'
    meson-parameters:
      - -Dprefix=/usr
    build-packages:                 # Пакунки хоста, необхідні лише під час компіляції
      - build-essential
      - libglib2.0-dev
    stage-packages:                 # .deb пакунки Ubuntu, які копіюються всередину Snap
      - libglib2.0-0
      - libpng16-16
```

### 3.7 Управління збіркою через утиліту snapcraft

Утиліта `snapcraft` використовує контейнери LXD або Multipass для чистої збірки пакунків:

```bash
# Запуск чистої збірки Snap у контейнері
snapcraft --debug
```

## 4. Зведена порівняльна специфікація

Нижче наведено зведені характеристики маніфестів та середовищ виконання всіх трьох форматів:

| Параметр | AppImage | Flatpak | Snap |
| :--- | :--- | :--- | :--- |
| **Формат конфігурації** | Структура каталогу AppDir | Декларативний JSON / YAML | Декларативний `snapcraft.yaml` |
| **Інструмент збірки** | `appimagetool` | `flatpak-builder` | `snapcraft` |
| **Контроль доступу** | Змінні оточення (без пісочниці) | `finish-args` (bwrap namespaces) | `plugs` (AppArmor + seccomp) |
| **Базове середовище** | Усередині пакунка | `runtime` + `runtime-version` | `base: coreXX` |
| **Підтримка демонів** | Ні | Ні | Так (`daemon: simple/forking`) |
