# 📋 Специфікація конфігурацій довіри та метаданих репозиторіїв

Формальні специфікації файлів конфігурації, заголовочних полів метаданих, структур індексів та директив криптографічної довіри визначають сумісність пакетних менеджерів APT (Debian, Ubuntu) та DNF/RPM (Red Hat Enterprise Linux, Fedora, SUSE Linux Enterprise).

---

## 1. Специфікація конфігурації APT Deb822 (`.sources`)

Сучасний стандарт налаштування джерел пакунків у системі APT спирається на розширений формат RFC 822 (deb822). Замість застарілого однорядкового формату `sources.list`, де всі параметри пакувалися в один рядок, deb822 використовує підхід на основі блоків ключ-значення, розділених порожніми рядками. Файли налаштувань розміщуються в каталозі `/etc/apt/sources.list.d/` і повинні мати обов'язкове розширення `.sources`.

Формат deb822 забезпечує високу читабельність, чітку структурованість і дозволяє задавати індивідуальні криптографічні політики для кожного окремого репозиторійного блоку.

### Правила синтаксичного розбору (Parsing Rules)

Парсер APT застосовує наступні формальні правила при розборі файлів `.sources`:

1. **Блочна структура**: Кожен блок описує один репозиторій або групу пов'язаних репозиторіїв. Блоки відокремлюються один від одного принаймні одним порожнім рядком (або рядком, що містить лише символи пробілу).
2. **Формат пар ключ-значення**: Рядок починається з назви ключа, за якою слідує символ двокрапки `:` та значення поля (`Key: Value`). Назви ключів є регістронезалежними (`Signed-By` еквівалентно `signed-by`).
3. **Багаторядкові значення**: Значення полів можуть продовжуватися на наступних рядках, якщо кожен наступний рядок починається з принаймні одного символу пробілу або табуляції. Це часто використовується для визначення списків URI або вбудованих ключів GPG.
4. **Коментарі**: Рядки, що починаються з символу `#`, вважаються коментарями й повністю ігноруються парсером. Коментарі не можуть розривати багаторядкові значення полів.

### Повний перелік полів конфігурації deb822

Нижче наведено формальну специфікацію полів, які підтримуються парсером APT при обробці конфігураційних блоків репозиторіїв.

| Поле | Обов'язкове | Тип даних | Опис, семантика та допустимі значення |
| :--- | :---: | :---: | :--- |
| `Types` | Так | Список | Типи вмісту репозиторію. Допустимі значення: `deb` (бінарні пакунки) та `deb-src` (початковий код програм). |
| `URIs` | Так | Список URI | Базові мережеві адреси репозиторію (`http://`, `https://`, `file://`, `ftp://`, `cdrom:`). |
| `Suites` | Так | Рядок/Список | Кодове ім'я релізу дистрибутиву (`jammy`, `noble`, `bookworm`) або шлях до дистрибуції. |
| `Components` | Так | Список | Секції або категорії репозиторію (`main`, `restricted`, `universe`, `multiverse`, `contrib`, `non-free`). |
| `Signed-By` | Ні | Шлях/Текст | Криптографічний якір довіри. Передає абсолютний шлях до файлу ключа (`/etc/apt/keyrings/app.gpg`) або вбудований текстовий PGP-блок. |
| `Architectures` | Ні | Список | Обмеження списку цільових архітектур процесора (`amd64`, `arm64`, `i386`, `riscv64`). |
| `Check-Valid-Until` | Ні | Булевий | Контроль перевірки терміну придатності метаданих `Release`. Значення: `yes` (за замовчуванням) або `no`. |
| `Valid-Until-Min` | Ні | Число | Мінімально допустимий термін придатності індексу в секундах (запобігає передчасній заміні). |
| `Valid-Until-Max` | Ні | Число | Максимально допустимий термін придатності індексу в секундах (обмежує час життя кешу). |
| `PDiffs` | Ні | Булевий | Дозвіл на інкрементальне завантаження патчів індексів `Packages` (`yes`/`no`). |
| `By-Hash` | Ні | Рядок | Використання завантаження індексів за хешем `by-hash` (`yes`/`no`/`force`). |

### Повідомлення про обробку поля Signed-By та розбір варіантів застосування

Поле `Signed-By` виконує функцію суворого ізолятора криптографічних повноважень. При аналізі значення цього поля системна бібліотека `libapt-pkg` діє за наступними сценаріями:

- **Випадок 1: Одиничний абсолютний шлях**. Якщо значенням поля є шлях на кшталт `/etc/apt/keyrings/vendor.gpg`, системний менеджер створює новий локальний контекст GPGME й імпортує у нього **виключно** цей відкритий ключ. Перевірка підпису файлу `InRelease` вважається успішною тільки якщо підпис згенеровано цим конкретним ключем. Будь-які інші ключі, присутні в системному масиві `/etc/apt/trusted.gpg.d/`, ігноруються.
- **Випадок 2: Список декількох шляхів**. Якщо значення містить кілька шляхів, розділених пробілом (наприклад, `/etc/apt/keyrings/old.gpg /etc/apt/keyrings/new.gpg`), менеджер підвантажує обидва ключі. Це використовується під час планової ротації ключів підпису мейнтейнера, коли старий і новий ключі діють паралельно.
- **Випадок 3: Вбудований ASCII-armored PGP блок**. Починаючи з версії APT 2.4, утиліта дозволяє вставляти текстовий блок відкритого ключа напряму у поле `Signed-By`. При цьому всі рядки відкритого ключа повинні мати відступ у один пробіл відповідно до синтаксису багаторядкових полів deb822. Це позбавляє необхідності створювати окремі файли на диску та спрощує поширення конфігурацій через інструменти Ansible або Puppet.

### Приклад повної конфігурації deb822

```deb822
Types: deb deb-src
URIs: https://packages.example.com/ubuntu
Suites: noble noble-updates
Components: main enterprise
Architectures: amd64 arm64
Signed-By: /etc/apt/keyrings/example-archive-keyring.gpg
Check-Valid-Until: yes
Valid-Until-Max: 604800
PDiffs: yes
```

## 2. Формат та заголовочні поля файлів `Release` та `InRelease`

Кореневим елементом структури метаданих репозиторію Debian/Ubuntu є файл `Release` (разом з його підписаним аналогом `InRelease`). Цей файл містить підсумкову декларацію стану репозиторію та каскадний список контрольних сум усіх внутрішніх індексів.

### Повний розбір заголовочних полів `Release`

Кожне поле у файлі `Release` виконує чітку функцію в процесі формування локального кешу та перевірки безпеки:

- `Origin`: Рядок, що ідентифікує джерело дистрибутиву (наприклад, `Ubuntu`, `Debian`, `Docker`). Використовується у механізмі пінінгу версій (APT Pinning).
- `Label`: Описова мітка репозиторію, яка відображається у графічних менеджерах пакунків та звітах діагностики.
- `Suite`: Назва поточного релізу або гілки (наприклад, `stable`, `testing`, `noble`). Дозволяє відстежувати стабільність джерела.
- `Codename`: Офіційне кодове ім'я релізу дистрибутиву (наприклад, `noble`, `bookworm`, `bullseye`).
- `Date`: Час формування індексу на сервері збірки у стандартному RFC 1123 / HTTP-date форматі.
- `Valid-Until`: Граничний час дійсності індексу. Після настання цього часу APT вважає індекс застарілим і зупиняє встановлення програм.
- `Acquire-By-Hash`: Булевий прапорець (`yes`/`no`), що вказує, чи підтримує сервер завантаження індексних файлів за їхніми криптографічними SHA-256 хешами через каталоги `/by-hash/`. Це запобігає помилкам `Hash Sum mismatch` під час синхронізації дзеркал.
- `Architectures`: Список усіх архітектур процесорів, підтримуваних у даному репозиторії.
- `Components`: Список усіх підрозділів репозиторію (`main`, `contrib`, `non-free`).
- `Description`: Короткий текстовий опис призначення даного репозиторію.
- `MD5Sum`, `SHA1`, `SHA256`, `SHA512`: Блоки списків файлів, де для кожного індексу (`Packages.xz`, `Sources.xz`, `Icons.tar.gz`) вказується його розмір у байтах та криптографічний хеш відповідного алгоритму. Сучасні версії APT ігнорують застарілі блоки `MD5Sum` та `SHA1` і спираються виключно на `SHA256` та `SHA512`.

```txt
Origin: ExampleOS Corporation
Label: ExampleOS Official Repository
Suite: noble
Codename: noble
Date: Thu, 15 Aug 2026 10:00:00 UTC
Valid-Until: Thu, 22 Aug 2026 10:00:00 UTC
Architectures: amd64 arm64 i386
Components: main universe multiverse
Description: Official production package repository for ExampleOS Linux 24.04 LTS
MD5Sum:
 d41d8cd98f00b204e9800998ecf8427e            12450 main/binary-amd64/Packages
 70f1a89c922572b8d0092c47b59e3557             3410 main/binary-amd64/Packages.gz
SHA256:
 e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855             12450 main/binary-amd64/Packages
 8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4              3410 main/binary-amd64/Packages.gz
 156702b8d0092c47b59e3557e4e0b04e6c38221804f5e71239c03dd087d390c5              1890 main/binary-amd64/Packages.xz
```

### Формат Cleartext Signature в `InRelease`

При створенні файлу `InRelease` вихідний текстовий вміст `Release` обгортається в криптографічну обгортку OpenPGP Cleartext Signature (RFC 4880 Section 7). 

Системна утиліта підпису виконує нормалізацію кінців рядків (перевозячи їх у формат `CRLF`) та обчислює підпис над текстовим тілом:

```txt
-----BEGIN PGP SIGNED MESSAGE-----
Hash: SHA512

<Оригінальний текстовий вміст файлу Release>
-----BEGIN PGP SIGNATURE-----

iQIzBAEBCgAdFiEE4A5... <бінарні дані підпису у форматі Base64>
-----END PGP SIGNATURE-----
```

## 3. Специфікація конфігурації DNF/YUM (`.repo`)

В операційних системах родини Red Hat Enterprise Linux, Fedora, CentOS, Rocky Linux та openSUSE налаштування джерел пакунків зберігаються у файлах конфігурації `/etc/yum.repos.d/*.repo`. Конфігурація використовує класичний синтаксис секцій INI.

### Повний перелік параметрів секції `.repo`

Формальний розбір ключів налаштувань, які інтерпретуються менеджерами `dnf`, `yum` та `zypper`.

| Параметр конфігурації | Тип даних | Опис, поведінка та системні значення |
| :--- | :---: | :--- |
| `[repo_id]` | Ідентифікатор | Унікальна назва секції репозиторію в квадратних дужках (без пробілів). |
| `name` | Текст | Зрозуміла описова назва репозиторію для відображення в інтерфейсі CLI. |
| `baseurl` | URI | Пряма URL-адреса каталогу репозиторію (повинна містити підкаталог `repodata/`). |
| `metalink` | URI | URL-адреса сервісу Metalink для автоматичного вибору найшвидшого дзеркала. |
| `mirrorlist` | URI | URL-адреса файлу зі списком актуальних дзеркал репозиторію. |
| `enabled` | `0` / `1` | Прапорець активації репозиторію. `1` — активний, `0` — проігнорований. |
| `gpgcheck` | `0` / `1` | Вимога криптографічної перевірки PGP-підпису окремих файлів `.rpm`. |
| `repo_gpgcheck` | `0` / `1` | Вимога криптографічної перевірки підпису метаданих репозиторію (`repomd.xml.asc`). |
| `gpgkey` | Список URI | Адреси відкритого ключа GPG (`file:///etc/pki/rpm-gpg/...` або `https://...`). |
| `sslverify` | `0` / `1` | Перевірка TLS-сертифіката вебсервера репозиторію. |
| `sslcacert` | Шлях | Шлях до власного файла CA-сертифіката для перевірки TLS сервера. |
| `sslclientcert` | Шлях | Шлях до клієнтського TLS-сертифіката (mTLS автентифікація). |
| `sslclientkey` | Шлях | Шлях до приватного ключа клієнтського TLS-сертифіката. |
| `metadata_expire` | Час | Час життя кешу метаданих (наприклад, `6h`, `1d`, `never`). |
| `priority` | Число | Пріоритет репозиторію для плагіна `dnf-plugins-core` (від 1 до 99). |
| `cost` | Число | Включення пріоритету вибору дзеркала при розв'язанні залежностей (за замовчуванням 1000). |
| `exclude` | Список | Список шаблонів пакунків, які заборонено встановлювати з цього джерела. |
| `includepkgs` | Список | Список шаблонів пакунків, які дозволено встановлювати виключно з цього джерела. |

### Пояснення взаємодії gpgcheck та repo_gpgcheck у DNF

Параметри перевірки цифрових підписів у DNF забезпечують двоі рівні безпеки:

- Якщо ввімкнено `gpgcheck=1`, менеджер DNF після завантаження `.rpm` файлу звертається до бібліотеки `librpm` і вимагає перевірити підпис у секції **RPM Signature Header**. Якщо відкритий ключ із вказаним Key ID відсутній у базу даних RPM DB, DNF зупиняє встановлення й запитує у користувача дозвіл на імпорт ключа з адреси `gpgkey`.
- Якщо ввімкнено `repo_gpgcheck=1`, менеджер DNF перед розпакуванням метаданих `repodata/repomd.xml` завантажує від'єднаний підпис `repomd.xml.asc` і перевіряє його валідність за допомогою GPG-ключа. Це гарантує, що сам каталог пакунків не був модифікований на сервері дзеркала.

### Приклад конфігурації `.repo` з повною перевіркою

```ini
[example-enterprise-main]
name=Example Enterprise Linux 9 - Production x86_64
baseurl=https://packages.example.com/eel/9/main/x86_64/
enabled=1
gpgcheck=1
repo_gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-example-9
sslverify=1
metadata_expire=12h
priority=10
```

## 4. Структурні теги підпису в RPM Header

Формат пакетів `.rpm` містить внутрішню бінарну секцію **Signature Header**, яка передує основними метаданим пакета. Системна бібліотека `librpm` зчитує цю секцію для перевірки цілісності файлу до його розпакування.

### Теги секції Signature Header

Під час обробки пакета утилітою `rpm -K` (або виклику `rpm PGP verify`) розбираються наступні стандартизовані теги структури:

- `RPMTAG_SIGPGP` (Tag 1002): Містить бінарний OpenPGP-підпис, обчислений над заголовочною секцією пакета (Header).
- `RPMTAG_PGP` (Tag 1003): Містить застарілий OpenPGP-підпис, обчислений над всім вмістом пакета (Header + Payload).
- `RPMTAG_SHA256HEADER` (Tag 1012): Текстовий рядок у шестнадцятирічному форматі, що містить SHA-256 хеш секції Header.
- `RPMTAG_PAYLOADSIZE` (Tag 1007): 64-бітне ціле число, що вказує нестиснутий розмір архіву CPIO з файлами програми.
- `RPMTAG_RSAHEADER` (Tag 1014): Бінарний RSA-підпис секції заголовка.

### Системні команди діагностики ключів та підписів RPM

```bash
# Детальна перевірка підпису конкретного пакета з виведенням Key ID
rpm -K -v package.rpm

# Перегляд усіх імпортованих PGP-ключів у локальній системній базі даних RPM DB
rpm -q gpg-pubkey --qf '%{NAME}-%{VERSION}-%{RELEASE}: %{SUMMARY}\n'

# Видалення застарілого ключа з бази даних RPM за його ідентифікатором
sudo rpm -e gpg-pubkey-a1b2c3d4-5e6f7a8b
```

## 5. Повний довідник кодових помилок верифікації

У цій таблиці зведено всі стандартні коди помилок, що виникають під час криптографічної верифікації індексів і пакетів у системах APT та DNF, із вказівкою діагностичних кроків для їх усунення.

| Повідомлення / Код помилки | Менеджер | Системна причина виникнення | Діагностичні кроки та вирішення |
| :--- | :---: | :--- | :--- |
| `NO_PUBKEY <KEY_ID>` | APT | Відсутній відкритий ключ із вказаним ідентифікатором у локальному `keyring`. | Отримати відкритий ключ розробника, зберегти у `/etc/apt/keyrings/` та вказати у `Signed-By`. |
| `EXPKEYSIG <KEY_ID>` | APT / DNF | Сплив визначений термін дії (Expiration Date) ключа підпису. | Завантажити оновлений файл ключа з продовженим терміном дії від мейнтейнера. |
| `REVKEYSIG <KEY_ID>` | APT / DNF | Ключ підпису було відкликано розробником через компрометацію закритим сертифікатом. | Терміново видалити ключ, оновити джерело репозиторію та замінити ключ на новий. |
| `Hash Sum mismatch` | APT | Хеш завантаженого `Packages` або `.deb` не збігається з записом у `InRelease`. | Перевірити працездатність дзеркала, очистити кеш `apt clean` та перевірити мережевий проксі. |
| `Repository is not signed` | APT / DNF | Відсутній файл `InRelease` або `repomd.xml.asc` при вимозі перевірки. | Перевірити налаштування `gpgcheck`/`repo_gpgcheck` або доступність файлів на дзеркалі. |
| `BAD GPG SIGNATURE` | DNF / RPM | Цифровий підпис пакета підроблений або файл пошкоджено при мережевій передачі. | Перезавантажити файл `.rpm`; перевірити цілісність диска та відсутність підміни в мережі. |
