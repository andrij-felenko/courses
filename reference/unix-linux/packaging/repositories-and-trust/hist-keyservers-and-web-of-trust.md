# 📜 Еволюція моделей довіри: від Web of Trust та apt-key до ізольованих keyring-файлів

Історично криптографічний захист програмного забезпечення у світі UNIX формувався під впливом двох принципово різних філософій: класичної децентралізованої мережі довіри PGP (Web of Trust) та централізованого ланцюжка довіри дистрибутиву (Distribution Chain of Trust). Еволюція від першої до другої зайняла понад два десятиліття й була супроводжена низкою критичних атак на мережеву інфраструктуру ключових серверів.

## 1. Парадигма Web of Trust та пік розвитку мережі SKS

На початку 1990-х років Філіп Ціммерманн (Philip Zimmermann), створюючи PGP (Pretty Good Privacy, латин. *pristinus* — чистий, англ. *privacy* — приватність), заклав концепцію Web of Trust (переплетена мережа довіри). На відміну від ієрархічної інфраструктури публічних ключів PKI (Public Key Infrastructure), яка використовує центральні органи сертифікації (CA), у Web of Trust не існувало жодного головного авторитету. 

Користувачі особисто зустрічалися на так званих «ключових вечірках» (Key Signing Parties), перевіряли особисті документи один одного (паспорти, посвідчення), після чого підписували відкрий ключ колеги своїм власним закритим ключем GPG. Ступінь довіри до ключа обчислювався математично на основі графа підписів: якщо ключ був підписаний кількома особами, яким ви вже довіряли, системний інструмент `gpg` автоматично підвищував рівень довіри до власника цього ключа.

Для централізованого обміну та пошуку публічних ключів у середині 1990-х років Марк Горовіц (Marc Horowitz) розробив перший сервер ключів у MIT. Згодом це переросло у глобальну мережу серверів SKS (Synchronizing Key Server), які зв'язувалися між собою за допомогою мережевого протоколу HKP (HTTP Keyserver Protocol, зазвичай на порту 11371). Головною грою цієї мережі була повна децентралізація: будь-який користувач міг відправити свій відкритий ключ на один із серверів (наприклад, `keys.gnupg.net`), і за допомогою пліованого алгоритму пліток (gossip protocol) цей ключ протягом кількох годин синхронізувався з усіма дзеркалами SKS у світі.

Однак ця архітектурна модель, створена для особистого листування людей, виявилася принципово непридатною для масової автоматизованої дистрибуції операційних систем Linux.

## 2. Скомпрометована мережа: атака Poisoned Keys

Головний архітектурний дефект мережі серверів SKS полягав у відсутності автентифікації та контролю доступу при додаванні нових підписів до існуючого ключа. За специфікацією OpenPGP (RFC 4880), будь-хто мав право додати власний підпис (або сертифікат відкликання) до будь-якого публічного ключа, що вже зберігався на сервері. Сервери SKS зобов'язані були приймати ці доповнення й розповсюджувати їх по всьому світу.

У червні 2019 року відомі дослідники безпеки та розробники OpenPGP — Роберт Гансен (Robert J. Hansen) та Даніель Кан Гіллмор (Daniel Kahn Gillmor) — зазнали спланованої атаки на їхні публічні GPG-ключі. Зловмисники згенерували понад 55 000 фіктивних PGP-підписів для їхніх публічних ключів і завантажили ці модифіковані блоки ключів у публічну мережу SKS.

Коли стандартні утиліти `gpg` намагалися імпортувати або оновити такий «отруєний» ключ (Poisoned Key) через команду `gpg --recv-keys`, виникав катастрофічний збій:

- Розмір публічного ключа зростав від звичайних 4–8 кілобайтів до десятків мегабайтів.
- При спробі обчислити граф підписів утиліта `gpg` впадала в нескінченний цикл рекурсивного парсингу або завершувалася критично через вичерпання виділеної пам'яті (Denial of Service).
- Оскільки публічний ключ неможливо було видалити або очистити в мережі SKS, розробники втрачали можливість використовувати власні криптографічні ідентичності.

Ця атака фактично зруйнувала публічну мережу серверів SKS. Спільнота розробників Linux дистрибутивів остаточно заборонила використання автоматичного завантаження ключів з публічних keyservers під час збірки або оновлення пакетів. Замість SKS виникли нові, строго моперовані сервіси (такі як `keys.openpgp.org` та протокол WKD — Web Key Directory), які перевіряють володіння доміном або поштовою скринькою і видаляють сторонні підписи.

## 3. Епоха apt-key: глобальне кільце довіри в Debian та Ubuntu

На зорі створення підсистеми захищеного встановлення пакетів `secure-apt` у Debian 3.1 (Sarge, 2005 рік) розробники шукали максимально простий спосіб інтеграції перевірки підписів у повсякденну роботу системного адміністратора.

Для управління довіреними ключами було створено утиліту командного рядка `apt-key`. Вона працювала як обгортка довкола системного бінарного файлу списку ключів `/etc/apt/trusted.gpg` (а пізніше й додаткового каталогу `/etc/apt/trusted.gpg.d/`).

Протягом майже п'ятнадцяти років стандартна інструкція з підключення будь-якого стороннього репозиторію (наприклад, для встановлення вебсервера, бази даних чи середовища виконання мов програмування) вимагала виконання команди видачі довіри:

```bash
curl -fsSL https://vendor.example.com/gpg.key | sudo apt-key add -
```

Ця команда зчитувала відкритий ключ розробника з мережі і додавала його безпосередньо у глобальне системне кільце довіри.

### Архітектурний дефект глобального кільця ключів

Глобальне сховище ключів `/etc/apt/trusted.gpg` не мало жодної прив'язки ключа до конкретного мережевого URL, назви репозиторію чи сукупності доступних пакетів. Якщо ключ зберігався у `trusted.gpg`, менеджер APT вважав його цифровий підпис валідним для **будь-якого** репозиторію, прописаного у файлі конфігурації `/etc/apt/sources.list`.

Це створювало критичний вектор компрометації операційної системи (Cross-Repository Package Spoofing):

1. Адміністратор додавав ключ стороннього розробника для встановлення однієї конкретної прикладної програми.
2. Якщо цей сторонній розробник виявлявся недобросовісним (або його інфраструктуру збірки зламували зловмисники), він міг зібрати у своєму репозиторії свій пакет з назвою `libc6`, `systemd` або `linux-image-generic` і підвищити його номер версії (наприклад, `2.35-0ubuntu3.999`).
3. При наступному виконанні `apt upgrade` локальний менеджер APT бачив у сторонньому репозиторії «новішу» версію критичної системної бібліотеки `glibc`.
4. Оскільки ключ стороннього розробника вже перебував у глобальному сховищі `/etc/apt/trusted.gpg`, APT вважав підпис абсолютно валідним і мовчки замінював системну `glibc` на модифіковану версію від стороннього джерела, що призводило до миттєвого захоплення прав `root` на сервері.

## 4. Перехід до ізольованих keyring-файлів у сучасному Linux

У зв'язку з високими ризиками міжрепозиторійного підміни пакетів утиліту `apt-key` було оголошено застарілою (deprecated) у Debian 11 та Ubuntu 22.04, а в наступних релізах дистрибутивів її повністю вилучено із дистрибутиву.

Сучасний стандарт безпеки Linux вимагає суворої ізоляції ключів підпису (Key Scope Isolation):

1. **Окреме зберігання ключів**: Кожен відкритий ключ стороннього репозиторію зберігається у вигляді окремого бінарного або текстового файлу у каталозі `/etc/apt/keyrings/` (для локальних налаштувань) або `/usr/share/keyrings/` (для офіційних пакетів дистрибутиву).
2. **Явна прив'язка `signed-by`**: Конфігураційний файл репозиторію у форматі deb822 (`.sources`) або класичному `sources.list` містить обов'язкову директиву `Signed-By: /etc/apt/keyrings/vendor.gpg`. Ця директива вказує менеджеру APT точний шлях до ключа, яким дозволено підписувати індекси **лише цього конкретного джерела**.
3. **Відмова від конвертації dearmor**: Сучасні версії менеджерів пакунків (APT 2.4+) навчилися розпізнавати як бінарні кільця ключів GPG, так і відкриті текстові блоки ASCII-armored (`.asc`), що спростило скрипти автоматизації та розгортання без залучення важкої утиліти `gpg --dearmor`.

Аналогічна еволюція відбулася й у світлі RPM-дистрибутивів (Fedora, RHEL, openSUSE). Хоча RPM перевіряє підпис кожного пакета окремо через системний масив ключів у RPM DB (`rpm -q gpg-pubkey`), сучасний менеджер DNF підтримує параметр `gpgkey=` безпосередньо у файлі репозиторію `.repo`, а також дозволяє включати жорстку перевірку підпису індексів `repo_gpgcheck=1`.

Завдяки впровадженню ізольованих keyring-файлів компрометація або викрадення закритого ключа стороннього мейнтейнера більше не дозволяє йому підробляти системні пакунки дистрибутиву, ізолюючи можливі збитки межами його власного репозиторію.
