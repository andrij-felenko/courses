# 📋 Інтерфейси та конфігурація Multilib і Multiarch

Ця вставка містить довідник системних інтерфейсів, специфікацій триплетів GNU, полів метаданих пакетних менеджерів (Debian `dpkg` та RPM), налаштувань конфігураційного шару динамічного лінкера `ld.so` та змінних оточення компілятора та завантажувача.

## 1. Специфікація та структура GNU-триплетів (GNU Triplets)

GNU-триплет визначає унікальний ідентифікатор цільової архітектури платформенного тулчейну у форматі `<cpu>-<vendor>-<os>` або `<cpu>-<vendor>-<kernel>-<os>`. У дистрибутивах із підтримкою стандарту Multiarch ці триплети слугують назвами підкаталогів для ізоляції розділюваних бібліотек у `/lib/` та `/usr/lib/`, а також заголовних файлів у `/usr/include/`.

Формування триплета визначається трьома основними компонентами:
1. **Ідентифікатор процесора (`<cpu>`):** Вказує на архітектуру набору інструкцій (ISA). Наприклад, `x86_64` вказує на 64-бітний режим AMD64/Intel64, `i386` чи `i686` — на 32-бітний x86, `aarch64` — на 64-бітну архітектуру ARMv8-A, `arm` — на 32-бітний ARM, `riscv64` — на 64-бітний RISC-V.
2. **Виробник або постачальник (`<vendor>`):** У більшості систем Linux це поле набуває значення `pc`, `unknown` або за замовчуванням опускається (скорочений запис), залишаючи двокомпонентний чи трикомпонентний варіант.
3. **Операційна система та ABI (`<kernel>-<os>` або `<os>-<abi>`):** Вказує ядро операційної системи та бінарний інтерфейс додатків. Поєднання `linux-gnu` означає ядро Linux із системною бібліотекою GNU C Library (glibc). Варіант `linux-gnueabihf` додатково вказує на розширене ABI EABI з апаратною підтримкою обчислень із плаваючою комою (Hard-Float), тоді як `linux-gnueabi` означає програмну емуляцію (Soft-Float).

### Канонічний перелік основних GNU-триплетів:

- **`x86_64-linux-gnu` (Debian/Ubuntu `amd64`, RPM `x86_64`):** Нативна 64-бітна архітектура x86_64. Використовує модель пам'яті LP64 (`sizeof(long) = 8`, `sizeof(void*) = 8`). Шляхи розташування бібліотек: `/usr/lib/x86_64-linux-gnu` та `/lib/x86_64-linux-gnu`.
- **`i386-linux-gnu` (Debian/Ubuntu `i386`, RPM `i686`):** 32-бітна архітектура x86. Використовує модель пам'яті ILP32 (`sizeof(long) = 4`, `sizeof(void*) = 4`). Шляхи розташування бібліотек: `/usr/lib/i386-linux-gnu` та `/lib/i386-linux-gnu`.
- **`aarch64-linux-gnu` (Debian/Ubuntu `arm64`, RPM `aarch64`):** 64-бітна архітектура ARMv8-A. Модель пам'яті LP64. Шляхи розташування бібліотек: `/usr/lib/aarch64-linux-gnu`.
- **`arm-linux-gnueabihf` (Debian/Ubuntu `armhf`, RPM `armv7hl`):** 32-бітна архітектура ARMv7 із підтримкою регістрів VFP/NEON для апаратного плаваючого котика. Модель пам'яті ILP32. Шляхи: `/usr/lib/arm-linux-gnueabihf`.
- **`arm-linux-gnueabi` (Debian/Ubuntu `armel`, RPM `armv5tel`):** 32-бітна застаріла архітектура ARMv5/v6 із програмною емуляцією плаваючої крапки. Шляхи: `/usr/lib/arm-linux-gnueabi`.
- **`riscv64-linux-gnu` (Debian/Ubuntu `riscv64`, RPM `riscv64`):** 64-бітна відкрита архітектура RISC-V. Модель пам'яті LP64. Шляхи: `/usr/lib/riscv64-linux-gnu`.
- **`powerpc64le-linux-gnu` (Debian/Ubuntu `ppc64el`, RPM `ppc64le`):** 64-бітна архітектура PowerPC у режимі Little-Endian. Шляхи: `/usr/lib/powerpc64le-linux-gnu`.
- **`s390x-linux-gnu` (Debian/Ubuntu `s390x`, RPM `s390x`):** 64-бітна мейнфрейм-архітектура IBM z/Architecture. Шляхи: `/usr/lib/s390x-linux-gnu`.
- **`x86_64-linux-gnux32` (Debian/Ubuntu `x32`):** Спеціальне ABI x32, у якому процесор виконує 64-бітні інструкції x86_64, але використовує 32-бітні вказівники адреси для зменшення витрат пам'яті кешу. Шляхи: `/usr/lib/x86_64-linux-gnux32`.

## 2. Поля метаданих Debian Control (`Multi-Arch`) та алгоритми розв'язання залежностей

У дистрибутивах Debian, Ubuntu та їхніх похідних керування співіснуванням пакетів різних архітектур реалізовано у пакетному менеджері `dpkg` та депозитарії `apt` через спеціалізований атрибут `Multi-Arch:` у файлі метаданих `debian/control`.

Цей атрибут визначає семантику розв'язання залежностей у графі пакетів `apt` під час виконання команд `apt install` або `apt dist-upgrade`.

### 1. Семантика `Multi-Arch: same`
Застосовується для розділюваних бібліотек (`.so` файлів), системних плагінів та розробницьких пакетів із заголовними файлами, вміст яких жорстко прив'язаний до бінарної архітектури.

Правила функціонування та обмеження `Multi-Arch: same`:
- Дозволяє пакетному менеджеру `dpkg` одночасно встановлювати в систему декілька екземплярів одного пакета для різних архітектур (наприклад `libz1:amd64` та `libz1:i386`).
- Кожен пакет розміщує свої бінарні бібліотеки у відповідний триплетний каталог (`/usr/lib/x86_64-linux-gnu/libz.so.1` та `/usr/lib/i386-linux-gnu/libz.so.1`).
- Усі архітектурно-незалежні файли (наприклад текстові ліцензії або документація у `/usr/share/doc/libz1/`), якими володіють обидва пакети, повинні бути **абсолютно бінарно ідентичними**. У разі відмінності бодай одного байта `dpkg` перериває встановлення з помилкою конфлікту файлів.
- Версії пакетів для різних архітектур мають повністю збігатися аж до номера збірки дистрибутиву (Upstream та Debian revision).

### 2. Семантика `Multi-Arch: foreign`
Застосовується для архітектурно-незалежних утиліт, інтерпретаторів, компіляторів ресурсів та інструментів збірки (наприклад `make`, `python3`, `bison`, `flex`, `pkg-config`, `doxygen`).

Правила функціонування `Multi-Arch: foreign`:
- Пакет нативної архітектури системи (наприклад `python3:amd64`) може задовольняти залежності пакетів будь-якої інородної архітектури (наприклад `libfoo:armhf`, який вимагає `python3`).
- Пакетний менеджер `apt` розуміє, що інтерпретатор чи інструмент надає інтерфейс, який не залежить від бінарного ABI цільової бібліотеки. Це запобігає безглуздому завантаженню інородного бінарника `python3:armhf`, який не зміг би запуститися на x86_64 ядрі без шарніра `qemu-user`.

### 3. Семантика `Multi-Arch: allowed`
Застосовується для гнучких пакетів, які залежно від контексту запиту можуть виступати або у ролі `Multi-Arch: same`, або у ролі `Multi-Arch: foreign`.

Правила функціонування `Multi-Arch: allowed`:
- За замовчуванням пакет трактується так само, як звичайний пакет без прапорця Multi-Arch (`Multi-Arch: no`).
- Якщо залежний пакет оголошує залежність із додаванням кваліфікатора `:any` (наприклад `Depends: foo:any`), пакетний менеджер дозволяє використати нативний екземпляр `foo` для задоволення залежності інородного пакета.

### 4. Семантика `Multi-Arch: no` (значення за замовчуванням)
Якщо поле `Multi-Arch:` відсутнє у метаданих пакета, йому присвоюється значення `no`. Такий пакет може задовольняти залежності тільки тих пакетів, які скомпільовані під таку ж бінарну архітектуру.

## 3. Специфікація макросів збирання та конфігурації RPM Multilib

У дистрибутивах на базі RPM (Red Hat Enterprise Linux, Fedora, CentOS, Rocky Linux) розділення бібліотек здійснюється на етапі збирання через макроси інструменту `rpmbuild` та налаштування конфігуратора `dnf`.

### Основні макроси розгортання шляхів у RPM Spec-файлах:

- **`%{_lib}`:** Автоматично розгортається у рядок `lib` на 32-бітних архітектурах (i686) та у рядок `lib64` на 64-бітних архітектурах (x86_64).
- **`%{_libdir}`:** Повний шлях до системного каталогу бібліотек. Розгортається у `/usr/lib` на 32-бітних системах та у `/usr/lib64` на 64-бітних системах.
- **`%{_exec_prefix}`:** Базовий префікс виконуваних каталогів системи (за замовчуванням `/usr`).
- **`%{_bindir}`:** Шлях до виконуваних утилит (`/usr/bin`). У системі Multilib є спільним каталогом, що викликає конфлікти бінарників.
- **`%{_includedir}`:** Шлях до каталогів C/C++ заголовків (`/usr/include`). В RPM Multilib потребує використання макросних обгорток `#if __WORDSIZE == 64`.
- **`%{_arch}`:** Повертає назву цільової архітектури процесора (`x86_64`, `i686`, `aarch64`).

### Політика конфігуратора DNF (`multilib_policy`):

У конфігураційному файлі `/etc/dnf/dnf.conf` опція `multilib_policy` керує поведінкою завантаження 32-бітних пакетів у 64-бітній системі:
- **`multilib_policy=best` (значення за замовчуванням):** Під час встановлення пакета `dnf` вибирає тільки найкращу нативну архітектуру (x86_64), не завантажуючи 32-бітні дублікати без явного вказівки архітектурного суфікса.
- **`multilib_policy=all`:** Під час встановлення будь-якого пакета `dnf` автоматично намагається завантажити та встановити як 64-бітну (x86_64), так і 32-бітну (i686) версії пакета та їхні залежності.

## 4. Глибока конфігурація динамічного завантажувача ld.so

Динамічний завантажувач Linux (`/lib64/ld-linux-x86-64.so.2` або `/lib/ld-linux.so.2`) зчитує системні шляхи з двівійкового кешу `/etc/ld.so.cache`, який генерується системною утилітою `ldconfig` під час обробки конфігураційних файлів.

### Порядок пріоритету пошуку shared objects у ld.so:

Під час виконання виклику `dlopen()` або старту бінарного файлу завантажувач виконує пошук потрібного `.so` файлу в суворо визначеному порядку:
1. **Секція `DT_RPATH` у заголовку ELF:** Шляхи, закодовані під час компіляції (якщо відсутня секція `DT_RUNPATH`).
2. **Змінна оточення `LD_LIBRARY_PATH`:** Перелічені через двокрапку користувацькі шляхи (ігноруються для бінарників із прапорцями SUID/SGID з міркувань безпеки).
3. **Секція `DT_RUNPATH` у заголовку ELF:** Сучасний аналог RPATH, який оцінюється після перевірки `LD_LIBRARY_PATH`.
4. **Бінарний кеш `/etc/ld.so.cache`:** Індексований бінарний файл, який містить пари "назва бібліотеки -> абсолютний шлях на диску".
5. **Системні каталоги за замовчуванням:** Для Multiarch це `/lib/<triplet>` та `/usr/lib/<triplet>`, для Multilib — `/lib64` та `/usr/lib64` (або `/lib` та `/usr/lib`).

### Структура конфігураційних файлів `ld.so.conf`:

- **`/etc/ld.so.conf`:** Головний текстовий конфігураційний файл завантажувача. Містить директиву включення дочірніх конфігурацій:
  ```text
  include /etc/ld.so.conf.d/*.conf
  ```
- **`/etc/ld.so.conf.d/x86_64-linux-gnu.conf` (Debian Multiarch 64-bit):**
  ```text
  # Multiarch path for x86_64
  /usr/local/lib/x86_64-linux-gnu
  /lib/x86_64-linux-gnu
  /usr/lib/x86_64-linux-gnu
  ```
- **`/etc/ld.so.conf.d/i386-linux-gnu.conf` (Debian Multiarch 32-bit):**
  ```text
  # Multiarch path for i386
  /usr/local/lib/i386-linux-gnu
  /lib/i386-linux-gnu
  /usr/lib/i386-linux-gnu
  ```
- **`/etc/ld.so.conf.d/zz_multilib.conf` (RPM Multilib 64-bit):**
  ```text
  /usr/lib64
  /lib64
  ```

### Команди та прапорці керування утиліти `ldconfig`:

- **`ldconfig -p`:** Вивести повний розпарсений вміст двійкового кешу `/etc/ld.so.cache`. Дозволяє перевірити, з якого саме каталогу завантажувач братиме конкретну бібліотеку.
- **`ldconfig -v`:** Деталізоване сканування системних каталогів із виводом знайдених версій бібліотек та оновленням символьних лінків `lib*.so.X -> lib*.so.X.Y.Z`.
- **`ldconfig -n <directory>`:** Обробити лінки бібліотек тільки у вказаному каталозі без генерації глобального кешу `/etc/ld.so.cache`.

## 5. Довідник змінних оточення виконання та тулчейну компіляції

Змінні оточення дозволяють розробникам та адміністраторам гнучко керувати шляхами завантаження бібліотек та пошуку заголовків під час виконання та компіляції.

### 1. Змінні оточення середовища виконання (Runtime):
- **`LD_LIBRARY_PATH`:** Список каталогів, розділених двокрапкою, які завантажувач `ld.so` сканує першочергово. Використовується для тестування нових версій бібліотек без їх встановлення в систему.
- **`LD_PRELOAD`:** Список конкретних shared objects, які завантажуються в адресний простір процесу перед усіма іншими бібліотеками. Використовується для перехоплення системних функцій C (наприклад підміна `malloc` на `jemalloc`).
- **`LD_DEBUG`:** Керує налагоджувальним виводом динамічного завантажувача. Приймає значення `libs` (вивід пошуку файлів), `symbols` (вивід пошуку функцій у таблицях символів), `reloc` (вивід релокацій) або `all`.

### 2. Змінні інструменту `pkg-config`:
- **`PKG_CONFIG_PATH`:** Додаткові шляхи до `.pc` файлів опису бібліотек. У Multiarch використовує розділення каталогів:
  - `/usr/lib/x86_64-linux-gnu/pkgconfig` (для 64-бітних бібліотек)
  - `/usr/lib/i386-linux-gnu/pkgconfig` (для 32-бітних бібліотек)
- **`PKG_CONFIG_LIBDIR`:** Повністю заміщує системні шляхи пошуку `pkg-config`. Застосовується під час крос-компіляції, щоб змусити `pkg-config` зчитувати конфігурації тільки для цільової архітектури.

### 3. Змінні тулчейну компіляції (GCC / Clang):
- **`LIBRARY_PATH`:** Список каталогів, у яких компілятор шукає бібліотеки під час етапу лінкування (аналог передачі прапорців `-L`).
- **`C_INCLUDE_PATH` / `CPLUS_INCLUDE_PATH`:** Список каталогів, у яких компілятор шукає заголовні файли C та C++ відповідно на етапі препроцесингу (аналог передачі прапорців `-I`).
