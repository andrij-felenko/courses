# 📋 Специфікація форматів DEB та RPM: структури, заголовки та файли конфігурації

Цей довідник визначає точну бінарну та текстову структуру контейнерів `.deb` і `.rpm`, схеми метаданих, життєвий цикл керуючих скриптів, а також формати конфігураційних файлів збірки. Опис розрахований на системних інженерів, розробників пакетних менеджерів та авторів інструментів автоматизації збірки, яким необхідне вичерпне розуміння низькорівневих форматів пакетування у системному просторі Linux.

## 1. Специфікація контейнера DEB (версія 2.0)

Файл `.deb` є стандартним бінарним архівом `ar` (Unix Archive Format), який містить три обов'язкові файли у чітко визначеній послідовності. Першим завжди йде текстовий маркер версії `debian-binary`, яким керується інструмент `dpkg` для визначення сумісності формату. Другим іде стиснений архів метаданих `control.tar.*`, третім — стиснений архів корисного навантаження файлової системи `data.tar.*`. Спроба змінити порядок файлів всередині контейнера робить пакунок невалідним для утиліти `dpkg`.

```
+-------------------------------------------------------------------+
| ar Header: "!<arch>\n" (8 bytes)                                  |
+-------------------------------------------------------------------+
| File Header: "debian-binary"    | Data: "2.0\n"                   |
+-------------------------------------------------------------------+
| File Header: "control.tar.xz"   | Data: Compressed control tarball|
+-------------------------------------------------------------------+
| File Header: "data.tar.xz"      | Data: Compressed payload tarball|
+-------------------------------------------------------------------+
```

### 1.1. Заголовок архіву `ar`

Кожен файл всередині `ar`-контейнера починається з 60-байтового заголовка ASCII, який задає атрибути файлу без використання бінарних цілочисельних форматів. Це гарантує сумісність між архітектурами з різним порядком байтів (Big-Endian та Little-Endian).

- `0..15` (16 байтів): Ім'я файлу, заповнене пробілами справа (наприклад, `debian-binary   ` або `control.tar.xz/  `).
- `16..27` (12 байтів): Час модифікації у форматі десятичного UNIX timestamp.
- `28..33` (6 байтів): Ідентифікатор користувача-власника (UID) у текстовому вигляді.
- `34..39` (6 байтів): Ідентифікатор групи-власника (GID) у текстовому вигляді.
- `40..47` (8 байтів): Права доступу до файлу у вісімковій системі числення ASCII.
- `48..57` (10 байтів): Розмір даних файлу в байтах у текстовому вигляді.
- `58..59` (2 байти): Завершальний маркер заголовка, який завжди дорівнює символам `` `\n `` (`0x60 0x0A`).

### 1.2. Файл `debian-binary`

Файл `debian-binary` є звичайним текстовим файлом без байтів BOM, який завжди містить лише один рядок з номером версії формату та символом нового рядка: `2.0\n`. Спроба подати версію `1.0` (старий формат Debian початку 1990-х) або незнайому версію змушує `dpkg` миттєво відхилити пакунок до розпакування інших файлів.

### 1.3. Файли `symbols` та `shlibs` в `control.tar.*`

Для автоматичного управління залежностями від shared-бібліотек пакетні менеджери Debian використовують два додаткових файли у `control.tar.*`:

- `symbols`: Містить точну картування кожного експортованого ELF-символу бібліотеки на конкретну версію пакунка.
  Формат запису:
  `libfoo.so.1 libfoo1 #MINVER#`
  ` foo_init@Base 1.0.0`
  ` foo_process@Base 1.2.0`
  Це дозволяє `dpkg-shlibdeps` згенерувати точну залежність `libfoo1 (>= 1.2.0)`, якщо програма використовує функцію `foo_process`, але не вимагати версії 1.2.0, якщо використовується лише `foo_init`.

- `shlibs`: Історичний формат, який визначає залежність на рівні усієї SONAME-бібліотеки.
  Формат запису:
  `libfoo 1 libfoo1 (>= 1.0.0)`

### 1.4. Файл `conffiles` та механізм захисту налаштувань

Файл `conffiles` у `control.tar.*` містить список абсолютних шляхів до файлів (наприклад, `/etc/sysmon.conf`), які є конфігураційними. Під час оновлення пакунка `dpkg` порівнює MD5-хеш поточного файлу на диску з трьома значеннями:
1. Хешем файлу з попереднього пакунка.
2. Хешем файлу з нового пакунка.
3. Поточним хешем файлу на диску.

Якщо адміністратор змінював файл локально, а новий пакунок пропонує оновлену конфігурацію від розробника, `dpkg` призупиняє встановлення і пропонує вибір: залишити локальну версію, встановити версію розробника або показати різницю (`diff`). Якщо локальна версія зберігається, оновлений файл від розробника записується поруч із розширенням `.dpkg-dist`.

### 1.5. Структура файлу `control` (Формат RFC 822 / Debian Control)

Файл `control` містить ключові метадані пакунка у формі заголовків RFC 822. Кожен рядок складається з назви поля, двокрапки та значення. Якщо значення є багаторядковим (наприклад, розширений опис програми `Description`), наступні рядки обов'язково починаються з одного пробілу. Порожні рядки всередині тексту опису замінюються на комбінацію пробілу та крапки ` .`.

- `Package`: Унікальне ім'я бінарного пакунка в системі. Дозволені лише малі латинські літери, цифри та дефіс.
- `Version`: Повний рядок версії у форматі `[Epoch:]Upstream_Version[-Debian_Revision]`. Епоха `Epoch` використовується для зміни логіки порівняння версій, якщо нумерація розробника змінилася (наприклад, перехід з 2.0 на 2025.1).
- `Architecture`: Назва цільової архітектури (`amd64`, `arm64`, `i386`, `riscv64`). Значення `all` вказує, що пакунок містить архітектурно-незалежні дані (скрипти Python, документацію, медиа-файли).
- `Maintainer`: Контактні дані мейнтейнера або команди розробки у форматі `Ім'я <email@domain>`.
- `Description`: Однорядкове коротке резюме програми та послідуючий розширений опис функціональності.
- `Depends`: Перелік пакунків з операторами версій (`>=`, `<=`, `=`, `>>`, `<<`), без яких даний пакунок не може бути розпакований і налаштований.
- `Pre-Depends`: Особливий тип залежностей. APT гарантує, що вказані пакунки будуть не просто завантажені, а повністю встановлені й конфігуровані **до того**, як почнеться розпакування даного `.deb` файлу.
- `Recommends`: Рекомендовані пакунки, які зазвичай встановлюються разом із програмою, але відсутність яких не блокує її базову працездатність.
- `Suggests`: Додаткові пакунки, які розширюють можливості програми для специфічних сценаріїв використання.
- `Conflicts`: Список пакунків, які не можуть співіснувати в системі одночасно з даним пакунком.
- `Breaks`: Оголошує, що встановлення цього пакунка зламає працездатність вказаних версій інших пакунків.
- `Provides`: Оголошує віртуальне ім'я (наприклад, `mail-transport-agent`), яке може задовольняти залежності інших програм.
- `Replaces`: Дозволяє даному пакунку перезаписувати файли, що належать іншим зазначеним пакункам.

### 1.6. Скрипти обслуговування (Maintainer Scripts) та аргументи виклику

Під час маніпуляцій з пакунком менеджер `dpkg` викликає виконувані скрипти з архіву `control.tar.*`, передаючи їм конкретні позиційні аргументи залежно від фази транзакції.

- `preinst`: Виконується перед розпакуванням нових файлів з `data.tar.*`.
  - `preinst install`: Первинне встановлення пакунка в систему.
  - `preinst upgrade <old-version>`: Оновлення існуючого пакунка з вказаної старої версії.
  - `preinst abort-upgrade <new-version>`: Викликається під час відкату, якщо спроба оновлення зазнала невдачі.

- `postinst`: Виконується після того, як файли розпаковані на файлову систему.
  - `postinst configure <most-recently-configured-version>`: Головний виклик для стабілізації конфігурації, запуску системних служб `systemd` та створення динамічних користувачів.
  - `postinst abort-upgrade <new-version>`: Викликається під час скасування оновлення.

- `prerm`: Виконується перед видаленням файлів пакунка.
  - `prerm remove`: Стандартна деінсталяція пакунка.
  - `prerm upgrade <new-version>`: Підготовка до заміни файлів на нову версію.
  - `prerm failed-upgrade <old-version>`: Скасування процедури оновлення.

- `postrm`: Виконується після повного вилучення файлів з диска.
  - `postrm remove`: Очищення тимчасових системних даних.
  - `postrm purge`: Повне очищення конфігураційних файлів (викликається при `dpkg --purge` або `apt purge`).
  - `postrm upgrade <new-version>`: Завершальне очищення старої версії після інсталяції нової.

```
 [Встановлення пакунка A]
       │
       ▼
 1. preinst install
       │
       ▼  (Розпакування data.tar.*)
       │
 2. postinst configure <old-version>
```

```
 [Оновлення з версії A до версії B]
       │
       ▼
 1. new-preinst upgrade <old-version>
       │
       ▼  (Розпакування нових файлів B)
       │
 2. old-prerm upgrade <new-version>
       │
       ▼
 3. new-postinst configure <old-version>
       │
       ▼
 4. old-postrm upgrade <new-version>
```

### 1.7. Механізм тригерів DPKG (dpkg-trigger)

Тригери дозволяють відкласти виконання важких системних дій (таких як оновлення кешу динамічних бібліотек `ldconfig`, оновлення баз даних мануалів `mandb` або перекомпіляція іконок стільниці) до завершення всієї транзакції.

- `interest <trigger-name>`: Оголошує, що даний пакунок бажає обробити подію `<trigger-name>`, коли будь-який інший пакунок змінить відповідні шляхи.
- `interest-noawait <trigger-name>`: Аналогічно, але не змушує викликувача чекати завершення конфігурації поточного пакунка.
- `activate <trigger-name>`: Примусово активує подію тригера під час інсталяції.

## 2. Специфікація бінарного контейнера RPM (версія 4.x)

Файл `.rpm` є суворо бінарним файлом із чітким розділенням на чотири блоки: RPM Lead, Signature, Header та Payload.

```
+-------------------------------------------------------------------+
| RPM Lead (96 bytes legacy header)                                 |
+-------------------------------------------------------------------+
| Signature Structure (Tag-based GPG/SHA256 digests)                |
+-------------------------------------------------------------------+
| Header Structure (Tag-based Metadata Index & Store)               |
+-------------------------------------------------------------------+
| Payload Stream (Compressed cpio archive: gz/xz/zstd)               |
+-------------------------------------------------------------------+
```

### 2.1. Специфікація RPM Lead

Блок Lead займає перші 96 байтів файлу. У сучасних версіях RPM більшість його полів ігноруються на користь тегованого Header, однак значення magic-байтів обов'язково перевіряються для швидкої ідентифікації типу файлу утилітами ОС.

:::tabs
```c
#include <stdint.h>

struct rpmlead {
    unsigned char magic[4];      /* 0xED, 0xAB, 0xEE, 0xDB */
    unsigned char major;         /* Версія формату (наразі 3 або 4) */
    unsigned char minor;         /* Підверсія формату */
    uint16_t type;               /* 0 = Binary, 1 = Source */
    uint16_t archtag;            /* Ідентифікатор архітектури (1 = x86) */
    char name[66];               /* Назва пакунка (доповнена нульовими байтами) */
    uint16_t osnum;              /* Ідентифікатор ОС (1 = Linux) */
    uint16_t signature_type;     /* Тип заголовку підпису (зазвичай 5 = Header-style) */
    char reserved[16];           /* Зарезервоване поле (нульові байти) */
};
```
```cpp
#include <cstdint>
#include <array>

struct RpmLead {
    std::array<uint8_t, 4> magic; /* 0xED, 0xAB, 0xEE, 0xDB */
    uint8_t major;                /* Версія формату (3 або 4) */
    uint8_t minor;                /* Підверсія формату */
    uint16_t type;                /* 0 = Binary, 1 = Source */
    uint16_t archtag;             /* Ідентифікатор архітектури */
    std::array<char, 66> name;    /* Назва пакунка */
    uint16_t osnum;               /* Ідентифікатор ОС */
    uint16_t signature_type;      /* Тип підпису */
    std::array<char, 16> reserved;/* Зарезервовано */
};
```
:::

### 2.2. Специфікація Header (Тегована структура даних)

Блок Header використовує систему індексних записів для опису довільної кількості полів метаданих. Він починається з 16-байтового заголовка структури, після якого йде масив записів `rpm_index_entry`, а далі — суцільне сховище даних (Data Store).

:::tabs
```c
struct rpm_index_entry {
    int32_t tag;     /* Числовий ідентифікатор тегу (RPMTAG) */
    int32_t type;    /* Тип даних (RPM_STRING_TYPE, RPM_INT32_TYPE тощо) */
    int32_t offset;  /* Зсув від початку Data Store у байтах */
    int32_t count;   /* Кількість елементів даного типу */
};
```
```cpp
struct RpmIndexEntry {
    std::int32_t tag;    /* Числовий ідентифікатор тегу (RPMTAG) */
    std::int32_t type;   /* Тип даних (RPM_STRING_TYPE, RPM_INT32_TYPE тощо) */
    std::int32_t offset; /* Зсув від початку Data Store у байтах */
    std::int32_t count;  /* Кількість елементів даного типу */
};
```
:::

#### Типи даних тегів RPM (Header Data Types):

- `0` (`RPM_NULL_TYPE`): Порожній тип.
- `1` (`RPM_CHAR_TYPE`): Одиночний символ ASCII.
- `2` (`RPM_INT8_TYPE`): 8-бітове ціле число без знаку.
- `3` (`RPM_INT16_TYPE`): 16-бітове ціле число (big-endian).
- `4` (`RPM_INT32_TYPE`): 32-бітове ціле число (big-endian).
- `5` (`RPM_INT64_TYPE`): 64-бітове ціле число (big-endian).
- `6` (`RPM_STRING_TYPE`): Рядок ASCII, що завершується нульовим байтом `\0`.
- `7` (`RPM_BIN_TYPE`): Двійковий масив байтів.
- `8` (`RPM_STRING_ARRAY_TYPE`): Масив рядків, розділених нульовими байтами.
- `9` (`RPM_I18NSTRING_TYPE`): Інтернаціоналізований рядок з локалізацією.

#### Стандартні числові теги RPM (RPMTAG):

- `1000` (`RPMTAG_NAME`): Рядок з іменем пакунка.
- `1001` (`RPMTAG_VERSION`): Версія оригінального вихідного коду (Upstream Version).
- `1002` (`RPMTAG_RELEASE`): Номер збірки пакунка в дистрибутиві.
- `1004` (`RPMTAG_SUMMARY`): Коротка однорядкова анотація.
- `1005` (`RPMTAG_DESCRIPTION`): Повний багаторядковий текстовий опис.
- `1006` (`RPMTAG_BUILDTIME`): Час збірки пакунка у секундах з початку епохи POSIX.
- `1014` (`RPMTAG_LICENSE`): Ліцензія програмного забезпечення (наприклад, GPLv3+, Apache-2.0).
- `1022` (`RPMTAG_ARCH`): Назва цільової архітектури (`x86_64`, `aarch64`, `noarch`).
- `1049` (`RPMTAG_REQUIRENAME`): Масив рядків із назвами необхідних пакунків та системних бібліотек (`libc.so.6()(64bit)`).
- `1050` (`RPMTAG_REQUIREVERSION`): Масив рядків з операторами порівняння та версіями для `REQUIRENAME`.
- `1047` (`RPMTAG_PROVIDENAME`): Масив віртуальних можливостей та назв shared-бібліотек, які експортує пакунок.
- `1054` (`RPMTAG_CONFLICTNAME`): Масив назв пакунків, несумісних з даним.
- `1117` (`RPMTAG_BASENAMES`): Масив баз імен усіх файлів у пакунку.
- `1118` (`RPMTAG_DIRNAMES`): Масив унікальних шляхів каталогів для реконструювання повних шляхів файлів.
- `1119` (`RPMTAG_FILEFLAGS`): Бітова маска прапорців файлів (`RPMFILE_CONFIG` = 0x01, `RPMFILE_DOC` = 0x02, `RPMFILE_NOREPLACE` = 0x10).

### 2.3. Послідовність виконання скриптлетів RPM

Скриптлети RPM приймають єдиний числовий аргумент `$1`, який вказує на кількість екземплярів пакунка, що залишаться в системі після завершення поточної транзакції.

- `%pre`: Виконується перед встановленням файлів. При першій інсталяції `$1 == 1`, при оновленні `$1 == 2`.
- `%post`: Виконується після копіювання файлів на диск. При першій інсталяції `$1 == 1`, при оновленні `$1 == 2`.
- `%preun`: Виконується перед видаленням файлів. При оновленні (видалення старої версії) `$1 == 1`, при повному видаленні пакунка `$1 == 0`.
- `%postun`: Виконується після вилучення файлів з диска. При оновленні `$1 == 1`, при повному видаленні `$1 == 0`.
- `%pretrans`: Виконується один раз на самому початку всієї транзакції пакетного менеджера (до обробки будь-яких фактів встановлення). Аргумент `$1` завжди дорівнює `0`.
- `%posttrans`: Виконується один раз в самому кінці транзакції після завершення всіх операцій встановлення та видалення. Аргумент `$1` завжди дорівнює `0`.

Коли `$1 == 1` у `%postun`, це означає, що система здійснює оновлення пакунка. Старий пакунок приборкує власні файли, але **не повинен** зупиняти працюючі системні сервіси, оскільки нова версія сервісу вже розпакована і запущена новим скриптлетом `%post`. Якщо ж `$1 == 0`, відбувається остаточна деінсталяція програми, і скрипт має зупинити демон та видалити системних користувачів.

## 3. Порівняльна таблиця конфігурацій збірки

| Опис метаданих | Екосистема Debian (`debian/`) | Екосистема Red Hat RPM (`.spec`) |
| :--- | :--- | :--- |
| Залежності збірки | `debian/control` (`Build-Depends`) | `.spec` (`BuildRequires:`) |
| Залежності виконання | `debian/control` (`Depends`) | `.spec` (`Requires:`) |
| Покрокова компіляція | `debian/rules` (цілі `override_dh_auto_build`) | Секції `%build` у файлі `.spec` |
| Розподіл файлів | `debian/<package>.install` | Секція `%files` з макросами шляхів |
| Скрипти інсталяції | `debian/postinst`, `debian/prerm` | Секції `%post`, `%preun`, `%postun` |
| Історія релізів | `debian/changelog` | Секція `%changelog` |
