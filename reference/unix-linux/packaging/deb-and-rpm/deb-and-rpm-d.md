# deb і rpm: два світи пакування

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Системи управління пакунками (пакетні менеджери) є одними з найважливіших компонентів сучасних дистрибутивів Linux. Вони забезпечують встановлення, оновлення, налаштування та видалення програмного забезпечення, а також автоматичне вирішення залежностей між різними програмами та бібліотеками. У світі Linux історично склалися дві домінуючі системи пакування: **DEB** (Debian) та **RPM** (Red Hat Package Manager). Хоча сьогодні існує багато інших форматів (наприклад, Flatpak, Snap, AppImage, або спеціалізовані менеджери типу pacman в Arch Linux), DEB і RPM залишаються фундаментальними стовпами, на яких тримається більшість серверних і десктопних дистрибутивів.

У цій статті ми глибоко зануримося у внутрішню будову форматів `.deb` та `.rpm`, розглянемо їхню історію, інструментарій, алгоритми роботи та способи створення пакунків.

## 1. Історичний контекст та еволюція

Розуміння того, чому існують два основних формати пакунків і чим вони відрізняються, неможливе без погляду на їхню історію. На початку 1990-х років встановлення програмного забезпечення в Unix-подібних системах зводилося переважно до розпакування tar-архівів і ручної компіляції вихідних кодів (відомий цикл `./configure && make && make install`). Цей процес був складним, схильним до помилок і не дозволяв легко видаляти чи оновлювати програми. Крім того, відстеження того, які файли належать якій програмі, було практично неможливим завданням для системного адміністратора.

### Народження DEB

Формат `.deb` був розроблений Яном Мердоком (Ian Murdock), засновником проєкту Debian, у 1993- 1994 роках. Метою було створення надійної системи управління програмним забезпеченням, яка б дозволяла дистрибутиву Debian оновлюватися "на льоту" без необхідності перевстановлення всієї системи. Перші версії інструменту `dpkg` (Debian package manager) були написані на Perl, але згодом, для підвищення продуктивності та надійності, його переписали на C.

Формат `.deb` від самого початку проєктувався з думкою про прозорість і використання стандартних Unix-інструментів. Це рішення виявилося настільки вдалим, що базова структура `.deb` файлу практично не змінилася за останні тридцять років. Згодом навколо `dpkg` було створено потужнішу надбудову — Advanced Package Tool (APT), яка автоматизувала завантаження пакунків з мережевих репозиторіїв та вирішення складних дерев залежностей. Ця комбінація (dpkg + APT) стала стандартом де-факто не лише для Debian, але й для всіх його похідних, включаючи Ubuntu, Linux Mint, Pop!_OS та багато інших.

### Еволюція RPM

Формат RPM (спочатку Red Hat Package Manager, пізніше розшифровувався як RPM Package Manager — рекурсивний акронім) був розроблений компанією Red Hat. Його створення приписують Еріку Троану (Erik Troan) та Марку Юінгу (Marc Ewing) у 1997 році, хоча він базувався на попередніх розробках, таких як RPP (дослідження Річарда Феїта) та PMS.

На відміну від DEB, який спирався на стандартний архіватор `ar`, розробники RPM пішли шляхом створення більш монолітного бінарного формату з розширеними можливостями вбудованої криптографічної перевірки (підписи) та метаданих. RPM швидко став стандартом для комерційних дистрибутивів Linux. У 1997 році він був обраний як стандартний формат пакунків у специфікації Linux Standard Base (LSB), хоча це і не призвело до його абсолютного домінування.

Навколо утиліти `rpm` також з'явилися інструменти вищого рівня для вирішення залежностей: спочатку це був `up2date` (у Red Hat Enterprise Linux), потім `yum` (Yellowdog Updater, Modified), який згодом був замінений на більш сучасний та швидкий `dnf` (Dandified YUM). Інші дистрибутиви на базі RPM розробили власні надбудови, наприклад, `zypper` у SUSE Linux.

Сьогодні DEB і RPM представляють дві потужні екосистеми. Вибір між ними часто зводиться до вибору дистрибутиву, оскільки технічні можливості обох форматів на сьогоднішній день є більш-менш еквівалентними, хоча підходи до їх реалізації суттєво відрізняються.

## 2. Анатомія формату .deb

Філософія Unix проголошує: "роби одну річ і роби її добре", а також "зберігай дані в простому текстовому форматі, де це можливо". Формат `.deb` є чудовим втіленням цих принципів. Замість того, щоб винаходити новий складний бінарний контейнер, розробники Debian використали існуючий стандартний формат архіву `ar`.

Якщо ви візьмете будь-який файл `.deb` і дослідите його за допомогою утиліти `file`, ви побачите наступне:

```bash
$ file nano_5.4-2_amd64.deb
nano_5.4-2_amd64.deb: Debian binary package (format 2.0), uses xz compression
```

Але якщо ви використаєте інструмент `ar`, ви зможете легко розпакувати його без використання `dpkg`:

```bash
$ ar x nano_5.4-2_amd64.deb
$ ls -l
-rw-r--r-- 1 user user       4 Mar 10 12:00 debian-binary
-rw-r--r-- 1 user user    1520 Mar 10 12:00 control.tar.xz
-rw-r--r-- 1 user user  654320 Mar 10 12:00 data.tar.xz
```

Сучасний (формат 2.0) `.deb` файл — це просто `ar` архів, який завжди містить рівно три файли у строго визначеному порядку: `debian-binary`, архів керуючих даних (`control.tar.*`) та архів з даними (`data.tar.*`).

### 2.1. debian-binary

Це простий текстовий файл, який містить лише один рядок з номером версії формату. Наразі це завжди `2.0`.

```bash
$ cat debian-binary
2.0
```

Цей файл дозволяє інструментам швидко перевірити, чи дійсно файл є пакунком Debian і яку версію специфікації він використовує. Нова версія формату може бути впроваджена в майбутньому шляхом зміни цього номера, але формат 2.0 залишається незмінним вже багато років.

### 2.2. control.tar.* (Архів метаданих та скриптів)

Цей архів містить метадані пакунка та так звані "керуючі скрипти" (maintainer scripts). Формат стиснення зазвичай `xz` або `gz` (у старих пакунках). Розпакувавши його, ми побачимо кілька ключових файлів:

- **control**: Найважливіший файл. Він містить метадані пакунка у форматі, схожому на заголовки електронної пошти (RFC 2822). Тут вказується ім'я пакунка, версія, архітектура, розробник (maintainer), короткий і довгий опис, а також — найголовніше — залежності (`Depends`, `Pre-Depends`, `Recommends`, `Suggests`, `Conflicts`, `Replaces`, `Provides`).

Приклад вмісту файлу `control`:
```text
Package: nano
Version: 5.4-2
Architecture: amd64
Maintainer: Ubuntu Developers <ubuntu-devel-discuss@lists.ubuntu.com>
Depends: libc6 (>= 2.29), libncursesw6 (>= 6), libtinfo6 (>= 6)
Section: editors
Priority: important
Description: small, friendly text editor inspired by Pico
 GNU nano is an easy-to-use text editor originally designed as a replacement
 for Pico, the ncurses-based editor from the non-free mailer Pine...
```

- **md5sums**: Містить MD5-хеші всіх файлів у пакунку. `dpkg` використовує їх для перевірки цілісності встановлених файлів. Якщо користувач змінить конфігураційний файл, `dpkg` знатиме про це завдяки незбігу хешу і запропонує варіанти дій під час оновлення (залишити стару версію, замінити новою або показати різницю).

- **conffiles**: Список файлів, які система повинна трактувати як конфігураційні. Під час оновлення пакунка `dpkg` ставиться до цих файлів з особливою обережністю, щоб не перезаписати налаштування, зроблені адміністратором.

- **preinst, postinst, prerm, postrm** (Maintainer Scripts): Це виконувані скрипти (зазвичай оболонкові скрипти `sh` або `bash`), які запускаються на різних етапах життєвого циклу пакунка:
  - `preinst`: виконується перед розпакуванням нових файлів.
  - `postinst`: виконується після розпакування файлів (часто використовується для запуску служб, компіляції Python байт-коду, оновлення кешів шрифтів тощо).
  - `prerm`: виконується перед тим, як файли будуть видалені під час деінсталяції або оновлення.
  - `postrm`: виконується після видалення файлів (використовується для очищення залишкових даних).

- **shlibs, symbols**: Файли, що використовуються для управління залежностями від спільних бібліотек.

Керуючі скрипти надають розробникам пакунків величезну гнучкість, але водночас є джерелом багатьох проблем. Помилка в `postinst` скрипті може призвести до того, що пакунок опиниться в стані "broken" (зламаний) або "half-configured" (напівналаштований), що може заблокувати роботу всього пакетного менеджера, поки проблему не буде вирішено вручну адміністратором.

### 2.3. data.tar.* (Архів даних)

Цей архів містить власне файли, які потрібно встановити в систему. Структура каталогів всередині `data.tar.xz` повністю відповідає структурі кореневої файлової системи (`/`).

Наприклад, якщо програма має виконуваний файл `nano`, сторінку керівництва (man page) і конфігураційний файл, архів даних виглядатиме так:

```
./usr/
./usr/bin/
./usr/bin/nano
./usr/share/
./usr/share/man/
./usr/share/man/man1/nano.1.gz
./etc/
./etc/nanorc
```

Під час встановлення `dpkg` просто розпаковує цей архів відносно кореневого каталогу `/`, розміщуючи файли на їхніх законних місцях, і фіксує інформацію про ці файли у своїй локальній базі даних (зазвичай у `/var/lib/dpkg/info/`).

## 3. Анатомія формату .rpm

Формат RPM спроєктований інакше. Замість використання стандартного архіватора як зовнішньої оболонки, файл `.rpm` є спеціалізованим бінарним файлом. Він має більш жорстку внутрішню структуру, яка складається з кількох чітко визначених секцій: RPM Lead (застаріла частина), Signature (цифровий підпис), Header (заголовок з метаданими) та Payload (корисне навантаження).

Давайте розглянемо ці частини детальніше. Щоб зазирнути всередину RPM-пакунка без його встановлення, можна використати утиліту `rpm2cpio` в поєднанні з `cpio`, оскільки Payload традиційно є cpio-архівом:

```bash
$ rpm2cpio htop-2.2.0-3.el7.x86_64.rpm | cpio -idmv
```

### 3.1. RPM Lead (Заголовок "Свинець")

Це історична частина формату, яка присутня в кожному файлі `.rpm` на самому початку. Її розмір становить рівно 96 байтів. Спочатку Lead призначався для ідентифікації файлу утилітою `file` та збереження базової інформації, необхідної для роботи з пакунком.

Сьогодні інформація в Lead ігнорується сучасними версіями RPM, оскільки вона дублюється у внутрішньому Header-і. Однак ця структура зберігається для забезпечення зворотної сумісності (magic number `ed ab ee db` залишається незмінним).

### 3.2. Signature (Підпис)

Безпека була одним з ключових пріоритетів під час розробки RPM. Секція Signature містить криптографічний підпис пакунка (найчастіше GPG або PGP), а також інформацію про розмір Payload і хеш (MD5/SHA256) всього заголовка (Header) та даних.

Коли ви запускаєте команду `rpm -K package.rpm`, інструмент перевіряє цей підпис. Якщо відкритий ключ розробника (maintainer) присутній у вашій системі, RPM підтверджує, що пакунок не був змінений після його створення. Це критично важливо для корпоративних середовищ. Хоча DEB також підтримує підписи (через `dpkg-sig` або підписування файлів `.changes`), в екосистемі Debian/Ubuntu основний акцент робиться на підписуванні самих репозиторіїв (файлів `Release`), а не окремих пакетів `.deb`. У світі RPM загальноприйнятою практикою є підписування кожного окремого файлу `.rpm`.

### 3.3. Header (Заголовок метаданих)

Це найважливіша частина RPM-пакунка для системи управління залежностями. Header містить всю інформацію про пакунок, яка в DEB зберігається у файлі `control` та інших допоміжних файлах.

Header організований як структура даних на основі тегів (tag-based structure). Замість простого тексту, тут використовуються цілочисельні ідентифікатори (теги) для позначення різних типів даних. Наприклад:
- Тег `RPMTAG_NAME` (1000) містить ім'я пакунка.
- Тег `RPMTAG_VERSION` (1001) містить версію.
- Тег `RPMTAG_REQUIRENAME` (1049) містить список залежностей.

Ви можете витягти ці метадані за допомогою команди:
```bash
$ rpm -qp --info htop-2.2.0-3.el7.x86_64.rpm
```

Header також містить скрипти (pre/post-install/uninstall), інформацію про changelog, імена та права доступу до всіх файлів, що містяться в пакунку. Цікавою відмінністю від DEB є те, що RPM зберігає детальну інформацію про кожен файл (розмір, власник, група, права доступу, хеш, тип) безпосередньо в Header-і, ще до розпакування Payload. Це дозволяє команді `rpm -qlp package.rpm` дуже швидко вивести список файлів, не торкаючись архівованих даних.

### 3.4. Payload (Корисне навантаження)

Payload містить власне стиснені файли. Історично RPM використовував формат `cpio` (від "copy in, copy out") стиснутий за допомогою `gzip`. Формат `cpio` був обраний через те, що він, як вважалося, краще обробляє метадані файлової системи (hard links, device nodes), ніж ранні версії `tar`.

Сьогодні формат Payload може варіюватися. Хоча `cpio` залишається стандартом, методи стиснення еволюціонували: спочатку це був `gzip`, потім `bzip2`, `xz` (LZMA2), і зараз багато сучасних дистрибутивів (наприклад, Fedora) перейшли на `zstd` (Zstandard), який забезпечує надзвичайно високу швидкість декомпресії при збереженні відмінного ступеня стиснення. Це значно прискорює процес встановлення та оновлення системи.

Отже, внутрішньо RPM — це бінарний формат із чітким розділенням на заголовок на основі тегів і cpio-архів файлів. Ця структура робить його дуже швидким для запитів бази даних (адже при встановленні Header просто копіюється в локальну базу даних RPM у `/var/lib/rpm/`), але менш прозорим для дослідження за допомогою звичайних утиліт без використання `rpm` або `rpm2cpio`.

## 4. Створення пакунків: Процес пакування

Створення пакунків (packaging) — це мистецтво. Пейкеджер (maintainer) повинен взяти вихідний код, написаний розробником програми, скомпілювати його (якщо необхідно), розмістити файли у правильних каталогах відповідно до стандарту ієрархії файлової системи (FHS), та написати метадані і скрипти, які забезпечать гладке встановлення.

Підходи до створення пакунків у DEB та RPM кардинально відрізняються. У світі RPM пакування зазвичай базується на одному великому файлі рецепту — `spec`-файлі. У світі DEB пакування базується на каталозі `debian/`, який містить багато маленьких файлів, кожен з яких відповідає за певну функцію.

### 4.1. Створення RPM пакунків (rpmbuild та .spec)

Основою RPM-пакування є файл `.spec`. Цей файл описує все: від того, звідки завантажити вихідний код, до того, як його скомпілювати, куди встановити файли та які скрипти виконати.

Процес створення пакунка виглядає так:
1. Ви створюєте структуру каталогів `~/rpmbuild/{BUILD,RPMS,SOURCES,SPECS,SRPMS}`.
2. Ви завантажуєте вихідний архів (tarball) у каталог `SOURCES`.
3. Ви пишете файл `програма.spec` у каталозі `SPECS`.
4. Ви запускаєте команду `rpmbuild -ba програма.spec`.

Файл `.spec` має чітко визначені секції. Ось спрощений приклад:

```spec
Name:           mypackage
Version:        1.0
Release:        1%{?dist}
Summary:        A simple example package

License:        GPLv3
URL:            https://example.com/mypackage
Source0:        %{name}-%{version}.tar.gz

BuildRequires:  gcc, make
Requires:       glibc >= 2.17

%description
This is a detailed description of mypackage.

%prep
# Розпаковує Source0
%autosetup

%build
# Компіляція
%configure
%make_build

%install
# Встановлення в тимчасовий корінь (buildroot)
%make_install

%files
# Список файлів, що увійдуть в пакунок
%doc README.md
%license LICENSE
%{_bindir}/myprogram
%{_mandir}/man1/myprogram.1*

%changelog
* Mon Mar 10 2025 Author Name <author@example.com> - 1.0-1
- Initial release
```

Цей підхід, орієнтований на один файл, дуже зручний. Він дозволяє пейкеджеру бачити весь процес збірки в одному місці. Макроси RPM (наприклад, `%configure`, `%{_bindir}`) автоматично розгортаються у правильні команди та шляхи (наприклад, `./configure --prefix=/usr --libdir=/usr/lib64`), що значно спрощує підтримку пакунка для різних архітектур і версій дистрибутиву.

Крім бінарного пакунка (наприклад, `.x86_64.rpm`), `rpmbuild` також створює Source RPM (SRPM, розширення `.src.rpm`). SRPM містить вихідний архів, патчі та сам `spec`-файл. Будь-який користувач може завантажити SRPM і перезібрати його на своїй системі за допомогою `rpmbuild --rebuild package.src.rpm`.

### 4.2. Створення DEB пакунків (каталог debian/)

У світі Debian філософія інша. Пакування базується на додаванні каталогу `debian/` до дерева вихідних кодів програми. Цей каталог містить набір файлів, кожен з яких має своє призначення. Інструмент, який керує процесом збірки, називається `dpkg-buildpackage` (або більш сучасні оболонки типу `debuild` з пакету `devscripts` чи інструмент `sbuild` для збірки в ізольованому середовищі).

Основні файли в каталозі `debian/`:

- `debian/control`: Описує метадані вихідного пакунка (Source) та одного або кількох бінарних пакунків (Package), які з нього збираються, включаючи залежності (`Build-Depends`, `Depends`).
- `debian/rules`: Це звичайний `Makefile`, який є серцем процесу збірки. Він визначає правила `build`, `binary`, `clean` тощо. У сучасних пакунках цей файл зазвичай складається з трьох рядків, оскільки він викликає інструмент `dh` (Debhelper), який автоматизує більшість типових кроків збірки (запуск configure, make, make install).
- `debian/changelog`: Файл історії змін. Його формат жорстко стандартизований, оскільки `dpkg` парсить його для визначення версії пакунка, що збирається.
- `debian/copyright`: Опис ліцензій та авторів коду. В екосистемі Debian ліцензійна чистота сприймається дуже серйозно.
- `debian/<package>.install`: Текстовий файл, який вказує `debhelper`, які файли слід перемістити з тимчасового каталогу збірки в кінцевий бінарний пакунок (корисно, коли один вихідний код генерує кілька різних `.deb` файлів, наприклад, `libfoo`, `libfoo-dev`, `foo-bin`).
- `debian/postinst`, `debian/prerm` тощо: Ті самі керуючі скрипти, про які ми згадували раніше.

Приклад сучасного `debian/rules`:
```makefile
#!/usr/bin/make -f
%:
	dh $@
```

Коли ви запускаєте `dpkg-buildpackage`, система читає `debian/rules`, запускає потрібні команди для компіляції програми, встановлює файли в тимчасовий каталог (`debian/<package>/`), потім генерує метадані на основі `debian/control` і `debian/changelog`, створює `control.tar.xz` і `data.tar.xz`, і, нарешті, збирає їх за допомогою `ar` у кінцевий файл `.deb`.

Цей підхід може здатися розкиданим у порівнянні з монолітним `spec`-файлом RPM. Однак він стимулює модульність. Інструмент `debhelper` має величезну кількість плагінів (`dh_python`, `dh_systemd`, `dh_installinit`), які роблять процес пакування складних застосунків дуже гнучким і надійним.

## 5. Порівняння архітектурних рішень

Дебати "DEB проти RPM" тривають десятиліттями, але насправді обидва формати чудово виконують свою роботу. Їхні відмінності лежать скоріше в філософії дизайну та історичному контексті екосистем, ніж у абсолютних технічних перевагах.

### 5.1. Управління метаданими
- **RPM** зберігає метадані в бінарному заголовку всередині пакунка і використовує бінарну базу даних (історично Berkeley DB, зараз часто SQLite або ndb) для відстеження встановлених пакунків. Це забезпечує швидкий пошук і надійність, але при пошкодженні бази даних її відновлення може бути складним завданням (`rpm --rebuilddb`).
- **DEB** використовує прості текстові файли в `/var/lib/dpkg/` (наприклад, файл `status`). База даних `dpkg` — це, по суті, великий текстовий файл. З одного боку, це повільніше для парсингу, але з іншого боку, його можна прочитати `cat` або відредагувати в `nano` (хоча це не рекомендується), і він дуже стійкий до пошкоджень.

### 5.2. Вирішення залежностей
Самі формати `.deb` та `.rpm` (і базові інструменти `dpkg` та `rpm`) **не вирішують залежності автоматично**. Якщо пакет A вимагає пакет B, а ви намагаєтесь встановити пакет A за допомогою `dpkg -i` або `rpm -i`, команда просто завершиться помилкою, повідомивши про відсутню залежність.

Для завантаження і встановлення залежностей існують високорівневі менеджери:
- **У світі DEB** це **APT** (Advanced Package Tool). APT завантажує списки пакунків (`Packages.gz`) з репозиторіїв, будує локальне граф-дерево залежностей і обчислює оптимальний шлях встановлення.
- **У світі RPM** це історично **Yum**, а нині **DNF** (у Fedora/RHEL/CentOS) та **Zypper** (у SUSE). Сучасний DNF використовує потужну бібліотеку `libsolv` (розроблену спочатку для Zypper), яка застосовує SAT-солвер для математично точного вирішення складних графів залежностей. Це робить DNF і Zypper надзвичайно надійними при вирішенні конфліктів, хоча розв'язання SAT може займати більше часу та ресурсів процесора.

### 5.3. Тригери (Triggers) проти Скриптів
Обидві системи підтримують pre/post скрипти. Але що відбувається, якщо 50 пакунків, які встановлюються одночасно, містять нові сторінки керівництва (man pages) або шрифти?
- **DEB** має концепцію **Triggers**. Замість того, щоб кожен пакет самостійно запускав `mandb` або `fc-cache`, вони просто активують "тригер". В кінці всього процесу встановлення DPKG обробляє ці тригери, виконуючи "важку" операцію лише один раз. Це значно прискорює масові оновлення.
- **RPM** історично покладався на `%post` скрипти, що могло призводити до багаторазового виконання однієї і тієї ж дії. Однак сучасний RPM також впровадив власну концепцію тригерів (File Triggers), яка працює схожим чином: відстежує зміни в певних каталогах і виконує скрипт лише один раз в кінці транзакції.

### 5.4. Взаємозамінність: Alien
Якщо ви опинилися в ситуації, коли вам потрібна програма, яка розповсюджується лише у форматі RPM, а ви працюєте в Ubuntu (або навпаки), існує утиліта під назвою **Alien**.
Команда `alien -d package.rpm` перепакує RPM-архів у файл `.deb`, змінивши внутрішню структуру. Команда `alien -r package.deb` зробить зворотне.

Хоча Alien дуже корисний, слід пам'ятати, що він конвертує лише файли та базові метадані. Він не може магічним чином конвертувати скрипти `preinst`/`postinst` у `%post`/`%pre` секції, оскільки ці скрипти часто специфічні для дистрибутиву (наприклад, використовують різні команди для управління сервісами). Крім того, імена залежностей (наприклад, `libncurses` в DEB може називатися `ncurses-libs` в RPM) не збігатимуться. Тому встановлення конвертованих пакунків може вимагати ручного втручання.

## 6. Майбутнє пакування: чи настане кінець DEB і RPM?

Останнім часом ми спостерігаємо тенденцію до нових, "універсальних" форматів пакування для десктопних застосунків, таких як **Flatpak** та **Snap**. Ці формати вирішують головну проблему DEB та RPM: прив'язку до конкретної версії дистрибутиву та його бібліотек. Flatpak та Snap "пакують" програму разом з усіма її залежностями (до певного базового рівня) і запускають її в ізольованому середовищі (sandbox).

Чи означає це смерть DEB та RPM? Однозначно ні.
1. **Системний рівень**: Універсальні формати не підходять для ядра Linux, драйверів, системних демонів, середовищ стільниці та базових бібліотек. Для цих фундаментальних компонентів системи DEB та RPM залишатимуться незамінними.
2. **Серверне використання**: На серверах контейнеризація (Docker, Podman) значною мірою замінила пакування застосунків. Однак базові образи контейнерів (наприклад, `ubuntu:latest` або `almalinux:9`) все ще створюються за допомогою DEB або RPM, і всередині цих контейнерів `apt` та `dnf` використовуються для встановлення необхідних пакетів.
3. **Стабільність і безпека**: Механізми підпису, аудиту та централізованого управління оновленнями, які пропонують репозиторії DEB і RPM, досі не мають аналогів за рівнем зрілості та довіри у корпоративному сегменті.

## Висновки

DEB і RPM є прикладами видатного програмного інжинірингу. Вони виникли в епоху, коли управління програмним забезпеченням було хаотичним, і навели порядок у світі Linux. 

- **DEB** обрав шлях простоти та прозорості, використовуючи стандартний інструмент `ar` та текстові метадані, і породив екосистему Debian, яка славиться своєю стабільністю та незліченною кількістю доступних пакетів.
- **RPM** пішов шляхом інтегрованого бінарного дизайну з потужними можливостями верифікації, ставши стандартом для корпоративних систем на базі технологій Red Hat, SUSE та інших.

Розуміння того, як ці пакети влаштовані зсередини (архів усередині архіву, скрипти обслуговування, дерева залежностей), дозволяє системному адміністратору не лише ефективніше управляти серверами, але й впевнено вирішувати складні проблеми, які виникають під час оновлень системи. Обидва світи пакування продовжують еволюціонувати (впроваджуючи нові алгоритми стиснення типу `zstd` чи нові SAT-солвери для вирішення залежностей), гарантуючи, що Linux залишатиметься гнучкою, керованою і безпечною операційною системою.
