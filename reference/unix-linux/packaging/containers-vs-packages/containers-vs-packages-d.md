Коли на одному Linux-сервері необхідно одночасно запустити веб-застосунок на Python, якому потрібна динамічна бібліотека `libssl.so.1.1` та `glibc 2.31`, і нову службу на Go, яка вимагає `glibc 2.35`, системний адміністратор стикається з фундаментальною перепоною. Динамічний лінкувальник хоста (`ld.so`) може завантажити в глобальний простір імен файлової системи лише одну версію `glibc` для виконання стандартних бінарних файлів. Спроба оновити `glibc` до версії 2.35 через системний пакетний менеджер миттєво робить веб-застосунок непрацездатним через несумісність символів ABI, тоді як відмова від оновлення блокує запуск нової служби.

Цей конфлікт показує фундаментальне протиріччя в архітектурі розгортання програмного забезпечення. З одного боку, системні пакунки (`.deb`, `.rpm`) будувалися довкола ідеї **максимального повторного використання спільних ресурсів ОС** в єдиній ієрархії каталогів FHS. З іншого боку, контейнерні технології стандарту OCI (Open Container Initiative) пропонують принципово іншу парадигму: **повну автономність середовища виконання застосунку** у власному ізольованому кореневому каталозі (`rootfs`).

## 1. Проблема спільного середовища: Чому виник розкол

Історично операційні системи сімейства Unix проективалися для роботи на обмеженому апаратному забезпеченні, де оперативна пам'ять та дисковий простір вимірювалися мегабайтами. Щоб не дублювати системний код, було створено механізм динамічних бібліотек (`shared objects`, `.so`) та стандарт ієрархії файлової системи FHS (Filesystem Hierarchy Standard).

У цій класичній моделі всі програми ділять між собою єдиний простір каталогів:
- Виконувані файли розгортаються у спільний каталог `/usr/bin`.
- Динамічні бібліотеки потрапляють у `/usr/lib` або `/usr/lib64`.
- Конфігурації зберігаються в уніфікованій структурі `/etc`.

Коли програма запускається, ядро завантажує її ELF-заголовок, знаходить секцію `DT_NEEDED` із назвою потрібної бібліотеки (наприклад, `libc.so.6`) та передає управління динамічному компонувальнику `ld.so`. Компонувальник шукає цей файл у системному кеші `/etc/ld.so.cache` і мапить його в оперативну пам'ять процесу.

Для розв'язання адрес динамічних функцій ядро та компонувальник використовують таблицю імпорту процедур (Procedure Linkage Table, PLT) та глобальну таблицю зсувів (Global Offset Table, GOT). Під час першого виклику функції з `.so` бібліотеки компонувальник знаходить її адрес у динамічній таблиці символів (`.dynsym`) та записує її в GOT.

![Архітектура розгортання: системний пакунок проти OCI-контейнера](/reference/unix-linux/packaging/containers-vs-packages/img/pkg-vs-container-layers.svg)
*Порівняльна архітектура розгортання: інтеграція пакунка в спільне середовище хоста проти автономного rootfs контейнера в ізольованих namespaces ядра.*

Головна перевага такої архітектури полягає у винятковій ефективності споживання оперативної пам'яті та дискового простору. Якщо на сервері виконується сотня різних процесів, кожен із яких використовує `libc.so.6`, ядро Linux завантажує фізичні сторінки пам'яті цієї бібліотеки в системний Page Cache лише **один раз**. Усі сотня процесів через свої таблиці сторінок (page tables) віртуальної пам'яті посилаються на ті самі фізичні кадри RAM у режимі `read-only`. Це дозволяє суттєво економити фізичну оперативну пам'ять на високонавантажених серверах.

Однак із ростом кількості незалежних сервісів та прискоренням циклів розробки програмного забезпечення ця перевага перетворилася на серйозну системну проблему, відому під назвою "пекло залежностей" (dependency hell):
1. **Глобальний простір імен бібліотек:** Дві програми на одному хості не можуть використовувати різні несумісні версії однієї динамічної бібліотеки, якщо вони розгортаються в спільний каталог `/usr/lib`. Оновлення бібліотеки для одного застосунку може непомітно зламати суміжний застосунок.
2. **Жорсткий зв'язок із дистрибутивом хоста:** Версії програмувальних мов, середовищ виконання та системних утиліт виявляються жорстко прив'язаними до циклу релізів конкретного дистрибутива (Debian, RHEL або Ubuntu). Якщо дистрибутив постачається з Python 3.8, встановлення Python 3.11 через системний пакетний менеджер загрожує пошкодженням системних скриптів самого дистрибутива.
3. **Побічні ефекти інсталяційних скриптів:** Установлення системного пакунка виконує керуючі скрипти (`postinst`, `%post`) із необмеженими правами `root`, які можуть змінити глобальний стан системи, перезапустити не пов'язані служби або пошкодити конфігурації інших програм.

Детальний аналіз того, як системні адміністратори намагалися розв'язати ці проблеми до появи контейнерів, описує історичний огляд у вставці [Історія еволюції ізоляції: від chroot до стандарту OCI](book:unix-linux/containers-vs-packages/hist-chroot-to-oci.md).

## 2. Анатомія розгортання: Мутабельний хост проти ізольованого rootfs

Фундаментальна різниця між системним пакунком і контейнером полягає в тому, **де саме пролягає межа автономності файлової системи**.

### Системний пакунок як елемент графу дистрибутива
Системний пакунок (`.deb` або `.rpm`) являє собою стиснутий архів, який містить точне дерево файлів та машинний паспорт (метадані зі списком залежностей). Коли менеджер пакунків (APT або DNF) встановлює пакунок, він виконує такі послідовні дії:
- Обчислює граф залежностей за допомогою розв'язувача логічних формул (SAT-солвера), перевіряючи відсутність конфліктів версій.
- Розпаковує вміст корисного навантаження (payload) безпосередньо в існуюче дерево файлової системи хоста (`/usr`, `/etc`, `/var`).
- Реєструє кожен створений файл у системній базі даних (`/var/lib/dpkg/status` або RPM database) для подальшого обліку.

У результаті встановлення файлова система хоста мутує. Якщо два пакунки містять файл із однаковим шляхом (наприклад, `/usr/bin/config-tool`), пакетний менеджер зупинить інсталяцію та виведе помилку через конфлікт власників файла.

### OCI-контейнер як автономне середовище виконання
Контейнер стандарту OCI не записує свої файли в загальні каталоги хоста. Замість цього контейнер постачається у вигляді образу (OCI Image), який містить повноцінне, автономне кореневе дерево файлової системи — **`rootfs`**.

Усередині цього `rootfs` розміщено геть усе, що потрібно для виконання застосунку:
- Власна копія C-бібліотеки (`glibc` або `musl`).
- Власний динамічний лінкувальник (`/lib64/ld-linux-x86-64.so.2`).
- Інтерпретатори мов, бінарники та системні утиліти.
- Власна ієрархія каталогів `/etc`, `/usr`, `/var`, повністю відсічена від хоста.

Коли контейнерний рушій (runc, podman або containerd) запускає контейнер, він не розпаковує ці файли в `/usr` хоста. Замість цього ядро Linux створює новий **Mount Namespace** (`CLONE_NEWNS`) та виконує системний виклик `pivot_root()`, який непомітно для процесу підміняє глобальний корінь `/` на підготовлений `rootfs` контейнера.

Для порівняння внутрішнього устрою реєстраційних файлів обох систем зверніться до довідника [Порівняльний довідник маніфестів: DEB/RPM проти OCI Spec](book:unix-linux/containers-vs-packages/api-container-vs-pkg-manifests.md).

## 3. Шаруваті файлові системи (OverlayFS) проти графу залежностей (SAT Solver)

Механізм доставки та зберігання даних у контейнерах радикально відрізняється від системних пакунків за принципом формування дискових образів та побудови зв'язків між компонентами.

### Граф залежностей системних пакунків
Пакетний менеджер оперує декларативним графом. Якщо застосунку потрібен сервер Nginx, пакетний менеджер не пакує Nginx разом із бібліотекою OpenSSL. Він декларує залежність `Requires: libssl.so.3` і покладається на те, що окремий пакунок `openssl` буде завантажено та встановлено в системні каталоги хоста. Це дозволяє уникнути дублювання однакових файлів на диску та забезпечує єдиний центр оновлень.

### Шари образів OCI та драйвер OverlayFS
Контейнерний образ будується з масиву незмінних (read-only) шарів. Кожен шар являє собою стиснутий tarball-архів, який виникає в результаті виконання окремої інструкції в `Dockerfile` або `Containerfile`.

Щоб об'єднати ці шари в єдине цілісне дерево файлової системи без фізичного копіювання гігабайтів даних на диску, ядро Linux використовує спеціалізовану файлову систему **OverlayFS**.

![Схема монтування OverlayFS у контейнерному середовищі](/reference/unix-linux/packaging/containers-vs-packages/img/overlayfs-structure.svg)
*Схема монтування OverlayFS: об'єднання незмінних базових шарів (lowerdir) із мутабельним шаром контейнера (upperdir) у віртуальне дерево (merged).*

OverlayFS об'єднує кілька каталогів на хості в одну віртуальну точку монтування:
- **`lowerdir`:** Список каталогів, що відповідають незмінним шарам OCI-образу (базовий дистрибутив, рантайм мови, код програми). Вони змонтовані в режимі `read-only`.
- **`upperdir`:** Верхній мутабельний шар, створений для конкретного екземпляра контейнера у режимі `read-write`.
- **`workdir`:** Службовий каталог ядра для атомарної підготовки файлових операцій.
- **`merged`:** Віртуальний каталог, який презентує об'єднаний результат для процесів усередині контейнера.

Коли процес усередині контейнера читає файл, VFS-драйвер OverlayFS шукає його спочатку в `upperdir`, а якщо не знаходить — проходить по шарах `lowerdir` згори донизу.

Якщо процес намагається **змінити** файл великого розміру (наприклад, файл бази даних SQLite), який лежить у нижньому read-only шарі `lowerdir`, ядро прозоро застосовує механізм **Copy-on-Write (CoW)**:
1. Ядро повністю копіює весь файл із `lowerdir` у мутабельний `upperdir` (операція `copy_up`).
2. Модифікація записується в копію усередині `upperdir`.
3. Оригінальний файл у базовому шарі образу залишається недоторканим і продовжує використовуватися іншими контейнерами.

Важливо враховувати, що перша спроба запису у великий файл усередині OverlayFS супроводжується затримкою I/O через фізичне копіювання блоків диска з `lowerdir` у `upperdir`. Для бази даних чи інтенсивного I/O слід монтувати розвантажувальні томи (bind mounts або persistent volumes), які оминають драйвер OverlayFS.

Якщо файл видаляється, ядро створює у верхньому шарі `upperdir` спеціальний символ-заглушку — **whiteout device** (символьний пристрій із мажорним та мінорним номером `0,0`). Для процесів усередині контейнера файл зникає, хоча у незмінному шарі образу на диску він зберігається. Якщо у верхньому шарі створюється каталог з однаковою назвою, OverlayFS може позначити його як непрозорий (`opaque`), блокуючи видимість підкаталогів нижніх шарів.

### Порівняльна характеристика моделей пакування

| Архітектурний критерій | Системний пакунок (`.deb` / `.rpm`) | OCI-контейнер (`Docker` / `Podman`) |
| :--- | :--- | :--- |
| **Одиниця ізоляції** | Немає (спільне середовище хоста) | Mount, PID, NET, USER Namespaces |
| **Формування rootfs** | Прямий запис у FHS хоста (`/usr`) | Збирання незмінних шарів у OverlayFS |
| **Вирішення залежностей** | SAT-солвер під час інсталяції | Запікання залежностей у базові шари |
| **Модифікація файлів** | Пряма перезапис файлів на диску | Механізм Copy-on-Write (upperdir) |
| **Повторне використання RAM** | Спільний Page Cache для `.so` файлів | Ізольований Page Cache (різні rootfs) |
| **Ефективність диска** | Висока (файли не дублюються) | Середня (дедуплікація лише на рівні шарів) |

## 4. Граничні витрати: Продуктивність, ресурси та безпека

Розгортання програм через контейнери часто супроводжується міфом про "важкі накладні витрати", притаманні віртуальним машинам. Однак з точки зору ядра Linux контейнер — це **звичайний процес**, обмежений системними примітивами.

### Продуктивність CPU та системних викликів (Zero Overhead)
На відміну від апаратних гіпервізорів (KVM, ESXi, Hyper-V), які віртуалізують процесор через інструкції VT-x/AMD-V та перехоплюють виклики через таблиці EPT/NPT, контейнери **не створюють жодного проміжного шару емуляції**.

Коли процес усередині OCI-контейнера виконує системний виклик (наприклад, `read()`, `write()`, `socket()`), інструкція `syscall` передає управління безпосередньо хостовому ядру Linux. Планувальник ядра (CFS / EEVDF) розподіляє процесорний час між контейнеризованими та звичайними процесами хоста абсолютно однаково. Накладні витрати на виконання обчислень та I/O у контейнерах дорівнюють **0%**.

### Управління ресурсами через cgroups v2
Для запобігання ситуаціям, коли один контейнер вичерпує процесорний час або пам'ять хоста, ядро застосовує контролери **cgroups v2** (Control Groups):
- **`memory.max`:** Суворе лімітування оперативної пам'яті. При перевищенні ліміту ядро активує OOM Killer лише для процесів усередині цієї групи.
- **`memory.high`:** М'яке обмеження пам'яті, яке викликає асинхронне витіснення сторінок пам'яті (page reclaim) без негайного вбивства процесів.
- **`cpu.max`:** Квотування CPU за допомогою CFS bandwidth control (наприклад, 200000 мкс з 100000 мкс кванту означає дозвіл на використання 2 ядер CPU).
- **`io.weight`:** Пропорційний розподіл пропускної здатності блокових пристроїв I/O.

### Пастка споживання пам'яті: Розрив Page Cache
Головна реальна вартість контейнеризації полягає у **збільшенні споживання оперативної пам'яті** через втрату спільного системного Page Cache.

Розглянемо випадок, коли на хості запущено 20 примірників сервісу:
- **У системних пакунках:** Усі 20 процесів посилаються на один і той самий файл `/usr/lib/x86_64-linux-gnu/libc.so.6`. Ядро утримує у фізичній пам'яті RAM лише **одну** копію коду `glibc` (приблизно 2 МБ).
- **У контейнерах OCI:** Якщо контейнери зібрані на базі різних базових образів (наприклад, 10 на Debian Alpine з `musl libc`, 5 на Ubuntu 22.04 з `glibc 2.35` та 5 на Debian 11 з `glibc 2.31`), ядро змушене завантажити у RAM **три різні копії** C-бібліотек у три окремі Page Cache.

Крім того, оскільки файли усередині `upperdir` та `lowerdir` OverlayFS мають різні i-node з точки зору хостової VFS, ядро не завжди може дедуплікувати однакові бінарні файли між різними контейнерами, якщо шари не мають ідентичного SHA-256 хешу.

### Межі безпеки: Скрипти майнтайнера проти Kernel Isolation
Безпека системних пакунків тримається на **довірі до репозиторію**. Установлення `.deb` пакунка з невідомого джерела є смертельно небезпечним: скрипт `postinst` виконується з UID 0 у контексті хоста і може форматувати диски, встановлювати руткіти або викрадати SSH-ключі.

Контейнери будують безпеку на **ізоляції примітивів ядра**:
- **Namespaces:** Обмежують видимість системних ресурсів (`mnt`, `pid`, `net`, `ipc`, `uts`, `user`). Наприклад, User Namespaces дозволяють процесу вважати себе `root` (UID 0) усередині контейнера, залишаючись звичайним непривілейованим користувачем (наприклад, UID 10001) на хості.
- **Cgroups v2:** Гарантують, що збійний контейнер не зможе вичерпати всю RAM хоста і спровокувати виклик Out-Of-Memory (OOM) Killer для системних служб.
- **Capabilities:** Контейнери за замовчуванням позбавлені небезпечних привілеїв `root` (наприклад, `CAP_SYS_ADMIN`, `CAP_SYS_RAWIO`, `CAP_NET_ADMIN`).
- **Seccomp:** Профілі BPF-фільтрації системних викликів блокують виконання небезпечних syscalls (наприклад, `kexec_load` або `reboot`) на рівні ядра.

## 5. Обслуговування та ланцюжок постачання: Модель оновлень та CVE Drift

Різниця в архітектурах створює два фундаментально протилежні підходи до усунення вразливостей (CVE patching) та забезпечення цілісності ланцюжка постачання ПЗ.

### Модель атомарного оновлення системних пакунків
Коли в бібліотеці `OpenSSL` виявляють критичну вразливість, розробники дистрибутива (Debian або Red Hat) випускають оновлений пакунок `libssl3`.

Адміністратор хоста виконує одну команду:
```bash
sudo apt update && sudo apt install --only-upgrade libssl3
```

Пакетний менеджер атомарно замінює файл `/usr/lib/x86_64-linux-gnu/libssl.so.3` на диску та перезапускає залежні демони. Усі програми на хості **миттєво** починають використовувати захищену бібліотеку. Відповідальність за моніторинг вразливостей лежить на команді безпеки дистрибутива.

### Модель запікання та дрейф вразливостей (CVE Drift) у контейнерах
У контейнерному світі заміна бібліотеки на хості **нічого не змінює** для контейнерів, оскільки кожен контейнер містить власну автономну копію `libssl.so` всередині свого OCI-образу.

Щоб усунути вразливість у контейнері, необхідно пройти повний ланцюжок CI/CD:
1. Майнтайнер базового образу (Debian/Alpine) випускає новий патчений базовий образ.
2. Розробник застосунку повинен тригерити новий білд у CI/CD, щоб заново виконати `docker build`.
3. Збирається новий шар з оновленою бібліотекою і публікується в Container Registry.
4. Оркестратор (Kubernetes або Podman) виконує перезапуск подов (rolling update) із витягуванням нового образу.

Якщо розробники забули оновити `Dockerfile` або проєкт перебуває у стадії підтримки без активної розробки, контейнер роками продовжує виконуватися із вразливою копією бібліотеки, незважаючи на те, що хостова система повністю оновлена. Цей ефект називається **CVE Drift** (дрейф вразливостей у контейнерних шарах).

## 6. Практична діагностика: Простеження контейнерів інструментами хоста

Оскільки процес у контейнері — це звичайний процес Linux, системний адміністратор може інспектувати його безпосередньо з хоста через системні утиліти та файлову систему `/proc`.

### Пошук просторів імен та точок монтування
Щоб дізнатися, у яких саме namespaces працює процес контейнера, використовується утиліта `lsns` або аналіз файлової системи `/proc`. Нижче наведено приклади простеження стану процесів та їхніх просторів імен мовами C та C++:

:::tabs
```c
/* inspect_ns.c — Перевірка просторів імен процесу мовою C */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <string.h>
#include <errno.h>

static int check_namespace_entry(const char *pid_str, const char *ns_name) {
    char path[256];
    snprintf(path, sizeof(path), "/proc/%s/ns/%s", pid_str, ns_name);

    int fd = open(path, O_RDONLY);
    if (fd < 0) {
        fprintf(stderr, "Помилка відкриття %s: %s\n", path, strerror(errno));
        return -1;
    }

    printf("[C Inspector] Namespace %s для PID %s успішно відкрито (fd=%d)\n",
           ns_name, pid_str, fd);
    close(fd);
    return 0;
}

int main(int argc, char *argv[]) {
    if (argc < 2) {
        fprintf(stderr, "Використання: %s <PID>\n", argv[0]);
        return EXIT_FAILURE;
    }

    const char *pid = argv[1];
    printf("=== Аналіз просторів імен процесу PID %s ===\n", pid);

    check_namespace_entry(pid, "mnt");
    check_namespace_entry(pid, "pid");
    check_namespace_entry(pid, "net");
    check_namespace_entry(pid, "uts");
    check_namespace_entry(pid, "ipc");
    check_namespace_entry(pid, "user");

    return EXIT_SUCCESS;
}
```
```cpp
// inspect_ns.cpp — Ідіоматична перевірка просторів імен мовою C++20
#include <iostream>
#include <filesystem>
#include <string_view>
#include <system_error>
#include <vector>

namespace fs = std::filesystem;

class NamespaceInspector {
public:
    explicit NamespaceInspector(std::string_view pid)
        : proc_ns_path_(fs::path("/proc") / pid / "ns") {}

    void print_namespaces() const {
        std::error_code ec;
        if (!fs::exists(proc_ns_path_, ec)) {
            std::cerr << "Каталог процесу " << proc_ns_path_ << " не існує або недоступний\n";
            return;
        }

        std::cout << "=== [C++ Inspector] Inspecting namespaces for PID " << proc_ns_path_ << " ===\n";
        for (const auto& entry : fs::directory_iterator(proc_ns_path_, ec)) {
            std::error_code symlink_ec;
            auto target = fs::read_symlink(entry.path(), symlink_ec);
            if (!symlink_ec) {
                std::cout << "  * " << entry.path().filename().string() 
                          << " -> " << target.string() << "\n";
            }
        }
    }

private:
    fs::path proc_ns_path_;
};

int main(int argc, char* argv[]) {
    if (argc < 2) {
        std::cerr << "Використання: inspect_ns <PID>\n";
        return EXIT_FAILURE;
    }

    NamespaceInspector inspector(argv[1]);
    inspector.print_namespaces();
    return EXIT_SUCCESS;
}
```

### Простеження монтувань OverlayFS через `/proc`
Системний файл `/proc/<PID>/mountinfo` демонструє точний склад шарів OverlayFS, що використовуються контейнером. При виконанні команди `cat /proc/4820/mountinfo` утиліта виведе рядок монтування ядра:

```text
581 540 0:52 / / merged rw,relatime lowerdir=/var/lib/containers/storage/overlay/lower2:/var/lib/containers/storage/overlay/lower1,upperdir=/var/lib/containers/storage/overlay/upper,workdir=/var/lib/containers/storage/overlay/work
```

Цей рядок підтверджує, що ядро Linux прозоро зшиває незмінні шари `lower1` та `lower2` із верхнім мутабельним шаром `upper` безпосередньо у віртуальній файловій системі VFS.

Щоб практично випробувати створення власного контейнера без додаткових інструментів, виконайте покроковий приклад із вставки [Проєкт: Мінімальний контейнерний рушій на OverlayFS](book:unix-linux/containers-vs-packages/proj-chroot-overlay-runner.md).
