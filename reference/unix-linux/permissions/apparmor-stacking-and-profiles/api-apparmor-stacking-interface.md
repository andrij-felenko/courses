# 📋 Програмний інтерфейс та контракти libapparmor і securityfs

Взаємодія програмного забезпечення з механізмом стекування та просторами імен AppArmor здійснюється через два основні рівні: вищий рівень системної бібліотеки `libapparmor` (заголовок `<sys/apparmor.h>`) та низькорівневий інтерфейс ядра, представлений атрибутами procfs (`/proc/self/attr/`) та віртуальною файловою системою `securityfs` (зазвичай змонтованою в `/sys/kernel/security/apparmor/`).

### 1. Функції C API бібліотеки `libapparmor`

Системна бібліотека `libapparmor` надає набір обгортальних C-функцій над операціями запису в procfs-атрибути поточного процесу. Кожна з функцій приймає специфікатор профілю або мітки й повертає коди помилок у разі невдачі.

| Функція | Аргументи | Семантика та семантична дія під час стекування | Код повернення |
| :--- | :--- | :--- | :--- |
| `aa_change_profile` | `const char *profile` | Негайно змінює поточний політичний контекст. Якщо переданий рядок містить оператор `//&`, ядро створює нову стековану мітку. | `0` у разі успіху, `-1` при помилці (`errno` встановлюється). |
| `aa_change_onexec` | `const char *profile` | Запланувати зміну або додавання профілю під час наступного виклику `execve()`. | `0` у разі успіху, `-1` при помилці. |
| `aa_stack_profile` | `const char *profile` | Додає вказаний профіль до існуючого стеку профілів поточного процесу, звужуючи множину дозволів. | `0` у разі успіху, `-1` при помилці. |
| `aa_stack_onexec` | `const char *profile` | Запланувати додавання вказаного профілю до існуючого стеку під час наступного виклику `execve()`. | `0` у разі успіху, `-1` при помилці. |
| `aa_getcon` | `char **con, char **mode` | Повертає активну мітку безпеки процесу (виділяє пам'ять через `malloc`) та поточний режим (`enforce`/`complain`). | Довжина рядка мітки або `-1` при помилці. |
| `aa_change_hat` | `const char *subprofile, unsigned long magic_token` | Перехід у підпрофіль (hat) з можливістю повернення за токеном `magic_token`. | `0` у разі успіху, `-1` при помилці. |
| `aa_query_label` | `uint32_t mask, char *query, size_t size, int *allowed, int *audited` | Динамічне запитування ядра щодо дозволу конкретної операції для вказаної мітки без її виконання. | `0` у разі успіху, `-1` при помилці. |

Виклик `aa_query_label` дозволяє високонавантаженим демонам або серверним платформам виконувати авторизаційні перевірки на рівні користувацького простору до здійснення реального файлового або мережевого системного виклику. Модуль ядра AppArmor приймає запит через pseudo-файл `/sys/kernel/security/apparmor/.access`, проганяє запитуваний шлях та маску прав через активні автомати DFA усіх профілів у стеку і повертає бітові прапори `allowed` та `audited`.

### 2. Синтаксис специфікаторів стеку та просторів імен

Рядок профілю, що передається системним функціям `aa_change_profile`, `aa_change_onexec` або записується безпосередньо у procfs-файли, підпорядковується суворому граматичному формату.

Формальна граматика BNF для специфікатора мітки:

```text
<label_spec>     ::= <profile_ident> ( "//&" <profile_ident> )*
<profile_ident>  ::= ( ":" <ns_name> "://" )? <profile_name>
<ns_name>        ::= [a-zA-Z0-9_\-\.]+ ( "//" [a-zA-Z0-9_\-\.]+ )*
<profile_name>   ::= [a-zA-Z0-9_\-\.\/]+
```

Типові приклади рядків міток у реальних контейнерних системах:
- `usr.sbin.nginx` — одиночний профіль у поточному (глобальному) просторі імен AppArmor.
- `:containers:lxd-web://usr.sbin.nginx` — профіль `usr.sbin.nginx`, який завантажено у вкладений простір імен `containers:lxd-web`.
- `docker-default//&usr.sbin.nginx` — стек із двох профілів, що знаходяться в поточному просторі імен.
- `lxc-container-default//&:lxd-db-1://usr.sbin.mysqld` — складна стекована мітка, яка поєднує хостовий профіль контейнера `lxc-container-default` із локальним профілем СУБД у просторі імен контейнера.

### 3. Низькорівневий procfs-інтерфейс `/proc/[pid]/attr/`

Бібліотека `libapparmor` виконує свої операції шляхом формування спеціалізованого тексту та його запису в атрибутивні pseudo-файли Linux procfs.

Атрибути безпеки процесу у каталозі `/proc/self/attr/`:
- `/proc/self/attr/current`: Прямий запис команди у форматі `exec <profile>` або `stack <profile>` викликає негайну зміну політичного контексту поточного процесу.
- `/proc/self/attr/exec`: Запис команди у форматі `exec <profile>` або `stack <profile>` задає заплановану мітку, яка активується ядром в момент виконання виклику `execve()`.
- `/proc/self/attr/prev`: Містить рядок мітки, у якій процес перебував до останнього переходу (використовується для аудиту та підпрофілів hat).

Оператор `exec` у записі procfs вимагає явного дозволу `change_profile` у поточному профілі, тоді як оператор `stack` вимагає правил `change_profile -> <target>` або `change_profile -> //&*`.

### 4. Ієрархічна структура файлової системи `securityfs`

Файлова система `securityfs` (зазвичай змонтована за шляхом `/sys/kernel/security/apparmor/`) надає користувацькому простору доступ до завантаження, вивантаження та інспектування профілів і просторів імен.

Структура каталогів та файлів управління:

```text
/sys/kernel/security/apparmor/
├── .access                   # Програмне запитування прав для простору користувача
├── .load                     # Інтерфейс завантаження нових профілів (binary/text stream)
├── .replace                  # Точка гарячої заміни існуючих профілів без втрати стану
├── .remove                   # Точка видалення профілю з ядра
├── profiles                  # Перелік усіх завантажених профілів у дефолтному namespace
└── policy/
    └── namespaces/           # Каталог ієрархії просторів імен AppArmor
        ├── container-alpha/
        │   ├── raw_data      # Бінарні дані завантажених профілів
        │   ├── profiles      # Список профілів у даному просторі імен
        │   └── namespaces/   # Підпорядковані простори імен (child namespaces)
        └── container-beta/
            └── profiles
```

Запис у `.load`, `.replace` та `.remove` вимагає системної capability `CAP_MAC_ADMIN` у початковому просторі імен користувачів (user namespace).

### 5. Параметри модуля ядра `/sys/module/apparmor/parameters/`

Поведінка механізму стекування та виключень глобально регулюється через параметри модуля ядра AppArmor, доступні в `/sys/module/apparmor/parameters/`:

- `enabled` (read-only, boolean): Відображає, чи активовано AppArmor у поточному завантаженні ядра.
- `debug` (read-write, integer): Рівень деталізації налагоджувальних повідомлень AppArmor у `dmesg`.
- `audit` (read-write, string): Глобальний режим аудиту (`normal`, `quiet_rejected`, `dbug`, `all`).
- `mode` (read-write, string): Глобальний примусовий режим (`enforce`, `complain`).
- `lock_policy` (read-write, boolean): Якщо встановлено у `1`, блокує будь-які подальші зміни або завантаження нових профілів у ядро до перезавантаження системи.

### 6. Коди помилок ядра та умови їх виникнення

При невдалій спробі зміни чи стекування профілів системні виклики повертають значення `-1`, а змінна `errno` встановлюється в один із наступних стандартних кодів:

- `EACCES`: Поточний профіль процесу не містить правила `change_profile`, яке дозволяє перехід на вказаний цільовий профіль або додавання його у стек.
- `EINVAL`: Некоректний синтаксис рядка мітки (наприклад, незакриті двокрапки простору імен або відсутність профілю після `//&`).
- `ENOENT`: Вказаний профіль або простір імен AppArmor не завантажено в ядро.
- `EPERM`: Спроба видалити батьківський профіль зі стеку або виконувати маніпуляції з политиками без наявності `CAP_MAC_ADMIN`.
- `E2BIG`: Перевищено максимальну кількість профілів у векторі мітки `aa_label` (понад 32 профілі).
- `ENOMEM`: Недостатньо оперативної пам'яті ядра для виділення нової структури `struct aa_label` чи обчислення таблиць hash.

### 7. Формат запису аудиту при виникненні конфліктів у стеку

Коли системна операція блокується ядром через відмову одного з профілів у стеку, демон аудиту `auditd` або журнал ядра `dmesg` отримує запис типу `AUDIT_APPARMOR_DENIED` (код `1400`):

```text
type=1400 audit(1700000000.789:4321): apparmor="DENIED" operation="open" 
  profile="docker-default//&:container-ns-1://usr.sbin.nginx" 
  name="/etc/shadow" pid=12345 comm="nginx" requested_mask="r" denied_mask="r" fsuid=0 ouid=0
```

Розбір ключів аудиторського повідомлення:
- `apparmor="DENIED"`: Статус операції (відхилено за відсутності дозволу).
- `operation`: Назва перехопленого LSM-хука чи файлової операції VFS (`open`, `file_mmap`, `execve`, `cap_capable`, `net_bind`).
- `profile`: Повна активна мітка процесу. Символ `//&` вказує на те, що відмова сталася під час оцінки стекованого политичного контексту.
- `name`: Абсолютний шлях до файлового ресурсу або назва мережевої операції, щодо якої запитувався доступ.
- `requested_mask` / `denied_mask`: Запитані та заблоковані біти прав (`r` — читання, `w` — запис, `x` — виконання, `a` — дописування).
- `pid` / `comm`: Ідентифікатор процесу та назва виконуваного бінарного файла.
