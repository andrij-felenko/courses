</preknowlist>

Придумати правило безпеки легко: «цій програмі не можна відкривати мережеві сокети — ніколи, ким би її не запустили». Значно важче відповісти на технічне питання: куди це правило покласти, щоб воно справді діяло.

Усередину самої програми — марно. Правило має стримувати її тоді, коли всередині вже виконується чужий код; перевірка, яку робить сам підозрюваний, нічого не варта.

На вході в ядро, за номером виклику й аргументами? Там правило ще нема про що висловити. `open()` дістає рядок; на що цей рядок насправді вкаже, залежить від поточного каталогу, символьних посилань і того, що куди змонтовано — а розбір шляху ще попереду. Судити за аргументами — судити за здогадом; це відома межа [seccomp](book:unix-linux/seccomp-filtering), який навмисне дивиться лише на числа в регістрах.

У файлову систему? Тоді ext4 нестиме свою копію правил, XFS свою, а сокети туди не влізуть узагалі: вони не файлова система.

Лишається одне місце — те, де ядро вже тримає в руках сам об'єкт і ось-ось над ним щось зробить. Приємна обставина в тому, що ядро й так туди приходить: саме там воно ставить власне питання «а чи можна?» і перевіряє права. Отже, нового місця шукати не треба — треба поставити в тому самому місці **друге питання** й дати комусь право на нього відповісти.

Так виглядає весь задум Linux Security Modules: точки, у яких ядро питає сторонній код про операцію, яку збирається виконати. Гачок (англ. *hook* — гак, зачіп) — це і є така точка.

## Один гачок зблизька

Уся LSM-частина функції, яку викликають на відкритті файлу, — один рядок:

```c
/* security/security.c, суть виклику */
int security_file_open(struct file *file)
{
	return call_int_hook(file_open, file);
}
```

Кличуть її з `do_dentry_open()` — тоді, коли `struct file` уже зібрано: інод знайдено, режим відкриття розібрано, класичні права перевірено. Питання поставлено над готовим об'єктом, а не над рядком, який колись мав ним стати.

Таких функцій у ядрі 6.12 рівно 268. Їхній перелік зведено в один файл, `include/linux/lsm_hook_defs.h`, і кожен рядок там оголошує тип відповіді, типове значення й підпис:

```c
LSM_HOOK(int, 0, file_open, struct file *file)
LSM_HOOK(int, 0, inode_permission, struct inode *inode, int mask)
LSM_HOOK(int, 0, task_kill, struct task_struct *p, struct kernel_siginfo *info,
	 int sig, const struct cred *cred)
LSM_HOOK(int, 0, socket_connect, struct socket *sock, struct sockaddr *address,
	 int addrlen)
```

Друге поле — те, що вважати відповіддю, коли не відповів ніхто. Для перевірок доступу це нуль: «не заперечую».

Тепер найцікавіше — макрос, який стоїть за викликом. Він визначає властивості всієї конструкції куди більше, ніж будь-яка політика безпеки:

```c
#define __CALL_STATIC_INT(NUM, R, HOOK, LABEL, ...)			     \
do {									     \
	if (static_branch_unlikely(&SECURITY_HOOK_ACTIVE_KEY(HOOK, NUM))) {  \
		R = static_call(LSM_STATIC_CALL(HOOK, NUM))(__VA_ARGS__);    \
		if (R != LSM_RET_DEFAULT(HOOK))				     \
			goto LABEL;					     \
	}								     \
} while (0);
```

Читається це так. У кожного гачка є кілька гнізд — рівно стільки, скільки модулів узагалі може виявитися в цій збірці ядра. Гнізда обходять по черзі. Порожнє пропускають. Заповнене викликають — і **перша ж відповідь, що не збігається з типовою, обриває обхід і стає відповіддю всього гачка**.

![Що відбувається всередині одного виклику гачка. Ліворуч згори вниз: код ядра do_dentry_open, класична перевірка прав, а від неї бічна стрілка вбік із написом, що при відмові гачок нижче не викликають узагалі. Далі виклик security_file_open і під ним ланцюг із чотирьох гнізд. Гніздо нуль — модуль capability, повернув нуль, далі. Гніздо один — landlock, повернув нуль, далі. Гніздо два — apparmor, повернув мінус EACCES, стоп. Гніздо три — bpf, сірим, не питали. Унизу підсумок: security_file_open повертає мінус EACCES, гнізда після другого не опитано ніколи](/reference/unix-linux/permissions/lsm-framework/img/hook-call.svg)

*Обхід гнізд обривається на першій відмові. Модуль, що стоїть далі в черзі, чужого «ні» не бачить — і тому не має способу його скасувати.*

## Чому гачок уміє лише забороняти

Дві незалежні обставини змовилися дати одну властивість.

Перша — розташування. Гачок стоїть **після** класичної перевірки, а та повертається одразу, щойно сказала «ні». Заборонена дев'ятьма бітами операція до гачка просто не доходить: модуля не питають, бо все вже скінчилося вище.

Друга — той самий макрос. Обхід обривається на першому «ні», і жодного місця, де чужу відмову можна було б перетворити на дозвіл, у коді немає. Не «заборонено правилами» — саме немає, як немає операції, якої не написали.

Разом це означає: модуль безпеки здатний тільки **звужувати** дозволене. Такі гачки називають обмежувальними на противагу владним (англ. *authoritative* — повновладний), які вміли б і дозволяти. Владних у Linux немає, і це не випадковість, а рішення, ухвалене 2001 року разом із самим каркасом; чому саме так і чого це коштувало — окремо: [чому гачкам заборонили дозволяти](book:unix-linux/lsm-framework/hist-restrictive-hooks.md).

Один виняток усе-таки є, і він показовий. Серед гачків є `capable` — те саме питання «чи має цей процес такий мандат», яким ядро користується скрізь, зокрема й для того, щоб **обійти** дев'ять бітів через `CAP_DAC_OVERRIDE`. Тут «так» справді дозволяє те, чого класична перевірка не дозволила б. Тому відповідати на нього першим поставлено не чийсь модуль, а вбудовану логіку можливостей — і це записано в перелік місць у черзі:

```c
enum lsm_order {
	LSM_ORDER_FIRST = -1,	/* This is only for capabilities. */
	LSM_ORDER_MUTABLE = 0,
	LSM_ORDER_LAST = 1,	/* This is only for integrity. */
};
```

Модуль `capability` відповідає завжди й завжди перший. Сказав «ні» — обхід обірвано, решти не питають. Сказав «так» — далі можуть відмовити інші. Отже, навіть у єдиному гачку, чия відповідь щось дозволяє, право дозволяти лишилося за самим ядром.

## Пам'ять модуля на чужому об'єкті

Відповідати на питання про інод, не пам'ятаючи про цей інод нічого, здебільшого неможливо: SELinux має тримати на ньому мітку, Landlock — посилання на правило, яке його накриває. Заводити збоку хеш-таблицю «об'єкт → дані» — це і зайвий пошук на кожній операції, і окрема морока з тим, коли запис видаляти.

Тому потрібні дані живуть **на самому об'єкті**: у `struct inode`, `struct cred`, `struct file`, `struct task_struct` і десятку інших є поле `void *`, у яке модуль кладе своє. Спершу цим полем модуль володів сам — сам виділяв, сам звільняв. Наслідок був неминучий: другому модулеві покласти туди своє було нікуди, тож у системі міг працювати лише один.

Тепер полем розпоряджається каркас. Модуль на старті лише **оголошує апетит** — скільки байтів йому треба на об'єкт кожного роду:

```c
struct lsm_blob_sizes {
	int lbs_cred;
	int lbs_file;
	int lbs_inode;
	int lbs_sock;
	int lbs_task;
	int lbs_superblock;
	/* … і ще кілька родів об'єктів */
};
```

Каркас додає ці числа докупи, дає кожному модулеві його зсув усередині спільного шматка й від того моменту виділяє пам'ять сам — одним разом на об'єкт. Модуль читає й пише за своїм зсувом і про сусіда навіть не знає.

![Як каркас ділить одне поле об'єкта між кількома модулями. Ліворуч три рядки з тим, що кожен модуль просить на старті: selinux шістнадцять байтів на інод для мітки контексту, landlock вісім байтів для посилання на правило, apparmor нуль, бо судить за шляхом і на інод не пише. *Зсуви рахують один раз на завантаженні системи. Саме ця дрібниця, а не політики й не гачки, перетворила «один модуль» на «скільки завгодно».*

## Не всі гачки — присуди

Тепер видно, чому «гачок уміє лише забороняти» — твердження про перевірки доступу, а не про каркас загалом. Із 268 гачків 52 не повертають нічого зовсім. Це сповіщення: об'єкт народився, об'єкт помирає, облікові дані скопійовано. Вирішувати там нічого — навпаки, каркас кличе **всі** модулі по черзі, нікого не пропускаючи: сповіщення адресоване кожному, кому воно про щось каже — одному завести свої байти на щойно народженому об'єкті, іншому прибрати їх зі шматка, який ось-ось звільнять.

Є й третій рід, який не судить, а постачає. Коли файл щойно створюють, каркас питає гачком `inode_init_security`, які розширені атрибути на нього покласти, — і саме звідти новий файл дістає свою мітку. Типове значення тут не нуль, а `-EOPNOTSUPP`: «мені нема чого сказати». Такі гачки каркас обходить не тим макросом, а власним циклом, який збирає відповіді від усіх, у кого вони є.

Разом виходить розподіл праці, який легко не помітити: обмежувальні гачки судять про дію, а сповіщальні тримають у порядку той самий стан на об'єктах, на який судження спираються. Без других перші не мали б про що судити.

## Як модуль потрапляє в каркас

Уся реєстрація — це таблиця пар «гачок, функція» і оголошення себе. Ось Yama, найкоротший модуль у ядрі: він робить рівно одне — обмежує, хто кого може взяти під [ptrace](book:unix-linux/ptrace-model):

```c
static struct security_hook_list yama_hooks[] __ro_after_init = {
	LSM_HOOK_INIT(ptrace_access_check, yama_ptrace_access_check),
	LSM_HOOK_INIT(ptrace_traceme,      yama_ptrace_traceme),
	LSM_HOOK_INIT(task_prctl,          yama_task_prctl),
	LSM_HOOK_INIT(task_free,           yama_task_free),
};

static int __init yama_init(void)
{
	security_add_hooks(yama_hooks, ARRAY_SIZE(yama_hooks), &yama_lsmid);
	yama_init_sysctl();
	return 0;
}

DEFINE_LSM(yama) = {
	.name = "yama",
	.init = yama_init,
};
```

Дві дрібниці тут важать більше, ніж здається. `__ro_after_init` кладе таблицю в ділянку, яку ядро робить незаписуваною, щойно завантаження скінчилося: підмінити чужий гачок після старту не вийде навіть коду ядра. А `DEFINE_LSM` — це не виклик, а розміщення запису в окремій секції образу, `.lsm_info.init`. Ніхто нікого не реєструє на ходу: каркас на завантаженні просто проходить цю секцію від початку до кінця.

Звідси й відповідь на питання, яке виникає в кожного, хто дійшов сюди: чому це не звичайний [модуль ядра](book:unix-linux/kernel-modules), який можна довантажити? Причин дві, і обидві нездоланні.

Перша — час. Модулі безпеки піднімаються серед найперших, до кореневої файлової системи: SELinux має проставити мітку вже першому іноду, який з'явиться. Те, що довантажили пізніше, пропустило все, що сталося до нього, — і не має способу дізнатися, що саме.

Друга — вихід. Прибрати гачки з працюючої системи нікому не вдалося сформулювати безпечно: на живих об'єктах уже лежать байти модуля, ухвалені рішення вже осіли в кешах, і половина стану машини залежить від того, кого хочуть вимкнути. Саме тому `register_security` перестали віддавати назовні ще у 2.6.24 (латка 2007-го, випуск 2008-го), і відтоді модуль безпеки — це код у складі ядра, зібраний разом із ним. Ціна відома й визнана: щоб спробувати свій модуль, треба зібрати своє ядро, а щоб він потрапив до людей — прийняти його в дерево ядра, бо [сталого внутрішнього ABI](book:unix-linux/kernel-abi-stability) для нього ніхто не обіцяє.

## Хто увімкнений і в якому порядку

Скільки записів у секції — стільки й кандидатів; хто з них справді працюватиме, вирішує звичайний текстовий рядок. У образі це `CONFIG_LSM`; у командному рядку завантаження — `lsm=`, і він переважає повністю. Старий `security=` лишився для сумісності й називає лише один головний модуль.

Порядок у цьому рядку — це порядок обходу гнізд, тобто те, чия відмова спрацює першою й чиє ім'я побачить [аудит](book:unix-linux/audit-framework). Два місця незмінні: `capability` завжди першим, підсистема цілісності — завжди останньою.

І є відсів, який пояснює найчастіше здивування. SELinux, AppArmor і Smack позначені прапорцем виключності:

```c
DEFINE_LSM(apparmor) = {
	.name = "apparmor",
	.flags = LSM_FLAG_LEGACY_MAJOR | LSM_FLAG_EXCLUSIVE,
	.enabled = &apparmor_enabled,
	.blobs = &apparmor_blob_sizes,
	.init = apparmor_init,
};
```

Каркас бере перший виключний, який трапився в черзі, а решту тихо вимикає. Тому [SELinux і AppArmor](book:unix-linux/mac-selinux-apparmor) не працюють разом — і причина не в гачках, яких вистачило б на обох, і не в блобах, які тепер діляться. Причина назовні: обидва хочуть тих самих поверхонь у просторі користувача — `/proc/self/attr`, атрибути `security.*`, ті самі поля в записах аудиту, — а кожної з них по одній. Розв'язати це намагаються з іншого боку: у 6.8 (2024) з'явилися системні виклики `lsm_list_modules`, `lsm_get_self_attr` і `lsm_set_self_attr`, які від початку говорять про **кілька** модулів одночасно; повне їх поєднання досі лишається незакінченою роботою.

![Шлях від записів у образі ядра до живого списку модулів. *Черга складається на завантаженні й уже не змінюється. Вимкнений виключний модуль не залишає по собі ні помилки, ні натяку — крім рядка в докладному журналі старту.*

> 🔧 **Навіщо це.** Коли служба з правильними правами дістає `Permission denied`, перше питання — хто взагалі має право сказати «ні» на цій машині. `cat /sys/kernel/security/lsm` показує живий список у порядку обходу — саме той, а не той, що в конфігурації дистрибутива. Якщо в ньому нема модуля, який ви налаштовуєте, далі можна не шукати: він вимкнений або витіснений виключністю, і жодне правило його політики не виконується. Якщо є — відмову шукають в аудиті, і запис назве модуль, який її ухвалив. Порядок у списку теж робочий: відмовляє перший, хто заперечив, тож коли два модулі накривають ту саму дію, у журналі буде видно лише того, хто стоїть раніше.

## Скільки це коштує

268 гачків стоять у найгарячіших місцях ядра: кожне відкриття файлу, кожен складник кожного шляху, кожен надісланий сигнал. Довгий час кожен виклик був непрямим — крізь список зареєстрованих функцій, а на процесорах з захистом від Spectre непрямий виклик коштує особливо дорого.

У 6.12 (2024) список замінили на статичні виклики. Тепер число гнізд відоме на збірці — його виводять із того, які модулі взагалі є в образі, — а місце кожного гнізда виправляють [латанням машинного коду](book:unix-linux/kernel-text-patching) прямо на завантаженні: заповнене гніздо стає прямим викликом, порожнє — переходом, що ніколи не спрацьовує. Заміряний виграш на наборі UnixBench — від 1.9% на запуску процесів до 9.5% на каналах; найбільше виграють дешеві виклики, де кілька гачків важать помітну частку всієї роботи.

Числа скромні, і саме тому вони показові: плата за сам каркас лежить не в політиках, а в непрямому виклику, який робиться сотні тисяч разів на секунду.

## Що влізло в каркас, коли його відчинили

Задумували його під обов'язковий контроль доступу, а заселили значно ширше — бо «місце, де ядро питає дозволу перед дією» виявилося потрібним усім, хто хоче щось заборонити.

Yama — дев'ять сторінок коду й одна думка про `ptrace`. LoadPin — вимога, щоб усі модулі ядра й прошивки приходили з одного носія. SafeSetID — обмеження на те, у кого саме процесові вільно перевтілитися. Lockdown — відрізання шляхів, якими root дописує щось у працююче ядро. Підсистема цілісності, яка [перевіряє підписи файлів перед запуском](book:unix-linux/ima-appraisal), сидить у тому ж каркасі й тому й стоїть останньою в черзі. [Landlock](book:unix-linux/landlock) перевернув передумову: він дозволяє **непривілейованому** процесу самому себе обмежити, без адміністратора й без спільної політики.

Осібно стоїть модуль `bpf`. Він не має власних правил — він віддає гачки програмам, які приносить простір користувача: перевірена програма [eBPF](book:unix-linux/ebpf-extended-berkeley-packet-filter) чіпляється до потрібного гачка й відповідає замість модуля. По суті це та сама довантажувана безпека, від якої відмовилися 2007 року, — тільки повернулася вона крізь інші двері: перевіряльник обмежує, що програма може зробити, а від'єднання визначене й безпечне, бо жодного стану на об'єктах вона не тримає. Як написати й підключити такий гачок за кілька десятків рядків — окремо: [власний модуль безпеки на BPF](book:unix-linux/lsm-framework/proj-bpf-lsm.md). Формальний бік — підписи гачків, поля `DEFINE_LSM`, розміри блобів і перемикачі завантаження — зібрано тут: [що саме треба оголосити модулеві](book:unix-linux/lsm-framework/api-lsm-module.md).

Каркас, отже, відповідає не на питання «як зробити Linux захищеним», а на питання про владу: хто всередині ядра має право сказати «ні», у якому порядку його про це питають і чи може хтось сказати «так» поверх цього «ні». Linux відповів: право має код, прийнятий у дерево ядра, питають його у двохстах з гаком названих місцях, у порядку, зафіксованому на завантаженні, і «так» поверх чужого «ні» не каже ніхто. Усе інше — від дев'ятирядкового вимикача `ptrace` до повної системи міток — це та сама форма влади, і різняться модулі лише тим, яку її частину беруть.
