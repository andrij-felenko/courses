# 📜 Історія еволюції аудиту Linux: від auditd та Netlink до програмованого eBPF

Підсистема аудиту безпеки в ядрі Linux пройшла довгий шлях від статичних механізмів журналювання системних викликів початку 2000-х років до гнучкого, програмованого моніторингу в реальному часі на базі eBPF. Розуміння цієї еволюції пояснює фундаментальні архітектурні обмеження класичних інструментів і причини масового переходу сучасної безпекової інженерії на BPF-трасування.

## Ера класичного Linux Audit Framework (KAUDIT)

У ядрі Linux 2.6 (випущеному в 2003 році) з'явилася підсистема **KAUDIT** (Kernel Audit), розроблена переважно інженерами Red Hat для забезпечення відповідності вимогам корпоративної безпеки CAPP (Controlled Access Protection Profile) та стандартам POSIX.

Архітектура KAUDIT побудована навколо перехоплення системних викликів на вході (`sys_enter`) та виході (`sys_exit`). Коли процес здійснює системний виклик (наприклад, `openat` або `execve`), ядро перевіряє його проти статично завантажених правил аудиту (підсистема `auditctl`). Якщо правило спрацьовує, ядро формує текстове повідомлення аудиту й надсилає його через Netlink-сокет (`NETLINK_AUDIT`) у простір користувача, де його читає демон `auditd` та записує у `/var/log/audit/audit.log`.

```
[Системний виклик] → [KAUDIT Перехоплення] → [Фільтр правил auditctl]
                                                       ↓
[/var/log/audit/audit.log] ← [Демон auditd] ← [NETLINK_AUDIT Socket]
```

### Архітектурні обмеження KAUDIT

Незважаючи на довголіття та широке розповсюдження, модель KAUDIT зіткнулася з критичними проблемами при масштабуванні у хмарних середовищах:

1. **Накладні витрати контекстного перемикання:** Кожна подія аудиту вимагала копіювання даних із пам'яті ядра в простір користувача через Netlink-сокет. При високій інтенсивності системних викликів (наприклад, 100 000+ викликів/с на високонавантаженому вебсервері) середовище витрачало до 20–30% ресурсів процесора лише на серіалізацію та передачу логів аудиту.
2. **Переповнення буфера та втрата подій (`audit_backlog_limit`):** Демон `auditd` виконується у просторі користувача як однопотоковий або обмежений демон. Якщо швидкість генерації подій ядром перевищує швидкість читання демоном, кільцевий буфер ядра переповнюється. Ядро вимушене або відкидати нові події аудиту (що неприпустимо для безпеки), або призупиняти виконання процесів системи (що спричиняє відмову в обслуговуванні).
3. **Відсутність контейнерного контексту:** Підсистема KAUDIT створювалася задовго до появи ізоляції cgroups та User Namespaces. Повідомлення `auditd` містять лише системний `pid`, `uid` та `comm`. Вони нічого не знають про ідентифікатори контейнерів Docker/Kubernetes (Container ID, Pod Name, Namespace), що робить прив'язку подій безпеки у Kubernetes надзвичайно складною.
4. **Неможливість синхронного блокування (In-kernel Enforcement):** KAUDIT є виключно пасивним механізмом пасивного запису подій post-factum. Він не може зупинити шкідливий виклик до його виконання.

## Поява eBPF та переломний момент у трасуванні

У 2014 році Олексій Старовойтов та Деніел Боркманн (Daniel Borkmann) запропонували докорінну переробку класичного BPF (використовуваний у tcpdump) в ядрі Linux 3.18, створивши **eBPF (Extended BPF)**. Замість простого фільтра мережевих пакетів eBPF перетворився на повноцінну 64-бітну віртуальну машину всередині ядра з RISC-подібним набором інструкцій, регістрами та мапами пам'яті.

Початково eBPF застосовувався для аналізу мережевого трафіку (XDP, tc). Однак поява можливості прив'язувати eBPF-програми до динамічних зондів ядра (`kprobes`) та статичних точок трасування (`tracepoints`) відкрила нову еру в безпековому моніторингу.

### Ключові етапи розвитку eBPF-трасування безпеки:

- **Linux 4.1–4.4 (2015–2016):** Додано підтримку `BPF_PROG_TYPE_KPROBE` та `BPF_PROG_TYPE_TRACEPOINT`. Інструменти першого покоління (на базі бібліотеки BCC / Python) отримали можливість аналізувати будь-які функції ядра без модифікації коду ядра.
- **Linux 5.1–5.8 (2019–2020):** 
  - Запроваджено **BTF (BPF Type Format)** та концепцію **CO-RE (Compile Once – Run Everywhere)**, що усунуло потребу встановлювати повні вихідні тексти та заголовки ядра (`kernel-devel`) на кожний цільовий вузол для компіляції BPF-коду.
  - Поява **BPF Ring Buffer** (`bpf_ringbuf`), який замінив застарілий Perf Ring Buffer, зменшивши споживання пам'яті та забезпечивши високу швидкість передачі подій між ядром і користувацьким простором.
  - Запровадження **BPF LSM** у Linux 5.7 — інтеграція eBPF безпосередньо у фреймворк Linux Security Modules, що дало змогу eBPF-програмам повертати від'ємні коди помилок (наприклад, `-EPERM`) і активувати синхронний контроль доступу.

## Сучасний стан: Від інструментів аудиту до автономних систем безпеки

Еволюція від KAUDIT до eBPF змінила саму парадигму моніторингу безпеки Linux:

| Характеристика | Класичний Auditd (KAUDIT) | Сучасний eBPF моніторинг |
| :--- | :--- | :--- |
| **Точка перехоплення** | Системні виклики (sys_enter/sys_exit) | Kprobes, Tracepoints, fentry, LSM hooks |
| **Програмованість** | Статичні декларативні правила | Повноцінні C/BPF програми з логікою |
| **Збагачення контекстом** | Лише базова інформація процесу | Динамічний збір cgroup, namespace, kstack |
| **Накладні витрати CPU** | Високі при великій кількості подій | Мінімальні (обробка та фільтрація в ядрі) |
| **Передавання даних** | Netlink сокет (текстовий формат) | BPF Ring Buffer (структурована пам'ять) |
| **Активний захист** | Відсутній (лише логування) | Можливий (BPF LSM, `bpf_send_signal`) |

Сучасні проекти CNCF (Cloud Native Computing Foundation), такі як **Falco** та **Tetragon**, повністю покладаються на eBPF. Вони дозволяють аналізувати події безпеки безпосередньо у просторі ядра, відсікати легітимний трафік без перемикання контексту й передавати у простір користувача лише критичні безпекові аномалії.
