# 🧮 Математична модель відображення ідентифікаторів (UID/GID Mapping)

Відображення ідентифікаторів у просторах імен користувачів Linux формалізується як кусково-афінне перетворення на множині цілих невід'ємних чисел. Підсистема безпеки ядра Linux виконує трансляцію ідентифікаторів в обох напрямках при кожному виклику перевірки прав доступу VFS, системних викликах `stat`, `getuid`, `chown` та перевірках володіння процесами.

## Математичне означення та алгебраїчні властивості

Нехай `U_ns` — множина цілочисельних ідентифікаторів усередині даного user namespace, а `U_host` — множина ідентифікаторів у батьківському просторі імен (або на хості). В операційній системі Linux ідентифікатори представлені типом `uid_t` (32-бітне ціле без знаку, від 0 до 4294967295).

Відображення задається впорядкованою послідовністю з `K` неперетинних екстентів (впорядкованих діапазонів):

```text
E = { e_0, e_1, ..., e_{K-1} }
```

Де кожен екстент `e_k` описується кортежем із трьох цілих чисел:

```text
e_k = (first_ns_k, first_host_k, count_k)
```

Компоненти кортежу описують:
- `first_ns_k` — початковий UID усередині простору імен;
- `first_host_k` — початковий UID у батьківському просторі імен;
- `count_k` — кількість неперервних ідентифікаторів у даному діапазоні (`count_k > 0`).

### Умови ін'єктивності та коректності відображення

Щоб відображення було коректним та унеможливлювало ситуації, коли два різні хостові UID відображаються в один внутрішній UID (або навпаки), ядро вимагає суворого виконання трьох інваріантів неперетинності.

Для будь-якої пари різних екстентів `i` та `j` (де `0 ≤ i < j < K`):

1. **Неперетинність у внутрішньому просторі імен**:
   `[first_ns_i, first_ns_i + count_i - 1] ∩ [first_ns_j, first_ns_j + count_j - 1] = ∅`

2. **Неперетинність у зовнішньому (батьківському) просторі імен**:
   `[first_host_i, first_host_i + count_i - 1] ∩ [first_host_j, first_host_j + count_j - 1] = ∅`

3. **Обмеження діапазону типів**:
   Для всіх `k` сума не має переповнювати 32-бітний тип: `first_ns_k + count_k ≤ 2³²` та `first_host_k + count_k ≤ 2³²`; окремо ядро відкидає `first`, що дорівнює `4294967295` — це значення зарезервоване як «недійсний ідентифікатор».

Якщо при записі у `/proc/[pid]/uid_map` порушується хоча б одна з цих умов, системний виклик `write` повертає помилку `EINVAL`. Це захищає підсистему VFS від створення колізій ідентифікаторів володіння файлами.

## Формалізація функцій трансляції

### 1. Пряма функція трансляції (Inside → Outside)

Пряма функція `f: U_ns → U_host` переводить внутрішній UID процесу чи файла у відповідний зовнішній UID для перевірки привілеїв у ядрі:

```text
f(uid_ns) =
  first_host_k + (uid_ns - first_ns_k),  якщо ∃ k : first_ns_k ≤ uid_ns < first_ns_k + count_k
  ⊥ (немає відображення),                якщо ∀ k : uid_ns ∉ [first_ns_k, first_ns_k + count_k - 1]
```

У разі `⊥` ядро повертає не число, а ознаку недійсності (`INVALID_UID`), і системний виклик, якому цей ідентифікатор був потрібен, завершується помилкою — саме тому `setuid()` на невідображений UID дає `EINVAL`. Значення `overflowuid` (типово `65534`, що відповідає `nobody`) вживається лише у зворотному напрямку, коли ядро мусить щось показати процесові.

Пряма трансляція виконується щоразу, коли процес всередині user namespace виконує дії щодо системних ресурсів хоста (наприклад, відкриває файл, створює новий сокет чи надсилає сигнал іншому процесу). Ядро переводить внутрішній UID процесу у системний `kuid_t` та перевіряє права доступу на рівні хоста.

### 2. Обернена функція трансляції (Outside → Inside)

Обернена функція `g: U_host → U_ns` переводить хостовий UID у внутрішній UID, який повертається процесу під час системних викликів `stat(2)` або `getuid(2)`:

```text
g(uid_host) =
  first_ns_k + (uid_host - first_host_k), якщо ∃ k : first_host_k ≤ uid_host < first_host_k + count_k
  overflowuid,                            якщо ∀ k : uid_host ∉ [first_host_k, first_host_k + count_k - 1]
```

Обернена трансляція захищає простір імен від витоку інформації про реальні хостові ідентифікатори. Якщо файл на хості належить користувачеві, чий UID не входить до жодного екстенту мапінгу даного user namespace, процес бачитиме цього власника як `65534` (`nobody`).

### 3. Композиція багаторівневих відображень

У разі ієрархії із трьох просторів імен (Host → UserNS_Parent → UserNS_Child) трансляція обчислюється шляхом послідовної композиції функцій.

Якщо відображення `UserNS_Child → UserNS_Parent` задається функцією `f_1`, а відображення `UserNS_Parent → Host` — функцією `f_2`, підсумковий UID на хості обчислюється як:

```text
f_total(uid_child) = (f_2 ∘ f_1)(uid_child) = f_2( f_1(uid_child) )
```

Якщо на будь-якому з проміжних рівнів ідентифікатор не знаходить мапінгу, ланцюжок обривається: у прямому напрямку виклик відхиляється як недійсний, у зворотному процес бачить `overflowuid`. Ізоляція зберігається на всіх рівнях ієрархії.

## Алгоритми та структури даних ядра (`struct uid_gid_map`)

У коді ядра Linux відображення описується структурою `struct uid_gid_map`. Для забезпечення високої швидкодії гарячих шляхів VFS ядро використовує гібридну структуру даних залежно від кількості екстентів `K`.

:::tabs
```c
struct uid_gid_map {
    u32 nr_extents;
    union {
        struct uid_gid_extent extent[UID_GID_MAP_MAX_BASE_EXTENTS];
        struct {
            struct uid_gid_extent *forward;
            struct uid_gid_extent *reverse;
        };
    };
};
```
```cpp
struct UidGidExtent {
    uid_t first_ns;
    uid_t first_host;
    uid_t count;
};

struct UidGidMap {
    std::uint32_t nr_extents;
    std::variant<
        std::array<UidGidExtent, 5>,
        std::pair<std::vector<UidGidExtent>, std::vector<UidGidExtent>>
    > extents;
};
```
:::

### Внутрішні типи ядра (`kuid_t` та `kgid_t`)

Ядро Linux не оперує сирими числами `uid_t` усередині VFS та підсистеми процесів. Замість цього використовуються безпечні обгортки типів `kuid_t` та `kgid_t`:

:::tabs
```c
typedef struct { uid_t val; } kuid_t;
typedef struct { gid_t val; } kgid_t;
```
```cpp
enum class KUid : uid_t {};
enum class KGid : gid_t {};
```
:::

Це запобігає випадковому порівнянню внутрішнього UID одного простору імен із внутрішнім UID іншого простору імен без виконання процедури мапінгу.

### Режими зберігання екстентів

1. **Малий режим (K ≤ 5 extents)**:
   Константа `UID_GID_MAP_MAX_BASE_EXTENTS = 5`.
   Для малих мапінгів ядро використовує простий масив `struct uid_gid_extent extent[5]`. Пошук виконується прямим лінійним скануванням за `O(K)`. Оскільки `K ≤ 5`, увесь масив лежить в одній-двох кеш-лініях, і сканування коштує лічені такти — дешевше за будь-яку розгалужену структуру.

2. **Великий режим (5 < K ≤ 340 extents)**:
   Константа `UID_GID_MAP_MAX_EXTENTS = 340`.
   Якщо кількість діапазонів перевищує 5, ядро виділяє динамічний масив із двома впорядкованими покажчиками:
   - `forward` — екстенти, відсортовані за `first_ns` для прискорення прямого пошуку `map_id_down()`;
   - `reverse` — екстенти, відсортовані за `first_host` для прискорення оберненого пошуку `map_id_up()`.

Пошук у великому режимі виконується через алгоритм двійкового пошуку (Binary Search) за `O(log K)`. При максимальному `K = 340` двійковий пошук виконує не більше `ceil(log2(340)) = 9` порівнянь.

## Детальні покрокові обчислення відображення

Розглянемо конфігурацію мапінгу з трьома екстентами:

```text
Рядок 1: 0      100000  1000    [Екстент 0: root та системні користувачі]
Рядок 2: 1000   1000    1       [Екстент 1: відображення самого власника]
Рядок 3: 2000   200000  5000    [Екстент 2: додатковий блок користувачів]
```

Параметри екстентів:
- `Extent 0`: `first_ns = 0`, `first_host = 100000`, `count = 1000` (внутрішні 0..999 → хостові 100000..100999).
- `Extent 1`: `first_ns = 1000`, `first_host = 1000`, `count = 1` (внутрішній 1000 → хостовий 1000).
- `Extent 2`: `first_ns = 2000`, `first_host = 200000`, `count = 5000` (внутрішні 2000..6999 → хостові 200000..204999).

### Приклад 1: Пряма трансляція внутрішнього UID 500 (Inside → Outside)

```text
Вхідне значення: uid_ns = 500

Крок 1: Перевірка Extent 0
  first_ns_0 = 0, count_0 = 1000
  Діапазон: [0, 0 + 1000 - 1] = [0, 999]
  Перевірка: 0 <= 500 <= 999  --> ІСТИНА (Збіг з Extent 0)

Крок 2: Обчислення хостового UID
  f(500) = first_host_0 + (500 - first_ns_0)
         = 100000 + (500 - 0)
         = 100500

Підсумок: Внутрішній UID 500 відображається у хостовий UID 100500.
```

### Приклад 2: Обернена трансляція хостового UID 201500 (Outside → Inside)

```text
Вхідне значення: uid_host = 201500

Крок 1: Перевірка Extent 0
  first_host_0 = 100000, count_0 = 1000
  Діапазон: [100000, 100999]
  Перевірка: 100000 <= 201500 <= 100999 --> ХИБА

Крок 2: Перевірка Extent 1
  first_host_1 = 1000, count_1 = 1
  Діапазон: [1000, 1000]
  Перевірка: 1000 <= 201500 <= 1000 --> ХИБА

Крок 3: Перевірка Extent 2
  first_host_2 = 200000, count_2 = 5000
  Діапазон: [200000, 204999]
  Перевірка: 200000 <= 201500 <= 204999 --> ІСТИНА (Збіг з Extent 2)

Крок 4: Обчислення внутрішнього UID
  g(201500) = first_ns_2 + (201500 - first_host_2)
            = 2000 + (201500 - 200000)
            = 2000 + 1500
            = 3500

Підсумок: Хостовий UID 201500 у даному User Namespace бачиться як UID 3500.
```

### Приклад 3: Трансляція невідображеного хостового UID 50000

```text
Вхідне значення: uid_host = 50000

Перевірка Extent 0: 100000 <= 50000 <= 100999 --> ХИБА
Перевірка Extent 1: 1000 <= 50000 <= 1000     --> ХИБА
Перевірка Extent 2: 200000 <= 50000 <= 204999 --> ХИБА

Результат: Жоден екстент не покриває UID 50000.
  g(50000) = overflowuid = 65534 (nobody)

Підсумок: Процес у контейнері бачить власника файла з UID 50000 як nobody.
```

Математична строгість перевірок у ядрі гарантує, що жоден непривілейований процес не зможе отримати доступ до ресурсів хоста за межами явно записаних екстентів.
