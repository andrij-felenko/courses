# Юзер-простори імен (User Namespaces) та відображення UID/GID

<preknowlist>
- [Простори імен (Namespaces)](book:unix-linux/namespaces) — як ядро ізолює глобальні ресурси (PID, мережа, монтування).
- [Ідентифікатори користувачів і груп](book:unix-linux/process-credentials-uids-gids) — що таке реальний та ефективний UID, `capabilities`.
</preknowlist>

До появи просторів імен користувачів контейнеризація стикалася з фундаментальною проблемою привілеїв. Щоб створити повноцінний контейнер (із власним мережевим стеком, таблицею маршрутизації та власними точками монтування), процес мусив мати права справжнього адміністратора (`root` хоста). Проте надання процесу прав `root` на хості є небезпечним: якщо зловмисник знайде вразливість у контейнері і вийде за його межі (container breakout), він отримає повний контроль над фізичним сервером.

User Namespaces розв'язали цю проблему, розірвавши зв'язок між привілеями всередині ізольованого середовища та привілеями на хості. Вони дозволяють процесу мати власну незалежну таблицю ідентифікаторів користувачів (UID) і груп (GID). Процес, що має звичайний непривілейований UID на хості (наприклад, 1000), може мати UID 0 (root) всередині свого простору імен. 

Це механізм, що лежить в основі **rootless** контейнерів: користувач створює середовище, де він є адміністратором і може виконувати налаштування системи (монтувати файлові системи, конфігурувати мережу), але з погляду хостового ядра він залишається звичайним користувачем, і його дії обмежені ресурсами цього конкретного простору.

## Створення та ізоляція привілеїв

Новий простір імен користувачів створюється прапорцем `CLONE_NEWUSER` у системних викликах `clone(2)` або `unshare(2)`. Головна відмінність `CLONE_NEWUSER` від створення інших просторів імен (мережі, PID тощо) полягає в тому, що **для його створення не потрібні жодні привілеї**. Будь-який звичайний користувач може викликати `unshare(CLONE_NEWUSER)`.

Коли процес створює новий user namespace, ядро надає йому **повний набір capabilities** (включно з `CAP_SYS_ADMIN`, `CAP_NET_ADMIN` тощо) — але **тільки щодо цього нового простору імен**. 

Межі цих привілеїв суворо контролюються архітектурою ядра:
1. Процес має привілеї лише над тими ресурсами, які «належать» цьому ж user namespace (або його нащадкам).
2. Якщо процес спробує вплинути на ресурс батьківського простору імен (наприклад, змінити хостовий мережевий інтерфейс або прочитати `/etc/shadow` хоста), ядро перевірить його capabilities у батьківському просторі, яких він не має.

Саме тому `CLONE_NEWUSER` часто комбінують з іншими прапорцями. Наприклад, виклик `unshare(CLONE_NEWUSER | CLONE_NEWNET)` створює новий простір користувачів і відразу ж — новий мережевий простір. Оскільки новий user namespace отримує `CAP_NET_ADMIN`, він має право створити мережевий простір. Усередині нього процес може налаштовувати `iptables` або піднімати інтерфейси, але він не зможе створити міст (bridge) з хостовою мережею.

## Відображення ідентифікаторів (Mapping)

Самого лише створення простору недостатньо. Ядро має знати, як внутрішні ідентифікатори (UID/GID) процесу співвідносяться з реальними (хостовими). Поки це не налаштовано, процес матиме фіктивний UID `65534` (відомий як `nobody` або `overflowuid`), і всі його дії відхилятимуться ядром через відсутність мапінгу.

Правила трансляції задаються через два спеціальні файли: `/proc/PID/uid_map` та `/proc/PID/gid_map`. 

### Формат uid_map та gid_map

Кожен рядок у цих файлах описує один неперервний діапазон ідентифікаторів і складається з трьох чисел:

`ID_внутрішній   ID_зовнішній   Довжина`

Наприклад, запис:
`0 1000 1`
Означає: внутрішній UID 0 відповідає зовнішньому UID 1000. Довжина діапазону — 1 ідентифікатор.

Запис:
`1 100000 65536`
Означає: внутрішні UID від 1 до 65536 послідовно відображаються на зовнішні UID від 100000 до 165535.

Ядро застосовує цей мапінг в обох напрямках:
- Коли процес звертається до ядра (наприклад, відкриває файл), ядро бере його внутрішній UID, знаходить відповідний зовнішній UID через `uid_map` і виконує перевірку доступу вже за зовнішнім ідентифікатором.
- Коли процес запитує ідентифікатор (через `stat(2)` для файла або через `getuid(2)`), ядро бере зовнішній UID файла, знаходить його у мапінгу і повертає процесу внутрішнє значення. Якщо зовнішній UID не має відображення, ядро повертає фіктивне значення `65534` (`nobody`).

### Запис у мапінг: Обмеження безпеки

Файли мапінгу можна записати **лише один раз**. Це захищає від атак, де процес міг би динамічно міняти свої ідентифікатори для доступу до різних ресурсів.

До того ж, ядро суворо контролює, хто і що може туди записати:
1. **Процес з привілеями на хості** (`CAP_SETUID` у батьківському просторі) може налаштувати будь-який мапінг (відображати будь-які внутрішні UID на будь-які зовнішні).
2. **Непривілейований процес** (той, що створив namespace) може відобразити **тільки свій власний ефективний UID**. Він може записати `0 1000 1` (щоб стати root-ом всередині), але ядро відхилить спробу відобразити інші UID.

Це створює проблему для rootless контейнерів: одного лише UID 0 недостатньо. Сучасний Linux-дистрибутив або контейнер може вимагати створення користувачів `nobody`, `daemon`, `www-data` всередині контейнера. Якщо ми маємо лише `0 1000 1`, будь-яка спроба `setuid(33)` (`www-data`) завершиться помилкою (бо UID 33 не відображено).

### Додаткові ідентифікатори (subuid / subgid)

Щоб звичайний користувач міг створити повноцінний контейнер із тисячами доступних UID (для різних сервісів всередині), система використовує механізм підпорядкованих ідентифікаторів (subordinate IDs).

Адміністратор системи виділяє кожному користувачеві блок "віртуальних" ідентифікаторів, записуючи їх у файли `/etc/subuid` та `/etc/subgid`.
Запис `bob:100000:65536` у `/etc/subuid` означає, що користувач `bob` (крім свого основного UID) має право розпоряджатися ідентифікаторами від 100000 до 165535. 

Оскільки ядро не дозволяє звичайному процесу писати такі широкі мапінги, застосовуються спеціальні `setuid`-утиліти (хелпери): `newuidmap` та `newgidmap`. Процес створює user namespace, призупиняється і просить ці утиліти записати потрібний мапінг від імені справжнього `root`. Утиліти перевіряють `/etc/subuid`, переконуються, що користувач має право на запитувані ідентифікатори, і записують масивний мапінг у `/proc/PID/uid_map`.

## Проблема `setgroups` і negative permissions

Безпека user namespaces мала одну серйозну вразливість, пов'язану з групами. У UNIX існують так звані негативні права (negative permissions). Наприклад, тека може мати права `rwx---r-x`, а її власник-група — `secret`. Це означає, що користувачі з групи `secret` **не мають доступу** (бо права групи нульові), тоді як решта (other) — мають.

Якщо непривілейований процес створює user namespace і стає там `root` (отримуючи `CAP_SETGID` всередині), він міг би викликати системний виклик `setgroups(2)` з порожнім масивом, щоб "скинути" з себе всі додаткові групи, включно з `secret`. Після цього, з погляду хоста, процес більше не належить до забороненої групи і отримує доступ (через `other`).

Щоб закрити цю діру, ядро вимагає обов'язкової дії перед тим, як дозволить непривілейованому процесу налаштувати `gid_map`. У `/proc/PID/setgroups` треба записати рядок `deny`. Це **назавжди забороняє** виклик `setgroups(2)` у цьому просторі імен та всіх його нащадках. Тільки після запису `deny` ядро приймає запис у `gid_map` від непривілейованого користувача.

## Практичний приклад

Нижче показано базове створення user namespace. На одній вкладці ми використовуємо `unshare` (bash-утиліту), на іншій — C-код через системний виклик `clone(2)`.

### Bash (unshare)
```bash
# Створюємо новий user namespace і відображаємо себе на root (-r)
$ unshare -U -r /bin/bash

# Ми є root всередині простору
root@host:# id
uid=0(root) gid=0(root) groups=0(root),65534(nobody)

# Наш мапінг показує 0 -> 1000
root@host:# cat /proc/self/uid_map
         0       1000          1

# Проте на хості ми лишаємося звичайним користувачем
root@host:# cat /etc/shadow
cat: /etc/shadow: Permission denied
```

### C (clone)
```c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>
#include <fcntl.h>

// Функція, що виконується в новому просторі
int child_func(void *arg) {
    // Внутрішній процес спершу має UID 65534, доки батько не запише uid_map.
    // Щоб дочекатися мапінгу, на практиці використовують pipe для синхронізації.
    // Тут ми просто спимо для прикладу.
    sleep(1);
    
    printf("[Child] Ефективний UID: %d\n", geteuid()); // Виведе 0
    return 0;
}

int main() {
    // Виділяємо стек для нащадка
    char *stack = malloc(1024 * 1024);
    
    // Створюємо процес з новим user namespace
    pid_t pid = clone(child_func, stack + 1024 * 1024, CLONE_NEWUSER | SIGCHLD, NULL);
    
    // Батьківський процес (UID 1000) налаштовує uid_map для нащадка
    char path[256];
    sprintf(path, "/proc/%d/uid_map", pid);
    int fd = open(path, O_WRONLY);
    
    // Мапінг: внутрішній 0 -> зовнішній 1000, довжина 1
    dprintf(fd, "0 %d 1\n", getuid());
    close(fd);
    
    waitpid(pid, NULL, 0);
    return 0;
}
```
