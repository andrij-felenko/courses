# 📜 Історія появи User Namespaces у ядрі Linux

Простори імен користувачів (User Namespaces) пройшли найдовший і найдраматичніший шлях розробки серед усіх типів namespaces у Linux. Ідея надати непривілейованому користувачеві можливість поводитися як `root` усередині ізольованого середовища вимагала повної ревізії моделі безпеки ядра, яка формувалася протягом 40 років розвитку UNIX-подібних систем.

## Перші спроби та проблема привілеїв (2006–2008)

На початку 2000-х років концепція контейнеризації у світі UNIX виглядала дуже різнорідною. У FreeBSD існувала підсистема FreeBSD Jails (створена Поулом-Хеннінгом Кампом 1999 року), у Solaris — Solaris Zones (2004 рік). Обидва підходи надавали високий рівень ізоляції, проте мали фундаментальне обмеження: суперкористувач усередині ізольованого середовища залишався пов'язаним із глобальним суперкористувачем системи. У Linux існували сторонні патчі ядра, такі як OpenVZ, Linux-VServer та `chroot`-пісочниці, проте жоден із них не був частиною офіційного ядра.

Простір монтування (MNT) з'явився в Linux ще 2002 року, у 2.4.19. А коли 2006-го Ерік Бідерман (Eric Biederman), Серж Халлін (Serge Hallyn, IBM) та спільнота розробників ядра взялися за підсистему `namespaces` системно, решта простих просторів лягла відносно швидко: UTS та IPC — у 2.6.19, PID — у 2.6.24, мережевий — на межі 2.6.24–2.6.29.

Однак усі ці простори мали фундаментальне обмеження безпеки: створити їх міг лише процес із системною можливістю `CAP_SYS_ADMIN` у глобальному контексті ядра. Це означало, що будь-який демон контейнеризації мусив запускатися від імені справжнього `root` хоста. Якщо додаток усередині контейнера знаходив вразливість і здійснював втечу з контейнера (container breakout), зловмисник миттєво отримував повний контроль над усією фізичною машиною, дисками та мережевою інфраструктурою.

Ерік Бідерман (Eric W. Biederman) сформулював концепцію User Namespaces як необхідний фундамент справді безпечної контейнеризації: розділити поняття "адміністратор конкретного середовища" та "адміністратор фізичної системи". За його задумом, користувач із UID 1000 на хості мав отримати UID 0 (root) всередині свого простору, але ядро мусило ізолювати його права лише тими ресурсами, які належать цьому простору.

## Головна перешкода: Перевірка привілеїв по всьому коду ядра

Головна складність полягала не у створенні самої структури `struct user_namespace`, а у фундаментальній зміні способу перевірки привілеїв у коді ядра Linux. 

Історично ядро перевіряло привілеї двох типів:
1. Перевірка за числовим UID: `if (current_euid() == 0)` або `if (uid == inode->i_uid)`.
2. Перевірка системних привілеїв Capabilities: `if (capable(CAP_SYS_ADMIN))` або `if (capable(CAP_NET_ADMIN))`.

Виклик `capable(CAP_SYS_ADMIN)` перевіряв, чи має процес глобальні привілеї на всю систему. Якби процес у новому user namespace отримав `CAP_SYS_ADMIN`, застарілий виклик `capable()` дав би йому змогу змінювати хостові налаштування, підключати модулі ядра чи монтувати фізичні диски.

Розробникам довелося переписати тисячі точок перевірки привілеїв по всьому ядру, замінивши `capable(cap)` на `ns_capable(ns, cap)`. Виклик `ns_capable()` перевіряє, чи має процес привілеї `cap` *саме у вказаному простірі імен `ns`*, або в його батьківських просторах.

Ця робота вимагала колосального аудиту кожної файлової системи, мережевого протоколу, драйвера пристроїв та системного виклику. Будь-який пропущений виклик `capable()` замість `ns_capable()` створював вектор локального підвищення привілеїв (LPE).

## Розбіжності у спільноті та реліз Linux 3.8 (2013)

Суперечки щодо безпеки User Namespaces тривали в поштовій розсилці Linux Kernel Mailing List (LKML) понад 5 років. Частина провідних розробників ядра вважала надання непривілейованим користувачам права створювати простори імен та монтувати файлові системи надто ризикованим кроком. Справа в тому, що код багатьох файлових систем (ext4, xfs, nfs, iso9660) і мережевих стеків (Netfilter, DCCP, SCTP) ніколи не розроблявся з розрахунком на те, що його викликатиме необмежений непривілейований користувач із довільно сформованими структурованими даними.

Фахівці з безпеки ядра висловлювали побоювання, що непривілейований `unshare(CLONE_NEWUSER)` зробить доступними для атак сотні внутрішніх інтерфейсів ядра, які раніше були приховані за завісою root-привілеїв.

У Linux 3.5 (літо 2012 року) з'явилися початкові файли відображення `/proc/PID/uid_map` та `/proc/PID/gid_map`. І лише в Linux 3.8 (лютий 2013 року) Ерік Бідерман завершив фундаментальну роботу: User Namespaces стали повністю функціональними та дозволеними для непривілейованих користувачів без прапорця `CAP_SYS_ADMIN` на хості.

Це був історичний переломний момент: вперше у UNIX-подібних системах звичайний користувач зміг викликати `unshare(CLONE_NEWUSER)` і отримати повні привілеї `root` для ізольованого середовища.

## Сплеск вразливостей та реакція дистрибутивів

Відразу після виходу Linux 3.8 відкриття `CLONE_NEWUSER` для всіх користувачів очікувано спричинило сплеск виявлення вразливостей у ядрі. Непривілейовані користувачі отримали доступ до створення нових мережевих просторів (`CLONE_NEWNET`) з усім стеком `iptables`/`nftables`, а також до тих файлових систем, монтувати які всередині user namespace дозволяло ядро: у мейнлайні це насамперед FUSE, тоді як непривілейований `overlayfs` довго лишався патчем Ubuntu.

З'явилася серія знаменитих експлойтів, які використовували userns як «відкривачку дверей» для доступу до інших вразливих підсистем ядра:
- Вразливості у підсистемі raw-сокетів `packet_sockets` (`CVE-2016-8655`);
- Помилки логіки в непривілейованому `overlayfs` — `CVE-2015-1328` стосувалася саме Ubuntu-патча, який таке монтування дозволяв;
- Проблеми перевірки привілеїв у підсистемі cgroups v1 (`CVE-2022-0492`).

У зв'язку з цим Debian, SUSE та Arch Linux протягом багатьох років поставляли власні патчі ядра із вимикачем `sysctl kernel.unprivileged_userns_clone=0`, а Red Hat Enterprise Linux тримав нульовим штатний ліміт `user.max_user_namespaces`. І там, і там створювати user namespaces могли тільки процеси з `CAP_SYS_ADMIN` на хості або спеціально авторизовані сервіси.

## Революція Rootless-контейнерів та сучасний стан

Попри дитячі хвороби безпеки, User Namespaces стали технологічною основою для революції **Rootless-контейнеризації**. 

У 2014–2018 роках виникли такі проєкти, як LXC 1.0 (який першим застосував unprivileged userns для повноцінних контейнерів операційної системи), Singularity/Apptainer (у високопродуктивних обчисленнях HPC, де користувачам категорично заборонено мати root-права на обчислювальних вузлах), RootlessKit та unprivileged Docker.

Розвиток досяг апогею зі створенням Podman (від Red Hat) — інструменту контейнеризації, який за умовчанням працює повністю у просторі користувача без фонового демона з root-правами. А вихід системного виклику `mount_setattr(MOUNT_ATTR_IDMAP)` у Linux 5.12 остаточно вирішив останню проблему — сумісність томів файлових систем без необхідності виконання коштовної процедури `chown`.

Сьогодні User Namespaces є основою безпеки не лише контейнерів, а й пісочниць веб-браузерів (Google Chrome renderer sandbox, Mozilla Firefox sandbox), інструментів ізоляції додатків (Flatpak, Bubblewrap) та системних служб `systemd` (опція `PrivateUsers=yes`).
