# Підсистема ключів ядра (Kernel Keyring Subsystem)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У сучасних операційних системах сімейства Linux безпечне керування ключами шифрування, маркерами автентифікації та іншими конфіденційними даними (секретами) є надзвичайно важливим завданням. Раніше додатки часто зберігали ключі безпосередньо у своєму адресному просторі (в пам’яті процесу користувача). Однак такий підхід мав суттєві недоліки: пам’ять процесу може бути скинута на диск у файл ядра (core dump), прочитана через механізм `ptrace`, або вивантажена у файл підкачки (swap), що створює ризики витоку критичних даних.

Для вирішення цих проблем у ядрі Linux було створено **Kernel Key Retention Service** (службу зберігання ключів у ядрі) — механізм, який дозволяє процесам простору користувача безпечно зберігати ключі безпосередньо в оперативній пам’яті ядра та керувати ними, уникаючи їх розміщення в адресному просторі користувацьких додатків.

## 1. Архітектура та основні концепції

Підсистема ключів базується на кількох базових концепціях: **ключ** (key) та **в'язка ключів** (keyring).

### 1.1. Що таке ключ?

**Ключ** — це криптографічний або автентифікаційний секрет (токен), що управляється ядром. Кожен ключ складається з кількох обов’язкових компонентів:
- **Серійний номер (Serial Number):** Унікальний 32-бітний ідентифікатор ключа в системі. Завжди додатний.
- **Тип ключа (Key Type):** Визначає структуру даних ключа та спосіб управління ним.
- **Опис (Description / Name):** Рядок, що ідентифікує ключ серед інших ключів того ж типу. Використовується для пошуку.
- **Власник (UID та GID):** Ідентифікатори користувача та групи, що володіють ключем.
- **Права доступу (Permissions):** Маска, що визначає, хто і що може робити з ключем (view, read, write, search, link, setattr).
- **Корисне навантаження (Payload):** Безпосередньо самі дані ключа (наприклад, симетричний ключ шифрування AES). Для деяких типів ключів payload може зберігатися в зашифрованому вигляді або апаратно.
- **Термін дії (Expiration Time):** Час, після якого ключ стає недійсним і згодом видаляється складальником сміття (garbage collector) ядра.

### 1.2. Що таке Keyring (в'язка ключів)?

**Keyring** — це особливий тип ключа, корисним навантаженням якого є список посилань на інші ключі (або інші в'язки ключів). Це створює ієрархічну структуру, подібну до файлової системи, але для секретів.
Існує декілька стандартних прив'язок (keyrings), пов'язаних з контекстом виконання:
1. **Thread Keyring (`@t`):** Специфічний для потоку (thread). Якщо не встановлено, пошук переходить далі.
2. **Process Keyring (`@p`):** Специфічний для процесу. Розділяється всіма потоками процесу.
3. **Session Keyring (`@s`):** Прив’язаний до сесії користувача. Дозволяє процесам у межах однієї сесії входу використовувати спільні ключі (наприклад, для доступу до зашифрованої домашньої директорії).
4. **User Keyring (`@u`):** Специфічний для UID. Усі процеси користувача з даним UID можуть мати сюди доступ.
5. **User Session Keyring (`@us`):** Глобальна сесійна в'язка для користувача.

## 2. Типи ключів у Linux

Ядро Linux підтримує різноманітні типи ключів, що мають власну поведінку та обмеження доступу:

### 2.1. `user`
Це найпростіший тип ключа. Корисне навантаження довільне і може читатися і записуватися з простору користувача. Оскільки `user`-ключ можна зчитати з user-space, його небезпечно використовувати для дуже критичних секретів, хоча це підходить для кешування паролів чи токенів.

### 2.2. `logon`
Дуже схожий на `user`, але має фундаментальну відмінність: **його неможливо зчитати з простору користувача**. Він може бути створений і оновлений з простору користувача, але використовувати його може лише ядро (наприклад, для монтування зашифрованого блочного пристрою `dm-crypt` або файлової системи `fscrypt`). Це робить `logon`-ключі дуже безпечними для передачі ключів від утиліт (наприклад, `cryptsetup`) в ядро.

### 2.3. `encrypted`
Цей тип ключа дозволяє зберігати ключ зашифрованим (encrypted) іншим ключем (master key), яким часто виступає ключ типу `trusted` (TPM) або `user`. У пам'яті ядра ключ `encrypted` розшифровується тільки в момент його використання підсистемою ядра, що додає рівень безпеки. Ключ не покидає ядро у відкритому вигляді.

### 2.4. `trusted`
Ключі типу `trusted` генеруються та захищаються апаратним модулем (TPM - Trusted Platform Module) або іншим TrustZone (наприклад, TEE). Ядро лише передає запити до TPM. Відкритий ключ (plaintext) доступний ядру (а не процесам користувача), але він захищений апаратним коренем довіри. Зазвичай використовується як master key для ключів типу `encrypted`.

### 2.5. `big_key`
Якщо корисне навантаження ключа перевищує ліміт (зазвичай близько 32 КБ), можна використовувати `big_key`. Він дозволяє зберігати до 1 МБ даних. Дані можуть бути збережені у `tmpfs` (у файлі, доступному тільки ядру) та автоматично шифруються ядром випадковим сесійним ключем.

### 2.6. `asymmetric`
Цей тип ключа представляє асиметричну пару ключів (наприклад, RSA або ECDSA) або публічний сертифікат X.509. Використовується ядром для верифікації модулів ядра, kexec-образів, підписів IMA/EVM, а також Btrfs.

## 3. Системні виклики (Syscalls)

Робота з підсистемою ключів з рівня C-коду (glibc або прямі syscalls) здійснюється через три основні системні виклики: `add_key`, `request_key`, та `keyctl`.

### 3.1. `add_key()`
```c
key_serial_t add_key(const char *type, const char *description,
                     const void *payload, size_t plen,
                     key_serial_t keyring);
```
Додає новий ключ у визначену в'язку `keyring`. Якщо ключ з таким типом і описом вже існує у цій в'язці, він оновлюється (якщо дозволяють права доступу).
Наприклад, завантажити `logon` ключ:
```c
add_key("logon", "ext4:mykey", key_data, key_len, KEY_SPEC_SESSION_KEYRING);
```

### 3.2. `request_key()`
```c
key_serial_t request_key(const char *type, const char *description,
                         const char *callout_info,
                         key_serial_t dest_keyring);
```
Цей виклик є серцем динамічного керування ключами. Він дозволяє процесу попросити ядро знайти ключ.
1. Ядро шукає ключ у thread, process, session, та user keyrings.
2. Якщо ключ знайдено і права дозволяють — повертається його серійний номер.
3. Якщо ключ **не знайдено**, ядро може ініціювати процес "виклик помічника" (upcall). Використовуючи `callout_info`, ядро звертається до демона у просторі користувача (наприклад, `request-key`), який спробує згенерувати або дістати цей ключ (наприклад, запитати пароль у користувача через GUI, або скачати токен з мережі) та завантажити його назад в ядро.

### 3.3. `keyctl()`
```c
long keyctl(int operation, ...);
```
Це універсальний мультиплексорний системний виклик для управління ключами. Через параметр `operation` він може виконувати десятки дій:
- `KEYCTL_REVOKE`: Анулювати ключ.
- `KEYCTL_CHOWN` / `KEYCTL_SETPERM`: Змінити власника або права доступу.
- `KEYCTL_CLEAR`: Очистити в'язку ключів (видалити всі посилання).
- `KEYCTL_LINK` / `KEYCTL_UNLINK`: Додати або видалити посилання на ключ у в'язці.
- `KEYCTL_READ`: Зчитати корисне навантаження ключа (для ключів `user`).

## 4. Утиліта `keyctl` (Простір користувача)

Для роботи з ключами з командного рядка (bash/shell) використовується утиліта `keyctl`, яка є обгорткою над однойменним системним викликом.

**Перегляд сесійної в'язки:**
```bash
$ keyctl show
Session Keyring
 1083423719 --alswrv    1000  1000  keyring: _ses
   98231234 --alswrv    1000  1000   \_ keyring: _uid.1000
```

**Додавання ключа:**
```bash
$ keyctl add user my_secret_key "This is a very secret payload" @s
543987123
```

**Зчитування ключа:**
```bash
$ keyctl print 543987123
This is a very secret payload
```

**Пошук ключа за назвою:**
```bash
$ keyctl search @s user my_secret_key
543987123
```

## 5. Безпека, інтеграція та файлові системи `/proc/keys`

### 5.1. `/proc/keys`
Ядро експортує інформацію про всі ключі в системі, до яких поточний процес має право `view`, через файл `/proc/keys` (за умови, що ядро зібрано з `CONFIG_KEYS_DEBUG_PROC_KEYS`).
```text
030a51c7 I--Q---    1000    1000 keyring   _uid.1000: empty
18df2410 I--Q---    1000    1000 user      my_secret_key: 29
3ef423a1 I--Q---       0       0 logon     ext4:key_vol1: 32
```
Варто зазначити, що у `/proc/keys` ніколи не відображається саме корисне навантаження ключа. Показується лише серійний номер, прапорці, UID/GID, тип ключа, опис і розмір даних.

### 5.2 Права доступу до ключів (Permissions)
Кожен ключ має права, розбиті на 4 категорії: Possessor (володілець - той, хто має посилання на ключ у своїх keyrings), User, Group, та Other.
Доступні дії:
- **View (v):** Дозволяє побачити ключ у списках і зчитати його метадані (тип, опис).
- **Read (r):** Дозволяє зчитати корисне навантаження.
- **Write (w):** Дозволяє змінити (оновити) корисне навантаження.
- **Search (s):** Дозволяє знайти ключ за описом (і для keyrings - шукати всередині них).
- **Link (l):** Дозволяє створити посилання на цей ключ у своїй в'язці.
- **Setattr (a):** Дозволяє змінити власника, групу, права доступу або анулювати ключ.

## 6. Використання на практиці: Випадки застосування

**eCryptfs та fscrypt (ext4/f2fs/ubifs)**
Вбудоване шифрування на рівні файлової системи широко використовує підсистему ключів. Наприклад, утиліта `fscrypt` зчитує пароль користувача, виводить з нього криптографічний ключ (через PBKDF2/Argon2), а потім завантажує його в ядро як `logon` ключ. Ядро використовує цей ключ для розшифрування вмісту файлів і назв каталогів "на льоту".

**dm-crypt (LUKS)**
Історично `dm-crypt` тримав Master Key у власних структурах ядра. Проте в сучасних реалізаціях можна налаштувати `dm-crypt` (через cryptsetup) зберігати Volume Key у Kernel Keyring. Це робиться для захисту ключа від читання через потенційні вразливості та для інтеграції з TPM (ключ до LUKS може бути `trusted` ключем, прив'язаним до стану TPM - PCRs).

**NFSv4 та AFS**
Мережеві файлові системи використовують ключі типу `rxrpc` або `dns_resolver` для кешування DNS-запитів ядра та зберігання Kerberos квитків автентифікації безпосередньо в сесійній в'язці користувача.

## 7. Підсумки
Linux Kernel Key Retention Service є фундаментальним механізмом безпеки, що ізолює криптографічні секрети від користувацьких додатків, мінімізуючи ризики компрометації. Завдяки ієрархічним в'язкам (keyrings), розмаїттю типів (особливо `logon` і `trusted`), та гнучкому API (`keyctl`), він став стандартом для шифрування дисків, мережевої автентифікації та інтеграції з апаратними модулями безпеки.
