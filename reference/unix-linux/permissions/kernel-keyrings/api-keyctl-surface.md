# 📋 Інтерфейс служби ключів: виклики, команди `keyctl`, типи, `/proc/keys`, біти прав

Це довідка про точну поверхню підсистеми ключів: підписи трьох системних викликів, повний перелік операцій `keyctl` з їхніми номерами, синтаксис опису й вмісту для кожного типу ключа, розбір рядка `/proc/keys` поле за полем і значення всіх бітів у масці прав. Потрібна вона тоді, коли треба не зрозуміти задум, а написати виклик, який працює з першого разу, і прочитати те, що система показує у відповідь.

Числа й підписи звірено з деревом джерел Linux 6.12 (`include/uapi/linux/keyctl.h`, `security/keys/proc.c`) і зі сторінками довідника `add_key(2)`, `request_key(2)`, `keyctl(2)`, `keyctl(1)`, `keyrings(7)`.

## Три виклики й де взяти обгортки

```c
key_serial_t add_key(const char *type, const char *description,
                     const void *payload, size_t plen,
                     key_serial_t keyring);

key_serial_t request_key(const char *type, const char *description,
                         const char *callout_info,
                         key_serial_t dest_keyring);

long keyctl(int operation, ...);
```

`key_serial_t` — це знакове 32-бітне число. Успіх `add_key` і `request_key` — порядковий номер ключа, невдача — `-1` з виставленим `errno`. У `request_key` аргумент `callout_info` вирішує все: `NULL` означає «просто пошукай», непорожній рядок — «а якщо не знайдеш, запусти `/sbin/request-key` і передай йому оцей рядок».

[Бібліотека C](topic:unix-linux/libc-as-gateway) обгорток для цих трьох викликів **не має** — сторінки довідника прямо про це попереджають. Обгортки дає окремий пакет `keyutils` — заголовок `<keyutils.h>`, лінкування `-lkeyutils`. Без нього лишається `syscall(__NR_add_key, …)` вручну. Замість голого `keyctl(op, …)` пакет пропонує типізовані функції на кожну операцію: `keyctl_search()`, `keyctl_read()`, `keyctl_setperm()` і решта.

## Куди класти: спеціальні номери кілець

Там, де очікується номер кільця, приймають ще й від'ємні константи — вони означають не конкретне кільце, а «те, яке зараз відповідає цій області дії».

| Константа | Число | `keyctl(1)` | Що це |
|---|---|---|---|
| `KEY_SPEC_THREAD_KEYRING` | −1 | `@t` | кільце окремої нитки |
| `KEY_SPEC_PROCESS_KEYRING` | −2 | `@p` | спільне для всіх ниток процесу |
| `KEY_SPEC_SESSION_KEYRING` | −3 | `@s` | сеансове; переживає `fork` і `exec` |
| `KEY_SPEC_USER_KEYRING` | −4 | `@u` | спільне для всіх процесів UID |
| `KEY_SPEC_USER_SESSION_KEYRING` | −5 | `@us` | типове сеансове кільце UID |
| `KEY_SPEC_GROUP_KEYRING` | −6 | `@g` | заглушка; у Linux не реалізовано |
| `KEY_SPEC_REQKEY_AUTH_KEY` | −7 | `@a` | ключ-повноваження, виданий помічникові |
| `KEY_SPEC_REQUESTOR_KEYRING` | −8 | — | кільце того, хто просив (лише в помічнику) |

Використання константи `−1`…`−3` має побічну дію: якщо потрібного кільця в процесу ще немає, ядро його створює на місці.

## Команди `keyctl`

Перший аргумент `keyctl(2)` — номер операції. Стовпчик «командою» — те саме через утиліту `keyctl(1)`, яка є в кожному дистрибутиві.

| № | Операція | Командою | Що робить |
|---|---|---|---|
| 0 | `KEYCTL_GET_KEYRING_ID` | `id` | перетворює спеціальну константу на справжній номер |
| 1 | `KEYCTL_JOIN_SESSION_KEYRING` | `session`, `new_session` | увійти в іменований сеанс або створити порожній |
| 2 | `KEYCTL_UPDATE` | `update`, `pupdate` | замінити вміст наявного ключа |
| 3 | `KEYCTL_REVOKE` | `revoke` | відкликати: лишається надгробок, звертання дають `EKEYREVOKED` |
| 4 | `KEYCTL_CHOWN` | `chown`, `chgrp` | змінити UID/GID власника |
| 5 | `KEYCTL_SETPERM` | `setperm` | записати нову маску прав |
| 6 | `KEYCTL_DESCRIBE` | `describe`, `rdescribe` | видати рядок «тип;uid;gid;маска;опис» |
| 7 | `KEYCTL_CLEAR` | `clear` | зняти з кільця всі посилання |
| 8 | `KEYCTL_LINK` | `link` | почепити ключ на кільце |
| 9 | `KEYCTL_UNLINK` | `unlink` | зняти одне посилання |
| 10 | `KEYCTL_SEARCH` | `search` | шукати за «тип + опис» углиб по вкладених кільцях |
| 11 | `KEYCTL_READ` | `read`, `print`, `pipe`, `list`, `rlist` | прочитати вміст (для кільця — перелік номерів) |
| 12 | `KEYCTL_INSTANTIATE` | `instantiate`, `pinstantiate` | наповнити ключ, який чекає на матеріал |
| 13 | `KEYCTL_NEGATE` | `negate` | наповнити від'ємно: подальші звертання дістануть `ENOKEY` |
| 14 | `KEYCTL_SET_REQKEY_KEYRING` | — | куди типово класти результат `request_key` |
| 15 | `KEYCTL_SET_TIMEOUT` | `timeout` | строк придатності в секундах; `0` знімає |
| 16 | `KEYCTL_ASSUME_AUTHORITY` | — | помічник заявляє повноваження на один ключ |
| 17 | `KEYCTL_GET_SECURITY` | `security` | мітка [LSM](topic:unix-linux/lsm-framework) ключа |
| 18 | `KEYCTL_SESSION_TO_PARENT` | — | нав'язати батьківському процесу свій сеанс |
| 19 | `KEYCTL_REJECT` | `reject` | від'ємне наповнення з конкретним `errno` |
| 20 | `KEYCTL_INSTANTIATE_IOV` | — | те саме, що 12, але з розсипаних буферів |
| 21 | `KEYCTL_INVALIDATE` | `invalidate` | знищити негайно, знявши з усіх кілець |
| 22 | `KEYCTL_GET_PERSISTENT` | `get_persistent` | дістати стале кільце UID |
| 23 | `KEYCTL_DH_COMPUTE` | `dh_compute` | обчислення Діффі — Гелмана на вмісті ключів |
| 24–28 | `KEYCTL_PKEY_*` | `pkey_query`, `pkey_sign`, `pkey_verify`, … | операції асиметричним ключем (з 4.20) |
| 29 | `KEYCTL_RESTRICT_KEYRING` | `restrict_keyring` | накласти на кільце правило прийому (з 4.12) |
| 30 | `KEYCTL_MOVE` | `move` | перенести посилання між кільцями атомарно (з 5.0) |
| 31 | `KEYCTL_CAPABILITIES` | `supports` | що вміє ця збірка ядра (з 5.0) |
| 32 | `KEYCTL_WATCH_KEY` | `watch` | сповіщення про зміни через `watch_queue` (з 5.8) |

Утиліта додає кілька команд без власної операції — вони складені з наявних: `add`/`padd` (це `add_key`), `newring`, `request`/`request2`, `show` (обхід дерева читанням), `purge`, `reap`. Суфікс `p` у назві (`padd`, `pupdate`, `pinstantiate`) означає «вміст брати зі стандартного входу», а не з аргументу — саме так секрет не потрапляє в командний рядок, видний у `ps`.

## Опис і вміст за типами

Тип вирішує, як розібрати вміст, який опис вважати правильним і чи можна вміст прочитати назад.

| Тип | Вимога до опису | Вміст під час створення | `read` |
|---|---|---|---|
| `user` | будь-який рядок | довільні байти, ≤ 32 767 | так |
| `logon` | обов'язково `служба:ім'я` | довільні байти, ≤ 32 767 | **ніколи** |
| `big_key` | будь-який рядок | довільні байти, ≤ 1 МіБ | так |
| `keyring` | будь-який, але **не з крапки** | `NULL`, довжина `0` | перелік номерів |
| `asymmetric` | можна порожній | DER-потік сертифіката X.509 | не секрет; операції `pkey_*` |
| `trusted` | будь-який рядок | командний рядок (нижче) | лише шифроблоб |
| `encrypted` | будь-який рядок | командний рядок (нижче) | лише шифроблоб |

Порожній опис для `asymmetric` — не помилка, а прийом: розбирач сертифіката сам складе опис із його вмісту, і ключ з'явиться під іменем на кшталт `modsign.0: DSA 5acc2142 []`. Тип ключа, що починається з крапки, зарезервований для ядра — спроба дає `EPERM`; те саме для кільця з описом, що починається з крапки.

Вміст `trusted` і `encrypted` — не байти секрету, а **команда**, яку розбирає сам тип:

```
trusted:    new <довжина> [keyhandle=… hash=… pcrinfo=… policydigest=… migratable=0|1]
            load <шістнадцятковий-блоб> [pcrlock=<номер PCR>]
            update [ті самі опції]

encrypted:  new [default|ecryptfs|enc32] <тип>:<ім'я-господаря> <довжина> [<матеріал>]
            load <шістнадцятковий-блоб>
            update <тип>:<ім'я-господаря>
```

Господарем для `encrypted` може бути ключ типу `trusted` або `user` — і більше ніякий. Джерело довіри для `trusted` обирають параметром модуля `trusted.source=`: `tpm` ([TPM](topic:programming/tpm-root-of-trust)), `tee` (OP-TEE на Arm TrustZone), `caam` (блок у SoC від NXP), `dcp` (прискорювач в i.MX).

Правило прийому для `KEYCTL_RESTRICT_KEYRING` задають парою «тип; обмеження»: `asymmetric; builtin_trusted`, `asymmetric; builtin_and_secondary_trusted` або `asymmetric; key_or_keyring:<ключ>[:chain]`. Порожній тип означає «не приймати нічого взагалі».

## Рядок `/proc/keys`

Дев'ять полів, розділених пробілами; останнє — опис із коротким підсумком після двокрапки.

```
  3a1c0d21 I--Q---   2 perm 3f030000  1000  1000 keyring   _ses: 3
  │        │       │ │    │        │     │     │        └── тип
  │        │       │ │    │        │     └─────┴─── UID і GID власника
  │        │       │ │    │        └── маска прав, чотири байти
  │        │       │ │    └── строк: perm · expd · 45s · 12m · 5h · 3d · 2w
  │        │       │ └── лічильник посилань на ключ усередині ядра
  │        │       └── прапорці стану, рівно сім позицій
  └── порядковий номер, шістнадцятково
```

Прапорці завжди стоять у порядку `I R D Q U N i`; на місці невиставленого — дефіс.

| Знак | Значення |
|---|---|
| `I` | ключ наповнено (`-` — ще чекає на матеріал) |
| `R` | відкликано |
| `D` | мертвий: тип, що ним завідував, вивантажено |
| `Q` | зараховано до квоти власника |
| `U` | триває виклик назовні, помічник іще працює |
| `N` | наповнено від'ємно: у ключі лежить помилка |
| `i` | знищено через `invalidate` |

Рядок бачить лише той, кому дозволяє право `view` — тримачеві або за байтом свого UID чи GID. Тому та сама команда від `root` і від звичайного користувача показує різні файли.

## Квоти й ручки

```
$ cat /proc/key-users
    0:    12 11/11 4/1000000 87/25000000
 1000:    31 30/30 12/200 296/20000
   uid  usage nkeys/nikeys qnkeys/maxkeys qnbytes/maxbytes
```

`nkeys` — усі ключі UID, `nikeys` — з них наповнені; далі йдуть дві пари «спожито / стеля». Стелі й таймери крутить [sysctl](topic:unix-linux/sysctl-tunables):

| Файл у `/proc/sys/kernel/keys/` | Типово |
|---|---|
| `maxkeys` · `maxbytes` | 200 · 20 000 |
| `root_maxkeys` · `root_maxbytes` | 1 000 000 · 25 000 000 |
| `gc_delay` | 300 с — затримка перед прибиранням |
| `persistent_keyring_expiry` | 259 200 с (три доби) |

## Маска прав

Чотири байти, зліва направо: тримач, користувач, група, решта. Усередині кожного — ті самі шість бітів.

```
0x 3f    01    00    00
   тримач користувач група решта

0x01 view     бачити атрибути
0x02 read     читати вміст (для кільця — перелік)
0x04 write    міняти вміст, чіпляти на кільце
0x08 search   бути знайденим пошуком крізь це кільце
0x10 link     чіпляти цей ключ на інші кільця
0x20 setattr  міняти власника, маску, строк
```

**Умова: кільце має бути видиме й придатне для пошуку всім процесам того самого користувача, а міняти його дозволено тільки тримачеві.**

```
тримач     = view|read|write|search|link|setattr = 0x3f
користувач = view|search = 0x01|0x08             = 0x09
група      = 0x00
решта      = 0x00

маска = 0x3f·2²⁴ + 0x09·2¹⁶ = 0x3f090000
```

Це вже не [трійка «власник · група · решта»](topic:unix-linux/permission-bits): перший байт відповідає не на питання «хто ти», а на «чи дотягуєшся». Маска не може дати того, чого не дозволяє тип: перевірку типу проходять раніше за перевірку прав.

## Помилки

| `errno` | Коли |
|---|---|
| `ENOKEY` | пари «тип + опис» не знайдено; або такого номера немає; або ключ наповнено від'ємно через `negate` |
| `EKEYEXPIRED` | ключ або кільце протухли за строком |
| `EKEYREVOKED` | по ключу пройшлися `revoke` |
| `EKEYREJECTED` | від'ємне наповнення через `reject`; саме це видно як «Key was rejected by service» при відмові перевірити підпис [модуля](topic:unix-linux/kernel-modules) |
| `EACCES` | у масці бракує потрібного біта — і в байті тримача, і у вашому |
| `EPERM` | ім'я типу починається з крапки; або опис кільця починається з крапки |
| `EOPNOTSUPP` | тип не вміє цієї операції — це відповідь на `read` для `logon` |
| `EDQUOT` | вичерпано `maxkeys` або `maxbytes` цього UID |
| `EINVAL` | тип довший за 32 байти, опис за 4096; вміст не розібрався; `logon` без префікса `служба:` |
| `ENOTDIR` | там, де мало бути кільце, лежить звичайний ключ |
| `EDEADLK` | посилання замкнуло б цикл кілець |
| `ENFILE` | кільце переповнене |

## Мінімальний робочий виклик

```c
/* збірка: cc -o keydemo keydemo.c -lkeyutils */
#include <keyutils.h>
#include <errno.h>
#include <stdio.h>
#include <string.h>

int main(void)
{
    /* 1. покласти секрет так, щоб назад його не забрав ніхто */
    key_serial_t k = add_key("logon", "myfs:vol0", "s3cret", 6,
                             KEY_SPEC_SESSION_KEYRING);
    if (k == -1) { perror("add_key"); return 1; }
    printf("serial = %d (0x%08x)\n", k, k);

    /* 2. знайти той самий ключ пошуком — так само робить ядро */
    key_serial_t f = keyctl_search(KEY_SPEC_SESSION_KEYRING,
                                   "logon", "myfs:vol0", 0);
    printf("search -> %d\n", f);

    /* 3. тип не віддає вміст навіть тому, хто його поклав */
    char buf[64];
    if (keyctl_read(k, buf, sizeof buf) == -1)
        printf("read -> %s\n", strerror(errno));   /* Operation not supported */

    /* 4. усе тримачеві, собі — лише право бачити */
    keyctl_setperm(k, KEY_POS_ALL | KEY_USR_VIEW);

    /* 5. хай згине сам через п'ять хвилин */
    keyctl_set_timeout(k, 300);
    return 0;
}
```

Те саме з оболонки, рядок у рядок:

```sh
$ keyctl add logon myfs:vol0 s3cret @s
723106221
$ keyctl search @s logon myfs:vol0
723106221
$ keyctl print 723106221
keyctl_read_alloc: Operation not supported
$ keyctl setperm 723106221 0x3f010000
$ keyctl timeout 723106221 300
```

Перший рядок годиться для проби, але не для роботи: секрет тут стоїть аргументом і видний у `ps` кожному. У справжньому скрипті беруть `padd`, що читає вміст зі стандартного входу:

```sh
$ printf %s "$PASSPHRASE" | keyctl padd logon myfs:vol0 @s
```
