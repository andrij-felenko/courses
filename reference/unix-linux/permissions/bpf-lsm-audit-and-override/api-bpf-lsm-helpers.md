# 📋 Довідник BPF LSM: хелпери, макроси BPF_PROG та коди повернення

Вставка містить розширені довідкові відомості про макроси оголошення програм BPF LSM, стандартні коди повернення для перевизначення дій (override), хелпери роботи з локальним сховищем, шляхами VFS, атрибутами процесів та мережевими сокетами.

## Макроси оголошення та типи програм

Програми BPF LSM компілюються із зазначенням спеціального розділу `SEC("lsm/...")` або `SEC("lsm.s/...")` (для сліпабельних хуків). Сигнатура програми формується макросом `BPF_PROG`, який автоматично розпаковує контекст BTF відповідно до сигнатури конкретного хука ядра.

```c
#include <vmlinux.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

SEC("lsm/file_open")
int BPF_PROG(file_open_audit, struct file *file)
{
    // Початок логіки аудиту або перевірки права доступу
    return 0;
}
```

Макрос `BPF_PROG` трансформує аргументи ядерної функції у зручний для C-програми вигляд, забезпечуючи сувору перевірку типів під час завантаження верифікатором. Під капотом `BPF_PROG` розгортається у масив покажчиків контексту, де кожен аргумент прив'язується до відповідного поля BTF (BPF Type Format).

### Основні типи розділів секцій (`SEC`)

Кожен хук у підсистемі BPF LSM має свій режим виконання. Вибір правильної секції визначає перелік доступних хелперів та впливає на стабільність ядра.

| Секція | Режим виконання | Припустимі дії та хелпери |
| :--- | :--- | :--- |
| `SEC("lsm/<hook_name>")` | RCU Read Lock (атомарний контекст) | Швидкі перевірки, читання аргументів BTF, `bpf_inode_storage_get`, `bpf_task_storage_get`, `bpf_ringbuf_output`. За заборонено викликати функції, що можуть спати. |
| `SEC("lsm.s/<hook_name>")` | Sleepable Context (`BPF_F_SLEEPABLE`) | Дозволено читати пам'ять користувача (`bpf_copy_from_user`), виділяти пам'ять, копіювати довгі шляхи VFS. Працює лише для хуків, де ядро допускає сліпабельність. |

Режим `SEC("lsm.s/...")` слід застосовувати тільки там, де ядро явно дозволяє сліпабельність, оскільки викликання сліпабельних хелперів у непідтримуваному атомарному контексті призведе до відмови верифікатора BPF на етапі завантаження.

## Коди повернення BPF LSM (Override Semantics)

Значення, яке повертає функція `BPF_PROG`, інтерпретується фреймворком LSM як результат перевірки безпеки. Повернення від'ємного числа негайно призупиняє обхід ланцюжка LSM-модулів і трансформує цей код у помилку системного виклику.

```
                  +-------------------------------------------------+
                  | Значення повернутого int з BPF_PROG             |
                  +------------------------+------------------------+
                                           |
                    +----------------------+----------------------+
                    |                                             |
            int == 0 (Pass)                               int < 0 (Deny / Override)
                    |                                             |
   Дозволяє операцію. Передає                    Перериває ланцюжок LSM.
   керування наступним LSM у ланцюжку            Повертає код помилки у VFS / System Call.
   (AppArmor, SELinux, IMA).                     Операція скасовується.
```

### Деталізована семантика кодів помилок для підміни статусів

Кожен код від'ємного значення, повернений із BPF LSM, має чітку семантику в підсистемі VFS та POSIX-стандартах. Розробник BPF-програми повинен обирати код помилки, який точно відповідає характеру блокування, щоб не вводити у оману програми простору користувача.

- **`0` (`OK` / `SUCCESS`)**: Дозвіл на виконання операції. BPF LSM повідомляє фреймворку LSM, що даний модуль не має заперечень проти виконання системного виклику. Керування передається наступним модулям у ланцюжку stacking.
- **`-EACCES` (`-13`, `Permission denied`)**: Стандартний код відмови у доступі через невідповідність політиці безпеки. Використовується при блокуванні відкриття файлів, виконання бінарних кодів чи створення каталогів.
- **`-EPERM` (`-1`, `Operation not permitted`)**: Відмова у виконанні привілейованої операції. Використовується при спробі виконання дій, які вимагають специфічних Linux capabilities (наприклад, `CAP_SYS_ADMIN`, `CAP_NET_ADMIN` чи `CAP_SYS_PTRACE`).
- **`-ENOENT` (`-2`, `No such file or directory`)**: Симуляція відсутності файлу або каталогу. Дає змогу приховати існування чутливих об'єктів файлової системи від небажаних процесів. Процес отримує помилку, ніби об'єкта не існує в VFS.
- **`-EROFS` (`-30`, `Read-only file system`)**: Блокування операцій модифікації для імітації файлової системи у режимі "лише для читання". Застосовується при захисті конфігураційних каталогів від запису.
- **`-ENOMEM` (`-12`, `Out of memory`)**: Симуляція браку ресурсів пам'яті. Використовується вкрай рідко, переважно для тестування стійкості системних демонів до відмов.

## Хелпери локального сховища (BPF Local Storage Helpers)

Локальне сховище BPF дає змогу прив'язувати власні структури даних до об'єктів ядра без створення глобальних BPF-карт (Hash Maps) і без використання важких блокувань. Це забезпечує час доступу `O(1)` завдяки прямому доступу через LSM security blob.

Механізм функціонує за рахунок попередньо виділеного масиву зсувів у структурі `security_blob_sizes`. Коли BPF LSM завантажує карту локального сховища, ядро резервує слот у списку LSM-блобів відповідного об'єкта (`inode`, `task_struct`, `sock`).

### 1. `bpf_inode_storage_get`

Функція призначена для отримання або ініціалізації вказівника на локальну структуру даних, прив'язану до конкретного файлу чи каталогу (`struct inode`).

```c
void *bpf_inode_storage_get(
    struct bpf_map *map,
    struct inode *inode,
    void *value,
    u64 flags
);
```

- **`map`**: Вказівник на оголошену BPF-карту типу `BPF_MAP_TYPE_INODE_STORAGE`.
- **`inode`**: Вказівник на об'єкт `struct inode` ядра з контексту LSM-хука.
- **`value`**: Шаблон структури для первинної ініціалізації значення (використовується, якщо запис ще не існує в сховищі).
- **`flags`**: Прапор `BPF_LOCAL_STORAGE_GET_F_CREATE` наказує виділити пам'ять під новий запис, якщо його не було в сховищі.
- **Повертає**: Вказівник на виділену пам'ять у локальному сховищі inode або `NULL` у разі браку пам'яті чи відсутності об'єкта.

### 2. `bpf_task_storage_get`

Функція забезпечує збереження стану для процесів та потоків (`struct task_struct`). Вона дає змогу відстежувати лічильники дій процесу, зберігати тимчасові мітки або прапори обмежень.

```c
void *bpf_task_storage_get(
    struct bpf_map *map,
    struct task_struct *task,
    void *value,
    u64 flags
);
```

- **`map`**: Вказівник на BPF-карту типу `BPF_MAP_TYPE_TASK_STORAGE`.
- **`task`**: Вказівник на `struct task_struct` (отриманий, наприклад, через `bpf_get_current_task_btf()`).
- **`flags`**: Прапор `BPF_LOCAL_STORAGE_GET_F_CREATE` для автоматичного створення запису.

### 3. `bpf_sk_storage_get`

Забезпечує прив'язку даних до мережевих сокетів (`struct sock`).

```c
void *bpf_sk_storage_get(
    struct bpf_map *map,
    struct sock *sk,
    void *value,
    u64 flags
);
```

Використовується в хуках мережевої безпеки, таких як `security_socket_connect` або `security_socket_bind`, для збереження стану з'єднання, аналізу джерела запиту та підрахунку переданих байтів на рівні транспортного протоколу.

## Хелпери отримання контексту та шляхів VFS

### `bpf_d_path`

Отримує повний канонічний шлях до файлу у файловій системі VFS за вказівником на структуру `struct path`.

```c
long bpf_d_path(
    struct path *path,
    char *buf,
    u32 sz
);
```

- **`path`**: Вказівник на `file->f_path` або `dentry->d_name` зі структури виклику.
- **`buf`**: Буфер у BPF-стеку або пер-процесорній пам'яті для запису сформованого рядка.
- **`sz`**: Максимальний розмір буфера у байтах.
- **Обмеження та повернені значення**: Працює тільки для переліку хуків, відмічених у білому списку ядра для безпечного відновлення шляхів VFS. Повертає довжину записаного рядка або від'ємне значення при помилці (наприклад, `-ENAMETOOLONG`, якщо буфер виявився занадто малим).

### `bpf_get_current_pid_tgid` та `bpf_get_current_cred_uid`

Функції для швидкого зчитування ідентифікаторів поточного процесу та облікового запису користувача.

```c
u64 bpf_get_current_pid_tgid(void); // Верхні 32 біти: TGID (PID), нижні 32 біти: PID (TID)
u64 bpf_get_current_uid_gid(void);  // Нижчі 32 біти: UID користувача, верхні 32 біти: GID
```

Завдяки цим хелперам BPF LSM може швидко порівнювати мандати процесу з політикою безпеки без використання важких викликів VFS та без ризику блокування атомарного контексту.

## Хелпери аудиту та передачі подій (Ring Buffer)

### `bpf_ringbuf_output`

Призначений для відправки структурованих подій аудиту у високоефективний кільцевий буфер простору користувача.

```c
long bpf_ringbuf_output(
    void *ringbuf,
    void *data,
    u64 size,
    u64 flags
);
```

Використання Ring Buffer мінімізує накладні витрати на передачу даних аудиту у простір користувача порівняно зі старим механізмом Perf Buffer за рахунок підтримки спільної пам'яті без зайвих копіювань. Атомарне резервування за допомогою `bpf_ringbuf_reserve()` дозволяє BPF-програмі формувати події безпосередньо у буфері спільної пам'яті, усуваючи необхідність у додатковому копіюванні через стек.
