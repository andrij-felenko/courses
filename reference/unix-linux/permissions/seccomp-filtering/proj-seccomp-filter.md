# ⚙️ Робочий фільтр: від голого BPF до бібліотеки

Тут ми двічі напишемо ту саму політику для того самого процесу — спершу руками, масивом інструкцій, потім через `libseccomp` — і подивимося, що саме бібліотека робить за нас. Руками варто зробити хоча б раз: після цього стає видно, чому одні перевірки в політиці пишуться легко, а інші не пишуться взагалі.

Задача така. Служба-конвертер прочитала конфіг, відкрила сокет і робочу теку, розібралася з бібліотеками — і далі до кінця життя лише читає з дескрипторів, пише в дескриптори й крутить піксели в пам'яті. Усе цікаве вона зробила на старті. Отже, ставимо фільтр саме тут, між ініціалізацією й головним циклом.

## Масив інструкцій

Програма фільтра — це `struct sock_filter filter[]`, звичайний масив у пам'яті процесу. Кожен елемент — одна інструкція: код операції, два зсуви переходу й константа. Машина має один акумулятор; `BPF_LD | BPF_W | BPF_ABS` кладе в нього 32-бітне слово зі знімка регістрів за вказаним зсувом, `BPF_JMP` порівнює акумулятор із константою, `BPF_RET` завершує програму й повертає вирок.

Уся хитрість — у переходах, і саме на ній спотикаються найчастіше. `jt` і `jf` — не адреси й не індекси в масиві, а **зсуви**: скільки інструкцій пропустити, рахуючи від наступної. Тому `jt = 0` означає не «нікуди не переходити», а «перейти на наступну» — тобто просто впасти вниз.

Через це пряме бажання «зібрати всі дозволені номери, а в кінці поставити `RET ALLOW`» перетворюється на арифметику зі зсувами, яка ламається від додавання одного рядка посередині. Робочий прийом інший: на кожен дозволений виклик пишемо **пару** — порівняння, а одразу за ним його власний `RET ALLOW`. Збіг (`jt = 0`) падає на дозвіл, розбіжність (`jf = 1`) перестрибує його й іде на наступне порівняння. Усі зсуви назавжди лишаються нулем і одиницею.

![Ліворуч вертикальний список інструкцій масиву struct sock_filter із номерами позицій: нуль — завантажити arch, один — порівняти arch з AUDIT_ARCH_X86_64 зі зсувами jt=1 jf=0, два — повернути KILL_PROCESS, три — завантажити nr, чотири — порівняти nr із 0x40000000 зі зсувами jt=0 jf=1, п'ять — повернути KILL_PROCESS, далі пари порівняння й дозволу для read і write, і в кінці повернення ERRNO з кодом ENOSYS. У проміжку між списком і поясненнями дві стрілки показують, куди насправді ведуть переходи: зсув jt=1 з рядка один веде на рядок три, зсув jf=1 з рядка шість веде на рядок вісім. Праворуч чотири панелі пояснень: зсуви рахуються від наступної інструкції, тому jt=0 означає перейти на наступну; звідси прийом «пара» — порівняння й одразу за ним RET ALLOW, усі зсуви лишаються нулем і одиницею; ціна прийому — дві інструкції на кожен дозволений виклик, тож сто дозволених дають двісті інструкцій поспіль; arch перевіряють першим, бо номер без таблиці нічого не означає, а одразу за ним відсіюють x32 за бітом 0x40000000](/reference/unix-linux/permissions/seccomp-filtering/img/bpf-chain.svg)

*Зсуви переходів рахуються від наступної інструкції — саме тому дозволи пишуть парами й ніколи не рахують довжину хвоста.*

Ось уся програма. Перші шість інструкцій — обов'язкова передмова, решта — власне політика.

```c
#define _GNU_SOURCE
#include <errno.h>
#include <stddef.h>
#include <unistd.h>
#include <sys/prctl.h>
#include <sys/syscall.h>
#include <linux/audit.h>
#include <linux/filter.h>
#include <linux/seccomp.h>

#define X32_BIT 0x40000000

#define ALLOW(name)                                             \
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_##name, 0, 1),     \
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW)

static struct sock_filter filter[] = {
    /* 0 */ BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
                     offsetof(struct seccomp_data, arch)),
    /* 1 */ BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_X86_64, 1, 0),
    /* 2 */ BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),

    /* 3 */ BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
                     offsetof(struct seccomp_data, nr)),
    /* 4 */ BPF_JUMP(BPF_JMP | BPF_JGE | BPF_K, X32_BIT, 0, 1),
    /* 5 */ BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),

    ALLOW(read),    ALLOW(write),   ALLOW(close),  ALLOW(lseek),
    ALLOW(fstat),   ALLOW(mmap),    ALLOW(munmap), ALLOW(brk),
    ALLOW(rt_sigreturn), ALLOW(exit_group),

    BPF_STMT(BPF_RET | BPF_K,
             SECCOMP_RET_ERRNO | (ENOSYS & SECCOMP_RET_DATA)),
};

static int lock_down(void)
{
    struct sock_fprog prog = {
        .len    = (unsigned short)(sizeof filter / sizeof filter[0]),
        .filter = filter,
    };
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) != 0)
        return -1;
    return syscall(SYS_seccomp, SECCOMP_SET_MODE_FILTER, 0, &prog);
}
```

Три речі в цьому коді неочевидні. По-перше, `seccomp` викликається через `syscall()`: обгортки в glibc для нього немає, і це записано просто в описі виклику. По-друге, `rt_sigreturn` і `exit_group` у списку — не прикраса: без першого процес гине від першого-ліпшого сигналу, без другого не може завершитися. По-третє, інструкція 4 порівнює **номер** із `0x40000000` — той самий біт `__X32_SYSCALL_BIT`, яким ABI x32 відрізняється від звичайного 64-бітного ([32-бітні програми на 64-бітному ядрі](book:unix-linux/compat-32-on-64) живуть у своїй таблиці номерів, і перевірка `arch` їх ловить, а от x32 подає той самий `AUDIT_ARCH_X86_64` і відрізняється лише цим бітом). Пропустивши цю інструкцію, ви лишаєте фільтр із чорним списком повністю обхідним: заборонений виклик роблять із виставленим тридцятим бітом і повз усі порівняння. У ядрах до 5.4 ця плутанина була ще гіршою — там проходили й номери діапазону 512–547 з бітом і без нього, з переплутаною семантикою.

## Умова на аргумент і чому вона довша, ніж здається

Скажімо, писати дозволено лише у два дескриптори — 1 і 2. Аргументи у знімку 64-бітні, а акумулятор 32-бітний, тож одне порівняння тут неможливе:

```c
/* args[0] == 1, чесно, обома половинами (little-endian) */
BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
         offsetof(struct seccomp_data, args[0]) + 4),   /* старші 32 біти */
BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, 0, 0, 3),
BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
         offsetof(struct seccomp_data, args[0])),       /* молодші 32 біти */
BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, 1, 0, 1),
BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
```

Порівняти лише молодшу половину — класична дірка: значення `0x1_0000_0001` пройде перевірку «дорівнює одиниці», а в ядро потрапить зовсім інше число. І ще: після звертання до `args` в акумуляторі більше не лежить `nr`, тож перед наступним порівнянням номера його треба завантажити знову.

## Те саме через libseccomp

Тепер та сама політика, лише без ручної арифметики. Бібліотека тримає правила як набір, а програму збирає при завантаженні.

```c
#include <errno.h>
#include <seccomp.h>
#include <stddef.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sys/mman.h>

static int lock_down(void)
{
    /* дія за замовчуванням — те, що дістанеться всьому недозволеному */
    scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_ERRNO(ENOSYS));
    if (ctx == NULL)
        return -1;

    /* 2 — збирати дерево, а не ланцюг порівнянь */
    seccomp_attr_set(ctx, SCMP_FLTATR_CTL_OPTIMIZE, 2);

    static const int plain[] = {
        SCMP_SYS(read),  SCMP_SYS(close),  SCMP_SYS(lseek), SCMP_SYS(fstat),
        SCMP_SYS(munmap), SCMP_SYS(brk),
        SCMP_SYS(rt_sigreturn), SCMP_SYS(exit_group),
    };
    for (size_t i = 0; i < sizeof plain / sizeof plain[0]; i++)
        seccomp_rule_add(ctx, SCMP_ACT_ALLOW, plain[i], 0);

    /* писати — лише у два вже відкриті дескриптори */
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
                     SCMP_A0(SCMP_CMP_EQ, 1));
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
                     SCMP_A0(SCMP_CMP_EQ, 2));

    /* анонімна пам'ять — так; відображення файлу в пам'ять — ні */
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(mmap), 1,
                     SCMP_A3(SCMP_CMP_MASKED_EQ, MAP_ANONYMOUS, MAP_ANONYMOUS));

    /* з усього мультиплексора ioctl — один-єдиний запит */
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(ioctl), 1,
                     SCMP_A1(SCMP_CMP_EQ, TIOCGWINSZ));

    seccomp_export_pfc(ctx, STDOUT_FILENO);   /* подивитися, що вийшло */

    int rc = seccomp_load(ctx);   /* сама виставить no_new_privs */
    seccomp_release(ctx);
    return rc;
}
```

Умова на аргумент задається трійкою «номер аргументу — операція — значення»: `SCMP_A0` то й є нульовий аргумент. Порівняння з маскою (`SCMP_CMP_MASKED_EQ`) бере два числа — маску й очікуване значення після накладання маски; саме так перевіряють окремі прапорці, не вимагаючи точної рівності всього слова. Половинки 64-бітного аргументу бібліотека розбиває сама.

`ioctl` тут — окремий випадок і головна причина взагалі мати умови на аргументи. Це не один виклик, а [мультиплексор із сотень операцій](book:unix-linux/ioctl-interface), схованих за числом у другому аргументі; дозволивши `ioctl` цілком, ви дозволяєте все, що вміє драйвер за дескриптором.

## Що бібліотека згенерувала

`seccomp_export_pfc()` друкує зібрану програму людською мовою — це найшвидший спосіб побачити, чи політика означає те, що ви думали:

```
# filter for arch x86_64 (3221225534)
if ($arch == 3221225534)
  if ($syscall > 9)
    if ($syscall > 16)
      # filter for syscall "exit_group" (231) [priority: 65535]
      if ($syscall == 231)
        action ALLOW;
    else # ($syscall <= 16)
      # filter for syscall "ioctl" (16) [priority: 65525]
      if ($syscall == 16)
        if ($a1 == 21523)
          action ALLOW;
  else # ($syscall <= 9)
    # filter for syscall "write" (1) [priority: 65523]
    if ($syscall == 1)
      if ($a0.hi32 == 0)
        if ($a0.lo32 == 1)
          action ALLOW;
      ...
  # default action
  action ERRNO(38);
# invalid architecture action
action KILL;
```

Видно і дерево (`if ($syscall > 9)` / `else`), і роздвоєння 64-бітного аргументу на `hi32` та `lo32`, і те, що чужа архітектура зустрічається смертю. Варто знати, що дерево — **не** типовий стан: за замовчуванням (`SCMP_FLTATR_CTL_OPTIMIZE` дорівнює 1) бібліотека сортує правила за пріоритетом і складністю й ставить їх ланцюгом. Двійкове дерево — це рівень 2, який з'явився в libseccomp 2.5.0 і вмикається явно; на кожному вузлі перелік номерів ділиться навпіл, і глибина зростає логарифмічно замість лінійно.

## Пастки

**`EPERM` чи `ENOSYS` у дії за замовчуванням.** Це не косметика, а частина контракту з бібліотекою C: `ENOSYS` означає «такого виклику в ядрі немає» і вмикає в програмі запасний шлях на старіший виклик, а `EPERM` вона вважає справжньою помилкою й здається. Для дії за замовчуванням (все невідоме) правильна відповідь майже завжди `ENOSYS`; для навмисно закритого виклику, який програма точно знає, `EPERM` чесніший. І дрібниця з ядра: значення в молодших бітах обрізається зверху до 4095, тож туди має сенс класти лише справжній номер помилки.

**Дескриптор — не гарантія.** Умова `write` на дескриптор 1 обмежує номер, а не те, куди цей номер веде: якщо процес уміє відкривати файли, він відкриє потрібне й отримає той самий номер. Умова на дескриптор має сенс лише в парі із забороною відкривати нове.

**Обробник `SIGSYS`.** Дія `TRAP` замість негайної смерті надсилає сигнал, і в його описі лежить усе для діагностики: номер виклику, архітектура й адреса самої інструкції, з якої зроблено виклик. Це найдешевший спосіб дізнатися, чого політиці бракує.

```c
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

static void on_sigsys(int sig, siginfo_t *si, void *uc)
{
    (void)sig; (void)uc;
    char buf[160];
    int n = snprintf(buf, sizeof buf,
                     "seccomp: заборонено виклик %d (arch 0x%x) з адреси %p\n",
                     si->si_syscall, si->si_arch, si->si_call_addr);
    write(STDERR_FILENO, buf, n > 0 ? (size_t)n : 0);
    _exit(159);
}

static void catch_sigsys(void)
{
    struct sigaction sa = { 0 };
    sa.sa_sigaction = on_sigsys;
    sa.sa_flags = SA_SIGINFO;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSYS, &sa, NULL);
}
```

Тут два капкани одразу. Перший: `write` і `exit_group`, якими користується сам обробник, мусять бути дозволені фільтром — інакше обробник заборони спричиняє нову заборону. Другий: `snprintf` не входить до переліку функцій, безпечних у обробнику сигналу ([що можна робити в обробнику](book:unix-linux/async-signal-safety)); тут це терпимо, бо наступним рядком процес однаково гине, але в обробнику, який повертається, форматування треба замінити ручним складанням рядка. І якщо він таки повертається — `rt_sigreturn` у білому списку обов'язковий.

**Потоки.** `SECCOMP_SET_MODE_FILTER` без прапорців чіпляє фільтр лише до потоку, який його встановив. Якщо політику ставлять уже після створення потоків, потрібен прапорець `SECCOMP_FILTER_FLAG_TSYNC` — тоді ядро або застосує фільтр до всіх потоків процесу, або не застосує ні до кого. Простіше, звісно, ставити фільтр до першого `pthread_create`.

**Ціна.** Ланцюг із пар коштує дві інструкції на дозволений виклик, і останній у ланцюзі платить за всіх попередніх. Дерево зводить це до логарифма. А з ядра 5.11 більшість політик узагалі не доходить до прогону програми: якщо для номера вирок виходить сталим `ALLOW` і програма при цьому жодного разу не дивилася на аргументи, ядро запам'ятовує це бітом у карті й далі відповідає одним зверненням. Практичний висновок парадоксальний: кожна додана умова на аргумент вибиває свій виклик із швидкого шляху й повертає його до чесного прогону BPF. Тож умови на аргументи ставлять там, де вони справді щось закривають, а не «про всяк випадок».
