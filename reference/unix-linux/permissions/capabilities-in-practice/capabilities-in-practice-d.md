Коли ми знаємо, як ядро обробляє можливості, постає суто практичне питання: як їх призначити програмі, як перевірити наявність і як обмежити їхнє поширення. У цьому розділі ми розглянемо три основні шляхи отримання можливостей на практиці: через розширені атрибути файлу, через успадкування від менеджера служб (Systemd) та інструменти перевірки (capsh, libcap).

## Файлові можливості: setcap та getcap

Найстаріший і найочевидніший спосіб дати програмі повноваження — записати їх прямо на виконуваний файл. Ядро прочитає їх під час виклику `execve` і покладе у відповідні набори процесу.

Для роботи з файловими можливостями використовують утиліти з пакунка `libcap2-bin`: `setcap` для призначення та `getcap` для читання.

```bash
== Bash
# Призначення можливості відкривати привілейовані порти (нижче 1024)
sudo setcap cap_net_bind_service=ep /usr/bin/my-web-server

# Перевірка
getcap /usr/bin/my-web-server
```

Після імені можливості йде знак дорівнює та список наборів (суфіксів), у які її треба покласти:
- `e` (effective) — зробити діючою відразу після запуску.
- `p` (permitted) — додати в набір дозволених.
- `i` (inheritable) — додати в набір успадковуваних.

Формат `+ep` означає, що можливість дозволена й одразу діє. Якщо вказати лише `+p`, програма мусить сама перевести її в діючі через виклик `capset()`.

### Обережно з архівами та копіюванням

Оскільки можливості зберігаються як розширені атрибути (xattr), звичайне копіювання за допомогою `cp` їх втратить. Архіватор `tar` теж ігнорує xattr за замовчуванням.

```bash
== Bash
# Копіювання зі збереженням xattr
cp --preserve=xattr /usr/bin/my-web-server /opt/bin/
```

## Systemd і навколишні (ambient) можливості

Хоча файлові можливості працюють, для розгортання сотень служб вони незручні. Пакетний менеджер мусить ставити позначки при оновленні, а `tar` може їх загубити під час розгортання бекапів.

Тому сучасний підхід — **навколишні можливості (ambient capabilities)**, які процес передає через `execve` без жодних позначок на самому файлі. Systemd ідеально підходить для цього: він стартує від root, збирає потрібні набори, скидає UID до непривілейованого і запускає звичайний бінарник.

```ini
== Systemd Unit
[Service]
ExecStart=/opt/myapp/server
User=myappuser
Group=myappgroup
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
```

- `AmbientCapabilities=` — вказує, які можливості передати в навколишній набір.
- `CapabilityBoundingSet=` — звужує граничну стелю (bounding set). Без цього рядка служба не зможе перевищити навколишні можливості через `exec`, але її нащадки теоретично змогли б підняти інші, якби запустили файл із `setcap`.

## Перевірка через capsh

Для дослідження та налагодження ідеально підходить `capsh` (capability shell). Він дозволяє запустити оболонку з конкретними наборами або розшифрувати статус іншого процесу.

```bash
== Bash
# Декодування маски можливостей (наприклад, з /proc/<pid>/status)
capsh --decode=0000000000003000

# Запуск оболонки зі зниженими правами для тестування
sudo capsh --caps="cap_net_raw+eip cap_setpcap,cap_setuid,cap_setgid+ep" \
           --keep=1 --user=nobody --addamb=cap_net_raw -- -c "ping -c 1 8.8.8.8"
```

Цей ланцюжок робить саме те, що systemd: готує набори, переходить у непривілейованого користувача (`nobody`) та кидає можливість `CAP_NET_RAW` у навколишній набір.

## Підсумок

Уникнення root — це не завжди ізоляція в контейнері. Правильне використання `AmbientCapabilities` у Systemd або точкове призначення через `setcap` дає змогу надійно прив'язати необхідні повноваження до служб, не розширюючи поверхню атаки на всю систему.
