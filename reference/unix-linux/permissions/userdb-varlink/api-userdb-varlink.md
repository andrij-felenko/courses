# 📋 io.systemd.UserDatabase: сигнатури, помилки, кадр на дроті й команди

Це контракт у двох ролях одразу: за ним пишуть клієнта, який питає про облікові записи, і за ним же пишуть власну службу, яка на ці питання відповідає. Три методи, шість власних імен помилок, один кадр на дроті, шість тек — і дві команди, якими все це перевіряють з оболонки, не написавши жодного рядка коду.

## Опис інтерфейсу

Мовою опису інтерфейсів Varlink. Знак `?` перед типом означає, що поле можна не передавати; `[]` — масив. Усе, що без `?`, у повідомленні бути мусить.

```
interface io.systemd.UserDatabase

method GetUserRecord(
    uid: ?int,
    userName: ?string,
    fuzzyNames: ?[]string,
    dispositionMask: ?[]string,
    uidMin: ?int,
    uidMax: ?int,
    uuid: ?string,
    service: string
) -> (
    record: object,
    incomplete: ?bool
)

method GetGroupRecord(
    gid: ?int,
    groupName: ?string,
    fuzzyNames: ?[]string,
    dispositionMask: ?[]string,
    gidMin: ?int,
    gidMax: ?int,
    uuid: ?string,
    service: string
) -> (
    record: object,
    incomplete: ?bool
)

method GetMemberships(
    userName: ?string,
    groupName: ?string,
    service: string
) -> (
    userName: string,
    groupName: string
)

error NoRecordFound()
error BadService()
error ServiceNotAvailable()
error ConflictingRecordFound()
error NonMatchingRecordFound()
error EnumerationNotSupported()
```

Усі три методи оголошено з підтримкою прапорця `more`: на один виклик служба має право відповісти багато разів.

## Параметри пошуку

`GetUserRecord` і `GetGroupRecord` — близнюки, у яких різняться лише імена чотирьох полів: числових і тих, що звужують діапазон.

| параметр | тип | що робить |
|---|---|---|
| `uid` / `gid` | `?int` | головний ключ: шукати за 32-бітним числом |
| `userName` / `groupName` | `?string` | головний ключ: шукати за іменем |
| `fuzzyNames` | `?[]string` | нестрогий пошук за переліченими рядками |
| `dispositionMask` | `?[]string` | звузити до перелічених родів запису: `intrinsic`, `system`, `regular`, `dynamic`, `container`, `foreign`, `reserved` |
| `uidMin` / `uidMax`, `gidMin` / `gidMax` | `?int` | звузити до діапазону чисел |
| `uuid` | `?string` | звузити до запису з таким UUID |
| `service` | `string` | обов'язковий; ім'я служби, до якої ви під'єдналися |

Відповідь:

| поле | тип | що означає |
|---|---|---|
| `record` | `object` | сам запис JSON |
| `incomplete` | `?bool` | `true`, коли секція `privileged` у записі була й її вирізали |

Прочитати `incomplete` як «запис короткий» — типова помилка. Поле каже не про повноту даних, а про ваші права: `false` стоїть і тоді, коли секції не було зовсім, і тоді, коли вона була й вам її віддали. `true` означає рівно одне — секція існує, але не для вас.

`fuzzyNames` теж варто описати точно, бо «нестрогий» тут не здогадка, а два конкретні правила. Кожен ваш рядок звіряють, знехтувавши регістром, з усіма іменами, які має запис: власне ім'я, ім'я з областю (`andrij@example.com`), справжнє ім'я, адреса пошти, ім'я для CIFS і кожен із псевдонімів. Спершу шукають підрядок; а якщо ваш рядок має щонайменше п'ять знаків, додатково рахують відстань Левенштайна й приймають збіг, коли вона менша за 3. Тобто дві літери помилки пробачають лише довгим запитам — коротким ні, бо інакше збігалося б геть усе.

## Правила, що випливають із ключів

Головних ключів два — число й ім'я. Три способи їх поєднати дають три різні відповіді, і жодна не та, якої чекають за звичкою.

**Задано обидва.** Служба шукає за іменем, а число звіряє вже зі знайденим записом. Збіглося ім'я, але не число (чи навпаки) — це `ConflictingRecordFound`, а не мовчазна перевага одного ключа над іншим.

**Головний ключ збігся, додаткові фільтри — ні.** Запис із таким іменем є, але його рід не входить у `dispositionMask`, або число поза `uidMin…uidMax` — це `NonMatchingRecordFound`. Помилка окрема саме тому, що змістом вона протилежна до «такого немає»: запис існує, просто не той, який ви описали.

**Не задано жодного.** Це запит на перелік усієї бази, і робити його треба з `more` — інакше службі нікуди подіти другий і наступні записи. Служба, яка себе перелічувати не вміє, каже це прямо: `EnumerationNotSupported`.

`GetMemberships` живе за тим самим правилом, тільки ключі в нього рівноправні: задали `userName` — дістанете групи цієї людини, задали `groupName` — її учасників, не задали нічого — усі пари, які служба знає. Одна відповідь несе рівно одну пару «людина, група», тож усе, крім питання про одну конкретну пару, потребує `more`.

## Параметр service

Обов'язковий у кожному виклику й перевіряється буквально: він мусить дорівнювати базовому імені сокета, до якого ви під'єдналися, — шляхові `/run/systemd/userdb/<ім'я>` без теки. Правило потрібне, щоб одна служба могла тримати кілька імен на одному сокеті: сам сокет тоді вже не каже, кого саме питають.

У `systemd-userdbd` таких імен три, і кожне звужує пошук:

| `service` | що відповідає |
|---|---|
| `io.systemd.Multiplexer` | усе, що є на машині: обхід решти сокетів робиться за клієнта |
| `io.systemd.NameServiceSwitch` | лише те, що дає [класичний перемикач](topic:unix-linux/user-database-nss) |
| `io.systemd.DropIn` | лише записи з файлів у теках `userdb` |

Будь-яке інше значення — і навіть просто відсутність поля — дає `BadService`.

## Помилки

На дроті кожне ім'я їде з префіксом інтерфейсу: `io.systemd.UserDatabase.NoRecordFound`.

| ім'я | коли виникає |
|---|---|
| `NoRecordFound` | запису з таким числом чи іменем немає; при переліку — база порожня; для членств — жодної пари |
| `BadService` | поле `service` не задане або не збігається з іменем сокета |
| `ServiceNotAvailable` | джерело непрацездатне: ні запису, ні відповіді «немає» дати не можна |
| `ConflictingRecordFound` | задано число й ім'я, а знайдене збігається лише з одним із них |
| `NonMatchingRecordFound` | головний ключ збігся, додаткові фільтри — ні |
| `EnumerationNotSupported` | ця служба відповідає лише на пошук за числом чи іменем, перелічувати себе не вміє |

Розрізнення `NoRecordFound` і `ServiceNotAvailable` — головне, заради чого цей перелік узагалі варто читати уважно. Перше — це знання: подивилися, такого запису немає. Друге — відсутність знання: спитати не вдалося, і про існування запису не сказано нічого. Клієнт, який зводить обидві відповіді в один `NULL`, у мить недоступності каталогу поведеться так, ніби людей не існує зовсім.

Крім цих шести, будь-яка служба Varlink може відповісти помилками службового інтерфейсу `org.varlink.service`: `MethodNotFound`, `InvalidParameter` (з іменем хибного поля), `PermissionDenied`, `ExpectedMore`. Їхні імена йдуть з іншим префіксом — саме за префіксом їх і відрізняють від помилок самої бази.

## Кадр на дроті

З'єднання — [сокет домену Unix](topic:unix-linux/unix-domain-sockets) типу `SOCK_STREAM`. Кадр — один об'єкт [JSON](topic:programming/json-format), за яким іде один нульовий байт. Роздільник обрано саме такий, бо всередині коректного JSON нульовий байт не трапляється ніколи: розбирати потік можна, не рахуючи дужок і не знаючи довжини наперед.

Виклик:

| поле | тип | що означає |
|---|---|---|
| `method` | `string` | повне ім'я: інтерфейс, крапка, метод |
| `parameters` | `?object` | вхідні параметри |
| `more` | `?bool` | клієнт готовий прийняти багато відповідей |
| `oneway` | `?bool` | відповіді не буде взагалі |
| `upgrade` | `?bool` | після однієї відповіді з'єднання переходить під інший протокол |

Відповідь:

| поле | тип | що означає |
|---|---|---|
| `parameters` | `?object` | вихідні поля — або поля помилки |
| `continues` | `?bool` | за цією відповіддю буде ще принаймні одна |
| `error` | `?string` | повне ім'я помилки; виклик не вдався |

`more` і `oneway` разом не ставлять: перший просить багато відповідей, другий — жодної. Поки служба відповідає з `continues: true`, з'єднання зайняте цим викликом; відповідь без `continues` його закриває. Клієнтові, якому досить перших записів, домовлятися ні про що не треба — він просто закриває з'єднання.

```
→ {"method":"io.systemd.UserDatabase.GetUserRecord",
   "parameters":{"service":"io.systemd.Multiplexer"},"more":true}\0

← {"parameters":{"record":{"userName":"root",…},"incomplete":false},"continues":true}\0
← {"parameters":{"record":{"userName":"andrij",…},"incomplete":true},"continues":true}\0
← {"parameters":{"record":{"userName":"nobody",…},"incomplete":false}}\0
```

Кадр помилки влаштований інакше: `continues` у ньому немає ніколи, а головним полем стає `error` із повним іменем. Поля помилки, якщо вони в неї є, їдуть у `parameters`; жодна з шести помилок цього інтерфейсу власних полів не має, тож `parameters` у такому кадрі буває або порожнім об'єктом, або відсутнім зовсім — покладатися на його наявність клієнтові не варто.

```
→ {"method":"io.systemd.UserDatabase.GetUserRecord",
   "parameters":{"userName":"zzz-no-such-user","service":"io.systemd.Multiplexer"}}\0

← {"error":"io.systemd.UserDatabase.NoRecordFound"}\0
```

Хто питає, служба не запитує в клієнта, а бере зі з'єднання: ядро саме засвідчує UID того, хто під'єднався. `systemd-userdbd` вважає клієнта довіреним, коли цей UID дорівнює нулю або збігається з UID самого запису, — і лише тоді лишає в записі секцію `privileged`.

Протокол настільки малий, що найкоротший робочий виклик не потребує ні бібліотеки, ні спеціальної команди — досить будь-чого, що вміє з'єднатися з сокетом:

```sh
req='{"method":"io.systemd.UserDatabase.GetUserRecord",
      "parameters":{"userName":"root","service":"io.systemd.Multiplexer"}}'

printf '%s\0' "$req" |
    socat - UNIX-CONNECT:/run/systemd/userdb/io.systemd.Multiplexer
```

Це варто зробити хоч раз власноруч: далі стає видно, що `varlinkctl` і `userdbctl` — не окремі канали до бази, а зручні обгортки над оцим самим обміном.

## Шляхи

| шлях | що там лежить |
|---|---|
| `/run/systemd/userdb/` | сокети служб; ім'я файлу дорівнює значенню `service` |
| `/etc/userdb/` | статичні записи, які завів адміністратор |
| `/run/userdb/` | статичні записи, створені на час роботи системи |
| `/run/host/userdb/` | записи, вкладені в контейнер знадвору |
| `/usr/local/lib/userdb/` | записи, поставлені руками повз пакунковий менеджер |
| `/usr/lib/userdb/` | записи, що приїхали з пакунком |

П'ять останніх тек читає служба `io.systemd.DropIn`, і ключ пошуку в неї — саме ім'я файлу:

| файл | що описує |
|---|---|
| `<ім'я>.user` | обліковий запис людини |
| `<ім'я>.group` | групу |
| `<людина>:<група>.membership` | одне членство |

Однойменні файли з різних тек не складаються — діє звичайне правило вставок systemd. Теки переглядають саме в тому порядку, як у таблиці: `/etc` → `/run` → `/run/host` → `/usr/local/lib` → `/usr/lib`, і перший знайдений файл із цим іменем виграє. Звідси два наслідки, обидва навмисні: адміністратор перекриває пакунковий запис, поклавши свій файл у `/etc/userdb/`, а прибрати пакунковий запис зовсім можна символьним посиланням на `/dev/null` під тим самим іменем — такий файл вважається заглушеним, а не порожнім.

## varlinkctl: сирий виклик

```sh
varlinkctl info /run/systemd/userdb/io.systemd.Multiplexer
varlinkctl introspect /run/systemd/userdb/io.systemd.Multiplexer io.systemd.UserDatabase
varlinkctl call /run/systemd/userdb/io.systemd.Multiplexer \
    io.systemd.UserDatabase.GetUserRecord \
    '{"userName":"andrij","service":"io.systemd.Multiplexer"}'
```

`info` друкує те, що віддає службовий метод `org.varlink.service.GetInfo`:

```
    Vendor: The systemd Project
   Product: systemd (systemd-userwork)
   Version: 257 (257.5-1.fc42)
       URL: https://systemd.io/
Interfaces: io.systemd.UserDatabase
            org.varlink.service
```

`introspect` віддає опис інтерфейсу — той самий, що на початку цієї сторінки, тільки з коментарем до кожного поля. Це і є спосіб дізнатися контракт від самої машини, а не з документації, яка могла відстати від встановленої версії.

Параметри, без яких `call` мало корисний:

| параметр | дія |
|---|---|
| `--more` | поставити прапорець `more`; вивід стає потоком об'єктів JSON |
| `--collect` | те саме, але всі відповіді зібрати в один масив |
| `--json=pretty` | розкласти вивід з відступами |
| `--graceful=<ім'я>` | вважати названу помилку успіхом, тобто повернути код виходу 0 |
| `--timeout=<с>` | замінити типові 45 секунд |

`--graceful` існує саме через `NoRecordFound`: у скрипті «такого користувача немає» — звичайна відповідь, а не збій, і зводити її до ненульового коду виходу незручно.

## userdbctl: готові запити

```sh
userdbctl user                        # перелік усіх записів таблицею
userdbctl user andrij --json=pretty   # один запис як JSON
userdbctl group wheel --json=pretty
userdbctl users-in-group wheel
userdbctl groups-of-user andrij
userdbctl services
userdbctl ssh-authorized-keys andrij
```

Запис, що приїхав із класичного перемикача, впізнається у виводі відразу — служба дописує собі підпис у секцію `status`, під ключем машинного ідентифікатора:

```
$ userdbctl group wheel --json=pretty
{
        "groupName" : "wheel",
        "disposition" : "system",
        "gid" : 10,
        "members" : [
                "andrij"
        ],
        "status" : {
                "3a9f1c8d5e2b4a7f9c1d6e0b3a8f5c24" : {
                        "service" : "io.systemd.NameServiceSwitch"
                }
        }
}
```

```
$ userdbctl services
SERVICE                      LISTENING
io.systemd.DropIn            yes
io.systemd.DynamicUser       yes
io.systemd.Home              yes
io.systemd.Multiplexer       yes
io.systemd.NameServiceSwitch yes

5 services listed.
```

Стовпчик `LISTENING` — не окраса: команда справді під'єднується до кожного сокета в теці. Замість `yes` ви побачите `No (ECONNREFUSED)` там, де файл-сокет лишився від служби, якої вже немає, — а це і є найчастіша причина того, що частина людей раптом «зникла».

| параметр | дія |
|---|---|
| `--json=pretty` / `--json=short` | віддати сам запис JSON замість таблиці |
| `--service=<a>:<b>` | питати лише названі служби |
| `--with-nss=no` | не питати класичний шлях через бібліотеку C |
| `--with-dropin=no` | не брати записи з файлів |
| `--with-varlink=no` | не питати служб Varlink |
| `--multiplexer=no` | обійти теку сокетів самотужки, як це робить рання система |
| `-z`, `--fuzzy` | нестрогий пошук — той самий `fuzzyNames` |
| `--disposition=`, `--uid-min=`, `--uid-max=` | ті самі фільтри, що й у параметрах методу |

Три перемикачі `--with-…` разом із `--multiplexer=` — це готовий інструмент розбору несправностей: вони дозволяють спитати кожне джерело окремо й побачити, котре саме дало відповідь, якої ви не чекали.

Останній рядок прикладів варто знати окремо. `userdbctl ssh-authorized-keys` друкує ключі з секції `privileged` рівно в тому вигляді, у якому їх чекає `sshd`, тож у `/etc/ssh/sshd_config` пишуть так:

```
AuthorizedKeysCommand /usr/bin/userdbctl ssh-authorized-keys %u
AuthorizedKeysCommandUser root
```

Другий рядок тут обов'язковий, і причина вже названа вище: секцію `privileged` служба віддає лише нульовому UID або самому власникові запису. Запущена від будь-кого іншого, ця команда чесно віддасть запис — просто без ключів, і вхід не відбудеться.
