# 📜 Еволюція Secure Computing Mode: від строгого режиму 2005 року до BPF та User Notification

Механізм фільтрації системних викликів Seccomp пройшов шлях від вузькоспеціалізованого засобу захисту обчислювальних вузлів до центрального фундаменту контейнерної безпеки та пісочниць (sandboxes) сучасного веб-браузингу. Розуміння цієї еволюції дозволяє усвідомити, які саме загрози та інженерні компроміси сформували поточну архітектуру ядра Linux.

Початкова версія підсистеми, відома як **Seccomp Strict Mode**, була розроблена інженером Андреа Арканжелі (Andrea Arcangeli) і включена до ядра Linux 2.6.12 у травні 2005 року. Мотивацією для створення механізму був проект CPUShare — платформа розподілених peer-to-peer обчислень, де користувачі здавали в оренду вільні такти процесора для виконання стороннього некопмільованого коду. Потрібен був абсолютний гарант того, що орендований потік не зможе пошкодити файлову систему господарської машини, відкрити мережеве з'єднання або модифікувати інші процеси.

Арканжелі запропонував максимально радикальний підхід: після активації прапорця через `prctl(PR_SET_SECCOMP, 1)` процес переходив у режим, у якому ядро дозволяло виконання лише чотирьох системних викликів:
- `read(2)` — читання з уже відкритих дескрипторів;
- `write(2)` — запис у вже відкриті дескриптори;
- `_exit(2)` — завершення потоку;
- `sigreturn(2)` — повернення з обробника сигналів.

Будь-яка спроба виконати п'ятий системний виклик (наприклад, `open`, `fork`, `socket` чи навіть `getpid`) призводила до негайного знищення процесу ядром через сигнал `SIGKILL` (або `SIGBUS` на деяких архітектурах). Хоча такий підхід гарантував повну ізоляцію, він виявився практично непридатним для загального програмного забезпечення. Більшість бібліотек середовища виконання (C runtime) вимагають динамічного виділення пам'яті (`brk`/`mmap`), перевірки часу (`clock_gettime`) або отримання ідентифікаторів процесу.

Зі стрімким розвитком веб-браузерів у 2010–2012 роках розробники проекту Google Chrome (зокрема Вілл Дрюрі, Will Drewry) зіткнулися з необхідністю ізоляції процесів рендерингу вкладків (renderer processes). Вкладка мала обробляти складний HTML/JavaScript вміст із мережі, але не повинна була мати доступу до дисків або мережевих сокетів користувача. Строгий режим Seccomp був занадто жорстким, а повноцінні модулі обов'язкового контролю доступу (SELinux/AppArmor) вимагали прав суперкористувача для розгортання та були занадто громіздкими.

У 2012 році в ядрі Linux 3.5 Вілл Дрюрі презентував **Seccomp-BPF** (Filter Mode). Ідея полягала у повторному використанні байт-коду Classic BPF (cBPF), який з 1990-х років застосовувався у мережевому стеку для фільтрації пакетів у `tcpdump`. Замість мережевого пакета BPF-програмі на вхід подавалася структура `seccomp_data`, що описувала системний виклик (номер `nr`, архітектуру `arch` та 64-бітні аргументи `args`). Це дозволило розробникам декларувати точні «білі списки» (whitelists) дозволених викликів безпосередньо у коді додатка.

Критичним етапом стабілізації Seccomp-BPF стало вирішення проблеми безпеки незапрошених процесів. Якщо непривілейований процес міг би завантажити BPF-фільтр, а потім виконати привілейовану програму з бітом `setuid` (наприклад, `/usr/bin/sudo`), то фільтр міг би перехопити виклики `sudo` і змусити його діяти некоректно, що веде до ескалації привілеїв. Енді Лутомірскі (Andy Lutomirski) вирішив цю проблему, додавши прапорець ядра `PR_SET_NO_NEW_PRIVS` (Linux 3.5). Цей прапорець гарантує, що процес та його діти не зможуть отримати привілеї через `setuid/setgid` біти чи файлові capabilities, зробивши безпечним встановлення фільтрів непривілейованими користувачами.

Еволюція Seccomp продовжувалася й у наступні роки:
- **Linux 4.14 (2017)**: Додано дію `SECCOMP_RET_LOG` для безпечного аудиту без зупинки процесів, а також `SECCOMP_RET_KILL_PROCESS` для знищення всього багатопоточного процесу замість одного потоку.
- **Linux 5.0 (2019)**: Крістіан Браунер (Christian Brauner) та Тихо Андерсен (Tycho Andersen) впровадили дію `SECCOMP_RET_USER_NOTIF`. Вона дозволила передавати обробку перехопленого системного виклику у простір користувача через дескриптор сповіщення. Це зробило можливим безпечну емуляцію привілейованих дій (наприклад, створення вузлів пристроїв `mknod` чи монтування файлових систем) всередині unprivileged-контейнерів.

Сьогодні Seccomp-BPF є стандартом де-факто для сучасної контейнерної інфраструктури (Docker, OCI runc, containerd, Kubernetes Container Runtime Interface) та браузерних пісочниць, забезпечуючи мінімізацію поверхні атак на ядро Linux.
