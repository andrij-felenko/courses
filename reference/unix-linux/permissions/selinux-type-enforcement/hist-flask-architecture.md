# 📜 Історія FLASK та народження Type Enforcement

Архітектура FLASK (Flux Advanced Security Kernel) та концепція Type Enforcement (TE), розроблені Агентством національної безпеки США (NSA) спільно з Університетом Юти, перетворили жорсткі військові моделі доступу на гнучкий інструмент безпеки сучасних операційних систем.

## 1. Проблема фіксованих політик безпеки у 1980–1990-х роках

До поява SELinux дослідження у галузі мандатного управління доступом (Mandatory Access Control, MAC) значною мірою спиралися на стандарти Міністерства оборони США, відомі як «Оранжева книга» (Trusted Computer System Evaluation Criteria, TCSEC). Головними математичними формалізмами того часу були модель Белла — ЛаПадули (Bell-LaPadula) для забезпечення конфіденційності та модель Біба (Biba) для цілісності даних.

Ці моделі оперували жорсткою ієрархією рівнів секретності (Unclassified, Confidential, Secret, Top Secret) та категоріями доступу. Їхня головна вада полягала в жорсткому вплетенні правил перевірки в код самої операційної системи. Операційні системи, збудовані за цим принципом (такі як Trusted Solaris або Secure UNIX), мали декілька фундаментальних обмежень:

- **Незнучкість:** Політика безпеки зашивалася на етапі компіляції ядра. Якщо системному демону потрібен був виняток із загального правила (наприклад, вебсерверу потрібен доступ лише до файлів у `/var/www`, але не до `/etc/shadow`), математичні моделі рівня секретності не мали інструментів для вираження такого дрібнозернистого обмеження.
- **Монолітність суперкористувача:** Процеси з ідентифікатором `UID 0` (root) повністю обходили всі обмеження MAC. Якщо зловмисник отримував контроль над привілейованим процесом, вся мандатна система безпеки ставала безпомічною.
- **Неможливість адаптації:** Ззвичайні програмні додатки не мали можливості визначати власні домени безпеки або динамічно змінювати правила доступу під час оновлення програмного забезпечення.

Наприкінці 1990-х років стало очевидно, що для корпоративних та мережевих серверних систем потрібна принципово інша модель, здатна контролювати взаємодію між довільними компонентами системи без прив'язки до військових грифів секретності.

## 2. Поява концепції Type Enforcement (TE) та DTE

Концепцію Type Enforcement (TE) уперше запропонували В. Ерл Беберт (W. Earl Boebert) та Річард Кейн (Richard Y. Kain) у 1985 році. Згодом, у 1995–1996 роках, дослідники Лі Бадхер (Lee Badger), Річард О'Браєн (Richard O'Brien) та їхні колеги з компанії Trusted Information Systems (TIS) адаптували та розширили її для операційних систем UNIX у проєкті Domain and Type Enforcement (DTE).

Ключова ідея TE полягала у відмові від ієрархічних рівнів секретності на користь абстрактного групування:

1. Усі об'єкти системи (файли, каталоги, пристрої, сокети) класифікуються за **типами** (`type`).
2. Усі суб'єкти (процеси) класифікуються за **доменами** (`domain`), які насправді є тими самими типами, застосованими до активних системних сутностей.
3. Доступ надається не на основі того, «хто затіяв дію», а на основі явних правил у матриці доступу, які визначають, які саме операції дозволені для конкретного домену щодо конкретного типу.

Модель DTE долала головну проблему традиційних систем: вона дозволяла ізолювати демонів із реальними правами root. Наприклад, демон DNS-сервера `named` міг працювати у домені `named_t`, який мав право читати лише свої конфігурації `named_conf_t` та слухати мережевий порт `dns_port_t`. Навіть якщо зловмисник захоплював контроль над `named` через вразливість витоку буфера, ядро блокувало будь-яку спробу прочитати файл `/etc/shadow` або виконати командну оболонку `/bin/sh`, бо у матриці TE не існувало правила `allow named_t shadow_t : file read;`.

Однак ранні реалізації DTE все ще мали недоліки: вони не дозволяли динамічно перемикати та комбінувати різні моделі безпеки (наприклад, одночасно використовувати TE та розмежування за рольовою моделлю RBAC).

## 3. Проєкт FLASK у NSA та Університеті Юти

У 1997 році Відділ досліджень інформаційної безпеки NSA (Information Assurance Research Group) під керівництвом Пітера Лоскокко (Peter Loscocco) та дослідники з NAI Labs / Secure Computing Corporation, зокрема Рей Спенсер (Ray Spencer), об'єднали зусилля з дослідницькою групою Flux Research Group під керівництвом професора Джея Лепреа (Jay Lepreau) з Університету Юти. Результатом цієї співпраці стала архітектура **FLASK (Flux Advanced Security Kernel)**.

Початково FLASK розроблялася для експериментальної операційної системи Fluke (на базі мікроядра Mach). Дослідники прагнули розв'язати критичну проблему мікроядерних систем: як забезпечити швидкий контроль доступу між абстрактними об'єктами IPC без розповсюдження коду перевірки політики по всім серверам.

Головним науковим досягненням FLASK стало **абсолютне відокремлення механізму забезпечення безпеки (Enforcement Engine) від компонента прийняття рішень (Security Server)**.

Артефакти та рішення FLASK, які лягли в основу SELinux:

- **Security Server (Сервер безпеки):** Ізольований модуль усередині ядра, який утримує завантажену політику безпеки, обчислює вектори доступу та обробляє запити на перехід типів. Двигун ядра нічого не знає про синтаксис правил — він лише питає в Security Server: «Чи має суб'єкт A право виконати дію X над об'єктом B?».
- **Security Identifier (SID):** Оскільки рядкові контексти безпеки (наприклад, `system_u:system_r:httpd_t:s0`) можуть досягати десятків байтів, порівняння рядків при кожному VFS-виклику знищило б продуктивність системи. FLASK увів 32-бітне ціле число — SID. Під час монтування файлової системи чи створення процесу Security Server присвоює кожному контексту унікальний цілочисельний SID, і всі внутрішні перевірки ядра виконуються через порівняння залишків та індексів SID у таблицях.
- **Access Vector Cache (AVC):** Ключовий компонент для оптимізації продуктивності. AVC зберігає результати попередніх рішень Security Server у швидкому кеші з дрібнозернистим блокуванням, дозволяючи виконувати понад 99% перевірок прав за кілька наносекунд без звернення до складних структур політики.

Архітектура FLASK продемонструвала дивовижну гнучкість. Оскільки ядро операційної системи повністю позбулося кодів інтерпретації правил, розробники отримали можливість замінювати або оновлювати політику безпеки у реальному часі без перезавантаження системи і без компіляції ядра.

## 4. Інтеграція SELinux у магістральне ядро Linux (2000–2003)

Наприкінці 2000 року NSA вирішило портувати архітектуру FLASK на операційну систему Linux. Проєкт отримав назву Security-Enhanced Linux (SELinux). Головними архітекторами портування з боку NSA виступили Стівен Смоллі (Stephen Smalley) та Рей Спенсер. Перший публічний реліз патчів SELinux відбувся у грудні 2000 року, а у червні 2001 року інженери NSA презентували систему спільноті на конференції USENIX Annual Technical Conference.

Початково патчі SELinux модифікували ядра Linux 2.4 у сотнях місць, вплітаючи прямо в код VFS, обробку сокетів та підсистему IPC прямі виклики функцій SELinux. Коли NSA запропонувало включити SELinux безпосередньо до магістрального ядра Linux 2.5, Лінус Торвальдс та ключові розробники ядра висловили рішуче заперечення:

> «Ми не можемо прийняти патч, який жорстко прив'язує ядро Linux до однієї конкретної системи безпеки. Завтра прийде інша група зі власною моделлю доступу, і ядро перетвориться на хаос із конфліктуючих перевірок.»

Для вирішення цієї проблеми у 2001–2002 роках спільнота ядра під керівництвом Кріса Райта (Chris Wright), Грега Кроа-Гартмана (Greg Kroah-Hartman), Стівена Смоллі та інженерів корпорації IBM створила фреймворк **Linux Security Modules (LSM)**.

LSM надав у загальних точках ядра (наприклад, `vfs_open`, `sys_execve`, `socket_create`) набір універсальних зворотних викликів (hooks). SELinux був переписаний як один із модулів LSM, який підключає свої обробники до цих гачків.

У грудні 2003 року відбувся реліз ядра **Linux 2.6.0**, у якому SELinux разом із LSM офіційно стали частиною магістрального ядра. У 2004–2005 роках Red Hat включила SELinux як стандартну систему захисту у дистрибутиви Fedora Core 2 (2004) та Red Hat Enterprise Linux 4 (RHEL 4, 2005), що зробило Type Enforcement базовим стандартом безпеки для серверних систем корпоративного класу.

Згодом, починаючи з версії Android 4.4 (а у суворому Enforcing режимі з Android 5.0 Lollipop), компанія Google адаптувала SELinux для захисту мобільної операційної системи Android (проєкт SEAndroid). Кожен додаток Android та кожен демон апаратного шару HAL отримує власний SELinux домен Type Enforcement (наприклад, `untrusted_app`, `platform_app`, `hal_camera_default`), що стало головним бар'єром проти розповсюдження мобільних шкідливих програм та підвищення привілеїв через вразливості драйверів пристроїв.
