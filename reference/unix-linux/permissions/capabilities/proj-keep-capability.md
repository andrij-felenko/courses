# ⚙️ Зберегти рівно одну можливість після зниження UID

Служба стартує від root, бо їй потрібен порт 443, і за мить мусить стати `nobody` — але так, щоб право ставати на низькі порти лишилося при ній. Наївне зниження забирає це право мовчки: усі виклики повертають нуль, числа в `/proc` міняються як належить, а `bind` після першого ж переналаштування падає з `Permission denied`. Нижче — послідовність, у якій можливість справді переживає зниження, той самий результат зовсім без коду, і чесна ціна кожного зі способів.

## Спершу — чи справді її треба зберігати

Прив'язаний сокет — це вже дескриптор, і привілей ядро перевіряє рівно один раз, усередині `bind`. Служба, яка стала на порт на старті й тримає той самий дескриптор до кінця життя, після зниження UID не втрачає нічого: можливість їй більше не знадобиться, тож і зберігати нема чого.

Потреба з'являється тоді, коли порт доводиться відкривати **вдруге** — уже непривілейованим. Найзвичніший привід — переналаштування за `SIGHUP`: у конфізі змінився перелік адрес, старі слухачі треба закрити, нові — відкрити. Ось тоді `CAP_NET_BIND_SERVICE` мусить дожити до тієї хвилини.

І тут дорогу заступають два правила ядра, що спрацьовують на самій зміні UID ([числа ідентичності процесу](book:unix-linux/uid-gid-model) — реальний, діючий і збережений UID, які міняють через `setresuid`). Перше: якщо хоч один із трьох UID був нулем, а після зміни всі три стали ненульовими, ядро вичищає **дозволені, діючі й навколишні** набори повністю. Друге, окреме: щойно діючий UID міняється з нуля на ненульовий, гасяться **діючі**.

Обидва правила існують заради сумісності — мільйони рядків старого коду роблять `setuid()` і мусять справді втрачати владу. Вимикач до них є, але він один і вимикає рівно половину: `PR_SET_KEEPCAPS` скасовує чистку дозволених у першому правилі — і другого не чіпає взагалі. Тому після зниження процес опиняється в стані, якого автор не чекав: дозволені на місці, діючі порожні, перевірка в ядрі бачить нуль. Підняти діючі назад мусить сама програма, і саме цей крок забувають найчастіше.

## Порядок, і чому він саме такий

Кожен крок стоїть на своєму місці не за смаком, а тому, що інакше не працює.

**Гранична стеля — першою.** `PR_CAPBSET_DROP` (з ядра 2.6.25) вимагає `CAP_SETPCAP` у діючих, а діючі повні лише поки процес — root. Пропустити цей крок спокусливо: адже дозволені ми й так звузимо до однієї назви. Але стеля обмежує не тільки нас: це маска того, що взагалі колись зможе потрапити в дозволені через `exec`. Лишивши її широкою, ми лишаємо відчиненою кватирку — будь-який запущений далі файл із власними позначками можливостей дістане їх сповна.

**Прапорець — до зниження.** `PR_SET_KEEPCAPS` міняє поведінку самого `setresuid`, тож піднімати його після нема сенсу: чистка вже сталася.

**Групи — перед користувачем.** Прибрати додаткові групи дозволено лише привілейованому, а після `setresuid` привілею вже нема.

**Звуження дозволених — після зниження, а не до нього.** Ось де інтуїція підводить найчастіше. Здається природним викинути зайве якнайраніше, ще від root. Але щоб знизити UID, потрібні `CAP_SETGID` і `CAP_SETUID` — і програма, яка завчасно лишила собі саму тільки `CAP_NET_BIND_SERVICE`, більше не має чим виконати власне зниження. Отже `capset` іде **після**, і той самий виклик робить одразу дві речі: обрізає дозволені до однієї назви й піднімає її в діючі.

**Звірка — читанням назад.** Питання не «чи повернув виклик нуль», а який набір бачить ядро.

## Код

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <errno.h>
#include <stdint.h>
#include <unistd.h>
#include <fcntl.h>
#include <grp.h>
#include <pwd.h>
#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <sys/syscall.h>
#include <sys/prctl.h>
#include <sys/wait.h>
#include <linux/capability.h>

#define CAPMASK(c) (1u << (c))       /* можливості 0..31 живуть у першому слові */
#define NBS        CAPMASK(CAP_NET_BIND_SERVICE)      /* номер 10, тобто 0x400 */

static uid_t g_uid = 65534;                       /* nobody, якщо бази не буде */
static gid_t g_gid = 65534;

/* capset/capget глібк не загортає — кличемо їх напряму.
   pid = 0 в заголовку означає «цей потік», і нічого іншого ядро не бере. */
static int caps_set(uint32_t permitted, uint32_t effective, uint32_t inheritable)
{
    struct __user_cap_header_struct h = { _LINUX_CAPABILITY_VERSION_3, 0 };
    struct __user_cap_data_struct   d[2];
    memset(d, 0, sizeof d);          /* друге слово — можливості 32..40: гасимо */
    d[0].permitted   = permitted;
    d[0].effective   = effective;
    d[0].inheritable = inheritable;
    return syscall(SYS_capset, &h, d);
}

static int caps_get(uint64_t *permitted, uint64_t *effective)
{
    struct __user_cap_header_struct h = { _LINUX_CAPABILITY_VERSION_3, 0 };
    struct __user_cap_data_struct   d[2];
    if (syscall(SYS_capget, &h, d) != 0) return -1;
    *permitted = ((uint64_t)d[1].permitted << 32) | d[0].permitted;
    *effective = ((uint64_t)d[1].effective << 32) | d[0].effective;
    return 0;
}

static void show(const char *label)
{
    uint64_t prm = 0, eff = 0;
    uid_t r, e, s;
    if (getresuid(&r, &e, &s) != 0 || caps_get(&prm, &eff) != 0) { perror("show"); return; }
    printf("    %-20s uid=%u/%u/%u  CapPrm=%016llx CapEff=%016llx\n",
           label, (unsigned)r, (unsigned)e, (unsigned)s,
           (unsigned long long)prm, (unsigned long long)eff);
}

/* Стеля: усе, що колись зможе потрапити в дозволені через exec.
   Звужувати її вільно лише тому, хто має CAP_SETPCAP у діючих, — тобто ще root. */
static int bound_to_only(int keep)
{
    int last = 40;
    FILE *f = fopen("/proc/sys/kernel/cap_last_cap", "r");
    if (f) { if (fscanf(f, "%d", &last) != 1) last = 40; fclose(f); }
    for (int c = 0; c <= last; c++) {
        if (c == keep) continue;
        if (prctl(PR_CAPBSET_DROP, c, 0, 0, 0) != 0 && errno != EINVAL) return -1;
    }
    return 0;
}

/* Кроки 1–3: звузити стелю, підняти прапорець, стати непривілейованим. */
static int drop_uid_keeping_caps(int keep)
{
    if (bound_to_only(keep)                != 0) return -1;
    if (prctl(PR_SET_KEEPCAPS, 1, 0, 0, 0) != 0) return -1;

    if (setgroups(1, &g_gid)               != 0) return -1;   /* групи — першими */
    if (setresgid(g_gid, g_gid, g_gid)     != 0) return -1;
    if (setresuid(g_uid, g_uid, g_uid)     != 0) return -1;   /* аж тепер користувач */
    return 0;
}

/* Кроки 4–5: лишити рівно одну назву, повернути її в діючі, звірити з ядром. */
static int narrow_caps_to(int keep)
{
    uint64_t prm = 0, eff = 0;
    uid_t r, e, s;

    if (caps_set(CAPMASK(keep), CAPMASK(keep), 0) != 0) return -1;
    if (prctl(PR_SET_KEEPCAPS, 0, 0, 0, 0)        != 0) return -1;

    if (caps_get(&prm, &eff) != 0)                      return -1;
    if (prm != CAPMASK(keep) || eff != CAPMASK(keep)) { errno = EPERM; return -1; }
    if (getresuid(&r, &e, &s) != 0)                     return -1;
    if (r != g_uid || e != g_uid || s != g_uid)       { errno = EPERM; return -1; }
    return 0;
}

static void try_bind(int port)
{
    struct sockaddr_in a;
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0) { perror("    socket"); return; }
    memset(&a, 0, sizeof a);
    a.sin_family = AF_INET;
    a.sin_port   = htons(port);
    a.sin_addr.s_addr = htonl(INADDR_ANY);
    printf("    bind(0.0.0.0:%d)     -> %s\n", port,
           bind(fd, (struct sockaddr *)&a, sizeof a) == 0 ? "порт наш" : strerror(errno));
    close(fd);
}

/* (1) Усе те саме, лише без одного рядка. */
static void scene_no_keepcaps(void)
{
    puts("[1] Без KEEPCAPS");
    show("до зниження:");
    if (setgroups(1, &g_gid)           != 0 ||
        setresgid(g_gid, g_gid, g_gid) != 0 ||
        setresuid(g_uid, g_uid, g_uid) != 0) { perror("    зниження"); _exit(1); }
    show("після зниження:");
    if (caps_set(NBS, NBS, 0) != 0)
        printf("    capset               -> %s  ← брати вже нема звідки\n", strerror(errno));
    try_bind(443);
}

/* (2) Стеля -> прапорець -> зниження -> capset -> звірка. */
static void scene_keepcaps(void)
{
    int fd;
    puts("[2] З KEEPCAPS");
    if (drop_uid_keeping_caps(CAP_NET_BIND_SERVICE) != 0) {
        printf("    зниження не вдалося: %s — тут служба мусить померти\n", strerror(errno));
        _exit(1);
    }
    show("після зниження:");
    if (narrow_caps_to(CAP_NET_BIND_SERVICE) != 0) {
        printf("    звуження не вдалося: %s — і тут теж\n", strerror(errno));
        _exit(1);
    }
    show("після capset:");
    try_bind(443);
    fd = open("/etc/shadow", O_RDONLY);
    printf("    /etc/shadow          -> %s\n", fd >= 0 ? "ВІДКРИТО" : strerror(errno));
    if (fd >= 0) close(fd);

    fflush(stdout);                       /* що дістанеться запущеному помічникові */
    execl("/bin/sh", "sh", "-c",
          "sed -n 's/^CapPrm:/    після exec: CapPrm/p' /proc/self/status", (char *)NULL);
    perror("    execl");
}

static void run(void (*scene)(void))
{
    pid_t pid = fork();                   /* зниження безповоротне: сцена — на процес */
    if (pid == 0) { scene(); _exit(0); }
    if (pid  > 0) waitpid(pid, NULL, 0);
    putchar('\n');
}

int main(void)
{
    struct passwd *pw = getpwnam("nobody");
    if (pw) { g_uid = pw->pw_uid; g_gid = pw->pw_gid; }
    if (geteuid() != 0) { puts("Потрібен root: усе цікаве починається з привілею."); return 1; }

    run(scene_no_keepcaps);
    run(scene_keepcaps);
    return 0;
}
```

## Як зібрати й запустити

```
cc -Wall -O2 -o keepcap keepcap.c
sudo ./keepcap
```

Бібліотек не треба: `capset` і `capget` глібк не загортає, тож системні виклики звемо самі, а структури беремо з заголовка ядра.

```
    capset               -> Operation not permitted  ← брати вже нема звідки
    bind(0.0.0.0:443)    -> Permission denied

[2] З KEEPCAPS
    після зниження:      uid=65534/65534/65534  CapPrm=000001ffffffffff CapEff=0000000000000000
    після capset:        uid=65534/65534/65534  CapPrm=0000000000000400 CapEff=0000000000000400
    bind(0.0.0.0:443)    -> порт наш
    /etc/shadow          -> Permission denied
    після exec: CapPrm:  0000000000000000
```

## Що саме тут гасне і чому

Перша сцена не зробила жодної помилки в самих викликах: `setgroups`, `setresgid` і `setresuid` повернули нуль, числа стали такими, як задумано. Вимкнулося дещо інше — спрацювало перше правило, і разом із нулями пішли самі повноваження. Тому наступний `capset` уперся не в брак прав, а в арифметику: **нові дозволені мусять бути підмножиною старих**, а старі щойно стали порожньою множиною. Порожня множина не має з чого дати `CAP_NET_BIND_SERVICE`, і ядро відповідає `EPERM`. Прикметно, що з `CAP_SETPCAP` це нічого не змінило б: правило підмножини не має винятків узагалі, дозволені можна тільки звужувати.

Друга сцена показує, чому одного прапорця мало. Після зниження `CapPrm` повний — прапорець спрацював, — а `CapEff` порожній, бо друге правило гасить діючі незалежно від нього. У цю мить служба вже нічого не може, хоч і має право все повернути. Виклик `capset` і є тим поверненням: одна назва в дозволених, вона ж у діючих, `0x400` — це біт номер 10, `CAP_NET_BIND_SERVICE`.

![Пʼять кроків зниження UID у двох стовпцях: без PR_SET_KEEPCAPS дозволені й діючі гаснуть на setresuid, capset падає з EPERM, bind — з EACCES; з прапорцем дозволені лишаються повними, діючі гасне окреме правило, capset звужує дозволені до однієї назви й піднімає її в діючі, bind проходить](/reference/unix-linux/permissions/capabilities/img/keepcaps-order.svg)

*Прапорець рятує лише дозволені — і без четвертого кроку служба лишається з правом, якого не ввімкнено.*

> 🔧 **Навіщо це.** Дві діагностики в полі розрізняються одним рядком у `/proc/<pid>/status`. `CapPrm=0000000000000000` означає, що можливість згоріла на зміні UID: шукати треба `PR_SET_KEEPCAPS`, якого нема. `CapPrm=0000000000000400` при порожньому `CapEff` означає протилежне — прапорець є, а `capset` після зниження ніхто не зробив. Розшифрувати маску вміє `capsh --decode=0000000000000400`, показати чужий процес — `getpcaps <pid>`.

## Те саме зовсім без коду

Сорок рядків вище існують лише тому, що процес **проходить через root**. Якщо його туди не пускати, обидва правила не спрацюють жодного разу — і зберігати не доведеться нічого.

Перший спосіб — позначка на самому файлі:

```
setcap cap_net_bind_service+ep /usr/local/bin/webd
getcap /usr/local/bin/webd
```

Літери означають набори на файлі: `p` — дозволені, `e` — той єдиний біт «діючий», що піднімає їх у діючі просто на старті. Служба запускається одразу від `webd`, ніколи не буває нулем, і можливість лежить у неї в наборах від першої інструкції. Живе позначка в [розширеному атрибуті](book:unix-linux/acl-and-xattr) `security.capability` — тобто не є частиною режиму файлу з усіма наслідками: `ls -l` її не покаже, `cp` без `--preserve=xattr` не перенесе, шар образу не збереже, файлова система без атрибутів мовчки не запише. І ще одне, дорожче: позначений файл переходить у захищений режим запуску, де ядро скидає `LD_PRELOAD` і `LD_LIBRARY_PATH` — програма з власними бібліотеками поруч просто не знайде їх і не стартує.

Другий спосіб — рядок у юніті [systemd](book:unix-linux/systemd-model):

```ini
[Service]
User=webd
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes
ExecStart=/usr/local/bin/webd
```

Менеджер служб робить іззовні рівно те, що робила наша програма зсередини, — і навіть той самий прапорець ставить сам: у документації прямо сказано, що разом з `AmbientCapabilities=` до `SecureBits=` автоматично додається `keep-caps`, «щоб зберегти можливості крізь зміну користувача». Ще він кладе назву в успадковувані, бо навколишньою вона без цього бути не може, і звіряється з граничною стелею — назви поза `CapabilityBoundingSet=` в навколишні не потраплять. Виконуваний файл при цьому лишається **непозначеним**: навколишні тим і цінні, що переживають `exec` без жодних позначок ([що взагалі переживає заміну образу](book:unix-linux/exec-semantics) — дескриптори переживають, повноваження за замовчуванням ні). Налаштування з'явилося в systemd 229 і вимагає ядра 4.3, де навколишній набір і завели.

| спосіб | хто дає можливість | що ламається | хто ще її дістає |
|---|---|---|---|
| код у службі | сама програма | нічого ззовні; ціна — сорок рядків, у яких легко переплутати порядок | ніхто: набір живе в одному процесі |
| `setcap` на файлі | ядро при `exec` | `cp`, архіви, шари образів, ФС без xattr, `LD_*` у середовищі | **кожен**, хто має право запустити цей файл |
| `AmbientCapabilities=` | менеджер служб перед `exec` | нічого; потрібні systemd ≥ 229 і ядро ≥ 4.3 | лише процеси цього юніта |

Стовпець «хто ще» й вирішує. Позначка на файлі — це право, видане **файлові**, а не службі: будь-хто, кому дозволено його запустити, дістане `CAP_NET_BIND_SERVICE` разом із ним. Рядок у юніті — право, видане одному юнітові, і зникає воно разом з ним. Тому за наявності менеджера служб перший вибір — юніт, `setcap` лишається для випадків, коли менеджера нема (утиліта, яку запускає людина з оболонки), а код у службі потрібен лише тоді, коли процес мусить побувати root по-справжньому — прочитати ключ, доступний тільки нулю, чи ввійти в простір імен, — і аж потім знизитися.

Найдешевша ж можливість — та, якої не треба зовсім: за [активації через сокет](book:unix-linux/socket-activation) порт відкриває сам менеджер служб і передає готовий дескриптор, а служба стартує непривілейованою й без жодної назви в наборах.

## На чому легко спіткнутися

**`capset` діє на потік, а не на процес.** Це не дрібниця реалізації: ядро взагалі не знає поняття «можливості процесу» — набори належать [задачі, тобто окремому потоку](book:unix-linux/threads-as-tasks). Зі зміною UID інакше: POSIX вимагає єдиної для процесу ідентичності, і глібк розсилає її всім потокам сигналом. Виходить перекіс — після зниження в багатопотоковій службі новий UID матимуть усі, а `CAP_NET_BIND_SERVICE` лише той потік, що викликав `capset`. Звідси залізне правило: усе зниження робити **до** створення потоків. Кому не щастить, у libcap від 2.27 є `libpsx`: зібрана з `-lpsx` бібліотека розсилає такі виклики всім потокам тим самим механізмом, що й глібк.

**Прапорець не передається у спадок.** `PR_SET_KEEPCAPS` гаситься на кожному `execve` — саме тому останній рядок досліду показує в запущеній оболонці порожній `CapPrm`. Дозволені заміну образу теж не переживають, тож передати можливість помічникові можна лише двома каналами: позначкою на його файлі або навколишнім набором.

**Стелю звужуємо, поки є чим.** Забути `PR_CAPBSET_DROP` легко, бо без нього все працює. Дірка відкривається пізніше й в іншому місці: широка стеля означає, що запущений із цієї служби файл із позначкою `setcap` дістане свої можливості сповна, хай сама служба має лише одну.

**Кожен код повернення — окремо.** `capset` падає з `EPERM`, коли дозволених уже нема; `prctl` — з `EINVAL` на старому ядрі; `setgroups` — коли привілею вже нема. Служба, яка після невдалого зниження продовжує роботу, продовжує її від імені root — і це той самий сценарій, через який колись горіли поштові демони.
