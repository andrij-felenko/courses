# 📋 Довідник інтерфейсів можливостей: виклики, поля, атрибут, утиліти

Повний контракт роботи з можливостями зібрано тут в одному місці: два системні виклики, якими ядро віддає й приймає набори, сім операцій `prctl`, п'ять рядків у `/proc`, один розширений атрибут на файлі та функції libcap, що ховають усе перелічене за зручнішими іменами. Підписи, числові значення констант і коди помилок — те, за чим інакше доводиться ходити по восьми різних сторінках man.

## Ядро: capget і capset

Ці два виклики порядкують рівно трьома наборами потоку — дозволеними, діючими, успадковуваними. Граничної стелі й навколишніх тут немає взагалі: до них веде `prctl`.

```c
#include <linux/capability.h>
#include <sys/syscall.h>

int syscall(SYS_capget, cap_user_header_t hdrp,       cap_user_data_t datap);
int syscall(SYS_capset, cap_user_header_t hdrp, const cap_user_data_t datap);
```

Обгорток у glibc немає навмисно: [бібліотека С](book:unix-linux/libc-as-gateway) — звичайний посередник між програмою й ядром, і саме ці два виклики вона лишила без прикриття, бо їхній контракт версіонований. Тож звертатися доводиться або через `syscall()`, або через libcap.

```c
typedef struct __user_cap_header_struct {
    __u32 version;      /* яку версію структури даних вживаємо */
    int   pid;          /* 0 = сам потік */
} *cap_user_header_t;

typedef struct __user_cap_data_struct {
    __u32 effective;
    __u32 permitted;
    __u32 inheritable;
} *cap_user_data_t;
```

Кожне поле — тридцять два біти, а можливостей більше. Звідси й три версії контракту: у другій і третій `datap` показує не на одну структуру, а на **масив із двох** — елемент `[0]` несе можливості 0–31, елемент `[1]` — від 32 і вище.

| Константа | Значення | Структур у масиві | З ядра | Стан |
|---|---|---|---|---|
| `_LINUX_CAPABILITY_VERSION_1` | `0x19980330` | 1 | 2.2 | лише перші 32 назви |
| `_LINUX_CAPABILITY_VERSION_2` | `0x20071026` | 2 | 2.6.25 | застаріла, не вживати |
| `_LINUX_CAPABILITY_VERSION_3` | `0x20080522` | 2 | 2.6.26 | чинна |

Друга й третя версії однакові за розкладкою: третю додали, щоб виправити хибу в самому оголошенні другої, а не формат даних. Число замість номера — це дата, коли версію зафіксували.

Питати ядро про версію не треба вгадуванням: воно саме назве бажану. Передайте заголовок із нульовою версією й `datap` рівним `NULL` — виклик впаде з `EINVAL` і **впише свою версію** у `hdrp->version`. Це єдиний випадок, коли `datap` дозволено лишити порожнім.

```c
struct __user_cap_header_struct hdr = { .version = 0, .pid = 0 };
syscall(SYS_capget, &hdr, NULL);      /* поверне -1, errno = EINVAL */
/* hdr.version тепер = 0x20080522 на будь-якому сучасному ядрі */
```

Щодо поля `pid`: `capget` дозволяє зазирнути в чужий потік, назвавши його TID, а `capset` — ні. З появою файлових можливостей право міняти набори іншого потоку з ядра прибрали, тож для `capset` `pid` мусить бути нулем або TID самого викликача; інакше `EPERM`.

## prctl: стеля, навколишні, вимикачі сумісності

Усе, чого немає в `capget`/`capset`, живе в `prctl`. Невживані аргументи мусять бути нулями — інакше `EINVAL`.

| Операція | № | arg2 | arg3 | Повертає | Треба мати | З ядра |
|---|---|---|---|---|---|---|
| `PR_CAPBSET_READ` | 23 | номер можливості | 0 | 1 або 0 | — | 2.6.25 |
| `PR_CAPBSET_DROP` | 24 | номер можливості | 0 | 0 | `CAP_SETPCAP` | 2.6.25 |
| `PR_GET_KEEPCAPS` | 7 | 0 | 0 | 1 або 0 | — | 2.2.18 |
| `PR_SET_KEEPCAPS` | 8 | 0 або 1 | 0 | 0 | — | 2.2.18 |
| `PR_GET_SECUREBITS` | 27 | 0 | 0 | маска | — | 2.6.26 |
| `PR_SET_SECUREBITS` | 28 | маска | 0 | 0 | `CAP_SETPCAP` | 2.6.26 |
| `PR_CAP_AMBIENT` | 47 | підоперація | залежить | залежить | — | 4.3 |

`PR_SET_KEEPCAPS` і біт `SECBIT_KEEP_CAPS` — це не два механізми, а дві двері до одного біта: `PR_GET_KEEPCAPS` буквально повертає стан того самого біта в масці securebits. Прапорець **гаситься при `exec`** — тримати дозволені він допомагає лише через зниження UID, не через заміну образу.

Підоперації `PR_CAP_AMBIENT` подають у `arg2`, а саму назву — у `arg3`:

| Підоперація | № | arg3 | Повертає | Коли `EPERM` |
|---|---|---|---|---|
| `PR_CAP_AMBIENT_IS_SET` | 1 | номер можливості | 1 або 0 | — |
| `PR_CAP_AMBIENT_RAISE` | 2 | номер можливості | 0 | назви немає **водночас** у дозволених і успадковуваних, або стоїть `SECBIT_NO_CAP_AMBIENT_RAISE` |
| `PR_CAP_AMBIENT_LOWER` | 3 | номер можливості | 0 | — |
| `PR_CAP_AMBIENT_CLEAR_ALL` | 4 | 0 | 0 | — |

Маска securebits складається з пар «біт рішення — біт замка»; замкнений біт більше не міняється до кінця життя процесу й переходить нащадкам.

| Прапорець | Маска | Що робить |
|---|---|---|
| `SECBIT_NOROOT` | `0x01` | UID 0 більше не дає можливостей автоматично |
| `SECBIT_NOROOT_LOCKED` | `0x02` | замикає попередній |
| `SECBIT_NO_SETUID_FIXUP` | `0x04` | зміна UID більше не чіпає наборів |
| `SECBIT_NO_SETUID_FIXUP_LOCKED` | `0x08` | замикає попередній |
| `SECBIT_KEEP_CAPS` | `0x10` | те саме, що `PR_SET_KEEPCAPS` |
| `SECBIT_KEEP_CAPS_LOCKED` | `0x20` | замикає попередній |
| `SECBIT_NO_CAP_AMBIENT_RAISE` | `0x40` | забороняє підіймати навколишні |
| `SECBIT_NO_CAP_AMBIENT_RAISE_LOCKED` | `0x80` | замикає попередній |

## Що видно у /proc

П'ять рядків у [`/proc/<pid>/status`](book:unix-linux/proc-filesystem) — найшвидший спосіб побачити всі набори живого процесу без жодного коду.

| Рядок | Набір | З ядра |
|---|---|---|
| `CapInh` | успадковувані | давно |
| `CapPrm` | дозволені | давно |
| `CapEff` | діючі | давно |
| `CapBnd` | гранична стеля | 2.6.26 |
| `CapAmb` | навколишні | 4.3 |

Кожен — шістнадцять шістнадцяткових цифр, тобто шістдесятичотирибітна маска, де біт номер *i* означає можливість номер *i*. Верхню межу того, що ядро взагалі знає, показує `/proc/sys/kernel/cap_last_cap` — сьогодні там 40, тобто назв сорок одна, і повна маска має вигляд `000001ffffffffff`.

![Шістнадцять шістнадцяткових цифр маски CapPrm; цифра «3» — четверта справа — розкладається на біти 15, 14, 13, 12 зі значеннями 0, 0, 1, 1, звідки виходять CAP_NET_ADMIN і CAP_NET_RAW](/reference/unix-linux/permissions/capabilities/img/hex-mask.svg)

*Розкладати маску вручну доводиться рідко: те саме робить `capsh --decode=`.*

## libcap: робоча копія й момент запису

Головна річ, яку варто знати про libcap, — де саме її функції торкаються ядра. Більшість не торкається зовсім: вони правлять `cap_t`, звичайну структуру в пам'яті процесу. Ядро дізнається про зміну лише в мить `cap_set_proc` або `cap_set_file`.

| Функція | Що робить | Де діє |
|---|---|---|
| `cap_get_proc()` | знімок трьох наборів потоку | ядро (`capget`) |
| `cap_get_pid(pid)` | те саме для чужого процесу | ядро (`capget`) |
| `cap_init()` | порожній стан | пам'ять |
| `cap_set_flag(cap, прапор, n, назви[], значення)` | піднімає чи гасить назви в копії | пам'ять |
| `cap_get_flag(cap, назва, прапор, &знач)` | питає одну назву | пам'ять |
| `cap_clear(cap)`, `cap_clear_flag(cap, прапор)` | чистить усе чи один набір | пам'ять |
| `cap_set_proc(cap)` | записує копію в ядро | ядро (`capset`) |
| `cap_get_file(шлях)`, `cap_set_file(шлях, cap)` | читає й пише позначку файлу | ядро (xattr) |
| `cap_get_fd(fd)`, `cap_set_fd(fd, cap)` | те саме через дескриптор | ядро (xattr) |
| `cap_from_text(рядок)`, `cap_to_text(cap, &len)` | текст ↔ `cap_t` | пам'ять |
| `cap_from_name(ім'я, &num)`, `cap_to_name(num)` | назва ↔ номер | пам'ять |
| `cap_get_bound(назва)`, `cap_drop_bound(назва)` | гранична стеля | ядро (`prctl`) |
| `cap_get_ambient(назва)`, `cap_set_ambient(назва, знач)`, `cap_reset_ambient()` | навколишні | ядро (`prctl`) |
| `cap_get_secbits()`, `cap_set_secbits(маска)` | securebits | ядро (`prctl`) |
| `cap_free(вказівник)` | звільняє `cap_t` **і** рядки від `cap_to_text` | пам'ять |

Прапор — це `CAP_EFFECTIVE`, `CAP_PERMITTED` або `CAP_INHERITABLE`; значення — `CAP_SET` або `CAP_CLEAR`. Найменша робоча програма (збирається як `cc prog.c -lcap`):

```c
#include <sys/capability.h>
#include <stdio.h>

int main(void) {
    cap_value_t want[] = { CAP_NET_RAW };
    cap_t caps = cap_get_proc();                          /* знімок із ядра */
    if (!caps) return 1;

    cap_set_flag(caps, CAP_EFFECTIVE, 1, want, CAP_SET);  /* лише копія */
    if (cap_set_proc(caps) != 0) {                        /* ось тут capset */
        perror("cap_set_proc");   /* EPERM: назви немає в дозволених */
        return 1;
    }
    char *txt = cap_to_text(caps, NULL);
    printf("%s\n", txt);                                  /* cap_net_raw=ep */
    cap_free(txt);
    cap_free(caps);
    return 0;
}
```

Текстовий запис, який розбирає `cap_from_text` і приймає `setcap`, будується з речень «список назв — дії». Дія — це оператор і літери наборів: `p` дозволені, `e` діючі, `i` успадковувані. Оператор `=` спершу **гасить** названі можливості в усіх трьох наборах, а тоді підіймає в тих, чиї літери стоять після нього; `+` і `-` вимагають явного списку й хоча б однієї літери. Слово `all` означає всі назви, а порожній список перед `=` — теж усі. Назви нечутливі до регістру, замість імені можна писати номер.

```
=                    порожньо в усіх трьох наборах
cap_net_raw+ep       підняти одну назву в дозволених і діючих
all=p                усе в дозволені, решта наборів порожня
cap_fowner+p-i       підняти в дозволених, зняти з успадковуваних
```

## Позначка на файлі: security.capability

Позначка живе в [розширеному атрибуті](book:unix-linux/acl-and-xattr) — парі «ім'я → байти» збоку від інода. Байти мають сталу розкладку, і всі числа в ній записані [від молодшого байта](book:programming/endianness) незалежно від того, як влаштований процесор.

![Три ревізії атрибута security.capability у байтах: спільне поле magic_etc, далі пари permitted/inheritable — одна в першій ревізії, дві в другій і третій, а третя додає в кінці поле rootid](/reference/unix-linux/permissions/capabilities/img/xattr-layout.svg)

*Пари «дозволені — успадковувані» йдуть упереміш, а не двома окремими блоками.*

```c
struct vfs_ns_cap_data {
    __le32 magic_etc;                 /* ревізія | 0x000001, якщо біт «діючий» */
    struct {
        __le32 permitted;
        __le32 inheritable;
    } data[VFS_CAP_U32];              /* 1 у ревізії 1, 2 у ревізіях 2 і 3 */
    __le32 rootid;                    /* лише ревізія 3 */
};
```

| Ревізія | `magic_etc` | Розмір | З ядра | Що додала |
|---|---|---|---|---|
| `VFS_CAP_REVISION_1` | `0x01000000` | 12 Б | 2.6.24 | перші 32 назви |
| `VFS_CAP_REVISION_2` | `0x02000000` | 20 Б | 2.6.25 | усі 64 біти |
| `VFS_CAP_REVISION_3` | `0x03000000` | 24 Б | 4.14 | `rootid` — кореневий UID [простору імен](book:unix-linux/namespaces), поза яким позначка не діє |

Біт `VFS_CAP_FLAGS_EFFECTIVE` (`0x000001`) домішується до `magic_etc` — він один на весь файл. Звідси й правило libcap, об яке спотикаються найчастіше: якщо в тексті стоїть хоч одне `e`, воно мусить покривати **все** об'єднання дозволених і успадковуваних, інакше `cap_set_file` відмовляє з `EINVAL`. Записати `cap_net_raw+ep cap_chown+p` одним атрибутом просто нема куди.

## Утиліти

| Команда | Що робить |
|---|---|
| `getcap ФАЙЛ` | показує позначку; `-r` рекурсивно, `-v` перевіряє, `-n` показує `rootid` |
| `setcap 'ТЕКСТ' ФАЙЛ` | ставить позначку; треба `CAP_SETFCAP` |
| `setcap -r ФАЙЛ` | знімає позначку зовсім |
| `setcap -n UID 'ТЕКСТ' ФАЙЛ` | пише ревізію 3 з чужим `rootid` |
| `getpcaps PID…` | набори живого процесу (через `capget`, не через `/proc`) |
| `capsh --print` | усе про поточний процес: набори, стеля, securebits |
| `capsh --decode=0x3000` | маска → назви |
| `capsh --drop=cap_sys_module -- -c 'КОМАНДА'` | зрізає зі стелі й запускає |
| `capsh --supports=cap_bpf` | чи знає ядро таку назву (інакше код виходу 1) |

Порожня позначка — не те саме, що знята. Файл із порожньою позначкою ядро вважає привілейованим, тому при `exec` гасить навколишні й не дає нічого: це спосіб гарантувати, що програма стартує геть без привілею.

## Коди повернення

| Код | Де його бачать | Причина |
|---|---|---|
| `EINVAL` | `capget`, `capset` | незнана `version`; ядро при цьому вписує свою в `hdrp->version` |
| `EINVAL` | `prctl` | номер можливості вище за `cap_last_cap`; ненульові невживані аргументи |
| `EINVAL` | `cap_set_file` | біт «діючий» не покриває всього об'єднання дозволених і успадковуваних |
| `EPERM` | `capset` | додати в дозволені те, чого там не було; підняти в діючі те, чого немає в дозволених; чужий потік |
| `EPERM` | `PR_CAPBSET_DROP`, `PR_SET_SECUREBITS` | немає `CAP_SETPCAP` або біт уже замкнено |
| `EPERM` | `PR_SET_KEEPCAPS` | стоїть `SECBIT_KEEP_CAPS_LOCKED` |
| `EPERM` | `PR_CAP_AMBIENT_RAISE` | назви немає в дозволених або в успадковуваних |
| `EPERM` | `cap_set_file` | немає `CAP_SETFCAP` |
| `ENODATA` | `cap_get_file` | на файлі просто немає атрибута — це «позначки нема», а не поломка |
| `EOPNOTSUPP` | `cap_set_file` | файлова система не тримає розширених атрибутів |
| `ESRCH` | `capget` | такого потоку немає |
| `EFAULT` | `capget`, `capset` | `hdrp` порожній; `datap` дозволено лишити порожнім лише при промацуванні версії |

Одна пастка тут не про можливості, а про звичку: `cap_get_proc` повертає `NULL`, а не число, і [`errno`](book:programming/errno) в такому разі варто читати одразу, бо наступний виклик libcap його перепише.
