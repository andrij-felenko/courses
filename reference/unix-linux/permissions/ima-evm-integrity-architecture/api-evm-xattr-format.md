# 📋 Структура розширених атрибутів security.ima та security.evm

Підсистеми цілісності IMA та EVM зберігають криптографічні дані про стан файлів безпосередньо в іноді файлової системи за допомогою розширених атрибутів файлів (extended attributes, xattrs) у захищеному просторі імен `security.*`. Ядро Linux інтерпретує ці атрибути як бінарні структури даних із заголовочним байтом типу, який визначає формат упакованих даних та криптографічний алгоритм.

Використання розширених атрибутів дозволяє прив'язати цілісність до конкретного об'єкта файлової системи без введення зовнішніх баз даних чи окремих індексних файлів. Проте бінарний формат розширених атрибутів вимагає строгой структуризації: перший байт кожного атрибута діє як дискримінатор типу (type tag), який повідомляє ядру, як саме інтерпретувати решту байтів — як простий сирий дайджест, як розширений дайджест нового покоління чи як підписаний асиметричний контейнер.

## Формат розширеного атрибута security.ima

Атрибут `security.ima` зберігає або очікуваний криптографічний хеш вмісту файлу, або цифровий підпис (асиметричний). Перший байт атрибута визначає тип заголовочної структури та формат подальших байтів.

### Перелік типів заголовків (evm_ima_xattr_type)

У вихідному коді ядра Linux (`include/linux/integrity.h`) визначено наступні типи заголовочних значень для атрибутів цілісності:

:::tabs
```c
/* Визначення заголовків атрибутів у C (kernel/uapi header) */
enum evm_ima_xattr_type {
    IMA_XATTR_DIGEST = 0x01,       /* Простий хеш SHA-1 (застарілий формат) */
    EVM_IMA_XATTR_DIGEST = 0x01,   /* Синтаксичний синонім для сумісності */
    EVM_IMA_XATTR_DIGEST_NG = 0x02,/* Хеш із зазначенням алгоритму (Next Generation) */
    EVM_SIGNATURE_EVM = 0x03,      /* Симетричний HMAC EVM над метаданими */
    EVMSIG_XATTR_DIGEST = 0x04,    /* Асиметричний цифровий підпис (v2/v3) */
    IMA_ASYM_DIGSIG = 0x05,        /* Асиметричний підпис IMA (NextGen) */
};
```
```cpp
// Ідіоматичний еквівалент типів атрибутів у C++20
enum class EvmImaXattrType : uint8_t {
    DigestLegacy = 0x01,
    DigestNg     = 0x02,
    EvmHmac      = 0x03,
    EvmSignature = 0x04,
    ImaAsymSig   = 0x05
};
```
:::

Тип `IMA_XATTR_DIGEST` (0x01) вважається застарілим, оскільки він жорстко припускає використання алгоритму SHA-1 без вказівки довжини або алгоритму в заголовку. Сучасні дистрибутиви застосовують типи `0x02` (для сирих хешів) та `0x04`/`0x05` (для цифрових підписів).

### Бінарна структура EVM_IMA_XATTR_DIGEST_NG (тип 0x02)

Формат `DIGEST_NG` (Next Generation) застосовується у випадках, коли в атрибуті зберігається необроблений дайджест файлу без асиметричного цифрового підпису. Він містить ідентифікатор алгоритму хешування, що дозволяє ядру динамічно обирати відповідний криптографічний трансформатор у фреймворку `Crypto API`.

| Зсув (байтовий) | Поле | Тип даних | Опис та значення |
| :--- | :--- | :--- | :--- |
| `0x00` | `type` | `uint8_t` | Завжди `0x02` (`EVM_IMA_XATTR_DIGEST_NG`). |
| `0x01` | `algo` | `uint8_t` | Ідентифікатор алгоритму хешування (enum `hash_algo` в ядрі). |
| `0x02..N` | `digest[]` | `uint8_t[]` | Необроблені байти дайджесту (наприклад, 32 байти для SHA-256 або 64 байти для SHA-512). |

Значення поля `algo` відповідає системному переліку `enum hash_algo`:
- `0` (`HASH_ALGO_MD5`): MD5 (не рекомендується).
- `1` (`HASH_ALGO_SHA1`): SHA-1 (історичний дефолт).
- `2` (`HASH_ALGO_RIPE_MD160`): RIPEMD-160.
- `4` (`HASH_ALGO_SHA256`): SHA-256 (сучасний стандарт).
- `5` (`HASH_ALGO_SHA384`): SHA-384.
- `6` (`HASH_ALGO_SHA512`): SHA-512.

### Бінарна структура EVMSIG_XATTR_DIGEST (тип 0x04 / 0x05)

Коли файл підписується закритим ключем розробника (за допомогою утиліти `evmctl`), атрибут `security.ima` пакується у бінарний контейнер `signature_v2_hdr`:

:::tabs
```c
/* Опис заголовка підпису у C */
struct signature_v2_hdr {
    uint8_t type;        /* EVMSIG_XATTR_DIGEST (0x04) або IMA_ASYM_DIGSIG (0x05) */
    uint8_t version;     /* Версія заголовка (зазвичай 2) */
    uint8_t hash_algo;   /* Алгоритм хешування (enum hash_algo, наприклад 4 для SHA-256) */
    uint32_t keyid;      /* Big-endian Key ID відкритого ключа у системному брелоку .ima */
    uint16_t sig_size;   /* Big-endian розмір цифрового підпису в байтах */
    uint8_t sig[];       /* Сирі байти цифрового підпису (PKCS#1 v1.5 RSA або ECDSA) */
} __attribute__((packed));
```
```cpp
// Ідіоматична C++20 структура з упакованим вирівнюванням
#pragma pack(push, 1)
struct SignatureV2Hdr {
    uint8_t type;
    uint8_t version;
    uint8_t hash_algo;
    uint32_t keyid;      // Big-endian Key ID
    uint16_t sig_size;   // Big-endian розмір підпису
};
#pragma pack(pop)
```
:::

Поле `keyid` являє собою останні 4 байти ідентифікатора відкритого ключа (Key ID / SKID з X.509 сертифіката). Це дозволяє ядру не перебирати всі сертифікати у брелоку `.ima`, а миттєво знайти потрібний відкритий ключ за його хеш-ідентифікатором при виконанні системного виклику.

## Формат розширеного атрибута security.evm

Атрибут `security.evm` призначений для криптографічного захисту метаданих файлу від офлайн-підміни та маніпуляцій із розширеними атрибутами безпеки інших модулів LSM.

### Склад полів для обчислення дайджесту EVM

Обчислення дайджесту EVM охоплює чітко визначену послідовність розширених атрибутів та внутрішніх полів inode:

1. **Захищені розширені атрибути** (у суворій алфавітній послідовності назв атрибутів):
   - `security.capability` — сфокусовані можливості Linux (Capabilities).
   - `security.ima` — атрибут оцінки цілісності IMA.
   - `security.selinux` — контекст безпеки SELinux.
   - `security.SMACK64` — мітка контролю доступу SMACK (якщо ввімкнено).
2. **Структурні метадані inode** (`struct h_integrity_metadata` у ядрі):
   - `i_ino` (`uint64_t`) — унікальний номер inode у файловій системі.
   - `i_generation` (`uint32_t`) — номер генерації inode (запобігає reuse-атакам).
   - `i_uid` (`uint32_t`) — ідентифікатор користувача-власника.
   - `i_gid` (`uint32_t`) — ідентифікатор групи-власника.
   - `i_mode` (`uint16_t`) — маска прав доступу (включаючи SUID/SGID).

### Бінарна структура security.evm для HMAC (тип 0x03)

У стандартному робочому режимі із симетричним HMAC атрибут `security.evm` має наступний бінарний вигляд:

| Зсув (байтовий) | Поле | Тип даних | Опис |
| :--- | :--- | :--- | :--- |
| `0x00` | `type` | `uint8_t` | Завжди `0x03` (`EVM_SIGNATURE_EVM`). |
| `0x01` | `algo` | `uint8_t` | Алгоритм хешування HMAC (наприклад, `0x04` для SHA-256). |
| `0x02..N` | `hmac[]` | `uint8_t[]` | 32 байти значення HMAC-SHA256, обчисленого з використанням майстер-ключа EVM. |

### Огляд системних брелоків ключів ядра (Keyring Interface)

Для валідації підписів ядро Linux створює спеціалізовані брелоки ключів у підсистемі Keyrings:

- **`.ima`**: Системний брелок для збереження X.509 сертифікатів відкритих ключів, якими підписуються атрибути `security.ima`. Завантаження ключів можливе лише під час раннього завантаження (в initramfs), після чого брелок зв'язується та блокується від подальших модифікацій.
- **`.evm`**: Брелок для ключів верифікації атрибута `security.evm` (симетричних HMAC або асиметричних ключів).
- **`.builtin_trusted_keys`**: Вбудовані відкриті ключі розробників ядра, вкомпільовані безпосередньо у бінарний образ `vmlinuz`.
- **`.platform`**: Ключі, завантажені з таблиць системного прошивки UEFI (бази даних Secure Boot `db` та `MOK`).
