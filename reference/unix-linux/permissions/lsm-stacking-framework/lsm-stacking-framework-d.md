# Каркас модулів безпеки Linux (LSM Hooks)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Система Linux Security Modules (LSM) є однією з найважливіших архітектурних складових ядра Linux у контексті безпеки. Вона надає гнучкий, розширюваний і стандартизований інтерфейс для імплементації різних моделей контролю доступу без необхідності безпосередньо модифікувати основний код ядра. У цій статті ми детально розглянемо історію створення LSM, його архітектуру, анатомію хуків (hooks), принципи роботи механізму стекінгу (stacking) та процес розробки власних модулів безпеки.

## Вступ до Linux Security Modules

Історично ядро Linux покладалося на традиційну модель контролю доступу Discretionary Access Control (DAC), засновану на правах власників файлів (user, group, others) та списках контролю доступу (POSIX ACL). Однак, з розвитком кіберзагроз і зростанням потреб у корпоративних та військових секторах, DAC виявилося недостатньо. Виникла потреба в Mandatory Access Control (MAC) — мандатному контролі доступу, де політики безпеки нав'язуються системою централізовано і не можуть бути змінені звичайними користувачами.

У 2001 році на саміті розробників ядра (Kernel Summit) АНБ (NSA) запропонувало включити свою розробку Security-Enhanced Linux (SELinux) безпосередньо в основне ядро. Лінус Торвальдс та інші провідні розробники відмовилися жорстко прив'язувати ядро до однієї конкретної моделі MAC. Замість цього було вирішено створити загальний інтерфейс, який би дозволив будь-якій моделі безпеки інтегруватися з ядром у вигляді модулів. Так народився фреймворк Linux Security Modules.

Перша реалізація LSM з'явилася в ядрі 2.6.0. З того часу архітектура суттєво еволюціонувала: було додано підтримку кількох одночасно працюючих модулів (stacking), розширено перелік точок перехоплення (hooks), а самі модулі згодом перестали бути завантажуваними модулями ядра (LKM) у класичному розумінні, ставши статично скомпільованими компонентами задля уникнення атак типу "rootkit".

## Архітектура та дизайн LSM

Дизайн LSM ґрунтується на концепції "перехоплення" (hooking). Ядро Linux наповнене сотнями точок, де приймаються важливі рішення щодо доступу: відкриття файлу, створення сокета, виділення пам'яті, зміна прав, відправка сигналу процесу тощо.

Замість того, щоб вбудовувати складну логіку перевірок безпосередньо в системні виклики або підсистеми віртуальної файлової системи (VFS), ядро просто викликає відповідну функцію-хук LSM перед тим, як виконати дію. Якщо модуль безпеки повертає помилку (наприклад, `-EACCES` або `-EPERM`), дія блокується і системний виклик завершується з відповідною помилкою для користувацького простору.

![Архітектура LSM](/reference/unix-linux/permissions/lsm-stacking-framework/img/lsm-architecture.svg)
*Рис. 1. Базова архітектура Linux Security Modules.*

Ключові принципи архітектури LSM:
1. **Зосередженість на об'єктах:** Хуки розміщені на рівні роботи з внутрішніми об'єктами ядра (inodes, file, task_struct, socket), а не на рівні інтерфейсу системних викликів. Це запобігає атакам типу TOCTOU (Time-of-Check to Time-of-Use).
2. **Restrictive by default (обмежувальні за замовчуванням):** LSM може лише обмежити доступ, який вже дозволений DAC. LSM ніколи не може надати доступ до об'єкта, якщо базова перевірка прав DAC (власник/група) відмовила у доступі.
3. **Непрозорі вказівники на дані (Opaque pointers):** Структури ядра мають спеціальні поля `void *security`, які модулі LSM використовують для збереження своїх внутрішніх контекстів безпеки (security context / SID).
4. **Мінімальний вплив на продуктивність:** Якщо модуль не активований, виклик хука зазвичай зводиться до простої inline-функції, яка швидко повертає 0.

## Анатомія struct security_hook_heads

У серці LSM лежить структура `security_hook_heads`, визначена у файлі `include/linux/lsm_hooks.h`. Вона містить списки для кожного доступного хука.

```c
struct security_hook_heads {
    #define LSM_HOOK(RET, DEFAULT, NAME, ...) struct hlist_head NAME;
    #include "linux/lsm_hook_defs.h"
    #undef LSM_HOOK
};
```

Макрос `LSM_HOOK` зчитує всі визначення хуків з `lsm_hook_defs.h` і створює для кожного з них заголовок хеш-списку (`struct hlist_head`).

Приклади найважливіших хуків:

### Файлова система (VFS)
- `security_inode_permission(struct inode *inode, int mask)`: Перевіряє права на читання, запис або виконання inode.
- `security_file_open(struct file *file)`: Викликається під час відкриття файлу. Це один з найчастіше використовуваних хуків у політиках MAC.
- `security_file_receive(struct file *file)`: Важливий хук для захисту від передачі файлових дескрипторів через Unix domain sockets.

### Управління процесами (Tasks)
- `security_task_alloc(struct task_struct *task, unsigned long clone_flags)`: Викликається при створенні нового процесу (fork/clone).
- `security_task_kill(struct task_struct *p, struct kernel_siginfo *info, int sig, const struct cred *cred)`: Перевіряє право одного процесу надсилати сигнал іншому.
- `security_cred_prepare(struct cred *new, const struct cred *old, gfp_t gfp)`: Викликається перед зміною облікових даних процесу (наприклад, при `setuid`).

### Мережа (Networking)
- `security_socket_create(int family, int type, int protocol, int kern)`: Контролює право процесу на створення сокета певного типу та протоколу.
- `security_socket_connect(struct socket *sock, struct sockaddr *address, int addrlen)`: Перевіряє спробу з'єднання з віддаленим вузлом.

Кожен хук має свою сигнатуру і очікує повернення цілого числа (`int`), де `0` означає успіх, а від'ємне значення (наприклад, `-EACCES`) — відмову у доступі.

## LSM Stacking (Стекування)

Ранні версії LSM підтримували лише один активний модуль безпеки (так званий "major" модуль), плюс можливості модулів меншого масштабу (minor), таких як Yama або LoadPin. Якщо система використовувала SELinux, вона не могла одночасно використовувати AppArmor.

Починаючи з версії ядра 5.1 (2019 рік), була представлена повноцінна підтримка LSM Stacking, над якою розробник Кес Кук (Kees Cook) та інші працювали багато років. Стекування дозволяє кільком модулям безпеки працювати одночасно і незалежно перевіряти доступ.

![LSM Stacking](/reference/unix-linux/permissions/lsm-stacking-framework/img/lsm-stacking.svg)
*Рис. 2. Ланцюг викликів при використанні LSM Stacking.*

### Як працює стекування?
Коли ядро ініціалізується, воно зчитує конфігурацію модулів (з параметрів завантаження або значень за замовчуванням). Кожен активований модуль реєструє свої функції у відповідних списках `hlist_head` структури `security_hook_heads`.

Під час роботи ядра, коли викликається, наприклад, `security_file_open`, фреймворк LSM проходить по списку всіх зареєстрованих функцій для цього хука.
Логіка перевірки така (у спрощеному вигляді):
```c
int security_file_open(struct file *file)
{
    int ret = 0;
    struct security_hook_list *hp;

    hlist_for_each_entry(hp, &security_hook_heads.file_open, list) {
        ret = hp->hook.file_open(file);
        if (ret)
            break; // Short-circuit: якщо один модуль заборонив, далі не перевіряємо
    }
    return ret;
}
```
Якщо хоч один модуль у стеку повертає помилку, перевірка негайно припиняється (short-circuit), і системний виклик відхиляється. Це гарантує найвищий рівень безпеки: доступ надається лише тоді, коли **усі** активні модулі LSM дозволили його (логічне "І").

### Спільне використання контексту (`secid` та `secctx`)
Найскладнішою проблемою при реалізації стекінгу було управління пам'яттю для полів `security` всередині об'єктів (вказівників на контексти). Раніше один модуль цілком володів вказівником. Тепер фреймворк виділяє один великий блок пам'яті (blob), який містить контексти для всіх активних модулів. Кожен модуль отримує своє зміщення (offset) у цьому блоці, щоб зберігати власні дані, не заважаючи іншим.

## Популярні модулі LSM

Сучасне ядро Linux включає кілька офіційних "великих" і "малих" модулів LSM:

1. **SELinux (Security-Enhanced Linux):** Найстаріший, найскладніший і найбільш гнучкий модуль. Використовує політики на основі типів (Type Enforcement) та міток. Standard de facto у дистрибутивах сімейства Red Hat (Fedora, RHEL, CentOS) та ОС Android.
2. **AppArmor:** Модуль, що базується на шляхах (path-based MAC). Значно простіший у налаштуванні, ніж SELinux. Активно використовується в Ubuntu, Debian, SUSE.
3. **Smack (Simplified Mandatory Access Control Kernel):** Спрощена реалізація MAC, популярна у вбудованих системах, зокрема в Tizen та Automotive Grade Linux.
4. **TOMOYO:** Ще одна path-based система, яка відрізняється здатністю до автоматичного навчання (learning mode), будуючи дерево можливих дій програми.
5. **Yama:** "Малий" модуль, який спеціалізується на обмеженні системного виклику `ptrace()`, не даючи процесам підключатися як зневаджувачі до інших процесів без явної спорідненості (descendant relationship).
6. **LoadPin:** Гарантує, що всі модулі ядра, прошивки (firmware) та kexec-образи завантажуються з однієї захищеної (наприклад, read-only) файлової системи.
7. **SafeSetID:** Дозволяє безпечніше переходити між UID без необхідності надавати процесу можливості `CAP_SETUID`.
8. **Lockdown:** Блокує можливість навіть користувача root модифікувати ядро в пам'яті, коли включено UEFI Secure Boot.
9. **Landlock:** Новий (з ядра 5.13) unprivileged LSM. Дозволяє звичайним програмам (навіть без прав root) ізолювати себе (створювати пісочниці), обмежуючи доступ до файлової системи для себе та своїх нащадків.

## Управління LSM: Параметри ядра та `lsm=`

Порядок, у якому ініціалізуються та викликаються модулі LSM, можна налаштовувати під час завантаження ядра через параметр `lsm=`.
Значення цього параметра — це список модулів, розділених комами, у порядку їхнього виконання.

Наприклад:
```text
lsm=lockdown,yama,loadpin,safesetid,integrity,smack,selinux,apparmor,bpf
```

Слід пам'ятати, що ядро повинно бути скомпільовано з підтримкою цих модулів (наприклад, `CONFIG_SECURITY_SELINUX=y`). Якщо в параметрі `lsm=` вказано модуль, якого немає в ядрі, він буде проігнорований.

Якщо параметр не задано, використовується порядок за замовчуванням, визначений конфігурацією ядра під час збірки (зазвичай `CONFIG_LSM`). Змінити конфігурацію "на льоту" (після завантаження системи) неможливо — це фундаментальна вимога безпеки.

## LSM на базі eBPF (BPF-LSM)

Одним з найпотужніших нововведень у сфері Linux-безпеки останніх років стала поява BPF-LSM (інтегровано в ядро 5.7).
BPF (Berkeley Packet Filter), а точніше його сучасна розширена версія eBPF, дозволяє безпечно виконувати кастомний байт-код всередині ядра без його перекомпіляції та без завантаження зовнішніх модулів ядра (LKM).

BPF-LSM об'єднує міць eBPF та фреймворку LSM. Він дозволяє прикріплювати BPF-програми безпосередньо до будь-яких хуків `security_hook_heads`.

### Переваги BPF-LSM
1. **Динамічність:** Політики можна оновлювати, додавати та знімати "на льоту" з користувацького простору.
2. **Програмованість:** Замість написання статичних правил (як у SELinux), адміністратор пише логіку (на C, Rust, чи через інструменти на кшталт Cilium Tetragon). BPF-програма може перевіряти стан системи, читати структури ядра, вести складну статистику.
3. **Безпека:** Перед виконанням BPF-код проходить жорстку перевірку BPF Verifier у ядрі, яка гарантує відсутність нескінченних циклів, доступу до невідповідної пам'яті або краху ядра (kernel panic).

Приклад сценарію: заборонити виконання певного двійкового файлу лише з певної IP-адреси мережі. Створити таке правило у стандартному AppArmor чи SELinux може бути складно або неможливо через відсутність доступу до стану мережі у файловому хуці. З BPF-LSM програма може отримати доступ до необхідних контекстів за допомогою BPF helpers.

## Програмування та розробка власних LSM

Хоча BPF-LSM робить створення кастомних політик простішим, іноді є потреба розробити повноцінний in-tree (вбудований у ядро) LSM модуль.

### Базові кроки розробки in-tree LSM
1. **Визначення структури:** Створюється директорія `security/my_lsm/`.
2. **Реєстрація хуків:** Пишеться масив структур `security_hook_list`.
```c
static struct security_hook_list my_hooks[] __lsm_ro_after_init = {
    LSM_HOOK_INIT(file_open, my_file_open_hook),
    LSM_HOOK_INIT(socket_create, my_socket_create_hook),
};
```
3. **Ініціалізація:** Пишеться функція ініціалізації, яка викликає `security_add_hooks()`.
```c
static int __init my_lsm_init(void)
{
    security_add_hooks(my_hooks, ARRAY_SIZE(my_hooks), "my_lsm");
    pr_info("My_LSM: initialized\n");
    return 0;
}
DEFINE_LSM(my_lsm) = {
    .name = "my_lsm",
    .init = my_lsm_init,
};
```
4. **Конфігурація (Kconfig):** Додається запис до системи складання Kconfig, щоб модуль можна було обрати під час `make menuconfig`.
5. **Компіляція:** Перезбирається ядро і модуль стає частиною стеку.

## Висновки та майбутнє розвитку LSM

Фреймворк Linux Security Modules пройшов довгий шлях від простого інтерфейсу для підтримки SELinux до складної системи стекування, яка дозволяє об'єднувати сильні сторони різних модулів в єдиній системі. 

Стекування дозволило дистрибутивам впроваджувати множинні рівні захисту. Наприклад, контейнерні технології (Docker, Kubernetes) можуть покладатися на AppArmor для ізоляції контейнерів, в той час як система в цілому використовує Yama для захисту від ptrace-атак та Lockdown для захисту самого ядра, і все це працює паралельно без конфліктів.

Розвиток BPF-LSM та unprivileged-LSM (таких як Landlock) відкриває нову еру в безпеці Linux, передаючи контроль над політиками доступу від статичних конфігурацій системного адміністратора безпосередньо розробникам додатків та динамічним системам оркестрації. Завдяки модульній і розширюваній природі LSM, ядро Linux залишатиметься надійним фундаментом для захищених систем у майбутньому.
