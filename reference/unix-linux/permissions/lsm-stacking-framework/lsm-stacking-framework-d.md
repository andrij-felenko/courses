Класична модель розмежування доступу в операційних системах Unix — Discretionary Access Control (DAC) — опирається на ідентифікатори користувачів (UID), груп (GID) та біти режимів файлів (`rwxrwxrwx`). У цій традиційній схемі процес, запущений від імені суперкористувача (`root` з UID 0), володіє повністю необмеженими правами над усім системним середовищем. Якщо мережевий демон, вебсервер або служба управління контейнерами містить вразливість витоку пам'яті чи виконання довільного коду (Remote Code Execution, RCE), зловмисник, захопивши привілейований процес, миттєво отримує повний контроль над дисковими накопичувачами, мережевими сокетами, таблицями маршрутизації та адресним простором інших процесів у системі.

Навіть розбиття монолітного всевладдя суперкористувача на атомарні можливості (POSIX Capabilities, такі як `CAP_NET_ADMIN`, `CAP_SYS_PTRACE` чи `CAP_DAC_OVERRIDE`) не вирішує фундаментальної проблеми централізованого нав'язування правил: у моделі DAC власник об'єкта чи привілейований процес усе одно володіє правом змінити атрибути доступу на власний розсуд (discretionary). Якщо процес має право запису у файл, він може змінити його маску доступу `chmod 0777` чи передати право володіння сторонньому користувачеві.

Для побудови справді захищених ОС виникла потреба в мандатному контролі доступу (Mandatory Access Control, MAC). У моделі MAC системний адміністратор визначає глобальну, незмінну політику безпеки, яку ядро безумовно застосовує до всіх суб'єктів (процесів) та об'єктів (файлів, сокетів, IPC, ключів). Жоден користувач — включно із суперкористувачем `root` — не може послабити, обійти чи змінити ці правила з простору користувача.

Проте спроба вбудувати одну конкретну реалізацію MAC безпосередньо в код підсистем ядра Linux викликала сувору відмову спільноти розробників ядра. Корпорація Red Hat та NSA просували підсистему SELinux із її гнучкою моделлю розмежування за типами (Type Enforcement), компанії Canonical та Novell/SUSE віддавали перевагу простішій у налаштуванні системі AppArmor, орієнтованій на шляхи у файловій системі, а у вбудованих та автомобільних пристроях застосовували Smack. Щоб уникнути розколу ядра на конкуруючі форки та запобігти хардкоду сотень спеціалізованих перевірок у VFS чи мережевому стеку, розробники ядра під керівництвом Лінуса Торвальдса створили уніфіковану підсистему Linux Security Modules (LSM) та механізм стекування модулів безпеки (LSM Stacking).

## Обмежувальна модель перехоплення (Restrictive Hooks)

Фундаментальний принцип LSM (англ. *Linux Security Modules* — модулі безпеки Linux) полягає в тому, що ядро надає стандартизовані точки перехоплення — гачки (англ. *hooks* — гаки, зачіпи) — у критичних місцях внутрішніх підсистем ядра. Гачок розташовується не на самому вході в системний виклик (де аргументи є лише сирими числами чи нерозібраними рядками шляхів), а глибоко всередині ядра — у момент, коли відповідну структуру даних уже виділено, розібрано й перевірено базовими механізмами ядра.

```
       [ Запит системного виклику (openat / execve / socket) ]
                                 │
                                 ▼
             [ Перевірка DAC (UID, GID, mode, POSIX ACL) ]
                                 │
                   ┌─────────────┴─────────────┐
                   │ Відмова (ret < 0)         │ Дозволено (ret == 0)
                   ▼                           ▼
        [ Помилка -EACCES / -EPERM ]  [ Точка перехоплення LSM Hook ]
                                               │
                                               ▼
                                      [ Ланцюг модулів LSM ]
                                      (Landlock, SELinux, BPF-LSM)
```

Підсистема LSM функціонує строго за **обмежувальною моделлю** (англ. *restrictive model*). Це означає такий непорушний порядок перевірки дій:
1. Якщо базова перевірка DAC (наприклад, перевірка власника файлу, групи чи стандартних дозволів `rwxr-xr-x`) відхилила запит, ядро негайно повертає помилку `-EACCES` або `-EPERM`. Модулі LSM навіть не викликаються і принципово не можуть надати дозвіл на дію, заборонену базовою моделлю DAC.
2. Якщо базова перевірка DAC успішно дозволила операцію, ядро передає управління інфраструктурі LSM Hooks.
3. Кожен модуль LSM у стеку виконує перевірку у відповідності до власної завантаженої політики. Якщо хоча б один модуль повертає від'ємний код помилки, операція негайно блокується.
4. Запитана дія виконується лише тоді, коли DAC **та всі активні модулі LSM у стеку** повернули згоду (`0`).

![Архітектура LSM Hooks та DAC](/reference/unix-linux/permissions/lsm-stacking-framework/img/lsm-architecture.svg)
*Рис. 1. Взаємодія підсистеми VFS, перевірки DAC та каркасу LSM Hooks.*

Точки перехоплення охоплюють усі ключові об'єкти ядра, що несуть потенційні ризики для безпеки системи:
- **Файлова система та іноди (VFS):** `security_file_open()`, `security_inode_permission()`, `security_path_mkdir()`, `security_file_mmap()`, `security_file_fcntl()`.
- **Управління процесами та завданнями (Tasks/Credentials):** `security_task_alloc()`, `security_task_fix_setuid()`, `security_cred_prepare()`, `security_task_kill()`, `security_task_prctl()`.
- **Мережевий стек та сокети (Networking):** `security_socket_create()`, `security_socket_connect()`, `security_socket_bind()`, `security_sock_rcv_skb()`.
- **Міжпроцесна взаємодія та ключі (IPC/Keyrings):** `security_ipc_permission()`, `security_msg_queue_msgsnd()`, `security_key_alloc()`.
- **Безпека ядра та прошивки (System Integrity):** `security_kernel_read_file()`, `security_kernel_load_data()`, `security_locked_down()`.

Переліки всіх наявних у ядрі гачків зведено в системному заголовочному файлі `include/linux/lsm_hook_defs.h`. Кожен запис оголошується за допомогою макроса `LSM_HOOK`:

```c
/* include/linux/lsm_hook_defs.h */
LSM_HOOK(int, 0, file_open, struct file *file)
LSM_HOOK(int, 0, inode_permission, struct inode *inode, int mask)
LSM_HOOK(int, 0, task_kill, struct task_struct *p, struct kernel_siginfo *info,
	 int sig, const struct cred *cred)
LSM_HOOK(int, 0, socket_connect, struct socket *sock, struct sockaddr *address,
	 int addrlen)
```

Перший аргумент макроса вказує тип значення, що повертається (`int`), другий — дефолтну відповідь за відсутності зареєстрованих обробників (`0` — дозвіл), третій — назву гачка, а далі йде підпис функції.

Архітектурний розвиток від початкового єдиного слота до сучасної системи стекування детально розкрито у вставці [Еволюція стекування LSM](book:unix-linux/lsm-stacking-framework/hist-stacking-evolution.md).

## Механіка стекування (LSM Stacking Infrastructure)

Під стекуванням модулів безпеки (англ. *LSM Stacking* — нашарування модулів) розуміють здатність ядра Linux одночасно утримувати в пам'яті й послідовно викликати обробники кількох незалежних модулів безпеки для одного й того ж гачка.

Серцем інфраструктури стекування є глобальна структура `security_hook_heads`, визначена у файлі `security/security.c`. Вона містить двозв'язні списки `struct hlist_head` для кожного гачка ядра:

```c
/* include/linux/lsm_hooks.h */
struct security_hook_heads {
	#define LSM_HOOK(RET, DEFAULT, NAME, ...) struct hlist_head NAME;
	#include <linux/lsm_hook_defs.h>
	#undef LSM_HOOK
};

extern struct security_hook_heads security_hook_heads;
```

Коли модуль безпеки реєструє свої обробники під час старту ядра, він додає елементи `struct security_hook_list` до відповідного списку `hlist_head`.

```c
struct security_hook_list {
	struct hlist_node	list;
	struct hlist_head	*head;
	union security_list_options	hook;
	const struct lsm_id	*lsmid;
};
```

### Семантика раннього завершення (Short-Circuit Execution)

Викликаючи гачок із місця операції (наприклад, при відкритті файлу системним викликом `openat`), ядро ітерує по списку зареєстрованих обробників. Впроваджено логіку «короткого замикання» (англ. *short-circuit evaluation*): виконання списку припиняється негайно, як тільки один із модулів повертає помилку.

![Ланцюг виконання LSM Stacking](/reference/unix-linux/permissions/lsm-stacking-framework/img/lsm-stacking.svg)
*Рис. 2. Послідовне виконання списку гачків при стекуванні модулів безпеки.*

У спрощеному вигляді внутрішній обробник `security_file_open()` у ядрі реалізовано так:

```c
/* security/security.c */
int security_file_open(struct file *file)
{
	struct security_hook_list *hp;
	int rc;

	hlist_for_each_entry(hp, &security_hook_heads.file_open, list) {
		rc = hp->hook.file_open(file);
		if (rc)
			return rc; /* Short-circuit: відмова одного модуля зупиняє ланцюг */
	}
	return 0; /* Усі модулі в стеку дозволили операцію */
}
```

Такий підхід забезпечує максимальний рівень захисту: для успішного виконання системного виклику потрібна згода **кожного** активованого модуля безпеки. Якщо Landlock дозволяє відкрити файл, SELinux також дозволяє, але BPF-LSM повертає `-EACCES`, підсумковим результатом для користувацького процесу буде відмова у доступі (`-EACCES`), а решта ланцюга навіть не викликатиметься, економлячи такти процесора. Важливо, що в ланцюгу конкретного гачка стоять лише ті модулі, які саме цей гачок зареєстрували: Yama, наприклад, чіпляється до операцій над процесами (`ptrace`) і в ланцюгу `file_open` не з'являється взагалі.

### Оптимізація викликів: `static_call` та Static Keys

Для досягнення мінімальної затримки на гарячих шляхах ядра розробники LSM інтегрували механізм static calls та jump labels (`static_key`). 

Починаючи з Linux 6.10 списки `hlist` на гарячих шляхах замінено масивом слотів `static_call`: під час ініціалізації ядро переписує машинний код кожного слота на прямий виклик `CALL` за адресою функції зареєстрованого модуля, тож непрямого виклику по покажчику не лишається навіть у стеку з кількох модулів. Семантика обходу при цьому не змінилася — той самий порядок і те саме раннє завершення. Якщо ж гачок не використовується жодним модулем, відповідна гілка виклику вимикається на рівні NOP-інструкцій процесора, зводячи накладні витрати порожнього LSM до нуля.

## Розподіл пам'яті контекстів (Security Blob Management)

Кожному об'єкту ядра, який підлягає контролю безпеки (`struct task_struct`, `struct inode`, `struct file`, `struct cred`, `struct socket`, `struct super_block`), необхідне місце в пам'яті для збереження внутрішнього контексту безпеки модуля. Це може бути числовий ідентифікатор сесії (SID) у SELinux, покажчик на профіль в AppArmor чи дерево обмежень у Landlock.

У ранніх версіях ядра ці структури мали єдиний непрозорий покажчик `void *security`. Це унеможливлювало одночасну роботу кількох модулів, бо кожен намагався записати за цією адресою власну структуру.

Сучасний каркас LSM розв'язує цю проблему через механізм **спільних блоків пам'яті** (англ. *cumulative security blobs* — двійкові згустки пам'яті).

### Механізм обчислення зміщень (Blob Offsets)

Під час підготовки ядра до роботи (етап `initcalls`) кожен модуль оголошує свої потреби в пам'яті за допомогою структури `struct lsm_blob_sizes`:

```c
static struct lsm_blob_sizes apparmor_blob_sizes __lsm_ro_after_init = {
	.lbs_cred = sizeof(struct apparmor_cred_label),
	.lbs_file = sizeof(struct aa_file_ctx),
	.lbs_task = sizeof(struct aa_task_ctx),
};
```

Підсистема LSM підсумовує розміри запитаних блоків від усіх активних модулів і обчислює для кожного з них фіксоване зміщення у байтах (offset):

1. SELinux запитує 4 байти для `inode` (offset = 0).
2. AppArmor запитує 8 байт для `inode` (offset = 8).
3. Landlock запитує 8 байт для `inode` (offset = 16).
4. BPF-LSM запитує 16 байт для `inode` (offset = 24).

Зміщення не йдуть упритул: початок кожного наступного слота ядро вирівнює вгору до межі `sizeof(void *)` (8 байт на x86-64), щоб модуль міг покласти у свій слот покажчик.

Ядро виділяє єдиний неперервний блок пам'яті розміром 40 байт і записує його адресу в покажчик `i_security` об'єкта `struct inode`. Так само влаштований доступ і до решти об'єктів: коли AppArmor звертається до свого контексту у `struct file`, він вираховує потрібну адресу простою арифметикою покажчиків — поле `lbs_file`, яке модуль заповнив запитаним розміром, ядро на старті замінило на готове зміщення:

```c
struct aa_file_ctx *ctx = file->f_security + apparmor_blob_sizes.lbs_file;
```

Це рішення усунуло додаткові непрямі адресації (pointer chasing), забезпечило чудову локальність даних у кеші L1/L2 процесора та дозволило довільній кількості модулів прозоро ділити один об'єкт ядра.

Повний опис структур та підписи системних функцій наведено у вставці [Довідник ядерних структур та системних викликів LSM](book:unix-linux/lsm-stacking-framework/api-lsm-kernel-interface.md).

## Конфігурація та порядок завантаження: `lsm=` і `CONFIG_LSM`

Не всі модулі безпеки рівноцінні за своєю природою та призначенням. Ядро Linux поділяє модулі LSM на чотири категорії:

1. **Ранні модулі (Early LSMs):** Невеликі захисні механізми, які повинні ініціалізуватися на найперших етапах завантаження ядра, ще до змонтування кореневої файлової системи (наприклад, `lockdown`, `yama`, `loadpin`, `safesetid`).
2. **Системні модулі MAC (Major MAC LSMs):** Повноцінні системи мандатного контролю доступу, що вимагають завантаження політик із диска (`selinux`, `apparmor`, `smack`, `tomoyo`). SELinux, Smack і AppArmor позначені прапорцем `LSM_FLAG_EXCLUSIVE`, і в мейнлайновому ядрі активним може бути лише **один** із них — стекування двох повноцінних MAC-систем досі не завершено. Тож усе сказане про стек стосується поєднання одного такого модуля з модулями решти категорій.
3. **Непривілейовані модулі (Unprivileged LSMs):** Модулі, які дозволяють звичайним користувацьким процесам створювати пісочниці без прав `CAP_SYS_ADMIN` (`landlock`).
4. **Динамічні модулі (Dynamic LSMs):** Модулі, чиї правила завантажуються та змінюються в процесі роботи системи (`bpf`).

### Задавання порядку завантаження через параметр `lsm=`

Порядок ініціалізації та порядок виконання модулів у ланцюгах гачків контролюється параметром командного рядка ядра `lsm=`. Його значенням є список назв модулів, розділених комами:

```text
lsm=lockdown,yama,loadpin,safesetid,selinux,bpf,landlock
```

Якщо параметр `lsm=` не задано під час завантаження завантажувачем GRUB/systemd-boot, ядро використовує дефолтну послідовність, визначену конфігурацією збірки ядра `CONFIG_LSM`:

```text
CONFIG_LSM="landlock,lockdown,yama,loadpin,safesetid,integrity,selinux,smack,tomoyo,apparmor,bpf"
```

Коли ядро обробляє цей рядок, воно реєструє модулі строго в зазначеному порядку. Це гарантує, наприклад, що легковагі перевірки `yama` будуть виконані раніше за важкі перевірки графа політики `selinux`. У дефолтному рядку перелічено всі зібрані модулі, зокрема кілька взаємовиключних: із них ядро вмикає перший доступний, а решту мовчки пропускає.

Слід підкреслити важливе правило безпеки: **змінити перелік або порядок завантажених вбудованих LSM модулів після завершення ініціалізації ядра неможливо**. Масив гачків розміщується у захищеній від запису пам'яті ядра (`__lsm_ro_after_init`), що унеможливлює відключення модулів безпеки навіть у випадку компрометації користувацького простору чи атаки з боку зловмисника з правами root.

## Інтерфейс користувача: `/proc/self/attr/<lsm>/` та системні виклики (Linux 6.8+)

Історично програми користувацького простору (наприклад, `ps`, `ls -Z`, `systemd` або `coreutils`) взаємодіяли з підсистемою безпеки через файлову систему procfs за шляхом `/proc/self/attr/current`.

Коли в системі працював лише один модуль (SELinux), читання файлу `/proc/self/attr/current` повертало рядок контексту на кшталт `unconfined_u:unconfined_r:unconfined_t:s0`. Проте щойно поряд із головним MAC-модулем стають інші модулі зі своїми контекстами, виникає конфлікт: чий саме контекст має повертати цей єдиний файл?

Для розв'язання цього конфлікту ядро заводить у `/proc/self/attr/` окремий підкаталог на кожен зареєстрований модуль (спільні файли `current`, `exec`, `prev` лишилися на місці заради сумісності):

```text
/proc/self/attr/
├── current              # успадкований спільний файл
├── apparmor
│   ├── current
│   ├── exec
│   └── prev
├── selinux
│   ├── current
│   ├── exec
│   └── keycreate
└── smack
    └── current
```

Підкаталог з'являється лише для тих модулів, які справді зареєстровані в цьому ядрі (вище показано всі можливі варіанти разом). Тепер кожна програма може явно вказати, контекст якого саме модуля її цікавить, звернувшись до відповідної директорії.

> 🔧 **Навіщо це в реальній розробці.**
> Під час створення контейнерних ізоляторів (Docker, podman, systemd-nspawn) або прикладних пісочниць програма повинна перевірити, які саме модулі захищають поточне середовище, і встановити відповідний профіль перед викликом `execve()`. Використання нового інтерфейсу `/proc/self/attr/<lsm>/` або системних викликів Linux 6.8+ гарантує, що налаштування AppArmor не збурять роботу SELinux чи Landlock.

### Новий API системних викликів LSM (Linux 6.8+)

Починаючи з версії ядра Linux 6.8, розробники отримали прямий і продуктивний системний виклик для інспектування та налаштування атрибутів безпеки без використання проміжної файлової системи procfs: `lsm_list_modules()`, `lsm_get_self_attr()` та `lsm_set_self_attr()`.

Нижче наведено приклад програми користувацького простору, яка запитує перелік активних модулів LSM у системі з використанням вкладки **C** та ідіоматичної вкладки **C++**:

:::tabs
```c
/* inspect_lsm.c */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <stdint.h>
#include <errno.h>

#ifndef __NR_lsm_list_modules
#define __NR_lsm_list_modules 461
#endif

int main(void)
{
	uint64_t ids[16];
	uint32_t size = sizeof(ids);

	/* Запитуємо у ядра масив ідентифікаторів активованих модулів LSM */
	long count = syscall(__NR_lsm_list_modules, ids, &size, 0);

	if (count < 0) {
		if (errno == ENOSYS) {
			printf("Системний виклик lsm_list_modules відсутній (потрібне ядро >= 6.8)\n");
		} else {
			perror("Помилка виконання lsm_list_modules");
		}
		return 1;
	}

	printf("Кількість активних модулів LSM у стеку: %ld\n", count);
	for (long i = 0; i < count; i++) {
		printf("  [%ld] Module LSM ID: 0x%lx\n", i, (unsigned long)ids[i]);
	}

	return 0;
}
```

```cpp
// inspect_lsm.cpp
#include <iostream>
#include <vector>
#include <cstdint>
#include <cerrno>
#include <cstring>
#include <unistd.h>
#include <sys/syscall.h>
#include <expected>

#ifndef __NR_lsm_list_modules
#define __NR_lsm_list_modules 461
#endif

namespace sys::lsm {

// Запит активних модулів безпеки через новий системний виклик Linux 6.8+
std::expected<std::vector<std::uint64_t>, std::string> get_active_lsm_ids() {
    std::vector<std::uint64_t> ids(16);
    std::uint32_t size = static_cast<std::uint32_t>(ids.size() * sizeof(std::uint64_t));

    const long count = ::syscall(__NR_lsm_list_modules, ids.data(), &size, 0);
    if (count < 0) {
        if (errno == ENOSYS) {
            return std::unexpected("Системний виклик lsm_list_modules не підтримується цим ядром (< 6.8)");
        }
        return std::unexpected(std::string("Помилка lsm_list_modules: ") + std::strerror(errno));
    }

    ids.resize(static_cast<std::size_t>(count));
    return ids;
}

} // namespace sys::lsm

int main() {
    auto lsm_ids = sys::lsm::get_active_lsm_ids();
    if (!lsm_ids) {
        std::cerr << "Помилка: " << lsm_ids.error() << "\n";
        return 1;
    }

    std::cout << "Кількість активних модулів LSM у стеку: " << lsm_ids->size() << "\n";
    std::size_t idx = 0;
    for (const auto id : *lsm_ids) {
        std::cout << "  [" << idx++ << "] Module LSM ID: 0x" << std::hex << id << std::dec << "\n";
    }

    return 0;
}
```

## Очікувана ціна стекування: продуктивність, пам'ять та крайові випадки

Запровадження повноцінного стекування модулів LSM вимагало компромісів між гнучкістю захисту та ресурсомісткістю ядра.

### 1. Витрати пам'яті (Memory Overhead)

Кожен об'єкт `struct inode` або `struct task_struct` у ядрі тепер несе додатковий блок пам'яті `security blob`. Якщо в системі активовано SELinux, AppArmor, Landlock та BPF-LSM, розмір цього блоку для кожного іноду може становити від 32 до 64 байт.
У системах із мільйонами закешованих інодів це додає десятки мегабайт оперативної пам'яті. Проте ядро виділяє один спільний блок на об'єкт з окремого `kmem_cache`, а не по ділянці на кожен модуль, — тож службові витрати розподільника slab платяться один раз, а не стільки разів, скільки модулів у стеку.

### 2. Затримки виконання (CPU Overhead)

Кожен викликаний гачок LSM спирається на виконання ланцюга функцій. При звичайній роботі файлової системи (наприклад, масовому зчитуванні дрібних файлів або комбінаціях системних викликів `stat`/`open`) виконання 3–4 обробників поспіль додає затримку.
Однак використання механізму `static_call` дозволило мінімізувати накладні витрати на промахи передбачувача розгалужень (branch predictor) у процесорі. Вимірювання продуктивності показали, що накладні витрати від додавання другого модуля в стек зазвичай не перевищують 1–2% для загальносистемних бенчмарків.

### 3. Крайові випадки та конфлікти (Edge Cases)

- **Конфлікти мережевих міток (CIPSO / NetLabel):** Якщо SELinux та Smack намагаються одночасно маркувати вихідні мережеві пакети для мандатного контролю мережі (IPSec / CIPSO), виникає конфлікт пакетних міток. Наразі ядро вимагає, щоб лише один модуль відповідав за активне маркування мережевого трафіку.
- **Взаємодія з eBPF-LSM:** Програми BPF-LSM виконуються динамічно в контексті ядра. Якщо розробник написав BPF-програму, яка змінює значення аргументів або завершується з помилкою без урахування стану AppArmor, це може призвести до непередбачуваної поведінки системних демонів.

Завдяки послідовній архітектурі LSM Stacking сучасне ядро Linux дозволяє скласти захист із різнорідних частин: обраний головний MAC-модуль (перевірка шляхів в AppArmor або розмежування за типами в SELinux), непривілейовані пісочниці Landlock, динамічні правила eBPF-LSM і дрібні захисні модулі на кшталт Yama працюють в одному ланцюгу, не заважаючи один одному.
