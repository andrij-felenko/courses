# 📜 Історія креденшелів Unix: від V7 до Saved UID та Linux fsuid

Модель ідентифікаторів процесів Unix розвивалася упродовж п'яти десятиліть разом із зростанням складності операційних систем та вимог до безпеки мережевих служб.

У перших версіях Unix (Research Unix Version 6 та Version 7) процес мав лише два ідентифікатори: Real UID та Effective UID. Цього вистачало для простих утиліт із бітом SUID (як-от `passwd`), але створювало серйозний системний недолік при створенні фонових служб та демонів.

## Проблема двох ідентифікаторів у ранніх Unix

У системі з лише RUID та EUID процес SUID-програми не мав проміжного стану між привілейованим та непривілейованим режимом:

- Якщо привілейований процес (EUID = 0) викликав `setuid(ruid)`, він незворотно втрачав привілеї `root`.
- Для тимчасового скидання привілеїв процес міг змінити EUID на RUID через `seteuid(ruid)`. Проте в оригінальній моделі BSD непривілейований процес (з EUID != 0) не мав жодної системної пам'яті про те, що раніше він був привілейованим. Спроба викликати `seteuid(0)` відхилялася ядром як неавторизована.

Це змушувало розробників утиліт тримати привілеї `root` протягом усього часу роботи програми, що призводило до численних уразливостей витоку привілеїв при переповненні буферів.

## Поява Saved Set-User-ID у System V та POSIX

Для вирішення цієї проблеми у розробці Unix System V Release 4 (SVR4) наприкінці 1980-х років та у виданні стандарту POSIX.1-1990 було введено третій ідентифікатор — **Saved Set-User-ID (suid)**.

Ідея полягала в тому, що під час системного виклику `execve()`, якщо виконуваний файл мав встановлений біт SUID, ядро копіювало новий привілейований Effective UID у збережене поле `suid`. Тепер процес міг вільно перемикати свій `euid` між `ruid` та `suid`:

- Виклик `seteuid(ruid)` тимчасово вимикав привілеї (EUID ставав RUID).
- Виклик `seteuid(suid)` відновлював привілеї (EUID ставав SUID = 0).
- Остаточна відмова від привілеїв виконувалася через `setuid(ruid)` від імені root, який перезаписував усі три поля (`ruid`, `euid`, `suid`), унеможливлюючи повернення.

## Поява Linux fsuid: проблема NFS-серверів 1990-х років

У 1995 році під час розробки ядра Linux 1.2 виникла унікальна проблема із сервером мережевої файлової системи (NFS daemon). 

Сервер NFS працює в просторі користувача і мусить перевіряти права доступу до файлів від імені віддаленого користувача (наприклад, з UID 1001). Для цього демон NFS мав змінити свій `euid` на 1001 перед викликом `open()` чи `read()`.

Проте в традиційній POSIX-моделі процес із `euid == 1001` втрачав можливість надсилати сигнатури або керувати іншими процессами NFS, оскільки ядро дозволяло надсилання сигналів `kill()` лише тоді, коли `euid` відправника збігався з `ruid` чи `euid` отримувача (чи відправник був root). Якщо демон NFS змінював `euid` на 1001, він тимчасово ставав звичайним користувачем і втрачав контроль над іншими нитками демона.

Для розв'язання цієї проблеми Лінус Торвальдс ввів у Linux специфічні ідентифікатори: **Filesystem UID (fsuid)** та **Filesystem GID (fsgid)**. 

Ядро Linux було змінено так, що всі перевірки доступу до файлової системи (VFS) почали використовувати `fsuid`/`fsgid` замість `euid`/`egid`. Демон NFS міг змінити лише `fsuid` на 1001 через новий системний виклик `setfsuid(1001)`, зберігаючи при цьому `euid = 0`. Це дозволяло безпечно здійснювати файлові операції від імені користувача, не втрачаючи привілеїв root для системного управління та міжпроцесної взаємодії.

З появою у ядрі Linux 2.2 механізму **Capabilities** (`CAP_DAC_OVERRIDE`, `CAP_FOWNER`) необхідність у прямому маніпулюванні `fsuid` зменшилася, проте `fsuid` залишається частиною архітектури ядра для збереження сумісності.
