Коли користувач запускає програму, операційній системі потрібно знати, які права має цей новий процес. Unix-подібні системи вирішують це, призначаючи кожному процесу набір ідентифікаторів — **креденшелів** (credentials). Це не просто один ідентифікатор, а цілий набір UID (User ID) та GID (Group ID), кожен з яких має свою конкретну мету.

Система креденшелів дозволяє процесам не лише діяти від імені користувача, який їх запустив, але й тимчасово підвищувати свої привілеї для виконання системних задач, а потім безпечно відмовлятися від них, щоб мінімізувати ризики безпеки.

## Види ідентифікаторів процесу

Кожен процес у Linux має три основні ідентифікатори користувача (UID) та три основні ідентифікатори групи (GID), а також один специфічний для Linux ідентифікатор та список додаткових груп.

### Real UID та Real GID (ruid, rgid)

**Real UID (Дійсний UID)** — це ідентифікатор користувача, який фактично запустив процес. 

Коли ви входите в систему, оболонка (shell) отримує ваш UID як свій Real UID. Коли оболонка запускає будь-яку програму (наприклад, `ls` або `cat`), процес-нащадок успадковує Real UID батьківського процесу. Real UID відповідає на запитання: *"Хто є справжнім власником цього процесу?"*. 

Real UID використовується для обліку ресурсів та для визначення того, які процеси можуть надсилати сигнали іншим процесам (зазвичай, непривілейований процес може надсилати сигнали лише процесам з таким самим Real UID).

### Effective UID та Effective GID (euid, egid)

**Effective UID (Ефективний UID)** — це ідентифікатор, який ядро операційної системи використовує для перевірки прав доступу в даний момент.

Коли процес намагається відкрити файл, створити сокет або виконати привілейовану дію, ядро дивиться саме на Effective UID, а не на Real UID. У більшості звичайних програм `euid` дорівнює `ruid`. Але вони можуть відрізнятися у випадку програм із встановленим бітом Set-UID (SUID).

Наприклад, утиліта `passwd` дозволяє звичайному користувачу змінити свій пароль. Файл з паролями `/etc/shadow` може записувати лише `root`. Програма `passwd` має власником `root` і встановлений біт SUID. Коли звичайний користувач (наприклад, з UID 1000) запускає `passwd`:
- Його `ruid` стає 1000 (бо він запустив програму).
- Його `euid` стає 0 (`root`), оскільки програма має біт SUID.
Ядро, перевіряючи права на запис у `/etc/shadow`, бачить `euid = 0` і дозволяє операцію.

### Saved Set-User-ID та Saved Set-Group-ID (suid, sgid)

**Saved Set-User-ID (Збережений UID)** — це механізм, який дозволяє процесам із підвищеними привілеями тимчасово скидати свої права, а потім знову їх повертати.

Коли програма запускається (через системний виклик `execve`), ядро копіює значення Effective UID у Saved Set-UID. Якщо програма (наприклад, SUID-бінарник) хоче тимчасово стати звичайним користувачем, вона може змінити свій `euid` на значення `ruid`. При цьому привілейований `euid` (наприклад, 0) залишається збереженим у `suid`. 

Коли програмі знову потрібні привілеї, вона може змінити свій `euid` назад на значення з `suid`. Без `suid` тимчасове відкидання привілеїв було б неможливим, оскільки непривілейований процес не зміг би знову стати привілейованим.

### Filesystem UID та GID (fsuid, fsgid)

Це специфічні для Linux ідентифікатори. Вони використовуються **виключно для перевірки прав доступу до файлової системи**.

Історично `fsuid` був створений у Linux для підтримки мережевих файлових систем (NFS). NFS-сервери мали працювати від імені клієнта при доступі до файлів, але при цьому зберігати свій `euid`, щоб мати змогу надсилати сигнали як `root`. 

У сучасному Linux значення `fsuid` автоматично слідує за `euid`. Якщо процес змінює свій `euid`, ядро автоматично змінює і `fsuid`. Розробникам додатків рідко потрібно взаємодіяти з `fsuid` напряму.

### Supplementary GIDs (Додаткові групи)

Крім основного GID, процес має список додаткових ідентифікаторів груп. Це дозволяє користувачу належати до багатьох груп одночасно (наприклад, `audio`, `docker`, `wheel`) і отримувати відповідні права доступу. Ядро перевіряє права на файл, порівнюючи групу файлу з `egid` процесу, а потім з усіма групами у списку Supplementary GIDs.

## Як ідентифікатори зберігаються в ядрі: struct cred

У ядрі Linux (починаючи з версії 2.6.29) усі ці ідентифікатори інкапсульовані в окрему структуру `struct cred`. Кожен процес (представлений `task_struct`) має вказівники на свої креденшели: `real_cred` та `cred` (об'єктивні та суб'єктивні креденшели).

```c
// Спрощений вигляд struct cred у ядрі Linux
struct cred {
    atomic_t    usage;
    kuid_t      uid;        // Real UID
    kgid_t      gid;        // Real GID
    kuid_t      suid;       // Saved set-UID
    kgid_t      sgid;       // Saved set-GID
    kuid_t      euid;       // Effective UID
    kgid_t      egid;       // Effective GID
    kuid_t      fsuid;      // Filesystem UID
    kgid_t      fsgid;      // Filesystem GID
    struct group_info *group_info; // Supplementary groups
    // ... capabilities, namespaces, seccomp filters тощо
};
```

Ця структура є **незмінною (immutable)** після її створення. Це зроблено для безпеки та продуктивності за допомогою RCU (Read-Copy-Update). Якщо процес хоче змінити свій UID (наприклад, викликаючи `setuid`), ядро створює *нову* копію `struct cred`, змінює необхідні поля в копії, а потім атомарно перемикає вказівник процесу на нову структуру. Стара структура звільняється, коли на неї більше немає посилань.

Така архітектура гарантує, що інші частини ядра, які перевіряють права процесу в даний момент часу, не побачать проміжний, неконсистентний стан креденшелів.

## Керування привілеями: зміна UID/GID

Процес не може просто змінити свій UID на будь-який інший. Правила зміни суворо контролюються ядром. Існує кілька системних викликів для зміни ідентифікаторів.

### setuid(uid)

Поведінка `setuid` залежить від поточних привілеїв:
- Якщо процес має привілеї (`euid == 0` або має capability `CAP_SETUID`), `setuid(uid)` встановлює **усі три** ідентифікатори (`ruid`, `euid`, `suid`) у нове значення `uid`. Це незворотна дія — процес назавжди стає цим користувачем і втрачає привілеї.
- Якщо процес непривілейований, він може змінити свій `euid` лише на значення, що дорівнює його `ruid` або `suid`. У цьому випадку `ruid` та `suid` залишаються незмінними.

### seteuid(euid)

Цей виклик змінює **лише Effective UID**.
- Привілейований процес може встановити `euid` у будь-яке значення. Це дозволяє тимчасово відмовитися від привілеїв, зберігаючи їх у `suid`.
- Непривілейований процес може встановити `euid` лише у значення `ruid` або `suid`.

### setresuid(ruid, euid, suid)

Це найбільш чіткий і безпечний виклик, специфічний для Linux (і деяких інших ОС, як-от FreeBSD). Він дозволяє встановити всі три ідентифікатори одночасно і явно. Якщо ви не хочете змінювати певний ідентифікатор, передається значення `-1`.
- Привілейований процес може встановити будь-які значення.
- Непривілейований процес може встановлювати кожен з ідентифікаторів лише у значення одного з поточних (`ruid`, `euid`, або `suid`).

Саме `setresuid` рекомендується використовувати для безпечного керування привілеями, оскільки він позбавлений неоднозначностей історичного `setuid`.

## Приклади в коді

Ось як можна взаємодіяти з ідентифікаторами процесу на різних мовах програмування.

:::tabs
== C
У C використовується стандартний POSIX API з `<unistd.h>`.

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <stdio.h>
#include <sys/types.h>

int main() {
    uid_t ruid, euid, suid;

    // Отримання поточних UID
    getresuid(&ruid, &euid, &suid);
    printf("Поточні: RUID=%d, EUID=%d, SUID=%d\n", ruid, euid, suid);

    // Тимчасове скидання привілеїв (наприклад, з euid 0 на ruid 1000)
    // Змінюємо лише ефективний UID
    if (seteuid(ruid) == -1) {
        perror("seteuid failed");
        return 1;
    }
    getresuid(&ruid, &euid, &suid);
    printf("Після seteuid: RUID=%d, EUID=%d, SUID=%d\n", ruid, euid, suid);

    // Відновлення привілеїв зі збереженого SUID
    if (seteuid(suid) == -1) {
        perror("seteuid restore failed");
        return 1;
    }
    printf("Відновлено привілеї.\n");

    return 0;
}
```

== Python
У Python модуль `os` надає обгортки для цих системних викликів.

```python
import os

# Отримання поточних ідентифікаторів
ruid, euid, suid = os.getresuid()
print(f"Поточні: RUID={ruid}, EUID={euid}, SUID={suid}")

# Тимчасове скидання привілеїв
try:
    os.seteuid(ruid)
    print(f"Після seteuid(ruid): EUID={os.geteuid()}")
    
    # Виконання непривілейованих дій...
    
    # Відновлення привілеїв
    os.seteuid(suid)
    print("Привілеї відновлено.")
except PermissionError:
    print("Помилка: процес не має достатньо прав.")
```

== Go
У Go пакет `syscall` надає прямий доступ до системних викликів, але взаємодія з UIDs/GIDs у багатониткових програмах на Go (де кожна нитка ОС може мати власні креденшели, хоча Linux намагається тримати їх синхронізованими) має нюанси.

```go
package main

import (
	"fmt"
	"syscall"
)

func main() {
	// Отримання UID
	ruid := syscall.Getuid()
	euid := syscall.Geteuid()
	fmt.Printf("RUID: %d, EUID: %d\n", ruid, euid)

	// Зміна UID
	// Примітка: Setreuid у Go впливає на поточну нитку ОС.
	// Для синхронізації між усіма нитками використовують syscall.Setresuid
	err := syscall.Setresuid(ruid, ruid, euid)
	if err != nil {
		fmt.Printf("Помилка: %v\n", err)
	} else {
		fmt.Printf("Успішно скинуто привілеї\n")
	}
}
```
