# Платформа авторизації PAM

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Система **Pluggable Authentication Modules (PAM)** — це гнучкий механізм автентифікації користувачів, який використовується в більшості сучасних UNIX-подібних операційних систем, включаючи Linux. PAM забезпечує абстракцію, що дозволяє відокремити процес розробки прикладних програм від деталей реалізації автентифікації. 

## Вступ до PAM

До появи PAM кожна програма, що вимагала автентифікації (наприклад, `login`, `su`, `ftp`), містила власні механізми перевірки паролів та доступу до файлу `/etc/passwd` чи `/etc/shadow`. Це призводило до дублювання коду, проблем із безпекою та ускладнювало впровадження нових методів автентифікації, таких як біометрія, смарт-картки чи LDAP-сервери. З PAM розробникам потрібно лише викликати функції API PAM, а налаштування автентифікації перекладаються на системного адміністратора, який може змінювати їх через файли конфігурації без перекомпіляції програм.

## Архітектура PAM

Архітектура PAM поділяється на три основні рівні:

1. **Програми (Application Privilege/Authentication Layer):** Застосунки (наприклад, `sshd`, `sudo`, `login`), які ініціюють процес автентифікації, викликаючи бібліотеку PAM.
2. **Бібліотека `libpam.so` (PAM API/SPI Layer):** Проміжний шар, який приймає запити від програм, читає файли конфігурації (зазвичай у каталозі `/etc/pam.d/`) та завантажує відповідні модулі. Цей рівень реалізує функції, такі як `pam_authenticate()`.
3. **Модулі (PAM Modules Layer):** Динамічні бібліотеки (зазвичай розміщені у `/lib/security/` або `/lib/x86_64-linux-gnu/security/`), які виконують фактичну роботу (наприклад, `pam_unix.so` для перевірки локальних паролів, `pam_ldap.so` для мережевої автентифікації).

## 4 Фази (Management Groups) PAM

PAM розділяє процес управління сеансами та автентифікацією на 4 логічні фази. Кожна програма може використовувати одну або кілька з цих фаз:

1. **`auth` (Автентифікація):** 
   Відповідає за перевірку ідентичності користувача, зазвичай шляхом запиту пароля або іншого токена (наприклад, біометричних даних чи OTP). Також може встановлювати облікові дані, наприклад, членство у групах.

2. **`account` (Управління обліковими записами):**
   Виконується після успішної автентифікації. Перевіряє, чи має користувач право на доступ саме зараз. Наприклад, перевіряє, чи не закінчився термін дії пароля, чи дозволено вхід у цей час доби, чи не заблоковано обліковий запис.

3. **`session` (Управління сеансом):**
   Відповідає за налаштування середовища перед наданням доступу користувачеві та за очищення після завершення сеансу. До цієї фази належить монтування домашніх каталогів, встановлення обмежень на ресурси (`ulimit`, `pam_limits.so`), запис у лог-файли.

4. **`password` (Оновлення токена авторизації):**
   Використовується для зміни пароля або іншого токена автентифікації. Гарантує виконання правил безпеки, таких як перевірка надійності нового пароля (наприклад, за допомогою `pam_pwquality.so`).

## Контрольні прапорці (Control Flags)

Кожен модуль у конфігураційному файлі супроводжується контрольним прапорцем, який визначає, як результат виконання цього модуля вплине на загальний результат фази. У PAM існує 4 основні прапорці:

- **`required`:** 
  Успішне виконання цього модуля є обов'язковим. Якщо модуль повертає помилку, загальний результат фази буде негативним. Однак PAM не припиняє виконання інших модулів у стеку, що дозволяє приховати, на якому саме етапі сталася помилка (це важливо для захисту від перебору).
- **`requisite`:** 
  Схожий на `required`, але якщо модуль завершується з помилкою, PAM негайно припиняє виконання фази та повертає помилку застосунку. Це оптимізує час виконання, але може видати інформацію про причину відмови.
- **`sufficient`:** 
  Якщо цей модуль виконується успішно (і жоден попередній `required` модуль не зазнав невдачі), фаза негайно завершується з успіхом, і наступні модулі ігноруються. Якщо модуль зазнає невдачі, це не впливає на загальний результат (виконання продовжується).
- **`optional`:** 
  Результат цього модуля впливає на загальний успіх фази лише в тому випадку, якщо він є єдиним модулем у стеку для цієї фази. В інших випадках його успіх чи невдача просто ігнорується, хоча модуль може виконувати корисні дії, наприклад логування.

Існує також складніший синтаксис управління (complex control syntax), де можна вказати точні дії для кожного коду повернення модуля, наприклад `[success=ok new_authtok_reqd=ok ignore=ignore default=bad]`.

## Структура файлів у /etc/pam.d/

Файли конфігурації для кожного застосунку (сервісу) зберігаються у директорії `/etc/pam.d/`. Ім'я файлу зазвичай відповідає імені програми (наприклад, `sshd`, `sudo`, `su`). Якщо файл не знайдено, використовується файл за замовчуванням `/etc/pam.d/other`.

Рядок конфігурації має такий формат:
`тип   контрольний_прапорець   шлях_до_модуля   аргументи`

Наприклад:
```
# /etc/pam.d/su
auth       sufficient pam_rootok.so
auth       required   pam_unix.so
account    required   pam_unix.so
session    required   pam_unix.so
```
Цей конфіг дозволяє `root` користувачеві використовувати `su` без пароля (через `pam_rootok.so`), тоді як іншим доведеться вводити пароль (через `pam_unix.so`).

Замість дублювання конфігурації в різних файлах, в сучасних системах часто використовується директива `@include` (у Debian/Ubuntu) або `include` / `substack` (у Red Hat/CentOS) для залучення спільних файлів, таких як `common-auth` або `system-auth`.

## Приклад роботи: pam_authenticate()

Коли користувач намагається увійти в систему, програма (наприклад, `login`) викликає функцію ініціалізації:
`pam_start("login", "username", &conv, &pamh);`
Ця функція створює дескриптор `pamh`. Далі викликається `pam_authenticate(pamh, 0);`.
Бібліотека `libpam.so` читає файл `/etc/pam.d/login`, знаходить усі рядки типу `auth` та викликає відповідну функцію для кожного модуля в стеку. Кожен модуль може взаємодіяти з користувачем через функцію розмови (conversation function `conv`), наприклад, запитуючи пароль.
Після завершення `pam_authenticate()`, програма може перевірити код повернення (наприклад, `PAM_SUCCESS`) та продовжити з фазою `account` (`pam_acct_mgmt()`), а потім `session` (`pam_open_session()`). Наприкінці роботи викликається `pam_end()`.

## Висновок

PAM (Pluggable Authentication Modules) — це потужна і гнучка архітектура, яка стандартизує процес автентифікації в UNIX/Linux. Її здатність поділяти логіку на 4 фази (`auth`, `account`, `session`, `password`), можливість гнучкого налаштування за допомогою контрольних прапорців (`required`, `requisite`, `sufficient`, `optional`) та використання динамічних модулів забезпечує високий рівень безпеки й розширюваності. Розуміння того, як працює конфігурація в `/etc/pam.d/` та як взаємодіють модулі через `libpam.so`, є критично важливим для будь-якого системного адміністратора та розробника ПЗ для Linux.
