# Платформа авторизації PAM

<preknowlist>
- [Ідентичність процесів: UID, GID та їх зміна](book:unix-linux/process-credentials-uids-gids) — процес у Linux несе діючий (effective) та реальний (real) UID, які визначають його привілеї при доступі до системних ресурсів.
- [База даних користувачів та NSS](book:unix-linux/user-database-nss) — служба Name Service Switch розмежовує запити облікових даних і розпізнає системні записи у /etc/passwd чи мережевих службах.
- [Механізм setuid та розмежування привілеїв](book:unix-linux/setuid-and-privilege) — прапорець SUID дозволяє програмі тимчасово піднімати привілеї до власника файлу для виконання адміністративних дій.
- [Підсистема збереження секретів у ядрі](book:unix-linux/kernel-keyring-subsystem) — ядро зберігає ключі та аутентифікаційні токени сесії в оперативній пам'яті з розмежуванням за UID та сесією.
</preknowlist>

Коли системний службовець налаштовує двофакторну автентифікацію через TOTP для входу через SSH, програма OpenSSH (`sshd`) у чистому вигляді не знає жодної деталі про алгоритм RFC 6238, HMAC-SHA1 чи локальні секретні ключі в каталозі користувача. Якби розробникам `sshd` доводилося вручну переписувати сирцевий код для підтримки біометрії, смарт-карток PKCS#11, корпоративного LDAP та розпізнавання відбитків пальців, кожна оновлена версія демона потребувала б нескінченної перекомпіляції, а будь-яка помилка в локальному коді автентифікації відкривала б критичну вразливість у системній утиліті з привілеями `root`.

Розрив між потребою перевірити особу користувача та різноманіттям методів цієї перевірки вирішує платформа Pluggable Authentication Modules (PAM). Вона виступає динамічним абстракційним прошарком між прикладними утилітами й конкретними механізмами підтвердження особи.

## Архітектурний борг монолітних перевірок та відокремлення шарів

У перших операційних системах сімейства UNIX кожна програма входу — від консольного `login` до серверів `ftpd` та `rshd` — мала власну логіку підтвердження осіб. Програми відкривали системний файл `/etc/passwd` або `/etc/shadow`, власноруч запитували пароль з термінала та порівнювали його з криптографічним хешем за допомогою функції `crypt()`.

Це призводило до трьох системних проблем:

1. **Дублювання коду та помилки безпеки:** Кожен прикладний демон мусив самостійно обробляти тіньові паролі, обмежувати кількість невдалих спроб входу та записувати системні журнальні аудит-події.
2. **Вимога надлишкових привілеїв:** Оскільки файл `/etc/shadow` має права доступу `0600` і читається лише користувачем `root`, усім утилітам автентифікації доводилося встановлювати прапорець SUID root, розширюючи поверхню атаки на всю систему.
3. **Жорстка зв'язаність (tight coupling):** Впровадження нової схеми перевірки (наприклад, Kerberos чи біометричних сканерів) вимагало перекомпіляції всіх програм у системі з додаванням специфічних зовнішніх бібліотек.

Слід чітко розрізняти зони відповідальності підсистем NSS (Name Service Switch) та PAM. Служба NSS відповідає на питання «хто існує в системі» — вона транслює імена користувачів у числові UID та списки груп (через `/etc/passwd` чи LDAP). Платформа PAM відповідає на принципово інше питання: «чи є дана сутність тією, за кого себе видає, і чи має вона право увійти зараз».

У 1995 році компанія Sun Microsystems розробила концепцію PAM, яка розділила автентифікацію на три незалежні рівні. Детальний аналіз передумов створення стандарту та відмінностей між його сучасними реалізаціями наведено у [історії створення та еволюції стандарту PAM](book:unix-linux/pam-authentication-stack/hist-sun-openpam.md).

![Трирівнева архітектура Pluggable Authentication Modules](/reference/unix-linux/permissions/pam-authentication-stack/img/pam-arch.svg)
*Трирівнева архітектура PAM відокремлює програми від модулів за допомогою абстракції бібліотеки libpam та конфігураційних стеків.*

Програма лише ініціює сесію через виклик API `pam_start()`, а бібліотека-посередник `libpam.so` під час виконання зчитує конфігураційні правила з каталогу `/etc/pam.d/` і завантажує динамічні об'єкти `.so` через виклик `dlopen()`. Прикладна програма повністю позбавляється знань про те, як саме перевіряється особа.

## Чотири фази управління (Management Groups)

Процес допуску користувача до системи складається не лише з введення пароля: необхідно перевірити стан облікового запису, налаштувати оточення сесії та дати можливість змінити вичерпаний токен. PAM розділяє ці задачі на чотири незалежні фази:

```
+-------------------------------------------------------------------+
|                        Прикладна програма                         |
+-------------------------------------------------------------------+
       |                  |                   |                 |
       v                  v                   v                 v
+--------------+  +---------------+  +----------------+  +---------------+
|     auth     |  |    account    |  |    session     |  |   password    |
| (Хто ти є?)  |  | (Чи можна?)   |  | (Готуємо дім)  |  | (Онови токен) |
+--------------+  +---------------+  +----------------+  +---------------+
```

### 1. Фаза auth (Автентифікація)
Перевіряє особу користувача (наприклад, запитує пароль, OTP-код або приймає токен смарт-картки) через функцію бібліотеки `pam_authenticate()`. Також встановлює додаткові атрибути доступу (наприклад, додаткові групи або токени Kerberos) за допомогою виклику `pam_setcred()`.

### 2. Фаза account (Управління обліковими записами)
Виконується після успішної автентифікації через функцію `pam_acct_mgmt()`. Вона перевіряє, чи дозволено користувачеві увійти в систему **саме зараз**, незалежно від правильності пароля:
- Чи не закінчився термін дії облікового запису або пароля.
- Чи не заблоковано користувача через перевищення спроб входу (`pam_faillock.so`).
- Чи дозволено вхід з даного термінала або у цей час доби (`pam_time.so`).

### 3. Фаза session (Управління сеансом)
Охоплює дії, які необхідно виконати перед наданням користувачеві командної оболонки та після завершення роботи (`pam_open_session()` та `pam_close_session()`):
- Монтування домашнього каталогу чи зашифрованого розділу (`pam_mount.so`).
- Встановлення лімітів системних ресурсів `rlimit` (`pam_limits.so`).
- Ініціалізація зв'язки ключів у ядрі (`pam_keyinit.so`).
- Створення для сесії окремої контрольної групи cgroups у слайсі користувача systemd (`pam_systemd.so`).
- Запис часу та IP-адреси останнього входу у системний журнал `wtmp`/`utmp` (`pam_lastlog.so`).

### 4. Фаза password (Оновлення токена авторизації)
Використовується при виклику `pam_chauthtok()` для зміни пароля або іншого автентифікаційного токена. Вона проходить у два етапи: спершу перевіряється готовність модулів та надійність нового пароля (`pam_pwquality.so`), а потім здійснюється безпосередній запис нового хешу в базі даних.

## Двигун обчислення стеків та логіка контрольних прапорців

Кожен файл у каталозі `/etc/pam.d/` визначає послідовність викликів модулів (стек) для кожної з чотирьох фаз. Порядок рядків має вирішальне значення.

![Фази управління PAM та логіка контрольних прапорців](/reference/unix-linux/permissions/pam-authentication-stack/img/pam-phase-flow.svg)
*Динамічний двигун libpam послідовно обчислює модулі у стеку, застосовуючи контрольні прапорці для прийняття остаточного рішення.*

Кожен рядок конфігураційного файлу описує один крок обчислення:

```
тип_фази   контрольний_прапорець   модуль.so   [аргументи_модуля]
```

Бібліотека `libpam` послідовно проходить модуль за модулем. Обчислюючи фазу, `libpam` веде в циклі диспетчеризації два робочі стани: позначку фатальної помилки (`must_fail`) та поточну оцінку фази (`impression`); обидва живуть лише під час обходу стеку й не зберігаються в дескрипторі `pam_handle_t`.

Для прийняття підсумкового рішення двигун використовує чотири класичні **контрольні прапорці** (Control Flags):

### required (Обов'язковий)
Модуль **мусить** повернути успіх (`PAM_SUCCESS`). Якщо модуль зазнає невдачі, двигун встановлює прапорець `must_fail = 1`, збереже код помилки, проте PAM **не перериває** виконання стеку. Він продовжує обчислювати наступні модулі. Це зроблено, щоб зловмисник не дізнався ні з тексту помилки, ні з часу відповіді, який саме модуль у ланцюжку відхилив запит (наприклад, чи існує користувач у системі).

### requisite (Критичний)
Як і `required`, модуль мусить повернути успіх. Але у разі помилки PAM **негайно перериває** виконання фази й повертає помилку застосунку без виконання наступних модулів. Це використовується для швидкого відсікання марних подальших перевірок (наприклад, якщо мережевий сервер недоступний або користувача заблоковано).

### sufficient (Достатній)
Якщо цей модуль повертає успіх **і прапорець `must_fail` дорівнює нулю** (тобто жоден із попередніх `required` модулів не зазнав невдачі), стек негайно переривається з результатом `PAM_SUCCESS`. Решта модулів фази ігнорується. Якщо ж модуль `sufficient` зазнає невдачі, його результат просто ігнорується, і обчислення продовжується.

### optional (Опціональний)
Результат цього модуля враховується лише тоді, коли він є єдиним модулем у даній фазі або коли всі попередні модулі повернули код `PAM_IGNORE`. У більшості випадків використовується для допоміжних дій (наприклад, показу банера чи оновлення статистики).

### Складний синтаксис керування прапорцями

Класичні контрольні прапорці (`required`, `requisite`, `sufficient`, `optional`) мають жорстко зафіксовану поведінку: вони не дозволяють реалізувати складну розгалужену логіку. Вони оцінюють лише узагальнений факт успіху чи помилки і не здатні обробляти конкретні коди повернення (наприклад, відрізнити відсутність користувача `PAM_USER_UNKNOWN` від помилки мережі `PAM_AUTHINFO_UNAVAIL`). Крім того, класичний синтаксис не підтримує умовні стрибки — він не дає змоги пропустити наступні N модулів у стеку, якщо поточна перевірка пройшла успішно (наприклад, оминути перевірку локального пароля при успішному розпізнаванні токена). Для розв'язання цих обмежень у сучасних дистрибутивах використовується розширений синтаксис керування у квадратних дужках:

```
[значення_коду_1=дія_1  значення_коду_2=дія_2 ... default=дія_за_замовчуванням]
```

Дії визначають точний крок обчислювача `libpam`:
- `ok`: Прирівняти статус до успішного, якщо раніше не було помилок `required`.
- `done`: Перервати стек та повернути поточний статус (аналог `sufficient`/`requisite`).
- `bad`: Позначити фазу як невдалу, але продовжити стек (аналог `required`).
- `die`: Позначити фазу як невдалу та негайно перервати стек (аналог `requisite`).
- `ignore`: Ігнорувати код повернення даного модуля.
- `reset`: Забути весь накопичений стан стеку й почати оцінювання наново з наступного модуля.
- `N` (ціле число): Пропустити наступні `N` модулів у стеку.

| Складний примітив | Еквівалентна дія обчислювача libpam |
| :--- | :--- |
| `[success=ok default=bad]` | Відповідає класичному прапорцю `required` |
| `[success=ok default=die]` | Відповідає класичному прапорцю `requisite` |
| `[success=done default=ignore]` | Відповідає класичному прапорцю `sufficient` |
| `[success=2 default=ignore]` | У разі успіху пропустити наступні 2 модулі в стеку |

## Геометрія конфігураційних файлів у /etc/pam.d/

Конфігураційні правила зберігаються у директорії `/etc/pam.d/`, де назва кожного файлу відповідає назві сервісу, що передається у функцію `pam_start()`. При зверненні сервісу `sshd` читається файл `/etc/pam.d/sshd`. Якщо файл сервісу відсутній, `libpam` використовує конфігурацію за замовчуванням `/etc/pam.d/other`.

Щоб уникнути дублювання стандартних правил між сотнями сервісів, використовуються директиви вкладення:

### `@include` та `include`
Просто вставляють вміст вказаного файлу у поточний стек на місце директиви. Усі контрольні прапорці включеного файлу діють так, ніби вони були записані в основному файлі.

### `substack`
При використанні директиви `include` вміст включеного файлу підставляється безпосередньо в головний стек. Якщо у включеному файлі спрацьовує прапорець `sufficient` або `requisite`, він перериває обчислення всього головного стеку, а прапорець `required` виставляє біт фатальної помилки `must_fail` для всього головного стеку. Це унеможливлює створення безпечних підмодулів, адже внутрішня логіка спільного файлу конфігурації (наприклад, `system-auth`) починає безпосередньо впливати на перевірки у батьківському сервісі (наприклад, `sudo`).

Для усунення цього побічного ефекту розроблено механізм вкладених стеків. Виклики у вкладеному файлі оцінюються як **окремий ізольований стек**. Результат виконання всього підстеку згортається в один підсумковий код повернення, який повертається в батьківський стек і оцінюється за правилом рядка `substack`.

```
Головний стек (/etc/pam.d/sudo)        Підстек (/etc/pam.d/system-auth)
+-------------------------------+      +-------------------------------+
| auth sufficient pam_rootok.so |      | auth required pam_faillock.so |
| auth substack system-auth     | ---> | auth sufficient pam_unix.so   |
| session include system-auth   |      | auth required pam_deny.so     |
+-------------------------------+      +-------------------------------+
                                                      |
                                                      v (згортання результату)
                                       Повертає PAM_SUCCESS або помилку
```

Розглянемо типовий файл конфігурації `/etc/pam.d/sudo`:

```pam
# /etc/pam.d/sudo
auth       sufficient   pam_rootok.so
auth       substack     system-auth
account    required     pam_nologin.so
account    include      system-auth
session    required     pam_env.so
session    include      system-auth
```

1. Перший рядок `auth sufficient pam_rootok.so` перевіряє, чи викликає `sudo` користувач `root`. Якщо так — автентифікація миттєво зараховується без запиту пароля.
2. Якщо ж це звичайний користувач, `pam_rootok.so` повертає `PAM_AUTH_ERR`. Оскільки прапорець `sufficient` при невдачі ігнорується, процес рухається до `substack system-auth`, де відбувається стандартна перевірка пароля чи токена.

## Протокол розмови (Conversation Protocol)

Функція розмови (conversation function) — це серце абстракції PAM. Вона вирішує принципове питання: як модуль, що виконується всередині `libpam.so`, може показати текст користувачеві чи прочитати пароль, якщо сам модуль не знає, де працює — у графічному оточенні GNOME, у консолі `tty` чи через мережевий зашифрований канал SSH?

![Протокол розмови у стеку PAM](/reference/unix-linux/permissions/pam-authentication-stack/img/pam-conv-handshake.svg)
*Протокол розмови дозволяє модулю запитувати дані у користувача через зворотний виклик (callback) у прикладному застосунку.*

Прикладна програма створює структуру `struct pam_conv` та передає її у `pam_start()`. Коли модулю (наприклад, `pam_unix.so`) потрібен пароль, він викликає цю функцію, передаючи масив структур `struct pam_message`:

```c
struct pam_message {
    int msg_style;      /* PAM_PROMPT_ECHO_OFF, PAM_PROMPT_ECHO_ON, PAM_ERROR_MSG, PAM_TEXT_INFO */
    const char *msg;    /* Текст підказки, наприклад "Password: " */
};
```

Застосунок отримує запит, відображає його у своєму інтерфейсі (наприклад, ховає символи в GUI-полі або консолі), виділяє пам'ять під відповідь `struct pam_response` і повертає її модулю. Повний довідник за функціями бібліотеки та структурою даних зібрано у [довіднику C та C++ API бібліотеки PAM](book:unix-linux/pam-authentication-stack/api-pam-library-contract.md).

## Взаємодія з ядром, привілеями та підсистемами Linux

Бібліотека PAM працює у просторі користувача (userspace), проте її модулі безпосередньо взаємодіють із механізмами ядра Linux та підсистемами безпеки:

### Безпечний доступ до `/etc/shadow` через `unix_chkpwd`
Прикладні програми, що використовують PAM (наприклад, екранний заставник `xscreensaver`), працюють від імені звичайного неуповноваженого користувача. Проте модуль `pam_unix.so` повинен перевірити введений пароль проти `/etc/shadow`. 

Щоб не надавати самому `xscreensaver` привілеїв root, модуль `pam_unix.so` запускає через `fork()` та `execve()` допоміжний системний бінарний файл `/sbin/unix_chkpwd`. Цей файл має встановлений біт SUID root або належить до групи `shadow`. Він приймає введений пароль через конвеєр (pipe), перевіряє його та повертає кодову відповідь. Таким чином, основна програма не отримує прямого доступу до бази хешів.

```
[Прикладний процес (UID 1000)]
         |
         | (запуск через fork/execve)
         v
[/sbin/unix_chkpwd (SUID root)] ---> читає /etc/shadow ---> повертає 0 або 1
```

### Модифікація системних обмежень (`pam_limits.so`)
Під час фази `session` модуль `pam_limits.so` зчитує конфігурацію з `/etc/security/limits.conf`. Він виконує системний виклик `setrlimit()`, встановлюючи максимальну кількість відкритих файлів (`RLIMIT_NOFILE`), процесорний час (`RLIMIT_CPU`) або межу пам'яті для процесу користувача перед запуском оболонки.

### Інтеграція з SELinux та LSM (`pam_selinux.so`)
При вході користувача модуль `pam_selinux.so` визначає безпечний контекст сесії (наприклад, `user_u:user_r:user_t:s0`). Модуль записує отриманий контекст у спеціальний файл контролю ядра `/proc/self/attr/exec`. Завдяки цьому наступний системний виклик `execve()`, який запускає командну оболонку користувача, атомарно переводить новий процес у відповідний контекст безпеки SELinux.

### Збереження токенів у ядрі (`pam_keyinit.so`)
Модуль `pam_keyinit.so` звертається до підсистеми збереження секретів ядра (Kernel Keyring). Він викликає `add_key()` або `keyctl()`, створюючи нову сесійну зв'язку ключів `KEY_SPEC_SESSION_KEYRING` та прив'язуючи до неї токени Kerberos чи ключі шифрування файлової системи.

### Управління контрольно-ресурсними групами (`pam_systemd.so`)
Модуль `pam_systemd.so` під час відкриття сесії надсилає D-Bus повідомлення до системного демона `systemd-logind`. Демон створює для сесії новий scope у слайсі користувача (наприклад, `/sys/fs/cgroup/user.slice/user-1000.slice/session-2.scope`) та переміщує туди PID процесу користувача, забезпечуючи ізоляцію ресурсів та коректне завершення всіх фонових процесів при виході з системи.

## Розробка власного модуля PAM

Створення власного модуля PAM зводиться до компіляції динамічної бібліотеки `.so`, яка експортує визначені специфікацією C-функції з префіксом `pam_sm_`. Детальний приклад створення кастомного модуля з підтримкою C та C++ подано у [практичній реалізації власного модуля PAM](book:unix-linux/pam-authentication-stack/proj-custom-pam-module.md).

Критичні вимоги до сирцевого коду модулів PAM:
- **Безпека пам'яті:** Будь-які чутливі дані (паролі, PIN-коди) у буферах пам'яті модулів повинні обов'язково очищатися за допомогою `explicit_bzero()` або `memset_s()` перед звільненням пам'яті, щоб запобігти витоку секретів у дампах пам'яті.
- **Потокобезпечність (Thread Safety):** Модуль не повинен використовувати глобальні статичні змінні без належного блокування, оскільки `libpam` може викликатися у багатопотокових демонах.
- **Ізоляція помилок:** Будь-який необроблений виняток (exception) або падіння (segmentation fault) у коді модуля призводить до падіння всього прикладного демона (наприклад, `sshd`), що відкриває можливість для відмови у обслуговуванні (DoS).

## Вразливості, помилки налаштування та системна ціна

Гнучкість PAM створює потенційні ризики при помилках у геометрії стеків конфігурації.

### 1. Обхід автентифікації через невірне розміщення sufficient
Найпоширенішою адміністративною помилкою є розміщення модуля `pam_permit.so` або невдало налаштованого `pam_succeed_if.so` з прапорцем `sufficient` вище за основний модуль автентифікації. Якщо модуль `sufficient` повертає успіх, виконання стеку припиняється, і зловмисник отримує доступ у систему без перевірки пароля.

### 2. Привілеї модуля в контексті викликача
Динамічні модулі PAM завантажуються безпосередньо в адресний простір процесу, що викликав `libpam`. Якщо процес `sudo` або `sshd` працює з UID 0, то й кожен рядок коду всередині модуля PAM виконується з повними привілеями `root`. Помилка переповнення буфера у сторонньому модулі PAM дає миттєвий віддалений компроміс всієї операційної системи.

### 3. Витік файлових дескрипторів
Якщо модуль PAM відкриває системні файли чи сокети й не встановлює прапорець `FD_CLOEXEC`, ці дескриптори залишаються відкритими й успадковуються дочірніми процесами користувача після виклику `execve()`, надаючи неуповноваженому користувачеві доступ до службових каналів.

Незважаючи на ці ризики, Pluggable Authentication Modules залишаються фундаментальним стандартом безпеки у світі UNIX/Linux. Абстрагування логіки перевірок у 4 фази (`auth`, `account`, `session`, `password`), прозора підтримка протоколу розмови та гнучкість обчислення стеків роблять PAM універсальним інструментом побудови сучасних систем ідентифікації.
