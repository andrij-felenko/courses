# 📜 Історія та еволюція стандарту PAM: від монолітних утиліт до модульної автентифікації

Коли у перших дистрибутивах UNIX виникала потреба додати новий метод автентифікації користувачів, розробникам доводилося модифікувати та перекомпільовувати сирцевий код кожної системної утиліти входу. Розуміння того, як виникла архітектура Pluggable Authentication Modules, розкриває історичний контекст переходу UNIX від жорстко зашитих перевірок у `/etc/passwd` до гнучкої моделі динамічних модулів.

## Борг монолітних перевірок у ранніх версіях UNIX

У системі UNIX 1970-х та початку 1980-х років процес перевірки токена доступу був нерозривно пов'язаний з логікою самих утиліт входу. Програми `login`, `su`, `passwd`, `ftpd` та `rshd` самостійно відкривали системний файл `/etc/passwd`, зчитували хешований пароль за допомогою системної функції `getpwnam()` та порівнювали його з введеним значенням через виклик `crypt()`.

Перші реалізації `crypt()` спиралися на спрощену версію алгоритму DES (Data Encryption Standard) з 12-бітним випадковим значенням солі (salt) та 56-бітним ключем. Оскільки файл `/etc/passwd` був доступний для читання всім користувачам системи (права `0644`), будь-який користувач міг скопіювати хеші паролів на власний комп'ютер та провести офлайн-перебір методом прямого перебору (brute-force) або за допомогою словникових атак.

З появою у середині 1980-х років механізму теневих паролів (shadow passwords) у системі UNIX System V Release 3.2 та BSD 4.3 хеші паролів було винесено в окремий файл `/etc/shadow`. Файл `/etc/shadow` отримав суворі права доступу `0600` (читання лише суперкористувачем `root`), щоб унеможливити читання хешів звичайними обліковими записами.

Ця зміна породила першу масштабну архітектурну проблему. Оскільки звичайні користувачі не мали права читати `/etc/shadow`, програмам автентифікації (наприклад, екранному заставникові чи утиліті зміни пароля `passwd`) знадобилося встановити спеціальний атрибут SUID root (`chmod u+s`). Кожна програма, якій потрібно було бодай один раз перевірити пароль, ставала повноправним бінарним файлом із привілеями суперкористувача. Помилка переповнення буфера в будь-якому термінальному демоні означала повний компроміс системи.

Ситуація остаточно зайшла в кут із розвитком корпоративних мереж на початку 1990-х років. З появою мережевих каталогів Sun NIS (Network Information Service), служб централізованої автентифікації Kerberos v4/v5 та смарт-карток PKCS#11 кожен вендор намагався адаптувати системні утиліти під свої потреби. Додавання підтримки Kerberos у мережевий демон `ftpd` вимагало переписання сирцевого коду демона, додавання прямих викликів бібліотек Kerberos та повторної компіляції. Якщо організація мала власний унікальний фактор автентифікації, його впровадження вимагало підтримки власних форків усіх системних утиліт ОС.

## Ініціатива Sun Microsystems та RFC 86.0 (1995)

У жовтні 1995 року інженери компанії Sun Microsystems Віпін Самар (Vipin Samar) та Роланд Счемерс (Roland J. Schemers III) запропонували принципово нову архітектурну концепцію — Pluggable Authentication Modules (PAM). Свій задум вони описували як «абстрактну платформу, яка дозволяє змінювати системну політику автентифікації без перекомпіляції системних програм».

Головною ідеєю PAM стало строге розділення привілейованого застосунку та механізму перевірки на два незалежні рівні:

1. **Прикладний шар (Application Layer):** Програми викликають стандартизований API (`pam_start()`, `pam_authenticate()`), абсолютно не знаючи, де зберігаються паролі — в `/etc/shadow`, у базі даних LDAP чи на віддаленому сервері RADIUS.
2. **Шар модулів (Module Layer):** Системний адміністратор описує конфігурацію стеків у текстових файлах, а бібліотека-посередник під час виконання завантажує динамічні об'єкти `.so` за допомогою системних викликів `dlopen()` та `dlsym()`.

Основою стандартизації став документ Open Software Foundation (OSF) RFC 86.0, заснований на роботах групи X/Open Single Sign-On (XSSO). Стандарт визначив чотири фундаментальні групи управління (Management Groups): `auth`, `account`, `session` та `password`. Щоб відокремити інтерфейс користувача (GUI чи CLI) від логіки модуля, стандарт ввів зворотний виклик через функцію розмови (conversation function `pam_conv`). Це дозволило модулям запитувати дані у користувача через графічні вікна або термінал, не прив'язуючись до I/O пристроїв.

## Поява Linux-PAM та розходження реалізацій

Ідея Sun Microsystems виявилася настільки вдалою, що її швидко підхопили розробники всього UNIX-світу. Проте в процесі адаптації сформувалися дві основні гілки реалізації стандарту.

### Linux-PAM: розширюваність та гнучкість
У 1996 році Ендрю Морган (Andrew G. Morgan) ініціював проєкт Linux-PAM для операційної системи Linux. Linux-PAM не лише реалізував стандарт RFC 86.0, але й суттєво розширив його можливості:

- **Каталог `/etc/pam.d/`:** Замість єдиного монолітного файлу конфігурації `/etc/pam.conf` Linux-PAM увів окрему директорію, де кожен сервіс отримав власний конфігураційний файл (`sshd`, `sudo`, `login`). Це спростило пакетизацію модулів дистрибутивами.
- **Складні графі керування:** Окрім чотирьох класичних прапорців (`required`, `requisite`, `sufficient`, `optional`), було додано новий синтаксис `[value=action]`, що дозволяє здійснювати безумовні стрибки через модулі та будувати складні дерева рішень.
- **Директиви включення:** Додано підтримку `@include` та `substack` для ізольованого обчислення підстеків.

### OpenPAM: строгість стандарту та безпека
Операційні системи FreeBSD, NetBSD, DragonFly BSD та Apple macOS обрали інший шлях і створили реалізацію OpenPAM, розроблену Дагом Рабсоном (Dag-Erling Smørgrav). 

Філософія OpenPAM спирається на мінімалізм та сувору відповідність специфікації XSSO:
- Відсутність невідповідних стандарту розширень керування прапорцями.
- Строгий контроль за безпекою завантаження динамічних бібліотек через `dlopen()` з перевіркою власника та прав доступу файлів модулів (захист від підміни `.so` через `LD_PRELOAD` або неавторизований запис).
- Чітка ізоляція пам'яті та захист від витоків дескрипторів.

| Характеристика | Sun PAM (1995) | Linux-PAM | OpenPAM |
| :--- | :--- | :--- | :--- |
| **Основні платформи** | Solaris / Illumos | Linux (Debian, RHEL, Arch) | FreeBSD, NetBSD, macOS |
| **Формат конфігурації** | `/etc/pam.conf` | `/etc/pam.d/` та `pam.conf` | `/etc/pam.d/` та `pam.conf` |
| **Контрольні прапорці** | 4 класичні | Класичні + `[code=action]` | 4 класичні прапорці |
| **Підтримка `substack`** | Ні | Так | Ні (використовує `include`) |
| **Сумісність із XSSO** | Базова | Розширена (з нонами) | Строга відповідність |

## Сучасний етап: PAM у добу контейнерів та FIDO2/Passkeys

У сучасній інфраструктурі платформа PAM продовжує активно розвиватися, адаптуючись до нових безпекових викликів:

1. **Інтеграція з SSSD (System Security Services Daemon):** Завдяки модулю `pam_sss.so` сучасні серверні системи Linux підключаються до Active Directory, FreeIPA та LDAP каталогів. SSSD виконує локальне кешування токенів, дозволяючи виконувати автентифікацію навіть при тимчасовій втраті мережевого зв'язку з домен-контролером.
2. **Апаратна автентифікація FIDO2/WebAuthn:** Модулі на кшталт `pam_u2f.so` додають підтримку апаратних ключів YubiKey та біометричних систем (TouchID/FaceID) безпосередньо у стек автентифікації `sudo` або `sshd`.
3. **Контейнеризація та cgroups v2:** Модуль `pam_systemd.so` забезпечує зв'язок між відкриттям сесії PAM та викликом D-Bus API `systemd-logind`. При вхідній сесії ядро прозоро виділяє ізольований cgroup slice для користувача, гарантуючи контроль за ресурсами CPU та RAM.

Історія PAM демонструє важливий архітектурний урок: вчасна відмова від монолітних перевірок на користь стандартизованого динамічного прошарку дозволила системі UNIX зберегти гнучкість та забезпечити безпеку протягом кількох десятиліть технологічних змін.
