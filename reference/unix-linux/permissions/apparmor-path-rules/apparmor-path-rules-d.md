Коли мережевий службовий процес, такий як вебсервер Nginx або СУБД PostgreSQL, піддається компрометації через вразливість у коді (наприклад, через переповнення буфера, впорскування коду або віддалене виконання коду, RCE), дискреційна модель доступу Linux (DAC) оцінює привілеї атакованого процесу виключно за його ефективним ідентифікатором користувача (`eUID`). Якщо Nginx запущено від імені системного облікового запису `www-data`, зловмисник, що захопив контроль над потоком виконання, отримує право читати будь-які файли в системі, відкриті для зчитування даному користувачу, створювати виконувані файли у каталозі `/tmp` та встановлювати мережеві з'єднання з довільними вузлами. Традиційні розмежування DAC виявляються безсилими, оскільки вони перевіряють, *хто* запустив процес, а не *що саме* цьому конкретному бінарному файлу дозволено робити в рамках його службових обов'язків.

Система примусового контролю доступу (MAC — Mandatory Access Control) AppArmor виправляє цю фундаментальну прогалину, прив'язуючи суворий шар обмежень безпосередньо до виконуваного бінарного файла за його абсолютним шляхом у файловій системі.

## 1. Захист бінарних служб та перехоплення викликів у VFS

У системі з активним AppArmor спроба процесу виконати будь-яку дію з файловою системою, мережею або системними привілеями проходить двофазову авторизацію. Першою фазою залишається класична перевірка DAC: ядро Linux звіряє права доступу бітів `mode` (rwx) та ідентифікатори `UID`/`GID` відповідного `inode`. Якщо перевірку DAC пройдено успішно, ядро не відразу виконує операцію, а передає управління у фреймворк Linux Security Modules (LSM).

Під час завантаження ядра модуль AppArmor реєструє власні обробники хуків у глобальній таблиці LSM-операцій (`security_add_hooks`). У структурі `cred->security` кожного процесу зберігається посилання на його активний політичний контекст — структуру `aa_label` (або `aa_profile`). На відміну від SELinux, який пов'язує політики безпеки з розширеними атрибутами файлів (`xattr` security labels) і перевіряє мітки безпосередньо в структурі `inode`, AppArmor працює на рівні файлових шляхів Віртуальної файлової системи (VFS). Коли процес виконує системний виклик `openat(AT_FDCWD, "/etc/shadow", O_RDONLY)`, хук AppArmor LSM перехоплює цей виклик і аналізує не числове значення `inode`, а текстовий шлях файлу відносно кореня маунт-простору процесу.

Такий підхід позбавляє адміністратора потреби перемарковувати вміст диска (`relabeling`) під час відновлення системи або додавання нових носіїв. Профіль AppArmor є звичайним текстовим файлом конфігурації, прив'язаним до шляху бінарника (наприклад, `/usr/sbin/nginx`), що дозволяє створювати ізольовані контейнери безпеки для кожної програми окремо.

Ланцюжок прийняття рішень під час здійснення файлового системного виклику складається з послідовних кроків:

```
[Системний виклик (openat)] 
           │
           ▼
[Перевірка DAC (UID/GID, mode)] ──(Відмова)──> [-EPERM / -EACCES]
           │
       (Успіх)
           ▼
[LSM Hook: security_file_open]
           │
           ▼
[Відновлення шляху d_path()]
           │
           ▼
[Зіставлення з DFA AppArmor] ─────(Порушення)──> [-EACCES + Audit Event]
           │
       (Дозвіл)
           ▼
[Відкриття файла та повернення fd]
```

Навіть у випадку компрометації бінарного файла з правами `root` (наприклад, через вразливість утиліти зі встановленим бітом `SUID`), AppArmor обмежує права процесу рамками його профілю. Якщо для бінарника заборонено запуск командної оболонки `/bin/sh` або зчитування ключів `/root/.ssh/id_rsa`, ядро заблокує ці операції незалежно від того, що `eUID == 0`.

Таке розмежування забезпечує принципову перевагу: навіть якщо вразливість нульового дня (0-day) дозволяє зловмиснику домогтися виконання довільного машинного коду всередині адресного простору Nginx, спроба відкрити непередбачений конфігураційний файл чи підключитися до службового сокету буде зупинена ядром Linux на етапі аналізу LSM-хука, запобігаючи подальшому просуванню атаки по системі (lateral movement).

## 2. Механіка відновлення шляху ядра через d_path()

Оскільки внутрішнє ядро Linux працює з файлами через об'єкти пам'яті `struct dentry` (Directory Entry) та `struct vfsmount` (точка монтування), ядро не зберігає повний текстовий шлях файлу всередині структури `struct file` або `struct inode`. Для перевірки AppArmor мусить динамічно реконструювати абсолютний шлях файлу в момент здійснення системного виклику.

Коли операція досягає LSM-хука доступу до шляхів (наприклад, `security_path_mkdir` або `security_file_open`), ядро отримує структуру `struct path`, яка містить посилання на `dentry` та `vfsmount`. AppArmor викликає внутрішню функцію ядра `d_path()`.

```
[struct path] ──> dentry (file.txt) ──> dentry (log) ──> dentry (var) ──> root
                        │
                        └──> vfsmount (mnt_root) ──> d_path() ──> "/var/log/file.txt"
```

Внутрішньо функція `d_path()` виділяє тимчасовий буфер пам'яті (розміром в одну сторінку `PAGE_SIZE`, зазвичай 4096 байтів) і розміщує вказівник у кінець цього буфера. Потім вона виконує рекурсивний обхід дерева `dentry` знизу вгору — від цільового файла до кореневого каталогу (`/`), записуючи компоненти шляху у зворотному напрямку та розділяючи їх символом `/`.

Щоб запобігти стану гонки (race condition) під час одночасного перейменування файлів іншими процесами, обхід `dentry` захищається послідовним блокуванням `rename_lock` та механізмом RCU (`rcu_read_lock`). Коли обхід доходить до кореня поточної точки монтування (`mnt->mnt_root`), функція переходить через межу монтування у батьківську точку монтування (`real_mount(mnt)->mnt_mountpoint`), продовжуючи підйом до кореня маунт-простору процесу.

Цей механізм створює кілька специфічних крайових випадків, які відрізняють AppArmor від inode-орієнтованих систем MAC:

1. **Простори імен монтування та chroot**: Якщо процес виконується всередині ізольованого оточення `chroot` або контейнера з власним `mount namespace`, корінь процесу може відрізнятися від кореня всієї системи. За замовчуванням `d_path()` повертає шлях відносно кореня поточного маунт-простору. Якщо файл знаходиться поза цим коренем (disconnected path), AppArmor за замовчуванням відмовляє в доступі до такого відірваного шляху; прапорець профілю `attach_disconnected` наказує натомість долучити його до кореня простору імен процесу й перевіряти як звичайний.
2. **Перемонтування (Bind mounts)**: Створення перемонтованого каталогу через `mount --bind /var/data /mnt/data` робить ті самі файли доступними за новими шляхами. AppArmor перевірятиме той текстовий рядок шляху, через який здійснюється відкриття, тому правильний профіль повинен описувати або обидва шляхи, або використовувати маски.
3. **Жорсткі посилання (Hard links)**: Жорсткі посилання живуть у межах однієї файлової системи, тож `/etc/passwd` і `/etc/backup/passwd_link` можуть указувати на один і той самий `inode`. Проте AppArmor авторизує доступ виключно за тим шляхом, який був використаний при виклику `open()`. Якщо профіль дозволяє читання `/etc/passwd`, але нічого не каже про `/etc/backup/**`, спроба відкрити той самий inode через посилання `/etc/backup/passwd_link` буде заблокована.
4. **Видалені файли (Deleted files)**: Якщо процес утримує файловий дескриптор файла, який був видалений з диска іншим процесом, `d_path()` повертає рядок із суфіксом ` (deleted)`. Звичайні правила профілю такий шлях уже не покривають, а посередництво над видаленими об'єктами вмикає окремий прапорець профілю `mediate_deleted`.
5. **Операції перейменування (Rename)**: При виконанні `rename()` ядро викликає хук `security_path_rename`, передаючи йому як старий, так і новий `struct path`. AppArmor атомарно перевіряє права на видалення зі старого шляху та створення за новим шляхом до здійснення модифікації дерева `dentry`.

Прочитати про [історію розробки SubDomain та дебати в LKML щодо шляхового підходу](book:unix-linux/apparmor-path-rules/hist-apparmor-pathname-lsm.md) можна у відповідній вставці.

## 3. Компіляція правил у детерміновані скінченні автомати (DFA)

Пряме порівняння текстового шляху файлу з сотнями масок та правил під час кожного системного виклику створило б неприпустимі накладні витрати й сповільнило б виконання операцій I/O. Якби ядро послідовно перевіряло рядок `/var/log/nginx/access.log` проти кожного правила у профілі за допомогою послідовних порівнянь, складність перевірки складала б `O(M · N)`, де `M` — кількість правил у профілі, а `N` — довжина шляху.

Для досягнення високої продуктивності AppArmor переносить обчислювальне навантаження на етап завантаження політики у простір користувача. Утиліта `apparmor_parser` компілює текстовий профіль у Детермінований Скінченний Автомат (DFA — Deterministic Finite Automaton).

![Схема відновлення шляху VFS та перевірки LSM](/reference/unix-linux/permissions/apparmor-path-rules/img/apparmor-vfs-path-resolution.svg)
*Механізм перехоплення VFS-викликів LSM-хуком AppArmor та генерація абсолютного шляху через d_path()*

Процес компіляції проходить кілька етапів:
- **Генерація НФА (NFA, побудова Томпсона)**: Синтаксичні правила з шаблонами (`*`, `**`, `?`, `{...}`) розгортаються у Недетермінований Скінченний Автомат.
- **Детермінізація (побудова підмножин, Рабіна–Скотта)**: NFA перетворюється на DFA, де кожному стану відповідає унікальний набір переходів.
- **Мінімізація (Алгоритм Хопкрофта)**: Еквівалентні стани DFA об'єднуються для зменшення обсягу оперативної пам'яті.

DFA — це граф станів, де переходи між станами відбуваються поодинокими символами файлового шляху. Усі маски під час компіляції розгортаються у відповідні ребра автомата.

![Схема обходу скінченного автомата DFA](/reference/unix-linux/permissions/apparmor-path-rules/img/apparmor-dfa-matching.svg)
*Політерний обхід скінченного автомата (DFA) під час зіставлення шляху з правилом дозволу; мітки на ребрах згортають ланцюжки односимвольних переходів*

У пам'яті ядра DFA зберігається у вигляді п'яти стиснутих одномірних таблиць: `base`, `check`, `next`, `default` та `accept`. Під час завантаження бінарного блоба функція ядра `aa_dfa_unpack()` перевіряє цілісність цих таблиць і переконується у відсутності циклів або виходів за межі виділених масивів.

Обхід стану для кожного наступного символу шляху `c` здійснюється за один обчислювальний крок:

```
next_state = check[base[current_state] + c] == current_state 
             ? next[base[current_state] + c] 
             : default[current_state]
```

Ця технологія стиснення переходів (запозичена з класичних лексичних аналізаторів flex) забезпечує гранично компактне представлення графа в пам'яті ядра та мінімальне використання кешу процесора (L1/L2 data cache).

Коли ядро перевіряє доступ для згенерованого шляху, функція `aa_dfa_match_len()` здійснює політерний обхід DFA:

1. Вхідний рядок (наприклад, `/var/log/app.log`) подається на вхід автомата символ за символом.
2. Ядро виконує перехід між станами DFA за допомогою вищезазначених бінарних таблиць.
3. Досягнувши кінця рядка шляху, ядро зчитує з кінцевого стану автомата (accepting state) бітову маску дозволених прав (`allow`), маску запитів журналу (`audit`) та маску явних заборон (`deny`).

Завдяки DFA складність перевірки доступу становить `O(N)`, де `N` — довжина текстового шляху. Час перевірки повністю не залежить від кількості правил у профілі: профіль з 10 правилами та профіль з 50 000 правил перевіряються практично однаково швидко — різницю дає хіба що більший обсяг таблиць у кеші процесора.

## 4. Структура профілю, синтаксис масок та режими переходу exec

Профілі AppArmor розміщуються в директорії `/etc/apparmor.d/`. Імена файлів зазвичай повторюють абсолютний шлях до бінарника, де слеші замінено крапками (наприклад, профіль для `/usr/sbin/nginx` зберігається у файлі `/etc/apparmor.d/usr.sbin.nginx`).

Для зменшення дублювання правил AppArmor використовує механізм абстракцій. Директива `#include <abstractions/base>` підключає стандартні правила, необхідні для роботи майже будь-якої програми в Linux (доступ до динамічного завантажувача `/lib/ld-linux*.so`, базових системних бібліотек C `libc.so`, налаштувань локалі та часових поясів).

Кожен профіль визначає маски прав для конкретних шляхів, мережевих сокетів, POSIX capabilities та правил виконання додаткових програм через системний виклик `execve()`:

```apparmor
#include <tunables/global>

/usr/sbin/nginx flags=(complain, attach_disconnected) {
  #include <abstractions/base>
  #include <abstractions/nameservice>

  # Права доступу до бінарників та конфігурації
  /usr/sbin/nginx mr,
  /etc/nginx/** r,
  /var/log/nginx/* rw,
  /run/nginx.pid rw,

  # POSIX привілеї та мережеві сокети
  capability net_bind_service,
  capability setuid,
  capability setgid,
  network inet tcp,
  network inet6 tcp,

  # Перехід при виконанні допоміжних скриптів
  /usr/bin/display_status Px,

  # Явна заборона доступу до приватних ключів
  deny /etc/ssl/private/dangerous.key r,
}
```

Файлові права включають прапорці:
- `r` (read) — дозвіл на зчитування даних;
- `w` (write) — дозвіл на модифікацію та перезапис;
- `a` (append) — дозвіл лише на дописування в кінець файла;
- `l` (link) — створення жорстких посилань;
- `k` (lock) — файлове блокування (`flock`/`fcntl`);
- `m` (memory map) — відображення у пам'яті із правом виконання (`PROT_EXEC`).

Особливе значення мають модифікатори виконання (`exec transitions`):
- `ix` (inherit): новий процес успадковує поточний профіль.
- `px` / `Px` (profile): новий процес переходить у власний окремий профіль AppArmor. Варіант `Px` додатково очищує змінні середовища `LD_PRELOAD` та `LD_LIBRARY_PATH` для запобігання впорскуванню сторонніх бібліотек.
- `cx` / `Cx` (child): перехід у вкладений підпрофіль (child profile).
- `ux` / `Ux` (unconfined): новий процес повністю виходить з-під контролю AppArmor і виконується без обмежень MAC.
- `pix` / `pux`: комбіновані резервні режими (якщо цільовий профіль існує — переходить у нього, інакше успадковує `ix` або виходить у `ux`).

Правила заборони з ключовим словом `deny` мають абсолютний пріоритет над будь-якими дозволами `allow`. Якщо в профілі вказано `allow /etc/nginx/** r` та `deny /etc/nginx/secret.conf r`, спроба відкрити `secret.conf` буде негайно заблокована.

Ознайомитися з [повним довідником масок доступу, підстановочних символів та режимів переходу exec](book:unix-linux/apparmor-path-rules/api-apparmor-rule-syntax.md) можна у спеціальній вставці.

## 5. Режими Enforce та Complain, журналювання auditd

AppArmor підтримує два основних режими роботи для кожного завантаженого профілю:

1. **Режим Enforce (Примусовий)**: Усі правила безпеки активно застосовуються ядром. При спробі виконання недозволеної операції LSM-хук повертає процесу помилку `-EACCES` (`-13`, Permission denied). Одночасно ядро генерує запис у системний журнал auditd з типом `AVC` або `APPARMOR_DENIED`.
2. **Режим Complain (Навчання / Скарги)**: Спроба виконання недозволеної операції не блокується — LSM-хук повертає `0` (успіх), і програма продовжує функціонування. Проте ядро фіксує факт порушення в журналі із позначкою `apparmor="ALLOWED"`.

Типове повідомлення підсистеми аудиту в журналі системних подій має наступний вигляд:

```text
type=AVC msg=audit(1628765432.123:456): apparmor="DENIED" operation="open" 
profile="/usr/sbin/nginx" name="/etc/shadow" pid=1420 comm="nginx" 
requested_mask="r" denied_mask="r" fsuid=33 ouid=0
```

У повідомленні чітко зафіксовано назву профілю (`profile`), операцію (`operation="open"`), цільовий шлях (`name="/etc/shadow"`), ідентифікатор процесу (`pid`), запитану маску прав (`requested_mask="r"`) та ідентифікатори користувача (`fsuid` процесу й `ouid` власника файла). Якщо адміністратор прагне приглушити журналювання для певних очікуваних заперечень, у профілі можна використати префікс `quiet deny`.

Режим Complain є основним інструментом для розробки нових політик безпеки. Процес створення профілю складається з п'яти кроків:

```
[Порожній профіль] ──> aa-complain ──> [Тестування програми] ──> aa-logprof ──> aa-enforce
```

Для керування режимами та аналізу логів використовується набір утиліт `apparmor-utils`:
- `aa-status`: показує список завантажених профілів, їхні режими та перелік процесів, що працюють під захистом профілів.
- `aa-complain /path/to/binary`: переводить профіль бінарника в режим скарг.
- `aa-enforce /path/to/binary`: переводить профіль у строгий режим Enforce.
- `aa-logprof`: інтерактивна утиліта, яка розбирає журнали аудиту (`/var/log/audit/audit.log` або `journalctl`) і пропонує користувачеві автоматично доповнити профіль новими правилами на основі зафіксованих дій.
- `aa-genprof`: покроковий майстер створення нового профілю для бінарного файла.
- `aa-autodep`: автоматична генерація базового каркаса профілю на основі аналізу залежностей бінарника (зчитування зв'язаних shared libraries через `ldd`).

## 6. Завантаження профілів у ядро через securityfs та procfs

Ядро Linux не містить всередині текстового парсера для аналізу файлів конфігурації у `/etc/apparmor.d/`. Переклад текстового опису в бінарний блоб DFA здійснюється утилітою `apparmor_parser` в просторі користувача (userspace).

Передача згенерованого бінарного профілю в ядро здійснюється через віртуальну файлову систему **securityfs**, яка зазвичай змонтована за шляхом `/sys/kernel/security/`.

```
/etc/apparmor.d/usr.sbin.nginx ──> apparmor_parser -r ──> /sys/kernel/security/apparmor/.load ──> Policy Database
```

Утиліта `apparmor_parser` відкриває один зі спеціальних керуючих файлів у `/sys/kernel/security/apparmor/`:
- `.load`: запис бінарного блоба для завантаження нового профілю.
- `.replace`: запис бінарного блоба для атомарного оновлення існуючого профілю "на льоту".
- `.remove`: запис текстового імені профілю для його вивантаження з пам'яті ядра.

Записаний бінарний блоб має заголовок із магічним числом інтерфейсу політики, ідентифікатором ABI ядра та серіалізованими таблицями переходів DFA. Під час запису у файл `.replace` ядро атомарно змінює вказівник на таблицю DFA для всіх нових системних викликів. Запущені процеси негайно починають підпорядковуватися оновленій політиці без необхідності їхнього перезапуску.

Для прискорення завантаження під час старту ОС скомпільовані бінарні автомати кешуються у каталозі `/var/cache/apparmor/`. Якщо вихідний текстовий файл профілю у `/etc/apparmor.d/` не змінювався, `apparmor_parser` зчитує готовий бінарний блоб безпосередньо з кешу, що прибирає з завантаження найдорожчу частину — компіляцію правил у автомат.

Для перевірки стану конкретного процесу під час виконання можна використати віртуальну файлову систему `procfs`. Файл `/proc/<pid>/attr/apparmor/current` (або `/proc/<pid>/attr/current`) містить назву активного профілю та його поточний режим.

Багатопотокові сервери можуть додатково переходити у підпрофіль обробника запитів за допомогою ChangeHat API (`aa_change_hat()`), створюючи ізольовані пісочниці для кожного вхідного HTTP-з'єднання.

Детальний [приклад взаємодії з інтерфейсом procfs та securityfs на C та C++](book:unix-linux/apparmor-path-rules/proj-apparmor-securityfs-interface.md) розглянуто у відповідному матеріалі.

## 7. Продуктивність, порівняння з SELinux та межі застосування

Обираючи між AppArmor та SELinux, системні інженери зважують компроміс між простотою адміністрування та абсолютною гарантією контролю об'єктів.

| Характеристика | AppArmor | SELinux |
| :--- | :--- | :--- |
| **Базовий об'єкт** | Абсолютний шлях файлу у VFS (`d_path`) | Мітка безпеки `inode` (атрибут `security.selinux` у `xattr`) |
| **Прив'язка політики** | До виконуваного файлу за шляхом | До типів процесів та типів файлів (TE) |
| **Залежність від диска** | Немає (профілі зберігаються в `/etc/`) | Вимагає маркування диска (`relabeling`) |
| **Складність перевірки** | `O(N)` через DFA (де `N` — довжина шляху) | `O(1)` через AVC cache (перевірка SID) |
| **Обхід через Hard links** | Можливий, якщо шлях посилання не враховано | Неможливий (перевіряється сам `inode`) |

З точки зору накладних витрат продуктивності, обхід DFA у пам'яті ядра під час виклику `aa_dfa_match_len()` додає десятки-сотні наносекунд до часу виконання системного виклику `openat()` — по одному табличному переходу на кожен символ шляху. Основні витрати в AppArmor припадають на реконструкцію шляху функцією `d_path()`. Проте для переважної більшості реальних серверних навантажень ці витрати складають менше ніж 1% загального часу виконання I/O операцій.

Головна перевага AppArmor полягає в ізольованості та простоті: додати профіль для одного конкретного сервісу можна за кілька хвилин, не ризикуючи порушити роботу всієї системи. Відсутність вимог до розширених атрибутів файлової системи робить AppArmor ідеальним вибором для захисту систем у контейнерних середовищах (Docker, Snap, LXC) та на дистрибутивах Ubuntu/Debian/SUSE.

Разом із тим, інженери повинні враховувати особливості VFS: якщо застосунок покладається на складну динамічну структуру жорстких посилань або маніпулює переміщенням файлів між різними просторами імен монтування без налаштування прапорців `attach_disconnected`, створення профілю AppArmor вимагатиме ретельного тестування у режимі Complain.
