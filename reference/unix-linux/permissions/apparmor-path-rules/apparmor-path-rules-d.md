## Вступ

Безпека в сучасних операційних системах сімейства Linux базується не лише на традиційній моделі прав доступу (DAC — Discretionary Access Control), але й на системах примусового контролю доступу (MAC — Mandatory Access Control). Однією з найпопулярніших і найдоступніших систем MAC є **AppArmor** (Application Armor). Вона розроблена як модуль безпеки ядра Linux (LSM — Linux Security Modules) і пропонує інтуїтивно зрозумілий підхід до обмеження прав програм на основі їхніх шляхів у файловій системі.

У цьому розділі ми детально розглянемо архітектуру AppArmor, концепцію профілів на основі файлових шляхів, відмінності між режимами *enforce* і *complain*, основні інструменти управління (такі як `aa-status`, `aa-complain`, `aa-enforce`), а також механізм завантаження профілів у ядро через `securityfs`. Ця стаття розрахована на системних адміністраторів, інженерів з безпеки та розробників, які прагнуть глибоко розуміти механізми ізоляції та захисту процесів у Linux.

## 1. AppArmor як модуль LSM (Linux Security Modules)

Linux Security Modules (LSM) — це фреймворк ядра, який дозволяє різним моделям безпеки інтегруватися у процес прийняття рішень щодо доступу до системних ресурсів. Коли процес намагається виконати певну дію (наприклад, відкрити файл, створити мережевий сокет або змінити права), ядро спочатку перевіряє традиційні права DAC (owner, group, others). Якщо перевірку DAC пройдено, ядро звертається до активного модуля LSM (наприклад, AppArmor, SELinux або Smack) за додатковою авторизацією.

AppArmor відрізняється від свого головного конкурента SELinux тим, що він прив'язує права до **файлових шляхів**, а не до inode і розширених атрибутів файлів (xattrs). Це означає, що профіль AppArmor застосовується до виконуваного файлу за його шляхом (наприклад, `/usr/bin/nginx`), що значно спрощує адміністрування та написання політик безпеки.

### 1.1. Переваги підходу на основі шляхів

- **Простота розуміння:** Адміністратору легше читати та писати правила, використовуючи звичні файлові шляхи замість складних міток безпеки.
- **Відсутність необхідності маркування:** На відміну від SELinux, який вимагає перемаркування всієї файлової системи (relabeling) після оновлення або відновлення з бекапу, AppArmor не залежить від метаданих файлів на диску.
- **Гнучкість:** Профілі можна легко створювати, копіювати та поширювати, оскільки вони є звичайними текстовими файлами конфігурації.

### 1.2. Недоліки підходу на основі шляхів

- **Проблеми з жорсткими посиланнями (hardlinks):** Оскільки AppArmor контролює доступ за шляхом, створення жорсткого посилання на файл може потенційно дозволити обхід профілю, якщо цей новий шлях не врахований у політиці.
- **Перейменування файлів:** Якщо програма виконується з перейменованого бінарного файлу, відповідний профіль може не застосуватися (хоча AppArmor має механізми для боротьби з цим, наприклад, attachment rules).

## 2. Структура та синтаксис профілів (/etc/apparmor.d/)

Усі профілі AppArmor за замовчуванням зберігаються в директорії `/etc/apparmor.d/`. Кожен профіль є текстовим файлом, який описує, які ресурси (файли, мережа, можливості POSIX capabilities) дозволено використовувати певному виконуваному файлу.

### 2.1. Іменування файлів профілів

Традиційно імена файлів профілів відповідають повному шляху до виконуваного файлу, де слеші (`/`) замінюються на крапки (`.`). Наприклад, профіль для `/usr/sbin/nginx` буде називатися `usr.sbin.nginx`. Хоча це не є жорсткою вимогою (ви можете назвати файл як завгодно, головне — який шлях вказано всередині самого профілю), ця конвенція є стандартом де-факто, що полегшує пошук та управління.

### 2.2. Анатомія профілю

Типовий профіль виглядає наступним чином:

```apparmor
#include <tunables/global>

/usr/bin/example_app {
  #include <abstractions/base>

  # Дозволити читання конфігурації
  /etc/example_app.conf r,

  # Дозволити читання та запис у логи
  /var/log/example_app.log rw,

  # Дозволити доступ до мережі
  network inet tcp,

  # Заборонити доступ до важливих системних файлів
  deny /etc/shadow r,
}
```

Основні елементи:
- `#include`: Директиви включення дозволяють повторно використовувати готові блоки правил (абстракції). Наприклад, `abstractions/base` містить базові правила, необхідні для запуску більшості програм (доступ до динамічних бібліотек тощо).
- `Заголовок профілю`: `/usr/bin/example_app` визначає, до якого виконуваного файлу застосовується цей профіль.
- `Правила доступу до файлів`: Вказується шлях (або шаблон) і права (`r` - читання, `w` - запис, `a` - дописування, `x` - виконання, `k` - блокування, `m` - mmap для виконання).
- `Мережеві правила`: Визначають, які типи сокетів і протоколів дозволено використовувати.
- `Capabilities`: Дозвіл на використання специфічних привілеїв Linux (наприклад, `capability net_bind_service,`).
- `deny`: Явна заборона. Вона має вищий пріоритет над дозволами і часто використовується для захисту критичних файлів навіть якщо інші правила з масками дозволяють до них доступ.

## 3. Режими роботи: Enforce та Complain

AppArmor підтримує два основних режими роботи для кожного профілю, що робить його впровадження безпечним і керованим.

### 3.1. Режим Enforce (Примус)

У режимі *Enforce* політика безпеки активно застосовується. Будь-яка дія процесу, яка явно не дозволена у профілі, буде заблокована ядром, а у системний журнал (dmesg, syslog або audit.log) буде записано відповідне повідомлення про порушення (DENIED).

Цей режим використовується для робочих середовищ (production), де необхідно гарантувати захист системи від компрометованих або вразливих програм.

### 3.2. Режим Complain (Скарги / Навчання)

У режимі *Complain* AppArmor не блокує дії, які порушують політику, але записує інформацію про ці порушення в журнал (ALLOWED). Програма продовжує працювати так, ніби профілю не існує (з точки зору відмов доступу), але ядро фіксує всі виходи за межі дозволеного.

Цей режим є критично важливим для розробки та тестування нових профілів:
1. Адміністратор створює базовий (часто порожній) профіль і переводить його в режим Complain.
2. Програма використовується в нормальному режимі, виконуючи всі свої функції.
3. AppArmor логує всі дії програми.
4. Адміністратор використовує утиліти (наприклад, `aa-logprof`) для автоматичного аналізу логів і генерації або оновлення правил у профілі на основі реальної поведінки програми.
5. Коли профіль стає повним і точним, його переводять у режим Enforce.

## 4. Утиліти управління AppArmor

Для зручного управління профілями існує набір інструментів командного рядка, які входять до пакету `apparmor-utils`.

### 4.1. aa-status

Команда `aa-status` (або `apparmor_status`) відображає поточний стан AppArmor у системі. Вона надає зведений звіт про завантажені профілі та запущені процеси.

```bash
$ sudo aa-status
apparmor module is loaded.
42 profiles are loaded.
40 profiles are in enforce mode.
   /sbin/dhclient
   /usr/bin/man
   ...
2 profiles are in complain mode.
   /usr/bin/test_app
0 processes have profiles defined.
0 processes are in enforce mode.
0 processes are in complain mode.
0 processes are unconfined but have a profile defined.
```

Ця команда дозволяє швидко зрозуміти, чи включений AppArmor, скільки профілів активно і чи є процеси, які працюють під їхнім захистом.

### 4.2. aa-complain та aa-enforce

Ці дві утиліти використовуються для швидкого перемикання режимів конкретних профілів.

- `aa-complain <шлях до профілю або бінарника>`: Переводить профіль у режим навчання. Утиліта модифікує файл профілю (додає прапорець `flags=(complain)`) і негайно перезавантажує його в ядро.
  ```bash
  sudo aa-complain /etc/apparmor.d/usr.sbin.nginx
  # або просто
  sudo aa-complain /usr/sbin/nginx
  ```

- `aa-enforce <шлях>`: Переводить профіль у строгий режим. Видаляє прапорець скарг і перезавантажує політику.
  ```bash
  sudo aa-enforce /usr/sbin/nginx
  ```

Існує також команда `aa-disable`, яка створює символічне посилання на профіль у `/etc/apparmor.d/disable/` і вивантажує його з ядра, повністю відключаючи захист для цієї програми.

## 5. Внутрішня механіка: завантаження профілів через securityfs

Усі текстові файли в `/etc/apparmor.d/` — це лише конфігурації для простору користувача (user space). Ядро Linux не вміє читати або парсити ці текстові файли безпосередньо. Процес перекладу правил зі зрозумілого людині формату у формат ядра відбувається за допомогою інструменту `apparmor_parser`.

### 5.1. apparmor_parser

`apparmor_parser` — це ключова утиліта низького рівня. Вона виконує такі функції:
1. Читає текстові профілі, розкриває всі `#include` та змінні (tunables).
2. Перевіряє синтаксис профілю.
3. Компілює профілі у бінарний формат (який є оптимізованим для швидкої перевірки прав доступу в ядрі, часто це представлення у вигляді детермінованих скінченних автоматів — DFA).
4. Завантажує (або вивантажує/оновлює) цей бінарний блоб безпосередньо в ядро.

Приклад ручного завантаження профілю (з заміною існуючого):
```bash
sudo apparmor_parser -r /etc/apparmor.d/usr.sbin.nginx
```

### 5.2. securityfs та інтерфейс ядра

Як саме `apparmor_parser` передає скомпільований бінарний профіль до ядра? Це відбувається через спеціальну віртуальну файлову систему — **securityfs**.

Securityfs зазвичай монтується у `/sys/kernel/security/`. У цій директорії кожен модуль LSM може створити свою піддиректорію для комунікації з простором користувача. Для AppArmor це `/sys/kernel/security/apparmor/`.

Коли ви використовуєте `apparmor_parser` для завантаження профілю, утиліта:
1. Відкриває спеціальний файл `/sys/kernel/security/apparmor/.load` на запис.
2. Відправляє туди скомпільований бінарний блоб профілю.
3. Ядро (код AppArmor LSM) перехоплює цей запис, зчитує бінарні дані, валідує їхню цілісність і додає до своїх внутрішніх структур у пам'яті (policy database).

Аналогічно працюють інші операції:
- `/sys/kernel/security/apparmor/.replace` — для оновлення профілю.
- `/sys/kernel/security/apparmor/.remove` — для видалення профілю з пам'яті ядра.

Цей механізм дозволяє оновлювати політики безпеки "на льоту" (hot-plug), не зупиняючи запущені процеси. Якщо ви оновлюєте профіль для nginx, нові правила застосовуються негайно до всіх уже запущених робочих процесів nginx (однак існують нюанси з кешуванням файлових дескрипторів).

## Висновок

AppArmor є потужним, але водночас зрозумілим інструментом для підвищення безпеки систем Linux. Його підхід на основі файлових шляхів, можливість ітеративної розробки профілів через режими Complain та Enforce, а також зручний набір утиліт `aa-*` роблять його ідеальним вибором як для десктопних систем (наприклад, Ubuntu), так і для серверних інсталяцій. 

Розуміння внутрішньої роботи, зокрема взаємодії `apparmor_parser` із ядром через `securityfs`, дає системним адміністраторам змогу краще діагностувати проблеми та автоматизувати управління політиками безпеки на масштабі.
