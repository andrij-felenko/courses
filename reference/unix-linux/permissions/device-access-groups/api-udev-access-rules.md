# 📋 Як правилом видають доступ до вузла: ключі, файли, перевірка

Довідка за клавіатурою: які саме ключі правила udev проставляють права на вузлі `/dev`, чим вони відрізняються від ключів, за якими правило вибирає пристрій, у якій теці й під яким номером має лежати ваш файл, щоб виграти, і якою командою перевірити кожну ланку окремо. Головне питання, на яке ця довідка відповідає: що написати в рядку — і як довести, що він спрацював.

## Оператори: дві сім'ї, і в цьому вся граматика

Правило — один рядок із пар «ключ-оператор-значення» через кому. Оператор сам каже, до якої сім'ї належить пара: **збіг** (умова, за якою правило або вибирає пристрій, або мовчки пропускає його) чи **присвоєння** (дія над тим, що вийде).

| оператор | сім'я | значення |
|---|---|---|
| `==` | збіг | значення збігається (шаблони оболонки: `*`, `?`, `[0-9]`) |
| `!=` | збіг | не збігається |
| `=` | присвоєння | присвоїти; для списків — **скинути** список і покласти одне значення |
| `+=` | присвоєння | додати до списку |
| `-=` | присвоєння | вилучити зі списку |
| `:=` | присвоєння | присвоїти остаточно — пізніші правила змінити вже не зможуть |

Різниця між `=` і `+=` не косметична. `SYMLINK="ttyPROG"` витирає всі імена, які встигли додати попередні правила, і вузол втрачає звичні назви на кшталт `/dev/serial/by-id/…`; `SYMLINK+="ttyPROG"` дописує ще одне.

## Ключі збігу: чим правило вибирає пристрій

| ключ | де шукає | приклад |
|---|---|---|
| `ACTION` | тип події | `ACTION=="add"` |
| `SUBSYSTEM` | підсистема **самого** пристрою | `SUBSYSTEM=="tty"` |
| `KERNEL` | ім'я, яке дало ядро | `KERNEL=="ttyUSB[0-9]*"` |
| `ATTR{…}` | атрибут [sysfs](topic:unix-linux/sysfs-device-model) **самого** пристрою | `ATTR{dev}=="188:0"` |
| `SUBSYSTEMS`, `KERNELS`, `DRIVERS`, `ATTRS{…}` | те саме, але **вгору по ланцюгу предків** | `ATTRS{idVendor}=="1a86"` |
| `ENV{…}` | властивість, яку вже проставили **попередні** правила | `ENV{ID_SERIAL_SHORT}=="A5069RR4"` |
| `TAG` | мітка, вже почеплена раніше | `TAG=="uaccess"` |

Множина без `S` проти множини з `S` — головна пастка цієї таблиці. Вузол `/dev/ttyUSB0` належить підсистемі `tty` і сам не має жодного `idVendor`: ідентифікатори виробника й виробу лежать на предку — на USB-пристрої, у який утулено перехідник. Тому `SUBSYSTEM=="tty"` і `ATTRS{idVendor}=="1a86"` в одному рядку не суперечать одне одному: перший ключ дивиться на вузол, другий підіймається по ланцюгу.

Обмеження, через яке правило часто не збігається взагалі: **якщо ключів `ATTRS{…}` кілька, усі вони мусять збігтися на одному й тому самому предку.** Узяти `idVendor` з USB-пристрою, а `serial` — з концентратора над ним не можна.

Окремо про `ENV{ID_*}`: ці властивості не приходять від ядра. Їх обчислюють і кладуть у подію попередні правила (наприклад, файли з номерами `60-*`), тому в рядку з меншим номером вони порожні.

## Ключі присвоєння: чим правило видає доступ

| ключ | що робить |
|---|---|
| `OWNER="root"` | власник вузла (UID) |
| `GROUP="dialout"` | група вузла (GID) |
| `MODE="0660"` | [біти прав](topic:unix-linux/permission-bits) вісімковим числом |
| `SYMLINK+="ttyPROG"` | додає ще одне ім'я в `/dev`, що вказує на цей вузол |
| `TAG+="uaccess"` | мітка «віддати тому, хто зараз сидить за цим комп'ютером» |
| `ENV{ключ}="…"` | властивість для наступних правил |
| `RUN{program}+="…"` | програма, яку запустити після обробки події |

`OWNER`, `GROUP` і `MODE` перекривають вбудовану типову величину; що саме буде, якщо їх не писати, задає файл `50-udev-default.rules` — саме він розкладає вузли по групах: послідовні `ttyUSB*`, `ttyACM*`, `ttyS*` → `dialout` (а сама підсистема `tty`, тобто консолі й псевдотермінали, — у групу `tty`), `video4linux` → `video`, `block` → `disk`, `input` → `input`.

`TAG+="uaccess"` працює інакше за всі інші: сам по собі він нічого не змінює. Мітку пізніше читає правило `73-seat-late.rules` і запускає вбудовану дію `uaccess`, а та питає [systemd-logind](topic:unix-linux/logind-sessions-seats), чий сеанс зараз активний на цьому місці, і дописує на вузол [запис ACL](topic:unix-linux/acl-and-xattr) для конкретної людини.

Мінімальне робоче правило:

```
# /etc/udev/rules.d/99-usb-serial.rules
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", GROUP="dialout", MODE="0660", SYMLINK+="ttyPROG"
```

## Де лежать файли й у якому порядку їх читають

| тека | для кого | вага при однакових іменах |
|---|---|---|
| `/usr/lib/udev/rules.d` | пакети дистрибутива | найнижча |
| `/usr/local/lib/udev/rules.d` | зібране локально | вище |
| `/run/udev/rules.d` | тимчасове, до перезавантаження | ще вище |
| `/etc/udev/rules.d` | адміністратор | найвища |

Тут працюють два незалежні механізми, і плутати їх дорого.

**Порядок читання** — усі файли з усіх чотирьох тек зливають в один перелік і сортують **за іменем**; тека при цьому не важить нітрохи. `50-udev-default.rules` з `/usr/lib` читають раніше за ваш `99-my.rules` з `/etc` не тому, що `/usr` головніший, а тому що `50` менше за `99`.

**Перекриття за іменем** — імена файлів утворюють спільний простір. Якщо однакове ім'я є в кількох теках, беруть лише найваговіше, решту ігнорують цілком. Звідси спосіб вимкнути правило пакета: покласти в `/etc/udev/rules.d` симлінк на `/dev/null` з **тим самим** іменем.

Номер обирають не «щоб пізніше», а під вікно, у яке ключ мусить потрапити:

```
50-udev-default.rules   типові GROUP= і MODE= для кожної підсистеми
60-*.rules              проставляють ENV{ID_*}
70-uaccess.rules        чіпляють TAG+="uaccess" камерам, сканерам, зчитувачам
73-seat-late.rules      ЧИТАЄ мітку uaccess і дописує ACL
99-my.rules             ← сюди своє GROUP= / MODE= / SYMLINK+=
```

Тому: **`GROUP=`, `OWNER=`, `MODE=` — номер понад 70** (усі типові значення й усі `ENV{ID_*}` уже на місці, ваш рядок кладеться зверху); **`TAG+="uaccess"` — номер, менший за 73**, інакше мітку чіпляють після того, як її прочитали, і вона не робить нічого.

## Обмеження systemd 258

Від systemd 258 (17 вересня 2025) `systemd-udevd` **ігнорує `OWNER=` і `GROUP=`, які називають несистемного користувача чи групу**, — щоб вузли пристроїв не діставалися звичайним обліковим записам. Група, створена `groupadd` без ключа `--system`, дістає число з користувацького діапазону (від 1000) і саме такою й є.

```
$ journalctl -u systemd-udevd | grep -i 'not a system'
systemd-udevd[412]: 99-my.rules:3 Group 'labdev' is not a system group, ignoring.
```

Ключ відкидають мовчки з погляду програми: вузол просто лишається з групою `root`, а `open` повертає `EACCES`. Лагодять створенням системної групи — `groupadd --system labdev`, потім `usermod -aG labdev andrij` і `udevadm trigger`.

## Команди перевірки: кожна дивиться на свою ланку

| команда | на що відповідає |
|---|---|
| `udevadm info -a -n /dev/ttyUSB0` | які ключі взагалі можна писати: атрибути вузла й усіх предків, готовими до вставки блоками |
| `udevadm info -q property -n /dev/ttyUSB0` | які `ENV{…}` уже проставлені |
| `udevadm test /sys/class/tty/ttyUSB0` | програти подію на сухо: які правила збіглися і які значення виграли |
| `udevadm verify /etc/udev/rules.d/99-my.rules` | синтаксис, семантика й стиль файлу (systemd 254 і новіші) |
| `udevadm control --reload` | перечитати правила — **на наявні вузли не впливає** |
| `udevadm trigger --action=add --subsystem-match=tty` | перепрогравання подій, щоб нові правила лягли на вже підключене |

Блоки у виводі `udevadm info -a` — це і є ланцюг предків: перший блок описує сам вузол (`KERNEL`, `SUBSYSTEM`, `ATTR{}`), кожен наступний — предка (`KERNELS`, `SUBSYSTEMS`, `DRIVERS`, `ATTRS{}`). Правило беруть із **одного** блоку предків плюс першого.

Повний цикл від нуля:

```sh
$ udevadm info -a -n /dev/ttyUSB0 | grep -E 'idVendor|idProduct'
    ATTRS{idVendor}=="1a86"
    ATTRS{idProduct}=="7523"
$ sudoedit /etc/udev/rules.d/99-usb-serial.rules
$ udevadm verify /etc/udev/rules.d/99-usb-serial.rules
$ sudo udevadm control --reload
$ sudo udevadm trigger --action=add --subsystem-match=tty
$ ls -l /dev/ttyUSB0
crw-rw---- 1 root dialout 188, 0 Aug  8 11:42 /dev/ttyUSB0
```

## Другий бік: рядок групи й членство

Рядок [бази облікових записів](topic:unix-linux/user-database-nss) має чотири поля через двокрапку — назва, пароль, число, перелік:

```
dialout:x:20:andrij,maria
```

`x` означає, що пароль групи винесено у `/etc/gshadow`. Перелік — через кому **без пробілів**. Головне про нього: у ньому немає людей, для яких ця група основна (основну записано четвертим полем у `/etc/passwd`), тому порожній перелік не означає «нікого немає».

| команда | що робить |
|---|---|
| `usermod -aG dialout andrij` | **додає** до наявних додаткових груп |
| `usermod -G dialout andrij` | ⚠ **замінює перелік цілком** — людину виключають з усіх груп, яких немає в аргументі |
| `gpasswd -a andrij dialout` | те саме додавання, але аргумент — сама група: стерти чужі членства неможливо в принципі |
| `gpasswd -d andrij dialout` | вилучити з групи |
| `id -nG andrij` | перелік **із бази** — яким він стане після нового входу |
| `id -nG` | перелік **поточного процесу** — знімок, зроблений при вході |

Забутий `-a` — катастрофа з одного символа: `usermod -G dialout andrij` виносить людину з `sudo` й `wheel` разом з усім іншим, і повернути це вона вже не може, бо права піднімати немає. Безпечніше додавати через `gpasswd -a`, який просто не вміє нашкодити.

Два останні рядки таблиці разом дають точну перевірку «чи треба перезаходити»: якщо `id -nG andrij` показує групу, а `id -nG` без аргумента — ні, справа не в правилах і не в правах, а в тому, що перелік груп процесу створюють один раз.

## ACL на вузлі: прочитати й поправити руками

| команда | що робить |
|---|---|
| `getfacl -p /dev/ttyUSB0` | показати; `-p` не зрізає початкову похилу в рядку `# file:` |
| `setfacl -m u:andrij:rw /dev/ttyUSB0` | додати або змінити запис для користувача |
| `setfacl -m g:labdev:rw /dev/ttyUSB0` | те саме для групи |
| `setfacl -x u:andrij /dev/ttyUSB0` | вилучити запис — **без поля прав** в аргументі |
| `setfacl -b /dev/ttyUSB0` | зняти всі розширені записи, лишити базові три |
| `setfacl -n -m …` | не перераховувати `mask` |

Поле `mask` — стеля, а не окремий дозвіл: чинні права іменованого запису є перетином самого запису й маски. `setfacl` типово **перераховує** маску після кожного `-m`, кладучи туди об'єднання прав групи-власника й усіх іменованих записів, — тому зазвичай вона не заважає. Заважає, коли маску задали явно:

```sh
$ setfacl -m u:andrij:rw,m::r /dev/ttyUSB0
$ getfacl -p /dev/ttyUSB0
# file: /dev/ttyUSB0
# owner: root
# group: dialout
user::rw-
user:andrij:rw-			#effective:r--
group::rw-			#effective:r--
mask::r--
other::---
```

Коментар `#effective:` з'являється рівно тоді, коли маска щось ріже. Ще одна прикмета: `ls -l` дописує `+` після дев'яти символів режиму, якщо на файлі є розширені записи.

Контрактна деталь, важлива саме для пристроїв: **ACL, поставлений руками, не переживає перевтикання** — вузол створюється наново й приходить із тим, що написано в правилі. Постійним його робить або `TAG+="uaccess"`, або `RUN+=` з викликом `setfacl` у самому правилі.

## Типові помилки й точний симптом кожної

| помилка | симптом | чим лікується |
|---|---|---|
| правило написане, але `udevadm control --reload` не зроблено | нічого не змінилося навіть після перевтикання | `udevadm control --reload` |
| reload зроблено, а вузол уже існує | нові пристрої отримують нові права, старий вузол — ні | `udevadm trigger` або перевтикання |
| номер файлу менший за 50 | ваші `GROUP=`/`MODE=` затирає `50-udev-default.rules` пізніше | перейменувати на `99-…` |
| `TAG+="uaccess"` у файлі з номером ≥ 73 | мітка є, ACL немає; `getfacl` показує лише базові записи | перейменувати на `70-…` |
| несистемна група в `GROUP=` на systemd ≥ 258 | вузол лишається `root:root`, у журналі `is not a system group, ignoring` | `groupadd --system` |
| `ATTRS{}` з різних предків в одному рядку | правило не збігається ніколи, помилок при цьому немає | звіряти з блоками `udevadm info -a` |
| `ENV{ID_*}` у файлі з номером до 60 | значення порожнє, збіг не відбувається | номер понад 60 або збіг за `ATTRS{}` |
| `SYMLINK=` замість `SYMLINK+=` | зникають назви `/dev/serial/by-id/…` | повернути `+=` |
| іменований запис ACL є, доступу немає | у `getfacl` видно `#effective:` | `setfacl -m m::rw` |
| вузла в `/dev` немає взагалі | `ENOENT`, а не `EACCES` | це не про права: дивитися, чи не забрав пристрій інший драйвер |
