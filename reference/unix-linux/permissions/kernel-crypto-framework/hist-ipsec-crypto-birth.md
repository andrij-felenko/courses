# 📜 Від фрагментоованого шифрування 1990-х до підсистеми Crypto API

Наприкінці 1990-х років ядро Linux не мало централізованої підсистеми для криптографічних обчислень. Кожен драйвер пристрою або мережевий протокол реалізовував потрібні шифри власними силами. Драйвери мережевих карт, сервери захищених протоколів та експериментальні файлові системи включали компильовані файли C з реалізаціями DES, 3DES чи MD5 безпосередньо у власне дерево вихідного коду. Це призводило до небезпечного дублювання коду, різнорідних реалізацій однакових алгоритмів із різним рівнем захисту від атак за побічними каналами (side-channel attacks), а також унеможливлювало прозоре використання апаратних прискорювачі іншими компонентами ядра.

Конфлікт загострився довкола підтримки безпеки мережевого стеку. Проект FreeS/WAN (Free Secure Wide Area Network), заснований Джоном Ґілмором (John Gilmore) та Г'ю Деніелом (Hugh Daniel), пропонував власну реалізацію IPsec для Linux під назвою KLIPS (Kernel IPsec Support). Однак KLIPS був монолітною обгорткою, яка створювала віртуальні мережеві інтерфейси `ipsecX`, повністю дублювала код симетричного шифрування (DES, 3DES, Blowfish) та обходила стандартні таблиці маршрутизації мережевого стеку ядра. Через це розробники ядра (і перш за все Олексій Кузнецов та Лінус Торвальдс) відмовилися вмикати KLIPS до основного дерева ядра.

Головним імпульсом для створення єдиного Kernel Crypto API стала масштабна реорганізація мережевого стеку під час розробки ядра Linux 2.5 у 2002 році. Для заміни застарілого KLIPS було створено підсистему `xfrm` (IPsec Transform Framework), яку розробляли Олексій Кузнецов та Девід Міллер. Одночасно розробники Джеймс Морріс (James Morris), Расті Расселл (Rusty Russell) та Герберт Сю (Herbert Xu) запропонували відмовитися від розрізнених криптографічних функцій і побудувати єдину підсистему реєстрації алгоритмів — **Kernel Crypto API**.

Архітектура 2002 року спиралася на два ключові поняття: уніфіковану структуру опису алгоритму `struct crypto_alg` та об'єкт трансформації `struct crypto_tfm`. Будь-який модуль міг зареєструвати алгоритм у глобальному списку ядра, вказавши текстове ім'я (наприклад, `"aes"` або `"sha1"`) і числове значення пріоритету реалізації. Споживачі підсистеми, такі як IPsec `xfrm`, запитували трансформацію за текстовим ім'ям, а ядро повертало готовий контекст. Це дозволило видалити сотні рядків дубльованого коду з драйверів та запровадити централізоване самотестування алгоритмів при завантаженні за допомогою векторів тестування FIPS / KAT (Known Answer Tests).

З виходом ядра 2.6 у грудні 2003 року Crypto API став стандартною підсистемою ядра. Його споживачами стали підсистема блокового шифрування дискових розділів `dm-crypt` (яка замінила застарілий `cryptoloop`), механізм шифрування swap-сторінок, файлові системи `ext4` та `f2fs` (`fscrypt`), а також захищений протокол бездротових мереж `mac80211`.

У 2006 році (версія ядра 2.6.19) підсистема зазнала другої великої трансформації: впровадження асинхронного криптографічного API. Початковий інтерфейс був суто синхронним — потік ядра повністю блокувався на час виконання обчислень процесором. З появою корпоративних PCIe-плат апаратного шифрування (ранніх моделей VIA PadLock, Cavium NITROX та Intel QAT) синхронний виклик став вузьким місцем: центральний процесор марнував мільйони тактів в очікуванні відповіді від пристрою. Перехід на асинхронні запити `ahash` та `skcipher` із використанням переривань, векторів DMA та списків розсіювання-збирання (Scatterlist) дозволив передавати обчислення на контролери зовнішніх плат без блокування ядер процесора.

Останнім етапом еволюції стало відкриття ядерного криптографічного фреймворку для простору користувача. У ядрі 2.6.38 (2011 рік) за ініціативою Герберта Сю було додано сімейство адресації `AF_ALG`. Це дозволило системним утилітам (`util-linux`, `cryptsetup`) та криптографічним бібліотекам користувацького простору використовувати перевірені та апаратно прискорені реалізації шифрів із ядра через стандартні сокетні виклики POSIX, виключаючи потребу тримати власні дубльовані реалізації в бібліотеках користувача.
