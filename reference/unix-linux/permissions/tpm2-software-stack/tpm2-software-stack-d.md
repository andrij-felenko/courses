</preknowlist>

Криптографічні ключі, що зберігаються у звичайній оперативній пам'яті операційної системи, залишаються відкритими для широкого спектра програмних та апаратних атак: від отримання зліпків пам'яті через механізми дампу ядра до атак Cold Boot та прямого читання через шину PCI Express за допомогою DMA. Для розв'язання цієї фундаментальної проблеми в архітектуру сучасних комп'ютерних систем впроваджують апаратний якір довіри (Root of Trust) — мікроконтролер Trusted Platform Module (TPM 2.0). Цей захищений модуль виконує криптографічні обчислення у повністю ізольованому середовищі, гарантуючи, що приватні ключі шифрування ніколи не залишають його внутрішню кремнієву структуру у відкритому вигляді.

## 1. Механізм апаратного якоря довіри TPM 2.0

Trusted Platform Module являє собою автономну обчислювальну систему на чипі (SoC), яка функціонує незалежно від стану головного процесора та операційної системи. Модуль містить власне захищене процесорне ядро, енергозалежну та енергонезалежну пам'ять, апаратний генератор справжніх випадкових чисел (TRNG) та спеціалізований криптографічний акселератор.

```
+-------------------------------------------------------------------+
|                        TPM 2.0 Hardware Microcontroller           |
|                                                                   |
|  +--------------------+  +--------------------+  +-------------+  |
|  | Cryptographic Engine|  | Platform Regs (PCR)|  | TRNG Hardware|  |
|  | RSA, ECC, AES, SHA |  | SHA-256 / SHA-384  |  | Generator   |  |
|  +--------------------+  +--------------------+  +-------------+  |
|                                                                   |
|  +--------------------+  +-------------------------------------+  |
|  | Primary Seeds      |  | Non-Volatile RAM (NVRAM)            |  |
|  | Endorsement, Owner |  | Persistent Keys, EK Certificates   |  |
|  +--------------------+  +-------------------------------------+  |
+-------------------------------------------------------------------+
```

### Фізичні та логічні форм-фактори TPM 2.0

Залежно від вимог до захищеності обладнання та фізичного доступу пристрій TPM 2.0 інтегрується у системну платформу в одному з трьох форм-факторів:

1. **Дискретний чип (dTPM):** Окрема фізична мікросхема, що запаюється на материнську плату та підключається до південного мосту або процесора через шину SPI (Serial Peripheral Interface) чи LPC (Low Pin Count). dTPM пропонує найвищий рівень захисту проти атак з активним зондуванням кристала (microprobing) та аналізу побічних каналів (side-channel analysis). Кадри передачі через регістри FIFO обробляє драйвер родини TIS: `tpm_tis` — для LPC та відображених у пам'ять регістрів, `tpm_tis_spi` — для шини SPI.
2. **Мікропрограмний модуль (fTPM):** Реалізація функцій TPM у формі захищеної прошивки, яка виконується в ізольованій зоні основного процесора (Trusted Execution Environment) — наприклад, технологія Intel PTT (Platform Trust Technology) або AMD fTPM на базі підсистеми ARM TrustZone / AMD PSP. fTPM не потребує окремої мікросхеми і взаємодіє з ядром через драйвер `tpm_crb` (Command Response Buffer), що використовує спільну область пам'яті для обміну командами.
3. **Віртуальний TPM (vTPM):** Програмна емуляція, яку гіпервізор (KVM/QEMU) надає гостьовим віртуальним машинам. Кожна віртуальна машина отримує свій ізольований екземпляр NVRAM та регістрів PCR, що дозволяє підтримувати функціонал виміряного завантаження у хмарі.

Докладний аналіз еволюційного шляху від специфікації 1.2 до сучасної гнучкої архітектури наведено в матеріалі [Історія еволюції стандарту від TPM 1.2 до 2.0](topic:unix-linux/tpm2-software-stack/hist-tpm-12-to-20.md).

### Функціональні підсистеми всередині чипа

- **Генератор випадкових чисел (TRNG):** Отримує ентропію з фізичних явищ (наприклад, теплового шуму P-N переходів напівпровідника). Його вихідний потік використовується для генерації ключів всередині чипа та підживлення системної ентропії ядра Linux (`/dev/random`).
- **Криптографічний двигун (Crypto Engine):** Реалізує асиметричні алгоритми (RSA 2048/4096 біт, еліптичні криві ECC NIST P-256, P-384, SM2), симетричні блоки (AES-128, AES-256 у режимах CBC, CFB) та геш-функції (SHA-256, SHA-384).
- **Енергонезалежна пам'ять (NVRAM):** Використовується для довготривалого збереження заводських сертифікатів виробника (EK Certificate), лічильників захисту від повторного відтворення (Anti-Replay Counters) та фіксованих індексів конфігурації.

## 2. Ядро Linux: розмежування пристроїв /dev/tpm0 та /dev/tpmrm0

Для взаємодії з апаратним чипом ядро Linux надає драйвери транспортного рівня (наприклад, `tpm_tis` і `tpm_tis_spi` для інтерфейсу TIS на шинах LPC та SPI, `tpm_crb` — для інтерфейсу Command Response Buffer). Початкові реалізації відкривали для прикладних програм прямий символьний пристрій `/dev/tpm0`.

### Проблема вичерпання внутрішньої пам'яті

TPM 2.0 має суворі апаратні обмеження щодо обсягу внутрішньої оперативної пам'яті SRAM. Як правило, чип може одночасно утримувати у завантаженому стані не більше ніж 3–4 об'єкти (активні ключі або сесії авторизації). 

Якщо кілька процесів операційної системи спробують одночасно виконати криптографічні операції через прямий пристрій `/dev/tpm0`, внутрішні слоти пам'яті чипа миттєво вичерпаються. TPM поверне критичну помилку `TPM2_RC_OBJECT_MEMORY`, і застосунки повинні будуть самостійно виконувати збереження та відновлення контекстів (Context Swapping).

```
Юзерспейс Процеси            Менеджер ресурсів Ядра           Апаратний TPM
+-----------------+          +----------------------+         +---------------+
| Process A (LUKS)| ------>  |                      |         | TPM 2.0 SRAM  |
+-----------------+          |  /dev/tpmrm0         |         | Slot 1: Key A |
                             |  In-Kernel Resource  | ------> | Slot 2: Key B |
+-----------------+          |  Manager             |         | (Swapping via |
| Process B (SSH) | ------>  |  - Virtual Handles   |         |  Context Encryption)
+-----------------+          |  - Auto Swap to RAM  |         +---------------+
                             +----------------------+
```

### Внутрішньоядерний менеджер ресурсів (`/dev/tpmrm0`)

Для розв'язання проблеми паралельного доступу починаючи з версії ядра Linux 4.12 було реалізовано менеджер ресурсів (TPM Resource Manager), який надає системі символьний пристрій `/dev/tpmrm0`.

Внутрішньоядерний менеджер ресурсів виконує функції планувальника та менеджера віртуальної пам'яті для TPM:
1. **Віртуалізація дескрипторів (Handles):** Кожен виклик `open("/dev/tpmrm0")` створює ізольований простір віртуальних дескрипторів для даного файлового дескриптора.
2. **Прозорий Context Swapping:** Перед передачею команди до чипа менеджер ресурсів перевіряє наявність потрібного об'єкта в SRAM чипа. Якщо об'єкт знаходиться у системній оперативній пам'яті, менеджер виконує команду `TPM2_ContextLoad`. Після завершення операції об'єкт автоматично вивантажується через `TPM2_ContextSave`: блоб контексту шифрує сам чип на власному ключі контекстів, тож у системній пам'яті ядро тримає лише непрозорі дані.
3. **Ізоляція сесій:** Запобігає випадковому або навмисному скиданню авторизаційних сесій одного процесу іншим.

Завдяки цьому сучасні стандарти розробки ПЗ у Linux вимагають **завжди використовувати пристрій `/dev/tpmrm0`**, залишаючи `/dev/tpm0` виключно низкорівневим інструментам діагностики чи оновлення прошивки.

### Інтерфейси псевдофайлових систем /sys та securityfs

Ядро Linux експортує діагностичні параметри TPM через псевдофайлову систему `/sys/class/tpm/tpm0/`:
- `/sys/class/tpm/tpm0/device/description`: Текстова назва та виробник чипа (наприклад, `"Infineon SLB9670"`).
- `/sys/class/tpm/tpm0/tpm_version_major`: Версія специфікації (`"2"`).
- `/sys/kernel/security/tpm0/binary_bios_measurements`: Повний бінарний журнал вимірювань завантаження (Event Log), який зчитується серверами атестації.

## 3. Програмний стек TSS2 (TPM2 Software Stack)

Формування бінарних кадрів команд TPM 2.0 є складною задачею: параметри треба впорядкувати за специфікацією, а на кожну авторизаційну сесію — обчислити HMAC. Для спрощення розробки TCG затвердила специфікацію програмного стеку TSS2, реалізовану в Linux бібліотекою `tpm2-tss`.

![Архітектура TPM2 Software Stack (TSS2) у Linux](img/tpm2-tss-architecture.svg)
*Архітектура програмного стеку TSS2 у Linux: маршрутизація викликів через TCTI до менеджера ресурсів ядра /dev/tpmrm0 та апаратного чипа TPM 2.0.*

### Чотири рівні абстракції TSS2

Стек TSS2 розбито на чотири функціональні рівні:

1. **TCTI (TPM Command Transmission Interface):** Шар транспортування. Абстрагує спосіб передачі байтових масивів до `/dev/tpmrm0`, сокета програмного емулятора (mssim) або користувацького демона `tpm2-abrmd`.
2. **SYS / SAPI (System API):** Пряма відповідність бінарним командам специфікації TPM 2.0. Генерує кадри команд, але вимагає від розробника ручного розрахунку сесій та HMAC.
3. **ESAPI (Enhanced System API):** Автоматизує керування сесіями авторизації, обчислення HMAC та шифрування параметрів команд. ESAPI виступає базовим фундаментом для інструментарію `tpm2-tools`.
4. **FAPI (Feature API):** Високорівневий шар, розроблений для спрощення стандартних сценаріїв. FAPI оперує профілями конфігурації у форматі JSON та текстовими шляхами до ключів (наприклад, `"/HS/SRK/my_key"`), зводячи роботу до 1–2 функціональних викликів.

Опис структур системних заголовочних файлів C API та командного інтерфейсу наведено у вставці [Специфікація API стеку TSS2 (ESAPI/FAPI) та консольний інструментарій](topic:unix-linux/tpm2-software-stack/api-tss2-esapi.md).

## 4. Ієрархії об'єктів та генерація ключів

Усі об'єкти TPM 2.0 (ключі, дані NVRAM, паролі) організовані у чотири криптографічні дерева — ієрархії. На вершині кожної ієрархії знаходиться **Primary Seed** — велике випадкове число, яке генерується всередині TPM і ніколи не виводиться за його межі.

```
                     +----------------------------------+
                     |  Primary Seed (stored in NVRAM)  |
                     +----------------------------------+
                                      |
                                      v
                     +----------------------------------+
                     |  Storage Root Key (SRK / Primary)|
                     +----------------------------------+
                                      |
                 +--------------------+--------------------+
                 |                                         |
                 v                                         v
   +---------------------------+             +---------------------------+
   | Child Symmetric Key (AES) |             | Child Asymmetric Key (RSA)|
   +---------------------------+             +---------------------------+
```

### Чотири ієрархії TPM 2.0

- **Owner/Storage Hierarchy (`TPM2_RH_OWNER`):** Головна ієрархія для операційної системи. З її зерна за допомогою функції KDFa (Key Derivation Function in Counter Mode) генерується Storage Root Key (SRK), під яким створюються дочірні ключі шифрування дисків та користувацьких даних.
- **Endorsement Hierarchy (`TPM2_RH_ENDORSEMENT`):** Ієрархія апаратної ідентифікації. Містить Endorsement Key (EK) — унікальний ключ чипа, який підтверджує справжність обладнання.
- **Platform Hierarchy (`TPM2_RH_PLATFORM`):** Призначена для використання мікропрограмою платформи (UEFI BIOS). Операційна система втрачає доступ до управління цією ієрархією після завантаження.
- **Null Hierarchy (`TPM2_RH_NULL`):** Ефемерна ієрархія. Її зерно регенерується при кожному перезавантаженні TPM, а об'єкти не зберігаються між сесіями живлення.

### Ключі ідентифікації та атестації: EK та AK

1. **Endorsement Key (EK):** Приватна частина EK детерміновано виводиться із зерна ієрархії Endorsement, закладеного в чип на заводі, і **ніколи** не використовується для операцій підпису — EK є обмеженим ключем розшифрування. Виробник надає сертифікат (EK Certificate), підписаний своїм Root CA, який зберігається в NVRAM і підтверджує, що публічний EK належить справжньому чипу TPM.
2. **Attestation Key (AK / AIK):** Ефемерний ключ підпису, згенерований в ієрархії Endorsement. AK має атрибут `restricted signing`, що дозволяє йому підписувати виключно внутрішньо створені TPM структури даних (цитати PCR). AK доводить свою приналежність справжньому чипу через процедуру `MakeCredential` / `ActivateCredential`.

Під час процедури `MakeCredential` сервер атестації створює симетричний секретний ключ, зашифровує його публічним ключем EK та прив'язує до публічного ключа AK. Отримати цей секрет клієнт може лише за допомогою команди `ActivateCredential`, яка виконується всередині TPM за наявності приватної частини EK.

## 5. Регістри конфігурації платформи (PCR) та Sealing

Platform Configuration Registers (PCR) — це криптографічні регістри TPM, призначені для накопичення підписів цілісності завантаження системи. TPM 2.0 підтримує кілька паралельних банків PCR (наприклад, банк SHA-256 та банк SHA-384).

### Властивості операції Extend

Запис значення в регістр PCR можливий виключно через операцію **Extend**:

```
PCR_New = Hash( PCR_Current || Measured_Data_Digest )
```

Ця криптографічна властивість дає такі гарантії:
- Фінальне значення PCR залежить від **усіх** вимірювань, внесених з моменту увімкнення системи.
- Порядок вимірювань є критичним: зміна послідовності завантаження компонентів повністю змінює підсумковий геш.
- Регістри вимірювання завантаження (`PCR 0`–`PCR 15`) не мають операції скидання: їхні значення обнуляються лише разом із перезапуском платформи, а підібрати вхідні дані під бажаний підсумковий геш не дає стійкість геш-функції.

### Розподіл PCR за специфікацією TCG Client Specification

- `PCR 0`: BIOS/UEFI прошивка, код CRTM (Core Root of Trust for Measurement).
- `PCR 1`: Налаштування та конфігурація материнської плати/UEFI.
- `PCR 2`: Код додаткових контролерів (Option ROMs).
- `PCR 4`: Код завантажувача (GRUB2, `systemd-boot`) і рішення про те, що запускається далі.
- `PCR 5`: Конфігурація завантажувача та таблиця розділів GPT/MBR.
- `PCR 7`: Стан Secure Boot, вміст баз даних ключів `PK`, `KEK`, `db`, `dbx`.
- `PCR 8-15`: Власні вимірювання завантажувача та операційної системи (ядро Linux, командний рядок ядра, initramfs, підсистема IMA).

### Механізм запечатування даних (Sealing)

Sealing — це процес шифрування об'єкта (наприклад, ключа розблокування диска LUKS) за допомогою TPM із вказівкою авторизаційної політики (Policy Digest).

```
                                  TPM Sealing & Unsealing
                                  
  +------------------+     tpm2_create (-L Policy)      +--------------------+
  | Secret Disk Key  | -------------------------------> | Sealed Blob        |
  +------------------+                                  | (enc by SRK)       |
                                                        +--------------------+
                                                                  |
                                                                  | tpm2_unseal
                                                                  v
  Current PCR 0,7    =================================> Checks Policy Digest
  State Matches?     --- YES ---> Unseals Payload        --- NO ---> Access Denied
```

Під час розпечатування (`Unseal`) TPM обчислює поточний геш зазначених регістрів PCR і порівнює його з авторизаційним гешем `PolicyDigest`, зафіксованим під час створення об'єкта. Якщо конфігурація завантаження була змінена (наприклад, відключено Secure Boot або підмінено завантажувач), значення `PCR 7` зміниться, TPM відмовить у виконанні `Unseal`, і зашифрований диск залишиться недоступним.

Програмну реалізацію C та C++ для проведення Sealing та Unsealing через ESAPI наведено у вставці [Практична реалізація Sealing та Unsealing через ESAPI на C/C++](topic:unix-linux/tpm2-software-stack/proj-tpm2-esys-unseal.md).

## 6. Віддалена атестація цілісності (Remote Attestation)

Віддалена атестація дозволяє централізованому серверу перевірки (Verifier) переконатися у тому, що віддалений вузол завантажився у безпечному стані та працює під управлінням немодифікованого ядра Linux.

```
  Client (Attested Node)                                Server (Verifier)
  +--------------------+                               +------------------+
  |                    | <------ 1. Send Nonce ------- |                  |
  |  Generate Quote    |                               |                  |
  |  via AK Key        | ------ 2. Send Quote, -------> | Verify AK Cert   |
  |                    |       Signature & EventLog    | Replay EventLog  |
  +--------------------+                               +------------------+
```

### Етапи протоколу Quote

1. **Генерація випадкового завдання (Nonce):** Сервер генерує випадкове криптографічне число (Nonce) для захисту від атак повторного відтворення (Replay Attacks) і відправляє його клієнту.
2. **Формування цитати (Quote):** Клієнт викликає команду `TPM2_Quote`, передаючи маску регістрів (наприклад, `PCR 0, 2, 4, 7`) та отриманий `Nonce`. TPM створює структуру `TPMS_ATTEST`, що містить геш вибраних регістрів PCR та отриманий Nonce, і підписує її приватною частиною ключа атестації (AK).
3. **Передача журналу вимірювань (Event Log):** Клієнт надсилає серверу підписану цитату, підпис та системний журнал вимірювань ядра Linux (доступний через `/sys/kernel/security/tpm0/binary_bios_measurements`).
4. **Верифікація на сервері:**
   - Сервер перевіряє підпис цитати за допомогою публічного ключа AK.
   - Сервер виконує емуляцію операцій Extend над записами `Event Log` і порівнює обчислені значення регістрів із гешем PCR, зафіксованим усередині підписаної цитати.
   - Сервер порівнює кожен виміряний геш (версію BIOS, ядро, конфігурацію) із базою еталонних значень (Reference Integrity Manifest — RIM).

## 7. Системна інтеграція у Linux

Сучасні дистрибутиви Linux надають високорівневу інтеграцію TPM 2.0 у ключові підсистеми операційної системи.

### Автоматичне розблокування LUKS2 через `systemd-cryptenroll`

Утиліта `systemd-cryptenroll` дозволяє прив'язати ключ шифрування диска LUKS2 до регістрів TPM 2.0 без написання низькорівневих скриптів.

```bash
# Прив'язка ключа LUKS2 до стану Secure Boot (PCR 7) та конфігурації завантажувача (PCR 4)
sudo systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=4+7 /dev/nvme0n1p3
```

Файл конфігурації `/etc/crypttab` при цьому розширюється опцією:
```text
root_luks /dev/nvme0n1p3 none tpm2-device=auto,tpm2-pcrs=4+7
```
Під час завантаження `systemd-cryptsetup` самостійно ініціалізує сесію політики через `/dev/tpmrm0`, перевіряє PCR 4+7 та вилучає секрет для монтування кореневої файлової системи.

### SSH-ключі апаратного базування (`tpm2-pkcs11`)

Модуль `tpm2-pkcs11` реалізує стандартний інтерфейс PKCS#11 поверх стеку TSS2. Це дозволяє генерувати SSH-ключі усередині TPM:

```bash
# Ініціалізація PKCS#11 токена в TPM 2.0
tpm2_ptool init
tpm2_ptool addtoken --pid 1 --label "ssh_token"

# Створення RSA ключа всередині токена TPM
tpm2_ptool addkey --label "ssh_token" --key-label "my_ssh_key"

# Авторизація в SSH з використанням апаратного ключа TPM
ssh -I /usr/lib/x86_64-linux-gnu/pkcs11/libtpm2_pkcs11.so user@remote-host
```
Приватний SSH-ключ фізично не існує у файловій системі ноутбука, унеможливлюючи його викрадення при компрометації диска.

### Криптографічні провайдери OpenSSL 3.0 (`tpm2-provider`)

Провайдер `tpm2-provider` для OpenSSL 3.0 дозволяє веб-серверам (Nginx, Apache) виконувати обробку TLS-з'єднань із приватними ключами RSA/ECC, закріпленими всередині TPM 2.0, захищаючи TLS-сертифікати серверів від крадіжки.

## 8. Атаки та апаратні обмеження

Незважаючи на апаратну ізоляцію, використання TPM 2.0 вимагає врахування таких векторів атак:

1. **Пасивне перехоплення шини (Bus Sniffing):** Дискретні чипи dTPM передають дані до процесора через незашифровані доріжки шини SPI на материнській платі. Зловмисник із логічним аналізатором може підключитися до контактів SPI і перехопити секретний ключ LUKS під час виконання `Unseal`.
   - *Захист:* Використання сесій із шифруванням параметрів (Parameter Encryption) у TSS2, що зашифровує вихідний буфер `Unseal` на сесійному ключі до його передачі по SPI.
2. **Атаки на прошивку (Firmware Vulnerabilities):** Вразливості у мікрокоді чипа (наприклад, уразливість ROCA CVE-2017-15361 в алгоритмах генерації ключів RSA чипів Infineon).
   - *Захист:* Своєчасне оновлення мікрокоду TPM через капсульні оновлення UEFI (`fwupd`).
3. **Словникові атаки та блокування (Dictionary Attack Protection):** При багаторазовому введенні неправильного пароля авторизації (Auth Value) TPM переходить у стан Lockout і блокує виконання команд на визначений час відновлення (Recovery Time).

Використання TPM 2.0 та стеку TSS2 створює надійний криптографічний якір довіри, переносячи зберігання ключів та оцінку цілісності завантаження з незахищеної оперативної пам'яті у спеціалізований апаратний мікроконтролер.
