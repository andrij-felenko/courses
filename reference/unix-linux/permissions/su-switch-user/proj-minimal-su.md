# ⚙️ Робоча su на C: сто рядків, де немає жодного зайвого

Програма, що робить те саме, що `su - postgres`, вміщується в один файл — і прочитати її варто цілком, бо тільки в коді видно те, чого не видно в описі: «перемкнутися на іншого користувача» складається з дюжини окремих прохань до системи, і майже кожне вміє мовчки не спрацювати.

## Задача

Написати `minisu [-] <користувач>`: спитати пароль **цілі** й, якщо він правильний, запустити оболонку цілі з її ідентичністю. Файл ставиться з бітом setuid і власником root — інакше чужі числа поставити ніхто не дасть.

Мову тут обирати нема з чого. Ідентичність процесу міняється системними викликами, а пароль перевіряє бібліотека PAM, чий інтерфейс написаний на C і виконується просто в процесі, що її покликав. Та сама програма будь-якою іншою мовою — це та сама дюжина викликів під обгорткою, яка лише ховає місця, де все ламається.

## Ідея

Робота ділиться надвоє, і межа проходить рівно по `fork()`.

**До** розгалуження робиться все, що стосується **дозволу** й потребує прав root: знайти ціль у [базі облікових записів](book:unix-linux/user-database-nss), прогнати [стек PAM](book:unix-linux/pam-stack), відкрити сеанс. **Після** розгалуження, у дитині, робиться все, що стосується **ідентичності**: узяти чужі числа, скласти оточення, [замінити образ](book:unix-linux/exec-semantics) на оболонку.

Батько при цьому нікуди не дівається й більше нічого не робить, крім чекання. Причина одна й неусувна: сеанс PAM, відкритий з правами root, комусь треба закрити — а дитина цих прав уже не має. Тож привілейована рамка тримається зовні, а всередині неї живе процес без привілею.

Усередині дитини порядок так само не вибирають. `setuid` — це двері, що зачиняються за собою: після нього процес уже не root, і будь-яке наступне прохання про чужі групи чи чужий `gid` дістане відмову. Тому спершу додаткові групи, потім `gid`, і лише останнім `uid`.

## Код

```c
/* minisu.c — навчальна su: тільки те, без чого вона не працює.
 *   cc -O2 -Wall -Wextra -o minisu minisu.c -lpam -lpam_misc
 *   sudo chown root:root minisu && sudo chmod 4755 minisu
 * Потрібен власний стек /etc/pam.d/minisu (для проби — копія файлу su).
 * misc_conv і -lpam_misc — розширення Linux-PAM, не переносне.
 */
#define _GNU_SOURCE
#include <errno.h>
#include <grp.h>
#include <pwd.h>
#include <security/pam_appl.h>
#include <security/pam_misc.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static pam_handle_t *pamh;
static volatile pid_t child = -1;

/* stderr не буферизований, тож _exit безпечний — і саме він потрібен у дитині:
   exit() злив би успадковані від батька буфери stdio вдруге */
static void die(const char *msg)
{
    fprintf(stderr, "minisu: %s: %s\n", msg, strerror(errno));
    _exit(1);
}

static void pam_die(int rc, const char *msg)
{
    fprintf(stderr, "minisu: %s: %s\n", msg, pam_strerror(pamh, rc));
    pam_end(pamh, rc);                  /* модулі мусять прибрати за собою */
    exit(1);
}

/* kill() — з дозволених в обробнику; більше тут нічого й не робиться */
static void forward(int sig)
{
    if (child > 0)
        kill(child, sig);
}

int main(int argc, char **argv)
{
    int login = 0, i = 1;
    if (i < argc && strcmp(argv[i], "-") == 0) { login = 1; i++; }
    if (i != argc - 1) {
        fprintf(stderr, "вжиток: minisu [-] <користувач>\n");
        return 1;
    }

    /* 1. Ціль у базі. Поля копіюємо ОДРАЗУ: getpwnam повертає вказівник на
          статичну область, і будь-який виклик NSS далі — у тому числі
          всередині модулів PAM — перепише її під нами. */
    struct passwd *pw = getpwnam(argv[i]);
    if (!pw) {
        fprintf(stderr, "minisu: немає такого користувача: %s\n", argv[i]);
        return 1;
    }
    uid_t uid = pw->pw_uid;
    gid_t gid = pw->pw_gid;
    char *name  = strdup(pw->pw_name);
    char *home  = strdup(pw->pw_dir);
    char *shell = strdup(pw->pw_shell[0] ? pw->pw_shell : "/bin/sh");
    if (!name || !home || !shell) die("пам'ять");

    /* 2. Стек PAM. Перший аргумент — ім'я СЛУЖБИ, тобто файлу в /etc/pam.d */
    struct pam_conv conv = { misc_conv, NULL };
    int rc = pam_start("minisu", name, &conv, &pamh);
    if (rc != PAM_SUCCESS) { fprintf(stderr, "minisu: pam_start\n"); return 1; }

    rc = pam_authenticate(pamh, 0);          /* уся розмова з паролем — тут */
    if (rc != PAM_SUCCESS) pam_die(rc, "автентифікація");

    rc = pam_acct_mgmt(pamh, 0);             /* запис не заблокований і не прострочений? */
    if (rc == PAM_NEW_AUTHTOK_REQD)
        rc = pam_chauthtok(pamh, PAM_CHANGE_EXPIRED_AUTHTOK);
    if (rc != PAM_SUCCESS) pam_die(rc, "перевірка запису");

    rc = pam_setcred(pamh, PAM_ESTABLISH_CRED);   /* квитки, ключі, членства від модулів */
    if (rc != PAM_SUCCESS) pam_die(rc, "видача облікових даних");

    rc = pam_open_session(pamh, 0);
    if (rc != PAM_SUCCESS) {
        pam_setcred(pamh, PAM_DELETE_CRED);
        pam_die(rc, "відкриття сеансу");
    }
    char **pamenv = pam_getenvlist(pamh);    /* що модулі дописали в оточення */

    /* 3. Сигнали блокуємо ДО fork: інакше SIGINT у щілину між fork і
          встановленням обробника вб'є батька, і сеанс лишиться відкритим */
    sigset_t block, old;
    sigemptyset(&block);
    sigaddset(&block, SIGINT);
    sigaddset(&block, SIGQUIT);
    sigaddset(&block, SIGTERM);
    sigprocmask(SIG_BLOCK, &block, &old);

    child = fork();
    if (child < 0) die("fork");

    if (child == 0) {
        /* ---- дитина: до pamh більше не торкається ----
           диспозиції обробників exec скине сам, а от МАСКА сигналів його
           переживає — тому відновлюємо явно */
        sigprocmask(SIG_SETMASK, &old, NULL);

        if (initgroups(name, gid) != 0) die("initgroups");   /* порядок */
        if (setgid(gid) != 0)           die("setgid");       /* незворотний: */
        if (setuid(uid) != 0)           die("setuid");       /* групи → gid → uid */
        if (uid != 0 && setuid(0) != -1) {                   /* доказ, а не віра */
            fprintf(stderr, "minisu: права не знялися\n");
            _exit(1);
        }

        if (login) {                     /* вхідний режим: оточення з нуля */
            char *term = getenv("TERM");
            char *keep = term ? strdup(term) : NULL;
            clearenv();
            if (keep) setenv("TERM", keep, 1);
            setenv("PATH", uid ? "/usr/local/bin:/usr/bin:/bin"
                               : "/usr/local/sbin:/usr/local/bin:/usr/sbin:"
                                 "/usr/bin:/sbin:/bin", 1);
            setenv("HOME", home, 1);
            setenv("SHELL", shell, 1);
            setenv("USER", name, 1);
            setenv("LOGNAME", name, 1);
            if (chdir(home) != 0) die("домівка недоступна");
        } else {                         /* невхідний: чуже оточення лишається */
            setenv("HOME", home, 1);
            setenv("SHELL", shell, 1);
            if (uid != 0) {              /* до root USER і LOGNAME не переносять */
                setenv("USER", name, 1);
                setenv("LOGNAME", name, 1);
            }
        }
        for (char **e = pamenv; e && *e; e++)
            putenv(*e);

        /* дефіс попереду argv[0] — єдиний спосіб сказати оболонці «ти вхідна» */
        char *base = strrchr(shell, '/');
        base = base ? base + 1 : shell;
        char arg0[128];
        snprintf(arg0, sizeof arg0, "%s%s", login ? "-" : "", base);
        char *args[] = { arg0, NULL };
        execv(shell, args);
        die("не запустити оболонку");
    }

    /* ---- батько: лишається root рівно заради прибирання ---- */
    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = forward;             /* без SA_RESTART — waitpid дасть EINTR */
    sigaction(SIGINT, &sa, NULL);
    sigaction(SIGQUIT, &sa, NULL);
    sigaction(SIGTERM, &sa, NULL);
    sigprocmask(SIG_SETMASK, &old, NULL);

    int status;
    while (waitpid(child, &status, 0) < 0)
        if (errno != EINTR) die("waitpid");

    pam_close_session(pamh, 0);
    pam_setcred(pamh, PAM_DELETE_CRED);
    pam_end(pamh, PAM_SUCCESS);

    return WIFEXITED(status) ? WEXITSTATUS(status) : 128 + WTERMSIG(status);
}
```

## Чотири прохання до PAM, а не одне

Перед ними варто затриматися на рядку, який виглядає зайвим: копіюванні полів `struct passwd`. `getpwnam` повертає вказівник на статичну область усередині libc, і наступний запит до бази цю область перепише — а модулі PAM ходять у неї постійно. Хто не скопіював, той після `pam_authenticate` має під тим самим вказівником уже чужі домівку й оболонку, і жодного попередження про це не буде.

Сама ж перевірка складається з чотирьох викликів, і рівно один із них про пароль. `pam_acct_mgmt` питає про сам обліковий запис: чи не заблокований, чи не вийшов строк пароля, чи взагалі дозволено заходити цій людині зараз; окремою відповіддю `PAM_NEW_AUTHTOK_REQD` він каже «пароль прострочений» — і чесна реакція тут не відмова, а можливість його змінити. Два останні виклики не перевіряють нічого: `pam_setcred` просить модулі **видати** те, чим ціль користуватиметься далі — квиток Kerberos, ключ у [кільці ядра](book:unix-linux/kernel-keyrings), додаткові членства, — а `pam_open_session` просить їх щось **зробити**. Обидва — дії, і саме тому за ними потрібне прибирання.

## Оточення складають, а не успадковують

Числа в обох режимах виходять однакові; різниця вся в тому, скільки вашого переживе перехід. Без тире міняються рівно чотири змінні: `HOME` і `SHELL` завжди, `USER` і `LOGNAME` — лише коли ціль не root. Виняток для root не випадковий: у бік підвищення ім'я лишають вашим навмисно, щоб запрошення й журнали показували, хто за цим сидить.

З тире оточення витирається цілком — звідси й окремий клопіт із `TERM` у коді: не зберегти його означає віддати оболонці цілі термінал, про який вона нічого не знає, після чого не запуститься жоден повноекранний редактор. Далі змінні ставлять з нуля, і `PATH` серед них найважливіший, бо саме він визначає, чиї програми виконуватимуться від нового імені.

Останнім лягає те, що віддав `pam_getenvlist`: готовий масив рядків, у який `pam_env` склав загальносистемні змінні, `pam_krb5` — шлях до кешу квитків, `pam_systemd` — `XDG_RUNTIME_DIR`. Це відповідь стеку на питання «у якому оточенні має жити цей сеанс», тож вона й має накриватися останньою.

І вже перед самим `exec` складають нульовий аргумент — `-bash` замість `bash`. Прапорця «будь вхідною» в оболонок ніколи не було: вона дивиться на власне ім'я й читає профілі, якщо те починається з дефіса.

## Порядок, який не можна переставити

![Два стовпці: ліворуч виклики initgroups, setgid, setuid у правильному порядку зі станом ідентичності після кожного; праворуч setuid першим, після чого setgid і initgroups повертають EPERM, і додаткові групи запускача лишаються при новому uid](/reference/unix-linux/permissions/su-switch-user/img/identity-order.svg)

*Ідентичність — не одне число, а набір; правий стовпець показує, що виходить, коли з цього набору встигає змінитися лише перший елемент.*

Зворотний порядок — найчастіша поломка саморобних аналогів, і виглядає вона невинно: спершу ж головне число, а дрібниці потім. Але `setuid` знімає з процесу право міняти будь-що з ідентичності, тож «дрібниці» після нього просто не міняються. Виходить кентавр: `uid` цільовий, груповий — запускачів, а в переліку додаткових груп так і лишилася `wheel`. Ядро судить за цим набором цілком, тож новий процес дістає доступ до всього, що відкрите вашим групам, а кожен створений ним файл лягає з групою `andrij`. Про решту наслідків такої напівзміни — [модель uid і gid](book:unix-linux/uid-gid-model).

## Помилка `setuid`, на яку не подивилися

Виклик, що знімає привілей, — не формальність, і сторінка `setuid(2)` каже про це прямо: пропустити перевірку повернутого значення — тяжка помилка безпеки, бо `setuid` уміє не спрацювати навіть у root. Програма, яка після невдачі поїхала далі, запускає оболонку не від імені `postgres`, а від імені root — і людині, що знала пароль бази даних, віддає всю машину.

Найгостріше це виглядало на [ліміті `RLIMIT_NPROC`](book:unix-linux/resource-limits): межа успадковується через `exec`, тобто ставите її **ви**, перед запуском, а ціль на кшталт `postgres` тримає десятки процесів постійно — отже `setuid` мав повернути `EAGAIN` рівно тоді, коли вам це вигідно. Цей клас помилок виявився таким поширеним, що поступитися врешті довелося **ядру**. У `kernel/sys.c` про це сказано без дипломатії: завелика частина погано написаних програм не дивиться на код повернення `set*uid()`, вважаючи, що в root він не падає, — тому Linux перестав валити тут `setuid`, а натомість зводить на процесі прапорець і завалює наступний `execve`, де проігнорувати відмову вже нешкідливо.

```sh
$ ulimit -u 20              # межа переходить у minisu через exec
$ ./minisu - postgres       # setuid(999) → 0, зате execv → -1, EAGAIN
```

Ця латка закриває один випадок, а не проблему: `setuid` і далі повертає `EAGAIN`, коли ядру бракує пам'яті на свої структури, і `EPERM`, коли в цьому просторі імен користувачів такого числа просто немає. Заразом видно, чому `die()` після `execv` — не окраса: тепер саме туди перенесено відмову. Що вся ця сім'я викликів систематично вживається неправильно, розібрано в праці «Setuid Demystified» (Hao Chen, David Wagner, Drew Dean, USENIX Security Symposium, 2002): там її поведінку в різних ядрах описали формально й на випадках з життя показали, як із порядку викликів і непрочитаних кодів повернення виростають діри. Звідси й рядок із `setuid(0)` одразу після зниження: він не вірить жодному коду, а перевіряє результат — спроба повернути root **мусить** не вдатися.

## Сеанс, який ніхто не закрив

Спокуса прибрати `fork()` сильна: навіщо тримати зайвий процес, якщо можна просто замінити свій образ на оболонку? Відповідь — у тому, що `pam_open_session()` не є перевіркою. Це прохання до модулів **зробити** щось, що потім треба скасувати: `pam_systemd` реєструє сеанс у logind, `pam_mount` монтує домівку, `pam_krb5` кладе на диск файл із квитком, `pam_lastlog` пише запис. `pam_close_session()` — єдине, що це розбирає, і воно потребує тих самих прав root.

Програма, яка зробила `exec` замість `fork`, не закриє сеанс ніколи: процесу, який його відкривав, більше немає, а той, що є, вже не привілейований. Наслідок видно не одразу — просто в системі накопичуються сеанси, які ніколи не закінчуються, змонтовані домівки й покинуті кеші квитків.

З того самого міркування випливає й заборона для дитини: після `fork` вона має **копію** `pamh`, і кожен виклик `pam_end` чи `pam_close_session` там — це друге прибирання по тих самих модулях. Дитина не торкається дескриптора PAM зовсім; батько ж [дочікується її](book:unix-linux/exit-wait-zombies), прибирає й віддає її код виходу далі.

## Термінал і дескриптори, які перейшли у спадок

Дитина отримує ті самі дескриптори `0`, `1`, `2` і той самий керуючий термінал, у якому сидите ви. Саме це робить таку програму зручною й водночас непридатною для походів **униз**, до менш довіреного запису: процес, що тримає ваш термінал відкритим, історично міг через `ioctl(TIOCSTI)` вкинути символи прямо в чергу вводу — і після виходу з `minisu` їх виконає вже ваша оболонка з вашими правами (CVE-2016-2779). Наша сотня рядків не робить із цим нічого, тож чесно годиться лише в бік підвищення. Найчистіша латка — те, що в справжній `su` зветься ключем `--pty`: цілі видають свіжий [псевдотермінал](book:unix-linux/pseudo-terminal) замість вашого, а разом із ним і власний [сеанс](book:unix-linux/sessions-and-process-groups).

Так само переходить усе, що ви лишили відкритим вище двійки: кожен такий [дескриптор](book:unix-linux/file-descriptor) — це готовий доступ, який дитина нізвідки не брала.

## Скільки це коштує

Складність тут не алгоритмічна: вартість роботи — один `fork`, один `exec` і одна перевірка пароля. Уся ціна — у кількості місць, де щось повертає значення: півтора десятка викликів, і кожен має власну гілку помилки, бо жодна з них, залишена без нагляду, не дає збою — вона дає тихо неправильну ідентичність.

Справжня `su` в `util-linux` — це близько тисячі рядків, і різниця з нашою сотнею майже цілком лежить у тому, що ми не робили: псевдотермінал, керування завданнями (`Ctrl-Z` у нашій версії зупинить дитину, а батько цього не помітить), запис у `utmp`, білий список змінних оточення, окремі стеки для вхідного й невхідного режимів, `setsid()` під `-c`. Ідентичність міняється трьома викликами, дозвіл на неї — ще чотирма; усе інше в тій тисячі рядків написано про сеанс, змінити який нічим.
