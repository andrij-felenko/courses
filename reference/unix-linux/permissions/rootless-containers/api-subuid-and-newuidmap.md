# 📋 Інтерфейс конфігурації subuid та утиліт newuidmap

Ця довідкова вставка містить точну специфікацію конфігураційних файлів `/etc/subuid` та `/etc/subgid`, процедурних інтерфейсів ядра `/proc/[pid]/uid_map` і `/proc/[pid]/gid_map`, утиліт делегування `newuidmap`/`newgidmap`, системного API бібліотеки `libsubid` та параметрів ядра sysctl. Вона слугує довідником для налаштування та системної діагностики rootless-середовищ Linux.

## Конфігураційні файли /etc/subuid та /etc/subgid

Файли `/etc/subuid` та `/etc/subgid` визначають пули допоміжних ідентифікаторів користувачів (UID) та груп (GID), які системний адміністратор делегує непривілейованим обліковим записам для відображення у просторах імен користувачів (*User Namespaces*).

### Формат синтаксису конфігурації

Кожен рядок описує один виділений діапазон для користувача і складається з трьох полів, розділених двокрапкою:

```
користувач:початковий_ідентифікатор:кількість
```

| Поле | Тип | Опис та правила валідації |
| :--- | :--- | :--- |
| `користувач` | `String` | Логін користувача у системі (або його числовий UID хоста). Повинно відповідати запису у `/etc/passwd`. |
| `початковий_ідентифікатор` | `Unsigned Int32` | Перший UID/GID у системному діапазоні хоста, виділений цьому користувачеві. Значення за замовчуванням починаються від `100000`. |
| `кількість` | `Unsigned Int32` | Розмір виділеного пулу (кількість неперервних ідентифікаторів). Стандартний розмір становить `65536` ідентифікаторів. |

Приклад конфігураційного файлу `/etc/subuid`:

```
alice:100000:65536
bob:165536:65536
1002:231072:65536
```

### Правила парсингу та брандмауер колізій

Під час аналізу файлів `/etc/subuid` та `/etc/subgid` парсер ядра та системні утиліти дотримуються наступних жорстких правил:
1. **Ігнорування коментарів та порожніх рядків**: Рядки, що починаються з символу `#`, та порожні рядки ігноруються.
2. **Захист від перетинів (Overlaps)**: Діапазони ідентифікаторів різних користувачів не повинні мати спільних UID/GID. У разі виявлення перетинів утиліти модифікації утворюють блокування через файл блокування `/etc/subuid.lock`.
3. **Числові ідентифікатори**: Поле `користувач` може бути як символьним ім'ям (`alice`), так і числовим ідентифікатором (`1000`). Парсер спочатку намагається знайти ім'я в `/etc/passwd`, а у разі невдачі трактує рядок як числовий UID.

### Джерела даних NSS та централізоване керування

Окрім локальних файлів `/etc/subuid` та `/etc/subgid`, система Linux підтримує розпізнавання підпорядкованих ідентифікаторів через перемикач служб імен NSS (від англ. *Name Service Switch*).

У конфігураційному файлі `/etc/nsswitch.conf` базова база даних `subid` керує джерелами пошуку:

```
# Синтаксис джерел subid у /etc/nsswitch.conf
subid: files sss
```

1. **`files`**: Зчитує локальні файли `/etc/subuid` та `/etc/subgid`.
2. **`sss`**: Використовує демон SSSD (від англ. *System Security Services Daemon*) для отримання делегованих діапазонів `subuid` із централізованих каталогів LDAP або FreeIPA/Active Directory. Це дозволяє централізовано виділяти діапазони для тисяч користувачів у корпоративних кластерах.

### Утиліти управління usermod та useradd

Системне додавання та зміна підпорядкованих діапазонів виконується утилітами з пакету `shadow-utils`:

```bash
# Автоматичне виділення діапазону subuid при створенні користувача
useradd -m -v 100000-165535 -w 100000-165535 alice

# Додавання або зміна діапазону subuid для існуючого користувача
usermod --add-subuids 200000-265535 alice
usermod --add-subgids 200000-265535 alice

# Перевірка виділених діапазонів через C-бібліотеку libsubid
getsubids alice
```

Прапорці `--add-subuids` та `--add-subgids` автоматично перевіряють файл `/etc/subuid` на наявність перетинів із виділеними діапазонами інших користувачів, запобігаючи колізіям ідентифікаторів.

## Процедурний інтерфейс /proc/[pid]/uid_map та gid_map

Трансляція ідентифікаторів між батьківським та контейнерним просторами імен керується безпосередньо ядром через псевдофайли у файловій системі `/proc`.

### Формат таблиці відображення

Файли `/proc/[pid]/uid_map` та `/proc/[pid]/gid_map` містять текстові рядки мапінгу. Кожен рядок складається з трьох чисел:

```
ID_внутрішній   ID_зовнішній   Довжина
```

| Елемент | Опис семантики ядра |
| :--- | :--- |
| `ID_внутрішній` | Початковий UID/GID всередині цільового `user namespace`. |
| `ID_зовнішній` | Початковий UID/GID у батьківському `user namespace` (відносно якого виконується запис). |
| `Довжина` | Кількість послідовних ідентифікаторів, до яких застосовується дане лінійне відображення. |

Типова таблиця відображення для rootless-контейнера користувача `alice` (UID 1000 на хості):

```
         0       1000          1
         1     100000      65536
```

Розшифровка таблиці ядром:
* Рядок `0 1000 1`: Внутрішній `root` (UID 0) у контейнері відповідає хостовому UID 1000 (`alice`).
* Рядок `1 100000 65536`: Внутрішні системні UID від `1` до `65536` відповідають хостовим UID від `100000` до `165535`.

### Правила атомарності та системні обмеження ядра

1. **Одноразовий запис**: Запис у файли `/proc/[pid]/uid_map` та `/proc/[pid]/gid_map` є **атомарним і одноразовим**. Після того, як у файл було успішно записано хоча б один рядок відображення, будь-які наступні спроби виклику `write(2)` до цього файлу повертатимуть помилку `EPERM` (*Permission denied*). Це запобігає динамічній зміні ідентифікаторів працюючого процесу.
2. **Лише один рядок для непривілейованих процесів**: Непривілейований процес без `CAP_SETUID` у батьківському просторі імен може записати у `uid_map` **лише 1 рядок**, і в цьому рядку `ID_зовнішній` мусить точно дорівнювати його власному ефективному UID.
3. **Обмеження на кількість рядків**: Максимальна кількість рядків у таблиці мапінгу обмежена константою ядра `MAX_USER_NS_MAP_ENTRIES` (340 рядків починаючи з ядра Linux 4.15).

### Контроль допоміжних груп через /proc/[pid]/setgroups

Перед записом у файл `/proc/[pid]/gid_map` ядро перевіряє стан псевдофайла `/proc/[pid]/setgroups`.

```bash
# Зчитування поточного стану прапорця setgroups
cat /proc/self/setgroups
```

Файл може містити одне з двох текстових значень:
* **`deny`**: Забороняє системні виклики `setgroups(2)` та `initgroups(3)` всередині цього та дочірніх просторів імен.
* **`allow`**: Дозволяє виклики `setgroups(2)` (вимагає привілеїв `CAP_SETGID` у цьому namespace).

> ⚠️ **Важливе правило безпеки:** Непривілейований процес **мусить обов'язково** записати `deny` у `/proc/[pid]/setgroups` перед тим, як писати у `/proc/[pid]/gid_map`. Якщо цей крок пропущено, ядро відхилить запис у `gid_map` з помилкою `EPERM`. Це закриває історичну вразливість, коли процес міг створити user namespace, налаштувати `gid_map` і скинути свої додаткові групи для обходу заборонних прав у POSIX ACL.

## CLI утиліти newuidmap та newgidmap

Оскільки звичайний процес користувача не має права самостійно записувати декілька рядків у `/proc/[pid]/uid_map`, розробники створили системні утиліти `newuidmap` та `newgidmap`. Вони встановлюються у системі з прапорцем `setuid root` (права `-rwsr-xr-x`, власник `root:root`).

### Специфікація виклику newuidmap

```
newuidmap PID UID_внутр1 UID_зовн1 Кількість1 [UID_внутр2 UID_зовн2 Кількість2 ...]
```

### Параметри командного рядка

| Аргумент | Тип | Призначення |
| :--- | :--- | :--- |
| `PID` | `Integer` | PID цільового процесу, який створив новий `user namespace` і перебуває в стані очікування. |
| `UID_внутр` | `Integer` | Початковий ідентифікатор всередині цільового простору імен. |
| `UID_зовн` | `Integer` | Початковий ідентифікатор у батьківському просторі імен хоста. |
| `Кількість` | `Integer` | Кількість неперервних ідентифікаторів для даної мапінг-секції. |

Приклад реального виклику з Podman або RootlessKit:

```bash
# Створення мапінгу для PID 14205 від імені утиліти newuidmap
newuidmap 14205 0 1000 1 1 100000 65536
```

### Коди повернення та діагностика помилок newuidmap

При виконанні `newuidmap` може завершуватися з наступними кодами стану (Exit Codes):

* `0`: Запис мапінгу пройшов успішно.
* `1`: Помилка синтаксису аргументів або відсутність прав (`target uid 'X' not allowed`). Виникає, якщо виділений діапазон виходить за межі `/etc/subuid`.
* `2`: Цільовий процес з вказаним `PID` не існує або завершився до моменту запису.
* `3`: Помилка відкриття або запису у `/proc/[PID]/uid_map` (наприклад, мапінг уже було заповнено раніше).

### Внутрішній алгоритм авторизації newuidmap

Коли утиліта `newuidmap` запускається непривілейованим користувачем, вона виконує суворий алгоритм перевірки:

1. Отримує реальний UID процесу, що її викликав, за допомогою виклику `getuid()`.
2. Читає конфігураційний файл `/etc/subuid` (або запитує через NSS/SSSD).
3. Знаходить делегований пул для цього реального UID (наприклад, `100000..165535` для `alice`).
4. Для кожного аргументу `[UID_внутр, UID_зовн, Кількість]` перевіряє:
   * Якщо `UID_зовн == real_uid`, то `Кількість` мусить дорівнювати `1` (відображення власника).
   * Якщо `UID_зовн != real_uid`, то весь діапазон `[UID_зовн .. UID_зовн + Кількість - 1]` мусить повністю входити у виділений пул з `/etc/subuid`.
5. Якщо хоча б один ідентифікатор виходить за межі дозволеного пулу, `newuidmap` виводить повідомлення про помилку `target uid '...' not allowed` у `stderr` і завершує роботу з кодом `1`.
6. Якщо перевірка успішна, утиліта відкриває `/proc/[PID]/uid_map` і записує сформовану таблицю від імені суперкористувача `root`.

## Системні виклики unshare(2), clone3(2) та sysctl параметри

### Системний виклик unshare(2) та прапорець CLONE_NEWUSER

Створення ізольованого простору імен користувача виконується системним викликом `unshare(2)` з прапорцем `CLONE_NEWUSER`:

:::tabs
```c
#define _GNU_SOURCE
#include <sched.h>
#include <unistd.h>

// Створення нового user namespace у поточному потоці C
int res = unshare(CLONE_NEWUSER);
```
```cpp
#include <sched.h>
#include <system_error>
#include <unistd.h>

// Системний виклик unshare з обробкою помилок C++
void create_user_namespace() {
    if (::unshare(CLONE_NEWUSER) == -1) {
        throw std::system_error(errno, std::generic_category(), "unshare(CLONE_NEWUSER) failed");
    }
}
```
:::

Сучасний системний виклик `clone3(2)` у ядрі Linux 5.3+ використовує структуру `struct clone_args` для передачі розширеного набору прапорців:

:::tabs
```c
#include <linux/sched.h>
#include <sys/syscall.h>
#include <unistd.h>

struct clone_args cl_args = {
    .flags = CLONE_NEWUSER | CLONE_NEWNS | CLONE_NEWNET,
    .exit_signal = SIGCHLD,
};
long pid = syscall(SYS_clone3, &cl_args, sizeof(cl_args));
```
```cpp
#include <linux/sched.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <system_error>

pid_t invoke_clone3_user_ns() {
    struct clone_args cl_args{};
    cl_args.flags = CLONE_NEWUSER | CLONE_NEWNS | CLONE_NEWNET;
    cl_args.exit_signal = SIGCHLD;
    
    long pid = ::syscall(SYS_clone3, &cl_args, sizeof(cl_args));
    if (pid == -1) {
        throw std::system_error(errno, std::generic_category(), "clone3 failed");
    }
    return static_cast<pid_t>(pid);
}
```
:::

Після успішного виконання виклику `unshare(CLONE_NEWUSER)` поточний процес отримує новий простір імен користувачів, а його ефективний UID та GID тимчасово змінюються на `65534` (`nobody` / `overflowuid`), поки не буде завершено конфігурацію файлів `uid_map` та `gid_map`.

### Системний виклик setns(2)

Перехід існуючого процесу в вже створений user namespace іншого процесу виконується викликом `setns(2)`:

:::tabs
```c
#define _GNU_SOURCE
#include <sched.h>
#include <fcntl.h>
#include <unistd.h>

int fd = open("/proc/14205/ns/user", O_RDONLY);
int res = setns(fd, CLONE_NEWUSER);
close(fd);
```
```cpp
#include <sched.h>
#include <fcntl.h>
#include <unistd.h>
#include <system_error>

void join_user_namespace(int fd) {
    if (::setns(fd, CLONE_NEWUSER) == -1) {
        throw std::system_error(errno, std::generic_category(), "setns(CLONE_NEWUSER) failed");
    }
}
```
:::

Файловий дескриптор `fd` відкривається з процедурного файлу `/proc/[PID]/ns/user`. Для успішного переходу процес повинен мати capability `CAP_SYS_ADMIN` у цільовому user namespace.

### Параметри ядра sysctl

Керування глобальною поведінкою та межами rootless контейнеризації здійснюється через параметри ядра sysctl:

| Параметр sysctl | Значення за замовчуванням | Вплив на rootless-середовище |
| :--- | :--- | :--- |
| `kernel.unprivileged_userns_clone` | `1` (у Debian/Ubuntu; `0` у старих RHEL) | Головний перемикач. Якщо встановлено у `0`, непривілейовані процеси не можуть викликати `unshare(CLONE_NEWUSER)`. |
| `net.ipv4.ping_group_range` | `0 2147483647` | Визначає діапазон GID користувачів, яким дозволено створювати непривілейовані ICMP-сокети (`ping`). |
| `net.ipv4.ip_unprivileged_port_start` | `1024` (або `80`) | Нижній номер TCP/UDP порту, доступний для прив'язки без `CAP_NET_BIND_SERVICE`. Значення `80` дозволяє контейнеру відкривати порти 80/443. |
| `user.max_user_namespaces` | `1024..65536` | Максимальна загальна кількість просторів імен користувачів, які можуть існувати в системі одночасно. |
