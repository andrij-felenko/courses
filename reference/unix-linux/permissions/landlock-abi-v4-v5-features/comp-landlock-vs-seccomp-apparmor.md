# Порівняльний аналіз Landlock ABI v4/v5, Seccomp-BPF та класичних LSM (SELinux/AppArmor)

Ізоляція процесів у операційних системах Linux розвивалася через три концептуально відмінні підходи: низькорівневе фільтрування системних викликів на рівні регістрів процесора (Seccomp-BPF), централізований мандатний контроль доступу адміністратора системи (SELinux / AppArmor) та динамічне безпривілейоване сандбоксування у коді самої прикладної програми (Landlock LSM).

Нижче наведено вичерпний порівняльний аналіз архітектурних характеристик, моделей довіри та сфер застосування кожного механізму.

## 1. Сводна порівняльна матриця

| Критерій | Landlock ABI v4/v5 | Seccomp-BPF | SELinux / AppArmor |
| :--- | :--- | :--- | :--- |
| **Точка перехоплення (Hook Layer)** | LSM Hooks (VFS Path, BSD Socket, Device Ioctl) | Syscall Entry (`tracehook` на вході в системний виклик) | LSM Hooks (`struct inode`, `cred`, `socket`, `ipc`) |
| **Потреба привілеїв `root`** | **Ні** (вимагає лише `PR_SET_NO_NEW_PRIVS`) | **Ні** (з `PR_SET_NO_NEW_PRIVS`) | **Так** (завантаження політик лише з `CAP_MAC_ADMIN` / `root`) |
| **Аналіз VFS-шляхів** | **Повний** (ієрархічна перевірка inode у ядрі) | **Відсутній** (бачить лише сирі 64-бітні вказівники у пам'яті) | **Повний** (позначки контекстів SELinux або шляхи AppArmor) |
| **Контроль TCP-мережі** | **Портовий** (`bind` / `connect` для TCP у v4) | **Нестійкий** (перевіряє номери викликів, але не порти) | **Гнучкий** (порти, інтерфейси, IP-адреси, типи сокетів) |
| **Обмеження `ioctl()`** | **Глобальне** за типами пристроїв (v5) | **За номерами `ioctl`** (числові константи `cmd`) | **Тонке** (за контекстами файлів пристроїв та масками) |
| **Життєвий цикл політики** | Динамічний, декларується у коді самої програми | Динамічний, завантажується BPF-фільтром у процес | Статичний, завантажується в ядро під час старту ОС |
| **Складність розробки** | Низька (простий декларативний C/C++ API) | Висока (написання BPF-інструкцій чи `libseccomp`) | Висока (складний синтаксис політик SELinux / AppArmor) |
| **Накладні витрати (Overhead)** | Мінімальні (`O(1)` для портів, хеш-таблиці VFS) | `O(N)` перевірка BPF-інструкцій на кожен syscall | Мінімальні до середніх (залежно від розміру політики) |

## 2. Глибинний порівняльний аналіз підходів

### 2.1. Seccomp-BPF проти Landlock: Низький рівень проти семантики об'єктів

Seccomp-BPF працює на найнижчому можливому рівні ядра — на точці входу в системний виклик (`tracehook_report_syscall_entry`). У цей момент у BPF-програми є доступ лише до структури `seccomp_data`, яка містить номер системного виклику, архітектуру CPU та 64-бітні значення п'яти регістрів процесора.

Це робить Seccomp ідеальним інструментом для відсікання цілих категорій системних викликів. Якщо додатку не потрібен `ptrace()`, `kexec_load()`, `bpf()`, `unshare()` чи `syslog()`, Seccomp блокує їх із нульовими накладними витратами.

Проте Seccomp принципово не здатен безпечно перевіряти вказівники у пам'яті користувацького простору (user-space memory pointers). При виклику `openat(dfd, path_ptr, flags)` у регістрі лежить лише 64-бітна адреса `path_ptr`. Якщо BPF-фільтр спробує прочитати пам'ять за цим вказівником, виникає серйозна вразливість **TOCTOU (Time-of-Check to Time-of-Use)**: інший потік процесу може змінити вміст рядка у пам'яті між моментом перевірки Seccomp та моментом відкриття файла ядром.

Landlock LSM позбавлений цієї вади, оскільки він діє всередині мандатних хуків LSM, коли ядро вже безпечно скопіювало шлях у простір ядра, розпарсило VFS-дескриптор, знайшло індекс `struct inode` або асоціювало сокет із конкретним портом. Landlock гарантує семантично точну та TOCTOU-захищену перевірку об'єктів.

### 2.2. AppArmor / SELinux проти Landlock: Централізований контроль проти Self-Sandboxing

Мандатні механізми SELinux та AppArmor надають системному адміністратору абсолютну владу над ОС. SELinux маркує кожен inode та процес безпековими мітками (security contexts) і перевіряє матрицю дозволів Type Enforcement. AppArmor зв'язує профілі безпеки зі шляхами виконуваних файлів.

Незважаючи на потужність, ці підсистеми мають фундаментальні обмеження для прикладного ПЗ:
1. **Залежність від прав адміністратора**: Завантаження або зміна політик SELinux/AppArmor вимагає прав `root` (`CAP_MAC_ADMIN`). Звичайний користувач або сервіс у контейнері не може змінити свій профіль.
2. **Фрагментація дистрибутивів**: Ubuntu типово використовує AppArmor, Red Hat / Fedora — SELinux, а Alpine / Arch — часто поставляються без активного MAC. Розробник ПЗ не може гарантувати, що його програма буде захищена на машині користувача.
3. **Відсутність динамічного зниження привілеїв**: Програма не може самостійно зменшити свої права після ініціалізації. Наприклад, веб-сервер відкриває слухаючий порт 80 і конфігураційний файл, а потім хоче назавжди позбавити себе права відкривати будь-які інші порти або файли.

Landlock реалізує парадигму **Self-Sandboxing (самоізоляції)**. Програма несе логіку захисту всередині власного двійкового коду, виконуючи системні виклики Landlock після завершення фази ініціалізації. Це працює на будь-якому ядрі Linux із підтримкою Landlock незалежно від дистрибутива чи налаштувань SELinux/AppArmor.

## 3. Багаторівневий захист (Defense in Depth)

У сучасних виробничих системах Landlock, Seccomp-BPF та AppArmor не конкурують, а доповнюють один одного:

- **Рівень 1 (Seccomp-BPF)**: Відсікає небезпечні та невикористовувані системні виклики ядра (блокування атаки на повернемо віддалений код через `kexec`, `bpf`, `ptrace`).
- **Рівень 2 (Landlock ABI v4/v5)**: Динамічно ізолює дозволені системні виклики за контекстом — обмежує VFS-каталоги, TCP-порти та заблоковує виклики `ioctl` на файлах пристроїв.
- **Рівень 3 (AppArmor / SELinux)**: Забезпечує жорстку системну межу між різними користувачами та системними демонами в масштабі всієї операційної системи.
