# Еволюція Landlock LSM: ABI v4/v5 (мережеві обмеження та ioctl)

<preknowlist>
- Концепція файлових дескрипторів, процесів і прав доступу (DAC/MAC) в Linux.
- Базові знання про Linux Security Modules (LSM), такі як SELinux, AppArmor, BPF.
- Розуміння концепції "пісочниці" (sandbox) та ізоляції процесів.
- Системні виклики (syscalls) в Linux, зокрема `bind()`, `connect()`, `ioctl()`.
- Основи протоколу TCP і мережевих сокетів.
</preknowlist>

Landlock — це сучасний модуль безпеки Linux (LSM), що дозволяє створювати безпечні "пісочниці" (sandboxes) для неревілейованих процесів. На відміну від традиційних механізмів, таких як SELinux чи AppArmor, які вимагають прав суперкористувача (root) для налаштування глобальних політик, Landlock був створений з однією ключовою ідеєю: **дозволити будь-якому процесу обмежувати власні права**, без необхідності бути root. 

У цій статті ми детально розглянемо еволюцію Landlock від першої версії до ABI v4 та v5, де з'явилися революційні можливості: обмеження мережевих з'єднань (TCP bind/connect) та контроль над викликами `ioctl()`.

## Філософія Landlock: Безпривілейне пісочничне ізолювання

До появи Landlock, створення пісочниці в Linux вимагало використання Seccomp-BPF, просторів імен (namespaces) або складних політик SELinux/AppArmor. Seccomp обмежує системні виклики, але не розуміє контексту (наприклад, він не може легко відрізнити відкриття файлу `/etc/passwd` від відкритого `/tmp/foo`). Простори імен вимагають або прав root, або використання user namespaces, що часто збільшує площу атаки.

Landlock вирішує цю проблему, дозволяючи процесу сказати ядру: "З цього моменту я і всі мої нащадки не маємо права звертатися до жодних файлів, крім цієї теки, і не можемо створювати жодних мережевих з'єднань". Це робиться за допомогою простого API.

### Як працює Landlock?

Процес створює "набір правил" (ruleset), додає до нього правила (наприклад, дозволити читання з `/usr/lib`) і потім "застосовує" цей набір до себе. Після застосування правила не можуть бути скасовані. Вони успадковуються всіма дочірніми процесами.

Ключовим моментом є версіювання (ABI - Application Binary Interface). Оскільки ядро Linux розвивається, Landlock отримує нові можливості. Ядро повідомляє процесу, яку версію ABI Landlock воно підтримує, і процес може адаптувати свої правила.

## Еволюція ABI: від файлів до мережі та пристроїв

Еволюція Landlock є яскравим прикладом поступового нарощування функціоналу ядра.

### ABI v1, v2 та v3: Файлова система

Перші версії Landlock (ABI v1 у Linux 5.13, v2 та v3 у наступних релізах) фокусувалися виключно на обмеженні доступу до файлової системи.

- **ABI v1** дозволив процесам обмежувати базові операції: читання, запис, виконання файлів, створення тек, посилань (hard/symlinks) тощо. Це вже було величезним кроком: веб-сервер міг замкнути себе в теці `/var/www` без `chroot()`.
- **ABI v2 та v3** додали тонші налаштування файлової системи, такі як підтримка зміни видимості файлів та вдосконалення перейменування (rename).

Але сучасний світ не обмежується файлами. Зловмисник, зламавши процес, ізольований у файловій системі, міг відкрити сокет і передати дані на віддалений сервер, або використати вразливості в драйверах пристроїв через `ioctl`.

### ABI v4: Мережеві обмеження (TCP)

У ядрі Linux 6.7 з'явився **Landlock ABI v4**, який додав дві критично важливі права: `LANDLOCK_ACCESS_NET_BIND_TCP` та `LANDLOCK_ACCESS_NET_CONNECT_TCP`.

Це означало, що тепер розробники можуть не лише замкнути процес у теці, але й заборонити йому спілкуватися по мережі.

#### LANDLOCK_ACCESS_NET_BIND_TCP

Це право контролює здатність процесу використовувати системний виклик `bind()` для TCP-сокетів. `bind()` використовується для прив'язки сокета до певного порту, що є необхідним для створення сервера, який слухає вхідні з'єднання.

Якщо процес обмежує себе за допомогою Landlock і не надає собі `LANDLOCK_ACCESS_NET_BIND_TCP` для конкретного порту, виклик `bind()` поверне помилку `EACCES`.

Це захищає від атак, коли зловмисник, зламавши процес, намагається підняти бекдор-сервер (backdoor bind shell) на високому порту.

#### LANDLOCK_ACCESS_NET_CONNECT_TCP

Це право контролює системний виклик `connect()`, який використовується для встановлення вихідних TCP-з'єднань.

Якщо веб-серверу потрібно лише приймати з'єднання (через `bind` і `accept`) і йому ніколи не потрібно самому ініціювати з'єднання з іншими серверами (наприклад, він не робить запитів до бази даних, або робить їх лише через локальні UNIX-сокети), він може назавжди заборонити собі TCP connect.

Це знищує цілий клас атак: reverse shell. Навіть якщо хакер виконає довільний код, він не зможе змусити скомпрометований процес підключитися назад до сервера зловмисника (Command and Control сервер).

#### Приклад використання ABI v4

Щоб застосувати ці правила, програма спочатку перевіряє, чи підтримується ABI v4:

```c
int abi = landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION);
if (abi < 4) {
    // Ядро застаріле, мережеві правила не підтримуються
}
```

Потім створюється `ruleset_attr`, в якому декларуються наміри контролювати мережу:

```c
struct landlock_ruleset_attr attr = {
    .handled_access_net = LANDLOCK_ACCESS_NET_BIND_TCP |
                          LANDLOCK_ACCESS_NET_CONNECT_TCP,
};
int ruleset_fd = landlock_create_ruleset(&attr, sizeof(attr), 0);
```

Після цього можна додати правила (дозволи) для конкретних портів. Наприклад, дозволити `bind` тільки на порт 8080:

```c
struct landlock_net_port_attr net_attr = {
    .allowed_access = LANDLOCK_ACCESS_NET_BIND_TCP,
    .port = 8080,
};
landlock_add_rule(ruleset_fd, LANDLOCK_RULE_NET_PORT, &net_attr, 0);
```

І наприкінці — застосувати правила:

```c
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
landlock_restrict_self(ruleset_fd, 0);
```

### ABI v5: Контроль над `ioctl()`

У Linux 6.8 було представлено **Landlock ABI v5**, що приніс `LANDLOCK_ACCESS_FS_IOCTL_DEV`. Цей крок закрив ще одну величезну діру в пісочницях.

Системний виклик `ioctl()` (input/output control) — це своєрідна "чорна діра" Linux API. Він дозволяє програмам надсилати специфічні для пристрою команди безпосередньо до драйверів (наприклад, графічної карти, аудіо, терміналу тощо). Оскільки кожен драйвер має свій власний набір команд `ioctl`, ядру дуже важко уніфіковано їх перевіряти.

Зловмисники часто використовують `ioctl` для експлуатації вразливостей у драйверах (LPE - Local Privilege Escalation). Якщо процес у пісочниці міг відкрити файл пристрою (наприклад `/dev/dri/renderD128`), він міг надіслати туди зловмисний `ioctl`.

#### LANDLOCK_ACCESS_FS_IOCTL_DEV

Завдяки ABI v5, Landlock тепер може забороняти виклики `ioctl` для спеціальних файлів пристроїв (character and block devices).

За замовчуванням, якщо набір правил декларує `LANDLOCK_ACCESS_FS_IOCTL_DEV`, усі виклики `ioctl` до пристроїв будуть заблоковані, окрім базових і безпечних команд (таких як `FIOCLEX` або `TCGETS`).

Щоб дозволити певні команди, розробник повинен явно прописати їх у правилах. Це фундаментально змінює парадигму: від "заборонити відомі погані `ioctl`" (що робив Seccomp, але це вкрай складно через їхню величезну кількість і перетин номерів) до "дозволити тільки відомі хороші `ioctl`".

## Взаємодія з Seccomp-BPF

Landlock не замінює Seccomp-BPF, а доповнює його.
Seccomp чудовий для блокування цілих системних викликів (наприклад, заборонити `ptrace` або `unshare`). Але коли справа доходить до аргументів системних викликів, Seccomp може перевіряти лише значення вгістрах (pointer values). Він не може розіменувати вказівники. Тому Seccomp не знає, який шлях у рядку, переданому в `openat()`.
Landlock, як LSM, працює на іншому рівні: він діє, коли ядро вже розпарсило шлях і знає, який inode відкривається, який порт TCP використовується тощо.

Використання обох механізмів дає найсильніший захист: Seccomp відсікає непотрібні системні виклики, а Landlock обмежує файли, мережу та `ioctl` для тих викликів, що дозволені.

## Виклики та перспективи впровадження

### Проблема сумісності (Fallback)
Основна складність для розробників — це фрагментація версій ядер Linux. Програма, що використовує ABI v5, може бути запущена на старій системі (наприклад, Ubuntu 20.04), де Landlock має лише ABI v1 або взагалі відсутній.

Landlock спроєктований так, щоб дозволити gracefully degrade (м'яку деградацію). Розробник має запитати версію за допомогою `landlock_create_ruleset(..., LANDLOCK_CREATE_RULESET_VERSION)` і використовувати лише ті прапорці `handled_access_...`, які підтримуються цією версією. Якщо ядро не підтримує обмеження мережі, програма просто застосує файлові обмеження.

### Майбутнє Landlock

Розробники (насамперед Mickaël Salaün) продовжують розвивати Landlock. Очікується поява підтримки:
- **UDP сокетів**: ABI v4 обмежує лише TCP. UDP, будучи stateless протоколом, вимагає інших підходів у ядрі для ефективного обмеження.
- **UNIX доменних сокетів (IPC)**: для заборони процесам спілкуватися з іншими локальними демонами (наприклад, D-Bus).
- **Сигналів (kill, ptrace)**: для ізоляції міжпроцесної взаємодії на рівні сигналів.

## Детальний розбір архітектури Landlock

### Як ядро інтегрує Landlock
Landlock реалізований як модуль LSM (Linux Security Module), що використовує eBPF під капотом (хоча API для користувача приховує всю складність eBPF). Коли процес робить системний виклик, наприклад, `bind()`, ядро проходить через стандартні перевірки (DAC - чи належить порт користувачу, MAC - SELinux/AppArmor), і потім викликає хуки LSM.

Landlock перевіряє правила, застосовані до поточного процесу. Якщо процес не має доступу, повертається `EACCES`.

### Практичний посібник: Створення безпечного мережевого демона

Уявімо, що ми розробляємо простий веб-сервер на C. Він повинен слухати порт 80 (або 8080 для непривілейованого режиму) і читати файли з `/var/www/html`. Він не повинен мати можливості запускати інші програми або з'єднуватися з іншими серверами.

Крок 1. Визначаємо необхідні права.
Для файлів нам знадобиться `LANDLOCK_ACCESS_FS_READ_FILE`.
Для мережі: `LANDLOCK_ACCESS_NET_BIND_TCP`.

Крок 2. Ініціалізація Landlock.
Програма стартує. Вона може відкрити конфігураційні файли або порти (до застосування Landlock), або ж застосувати Landlock одразу, дозволивши лише потрібне.

```c
int abi = landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION);
```

Крок 3. Підготовка атрибутів.
```c
struct landlock_ruleset_attr attr = {0};
attr.handled_access_fs = LANDLOCK_ACCESS_FS_READ_FILE | LANDLOCK_ACCESS_FS_READ_DIR;
if (abi >= 4) {
    attr.handled_access_net = LANDLOCK_ACCESS_NET_BIND_TCP | LANDLOCK_ACCESS_NET_CONNECT_TCP;
}
```
Ми завжди декларуємо `CONNECT_TCP` в `handled_access_net`, якщо хочемо його заборонити. Суть у тому, що все, що вказано в `handled_access_net`, за замовчуванням забороняється, поки не буде додано відповідне правило. Якщо ми не додамо правило для CONNECT, він буде повністю заблокований.

Крок 4. Додавання файлових правил.
```c
struct landlock_path_beneath_attr path_attr = {
    .allowed_access = LANDLOCK_ACCESS_FS_READ_FILE | LANDLOCK_ACCESS_FS_READ_DIR,
};
path_attr.parent_fd = open("/var/www/html", O_PATH | O_CLOEXEC);
landlock_add_rule(ruleset_fd, LANDLOCK_RULE_PATH_BENEATH, &path_attr, 0);
close(path_attr.parent_fd);
```

Крок 5. Додавання мережевих правил.
```c
if (abi >= 4) {
    struct landlock_net_port_attr net_attr = {
        .allowed_access = LANDLOCK_ACCESS_NET_BIND_TCP,
        .port = 8080,
    };
    landlock_add_rule(ruleset_fd, LANDLOCK_RULE_NET_PORT, &net_attr, 0);
}
```

Крок 6. Застосування.
```c
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
landlock_restrict_self(ruleset_fd, 0);
```

Тепер, якщо у веб-сервері буде знайдена вразливість, що дозволяє виконання довільного коду (RCE), зловмисник не зможе прочитати `/etc/shadow`, запустити `/bin/sh` або створити з'єднання з `hacker.com`. Всі ці дії будуть негайно відхилені ядром з помилкою Permission Denied.

### Глибинний аналіз IOCTL (ABI v5)

Для розуміння ваги ABI v5, розглянемо природу `ioctl()`. Це системний виклик, який приймає файловий дескриптор, номер запиту і додатковий аргумент (часто вказівник на структуру).

```c
int ioctl(int fd, unsigned long request, ...);
```
Номери `request` є специфічними для кожного пристрою (чи класу пристроїв). Наприклад, драйвер відеокарти має свої ioctl для виділення пам'яті (GEM) або сабміту команд GPU.

Ізолюючи процес (наприклад, веб-браузер або контейнер), нам може знадобитися дати йому доступ до `/dev/urandom` або `/dev/null`. Ці пристрої в цілому безпечні. Проте, якщо процес отримує доступ до `/dev/tty` (що може статися випадково при успадкуванні дескрипторів), він може використовувати специфічні ioctl для терміналів, зокрема `TIOCSTI`, щоб вставляти символи в чергу вводу терміналу. Це дозволяє пісочничному процесу виконувати команди в контексті батьківського терміналу!

З Landlock ABI v5 розробник вказує `LANDLOCK_ACCESS_FS_IOCTL_DEV` у правилах. Це автоматично блокує всі ioctl для всіх файлів пристроїв (character/block).
Ядро має внутрішній "білий список" (whitelist) базових ioctl, які є безпечними і дозволяються завжди (наприклад, `FIOCLEX` - set close-on-exec, або `TCGETS` для читання термінальних параметрів). Всі інші, які можуть змінити стан системи, блокуються.

Якщо додатку справді потрібен якийсь ioctl, розробник поки що (в v5) не може додати вибіркові ioctl-правила! В ABI v5 введено лише загальний рубильник `LANDLOCK_ACCESS_FS_IOCTL_DEV`. Якщо ви обмежуєте ioctl, ви забороняєте їх всі (окрім безпечного мінімуму). Підтримка тонкого налаштування ioctl очікується в майбутніх версіях (ABI v6+).

### Безпека без прав root

Перевага Landlock полягає в тому, що він працює з `PR_SET_NO_NEW_PRIVS`. Цей прапорець гарантує, що процес ніколи не зможе отримати більше прав (навіть виконавши setuid-файл на кшталт `/usr/bin/sudo`).
Це фундаментально відрізняє Landlock від AppArmor, де політики повинні бути завантажені користувачем root у систему перед запуском програми. З Landlock, сама програма несе свої правила з собою. Це ідеально для розробників: вони можуть писати безпечне ПЗ, не турбуючись про те, чи правильно системний адміністратор налаштував профіль AppArmor/SELinux для їхньої програми.

### Підсумок
Landlock змінює правила гри. Він демократизує безпеку в Linux. З кожною новою версією ABI (v1-v3 для ФС, v4 для мережі, v5 для ioctl) площа атаки, яку можна відсікти, стає все більшою. Застосування Landlock стає "best practice" для розробки будь-яких сервісів або програм, що працюють із недовіреними даними.

Для тих, хто використовує Landlock, необхідно завжди перевіряти версію ABI і застосовувати всі доступні обмеження, щоб забезпечити максимальну безпеку на актуальних ядрах Linux.
