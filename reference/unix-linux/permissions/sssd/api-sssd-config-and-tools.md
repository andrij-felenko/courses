# 📋 Довідка SSSD: sssd.conf, шляхи на диску, sssctl

Це поверхня керування демоном: із яких секцій складається `/etc/sssd/sssd.conf` і хто читає кожну, якими ключами вибирають провайдерів і терміни життя кеша, де лежать бази й сокети, і якими командами з демона дістають стан. Типові значення винесено окремою колонкою навмисно: більшість несподіванок у налаштуванні — не хибний ключ, а забуте типове.

## Файл конфігурації: форма й права

Синтаксис — ini: секція у квадратних дужках, `ключ = значення`, список через кому, коментар — рядок, що починається з `#` або `;` (усередині рядка коментарів немає).

Права на файл — не порада, а умова запуску: `sssd.conf` мусить бути звичайним файлом, доступним **лише** тому користувачеві, від якого працює служба, або `root`. На практиці це режим `0600` і власник `root:root` (у складаннях із непривілейованим демоном — `sssd:sssd`). Причина в тому, що саме тут стоїть пароль службового запису, яким машина прив'язується до каталогу; [біти прав](book:unix-linux/permission-bits) — про сам механізм перевірки.

Окремі шматки конфігурації кладуть у `/etc/sssd/conf.d/`. Правила такі: беруться файли з розширенням `.conf`, що не починаються з крапки; власник і режим у них ті самі, що в основного файлу; **фрагмент має вищий пріоритет за `sssd.conf`**, а серед фрагментів виграє прочитаний пізніше за алфавітом.

На старті демон переливає текст конфігурації у власну базу `/var/lib/sss/db/config.ldb` і далі працює вже з неї — тому правка файлу без перезапуску служби не діє.

| Секція | Хто читає | Що задає |
|---|---|---|
| `[sssd]` | монітор | перелік доменів і служб, спільні налаштування |
| `[domain/ІМ'Я]` | бекенд цього домену | провайдери, адреси серверів, терміни кеша |
| `[domain/ІМ'Я/ПІДДОМЕН]` | той самий бекенд | окремі значення для довіреного піддомену |
| `[nss]`, `[pam]` | відповідний респондер | поведінку саме цього виду відповідей |
| `[sudo]`, `[ssh]`, `[autofs]`, `[pac]`, `[ifp]`, `[kcm]` | респондери | те саме для решти видів запитів |
| `[application/ІМ'Я]` | бекенд | домен, невидимий через NSS — лише для програм |
| `[certmap/ДОМЕН/ПРАВИЛО]` | бекенд | зіставлення сертифіката з користувачем |
| `[prompting/password]`, `[prompting/2fa]`, `[prompting/passkey]` | pam-респондер | форму й текст запиту при вході |

Перелік дозволених секцій і ключів вшито в сам SSSD, і звіряє з ним `sssctl config-check`. Через це старий рядок `config_file_version = 2` із першої гілки в новому файлі зайвий — у чинному переліку його вже немає.

## `[sssd]`: що взагалі вмикається на машині

| Ключ | Значення | Нотатка |
|---|---|---|
| `domains` | список через кому | порядок у списку = порядок опитування |
| `services` | `nss, pam, sudo, ssh, autofs, pac, ifp` | у сучасних складаннях необов'язковий: респондери піднімає systemd [за сокетом](book:unix-linux/socket-activation) |
| `user` | ім'я службового користувача | є лише там, де демон зібрано з підтримкою непривілейованої роботи |
| `debug_level` (коротко `debug`) | 0–9 або бітова маска | типове для всіх частин одразу |
| `default_domain_suffix` | ім'я домену | до якого домену віднести ім'я без `@` |
| `domain_resolution_order` | список доменів | порядок пошуку коротких імен |
| `re_expression`, `full_name_format` | шаблони | як розбирати й як друкувати `ім'я@домен` |
| `try_inotify`, `monitor_resolv_conf` | булеві | чи стежити за змінами файлів |

## `[domain/…]`: чотири провайдери

Домен — це одна база облікових записів. Що з нею робити, задають чотири ключі, і кожен відповідає за окрему операцію.

| Ключ | Допустимі значення | Типово |
|---|---|---|
| `id_provider` | `ldap`, `ad`, `ipa`, `proxy`, `idp` | типового немає — ключ обов'язковий |
| `auth_provider` | `ldap`, `krb5`, `ad`, `ipa`, `proxy`, `idp`, `none` | `id_provider`, якщо той уміє автентифікацію |
| `access_provider` | `permit`, `deny`, `ldap`, `ad`, `ipa`, `simple`, `krb5`, `proxy` | **`permit`** |
| `chpass_provider` | `ldap`, `krb5`, `ad`, `ipa`, `proxy`, `none` | `auth_provider`, якщо той уміє змінювати пароль |

Типове `permit` варте окремої уваги: домен, у якому `access_provider` не задано, пускає на машину **кожного, кого бачить у каталозі**. Обмеження кола — завжди окреме свідоме рішення (`simple` зі списками, `ldap` із фільтром, `ad` за політиками).

Поруч живуть провайдери інших видів запитів: `sudo_provider`, `resolver_provider` (імена машин), `selinux_provider`, `autofs_provider`, `subdomains_provider`. І ще одне типове, яке щоразу дивує: `enumerate = FALSE`, тобто `getent passwd` без імені доменних людей не показує. Це не поламка, а відмова тягнути через мережу весь каталог заради переліку.

**Мінімальний робочий домен — [LDAP](book:unix-linux/ldap-directory) для записів, [Kerberos](book:communications/kerberos-authentication) для паролів:**

```
[sssd]
domains = firma.ua

[domain/firma.ua]
id_provider = ldap
auth_provider = krb5
access_provider = simple
simple_allow_groups = staff, admins
ldap_uri = ldaps://ldap.firma.ua
ldap_search_base = dc=firma,dc=ua
krb5_server = kdc.firma.ua
krb5_realm = FIRMA.UA
cache_credentials = true
```

## Терміни життя кеша

| Ключ | Секція | Типово | Що означає |
|---|---|---|---|
| `entry_cache_timeout` | `[domain/…]` | `5400` с | скільки секунд запис вважається чинним |
| `entry_cache_user_timeout`, `…_group_…`, `…_netgroup_…`, `…_sudo_…`, `…_ssh_host_…`, `…_resolver_…` | `[domain/…]` | = `entry_cache_timeout` | те саме, але для одного виду записів |
| `entry_negative_timeout` | `[nss]` | `15` с | скільки пам'ятати відповідь «такого немає» |
| `entry_cache_nowait_percentage` | `[nss]` | `0` | з якого відсотка терміну оновлювати запис у фоні, віддаючи поки що старе |
| `refresh_expired_interval` | `[domain/…]` | — | як часто бекенд сам оновлює те, що вже протухло; `0` вимикає |
| `memcache_timeout` | `[nss]` | `300` с | термін життя запису у відображеній пам'яті |
| `memcache_size_passwd`, `…_group`, `…_initgroups` | `[nss]` | розмір у МБ | `0` вимикає цей рівень зовсім |
| `cache_credentials` | `[domain/…]` | `FALSE` | чи зберігати хеш пароля для входу без мережі |
| `offline_credentials_expiration` | **`[pam]`** | `0` (без межі) | скільки днів після останнього входу з мережею ще пускати без неї |
| `account_cache_expiration` | `[domain/…]` | `0` (без межі) | через скільки днів після останнього входу прибрати запис при чистці кеша |

Два останні ключі — найчастіше джерело здивування, і причин дві. По-перше, вони керують тим самим офлайн-входом, але живуть у **різних секціях**. По-друге, їхні значення пов'язані: дозвіл заходити не може пережити сам запис, тому `account_cache_expiration` мусить бути не меншим за `offline_credentials_expiration` — інакше чистка прибере запис раніше, ніж скінчиться дозвіл.

Поряд у `[nss]` стоїть `filter_users` / `filter_groups` — імена, про які респондер не питає домен узагалі; типово туди входить `root`, і саме тому мертвий каталог не заважає адміністраторові зайти.

Арифметика типових значень:

```
entry_cache_timeout       = 5400 с
найбільший вік відповіді  = 5400 с = 1.5 год
середній вік відповіді    ≈ 2700 с ≈ 45 хв
запитів у мережу на запис ≈ 86400 / 5400 = 16 на добу
```

Тобто зміна в каталозі доїжджає до машини щонайпізніше за півтори години, а кожен запис коштує шістнадцяти мережевих звертань на добу — незалежно від того, скільки тисяч разів його спитали локально.

## Шляхи на диску

| Шлях | Що там | Хто пише | Хто читає |
|---|---|---|---|
| `/etc/sssd/sssd.conf` | конфігурація, режим `0600` | адміністратор | монітор на старті |
| `/etc/sssd/conf.d/*.conf` | фрагменти, ті самі права | адміністратор | монітор на старті |
| `/var/lib/sss/db/config.ldb` | розібрана конфігурація | монітор | усі частини демона |
| `/var/lib/sss/db/cache_<домен>.ldb` | записи каталогу, хеші паролів | бекенд домену | респондери |
| `/var/lib/sss/db/timestamps_<домен>.ldb` | лише позначки часу тих самих записів | бекенд | бекенд |
| `/var/lib/sss/mc/` | `passwd`, `group`, `initgroups` — найшвидший рівень | nss-респондер | **кожен процес** через [відображення в пам'ять](book:unix-linux/mmap-model) |
| `/var/lib/sss/pipes/` | сокети `nss`, `pam`, `sudo`, `ssh`, `autofs`, `pac` | демон | клієнтські модулі |
| `/var/lib/sss/pipes/private/` | внутрішні канали, режим `0700` | демон | лише сам демон |
| `/var/lib/sss/pubconf/` | `kdcinfo.<REALM>` — адреси KDC для бібліотеки Kerberos | бекенд | клієнт Kerberos |
| `/var/lib/sss/keytabs/`, `/var/lib/sss/secrets/` | ключі й секрети машини | демон | демон |
| `/var/lib/sss/backup/` | копія перевизначень перед стиранням кеша | `sssctl` | `sssctl` |
| `/var/log/sssd/` | журнали служб і доменів | демон | адміністратор |

Різниця в режимах тут змістовна. Каталог `db/` закритий, бо в ньому хеші паролів; `mc/` навпаки — читають усі процеси, бо туди кладуть лише те, що й так лежало б у відкритому `/etc/passwd`. Сокет `pipes/pam` доступний тим, хто входить, а коло клієнтів, яким дозволено привілейовані дії, задає `pam_trusted_users` у `[pam]`; [стек PAM](book:unix-linux/pam-stack) дістається сюди через модуль `pam_sss`.

Самі шляхи задаються при складанні (`--with-db-path`, `--with-mcache-path`, `--with-pipe-path`, `--with-log-path`), тож у дистрибутивах збігаються.

## `sssctl`: чим питають демон

| Група | Команди |
|---|---|
| стан | `domain-list`, `domain-status`, `user-checks`, `access-report` |
| що в кеші | `user-show`, `group-show`, `netgroup-show` |
| дані на машині | `cache-expire`, `cache-remove`, `cache-index`, `client-data-backup`, `client-data-restore` |
| журнали | `debug-level`, `logs-fetch`, `logs-remove`, `analyze` |
| конфігурація | `config-check` |
| сертифікати, GPO, ключі | `cert-show`, `cert-map`, `cert-eval-rule`, `gpo-list`, `gpo-show`, `gpo-remove`, `gpo-purge`, `passkey-register` |

Сигнатури того, що вживають щодня:

```
sssctl domain-list [-v] [-s]
sssctl domain-status ДОМЕН [-o] [-a] [-r] [-s]
        -o онлайн-стан   -a чинний сервер   -r знайдені сервери   -s підняти SSSD
sssctl user-checks КОРИСТУВАЧ [-a auth|acct|setc|chau|open|clos] [-s СЛУЖБА]
        типово: -a acct, -s system-auth
sssctl user-show КОРИСТУВАЧ
sssctl cache-expire -E | -u КОРИСТУВАЧ | -U | -g ГРУПА | -G | -r ПРАВИЛО | -R [-d ДОМЕН]
sssctl config-check [-c ФАЙЛ] [-s ТЕКА-ФРАГМЕНТІВ]
sssctl debug-level [РІВЕНЬ]
sssctl logs-fetch ФАЙЛ
sssctl analyze request list | show НОМЕР
```

`user-checks` варта окремого слова: це єдина команда, що проходить увесь ланцюжок за один раз — питає ім'я через NSS, дістає атрибути через канал InfoPipe і **виконує справжню дію PAM** для вказаної служби, друкуючи її наслідок. Тому вона й відповідає на питання «чому людина не заходить», якого `getent passwd` навіть не ставить.

`cache-expire` власної реалізації не має: вона складає команду `sss_cache` з тими самими аргументами й запускає її. Тобто `sss_cache` — не застарілий двійник, а той самий інструмент рівнем нижче, який `sssctl` зібрав під спільною назвою; ключі в них ті самі. Обидва **не стирають** кеш, а позначають записи недійсними — наступний запит піде в каталог, а збережені перевірки паролів лишаються на місці. Стирає `sssctl cache-remove`, і саме тому перед стиранням він відкладає копію перевизначень у `/var/lib/sss/backup/`.

## Рівні `debug_level` і журнали

| Рівень | Що додається |
|---|---|
| 0 | фатальні збої — демон не піднявся |
| 1 | критичні — щось велике працювати не буде |
| 2 | серйозні — конкретний запит не вдався |
| 3 | дрібні — причини попереднього |
| 4 | прочитані налаштування |
| 5 | дані функцій |
| 6–7 | трасування викликів: робочих і внутрішніх |
| 8 | вміст внутрішніх змінних |
| 9 | найнижчий рівень, дуже багато |

Типове значення — `0x0070`, тобто рівні 0–2. Ставиться воно окремо в кожній секції (`[sssd]`, `[nss]`, `[pam]`, `[domain/…]`), і піднімати варто саме ту частину, яка підозріла: дев'ятка на домені за хвилину дає десятки мегабайтів. На вже запущеному демоні рівень міняють без перезапуску — `sssctl debug-level 9`, а потім назад.

Окремий важіль — `debug_backtrace_enabled` (типово ввімкнений): демон тримає докладні повідомлення в кільцевому буфері й вивалює їх у журнал лише тоді, коли справді сталася помилка. Тому подробиці про поламаний запит є навіть при типовому рівні 2.

Куди пишеться, вирішує ключ запуску `--logger`: `files`, `journald` або `stderr`. Без нього демон бере journald, якщо той доступний, інакше stderr; юніти більшості дистрибутивів ставлять `--logger=files` явно, і тоді в `/var/log/sssd/` з'являється окремий файл на кожну частину: `sssd.log` (монітор), `sssd_nss.log`, `sssd_pam.log`, `sssd_<домен>.log`. Цей поділ і є перше знаряддя розбирання: питання про імена й питання про вхід лежать у різних файлах, а мережеві невдачі — завжди у файлі домену.

**Порядок після кожної правки конфігурації:**

```
sssctl config-check                     # синтаксис, невідомі ключі, права на файл
systemctl restart sssd                  # sssd.conf перечитується лише на старті
sssctl domain-status firma.ua -o        # чи домен онлайн
sssctl user-checks ivan -a acct         # NSS + InfoPipe + справжня дія PAM
```
