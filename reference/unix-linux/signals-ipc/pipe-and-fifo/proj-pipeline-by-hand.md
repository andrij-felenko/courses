# ⚙️ Конвеєр власними руками: `pipe`, `fork`, `dup2`, `exec`

Ось повна програма на C, яка виконує `ls -l | wc -l` без жодної оболонки: сама створює канал, сама розводить дескриптори по трьох процесах і сама повертає код виходу останньої ланки. А потім із неї прибрано рівно один рядок — і вона зависає назавжди, тож механіку кінця даних можна не уявляти, а побачити на власній машині за півхвилини.

## Умова

Програма зветься `mypipe`, а двокрапка окремим словом розділяє ланки:

```
./mypipe ls -l : wc -l
```

Вимоги — рівно ті чотири, що їх забезпечує оболонка на рядку `ls -l | wc -l`:

- обидві ланки працюють **одночасно**, а не по черзі через тимчасовий файл;
- код виходу програми дорівнює коду виходу **останньої** ланки;
- жодного зайвого дескриптора не лишається — інакше конвеєр не завершиться;
- ланки не перероблено: запускаються справжні `/bin/ls` і `/usr/bin/wc`, які про канали нічого не знають.

Мова тут не обирається: `pipe`, `fork`, `dup2`, `execvp` — це системні виклики, і природний спосіб покликати їх один.

## Ідея: усе зводиться до бухгалтерії `close`

Творчої роботи в цій програмі рівно стільки, скільки в перерахунку копій. Порахуймо їх.

**Скільки копій кінців каналу існує в кожну мить і скільки має лишитися.**

```
після pipe() у батька         2 дескриптори — fd[0] і fd[1]
після двох fork()             3 процеси × 2 = 6 копій
dup2 у кожній дитині додає    + 2 = 8 копій
має лишитися                  2 — stdout у ls і stdin у wc
отже close() рівно            8 − 2 = 6 разів
```

Шість викликів `close`, розкиданих по трьох процесах, і **жодного не можна пропустити**: кожен пропущений тримає лічильник відповідного кінця ненульовим, а всі граничні події каналу — кінець даних і `SIGPIPE` — виникають саме з нуля в лічильнику. Уся решта коду — це `fork` і `exec`, які самі по собі не помиляються.

Порядок теж не довільний. У кожній дитині спершу `dup2`, і лише потім `close`: `close` перед `dup2` знищив би саме те, що збиралися копіювати ([перенаправлення як робота з дескрипторами](book:unix-linux/redirection-model) — `dup2(fd, 1)` мовчки закриває старий дескриптор 1 і робить його другим іменем для `fd`). І окремо: батько мусить закрити свої два кінці **до** `waitpid`, а не після. Закрити після — це чекати на дитину, яка чекає на тебе.

## Код

Спершу помічник, який ставить дескриптор на місце стандартного потоку. Він довший, ніж можна було б очікувати, і рівно через один випадок — коли дескриптор уже має потрібний номер:

```c
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

/* Поставити fd на місце стандартного потоку slot і прибрати зайву копію.
   Випадок fd == slot окремий: dup2 тоді НЕ РОБИТЬ НІЧОГО і повертає slot,
   отже й прапорець FD_CLOEXEC лишається таким, як був. Знімаємо його руками,
   інакше exec закриє потік і програма прокинеться без stdout. */
static int move_to(int fd, int slot)
{
    if (fd == slot) {
        int fl = fcntl(fd, F_GETFD);
        return (fl < 0) ? -1 : fcntl(fd, F_SETFD, fl & ~FD_CLOEXEC);
    }
    if (dup2(fd, slot) < 0)     /* у копії під номером slot FD_CLOEXEC завжди знято */
        return -1;
    return close(fd);           /* close №1 і №2 з наших шести */
}
```

Далі — народження однієї ланки. Дитина дістає номер свого кінця каналу й номер чужого, який їй треба просто викинути:

```c
static pid_t spawn(char **argv, int in_fd, int out_fd, int foreign_fd)
{
    pid_t pid = fork();
    if (pid != 0)
        return pid;                              /* батько; −1 розбере той, хто кликав */

    /* Далі тільки дитина. Виходимо через _exit, а не exit: exit злив би буфери
       stdio, успадковані від батька, і той самий текст надрукувався б удруге. */
    close(foreign_fd);                           /* close №3 і №4 */
    if (in_fd  >= 0 && move_to(in_fd,  STDIN_FILENO)  < 0) _exit(126);
    if (out_fd >= 0 && move_to(out_fd, STDOUT_FILENO) < 0) _exit(126);

    execvp(argv[0], argv);
    dprintf(STDERR_FILENO, "mypipe: %s: %s\n", argv[0], strerror(errno));
    _exit(127);   /* коди за угодою оболонок: 126 — не вдалося виконати,
                     127 — не вдалося знайти чи запустити команду взагалі */
}
```

І головна частина, де видно всі шість `close` на своїх місцях:

```c
int main(int argc, char **argv)
{
    int sep = 0;
    for (int i = 1; i < argc; i++)
        if (strcmp(argv[i], ":") == 0) { sep = i; break; }
    if (sep < 2 || sep == argc - 1) {
        dprintf(STDERR_FILENO, "вжиток: %s ланка [арг…] : ланка [арг…]\n", argv[0]);
        return 2;
    }
    argv[sep] = NULL;                            /* два окремі масиви argv в одному */
    char **left = &argv[1], **right = &argv[sep + 1];

    int pfd[2];
    if (pipe2(pfd, O_CLOEXEC) < 0) { perror("pipe2"); return 1; }

    pid_t p1 = spawn(left,  -1, pfd[1], pfd[0]);   /* пише в канал */
    if (p1 < 0) { perror("fork"); return 1; }
    pid_t p2 = spawn(right, pfd[0], -1, pfd[1]);   /* читає з каналу */
    if (p2 < 0) { perror("fork"); return 1; }

    /* Найважливіші два рядки в усій програмі: close №5 і №6.
       Без другого з них лічильник кінців на запис ніколи не дійде до нуля. */
    close(pfd[0]);
    close(pfd[1]);

    int status = 0, last = 0;
    for (int alive = 2; alive > 0; ) {
        pid_t done = waitpid(-1, &status, 0);
        if (done < 0) { if (errno == EINTR) continue; perror("waitpid"); return 1; }
        if (done == p2) last = status;           /* код виходу — від ОСТАННЬОЇ ланки */
        alive--;
    }

    if (WIFEXITED(last))   return WEXITSTATUS(last);
    if (WIFSIGNALED(last)) return 128 + WTERMSIG(last);
    return 1;
}
```

Збираємо й перевіряємо всі чотири вимоги одразу:

```
$ cc -O2 -Wall -o mypipe mypipe.c
$ ./mypipe ls -l : wc -l
     42
$ ./mypipe true : false ; echo $?
1
$ ./mypipe false : true ; echo $?
0
$ ./mypipe yes : head -3 ; echo $?
y
y
y
0
```

Останній рядок вартий погляду: `yes` нескінченний, але помирає від `SIGPIPE`, щойно `head` закриває свій кінець, — а код виходу однаково береться від `head`. Це не наша поблажливість, а точно та сама угода, що й в оболонки ([код виходу як інтерфейс програми](book:unix-linux/exit-status) — одне число, за яким той, хто запустив, вирішує, що робити далі; 128 + номер сигналу означає загибель від сигналу).

Про `pipe2` окремо. POSIX знає лише `pipe`; `pipe2` з прапорцем `O_CLOEXEC` — Linux-специфічний і з'явився в ядрі 2.6.27, у glibc — з версії 2.9. Різниця не косметична: `pipe` плюс `fcntl` двома викликами лишають вікно, у якому інший потік устигає зробити `fork` і винести дескриптор у чужу програму.

## Тепер зламаймо: один забутий `close`

Приберіть із `main` рядок `close(pfd[1])` — той єдиний, що позначений як найважливіший, — і зберіть наново:

```
$ ./mypipe ls -l : wc -l
(нічого; програма висить і не їсть процесора)
```

`ls` давно завершився й закрив усе своє. `wc` прочитав усі рядки й тепер спить у `read`, чекаючи на решту. Решти не буде ніколи — але звідки йому це знати? Кінець даних означає «кінців на запис лишилося нуль», а один такий кінець досі відкритий: у батька, який у передачі даних не бере жодної участи й просто про нього забув.

![Чотири моменти життя конвеєра і лічильник відкритих кінців на запис у кожен із них — у правильній збірці й у зламаній](/reference/unix-linux/signals-ipc/pipe-and-fifo/img/close-accounting.svg)

*Уся різниця між робочим конвеєром і вічним зависанням — один дескриптор у третьому рядку.*

Знайти винуватця можна за півхвилини й без здогадів — з другого термінала, доки перший висить. Спершу дивимося, чим тримається той, хто спить:

```
$ ls -l /proc/$(pgrep -x wc)/fd
lr-x------ … 0 -> pipe:[812733]
lrwx------ … 1 -> /dev/pts/3
lrwx------ … 2 -> /dev/pts/3
```

Далі шукаємо, хто ще у всій системі тримає канал із тим самим номером:

```
$ ls -l /proc/[0-9]*/fd/* 2>/dev/null | grep 'pipe:\[812733\]'
lr-x------ … /proc/4412/fd/0 -> pipe:[812733]     ← wc, читає
l-wx------ … /proc/4410/fd/4 -> pipe:[812733]     ← mypipe, ПИШЕ
```

Права на посиланні читаються прямо: `lr-x` — кінець на читання, `l-wx` — на запис. Отже, процес 4410, який жодного байта в цей канал не збирався писати, тримає кінець на запис, і саме він не дає лічильнику дійти до нуля. Того ж висновку можна дійти з іншого боку: перше число у `/proc/4412/syscall` — номер системного виклику, у якому задача зараз спить (нуль на x86-64 — це `read`) ([/proc: процеси як файли](book:unix-linux/proc-filesystem) — каталог на кожен процес, у якому файли не лежать на диску, а формуються ядром у мить читання). Або просто `strace -p 4412` — і видно виклик, який не повертається ([трасування системних викликів](book:unix-linux/syscall-tracing) — перехоплення межі між програмою і ядром без правки програми).

## Друга версія тієї самої помилки, підступніша

Поверніть `close(pfd[1])` у батька, зате приберіть `close(foreign_fd)` із `spawn` — і замініть `pipe2(pfd, O_CLOEXEC)` на звичайний `pipe(pfd)`. Конвеєр зависне знову, але тепер у виводі буде таке:

```
$ ls -l /proc/$(pgrep -x wc)/fd
lr-x------ … 0 -> pipe:[812740]
l-wx------ … 4 -> pipe:[812740]      ← той самий канал, кінець на запис
```

Той самий канал у того самого процесу, з обох боків. `wc` чекає на кінець даних, який може настати лише тоді, коли `wc` закриє власний дескриптор — а він його не закриє, бо зайнятий чеканням. Процес завис, чекаючи на самого себе.

І ось навіщо в робочій версії стояв `O_CLOEXEC`: цю помилку він знімає безкоштовно, бо зайва копія просто не переживає `exec`. Першу — ту, що в батькові, — не знімає ніяк, бо батько `exec` не робить. Різниця варта того, щоб її запам'ятати: **прапорець рятує від забутих копій у дітях і ніколи — від забутих копій у собі.**

## Складність і пастки

**Довший конвеєр не додає складности, якщо не тримати зайвого.** На `N` ланок треба `N−1` каналів, але одночасно живим має бути лише один: створили канал, народили ланку, закрили обидва кінці, перейшли до наступної. Тримати всі канали відкритими до кінця циклу — це квадратично більше викликів `close` наприкінці, і кожна зайва копія дістає ще одну нагоду залишитися незакритою.

**`waitpid(-1, …)` забирає будь-яку дитину.** У маленькій програмі це зручно, у бібліотеці — джерело важкої помилки: ви заберете чужу дитину й з'їсте її статус у того, хто на неї чекав. Чекайте на конкретні `p1` і `p2` ([завершення, wait і зомбі](book:unix-linux/exit-wait-zombies) — статус дитини живе в ядрі, доки батько його не забере). Цикл із `EINTR` теж не окраса: будь-який сигнал з обробником уриває `waitpid` ([EINTR: перервані виклики й перезапуск](book:unix-linux/eintr-and-restart) — виклик повертає −1 не через помилку, а бо його треба повторити).

**Диспозиція сигналів переїжджає в дитину через `exec`.** Спокуслива «страховка» на початку `main` — `signal(SIGPIPE, SIG_IGN)` — ламає конвеєр так, що причину шукають годинами. При `exec` власні обробники скидаються на типову дію, а от **ігнорування лишається ігноруванням**: запущена ланка прокидається з `SIGPIPE`, вимкненим за неї кимось стороннім. Замість тихої смерті на закритому каналі вона дістає `EPIPE` — і далі як пощастить: та, що помилок запису не перевіряє, крутиться в циклі вічно, а сумлінна друкує чужу діагностику й повертає ненульовий код там, де його ніхто не чекав ([диспозиція сигналу](book:unix-linux/signal-disposition) — три можливі долі сигналу: типова дія, ігнорування, власний обробник; лише ігнорування переживає `exec`). Вимикати `SIGPIPE` має право той, хто сам пише в канал і сам розбирає `EPIPE`, — і аж ніяк не той, хто запускає чужі програми.

**Ваша власна ланка — не те саме, що `ls`.** Якщо всередину конвеєра ви ставите не чужу програму, а свій код, який пише через `printf`, наступна ланка дістане ваші рядки не тоді, коли ви їх надрукували, а великими порціями по кілька кілобайтів: у каналі stdio перемикається з порядкової буферизації на поблокову ([буферизація stdio](book:unix-linux/stdio-buffering) — та сама програма поводиться інакше, коли вивід іде не на термінал). Інтерактивний конвеєр від цього перестає бути інтерактивним, а вивід у `stdout` і `stderr` перестає йти в тому порядку, у якому ви його писали.

**Переносна альтернатива до `fork` + `exec` уже існує.** Ту саму розводку дескрипторів `posix_spawn` приймає списком дій — `posix_spawn_file_actions_adddup2` і `_addclose` — і виконує її сам, без вікна між `fork` і `exec` ([vfork, posix_spawn і clone](book:unix-linux/spawn-alternatives) — чим ще народжують процес і чому це буває дешевше). Бухгалтерія від цього не зникає: ті самі шість дій доводиться перелічити явно, просто тепер їх видно списком.
