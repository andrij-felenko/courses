# 📋 Канал і FIFO: контракт викликів

Точна довідка по чотирьох викликах, які створюють канал, по всіх прапорцях, що на них впливають, і по кожній відповіді, яку ядро дає на `open`, `read` і `write` над трубою. Потрібна тоді, коли питання звучить не «як канал влаштований», а «що саме поверне ось цей виклик ось у цій ситуації і яке буде `errno`».

Одна річ пояснює половину таблиць нижче: у каналу немає розміру, зате є **два лічильники відкритих кінців** і **скінченна ємність**. Усі граничні відповіді — `0` від `read`, `EPIPE` від `write`, `ENXIO` від `open`, `EAGAIN` в обидва боки — це не окремі правила, які треба вивчити напам'ять, а різні способи побачити ззовні ті самі два лічильники й ту саму межу кільця.

---

## Створити безіменний канал

```c
#include <unistd.h>
int pipe(int pipefd[2]);                 /* POSIX.1-2001 */

#define _GNU_SOURCE
#include <fcntl.h>                       /* заради констант O_* */
#include <unistd.h>
int pipe2(int pipefd[2], int flags);     /* Linux 2.6.27, glibc 2.9 */
```

Успіх — `0`, і в `pipefd[0]` лежить кінець на читання, у `pipefd[1]` — кінець на запис. Невдача — `−1`, і масив лишається незайманим.

| Прапорець `pipe2` | Що робить | Відколи |
|---|---|---|
| `O_CLOEXEC` | ставить `FD_CLOEXEC` на обидва дескриптори — вони не переживуть `exec` | 2.6.27 |
| `O_NONBLOCK` | ставить `O_NONBLOCK` на обидва описи відкритого файлу | 2.6.27 |
| `O_DIRECT` | «пакетний» режим: кожен `write` — окремий пакет, кожен `read` віддає рівно один пакет | 3.4 |
| `O_NOTIFICATION_PIPE` | канал стає приймачем сповіщень від ядра, а не звичайною трубою між процесами | 5.8 |

`pipe2` існує не заради зручности, а заради `O_CLOEXEC`: між `pipe()` і `fcntl()`, який ставить прапорець, є щілина, у яку встигає впасти `fork` із сусіднього потоку — і дескриптор поїде в чужу програму ([блокуючий і неблокуючий режим](book:unix-linux/blocking-and-nonblocking) — той самий аргумент детально, разом із рештою викликів, що вміють народжувати дескриптор уже налаштованим).

Пакетний режим варто знати окремо, бо він єдиний змінює саму природу труби. Записи більші за `PIPE_BUF` ріжуться на кілька пакетів; якщо буфер `read` менший за черговий пакет, зайві байти пакета **мовчки викидаються**, тож буфер у `PIPE_BUF` байтів завжди достатній; пакетів нульової довжини не буває. Ядра до 3.4 відмовляють із `EINVAL`, а з 4.5 цей прапорець можна вмикати й вимикати через `fcntl(fd, F_SETFL, …)`.

| `errno` виклику `pipe`/`pipe2` | Причина |
|---|---|
| `EFAULT` | `pipefd` указує не в доступну пам'ять |
| `EINVAL` | (`pipe2`) неприпустиме значення в `flags` — зокрема `O_DIRECT` на ядрі до 3.4 |
| `EMFILE` | вичерпано ліміт дескрипторів процесу ([ліміти ресурсів](book:unix-linux/resource-limits) — `RLIMIT_NOFILE` та решта меж, які система накладає на процес) |
| `ENFILE` | вичерпано загальносистемний ліміт відкритих файлів **або** користувач уперся в жорстку межу пам'яті на канали |
| `ENOPKG` | (`pipe2`) попросили `O_NOTIFICATION_PIPE`, а підтримки в ядрі не зібрано |

## Створити іменований канал

```c
#include <sys/stat.h>
int mkfifo(const char *path, mode_t mode);               /* POSIX.1-2001 */
int mkfifoat(int dirfd, const char *path, mode_t mode);  /* glibc 2.4, POSIX.1-2008 */
```

Права створеного запису — `mode & ~umask`, як у будь-якого новоствореного файлу ([umask і типові права](book:unix-linux/umask-and-defaults) — маска процесу, яка гасить біти в кожному `mode`, тому `0666` часто перетворюється на `0644`). `mkfifoat` відрізняється лише тим, що відносний шлях відлічує від каталогу за `dirfd`, а `AT_FDCWD` повертає поведінку `mkfifo` ([сімейство `*at`](book:unix-linux/at-family-syscalls) — чому відлік від дескриптора каталогу рятує від підміни шляху між перевіркою й дією). Той самий inode створює й `mknod(path, S_IFIFO | mode, 0)`, а з оболонки — команда `mkfifo`.

| `errno` | Причина |
|---|---|
| `EEXIST` | `path` уже існує — навіть якщо це обірване символьне посилання |
| `EACCES` | бракує права пошуку в якомусь каталозі шляху або права запису в останній |
| `ENOENT` | проміжного каталогу немає, або шлях веде в обірване посилання |
| `ENOTDIR` | складник шляху не каталог; для `mkfifoat` — `dirfd` указує не на каталог |
| `EBADF` | (`mkfifoat`) шлях відносний, а `dirfd` — не `AT_FDCWD` і не дійсний дескриптор |
| `ENAMETOOLONG` | шлях довший за `PATH_MAX` або складник довший за `NAME_MAX` |
| `ENOSPC` | на файловій системі немає місця під новий запис чи inode |
| `EDQUOT` | вичерпано квоту користувача на блоки або inode |
| `EROFS` | файлова система змонтована лише на читання |

## Відкрити FIFO

Це єдине місце, де іменований канал поводиться не так, як безіменний, і саме тут програми найчастіше зависають. Таблиця повна — інших випадків немає.

| Прапорці `open` | Пара з того боку є | Пари немає |
|---|---|---|
| `O_RDONLY` | повертає дескриптор одразу | **блокує**, доки хтось не відкриє на запис |
| `O_WRONLY` | повертає дескриптор одразу | **блокує**, доки хтось не відкриє на читання |
| `O_RDONLY \| O_NONBLOCK` | повертає одразу | повертає одразу — читач нікому не шкодить |
| `O_WRONLY \| O_NONBLOCK` | повертає одразу | `−1`, `ENXIO` — приймати байти нікуди |
| `O_RDWR` | повертає одразу | повертає одразу; **у POSIX поведінка не визначена**, це вільність Linux |
| `O_RDWR \| O_NONBLOCK` | повертає одразу | те саме — прапорець тут нічого не міняє |

Несиметрія двох середніх рядків має причину, а не історію: читач без записувача просто нічого не прочитає, а записувач без читача мусив би класти байти, яких гарантовано ніхто не забере.

Решта помилок `open` на FIFO — звичайні файлові: `EACCES` на правах запису в каталозі, `ENOENT`, `ELOOP`, `ENAMETOOLONG`. Прапорець `O_TRUNC` на FIFO не робить нічого: усікати нема чого.

> 🔧 **Навіщо це.** Процес, що застряг в `open` на FIFO, ззовні не відрізнити від того, який просто чекає на дані: сон, нуль процесора. Але прикмета однозначна — потрібного дескриптора **ще не існує**: `ls -l /proc/<pid>/fd` не покаже ані `pipe:[…]`, ані шляху до каналу, бо `open` не повернувся. Якщо дескриптор уже є, а процес спить, зависання не на зустрічі, а на `read` порожньої труби — і шукати треба записувача. Тут же перевіряють порядок відкриття: дві сторони, які для двобічної розмови обидві відкривають спершу свій кінець на читання, чекатимуть одна одної вічно.

## Читання

| Ситуація | `read(fd, buf, n)` |
|---|---|
| у трубі є дані | `k` — скільки є, від 1 до `n`; **часткове читання нормальне** |
| труба порожня, записувачі є, блокуючий режим | чекає, доки хтось напише |
| труба порожня, записувачі є, `O_NONBLOCK` | `−1`, `EAGAIN` |
| записувальних кінців не лишилося | `0` — кінець даних, незалежно від режиму |
| `n == 0` | `0`, нічого не робить |
| читання з кінця на запис (`pipefd[1]`) | `−1`, `EBADF` |

| `errno` читання | Причина |
|---|---|
| `EAGAIN` | порожньо на неблокуючому дескрипторі; на Linux те саме число, що `EWOULDBLOCK` ([errno](book:programming/errno) — окремий на кожен потік номер останньої помилки, дійсний лише одразу після невдалого виклику) |
| `EINTR` | виклик вибито сигналом, не встигнувши прочитати жодного байта ([перервані виклики й перезапуск](book:unix-linux/eintr-and-restart) — коли ядро повторює виклик само, а коли перекладає це на програму) |
| `EBADF` | дескриптор недійсний або відкритий не на читання |
| `EFAULT` | `buf` указує не в доступну пам'ять |

Нуль тут означає рівно одне й ніколи не означає «даних поки що немає»: доки живий бодай один записувальний кінець у будь-якому процесі системи, порожня труба дає або чекання, або `EAGAIN`.

## Запис

Неподільність запису — не побічний ефект, а гарантія з чіткою межею.

| Розмір запиту | Блокуючий режим | `O_NONBLOCK` |
|---|---|---|
| `n ≤ PIPE_BUF` | усі `n` байтів одним шматком; чекає, доки звільниться місце **на всі** | усі `n` або `−1`, `EAGAIN` — і тоді не записано нічого |
| `n > PIPE_BUF` | усі `n` байтів, але **не одним шматком**: між шматками може вклинитися чужий запис | від 1 до `n` байтів (частковий запис); `−1`, `EAGAIN`, якщо труба повна геть |

```
PIPE_BUF у Linux            = 4096 Б
мінімум за POSIX            = 512 Б      (_POSIX_PIPE_BUF)
запит у програмі            = fpathconf(fd, _PC_PIPE_BUF)
```

| `errno` запису | Причина |
|---|---|
| `EPIPE` | читальних кінців не лишилося; **перед поверненням ядро шле `SIGPIPE`**, і типова дія цього сигналу вбиває процес ([диспозиція сигналу](book:unix-linux/signal-disposition) — три можливі долі сигналу; щоб побачити `EPIPE`, сигнал треба спершу ігнорувати) |
| `EAGAIN` | немає місця на неблокуючому дескрипторі |
| `EINTR` | сигнал перервав виклик до першого записаного байта; якщо частина вже лягла, повертається не помилка, а кількість записаного |
| `EBADF` | дескриптор недійсний або відкритий не на запис |
| `EFAULT` | `buf` указує не в доступну пам'ять |

## Ємність та інші операції над дескриптором

```c
int size = fcntl(fd, F_GETPIPE_SZ);        /* поточна ємність у байтах */
int got  = fcntl(fd, F_SETPIPE_SZ, 262144);/* нова; повертає ту, що вийшла */
```

Обидві операції з'явилися в Linux 2.6.35. Прохане значення **округлюється вгору**: менше за сторінку піднімається до сторінки, далі ядро бере наступний степінь двійки в сторінках — тому повернуте число зазвичай більше за прохане, і саме його треба вважати правдою.

| Межа | Значення |
|---|---|
| типова ємність | 16 сторінок = 65 536 Б (з Linux 2.6.11) |
| стеля для непривілейованого | `/proc/sys/fs/pipe-max-size`, типово 1 МіБ |
| хто обходить стелю | процес із `CAP_SYS_RESOURCE` ([можливості](book:unix-linux/capabilities) — root, розібраний на окремі повноваження, які видають поштучно) |
| м'яка межа на користувача | `/proc/sys/fs/pipe-user-pages-soft`, типово 16384 сторінки; за нею нові канали народжуються меншими за 16 сторінок (з Linux 4.5) |
| жорстка межа на користувача | `/proc/sys/fs/pipe-user-pages-hard`, типово 0 — без обмеження |

Помилки: `EBUSY` — просите ємність, меншу за обсяг даних, що вже лежать у трубі; `EPERM` — непривілейований процес переліз через `pipe-max-size` ([sysctl](book:unix-linux/sysctl-tunables) — параметри ядра, які читають і крутять на ходу через `/proc/sys`).

Решта того, що дескриптор каналу вміє й не вміє:

| Операція | Відповідь |
|---|---|
| `ioctl(fd, FIONREAD, &n)` | кладе в `n` кількість непрочитаних байтів; працює з будь-якого кінця, у стандартах не описана |
| `lseek(fd, …)` | `−1`, `ESPIPE` — позиції в каналі не існує |
| `fstat(fd, &st)` | `S_ISFIFO(st.st_mode)` істинне, `st_size` завжди `0` |
| `fcntl(fd, F_SETFL, …)` | з усіх прапорців стану на каналі мають сенс лише `O_NONBLOCK`, `O_ASYNC` і (з 4.5) `O_DIRECT` |
| `poll`/`epoll` на кінці читання | `POLLIN` — є дані; `POLLHUP` — записувачів не лишилося ([select, poll, epoll](book:unix-linux/select-poll-epoll) — чекання на готовність багатьох дескрипторів одразу) |
| `poll`/`epoll` на кінці запису | `POLLOUT` — є місце; `POLLERR` — читальний кінець закрито |
| `splice`, `vmsplice`, `tee` | працюють лише тоді, коли хоч один кінець операції — канал; у `tee` каналами мусять бути обидва ([передача без копіювання](book:unix-linux/zero-copy) — чому дані взагалі не мусять заходити в простір користувача) |

## Що з цього переносне

Половина таблиць вище описує саме Linux, і межу варто провести явно, бо код, написаний за цією довідкою, часто переїжджає на BSD або macOS.

| Річ | Стан |
|---|---|
| `pipe`, `mkfifo`, `PIPE_BUF` і неподільність, `SIGPIPE`/`EPIPE`, `ENXIO` на записі без читача | POSIX — є всюди |
| `mkfifoat` | POSIX.1-2008 |
| `pipe2` | Linux 2.6.27; у POSIX аж із редакції 2024 року |
| `open` FIFO з `O_RDWR` | POSIX не визначає; на Linux вдається завжди й ніколи не блокує |
| `F_GETPIPE_SZ`, `F_SETPIPE_SZ`, `/proc/sys/fs/pipe-*` | лише Linux |
| `O_DIRECT` (пакетний режим), `O_NOTIFICATION_PIPE` | лише Linux |
| `splice`, `vmsplice`, `tee` | лише Linux |
| `ioctl FIONREAD` | у стандартах немає, але реалізовано в багатьох системах |

Ємність каналу окремої згадки варта тим, що переносного способу її дізнатися немає взагалі: `PIPE_BUF` — це межа неподільности запису, а не розмір труби, і плутати їх не варто. Переносний код мусить припускати найгірше — 512 байтів неподільности й невідому ємність.

## Мінімальний робочий виклик

Служба, яка приймає команди через іменований канал і не помирає між клієнтами:

```c
#define _GNU_SOURCE
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <signal.h>

void handle(const char *cmd, size_t len);   /* розбір команди — не про цю довідку */

int main(void)
{
    const char *path = "/tmp/commands";

    /* 1. Запис у каталозі. Уже існує — не помилка, а звичайна річ. */
    if (mkfifo(path, 0600) == -1 && errno != EEXIST)
        return 1;

    /* 2. O_RDWR: власний кінець на запис тримає лічильник записувачів
          ненульовим, тож read не поверне 0, коли останній клієнт відійде.
          Ціна — переносности немає, POSIX цього не визначає. */
    int fd = open(path, O_RDWR | O_CLOEXEC);
    if (fd == -1)
        return 1;

    /* 3. Відповіді ми пишемо в інші канали — SIGPIPE не має нас убивати. */
    signal(SIGPIPE, SIG_IGN);

    for (;;) {
        char    buf[4096];             /* PIPE_BUF: клієнтський запис приходить цілим */
        ssize_t n = read(fd, buf, sizeof buf);

        if (n > 0) {
            handle(buf, (size_t)n);
            continue;
        }
        if (n == -1 && errno == EINTR)
            continue;                  /* сигнал — просто повторити */
        break;                         /* справжня помилка; n == 0 тут неможливе */
    }

    close(fd);
    return 0;
}
```

Три рішення в цьому короткому `main` варті того, щоб їх упізнавати. `O_RDWR` прибирає цикл «дочитати до кінця даних — перевідкрити», але водночас робить `read` == 0 недосяжним: виходу з циклу за кінцем даних більше немає, і зупиняти службу доводиться сигналом. Буфер рівно в `PIPE_BUF` означає, що клієнт, який шле команду одним викликом `write` і не довшу за 4096 байтів, гарантовано не перемішається з іншими — на довших командах межі повідомлень доводиться будувати самому. І `SIGPIPE` вимкнено ще до першого запису: сигнал приходить не тоді, коли зручно перевіряти, а посеред довільного `write`.
