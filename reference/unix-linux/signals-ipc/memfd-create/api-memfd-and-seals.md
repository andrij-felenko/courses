# 📋 memfd_create і пломби: сигнатура, прапорці, коди помилок

Тут зібрано точний контракт виклику: числові значення всіх `MFD_*` і `F_SEAL_*`, мінімальна версія ядра для кожного, які саме операції відмовляють і з якою помилкою. Довідка для тієї миті, коли код уже пишеться, а питання стоїть конкретно: чи є цей прапорець у ядрі, на якому програма запуститься, і що прийде замість дескриптора, якщо його немає.

## Сигнатура

```c
#define _GNU_SOURCE
#include <sys/mman.h>

int memfd_create(const char *name, unsigned int flags);
```

Успіх — новий дескриптор, відкритий на читання й запис (`O_RDWR`), зі зміщенням 0 і **нульовим розміром**: перш ніж файлом користуватися, розмір задають окремим `ftruncate`. Помилка — `-1` і `errno`.

Обгортка є в glibc від 2.27 (лютий 2018) і в musl від 1.1.20; сам виклик — від Linux 3.17. Де обгортки немає, виклик роблять напряму, а номер бере `<sys/syscall.h>`:

```c
#include <sys/syscall.h>
#include <unistd.h>

static int memfd_create_compat(const char *name, unsigned int flags)
{
    return (int)syscall(SYS_memfd_create, name, flags);
}
```

`name` не ідентифікує нічого: два виклики з однаковим рядком дають два різні файли. Довжина — щонайбільше 249 байтів без завершального нуля (це `NAME_MAX` мінус префікс `memfd:`); довше — `EINVAL`.

## Прапорці memfd_create

| Прапорець | Значення | Ядро | Що робить |
| --- | --- | --- | --- |
| `MFD_CLOEXEC` | `0x0001` | 3.17 | ставить close-on-exec на новий дескриптор; без нього дескриптор переживає `exec` |
| `MFD_ALLOW_SEALING` | `0x0002` | 3.17 | дозволяє пломби; **без нього** на файлі від народження стоїть `F_SEAL_SEAL` |
| `MFD_HUGETLB` | `0x0004` | 4.14 | сторінки беруться з `hugetlbfs`, а не з внутрішньої tmpfs |
| `MFD_NOEXEC_SEAL` | `0x0008` | 6.3 | режим файлу `0666` плюс одразу `F_SEAL_EXEC`; сам вмикає пломбування |
| `MFD_EXEC` | `0x0010` | 6.3 | режим файлу `0777` — явне «виконання мені потрібне» |

`MFD_HUGETLB` віддає ділянку в **великих сторінках** — заздалегідь зарезервованому пулі сторінок по 2 МіБ або 1 ГіБ, за який процесор тримає окремі записи в буфері трансляції ([великі сторінки](book:unix-linux/huge-pages)). Розмір сторінки кодують у старших бітах того самого `flags` — двійковим логарифмом розміру, зсунутим на `MFD_HUGE_SHIFT`:

```
MFD_HUGE_SHIFT = 26
MFD_HUGE_MASK  = 63

MFD_HUGE_2MB = 21 << 26      (2²¹ байтів = 2 МіБ)
MFD_HUGE_1GB = 30 << 26      (2³⁰ байтів = 1 ГіБ)

розмір назад із прапорців:  1 << ((flags >> MFD_HUGE_SHIFT) & MFD_HUGE_MASK)
```

Заголовок визначає й проміжні значення — від `MFD_HUGE_64KB` до `MFD_HUGE_16GB`, — але який із них справді підтримано, залежить від архітектури й від того, чи зарезервовано пул. Нуль у цих бітах означає «типовий розмір великої сторінки системи».

## Пломби: операції fcntl

```c
#include <fcntl.h>              /* F_ADD_SEALS, F_GET_SEALS, F_SEAL_* */

int rc    = fcntl(fd, F_ADD_SEALS, (int)mask);   /* 0 або -1 */
int seals = fcntl(fd, F_GET_SEALS);              /* маска або -1 */
```

Числові значення операцій — `F_ADD_SEALS = 1033` і `F_GET_SEALS = 1034` (`F_LINUX_SPECIFIC_BASE + 9` і `+ 10`). Три властивості визначають усе інше: набір пломб належить **inode**, тож усі дескриптори на цей файл бачать однакову маску; набір **тільки росте** — знятої пломби не буває; `F_ADD_SEALS` вимагає, щоб **дескриптор був відкритий на запис**, інакше `EPERM` (важливо для того, хто отримав дескриптор лише на читання: пломбувати він не зможе).

| Пломба | Значення | Ядро | Що починає відмовляти | Помилка |
| --- | --- | --- | --- | --- |
| `F_SEAL_SEAL` | `0x0001` | 3.17 | будь-який наступний `F_ADD_SEALS` | `EPERM` |
| `F_SEAL_SHRINK` | `0x0002` | 3.17 | `ftruncate`/`truncate` донизу, `open(O_TRUNC)` | `EPERM` |
| `F_SEAL_GROW` | `0x0004` | 3.17 | `write` за кінець файлу, `ftruncate`/`truncate` вгору, `fallocate`, що подовжує | `EPERM` |
| `F_SEAL_WRITE` | `0x0008` | 3.17 | `write`/`pwrite`, `fallocate(FALLOC_FL_PUNCH_HOLE)`, нове `mmap` із `MAP_SHARED\|PROT_WRITE` | `EPERM` |
| `F_SEAL_FUTURE_WRITE` | `0x0010` | 5.1 | те саме, але **наявні** спільні відображення на запис лишаються чинними | `EPERM` |
| `F_SEAL_EXEC` | `0x0020` | 6.3 | `chmod`, що міняє біти виконання; відображення з `PROT_EXEC` | `EPERM` |

Вибивання дірки, яке забороняє `F_SEAL_WRITE`, — це обнулення середини файлу без зміни його довжини; звільнені сторінки просто перестають існувати ([розріджені файли](book:unix-linux/sparse-files)). Без цієї заборони пломба на розмір нічого не варта: файл лишався б тієї самої довжини, а читач отримував би нулі там, де були дані.

Відображення **лише на читання** під обома записувальними пломбами дозволене — і ядро додатково знімає з ділянки право коли-небудь стати записуваною, тож пізніший `mprotect(…, PROT_WRITE)` над нею відмовляє з `EACCES`.

## Що з чим не поєднується

- `MFD_EXEC` разом із `MFD_NOEXEC_SEAL` — `EINVAL`: це протилежні вимоги.
- `MFD_NOEXEC_SEAL` **сам вмикає** пломбування, тож `MFD_ALLOW_SEALING` до нього дописувати не обов'язково (але й не шкідливо).
- `MFD_HUGETLB` разом із `MFD_ALLOW_SEALING` до Linux 4.16 давало `EINVAL`; від 4.16 поєднання дозволене. Старіші man-сторінки досі згадують заборону в переліку помилок — на 4.16+ це вже неправда.
- Без `MFD_ALLOW_SEALING` файл народжується з `F_SEAL_SEAL`: `F_GET_SEALS` поверне `1`, а будь-який `F_ADD_SEALS` — `EPERM`.
- `F_SEAL_EXEC` на файлі, у якого біти виконання **стоять**, ядро мовчки розширює до `F_SEAL_SHRINK | F_SEAL_GROW | F_SEAL_WRITE | F_SEAL_FUTURE_WRITE`. Логіка — «або пишемо, або виконуємо»: запускний вміст, який ще можна переписати, і є та діра, від якої пломба захищає. Тому на виконуваному `memfd` ця пломба заморожує не лише права, а й дані.

## Коди помилок

`memfd_create`:

| `errno` | Коли |
| --- | --- |
| `EINVAL` | невідомі біти у `flags`; `name` довший за 249 байтів; `MFD_EXEC` разом із `MFD_NOEXEC_SEAL`; хибне кодування розміру великої сторінки |
| `EFAULT` | `name` указує поза адресний простір процесу |
| `EMFILE` | вичерпано ліміт дескрипторів процесу |
| `ENFILE` | вичерпано системний ліміт відкритих файлів |
| `ENOMEM` | бракує пам'яті на новий анонімний файл |
| `EPERM` | `MFD_HUGETLB` без права `CAP_IPC_LOCK` і поза групою `hugetlb_shm_group` |
| `EACCES` | (6.3+) немає ні `MFD_EXEC`, ні `MFD_NOEXEC_SEAL`, а `vm.memfd_noexec` дорівнює 2 |

`CAP_IPC_LOCK` — одна з можливостей, на які розібрано всесилля root: право закріплювати пам'ять так, щоб її не забрали під тиском ([можливості замість root](book:unix-linux/capabilities)).

`F_ADD_SEALS`:

| `errno` | Коли |
| --- | --- |
| `EPERM` | у наборі вже є `F_SEAL_SEAL`, **або** дескриптор відкрито не на запис |
| `EBUSY` | просять `F_SEAL_WRITE`, а на файлі існує спільне відображення на запис або сторінки, закріплені для прямого вводу-виводу чи RDMA |
| `EINVAL` | невідомий біт у масці або файлова система не вміє пломб |

`F_GET_SEALS` має лише один спосіб зазнати невдачі — `EINVAL`, якщо файлова система не підтримує пломбування. Саме тому `fcntl(fd, F_GET_SEALS) < 0` і є точною перевіркою «це взагалі `memfd`?»: на звичайному файлі з диска виклик відмовить.

## Параметр vm.memfd_noexec

Файл `/proc/sys/vm/memfd_noexec` (Linux 6.3+) визначає, що робити з викликами, у яких не вказано ні `MFD_EXEC`, ні `MFD_NOEXEC_SEAL` — тобто з усім кодом, написаним до 6.3 ([параметри ядра, які крутять на ходу](book:unix-linux/sysctl-tunables)):

| Значення | Поведінка |
| --- | --- |
| `0` | виклик спрацьовує так, ніби вказано `MFD_EXEC` — стара поведінка |
| `1` | виклик спрацьовує так, ніби вказано `MFD_NOEXEC_SEAL` |
| `2` | виклик без `MFD_NOEXEC_SEAL` відхиляється з `EACCES` |

Параметр окремий для кожного простору імен PID — ізоляції, у якій процеси бачать власне дерево номерів ([простори імен](book:unix-linux/namespaces)). Дочірній простір дістає значення батька на момент створення, а перевірка **ієрархічна**: ядро йде від поточного простору до кореневого й бере найсуворіше зі знайдених. Тож підняти планку в контейнері можна, а тихцем опустити її зсередини — ні.

Ядра 6.3–6.6 додатково писали в журнал попередження про кожен виклик без цих прапорців; у 6.7 повідомлення прибрали — саме через потоки записів від програм, які нічого поганого не робили.

## Як memfd виглядає ззовні

```
$ ls -l /proc/1873/fd/
lrwx------ 1 u u 64 сер  8 11:04 7 -> '/memfd:frame (deleted)'
```

Формат сталий: `/memfd:<name> (deleted)`. Слово `(deleted)` ядро дописує до будь-якого шляху, за яким уже немає запису в каталозі, — а в `memfd` його не було ніколи.

## Мінімальний робочий виклик

```c
#define _GNU_SOURCE
#include <sys/mman.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <errno.h>

/* Виробник: наповнити й заморозити. Повертає дескриптор або -1. */
int sealed_blob(const void *data, size_t len)
{
    int e, fd = memfd_create("payload", MFD_CLOEXEC | MFD_ALLOW_SEALING);
    if (fd < 0)
        return -1;

    if (ftruncate(fd, (off_t)len) < 0)
        goto fail;

    void *p = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED)
        goto fail;
    memcpy(p, data, len);
    munmap(p, len);                 /* доки воно живе, F_SEAL_WRITE дасть EBUSY */

    if (fcntl(fd, F_ADD_SEALS, F_SEAL_SHRINK | F_SEAL_GROW
                             | F_SEAL_WRITE  | F_SEAL_SEAL) < 0)
        goto fail;

    return fd;

fail:
    e = errno;
    close(fd);
    errno = e;
    return -1;
}

/* Отримувач: вірити лише ядру. 0 — пломби на місці. */
int blob_is_frozen(int fd)
{
    const int need = F_SEAL_SHRINK | F_SEAL_WRITE;
    int seals = fcntl(fd, F_GET_SEALS);

    if (seals < 0)                  /* EINVAL — це не memfd */
        return -1;
    return (seals & need) == need ? 0 : -1;
}
```

Порядок у виробнику неспроста: `munmap` стоїть **перед** `fcntl`, бо доки в чиїхось таблицях сторінок є запис із дозволом на запис, ядро не може пообіцяти, що більше ніхто не пише, — і чесно віддає `EBUSY`. А `F_SEAL_SEAL` в тій самій масці замикає набір: перевірка «чи вже є `F_SEAL_SEAL`» дивиться на **поточні** пломби, тому додати її разом з іншими за один виклик можна.
