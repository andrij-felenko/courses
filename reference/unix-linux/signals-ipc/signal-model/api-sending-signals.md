# 📋 Контракт надсилання сигналу

Надіслати сигнал — це попросити ядро позначити один номер для чужої задачі, і ядро вдовольнить прохання лише тоді, коли адреса розібрана, право підтверджене й номер чинний. Тут зібрано все, що входить у цю перевірку: підписи родини `kill`, значення **знака** в аргументі `pid`, правило права надсилання, повний перелік відмов і поле `si_code`, за яким одержувач бачить, звідки сигнал узявся.

## Підписи

```c
#include <signal.h>

int kill(pid_t pid, int sig);                  /* процес або група процесів  */
int killpg(int pgrp, int sig);                 /* тотожне kill(-pgrp, sig)   */
int raise(int sig);                            /* собі                       */
int sigqueue(pid_t pid, int sig, const union sigval value);  /* зі значенням */
int tgkill(pid_t tgid, pid_t tid, int sig);    /* обгортка з glibc 2.30      */

#include <pthread.h>
int pthread_kill(pthread_t thread, int sig);   /* потоку свого процесу       */

/* Обгорток у glibc немає — лише через syscall(2): */
int syscall(SYS_tkill, pid_t tid, int sig);
int syscall(SYS_pidfd_send_signal, int pidfd, int sig,
            siginfo_t *info, unsigned int flags);

union sigval {              /* вантаж, який несе sigqueue() */
    int   sival_int;
    void *sival_ptr;
};
```

Усі, крім `pthread_kill()`, повертають 0 або −1 і ставлять `errno`. **`pthread_kill()` не чіпає `errno`**: він повертає номер помилки як власне значення, тож звична перевірка `if (pthread_kill(...) < 0)` не спрацює ніколи — треба порівнювати результат із нулем.

| виклик | кого називає адреса | `si_code` в одержувача |
|---|---|---|
| `kill(pid, sig)` | процес, групу процесів або «усіх дозволених» | `SI_USER` |
| `killpg(pgrp, sig)` | групу процесів | `SI_USER` |
| `raise(sig)` | себе | залежить від libc (див. нижче) |
| `sigqueue(pid, sig, val)` | процес | `SI_QUEUE` + `si_value` |
| `pthread_kill(th, sig)` | потік **свого** процесу | `SI_TKILL` |
| `tgkill(tgid, tid, sig)` | потік будь-якого процесу | `SI_TKILL` |
| `pidfd_send_signal(fd, …)` | процес за сталою відсилкою | задає відправник |

`raise(sig)` стандарт означує через тотожність: в однопотоковій програмі це `kill(getpid(), sig)`, у багатопотоковій — `pthread_kill(pthread_self(), sig)`. Тому `si_code` тут залежить від того, яким шляхом його провела бібліотека. Окрема гарантія `raise()` корисніша за номер: якщо сигнал запускає обробник, виклик поверне керування **лише після того, як обробник завершиться**.

`tkill()` — застарілий попередник `tgkill()`: він називає тільки TID, а якщо потік уже помер і його TID дістався новому, сигнал піде не туди. `tgkill()` вимагає ще й TGID (номер групи потоків, тобто PID процесу), і ядро надішле сигнал лише тоді, коли пара збігається ([потоки як задачі](book:unix-linux/threads-as-tasks) — чому в Linux у потоку є власний TID, а PID належить усій групі).

## Номер сигналу

Чинні номери в Linux — від 1 до 64; нуль означає окрему дію й розібраний нижче. Усе інше — `EINVAL`.

Верхня половина (32…64, тобто 33 номери) — реальночасові, і саме з ними пов'язана єдина пастка, що ламає програми ще на складанні. **`SIGRTMIN` у glibc не є сталою часу компіляції.** Реалізація потоків забирає собі два перші реальночасові номери й відповідно зсуває початок родини — на практиці до 34; у заголовках через це стоїть не число, а звертання до функції. Звідси три наслідки:

- писати `SIGRTMIN+n`, ніколи голий номер;
- перевіряти **під час роботи**, що `SIGRTMIN+n` не переріс `SIGRTMAX`;
- `case SIGRTMIN+1:` не збереться взагалі — мітка `case` вимагає сталої, тож розбирати реальночасові номери доводиться ланцюжком `if`.

Окремо варто знати гарантію самонадсилання, бо на неї спираються обробники. Якщо адреса така, що сигнал породжується й для того, хто кличе, і в нього цей сигнал не заблокований, то **до повернення з `kill()`** буде доправлений або він сам, або принаймні один інший незаблокований очікуваний сигнал. Тобто `raise(SIGUSR1)` з установленим обробником не відкладає роботу на потім: обробник відпрацює всередині виклику, а рядок після нього виконається вже після повернення з обробника.

## Аргумент `pid`: знак важить більше за число

Це найчастіше джерело несподіванок, бо один параметр означає чотири різні речі.

| `pid` | адресат |
|---|---|
| `> 0` | процес із цим PID |
| `0` | кожен процес у групі процесів **того, хто кличе** |
| `-1` | кожен процес, якому той, хто кличе, має право надіслати, **крім PID 1** (`init`) |
| `< -1` | кожен процес у групі процесів із PGID `= -pid` |

`killpg(pgrp, sig)` — та сама третя й четверта дія під зрозумілішим іменем: у glibc це бібліотечна обгортка, що кличе `kill(-pgrp, sig)`. `killpg(0, sig)` цілиться у власну групу; якщо в того, хто кличе, групи процесів немає, це `ESRCH`.

Виняток для `init` у рядку `-1` не косметичний: без нього одна помилка в сценарії прибирання, запущеного від адміністратора, зупиняла б систему цілком.

![Чотири обсяги адресації сигналу — сеанс, група процесів, процес і потік — та виклики, що цілять у кожен із них](/reference/unix-linux/signals-ipc/signal-model/img/addressing-scopes.svg)

*Кожен виклик називає свій рівень вкладеності; сеанс не має власного виклику й з'являється лише як межа винятку для `SIGCONT`.*

Групи процесів і сеанси — не абстракція заради симетрії, а те, чим оболонка порядкує завданнями: конвеєр `a | b | c` складає одну групу, і `Ctrl-C` доходить до всіх трьох саме як сигнал групі ([PID, PGID і сеанс](book:unix-linux/pid-and-hierarchy) — три рівні, у які об'єднані процеси, і хто кому їх призначає).

## Право надіслати

Ядро пропустить надсилання, якщо виконано **хоча б одну** умову:

- **реальний або чинний** UID відправника дорівнює **реальному або збереженому set-user-ID** адресата ([користувачі, групи й ідентичність процесу](book:unix-linux/uid-gid-model) — навіщо процесові аж три ідентифікатори власника й чим вони різняться);
- відправник має можливість `CAP_KILL` у просторі імен користувачів адресата ([можливості процесу](book:unix-linux/capabilities) — розібрані на частки права, що колись належали одному лише кореневому користувачеві);
- сигнал — `SIGCONT`, і обидва процеси належать одному сеансові.

Асиметрія в першому рядку навмисна. З боку адресата в правилі стоїть **збережений**, а не чинний ідентифікатор — інакше програма, що на час роботи піднімає чинний UID через біт setuid, випадала б з-під контролю того, хто її запустив, і власник не міг би її навіть зупинити.

Виняток для `SIGCONT` існує заради оболонки: продовжити зупинене завдання треба вміти навіть тоді, коли воно вже змінило власника, — інакше `fg` мовчки перестав би працювати на половині запусків ([керування завданнями й термінальні сигнали](book:unix-linux/job-control) — як оболонка спиняє, продовжує й переводить завдання на передній план).

> 🔧 **Навіщо це.** Коли `kill` від адміністратора служби відповідає `EPERM`, шукати треба не в самому виклику. Або служба працює під іншим користувачем, або її запущено в іншому просторі імен користувачів — і тоді `CAP_KILL`, який ви маєте у своєму, для неї нічого не важить.

## Відмови

| помилка | коли |
|---|---|
| `EINVAL` | номера `sig` не існує; для `pidfd_send_signal()` — ще й неприпустимі `flags` або спроба перетнути простір імен |
| `EPERM` | немає права **на жодного** з адресатів; для `rt_sigqueueinfo()` — ще й підроблений `si_code` |
| `ESRCH` | адресата немає: процес, група чи потік не існують |
| `EAGAIN` | немає місця в черзі реальночасових сигналів |
| `EBADF` | лише для `pidfd_send_signal()`: `pidfd` не є дескриптором |

Три подробиці, які видно тільки при зіставленні сторінок керівництва.

**`EPERM` для групи означає «нікому».** POSIX вимагає віддати `EPERM` лише тоді, коли перевірка права провалилася для **всіх** адресатів; BSD історично віддавав його, коли не пощастило хоча б з одним. Linux тримається POSIX: нуль у відповідь не обіцяє, що сигнал дійшов до кожного члена групи.

**У `kill()` немає `EAGAIN`, а в `sigqueue()` і `tgkill()` є.** Причина не в різних лімітах, а в тому, що ці виклики обіцяють різне. Ліміт `RLIMIT_SIGPENDING` рахує записи черги **на реального користувача** по всіх його процесах ([обмеження ресурсів](book:unix-linux/resource-limits) — набір стель, які ядро тримає на процес і на користувача). Коли запис виділити не вдалося, ядро дивиться на `si_code`: для `kill()` (тобто `SI_USER`) воно мовчки знижує сигнал до голого біта — номер дійде, супровідні поля пропадуть; для всього іншого втратити поля означало б збрехати одержувачеві, тож ядро чесно відмовляє з `EAGAIN`.

**`ESRCH` у `pthread_kill()` не є надійною перевіркою.** Керівництво прямо попереджає: звертання за ідентифікатором потоку, чий час уже минув, — невизначена поведінка, аж до аварії всередині самої бібліотеки. `ESRCH` ви отримаєте лише тоді, коли реалізації пощастило це помітити.

## `si_code`: звідки прийшов сигнал

Одержувач бачить це поле лише тоді, коли призначив обробник із прапорцем `SA_SIGINFO` і бере триаргументну форму ([диспозиція сигналу](book:unix-linux/signal-disposition) — як програма оголошує, що робити з номером, і які прапорці при цьому доступні).

| `si_code` | значення | джерело | що ще заповнено |
|---|---|---|---|
| `SI_USER` | 0 | `kill()` | `si_pid`, `si_uid` відправника |
| `SI_KERNEL` | 0x80 | саме ядро | — |
| `SI_QUEUE` | −1 | `sigqueue()` | `si_pid`, `si_uid`, `si_value` |
| `SI_TIMER` | −2 | доспів таймер | `si_timerid`, `si_overrun` |
| `SI_MESGQ` | −3 | змінився стан черги повідомлень | `si_value` |
| `SI_ASYNCIO` | −4 | завершилося асинхронне введення-виведення | — |
| `SI_SIGIO` | −5 | поставлений у чергу `SIGIO` | — |
| `SI_TKILL` | −6 | `tkill()` або `tgkill()` | `si_pid`, `si_uid` |

Знак тут не випадковий, і на ньому тримається довіра до поля. Виклик `rt_sigqueueinfo()` дозволяє відправникові скласти запис `siginfo_t` самому — але ядро перевіряє `si_code` і **не дає підробити ті коди, які означають «це заповнило ядро»**: для чужого процесу заборонено будь-яке значення `≥ 0` (тобто `SI_USER` і `SI_KERNEL`), а з Linux 2.6.39 — ще й `SI_TKILL`.

Наслідок для одержувача читається просто. Побачили невід'ємний `si_code` або `SI_TKILL` — `si_pid` і `si_uid` проставило ядро, їм можна вірити. Побачили `SI_QUEUE` — запис склав відправник: навіть у звичайному `sigqueue()` поля `si_pid` і `si_uid` заповнює бібліотека зі свого боку, викликаючи `getpid()` і `getuid()`, тож той, хто піде в обхід бібліотеки, напише туди що завгодно. Розрізняти джерела за цим полем можна; будувати на ньому право доступу — ні.

## `kill(pid, 0)` — перевірка без надсилання

Якщо `sig` дорівнює 0, сигналу немає, але перевірки існування й права виконуються повністю. Відповідь читається на три боки:

| результат | висновок |
|---|---|
| 0 | процес існує **і** ви маєте право йому надсилати |
| −1, `ESRCH` | процесу з таким PID немає |
| −1, `EPERM` | процес існує, але він не ваш |

Тобто `EPERM` — теж відповідь: номер зайнятий. Прийом дешевий і не має побічної дії, тому саме ним перевіряють живість за PID-файлом.

Дві межі, за які він не заходить. По-перше, померлий, але не прибраний нащадок (зомбі) досі має номер, і перевірка скаже «існує» — про завершення вона не знає нічого. По-друге, це знімок минулої миті: між відповіддю й наступним справжнім `kill()` процес може померти, а його номер — дістатися новому. Уникнути цієї гонки перевіркою не можна взагалі; її прибирають зміною адреси — цілитися не в число, а в дескриптор ([дескриптор процесу (pidfd)](book:unix-linux/pidfd) — стала відсилка, що після смерті адресата не переходить на іншого).

## Мінімальний виклик без гонки

```c
#include <sys/syscall.h>
#include <unistd.h>
#include <signal.h>
#include <stdio.h>

/* Надіслати SIGTERM саме тому процесові, якого ми мали на увазі.
   pidfd_open — Linux 5.3, pidfd_send_signal — Linux 5.1;
   обгорток у glibc немає ні для того, ні для того. */
int term_exactly(pid_t pid)
{
    int pidfd = syscall(SYS_pidfd_open, pid, 0);
    if (pidfd < 0) {
        perror("pidfd_open");            /* процес уже помер — і це видно тут */
        return -1;
    }

    /* info == NULL → поводиться як kill(): одержувач побачить SI_USER.
       flags == 0 → обсяг береться з самого pidfd (процес, не потік).      */
    int rc = syscall(SYS_pidfd_send_signal, pidfd, SIGTERM, NULL, 0);
    if (rc < 0)
        perror("pidfd_send_signal");     /* ESRCH тут означає саме смерть   */

    close(pidfd);
    return rc;
}
```

Ключове в цьому коді — не економія рядків, а те, що між двома викликами PID уже нічого не важить. Дескриптор, відкритий на живий процес, після його смерті не «перевзувається» на новий процес із тим самим номером, а віддає `ESRCH`. З Linux 6.9 обсяг можна ще й уточнити прапорцями: `PIDFD_SIGNAL_THREAD` цілить у той самий потік, на який відкрито дескриптор, `PIDFD_SIGNAL_THREAD_GROUP` — у всю групу потоків, `PIDFD_SIGNAL_PROCESS_GROUP` — у групу процесів.
