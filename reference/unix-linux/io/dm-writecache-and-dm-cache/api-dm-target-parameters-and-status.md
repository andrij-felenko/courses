# 📋 Параметри таблиць та статусний інтерфейс dm-cache і dm-writecache

Ця довідка містить вичерпний структурний опис параметрів конструювання таблиць Device Mapper для цілей `dm-cache` та `dm-writecache`, детальний опис прапорів повернення, системних параметрів sysfs, а також декодування полів виводу команд `dmsetup status` та `dmsetup message`. Вона призначена для системних адміністраторів, розробників низькорівневого ПЗ та спеціалістів з автоматизації, яким необхідно конфігурувати кешувальні таргети вручну без LVM або будувати парсери телеметрії для систем моніторингу.

---

## 1. Специфікація таблиці конструювання `dm-cache`

Створення таргету `dm-cache` здійснюється шляхом передачі в ядро структурованого рядка конструювання через системний виклик або утиліти Device Mapper. Цей рядок передає позиційні аргументи драйверу ядра для визначення геометрії пристроїв, розміру блоку та підключення модулів політик:

Синтаксис рядка таблиці має такий вигляд:

```
start length cache metadata_dev cache_dev origin_dev block_size #feature_args [features] policy #policy_args [policy_args]
```

### 1.1 Поле за полем: параметри конструювання

Кожен параметр таблиці конструювання відіграє чітку роль у налаштуванні В/В конвеєра:

- **`start` (позиція 1):** Початковий логічний сектор віртуального блокового пристрою. У переважній більшості випадків дорівнює `0`.
- **`length` (позиція 2):** Загальний розмір логічного пристрою у секторах по 512 байтів. Цей розмір повинен точно відповідати розміру оригінального повільного накопичувача (`origin_dev`).
- **`cache` (позиція 3):** Ключове слово, що вказує ядру на використання драйвера `dm-cache`.
- **`metadata_dev` (позиція 4):** Шлях до накопичувача метаданих. На цьому пристрої розміщується транзакційний суперблок, B-дерево відповідності чанків та лічильники `smq`. Мінімальний розмір цього пристрою становить 2 МіБ, але для великих кешів рекомендовано виділяти від 100 МіБ до 1 ГіБ.
- **`cache_dev` (позиція 5):** Шлях до блокового пристрою даних кешу (наприклад, NVMe SSD). Тут зберігаються безпосередньо копії блоків даних.
- **`origin_dev` (позиція 6):** Шлях до оригінального накопичувача (HDD, RAID-масив), де зберігається повна майстер-копія всіх даних.
- **`block_size` (позиція 7):** Розмір чанка у 512-байтових секторах. Мінімальне значення `64` (32 КіБ), максимальне — `2097152` (1 ГіБ). Значення повинно бути кратним 64.
- **`#feature_args` (позиція 8):** Кількість наступних додаткових прапорців конфігурації.
- **`features` (позиція 9+):** Додаткові прапори (детальніше див. нижче).
- **`policy`:** Назва алгоритму прийняття рішень про просування/витіснення (типово `smq`).
- **`#policy_args`:** Кількість аргументів політики кешування.
- **`policy_args`:** Додаткові налаштування політики у формі пар «ключ-значення».

| Параметр | Позиція | Опис та допустимі значення |
| :--- | :--- | :--- |
| `start` | 1 | Початковий сектор логічного пристрою (зазвичай `0`). |
| `length` | 2 | Розмір пристрою у секторах по 512 байтів (дорівнює розміру `origin_dev`). |
| `cache` | 3 | Ідентифікатор типу таргету Device Mapper (`cache`). |
| `metadata_dev` | 4 | Шлях до блокового пристрою метаданих (наприклад, `/dev/nvme0n1p1`). |
| `cache_dev` | 5 | Шлях до блокового пристрою даних кешу (наприклад, `/dev/nvme0n1p2`). |
| `origin_dev` | 6 | Шлях до оригінального повільного пристрою (наприклад, `/dev/sdb`). |
| `block_size` | 7 | Розмір чанка у секторах по 512 байтів. Діапазон: `64`..`2097152` (від 32 КіБ до 1 ГіБ). |
| `#feature_args` | 8 | Кількість додаткових прапорців конфігурації. |
| `features` | 9.. | Прапорці: `writeback`, `writethrough`, `passthrough`, `no_discard_pass`. |
| `policy` | 10 | Алгоритм кешування: `smq` (стандарт) або `cleaner` (вигрузка). |
| `#policy_args` | 11 | Кількість додаткових аргументів політики кешування. |
| `policy_args` | 12.. | Параметри політики у форматі `ключ значення`. |

### 1.2 Прапорці конфігурації (Features)

Прапорці дозволяють коригувати поведінку таргету на льоту чи під час ініціалізації:

- `writeback`: Умикає режим відкладеного запису. Операції запису підтверджуються одразу після збереження в SSD-кеші.
- `writethrough`: Умикає режим наскрізного запису. Запис здійснюється одночасно в кеш та на origin.
- `passthrough`: Обхід кешування. Усі записи йдуть на origin, а застарілі чанки в кеші вилучаються.
- `no_discard_pass`: Забороняє передавати команди DISCARD (TRIM) з віртуального пристрою на origin-диск. Це корисно для товстих RAID-масивів, де TRIM викликає зайву деградацію продуктивності.

### 1.3 Приклад таблиці `dm-cache`

Для розрахунку конфігурації пристрою розміром 100 ГіБ загальний розмір у 512-байтових секторах становить `100 * 1024 * 1024 * 1024 / 512 = 204800000` секторів, а чанк 256 КіБ відповідає `256 * 1024 / 512 = 512` секторам. Створення пристрою у режимі `writeback` з політикою `smq` виконується наступним чином:

```bash
dmsetup create my_cache --table \
"0 204800000 cache /dev/nvme0n1p1 /dev/nvme0n1p2 /dev/sdb 512 1 writeback smq 0"
```

## 2. Специфікація таблиці конструювання `dm-writecache`

Таргет `dm-writecache` оперує журналом записів на швидкому накопичувачі та має спрощений синтаксис конструктора. Розрізнення типів носіїв задається через параметр `type`: `p` вмикає підтримку Persistent Memory (PMEM DAX) з викликом `memcpy_to_pmem` та `clwb`, а `s` використовує стандартний блоковий шар для SSD.

Формат рядка таблиці:

```
start length writecache type origin_dev cache_dev block_size [#options [option_args]]
```

### 2.1 Детальний опис параметрів `dm-writecache`

- **`type` (позиція 4):** Визначає режим роботи драйвера з апаратним забезпеченням кешу.
  - `p` (Persistent Memory): Драйвер очікує пристрій NVDIMM з підтримкою DAX. Запис виконується через пряме мапування пам'яті (`memcpy_to_pmem` та `clwb`).
  - `s` (SSD/Block device): Стандартний блоковий накопичувач (NVMe/SATA SSD). Запис виконується через звичайний блок-шар ядра.
- **`block_size` (позиція 7):** Розмір блоку в байтах. Повинен відповідати розміру сторінки файлової системи (зазвичай 4096 байтів).

| Параметр | Позиція | Опис та допустимі значення |
| :--- | :--- | :--- |
| `start` | 1 | Початковий сектор логічного пристрою (`0`). |
| `length` | 2 | Розмір пристрою у секторах по 512 байтів (дорівнює розміру `origin_dev`). |
| `writecache` | 3 | Ідентифікатор типу таргету Device Mapper (`writecache`). |
| `type` | 4 | Тип накопичувача: `p` (Persistent Memory DAX) або `s` (SSD/Block). |
| `origin_dev` | 5 | Шлях до повільного пристрою даних (наприклад, `/dev/sdb`). |
| `cache_dev` | 6 | Шлях до швидкого пристрою кешу (наприклад, `/dev/pmem0` або `/dev/nvme0n1p3`). |
| `block_size` | 7 | Розмір блоку в байтах (зазвичай `4096`). |
| `#options` | 8 | Кількість опціональних параметрів конфігурації. |
| `option_args` | 9.. | Пари `ключ значення` для тонкого налаштування скидання. |

### 2.2 Тонке налаштування процесів скидання (Flushing Options)

Таргет `dm-writecache` надає набір опцій для регулювання інтенсивності фонової синхронізації брудних блоків з origin-диском:

1. `high_watermark N`: Відсоток заповнення журналу брудними блоками (0–100), при досягненні якого ядро починає агресивне фонове скидання на origin (за замовчуванням `50`).
2. `low_watermark N`: Відсоток заповнення журналу, при досягненні якого агресивне скидання зупиняється і відновлюється звичайний режим (за замовчуванням `45`).
3. `writeback_jobs N`: Кількість паралельних робочих потоків у черзі ядра, які відправлять блоки на origin (за замовчуванням `16`).
4. `autoflush_blocks N`: Порція накопичених брудних блоків, після досягнення якої ініціюється примусова синхронізація на диск навіть без команд `fsync` (за замовчуванням `64`).
5. `autoflush_busy_delay N`: Затримка в мілісекундах перед скиданням брудних блоків під час активного потоку записів від додатка (за замовчуванням `1000`).

## 3. Декодування полів статусу `dmsetup status`

Інформація про стан кешу експортується ядром через системний виклик Device Mapper та доступна через утиліти `dmsetup status` або файл у sysfs `/sys/block/dm-X/dm/status`.

### 3.1 Повне декодування статусу `dm-cache`

Драйвер ядра `dm-cache` експортує телеметрію у вигляді текстового рядка, де кожне позиційне поле відповідає конкретному лічильнику роботи накопичувача (блокам метаданих, нарізці чанків, влучанням, промахам та брудним блокам):

```
0 204800000 cache 2 1024/32768 512 452100/524288 452100 12400 189000 3200 4500 12800 1024 1 writeback 2 migration_threshold 2048 smq 0
```

Покрокова розшифровка кожного значення в рядку:

- **`0 204800000 cache`:** Початковий сектор, довжина пристрою в секторах та тип таргету.
- **`2`:** Розмір блоку метаданих у 512-байтових секторах (2 = 1 КіБ).
- **`1024/32768`:** Зайнято 1024 з 32768 доступних блоків у пристрої метаданих.
- **`512`:** Розмір чанка кешу в секторах (512 секторів = 256 КіБ).
- **`452100/524288`:** Зайнято 452,100 з 524,288 доступних чанків у пристрої даних SSD.
- **`452100` (read_hits):** Кількість операцій читання, обслужених безпосередньо з SSD-кешу.
- **`12400` (read_misses):** Кількість операцій читання, які вимагали звернення до повільного origin-диска.
- **`189000` (write_hits):** Кількість записів у чанки, які вже були присутні у кеші.
- **`3200` (write_misses):** Кількість записів у нові чанки, що вимагали виділення місця в кеші.
- **`4500` (demotions):** Кількість блоків, витіснених із SSD-кешу назад на HDD.
- **`12800` (promotions):** Кількість блоків, скопійованих з HDD на SSD через високу частоту доступу.
- **`1024` (dirty_blocks):** Поточна кількість брудних блоків у кеші, які ще не були вигружені на origin.
- **`1 writeback`:** Кількість активних прапорців та поточний режим запису.
- **`2 migration_threshold 2048 smq 0`:** Параметри політики `smq` та порівняльні лічильники.

### 3.2 Повне декодування статусу `dm-writecache`

Для таргету `dm-writecache` рядок телеметрії описує стан журнальних блоків, лічильник помилок та обсяг брудних даних, що очікують на синхронізацію з origin:

```
0 204800000 writecache 0 13107200 4200000 0 150200
```

Розшифровка полів:

- **`0 204800000 writecache`:** Стандартний заголовок таргету.
- **`0` (error_code):** Код помилки (0 означає відсутність помилок; від'ємний код показує сбій пристрою або В/В).
- **`13107200` (total_blocks):** Загальна кількість блоків у кеші (13,107,200 блоків по 4 КіБ = 50 ГіБ).
- **`4200000` (free_blocks):** Кількість повністю вільних блоків журналу.
- **`0` (writeback_in_progress):** Кількість блоків, які в цей момент записуються потоками скидання на origin-диск.
- **`150200` (dirty_blocks):** Кількість брудних блоків, що очікують на синхронізацію.

## 4. Команди динамічного управління `dmsetup message`

Підсистема Device Mapper підтримує відправку повідомлень активним таргетам без їхнього зупинення чи перебудови за допомогою команди `dmsetup message <device_name> <sector> <message>`.

### 4.1 Зміна режимів та керування політикою `dm-cache`

- Перемикання режиму кешування на льоту:
  ```bash
  dmsetup message my_cache 0 switch_mode writethrough
  ```
- Перехід у режим очищення `cleaner` (для вигрузки всіх брудних блоків перед вилученням кешу):
  ```bash
  dmsetup message my_cache 0 switch_mode cleaner
  ```
- Налаштування порогу міграції для політики `smq`:
  ```bash
  dmsetup message my_cache 0 migration_threshold 4096
  ```

### 4.2 Ручне керування скиданням у `dm-writecache`

- Примусовий виклики синхронізації всіх брудних сторінок журналу на origin:
  ```bash
  dmsetup message my_wc 0 flush
  ```
- Зміна високої водороздільної межі `high_watermark` під час роботи системи:
  ```bash
  dmsetup message my_wc 0 high_watermark 80
  ```

## 5. Діагностичні події та трасування ftrace

Для глибокого аналізу поведінки `dm-cache` та `dm-writecache` ядро Linux надає набір трасувальних подій (tracepoints) у підсистемі ftrace. Події розташовані в каталозі `/sys/kernel/tracing/events/dm_cache/` та `/sys/kernel/tracing/events/dm_writecache/`.

Основні трасувальні події:

- `dm_cache_req`: Фіксує кожен біо-запит, який надходить до таргету (тип запиту, початковий сектор, довжина, влучання чи промах).
- `dm_cache_promote`: Фіксує момент початку та завершення просування блоку з HDD на SSD.
- `dm_cache_demote`: Фіксує витіснення блоку з SSD на HDD.
- `dm_writecache_flush`: Фіксує пачки скидання брудних блоків журнальним потоком.

Увімкнення трасування подій `dm-cache` виконується командою:

```bash
echo 1 > /sys/kernel/tracing/events/dm_cache/enable
cat /sys/kernel/tracing/trace_pipe
```

Аналіз трасувальних подій дозволяє точно визначити, чи відповідає обраний розмір чанка реальному профілю запитів додатка, та своєчасно виявити аномальні затримки при скиданні брудних блоків.
