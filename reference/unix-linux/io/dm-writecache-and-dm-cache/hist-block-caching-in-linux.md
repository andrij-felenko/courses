# 📜 Від flashcache та bcache до dm-cache й dm-writecache

Ця історична довідка розкриває еволюцію механізмів блокового кешування в ядрі Linux — від ранніх сторонніх модулів Facebook flashcache до канонічних таргетів Device Mapper `dm-cache` та `dm-writecache`. Розуміння цієї еволюції пояснює, чому спільнота ядра відмовилася від ізольованих кешувальних драйверів на користь уніфікованого фреймворку Device Mapper, і чому з появою пристроїв енергонезалежної пам'яті (PMEM) знадобився окремий вузькоспеціалізований таргет запису.

---

## 1. Світанок SSD та виклики гібридного зберігання (2008–2010)

Наприкінці 2000-х років твердотільні накопичувачі (SSD) почали масово виходити на ринок корпоративних серверів. У 2008–2010 роках вартість одного гігабайта SSD-пам'яті у десятки разів перевищувала вартість гігабайта на механічному жорсткому диску (HDD). Дата-центри баз даних та вебсерверів стикнулися з дилемою: розмістити всі дані на SSD було економічно неможливо, а залишатися на HDD означало терпіти пляшкове горло в сотні IOPS на довільних операціях читання й запису.

Природним рішенням стало використання невеликих SSD (ємністю 32–128 ГіБ) як швидкого проміжного буфера (кешу) для масивів HDD ємністю у кілька терабайтів. Однак у ядрі Linux того часу не існувало вбудованого прозорого механізму кешування на рівні блокових пристроїв.

Першу популярну спробу розв'язати цю проблему зробила інженерна команда Facebook під керівництвом Мохана Срінівасана (Mohan Srinivasan). У 2010 році Facebook випустив у відкритий доступ проєкт **flashcache** — модуль ядра Linux, побудований поверх Device Mapper, який дозволяв використовувати SSD як кеш типу writeback або writethrough для пристроїв зберігання даних MySQL.

`flashcache` демонстрував вражаючі результати на реальних навантаженнях Facebook, підвищуючи продуктивність В/В баз даних у 5–10 разів. Проте проєкт мав суттєві архітектурні обмеження:
- Політика кешування була жорстко зафіксована у вигляді N-way set-associative хеш-таблиці. Це призводило до колізій хешів при певних ключах доступу і неефективного витіснення даних при нерівномірних навантаженнях.
- Метадані кешу зберігалися в неоптимізованій формі, що робило відновлення після аварійного вимкнення живлення тривалим і ризикованим.
- Проєкт розвивався як окремий позадерева модуль (out-of-tree module) і постійно ламався при оновленнях внутрішнього API ядра Linux.

Згодом виникла модифікація `enhanceio`, яка намагалася спростити конфігурування `flashcache`, однак фундаментальна проблема відсутності інтеграції з основним деревом ядра залишилася нерозв'язаною.

## 2. Поява bcache та боротьба за вхід у ядро (2010–2013)

У той самий період розробник Кент Оверстріт (Kent Overstreet) розпочав роботу над проєктом **bcache**. На відміну від `flashcache`, `bcache` проєктувався від самого початку як частина офіційного ядра Linux і працював не як таргет Device Mapper, а як окремий шар у блоковому стеку (`block/bcache`).

Ключові архітектурні новації `bcache`:
- **B-дерева для метаданих:** Замість хеш-таблиць `bcache` використовував B+ дерева з оптимізацією під твердотільні накопичувачі. Це дозволяло кешувати блоки довільного розміру, відстежувати суміжні записи та мінімізувати знос накопичувача (write amplification factor).
- **Автоматичне визначення послідовного В/В:** `bcache` виявляв великі послідовні операції вводу-виводу (наприклад, перегляд відео чи копіювання великих файлів) і автоматично направляв їх в обхід SSD безпосередньо на HDD, щоб не вимивати гарячі дрібні блоки баз даних.
- **Підтримка декількох HDD на один SSD:** Можливість прив'язувати один кешувальний пристрій (cache set) до багатьох накопичувачів даних (backing devices).

У ядрі Linux 3.10 (червень 2013 року) `bcache` було офіційно прийнято до основного дерева ядра після кількох років палких дискусій. Проте підсистема мала суттєвий недолік для корпоративних дистрибутивів: `bcache` вимагав власної специфічної розмітки блокових пристроїв (ондиск-формату) під час створення. Неможливо було взяти існуючий логічний том LVM чи диск із даними і прозоро додати до нього SSD-кеш без переформатування та міграції даних.

## 3. Відповідь Red Hat: `dm-cache` та екосистема LVM2 (2013)

Паралельно з розробкою `bcache`, архітектор Device Mapper у компанії Red Hat Джо Торнбер (Joe Thornber) разом із колегами розробляв альтернативне рішення — **dm-cache**. 

Основні мотивації Red Hat полягали у наступному:
1. **Інтеграція з LVM2:** `dm-cache` створювався як стандартний target для Device Mapper. Це означало, що адміністратор міг взяти будь-який існуючий LVM Logical Volume і однією командою `lvcreate --type cache` приєднати до нього SSD як кеш, не перериваючи роботу систем і не форматуючи HDD.
2. **Модульні політики кешування:** `dm-cache` відокремив механізм збереження даних від алгоритму прийняття рішень про просування (promotion) та витіснення (demotion). Інтерфейс політик дозволяв підключати різні модулі: від базового `mq` (Multiqueue) до пізнішого `smq` (Stochastic Multiqueue).
3. **Спільні транзакційні метадані:** `dm-cache` використав бібліотеку метаданих `dm-persistent-data`, розроблену Джо Торнбером для `dm-thin` (thin provisioning). Це забезпечило атомарність оновлень суперблока та надійність транзакцій при аварійних зупинках.

У квітні 2013 року разом із ядром **Linux 3.9** вийшов офіційний реліз `dm-cache`. Щойно підтримку додав LVM2, `dm-cache` став основним промисловим стандартом блокового кешування у дистрибутивах Enterprise Linux (RHEL, CentOS, Debian, Ubuntu Server).

З виходом ядра **Linux 4.2** у 2015 році застаріла політика `mq` була замінена на `smq` (Stochastic Multiqueue). `smq` зменшила споживання оперативної пам'яті приблизно втричі — близько 25 байтів на чанк замість 88 у `mq` — і усунула проблему «залипання» застарілих гарячих блоків.

## 4. Революція Persistent Memory та поява `dm-writecache` (2018)

До 2018 року апаратний ландшафт знову кардинально змінився. На ринку з'явилися енергонезалежна оперативна пам'ять (Persistent Memory / NVDIMM) та надшвидкі NVMe накопичувачі на базі технології Intel Optane (3D XPoint). Затримка доступу до таких носіїв вимірювалася сотнями наносекунд або одиницями мікросекунд — замість десятків мікросекунд у класичних SATA/SAS SSD.

Зіткнувшись із пристроями PMEM, розробники виявили, що `dm-cache` став внутрішнім пляшковим горлом:
- Оверхед від обчислення складних політик `smq`, підтримання ієрархії черг та оновлення метаданих у пам'яті вимагав значних ресурсів CPU.
- Для пристроїв із затримкою у сотні наносекунд самі лише блокування, черги та оновлення метаданих у `dm-cache` коштували більше, ніж власне доступ до носія.
- Багатьом високоінтенсивним навантаженням (наприклад, журналам транзакцій DBMS WAL, ZFS ZIL, Write-Ahead Logs) потрібне було виключно прискорення запису з гарантованим скиданням на HDD, тоді як читання обслуговувалися з RAM самого додатка.

У зв'язку з цим інженер Red Hat Мікулаш Паточка (Mikulas Patocka) у ядрі **Linux 4.18** (серпень 2018 року) представив новий таргет — **dm-writecache**.

Філософія `dm-writecache` полягала в крайньому спрощенні:
- Повна відмова від кешування операцій читання (read caching).
- Пласка журнальна структура — суперблок і масив записів метаданих — замість B-дерева чи хеш-таблиць.
- Пряме використання інструкцій CPU для роботи з пам'яттю (DAX / pmem) через `memcpy_to_pmem` та `clwb` (cache line write back) без залучення традиційних I/O request queues.

## 5. Порівняльний підсумок еволюції

Еволюція блокового кешування в Linux пройшла шлях від вузькоспеціалізованих рішень до гнучкого двокомпонентного стандарту в Device Mapper:

| Ера / Технологія | Роки | Розробник | Ключова архітектурна ідея | Чому змінилася |
| :--- | :--- | :--- | :--- | :--- |
| **Flashcache** | 2010 | Facebook | Простий DM-модуль на хеш-таблицях для MySQL | Неоптимізоване витіснення, позадеревовий статус |
| **Bcache** | 2013 | Kent Overstreet | B+ дерева в шарі `block/`, автоматичний байпас | Вимагає власного ондиск-формату, не інтегрований з LVM |
| **dm-cache** | 2013 | Joe Thornber (Red Hat) | Повнофункціональний target у Device Mapper із виділеними метаданими | Оверхед обчислень політик надто високий для NVDIMM/PMEM |
| **dm-writecache** | 2018 | Mikulas Patocka (Red Hat) | Вузькоспеціалізований журнал запису для PMEM/NVMe без кешу читань | Діючий стандарт для прискорення записів із найнижчою затримкою |

Сучасне ядро Linux надає адміністратору чіткий вибір: використовувати **`dm-cache`** як універсальне рішення для гібридних томів (читання + запис) або **`dm-writecache`** для критичних до затримок запису навантажень на новітніх накопичувачах.
