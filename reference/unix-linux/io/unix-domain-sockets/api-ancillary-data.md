# 📋 Допоміжні дані: контракт

Ця вставка пояснює 📋 допоміжні дані: контракт та дозволяє зрозуміти її детальніше. Керівна смуга повідомлення — не суцільний буфер, а послідовність вирівняних блоків, кожен з яких ядро розбирає окремо; тут зібрано все, чим цей розбір керується: поля структур, макроси обходу, типи блоків, опції сокета, прапорці й помилки. Ціна арифметичної помилки тут — пошкоджена пам'ять або мовчазний витік дескрипторів, тож усе подано формулами, а не «приблизно так».

## Виклики

```c
#include <sys/socket.h>

ssize_t sendmsg(int sockfd, const struct msghdr *msg, int flags);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);
```

Повертають кількість байтів **смуги даних**; допоміжні дані в це число не входять зовсім. Прапорці передають третім аргументом — поле `msg_flags` усередині структури на відправлення ядро ігнорує, а на прийом заповнює саме.

| поле `struct msghdr` | на відправлення | на прийом |
|---|---|---|
| `msg_name`, `msg_namelen` | адреса отримувача для незʼєднаного сокета, інакше `NULL` і `0` | буфер під адресу відправника: довжина на вході — розмір буфера, на виході — справжня |
| `msg_iov`, `msg_iovlen` | шматки, які ядро склеїть в одне повідомлення | буфери, що заповнюються по черзі |
| `msg_control`, `msg_controllen` | буфер керівної смуги; довжина — **сума заповнених блоків**, а не розмір буфера | на вході розмір буфера, на виході — скільки ядро справді записало |
| `msg_flags` | ігнорується | сюди ядро ставить `MSG_CTRUNC`, `MSG_TRUNC`, `MSG_EOR`, `MSG_OOB` |

Рядок про `msg_controllen` на відправлення — найтихіша пастка всього контракту. Лишите там розмір усього буфера, заповнивши не весь, — і якщо в хвості вистачить місця бодай на цілий заголовок, ядро візьме ті нулі за наступний блок, побачить нульову довжину й поверне `EINVAL`.

## Заголовок блока

```c
struct cmsghdr {
    size_t cmsg_len;    /* заголовок + дані, БЕЗ хвостового доповнення
                           (у POSIX тип поля — socklen_t) */
    int    cmsg_level;  /* SOL_SOCKET для всього, що описано нижче */
    int    cmsg_type;   /* SCM_RIGHTS, SCM_CREDENTIALS, … */
    /* далі йде unsigned char cmsg_data[] */
};
```

## Макроси обходу

| макрос | що дає | коли повертає `NULL` |
|---|---|---|
| `CMSG_FIRSTHDR(&msg)` | вказівник на перший блок | `msg_controllen` менший за `sizeof(struct cmsghdr)` |
| `CMSG_NXTHDR(&msg, c)` | вказівник на блок після `c` | у буфері не лишилося місця навіть на цілий заголовок |
| `CMSG_DATA(c)` | `unsigned char *` на початок навантаження | — |
| `CMSG_LEN(n)` | значення для поля `cmsg_len` | — |
| `CMSG_SPACE(n)` | скільки байтів блок займе в буфері | — |
| `CMSG_ALIGN(n)` | довжину, доповнену до вирівнювання | — |

```
CMSG_ALIGN(l) = (l + sizeof(size_t) − 1) & ~(sizeof(size_t) − 1)   ← кратне 8 на x86-64
CMSG_LEN(l)   = CMSG_ALIGN(sizeof(struct cmsghdr)) + l
CMSG_SPACE(l) = CMSG_ALIGN(sizeof(struct cmsghdr)) + CMSG_ALIGN(l)
```

Уся різниця між двома схожими іменами — в останньому доданку: `CMSG_LEN` вирівнює тільки заголовок, `CMSG_SPACE` — ще й навантаження, бо наступний блок мусить початися з вирівняної адреси.

![Байтова розкладка керівного блока: заголовок, навантаження і хвостове доповнення, яке враховує лише CMSG_SPACE](/reference/unix-linux/io/unix-domain-sockets/img/cmsg-layout.svg)

*Хвостове доповнення належить блокові, але не належить його «корисній» довжині — звідси два різні числа для однієї структури.*

Кількість дескрипторів у прийнятому блоці окремим полем не приходить — її рахують із довжини: `n = (c->cmsg_len - CMSG_LEN(0)) / sizeof(int)`.

Про переносність: `CMSG_FIRSTHDR`, `CMSG_NXTHDR` і `CMSG_DATA` описані в POSIX.1-2008, `CMSG_SPACE` і `CMSG_LEN` увійдуть у наступну редакцію стандарту, а `CMSG_ALIGN` — розширення Linux, у переносній програмі його не вживають. І окремо: `CMSG_DATA` не обіцяє вирівнювання під `int`, тому навантаження копіюють через `memcpy`, а не читають розіменуванням вказівника.

## Типи блоків (рівень `SOL_SOCKET`)

| `cmsg_type` | навантаження | що треба ввімкнути отримувачеві | доступність |
|---|---|---|---|
| `SCM_RIGHTS` | масив `int` — дескриптори; не більш ніж `SCM_MAX_FD` = 253 | нічого | завжди |
| `SCM_CREDENTIALS` | `struct ucred` — pid, uid, gid | `SO_PASSCRED` | потрібен `_GNU_SOURCE` для оголошення `struct ucred` |
| `SCM_SECURITY` | рядок — мітка безпеки; буфер беруть від `NAME_MAX` | `SO_PASSSEC` | датаграми з Linux 2.6.18, потоки з 4.2 |
| `SCM_PIDFD` | один `int` — новий дескриптор процесу-відправника | `SO_PASSPIDFD` | з Linux 6.5 (glibc 2.39) |

```c
struct ucred {
    pid_t pid;    /* ідентифікатор процесу-відправника */
    uid_t uid;    /* за замовчуванням — РЕАЛЬНИЙ uid відправника */
    gid_t gid;    /* за замовчуванням — РЕАЛЬНИЙ gid відправника */
};
```

Відправник має право підставити в `struct ucred` власні значення й не має права підставити чужі: чужий pid потребує `CAP_SYS_ADMIN`, чужий uid — `CAP_SETUID`, чужий gid — `CAP_SETGID` ([можливості](book:unix-linux/capabilities) — повноваження `root` розділені на окремі дозволи, кожен з яких процес може мати чи не мати незалежно від інших). Не вказав нічого — ядро заповнить структуру саме.

Мітка з `SCM_SECURITY` — рядок, який видає не відправник, а модуль обовʼязкового контролю доступу; для чогось осмисленого його треба порівнювати з політикою, а не з рядковою константою в програмі ([обовʼязковий контроль доступу](book:unix-linux/mac-selinux-apparmor) — шар поверх звичайних прав, де кожен обʼєкт і кожен процес мають мітку, а дозволене описує окрема політика, яку не змінює власник файлу).

Блоків в одному повідомленні може бути кілька, і різних типів: нічого не заважає надіслати `SCM_RIGHTS` і `SCM_CREDENTIALS` разом. Складають їх підряд, кожен наступний — з адреси, яку дав `CMSG_NXTHDR`, а `msg_controllen` наприкінці дорівнює сумі `CMSG_SPACE` усіх блоків, окрім останнього, плюс `CMSG_LEN` останнього. Порядок, у якому блоки прийдуть отримувачеві, не обіцяний ніде — тому цикл із перевіркою `cmsg_level` і `cmsg_type` обовʼязковий, а «перший блок — це той, на який я чекаю» є припущенням, а не фактом.

## Опції сокета (рівень `SOL_SOCKET`)

| опція | доступ | значення | що робить |
|---|---|---|---|
| `SO_PASSCRED` | `get`/`set` | `int`, 0 або 1 | вмикає прихід `SCM_CREDENTIALS` у **кожному** наступному повідомленні |
| `SO_PEERCRED` | тільки `get` | `struct ucred` | облікові дані співрозмовника, зафіксовані в мить `connect`, `listen` або `socketpair`; лише для зʼєднаних потокових сокетів і пар від `socketpair` |
| `SO_PASSPIDFD` | `get`/`set` | `int`, 0 або 1 | вмикає прихід `SCM_PIDFD` |
| `SO_PEERPIDFD` | тільки `get` | `int` | **новий дескриптор**, що вказує на процес-співрозмовника; закрити його — обовʼязок того, хто спитав |
| `SO_PASSSEC` | `get`/`set` | `int`, 0 або 1 | вмикає прихід `SCM_SECURITY` |
| `SO_PEERSEC` | тільки `get` | буфер під рядок | мітка безпеки співрозмовника |

Дві половини цієї таблиці відповідають на різні питання, і сплутати їх легко. `SO_PEERCRED` дає **знімок**: облікові дані, чинні тоді, коли зʼєднання виникло. Якщо співрозмовник після цього змінив користувача або запустив через `exec` іншу програму, опитування покаже старе — і це радше добре, бо саме на момент зʼєднання ви приймали рішення пустити його. `SO_PASSCRED` дає дані **на кожне повідомлення** окремо, і для датаграмного сервера це єдиний правильний варіант: там один сокет обслуговує багатьох відправників, спільного «співрозмовника» просто немає, а `SO_PEERCRED` для незʼєднаного сокета не працює взагалі.

Одна побічна дія, яка дивує: коли `SO_PASSCRED` вмикають на сокеті, який ще нікуди не приєднався і не має власного імені, ядро саме видає йому унікальне імʼя в абстрактному просторі — інакше відповідати такому сокетові було б нікуди.

Пара з `pidfd` розвʼязує стару гонитву: номер процесу після його завершення повертається в обіг, а дескриптор процесу вказує на конкретний процес і після його смерті стає лише «мертвим», але не чужим ([дескриптор процесу](book:unix-linux/pidfd) — стійке посилання на процес як на обʼєкт ядра, з яким працюють тими самими викликами, що й з файлом).

Ще одна тонкість, про яку легко забути в контейнері: uid і gid ядро перекладає в простір користувачів того, хто читає. Якщо відображення для них немає, приходить не помилка, а переповнене значення з `/proc/sys/kernel/overflowuid` — типово 65534 ([простори імен](book:unix-linux/namespaces) — процес бачить не систему, а свій зріз її, і той самий користувач має різні номери в різних зрізах).

## Прапорці

| прапорець | де | дія |
|---|---|---|
| `MSG_CMSG_CLOEXEC` | аргумент `flags` виклику `recvmsg` | ставить «закрити при `exec`» на прийняті дескриптори **атомарно**; лише для `AF_UNIX`, з Linux 2.6.23 |
| `MSG_CTRUNC` | `msg_flags` на виході | керівну смугу вкоротили: буфера забракло або його не було зовсім |
| `MSG_TRUNC` | `msg_flags` на виході | не влізла смуга даних (для датаграм — хвіст повідомлення відкинуто) |

## Мінімальний виклик

Буфер оголошують не масивом `char`, а `union` з `struct cmsghdr`. Причина суто механічна: перше поле заголовка має тип `size_t` і вимагає вирівнювання під розмір слова (8 байтів на x86-64), а звичайний масив `char` компілятор має право покласти за будь-якою адресою. Запис у невирівняний заголовок на x86 просто повільніший, на суворіших архітектурах — падіння. `union` змушує компілятор вирівняти буфер під найвимогливіше зі своїх полів.

Відправлення одного дескриптора разом з одним байтом даних:

```c
int             fd;                       /* що передаємо */
char            byte = 'x';
struct iovec    iov  = { .iov_base = &byte, .iov_len = 1 };
union {                                   /* union дає буферу правильне вирівнювання */
    char           buf[CMSG_SPACE(sizeof(int))];
    struct cmsghdr align;
} u = { 0 };
struct msghdr   msg  = { 0 };

msg.msg_iov        = &iov;
msg.msg_iovlen     = 1;
msg.msg_control    = u.buf;
msg.msg_controllen = sizeof u.buf;        /* поки що — щоб CMSG_FIRSTHDR побачив місце */

struct cmsghdr *c = CMSG_FIRSTHDR(&msg);
c->cmsg_level = SOL_SOCKET;
c->cmsg_type  = SCM_RIGHTS;
c->cmsg_len   = CMSG_LEN(sizeof(int));
memcpy(CMSG_DATA(c), &fd, sizeof(int));
msg.msg_controllen = c->cmsg_len;         /* ← тепер сума заповненого, не розмір буфера */

if (sendmsg(sock, &msg, 0) < 0)
    perror("sendmsg");
```

Прийом із негайним закриттям при `exec` і перевіркою вкорочення:

```c
char            byte;
struct iovec    iov = { .iov_base = &byte, .iov_len = 1 };
union {
    char           buf[CMSG_SPACE(8 * sizeof(int))];   /* максимум, який ми згодні взяти */
    struct cmsghdr align;
} u;
struct msghdr   msg = { 0 };

msg.msg_iov        = &iov;
msg.msg_iovlen     = 1;
msg.msg_control    = u.buf;
msg.msg_controllen = sizeof u.buf;

if (recvmsg(sock, &msg, MSG_CMSG_CLOEXEC) <= 0)
    return -1;
if (msg.msg_flags & MSG_CTRUNC)
    return -1;                            /* зайві дескриптори ядро вже закрило само */

for (struct cmsghdr *c = CMSG_FIRSTHDR(&msg); c != NULL; c = CMSG_NXTHDR(&msg, c)) {
    if (c->cmsg_level != SOL_SOCKET || c->cmsg_type != SCM_RIGHTS)
        continue;
    int n = (c->cmsg_len - CMSG_LEN(0)) / sizeof(int);
    for (int i = 0; i < n; i++) {
        int got;
        memcpy(&got, CMSG_DATA(c) + i * sizeof(int), sizeof(int));
        /* … got належить нам, і закрити його теж нам */
    }
}
```

## Помилки

| код | виклик | причина |
|---|---|---|
| `EINVAL` | `sendmsg` | у блоці більш ніж `SCM_MAX_FD` = 253 дескриптори (до Linux 2.6.38 — 255), або `cmsg_len` не сходиться з `msg_controllen` |
| `EBADF` | `sendmsg` | у масиві є число, яке не є відкритим дескриптором; не передається жоден |
| `ETOOMANYREFS` | `sendmsg` | дескрипторів «у польоті» більше за `RLIMIT_NOFILE`, і немає `CAP_SYS_RESOURCE` ([обмеження ресурсів](book:unix-linux/resource-limits) — мʼяка й жорстка межа на процес, зокрема на кількість відкритих файлів) |
| `EPERM` | `sendmsg` | у `struct ucred` чужі pid, uid або gid без потрібної можливості |
| `ESRCH` | `sendmsg` | у `struct ucred` pid, якого не існує |
| `ENOMEM` | обидва | ядру немає з чого виділити керівну смугу |

Окремо варто знати, чого в цій таблиці **немає**. Якщо прийнятих дескрипторів стільки, що процес перевищив би `RLIMIT_NOFILE`, помилки не буде: зайві ядро тихо закриє. Так само нічого не станеться, коли ви не виділили буфера під керівну смугу зовсім, — дескриптори просто зникнуть, а ви дізнаєтеся про це лише з `MSG_CTRUNC`, якщо здогадаєтеся подивитись.

## Правила, яких у сигнатурах не видно

- **Потоковий сокет вимагає хоча б одного байта даних.** `sendmsg` без смуги даних не перенесе й керівної смуги — дескриптори не поїдуть нікуди.
- **Список не ділиться між викликами.** Дочитати решту блоків наступним `recvmsg` неможливо, тому буфер готують одразу на весь максимум, який ви згодні прийняти.
- **Читання зупиняється на межі блока.** Один `recvmsg` на потоковому сокеті ніколи не змішає байти з двома різними керівними смугами: ядро урве читання раніше.
- **Перевіряти прихід `SCM_RIGHTS` треба завжди,** щойно ви взагалі виділили буфер під керівну смугу, — навіть коли дескрипторів не чекали. Інакше співрозмовник надішле їх без попиту, а ви їх не закриєте.
