Сучасні високопродуктивні додатки (бази даних, веб-сервери, системи кешування) стикаються з фундаментальним обмеженням: процесор набагато швидший за пристрої зберігання даних і мережу. Коли програма хоче прочитати файл або відправити мережевий пакет, вона змушена чекати. 

Історично Linux пропонував кілька шляхів розв'язання цієї проблеми. Найпростіший — синхронні виклики `read()` та `write()`, які блокують потік виконання до завершення апаратної операції. Щоб не блокувати всю програму, розробники використовували багатопотоковість, створюючи окремий потік для кожного клієнтського з'єднання. Проте тисячі потоків вимагають величезних витрат пам'яті на стеки та постійних перемикань контексту (context switches), під час яких процесор витрачає час вхосту, зберігаючи та відновлюючи регістри замість корисної роботи.

Альтернативою став неблокуючий I/O (non-blocking I/O) у комбінації з `epoll`. Програма каже ядру: «повідом мене, коли файловий дескриптор буде готовий до читання». Але `epoll` добре працює лише з мережевими сокетами; для звичайних локальних файлів на диску він майже завжди повідомляє «готово» (через те, що файл теоретично завжди доступний на локальній файловій системі), а реальне читання все одно блокує процес під час підвантаження даних у кеш сторінок ядра (page cache). 

Інтерфейс POSIX AIO (асинхронний I/O) намагався розв'язати це, але його найпопулярніша реалізація (у бібліотеці glibc) зводилася до створення пулу прихованих потоків у просторі користувача, що не вирішувало проблеми продуктивності, а лише ховало її. Справжній асинхронний I/O в ядрі (Linux AIO, виклики `io_submit`) працював лише з файлами, відкритими в режимі `O_DIRECT` (в обхід кешу сторінок), що робило його непридатним для більшості повсякденних додатків, які покладаються на оптимізації файлової системи.

Отже, виникла гостра необхідність у механізмі, який би підтримував **усі** види вводу-виводу (мережу, файли з кешем сторінок і без кешу), не вимагав би створення нових потоків і до того ж мінімізував накладні витрати на взаємодію між користувацькою програмою та ядром. Відповіддю на цей виклик став **`io_uring`**, розроблений інженером Єнсом Аксоу (Jens Axboe) і доданий до ядра Linux у версії 5.1 (2019 рік).

## Архітектура io_uring: Кільцеві буфери у спільній пам'яті

Фундаментальна ідея `io_uring` полягає в радикальному зменшенні кількості системних викликів на шляху подачі I/O запитів та отримання їхніх результатів. 

Системний виклик (наприклад, `read()` або `epoll_wait()`) — це дорога операція. Вона вимагає збереження стану процесора, перемикання в привілейований режим ядра (ring 0), перевірки прав доступу, виконання самої функції в ядрі та, зрештою, повернення назад у простір користувача (ring 3). Крім того, сучасні захисні механізми (такі як пом'якшення вразливостей Spectre/Meltdown) зробили ці переходи між просторами ще повільнішими.

Щоб уникнути цих перемикань, `io_uring` використовує **спільну пам'ять (shared memory)**, видиму одночасно і програмі користувача, і ядру. У цій спільній пам'яті розміщуються два **кільцеві буфери (ring buffers)**:

1.  **Submission Queue (SQ) — Черга подання:** Сюди програма записує свої I/O-запити (наприклад, «прочитати 4 КБ із файлу X у буфер Y»).
2.  **Completion Queue (CQ) — Черга завершення:** Сюди ядро записує результати виконаних операцій (наприклад, «успішно прочитано 4096 байт» або «виникла помилка -EAGAIN»).

Обидві черги є кільцевими буферами (circular buffers), що працюють за принципом Single Producer / Single Consumer (хоча архітектурно `io_uring` може підтримувати і складніші конфігурації через синхронізацію).
- Для SQ: програма виступає в ролі виробника (Producer) запитів, а ядро є їхнім споживачем (Consumer).
- Для CQ: ядро виступає в ролі виробника результатів, а програма є споживачем.

Оскільки пам'ять буферів спільна, програма може сформувати запит і розмістити його в черзі SQ звичайним записом у пам'ять, взагалі без звернення до ядра. Так само програма зчитує готові результати з черги CQ напряму зі спільної оперативної пам'яті.

### Елементи черг: SQE та CQE

Запити, що розміщуються в Submission Queue, називаються **SQE (Submission Queue Entry)**. Кожен запит SQE має жорстко фіксований розмір (64 байти) і містить усю необхідну ядру інформацію для виконання апаратної чи логічної операції:
- **Опкод (Opcode):** Вказує, що саме треба зробити (наприклад, `IORING_OP_READV`, `IORING_OP_WRITEV`, `IORING_OP_ACCEPT`, `IORING_OP_POLL_ADD`).
- **Файловий дескриптор (fd):** Ідентифікатор відкритого файлу або сокета, над яким виконується дія.
- **Вказівник на буфер та його розмір:** Адреса в просторі користувача, звідки читати дані для запису, або куди записувати прочитані дані.
- **Зміщення (Offset):** Позиція у файлі, з якої починати операцію.
- **User Data (64-бітне поле):** Поле, куди програма може записати будь-яке довільне значення (зазвичай це вказівник на структуру контексту запиту в пам'яті користувача). Ядро ніколи не читає і не інтерпретує це поле; воно просто гарантовано повертає його назад разом із результатом, щоб програма могла зрозуміти, який саме запит щойно завершився.

Результати, які ядро повертає в Completion Queue, називаються **CQE (Completion Queue Entry)**. Вони значно менші за розміром (всього 16 байтів) і містять лише три поля:
- **User Data:** Абсолютно те саме значення, що було передане в ініціалізуючому SQE.
- **Result (res):** Результат операції. Якщо операція успішна, це зазвичай кількість оброблених байтів. У випадку невдачі тут повертається від'ємний код помилки (наприклад, `-EINVAL` або `-EAGAIN`).
- **Прапорці (Flags):** Додаткова метаінформація від ядра щодо цієї завершеної операції.

## Життєвий цикл I/O з io_uring

Взаємодія програми з ядром через `io_uring` зазвичай складається з трьох послідовних етапів.

### 1. Ініціалізація: io_uring_setup()

Щоб почати роботу, програма повинна створити екземпляр `io_uring`. Це виконується за допомогою системного виклику ядра:

```c
int io_uring_setup(u32 entries, struct io_uring_params *p);
```

Програма вказує бажану глибину черг (параметр `entries`, який має бути ступенем двійки, наприклад 1024 або 4096). Ядро виділяє пам'ять у просторі ядра, ініціалізує внутрішні структури і повертає спеціальний файловий дескриптор (ring fd), який представляє цей конкретний екземпляр io_uring. Структура `io_uring_params` заповнюється ядром і повертає програмі набір зміщень (offsets). 

Після цього програма повинна викликати `mmap()` на отриманому файловому дескрипторі, використовуючи зміщення, щоб успішно відобразити ділянки пам'яті черг SQ та CQ у свій адресний простір. (Оскільки ця процедура мапінгу та синхронізації вказівників (head/tail) вимагає суворого дотримання бар'єрів пам'яті та є дуже об'ємною, на практиці розробники майже завжди використовують бібліотеку-обгортку `liburing`, де вся ініціалізація зводиться до єдиного виклику `io_uring_queue_init()`).

### 2. Подання запитів (Submission)

Для початку операції програма заповнює один або кілька SQE у вільних комірках черги Submission Queue і атомарно оновлює її хвостовий вказівник (tail pointer). На цьому етапі запити лише лежать у спільній пам'яті; ядро ще не знає, що з'явилася нова робота.

Щоб повідомити ядро, програма виконує системний виклик `io_uring_enter()`:

```c
int io_uring_enter(unsigned int fd, unsigned int to_submit,
                   unsigned int min_complete, unsigned int flags,
                   sigset_t *sig);
```

Цей один системний виклик виконує одразу дві важливі функції, залежно від переданих параметрів:
- **Submit (Подання):** Повідомляє ядро: «Я додав `to_submit` нових запитів у SQ, будь ласка, почни їх обробляти».
- **Wait (Очікування):** Повідомляє ядро: «Заблокуй мій процес і розбуди мене лише тоді, коли завершиться принаймні `min_complete` запитів».

Якщо програма хоче лише повідомити ядро про нові запити і миттєво продовжити своє виконання (наприклад, щоб обробити іншу логіку), вона передає `min_complete = 0`. Ядро підхоплює SQE з черги і розпочинає їх асинхронне виконання. Якщо ядро не може виконати запит миттєво (без блокування), воно автоматично делегує цю задачу прихованим робочим потокам ядра (`io-wq`), які виконають блокуюче читання з диска, не зупиняючи саму програму.

### 3. Отримання результатів (Completion)

Коли пристрій завершує фізичну операцію або мережевий пакет прибуває, ядро записує результат у CQE і оновлює хвостовий вказівник Completion Queue. Програма у просторі користувача може в будь-який момент перевірити головний вказівник (head) CQ. Якщо в черзі з'явилися нові CQE, програма просто зчитує їх результати зі спільної пам'яті. 

Читання результатів із CQ відбувається суто в просторі користувача — **без жодних системних викликів**. Програма ідентифікує, який саме запит завершився, зчитуючи поле `User Data`, і передає результат (res) у відповідний обробник. Після зчитування програма оновлює вказівник CQ, сигналізуючи ядру, що комірку можна використовувати повторно.

## Розширені оптимізації продуктивності

Навіть у своєму базовому режимі `io_uring` значно ефективніший за `epoll` та POSIX AIO, оскільки він дозволяє об'єднувати подання сотень запитів та очікування їхніх результатів (batching) всього в один системний виклик `io_uring_enter`. Проте справжня екстремальна продуктивність розкривається завдяки розширеним режимам, орієнтованим на High-Performance Computing (HPC) та високонавантажені сервери.

### Режим SQPOLL (Kernel Polling)

Системні виклики все ще потрібні (`io_uring_enter`), щоб розбудити ядро і дати йому знати про нові SQE. Але режим **SQPOLL** (Submission Queue Polling) повністю усуває цю необхідність, створюючи справжній **zero-syscall I/O**.

Якщо під час створення екземпляра `io_uring_setup()` встановити прапорець `IORING_SETUP_SQPOLL`, ядро створить спеціальний виділений потік (kernel thread). Цей потік буде неперервно сканувати (poll) спільну пам'ять Submission Queue на наявність нових SQE. 

У цьому режимі програмі **взагалі не потрібно викликати `io_uring_enter()`** для подання запитів. Вона просто заповнює SQE в пам'яті, і потік ядра миттєво їх підхоплює. Це ідеальне рішення для додатків із надзвичайно високою інтенсивністю I/O, де затримка на виконання системного виклику стає головним вузьким місцем (bottleneck). Аби потік ядра не марнував 100% часу процесора в режимі очікування, якщо запитів довго немає, SQPOLL-потік «засинає» після короткого періоду неактивності. Лише в такому разі програмі доведеться зробити один виклик `io_uring_enter` із прапорцем `IORING_SQ_NEED_WAKEUP`, щоб розбудити його, після чого нульові системні виклики продовжуються.

### Попередньо зареєстровані ресурси (Registered Resources)

Кожного разу, коли ядро виконує операцію I/O, воно виконує певну рутинну роботу: перевіряє права доступу, резолвить файловий дескриптор у внутрішню структуру файлу, блокує пам'ять сторінок буфера користувача (pinning), щоб операційна система не вивантажила їх на диск (у swap) під час DMA-передачі пристроєм, а потім знімає це блокування після завершення. Ці накладні витрати стають дуже помітними, коли сервер обробляє мільйони операцій на секунду. `io_uring` дозволяє зареєструвати ці ресурси в ядрі одноразово наперед:

- **Registered Files:** Програма передає ядру масив своїх файлових дескрипторів. Ядро ідентифікує їх і жорстко прив'язує до екземпляра `io_uring`. У всіх наступних SQE програма вказує вже не звичайний дескриптор, а просто індекс у цьому масиві (разом із прапорцем `IOSQE_FIXED_FILE`), минаючи повторні перевірки та пошук у таблиці дескрипторів процесу.
- **Registered Buffers (Fixed Buffers):** Програма заздалегідь передає ядру масив своїх буферів даних. Ядро блокує (pin) їхні сторінки в оперативній пам'яті лише один раз. Усі наступні операції читання та запису з опкодами `IORING_OP_READ_FIXED` та `IORING_OP_WRITE_FIXED` використовують ці попередньо замаплені буфери. Це усуває величезні накладні витрати на виклик `get_user_pages()` при кожній транзакції.

### Zero-copy мережевий I/O

Починаючи з версій ядра 6.x, в екосистему `io_uring` була додана довгоочікувана підтримка **zero-copy I/O** для мережевих сокетів (наприклад, через опкод `IORING_OP_SEND_ZC` та відповідні recv-варіанти).

Зазвичай під час відправки мережевого пакету дані копіюються з буфера користувача у внутрішній буфер ядра (`sk_buff`), і лише потім мережева карта (NIC) зчитує їх через шину DMA для фізичної відправки. Під час виконання операцій zero-copy мережева карта за допомогою DMA читає дані **безпосередньо з буфера простору користувача**. Це заощаджує цикли процесора на зайвому копіюванні пам'яті та значно підвищує пропускну здатність шини пам'яті, що є критично важливим для мережевих застосунків високого навантаження (відео-стрімінг, високочастотний трейдинг, масивні CDN).

## Приклад: Читання з файлу через liburing

Оскільки налаштування кільцевих буферів вручну через виклики `mmap`, вирівнювання структур та маніпуляції з атомарними вказівниками є надто складним і вразливим до помилок завданням, більшість розробників використовують офіційну бібліотеку-обгортку **`liburing`**, яка надає дуже зручний та безпечний API на мові C.

```c
#include <liburing.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

#define QUEUE_DEPTH 1
#define BLOCK_SIZE 4096

int main() {
    struct io_uring ring;
    int fd;
    char buffer[BLOCK_SIZE];

    // 1. Ініціалізація структур io_uring у ядрі та мапінг пам'яті
    if (io_uring_queue_init(QUEUE_DEPTH, &ring, 0) < 0) {
        perror("io_uring_queue_init failed");
        return 1;
    }

    fd = open("test.txt", O_RDONLY);
    if (fd < 0) {
        perror("Failed to open file");
        return 1;
    }

    // 2. Отримання наступного вільного SQE та підготовка запиту на читання
    struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
    io_uring_prep_read(sqe, fd, buffer, BLOCK_SIZE, 0);
    
    // User data встановлюється для ідентифікації запиту при його завершенні
    io_uring_sqe_set_data(sqe, (void*)1); 

    // 3. Подання запиту ядру (виклик io_uring_enter під капотом)
    io_uring_submit(&ring);

    // 4. Очікування на появу результату (CQE) в черзі завершення
    struct io_uring_cqe *cqe;
    io_uring_wait_cqe(&ring, &cqe);

    if (cqe->res < 0) {
        fprintf(stderr, "Помилка читання: код %d\n", cqe->res);
    } else {
        printf("Успішно прочитано %d байт\n", cqe->res);
    }

    // 5. Позначення отриманого CQE як обробленого (зсув головного вказівника черги)
    io_uring_cqe_seen(&ring, cqe);

    close(fd);
    io_uring_queue_exit(&ring);
    return 0;
}
```

*Примітка: написання коду безпосередньо через системні виклики (raw syscalls) вимагає виклику `syscall(__NR_io_uring_setup, ...)`, виконання щонайменше трьох викликів `mmap()` та ручного керування бар'єрами пам'яті. Через надзвичайну складність розробники завжди покладаються на `liburing`.*

## Висновок

`io_uring` кардинально змінив парадигму асинхронного системного програмування в Linux. Він повністю вирішив фундаментальні архітектурні проблеми попередніх I/O інтерфейсів: він справді універсальний (підтримує як файловий ввід-вивід, так і мережеві сокети), позбавлений прихованих накладних витрат на створення пулу фонових потоків і, найголовніше, дозволяє радикально зменшити кількість системних викликів. Завдяки спільним кільцевим буферам та використанню режиму SQPOLL, додатки можуть здійснювати ввід-вивід із нульовою кількістю контекстних перемикань. Подальша підтримка технологій zero-copy та попередньо замаплених ресурсів зробила `io_uring` стандартом де-факто для створення новітніх високопродуктивних інфраструктурних систем, серверів баз даних та мережевих платформ на базі Linux.
