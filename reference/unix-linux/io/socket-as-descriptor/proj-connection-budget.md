# ⚙️ Бюджет з'єднань наживо

Ця вставка пояснює ⚙️ бюджет з'єднань наживо та дозволяє зрозуміти її детальніше. Скільки пам'яті ядра з'їдає одне TCP-з'єднання і скільки їх узагалі влізе в процес — питання, на які жодна таблиця не відповість наперед: числа залежать від версії ядра, від налаштувань дистрибутива й насамперед від того, чи їздить по з'єднанні трафік. Зате відповідь легко здобути власноруч. Нижче дві невеликі програми: перша відкриває тисячі з'єднань і дивиться, як ростуть лічильники ядра, друга навмисно впирається в стелю дескрипторів і виборсується з неї прийомом, який тримають напоготові всі серйозні сервери.

## Куди дивитися

Витрати на з'єднання бувають двох різних природ, тому й лічильники потрібні різні.

Стала частина — структури стану TCP, запис сокета, місце в геш-таблиці. Вона з'являється разом із сокетом і живе, доки той живий, незалежно від трафіку. Уся ця дрібнота лежить у слабових кешах ядра, а їхній сумарний обсяг видно в рядку `Slab:` файлу `/proc/meminfo` ([слабовий розподільник](book:unix-linux/kernel-memory-slab) — механізм, яким ядро роздає пам'ять під безліч однакових дрібних структур замість того, щоб щоразу ходити по цілу сторінку).

Змінна частина — самі черги. Її облік ведеться окремо, у рядку `TCP:` файлу `/proc/net/sockstat`, поле `mem`, і міряється **сторінками** по 4 КіБ. Це той самий облік, який зіставляється з порогами `net.ipv4.tcp_mem`.

Третій лічильник — самі номери, і його ми ведемо самі, бо знаємо, скільки дескрипторів відкрили. Обидва файли — звичайні текстові рядки, що ядро малює на льоту ([файлова система /proc](book:unix-linux/proc-filesystem) — каталог, у якому ядро подає власний стан у вигляді файлів, читаних будь-яким текстовим інструментом).

## Програма перша: ціна з'єднання

Задум простий. Клієнт і сервер живуть в одному процесі й розмовляють через петлю зворотного зв'язку; порт ядро видає само, аби не сваритися з чужими службами. Спершу піднімаємо м'який ліміт дескрипторів до жорсткого — програма має на це право без жодних привілеїв ([ліміти ресурсів](book:unix-linux/resource-limits) — пара «м'яке/жорстке» на кожен ресурс процесу; м'яке значення процес міняє сам, жорстке — стеля, яку опускати можна, а піднімати лише з правами). Далі — тисячі з'єднань, і заміри кожної тисячі.

```c
/* budget.c — скільки коштує одне з'єднання.  cc -O2 -o budget budget.c */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/resource.h>
#include <sys/socket.h>
#include <netinet/in.h>

#define PAIRS 5000

/* рядок виду "Slab:   123456 kB" */
static long meminfo_kb(const char *key)
{
    char line[256]; long v = -1; size_t n = strlen(key);
    FILE *f = fopen("/proc/meminfo", "r");
    if (!f) return -1;
    while (fgets(line, sizeof line, f))
        if (!strncmp(line, key, n)) { sscanf(line + n, " %ld", &v); break; }
    fclose(f);
    return v;
}

/* рядок виду "TCP: inuse 9 orphan 0 tw 2 alloc 24 mem 5" — mem у сторінках */
static long tcp_mem_pages(void)
{
    char line[256]; long v = -1;
    FILE *f = fopen("/proc/net/sockstat", "r");
    if (!f) return -1;
    while (fgets(line, sizeof line, f)) {
        if (strncmp(line, "TCP: ", 5)) continue;   /* не сплутати з TCPv6 */
        char *p = strstr(line, "mem ");
        if (p) sscanf(p + 4, "%ld", &v);
        break;
    }
    fclose(f);
    return v;
}

int main(void)
{
    struct sockaddr_in a = { .sin_family = AF_INET };
    socklen_t alen = sizeof a;
    struct rlimit rl;
    int srv, *fds;
    long slab0, mem0;

    getrlimit(RLIMIT_NOFILE, &rl);
    rl.rlim_cur = rl.rlim_max;             /* м'який ліміт піднімаємо самі */
    setrlimit(RLIMIT_NOFILE, &rl);

    srv = socket(AF_INET, SOCK_STREAM, 0);
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    a.sin_port = 0;                        /* вільний порт добере ядро */
    bind(srv, (struct sockaddr *)&a, sizeof a);
    listen(srv, 1024);
    getsockname(srv, (struct sockaddr *)&a, &alen);

    fds = malloc(sizeof(int) * PAIRS * 2);
    slab0 = meminfo_kb("Slab:");
    mem0  = tcp_mem_pages();

    for (int i = 0; i < PAIRS; i++) {
        int c = socket(AF_INET, SOCK_STREAM, 0);
        if (c < 0 || connect(c, (struct sockaddr *)&a, sizeof a) < 0) {
            perror("клієнт"); break;
        }
        int s = accept(srv, NULL, NULL);
        if (s < 0) { perror("accept"); break; }
        fds[2 * i] = c;
        fds[2 * i + 1] = s;

        if ((i + 1) % 1000 == 0) {
            long pages = tcp_mem_pages() - mem0;
            printf("%5d пар | Slab +%ld КіБ | черги %ld стор.\n",
                   i + 1, meminfo_kb("Slab:") - slab0, pages);
        }
    }

    char *buf = malloc(65536);
    memset(buf, 'x', 65536);
    for (int i = 0; i < PAIRS; i++)        /* наливаємо й НЕ читаємо */
        send(fds[2 * i], buf, 65536, MSG_DONTWAIT | MSG_NOSIGNAL);

    long pages = tcp_mem_pages() - mem0;
    printf("після наливання | Slab +%ld КіБ | черги %ld стор. (%ld МіБ)\n",
           meminfo_kb("Slab:") - slab0, pages, pages * 4 / 1024);
    return 0;
}
```

Ось що вона друкує на ядрі 6.8 (числа з тихої машини, у вас будуть свої):

```
 1000 пар | Slab +8120 КіБ  | черги 3 стор.
 2000 пар | Slab +16380 КіБ | черги 3 стор.
 3000 пар | Slab +24560 КіБ | черги 4 стор.
 4000 пар | Slab +32700 КіБ | черги 4 стор.
 5000 пар | Slab +40900 КіБ | черги 5 стор.
після наливання | Slab +41100 КіБ | черги 84512 стор. (330 МіБ)
```

Читається це за один погляд. Слаб росте рівно, по вісім із чимось мегабайтів на тисячу пар; через петлю зворотного зв'язку кожна пара — це **два** сокети, тож на один сокет виходить

```
40900 КіБ ÷ 10000 сокетів ≈ 4.09 КіБ
```

— саме той порядок сталої частини, який доводиться платити за факт існування з'єднання.

А тепер головне: доки з'єднання мовчать, поле `mem` тримається біля нуля. П'ять тисяч з'єднань — п'ять сторінок, двадцять кілобайтів на всіх. Ніяких «по 128 КіБ на буфер прийому» не зарезервовано, бо резервувати нема чого: черга порожня. Щойно ми налили по 64 КіБ у кожне — облік підскочив до 330 МіБ, тобто до реально зайнятої пам'яті плюс кілька відсотків службової обгортки.

У тому ж рядку `sockstat` стоять іще три числа, і вони пояснюють, чому лік дескрипторів — оцінка знизу, а не міра. `inuse` — сокети з установленим з'єднанням; `tw` — ті, що вже в `TIME_WAIT`; `orphan` — сокети, у яких дескриптора вже немає, а ядро ще дотискає недовідправлені байти; `alloc` — усі разом. На завантаженому сервері `alloc` буває вдвічі-втричі більший за кількість відкритих дескрипторів, і пам'ять тримає саме він, а не наша таблиця номерів.

Ту саму бухгалтерію можна побачити не сумарно, а по одному з'єднанню: `ss -tm` друкує біля кожного рядок виду `skmem:(r0,rb131072,t0,tb16384,…)` — фактично зайняте проти чинної стелі, окремо для прийому й передачі. Зручно, коли треба знайти не середнє, а того одного клієнта, що набрав повну чергу.

> 🔧 **Навіщо це.** Плануючи ємність, множте на кількість з'єднань не стелю буфера, а **очікуваний обсяг незабраних даних**. Стеля описує найгірший випадок швидкого каналу з великою затримкою; помножена на всіх, вона дає числа в сотні гігабайтів і жодного стосунку до дійсності не має. Дві величини, які варто рахувати окремо, — стала частина (кілька КіБ × усі з'єднання) і черги (середня заповненість × активні з'єднання).

## Програма друга: стеля дескрипторів і резерв

Друга межа — самі номери, і впирається в неї програма особливо неприємно. Щоб побачити це, не кладучи машину, штучно занижуємо м'який ліміт до 64 дескрипторів. Далі: слухаючий сокет, резервний дескриптор на `/dev/null`, `epoll`, кілька клієнтів, які стукають і лишаються в черзі ядра, — і вигрібання всіх решти вільних чисел.

Один рядок у цій програмі варто прочитати уважно: вісім клієнтів кличуть `connect` і їхній виклик успішно повертається, хоча сервер жодного разу не викликав `accept`. Рукостискання завершує ядро само, щойно з'єднання прийшло на слухаючий сокет; готову розмову воно кладе в чергу й чекає, коли програма забере номер. Тому клієнт уже вважає себе під'єднаним і може навіть надіслати запит — а на нашому боці ще нікого немає. Саме через це з'єднання, яких не прийняли, не зникають самі: вони мовчки чекають у ядрі до тайм-ауту з боку клієнта.

```c
/* emfile.c — EMFILE, крутіння вхолосту й резервний дескриптор */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <errno.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/epoll.h>
#include <sys/resource.h>
#include <sys/socket.h>
#include <netinet/in.h>

static int reserve;                        /* число, яке тримаємо про запас */

static void refuse_one(int srv)
{
    close(reserve);                        /* звільнили одне число */
    int c = accept(srv, NULL, NULL);       /* тепер є куди прийняти */
    if (c >= 0) {
        send(c, "503\n", 4, MSG_NOSIGNAL); /* чесна відмова замість мовчанки */
        close(c);
    }
    reserve = open("/dev/null", O_RDONLY); /* і знову беремо запас */
}

int main(void)
{
    struct sockaddr_in a = { .sin_family = AF_INET };
    socklen_t alen = sizeof a;
    struct rlimit rl;
    struct epoll_event ev = { .events = EPOLLIN };
    int srv, ep;

    getrlimit(RLIMIT_NOFILE, &rl);
    rl.rlim_cur = 64;                      /* штучна стеля замість справжньої */
    setrlimit(RLIMIT_NOFILE, &rl);

    srv = socket(AF_INET, SOCK_STREAM, 0);
    a.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    bind(srv, (struct sockaddr *)&a, sizeof a);
    listen(srv, 128);
    getsockname(srv, (struct sockaddr *)&a, &alen);

    ep = epoll_create1(0);                 /* заводимо ДО вичерпання чисел */
    ev.data.fd = srv;
    epoll_ctl(ep, EPOLL_CTL_ADD, srv, &ev);
    reserve = open("/dev/null", O_RDONLY);

    for (int i = 0; i < 8; i++) {          /* клієнти стукають — ми не приймаємо */
        int c = socket(AF_INET, SOCK_STREAM, 0);
        connect(c, (struct sockaddr *)&a, sizeof a);
    }
    while (open("/dev/null", O_RDONLY) >= 0)
        ;                                  /* вигрібаємо решту вільних чисел */

    for (int spin = 1; spin <= 5; spin++) {
        epoll_wait(ep, &ev, 1, -1);        /* повертається МИТТЄВО */
        int c = accept(srv, NULL, NULL);
        printf("прохід %d: epoll — «готовий», accept — %s\n",
               spin, c < 0 ? strerror(errno) : "прийнято");
    }

    puts("--- вмикаємо резерв ---");
    int refused = 0;
    while (epoll_wait(ep, &ev, 1, 0) > 0) {
        refuse_one(srv);
        refused++;
    }
    printf("відмовлено %d з'єднанням; черга порожня, цикл засинає\n", refused);
    return 0;
}
```

Вивід:

```
прохід 1: epoll — «готовий», accept — Too many open files
прохід 2: epoll — «готовий», accept — Too many open files
прохід 3: epoll — «готовий», accept — Too many open files
прохід 4: epoll — «готовий», accept — Too many open files
прохід 5: epoll — «готовий», accept — Too many open files
--- вмикаємо резерв ---
відмовлено 8 з'єднанням; черга порожня, цикл засинає
```

П'ять проходів за мікросекунди — це і є та сама сотня відсотків процесора без жодної корисної роботи. Причина видна просто в коді: `epoll` у рівневому режимі каже правду («у черзі є з'єднання»), `accept` каже правду («номерів немає»), і жоден із них не бреше — просто ніхто нічого не змінює, тож наступний оберт буде дослівно таким самим ([select, poll, epoll](book:unix-linux/select-poll-epoll) — способи спитати ядро, котрий із дескрипторів уже готовий; у рівневому режимі відповідь повторюється, доки причина готовності не зникне).

Резерв ламає це коло найдешевшим із можливих способів. `accept` потребує не пам'яті й не сокета — йому потрібне **вільне число**. Одне-єдине. Ми тримаємо його заздалегідь відкритим на `/dev/null`, а в скруті звільняємо, приймаємо з'єднання, чемно відмовляємо й забираємо число назад. Клієнт дістає відмову за мілісекунди замість того, щоб гнити в черзі до тайм-ауту, а цикл подій повертається до сну. Прийом описаний у документації бібліотеки libev (Марк Леманн) і в тому ж вигляді відтворений у libuv; nginx розв'язує ту саму проблему з іншого боку — вимикає події прийому й переспить задану паузу, тобто теж не крутиться вхолосту, але й черги не розбирає.

## Складність і пастки

Обидві програми лінійні за кількістю з'єднань і не мають жодної хитрої структури даних — уся їхня цінність у лічильниках. Пастки натомість є, і всі практичні.

**Порти скінчаться раніше за дескриптори.** П'ять тисяч з'єднань до однієї пари «адреса-порт» беруть п'ять тисяч ефемерних портів із діапазону `net.ipv4.ip_local_port_range` (типово близько 28 тисяч). Хочете вимірювати далі — розкидайте з'єднання по кількох портах або адресах петлі.

**`Slab:` — величина загальносистемна.** Вона включає все, що робить ядро, тому міряти треба різницю на тихій машині й не дивуватися шумові в сотні кілобайтів.

**EMFILE — не єдина біда.** `ENFILE` означає, що номери скінчилися в усій системі (`fs.file-max`), а не в нашому процесі, і резерв тут теж рятує. А `ECONNABORTED` чи `ECONNRESET` від `accept` — узагалі не вичерпання: клієнт передумав, поки чекав у черзі, і таке з'єднання просто пропускають.

**Резерв погано переживає багатопотоковість.** Між `close(reserve)` і `accept` звільнене число може перехопити сусідній потік — і `accept` знову впаде з `EMFILE`. Робочі варіанти: власний резерв на кожен потік або замок навколо цих трьох рядків.

**Межовий режим `epoll` не рятує, а маскує.** З `EPOLLET` крутіння зникає, бо подія віддається один раз. Але й з'єднання лишається в черзі мовчки, аж доки не постукає наступний клієнт, — а це гірше за помітну проблему.

**Ліміт можна підняти, але не безмежно.** Жорстка стеля процесу — `fs.nr_open`, типово 1 048 576; systemd від версії 240 роздає службам пару «м'яке 1024, жорстке 524288», і саме тому програми, які самі не піднімають м'який ліміт, упираються в тисячу з'єднань на цілком потужній машині.

**Резерв — це сигналізація, а не ліки.** Він рятує цикл подій від крутіння вхолосту й дає клієнтові чесну відмову, але з'єднань більше від нього не стане. Спрацював резерв — це привід підняти ліміт, порахувати, хто тримає дескриптори, або скидати навантаження раніше; лишити його єдиною реакцією означає віддавати помилку кожному новому клієнтові й вважати, що все гаразд.

І остання дрібниця, яку варто мати в пальцях: у справжньому сервері приймають не `accept`, а `accept4(srv, NULL, NULL, SOCK_CLOEXEC | SOCK_NONBLOCK)` — інакше між прийомом і виставленням прапорців лишається щілина, у яку встигає влізти `exec` із чужого потоку ([блокуючий і неблокуючий режим](book:unix-linux/blocking-and-nonblocking) — той самий виклик або чекає готовності, або одразу вертає `EAGAIN`; вибір задається прапорцем на дескрипторі).
