# Багаточергова підсистема блокового вводу-виводу (blk-mq)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
- [Пам'ять та сторінки](book:unix-linux/paging-and-mmu) — концепція сторінок пам'яті (pages).
</preknowlist>

Блоковий рівень вводу-виводу (Block I/O Layer) є прошарком між файловими системами та драйверами блокових пристроїв (дисків, SSD, NVMe). Його головне завдання — приймати запити від вищих рівнів (VFS, файлові системи), оптимізувати їх, зливати, планувати та безпечно передавати драйверам пристроїв. 

Сучасна архітектура блокового рівня в Linux спирається на механізм `blk-mq` (Multi-Queue Block IO), створений для подолання обмежень старих систем, де єдине блокування (spinlock) черги ставало вузьким місцем для швидких NVMe-накопичувачів. 

## Одиниця вводу-виводу: `struct bio`

Увесь життєвий цикл блокової операції починається з формування структури `struct bio`. Коли файлова система або підсистема віртуальної пам'яті бажає прочитати чи записати дані на диск, вона створює `bio`.

Структура `bio` описує логічну операцію I/O і вказує, **що** потрібно зробити (читання/запис), **де** на диску (логічний сектор), і **звідки/куди** в оперативній пам'яті копіювати дані. Оскільки запит може складатися з розкиданих фізичних сторінок пам'яті, `bio` містить масив `struct bio_vec` (векторів), де кожен вектор вказує на конкретну сторінку, зміщення в ній та довжину.

```c
struct bio_vec {
    struct page *bv_page;   // сторінка в пам'яті
    unsigned int bv_len;    // довжина даних (в байтах)
    unsigned int bv_offset; // зміщення всередині сторінки
};

struct bio {
    struct bio        *bi_next;    // для списків bio
    struct block_device *bi_bdev;  // цільовий блоковий пристрій
    unsigned int      bi_opf;      // операція (REQ_OP_READ/WRITE) та прапорці
    unsigned short    bi_vcnt;     // кількість елементів у bi_io_vec
    struct bio_vec    *bi_io_vec;  // масив векторів пам'яті
    sector_t          bi_sector;   // цільовий сектор на диску
    bio_end_io_t      *bi_end_io;  // callback після завершення
    // ...
};
```
### Bio Splitting (Розщеплення)

Драйвери пристроїв і самі контролери (наприклад, NVMe чи SATA) мають апаратні обмеження. Вони не можуть обробити `bio` нескінченної довжини або запит, який містить більше сегментів пам'яті, ніж підтримує апаратний DMA-контролер. 

Якщо VFS генерує гігантський `bio`, блоковий рівень виконує **bio splitting**. Він відрізає від початкового `bio` шматок, який "влазить" у ліміти драйвера, створює новий `bio` для цього шматка, і відправляє його далі, залишаючи решту оригінального `bio` для наступних ітерацій.

## Структура `struct request` та злиття (I/O Merge)

Хоча файлова система говорить термінами `bio`, планувальники та драйвери пристроїв оперують більшими сутностями — `struct request`.
`request` (запит) — це контейнер, який драйвер безпосередньо відправляє апаратній черзі пристрою. Один `request` може містити **декілька** суміжних `bio`.

### Як працює I/O Merge

Ядро намагається мінімізувати кількість звернень до диска (адже один великий запит виконується ефективніше за десять дрібних). Коли новий `bio` надходить до блокового рівня, ядро перевіряє, чи не лежить вже в черзі `request`, чий кінцевий сектор збігається з початковим сектором нашого `bio` (Back Merge), або чий початковий сектор є одразу після нашого (Front Merge).

1. **Back Merge:** Якщо `bio` продовжує існуючий `request`, `bio` просто додається в кінець списку `bi_next` всередині `request`, а розмір `request` збільшується.
2. **Front Merge:** Якщо `bio` передує існуючому `request`, він вставляється на початок.

Якщо злиття неможливе (суміжного `request` немає, або ліміт розміру вже вичерпано), ядро виділяє новий `request` із наперед зарезервованого пулу тегів (tag pool) і асоціює його з цим `bio`.

## Plug та Unplug: Накопичення запитів

Щоб злиття (merge) було ефективним, запити мають зустрітися в черзі. Якщо ядро одразу ж відправлятиме кожен `request` до драйвера, черга буде порожньою, і шанси на злиття дорівнюватимуть нулю.

Тут у гру вступає механізм **Plugging** (затикання).

Коли процес починає надсилати пакет запитів (наприклад, файлова система скидає кеш), він викликає функцію `blk_start_plug`. Вона створює тимчасову локальну для потоку (task-local) чергу `struct blk_plug`.
Всі нові `bio`, згенеровані цим потоком, не йдуть до загальної черги диска, а накопичуються в цій локальній черзі, активно зливаючись один з одним. 

Коли процес закінчує пачку вводу-виводу (або коли він засинає/перемикається), викликається `blk_finish_plug` (Unplug). Всі накопичені й оптимізовані `request` одразу, батчем, "виштовхуються" у черги рівня `blk-mq`. Це радикально зменшує затримки на блокування, бо список переноситься цілком.

## Архітектура blk-mq: Дворівневі черги

Центральним об'єктом диска є `request_queue`. У традиційному блоковому шарі це була одна черга під захистом одного spinlock. Якщо у вас 64-ядерний сервер, і всі ядра намагаються прочитати з NVMe-диска, 63 ядра стоятимуть у черзі за spinlock, щоб додати свій `request`.

**blk-mq (Multi-Queue)** розв'язав це через поділ `request_queue` на два рівні: Software Staging Queues та Hardware Dispatch Queues.

### 1. Software Staging Queues (per-CPU)

Для кожного логічного процесора (CPU) ядро створює окрему програмну чергу (Software Queue). Коли потік на CPU 3 відправляє запит (або коли його `blk_plug` спустошується), `request` потрапляє **лише** в програмну чергу CPU 3.
Оскільки CPU 3 пише лише у власну чергу, потреби в жорстких спільних блокуваннях (global spinlocks) між ядрами немає. Локальне блокування per-CPU забирає наносекунди і не конкурує з іншими ядрами.

Саме в цих програмних чергах працюють **планувальники (I/O schedulers)**. Вони можуть пересортовувати запити (наприклад, `mq-deadline` або `kyber`), зливати їх та визначати пріоритети.

### 2. Hardware Dispatch Queues (per-hctx)

Апаратні черги, або апаратні контексти (`hctx`), відповідають реальним апаратним чергам контролера накопичувача. 
Наприклад, сучасні NVMe SSD можуть мати десятки внутрішніх апаратних черг.

Блоковий шар встановлює мапінг (відображення) між Software Queues та Hardware Queues. 
- Якщо NVMe має 64 апаратні черги, а сервер — 64 ядра, мапінг буде 1:1. Кожен CPU відправлятиме запити у свою незалежну апаратну чергу, повністю усуваючи будь-які затримки на синхронізацію драйвера.
- Якщо апаратних черг менше (наприклад, SATA має лише 1 чергу, або SCSI-контролер має 4 черги на 32-ядерному сервері), ядро групує кілька Software Queues в одну Hardware Queue (відношення N:1). У такому випадку конкуренція існує, але вона ізольована і керована на рівні `hctx`.

## Життєвий цикл запиту: від VFS до Переривання

Зібравши архітектуру до купи, життєвий цикл I/O виглядає так:

1. **Submit**: Прикладний рівень (через VFS) викликає `submit_bio`.
2. **Plug**: `bio` потрапляє в `blk_plug` поточного завдання. Там відбувається спроба злиття з попередніми запитами.
3. **Queue**: При unplug, якщо `bio` не злився, під нього виділяється новий `struct request` (з тегом), і він переміщується в Software Queue поточного CPU.
4. **Schedule**: Якщо увімкнено планувальник (напр. `kyber`), він може відкласти або пересортувати запит. Якщо планувальник `none`, запит проходить наскрізь.
5. **Dispatch**: Запит витягується з Software Queue і переміщується до Hardware Dispatch Queue (`hctx`).
6. **Issue**: Драйвер пристрою (NVMe/SCSI) забирає запит із `hctx` і програмує контролер пристрою через регістри.
7. **Complete**: Накопичувач завершує читання/запис і генерує переривання (або драйвер здійснює polling). Драйвер викликає `blk_mq_complete_request`, який своєю чергою кличе колбек `bi_end_io` початкового `bio`, сповіщаючи VFS про завершення операції. Тег `request` звільняється.

## Висновок

Підсистема `blk-mq` перетворила I/O з повільного монолітного "горлечка", обмеженого одним блокуванням, на високопаралельну архітектуру. Розділення на локальні для процесорів програмні черги (де працюють планувальники та злиття) та апаратні черги відправки дозволило Linux повністю реалізувати шалений потенціал NVMe накопичувачів, зберігаючи при цьому механізми оптимізації та справедливості.
