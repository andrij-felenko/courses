# 📋 Контракт та поверхня системних викликів скидання кешу

Для надійного збереження даних на диск ядро Linux надає низку системних викликів та прапорців відкриття файлів, кожен із яких оголошує власний контракт щодо межі скидання кешу, гарантій метаданих та синхронності виконання. Ця вставка містить вичерпний довідник сигнатур, параметрів, кодів помилок, внутрішньоядерних шляхів виклику та засобів простеження (tracing) для системних викликів `fsync`, `fdatasync` та `sync_file_range`.

## 1. Сигнатури системних викликів та контракти POSIX

Основою керування скиданням кешу є три системні виклики POSIX та Linux:

:::tabs
```c
#include <unistd.h>

int fsync(int fd);
int fdatasync(int fd);

#define _GNU_SOURCE
#include <fcntl.h>

int sync_file_range(int fd, off64_t offset, off64_t nbytes, unsigned int flags);
```
```cpp
#include <unistd.h>
#include <fcntl.h>

extern "C" {
    int fsync(int fd);
    int fdatasync(int fd);
    int sync_file_range(int fd, off64_t offset, off64_t nbytes, unsigned int flags);
}
```
:::

### Контракт fsync(fd)
Згідно зі стандартом POSIX (IEEE Std 1003.1-2017), виклик `fsync` переводить усі брудні сторінки ядра, що належать файлу `fd`, у стан запису на носій і призупиняє виконання викликового потоку до повного завершення В/В. Одночасно `fsync` гарантує, що всі модифіковані метадані файлу (включаючи `st_mtime`, `st_ctime`, `st_size`, власників, права доступу та карти дискових блоків) будуть записані у журнал файлової системи та закріплені дисковою командою `FLUSH`.

### Контракт fdatasync(fd)
Виклик `fdatasync` належить до розширення POSIX Realtime Extension та примусово виштовхує брудні сторінки даних файлу `fd` та лише ті метадані, які необхідні для успішного зчитування цих даних у майбутньому. Якщо під час запису змінився розмір файла `st_size` або було додано нові фізичні блоки на диску, `fdatasync` скидає нові метадані. Якщо зміна стосувалася лише перезапису існуючих блоків, оновлення інформаційних міток часу `st_mtime` та `st_ctime` залишається у RAM і не викликає запису в журнал диска.

### Контракт sync_file_range(...)
Виклик `sync_file_range` є специфічним для Linux і працює з конкретним діапазоном байтів від зсуву `offset` довжиною `nbytes`. Він дозволяє асинхронно ініціювати виштовхування сторінок або чекати завершення раніше відправленого В/В. Головна відмінність контракту: `sync_file_range` **не видає** дискову команду `FLUSH`/`FUA` контролеру накопичувача і **не скидає** метадані файлової системи.

| Системний виклик | Обов'язковість скидання сторінок даних | Обов'язковість метаданих `st_mtime` / `st_ctime` | Обов'язковість метаданих `st_size` / allocation | Команда накопичувачу `FLUSH` / `FUA` |
| :--- | :--- | :--- | :--- | :--- |
| `fsync(fd)` | Так (усі сторінки) | Так (завжди) | Так (завжди) | Так (`REQ_PREFLUSH`) |
| `fdatasync(fd)` | Так (усі сторінки) | Ні (ігнорує `st_mtime`) | Так (якщо змінилися) | Так (`REQ_PREFLUSH`) |
| `sync_file_range(...)` | Так (лише для діапазону) | Ні | Ні | **Ні** (пропускає `FLUSH`) |

## 2. Повний розбір прапорців sync_file_range

Параметр `flags` у системному виклику `sync_file_range` визначає поведінку виклику щодо очікування та ініціалізації запису. Прапорці комбінуються побітовим «АБО»:

| Прапорець | Числове значення | Семантика та поведінка ядра |
| :--- | :--- | :--- |
| `SYNC_FILE_RANGE_WAIT_BEFORE` | `1` | Блокує викликовий потік до завершення запису всіх брудних сторінок у вказаному діапазоні, відправлених на диск **до** цього виклику. |
| `SYNC_FILE_RANGE_WRITE` | `2` | Ініціює виштовхування (writeback) усіх брудних сторінок у діапазоні, які ще не були відправлені до блокового шару. Виклик повертається одразу, не чекаючи завершення В/В. |
| `SYNC_FILE_RANGE_WAIT_AFTER` | `4` | Блокує викликовий потік до завершення запису всіх сторінок, відправлених на диск під час поточного виклику `SYNC_FILE_RANGE_WRITE`. |

### Особливості параметрів зсуву та довжини
- Параметри `offset` та `nbytes` вказують межі виштовхування в байтах. Якщо `nbytes == 0`, ядро трактує це як виштовхування всього діапазону від `offset` до кінця файла.
- Оскільки підсистема сторінкового кешу ядра оперує цілими сторінками `struct page`, ядро Linux автоматично округлює межі діапазону до розміру апаратної сторінки пам'яті (`PAGE_SIZE`, зазвичай 4096 байтів): `offset` округлюється вниз до кратного 4096 (`offset & ~(PAGE_SIZE-1)`), а `offset + nbytes` округлюється вгору.

### Типові комбінації прапорців
1. `SYNC_FILE_RANGE_WRITE`: чисто асинхронне виштовхування сторінок без блокування потоку. Використовується фоновими потоками баз даних для запобігання накопиченню брудних сторінок.
2. `SYNC_FILE_RANGE_WAIT_BEFORE | SYNC_FILE_RANGE_WRITE`: гарантує, що нові брудні сторінки поставлено в чергу В/В, а всі раніше відправлені сторінки вже доїхали до дискового контролера.
3. `SYNC_FILE_RANGE_WAIT_BEFORE | SYNC_FILE_RANGE_WRITE | SYNC_FILE_RANGE_WAIT_AFTER`: повний синхронний запис діапазону сторінок (блокуючий виклик), який чекає завершення запису всіх сторінок заданого діапазону.

## 3. Прапорці відкриття файла open(2) та синхронний В/В

Гарантії синхронізації можна запросити атомарно для кожного виклику `write()`, вказавши відповідні прапорці під час відкриття файлового описувача:

:::tabs
```c
int fd = open("wal.log", O_WRONLY | O_CREAT | O_DSYNC, 0644);
```
```cpp
storage::FileDescriptor fd{::open("wal.log", O_WRONLY | O_CREAT | O_DSYNC, 0644)};
```
:::

| Прапорець `open` | Відповідний системний виклик на кожен `write()` | Поведінка |
| :--- | :--- | :--- |
| `O_SYNC` | Автоматичний `fsync(fd)` після кожного `write()` | Блокує `write()` до завершення запису даних та всіх метаданих. |
| `O_DSYNC` | Автоматичний `fdatasync(fd)` після кожного `write()` | Блокує `write()` до завершення запису даних та необхідних метаданих. |
| `O_RSYNC` | У Linux не реалізований: glibc визначає `O_RSYNC` тим самим значенням, що й `O_SYNC` | За POSIX мав би вимагати скидання всіх невиконаних записів на файл перед `read()`; на Linux цієї семантики немає. |

Ядро Linux реалізує лише `O_SYNC` та `O_DSYNC`; окремої поведінки для `O_RSYNC` немає, бо glibc визначає його значенням `O_SYNC`. Тому комбінація `O_DSYNC | O_RSYNC` не дає жодних додаткових гарантій для `read()` — розраховувати на синхронізацію читань на Linux не можна.

## 4. Коди помилок та обробка повернень

Усі виклики скидання кешу повертають `0` у разі успіху та `-1` у разі помилки із встановленням змінної `errno`:

| Код помилки | Причина | Необхідні дії застосунку |
| :--- | :--- | :--- |
| `EBADF` | Описувач `fd` не є дійсним відкритим файловим описувачем. | Перевірити, чи описувач не було закрито раніше. |
| `EIO` | Сталася апаратна помилка вводу-виводу при виштовхуванні сторінок на накопичувач. | **Критично:** сторінки в кеші втрачені. Необхідно закрити файл та запустити відновлення транзакцій. |
| `ENOSPC` | Не вистачило вільного місця на пристрої під час запису розширених метаданих або CoW-блоків (btrfs/zfs). | Звільнити місце на диску, повідомити оператора. |
| `EROFS` | Файлова система переведена у режим "read-only" через збій або аварійне перемонтування. | Аварійна зупинка сервісу (panic/abort). |
| `EINVAL` | Недійсне зміщення, від'ємна довжина в `sync_file_range`, або `fd` вказує на сокет/pipe. | Виправлення параметрів виклику. |

Починаючи з Linux 4.13, ядро застосовує лічильники `errseq_t`: помилка `EIO` гарантовано передається кожному описувачу, відкритому на момент збою, — але кожному рівно один раз. Якщо `fsync()` повертає `EIO`, повторний виклик `fsync()` на тому самому дескрипторі поверне `0`, але дані **не були** збережені! Рекомендація розробникам: при отриманні `EIO` негайно закривати дескриптор.

## 5. Внутрішньоядерний шлях виконання (Kernel Call Graph)

При виклику `fsync(fd)` у ядрі Linux відбувається наступний ланцюжок викликів:

1. `sys_fsync(fd)` -> `do_fsync(fd, datasync=0)` -> `vfs_fsync_range(file, start, end, datasync)`.
2. `vfs_fsync_range` викликає `file_write_and_wait_range(file, start, end)`, який надсилає брудні сторінки в блоковий шар через `mapping->a_ops->writepages` і чекає їх завершення (`filemap_fdatawait_keep_errors`).
3. Викликається специфічний для файлової системи метод `file->f_op->fsync(...)` (наприклад, `ext4_sync_file` для ext4 або `xfs_file_fsync` для XFS). Сигнатура методу в структурі `struct file_operations`:
   `int (*fsync) (struct file *file, loff_t start, loff_t end, int datasync);`
4. Метод файлової системи викликає транзакційний журнал (для ext4 це `jbd2_log_start_commit` та `jbd2_log_wait_commit`), відправляючи транзакцію метаданих на диск.
5. Блоковий шар формує `bio` з `REQ_PREFLUSH`, який примушує контролер накопичувача очистити свій волатильний DRAM-кеш на фізичний носій.

## 6. Асинхронна синхронізація у підсистемі io_uring

Сучасні високопродуктивні застосунки викликають скидання кешу без блокування потоків виконання через підсистему `io_uring`:

:::tabs
```c
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_fsync(sqe, fd, IORING_FSYNC_DATASYNC);
sqe->off = offset;
sqe->len = len;
```
```cpp
io_uring_sqe* sqe = io_uring_get_sqe(&ring);
io_uring_prep_fsync(sqe, file.get(), IORING_FSYNC_DATASYNC);
sqe->off = offset;
sqe->len = len;
```
:::

Прапорці `sqe->fsync_flags`:
- `0`: асинхронний аналог `fsync(fd)` (повне скидання даних та метаданих).
- `IORING_FSYNC_DATASYNC`: асинхронний аналог `fdatasync(fd)` (лише дані та необхідні метадані).

Також підтримується операція `IORING_OP_SYNC_FILE_RANGE`, яка дозволяє асинхронно відправляти діапазони сторінок на виштовхування без блокування потоку подій `epoll`/`io_uring`.

## 7. Порівняння із системами Windows NT та POSIX-аналогами

У системному програмуванні на платформі Windows NT аналогами UNIX системних викликів скидання кешу виступають наступні функції системного API:

| Операція POSIX / Linux | Відповідник у Windows API (Win32) | Опис та механіка поведінки |
| :--- | :--- | :--- |
| `fsync(fd)` | `FlushFileBuffers(HANDLE hFile)` | Очищає системні буфери файлу та надсилає дискову команду `FLUSH` накопичувачу. |
| `open(..., O_SYNC)` | `FILE_FLAG_WRITE_THROUGH` | Кожна операція запису через `WriteFile` оминає кеш і пишеться синхронно на диск. |
| `open(..., O_DIRECT)` | `FILE_FLAG_NO_BUFFERING` | Повний обхід системного кешу сторінок із вимогами щодо вирівнювання буферів та секторів. |

Головна відмінність Linux полягає у наявності тонкого розділення на `fdatasync()` та `sync_file_range()`, якого немає у підсистемі Windows NT.

## 8. Перевірка параметрів крізь sysfs та контролери диска

Перевірка статусу волатильного кешування накопичувача у Linux здійснюється через інтерфейс sysfs:

```bash
# Перевірка поточного режиму кешу запису накопичувача (write through / write back)
cat /sys/block/nvme0n1/queue/write_cache

# Перевірка підтримки команди FUA (Force Unit Access) блоковим пристроєм
cat /sys/block/nvme0n1/queue/fua
```

Якщо `write_cache` повертає `write back`, системні виклики `fsync()` та `fdatasync()` зобов'язані відправляти апаратний `FLUSH`. Якщо накопичувач налаштовано в режим `write through` (або в разі використання enterprise SSD з іоністорами PLP), ядро автоматично оптимізує виконання `fsync`, пропускаючи зайві команди очищення.

## 9. Простеження ядра через tracepoints та sysctl-параметри

Для перевірки дійсної поведінки системних викликів у ядрі використовуються точки простеження (tracepoints) підсистеми `writeback`, `ext4` та `block`:

```bash
# Ввімкнення простеження виштовхування сторінок ядра
echo 1 > /sys/kernel/tracing/events/writeback/writeback_written/enable
echo 1 > /sys/kernel/tracing/events/writeback/wbc_writepage/enable

# Ввімкнення простеження команд FLUSH/FUA на блоковому рівні
echo 1 > /sys/kernel/tracing/events/block/block_bio_queue/enable
cat /sys/kernel/tracing/trace_pipe | grep -E "FLUSH|FUA"
```

Налаштування фонового скидання брудних сторінок у `/proc/sys/vm/`:
- `dirty_background_ratio`: відсоток системної пам'яті, при досягненні якого фонові потоки `kworker` починають асинхронно скидати брудні сторінки на диск (за замовчуванням 10%).
- `dirty_ratio`: відсоток системної пам'яті, при досягненні якого будь-який процес, що викликає `write()`, сам блокується і починає виштовхувати брудні сторінки на диск (за замовчуванням 20%).
- `dirty_expire_centisecs`: час в сантисекундах (1/100 с), після якого брудна сторінка вважається застарілою і підлягає обов'язковому скиданню на диск (за замовчуванням 3000 = 30 секунд).
