</preknowlist>

Коли база даних або транзакційний сервіс виконує системний виклик `write()` для оновлення сторінки індексу обсягом 4 КіБ, операційна система не переносить ці байти на фізичний накопичувач миттєво. Вона копіює їх у сторінковий кеш ядра і повертає керування за одиниці мікросекунд, залишаючи дані у волатильній оперативній пам'яті. Якщо в цей момент знеструмити сервер, транзакція, яку застосунок вважав підтвердженою, зникне або залишить файлову систему у зламаному стані. Для запобігання втратам даних у ядрі Linux передбачено системні виклики `fsync`, `fdatasync` та `sync_file_range`, кожен з яких надає кардинально різні гарантії довговічності, швидкодії та взаємодії з апаратними кешами дискового накопичувача.

## 1. Ілюзія успішного запису та багатошарова ієрархія кешування

Звичайні системні виклики запису `write()` та `pwrite()` гарантують лише те, що байти із буфера користувацької програми успішно скопійовані в оперативну пам'ять ядра. У цій точці сторінка пам'яті у структурі `struct page` або `struct folio` отримує позначку «брудна» (`PAGECACHE_TAG_DIRTY`). Згодом фонові потоки ядра (flusher threads, як-от `kworker/u:X`) сканують сторінковий кеш через структуру адресового простору `struct address_space` і поступово відправляють брудні сторінки до блокового шару для запису на накопичувач.

Проте успішне відправлення сторінок ядром у дискову чергу ще не означає їх довговічного збереження на фізичному носії. Сучасна підсистема зберігання даних містить шість послідовних рівнів кешування та черг, через які мусять пройти байти:

1. **Буфери прикладної програми (App RAM)** — оперативна пам'ять процесу (наприклад, буферний пул бази даних).
2. **Сторінковий кеш ядра (Page Cache)** — системна оперативна пам'ять, у якій ядро утримує брудні сторінки файлової системи у структурі дерев `xarray`.
3. **Журнал та структури файлової системи** — таблиці inode, карти виділення блоків та транзакційний журнал (Journal / Intent Log, наприклад JBD2 у ext4 або log у XFS).
4. **Черга блокового рівня (Block Layer)** — черга запитів В/В (`struct request_queue`), де працюють планувальники дискових операцій (BFQ, kyber, none) та формуються структури `bio`.
5. **Волатильний DRAM-кеш накопичувача (Drive Controller DRAM)** — швидка оперативна пам'ять на платі контролера SSD або HDD накопичувача.
6. **Енергонезалежний носій (Flash / Platter)** — фізичні осередки NAND Flash або магнітні пластини, де дані зберігаються після вимкнення живлення.

![Стек зберігання та межі гарантій скидання кешу](/reference/unix-linux/io/fsync-fdatasync-sync-file-range/img/fig-flushing-stack.svg)
*Багатошарова ієрархія зберігання Linux та межі дії системних викликів скидання кешу.*

Головна небезпека полягає у тому, що волатильний DRAM-кеш дискового контролера (рівень 5) за замовчуванням повертає підтвердження завершення запису ядра Linux одразу після прийому байтів у свій внутрішній буфер. Якщо електроживлення сервера вимкнеться до того, як контролер диска встигне перенести дані з DRAM-буфера у NAND-осередки, виклик `write()` втратить дані, незважаючи на успішне завершення системного виклику. 

Для проходження цієї ієрархії до самого дна необхідні спеціальні інструкції примусового очищення кешу. Детальний [договір системних викликів та прапорці open](book:unix-linux/fsync-fdatasync-sync-file-range/api-sync-contracts.md) розглядає сигнатури та специфічні параметри кожного виклику.

## 2. Механізм та контракт fsync(fd): повне скидання сторінок та метаданих

Системний виклик `fsync(fd)` є класичним інструментом POSIX для забезпечення повної довговічності. Коли програма викликає `fsync(fd)`, ядро Linux виконує три послідовні критичні дії:

1. **Виштовхування всіх брудних сторінок файла**: ядро знаходить усе дерево сторінок (radix tree / xarray) даного файла у сторінковому кеші та примусово переводить брудні сторінки у стан запису (`PAGECACHE_TAG_WRITEBACK`), чекаючи завершення їх передачі по шині NVMe або SATA через виклик `file_write_and_wait_range()`.
2. **Фіксація метаданих файлової системи**: якщо під час роботи з файлом оновилися будь-які його метадані у структурі `inode` (розмір файла `st_size`, мітка часу останньої модифікації `st_mtime`, мітка зміни статусу `st_ctime`, власник `st_uid`, права доступу або дерева виділених блоків/екстентів), ядро формує транзакцію у журналі файлової системи (наприклад, ext4 JBD2) та чекає її завершення через виклик `jbd2_log_wait_commit()`.
3. **Примусове очищення кешу накопичувача**: блоковий шар ядра формує біо-запит (`struct bio`) з прапорцем `REQ_PREFLUSH` або `REQ_FUA` (Force Unit Access). Цей запит перетворюється у низькорівневу команду SCSI `SYNCHRONIZE CACHE` (команда `0x35`) або NVMe `FLUSH` (команда `0x00`), яка змушує дисковий контролер перенести свій волатильний DRAM-кеш у фізичні комірки Flash/пластини.

Ціна повної довговічності `fsync()` виявляється дуже високою. Оскільки навіть найпростіша зміна байта у виклику `write()` оновлює мітку часу `st_mtime` у структурі `inode`, виклик `fsync()` змушений виконувати щонайменше **дві окремі дискові операції**: спочатку записати блок даних файла, а потім записати транзакцію метаданих у журнал файлової системи. На жорстких дисках (HDD) це вимагає фізичного переміщення зчитувальної голівки між зоною даних та зоною журнала, що збільшує затримку із мікросекунд до 10–15 мілісекунд на кожну транзакцію.

У файлових системах із журналюванням метаданих (ext4 у режимі `data=ordered`, XFS) `fsync` змушує фоновий потік журналу (наприклад, `jbd2/nvme0n1p2-8`) перевести поточну журнальну транзакцію зі стану Running у стан Committing, що піддає блокуванню всі інші паралельні потоки, які намагаються модифікувати метадані в цій самій файловій системі.

## 3. Оптимізація fdatasync(fd): розрізнення істотних та неістотних метаданих

Для зменшення накладних витрат подвійного запису POSIX оголошує системний виклик `fdatasync(fd)`. Головна ідея `fdatasync` полягає у семантичному розрізненні **істотних** та **неістотних** метаданих файла:

- **Істотні метадані (Essential Metadata)** — це метадані, без скидання яких на диск стає неможливим успішне зчитування збережених байтів після перезавантаження системи. Сюди належать: новий розмір файла (`st_size`), якщо файл розширився, та нові покажчики на дискові блоки/екстенти (`ext4_extent_header`), якщо для файла було виділено нові фізичні сектори.
- **Неістотні метадані (Non-essential Metadata)** — це інформаційні метки, відсутність яких на диску не заважає зчитати записані байти. Головні приклади: мітка часу модифікації `st_mtime`, мітка доступу `st_atime` та мітка зміни статусу `st_ctime`.

Поведінка `fdatasync(fd)` залежить від сценарію роботи з файлом:

![Відмінності метаданих між fsync та fdatasync](/reference/unix-linux/io/fsync-fdatasync-sync-file-range/img/fig-metadata-split.svg)
*Порівняння роботи fsync та fdatasync при перезаписі блоків та розширенні файла.*

### Сценарій А: Перезапис у межах наявних блоків (In-place Overwrite)
Якщо програма відкрила заздалегідь виділений файл (наприклад, файл даних бази даних обсягом 1 ГБ) і виконала `write()` у вже виділений блок без зміни розміру файла:
- `fdatasync(fd)` скидає брудну сторінку даних і відразу відправляє команду `FLUSH` дисковому накопичувачу. Мітка `st_mtime` залишається оновленою лише у RAM в структурі `inode` і не записується у журнал файлової системи. **Результат:** 1 дискова операція.
- `fsync(fd)` скидає сторінку даних, а потім обов'язково відкриває транзакцію у журналі ФС для збереження оновленого `st_mtime`. **Результат:** 2+ дискові операції.

### Сценарій Б: Розширення файла (Append Write)
Якщо `write()` збільшив розмір файла або спричинив виділення нових екстентів на диску:
- `fdatasync(fd)` визначає, що `st_size` змінено. Для збереження здатності прочитати нові байти ядро зобов'язане записати і байти даних, і оновлений `inode` із новим розміром `st_size`.
- Поведінка `fdatasync(fd)` та `fsync(fd)` у цьому сценарії повністю збігається — обидва виклики виконують скидання даних та фіксацію метаданих у журналі.

🔧 **Навіщо це у базах даних:** Системи керування базами даних (PostgreSQL, MySQL InnoDB, SQLite WAL) заздалегідь створюють файли транзакційних журналів фіксованого розміру (у PostgreSQL сегмент WAL — 16 МіБ): новий сегмент або заповнюється нулями, або виділяється викликом `fallocate()`. Завдяки цьому всі наступні записи у WAL є перезаписом наявних блоків, що дозволяє `fdatasync()` працювати зі швидкістю однієї операції В/В замість двох — і виграш тим відчутніший, чим дорожча журнальна транзакція файлової системи.

## 4. Пастка sync_file_range: асинхронна конвеєризація проти гарантій катастрофостійкості

У ядрах Linux починаючи з версії 2.6.17 з'явився специфічний для Linux системний виклик `sync_file_range`:

:::tabs
```c
int sync_file_range(int fd, off64_t offset, off64_t nbytes, unsigned int flags);
```
```cpp
extern "C" int sync_file_range(int fd, off64_t offset, off64_t nbytes, unsigned int flags);
```
:::

Цей виклик дає змогу виштовхувати брудні сторінки не для всього файла, а для точного діапазону байтів від `offset` довжиною `nbytes`. Головна мета створення виклику — надати високопродуктивним сховищам даних можливість **конвеєризації** (pipelining) виштовхування сторінок у фоновому режимі.

![Асинхронний конвеєр sync_file_range та очищення кешу](/reference/unix-linux/io/fsync-fdatasync-sync-file-range/img/fig-sync-file-range-pipeline.svg)
*Асинхронний конвеєр виштовхування брудних сторінок за допомогою sync_file_range.*

Поведінка регулюється маскою прапорців `flags`:
- `SYNC_FILE_RANGE_WRITE`: знаходить брудні сторінки у вказаному діапазоні та передає їх блоковому шару ядра для запису. Виклик **не блокує** потік виконання і повертає керування негайно.
- `SYNC_FILE_RANGE_WAIT_BEFORE`: блокує потік доти, доки не завершиться запис сторінок у цьому діапазоні, які вже перебували в дорозі до моменту виклику.
- `SYNC_FILE_RANGE_WAIT_AFTER`: блокує потік доти, доки не завершиться запис сторінок, відправлених поточним викликом `SYNC_FILE_RANGE_WRITE`.

### Критична пастка довговічності (The Power Loss Trap)
Нераціональне використання `sync_file_range` є однією з найпоширеніших причин прихованого пошкодження даних при аварійному вимкненні систем.

> [!CAUTION]
> `sync_file_range` **НЕ ВІДПРАВЛЯЄ** команду `FLUSH` або `FUA` волатильному DRAM-кешу накопичувача і **НЕ ФІКСУЄ** метадані файлової системи!

Коли `sync_file_range` із прапорцями `SYNC_FILE_RANGE_WAIT_BEFORE | SYNC_FILE_RANGE_WRITE | SYNC_FILE_RANGE_WAIT_AFTER` повертає `0`, це означає лише те, що байти залишили оперативну пам'ять ядра і потрапили до... DRAM-кешу дискового контролера. Якщо в цей момент станеться збій живлення сервера, байти у DRAM-кеші диска буде безповоротно втрачено!

Правильний паттерн використання `sync_file_range` у високопродуктивних рушіях передбачає фонове виштовхування сторінок під час обчислень за допомогою `SYNC_FILE_RANGE_WRITE`, після чого у момент фіксації транзакції обов'язково викликається `fdatasync(fd)` для видачі фінального `FLUSH` на накопичувач.

## 5. Синхронний ввід-вивід на рівні прапорців open(): O_SYNC та O_DSYNC

Замість виклику `fsync()` або `fdatasync()` після кожного `write()`, програма може передати прапорці синхронізації безпосередньо під час відкриття файла у виклику `open()`:

:::tabs
```c
int fd = open("wal.log", O_WRONLY | O_CREAT | O_DSYNC, 0644);
```
```cpp
storage::FileDescriptor fd{::open("wal.log", O_WRONLY | O_CREAT | O_DSYNC, 0644)};
```
:::

- `O_DSYNC`: кожен виклик `write(fd, ...)` поводиться так, ніби одразу після нього виконали `fdatasync(fd)`. Системний виклик `write()` не повертає керування доти, доки байти та необхідні метадані не будуть записані на носій з урахуванням дискового `FLUSH`.
- `O_SYNC`: кожен виклик `write(fd, ...)` поводиться так, ніби одразу після нього виконали `fsync(fd)` із примусовим журналюванням метаданих `st_mtime`.

Порівняння двох підходів до синхронізації:

```
Підхід A (пакетний запис):
  write(fd, buf1, 4096);
  write(fd, buf2, 4096);
  write(fd, buf3, 4096);
  fdatasync(fd);          <-- 1 виклик fdatasync, 1 дисковий FLUSH на всі 3 блоки!

Підхід Б (O_DSYNC):
  write(fd, buf1, 4096);  <-- 1 дисковий FLUSH
  write(fd, buf2, 4096);  <-- 1 дисковий FLUSH
  write(fd, buf3, 4096);  <-- 1 дисковий FLUSH
```

Якщо програмі потрібно записати серію з 10 блоків поспіль, використання `O_DSYNC` примусить диск виконати 10 послідовних операцій `FLUSH`. Використання звичайного `write()` для 10 блоків із одним підсумковим викликом `fdatasync()` дозволить ядру об'єднати 10 блоків у один суцільний дисковий запит і виконати лише 1 `FLUSH`, підвищивши пропускну здатність в рази.

## 6. Обробка помилок В/В та уроки інциденту fsyncgate

Тривалий час серед розробників існувало переконання: якщо `fsync()` повернув помилку `EIO` (Input/Output Error), можна зачекати кілька секунд і повторити виклик `fsync()` у циклі. 

У 2018 році дослідження спільноти PostgreSQL викрило фундаментальну ваду у реалізації сторінкового кешу Linux (так званий інцидент **fsyncgate**). Докладно [еволюцію гарантій скидання та скандал fsyncgate](book:unix-linux/fsync-fdatasync-sync-file-range/hist-fsyncgate-and-cache.md) висвітлено у відповідній історичній вставці.

Суть проблеми полягала у тому, що при виникненні апаратної помилки диска під час фонового скидання брудної сторінки ядро Linux позначало цю сторінку як **чисту** (щоб запобігти переповненню RAM брудними сторінками, які неможливо записати) і встановлювало прапорець `AS_EIO` у файлі. Перший виклик `fsync()` повертав `-1` з `errno = EIO` і... **скидав** прапорець `AS_EIO`. Повторний виклик `fsync()` бачив очищений прапорець і повертав успіх `0`, хоча дані на диск так і не потрапили!

### Поведінка в сучасних ядрах Linux (4.13+)
Починаючи з версії Linux 4.13 ядро перейшло на систему відстеження помилок через відносні лічильники `errseq_t`. Помилка `EIO` або `ENOSPC` тепер утримується в адресовому просторі файла (`struct address_space`), а кожен відкритий описувач (`struct file`) зберігає власний знімок лічильника — тож факт помилки отримає рівно один раз кожен описувач, відкритий на момент збою, а не лише той, хто викликав `fsync()` першим.

> [!IMPORTANT]
> Якщо системний виклик `fsync()` або `fdatasync()` повернув `EIO`, додаток **не повинен** намагатися повторювати виклик `fsync()`. Єдиним безпечним розв'язком для баз даних є аварійне припинення роботи (panic/abort), скидання буферного кешу та запуск процедури аварійного відновлення з транзакційного журналу (crash recovery).

Для глибшого аналізу практичних вимірювань затримок дискових викликів та ознайомлення з кодом перевірки перегляньте [практичний бенчмарк та вимірювання затримок](book:unix-linux/fsync-fdatasync-sync-file-range/proj-sync-bench.md).

## 7. Взаємодія з Copy-on-Write файловими системами (Btrfs, ZFS)

У файлових системах із підтримкою механізму Copy-on-Write (CoW), таких як Btrfs та ZFS, поведінка системного виклику `fsync` суттєво відрізняється від традиційних журнальних систем (ext4, XFS):

1. **Відсутність оновлення "поверх" (No In-place Update)**:
   У CoW-системах нові байти файлу ніколи не перезаписують існуючі фізичні блоки на диску. Замість цього ядро виділяє нові фізичні сектори для модифікованих блоків даних, що вимагає оновлення всього дерева покажчиків (B-tree / Merkle tree) від видозміненого листа аж до кореневого вузла транзакції.

2. **Дерева скидання метаданих (Log Trees / ZIL)**:
   Для уникнення надто дорогих викликів перерахунку всього дерева метаданих файлової системи при кожному `fsync()`, Btrfs реалізує спеціальні дерева журналювання під назвою `log_tree`, а ZFS застосовує окремий інтент-лог ZFS Intent Log (ZIL). Під час виклику `fsync()` байти даних та оновлені покажчики записуються у `log_tree`/ZIL, що дозволяє завершити скидання за один швидкий дисковий транш. 

3. **Специфіка fdatasync у CoW**:
   На файлових системах Btrfs виклик `fdatasync()` ініціює запис нового екстента даних та оновлення покажчика у `log_tree`. Проте оскільки будь-яка зміна блоку в CoW створює новий фізичний екстент, `fdatasync` на Btrfs змушений оновлювати структури метаданих дерева екстентів навіть при перезаписі блоків однакового розміру.

## 8. Проходження команд FLUSH крізь віртуалізацію та Device Mapper

У складних корпоративних стеках зберігання (LVM, Software RAID, DM-Crypt, Docker/OverlayFS) системні виклики `fsync()` та `fdatasync()` проходять крізь кілька проміжних шарів трансформації:

- **DM-Crypt (LUKS шифрування)**: Шар шифрування `dm-crypt` перехоплює `bio` з прапорцем `REQ_PREFLUSH`, прозоро пересилає команду очищення базовому блоковому пристрою, чекає її виконання та лише після цього підтверджує успіх виклику ядра.
- **MD-RAID (RAID1 / RAID5 / RAID6)**: При отриманні `fsync()` дзеркало RAID1 надсилає паралельні команди `FLUSH` усім накопичувачам масиву і чекає підтвердження від кожного диска. RAID5/6 додатково гарантує, що обчислені блоки парності (parity blocks) записані й пройшли те саме скидання кешів на своїх дисках, що й блоки даних.
- **Контейнерне середовище (OverlayFS)**: У середовищі Docker або Podman виклик `fsync()` на файлі верхнього шару (upper layer) транслюється у виклик `fsync` нижньої файлової системи хоста, забезпечуючи реальну довговічність для контейнеризованих СУБД.

## 9. Практичні паттерни у реальних СУБД та файлових операціях

Різні бази даних застосовують специфічні конфігурації скидання кешу:

### PostgreSQL
PostgreSQL надає параметр `wal_sync_method` у конфігураційному файлі `postgresql.conf`:
- `fdatasync` (за замовчуванням у Linux): викликає `fdatasync()` після кожного скидання WAL-сегмента.
- `fsync`: викликає `fsync()` після кожного запису WAL.
- `open_datasync`: відкриває WAL-файли з прапорцем `O_DSYNC`.

### SQLite
SQLite використовує `PRAGMA synchronous`:
- `FULL`: викликає `fsync()` для файлу журналу та для каталогу при створенні транзакції.
- `NORMAL`: синхронізує рідше — у режимі WAL скидання відбувається на контрольних точках (checkpoint), а не на кожній транзакції.
- `OFF`: відключає виклики синхронізації, покладаючись на виштовхування сторінок ядром (ризик пошкодження при збої).

### Атомарний перезапис файлів конфігурації (Write-Fsync-Rename Pattern)
Для безпечного оновлення конфігураційного файла без ризику отримати 0-байтовий файл при знеструмленні застосовується наступний алгоритм:
1. Записати нові байти у тимчасовий файл `config.tmp`.
2. Викликати `fdatasync(fd_tmp)` або `fsync(fd_tmp)`, щоб байти та метадані потрапили на диск.
3. Викликати системний виклик `rename("config.tmp", "config.json")` — у межах однієї файлової системи заміна імені атомарна.
4. Викликати `fsync(dir_fd)` для описувача **батьківського каталогу**, щоб сам запис у каталозі (нове ім'я замість старого) був зафіксований у журналі файлової системи.

```c
/* Приклад атомарного запису конфігураційного файла на мові C */
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>

int save_config_atomic(const char *path, const char *data, size_t len) {
    char tmp_path[256];
    snprintf(tmp_path, sizeof(tmp_path), "%s.tmp", path);

    int fd = open(tmp_path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return -1;

    if (write(fd, data, len) != (ssize_t)len) {
        close(fd);
        unlink(tmp_path);
        return -1;
    }

    if (fdatasync(fd) < 0) {
        close(fd);
        unlink(tmp_path);
        return -1;
    }
    close(fd);

    if (rename(tmp_path, path) < 0) {
        unlink(tmp_path);
        return -1;
    }

    char dir_path[256];
    snprintf(dir_path, sizeof(dir_path), "%s", path);
    char *slash = strrchr(dir_path, '/');
    if (slash) *slash = '\0';
    else snprintf(dir_path, sizeof(dir_path), ".");

    int dir_fd = open(dir_path, O_RDONLY | O_DIRECTORY);
    if (dir_fd >= 0) {
        fsync(dir_fd);
        close(dir_fd);
    }
    return 0;
}
```

```cpp
// Приклад атомарного запису конфігураційного файла на мові C++20
#include <iostream>
#include <fstream>
#include <string_view>
#include <system_error>
#include <unistd.h>
#include <fcntl.h>

namespace storage {

void save_config_atomic(std::string_view path, std::string_view data) {
    const std::string dest(path);
    const std::string tmp_path = dest + ".tmp";

    int fd = ::open(tmp_path.c_str(), O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) {
        throw std::system_error(errno, std::generic_category(), "Не вдалося створити тимчасовий файл");
    }

    if (::write(fd, data.data(), data.size()) != static_cast<ssize_t>(data.size())) {
        ::close(fd);
        ::unlink(tmp_path.c_str());
        throw std::system_error(errno, std::generic_category(), "Помилка запису даних");
    }

    if (::fdatasync(fd) < 0) {
        ::close(fd);
        ::unlink(tmp_path.c_str());
        throw std::system_error(errno, std::generic_category(), "Помилка fdatasync");
    }
    ::close(fd);

    if (::rename(tmp_path.c_str(), dest.c_str()) < 0) {
        ::unlink(tmp_path.c_str());
        throw std::system_error(errno, std::generic_category(), "Помилка атомарного перейменування");
    }

    const auto slash = dest.find_last_of('/');
    const std::string dir_path = (slash == std::string::npos) ? std::string(".") : dest.substr(0, slash);

    int dir_fd = ::open(dir_path.c_str(), O_RDONLY | O_DIRECTORY);
    if (dir_fd >= 0) {
        ::fsync(dir_fd);
        ::close(dir_fd);
    }
}

} // namespace storage
```

## 10. Підсумкове порівняння та правила вибору

Узагальнена таблиця характеристик системних викликів скидання кешу:

| Характеристика | `fsync` | `fdatasync` | `sync_file_range` | `open(O_DSYNC)` |
| :--- | :--- | :--- | :--- | :--- |
| **Гарантія даних** | Повна | Повна | Часткова (лише в RAM/Block Layer) | Повна |
| **Гарантія метаданих** | Повна (`st_mtime`, `st_size`) | Лише істотні (`st_size`) | Відсутня | Лише істотні (`st_size`) |
| **Дисковий FLUSH/FUA** | Так (обов'язково) | Так (обов'язково) | **Ні** | Так (на кожен `write`) |
| **Відносний IOPS** | Базовий (1x) | Високий (1.3x–1.5x) | Екстремальний (5x–10x, без FLUSH) | Низький при пакетному записі |
| **Область застосування** | Критичні конфіги, rename | WAL баз даних, логи | Асинхронне виштовхування В/В | Потоковий запис без пакетування |

Практичні правила вибору для розробника:
1. **Для транзакційних журналів баз даних (WAL):** Використовувати `fdatasync()` на заздалегідь виділених файлах (`fallocate`).
2. **Для заміни конфігураційних файлів через atomic rename:** Використовувати `fsync()` перед викликом `rename()`, щоб гарантувати скидання файлу та нового запису каталогу.
3. **Для фонового виштовхування великих масивів даних:** Використовувати `sync_file_range(SYNC_FILE_RANGE_WRITE)` для асинхронного фонового скидання, завершуючи процедуру обов'язковим `fdatasync()`.
