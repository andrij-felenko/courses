# 🧪 Лабораторія буферизації: п'ять дослідів на власній машині

Тут зібрано чотири маленькі програми на C і десяток команд, які перетворюють кожне твердження про буферизацію stdio на число або на рядок у трасі — на вашій машині, з вашою бібліотекою C. Прочитати, що режим обирає бібліотека, і побачити, як та сама двійка пише по рядку в терміналі й по 4096 байтів у канал, — різні речі, і друге тримається в голові набагато міцніше.

Потрібні `cc`, `strace` і coreutils; збірка скрізь однакова — `cc -O2 -o назва назва.c`. Тексти всередині програм навмисне латиницею: `strace` друкує байти поза ASCII вісімковими екрануваннями, і траса з кирилицею стає нечитабельною кашею.

## 1. Скільки коштує перетин межі

Перший дослід міряє те, заради чого буфер узагалі існує, — ціну одного походу в ядро. Той самий мегабайт іде в `/dev/null` п'ятьма способами, щоб на виході було не одне число, а розклад, з чого воно складається.

```c
/* bench.c — ціна перетину межі: посимвольний write проти буфера stdio */
#define _POSIX_C_SOURCE 200809L
#include <fcntl.h>
#include <stdio.h>
#include <time.h>
#include <unistd.h>

enum { N = 1 << 20, BLK = 4096 };          /* рівно 1 МіБ */

static double now(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec * 1e-9;
}

static void row(const char *name, double sec, long calls)
{
    fprintf(stderr, "%s\n    %8.2f мс   %8.1f нс на виклик\n",
            name, sec * 1e3, sec * 1e9 / calls);
}

int main(void)
{
    static char block[BLK];
    double t;

    for (int i = 0; i < BLK; i++) block[i] = 'x';

    int fd = open("/dev/null", O_WRONLY);
    FILE *f = fopen("/dev/null", "w");
    if (fd < 0 || !f) { perror("/dev/null"); return 1; }
    setvbuf(f, NULL, _IOFBF, 0);           /* до першої операції — так можна */

    t = now();
    for (long i = 0; i < N; i++)
        if (write(fd, block, 1) < 0) { perror("write"); return 1; }
    row("А  write по одному байту", now() - t, N);

    t = now();
    for (long i = 0; i < N / BLK; i++)
        if (write(fd, block, BLK) < 0) { perror("write"); return 1; }
    row("Б  write по 4096 байтів", now() - t, N / BLK);

    t = now();
    for (long i = 0; i < N; i++) putc('x', f);
    fflush(f);
    row("В  putc крізь буфер stdio", now() - t, N);

    t = now();
    flockfile(f);
    for (long i = 0; i < N; i++) putc_unlocked('x', f);
    funlockfile(f);
    fflush(f);
    row("Г  putc_unlocked під одним flockfile", now() - t, N);

    t = now();
    for (long i = 0; i < N / BLK; i++)
        if (fwrite(block, 1, BLK, f) != BLK) { perror("fwrite"); return 1; }
    fflush(f);
    row("Д  fwrite блоками по 4096", now() - t, N / BLK);

    fclose(f);
    close(fd);
    return 0;
}
```

Годинник тут не спотворює результату: `clock_gettime(CLOCK_MONOTONIC, …)` у Linux зазвичай узагалі не доходить до ядра — [vDSO](book:unix-linux/vdso) (ядро підсовує кожному процесові крихітну бібліотеку зі своїм кодом, і читання годинника коштує наносекунди замість повноцінного перетину межі). Тому вимірювальний код не додає до підсумку власних системних викликів.

На типовій машині x86-64 виходить приблизно так: А — триста-шістсот мілісекунд, тобто триста-шістсот наносекунд на виклик; Б — за ті самі байти в тисячі разів менше часу, рівно в стільки, у скільки менше стало викликів; В — одиниці мілісекунд; Г — помітно менше за В; Д — майже те саме, що Б.

Кожна пара відповідає на своє питання. **А проти Б** перевіряє головне: ціна не залежить від кількости байтів, залежить від кількости перетинів. **В проти Г** показує ціну замка на структурі `FILE`, який кожен виклик stdio бере, щоб два потоки виконання не поклали свої байти в одне місце. **Д проти В** пояснює, чому в реальному коді пишуть `fwrite` великими шматками, а не по символу: коли запит більший за буфер і буфер порожній, бібліотека віддає його в `write` напряму, не копіюючи через себе.

> 🔧 **Навіщо це.** Найкорисніша пара — А проти В, і вона ж найменш очікувана. Арифметика «мільйон викликів проти двохсот п'ятдесяти шести» обіцяє виграш у тисячі разів, а міряється сотня з чимось. Різницю з'їдає сам буфер: системні виклики він прибирає, але додає власний виклик функції на кожен символ. Плануючи, скільки ви виграєте від буферизації, беріть до уваги друге число, а не перше.

## 2. Та сама двійка, два режими

Тепер найголовніше твердження статей про stdio: режим — не властивість програми. Перевіряється це однією двійкою, запущеною двічі.

```c
/* modes.c — куди веде дескриптор 1, такий і режим */
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    fprintf(stderr, "isatty(1) = %d\n", isatty(STDOUT_FILENO));
    for (int i = 1; i <= 400; i++)
        printf("progress %3d of 400\n", i);
    return 0;
}
```

Кожен рядок тут — рівно 20 байтів (`%3d` завжди займає три позиції), тож усі числа далі можна порахувати наперед.

```bash
$ strace -e trace=write -o tty.txt  ./modes            # вивід на термінал
$ strace -e trace=write -o pipe.txt ./modes | cat      # вивід у канал
$ wc -l tty.txt pipe.txt
```

У `tty.txt` буде близько чотирьохсот викликів по 20 байтів — по одному на рядок. У `pipe.txt` їх два: перший рівно на 4096 байтів (204 повні рядки це 4080, отже 205-й розрізано після шістнадцятого свого байта — саме тому в трасі видно обірваний посередині текст), другий на решту 3904 при виході з `main`. Рядок про `isatty` у `stderr` показує, яку саме відповідь дістала бібліотека в кожному запуску.

Про сам інструмент варто знати одне: [трасування системних викликів](book:unix-linux/syscall-tracing) зупиняє процес на кожному вході в ядро й на кожному виході з нього, друкуючи ім'я виклику та аргументи. Звідси й правило гігієни: під `strace` дивляться, **що** і **якими порціями** сталося, але ніколи не міряють час — трасування дорожчає кожен виклик у десятки разів і всі числа з першого досліду перекручує.

## 3. fork, який подвоює вивід

Буфер stdio живе в пам'яті процесу, а `fork` копіює пам'ять цілком ([fork: розмноження процесу](book:unix-linux/fork-semantics) — дитина дістає власну копію всього адресного простору батька). Отже, недописане подвоюється разом із рештою.

```c
/* twice.c — ./twice зламано, ./twice fix полагоджено */
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(int argc, char **argv)
{
    int fix = (argc > 1 && strcmp(argv[1], "fix") == 0);

    printf("count: %d\n", 42);
    if (fix)
        fflush(stdout);          /* буфер порожній — копіювати нема чого */

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {
        if (fix) _exit(0);       /* дитина не зливає чужого недописаного */
        return 0;                /* а так — зливає свою копію буфера */
    }
    wait(NULL);
    return 0;
}
```

```bash
$ ./twice                 # термінал: один рядок
$ ./twice | cat           # канал: ДВА однакові рядки
$ ./twice fix | cat       # знову один
$ strace -f -e trace=write -o fork.txt ./twice > /dev/null && cat fork.txt
```

Остання команда показує обидва `write` із різними номерами процесів — доказ, що рядок надрукували двічі саме два різні процеси, а не один двічі. Зверніть увагу на `> /dev/null`: це символьний пристрій, але не термінал, тож режим поблоковий і подвоєння відтворюється так само, як у каналі. І на другу половину ліків — `_exit` замість `return` у дитині: він завершує процес, не зачіпаючи потоків stdio, і саме тому його ставлять у дитині, яка йде аварійно.

## 4. «Лише до першої операції»: що саме ламається

Правило відоме — `setvbuf` можна кликати тільки до першої операції над потоком. Цікаве починається, коли його порушити: стандарт каже «невизначена поведінка», а машина показує щось конкретне.

```c
/* late.c — запуск: strace -e trace=write -o late.txt ./late > /dev/null */
#include <stdio.h>

static char mine[64];            /* статичний: мусить пережити потік */

int main(void)
{
    printf("A: already in the buffer\n");

    int r = setvbuf(stdout, NULL, _IOLBF, 64);
    fprintf(stderr, "setvbuf -> %d\n", r);

    printf("B: goes out on the newline\n");

    setvbuf(stdout, mine, _IOFBF, sizeof mine);
    for (int i = 0; i < 8; i++)
        printf("filler line %d\n", i);

    return 0;
}
```

На glibc `setvbuf` поверне нуль, а в трасі перший `write` буде на 52 байти — обидва рядки разом. Читається це так. Прапорець режиму таки перемкнувся: рядок «B» вийшов на своєму переході рядка, а не в кінці програми. Але рядок «A» сам виклик `setvbuf` нікуди не випхнув — він так і чекав у буфері до найближчого приводу. І головне: **числа 64 бібліотека не побачила взагалі**. Довідка формулює це прямо — коли `buf` дорівнює `NULL`, зачеплено лише режим, а буфер буде виділено при наступній операції; у нашому випадку він уже виділений, і його розмір лишається тим, що бібліотека обрала на старті.

Другий виклик — з власною пам'яттю — уже змінює розмір по-справжньому: порції в трасі стають рівно такими, який буфер ви дали. Ціна цієї можливости записана в довідці поруч: пам'ять мусить жити щонайменше стільки, скільки живе потік. Масив на стеку функції, яка налаштувала потік і повернулася, — готова аварія, тому `mine` тут статичний.

І про переносність, бо саме тут ілюзія найнебезпечніша. Терпимість glibc — не гарантія стандарту, а властивість однієї реалізації. У musl `setvbuf` не перевіряє нічого й не зливає нічого: він просто підмінює вказівник на буфер, і рядок «A» на тій самій програмі може зникнути безслідно. Правило «лише до першої операції» — не формальність, а єдиний стан, у якому поведінка однакова всюди.

## 5. Межі stdbuf

Коли джерел нема, режим чужій програмі нав'язують ззовні — `stdbuf`. Механізм видно однією командою, без жодного трасування:

```bash
$ stdbuf -oL env | grep -E '_STDBUF|LD_PRELOAD'
LD_PRELOAD=libstdbuf.so
_STDBUF_O=L
```

`stdbuf` не чаклує: він ставить кілька змінних оточення, додає в `LD_PRELOAD` свою бібліотеку й робить `exec`. Далі спрацьовує [перекриття символів завантажувачем](book:unix-linux/symbol-resolution) (`LD_PRELOAD` змушує динамічний завантажувач підтягнути вказану бібліотеку раніше за всі інші й дати їй виконати свій конструктор). Конструктор `libstdbuf` читає змінну й кличе `setvbuf` — до головної функції програми, тобто в єдиний дозволений момент.

![Ланцюг stdbuf: змінні оточення, LD_PRELOAD, конструктор libstdbuf із setvbuf до main — і дві ситуації, у яких цей ланцюг не діє](/reference/unix-linux/io/stdio-buffering/img/stdbuf-mechanism.svg)

*Важіль дотягується до потоку рівно один раз і рівно в потрібну мить — а далі програма може все переграти або взагалі не мати того, на що він тисне.*

```bash
$ ./modes | cat                        # пачками по 4096
$ stdbuf -oL ./modes | cat             # по рядку, як у терміналі

$ (for i in 1 2 3 4 5; do echo "line $i"; sleep 1; done) | grep line | cat
$ (for i in 1 2 3 4 5; do echo "line $i"; sleep 1; done) | stdbuf -oL grep line | cat
```

Перша пара міняє режим нашій програмі, друга — чужій: `grep` посеред конвеєра теж бачить каналом свій вивід, теж стає поблоковим і теж мовчить п'ять секунд, поки `stdbuf` не втрутиться. А от на `tee`, `dd` і `cat` той самий важіль не діє зовсім, і причини різні. Довідка coreutils наводить `tee` прикладом програми, яка сама налаштовує буферизацію своїх потоків і тим перекриває зроблене ззовні; у нинішніх джерелах `tee` пішов ще далі й переганяє дані парою `read` і `write`, обминаючи stdio цілком. `dd` і `cat` не користуються stdio за задумом — у `dd` розмір порції задає `bs=`, і жодного буфера бібліотеки там просто немає, отже нема чого перемикати.

Лишається обхідний шлях — збрехати програмі про пристрій. `script -qec './modes | tee out.log' /dev/null` виконує конвеєр під [псевдотерміналом](book:unix-linux/pseudo-terminal) (пара пристроїв, де один кінець виглядає для програми справжнім терміналом, а другий читає той, хто його створив). Тоді `isatty` каже «так», і бібліотека сама, без жодних змінних оточення, обирає порядковий режим.

## Де лабораторія спотикається

**Термінал, який не термінал.** Консоль редактора, панель складання, журнал системи неперервної інтеграції — це канали, а не tty. Запустивши досліди там, ви щоразу дістанете поблоковий режим і вирішите, що програма зламана. Рядок `isatty(1)` у `modes` існує саме для того, щоб це побачити першим, а не останнім.

**Інша бібліотека — інші числа.** На Alpine з musl типовий буфер удвічі менший: `BUFSIZ` там 1024, і в трасі ви побачите порції по 1024 замість 4096. У glibc розмір береться з `st_blksize` файлової системи, обмеженого зверху вісьмома кілобайтами, тож на ext4 виходить 4096, а на мережевій ФС може вийти інше число.

**`strace` не всюди дозволений.** У контейнерах трасування типово вимкнене — потрібна можливість `SYS_PTRACE`; на системах із Yama значення `/proc/sys/kernel/yama/ptrace_scope` обмежує приєднання до вже запущених процесів (запуск дитини під трасувальником зазвичай лишається дозволеним).

**Оптимізатор трохи міняє картину.** З `-O2` компілятор перетворює `printf` зі сталим форматом без аргументів на `puts` — на буферизацію це не впливає ніяк, але в трасі ви не знайдете жодної згадки про `printf`, бо на рівні системних викликів її ніколи там і не було: назовні видно лише `write`.
