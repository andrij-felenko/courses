# 📋 Ядерний інтерфейс nvmet: структури nvmet_req, nvmet_fabrics_ops та бекенд-операції

Підсистема `nvmet` у ядрі Linux побудована на чіткому розділенні функціональних обов'язків між мережевими транспортиами, центральним диспетчером команд та бекендами зберігання. Для цього ядро визначає набір внутрішніх C-структур та таблиць зворотних викликів (callback tables) у заголовних файлах вихідного коду ядра `drivers/nvme/target/nvmet.h`.

Оскільки `nvmet` є внутрішньоядерним модулем (Kernel Subsystem), цей інтерфейс виконується виключно в просторі ядра (Kernel Space). Розуміння цих структур необхідне для розробки нових мережевих транспортів (наприклад, для експериментальних мережевих протоколів або апаратних акселераторів DPU/SmartNIC) та створення власного бекенду зберігання даних (наприклад, для розподілених файлових систем чи об'єктних сховищ).

## 1. Головна контекстна структура: struct nvmet_req

Об'єкт `struct nvmet_req` представляє одну I/O або Admin команду NVMe, що перебуває в процесі виконання цільовою системою. Ця структура виділяється зі спеціалізованого пулу кешу ядра (slab cache `nvmet_req_cache`) для кожної прибулої капсули і супроводжує її від моменту вилучення з мережевого сокета до відправки підтвердження (CQE).

```c
/* Витяг із вихідного коду ядра Linux: drivers/nvme/target/nvmet.h */
struct nvmet_req {
    struct nvme_command    *cmd;          /* Вказівник на сиру 64-байтову NVMe-команду з капсули */
    struct nvme_completion *cqe;          /* Елемент черги завершення (CQE), що повертається */
    struct nvmet_sq        *sq;           /* Submission Queue, з якої прийшла команда */
    struct nvmet_cq        *cq;           /* Completion Queue для відправки відповіді */
    struct nvmet_ns        *ns;           /* NVMe Namespace, до якого адресована команда */
    struct nvmet_port      *port;         /* Фізичний або логічний порт прийому */
    
    struct scatterlist     *sg;           /* SGL-список сторінок пам'яті для даних */
    int                    sg_cnt;        /* Кількість елементів у SGL-списку */
    size_t                 data_len;      /* Загальний розмір буфера даних у байтах */
    size_t                 metadata_len;  /* Розмір метаданих (якщо підтримуються) */
    
    void (*execute)(struct nvmet_req *req); /* Функція виконання команди бекендом */
    
    struct bio             inline_bio;    /* Вбудований bio для уникнення kmalloc на fast-path */
    struct bio             *bio;          /* Вказівник на ланцюжок bio для підсистеми blk-mq */
    
    u16                    error_loc;     /* Зсув поля команди, що спричинило помилку */
    u16                    status;        /* Статус виконання (NVMe status code) */
};
```

### Детальний аналіз полів та життєвого циклу

- **`cmd` та `cqe`:** Поле `cmd` вказує на 64-байтовий блок команди NVMe (наприклад, `struct nvme_rw_command` або `struct nvme_identify_command`), розпакований з мережевої капсули. Поле `cqe` вказує на 16-байтову структуру відповіді, де підсистема `nvmet` формує статус виконання (`status`), результат виконання та ідентифікатор команди (`command_id`).
- **`sq` та `cq`:** Посилання на об'єкти черг надсилання та завершення. Кожна черга `nvmet_sq` прив'язана до конкретного контексту контролера `struct nvmet_ctrl`, що забезпечує беззамкову ідентифікацію сесії.
- **`sg` та `sg_cnt`:** Описують фізичні сторінки оперативної пам'яті цілі (Scatter-Gather List). При операціях читання бекенд заповнює ці сторінки даними з носія, після чого транспорт надсилає їх у мережу. При операціях запису транспорт спочатку отримує дані з мережі у ці сторінки, після чого викликає колбек `execute`.
- **`inline_bio` та `bio`:** Оптимізація підсистеми `blk-mq` для малого I/O. Якщо розмір операції введення-виведення не перевищує розмір вбудованої структури (зазвичай 4 КБ), ядро використовує об'єкт `inline_bio`, розміщений безпосередньо в `struct nvmet_req`. Це повністю усуває динамічні виклики `kmalloc()` або `bio_alloc()` на гарячому шляху виконання (Fast-Path). Для великих запитів виділяється додатковий ланцюжок `struct bio`.
- **`execute`:** Вказівник на конкретну функцію обробки бекенду (`nvmet_bdev_execute_rw`, `nvmet_file_execute_rw` або `nvmet_passthru_execute_cmd`), що ініціалізує фактичну роботу з носієм.

## 2. Інтерфейс мережевих транспортів: struct nvmet_fabrics_ops

Кожен мережевий транспорт (`nvmet-tcp`, `nvmet-rdma`, `nvmet-fc`, `nvmet-loop`) реєструється у центральному ядрі за допомогою структури `struct nvmet_fabrics_ops`. Ця структура визначає спосіб взаємодії ядра NVMe Target з конкретним мережевим стеком.

```c
/* Витяг із вихідного коду ядра Linux: drivers/nvme/target/nvmet.h */
struct nvmet_fabrics_ops {
    struct module       *owner;
    u8                  type;             /* Тип транспорту: NVMF_TRTYPE_TCP, NVMF_TRTYPE_RDMA тощо */
    u32                 msdbd;            /* Maximum SGL Data Blocks Descriptor */
    bool                has_ip_endpoints; /* Прапор використання IP-адрес (TCP/RDMA) */
    
    int (*add_port)(struct nvmet_port *port);
    void (*remove_port)(struct nvmet_port *port);
    
    void (*queue_response)(struct nvmet_req *req);
    void (*delete_ctrl)(struct nvmet_ctrl *ctrl);
    void (*disc_add)(struct nvmet_port *port, struct nvmf_disc_rsp_page_hdr *hdr);
};
```

### Семантика зворотних викликів транспортного рівня

1. **`add_port(port)` / `remove_port(port)`:** Викликаються підсистемою `configfs` при прив'язці або відв'язці мережевого порту. Наприклад, для `nvmet-tcp` функція `add_port` створює сокет ядра (`struct socket`), прив'язує його до вказаного IP та TCP-порту (за замовчуванням 4420) і реєструє обробник подій прийому даних `sk_data_ready`.
2. **`queue_response(req)`:** Головна асинхронна функція завершення I/O. Коли бекенд завершив виконання читання чи запису, ядро викликає `queue_response`. Транспортний модуль формує відповідний кадр (Response PDU для TCP або RDMA Send Work Request) і надсилає його мережевому ініціатору.
3. **`delete_ctrl(ctrl)`:** Очищає мережеві ресурси та закриває з'єднання при припиненні сесії ініціатором або виникненні таймауту Keep-Alive.
4. **`disc_add(port, hdr)`:** Заповнює записи сторінки виявлення (Discovery Log Page). Це дозволяє віддаленим ініціаторам під час виконання команди `nvme discover` автоідентифікувати доступні транспорти, NQN та мережеві адреси цілі.

## 3. Інтерфейс бекендів зберігання: struct nvmet_type_ops

Усі бекенди зберігання зареєстровані як типи обробників команд підсистеми `nvmet`:

```c
/* Витяг із вихідного коду ядра Linux: drivers/nvme/target/nvmet.h */
struct nvmet_type_ops {
    struct module   *owner;
    u8              type;                 /* NVMET_ASYNC_BDEV_OPT, NVMET_FILEIO_OPT тощо */
    
    int (*connect)(struct nvmet_ctrl *ctrl, struct nvmet_ns *ns);
    void (*disconnect)(struct nvmet_ctrl *ctrl, struct nvmet_ns *ns);
    
    void (*flush)(struct nvmet_req *req);
    void (*rw)(struct nvmet_req *req);
    int (*identify)(struct nvmet_req *req);
};
```

### Функціонал методів бекенду

- **`connect` / `disconnect`:** Виклики ініціалізації та деініціалізації простору імен для конкретного контролера (наприклад, відкриття блокового пристрою `blkdev_get_by_path()` для `bdev` або файлу `filp_open()` для `file`).
- **`rw`:** Призначає асинхронні обробники виконання операцій читання та запису. Для бекенду `bdev` сформований об'єкт `struct bio` передається у підсистему `blk-mq` через функцію `submit_bio()`, забезпечуючи беззамкову асинхронну передачу запиту.
- **`flush`:** Організовує синхронізацію буферів носія. Для блокового бекенду генерує запит з прапорами `REQ_PREFLUSH | REQ_FUA`, а для файлового — викликає `vfs_fsync()`.
- **`identify`:** Динамічно заповнює 4096-байтову структуру даних `struct nvme_id_ns` (Identify Namespace Data Structure), повертаючи ініціатору розмір простору імен, розмір LBA-сектора та підтримувані апаратні функції.

## 4. Коди статусів NVMe (NVMe Status Codes)

При ініціалізації та виконанні запиту `nvmet_req` заповнює поле `status` 16-бітним значенням відповідно до специфікації NVMe. Старші біти визначають тип помилки (Command Specific Status, Data Transfer Error, Media and Data Integrity Errors), а молодші біти — конкретну причину.

| Константа ядра Linux | Значення (HEX) | Опис та сценарій виникнення |
| :--- | :--- | :--- |
| `NVME_SC_SUCCESS` | `0x0000` | Успішне виконання команди бекендом без помилок |
| `NVME_SC_INVALID_OPCODE` | `0x0001` | Непідтримуваний Opcode (наприклад, спроба виконання Admin-команди на I/O черзі) |
| `NVME_SC_INVALID_FIELD` | `0x0002` | Некоректне значення поля у команді або невалідний список SGL-дескрипторів |
| `NVME_SC_DATA_XFER_ERROR` | `0x0005` | Помилка мережевого перенесення даних (таймаут TCP-сокета або розрив RDMA-сесії) |
| `NVME_SC_INTERNAL` | `0x0006` | Внутрішня помилка ядра (відмова виділення пам'яті або збій бекенду диска) |
| `NVME_SC_INVALID_NS` | `0x000B` | Вказаний Namespace ID не існує, вимкнений або не прив'язаний до підсистеми |
| `NVME_SC_BAD_ATTRIBUTES` | `0x0180` | Невідповідні атрибути при Connect (невідповідність Host NQN або версії протоколу) |

## 5. Процедура ініціалізації та асинхронного завершення

Коли мережевий транспортний модуль отримує кадр з NVMe-капсулою, ядро виконує наступну послідовність викликів внутрішньоядерних функцій:

```c
/* Витяг із вихідного коду ядра Linux: drivers/nvme/target/nvmet.h */

/* 1. Ініціалізація структури запиту з перевіркою валідності */
bool nvmet_req_init(struct nvmet_req *req, struct nvmet_cq *cq,
                    struct nvmet_sq *sq, const struct nvmet_fabrics_ops *ops);

/* 2. Диспетчеризація команд встановлення сесії та авторизації */
void nvmet_parse_connect_cmd(struct nvmet_req *req);
void nvmet_execute_admin_connect(struct nvmet_req *req);
void nvmet_execute_io_connect(struct nvmet_req *req);

/* 3. Асинхронне завершення запиту після виконання I/O */
void nvmet_req_complete(struct nvmet_req *req, u16 status);
```

Послідовність роботи ядра:
1. `nvmet_req_init()` розбирає заголовок прибулої капсули, звіряє ID простору імен `nsid` і призначає відповідні процедури обробки.
2. Якщо команда є мережевою фабричною командою (Fabrics Command), викликається `nvmet_parse_connect_cmd()`, яка перевіряє права доступу ініціатора та валідує NQN.
3. Після завершення читання/запису дисковим бекендом викликається `nvmet_req_complete()`. Вона записує підсумковий статус у 16-байтову структуру CQE і передає запит у метод транспорту `ops->queue_response(req)`. Якщо операція завершилася з помилкою, `nvmet_req_complete()` заповнює поле `error_loc`, вказуючи байтовий зсув у команді ініціатора, що спричинив відмову.
