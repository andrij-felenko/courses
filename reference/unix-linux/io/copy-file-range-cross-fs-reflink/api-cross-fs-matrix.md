# 📋 Матриця технологій копіювання та клонування даних у файлових системах Linux

Ця довідкова вставка містить системну порівняльну матрицю системних викликів, інтерфейсів Віртуальної файлової системи (VFS), апаратних технологій та мережевих протоколів offload для копіювання діапазонів файлів у середовищі операційних систем Linux та POSIX. Таблиці та технічні розділи розкривають межі застосування, вимоги до операндів, гарантії атомарності, поведінку при перетині файлових систем (Cross-FS) та специфічні коди помилок `errno`.

## Порівняння системних інтерфейсів копіювання

У системному програмуванні для операційної системи Linux існує кілька ключових механізмів передачі та дублювання байтів між файловими дескрипторами. Кожен інтерфейс володіє власною семантикою, вимогами до типів операндів, рівнем навантаження на системний процесор та пам'ять, а також суворими межами застосування при перетині пристроїв сховища.

При виборі технології копіювання розробник системного ПЗ повинен враховувати не лише теоретичну швидкість виконання операції, але й гарантії атомарності, вплив на кеш сторінок ядра та поведінку системи при раптових відмовах живлення. Виклик Reflink гарантує атомарне збереження стану, тоді як потокові фолбеки через `splice` або буфери користувацького простору виконують копіювання фрагментами, залишаючи цільовий файл у частково заповненому стані у разі виникнення помилки або переривання процесу.

Для досягнення оптимального балансу між надійністю та продуктивністю рекомендується завжди надавати перевагу декларативним системним викликам ядра перед вручну написаними циклами буферизованого читання.

Нижче наведено порівняльну специфікацію основних викликів ядра Linux, які застосовуються для копіювання даних.

| Механізм | Системний виклик / `ioctl` | Межі застосування (Scope) | Механізм переміщення байтів | Атомарність та CoW | Вплив на CPU та DRAM |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Reflink Cloning** | `ioctl(fd_out, FICLONE, fd_in)` / `FICLONERANGE` | Лише у межах **одного екземпляра ФС** (`sb_in == sb_out`) | Модифікація B-дерева екстентів та інкремент `refcount` | Повна атомарність. Строгий Copy-on-Write | CPU: ~0%<br>DRAM: 0 B |
| **copy_file_range** | `copy_file_range(fd_in, off_in, fd_out, off_out, len, 0)` | Intra-FS, **Cross-FS**, Cross-Mount, Network SSC | Каскадний offload (Reflink → Driver Hook → Block Offload → Splice) | Атомарно при Reflink; прогресивне копіювання при fallback | Від 0% (offload) до високого (splice fallback) |
| **Zero-Copy Pipe Splice** | `splice(fd_in, off_in, pipe, NULL, len, flags)` + `splice(pipe, NULL, fd_out, ...)` | Будь-які дискові файли, сокети, безадресні канали | Транзит сторінок Page Cache через буфер `pipe` у ядрі | Неатомарне прогресивне копіювання | CPU: середня (робота зі сторінками пам'яті ядра)<br>DRAM: без User Space |
| **User Space Loop** | `read(fd_in, buf, len)` + `write(fd_out, buf, len)` | Універсально для всіх типів файлів та пристроїв | Копіювання сторінок через буфер прикладного процесу | Неатомарне прогресивне копіювання | CPU: високе (перемикання контексту)<br>DRAM: подвійне прокачування |

## Матриця поведінки при перетині меж сховища (Cross-Boundary Matrix)

Поведінка системних викликів змінюється залежно від того, де фізично та логічно розташовані файли-операнди — у межах однієї файлової системи, між сабтомами, між різними дисками чи у віддалених мережевих ресурсах.

Особливу увагу слід приділяти поведінці в середовищах із віртуалізованими томами LVM, файловими системами OverlayFS та мережевими експортами NFS. У таких конфігураціях файли можуть зовні виглядати розташованими в єдиному дереві каталогів, але мати різні вказівники на `super_block` ядра, що робить операцію Reflink неможливою.

| Сценарій розташування файлів | `FICLONE` (`ioctl`) | `copy_file_range` (Linux 4.5–5.2) | `copy_file_range` (Linux 5.3–5.17) | `copy_file_range` (Linux 5.18+) |
| :--- | :--- | :--- | :--- | :--- |
| **Одна ФС, один томи (Same Superblock)** | Успіх (Reflink CoW) | Успіх (Reflink CoW) | Успіх (Reflink CoW) | Успіх (Reflink CoW) |
| **Різні сабволюми Btrfs одного пулу** | Успіх (Спільне B-дерево) | Успіх (Reflink CoW) | Успіх (Reflink CoW) | Успіх (Reflink CoW) |
| **Різні пули Btrfs / моунт-поінти XFS** | Помилка `EXDEV` | Помилка `EXDEV` | Авто-фолбек на In-Kernel Splice | Оптимізований каскад offload / Splice |
| **З Btrfs/XFS на Ext4 (Cross-FS)** | Помилка `EXDEV` | Помилка `EXDEV` | Авто-фолбек на In-Kernel Splice | Апаратний Block Offload або Splice |
| **Різні ресурси NFS v4.2 одного сервера** | Помилка `EXDEV` | Помилка `EXDEV` | Server-Side Copy (RPC `COPY`) | Server-Side Copy (RPC `COPY` / `CLONE`) |
| **Мережеві ресурси SMB3 (CIFS)** | Помилка `EXDEV` | Помилка `EXDEV` | Server-Side Copy (`COPYCHUNK`) | Server-Side Copy (`COPYCHUNK`) |

## Сигнатури функцій ядра та структура file_operations

Маршрутизація виклику `copy_file_range` здійснюється через таблицю вказівників на функції відповідного драйвера файлової системи у ядрі Linux.

```c
// Сигнатури функцій у структурі file_operations (include/linux/fs.h)
struct file_operations {
    // Вказівник на специфічну реалізацію copy_file_range у драйвері ФС
    ssize_t (*copy_file_range)(struct file *file_in, loff_t pos_in,
                               struct file *file_out, loff_t pos_out,
                               size_t len, unsigned int flags);

    // Вказівник на реалізацію Reflink / CoW клонування екстентів
    loff_t (*remap_file_range)(struct file *file_in, loff_t pos_in,
                               struct file *file_out, loff_t pos_out,
                               loff_t len, unsigned int remap_flags,
                               struct inode_pair *idmap);

    // Вказівники на потоковий splice
    ssize_t (*splice_read)(struct file *in, loff_t *ppos,
                           struct pipe_inode_info *pipe, size_t len,
                           unsigned int flags);
    ssize_t (*splice_write)(struct pipe_inode_info *pipe, struct file *out,
                            loff_t *ppos, size_t len, unsigned int flags);
};
```

При отриманні виклику `copy_file_range` ядро VFS перевіряє наявність реалізації `file_in->f_op->copy_file_range`. Якщо вказівник дорівнює `NULL`, VFS виконує перехід на `generic_copy_file_range()`, яка використовує `splice_read` та `splice_write`.

У реалізації драйвера XFS вказівник `remap_file_range` посилається на функцію `xfs_file_remap_range()`, яка обробляє додаткові прапорці `REMAP_FILE_EXCL` (вимога повернення помилки у разі неможливості CoW) та `REMAP_FILE_CAN_SHORTEN` (дозвіл часткового клонування діапазону).

## Специфікація ioctl FICLONERANGE та структури file_clone_range

Для вибіркового клонування окремих діапазонів файлу у межах однієї файлової системи застосовується виклик `ioctl(fd_out, FICLONERANGE, &range)`.

```c
// Структура для ioctl(FICLONERANGE) у linux/fs.h
struct file_clone_range {
    __s64 src_fd;       // Файловий дескриптор джерела
    __u64 src_offset;   // Початкове зміщення джерела у байтах
    __u64 src_length;   // Довжина діапазону клонування у байтах (0 = до EOF)
    __u64 dest_offset;  // Початкове зміщення цільового файлу у байтах
};
```

Операнд `src_fd` передається як 64-бітне ціле число. Зміщення `src_offset`, `dest_offset` та довжина `src_length` мають бути кратними розміру логічного блоку файлової системи (типово 4096 байтів). Якщо довжина не є кратною розміру блоку, клонування допускається лише у разі, якщо `src_offset + src_length` досягає точного кінця файлу джерела (`EOF`).

## Перевірки безпеки та прав доступу VFS (Security Checks)

Перш ніж передати запит системного виклику `copy_file_range` драйверу файлової системи або запустити фолбек, VFS виконує серію обов'язкових перевірок прав доступу:

1. **Перевірка прав файлового дескриптора**: Вхідний файл `file_in` має бути відкритий із правами на зчитування (прапорець `FMODE_READ`), а вихідний `file_out` — із правами на запис (прапорець `FMODE_WRITE`).
2. **Типізація файлів**: Обидва дескриптори мають вказувати на звичайні дискові файли (`S_ISREG`). Якщо будь-який операнд є каталогом, символьним пристроєм або сокетом, VFS повертає `EISDIR` або `EINVAL`.
3. **Модулі безпеки LSM (Linux Security Modules)**: Функція VFS викликає `security_file_permission(file_in, MAY_READ)` та `security_file_permission(file_out, MAY_WRITE)`. Модулі SELinux або AppArmor перевіряють контексти безпеки процесів.
4. **Перевірка режиму O_APPEND**: Якщо цільовий файл відкрито з прапорцем `O_APPEND`, VFS забороняє виклик `copy_file_range` з кодом `EBADF`, оскільки залучення фіксованого зміщення `off_out` суперечить семантиці допису в кінець файлу.
5. **Файлові блокування POSIX**: Якщо на якийсь із файлів накладено жорстке блокування запису або читання (`flock` / `fcntl` із прапорцем `MANDATORY_LOCK`), VFS виконує виклик `locks_verify_truncate()` для захисту від конфліктів паралельного доступу.

Окрім того, VFS перевіряє право процесів на запис у файл за допомогою функції `rw_verify_area()`. Ця функція контролює, що записуваний діапазон не перетинає обмеження розміру файлу процесу (Resource Limit `RLIMIT_FSIZE`). Якщо запит перевищує поріг `RLIMIT_FSIZE`, ядро надсилає процесу сигнал `SIGXFSZ` та повертає помилку `EFBIG`.

## Детальна матриця кодів помилок `errno`

При роботі з `copy_file_range` та `FICLONE` у разі неможливості виконання операції або спроби виходу за межі файлової системи ядро повертає `-1` та встановлює відповідний код у змінній `errno`.

| Код помилки `errno` | Числовий код (x86_64) | Джерело виклику | Причина виникнення у контексті Cross-FS | Спосіб обробки у прикладному коді |
| :--- | :--- | :--- | :--- | :--- |
| `EXDEV` | 18 | `FICLONE`, `copy_file_range` (Linux < 5.3) | Спроба клонування екстентів між різними екземплярами `super_block` | Перейти на виклик `copy_file_range` або `splice` |
| `EOPNOTSUPP` / `ENOTTY` | 95 / 25 | `FICLONE`, `copy_file_range` | Файлова система або драйвер носія не підтримують CoW чи offload | Виконати фолбек на потоковий `splice` або `read/write` |
| `EINVAL` | 22 | `copy_file_range` | Файли відкриті з `O_APPEND`, перекриття діапазонів в одному файлі, або непідтримувані прапорці | Валідувати аргументи зміщення та режим відкриття файлів |
| `ETXTBSY` | 26 | `copy_file_range` | Цільовий файл є виконуваним файлом, який наразі виконується ядром | Завершити процес або копіювати у тимчасовий файл |
| `EBADF` | 9 | `copy_file_range` | Вхідний файл не відкритий на читання (`O_RDONLY`), або вихідний — на запис (`O_WRONLY`) | Перевірити прапорці `open(2)` при створенні дескрипторів |
| `ENOSPC` | 28 | `copy_file_range` | На цільовому дисковому томі недостатньо вільного місця для виділення нових блоків | Звільнити місце на цільовому томі сховища |
| `EFBIG` | 27 | `copy_file_range` | Спроба копіювання перевищує максимально допустимий розмір файлу для даної ФС | Обрізати довжину передачі або зміщення |
| `EIO` | 5 | `copy_file_range` | Фізична помилка зчитування або запису сектора на накопичувачі | Зафіксувати апаратний збій накопичувача |
| `ENOMEM` | 12 | `copy_file_range` | Нестача оперативної пам'яті ядра для виділення буферів сторінок Page Cache | Зменшити розмір чанка передачі даних у виклику |
| `EINTR` | 4 | `copy_file_range` | Системний виклик перервано асинхронним сигналом до завершення операції | Повторити виклик у циклі з оновленими зміщеннями |

Для правильної відладки системного коду розробникам рекомендується звертати увагу на різницю між кодами `EOPNOTSUPP` та `ENOTTY`. Код `ENOTTY` (*Inappropriate ioctl for device*) повертається шаром VFS тоді, коли драйвер файлової системи взагалі не підтримує обробку ioctl-команд `FICLONE`. У той же час код `EOPNOTSUPP` повернутий безпосередньо драйвером (наприклад, Ext4 без прапорця CoW), показуючи, що сам ioctl відомий, але дана файлова система не володіє функціоналом клонування метаданих.

## Правила вирівнювання операндів та режими введення-виведення

Залежно від режимів відкриття файлових дескрипторів та типів накопичувачів VFS вимагає дотримання суворих правил вирівнювання за адресами пам'яті та дисковими секторами.

### 1. Вирівнювання для буферизованого введення-виведення (Buffered I/O)
При копіюванні буферизованих файлів (`O_RDONLY` / `O_WRONLY` без `O_DIRECT`) ядро Linux дозволяє довільне вирівнювання зміщень `off_in`, `off_out` та довжини `len` з точністю до 1 байта. Проте якщо файлова система підтримує Reflink (`remap_file_range`), часткові блоки на межах діапазонів не можуть бути заклоновані через CoW і переносяться ядром шляхом звичайного виділення нових блоків та копіювання байтів (Block Splitting).

### 2. Вирівнювання для прямого введення-виведення (O_DIRECT)
Якщо хоча б один із дескрипторів відкрито з прапорцем `O_DIRECT`, діють наступні правила:
- **Логічний сектор (LBA Sector)**: Зміщення `off_in`, `off_out` та довжина `len` мають бути кратними 512 байтам (для традиційних секторів) або 4096 байтам (для секторів Advanced Format 4Kn).
- **Виклик апаратного offload**: Якщо невирівняний виклик відправляється контролеру NVMe або SCSI, драйвер блочного шару ядра повертає помилку `EINVAL`. Ядро VFS перехоплює `EINVAL` і здійснює тимчасовий перехід на сторінкове копіювання через Page Cache.

## Технічна специфікація апаратних та протокольних механізмів Offload

Нижче деталізовано специфікації апаратних прискорень та мережевих протоколів, які викликаються ядром Linux під час виконання системного виклику `copy_file_range`.

### 1. NVMe Simple Copy Command (NVM Express TP 4040)
- **Підсистема ядра**: Блочний шар Linux (`block/blk-lib.c`, `blkdev_issue_copy`).
- **Специфікація стандарту**: NVM Express TP 4040 / NVMe 2.0 Command Set.
- **Вимоги до операндів**: Джерело і ціль повинні знаходитися у межах одного NVMe Namespace. Зміщення та довжина мають бути кратними розміру логічного сектора LBA (512B або 4096B).
- **Структура команди**: Команда NVMe Simple Copy містить `CDW10`–`CDW15`, що визначають початковий LBA (Starting LBA, SLBA), кількість блоків (Number of Logical Blocks, NLB) та масив Source Range Entries (до 256 діапазонів джерела).
- **Принцип роботи**: Контролер SSD зчитує блоки з осередків NAND-пам'яті у внутрішній буфер SRAM контролера та відразу переміщує їх за цільовими LBA-адресами.
- **Пропускна здатність**: Від 5 до 8 Гігобайт/сек без транзиту даних через системну шину PCIe та без використання системної оперативно пам'яті (DRAM) комп'ютера.

### 2. SCSI EXTENDED COPY / XCOPY (SPC-4 / SBC-3)
- **Підсистема ядра**: Драйвер SCSI-шару (`drivers/scsi/sd.c`).
- **Специфікація стандарту**: ANSI INCITS SCSI Primary Commands - 4 (SPC-4).
- **Вимоги до операндів**: Файли повинні належати томам, що обслуговуються одним контролером дискового масиву SAN (Storage Area Network).
- **Структура команди**: Хост відправляє команду `EXTENDED COPY (LIR=1)` з переліком Target/Source Segment Descriptors. Дескриптор містить ідентифікатори NAA IEEE Registered Extended LUN та блоки LBA.
- **Принцип роботи**: Масив сховища виконує передачу блоків всередині своєї дискової фабрики.

### 3. NFS v4.2 Server-Side Copy (RFC 7862)
- **Підсистема ядра**: Мережевий драйвер NFS (`fs/nfs/nfs4file.c`).
- **Специфікація стандарту**: IETF RFC 7862 (NFS Version 4 Minor Version 2).
- **Типи RPC-операцій**:
  - `COPY`: Послідовне копіювання блоків на боці NFS-сервера без транзиту мережею.
  - `CLONE`: Миттєве клонування екстентів на боці сервера (активується, якщо серверна ФС — Btrfs/XFS/ZFS).
- **Cross-Mount підтримка**: Якщо клієнт монтує два різні експорти з одного сервера (`/mnt/export1` та `/mnt/export2`), виклик `copy_file_range` виконує SSC через внутрішній серверний масив.

### 4. SMB3 / CIFS CopyChunk (MS-SMB2)
- **Підсистема ядра**: Драйвер мережевої ФС `cifs.ko` (`fs/cifs/cifsfs.c`).
- **Специфікація стандарту**: Microsoft Server Message Block Protocol 3.0+.
- **Керуючий IOCTL**: `FSCTL_SRV_COPYCHUNK` або `FSCTL_SRV_COPYCHUNK_WRITE`.
- **Обмеження розміру**: Копіювання виконується чанками (типово до 1 Мігабайта або 16 Мігабайт за один запит). Клієнтський драйвер ядра Linux розбиває великий виклик `copy_file_range` на серію послідовних запитів `COPYCHUNK`.
