# 📜 Хронологія розвитку та архітектурні дебати Cross-FS у ядрі Linux

Еволюція механізмів копіювання даних у ядрі Linux пройшла шлях від створення перших системних викликів `sendfile` та `splice` до суперечливих архітектурних рішень довкола системного виклику `copy_file_range(2)` у версіях ядра 4.5, 5.3 та 5.18+. Тривала боротьба між концепціями «суворих помилок» та «прозорої емуляції ядра» остаточно сформувала сучасний підхід підсистеми VFS до offload та клонування даних між різними файловими системами.

## Епоха класичного POSIX та перші спроби Offload (1990–2010)

У ранніх версіях ядра Linux та стандарті POSIX 1003.1 єдиним можливим способом скопіювати вміст файлу A у файл B був послідовний цикл зчитування та запису через буфер у користувацькому просторі:

```
[Диск A] ──> Page Cache ──> User Buffer ──> Page Cache ──> [Диск B]
```

Цей підхід змушував центральний процесор виконувати мільйони перемикань контекстів між режимом користувача та режимом ядра (User/Kernel Context Switch) та двічі прокачувати кожен байт даних через системну оперативну пам'ять (DRAM), створюючи критичне вузьке місце у пропускній здатності системної шини пам'яті.

У ядрі Linux 2.2 z'явився системний виклик `sendfile(2)`, розроблений для прискорення високопродуктивних вебсерверів (зокрема Apache HTTPD). Він дозволяв копіювати дані з дискового файлу безпосередньо у сокет мережевої карти без копіювання у буфер користувача. Однак `sendfile` мав жорстке обмеження: він вимагав, щоб вихідний дескриптор обов'язково був сокетом, і не підтримував копіювання між двома звичайними дисковими файлами.

У ядрі Linux 2.6.17 (червень 2006 року) Єнс Аксбое (Jens Axboe) створив та реалізував системні виклики `splice(2)` та `vmsplice(2)`, побудувавши їх на основі концепції буфера каналу (pipe buffer, `pipe_inode_info`), яку запропонував Лінус Торвальдс. Завдяки цьому прикладні програми отримали можливість створювати довільні ланцюжки копіювання всередині ядра. Незважаючи на усунення перемикання контекстів користувача, `splice` вимагав наявності принаймні одного безадресного каналу `pipe` як проміжної ланки і все одно виконував фізичне прокачування кожної сторінки через оперативну пам'ять (DRAM).

Паралельно у світі UNIX розроблялися інші підходи: в операційній системі Solaris з'явився виклик `sendfilev`, а в macOS (BSD) — системна функція `fcopyfile(3)`. Проте в Linux універсального інтерфейсу для дискових файлів не існувало до появі Copy-on-Write файлових систем.

## Поява `copy_file_range` та ера суворого `EXDEV` (Linux 4.5, 2016)

З поширенням Copy-on-Write файлових систем (Btrfs, ZFS) та апаратних дискових масивів SAN виникла потреба передавати дескрипторам команду декларативного клонування: «зроби так, щоб цільовий файл отримав ті самі дані, що й файл-джерело, найшвидшим можливим способом».

У березні 2016 року у ядрі Linux 4.5 розробник Анна Шумейкер (Anna Schumaker) із компанії NetApp впровадила системний виклик `copy_file_range(2)`. Початковою метою виклику була реалізація специфікації Server-Side Copy (SSC) для мережевої файлової системи NFS v4.2 (RFC 7862).

У версіях ядра Linux 4.5–5.2 реалізація `copy_file_range` мала сувору архітектурну межу:
- Якщо обидва файли знаходилися у межах **однакового екземпляра файлової системи** (`file_inode(file_in)->i_sb == file_inode(file_out)->i_sb`), ядро викликало внутрішній хук файлової системи (Reflink в Btrfs/XFS або NFS SSC).
- Якщо файли знаходилися на **різних файлових системах чи моунт-поінтах** (`sb_in != sb_out`), ядро негайно відхиляло запит і повертало помилку `EXDEV` (*Invalid cross-device link*).

Така семантика змушувала прикладне програмне забезпечення (і системну бібліотеку `glibc`) вручну перехоплювати код `EXDEV` і переходити на звичайне копіювання через `splice` або `read`/`write`.

## Суперечки в glibc довкола емуляції у User Space (2018–2020)

Додаткова суперечка виникла на рівні системної бібліотеки `glibc`. Обгортка `copy_file_range()` з'явилася у `glibc 2.27` (лютий 2018 року). Для підтримки старих ядер Linux розробники `glibc` додали внутрішній фолбек у користувацькому просторі: якщо системний виклик повертав `ENOSYS` або `EXDEV`, бібліотека `glibc` непомітно для розробника запускала свій внутрішній цикл `read`/`write`.

Ця емуляція призвела до серйозних проблем:
1. **Випереджвальні стани (Race Conditions)**: Емуляція у `glibc` не була атомарною і порушувала файлові блокування `flock`/`fcntl`, встановлені іншими потоками.
2. **Непередбачувані зсуви каретки**: Якщо процес передавав `off_in == NULL`, емуляція `glibc` змінювала позицію файлової каретки через `read`, навіть якщо сам системний виклик у ядрі мав завершитися з помилкою.

У версії `glibc 2.31` (лютий 2020 року) після численних скарг розробників баз даних емуляцію у `glibc` було повністю вилучено. З того часу `glibc` надає тонку обгортку над системним викликом ядра без жодної прихованої емуляції.

## Велика реформа ядра 5.3 та суперечки довкола прозорого фолбеку (2019)

У ядрі Linux 5.3 (вересень 2019 року) підсистема VFS зазнала радикальних змін. Розробники вирішили зробити `copy_file_range` «універсальним» викликом, який ніколи не повинен повертати `EXDEV` для звичайних файлів.

У функцію `generic_copy_file_range()` було додано автоматичний VFS-фолбек: якщо файлові системи відрізнялися (`sb_in != sb_out`), ядро не повертало `EXDEV`, а прозоро запускало внутрішнє копіювання сторінок через `splice_direct_to_actor()`.

Це рішення спростило життя розробникам високорівневих мов програмування, але створило серйозні проблеми у системній інфраструктурі:

1. **Ілюзія швидкого копіювання**: Прикладний код очікував, що `copy_file_range` завершується миттєво (як Reflink). Замість цього при копіюванні 100-гігабайтного файлу між різними дисками системний виклик непомітно блокував потік на хвилини, інтенсивно вимиваючи кеш сторінок (Page Cache) ядра.
2. **Пастки у контейнерах OverlayFS**: У середовищах Docker та Kubernetes файлова система OverlayFS об'єднує нижні шари (Lowerdir, read-only) та верхній шар (Upperdir, read-write). Спроба скопіювати файл з нижнього шару у верхній (`copy-up` процедура у `overlay2`) викликала фолбек ядра замість швидкого Copy-Up оператора.
3. **Безпека та мережеві файлові системи**: У SMB3 та NFS виникли крайові випадки, коли прозорий фолбек порушував семантику системних викликів `copy_file_range`, створюючи прогалини у перевірці прав доступу до файлів віддаленого ресурсу.

Критика цього підходу з боку провідних розробників ядра (зокрема Крістофа Гельвіґа та Аміра Ґольдштейна) призвела до тривалих дискусій у розсилці `linux-fsdevel`.

```
[Обговорення linux-fsdevel 2020-2021]
Christoph Hellwig: "copy_file_range fallback in vfs breaks user assumptions about EXDEV"
Amir Goldstein: "Overlayfs copy-up should not trigger heavy in-kernel splice loop"
Linus Torvalds: "VFS must distinguish metadata cloning from cross-fs offload and page fallback"
```

Розробники відзначали, що користувацький простір позбувся обов'язку обробляти `EXDEV`, але ціною цього стало непередбачуване навантаження на систему при спробі переміщення файлів між віддаленими мережевими ресурсами або віртуальними томами.

## Еволюція асинхронного копіювання: від блокуючих викликів до io_uring (Linux 5.7+)

З появою високопродуктивного асинхронного інтерфейсу `io_uring` у ядрі Linux 5.1 постало питання про можливість асинхронного копіювання та передачі даних без блокування потоку виконання. У ядрі Linux 5.7 (травень 2020 року) Єнс Аксбое (Jens Axboe) додав коди операцій `IORING_OP_SPLICE` та `IORING_OP_TEE` у `io_uring` для підтримки асинхронної передачі даних через черги (окремої операції `IORING_OP_COPY_FILE_RANGE` у `io_uring` не існує, тому для `copy_file_range` асинхронність реалізується комбінацією `IORING_OP_SPLICE` з каналом `pipe`).

Це дозволило асинхронним подійно-орієнтованим серверам (на кшталт NGINX, Seastar або власного Storage Engine) відправляти запити передачі даних через проміжні буфери каналу (splice/pipe) безпосередньо у кільцеві буфери SQ (Submission Queue) і отримувати сповіщення про завершення у CQ (Completion Queue). Якщо ядро виявляє, що операція перекачування даних вимагатиме тривалого блокування (наприклад, фолбек копіювання через Page Cache або мережевий NFS SSC), `io_uring` автоматично делегує її виконання внутрішньому пулу системних потоків `io-wq` (async worker queue).

Паралельно файлова система Btrfs вдосконалила механізм `btrfs send / btrfs receive`, дозволяючи передавати різницеві снапшоти (incremental snapshots) між окремими пристроями через потокові інструкції копіювання екстентів, що стало стандартним інструментом резервного копіювання у серверних дистрибутивах Linux.

## Сучасний консенсус: Стабілізація VFS у Linux 5.18+ (2022+)

У версіях ядра Linux 5.18 та 6.0 підсистему VFS було остаточно рефакторено. Лінус Торвальдс затвердив нову двокомпонентну модель маршрутизації викликів:

1. **Відокремлення Reflink (`remap_file_range`) від Copy Offload**: Системний виклик `ioctl(FICLONE)` залишився строго обмеженим межою одного `super_block` і завжди повертає `EXDEV` при виході за межі тома.
2. **Адаптивний каскад у `vfs_copy_file_range`**: Виклик `copy_file_range` спершу намагається виконати апаратний offload (NVMe Copy, SCSI XCOPY, NFS SSC). Якщо апаратне прискорення неможливе, ядро виконує контроль прав доступу, валідує файлові типи і лише після цього свідомо запускає внутрішній фолбек.

Завдяки цьому у сучасних дистрибутивах Linux утиліта `cp(1)`, рантайми контейнерів (`containerd`, `CRI-O`) та бази даних можуть покладатися на `copy_file_range` як на єдиний декларативний API копіювання, який прозоро обирає найефективніший спосіб передачі байтів для будь-якої комбінації накопичувачів.
