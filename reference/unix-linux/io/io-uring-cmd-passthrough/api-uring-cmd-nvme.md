# 📋 Специфікація API та структур IORING_OP_URING_CMD для NVMe

Взаємодія з NVMe-пристроями через механізм io_uring passthrough вимагає суворого дотримання бітових структур та прапорців підсистеми `io_uring` і драйвера NVMe. На відміну від стандартних векторних операцій читання/запису (`IORING_OP_READV` / `IORING_OP_WRITEV`), опкод `IORING_OP_URING_CMD` повністю перевизначає значення полів усередині елемента черги подачі (SQE). 

Ця вставка містить вичерпний розбір полів структур, прапорців, режимів розширеної пам'яті SQE128/CQE32 та відмінностей між символьними й блочними дескрипторами пристроїв у ядрах Linux 5.19+.

## Структура SQE при IORING_OP_URING_CMD

Коли в полі `sqe->opcode` встановлено значення `IORING_OP_URING_CMD` (числовий код `46`), стандартні поля `sqe->off`, `sqe->addr` та `sqe->len` перестають виконувати свої звичайні функції розрахунку файлових зсувів. Замість цього підсистема `io_uring` передає керування драйверу пристрою, а корисне навантаження команди розміщується в універсальному масиві `sqe->cmd`. Він починається зі зсуву 48 байт від початку SQE, тож у звичайному 64-байтовому елементі під нього лишається лише 16 байт — замало навіть для базової NVMe-команди.

Нижче наведено бінарну структуру елемента черги подачі `struct io_uring_sqe` (із заголовочного файла `linux/io_uring.h` ядра Linux):

```c
struct io_uring_sqe {
    __u8   opcode;     /* IORING_OP_URING_CMD = 46 */
    __u8   flags;      /* IOSQE_FIXED_FILE, IOSQE_ASYNC, IOSQE_CQE_SKIP_SUCCESS */
    __u16  ioprio;     /* Пріоритет виконання I/O (ioprio_set) */
    __s32  fd;         /* Файловий дескриптор символьного пристрою /dev/ngXnY */
    union {
        __u64  off;
        __u64  addr2;
        struct {           /* саме тут лежить cmd_op при IORING_OP_URING_CMD */
            __u32  cmd_op; /* код підкоманди драйвера (NVME_URING_CMD_*) */
            __u32  __pad1;
        };
    };
    union {
        __u64  addr;
        __u64  splice_off_in;
    };
    __u32  len;
    __u32  op_flags;   /* Прапорці конкретної операції; для URING_CMD не вживається */
    __u64  user_data;  /* Користувацький ідентифікатор запиту (повертається в CQE) */
    __u16  buf_index;  /* Індекс зареєстрованого буфера (при IORING_URING_CMD_FIXED) */
    __u16  personality;/* Контекст ідентичності (credentials) */
    union {
        __s32  splice_fd_in;
        __u32  file_index;
    };
    union {            /* усі варіанти починаються зі зсуву 48 байт */
        struct {
            __u64  addr3;
            __u64  __pad2[1];
        };
        __u8   cmd[0]; /* 16 байт у звичайному SQE, 80 байт при SQE128 */
    };
};
```

Поле `cmd_op` є ключовим перемикачем у драйвері NVMe. Воно визначає, який саме клас NVMe-команд передається у навантаженні `cmd`:
- `NVME_URING_CMD_IO` (`_IOWR('N', 0x80, struct nvme_uring_cmd)`) — підготовка звичайної I/O-команди читання, запису або скидання кешу (Read, Write, Flush, Dataset Management).
- `NVME_URING_CMD_IO_VEC` (`_IOWR('N', 0x81, struct nvme_uring_cmd)`) — підготовка I/O-команди із векторизованими буферами даних (аналог `readv`/`writev`).
- `NVME_URING_CMD_ADMIN` (`_IOWR('N', 0x82, struct nvme_uring_cmd)`) — підготовка Admin-команди керування накопичувачем (Identify, Get Log Page, Set Features, Firmware Download).

Використання `cmd_op` дозволяє драйверу швидко розділити шляхи обробки: адміністративні команди направляються у чергу Admin SQ (qid 0), тоді як звичайні I/O-операції потрапляють у високошвидкісні черги I/O SQ. Межа проходить і по дескрипторах: `NVME_URING_CMD_IO` та `NVME_URING_CMD_IO_VEC` приймає символьний вузол простору імен `/dev/ngXnY`, а `NVME_URING_CMD_ADMIN` — символьний вузол самого контролера `/dev/nvmeX`.

## Детальний розбір структури nvme_uring_cmd

Уміст масиву `sqe->cmd` драйвер NVMe інтерпретує як бінарну структуру `struct nvme_uring_cmd` (визначена у заголовочному файлі `linux/nvme_ioctl.h`). Перелічені нижче поля дають рівно 72 байти — саме тому команда й потребує 128-байтового SQE. Кожне поле відповідає за точну конфігурацію апаратної командної структури пристрою:

```c
struct nvme_uring_cmd {
    __u8   opcode;       /* Опкод команди NVMe (наприклад, 0x02 = Read, 0x01 = Write) */
    __u8   flags;        /* Прапорці NVMe команди (NVME_CMD_SGL_METABUF тощо) */
    __u16  rsvd1;        /* Зарезервовано для вирівнювання */
    __u32  nsid;         /* Ідентифікатор простору імен (Namespace ID) */
    __u32  cdw2;         /* Command Dword 2 (опціональне розширення) */
    __u32  cdw3;         /* Command Dword 3 (опціональне розширення) */
    __u64  metadata;     /* Указник на буфер метаданих простору користувача */
    __u64  addr;         /* Указник на буфер даних простору користувача */
    __u32  metadata_len; /* Довжина метаданих у байтах */
    __u32  data_len;     /* Довжина буфера даних у байтах */
    __u32  cdw10;        /* Command Dword 10 (нижні 32 біти Starting LBA) */
    __u32  cdw11;        /* Command Dword 11 (верхні 32 біти Starting LBA) */
    __u32  cdw12;        /* Command Dword 12 (кількість блоків LBA мінус 1) */
    __u32  cdw13;        /* Command Dword 13 (прапорці DSM, частота доступу) */
    __u32  cdw14;        /* Command Dword 14 (специфічні апаратні параметри) */
    __u32  cdw15;        /* Command Dword 15 (параметри перевірки цілісності) */
    __u32  timeout_ms;   /* Таймаут виконання операції пристроєм у мілісекундах */
    __u32  rsvd2;        /* Зарезервовано */
};
```

Пояснення ключових командних слів (Command Dwords):
- `cdw10` та `cdw11` утворюють 64-бітне значення Starting LBA (адреса першого логічного блоку на диску, з якого починається читання або запис).
- `cdw12` містить кількість блоків для передачі. Згідно зі специфікацією NVMe, це значення записується як 0-based: передача 1 блоку вимагає значення `0`, передача 8 блоків (4096 байт при розмірі сектора 512 байт) вимагає значення `7`.
- `addr` визначає віртуальну адресу в оперативній пам'яті процесу, куди контролер за допомогою PCIe DMA запише або звідки зчитає дані.
- `metadata` та `metadata_len` дозволяють передавати додаткові блоки захисту цілісності даних DIF/DIX (Protection Information), що застосовуються у корпоративних дискових масивах.

Кожен апаратний опкод має власну розшифровку у командних словах `cdw10`–`cdw15`. Наприклад, для команди `Zone Append` (`0x7d`) `cdw10` і `cdw11` містять Starting LBA зони, а результативна адреса записи повертається контролером у полі `cdw0` під час завершення CQE.

## Розширені режими: SQE128 та CQE32

У звичайному 64-байтовому SQE під `sqe->cmd` лишається всього 16 байт — цього не вистачає навіть на базову 72-байтну `nvme_uring_cmd`, не кажучи про вендорські команди з розширеними полями. Тому разом із самим опкодом `IORING_OP_URING_CMD` у ядрі Linux 5.19 з'явилася підтримка подвоєних розмірів елементів обох кілець.

### Режим SQE128 (IORING_SETUP_SQE128)

При створенні кільця за допомогою `io_uring_queue_init_params()` із прапорцем `IORING_SETUP_SQE128` розмір одного SQE подвоюється з 64 до 128 байт. Це розширює корисну площу `sqe->cmd` з 16 до 80 байт — звідси й береться вимога вмикати `IORING_SETUP_SQE128` для будь-якої NVMe passthrough-команди. 

Завдяки цьому 72-байтна `struct nvme_uring_cmd` уміщується в один SQE цілком, а решта 8 байт лишається запасом. Від спорідненої `struct nvme_passthru_cmd64` з `ioctl`-інтерфейсу вона відрізняється не розрядністю командних слів (`cdw10`–`cdw15` в обох 32-бітні), а способом повернення результату завершення.

### Режим CQE32 (IORING_SETUP_CQE32)

Стандартний CQE має розмір 16 байт і повертає лише 64-бітне поле `user_data`, 32-бітний результат `res` та 32-бітні прапорці `flags`. Для passthrough команд цього недостатньо, оскільки NVMe-контролер при завершенні операції повертає не лише код помилки, а й специфічний результат у командному слові `cdw0` та 16-бітний код статусу NVMe (Status Code та Status Code Type).

При увімкненні прапорця `IORING_SETUP_CQE32` розмір CQE розширюється до 32 байт за рахунок додавання масиву `big_cqe`:

```c
struct io_uring_cqe {
    __u64  user_data; /* Значення sqe->user_data */
    __s32  res;       /* Результат виконання: 0 або від'ємний -errno */
    __u32  flags;     /* Прапорці io_uring */
    __u64  big_cqe[2];/* Додаткові 16 байт у режимі CQE32 */
};
```

Драйвер NVMe розкладає завершення так:
- `cqe->res` містить статус виконання: `0` при успіху, від'ємний `-errno` при помилці ядра або **додатне** значення Status Field контролера (Status Code разом зі Status Code Type), коли команду відкинула сама апаратура.
- `big_cqe[0]` містить командно-специфічний результат `cdw0` (наприклад, адресу фактично записаного блоку при `Zone Append`); `big_cqe[1]` драйвер NVMe не заповнює й лишає нульовим.

Від'ємні значення `res` — це системні помилки Linux: `-EFAULT` при невирівняній пам'яті, `-EINVAL` при неправильному опкоді, `-EOPNOTSUPP` при спробі викликати passthrough на блочному дескрипторі або на кільці, створеному без `IORING_SETUP_SQE128`.

Додатне значення `res` дозволяє точково діагностувати апаратні помилки накопичувача. Зчитуючи біти Status Code (SC) та Status Code Type (SCT), програма дізнається, чи була помилка викликана збоєм носія (Media and Data Integrity Errors), виходом за межі простору імен (LBA Out of Range) чи внутрішньою відмовою контролера (Internal Error).

## Порівняльний аналіз символьних та блочних дескрипторів

Для використання механізму `IORING_OP_URING_CMD` застосунок зобов'язаний відкривати саме символьний пристрій NVMe generic character device (`/dev/ngXnY`), який з'явився у ядрі 5.19, а не звичайний блоковий дескриптор (`/dev/nvmeXnY`).

Нижче наведено детальне порівняння двох класів файлових дескрипторів:

| Параметр | Блоковий вузол `/dev/nvme0n1` | Символьний вузол `/dev/ng0n1` |
| :--- | :--- | :--- |
| **Тип пристрою у VFS** | Block Device (`S_IFBLK`) | Character Device (`S_IFCHR`) |
| **Призначення** | Монтування ФС (ext4/xfs), `pread`/`pwrite` | Прямий passthrough команд NVMe |
| **Проходження через blk-mq** | Обов'язкове (через `struct request` та bio) | Повне обходження (Bypass) |
| **Підтримка uring_cmd** | Відсутня (повертає `-EOPNOTSUPP`) | Повна (`.uring_cmd = nvme_ns_chr_uring_cmd`) |
| **Підтримка IOPOLL** | Через гібридні черги блочного шару | Прямий busy-polling апаратної CQ |
| **Вимоги до прав** | Права на читання/запис у файл блоку | Права на файл для звичайних I/O-команд; `CAP_SYS_ADMIN` для адмін- і вендорських |
| **Придатність для ZNS/CSD** | Обмежена абстракцією блоків | Повна підтримка будь-яких команд NVMe |

Завдяки розділенню на символьні та блокові вузли Linux досягає повної ізоляції: звичайні утиліти операційної системи та монтовані файлові системи працюють через безпечний блоковий шар `/dev/nvme0n1`, тоді як високопродуктивні бази даних звертаються до символьного вузла `/dev/ng0n1`.

## Системний інтерфейс реєстрації в ядрі

З боку ядра драйвер NVMe реєструє обробники `uring_cmd` у таблиці `file_operations` для символьних пристроїв простору імен (`nvme_ns_chr_fops`) та контролера (`nvme_dev_fops`):

```c
const struct file_operations nvme_ns_chr_fops = {
    .owner            = THIS_MODULE,
    .open             = nvme_ns_chr_open,
    .release          = nvme_ns_chr_release,
    .uring_cmd        = nvme_ns_chr_uring_cmd,
    .uring_cmd_iopoll = nvme_ns_chr_uring_cmd_iopoll,
};
```

Коли подія потрапляє в ядро, `io_uring` викликає `.uring_cmd`, передаючи йому покажчик на внутрішній контекст `struct io_uring_cmd *cmd`. Драйвер перевіряє право доступу користувача, конвертує структуру `nvme_uring_cmd` у внутрішнє апаратне навантаження та передає його контролеру, забезпечуючи мінімальну затримку обробки.

## Точки трасування ядра (Kernel Tracepoints)

Для діагностики виконання `IORING_OP_URING_CMD` розробники можуть використовувати стандартні події трасування ядра Linux у підсистемах `io_uring` та `nvme`:

- `nvme:nvme_setup_cmd` — спрацьовує, коли драйвер сформував апаратну команду, і показує qid, cid та опкод; парний до нього `nvme:nvme_complete_rq` фіксує її завершення контролером.
- `trace_io_uring_submit_req(void *ctx, void *req, unsigned long long user_data, u8 opcode, u32 flags)` — фіксує подання SQE підсистемою `io_uring`.
- `trace_io_uring_complete(void *ctx, void *req, unsigned long long user_data, int res, unsigned int cflags)` — фіксує момент публікації CQE у кільці завершення.

Використання цих трасувальників дозволяє точково проаналізувати затримки на кожному етапі проходження команди та підтвердити факт прямого виконання запиту без затримок у підсистемі `blk-mq`.
