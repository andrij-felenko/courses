# 📋 Поверхня getdents64: структури, прапори та типи файлів

Ця довідкова вставка містить вичерпний опис структури даних ядра `struct linux_dirent64`, інтерфейсу системного виклику `getdents64()`, системних констант типів файлів `d_type`, а також їхнього відповідника у прикладній бібліотеці POSIX `struct dirent`. Вставка розрахована на роботу з низькорівневими системними викликами та сирими буферами пам'яті під час оптимізації обходу великих каталогів.

Усі описи орієнтовані на 64-бітний системний виклик `getdents64()`, який є стандартом для всіх сучасних архітектур Linux (x86_64, ARM64, RISC-V, MIPS64, LoongArch) та забезпечує повну підтримку великих індексних номерів inode і 64-бітних дискових кукі.

## Системний виклик `getdents64()`

Системний виклик `getdents64()` читає декілька записів каталогу з відкритого файлового дескриптора у наданий користувацький буфер пам'яті за один перехід межі привілеїв між користувацьким простором та ядром Linux.

```c
#define _GNU_SOURCE
#include <unistd.h>
#include <sys/syscall.h>

long syscall(SYS_getdents64, unsigned int fd, struct linux_dirent64 *dirp, unsigned int count);
```

### Детальний опис аргументів виклику

- `fd` — відкритий файловий дескриптор каталогу. Дескриптор має бути попередньо створений викликом `open()`, `openat()` або `dirfd()`. Дескриптор має бути відкритий на читання (`O_RDONLY`). Прапорець `O_DIRECTORY` — не режим доступу, а вимога до самого `open()`: він змушує ядро відмовити з `ENOTDIR`, якщо шлях виявиться не каталогом. Відкрити каталог на запис не вийде взагалі: `open()` з `O_WRONLY` чи `O_RDWR` на каталозі відмовляє з `EISDIR`.
- `dirp` — вказівник на неперервний буфер у просторі користувача, куди ядро запише послідовність упакованих структур `struct linux_dirent64`. Буфер повинен бути вирівняний у пам'яті принаймні за межею 8 байтів, щоб запобігти помилкам непідтримуваного адресування на архітектурах із суворими вимогами до вирівнювання (таких як ARM або SPARC).
- `count` — розмір буфера у байтах. Мінімально допустимий розмір має бути достатнім для розміщення щонайменше одного запису з найдовшим ім'ям (принаймні `sizeof(struct linux_dirent64) + 256` байтів). Для досягнення максимальної продуктивності на великих каталогах рекомендований розмір становить від 32 KB до 64 KB, що мінімізує кількість системних викликів.

### Повернене значення та семантика кінця каталогу

- `> 0` — кількість дійсно записаних байтів у буфер `dirp`. Отриманий розмір майже завжди менший за затребуваний `count`, оскільки ядро гарантує цілісність записів і ніколи не розриває структуру `linux_dirent64` на межі наданого буфера. Якщо наступний запис не вміщується в залишок буфера, ядро завершує запис і повертає поточну кількість байтів.
- `0` — досягнуто кінця каталогу (End-Of-File). Усі записи з файлової системи вже зчитано, подальші виклики повертатимуть 0.
- `-1` — виникла помилка під час виконання виклику у ядрі; детальний код помилки записується у глобальну змінну `errno`.

## Внутрішня структура ядра `struct linux_dirent64`

У системних заголовних файлах ядра Linux (`<linux/dirent.h>`) та C-бібліотеці структура визначена так:

```c
struct linux_dirent64 {
    uint64_t        d_ino;    /* 64-бітний номер inode об'єкта */
    int64_t         d_off;    /* Зсув/кукі для наступного запису каталогу */
    unsigned short  d_reclen; /* Загальна довжина цього запису у байтах */
    unsigned char   d_type;   /* Тип файлу (DT_REG, DT_DIR тощо) */
    char            d_name[]; /* Нуль-терміноване ім'я файлу (змінна довжина) */
};
```

### Покомпонентний аналіз полів структури

Поле `d_ino` містить унікальний 64-бітний номер inode, під яким об'єкт зареєстровано в індексних таблицях файлової системи. Це число збігається з полем `st_ino` структури `stat`. Значення 0 у полі `d_ino` в історичних файлових системах позначало видалений або звільнений запис, проте сучасний шар VFS Linux не повертає записи з `d_ino == 0` користувачеві.

Поле `d_off` являє собою непрозорий кукі зсуву (directory offset cookie), який показує позицію в каталозі для *наступного* елемента після поточного. Це значення не є байтовим зсувом у файлі, а представляє внутрішній індекс або хеш позиції у B-дереві файлової системи. Це значення використовується для подальших викликів `lseek(fd, d_off, SEEK_SET)` або `seekdir()`.

Поле `d_reclen` зберігає повну довжину даного конкретного запису `linux_dirent64` у байтах. Оскільки ім'я `d_name` має змінну довжину, поле `d_reclen` використовується як крок покажчика при переборі буфера. Значення `d_reclen` завжди вирівнюється ядром до кратного 8 байтам.

Поле `d_type` містить однобайтовий код типу об'єкта. Це поле заповнюється безпосередньо з елемента каталогу файлової системи, що дає змогу визначити тип файла без виконання додаткового системного виклику `stat()`.

Поле `d_name` є нуль-термінованим масивом символів (C-string), який містить власне ім'я файла або каталогу. У визначенні структури `d_name` оголошено як гнучкий масив (flexible array member): місця під нього займається рівно стільки, скільки має саме ім'я, плюс нульовий байт `\0`.

## Значення та розшифровка поля `d_type`

Символьні константи для перевірки поля `d_type` визначені в системному файлі `<dirent.h>`:

- `DT_UNKNOWN` (0) — Тип об'єкта невідомий. Файлова система або не підтримує зберігання типів у записах каталогів (наприклад, старі версії XFS без `ftype=1` або FAT16), або не змогла вичитати тип з диска. Потребує додаткової перевірки через `fstatat()`.
- `DT_FIFO` (1) — Іменований канал (FIFO / named pipe), створений викликом `mkfifo()`.
- `DT_CHR` (2) — Символьний спеціальний пристрій (character device node), такий як `/dev/tty` чи `/dev/null`.
- `DT_DIR` (4) — Каталог (directory).
- `DT_BLK` (6) — Блочний спеціальний пристрій (block device node), такий як `/dev/sda` чи `/dev/nvme0n1`.
- `DT_REG` (8) — Звичайний файл (regular file).
- `DT_LNK` (10) — Символьне посилання (symbolic link).
- `DT_SOCK` (12) — Доменний сокет UNIX (UNIX domain socket), створений викликом `bind()`.
- `DT_WHT` (14) — Запис маскування видалення (Whiteout entry). Успадковано від union-монтувань BSD; у Linux назовні майже не трапляється — OverlayFS позначає видалене символьним пристроєм 0/0 і власні маскувальні записи користувачеві не показує.

## Порівняльний аналіз `struct linux_dirent64` та POSIX `struct dirent`

C-бібліотека `glibc` надає користувачеві високорівневу структуру `struct dirent`, яка відрізняється від системної `struct linux_dirent64` низкою важливих деталей:

```c
#include <dirent.h>

struct dirent {
    ino_t          d_ino;       /* Номер inode */
    off_t          d_off;       /* Зсув у каталозі */
    unsigned short d_reclen;    /* Розмір структури dirent */
    unsigned char  d_type;      /* Тип файлу */
    char           d_name[256]; /* Масив імені фіксованого розміру */
};
```

Головна відмінність полягає у виділенні пам'яті під ім'я `d_name`. У системній структурі `linux_dirent64` ядро пакує ім'я у масив мінімально необхідної довжини із 8-байтовим вирівнюванням, що дозволяє максимально щільно заповнити буфер. У структурі POSIX `struct dirent` C-бібліотека виділяє під `d_name` фіксований масив розміром `256` байтів (або `NAME_MAX + 1`), що робить розмір структури постійним у її оголошенні. Копіювання при цьому не відбувається: на Linux `readdir()` віддає вказівник просто у внутрішній буфер `DIR*`, де фактичне ім'я зазвичай коротше за оголошені 256 байтів. Копіювати `d_name` доводиться самому — але лише тоді, коли ім'я потрібне після наступного `readdir()`.

Крім того, типи `ino_t` та `off_t` у структурі `struct dirent` є залежними від макросів конфігурації компіляції (таких як `_FILE_OFFSET_BITS=64`), тоді як `struct linux_dirent64` у ядрі Linux завжди використовує строгі 64-бітні типи `uint64_t` та `int64_t`.

## Деталізація кодів помилок системного виклику `getdents64()`

Якщо системний виклик `getdents64()` повертає значення `-1`, значення у змінній `errno` вказує на конкретну причину відмови:

- `EBADF` — Переданий файловий дескриптор `fd` не є дійсним відкритим дескриптором цього процесу.
- `EFAULT` — Вказівник `dirp` вказує на область адресового простору, яка не належить процесу або недоступна для запису ядра.
- `EINVAL` — Розмір буфера `count` є занадто малим. Значення `count` менше за розмір одного запису `linux_dirent64` з поточним ім'ям файла у каталозі.
- `ENOTDIR` — Переданий файловий дескриптор `fd` посилається на звичайний файл, сокет або пристрій, який не є каталогом.
- `ENOENT` — Каталог було видалено з файлової системи або розмонтовано під час виконання читання.
- `EIO` — Виникла фізична помилка зчитування блоку метаданих каталогу з дискового накопичувача (I/O error).
