Сканування каталогу `/var/log` з 500 000 дрібних текстових файлів наївним кодом із викликом `stat()` для кожного елемента змушує систему виконати 500 000 окремих системних викликів. За продуктивності накопичувача 100 000 IOPS такий обхід триває понад 5 секунд лише на зчитування типів об'єктів, навіть якщо всі метадані лежать у кеші сторінок ядра. Якщо ж застосувати пакетне читання записів через системний виклик `getdents64()` та зчитувати тип файлу безпосередньо з елемента каталогу, час сканування зменшується до 12 мілісекунд.

Різниця на два порядки виникає з того, як саме ядро Linux та віртуальна файлова система (VFS) представляють каталоги й надають процесам змогу обходити їхній вміст.

## Чому каталог не читається через `read()`: межа VFS та абстракція `iterate_shared`

У ранніх версіях Unix (Version 7 та System V) каталог був звичайним файлом, вміст якого програма могла прочитати за допомогою стандартного системного виклику `read()`. Записи мали фіксовану довжину 16 байтів: 2 байти під номер inode та 14 байтів під ім'я файла. Додаток відкривав каталог, читав байти підряд та розбивав їх на записи власними силами.

Спроба зробити те саме в сучасному Linux повертає помилку:

```sh
$ cat /var/log
cat: /var/log: Is a directory
```

Системний виклик `read()` повертає код помилки `-1`, а змінна `errno` набуває значення `EISDIR` (Is a directory). Заборона прочитати каталог як байтовий файл є наслідком еволюції файлових систем. Сучасні файлові системи не зберігають каталоги у вигляді плоских лінійних масивів. Файлова система ext4 використовує індексовані хеш-дерева (HTree), XFS застосовує B+дерева над віртуальним адресовим простором каталогу, а Btrfs зберігає записи каталогу як пари ключ-значення у спільному дереві файлової системи (FS tree).

Якби ядро дозволило програмам читати сирі дискові байти каталогу через `read()`, кожна прикладна програма мала б містити внутрішній драйвер для розбору внутрішніх структур даних ext4, XFS, Btrfs, OverlayFS та NFS. Будь-яка зміна внутрішньої версії дискового формату ламала б усі утиліти обходу файлових систем.

Щоб відокремити внутрішню структуру дискових даних від прикладного рівня, ядро Linux вводить абстракцію у шарі VFS. Операція обходу каталогу описується у таблиці `file_operations` файлової системи методом `iterate_shared` (або застарілим `iterate`):

```c
struct file_operations {
    int (*iterate_shared) (struct file *, struct dir_context *);
    /* ... */
};
```

Під час виконання обходу VFS захоплює блокування читача-записника індексу каталогу `inode->i_rwsem` у спільному режимі (`down_read`). Це дозволяє кільком паралельним потокам або процесам одночасно виконувати обхід того самого каталогу без взаємного блокування. Виключне блокування (`down_write`) захоплюється лише під час модифікацій каталогу — створення (`mkdir`), видалення (`unlink`) чи перейменування (`rename`) елементів.

Коли програма запитує перелік файлів у каталозі, VFS викликає метод `iterate_shared` відповідної файлової системи, передаючи йому контекст обходу `struct dir_context`. Драйвер файлової системи здійснює обхід власного внутрішнього дерева чи хеш-таблиці та для кожного знайденого елемента викликає функцію-заповнювач `filldir()`, яка перекладає внутрішній дисковий запис у єдиний уніфікований формат запису ядра.

![Багатошарова архітектура обходу каталогів у Linux](/reference/unix-linux/io/readdir-getdents64-directory-traversal/img/dir-traversal-flow.svg)

*Багатошарова архітектура обходу каталогів: від прикладного виклику readdir() через буферизацію в C-бібліотеці та системний виклик getdents64() до абстракції VFS dir_context і драйверів конкретних файлових систем.*

З цього випливає важливий наслідок: позиція в каталозі не є лінійним байтовим зміщенням (byte offset), як у звичайному файлі. Значення зміщення (дисковий кукі або directory offset `d_off`) — це 64-бітне число, зміст якого визначається самою файловою системою. У ext4 це хеш-ключ елемента в HTree з урахуванням колізій, у XFS — позиція елемента в B+дереві, а у tmpfs — індекс у масиві. Виклик `lseek(fd, 100, SEEK_SET)` на дескрипторі каталогу ядро здебільшого виконає без помилки, але користі з цього немає: число 100 не відповідає жодному дійсному вузлу в індексному дереві файлової системи, тож наступний `getdents64()` поверне не той елемент, на який чекає програма, або відмовить із `EINVAL`.

### Внутрішній устрій індексації каталогів у ext4 та XFS

Для розуміння того, як ядро генерує значення `d_off`, варто розглянути внутрішню структуру каталогів найпоширеніших файлових систем.

У файловій системі ext4 каталоги з невеликою кількістю файлів (до 12-20 записів) зберігаються у вигляді плоского масиву в одному блоці даних. Проте як тільки кількість елементів зростає, ext4 прозоро вмикає механізм `dir_index` (HTree). Хеш-дерево HTree обчислює 32-бітний хеш імені файла за допомогою алгоритму Half-MD4 або TEA. Ключем пошуку у дереві стає саме хеш імені. Значення `d_off`, яке ядро повертає користувачеві при обході HTree-каталогу, складається з 32-бітного хешу імені у старших бітах та індексу колізії у молодших бітах.

Файлова система XFS підтримує п'ять форматів каталогів залежно від обсягу даних: *shortform* (всередині inode), *block* (один блок 4 KB), *leaf* (окремі блоки імен та індексів), *node* (багаторівневе B+дерево) та *btree* (повне розширене B+дерево для мільйонів елементів). У XFS значення `d_off` являє собою 64-бітне індексне число, яке вказує на точну 8-байтову межу (directory block offset) у віртуальному 32-гігабайтному адресовому просторі каталогу XFS.

## Анатомія системного виклику `getdents64()` та структура пакетованого буфера

Передавання даних про елементи каталогу з ядра у простір користувача здійснюється за допомогою системного виклику `getdents64()` (get directory entries).

```c
long syscall(SYS_getdents64, unsigned int fd, struct linux_dirent64 *dirp, unsigned int count);
```

За один виклик `getdents64()` ядро копіює у буфер користувача `dirp` розміром `count` байтів максимально можливу кількість записів каталогів. Повне визначення полів та прапорців цієї структури зібрано у [довідці системних структур getdents64](book:unix-linux/readdir-getdents64-directory-traversal/api-getdents64-structs.md).

На відміну від звичайних структур мови C із фіксованим розміром, структура `struct linux_dirent64` має змінну довжину. Ім'я файла `d_name` пакується впритиск, одразу після метаданих елемента.

![Структура буфера getdents64 та пакування змінної довжини записів linux_dirent64](/reference/unix-linux/io/readdir-getdents64-directory-traversal/img/getdents64-buffer-layout.svg)

*Пакування записів змінної довжини у неперервному буфері getdents64(): кожен запис містить довжину d_reclen, за якою розраховується адреса наступного елемента з урахуванням 8-байтового вирівнювання.*

Кожен запис `linux_dirent64` починається з 8-байтового номера `d_ino` та 8-байтового кукі зміщення `d_off`. За ними йде 2-байтове поле `d_reclen`, яке вказує повний розмір даного запису у байтах. Байт `d_type` зберігає тип об'єкта, а за ним слідує нуль-термінований рядок імені файла `d_name`.

Оскільки чимало архітектур (ARM64, RISC-V, MIPS) вимагають, щоб 64-бітне ціле лежало за адресою, кратною 8, ядро вирівнює кожен запис `linux_dirent64` до кратного 8 байтів. Для цього після нуль-термінатора імені додається від 0 до 7 байтів наповнення (padding): коли довжина запису й так кратна восьми, наповнення немає взагалі. Поле `d_reclen` враховує це вирівнювання, тому перехід до наступного запису в буфері здійснюється адресною арифметикою:

```c
struct linux_dirent64 *d = (struct linux_dirent64 *)(buf + bpos);
bpos += d->d_reclen;
```

Якщо розмір буфера `count` становить, наприклад, 64 KB, то один системний виклик `getdents64()` повертає інформацію про 1500–2000 файлів за один перехід межі ядра. Це на три порядки зменшує кількість переходів межі ядра порівняно з поштучним запитом кожного файла.

При заповненні користувацького буфера функція ядра `filldir64()` обчислює точний розмір поточного запису за формулою:

```c
size_t reclen = ALIGN(offsetof(struct linux_dirent64, d_name) + namelen + 1, sizeof(u64));
```

Якщо розмір `reclen` перевищує обсяг вільного місця, що залишилося у користувацькому буфері `dirp`, ядро зупиняє розбір і повертає кількість вже скопійованих байтів. Запис, який не вмістився, буде зчитаний під час наступного виклику `getdents64()`, для чого ядро зберігає поточне значення кукі у файловому описі `struct file`.

> 🔧 **Навіщо це.** При написанні високонавантажених утиліт обходу диска (backup-агенти, системи індексації, антивірусні сканери) стандартний буфер C-бібліотеки може бути недостатнім. Прямий виклик `sys_getdents64` з виділеним буфером розміром 64 KB або 128 KB дозволяє зчитувати інформацію про мільйони файлів з мінімальним навантаженням на процесор.

## Управління потоком у C-бібліотеці: буферизація `DIR*` та застарілість `readdir_r()`

Більшість прикладних програм не викликають `getdents64()` напряму через `syscall()`, а використовують стандартний POSIX-інтерфейс C-бібліотеки: `opendir()`, `readdir()`, `closedir()`, `telldir()` та `seekdir()`.

Функція `opendir(path)` виконує системний виклик `open(path, O_RDONLY | O_DIRECTORY)` і виділяє у динамічній пам'яті (купа, heap) внутрішню структуру `DIR`. Згідно з реалізацією у glibc та musl, структура `DIR` містить:

1. Файловий дескриптор відкритого каталогу `fd`.
2. Внутрішній буфер пам'яті для записів каталогу (у glibc його розмір за замовчуванням становить 32 KB).
3. Покажчик поточного зміщення всередині внутрішнього буфера.
4. Кількість байтів, повернутих останнім системним викликом `getdents64()`.

Коли програма викликає `readdir(dirp)`, C-бібліотека перевіряє, чи є нерозбирані записи у її внутрішньому буфері. Якщо буфер не порожній, `readdir()` розбирає поточний `linux_dirent64` і повертає вказівник просто всередину цього буфера: на Linux розкладка запису ядра збігається зі `struct dirent`, тож копіювати нічого не треба. Жодного системного виклику при цьому не відбувається — саме тому повернутий вказівник живий лише до наступного `readdir()` чи `closedir()`.

Лише тоді, коли внутрішній буфер C-бібліотеки вичерпано (покажчик досяг кінця прочитаних байтів), `readdir()` прозоро здійснює наступний системний виклик `getdents64(fd, buf, 32768)`.

```
Додаток               C-бібліотека (glibc)             Ядро (VFS getdents64)
   │                           │                                │
   │─────── opendir() ────────>│                                │
   │                           │────── open(O_DIRECTORY) ──────>│
   │                           │<───── return fd ───────────────│
   │                           │                                │
   │─────── readdir() ────────>│                                │
   │                           │────── getdents64(32KB) ───────>│
   │                           │<───── 32KB entries ────────────│
   │<── struct dirent * ───────│ (кешовано в буфері DIR*)       │
   │                           │                                │
   │─────── readdir() ────────>│                                │
   │<── struct dirent * ───────│ (читання з буфера, 0 syscalls) │
```

Ця архітектурна схема пояснює особливості навігації за допомогою `telldir()` та `seekdir()`. Функція `telldir(dirp)` повертає поточне значення `d_off` останнього розібраного запису, отримати яке допомогло ядро. Виклик `seekdir(dirp, loc)` скидає внутрішній буфер `DIR*`, виконує `lseek(fd, loc, SEEK_SET)` для передачі кукі ядру і готує наступний `readdir()` до нового виклику `getdents64()`.

Оскільки значення `d_off` є непрозорим кукі файлової системи, використання арифметичних операцій над значенням, повернутим `telldir()`, є категорично забороненим. Додавання або віднімання одиниці від повернутого числа не перемістить потік на попередній чи наступний файл, а призведе до втрати зв'язку із B-деревом каталогу.

### Пастка багатопотоковості та позиція `readdir_r()`

У 1990-х роках із появою багатопотокових програм постало питання потокобезпечності `readdir()`. Оскільки `readdir()` повертає вказівник на внутрішню структуру всередині `DIR*`, паралельний виклик `readdir()` для того самого дескриптора перезаписував дані.

Для розв'язання цієї проблеми стандарт POSIX.1c ввів функцію `readdir_r()`, де буфер для результату мав надаватися викликачем. Проте розробка виявилася помилковою через неможливість точно передбачити максимальну довжину імені файла `NAME_MAX` для мережевих та FUSE файлових систем. Детальний аналіз анатомії цієї помилки та причин вилучення функції описано в [історичному екскурсі застарілості readdir_r](book:unix-linux/readdir-getdents64-directory-traversal/hist-readdir-r-deprecation.md).

У сучасному POSIX та glibc 2.24+ функція `readdir_r()` є застарілою. Виклик `readdir()` є повністю потокобезпечним за умови, що різні потоки працюють із *різними* об'єктами `DIR*`. Якщо ж кілька потоків обходять один і той самий об'єкт `DIR*`, синхронізація має виконуватися зовнішнім м'ютексом.

## Оптимізація сканування: поле `d_type` та випадки fallback-запитів

При рекурсивному обході дерев каталогів головним завданням алгоритму є розрізнення звичайних файлів та підкаталогів, в які потрібно занурюватися далі.

У наївній реалізації для кожного поверненого імені виконується виклик `stat()` або `lstat()`:

```c
struct dirent *entry;
while ((entry = readdir(dirp)) != NULL) {
    struct stat st;
    stat(entry->d_name, &st); /* Додатковий системний виклик для КОЖНОГО файла! */
    if (S_ISDIR(st.st_mode)) {
        /* Рекурсивний обхід підкаталогу */
    }
}
```

Виклик `stat()` змушує ядро виконати повне розв'язання шляху, звернутися до dentry-кешу, вичитати inode з диска або кеша сторінок і заповнити повну структуру метаданих (права, розмір, часи `st_mtime`, власники `st_uid`). Для простого визначення типу об'єкта 99% цієї роботи є зайвою.

Щоб усунути ці витрати, системний виклик `getdents64()` повертає тип об'єкта безпосередньо у полі `d_type` структури `struct linux_dirent64`. Файлові системи експортують тип об'єкта безпосередньо з блоків записів каталогу (leaf blocks), що позбавляє ядро потреби піднімати з диска inode кожного елемента.

Байт `d_type` може набувати наступних основних значень:

- `DT_DIR` (4) — елемент є каталогом.
- `DT_REG` (8) — елемент є звичайним файлом.
- `DT_LNK` (10) — елемент є символьним посиланням.
- `DT_UNKNOWN` (0) — тип об'єкта невідомий.

### Чому виникає `DT_UNKNOWN` і як з ним працювати

Поле `d_type` працює за рахунок того, що файлова система зберігає тип об'єкта безпосередньо в елементі каталогу поруч з номером inode та ім'ям. Проте не всі файлові системи підтримують це поле або зберігають його за замовчуванням:

1. **Старі формати XFS**: У старіших версіях XFS, створених без опції `ftype=1`, елементи каталогів не містили байта типу.
2. **Мережеві файлові системи (NFS / CIFS)**: Деякі версії протоколу NFS v2/v3 не передають тип об'єкта під час читання каталогів.
3. **Видалені або пошкоджені записи**: Під час відновлення файлової системи після збоїв поле типу може бути втрачено.

Якщо файлова система не може гарантувати тип об'єкта, вона записує у поле `d_type` значення `DT_UNKNOWN` (0).

Коректно написана програма повинна завжди перевіряти `d_type` і робити запасний виклик `fstatat()` лише тоді, коли тип дійсно дорівнює `DT_UNKNOWN`:

```c
unsigned char dtype = entry->d_type;
if (dtype == DT_UNKNOWN) {
    struct stat st;
    if (fstatat(dirfd(dirp), entry->d_name, &st, AT_SYMLINK_NOFOLLOW) == 0) {
        if (S_ISDIR(st.st_mode)) dtype = DT_DIR;
        else if (S_ISREG(st.st_mode)) dtype = DT_REG;
    }
}
```

Використання прапорця `AT_SYMLINK_NOFOLLOW` у виклику `fstatat()` є принциповим: воно гарантує, що якщо об'єкт є символьним посиланням на каталог, виклик поверне тип самого посилання, запобігаючи нескінченним циклам при рекурсії.

### Взаємодія з dentry-кешем ядра (dcache)

Коли додаток обходить каталог, ядро Linux може створювати або оновлювати записи в кеші імен (dentry cache, `dcache`). Цей кеш тримає в оперативній пам'яті ядра зв'язки між назвами файлів та їхніми `struct inode`.

Під час виконання `getdents64()` ядро зчитує блоки каталогу безпосередньо через кеш сторінок (page cache). При цьому створення об'єктів `struct dentry` для кожного файла в каталозі не відбувається. Це робить `getdents64()` значно легшим для пам'яті ядра, ніж серія викликів `lookup`/`stat`, які заповнили б кеш dentry мільйонами тимчасових об'єктів, витісняючи зі slab-кешів ядра справді потрібні записи.

## Безпечний та високопродуктивний обхід великих дерев: TOCTOU та ресурси

При скануванні реальних файлових систем на сервері алгоритм обходу стикається з трьома фундаментальними проблемами: гонки перевірки та використання (TOCTOU), обмеження на кількість відкритих дескрипторів та переповнення стеку викликів.

### 1. Захист від атак TOCTOU через `openat()`

Наївна рекурсивна програма будує шляхи файлів шляхом конкатенації рядків: `/var/log` + `/` + `nginx` = `/var/log/nginx`. Потім вона викликає `opendir("/var/log/nginx")`.

Якщо під час виконання обходу сторонній процес (або зловмисник у системі) перейменує каталог `/var/log/nginx` і створить на його місці символьне посилання на корінь файлової системи `/`, наступний виклик `opendir()` відкриє корінь диска, і сканер вийде за межі цільового дерева.

Ця пастка усувається відносним відкриванням дескрипторів за допомогою викликів родини `*at`. Програма відкриває початковий каталог, отримує його дескриптор `dir_fd`, а кожен підкаталог відкриває відносно батьківського дескриптора з використанням прапорців `O_DIRECTORY` та `O_CLOEXEC`:

```c
int child_fd = openat(parent_fd, entry->d_name, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
```

Прапорець `O_DIRECTORY` гарантує лише те, що відкриття не-каталогу завершиться помилкою `ENOTDIR`: символьне посилання ядро все одно розкриє, і якщо воно вказує на каталог, відкриття вдасться. Тому проти підміни каталогу посиланням до `O_DIRECTORY` додають `O_NOFOLLOW` (посилання дає `ELOOP` замість переходу). Надійніший захист у сучасних ядрах Linux дає системний виклик `openat2()` із прапорцями розв'язання `RESOLVE_BENEATH` (забороняє вихід за межі відкритого каталогу) та `RESOLVE_NO_SYMLINKS` (забороняє розкриття будь-яких символьних посилань під час обходу).

### 2. Запобігання вичерпанню дескрипторів (`EMFILE`) та переповненню стеку

При глибокій ієрархії каталогів (наприклад, 2000 вкладених рівнів) рекурсивний алгоритм відкриває новий файловий дескриптор для кожного рівня. Стандартне обмеження Linux на кількість відкритих дескрипторів процесу (`RLIMIT_NOFILE`) за замовчуванням становить 1024. Перевищення цього ліміту призводить до помилки `EMFILE` (Too many open files), і сканування зупиняється.

Крім того, глибока рекурсія у C/C++ викликах функцій призводить до вичерпання пам'яті стеку процесу (Stack Overflow) та аварійного завершення програми сигналом `SIGSEGV`.

Професійні утиліти (такі як `find`, `rsync` або бібліотека `fts(3)`) розв'язують цю проблему одним із двома способів:

- **Ітеративний стек каталогів у купі**: Замість рекурсивних викликів функцій алгоритм підтримує власний стек або чергу шляхів/дескрипторів у динамічній пам'яті heap.
- **Закриття дескрипторів під час занурення**: Програма тримає відкритим лише один дескриптор поточного каталогу та використовує `fchdir()` для переходу по дереву вниз, а вгору повертається через запис «..» того самого каталогу.

### 3. Конкурентні зміни каталогів під час обходу

Важливо усвідомлювати, що обхід каталогу в POSIX не є атомарним знімком (snapshot). Якщо під час виконання `readdir()` інший процес створює або видаляє файли у цьому каталозі:

- Нові створені файли можуть бути внесені до виводів `readdir()`, а можуть бути пропущені залежно від того, куди файлова система записала нові елементи в індексному дереві.
- Видалені файли можуть бути повернуті `readdir()`, якщо вони знаходилися у вже вичитаному буфері `DIR*`, але подальші виклики `stat()` для них повернуть `ENOENT`.
- Перейменування файлів під час обходу може призвести до того, що той самий файл буде повернутий `readdir()` двічі або не повернутий жодного разу.
