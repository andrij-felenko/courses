# 📜 Історія readdir_r: від потокобезпечності до застарілості

Еволюція системного виклику `readdir()` відображає тривалий пошук балансу між потокобезпечністю, продуктивністю та надійністю роботи з файловими системами. Спроба розв'язати проблему потокобезпечності `readdir()` шляхом введення інтерфейсу `readdir_r()` у стандартах POSIX 1990-х років виявила глибинні архітектурні недоліки, пов'язані з динамічною довжиною імен файлів та загрозою переповнення буфера пам'яті. Через ці приховані вразливості та неефективність виділення пам'яті розробники glibc та комітет POSIX оголосили `readdir_r()` застарілим (deprecated) у POSIX.1-2008, повернувшись до ізольованого буферизаційного механізму в межах об'єкта `DIR*`.

## Зародження проблеми: потоки виконання та статичні буфери в ранньому POSIX

У перших стандартах POSIX.1-1988 функція `readdir()` мала наступну сигнатуру:

```c
struct dirent *readdir(DIR *dirp);
```

За специфікацією, `readdir()` повертала вказівник на структуру `struct dirent`. Оскільки ця структура виділялася або як статична змінна в межах бібліотеки, або як внутрішній буфер у структурі `DIR`, виклик `readdir()` не був потокобезпечним (Thread-Unsafe). Якщо два паралельні потоки (POSIX threads) викликали `readdir()` для одного й того самого об'єкта `DIR*` (або у деяких ранніх реалізаціях — навіть для різних об'єктів `DIR*`), вміст поверненої структури перезаписувався другим потоком, спричиняючи гонку даних (Data Race).

На початку 1990-х років із масовим поширенням багатопотокового програмування (POSIX 1003.1c-1995) виникла гостра потреба у потокобезпечних версіях стандартних системних функцій (`gethostbyname_r`, `strtok_r`, `asctime_r` тощо). За цим шаблоном було розроблено й виклик `readdir_r()`.

## Ідея `readdir_r()` та виділення буфера викликачем

Ідея `readdir_r()` полягала у винесенні пам'яті для структури результату з бібліотеки у простір викликача:

```c
int readdir_r(DIR *restrict dirp, struct dirent *restrict entry, struct dirent **restrict result);
```

Схема мала працювати так:
1. Викликач виділяє пам'ять під структуру `struct dirent entry` на власному стеку або в купі.
2. `readdir_r()` копіює поточний запис у наданий буфер `entry`.
3. У змінну `*result` записується вказівник на `entry` (або `NULL`, якщо досягнуто кінця каталогу).

На перший погляд це розв'язувало проблему: кожен потік мав власний стек і власний буфер `entry`, отже копіювання даних не перекривалося. Проте в самому задумі був фундаментальний дефект.

## Пастка розміру `NAME_MAX` та виклики `pathconf()`

Як правильно обчислити розмір буфера `struct dirent` для виклику `readdir_r()`?

Стандартна структура `struct dirent` у системних заголовках зазвичай має вигляд:

```c
struct dirent {
    ino_t          d_ino;
    off_t          d_off;
    unsigned short d_reclen;
    unsigned char  d_type;
    char           d_name[256]; /* 255 символів + null-байт */
};
```

Більшість файлових систем POSIX (ext4, XFS, Btrfs) обмежують максимальну довжину імені файла константою `NAME_MAX = 255`. Проте деякі мережеві та спеціальні файлові системи (наприклад, NFS, SMB/CIFS, FUSE-модулі або кастомні розподілені СУБД) можуть повертати імена файлів, довжина яких перевищує 255 байтів (наприклад, 1024 або 4096 байтів).

Аби виділити буфер достатнього розміру, специфікація пропонувала викликати `fpathconf(dirfd, _PC_NAME_MAX)`:

```c
long name_max = fpathconf(dirfd(dirp), _PC_NAME_MAX);
if (name_max == -1) name_max = 255; /* fallback */

size_t alloc_size = offsetof(struct dirent, d_name) + name_max + 1;
struct dirent *entry = malloc(alloc_size);
```

### Чому це виявилося небезпечним і некоректним

1. **Динамічність файлових систем**: Функція `fpathconf()` повертає значення, актуальне на момент виклику. Для мережевих томів (NFS/CIFS) точка монтування може змінитися у динаміці, або монтована система може повернути запис із довжиною, що перевищує попереднє обмеження.
2. **Вразливість переповнення буфера (Buffer Overflow)**: Якщо файлова система повертала запис з ім'ям, довшим ніж виділений викликачем буфер у `entry`, реалізація `readdir_r()` у бібліотеці перезаписувала пам'ять за межами `entry`, що призводило до руйнування стеку або потенційного виконання довільного коду (security exploit).
3. **Складність та неефективність API**: Вимога виділяти динамічний буфер через `malloc()` із викликами `fpathconf()` для кожного обходу каталогу перетворювала простий код на громіздку та повільну конструкцію.

## Визнання застарілим у POSIX.1-2008 та рішення glibc

У 2016 році, під час оновлення стандарту POSIX.1-2008 (Austin Group Technical Corrigendum 2), функцію `readdir_r()` було офіційно оголошено застарілою (deprecated). З версії **glibc 2.24** при компіляції коду з `readdir_r()` видається застереження компілятора:

```
warning: 'readdir_r' is deprecated [-Wdeprecated-declarations]
```

### Як було відновлено потокобезпечність звичайного `readdir()`

Зараз POSIX та glibc гарантують наступну поведінку звичайного `readdir(DIR *dirp)`:

1. **Потокобезпечність між різними дескрипторами `DIR*`**: Викликати `readdir()` паралельно з двох різних потоків для *різних* об'єктів `DIR*` є абсолютно безпечним. Буфер запису зберігається всередині конкретного об'єкта `DIR*`, виділеного під час `opendir()`.
2. **Синхронізація для одного `DIR*`**: Якщо кілька потоків мають доступ до *одного й того самого* об'єкта `DIR*`, розробник мусить явно синхронізувати виклики `readdir()` за допомогою м'ютекса (`pthread_mutex_t`).

Таким чином, відмова від `readdir_r()` повернула системне програмування до простого, безпечного та ефективного API `readdir()`.

## Еволюція підходів у системному програмуванні

Історія з `readdir_r()` стала важливим уроком для розробників операційних систем і системних бібліотек. Вона продемонструвала, що спроба зробити API потокобезпечним шляхом перекладання обов'язків виділення пам'яті на викликача створює серйозні проблеми при роботі зі змінною довжиною даних.

Подібні проблеми виникали й в інших системних функціях POSIX. Наприклад, функції `gethostbyname_r()` та `getpwuid_r()` також вимагають передавання користувацького буфера та його розміру. Проте на відміну від файлових систем, де довжина імен описується динамічними структурами на диску, мережеві записи мають більш передбачувані межі.

Сучасний дизайн системних API Linux віддає перевагу або використанню статично ізольованих структур у межах контекстного об'єкта (як це зроблено в `DIR*`), або поверненню описувачів ресурсів через файлові дескриптори та прямі системні виклики (на кшталт `getdents64()`).

Використання прямого системного виклику `getdents64()` повністю позбавлене проблем `readdir_r()`, оскільки ядро самостійно контролює межі користувацького буфера `dirp` і ніколи не записує більше байтів, ніж вказано в аргументі `count`. Якщо запис не вміщується в буфер, ядро просто зупиняє розбір, гарантуючи повну захищеність від переповнення пам'яті.
