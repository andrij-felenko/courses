# ⚙️ Копіювання файлу прямим вводом-виводом: програма, що не лишає слідів у пам'яті

Ця вставка пояснює ⚙️ копіювання файлу прямим вводом-виводом: програма, що не лишає слідів у пам'яті та дозволяє зрозуміти її детальніше. Ця програма на C копіює файл із прапорцем `O_DIRECT` так, що після неї в кеші сторінок не лишається жодної сторінки — ані джерела, ані цілі, — і при цьому не програє звичайному копіюванню в швидкості. Той самий код без одного ключа працює буферизовано, тож обидва шляхи міряє той самий двигун і різниця в числах належить прапорцеві, а не двом різним програмам.

Відмовившись від кеша, програма лишається без того, що він робив мовчки, і мусить відтворити це сама. Звідси й весь її обсяг: вирівняні запити, глибина черги замість читання наперед, окреме прибирання хвоста файлу — і довговічність, якої прапорець не давав ніколи.

## Числа вирівнювання питають у ядра

Вирівнювання — не константа програми, а властивість конкретного файлу на конкретній файловій системі. Від ядра 6.1 його можна просто спитати: [statx](book:unix-linux/statx-extended-stat) із запитом `STATX_DIOALIGN` повертає окремо потрібне вирівнювання адреси буфера й окремо — вирівнювання зміщень і довжин.

```c
struct align { size_t mem, off; };

static struct align dio_align(int fd)
{
    struct align a = { 4096, 4096 };     /* безпечна стеля, якщо не відповіли */
    struct statx stx;

    if (statx(fd, "", AT_EMPTY_PATH, STATX_DIOALIGN, &stx) == 0
        && (stx.stx_mask & STATX_DIOALIGN) && stx.stx_dio_mem_align) {
        a.mem = stx.stx_dio_mem_align;
        a.off = stx.stx_dio_offset_align;
    }
    return a;
}
```

Нуль у полі означає не «вирівнювання не потрібне», а «ця файлова система не звітує» — саме тому перевірка стоїть на `stx_dio_mem_align`, а не на самому виклику. Підтримку мають блокові пристрої, ext4, XFS і f2fs; на решті лишається запасне значення 4096, яке більше за будь-який реальний логічний блок і тому завжди законне. Джерело й ціль можуть жити на різних файлових системах, тож програма бере від обох і лишає більше з двох.

## Хвіст, який не ділиться на блок

Розмір файлу — довільне число, а довжина прямого запиту мусить бути кратною блоку. Останній шматок у це правило не вкладається, і саме на ньому найчастіше ламаються перші спроби.

**Файл на 5 000 000 байтів, блок 4096:**

```
цілих блоків       = 5 000 000 / 4096 = 1220.7…  →  1220
байтів у них       = 1220 · 4096 = 4 997 120
хвіст              = 5 000 000 − 4 997 120 = 2 880

довжина запиту     = 4 096       (округлення вгору)
доповнення         = 4 096 − 2 880 = 1 216 байтів
файл після запису  = 4 997 120 + 4 096 = 5 001 216
ftruncate          → 5 000 000
```

Читання на 4096 байтів із зміщення 4 997 120 поверне 2880 — коротка відповідь на кінці файлу нормальна й для прямого шляху. А от записати 2880 байтів уже не можна: довжина не кратна блоку. Тому пишемо цілий блок, доповнивши буфер нулями, і наприкінці повертаємо файлові справжню довжину через `ftruncate`.

![Три смуги по 4096 байтів: у джерелі 2880 байтів даних і решта за кінцем файлу, у буфері ті самі 2880 плюс 1216 нулів, у цілі записано цілий блок, після чого ftruncate вкорочує файл до 5 000 000](/reference/unix-linux/io/buffered-and-direct-io/img/tail.svg)

*Занулити доповнення обов'язково: інакше на носій поїде вміст купи, і хоч `ftruncate` його й відріже, кілька секунд він там пролежить.*

Другий спосіб — відкрити ціль ще раз, без `O_DIRECT`, і дописати хвіст звичайним `write`. Він коротший у коді, але змішує два шляхи на одному файлі, тож потребує `fsync` між ними.

## Програма

Один файл, дві залежності: ядро 6.1 і `liburing`. Збірка — `cc -O2 -Wall -Wextra -o dcopy dcopy.c -luring`.

```c
/* dcopy.c — копіювання файлу прямим вводом-виводом із заданою глибиною черги.
   Ключ -B вимикає O_DIRECT: буферизований шлях тим самим двигуном.

   вжиток: ./dcopy [-d глибина] [-b блок,КіБ] [-B] джерело ціль            */

#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <liburing.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <time.h>
#include <unistd.h>

#define MAXQD 256

enum { OP_READ = 0, OP_WRITE = 1 };

struct slot {
    unsigned char *buf;
    off_t  off;              /* зміщення порції у файлі                    */
    size_t len;              /* довжина порції, вже округлена до блоку     */
    size_t done;             /* скільки байтів порції вже перенесено       */
};

static size_t up(size_t v, size_t a) { return (v + a - 1) / a * a; }

static double now(void)
{
    struct timespec t;

    clock_gettime(CLOCK_MONOTONIC, &t);
    return (double)t.tv_sec + (double)t.tv_nsec / 1e9;
}

/* ── Вирівнювання: питаємо ядро (див. вище) ────────────────────────────────── */

struct align { size_t mem, off; };

static struct align dio_align(int fd)
{
    struct align a = { 4096, 4096 };
    struct statx stx;

    if (statx(fd, "", AT_EMPTY_PATH, STATX_DIOALIGN, &stx) == 0
        && (stx.stx_mask & STATX_DIOALIGN) && stx.stx_dio_mem_align) {
        a.mem = stx.stx_dio_mem_align;
        a.off = stx.stx_dio_offset_align;
    }
    return a;
}

/* ── Скільки байтів файлу зараз лежить у кеші сторінок ─────────────────────── */
/* mmap сам нічого не читає, а mincore каже, які сторінки відображення вже
   резидентні. Ядро віддає правду лише тому, хто МІГ БИ відкрити цей файл на
   запис; решті воно заповнює вектор одиницями — латка бічного каналу з Linux
   5.0. Свої файли міряти можна, чужі — ні.                                  */

static long long cached(const char *path)
{
    size_t page = (size_t)sysconf(_SC_PAGESIZE), n, i;
    long long sum = 0;
    unsigned char *vec;
    struct stat st;
    void *m;
    int fd = open(path, O_RDONLY);

    if (fd < 0) return -1;
    if (fstat(fd, &st) || st.st_size <= 0) { close(fd); return -1; }
    m = mmap(NULL, (size_t)st.st_size, PROT_READ, MAP_SHARED, fd, 0);
    close(fd);                       /* відображення само тримає файл живим */
    if (m == MAP_FAILED) return -1;

    n = ((size_t)st.st_size + page - 1) / page;
    vec = malloc(n);
    if (vec && mincore(m, (size_t)st.st_size, vec) == 0)
        for (i = 0; i < n; i++)
            sum += (vec[i] & 1) ? (long long)page : 0;
    else
        sum = -1;
    free(vec);
    munmap(m, (size_t)st.st_size);
    return sum;
}

/* ── Двигун: qd порцій у польоті, кожна проходить читання → запис ──────────── */

static int pump(struct io_uring *ring, int in, int out, off_t size,
                size_t blk, size_t offal, struct slot *s, int qd)
{
    int freelist[MAXQD], nfree = 0, inflight = 0, i;
    struct io_uring_sqe *sqe;
    struct io_uring_cqe *cqe;
    off_t next = 0;

    for (i = qd - 1; i >= 0; i--)
        freelist[nfree++] = i;

    while (next < size || inflight) {
        while (nfree && next < size) {          /* набиваємо чергу читаннями */
            size_t want;

            i = freelist[--nfree];
            want = (size - next) < (off_t)blk ? (size_t)(size - next) : blk;
            s[i].off  = next;
            s[i].len  = up(want, offal);        /* хвіст округлюємо вгору    */
            s[i].done = 0;
            if (s[i].len > want)                /* і зануляємо доповнення    */
                memset(s[i].buf + want, 0, s[i].len - want);

            sqe = io_uring_get_sqe(ring);       /* кільце вдвічі більше за qd,
                                                   тож NULL тут неможливий  */
            io_uring_prep_read(sqe, in, s[i].buf, (unsigned)s[i].len, s[i].off);
            io_uring_sqe_set_data(sqe, (void *)(uintptr_t)((unsigned)i << 1 | OP_READ));
            next += (off_t)want;
            inflight++;
        }
        if (io_uring_submit(ring) < 0) { perror("io_uring_submit"); return -1; }

        if (io_uring_wait_cqe(ring, &cqe) < 0) { perror("io_uring_wait_cqe"); return -1; }
        do {                                    /* чекаємо на одне, забираємо всі готові */
            uintptr_t d = (uintptr_t)io_uring_cqe_get_data(cqe);
            int op = (int)(d & 1), res = cqe->res;

            i = (int)(d >> 1);
            io_uring_cqe_seen(ring, cqe);
            if (res < 0) {
                errno = -res;                   /* io_uring кладе −errno у res */
                perror(op == OP_READ ? "read" : "write");
                return -1;
            }
            s[i].done += (size_t)res;

            /* Коротка відповідь буває двічі. На кінці файлу читання поверне
               менше, ніж просили, — це не помилка, решту буфера ми занулили
               заздалегідь. Посеред файлу вона теж можлива; тоді доподаємо
               залишок тим самим оператором. Результат прямого обміну кратний
               блоку, тож зміщення лишається законним; коли ядро вимагає для
               пам'яті більшого вирівнювання, ніж для зміщень, залишок треба
               спершу пересунути на початок буфера.                          */
            if (op == OP_READ && s[i].off + (off_t)s[i].done >= size)
                s[i].done = s[i].len;

            if (s[i].done < s[i].len) {
                size_t rest = s[i].len - s[i].done;
                off_t  at   = s[i].off + (off_t)s[i].done;

                sqe = io_uring_get_sqe(ring);
                if (op == OP_READ)
                    io_uring_prep_read(sqe, in, s[i].buf + s[i].done, (unsigned)rest, at);
                else
                    io_uring_prep_write(sqe, out, s[i].buf + s[i].done, (unsigned)rest, at);
                io_uring_sqe_set_data(sqe, (void *)(uintptr_t)((unsigned)i << 1 | (unsigned)op));
            } else if (op == OP_READ) {         /* прочитали — пишемо тим самим буфером */
                s[i].done = 0;
                sqe = io_uring_get_sqe(ring);
                io_uring_prep_write(sqe, out, s[i].buf, (unsigned)s[i].len, s[i].off);
                io_uring_sqe_set_data(sqe, (void *)(uintptr_t)((unsigned)i << 1 | OP_WRITE));
            } else {                            /* порція закрита — слот вільний */
                freelist[nfree++] = i;
                inflight--;
            }
        } while (io_uring_peek_cqe(ring, &cqe) == 0);
    }
    return 0;
}

int main(int argc, char **argv)
{
    size_t blk = 1u << 20, bufal;
    int qd = 32, direct = 1, opt, in, out, i;
    struct io_uring ring;
    struct slot s[MAXQD];
    struct align a, b;
    struct stat st;
    double t0, t1;
    off_t size;

    while ((opt = getopt(argc, argv, "d:b:B")) != -1)
        switch (opt) {
        case 'd': qd = atoi(optarg); break;
        case 'b': blk = (size_t)atoi(optarg) << 10; break;
        case 'B': direct = 0; break;
        default:  return 2;
        }
    if (qd < 1 || qd > MAXQD || optind + 2 > argc) {
        fprintf(stderr, "вжиток: dcopy [-d глибина] [-b блок,КіБ] [-B] джерело ціль\n");
        return 2;
    }

    /* Саме тут ловиться EINVAL від файлових систем, які прямого шляху не мають. */
    in = open(argv[optind], O_RDONLY | (direct ? O_DIRECT : 0));
    if (in < 0) { perror(argv[optind]); return 1; }
    out = open(argv[optind + 1], O_WRONLY | O_CREAT | O_TRUNC | (direct ? O_DIRECT : 0), 0644);
    if (out < 0) { perror(argv[optind + 1]); return 1; }
    if (fstat(in, &st)) { perror("fstat"); return 1; }
    size = st.st_size;

    a = dio_align(in);
    b = dio_align(out);
    if (b.mem > a.mem) a.mem = b.mem;
    if (b.off > a.off) a.off = b.off;
    blk = up(blk, a.off);
    bufal = a.mem > a.off ? a.mem : a.off;

    /* Місце під ціль беремо одним рухом: інакше кожен запис, що продовжує
       файл, тягне за собою зміну розміру, тобто роботу з метаданими.       */
    if (fallocate(out, 0, 0, size) && errno != EOPNOTSUPP)
        perror("fallocate (не критично)");

    for (i = 0; i < qd; i++)
        if (posix_memalign((void **)&s[i].buf, bufal, blk)) {
            fprintf(stderr, "posix_memalign: немає пам'яті\n");
            return 1;
        }
    if (io_uring_queue_init((unsigned)qd * 2, &ring, 0) < 0) {
        perror("io_uring_queue_init");
        return 1;
    }

    printf("вирівнювання: пам'ять %zu, зміщення %zu; блок %zu КіБ; глибина %d; %s\n",
           a.mem, a.off, blk >> 10, qd, direct ? "O_DIRECT" : "буферизовано");

    t0 = now();
    if (pump(&ring, in, out, size, blk, a.off, s, qd))
        return 1;
    if (ftruncate(out, size)) perror("ftruncate");   /* зрізаємо доповнення хвоста */
    if (fdatasync(out))       perror("fdatasync");   /* прапорець довговічності не дає */
    t1 = now();

    printf("%.2f с, %.0f МБ/с\n", t1 - t0, (double)size / 1e6 / (t1 - t0));
    printf("у кеші після: джерело %lld МіБ, ціль %lld МіБ\n",
           cached(argv[optind]) >> 20, cached(argv[optind + 1]) >> 20);

    io_uring_queue_exit(&ring);
    close(in);
    close(out);
    return 0;
}
```

Слот тут — це буфер разом із його порцією файлу, і живе він весь шлях порції: спершу в нього читають, потім із нього ж пишуть, і аж тоді він повертається у вільний список. Тому програма займає рівно `глибина × блок` пам'яті й від розміру файлу не залежить зовсім. Кільце [io_uring](book:unix-linux/io-uring) тут потрібне саме для глибини: воно дозволяє тримати десятки запитів у польоті з одного потоку, тоді як звичайний `pread` тримав би рівно один.

## Глибина черги проти розміру блоку

Виміри — x86-64, вісім ядер, 16 ГіБ пам'яті, ext4 на NVMe PCIe 4.0 з паспортними 7.0 ГБ/с, ядро 6.8. Файл на 8 ГіБ, джерело й ціль на одному носії.

```
$ dd if=/dev/urandom of=src.bin bs=1M count=8192
$ sync; sudo sysctl -w vm.drop_caches=3        # перед КОЖНИМ прогоном
$ rm -f dst.bin && ./dcopy -d 8 -b 1024 src.bin dst.bin
```

Груба зброя `drop_caches` тут доречна саме тому, що вимірів кілька й вони йдуть підряд: точковіший `posix_fadvise(POSIX_FADV_DONTNEED)` на обидва файли зробив би те саме, але брудних сторінок цілі він не викидає, тож після буферизованого прогону перед ним довелося б викликати `fsync`. Пропускна здатність у мегабайтах за секунду:

| блок \ глибина | 1 | 8 | 32 |
|---|---|---|---|
| 4 КіБ | 28 | 215 | 690 |
| 64 КіБ | 390 | 2350 | 3280 |
| 1 МіБ | 2380 | 3430 | 3450 |

Лівий верхній кут пояснюється арифметикою без жодних припущень:

```
затримка читання 4 КіБ з NVMe          ≈  80 мкс
затримка запису 4 КіБ                  ≈  65 мкс
одна порція = читання + запис          = 145 мкс
пропускна здатність = 4096 / 145·10⁻⁶  ≈  28 МБ/с
```

Двадцять вісім мегабайтів на секунду з носія, здатного на сім гігабайтів. Права колонка того самого рядка показує, чим це лікується: глибина 32 збільшує потік у двадцять п'ять разів, бо носій нарешті має що робити, поки програма розбирає попередні відповіді.

Нижній рядок показує другий важіль. Мегабайтова порція сама по собі тримає пристрій зайнятим 150 мікросекунд, тож навіть при глибині один затримка розчиняється в переносі, і вся додаткова глибина додає лише 45%. Стелю ж задає не програма:

```
паспортна швидкість носія            = 7.0 ГБ/с
кожен байт проходить двічі: читання + запис
стеля копіювання на одному носії     = 7.0 / 2 = 3.5 ГБ/с
```

Три з половиною гігабайти — це те, що видно в правому нижньому куті таблиці. Далі впирається вже не код, а сам носій: один пристрій на два потоки даних.

> 🔧 **Навіщо це.** Глибина й розмір блоку заступають дві різні служби кеша, і плутати їх дорого. Великий блок заступає групування дрібних записів: порція приходить на пристрій уже однією великою операцією. Глибина заступає читання наперед: поки одна порція їде, наступні вже замовлені. Програмі з дрібними випадковими запитами великий блок узяти нізвідки — їй лишається сама лише глибина, і саме тому бази даних міряють свій ввід-вивід у запитах за секунду, а не в мегабайтах.

## Прямий проти буферизованого

Той самий двигун, той самий файл, блок 1 МіБ, глибина 8, холодний кеш перед кожним прогоном:

| режим | час, с | МБ/с | кеш: джерело | кеш: ціль |
|---|---|---|---|---|
| прямий, `O_DIRECT` | 2.50 | 3436 | 0 МіБ | 0 МіБ |
| буферизований | 2.86 | 3004 | 8192 МіБ | 4870 МіБ |
| буферизований, `fdatasync` поза виміром | 1.10 | 7809 | 8192 МіБ | 4870 МіБ |

Перші два рядки й дають головну відповідь: за швидкістю шляхи майже рівні, за наслідками — ні. Буферизований прогін виштовхав із пам'яті все, що там було, і поклав на звільнене місце 13 гігабайтів, які більше ніколи нікому не знадобляться. Ціль потрапила в кеш не цілком саме тому, що на неї вже не вистачило: копія почала витісняти сама себе.

Третій рядок — найдорожча пастка виміру. Винести `fdatasync` за межі секундоміра означає зупинити його тоді, коли байти лежать у кеші, а не на носії: 7809 мегабайтів на секунду носій не приймав ніколи, він просто ще не бачив більшої частини цього запису. Прямому шляху така помилка недоступна — його `write` повертається, коли пристрій відповів.

Одне застереження про чесність порівняння: на буферизованому файлі io_uring не завжди справді асинхронний. Читання, які не знайшлися в кеші, від ядра 5.9 виконуються без блокування, а от буферизовані записи ядро віддає робочим потокам — тож глибина 8 у другому рядку насправді означає вісім потоків, які пишуть у кеш, а не вісім запитів у пристрої. На спільний висновок це не впливає, але на мікровиміри — так.

## Пастки

**Прапорець спрацював не всюди.** Рядок «у кеші після» і є перевіркою: якщо після прямого прогону там не нуль, обмін ішов через кеш. На tmpfs `open` чесно провалюється з `EINVAL`; btrfs завжди повертає пряме читання стисненого вмісту до буферизованого; мережеві й накладкові (overlay) файлові системи поводяться по-різному. Мовчазне повернення небезпечніше за помилку саме тим, що програма далі вважає, ніби пам'яті не займає.

**`fallocate` прибирає не всі метадані.** Виділене місце лягає в дерево екстентів як «невиписане», і перший запис у кожен такий екстент вимагає перевести його в звичайний — це транзакція журналу на завершенні операції. Рушії, яким потрібна стабільна затримка, тому один раз пишуть нулі по всьому виділеному файлу під час створення, а не покладаються на саме резервування ([контракт розріджених операцій](book:unix-linux/sparse-files/api-sparse-syscalls.md) — вісім режимів `fallocate` і що кожен робить із блоками й розміром).

**`fdatasync` наприкінці не декоративний.** Прямий запис доїжджає до контролера, а не до пластини: енергозалежний кеш на платі накопичувача підтверджує прийом одразу. Прапорець `O_DIRECT` цього кеша не скидає й скидати не вміє ([кеш сторінок, fsync і довговічність запису](book:unix-linux/page-cache-durability) — де саме закінчується обіцянка кожного виклику).

**Глибина коштує закріпленої пам'яті.** Кожен буфер у польоті — це сторінки, які ядро закріпило й не може ані витіснити, ані пересунути. Глибина 32 при мегабайтовому блоці — це 32 МіБ такої пам'яті; глибина 512 при тому самому блоці — половина гігабайта, вирвана з-під усієї машини. Понад те, пристрій має власну межу черги (`/sys/block/nvme0n1/queue/nr_requests`), за якою запити просто стоять у ядрі й додають затримки, не додаючи швидкості.

**Джерело й ціль на одному носії ділять смугу навпіл.** Таблиця вище зроблена саме так, і стеля в ній — 3.5 ГБ/с замість 7.0. Той самий код на двох різних накопичувачах дає близько семи, не змінившись ані рядком.

**Копіювати руками, може, не треба зовсім.** `copy_file_range` переносить дані всередині ядра, не піднімаючи їх у простір користувача, а на btrfs і XFS у межах однієї файлової системи взагалі створює посилання на ті самі блоки замість копії. Ця програма має сенс тоді, коли копіювання — привід зрозуміти механізм, або коли байти справді мусять пройти через пам'ять процесу: перевірка контрольної суми, шифрування, зміна формату ([передача без копіювання](book:unix-linux/zero-copy) — виклики, які пересувають дані, не заводячи їх у програму).
