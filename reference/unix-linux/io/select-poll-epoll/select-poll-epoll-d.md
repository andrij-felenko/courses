Уявімо службу, до якої підключено десять тисяч клієнтів. Більшість мовчить: з'єднання відкрите, але нічого не надсилає — чат із зачиненим вікном, застосунок у фоні, датчик, що озивається раз на хвилину. У будь-яку мить дані є, скажімо, на двохстах з'єднаннях. На яких саме — програма не знає.

Найпростіша відповідь: спитати кожне. Обійти всі десять тисяч дескрипторів, кожному сказати «дай, що є», і обслужити ті двісті, що відповіли байтами. Але дев'ять тисяч вісімсот разів ми дістанемо «нічого немає» — і кожна така відповідь коштує повного переходу в ядро й назад. Обхід, що триває мілісекунди й на дві сотих складається з корисної роботи, з'їдає ціле ядро процесора; коротшим його не зробиш, бо кількість запитань задано наперед.

Друга відповідь така сама проста й така сама погана: заснути. Викликати `read` на першому з'єднанні й спати, доки прийдуть байти. Процесор тоді не витрачається зовсім — але потік застряг на одному дескрипторі, а решта дев'ять тисяч дев'ятсот дев'яносто дев'ять чекають на нього. Один потік уміє чекати рівно на одну річ.

Обидві відповіді хибні з тієї самої причини: **у них програма з'ясовує стан з'єднань сама**. Тим часом стан кожного буфера прийому вже відомий — його веде ядро. Мережевий стек розклав пакети по сокетах і достеменно знає, у котрих із них щось лежить. Питання не в тому, як програмі це вирахувати, а в тому, як попросити ядро сказати. Одним запитанням про всіх одразу — і не прокидатися, поки відповідь порожня.

Це і називають мультиплексуванням вводу-виводу (від лат. *multiplex* — багатоскладовий): один потік, одне засинання, багато джерел. У Unix його дають три інтерфейси — `select`, `poll` і `epoll`. Вони роблять на позір те саме, але різняться в одному місці, і саме це місце визначає, скільки з'єднань служба потягне.

## Одна задача, багато черг

Механізм, на якому все тримається, уже є в ядрі — його лишається тільки застосувати не до одного об'єкта, а до багатьох.

Коли задача блокується на порожньому сокеті, ядро записує її в **чергу очікування** цього сокета: список тих, кого треба розбудити, коли тут щось станеться. Потім переводить задачу в сплячий стан і віддає процесор іншим. Прийшов пакет — мережевий стек будить чергу, задача знову стає готовою.

Нічого в цій конструкції не вимагає, щоб черга була одна. Задача — це запис у списку; записів можна лишити скільки завгодно й у скількох завгодно списках. Тож послідовність така: пройтися по всіх дескрипторах, у кожному записатися в чергу, потім заснути один раз. Пробудження від будь-якої з черг повертає задачу до життя, і далі лишається з'ясувати, хто саме її розбудив, — обійти дескриптори ще раз і зібрати їхні стани. Наприкінці записи з усіх черг треба прибрати.

Щоб цей обхід узагалі був можливий, кожен вид об'єкта мусить уміти дві речі: сказати свою поточну готовність і прийняти задачу в свою чергу. У ядрі це один метод у таблиці операцій файлу — той самий для сокета, каналу, термінала й `eventfd`, лише реалізований по-різному. Тут «усе є файлом» перестає бути гаслом і стає технічною умовою: без єдиного інтерфейсу очікування не було б жодної можливості чекати на сокет і на канал одним викликом ([«усе є файлом»](book:unix-linux/everything-is-a-file) — довільно різні об'єкти сховано за спільним набором операцій, і саме тому їх можна змішувати в одному списку).

Отже, примітив у ядрі є, і він однаковий для всіх трьох інтерфейсів. Уся різниця між `select`, `poll` та `epoll` — у тому, **як програма передає ядру список і хто зберігає його між викликами**. Це звучить як дрібниця про формат аргументів. Це не дрібниця.

## select: три бітові маски

`select` з'явився у 4.2BSD (1983) — за часів, коли «багато дескрипторів» означало десяток. Його форма несе на собі відбиток тієї доби.

Список передають не переліком, а **бітовою мапою**: тип `fd_set` — це масив бітів, де біт номер *k* означає «мене цікавить дескриптор *k*». Мап три, за трьома видами інтересу: читання, запис, виняткові стани. Ядро сканує біти від нуля до `nfds`, де `nfds` треба передати самому — на одиницю більше за найбільший дескриптор у мапах.

:::tabs
== C (системний виклик POSIX)
```c
fd_set rfds;
struct timeval tv;

for (;;) {
    FD_ZERO(&rfds);                     /* мапу доводиться будувати щоразу заново */
    int maxfd = 0;
    for (int i = 0; i < nconn; i++) {
        FD_SET(conn[i].fd, &rfds);
        if (conn[i].fd > maxfd) maxfd = conn[i].fd;
    }
    tv.tv_sec = 1; tv.tv_usec = 0;      /* Linux змінює tv — теж щоразу наново */

    int n = select(maxfd + 1, &rfds, NULL, NULL, &tv);
    if (n < 0) { if (errno == EINTR) continue; die("select"); }

    for (int i = 0; i < nconn; i++)     /* хто саме готовий — знову шукаємо перебором */
        if (FD_ISSET(conn[i].fd, &rfds))
            handle(&conn[i]);
}
```
== C++ (стандартна функція std::max та контейнер)
```cpp
fd_set rfds;
struct timeval tv;

for (;;) {
    FD_ZERO(&rfds);
    int maxfd = 0;
    for (const auto& c : conn) {
        FD_SET(c.fd, &rfds);
        maxfd = std::max(maxfd, c.fd);
    }
    tv.tv_sec = 1; tv.tv_usec = 0;

    int n = select(maxfd + 1, &rfds, nullptr, nullptr, &tv);
    if (n < 0) {
        if (errno == EINTR) continue;
        throw std::system_error(errno, std::generic_category(), "select");
    }

    for (auto& c : conn) {
        if (FD_ISSET(c.fd, &rfds)) {
            handle(c);
        }
    }
}
```
:::

Три рядки цього коду варті окремої уваги, бо кожен — наслідок форми аргументів.

**Мапи руйнуються.** `select` не має окремих полів «питаю» і «відповідаю»: він переписує ті самі мапи, лишаючи в них тільки готові дескриптори. Після виклику список інтересу зникає, і будувати його доводиться з нуля на кожному оберті циклу. Це не помилка вжитку — так задумано, і в довідці це прямо названо хибою конструкції, якої в наступниках уже немає.

**Стеля вшита в тип.** `fd_set` має сталий розмір: у glibc це `FD_SETSIZE` = 1024 біти. Дескриптор із номером 1024 і вище в мапу просто не влазить — а `FD_SET` для нього псує чужу пам'ять поруч, мовчки й без жодної діагностики. Змінити `FD_SETSIZE` неможливо: це не налаштування, а частина двійкового інтерфейсу, спільна для програми, бібліотек і ядра.

**Ціна залежить від номерів, а не від кількості.** Ядро сканує біти підряд від нуля до `nfds`. Три відкриті з'єднання з номерами 5, 6 і 900 змусять його переглянути дев'ятсот одну позицію. Дескриптори видають найменшим вільним номером ([файловий дескриптор](book:unix-linux/file-descriptor)), тож у довгоживучій службі номери розповзаються, і робота росте разом із ними.

Дрібніша, але дошкульна деталь — таймаут. `struct timeval` задає час у мікросекундах, і на Linux `select` **змінює його на місці**, лишаючи там недоспаний залишок. Більшість інших систем цього не робить, тож переносний код мусить заповнювати структуру заново перед кожним викликом і не має права робити висновків з того, що там лишилося.

## poll: масив замість масок

`poll` прийшов зі System V Release 3 (1987) і виправляє саме форму, не глибину. Замість бітових мап — масив записів, по одному на дескриптор:

```c
struct pollfd {
    int   fd;         /* за яким дескриптором стежимо      */
    short events;     /* що нас цікавить — заповнює програма */
    short revents;    /* що сталося — заповнює ядро          */
};
```

Розділення `events` і `revents` знімає головний клопіт `select`: масив між викликами не псується, ядро пише тільки в поле відповіді. Один раз збудували — і крутимо цикл, чіпаючи лише `revents`.

:::tabs
== C (системний виклик POSIX)
```c
struct pollfd *pfd = calloc(nconn, sizeof *pfd);
for (int i = 0; i < nconn; i++) {
    pfd[i].fd = conn[i].fd;
    pfd[i].events = POLLIN;             /* масив живий між обертами циклу */
}

for (;;) {
    int n = poll(pfd, nconn, 1000);
    if (n < 0) { if (errno == EINTR) continue; die("poll"); }

    for (int i = 0; i < nconn && n > 0; i++) {
        if (!pfd[i].revents) continue;
        n--;
        handle(&conn[i], pfd[i].revents);
    }
}
```
== C++ (стандартний контейнер std::vector)
```cpp
std::vector<struct pollfd> pfd;
pfd.reserve(conn.size());
for (const auto& c : conn) {
    pfd.push_back({.fd = c.fd, .events = POLLIN, .revents = 0});
}

for (;;) {
    int n = poll(pfd.data(), static_cast<nfds_t>(pfd.size()), 1000);
    if (n < 0) {
        if (errno == EINTR) continue;
        throw std::system_error(errno, std::generic_category(), "poll");
    }

    for (size_t i = 0; i < pfd.size() && n > 0; ++i) {
        if (!pfd[i].revents) continue;
        --n;
        handle(conn[i], pfd[i].revents);
    }
}
```
:::

Разом із зручністю зникла й стеля: кількість записів обмежена хіба що лімітом на відкриті файли, а номер дескриптора більше нічого не важить — робота залежить від довжини масиву, а не від значень усередині. Набір станів теж став точнішим: `POLLHUP` (інший бік закрив), `POLLERR` (помилка на об'єкті), `POLLNVAL` (у полі `fd` не дескриптор) розрізняються між собою, тоді як `select` перші два подавав однаково — просто «готовий до читання», — а на закритому дескрипторі валив увесь виклик помилкою `EBADF`, не кажучи, який саме з тисячі номерів зіпсовано.

І все ж `poll` — це той самий `select` з іншим синтаксисом. У Linux обидва зроблено над однією внутрішньою машинерією: ядро так само обходить кожен запис, так само записує задачу в кожну чергу, так само обходить усе вдруге після пробудження. Форма аргументів стала людською; **робота лишилася пропорційною довжині списку**.

## Чому пропорційність списку — це стеля

Порахуймо, у що обходиться один оберт циклу на десяти тисячах з'єднань, з яких активні двісті.

**Умова: 10 000 з'єднань, події на 200 із них, `poll` із таймаутом.**

```
записів у масиві            = 10 000
байтів на запис             = 8              (struct pollfd)
копіювання в ядро           = 10 000 · 8 = 80 КБ  (увесь масив)
копіювання назад            = 10 000 · 2 = 20 КБ  (самі лише revents)
запис у черги очікування    = 10 000 разів   (кожна — під замком свого об'єкта)
обхід після пробудження     = 10 000 разів
прибирання з черг           = 10 000 разів
корисних записів у відповіді = 200            = 2 %

ціна одного обходу          ≈ 0.2 мс         (виміряно 215 мкс)
подій за секунду            = 20 000
подій за один виклик        ≈ 200
викликів за секунду         = 100
процесорний час на poll     ≈ 100 · 0.2 мс = 0.02 с/с ≈ 2 % одного ядра
```

Два відсотки ядра — ще не катастрофа, і навіть на навантаженій машині, де сокети справжні мережеві, кеші холодні, а за замки черг очікування є суперечка, той самий обхід подорожчає в кілька разів, не більше. Катастрофа в тому, **за чим ця цифра росте**. Подвойте число мовчазних з'єднань, не додавши ані байта трафіку, — і вона подвоїться. Робота пропорційна тому, чого ви не просили робити: кожен виклик заново розповідає ядру про дев'ять тисяч вісімсот з'єднань, на яких нічого не сталося й не станеться. При ста тисячах з'єднань один обхід коштує вже понад дві мілісекунди, і якщо трафік виріс так само вдесятеро, самі лише переліки забирають два ядра з гаком, а затримка обробки події росте разом із довжиною масиву — бо подію не побачать, доки обхід не дійде до її запису.

Оце і є справжня стеля. Не швидкість системного виклику, не пропускна здатність мережі, а те, що **ціна очікування прив'язана до кількості з'єднань, а не до кількості подій**. Наприкінці дев'яностих у цю стелю вперлися всі одразу, і в неї навіть з'явилося ім'я — задача десяти тисяч клієнтів ([як народилася задача C10k](book:unix-linux/select-poll-epoll/hist-c10k.md): звідки взялося саме число десять тисяч, які механізми пробували до `epoll` — сигнали реального часу, `/dev/poll` у Solaris, `kqueue` у FreeBSD — і чому переміг варіант, що з'явився останнім).

> 🔧 **Навіщо це.** Служба на `poll`, яка «раптом почала гальмувати», часто не гальмує, а просто набрала з'єднань. Перевірка займає хвилину: `strace -c -p <pid>` покаже частку часу в `poll`, а `ls /proc/<pid>/fd | wc -l` — довжину масиву. Якщо час у `poll` росте лінійно з числом дескрипторів, а трафік стоїть на місці, це не привід оптимізувати обробники — це привід міняти інтерфейс очікування.

## Список майже не змінюється

Погляньте на цикл `poll` ще раз і спитайте: **наскільки масив відрізняється від того, що був мілісекунду тому?** На десяти тисячах з'єднань за оберт додається кілька нових і зникає кілька закритих. Решта — та сама, байт у байт.

Тобто програма щоразу пересилає в ядро те, що ядро вже знає, і змушує його щоразу наново будувати те, що воно щойно розібрало. Уся зайва робота — це переказ незміненого.

Звідси й рішення, і воно єдине можливе: **хай список живе в ядрі**. Програма один раз каже, що її цікавить, потім лише повідомляє про зміни, а на очікування ходить із порожніми руками. Один виклик доводиться розділити на три — і саме так побудовано `epoll` (від *event poll* — опитування подій):

:::tabs
== C (системний виклик POSIX)
```c
int ep = epoll_create1(EPOLL_CLOEXEC);          /* завести список у ядрі */

struct epoll_event ev = { .events = EPOLLIN, .data.ptr = &conn[i] };
epoll_ctl(ep, EPOLL_CTL_ADD, conn[i].fd, &ev);  /* змінити список */

struct epoll_event out[64];
int n = epoll_wait(ep, out, 64, 1000);          /* чекати; повертає лише готові */
```
== C++ (клас-обгортка та масив std::array)
```cpp
class Epoll {
    int epfd_;
public:
    Epoll() : epfd_(epoll_create1(EPOLL_CLOEXEC)) {
        if (epfd_ < 0) throw std::system_error(errno, std::generic_category(), "epoll_create1");
    }
    ~Epoll() { if (epfd_ >= 0) ::close(epfd_); }

    void add(int fd, uint32_t events, void* ptr) {
        struct epoll_event ev{};
        ev.events = events;
        ev.data.ptr = ptr;
        if (epoll_ctl(epfd_, EPOLL_CTL_ADD, fd, &ev) < 0) {
            throw std::system_error(errno, std::generic_category(), "epoll_ctl");
        }
    }

    int wait(std::span<struct epoll_event> events, int timeout_ms) {
        int n = epoll_wait(epfd_, events.data(), static_cast<int>(events.size()), timeout_ms);
        if (n < 0 && errno != EINTR) throw std::system_error(errno, std::generic_category(), "epoll_wait");
        return n;
    }
};

Epoll ep;
ep.add(conn[i].fd, EPOLLIN, &conn[i]);

std::array<struct epoll_event, 64> out;
int n = ep.wait(out, 1000);
```
:::

Дрібниця з великими наслідками: `epoll_create1` повертає **звичайний дескриптор**. Набір спостереження — такий самий об'єкт ядра, як сокет чи канал, і його можна закрити, успадкувати, передати іншому процесові, а головне — вкласти в інший `epoll`. Бібліотеки цим користуються: кожна тримає власний набір і віддає застосункові один дескриптор, який той укладає у свій цикл подій.

Поле `data` — вісім байтів, які ядро зберігає й повертає без змін. Туди кладуть не номер дескриптора, а вказівник на структуру з'єднання, і обробник дістає весь контекст без жодного пошуку. Дрібна на вигляд зручність насправді знімає останнє місце, де лишався перебір: у циклі на `poll` за індексом у масиві ще треба знайти з'єднання.

## Хто кому каже про готовність

Зберігання списку в ядрі економить копіювання. Але сама собою ця економія не прибрала б обходу: ядро все одно могло б перебирати збережений список на кожному `epoll_wait`. `epoll` швидкий не тому, а через глибшу переміну — **у ньому змінено напрямок, у якому рухається звістка про готовність**.

У `select` і `poll` звістка йде на вимогу: програма питає, ядро в цю мить обходить файли й з'ясовує їхній стан. У `epoll` вона йде сама, у мить події.

Ось як це влаштовано. `epoll_ctl(EPOLL_CTL_ADD)` створює в ядрі невеликий запис — `epitem` — і кладе його у **червоно-чорне дерево**, впорядковане так, щоб згодом швидко знайти запис за дескриптором ([червоно-чорне дерево](book:algorithms/red-black-tree) — збалансоване дерево пошуку, у якому вставка, видалення й пошук коштують логарифм від кількості елементів). Але важливіше друге: разом із записом у чергу очікування самого файлу вставляють **зворотний виклик**.

Тепер, коли на сокет приходять байти, мережевий стек робить те саме, що робив завжди, — будить чергу очікування цього сокета. Тільки в черзі тепер сидить не задача, а функція. Вона виконується просто там, у контексті пробудження, і робить одну дію: чіпляє `epitem` у **список готових** свого набору. Якщо в `epoll_wait` хтось спить — будить і його.

Наслідок, заради якого все й будувалося: `epoll_wait` не обходить набору. Він знімає готовий список і копіює його викликачеві. Робота пропорційна кількості подій — і цілком байдужа до того, скільки дескрипторів у наборі, десять чи мільйон.

![Ліворуч: на кожному виклику ядро обходить увесь список і питає кожен файл. Праворуч: зворотний виклик, вставлений один раз, кладе запис у список готових у мить події](/reference/unix-linux/io/select-poll-epoll/img/two-ways.svg)

*Робота ядра прив'язана або до довжини списку, або до кількості подій — залежно від того, хто кого питає.*

Ціни решти дій розкладаються так само чисто. `epoll_ctl` коштує логарифм — пошук і вставка в дереві. Реєстрація нового дескриптора одразу опитує його стан, тож сокет, у якому вже щось лежить, потрапляє в список готових негайно, а не після наступного пакета. Пам'ять — близько ста шістдесяти байтів на запис на 64-бітному ядрі, і кількість записів обмежує `/proc/sys/fs/epoll/max_user_watches`, щоб один користувач не з'їв пам'ять ядра наборами спостереження.

![Таблиця: що перетинає межу за виклик, стеля кількості дескрипторів, потреба перебудовувати список, робота ядра, джерело готовності — для select, poll і epoll](/reference/unix-linux/io/select-poll-epoll/img/cost-model.svg)

*Три інтерфейси розв'язують одну задачу; різняться вони тим, де зберігається список і хто з'ясовує готовність.*

Повний перелік того, чим саме керують ці виклики — прапорці подій, коди операцій `epoll_ctl`, поведінка `epoll_pwait` із маскою сигналів, помилки кожного виклику — зібрано окремо ([інтерфейси очікування](book:unix-linux/select-poll-epoll/api-epoll-interfaces.md): сигнатури `select`, `poll` і трьох викликів `epoll`, повна таблиця прапорців від `EPOLLIN` до `EPOLLEXCLUSIVE` із версією ядра, у якій кожен з'явився, і що означає кожен код помилки).

## Рівень і фронт

У `epoll` є режим, якого немає в попередників, і саме на ньому найчастіше ламаються.

Типова поведінка — **за рівнем** (англ. *level-triggered*, за аналогією з електронікою, де сигнал розрізняють за рівнем напруги або за перепадом). `epoll_wait` повертає дескриптор доти, доки умова тримається: є хоч байт у буфері — дескриптор готовий. Прочитали сто байтів із трьохсот — наступний виклик поверне його знову, бо двісті лишилося. Так само поводяться `select` і `poll`, тож перехід на `epoll` не змінює логіки обробника.

Режим **за фронтом** (`EPOLLET`, *edge-triggered*) повертає дескриптор тільки на **переході**: коли щось надійшло. Прочитали сто із трьохсот — і все, більше про ці двісті ніхто не нагадає. Дескриптор озветься наступного разу, коли ззовні прийде нова порція, а якщо клієнт замовк і чекає на відповідь, з'єднання завмре назавжди.

![Таблиця по мірі надходження й вичитування байтів: що повертає epoll_wait у режимі рівня і в режимі фронту](/reference/unix-linux/io/select-poll-epoll/img/level-vs-edge.svg)

*Один недовичитаний залишок у режимі фронту не породжує нового сповіщення — саме тому там читають у циклі до `EAGAIN`.*

Звідси єдине правило роботи за фронтом: **читати в циклі, доки `read` не поверне `EAGAIN`**. Порожня відповідь — це і є доказ, що буфер вичерпано й наступне надходження неодмінно дасть новий фронт. Те саме на записі: писати, доки `write` не впреться в `EAGAIN`. І тому фронт неможливий на блокуючих дескрипторах: останній `read` у такому циклі не мав би куди повернути «більше нічого» — він просто заснув би й зупинив цикл разом із усіма іншими з'єднаннями ([блокуючий і неблокуючий режим](book:unix-linux/blocking-and-nonblocking) — чому в циклі подій `O_NONBLOCK` обов'язковий, а не бажаний).

:::tabs
== C (системний виклик POSIX)
```c
for (;;) {
    ssize_t k = read(fd, buf, sizeof buf);
    if (k > 0)              { consume(buf, k); continue; }
    if (k == 0)             { peer_closed(fd); break; }
    if (errno == EINTR)     continue;
    if (errno == EAGAIN)    break;      /* єдиний коректний вихід із циклу */
    fail(fd, errno);        break;
}
```
== C++ (обгортка буфера std::span)
```cpp
std::array<char, 4096> buf;
for (;;) {
    ssize_t k = read(fd, buf.data(), buf.size());
    if (k > 0) {
        consume(std::span<const char>(buf.data(), static_cast<size_t>(k)));
        continue;
    }
    if (k == 0) {
        peer_closed(fd);
        break;
    }
    if (errno == EINTR) continue;
    if (errno == EAGAIN || errno == EWOULDBLOCK) break; /* єдиний вихід із циклу */
    throw std::system_error(errno, std::generic_category(), "read");
}
```
:::

Навіщо тоді фронт, якщо він дорожчий у супроводі? Заради двох речей. По-перше, за рівнем ядро на кожному `epoll_wait` перевіряє повернуті записи ще раз, щоб вирішити, чи лишати їх у списку готових; за фронтом цієї перевірки немає — на завантаженому сервері різниця помітна. По-друге й важливіше, за рівнем один і той самий дескриптор віддається всім, хто чекає: у пулі потоків на спільному наборі це означає, що на одну подію прокидаються кілька потоків, і всі, крім одного, дістають `EAGAIN` ([громовий табун](book:programming/thundering-herd) — юрба, розбуджена однією подією, з якої корисно спрацьовує лише хтось один). Фронт цю юрбу прибирає природно, бо перехід один.

Проміжний варіант — `EPOLLONESHOT`: подія віддається один раз, після чого дескриптор мовчить, доки його не переозброять через `epoll_ctl(EPOLL_CTL_MOD)`. Це дає головну гарантію для пулу потоків — з одним з'єднанням у будь-яку мить працює рівно один потік — ціною зайвого системного виклику на кожну подію ([пул потоків](book:programming/thread-pool)).

## Три пастки

**Набір тримається за опис, а не за номер.** Це джерело найзагадковіших помилок. `epoll_ctl` бере номер дескриптора, але ключем запису стає пара «номер + **опис відкритого файлу**», на який той указує, і живе запис рівно доти, доки живий опис ([опис відкритого файлу](book:unix-linux/open-file-description) — спільна структура, яку `dup` і `fork` не копіюють, а розділяють). Тому дескриптор зникає з набору лише тоді, коли закрито **всі** копії. Зробили `dup`, закрили оригінал — з'єднання далі в наборі й далі шле події, а `epoll_ctl(EPOLL_CTL_DEL)` за старим номером поверне `EBADF`, бо номера вже немає. Зворотний бік того ж механізму: після `close` останньої копії запис зникає сам, мовчки, і код, який чекав на прощальну подію, не дочекається її ніколи. Правило звідси однозначне: `EPOLL_CTL_DEL` перед `close`, завжди й без винятків.

**Вказівник переживає структуру.** У `data` кладуть вказівник на структуру з'єднання. Якщо з'єднання звільнили, а видалити з набору забули, наступна подія віддасть вказівник на звільнену пам'ять — і це вже не логічна помилка, а пошкодження пам'яті з падінням у випадковому місці. Порядок дій має бути незмінний: спершу `EPOLL_CTL_DEL`, потім `close`, і аж потім звільнення структури.

**Один жвавий дескриптор голодує решту.** `epoll_wait` віддає не більше подій, ніж уміщується в переданий масив, а решта чекає наступного виклику. Голодування береться не звідси: незабрані записи ядро повертає в голову списку готових, тож наступним викликом вони підуть першими. Голодує той, до кого не дійшли руки в **обробнику**: з'єднання, яке безперервно шле дані, здатне тримати цикл на собі, поки решта черги стоїть. У режимі фронту це загострюється: вичитування «до `EAGAIN`» на швидкому потоці може не закінчитися взагалі. Лікують межею — стільки-то байтів на з'єднання за оберт, далі запис у власну чергу «є ще робота» й перехід до наступного ([справедливість і квоти](book:programming/fairness-quotas) — як розподіляти обмежений ресурс між споживачами, не даючи найгучнішому забрати все).

> 🔧 **Навіщо це.** Дві найчастіші поломки циклів подій діагностуються без налагоджувача. З'єднання, які зависають назавжди після кількох повідомлень, — майже завжди `EPOLLET` без вичитування до `EAGAIN`. Стовідсоткове завантаження ядра при порожньому трафіку — майже завжди `EPOLLOUT`, який лишили ввімкненим, коли писати вже нічого: сокет із вільним буфером готовий до запису **завжди**, і цикл крутиться на ньому вхолосту. Перше видно в `strace` як тишу після часткового читання, друге — як нескінченний потік `epoll_wait`, що повертається негайно.

## Де готовність нічого не означає

Уся конструкція стоїть на припущенні, яке для сокетів і каналів очевидне, а поза ними хибне: що об'єкт **буває неготовим**.

Звичайний файл на диску неготовим не буває ніколи. Питання «чи є дані» для нього не має сенсу — дані там є за визначенням, питання лише в тому, скільки триватиме їх діставання. `select` і `poll` тому завжди позначають звичайний файл готовим, а `epoll_ctl` на ньому взагалі відмовляє з `EPERM`. Це не недогляд: у моделі готовності просто немає, що повідомляти.

І це не дрібний виняток, а межа самої моделі. Готовність повідомляє, що **можна діяти без чекання**; вона нічого не каже про операції, де чекання невіддільне від роботи. Читання з диска, `fsync`, розв'язання доменного імені лишаються синхронними, і в циклі подій кожна з них зупиняє все. Класичний обхідний шлях — окремий пул потоків, які блокуються замість вас; принциповий — інша модель, де ядро не сповіщає про можливість, а виконує операцію й доповідає про результат ([готовність проти завершення](book:unix-linux/readiness-vs-completion) — дві моделі вводу-виводу, у другій з яких питання «чи готовий» не ставиться взагалі; [io_uring](book:unix-linux/io-uring) — її втілення в Linux через кільця подань і завершень, однакове для сокетів і для файлів).

Зате все, що вміє бути неготовим, у Linux навмисно зроблено дескриптором — щоб потрапити в той самий набір. Таймер — `timerfd`, сигнал — `signalfd`, лічильник для пробудження циклу з іншого потоку — `eventfd`. Замість трьох різних механізмів очікування цикл подій має один ([eventfd і futex](book:unix-linux/eventfd-and-futex) — дешевий спосіб розбудити цикл ззовні; [маскування сигналів і signalfd](book:unix-linux/signal-mask-signalfd) — як асинхронне сповіщення перетворюють на читабельний дескриптор; [таймери процесу](book:unix-linux/process-timers) — те саме для часу).

## Що з цього виходить

`epoll` — інтерфейс Linux і більше нічий. У FreeBSD і macOS ту саму задачу розв'язує `kqueue` (Джонатан Лемон, FreeBSD 4.1, липень 2000), побудований на тій самій ідеї збереженого в ядрі набору, але з ширшим охопленням: одним механізмом він доставляє й готовність сокетів, і зміни у файлах, і завершення процесів, і таймери. Windows пішов іншою гілкою — порти завершення вводу-виводу, тобто модель не готовності, а завершення. Переносні бібліотеки циклів подій існують саме тому, що спільного інтерфейсу тут немає й не буде; вони ховають різницю під однаковим API ([цикл подій](book:programming/event-loop) — узагальнена архітектура «чекати на події, розкладати їх по обробниках», незалежна від того, чим саме реалізовано очікування).

Наскільки все це змістило стелю, найкраще видно в наших-таки числах. Цикл на `poll` з десятьма тисячами з'єднань витрачав на самі лише переліки два відсотки ядра, і ця частка подвоювалася з кожним подвоєнням мовчазних клієнтів: на ста тисячах — уже п'ята частина ядра при тому самому трафіку й два ядра з гаком, якщо трафік виріс разом із ними. Той самий цикл на `epoll` витрачає на переліки нуль: сто викликів за секунду, кожен віддає двісті готових записів, і про решту дев'ять тисяч вісімсот не згадують ніде. Зростання числа мовчазних з'єднань більше не додає роботи взагалі — воно додає лише пам'яті — близько ста шістдесяти байтів на запис у наборі плюс буфери сокета.

Тому й питання «скільки з'єднань потягнемо» після `epoll` звучить інакше. Воно перестало бути питанням про очікування — механізм очікування вже не залежить від кількості з'єднань — і стало питанням про пам'ять на одне з'єднання й про роботу на одну подію. Це не порада порівнювати варіанти на папері: різниця між `poll` і `epoll` — не кілька відсотків, які вимірюють, а різна залежність від числа клієнтів, яку видно на графіку одразу ([виміряти залежність своїми руками](book:unix-linux/select-poll-epoll/proj-scaling-measure.md): невелика програма на C, що тримає N з'єднань, з яких активне одне, і міряє час очікування для `select`, `poll` та `epoll` при N від сотні до ста тисяч — дві криві ростуть лінійно, третя лишається горизонтальною).
