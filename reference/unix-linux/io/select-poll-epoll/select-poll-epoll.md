Уявіть сервер, до якого підключено десять тисяч клієнтів. У більшості з'єднань нічого не відбувається, дані приходять лише на кількох десятках. Як програмі дізнатися, хто саме надіслав дані, не витрачаючи процесор даремно?

Якщо перевіряти кожне з'єднання по черзі, ми витратимо час на тисячі запитань «чи є щось?», отримуючи у відповідь порожнечу. Якщо викликати читання і заснути, програма зупиниться на одному з'єднанні й пропустить інші. Правильний шлях — віддати список усіх з'єднань ядру операційної системи й сказати: «розбуди мене, коли хоч на одному з них щось з'явиться». Це називають мультиплексуванням вводу-виводу.

## select і poll: опитування за списком

Історично першими були `select` та `poll`. Їхній принцип простий: програма передає ядру повний перелік дескрипторів, які її цікавлять, і засинає. Ядро перевіряє кожен із них. Коли надходять дані, ядро знову перебирає весь список і позначає ті, що готові. Програма прокидається, шукає у списку готові дескриптори й обробляє їх.

Цей підхід добре працює для сотні з'єднань, але на десятках тисяч стає проблемою. **Робота ядра тут пропорційна загальній кількості з'єднань**, а не кількості тих, що надіслали дані. З кожним викликом програма змушена передавати величезний список, який майже не змінився, а ядро — перевіряти тисячі мовчазних клієнтів.

## epoll: список у ядрі та сповіщення від подій

Щоб уникнути зайвої роботи, у Linux створили `epoll`. Він змінює дві ключові речі:

1. **Список зберігається в ядрі.** Програма більше не передає тисячі дескрипторів на кожному кроці. Вона створює набір один раз, а потім лише додає або видаляє з нього з'єднання.
2. **Готовність з'ясовується в мить події.** Коли на сокет приходять дані, мережевий стек негайно додає цей сокет до невеликого "списку готових".

Коли програма викликає `epoll_wait`, ядро нічого не перевіряє — воно просто бере список тих, хто вже готовий, і віддає його. Тепер **робота ядра пропорційна лише кількості подій**, і зовсім не залежить від того, скільки всього клієнтів тримає сервер.

Робота з `epoll` складається з трьох кроків:
- `epoll_create` — створює набір у ядрі (сам повертається як дескриптор).
- `epoll_ctl` — додає, змінює або видаляє дескриптори з набору.
- `epoll_wait` — зупиняє програму, доки не з'являться готові дескриптори, і повертає лише їх.

:::tabs
== C
```c
int ep = epoll_create1(0);

// Додаємо з'єднання в набір
struct epoll_event ev = { .events = EPOLLIN, .data.fd = conn_fd };
epoll_ctl(ep, EPOLL_CTL_ADD, conn_fd, &ev);

struct epoll_event events[64];
for (;;) {
    // Чекаємо на події. Повернуться лише готові.
    int n = epoll_wait(ep, events, 64, -1);
    for (int i = 0; i < n; i++) {
        handle_data(events[i].data.fd);
    }
}
```
== Python
```python
import select

ep = select.epoll()

# Додаємо з'єднання в набір, цікавить готовність до читання
ep.register(conn_fd, select.EPOLLIN)

while True:
    # Чекаємо на події
    events = ep.poll(-1)
    for fd, event in events:
        handle_data(fd)
```
:::

## Рівень і фронт (Level vs Edge Triggered)

Ще одна відмінність `epoll` — два режими сповіщень.

Типовий режим — **за рівнем (Level Triggered)**. Поки в буфері сокета є хоча б один байт, `epoll_wait` щоразу казатиме, що сокет готовий. Ви можете прочитати частину даних, і наступний виклик знову нагадає про залишок. Це пробачає помилки, але на серверах із високим навантаженням постійні нагадування можуть бути зайвими.

Режим **за фронтом (Edge Triggered, `EPOLLET`)** повертає дескриптор лише в мить **переходу** — коли нові дані щойно надійшли. Якщо ви прочитали не все, більше вам про цей залишок ніхто не нагадає. 

Головне правило роботи за фронтом: **дескриптор обов'язково має бути неблокуючим, і читати з нього треба в циклі, доки він не поверне `EAGAIN`** (ознаку порожнього буфера). Лише так ви будете певні, що забрали все до останнього байта і готові чекати на наступний "фронт".
