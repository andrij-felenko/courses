# 📜 Еволюція DMA-відображень у ядрі Linux: від архітектурних хаків до єдиного підрозділу

Цей історичний екскурс простежує еволюцію підсистеми прямого доступу до пам'яті (Direct Memory Access, DMA) в ядрі Linux — від найпростіших макросів ядра для 32-бітних архітектур 1990-х років до сучасного уніфікованого шару `dma-mapping` та драйверного фреймворку `iommu-dma`.

## Ера ISA та early PCI: лінійне адресування та макроси virt_to_bus

На світанку розвитку ядра Linux (серії 1.0–2.0) основними системними шинами периферійних пристроїв були 16-бітна шина ISA (Industry Standard Architecture) та 32-бітна шина PCI (Peripheral Component Interconnect). На архітектурі x86 фізична оперативна пам'ять (Physical Address, PA) мала сувору 1:1 відповідність із шинними адресами (Bus Address). Якщо процесор звертався до фізичної адреси `0x01000000` (16 МБ), контролер DMA на шині PCI бачив на електричних лініях точно таку ж числову адресу `0x01000000`.

Для конвертації віртуальних адрес ядра (`void *`) у шинні адреси розробники драйверів використовували найпростіші препроцесорні макроси `virt_to_bus()` та `bus_to_virt()`:

```c
/* Простий підхід у ядрі Linux 2.0 (зараз канонічно заборонений) */
unsigned long bus_addr = virt_to_bus(kernel_buffer_ptr);
outl(bus_addr, dev->io_port + DMA_REG_ADDR);
```

Схема працювала ідеально доти, доки Linux лишався операційною системою виключно для персональних комп'ютерів на базі 32-бітних процесорів Intel x86 з обсягом оперативної пам'яті до 1 або 4 Гігабайт.

## Криза 64-бітних RISC-архітектур та виникнення PCI DMA API

Прикрощі розпочалися наприкінці 1990-х років, коли ядро Linux портували на потужні 64-бітні серверні RISC-платформи: UltraSPARC від Sun Microsystems, Alpha від Digital Equipment Corporation (DEC) та PA-RISC від Hewlett-Packard.

Ці машини використовували апаратні блоки трансляції вводу-виводу (IOMMU), такі як UltraSPARC IOMMU або Alpha TSUNAMI. На цих архітектурах шинна адреса пристрою категорично не дорівнювала фізичній адресі RAM:
1. Контролер шини PCI генерував шинну адресу у власному 32-бітному вікні.
2. Апаратний блок IOMMU перехоплював транзакцію PCI і через власні багаторівневі таблиці сторінок транпонював її у 64-бітну фізичну адресу в системній оперативній пам'яті.

Виклики макросу `virt_to_bus()` на UltraSPARC видавали сміття: макрос просто віднімав константний зсув ядра `PAGE_OFFSET`, не підозрюючи про існування апаратних таблиць IOMMU. Пристрої записували дані у довільні ділянки пам'яті, що призводило до миттєвого руйнування ядра (kernel panic).

У ядрі Linux 2.4 розробники Лінус Торвальдс (Linus Torvalds) та Девід Міллер (David S. Miller) здійснили архітектурний перелом: макроси `virt_to_bus()` оголосили застарілими (deprecated), а для драйверів встановили суворий контракт у вигляді підсистеми **PCI DMA API** (`pci_alloc_consistent()`, `pci_map_single()`, `pci_map_sg()`). Відтоді жоден драйвер пристрою не мав права передавати апаратурі віртуальну або фізичну адресу безпосередньо. Драйвер був зобов'язаний запросити у ядра шинну адресу через функцію-відображення.

## Проблема HighMem та народження SWIOTLB на архітектурі AMD64

На початку 2000-х років виклики адресування повернулися на платформу x86 з появою серверів з обсягом RAM понад 4 Гігабайти та появою 64-бітної архітектури AMD64 (x86-64).

Більшість масових мережевих карт, RAID-контролерів та SCSI-адаптерів тих часів мали апаратне обмеження DMA-маски у 32 біти (`DMA_BIT_MASK(32)`). Вони здатні були адресувати лише перші 4 Гігабайти RAM (адреси від `0x00000000` до `0xFFFFFFFF`). Якщо система мала 64 ГБ RAM і сторінковий розподільник ядра виділяв мережевий буфер за фізичною адресою `0x0000000500000000` (20 ГБ), 32-бітний мережевий контролер відтинав старші 32 біти адреси та намагався виконати DMA за адресою `0x00000000`. Пристрій нищив пам'ять системних процесів у першому гігабайті.

Оскільки масові чипсети x86-64 тих часів (наприклад, ранні серії AMD K8 або чипсети Intel для процесорів Core 2) ще не мали апаратного IOMMU, розробники ядра Йенс Аксбо (Jens Axboe) та Анді Клін (Andi Kleen) створили програмний емулятор трансляції — підсистему **SWIOTLB** (Software Input/Output Translation Lookaside Buffer, або *bounce buffers*).

SWIOTLB виділяла під час завантаження системи невеликий фізичний пул пам'яті (зазвичай 64 МБ) у межах перших 4 ГБ RAM. Якщо пристрій з обмеженою 32-бітною маскою намагався відобразити буфер з адресою >4 ГБ, SWIOTLB прозоро перенаправляла DMA на тимчасовий транзитний буфер (bounce buffer) у низькій пам'яті, а після завершення операції копіювала дані центральним процесором у цільовий високий буфер. Це врятувало сумісність зі старим обладнанням, хоча й створювало суттєвий оверхед через подвійне копіювання даних.

## Об'єднання під прапором dma_map_ops та iommu-dma

До версії ядра Linux 4.0 у вихідному коді існувала значна фрагментація: кожна апаратна архітектура (`arch/x86`, `arch/arm`, `arch/sparc`, `arch/powerpc`) мала власні закриті реалізації DMA-відображень. Це ускладнювало підтримку універсальних драйверів і заважало розвитку нових процесорних архітектур (наприклад, ARM64 та RISC-V).

У результаті серії рефакторингів під керівництвом Крістофа Хелльвіга (Christoph Hellwig) та Робіна Мерфі (Robin Murphy) у ядрах Linux 4.x–5.x відбулася повна уніфікація:
1. Застарілі функції `pci_map_*` вилучили або перетворили на тонкі обгортки навколо універсального API `dma_map_*`.
2. Увесь код підсистеми перенесли в єдиний каталоговий шар `kernel/dma/`.
3. Усі архітектури перевели на структуру абстракції `struct dma_map_ops`.
4. Блок управління IOMMU виділили в ізольовану підсистему `drivers/iommu/`, а зв'язок між DMA API та апаратним IOMMU стандартизували через модуль `iommu-dma`.

Сьогодні ядро Linux використовує єдиний прозорий маршрутизатор: залежно від наявності апаратного IOMMU, конфігурації шини та DMA-маски конкретного пристрою, ядро автоматично вибирає найбільш ефективний шлях виконання (пряме фізичне відображення `dma-direct`, апаратну трансляцію `iommu-dma` або транзитний буфер `swiotlb`), звільняючи розробника драйвера від специфіки апаратури.
