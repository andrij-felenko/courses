</preknowlist>

Сучасні високопродуктивні периферійні пристрої — мережеві адаптери 100GbE, NVMe-накопичувачі, графічні прискорювачі (GPU) та апаратні нейропроцесори (NPU) — прокачують десятки гігабайтів даних на секунду безпосередньо у системну оперативну пам'ять (RAM) в обхід центрального процесора. За високого навантаження 100-гігабітний мережевий контролер обробляє понад 148 мільйонів мережевих пакетів на секунду. Якщо центральний процесор (CPU) втручатиметься у пересилання кожного байта або перериватиметься на кожну сторінку пам'яті, продуктивність обчислювальної системи провалиться до нуля через високі накладні витрати на переривання й контекстні перемикання та через переповнення системних шин.

Прямий доступ до пам'яті (Direct Memory Access, DMA) вирішує цю проблему, дозволяючи периферійним контролерам самостійно читати й писати комірки системної оперативної пам'яті. Однак прямий доступ створює фундаментальний архітектурний конфлікт: центральний процесор виконує код у віртуальному адресному просторі, який формується блоком управління пам'яттю (Memory Management Unit, MMU), тоді як контролери на системних шинах (PCI Express, AHB, AXI) оперують шинними адресами. Додатково процесор працює через надшвидкісні багаторівневі кеші L1/L2/L3, про існування яких зовнішня периферія навіть не підозрює, а периферійні пристрої часто мають апаратні обмеження розрядності адресної шини (наприклад, 32-бітне адресування на 64-бітних системах з 128 ГБ RAM).

Для безпечного, прозорого та незалежного від процесорної архітектури розв'язання цих суперечностей в ядрі Linux функціонує підсистема **DMA mapping** (відображення прямого доступу до пам'яті) у поєднанні з апаратними блоками **IOMMU** (Input-Output Memory Management Unit — пристрій керування пам'яттю вводу-виводу).

## Передумови та конфлікт адресування

### Віртуальна пам'ять процесора проти шинної адреси пристрою

Операційна система Linux виділяє пам'ять для системних процесів та драйверів за допомогою сторінкового розподільника (buddy allocator) або надбудованого над ним розподільника блоків `kmalloc()`. Для центрального процесора буфер розміром 1 Мегабайт виглядає як єдиний, фізично суцільний масив віртуальних адрес. Проте під капотом блоку MMU цей буфер складається з 256 окремих сторінок розміром по 4 Кілобайти кожна, які можуть бути розкидані по всьому фізичному обсягу оперативної пам'яті.

Апаратний контролер шини PCI Express, виділений для мережевої карти або диска, не має доступу до багаторівневих таблиць сторінок MMU центрального процесора (PGD, P4D, PUD, PMD, PTE). Коли периферійний пристрій ініціює пакет транзакційного рівня (Transaction Layer Packet, TLP) на шині PCIe, він передає цільову адресу вводу-виводу. Якщо драйвер пристрою передасть віртуальну адресу ядра `0xffff888102a40000` безпосередньо у DMA-реєстр пристрою, контролер шини сприйме цей набір бітів як фізичну адресу або адресу шини. У кращому разі пристрій звернеться до неіснуючої комірки пам'яті й згенерує шинну помилку (Bus Error), у гіршому — безповоротно пошкодить пам'ять іншого процесу або самого ядра.

Для опису шляху даних в ядрі Linux строго розрізняють три типи адрес:
1. **Віртуальна адреса ядра (Kernel Virtual Address, VA):** покажчик у просторі адрес CPU, який використовується програмами та драйверами для читання й запису через інструкції CPU.
2. **Фізична адреса (Physical Address, PA):** реальна координата комірки в модулях оперативної пам'яті (DRAM).
3. **Шинна адреса / IOVA (Bus Address / IO Virtual Address):** адреса, яку периферійний пристрій виставляє на системну шину (PCIe, AXI) під час виконання DMA-транзакції.

### Конфлікт когерентності кешу CPU

Другим викликом є операції з кеш-пам'яттю центрального процесора. Коли CPU виконує запис у буфер пам'яті, нові дані не потрапляють у фізичну RAM миттєво — вони осідають у швидкісних кеш-рядках L1, L2 або L3 процесора (розміром 64 або 128 байтів, стратегія write-back).

Якщо у цей момент пристрій DMA почне зчитувати дані безпосередньо з фізичних комірок RAM, він прочитає застарілі дані (stale data), оскільки свіжа версія інформації все ще знаходиться в кеші CPU. І навпаки: коли пристрій DMA записує нові дані з мережі безпосередньо у RAM, кеш-рядки CPU про це не знають. Коли CPU спробує прочитати буфер, він прочитає застаріле значення зі свого кешу замість нових даних з RAM.

На архітектурах x86/x86-64 когерентність DMA гарантується апаратно на рівні шини системного контролера (snooping mechanism). На багатьох ARM64, MIPS та RISC-V системах апаратне стеження за кешем відсутнє (non-coherent DMA interconnect), тому ядро Linux зобов'язане вручну примусово скидати (flush) та інвалідувати (invalidate) кеш-рядки CPU перед і після кожної операції вводу-виводу.

![Архітектура підсистеми dma-mapping](/reference/unix-linux/io/dma-mapping-subsystem-and-iommu/img/dma-mapping-arch.svg)
*Схема взаємодії драйвера пристрою, обгортки struct dma_map_ops, підсистем dma-direct, SWIOTLB, iommu-dma та оперативної пам’яті.*

Детальний аналіз того, як ядро Linux пройшло шлях від найпростіших архітектурних макросів `virt_to_bus()` до сучасного шару `dma_map_ops`, винесено у статтю [📜 Еволюція DMA-відображень у ядрі Linux](book:unix-linux/dma-mapping-subsystem-and-iommu/hist-dma-evolution.md).

## Дві парадигми DMA-відображень: Coherent та Streaming

Для оптимізації роботи з пам'яттю підсистема DMA mapping ядра Linux надає розробникам драйверів два кардинально різних механізми відображення: **Coherent** (послідовне / зв'язане) та **Streaming** (потокове).

![Порівняння Coherent та Streaming DMA](/reference/unix-linux/io/dma-mapping-subsystem-and-iommu/img/coherent-vs-streaming.svg)
*Порівняльний огляд двох режимів DMA: безкешові кільцеві буфери проти тимчасових відображень із синхронізацією кешу.*

### 1. Зв'язані відображення (Coherent DMA Mappings)

Під час обробки високонавантаженого вводу-виводу периферійний пристрій та драйвер ядра постійно обмінюються службовими дескрипторами пакетів та станами кільцевих черг мільйони разів на секунду. Якби кожна зміна дескриптора вимагала від процесора виконання явних інструкцій скидання та інвалідації кеш-рядків (cache flush/invalidate), накладні витрати CPU повністю знищили б пропускну здатність системи. Драйверу фізично необхідна спеціальна ділянка пам'яті, де будь-яка зміна байта процесором або контролером негайно стає видимою для іншої сторони без ручного керування кеш-пам'яттю.

**Зв'язане DMA-відображення** — створює довготривалу ділянку пам'яті, яка залишається синхронною між процесором та пристроєм протягом усього часу існування драйвера.

- **Характеристики:** На когерентних платформах (x86-64, частина ARM64 з CCI чи CXL) пам'ять лишається звичайною кешованою — синхронність забезпечує апаратне стеження шини. На некогерентних платформах ядро під час виділення змінює атрибути кешування в таблицях сторінок CPU на Uncached або Write-Combining. В обох випадках запис, виконаний CPU, стає видимим для пристрою без явних операцій із кешем.
- **Типовий сценарій:** Кільцеві буфери дескрипторів (TX/RX Ring Buffers) мережевих карт, дескрипторні кільця NVMe-контролерів, командні буфери графічних процесорів.
- **Виклики API ядра:** `dma_alloc_coherent()` виділяє пам'ять і повертає як віртуальний покажчик для CPU, так і шинну адресу `dma_addr_t` для пристрою. За необхідності виділення фізично неперервних блоків ядро залучає резервовану область пам'яті CMA (Contiguous Memory Allocator).

```c
/* Виділення 64 КБ зв'язаної пам'яті під дескриптори кільця */
dma_addr_t ring_dma_handle;
void *ring_cpu_virt = dma_alloc_coherent(dev, 65536, &ring_dma_handle, GFP_KERNEL);
```

Оскільки там, де ядро вимикає кешування, доступ CPU різко сповільнюється, виділяти гігабайти пам'яті через Coherent DMA недоцільно — це призведе до неефективного використання кеш-пам'яті процесора та зниження загальної обчислювальної швидкодії системи.

### 2. Потокові відображення (Streaming DMA Mappings)

Більшість буферів даних у ядрі (наприклад, мережеві пакети `sk_buff` або дискові блоки `struct bio`) виділяються у стандартній кешованій пам'яті для забезпечення максимальної швидкості обробки процесором. Коли такий буфер передається периферійному пристрою для виконання DMA-транзакції, ядро реалізує механізм чіткої передачі прав володіння (ownership transfer): на час активності шинного контролера процесор повністю втрачає право звертатися до буфера, а кеш-рядки CPU синхронізуються з оперативною пам'яттю; після завершення DMA право володіння повертається процесору з гарантією актуальності даних у кеші.

**Потокове DMA-відображення** — розраховане на короткотривалі операції вводу-виводу для вже існуючих буферів пам'яті, виділених іншими підсистемами ядра (наприклад, сокетні буфери `sk_buff` у мережевому стеку або блоки `struct bio` у дисковому шарі).

- **Характеристики:** Буфер зберігає стандартне кешування CPU. Драйвер відображає буфер безпосередньо перед початком DMA-транзакції та скасовує відображення одразу після її завершення.
- **Передача прав володіння (Ownership Contract):** Під час виконання DMA-транзакції ділянка пам'яті належить периферійному пристрою. Процесор **категорично не має права** читати або змінювати буфер під час активної фази DMA.
- **Синхронізація кешу:** Залежно від напрямку передачі даних, ядро виконує необхідні операції з кешем CPU:
  - `DMA_TO_DEVICE`: ядро примусово очищає (flushes) кеш-рядки CPU у RAM перед початком передачі, щоб пристрій прочитав свіжі дані;
  - `DMA_FROM_DEVICE`: ядро інвалідує (invalidates) кеш-рядки CPU перед і після передачі, щоб CPU не прочитав застарілі дані зі свого кешу;
  - `DMA_BIDIRECTIONAL`: комбінація обох операцій.

```c
/* Потокове відображення вже існуючого мережевого пакета */
dma_addr_t pkt_dma_addr = dma_map_single(dev, skb->data, skb->len, DMA_TO_DEVICE);
if (dma_mapping_error(dev, pkt_dma_addr)) {
    /* Обробка помилки відображення */
}
```

Повний список функцій API, типів даних та прапорців напрямку передачі зібрано в довіднику [📋 Інтерфейс DMA mapping subsystem у ядрі Linux](book:unix-linux/dma-mapping-subsystem-and-iommu/api-dma-mapping-surface.md).

## Розсіювання-збирання (Scatter-Gather) та транзитні буфери (SWIOTLB)

### Списки розсіювання-збирання (Scatter-Gather Lists)

У реальних операціях дискового вводу-виводу або обробки мережевих кадрів буфер даних великого розміру (наприклад, 4 Мегабайти) складається з тисячі окремих фізичних сторінок по 4 Кілобайти, розкиданих по всій оперативній пам’яті.

Викликати `dma_map_single()` для кожної сторінки окремо у циклі вкрай неефективно через високі затрати на виклики функцій та оновлення системних структур. Для оптової обробки таких буферів ядро використовує списки розсіювання-збирання (`struct scatterlist` та `struct sg_table`).

Структура `struct scatterlist` описує окремий фізичний елемент пам'яті:
```c
struct scatterlist {
    unsigned long page_link; /* Посилання на фізичну сторінку struct page */
    unsigned int  offset;    /* Зсув усередині сторінки у байтах */
    unsigned int  length;    /* Довжина сегмента у байтах */
    dma_addr_t    dma_address; /* Шинна адреса (згенерована під час map) */
    unsigned int  dma_length;  /* Сформована довжина DMA-сегмента */
};
```

Виклик `dma_map_sgtable()` приймає таблицю з `sgt->orig_nents` фізичних сегментів і відображає їх за один підхід:

```c
int ret = dma_map_sgtable(dev, sgt, DMA_FROM_DEVICE, 0);
if (ret) {
    /* Обробка збою відображення */
}
```

Функція повертає `0` за успіху й від'ємний код помилки за збою, а кількість фактично відображених DMA-сегментів записує у поле `sgt->nents`. Важливо: значення `sgt->nents` може бути **меншим** за початкову кількість фізичних сегментів `sgt->orig_nents`. Це відбувається у випадках, коли суміжні фізичні сторінки виявилися розташованими послідовно у фізичній RAM або коли апаратний блок IOMMU об'єднав фрагментовані фізичні сторінки у єдине неперервне вікно шинних адрес (IOVA).

### Обмеження розрядності шини та буфери перекачування (SWIOTLB)

Кожен периферійний пристрій зв'язується з системною шиною через контролер певної розрядності. Старі або спеціалізовані пристрої (наприклад, 32-бітні PCIe контролери) здатні формувати шинні адреси лише у межах 32 бітів (перші 4 Гігабайти адресного простору RAM).

Якщо сервер обладнано 128 Гігабайтами RAM і сторінковий розподільник ядра видав під мережевий пакет сторінку за фізичною адресою `0x0000000410000000` (16.25 ГБ), 32-бітний пристрій фізично не зможе виставити старші біти адреси на шину.

Коли пристрій повідомив ядру свою маску через `dma_set_mask_and_coherent(dev, DMA_BIT_MASK(32))`, а апаратний IOMMU у системі відсутній, підсистема `dma-mapping` прозоро залучає **SWIOTLB** (Software Input/Output Translation Lookaside Buffer, або *bounce buffers* — транзитні буфери перекачування).

SWIOTLB виділяє під час старту ядра статичний резервний пул фізично неперервної пам'яті у нижній ділянці RAM (адреси <4 ГБ; типовий розмір пулу — 64 Мегабайти), розбитий на слоти по 2 Кілобайти:
1. **При записі на пристрій (`DMA_TO_DEVICE`):** ядро виділяє тимчасовий транзитний слот у пулі SWIOTLB (<4 ГБ), копіює туди вміст високої сторінки (>4 ГБ) за допомогою CPU і передає пристрою шинну адресу транзитного слота.
2. **При читанні з пристрою (`DMA_FROM_DEVICE`):** пристрій виконує DMA у транзитний слот SWIOTLB (<4 ГБ). Під час виклику `dma_unmap_single()` ядро копіює дані з транзитного слота назад у цільову високу сторінку пам'яті процесу.

Використання SWIOTLB забезпечує повну сумісність зі старим обладнанням, проте руйнує ідеологію zero-copy: примусове копіювання даних процесором споживає ресурси CPU та створює додаткові затримки (latency).

## Архітектура апаратного IOMMU

Сучасні обчислювальні платформи розв'язують проблему фрагментації та обмежень адресування на апаратному рівні за допомогою блока **IOMMU** (*Input-Output Memory Management Unit*). Провідні розробники процесорних архітектур реалізують цю технологію під власними торговельними марками: Intel VT-d (Virtualization Technology for Directed I/O), AMD-Vi, ARM SMMU (System MMU v2/v3) та RISC-V IOPMP/IOMMU.

![Трансляція адрес апаратним IOMMU](/reference/unix-linux/io/dma-mapping-subsystem-and-iommu/img/iommu-iova-translation.svg)
*Апаратна трансляція IOVA у фізичні адреси RAM з підтримкою захисту сторінок та об'єднання розкиданих блоків.*

### Фундаментальні функції IOMMU

Апаратний IOMMU розташовується безпосередньо між периферійними шинами (PCI Express Root Complex) та системною шиною оперативної пам'яті. Він надає чотири фундаментальні можливості:

1. **Динамічна трансляція адрес (IOVA → PA):** IOMMU транслює віртуальні адреси вводу-виводу (IOVA), що генеруються периферійними пристроями, у реальні фізичні адреси оперативної пам'яті (PA) на основі багаторівневих таблиць сторінок IOMMU (IOMMU Page Tables).
2. **Об'єднання фрагментованої пам'яті:** Спеціалізовані пристрої, які вимагають фізично неперервного буфера пам'яті (наприклад, застарілі відеодекодери), завдяки IOMMU можуть працювати з абсолютно фрагментованими сторінками RAM. IOMMU відображає розкидані фізичні сторінки `Page #5`, `Page #88`, `Page #102` у єдиний суцільний діапазон адрес IOVA.
3. **Обхід обмежень 32-бітного DMA:** Пристрій з 32-бітною маскою генерує 32-бітну адресу IOVA. IOMMU прозоро перенаправляє цю адресу на 64-бітну фізичну сторінку RAM у ділянці >4 ГБ, повністю усуваючи потребу у транзитних буферах SWIOTLB.
4. **Апаратна ізоляція пристроїв та захист від DMA-атак:** Без IOMMU будь-який компрометований або зловмисний пристрій на шині PCI Express здатний виконати DMA-читання або запис у довільну комірку системної RAM (включаючи ядро операційної системи та паролі в пам'яті). IOMMU блокує будь-які транзакції DMA, адреси яких не були явно зареєстровані у таблицях сторінок пристрою, генеруючи апаратне переривання збою вводу-виводу (IOMMU Page Fault).

### Групи IOMMU (IOMMU Groups) та прокидання пристроїв (VFIO)

Найменшою одиницею апаратної ізоляції в ядрі Linux є **IOMMU Group** (`struct iommu_group`). Група визначається топологією шини PCI Express і наявністю підтримки специфікації ACS (Access Control Services) у PCIe-мостах. Якщо два пристрої знаходяться за мостом без ACS, вони можуть обмінюватися DMA-транзакціями напряму один з одним (peer-to-peer DMA) в обхід IOMMU. Тому ядро об'єднує такі пристрої у єдину IOMMU-групу.

Ізоляція на рівні IOMMU-груп є основою для роботи фреймворку **VFIO** (Virtual Function I/O). VFIO дозволяє безпечно від'єднати пристрій (або всю IOMMU-групу) від драйверів ядра Linux та передати пряме управління ним у простір користувача або гіпервізор KVM/QEMU для прокидання (passthrough) у віртуальну машину з майже нативною продуктивністю.

## Архітектурні шари ядра: dma-direct, iommu-dma та struct dma_map_ops

Коли драйвер ініціює передачу даних викликом `dma_map_single()`, ядро повинно визначити оптимальний шлях побудови шинної адреси для конкретного пристрою. За наявності апаратного блока IOMMU трансляція адреси делегується підсистемі `iommu-dma`, яка виділяє віртуальний простір IOVA та програмує таблиці сторінок IOMMU. Якщо IOMMU відсутній, підсистема `dma-direct` виконує пряме арифметичне відображення фізичної адреси, але якщо ця адреса перевищує розрядність адресної маски пристрою, ядро прозоро перенаправляє транзакцію через буфери перекачування `swiotlb`.

Для уніфікації цього розгалуження та забезпечення прозорості для драйверів шлях виконання DMA-операції в сучасних ядрах Linux повністю абстрагований від конкретного процесора та шини. Кожен екземпляр `struct device` містить покажчик на таблицю операцій `const struct dma_map_ops *dma_ops`.

Коли драйвер викликає `dma_map_single()` або `dma_alloc_coherent()`, ядро делегує виконання відповідному обробнику у `dma_ops`:

```c
/* Спрощена схема виклику всередині dma_map_single_attrs() у kernel/dma/mapping.c */
const struct dma_map_ops *ops = get_dma_ops(dev);
if (dma_map_direct(dev, ops))
    addr = dma_direct_map_page(dev, page, offset, size, dir, attrs);
else
    addr = ops->map_page(dev, page, offset, size, dir, attrs);
```

В ядрі Linux виділяють три головних внутрішніх модулі виконання DMA:

1. **`dma-direct` (`kernel/dma/direct.c`):** Використовується, коли апаратний IOMMU відсутній або вимкнений. Виконує пряме обчислення шинної адреси з фізичної: `dma_addr = virt_to_phys(addr) − зсув шини пристрою` (до ядра 5.15 зсув брався з поля `dev->dma_pfn_offset`, від 5.15 — з таблиці діапазонів `dev->dma_range_map`). За потреби перевіряє межі маски та звертається до SWIOTLB.
2. **`iommu-dma` (`drivers/iommu/dma-iommu.c`):** Зв'язує загальну підсистему DMA mapping з апаратним драйвером IOMMU. Виділяє віртуальні адреси з пулу IOVA (IOVA allocator), програмує таблиці сторінок IOMMU та керує інвалідацією буферів TLB вводу-виводу (IOTLB).
3. **`swiotlb` (`kernel/dma/swiotlb.c`):** Модуль обслуговування резервних транзитних буферів для пристроїв з обмеженою адресною маскою.

Повний приклад реалізації драйвера ядра з використанням Coherent та Streaming DMA відображень подано у практичному модулі [⚙️ Практична реалізація DMA-відображень у драйвері ядра Linux](book:unix-linux/dma-mapping-subsystem-and-iommu/proj-dma-driver-example.md).

## Навіщо це в реальній розробці

> 🔧 **Навіщо це.**
> Розуміння підсистеми DMA mapping та IOMMU є критичним під час розробки високошвидкісних драйверів мережевих карт, NVMe-накопичувачів, відеозахоплення V4L2, а також під час налагодження систем системного програмування у просторі користувача (DPDK, SPDK, QEMU/KVM).
>
> ### Практичні інструменти діагностики та налагодження ядра:
>
> 1. **Аналіз витоків та порушень контракту DMA (`CONFIG_DMA_API_DEBUG`):**
>    Увімкнення цієї опції ядра активує суворий перевірочний шар, який фіксує помилки розробників драйверів у реальному часі:
>    - спроби читання буфера CPU під час активної фази DMA;
>    - відсутність перевірки результату через `dma_mapping_error()`;
>    - невідповідність напрямків `enum dma_data_direction` під час map та unmap;
>    - витоки відображень (unmap memory leak).
>    Статистика діагностики доступна через debugfs:
>    ```bash
>    cat /sys/kernel/debug/dma_debug/statistics
>    ```
>
> 2. **Моніторинг вичерпання транзитних буферів SWIOTLB:**
>    Якщо у системі працюють 32-бітні пристрої на 64-бітній RAM без IOMMU, високе навантаження вводу-виводу може вичерпати пул SWIOTLB, що призведе до збоїв `dma_map_single()` та втрати мережевих пакетів. Перевірити використання пулу SWIOTLB можна через debugfs:
>    ```bash
>    cat /sys/kernel/debug/swiotlb/io_tlb_used
>    ```
>
> 3. **Інспекція IOMMU-груп для прокидання пристроїв (VFIO):**
>    Перед прокиданням PCIe-пристрою у віртуальну машину (KVM) або DPDK-застосунок необхідно переконатися, які саме пристрої входять до однієї IOMMU-групи:
>    ```bash
>    ls -la /sys/kernel/iommu_groups/*/devices/
>    ```
