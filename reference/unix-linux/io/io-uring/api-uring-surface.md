# 📋 Інтерфейс io_uring: три виклики, дві структури, таблиці прапорців

Ця вставка пояснює 📋 інтерфейс io_uring: три виклики, дві структури, таблиці прапорців та дозволяє зрозуміти її детальніше. Тут зібрано точний контракт голого io_uring: підписи трьох системних викликів, поле-в-поле обидві структури кільця, зміщення для `mmap` і те, що лежить у кожному відображенні, повні таблиці прапорців налаштування й прапорців окремого запису, найуживаніші коди операцій із версією ядра, у якій кожен з'явився, та розбір того, куди саме приходить помилка. Це довідка на ту мить, коли код уже пишеться — або коли треба зрозуміти, що саме `liburing` робить за вас.

## Три системні виклики

Обгорток у glibc для них немає — жодного. Кличуть або через `syscall(2)` напряму, або через `liburing`, де ті самі три виклики сховано за функціями з префіксом `io_uring_`.

```c
#include <linux/io_uring.h>
#include <sys/syscall.h>

int io_uring_setup(u32 entries, struct io_uring_params *p);

int io_uring_enter(unsigned int fd, unsigned int to_submit,
                   unsigned int min_complete, unsigned int flags,
                   sigset_t *sig);

int io_uring_enter2(unsigned int fd, unsigned int to_submit,       /* Linux 5.11 */
                    unsigned int min_complete, unsigned int flags,
                    void *arg, size_t sz);

int io_uring_register(unsigned int fd, unsigned int opcode,
                      void *arg, unsigned int nr_args);
```

| виклик | що робить | що повертає |
|---|---|---|
| `io_uring_setup` | створює кільце щонайменше на `entries` записів і заповнює `p` усім, що потрібно для `mmap` | новий дескриптор кільця |
| `io_uring_enter` | повідомляє про `to_submit` уже покладених SQE й за потреби чекає на `min_complete` завершень | скільки SQE прийнято |
| `io_uring_enter2` | те саме, але замість `sigset_t *` — розширений аргумент `struct io_uring_getevents_arg`: маска сигналів **і** таймаут очікування | те саме |
| `io_uring_register` | віддає ядру ресурси на все життя кільця: буфери, дескриптори, `eventfd`, обмеження | `0` або `−1` |

`entries` ядро округлює вгору до степеня двійки. Стеля в поточних ядрах — 32768 записів у кільці подань і вдвічі більше в кільці завершень; перевищення дає `EINVAL`, а з прапорцем `IORING_SETUP_CLAMP` — мовчазне обрізання до стелі. Закриття поверненого дескриптора звільняє геть усі ресурси кільця, але не миттєво: ядро спершу доводить до кінця або скасовує все, що ще в польоті.

Розподіл праці між цими трьома різкий. `io_uring_setup` кличуть раз на кільце, `io_uring_register` — рідко й свідомо, а `io_uring_enter` і є весь гарячий шлях; саме тому в ньому два незалежні числа. `to_submit` каже, скільки нових записів програма вже поклала в кільце, `min_complete` — скільки завершень вона хоче побачити перед поверненням. Нуль у першому означає «нічого не подаю, лише забираю», нуль у другому — «подаю й одразу вертаюся». Обидва ненульові дають той самий один перехід межі, що заміняє і подання, і очікування.

## Розмова при створенні: `struct io_uring_params`

Ця структура — двобічна: частину полів заповнює програма перед викликом, решту ядро дописує після. Саме тому `memset` у нуль перед `io_uring_setup` обов'язковий: масив `resv` мусить бути нульовим, інакше виклик відмовить.

```c
struct io_uring_params {
    __u32 sq_entries;                  /* ← ядро: скільки SQE виділено насправді */
    __u32 cq_entries;                  /* ⇄ з CQSIZE — прохання; без нього — відповідь */
    __u32 flags;                       /* → IORING_SETUP_*                        */
    __u32 sq_thread_cpu;               /* → з SQ_AFF: до якого ядра прив'язати потік */
    __u32 sq_thread_idle;              /* → з SQPOLL: скільки мс простою до засинання */
    __u32 features;                    /* ← ядро: IORING_FEAT_* — що воно вміє    */
    __u32 wq_fd;                       /* → з ATTACH_WQ: чиї робітники позичаємо  */
    __u32 resv[3];                     /* → мусить бути нулем                     */
    struct io_sqring_offsets sq_off;   /* ← де що лежить у відображенні SQ        */
    struct io_cqring_offsets cq_off;   /* ← те саме для CQ                        */
};

struct io_sqring_offsets {
    __u32 head, tail;          /* лічильники: голову рухає ядро, хвіст — програма */
    __u32 ring_mask;           /* розмір − 1: індекс = лічильник & ring_mask       */
    __u32 ring_entries;
    __u32 flags;               /* IORING_SQ_NEED_WAKEUP і решта                    */
    __u32 dropped;             /* скільки SQE ядро відкинуло як зіпсовані          */
    __u32 array;               /* масив індексів у масив SQE                       */
    __u32 resv1;
    __u64 user_addr;           /* із IORING_SETUP_NO_MMAP — адреса від програми    */
};

struct io_cqring_offsets {
    __u32 head, tail;          /* тут навпаки: хвіст рухає ядро, голову — програма */
    __u32 ring_mask;
    __u32 ring_entries;
    __u32 overflow;            /* скільки разів завершення не влізли в кільце      */
    __u32 cqes;                /* самі записи CQE — у цьому ж відображенні         */
    __u32 flags;
    __u32 resv1;
    __u64 user_addr;
};
```

Числа в `sq_off`/`cq_off` — це не адреси, а **зміщення в байтах усередині відображення**. Ядро не обіцяє сталої розкладки полів: правильний код завжди рахує адресу як «початок відображення + зміщення з `p`», і тільки такий код переживе наступне ядро.

## Прапорці `features`: як спитати ядро про його вік

Кільце створюється навіть на старому ядрі — просто без половини можливостей. Питати версію через `uname` марно: дистрибутиви переносять зміни в старіші ядра. Єдина чесна перевірка — біти `p.features` після успішного `io_uring_setup`.

| прапорець | ядро | що з'явилося |
|---|---|---|
| `IORING_FEAT_SINGLE_MMAP` | 5.4 | обидва кільця відображаються одним `mmap` |
| `IORING_FEAT_NODROP` | 5.5 | завершення практично ніколи не губляться: переповнення тримають у списку |
| `IORING_FEAT_SUBMIT_STABLE` | 5.5 | дані з SQE забрані вже на поданні — запис можна перевикористати одразу |
| `IORING_FEAT_RW_CUR_POS` | 5.6 | `off = −1` означає «з поточної позиції файлу» |
| `IORING_FEAT_CUR_PERSONALITY` | 5.6 | операція виконується з правами того, хто викликав `io_uring_enter` |
| `IORING_FEAT_FAST_POLL` | 5.7 | внутрішнє очікування готовності замість передачі робітникові |
| `IORING_FEAT_SQPOLL_NONFIXED` | 5.11 | `SQPOLL` більше не вимагає зареєстрованих дескрипторів |
| `IORING_FEAT_EXT_ARG` | 5.11 | `io_uring_enter2` з таймаутом очікування |
| `IORING_FEAT_NATIVE_WORKERS` | 5.12 | робітники `io-wq` стали власними потоками задачі |
| `IORING_FEAT_CQE_SKIP` | 5.17 | працює `IOSQE_CQE_SKIP_SUCCESS` |
| `IORING_FEAT_LINKED_FILE` | 5.17 | дескриптор для зв'язаного SQE беруть аж перед виконанням |
| `IORING_FEAT_REG_REG_RING` | 6.3 | `io_uring_register` приймає зареєстрований дескриптор кільця |

## Три відображення

Кільце живе не в пам'яті програми й не в пам'яті ядра, а в спільних сторінках, які треба взяти через [mmap](book:unix-linux/mmap-model) — відображення, після якого одні й ті самі фізичні сторінки видно з обох боків. Дескриптор кільця тут виступає файлом, а роль «місця у файлі» грають три чарівні зміщення.

Слово «чарівні» тут точне: це не позиції в жодному файлі, а умовні номери. Дескриптор кільця не можна ані читати, ані писати звичайними викликами — він існує лише щоб бути аргументом `mmap` та `io_uring_enter`, і ядро дивиться на зміщення просто як на відповідь на питання «що саме тобі відобразити».

| зміщення | значення | що відкриває |
|---|---|---|
| `IORING_OFF_SQ_RING` | `0` | лічильники й службові поля SQ плюс масив `array[]` з індексами |
| `IORING_OFF_CQ_RING` | `0x8000000` | лічильники CQ **і самі записи CQE** |
| `IORING_OFF_SQES` | `0x10000000` | масив самих SQE |

![Три відображення io_uring: що лежить за кожним зміщенням і як їх зводить IORING_FEAT_SINGLE_MMAP](/reference/unix-linux/io/io-uring/img/mmap-layout.svg)

*Асиметрія не випадкова: CQE лежать усередині відображення кільця завершень, а SQE винесені окремо — бо кільце подань зберігає лише індекси в цей масив.*

```c
/* розміри рахують так і тільки так — константи тут не працюють */
size_t sring_sz = p.sq_off.array + p.sq_entries * sizeof(__u32);
size_t cring_sz = p.cq_off.cqes  + p.cq_entries * sizeof(struct io_uring_cqe);

/* із IORING_FEAT_SINGLE_MMAP — одне відображення на більший із двох розмірів */
if (cring_sz > sring_sz) sring_sz = cring_sz;

void *ring = mmap(NULL, sring_sz, PROT_READ | PROT_WRITE,
                  MAP_SHARED | MAP_POPULATE, ring_fd, IORING_OFF_SQ_RING);
void *sqes = mmap(NULL, p.sq_entries * sizeof(struct io_uring_sqe),
                  PROT_READ | PROT_WRITE,
                  MAP_SHARED | MAP_POPULATE, ring_fd, IORING_OFF_SQES);
```

`MAP_POPULATE` тут не прикраса: без нього перший доступ до кожної сторінки кільця коштує помилки сторінки саме в гарячому шляху, заради здешевлення якого все й будувалося. З ядра 6.5 є й зворотний варіант — `IORING_SETUP_NO_MMAP`, коли пам'ять під кільця виділяє сама програма й передає адреси в полях `user_addr`.

## SQE: 64 байти опису роботи

Запис подання — це структура сталого розміру, у якій більшість полів — об'єднання: те саме місце різні операції тлумачать по-різному. Тому єдиний безпечний спосіб заповнити SQE — занулити його цілком і виставити лише потрібні поля.

| зміщення | поле | розмір | що це |
|---|---|---|---|
| 0 | `opcode` | 1 Б | код операції `IORING_OP_*` |
| 1 | `flags` | 1 Б | прапорці `IOSQE_*` саме цього запису |
| 2 | `ioprio` | 2 Б | пріоритет вводу-виводу; деякі операції кладуть сюди свої біти |
| 4 | `fd` | 4 Б | дескриптор — або індекс у зареєстрованому масиві, якщо стоїть `IOSQE_FIXED_FILE` |
| 8 | `off` / `addr2` / `cmd_op` | 8 Б | зміщення у файлі (`−1` — поточна позиція) або друга адреса |
| 16 | `addr` / `splice_off_in` | 8 Б | адреса буфера чи масиву `iovec` |
| 24 | `len` | 4 Б | довжина буфера або кількість елементів `iovec` |
| 28 | `rw_flags`, `msg_flags`, `timeout_flags`, `open_flags`, … | 4 Б | прапорці, свої в кожної операції |
| 32 | `user_data` | 8 Б | вісім байтів програми; ядро повертає їх у CQE недоторканими |
| 40 | `buf_index` / `buf_group` | 2 Б | номер зареєстрованого буфера або групи наданих буферів |
| 42 | `personality` | 2 Б | зареєстровані облікові дані, з якими виконати операцію |
| 44 | `splice_fd_in` / `file_index` / `optlen` | 4 Б | другий дескриптор або комірка, куди покласти новий |
| 48 | `addr3` + доповнення / `optval` / `cmd[]` | 16 Б | третя адреса або початок команди `IORING_OP_URING_CMD` |

Останні шістнадцять байтів — саме та причина, з якої існує `IORING_SETUP_SQE128`: команди пристроїв (наприклад, наскрізний доступ до NVMe) не влазять у 64 байти, і з цим прапорцем кожен запис стає 128-байтовим, а `cmd[]` дістає ще 64 байти.

Поле `user_data` варте окремої уваги, бо воно єдине зв'язує запит із відповіддю. Ядро не тлумачить ці вісім байтів ніяк: не перевіряє, не змінює, не вимагає унікальності. Зазвичай туди кладуть покажчик на власну структуру запиту, і тоді обробка завершення зводиться до розіменування. Зворотний бік тієї самої зручності — завершення скасованої чи забутої операції принесе покажчик на вже звільнену пам'ять, тож стежити за життям цих структур доводиться самій програмі.

## CQE: 16 байтів звіту

```c
struct io_uring_cqe {
    __u64 user_data;   /* те саме, що поклали в SQE          */
    __s32 res;         /* ≥ 0 — результат; < 0 — це −errno   */
    __u32 flags;       /* IORING_CQE_F_*                     */
    __u64 big_cqe[];   /* +16 Б лише з IORING_SETUP_CQE32    */
};
```

| прапорець у `flags` | що означає |
|---|---|
| `IORING_CQE_F_BUFFER` | буфер обрало ядро; його номер — у верхніх 16 бітах, тобто `flags >> 16` |
| `IORING_CQE_F_MORE` | операція багаторазова: з тим самим `user_data` прийдуть іще CQE |
| `IORING_CQE_F_SOCK_NONEMPTY` | у сокеті лишилися дані — читати ще раз має сенс |
| `IORING_CQE_F_NOTIF` | це не результат, а сповіщення, що буфер надсилання без копіювання вільний |

Прапорець `IORING_CQE_F_MORE` — єдина ознака, за якою відрізняють останнє завершення багаторазової операції від проміжного. Поки він стоїть, SQE живий; щойно прийшов CQE без нього — операції більше немає, і `accept` чи `recv` треба подавати наново.

Тридцять два байти замість шістнадцяти (`IORING_SETUP_CQE32`) потрібні там, де відповідь не вміщається в одне число: наскрізні команди пристроїв повертають власний статус у `big_cqe`, і без цього прапорця такі операції не працюють. Розмір записів обирають на все кільце наперед — аж до ядра 6.18, де з'явився змішаний режим `IORING_SETUP_CQE_MIXED`.

## Прапорці налаштування `IORING_SETUP_*`

| прапорець | ядро | що змінює |
|---|---|---|
| `IORING_SETUP_IOPOLL` | 5.1 | завершення виловлюють опитуванням пристрою, без переривань; лише для прямого вводу-виводу на носіях, що це вміють |
| `IORING_SETUP_SQPOLL` | 5.1 | потік ядра сам стежить за хвостом SQ — подання без жодного системного виклику |
| `IORING_SETUP_SQ_AFF` | 5.1 | прив'язати цей потік до ядра процесора з `sq_thread_cpu` |
| `IORING_SETUP_CQSIZE` | 5.5 | розмір CQ береться з `cq_entries`, а не «удвічі більший за SQ» |
| `IORING_SETUP_CLAMP` | 5.6 | завеликі розміри обрізати до стелі замість `EINVAL` |
| `IORING_SETUP_ATTACH_WQ` | 5.6 | позичити пул робітників уже наявного кільця з `wq_fd` |
| `IORING_SETUP_R_DISABLED` | 5.10 | кільце створюється вимкненим — щоб накласти обмеження до першого подання |
| `IORING_SETUP_SUBMIT_ALL` | 5.18 | помилка в одному SQE не спиняє подання решти пачки |
| `IORING_SETUP_COOP_TASKRUN` | 5.19 | не смикати задачу міжпроцесорним перериванням заради завершень |
| `IORING_SETUP_TASKRUN_FLAG` | 5.19 | натомість піднімати біт `IORING_SQ_TASKRUN` у прапорцях кільця |
| `IORING_SETUP_SQE128` / `IORING_SETUP_CQE32` | 5.19 | подвоєні записи: 128 Б на SQE, 32 Б на CQE |
| `IORING_SETUP_SINGLE_ISSUER` | 6.0 | обіцянка, що подає рівно одна задача — ядро знімає частину блокувань |
| `IORING_SETUP_DEFER_TASKRUN` | 6.1 | відкладену роботу виконувати тільки всередині `io_uring_enter` з `GETEVENTS` |
| `IORING_SETUP_NO_MMAP` | 6.5 | пам'ять під кільця дає програма, адреси — у полях `user_addr` |
| `IORING_SETUP_REGISTERED_FD_ONLY` | 6.5 | кільце без звичайного дескриптора, лише зареєстроване |
| `IORING_SETUP_NO_SQARRAY` | 6.6 | без непрямості: ядро читає SQE підряд, у порядку кільця |

Пара `COOP_TASKRUN` + `DEFER_TASKRUN` разом із `SINGLE_ISSUER` — це те, чим сучасний цикл подій купує решту продуктивності: програма обіцяє, що подає й забирає в одному потоці, а ядро за цю обіцянку перестає переривати її задля чужої роботи.

## Прапорці окремого запису `IOSQE_*`

| прапорець | ядро | що робить |
|---|---|---|
| `IOSQE_FIXED_FILE` | 5.1 | `fd` — це індекс у зареєстрованому масиві дескрипторів, а не дескриптор |
| `IOSQE_IO_DRAIN` | 5.2 | не починати, доки не завершилося геть усе подане раніше |
| `IOSQE_IO_LINK` | 5.3 | наступний SQE пачки почнеться лише після успіху цього; помилка обриває ланцюжок із `−ECANCELED` |
| `IOSQE_IO_HARDLINK` | 5.5 | те саме, але ланцюжок триває навіть після помилки |
| `IOSQE_ASYNC` | 5.6 | не пробувати виконати на місці — одразу віддати робітникові `io-wq` |
| `IOSQE_BUFFER_SELECT` | 5.7 | буфер обирає ядро з групи `buf_group`; номер повернеться в `flags` CQE |
| `IOSQE_CQE_SKIP_SUCCESS` | 5.17 | не породжувати CQE, якщо операція вдалася |

Різниця між `IOSQE_IO_DRAIN` і `IOSQE_IO_LINK` — це різниця між бар'єром і ниткою. `DRAIN` спиняє все кільце: запис із ним чекає геть на всі попередні, а отже вбиває паралельність рівно там, де вона потрібна. `LINK` в'яже лише сусідів у ланцюжку, тож решта поданих операцій їде повз нього своїм ходом. Тому послідовність «спершу записати, потім скинути на диск» виражають ланцюжком, а не бар'єром, і `DRAIN` лишають на рідкісні випадки на кшталт зміни спільного стану всього кільця.

## Що передають у `io_uring_enter`

| прапорець | що означає |
|---|---|
| `IORING_ENTER_GETEVENTS` | без нього `min_complete` ігнорується: чекати ядро буде, тільки якщо його попросили цим бітом |
| `IORING_ENTER_SQ_WAKEUP` | розбудити приспаний потік `SQPOLL` |
| `IORING_ENTER_SQ_WAIT` | почекати, доки в кільці подань звільниться місце |
| `IORING_ENTER_EXT_ARG` | останні два аргументи — це `struct io_uring_getevents_arg` (маска сигналів і таймаут), а не `sigset_t *` |
| `IORING_ENTER_REGISTERED_RING` | `fd` — індекс зареєстрованого кільця, а не справжній дескриптор |

Дзеркально програма читає поле `flags` кільця подань — те, чиє зміщення лежить у `sq_off.flags`.

| біт у `sq_off.flags` | коли ядро його ставить |
|---|---|
| `IORING_SQ_NEED_WAKEUP` | потік `SQPOLL` заснув — потрібен один `io_uring_enter` із `SQ_WAKEUP` |
| `IORING_SQ_CQ_OVERFLOW` | є завершення, що не влізли в кільце й чекають у списку переповнення |
| `IORING_SQ_TASKRUN` | накопичилася відкладена робота — варто зайти в ядро, щоб її виконали |

## Коди операцій

Перевіряти доступність операції правильно не за версією ядра, а поданням: невідомий чи невпроваджений `opcode` повертає в `res` значення `−EOPNOTSUPP`, не ламаючи нічого. Другий спосіб — `IORING_REGISTER_PROBE`, який віддає таблицю підтримуваних кодів одним викликом.

| операція | ядро | замінює |
|---|---|---|
| `IORING_OP_NOP` | 5.1 | нічого не робить — міряють нею дорогу кільця |
| `IORING_OP_READV`, `IORING_OP_WRITEV` | 5.1 | `preadv`, `pwritev` |
| `IORING_OP_READ_FIXED`, `IORING_OP_WRITE_FIXED` | 5.1 | те саме, але в зареєстрований буфер за індексом |
| `IORING_OP_FSYNC` | 5.1 | `fsync`, `fdatasync` |
| `IORING_OP_POLL_ADD`, `IORING_OP_POLL_REMOVE` | 5.1 | `poll` на одному дескрипторі |
| `IORING_OP_SYNC_FILE_RANGE` | 5.2 | `sync_file_range` |
| `IORING_OP_SENDMSG`, `IORING_OP_RECVMSG` | 5.3 | `sendmsg`, `recvmsg` |
| `IORING_OP_TIMEOUT` | 5.4 | таймер усередині кільця |
| `IORING_OP_ACCEPT`, `IORING_OP_CONNECT` | 5.5 | `accept4`, `connect` |
| `IORING_OP_ASYNC_CANCEL` | 5.5 | **просить** скасувати операцію за `user_data` |
| `IORING_OP_LINK_TIMEOUT` | 5.5 | обмеження часу на попередній SQE в ланцюжку |
| `IORING_OP_READ`, `IORING_OP_WRITE` | 5.6 | `pread`, `pwrite` — без масиву `iovec` |
| `IORING_OP_SEND`, `IORING_OP_RECV` | 5.6 | `send`, `recv` |
| `IORING_OP_OPENAT`, `IORING_OP_OPENAT2`, `IORING_OP_CLOSE` | 5.6 | відкриття й закриття файлу |
| `IORING_OP_STATX`, `IORING_OP_FALLOCATE`, `IORING_OP_FADVISE`, `IORING_OP_MADVISE` | 5.6 | однойменні виклики |
| `IORING_OP_EPOLL_CTL` | 5.6 | `epoll_ctl` |
| `IORING_OP_SPLICE` | 5.7 | `splice` |
| `IORING_OP_PROVIDE_BUFFERS`, `IORING_OP_REMOVE_BUFFERS` | 5.7 | наповнення групи буферів для `IOSQE_BUFFER_SELECT` |
| `IORING_OP_TEE` | 5.8 | `tee` |
| `IORING_OP_SHUTDOWN`, `IORING_OP_RENAMEAT`, `IORING_OP_UNLINKAT` | 5.11 | `shutdown`, `renameat2`, `unlinkat` |
| `IORING_OP_MKDIRAT`, `IORING_OP_SYMLINKAT`, `IORING_OP_LINKAT` | 5.15 | створення каталогу й посилань |
| `IORING_OP_MSG_RING` | 5.18 | надіслати CQE в інше кільце |
| `IORING_OP_SOCKET` | 5.19 | `socket` |
| `IORING_OP_URING_CMD` | 5.19 | наскрізна команда драйверові (звідси й потреба у SQE128) |
| `IORING_OP_SEND_ZC` | 6.0 | надсилання без копіювання; успіх приходить двома CQE |
| `IORING_OP_SENDMSG_ZC` | 6.1 | те саме для `sendmsg` |
| `IORING_OP_WAITID` | 6.5 | `waitid` — навіть очікування дитини стає операцією кільця |
| `IORING_OP_FUTEX_WAIT`, `IORING_OP_FUTEX_WAKE` | 6.7 | операції з ф'ютексом усередині кільця |
| `IORING_OP_FIXED_FD_INSTALL` | 6.8 | зробити із зареєстрованого дескриптора звичайний |
| `IORING_OP_BIND`, `IORING_OP_LISTEN` | 6.11 | `bind`, `listen` |

Багаторазову форму дає не окремий код, а прапорець в `ioprio` — так працюють `accept`, `recv` і `recvmsg` починаючи з ядра 5.19; винятком є `IORING_OP_READ_MULTISHOT` (6.7), який таки виділено в окремий код.

Загальний малюнок цієї таблиці читається згори вниз. Спершу io_uring умів лише те, що болить у гарячому шляху: читати, писати, синхронізувати, опитувати. Далі в нього переїхали мережеві виклики, потім робота з іменами файлів, а зрештою й речі, що з вводом-виводом не пов'язані взагалі — ф'ютекси, очікування дитини, створення сокета. Кільце перестало бути прискорювачем вводу-виводу й стало другим способом кликати ядро, у якому виклик є даними, а не переходом межі.

## `io_uring_register`: що віддають ядру назавжди

| код | ядро | що реєструє |
|---|---|---|
| `IORING_REGISTER_BUFFERS` | 5.1 | масив буферів — сторінки закріплюють один раз, а не на кожну операцію |
| `IORING_REGISTER_FILES` | 5.1 | масив дескрипторів — пошук файлової структури зникає з гарячого шляху |
| `IORING_REGISTER_EVENTFD` | 5.2 | [eventfd](book:unix-linux/eventfd-and-futex), у який ядро писатиме про нові завершення; так кільце вставляють у наявний цикл на `epoll` |
| `IORING_REGISTER_FILES_UPDATE` | 5.5 | замінити окремі комірки масиву дескрипторів на ходу |
| `IORING_REGISTER_PROBE` | 5.6 | спитати, які коди операцій це ядро підтримує |
| `IORING_REGISTER_PERSONALITY` | 5.6 | запам'ятати поточні облікові дані під номером для поля `personality` |
| `IORING_REGISTER_RESTRICTIONS` | 5.10 | обмежити перелік дозволених операцій — разом із `R_DISABLED` |
| `IORING_REGISTER_BUFFERS2`, `IORING_REGISTER_FILES2` | 5.13 | те саме з мітками ресурсів і оновленням на місці |
| `IORING_REGISTER_IOWQ_MAX_WORKERS` | 5.15 | стеля кількості робітників `io-wq` |
| `IORING_REGISTER_RING_FDS` | 5.18 | зареєструвати саме кільце — щоб `io_uring_enter` не шукав дескриптор |
| `IORING_REGISTER_PBUF_RING` | 5.19 | кільце наданих буферів замість `PROVIDE_BUFFERS` |

Реєстрація — не гарячий шлях, і платять за неї наперед. Буфери, віддані `IORING_REGISTER_BUFFERS`, ядро закріплює в пам'яті: вони мусять бути анонімними (з `malloc` або `mmap` з `MAP_ANONYMOUS`), не більшими за гігабайт кожен, і рахуються проти обмеження `RLIMIT_MEMLOCK`. До ядра 5.13 реєстрація ще й чекала, доки кільце спорожніє: усі операції в польоті мусили спершу завершитися. Звідси проста порада — реєструвати один раз при старті, а не в циклі подій.

## Куди приходить помилка

Помилки тут живуть на двох рівнях, і плутанина між ними — класична пастка. Сам виклик `io_uring_enter` повертає `−1` та `errno` лише тоді, коли зламано взаємодію з кільцем: **подання не відбулося**. Помилка ж конкретної операції — це нормальне завершення, і вона приходить у `res` того самого CQE, від'ємним значенням коду.

| `errno` самого виклику | причина |
|---|---|
| `EBADF` | `fd` не є дескриптором |
| `EOPNOTSUPP` | `fd` існує, але це не кільце io_uring |
| `EBADFD` | кільце створено з `R_DISABLED` і ще не ввімкнене |
| `EBUSY` | немає місця в кільці завершень для нових запитів |
| `EBADR` | завершення довелося відкинути — їх втрачено |
| `EINVAL` | заборонена комбінація бітів у `flags` |
| `EINTR` | очікування перервав сигнал |
| `EOWNERDEAD` | потік `SQPOLL` загинув; кільце ще живе, але подавати доводиться самим |

| `res` у CQE | причина |
|---|---|
| `≥ 0` | кількість байтів, новий дескриптор або просто `0` |
| `−EOPNOTSUPP` | код операції правильний, але це ядро його не вміє — головна перевірка можливостей |
| `−ECANCELED` | операцію скасовано або обірвано ланцюжок `IOSQE_IO_LINK` |
| `−ENOBUFS` | `IOSQE_BUFFER_SELECT` при порожній групі буферів |
| `−ETIME` | таймер `IORING_OP_TIMEOUT` доробив своє |
| `−EAGAIN` | операція не змогла виконатися без блокування — подавати наново |
| `−EBADF`, `−EFAULT`, `−EINVAL` | те саме, що повернув би звичайний виклик із такими аргументами |

## Мінімальний робочий виклик

Найкоротший шлях від нуля до одного завершення, без `liburing` — щоб було видно, з чого воно складається. Бар'єри тут не прикраса: без запису-звільнення на хвості ядро може побачити новий індекс раніше за вміст SQE.

```c
#define _GNU_SOURCE
#include <linux/io_uring.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    struct io_uring_params p;
    memset(&p, 0, sizeof p);                        /* resv мусить бути нулем */

    int fd = (int)syscall(__NR_io_uring_setup, 8, &p);
    if (fd < 0) { perror("io_uring_setup"); return 1; }
    if (!(p.features & IORING_FEAT_SINGLE_MMAP)) {
        fprintf(stderr, "ядро старше за 5.4: CQ треба відображати окремо\n");
        return 1;
    }

    size_t sz = p.sq_off.array + p.sq_entries * sizeof(__u32);
    size_t cz = p.cq_off.cqes  + p.cq_entries * sizeof(struct io_uring_cqe);
    if (cz > sz) sz = cz;

    char *ring = mmap(NULL, sz, PROT_READ | PROT_WRITE,
                      MAP_SHARED | MAP_POPULATE, fd, IORING_OFF_SQ_RING);
    struct io_uring_sqe *sqes =
        mmap(NULL, p.sq_entries * sizeof(*sqes), PROT_READ | PROT_WRITE,
             MAP_SHARED | MAP_POPULATE, fd, IORING_OFF_SQES);

    unsigned *sq_tail  = (unsigned *)(ring + p.sq_off.tail);
    unsigned *sq_mask  = (unsigned *)(ring + p.sq_off.ring_mask);
    unsigned *sq_array = (unsigned *)(ring + p.sq_off.array);
    unsigned *cq_head  = (unsigned *)(ring + p.cq_off.head);
    unsigned *cq_tail  = (unsigned *)(ring + p.cq_off.tail);
    unsigned *cq_mask  = (unsigned *)(ring + p.cq_off.ring_mask);
    struct io_uring_cqe *cqes = (struct io_uring_cqe *)(ring + p.cq_off.cqes);

    static char buf[4096];
    unsigned tail = *sq_tail, i = tail & *sq_mask;

    memset(&sqes[i], 0, sizeof sqes[i]);            /* поля — об'єднання: нулюємо все */
    sqes[i].opcode    = IORING_OP_READ;
    sqes[i].fd        = 0;                          /* стандартний ввід          */
    sqes[i].off       = (__u64)-1;                  /* поточна позиція файлу     */
    sqes[i].addr      = (__u64)(uintptr_t)buf;
    sqes[i].len       = sizeof buf;
    sqes[i].user_data = 0x1234;

    sq_array[i] = i;
    __atomic_store_n(sq_tail, tail + 1, __ATOMIC_RELEASE);   /* запис-звільнення */

    /* один перехід межі: подати рівно 1 і дочекатися рівно 1 завершення */
    if (syscall(__NR_io_uring_enter, fd, 1, 1, IORING_ENTER_GETEVENTS, NULL, 0) < 0)
        { perror("io_uring_enter"); return 1; }

    unsigned t = __atomic_load_n(cq_tail, __ATOMIC_ACQUIRE); /* читання-захоплення */
    while (*cq_head != t) {
        struct io_uring_cqe *c = &cqes[*cq_head & *cq_mask];
        printf("user_data=0x%llx res=%d flags=0x%x\n",
               (unsigned long long)c->user_data, c->res, c->flags);
        __atomic_store_n(cq_head, *cq_head + 1, __ATOMIC_RELEASE);
    }
    return 0;
}
```

Ці півсотні рядків — рівно те, що `liburing` ховає за трьома викликами `io_uring_queue_init`, `io_uring_submit` і `io_uring_wait_cqe`. Писати їх руками варто один раз — щоб потім знати, що саме бібліотека робить із вашим хвостом і чому буфер не можна чіпати до CQE.
