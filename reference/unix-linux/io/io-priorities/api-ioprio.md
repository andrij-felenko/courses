# 📋 Контракт ioprio: виклики, константи й точки керування

Це формальний бік пріоритету вводу-виводу: сигнатури двох системних викликів, розкладка бітів у числі пріоритету, повний перелік класів, рівнів і підказок, коди помилок із точною умовою кожного, а також усі поверхні, крізь які це число задають, — `ionice`, юніт systemd, поле в описі асинхронної операції та файл у cgroup. Довідка потрібна тому, що інтерфейс тут розкиданий: константи лежать у заголовку ядра, обгорток у бібліотеці немає, а одне й те саме число в різних місцях називають по-різному.

Усе нижче звірено з мейнлайновим кодом ядра (`include/uapi/linux/ioprio.h`, `include/linux/ioprio.h`, `block/ioprio.c`, `block/blk-ioc.c`, `block/mq-deadline.c`, `io_uring/rw.c`), сторінками `ioprio_set(2)`, `ionice(1)`, `systemd.exec(5)`, вихідним кодом `util-linux` і документацією `Documentation/admin-guide/cgroup-v2.rst`.

---

## 1. Два системні виклики

Обгорток у glibc немає й не планується, тож звертаються через [`syscall()`](topic:unix-linux/syscall-mechanics). Константи бере з `<linux/ioprio.h>` — це заголовок ядра, а не бібліотеки.

```c
#include <linux/ioprio.h>
#include <sys/syscall.h>
#include <unistd.h>

static inline int ioprio_set(int which, int who, int ioprio) {
    return syscall(SYS_ioprio_set, which, who, ioprio);
}
static inline int ioprio_get(int which, int who) {
    return syscall(SYS_ioprio_get, which, who);
}
```

`ioprio_set` повертає `0` або `-1` з `errno`. `ioprio_get` повертає саме значення пріоритету — воно завжди невід'ємне, тож `-1` однозначно означає помилку.

**Мінімальний робочий виклик: перевести себе в клас `idle`.**

```c
if (ioprio_set(IOPRIO_WHO_PROCESS, 0,
               IOPRIO_PRIO_VALUE(IOPRIO_CLASS_IDLE, 0)) == -1)
    perror("ioprio_set");
```

## 2. Адресат: which і who

| `which` | Значення | Що означає `who` | `who = 0` |
| --- | --- | --- | --- |
| `IOPRIO_WHO_PROCESS` | 1 | ідентифікатор **задачі** (TID), не процесу | ця задача |
| `IOPRIO_WHO_PGRP` | 2 | ідентифікатор групи процесів | група викликача |
| `IOPRIO_WHO_USER` | 3 | реальний UID | UID викликача |

Одиницею тут є задача, тому [потоки одного процесу](topic:unix-linux/threads-as-tasks) можуть мати різні пріоритети; `IOPRIO_WHO_PROCESS` із чужим TID цілком законний. Будь-яке інше значення `which` дає `EINVAL`.

Два групові адресати не рівноцінні за змістом: `ioprio_set` проходить кожну знайдену задачу й виставляє число їй окремо, тобто змінює стільки атрибутів, скільки знайшов, — а `ioprio_get` мусить відповісти одним числом і тому знайдене згортає. Читання групи не є оберненим до запису в групу: між ними задачі могли з'явитися, зникнути або перевиставити пріоритет собі самі.

## 3. Розкладка числа

Число займає 16 біт і ділиться на три поля. Усі імена нижче — з `include/uapi/linux/ioprio.h`.

| Константа | Значення | Що описує |
| --- | --- | --- |
| `IOPRIO_CLASS_SHIFT` | 13 | клас — біти 15–13 |
| `IOPRIO_NR_CLASSES` | 8 | скільки значень уміщує поле класу |
| `IOPRIO_CLASS_MASK` | 7 | `IOPRIO_NR_CLASSES − 1` |
| `IOPRIO_HINT_SHIFT` | 3 | підказка — біти 12–3 |
| `IOPRIO_HINT_NR_BITS` | 10 | ширина поля підказки |
| `IOPRIO_NR_HINTS` | 1024 | скільки значень уміщує поле підказки |
| `IOPRIO_LEVEL_NR_BITS` | 3 | рівень — біти 2–0 |
| `IOPRIO_NR_LEVELS` | 8 | рівні 0…7, нуль — найвищий |
| `IOPRIO_LEVEL_MASK` | 7 | `IOPRIO_NR_LEVELS − 1` |
| `IOPRIO_PRIO_MASK` | 8191 | тринадцять молодших біт: підказка **разом** із рівнем |
| `IOPRIO_NORM` | 4 | типовий рівень best-effort |

Складають і розбирають число макросами. Зверніть увагу на відмінність двох останніх у першій групі: `IOPRIO_PRIO_LEVEL` дає лише три молодші біти, а `IOPRIO_PRIO_DATA` — усі тринадцять, тобто підказку разом із рівнем. Саме `IOPRIO_PRIO_DATA` друкує `ionice`.

```c
IOPRIO_PRIO_CLASS(v)                       /* (v >> 13) & 7      */
IOPRIO_PRIO_HINT(v)                        /* (v >> 3) & 0x3ff   */
IOPRIO_PRIO_LEVEL(v)                       /* v & 7              */
IOPRIO_PRIO_DATA(v)                        /* v & 0x1fff         */

IOPRIO_PRIO_VALUE(class, level)            /* підказка = IOPRIO_HINT_NONE */
IOPRIO_PRIO_VALUE_HINT(class, level, hint)
```

Обидва макроси-конструктори звертаються до вбудованої функції `ioprio_value()`, і вона **не сигналізує про помилку на місці**: аргумент поза діапазоном дає `IOPRIO_CLASS_INVALID << 13`, тобто цілком нормальне на вигляд число, яке відхилить уже системний виклик.

**Кілька готових значень.**

```
IOPRIO_PRIO_VALUE(IOPRIO_CLASS_BE, 7)      = (2 << 13) | 7            = 16391
IOPRIO_PRIO_VALUE(IOPRIO_CLASS_IDLE, 0)    = (3 << 13) | 0            = 24576
IOPRIO_PRIO_VALUE_HINT(IOPRIO_CLASS_RT, 0, 3)
                                           = (1 << 13) | (3 << 3) | 0 = 8216
IOPRIO_CLASS_INVALID << IOPRIO_CLASS_SHIFT = 7 << 13                  = 57344

IOPRIO_PRIO_CLASS(16391) = 16391 >> 13 = 2
IOPRIO_PRIO_LEVEL(16391) = 16391 & 7   = 7
```

Половина цих імен молодша за саме число. До 6.4 включно заголовок знав лише `IOPRIO_PRIO_CLASS`, `IOPRIO_PRIO_DATA` і `IOPRIO_PRIO_VALUE`; ні `IOPRIO_PRIO_LEVEL`, ні `IOPRIO_PRIO_HINT`, ні `IOPRIO_PRIO_VALUE_HINT`, ні `IOPRIO_CLASS_INVALID` там ще не було. Старий `IOPRIO_PRIO_VALUE` до того ж був звичайним макросом і **обрізав** аргументи маскою замість того, щоб віддати неправильне значення: клас 9 тихо ставав класом 1. Тому переносний код зазвичай не покладається на заголовок узагалі, а визначає потрібні три-чотири макроси сам — зсув 13 і ширина полів не мінялися ніколи.

## 4. Класи

| Константа | Значення | Рівні | Права на встановлення |
| --- | --- | --- | --- |
| `IOPRIO_CLASS_NONE` | 0 | лише 0 | без прав; рівень ≠ 0 дає `EINVAL` |
| `IOPRIO_CLASS_RT` | 1 | 0…7 | `CAP_SYS_ADMIN` **або** `CAP_SYS_NICE` |
| `IOPRIO_CLASS_BE` | 2 | 0…7 | без прав |
| `IOPRIO_CLASS_IDLE` | 3 | ігноруються | без прав (до 2.6.25 треба був `CAP_SYS_ADMIN`) |
| `IOPRIO_CLASS_INVALID` | 7 | — | не задають; повертається з макроса при поганих аргументах |

Значення 4–6 не визначені й дають `EINVAL`. Клас `NONE` — не політика, а позначка «не задавали»; його ставлять, щоб скинути раніше виставлений пріоритет. Перевірку робить `ioprio_check_cap()` у `block/ioprio.c`; про самі [можливості](topic:unix-linux/capabilities) — окрема тема.

## 5. Підказка (з ядра 6.5)

Десять біт між класом і рівнем несуть номер обмеження тривалості команди (Command Duration Limits) — конфігурації, заздалегідь записаної в сам накопичувач. Підказка не впливає на порядок обслуговування в черзі, вона каже пристрою, як довго він має право поратися з цією командою.

| Константа | Значення |
| --- | --- |
| `IOPRIO_HINT_NONE` | 0 |
| `IOPRIO_HINT_DEV_DURATION_LIMIT_1` … `_7` | 1 … 7 |

Визначено вісім значень із 1024 можливих; решта поля зарезервована. Підказку приймають лише класи `RT` і `BE`, а розуміє її пристрій — накопичувач без налаштованих CDL її просто не помітить.

## 6. Що саме повертає ioprio_get

Тут ховається асиметрія, через яку прочитане число часто не збігається з тим, що ядро чіпляє на запит.

| Випадок | Результат |
| --- | --- |
| `IOPRIO_WHO_PROCESS` | **сире** збережене значення; задача, яка ніколи не викликала `ioprio_set`, дає `0` (клас `NONE`) |
| `IOPRIO_WHO_PGRP`, `IOPRIO_WHO_USER` | згортка всіх знайдених через `ioprio_best()` — числовий **мінімум**, тобто найвищий пріоритет |
| жодного адресата не знайдено | `-1`, `errno = ESRCH` |

`ioprio_best()` спершу зводить кожне невалідне значення (а клас `NONE` саме таким і вважається) до нуля, тож досить одного незаданого процесу в групі — і відповідь за всю групу буде `none`.

На запит же ядро кладе **виведене** значення: `__get_task_ioprio()` підставляє замість класу `NONE` клас, що випливає з [політики планування процесора](topic:unix-linux/priority-nice-realtime), і рівень, що випливає з `nice`.

```
SCHED_IDLE             → IOPRIO_CLASS_IDLE
SCHED_FIFO / RR / DEADLINE → IOPRIO_CLASS_RT
решта                  → IOPRIO_CLASS_BE

рівень = (nice + 20) / 5        (цілочисельне ділення)
```

Наслідок, який рідко очікують: задача з реальночасовою політикою процесора дістає клас `RT` у дисковій черзі **даром**, без жодної можливості, — бо `ioprio_check_cap()` цього шляху взагалі не бачить.

## 7. Помилки

| `errno` | Точна умова |
| --- | --- |
| `EINVAL` | `which` поза 1…3; клас 4…7 включно з `INVALID`; клас `NONE` з ненульовим рівнем |
| `EPERM` | клас `RT` без `CAP_SYS_ADMIN` і без `CAP_SYS_NICE`; або реальний UID цілі не збігається ні з ефективним, ні з реальним UID викликача — і немає `CAP_SYS_NICE` |
| `ESRCH` | за парою (`which`, `who`) не знайдено жодного процесу |

Правило власності перевіряє `set_task_ioprio()` у `block/blk-ioc.c` і порівнює саме **реальний** UID цілі — не ефективний.

## 8. ionice(1) з util-linux

Три форми: прочитати, змінити наявній задачі, запустити нову з потрібним пріоритетом (атрибут виставляють між `fork` і `exec`, далі його успадковує все дерево).

| Ключ | Довга форма | Що робить |
| --- | --- | --- |
| `-c` | `--class` | клас: ім'я (`none`, `realtime`, `best-effort`, `idle`) або число 0–3 |
| `-n` | `--classdata` | рівень 0–7; діє лише для `realtime` і `best-effort` |
| `-p` | `--pid` | адресат — PID (один або кілька) |
| `-P` | `--pgid` | адресат — група процесів |
| `-u` | `--uid` | адресат — усі процеси користувача |
| `-t` | `--ignore` | не вважати невдачу помилкою: команду запустити однаково |

Без `-c` береться `best-effort`, без `-n` — рівень 4.

```
$ ionice -c 3 tar czf /backup/home.tgz /home   # запустити в класі idle
$ ionice -c 2 -n 7 -p 4821                     # перевести на льоту
$ ionice -p 4821                               # прочитати
best-effort: prio 7
$ ionice -p 1
none: prio 0
```

Формат виводу: для `idle` друкують лише ім'я класу, для решти — `клас: prio N`. Число `N` — це `IOPRIO_PRIO_DATA`, тобто підказка разом із рівнем; якщо підказка не нульова, надруковане число не є рівнем.

## 9. systemd

Директиви належать до `systemd.exec(5)` і виставляються процесові перед `exec` — це той самий атрибут, а не налаштування cgroup, тож діє він тільки на дерево юніта й тільки за успадкуванням. Про [модель юнітів](topic:unix-linux/systemd-model) — окремо.

| Директива | Приймає | Типове |
| --- | --- | --- |
| `IOSchedulingClass=` | `none`, `realtime`, `best-effort`, `idle` (або 0–3) | клас ядра — `best-effort` |
| `IOSchedulingPriority=` | 0…7 | 4 |

## 10. Пріоритет на самій операції

Коли пріоритет треба задати не заняттю, а окремій операції, число кладуть просто в її опис — кодування те саме.

У [libaio](topic:unix-linux/linux-aio-io-submit) поле `aio_reqprio` без прапорця ядро ігнорує:

```c
struct iocb cb = {0};
cb.aio_lio_opcode = IOCB_CMD_PREAD;
cb.aio_reqprio    = IOPRIO_PRIO_VALUE(IOPRIO_CLASS_IDLE, 0);
cb.aio_flags     |= IOCB_FLAG_IOPRIO;   /* (1 << 1); з ядра 4.18 */
```

В [io_uring](topic:unix-linux/io-uring) поле `__u16 ioprio` стоїть третім у кожному записі черги подань:

```c
struct io_uring_sqe *sqe = io_uring_get_sqe(ring);
io_uring_prep_read(sqe, fd, buf, len, off);
sqe->ioprio = IOPRIO_PRIO_VALUE(IOPRIO_CLASS_RT, 0);
```

Дві пастки. Перша: нуль у полі означає «взяти пріоритет задачі», а ненульове значення проходить той самий `ioprio_check_cap()` — тож `EPERM` за клас `RT` прилетить не з `io_uring_submit()`, а результатом самого запису в черзі завершень. Друга: для мережевих операцій це поле зайняте під прапорці операції (`IORING_RECVSEND_POLL_FIRST`, `IORING_RECV_MULTISHOT`, `IORING_ACCEPT_MULTISHOT` та інші) — там воно пріоритетом не є взагалі.

## 11. Точки перевірки в sysfs

Перш ніж покладатися на пріоритет, варто пересвідчитися, що його є кому прочитати. Файли живуть у [моделі пристроїв sysfs](topic:unix-linux/sysfs-device-model), назви `<dev>` беруться з `/sys/block/`. Перевіряти треба **кожну** чергу на шляху окремо: складений пристрій — том LVM, програмний RAID, `loop` — має власну чергу з власним планувальником, і налаштування нижнього носія про неї нічого не каже.

| Шлях | Що показує |
| --- | --- |
| `/sys/block/<dev>/queue/scheduler` | доступні [планувальники](topic:unix-linux/io-schedulers), чинний — у квадратних дужках; `[none]` означає, що пріоритет не читає ніхто |
| `/sys/block/<dev>/queue/iosched/prio_aging_expire` | лише в `mq-deadline`: мілісекунди, після яких запит нижчого класу пускають попри вищі; типово 10000 |
| `/sys/block/<dev>/queue/nr_requests` | глибина програмної черги — верхня межа того, скільки роботи взагалі є що переставляти |

## 12. cgroup: io.prio.class

Файл групи в cgroup v2 перебиває клас усіх запитів, що з неї виходять, — включно з тими, що йдуть від потоків зворотного запису. Подробиці шару — в темі про [керування вводом-виводом по cgroup](topic:unix-linux/io-cgroup-control).

| Значення | Дія |
| --- | --- |
| `no-change` | типове: не чіпати |
| `promote-to-rt` | запитам не з класу `RT` поставити `RT` і рівень 4 |
| `restrict-to-be` | запитам без класу або з класом `RT` поставити `BE` і рівень 0; `IDLE` не чіпати |
| `idle` | усім запитам поставити `IDLE` |
| `none-to-rt` | застарілий синонім `promote-to-rt` |

```
# echo restrict-to-be > /sys/fs/cgroup/tenants/app/io.prio.class
```

Правило групи діє в обидва боки й не потребує узгодження з процесами всередині: `restrict-to-be` — саме той запобіжник, який не пускає в реальний час групу, де хтось усе-таки має `CAP_SYS_NICE`.
