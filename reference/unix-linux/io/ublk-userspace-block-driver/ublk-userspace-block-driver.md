# Фреймворк ublk: блокові драйвери у просторі користувача

- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — межа між ядром та простором користувача, системні виклики та VFS.
- [Механізм io_uring](book:unix-linux/io-uring) — асинхронне кільце операцій вводу-виводу без перемикання контексту.
- [Пасстру-команди io_uring](book:unix-linux/io-uring-cmd-passthrough) — прямий обмін викликами IORING_OP_URING_CMD між пристроєм і демоном.

**ublk (Userspace Block Device)** — це фреймворк у ядрі Linux (починаючи з версії 6.0), який дозволяє створювати високопродуктивні блокові драйвери повністю у просторі користувача. Він вирішує давню фундаментальну проблему розробки систем зберігання даних: як реалізувати складну логіку блокового накопичувача у звичайній програмі (userspace daemon) без ризику обвалити ядро Linux і без втрати пропускної здатності диска.

Історично створення блокового драйвера вимагало написання модуля ядра (kernel module). Доступ до підсистеми `blk-mq` через код ядра вимагав дотримання суворих правил конкурентності та синхронізації спінлоків. Найменша помилка в коді модуля призводить до kernel panic і негайного краху всієї операційної системи. Ранні спроби винести драйвери у простір користувача — такі як Network Block Device (NBD), BUSE чи TCMU — створювали величезні накладні витрати CPU. Кожен запит читання чи запису вимагав суттєвих затримок через постійні перемикання контексту процесора та копіювання буферів даних у пам'яті. Детальніше про цей еволюційний шлях розповідає [історія блокових драйверів простору користувача](book:unix-linux/ublk-userspace-block-driver/hist-userspace-block-devs.md).

## Архітектурний принцип ublk

Фреймворк ublk спирається на асинхронний інтерфейс `io_uring` та його спеціальне розширення — **io_uring command passthrough** (`IORING_OP_URING_CMD`). Система складається з двох основних компонентів:

1. **Модуль ядра (`ublk_drv`)**: створює віртуальний блоковий пристрій `/dev/ublkbN` для файлових систем та керуючий символьний пристрій `/dev/ublkcN` для комунікації з демоном.
2. **Демон у просторі користувача (`ublksrv`)**: містить логіку обробки запитів (читання/запис у файл, мережевий диск Ceph RBD, розархівацію чи дедуплікацію даних).

![Архітектура ublk](/reference/unix-linux/io/ublk-userspace-block-driver/img/ublk-arch.svg)
*Архітектура ublk: взаємодія модуля ядра ublk_drv та таргет-демона у просторі користувача через кільцеві буфери io_uring.*

Обмін командами між ядром та демоном відбувається без виконання класичних системних викликів на кожен I/O-запит. Демон заздалегідь надсилає в Submission Queue (SQ) `io_uring` спеціальні команди очікування (`UBLK_U_IO_FETCH_REQ`). Коли операційна система надсилає блоковий запит на пристрій `/dev/ublkbN`, модуль ядра заповнює готове кільце Completion Queue (CQ) метаданими запиту. Демон зчитує ці дані, обробляє I/O і повертає результат через комбіновану команду `UBLK_U_IO_COMMIT_AND_FETCH_REQ`, яка одночасно повертає результат і запитує наступний запит.

> 🔧 **Навіщо це.** ublk дозволяє писати драйвери зберігання будь-якою мовою (C, C++, Rust, Go) та зневаджувати їх звичайними інструментами (GDB, Valgrind) без загрози зупинити роботу сервера. Падіння демона не обвалює ядро, а новіші версії ublk підтримують прозоре відновлення після збоїв (crash recovery).

## Передача даних без копіювання (Zero-Copy)

Головною перевагою ublk над NBD та BUSE є підтримка архітектури **Zero-Copy**. У звичайних користувацьких драйверах дані копіюються з буфера застосунку в ядро, а потім з ядра у буфер демона, створюючи подвійне навантаження на шину пам'яті. ublk уникає цього шляхом безпосереднього відображення фізичних сторінок пам'яті (`bio_vec`) або використання закріплення сторінок (page pinning) та mmap пристрою `/dev/ublkc*`.

![Шлях даних Zero-Copy](/reference/unix-linux/io/ublk-userspace-block-driver/img/zero-copy.svg)
*Схема Zero-Copy: пряма передача сторінок пам'яті між застосунком та апаратним диском без копіювання процесором.*

Дані передаються прямо з буфера користувацького застосунку у фізичний пристрій через DMA-контролер накопичувача, що забезпечує продуктивність на рівні мільйонів IOPS на одне ядро CPU, порівнянну з нативними драйверами ядра. Для розробки власних рішень існує [практичний приклад створення ublk-таргета мовами C та C++](book:unix-linux/ublk-userspace-block-driver/proj-ublk-target.md).

## Сфери застосування та відмовостійкість

- **Формати віртуальних дисків**: швидкісний доступ до образів `qcow2` чи `vmdk` без використання повільного NBD.
- **Розподілені сховища**: побудова високопродуктивних клієнтів для Ceph RBD чи GlusterFS повністю у просторі користувача без модифікації ядра.
- **Спеціалізовані алгоритми**: реалізація дедуплікації, шифрування та вирівнювання зносу для SMR/ZNS накопичувачів (Zoned Block Devices).
- **Відновлення після збоїв (Crash Recovery)**: у разі аварійного завершення таргет-демона (наприклад, по сигналу `SIGSEGV`) ядро не панікує, а утримує I/O-запити в черзі протягом настроюваного тайм-ауту. Перезапущений демон підключається заново і відновлює роботу без видачі помилок `EIO` користувацьким програмам.
- **Модель без блокувань (Lockless)**: демон зазвичай використовує по одному потоку на ядро CPU з прив'язкою до ядер та опитуванням кольора `SQPOLL`, що зберігає кеші процессора L1/L2 гарячими і виключає конкуренцію спінлоків.
