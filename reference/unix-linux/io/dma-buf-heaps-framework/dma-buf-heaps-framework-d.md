# Фреймворк dma-buf heaps: заміна ION для виділення неперервної памʼяті

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Історично екосистема Linux, особливо в контексті вбудованих пристроїв і платформ Android, стикалася з серйозними викликами у питаннях керування памʼяттю. Однією з найважливіших проблем була потреба у виділенні великих, фізично неперервних блоків памʼяті, які могли б використовуватися апаратними прискорювачами, такими як GPU, блоки апаратного декодування відео, контролери дисплеїв, камери тощо, без зайвих копіювань. Довгий час вирішенням цієї проблеми для платформи Android був фреймворк **ION**. Проте, незважаючи на свою популярність у світі Android, ION роками залишався у staging-гілці ядра Linux і мав численні недоліки, повʼязані з фрагментацією коду та відсутністю уніфікованого підходу. 

Як відповідь на ці виклики спільнотою розробників ядра Linux був створений **dma-buf heaps** — новий, сучасний фреймворк для виділення памʼяті, який стандартизує процес аллокації та є офіційною заміною ION. У цій статті ми детально розглянемо архітектуру dma-buf heaps, процес переходу від ION, типи доступних куп (heaps), API для простору користувача та ядра, а також практичні аспекти використання dma-buf heaps для обміну буферами типу zero-copy (нульове копіювання) між підсистемами V4L2 (камера), DRM (дисплей) та GPU.

## Передумови та історія: чому ми відмовляємося від ION

### Проблема, яку вирішував ION

У класичному Linux керування памʼяттю розроблялося переважно для процесорів загального призначення (CPU). CPU використовує блок керування памʼяттю (MMU), який дозволяє віртуально неперервним буферам фізично складатися з фрагментованих сторінок памʼяті. Однак багато вбудованих апаратних блоків (наприклад, апаратні кодеки або застарілі DMA-контролери) не мають власного IOMMU (Input-Output Memory Management Unit) і вимагають, щоб буфер був неперервним саме на рівні *фізичної памʼяті*. 

Більше того, у сучасних SoC виникає необхідність передавати великі масиви даних (наприклад, кадри відео з високою роздільною здатністю 4K або 8K) від камери до GPU для обробки, а потім до контролера дисплея для виведення на екран. Копіювання таких обсягів даних через CPU (навіть за допомогою DMA) є неприйнятним з точки зору продуктивності, енергоспоживання та пропускної здатності шини памʼяті. Виникла потреба в механізмі **zero-copy**, де один і той самий фізичний буфер розшарюється між різними апаратними пристроями та їх драйверами.

Для вирішення цих завдань компанія Google створила **ION** (Android ION memory allocator). ION дозволяв простору користувача виділяти памʼять з різних "куп" (heaps), таких як неперервна памʼять (CMA), памʼять з підтримкою IOMMU, carveout-регіони (зарезервована фізична памʼять) тощо. ION експортував файловий дескриптор, який потім можна було передавати через механізм **dma-buf** в інші підсистеми ядра.

### Чому ION не увійшов в основну гілку ядра (Mainline)

Незважаючи на ефективність для Android-пристроїв, ION мав суттєві архітектурні недоліки з точки зору спільноти Linux:
1. **Зловживання ioctl API:** ION мав один центральний пристрій `/dev/ion`, через який простором користувача виконувалися складні ioctl-запити. Щоб вибрати конкретний тип памʼяті, користувач використовував бітові маски (heap masks), що було специфічним для кожного SoC. 
2. **Фрагментація:** Кожен виробник чипів (Qualcomm, MediaTek, Rockchip) створював власні специфічні купи ION. Ядро містило безліч специфічного для вендорів коду.
3. **Відсутність модульності:** Додавання нової купи часто вимагало втручання в ядро фреймворку ION.
4. **ABI (Application Binary Interface):** ION не міг гарантувати стабільний ABI, оскільки ідентифікатори куп постійно змінювалися.

Через ці причини ION залишався в теці `drivers/staging/android/ion/` багато років, і врешті-решт було прийнято рішення замінити його на чистіший, простіший і більш модульний підхід.

## Архітектура dma-buf heaps

Фреймворк **dma-buf heaps** (введено в ядро Linux версії 5.6) вирішує проблеми ION шляхом кардинального спрощення архітектури. Основна ідея полягає в тому, щоб кожна купа (heap) мала власний файл пристрою в системі (character device) у теці `/dev/dma_heap/`. 

Замість того, щоб відкривати `/dev/ion` і вказувати складну маску для вибору типу памʼяті, програма простору користувача безпосередньо відкриває потрібний пристрій, наприклад `/dev/dma_heap/system`, і просить виділити буфер.

![Архітектура dma-buf heaps](dma_buf_heaps_arch.svg)

### Ключові принципи dma-buf heaps

1. **Один пристрій — одна купа:** Кожна купа експортується як окремий character device у просторі імен `/dev/dma_heap/`.
2. **Простий API:** Фреймворк надає лише один основний `ioctl` для виділення памʼяті: `DMA_HEAP_IOC_ALLOC`.
3. **Стандартний вихідний формат:** Результатом успішного виділення памʼяті є файловий дескриптор `dma-buf`. Цей дескриптор відразу готовий до розшарювання між драйверами ядра або передачі іншим процесам через Unix domain sockets.
4. **Використання існуючих механізмів:** dma-buf heaps тісно інтегрований із загальносистемним механізмом `dma-buf`. Сама по собі купа просто реалізує операції експорту `dma-buf` (`dma_buf_ops`).
5. **Чітке розділення стандартних і вендорських куп:** Стандартні купи (system, cma) реалізовані у загальній частині ядра. Вендорські купи можуть створюватися модулями, додаючи власні вузли в `/dev/dma_heap/`, але вони повинні дотримуватися єдиного API.

## Типи доступних куп (Heaps)

В основній гілці ядра зараз стандартизовано два основні типи куп, які покривають більшість потреб.

### 1. System Heap (`/dev/dma_heap/system`)

Ця купа виділяє памʼять за допомогою стандартного розподільника сторінок ядра (buddy allocator) через функцію `alloc_pages()`.
- **Характеристики:** Памʼять фізично розривна (розкидана по різних сторінках памʼяті). 
- **Кешування:** Памʼять є кешованою процесором, що робить її ефективною для читання/запису з боку CPU. Проте, при передачі такого буфера пристрою, драйвер зобовʼязаний виконувати операції синхронізації кешу (cache flush/invalidate), щоб апаратний пристрій бачив актуальні дані в оперативній памʼяті (а не ті, що залишилися в кеші CPU).
- **Використання:** Ідеально підходить для пристроїв, які підтримують IOMMU або scatter-gather DMA (коли пристрій сам здатний працювати з розірваною на сторінки фізичною памʼяттю). Це найбільш універсальний тип купи, наприклад, для обміну даними з GPU або сучасними дисплейними контролерами, захищеними IOMMU.

### 2. CMA Heap (`/dev/dma_heap/system-uncached` або специфічні CMA, напр. `/dev/dma_heap/linux,cma`)

CMA (Contiguous Memory Allocator) дозволяє системі резервувати великі блоки памʼяті, які можуть використовуватися для мігруючих сторінок операційної системи, поки вони не знадобляться для апаратних виділень. Коли драйверу або dma-buf heap потрібна велика неперервна памʼять, CMA витісняє звідти сторінки ОС і віддає неперервний блок.
- **Характеристики:** Памʼять фізично неперервна.
- **Використання:** Життєво необхідно для апаратних пристроїв, які не мають IOMMU і працюють лише з неперервною лінійною фізичною адресацією (старі DMA-контролери, прості LCD-контролери, деякі апаратні кодеки).
- **Доступність:** Зазвичай система може мати кілька CMA зон (наприклад, загальна CMA зона, або специфічна для мультимедіа). Вони можуть експортуватися під іменами на кшталт `/dev/dma_heap/linux,cma`.

У майбутньому розробники можуть додавати специфічні купи, наприклад, для виділення захищеної памʼяті (TrustZone / TEE), яка не доступна для читання з боку CPU (для захисту DRM-контенту).

## API простору користувача (User-Space API)

Використання dma-buf heaps у просторі користувача зводиться до кількох простих кроків на мові C/C++. Заголовковий файл API знаходиться у `<linux/dma-heap.h>`.

### Структура `dma_heap_allocation_data`

Єдина структура, яка використовується для ioctl запиту виділення:

```c
#include <linux/dma-heap.h>

struct dma_heap_allocation_data {
    __u64 len;        /* Бажаний розмір буфера у байтах (повинен бути кратним розміру сторінки PAGE_SIZE) */
    __u32 fd;         /* Файловий дескриптор (повертається сюди) */
    __u32 fd_flags;   /* Прапорці для файлового дескриптора (O_CLOEXEC, O_RDWR) */
    __u64 heap_flags; /* Прапорці купи (наприклад, для керування кешуванням, зараз переважно зарезервовано) */
};
```

### Приклад коду: Виділення буфера

Наведений нижче код демонструє, як програма простору користувача може виділити буфер розміром 4 МБ з системної купи (System Heap).

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <linux/dma-heap.h>
#include <errno.h>

int allocate_dma_buf(const char *heap_name, size_t size) {
    int heap_fd, dma_buf_fd, ret;
    struct dma_heap_allocation_data alloc_data = {0};
    char dev_path[256];

    snprintf(dev_path, sizeof(dev_path), "/dev/dma_heap/%s", heap_name);

    /* Відкриваємо пристрій купи */
    heap_fd = open(dev_path, O_RDONLY | O_CLOEXEC);
    if (heap_fd < 0) {
        perror("Failed to open dma_heap device");
        return -1;
    }

    alloc_data.len = size;
    alloc_data.fd_flags = O_RDWR | O_CLOEXEC;
    alloc_data.heap_flags = 0; /* Обов'язково 0, якщо інші прапорці не підтримуються */

    /* Запитуємо виділення пам'яті */
    ret = ioctl(heap_fd, DMA_HEAP_IOC_ALLOC, &alloc_data);
    if (ret < 0) {
        perror("DMA_HEAP_IOC_ALLOC failed");
        close(heap_fd);
        return -1;
    }

    dma_buf_fd = alloc_data.fd; /* Отримуємо файловий дескриптор dma-buf */
    close(heap_fd); /* Пристрій купи більше не потрібен */

    return dma_buf_fd;
}

int main() {
    size_t buffer_size = 4 * 1024 * 1024; /* 4 Мегабайти */
    int dma_buf_fd = allocate_dma_buf("system", buffer_size);
    
    if (dma_buf_fd < 0) {
        fprintf(stderr, "Allocation failed\n");
        return 1;
    }

    printf("Successfully allocated %zu bytes, dma-buf fd: %d\n", buffer_size, dma_buf_fd);

    /* Мапування пам'яті в простір користувача для запису даних (опціонально) */
    void *ptr = mmap(NULL, buffer_size, PROT_READ | PROT_WRITE, MAP_SHARED, dma_buf_fd, 0);
    if (ptr == MAP_FAILED) {
        perror("mmap failed");
        close(dma_buf_fd);
        return 1;
    }

    /* Записуємо дані у буфер */
    memset(ptr, 0xAA, buffer_size);

    /* Важливо: перед відправкою буфера апаратному пристрою може знадобитися синхронізація кешу 
       за допомогою DMA_BUF_IOCTL_SYNC */

    munmap(ptr, buffer_size);
    close(dma_buf_fd); /* Буфер буде автоматично звільнено, коли остання ссилка зникне */

    return 0;
}
```

Зверніть увагу на важливу особливість: життєвим циклом буфера керує лічильник посилань на файловий дескриптор (reference counting). Памʼять фізично звільняється лише тоді, коли всі відкриті файлові дескриптори на цей dma-buf закриваються (через `close()`), і всі драйвери в ядрі, яким цей буфер був переданий, також відпускають свої посилання.

## Механізм Zero-Copy між підсистемами

Головна цінність dma-buf heaps полягає не просто у виділенні памʼяті, а у можливості безперешкодно передавати цей буфер (як файловий дескриптор) між абсолютно різними підсистемами Linux (V4L2, DRM, ALSA, GPU) без створення додаткових копій даних (zero-copy). 

Розглянемо типовий пайплайн захоплення відео та виведення його на дисплей (Camera -> Display).

### Крок 1. Виділення пулу буферів (Allocator)

Процес (або окремий процес-аллокатор, наприклад, композитор Wayland/Weston або GStreamer пайплайн) використовує dma-buf heaps для виділення, скажімо, трьох буферів (для потрійної буферизації). Він відкриває `/dev/dma_heap/linux,cma`, викликає `DMA_HEAP_IOC_ALLOC` тричі і отримує три файлові дескриптори `fd1, fd2, fd3`.

### Крок 2. Передача буферів у V4L2 (Video for Linux 2)

Драйвер камери працює через фреймворк V4L2. Замість того, щоб просити V4L2 самостійно виділяти памʼять (`V4L2_MEMORY_MMAP`), програма каже V4L2 імпортувати зовнішні буфери (`V4L2_MEMORY_DMABUF`).

Додаток заповнює структуру `v4l2_buffer`:
```c
struct v4l2_buffer buf = {0};
buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
buf.memory = V4L2_MEMORY_DMABUF; /* Вказуємо, що ми передаємо dma-buf */
buf.index = 0;
buf.m.fd = fd1; /* Передаємо дескриптор з dma-buf heap */
ioctl(camera_fd, VIDIOC_QBUF, &buf); /* Ставимо буфер у чергу камери */
```
Тепер ядро (драйвер камери) імпортує `fd1`, отримує фізичні адреси і налаштовує DMA контролер камери писати кадри прямо в цей фізичний буфер.

### Крок 3. Передача буферів у DRM (Direct Rendering Manager)

Щоб вивести кадр на екран, програмі потрібно передати цей же буфер контролеру дисплея (DRM/KMS). DRM також підтримує імпорт dma-buf.

Додаток викликає `DRM_IOCTL_PRIME_FD_TO_HANDLE`, щоб перетворити `dma-buf fd` на внутрішній обʼєкт DRM (GEM handle):
```c
struct drm_prime_handle prime = {0};
prime.fd = fd1; /* Той самий fd1, що зараз містить кадр від камери */
ioctl(drm_fd, DRM_IOCTL_PRIME_FD_TO_HANDLE, &prime);
```
Після отримання GEM handle (`prime.handle`), програма додає фреймбуфер через `DRM_IOCTL_MODE_ADDFB2` і вказує дисплею відображати його (через `drmModeSetCrtc` або Atomic KMS API). Контролер дисплея починає читати пікселі з тої самої фізичної памʼяті.

### Синхронізація (Fences / DMA_BUF_IOCTL_SYNC)

Коли буфер постійно гуляє між процесором (CPU), камерою та дисплеєм, критично важливо уникати стану гонки (race conditions) і підтримувати когерентність кешу. 
1. **Синхронізація кешу CPU:** Якщо CPU звертається до даних, він повинен використовувати `ioctl(fd, DMA_BUF_IOCTL_SYNC, &sync_args)` з прапорцями `DMA_BUF_SYNC_START` перед читанням/записом і `DMA_BUF_SYNC_END` після. Це змусить ядро скинути (flush) або анулювати (invalidate) кеш CPU.
2. **Синхронізація виконання (Fences / dma_fence):** Механізм dma-buf підтримує "паркани" (fences), які дозволяють підсистемам чекати, поки інша підсистема закінчить роботу з буфером (наприклад, дисплей чекає, поки камера закінчить запис кадру). Це відбувається на рівні ядра без втручання простору користувача, що забезпечує надвисоку продуктивність.

## API розробки ядра: Як створити власну купу (Custom Heap)

Хоча стандартних куп (system, cma) часто достатньо, розробники платформ (SoC vendors) можуть реалізувати власні типи dma-buf heaps. Наприклад, для виділення памʼяті у швидкій SRAM (вбудованій статичній памʼяті на кристалі) замість повільної зовнішньої DDR памʼяті.

Щоб створити власну купу, драйвер має:
1. Визначити структуру `struct dma_heap_ops`, реалізувавши ключовий метод `allocate`.
2. Заповнити структуру `struct dma_heap_export_info`.
3. Викликати `dma_heap_add()`.

Приклад скелету коду для розробника ядра:

```c
#include <linux/dma-heap.h>
#include <linux/err.h>

static struct dma_buf *my_custom_heap_allocate(struct dma_heap *heap,
                                               unsigned long len,
                                               unsigned long fd_flags,
                                               unsigned long heap_flags)
{
    /* 1. Виділити фізичну пам'ять (наприклад, з SRAM) */
    /* 2. Створити структуру sg_table (Scatter-Gather) для фізичної пам'яті */
    /* 3. Заповнити struct dma_buf_export_info */
    /* 4. Викликати dma_buf_export() і повернути struct dma_buf * */
    
    return ERR_PTR(-ENOMEM);
}

static const struct dma_heap_ops my_custom_heap_ops = {
    .allocate = my_custom_heap_allocate,
};

static int __init my_custom_heap_init(void)
{
    struct dma_heap_export_info exp_info = {
        .name = "my-sram-heap",
        .ops = &my_custom_heap_ops,
        .priv = NULL,
    };
    struct dma_heap *heap;

    heap = dma_heap_add(&exp_info);
    if (IS_ERR(heap))
        return PTR_ERR(heap);

    return 0;
}
module_init(my_custom_heap_init);
```
Після завантаження такого модуля, у системі зʼявиться пристрій `/dev/dma_heap/my-sram-heap`.

## Підсумок

Фреймворк **dma-buf heaps** є довгоочікуваною еволюцією механізмів виділення памʼяті в Linux. Відкинувши спадщину ION з його складним і незграбним ioctl API, ядро отримало елегантний, модульний та стандартизований інтерфейс. Спираючись на загальну інфраструктуру `dma-buf`, він забезпечує універсальний шлях для реалізації ефективних пайплайнів обробки медіа та графіки з нульовим копіюванням (zero-copy), що робить його ключовим компонентом розробки сучасних вбудованих систем, інфотейнмент-систем автомобілів та мультимедійних платформ. 

Ключовим фактором успіху dma-buf heaps є те, що він пропонує простий API для користувачів — достатньо відкрити файл і зробити один `ioctl`, отримуючи на виході універсальний дескриптор, який без проблем розуміють V4L2, DRM, OpenGL/Vulkan та інші сучасні мультимедійні фреймворки Linux.
