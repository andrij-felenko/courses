# ⚙️ Віддача файлу без копіювання: сервер на epoll

Один виклик `sendfile` віддає стільки, скільки влізло в чергу сокета, — тож увесь робочий код навколо нього про те, як пам'ятати, де ми зупинилися, і як повернутися саме туди. Тут — сервер, який віддає файл на неблокуючому сокеті: облік зсуву, `EAGAIN` на повній черзі, запасний шлях, коли ядро відмовляє, і той самий цикл, переписаний на `splice`.

## Чому трирядковий цикл більше не годиться

У блокуючому циклі `read`/`write` позиція у файлі живе у змінній циклу. Це зручно рівно тому, що потік має право заснути: коли черга сокета повна, `write` просто чекає, а разом із ним чекає й уся змінна.

Неблокуючому серверові чекати заборонено — на одному потоці висять тисячі з'єднань, і сон на будь-якому з них зупинив би всі інші ([блокуючий і неблокуючий ввід-вивід](book:unix-linux/blocking-and-nonblocking) — з `O_NONBLOCK` виклик не засинає, а повертає −1 з `errno == EAGAIN`, коли зараз зробити нічого не може). Отже, замість сну — вихід із функції. А те, що жило у змінній циклу, мусить переїхати в структуру з'єднання й дожити там до наступного разу.

Уся складність далі — це складність такого переїзду. Не в `sendfile`.

## Стан з'єднання

```c
#define _GNU_SOURCE
#include <sys/sendfile.h>
#include <sys/epoll.h>
#include <unistd.h>
#include <fcntl.h>
#include <errno.h>

#define CHUNK (1 << 20)          /* стеля однієї порції, 1 МіБ */

struct conn {
    int    sock;                 /* неблокуючий, у epoll */
    int    file;                 /* відкритий звичайний файл */
    off_t  off;                  /* скільки вже віддано */
    off_t  end;                  /* розмір файлу зі stat */
    int    raw;                  /* sendfile відмовив — ідемо копією */
    int    pipe[2];              /* тільки для splice-варіанта */
    size_t in_pipe;              /* скільки байтів висить у каналі */
};

static int pump_copy(struct conn *c);
```

Двох полів — `off` і `end` — вистачає, щоб описати будь-який момент віддачі. Решта коду лише посуває `off`.

## Помпа

Одна функція, яку кличуть на кожен `EPOLLOUT`. Повертає `1` — усе віддано, `0` — черга повна, чекаємо наступної події, `−1` — з'єднання мертве.

```c
static int pump(struct conn *c)
{
    if (c->raw)
        return pump_copy(c);

    while (c->off < c->end) {
        size_t want = (size_t)(c->end - c->off);
        if (want > CHUNK)
            want = CHUNK;

        ssize_t n = sendfile(c->sock, c->file, &c->off, want);

        if (n > 0)
            continue;                     /* ядро вже посунуло c->off */
        if (n == 0)
            return -1;                    /* файл зрізали під нами */
        if (errno == EINTR)
            continue;
        if (errno == EAGAIN)
            return 0;                     /* черга повна — вихід, не сон */
        if (errno == EINVAL || errno == ENOSYS) {
            c->raw = 1;
            return pump_copy(c);
        }
        return -1;                        /* EPIPE, ECONNRESET, EIO… */
    }
    return 1;
}
```

Цикл усередині потрібен тому, що `sendfile` віддає не все замовлене: він набиває чергу сокета й повертається з тим, що влізло. Коли клієнт швидкий, за один прохід циклу відбудеться кілька викликів поспіль, і кожен віддасть чергову порцію; коли повільний — перший же виклик упреться в `EAGAIN`. Обидва випадки той самий код опрацьовує однаково.

Гілка `n == 0` виглядає зайвою, але без неї сервер зависає намертво. Нуль означає кінець вхідного файлу: хтось урізав його `truncate`, а `c->end` ми взяли зі старого `stat`. Без цієї перевірки умова `c->off < c->end` лишиться істинною назавжди, `sendfile` вертатиме нуль, і потік згорить у нескінченному циклі, забравши з собою всі інші з'єднання.

`EINTR` тут — звичайна гігієна: сигнал, що прийшов посеред виклику, не є помилкою ([перервані виклики й перезапуск](book:unix-linux/eintr-and-restart) — `EINTR` означає лише «нас перервали, спробуй ще», і повторити виклик мусить програма).

## Пастка обліку зсуву

`sendfile` посуває `*offset` **сам** — на стільки байтів, скільки віддав. Тому в коді вище після успішного виклику немає жодного `c->off += n`. Класична помилка виглядає точнісінько так:

```c
ssize_t n = sendfile(c->sock, c->file, &c->off, want);
if (n > 0)
    c->off += n;            /* ✖ подвійний облік: ядро вже додало n */
```

Наслідок підступний: половина файлу доходить до клієнта, друга половина — ні, а сервер вважає, що віддав усе. Проявиться це лише на порціях, тобто на великих файлах і повільних клієнтах — саме там, де сервер уже в бою.

Правил тут два, і плутати їх не можна. Або ви передаєте вказівник на своє поле й дозволяєте ядру ним керувати — і тоді самі його не чіпаєте. Або тримаєте зсув у локальній копії й додаєте повернене `n` вручну. Обидва способи правильні; змішані дають рівно ту помилку, що вище.

Друга частина тієї самої пастки: коли `offset` не `NULL`, **власна позиція дескриптора `file` не рухається взагалі**. Ядро читає з указаного місця й лишає позицію файлу як була. Тому будь-який запасний шлях мусить брати зсув із `c->off` явно — інакше він почне читати з нуля.

І дрібниця, яка стріляє на 32-бітних збірках: `off_t` там за замовчуванням 32-бітний, і на файлі понад 2 ГіБ виклик поверне `EOVERFLOW`. Лікується прапорцем компіляції `-D_FILE_OFFSET_BITS=64` ([підтримка великих файлів](book:unix-linux/large-file-support) — сімейство 64-бітних варіантів викликів і макрос, який перемикає на них увесь код). Незалежно від розрядності `sendfile` за один виклик передає щонайбільше 0x7ffff000 байтів — тобто файл на 4 ГіБ віддається мінімум трьома викликами навіть теоретично.

## Коли ядро відмовляє

`EINVAL` від `sendfile` — не завжди фатальна помилка. Він приходить, коли `in_fd` не вміє віддавати сторінки (канал, сокет, деякі псевдофайлові системи), коли на `out_fd` стоїть `O_APPEND`, або коли файлова система не підтримує потрібної операції. Для сервера, який роздає що завгодно, це нормальна ситуація, а не привід рвати з'єднання.

```c
static int pump_copy(struct conn *c)
{
    static char buf[64 * 1024];          /* спільний, стану не тримає */

    while (c->off < c->end) {
        ssize_t r = pread(c->file, buf, sizeof buf, c->off);
        if (r < 0) { if (errno == EINTR) continue; return -1; }
        if (r == 0) return -1;

        ssize_t sent = 0;
        while (sent < r) {
            ssize_t w = write(c->sock, buf + sent, r - sent);
            if (w < 0) {
                if (errno == EINTR) continue;
                if (errno == EAGAIN) { c->off += sent; return 0; }
                return -1;
            }
            sent += w;
        }
        c->off += r;
    }
    return 1;
}
```

Тут `pread` не випадковий: він читає із заданого місця, не чіпаючи позиції дескриптора — рівно так, як поводився `sendfile`. Завдяки цьому обидва шляхи бачать однаковий стан, і перемкнутися між ними можна посеред файлу.

Буфер спільний на всі з'єднання й статичний саме тому, що між викликами він нічого не зберігає: усе, що з нього треба, дописано в сокет до виходу з функції. Ціна відмови від копії — облік між викликами; ціна копії — навпаки, повна свобода з буфером.

Прапорець `c->raw` робить відмову остаточною. Без нього кожна наступна порція знову пробувала б `sendfile`, знову отримувала `EINVAL` і знову падала в запасний шлях — правильно, але із зайвим системним викликом на кожні 64 КіБ.

## Той самий цикл на splice

Переписати помпу на `splice` — це додати канал і рахувати не один показник, а два: скільки віддано з файлу і скільки байтів зараз висить у каналі.

```c
static int pump_splice(struct conn *c)
{
    for (;;) {
        if (c->in_pipe == 0 && c->off < c->end) {
            size_t want = (size_t)(c->end - c->off);
            if (want > 64 << 10)
                want = 64 << 10;                  /* місткість каналу */

            ssize_t n = splice(c->file, &c->off, c->pipe[1], NULL,
                               want, SPLICE_F_MORE);
            if (n < 0) { if (errno == EINTR) continue; return -1; }
            if (n == 0) return -1;
            c->in_pipe += (size_t)n;
        }

        if (c->in_pipe == 0)
            return 1;                             /* усе віддано */

        ssize_t m = splice(c->pipe[0], NULL, c->sock, NULL, c->in_pipe,
                           SPLICE_F_MORE | SPLICE_F_NONBLOCK);
        if (m < 0) {
            if (errno == EINTR) continue;
            if (errno == EAGAIN) return 0;
            return -1;
        }
        c->in_pipe -= (size_t)m;
    }
}
```

Порядок гілок тут важить більше за самі виклики. Наповнювати канал можна лише тоді, коли він порожній, а виходити з функції — лише коли він порожній **і** файл вичерпано. Порушите друге — і хвіст даних лишиться в каналі назавжди: клієнт чекатиме на кінець відповіді, якого ніхто не надішле, бо з погляду сервера все вже віддано.

Правило «наповнювати лише порожній канал» простіше за облік вільного місця, але трохи марнотратне: поки канал спорожнюється наполовину, друга половина місця простоює. Точніший варіант тримає канал повним і рахує залишок місця самотужки.

І головна ціна цього шляху: **кожне з'єднання тримає власний канал — це ще два дескриптори**: разом із сокетом і відкритим файлом уже чотири на з'єднання замість двох, тож стелю відкритих файлів доводиться піднімати вдвічі ([обмеження ресурсів](book:unix-linux/resource-limits) — `RLIMIT_NOFILE` та інші стелі, що їх ядро накладає на процес). Гірше того, є окрема стеля на пам'ять каналів одного непривілейованого користувача — `/proc/sys/fs/pipe-user-pages-soft`, типово 16384 сторінки, тобто приблизно тисяча каналів звичайної місткості. Перевищите — нові канали народжуватимуться на дві сторінки замість шістнадцяти, і продуктивність тихо просяде без жодної помилки.

## Заголовок і тіло

Справжня відповідь починається не з файлу, а із заголовка, і він лежить у пам'яті програми. Наївне рішення — записати заголовок звичайним `write`, а тіло віддати помпою — працює, але породжує окремий крихітний пакет на двісті байтів, за яким лише потім піде перший повноцінний сегмент.

Ліки — сказати ядру, що відповідь ще не скінчилася. `MSG_MORE` у `send` заголовка або `TCP_CORK` на сокеті затримують відправлення, доки не набереться повний сегмент; `SPLICE_F_MORE` у коді вище — той самий прапорець для `splice`. Пастка симетрична: затичку треба зняти після останньої порції. Забудете — хвіст відповіді пролежить у ядрі до спрацювання внутрішнього таймера на 200 мс, і кожен запит отримає рівно цю затримку на кінці.

## Дві речі, які ламають цей сервер насправді

**Холодний файл зупиняє все.** `O_NONBLOCK` не діє на звичайні файли: якщо потрібних сторінок немає в кеші, `sendfile` чекатиме на диск, і разом з ним чекатимуть усі інші з'єднання цього потоку. Мілісекунда очікування диска на одному клієнті — це мілісекунда простою для тисячі. Пом'якшують це підказкою ядру прогріти сторінки заздалегідь ([випереджальне читання](book:unix-linux/readahead) — ядро підтягує наступні сторінки файлу в кеш до того, як їх попросять, і програма може підказати обсяг наперед), а по-справжньому лікують — виносячи віддачу холодних файлів у окремі потоки або в кільце подань.

**`EPOLLOUT` треба вмикати й вимикати.** Сокет із порожньою чергою готовий до запису **завжди**. Залишите передплату ввімкненою після того, як файл віддано, — і `epoll_wait` повертатиметься негайно, знову й знову, з'їдаючи ядро процесора на порожньому місці ([select, poll, epoll](book:unix-linux/select-poll-epoll) — очікування готовності багатьох дескрипторів одним викликом; рівневий режим повідомляє про готовність доти, доки вона є). Тому передплату тримають увімкненою рівно тоді, коли є що віддавати, — і весь драйвер помпи зводиться до цього правила:

```c
static void arm(int ep, struct conn *c, int want_out)
{
    struct epoll_event ev = {
        .events   = EPOLLIN | EPOLLRDHUP | (want_out ? EPOLLOUT : 0),
        .data.ptr = c,
    };
    epoll_ctl(ep, EPOLL_CTL_MOD, c->sock, &ev);
}

for (;;) {
    int k = epoll_wait(ep, evs, MAXEV, -1);
    for (int i = 0; i < k; i++) {
        struct conn *c = evs[i].data.ptr;

        int r = pump(c);
        if (r == 0)
            arm(ep, c, 1);       /* черга повна — чекаємо місця */
        else if (r == 1)
            finish(c);           /* arm(ep, c, 0) або закриття */
        else
            drop(c);
    }
}
```

Помпа не знає ні про `epoll`, ні про решту з'єднань; драйвер не знає ні про `sendfile`, ні про канали. Уся передача без копіювання сховалася в трьох значеннях, які повертає одна функція, — і саме тому запасний шлях через `read`/`write` вставляється в цей сервер, не міняючи в ньому більше нічого.
