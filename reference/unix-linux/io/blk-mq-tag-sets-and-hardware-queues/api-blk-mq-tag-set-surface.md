# 📋 Поверхня ядра Linux: API та структури blk_mq_tag_set

Вставка розкриває програмний контракт рівня підсистеми `blk-mq` у ядрі Linux, деталізуючи конфігураційні структури даних `struct blk_mq_tag_set`, Таблицю операцій `struct blk_mq_ops`, внутрішній стан апаратного контексту `struct blk_mq_hw_ctx`, допоміжні структури передачі даних `struct blk_mq_queue_data`, функції управління життєвим циклом пулів тегів та відповідні інтерфейси моніторингу VFS (каталоги sysfs у `/sys/block/<dev>/mq/`, статистику debugfs і трасувальні точки tracepoints). Вона слугує прямою довідковою опорою для розробників драйверів блокових пристроїв та системних програмістів підсистеми вводу-виводу.

---

## 1. Головна конфігураційна структура: `struct blk_mq_tag_set`

Центральним об'єктом, який об'єднує всі апаратні черги, алгоритми виділення слотів команд та параметри контролера накопичувача, є структура `struct blk_mq_tag_set`. Вона оголошена в заголовочному файлі `<linux/blk-mq.h>`.

Нижче наведено повне визначення цієї структури з основними полями ядра:

```c
struct blk_mq_tag_set {
    /* Таблиця функцій зворотного виклику низькорівневого драйвера */
    const struct blk_mq_ops *ops;

    /* Загальна кількість апаратних диспетчерських черг (hctx) */
    unsigned int            nr_hw_queues;

    /* Максимальна глибина черги (загальна кількість тегів у наборі) */
    unsigned int            queue_depth;

    /* Кількість тегів, резервованих для високопріоритетних/системних запитів */
    unsigned int            reserved_tags;

    /* Розмір приватних даних драйвера (в байтах), що додаються до кожної struct request */
    unsigned int            cmd_size;

    /* Ідентифікатор NUMA-вузла для оптимального виділення пам'яті під структури */
    int                     numa_node;

    /* Таймаут виконання операцій вводу-виводу у системних тиках (jiffies) */
    unsigned int            timeout;

    /* Бітові прапори конфігурації поведінки черги (BLK_MQ_F_*) */
    unsigned int            flags;

    /* Неструктурований вказівник на приватну контекстну структуру драйвера */
    void                   *driver_data;

    /* Двовимірний масив пулів тегів для кожної апаратної черги */
    struct blk_mq_tags    **tags;

    /* Масиви відображення процесорних ядер на апаратні черги (для різних типів I/O) */
    struct blk_mq_queue_map map[HCTX_MAX_TYPES];

    /* Кількість активних типів черг у масиві map (Default, Read, Poll) */
    unsigned int            nr_maps;

    /* Зв'язаний список усіх блокових черг (request_queue), які ділять цей tag_set */
    struct list_head        tag_list;

    /* М'ютекс для синхронізації змін у списку tag_list */
    struct mutex            tag_list_lock;
};
```

### Деталізація полів `blk_mq_tag_set`

1. **`ops`**: Вказівник на таблицю колбеків. Драйвер зобов'язаний реалізувати як мінімум метод `queue_rq` для відправки команд у фізичний накопичувач.
2. **`nr_hw_queues`**: Визначає кількість апаратних контекстів `blk_mq_hw_ctx`. Наприклад, для NVMe-накопичувача це значення зазвичай відповідає кількості переривань MSI-X або кількості доступних процесорних ядер.
3. **`queue_depth`**: Фізична межа кількості одночасних команд, які контролер здатний утримувати в станції обробки. Визначає розмір внутрішніх бітових карт аллокатора тегів.
4. **`reserved_tags`**: Захисна зона тегів. Ці слоти виділяються лише під службові операції (скидання кешу `flush`, скидання контролера при збоях, виконання passthrough `ioctl`). Без reserved-тегів при повному заповненні черги звичайними запитами читання/запису системні команди скидання кешу потрапляють у взаємне блокування (deadlock).
5. **`cmd_size`**: Аллокатор `blk-mq` виділяє пам'ять під кожну структуру `struct request` разом із додатковим "хвостом" (tail buffer) розміром `cmd_size`. Драйвер зберігає там свої приватні структури (наприклад, NVMe command dword, розсіяні масиви SGL або DMA-дескриптори) без необхідності додаткових викликів `kmalloc`.
6. **`map[HCTX_MAX_TYPES]`**: Ядро Linux підтримує до трьох різних мап відображення CPU на `hctx`:
   - `HCTX_TYPE_DEFAULT`: Стандартні черги для змішаного читання та запису.
   - `HCTX_TYPE_READ`: Окремі черги, оптимізовані виключно під операції читання (зменшують конфлікти блокувань при паралельних записах).
   - `HCTX_TYPE_POLL`: Окремі апаратні черги без обробників переривань, призначені для підсистеми асинхронного опитування (I/O polling / `io_uring`).

## 2. Прапори конфігурації поведінки: `flags`

Поле `flags` у структурі `blk_mq_tag_set` керує внутрішньою логікою обробки запитів на рівні шару `blk-mq`:

- **`BLK_MQ_F_SHOULD_MERGE`**: Вмикає програмну перевірку на злиття суміжних `bio` (bio merging) у програмній черзі `blk_mq_ctx`. Якщо прапор вимкнено, кожен `bio` миттєво перетворюється на окремий `struct request`.
- **`BLK_MQ_F_TAG_QUEUE_SHARED`**: Вказує ядру, що декілька незалежних черг пристроїв (`request_queue`) ділять один і той самий пул тегів `blk_mq_tag_set`. Це активує динамічне зважування та обмеження тегів між пристроями, запобігаючи ситуації, коли один диск захоплює 100% слотів спільного контролера.
- **`BLK_MQ_F_BLOCKING`**: Сигналізує, що колбек драйвера `queue_rq()` має право переходити у стан сну (наприклад, викликати м'ютекси, чекати на затискачах або виконувати блокуючі виклики пам'яті). За замовчуванням `queue_rq()` виконується в атомному контексті з вимкненими перериваннями або під rcu-блокуванням.
- **`BLK_MQ_F_NO_SCHED`**: Забороняє підключення зовнішніх I/O планувальників (таких як `kyber` або `bfq`) до даної черги. Використовується для пристроїв, де планування на рівні ядра лишь створює накладні витрати (наприклад, ramdisk або zram).
- **`BLK_MQ_F_ALLOC_POLICY_START_BIT`**: Змінює стратегію пошуку вільних тегів в аллокаторі з круглого (round-robin) на пошук з першого вільного біта (first-fit).

## 3. Таблиця операцій драйвера: `struct blk_mq_ops`

Драйвер блокового пристрою реєструє свій функціонал через систему зворотних викликів `struct blk_mq_ops`:

```c
struct blk_mq_ops {
    /* Обов'язковий метод: передача запиту безпосередньо у контролер пристрою */
    blk_status_t (*queue_rq)(struct blk_mq_hw_ctx *hctx,
                             const struct blk_mq_queue_data *bd);

    /* Необов'язковий метод: сповіщення про завершення пакетної відправки (batch) */
    void (*commit_rqs)(struct blk_mq_hw_ctx *hctx);

    /* Необов'язковий метод: обробка завершення запиту на вищому рівні */
    void (*complete)(struct request *rq);

    /* Метод обробки таймауту операції (коли пристрій не відповів вчасно) */
    enum blk_eh_timer_return (*timeout)(struct request *rq);

    /* Конструктор та деструктор апаратного контексту hctx */
    int (*init_hctx)(struct blk_mq_hw_ctx *hctx, void *data, unsigned int idx);
    void (*exit_hctx)(struct blk_mq_hw_ctx *hctx, unsigned int idx);

    /* Конструктор та деструктор приватних даних у структурі request */
    int (*init_request)(struct blk_mq_tag_set *set, struct request *rq,
                        unsigned int hctx_idx, unsigned int numa_node);
    void (*exit_request)(struct blk_mq_tag_set *set, struct request *rq,
                         unsigned int hctx_idx);

    /* Колбек для побудови топології мапінгу CPU -> hctx */
    int (*map_queues)(struct blk_mq_tag_set *set);

    /* Метод опитування стану пристрою (для черг HCTX_TYPE_POLL) */
    int (*poll)(struct blk_mq_hw_ctx *hctx, struct io_comp_batch *iob);
};
```

### Структура `struct blk_mq_queue_data`

При виклику `queue_rq()` ядро передає драйверу об'єкт `struct blk_mq_queue_data`:

```c
struct blk_mq_queue_data {
    struct request *rq;   /* Вказівник на підготовлений запит із присвоєним тегом */
    bool last;            /* Прапор: true, якщо це останній запит у поточному батчі */
};
```

Прапор `last` дозволяє драйверу оптимізувати відправку: якщо `last == false`, драйвер записує команду в PCIe-кільце Submission Queue, але відкладає оновлення MMIO-регістра `doorbell`. Лише коли приходить запит із `last == true` (або викликається `commit_rqs()`), драйвер виконує один виклик `doorbell`, відправляючи весь пакет команд за одну операцію на шині PCIe.

### Коди повернення `blk_status_t` у виклику `queue_rq`

Коли шар `blk-mq` викликає `ops->queue_rq()`, драйвер намагається записати команду в апаратне кільце (Submission Queue). Залежно від стану накопичувача, метод повертає один із наступних статусів:

- **`BLK_STS_OK`**: Команду успішно прийнято пристроєм.
- **`BLK_STS_RESOURCE`**: У драйвері або апаратному пристрої тимчасово закінчилися внутрішні ресурси (наприклад, заповнено внутрішнє кільце кольця PCIe). Шар `blk-mq` призупиняє відправку запитів із цієї `hctx` і ставить запит назад у чергу диспетчеризації (`dispatch list`).
- **`BLK_STS_DEV_RESOURCE`**: Спеціалізований варіант `BLK_STS_RESOURCE`, який вказує, що ресурс вичерпано саме на конкретному цільовому пристрої (а не на рівні глобального контролера). Це дозволяє `blk-mq` продовжувати відправку запитів на інші диски того самого tag_set.
- **`BLK_STS_IOERR`**: Критична апаратна помилка шини або контролера. Запит негайно завершується з помилкою вводу-виводу для користувацького процесу.
- **`BLK_STS_AGAIN`**: Тимчасова відмова, яка вимагає повторної спроби відправки через коротку затримку.

## 4. Контекст апаратної черги: `struct blk_mq_hw_ctx`

Кожна апаратна диспетчерська черга представлена в ядрі структурою `struct blk_mq_hw_ctx` (скорочено `hctx`). Вона утримує стан диспетчеризації для групи прив'язаних CPU:

```c
struct blk_mq_hw_ctx {
    /* Окремі спінлоки для захисту локального списку диспетчеризації */
    spinlock_t              lock;

    /* Список запитів, готові до передачі драйверу (dispatch list) */
    struct list_head        dispatch;

    /* Кількість послідовних невдалих спроб відправки через BLK_STS_RESOURCE */
    unsigned long           dispatch_busy;

    /* Маска логічних CPU, які прив'язані до цієї hctx */
    cpumask_var_t           cpumask;

    /* Вказівник на пул тегів, що використовується цією hctx */
    struct blk_mq_tags     *tags;

    /* Вказівник на I/O планувальник, підключений до цієї апаратної черги */
    struct blk_mq_sched_data *sched_data;

    /* Вказівник на батьківську чергу пристрою request_queue */
    struct request_queue   *queue;

    /* Індекс цієї hctx у загальному масиві пристрою (від 0 до nr_hw_queues-1) */
    unsigned int            queue_num;

    /* Прапор стану черги (наприклад, HCTX_S_STOPPED) */
    unsigned long           state;

    /* Відкладена робота kworker для фонової відправки запитів */
    struct delayed_work     run_work;
};
```

## 5. Функції управління життєвим циклом в ядрі

Драйвер блокового пристрою використовує наступний базовий набор функцій ядра для реєстрації та управління об'єктом `blk_mq_tag_set`:

```c
/* 1. Виділення та ініціалізація внутрішніх бітових карт sbitmap і масивів tags */
int blk_mq_alloc_tag_set(struct blk_mq_tag_set *set);

/* 2. Звільнення всіх виділених ресурсів та таблиць мапінгу */
void blk_mq_free_tag_set(struct blk_mq_tag_set *set);

/* 3. Створення та прив'язка черги request_queue на основі готового tag_set */
struct request_queue *blk_mq_init_queue(struct blk_mq_tag_set *set);

/* 4. Динамічна зміна кількості апаратних черг (наприклад, при зміні векторів MSI-X) */
int blk_mq_update_nr_hw_queues(struct blk_mq_tag_set *set, int nr_hw_queues);

/* 5. Динамічна зміна глибини черги пристрою під тиском навантаження */
int blk_mq_tag_resize(struct blk_mq_tag_set *set, unsigned int new_depth);

/* 6. Заморожування та розморожування черги при зміні конфігурації */
void blk_mq_freeze_queue(struct request_queue *q);
void blk_mq_unfreeze_queue(struct request_queue *q);

/* 7. Зупинка та відновлення диспетчеризації апаратних черг */
void blk_mq_stop_hw_queues(struct request_queue *q);
void blk_mq_start_hw_queues(struct request_queue *q);
```

Функція `blk_mq_freeze_queue()` призупиняє надходження нових `bio`, чекає на завершення всіх команд у польоті (*in-flight*) та гарантує, що жоден потік не використовує теги під час перебудови мапінгу ядра.

## 6. Інтерфейси моніторингу VFS, sysfs та debugfs

Підсистема `blk-mq` надає розробникам та адміністраторам прозорий вигляд внутрішнього стану черг через файлову систему `sysfs` за шляхом `/sys/block/<dev>/mq/`.

### Дерево псевдофайлів `/sys/block/<dev>/mq/`

```text
/sys/block/nvme0n1/mq/
├── 0/                      # Каталог апаратної черги hctx 0
│   ├── cpu0 -> ../../../   # Символьне посилання на прив'язане процесорне ядро
│   ├── cpu_list            # Текстовий список усіх ядер, мапованих на цю hctx ("0, 1")
│   ├── dispatch            # Список запитів у локальному dispatch list
│   ├── dispatch_busy       # Лічильник відмов драйвера через BLK_STS_RESOURCE
│   ├── nr_reserved_tags    # Кількість виділених резервованих тегів
│   ├── nr_tags             # Загальна кількість доступних тегів у даній hctx
│   ├── queued              # Кількість запитів, надісланих у цю hctx з моменту завантаження
│   ├── run                 # Лічильник запусків функції відправки blk_mq_run_hw_queue
│   ├── active              # Кількість активних команд у польоті (in-flight)
│   └── type                # Тип черги (default, read, poll)
├── 1/                      # Каталог апаратної черги hctx 1
└── sched/                  # Налаштування та статистика активного I/O планувальника
```

### Моніторинг через `debugfs` та `tracepoints`

Детальний стан бітових карт `sbitmap` та черг очікування виноситься у `debugfs`:
- `/sys/kernel/debug/block/<dev>/hctxN/tags`: Показує сирий вміст масивів `sbitmap`, поточні значення `alloc_hint` та активні біти зайнятих тегів.
- `/sys/kernel/debug/block/<dev>/hctxN/sched_tags`: Показує стан тегів на рівні I/O планувальника.

Ядро експортує наступні стандартні точки трасування (tracepoints) для інструменту `ftrace` та `eBPF`:
- `trace_block_rq_issue`: Фіксує момент передачі запиту з `hctx` у драйвер `queue_rq()`.
- `trace_block_rq_complete`: Фіксує момент обробки переривання завершення та повернення тегу.
- `trace_blk_mq_sbitmap_wait`: Фіксує події вичерпання тегів, коли процес переходить у стан сну в очікуванні вільного слота.
