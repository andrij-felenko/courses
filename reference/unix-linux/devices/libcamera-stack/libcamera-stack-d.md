Коли оптичний сенсор Sony IMX477 на платі Raspberry Pi чи промисловому комп'ютері захоплює 12-мегапіксельний кадр із частотою 60 кадрів/с, по чотирьох диференційних лініях шини MIPI CSI-2 у процесор надходить потік сирих даних (RAW12) зі швидкістю понад 6 Гбіт/с. На відміну від стандартної USB-вебкамери, де вбудований у пластиковий корпус чип віддає готовий стиснений потік `YUYV` або `MJPEG`, у сенсорі вбудованої камери немає жодного процесора обробки зображень (ISP, від англ. *Image Signal Processor*, від лат. *processus* — просування). Світлочутлива кремнієва матриця генерує лише електричні потенціали, вкриті мозаїчним колірним фільтром Байєра (Bayer filter), а зміщення оптичних лінз автофокусу виконується окремою котушкою Voice Coil Motor (VCM), що керується через повільну шину I2C.

Спроба керувати таким складним комплексом через традиційний монолітний інтерфейс Video4Linux2 (`/dev/video0`) зазнає повного краху: ядро Linux не може одночасно конфігурувати розгалужену топологію шин, застосовувати закриті математичні алгоритми відновлення кольору та синхронізувати час експозиції з кожним окремим буфером кадру. Щоб розв'язати цю системну кризу, у просторі користувача було створено **libcamera** — відкритий програмний стек нового покоління, що об'єднує низькорівневі інтерфейси ядра Media Controller, V4L2 Subdev та Media Request у цілісну модель керування на основі покрокових запитів (Request-based API).

## 1. Проблема вбудованих камер: UVC проти комплексного конвеєра ISP

Щоб зрозуміти причини появи libcamera, необхідно зіставити два діаметрально протилежних класи оптичних пристроїв у світі Linux: прості камери класу USB Video Class (UVC) та вбудовані камери систем на кристалі (SoC).

![Порівняння архітектури UVC та вбудованої CSI-2 камери](/reference/unix-linux/devices/libcamera-stack/img/uvc-vs-embedded-pipeline.svg)
*Рис. 1. Архітектурне порівняння: інтегрований ISP у веб-камері UVC проти розподіленого апаратного конвеєра вбудованої камери з програмним керуванням 3A.*

### Анатомія UVC-камери

У звичайній USB-вебкамері оптичний сенсор, сигнальний процесор і контролер інтерфейсу зібрані в єдиному апаратному модулі. Усередині мікросхеми ISP жорстко зашито мікропрограму (firmware), яка самостійно здійснює:
- безперервний вимір освітленості сцени та зміну витримки матриці (автоекспозиція, AE — *Auto Exposure*);
- аналіз колірної температури та розрахунок балансу білого (AWB — *Auto White Balance*);
- дебайєризацію (перетворення сирої сітки Bayer у повноколірний простір RGB або YUV);
- апаратне стиснення в JPEG або передачу нестиснених потоків `YUYV 4:2:2`.

Драйвер ядра Linux `uvcvideo` сприймає таку камеру як "чорну скриньку". Застосунок просто відкриває `/dev/video0`, вибирає формат через системний виклик `ioctl(VIDIOC_S_FMT)` і циклічно забирає готові пікселі через чергу буферів Videobuf2 (`VIDIOC_DQBUF`).

### Анатомія вбудованої камери (MIPI CSI-2 + SoC ISP)

У сучасних мобільних платформах, автомобільних автопілотах, промислових роботах і платах для розробників (Raspberry Pi, Intel IPU3/IPU4, NXP i.MX8, Rockchip RK3588, Qualcomm Snapdragon) камера влаштована принципово інакше:
1. **Оптичний модуль (Sensor Module):** містить виключно кремнієву матрицю (наприклад, Sony IMX219, IMX477, Omnivision OV5647). Зв'язок із SoC здійснюється двома роздільними шинами:
   - **I2C/SPI:** низькошвидкісна шина керування. Через неї передаються значення аналогового підсилення (Analogue Gain), часу інтеграції фотодіодів (Shutter Time/ExposureTime) та керування драйвером лінзи фокусування (VCM Actuator).
   - **MIPI CSI-2:** високошвидкісна серійна шина передачі даних (D-PHY або C-PHY), якою передаються пакети сирих пікселів RAW8, RAW10, RAW12 або RAW14. На фізичному рівні потік упакований у короткі пакети синхронізації (початок/кінець кадру Frame Start/End) та довгі пакети корисного навантаження з ідентифікаторами віртуальних каналів (Virtual Channels VC0–VC3) і перевіркою контрольної суми CRC.
2. **Апаратний блок ISP всередині SoC:** процесор обробки сигналів є частиною центрального процесора. Він складається з десятка послідовних конвеєрних блоків:
   - **Black Level Correction (BLC):** віднімання темнового струму фотодіодів (фіксованого зміщення нульового рівня сигналу). Навіть у повній темряві через тепловий рух електронів фотодіод генерує паразитна напруга, яку необхідно відняти від кожного відліку.
   - **Defect Pixel Correction (DPC):** фільтрація та інтерполяція битих або "гарячих" пікселів матриці, які постійно видають максимальну яскравість.
   - **Lens Shading Correction (LSC):** оптична корекція віньєтування (падіння яскравості на краях лінзи) та хроматичних аберацій за допомогою двовимірних сіток поправочних коефіцієнтів для кожного колірного каналу окремо.
   - **Demosaicing (Дебайєризація, від фр. *mosaïque*):** відновлення відсутніх колірних компонентів для кожного пікселя. Оскільки кожен фотодіод матриці Bayer накритий червоним, зеленим або синім світлофільтром (шаблон RGGB, BGGR, GBRG), алгоритм відновлює повноцінний трикомпонентний вектор `[R, G, B]` за допомогою адаптивних градієнтних інтерполяцій (наприклад, алгоритмів Malvar-He-Cutler або AHD).
   - **Color Correction Matrix (CCM):** множення вектора `[R, G, B]` на калібрувальну матрицю 3×3 для точної корекції спектральної чутливості кремнію під сприйняття людського ока в поточних умовах освітлення.
   - **3D Noise Reduction (3DNR):** часове та просторове фільтрування шумів на основі зваженого порівняння поточного кадру з попередніми кадрами з буфера оперативної пам'яті.
   - **Tone Mapping / Gamma Correction:** нелінійне перетворення логарифмічної або лінійної динамічної шкали яскравості сенсора у формат дисплея (sRGB, Rec.709 або HDR PQ/HLG).
   - **Resizer / Scaler:** зміна розміру зображення та паралельне формування кількох виходів (наприклад, повнорозмірний потік для відеозапису та зменшений потік для екранного видошукача або алгоритмів детекції нейромережами).
3. **Генератор апаратної статистики 3A:** блок ISP під час проходження пікселів обчислює гістограми яскравості, сітку середніх колірних сум і коефіцієнти просторового градієнта для автофокусу, записуючи ці масиви в окремий буфер оперативної пам'яті.

Апаратний ISP не знає, як інтерпретувати цю статистику — він лише виконує матричну математику над пікселями. Усі рішення щодо зміни витримки, зміщення лінзи чи налаштування матриці балансу білого мають прийматися програмним забезпеченням.

## 2. Межі ядра Linux: Media Controller, V4L2 Subdev та неможливість монолітного керування

Чому ядро Linux не може реалізувати повний цикл керування такою камерою самостійно? Відповідь полягає в архітектурній філософії Unix: ядро надає механізми доступу до обладнання, але не реалізує складну прикладну політику обробки даних.

### Анатомія Media Controller (`/dev/mediaX`) та V4L2 Subdevices (`/dev/v4l-subdevX`)

Для представлення складної топології вбудованих камер ядро Linux використовує підсистему Media Controller. Апаратний тракт моделюється у вигляді орієнтованого графа:
- **Entities (Сутності):** апаратні функціональні блоки (`struct media_entity`). Наприклад, сутність сенсора камери, сутність приймача MIPI CSI-2, сутність блока ISP, сутність апаратного скалера та кінцеві вузли DMA захоплення.
- **Pads (Контактні майданчики):** точки входу (`MEDIA_PAD_FL_SINK`) та виходу (`MEDIA_PAD_FL_SOURCE`) потоків даних на кожній сутності.
- **Links (Зв'язки):** логічні або апаратні канали передачі даних між майданчиками (`struct media_link`), які можна динамічно активувати чи вимикати.

Кожен проміжний апаратний блок у цьому графі виноситься в простір користувача як символьний пристрій субпристрою V4L2: `/dev/v4l-subdev0`, `/dev/v4l-subdev1` тощо. Налаштування форматів пікселів і кадрування на проміжних етапах виконується за допомогою pad-level викликів ioctl:

:::tabs
```c
/* Налаштування формату на вихідному контакті сенсора через субпристрій V4L2 */
struct v4l2_subdev_format fmt;
memset(&fmt, 0, sizeof(fmt));
fmt.pad = 0; /* Вихідний Pad 0 сенсора */
fmt.which = V4L2_SUBDEV_FORMAT_ACTIVE;
fmt.format.width = 1920;
fmt.format.height = 1080;
fmt.format.code = MEDIA_BUS_FMT_SRGGB10_1X10; /* RAW10 Bayer */

if (ioctl(subdev_fd, VIDIOC_SUBDEV_S_FMT, &fmt) < 0) {
    perror("VIDIOC_SUBDEV_S_FMT failed");
}
```
```cpp
// Ідіоматичний еквівалент на C++ для налаштування формату субпристрою
#include <linux/v4l2-subdev.h>
#include <sys/ioctl.h>
#include <system_error>
#include <cstring>

void configureSubdevFormat(int subdevFd, uint32_t pad, uint32_t width, uint32_t height, uint32_t mbusCode) {
    v4l2_subdev_format fmt{};
    fmt.pad = pad;
    fmt.which = V4L2_SUBDEV_FORMAT_ACTIVE;
    fmt.format.width = width;
    fmt.format.height = height;
    fmt.format.code = mbusCode;

    if (::ioctl(subdevFd, VIDIOC_SUBDEV_S_FMT, &fmt) < 0) {
        throw std::system_error(errno, std::generic_category(), "Помилка VIDIOC_SUBDEV_S_FMT");
    }
}
```

### Проблема синхронізації параметрів та закритих алгоритмів

У класичному V4L2 зміна параметрів камери виконувалася викликом `ioctl(VIDIOC_S_CTRL)`. Однак цей виклик є асинхронним відносно черги відеокадрів. Сенсор камери на шині I2C має власну внутрішню затримку застосування параметрів (pipeline latency): наприклад, нове значення часу витримки, записане в регістри сенсора під час кадру `N`, почне діяти лише на кадрі `N + 2`.

Якщо програма паралельно змінює налаштування ISP (матрицю CCM чи коефіцієнти дебайєризатора), виникає десинхронізація: блок ISP застосує нові параметри до кадру `N + 1`, який насправді ще експонувався за старими правилами. Зображення зазнає різких колірних спалахів і артефактів експозиції.

Ба більше, алгоритми 3A та калібрувальні таблиці оптичних модулів (tuning files) містять сотні тисяч рядків математики з рухомою комою (floating point), оптимізовані алгоритми машинного навчання та закриті комерційні секрети виробників. Завантажувати такий код у простір ядра Linux категорично заборонено політикою безпеки та ліцензією GPLv2 ядра.

Ядро Linux вирішило апаратну частину проблеми, впровадивши **Media Request API** (`MEDIA_IOC_REQUEST_ALLOC`). Цей інтерфейс дозволяє створювати в ядрі атомарні файлові дескриптори запитів `request_fd`, до яких прив'язуються конкретні буфери кадру `struct v4l2_buffer` із прапорцем `V4L2_BUF_FLAG_REQUEST_FD` та набір керуючих параметрів `VIDIOC_S_EXT_CTRLS`. Проте все завдання побудови черги запитів, сканування медіаграфа, синхронізації та обчислення 3A лягло на простір користувача.

Детальний перебіг становлення системної підсистеми камер від перших плат Video4Linux до відкриття проєкту libcamera викладено в історичному нарисі [📜 Від монолітного V4L2 та Android CameraHAL до libcamera](book:unix-linux/libcamera-stack/hist-complex-cameras-and-libcamera.md).

## 3. Архітектура бібліотеки libcamera: шари, сутності та інтерфейси

Бібліотека **libcamera** створена для того, щоб повністю приховати від прикладного програміста складність роботи з десятками файлів `/dev/v4l-subdevX`, ручне з'єднання майданчиків Media Controller і низькорівневий обмін буферами.

### Ієрархія публічного C++ API

Публічний інтерфейс libcamera спроєктовано за сучасними стандартами C++17 з акцентом на безпеку пам'яті (RAII, розумні вказівники `std::unique_ptr` та `std::shared_ptr`) і механізми сигналів/слотів (`libcamera::Signal`):

1. **`CameraManager`:** кореневий синглтон або менеджер екземпляра. Відповідає за виявлення медіапристроїв у системі (`/dev/media0..N`), перерахування підключених сенсорів і створення об'єктів камер.
2. **`Camera`:** абстракція фізичної або логічної камери. Забезпечує ексклюзивне захоплення пристрою (`acquire()`), конфігурацію, запуск/зупинку конвеєра та обробку сигналів завершення запитів (`requestCompleted`).
3. **`CameraConfiguration` та `StreamConfiguration`:** набір об'єктів для узгодження параметрів. Застосунок описує бажані ролі потоків (`StreamRole::Viewfinder`, `StreamRole::StillCapture`), після чого викликає `validate()`. Бібліотека автоматично підбирає найближчі підтримувані роздільні здатності та формати, враховуючи обмеження ISP процесора.
4. **`Stream`:** логічний потік даних усередині камери. Дозволяє одній камері генерувати одночасно кілька виходів із різними форматами (наприклад, потік NV12 1080p для нейромережі та потік BGR888 4K для запису).
5. **`Request`:** атомарна одиниця захоплення кадру. Містить набір буферів для кожного активного потоку, перелік вхідних налаштувань `ControlList` і вихідні метадані.
6. **`FrameBuffer`:** представлення фізичного кадру в пам'яті через файлові дескриптори DMA-BUF.

### Роль Pipeline Handler: Драйвери процесорів у просторі користувача

Серцем внутрішньої модульності libcamera є **Pipeline Handlers** (обробники конвеєрів, від англ. *pipeline* — конвеєр). Оскільки кожен виробник процесорів (Broadcom, Intel, Rockchip, NXP, Qualcomm) має власну унікальну топологію блоків ISP і специфіку регістрів, Pipeline Handler виконує роль апаратного драйвера простору користувача для конкретної SoC.

Існують спеціалізовані реалізації Pipeline Handler:
- `PipelineHandlerRPi` — для процесорів Broadcom BCM2835/BCM2711 та чипа ISP Raspberry Pi 5. Керує драйвером приймача Unicam і блоком bcm2835-isp.
- `PipelineHandlerIPU3` — для систем з інтегрованими ISP Intel IPU3 (ноутбуки Microsoft Surface, Dell тощо). Керує вхідним блоком CIO2 та обчислювальним блоком ImgU.
- `PipelineHandlerRkISP1` — для процесорів Rockchip RK3399, RK3568, RK3588, що використовують апаратний ISP rkisp1.
- `PipelineHandlerImx8` — для процесорів NXP i.MX8 з блоками захоплення ISI та апаратними модулями ISP.
- `PipelineHandlerSimple` — універсальний спрощений обробник для сенсорів із прямим підключенням до DMA без складного ISP.
- `PipelineHandlerUVC` — обробник для стандартних USB-камер, що забезпечує єдиний API для всієї оптики в системі.

Кожен Pipeline Handler реалізує строгий внутрішній інтерфейс:
- `match(DeviceEnumerator *enumerator)`: перевіряє наявність у системі відповідного графа Media Controller. Якщо топологія та назви сутностей збігаються, обробник реєструє нові екземпляри `Camera`.
- `configure(Camera *camera, CameraConfiguration *config)`: відкриває потрібні `/dev/v4l-subdevX`, налаштовує медіазв'язки між майданчиками через ioctl `MEDIA_IOC_SETUP_LINK` і програмує формати пікселів на кожному кроці конвеєра.
- `allocateBuffers(Camera *camera, Stream *stream)`: створює буфери Videobuf2 на відеовузлах ядра за допомогою системного виклику `VIDIOC_REQBUFS`.
- `queueRequestDevice(Camera *camera, Request *request)`: перетворює об'єкт `libcamera::Request` у виклики `MEDIA_IOC_REQUEST_ALLOC` ядра Linux, додає буфери у черги V4L2 і передає запити на обробку в модуль IPA.

Повний довідник класів ядра, перелік елементів керування та статичних властивостей наведено у вичерпному посібнику [📋 Довідник класів, елементів керування та IPA-інтерфейсів](book:unix-linux/libcamera-stack/api-libcamera-core.md).

## 4. Модулі Image Processing Algorithm (IPA) та безпека пісочниць

Алгоритми 3A (Auto Exposure, Auto White Balance, Auto Focus) є критично важливими для отримання якісного зображення. У libcamera вони відокремлені від драйверів апаратури та виносяться в спеціальні модулі **IPA** (Image Processing Algorithm).

```
 ┌─────────────────────────────────────────────────────────────┐
 │                      libcamera Core                         │
 │                                                             │
 │   ┌──────────────────────┐         ┌────────────────────┐   │
 │   │   Pipeline Handler   │         │  EventDispatcher   │   │
 │   └──────────┬───────────┘         └────────────────────┘   │
 └──────────────┼──────────────────────────────────────────────┘
                │ IPC (Unix Domain Socket + memfd)
                ▼
 ┌─────────────────────────────────────────────────────────────┐
 │            IPA Proxy / Sandbox (seccomp jail)               │
 │                                                             │
 │   ┌──────────────────┐  ┌──────────────────┐  ┌─────────┐   │
 │   │ Auto Exposure AE │  │ Auto White Bal.  │  │ Auto    │   │
 │   │ & Analogue Gain  │  │ & CCM Matrix     │  │ Focus   │   │
 │   └──────────────────┘  └──────────────────┘  └─────────┘   │
 └─────────────────────────────────────────────────────────────┘
```

### Замикання контуру зворотного зв'язку 3A

Робота IPA організована у вигляді циклічного автомата зворотного зв'язку:
1. **Збір статистики:** Апаратний блок ISP під час обробки кадру записує в окремий буфер пам'яті (DMA-BUF) статистичні дані: 256-бінову гістограму яскравості, зональні інтеграли червоного, зеленого та синього каналів за сіткою 32×32, а також оцінку високочастотних просторових градієнтів для контрастного фокусування.
2. **Передача в IPA:** Pipeline Handler перехоплює завершення кадру і викликає метод IPA `processStatsBuffer()`.
3. **Обчислення нових параметрів:**
   - Алгоритм **AE** порівнює поточну яскравість сцени з цільовою та розраховує нові значення експозиції (`ExposureTime`) і підсилення матриці (`AnalogueGain`).
   - Алгоритм **AWB** (за методом Gray World або White Patch) розраховує поправочні коефіцієнти для колірних каналів `R_gain` і `B_gain` та заповнює матрицю колірної корекції (CCM).
   - Алгоритм **AF** аналізує різкість контрастних меж і формує нову координату зсуву лінзи для драйвера VCM.
4. **Застосування:** Розраховані параметри повертаються до Pipeline Handler і закладаються в об'єкт `Request` для кадру `N + 2`, гарантуючи безперервну динамічну адаптацію камери.

### Ізоляція закритих двійкових блобів через seccomp-пісочниці

Багато виробників кремнію та оптичних модулів відмовляються відкривати вихідний код своїх алгоритмів 3A, поширюючи їх у вигляді закритих динамічних бібліотек. Якщо завантажити пропрієтарний `.so` файл безпосередньо в адресний простір застосунку, виникають серйозні загрози:
- Падіння через помилку або витік пам'яті в закритому коді призведе до аварійного завершення всієї програми.
- Закритий бінарний код може здійснювати несанкціонований доступ до файлової системи, пам'яті інших потоків або мережевих сокетів.

Для подолання цієї загрози libcamera реалізує архітектуру **IPA Sandboxing** (ізоляція пісочниць, від англ. *sandbox* — пісочниця):
- Інтерфейс модуля IPA формально описується за допомогою мови опису інтерфейсів Mojo IDL.
- Спеціальний генератор коду створює шар IPC-проксі (`ipa-proxy`).
- Під час ініціалізації камери libcamera створює окремий дочірній процес через виклик `fork() / execve()`.
- У дочірньому процесі активується жорсткий фільтр системних викликів ядра **seccomp** (Secure Computing Mode): процесу повністю забороняються виклики відкриття файлів (`open`), створення мережевих сокетів (`socket`), міжпроцесної сигналізації тощо. Дозволеними залишаються лише читання та запис у надані дескриптори IPC.
- Передача структур налаштувань виконується через сокети Unix Domain (`AF_UNIX`), а масиви статистики передаються без копіювання через дескриптори анонімної спільної пам'яті `memfd_create` або `dma-buf`.

## 5. Модель керування запитами (Request-based API) та життєвий цикл кадрів

На відміну від застарілих інтерфейсів захоплення, де програма оперує лише сирими буферами, libcamera будує всю роботу навколо концепції **Запиту (Request)**.

![Життєвий цикл об'єкта Request](/reference/unix-linux/devices/libcamera-stack/img/request-buffer-lifecycle.svg)
*Рис. 3. Життєвий цикл об'єкта Request: конфігурація буферів dma-buf, динамічне застосування ControlList, обробка в ядрі та повернення метаданих.*

### Структура об'єкта Request

Об'єкт `libcamera::Request` є контейнером, що інкапсулює:
1. **Буфери потоків (`FrameBuffer`):** для кожного сконфігурованого потоку `Stream` до запиту додається відповідний буфер пам'яті. Якщо камера налаштована на два потоки (Viewfinder та StillCapture), запит об'єднує два буфери різної роздільної здатності.
2. **Вхідні елементи керування (`ControlList`):** динамічні параметри, які повинні набути чинності саме під час експонування та обробки цього кадру. Наприклад, точний час затвора в мікросекундах `controls::ExposureTime`, аналогове підсилення `controls::AnalogueGain` або координати кадрування `controls::ScalerCrop`.
3. **Вихідні метадані (`Metadata`):** параметри, зафіксовані апаратурою та модулем IPA за фактом захоплення кадру (фактична експозиція, колірна температура, статус фокусу, апаратні часові мітки `timestamp` від таймера `CLOCK_BOOTTIME`).

### Покроковий життєвий цикл кадру

Життєвий цикл запиту складається з чотирьох строго регламентованих фаз:

1. **Фаза створення та наповнення:**
   Застосунок створює об'єкт через `camera->createRequest()`, прив'язує буфери викликом `request->addBuffer(stream, buffer)` та заповнює налаштування:
   ```cpp
   request->controls().set(controls::ExposureTime, 20000); // 20 мс
   request->controls().set(controls::AnalogueGain, 2.0f);   // +6 дБ
   ```
2. **Фаза постановки в чергу:**
   Виклик `camera->queueRequest(request.get())` передає об'єкт до Pipeline Handler. Обробник виділяє в ядрі дескриптор `request_fd` через ioctl `MEDIA_IOC_REQUEST_ALLOC`, додає буфери DMA у черги відповідних відеовузлів V4L2 з прапорцем `V4L2_BUF_FLAG_REQUEST_FD` і ставить запит на виконання через `ioctl(request_fd, MEDIA_REQUEST_IOC_QUEUE)`.
3. **Фаза апаратного виконання:**
   Сенсор видає пікселі по лініях MIPI CSI-2. Приймач і блок ISP обробляють потік за вказаними в запиті параметрами. Після завершення останнього циклу DMA контролер генерує переривання, а драйвер ядра переводить буфери у стан `VB2_BUF_STATE_DONE`.
4. **Фаза завершення та виклику зворотного зв'язку:**
   Pipeline Handler заповнює вихідні метадані в об'єкті `Request` і генерує сигнал `camera->requestCompleted`. Застосунок отримує повідомлення у своєму циклі подій, зчитує готові пікселі з буферів, після чого викликає `request->reuse(Request::ReuseBuffers)` і повертає запит у чергу для наступних кадрів.

Повну практичну реалізацію програми на C++, що керує конвеєром захоплення двох паралельних потоків із динамічною експозицією, наведено в матеріалі [⚙️ Практична реалізація конвеєра захоплення на C++](book:unix-linux/libcamera-stack/proj-libcamera-capture-pipeline.md).

## 6. Нульове копіювання (Zero-Copy) та інтеграція dma-buf

В обробці відео з роздільною здатністю 4K (3840×2160) кожен нестиснений кадр у форматі NV12 або RGB888 займає від 12 до 24 мегабайтів оперативної пам'яті. За частоти 60 кадрів/с копіювання таких обсягів через центральний процесор за допомогою викликів `memcpy()` створювало б трафік на шині пам'яті понад 1.4 ГБ/с, повністю блокуючи кеш процесора та призводячи до деградації продуктивності й перегріву системи.

Для усунення цієї проблеми libcamera базується на системній архітектурі **нульового копіювання (Zero-Copy)** за допомогою спільних буферів ядра **dma-buf**.

### Анатомія `libcamera::FrameBuffer`

Об'єкт `FrameBuffer` у libcamera не містить виділеного масиву байтів у користувацькому просторі. Натомість він інкапсулює вектор апаратних площин `FrameBuffer::Plane`:

```cpp
struct Plane {
    SharedFD fd;     // Файловий дескриптор анонімного об'єкта dma-buf
    size_t offset;   // Зміщення початку площини всередині буфера в байтах
    size_t length;   // Довжина площини пам'яті в байтах
};
```

Кожна площина відповідає окремому колірному шару пікселів (наприклад, у планарному форматі `NV12` площина 0 містить яскравість Y, а площина 1 — черговані компоненти хроматичності UV).

```
 ┌─────────────────────────────────────────────────────────────┐
 │                Фізична пам'ять RAM (DMA Buffer)             │
 └───────┬─────────────────────────────────────────────┬───────┘
         │ DMA Write                                   │ Direct Scanout / Import
         ▼                                             ▼
 ┌───────────────┐                             ┌───────────────┐
 │   SoC ISP /   │                             │  GPU / DRM /  │
 │  CSI-2 Driver │                             │ Video Encoder │
 └───────────────┘                             └───────────────┘
         ▲                                             ▲
         │ fd: 14                                      │ fd: 14
         └───────────── [ dma-buf fd ] ────────────────┘
                                │
                        libcamera FrameBuffer
```

### Шлях кадру без участі процесора (Zero-Copy Dataflow)

1. **Виділення буферів:** За допомогою `FrameBufferAllocator` драйвер ISP виділяє фізично неперервні сторінки пам'яті ядра (через механізм CMA — *Contiguous Memory Allocator* або IOMMU) та експортує їх у простір користувача як файлові дескриптори `dma-buf fd`.
2. **Апаратний запис:** Контролер DMA блоку ISP записує оброблені пікселі безпосередньо за фізичними адресами сторінок оперативної пам'яті.
3. **Передача дескриптора:** libcamera передає числовий файловий дескриптор `dma-buf fd` графічному рушію застосунку (наприклад, через інтерфейс EGL/OpenGL `EGLImageKHR`, розширення Vulkan `VK_EXT_external_memory_dma_buf` або дисплейний сервер Wayland через протокол `linux-dmabuf`).
4. **Апаратне відображення або кодування:** Графічний процесор (GPU) або апаратний відеоенкодер H.264/HEVC напряму читає пікселі з тих самих фізичних сторінок пам'яті через свій власний DMA-контролер.

Центральний процесор під час усього цього циклу не торкається жодного байта піксельних даних, виконуючи лише легковагову маршрутизацію файлових дескрипторів та обробку подій завершення кадру.

## 7. Екосистема сумісності: V4L2 compat, GStreamer libcamerasrc та PipeWire

Створення сучасного API вимагає плавної інтеграції з величезним масивом уже існуючого програмного забезпечення. Бібліотека libcamera надає три рівні системної сумісності, що охоплюють як застарілі утиліти, так і сучасні десктопні платформи.

![Стек сумісності та PipeWire](/reference/unix-linux/devices/libcamera-stack/img/compatibility-and-pipewire-stack.svg)
*Рис. 4. Екосистема сумісності: трансляція запитів через v4l2-compat, плагін GStreamer libcamerasrc та безпечне мультиплексування потоків у PipeWire.*

### Шар емуляції V4L2 (`v4l2-compat.so`)

Тисячі готових програм комп'ютерного зору та відеозв'язку (веббраузери Chromium і Firefox, месенджери Zoom, Skype, бібліотека OpenCV `VideoCapture`) жорстко розраховані на відкриття класичного файлу пристрою `/dev/videoX`.

Для роботи таких застосунків із комплексними камерами libcamera містить проміжну динамічну бібліотеку **`v4l2-compat.so`**. Вона підключається через механізм попереднього завантаження динамічного лінкера `LD_PRELOAD`:

```bash
# Прозорий запуск Firefox із підтримкою CSI-2 камер через libcamera
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libcamera/v4l2-compat.so firefox
```

Бібліотека перехоплює системні виклики `open()`, `close()`, `ioctl()`, `mmap()` та `munmap()`:
- Під час виклику `open("/dev/video0")` бібліотека ініціалізує внутрішній екземпляр `CameraManager` і створює емульований дескриптор віртуальної камери.
- Виклики `ioctl(VIDIOC_ENUM_FMT)` та `VIDIOC_S_FMT` транслюються у методи `CameraConfiguration` та `validate()`.
- Виклики `VIDIOC_QBUF` та `VIDIOC_DQBUF` автоматично упаковуються в об'єкти `libcamera::Request` і ставляться в апаратну чергу.

Застосунок переконаний, що працює зі звичайною веб-камерою, у той час як за лаштунками libcamera прозоро керує складною топологією Media Controller та алгоритмами 3A.

### Інтеграція в GStreamer: Елемент `libcamerasrc`

У мультимедійних конвеєрах GStreamer доступ до камер забезпечує спеціалізований елемент-джерело **`libcamerasrc`**. Він автоматично формує формати `GstCaps` на основі можливостей ISP, підтримує переговори про формати (caps negotiation) і дозволяє легко створювати складні розгалужені конвеєри:

```bash
# Перегляд відеопотоку у форматі NV12 на дисплеї
gst-launch-1.0 libcamerasrc camera-name="/base/soc/i2c0mux/i2c@1/imx477@1a" ! \
    video/x-raw,width=1920,height=1080,framerate=30/1,format=NV12 ! \
    autovideosink

# Одночасний запис у файл зі стисненням H.264 та виведення вікна перегляду
gst-launch-1.0 libcamerasrc name=cam \
    cam.src ! queue ! video/x-raw,width=1920,height=1080 ! v4l2h264enc ! mp4mux ! filesink location=video.mp4 \
    cam.src_1 ! queue ! video/x-raw,width=640,height=480 ! autovideosink
```

### Мультиплексування та ізоляція через аудіо-відео сервер PipeWire

Історичним обмеженням V4L2 була неможливість відкриття одного сенсора декількома незалежними процесами одночасно. Якщо фоновий сервіс комп'ютерного зору або сканер обличчя займав `/dev/video0`, користувач не міг відкрити вебкамеру у браузері чи програмі відеодзвінків.

У сучасному десктопному стеку Linux (GNOME, KDE, Fedora, Ubuntu) центральним диспетчером мультимедіа став сервер **PipeWire**. Завдяки плагіну архітектури SPA (Simple Plugin Architecture) для libcamera, PipeWire бере на себе ексклюзивне монопольне керування фізичною камерою через libcamera C++ API:
- Фізичний потік кадрів DMA-BUF захоплюється сервером PipeWire один раз.
- PipeWire створює віртуальні вузли-джерела для клієнтів.
- Десятки незалежних застосунків (включно з ізольованими пісочницями Flatpak і Snap) отримують доступ до одного й того самого відеопотоку через портал **XDG Desktop Portal Camera**.
- Користувач отримує системне діалогове вікно підтвердження доступу до камери (Privacy Guard), що унеможливлює негласне стеження шкідливим програмним забезпеченням.

## 8. Підсумок

Проєкт **libcamera** подолав багаторічний розкол між закритими мобільними HAL-стеками та застарілим монолітним інтерфейсом V4L2. Перенесення складної логіки конфігурації, синхронізації та алгоритмів 3A у простір користувача над стандартизованими механізмами ядра (Media Controller, V4L2 Subdevices, Media Request API та dma-buf) дозволило створити відкритий, безпечний та високопродуктивний стек для оптичних систем будь-якої складності — від крихітних вбудованих роботів до сучасних багатокамерних ноутбуків та серверів комп'ютерного зору.
