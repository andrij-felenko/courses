# 📜 Від монолітного V4L2 та Android CameraHAL до libcamera

Коли наприкінці 1990-х років у ядрі Linux з'явилася підсистема Video4Linux (V4L), типовим пристроєм захоплення відео була аналогова плата ТБ-тюнера на шині PCI (наприклад, чип Conexant BT878) або перші паралельні веб-камери. Архітектурна модель була гранично прямолінійною: єдиний апаратний блок приймав аналоговий сигнал, оцифровував його у фіксований формат YUV або RGB і записував у виділений буфер системної пам'яті через контролер прямого доступу до пам'яті (DMA). Для простору користувача вся ця апаратура виглядала як один файл пристрою `/dev/video0`.

Поява на початку 2000-х років стандарту USB Video Class (UVC) лише зміцнила цю парадигму. Усі операції попередньої обробки світла, дебайєризації, автоекспозиції (AE) та автоматичного балансу білого (AWB) виробники веб-камер сховали всередину спеціалізованої мікросхеми (ASIC) у корпусі камери. Драйвер ядра `uvcvideo` отримував через шину USB уже сформовані пікселі у форматах `YUYV` або стиснених кадрах `MJPEG`. Застосунку залишалося виконати послідовність викликів ioctl: узгодити формат через `VIDIOC_S_FMT`, запросити буфери пам'яті через `VIDIOC_REQBUFS` і запустити передачу викликами `VIDIOC_QBUF` та `VIDIOC_DQBUF`.

## Смартфонна криза та розкол екосистеми

Крах монолітної моделі настав із бурхливим розвитком мобільних процесорів (System-on-Chip, SoC) наприкінці 2000-х років. У смартфонах і портативних пристроях розмістити повноцінний апаратний ISP всередині крихітного оптичного модуля камери було неможливо через жорсткі обмеження за габаритами, енергоспоживанням і вартістю. Виробники пішли іншим шляхом: у модуль встановлювали виключно "голу" кремнієву матрицю (Raw Sensor — наприклад, OmniVision або Sony), яка підключалася до процесора через швидкісний серійний інтерфейс MIPI CSI-2 (Camera Serial Interface).

Сам процесор обробки сигналів зображення (ISP — Image Signal Processor) перемістився на кристал головного процесора SoC (Texas Instruments OMAP3/OMAP4, Qualcomm Snapdragon, Samsung Exynos, NXP i.MX, Intel Atom/IPU). Від оптичного сенсора процесор отримував сирі баєрівські дані (RAW8, RAW10, RAW12), які вимагали десятків послідовних математичних перетворень: від виправлення дефектних пікселів і компенсації віньєтування об'єктива (Lens Shading Correction) до відновлення повноколірного RGB-зображення (Demosaicing), тривимірного шумозаглушення (3DNR) і локального тонового відображення (HDR Tone Mapping).

Ба більше, алгоритми зворотного зв'язку 3A (Auto Exposure, Auto White Balance, Auto Focus) стали програмними. Щоб сфокусувати лінзу або відкоригувати витримку, програма мала отримати від апаратного блоку ISP математичну статистику поточного кадру (гістограми яскравості, зональні коефіцієнти різкості), розрахувати нові коефіцієнти підсилення та час затвора, після чого записати їх у регістри сенсора через шину I2C строго до початку експонування наступного кадру.

```
Класична екосистема Linux:
Сенсор ──(MIPI CSI-2)──> [ SoC ISP ] ──> /dev/video0 (Чорний ящик, брак контролю 3A)

Екосистема Android:
Сенсор ──(MIPI CSI-2)──> [ SoC ISP ] ──> /dev/mediaX + /dev/v4l-subdevX
                                              │
                                              ▼
                             [ Пропрієтарний Android CameraHALv3 ] (Закритий блоб)
```

Класичний інтерфейс V4L2 не мав засобів для опису розгалуженої апаратної топології, роздільного налаштування сенсора, CSI-2 приймача та блоків ISP, а головне — для покрокової атомарної синхронізації керуючих параметрів із кожним окремим кадром.

Операційна система Android вирішила цю проблему створенням власного апаратного рівня абстракції — Android Camera HAL (зокрема версії CameraHALv3). CameraHALv3 запропонував сучасну модель на основі покрокових запитів (Request-based model), де кожен кадр супроводжується власним списком метаданих і налаштувань. Однак реалізація цих HAL-модулів лягла на плечі виробників процесорів (Qualcomm, MediaTek, Samsung), які створили закриті бінарні динамічні бібліотеки (`camera.vendor.qcom.so` тощо).

У результаті екосистема Linux розкололася:
1. Мобільний світ Android володів складними алгоритмами обробки камер, але вони були закритими, прив'язаними до внутрішніх API Android (Bionic libc, Binder IPC) і непридатними для використання в дистрибутивах загального призначення.
2. Традиційний світ Linux (десктопи, промислові контролери, робототехніка, автомобільні системи) залишився з монолітним V4L2, який не дозволяв підключити жодну сучасну CSI-2 камеру без написання унікального пропрієтарного драйвера користувацького простору для кожного конкретного процесора.

## Ініціатива розробників ядра: Народження libcamera

До 2018 року ситуація стала критичною. Сучасні ноутбуки (наприклад, лінійки Microsoft Surface, Dell XPS, Lenovo ThinkPad) почали оснащуватися процесорами Intel із вбудованими ISP Intel IPU3 та IPU4 замість USB-камер. Після встановлення стандартного дистрибутива Linux (Ubuntu, Fedora, Debian) вбудовані веб-камери в цих ноутбуках перетворювалися на "мертвий вантаж", оскільки в системі не існувало програмного стека для керування IPU3 ISP.

На конференції Embedded Linux Conference Europe (ELCE) у жовтні 2018 року провідні розробники підсистеми V4L2 ядра Linux — Лоран Піншар (Laurent Pinchart), Якопо Монді (Jacopo Mondi), Кіран Бінгем (Kieran Bingham) та Ніклас Седерлунд (Niklas Söderlund) — оголосили про заснування проєкту **libcamera**.

Головними засадами архітектури libcamera стали:
- **Повна відкритість коду:** Створення вільного стека обробки камер із ліцензією LGPL-2.1+ для базової бібліотеки.
- **Абстракція складної апаратури:** Простір користувача отримує елегантний об'єктноорієнтований C++17 API (`CameraManager`, `Camera`, `Request`, `FrameBuffer`), повністю ізольований від специфіки сотень вузлів `/dev/v4l-subdevX` та `/dev/mediaX`.
- **Модульність через Pipeline Handlers:** Відокремлення ядра бібліотеки від специфічних драйверів процесорів (Pipeline Handlers для Broadcom, Intel, Rockchip, NXP, Qualcomm).
- **Ізоляція закритих алгоритмів (IPA Sandboxing):** Виробники оптики та сенсорів отримали можливість запускати свої пропрієтарні або запатентовані алгоритми 3A у вигляді окремих модулів Image Processing Algorithm (IPA), ізольованих у безпечній пісочниці під керуванням `seccomp`.

## Поворотний момент: Міграція Raspberry Pi

Найважливішим каталізатором масового впровадження libcamera став перехід платформи Raspberry Pi.

Історично мікрокомп'ютери Raspberry Pi (RPi 1, 2, 3, 4) використовували закриту графічну підсистему Broadcom VideoCore IV. Офіційні модулі камер (Raspberry Pi Camera Module v1 на сенсорі OV5647 та v2 на сенсорі IMX219) керувалися через фірмовий двійковий інтерфейс MMAL (Multi-Media Abstraction Layer). Користувачі застосовували системні утиліти `raspistill` та `raspivid`, які зверталися до закритої прошивки GPU VideoCore (`start.elf`), де відбувалася вся магія ISP та 3A-алгоритмів.

Цей підхід мав фатальний недолік: розробники не могли змінювати алгоритми обробки, не могли підключити сторонні сенсори без перепрошивки закритого коду Broadcom, а сама система була повністю відірвана від стандартної інфраструктури ядра Linux.

```
Історичний стек Raspberry Pi (до 2021):
raspistill ──> MMAL API ──> /dev/vchiq ──> [ Прошивка GPU VideoCore (start.elf) ] ──> Сенсор

Сучасний відкритий стек Raspberry Pi (після 2021):
rpicam-apps / Picamera2 ──> libcamera ──> PipelineHandlerRPi ──> V4L2 Unicam + bcm2835-isp ──> Сенсор
```

У листопаді 2021 року команда інженерів Raspberry Pi на чолі з Девідом Плауманом (David Plowman) та Науширом Патаком (Naushir Patuck) офіційно оголосила про повну відмову від драйверів MMAL на користь стандартного ядра Linux з драйверами V4L2 Unicam (приймач CSI-2) та bcm2835-isp, а також перехід на `libcamera` як основний системний стек. Усі закриті алгоритми автоекспозиції, калібрування сенсорів та автофокусу було відкрито й перенесено в модуль `ipa_rpi.so`.

Для заміни застарілих утиліт було створено офіційний пакет програм `libcamera-apps` (згодом перейменований на `rpicam-apps`: `rpicam-still`, `rpicam-vid`, `rpicam-hello`), а також бібліотеку `Picamera2` для мови Python. Це довело, що повністю відкритий стек здатен забезпечувати якість фотозйомки та швидкодію, еквівалентну комерційним закритим рішенням.

## Інтеграція в сучасний дистрибутив Linux

На сучасному етапі libcamera перетворилася на загальносистемний фундамент для роботи з камерами в екосистемі вільного програмного забезпечення.

Завдяки плагіну `libcamerasrc` для мультимедійного фреймворку GStreamer та модулю камер для аудіо-відео сервера **PipeWire**, складні сенсори ноутбуків і вбудованих плат отримали прозору інтеграцію з графічними оточеннями GNOME та KDE. Користувацькі програми в ізольованих контейнерах Flatpak або Snap можуть безпечно запитувати доступ до відеопотоку через портал XDG Desktop Portal Camera, не знаючи нічого про внутрішню будову апаратних ISP процесора.
