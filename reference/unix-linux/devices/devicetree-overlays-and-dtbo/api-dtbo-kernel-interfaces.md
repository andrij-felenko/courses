# 📋 Структура даних та системний API оверлеїв Дерева Пристроїв

Цей довідник містить формальну специфікацію внутрішніх структур даних ядра Linux, інтерфейсів простору користувача ConfigFS та схем метаданих компілятора `dtc`, які забезпечують функціонування та внутрішню транзакційність динамічних оверлеїв Дерева Пристроїв (Device Tree Overlays).

## 1. Схема метаданих компілятора dtc (версія 1.4.1+)

Під час компіляції вихідного коду оверлею з використанням прапора `-@` або під час обробки вихідного файлу з директивою `/plugin/`, компілятор `dtc` вносить суттєві зміни до підсумкової структури бінарного файла `.dtbo`. Оскільки у звичайному бінарному файлі `.dtb` усі текстові мітки вузлів вилучаються для економії обсягу пам'яті, компілятор створює три спеціальні мета-вузли верхнього рівня, які зберігають інформацію про текстові назви та адреси посилань.

### 1.1. Вузол `__symbols__`
Вузол `__symbols__` слугує локальним реєстром міток, оголошених у самому файлі оверлею. Він описує текстові ідентифікатори вузлів, до яких інші оверлеї або зовнішні компоненти ядра можуть звертатися за текстовим іменем. Властивості всередині цього вузла мають вигляд рядкових пар, де ім'я властивості відповідає назві мітки у коді `.dts`, а значення являє собою абсолютний шлях до створеного вузла у системі оверлею.

```dts
__symbols__ {
    sensor_label = "/fragment@0/__overlay__/temp-sensor@48";
    display_label = "/fragment@1/__overlay__/display@0";
};
```

Під час завантаження оверлею ядро Linux зчитує цей вузол і копіює його вміст до глобального вузла `__symbols__`, який розміщується в корені live-дерева `of_root`. Це забезпечує можливість каскадного накладання кількох оверлеїв, коли другий оверлей посилається на мітку, створену першим оверлеєм у системі.

### 1.2. Вузол `__fixups__`
Вузол `__fixups__` перелічує всі зовнішні посилання на мітки базового Дерева Пристроїв, які не були вирішені на етапі компіляції оверлею. Оскільки під час збирання файлу `.dtbo` компілятор `dtc` не знає фактичного значення індексу phandle цільового вузла у базовому дереві (наприклад, шини `&i2c1` або контролера переривань `&gpio2`), він записує у поля `target` та `interrupt-parent` тимчасовий заповнювач зі значенням `0x00000000`.

Для кожного зовнішнього посилання у вузлі `__fixups__` створюється окрема властивість. Назва цієї властивості відповідає текстовій назві мітки базового дерева, а значення являє собою список рядків. Кожен рядок описує шлях до вузла оверлею, назву властивості та байтовий зсув всередині цієї властивості, де лежить тимчасове значення `0x00000000`.

```dts
__fixups__ {
    i2c1 = "/fragment@0:target:0";
    gpio2 = "/fragment@0/__overlay__/temp-sensor@48:interrupt-parent:0";
    spi0 = "/fragment@1:target:0";
};
```

Під час виконання функції `of_overlay_fdt_apply()` ядро шукає ім'я `i2c1` у глобальному вузлі `__symbols__` базового дерева. Знайшовши відповідний абсолютний шлях, ядро дістає фактичний індекс phandle цільового вузла та перезаписує нульовий заповнювач за вказаним у `__fixups__` байтовим зсувом.

### 1.3. Вузол `__local_fixups__`
Вузол `__local_fixups__` вирішує проблему внутрішніх посилань між вузлами самого оверлею. Якщо один вузол усередині оверлею посилається на інший вузол того ж оверлею (наприклад, датчик посилається на контролер тактування, описаний у цьому ж фрагменті), компілятор призначає їм локальні значення phandle, починаючи з одиниці.

Однак при накладанні оверлею на базове дерево ці локальні значення phandle можуть збігатися з уже існуючими значеннями phandle в `of_root`. Щоб уникнути колізій, ядро вираховує унікальний діапазон phandle і додає до кожного локального значення постійний зсув (delta). Вузол `__local_fixups__` має дзеркальну деревну структуру, яка повторює ієрархію фрагментів оверлею та вказує точні зсуви властивостей, де вимагається перерахунок локальних phandle.

```dts
__local_fixups__ {
    fragment@0 {
        __overlay__ {
            temp-sensor@48 {
                clocks = <0x00>;
            };
        };
    };
};
```

## 2. Системний інтерфейс ConfigFS

Динамічне керування оверлеями з простору користувача реалізовано через віртуальну файлову систему ConfigFS. Підсистема оверлеїв реєструє свою групу елементів за шляхом `/sys/kernel/config/device-tree/overlays`.

### 2.1. Ієрархія каталогів та атрибутів

Кожен окремий оверлей представляє собою підкаталог у групі `overlays`. Створення нового каталогу за допомогою системного виклику `mkdir()` викликає аллокацію внутрішньої структури `struct cfs_overlay_item` у ядрі.

```
/sys/kernel/config/device-tree/overlays/
├── <ім'я_оверлею>/
│   ├── dtbo     (WO: запис бінарного блоку DTBO)
│   ├── status   (RO: статус виконання, "applied" або код помилки)
│   └── path     (RO: шлях до цільового вузла базового дерева)
```

### 2.2. Опис атрибутів та процедури запису

Драйвер ConfigFS обробляє атрибути файлів через набір обробників читання та запису.

- `dtbo` (Write-Only): Атрибут для передачі бінарного файлу `.dtbo`. Коли програма простору користувача виконує запис у цей файл, драйвер ConfigFS виділяє безперервний буфер у пам'яті за допомогою `vmalloc()` або `kmalloc()`, зчитує вміст бінарного блоку та викликає внутрішню функцію ядра `of_overlay_fdt_apply()`. Повторний запис у вже завантажений атрибут повертає помилку `-EBUSY`.
- `status` (Read-Only): Повертає поточний стан оверлею. Якщо накладання пройшло успішно, атрибут містить рядок `"applied\n"`. У разі виникнення помилки під час підключення вузлів або виклику `probe()` драйверів, атрибут повертає текстовий опис помилки (наприклад, `"failed to apply: -EINVAL\n"`).
- `path` (Read-Only): Менеджер оверлеїв записує у цей атрибут абсолютний канонічний шлях до вузла Дерева Пристроїв, який слугує точкою монтування даного фрагмента (`target-path`).

Демонтування оверлею виконується викликом `rmdir()` над каталогом оверлею. Драйвер ConfigFS перехоплює видалення каталогу, викликає функцію `of_overlay_remove()` для відкату змін у `of_root`, чекає завершення розмонтування пристроїв та звільняє виділену пам'ять.

## 3. Внутрішні структури даних ядра Linux (drivers/of/overlay.c)

Для забезпечення атомарності та можливості повного відкату внесених змін ядро Linux використовує концепцію журнальованих змін (changesets).

### 3.1. Структура `struct fragment`
Представляє собою розгорнутий у пам'яті фрагмент оверлею, прив'язаний до конкретного цільового вузла.

```c
struct fragment {
    struct device_node *target;     /* Вказівник на цільовий вузол у базовому дереві of_root */
    struct device_node *overlay;    /* Вказівник на розгорнутий вузол __overlay__ */
    struct device_node *pnode;      /* Батьківський вузол самого фрагмента */
};
```

### 3.2. Структура `struct of_changeset`
Структура `struct of_changeset` реалізує паттерн "Транзакційний журнал". Усі операції з додавання нових вузлів, модифікації існуючих властивостей або видалення елементів не застосовуються до `of_root` напряму. Замість цього вони записуються у список записів `struct of_changeset_entry`.

```c
enum of_reconfig_change_action {
    OF_RECONFIG_ATTACH_NODE,    /* Приєднання нового вузла до дерева */
    OF_RECONFIG_DETACH_NODE,    /* Від'єднання вузла від дерева */
    OF_RECONFIG_ADD_PROPERTY,   /* Додавання нової властивості */
    OF_RECONFIG_REMOVE_PROPERTY,/* Видалення властивості */
    OF_RECONFIG_UPDATE_PROPERTY /* Оновлення вмісту властивості */
};

struct of_changeset_entry {
    struct list_head node;
    enum of_reconfig_change_action action;
    struct device_node *np;
    struct property *prop;
    struct property *old_prop;
};

struct of_changeset {
    struct list_head entries;   /* Двобічно зв'язаний список журнальованих дій */
};
```

Під час виконання `of_changeset_apply()` ядро послідовно проходить по списку `entries`, виконуючи необхідні маніпуляції з покажчиками структур `device_node` та `property`. Для демонтування оверлею функція `of_changeset_revert()` проходить по цьому ж списку у зворотному порядку, повністю відновлюючи початковий стан live-дерева.

## 4. C-API ядра Linux для програмного керування

Для внутрішніх підсистем ядра Linux, яким необхідно динамічно завантажувати оверлеї без участі файлової системи ConfigFS (наприклад, драйвер FPGA Manager або розширювальні мости шин), надається спеціалізований C-інтерфейс.

### 4.1. `of_overlay_fdt_apply()`

Завантажує та розгортає бінарний оверлей FDT у жива Дерево Пристроїв `of_root`.

```c
int of_overlay_fdt_apply(const void *overlay_fdt, u32 overlay_size, int *ovcs_id);
```

Функція виконує наступну послідовність дій під захистом глобального м'ютекса `of_mutex`:
1. Перевіряє заголовок FDT на коректність магічного числа `0xd00dfeed` та відповідність загального розміру `overlay_size`.
2. Викликає `unflatten_device_tree()` для перетворення бінарного блоку у дерево об'єктів `struct device_node`.
3. Розв'язує посилання у вузлах `__fixups__` та `__local_fixups__`, оновлюючи індекси phandle.
4. Ініціалізує транзакцію `struct of_changeset` та додає до неї всі нові вузли та властивості.
5. Відправляє сповіщення `OF_OVERLAY_PRE_APPLY` зареєстрованим нотифікаторам.
6. Застосовує транзакцію через `of_changeset_apply()`, модифікуючи live-дерево.
7. Відправляє сповіщення `OF_OVERLAY_POST_APPLY` та реєструє унікальний числовий токен транзакції у змінну `ovcs_id`.

Повертає `0` у разі успішного накладання або від'ємний код помилки (`-EINVAL` при пошкодженому блобі, `-ENOMEM` при нестачі пам'яті, `-ENODEV` при відсутності цільового вузла).

### 4.2. `of_overlay_remove()`

Видаляє накладений оверлей за його унікальним ідентифікатором транзакції.

```c
int of_overlay_remove(int *ovcs_id);
```

Функція шукає транзакцію з вказаним ідентифікатором `ovcs_id`, відправляє сповіщення `OF_OVERLAY_PRE_REMOVE`, відкочує всі зміни за допомогою `of_changeset_revert()`, відключає створені пристрої від шин, викликає `OF_OVERLAY_POST_REMOVE` та звільняє виділені структури пам'яті. У разі успіху значення `*ovcs_id` скидається в `0`.

### 4.3. Інтерфейс сповіщень (Overlay Notifiers)

Підсистеми ядра можуть підписуватися на події накладання та видалення оверлеїв за допомогою ланцюжка сповіщень.

```c
int of_overlay_notifier_register(struct notifier_block *nb);
int of_overlay_notifier_unregister(struct notifier_block *nb);
```

Обробник подій підписника отримує вказівник на структуру `struct of_overlay_notify_data`:

```c
struct of_overlay_notify_data {
    struct device_node *target;     /* Цільовий вузол у базовому дереві */
    struct device_node *overlay;    /* Вузол оверлею, що приєднується */
};
```

#### Визначені події нотифікатора:
- `OF_OVERLAY_PRE_APPLY`: викликається до зміни live-дерева; дозволяє підсистемам перевірити доступність ресурсів або заблокувати накладання;
- `OF_OVERLAY_POST_APPLY`: викликається після модифікації live-дерева; ініціює виклики `of_platform_default_populate()` для створення нових пристроїв та їх зв'язування з драйверами;
- `OF_OVERLAY_PRE_REMOVE`: викликається до відкату змін; сповіщає шини про необхідність виклику `remove()` драйверів та вилучення `struct device`;
- `OF_OVERLAY_POST_REMOVE`: викликається після повного вилучення вузлів з `of_root`; використовується для очищення внутрішніх кешів та індексів.

## 5. Діагностичні інтерфейси та точки трасування

Для налагодження процесів динамічного накладання оверлеїв у ядрі Linux передбачено ряд системних діагностичних механізмів:

1. **Віртуальна файлова система procfs/sysfs (`/proc/device-tree`):** Після успішного накладання оверлею додані вузли та властивості стають негайно видимими у каталозі `/proc/device-tree` (що є посиланням на `/sys/firmware/devicetree/base`). Інструмент `dtc` може роздрукувати поточний відновлений стан дерева командою `dtc -I fs /proc/device-tree`. Це дозволяє розробнику візуально перевірити правильно підключені вузли та перевірити правильність підстановки значень phandle.
2. **Точки трасування ftrace (`events/of`):** Підсистема Device Tree експортує події трасування, які фіксують початок та завершення підключення вузлів. Активація трасування виконується командою `echo 1 > /sys/kernel/debug/tracing/events/of/enable`. Вивід ftrace дозволяє детально відстежити час виконання кожної фази накладання та виявити затримки при зв'язуванні пристроїв з драйверами.
3. **Параметр ядра `of_debug`:** Передача параметра `of_debug` у командному рядку завантажувача ядра змушує менеджер оверлеїв виводити детальний покроковий журнал розв'язання phandle та перевірки `__fixups__` у системний лог `dmesg`. Це корисно у випадках, коли накладання оверлею відхиляється з помилкою `-EINVAL` або `-ENODEV`.

Комплексне використання цих внутрішніх C-функцій, структур транзакційного журналу `of_changeset` та системних атрибутів ConfigFS надає розробникам ядра та вбудованих систем повний контрольований інструментарій для динамічного конфігурування складних периферійних комплексів на базі Linux. Вона гарантує стабільну та передбачувану поведінку як при старті ОС, так і при тривалій експлуатації реконфігуровної апаратури.
