- **Віртуальна файлова система sysfs:** представлення апаратних ресурсів через файли (шлях `/sys/...`), операції `open`/`read`/`write`.
- **Символьні пристрої (Character devices):** абстракція `/dev/...`, де взаємодія відбувається через системні виклики `ioctl()`.
- **Простір ядра (Kernel space) та простір користувача (Userspace):** межа між драйверами ядра, які безпосередньо керують залізом, і прикладними програмами.

# Сучасний дворівневий API GPIO descriptors (gpiod)

Історично екосистема Linux керувала лініями загального призначення (GPIO — General Purpose Input/Output) за допомогою примітивного числового API та інтерфейсу sysfs (`/sys/class/gpio`). Ця модель, створена на зорі вбудованих систем, засновувалася на глобальних цілочисельних ідентифікаторах. Однак з розвитком багатоядерних архітектур, систем на кристалі (SoC) з тисячами виводів, а також жорстких вимог до безпеки та продуктивності, старий підхід вичерпав себе.

Відповіддю на недоліки sysfs став сучасний дескрипторний API — **gpiod** (GPIO Descriptors). Він поділяється на два рівні:
1. **Ядерний рівень (Kernel API):** використання `struct gpio_desc` замість чисел для драйверів усередині ядра.
2. **Рівень користувача (Userspace API):** символьні пристрої (`/dev/gpiochipN`) та бібліотека `libgpiod` замість роботи з текстовими файлами в `/sys/class/gpio`.

Ця стаття глибоко розглядає архітектуру gpiod, причини відмови від старого API, ядерні функції та прикладний рівень, а також демонструє приклади сучасного коду.

## 1. Смерть старого Integer API та SysFS

Щоб зрозуміти сучасну архітектуру, потрібно проаналізувати проблеми попередньої.

### 1.1. Глобальний простір цілих чисел
Старий ядерний API працював з глобальними номерами GPIO. Кожна лінія мала унікальний цілочисельний ідентифікатор (наприклад, 42).
- **Проблема колізій:** На складних платах з кількома розширювачами портів (I2C/SPI GPIO expanders) нумерація залежала від порядку ініціалізації драйверів (probe order). Номер 42 сьогодні міг бути світлодіодом, а завтра, через зміну конфігурації ядра, — лінією скидання критичного датчика.
- **Відсутність стану (Stateless):** Функція `gpio_request(int gpio, const char *label)` була єдиним способом «забронювати» пін, але ядро не могло надійно відстежити, який саме драйвер ним володіє, що призводило до витоків ресурсів.

### 1.2. Прокляття SysFS (`/sys/class/gpio`)
Для користувача старий інтерфейс полягав у записі магічних чисел у файли:
```bash
echo 42 > /sys/class/gpio/export
echo out > /sys/class/gpio/gpio42/direction
echo 1 > /sys/class/gpio/gpio42/value
```
Це здавалося в стилі UNIX ("усе є файл"), але містило фатальні архітектурні вади:
1. **Неатомарність (Race conditions):** Запис напрямку (direction) і значення (value) — це дві різні операції `write()`. Між ними міг відбутися контекстний перемикач, і лінія могла мимоволі генерувати небажаний імпульс (glitch).
2. **Продуктивність:** Перетворення цілих чисел у рядки (ASCII) для запису у файл і зворотне перетворення в ядрі — неймовірно повільний процес. Це робило неможливим використання sysfs для бітбенгінгу (bitbanging) або швидких протоколів.
3. **Безпека та права доступу:** Вузол `/sys/class/gpio/export` глобальний. Якщо дати користувачу права на запис, він міг експортувати *будь-який* пін, включаючи ті, що вже контролюються ядром (наприклад, пін регулятора напруги), і випадково спалити плату.
4. **Брак відстеження життєвого циклу:** Якщо процес, який експортував GPIO 42 і встановив його в одиницю, аварійно завершувався (SIGKILL), система не повертала пін у безпечний стан. Він залишався «завислим» назавжди.

## 2. Ядерний рівень: `struct gpio_desc`

У ядрі Linux (починаючи з версії 3.13) введено новий тип: вказівник на непрозору структуру `struct gpio_desc *`. Це змінило саму парадигму роботи.

### 2.1. Концепція дескриптора
Дескриптор — це об'єкт, керований підсистемою gpiolib. Драйвер не знає глобального номера; він просить ядро: «Дай мені лінію GPIO, яка в Device Tree описана як "reset-gpios"».
Ядро шукає цю лінію у дереві пристроїв, виділяє дескриптор і повертає його.

### 2.2. Отримання дескрипторів
Замість `gpio_request()` використовуються функції сімейства `gpiod_get`:
```c
#include <linux/gpio/consumer.h>

struct gpio_desc *reset_gpio;

/* Отримання GPIO, визначеного як "reset-gpios" у Device Tree */
reset_gpio = gpiod_get(dev, "reset", GPIOD_OUT_LOW);
if (IS_ERR(reset_gpio)) {
    return PTR_ERR(reset_gpio);
}
```
Тут ми бачимо дві фундаментальні переваги:
1. **Прив'язка до пристрою (`dev`):** Дескриптор прив'язаний до конкретного драйвера. Якщо драйвер вивантажується, ядро автоматично звільняє GPIO.
2. **Ініціалізація атомарно:** Прапорець `GPIOD_OUT_LOW` атомарно встановлює лінію на вихід і задає їй логічний нуль ще на етапі запиту. Ніяких небажаних станів між запитом і конфігурацією.

Також доступні `gpiod_get_optional()` (якщо лінія не є обов'язковою) та `gpiod_get_index()` (для отримання масиву ліній, наприклад, шини даних).

### 2.3. Логічні рівні (Active-Low Semantics)
Найпотужнішою зміною в дескрипторному API є **логічна інверсія на рівні ядра**.
Часто в апаратному забезпеченні сигнал скидання (RESET) спрацьовує при низькому рівні напруги (0 В), тобто він є "active-low".
У старому API драйвер мусив пам'ятати про це і писати `gpio_set_value(gpio, 0)`, щоб активувати скидання. Це спричиняло плутанину.
Новий API оперує *логічними* станами. Якщо в Device Tree (DTS) лінія позначена як `GPIO_ACTIVE_LOW`:
```dts
reset-gpios = <&gpio1 5 GPIO_ACTIVE_LOW>;
```
Тоді виклик:
```c
gpiod_set_value(reset_gpio, 1); // 1 = "Активно"
```
Автоматично перетвориться ядром у фізичний 0 на виводі. Драйвер більше не дбає про апаратну полярність. Для обходу логіки (якщо потрібні саме фізичні рівні) існують функції `gpiod_set_raw_value()`.

### 2.4. Основні функції gpiod API (Ядро)
- `gpiod_direction_input(desc)` / `gpiod_direction_output(desc, value)` — зміна напрямку.
- `gpiod_set_value(desc, value)` / `gpiod_get_value(desc)` — робота з логічними значеннями.
- `gpiod_to_irq(desc)` — отримання номера переривання для даного GPIO.
- `gpiod_put(desc)` — звільнення (якщо не використовується managed-версія `devm_gpiod_get`).

## 3. Користувацький рівень: Character Devices

Оскільки `/sys/class/gpio` офіційно оголошено застарілим і вилучено з нових ядер, простір користувача отримав свій еквівалент дескрипторного API: символьні пристрої `/dev/gpiochipN`.

### 3.1. Як це працює?
Замість глобальних пінів, користувач бачить контролери (чіпи). Наприклад, `/dev/gpiochip0` — це перший контролер GPIO у системі, який може мати 32 лінії.
Програма відкриває цей файл (`open()`) і спілкується з ним через виклики `ioctl()`.
- **Безпека:** Доступ до `/dev/gpiochip0` регулюється стандартними правами файлової системи (наприклад, група `gpio`).
- **Відстеження (Tracking):** Коли процес отримує лінії через `ioctl`, вони прив'язуються до файлового дескриптора (`fd`). Якщо процес падає або закриває `fd`, ядро негайно звільняє лінії, залишаючи систему в чистому стані.
- **Атомарність:** Можна одночасно запитати відразу кілька ліній (Bulk operations) і змінити їх стан за один системний виклик. Наприклад, змінити стан 8 ліній шини одночасно без затримок.

### 3.2. Бібліотека libgpiod
Оскільки працювати з `ioctl` безпосередньо незручно, розробники ядра створили офіційну бібліотеку **libgpiod**. Вона містить C API (та біндинги для C++, Python) і набір консольних утиліт, які замінюють скрипти на базі sysfs.

#### Консольні утиліти libgpiod:
- **`gpioinfo`** — виводить детальну карту всіх контролерів і ліній у системі, їхні назви (з Device Tree) та статус (хто ними зараз користується).
- **`gpioget`** — атомарно читає значення однієї або кількох ліній.
- **`gpioset`** — атомарно встановлює значення і (за замовчуванням) одразу звільняє лінію (хоча є опції для утримання).
- **`gpiomon`** — підписується на переривання (зміни стану) і виводить події в реальному часі в консоль. Підтримує фільтрацію шумів (debouncing) на рівні ядра.

#### Приклад на C (libgpiod v2):
```c
#include <gpiod.h>
#include <stdio.h>

int main() {
    struct gpiod_chip *chip;
    struct gpiod_line_request *request;
    struct gpiod_request_config *req_cfg;
    struct gpiod_line_config *line_cfg;
    int value;

    chip = gpiod_chip_open("/dev/gpiochip1");
    if (!chip) return 1;

    /* Сучасний підхід вимагає створення конфігураційних об'єктів */
    req_cfg = gpiod_request_config_new();
    line_cfg = gpiod_line_config_new();
    
    /* Запит лінії зсуву (offset) 5 як входу */
    gpiod_line_config_set_direction_default(line_cfg, GPIOD_LINE_DIRECTION_INPUT);
    gpiod_request_config_set_offsets(req_cfg, 1, (unsigned int[]){5});

    request = gpiod_chip_request_lines(chip, req_cfg, line_cfg);
    
    if (request) {
        value = gpiod_line_request_get_value(request, 5);
        printf("Значення лінії 5: %d\n", value);
        gpiod_line_request_release(request);
    }

    gpiod_line_config_free(line_cfg);
    gpiod_request_config_free(req_cfg);
    gpiod_chip_close(chip);
    return 0;
}
```
У цьому коді ми бачимо строге управління ресурсами. Лінія запитується атомарно з вказанням напрямку. Після завершення роботи файлові дескриптори закриваються.

### 3.3. Обмеження та нюанси
Хоча character devices і libgpiod перевершують sysfs, вони мають особливості:
1. **Без збереження стану для shell-скриптів:** У sysfs ви могли зробити `echo 1 > value` і залишити лінію в цьому стані. У `libgpiod` команда `gpioset` встановлює значення, а коли завершується — ядро звільняє лінію, що може скинути стан контролера (залежно від драйвера, іноді він повертається в input). Для скриптів `gpioset` має інтерактивний режим або параметри затримки (toggle/hold).
2. **Апаратна підтримка:** Можливості на кшталт debouncing або підтягувальних резисторів (pull-up/pull-down) через libgpiod працюють лише тоді, коли апаратний контролер і його драйвер у ядрі це підтримують (через pinctrl).

## Висновки

Перехід від `sysfs` до `gpiod` — це еволюційний стрибок для Linux. Глобальні числа поступилися місцем суворо типізованим дескрипторам, що вирішило проблеми колізій і витоку ресурсів. Простір користувача отримав швидкий, безпечний і атомарний API на базі `ioctl` та `libgpiod`. 
Для нових розробок використання `/sys/class/gpio` вважається грубим антипатерном, тоді як дескрипторний API є стандартом де-факто як для драйверів, так і для прикладних програм.
