# 📋 Ключі правил udev: повна довідка мови

Правило udev — це один рядок, у якому через кому сказано, **про який пристрій** ідеться і **що з ним зробити**. Мова цього рядка невелика й закінчена: два десятки питальних ключів, півтора десятка призначальних, шість операторів і набір підстановок. Тут вони зібрані всі: що кожен означає й на що зважати.

## Форма рядка

```udev
# коментар
SUBSYSTEM=="tty", ATTRS{serial}=="A6008isP", SYMLINK+="laser", MODE="0660"
```

Порожні рядки й рядки, що починаються з `#`, демон пропускає. Одне правило займає один рядок. Правило **спрацьовує**, коли справдилися **всі** його питальні ключі; тоді виконують **усі** призначення цього самого рядка.

Значення завжди беруть у подвійні лапки. Є й друга форма — з малою латинською `e` попереду (`e"рядок\n"`): вона каже читати екранування так, як у мові C, і потрібна там, де у значенні мусить опинитися символ, якого просто так не напишеш.

Порядок ключів усередині рядка на результат не впливає — за двома винятками: `RESULT` читає те, що надрукував `PROGRAM`, а `ENV{…}` бачить те, що приніс `IMPORT{…}`, тож той, хто кладе, мусить стояти лівіше.

І залізне обмеження: якщо в одному рядку кілька ключів **у множині** (`SUBSYSTEMS`, `KERNELS`, `DRIVERS`, `ATTRS`, `TAGS`), усі вони мусять збігтися на **одному й тому самому** предкові, а не кожен на своєму.

## Оператори

| Оператор | Рід ключа | Дія |
|---|---|---|
| `==` | питальний | значення збігається (з підтримкою шаблонів) |
| `!=` | питальний | значення **не** збігається |
| `=` | призначальний | присвоїти; ключеві-списку — затерти список цілком |
| `+=` | призначальний | дописати ще один елемент до списку |
| `-=` | призначальний | вилучити елемент зі списку |
| `:=` | призначальний | присвоїти й **заборонити** пізнішим правилам це міняти |

`+=` і `-=` мають сенс лише для ключів, що тримають список: `SYMLINK`, `RUN`, `TAG`, `OPTIONS`. А `:=` потрібен тому, що перебір правил не спиняється на першому збігові: без нього пізніший файл із більшим числом в імені спокійно перепише ваше рішення.

## Питальні ключі

**Про сам пристрій, про який прийшла подія.**

| Ключ | Питає |
|---|---|
| `ACTION` | назву дії події |
| `DEVPATH` | шлях пристрою в sysfs, без початкового `/sys` |
| `KERNEL` | ім'я, яке дало пристроєві ядро (`ttyUSB0`, `sda1`) |
| `SUBSYSTEM` | підсистему пристрою (`tty`, `block`, `net`, `usb`) |
| `DRIVER` | ім'я драйвера, прив'язаного до пристрою |
| `ATTR{файл}` | вміст файлу-атрибута в теці пристрою |
| `NAME` | нинішнє ім'я **мережевого інтерфейсу** |
| `SYMLINK` | одне з посилань, уже призначених пристроєві раніше |
| `TAG` | одну з позначок, уже почеплених на пристрій |
| `ENV{ключ}` | властивість пристрою — з події або дописану раніше |
| `CONST{ключ}` | сталу всієї системи, а не пристрою |
| `SYSCTL{параметр}` | значення параметра ядра |

`ACTION` бере значення з набору, який визначає ядро: `add`, `remove`, `change`, `move`, `online`, `offline`, `bind`, `unbind`. `CONST{}` знає рівно три ключі — `arch` (архітектура машини), `virt` (у якій віртуалізації працює система) і `cvm` (технологія конфіденційних обчислень). Це прикмети машини, а не окремого пристрою, тому в правилі вони радше вимикач цілої гілки, ніж спосіб когось упізнати.

`ATTR{…}` читає [атрибути sysfs](book:unix-linux/sysfs-device-model) — файли в теці пристрою, кожен з одним значенням усередині. `SYSCTL{…}` дивиться на [налаштовні параметри ядра](book:unix-linux/sysctl-tunables), ті самі, що видно як файли в `/proc/sys`.

**Про предків угору по шині.** Ті самі питання, але з пошуком: udev іде від пристрою вгору деревом і питає кожного предка по черзі.

| Ключ | Питає в предків |
|---|---|
| `KERNELS` | ім'я пристрою |
| `SUBSYSTEMS` | підсистему |
| `DRIVERS` | ім'я драйвера |
| `ATTRS{файл}` | атрибут sysfs |
| `TAGS` | позначку |

**Обчислені.** Ці три не читають готове значення, а добувають його самі.

| Ключ | Що робить |
|---|---|
| `TEST{маска}` | істинний, якщо файл існує; вісімкова маска додає перевірку бітів прав |
| `PROGRAM` | запускає програму; істинний, якщо вона повернула нуль |
| `RESULT` | збіг із рядком, який надрукував останній `PROGRAM` |

```udev
KERNEL=="sd*", PROGRAM="/usr/local/bin/disk-role %k", RESULT=="backup", SYMLINK+="backup-disk"
```

`PROGRAM` — питальний ключ, який виконує програму: усе, що udev знає про пристрій, вона дістає [через змінні середовища](book:unix-linux/argv-and-environment), а відповідь віддає рядком у стандартний вивід.

Різниця в часі між `PROGRAM` і `RUN` — не дрібниця, а те, що вирішує ціну правила. `PROGRAM` виконують **під час** добору, щоб з'ясувати, чи правило взагалі підходить; `RUN` — аж після того, як для цієї події перебрано всі правила. Тобто `PROGRAM` без вузької питальної частини перед ним запускає програму на кожну подію, що дійшла до цього рядка, — а їх на завантаженні тисячі. Тому спершу ставлять дешеві ключі (`SUBSYSTEM`, `KERNEL`), і тільки коли вони вже відсіяли зайве — `PROGRAM`.

## Призначальні ключі

| Ключ | Призначає |
|---|---|
| `NAME` | ім'я мережевого інтерфейсу (вузол у `/dev` перейменувати не можна) |
| `SYMLINK` | додаткове ім'я-посилання на вузол |
| `OWNER` / `GROUP` / `MODE` | власника, групу й [режим доступу](book:unix-linux/permission-bits) вузла |
| `SECLABEL{модуль}` | мітку [модуля безпеки](book:unix-linux/mac-selinux-apparmor) на вузлі |
| `ATTR{файл}` | значення, яке треба **записати** в атрибут sysfs |
| `SYSCTL{параметр}` | значення параметра ядра |
| `ENV{ключ}` | властивість пристрою |
| `TAG` | позначку на пристрої |
| `RUN{тип}` | програму, яку запустити після обробки події |
| `IMPORT{тип}` | звідки набрати цілу пачку властивостей |
| `OPTIONS` | налаштування самого правила чи пристрою |
| `LABEL` | мітку, куди можна стрибнути |
| `GOTO` | стрибок уперед до найближчої мітки з такою назвою |

Дрібниця з наслідками: `ENV{.ключ}` — властивість, чиє ім'я починається з крапки, — не потрапляє ні в базу демона, ні в подію назовні. Так позначають робочі значення, потрібні лише сусіднім правилам того самого прогону.

`GOTO` з `LABEL` — єдиний спосіб не перебирати решту файлу дарма; ним зазвичай і починають власний набір:

```udev
SUBSYSTEM!="block", GOTO="my_rules_end"
KERNEL=="sd?1", ATTRS{idVendor}=="0781", SYMLINK+="usbstick"
LABEL="my_rules_end"
```

### IMPORT{тип}

| Тип | Звідки бере властивості |
|---|---|
| `program` | зі стандартного виводу зовнішньої програми, у форматі `КЛЮЧ=значення` |
| `builtin` | так само, але програма вбудована в демона |
| `file` | з текстового файлу в тому самому форматі |
| `db` | одну властивість із наявного запису пристрою в базі udev |
| `cmdline` | одну властивість із [командного рядка ядра](book:unix-linux/bootloader-and-cmdline); для простого прапорця значенням стає `1` |
| `parent` | ключі, збережені в записі батьківського пристрою |

```udev
KERNEL=="sd*", IMPORT{builtin}="blkid", ENV{ID_FS_UUID}=="?*", SYMLINK+="disk/by-uuid/$env{ID_FS_UUID}"
```

Саме `IMPORT{parent}` пояснює, чому розділ диска знає марку самого диска: прикмети опускають донизу один раз і далі беруть із бази, а не перечитують sysfs у кожному правилі. Перелік убудованих програм залежить від версії systemd — чинний друкує `udevadm test-builtin` без аргументів.

### RUN{тип}

| Тип | Що запускає |
|---|---|
| `program` | зовнішню програму; без абсолютного шляху її шукають у `/usr/lib/udev` |
| `builtin` | одну з програм, убудованих у демона |

Довгих процесів звідси не запускають: усе, що народила подія, демон **безумовно вбиває**, коли обробку завершено, — хоч воно відчепилося від батька, хоч ні.

## Підстановки

Підстановку пишуть у значенні ключа; довга форма з `$` і коротка з `%` рівносильні.

| Коротко | Довго | Значення |
|---|---|---|
| `%k` | `$kernel` | ім'я пристрою від ядра |
| `%n` | `$number` | число з цього імені (`3` для `sda3`) |
| `%p` | `$devpath` | шлях пристрою в sysfs |
| `%b` | `$id` | ім'я предка, на якому зійшлися ключі в множині |
| — | `$driver` | ім'я драйвера того самого предка |
| `%s{файл}` | `$attr{файл}` | значення атрибута sysfs |
| `%E{ключ}` | `$env{ключ}` | значення властивості пристрою |
| `%M` | `$major` | старший номер пристрою |
| `%m` | `$minor` | молодший номер |
| `%c` | `$result` | рядок, який надрукував `PROGRAM` |
| `%P` | `$parent` | ім'я вузла батьківського пристрою |
| — | `$name` | нинішнє ім'я вузла або інтерфейсу |
| — | `$links` | усі нинішні посилання, через пробіл |
| `%N` | `$devnode` | ім'я вузла пристрою |
| `%r` | `$root` | тека вузлів, зазвичай `/dev` |
| `%S` | `$sys` | точка монтування sysfs, зазвичай `/sys` |
| `%%` | `$$` | сам символ `%` або `$` |

Вивід `PROGRAM` ріжеться на слова по пробілах, і слово беруть за номером: `%c{2}` — друге слово, `%c{2+}` — друге й усе, що за ним. Це рятує там, де помічна програма віддає кілька значень одним рядком.

## Шаблони збігу

Значення питального ключа — не обов'язково точний рядок; у ньому працюють [ті самі шаблони, що в оболонці](book:unix-linux/expansion-and-quoting).

| Шаблон | Збігається з |
|---|---|
| `*` | будь-якою кількістю будь-яких символів, зокрема нулем |
| `?` | рівно одним будь-яким символом |
| `[…]` | одним символом із дужок; `[0-9]` — діапазон, `[!0-9]` — усе, крім нього |

Окремо стоїть вертикальна риска: вона розділяє цілі варіанти значення, і збіг із будь-яким із них зараховують.

```udev
KERNEL=="sd[a-z]", SUBSYSTEM=="block", ENV{ID_BUS}=="usb|ieee1394", TAG+="removable"
```

Звідси й звичний зворот `ENV{ID_FS_UUID}=="?*"`: він читається як «властивість є і вона не порожня».

## OPTIONS

| Значення | Дія |
|---|---|
| `link_priority=число` | вага посилання; коли на одне ім'я претендують кілька пристроїв, виграє більше число |
| `string_escape=…` | чи замінювати небезпечні символи у значеннях `NAME`, `SYMLINK` і `ENV{…}`: `replace` — замінювати, `none` — ні |
| `static_node=ім'я` | застосувати права цього правила до статичного вузла з таким іменем — того, що існує ще до появи самого пристрою |
| `watch` | стежити за вузлом через [inotify](book:unix-linux/inotify-and-fanotify): коли його закриють після запису, система синтезує подію `change` |
| `nowatch` | вимкнути таке стеження |
| `db_persist` | поставити «липкий» прапорець на записі пристрою в базі udev: властивості лишаються в базі навіть після `udevadm info --cleanup-db` |
| `log_level=рівень` | рівень журналювання (`debug`, `info`, а також `reset`) на решту обробки цієї події |

`watch` варто розуміти правильно: це не стеження за вмістом диска, а хитрий гачок. Програма розмітки закриває блоковий пристрій після запису — і udev перечитує підпис файлової системи, тож `/dev/disk/by-uuid/…` оновлюється сам, без жодної команди. Ціна — зайві події там, де у вузол пишуть часто; саме тоді і вмикають `nowatch`.

Позначка `TAG+="uaccess"` стоїть окремо від решти: права за нею роздає не udev, а [logind](book:unix-linux/logind-sessions-seats) — тому, хто зараз фізично сидить за цією машиною, і забирає їх, коли той виходить.

Набір значень `OPTIONS` із версіями systemd росте (новіші додали, приміром, `dump` і `dump-json`), тому останнє слово завжди за `man udev` тієї версії, що стоїть у вас.
