# 📋 Інтерфейс RCU: примітиви, контракти й типові помилки

Інтерфейс RCU — це кількадесят макросів і функцій, з яких жодна не перевіряє в мить виклику, чи маєте ви право її кликати: неправильно вжитий примітив не дає ані попередження компілятора, ані падіння на місці, а виявляється через тижні випадковим пошкодженням пам'яті на чужій машині. Тому тут до кожної сигнатури додано те, чого в ній не видно: **що вона гарантує**, **звідки її вільно кликати** і **як її зазвичай ламають**.

Оголошення — з `include/linux/rcupdate.h`, `rculist.h`, `srcu.h`; стан дерева Linux — 2026 рік, і там, де інтерфейс за останні роки змінювався, версію названо окремо.

## Позначення ділянки читання

| позначка | чим є насправді | читач може спати |
|---|---|---|
| `rcu_read_lock()` / `rcu_read_unlock()` | у витісненому ядрі — `current->rcu_read_lock_nesting++`; у невитісненому — жодної машинної інструкції, лише заборона компіляторові переставляти доступи | ні |
| `rcu_read_lock_bh()` / `rcu_read_unlock_bh()` | `local_bh_disable()` плюс позначка для перевіряча замків | ні |
| `rcu_read_lock_sched()` / `rcu_read_unlock_sched()` | `preempt_disable()` плюс позначка | ні |
| `preempt_disable()`, закриті переривання, тіло обробника переривання | ділянка читання без жодного макроса — просто тому, що витіснення тут неможливе | ні |
| `srcu_read_lock(&ssp)` → `int idx` | лічильники свого ядра процесора в межах окремого домену | **так** |
| `rcu_read_lock_trace()` / `rcu_read_unlock_trace()` | позначка для різновиду RCU-tasks-trace | **так** |

Три верхні рядки колись були трьома **різними** механізмами, кожен зі своїм набором очікування: `synchronize_rcu_bh()`, `synchronize_sched()`, `call_rcu_bh()`, `call_rcu_sched()`. Обрати не той набір означало дочекатися не тих читачів — тиха помилка, що одного разу вилилася у вразливість. У версії 4.20 різновиди звели в один: `synchronize_rcu()` тепер чекає на **всі** читацькі позначення одразу, окремі оновлювальні виклики спершу стали синонімами, а невдовзі зникли з ядра. Читацькі позначки лишилися — але вже не як «різновиди RCU», а як те, чим вони й були: способом закрити нижні половини або витіснення.

Типові помилки:

- **Сон усередині ділянки.** Явний (`mutex_lock()`, `kmalloc(GFP_KERNEL)`) або прихований — `copy_to_user()` може впертися у сторінковий збій і заснути. Межа тут та сама, що й для решти [атомарного контексту ядра](book:unix-linux/kernel-locking): примітив, який має право чекати, у ділянці читання поза законом.
- **Вказівник, винесений назовні.** Після `rcu_read_unlock()` усе, здобуте всередині, недійсне, хоч і виглядає живим. Або копіюйте потрібне поле в межах ділянки, або беріть посилання на об'єкт, поки вона ще триває.
- **`rcu_read_lock()` замість замка між письменниками.** Позначка нікого не спиняє; двох одночасних письменників вона не розведе.

## Публікація й підписка

| виклик | сторона | упорядкування | коли саме він |
|---|---|---|---|
| `rcu_assign_pointer(p, v)` | письменник | запис зі звільненням: усе, що заповнено раніше, стає видним раніше за сам вказівник | публікуємо структуру, яку читач зараз побачить |
| `RCU_INIT_POINTER(p, v)` | письменник | **жодного** — звичайний запис | `v` — `NULL`; або `p` ще нікому не видно; або читачів уже гарантовано немає |
| `rcu_replace_pointer(p, v, c)` | письменник | читає старе значення з перевіркою умови `c` і публікує нове, повертає старе | заміна вказівника під своїм замком одним рядком |
| `rcu_dereference(p)` | читач | забороняє компіляторові вгадати значення й тим знищити залежність за адресою | усередині ділянки читання, коли підемо за вказівником |
| `rcu_dereference_check(p, c)` | читач | те саме, але перевіряч замків мовчить ще й тоді, коли істинна `c` | читач, захищений іншим способом |
| `rcu_dereference_protected(p, c)` | письменник | **жодного** — тільки перевірка `c` | ми тримаємо замок оновлення, читачів тут не буває |
| `rcu_access_pointer(p)` | будь-хто | тільки читання самого слова | вказівник порівнюємо чи віддаємо на звільнення, але **не йдемо** за ним |

Стовпець «сторона» тут головний. Читач і письменник дивляться на те саме поле, але з різних боків: читачеві потрібна гарантія, що адреса не вигадана, а письменникові — щоб вміст структури став видним раніше за вказівник на неї. Природа цієї другої гарантії — [запис зі звільненням](book:programming/memory-ordering-barriers): без нього процесор має право переставити записи, і читач дістане адресу вузла, у якому ще сміття.

> 🔧 **Навіщо це.** Підміна одного макроса іншим — найтихіша з помилок у цьому інтерфейсі. `RCU_INIT_POINTER()` замість `rcu_assign_pointer()` компілюється, працює на x86 роками й ламається на ARM під навантаженням, бо там перестановка записів справді видима збоку. А `rcu_dereference_protected()` у читача взагалі нічого не робить — код виглядає захищеним, хоч захисту немає. Саме тому кожен макрос має вузьке призначення й окрему назву: жоден із них не «трохи кращий» за сусіда, вони відповідають на різні питання.

Типові помилки:

- **Публікація через `RCU_INIT_POINTER()`.** Дешевше — і неправильно, щойно за вказівником є хоч одне поле, яке читач прочитає.
- **`rcu_dereference()` під замком оновлення.** Формально безпечно, але перевіряч замків не мовчатиме, а зайвий бар'єр стане на гарячому шляху письменника. Тут потрібен `rcu_dereference_protected(p, lockdep_is_held(&my_lock))`.
- **Повторне зняття вказівника в циклі.** Кожен `rcu_dereference()` — окреме прочитання; значення могло змінитися між ними. Знімайте раз у локальну змінну й працюйте з нею.
- **Пряме `p->field` в обхід макросів.** Ловиться статичним аналізатором `sparse` за позначкою `__rcu` у полі — і тільки ним.

Варіанти `rcu_dereference_bh()` і `rcu_dereference_sched()` роблять те саме, що звичайний, і різняться лише тим, яку позначку ділянки очікують від перевіряча замків; після зведення різновидів вони лишилися саме як засіб самоперевірки, а не як окремий механізм.

## Очікування й звільнення

| виклик | чого чекає | спить | звідки можна |
|---|---|---|---|
| `synchronize_rcu(void)` | повного періоду відстрочки | **так** | тільки контекст задачі, без узятих спін-замків |
| `synchronize_rcu_expedited(void)` | того самого, але примусово підганяючи ядра процесора | **так** | там само; коштує [міжпроцесорних переривань](book:unix-linux/inter-processor-interrupts) на всі ядра |
| `call_rcu(struct rcu_head *head, rcu_callback_t func)` | нічого, повертається одразу | ні | будь-який контекст, зокрема обробник переривання |
| `kfree_rcu(ptr, rhf)` | нічого; `rhf` — ім'я поля `struct rcu_head` усередині структури | ні | будь-який контекст |
| `kfree_rcu_mightsleep(ptr)` | нічого, але може чекати пам'яті під пакет | **так** | контекст задачі; для структур без власного `rcu_head` |
| `rcu_barrier(void)` | **виконання** всіх раніше поставлених зворотних викликів | **так** | контекст задачі |
| `get_state_synchronize_rcu()` / `poll_state_synchronize_rcu(s)` | нічого — запам'ятовує мітку й потім питає, чи період уже минув сам | ні | будь-який контекст |
| `queue_rcu_work(wq, rwork)` | нічого; робочий елемент піде в чергу після періоду | ні | будь-який контекст |

Два останні рядки — відповідь на дві частих потреби. Мітка періоду рятує, коли звільняти нічого, а просто треба знати, чи можна вже переходити далі: замість чекання — порівняння двох чисел (а `cond_synchronize_rcu(s)` чекає лише в тому разі, якщо період ще не минув сам собою). `queue_rcu_work()` рятує, коли прибирання **мусить** спати (звільнити пристрій, закрити файл): зворотний виклик `call_rcu()` виконується в контексті [нижньої половини](book:unix-linux/interrupts-bottom-halves) і спати не має права, тому сплячу роботу перекладають на робочу чергу.

Окремо варто знати, чого `call_rcu()` **не** обіцяє. Він не обіцяє, що зворотний виклик виконається на тому ядрі процесора, з якого його поставили: у ядрі, зібраному з `CONFIG_RCU_NOCB_CPU`, черги виносять у спеціальні потоки `rcuo`, щоб зняти цю роботу з ядер, чутливих до затримок. Не обіцяє порядку: два виклики, поставлені один за одним, можуть спрацювати в будь-якій послідовності. Не обіцяє й того, що вони не виконаються одночасно на різних ядрах. Єдина обіцянка — «не раніше, ніж скінчиться період відстрочки»; усе, що ваш код виводить понад це, — здогад, який одного дня не справдиться.

Типові помилки:

- **`synchronize_rcu()` у циклі.** Кожен виток — окремі мілісекунди. Правильно — зібрати пачку змін і дочекатися одного періоду на всю; для цього ж існує `call_rcu()`.
- **`synchronize_rcu()` під замком, який бере читач.** Класичне самоблокування: період не закінчиться, доки читач не вийде, а читач не вийде, доки не візьме замок.
- **Прискорений варіант за звичкою.** `synchronize_rcu_expedited()` розсилає переривання на всі ядра процесора; у циклі він перетворює прискорення на глобальне гальмо.
- **Повторний `call_rcu()` на той самий `rcu_head`, доки перший не спрацював.** Черга — однозв'язна, вузол у ній один; ловиться збіркою з `CONFIG_DEBUG_OBJECTS_RCU_HEAD`.
- **Сон у зворотному виклику.** Він виконується там, де спати не можна.
- **`synchronize_rcu()` замість `rcu_barrier()` перед вивантаженням [модуля](book:unix-linux/kernel-modules).** Період відстрочки не обіцяє, що вже поставлені зворотні виклики **виконалися**, — а саме їхній код зникає разом із модулем. `kfree_rcu()` тут виняток: він кличе `kfree()` з самого ядра, коду модуля не чіпає; але якщо структури бралися з власного кеша модуля, `rcu_barrier()` усе одно обов'язковий перед `kmem_cache_destroy()`.

## Списки й хеші

Обгортки зі `rculist.h` роблять рівно дві речі: додають потрібний бар'єр публікації в операції письменника й лишають цілим той вказівник, за яким читач вийде назад у живий список.

| письменник (під своїм замком) | що робить особливого |
|---|---|
| `list_add_rcu(new, head)`, `list_add_tail_rcu(new, head)` | публікують вузол як `rcu_assign_pointer()` |
| `list_del_rcu(entry)` | отруює лише `prev`; `next` лишає живим |
| `list_replace_rcu(old, new)` | `new` має бути заповнений цілком, включно з `next`/`prev`, до перемикання |
| `hlist_add_head_rcu`, `hlist_add_before_rcu`, `hlist_add_behind_rcu` | те саме для хеш-ланцюжка |
| `hlist_del_rcu(n)`, `hlist_del_init_rcu(n)` | другий скидає `pprev` у `NULL` (є за чим упізнати вилучений вузол), `next` лишає |

| читач (усередині ділянки) | примітка |
|---|---|
| `list_for_each_entry_rcu(pos, head, member[, cond])` | необов'язковий `cond` — умова для перевіряча замків |
| `list_first_or_null_rcu(head, type, member)`, `list_entry_rcu(p, type, member)` | поодинокий доступ без обходу |
| `list_for_each_entry_srcu(pos, head, member, cond)` | обхід під `srcu_read_lock()` |
| `hlist_for_each_entry_rcu(pos, head, member[, cond])` | те саме для хеш-таблиці |

Типові помилки:

- **Повторна ініціалізація вилученого вузла.** `list_del_rcu()` навмисно лишає `next` цілим — це єдиний шлях назовні для читача, що саме стоїть на цьому вузлі. Затерти `next` до кінця періоду означає завести читача в нікуди.
- **Звичайний `list_add()` у список, який читають без замка.** Компілюється; бар'єра публікації немає.
- **Обхід `_rcu`-макросом без позначеної ділянки.** Ловиться `CONFIG_PROVE_RCU`.
- **Повторне використання об'єкта до кінця періоду.** Для хеш-таблиць із кешем `SLAB_TYPESAFE_BY_RCU`, де об'єкт [повертається в той самий кеш](book:unix-linux/kernel-memory-slab) і одразу оживає під іншим змістом, звичайного `hlist` замало: читач може непомітно опинитися в іншому ланцюжку. Для цього випадку існує `hlist_nulls`, у якому кінець кожного ланцюжка позначено **його власним** значенням, і читач бачить, що заблукав, — саме так побудована таблиця сокетів.

## SRCU: домени й індекс

SRCU (*sleepable RCU* — «RCU, у якому можна спати») повертає читачеві частину витрат: він таки пише в лічильники свого ядра процесора. Плата за право заснути всередині читання.

| виклик | контракт |
|---|---|
| `DEFINE_SRCU(name)`, `DEFINE_STATIC_SRCU(name)`, `init_srcu_struct(&ssp)` | домен оголошують явно; чекання стосується **лише** свого домену |
| `cleanup_srcu_struct(&ssp)` | обов'язковий перед звільненням домену; вимагає, щоб не лишилося ні читачів, ні зворотних викликів |
| `int idx = srcu_read_lock(&ssp)` | повертає індекс, який **обов'язково** віддають назад: `srcu_read_unlock(&ssp, idx)` |
| `synchronize_srcu(&ssp)`, `synchronize_srcu_expedited(&ssp)` | спить; чекає читачів тільки цього домену |
| `call_srcu(&ssp, head, func)`, `srcu_barrier(&ssp)` | відкладення й бар'єр, точні відповідники загальних |
| `srcu_read_lock_held(&ssp)` | умова для `rcu_dereference_check()` у коді під SRCU |

Типові помилки:

- **Загублений або підмінений `idx`.** Значення не «прапорець зайнятості», а номер лічильника; віддати треба саме те, що дали, і саме тому домену.
- **Один домен на все.** Період SRCU не коротший за найдовшого читача, а читач тут має право спати хоч секунду. Спільний домен на непов'язані підсистеми означає, що найповільніший читач тримає всіх; домен заводять вузьким.
- **`synchronize_srcu()` усередині читача того самого домену.** Самоблокування, тепер уже без жодного посередника.

## RCU-tasks: коли ділянки немає взагалі

Окремий різновид для випадку, коли прибрати треба **сам код**, а не дані: на трампліні, який ставить [ftrace](book:unix-linux/ftrace-kernel-tracing), задача може стояти без будь-якої позначки — трамплін не має ні `rcu_read_lock()`, ні можливості її додати.

| виклик | чого чекає | хто вживає |
|---|---|---|
| `synchronize_rcu_tasks()`, `call_rcu_tasks()`, `rcu_barrier_tasks()` | доки **кожна** задача добровільно перепланується, побуває в просторі користувача або в простої | звільнення трамплінів трасування |
| `rcu_read_lock_trace()` / `rcu_read_unlock_trace()`, `synchronize_rcu_tasks_trace()`, `call_rcu_tasks_trace()`, `rcu_barrier_tasks_trace()` | явно позначених ділянок, усередині яких **вільно спати** | звільнення програм і мап [eBPF](book:unix-linux/ebpf-extended-berkeley-packet-filter) |

Типова помилка тут одна, зате дорога: сплутати `synchronize_rcu_tasks()` зі звичайним очікуванням і поставити його на шлях, яким ходять часто. Період RCU-tasks не має верхньої межі в мілісекундах — він триває стільки, скільки найдовше не переплановувалася найупертіша задача в системі.

## Діагностика

| засіб | що ловить |
|---|---|
| `CONFIG_PROVE_RCU` (входить у `CONFIG_PROVE_LOCKING`) | `rcu_dereference()` поза ділянкою й без оголошеного замка — «suspicious RCU usage» зі стеком |
| `rcu_read_lock_held()`, `rcu_read_lock_bh_held()`, `rcu_read_lock_sched_held()`, `srcu_read_lock_held(&ssp)`, `lockdep_is_held(&lock)` | будівельні цеглинки для аргументу `c` у `_check`/`_protected` |
| `RCU_LOCKDEP_WARN(cond, "текст")` | власна перевірка контексту в коді підсистеми |
| `CONFIG_DEBUG_OBJECTS_RCU_HEAD` | повторний `call_rcu()` на тому самому `rcu_head` |
| позначка `__rcu` у полі + `make C=1` (`sparse`) | пряме розіменування в обхід макросів, ще на збірці |

Механізм перевірок — той самий [перевіряч замків ядра](book:unix-linux/kernel-locking/proj-lockdep-lab.md), тому й вигляд повідомлень звичний, і ціна та сама: на робочих ядрах ці параметри вимкнені, тож ганяти новий код під ними треба самому.

Застій періоду відстрочки ядро діагностує само; параметри задають у [командному рядку ядра](book:unix-linux/bootloader-and-cmdline) або крутять на ходу файлами в `/sys/module/rcupdate/parameters/`.

| параметр | типове значення | що робить |
|---|---|---|
| `rcupdate.rcu_cpu_stall_timeout` | 21 (секунди) | скільки чекати, перш ніж писати попередження про застій |
| `rcupdate.rcu_cpu_stall_suppress` | 0 | вимикає попередження зовсім |
| `rcupdate.rcu_exp_cpu_stall_timeout` | 0 (брати звичайне) | окремий поріг для прискорених періодів, у мілісекундах |
| `rcupdate.rcu_task_stall_timeout` | — | поріг для RCU-tasks; нуль або менше вимикає |
| `rcutree.kthread_prio` | — | пріоритет потоків ядра RCU: рятує, коли їх витісняє реальночасова задача |
| `/sys/kernel/rcu_expedited`, `/sys/kernel/rcu_normal` | 0 | глобально перевести всі очікування на прискорені або, навпаки, заборонити прискорення |

## Мінімальний робочий приклад

Усе, що вище, в одному шматку: список пристроїв, який читають без замка, змінюють під м'ютексом і звільняють через період відстрочки.

```c
struct dev_entry {
    struct list_head node;
    struct rcu_head  rcu;
    int              ifindex;
    char             name[16];
};

static LIST_HEAD(dev_list);
static DEFINE_MUTEX(dev_mutex);            /* лише між письменниками */

/* читач: жодного спільного запису на всьому шляху */
static int dev_name_of(int ifindex, char *out, size_t n)
{
    struct dev_entry *d;
    int ret = -ENODEV;

    rcu_read_lock();
    list_for_each_entry_rcu(d, &dev_list, node) {
        if (d->ifindex == ifindex) {
            strscpy(out, d->name, n);      /* копіюємо ТУТ, поки вузол живий */
            ret = 0;
            break;
        }
    }
    rcu_read_unlock();
    return ret;                            /* d назовні вже недійсний */
}

/* зворотний виклик: спати тут не можна */
static void dev_free(struct rcu_head *head)
{
    kfree(container_of(head, struct dev_entry, rcu));
}

static void dev_remove(int ifindex)
{
    struct dev_entry *d;

    mutex_lock(&dev_mutex);
    list_for_each_entry(d, &dev_list, node) {   /* під замком — звичайний обхід */
        if (d->ifindex == ifindex) {
            list_del_rcu(&d->node);
            mutex_unlock(&dev_mutex);
            call_rcu(&d->rcu, dev_free);
            return;
        }
    }
    mutex_unlock(&dev_mutex);
}

static void __exit dev_exit(void)
{
    rcu_barrier();      /* інакше dev_free зникне разом із модулем */
}
```

Три деталі, задля яких цей приклад і написано: читач копіює **значення**, а не вказівник; письменник обходить список звичайним макросом, бо тримає замок; вивантаження чекає не періоду, а зворотних викликів.
