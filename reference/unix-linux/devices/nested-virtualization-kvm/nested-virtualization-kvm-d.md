Запуск гіпервізора всередині віртуальної машини є стандартною потребою сучасних хмарних інфраструктур, тестових стендів розробників, оркестраторів Kubernetes із безпечною ізоляцією контейнерів (наприклад, Kata Containers) та конвеєрів безперервної інтеграції (CI/CD). Проте фізичні процесори архітектури x86_64 апаратно не мають підтримки рекурсивної або нескінченно вкладеної віртуалізації. Апаратні розширення Intel VT-x та AMD-V надають лише два фундаментальні режими виконання: режим root (VMX Root / SVM Host) для гіпервізора та режим non-root (VMX Non-Root / SVM Guest) для гостя. Коли гостьова операційна система намагається сама виконати інструкцію віртуалізації (наприклад, `VMLAUNCH` або `VMRESUME` на Intel, чи `VMRUN` на AMD), щоб утворити власну вкладену ВМ, процесор перебуває у VMX Non-Root і безумовно генерує апаратне перехоплення (VM Exit). Без узгодженої підтримки з боку хостового гіпервізора ця спроба викликає виняткову ситуацію `#UD` (Invalid Opcode) або аварійний зупинок гостя.

Вкладена віртуалізація (Nested Virtualization) у підсистемі KVM розв'язує цю суперечність шляхом комбінованої емуляції апаратних розширень VMX/SVM та динамічного злиття структур управління віртуальними машинами.

## 1. Рівні виконання: L0, L1 та L2

Для опису потоку керування та розподілу відповідальності у вкладеній віртуалізації використовують трирівневу модель:

1. **L0 (Level 0 — Host Hypervisor):** Фізичний сервер та хостовий гіпервізор KVM, що працює безпосередньо на апаратному забезпеченні. L0 виконаний у режимі VMX Root (або SVM Host) і володіє монопольним правом керування фізичним процесором, оперативною пам'яттю, контролером переривань APIC та пристроями введення-виведення.
2. **L1 (Level 1 — Guest Hypervisor):** Віртуальна машина, запущена гіпервізором L0, у якій працює власна операційна система зі своїм екземпляром гіпервізора (KVM, Xen, Hyper-V або VMware ESXi). З точки зору L0, L1 є звичайним гостем, що працює у VMX Non-Root. Проте з точки зору власних гостьових систем, L1 виступає повноцінним гіпервізором.
3. **L2 (Level 2 — Nested Guest):** Вкладена віртуальна машина, що створюється та керується гіпервізором L1. L2 працює у режимі VMX Non-Root, але її апаратний стан налаштовується гіпервізором L0 за вказівками L1.

Фізичний процесор не знає про існування трьох рівнів: для процесора існують лише VMX Root (де виконується L0) та VMX Non-Root (де почергово виконуються L1 та L2). Коли L1 вважає, що він перемикає процесор у режим VMX Root для виконання своїх інструкцій віртуалізації, L0 прозоро перехоплює ці виклики та симулює очікувану поведінку.

Детальний аналіз того, як віртуалізація пройшла шлях від програмної інтерпретації до сучасних апаратних розширень, описано в [історії еволюції вкладеності та VMCS Shadowing](book:unix-linux/nested-virtualization-kvm/hist-shadow-vmcs-and-nested-evolution.md).

## 2. Емуляція VMX/SVM інструкцій та Trap-and-Emulate

Коли у гості L1 вмикається підсистема KVM, вона починає виконувати інструкції керування віртуалізацією: `VMON`, `VMPTRLD`, `VMCLEAR`, `VMREAD`, `VMWRITE`, `VMLAUNCH` та `VMRESUME` на платформі Intel, або `VMSAVE`, `VMLOAD`, `VMRUN` на платформі AMD. Оскільки L1 працює у VMX Non-Root, кожна з цих інструкцій викликає апаратне перехоплення VM Exit з відповідною причиною.

Усі такі перехоплення потрапляють у хостовий KVM (L0). Модуль `kvm_intel.ko` або `kvm_amd.ko` реалізує внутрішній інтерпретатор VMX/SVM, який перевіряє права виконання, стан прапорців CPUID та регістрів MSR, після чого оновлює програмний стан гостя:

- **Виконання `VMON` / `VMRUN` у L1:** KVM (L0) перевіряє, чи увімкнено підтримку вкладеності у гості. Якщо вкладеність дозволена, KVM виділяє внутрішню структуру `struct nested_vmx` (або `struct nested_svm`) всередині об'єкта `struct vcpu_vmx` в пам'яті ядра L0, встановлює прапорець `nested.vmxon = true` і повертає L1 успішний код виконання без виклику справжнього апаратного `VMON`.
- **Виконання `VMPTRLD` у L1:** L1 передає фізичну адресу структури управління (VMCS12) у своїй пам'яті. L0 зчитує цю адресу, відображає її у власний адресний простір ядра і робить її активною "поінтерною" VMCS12 для даного віртуального процесора.
- **Виконання `VMLAUNCH` / `VMRESUME` / `VMRUN` у L1:** Це найвідповідальніший крок. L1 намагається запустити вкладеного гостя L2. L0 перехоплює цей виклик, бере конфігурацію з VMCS12 (або VMCB12 у випадку AMD), яку підготував L1, поєднує її з власними обмеженнями з VMCS01 та будує реальну апаратну структуру **VMCS02** (або VMCB02). Після цього L0 завантажує VMCS02 у фізичний процесор і виконує справжню апаратну інструкцію `VMLAUNCH`/`VMRESUME`, перемикаючи CPU безпосередньо у виконання коду L2.

## 3. Оптимізація VMCS Shadowing та AMD VMCB Clean Bits

У ранніх реалізаціях вкладеної віртуалізації кожен запис або читання полів VMCS з боку L1 за допомогою інструкцій `VMREAD` та `VMWRITE` викликав обов'язковий VM Exit до L0. Оскільки будь-який гіпервізор перед запуском гостя оновлює десятки полів VMCS (регістри `CR0`/`CR3`/`CR4`, покажчик стека `RSP`, інструкційний покажчик `RIP`, селектори сегментів, контролери переривань), запуск L2 вимагав виконання тисяч послідовних VM Exits. Це створювало колосальні накладні витрати (overhead), роблячи продуктивність L2 непридатною для практичного використання.

Для усунення цієї проблеми компанія Intel запровадила апаратну технологію **VMCS Shadowing** (впроваджену у мікроархітектурі Haswell), а AMD реалізувала механізм **VMCB Clean Bits**.

![Оптимізація VMCS Shadowing](/reference/unix-linux/devices/nested-virtualization-kvm/img/vmcs-shadowing.svg)
*Оптимізація VMCS Shadowing: скорочення апаратних трапів до L0 під час модифікації полів VMCS.*

За наявності VMCS Shadowing процесор підтримує нове поле у VMCS01 — **VMCS Shadowing Bitmap** та покажчик на **Shadow VMCS** (Тіньовий VMCS). Коли L1 виконує інструкції `VMREAD` або `VMWRITE`, спрямовані на теневий VMCS:

1. Апаратне забезпечення процесора перевіряє маску доступу у Bitmap.
2. Якщо біт відповідного поля встановлено у `0` (дозволений прямий доступ), процесор виконує читання або запис безпосередньо у фізичну пам'ять Shadow VMCS **без викликання VM Exit**.
3. Якщо біт встановлено у `1` (критичне поле, таке як EPT Pointer або регістри контролю переривань), процесор генерує VM Exit, дозволяючи L0 проконтролювати зміни.

На архітектурі AMD-V замість двох окремих інструкцій читання/запису використовується суцільна структура VMCB у пам'яті. Щоб L0 не перевіряв усі 4 кілобайти VMCB12 при кожному виклику `VMRUN`, AMD запровадила біти чистих областей (**VMCB Clean Bits**). L1 встановлює відповідний біт у масці Clean Bits, якщо певна група регістрів (наприклад, сегментні регістри або CR0/CR4) не змінювалася з моменту останнього запуску. L0 зчитує цю маску і пропускає парсинг незмінених блоків, що знижує витрати на синхронізацію VMCB02 до мінімуму.

Завдяки VMCS Shadowing та VMCB Clean Bits кількість апаратних перехоплень під час підготовки та запуску L2 зменшується на 95–98%. L0 втручається лише під час остаточного виклику `VMLAUNCH`/`VMRESUME`/`VMRUN`, де виконує синхронізацію даних між Shadow VMCS12 та робочим VMCS02.

## 4. Двохрівнева трансляція пам'яті (Nested EPT / NPT)

Одним із найскладніших завдань у вкладеній віртуалізації є трансляція віртуальних адрес вкладеного гостя у фізичні адреси хоста. У традиційній віртуалізації трансляція є двокроковою:
`GVA (Guest Virtual) → GPA (Guest Physical) → HPA (Host Physical)`.

У вкладеній віртуалізації виникає трирівнева ієрархія адрес:
- **L2 GVA:** Віртуальна адреса всередині програми, що працює у L2.
- **L2 GPA:** Фізична адреса з точки зору L2 (яка є віртуальною фізичною адресою у L1).
- **L1 GPA:** Фізична адреса з точки зору L1 (яка є віртуальною фізичною адресою у L0).
- **L0 HPA:** Дійсна фізична адреса у мікросхемах оперативної пам'яті (DRAM) хоста.

Трансляція відбувається за такою схемою:
`L2 GVA → (Таблиці сторінок L2) → L2 GPA → (EPT12 у L1) → L1 GPA → (EPT01 у L0) → L0 HPA`.

![Маршрутизація EPT Violations та злиття EPT02 у KVM](/reference/unix-linux/devices/nested-virtualization-kvm/img/ept-routing.svg)
*Маршрутизація EPT Violations та побудова об'єднаного EPT02 у гіпервізорі KVM.*

Апаратний блок MMU процесора має лише один регістр `EPTP` (Extended Page Table Pointer) на Intel або `nCR3` на AMD, і не здатен апаратно проходити дві таблиці EPT/NPT послідовно. Щоб забезпечити виконання коду L2 з апаратною швидкістю, KVM у L0 будує **Тіньовий EPT (Shadow EPT, або EPT02)**, який відображає `L2 GPA → L0 HPA` напряму.

### Алгоритм злиття сторінок та обробка EPT Violations

Під час роботи L2 процесор використовує `EPTP02`, завантажений гіпервізором L0. Коли L2 звертається до сторінки пам'яті, якої немає в EPT02, виникає апаратне порушення **EPT Violation**, яке викликає VM Exit у L0:

1. **Аналіз причини:** L0 отримує фізичну адресу `L2 GPA`, яка спричинила помилку, та аналізує стан обох таблиць: `EPT12` (підготовленої L1) та `EPT01` (підготовленої L0).
2. **Сценарій А (Помилка на рівні L0):** Якщо запитаний мапінг `L1 GPA → L0 HPA` відсутній у `EPT01` (наприклад, сторінка пам'яті L1 була вивантажена хостом у swap або ще не була виділена за механізмом Copy-on-Write), L0 обробляє помилку самостійно. L0 виділяє хостову сторінку DRAM, оновлює `EPT01`, добудовує відповідний запис у `EPT02` і відновлює виконання L2. Гіпервізор L1 навіть не дізнається про цей випадок.
3. **Сценарій Б (Помилка на рівні L1):** Якщо мапінг `L2 GPA → L1 GPA` відсутній у таблиці `EPT12` (наприклад, L2 звертається до пам'яті, яку L1 ще не виділив для свого гостя), L0 не може вирішити це порушення самостійно. L0 формує синтетичне перехоплення VM Exit, записує причину `EXIT_REASON_EPT_VIOLATION` у VMCS12, перемикає стан VCPU на виконання L1 і передає управління обробнику EPT у ядрі L1. L1 виділяє пам'ять, оновлює `EPT12` і виконує `VMRESUME`. L0 перехоплює цей `VMRESUME`, оновлює `EPT02` і повертає процесор до виконання L2.

### EPT Misconfiguration проти EPT Violation

Важливо розрізняти `EPT Violation` та `EPT Misconfiguration`:
- **EPT Violation:** Аналог звичайного `#PF` (Page Fault). Сторінка відсутня у мапінгу або порушено права доступу (`R/W/X`).
- **EPT Misconfiguration:** Критична помилка структури EPT, коли у записі сторінки встановлено недопустиму комбінацію бітів (наприклад, непідтримуваний атрибут пам'яті Memory Type, такий як `UC` або `WB` у невідомій комбінації, або зарезервовані біти адреси). EPT Misconfiguration генерується апаратно і завжди свідчить про помилку у злитті полів VMCS02 чи EPT02 з боку ядра L0.

## 5. Злиття MSR-бітових масок та віртуалізація переривань

Окрім пам'яті та структур керування, KVM у L0 повинен коректно об'єднувати маски доступу до системних регістрів MSR (Model Specific Registers) та віртуалізувати APIC.

### Злиття масок MSR (MSR Bitmaps Merging)

Кожен процесор підтримує бітову маску MSR Bitmap, яка вказує, які регістри MSR викликають VM Exit при спробі їх читання (`RDMSR`) або запису (`WRMSR`). L0 має власну маску `msr_bitmap_l0`, а L1 формує маску `msr_bitmap_l1` у VMCS12.

Під час побудови VMCS02 KVM у L0 виконує побітову операцію OR:
`msr_bitmap_l02 = msr_bitmap_l0 | msr_bitmap_l1`.

Це означає, що якщо хоча б один із гіпервізорів (L0 або L1) побажав перехопити доступ до MSR (наприклад, до `IA32_TIME_STAMP_COUNTER` або `IA32_SYSENTER_EIP`), відповідна інструкція в L2 призведе до VM Exit у L0. Якщо ж обидва гіпервізори дозволили прямий доступ (наприклад, до регістрів `FS_BASE`/`GS_BASE`), L2 читає та пише MSR апаратно без втручання L0 чи L1.

### Віртуалізація переривань, APICv та Posted Interrupts

Управління перериваннями у вкладеній віртуалізації вимагає чіткого розмежування фізичних та віртуальних джерел сигналів:

- **Фізичні переривання (Hardware Interrupts):** Будь-яке фізичне переривання (від мережевої карти, NVMe-накопичувача або таймера хоста), що виникає під час виконання L2, викликає безумовний апаратний VM Exit до L0. L0 обробляє переривання у своєму контексті і, якщо воно не стосується гостя, повертає процесор у режим L2.
- **Впорскування переривань від L1 до L2:** Коли L1 хоче надіслати віртуальне переривання своєму гостю L2, він записує вектор переривання у VMCS12 і виконує `VMRESUME`. L0 під час створення VMCS02 зчитує ці поля та налаштовує апаратний механізм **Virtual Interrupt Delivery (APICv)**. Якщо апаратура підтримки APICv доступна, процесор впорскує переривання в L2 під час завантаження VMCS02 без додаткових програмних затримок.
- **Posted Interrupts у вкладеному режимі:** Сучасні процесори Intel підтримують механізм Posted Interrupts, який дозволяє L0 або апаратному пристрою (через VT-d) записувати вектор переривання безпосередньо у спеціальний буфер у пам'яті (Posted Interrupt Descriptor) та надсилати IPI-сигнал на фізичний CPU. Процесор під час виконання L2 перехоплює цей IPI і автоматично впорскує вектор у vAPIC L2 без викликання VM Exit.

За відсутності APICv KVM у L0 повинен емулювати віртуальний контролер APIC для L1, симулюючи вікна переривань (Interrupt Windows) та перехоплюючи доступи до сторінки APIC-access page.

## 6. Внутрішня механіка KVM: `vcpu_vmx_run` та `nested_vmx_reflect_vmexit`

У вихідному коді ядра Linux (модуль `arch/x86/kvm/vmx/nested.c`) ключовою структурою збереження стану вкладеності є `struct nested_vmx`. Вона містить покажчики на `vmcs12`, теневі сторінки EPT02, маски перехоплення MSR та стан віртуального VMX.

Головний цикл виконання VCPU у KVM проходить через функцію `vcpu_vmx_run()`. При активованій вкладеності потік обробки має таку послідовність:

```
[ L1 викликає VMLAUNCH / VMRESUME ]
         │
         ▼
 1. vmx_handle_exit() у L0
         │
         ▼
 2. handle_vmlaunch() / handle_vmresume()
         │
         ▼
 3. nested_vmx_run()
    ├── Перевірка лімітів та полів у VMCS12
    ├── prepare_vmcs02()  <-- Злиття VMCS01 + VMCS12
    └── nested_ept_init_mmu_context() <-- Побудова EPT02
         │
         ▼
 4. vcpu_enter_guest() --> Фізичний VMLAUNCH (Виконання L2)
         │
         ▼ (Апаратний VM Exit під час роботи L2)
 5. vmx_handle_exit() у L0
         │
         ▼
 6. nested_vmx_reflect_vmexit()
    ├── Якщо Exit призначений для L0 --> обробка в KVM L0
    └── Якщо Exit призначений для L1 --> nested_vmx_vmexit()
                                          ├── Збереження стану L2 у VMCS12
                                          └── Завантаження VMCS01 (Повернення в L1)
```

Перевірка призначення VM Exit у функції `nested_vmx_reflect_vmexit()` здійснюється на основі бітових масок `vmcs12->exception_bitmap`, `vmcs12->cpu_based_vm_exec_control` та аналізу причин виходу. Якщо L1 запросив перехоплення конкретної події (наприклад, виклику `cpuid` або винятку `#PF`), L0 "відображає" (reflects) це перехоплення у L1, роблячи вигляд, що воно сталося безпосередньо на апаратурі.

Приклад взаємодії з KVM через інтерфейс `ioctl` для перевірки можливостей вкладеності зі сторони простору користувача розібрано у [проєктному прикладі перевірки та прокидання VMX через ioctl](book:unix-linux/nested-virtualization-kvm/proj-kvm-nested-control-and-ioctl.md).

## 7. Жива міграція вкладених ВМ (Nested Live Migration)

Перенесення віртуальної машини L1 разом із запущеними всередині неї вкладеними ВМ L2 на інший фізичний хост L0 є складною інженерною задачею. Для успішної міграції KVM повинен серіалізувати не лише стан віртуальних регістрів процесора L1, а й весь внутрішній стан вкладеності `struct nested_vmx`.

Ця можливість з'явилася в ядрі Linux завдяки додаванню двох спеціальних системних викликів `ioctl` на рівні VCPU:

- `KVM_GET_NESTED_STATE`: L0 дамплює вміст активного `VMCS12`, прапорці `VMXON`, накопичені EPT-карти та стан Shadow VMCS у бінарну структуру `struct kvm_nested_state`.
- `KVM_SET_NESTED_STATE`: Під час відновлення ВМ на цільовому хості демони управління (QEMU або libvirt) передають структуру `kvm_nested_state` цільовому ядру L0. L0 відновлює контекст VMX, реконструює VMCS02 та EPT02, після чого ВМ L1 відновлює виконання коду L2 без обриву мережевих з'єднань або збоїв вкладених операційних систем.

## 8. Конфігурування та діагностика в Linux

За замовчуванням у багатьох дистрибутивах Linux модуль ядра `kvm_intel` або `kvm_amd` може мати вимкнену або обмежену вкладену віртуалізацію.

### Перевірка та активація вкладеності

Для перевірки поточного стану модуля на процесорах Intel виконують читання з sysfs:

```bash
cat /sys/module/kvm_intel/parameters/nested
```

Для процесорів AMD відповідний шлях:

```bash
cat /sys/module/kvm_amd/parameters/nested
```

Повернення `Y` або `1` свідчить про увімкнений режим nested. Якщо параметр дорівнює `N` або `0`, його можна ввімкнути під час завантаження модуля.

Динамічне перезавантаження модуля на хості (вимагає зупинки всіх працюючих ВМ):

```bash
modprobe -r kvm_intel
modprobe kvm_intel nested=1
```

Для постійного увімкнення створюють конфігураційний файл `/etc/modprobe.d/kvm.conf`:

```text
options kvm_intel nested=1
options kvm_amd nested=1
```

> 🔧 **Навіщо це.** Простого ввімкнення `nested=1` на хості L0 недостатньо для того, щоб ВМ L1 могла запускати гостей L2. Гіпервізор L0 повинен явним чином прокинути прапорці VMX/SVM у підсистему CPUID віртуальної машини L1. У QEMU це досягається передачею прапорця `-cpu host` або конфігурацією libvirt `<cpu mode='host-passthrough'/>`. Якщо прокинути абстрактну модель CPU без прапорця `vmx`/`svm`, ядро L1 розпізнає відсутність апаратних інструкцій і модуль `kvm_intel` у L1 відмовиться завантажуватися.

Детальні таблиці параметрів sysfs, регістрів MSR та подій tracepoints зібрано у [довіднику точок керування sysfs, MSR-регістрів та tracepoints](book:unix-linux/nested-virtualization-kvm/api-kvm-nested-sysfs-and-msr.md).

## 9. Безпека, вектори атак та ціна продуктивності

Незважаючи на апаратне прискорення, вкладена віртуалізація впроваджує специфічні накладні витрати та нові вектори загроз.

### Ціна продуктивності (Overhead)

Основою сповільнення у L2 є мультиплікація апаратних VM Exits:

1. **Затримка обробки перехоплення (Exit Latency):** Якщо у звичайній віртуалізації L1 VM Exit обробляється за сотні тактів процесора, то L2 VM Exit, який потребує відображення у L1 (reflection), проходить через подвійний контекстний перемикач: `L2 → L0 → L1 → L0 → L2`. Це збільшує затримку у 3–5 разів.
2. **Деградація кешів MMU (TLB Flushes):** Часті зміни `EPTP` між `EPTP01` та `EPTP02` призводять до скидання записів у кеші трансляції буфера сторінок (TLB), якщо процесор або гіпервізор не використовують тегування VPID (Virtual Processor ID).

### Вектори атак та ізоляція

Вкладена віртуалізація значно розширює поверхню атаки ядра L0:

- **Помилки синхронізації EPT02 / Shadow VMCS:** Складність алгоритмів злиття у `nested.c` історично ставала джерелом уразливостей типу Kernel Memory Corruption та Host Escape, коли скомпрометований гість L1 міг маніпулювати полями VMCS12 для виходу з ізоляції в L0.
- **Спекулятивні атаки (Spectre / Meltdown / L1TF):** У вкладеному середовищі межі ізоляції між L2 та L1 можуть протікати через спільні процесорні кеші та мікроархітектурні буфери. Виконання L2 вимагає обов'язкового застосування загороджень `IBPB` (Indirect Branch Predictor Barrier) та очищення кешів L1D під час перемикання контекстів між L1 та L2.

З міркувань безпеки багато публічних хмарних провайдерів вимикають вкладену віртуалізацію на загальних екземплярах віртуальних машин або надають її лише на виділених фізичних серверах (Bare-Metal).

## 10. Синтез

Вкладена віртуалізація у KVM — це архітектурно зрілий механізм, який трансформує жорсткі дворевневі апаратні обмеження x86_64 у гнучку програмно-апаратну ієрархію. Завдяки технологіям Intel VMCS Shadowing, AMD VMCB Clean Bits та динамічному злиттю EPT02 підсистема KVM досягає високої продуктивності виконання вкладених ВМ. Розуміння точок маршрутизації перехоплень `nested_vmx_reflect_vmexit`, механізмів EPT Violations та серіалізації `kvm_nested_state` є критичним для проектування захищених інфраструктур, високопродуктивних тестових середовищ та сучасних систем контейнеризації на основі мікровіртуальних машин.
