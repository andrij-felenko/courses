# 📋 Інтерфейс випадковості: виклик, файли, ioctl і параметри ядра

Тут зібрано весь контракт підсистеми випадковості Linux — підпис системного виклику, прапорці, помилки, операції `ioctl`, файли в `/proc`, параметри завантаження й виклики всередині ядра, — а наприкінці окремим списком те, що в чинних довідниках уже неправда. Останнє важить не менше за перше: сторінки `random(4)` і `getrandom(2)` подекуди досі описують ядро, якого немає з 2020 року, і саме звідти беруться найживучіші помилки в чужому коді.

## Системний виклик

```c
#include <sys/random.h>

ssize_t getrandom(void *buf, size_t buflen, unsigned int flags);
```

Повертає кількість записаних байтів — вона може бути меншою за `buflen`. За помилки повертає `-1` і виставляє `errno`.

**Прапорці** (визначені в `<linux/random.h>`, доступні через `<sys/random.h>`):

| Прапорець | Біт | З версії | Дія |
| --- | --- | --- | --- |
| `GRND_NONBLOCK` | `0x0001` | 3.17 | не чекати готовності генератора: якщо він ще не готовий — негайно `-1`/`EAGAIN` |
| `GRND_RANDOM` | `0x0002` | 3.17 | нічого не змінює; лишений заради сумісності зі старим кодом |
| `GRND_INSECURE` | `0x0004` | 5.6 | віддати байти негайно, навіть до готовності; для ключів вони не годяться |

Ядро судить прапорці двома правилами. Будь-який невідомий біт — `EINVAL`. `GRND_INSECURE` разом із `GRND_RANDOM` — теж `EINVAL`, бо вимоги «дай хоч що-небудь одразу» і «дай найякісніше» суперечать одна одній. Пара `GRND_NONBLOCK | GRND_INSECURE` законна, але беззмістовна: з `GRND_INSECURE` виклик не чекає ніколи, тож і скасовувати нічого.

**Помилки:**

| `errno` | Коли трапляється |
| --- | --- |
| `EAGAIN` | генератор ще не готовий, а стояв `GRND_NONBLOCK` |
| `EINTR` | очікування готовності перервав [сигнал](book:unix-linux/signal-model) |
| `EFAULT` | `buf` указує поза доступною процесові пам'яттю |
| `EINVAL` | невідомий біт у `flags` або заборонена пара прапорців |
| `ENOSYS` | ядро старіше за 3.17 — виклику просто немає |

**Гарантія на 256 байтів.** Якщо генератор готовий, запит на 256 байтів або менше повертає всі замовлені байти й не переривається сигналом. Це єдина обіцянка щодо повноти видачі, і саме на ній тримається `getentropy`, чия стеля — рівно ті самі 256. Довший запит вимагає циклу: часткова видача законна.

Сучасне ядро насправді щедріше — воно перевіряє наявність сигналу лише на межі сторінки, тобто не рве й чотирикілобайтового читання. Але писати код під це не можна: обіцяно 256, а обіцянка діє на всіх версіях.

**Стелі довжини.** Давня реалізація обмежувала одне читання 32 МіБ − 1 байт для джерела `urandom` і 512 байтами для `random`; ці числа й досі стоять у `getrandom(2)`. У переписаній підсистемі окремої стелі в самому виклику немає — довжину затискає спільний ліміт read-подібних шляхів ядра. Практичної різниці це не робить: правильний код усе одно циклить за поверненим значенням.

**vDSO.** З Linux 6.11 ядро подає `__vdso_getrandom` — ту саму видачу без переходу в ядро, через [vDSO](book:unix-linux/vdso). Інтерфейс має додаткові аргументи для непрозорого стану потоку (`struct vgetrandom_opaque_params`) і призначений реалізаціям libc, а не прикладному кодові: прикладна програма викликає звичайний `getrandom` і дістає прискорення тоді, коли її libc уміє.

## Обгортки libc

| Функція | Заголовок | З glibc | Контракт |
| --- | --- | --- | --- |
| `ssize_t getrandom(void *buf, size_t buflen, unsigned int flags)` | `<sys/random.h>` | 2.25 | тонка обгортка над викликом: часткову видачу й `EINTR` віддає програмі як є |
| `int getentropy(void *buffer, size_t length)` | `<unistd.h>` | 2.25 | `length` ≤ 256, інакше `-1`/`EIO`; повертає `0` або `-1` — часткового результату не буває; чекає готовності й **не** повертається через сигнал |

Різниця між ними суто в тому, хто пише цикл. `getentropy` бере його на себе ціною жорсткої стелі й неможливості не чекати; `getrandom` лишає всі важелі, разом з обов'язком їх правильно смикнути.

Найкоротший коректний виклик, що дає ключ на 32 байти:

```c
#include <sys/random.h>
#include <errno.h>
#include <stdint.h>

uint8_t key[32];
ssize_t n;

do {
	n = getrandom(key, sizeof key, 0);   /* 0 — почекати готовності, далі не чекати */
} while (n < 0 && errno == EINTR);

if (n != (ssize_t)sizeof key)
	fatal();   /* лишилися тільки ENOSYS (ядро < 3.17) і EFAULT — обидві невиправні */
```

Порівняння `n` із повною довжиною тут не перестраховка, а перевірка контракту: для 32 байтів коротша видача неможлива, тож будь-яке інше число означає, що припущення про систему не справдилося.

## Файли пристроїв

| Файл | Тип | Старший | Молодший | Типові права |
| --- | --- | --- | --- | --- |
| `/dev/random` | символьний | 1 | 8 | `0666 root:root` |
| `/dev/urandom` | символьний | 1 | 9 | `0666 root:root` |

Створюються, якщо `/dev` доводиться заповнювати вручну ([старший і молодший номери](book:unix-linux/major-minor-numbers)):

```sh
mknod -m 666 /dev/random  c 1 8
mknod -m 666 /dev/urandom c 1 9
chown root:root /dev/random /dev/urandom
```

Операції над відкритим дескриптором:

| Операція | `/dev/urandom` | `/dev/random` |
| --- | --- | --- |
| `read` | ніколи не чекає; до готовності генератора видає передбачні байти й пише попередження в журнал ядра | чекає рівно одного — першого засівання генератора; після того тотожний сусідові |
| `write` | домішує подані байти до накопичувача, **не** збільшуючи заліку; дозволено всім | так само |
| `lseek` | вдається й нічого не міняє — позиції в потоці немає | так само |
| `poll` | не підтримується | до готовності показує готовність до **запису** (запрошення підсипати), після готовності — до читання |
| `O_NONBLOCK` | ніколи нічого не значив | діє лише на очікування першого засівання: до готовності читання одразу повертає `EAGAIN` замість того, щоб чекати |

## Керування через ioctl

Операції подаються на дескриптор будь-якого з двох файлів ([керуючий канал до драйвера](book:unix-linux/ioctl-interface)), номери — з `<linux/random.h>`.

| Запит | Код | Аргумент | Права | Дія |
| --- | --- | --- | --- | --- |
| `RNDGETENTCNT` | `_IOR('R', 0x00, int)` | `int *` | будь-хто | читає оцінку зібраного в бітах — те саме число, що в `entropy_avail` |
| `RNDADDTOENTCNT` | `_IOW('R', 0x01, int)` | `int *` | `CAP_SYS_ADMIN` | додає до заліку задане число бітів, не подаючи жодного байта; від'ємне значення — `EINVAL` |
| `RNDADDENTROPY` | `_IOW('R', 0x03, struct rand_pool_info)` | структура | `CAP_SYS_ADMIN` | домішує байти **й одночасно збільшує залік** |
| `RNDZAPENTCNT` | `_IO('R', 0x04)` | — | `CAP_SYS_ADMIN` | історично обнуляв лічильник; сьогодні успішно повертається, не роблячи нічого |
| `RNDCLEARPOOL` | `_IO('R', 0x06)` | — | `CAP_SYS_ADMIN` | те саме: прийнято до відома, наслідків немає |
| `RNDRESEEDCRNG` | `_IO('R', 0x07)` | — | `CAP_SYS_ADMIN` | негайно перезаряджає ключ генератора з накопичувача; `ENODATA`, якщо генератор ще не готовий |
| `RNDGETPOOL` | `0x02` | — | — | вилучено ще в 2.6.9; ядро його не знає |

Без потрібного [повноваження](book:unix-linux/capabilities) все, крім `RNDGETENTCNT`, повертає `EPERM`. Розділення тут не формальне: звичайний `write` дозволено всім, бо домішування нікому не шкодить, а от `RNDADDENTROPY` — це ще й заява «тут стільки-то справжньої невідомості», і брехлива заява робить систему беззахисною.

```c
struct rand_pool_info {
	int   entropy_count;   /* БІТИ: скільки зарахувати */
	int   buf_size;        /* БАЙТИ: скільки їх у buf */
	__u32 buf[];
};
```

Різні одиниці в сусідніх полях — класична пастка цього інтерфейсу. Так виглядає подача 32 байтів від апаратного джерела із заявою на повні 256 бітів (саме це в циклі робить служба `rngd`):

```c
#include <linux/random.h>
#include <sys/ioctl.h>
#include <fcntl.h>
#include <string.h>

struct {
	struct rand_pool_info hdr;
	unsigned char data[32];
} req;

memcpy(req.data, from_hwrng, sizeof req.data);
req.hdr.entropy_count = 8 * sizeof req.data;   /* 256 бітів */
req.hdr.buf_size      = sizeof req.data;       /* 32 байти  */

int fd = open("/dev/urandom", O_WRONLY);
if (ioctl(fd, RNDADDENTROPY, &req) < 0)
	perror("RNDADDENTROPY");                   /* EPERM — немає CAP_SYS_ADMIN */
```

Прибрати звідси `ioctl` і лишити самий `write(fd, req.data, sizeof req.data)` — і байти так само потраплять до накопичувача, просто без заліку. Уся відмінність саме в цьому слові.

## Каталог /proc/sys/kernel/random

Спостереження й дрібні важелі — через [sysctl](book:unix-linux/sysctl-tunables).

| Файл | Режим | Що там сьогодні |
| --- | --- | --- |
| `poolsize` | `r` | `256` — розмір накопичувача в бітах після переписування підсистеми у 2022 році (раніше `4096`) |
| `entropy_avail` | `r` | оцінка зібраного в бітах зі стелею `256`; досягнення стелі й означає, що генератор готовий |
| `write_wakeup_threshold` | `rw` | залишок блокувального минулого; запис ядро мовчки поглинає, поведінки він не міняє |
| `urandom_min_reseed_secs` | `rw` | так само: значення читається, запис не має наслідків |
| `boot_id` | `r` | випадковий UUID, сталий до наступного завантаження |
| `uuid` | `r` | новий випадковий UUID на **кожне** читання |

## Параметри командного рядка ядра

| Параметр | Значення | Що вмикає |
| --- | --- | --- |
| `random.trust_cpu=0\|1` | типово `1` | чи зараховувати насіння від інструкції процесора (`RDRAND`/`RDSEED`) |
| `random.trust_bootloader=0\|1` | типово `1` | чи зараховувати насіння від прошивки чи завантажувача (протокол EFI RNG, вузол `rng-seed` у дереві пристроїв) |

Вимкнення довіри не означає відмови від джерела: недовірене насіння однаково домішують до накопичувача, просто без заліку — тобто воно не наближає готовності генератора. Збірні опції `CONFIG_RANDOM_TRUST_CPU` і `CONFIG_RANDOM_TRUST_BOOTLOADER` (обидві з типовим `y`) існували по 6.1 включно; у 6.2 їх прибрали, і єдиним важелем лишився командний рядок.

## Виклики всередині ядра

Драйвер чи підсистема не ходять через файли — для них є прямий набір:

| Виклик | Контекст | Поведінка |
| --- | --- | --- |
| `void get_random_bytes(void *buf, size_t len)` | будь-який, зокрема обробник переривання | ніколи не чекає; до готовності генератора віддає передбачне |
| `u8/u16/u32/u64 get_random_uN(void)` | будь-який | те саме, але дешевше: на кожному ядрі процесора лежить наперед породжений блок |
| `unsigned long get_random_long(void)` | будь-який | розрядність за архітектурою |
| `u32 get_random_u32_below(u32 ceil)` | будь-який | рівномірне число з `[0, ceil)` без хиби, яку дає звичайний остача-від-ділення |
| `u32 get_random_u32_above(u32 floor)`, `..._inclusive(floor, ceil)` | будь-який | те саме для інших меж діапазону |
| `bool rng_is_initialized(void)` | будь-який | чи готовий генератор — без очікування |
| `int wait_for_random_bytes(void)` | тільки там, де можна спати | чекає готовності; `0` або `-ERESTARTSYS` |
| `int get_random_bytes_wait(void *buf, size_t len)` | тільки там, де можна спати | пара попередніх одним викликом |
| `void add_device_randomness(const void *buf, size_t len)` | будь-який | домішати без заліку — для ідентифікаторів заліза |
| `void add_hwgenerator_randomness(const void *buf, size_t len, size_t entropy, bool sleep_after)` | процесний | вхід для драйверів апаратних генераторів, із заліком |
| `void add_bootloader_randomness(const void *buf, size_t len)` | ранній старт | насіння від завантажувача; залік — за `random.trust_bootloader` |

Поділ у другому стовпчику — головне, що звідси треба винести. `get_random_bytes` безпечно кликати звідусіль саме тому, що він не чекає; тому ж і рання його видача може виявитися передбачною, і код, якому потрібна справжня непередбачність на старті, мусить спершу пройти `wait_for_random_bytes`.

## Що в довідниках уже неправда

| Твердження | Де трапляється | Як насправді |
| --- | --- | --- |
| «`poolsize` — 4096 бітів», «`entropy_avail` від 0 до 4096» | `random(4)` | накопичувач — 256 бітів, стеля лічильника теж 256 |
| «`read_wakeup_threshold` — скільки бітів чекати читачам» | `random(4)` | файл зник разом із блокувальним пулом у 5.6 |
| «`/dev/random` блокує, поки не набереться ентропії» | безліч посібників | з 5.6 чекає лише першого засівання генератора |
| «`GRND_RANDOM` бере з іншого, кращого джерела» | `getrandom(2)` | джерело одне; біт не робить нічого |
| «стеля читання — 32 МіБ − 1 або 512 байтів» | `getrandom(2)` | числа давньої реалізації; сьогодні окремої стелі у виклику немає |
| «`RNDZAPENTCNT` обнуляє лічильник» | `random(4)` | разом із `RNDCLEARPOOL` приймається й нічого не робить |
| «для ключів беріть `/dev/random`, для дрібниць `/dev/urandom`» | посібники, HOWTO | обидва файли — та сама видача того самого генератора |
