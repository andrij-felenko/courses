# 📋 Інтерфейс v4l2-mem2mem: структури, зворотні виклики та операції

Каркас `v4l2-mem2mem` (Memory-to-Memory) у ядрі Linux уніфікує драйвери апаратних блоків, що не взаємодіють із фізичними зовнішніми інтерфейсами, а виконують трансформацію даних між буферами оперативної пам'яті. До цього класу належать апаратні відеодекодери, енкодери, двовимірні масштабувачі, деінтерлейсери, перетворювачі колірних просторів і модулі JPEG. Інтерфейс підсистеми поділяється на дві частини: внутрішній каркас ядра (`<media/v4l2-mem2mem.h>`) для побудови драйверів і набір команд `ioctl`, структур та подій користувацького простору V4L2 UAPI (`<linux/videodev2.h>`).

## Структури та реєстрація екземплярів ядра

Головною абстракцією пристрою на рівні драйвера є глобальний дескриптор апаратного контролера `struct v4l2_m2m_dev`. Він створюється під час ініціалізації модуля в єдиному екземплярі на весь фізичний кремнієвий блок і керує спільною чергою завдань `job_queue`.

Контекст сеансу `struct v4l2_m2m_ctx` створюється динамічно при кожному відкритті файлового вузла `/dev/videoX` і знищується при закритті дескриптора. Контекст інкапсулює стан взаємодії з конкретним процесом, включно з двома чергами `vb2_queue` та локальними параметрами формату.

```c
#include <media/v4l2-mem2mem.h>

struct v4l2_m2m_ops {
    void (*device_run)(void *priv);
    int  (*job_ready)(void *priv);
    void (*job_abort)(void *priv);
};

/* Ініціалізація глобального диспетчера завдань пристрою M2M */
struct v4l2_m2m_dev *v4l2_m2m_init(const struct v4l2_m2m_ops *m2m_ops);

/* Звільнення ресурсів диспетчера під час вивантаження драйвера */
void v4l2_m2m_release(struct v4l2_m2m_dev *m2m_dev);

/* Створення контексту для відкритого файлового дескриптора */
struct v4l2_m2m_ctx *v4l2_m2m_ctx_init(
    struct v4l2_m2m_dev *m2m_dev,
    void *drv_priv,
    int (*queue_init)(void *priv, struct vb2_queue *src_vq, struct vb2_queue *dst_vq));

/* Знищення контексту при закритті дескриптора файлу */
void v4l2_m2m_ctx_release(struct v4l2_m2m_ctx *m2m_ctx);
```

### Таблиця операцій `struct v4l2_m2m_ops`

Драйвер реєструє набір функцій зворотного виклику, які планувальник M2M викликає для керування апаратурою:

* **`device_run(void *priv)`** — головний робочий виклик. Викликається ядром тоді, коли планувальник обрав цей контекст для виконання, а в обох чергах є готові буфери. Драйвер витягує покажчики на вхідний і вихідний буфери, програмує базові адреси регістрів DMA в апаратуру, запускає апаратний блок і негайно повертає керування. Будь-які блокування або очікування всередині `device_run` суворо заборонені.
* **`job_ready(void *priv)`** — необов'язковий предикат готовності. Якщо функцію не визначено, планувальник вважає контекст готовим за наявності щонайменше одного буфера в черзі `OUTPUT` та одного в черзі `CAPTURE`. Якщо апаратурі потрібно кілька вхідних буферів або специфічний стан декодера, драйвер повертає `1` (готовий) або `0` (очікувати).
* **`job_abort(void *priv)`** — виклик скасування. Викликається ядром, коли процес викликає `STREAMOFF` або несподівано закриває дескриптор під час активної апаратної обробки. Драйвер повинен подати апаратну команду зупинки або дочекатися найближчого переривання, не допускаючи зависання чипа.

## Ініціалізація черг `vb2_queue` у функції `queue_init`

Функція зворотного виклику `queue_init` налаштовує обидві черги `videobuf2` під час створення контексту. Драйвер конфігурує типи підтримуваної пам'яті, операції пам'яті (DMA contig для фізично суцільної пам'яті або DMA SG для розсіяної пам'яті через IOMMU) та блокування.

```c
static int queue_init(void *priv, struct vb2_queue *src_vq, struct vb2_queue *dst_vq) {
    struct my_ctx *ctx = priv;
    int ret;

    /* 1. Налаштування вхідної черги (OUTPUT) */
    src_vq->type = V4L2_BUF_TYPE_VIDEO_OUTPUT_MPLANE;
    src_vq->io_modes = VB2_MMAP | VB2_DMABUF;
    src_vq->drv_priv = ctx;
    src_vq->buf_struct_size = sizeof(struct v4l2_m2m_buffer);
    src_vq->ops = &my_qops;
    src_vq->mem_ops = &vb2_dma_contig_memops;
    src_vq->timestamp_flags = V4L2_BUF_FLAG_TIMESTAMP_COPY;
    src_vq->lock = &ctx->q_lock;
    src_vq->dev = ctx->dev->dev;
    ret = vb2_queue_init(src_vq);
    if (ret)
        return ret;

    /* 2. Налаштування вихідної черги (CAPTURE) */
    dst_vq->type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE;
    dst_vq->io_modes = VB2_MMAP | VB2_DMABUF;
    dst_vq->drv_priv = ctx;
    dst_vq->buf_struct_size = sizeof(struct v4l2_m2m_buffer);
    dst_vq->ops = &my_qops;
    dst_vq->mem_ops = &vb2_dma_contig_memops;
    dst_vq->timestamp_flags = V4L2_BUF_FLAG_TIMESTAMP_COPY;
    dst_vq->lock = &ctx->q_lock;
    dst_vq->dev = ctx->dev->dev;
    return vb2_queue_init(dst_vq);
}
```

Прапорець `V4L2_BUF_FLAG_TIMESTAMP_COPY` вмикає автоматичне копіювання часових міток із вхідного буфера у вихідний силами підсистеми `videobuf2`.

## Диспетчеризація завдань: `v4l2_m2m_try_schedule`

Внутрішній механізм планування M2M базується на атомарному автоматі станів. Коли користувацький простір викликає `VIDIOC_QBUF` на будь-якій із черг, ядро викликає функцію `v4l2_m2m_try_schedule(ctx)`.

Алгоритм планувальника виконує такі перевірки:
1. Перевіряє, чи не встановлено прапорець `M2M_SCHEDULED` для поточного контексту (контекст уже стоїть у черзі або виконується).
2. Перевіряє, чи активні обидва потоки (`STREAMON` на черзі `OUTPUT` та `STREAMON` на черзі `CAPTURE`).
3. Викликає предикат `ops->job_ready(ctx)` (або перевіряє наявність буферів у списках `rdy_queue` обох черг за замовчуванням).
4. Якщо всі умови виконано, контекст додається до списку `job_queue` пристрою, і планувальник намагається захопити м'ютекс апаратного блоку `m2m_dev->job_spinlock`.
5. Якщо апаратний блок вільний, планувальник викликає `ops->device_run(ctx)` у контексті потоку ядра або відкладеного обробника tasklet.

## Допоміжні функції керування буферами

Під час роботи `device_run` та обробника апаратного переривання драйвер використовує спеціальні допоміжні підпрограми для навігації чергами та фіксації результатів:

```c
/* Отримання покажчика на наступний готовий буфер у черзі */
struct vb2_v4l2_buffer *v4l2_m2m_next_src_buf(struct v4l2_m2m_ctx *m2m_ctx);
struct vb2_v4l2_buffer *v4l2_m2m_next_dst_buf(struct v4l2_m2m_ctx *m2m_ctx);

/* Вилучення буфера зі списку очікування (перехід у стан обробки апаратурою) */
struct vb2_v4l2_buffer *v4l2_m2m_src_buf_remove(struct v4l2_m2m_ctx *m2m_ctx);
struct vb2_v4l2_buffer *v4l2_m2m_dst_buf_remove(struct v4l2_m2m_ctx *m2m_ctx);

/* Перенесення метаданих (часова мітка, flags, timecode) між буферами */
void v4l2_m2m_buf_copy_metadata(const struct vb2_v4l2_buffer *out_vb,
                                struct vb2_v4l2_buffer *cap_vb,
                                bool copy_frame_types);

/* Завершення обробки буфера в ISR/Tasklet */
void v4l2_m2m_buf_done(struct vb2_v4l2_buffer *vbuf, enum vb2_buffer_state state);

/* Фіналізація поточного завдання та запуск наступного */
void v4l2_m2m_job_finish(struct v4l2_m2m_dev *m2m_dev, struct v4l2_m2m_ctx *m2m_ctx);
```

### Стани буфера `enum vb2_buffer_state`

* `VB2_BUF_STATE_DONE` — операція завершена успішно. Буфер переходить у чергу готових даних, де очікує виклику `VIDIOC_DQBUF` від користувацького простору.
* `VB2_BUF_STATE_ERROR` — апаратний збій або пошкодження даних. Буфер повертається додатку з прапорцем `V4L2_BUF_FLAG_ERROR`.
* `VB2_BUF_STATE_QUEUED` — буфер зареєстровано в підсистемі, але він ще не передавався на виконання контролеру DMA.
* `VB2_BUF_STATE_ACTIVE` — буфер обробляється апаратурою в поточний момент.

Структура `struct v4l2_m2m_buffer` є стандартною обгорткою, яка об'єднує базовий об'єкт буфера `struct vb2_v4l2_buffer` та службові покажчики списку ядра `struct list_head list`. Завдяки цьому буфери M2M можуть одночасно перебувати в черзі `videobuf2` та у внутрішньому списку готових робіт драйвера без додаткових динамічних виділень пам'яті на гарячому шляху обробки кадру.

## Користувацький простір: типи черг та багатоплощинні формати

Користувацький простір адресує черги M2M-пристрою через єдиний дескриптор. Вибір черги задається полем `type` у структурах команд:

```c
#include <linux/videodev2.h>

/* Одноплощинні типи буферів */
#define V4L2_BUF_TYPE_VIDEO_CAPTURE        1  /* Вихід оброблених даних з ядра */
#define V4L2_BUF_TYPE_VIDEO_OUTPUT         2  /* Вхід необроблених даних у ядро */

/* Багатоплощинні типи (для неперервних площин Y та UV) */
#define V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE 9
#define V4L2_BUF_TYPE_VIDEO_OUTPUT_MPLANE  10
```

Для багатоплощинного API використовується структура `struct v4l2_pix_format_mplane`, де кожна площина описується окремим записом у масиві `plane_fmt`:

```c
struct v4l2_format fmt = {
    .type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE,
    .fmt.pix_mp = {
        .width = 1920,
        .height = 1080,
        .pixelformat = V4L2_PIX_FMT_NV12M,
        .num_planes = 2,
        .plane_fmt[0] = { .sizeimage = 1920 * 1080, .bytesperline = 1920 },
        .plane_fmt[1] = { .sizeimage = 1920 * 540,  .bytesperline = 1920 },
    },
};
ioctl(fd, VIDIOC_S_FMT, &fmt);
```

## Узгодження форматів: `VIDIOC_TRY_FMT` проти `VIDIOC_S_FMT`

При конфігурації параметрів відеопотоку додаток повинен дотримуватися суворого правила двох фаз:

1. **Фаза зондування (`VIDIOC_TRY_FMT`):** Додаток передає бажані параметри роздільності та формату пікселів. Драйвер округлює значення до підтримуваних апаратурою меж (наприклад, округлює ширину до найближчого числа, кратного 16), обчислює розмір кадру `sizeimage` та повертає скориговану структуру, **не змінюючи** внутрішній стан черги.
2. **Фаза фіксації (`VIDIOC_S_FMT`):** Застосовує перевірений формат до активної черги пристрою. Виклик `VIDIOC_S_FMT` дозволений лише тоді, коли черга не перебуває в стані активного потоку (`STREAMON`), і на ній не виділено буфери через `REQBUFS`.

Якщо програма спробує змінити формат під час активного потоку даних або наявності виділених буферів, ядро поверне помилку `-EBUSY`.

## Вибір прямокутників обробки: Selection API

Масштабування, позиціювання та обтинання кадрів конфігуруються за допомогою системного виклику `VIDIOC_S_SELECTION`:

| Мішень вибору (Target) | Тип черги | Призначення |
|---|---|---|
| `V4L2_SEL_TGT_CROP` | `OUTPUT` | Прямокутник вирізання з вхідного зображення перед масштабуванням |
| `V4L2_SEL_TGT_CROP_BOUNDS` | `OUTPUT` | Максимально дозволені апаратні межі вхідного кадру |
| `V4L2_SEL_TGT_COMPOSE` | `CAPTURE` | Прямокутник запису масштабованого результату у вихідний буфер |
| `V4L2_SEL_TGT_COMPOSE_BOUNDS` | `CAPTURE` | Максимальний розмір полотна вихідного кадру |

Прапорці `V4L2_SEL_FLAG_GE` (більше або дорівнює) та `V4L2_SEL_FLAG_LE` (менше або дорівнює) вказують драйверу напрямок округлення розмірів, якщо апаратура вимагає кратності блоків (наприклад, вирівнювання ширини по 16 або 32 пікселі).

## Події та команди керування потоком кодеків

Для асинхронного керування кодеками V4L2 визначає команди скидання конвеєра та механізм підписки на події:

```c
/* Команда завершення потоку (Drain / EOS) */
#define VIDIOC_DECODER_CMD               _IOWR('V', 96, struct v4l2_decoder_cmd)
#define V4L2_DEC_CMD_STOP                1
#define V4L2_DEC_CMD_START               2
#define V4L2_DEC_CMD_PAUSE               3
#define V4L2_DEC_CMD_RESUME              4
#define V4L2_DEC_CMD_FLUSH               5

/* Подія зміни роздільності потоку (DRC) */
#define V4L2_EVENT_SOURCE_CHANGE         5
#define V4L2_EVENT_SRC_CH_RESOLUTION     (1 << 0)

/* Підписка на подію */
struct v4l2_event_subscription sub = {
    .type = V4L2_EVENT_SOURCE_CHANGE,
};
ioctl(fd, VIDIOC_SUBSCRIBE_EVENT, &sub);
```

Коли настає подія зміни роздільності або вичерпання потоку, дескриптор сигналізує подію `POLLPRI`. Додаток зчитує детальну інформацію через `VIDIOC_DQEVENT`.

## Діагностика та трасування

Стан черг M2M-пристрою, виділені буфери та події планувальника доступні для динамічного інспектування через інтерфейси `sysfs` та `dynamic_debug`:

```
# Увімкнення докладного трасування ядра для модуля v4l2-mem2mem
echo -n 'file v4l2-mem2mem.c +p' > /sys/kernel/debug/dynamic_debug/control

# Перегляд зареєстрованих M2M пристроїв
v4l2-ctl --list-devices

# Інспектування форматів та черг вузла
v4l2-ctl -d /dev/video0 --all
```
