# 📋 Довідка: інтерфейси відкладеної роботи в ядрі

Тут зібрано сигнатури, прапорці, коди повернення й обмеження всіх механізмів, якими ядро Linux відкладає роботу з обробника переривання, — щоб не гортати заголовки, коли треба згадати, що саме робить `IRQF_ONESHOT` або чи можна кликати `flush_work()` з-під спін-замка. Оголошення наведено за ядром 6.12 (`include/linux/interrupt.h`, `include/linux/workqueue.h`); де інтерфейс змінювався від версії до версії, це позначено окремо — для ядра питання «а в якій версії?» доречне майже завжди.

## Реєстрація переривання

```c
#include <linux/interrupt.h>

typedef irqreturn_t (*irq_handler_t)(int irq, void *dev_id);

/* повна форма: два обробники — негайний і потоковий */
int request_threaded_irq(unsigned int irq,
                         irq_handler_t handler,    /* верхня половина; NULL → типова, що лише будить потік */
                         irq_handler_t thread_fn,  /* тіло в окремій задачі; NULL → потоку немає */
                         unsigned long flags,      /* IRQF_* через | */
                         const char *name,         /* це ім'я видно у /proc/interrupts */
                         void *dev);               /* прилетить в обробник як dev_id */

/* коротка форма — та сама функція з thread_fn = NULL */
static inline int request_irq(unsigned int irq, irq_handler_t handler,
                              unsigned long flags, const char *name, void *dev);

const void *free_irq(unsigned int irq, void *dev);   /* повертає той самий dev */

/* прив'язані до пристрою: знімаються самі, коли драйвер відпускає пристрій */
int devm_request_irq(struct device *dev, unsigned int irq, irq_handler_t handler,
                     unsigned long flags, const char *name, void *dev_id);
int devm_request_threaded_irq(struct device *dev, unsigned int irq, irq_handler_t handler,
                              irq_handler_t thread_fn, unsigned long flags,
                              const char *name, void *dev_id);
```

Коди повернення `request_*_irq()`: `0` — успіх; `-EBUSY` — лінію вже зайнято несумісно (найчастіше: хтось тримає її без `IRQF_SHARED`, або прапорці збігаються не в усьому); `-EINVAL` — немає такого номера, обидва обробники `NULL`, або сталася одна з двох пасток нижче; `-ENOMEM` — не вийшло створити опис чи потік. Усі вони оголошені з `__must_check`: не подивитися на результат — попередження від компілятора.

Дві пастки, що дають `-EINVAL` мовчки для неуважних. Перша: `dev` на спільній лінії обов'язковий і мусить бути унікальним — саме за ним `free_irq()` розуміє, кого з кількох зареєстрованих знімати. Друга: якщо `handler` — `NULL`, а `thread_fn` задано, ядро підставляє типову верхню половину, яка нічого не перевіряє й одразу будить потік, і тоді `IRQF_ONESHOT` **обов'язковий**. Без нього на рівневій лінії вийшов би нескінченний потік переривань, тому ядро відхиляє таку реєстрацію без розмов — виняток лише для контролерів з ознакою `IRQCHIP_ONESHOT_SAFE`.

`free_irq()` **чекає**, доки добіжить обробник і потік, тому з атомарного контексту її кликати не можна. Окремий прапорець `IRQF_COND_ONESHOT` драйвер ставить сам: він означає «згоден на `ONESHOT`, якщо на цій спільній лінії його вже хтось поставив».

## Прапорці IRQF_*

| прапорець | що робить | наслідок, з яким доведеться жити |
|---|---|---|
| `IRQF_SHARED` | дозволяє кільком драйверам сидіти на одній лінії | обробник **мусить** упізнавати свій пристрій за регістром стану й повертати `IRQ_NONE`, коли переривання чуже; `dev` унікальний; усі співмешканці мають узгоджені прапорці |
| `IRQF_ONESHOT` | лінія лишається замаскованою не до кінця верхньої половини, а до кінця потоку | єдиний спосіб працювати з пристроєм, чий запит гасне лише після обміну на шині; ціна — доки біжить потік, ця лінія не доставляє нічого |
| `IRQF_NO_THREAD` | забороняє переводити цей обробник у потік | `threadirqs` і складання з `PREEMPT_RT` лишають його в жорсткому контексті переривання; для таймера, каскадних контролерів і всього, від чого залежить сам механізм перемикання задач |
| `IRQF_NOBALANCING` | виводить переривання з-під автоматичного розкидання по ядрах | маска прив'язки лишається такою, як її поставили; потрібно там, де перенесення переривання на інше ядро зіпсувало б облік — наприклад, для лічильників, прив'язаних до ядра ([прив'язка до ядер](book:unix-linux/cpu-affinity)) |

Рідше, але варто знати: `IRQF_PERCPU` — переривання своє на кожному ядрі, спільного стану немає; `IRQF_TIMER` — позначка таймерного переривання (додає `NO_SUSPEND` і `NO_THREAD`); `IRQF_NO_SUSPEND` — не вимикати під час [засинання системи](book:unix-linux/suspend-and-resume); `IRQF_NO_AUTOEN` — зареєструвати, але не вмикати; вмикає драйвер сам через `enable_irq()`, коли пристрій готовий; `IRQF_PROBE_SHARED` — драйвер знає, що збіг прапорців може не вийти, і не хоче лайки в журнал; `IRQF_TRIGGER_RISING` / `FALLING` / `HIGH` / `LOW` — тип спрацювання, коли його не задано деревом пристроїв.

## Коди повернення обробника

| код | значення | коли повертати |
|---|---|---|
| `IRQ_NONE` | «це не мій пристрій» | на спільній лінії, коли регістр стану порожній — обов'язково, інакше ядро не відрізнить робочу лінію від застряглої |
| `IRQ_HANDLED` | «я його обслужив» | звичайний вихід верхньої половини або потоку |
| `IRQ_WAKE_THREAD` | «решту доробить мій потік» | лише коли реєстровано з `thread_fn`; повернути це без потоку — попередження в журнал і нічого більше |

Різницю між `IRQ_NONE` і `IRQ_HANDLED` ядро використовує для лову застряглих ліній: на кожні 100 000 спрацювань воно дивиться, скільки з них ніхто не визнав своїми, і якщо таких понад 99 900 — друкує в журнал `irq NN: nobody cared` і вимикає лінію. Драйвер, що повертає `IRQ_HANDLED` завжди, цей запобіжник обеззброює: система замість повідомлення дістає вічний потік переривань.

## Softirq

```c
void open_softirq(int nr, void (*action)(void));  /* ядра ≤ 6.8: action(struct softirq_action *) */
void raise_softirq(unsigned int nr);              /* сам глушить локальні переривання */
void raise_softirq_irqoff(unsigned int nr);       /* дешевший; вимагає, щоб їх уже було вимкнено */
```

Гнізда прошито в ядро на етапі збірки, драйвер нового завести не може. Номер — це і є пріоритет: обхід іде від нульового до дев'ятого.

| № | назва | хто підіймає й навіщо |
|---|---|---|
| 0 | `HI` | тасклети високого пріоритету і BH-черга з `WQ_HIGHPRI` |
| 1 | `TIMER` | спрацювання таймерів `timer_list` |
| 2 | `NET_TX` | передача мережевих пакетів, звільнення переданих буферів |
| 3 | `NET_RX` | прийом: саме тут крутиться опитування NAPI |
| 4 | `BLOCK` | доопрацювання завершених запитів до блокових пристроїв |
| 5 | `IRQ_POLL` | опитування замість переривань у блоковому шарі під навантаженням |
| 6 | `TASKLET` | звичайні тасклети і звичайна BH-черга |
| 7 | `SCHED` | періодичне балансування навантаження планувальником |
| 8 | `HRTIMER` | таймери високої роздільності, замовлені в режимі `HRTIMER_MODE_SOFT` |
| 9 | `RCU` | відкладені зворотні виклики [RCU](book:unix-linux/rcu-mechanism) — навмисно останнє гніздо |

Бюджет обходу заданий трьома сталими в `kernel/softirq.c`: `MAX_SOFTIRQ_RESTART` = 10 проходів, `MAX_SOFTIRQ_TIME` = 2 мс, і будь-який із них уривається достроково, щойно планувальник виставив `need_resched()`. Недороблене переходить потокові `ksoftirqd/N`.

Обробник softirq виконується одночасно на всіх ядрах, тому власний стан або тримають у [даних свого ядра](book:unix-linux/per-cpu-data), або накривають спін-замком.

## Тасклети та їхні відповідники в WQ_BH

```c
void tasklet_setup(struct tasklet_struct *t, void (*fn)(struct tasklet_struct *));
DECLARE_TASKLET(name, fn);          /* статичне оголошення */
void tasklet_schedule(struct tasklet_struct *t);      /* у гніздо TASKLET */
void tasklet_hi_schedule(struct tasklet_struct *t);   /* у гніздо HI */
void tasklet_disable(struct tasklet_struct *t);       /* чекає, доки добіжить */
void tasklet_enable(struct tasklet_struct *t);
void tasklet_kill(struct tasklet_struct *t);          /* спить — лише з процесного контексту */
```

Від ядра 6.9 те саме роблять робочі черги з ознакою `WQ_BH` — виконують у тому самому контексті softirq на тому ядрі, що поставило елемент, і в порядку постановки, але вже нормальним інтерфейсом.

| тасклет | те саме через WQ_BH |
|---|---|
| `tasklet_setup(&t, fn)` | `INIT_WORK(&w, fn)` |
| `tasklet_schedule(&t)` | `queue_work(system_bh_wq, &w)` |
| `tasklet_hi_schedule(&t)` | `queue_work(system_bh_highpri_wq, &w)` |
| `tasklet_disable()` / `tasklet_enable()` | `disable_work_sync(&w)` / `enable_work(&w)` — теж із лічильником глибини |
| `tasklet_kill(&t)` | `cancel_work_sync(&w)` |
| немає | `flush_work(&w)` — дочекатися, не скасовуючи |
| немає | своя черга: `alloc_workqueue("...", WQ_BH, 0)` |

## Робочі черги

```c
#include <linux/workqueue.h>

/* функція елемента завжди така: void fn(struct work_struct *work) */
INIT_WORK(&w, fn);
INIT_DELAYED_WORK(&dw, fn);
DECLARE_WORK(w, fn);                                  /* статичне оголошення */

bool schedule_work(struct work_struct *w);                       /* у спільну system_wq */
bool schedule_delayed_work(struct delayed_work *dw, unsigned long delay);
bool queue_work(struct workqueue_struct *wq, struct work_struct *w);
bool queue_work_on(int cpu, struct workqueue_struct *wq, struct work_struct *w);
bool queue_delayed_work(struct workqueue_struct *wq,
                        struct delayed_work *dw, unsigned long delay);

bool flush_work(struct work_struct *w);               /* дочекатися; сплять — лише процесний контекст */
bool cancel_work_sync(struct work_struct *w);
bool cancel_delayed_work_sync(struct delayed_work *dw);

struct workqueue_struct *alloc_workqueue(const char *fmt, unsigned int flags,
                                         int max_active, ...);
void destroy_workqueue(struct workqueue_struct *wq);
```

Головна тонкість — значення `false` від `queue_*()`: воно означає «цей елемент **уже** стоїть у черзі», і другий виклик просто нічого не зробив. Елемент не має лічильника: десять подій, що надійшли до першого запуску, дадуть один прохід функції, а не десять. Тому елемент відкладеної роботи мусить читати стан пристрою, а не покладатися на кількість викликів.

`delay` рахують у тіках, не в мілісекундах: `queue_delayed_work(wq, &dw, msecs_to_jiffies(100))` ([тики й час у ядрі](book:unix-linux/kernel-timekeeping)). `flush_work()` повертає `true`, якщо справді довелося чекати; `cancel_work_sync()` — `true`, якщо елемент устигли зняти до запуску. Обидві сплять. Перед звільненням структури, у якій живе `work_struct`, `cancel_work_sync()` обов'язковий — інакше працівник торкнеться вже звільненої пам'яті.

Прапорці `alloc_workqueue()`:

| прапорець | що змінює |
|---|---|
| `WQ_UNBOUND` | працівники не прив'язані до ядра; планувальник вільно їх переносить. Для довгих і нерівних завдань, де локальність кеша вже не окупається |
| `WQ_HIGHPRI` | окремий пул працівників зі зниженим `nice` — випереджають звичайні, лишаючись звичайними задачами ([пріоритети](book:unix-linux/priority-nice-realtime)) |
| `WQ_BH` | виконання в контексті softirq. Спати заборонено; `max_active` мусить бути `0`, а єдиний дозволений додатковий прапорець — `WQ_HIGHPRI` |
| `WQ_MEM_RECLAIM` | черзі гарантують запасного працівника. **Обов'язковий** для будь-якої черги, задіяної на шляху звільнення пам'яті: інакше система застрягне, чекаючи працівника, якого нема з чого створити |
| `WQ_FREEZABLE` | черга завмирає разом із системою під час засинання |
| `WQ_CPU_INTENSIVE` | елементи не рахуються в межу одночасності: рахунковим завданням розподіляє час планувальник, а не пул |
| `WQ_SYSFS` | черга видима в `/sys/bus/workqueue/`, звідки їй можна міняти прив'язку й `max_active` на ходу |

`max_active` — стеля одночасних виконань на процесор. Нуль означає типове значення `WQ_DFL_ACTIVE`, тобто половину стелі `WQ_MAX_ACTIVE` (у 6.12 це 256 із 512). Одиниця разом із `WQ_UNBOUND` дає впорядковану чергу, де елементи йдуть строго один за одним, — для цього є готовий `alloc_ordered_workqueue()`.

Готові черги, які не треба створювати: `system_wq` (у неї кладе `schedule_work()`), `system_highpri_wq`, `system_long_wq` (для завідомо повільних елементів), `system_unbound_wq`, `system_freezable_wq`, `system_power_efficient_wq`, `system_bh_wq`, `system_bh_highpri_wq`.

## Мінімальний виклик і порядок знімання

```c
struct mydev {
    void __iomem *regs;
    struct work_struct work;
    int irq;
};

static irqreturn_t mydev_isr(int irq, void *dev_id)          /* верхня половина */
{
    struct mydev *d = dev_id;

    if (!(readl(d->regs + REG_STATUS) & STATUS_DONE))
        return IRQ_NONE;                                     /* лінія спільна — не наше */

    writel(STATUS_DONE, d->regs + REG_STATUS);               /* зняти запит негайно */
    schedule_work(&d->work);                                 /* решту — колись потім */
    return IRQ_HANDLED;
}

static void mydev_work(struct work_struct *w)                /* тут спати можна */
{
    struct mydev *d = container_of(w, struct mydev, work);
    ...
}

/* під час підключення пристрою */
INIT_WORK(&d->work, mydev_work);
err = request_irq(d->irq, mydev_isr, IRQF_SHARED, "mydev", d);

/* під час від'єднання — саме в такому порядку */
free_irq(d->irq, d);
cancel_work_sync(&d->work);
kfree(d);
```

Порядок трьох рядків від'єднання — не смак, а єдиний правильний. Спершу знімають переривання: доки лінія жива, обробник будь-якої миті поставить у чергу новий елемент, і скасовувати його намарно. `free_irq()` при цьому сам дочекається обробника, що вже біжить. Далі `cancel_work_sync()` знімає елемент, якщо той ще чекає, або дочікує його, якщо він саме виконується; нового після цього взятися нізвідки. І лише тепер пам'ять, у якій живуть і `work_struct`, і сам `dev_id`, можна звільняти. Поміняти перші два рядки місцями — це залишити вікно, у яке обробник устигне поставити елемент уже після скасування, і працівник розбере структуру, звільнену третім рядком.

Для відкладення з таймером те саме роблять `cancel_delayed_work_sync()`, а для потокового обробника `free_irq()` дочікується й потоку теж, тож окремого кроку не треба. Якщо реєстрація йшла через `devm_request_irq()`, ядро зніме переривання само, — але зробить це **після** того, як драйвер вийде зі свого `remove()`, тому `cancel_work_sync()` в такому драйвері треба ставити разом із явним `free_irq()`, або не змішувати ці два способи взагалі.

## Що дозволено в якому контексті

| дія | верхня половина | softirq · тасклет · `WQ_BH` | потік переривання | робоча черга (`kworker`) |
|---|---|---|---|---|
| заснути, покликати `schedule()` | ні | ні | **так** | **так** |
| `mutex_lock()`, `down()` | ні | ні | **так** | **так** |
| `kmalloc(GFP_KERNEL)` | ні | ні | **так** | **так** |
| `kmalloc(GFP_ATOMIC)` | так | так | так, але зайве | так, але зайве |
| `msleep()`, `wait_for_completion()` | ні | ні | **так** | **так** |
| обмін на I²C / SPI | ні | ні | **так** | **так** |
| `copy_to_user()` / `copy_from_user()` | ні | ні | ні | ні |
| `spin_lock()` | так | так | так | так |
| `spin_lock_bh()` | ні (глушити нижні половини звідси не можна) | зайвий — їх уже глушено | так | так |
| `spin_lock_irqsave()` | так | так | так | так |
| `wake_up()`, `complete()` | так | так | так | так |
| `printk()` | так | так | так | так |

Про `copy_to_user()` в останніх двох стовпчиках: заборона тут іншої природи, ніж сон. Потік переривання і `kworker` — це [потоки ядра](book:unix-linux/kernel-threads), у них узагалі немає адресного простору користувача, тож копіювати нема куди. Дані передають через буфер у пам'яті ядра, а забирає їх звідти задача, що прийшла в драйвер через `read()`.

Правило вибору варіанта спін-замка одне: **замок береться в тій формі, якої вимагає найобмеженіший контекст, що його взагалі бере**. Якщо цей замок бере верхня половина — усі решта беруть його через `spin_lock_irqsave()`; якщо найжорсткіший претендент — softirq, у процесному контексті досить `spin_lock_bh()`. Порушити це означає дозволити перериванню прийти на власний уже взятий замок ([замки в ядрі й атомарний контекст](book:unix-linux/kernel-locking)). Заборона на `GFP_KERNEL` має ту саму причину: розподільник має право заснути, доки звільняє сторінки ([пам'ять ядра](book:unix-linux/kernel-memory-slab)).

## Як спитати в ядра, де ти зараз

Коли той самий допоміжний код кличуть і з обробника, і зі звичайної задачі, контекст перевіряють предикатами з `linux/preempt.h`: `in_hardirq()` — усередині верхньої половини, `in_softirq()` — усередині нижньої (сюди ж рахується й ділянка під `local_bh_disable()`), `in_interrupt()` — будь-яке з двох, `in_task()` — жодне, тобто спати можна. Усі вони читають той самий лічильник `preempt_count`, у якому кожному з цих станів відведено своє поле.

Покладатися на них як на спосіб «якщо можна спати, поспимо» вважають ознакою поганої будови: функція мусить знати свій контракт, а не вгадувати його на ходу. Правильне вживання інше — оголосити контракт: рядок `might_sleep()` на початку функції нічого не робить у робочому ядрі, але зі складанням `CONFIG_DEBUG_ATOMIC_SLEEP` друкує повний слід виклику, щойно цю функцію покликали звідти, де сон заборонено. Так помилку знаходять на першому ж запуску, а не за півроку по загадковому зависанню.

## Що показують лічильники ззовні

**`/proc/interrupts`** — рядок на кожне переривання: номер, лічильник спрацювань окремо на кожне ядро, ім'я контролера, тип (`edge` / `level`) і через кому імена всіх драйверів, що сидять на лінії, — це рівно ті рядки, що передавали в `name`. Лічильник рахує входи у верхню половину, а не обсяг роботи, тож він швидко росте й на пристрої, який нічого корисного не робить. Нижче звичайних номерів ідуть службові рядки: `NMI`, `LOC` (локальний таймер), `RES` і `CAL` (міжпроцесорні), `TLB`.

**`/proc/softirqs`** — рядок на кожне з десяти гнізд, стовпчик на кожне ядро, лічильники накопичувальні від завантаження. Сам по собі знімок нічого не каже; корисна різниця двох знімків за секунду — вона показує, якого саме відкладеного стало більше й на якому ядрі воно осіло.

**`/sys/kernel/irq/<номер>/`** — те саме, що в `/proc/interrupts`, але полями, які зручно читати програмою ([модель пристроїв у sysfs](book:unix-linux/sysfs-device-model)): `actions` — імена драйверів через кому, `chip_name` — контролер, `hwirq` — апаратний номер до перекладу в номер Linux, `name` — назва обробника потоку контролера, `per_cpu_count` — лічильники по ядрах, `type` — `level` або `edge`, `wakeup` — чи здатне це переривання будити систему.

Поруч, у `/proc/irq/<номер>/`, лежить керування: `smp_affinity` і `smp_affinity_list` — маска дозволених ядер, `effective_affinity` — куди контролер насправді доставляє, `spurious` — лічильники визнаних і невизнаних спрацювань, тобто сировина того самого запобіжника «nobody cared».

Виконавців видно в `ps`: `ksoftirqd/N` — переповнення softirq на ядрі N, `irq/NN-<ім'я>` — потік конкретного переривання (його пріоритет міняють через `chrt` за іменем), `kworker/N:x` — працівник, прив'язаний до ядра, `kworker/uN:x` — працівник із `WQ_UNBOUND`.
