# 📋 Файли контролера `io` в cgroup v2: що приймає й що повертає кожен

Це точний контракт файлів інтерфейсу контролера `io` у другій версії cgroup: які ключі приймає запис, у яких одиницях, для якого пристрою `$MAJ:$MIN` і що видно у відповідь. Помилка тут не падає гучно — ядро або поверне `EINVAL` на весь рядок, або застосує число не туди, куди ти думав, і виглядатиме це як «обмеження не працює».

## Де ці файли й звідки беруться числа пристрою

Файли з'являються в теці групи лише після того, як батько увімкнув контролер у `cgroup.subtree_control` ([cgroups](topic:unix-linux/cgroups) — облік іде по групах єдиної ієрархії, і кожен контролер додає групі свої файли):

```sh
echo "+io" > /sys/fs/cgroup/cgroup.subtree_control
mkdir /sys/fs/cgroup/backup
```

Пристрій усюди задають парою старшого й молодшого номерів через двокрапку ([головний і другорядний номери](topic:unix-linux/major-minor-numbers) — саме ця пара, а не шлях у `/dev`, ідентифікує пристрій для ядра). Брати їх найпростіше так:

```sh
lsblk -dno MAJ:MIN /dev/nvme0n1     # 259:0
stat -c '%t:%T' /dev/nvme0n1        # 103:0  — УВАГА: шістнадцяткові!
```

| Файл | Де існує | Доступ | Дає його |
|---|---|---|---|
| `io.stat` | корінь і нащадки | читання | `CONFIG_BLK_CGROUP` |
| `io.max` | лише не в корені | читання й запис | `CONFIG_BLK_DEV_THROTTLING` |
| `io.latency` | лише не в корені | читання й запис | `CONFIG_BLK_CGROUP_IOLATENCY` |
| `io.weight` | лише не в корені | читання й запис | `CONFIG_BLK_CGROUP_IOCOST` |
| `io.cost.qos`, `io.cost.model` | **лише корінь** | читання й запис | `CONFIG_BLK_CGROUP_IOCOST` |
| `io.prio.class` | лише не в корені | читання й запис | `CONFIG_BLK_CGROUP_IOPRIO` |
| `io.pressure` | корінь і нащадки | читання; запис реєструє тригер | `CONFIG_PSI` |

## io.max

Один рядок на пристрій, чотири ключі; значення — **десяткове ціле** або слово `max`. Суфіксів `K`/`M`/`G` розбір не знає: `rbps=2M` — це `EINVAL`.

| Ключ | Що обмежує | Одиниця |
|---|---|---|
| `rbps` | читання | байтів за секунду |
| `wbps` | запис | байтів за секунду |
| `riops` | читання | операцій за секунду |
| `wiops` | запис | операцій за секунду |

```sh
echo "259:0 rbps=2097152 wiops=120" > io.max
cat io.max
# 259:0 rbps=2097152 wbps=max riops=max wiops=120

echo "259:0 wiops=max" > io.max     # зняти одне обмеження
echo "259:0 rbps=max" > io.max      # усі чотири max → рядок зникає з виводу
```

Контракт запису: ключі йдуть у будь-якому порядку й будь-якою підмножиною, **не згадані ключі зберігають чинне значення**, `max` знімає конкретне обмеження. Облік ведеться короткими відрізками часу, тож миттєвий сплеск понад стелю можливий — рівним тримається середнє за секунди. Обмеження успадковується вниз: чинна межа групи — це найменше з її власної й усіх материнських.

## io.latency

```sh
echo "259:0 target=2000" > io.latency   # ціль 2000 мкс = 2 мс
cat io.latency
# 259:0 target=2000
echo "259:0 target=0" > io.latency      # 0 — захист знято
```

Єдиний ключ `target` — цільова затримка **в мікросекундах**. Як контролер поводиться, видно в `io.stat`, але лише коли ввімкнено налагоджувальну статистику блокового рівня (параметр `blkcg_debug_stats`, доступний на запис за адресою `/sys/module/blk_cgroup/parameters/blkcg_debug_stats`):

| Поле в `io.stat` | Значення | Одиниця |
|---|---|---|
| `depth` | чинна глибина подання групи; `depth=max` — не обмежена | запитів |
| `avg_lat` | ковзне середнє затримки завершень групи | мкс |
| `win` | вікно оцінювання; минає лише за наявности обігу | мс |

## io.weight

Плаский файл: перший рядок — вага за замовчуванням, далі перевизначення на конкретні пристрої. Діапазон — цілі `1`–`10000`, поза ним `EINVAL`; початкове значення — `100`.

```sh
echo 300 > io.weight               # те саме, що: echo "default 300"
echo "259:0 600" > io.weight       # перевизначення на пристрій
echo "259:0 default" > io.weight   # зняти перевизначення
cat io.weight
# default 300
# 259:0 600
```

Не плутати з `io.bfq.weight`: форма рядків та сама, але це вага іншого механізму — планувальника BFQ ([планувальники блокового введення-виведення](topic:unix-linux/io-schedulers)), з іншим діапазоном `1`–`1000`.

## io.cost.qos і io.cost.model — тільки на кореневій групі

Обидва файли — з вкладеними ключами, обидва існують **лише** в `/sys/fs/cgroup/`. Рядок для пристрою з'являється після першого запису в будь-який із двох.

```sh
cat /sys/fs/cgroup/io.cost.qos
# 259:0 enable=1 ctrl=auto rpct=95.00 rlat=75000 wpct=95.00 wlat=150000 min=50.00 max=150.00

cat /sys/fs/cgroup/io.cost.model
# 259:0 ctrl=auto model=linear rbps=1180000000 rseqiops=214000 rrandiops=210000 \
#       wbps=1130000000 wseqiops=170000 wrandiops=140000
```

| `io.cost.qos` | Значення | Одиниця / діапазон |
|---|---|---|
| `enable` | вмикає ваговий поділ на цьому пристрої | `0` / `1` |
| `ctrl` | хто тримає параметри | `auto` \| `user` |
| `rpct`, `wpct` | який перцентиль завершень стежимо | 0–100, дробове |
| `rlat`, `wlat` | у яку затримку цей перцентиль має вкластися | мкс |
| `min`, `max` | межі підгонки швидкости віртуального годинника | % від номіналу, 1–10000 |

| `io.cost.model` | Значення | Одиниця |
|---|---|---|
| `model` | вид моделі; наразі лише `linear` | — |
| `rbps`, `wbps` | потік на послідовній роботі | байтів за секунду |
| `rseqiops`, `wseqiops` | операції по 4 КіБ послідовно | за секунду |
| `rrandiops`, `wrandiops` | операції по 4 КіБ випадково | за секунду |

Три властивості, на яких найчастіше спотикаються. Перша: будь-який запис параметрів (усе, крім явного `ctrl=auto`) перемикає `ctrl` на `user` і **вимикає автопідбір** — ядро більше не чіпатиме ці числа саме; повертає автоматику `echo "259:0 ctrl=auto" > io.cost.model`. Друга: `enable=0` лишає файли `io.weight` на місці, але ваги перестають щось означати — типова причина «ваги виставив, а поділу немає». Третя: коефіцієнти під конкретний носій не вгадують, а міряють — скриптом `tools/cgroup/iocost_coef_gen.py` з дерева ядра.

## io.stat

Читання, по рядку на пристрій, порядок довільний. Лічильники з'являються, лише коли в цій групі по цьому пристрою був хоч якийсь обіг.

```
259:0 rbytes=1459200 wbytes=314773504 rios=192 wios=353 dbytes=0 dios=0 cost.usage=91324
```

| Ключ | Значення |
|---|---|
| `rbytes`, `wbytes` | прочитано й записано байтів |
| `rios`, `wios` | операцій читання й запису |
| `dbytes`, `dios` | байтів і операцій відкидання ([discard і TRIM](topic:unix-linux/discard-and-trim)) |

Що додається понад базу: за ввімкненого iocost у **кореневому** рядку є `cost.vrate` — чинна швидкість віртуального годинника у відсотках від номіналу, а в кожній групі `cost.usage` — спожитий час пристрою в мікросекундах. Під `blkcg_debug_stats` до них додаються `cost.wait`, `cost.indebt`, `cost.indelay` (теж мкс) і — для груп, яких зараз присипляють, — `use_delay` та `delay_nsec` (нс). Файла скидання лічильників немає: різницю двох знімків рахуєш сам.

## io.prio.class

Плаский файл без ключа пристрою, одне слово на всю групу; початкове значення — `no-change`.

| Значення | Дія над класом пріоритету запитів групи | Номер |
|---|---|---|
| `no-change` | не чіпати | 0 |
| `promote-to-rt` | не-RT запити → клас RT, рівень 4 | 1 |
| `restrict-to-be` | запити без класу й запити класу RT → BE | 2 |
| `idle` | усі запити → найнижчий клас IDLE | 3 |

Правило одне: `promote-to-rt` ставить клас RT напряму, а всі інші політики беруть **більше** з двох чисел — номера політики й номера класу самого запиту. Тобто, крім підвищення, політика вміє лише знижувати, ніколи не підвищує запит випадково. Значення `none-to-rt` — застарілий синонім до `promote-to-rt`. Сам клас нічого не робить, поки його ніхто не читає: рахується він у планувальнику, який пріоритети розрізняє ([пріоритети введення-виведення](topic:unix-linux/io-priorities)).

## io.pressure

Формат PSI, дві лінії; `avg10`/`avg60`/`avg300` — відсоток часу у вікні, `total` — сума в мікросекундах ([тиск на ресурси](topic:unix-linux/load-and-pressure) пояснює, чим `some` відрізняється від `full`).

```
some avg10=0.00 avg60=0.31 avg300=0.12 total=8419318
full avg10=0.00 avg60=0.28 avg300=0.10 total=7205044
```

Запис у цей файл не міняє нічого, а реєструє тригер для очікування подій: рядок `some 150000 1000000` означає «розбуди мене, коли за вікно в 1 с накопичиться 150 мс простою»; вікно — від 500 мс до 10 с. Загальносистемний той самий показник лежить у `/proc/pressure/io`.

## Мінімальний робочий приклад

```sh
DEV=$(lsblk -dno MAJ:MIN /dev/nvme0n1)      # 259:0
cd /sys/fs/cgroup
echo "+io" > cgroup.subtree_control
mkdir -p backup

echo "$DEV rbps=52428800" > backup/io.max   # 50 МіБ/с на читання
echo $$ > backup/cgroup.procs               # оболонка й усі її нащадки — у групі

dd if=/dev/nvme0n1 of=/dev/null bs=1M count=512 iflag=direct
cat backup/io.stat
```

`iflag=direct` тут не прикраса: читання, яке потрапило в сторінковий кеш, до блокового рівня не доходить і в `io.stat` не з'являється.

## Помилки запису

| Код | Коли |
|---|---|
| `EINVAL` | невідомий ключ, значення з суфіксом (`2M`), вага поза `1`–`10000`, пробіли навколо `=` |
| `ENODEV` | такої пари `$MAJ:$MIN` немає або це не блоковий пристрій |
| «немає файлу» | `io.cost.*` шукали не в корені, `io.max` — у корені, або контролер не ввімкнено батьком у `cgroup.subtree_control` |

І остання пастка, синтаксисом не вловима: числа треба ставити на тому пристрої, крізь який справді проходить дефіцит. Обмеження на логічному томі не бачить решти томів того самого носія, а обмеження на фізичному пристрої накриває разом усіх, хто на ньому живе ([device mapper](topic:unix-linux/device-mapper) — кожен шар відображення має власну пару номерів).
