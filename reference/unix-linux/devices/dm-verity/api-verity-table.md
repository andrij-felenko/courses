# 📋 Таблиця, суперблок і команди dm-verity

Точний контракт цілі `verity`: усі поля рядка таблиці по порядку з допустимими значеннями, необов'язкові параметри, 512 байтів суперблока на пристрої гешів і команди `veritysetup`. Це те, що потрібно, щоб зібрати пристрій руками, прочитати чужий вивід `dmsetup table` або зрозуміти, чому ядро відмовило з `EINVAL`. Звірено з `drivers/md/dm-verity-target.c`, документацією ядра `admin-guide/device-mapper/verity.rst` і кодом cryptsetup.

## Позиційні аргументи

```
<version> <data_dev> <hash_dev> <data_block_size> <hash_block_size>
<num_data_blocks> <hash_start_block> <algorithm> <digest> <salt>
[<к-сть опцій> <опції>…]
```

Десять полів, усі обов'язкові, порядок сталий. Перед ними стоїть звичайна для [device mapper](book:unix-linux/device-mapper) шапка рядка: перший сектор, довжина, ім'я цілі.

| # | поле | допустимі значення |
| --- | --- | --- |
| 1 | `version` | `0` або `1` — формат **дерева**, а не версія драйвера; більше — `Invalid version` |
| 2 | `data_dev` | шлях або `major:minor` |
| 3 | `hash_dev` | так само; **може бути тим самим пристроєм**, що й `data_dev` — тоді дерево кладуть у хвіст за даними |
| 4 | `data_block_size` | байти; степінь двійки, не менше логічного блока пристрою даних, не більше сторінки пам'яті |
| 5 | `hash_block_size` | байти; степінь двійки, не менше логічного блока пристрою гешів (формальна стеля `INT_MAX`, на ділі — та сама сторінка) |
| 6 | `num_data_blocks` | скільки блоків даних накрито деревом; усе, що на пристрої далі, недосяжне |
| 7 | `hash_start_block` | зсув **кореневого** блока, у блоках гешів від початку `hash_dev` |
| 8 | `algorithm` | ім'я з crypto API ядра: `sha256`, `sha512`, `sha1`, `blake2b-256` |
| 9 | `digest` | корінь шістнадцятково; довжина рядка мусить бути рівно вдвічі більша за розмір гешу обраного алгоритму, інакше `Invalid root digest` |
| 10 | `salt` | сіль шістнадцятково або `-`, коли солі немає |

Одиниці в цьому рядку різні, і плутанина між ними — найчастіша помилка при складанні руками. Довжина в шапці — у [секторах по 512 байтів](book:unix-linux/block-device-model), розміри блоків — у байтах, `hash_start_block` — у блоках гешів. Погоджувати їх доводиться самому: ядро не звіряє довжину з кількістю блоків.

**Розділ 4 ГіБ, блок 4096 байтів.**

```
num_data_blocks  = 4294967296 / 4096     = 1048576
довжина в шапці  = 1048576 · 4096 / 512  = 8388608 секторів
```

`hash_start_block` майже завжди дорівнює `1`. Суперблок займає перші 512 байтів пристрою гешів, а дерево вирівняне по цілих блоках гешів — тож нульовий блок віддано суперблокові, і корінь лягає в перший. З `--no-superblock` там стоїть `0`.

Кількості рівнів у рядку немає: ядро рахує її саме з `num_data_blocks` і того, скільки гешів уміщується в блок, а тоді перевіряє, чи вистачає місця (`Hash device is too small`). Стеля — 63 рівні, `DM_VERITY_MAX_LEVELS`.

## Нулю й одиниці різна сіль

Перше поле описує формат дерева на носії, і різниця між нулем та одиницею — у двох дрібницях, кожна з яких повністю змінює корінь.

```
версія 0 (Chromium OS)   геш блока = H( блок ‖ сіль )    сіль у хвіст
                         геші в блоці лежать щільно,
                         решту блока добито нулями

версія 1 (типова)        геш блока = H( сіль ‖ блок )    сіль наперед
                         кожен геш добито нулями
                         до найближчого степеня двійки
```

Наслідок першої дрібниці простий: те саме дерево, прочитане з іншою версією, дає інший корінь. Сумісності між форматами немає й бути не може.

Друга дрібниця коштує місця — і не дарма. Коли розмір гешу добито до степеня двійки, їхня кількість у блоці теж степінь двійки, а отже, номер потрібного гешу всередині блока береться зсувом, а не діленням (`hash_per_block_bits` у драйвері). Для SHA-256 це нічого не міняє: тридцять два байти вже степінь двійки. А от SHA-1 із його двадцятьма байтами дає в блоці 4 КіБ 204 геші у версії 0 і лише 128 у версії 1.

## Необов'язкові параметри

Хвіст рядка влаштований так само, як в інших цілей: спершу число — скільки слів далі, — потім рівно стільки слів. Параметр з аргументом рахується за два слова.

| параметр | що робить |
| --- | --- |
| `ignore_corruption` | розбіжність лише записати в журнал, дані віддати нагору |
| `restart_on_corruption` | негайне аварійне перезавантаження |
| `panic_on_corruption` | паніка ядра |
| `restart_on_error` | те саме перезавантаження, але на **помилку носія**, а не на розбіжність із деревом |
| `panic_on_error` | паніка на помилку носія |
| `ignore_zero_blocks` | блок, який має бути нульовим, не читати й не перевіряти — просто віддати нулі |
| `check_at_most_once` | тримати бітову мапу перевірених блоків і вдруге їх не перевіряти |
| `use_fec_from_device <dev>` | брати надлишковий код із цього пристрою |
| `fec_roots <n>` | байтів парності в кодовому слові на 255 байтів; від 2 до 24 |
| `fec_blocks <n>` | скільки блоків накрито надлишковим кодом |
| `fec_start <n>` | зсув парності на `<dev>`, у блоках **даних** |
| `root_hash_sig_key_desc <опис>` | опис ключа типу `user`, у якому лежить підпис кореня у форматі PKCS#7 |
| `try_verify_in_tasklet` | короткі запити з уже прогрітим кешем перевіряти в [нижній половині](book:unix-linux/interrupts-bottom-halves), не будячи робочої черги |

Три режими розбіжності взаємно виключні: другий у тому самому рядку дає `EINVAL` і `Conflicting error handling parameters`. Так само між собою виключаються два режими помилки носія. Надлишковий код однією опцією не вмикається: `use_fec_from_device` без `fec_roots`, `fec_blocks` і `fec_start` не описує геометрії [Ріда–Соломона](book:communications/reed-solomon), і ціль не збереться.

Приклад рядка з опціями — у хвості рівно десять слів:

```
0 8388608 verity 1 /dev/sda1 /dev/sda2 4096 4096 1048576 1 sha256 4392712b… 1a2b3c4d…
  10 restart_on_corruption ignore_zero_blocks use_fec_from_device /dev/sda3
  fec_roots 2 fec_blocks 1056833 fec_start 0
```

`dmsetup create` для verity подають із `--readonly`. Записати в такий пристрій усе одно не вийде, але без прапорця він оголошений записуваним — і файлова система над ним спробує змонтуватися для запису, тобто вмерти на першому ж програванні журналу.

## Параметри модуля

| параметр | типово | що робить |
| --- | --- | --- |
| `dm_verity.require_signatures` | `0` | коли `1`, жоден verity-пристрій не збереться без чинного підпису кореня — нікому, зокрема адміністраторові |
| `dm_verity.prefetch_cluster` | `262144` | скільки байтів дерева тягнути наперед |
| `dm_verity.use_bh_bytes` | `8192` × 4 | стеля розміру запиту для перевірки в нижній половині, окремо на кожен із чотирьох класів пріоритету вводу-виводу |

Права доступу до файла `require_signatures` — `0444`: значення ставлять у [командному рядку ядра](book:unix-linux/bootloader-and-cmdline), а на ходу вже не міняють. Підпис ядро перевіряє [власними кільцями ключів](book:unix-linux/kernel-keyrings) — кільцем `.dm-verity` і, залежно від конфігурації, ще вторинним та платформним; ключа з диска серед них немає жодного.

## Суперблок на пристрої гешів

512 байтів, які пише `veritysetup` за зсувом `--hash-offset` (типово нуль). **Ядро їх не читає.** У драйвері немає коду, який звертався б до цих байтів: усі параметри ціль бере з рядка таблиці. Суперблок — пам'ятка для інструментів простору користувача, а не джерело правди.

```c
struct verity_sb {              /* 512 байтів, packed, little-endian */
        uint8_t  signature[8];      /*   0   "verity\0\0" */
        uint32_t version;           /*   8   формат суперблока — завжди 1 */
        uint32_t hash_type;         /*  12   0 — Chromium OS, 1 — типовий */
        uint8_t  uuid[16];          /*  16   UUID пристрою гешів */
        uint8_t  algorithm[32];     /*  32   "sha256" і нулі */
        uint32_t data_block_size;   /*  64   байти */
        uint32_t hash_block_size;   /*  68   байти */
        uint64_t data_blocks;       /*  72 */
        uint16_t salt_size;         /*  80   байтів солі, до 256 */
        uint8_t  _pad1[6];          /*  82 */
        uint8_t  salt[256];         /*  88 */
        uint8_t  _pad2[168];        /* 344 … 512 */
};
```

Два поля з іменами про версію легко переплутати, а вони про різне. `version` описує сам суперблок і дорівнює одиниці завжди; формат дерева лежить у `hash_type` — і саме `hash_type` іде **першим** аргументом таблиці. Розміру солі ядро не обмежує взагалі; `veritysetup` типово бере 32 випадкові байти, а поле суперблока вміщує до 256.

Чого в суперблоці немає — кореневого гешу. Ні поля, ні місця під нього в доповненні. Це не недогляд формату: суперблок лежить на тому самому пристрої, який дерево й перевіряє, тож узятий звідти корінь був би коренем зі слів підозрюваного.

## Команди veritysetup

| команда | що робить | ключі |
| --- | --- | --- |
| `veritysetup format <дані> <геші>` | рахує дерево, пише суперблок, друкує параметри й корінь | `--hash` (типово `sha256`) · `--data-block-size` / `--hash-block-size` (по 4096) · `--data-blocks` (типово весь пристрій) · `--hash-offset` · `--salt` (типово 32 випадкові байти, `-` — без солі) · `--uuid` · `--format` (0 або 1, типово 1) · `--no-superblock` · `--root-hash-file` · `--fec-device` / `--fec-offset` / `--fec-roots` (типово 2) |
| `veritysetup open <дані> <ім'я> <геші> <корінь>` (застаріле ім'я — `create`) | збирає `/dev/mapper/<ім'я>` | `--root-hash-file` замість аргументу · `--root-hash-signature` · `--ignore-corruption` / `--restart-on-corruption` / `--panic-on-corruption` · `--error-as-corruption` · `--ignore-zero-blocks` · `--check-at-most-once` · `--use-tasklets` · `--fec-device` · `--shared` |
| `veritysetup verify <дані> <геші> <корінь>` | проходить усе дерево **у просторі користувача**; ядра не чіпає взагалі | ті самі ключі опису пристрою |
| `veritysetup status <ім'я>` | що ядро каже про живий пристрій | — |
| `veritysetup dump <геші>` | друкує вміст суперблока | `--hash-offset` |
| `veritysetup close <ім'я>` | розбирає пристрій | `--deferred` · `--cancel-deferred` |

`--error-as-corruption` прикладає обраний режим розбіжності ще й до помилок носія; у рядку таблиці це обертається на `restart_on_error` чи `panic_on_error`.

Вивід `format` — той самий блок, що дає `dump`, плюс один рядок:

```
VERITY header information for /dev/sda2
UUID:                   e48da609-…
Hash type:              1
Data blocks:            1048576
Data block size:        4096
Hash blocks:            8257
Hash block size:        4096
Hash algorithm:         sha256
Salt:                   1a2b3c4d…
Root hash:              4392712ba01368ef…
```

Останнього рядка в `dump` не буде — саме тому, що кореня в суперблоці немає: `dump` показує все, що записано на носії, і корінь до цього переліку не входить.

`--no-superblock` знімає з носія й цю пам'ятку. Тоді кожній наступній команді — `open`, `verify`, `dump` — доводиться повторювати геть усі ключі формату в тих самих значеннях. Помилка в будь-якому з них діагностики не дає: дерево просто порахується інакше й зійдеться на іншому корені.

Коди виходу: `0` — гаразд, `1` — хибні параметри, `2` — немає прав, `3` — бракує пам'яті, `4` — не той пристрій, `5` — пристрій уже існує або зайнятий.

> 🔧 **Навіщо це.** Ані `dmsetup create`, ані `veritysetup open` кореня не перевіряють. При складанні ціль не читає дерева взагалі: вона розбирає рядок, рахує глибину й дивиться, чи вистачає місця на пристрої гешів. Тому одруківка в тридцяти двох байтах кореня дає пристрій, який чудово створився й падає з `EIO` на першому ж читанні — а виглядає це достеменно як побитий носій. Звірити корінь наперед можна лише окремою дією: `veritysetup verify` проходить дерево в просторі користувача й каже про розбіжність прямо, ще до того, як пристрій з'явиться.

## Рядок status

```
<перший сектор> <довжина> verity <V|C> <виправлено блоків>
```

Формує його сама ціль, і містить він рівно дві речі.

| поле | значення |
| --- | --- |
| `V` / `C` | `V` — розбіжностей не було жодного разу; `C` — була принаймні одна |
| друге поле | скільки блоків полагоджено надлишковим кодом; `-`, коли коду немає |

Літера `C` не скидається: прапорець живе рівно стільки, скільки саме відображення. Тому `V` після перезавантаження не свідчить ні про що, крім поточного сеансу.

`dmsetup table` для verity віддає рядок цілком — із коренем, сіллю й усіма опціями, — на відміну від [dm-crypt](book:unix-linux/dm-crypt), де ключ у виводі підмінюють нулями. Ховати тут нічого: ані корінь, ані сіль не таємниця, вони лише мусять прийти ззовні.
