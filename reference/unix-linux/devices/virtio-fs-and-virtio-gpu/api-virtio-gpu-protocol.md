# 📋 Специфікація протоколу та структур даних Virtio GPU та Virtio FS

Цей довідник містить точний опис структур даних, констант типів команд, прапорців та заголовків пакетів, які використовуються при обміні даними між гостьовим драйвером та гіпервізором для спеціалізованих паравіртуалізованих пристроїв `virtio-gpu` та `virtio-fs`. Документ призначений для розробників системних драйверів, віртуальних точок монтування та гіпервізорів, яким необхідне глибоке розуміння бінарного ABI-контракту на рівні керуючих черг (virtqueues) та конфігураційних регіонів PCI.

---

## 1. Заголовки та команди Virtio GPU (Control Queue)

Усі управляючі команди `virtio-gpu` надсилаються через чергу `controlq` (Queue Index 0). Кожен запит починається з фіксованого заголовка `virtio_gpu_ctrl_hdr`, за яким слідують специфічні параметри конкретної команди. Гіпервізор повертає відповідь, що також починається з `virtio_gpu_ctrl_hdr`, де у полі `type` вказується статус виконання (наприклад, `VIRTIO_GPU_RESP_OK_NODATA` або код помилки).

### 1.1 Базовий заголовок управління (virtio_gpu_ctrl_hdr)

Структура `virtio_gpu_ctrl_hdr` є уніфікованим заголовком як для запитів від гостя, так і для відповідей від хоста.

```c
struct virtio_gpu_ctrl_hdr {
    uint32_t type;        /* Тип команди (VIRTIO_GPU_CMD_*) або відповіді (VIRTIO_GPU_RESP_*) */
    uint32_t flags;       /* Прапорці синхронізації та асинхронного сповіщення */
    uint64_t fence_id;    /* Унікальний ідентифікатор бар'єра синхронізації */
    uint32_t ctx_id;      /* Ідентифікатор 3D-контексту рендерингу (для VirGL / Venus) */
    uint8_t  ring_idx;    /* Індекс кільця виконання в контексті (Venus) */
    uint8_t  padding[3];  /* Доповнення до 24 байтів */
};
```

Детальне призначення полів заголовка:
* **`type`**: Вказує конкретну операцію. Коди запитів `VIRTIO_GPU_CMD_*` лежать нижче за `0x1000` (2D — від `0x0100`, 3D — від `0x0200`, курсор — від `0x0300`), коди відповідей `VIRTIO_GPU_RESP_*` — від `0x1100` для успіху й від `0x1200` для помилок. Тож за самим значенням поля видно, запит це чи відповідь.
* **`flags`**: Використовується для синхронізації виконання. Якщо встановлено біт `VIRTIO_GPU_FLAG_FENCE` (`1 << 0`), гіпервізор зобов'язаний згенерувати переривання та сповістити гостя лише після того, як графічне апаратне забезпечення хоста повністю завершить обробку цієї команди.
* **`fence_id`**: Монотонно зростаючий лічильник, який гостьовий драйвер присвоює кожній команді з прапорцем `FENCE`. Це дає змогу гостю відстежувати прогрес виконання графічного конвеєра без блокування центрального процесора.
* **`ctx_id`**: Вказує ізольований контекст рендерингу. Для звичайного 2D-виводу дорівнює `0`. Для 3D-сесій VirGL або Venus кожен процес гостя створює власний `ctx_id`, що гарантує ізоляцію стану OpenGL/Vulkan між різними додатками.
* **`ring_idx`**: Використовується у Vulkan (Venus) для прив'язки команд до конкретних черг виконання GPU хоста (Graphics, Compute, Transfer).

---

### 1.2 Коди команд та відповідей

Гіпервізор використовує чітко визначений набір відповідей для повідомлення гостя про стан обробки пакета.

Коди успішних відповідей хоста:
* `VIRTIO_GPU_RESP_OK_NODATA` (`0x1100`): Операцію успішно виконано, додаткових даних у відповіді немає (наприклад, після створення ресурсу або приєднання сторінок).
* `VIRTIO_GPU_RESP_OK_DISPLAY_INFO` (`0x1101`): Повертається у відповідь на `GET_DISPLAY_INFO`, містить масив роздільних здатностей моніторів.
* `VIRTIO_GPU_RESP_OK_CAPSET_INFO` (`0x1102`): Повертає інформацію про підтримувані набори можливостей 3D (VirGL, VirGL v2, Venus).
* `VIRTIO_GPU_RESP_OK_CAPSET` (`0x1103`): Повертає бінарні дані налаштувань capabilities для Mesa.
* `VIRTIO_GPU_RESP_OK_EDID` (`0x1104`): Повертає блок EDID віртуального монітора — з нього гість дізнається про підтримувані режими.

Коди помилок хоста:
* `VIRTIO_GPU_RESP_ERR_UNSPEC` (`0x1200`): Невизначена або внутрішня помилка гіпервізора.
* `VIRTIO_GPU_RESP_ERR_OUT_OF_MEMORY` (`0x1201`): Недостатньо оперативної або відеопам'яті на хості для виділення ресурсу.
* `VIRTIO_GPU_RESP_ERR_INVALID_SCANOUT_ID` (`0x1202`): Запропонований ID монітора виходить за межі налаштованих scanout-пристроїв.
* `VIRTIO_GPU_RESP_ERR_INVALID_RESOURCE_ID` (`0x1203`): Ресурс із вказаним `resource_id` не існує або вже був знищений.
* `VIRTIO_GPU_RESP_ERR_INVALID_CONTEXT_ID` (`0x1204`): Контекст з вказаним `ctx_id` не зареєстровано.
* `VIRTIO_GPU_RESP_ERR_INVALID_PARAMETER` (`0x1205`): Некоректний прямокутник, зсув або формат пікселів.

## 2. Структури створення та керування 2D-ресурсами

### 2.1 Створення 2D-ресурсу (virtio_gpu_resource_create_2d)

Команда `VIRTIO_GPU_CMD_RESOURCE_CREATE_2D` (`0x0101`) виділяє графічний буфер у пам'яті хоста.

```c
struct virtio_gpu_rect {
    uint32_t x;
    uint32_t y;
    uint32_t width;
    uint32_t height;
};

struct virtio_gpu_resource_create_2d {
    struct virtio_gpu_ctrl_hdr hdr;
    uint32_t resource_id; /* Унікальний ідентифікатор ресурсу, призначений гостем */
    uint32_t format;      /* Формат пікселів (наприклад, VIRTIO_GPU_FORMAT_B8G8R8A8_UNORM) */
    uint32_t width;       /* Ширина у пікселях */
    uint32_t height;      /* Висота у пікселях */
};
```

Пояснення полів:
* **`resource_id`**: Це унікальне 32-бітне число, яке генерується гостьовим драйвером DRM. Воно слугує дескриптором для всіх наступних операцій з цим кадровим буфером (передача пікселів, прив'язка пам'яті, відображення на монітор).
* **`format`**: Визначає макет пікселів у пам'яті. Значення `1` відповідає `VIRTIO_GPU_FORMAT_B8G8R8A8_UNORM` (32 біти на піксель: по 8 біт на Blue, Green, Red, Alpha), що є фактичним стандартом для кадрових буферів X11 та Wayland.

---

### 2.2 Прив'язка пам'яті гостя (virtio_gpu_resource_attach_backing)

Після створення ресурсу на хості, гостьовий драйвер повинен надати гіпервізору список фізичних сторінок своєї RAM (Scatter-Gather List), де фізично розташовані піксельні дані кадрового буфера. Для цього використовується команда `VIRTIO_GPU_CMD_RESOURCE_ATTACH_BACKING` (`0x0106`).

```c
struct virtio_gpu_mem_entry {
    uint64_t addr;   /* Фізична адреса сторінки в RAM гостя (Guest Physical Address, GPA) */
    uint32_t length; /* Довжина безперервного блоку в байтах */
    uint32_t padding;
};

struct virtio_gpu_resource_attach_backing {
    struct virtio_gpu_ctrl_hdr hdr;
    uint32_t resource_id; /* ID ресурсу, до якого додаються сторінки */
    uint32_t nr_entries;  /* Кількість елементів у масиві mem_entry */
    /* Далі в пам'яті слідує масив struct virtio_gpu_mem_entry entries[nr_entries] */
};
```

Механізм роботи:
1. Ядро гостя виділяє сторінки пам'яті через `alloc_pages()` або `kmalloc()`.
2. Драйвер формує масив `virtio_gpu_mem_entry`, де кожна запис вказує фізичну адресу сторінки (`GPA`).
3. Гіпервізор QEMU/crosvm конвертує адреси GPA у власні віртуальні адреси хоста (HVA) і створює внутрішню структуру прив'язки ресурсу.

---

### 2.3 Передача піксельних даних (virtio_gpu_transfer_to_host_2d)

Коли додаток гостя малює у кадровий буфер, дані оновлюються лише у локальній RAM гостя. Щоб хост скопіював ці нові пікселі у свій рендер-буфер, надсилається команда `VIRTIO_GPU_CMD_TRANSFER_TO_HOST_2D` (`0x0105`).

```c
struct virtio_gpu_transfer_to_host_2d {
    struct virtio_gpu_ctrl_hdr hdr;
    struct virtio_gpu_rect r; /* Координати та розмір видозміненого прямокутника */
    uint64_t offset;          /* Зсув байтів від початку буфера ресурсу */
    uint32_t resource_id;     /* ID ресурсу */
    uint32_t padding;
};
```

Ця команда дозволяє виконувати часткові оновлення екрана (dirty rect updates), передаючи по шині Virtqueue тільки ті прямокутники, де дійсно змінилося зображення, що суттєво економить пропускну здатність CPU та пам'яті.

## 3. Специфікація FUSE-повідомлень Virtio FS

Пристрій `virtio-fs` керується стандартним FUSE-протоколом ядра Linux, доповненим новими opcodes для керування регіонами Direct Access (DAX).

### 3.1 Конфігураційний простір PCI virtio_fs_config

Пристрій `virtio-fs` експортує у свій PCI Configuration Space структуру `virtio_fs_config`:

```c
struct virtio_fs_config {
    uint8_t tag[36];             /* UTF-8 назва, доповнена нулями; якщо займає всі 36 байтів — без завершального нуля */
    uint32_t num_request_queues; /* Кількість паралельних робочих черг запитів FUSE */
};
```

Поле `tag` містить ідентифікатор каталогу (наприклад, `my_shared_dir`), який передається гостьовій утиліті `mount`:
`mount -t virtiofs my_shared_dir /mnt/shared`

Поле `num_request_queues` вказує кількість Virtqueue черг для обробки запитів. Багаточерговість (Multi-queue) дозволяє кожному ядру CPU гостя мати власну чергу до `virtiofsd`, усуваючи конфлікти блокувань при паралельних файлових операціях.

---

### 3.2 Керування мапінгом DAX: FUSE_SETUPMAPPING та FUSE_REMOVEMAPPING

Для прямого відображення сторінок сторінкового кешу хоста у Shared Memory Region ВМ використовуються спеціальні FUSE-команди:

```c
#define FUSE_SETUPMAPPING    48
#define FUSE_REMOVEMAPPING 49

struct fuse_setupmapping_in {
    uint64_t fh;             /* Хендл відкритого файла, виданий у відповіді на FUSE_OPEN */
    uint64_t foffset;        /* Зсув усередині файла на хості */
    uint64_t len;            /* Довжина ділянки відображення в байтах */
    uint64_t flags;          /* Прапорці доступу (FUSE_SETUPMAPPING_FLAG_READ / WRITE) */
    uint64_t moffset;        /* Зсув усередині Shared Memory Region ВМ */
};

struct fuse_removemapping_in {
    uint32_t count;          /* Кількість елементів для видалення */
    uint32_t pad;
    /* Далі слідує масив struct fuse_removemapping_one[count] */
};

struct fuse_removemapping_one {
    uint64_t moffset;        /* Зсув усередині Shared Memory Region ВМ */
    uint64_t len;            /* Довжина ділянки для звільнення */
};
```

Послідовність виконання мапінгу DAX:
1. Гостьова ОС отримує сторінкове переривання (Page Fault) при доступі до адреси у своєму Shared Memory Region.
2. Драйвер `virtiofs.ko` надсилає запит `FUSE_SETUPMAPPING` з параметрами `foffset` (де лежать дані у файлі) та `moffset` (куди їх прикрутити в RAM ВМ).
3. Демон `virtiofsd` KVM не чіпає: він просить гіпервізор (повідомленням зворотного каналу `vhost-user`) зробити `mmap(MAP_FIXED)` потрібного діапазону файла всередину вже зареєстрованого вікна спільної пам'яті, а тоді повертає ядру статус успіху `0`.
4. Ядро гостя відновлює виконання інструкції CPU. Тепер читання відбувається зі швидкістю фізичної RAM.

---

### 3.3 Ініціалізація та узгодження можливостей FUSE_INIT

Під час монтування файлової системи `virtiofs` ядро гостя надсилає перше повідомлення `FUSE_INIT`. Воно містить структури узгодження версій та capabilities:

```c
struct fuse_init_in {
    uint32_t major;        /* Мажорна версія FUSE протоколу (7) */
    uint32_t minor;        /* Мінорна версія FUSE протоколу (наприклад, 38) */
    uint32_t max_readahead;/* Максимальний розмір попереднього читання в байтах */
    uint32_t flags;        /* Бітова маска прапорців capabilities гостя */
    uint32_t flags2;       /* Розширені прапорці capabilities */
    uint32_t unused[11];
};

struct fuse_init_out {
    uint32_t major;
    uint32_t minor;
    uint32_t max_readahead;
    uint32_t flags;
    uint16_t max_background;
    uint16_t congestion_threshold;
    uint32_t max_write;    /* Максимальний розмір блоку запису */
    uint32_t time_gran;    /* Точність позначок часу (в наносекундах) */
    uint16_t max_pages;    /* Максимальна кількість сторінок у виклику */
    uint16_t map_alignment;/* Вирівнювання для DAX мапінгів (log2 від розміру сторінки) */
    uint32_t flags2;       /* Розширені прапорці capabilities */
    uint32_t unused[7];    /* Зарезервовано; частину вже зайняли новіші версії протоколу */
};
```

Ключові прапорці capabilities для `virtio-fs`:
* `FUSE_CAP_MAP_ALIGNMENT` (`1 << 26`): Прапорець іде у зворотний бік — це демон `virtiofsd` у відповіді `fuse_init_out` повідомляє ядро гостя, що зсуви `foffset` і `moffset` мають бути вирівняні, а поле `map_alignment` каже, наскільки саме (log2 від потрібного розміру).
* `FUSE_CAP_POSIX_LOCKS` (`1 << 1`): Вмикає прокидання блокувань файлів на рівні ядра хоста.
* `FUSE_CAP_EXPLICIT_INVAL_DATA` (`1 << 25`): Дозволяє демону `virtiofsd` примусово інвалідувати сторінковий кеш гостя, коли файл змінюється на хості.
