# ⚙️ Зібрати integrity, зіпсувати байт і дати дзеркалу його полагодити

Усе, про що тут ідеться, вміщається в один файл на диску, кілька команд і один зіпсований байт: ми зберемо шар цілісності над звичайним файлом-образом, підмінимо в цьому образі один символ повз шар — і подивимося, чи справді читання після цього стане помилкою, а не тихим сміттям. Далі те саме зробимо під дзеркалом і поруч поставимо контрольний дослід — таке саме дзеркало без шару, щоб побачити різницю не на словах.

Потрібні `losetup`, `integritysetup` (пакет `cryptsetup`), `mdadm` і права root. Робіть це на чернетковій машині: команди пишуть на блокові пристрої, а помилка в імені `/dev/loop*` коштує дорого.

## Стенд: файл, який прикидається диском

Замість диска беремо файл і [підкладаємо його блоковим пристроєм](book:unix-linux/loop-device) — ядро зробить із файла `/dev/loopN`, і все, що вище, працюватиме так, наче це носій. Нам це дає головне: до «поверхні носія» можна дотягтися звичайним `dd`, не чіпаючи шару цілісності.

```bash
sudo truncate -s 256M /var/tmp/int0.img
sudo losetup --find --show /var/tmp/int0.img
# /dev/loop0

# --batch-mode прибирає питання-підтвердження; типовий алгоритм і так crc32c
sudo integritysetup format --batch-mode --integrity crc32c \
     --sector-size 4096 /dev/loop0
sudo integritysetup open /dev/loop0 int0
sudo integritysetup status int0
```

`format` не просто пише суперблок — він **затирає весь пристрій**, бо інакше в області тегів лишиться сміття й перше ж читання поскаржиться. На 256 мегабайтах це секунди; на справжньому диску це години, і саме тому існує `--no-wipe`, який лишає пристрій із завідомо неправильними тегами.

Далі — файлова система й упізнаваний вміст. Візерунок нам знадобиться, щоб потім знайти дані просто очима в сирому образі.

```bash
sudo mkfs.ext4 -q /dev/mapper/int0
sudo mkdir -p /mnt/int && sudo mount /dev/mapper/int0 /mnt/int
seq 1 4000 | sudo tee /mnt/int/probe.txt >/dev/null
sudo sha256sum /mnt/int/probe.txt
sudo sync
```

## Зіпсувати байт так, щоб дослід не збрехав

Тепер найважливіше місце всього досліду, і воно не про цілісність, а про кеші. Між `cat` і байтом у файлі-образі стоїть чотири схованки, і кожна вміє віддати старі байти замість нових.

![Чотири шари кешу між читанням файла і байтом у файлі-образі, і чим кожен спорожнити](/reference/unix-linux/devices/dm-integrity/img/cache-stack.svg)

*Найнижчий шар — єдиний, який працює нам на руку: буферизований `dd` пише в ту саму сторінку файла, з якої читає `loop`, тож вони узгоджені самі собою.*

Ці чотири шари можна розганяти поодинці — `sync`, `blockdev --flushbufs`, `echo 3 | sudo tee /proc/sys/vm/drop_caches`. Порядок тут не довільний: `drop_caches` викидає лише **чисті** сторінки, тож без попереднього `sync` брудні залишаться на місці — про це докладно в [кеші сторінок і `fsync`](book:unix-linux/page-cache-durability). Але третій шар, журнал цілі, розганяється надійно лише одним способом: закриттям. Тому найчесніший порядок дій — відмонтувати й закрити, псувати на спокійному образі, а тоді відкрити наново.

```bash
sudo umount /mnt/int
sudo integritysetup close int0          # журнал догравається до кінця

OFF=$(grep -abo '^3999$' /var/tmp/int0.img | head -1 | cut -d: -f1)
echo "візерунок лежить у сирому образі за зсувом $OFF"
printf 'X' | sudo dd of=/var/tmp/int0.img bs=1 seek="$OFF" \
     conv=notrunc status=none
```

Те, що `grep` узагалі знайшов рядок у образі, саме собою повчальне: шар цілісності не шифрує й не переставляє дані — він лише кладе поряд чотири байти тега. Ми щойно змінили один символ під цим тегом, і ніхто про це не знає.

```bash
sudo integritysetup open /dev/loop0 int0
sudo mount /dev/mapper/int0 /mnt/int
sudo cat /mnt/int/probe.txt > /dev/null
# cat: /mnt/int/probe.txt: Input/output error

sudo dmesg | tail -4
# device-mapper: integrity: dm-0: Checksum failed at sector 0x1a48
# Buffer I/O error on dev dm-0, logical block 3401, async page read
sudo dmsetup status int0
# 0 507904 integrity 1 507904 -
#                              ^ позиція перерахунку («-» — не рахували)
#                        ^ скільки секторів віддає ціль нагору
#              ^ лічильник розбіжностей
```

Ось і весь вердикт. Шістнадцяткове число в `dmesg` — номер сектора **на пристрої цілісності**, не в образі; ім'я `dm-0` звіряється командою `ls -l /dev/mapper/int0`. Файловій системі при цьому дісталася звичайна помилка вводу-виводу, хоч ціль повернула `EILSEQ`, «неприпустима послідовність байтів»: різницю між «не зміг прочитати» й «прочитав, і це не те» ext4 нагору не проносить.

## Те саме під дзеркалом — і контроль без шару

Тепер збираємо дві такі ноги й ставимо [дзеркало md raid1](book:unix-linux/md-raid) **над** ними.

```bash
for i in 0 1; do
  sudo truncate -s 256M /var/tmp/leg$i.img
  L=$(sudo losetup --find --show /var/tmp/leg$i.img)
  sudo integritysetup format --batch-mode --integrity crc32c \
       --sector-size 4096 "$L"
  sudo integritysetup open "$L" leg$i
done

sudo mdadm --create /dev/md/itest --level=1 --raid-devices=2 \
     --metadata=1.2 /dev/mapper/leg0 /dev/mapper/leg1
sudo mkfs.ext4 -q /dev/md/itest && sudo mount /dev/md/itest /mnt/int
seq 1 4000 | sudo tee /mnt/int/probe.txt >/dev/null
sudo sync && sudo umount /mnt/int && sudo mdadm --stop /dev/md/itest
sudo integritysetup close leg0 && sudo integritysetup close leg1
```

Псуємо байт **лише в `leg0.img`**, збираємо все назад і просимо масив прочитати обидві ноги повністю:

```bash
OFF=$(grep -abo '^3999$' /var/tmp/leg0.img | head -1 | cut -d: -f1)
printf 'X' | sudo dd of=/var/tmp/leg0.img bs=1 seek="$OFF" \
     conv=notrunc status=none
# …відкрити обидві цілі, зібрати масив, змонтувати…

sudo sha256sum /mnt/int/probe.txt        # той самий, що й до псування
MD=$(basename "$(readlink -f /dev/md/itest)")
echo check | sudo tee /sys/block/$MD/md/sync_action
cat /sys/block/$MD/md/mismatch_cnt
sudo dmesg | grep -E 'Checksum failed|read error corrected'
# device-mapper: integrity: dm-1: Checksum failed at sector 0x1a48
# md/raid1:md127: read error corrected (8 sectors at 6728 on dm-1)
```

Масив дістав із однієї ноги не байти, а відмову — а з відмовою на читанні RAID уміє працювати від народження: узяти копію з іншої ноги, віддати її нагору й **записати добрі байти назад** на ту, що збрехала. Зіпсоване місце полагоджене, і лічильник розбіжностей при цьому цілком може лишитися нулем: md не порівнював два успішні читання, він отримав помилку.

Слово «полагоджене» варто не приймати на віру, а перевірити — і перевірка тут навдивовижу пряма. Розберімо стос до самого низу й погляньмо в сирий образ хворої ноги: якщо ремонт справді відбувся, підмінений символ повернувся на місце, а тег над ним перерахований.

```bash
sudo umount /mnt/int && sudo mdadm --stop /dev/md/itest
sudo integritysetup close leg0 && sudo integritysetup close leg1
sudo dd if=/var/tmp/leg0.img bs=1 skip="$OFF" count=4 status=none | xxd
# 00000000: 3339 3939                                3999
```

Байт `X` зник — на його місці знову цифра, яку туди клав `seq`. Це і є вся суть конструкції в одному рядку виводу: надлишковість завжди лежала поруч, але доти, доки хвора нога відповідала успіхом, дістати з тієї надлишковості користь не було як.

Тепер контроль. Ті самі два образи, те саме дзеркало, той самий зіпсований байт — але без шару цілісності: `mdadm --create` дістає просто `/dev/loop3` і `/dev/loop4`, а `$MD2` — ім'я цього другого масиву.

```bash
echo check | sudo tee /sys/block/$MD2/md/sync_action
cat /sys/block/$MD2/md/mismatch_cnt
# 128    ← не нуль; одиниця обліку — цілий порівняний шматок, а не байт
sudo dmesg | tail -3
# (жодного рядка про те, котра нога винна)
```

Різниця вийшла не кількісна, а якісна. Лічильник каже, що ноги розбіглися, і замовкає: обидві повернули байти успішно, порівняння дає різницю, а вердикту не дає. Гірше того, `sha256sum` тут може віддати **зіпсований** вміст — котра нога відповість, залежить від розподілу читань. І `repair` становища не рятує: він розганяє розбіжність, беручи за істину ту ногу, яку масив вважає першою, — а вона й може бути хворою. Саме тому регулярним завданням ставлять `check`, а не `repair`.

## Скільки коштує журнал: міряти не час, а байти

Секундомір тут поганий свідок — на файлі-образі його показання визначає чужий кеш. Тому міряємо те, що не бреше: скільки секторів насправді лягло на нижній пристрій. Лічильник живе в сьомому полі `/sys/block/loopN/stat`.

Щоб вимір мав сенс, обидва кеші треба прибрати з дороги: `oflag=direct` — щоб `dd` не осідав у кеші блокового пристрою, `losetup --direct-io=on` — щоб `loop` не осідав у сторінковому кеші файла-образу. І файл має бути справжній, а не діркавий, інакше ми поміряємо роботу [розрідженого файла](book:unix-linux/sparse-files), а не шару. Про те, чим саме `oflag=direct` відрізняється від звичайного запису, — окремо: [буферизований і прямий ввід-вивід](book:unix-linux/buffered-and-direct-io).

```bash
run() {   # $1 — зайві прапорці формату («» або --integrity-bitmap-mode)
  sudo integritysetup format --batch-mode --integrity crc32c \
       --sector-size 4096 $1 /dev/loop0
  sudo integritysetup open $1 /dev/loop0 int0
  w0=$(awk '{print $7}' /sys/block/loop0/stat)
  sudo dd if=/dev/zero of=/dev/mapper/int0 bs=1M count=128 \
       oflag=direct conv=fsync
  w1=$(awk '{print $7}' /sys/block/loop0/stat)
  echo "на носій пішло $(( (w1-w0)/2048 )) МіБ на 128 МіБ корисних"
  sudo integritysetup close int0
}

sudo losetup -d /dev/loop0 && sudo rm -f /var/tmp/int0.img
sudo fallocate -l 512M /var/tmp/int0.img          # не діркавий, а справжній
sudo losetup --direct-io=on --find --show /var/tmp/int0.img
# /dev/loop0

run ""                            # журнальний режим
run "--integrity-bitmap-mode"     # бітова мапа
```

Чекайте приблизно такого: журнал — трохи більше за 256 мебібайтів на 128 корисних, бітова мапа — трохи більше за 128. Арифметика проста й перевіряється: журнал кладе кожен байт двічі — спершу в журнал разом із тегом, потім на місце, — а бітова мапа кладе один раз, і зверху в обох випадках ідуть ті самі 0.8 % тегів. Швидкість запису йде за цим числом слідом, і саме тому вона в журнальному режимі приблизно вдвічі менша. Коли той самий вимір роблять секундоміром на реальному диску, кожен прогін повторюють тричі й беруть середній.

## Де це ламається

**Псування не в тому місці.** Перші мегабайти образу — суперблок і журнал цілі, а не дані. Байт, покладений навмання, дасть або мовчанку, або відмову відкрити пристрій. Тому ми й шукаємо зсув за візерунком, а не тицяємо пальцем.

**Візерунок знайшовся двічі.** `grep -abo` віддасть і копію в журналі, якщо дані ще не переїхали на місця. Закриття цілі перед пошуком це знімає.

**Розмір сектора.** `--sector-size 4096` задається при форматуванні й далі незмінний; його ж мусить поважати все, що вище. Забудете — дістанете 512-байтові сектори й увосьмеро більші накладні витрати на теги.

**Читання, яке нічого не показало.** Просте `cat` через дзеркало може взагалі не заглянути в хвору ногу: md розкидає читання між копіями, і ваш запит цілком міг піти на здорову. Тому доказом служить `check` — він читає **обидві** ноги повністю й нічого пропустити не може.

**Автоскладання масиву.** `udev` може підхопити `md`-масив сам, щойно ви відкриєте цілі, — і зробити це раніше, ніж ви встигнете глянути на ноги. Перевіряйте `cat /proc/mdstat` перед кожним кроком.

**Прибирання.** У зворотному порядку, інакше пристрої лишаться зайнятими:

```bash
sudo umount /mnt/int; sudo mdadm --stop /dev/md/itest
sudo integritysetup close leg0; sudo integritysetup close leg1
sudo integritysetup close int0
# відчіплюємо лише свої loop-пристрої: losetup -D зніме ВСІ, зокрема чужі
for f in /var/tmp/int0.img /var/tmp/leg0.img /var/tmp/leg1.img; do
  sudo losetup -j "$f" | cut -d: -f1 | xargs -r sudo losetup -d
  sudo rm -f "$f"
done
```
