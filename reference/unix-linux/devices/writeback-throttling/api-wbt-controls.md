# 📋 Важелі й спостереження за wbt: `wbt_lat_usec`, стан петлі в debugfs і точки трасування

Керують гальмуванням фонового запису рівно одним записуваним числом, а бачать його роботу через вісім файлів у debugfs і чотири точки трасування. Тут зібрано ці імена з точними шляхами, одиницями й значеннями — щоб на три питання («чи механізм узагалі є на цьому пристрої», «чи він увімкнений», «чи гальмує саме зараз») відповідала команда, а не здогад.

## Чи є механізм у цьому ядрі

| Параметр складання | Умова | Що дає |
|---|---|---|
| `CONFIG_BLK_WBT` | — | сам код; без нього немає ні файла в sysfs, ні групи подій у трасуванні |
| `CONFIG_BLK_WBT_MQ` | `default y`, `depends on BLK_WBT` | заводити петлю **типово**, щойно з'явився пристрій. Без нього код є, але петлю піднімає лише ручний запис у `wbt_lat_usec` |

```sh
$ grep BLK_WBT /boot/config-$(uname -r)      # або: zcat /proc/config.gz | grep BLK_WBT
CONFIG_BLK_WBT=y
CONFIG_BLK_WBT_MQ=y
```

Звідки береться `.config` і як рядок `CONFIG_*` перетворюється на код в образі — [конфігурація й збірка ядра](topic:unix-linux/kernel-config-and-build): параметр вмикає гілку складання, а зібране ядро лишає свій набір параметрів у `/boot/config-…` або в `/proc/config.gz`.

Друга умова — сам пристрій. Петлю ядро заводить тільки там, де є черга запитів (blk-mq). Складені пристрої, які приймають bio й передають його нижче (`dm-*`, `md*`), власної черги не мають: файла в них або немає зовсім, або він віддає помилку. Крутити важіль треба тому пристроєві, що лежить в основі.

## Читання `wbt_lat_usec` як діагностика

`/sys/block/<пристрій>/queue/wbt_lat_usec`, читання-запис, **мікросекунди**. Відповідей рівно три:

| Що віддає `cat` | Значить |
|---|---|
| `cat: …: Invalid argument` (`EINVAL`) | політики wbt на черзі немає — не заводили або пристрій не blk-mq |
| `0` | політика є, але вимкнена |
| додатне число | ціль у мікросекундах; механізм працює |

Нуль не каже, **хто** вимкнув. Це показує окремий лічильник `enabled` у debugfs:

| `enabled` | Стан | Як потрапили |
|---|---|---|
| `1` | увімкнено типово | петлю завели при появі пристрою |
| `2` | увімкнено вручну | у `wbt_lat_usec` записали ненульове число |
| `3` | вимкнено типово | вимкнув планувальник |
| `4` | вимкнено вручну | у `wbt_lat_usec` записали `0` |

Поділ на «типово» й «вручну» тут не косметика: ядро скасовує лише ті рішення, які ухвалило саме.

## Запис: три особливі значення

| Записане | Дія | Стан після запису |
|---|---|---|
| `N > 0` | ціль `N` мкс | `2` |
| `-1` | підставити типове значення | `2` |
| `0` | вимкнути | `4` |
| менше за `-1` | `EINVAL`, нічого не змінилося | — |

Типове число, яке підставляє `-1`, ядро вибирає за ознакою обертання:

| `queue/rotational` | Типова ціль | У файлі |
|---|---|---|
| `0` — без обертання | 2 мс | `2000` |
| `1` — обертовий | 75 мс | `75000` |

Тобто `-1` означає не «повернути початковий стан», а «постав типове число» — і налаштування при цьому вважається ручним (стан `2`, не `1`).

**Пастка, через яку запис мовчки не спрацьовує.** Ядро порівнює нове значення з чинним і, якщо вони рівні, виходить одразу — не міняючи й стану. Вимикання ж чинного числа не стирає: воно лишається лежати. Звідси послідовність, яка збиває з пантелику:

```
було:   enabled=1   min_lat_nsec=2000000        # ціль 2 мс, петля працює
echo bfq > queue/scheduler
стало:  enabled=3   min_lat_nsec=2000000        # число те саме, петля вимкнена

echo 2000 > queue/wbt_lat_usec                  # 2000 мкс = 2000000 нс — рівне чинному
стало:  enabled=3                               # запис відкинуто, не змінилося ніщо

echo 0    > queue/wbt_lat_usec                  # спершу збити значення
echo 2000 > queue/wbt_lat_usec                  # тепер число інше — і стан теж
стало:  enabled=2   min_lat_nsec=2000000
```

Надійний спосіб увімкнути механізм вручну — **два записи**: спершу `0`, потім потрібна ціль. Рядок `-1` тієї самої пастки не оминає: він розгортається в типове число, і якщо саме воно вже стоїть, запис теж нічого не зробить.

Ще одна побічна дія: перед зміною ядро зупиняє видачу нових запитів і дочікується завершення наявних — інакше в пристрої лишилися б запити, обліковані за старим порогом. Під навантаженням запис у цей файл видно як коротку паузу.

Записане живе до зникнення пристрою. Постійності досягають [правилом udev](topic:unix-linux/udev-rules) — ядро повідомляє про появу пристрою, udev звіряє подію з правилами й виконує вказані записи в sysfs:

```
# /etc/udev/rules.d/60-wbt.rules
ACTION=="add|change", SUBSYSTEM=="block", KERNEL=="sd[a-z]", \
    ATTR{queue/rotational}=="1", ATTR{queue/wbt_lat_usec}="50000"
```

## Стан петлі: `/sys/kernel/debug/block/<пристрій>/rqos/wbt/`

Каталог існує, лише поки на черзі є політика wbt, і лежить у [debugfs](topic:unix-linux/debugfs) — службовій файловій системі ядра, яку монтують окремо (`mount -t debugfs none /sys/kernel/debug`), читають від root і чий склад між випусками ніхто не зобов'язувався зберігати. Усе тут доступне лише на читання.

| Файл | Од. | Що показує |
|---|---|---|
| `enabled` | 1–4 | стан із таблиці вище |
| `id` | — | номер політики в ланцюжку `rq_qos`; у wbt завжди `0` |
| `min_lat_nsec` | нс | ціль — те саме число, що у `wbt_lat_usec`, лише в наносекундах |
| `curr_win_nsec` | нс | довжина поточного вікна спостереження |
| `wb_normal` | запити | поріг для звичайного запису |
| `wb_background` | запити | поріг для фонового запису й `discard` |
| `inflight` | запити | по рядку на кожну з трьох черг очікування |
| `unknown_cnt` | вікна | скільки вікон поспіль не було ні читань, ні активності |

```sh
# cd /sys/kernel/debug/block/nvme0n1/rqos/wbt
# grep . enabled min_lat_nsec curr_win_nsec wb_normal wb_background
enabled:1
min_lat_nsec:2000000
curr_win_nsec:100000000
wb_normal:8
wb_background:4
# cat inflight
0: inflight 0
1: inflight 0
2: inflight 0
```

Три рядки `inflight` — три окремі черги очікування, а не три види лічильника:

| Рядок | Черга |
|---|---|
| `0` | звичайний і фоновий запис |
| `1` | запис у своп |
| `2` | `discard` |

Повної дозволеної глибини окремим файлом немає — її показує лише точка трасування `wbt_step`. Але глибина відновлюється з порогів, бо всі три числа рахуються з одного:

```
база          = min(16, глибина черги пристрою)
max_depth     = 1 + ((база − 1) >> щабель)         # щабель > 0
wb_normal     = (max_depth + 1) / 2                # цілочисельно
wb_background = (max_depth + 3) / 4
вікно, нс     = 100000000 · 16 / ⌊√((щабель+1)·256)⌋
```

Окремий випадок: коли `max_depth` не більший за 2, порогом звичайного запису стає сама глибина, а фонового — одиниця. Звідси вся шкала для типової бази 16:

| Щабель | `max_depth` | `wb_normal` | `wb_background` | `curr_win_nsec` |
|---|---|---|---|---|
| 0 | 16 | 8 | 4 | `100000000` (100 мс) |
| 1 | 8 | 4 | 2 | `72727272` (≈72.7 мс) |
| 2 | 4 | 2 | 1 | `59259259` (≈59.3 мс) |
| 3 | 2 | 2 | 1 | `50000000` (50 мс) |
| 4 | 1 | 1 | 1 | `45714285` (≈45.7 мс) |

Від'ємний щабель означає протилежне — глибину підняли вище за базу; вікно при цьому лишається рівно `100000000`.

> 🔧 **Навіщо це.** Одне число `curr_win_nsec` відповідає на питання «чи гальмує зараз» без жодного трасування: вікно стискається тільки при додатному щаблі, тож будь-яке значення, менше за `100000000`, означає, що механізм саме тепер тримає зворотний запис. Друга ознака поруч — `inflight` у рядку `0`, що вперся в `wb_background`: запити далі не проходять, і той, хто подає, спить. Разом ці два числа знімають найчастіший спір «диск повільний» проти «його притримують».

## Точки трасування

Група `wbt` — чотири події; каталог існує за тієї ж умови `CONFIG_BLK_WBT=y`.

| Подія | Коли спрацьовує | Поля |
|---|---|---|
| `wbt_timer` | наприкінці **кожного** вікна | `status`, `step`, `inflight` (сума по трьох чергах) |
| `wbt_lat` | **лише** коли ціль порушено | `latency` — мкс |
| `wbt_stat` | при порушенні, а також наприкінці вдалого вікна, поки щабель не нульовий | `rmean`, `rmin`, `rmax`, `rsamples` і те саме для запису — **нс** |
| `wbt_step` | лише коли щабель справді змінився | `msg` (`scale up` / `scale down`), `step`, `window` — мкс, `background`, `normal`, `max` |

Числове поле `status` у `wbt_timer` і є вироком вікна:

| `status` | Що зміряно | Що робить петля |
|---|---|---|
| `1` | мінімум затримки читань вклався в ціль | глибину піднімають на щабель |
| `2` | не було ні читань, ні активності | нічого; після п'яти таких вікон повзе до нейтрального щабля |
| `3` | читань не було, але були записи | глибину піднімають |
| `4` | мінімум перевищив ціль | глибину ріжуть |

Вмикають через tracefs — файлову систему керування трасуванням ядра ([ftrace і трасувальні точки](topic:unix-linux/ftrace-kernel-tracing): подія вмикається записом одиниці у свій файл `enable`, готовий текст читають із `trace_pipe`):

```sh
# mount -t tracefs none /sys/kernel/tracing        # якщо не змонтовано
# cd /sys/kernel/tracing
# echo 'name == "259:0"' > events/wbt/filter       # див. cat /sys/block/nvme0n1/dev
# echo 1 > events/wbt/enable
# cat trace_pipe
```

Поле `name` — не ім'я диска, а пара «старший:молодший номер» того самого пристрою; без фільтра в потік ідуть усі носії разом. Порядок рядків у межах одного вікна сталий: спершу порушення, далі вирок таймера, наприкінці — зміна щабля, якщо вона сталася.

```
kworker/2:1H-193 [002] ..... 41.532: wbt_lat: 259:0: latency 3187us
kworker/2:1H-193 [002] ..... 41.532: wbt_stat: 259:0: rmean=3402145, rmin=3187004, rmax=5211870, rsamples=12, …
kworker/2:1H-193 [002] ..... 41.532: wbt_timer: 259:0: status=4, step=0, inflight=16
kworker/2:1H-193 [002] ..... 41.532: wbt_step: 259:0: scale down: step=1, window=72727us, background=2, normal=4, max=8
```

Вимикають записом нуля в той самий `events/wbt/enable`; фільтр скидають так само — `echo 0 > events/wbt/filter`.

Відсутність `wbt_timer` у потоці — теж показання: таймер переставляють на нове вікно лише поки щабель ненульовий або в пристрої є незавершені записи. Тиша означає, що петля стоїть на нейтральному щаблі й нікого не тримає.

## Чому під BFQ порожньо

У [планувальника BFQ](topic:unix-linux/io-schedulers) — того, що ділить смугу між процесами за вагами, — є власне притримування запису, і два регулятори однієї величини разом розхитують систему. Тому планувальник несе прапорець «wbt тут не потрібен», і ядро на нього зважає:

| Дія | Що стається зі станом |
|---|---|
| перемкнули на `bfq` | `1` → `3`; `cat wbt_lat_usec` віддає `0` |
| перемкнули з `bfq` назад | `3` → `1` |
| стан був `2` (ручний), перемкнули на `bfq` | лишається `2` — механізм працює далі |
| стан `3`, спробували завести вручну | заводиться, але з поправкою на пастку двох записів |

Останні два рядки — саме та лазівка, про яку варто знати свідомо: ручно ввімкнений wbt під BFQ не вимикається, і обидва механізми притримують запис одночасно. Для вимірювання це буває потрібно, для постійної роботи — навряд.
