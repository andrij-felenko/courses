# 📋 UAPI ABI та ioctl-інтерфейс /dev/watchdog

Цей довідник описує двосторонній ABI-контракт простору користувача з підсистемою Watchdog ядра Linux (`<linux/watchdog.h>`), включаючи структури даних, маски прапорців, системні виклики `ioctl` та параметри нод `sysfs`. Контракт визначає способи налаштування таймаутів, зчитування причин попереднього перезавантаження та керування фоновим сторожовим таймером через символьні пристрої `/dev/watchdog` та `/dev/watchdogN`. Двостадійний зв'язок гарантує, що додаток супервізії може адаптувати свою поведінку під конкретні апаратні можливості підключеного контролера.

## 1. Базові структури даних UAPI

Для роботи з інтерфейсом сторожового таймера додаток простору користувача повинен підключити заголовочний файл ядра:

```c
#include <linux/watchdog.h>
```

Головною структурою опису апаратного драйвера є `watchdog_info`. Вона заповнюється ядром при виконанні виклику `WDIOC_GETSUPPORT`:

```c
struct watchdog_info {
    __u32 options;          /* Бітова маска підтримуваних функцій (WDIOF_*) */
    __u32 firmware_version; /* Версія прошивки контролера або драйвера */
    __u8  identity[32];     /* Рядок ідентифікатора драйвера (ASCII, null-terminated) */
};
```

Поле `identity` містить читабельну назву драйвера (наприклад, `"iTCO_wdt"` для систем Intel або `"Software Watchdog"` для емулятора `softdog`), що дозволяє демону ідентифікувати тип апаратури. Ядро гарантує, що рядок довжиною 32 байти завжди завершується нульовим символом `\0`. Поле `firmware_version` повертає номер версії мікропрограми контролера або ревізії кремнію.

### Бітові прапорці опцій та статусу (`options` / `status` / `bootstatus`)

Бітова маска `options` визначає, які саме функції підтримуються даним сторожовим таймером. Ці ж самі прапорці повертаються у виклику `WDIOC_GETSTATUS` для опису поточного стану помилок, або у виклику `WDIOC_GETBOOTSTATUS` для аналізу причин останнього аварійного перезавантаження системи:

| Прапорець | Двійкова маска | Опис |
| :--- | :--- | :--- |
| `WDIOF_OVERHEAT` | `0x0001` | Спрацювання через критичний перегрів процесора або плати |
| `WDIOF_FANFAULT` | `0x0002` | Відмова вентилятора охолодження |
| `WDIOF_EXTERN1` | `0x0004` | Спрацювання через сигнал на першій зовнішній тривожній лінії |
| `WDIOF_EXTERN2` | `0x0008` | Спрацювання через сигнал на другій зовнішній тривожній лінії |
| `WDIOF_POWERUNDER` | `0x0010` | Просідання напруги живлення нижче допустимого порогу |
| `WDIOF_CARDRESET` | `0x0020` | Останнє скидання виконав саме сторожовий таймер |
| `WDIOF_POWEROVER` | `0x0040` | Небезпечний сплеск напруги живлення |
| `WDIOF_SETTIMEOUT` | `0x0080` | Підтримка динамічного встановлення нового інтервалу таймауту |
| `WDIOF_MAGICCLOSE` | `0x0100` | Підтримка протоколу безпечного зупинення таймера символом `'V'` |
| `WDIOF_PRETIMEOUT` | `0x0200` | Підтримка попереднього переривання (Pretimeout) перед скиданням |
| `WDIOF_KEEPALIVEPING` | `0x8000` | Підтвердження успішного виконання скидання лічильника |

Аналіз поля `bootstatus` після завантаження системи є критично важливим для системної діагностики. Якщо після ввімкнення `bootstatus & WDIOF_OVERHEAT` повертає істину, це свідчить про те, що попередній ребут стався через термальне аварійне відключення, а не через програмне зависання. Якщо повертається `WDIOF_POWERUNDER`, причиною скидання було знеструмлення або просідання лінії живлення `VCC`.

## 2. Команди `ioctl` для `/dev/watchdog`

Взаємодія з пристроєм здійснюється через стандартний системний виклик `ioctl(fd, cmd, arg)`. Усі команди серії Watchdog мають базовий літерний код `WATCHDOG_IOCTL_BASE` (`'W'`):

| Команда `ioctl` | Напрямок / Тип аргументу | Опис системної операції |
| :--- | :--- | :--- |
| `WDIOC_GETSUPPORT` | `_IOR('W', 0, struct watchdog_info)` | Зчитування можливостей апаратури у структуру `watchdog_info` |
| `WDIOC_GETSTATUS` | `_IOR('W', 1, int)` | Зчитування поточного масиву прапорців помилок таймера |
| `WDIOC_GETBOOTSTATUS` | `_IOR('W', 2, int)` | Зчитування причин попереднього перезавантаження системи |
| `WDIOC_GETTEMP` | `_IOR('W', 3, int)` | Зчитування поточного значення термодатчика контролера |
| `WDIOC_SETOPTIONS` | `_IOR('W', 4, int)` | Примусове увімкнення або вимкнення таймера прапорцями `WDIOS_*`; напрямок у макросі історично записаний як `_IOR`, хоча значення йде в ядро |
| `WDIOC_KEEPALIVE` | `_IOR('W', 5, int)` | Скидання апаратного лічильника зворотного відліку (Heartbeat ping) |
| `WDIOC_SETTIMEOUT` | `_IOWR('W', 6, int)` | Встановлення нового таймауту у секундах (повертає фактично встановлений) |
| `WDIOC_GETTIMEOUT` | `_IOR('W', 7, int)` | Отримання поточного налаштованого таймауту в секундах |
| `WDIOC_SETPRETIMEOUT` | `_IOWR('W', 8, int)` | Встановлення інтервалу попередження Pretimeout у секундах |
| `WDIOC_GETPRETIMEOUT` | `_IOR('W', 9, int)` | Отримання поточного значення інтервалу Pretimeout |
| `WDIOC_GETTIMELEFT` | `_IOR('W', 10, int)` | Зчитування кількості секунд, що залишилися до спрацювання скидання |

Виклики `WDIOC_SETTIMEOUT` та `WDIOC_SETPRETIMEOUT` приймають вказівник на ціле число із бажаною кількістю секунд. Оскільки апаратні контролери мають фіксовані дискретні кроки лічильника, ядро коригує значення до найближчого підтримуваного апаратурою і перезаписує змінну фактично встановленим значенням.

### Коди помилок системного виклику `ioctl`

У просторі користувача `ioctl` повертає `-1`, а код помилки лягає в `errno`; усередині ядра ті самі коди повертаються з мінусом:

* `-EFAULT`: Аргумент `arg` вказує на неприпустиму область пам'яті простору користувача.
* `-EINVAL`: Передане значення таймауту знаходиться за межами `min_timeout` та `max_timeout`.
* `-EBUSY`: Символьний пристрій уже відкрито іншим процесом супервізії.
* `-EOPNOTSUPP` / `-ENOTTY`: Драйвер апаратно не підтримує запитану команду (наприклад, `WDIOC_GETTEMP` на чипсеті без термодатчика).

### Динамічне увімкнення та вимкнення (`WDIOC_SETOPTIONS`)

Для тимчасового деактивування апаратного таймера без закриття файлового дескриптора передається бітова маска опцій:
* `WDIOS_DISABLECARD` (`0x0001`) — Тимчасово призупинити апаратний зворотний відлік.
* `WDIOS_ENABLECARD` (`0x0002`) — Відновити роботу апаратного лічильника.

## 3. Протокол закриття "Magic Close" та безпека

Якщо драйвер повертає прапорець `WDIOF_MAGICCLOSE` у масці `options`, підсистема ядра `watchdog_dev` вмикає механізм захисту від випадкового розриву зв'язку з демоном супервізії. Для штатного вимкнення сторожового таймера демон зобов'язаний перед викликом `close()` записати у дескриптор символ `'V'` (`0x56` у кодуванні ASCII):

```c
/* Протокол безпечного зупинення таймера перед close() */
char magic_val = 'V';   /* саме char: write() бере перший байт, і в int він залежав би від порядку байтів */
if (write(fd, &magic_val, 1) < 0) {
    perror("Помилка відправки Magic Close");
}
close(fd);
```

Під час виконання виклику `write(fd, &magic_val, 1)` ядро встановлює внутрішній прапорець `WDOG_ALLOW_RELEASE` у контексті `watchdog_core_data`, який тримає поряд зі `struct watchdog_device`. 

Коли VFS виконує виклик `close(fd)`:
* **Якщо прапорець `WDOG_ALLOW_RELEASE` встановлено**: Ядро викликає операцію драйвера `ops->stop()` і деактивує апаратний таймер.
* **Якщо прапорець відсутній (аварійний краш демона `SIGKILL` або `SIGSEGV`)**: Ядро залишає апаратний таймер увімкненим. Оскільки демон загинув і не зможе надсилати Heartbeat, після вичерпання таймауту апаратура примусово перезавантажить систему.
* **Параметр `nowayout`**: Якщо ядро скомпільовано з конфігураційним параметром `CONFIG_WATCHDOG_NOWAYOUT=y` або модуль завантажено з аргументом `nowayout=1`, ядро ігнорує запис символу `'V'`. У цьому режимі таймер неможливо зупинити програмно до перезавантаження.

## 4. Інтерфейс підсистеми у sysfs

Для кожного зареєстрованого сторожового таймера ядро Linux створює каталог атрибутів у файловій системі `sysfs` за шляхом `/sys/class/watchdog/watchdogN/`. Інтерфейс `sysfs` дозволяє моніторити стан сторожових таймерів інструментами адміністрування без відкриття файлу символьного пристрою у монопольному режимі:

```
/sys/class/watchdog/watchdogN/
├── bootstatus    (r--)  Маска причин останнього перезавантаження у форматі HEX
├── identity      (r--)  Назва драйвера та контролера (ASCII рядок)
├── min_timeout   (r--)  Мінімальний допустимий таймаут апаратури у секундах
├── max_timeout   (r--)  Максимальний допустимий таймаут апаратури у секундах
├── timeout       (r--)  Поточний таймаут у секундах
├── pretimeout    (r--)  Поточний інтервал Pretimeout у секундах
├── timeleft      (r--)  Кількість секунд, що залишилися до спрацювання скидання
├── options       (r--)  Маска апаратних опцій WDIOF_* у HEX-форматі
└── status        (r--)  Поточний статус помилок драйвера у HEX-форматі
```

Зчитування файлу `timeleft` з інтервалом в 1 секунду дозволяє візуалізувати зворотний відлік таймера у консольних утилітах моніторингу. Змінити таймаут через `sysfs` не можна: атрибути тут лише для читання, і єдиний шлях запису — `WDIOC_SETTIMEOUT` на відкритому дескрипторі пристрою (із `sysfs` записується хіба що вибір регулятора, `pretimeout_governor`).

Поява й зникнення самих пристроїв `watchdogN` супроводжується звичайними `uevent` через netlink до `udevd`, тож правила `udev` можуть, наприклад, запускати демона супервізії одразу після реєстрації таймера. А от подія Pretimeout окремого `uevent` не породжує: штатні регулятори або вводять ядро в паніку, або лише лишають запис у журналі.
