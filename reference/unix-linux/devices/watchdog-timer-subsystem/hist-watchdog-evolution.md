# 📜 Еволюція підсистеми Watchdog: від плати ISA до Watchdog Core

Надійність серверних та вбудованих систем вимагає гарантованого відновлення після апаратних та програмних зависань, коли процесор втрачає здатність виконувати інструкції або потрапляє у безкінечний цикл із блокуванням переривань. Вбудовані та зовнішні сторожові таймери (Watchdog Timers) розроблялися як фізичні лічильники зворотного відліку, що при досягненні нуля примусово виставляють сигнал скидання на лінію `RESET#` процесора або контролера живлення (PMIC). Історія підсистеми Watchdog у Linux ілюструє шлях від фрагментованого набору вузькоспеціалізованих драйверів 1990-х років до уніфікованого ядра `watchdog_core` та дворівневої супервізії процесів у сучасних дистрибутивах.

## 1. Ера фрагментації драйверів (Linux 1.x — 2.4)

На початку 1990-х років апаратні сторожові таймери постачалися у вигляді окремих плат розширення для шини ISA або PCI (таких як ICS WDT500/501, Berkshire Products PC Watchdog чи Eurotech WDT). Кожен виробник розробляв власний символьний драйвер для Linux. Драйвери самостійно реєстрували персональні символьні пристрої, виділяли окремі молодші номери (minor numbers) у простір `miscdevice` (major 10) і реалізовували власні структури викликів `ioctl`.

Відсутність єдиної абстракції призводила до серйозних проблем сумісності:
* **Неузгодженість команди "Heartbeat"**: Деякі драйвери вимагали запису будь-якого байта у `/dev/watchdog` для скидання таймера, інші підтримували спеціальний `ioctl`, а дехто скидав лічильник лише при читанні з пристрою.
* **Різний таймаут за замовчуванням**: у різних плат апаратні таймаути різнилися від часток секунди до десятків секунд, здебільшого без можливості змінити їх із простору користувача.
* **Небезпека випадкового закриття**: Якщо демон супервізії примусово завершувався через помилку `SIGSEGV` або `SIGKILL`, файл `/dev/watchdog` закривався VFS. В одних драйверах закриття файлу зупиняло таймер (залишаючи систему без захисту), а в інших — залишало таймер активним, що призводило до неминучого перезавантаження системи через відсутність подальших пингів.

Для вирішення проблеми випадкового вимкнення таймера розробники запровадили концепцію "Magic Close" (чарівне закриття). Драйвер вимикав таймер при закритті файлу лише у тому разі, якщо безпосередньо перед викликом `close()` у дескриптор було записано символ `'V'` (`0x56`). Будь-яке аварійне завершення демона без запису `'V'` залишало таймер активним, гарантуючи примусове перезавантаження завислої системи.

## 2. Програмний емулятор Softdog

У середині 1990-х Алан Кокс (Alan Cox) створив модуль `softdog.c` — програмний сторожовий таймер, який не потребував спеціального апаратного забезпечення. `softdog` використовував внутрішній таймер ядра Linux (`timer_list` або пізніше `hrtimer`).

```
+--------------------------------------------------------------------+
|                         softdog.c Driver                           |
|                                                                    |
|  +-------------------+       Timeout        +-------------------+  |
|  | Kernel hrtimer    | -------------------> | panic() / reboot  |  |
|  +-------------------+                      +-------------------+  |
|            ^                                                       |
|            | WDIOC_KEEPALIVE                                       |
|  +-------------------+                                             |
|  | /dev/watchdog VFS |                                             |
|  +-------------------+                                             |
+--------------------------------------------------------------------+
```

Коли програмний таймер `softdog` згасав через відсутність пингів із простору користувача, він викликав функцію ядра `panic()` або `emergency_restart()`. Хоча `softdog` не міг врятувати систему при глибокому блокуванні апаратної шини або зависанні обробника переривань (коли процесор не реагує на таймерні переривання ядра), він став стандартним інструментом для моніторингу високорівневих демонів у звичайних серверах.

## 3. Реформа Watchdog Core (Linux 3.5+)

Зі зростанням кількості SoC для вбудованих систем (ARM, MIPS, PowerPC) у ядрі опинилися сотні драйверів сторожових таймерів з дубльованим кодом. На початку 2010-х супровідник підсистеми Вім Ван Себрук (Wim Van Sebroeck) провів масштабну реструктуризацію: спільне ядро `watchdog_core` увійшло до ядер серії 3.x і поступово, реліз за релізом, забрало собі логіку, дубльовану в драйверах.

Нова архітектура розділила підсистему на три чіткі шари:
1. **`watchdog_core.c`**: Загальна інфраструктура реєстрації та керування об'єктами `struct watchdog_device`.
2. **`watchdog_dev.c`**: Єдиний мультиплексор символьних пристроїв `/dev/watchdog` та `/dev/watchdogN`, який взяв на себе всю логіку VFS, перевірку прав, обробку `ioctl`, безпечне закриття Magic Close та захист від паралельних відкриттів (`EBUSY`).
3. **Низькорівневі драйвери**: Вузькі драйвери (такі як `iTCO_wdt.c` для систем Intel або `bcm2835_wdt.c` для Raspberry Pi), які лише заповнюють структуру `struct watchdog_ops` (функції `start`, `stop`, `ping`, `set_timeout`) і реалізують безпосередню взаємодію з регістрами вбудованого периферійного таймера.

```
                    Userspace Daemon (systemd)
                                |
                   /dev/watchdog (Character Dev)
                                |
             +------------------------------------+
             |  watchdog_dev.c (VFS & ioctl multiplexer)
             +------------------------------------+
                                |
             +------------------------------------+
             | watchdog_core.c (struct watchdog_device)
             +------------------------------------+
               /               |                \
              /                |                 \
     +----------------+ +----------------+ +----------------+
     |   iTCO_wdt     | |   sp805_wdt    | |    softdog     |
     | (Intel PCH HW) | | (ARM SP805 HW) | | (Kernel Timer)|
     +----------------+ +----------------+ +----------------+
```

Реформа Watchdog Core також додала підтримку підсистеми `sysfs` (`/sys/class/watchdog/watchdogN/`), що дозволило зчитувати статус пристроїв, таймаути та апаратні можливості без відкриття символьного пристрою.

## 4. Апаратне розвантаження Heartbeat та Pretimeout Governors

У наступних версіях ядра підсистема отримала два важливі розширення:

### Апаратне розвантаження (HW Keepalive Pinging)
Деякі апаратні сторожові таймери мають дуже короткий максимальний таймаут (наприклад, 1-2 секунди). Якщо демон у просторі користувача не може гарантувати пінг з інтервалом 500 мс через навантаження на систему, ядро Linux може взяти на себе періодичний пінг апаратури за допомогою внутрішнього таймера ядра `watchdog_kworker`. Демон із простору користувача спілкується з ядром з великим інтервалом (наприклад, 60 секунд), а ядро розвантажує апаратний таймер, пінгуючи його кожні 500 мілісекунд. Якщо демон зависає, ядро припиняє пингувати апаратуру, і через 1-2 секунди стається апаратний скид.

### Фреймворк Pretimeout
Багато сучасних Watchdog-контролерів підтримують двостадійне попередження: за кілька секунд до критичного скидання система генерує немасковане переривання (NMI) або високопріоритетне IRQ. Фреймворк `watchdog_pretimeout.c` дозволив підключати регулятори (Governors):
* `panic`: Примусово переводить ядро у стан `panic()`, що дозволяє зберегти дампи пам'яті (Kdump) та системні логи перед перезавантаженням.
* `noop`: Не робить нічого — у журналі лишається лише повідомлення самої підсистеми про подію Pretimeout.

Ці два регулятори — увесь набір, який є в основному дереві ядра; складніші реакції (дамп регістрів, сповіщення в простір користувача) дописують окремими регуляторами під конкретну платформу.

## 5. Інтеграція з systemd та сучасними супервізорами

Із появою `systemd` підхід до моніторингу системних служб змінився. `systemd` (як PID 1) перебрав на себе пряме володіння символьним пристроєм `/dev/watchdog`. PID 1 періодично надсилає `WDIOC_KEEPALIVE` в апаратний таймер. Якщо сам `systemd` зависає, апаратний таймер перезавантажує всю фізичну машину.

Одночасно `systemd` надає програмний Watchdog для підпорядкованих служб. У конфігураційному файлі юніта розробник вказує параметр `WatchdogSec=10s`. Служба під час роботи надсилає сокетні повідомлення `sd_notify(0, "WATCHDOG=1")`. Якщо служба зависає і не надсилає повідомлення протягом 10 секунд, PID 1 перезапускає конкретну службу або вживає визначені аварійні заходи, не перезавантажуючи при цьому весь сервер.

Таким чином, еволюція сторожових таймерів у Linux пройшла шлях від ізольованих ISA-плат із некоординованим керуванням до багаторівневої системи захисту, де апаратний Watchdog захищає PID 1 та ядро, а PID 1 захищає користувацькі сервіси.
