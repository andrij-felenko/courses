# Відео-підсистема V4L2 та Media Controller API

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Сучасні пристрої відеозахоплення та обробки відеоданих являють собою складні багатокомпонентні системи. Якщо раніше веб-камера була монолітним пристроєм, який просто видавав потік пікселів через USB, то сучасні мобільні камери (SoC camera subsystems) складаються з багатьох апаратних блоків: сенсорів, процесорів обробки зображень (ISP), ресайзерів, форматних конвертерів, кодерів тощо. Щоб керувати цією складністю в ядрі Linux, класичного API Video4Linux2 (V4L2) виявилося недостатньо, і було розроблено Media Controller API. Ця стаття детально розглядає обидві підсистеми, їхню взаємодію, а також механізми управління буферами відеопам'яті (videobuf2) та експорт буферів через DMA-BUF.

## 1. Еволюція та обмеження класичного V4L2

Класичний Video4Linux2 API був створений для простих пристроїв. У його моделі один пристрій відеозахоплення представлений одним символьним пристроєм у просторі користувача, наприклад `/dev/video0`. Програма відкриває цей файл, встановлює формат (наприклад, YUYV або MJPEG), запитує буфери, ставить їх у чергу і починає отримувати відеокадри. Усі налаштування сенсора (яскравість, контрастність, баланс білого) здійснюються через механізм V4L2 controls на цьому ж вузлі.

Однак ця монолітна модель дає збій на сучасних SoC (System-on-a-Chip). У SoC камера зазвичай підключається через шину MIPI CSI-2 до апаратного приймача (CSI-2 receiver), який потім передає дані до ISP (Image Signal Processor) для демозаїки (Debayering), корекції кольору, придушення шумів, і лише потім кадр записується в оперативну пам'ять (DMA) для доступу з боку процесора.

Проблема класичного V4L2 полягає в тому, що він не дозволяє застосунку побачити внутрішню топологію апаратного забезпечення або перенаправити потік даних (наприклад, пустити сирі дані від сенсора одразу в пам'ять, оминаючи ISP). V4L2 надає драйверу можливість "зробити магію" і видати готовий кадр, але це приховує від користувача всю гнучкість і робить розробку драйверів надзвичайно складною, оскільки кожен драйвер SoC повинен реалізовувати свій власний, нестандартний спосіб налаштування цих внутрішніх шляхів (routing).

## 2. Media Controller API: Відкриття "чорного ящика"

Щоб вирішити проблему складної топології, було створено Media Controller API. Його головна ідея полягає в тому, щоб представити мультимедійну апаратуру у вигляді орієнтованого графа, який користувацький простір може не тільки досліджувати, але й динамічно змінювати. 

Media Controller створює окремий символьний пристрій, зазвичай `/dev/media0`, через який користувацька програма може взаємодіяти з графом.

### Основні концепції Media Controller: Entities, Pads, Links

Граф Media Controller складається з трьох фундаментальних елементів:

1. **Entity (Сутність):** Це базовий будівельний блок графа, що представляє собою певний апаратний або програмний компонент, який обробляє або передає медіа-дані. Наприклад, сенсор камери (I2C пристрій), приймач MIPI CSI-2, модуль ISP, або кінцевий вузол відеозахоплення (який відповідає `/dev/videoX`). Сутності мають унікальні ідентифікатори та імена.

2. **Pad (Контактний майданчик):** Це точка підключення на Entity, через яку дані входять (Sink Pad) або виходять (Source Pad). Сутність може мати кілька pad-ів. Наприклад, ресайзер (resizer) може мати один Sink Pad для вхідного зображення високої роздільної здатності і два Source Pad-и для виведення двох різних потоків меншої роздільної здатності (один для запису, інший для попереднього перегляду).

3. **Link (Зв'язок):** Це з'єднання між Source Pad однієї Entity та Sink Pad іншої Entity. Links визначають, як дані протікають через систему. Важливо, що зв'язки можуть бути динамічними. Користувацька програма може вмикати (enable) або вимикати (disable) зв'язки через виклики ioctl до `/dev/mediaX`, тим самим змінюючи маршрутизацію відеопотоку на льоту.

Коли програма відкриває `/dev/media0`, вона спочатку викликає `MEDIA_IOC_DEVICE_INFO`, щоб дізнатися загальну інформацію про пристрій. Потім, використовуючи `MEDIA_IOC_ENUM_ENTITIES`, `MEDIA_IOC_ENUM_LINKS`, вона може обійти весь граф і побудувати його представлення у пам'яті. 

### Subdevices (v4l2_subdev)

Entities у Media Controller, які не є кінцевими вузлами DMA (тобто не є `/dev/videoX`), у V4L2 називаються subdevices (субпристрої). Для кожного субпристрою в системі створюється файл `/dev/v4l2-subdevX`.

Subdevice API дозволяє програмі взаємодіяти з конкретним апаратним блоком безпосередньо. Наприклад, програма може відкрити `/dev/v4l2-subdev0` (який відповідає сенсору) і налаштувати роздільну здатність та формат пікселів безпосередньо на pad-і сенсора. Це робиться за допомогою формату Pad (Pad format), який визначає параметри відеопотоку всередині графа (на відміну від формату V4L2, який визначає формат даних у пам'яті для кінцевого вузла).

Процес налаштування складної камери зазвичай виглядає так:
1. Дослідити граф через `/dev/media0`.
2. Увімкнути потрібні links (зв'язки) для побудови конвеєра (pipeline).
3. Налаштувати pad formats на кожному етапі конвеєра, починаючи від сенсора (через `/dev/v4l2-subdevX` вузли) і закінчуючи перед вузлом відеозахоплення. Кожен блок повинен бути налаштований так, щоб вихідний формат одного блоку відповідав вхідному формату наступного (це називається узгодженням форматів).
4. Налаштувати кінцевий формат буферів пам'яті на вузлі `/dev/videoX`.
5. Запустити відеозахоплення на `/dev/videoX`.

Ця складність дає неймовірну гнучкість, але перекладає відповідальність за правильну конфігурацію апаратури на простір користувача.

## 3. Буферизація відеоданих: Videobuf2 (vb2)

Після того, як граф налаштовано, дані потрібно передати між ядром та користувацьким простором. Відеокадри — це масиви даних великого об'єму, і їх копіювання (memcpy) між простором ядра та простором користувача вкрай неефективне. Тому V4L2 використовує механізми Zero-Copy обміну пам'яттю, які реалізовані у фреймворку Videobuf2 (vb2).

Videobuf2 є наступником старого videobuf. Це внутрішньоядерний фреймворк, який повністю керує життєвим циклом відеобуферів, звільняючи драйвери від цієї складної і схильної до помилок роботи. Vb2 підтримує черги буферів (buffer queues), абстрагує управління пам'яттю (виділення неперервної пам'яті, vmalloc, sg-DMA) та реалізує три основні моделі обміну пам'яттю з користувачем: MMAP, USERPTR та DMABUF.

### Робота з чергами буферів (Queue)

Незалежно від моделі пам'яті, загальний алгоритм захоплення кадрів виглядає так:

1. **REQBUFS (Request Buffers):** Застосунок запитує ядро ініціалізувати чергу певного розміру (наприклад, 4 буфери) і вказує метод обміну (MMAP, USERPTR, DMABUF).
2. **QUERYBUF та MMAP (для MMAP):** Застосунок запитує інформацію про кожен буфер і відображає його у свій адресний простір.
3. **QBUF (Queue Buffer):** Застосунок "ставить у чергу" (передає ядру) буфери. З цього моменту буфери належать ядру, і апаратура може записувати в них кадри.
4. **STREAMON:** Застосунок дає команду апаратурі почати захоплення (або виведення) відеопотоку. Апаратне забезпечення DMA бере перший доступний буфер з черги IN (вхідної) і записує в нього кадр. Після завершення кадру (зазвичай генерується апаратне переривання), драйвер переміщує буфер до черги OUT (вихідної).
5. **DQBUF (Dequeue Buffer):** Застосунок забирає "готовий" буфер з черги OUT, обробляє його (наприклад, виводить на екран або стискає), і після цього знову викликає QBUF, повертаючи буфер ядру. Це створює безперервний цикл.
6. **STREAMOFF:** Зупиняє захоплення.

### Моделі управління пам'яттю

Videobuf2 абстрагує від драйвера те, як саме виділяється пам'ять, пропонуючи три різні моделі для застосунку:

#### 1. MMAP (Memory Mapped)
У цій моделі пам'ять для буферів виділяється самим драйвером ядра під час виклику `REQBUFS`. Застосунок не керує виділенням, він лише відображає (mmap) цю пам'ять у свій адресний простір.
- **Переваги:** Найпростіший спосіб, добре працює для автономних застосунків, гарантує, що пам'ять підходить для апаратного DMA пристрою.
- **Недоліки:** Якщо застосунок хоче передати цей буфер іншому пристрою (наприклад, GPU для рендерингу), йому доведеться використовувати специфічні для драйвера механізми або копіювати дані.

#### 2. USERPTR (User Pointer)
Тут пам'ять виділяється користувацьким застосунком (наприклад, за допомогою `malloc` або `memalign`). Під час виклику QBUF застосунок передає ядру вказівник на свою пам'ять. Ядро (через vb2) повинно закріпити ці сторінки пам'яті в ОЗП (get_user_pages), налаштувати IOMMU (якщо є) або створити Scatter-Gather список для DMA контролера пристрою.
- **Переваги:** Застосунок контролює пам'ять. Це дозволяло інтегрувати відео з іншими підсистемами в ранні часи.
- **Недоліки:** Дуже складно для ядра (управління кешами, фрагментація пам'яті). Не всі апаратні DMA підтримують Scatter-Gather, що робить USERPTR неможливим для апаратури, яка потребує фізично неперервної пам'яті (CMA), якщо пам'ять виділена звичайним `malloc`. Сучасні системи відмовляються від USERPTR на користь DMABUF.

#### 3. DMABUF (DMA Buffer Sharing)
DMABUF — це стандартний механізм ядра Linux для спільного використання буферів між різними пристроями (наприклад, камерою V4L2, GPU через DRM/KMS, відеокодеком). Буфер представляється звичайним файловим дескриптором (FD).
У цій моделі застосунок є лише посередником, який передає FD від одного пристрою (який експортував буфер) іншому (який його імпортує). Vb2 чудово інтегрований з DMABUF як для імпорту, так і для експорту.

## 4. DMA-BUF Export у V4L2

Можливість експортувати буфери V4L2 як DMA-BUF файлові дескриптори є критично важливою для побудови ефективних мультимедійних конвеєрів (pipelines) без копіювання даних у просторі користувача.

Цей процес (Exporting) виглядає так:
1. Застосунок запитує буфери у пристрою V4L2 (наприклад, камери) використовуючи модель `V4L2_MEMORY_MMAP` (тобто драйвер V4L2 сам виділяє пам'ять).
2. Для кожного буфера застосунок викликає спеціальний ioctl `VIDIOC_EXPBUF`.
3. Ядро (через videobuf2) створює новий DMA-BUF об'єкт, асоціює його з пам'яттю цього буфера, і повертає застосунку файловий дескриптор.
4. Тепер застосунок має FD. Він може передати цей FD іншому API, наприклад OpenGL (через EGL extensions, такі як `EGL_EXT_image_dma_buf_import`), Vulkan, або DRM/KMS для безпосереднього виведення на екран (Zero-Copy display).

**DMABUF Import у V4L2** працює у зворотному напрямку:
1. Застосунок використовує модель `V4L2_MEMORY_DMABUF` під час виклику `REQBUFS`.
2. Інший пристрій (наприклад, GPU або DRM dumb buffer) виділяє пам'ять і експортує її як DMABUF FD.
3. Під час виклику `QBUF` застосунок передає цей FD драйверу V4L2.
4. Videobuf2 (vb2) імпортує цей FD, отримує доступ до базової пам'яті через фреймворк dma-buf, і налаштовує DMA камери для запису прямо в пам'ять GPU.

Перевага DMABUF полягає в тому, що ядро саме вирішує питання синхронізації (використовуючи dma-fences) та управління когерентністю кешу між різними апаратними пристроями (наприклад, коли CPU повинен отримати доступ до даних, модифікованих пристроєм через DMA). Це гарантує, що застосунку не потрібно виконувати примусові скидання кешу процесора, що було серйозною проблемою при використанні USERPTR.

## 5. Сучасний стек: libcamera та розширення ядра

Складність Media Controller і Subdevice API призвела до того, що написати універсальний застосунок для захоплення відео стало практично неможливо. Кожен SoC (Rockchip, NXP, Qualcomm) має власну, унікальну топологію графа Media Controller. Для того, щоб отримати кадр, потрібно знати, які конкретно links потрібно увімкнути для даної плати, які формати підтримує кожен ISP-блок і як їх узгоджувати.

Щоб вирішити цю проблему у просторі користувача, було створено проєкт **libcamera**. Це бібліотека з відкритим вихідним кодом, яка розміщується над V4L2, Media Controller і Subdevice API. Її головна мета — приховати всю специфіку апаратного графа (через систему плагінів, що називаються Pipeline Handlers) і надати програмам простий API високого рівня. Застосунок просить у libcamera камеру і отримує готовий потік кадрів, тоді як Pipeline Handler від libcamera автоматично досліджує `/dev/mediaX`, знаходить потрібний сенсор, будує граф, налаштовує формати, експортує DMABUF і запускає `vb2` черги.

В епоху MIPI камер і складних ISP, V4L2 сам по собі вже не є API користувача; він став низькорівневим інтерфейсом взаємодії між ядром та проміжним програмним забезпеченням (middleware), таким як libcamera. Media Controller став фундаментальною складовою, яка зробила таку еволюцію можливою, надаючи необхідний словник для опису будь-якої апаратної мультимедійної топології.

## Висновки

Video4Linux2 пройшов довгий шлях від простого API для веб-камер до складної екосистеми, здатної керувати багатокомпонентними сенсорними підсистемами сучасних SoC. 

- **Media Controller API** дозволяє ядру оголити апаратний граф (entities, pads, links), що дає безпрецедентну гнучкість маршрутизації даних.
- **Videobuf2 (vb2)** абстрагує складність управління пам'яттю, надаючи стандартизовані черги та підтримуючи сучасні механізми.
- **DMA-BUF Export/Import** є наріжним каменем ефективної обробки відео без копіювання (Zero-Copy), об'єднуючи підсистеми захоплення (V4L2) та рендерингу (DRM/KMS, GPU).
- Складність цього стеку успішно інкапсулюється такими бібліотеками як **libcamera**, що робить розробку прикладного ПЗ знову зручною.
