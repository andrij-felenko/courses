# 📜 Історія FIPS 140 у ядрі Linux: від RHEL-патчів до FIPS 140-3

Регуляторні вимоги безпеки федерального уряду США змусили відкриту операційну систему Linux докорінно перебудувати внутрішню криптографічну архітектуру ядра, запровадити обов'язкові передопераційні самоперевірки алгоритмів та суворий контроль цілісності бінарного коду ще до передачі керування простору користувача.

## Потреба у формальній верифікації криптографії

На початку 2000-х років ядро Linux стрімко виходило за межі академічних лабораторій та ентузіастських серверів у корпоративний і державний сектори. Однак для впровадження операційної системи в державних установах США, фінансових інституціях та оборонних відомствах існувала жорстка законодавча перепона — федеральний закон про управління інформаційною безпекою (Federal Information Security Modernization Act, FISMA) від 2002 року.

Закон вимагав, щоб будь-яке програмне або апаратне забезпечення, яке обробляє конфіденційну, але нетаємну інформацію (Sensitive but Unclassified), використовувало виключно криптографічні модулі, валідовані за стандартом FIPS 140 (Federal Information Processing Standard Publication 140). Стандарт розроблявся Національним інститутом стандартів і технологій США (National Institute of Standards and Technology, NIST) спільно з канадським Центром безпеки комунікацій (Communications Security Establishment, CSE) у межах програми CMVP (Cryptographic Module Validation Program).

У той час ядро Linux 2.4 та ранні версії 2.6 містили розрізнені реалізації шифрів для мережевих протоколів (зокрема IPsec), але не мали єдиної криптографічної межі, формалізованих самоперевірок під час старту чи механізмів гарантованого блокування нестійких алгоритмів. Якщо комерційні пропрієтарні системи (Solaris, Windows NT/2000) створювали окремі бінарні криптопровайдери та подавали їх на сертифікацію, то для ядра з відкритим кодом монолітна природа та можливість динамічного завантаження модулів створювали унікальні регуляторні виклики.

## Перші латки та шлях до апстріму

Головним рушієм сертифікації ядра Linux виступила компанія Red Hat. Для дистрибутива Red Hat Enterprise Linux 5 (RHEL 5), що базувався на ядрі Linux 2.6.18, інженери з безпеки створили спеціальний набір патчів. Цей шар запровадив файл `crypto/fips.c`, параметр завантаження `fips=1` та перевірку цілісності бінарного образу ядра за допомогою HMAC-SHA256 перед виконанням будь-яких криптографічних операцій.

У спільноті ядра точилися тривалі дискусії щодо доцільності інтеграції цих перевірок в основну гілку (upstream). Розробники ядра справедливо зазначали, що обов'язкове тестування відомими векторами (Known Answer Tests, KAT) при кожному старті сповільнює завантаження системи, а аварійна зупинка ядра (`panic`) у разі збою тесту суперечить загальній філософії стійкості Linux. Проте компроміс було знайдено через механізм умовної компіляції.

У ядрі Linux 2.6.28 (грудень 2008 року) криптографічний мейнтейнер Герберт Сюй (Herbert Xu) прийняв у ядро базову інфраструктуру `CONFIG_CRYPTO_FIPS`. Ця опція компіляції залишала ядро абсолютно стандартним за замовчуванням: режим активувався лише тоді, коли адміністратор явно передавав параметр `fips=1` у командному рядку завантажувача. Це дозволило постачальникам дистрибутивів постачати єдине спільне ядро як для звичайних користувачів, так і для сертифікованих FIPS-середовищ.

## Еволюція від FIPS 140-2 до FIPS 140-3

Стандарт FIPS 140-2, прийнятий у травні 2001 року, діяв понад два десятиліття. У межах рівня безпеки Security Level 1 (базовий рівень для програмних криптомодулів загального призначення) стандарт вимагав:
1. Чіткого визначення логічної криптографічної межі.
2. Проходження Known Answer Tests для всіх реалізацій алгоритмів під час ініціалізації.
3. Перевірки цілісності програмного коду за допомогою затвердженого алгоритму автентифікації (HMAC або RSA/ECDSA-підпис).
4. Тесту неперервності генератора випадкових чисел (Continuous RNG Test, CRNGT), який порівнював кожен новий блок випадковості з попереднім.

З роками криптоаналіз виявив слабкості низки вимог FIPS 140-2. Зокрема, старий тест неперервності CRNGT виявився теоретично неефективним для криптографічних генераторів псевдовипадкових чисел і навіть створював вразливості до витоку стану.

У 2019 році NIST офіційно оголосив про перехід на FIPS 140-3, який гармонізував американські вимоги з міжнародними стандартами ISO/IEC 19790:2012 та ISO/IEC 24759:2014. Перехідний період завершився у вересні 2021 року, після чого всі нові криптографічні модулі тестуються виключно за FIPS 140-3.

## Зміни архітектури ядра під FIPS 140-3

Перехід на FIPS 140-3 спричинив суттєві зміни в підсистемі Crypto API сучасних ядер Linux (серії 5.x та 6.x):

- **Нова архітектура генерації випадковості (SP 800-90A / SP 800-90B):** Старий CRNGT було остаточно вилучено. Замість нього впроваджено обов'язкові тести справності ентропії (Repetition Count Test та Adaptive Proportion Test), а ядро перейшло на детерміністичні генератори DRBG (Deterministic Random Bit Generator) на базі AES-CTR або HMAC-SHA256.
- **Розділення самоперевірок:** FIPS 140-3 чітко розмежував передопераційні самоперевірки (Pre-operational Self-Tests, POST), що запускаються до надання доступу до сервісів, та умовні самоперевірки (Conditional Self-Tests, CAST), які виконуються під час генерації ключів чи завантаження сторонніх модулів.
- **Повна заборона застарілих шифрів:** Якщо в епоху FIPS 140-2 алгоритм Triple-DES (3DES) ще допускався для обмеженого шифрування, то згідно з оновленнями SP 800-131A Rev 2 під FIPS 140-3 використання 3DES для шифрування нових даних повністю заборонено починаючи з 2024 року.

Сьогодні модуль ядра Linux Kernel Crypto API регулярно проходить сертифікацію CMVP різними дистриб'юторами (Red Hat, Canonical, SUSE, Oracle, Wind River), підтверджуючи відповідність стандарту FIPS 140-3 на різноманітних апаратних архітектурах від x86_64 до ARM64 та s390x.
