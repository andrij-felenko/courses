# 📋 Інтерфейси та конфігурація FIPS у ядрі: параметри, sysctl та прапорці Crypto API

Цей довідник містить детальний опис інтерфейсів ядра Linux, параметрів командного рядка завантажувача, вузлів у віртуальних файлових системах `procfs`/`sysfs`, внутрішніх структур даних ядра, системних подій аудиту та кодів помилок C API, що регулюють роботу операційної системи в режимі відповідності криптографічним стандартам FIPS 140-2 та FIPS 140-3.

## Опції конфігурації ядра (Kconfig)

Для підтримки FIPS-режиму ядро збирається з увімкненою підсистемою сертифікаційних перевірок. Усі опції задаються на етапі конфігурації перед компіляцією (`make menuconfig` або конфігураційні файли дистрибутива).

| Опція Kconfig | Тип | Опис та системний вплив |
| :--- | :--- | :--- |
| `CONFIG_CRYPTO_FIPS` | `bool` | Головний перемикач інфраструктури FIPS у ядрі. Додає компіляцію модуля `crypto/fips.c`, експортує глобальну змінну `fips_enabled` та створює вузол `/proc/sys/crypto/fips_enabled`. За замовчуванням `n`. |
| `CONFIG_CRYPTO_FIPS_NAME` | `string` | Рядковий ідентифікатор криптографічного модуля ядра (наприклад, `"Linux Kernel Cryptographic API"`). Відображається у `/proc/sys/crypto/fips_name`. |
| `CONFIG_CRYPTO_TESTMGR` | `tristate` | Менеджер алгоритмічних самоперевірок (`crypto/testmgr.c`). При `CONFIG_CRYPTO_FIPS=y` обов'язково встановлюється в `y` (вбудовано в монолітне ядро), оскільки перевірки мають виконуватися до реєстрації алгоритмів. |
| `CONFIG_CRYPTO_DRBG_MENU` | `tristate` | Підсистема детерміністичних генераторів випадкових бітів за стандартом NIST SP 800-90A (`crypto/drbg.c`). |
| `CONFIG_CRYPTO_DRBG_CTR` | `bool` | Реалізація CTR_DRBG на базі симетричного шифру AES. Обов'язкова для сертифікованих середовищ. |
| `CONFIG_CRYPTO_DRBG_HMAC` | `bool` | Реалізація HMAC_DRBG на базі геш-функцій SHA-256 / SHA-512. |
| `CONFIG_CRYPTO_DRBG_HASH` | `bool` | Реалізація Hash_DRBG на базі прямих перетворень гешу. |
| `CONFIG_CRYPTO_MANAGER_DISABLE_TESTS` | `bool` | Повне вимкнення тестів при старті. У разі `CONFIG_CRYPTO_FIPS=y` ця опція **суворо заборонена** (примусово деактивується ядром). |
| `CONFIG_CRYPTO_FIPS_CUSTOM_PANIC` | `bool` | Дозволяє вмикати аварійну зупинку ядра (`panic`) негайно при першому виявленому збої Known Answer Test. |

## Параметри командного рядка ядра (Boot Parameters)

Ядро, скомпільоване з `CONFIG_CRYPTO_FIPS=y`, не активує жорсткі обмеження FIPS автоматично, щоб не порушувати роботу звичайних середовищ. Активація відбувається через передачу параметрів завантажувача (GRUB, systemd-boot).

```
fips=1 [fips=0] [fips=boot=<пристрій>] [boot=<пристрій>]
```

### Деталізація параметрів

- `fips=1` — примусово активує режим FIPS під час завантаження ядра. Викликає функцію `fips_enable()`, яка встановлює внутрішній прапорець `fips_enabled = 1`. Усі наступні реєстрації алгоритмів підлягають обов'язковому проходженню Known Answer Tests (KAT). Спроби використання несхвалених шифрів відхиляються.
- `fips=0` — явно вимикає режим FIPS, навіть якщо дистрибутивний initramfs налаштовано на перевірку цілісності.
- `boot=<partition>` або `fips=boot=<uuid_or_device>` — вказує для initramfs (модуль dracut `fips`) розділ із завантажувальними файлами (де розміщено образ `vmlinuz` та його підпис `.vmlinuz.hmac`). Потрібно для обчислення HMAC образу ядра до монтування основного кореневого каталогу `/`.

## Інтерфейси у віртуальних файлових системах (Procfs / Sysfs)

### 1. `/proc/sys/crypto/fips_enabled`

Головний системний прапорець статусу.

- **Права доступу:** `0444` (`-r--r--r--`, тільки читання для всіх користувачів).
- **Тип даних:** ASCII-рядок з єдиним цілим числом (`"0\n"` або `"1\n"`).
- **Семантика значень:**
  - `0` — режим FIPS неактивний. Ядро працює у стандартному режимі: самоперевірки виконуються у фоновому режимі (якщо не вимкнені), усі зареєстровані алгоритми (зокрема MD5, DES, RC4) дозволені до виділення через Crypto API та сокети `AF_ALG`.
  - `1` — режим FIPS активний. Увімкнено жорстку фільтрацію алгоритмів, помилка будь-якого KAT спричиняє паніку ядра (`panic`) або блокування підсистеми, генератор випадковості переведено на детерміністичний DRBG.

> Запис у `/proc/sys/crypto/fips_enabled` під час роботи системи **неможливий** (виклики `open(..., O_WRONLY)` повертають помилку `-EACCES` або `-EPERM`). Зміна режиму вимагає повного перезавантаження системи.

### 2. `/proc/sys/crypto/fips_name`

Містить офіційну назву криптографічного модуля, яка зареєстрована в сертифікаті NIST CMVP.

```bash
$ cat /proc/sys/crypto/fips_name
Linux Kernel Cryptographic API
```

### 3. Фільтрація та статуси в `/proc/crypto`

Кожен зареєстрований алгоритм у ядрі має окремий блок у `/proc/crypto`. У режимі FIPS ключовими є такі поля:

```
name         : xts(aes)
driver       : xts-aes-aesni
module       : aesni_intel
priority     : 401
refcnt       : 2
selftest     : passed
internal     : no
type         : skcipher
async        : yes
blocksize    : 16
min keysize  : 32
max keysize  : 64
ivsize       : 16
```

Значення поля `selftest`:
- `passed` — алгоритм успішно пройшов усі обов'язкові вектори KAT для прямого та зворотного перетворення і допущений до роботи.
- `in_progress` — алгоритм зареєстровано, але його самотестування в поточний момент виконується в асинхронній черзі ядра `cryptomgr`.
- `failed` — самоперевірка завершилася розбіжністю результату з еталонним вектором. В активному FIPS-режимі такий алгоритм або блокується, або ініціює `fips_fail()`.
- `unknown` — самоперевірка не проводилася (можливо лише за умови ручного вимкнення тестів у не-FIPS ядрі).

## Дозволені та заборонені алгоритми за FIPS 140-3

У режимі FIPS ядро та бібліотеки простору користувача проводять жорстку сегрегацію зареєстрованих алгоритмів.

| Категорія криптографії | Схвалені FIPS алгоритми (Approved) | Заборонені та застарілі алгоритми (Blocked / Prohibited) |
| :--- | :--- | :--- |
| **Симетричні блокові шифри** | AES (128, 192, 256 біт) у режимах CBC, CTR, XTS, GCM, CCM, OFB, CFB. | DES, Triple-DES (3DES / DES-EDE3 для шифрування), Blowfish, Twofish, CAST5, RC2, Camellia, ARIA. |
| **Потокові шифри** | Відсутні серед схвалених примітивів (застосовується AES у режимі CTR/GCM). | RC4 (arc4), ChaCha20 (якщо не сертифіковано окремим додатком). |
| **Геш-функції** | SHA-224, SHA-256, SHA-384, SHA-512, SHA-512/224, SHA-512/256, SHA3-224, SHA3-256, SHA3-384, SHA3-512. | MD2, MD4, MD5, RIPEMD-160, SHA-0, SHA-1 (повна заборона для створення цифрових підписів). |
| **Коди автентичності (MAC)** | HMAC-SHA2/3, AES-CMAC, AES-GMAC. | HMAC-MD5, HMAC-SHA1 (для створення нових міток). |
| **Асиметрична криптографія** | RSA (довжина ключа ≥ 2048 біт), ECDSA (криві NIST P-256, P-384, P-521), Ed25519 (за FIPS 186-5). | RSA (< 2048 біт), DSA (< 2048 біт), несертифіковані криві еліптичної криптографії. |
| **Генерація псевдовипадковості** | NIST SP 800-90A DRBG (CTR_DRBG, HMAC_DRBG, Hash_DRBG). | Лінійні конгруентні генератори, чистий ANSI X9.31 PRNG. |

## Внутрішній C API ядра (`include/crypto/fips.h`, `linux/crypto.h`)

У просторі ядра стан FIPS та контроль алгоритмів регулюються спеціальними макросами, змінними та структурами.

### Глобальні змінні та функції керування

```c
#ifdef CONFIG_CRYPTO_FIPS
extern int fips_enabled;
extern struct atomic_t fips_fail;

void fips_fail_notify(void);
int fips_post_failed(void);
#else
#define fips_enabled 0
static inline void fips_fail_notify(void) {}
static inline int fips_post_failed(void) { return 0; }
#endif
```

- `fips_enabled` — глобальна змінна типу `int`. Доступна для перевірки в будь-якому модулі ядра через `#include <crypto/fips.h>`.
- `fips_fail_notify()` — внутрішня функція, що викликається з `testmgr.c` при падінні Known Answer Test. Вона інформує підсистему безпеки ядра та, залежно від налаштувань ядра, може викликати аварійну паніку `panic("FIPS self-test failure\n")`.
- `fips_post_failed()` — перевіряє, чи не зазнали аварії передопераційні самоперевірки (Pre-Operational Self-Tests).

### Прапорці алгоритмів (`cra_flags`)

Під час реєстрації криптографічного перетворення через `crypto_register_alg()` або `crypto_register_skcipher()` перевіряється маска прапорців у полі `cra_flags`:

| Прапорець | Числове значення | Семантика в режимі FIPS |
| :--- | :--- | :--- |
| `CRYPTO_ALG_FIPS_INTERNAL` | `0x00020000` | Алгоритм дозволено використовувати лише іншим внутрішнім компонентам ядра (наприклад, для валідації старих підписів або у складі HMAC), але заборонено виділяти безпосередньо з простору користувача через `AF_ALG`. |
| `CRYPTO_ALG_TESTED` | `0x00000400` | Встановлюється `testmgr` після успішного проходження KAT. До встановлення цього прапорця виділення алгоритму через `crypto_alloc_tfm()` блокується або очікує завершення тесту. |
| `CRYPTO_ALG_INTERNAL` | `0x00002000` | Внутрішній алгоритм, не видимий для звичайних пошукових запитів споживачів. |

### Структури тестових векторів (`crypto/testmgr.h`)

Усі еталонні значення жорстко скомпільовані в заголовочному файлі `crypto/testmgr.h` у вигляді статичних масивів структур.

```c
struct cipher_testvec {
    const char *key;      /* Байт-масив ключа */
    const char *p;        /* Відкритий текст (Plaintext) */
    const char *c;        /* Очікуваний шифротекст (Ciphertext) */
    const char *iv;       /* Вектор ініціалізації (IV) */
    unsigned char klen;   /* Довжина ключа в байтах */
    unsigned short plen;  /* Довжина відкритого тексту */
    unsigned short clen;  /* Довжина шифротексту */
    bool fail;            /* Ознака негативного тесту (має відхилятися) */
    unsigned char wk;     /* Прапорець слабкого ключа (weak key) */
};

struct hash_testvec {
    const char *key;      /* Ключ для HMAC (NULL для чистого гешу) */
    const char *plaintext;/* Вхідні дані для гешування */
    const char *digest;   /* Очікуваний дайджест */
    unsigned short psize; /* Довжина вхідних даних */
    unsigned char ksize;  /* Довжина ключа HMAC */
};

struct drbg_state {
    spinlock_t lock;
    unsigned char *v;               /* Внутрішній вектор стану DRBG V */
    unsigned char *c;               /* Константа C (для Hash_DRBG) */
    void *priv_data;                /* Дані контексту шифру чи гешу */
    size_t reseed_threshold;        /* Поріг ресідінгу (максимум операцій до оновлення) */
    size_t reseed_ctr;              /* Лічильник згенерованих блоків від останнього ресіду */
    const struct drbg_core *core;   /* Вказівник на специфікацію рушія */
    bool seeded;                    /* Ознака успішної ініціалізації ентропією */
    bool pr;                        /* Прапорець Prediction Resistance */
};
```

## Структури інтерфейсу `AF_ALG` у просторі користувача

Для взаємодії з криптографічною підсистемою ядра з простору користувача застосовується адресне сімейство `AF_ALG`. У режимі FIPS виклики `bind()` перевіряють статус алгоритму:

```c
#include <linux/if_alg.h>

struct sockaddr_alg {
    __u16 salg_family;          /* Завжди AF_ALG */
    __u8  salg_type[14];        /* "skcipher", "hash", "aead", "rng" */
    __u32 salg_feat;            /* Прапорці вимог до типу */
    __u32 salg_mask;            /* Маска фільтрації прапорців */
    __u8  salg_name[64];        /* Узагальнене або драйверне ім'я */
};
```

При спробі виконати `bind(sock_fd, (struct sockaddr *)&sa, sizeof(sa))` з `salg_name = "md5"` або `salg_name = "des"` ядро в режимі `fips_enabled = 1` негайно повертає код помилки `-ENOENT`.

## Повідомлення підсистеми аудиту (Audit Events)

У разі виявлення порушень криптографічної цілісності або збоїв алгоритмічних тестів ядро генерує спеціальні записи в системний журнал аудиту Linux Audit Framework (`auditd`):

```
type=ANOM_CRYPTO_FAIL msg=audit(1692612000.123:45): op=self_test name=xts-aes-aesni res=0
type=INTEGRITY_DATA msg=audit(1692612001.456:46): pid=1 comm="fipscheck" file="/boot/vmlinuz-6.6.0" res=0
```

- `type=ANOM_CRYPTO_FAIL` — аномалія криптографічної підсистеми: фіксує ім'я драйвера (`name`), тип операції (`op=self_test` або `op=drbg_health`) та результат (`res=0` означає збій).
- `type=INTEGRITY_DATA` — збій перевірки цілісності бінарного образу ядра чи бібліотеки модулем `fipscheck` або `dracut-fips`.

## Коди помилок при роботі з Crypto API в режимі FIPS

Під час виклику функцій алокації трансформацій (`crypto_alloc_skcipher()`, `crypto_alloc_shash()`, `crypto_alloc_aead()`) або операцій через сокети `AF_ALG` у режимі FIPS ядро повертає стандартизовані коди помилок:

- `-ENOENT` (`2`, No such file or directory) — запитаний алгоритм не знайдено в реєстрі, або він був виключений з доступних через несхвалення стандартом FIPS (наприклад, спроба створити `crypto_alloc_skcipher("cbc(des)", 0, 0)` або `crypto_alloc_shash("md5", 0, 0)`).
- `-EACCES` (`13`, Permission denied) — алгоритм позначено прапорцем `CRYPTO_ALG_FIPS_INTERNAL`, і простір користувача намагається створити його екземпляр напряму.
- `-ELIBBAD` (`80`, Accessing a corrupted shared library) або `-EKEYREJECTED` (`129`, Key was rejected by service) — виникає при спробі завантаження модуля ядра з недійсним або відсутнім криптографічним підписом при активному FIPS.
- `-EINVAL` (`22`, Invalid argument) — параметри алгоритму (розмір ключа, довжина IV, параметри еліптичної кривої) не відповідають мінімальним вимогам безпеки FIPS (наприклад, довжина RSA-ключа менша за 2048 біт).
- `-EDQUOT` (`122`, Disk quota exceeded) або `-EAGAIN` (`11`, Resource temporarily unavailable) — генератор DRBG вичерпав ліміт запитів без ресідінгу (`reseed_threshold`) і вимагає нового внесення ентропії.
