# 📋 Інтерфейси, які віддають і приймають номери пристрою

Це довідник по всіх місцях, де пара «старший:молодший» перетинає межу між ядром і програмою: поля структур, функції розбирання, виклик створення вузла, службові файли `/proc` і `/sys`, змінні події та ключі правил udev. Числа скрізь ті самі — а от пакування, ширина поля й система числення щоразу інші, і саме на цій розбіжності ламаються програми, які розбирають `dev_t` руками.

## Простір користувача: звідки прочитати пару

У структурі `stat` номери пристроїв лежать у двох різних полях, і плутати їх не можна.

```c
struct stat {
    dev_t st_dev;    /* пристрій, на якому лежить САМ файл */
    ...
    dev_t st_rdev;   /* пристрій, на який ПОКАЗУЄ вузол */
};
```

| поле | має сенс для | що означає |
|---|---|---|
| `st_dev` | будь-якого файла | ідентифікатор змонтованого примірника файлової системи; у tmpfs, мережевих і накладених ФС старший дорівнює `0` |
| `st_rdev` | лише `S_IFCHR` і `S_IFBLK` | пара, записана у вузлі; для решти типів там нуль або сміття |

`statx(2)` (ядро 4.11, обгортка в glibc з 2.28) віддає обидві пари вже **розділеними**, окремими 32-бітними полями — жодного пакування, жодних макросів:

```c
struct statx {
    __u32 stx_dev_major,  stx_dev_minor;    /* аналог st_dev  */
    __u32 stx_rdev_major, stx_rdev_minor;   /* аналог st_rdev */
};
```

Маскового біта під ці поля немає взагалі — ні `STATX_RDEV`, ні `STATX_DEV` не існує, — тому ядро заповнює їх без огляду на маску, а перевіряти `stx_mask` тут нічого. Решта полів працює інакше, і саме там маска обов'язкова: [контракт `stat` і `statx`](book:unix-linux/inode-model/api-stat-fields.md) розбирає це поле за полем.

```c
struct statx sx;
statx(AT_FDCWD, path, AT_SYMLINK_NOFOLLOW, 0, &sx);   /* просити нічого не треба */
printf("%u:%u\n", sx.stx_rdev_major, sx.stx_rdev_minor);
```

## `<sys/sysmacros.h>`: розібрати й скласти

```c
unsigned int major(dev_t dev);
unsigned int minor(dev_t dev);
dev_t        makedev(unsigned int maj, unsigned int min);
```

Заголовок треба підключати явно. До glibc 2.25 ці визначення приходили ще й із `<sys/types.h>`, у 2.25 таку поведінку оголосили застарілою, а з glibc 2.28 `<sys/types.h>` їх більше не дає — стара програма без явного `#include <sys/sysmacros.h>` просто не збереться.

Розкладка 64-бітного `dev_t` у glibc — переплетена: кожна половина розрізана на два шматки.

| біти `dev_t` | що там лежить |
|---|---|
| 0–7 | молодший, біти 0–7 |
| 8–19 | старший, біти 0–11 |
| 20–43 | молодший, біти 8–31 |
| 44–63 | старший, біти 12–31 |

Дивна на вигляд, ця розкладка має рівно одну причину: **молодші шістнадцять бітів відтворюють класичне 16-бітне пакування `(старший << 8) | молодший`.** Поки обидва числа менші за 256 — а таких пар більшість, — нове значення збігається зі старим байт у байт, і старі двійкові формати та записи на носіях лишаються читабельними. Те саме переплетення живе й у ядрі під іменем `new_encode_dev()`, тільки в 32 бітах; glibc просто розсунула його поля вгору.

**Порахуймо одну пару в обох виглядах.** Візьмімо `/dev/sda3` — старший 8, молодший 3.

```
ядро, MKDEV(8, 3):
    dev = (8 << 20) | 3 = 0x00800003 = 8388611

glibc, makedev(8, 3):
    молодший & 0xff        = 3        →  0x003
    (старший & 0xfff)  << 8 = 8 << 8  →  0x800
    (молодший & ~0xff) << 12 = 0      →  0
    (старший & 0xfffff000) << 32 = 0  →  0
    dev = 0x803 = 2051
```

Одна пара — два зовсім різні числа. Тому `st_rdev >> 20` дає не старший номер, а сміття, і жодна перевірка цього не викриє: результат виглядатиме як правдоподібний малий номер.

**Друга пара, де переплетення справді працює** — старший 259 (`BLOCK_EXT_MAJOR`), молодший 1000:

```
молодший 1000 = 0x3E8, старший 259 = 0x103

    0x3E8 & 0xff          = 0xE8       →  біти 0-7    0x0000E8
    (0x103 & 0xfff)  << 8              →  біти 8-19   0x010300
    (0x3E8 & ~0xff)  << 12 = 0x300<<12 →  біти 20-43  0x300000
    dev = 0x3103E8
```

## `mknod` і `mknodat`: створити вузол

```c
#include <sys/stat.h>
int mknod(const char *pathname, mode_t mode, dev_t dev);

#include <fcntl.h>
#include <sys/stat.h>
int mknodat(int dirfd, const char *pathname, mode_t mode, dev_t dev);
```

`mode` — це тип, поєднаний побітовим «або» з бітами прав: `S_IFCHR` (символьний), `S_IFBLK` (блоковий), `S_IFIFO` (іменований канал), `S_IFSOCK` (сокет), `S_IFREG` (порожній звичайний файл). Аргумент `dev` читається **лише** для `S_IFCHR` і `S_IFBLK`; для решти типів його треба передавати нулем. `mknodat` відрізняється тільки тим, що відносний шлях відлічують від каталогу `dirfd` (`AT_FDCWD` повертає звичайну поведінку) — уся [`*at`-родина](book:unix-linux/at-family-syscalls) влаштована так само.

| помилка | коли |
|---|---|
| `EPERM` | просили символьний або блоковий вузол без [можливості](book:unix-linux/capabilities) `CAP_MKNOD`; або файлова система вузлів не тримає |
| `EEXIST` | ім'я вже зайняте — хоч би й символьним посиланням у нікуди |
| `EACCES` | немає права запису в каталог або права проходу дорогою |
| `EINVAL` | у `mode` не той тип файла |
| `EROFS`, `ENOSPC`, `EDQUOT` | ФС лише для читання; немає місця; вичерпано квоту |
| `ENOENT`, `ENOTDIR`, `ELOOP`, `ENAMETOOLONG` | звичайні біди розбору шляху |

`CAP_MKNOD` потрібна саме на створення. Відкриття вже наявного вузла жодної можливості не вимагає — його судять звичайні права доступу, і це рівно та причина, з якої вузол на змінному носії небезпечний.

Три різні відмови на **відкритті** вузла варто розрізняти:

| код `open` | що сталося |
|---|---|
| `ENXIO` | під цією парою в ядрі ніхто не зареєстрований — драйвера немає або він уже вивантажений |
| `EACCES` | ФС змонтована з `nodev`: вузол цілий, ядро відмовляється його відкривати |
| `EPERM`, `EACCES` за правами | звичайна перевірка бітів прав і власника вузла |

## Мінімальний робочий виклик

```c
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/sysmacros.h>

int main(int argc, char **argv)
{
    if (argc != 2) { fprintf(stderr, "вжиток: %s ВУЗОЛ\n", argv[0]); return 2; }

    struct stat st;
    if (lstat(argv[1], &st) != 0) {
        fprintf(stderr, "lstat(%s): %s\n", argv[1], strerror(errno));
        return 1;
    }

    mode_t type = st.st_mode & S_IFMT;
    if (type != S_IFCHR && type != S_IFBLK) {
        fprintf(stderr, "%s — не вузол пристрою\n", argv[1]);
        return 1;
    }

    /* єдиний коректний розбір: зсуви руками дадуть сміття */
    unsigned maj = major(st.st_rdev), min = minor(st.st_rdev);
    printf("%s: %s %u:%u   (dev_t = 0x%llx)\n", argv[1],
           type == S_IFCHR ? "символьний" : "блоковий",
           maj, min, (unsigned long long)st.st_rdev);

    /* зворотний бік: складаємо ту саму пару під іншим іменем */
    char copy[64];
    snprintf(copy, sizeof copy, "/tmp/dev-%u-%u", maj, min);
    if (mknod(copy, type | 0600, makedev(maj, min)) != 0) {
        fprintf(stderr, "mknod(%s): %s\n", copy, strerror(errno));
        return errno == EPERM ? 3 : 1;      /* найімовірніше — немає CAP_MKNOD */
    }
    printf("створено %s — той самий пристрій\n", copy);
    return 0;
}
```

Збирається як `cc -O2 -o devno devno.c`; на `/dev/null` друкує `1:3` і `dev_t = 0x103`.

## З командного рядка

`ls -l` показує пару **десятково**, через кому, на місці розміру. `stat` дає її кількома способами, і тут чигає пастка:

| формат `stat -c` | що друкує | система числення |
|---|---|---|
| `%d` / `%D` | `st_dev` цілим числом | десяткова / шістнадцяткова |
| `%Hd` / `%Ld` | старший / молодший від `st_dev` | десяткова |
| `%t` / `%T` | старший / молодший від `st_rdev` | **шістнадцяткова** |
| `%F` | тип словами («character special file») | — |

```sh
$ ls -l /dev/null /dev/dm-0
crw-rw-rw- 1 root root  1,   3 /dev/null
brw-rw---- 1 root disk 253,   0 /dev/dm-0

$ stat -c '%F %t %T' /dev/dm-0
block special file fd 0
```

Той самий пристрій: `ls` каже «253», `stat -c '%t'` каже «fd». Скрипт, який порівнює вивід `%t` із десятковим числом, мовчки правильний для всіх старших менших за десять і мовчки хибний для решти.

Решта щоденних джерел:

```sh
$ mknod /tmp/mynull c 1 3            # тип: c, u (символьний), b (блоковий), p (канал)
$ lsblk -o NAME,MAJ:MIN,SIZE
$ udevadm info --device-id-of-file=/home     # пара ФС, на якій лежить шлях
$ udevadm info -q all -n /dev/sda            # усі властивості, разом із MAJOR і MINOR
```

## Ядро: хто пару роздає

Макроси розбирання — у `<linux/kdev_t.h>`, і поділ там жорсткий: `MINORBITS` дорівнює 20.

```c
#define MINORBITS   20
#define MINORMASK   ((1U << MINORBITS) - 1)
#define MAJOR(dev)  ((unsigned int) ((dev) >> MINORBITS))
#define MINOR(dev)  ((unsigned int) ((dev) & MINORMASK))
#define MKDEV(ma,mi)  (((ma) << MINORBITS) | (mi))
```

Усередині методів драйвера пару беруть просто з інода: `imajor(inode)` та `iminor(inode)` з `<linux/fs.h>`.

| виклик | заголовок | що робить |
|---|---|---|
| `int register_chrdev_region(dev_t from, unsigned count, const char *name)` | `<linux/fs.h>` | забронювати `count` молодших підряд від наперед відомої пари |
| `int alloc_chrdev_region(dev_t *dev, unsigned baseminor, unsigned count, const char *name)` | `<linux/fs.h>` | попросити **вільний** старший; ядро складе пару й покладе її в `*dev` |
| `void unregister_chrdev_region(dev_t from, unsigned count)` | `<linux/fs.h>` | звільнити відтинок |
| `int register_chrdev(unsigned major, const char *name, const struct file_operations *fops)` | `<linux/fs.h>` | давня спрощена форма: бере всі 256 молодших і сама чіпляє `fops` |
| `void cdev_init(struct cdev *, const struct file_operations *)` | `<linux/cdev.h>` | зв'язати структуру з таблицею операцій |
| `int cdev_add(struct cdev *, dev_t, unsigned count)` | `<linux/cdev.h>` | **увести пару в дію** — з цієї миті `open` знаходить драйвер |
| `void cdev_del(struct cdev *)` | `<linux/cdev.h>` | прибрати з таблиці |
| `int register_blkdev(unsigned major, const char *name)` | `<linux/blkdev.h>` | старший для блокового драйвера; `0` означає «дай вільний» і повертає його |
| `int misc_register(struct miscdevice *misc)` | `<linux/miscdevice.h>` | один молодший під старшим `10`; поле `minor` = `MISC_DYNAMIC_MINOR` (255) означає «вибери сам» |

Бронювання й уведення в дію — два різні кроки, і плутати їх дорого: `alloc_chrdev_region` лише позначає відтинок зайнятим, а знаходить драйвер саме `cdev_add`. Між цими двома викликами вузол відкриється з `ENXIO`.

```c
static dev_t base;                 /* старший разом із першим молодшим */
static struct cdev demo_cdev;

alloc_chrdev_region(&base, 0, 4, "demo");   /* 4 примірники, старший — на розсуд ядра */
cdev_init(&demo_cdev, &demo_fops);
cdev_add(&demo_cdev, base, 4);

/* усередині open(): котрий саме примірник відкривають */
unsigned idx = iminor(inode) - MINOR(base);
```

Відтинки, з яких ядро видає динамічні номери:

| що | звідки бере |
|---|---|
| символьний старший | спершу 254 → 234; коли там повно — 511 → 384 (`CHRDEV_MAJOR_MAX` = 512) |
| блоковий старший | 254 → 1 |
| молодший у `misc` | спершу вузький класичний пул під самим `MISC_DYNAMIC_MINOR`; коли той повний — сучасне ядро бере від 256 до `MINORMASK` через лічильник IDA |
| зайві розділи диска | старший 259 (`BLOCK_EXT_MAJOR`) з молодшим із загального лічильника, коли розділів більше, ніж драйвер відвів молодших |

Номер, виданий динамічно, залежить від порядку завантаження [модулів](book:unix-linux/kernel-modules) — тому вшивати його в скрипт не можна навіть як «тимчасове рішення».

## Де пара лежить текстом

| джерело | вигляд | зауваги |
|---|---|---|
| `/proc/devices` | два списки, `Character devices:` і `Block devices:`, у кожному рядку старший і назва | показує **зареєстровані старші**, а не наявні пристрої |
| `/proc/partitions` | стовпці `major minor #blocks name` | розмір — у блоках по 1024 байти |
| `/sys/dev/char/M:N`, `/sys/dev/block/M:N` | символьне посилання в теку пристрою | прямий шлях від пари до [дерева sysfs](book:unix-linux/sysfs-device-model) |
| `<тека пристрою>/dev` | рядок `M:N\n` | є в кожного пристрою, у якого є вузол |
| `<тека пристрою>/uevent` | `MAJOR=…`, `MINOR=…`, `DEVNAME=…`, `DEVTYPE=…` | те саме, що ядро надсилає повідомленням про появу |
| повідомлення `uevent` у сокет | `ACTION=add`, `SUBSYSTEM=block`, `MAJOR=8`, `MINOR=3` | звідси udev дізнається пару в мить появи пристрою |

Обидва файли в [`/proc`](book:unix-linux/proc-filesystem) відповідають на різні питання. `/proc/devices` каже, **хто взяв старший номер** — саме ним з'ясовують, чий драйвер ховається за незнайомою парою. `/proc/partitions` перелічує **готові до роботи блокові пристрої** разом із розділами, і його стовпці — це буквально пара плюс розмір; докладніше про самі розділи — у [моделі блокового пристрою](book:unix-linux/block-device-model).

## udev: добір за парою

Окремих ключів `MAJOR==` і `MINOR==` у мові правил немає. Пара приходить із події як звичайні властивості пристрою, тому добирають через `ENV{}`, а підставляють у дії — через `$major`/`%M` і `$minor`/`%m`.

```
SUBSYSTEM=="block", ENV{MAJOR}=="8", ENV{MINOR}=="3", SYMLINK+="my-root"
SUBSYSTEM=="block", KERNEL=="sd*", RUN+="/usr/bin/logger нова пара %M:%m"
```

Правило, написане через пару, тримається рівно доти, доки номер не змінився — а для драйвера з динамічним старшим це «до наступного завантаження». Надійні ключі — властивості самого пристрою (`ATTRS{serial}`, `ENV{ID_SERIAL}`, `KERNELS`), і саме на них будують [правила іменування](book:unix-linux/udev-rules); добір за парою лишається для випадків, коли пристрій більше нічим себе не називає.
