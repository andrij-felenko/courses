# Тепловий каркас ядра: зони, точки спрацювання й пристрої охолодження

- [Модель пристроїв у sysfs](book:unix-linux/sysfs-device-model) — `/sys` показує внутрішні об'єкти ядра теками й файлами, і читання такого файла означає звертання до драйвера.
- [Таблиці робочих точок (OPP)](book:unix-linux/opp-tables) — частота й напруга ходять парами, і саме зниження цієї пари зменшує тепловиділення.

Сучасні системи на кристалі (SoC) та процесори за лічені секунди виділяють стільки тепла, що без належного контролю кристали можуть деградувати або навіть фізично згоріти. Як ядро автоматично контролює температуру, враховуючи різноманіття архітектур, датчиків і методів охолодження? Для вирішення цієї проблеми у Linux реалізовано спеціальну підсистему — **Thermal Framework**.

## Логіка Thermal Framework

Thermal Framework у Linux — це абстракція, яка розмежовує апаратні датчики температури, алгоритми керування теплом (governors) та пристрої, які можуть змінювати температурний стан (cooling devices). Вона збирає все це в єдину логічну систему.

Основна ідея полягає у поділі системи на три головні складові:
1. **Thermal Zones (Теплові зони)**
2. **Cooling Devices (Пристрої охолодження)**
3. **Trip Points (Точки спрацювання)**

Ці компоненти взаємодіють під керуванням **Thermal Governors (теплових регуляторів)**.

### Thermal Zones (Теплові зони)

Теплова зона — це логічне об'єднання температурного датчика (sensor) та пов'язаних із ним меж температур і пристроїв охолодження. Фізично це може бути, наприклад, температурний датчик поруч із ядрами CPU або датчик батареї.

Кожна теплова зона експортується у sysfs за адресою `/sys/class/thermal/thermal_zoneX`, де `X` — номер зони.

Всередині цієї теки можна знайти файли:
- `temp`: поточна температура у міліградусах Цельсія (milliCelsius).
- `type`: тип або назва зони (наприклад, `cpu-thermal`, `battery`, `acpitz`).

Що ще лежить у теці зони й що з цього дозволено міняти з командного рядка, зібрано окремо: [тепловий каркас очима sysfs](book:unix-linux/thermal-framework/api-thermal-sysfs.md) — як знайти потрібну зону за її типом, як прочитати температуру й пороги, звідки береться значення порога на пакетному датчику x86 і що означають `cur_state` та `max_state` пристрою охолодження.

### Trip Points (Точки спрацювання)

У кожній тепловій зоні визначені температурні пороги, відомі як **Trip Points**. Коли температура досягає або перетинає певну точку спрацювання, ядро виконує певну дію (наприклад, запускає вентилятор або починає троттлінг).

Існує декілька основних типів точок спрацювання:
- **passive (Пасивні)**: при досягненні цього порогу ядро намагається знизити температуру без активних механізмів, зазвичай шляхом зниження частоти процесора (CPU throttling) або зменшення потужності інших пристроїв (power clamping).
- **active (Активні)**: активуються пристрої, що потребують енергії для охолодження, наприклад, вмикаються або прискорюються вентилятори (fans).
- **hot (Гарячі)**: інформують систему про серйозний перегрів. Користувацький простір може отримати сповіщення для збереження даних або підготовки до відключення.
- **critical (Критичні)**: при досягненні цієї температури система перебуває на межі фізичного пошкодження. Ядро ініціює негайне аварійне вимкнення (emergency shutdown).

### Cooling Devices (Пристрої охолодження)

Пристрої охолодження — це механізми, за допомогою яких система може впливати на температуру. Вони бувають двох типів:
1. **Активні**: вентилятори, рідинні помпи (забирають тепло, але споживають енергію).
2. **Пасивні**: зміна частоти процесора (cpufreq), обмеження підсвітки екрану (backlight) або пропускної здатності шин пам'яті. Це зменшує виділення тепла.

Пристрої охолодження представлені у sysfs як `/sys/class/thermal/cooling_deviceY`. Ядро дозволяє зв'язувати певний пристрій охолодження з однією або кількома точками спрацювання певної теплової зони.

## Алгоритми терморегулювання (Governors)

Зв'язок між датчиками, точками спрацювання та пристроями охолодження керується алгоритмами — **Thermal Governors**. 

До найпопулярніших регуляторів належать:
- **step_wise (Покроковий)**: найпоширеніший алгоритм. Він поступово (крок за кроком) збільшує стан пристрою охолодження, коли температура перевищує точку спрацювання, і так само поступово його зменшує, коли температура падає. Він простий і надійний.
- **power_allocator (IPA — Intelligent Power Allocator)**: складніший алгоритм, розроблений ARM. Він керує енергією (power) системи, а не просто станами пристроїв. Алгоритм використовує ПІД-регулятори для точного підтримання температури біля заданої межі, розподіляючи доступний "бюджет потужності" між різними компонентами (CPU, GPU тощо).
- **fair_share**: розподіляє навантаження між пристроями так, щоб не зосереджувати усе охолодження або троттлінг на одному компоненті.
- **bang_bang**: найпростіший алгоритм, схожий на звичайний термостат: вмикає пристрій на повну потужність при перетині верхнього порогу і вимикає при перетині нижнього гістерезису.

Регулятор — не сторонній модуль, який можна донести збоку: він живе всередині самого каркаса й потрапляє в список при збиранні ядра. Як виглядає найменший власний регулятор, які колбеки він мусить заповнити і що саме в цьому місці змінилося у версії 6.10, розібрано окремо: [власний тепловий регулятор](book:unix-linux/thermal-framework/proj-thermal-governor.md).

## Конфігурація: Device Tree

В архітектурах, що використовують Device Tree (наприклад, ARM), теплові зони та їх зв'язок з пристроями охолодження описуються статично.

Приклад опису теплової зони у Device Tree (DTS):

```dts
thermal-zones {
    cpu_thermal: cpu-thermal {
        polling-delay-passive = <250>; /* мілісекунди */
        polling-delay = <1000>;
        thermal-sensors = <&tsens 0>;

        trips {
            cpu_alert0: cpu-alert0 {
                temperature = <75000>; /* 75°C */
                hysteresis = <2000>;
                type = "passive";
            };
            cpu_crit: cpu-crit {
                temperature = <95000>; /* 95°C */
                hysteresis = <2000>;
                type = "critical";
            };
        };

        cooling-maps {
            map0 {
                trip = <&cpu_alert0>;
                cooling-device = <&cpu0 THERMAL_NO_LIMIT THERMAL_NO_LIMIT>;
            };
        };
    };
};
```
У цьому прикладі ми бачимо `cpu-thermal`, яка читає дані з сенсора `tsens 0`. Вона має дві точки спрацювання: `cpu-alert0` (пасивна, 75°C) та `cpu-crit` (критична, 95°C). Через секцію `cooling-maps` налаштовано, що при досягненні `cpu-alert0` спрацьовує пристрій охолодження `cpu0` (який, ймовірно, є `cpufreq` пристроєм для зниження частоти).

Самі числа й типи порогів — властивість платформи, а не каркаса, і однакова температура в різних зонах може означати різні дії. Тут 95 °C оголошено критичним статично в дереві пристроїв. А от драйвер пакетного датчика x86 заводить не більш як два пороги й обидва — пасивними (`trips[i].type = THERMAL_TRIP_PASSIVE` у `drivers/thermal/intel/x86_pkg_temp_thermal.c`), причому температуру для них не оголошують заздалегідь: її рахують від межі кристала `Tj_max` за зсувом, записаним у регістрі порогів, і дозволяють переставляти з простору користувача.

## Підсумок
Thermal Framework надає абстрагований і гнучкий інтерфейс для керування теплом, дозволяючи розробникам драйверів легко експортувати датчики, а розробникам систем інтегрувати складні алгоритми балансування енергії та температури.
