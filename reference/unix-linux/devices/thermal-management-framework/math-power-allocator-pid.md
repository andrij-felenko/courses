# 🧮 Математична модель регулятора Power Allocator та PID-контролера

У цьому документі розглядається математичний апарат, теорія автоматичного керування та дискретний алгоритм пропорційно-інтегрально-диференціального (PID) регулятора, який реалізовано у термальному регуляторі `power_allocator` ядра Linux. Алгоритм забезпечує замкнений контур зворотного зв'язку для динамічного розподілу теплової потужності у міліватах між різнорідними обчислювальними акторами системи на кристалі (SoC).

## 1. Постановка задачі керування тепловим бюджетом

Розглядається гетерогенна система на кристалі, яка складається з `N` виконавчих компонентів-акторів (наприклад, кластери високопродуктивних процесорних ядер CPU big, енергоефективних ядер CPU LITTLE, графічний прискорювач GPU та нейронний процесор NPU). Кожен актор `i` під час роботи на тактовій частоті `f_i` та напрузі `V_i` споживає електричну потужність `P_i`, яка майже повністю перетворюється на теплове випромінювання й нагріває кристал.

Сумарна потужність споживання кристала складається з двох ключових компонентів — динамічної потужності переключання транзисторів `P_dynamic` та статичної потужності витоку `P_static`:

```
P_total = P_dynamic + P_static
```

Динамічна потужність залежить від швидкості перезаряджання ємностей затворів транзисторів і пропорційна частоті та квадрату напруги:

```
P_dynamic = C_dyn · V² · f
```

Статична потужність витоку струму через діелектрик затвора нелінійно експоненційно зростає з підвищенням температури кристала `T`:

```
P_static(T) = I_leak0 · e^(α·T) · V
```

Ця нелінійна залежність утворює загрозу термального розгону (thermal runaway): підвищення температури збільшує струм витоку, що викликає додатковий нагрів, який ще більше збільшує струм витоку.

Задача регулятора `power_allocator` полягає у підтримці поточної температури кристала `T(t)` біля цільового значення `T_target` (зазвичай точки спрацьовування `passive trip point`) без перевищення допустимої межі нагріву, максимізуючи при цьому підсумкову обчислювальну продуктивність системи.

## 2. Безперервна модель PID-контролера та стійкість контуру

Помилка регулювання `e(t)` визначається як відхилення цільової температури від поточної температури термальної зони:

```
e(t) = T_target - T(t)
```

Загальна дозволена потужність розсіювання кристала `P_alloc(t)` у безперервному часі обчислюється як сума базової стійкої потужності `P_sustainable` та виходу PID-контролера:

```
P_alloc(t)
= P_sustainable + P_pid(t)                                    [розділення на стійке розсіювання та вихід PID]
= P_sustainable + k_p·e(t) + k_i·∫ e(τ) dτ + k_d·(de(t)/dt)  [розгортання пропорційної, інтегральної та диференціальної ланок]
```

Де:
- `P_sustainable` — номінальна теплова потужність у міліватах, яку система охолодження (радіатор, корпус) здатна стаціонарно розсіювати у навколишнє середовище без безнастанного зростання температури.
- `k_p` — коефіцієнт пропорційної ланки (підвищує швидкість реакції на поточне відхилення).
- `k_i` — коефіцієнт інтегральної ланки (усуває статичну похибку у стаціонарному режимі).
- `k_d` — коефіцієнт диференціальної ланки (прогнозує тренд зміни температури та гасить осциляції).

### Аналіз передавальної функції та теплового запізнення

Фізичний процес передачі тепла від кремнієвого кристала через теплорозподілювач до зовнішнього середовища володіє тепловою інерцією і описується передавальною функцією першого порядку із запізненням `τ_delay`:

```
H_thermal(s) = K_thermal / ((τ_thermal · s + 1) · e^(s · τ_delay))
```

Присутність чистого запізнення `τ_delay` (часовий інтервал між зміною напруги на транзисторах та фіксацією температури термодіодом) обмежує максимальні значення коефіцієнтів `k_p` та `k_d`. Занадто велике значення `k_p` призводить до фазового зсуву у контурі зворотного зв'язку і виникає автоколивальний режим перегріву/переохолодження.

## 3. Дискретизація алгоритму для ядра Linux

Оскільки ядро Linux виконує код регулятора через дискретні інтервали часу `Δt` (визначені параметром `passive_delay`), безперервне диференціальне рівняння замінюється дискретним аналогом для `k`-го кроку опитування.

Позначимо через `e[k] = T_target - T[k]` помилку температури на кроці `k`.

### Крок 1: Пропорційний внесок `P_prop`

```
P_prop[k]
= k_p · e[k]          [пропорційна реакція на поточну помилку]
```

Ця ланка забезпечує негайну реакцію: якщо температура перевищує поріг (`e[k] < 0`), пропорційний внесок стає від'ємним, відразу зменшуючи загальний бюджет потужності `P_alloc`.

### Крок 2: Дискретне інтегрування та захист від насичення (Anti-Windup)

Інтегральна сума `err_integral` накопичується на кожному кроці з урахуванням інтервалу `Δt`:

```
err_integral[k]
= err_integral[k-1] + e[k]·Δt      [чисельне інтегрування методом прямокутників]

P_integ[k]
= k_i · err_integral[k]            [інтегральний внесок у бюджет]
```

Для запобігання ефекту інтегрального насичення (Integral Windup), коли накопичена помилка за час тривалого нагріву блокує повернення системи у штатний режим після охолодження, інтегральний внесок жорстко обмежується діапазоном `[P_integ_min, P_integ_max]`:

```
P_integ[k]
= max(P_integ_min, min(P_integ_max, P_integ[k]))   [обмеження Anti-Windup]
```

Якщо не застосувати це обмеження, накопичене значення інтеграла під час тривалого стрес-тесту вимагатиме багатьох хвилин для "розряджання" після спаду навантаження, тримаючи процесор на мінімальній частоті навіть при холодній системі.

### Крок 3: Диференціальний внесок `P_deriv` та фільтрація шуму

Диференціал оцінюється за першою різницею помилки між сусідніми кроками опитування:

```
P_deriv[k]
= k_d · ((e[k] - e[k-1]) / Δt)     [чисельне диференціювання]
```

Оскільки виміряне значення температури від реального термодатчика піддається аналоговим шумам та флуктуаціям, застосування чистого диференціювання створює високочастотні сплески у бюджеті потужності. У ядрі Linux різниця температур додатково згладжується через експоненційне ковзне середнє (EMA filter):

```
filtered_diff[k]
= α · (e[k] - e[k-1]) + (1 - α) · filtered_diff[k-1]  [фільтрація шуму вимірювання]
```

### Крок 4: Підсумовування загального бюджету потужності `P_alloc[k]`

```
P_alloc[k]
= P_sustainable + P_prop[k] + P_integ[k] + P_deriv[k]  [сумарний бюджет потужності]
```

Отримане значення `P_alloc[k]` додатково обмежується знизу мінімально необхідною потужністю для функціонування чипа: `P_alloc[k] = max(0, P_alloc[k])`.

## 4. Математичний алгоритм розподілу потужності між акторами

Після обчислення загального доступного бюджету `P_alloc[k]` регулятор `power_allocator` повинен пропорційно розподілити цю потужність між усім набором активних пристроїв охолодження (акторів).

### Крок 1: Оцінка запитуваної потужності від акторів `P_requested`

Кожен актор `i` обчислює свою поточну запитувану потужність `P_req,i` на основі таблиці моделей енергоспоживання (Energy Model, EM) за формулою споживання кремнієвих транзисторів для поточної робочої точки OPP:

```
P_req,i
= C_dyn,i · V_i² · f_i + P_static,i   [динамічна та статична потужність актора i]
```

Якщо актор знаходиться у стані простою (idle), його запитувана потужність `P_req,i` оцінюється як нуль, і він виключається з розподілу активного бюджету.

### Крок 2: Нормалізація та виділення частки потужності `P_granted,i`

Сумарна запитувана потужність усіх акторів становить:

```
P_total_req
= ∑ P_req,i                          [сума запитів усіх N акторів]
```

У разі якщо сумарний запит не перевищує доступний бюджет (`P_total_req ≤ P_alloc[k]`), ядро не обмежує жоден актор: `P_granted,i = P_req,i`.

Якщо ж `P_total_req > P_alloc[k]` (запити перевищують безпечний бюджет), регулятор зменшує виділену потужність `P_granted,i` для кожного актора пропорційно його ваговій частці:

```
P_granted,i
= P_alloc[k] · (P_req,i / P_total_req)   [пропорційний розподіл бюджету]
```

Цей підхід гарантує справедливість: актор, який споживає більше тепла, зазнає пропорційно більшого придушення потужності, ніж актор із низьким рівнем споживання.

### Крок 3: Трансляція потужності у робочу точку OPP

Отримане значення `P_granted,i` для кожного актора `i` використовується для пошуку у таблиці Energy Model найвищої тактової частоти `f_allowed,i`, при якій споживання актора не перевищує виділену межу `P_granted,i`:

```
f_allowed,i
= max { f ∈ OPP_i | P_EM(f) ≤ P_granted,i }   [вибір максимально дозволеної частоти]
```

Знайдена частота `f_allowed,i` передається драйверу пасивного охолодження `cpufreq_cooling` або `devfreq_cooling` як верхня межа для притиснення робочого стану пристрою.

## 5. Граничні випадки та аварійна підсистема захисту

Математичний алгоритм PID-регулятора розрахований на плавне утримання температури у діапазоні пасивного охолодження. Проте в умовах екстремального нагріву (наприклад, при раптовому виході з ладу зовнішнього кулера або блокуванні вентиляційних отворів) алгоритм передбачає аварійні переходи:

1. **Аварійний перехід на максимальний тротлінг:** Якщо температура продовжує зростати і перетинає верхній поріг `trip_point_max`, регулятор миттєво ігнорує розраховані значення `P_granted,i` та примусово встановлює для всіх акторів мінімальну доступну частоту `f_min` (`cur_state = max_state`).
2. **Втрата даних від датчика (Sensor Failure):** Якщо виклик `get_temp()` повертає помилку `EIO` або від'ємне значення, регулятор переходить у консервативний безпечний режим (Fail-Safe mode), зберігаючи останнє відоме значення тротлінгу для запобігання термальному розгону.
