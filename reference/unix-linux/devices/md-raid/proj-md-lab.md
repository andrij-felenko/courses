# ⚙️ Масив із шести файлів: зібрати, зламати, полагодити

Справжній масив md не потребує жодного диска: шість звичайних файлів, підкладених як блокові пристрої, поводяться під драйвером точнісінько так само, як шість носіїв. Це дає лабораторію, у якій помилка не коштує нічого, — і в ній видно дві речі, яких з опису не вичитати: що `repair` не повертає правильних даних і що карта намірів скорочує догін відсталого учасника з хвилини до секунд.

Усе далі виконується від `root` на будь-якому ядрі з модулями `raid456` і `raid1`. Реальне місце на диску не перевищить 6 × 128 МіБ: файли починаються розрідженими, але початкова синхронізація й `repair` проходять учасників наскрізь і поступово заповнюють їх.

## Стенд

```bash
mkdir -p /var/tmp/mdlab && cd /var/tmp/mdlab

declare -a L
for i in 0 1 2 3 4 5; do
    truncate -s 128M disk$i.img            # файл розріджений: місця поки не займає
    L[$i]=$(losetup --find --show disk$i.img)
done
printf '%s\n' "${L[@]}"                    # /dev/loop0 … /dev/loop5 — номери можуть бути інші
```

`truncate` створює [розріджений файл](book:unix-linux/sparse-files): розмір є, зайнятих блоків немає. `losetup --find --show` бере перший вільний номер і одразу друкує ім'я готового [loop-пристрою](book:unix-linux/loop-device) — саме тому імена збираються в масив оболонки, а не вписуються в команди руками: на робочій машині перші номери майже напевно вже зайняті чужими образами.

## Масив і його суперблок

```bash
mdadm --create /dev/md0 --level=5 --raid-devices=3 --chunk=64 \
      --bitmap=none --metadata=1.2 --name=lab5 "${L[@]:0:3}"

mdadm --create /dev/md1 --level=1 --raid-devices=2 \
      --bitmap=none --metadata=1.2 --name=lab1 "${L[@]:4:2}"

cat /proc/mdstat
```

```
Personalities : [raid1] [raid6] [raid5] [raid4]
md1 : active raid1 loop5[1] loop4[0]
      129024 blocks super 1.2 [2/2] [UU]
      [=======>.............]  resync = 38.1% (49216/129024) ...

md0 : active raid5 loop2[3] loop1[1] loop0[0]
      258048 blocks super 1.2 level 5, 64k chunk, algorithm 2 [3/2] [UU_]
      [==========>..........]  recovery = 52.4% (67648/129024) ...
```

Перша несподіванка тут — рядок `md0`. Масив щойно створено з трьох цілих пристроїв, а склад показано як `[3/2] [UU_]`, і йде **recovery**, а не resync. Це не збій: `mdadm` навмисно створює RAID5 неповним, оголошуючи останнього учасника запасним, і потім відбудовує його. Вийшло дешевше, ніж чесний resync: відбудова читає дані й пише один носій, тоді як resync мусив би читати й переписувати всіх.

Тепер погляньмо, що лягло на учасника.

```bash
mdadm --examine "${L[0]}"
```

```
        Version : 1.2
     Array UUID : 6f8c1d7a:9e40b512:...
           Name : lab:lab5
     Raid Level : raid5
   Raid Devices : 3
 Avail Dev Size : 258048 sectors (126.00 MiB 132.12 MB)
     Array Size : 258048 KiB (252.00 MiB 264.24 MB)
    Data Offset : 4096 sectors
   Super Offset : 8 sectors
         Events : 18
     Chunk Size : 64K
    Device Role : Active device 0
    Array State : AAA ('A' == active, '.' == missing, 'R' == replacing)
```

Тут одразу приховано пастку читання: `Avail Dev Size` надруковано **в секторах**, а `Array Size` — **у кілобайтах**, і на масиві з трьох носіїв ці два числа збігаються цифрами при різних одиницях. `Data Offset : 4096 sectors` — це те, що знадобиться далі: дані масиву починаються на учаснику з двомегабайтного зсуву, а перед ними лежать суперблок і журнал поганих блоків.

## Записати відоме, зіпсувати навмисно

```bash
mdadm --wait /dev/md0 /dev/md1          # дочекатися кінця початкової синхронізації

dd if=/dev/urandom of=pattern.bin bs=1M count=8 status=none
dd if=pattern.bin of=/dev/md0 bs=1M oflag=direct conv=fsync status=none
dd if=/dev/md0 bs=1M count=8 iflag=direct status=none | cmp - pattern.bin && echo "збіглося"
```

`oflag=direct` і `iflag=direct` тут не примха: вони [обходять кеш сторінок](book:unix-linux/buffered-and-direct-io), тож порівнюємо ми справді те, що масив дістав із носіїв, а не те, що система запам'ятала дорогою.

Тепер зіпсуємо один шматок даних повз масив. Розкладка `left-symmetric` кладе нульовий шматок першої смуги на першого учасника, тож потрібне місце — рівно `Data Offset` на `L[0]`.

```bash
mdadm --stop /dev/md0
OFF=$(mdadm --examine "${L[0]}" | awk '/Data Offset/ {print $4}')   # у секторах
dd if=/dev/urandom of="${L[0]}" bs=512 seek="$OFF" count=8 conv=fsync status=none
mdadm --assemble /dev/md0 "${L[@]:0:3}"
```

Масив спиняється перед псуванням не для чистоти жанру. Живий md тримає смуги у власному кеші й читає учасників власними запитами повз кеш блокового пристрою — тож запис у працюючого учасника то видно, то ні. Зупинка й повторне збирання роблять дослід відтворюваним.

## check не лагодить, repair не рятує

```bash
echo check > /sys/block/md0/md/sync_action
while [ "$(cat /sys/block/md0/md/sync_action)" != idle ]; do sleep 1; done
cat /sys/block/md0/md/mismatch_cnt        # 8
```

Зіпсовано 4 КіБ, а лічильник показує 8. Він рахує **сектори**, і не ті, що справді відрізняються, а ті, що були б переписані: рівні масиву працюють сторінками, тож зіпсований один-єдиний байт дав би те саме число 8. Читати `mismatch_cnt` як «скільки помилок» — помилка сама собою.

Дані вже неправильні, і масив цього не приховує — він просто віддає те, що лежить на учаснику:

```bash
dd if=/dev/md0 bs=1M count=8 iflag=direct status=none | cmp - pattern.bin
# - pattern.bin differ: byte 1, line 1
```

А тепер головне в усьому досліді.

```bash
echo repair > /sys/block/md0/md/sync_action
while [ "$(cat /sys/block/md0/md/sync_action)" != idle ]; do sleep 1; done

dd if=/dev/md0 bs=1M count=8 iflag=direct status=none | cmp - pattern.bin
# - pattern.bin differ: byte 1, line 1     ← НЕ полагодилося
```

`repair` на масиві з парністю робить одне: перераховує парність із даних і записує її. Він не має підстав вважати дані зіпсованими — жодного незалежного свідчення про те, якими вони мають бути, у масиві немає. Тож розбіжність він усунув, оголосивши істиною сміття. Наступний `check` чесно покаже нуль: масив узгоджений, дані втрачені.

> 🔧 **Навіщо це.** Саме тому дистрибутиви ганяють за розкладом `check`, а не `repair`. Ненульовий `mismatch_cnt` — це привід шукати причину (кабель, пам'ять, носій), а не команда лагодити. Автоматичний `repair` перетворив би сигнал про псування на тихо зацементоване псування, ще й прибрав би єдиний слід.

Щоб побачити зворотний випадок, повернімо вміст і зіпсуймо тепер **парність** — вона в першій смузі лежить на останньому учаснику.

```bash
dd if=pattern.bin of=/dev/md0 bs=1M oflag=direct conv=fsync status=none
mdadm --stop /dev/md0
dd if=/dev/urandom of="${L[2]}" bs=512 seek="$OFF" count=8 conv=fsync status=none
mdadm --assemble /dev/md0 "${L[@]:0:3}"

echo check > /sys/block/md0/md/sync_action
while [ "$(cat /sys/block/md0/md/sync_action)" != idle ]; do sleep 1; done
cat /sys/block/md0/md/mismatch_cnt                                          # знову 8
dd if=/dev/md0 bs=1M count=8 iflag=direct status=none | cmp - pattern.bin   # збігається!
```

Розбіжність та сама, а дані цілі: у повному складі парність ніхто не читає. Тепер `repair` справді лікує, і перевірити це можна єдиним чесним способом — забравши носія й змусивши масив рахувати:

```bash
echo repair > /sys/block/md0/md/sync_action
while [ "$(cat /sys/block/md0/md/sync_action)" != idle ]; do sleep 1; done

mdadm --fail /dev/md0 "${L[0]}" && mdadm --remove /dev/md0 "${L[0]}"
dd if=/dev/md0 bs=1M count=8 iflag=direct status=none | cmp - pattern.bin && echo "неповний склад, дані цілі"
```

## Число, за яким масив упізнає свіжого

Знятий `L[0]` нікуди не подівся — він лежить на місці зі своїм суперблоком, і суперблок цей уже застарілий. Порівняймо його з тим, хто лишався в масиві:

```bash
mdadm --examine "${L[0]}" | grep -E 'Events|Array State'
#          Events : 24
#     Array State : AAA ('A' == active, '.' == missing, 'R' == replacing)

mdadm --examine "${L[1]}" | grep -E 'Events|Array State'
#          Events : 31
#     Array State : .AA ('A' == active, '.' == missing, 'R' == replacing)
```

Ось той арбітр, якого не існує на рівні окремого сектора. Знятий носій застиг на числі 24 і досі певен, що склад повний; решта масиву відрахувала подальші події й пам'ятає, що першої ролі в складі немає. Обидва суперблоки внутрішньо несуперечливі — розводить їх тільки порядок у часі.

Що з цього виходить, видно, якщо подати `mdadm` усіх трьох початкових учасників і попросити зібрати масив:

```bash
mdadm --stop /dev/md0
mdadm --assemble --verbose /dev/md0 "${L[@]:0:3}"
# mdadm: /dev/loop0 is identified as a member of /dev/md0, slot 0.
# ...
# mdadm: /dev/md0 has been started with 2 drives (out of 3).
```

Пристрій подали — а масив однаково запустився неповним. `mdadm` не збирає за іменами й не довіряє порядку в командному рядку: він читає всі подані суперблоки, знаходить найбільший лічильник і бере в склад лише тих, хто його має (невелике відставання терпить, бо суперблоки оновлюються не строго одночасно). Краще свідомо працювати вдвох, ніж прийняти за рівного того, хто пропустив частину записів.

Продавити це можна ключем `--force`, і саме тут ховається найдорожча помилка ночі. `--force` не лагодить масив: він підправляє лічильники, оголошуючи задавнений вміст свіжим, — після чого решта учасників чесно приводиться до нього. Ключ рятує тоді, коли інакше масив узагалі не запуститься, і губить тоді, коли ним намагаються прискорити звичайне збирання.

## Запасний і відбудова

Масив працює на двох учасниках із трьох. Даймо йому третього.

```bash
echo 2000 > /sys/block/md0/md/sync_speed_max    # КіБ/с — інакше на файлах усе минає миттєво
mdadm --add /dev/md0 "${L[3]}"

cat /proc/mdstat
cat /sys/block/md0/md/sync_completed            # 24576 / 258048
```

Обмеження швидкості тут — не оптимізація, а спосіб узагалі щось побачити: без нього 126 МіБ переллються швидше, ніж устигне намалюватися смужка. З ним відбудова триває приблизно `129024 / 2000 ≈ 65` секунд, а `sync_completed` показує, скільки секторів з усіх уже пройдено.

## Карта намірів: догін замість відбудови

Дзеркало `md1` ми створили без карти — на ньому й видно різницю. Спершу заміряймо голий випадок.

```bash
echo 2000 > /sys/block/md1/md/sync_speed_max
mdadm --fail /dev/md1 "${L[5]}" && mdadm --remove /dev/md1 "${L[5]}"
dd if=/dev/urandom of=/dev/md1 bs=1M count=4 seek=10 oflag=direct conv=fsync status=none

time { mdadm --add /dev/md1 "${L[5]}"
       while [ "$(cat /sys/block/md1/md/sync_action)" != idle ]; do sleep 0.2; done; }
# real ≈ 1m5s
```

За час відсутності носія в масив записали 4 МіБ — а догнати довелося всі 126. Тепер те саме з картою:

```bash
mdadm --grow /dev/md1 --bitmap=internal --bitmap-chunk=4M
grep -A2 '^md1' /proc/mdstat        # bitmap: 1/1 pages [4KB], 4096KB chunk

mdadm --fail /dev/md1 "${L[5]}" && mdadm --remove /dev/md1 "${L[5]}"
dd if=/dev/urandom of=/dev/md1 bs=1M count=4 seek=10 oflag=direct conv=fsync status=none

time { mdadm --add /dev/md1 "${L[5]}"
       while [ "$(cat /sys/block/md1/md/sync_action)" != idle ]; do sleep 0.2; done; }
# real ≈ 4s
```

Чотири секунди замість шістдесяти п'яти — і число не випадкове. Запис на 4 МіБ із зсувом 10 МіБ зачепив дві ділянки карти по 4 МіБ, тобто 8 МіБ; при тій самій межі швидкості це `8192 / 2000 ≈ 4` секунди. Копіювалося рівно те, що позначено бітами, решту масиву md навіть не читав.

Працює це лише тому, що `--remove` не стирає суперблока: `--add` бачить колишнього учасника й спершу пробує повернути його як свого (те саме, що явний `--re-add`). Досить було б між зняттям і поверненням зробити `--zero-superblock` — і карта не допомогла б, бо носій прийшов би чужим, а чужого доводиться відбудовувати цілком.

## Пастки

**Не монтувати учасника напряму.** З метаданими 1.2 спокуси майже немає — на початку носія лежить сигнатура md. А от із форматом 1.0 чи 0.90 суперблок сидить у хвості, і на початку залишається звичайна сигнатура файлової системи:

```bash
mdadm --stop /dev/md1                              # дзеркало вже відпрацювало, звільняємо пару
mdadm --zero-superblock "${L[4]}" "${L[5]}"

mdadm --create /dev/md2 --level=1 --raid-devices=2 --metadata=1.0 --bitmap=none \
      --name=lab0 "${L[4]}" "${L[5]}" && mdadm --wait /dev/md2
mkfs.ext4 -q /dev/md2 && mdadm --stop /dev/md2

blkid "${L[4]}"        # TYPE="ext4" — учасник виглядає самостійним томом
```

Змонтувати такий пристрій вдасться, і система нічого не запідозрить. Кожен запис туди піде повз масив і породить саме ту розбіжність копій, від якої масив мав захищати.

**Не плутати `check` з `repair`.** Різниця не в силі, а в праві на запис: перший записує в лічильник, другий записує на носії. На дзеркалі `repair` оголошує еталоном першу копію, на парності — дані; в обох випадках вибір робиться без жодного знання про те, хто правий.

**`--assume-clean` економить не там, де здається.** Ключ пропускає початкову синхронізацію: масив оголошується узгодженим одразу, без відбудови й без resync. На чистих носіях це виглядає безкоштовним прискоренням створення — але узгодженість при цьому ніхто не перевіряв. Досить одному учасникові прийти з чужими даними чи просто з іншим сміттям, і перший же `check` дасть тисячі розбіжностей, а `repair` зацементує парність під невідомий вміст. Місце ключа — відтворення масиву з відомим вмістом (наприклад, після помилкового `--create` над живими даними), а не звичайне створення.

**`mismatch_cnt` обнуляється на початку кожного проходу** й після `repair` показує не залишок розбіжностей, а те, скільки секторів було переписано. Побачити нуль можна лише наступним `check`.

**Час на loop — модель, а не вимір.** Усі шість «носіїв» лежать на одній файловій системі одного справжнього диска, тож затримки, паралелізм і поведінка черг тут ні про що не свідчать. Свідчить лише логіка: скільки прочитано, скільки записано, що і в якому порядку сталося.

**Не залишати за собою сміття.** На робочій машині [udev](book:unix-linux/udev-rules) реагує на кожен новий блоковий пристрій і може підхопити залишений учасник у наступному завантаженні, а `mdadm --detail --scan >> /etc/mdadm.conf` впише лабораторні масиви в конфігурацію системи. Прибирати треба в три кроки — зупинити, стерти суперблоки, відчепити:

```bash
mdadm --stop /dev/md0                    # md1 і md2 спинено раніше
for d in "${L[@]}"; do mdadm --zero-superblock "$d" 2>/dev/null; done
losetup -d "${L[@]}"
cd .. && rm -rf /var/tmp/mdlab
```

Найкорисніше, що лишається після цього досліду, — точне розуміння межі. md уміє тримати учасників однаковими й уміє швидко доводити відсталого до решти. Він ніде не вміє сказати, які байти правильні: за цим треба йти до шару з контрольними сумами на кшталт [dm-integrity](book:unix-linux/dm-integrity) або до файлової системи, що перевіряє прочитане сама.
