# ⚙️ Найпростіший символьний драйвер: дві реєстрації й чотири операції

Зберемо модуль ядра, який дає `/dev/lichylnyk` — файл, що на кожне читання видає рядок із лічильником відкриттів, а на запис той лічильник обнуляє. Заліза під ним немає навмисно: тоді в коді не лишиться нічого, крім самої механіки файлу пристрою, побаченої з протилежного боку — з боку того, хто відповідає на чужі `open` і `read`.

## Задача

Після `insmod` у системі має з'явитися вузол, з яким працюють звичайні програми, нічого про нас не знаючи:

```sh
$ sudo cat /dev/lichylnyk
відкриттів: 1
$ sudo cat /dev/lichylnyk
відкриттів: 2
$ echo скинь | sudo tee /dev/lichylnyk
скинь
$ sudo cat /dev/lichylnyk
відкриттів: 1
```

Вузол мусить створитися сам, без `mknod`; номер драйвер не обирає, а просить у ядра. Після `rmmod` усе має зникнути безслідно — і ми окремо подивимося, що буде, якщо вивантажити модуль тієї миті, коли хтось тримає дескриптор відкритим.

## Ідея: дві реєстрації, які нічого не знають одна про одну

Найбільша плутанина в цьому коді — думка, що всі чотири виклики ініціалізації роблять одну справу. Насправді це дві незалежні пари.

**Перша пара дає поведінку.** `alloc_chrdev_region()` просить ядро видати вільний старший номер (молодші ми беремо самі, від нуля). Просимо, а не вибираємо: колись номери роздавали з письмового реєстру, і зіткнення двох драйверів на одному числі було звичайною бідою; сьогодні статичні номери лишилися хіба що в найдавніших пристроїв, решта бере динамічний. Далі `cdev_init()` зшиває структуру `cdev` із нашою таблицею `file_operations`, а `cdev_add()` кладе цю пару в реєстр символьних пристроїв. Саме звідти ядро дістає таблицю, коли хтось відкриває вузол із такими номерами. Що означають самі числа — [старший і молодший номери](book:unix-linux/major-minor-numbers).

**Друга пара дає ім'я.** `class_create()` заводить клас у [моделі пристроїв](book:unix-linux/sysfs-device-model), `device_create()` — конкретний пристрій у ньому. Символьних пристроїв ці двоє не стосуються взагалі: вони лише ставлять пристрій у модель, а він несе в собі те саме число `dev_t`. До самої реєстрації підвішено `devtmpfs`: побачивши пристрій із непорожнім `dev_t`, він одразу створює для нього вузол у `/dev`. Драйвер вузла не створює — він публікує пристрій, а вузол з'являється як наслідок. (`udev` підхоплює це трохи згодом і вже з `sysfs`, з файла `dev`, читає ті самі `511:0`, щоб виставити права й додаткові імена.)

![Дві горизонтальні доріжки. Верхня, синя: alloc_chrdev_region видає вільний старший номер, cdev_init і cdev_add кладуть у реєстр пару 511:0 → file_operations, після чого open по цих номерах уже потрапляє в драйвер, хоч вузла в /dev ще немає. Нижня, зелена: class_create із device_create ставлять пристрій у модель разом із тим самим dev_t, підвішений до реєстрації devtmpfs одразу створює /dev/lichylnyk, а udev згодом читає 511:0 з файла dev у sysfs і доводить права та імена. Між доріжками сіра стрілка з підписом «той самий dev_t»](/reference/unix-linux/devices/device-file-model/img/two-registrations.svg)

*Спільне в двох доріжок рівно одне — число `dev_t`. Тому кожну можна завести без іншої, і кожна без іншої стає безглуздою по-своєму.*

Розділення — не примха, а слід історії: спершу існувала сама лише верхня доріжка, а вузли робили наперед і руками. Тому й сьогодні драйвер без `class_create` чудово збирається й працює — тільки після `insmod` доводиться самому дивитися виданий старший номер у `/proc/devices` і викликати `mknod`.

## Код

Один файл, дві пари реєстрацій, чотири операції. Мова тут не обговорюється: модуль ядра — це C, іншого способу немає.

```c
// SPDX-License-Identifier: GPL-2.0
#include <linux/cdev.h>
#include <linux/device.h>
#include <linux/err.h>
#include <linux/fs.h>
#include <linux/module.h>
#include <linux/mutex.h>
#include <linux/uaccess.h>

#define DEV_NAME  "lichylnyk"
#define BODY_MAX  64

static dev_t         lich_dev;      /* старший:молодший, видані ядром */
static struct cdev   lich_cdev;
static struct class *lich_class;

static DEFINE_MUTEX(lich_lock);
static unsigned long lich_opens;    /* тільки під lich_lock */

/* Увесь «вміст» файлу малює одна функція. Розміру наперед немає —
   отже, де кінець файлу, вирішує сам драйвер у lich_read().        */
static int lich_render(char *body, size_t cap)
{
	unsigned long n;

	mutex_lock(&lich_lock);
	n = lich_opens;
	mutex_unlock(&lich_lock);

	return scnprintf(body, cap, "відкриттів: %lu\n", n);
}

static int lich_open(struct inode *inode, struct file *filp)
{
	unsigned long n;

	mutex_lock(&lich_lock);
	n = ++lich_opens;
	mutex_unlock(&lich_lock);

	pr_info("lich: open, молодший %u, усього %lu\n", iminor(inode), n);
	return 0;
}

static int lich_release(struct inode *inode, struct file *filp)
{
	pr_info("lich: release\n");
	return 0;
}

static ssize_t lich_read(struct file *filp, char __user *buf,
			 size_t count, loff_t *ppos)
{
	char body[BODY_MAX];
	int  len = lich_render(body, sizeof body);

	/* Кінець файлу — наш обов'язок. Не повернемо нуля — cat не спиниться. */
	if (*ppos >= len)
		return 0;
	if (count > (size_t)(len - *ppos))
		count = len - *ppos;

	/* Повертає число НЕ скопійованих байтів; нуль означає успіх. */
	if (copy_to_user(buf, body + *ppos, count))
		return -EFAULT;

	*ppos += count;
	return count;
}

static ssize_t lich_write(struct file *filp, const char __user *buf,
			  size_t count, loff_t *ppos)
{
	char   kbuf[BODY_MAX];
	size_t n = min(count, sizeof(kbuf) - 1);

	if (copy_from_user(kbuf, buf, n))
		return -EFAULT;
	kbuf[n] = '\0';
	if (n && kbuf[n - 1] == '\n')
		kbuf[n - 1] = '\0';

	mutex_lock(&lich_lock);
	lich_opens = 0;
	mutex_unlock(&lich_lock);

	pr_info("lich: скинуто, прийшло %zu байтів: «%s»\n", count, kbuf);
	return count;   /* кажемо, що з'їли все: інакше запис повторять */
}

static const struct file_operations lich_fops = {
	.owner   = THIS_MODULE,   /* саме це тримає модуль, поки файл відкрито */
	.open    = lich_open,
	.release = lich_release,
	.read    = lich_read,
	.write   = lich_write,
};

static int __init lich_init(void)
{
	struct device *dev;
	int ret;

	ret = alloc_chrdev_region(&lich_dev, 0, 1, DEV_NAME);
	if (ret)
		return ret;

	/* Після cdev_add() пристрій живий: open може прийти наступної миті
	   й на іншому ядрі процесора. Усе, чого торкаються lich_*, має бути
	   готове ДО цього рядка.                                          */
	cdev_init(&lich_cdev, &lich_fops);
	lich_cdev.owner = THIS_MODULE;
	ret = cdev_add(&lich_cdev, lich_dev, 1);
	if (ret)
		goto err_region;

	lich_class = class_create("lich");   /* із ядра 6.4 — один аргумент */
	if (IS_ERR(lich_class)) {
		ret = PTR_ERR(lich_class);
		goto err_cdev;
	}

	dev = device_create(lich_class, NULL, lich_dev, NULL, DEV_NAME);
	if (IS_ERR(dev)) {
		ret = PTR_ERR(dev);
		goto err_class;
	}

	pr_info("lich: готово, номери %d:%d\n",
		MAJOR(lich_dev), MINOR(lich_dev));
	return 0;

err_class:
	class_destroy(lich_class);
err_cdev:
	cdev_del(&lich_cdev);
err_region:
	unregister_chrdev_region(lich_dev, 1);
	return ret;
}

static void __exit lich_exit(void)
{
	device_destroy(lich_class, lich_dev);
	class_destroy(lich_class);
	cdev_del(&lich_cdev);
	unregister_chrdev_region(lich_dev, 1);
	pr_info("lich: пішли\n");
}

module_init(lich_init);
module_exit(lich_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Символьний пристрій-лічильник відкриттів");
```

Вихід із помилки написано драбинкою `goto` не з любові до старовини: кожна мітка скасовує рівно один уже вдалий крок, а `lich_exit()` — це та сама драбинка, пройдена повністю. Розійдуться вони — і невдалий `insmod` лишить по собі зайнятий діапазон номерів, який до перезавантаження ніхто не звільнить.

Слово `owner` стоїть двічі, і це не описка. Ядро бере посилання на модуль у двох різних місцях: `cdev_get()` дивиться на `cdev->owner`, коли знаходить пристрій у реєстрі, а `fops_get()` — на `fops->owner`, коли підставляє таблицю в новий дескриптор. Заповнюють обидва, так само як драйвери в дереві ядра.

Роздільність двох пар — не єдиний можливий вигляд коду. Коли `struct cdev` вкладено в структуру самого пристрою, обидві реєстрації зшивають одним викликом `cdev_device_add()`: він робить те, що `cdev_add()` і `device_add()`, у правильному порядку й з правильним відкотом. Нарізно ми пишемо саме тому, що предмет розмови — роздільність.

## Збирання й перевірка

Модуль збирається не сам по собі, а системою збирання ядра — тому Makefile складається з двох рядків, а решту робить дерево ядра, установлене пакунком заголовків (`linux-headers-$(uname -r)` у Debian, `kernel-devel` у Fedora):

```makefile
obj-m += lich.o

KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules
clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean
```

```sh
$ make && sudo insmod lich.ko
$ dmesg | tail -1
[ 9412.771003] lich: готово, номери 511:0
$ ls -l /dev/lichylnyk
crw------- 1 root root 511, 0 сер  8 14:02 /dev/lichylnyk
$ sudo cat /dev/lichylnyk
відкриттів: 1
```

Вузол з'явився сам, із номерами, які ядро видало щойно — при наступному завантаженні старший номер може бути іншим, і це нормально. Права `0600` для `root` — типова відповідь `devtmpfs`; звичні `0660` для групи роздають уже [правилом udev](book:unix-linux/udev-rules), а не драйвером, і саме тому доступ до пристроїв [дають групами](book:unix-linux/device-access-groups), а не через `sudo`.

У [журналі ядра](book:unix-linux/kernel-log-printk) — кільцевому буфері, куди пише `pr_info` і який показує `dmesg`, — на кожен `cat` видно один `open` і один `release`, а `read` покликано двічі: перший раз віддано 24 байти (кирилиця в UTF-8 — по два байти на літеру), другий раз — нуль, і саме на нулі `cat` спинився.

Тепер найцікавіше — вивантаження при відкритому дескрипторі. В одному вікні:

```sh
$ sudo sh -c 'exec 3< /dev/lichylnyk; sleep 300'
```

У другому:

```sh
$ lsmod | grep lich
lich                   16384  1
$ sudo rmmod lich
rmmod: ERROR: Module lich is in use
```

Одиниця в стовпці `Used by` — це і є той дескриптор. Механізм точний: у `chrdev_open()` ядро робить `fops_get()`, тобто `try_module_get(fops->owner)`, а відпускає лічильник, коли закривається останнє посилання на `struct file`. Поки хоч один дескриптор живий, код модуля лишається в пам'яті, і повиснути на звільненій функції нема як.

## Пастки

**`copy_to_user()` — не `memcpy()`, і повертає не те, чого чекають.** Покажчик `buf` прийшов [з іншого адресного простору](book:unix-linux/kernel-and-userspace) і від того, кому не варто вірити: сторінка за ним може бути ще не відображена, а може бути й чужа. Тому копіювання йде через функцію, яка перевіряє діапазон і переживає сторінковий збій, повертаючи помилку замість того, щоб покласти ядро. Повертає вона **число не скопійованих байтів**, тож `if (copy_to_user(...))` читається як «щось лишилося — біда», а звичний рефлекс `if (copy_to_user(...) < 0)` не спрацює ніколи.

**Кінець файлу рахує драйвер.** `cat` читає, доки `read` не поверне нуль. Драйвер, що на кожен виклик віддає повний рядок, ігноруючи `*ppos`, — це `cat`, який друкує до `Ctrl-C`. Чотири рядки арифметики з `*ppos` настільки типові, що в ядрі є готовий `simple_read_from_buffer()`, який робить рівно їх. Там, де позиція взагалі не має змісту (потік, а не вміст), правильніше сказати це прямо — `stream_open()` в `.open`; поле `.llseek` при цьому лишають порожнім, бо колишню заглушку `no_llseek` з ядра прибрали у версії 6.12.

**`ENXIO` замість `ENOENT`.** Динамічний номер щоразу інший, тож вузол, зроблений `mknod` за вчорашнім числом, після перезавантаження вказує в порожнечу. `open` знайде ім'я, але не знайде драйвера в реєстрі й поверне саме `ENXIO` — «немає такого пристрою чи адреси». Цим і окупається друга пара викликів: вузол завжди робиться з тим номером, який ядро видало щойно.

**Лічильник модуля стереже дескриптори — і більше нічого.** Він не знає ні про таймер, який ви завели, ні про роботу в черзі, ні про потік ядра: жодне з них модуля не тримає. Не скасували їх у `lich_exit()` — і зворотний виклик стрибне в пам'ять, де коду вже немає. Про той самий лічильник варто пам'ятати й з іншого боку: `rmmod --force` існує саме для того, щоб його обійти, і тому в дистрибутивних ядрах цю можливість вимикають ще при [збиранні](book:unix-linux/kernel-config-and-build).

**Двері відчиняються раніше, ніж здається.** Небезпечне вікно на завантаженні й на вивантаженні симетричне, і воно вужче, ніж уся функція. `cdev_add()` не «готує» пристрій — він вмикає його: наступним тактом, на іншому ядрі процесора, вже може виконуватися ваш `lich_open()`. Тому в `lich_init()` він стоїть після всього, чого торкаються наші операції. І з тієї ж причини `device_create()` іде після нього, а не перед: інакше вузол устиг би з'явитися в `/dev` раніше, ніж запрацював реєстр, і найспритніший `open` дістав би `ENXIO` на цілком справному драйвері. З іншого кінця `cdev_del()` гарантує, що нових відкриттів більше не буде; тих, хто вже пройшов, він не чекає — за них відповідає лічильник модуля.

**Ядро не серіалізує ваші виклики.** Два процеси читають одночасно на різних ядрах процесора, і жодного спільного замка, який колись усе прикривав, у ядрі давно немає — звідси `mutex` навколо лічильника. У контексті системного виклику спати можна (мутекс і сторінковий збій у `copy_to_user` саме це й роблять), а от в обробнику переривання — ні, і плутанина між цими двома контекстами дає найдорожчі помилки в драйверах; про межу — [замки в ядрі й атомарний контекст](book:unix-linux/kernel-locking). Пристрій, який змушує читача чекати на дані, будують не на мутексі, а на [чергах очікування](book:unix-linux/kernel-wait-queues).

**Код прив'язаний до версії ядра, і це не помилка, а домовленість.** `class_create()` втратив аргумент `THIS_MODULE` у 6.4, `no_llseek` зник у 6.12 — усередині ядра сталого API немає й не обіцяли, [на відміну від межі з простором користувача](book:unix-linux/kernel-abi-stability). Практичний наслідок: модуль збирається проти конкретних заголовків, а при розбіжності `insmod` каже «Invalid module format». І `MODULE_LICENSE("GPL")` тут не формальність — без нього ядро позначається як заплямоване, а частина символів просто не лінкується.
