# 🧮 Математика обходу vring: кільцева арифметика 16-бітних індексів

Математична обґрунтованість та висока продуктивність кільцевих буферів Virtio vring базуються на властивостях модульної арифметики за модулем `2¹⁶ = 65536` та безблочній структурі Single-Producer Single-Consumer (SPSC). Завдяки використанню безперервно зростаючих 16-бітних цілих чисел беззнакового типу (`uint16_t`) для лічильників `avail->idx` та `used->idx`, система досягає абсолютно коректної обробки переповнення індексів без використання високовитратних операцій ділення з остачею (оператор `%`) на гарячому шляху виконання (fast path).

У цьому матеріалі наведено математичні докази коректності індексації, аналіз арифметики переповнення, формальні інваріанти стану черги та доказ відсутності умов гонки (race conditions) при роботі без блокувань на процесорах із слабкою моделлю впорядкування пам'яті.

---

## 1. Співвідношення розміру черги та індексації за модулем двійки

Нехай `N` — розмір віртуальної черги (максимальна кількість дескрипторів у таблиці). Специфікація OASIS Virtio вимагає, щоб розмір черги `N` завжди був степенем двійки:

```
N = 2ᵏ,  де k ∈ {1, 2, ..., 15},  N ≤ 32768
```

Оскільки `N` є степенем двійки, арифметична операція обчислення остачі від ділення для довільного 16-бітного цілого індексу `idx` тотожно замінюється побітовою кон'юнкцією `AND` із маскою `(N - 1)`:

```
idx mod N = idx & (N - 1)      [властивість степеня двійки N = 2ᵏ]
```

Розглянемо побітовий доказ цього тотожності. Довільне 16-бітне число `idx` у двійковій системі числення розкладається на дві суми бітів: старші біти (починаючи з позиції `k`) та молодші біти (позиції від `0` до `k - 1`):

```
idx = M · 2ᵏ + R,   де M = ⌊idx / 2ᵏ⌋,  a R = idx mod 2ᵏ,  0 ≤ R < 2ᵏ
```

Зазначимо, що доданок `M · 2ᵏ = M · N` націло ділиться на `N`. Отже, при взятті остачі від ділення на `N` ми отримуємо:

```
idx mod N = (M · N + R) mod N = (0 + R mod N) = R
```

Двійкова маска `N - 1 = 2ᵏ - 1` складається з `k` одиниць у молодших розрядах та нулів у старших розрядах. Побітове операція `idx & (2ᵏ - 1)` обнуляє всі старші біти `M · 2ᵏ` і залишає недоторканими молодші `k` бітів числа `R`. Таким образом, маска `(N - 1)` обчислює точне значення остачі від ділення за один процесорний такт.

## 2. Коректність переповнення 16-бітного лічильника (Free-Running Index)

Лічильник `idx` у структурах `virtq_avail` та `virtq_used` не скидається у нуль при досягненні `N`. Він безперервно збільшується на `1` при кожному додаванні буфера і вільно переповнюється за правилами арифметики беззнакових цілих чисел C/C++ за модулем `65536` (типи `uint16_t` або `unsigned short`).

Доведемо, що для будь-якого значення `idx` переповнення лічильника через межу `65535 → 0` не порушує адресуваність елементів у кільці.

Оскільки `65536 = 2¹⁶`, а `N = 2ᵏ` (де `k ≤ 15`), число `65536` є кратним `N`:

```
65536 = N · 2¹⁶⁻ᵏ
```

Розглянемо значення індексу `idx'`, утворене після додавання `65536` операцій до початкового індексу `idx`:

```
idx' = idx + 65536

idx' & (N - 1)
= (idx + 65536) mod N                          [забезпечено властивістю N = 2ᵏ]
= ((idx mod N) + (65536 mod N)) mod N          [розклад суми за модулем]
= ((idx mod N) + 0) mod N                      [оскільки 65536 є кратним N, 65536 mod N = 0]
= idx mod N
= idx & (N - 1)
```

Таким чином, математично доведено, що природне 16-бітне переповнення беззнакового цілого лічильника зберігає інваріант відповідності фізичної позиції у масиві. Програмісту не потрібно додавати перевірки умови `if (idx >= N)` у коді.

## 3. Математичний інваріант кількості нерозпізнаних буферів

Нехай `avail_idx` — поточне значення лічильника доступних буферів у `virtq_avail`, яке записав драйвер, а `last_seen_idx` — внутрішнє значення індексу в пам'яті пристрою (гіпервізора), до якого він уже встиг прочитати чергу.

Кількість буферів `count`, які очікують на обробку пристроєм, обчислюється як різниця двох 16-бітних беззнакових чисел:

```
count = (uint16_t)(avail_idx - last_seen_idx)
```

Завдяки властивостям додаткового коду (two's complement) у 16-бітній арифметиці беззнакових чисел, ця різниця обчислюється абсолютно коректно навіть тоді, коли `avail_idx` переповнився та обгорнувся через `0`, а `last_seen_idx` знаходиться біля межі `65535`.

Доведемо це на числовому прикладі. Нехай розрядність становить 16 бітів, а індекси мають значення:
```
last_seen_idx = 65534  (у шістнадцятковій формі: 0xFFFE)
avail_idx     = 2      (у шістнадцятковій формі: 0x0002)
```

За правилами 16-бітної арифметики беззнакових чисел:
```
count = (uint16_t)(0x0002 - 0xFFFE)
      = (uint16_t)(0x0002 + (0x10000 - 0xFFFE))   [арифметика додаткового коду]
      = (uint16_t)(2 + 2)
      = 4
```

Результат дорівнює `4`, що математично відповідає дійсності: драйвер додав буфери із номерами 65534, 65535, 0 та 1 (разом 4 буфери).

Основний математичний інваріант безпеки Split Virtqueue має вигляд:

```
0 ≤ (uint16_t)(avail_idx - used_idx) ≤ N
```

Якщо значення `count` перевищує `N`, це є математичним доказом фатального переповнення черги (Queue Overflow) у драйвері.

## 4. Формальний доказ відсутності Race Conditions (SPSC Lock-Free)

У Split Virtqueue драйвер є єдиним письменником у `virtq_avail` та `Descriptor Table`, а пристрій є єдиним письменником у `virtq_used`. Для забезпечення узгодженості пам'яті між CPU гостя та контролером хоста без використання виключних блокувань (lock-free) застосовується суворе впорядкування операцій запису й читання через бар'єри пам'яті.

Послідовність дій драйвера під час публікації нового буфера:

```
1. desc[head].addr = phys_addr;
2. desc[head].len  = buffer_len;
3. desc[head].flags = VIRTQ_DESC_F_NEXT;
4. desc[head].next  = next_desc_id;
   --- SMP WRITE MEMORY BARRIER (smp_wmb / sfence / dmb st) ---
5. avail->ring[avail->idx & (N - 1)] = head;
   --- SMP WRITE MEMORY BARRIER (smp_wmb / sfence / dmb st) ---
6. avail->idx += 1;
```

Формальний доказ безпеки публікації:

1. Нехай пристрій опитує `avail->idx`. Пристрій дізнається про наявність нового буфера тільки тоді, коли прочитає оновлене значення `avail->idx` на кроці 6.
2. Завдяки наявності бар'єра пам'яті на кроці 5, процесор гостя гарантує, що індекс `head` буде збережений у масиві `avail->ring` раніше, ніж оновлений лічильник `avail->idx` стане видимим для пристрою.
3. Завдяки наявності бар'єра пам'яті на кроці 4, процесор гостя гарантує, що всі поля структури дескриптора `desc[head]` (адреса, довжина, прапорці) вийдуть із буфера запису CPU і зафіксуються в пам'яті раніше, ніж пристрій прочитає індекс `head` із `avail->ring`.

Симетрична послідовність дій пристрою під час читання черги:

```
1. local_avail_idx = avail->idx;
   --- SMP READ MEMORY BARRIER (smp_rmb / lfence / dmb ld) ---
2. head = avail->ring[last_seen & (N - 1)];
   --- SMP READ MEMORY BARRIER (smp_rmb / lfence / dmb ld) ---
3. process_buffer(desc[head].addr, desc[head].len);
```

Оскільки пристрій читає вміст дескриптора `desc[head]` лише після виконання читального бар'єра `smp_rmb()`, гіпервізор гарантовано прочитає актуальні адреси пам'яті, які записав драйвер, а не застарілі дані з кешу. Це математично усуває умови гонки (race conditions).

## 5. Арифметика Packed Virtqueue та Wrap Counter

У Packed Virtqueue (v1.1+) відсутні окремі масиви `avail->ring` та `used->ring`. Усі дескриптори розташовані в єдиному масиві `pvirtq_desc` розміром `N`.

Для розрізнення стану належності комірки (драйвер чи пристрій) застосовується техніка **Wrap Counter** (інверсія біта обгортання).

Кожен дескриптор містить у полі `flags` два біти:
- `VIRTQ_PACKED_DESC_F_AVAIL` (біт 7, маска `0x80`)
- `VIRTQ_PACKED_DESC_F_USED` (біт 15, маска `0x8000`)

При ініціалізації драйвер і пристрій встановлюють власні лічильники обгортання:

```
driver_wrap_counter = 1
device_wrap_counter = 1
```

Коли драйвер записує дескриптор у позицію `idx`, він виставляє біти прапорців за правилом:

```
flags.AVAIL = driver_wrap_counter
flags.USED  = 1 - driver_wrap_counter
```

При досягненні кінця масиву (`idx == N - 1`) драйвер виконує інверсію лічильника:

```
idx = 0
driver_wrap_counter = 1 - driver_wrap_counter
```

Умова доступності дескриптора для пристрою:

```
is_available = (flags.AVAIL == device_wrap_counter) && (flags.USED != device_wrap_counter)
```

Після обробки запиту пристрій повертає дескриптор гостю, оновлюючи прапорець `USED`:

```
flags.AVAIL = device_wrap_counter
flags.USED  = device_wrap_counter
```

Драйвер вважає дескриптор обробленим, коли бачить, що `flags.AVAIL == flags.USED == driver_wrap_counter`.

Ця математична схема інверсії біта дозволяє повністю відмовитися від модифікації додаткових структур у пам'яті, зберігаючи локальність кеш-ліній (Cache Locality) та забезпечуючи максимальну продуктивність вводу/виводу.
