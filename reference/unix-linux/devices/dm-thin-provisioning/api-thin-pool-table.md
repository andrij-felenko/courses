# 📋 Поверхня тонкого пулу: рядки таблиці, повідомлення, стан

Усе, чим із тонким пулом розмовляють ззовні, вміщається у три речі: **рядок таблиці**, яким його збирають, **повідомлення**, якими створюють і нищать томи, і **рядок стану**, який пул віддає у відповідь. Далі — кожне поле з одиницею виміру, дозволеними значеннями й наслідком зміни; наприкінці — ті самі дії мовою LVM і засоби, які працюють із метаданими тоді, коли сам пул уже не працює.

Усі приклади — на `dmsetup` ([device mapper](book:unix-linux/device-mapper): пристрій описують таблицею «діапазон адрес → ціль із параметрами», а таблицю завантажують у ядро звичайним текстовим рядком).

## Рядок таблиці: `thin-pool`

```
<start> <length> thin-pool <metadata_dev> <data_dev> \
        <data_block_size> <low_water_mark> \
        [<feature_args_count> [<feature_arg>]*]
```

| Поле | Одиниця | Що задає |
|---|---|---|
| `start` | сектори | завжди `0`: пул — одна ціль на весь пристрій |
| `length` | сектори | скільки місця пул уважає своїм; не більше за пристрій даних |
| `metadata_dev` | — | окремий носій метаданих. Блок метаданих завжди 4 КіБ, стеля пристрою — 16 ГіБ |
| `data_dev` | — | носій, з якого видають блоки |
| `data_block_size` | **сектори** | від 128 (64 КіБ) до 2 097 152 (1 ГіБ), кратно 128. **Після створення не міняється ніколи** |
| `low_water_mark` | **блоки** | щойно вільних блоків даних стане менше — ядро видасть подію нагору |
| `feature_args_count` | — | скільки ознак іде далі; групу можна опустити цілком |

Одиниці різні навмисно, і саме на цьому найлегше помилитися: довжина цілі — у секторах, розмір блока — теж у секторах, а поріг тривоги — у блоках, і кожен рядок стану потім теж рахує блоками.

**Пул на 100 ГіБ із блоком 512 КіБ і тривогою на 80% заповнення.**

```
length         = 100 ГіБ / 512 Б        = 209 715 200 секторів
data_block_size = 512 КіБ / 512 Б       = 1024 сектори
усього блоків   = 209 715 200 / 1024    = 204 800
low_water_mark  = 204 800 · (1 − 0.80)  = 40 960 блоків
```

```
dmsetup create pool --table \
  "0 209715200 thin-pool /dev/vg/pmeta /dev/vg/pdata 1024 40960 1 skip_block_zeroing"
```

Перезавантаженням таблиці (`dmsetup reload` + `resume`) можна збільшити `length`, посунути `low_water_mark` і перемкнути будь-яку ознаку. Не можна одне: `data_block_size`. Це число вросло в кожне відображення на носії метаданих, і змінити його — те саме, що переформатувати пул.

## Ознаки-можливості

| Ознака | Що вимикає або вмикає | Чим платять |
|---|---|---|
| `skip_block_zeroing` | не занулювати щойно виданий блок перед першим записом | нова адреса покаже сміття попереднього пожильця — витік даних між томами |
| `ignore_discard` | не приймати [discard](book:unix-linux/discard-and-trim) взагалі (окремий запит блокового рівня «цей діапазон більше не потрібен») | місце не повертається в пул ніколи |
| `no_discard_passdown` | відображення знімати, але вниз на носій запит не переказувати | пул знає, що блок вільний, SSD — ні |
| `read_only` | жодних змін метаданих | ні нових блоків, ні знімків; режим для огляду й порятунку |
| `error_if_no_space` | на брак місця відповідати помилкою одразу, а не ставити запит у чергу | верхні шари дізнаються правду негайно — і мусять уміти її пережити |

## Рядок таблиці: `thin`

```
<start> <length> thin <pool_dev> <dev_id> [<external_origin_dev>]
```

| Поле | Одиниця | Що задає |
|---|---|---|
| `length` | сектори | **оголошений** розмір тому; може багаторазово перевищувати пул |
| `pool_dev` | — | пул, у якого том бере блоки |
| `dev_id` | число | номер тому **всередині метаданих пулу**, той самий, що в повідомленні `create_thin` |
| `external_origin_dev` | — | необов'язковий: читання з ще не виділених адрес підуть на цей пристрій, а не повернуть нулі |

Зовнішній первень робить із будь-якого готового пристрою основу для тонких копій: сотня томів однакового початкового вмісту не займає в пулі нічого, поки в них не почнуть писати.

## Повідомлення пулу

Надсилають їх на **пул**, а не на том, і завжди в сектор `0`:

```
dmsetup message <пул> 0 <повідомлення>
```

| Повідомлення | Дія |
|---|---|
| `create_thin <dev_id>` | завести в метаданих новий порожній том із таким номером |
| `create_snap <dev_id> <origin_id>` | завести том `dev_id` як знімок тому `origin_id` |
| `delete <dev_id>` | прибрати том із метаданих і зменшити лічильники посилань на його блоки |
| `set_transaction_id <поточний> <новий>` | переставити лічильник, яким менеджер томів звіряє свої метадані з метаданими пулу; спрацює лише якщо «поточний» справді збігся |
| `reserve_metadata_snap` | притримати копію дерева відображень для читання ззовні |
| `release_metadata_snap` | відпустити її |

Три правила, без яких ці рядки дадуть не те, на що розраховували. Перед `create_snap` том-первень треба **призупинити** (`dmsetup suspend`), інакше в знімок потрапить недописане, і він буде пошкоджений. `delete` чіпає лише метадані — сам пристрій `/dev/mapper/…` перед цим має бути прибраний `dmsetup remove`. А притриманий корінь у пулу може бути тільки один, і поки його не відпустили, він тримає в метаданих усі старі вузли — забутий `reserve_metadata_snap` тихо з'їдає той бак, який найтісніший.

> 🔧 **Навіщо це.** Метаданий знімок — це не зручність, а єдиний законний спосіб подивитися на пул під навантаженням. Засоби огляду читають носій метаданих як файл, а живий пул переписує його щосекунди, тож без притриманого кореня вони побачили б напівзмінене дерево. Звідси й розподіл праці: `reserve_metadata_snap` віддає незмінну копію, номер якої з'являється в рядку стану, засіб читає саме її з ключем `--metadata-snap`, а `release_metadata_snap` повертає ті блоки в обіг.

## Рядок стану, поле за полем

```
<transaction id> <used metadata blocks>/<total metadata blocks> \
<used data blocks>/<total data blocks> <held metadata root> \
ro|rw|out_of_data_space [no_]discard_passdown \
[error|queue]_if_no_space needs_check|- metadata_low_watermark
```

```
# dmsetup status pool
0 209715200 thin-pool 3 1046/262144 18944/204800 - rw discard_passdown queue_if_no_space - 1024
```

| Поле | У прикладі | Як читати |
|---|---|---|
| transaction id | `3` | 64-бітний лічильник для звірки з метаданими менеджера томів |
| метадані | `1046/262144` | блоками по 4 КіБ: зайнято 4.1 МіБ із 1 ГіБ |
| дані | `18944/204800` | блоками по `data_block_size`: 9.25 ГіБ із 100 ГіБ |
| held metadata root | `-` | `-` — притриманого кореня немає; інакше його номер у блоках |
| режим | `rw` | `ro` — метадані лише для читання після збою; `out_of_data_space` — блоки даних скінчилися |
| discard | `discard_passdown` | чи справді запити переказуються вниз (а не лише те, що це просили в таблиці) |
| брак місця | `queue_if_no_space` | черга чи негайна помилка |
| `needs_check` | `-` | стоїть, коли операція над метаданими зазнала невдачі; поки не знято — пул неповноцінний |
| metadata_low_watermark | `1024` | поріг тривоги по метаданих у блоках. У таблиці його не задають: ядро бере `min(1024, чверть пристрою метаданих)`, тобто не більше за 4 МіБ запасу |

Тонкий том звітує коротше — `<nr mapped sectors> <highest mapped sector>`:

```
# dmsetup status thin0
0 419430400 thin 15360000 104857599
```

Оголошено 200 ГіБ, справді відображено 7.3 ГіБ, а найдальша торкана адреса — на позначці 50 ГіБ. Якщо ж замість полів обидві цілі друкують `Fail`, метадані вже недосяжні, і читати треба не стан, а носій.

## `no_space_timeout`

Скільки пул тримає запити в черзі, перш ніж почне відмовляти, задає [параметр модуля](book:unix-linux/kernel-modules) `dm-thin-pool` (значення, яке модуль приймає при завантаженні й показує окремим файлом у `/sys/module/`):

```
# cat /sys/module/dm_thin_pool/parameters/no_space_timeout
60
# echo 0 > /sys/module/dm_thin_pool/parameters/no_space_timeout   # чекати вічно
```

Типово 60 секунд. Нуль вимикає відлік: запити висітимуть, поки пул не розширять — жодних помилок нагору, але й жодного руху.

## Те саме мовою LVM

[LVM](book:unix-linux/lvm-and-snapshots) складає ті самі рядки сам, лише називає речі інакше: те, що в ядрі `data_block_size`, тут **chunk**.

| Дія | Команда |
|---|---|
| створити пул | `lvcreate --type thin-pool -L 100G --chunksize 512k -n pool vg` |
| зібрати пул із готових томів | `lvconvert --type thin-pool --poolmetadata vg/meta vg/data` |
| створити тонкий том | `lvcreate -V 200G --thinpool vg/pool -n thin0 vg` |
| знімок | `lvcreate -s vg/thin0 -n snap0` |
| дивитися заповнення | `lvs -o lv_name,lv_size,data_percent,metadata_percent vg` |
| розширити дані / метадані | `lvextend -L +50G vg/pool` · `lvextend --poolmetadatasize +512M vg/pool` |
| полагодити | `lvconvert --repair vg/pool` |
| увімкнути нагляд | `lvchange --monitor y vg/pool` |

У `lvs` те саме `Data%` означає різні речі: у пулу — його заповнення, у тонкого тому — скільки з оголошеного розміру справді відображено. `Meta%` є лише в пулу.

| Налаштування `lvm.conf` | Типово | У що перетворюється |
|---|---|---|
| `allocation/thin_pool_chunk_size` | не задано | `data_block_size` |
| `allocation/thin_pool_chunk_size_policy` | `generic` | від якого числа рахувати: `generic` — від 64 КіБ, `performance` — від 512 КіБ |
| `allocation/thin_pool_zero` | `1` | `0` дає ознаку `skip_block_zeroing` |
| `allocation/thin_pool_discards` | `passdown` | `nopassdown` → `no_discard_passdown`, `ignore` → `ignore_discard` |
| `activation/thin_pool_autoextend_threshold` | `100` | відсоток, на якому `dmeventd` розширює пул; `100` означає «не розширювати» |
| `activation/thin_pool_autoextend_percent` | `20` | на скільки відсотків розширювати |

Автопоширення живе не в ядрі: подію по `low_water_mark` ловить `dmeventd`, і лише за ним іде `lvextend --use-policies`. Том без нагляду подію теж видасть — тільки слухати її буде нікому.

## Засоби для метаданих

Окремий пакет `device-mapper-persistent-data`. Усі його команди беруть **пристрій метаданих**, а не пул, і всі вимагають, щоб пул був неактивний — або щоб їм дали `--metadata-snap`.

| Засіб | Синопсис | Для чого |
|---|---|---|
| `thin_check` | `thin_check [опції] {пристрій}` | перевірити цілість. `--super-block-only` — лише суперблок; `--skip-mappings` — без основної маси відображень; `--auto-repair` — полагодити дрібне; `--clear-needs-check-flag` — зняти позначку (не зніметься, якщо перевірка провалилась) |
| `thin_repair` | `thin_repair -i <вхід> -o <вихід>` | зібрати вцілілі метадані **в інший** пристрій; на місці не лагодить |
| `thin_dump` | `thin_dump [опції] {пристрій}` | вивалити метадані в XML — для огляду й для резервної копії |
| `thin_restore` | `thin_restore -i <файл> -o <пристрій>` | зворотна дія до `thin_dump` |
| `thin_ls` | `thin_ls [опції] {пристрій}` | таблиця по томах: `MAPPED_BLOCKS`, `EXCLUSIVE_BLOCKS`, `SHARED_BLOCKS`, `TRANSACTION`, `CREATE_TIME`, `SNAP_TIME` — саме тут видно, скільки місця тримає конкретний знімок і скільки належить томові одноосібно |
| `thin_delta` | `thin_delta --thin1 <id> --thin2 <id> {пристрій}` | різниця відображень двох томів: що змінилося між знімком і теперішнім станом |
| `thin_rmap` | `thin_rmap [опції] {пристрій}` | зворотний перегляд: якому томові належить заданий блок даних |
| `thin_metadata_size` | `thin_metadata_size -b 512k -s 100g -m 200` | порахувати потрібний розмір метаданих наперед, замість `48 · розмір_пулу / розмір_блока` на папері |

`thin_ls` і `thin_delta` — саме ті, що потребують `--metadata-snap`, коли пул працює. Без цього ключа вони або відмовляться читати живі метадані, або прочитають дерево посеред зміни.
