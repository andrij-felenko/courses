# 📜 Історія балонінгу: від патенту VMware ESX до Free Page Reporting

У грудні 2002 року на конференції USENIX OSDI Карл Вальдшпурґер (Carl Waldspurger) представив статтю «Memory Resource Management in VMware ESX Server». У ній було вперше сформульовано фундаментальну проблему віртуалізації пам'яті: гіпервізор виділяє гостьовій системі фіксований обсяг оперативної пам'яті, проте реальне навантаження всередині віртуальної машини постійно коливається.

```
+-----------------------------------------------------------------------------+
| 2002  VMware ESX Server 1.5: Карл Вальдшпурґер формулює концепцію балона    |
| 2008  Linux 2.6.25: Расті Рассел стандартизує virtio-balloon у ядрі         |
| 2013  OASIS Virtio 1.0: розширення statsq, deflate_on_oom та 64-біт PFN     |
| 2018  Free Page Hinting: оптимізація живої міграції (Вей Ванг, QEMU/Linux)  |
| 2020  Linux 5.7: Александер Дуйк впроваджує Free Page Reporting у MM       |
+-----------------------------------------------------------------------------+
```

## Семантичний розрив і трагедія подвійного свопінгу

На початку 2000-х років гіпервізори першого покоління стикалися з дилемою розподілу ресурсів (англ. *resource allocation*). Якщо фізичний сервер мав 64 ГБ оперативної пам'яті, а адміністратор запускав вісім віртуальних машин по 8 ГБ, сумарний ліміт вичерпувався повністю. При цьому більшість гостьових ОС реально використовували лише 2–3 ГБ, а решта пам'яті залишалася незадіяною або займалася кешем диска.

Спроби гіпервізора примусово витісняти пам'ять віртуальної машини у власний файл підкачування (англ. *host-level swapping*) призводили до катастрофічної деградації продуктивності. Гіпервізор не міг знати, які сторінки всередині гостя є критично важливими (структури ядра, таблиці процесів, гарячі буфери баз даних), а які — порожніми. У результаті гіпервізор міг скинути на повільний диск сторінку, що містила планувальник гостьової ОС, викликаючи зависання всієї віртуальної машини.

Гостьова ОС також намагалася витісняти свої сторінки на віртуальний диск, створюючи явище «подвійного свопінгу» (англ. *double paging*). Замість одного дискового запису система виконувала два каскадних читання й записи через повільні емульовані контролери IDE та SCSI.

```
Затримка звернення = T_гостя(виділення) + T_хоста(swapping) + T_гостя(swapping)
```

Вальдшпурґер запропонував елегантне розв'язання семантичного розриву (англ. *semantic gap*): помістити всередину гостьової системи спеціальний паравіртуалізований псевдодрайвер (англ. *balloon driver*). Драйвер не мав жодного фізичного обладнання, але реєструвався в ядрі гостя як звичайний споживач пам'яті. Коли гіпервізору була потрібна фізична пам'ять, він наказував драйверу «надутися» (англ. *inflate*). Драйвер виділяв сторінки через штатний розподілювач ядра гостя, позбавляючи пам'яті інші гостьові процеси, і передавав фізичні адреси цих сторінок гіпервізору. Отримавши адреси, гіпервізор безпечно вилучав фізичну пам'ять у хоста.

## Стандартизація virtio-balloon у Linux

З появою відкритого стандарту paravirtualized I/O virtio, розробленого Расті Расселом (Rusty Russell), механізм балонінгу отримав єдину специфікацію для екосистеми KVM і QEMU. У ядрі Linux 2.6.25 (квітень 2008 року) дебютував драйвер `virtio_balloon.c`.

У першій версії специфікації протокол спирався на дві віртуальні черги (англ. *virtqueues*):
1. `inflateq` — черга, в яку драйвер гостя складав масиви 32-бітних номерів сторінкових кадрів (англ. *Page Frame Numbers, PFN*) розміром 4 КіБ для блокування пам'яті;
2. `deflateq` — черга, через яку драйвер гостя повідомляв хост про вивільнення сторінок і повернення їх гостьовій системі.

Ця схема працювала бездоганно на невеликих віртуальних машинах, але з ростом обсягів пам'яті до сотень гігабайтів виявила серйозні обмеження.

**Проблема 32-бітного PFN.** Традиційний протокол передавав номери кадрів у 32-бітному цілому числі (`__virtio32`). При базовому розмірі сторінки 4 КіБ це встановлювало жорстку стелю адресації:

```
Максимальний обсяг RAM = 2³² · 4 КіБ
                       = 4 294 967 296 · 4096 байтів [множення розрядності на розмір сторінки]
                       = 17 592 186 044 416 байтів   [переведення в байти]
                       = 16 ТіБ                      [максимальний простір GPA]
```

Для суперкомп'ютерних віртуальних машин розміром понад 16 ТіБ 32-бітний масив PFN переповнювався, викликаючи спотворення фізичних адрес.

**Накладні витрати на цикли PFN.** Для надування балона на 64 ГБ гостьовий драйвер мусив виділити 16 777 216 окремих 4 КіБ сторінок, розбити їх на пакети по 256 елементів і виконати понад 65 000 перемикань контексту (англ. *VM-exit*) між гостем і гіпервізором. Процес забивав віртуальні процесори на кілька секунд і руйнував великі 2 МіБ сторінки (англ. *Transparent HugePages*) усередині хоста.

## Поява Free Page Hinting та Free Page Reporting

У 2018–2020 роках спільнота розробників ядра Linux та QEMU (зокрема Вей Ванг з Intel та Александер Дуйк з Red Hat) кардинально переглянула архітектуру балонінгу, створивши два незалежні механізми наступного покоління.

```
ХРОНОЛОГІЯ ЕВОЛЮЦІЇ МЕХАНІЗМІВ ВИВІЛЬНЕННЯ ПАМ'ЯТІ:

Класичний балонінг (2008):
[alloc_pages(order 0)] ──> [масив 32-біт PFN] ──> [inflateq] ──> [madvise DONTNEED]
* Мінуси: фрагментація, високий vCPU, посторінковий цикл

Free Page Hinting (2018):
[Оптимізація Live Migration] ──> [Сканування Buddy Free Lists] ──> [Пропуск чистих сторінок]
* Зменшує час міграції ВМ через мережу на 60–80%

Free Page Reporting (2020):
[Buddy Allocator Hook] ──> [Блоки MAX_ORDER-1 (2 МБ)] ──> [Scatter-Gather] ──> [madvise]
* Плюси: нульове навантаження на процесор, збереження HugeTLB, пакетна передача
```

**Free Page Hinting (`VIRTIO_BALLOON_F_FREE_PAGE_HINT`).** Механізм створено спеціально для оптимізації живої міграції віртуальних машин (англ. *live migration*). Під час перенесення пам'яті ВМ через мережу гіпервізор передає всі сторінки, навіть якщо вони порожні. Free Page Hinting дозволяє гіпервізору запитати в гостя список вільних сторінок безпосередньо перед міграцією. Гість надає зріз списків вільної пам'яті, і QEMU пропускає передачу гігабайтів нулів, прискорюючи перенесення в рази.

**Free Page Reporting (`VIRTIO_BALLOON_F_REPORTING`).** Запропонований Александером Дуйком і прийнятий у ядро Linux 5.7 (червень 2020 року), цей підхід усунув необхідність у поштучному виділенні сторінок драйвером. Замість того щоб драйвер штучно захоплював пам'ять, підсистема керування пам'яттю ядра (англ. *Memory Management, MM*) отримала вбудований інтерфейс `page_reporting_register()`.

Коли гостьовий розподілювач buddy allocator об'єднує сторінки у великі неперервні блоки (наприклад, порядку `MAX_ORDER - 1`, що відповідає 2 МіБ на архітектурі x86_64), фоновий потік автоматично передає гіпервізору діапазон адрес через дескриптори scatter-gather. Гіпервізор скидає відповідний EPT-мапінг викликом `madvise(MADV_DONTNEED)`, а сторінки залишаються вільними всередині гостя.

Завдяки цьому балонінг еволюціонував від повільного посторінкового «перетягування канату» до прозорого та асинхронного повернення невикористаної пам'яті на рівні цілих сторінкових блоків.
