# Підсистема прискорювачів DRM Accel (/dev/accel/accelX для NPU та AI-чіпів)

Підсистема **DRM Accel** (Accelerator Framework), представлена у ядрі Linux починаючи з версії 6.3, є спеціалізованою гілкою в межах загальної архітектури Direct Rendering Manager (DRM). Вона була створена з єдиною метою: надати стандартизований, безпечний та ефективний інтерфейс для управління обчислювальними прискорювачами (Accelerators) — такими як NPU (Neural Processing Units), TPU (Tensor Processing Units) та іншими спеціалізованими ШІ-чіпами, які не мають жодного стосунку до виведення графіки на дисплей. 

У цій статті ми детально розглянемо передумови створення DRM Accel, його архітектуру, відмінності від класичного графічного стека DRM, а також механізми взаємодії простору користувача з апаратними прискорювачами через вузли `/dev/accel/accelX`.

## 1. Передумови виникнення: Чому не класичний DRM?

Історично підсистема **Direct Rendering Manager (DRM)** створювалася для управління відеокартами (GPU) у Linux. З роками DRM обріс потужними механізмами для управління пам'яттю (GEM — Graphics Execution Manager), синхронізації (через `dma_fence`) та шедулінгу команд. Коли на ринку почали масово з'являтися спеціалізовані прискорювачі для машинного навчання (наприклад, Habana Labs Gaudi або Intel VPU/NPU), розробники драйверів опинилися перед вибором: як інтегрувати ці пристрої в ядро?

Спершу багато драйверів писалися як прості символьні пристрої (character devices) у каталозі `drivers/misc` або `drivers/char`. Проте, обчислювальні прискорювачі потребували складного управління пам'яттю, поділу ресурсів між багатьма процесами, чергування завдань і синхронізації — усього того, що *вже було реалізовано* в DRM. 

Отже, розробники почали писати драйвери для NPU на базі DRM, використовуючи його як обчислювальний фреймворк. Такі драйвери створювали вузли `/dev/dri/renderD128`, що зазвичай використовуються для рендерингу GPU без дисплейного виводу (headless render nodes). Однак це породило концептуальну і практичну проблему:

1. **Забруднення простору імен та API:** Фреймворки користувача (як-от Mesa або Vulkan) автоматично сканують `/dev/dri/renderD*`, намагаючись знайти графічний процесор. Коли вони знаходили NPU, драйвер якого працював на базі DRM, відбувалися збої, адже NPU не підтримує ні OpenGL, ні Vulkan, ні KMS (Kernel Mode Setting).
2. **Зайвий дисплейний багаж:** Графічний стек DRM обтяжений логікою для роботи з моніторами, форматами пікселів, розгортками (vblank) та кадровими буферами. Для NPU цей код є абсолютно непотрібним і лише збільшує поверхню атаки та споживання пам'яті.

Щоб вирішити цю проблему, розробники ядра (зокрема Орідед Зігман з Habana Labs, а пізніше інженери з Intel, AMD та Red Hat) ініціювали виокремлення обчислювальної частини DRM у нову підсистему — **DRM Accel**.

## 2. Що таке DRM Accel?

**DRM Accel** — це, по суті, обрізана версія DRM, позбавлена будь-яких графічних або дисплейних API (таких як KMS — Kernel Mode Setting, Dumb Buffers, legacy modesetting тощо). Вона використовує той самий перевірений часом код для управління пам'яттю (GEM), ті самі примітиви синхронізації (DMA-BUF та `dma_fence`), а також загальний шедулер DRM (`drm_sched`).

Головна відмінність полягає в тому, як ці пристрої реєструються в системі:
- Замість створення вузлів `/dev/dri/cardX` та `/dev/dri/renderDX`, підсистема створює вузли **/dev/accel/accelX** (де `X` — це номер пристрою, починаючи з 0).
- Замість реєстрації у класі sysfs `drm`, пристрої реєструються у новому класі **/sys/class/accel**.
- Усі IOCTL (Input/Output Control) виклики, специфічні для дисплеїв, заблоковані на рівні фреймворку. Драйвери прискорювачів можуть реалізовувати лише свої унікальні IOCTL для управління виконанням команд та GEM.

## 3. Внутрішня архітектура та взаємодія

Архітектура підсистеми DRM Accel поділяється на кілька ключових рівнів.

### 3.1 Простір ядра (Kernel Space)

У ядрі Linux DRM Accel представлений ядром DRM (DRM core), яке надає інфраструктуру. Коли розробник пише драйвер для NPU (Kernel Mode Driver, KMD), він заповнює структуру `drm_driver`, вказуючи прапорець `DRIVER_COMPUTE_ACCEL`. 

Ось як це виглядає на рівні коду (спрощено):

```c
static const struct drm_driver my_npu_driver = {
    .driver_features = DRIVER_COMPUTE_ACCEL | DRIVER_GEM,
    .name = "my_npu",
    .desc = "My AI Accelerator",
    .major = 1,
    .minor = 0,
    .fops = &my_npu_fops,
    .ioctls = my_npu_ioctls,
    // ... специфічні колбеки для управління пам'яттю
};
```

Прапорець `DRIVER_COMPUTE_ACCEL` вказує ядру DRM, що цей пристрій не повинен реєструватися як графіка. Ядро автоматично створює для нього major-номер `261` (за замовчуванням для accel) та відповідні minor-номери. 

Драйвер обробляє два основних типи завдань:
1. **Управління пам'яттю (GEM):** Виділення буферів пам'яті (як локальної пам'яті NPU, так і системної пам'яті RAM) та їх картографування у простір користувача.
2. **Подання команд (Command Submission, CS):** Отримання пакетів інструкцій від користувача, їх перевірка, планування через `drm_sched` та відправлення на апаратні черги прискорювача.

### 3.2 Простір користувача (User Space)

У просторі користувача працюють високорівневі фреймворки (наприклад, TensorFlow, PyTorch, OpenVINO, або ONNX Runtime). Ці фреймворки зазвичай не спілкуються безпосередньо з ядром. Вони використовують **User Mode Driver (UMD)** — бібліотеку простору користувача, написану виробником апаратного забезпечення.

UMD відкриває файл `/dev/accel/accelX` за допомогою системного виклику `open()` і взаємодіє з драйвером ядра через спеціалізовані IOCTL виклики. Оскільки DRM Accel є частиною сімейства DRM, багато драйверів також використовують загальносистемну бібліотеку `libdrm`, хоча це не є строго обов'язковим. `libdrm` допомагає стандартизувати виклики для роботи з GEM та обробку помилок.

Процес типового циклу інференсу або навчання виглядає так:
1. UMD відкриває `/dev/accel/accelX`.
2. UMD виділяє пам'ять під ваги моделі (weights) та вхідні тензори через GEM IOCTL.
3. Дані копіюються або мапляться в цю пам'ять.
4. UMD формує чергу команд (Command Buffer) зі специфічними для NPU машинними інструкціями (матричні множення, згортки тощо).
5. UMD відправляє Command Buffer у ядро через CS (Command Submission) IOCTL.
6. Ядро ставить завдання у чергу (`drm_sched`) і повідомляє апаратне забезпечення.
7. Простір користувача чекає завершення виконання за допомогою об'єкта `dma_fence` (зазвичай через виклики `poll` або специфічні IOCTL очікування).

## 4. Інтерфейси: Вузли пристроїв та sysfs

### 4.1 Вузол /dev/accel/accelX
Як згадувалося раніше, кожен прискорювач експортується як символьний пристрій `/dev/accel/accelX`.
Додатки простору користувача можуть відкрити цей файл у режимі читання/запису. Важливою особливістю DRM Accel є те, що, на відміну від старих `/dev/dri/cardX`, тут **немає концепції DRM-майстра (DRM Master)**. Концепція DRM Master (де лише один процес міг контролювати дисплейні виходи) абсолютно недоречна для обчислювальних пристроїв, які від самого початку проектуються для безпечного паралельного використання багатьма процесами. Кожен клієнт, що відкриває `/dev/accel/accelX`, отримує власний ізольований контекст.

### 4.2 Інтерфейс sysfs
У каталозі `/sys/class/accel/` міститься інформація про всі підключені прискорювачі. Структура каталогів подібна до класичного DRM, але значно чистіша:

```bash
$ ls /sys/class/accel/
accel0  accel1
$ ls /sys/class/accel/accel0/
device  power  subsystem  uevent
```
Кожен каталог пристрою містить символічні посилання на фізичний пристрій (наприклад, на шині PCIe або Platform Bus). Драйвери можуть розширювати цей каталог, додаючи файли для експорту специфічної інформації: температури, споживання енергії, відсотка завантаження NPU або інформації про прошивку (firmware).

## 5. Робота з пам'яттю: GEM та DMA-BUF

Підсистема DRM Accel повністю інтегрована з інфраструктурою DMA-BUF. Це має критичне значення для сучасних гетерогенних обчислень.

**DMA-BUF** (Direct Memory Access Buffer) — це механізм ядра Linux для безкопійного обміну буферами пам'яті між різними драйверами та пристроями. Завдяки тому, що DRM Accel підтримує DMA-BUF, стає можливим наступний сценарій:
1. NPU (через `/dev/accel/accel0`) обчислює тензор, результат якого зберігається в локальній пам'яті NPU.
2. Цей буфер експортується як дескриптор файлу (file descriptor) DMA-BUF.
3. Цей дескриптор передається драйверу дисплея (GPU через `/dev/dri/renderD128`) або драйверу захоплення відео (V4L2 через `/dev/video0`).
4. Інший пристрій може напряму зчитати результати з пам'яті NPU за допомогою DMA, без потреби копіювати дані через центральний процесор (CPU).

Об'єкти GEM (Graphics Execution Manager) всередині DRM Accel використовуються для управління життєвим циклом цієї пам'яті, її картографування в mmap та управління кешуванням сторінок пам'яті.

## 6. Синхронізація: dma_fence

Обчислювальні прискорювачі працюють асинхронно відносно CPU. Коли UMD відправляє набір інструкцій у ядро, системний виклик повертається майже миттєво. Щоб простір користувача міг дізнатися, коли апаратний прискорювач завершив обчислення, використовується механізм `dma_fence`.

Ядро генерує об'єкт `dma_fence` для кожної відправленої команди. Цей fence (паркан/бар'єр) може бути експортований у простір користувача як `sync_file` (спеціальний дескриптор файлу). Простір користувача може використовувати стандартні виклики `poll()`, `select()` або `epoll()`, щоб дочекатися зміни стану цього дескриптора. 

Більше того, оскільки GPU, V4L2 та DRM Accel використовують спільну інфраструктуру `dma_fence`, можна побудувати конвеєр на рівні апаратного забезпечення:
- NPU дається команда: "Виконай цю нейромережу, але **чекай**, поки GPU не просигналізує ось цей `dma_fence`".
- GPU виконує попередню обробку зображення і сигналізує fence.
- NPU автоматично починає роботу.
Уся ця синхронізація відбувається без активної участі CPU, що мінімізує затримки та споживання енергії.

## 7. Підтримувані апаратні прискорювачі

На момент створення та активного розвитку (Linux 6.3 та пізніші версії), у DRM Accel почали мігрувати або одразу розроблятися наступні драйвери:

1. **Habana Labs (Intel):** Драйвер `habanalabs` був одним із перших, хто ініціював дискусію про DRM Accel. Чіпи Goya (inference) та Gaudi (training) використовують цей фреймворк. Спочатку драйвер існував у `drivers/misc/habanalabs`, але згодом був адаптований до нових стандартів Accel як драйвер `accel/habanalabs`.
2. **Intel VPU (Versatile Processing Unit) / NPU:** Драйвер `ivpu` підтримує інтегровані ШІ-прискорювачі, що входять до складу процесорів Intel Meteor Lake та пізніших архітектур. Ці модулі оптимізовані для локального виконання моделей (Client AI) з низьким енергоспоживанням. Драйвер `ivpu` є одним із канонічних зразків правильного використання підсистеми DRM Accel.
3. **QAIC (Qualcomm AI 100):** Драйвер для прискорювачів Qualcomm Cloud AI 100.
4. Розробляються та очікуються драйвери для рішень від AMD (наприклад, інтегровані XDNA NPU) та інших постачальників кремнію для ШІ.

## 8. Порівняння підходів: DRM Accel vs. GPGPU

Варто розуміти різницю між обчисленнями на NPU через DRM Accel та обчисленнями на GPU (GPGPU) через класичні API типу Vulkan Compute, OpenCL або CUDA.

- **GPU (Graphics Processing Unit):** Керується через `/dev/dri/renderDX` (класичний DRM). Пристрій багатоцільовий. У просторі користувача працює повноцінний графічний драйвер (наприклад, Mesa). На GPU можна виконувати як шейдери для рендерингу графіки, так і обчислювальні (Compute) шейдери для машинного навчання.
- **NPU (Neural Processing Unit):** Керується через `/dev/accel/accelX` (DRM Accel). Пристрій вузькоспеціалізований. У ньому немає конвеєра растеризації, текстурних блоків чи дисплейних контролерів. Його апаратна архітектура зазвичай складається з масивних матричних помножувачів (Systolic Arrays) та спеціальних векторних ядер. API драйвера оптимізовано виключно під передачу тензорів і графів обчислень.

## 9. Утиліти простору користувача та діагностика

Оскільки підсистема є частиною ширшого сімейства DRM, багато наявних інструментів для діагностики GPU можуть бути або вже адаптовані для роботи з `/dev/accel`. 
Програмісти та системні адміністратори можуть використовувати:
- `lsof /dev/accel/accel*` — щоб перевірити, які процеси зараз утримують прискорювач.
- `cat /sys/class/accel/accel0/device/...` — для зчитування сирих телеметричних даних.
- Спеціалізовані утиліти виробників (наприклад, `hl-smi` для Habana Labs, подібно до `nvidia-smi`), які збирають дані з sysfs та IOCTL для показу статистики використання NPU у реальному часі.

## 10. Перспективи розвитку та висновок

Впровадження підсистеми DRM Accel у Linux 6.3 стало важливим архітектурним кроком. Воно завершило епоху "дикого Заходу", коли кожен виробник AI-чіпів писав свій власний, ні з чим не сумісний фреймворк у `drivers/char`. Завдяки DRM Accel індустрія отримала стандартизований спосіб:
- Виділення пам'яті (GEM)
- Синхронізації (dma_fence, DMA-BUF)
- Планування завдань на апаратному рівні

Це значно спрощує розробку відкритих екосистем для машинного навчання (наприклад, у межах проекту Mesa, який вже розширюється за межі чистої графіки). Відмежування від дисплейного коду зробило ядро безпечнішим і менш роздутим для серверних ШІ-вузлів, а також для мобільних/десктопних систем із вбудованими NPU.
