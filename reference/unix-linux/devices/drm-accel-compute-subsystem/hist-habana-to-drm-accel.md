# 📜 Історія DRM Accel: від drivers/misc/habanalabs до Linux 6.3

Виокремлення спеціалізованої підсистеми для обчислювальних прискорювачів у ядрі Linux стало наслідком тривалого архітектурного конфлікту між розробниками драйверів ШІ-чіпів та мейнтейнерами графічного стека DRM. 

## 1. Стрімкий розвиток AI-заліза та період «дикого Заходу» (2018–2021)

У період з 2018 по 2021 рік на ринку напівпровідників відбувся вибухоподібний приріст спеціалізованих обчислювальних прискорювачів. Компанії Habana Labs (згодом придбана Intel), Google, Qualcomm, Hailo та Graphcore випустили власні мікросхеми, призначені виключно для прискорення обчислень глибокого навчання (Deep Learning). На відміну від універсальних графічних процесорів (GPU), ці чіпи не мали растрових графічних конвеєрів, шейдерних ядер у класичному розумінні та дисплейних блоків.

У 2019 році компанія Habana Labs запропонувала додати до ядра Linux 5.1 драйвер `habanalabs` для своїх прискорювачів Goya (інференс) та Gaudi (навчання моделей). На той час у ядрі Linux не існувало спеціалізованого підрозділу для чистих обчислювальних чіпів. Оскільки прискорювачі не мали дисплейних виходів, драйвер було вирішено розмістити у каталозі «інших пристроїв» — `drivers/misc/habanalabs`.

Розміщення драйвера складного прискорювача у `drivers/misc` швидко оголило декілька концептуальних та архітектурних проблем:

1. **Дублювання інфраструктури пам'яті:** Драйвер `habanalabs` змушений був з нуля реалізовувати логіку виділення пам'яті, фіксації сторінок у системній RAM (memory pinning), побудови таблиць Scatter-Gather та їх картографування у простір користувача. Усі ці механізми вже понад десятиліття вдосконалювалися в підсистемі DRM у формі менеджера пам'яті GEM (Graphics Execution Manager).
2. **Фрагментація UAPI:** Кожен новий вендор прискорювачів, намагаючись увійти до `drivers/misc`, створював власні унікальні IOCTL-виклики для керування чергами команд, мапування пам'яті та синхронізації. Це унеможливлювало створення уніфікованого користувацького стека для Linux.
3. **Ізоляція від екосистеми DMA-BUF:** Пристрої з `drivers/misc` не мали стандартних механізмів для безкопійного обміну буферами пам'яті (Zero-Copy) з іншими пристроями системи — відеокартами або контролерами відеозахоплення V4L2. Будь-яка передача даних вимагала проміжного копіювання через оперативну пам'ять процесора (CPU RAM).

## 2. Спроба адаптації DRM render nodes та тупик у просторі користувача

Усвідомлюючи переваги інфраструктури DRM, інші розробники (зокрема інженери Intel, що працювали над драйвером VPU/NPU, та Qualcomm зі своїм Cloud AI 100) спробували піти іншим шляхом. Вони почали створювати свої драйвери як стандартні DRM-драйвери, реєструючи пристрої через графічні вузли рендерингу без дисплеїв — `/dev/dri/renderD128`.

На перший погляд це вирішувало проблему: драйвер отримував менеджер пам'яті GEM, підтримку DMA-BUF та асинхронну синхронізацію через `dma_fence`. Проте в просторі користувача це спричинило катастрофічний конфлікт.

Графічні бібліотеки та системні середовища (Mesa, Vulkan loader, X11, Wayland-композитори) під час завантаження автоматично сканують усі вузли `/dev/dri/renderD*`, намагаючись знайти сумісний графічний процесор для 3D-рендерингу. Натрапляючи на вузол NPU/VPU, який реєструвався як DRM-пристрій, але відхиляв усі графічні виклики (KMS) та не мав 3D-конвеєра, графічний стек завершувався з помилкою, або витрачав тривалий час на некорисні спроби ініціалізації.

## 3. Велике обговорення в LKML та народження DRM Accel (2022–2023)

У вересні 2022 року Одед Ґаббай (Oded Gabbay) з Habana Labs та Яні Нікула (Jani Nikula) з Intel ініціювали масштабне обговорення у розсилці Linux Kernel Mailing List (LKML). Вони запропонували створити спеціалізовану підсистему під назвою **DRM Accel**.

Архітектурний спір точився навколо двох варіантів:
- **Варіант A:** Створити абсолютно нову підсистему ядра `subsystem/accel` повністю з нуля.
- **Варіант B:** Використати наявну інфраструктуру DRM core, але відсікти від неї графічний стек KMS та виділити окремий простір імен.

Ключові архітектори ядра Linux — Грег Кроа-Гартман (Greg Kroah-Hartman, мейнтейнер driver core) та Деніел Веттер (Daniel Vetter, мейнтейнер DRM) — підтримали другий варіант. Вони аргументували це тим, що обчислювальні прискорювачі потребують 90% тих самих механізмів ядра, що й графічні процесори у режимі Compute (GEM, DMA-BUF, `dma_fence`, `drm_sched`). Створення нової підсистеми з нуля призвело б до повторного написання тисяч рядків коду управління пам'яттю та синхронізацією.

Було сформовано компромісний план:
1. Підсистема залишається під парасолькою DRM і користується його спільним кодом.
2. Для прискорювачів вводиться новий прапорець ініціалізації драйвера `DRIVER_COMPUTE_ACCEL`.
3. Пристрої реєструються у новому каталозі пристроїв `/dev/accel/accelX` з офіційно виділеним мажорним номером `261`.
4. Створюється окремий клас sysfs `/sys/class/accel/`, ізольований від `/sys/class/drm/`.
5. Усі дисплейні IOCTL підсистеми KMS блокуються на рівні фреймворку DRM Accel.

У березні 2023 року код підсистеми DRM Accel було завершено, і він офіційно увійшов до релізу ядра **Linux 6.3**. Старий драйвер `habanalabs` було перенесено з `drivers/misc/` у новий каталог `drivers/accel/habanalabs/`, а нові драйвери Intel `ivpu` та Qualcomm `qaic` увійшли до ядра вже як канонічні драйвери підсистеми DRM Accel.
