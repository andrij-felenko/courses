Коли одноплатний комп'ютер або вбудована система ініціалізує модуль камери через шину MIPI CSI-2, зчитування кадрів роздільністю 1920×1080 із частотою 60 кадрів/с дає потік «сирих» даних (RAW Bayer) на швидкості понад 1.4 Гбіт/с. Забирати такий потік звичайним читанням `read()` означає, що кожен кадр іще раз копіює центральний процесор у буфер застосунку, а сам буфер знову стає вільним лише після завершення цієї копії: смуга пам'яті витрачається двічі, і кадри, які апаратура віддала тим часом, губляться. Для подолання цього бар'єра ядро Linux об'єднує підсистеми V4L2 (Video for Linux 2) та Media Controller у дворівневу архітектуру, яка відокремлює потокову передачу кадрів через DMA від керування складною апаратною топологією обробки зображень.

Розділення медіа-підсистеми ядра Linux на два рівні відповідає фундаментальній різниці між **потоком відеоданих** (чисті байти пікселів у системній пам'яті DRAM) та **топологією апаратного конвеєра** (як саме ці байти формуються всередині кремнієвого чипа).

## Архітектурний розрив: монолітний V4L2 проти графа Media Controller

Історично підсистема V4L2 створювалася для відносно простих пристроїв — USB-веб-камер та PCI ТВ-тюнерів, де вся апаратура була прихована всередині пристрою («чорна скринька»), а простір користувача бачив лише єдиний символьний пристрій `/dev/video0`. Проте з появою сучасних систем на кристалі (SoC) апаратура камери перетворилася на розподілений конвеєр із багатьох обчислювальних блоків.

![Архітектура підсистеми V4L2 та Media Controller у Linux](/reference/unix-linux/devices/v4l2-media-subsystem/img/v4l2-mc-architecture.svg)
*Архітектурний розподіл функцій між V4L2 та Media Controller у сучасному медіа-конвеєрі Linux.*

Причиною розколу на дві підсистеми стала нездатність класичного V4L2 керувати проміжними апаратними блоками. У сучасній системі обробки зображень відеопотік проходить через серію послідовних або паралельних трансформацій:

1. **Кристал сенсора камери**: Здійснює аналого-цифрове перетворення світла у піксельну матрицю Bayer (RAW8, RAW10, RAW12).
2. **Приймач MIPI CSI-2**: Десеріалізує потік високочастотних пакетів даних та перетворює їх на внутрішню паралельну або пакетну шину.
3. **Апаратний ISP (Image Signal Processor)**: Виконує корекцію рівнів чорного, дебайєризацію (Demosaicing — відновлення повноколірного RGB із матриці байєра), баланс білого, гамма-корекцію, шумозаглушення, кадрування та конвертацію колірного простору у YUV 4:2:0 (наприклад, у розкладку NV12).
4. **Контроллер DMA (Direct Memory Access)**: Записує готовий вектор пікселів у системну оперативну пам'ять (RAM).

У цій дуальній архітектурі підсистеми ядра розділяють сфери відповідальності:

- **V4L2 Framework (`/dev/videoX`)**: Забезпечує високорівневий інтерфейс обміну буферами кадру між ядром та простором користувача. Він відповідає за запит пам'яті, черги буферів (Videobuf2), старт/стоп потоку DMA (`VIDIOC_STREAMON`/`STREAMOFF`) та регулювання стандартних параметрів зображення (яскравість, контраст, насиченість).
- **Media Controller Framework (`/dev/mediaX`)**: Представляє апаратні блоки у вигляді спрямованого графа (Directed Graph). Він дозволяє додаткам виявляти внутрішні блоки (сенсори, CSI-приймачі, ISP, масштабувальники), конфігурувати зв'язки між ними та налаштовувати проміжні формати на майданчиках субпристроїв (`/dev/v4l-subdevX`).

Детальний аналіз того, як еволюціонувала медіа-підсистема від монолітного V4L1 у ядрі 2.1 до графової моделі Media Controller, висвітлено у вставці [історію еволюції медіа-підсистеми Linux](book:unix-linux/v4l2-media-subsystem/hist-v4l1-to-media-controller.md).

> 🔧 **Навіщо це.**
> Без Media Controller розробник вбудованої системи не зміг би підключити два окремі камери-сенсори до одного апаратного ISP або зняти «сирий» RAW-кадр для алгоритмів машинного зору безпосередньо з приймача CSI-2 паралельно з обробкою YUV-відеопотоку для дисплея. Media Controller робить топологію кристала прозорою для конфігурації.

## Анатомія графа Media Controller: Entities, Pads та Links

Фундаментальною абстракцією Media Controller є представлення апаратного комплексу у вигляді трьох типів графових об'єктів:

- **Сутність (Entity, `struct media_entity`)**: Логічний або фізичний блок обробки даних. Прикладами сутностей є сенсор камери (OmniVision OV5640), приймач MIPI CSI-2, апаратний ISP (Image Signal Processor) або вузол захоплення відео `/dev/video0`. Кожна сутність має унікальний ідентифікатор у ядрі та свою функційну категорію (`MEDIA_ENT_F_*`).
- **Майданчик (Pad, `struct media_pad`)**: Точка підключення на межі сутності, через яку проходять дані. Майданчики бувають двох типів:
  - `MEDIA_PAD_FL_SINK` (вхідний майданчик) — приймає потік даних від попередньої сутності;
  - `MEDIA_PAD_FL_SOURCE` (вихідний майданчик) — віддає потік даних наступній сутності.
- **Зв'язок (Link, `struct media_link`)**: Спрямоване з'єднання між вихідним майданчиком однієї сутності (`SOURCE`) та вхідним майданчиком іншої (`SINK`).

![Топологія графа Media Controller](/reference/unix-linux/devices/v4l2-media-subsystem/img/mc-graph-topology.svg)
*Граф сутностей (Entities), майданчиків (Pads) та зв'язків (Links) для обробки відеопотоку CSI-2.*

Зв'язки у графі Media Controller описуються прапорцями стану:

- `MEDIA_LNK_FL_ENABLED`: Зв'язок активований і дані можуть протікати між майданчиками.
- `MEDIA_LNK_FL_IMMUTABLE`: Зв'язок жорстко зафіксований в апаратурі і не може бути вимкнений програмно (наприклад, внутрішнє з'єднання всередині ISP).
- `MEDIA_LNK_FL_DYNAMIC`: Зв'язок може перемикатися «на льоту» під час активного потоку.

Простір користувача отримує доступ до управління цією топологією через системний виклик `ioctl` на пристрої `/dev/media0`. Викликом `MEDIA_IOC_SETUP_LINK` програма може динамічно комутувати медіа-потоки, перенаправляючи сигнал з одного сенсора на інший.

### Системні консольні утиліти керування графом

Для інспектування та налаштування графа у просторі користувача використовуються стандартні утиліти пакета `v4l-utils`:

- `media-ctl -p`: Виводить текстове дерево всіх сутностей графа Media Controller, номери майданчиків, поточні медіа-коди та активні зв'язки.
- `media-ctl -l '"ov5640 1-003c":0 -> "csi":0[1]'`: Активує зв'язок між вихідним майданчиком 0 сенсора `ov5640` та вхідним майданчиком 0 приймача `csi`.
- `v4l2-ctl --list-devices`: Групує наявні в системі медіа-пристрої за драйвером і показує, які символьні вузли `/dev/videoX`, `/dev/v4l-subdevX` і `/dev/mediaX` кожному з них належать.

## Узгодження форматів у конвеєрі (Subdev Format Negotiation)

У класичному V4L2 формат зображення (наприклад, `V4L2_PIX_FMT_NV12` або `V4L2_PIX_FMT_YUYV`) налаштовується безпосередньо на пристрої `/dev/video0` викликом `VIDIOC_S_FMT`. Проте у граф-моделі Media Controller кожен майданчик субпристрою (`/dev/v4l-subdevX`) працює з власною специфікацією форматів медіа-шини (Media Bus Formats, `MEDIA_BUS_FMT_*`).

Причиною цього є те, що формат даних на фізичній шині (наприклад, 10-бітний RAW Bayer `MEDIA_BUS_FMT_SBGGR10_1X10`) фундаментально відрізняється від формату, який ISP записує у системну оперативну пам'ять (упакований YUV420 / NV12).

### Процес узгодження форматів (Format Negotiation)

Конфігурація конвеєра виконується послідовно від джерела (сенсора) до приймача (відеовузла):

1. **Встановлення формату на сенсорі**: На вихідному майданчику сенсора (`/dev/v4l-subdev0`, pad 0) задається роздільна здатність та колірний код шини:
:::tabs
```c
struct v4l2_subdev_format fmt;
memset(&fmt, 0, sizeof(fmt));
fmt.pad = 0;
fmt.which = V4L2_SUBDEV_FORMAT_ACTIVE;
fmt.format.width = 1920;
fmt.format.height = 1080;
fmt.format.code = MEDIA_BUS_FMT_SBGGR10_1X10;
fmt.format.field = V4L2_FIELD_NONE;
ioctl(subdev_fd, VIDIOC_SUBDEV_S_FMT, &fmt);
```
```cpp
v4l2_subdev_format fmt{};
fmt.pad = 0;
fmt.which = V4L2_SUBDEV_FORMAT_ACTIVE;
fmt.format.width = 1920;
fmt.format.height = 1080;
fmt.format.code = MEDIA_BUS_FMT_SBGGR10_1X10;
fmt.format.field = V4L2_FIELD_NONE;
if (::ioctl(subdev_fd.get(), VIDIOC_SUBDEV_S_FMT, &fmt) < 0) {
    throw std::system_error(errno, std::generic_category(), "Failed subdev format");
}
```
:::
2. **Перевірка режимів TRY та ACTIVE**:
   - `V4L2_SUBDEV_FORMAT_TRY`: Дозволяє додатку випробувати можливість встановлення формату та геометрії без зміни реальних регістрів апаратури. Драйвер повертає скориговані значення, які апаратура здатна підтримати.
   - `V4L2_SUBDEV_FORMAT_ACTIVE`: Фіксує скоригований формат у фізичних регістрах субпристрою.
3. **Геометрія та кадрування (Crop/Compose)**: Субпристрої підтримують ioctl `VIDIOC_SUBDEV_S_SELECTION` для виділення внутрішньої області кадрування (`V4L2_SEL_TGT_CROP`) або масштабування (`V4L2_SEL_TGT_COMPOSE`).
4. **Валідація конвеєра (Pipeline Validation)**: Обробляючи `VIDIOC_STREAMON`, драйвер відеовузла запускає `media_pipeline_start()`. Вона обходить граф від `/dev/video0` назад до сенсора, збирає в конвеєр усі сутності, з'єднані активними зв'язками (`MEDIA_LNK_FL_ENABLED`), і для кожного зв'язку кличе зворотний виклик `link_validate()` відповідного субпристрою. Типова реалізація `v4l2_subdev_link_validate()` звіряє медіа-код і геометрію кадру на суміжних майданчиках (`SOURCE` pad `format.code` проти `SINK` pad `format.code`). Якщо виявлено розбіжність, `VIDIOC_STREAMON` повертає помилку `EPIPE` (Broken pipe).

## Підсистема керування буферами Videobuf2 (vb2)

Серцем передачі відеоданих з високою швидкістю є ядерний фреймворк **Videobuf2 (vb2)**. Він відповідає за виділення пам'яті під відеобуфери, організацію кільцевих черг (ring buffers) та узгоджене в часі керування контролерами прямого доступу до пам'яті (DMA).

![Життєвий цикл буфера у фреймворку Videobuf2](/reference/unix-linux/devices/v4l2-media-subsystem/img/vb2-buffer-lifecycle.svg)
*Стани буфера Videobuf2 при передачі кадрів через чергу dequeuing/queuing з DMA.*

### Життєвий цикл буфера у Videobuf2

Кожен буфер у фреймворку vb2 проходить п'ять станів:

1. **DEQUEUED (Вилучений)**: Буфер перебуває під управлінням простору користувача. Додаток може читати з нього піксельні дані або записувати їх (у випадку відеовиводу).
2. **PREPARED (Підготовлений)**: Драйвер ядра перевірив параметри буфера та здійснив прив'язку фізичних сторінок пам'яті (DMA mapping). Ця робота виконується всередині `VIDIOC_QBUF` або наперед, окремим викликом `VIDIOC_PREPARE_BUF`.
3. **QUEUED (У черзі)**: Викликом `VIDIOC_QBUF` додаток віддав буфер ядру; підготовлений буфер стоїть у вхідній черзі драйвера й чекає, поки апаратура візьме його під запис.
4. **ACTIVE (Активний DMA)**: Буфер передано безпосередньо апаратному контролеру DMA. Відеоконтролер записує поточний кадр камери за фізичною адресою буфера у RAM.
5. **DONE (Завершений)**: Апаратне переривання (IRQ) сповіщає про завершення запису кадру. Драйвер викликає `vb2_buffer_done()`, переміщуючи буфер у чергу готових кадрів. Додаток забирає його викликом `VIDIOC_DQBUF`.

### Режими виділення пам'яті у Videobuf2

V4L2 підтримує три основні моделі управління пам'яттю буферів:

- **`V4L2_MEMORY_MMAP`**: Пам'ять для буферів виділяється драйвером ядра (у неперервній зоні CMA або через IOMMU). Простір користувача отримує доступ до них через системний виклик `mmap()`. Це найпростіший режим для локальної обробки.
- **`V4L2_MEMORY_DMABUF`**: Найбільш продуктивний режим **Zero-Copy** у сучасних системах Linux. Буфер виділяється в іншій підсистемі (наприклад, DRM/KMS або dma-buf heap) та передається у V4L2 через файловий дескриптор. Це дозволяє передавати кадри камери напряму у GPU або відеокодек без жодного копіювання байтів центральним процесором.
- **`V4L2_MEMORY_USERPTR`**: Буфер виділяється у просторі користувача через `posix_memalign()`, а ядро прикріплює ці сторінки до DMA. Рідко використовується через високі витрати на перевірку сторінок (Page Pinning).

Формули обчислення частот піксельних генераторів, пропускної здатності шини DMA та необхідних розмірів буферів викладено у вставці [математичний розрахунок пропускної здатності медіа-конвеєра](book:unix-linux/v4l2-media-subsystem/math-media-pipeline-bandwidth.md).

## Ядерні структури даних та системні контракти IOCTL

З боку ядра Linux медіа-підсистема описується зв'язкою об'єктно-орієнтованих структур мовою C, де `struct v4l2_device` виступає контейнером для субпристроїв `struct v4l2_subdev`, а `struct media_device` вибудовує граф топології.

З боку простору користувача управління здійснюється через специфічні контракти системного виклику `ioctl`:

- Для топології графа: `MEDIA_IOC_DEVICE_INFO`, `MEDIA_IOC_G_TOPOLOGY`, `MEDIA_IOC_SETUP_LINK` на `/dev/mediaX`.
- Для субпристроїв: `VIDIOC_SUBDEV_G_FMT`, `VIDIOC_SUBDEV_S_FMT`, `VIDIOC_SUBDEV_S_SELECTION` на `/dev/v4l-subdevX`.
- Для відеопотоку: `VIDIOC_QUERYCAP`, `VIDIOC_S_FMT`, `VIDIOC_REQBUFS`, `VIDIOC_QBUF`, `VIDIOC_DQBUF`, `VIDIOC_EXPBUF`, `VIDIOC_STREAMON` на `/dev/videoX`.

Вичерпний технічний довідник усіх ядерних структур даних, прапорців та ioctl-контрактів наведено у вставці [довідник ядерних структур V4L2 та Media Controller](book:unix-linux/v4l2-media-subsystem/api-v4l2-mc-core.md).

## Повний життєвий цикл захоплення кадрів та взаємодія з libcamera

Для системного програміста захоплення кадрів із камери через V4L2 та Media Controller вимагає суворого дотримання послідовності викликів.

### Послідовність кроків додатка простору користувача

1. **Відкриття медіа-контролера**: `open("/dev/media0")` та активація зв'язків між сутностями через `MEDIA_IOC_SETUP_LINK`.
2. **Конфігурація субпристроїв**: `open("/dev/v4l-subdev0")` та фіксація формату медіа-шини викликом `VIDIOC_SUBDEV_S_FMT`.
3. **Налаштування відеовузла**: `open("/dev/video0")` та виклик `VIDIOC_S_FMT` із бажаним кодом FourCC (наприклад, `V4L2_PIX_FMT_NV12`).
4. **Виділення та розміщення буферів**: `VIDIOC_REQBUFS` із типом `V4L2_MEMORY_MMAP`, отримання адрес через `VIDIOC_QUERYBUF` та `mmap()`.
5. **Постановка буферів у чергу**: Наповнення вхідної черги драйвера викликами `VIDIOC_QBUF` для кожного буфера.
6. **Запуск потоку DMA**: Виклик `VIDIOC_STREAMON`.
7. **Цикл обробки кадрів**: Використання системного виклику `poll()` або `select()` для очікування готовності кадру → вилучення кадру викликом `VIDIOC_DQBUF` → обробка даних → повернення буфера у чергу викликом `VIDIOC_QBUF`.
8. **Зупинка**: Виклик `VIDIOC_STREAMOFF` та звільнення відображень `munmap()`.

Повний функціонуючий приклад коду захоплення кадрів мовами C та C++ з використанням сучасних RAII-обгорток зібрано у вставці [практичний проект захоплення кадрів та керування медіа-графом](book:unix-linux/v4l2-media-subsystem/proj-v4l2-capture.md).

### Роль відкритого стека libcamera

Оскільки самостійне налаштування графа Media Controller та реалізація складних алгоритмів 3A (Auto Exposure, Auto White Balance, Auto Focus) є надзвичайно трудомісткою задачею, у сучасному стеку Linux між ядром та прикладними програмами (GStreamer, PipeWire, FFmpeg) розташовується відкрита бібліотека **libcamera**.

`libcamera` автоматично сканує граф Media Controller через `/dev/mediaX`, знаходить потрібні сутності, конфігурує формат на субпристроях та запускає конвеєр V4L2. Це дає змогу високорівневому софту працювати зі складними апаратними камерами мобільних та вбудованих пристроїв так само просто, як зі звичайними USB-веб-камерами.
