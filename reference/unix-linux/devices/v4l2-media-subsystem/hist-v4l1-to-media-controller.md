# 📜 Історія еволюції медіа-підсистеми Linux: від V4L1 до Media Controller

Історія виникнення та трансформації медіа-підсистеми ядра Linux відображає фундаментальну еволюцію відеообладнання за останні чверть століття: від аналогових ТВ-тюнерів на шині PCI у пізніх 1990-х роках до мобільних систем обробки зображень (ISP) та багатпинових кадрових конвеєрів у сучасних системах на кристалі (SoC). Без осягнення цієї історичної трансформації неможливо збагнути, чому сучасне управління камери у Linux розділене між класичними потоковими вузлами `/dev/videoX`, графом Media Controller `/dev/mediaX` та проміжними субпристроями `/dev/v4l-subdevX`.

## Перша ера: Video for Linux 1 та аналогові ТВ-тюнери (1998–2002)

У пізніх 1990-х роках первинною задачею захоплення відео у персональних комп'ютерах з операційною системою Linux було приймання аналогового телевізійного сигналу проектів PAL/NTSC/SECAM та робота з першими споживчими веб-камерами на шині USB 1.1 (такими як QuickCam). Для вирішення цього завдання відомий розробник ядра Алан Кокс (Alan Cox) у ядрі Linux 2.1.20 у листопаді 1998 року представив першу версію інтерфейсу **Video for Linux (V4L1)**.

Модель V4L1 спиралася на концепцію єдиного монолітного символьного пристрою `/dev/video0`. Взаємодія з драйвером (найвідомішим з яких був легендарний драйвер `bttv` розробки Ральфа Мецара для чипів оцифровки Brooktree BT848/BT878, а згодом драйвери `saa7134` та `cx88`) здійснювалася через набір системних викликів `ioctl` та просте відображення пам'яті (`mmap`). Драйвер V4L1 виконував оцифрування аналогового відеосигналу у фіксований буфер кадру (Framebuffer) графічної карти або у системну пам'ять.

Проте V4L1 швидко виявив критичні обмеження під час появи цифрових відеокамер, плап захоплення та систем відеоспостереження:

1. **Відсутність механізму узгодження форматів**: API не мав гнучких викликів для перелічення (`enumeration`) та налаштування колірних просторів (RGB, YUV420, YUYV). Пристрої повертали відеодані у жорстко зафіксованому форматі драйвера, змушуючи прикладний софт виконувати конвертацію.
2. **Обмежена та жорстка буферизація**: V4L1 не підтримував кільцевих черг буферів (ring buffers). Захоплення кадрів супроводжувалося високим рівнем пропуску кадрів (frame drops) через блокуючий системний виклик `read()`, оскільки центральний процесор повинен був чекати завершення оцифровки кожного кадру.
3. **Нездатність керувати кількома потоками**: Спроба одночасного захоплення відео та читання телетексту або кадрів високої роздільної здатності викликала конфлікти у структурі `struct video_picture`.

## Друга ера: Стандартизація V4L2 та вибух USB-камер (2002–2009)

У 2002 році (офіційно інтегровано у ядрі Linux 2.5.46 та бэкпортовано у стабільну гілку 2.4.21) розробники Білл Діркс (Bill Dirks), Джастін Шуман (Justin Schoeman) та Мауро Карвальо Чехаб (Mauro Carvalho Chehab) створили другу версію інтерфейсу — **V4L2 (Video for Linux 2)**.

V4L2 заклав фундамент сучасної потокової відеообробки Linux:

- **Розділення ролей пристроїв**: Було введено поняття типів буферів (`V4L2_BUF_TYPE_VIDEO_CAPTURE`, `V4L2_BUF_TYPE_VIDEO_OUTPUT`, `V4L2_BUF_TYPE_VBI_CAPTURE`), що дозволило одному драйверу обслуговувати як захоплення, так і вивід або апаратне кодування відео.
- **Підсистема черг буферів (videobuf / videobuf2)**: З'явився чіткий життєвий цикл буферів `VIDIOC_REQBUFS`, `VIDIOC_QBUF`, `VIDIOC_DQBUF`, підтримка методів доступу `V4L2_MEMORY_MMAP` та `V4L2_MEMORY_USERPTR`.
- **Ієрархія контролів**: Механізм `v4l2_queryctrl` та `v4l2_control` (із подальшим розвитком у `v4l2_ctrl_handler`) дозволив додаткам динамічно виявляти та змінювати параметри зображення (яскравість, контраст, експозицію, баланс білого).

Завдяки появі специфікації USB Video Class (UVC) у 2003 році та випуску відкритого драйвера `uvcvideo` Лораном Піншаром у 2005 році, V4L2 став універсальним світовим стандартом для всіх споживчих USB-камер. Будь-який відеоплеєр (VLC, MPlayer, Skype) міг відкрити символьний вузол `/dev/video0`, встановити роздільну здатність через `VIDIOC_S_FMT` і запускати потік викликом `VIDIOC_STREAMON`.

## Третя ера: Криза мобільних SoC та народження Media Controller (2009–2011)

З бурхливим розвитком смартфонів та вбудованих систем на базі архітектур ARM (платформи TI OMAP3/OMAP4, Samsung Exynos, NXP i.MX, Qualcomm Snapdragon) споживча модель V4L2 зіштовхнулася з архітектурним глухим кутом.

У мобільних системах камера більше не була «чорною скринькою», яка віддає готовий JPEG або YUV-потік по шині USB. Сенсор камери (наприклад, Sony IMX або OmniVision) підключався через швидкісний послідовний шинний інтерфейс **MIPI CSI-2** до апаратного блоку обробки сигналів зображення — **ISP (Image Signal Processor)** всередині SoC.

Сучасний апаратний конвеєр камери перетворився на складну мережу:
1. Кристал сенсора дає «сирий» колірний масив байєра (RAW Bayer).
2. Приймач MIPI CSI-2 десеріалізує потік пакетів.
3. Блок ISP виконує корекцію чорного, дебайєризацію (Demosaicing), гамма-корекцію, шумозаглушення та кадрування.
4. Окремі ДМА-рушії записують نتائج у пам'ять, а додаткові сенсори вимірюють освітленість для фокусування.

Намагання описати такий конвеєр через єдиний вузол `/dev/video0` призвело до того, що драйвери змушені були приховувати внутрішню топологію або створювати нестандартні пропрієтарні `ioctl`. Користувацький простір втратив можливість налаштовувати проміжні точки конвеєра (наприклад, знімати RAW-кадр безпосередньо з CSI-2 для алгоритмів обробки та одночасно відправляти YUV-потік на прев'ю).

У 2011 році розробники Лоран Піншар (Laurent Pinchart), Сакарі Айлус (Sakari Ailus) та Ханс Веркейл (Hans Verkuil) представили фреймворк **Media Controller (MC)**, який було залайнено у ядрі Linux 2.6.39.

Media Controller відмовився від ідеї монолітного пристрою і представив відеосистему як **спрямований граф**:
- **Сутності (Entities)**: Кожен фізичний або логічний блок (сенсор, CSI-приймач, ISP, DMA-канал) отримав власний представник у графі.
- **Майданчики (Pads)**: Точки входу (`SINK`) та виходу (`SOURCE`) даних для кожної сутності.
- **Зв'язки (Links)**: Керовані з'єднання між майданчиками.

Для прямого управління параметрами проміжних блоків було створено символьні пристрої субпристроїв `/dev/v4l-subdevX`. Це дозволило налаштовувати роздільну здатність і колірні формати на кожному сегменті графа незалежно.

## Четверта ера: dma-buf та відкритий стек libcamera (2018–дотепер)

З появою у ядрі Linux фреймворку **dma-buf** медіа-підсистема отримала можливість здійснювати передачу кадрів із нульовим копіюванням (Zero-Copy) між V4L2, GPU (через DRM/KMS) та апаратними відеодекодерами (V4L2 Stateful/Stateless Codec API).

Проте зростання складності Media Controller створило новий виклик: звичайні додатки (веб-браузери, Zoom, Skype) не вміли самостійно будувати граф Media Controller, налаштовувати зв'язки та реалізовувати складні алгоритми автоекспозиції чи автофокусу (алгоритми 3A: Auto Exposure, Auto White Balance, Auto Focus).

Для вирішення цієї проблеми у 2018 році спільнота Linux Kernel та Linux Foundation розпочала розробку відкритого шару абстракції **libcamera**. Бібліотека `libcamera` бере на себе всю низькорівневу роботу з `/dev/mediaX` та `/dev/v4l-subdevX`, надаючи програмам верхнього рівня високрівневий API камери, зберігаючи при цьому відкритість та прозорість ядерного медіа-графа.
