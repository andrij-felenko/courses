## Двоконтролерне сховище і прихована ціна другого порту

Корпоративний сервер баз даних підключено двома оптичними кабелями Fibre Channel до дискової полиці зберігання корпоративного рівня. Дискова полиця містить два незалежні процесорні модулі — Контролер A та Контролер B. Кожен контролер виставляє у фабрику SAN по два порти зі швидкістю 32 Гбіт/с. З погляду операційної системи Linux на хості з'являються чотири блокові пристрої: `/dev/sdb`, `/dev/sdc`, `/dev/sdd` та `/dev/sde`. Усі чотири шляхи ведуть до одного й того самого дискового тому (LUN 0) обсягом 4 ТБ.

Адміністратор налаштовує підсистему багатошляховості `dm-multipath`, обираючи наївну політику балансування навантаження за круговим алгоритмом (*Round-Robin*): кожен наступний запит введення-виведення надсилається у наступний доступний порт по колу (`sdb → sdc → sdd → sde → sdb`). Очікування просте: сумарна пропускна здатність має зрости вчетверо, а затримка читання й запису — рівномірно розподілитися між усіма лінками.

Замість чотирикратного прискорення система демонструє деградацію:
- Середня затримка випадкового запису 8-кілобайтного блоку стрибає з 0.8 мс до 14 мс.
- Графік затримки набуває пилкоподібної форми: один запит завершується за сотні мікросекунд, наступний висить у черзі десятки мілісекунд.
- Навантаження на внутрішню міжконтролерну шину дискового масиву сягає 100%, витісняючи службовий трафік дзеркалення оперативної пам'яті.

Причина полягає в апаратно-програмній асиметрії контролерів масиву. Фізично обидва процесорні модулі з'єднані з кошиком дискових накопичувачів через двопортові інтерфейси SAS, проте логічним власником тому LUN 0 у цей момент є виключно Контролер A. Саме в його оперативній пам'яті виділено сегменти кешу запису, і саме його процесор володіє таблицями трансляції адрес та блокуваннями файлової структури тому.

Коли хост надсилає команду запису через порти `sdb` або `sdd`, вона потрапляє безпосередньо в процесор Контролера A. Контролер фіксує дані в локальному енергонезалежному кеші, дублює їх у пам'ять партнера для відмовостійкості та негайно повертає хосту статус успішного завершення `SAM_STAT_GOOD`. Час виконання становить менше мілісекунди.

Коли ж хост спрямовує команду через порти `sdc` або `sde`, вона надходить до Контролера B. Контролер B не має права самостійно модифікувати метадані чужого тому. Він змушений упакувати отриманий SCSI-запит у внутрішній транспортний кадр, передати його через міжконтролерну шину (наприклад, міст PCIe Non-Transparent Bridge або інтерфейс CMI) на Контролер A, дочекатися обробки запиту процесором Контролера A, забрати результат назад через шину і лише після цього відповісти хосту. 

Такий доступ через контролер-партнер називається **проксі-доступом** (*proxy I/O*). Він витрачає ресурси міжконтролерного з'єднання, додає затримки комутації та створює паразитне навантаження.

![Архітектура двоконтролерного сховища та асиметрія шляхів ALUA](/reference/unix-linux/devices/scsi-alua/img/alua-dual-controller-arch.svg)

*Двоконтролерне сховище: шляхи через Контролер A є прямими (Active/Optimized), тоді як шляхи через Контролер B вимагають пересилання через міжконтролерну шину (Active/Non-Optimized).*

Щоб хост міг розрізняти прямі та непрямі дороги до даних і не навантажував проксі-канали без крайньої потреби, у стандарті SCSI було розроблено протокольний механізм **ALUA** (*Asymmetric Logical Unit Access* — асиметричний доступ до логічного пристрою; корінь від грецького *ἀ-*, «не» + *συμμετρία*, «співмірність»).

Історично кожен виробник систем збереження намагався розв'язати цю проблему закритими вендорними розширеннями командного набору, що вимагало специфічних драйверів під кожну модель полиці; детальніше це описано в нарисі [еволюція від вендорних механізмів trespass до стандарту SPC](book:unix-linux/scsi-alua/hist-proprietary-failover-to-alua.md).

## Анатомія симетричного і асиметричного доступу

Усі корпоративні масиви зберігання даних за типом організації доступу до томів поділяються на три архітектурні класи:

```
+──────────────────────────────────────────────────────────────────────────+
|                    АРХІТЕКТУРНІ КЛАСИ ДИСКОВИХ МАСИВІВ                   |
+──────────────────────────────────────────────────────────────────────────+
| 1. Справжній симетричний доступ (Active-Active Symmetric):               |
|    Будь-який контролер має однаковий апаратний доступ до даних і кешу    |
|    (EMC Symmetrix/VMAX, Hitachi VSP). Ціна — надзвичайно складна фабрика |
|    спільної пам'яті. Не потребує ALUA.                                   |
+──────────────────────────────────────────────────────────────────────────+
| 2. Традиційний активний/пасивний доступ (Active-Passive Traditional):    |
|    Один контролер приймає I/O, інший перебуває в холодному резерві.      |
|    Запити на резервний порт повертають статус помилки NOT READY.         |
+──────────────────────────────────────────────────────────────────────────+
| 3. Асиметричний активний/активний доступ (Asymmetric Active-Active):     |
|    Обидва контролери готові приймати I/O, але шлях через контролер-      |
|    власник має найменшу затримку, а шлях через партнера — вищу затримку. |
|    Це цільовий сценарій використання ALUA (SPC-3 / SPC-4 / SPC-5).       |
+──────────────────────────────────────────────────────────────────────────+
```

1. **Справжній симетричний активний/активний доступ (Active-Active Symmetric).** Усі контролери масиву об'єднані надшвидкісною глобальною матрицею пам'яті (*Global Shared Memory*). Кожен порт будь-якого контролера має ідентичний прямий доступ до будь-якого сектора будь-якого LUN із абсолютно однаковою затримкою. Для таких систем уся багатошляховість є строго симетричною, і алгоритм Round-Robin працює ідеально. Проте вартість апаратної реалізації апаратно-узгодженого глобального кешу обмежує застосування цієї моделі найдорожчим сегментом *High-End* (наприклад, архітектури Dell PowerMax або Hitachi VSP).

2. **Класичний активний/пасивний доступ (Active-Passive Traditional).** Контролер B не обслуговує запити до тому взагалі, поки Контролер A залишається працездатним. Будь-яка команда вводу-виводу, спрямована на порти Контролера B, завершується апаратною помилкою SCSI `CHECK CONDITION` зі статусом `NOT READY`. Щоб перевести том на другий контролер, хост мав надіслати пропрієтарну команду зміни власника.

3. **Асиметричний активний/активний доступ (Asymmetric Active-Active / ALUA).** Компромісна і найбільш поширена архітектура сучасних дискових масивів (Dell PowerStore/Unity, NetApp ONTAP, HPE Primera/Alletra, Pure Storage, IBM FlashSystem, а також софтверні сховища на базі ядра Linux). Обидва контролери одночасно приймають команди вводу-виводу до всіх томів, жоден порт не відхиляє запити, проте продуктивність та внутрішній маршрут руху даних суттєво відрізняються.

ALUA стандартизує спосіб, за допомогою якого дисковий масив повідомляє операційній системі хоста: «Ці два порти зараз забезпечують прямий оптимальний доступ, а ось ті два — непрямий резервний. Шліть запити на перші, а другі тримайте напоготові на випадок аварії».

## Цільові групи портів (Target Port Groups — TPG)

Сучасний контролер системи зберігання рідко має лише один мережевий інтерфейс. Типова конфігурація містить 2, 4 або 8 портів Fibre Channel, iSCSI чи NVMe/TCP на кожній керуючій платі.

Якщо Контролер A володіє томом LUN 0, то абсолютно всі фізичні порти, виведені з цієї плати, забезпечують однаковий прямий доступ до кешу тому. Навпаки, всі порти плати Контролера B мають однакові характеристики затримки проксі-пересилання.

Описувати стан кожного окремого порту індивідуально було б надлишковим і неефективним: при відмові Контролера A змінюється статус не одного інтерфейсу, а одразу всієї сукупності портів плати.

Стандарт SCSI формалізує це через поняття **цільової групи портів** (*Target Port Group*, TPG):

> **Цільова група портів (TPG)** — це логічна сукупність одного або кількох цільових портів SCSI дискового масиву, які мають однаковий асиметричний стан доступу до конкретного логічного тому (LUN).

```
+──────────────────────────────────────────────────────────────────────────+
|                 СТРУКТУРА ЗВ'ЯЗКІВ LUN ТА ЦІЛЬОВИХ ГРУП ПОРТІВ           |
+──────────────────────────────────────────────────────────────────────────+
|  Дисковий масив:                                                         |
|  ┌─────────────────────────────────┐ ┌─────────────────────────────────┐ |
|  │          Контролер A            │ │          Контролер B            │ |
|  │ ┌──────────────┐ ┌────────────┐ │ │ ┌──────────────┐ ┌────────────┐ │ |
|  │ │ Порт FC 1    │ │ Порт FC 2  │ │ │ │ Порт FC 3    │ │ Порт FC 4  │ │ |
|  │ │ (RTPI: 0x01) │ │(RTPI: 0x02)│ │ │ │ (RTPI: 0x03) │ │(RTPI: 0x04)│ │ |
|  │ └───────┬──────┘ └──────┬─────┘ │ │ └───────┬──────┘ └──────┬─────┘ │ |
|  │         └───────┬───────┘       │ │         └───────┬───────┘       │ |
|  │        Target Port Group 1      │ │        Target Port Group 2      │ |
|  │           (TPG ID: 1)           │ │           (TPG ID: 2)           │ |
|  └─────────────────┬───────────────┘ └─────────────────┬───────────────┘ |
|                    │                                   │                 |
|      ┌─────────────┴───────────────────────────────────┴─────────────┐   |
|      │ LUN 0:   TPG 1 = Active/Optimized   | TPG 2 = Active/Non-Opt   │   |
|      │ LUN 1:   TPG 1 = Active/Non-Opt     | TPG 2 = Active/Optimized │   |
|      └───────────────────────────────────────────────────────────────┘   |
+──────────────────────────────────────────────────────────────────────────+
```

Кожен порт цілі в межах усього дискового масиву отримує унікальний числовий ідентифікатор — **відносний ідентифікатор порту цілі** (*Relative Target Port Identifier*, RTPI, 16-бітне число від `0x0001` до `0xFFFF`).

Група портів ідентифікується номером **TPG ID** (*Target Port Group Identifier*, 16-бітне число).

Критично важливо розуміти: **прив'язка стану ALUA до TPG є контекстною відносно кожного конкретного LUN**.
- Для **LUN 0** (власник — Контролер A) група TPG 1 перебуває в стані оптимального доступу, а TPG 2 — у стані проксі.
- Для **LUN 1** (власник — Контролер B) конфігурація дзеркальна: TPG 2 є оптимальною, а TPG 1 — проксі.

Це дозволяє дисковому масиву симетрично балансувати глобальне навантаження між обома процесорними вузлами: парні томи обслуговуються першим контролером, а непарні — другим.

## П'ять станів портів цільової групи

Специфікації SPC-3 та SPC-4 визначають п'ять дискретних станів асиметричного доступу цільової групи портів до логічного тому:

![Стани цільових портів ALUA та переходи між ними](/reference/unix-linux/devices/scsi-alua/img/alua-port-states.svg)

*Діаграма станів цільових портів ALUA, допустимі переходи та реакція масиву на команди ініціатора.*

### 1. Active/Optimized (AO, код стану `0x0`)
Стан оптимальної активності. Порти цієї групи забезпечують прямий доступ до локального кешу та внутрішніх дискових інтерфейсів контролера-власника.
- Всі команди читання (`READ 6/10/16`), запису (`WRITE 6/10/16`), верифікації та синхронізації кешу виконуються без додаткових затримок на максимальній швидкості інтерфейсу.
- Підсистема багатошляховості Linux присвоює шляхам у цьому стані найвищий пріоритет (за замовчуванням `50`). Весь робочий трафік спрямовується виключно сюди.

### 2. Active/Non-Optimized (ANO, код стану `0x1`)
Стан неоптимальної активності (проксі-режим). Порти контролера-партнера готові приймати ввід-вивід, але виконання запитів пов'язане з пересиланням даних через внутрішню шину.
- Усі команди введення-виведення виконуються успішно, проте зі збільшеною затримкою та можливим обмеженням пропускної здатності.
- Підсистема багатошляховості Linux присвоює цим шляхам знижений пріоритет (за замовчуванням `10`). Шляхи ANO не отримують запитів за наявності живих шляхів у групі Active/Optimized і виконують роль «гарячого резерву».

### 3. Standby (SB, код стану `0x2`)
Стан пасивного очікування. Характерний для систем із класичною моделлю резервування, де контролер-партнер тримає внутрішні структури LUN у заблокованому або напівініціалізованому стані.
- Спроба виконати будь-яку операцію читання чи запису відхиляється масивом: повертається статус SCSI `CHECK CONDITION` із сенс-ключем `0x02` (*NOT READY*) та додатковим кодом причини ASC/ASCQ `0x04/0x0C` (*LOGICAL UNIT NOT ACCESSIBLE, TARGET PORT IN STANDBY STATE*).
- Контролер приймає виключно службові та діагностичні команди: `INQUIRY`, `REPORT TARGET PORT GROUPS`, `TEST UNIT READY`, `REPORT LUNS` та команду примусової активації `SET TARGET PORT GROUPS`.
- Пріоритет у Linux: `1`.

### 4. Unavailable (UN, код стану `0x3`)
Стан повної недоступності. Означає, що цільові порти фізично присутні на фабриці SAN, але зв'язок між цими портами та дисковим бекендом втрачено (наприклад, висмикнуто кабель SAS всередині полиці, вийшов з ладу локальний RAID-експандер або вузол виведено в режим сервісного обслуговування).
- Будь-який ввід-вивід відхиляється статусом `CHECK CONDITION` із сенс-ключем `0x02` (*NOT READY*) та ASC/ASCQ `0x04/0x0D` (*LOGICAL UNIT NOT ACCESSIBLE, TARGET PORT IN UNAVAILABLE STATE*).
- Дозволено лише команди базової ідентифікації `INQUIRY` та `REPORT TARGET PORT GROUPS`.
- Пріоритет у Linux: `0`.

### 5. Transitioning (TO, код стану `0xF`)
Тимчасовий стан переходу. Виникає під час міграції прав володіння LUN між контролерами (наприклад, коли Контролер A перезавантажується, і Контролер B імпортує його журнали блокувань, скидає залишки кешу та змінює свій внутрішній статус на Active/Optimized).
- Усі команди вводу-виводу тимчасово відхиляються статусом `CHECK CONDITION` із кодом Sense `0x02/0x04/0x0A` (*LOGICAL UNIT NOT READY, TARGET PORT IN RAPID TRANSITION*).
- Хост не повинен вважати цей шлях остаточно мертвим або перемикати помилку на файлову систему. Драйвер ядра затримує чергу запитів і періодично повторює команду до виходу масиву зі стану Transitioning (зазвичай процес займає від 100 мс до кількох секунд).

## Неявне та явне керування станами (Implicit vs Explicit)

Стандарт передбачає два механізми зміни станів цільових груп портів:

```
+──────────────────────────────────────────────────────────────────────────+
|                    МЕХАНІЗМИ ПЕРЕМИКАННЯ СТАНІВ ALUA                     |
+──────────────────────────────────────────────────────────────────────────+
| 1. Неявний перехід (Implicit ALUA):                                      |
|    Дисковий масив САМОСТІЙНО змінює стани TPG (наприклад, при збої       |
|    вузла A). Хост дізнається про це через перехоплення сенс-коду         |
|    Unit Attention (06h / 2Ah / 06h: Asymmetric Access State Changed).    |
+──────────────────────────────────────────────────────────────────────────+
| 2. Явний перехід (Explicit ALUA):                                        |
|    Хост ЯВНО надсилає команду SET TARGET PORT GROUPS (STPG) на порти     |
|    резервного контролера з вимогою: «Зроби TPG 2 станом Active/Optimized».|
|    Масив підпорядковується команді ініціатора.                           |
+──────────────────────────────────────────────────────────────────────────+
```

Тип підтримки оголошується масивом у полі `TPGS` (біти 5:4 байта 5) стандартної відповіді `INQUIRY`:
- `01b` — тільки неявне перемикання (*Implicit only*);
- `10b` — тільки явне перемикання (*Explicit only*);
- `11b` — підтримуються обидва механізми (*Both*).

Більшість сучасних масивів обирають режим `Both` або `Implicit`. При неявному переході, якщо всі порти Контролера A втрачають оптичний лінк, внутрішній сторожовий таймер масиву фіксує аварію і автоматично підвищує статус TPG 2 з ANO до AO. Коли хост надсилає наступний запит до порту `sdc`, масив повертає сповіщення `UNIT ATTENTION` з додатковим кодом `0x2A/0x06` (*Asymmetric Access State Changed*), змушуючи ядро Linux перечитати топологію.

## Протокольний діалог: команди REPORT і SET TARGET PORT GROUPS

Взаємодія ініціатора і дискового масиву в рамках ALUA спирається на дві фундаментальні команди SCSI:

### 1. REPORT TARGET PORT GROUPS (RTPG)
Команда групи обслуговування (код операції `0xA3`, Service Action `0x0A`). Ініціатор надсилає 16-байтовий блок CDB із виділеним буфером прийому даних (зазвичай 1024 байти).

У відповідь масив повертає двійковий потік, що починається з 4-байтового поля загальної довжини даних (`Return Data Length`), за яким іде послідовність дескрипторів цільових груп портів:

![Формат бінарних дескрипторів відповіді REPORT TARGET PORT GROUPS](/reference/unix-linux/devices/scsi-alua/img/alua-rtpg-descriptor-format.svg)

*Бінарний формат дескрипторів відповіді REPORT TARGET PORT GROUPS: біти PREF і стану доступу, ідентифікатор TPG ID та масив ідентифікаторів портів.*

Кожен дескриптор TPG містить:
- **Бит PREF (Preferred Target Port Group)** у 7-му біті першого байта. Виробник масиву позначає цим бітом апаратно бажаний контролер для цього LUN. Навіть якщо обидва контролери тимчасово перебувають у стані AO, хост віддаватиме перевагу групі з бітом `PREF=1`.
- **Asymmetric Access State (4 біти)**: поточний стан доступу (`0h`..`Fh`).
- **Маска підтримуваних станів (1 байт)**: бітові прапорці, що вказують, чи дозволено переводити цю групу в стани AO, ANO, SB, UN тощо.
- **Target Port Group ID (2 байти)**: унікальний номер TPG.
- **Target Port Count (`k`) та список дескрипторів портів**: масив 4-байтових записів, де кожен запис містить відносний номер порту цілі (*Relative Target Port ID*).

Повні бінарні таблиці зміщень, формати кадрів STPG та коди Sense Key/ASC/ASCQ зведено в довіднику [повний бінарний формат дескрипторів RTPG/STPG, сенс-коди та атрибути sysfs](book:unix-linux/scsi-alua/api-rtpg-stpg-descriptors.md).

### 2. SET TARGET PORT GROUPS (STPG)
Команда примусової зміни стану (код операції `0xA4`, Service Action `0x0A`). Використовується хостом у режимі явного ALUA. Хост передає масиву список пар `[TPG ID, Новий стан]`, вимагаючи, наприклад, перевести групу 2 у стан `0x0` (Active/Optimized).

Якщо розробнику необхідно вручну надіслати команду RTPG до пристрою, розпарсити двійковий потік і вивести стан портів цілі мовами C чи C++, робочу реалізацію на базі інтерфейсу `SG_IO` наведено в проекті [практична утиліта зчитування та розбору станів ALUA через SG_IO](book:unix-linux/scsi-alua/proj-alua-rtpg-parser.md).

## Ядро Linux: підсистема SCSI Device Handler (scsi_dh_alua)

У ядрі Linux інтеграція ALUA реалізована на стику трьох підсистем: драйвера середнього рівня SCSI (*SCSI Mid-Layer*), обробника апаратних пристроїв SCSI (*SCSI Device Handler*) та підсистеми відображення пристроїв *Device Mapper* (`dm-multipath`).

![Стек взаємодії dm-multipath, scsi_dh_alua та драйверів у Linux](/reference/unix-linux/devices/scsi-alua/img/linux-alua-stack.svg)

*Архітектурний стек ALUA в Linux: координація між простором користувача multipathd, ядром dm-multipath і модулем scsi_dh_alua.*

Ключовим компонентом ядра, що інкапсулює логіку протоколу SPC-3/SPC-4, є модуль ядра `scsi_dh_alua` (код розташовано в `drivers/scsi/device_handler/scsi_dh_alua.c`).

### Життєвий цикл і структури ядра

При виявленні нового блокового SCSI-диска ядро зчитує байти стандартної відповіді `INQUIRY`. Якщо поле `TPGS` містить ненульове значення, до структури `struct scsi_device` автоматично прив'язується обробник `scsi_dh_alua`.

Всередині ядра модуль створює дві взаємопов'язані структури даних:

```
/* Контекст обробника для конкретного шляху (scsi_device) */
struct alua_dh_data {
    struct sdev_device_handler *handler;
    struct scsi_device *sdev;
    struct alua_port_group *pg;  /* Вказівник на спільну групу TPG */
    int init_error;
    struct mutex init_mutex;
};

/* Спільний стан цільової групи портів */
struct alua_port_group {
    struct kref kref;
    struct list_head node;
    uint16_t tpg_id;             /* Target Port Group Identifier */
    int state;                   /* Поточний стан (AO, ANO, SB, UN, TO) */
    int pref;                    /* Ознака Preferred (1 або 0) */
    unsigned valid_states;       /* Бітова маска дозволених станів */
    int transition_tmo;          /* Тайм-аут виходу зі стану Transitioning */
    spinlock_t lock;
    struct scsi_device *rtpg_sdev; /* Пристрій для надсилання RTPG */
};
```

Якщо до одного контролера веде кілька шляхів (`/dev/sdb` та `/dev/sdd`), їхні структури `alua_dh_data` посилаються на **один і той самий екземпляр `alua_port_group`**. Коли стан групи оновлюється, він миттєво стає відомим для всіх фізичних каналів цієї групи без потреби опитувати кожен диск окремо.

### Перехоплення помилок та асинхронне реагування

Модуль `scsi_dh_alua` реєструє функцію зворотного виклику `alua_check_sense()`, яку середній рівень SCSI викликає при отриманні статусу `CHECK CONDITION` на будь-яку операцію вводу-виводу:

1. **Sense Key `06h` / ASC `2Ah` / ASCQ `06h` (*Asymmetric access state changed*):**
   Обробник перехоплює цей сенс-код, не передаючи його вище на файлову систему, і ставить у системну робочу чергу (*workqueue*) завдання термінового виконання команди RTPG для оновлення топології.

2. **Sense Key `02h` / ASC `04h` / ASCQ `0Ah` (*Logical unit not ready, target port in rapid transition*):**
   Обробник сигналізує підсистемі введення-виведення про тимчасову затримку: запит повертається в чергу `dm-multipath` з кодом `BLK_STS_AGAIN`, де він очікує завершення міграції.

### Експорт інформації через sysfs

Для кожного SCSI-диска стан ALUA доступний для перегляду у файловій системі `sysfs`:

```sh
# Перевірка поточного стану порту
$ cat /sys/class/scsi_disk/2:0:0:0/device/alua_access_state
optimized

# Перевірка ідентифікатора групи TPG
$ cat /sys/class/scsi_disk/2:0:0:0/device/alua_tpg_id
1

# Перевірка підтримуваного типу перемикання
$ cat /sys/class/scsi_disk/2:0:0:0/device/alua_access_type
both
```

## Інтеграція з dm-multipath і multipathd

Підсистема ядра `dm-multipath` нічого не знає про специфікації SCSI, коди команд або кадри Fibre Channel — вона оперує виключно віртуальними **групами пріоритетів шляхів** (*Priority Path Groups*).

Зв'язок між бінарними станами ALUA в ядрі та маршрутизацією блокових запитів забезпечує демон простору користувача `multipathd` за допомогою динамічної бібліотеки пріоритетів `libprio_alua.so`.

### Розрахунок пріоритетів у multipathd

Коли `multipathd` виявляє фізичні шляхи до диска, він викликає плагін пріоритету `prio "alua"`. Плагін зчитує атрибути `sysfs` або безпосередньо надсилає команду RTPG через `ioctl(SG_IO)` і обчислює числовий пріоритет шляху за такою шкалою:

```
+──────────────────────────────────────────────────────────────────────────+
|                    ТАБЛИЦЯ РОЗРАХУНКУ ПРІОРИТЕТІВ ALUA                   |
+──────────────────────────────────────────────────────────────────────────+
| Стан ALUA за RTPG                   | PREF | Числовий пріоритет multipath |
+─────────────────────────────────────+──────+─────────────────────────────+
| Active/Optimized (AO)               |  1   | 50                          |
| Active/Optimized (AO) non-preferred |  0   | 50 (або 40 при ексклюзиві)  |
| Active/Non-Optimized (ANO)          |  -   | 10                          |
| Standby (SB)                        |  -   | 1                           |
| Unavailable (UN)                    |  -   | 0                           |
| Transitioning (TO)                  |  -   | 0 (помилка / retry)         |
+──────────────────────────────────────────────────────────────────────────+
```

### Групування шляхів у конфігурації

У файлі `/etc/multipath.conf` поведінка налаштовується директивами:

```
devices {
    device {
        vendor                  "NETAPP"
        product                 "LUN.*"
        path_grouping_policy    group_by_prio
        prio                    "alua"
        hardware_handler        "1 alua"
        path_selector           "service-time 0"
        failback                immediate
    }
}
```

Директива `path_grouping_policy group_by_prio` змушує `multipathd` створювати окремі групи пріоритетів усередині таблиці Device Mapper:
- **Група 1 (Пріоритет 50):** містить шляхи `sdb` та `sdd` (порти Контролера A). Вона є **активною групою** (*Active Path Group*). Всі запити розподіляються між цими двома шляхами алгоритмом `service-time`.
- **Група 2 (Пріоритет 10):** містить шляхи `sdc` та `sde` (порти Контролера B). Вона перебуває в **резерві** (*Enabled/Standby Path Group*) і не отримує жодного байта робочих даних.

Рядок таблиці Device Mapper, згенерований для ядра, виглядає так:

```
0 8388608000 multipath 1 queue_if_no_path 1 alua 2 1 service-time 0 2 2 8:16 1 1 8:48 1 1 service-time 0 2 2 8:32 1 1 8:64 1 1
```

Ядро чітко бачить: дві групи пріоритетів (`2`), активна зараз перша (`1`), обробник заліза — `alua`.

## Анатомія відмови й автоматичний перехід (Failover / Failback)

Розглянемо покрокову послідовність подій, коли під час інтенсивного навантаження Контролер A зазнає апаратної відмови (раптова паніка ядра контролера або відключення живлення):

![Послідовність повідомлень під час аварійного перемикання (Failover) в ALUA](/reference/unix-linux/devices/scsi-alua/img/alua-failover-sequence.svg)

*Хронологія аварійного перемикання: від падіння зв'язку з Контролером A через стан Transitioning до відновлення роботи на Контролері B.*

1. **Нормальний режим.** Застосунок виконує операції запису. `dm-multipath` спрямовує всі `bio` на шляхи `sdb` та `sdd` (Група 1, Active/Optimized). Контролер A повертає `SAM_STAT_GOOD`.

2. **Аварія вузла A.** Контролер A раптово вимикається. Фізичні лінки на портах `sdb` та `sdd` падають, або контролер перестає відповідати на кадри Fibre Channel.

3. **Детекція збою на хості.** Наступний запис на `sdb` завершується тайм-аутом транспорту SCSI. Драйвер HBA повертає статус помилки. Підсистема `dm-multipath` миттєво знімає позначку працездатності зі шляху `sdb` і переводить решту трафіку на `sdd`. Коли й на `sdd` фіксується помилка зв'язку, **Група 1 переходить у стан FAILED** — у ній не лишилося жодного живого шляху.

4. **Утримання в черзі (Queueing).** Завдяки опції `queue_if_no_path` (або параметру `no_path_retry`) ядро Linux не повертає помилку `EIO` файловій системі, а ставить нові запити в чергу очікування.

5. **Активація резервної Групи 2.** `dm-multipath` перемикає активний покажчик на Групу 2 (шляхи `sdc` та `sde`, пріоритет 10).
   - Якщо масив налаштовано на **Explicit ALUA**, ядро викликає метод активації обробника `scsi_dh_alua->activate()`. Модуль `scsi_dh_alua` генерує команду `SET TARGET PORT GROUPS (STPG)` і надсилає її на порт `sdc`, вимагаючи підвищити стан TPG 2 до Active/Optimized.
   - Якщо масив працює в режимі **Implicit ALUA**, внутрішній кластерний сторож полиці самостійно виявляє падіння партнера та ініціює захоплення ресурсів тома.

6. **Опрацювання стану Transitioning.** Під час імпорту метаданих і перехоплення блокувань Контролер B тимчасово повертає на перший запит статус `CHECK CONDITION` із сенс-кодом `02h/04h/0Ah` (*Target Port in Rapid Transition*). Модуль ядра `scsi_dh_alua` розпізнає цей код, не скидає ввід-вивід з помилкою, а робить мікропаузу (200 мс) і повторює опитування.

7. **Вихід на оптимальний режим.** Контролер B завершує ініціалізацію, TPG 2 переходить у стан Active/Optimized. Наступний запис на порт `sdc` успішно виконується з поверненням `SAM_STAT_GOOD`.

8. **Оновлення пріоритетів.** Демон `multipathd` через плагін `prio_alua` зчитує оновлену відповідь RTPG, бачить, що TPG 2 тепер має статус AO (пріоритет 50), і оновлює внутрішню карту шляхів. Весь стек вводу-виводу продовжує роботу. Застосунок зафіксував лише короткочасне збільшення затримки під час перемикання (зазвичай 1–3 секунди), жоден байт даних не втрачено.

9. **Процес відновлення (Failback).** Після заміни несправної плати Контролер A повертається в стрій. Він синхронізує кеш із партнером, повертає собі права володіння LUN 0 і переводить TPG 1 назад у стан AO. Масив надсилає хосту сенс-код `06h/2Ah/06h` (*Asymmetric Access State Changed*). `scsi_dh_alua` ініціює RTPG, `multipathd` виявляє відновлення первинного пріоритету 50 на Групі 1 і згідно з директивою `failback immediate` безшовно повертає робочий трафік на прямі порти Контролера A.

## Підводні камені, типові конфігураційні помилки та ціна компромісу

Попри високий рівень автоматизації стандарту ALUA, в експлуатації корпоративних SAN виникає низка критичних проблем, пов'язаних із помилками налаштування та апаратними крайовими випадками:

### 1. Явище «пінг-понгу» (ALUA Thrashing / LUN Ping-Pong)
Найнебезпечніша системна помилка у кластерних середовищах (наприклад, VMware ESXi, Proxmox VE або Red Hat Pacemaker).

Якщо на дисковому масиві з явним керуванням ALUA (Explicit) два хости мають різні або конфліктні налаштування пріоритетів (або один сервер вважає оптимальним Контролер A, а другий через помилку зонування Fibre Channel бачить лише порти Контролера B):
- Сервер 1 надсилає команду STPG, примусово перемикаючи LUN 0 на Контролер A.
- Через 100 мс Сервер 2 надсилає свій запит I/O на Контролер B, стикається з відмовою і надсилає зустрічну команду STPG, забираючи LUN 0 назад на Контролер B.
- LUN 0 починає безперервно мігрувати між контролерами зі швидкістю кілька разів на секунду (*thrashing*). 95% процесорного часу контролери витрачають на скидання кешу та обмін правами, продуктивність вводу-виводу падає до нуля, а сервери фіксують відмову дискової підсистеми.

*Захист:* налаштування на масиві виключно неявного режиму (*Implicit ALUA*) або використання опції `prio_args exclusive_pref` у `multipath.conf`, яка забороняє хосту самовільно надсилати STPG на непередбачені контролери.

### 2. Відсутність обробника заліза при використанні prio alua
Поширена помилка системних адміністраторів: оголошення в `multipath.conf` політики пріоритету `prio "alua"`, але пропуск директиви `hardware_handler "1 alua"`:

```
# ПОМИЛКОВА КОНФІГУРАЦІЯ:
device {
    vendor "VENDOR"
    product "STORAGE"
    prio "alua"
    # ПРОПУЩЕНО: hardware_handler "1 alua"
}
```

У цьому випадку демон `multipathd` успішно виявляє групи шляхів і знає, що Група 2 є резервною. Проте коли Група 1 вмирає, ядро `dm-multipath` перемикає активний покажчик на Групу 2, але **не має модуля, здатного надіслати команду STPG або коректно обробити коди Sense `Transitioning`**. В результаті перемикання зависає або завершується помилкою `I/O error`.

### 3. Невідповідність таймерів транспорту і тайм-аутів переходу
Якщо параметр тайм-ауту блокування порту SCSI Fibre Channel `fast_io_fail_tmo` встановлено в занадто мале значення (наприклад, 2 секунди), а дисковий масив під час аварійного скидання 128 ГБ "брудного" кешу переходить у стан Transitioning на 8 секунд:
- Драйвер Fibre Channel передчасно фіксує втрату зв'язку і відкидає чергу запитів.
- Підсистема `scsi_dh_alua` не встигає дочекатися завершення переходу, і файлова система перемонтовується в режим лише для читання (*read-only*).

*Правило налаштування:* тайм-аут `alua_transition_tmo` у `sysfs` повинен завжди перевищувати максимальний гарантований час скидання внутрішнього кешу масиву (типове рекомендоване значення — 60 секунд).

```
+──────────────────────────────────────────────────────────────────────────+
|                    ПОРІВНЯННЯ: SCSI ALUA ТА NVME ANA                     |
+──────────────────────────────────────────────────────────────────────────+
| Критерій                 | SCSI ALUA (SPC-3/4)    | NVMe ANA (TP 4004)   |
+──────────────────────────+────────────────────────+──────────────────────+
| Протокольний рівень      | SCSI Primary Commands  | NVMe over Fabrics    |
| Одиниця групування       | Target Port Group (TPG)| ANA Group Identifier |
| Спосіб виявлення         | Команда RTPG (0xA3)    | Асинхронний Asynch Event|
|                          | або сторінка VPD 0x83  | + Get Log Page 0x0C  |
| Реалізація в Linux       | dm-multipath +         | Вбудовано в драйвер  |
|                          | scsi_dh_alua           | nvme_core (Native MP)|
| Стани портів             | AO, ANO, SB, UN, TO    | Optimized, Non-Opt,  |
|                          |                        | Inaccessible, Change |
+──────────────────────────────────────────────────────────────────────────+
```

> 🔧 **Навіщо це.**
> ALUA перетворює фізичну асиметрію сховища з джерела аварій і деградацій на керований механізм підвищення надійності. Без ALUA будь-який багатошляховий доступ до сучасного двоконтролерного масиву перетворюється на вибір без вибору: або блокувати половину куплених портів у холодному простої, або втрачати продуктивність через постійний проксі-трафік міжконтролерної шини. Розуміння форматів RTPG/STPG, сенс-кодів переходів та поведінки модуля `scsi_dh_alua` дозволяє проектувати катастрофостійкі корпоративні кластери, виключати явища LUN Thrashing і гарантувати безперервну роботу баз даних під час планового оновлення мікропрограм чи раптових відмов дискових контролерів.
