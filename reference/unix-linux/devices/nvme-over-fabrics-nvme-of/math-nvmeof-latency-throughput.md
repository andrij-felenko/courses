# 🧮 Математичний розрахунок затримок та пропускної здатності NVMe/TCP та NVMe/RDMA

Ефективність мережевого блочного доступу у NVMe over Fabrics визначається сумарною затримкою передачі кадру (Latency Budget), доступною пропускною здатністю каналу (Throughput) та накладними витратами процесора хоста на інкапсуляцію пакетів. У цій вставці виведено точні математичні моделі порівняння транспорту NVMe/TCP та NVMe/RDMA.

## 1. Математична модель бюджету затримок (Latency Budget)

Загальний час обробки 4-кілобайтного запиту читання/запису `T_total` складається з п'яти основних компонентів:

```math
T_total = T_prop + T_ser + T_nic + T_kernel + T_nvm  [Формула сумарної затримки]
```

Де:
- `T_prop` — затримка поширення електромагнітного сигналу в оптичному волокні або мідному кабелі (Physical Propagation Delay).
- `T_ser` — затримка серіалізації бітового потоку у фізичний канал мережевого адаптера (Serialization Delay).
- `T_nic` — апаратна затримка обробки кадру в макросередках MAC/PHY та внутрішніх FIFO-буферах мережевої карти.
- `T_kernel` — затримка виконання програмного коду у ядрі операційної системи (проходження TCP/IP стека, робота підсистеми socket buffer `sk_buff` або обробка черг RDMA QP).
- `T_nvm` — апаратна затримка зчитування чи запису осередків flash-пам'яті віддаленого контролера SSD (NAND Controller Latency).

Фізична швидкість поширення світла у кварцовому склі оптичного волокна обмежується показником заломлення середовища (n ≈ 1.468). Швидкість сигналу становить близько 200 000 кілометрів на секунду, що додає приблизно 5 мікросекунд на кожен кілометр траси.

### Обчислення складових для 4-кілобайтного кадру у мережі 100 GbE:

1. Затримка поширення у оптичному волокні (`L = 100` м, `v_light = 2 * 10^8` м/с):

```math
T_prop = L / v_light  [Формула затримки поширення]
       = 100 / (2 * 10^8)  [Підстановка довжини кабелю та швидкості світла]
       = 0.5 мкс  [Підсумкова затримка поширення]
```

2. Затримка серіалізації кадру 4096 байтів + 106 байтів заголовків (`S_frame = 4202` байтів = 33 616 бітів, `B_link = 100` Гбіт/с):

```math
T_ser = S_frame / B_link  [Формула затримки серіалізації]
      = 33616 / (100 * 10^9)  [Підстановка розміру кадру у бітах та швидкості каналу]
      = 0.34 мкс  [Підсумкова затримка серіалізації]
```

При використанні менш швидкісних каналів (наприклад, 10 GbE) затримка серіалізації `T_ser` зростає у 10 разів і досягає 3.36 мікросекунди, що робить її вагомим чинником у загальному бюджеті затримок.

### Порівняльне рівняння затримок TCP vs RDMA

Для мережевого транспорту **NVMe/TCP**:

```math
T_total_tcp = T_prop + T_ser + T_nic_host + T_nic_target + T_kernel + T_nvm  [Сумарна затримка NVMe/TCP]
            = 0.5 + 0.34 + 2.0 + 2.0 + (15.0 + 20.0) + 80.0  [Підстановка чисельних компонентів у мікросекундах]
            = 119.84 мкс  [Підсумкова затримка обміну]
```

Для мережевого транспорту **NVMe/RDMA (RoCEv2)**:

```math
T_total_rdma = T_prop + T_ser + T_nic_host + T_nic_target + T_kernel + T_nvm  [Сумарна затримка NVMe/RDMA]
             = 0.5 + 0.34 + 1.2 + 1.2 + 0.0 + 80.0  [Підстановка чисельних компонентів у мікросекундах]
             = 83.24 мкс  [Підсумкова затримка обміну]
```

Вираховуємо виграш затримки при переході на RDMA:

```math
Delta_T = T_total_tcp - T_total_rdma  [Різниця затримок між TCP та RDMA]
        = 119.84 - 83.24  [Підстановка значень затримок]
        = 36.6 мкс  [Виграш за рахунок Kernel Bypass]
```

Цей виграш повністю формується за рахунок усунення затримки стека ядра `T_kernel` у режимі Kernel Bypass. Перехід у простір ядра Linux для виклику системних функцій `sys_sendmsg()` та `sys_recvmsg()`, обробка softirq і контекстні перемикання процесів додають від 30 до 40 мікросекунд на кожен мережевий запит.

## 2. Накладні витрати інкапсуляції та ефективність framing (Efficiency Ratio)

Корисна пропускна здатність мережі залежить від співвідношення корисного навантаження (Data Payload) до загального розміру переданих кадрів з урахуванням заголовків усіх рівнів L2–L7. Чим більший розмір корисного навантаження у кадрі, тим вищим є коефіцієнт корисної дії транспорту.

### Розмір заголовків кадру у NVMe/TCP:
- **Ethernet Header + VLAN + FCS:** 26 байтів (включає Преамбулу, SFD, MAC-адреси, 802.1Q тег та FCS).
- **IPv4 Header:** 20 байтів (стандартний заголовок мережевого рівня без опцій).
- **TCP Header:** 20 байтів (заголовок транспортного шару без вирівнювальних метушинок).
- **NVMe/TCP Common Header + C2HData Header:** 24 байти (заголовок PDU специфікації TP 8000).
- **Data Digest CRC32c + Header Digest:** 8 байтів (опціональні 32-бітні контрольні суми).
- **Загальний обсяг заголовків (`H_tcp`):** 98 байтів.

Коефіцієнт корисної дії (Framing Efficiency Ratio) для блоку даних 4096 байтів:

```math
Efficiency_tcp_4k = Payload / (Payload + H_tcp)  [Формула ефективності framing TCP]
                   = 4096 / (4096 + 98)  [Підстановка розміру блоку та заголовків]
                   = 4096 / 4194  [Сума байтів кадру]
                   = 97.66%  [Підсумковий коефіцієнт ефективності 4K]
```

При переході на дрібний розмір блоку 512 байтів ефективність суттєво падає через деградацію співвідношення даних до оверхеду:

```math
Efficiency_tcp_512 = Payload / (Payload + H_tcp)  [Формула ефективності framing для 512B]
                     = 512 / (512 + 98)  [Підстановка розміру 512B та заголовків]
                     = 512 / 610  [Сума байтів кадру]
                     = 83.93%  [Підсумковий коефіцієнт ефективності 512B]
```

### Розмір заголовків кадру у NVMe/RDMA (RoCEv2):
- **Ethernet + VLAN + FCS:** 26 байтів.
- **UDP Header:** 8 байтів (RoCEv2 загортається у протокол UDP для L3-маршрутизації).
- **RoCEv2 BTH (Base Transport Header):** 12 байтів (основний заголовок RDMA транспорту).
- **RDMA RETH (RDMA Extended Transport Header):** 16 байтів (передає віртуальну адресу та ключ `rkey`).
- **Invariant CRC (ICRC):** 4 байти (перевірка цілісності кадру на мережевих комутаторах).
- **Загальний обсяг заголовків (`H_roce`):** 66 байтів.

```math
Efficiency_roce_4k = Payload / (Payload + H_roce)  [Формула ефективності framing RoCEv2]
                    = 4096 / (4096 + 66)  [Підстановка розміру блоку 4K та заголовків]
                    = 4096 / 4162  [Сума байтів кадру]
                    = 98.41%  [Підсумковий коефіцієнт ефективності RoCEv2 4K]
```

## 3. Математичний розрахунок Jumbo Frames та зменшення навантаження на переривання

Використання стандартного значення MTU (1500 байтів) вимагає фрагментації 64-кілобайтного запису (`S_write = 65536` байтів) на декілька окремих Ethernet-кадрів. Кожне вхідне переривання від мережевого адаптера стимулює виконання обробника SoftIRQ у ядрі, що призводить до скидання системних кешів CPU.

1. **При стандартному MTU 1500 (`Payload = 1460` байтів):**

```math
N_pkts_1500 = ceil(65536 / 1460)  [Формула розрахунку кількості кадрів MTU 1500]
            = ceil(44.88)  [Обчислення дробової частки]
            = 45 пакетів  [Округлення до цілого числа кадрів]
```

2. **При Jumbo Frames MTU 9000 (`Payload = 8960` байтів):**

```math
N_pkts_9000 = ceil(65536 / 8960)  [Формула розрахунку кількості кадрів MTU 9000]
            = ceil(7.31)  [Обчислення дробової частки]
            = 8 пакетів  [Округлення до цілого числа кадрів]
```

Збільшення розміру кадрів до 9000 байтів скорочує кількість переданих пакетів у 5.6 разів.

Обчислення економії процесорних тактів на обробку переривань мережевої карти (Interruption Overhead Cost):

```math
C_saved = (N_pkts_1500 - N_pkts_9000) * C_pkt_header  [Рівняння економії тактів процесора]
        = (45 - 8) * 450  [Підстановка кількості пакетів та накладних витрат]
        = 37 * 450  [Множення різниці пакетів на витрати]
        = 16 650 тактів  [Підсумкова кількість заощаджених тактів CPU]
```

На кожну операцію запису розміром 64 КіБ застосування Jumbo Frames заощаджує понад 16 тисяч тактів процесора, що дозволяє суттєво підвищити масштабованість системи під високим навантаженням IOPS.

## 4. Вплив невтратності мережі (Lossless Ethernet, PFC та ECN) на RoCEv2

Протокол RoCEv2 відмовляється від механізмів повторної передачі кадрів на транспортному рівні TCP, тому навіть мінімальний відсоток втрати пакетів (`P_loss > 0.001%`) викликає паузи Go-Back-N і деградацію продуктивності на декілька порядків.

Для забезпечення невтратного середовища (Lossless Ethernet) використовується комбінація **PFC (Priority-based Flow Control)** та **ECN (Explicit Congestion Notification)**:

1. **Пороги спрацьовування PFC:** Мережевий комутатор при заповненні буфера порту на 80% надсилає кадр `PFC PAUSE` на віддалений порт, призупиняючи відправку нових кадрів.
2. **Маркування ECN:** При перевищенні середньої довжини черги `K_min` комутатор ставить позначку ECE в IP-заголовку кадру. Отримувач надсилає пакет CNP (Congestion Notification Packet), змушуючи передавача зменшити швидкість за алгоритмом DCQCN.

Математична модель розрахунку швидкості передавача `R_target` під дією ECN:

```math
R_target = R_current * (1 - Alpha / 2)  [Редукція швидкості передавача при отриманні CNP]
```

Де `Alpha` — коефіцієнт затору, що оновлюється на кожному кроці за виразом `alpha = (1 - g) * alpha + g * pi`. Використання тонкого налаштування ECN дозволяє підтримувати затримку на рівні 2–3 мкс без виникнення тупикових блокувань (PFC Deadlock). Мережева інфраструктура з правильно збалансованими параметрами ECN/PFC гарантує відсутність скидання пакетів у комутаторах.

## 5. Затримка зчитування дескрипторів SGL (Keyed SGL Fetch Delay)

На відміну від локального протоколу PCIe NVMe, де перші два покажчики PRP знаходяться у самому елементі SQE, при обробці некорисних (non-inlined) списків SGL мережевий контролер таргета змушений надсилати окремий запит читання пам'яті через шину PCIe.

Якщо командний блок оперує великим масивом неперервних даних, драйвер форматує таблицю SGL з декількох елементів.

Затримка отримання списку з 256 SGL-дескрипторів (`N_sgl = 256`):

```math
Size_sgl = N_sgl * 16  [Формула розміру таблиці SGL]
         = 256 * 16  [Підстановка кількості дескрипторів]
         = 4096 байтів  [Розмір сторінки SGL у байтах]
```

Час читання сторінки SGL через шину PCIe 4.0 x16 (`B_pcie = 31.5` ГБ/с):

```math
T_sgl_fetch = T_dma_req + (Size_sgl / B_pcie)  [Час вибірки дескрипторів з пам'яті]
            = 0.4 + (4096 / (31.5 * 10^9))  [Підстановка затримки DMA та пропускної здатності]
            = 0.4 + 0.13  [Сумування складових вибірки у мікросекундах]
            = 0.53 мкс  [Підсумкова затримка вибірки SGL]
```

Додаткова затримка 0.53 мікросекунди додається до кожного запиту, у якому використовується зовнішня таблиця SGL. Для мінімізації цієї затримки специфікація NVMe-oF дозволяє кодувати перший дескриптор безпосередньо всередині 64-байтного SQE (In-capsule SGL Descriptor).

## 6. Обчислення Bandwidth-Delay Product (BDP) та розміру TCP-вікна

Для повного завантаження 100-гігабітного мережевого каналу між хостом та віддаленим дисковим масивом розмір буфера сокета TCP (Socket Send/Receive Buffer) повинен покривати добуток пропускної здатності на круглу затримку RTT (Bandwidth-Delay Product). Якщо розмір вікна є меншим за BDP, передавач буде змушений призупиняти надсилання нових пакетів, очікуючи на підтвердження ACK від отримувача.

При RTT = 120 мікросекунд (`0.00012` с) та `B_network = 100` Гбіт/с (`12.5 * 10^9` Б/с):

```math
BDP = B_network * RTT  [Формула розрахунку BDP]
    = (12.5 * 10^9) * 0.00012  [Множення пропускної здатності на RTT]
    = 1 500 000 байтів  [Підсумковий мінімальний розмір TCP вікна 1.43 МіБ]
```

Якщо розмір TCP-вікна у параметрах ядра `net.ipv4.tcp_rmem` встановлено менше за 1.43 МіБ, пропускна здатність NVMe/TCP буде падати пропорційно обмеженню вікна за формулою:

```math
Throughput_max = TCP_Window / RTT  [Формула максимальної пропускної здатності TCP]
```

Наприклад, при стандартному розмірі вікна Linux `TCP_Window = 256` КіБ (262 144 байти):

```math
Throughput_max = 262144 / 0.00012  [Ділення вікна на RTT]
               = 2.18 * 10^9 Б/с  [Пропускна здатність у байтах на секунду]
               = 17.47 Гбіт/с  [Підсумкова швидкість каналу]
```

Це пояснює, чому без спеціального ручного налаштування мережевих буферів sysctl технологія NVMe/TCP може демонструвати лише 15–20% від реальної швидкості 100GbE адаптера. Для виправлення цього вузького місця параметри `tcp_rmem` та `tcp_wmem` підвищують до 32 або 64 Мегабайтів.

## 7. Витрати CPU на обчислення контрольних сум CRC32c

При виконанні софтверного захисту Digest у NVMe/TCP процесор хоста обчислює контрольні суми для кожного PDU кадру. Для прискорення обчислення CRC32c у сучасних процесорах x86_64 впроваджено апаратну інструкцію `crc32q`, яка обробляє по 8 байтів даних за один інструкційний такт.

Обчислення кількості інструкцій SSE4.2 / ARMv8 CRC32 для блоку 4096 байтів:

```math
C_crc = (Size_block / 8) * Latency_instruction  [Обчислення тактів CPU на CRC32c]
      = (4096 / 8) * 3  [Підстановка розміру блоку та латентності інструкції]
      = 512 * 3  [Множення кількості 64-бітних слів]
      = 1536 тактів CPU  [Сумарна кількість тактів на один блок 4К]
```

При інтенсивному навантаженні 1 000 000 IOPS обчислення CRC32c вимагає:

```math
F_crc_total = IOPS * C_crc  [Розрахунок частоти процесора на CRC32c]
            = 1000000 * 1536  [Множення IOPS на такти]
            = 1.536 * 10^9 тактів/с  [Підсумкова частота 1.536 ГГц]
```

Таким чином, увімкнення Data Digest без апаратного розвантаження Offload на SmartNIC споживає 1.5 ядра сучасного процесора виключно на математичний обрахунок контрольних сум. У продуктивних кластерах Data Digest рекомендується вимикати у межах захищеного стойкового комутатора або розвантажувати на апаратні SmartNIC.

## 8. Агрегація дверних дзвінків (Doorbell Batching & Aggregation)

При виконанні мільйонів операцій I/O на секунду системні виклики запису в Doorbell-регістр контролера через PCI MMIO створюють серйозне вузьке місце через затримку шини (PCIe Write Latency ≈ 0.4 мкс). З огляду на те, що кожна операція запису в MMIO вимагає синхронізації системної шини та очищення внутрішніх конвеєрів процесора, виконання індивідуального запису Doorbell на кожну 64-байтну капсулу SQE створює штучне обмеження продуктивності на рівні 2.5 млн IOPS для одного PCI-слота.

Для подолання цієї проблеми драйвери NVMe/TCP та NVMe/RDMA застосовують апаратний алгоритм **Doorbell Batching**. Замість активації Doorbell після кожної окремої команди драйвер підсистеми групує `N_batch` команд у єдину пакетну операцію. Драйвер оновлює лише підсумковий зсув кільцевого буфера у регістрі Doorbell після відправки всієї пачки капсул.

Математичне обчислення економії затримки при `N_batch = 16`:

```math
T_doorbell_saved = (N_batch - 1) * T_mmio_write  [Економія затримки дверних дзвінків]
                 = 15 * 0.4  [Множення кількості згрупованих команд на MMIO]
                 = 6.0 мкс  [Заощаджений час обробки пакета]
```

Агрегація дверних дзвінків у 16 разів зменшує кількість звернень до PCI MMIO регістрів, що дає змогу суттєво підвищити щільність IOPS на один мережевий сокет. Завдяки цій оптимізації процесор витрачає час не на очікування підтвердження транзакцій bus cycle, а на корисну обробку мережевих PDU та обслуговування черг користувацьких застосунків.

## 9. Розрахунок граничного показника IOPS на одне ядро CPU

Гранична продуктивність обробки кадрів NVMe/TCP одним процесорним ядром при частоті 3.2 ГГц (`F_cpu = 3.2 * 10^9` тактів/с) та середніх накладних витратах 1800 тактів на один кадр:

```math
IOPS_max_core = F_cpu / C_pkt  [Гранична кількість IOPS на одне ядро]
              = (3.2 * 10^9) / 1800  [Підстановка частоти та витрат тактів]
              = 1 777 777 IOPS  [Максимально можлива кількість IOPS на 1 ядро]
```

Для насичення 100GbE каналу дрібними блоками 4К потрібна пропускна здатність:

```math
Line_Rate = 12 500 000 000 Б/с  [Максимальна пропускна здатність 100GbE]
Block_Size = 4096 + 106  [Повний розмір кадру з заголовками 4202 Б]
```

Необхідна кількість IOPS для повного завантаження лінійного каналу 100GbE:

```math
IOPS_line_rate = Line_Rate / Block_Size  [Необхідний IOPS для 100GbE]
               = 12500000000 / 4202  [Ділення пропускної здатності на розмір кадру]
               = 2 974 773 IOPS  [Підсумковий IOPS лінійного каналу]
```

Розрахунок кількості процесорних ядер, необхідних для обробки мережевого потоку 100GbE NVMe/TCP:

```math
N_cores_required = IOPS_line_rate / IOPS_max_core  [Необхідна кількість ядер CPU]
                 = 2 974 773 / 1 777 777  [Ділення вимог каналу на продуктивність ядра]
                 = 1.67 cores  [Сумарна кількість ядер процесора]
```

Для порівняння, при NVMe/RDMA завдяки відсутності програмної обробки кадрів у ядрі навантаження на процесор хоста становить менше 0.1 ядра CPU незалежно від обсягу трафіку, оскільки апаратний мережевий адаптер виконує DMA-перенос пакетів без залучення ядер процесора.
