## Вступ: Природа випадковості в комп'ютерних системах

Комп'ютери є детермінованими машинами за своєю природою. Вони створені для того, щоб за однакових початкових умов та вхідних даних завжди видавати передбачуваний та повторюваний результат. Така детермінованість є фундаментальною перевагою для обчислень, проте вона стає критичною проблемою, коли мова заходить про криптографію, безпеку та генерацію унікальних ідентифікаторів. Криптографічні протоколи (наприклад, TLS, SSH), генерація ключів (RSA, ECDSA), солі для хешування паролів та механізми захисту пам'яті (такі як ASLR) покладаються на непередбачуваність випадкових чисел. Якщо зловмисник зможе передбачити або відтворити послідовність випадкових чисел, безпека всієї системи буде повністю скомпрометована.

У комп'ютерних науках розрізняють три основні категорії генераторів випадкових чисел (RNG):

1. **PRNG (Pseudo-Random Number Generator, псевдовипадковий генератор):** Алгоритм, який використовує математичну формулу для виробництва послідовності чисел. Послідовність здається випадковою, але повністю визначається початковим станом, який називається *seed* (зерно). Наприклад, лінійний конгруентний метод або алгоритм Вихор Мерсенна (Mersenne Twister). Вони швидкі і підходять для моделювання або ігор, але не для безпеки, оскільки, знаючи частину послідовності, можна вирахувати стан генератора і всі наступні числа.
2. **CSPRNG (Cryptographically Secure Pseudo-Random Number Generator, криптографічно стійкий псевдовипадковий генератор):** Особливий клас PRNG, розроблений таким чином, щоб зробити неможливим обчислення попередніх або наступних значень без знання внутрішнього стану (ключа). Навіть якщо зловмисник спостерігає терабайти згенерованих даних, він не зможе вгадати наступний біт із ймовірністю, значно більшою за 50%. Для підтримання безпеки CSPRNG необхідно періодично "пересідувати" (reseed) новими непередбачуваними даними.
3. **TRNG (True Random Number Generator, справжній генератор випадкових чисел):** Пристрій, що витягує випадковість з фізичних, квантових або теплових процесів, які є принципово непередбачуваними. Це може бути тепловий шум у резисторі, дробовий шум, розпад радіоактивних ізотопів або атмосферний шум. У контексті комп'ютерів такі пристрої називаються **HWRNG (Hardware Random Number Generator)**. Їх швидкість генерації зазвичай нижча, ніж у PRNG, тому в сучасних операційних системах TRNG не використовується безпосередньо для видачі даних прикладним програмам. Натомість TRNG використовується для збирання *ентропії* — сирої, непередбачуваної інформації, якою ініціалізується (seed) швидкий CSPRNG ядра.

Архітектура генерації випадкових чисел у ядрі Linux будується навколо безперервного збирання ентропії з фізичних процесів та її криптографічного перетворення за допомогою ChaCha20. Нижче розглянуто механізми функціонування підсистеми `hwrng`, просторового демону `rngd` (з пакету `rng-tools`), інструкцій процесорів сімейства x86 (`RDRAND`, `RDSEED`) та процесу змішування ентропії (`crng_reseed`).

## Еволюція підсистеми випадкових чисел у Linux

Розуміння сучасного стану справ з генерацією випадкових чисел у Linux неможливе без екскурсу в історію. Підсистема RNG у ядрі Linux зазнала фундаментальних змін, особливо у версіях 4.8 та 5.17+, оскільки старі парадигми виявилися невідповідними вимогам сучасного хмарного та вбудованого світу.

### Класична модель: /dev/random проти /dev/urandom

Протягом багатьох років (починаючи з розробки Теодора Ц'о у 1994 році) ядро Linux надавало два основні інтерфейси для користувацького простору: `/dev/random` та `/dev/urandom`.

Архітектура спиралася на концепцію **entropy pool** (пулу ентропії). Пул — це буфер у пам'яті ядра, у який змішується "шум" з різних джерел. Ядро збирало ентропію з таймінгів апаратних переривань (IRQ): час між натисканнями клавіш на клавіатурі, рухи миші, переривання від жорстких дисків та мережевих карт. Кожна така подія додавала кілька бітів ентропії, і ядро ретельно підраховувало "оцінку ентропії" (entropy estimate).

Дані з пулу видавалися користувачеві через два пристрої з різною поведінкою:
- **`/dev/random`**: Цей пристрій вважався джерелом "абсолютної" випадковості. Він видавав дані лише тоді, коли внутрішній лічильник ентропії був більшим за нуль. Кожен прочитаний байт зменшував оцінку ентропії. Якщо ентропія вичерпувалась, виклики `read()` до `/dev/random` **блокувалися**, поки користувач не посуває мишею або диск не згенерує нові переривання. Це створювало величезні проблеми для безголових (headless) серверів без миші та клавіатури, де генерація ключів могла зависнути на години.
- **`/dev/urandom` (unlimited random):** Цей пристрій не блокувався ніколи. Він брав ентропію з пулу для ініціалізації CSPRNG (базованого на хеш-функції SHA-1). Якщо сира ентропія вичерпувалась, `/dev/urandom` продовжував видавати криптографічно надійні псевдовипадкові числа. 

Протягом довгого часу розробникам рекомендували використовувати `/dev/random` для генерації довготривалих GPG/SSH ключів, а `/dev/urandom` — для всього іншого. Проте з розвитком криптографії стало зрозуміло, що ця дихотомія є хибною. Криптографічний PRNG, якщо його хоча б раз ініціалізувати справжньою ентропією у 256 біт, ніколи не потребуватиме "поповнення" ентропії, щоб залишатися непередбачуваним. Блокування `/dev/random` базувалося на теоретико-інформаційній парадигмі, яка недооцінювала обчислювальну стійкість криптографічних алгоритмів. 

### Сучасна модель: crng та уніфікація

Ядро Linux версії 4.8 здійснило перший значний крок: заміну старого PRNG на базі SHA-1 на новий, швидший та безпечніший алгоритм **ChaCha20** (потоковий шифр). Новий дизайн отримав назву **crng** (Cryptographic Random Number Generator). ChaCha20 ідеально підходить для цього завдання: він швидкий, стійкий до атак побічних каналів (timing attacks) і легко векторизується на сучасних процесорах.

Згодом, у ядрі 5.17, розробник Джейсон Доненфельд (автор WireGuard, який став новим мейнтейнером підсистеми `/dev/random`) провів масивний рефакторинг. Найважливіша зміна полягала в повній відмові від блокуючої поведінки `/dev/random` після початкової ініціалізації пулу. Крім того, функцію змішування було переведено з SHA-1 на надшвидку хеш-функцію **BLAKE2s**.

Сьогодні архітектура працює так:
1. При завантаженні системи crng знаходиться в неініціалізованому стані.
2. Ядро активно збирає ентропію з HWRNG, RDRAND, Jitter, таймінгів переривань тощо.
3. Як тільки зібрано 256 біт надійної ентропії, crng переходить у стан "ініціалізовано" (crng is ready).
4. Відтепер і `/dev/random`, і `/dev/urandom` видають дані з алгоритму ChaCha20 і **ніколи не блокуються**.
5. Ядро продовжує збирати ентропію у фоновому режимі та періодично оновлює ключ ChaCha20 (процес crng_reseed), щоб захиститися від компрометації стану (forward secrecy) та відновлення після знімків віртуальних машин (VM snapshots).

Єдина відмінність, що залишилася між `/dev/urandom` і `/dev/random` у сучасному ядрі Linux (починаючи з 5.6) — це поведінка на етапі раннього завантаження (early boot), коли 256 біт ентропії ще не зібрано. У цей короткий проміжок часу `/dev/random` блокується до ініціалізації crng, тоді як `/dev/urandom` видає числа, що можуть бути передбачуваними (використовуючи попередній, не до кінця випадковий стан). На практиці розробникам рекомендується використовувати системний виклик `getrandom()`, який блокується до ініціалізації пулу, а потім завжди працює швидко і надійно.

Детальніше про три десятиліття розробки та причини відмови від підрахунку ентропії див. у вставці [історичний розвиток суперечки про блокування /dev/random](book:unix-linux/hwrng-hardware-random-number-generator/hist-blocking-random.md).

## Проблема Early Boot Entropy (Ентропія раннього завантаження)

Одним з найсерйозніших викликів для архітектури генерації випадкових чисел є збирання ентропії одразу після увімкнення системи. Сучасні системи (зокрема віртуальні машини в хмарі, контейнери або вбудовані IoT-пристрої без жорстких дисків) завантажуються за лічені секунди або мілісекунди. Протягом цього часу генеруються криптографічні ключі (наприклад, ключі хоста SSH), і якщо ентропії недостатньо, ці ключі будуть слабкими і вразливими до зламу.

У віртуальних машинах проблема посилюється відсутністю реальних апаратних переривань. Миші немає, клавіатури немає, мережа працює віртуально і має дуже передбачувані таймінги. Як наслідок, ініціалізація `crng` може затримуватись на хвилини, блокуючи завантаження системних сервісів (systemd активно використовує `getrandom()` під час запуску демонів).

Для вирішення цієї проблеми Linux використовує кілька механізмів:
1. **Збережений seed-файл (Seed file):** Під час завершення роботи системи, дистрибутиви (через `systemd-random-seed.service`) зберігають 256 байт випадкових даних у файл `/var/lib/systemd/random-seed`. При наступному завантаженні цей файл читається і записується в пул ядра через ioctl `RNDADDENTROPY`. Ядро не знає, наскільки секретним є цей файл (можливо, його скопіювали разом з образом ВМ), тому це допомагає, але не завжди зараховується до "криптографічної ентропії", доки ядро не буде впевнене.
2. **Jitter Entropy:** Сучасні процесори мають надзвичайно складну мікроархітектуру: кеші, конвеєри передбачення розгалужень (branch prediction), зміна тактових частот, температурний троттлінг. Через це точний час виконання навіть найпростішої інструкції коливається на наносекунди (jitter). Ядро Linux включає в себе алгоритм (через опцію `CONFIG_CRYPTO_JITTERENTROPY`), який вимірює ці крихітні варіації часу і витягує з них ентропію. Це працює навіть у віртуальних машинах і гарантує швидку ініціалізацію пулу без зовнішніх пристроїв.
3. **virtio-rng:** Для віртуальних машин гіпервізор (KVM, QEMU) може експортувати випадкові числа з хостової машини (яка має багатий пул ентропії) всередину гостьової ОС через віртуальний PCI-пристрій `virtio-rng`. У гостьовій системі він виглядає як апаратний RNG.
4. **Апаратні генератори (HWRNG):** Модулі, вбудовані безпосередньо в материнські плати або процесори (TPM, RDRAND). Вони надають високу ентропію миттєво після ввімкнення живлення.

## Апаратні генератори: Підсистема hwrng

Для уніфікації роботи з різноманітними апаратними генераторами випадкових чисел, ядро Linux містить підсистему (фреймворк) **hwrng** (Hardware RNG). Її завдання — надати стандартизований інтерфейс для драйверів пристроїв і експортувати сирі випадкові дані до простору користувача та пулу ядра.

![Архітектура HWRNG у Linux](/reference/unix-linux/devices/hwrng-hardware-random-number-generator/img/hwrng-architecture.svg)
*Архітектура підсистеми апаратних генераторів випадкових чисел (hwrng) та її зв'язок із пулом ентропії ядра Linux і простором користувача.*

### Фізичні принципи HWRNG

На відміну від PRNG, справжні HWRNG використовують фізичні процеси на рівні кремнію. Деякі поширені джерела випадковості в мікросхемах:
- **Тепловий шум (Thermal noise / Johnson-Nyquist noise):** Випадковий рух електронів у провіднику під впливом температури генерує флуктуації напруги. Ці мікровольти підсилюються компараторами і переводяться в цифрові біти.
- **Шум лавинного пробою (Avalanche noise):** Струм, що протікає через p-n перехід діода у зворотному напрямку на межі пробою, має дуже високу непередбачуваність і генерує сильний шум.
- **Кільцеві осцилятори (Ring oscillators):** Непарна кількість інверторів, з'єднаних у кільце, генерує високочастотний меандр. Якщо розмістити кілька таких осциляторів поруч і знімати різницю фаз між ними (яка плаває через теплові флуктуації та нестабільність живлення), можна отримати відмінне джерело ентропії. Цей підхід є найбільш поширеним у сучасних SoC, оскільки він легко реалізується стандартними логічними вентилями без спеціальних аналогових компонентів.

### Драйвери hwrng у ядрі

Кожен апаратний модуль (наприклад, чіпсет Intel, модуль TPM, SoC Raspberry Pi) має власний драйвер у директорії `drivers/char/hw_random/`. Ці драйвери реалізують структуру `struct hwrng` і реєструють себе у фреймворку за допомогою функції `hwrng_register()`. Повний опис структури `struct hwrng`, реєстраційних функцій ядра та sysfs-інтерфейсу див. у вставці [інтерфейс драйверів hwrng та параметри sysfs](book:unix-linux/hwrng-hardware-random-number-generator/api-hwrng-framework.md).

Структура `hwrng` виглядає приблизно так (спрощено):

```c
struct hwrng {
    const char *name;
    int (*init)(struct hwrng *rng);
    void (*cleanup)(struct hwrng *rng);
    int (*data_present)(struct hwrng *rng, int wait);
    int (*data_read)(struct hwrng *rng, u32 *data);
    int (*read)(struct hwrng *rng, void *data, size_t max, bool wait);
    unsigned short quality; /* Оцінка якості ентропії з 1024 */
};
```

Найважливішим параметром тут є `quality`. Він визначає, наскільки розробник драйвера довіряє апаратному джерелу. Значення 1024 означає 1 біт ентропії на кожен біт даних. Значення 0 означає, що джерело є вкрай низькоякісним і його дані не повинні автоматично підвищувати рівень ентропії ядра.

Підсистема `hwrng` створює символьний пристрій `/dev/hwrng`. Цей файл експортує **сирі дані** з апаратного генератора, без будь-якої криптографічної обробки або змішування. **Читати з `/dev/hwrng` безпосередньо прикладними програмами КАТЕГОРИЧНО НЕ РЕКОМЕНДУЄТЬСЯ**. Апаратні генератори схильні до поломок. Сильні електромагнітні поля, екстремальні температури або дефекти старіння мікросхеми можуть призвести до того, що HWRNG почне видавати постійні нулі або детерміновані патерни (наприклад, `01010101`). Якщо криптографічний застосунок (наприклад, OpenSSL) прочитає ці сирі дані, він згенерує вразливі ключі.

Натомість, ядро Linux містить вбудований потік (kthread) `hwrng-fill`, який періодично читає дані з апаратного RNG і передає їх у функцію `add_hwgenerator_randomness()`. Ця функція не просто додає дані, вона пропускає їх через хеш-функцію BLAKE2s, змішуючи з поточним пулом. Навіть якщо HWRNG повністю зламався і видає нулі, хеш-функція гарантує, що вихідний пул залишається таким же безпечним, яким він був до змішування (оскільки нулі криптографічно змішуються зі старим секретним станом).

## Інструкції RDRAND та RDSEED в архітектурі x86

Intel (починаючи з мікроархітектури Ivy Bridge) та AMD реалізували генератор випадкових чисел безпосередньо у кристалі процесора і зробили його доступним через спеціальні машинні інструкції. Це забезпечує безпрецедентну пропускну здатність ентропії (гігабайти на секунду), яка доступна будь-якому процесу в просторі користувача без системних викликів. 

### RDRAND (Random Data)

`RDRAND` — це інструкція, яка повертає 16-, 32- або 64-бітне випадкове число. На апаратному рівні реалізація виглядає так:
1. **TRNG (Джерело ентропії):** Використовуються метастабільні засувки (metastable latches), стан яких визначається тепловим шумом. 
2. **Conditioning (Кондиціонування):** Сирі біти проходять через апаратний криптографічний блок (AES-CBC-MAC), який стискає їх і видаляє будь-яке статистичне зміщення (bias).
3. **DRBG (Deterministic Random Bit Generator):** Відбілена ентропія періодично (тисячі разів на секунду) ініціалізує (seeding) апаратний генератор псевдовипадкових чисел AES-CTR (на базі шифру AES-128 або AES-256 в режимі лічильника).
4. `RDRAND` читає дані з цього PRNG. 

Тобто `RDRAND` — це **CSPRNG**, вбудований у процесор, який безперервно пересідується. Він надзвичайно швидкий, але не дає доступу до "сирої" ентропії.

### RDSEED (Seed Data)

Інструкція `RDSEED` була додана пізніше (у мікроархітектурі Broadwell). На відміну від RDRAND, вона обходить стадію AES-CTR PRNG і повертає числа після стадії кондиціонування (AES-CBC-MAC). Таким чином, `RDSEED` надає **повну (Multiplicative) ентропію**. 

Якщо кілька ядер CPU одночасно бомбардують інструкцію `RDSEED`, вона може повернути помилку (через прапорець процесора Carry Flag), оскільки фізичний генератор не встигає виробляти достатньо справжньої ентропії. `RDRAND` ніколи не відчуває такого "голодування", бо він просто обертає алгоритм AES. 

Основне призначення `RDSEED` — бути джерелом (seed) для програмних CSPRNG (наприклад, для ініціалізації пулу Linux `crng`).

### Проблема довіри та рішення Лінуса Торвальдса

Коли `RDRAND` був представлений, виникла масова стурбованість у криптографічній спільноті. Специфікація є закритою, а алгоритм реалізований апаратно. Після витоків Едварда Сноудена (щодо бекдорів АНБ у генераторі Dual_EC_DRBG), розробники почали ставити питання: *А що, якщо Intel навмисно зробила RDRAND передбачуваним для спецслужб? А що, якщо він містить майстер-ключ, який дозволяє відновити весь внутрішній стан?*

Деякі розробники вимагали від Лінуса Торвальдса видалити підтримку `RDRAND` з ядра Linux. Відповідь Торвальдса стала класикою інженерного прагматизму. Він відмовився видаляти RDRAND, зазначивши, що ядро **не використовує RDRAND як єдине джерело випадковості**. 

Ядро Linux викликає макроси `arch_get_random_long()` (використовує RDRAND) та `arch_get_random_seed_long()` (використовує RDSEED) і **змішує** їхній результат з основним пулом за допомогою хеш-функції:

```c
long val;
if (arch_get_random_seed_long(&val)) {
    /* Змішуємо val з існуючим станом через BLAKE2s або XOR */
    crng_fast_key_erasure(...); 
}
```

Математика криптографічних хеш-функцій гарантує: якщо ви берете безпечний випадковий стан пулу і XOR-ите (або хешуєте) його з будь-якими даними від RDRAND (навіть якщо вони детерміновані, керовані зловмисником або складаються з суцільних нулів), вихідний результат буде **не менш безпечним, ніж початковий пул**. Якщо ж RDRAND чесний, то ентропія пулу лише зростає. 

Таким чином, Linux отримує максимальну користь від RDRAND, нівелюючи будь-які ризики потенційних апаратних бекдорів.

## Демон rng-tools (rngd)

Хоча сучасне ядро може самостійно забирати дані з HWRNG і пушити їх у crng, роль простору користувача залишається важливою. За це відповідає пакет `rng-tools` та його основний демон **`rngd`**.

`rngd` (Random Number Generator Daemon) — це фоновий процес, який діє як міст між різними джерелами ентропії (як апаратними, так і програмними) та ядром Linux. Його головне завдання — **перевірка якості даних перед їх додаванням до ядра**.

### Архітектура та джерела rngd

При запуску `rngd` ініціалізує кілька "джерел ентропії" (entropy sources). Серед найпопулярніших:
- **`hwrng`:** Читає сирі дані з `/dev/hwrng`.
- **`tpm`:** Читає ентропію з модуля Trusted Platform Module через пристрій `/dev/tpm0`. TPM має власний апаратний RNG, сертифікований для криптографії.
- **`pkcs11`:** Використовує апаратні токени або смарт-карти (наприклад, YubiKey) через стандартний криптографічний API.
- **`jitter`:** Використовує бібліотеку Jitterentropy API (JENT), яка вимірює варіації часу виконання потоків CPU. Це життєво необхідно на серверах або ВМ, які не мають апаратного HWRNG.
- **`rdrand`:** Використовує інструкції RDRAND/RDSEED безпосередньо.

### Статистичне тестування FIPS 140-2

Чому б просто не направити потік з `/dev/hwrng` безпосередньо в `/dev/random` за допомогою `cat`? Як зазначалося раніше, апаратні компоненти можуть вийти з ладу. Щоб запобігти отруєнню пулу детермінованими даними (entropy poisoning), `rngd` пропускає кожен блок зчитаних даних через набір статистичних тестів, визначених у федеральному стандарті США **FIPS 140-2 (додаток D)** або його сучасніших аналогах від NIST.

Основні тести, які виконує `rngd` у реальному часі:
1. **The Monobit Test (Тест монобіту):** Рахує кількість одиниць і нулів у блоці з 20,000 біт. Кількість одиниць має бути в межах від 9,725 до 10,275 (приблизно 50%). Якщо генератор видає суцільні 1 або 0, тест провалиться.
2. **The Poker Test (Покерний тест):** Блок ділиться на послідовності по 4 біти (нібли, від `0000` до `1111`). Тест підраховує частоту появи кожного з 16 можливих значень. У справді випадковій послідовності частота всіх 16 комбінацій має бути приблизно однаковою, як рівномірне випадіння карт у покері.
3. **The Runs Test (Тест серій):** Підраховує довжину "серій" поспіль йдучих нулів або одиниць (наприклад, `000` — серія з 3 нулів). Стандарт очікує певну кількість серій довжиною 1, 2, 3, 4 тощо. Якщо є занадто багато довгих серій (або їх взагалі немає), тест не пройдено.
4. **The Long Run Test (Тест довгої серії):** Шукає серії з 26 або більше однакових бітів поспіль. У блоці з 20,000 біт ймовірність такої події мізерно мала. Якщо знайдено — обладнання вважається несправним.

Якщо блок даних не проходить будь-який з цих тестів, `rngd` відкидає його і виводить повідомлення про помилку в syslog. Якщо тест пройдено, дані вважаються криптографічно безпечними і передаються до ядра.

### Запис ентропії в ядро: ioctl(RNDADDENTROPY)

Щоб передати перевірену ентропію до пулу ядра, `rngd` відкриває `/dev/random` для запису і викликає спеціальний системний виклик `ioctl` з командою `RNDADDENTROPY`.

Структура даних, що передається в ядро, має такий вигляд:
```c
struct rand_pool_info {
    int entropy_count;    /* Оцінка якості ентропії в бітах */
    int buf_size;         /* Розмір буфера даних у байтах */
    __u32 buf[0];         /* Самі випадкові дані */
};
```
Демон явно вказує ядру, скільки *реальної ентропії* (в бітах) він додає. Ядро змішує `buf` у свій внутрішній стан і збільшує внутрішній лічильник ентропії на `entropy_count`. Це дозволяє ядру швидше розблокувати системний виклик `getrandom()`.

Повний код власної користувацької утиліти статистичного контролю та поповнення пулу ядра мовами C та C++ див. у вставці [практична реалізація утиліти зчитування та FIPS-тестування](book:unix-linux/hwrng-hardware-random-number-generator/proj-entropy-feeder.md).

## crng_reseed: Як оновлюється криптографічний стан

Змішування ентропії у Linux не є одноразовим процесом. Сучасний алгоритм `crng` використовує потоковий шифр ChaCha20. ChaCha20 генерує нескінченний потік псевдовипадкових байт на основі 256-бітного ключа та 64-бітного лічильника/nonce.

Щоб система була безпечною від теоретичних атак, ключ ChaCha20 не повинен бути постійним. Він повинен періодично змінюватися за рахунок нової свіжої ентропії з пулу. Цей процес називається **reseed** (пересідування).

Функція `crng_reseed()` в ядрі Linux (файл `drivers/char/random.c`) працює за таким алгоритмом:
1. Забирає поточні зібрані дані з вхідного пулу ентропії (який змішувався через BLAKE2s з подій переривань, RDRAND, hwrng тощо).
2. Забирає трохи даних з поточного виходу ChaCha20, щоб прив'язати новий стан до старого (це гарантує, що новий стан завжди не гірший за попередній).
3. Виконує функцію криптографічного перемішування, генеруючи новий 256-бітний ключ.
4. Встановлює цей новий ключ як робочий ключ для генератора ChaCha20 та скидає його лічильник.
5. Зберігає час останнього пересідування.

Ядро запускає `crng_reseed()` примусово кожні 5 хвилин (за умови, що з'явилася нова ентропія). Це гарантує так звану **Forward Secrecy** (пряму секретність): якщо в якийсь момент часу зловмисник зможе прочитати пам'ять ядра і дізнатись ключ ChaCha20 (наприклад, через експлойт або холодну перезавантаження пам'яті), він зможе передбачити *майбутні* числа, але не зможе вирахувати *минулі* числа (бо старий ключ був знищений, а процес хешування є незворотнім). Наступний `crng_reseed()` через 5 хвилин ізолює зловмисника і від майбутніх даних.

## Практичні аспекти: Адміністрування RNG

Розуміння роботи HWRNG є критичним для системних адміністраторів. Неправильно налаштована підсистема випадкових чисел може призвести до вразливостей SSL/TLS, повільного старту системи або слабких SSH ключів.

### Перевірка стану ентропії

Основним індикатором здоров'я підсистеми є лічильник ентропії (оцінка якості пулу). Його можна перевірити за допомогою `sysctl` або читаючи файли в `/proc`:

```bash
$ cat /proc/sys/kernel/random/entropy_avail
256
```
У старих ядрах (до 5.17) це число коливалося від 0 до 4096. Адміністратори часто панікували, коли воно падало нижче 200, вважаючи, що серверу бракує ентропії, і встановлювали сторонні утиліти на кшталт `haveged`. 

У сучасному ядрі Linux (5.17+) концепцію "вичерпання ентропії" повністю скасовано. Число `entropy_avail` зазвичай дорівнює **256**. Це не означає, що залишилось лише 256 байт! Це просто свідчить про те, що crng має достатній 256-бітний криптографічний ключ (рівень безпеки ChaCha20/AES-256). Після ініціалізації пулу це значення більше не зменшується при читанні з `/dev/random`. Тому встановлення старих демонів на кшталт `haveged` на сучасних дистрибутивах є антипатерном.

Перевірити, які джерела апаратної ентропії доступні та активні, можна в sysfs:

```bash
# Перегляд доступних драйверів HWRNG
$ cat /sys/class/misc/hw_random/rng_available
tpm-rng intel-rng 

# Перегляд активного драйвера HWRNG, з якого зараз читає hwrng-fill
$ cat /sys/class/misc/hw_random/rng_current
tpm-rng
```

### Використання rng-tools

Якщо ваш сервер базується на відносно сучасному залізі, ядро само впорається зі збором ентропії. Але у віртуальних машинах, Docker-контейнерах або Raspberry Pi пакет `rng-tools` може стати в нагоді для використання `jitterentropy` або специфічних HWRNG.

Встановлення та запуск у системах на базі Debian/Ubuntu:
```bash
$ sudo apt install rng-tools
$ sudo systemctl enable --now rng-tools-debian
```
Перевірити логі роботи демона і результати тестів FIPS:
```bash
$ journalctl -u rng-tools-debian -n 50
```

## Висновок

Підсистема генерації випадкових чисел у Linux є яскравим прикладом еволюції архітектури під тиском сучасних криптографічних реалій. Відмовившись від парадигми "дефіциту ентропії" та блокування `/dev/random`, спільнота розробників ядра вирішила багаторічні проблеми продуктивності.

Сучасний дизайн елегантно поєднує швидкість потокового шифру ChaCha20, надійність криптографічних хешів BLAKE2s та непередбачуваність фізичних явищ, які забезпечують апаратні модулі (HWRNG, RDRAND, TPM, Jitter). Навіть якщо один з апаратних генераторів має прихований бекдор, строге математичне змішування в пулі ентропії (entropy pool) нейтралізує загрозу, роблячи Linux одним із найбезпечніших середовищ для криптографічних операцій. Розуміння ролі `/dev/hwrng` та `rng-tools` дозволяє архітекторам систем гарантувати, що їхні віртуальні машини та IoT-пристрої ніколи не генеруватимуть слабких ключів під час першого завантаження.
