# 🧮 Кількісний аналіз P2PDMA: пропускна здатність, затримки та оверхед TLP

У цій математичній вставці наведено кількісні та формальні фізичні моделі продуктивності передавання даних між пристроями PCIe. У ній детально виведено формули розвантаження системної оперативної пам'яті (RAM), розраховано накладні витрати заголовків пакетів транзакційного рівня (TLP Overhead) залежно від розміру Max Payload Size, а також побудовано математичну модель затримок (Latency Analysis) для порівняння проходження трафіку через хост та прямого проходження P2PDMA.

## 1. Математична модель розвантаження шини системної оперативної пам'яті

Для оцінки ефективності P2PDMA розглянемо потік даних загальним обсягом `D` байтів, який необхідно переслати від пристрою-джерела (наприклад, NVMe SSD) до пристрою-призначення (наприклад, GPU VRAM або SmartNIC) протягом часу `t`.

### Традиційна модель з транзитом через хост (Bounce Buffer)

У традиційній схемі без підтримки P2PDMA передача даних вимагає проведення двох послідовних операцій прямого доступу до пам'яті через контролер пам'яті центрального процесора (CPU Memory Controller):

1. Джерело (NVMe SSD) ініціює DMA-запис даних `D` у буфер хоста, виділений у системній оперативній пам'яті (RAM).
2. Призначення (GPU або SmartNIC) ініціює DMA-читання тих самих даних `D` із системної оперативної пам'яті хоста.

Оскільки кожна комірка оперативної пам'яті при першій операції піддається циклу запису, а при другій операції — циклу читання, сумарний обсяг даних `B_RAM`, проведений через фізичну шину оперативної пам'яті хоста, обчислюється як сума обох транзакцій:

```
B_RAM = D_write + D_read
= D + D            [кожен байт передається двічі: один запис, одне читання]
= 2·D              [подвійне навантаження на шину пам'яті]
```

Швидкість споживання смуги пропускання оперативної пам'яті `BW_RAM` при постійній швидкості передачі джерела `R = D / t` (вимірюється в Гігабайтах за секунду):

```
BW_RAM = B_RAM / t
= (2·D) / t        [підстановка сумарного обсягу B_RAM = 2·D]
= 2·(D / t)        [винесення постійного множника 2 за дужки]
= 2·R              [заміна частки D/t на швидкість джерела R]
```

Таким чином, для передачі даних зі швидкістю `R` системна шина пам'яті мусить виділити смугу пропускання `2·R`. Якщо масив NVMe-накопичувачів зчитує дані зі швидкістю `R = 50 ГБ/с`, системна оперативна пам'ять втрачає `100 ГБ/с` своєї пропускної здатності лише на утримання транзитного буфера.

### Розрахунок завантаження контролера пам'яті DDR5

Сучасна двоканална або восьмиканальна оперативна пам'ять DDR5 забезпечує теоретичний пік пропускної здатності `BW_MAX_RAM`. Наприклад, для 8-канальної системи DDR5-4800:

```
BW_MAX_RAM = 8 · 4.8 GT/s · 8 Bytes
= 307.2 ГБ/с      [теоретична пікова пропускна здатність RAM]
```

Частка завантаження контролера пам'яті `U_RAM` при традиційному транзиті даних I/O на швидкості `R = 64 ГБ/с`:

```
U_RAM = BW_RAM / BW_MAX_RAM
= (2 · 64) / 307.2  [підстановка BW_RAM = 2·R = 128 ГБ/с]
= 128 / 307.2       [ділення обсягів]
≈ 0.4167            [або 41.67% всієї пам'яті сервера]
```

Традиційний транзит I/O поглинає понад 41.6% усієї пропускної здатності серверної RAM.

### Модель з використанням PCIe P2PDMA

При використанні підсистеми P2PDMA транзакційні пакети TLP передаються напряму від джерела до призначення через матрицю комутатора PCIe або мости Root Complex. Сумарний обсяг даних, проведений через контролер системної RAM `B_P2P`, дорівнює нулю:

```
B_P2P = 0
BW_RAM_P2P = 0
U_RAM_P2P = 0
```

Абсолютна економія пропускної здатності оперативної пам'яті системного процесора `ΔBW_RAM`:

```
ΔBW_RAM = BW_RAM - BW_RAM_P2P
= 2·R - 0          [віднімання прямого шляху]
= 2·R              [100% вивільнення шини RAM від I/O трафіку]
```

Вивільнена смуга пропускання `2·R` залишається повністю доступною для процесорних ядер CPU, усуваючи затримки арбітражу кеш-пам'яті L3 та контролера пам'яті.

## 2. Аналіз ефективності пакетів PCIe TLP та оверхед заголовків

На транзакційному рівні PCIe (Transaction Layer) дані передаються у вигляді стандартних пакетів TLP. Кожен пакет містить службовий заголовок (Header), корисне навантаження (Payload) та службову контрольну суму LCRC (Link CRC).

Структура TLP-пакета для 64-бітної адресації пам'яті:
- **Header (`H`):** 16 байтів (містить тип транзакції, прапорці, ідентифікатор Requester ID, довжину та 64-бітну адресу призначення).
- **LCRC (`C`):** 4 байти (32-бітна контрольна сума для перевірки цілісності пакета на фізичному рівні).
- **Payload (`P`):** Корисні дані, розмір яких обмежено параметром Max Payload Size (MPS).

Загальний обсяг одного TLP-пакета `S_TLP` у байтах:

```
S_TLP = H + P + C
= 16 + P + 4       [підстановка розмірів заголовка H=16 та LCRC C=4]
= P + 20           [зведення числових констант]
```

Коефіцієнт корисного використання фізичної смуги пропускання шини PCIe `η_TLP`:

```
η_TLP = P / S_TLP
= P / (P + 20)     [підстановка загального розміру пакета S_TLP]
```

Накладні витрати заголовків (TLP Overhead) `Overhead_TLP` у відсотках:

```
Overhead_TLP = (1 - η_TLP)·100%
= (1 - P / (P + 20))·100%
= (20 / (P + 20))·100% [зведення до спільного знаменника]
```

Обчислимо ефективність `η_TLP` та оверхед для п'яти конфігурацій Max Payload Size (MPS):

### Випадок 1: MPS = 128 байтів (мінімальний розмір для багатьох систем)

```
η_128 = 128 / (128 + 20)
= 128 / 148        [сума у знаменнику]
≈ 0.86486          [або 86.49% ефективності]
```

```
Overhead_128 = 20 / (128 + 20)
= 20 / 148         [обчислення частки оверхеду]
≈ 0.13514          [або 13.51% втрат на заголовки]
```

При MPS = 128 байтів понад 13.5% усієї смуги пропускання шини PCIe витрачається на передачу службових заголовків TLP.

### Випадок 2: MPS = 256 байтів (стандарт для більшості NVMe SSD)

```
η_256 = 256 / (256 + 20)
= 256 / 276        [сума у знаменнику]
≈ 0.92753          [або 92.75% ефективності]
```

```
Overhead_256 = 20 / (256 + 20)
= 20 / 276         [обчислення частки оверхеду]
≈ 0.07247          [або 7.25% втрат на заголовки]
```

Збільшення MPS до 256 байтів знижує накладні витрати на заголовки майже вдвічі (до 7.25%).

### Випадок 3: MPS = 512 байтів (високопродуктивні PCIe Switches та GPU)

```
η_512 = 512 / (512 + 20)
= 512 / 532        [сума у знаменнику]
≈ 0.96240          [або 96.24% ефективності]
```

```
Overhead_512 = 20 / (512 + 20)
= 20 / 532         [обчислення частки оверхеду]
≈ 0.03760          [або 3.76% втрат на заголовки]
```

При MPS = 512 байтів ефективність використання шини досягає 96.24%, а оверхед становить менше 3.8%.

### Випадок 4: MPS = 1024 байти (спеціалізовані FPGA та прискорювачі)

```
η_1024 = 1024 / (1024 + 20)
= 1024 / 1044      [сума у знаменнику]
≈ 0.98084          [або 98.08% ефективності]
```

При MPS = 1024 байти втрати на заголовки знижуються до `1.92%`.

## 3. Математична модель затримок транспорту (Latency Analysis)

Розглянемо повну фізичну затримку виконання операції прямого передавання блоку даних між накопичувачем NVMe та прискорювачем GPU.

Позначення фізичних компонентів затримки:
- `t_nvme`: Внутрішня затримка зчитування даних із флеш-пам'яті/SRAM контролера NVMe.
- `t_gpu`: Затримка розміщення даних у вхідному буфері контролера пам'яті GPU VRAM.
- `t_sw`: Затримка проходження TLP через один фізичний хоп комутатора PCIe Switch (зазвичай 100–150 нс).
- `t_rc`: Затримка проходження TLP через мости Root Complex та перевірку IOMMU (зазвичай 250–400 нс).
- `t_ram`: Затримка повного циклу запису та зчитування системної оперативної пам'яті хоста DDR5 з урахуванням арбітражу кешу CPU та меж когерентності (зазвичай 1.5–3.5 мкс).

### Традиційна модель (Bounce Buffer через RAM хоста)

Траєкторія TLP-пакета: NVMe → PCIe Switch → Root Complex → CPU RAM → Root Complex → PCIe Switch → GPU.

Загальна затримка `T_bounce`:

```
T_bounce = t_nvme + t_sw + t_rc + t_ram + t_rc + t_sw + t_gpu
= t_nvme + t_gpu + 2·t_sw + 2·t_rc + t_ram
```

Виділимо системний накладний транспортний оверхед `T_bounce_sys`:

```
T_bounce_sys = 2·t_sw + 2·t_rc + t_ram
```

Підставимо середні числові значення для сучасної серверної платформи (`t_sw = 0.15 мкс`, `t_rc = 0.30 мкс`, `t_ram = 2.50 мкс`):

```
T_bounce_sys = 2·0.15 + 2·0.30 + 2.50
= 0.30 + 0.60 + 2.50 [додавання окремих затримок]
= 3.40 мкс          [загальний транспортний оверхед]
```

### Пряма модель PCIe P2PDMA через PCIe Switch

Траєкторія TLP-пакета: NVMe → PCIe Switch (Local Downstream Routing) → GPU. Пакети взагалі не досягають Root Complex та оперативної пам'яті хоста.

Загальна затримка `T_p2p`:

```
T_p2p = t_nvme + t_sw + t_gpu
```

Системний накладний транспортний оверхед `T_p2p_sys`:

```
T_p2p_sys = t_sw
= 0.15 мкс         [лише затримка одного хопа комутатора]
```

### Кількісна порівняльна оцінка

Обчислимо абсолютне зменшення затримки транспорту `ΔT_sys`:

```
ΔT_sys = T_bounce_sys - T_p2p_sys
= 3.40 - 0.15       [віднімання затримок]
= 3.25 мкс         [абсолютна економія часу на кожній операції I/O]
```

Обчислимо відносне прискорення транспортного шару (Factor of Latency Reduction):

```
K_speedup = T_bounce_sys / T_p2p_sys
= 3.40 / 0.15       [ділення системних затримок]
≈ 22.67            [зменшення транспортної затримки в 22.67 раза]
```

У результаті використання P2PDMA транспортна затримка передавання даних між пристроями PCIe скорочується більш ніж у 22 рази, що критично важливо для транзакційних систем високочастотного трейдингу (HFT) та високопродуктивних алгоритмів обробки графів.

## 4. Затримки в двосокетних базі NUMA (Cross-Socket P2P)

У двосокетних серверах (наприклад, Dual AMD EPYC або Dual Intel Xeon) пристрої можуть бути підключені до PCIe-контролерів різних фізичних процесорів (NUMA Nodes).

Траєкторія TLP-пакета при cross-socket P2P без локального комутатора:
NVMe → Root Complex 0 → Міжпроцесорна шина (UPI / Infinity Fabric) → Root Complex 1 → GPU.

Нехай затримка міжпроцесорного з'єднання дорівнює `t_numa` (близько 120–200 нс).

Загальний транспортний оверхед cross-socket P2P `T_numa_p2p`:

```
T_numa_p2p = t_rc0 + t_numa + t_rc1
= 0.30 + 0.15 + 0.30 [підстановка середніх значень]
= 0.75 мкс          [затримка міжпроцесорного P2P]
```

Навіть у найнесприятливішому випадку cross-socket P2P через міжпроцесорну шину Infinity Fabric / UPI затримка `0.75 мкс` залишається у 4.5 раза меншою за традиційний транзит через системну RAM хоста (`3.40 мкс`).

### Математична умова вибору шляху P2PDMA

Драйвер ядра Linux обирає шлях P2P-мапування на основі нерівності затримок. Передача P2PDMA вважається вигідною, якщо виконується умова:

```
T_p2p_sys < T_bounce_sys
```

Оскільки `0.15 мкс < 3.40 мкс` (для локального комутатора) та `0.75 мкс < 3.40 мкс` (для cross-socket P2P), підсистема P2PDMA віддає перевагу прямому мапуванню для усіх сумісних конфігурацій топології.
