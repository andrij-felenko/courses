## Вступ до Peer-to-Peer DMA

У сучасних високопродуктивних обчислювальних системах та серверах обробка величезних масивів даних вимагає мінімізації затримок та максимізації пропускної здатності. Традиційна модель обміну даними між двома периферійними пристроями на шині Peripheral Component Interconnect Express (PCIe), наприклад, між NVMe твердотілим накопичувачем (SSD) та графічним процесором (GPU) або мережевою картою (SmartNIC), передбачає використання системної пам'яті (RAM) хоста як проміжного буфера.

Цей процес виглядає наступним чином: спочатку дані зчитуються з NVMe SSD у системну оперативну пам'ять (RAM), після чого вони копіюються з системної пам'яті до локальної пам'яті GPU або SmartNIC. Такий підхід має низку суттєвих недоліків:
1. **Подвійне навантаження на шину пам'яті:** Дані двічі проходять через контролер пам'яті центрального процесора (CPU), заповнюючи смугу пропускання RAM.
2. **Збільшення затримок (Latency):** Кожна додаткова транзакція читання/запису додає мікросекунди затримки.
3. **Навантаження на CPU:** Процесор змушений керувати додатковими операціями прямого доступу до пам'яті (DMA) та обробляти більше переривань.
4. **Засмічення кешу:** Копіювання великих обсягів даних через CPU може витісняти корисні дані з кешу L3.

**PCIe Peer-to-Peer DMA (P2PDMA)** — це технологія, яка вирішує ці проблеми, дозволяючи пристроям PCIe обмінюватися даними безпосередньо один з одним, повністю обходячи системну пам'ять та центральний процесор. Завдяки P2PDMA, дані з NVMe SSD можуть передаватися прямо в відеопам'ять (VRAM) GPU, що критично важливо для таких завдань, як машинне навчання, обробка великих даних, високочастотний трейдинг та наукові симуляції.

У цій статті ми детально розглянемо, як працює технологія P2PDMA, механізми маршрутизації TLP-пакетів у PCIe Root Complex, використання Controller Memory Buffer (CMB), а також реалізацію підтримки P2PDMA в ядрі Linux, зокрема функцію `pci_p2pdma_map_sg()`.

## 1. Архітектура PCIe та TLP Routing

Щоб зрозуміти, як працює P2PDMA, необхідно розглянути базову архітектуру шини PCIe. PCIe використовує топологію "точка-точка", де пристрої з'єднані через комутатори (switches) або безпосередньо підключені до Root Complex (RC), який є частиною процесора (або чіпсета) і відповідає за інтерфейс між CPU, пам'яттю та ієрархією PCIe.

### Транзакційний рівень (Transaction Layer)

Зв'язок у PCIe здійснюється за допомогою пакетів Transaction Layer Packets (TLP). TLP містять інформацію про тип операції (читання, запис, завершення), адресу, довжину даних та самі дані. Маршрутизація TLP залежить від їх типу:
- **Маршрутизація на основі адреси (Address Routing):** Використовується для запитів читання/запису пам'яті або простору конфігурації. Пакет маршрутизується до пристрою, якому належить вказаний діапазон адрес пам'яті (BAR - Base Address Register).
- **Маршрутизація на основі ID (ID Routing):** Використовується для повідомлень (Message Requests) та завершень (Completions). Пакет маршрутизується на основі ідентифікатора пристрою (Bus, Device, Function - BDF).

### Як Root Complex і Switches маршрутизують P2P трафік

Коли один пристрій (Ініціатор) хоче записати дані в пам'ять іншого пристрою (Цілі), він формує TLP запиту на запис пам'яті (Memory Write Request) з адресою, яка належить Цілі.

У традиційній архітектурі без підтримки P2P комутаторами, такий TLP надсилається вгору по дереву до Root Complex. Якщо Root Complex не підтримує маршрутизацію P2P (Peer-to-Peer Routing), він може відкинути пакет або надіслати повідомлення про помилку Unsupported Request (UR).

Для успішної роботи P2PDMA необхідно, щоб апаратна інфраструктура (комутатори PCIe та Root Complex) підтримували правильну маршрутизацію TLP між гілками дерева:
1. **Транзакції через PCIe Switch:** Якщо Ініціатор і Ціль підключені до одного й того ж PCIe комутатора, комутатор може самостійно перенаправити TLP від одного порту до іншого, не піднімаючи його до Root Complex. Це найшвидший шлях із найменшими затримками.
2. **Транзакції через Root Complex:** Якщо Ініціатор і Ціль підключені до різних портів Root Complex, пакет піднімається до RC. RC повинен вміти розпізнати, що адреса призначення належить пристрою на іншій гілці PCIe, і відправити пакет вниз по цій гілці, не звертаючись до системної пам'яті. Не всі архітектури CPU та налаштування BIOS (особливо ACS - Access Control Services) дозволяють це.

### Access Control Services (ACS) та IOMMU

Однією з головних перепон для P2PDMA є Access Control Services (ACS). ACS — це розширення PCIe, яке дозволяє контролювати маршрутизацію транзакцій. Воно використовується для примусового відправлення всіх TLP вгору до Root Complex для перевірки IOMMU (Input/Output Memory Management Unit), щоб забезпечити безпеку віртуалізації та ізоляцію пристроїв (наприклад, у сценаріях VFIO / PCI Passthrough).

Якщо ACS налаштовано так, що всі пакети змушені йти до RC (Source Validation), а IOMMU не підтримує трансляцію адрес для P2P (або забороняє її), P2PDMA не працюватиме. Тому для використання P2PDMA часто потрібно послабити обмеження ACS або переконатися, що IOMMU правильно налаштований для P2P груп (IOMMU groups).

## 2. Controller Memory Buffer (CMB) та Persistent Memory Region (PMR)

Для того щоб один пристрій міг звертатися до пам'яті іншого, ця пам'ять повинна бути доступною через PCIe BAR. Для GPU це звична справа — їх відеопам'ять (VRAM) експонується (повністю або частково через Resizable BAR) у фізичний адресний простір CPU і, відповідно, PCIe. Але що робити з NVMe SSD, які є блочними пристроями і традиційно не мають експонованої оперативної пам'яті?

Тут на допомогу приходять специфікації NVMe CMB та PMR.

### Controller Memory Buffer (CMB)

Специфікація NVMe 1.2 додала підтримку Controller Memory Buffer (CMB). CMB — це область пам'яті на самому NVMe-накопичувачі, доступна для читання та запису через PCIe BAR. Зазвичай це невелика кількість швидкої SRAM або DRAM, розміщена на контролері SSD (зазвичай від кількох мегабайт до кількох десятків мегабайт).

Призначення CMB:
- Зберігання черг подання (Submission Queues) та черг завершення (Completion Queues).
- Буферизація даних для команд читання/запису.

Для P2PDMA CMB відіграє ключову роль. Наприклад, замість того, щоб копіювати дані з системної пам'яті на SSD, GPU може напряму записувати дані в CMB на SSD, після чого SSD сам запише ці дані на флеш-пам'ять.

### Persistent Memory Region (PMR)

Специфікація NVMe 1.4 додала Persistent Memory Region (PMR). На відміну від CMB, PMR — це енергонезалежна пам'ять, яка експонується через PCIe BAR. Вона може бути значно більшого об'єму і дозволяє іншим пристроям PCIe зберігати дані безпосередньо в енергонезалежному середовищі SSD, минаючи хост.

## 3. P2PDMA в ядрі Linux: Архітектура та еволюція

Довгий час розробники намагалися реалізувати P2PDMA нестандартними способами (так звані "хаки"). Наприклад, проприєтарні рішення типу NVIDIA GPUDirect Storage або AMD ROCm використовували специфічні драйвери та модифікації ядра для з'єднання буферів GPU та сторінок пам'яті SSD.

Починаючи з версії ядра Linux 4.20 (а пізніше значно вдосконалено в серіях 5.x та 6.x), з'явився офіційний, стандартизований фреймворк для P2PDMA — підсистема `pci-p2pdma`. Вона дозволяє пристроям реєструвати свою пам'ять як доступну для P2P і дозволяє іншим драйверам виділяти цю пам'ять та відображати її для транзакцій DMA.

### Зони (ZONE_DEVICE)

Основою реалізації P2PDMA в Linux є механізм `ZONE_DEVICE`, доданий у підсистему керування пам'яттю (Memory Management, MM). `ZONE_DEVICE` дозволяє репрезентувати пам'ять пристрою за допомогою стандартних структур `struct page`.

Коли драйвер пристрою (наприклад, драйвер NVMe для CMB) реєструє свою пам'ять через фреймворк `pci_p2pdma`, ядро створює структури `struct page` для кожної сторінки (4KB) цієї пам'яті. Це критично важливо, оскільки більшість існуючих API ядра Linux (таких як блок-рівень `bio`, `scatterlist`) очікують вказівники на `struct page`. Завдяки `ZONE_DEVICE`, сторінки пам'яті PCIe-пристрою виглядають для решти ядра як звичайні сторінки оперативної пам'яті, але з особливим прапорцем, який вказує на їхню природу (memory-mapped I/O, MMIO).

### Життєвий цикл пам'яті P2PDMA

1. **Реєстрація:** Драйвер пристрою, що надає пам'ять (Provider), наприклад, GPU або NVMe, викликає `pci_p2pdma_add_resource()`, передаючи діапазон фізичних адрес свого BAR.
2. **Виділення:** Клієнтський пристрій (Client), який хоче використати цю пам'ять, викликає `pci_alloc_p2pmem()`.
3. **Map (Відображення):** Перед передачею даних, фізичні адреси (MMIO) повинні бути перетворені в адреси DMA, які розуміє IOMMU. Це робиться за допомогою `pci_p2pdma_map_sg()`.
4. **Використання:** Клієнт використовує отримані DMA адреси для програмування свого DMA-рушія.
5. **Unmap:** Звільнення ресурсів IOMMU за допомогою `pci_p2pdma_unmap_sg()`.

## 4. Огляд функції `pci_p2pdma_map_sg()`

Функція `pci_p2pdma_map_sg()` є серцем фреймворку P2PDMA. Її призначення — підготувати scatterlist (перелік блоків пам'яті) для P2P-передачі між двома пристроями.

У стандартному DMA для пам'яті хоста використовується функція `dma_map_sg()`. Вона перетворює масив `struct scatterlist` (який містить `struct page` пам'яті RAM) в масив DMA-адрес (I/O Virtual Addresses, IOVA, якщо активний IOMMU).

Але `dma_map_sg()` не може працювати зі сторінками `ZONE_DEVICE`, які належать до P2PDMA пам'яті, оскільки IOMMU хоста може не мати можливості (або потреби) транслювати адреси для P2P-трафіку, що йде через комутатори PCIe.

### Прототип функції

```c
int pci_p2pdma_map_sg(struct device *dev, struct scatterlist *sg, int nents,
                      enum dma_data_direction dir);
```

- `dev`: `struct device` пристрою, який буде здійснювати DMA (Ініціатор).
- `sg`: Масив `struct scatterlist`, який містить сторінки `struct page`, отримані через P2P-алокатор.
- `nents`: Кількість записів у scatterlist.
- `dir`: Напрямок DMA (`DMA_TO_DEVICE`, `DMA_FROM_DEVICE`, або `DMA_BIDIRECTIONAL`).

### Внутрішня логіка маршрутизації

Головне завдання `pci_p2pdma_map_sg()` — визначити топологію підключення між пристроєм-Провайдером (чиї `struct page` лежать у scatterlist) та пристроєм-Клієнтом (ініціатором DMA). Відстань між ними визначає, як треба налаштовувати адреси.

Ядро обчислює "тип відстані" (P2PDMA distance) між пристроями:
1. **P2PDMA_MAP_THRU_HOST_BRIDGE:** Пристрої підключені до різних Root Complex (або до одного RC, який вимагає пропускати все через себе). У цьому випадку адреса шини Провайдера може потребувати трансляції через IOMMU Клієнта (якщо це підтримується архітектурою).
2. **P2PDMA_MAP_BUS_ADDR:** Пристрої підключені до одного комутатора PCIe. Це ідеальний випадок. Пакети не досягнуть IOMMU або Root Complex. Тому `pci_p2pdma_map_sg()` просто бере фізичну адресу BAR Провайдера і записує її як DMA-адресу (`sg_dma_address()`) у scatterlist. IOMMU ігнорується, бо він ніколи не побачить ці транзакції.
3. **Несумісність:** Якщо ядро (через аналіз дерева пристроїв PCI та налаштувань ACS) визначає, що P2P-маршрутизація між цими двома пристроями неможлива або заборонена правилами безпеки, функція повертає помилку.

### Приклад коду використання

Нижче наведено спрощений приклад того, як драйвер (наприклад, кастомний пристрій збору даних) може використовувати P2PDMA для запису даних безпосередньо в CMB NVMe-диска.

```c
#include <linux/pci-p2pdma.h>
#include <linux/dma-mapping.h>
#include <linux/scatterlist.h>

// Припустимо, ми маємо вказівник на наш пристрій (Ініціатор) і NVMe пристрій (Ціль)
struct pci_dev *my_dev;
struct pci_dev *nvme_dev;

// 1. Алокація P2P пам'яті (пам'яті NVMe CMB)
void *p2p_vaddr;
struct page *p2p_page;

// Виділяємо 4KB з P2P-регіону NVMe
p2p_vaddr = pci_alloc_p2pmem(nvme_dev, PAGE_SIZE);
if (!p2p_vaddr)
    return -ENOMEM;

// 2. Отримання struct page для цієї пам'яті
p2p_page = virt_to_page(p2p_vaddr);

// 3. Налаштування scatterlist
struct scatterlist sg;
sg_init_table(&sg, 1);
sg_set_page(&sg, p2p_page, PAGE_SIZE, 0);

// 4. Map для P2PDMA. 
// Ініціатор (my_dev) буде робити DMA у Ціль (напрямок TO_DEVICE не має прямого 
// сенсу для P2P у звичайному розумінні, беремо BIDIRECTIONAL або TO_DEVICE 
// в залежності від того, хто є ініціатором транзакцій запису)
int nents_mapped = pci_p2pdma_map_sg(&my_dev->dev, &sg, 1, DMA_BIDIRECTIONAL);
if (nents_mapped == 0) {
    // Маршрутизація P2P неможлива між цими пристроями!
    pci_free_p2pmem(nvme_dev, p2p_vaddr, PAGE_SIZE);
    return -EIO;
}

// 5. Отримання DMA-адреси
dma_addr_t p2p_dma_addr = sg_dma_address(&sg);

// 6. Програмування апаратного DMA-контролера my_dev використовувати p2p_dma_addr
my_hardware_set_dma_dest(my_dev, p2p_dma_addr);
my_hardware_start_dma(my_dev);

// 7. Чекаємо завершення DMA...

// 8. Unmap та звільнення
pci_p2pdma_unmap_sg(&my_dev->dev, &sg, 1, DMA_BIDIRECTIONAL);
pci_free_p2pmem(nvme_dev, p2p_vaddr, PAGE_SIZE);
```

## 5. Екосистема та застосування P2PDMA

Сьогодні P2PDMA активно використовується у кількох ключових технологічних екосистемах.

### NVMe Over Fabrics (NVMe-oF)

Одне з головних застосувань `pci-p2pdma` в ядрі Linux — це цільові системи NVMe-oF (Target). Якщо сервер виступає в ролі сховища і приймає запити по мережі RDMA (Remote Direct Memory Access) через SmartNIC, дані, що надходять з мережі, повинні бути записані на локальні NVMe SSD.
Використовуючи P2PDMA, мережева карта (RDMA RNIC) може перенаправляти вхідні мережеві пакети безпосередньо в CMB NVMe-накопичувача, повністю оминаючи CPU і системну RAM. Це різко знижує затримки та розвантажує CPU для інших завдань (наприклад, управління метаданими).

### GPUDirect Storage та NVIDIA Magnum IO

Компанія NVIDIA розробила технологію GPUDirect Storage, яка використовує P2PDMA (або проприєтарні аналоги, якщо ядро старе) для того, щоб графічний процесор міг самостійно ініціювати транзакції DMA до NVMe SSD. У світі машинного навчання обробка терабайтів зображень або текстів вимагає постійного живлення GPU даними. Копіювання цих даних через CPU стає вузьким місцем. GPUDirect Storage дозволяє передавати дані зі швидкістю понад 40-50 ГБ/с безпосередньо з масивів NVMe PCIe Gen4/Gen5 у VRAM GPU.

### Обмеження та виклики

Незважаючи на значні переваги, P2PDMA має певні складнощі у впровадженні:
- **Підтримка материнською платою:** BIOS/UEFI повинні коректно налаштовувати PCIe-мости. Будь-які невідповідні налаштування ACS (Access Control Services) можуть блокувати P2P-трафік.
- **Підтримка IOMMU:** У віртуалізованих середовищах (KVM/QEMU з VFIO) надання P2PDMA віртуальним машинам вимагає складної конфігурації груп IOMMU, щоб ізоляція не перешкоджала P2P транзакціям.
- **Обмеження об'єму пам'яті:** Розмір CMB на сучасних NVMe SSD рідко перевищує 16-64 МБ, що обмежує розмір буферів для P2P передач.
- **Відсутність когерентності кешу:** P2PDMA-передачі обходять системний кеш, тому розробникам драйверів потрібно ретельно стежити за тим, щоб CPU не намагався читати "старі" дані з оперативної пам'яті, якщо апаратне забезпечення вже оновило їх через P2PDMA (хоча зазвичай P2P не зачіпає RAM, тому ця проблема стосується скоріше синхронізації доступу до буферів MMIO).

## Висновок

PCIe Peer-to-Peer DMA (P2PDMA) — це революційна технологія для дата-центрів та високопродуктивних робочих станцій, яка усуває процесор і системну пам'ять як вузькі місця при масивних передачах даних між периферійними пристроями. Фреймворк `pci-p2pdma` в Linux, разом із функціями на кшталт `pci_p2pdma_map_sg()`, стандартизував доступ до цих можливостей, відкривши шлях для створення надефективних систем зберігання (NVMe-oF) та прискорювачів штучного інтелекту. Хоча правильне налаштування P2PDMA вимагає ретельного підбору апаратного забезпечення (підтримка комутаторів, сумісні налаштування ACS), її переваги у зниженні затримок та підвищенні пропускної здатності роблять її невід'ємною частиною сучасної екосистеми Linux I/O.
