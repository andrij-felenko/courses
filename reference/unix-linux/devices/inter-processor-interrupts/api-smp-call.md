# 📋 Родина міжпроцесорних викликів: сигнатури, контексти, коди повернення

Усі функції цієї родини компілюються однаково звідусіль, а працюють правильно лише з кількох місць: виклик із забороненого контексту не дає ані попередження компілятора, ані падіння на місці — він дає взаємне зависання двох ядер під навантаженням через тиждень. Тому до кожної сигнатури тут додано те, чого в ній не видно: **кого вона зачіпає**, **хто на кого чекає**, **звідки її вільно кликати** і **що повертається, коли ціль недосяжна**.

Оголошення — `include/linux/smp.h`, `include/linux/smp_types.h`, `include/linux/irq_work.h`; реалізація — `kernel/smp.c` і `kernel/irq_work.c`. Наведене звірено з деревом Linux 6.12.

## Сигнатури

```c
typedef void (*smp_call_func_t)(void *info);
typedef bool (*smp_cond_func_t)(int cpu, void *info);

int  smp_call_function_single(int cpu, smp_call_func_t func, void *info, int wait);
int  smp_call_function_any(const struct cpumask *mask, smp_call_func_t func,
                           void *info, int wait);
void smp_call_function_many(const struct cpumask *mask, smp_call_func_t func,
                            void *info, bool wait);
void smp_call_function(smp_call_func_t func, void *info, int wait);

void on_each_cpu(smp_call_func_t func, void *info, int wait);
void on_each_cpu_mask(const struct cpumask *mask, smp_call_func_t func,
                      void *info, bool wait);
void on_each_cpu_cond(smp_cond_func_t cond_func, smp_call_func_t func,
                      void *info, bool wait);
void on_each_cpu_cond_mask(smp_cond_func_t cond_func, smp_call_func_t func,
                           void *info, bool wait, const struct cpumask *mask);

int  smp_call_function_single_async(int cpu, call_single_data_t *csd);
bool irq_work_queue_on(struct irq_work *work, int cpu);
```

Три верхні `on_each_cpu*` — тонкі обгортки над `on_each_cpu_cond_mask()`: `NULL` замість умови означає «без відсіву», а невказана маска — `cpu_online_mask`.

| виклик | коло цілей | своє ядро | повертає |
|---|---|---|---|
| `smp_call_function_single()` | одне назване | виконує **на місці**, з вимкненими перериваннями, якщо `cpu` — своє | `int` |
| `smp_call_function_any()` | одне будь-яке з маски | обирає своє, якщо воно в масці; далі — сусіда по вузлу NUMA; далі — будь-кого | `int` |
| `smp_call_function_many()` | усі онлайн-ядра з маски | **не виконує** — своє викреслюється з маски мовчки | нічого |
| `smp_call_function()` | усі онлайн-ядра, крім свого | не виконує | нічого |
| `on_each_cpu()`, `on_each_cpu_mask()` | онлайн-ядра з маски (усі — для `on_each_cpu()`) | **виконує**, з вимкненими перериваннями | нічого |
| `on_each_cpu_cond()`, `on_each_cpu_cond_mask()` | ті з маски, для яких `cond_func(cpu, info)` істинна | так само | нічого |
| `smp_call_function_single_async()` | одне назване | виконує на місці, якщо `cpu` — своє | `int` |
| `irq_work_queue_on()` | одне назване | ставить у свою чергу відкладеної роботи | `bool` |

Різниця між `smp_call_function_many()` і родиною `on_each_cpu*` — саме в цьому стовпці, і на ній спотикалися не раз: «many» назване так, ніби охоплює всіх із маски, але своє ядро процесора воно **не** зачіпає ніколи.

Друга асиметрія стосується ядра, якого в цю мить немає. Поодинокий виклик про це чесно доповідає кодом повернення, а групові мовчки звужують коло до онлайн-частини маски й нічого не повертають. Тому вимога «виконати на всіх без винятку» жодним із цих викликів сама по собі не забезпечується: коло спершу фіксують, беручи замок гарячого підключення, і аж тоді розсилають.

Локальне виконання йде повз усю чергову механіку: функцію просто кличуть на місці, під вимкненими місцевими перериваннями, ще до повернення з виклику. Прапорець `wait` на це не впливає — своє ядро обслуговується синхронно завжди. Наслідок видно під час випробувань: скрізь, де ціллю виявилося власне ядро, помилки з часом життя аргументу не виявляються й терпляче чекають на багатоядерну машину.

## Що означає кожен аргумент

**`func`** виконується в контексті переривання цілі: не має права спати, брати сплячі замки чи виділяти пам'ять способом, що чекає. Обмеження те саме, що для будь-якого [атомарного контексту ядра](book:unix-linux/kernel-locking).

**`info`** передається як є, без копіювання. Пам'ять, на яку він показує, мусить жити до кінця виконання на всіх цілях — при `wait = 0` це, зокрема, означає, що локальна змінна викличної функції для `info` не годиться.

**`wait`** — не про надсилання, а про повернення. Істинний: керування повертається, коли `func` **уже повернулася** на всіх цілях. Хибний: керування повертається щойно запит покладено в чергу — можливо, ще до того, як ціль до нього дійшла. Пастка тут одна й неочевидна: `wait = 0` не означає «без очікування взагалі». Варіант без очікування бере **спільний описувач свого ядра процесора**, і другий такий виклик підряд крутитиметься на його прапорці, доки перший не заберуть. Виклик без очікування буває повільнішим за виклик з очікуванням.

**`mask`** читається з вимкненим витісненням, тому маска не роз'їдеться під руками. Ядра, що в цю мить [йдуть офлайн](book:unix-linux/cpu-hotplug), просто випадають із кола; ядра, що приходять онлайн, у це коло вже не потраплять.

**`cond_func(cpu, info)`** кличеться на ядрі-ініціаторі, по разу на кожного кандидата, з вимкненим витісненням. Її призначення — не надіслати зайвого: рішення ухвалюється до вставки в чергу, тож відсіяне ядро не платить нічого.

## Описувач і його прапорець

```c
struct __call_single_node {
        struct llist_node llist;      /* вузол черги цілі             */
        union { unsigned int u_flags; atomic_t a_flags; };
        u16 src, dst;                 /* лише на 64-бітних            */
};

struct __call_single_data {
        struct __call_single_node node;
        smp_call_func_t           func;
        void                     *info;
};
typedef struct __call_single_data call_single_data_t
        __aligned(sizeof(struct __call_single_data));

#define CSD_INIT(_func, _info) \
        (struct __call_single_data){ .func = (_func), .info = (_info), }
#define INIT_CSD(_csd, _func, _info)  do { *(_csd) = CSD_INIT((_func), (_info)); } while (0)
```

Одне слово прапорців тримає і зайнятість, і різновид запису — саме за різновидом ціль розуміє, як тлумачити решту структури:

| біти | значення |
|---|---|
| `CSD_FLAG_LOCK = 0x01` | описувач зайнятий: запит у дорозі, чіпати поля не можна |
| `CSD_TYPE_ASYNC = 0x00` | асинхронний виклик функції |
| `CSD_TYPE_SYNC = 0x10` | виклик, на який хтось чекає |
| `CSD_TYPE_IRQ_WORK = 0x20` | у черзі лежить не `csd`, а `struct irq_work` |
| `CSD_TYPE_TTWU = 0x30` | пробудження задачі; корисних полів після прапорців немає |
| `CSD_FLAG_TYPE_MASK = 0xF0` | маска різновиду |

Вирівнювання типу на власний розмір — не косметика: описувач не має перетинати межу рядка кеша, інакше кожна перевірка прапорця чіпала б два рядки замість одного.

![Ліворуч синхронний описувач: ціль спершу виконує функцію, потім знімає прапорець; праворуч асинхронний: прапорець знімають ще до виклику функції](/reference/unix-linux/devices/inter-processor-interrupts/img/csd-lifecycle.svg)

*Однакові кроки в різному порядку дають різні контракти: синхронний описувач зайнятий до кінця обробника, асинхронний звільняється раніше.*

Прапорець ставить ініціатор і знімає ціль — і цей обмін є ще й **бар'єром пам'яті**: після встановлення прапорця стоїть бар'єр запису, а зняття — це запис зі звільненням. Тож усе, що ініціатор заповнив у полях, ціль гарантовано бачить, а все, що ціль записала до зняття, бачить ініціатор ([порядок доступів до пам'яті](book:programming/memory-ordering-barriers)).

Для асинхронного варіанта звідси випливають три правила. Описувач мусить пережити виклик — стек не годиться, звичайне місце для нього — поле структури, що описує **ціль**. Серіалізацію двох надсилань в один описувач ядро не перевіряє ніяк; єдиний зворотний зв'язок — код `-EBUSY`. І прапорець знімають **до** виклику `func`, тож описувач вільно перезарядити зсередини його ж обробника.

## Звідки вільно кликати

| виклик | контекст задачі | softirq | жорсткий обробник | переривання вимкнені | NMI |
|---|---|---|---|---|---|
| `smp_call_function_single()` | так | ні | ні | ні | ні |
| `smp_call_function_any()` | так | ні | ні | ні | ні |
| `smp_call_function_many()` | так, з вимкненим витісненням | ні | ні | ні | ні |
| `smp_call_function()`, уся родина `on_each_cpu*` | так | ні | ні | ні | ні |
| `smp_call_function_single_async()` | так | так | так | **так** | ні |
| `irq_work_queue_on()` | так | так | так | **так** | ні (лише локальний `irq_work_queue()`) |

Чотири перші рядки тримає одна перевірка — `WARN_ON_ONCE(!in_task())` — і одне міркування: виклик з очікуванням, зроблений із вимкненими перериваннями, замикає пару ядер намертво, а виклик без очікування бере описувач свого ядра процесора, який може бути вже зайнятий перерваним кодом. Окремо стоїть звірка «переривання ввімкнені», яку робить перевіряч замків; її знімають на аварійних шляхах (`oops_in_progress`) і на ранньому завантаженні, де переривань ще немає за визначенням.

Останній стовпець спільний для всієї родини: архітектурні реалізації надсилання й приймання не є NMI-безпечними, тож із [немаскованого переривання](book:programming/nmi-exceptions) не можна ані `csd`, ані `irq_work` на **чуже** ядро процесора — ядро системи ловить це попередженням у `irq_work_queue_on()`. Безпечна тут рівно одна дія: `irq_work_queue()` на своє ядро. Сама ж робота на цілі виконується в жорсткому контексті переривання; якщо потрібен м'якший — його треба брати вже там, звичайними засобами [відкладеної роботи](book:unix-linux/interrupts-bottom-halves).

> 🔧 **Навіщо це.** Стовпці цієї таблиці частіше визначають будову підсистеми, ніж навпаки. Код, що живе в обробнику переривання чи під вимкненими перериваннями, від синхронної половини родини відрізано повністю — і жодним обходом цього не полагодити, бо заборона тут не стилістична, а є єдиним, що не дає двом ядрам замкнутися одне на одному. Лишається два виходи: винести дію в контекст задачі або перебудувати її під асинхронний описувач, де ніхто нікого не чекає. Обирати доводиться на етапі проєктування, а не тоді, коли попередження вже висвітилося в журналі.

## irq_work: коли на цілі потрібен саме жорсткий контекст

```c
struct irq_work {
        struct __call_single_node node;
        void (*func)(struct irq_work *);   /* аргумент — сам описувач */
        struct rcuwait irqwait;
};

#define IRQ_WORK_INIT(_func)        /* звичайна робота                    */
#define IRQ_WORK_INIT_LAZY(_func)   /* без переривання, до найближчого тику */
#define IRQ_WORK_INIT_HARD(_func)   /* жорсткий контекст навіть на PREEMPT_RT */
#define DEFINE_IRQ_WORK(name, _f)

void init_irq_work(struct irq_work *work, void (*func)(struct irq_work *));
bool irq_work_queue(struct irq_work *work);           /* своє ядро; NMI-безпечно */
bool irq_work_queue_on(struct irq_work *work, int cpu);
void irq_work_sync(struct irq_work *work);            /* спить: лише контекст задачі */
```

| біт у `node.a_flags` | значення |
|---|---|
| `IRQ_WORK_PENDING = 0x01` | робота вже в черзі, повторна постановка поверне `false` |
| `IRQ_WORK_BUSY = 0x02` | обробник виконується просто зараз |
| `IRQ_WORK_LAZY = 0x04` | переривання не надсилати — дочекатися тику (крім ядер, де тики зупинено) |
| `IRQ_WORK_HARD_IRQ = 0x08` | у ядрі реального часу виконати таки в жорсткому контексті, а не в потоці `irq_work/N` |

Контракт тут інший, ніж у `csd`, і різниця не в назві коду помилки. Повторна постановка вже поставленої роботи повертає `false` — і це не збій, а звичайний перебіг: вузол списку один, другого виконання не буде, а те, що ініціатор устиг записати перед постановкою, обробник однаково побачить. Позначку `LAZY` вживають там, де робота потрібна, але терміновості немає: вона економить саме переривання, а не такти на цілі. А `irq_work_sync()` — єдиний спосіб дізнатися, що обробник завершився; без неї не можна звільняти пам'ять, у якій лежить `struct irq_work`, і саме тому вона спить і кличеться лише з контексту задачі.

## Коди повернення

| код | від кого | що сталося |
|---|---|---|
| `0` | `single`, `any`, `single_async` | запит поставлено в чергу цілі — або вже виконано, якщо ціллю було своє ядро |
| `-ENXIO` | `single`, `any`, `single_async` | номер поза діапазоном або ядро офлайн; прапорець описувача при цьому знімають, тож його можна вживати далі |
| `-EBUSY` | лише `single_async` | попередній запит із цього самого описувача ще не забрали; нічого не надіслано |
| `true` / `false` | `irq_work_queue_on()` | `false` — робота вже в черзі десь; повторна постановка не потрібна й неможлива, вузол списку один |
| — | групові виклики | нічого не повертають: недосяжні ядра мовчки випадають із кола |

## Мінімальний виклик

```c
#include <linux/smp.h>

static void say_where(void *info)
{
        pr_info("виконано на ядрі %d, аргумент %lu\n",
                smp_processor_id(), (unsigned long)info);
}

static void poke_cpu3(void)
{
        /* синхронно: повернеться, коли say_where() уже відпрацювала на ядрі 3 */
        int err = smp_call_function_single(3, say_where, (void *)42UL, 1);

        if (err)
                pr_warn("ядро 3 недосяжне: %d\n", err);
}
```

Асинхронний варіант потребує описувача, прив'язаного до цілі, — звичайно це [змінна свого ядра процесора](book:unix-linux/per-cpu-data):

```c
static DEFINE_PER_CPU(call_single_data_t, poke_csd);

static int __init poke_init(void)
{
        int cpu;

        for_each_possible_cpu(cpu)
                INIT_CSD(per_cpu_ptr(&poke_csd, cpu), say_where, NULL);
        return 0;
}

/* кличеться звідки завгодно, зокрема з вимкненими перериваннями */
static void poke_async(int cpu)
{
        int err = smp_call_function_single_async(cpu, per_cpu_ptr(&poke_csd, cpu));

        /* -EBUSY: дзвінок уже в дорозі, другий зайвий; -ENXIO: ядра немає */
        if (err && err != -EBUSY)
                pr_warn("ядро %d недосяжне: %d\n", cpu, err);
}
```

## Коли ціль мовчить

За звичайних налаштувань очікування прапорця не має жодного часового обмеження: ядро системи просто крутиться, доки прапорець не знімуть. Сторож умикається окремо:

| параметр | де | замовчування | що робить |
|---|---|---|---|
| `csdlock_debug=1` | рядок завантаження | залежить від `CONFIG_CSD_LOCK_WAIT_DEBUG_DEFAULT` | вмикає сторожа в циклі очікування й запис того, який `csd` кожне ядро процесора виконує зараз |
| `smp.csd_lock_timeout=<мс>` | рядок завантаження, читання в `/sys/module/smp/parameters/` | `5000` | поріг першого повідомлення; `0` вимикає сторожа зовсім |
| `smp.panic_on_ipistall=<мс>` | там само | `0` — не панікувати | паніка, коли очікування перевищило цей час; типове значення — `300000`, тобто п'ять хвилин |

Обидва параметри `smp.*` доступні лише для читання: змінити їх можна тільки в рядку завантаження. Поріг не є чистим таймером — він зростає з кожним наступним повідомленням і з кількістю онлайн-ядер, тож друге повідомлення прийде помітно пізніше за перше.

```
csd: Detected non-responsive CSD lock (#1) on CPU#0, waiting 5000212345 ns
     for CPU#03 do_flush_tlb_all+0x0/0x30(0000000000000000).
	csd: CSD lock (#1) unresponsive.
csd: Re-sending CSD lock (#1) IPI from CPU#00 to CPU#03
```

Читається так: `Detected` — перша скарга на цей випадок (далі йтимуть `Continued` під тим самим номером `#1`); `on CPU#0` — хто чекає; `for CPU#03` — на кого; далі функція й аргумент, які ціль мала виконати. Другий рядок називає стан цілі, і саме він відповідає на питання «хто винен»:

- `unresponsive` — ціль зараз не виконує жодного запиту, тобто дзвінка не чує взагалі: або сидить із вимкненими перериваннями, або її віртуальному ядру не дають процесора;
- `handling this request` — уже взялася саме за наш і не встигає;
- `handling prior ...` — застрягла на **попередньому** запиті, і винний названий у дужках: це його функція й аргумент.

Після скарги ядро системи просить у цілі знімок стека, а на перший випадок друкує ще й стек того, хто чекає. Переривання перенадсилають лише в стані `unresponsive` — коли ціль уже щось виконує, повторний дзвінок нічого не змінить.
