# 📜 Еволюція прискорення I/O: від програмного vhost до апаратного vDPA

Історія прискорення введення-виведення (англ. *Input/Output*, I/O) у віртуалізації — це послідовна боротьба з накладними витратами на перемикання контексту процесора та копіювання пам'яті. Розуміння п'яти етапів цієї еволюції пояснює, чому архітектура vDPA виникла саме в такому вигляді й які фундаментальні обмеження попередників вона подолала.

## 1. Ера емуляції апаратури (100 Мбіт/с — 1 Гбіт/с)

На світанку віртуалізації x86 (початок 2000-х років) гіпервізори (QEMU, VMware) емулювали реальні фізичні мережеві карти, такі як Intel e1000 або Realtek rtl8139. Гостьова операційна система використовувала свій штатний драйвер фізичного пристрою, навіть не підозрюючи, що працює у віртуальній машині.

Кожен запис гостя в регістр контролера викликав перехоплення гіпервізором (англ. *VM Exit* — вихід із режиму виконання віртуального процесора VMX non-root в режим хоста VMX root). Обробка одного мережевого пакета вимагала десятків перехоплень регістрів MMIO/PIO, копіювання даних через буфери QEMU та емуляції переривань. Продуктивність обмежувалася десятками тисяч пакетів за секунду (PPS), а процесор хоста витрачав до 90% циклів на підтримку ілюзії апаратури.

## 2. Паравіртуалізація та Virtio (1 Гбіт/с — 10 Гбіт/с)

У 2008 році Расті Расселл (Rusty Russell) запропонував стандарт паравіртуалізації **virtio** (від англ. *virtual I/O* — віртуальне введення-виведення). Ідея полягала у відмові від емуляції реального кремнію на користь спеціально розробленого віртуального пристрою.

Замість емуляції регістрів MMIO гість і QEMU почали використовувати спільні кільцеві буфери у RAM хоста — **віртчерги** (англ. *virtqueues*, vring). Гість вміщує дескриптор пакета в кільце `Available` і робить один "сигнал" (англ. *kick* — запис у PCI BAR або дверний дзвінок *doorbell*). QEMU зчитує пакет, відправляє його у мережу хоста й кладе результат у кільце `Used`.

Накладні витрати впали в рази, але критичний шлях даних (англ. *datapath*) все одно проходив через процес користувацького простору QEMU:
```
[VM Virtio Driver] ──(VM Exit)──> [KVM Kernel] ──(eventfd)──> [QEMU Userspace] ──(write)──> [TAP / Kernel Net]
```
Кожен пакет вимагав перемикання між ядром хоста та процесом QEMU в просторі користувача.

## 3. Внутрішньоядерний vhost (10 Гбіт/с — 40 Гбіт/с)

Щоб прибрати QEMU зі шляху даних, на початку 2010 року в ядрі Linux з'явився модуль `vhost-net`. QEMU зберіг за собою рівень управління (англ. *control path* — налаштування MAC-адрес, узгодження можливостей, ініціалізація), але передав дескриптор кільця vring безпосередньо у внутрішньоядерний потік `vhost-PID`.

Тепер сповіщення `kick` від KVM обробляється безпосередньо у ядрі хоста:
```
[VM Virtio Driver] ──(VM Exit)──> [KVM Kernel] ──(vring poll)──> [vhost-net Kernel Thread] ──> [TAP / Bridge]
```
Це зменшило затримку (latency) з кількох десятків мікросекунд до 10–15 мікросекунд і дозволило прокачувати лінійну швидкість 10 Gbps. Проте обробка кілець vring усе одно виконувалася силами CPU хоста.

## 4. Обхід ядра хоста: DPDK та vhost-user (40 Гбіт/с — 100 Гбіт/с)

З появою мереж 40G та 100G накладні витрати ядра Linux на обробку мережевого стеку (мережеві переривання, реалізація `sk_buff`, сокети) стали вузьким місцем. У 2014 році було створено фреймворк **vhost-user**.

`vhost-user` виносить обробку virtqueue з ядра хоста у виділений процес простору користувача, такий як Open vSwitch (OVS) з підсистемою DPDK (Data Plane Development Kit). DPDK працює в режимі опитування (англ. *Poll Mode Driver*, PMD): один або кілька ядер CPU хоста виділяються на 100% під безперервний цикл зчитування дескрипторів із RAM гостя та відправки у мережеву карту.

Це забезпечило продуктивність понад 10–20 мільйонів pps на порт, але ціна виявилася високою: спалювання цілих ядер CPU хоста виключно на пересилку пакетів та складність налаштування дрібних деталей пам'яті Hugepages.

## 5. SR-IOV проти vDPA: Повернення до апаратури

Очевидним альтернативним рішенням для досягнення швидкостей 100G+ без витрат CPU був **SR-IOV** (Single Root I/O Virtualization) — апаратне прокидання віртуальних функцій (VF) мережевої карти напряму у віртуальну машину через VFIO.

Однак SR-IOV створив дві фундаментальні проблеми для хмарних провайдерів:
1. **Прив'язка до вендора (Vendor Lock-in):** Усередині VM потрібен був специфічний драйвер заліза (Mellanox `mlx5_core`, Intel `i40e`). Перенесення VM на хост із картою іншого виробника вимагало зміни драйверів і конфігурації гостя.
2. **Неможливість живої міграції (Live Migration):** Гіпервізор QEMU втратив контроль над станом пристрою, оскільки регістри й внутрішні черги були приховані в кремнії мережевої карти.

Наприкінці 2010-х років інженери Intel — зокрема Цуньмін Лян (Cunming Liang) — винесли концепцію **vDPA (virtio Data Path Acceleration)** на конференцію KVM Forum. Головна ідея vDPA — зберегти стандартний, вендоро-незалежний пристрій `virtio-net` для віртуальної машини, але навчити апаратний ASIC мережевої карти (SmartNIC/DPU) напряму читати й декодувати структури virtqueue через DMA.

У ядрі Linux 5.7 (2020 рік) підсистему vDPA було остаточно стандартизовано та прийнято у MAINLINE. Завдяки цьому мережева карта SmartNIC бере на себе весь Data Path (0% навантаження на CPU хоста), а QEMU зберігає стандартний Control Path через `/dev/vhost-vdpa-N`, забезпечуючи прозору живу міграцію та повну відсутність вендор-локу в гості.
