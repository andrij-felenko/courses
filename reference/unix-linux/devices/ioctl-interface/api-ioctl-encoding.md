# 🧾 Контракт номерів і аргументів ioctl

Кожна команда `ioctl` — домовленість між заголовком, з якого зібрана програма, і `switch`-ем усередині драйвера; ядро в цю домовленість не втручається й нічого в ній не звіряє. Тут зібрано все, з чого вона складається: як із чотирьох полів збирається 32-бітний номер, якими макросами його складають і розбирають, які підписи мають обробники, що означає повернене число і за якими правилами укладається структура-аргумент, щоб її не довелося ламати через рік.

## Чотири поля в одному числі

| поле | що каже | ширина | зсув | добувач |
|---|---|---|---|---|
| номер | порядковий номер команди в межах своєї підсистеми | 8 бітів | 0 | `_IOC_NR(cmd)` |
| тип | «магічна» літера підсистеми | 8 бітів | 8 | `_IOC_TYPE(cmd)` |
| розмір | `sizeof` типу третього аргументу | 14 бітів | 16 | `_IOC_SIZE(cmd)` |
| напрям | у який бік ідуть дані | 2 біти | 30 | `_IOC_DIR(cmd)` |

Самі константи живуть в `include/uapi/asm-generic/ioctl.h` і виражені одна через одну, тож зсуви не задані числами, а обчислені:

```c
#define _IOC_NRBITS      8
#define _IOC_TYPEBITS    8
#define _IOC_SIZEBITS   14
#define _IOC_DIRBITS     2

#define _IOC_NRSHIFT     0
#define _IOC_TYPESHIFT   (_IOC_NRSHIFT   + _IOC_NRBITS)     /*  8 */
#define _IOC_SIZESHIFT   (_IOC_TYPESHIFT + _IOC_TYPEBITS)   /* 16 */
#define _IOC_DIRSHIFT    (_IOC_SIZESHIFT + _IOC_SIZEBITS)   /* 30 */

#define _IOC_NONE        0U
#define _IOC_WRITE       1U
#define _IOC_READ        2U
```

Напрям читається **з боку програми**, а не з боку ядра — це найчастіше джерело плутанини:

| напрям | значення | що робить драйвер |
|---|---|---|
| `_IOC_NONE` | 0 | третій аргумент або відсутній, або сам є значенням |
| `_IOC_WRITE` | 1 | програма передає дані вниз → `copy_from_user` |
| `_IOC_READ` | 2 | програма забирає дані нагору → `copy_to_user` |
| `_IOC_READ \| _IOC_WRITE` | 3 | одна структура і приймає, і повертає |

Розбирається число дзеркально до складання — зсув і маска, де кожна маска є `(1 << ширина) - 1`:

```c
#define _IOC_DIR(nr)    (((nr) >> _IOC_DIRSHIFT)  & _IOC_DIRMASK)
#define _IOC_TYPE(nr)   (((nr) >> _IOC_TYPESHIFT) & _IOC_TYPEMASK)
#define _IOC_NR(nr)     (((nr) >> _IOC_NRSHIFT)   & _IOC_NRMASK)
#define _IOC_SIZE(nr)   (((nr) >> _IOC_SIZESHIFT) & _IOC_SIZEMASK)
```

**Архітектурний виняток.** На alpha, mips, parisc, powerpc і sparc розкладка інша: `_IOC_SIZEBITS` дорівнює 13, `_IOC_DIRBITS` — 3, а отже `_IOC_DIRSHIFT` — 29. Напрям там не число, а бітова маска: `_IOC_NONE` = 1, `_IOC_READ` = 2, `_IOC_WRITE` = 4. Тому та сама команда має на різних архітектурах різні номери — і це нормально, бо число щоразу обчислює препроцесор на місці збирання. Ненормально інше: вписати обчислене число в код константою. Тоді програма поїде куди завгодно, крім тієї архітектури, де ви його підглянули.

Наочно це видно на `TIOCGWINSZ` — команді, якою `ls` дізнається ширину вікна. На powerpc вона оголошена макросом, і `struct winsize` там чотири `unsigned short`, тобто вісім байтів:

**Умова: `TIOCGWINSZ` = `_IOR('t', 104, struct winsize)` на powerpc, де зсув напряму дорівнює 29.**

```
напрям   _IOC_READ = 2       →    2 << 29  =  0x40000000
розмір   8                   →    8 << 16  =  0x00080000
тип      't' = 0x74          → 0x74 <<  8  =  0x00007400
номер    104 = 0x68          → 0x68 <<  0  =  0x00000068
                                            ─────────────
                              TIOCGWINSZ     0x40087468
```

А на x86 та решті «generic»-архітектур та сама команда записана як `#define TIOCGWINSZ 0x5413` — голим числом, старшим за макроси. Спробуйте розібрати його добувачами: напрям 0, розмір 0, тип `'T'`, номер 0x13. За полями виходить команда без аргументу — хоча насправді вона бере адресу `struct winsize`. Звідси головне застереження до всієї цієї розкладки: поля описують **намір того, хто складав число макросом**, а не істину про виклик. Загальний шлях у ядрі їх не звіряє, а команди, успадковані від часів до макросів, розбираються на казна-що.

## Складання: чотири макроси

```c
#define _IO(type,nr)             _IOC(_IOC_NONE, (type),(nr), 0)
#define _IOR(type,nr,argtype)    _IOC(_IOC_READ, (type),(nr), (_IOC_TYPECHECK(argtype)))
#define _IOW(type,nr,argtype)    _IOC(_IOC_WRITE,(type),(nr), (_IOC_TYPECHECK(argtype)))
#define _IOWR(type,nr,argtype)   _IOC(_IOC_READ|_IOC_WRITE, (type),(nr), (_IOC_TYPECHECK(argtype)))
```

Третій аргумент — **тип**, а не розмір. Класична помилка виглядає нешкідливо: `_IOW('x', 1, sizeof(struct cfg))`. Макрос підставить `sizeof(sizeof(struct cfg))`, тобто `sizeof(size_t)` — вісім на 64-бітній збірці й чотири на 32-бітній. Номер вийде і хибний, і різний на різній розрядності. `ioctl-number.rst` попереджає про це окремим рядком, бо на цьому спотикаються регулярно.

Частину зловживань ловить компілятор — але лише в збірці ядра, де `_IOC_TYPECHECK` визначений так:

```c
extern unsigned int __invalid_size_argument_for_IOC;
#define _IOC_TYPECHECK(t) \
        ((sizeof(t) == sizeof(t[1]) && \
          sizeof(t) < (1 << _IOC_SIZEBITS)) ? \
          sizeof(t) : __invalid_size_argument_for_IOC)
```

Порівняння `sizeof(t)` з `sizeof(t[1])` відсіює масиви, друга умова — типи, більші за поле розміру; в обох випадках вираз посилається на змінну, оголошену `extern` і ніде не визначену, тож збирання падає на компонуванні. У заголовках для простору користувача той самий макрос — просто `sizeof(t)`, без жодної перевірки. Тобто бік програми зіб'ється мовчки, і ви побачите це аж у `strace`.

Поряд у тому ж заголовку лежать `_IOR_BAD`, `_IOW_BAD`, `_IOWR_BAD` — ті самі макроси, але з `sizeof(argtype)` замість `_IOC_TYPECHECK`, тобто без перевірки. Вони існують не для нового коду, а для старого: коли в уже випущеної команди в полі розміру стоїть щось не те, це число треба відтворити точно як є, а не полагодити. Для нового інтерфейсу `_BAD`-варіант — завжди помилка. Є там ще й `IOC_IN`, `IOC_OUT`, `IOC_INOUT`, `IOCSIZE_MASK`, `IOCSIZE_SHIFT` — ті самі напрям і розмір, але вже зсунуті на місце; вони лишилися від звукової підсистеми й нікому іншому не потрібні.

> 🔧 **Навіщо це.** Коли `strace` показує голе число замість імені команди, розкладка розбирається усно. У `0x40187801` старші два біти — `01`, тобто `_IOC_WRITE`; біти 29–16 дають `0x18` = 24 байти аргументу; байт типу — `0x78` = `'x'`; молодший — 1. Читається як «підсистема `'x'`, команда №1, програма передає вниз структуру на 24 байти». Далі лишається знайти в заголовках, чия літера `'x'`.

## Обробники

```c
struct file_operations {
        /* ... */
        long (*unlocked_ioctl) (struct file *, unsigned int, unsigned long);
        long (*compat_ioctl)   (struct file *, unsigned int, unsigned long);
        /* ... */
};
```

Підписи однакові, різниця — хто викликає. `unlocked_ioctl` дістає виклики від програм рідної розрядності, `compat_ioctl` — від [32-бітних програм на 64-бітному ядрі](book:unix-linux/compat-32-on-64), де і розкладка структур, і саме число команди можуть відрізнятися. Якщо всі команди драйвера беруть **лише покажчики** на структури, розкладка яких від розрядності не залежить, окремий обробник писати не треба — досить готового:

```c
.compat_ioctl = compat_ptr_ioctl,
```

Він проганяє аргумент крізь `compat_ptr()` — це важить на s390, де в 32-бітного покажчика треба скинути старший біт, — і передає виклик у `unlocked_ioctl`. Щойно бодай одна команда передає числом, а не покажчиком, або бодай одна структура викладається по-різному, `compat_ptr_ioctl` не годиться й потрібен власний обробник.

## Що означає повернене число

Обробник віддає `long` за [загальною угодою системних викликів](book:unix-linux/syscall-mechanics): від'ємне — це `-errno`, нуль і додатне — успіх. Помилкою вважається лише проміжок від −4095 до −1 (`MAX_ERRNO` = 4095); усе інше піде програмі як результат. Додатні значення повертають рідко й щоразу за приватною домовленістю команди (скільки байтів оброблено, який дескриптор створено) — тримайте їх малими, бо бібліотечна обгортка віддає програмі `int`.

| код | коли доречний |
|---|---|
| `-ENOTTY` | драйвер не знає цієї команди — гілка `default`. Єдиний код, за яким програма може **промацати** наявність можливості, тому підміняти його чимось іншим не можна |
| `-EINVAL` | команда відома, але аргументи негодящі: значення поза діапазоном, нульова довжина, невідома комбінація прапорців, ненульове поле-заповнювач |
| `-EFAULT` | `copy_from_user`/`copy_to_user` повернули ненуль: адреса [з простору користувача](book:unix-linux/kernel-and-userspace) веде нікуди або не належить процесові |
| `-EPERM` | команда відома, аргументи слушні, але викликачеві бракує [потрібної можливості](book:unix-linux/capabilities) — `capable(CAP_SYS_ADMIN)` відмовив |
| `-ENOIOCTLCMD` | внутрішній код (515), назовні не виходить: рівень VFS міняє його на `-ENOTTY` |

Остання підміна — буквально три рядки в `fs/ioctl.c`, і саме вона робить `ENOTTY` єдиною відповіддю на невідому команду незалежно від того, який із двох кодів обрав драйвер:

```c
error = filp->f_op->unlocked_ioctl(filp, cmd, arg);
if (error == -ENOIOCTLCMD)
        error = -ENOTTY;
```

Через це `-EINVAL` на **невідому** команду — окремо шкідлива помилка, хоч історично так робили: програма більше не може відрізнити «такої команди немає» від «команда є, але ти передав дурницю», і промацування можливостей ламається.

## Структура-аргумент

Номер команди містить `sizeof` — отже будь-яка зміна розкладки структури міняє саме число, і `switch` у драйвері перестає його впізнавати. Звідси весь список вимог; він короткий, але не має винятків.

- **Типи лише фіксованої ширини:** `__u8`/`__s8`, `__u16`/`__s16`, `__u32`/`__s32`, `__u64`/`__s64`. Ніяких `long`, `size_t`, `enum`, бітових полів і голого `char` — усе це або міняє ширину, або міняє знаковість між архітектурами.
- **Покажчик передається як `__u64`.** У програмі — приведенням через `uintptr_t`, у ядрі — макросом `u64_to_user_ptr()`, який робить із числа `void __user *`.
- **Доповнення виписується явно.** Усі поля мають лежати на своєму природному вирівнюванні, а дірки між ними — бути названими полями. Неявне доповнення — це неініціалізовані байти ядра, що їдуть у простір користувача, і різна розкладка на різних ABI. Перевірити готову структуру можна `pahole`.
- **Стеля розміру.** Структура мусить уміститися в поле розміру: 16383 байти там, де воно чотирнадцятибітне, і 8191 на архітектурах зі списку вище. Портативна межа, яку називає документація ядра, — саме **8191 байт**. Більший обсяг передається не самою структурою, а адресою й довжиною **всередині** неї.

```c
/* так не можна: розкладка залежить від розрядності */
struct bad_cfg {
        int     n;
        void   *buf;
        long    len;
};

/* так треба: однаково для 32- і 64-бітних програм */
struct good_cfg {
        __u32   n;
        __u32   flags;
        __u64   buf;      /* адреса як число, не покажчик */
        __u64   len;
        __u64   __pad;    /* запас на майбутнє, мусить бути 0 */
};
```

Бік ядра зобов'язаний перевірити все сам — жодної загальної перевірки під ним немає:

```c
struct good_cfg c;

if (copy_from_user(&c, (void __user *)arg, sizeof(c)))
        return -EFAULT;
if (c.__pad || (c.flags & ~CFG_KNOWN_FLAGS))
        return -EINVAL;                 /* незнайомого не пропускаємо */
if (c.len == 0 || c.len > CFG_MAX_LEN)
        return -EINVAL;
if (copy_from_user(kbuf, u64_to_user_ptr(c.buf), c.len))
        return -EFAULT;
```

Поле-заповнювач і перевірка невідомих прапорців тут не формальність, а єдиний спосіб пізніше розширити команду. Номер [заморожений назавжди](book:unix-linux/userspace-abi-stability), доростити структуру не можна — новий `sizeof` дасть новий номер. Зате новий біт у `flags` старе ядро відхилить із `-EINVAL`, і програма з цього дізнається, що можливості немає, замість мовчки отримати не той результат.

## Реєстрація літери

Магічна літера — не приватна справа драйвера, бо збіг двох літер означає, що команда, послана не в той дескриптор, буде виконана. Перелік зайнятих літер і діапазонів веде `Documentation/userspace-api/ioctl/ioctl-number.rst`. Правила прості: узяти вільний блок із запасом (документація радить закладати від 32 до 256 номерів), або — як роблять деякі пристрої — узяти за літеру власний старший номер пристрою, якщо він унікальний; після чого **надіслати патч до цього ж файлу**, бо реєстрація існує рівно доти, доки вона в дереві ядра.
