# 📋 Специфікація журналу ANA Log Page, структури дескрипторів та інтерфейси sysfs

Інтерфейс Asymmetric Namespace Access (ANA) описує двійковий протокол між контролером NVMe та хостом для динамічного передавання станів доступності просторів назв. Механізм стандартизовано в межах технічної пропозиції NVM Express TP 4004 та включено до базової специфікації NVMe 1.4 і NVMe 2.0. У цьому довіднику наведено точну розкладку двійкових структур журналу стану ANA Log Page (ідентифікатор сторінки `0x0c`), формати статусних кодів завершення команд, параметри черги асинхронних подій AER, правила ітерування динамічних дескрипторів у пам'яті ядра та повне дерево атрибутів підсистеми у віртуальній файловій системі `sysfs` операційної системи Linux.

---

## 1. Заголовок журналу ANA Log Page (Log Identifier 0x0c)

Журнал ANA повертається контролером у відповідь на команду адміністративного набору `Get Log Page` (код операції Opcode `0x02`) з ідентифікатором сторінки `LID = 0x0c`. Для читання журналу хост заповнює адміністративну команду `struct nvme_admin_cmd`, де у 10-му командному подвійному слові (`cdw10`) молодший байт містить номер сторінки `0x0c`, а старші два байти визначають молодшу частину довжини буфера в подвійних словах (`(length / 4) - 1`).

Журнал починається з фіксованого 16-байтного заголовка, після якого в пам'яті послідовно розташовуються дескриптори груп ANA:

| Зсув (байти) | Поле | Тип даних | Опис |
| :--- | :--- | :--- | :--- |
| `00:07` | `chgcnt` | `uint64_t` | **Глобальний лічильник змін (Change Counter):** монотонно зростаюче 64-бітне беззнакове число. Контролер збільшує це значення на одиницю щоразу, коли змінюється стан хоча б однієї групи ANA або склад прив'язаних просторів назв. |
| `08:09` | `ngrps` | `uint16_t` | **Кількість груп ANA (Number of ANA Groups):** загальне число дескрипторів груп, що слідують безпосередньо за заголовком у поточному буфері. |
| `10:15` | — | `uint8_t[6]` | Зарезервовано для майбутніх розширень специфікації NVM Express. Має скидатися в нуль цільовим вузлом. |

Глобальний лічильник `chgcnt` відіграє вирішальну роль у запобіганні стану перегонів (race conditions). Якщо хост зчитує журнал частинами через обмеження розміру буфера передачі даних (MDTS), він порівнює `chgcnt` першого фрагмента з наступними; неспівпадіння лічильника вказує на зміну топології безпосередньо під час зчитування, що вимагає повторного запиту всього журналу з самого початку.

## 2. Дескриптор групи ANA (ANA Group Descriptor)

Кожен дескриптор описує поточний стан маршрутизації для однієї групи просторів назв `ANAGRPID` та містить неперервний масив ідентифікаторів `NSID`, що входять до її складу. Довжина дескриптора є динамічною величиною і залежить від кількості просторів назв, зареєстрованих у цій групі:

```
Розмір дескриптора = 32 + (4 × nnsids) байтів
```

| Зсув (байти) | Поле | Тип даних | Опис |
| :--- | :--- | :--- | :--- |
| `00:03` | `anagrpid` | `uint32_t` | **Ідентифікатор групи ANA (ANA Group ID):** унікальний числовий номер групи в межах підсистеми (від `1` до `0xFFFFFFFF`). Номер `0` зарезервовано. |
| `04:07` | `nnsids` | `uint32_t` | **Кількість просторів назв (Number of NSIDs):** число 32-бітних ідентифікаторів у полі `nsids[]`. |
| `08:15` | `chgcnt` | `uint64_t` | **Локальний лічильник змін групи:** 64-бітне число, що збільшується лише під час зміни стану або складу саме цієї конкретної групи. |
| `16` | `state` | `uint8_t` | **Стан доступності групи (ANA State):** молодші 4 біти (`3:0`) кодують стан доступу (значення `0x01`–`0x0F`). Старші біти зарезервовані. |
| `17:31` | — | `uint8_t[15]` | Зарезервовано цільовим пристроєм. |
| `32:32 + 4·n - 1` | `nsids` | `uint32_t[n]` | **Масив ідентифікаторів NSID:** послідовність 4-байтних цілих чисел у форматі Little-Endian, що перелічує всі логічні томи, які розділяють цей стан. |

### Числові значення та семантика станів ANA (`state`)

Стан групи визначає правила обробки команд введення-виведення на стороні цільового вузла та поведінку драйвера хоста:

| Байт | Мнемоніка | Назва стану | Поведінка введення-виведення (I/O) |
| :--- | :--- | :--- | :--- |
| `0x01` | `AO` | **ANA Optimized** | Оптимальний прямий шлях. Найнижча затримка, максимальна пропускна здатність. Драйвер хоста спрямовує всі основні запити через цей інтерфейс. |
| `0x02` | `ANO` | **ANA Non-Optimized** | Неоптимальний шлях (проксі через внутрішню міжконтролерну шину). Працездатний, але має підвищену затримку. Використовується як гарячий резерв. |
| `0x03` | `AI` | **ANA Inaccessible** | Шлях апаратно недоступний (обрив внутрішнього каналу або перезавантаження вузла). Команди I/O відхиляються зі статусом `NVME_SC_ANA_INACCESSIBLE`. |
| `0x04` | `PL` | **ANA Persistent Loss** | Шлях втрачено безповоротно (демонтаж полиці, видалення тому). Команди повертають `NVME_SC_ANA_PERSISTENT_LOSS`. Ядро видаляє вузол шляху. |
| `0x0F` | `CHANGE` | **ANA Change State** | Перехідний стан під час аварійного перемикання контролерів. Команди повертають `NVME_SC_ANA_TRANSITION`. Драйвер тимчасово призупиняє чергу. |

## 3. Асинхронні сповіщення про зміну топології (AER)

Щоб хост не витрачав ресурси на періодичне опитування (polling) стану масиву, протокол NVMe використовує механізм Asynchronous Event Request (AER). Хост завчасно надсилає до черги керування кілька команд `NVME_ADMIN_ASYNC_EVENT`, які контролер «підвішує» у незавершеному стані до моменту виникнення події.

Коли на цільовому вузлі змінюється стан хоча б однієї групи ANA (наприклад, аварія оптичного лінку або планова міграція тому), контролер негайно завершує одну з команд AER, заповнюючи нульове слово запису завершення (`DW0`):

```
+───────────────────+───────────────────+───────────────────+───────────────────+
| 31             24 | 23             16 | 15              8 | 7               0 |
+───────────────────+───────────────────+───────────────────+───────────────────+
|   Log Page LID    |    Event Info     |    Event Type     |    Reserved       |
|      (0x0C)       |      (0x03)       |      (0x02)       |                   |
+───────────────────+───────────────────+───────────────────+───────────────────+
```

- **Event Type (`0x02` — Notice):** тип сповіщення про зміну конфігурації.
- **Event Information (`0x03` — ANA Change):** інформує драйвер про необхідність оновити карту доступності просторів назв.
- **Log Page Identifier (`0x0C` — ANA Log):** вказує точний ідентифікатор сторінки журналу, яку драйвер повинен зчитати для отримання нових статусів.

Отримавши апаратне переривання від черги завершення AER, драйвер `nvme-core` ставить у системну чергу ядра `kworker` відкладену задачу `nvme_mpath_ana_work()`, яка через команду `Get Log Page` оновлює структури `ns->ana_state` та миттєво перемикає потоки даних без втручання користувача.

## 4. Статусні коди завершення команд (Command Completion Status)

Коли контролер або драйвер хоста відхиляє команду введення-виведення через несумісний стан шляху, у полі Status Code (SC) запису черги завершення повертаються спеціалізовані коди сімейства Path Related Status (код типу статусу SCT = `0x1`):

| Код (SC) | Повний код | Мнемоніка ядра Linux | Поведінка та відновлення в ядрі |
| :--- | :--- | :--- | :--- |
| `0x28` | `0x0128` | `NVME_SC_ANA_INACCESSIBLE` | Запит не повертається у простір користувача. Драйвер перехоплює його, поміщає у чергу повтору (`head->requeue_list`) та спрямовує на резервний контролер. |
| `0x29` | `0x0129` | `NVME_SC_ANA_PERSISTENT_LOSS` | Помилка є остаточною для поточного контролера. Драйвер позначає шлях як неробочий та намагається надіслати команду через інший активний вузол. |
| `0x2A` | `0x012a` | `NVME_SC_ANA_TRANSITION` | Вказує на тимчасову перебудову масиву. Запит затримується у черзі хоста на короткий час (до 500 мс) до завершення оновлення карти ANA. |
| `0x70` | `0x0370` | `NVME_SC_HOST_PATH_ERROR` | Внутрішня транспортна помилка драйвера (тайм-аут з'єднання TCP/RDMA, втрата несучої). Ініціює негайний локальний failover. |

## 5. Структури ядра Linux (C / UAPI)

У системних заголовках ядра `include/linux/nvme.h` та `drivers/nvme/host/nvme.h` структури журналу ANA визначені відповідно до специфікації:

```c
/* Дескриптор окремої групи ANA */
struct nvme_ana_group_desc {
    __le32  grpid;      /* Ідентифікатор групи ANAGRPID (1..N) */
    __le32  nnsids;     /* Кількість ідентифікаторів NSID у масиві */
    __le64  chgcnt;     /* Локальний лічильник змін групи */
    __u8    state;      /* Стан: 0x01 (AO), 0x02 (ANO), 0x03 (AI), 0x04 (PL), 0x0F (Change) */
    __u8    rsvd17[15]; /* Зарезервовано */
    __le32  nsids[];    /* Гнучкий масив ідентифікаторів NSID */
};

/* Повний заголовок журналу ANA Log Page */
struct nvme_ana_log {
    __le64  chgcnt;     /* Глобальний лічильник змін підсистеми */
    __le16  ngrps;      /* Загальна кількість дескрипторів груп */
    __u8    rsvd10[6];  /* Зарезервовано */
};
```

### Алгоритм ітерування дескрипторів змінної довжини

Оскільки кожен дескриптор містить динамічну кількість елементів `nsids[]`, обчислення зсуву до наступного дескриптора в буфері пам'яті виконується за формулою:

```c
static inline struct nvme_ana_group_desc *
nvme_ana_next_desc(struct nvme_ana_group_desc *desc)
{
    size_t size = sizeof(*desc) + le32_to_cpu(desc->nnsids) * sizeof(__le32);
    return (struct nvme_ana_group_desc *)((void *)desc + size);
}
```

## 6. Дерево атрибутів у віртуальній файловій системі sysfs

Підсистема нативного мультипасингу NVMe експортує стан контролерів, спільних просторів назв та груп ANA через файлову систему `/sys`:

```
/sys/class/nvme-subsystem/nvme-subsys0/
├── iopolicy                    # [rw] Політика вибору шляху: numa | round-robin | queue-depth
├── model                       # [ro] Назва моделі дискового масиву
├── subsysnqn                   # [ro] NQN підсистеми (nqn.2014-08.org.nvmexpress:...)
├── nvme0                       # Символьне посилання на перший контролер (/dev/nvme0)
│   ├── address                 # Мережева адреса (traddr=192.168.10.1,trsvcid=4420)
│   ├── state                   # Поточний стан лінку: live | resetting | deleting
│   ├── transport               # Тип транспорту: tcp | rdma | pcie | fc
│   └── numa_node               # Номер вузла NUMA процесора (наприклад, 0)
├── nvme1                       # Символьне посилання на другий контролер (/dev/nvme1)
│   ├── address                 # Мережева адреса (traddr=192.168.20.1,trsvcid=4420)
│   ├── state                   # Поточний стан лінку: live
│   └── numa_node               # Номер вузла NUMA процесора (наприклад, 1)
└── nvme0n1                     # Спільний блоковий вузол простору назв (nvme_ns_head)
    ├── ana_grpid               # Номер групи ANA для цього тому (наприклад, 1)
    ├── ana_state               # Поточний стан маршруту: optimized | non-optimized
    └── hidden                  # Прапорець 0 (вузол відкритий для додатків)
```

### Практичні операції керування через sysfs

1. **Глобальне ввімкнення нативного мультипасингу під час старту системи:**
   Параметр передається в опціях завантаження ядра `nvme_core.multipath=Y` або конфігурується через модуль:
   ```bash
   echo "options nvme_core multipath=Y" > /etc/modprobe.d/nvme.conf
   ```

2. **Динамічне перемикання політики балансування введення-виведення (`iopolicy`):**
   ```bash
   # Встановлення кругової політики для конкретної підсистеми без перезавантаження
   echo "round-robin" > /sys/class/nvme-subsystem/nvme-subsys0/iopolicy

   # Встановлення політики на основі локальності пам'яті NUMA
   echo "numa" > /sys/class/nvme-subsystem/nvme-subsys0/iopolicy
   ```

3. **Моніторинг стану шляхів окремого простору назв:**
   ```bash
   # Перевірка групи ANA та стану для конкретного шляху контролера nvme0
   cat /sys/block/nvme0c0n1/ana_grpid
   cat /sys/block/nvme0c0n1/ana_state
   ```

## 7. Конфігурація цільового вузла (NVMe-oF Target ConfigFS)

У середовищі ядра Linux на боці програмного дискового масиву цільовий драйвер `nvmet` дозволяє вручну створювати групи ANA та керувати їхніми станами через віртуальну файлову систему `configfs`:

```bash
# 1. Створення групи ANA з ідентифікатором 1 для мережевого порту 1
mkdir -p /sys/kernel/config/nvmet/ports/1/ana_groups/1

# 2. Призначення стану Optimized для цієї групи на порту 1
echo "optimized" > /sys/kernel/config/nvmet/ports/1/ana_groups/1/state

# 3. Створення тієї самої групи ANA 1 на резервному мережевому порту 2 зі станом Non-Optimized
mkdir -p /sys/kernel/config/nvmet/ports/2/ana_groups/1
echo "non-optimized" > /sys/kernel/config/nvmet/ports/2/ana_groups/1/state

# 4. Прив'язка простору назв 1 цільової підсистеми до створеної групи ANA 1
echo 1 > /sys/kernel/config/nvmet/subsystems/nvme-subsys-test/namespaces/1/ana_grpid
```

## 8. Інтерфейс системних викликів ioctl (NVME_IOCTL_ADMIN_CMD)

Для взаємодії з адміністративною чергою контролера безпосередньо з простору користувача використовується виклик керування `ioctl(fd, NVME_IOCTL_ADMIN_CMD, &cmd)` над символьним вузлом контролера `/dev/nvmeX`.

Структура команди керування `struct nvme_passthru_cmd` (або `struct nvme_admin_cmd`) визначена у системному заголовку `linux/nvme_ioctl.h`:

```c
struct nvme_passthru_cmd {
    __u8    opcode;       /* Код операції: 0x02 (Get Log Page) */
    __u8    flags;        /* Прапорці команди */
    __u16   rsvd1;        /* Зарезервовано */
    __u32   nsid;         /* Ідентифікатор простору назв (0xFFFFFFFF для загального журналу) */
    __u32   cdw2;         /* Командне слово 2 */
    __u32   cdw3;         /* Командне слово 3 */
    __u64   metadata;     /* Вказівник на буфер метаданих (якщо підтримується) */
    __u64   addr;         /* Вказівник користувача на буфер даних (uintptr_t) */
    __u32   metadata_len; /* Довжина буфера метаданих */
    __u32   data_len;     /* Довжина буфера даних у байтах */
    __u32   cdw10;        /* Командне слово 10: молодші 8 бітів — LID (0x0C), біти 31:16 — NUMDL */
    __u32   cdw11;        /* Командне слово 11: біти 15:0 — NUMDU (старша частина довжини) */
    __u32   cdw12;        /* Командне слово 12: зміщення в журналі (Log Page Offset Low) */
    __u32   cdw13;        /* Командне слово 13: зміщення в журналі (Log Page Offset High) */
    __u32   cdw14;        /* Командне слово 14 */
    __u32   cdw15;        /* Командне слово 15 */
    __u32   timeout_ms;   /* Тайм-аут виконання команди у мілісекундах */
    __u32   result;       /* Результат виконання (Dword 0 відповіді контролера) */
};
```

### Обчислення розміру та зчитування фрагментованих журналів

Якщо кількість груп ANA на цільовому масиві велика (сотні або тисячі дескрипторів), розмір журналу може перевищувати максимальний розмір однієї транзакції передавання даних контролера (MDTS — *Maximum Data Transfer Size*).

У такому випадку хост виконує зчитування у два етапи:
1. **Зчитування заголовка (16 байтів):** хост надсилає команду `Get Log Page` з довжиною буфера 16 байтів (`data_len = 16`, `cdw10 = 0x0003000C`), зчитує поля `ngrps` та поточний глобальний лічильник `chgcnt`.
2. **Обчислення загального розміру:** на основі очікуваного числа груп хост виділяє динамічний буфер достатнього розміру і за потреби зчитує наступні блоки, передаючи зміщення у байтах через поля `cdw12` та `cdw13` (`Log Page Offset`).
3. **Верифікація цілісності:** після завершення завантаження драйвер повторно перевіряє лічильник `chgcnt` у заголовку. Якщо під час передавання відбулася зміна топології масиву, лічильник зміниться, і хост зобов'язаний повторити завантаження з нульового зміщення.

## 9. Події uevent ядра та моніторинг у просторі користувача

Коли ядро обробляє асинхронне сповіщення AER Notice про зміну стану ANA, воно не лише оновлює внутрішні вказівники маршрутизації `ns->ana_state`, а й генерує подію `uevent` для системного демона `udevd`.

Зразок середовища події ядра, яку можна перехопити через `udevadm monitor --environment`:

```
UDEV  [12485.621904] change   /devices/virtual/nvme-subsystem/nvme-subsys0 (nvme-subsystem)
ACTION=change
DEVPATH=/devices/virtual/nvme-subsystem/nvme-subsys0
SUBSYSTEM=nvme-subsystem
NVME_EVENT=ana_change
NVME_AEN=0x02030c
SEQNUM=4821
```

Це дозволяє створювати правила `udev` або запускати зовнішні скрипти моніторингу (наприклад, для надсилання метрик у Prometheus чи сповіщення чергового інженера про перемикання трафіку на неоптимальний проксі-канал) без жодного фонового навантаження на опитування підсистеми введення-виведення.
