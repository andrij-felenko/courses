# 📋 Відображення регістрів і доступ до них: усі виклики з їхніми гарантіями

Це контракт родини `ioremap`/`readl`: що повертає кожен виклик і чим сигналить про невдачу, який тип пам'яті ставить у запис таблиці сторінок, які бар'єри несе кожен доступник і звідки його можна кликати — плюс облік фізичних адрес і правила поводження з `void __iomem *`. Довідка потрібна тому, що імена тут різняться на суфікс, гарантії — принципово, а компілятор мовчить, коли взято сусіднє.

Підписи — з `include/asm-generic/io.h`, `include/linux/ioport.h`, `lib/devres.c` ядра 6.x. Де поведінка залежить від архітектури, названо конкретну.

## Три протоколи невдачі

Найдорожча помилка в цій родині — не переплутати виклик, а переплутати спосіб перевірки. Способів рівно три, і вони між собою несумісні.

| Що повертає | Ознака невдачі | Хто так робить |
| --- | --- | --- |
| `void __iomem *` | `NULL` | `ioremap` та всі його суфіксні варіанти, `devm_ioremap`, `of_iomap`, `pci_iomap` |
| `void __iomem *` | `IS_ERR()`, код через `PTR_ERR()` | усе, чиє ім'я містить `_resource`, і `devm_of_iomap` |
| `struct resource *` | `NULL` | `request_mem_region` і рідня |

Перевірка `if (!base)` над результатом `devm_ioremap_resource()` пропускає помилку далі: `ERR_PTR(-EBUSY)` — це вказівник `0xfffffffffffffff0`, і він не нуль. Перший же `readl` за ним валить ядро в місці, яке нічим не нагадує причину. Зворотна плутанина безпечніша, але теж хибна: `IS_ERR(NULL)` — хиба, тож невдалий `ioremap` пройде як успіх.

## Виклики відображення

```c
void __iomem *ioremap(phys_addr_t offset, size_t size);
void          iounmap(volatile void __iomem *addr);

void __iomem *devm_ioremap(struct device *dev, resource_size_t offset,
                           resource_size_t size);
void __iomem *devm_ioremap_resource(struct device *dev,
                                    const struct resource *res);
void __iomem *devm_platform_ioremap_resource(struct platform_device *pdev,
                                             unsigned int index);
void __iomem *devm_platform_ioremap_resource_byname(struct platform_device *pdev,
                                                    const char *name);
void __iomem *devm_platform_get_and_ioremap_resource(struct platform_device *pdev,
                                                     unsigned int index,
                                                     struct resource **res);
void __iomem *devm_of_iomap(struct device *dev, struct device_node *node,
                            int index, resource_size_t *size);
void __iomem *of_iomap(struct device_node *np, int index);

void __iomem *pci_iomap(struct pci_dev *dev, int bar, unsigned long max);
void          pci_iounmap(struct pci_dev *dev, void __iomem *addr);
```

| Виклик | Звідки бере діапазон | Записує себе в облік | Прибирає за собою | Невдача |
| --- | --- | --- | --- | --- |
| `ioremap` | з аргументів | ні | ні — потрібен `iounmap` | `NULL` |
| `devm_ioremap` | з аргументів | ні | так | `NULL` |
| `devm_ioremap_resource` | зі `struct resource` | так | так | `ERR_PTR` |
| `devm_platform_ioremap_resource` | ресурс №`index` [платформного пристрою](topic:unix-linux/platform-bus) | так | так | `ERR_PTR` |
| `devm_platform_ioremap_resource_byname` | ресурс на ім'я `name` | так | так | `ERR_PTR` |
| `devm_platform_get_and_ioremap_resource` | те саме, плюс віддає сам ресурс через `res` | так | так | `ERR_PTR` |
| `of_iomap` | властивість `reg` вузла [дерева пристроїв](topic:unix-linux/device-tree) | **ні** | ні | `NULL` |
| `devm_of_iomap` | те саме | так | так | `ERR_PTR` |
| `pci_iomap` | вікно (BAR) [пристрою PCI](topic:unix-linux/pci-in-linux) | ні — окремо `pci_request_regions` | ні | `NULL` |

Коди помилок з останнього стовпця не довільні, і кожен показує на свою причину: `-EINVAL` — ресурс не типу `IORESOURCE_MEM` (майже завжди це означає, що `platform_get_resource` повернув `NULL`, бо в описі пристрою такого діапазону просто нема); `-EBUSY` — діапазон уже записаний за кимось; `-ENOMEM` — саме відображення не вдалося. Перед поверненням `devm_ioremap_resource` сам друкує зрозумілий рядок у журнал через `dev_err_probe`, тож дублювати повідомлення в драйвері не треба.

Ланцюжок [керованих ресурсів](topic:unix-linux/devres-managed-resources) звільняє відображення при від'єднанні драйвера в порядку, зворотному до захоплення. Через це `devm_iounmap` майже ніколи не потрібен: він існує для тих рідкісних випадків, коли відображення треба зняти раніше, ніж помре пристрій.

Там, де `iounmap` таки пишуть руками, діє окреме правило: йому віддають рівно той вказівник, який повернув `ioremap`, — не зсунутий на адресу регістра, не вирівняний, не перерахований. Ядро шукає за цим числом свій запис у списку областей `vmalloc`; зсунутий вказівник у списку не знайдеться, і замість звільнення вийде `WARN` у журналі та назавжди втрачений шматок адресного простору ядра. Тому базу тримають в окремому полі структури драйвера, а арифметику зсувів роблять тільки в місці доступу.

## Тип пам'яті: варіанти ioremap

| Виклик | Що дозволено процесорові | Атрибут на arm64 | Якщо архітектура не вміє |
| --- | --- | --- | --- |
| `ioremap` | нічого: без кешу, без випереджального читання, без об'єднання, без перестановок | `Device-nGnRE` | є завжди |
| `ioremap_wc` | об'єднання записів, випередження, перестановки | `Normal-NC` | **тихо стає `ioremap`** |
| `ioremap_wt` | те саме плюс кешування наскрізь: читання можуть іти з кеша | нема окремого | **тихо стає `ioremap`** |
| `ioremap_cache` | усе, що й зі звичайною пам'яттю, зі зворотним записом | `Normal` | визначений не скрізь |
| `ioremap_np` | нічого, і запис не вважається завершеним, доки пристрій його не прийняв | `Device-nGnRnE` | **повертає `NULL`** |
| `ioremap_uc` | некешоване строго (UC, а не UC-) через таблиці PAT — x86 обох розрядностей, історично й ia64 | — | **повертає `NULL`** |

Різниця між двома видами відсутності — головне, що варто винести з цієї таблиці. Коли архітектура не має `ioremap_wc`, макрос розгортається в звичайний `ioremap`: драйвер працює правильно, просто повільніше, і перевіряти нічого не треба. Коли вона не має `ioremap_np` чи `ioremap_uc`, виклик повертає `NULL` — і драйвер, якому потрібні невідкладені записи, зобов'язаний мати запасний шлях через звичайний `ioremap`.

Здебільшого вибирати не доводиться зовсім. У ресурсі є прапорець `IORESOURCE_MEM_NONPOSTED`, який виставляє шина за описом заліза; побачивши його, і `devm_ioremap_resource`, і `of_iomap` самі підвищують відображення до `ioremap_np`. Саме тому переносні драйвери на машинах, де шина вимагає невідкладених записів, працюють без жодної правки.

> 🔧 **Навіщо це.** Найкоротший шлях до помилки, яку не видно на випробуванні, — узяти `ioremap_wc` для регістрів «щоб швидше». На arm64 це справді змінює атрибут на `Normal-NC`, і біт стану починає читатися з випередженням; на x86 різниця менша, а на архітектурі без підтримки різниці не буде взагалі. Помилка проявиться на третій платформі, у чужих руках.

## Доступники

Кожен доступник — три дії, і родини різняться саме тим, скільки з них лишається. Це видно просто з тіла:

```c
static inline u32 readl(const volatile void __iomem *addr)
{
        u32 val;
        __io_br();                                          /* бар'єр до доступу */
        val = __le32_to_cpu((__le32 __force)__raw_readl(addr));
        __io_ar(val);                                       /* бар'єр після доступу */
        return val;
}

static inline void writel(u32 value, volatile void __iomem *addr)
{
        __io_bw();                                          /* бар'єр до доступу */
        __raw_writel((u32 __force)__cpu_to_le32(value), addr);
        __io_aw();
}
```

Розстановка бар'єрів несиметрична, і саме так і треба. На arm64 `__io_bw()` — це `dma_wmb()`: усе, що вже записано у звичайну пам'ять, лягає туди раніше, ніж пристрій дістане команду. `__io_ar(v)` — це `dma_rmb()` плюс штучна залежність за даними від прочитаного значення, щоб наступний `udelay()` не поїхав уперед. А `__io_br()` та `__io_aw()` там порожні: перед читанням і після запису впорядковувати нема чого.

| Родина | Ширина | Порядок байтів | Бар'єри | З обробника переривання |
| --- | --- | --- | --- | --- |
| `readb/w/l/q`, `writeb/w/l/q` | 8/16/32/64 | від молодшого байта ↔ рідний | проти звичайної пам'яті **й** між собою | так |
| `*_relaxed` | те саме | те саме | лише між собою в межах пристрою | так |
| `__raw_read*`, `__raw_write*` | те саме | **рідний, без перетворення** | жодних, навіть проти замків | так |
| `ioread8/16/32/64`, `iowrite*` | те саме | від молодшого байта ↔ рідний | як у `readl`/`writel` | так |
| `ioread16be/32be/64be`, `iowrite*be` | 16/32/64 | **від старшого байта** ↔ рідний | як у `readl`/`writel` | так |
| `readsb/w/l/q`, `writesb/…`, `ioread32_rep` | пачка слів у ту саму адресу | **без перетворення** | як у базових | так |
| `memcpy_fromio`, `memcpy_toio`, `memset_io` | вибирає реалізація | **без перетворення** | як у базових | так |

Жоден доступник не спить і не бере замків, тож обмежень на [контекст](topic:unix-linux/interrupts-bottom-halves) немає ніде: усі вони придатні й у перериванні, і під спінлоком. Спати вміє інше — саме відображення (`ioremap` і все, що його обгортає), тому воно живе в `probe()`, а не в обробнику.

Родина `ioread*`/`iowrite*` відрізняється від `readl`/`writel` не гарантіями, а тим, що приймає й маркери простору портів, здобуті через `pci_iomap` чи `ioport_map`. Драйвер, який має обслуговувати ту саму мікросхему і у вікні пам'яті, і на портах, пишеться один раз саме через неї.

`readq` і `writeq` існують лише на 64-бітних архітектурах. Драйверові, якому потрібен 64-бітний регістр і на 32 бітах, треба підключити `<linux/io-64-nonatomic-lo-hi.h>` (або `-hi-lo.h`): там `readq` визначено як `lo_hi_readq` — два 32-бітні доступи, спершу молодша половина. Це вже дві транзакції на шині, а не одна, і порядок половин має значення: багато мікросхем клацають знімок регістра саме на доступі до однієї з них, тому заголовок вибирають за документацією, а не навмання.

Байтові операції над великими вікнами робляться тільки трьома названими функціями. Звичайний `memcpy` над `__iomem`-адресою — помилка не стилю, а суті: бібліотечна реалізація сама вибирає ширину доступів, порядок і кількість проходів, і залюбки скористається інструкціями, від яких залізо здригнеться. Але й `memcpy_toio` не годиться для регістрів із побічним ефектом — вона теж не обіцяє ні ширини, ні кількості транзакцій; її місце — суцільна пам'ять пристрою, кадровий буфер, вікно прошивки.

## Облік діапазонів

```c
struct resource *request_mem_region(resource_size_t start, resource_size_t n,
                                    const char *name);
struct resource *request_mem_region_exclusive(...);   /* + IORESOURCE_EXCLUSIVE */
struct resource *request_mem_region_muxed(...);       /* + IORESOURCE_MUXED */
void             release_mem_region(resource_size_t start, resource_size_t n);

struct resource *devm_request_mem_region(struct device *dev, ...);
void             devm_release_mem_region(struct device *dev, ...);
```

Усі вони — обгортки над `__request_region(&iomem_resource, …)`, тобто вставляють вузол у дерево `struct resource`, що описує зайнятість фізичного адресного простору. Повертають `NULL`, коли діапазон перетинається з чужим уже зайнятим. `IORESOURCE_MUXED` каже, що діапазон свідомо ділять кілька драйверів по черзі; `IORESOURCE_EXCLUSIVE` — навпаки, забороняє простору користувача відображати цей діапазон через `/dev/mem`, коли зібрано з `CONFIG_IO_STRICT_DEVMEM`.

## Формат /proc/iomem

Дерево ресурсів видно у [файлі](topic:unix-linux/proc-filesystem) `/proc/iomem`. Рядок друкує `r_show()` у `kernel/resource.c`, і формат у нього незмінний: два пробіли відступу на кожен рівень вкладеності, початок і кінець — шістнадцятковими з провідними нулями до восьми розрядів, розділювач ` : `, далі ім'я з `request_mem_region`.

```
40000000-bfffffff : System RAM
  40210000-41a4ffff : Kernel code
  41c00000-4213ffff : Kernel data
e0001000-e0001fff : e0001000.ethernet
  e0001000-e0001fff : e0001000.ethernet
```

Вкладена пара в кінці — не помилка: зовнішній рядок завела шина, розібравши опис пристрою, а внутрішній додав `devm_ioremap_resource`, і ім'я він склав сам із `dev_name(dev)` (плюс ім'я ресурсу, якщо воно є). Відсутність внутрішнього рядка означає рівно одне — драйвер до цього діапазону ще не прив'язався.

Числа видно тільки тому, хто має `CAP_SYS_ADMIN`; решті `r_show` підставляє нулі, тож звичайний користувач бачить стовпчик `00000000-00000000` з правильними іменами. Це не поламка виводу, а захист від того, щоб адреси ядра не витікали в підказку для атаки.

## void \_\_iomem \* і sparse

```c
# define __iomem   __attribute__((noderef, address_space(__iomem)))
# define __force   __attribute__((force))
```

У звичайній збірці обидва макроси порожні. Значення вони мають лише для статичного перевіряча [sparse](topic:unix-linux/sparse-checker), якого запускають окремо: `make C=1` — на щойно перезібрані файли, `make C=2` — на всі. Атрибут `noderef` забороняє розіменування, `address_space` робить цей вказівник несумісним зі звичайним в обидва боки.

Отже, з `void __iomem *` законні рівно три дії: віддати доступникові, додати цілий зсув і порівняти з `NULL` або перевірити через `IS_ERR`. Усе інше — привласнити `void *`, розіменувати, покласти в `struct` зі звичайним типом поля, надрукувати як `%p` — це діагностика.

`__force` глушить цю перевірку в одному конкретному перетворенні. У драйвері він майже завжди означає помилку; його місце — інфраструктура, і обидва приклади вже траплялися вище. Перший — усередині `readl`: `(__le32 __force)__raw_readl(addr)`, бо `__raw_readl` повертає простий `u32`, а `__le32_to_cpu` чекає окремого типу з міткою порядку байтів, і без примусу sparse обурився б саме на це. Другий — спосіб віддати код помилки крізь `__iomem`-вказівник:

```c
#define IOMEM_ERR_PTR(error)  (__force void __iomem *)ERR_PTR(error)
```

Саме він і робить можливим третій протокол невдачі з першої таблиці.

## Мінімальний повний виклик

```c
/* один раз, при прив'язці: займає діапазон, відображає, чіпляє звільнення */
priv->regs = devm_platform_ioremap_resource(pdev, 0);
if (IS_ERR(priv->regs))
        return PTR_ERR(priv->regs);

/* дескриптор у звичайній пам'яті — і команда пристроєві;
   бар'єр між ними несе сам writel, писати його вручну не треба */
desc->flags = cpu_to_le32(DESC_OWN);
writel(TX_KICK_GO, priv->regs + REG_TX_KICK);

/* скидання причини переривання — і зустрічне читання, щоб запис дійшов */
writel(cause, priv->regs + REG_IRQ_CAUSE);
readl(priv->regs + REG_IRQ_CAUSE);
```

Ні `request_mem_region`, ні `iounmap`, ні `release_mem_region` тут нема — і це не скорочення заради прикладу, а поточний вигляд правильного драйвера.
