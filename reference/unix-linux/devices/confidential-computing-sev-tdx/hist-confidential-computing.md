# 📜 Історія розвитку TEE: від TPM і SGX до ізоляції віртуальних машин

Концепція довірених середовищ виконання (Trusted Execution Environments, TEE) виникла як відповідь на фундаментальну суперечність хмарної епохи: власник фізичного сервера (хмарний провайдер) та власник алгоритмів і даних (орендар) є різними суб'єктами з різними рівнями довіри. У традиційній моделі віртуалізації той, хто контролює фізичний сервер і ядро хостової операційної системи, автоматично має повний доступ до всіх даних користувача. Зростання обсягів обробки конфіденційних даних у публічних ЦОД — банківських транзакцій, персональних медичних записів, моделей штучного інтелекту та криптографічних ключів — вимагало створення апаратних механізмів, які б криптографічно обмежували права самого власника обладнання.

Еволюція апаратної довіри тривала понад два десятиліття і пройшла чотири послідовні етапи: від пасивного вимірювання завантаження до повноцінної криптографічної ізоляції віртуальних машин.

---

## 1. Зародження апаратної довіри: TPM та концепція зафіксованого стану завантаження

Наприкінці 1990-х років альянс провідних технологічних компаній заснував організацію TCPA (Trusted Computing Platform Alliance, пізніше перейменовану на TCG — Trusted Computing Group). Метою альянсу було створення апаратного «кореня довіри» (Root of Trust) для персональних комп'ютерів та серверів. Результатом цієї роботи стала специфікація криптографічного мікроконтролера **TPM (Trusted Platform Module)**.

Основна ідея TPM полягала у створенні окремого захищеного чіпа, під'єднаного до системної шини (LPC або SPI). Чіп містив у собі генератор випадкових чисел, незмінний первинний ключ (Endorsement Key) та набір спеціальних регістрів — **PCR (Platform Configuration Registers)**. 

Детальний опис того, як прошивка та завантажувач використовують TPM для послідовного вимірювання коду ядра та збереження криптографічних хешів у регістрах PCR, наведено у [виміряному завантаженні та PCR](book:unix-linux/measured-boot-pcr).

Проте TPM мав фундаментальне обмеження: він був пасивним спостерігачем. TPM дозволяв перевірити, чи не було модифіковано початковий код завантаження (Measured Boot), та заблокувати видачу ключів розшифрування диска (Sealing), якщо стан регістрів PCR не відповідав еталону. Але після того, як операційна система завантажувалася в оперативну пам'ять, TPM ніяк не міг захистити дані в DRAM від зчитування зловмисником із привілеями `Ring 0`.

## 2. Мобільна розділеність: ARM TrustZone та концепція двох світів

З появою смартфонів та мобільних платіжних систем у середині 2000-х років виникла потреба захистити біометричні дані користувача та криптографічні ключі платіжних карток від потенційно вразливої або скомпрометованої операційної системи (наприклад, Android із кустарними root-правами). Реакцією компанії ARM стало створення технології **ARM TrustZone** (представленої у специфікаціях архітектур ARMv6Z та ARMv7-A).

TrustZone розділила процесорне ядро, системну шину та периферію на два криптографічно ізольовані рівні виконання (Dual-World Architecture):
- **Нормальний світ (Normal World / Non-Secure World)**: Звичайне середовище, у якому виконується операційна система Android чи Linux, усі її користувацькі програми та драйвери.
- **Захищений світ (Secure World)**: Захищене середовище, у якому працює спеціалізована мікроядерна ОС (Secure OS, наприклад OP-TEE чи Trusty) та довірені аплети (Trusted Applications, TA).

```
Архітектура ARM TrustZone (Розділення світів):

+----------------------------------+  +----------------------------------+
|           NORMAL WORLD           |  |           SECURE WORLD           |
|  +----------------------------+  |  |  +----------------------------+  |
|  | User Apps / Android OS     |  |  |  | Trusted Apps (TA)          |  |
|  +----------------------------+  |  |  +----------------------------+  |
|  | Linux Kernel (Non-Secure)  |  |  |  | Secure OS (OP-TEE / Trusty)|  |
|  +----------------------------+  |  |  +----------------------------+  |
+----------------------------------+  +----------------------------------+
|                  Secure Monitor / SMC Instruction                       |
+------------------------------------------------------------------------+
|                  Апаратні шини та контролери пам'яті                   |
+------------------------------------------------------------------------+
```

Перехід між світами здійснювався через спеціальну апаратну інструкцію `SMC` (Secure Monitor Call) та проміжний шар прошивки Secure Monitor. Контролер пам'яті перевіряв спеціальний біт `NS` (Non-Secure bit) на системній шині: якщо пристрій з Нормального світу намагався зчитати сторінку пам'яті, марковану як Захищена, апаратура повертала помилку bus fault.

TrustZone виявилася вкрай успішною для мобільних пристроїв та систем відбитків пальців (Apple Secure Enclave побудовано на схожих принципах). Однак для хмарних ЦОД ця модель виявилася непридатною: Захищений світ у TrustZone є єдиним і монолітним. Вбудувати туди тисячі незалежних віртуальних машин різних орендарів хмари було неможливо, оскільки всі аплети Захищеного світу мусили довіряти єдиній Secure OS.

## 3. Прикладні анклави: Злет і падіння Intel SGX

У 2015 році разом із мікроархітектурою Skylake компанія Intel зробила масштабну спробу вирішити проблему хмарного TEE для серверів x86-64, представивши технологію **Intel SGX (Software Guard Extensions)**.

Філософія SGX спиралася на парадигму «прикладного анклаву» (application enclave). Розробники SGX виходили з припущення, що передавати всю операційну систему чи ВМ у середовище довіри недоцільно, оскільки мільйони рядків коду ядра Linux містять вразливості. Замість цього SGX пропонував ізолювати лише найкритичніші функції застосунку (наприклад, модуль обчислення банківського траншу чи обробник приватного ключа RSA).

### Механіка роботи SGX

Програма користувача у звичайному `Ring 3` могла виділити ділянку пам'яті під назвою **EPC (Enclave Page Cache)**. При вступі в анклав за допомогою інструкції `EENTER` процесор перемикався у захищений режим виконання:
1. Апаратний рушій пам'яті MEE (Memory Encryption Engine) шифрував усі сторінки EPC у DRAM за допомогою ефемерного ключа AES.
2. Процесор блокував доступ до EPC для ядра Linux, гіпервізора, відлагоджувачів gdb та інших процесів. Будь-яке зчитування сторінки EPC ззовні анклаву апаратура обслуговувала як «покинуту сторінку» (abort page): читання повертало самі байти `0xFF`, а запис мовчки зникав.
3. Системні виклики (`syscall`) зсередини анклаву були заборонені на рівні мікрокоду CPU. Якщо анклаву потрібно було зчитати файл із диска або відправити пакет у мережу, він мусив виконати `EEXIT`, передати дані у відкриту пам'ять і попросити ядро Linux виконати операцію I/O.

### Чому концепція SGX зазнала невдачі у ЦОД

Попри революційну криптографію, практичне застосування Intel SGX у хмарах зіткнулося з трьома нездоланними бар'єрами:

1. **Колосальне ускладнення розробки**: Жоден готовий серверний застосунок (PostgreSQL, NGINX, Redis) не міг працювати в SGX без глибокого переписування. Відсутність прямого доступу до `syscall` змусила інженерну спільноту створювати складні проміжні прошарки (LibOS, такі як Gramine, Graphene чи Occlum), які емулювали системні виклики Linux усередині анклаву, що зводило нанівець ідею «малого обсягу довіреного коду».
2. **Апаратні обмеження EPC**: Початкові процесори Intel Xeon мали жорсткий розмір EPC пам'яті — всього від 64 МБ до 256 МБ на весь фізичний сокет. Коли анклав вимагав більше пам'яті, ядро Linux змушене було виконувати процедуру EWB (Enclave Page Write-Back) — криптографічне вивантаження сторінок у звичайну DRAM під контролем недовіреного ядра, що знижувало продуктивність у десятки разів.
3. **Хвиля атак по побічних каналах (Side-Channel Crisis)**: У період з 2018 по 2021 рік дослідники з безпеки виявили десятки фундаментальних атак на SGX (Foreshadow/L1TF, ZombieLoad, RIDL, Fallout, Plundervolt, SGAxe). Оскільки анклав виконувався на тих самих внутрішніх конвеєрах і кешах CPU, що й звичайні процеси, зловмисний гіпервізор міг через маніпуляцію спекулятивним виконанням команд (Speculative Execution), мікроархітектурними буферами та частотою процесора побайтово витягувати криптографічні ключі з «захищеного» анклаву.

## 4. Парадигма конфіденційних віртуальних машин (Confidential VMs)

Розчарування у прикладних анклавах SGX змусило індустрію переглянути підхід. У 2016–2020 роках компанія AMD запропонувала альтернативну концепцію: ізолювати не окремий процес чи функцію, а **всю віртуальну машину разом із її гостьовим ядром Linux та всім стеком програм**.

```
Порівняння підходів ізоляції:

+-----------------------------------+  +-----------------------------------+
|     Прикладний анклав (SGX)       |  | Конфіденційна ВМ (SEV-SNP / TDX)  |
|  +-----------------------------+  |  +---------------------------------+  |
|  | Довірений модуль (Enclave)  |  |  | Unmodified Apps (Postgres/NGINX)|  |
|  +-----------------------------+  |  +---------------------------------+  |
|  | Unencrypted User App & OS   |  |  | Guest Linux Kernel (Encrypted)  |  |
|  +-----------------------------+  |  +---------------------------------+  |
| (Вимагає переписування коду)    |  | (Працює повністю без змін коду)   |  |
+-----------------------------------+  +-----------------------------------+
```

Переваги підходу Confidential VMs виявилися вирішальними:
- **Нульові зміни у програмному забезпеченні**: Користувач може взяти готовий образ Ubuntu Server, Debian або Red Hat Enterprise Linux і запустити його всередині конфіденційного середовища без жодної перекомпіляції коду.
- **Апаратна підтримка обсягів пам'яті**: Замість МБ у SGX, нові технології AMD SEV-SNP та Intel TDX дозволяють шифрувати терабайти оперативної пам'яті для однієї ВМ.
- **Стандартизація в індустрії**: Заснування консорціуму Confidential Computing Consortium (CCC) під егідою Linux Foundation остаточно закріпило парадигму повноцінних конфіденційних віртуальних машин як стандарт апаратного захисту в хмарних інфраструктурах AWS, Google Cloud та Microsoft Azure.
