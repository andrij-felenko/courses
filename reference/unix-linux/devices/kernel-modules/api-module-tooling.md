# 📋 Контракт роботи з модулями: команди, директиви, покажчики, виклики

Це перелік точних форм, якими керують модулями: шість команд `kmod` з ключами, директиви `/etc/modprobe.d`, синтаксис параметрів у командному рядку ядра, покажчики в `/lib/modules/<версія>`, вікна в `/sys` і `/proc` — і три системні виклики, на яких усе це врешті лежить.

Поділ між рівнями тут не косметичний. Три системні виклики — це справжній контракт із ядром: їх не можна обійти й не можна замінити. Усе решта — угода простору користувача, яку `kmod` реалізує так, а не інакше; інша програма могла б домовитися по-своєму й ядро цього не помітило б.

## Шість команд

| команда | працює з | чим кінчається |
|---|---|---|
| `modprobe` | назвою або аліасом | `finit_module` — після читання покажчиків, конфігурації й розкриття залежностей |
| `insmod` | шляхом до файла | `finit_module` — негайно, без пошуку, конфігурації й залежностей |
| `rmmod` | назвою завантаженого модуля | `delete_module` — без залежностей |
| `lsmod` | нічим | нічим: форматує `/proc/modules` |
| `modinfo` | файлом `.ko` (або назвою — тоді шукає його) | нічим: читає секцію `.modinfo` |
| `depmod` | усім деревом модулів | нічим: переписує файли-покажчики |

Окремих програм тут насправді немає: усі шість — символьні посилання на один виконуваний файл `/usr/bin/kmod`, який дивиться, яким іменем його покликали, і робить відповідну роботу. Тому в нього є і власна форма виклику (`kmod list` замість `lsmod`), і дії, для яких старого імені ніколи не існувало — насамперед `kmod static-nodes`, що перетворює `modules.devname` на перелік вузлів, потрібних ще до появи самих модулів.

Половина набору ядра взагалі не торкається: `modinfo` і `depmod` читають файли на диску й можуть працювати на дереві чужого ядра, `lsmod` навпаки — читає лише ядро й на диск не дивиться. Ця дрібниця пояснює, чому `modinfo` показує параметри модуля, який ніколи не завантажували, а `lsmod` не знає про модулі, які лежать поруч.

### `modprobe`

```
modprobe [опції] <модуль> [<параметр>=<значення> …]
modprobe [опції] -a <модуль> [<модуль> …]
modprobe [опції] -r <модуль> [<модуль> …]
```

| ключ | дія |
|---|---|
| `-a`, `--all` | усі аргументи — назви модулів (параметри в цій формі не приймаються) |
| `-r`, `--remove` | вивантажити модуль і його залежності, що лишилися без користувачів |
| `-R`, `--show-alias` | показати всі назви модулів, які збігаються з аліасом, і вийти |
| `--show-depends` | вивести рядки `insmod <шлях> <параметри>` у порядку завантаження — разом із самим модулем |
| `-n`, `--dry-run` | зробити все, крім самого системного виклику |
| `-v`, `--verbose` | показувати кожну дію; з `-n` — найкращий спосіб зрозуміти, що станеться |
| `-c`, `--show-config` | зведена конфігурація з усіх файлів, як її бачить `modprobe` |
| `-i`, `--ignore-install`, `--ignore-remove` | не виконувати директиву `install`/`remove` |
| `-f`, `--force` | те саме, що `--force-vermagic` разом із `--force-modversion` |
| `--force-vermagic` | вирізати з образу рядок сумісності перед подачею ядру |
| `--force-modversion` | вирізати з образу хеші версій символів |
| `-C`, `--config <шлях>` | інший файл або тека конфігурації |
| `-d`, `--dirname <корінь>` | інший корінь, від якого відлічують `lib/modules` |
| `-S`, `--set-version <версія>` | дерево іншої версії ядра замість `uname -r` |
| `--first-time` | завершитися з помилкою, якщо робити було нічого (модуль уже завантажено) |
| `-q`, `--quiet` | мовчати про ненайдені модулі |
| `--show-modversions` | хеші версій символів із самого файла |
| `--show-exports` | символи, які модуль експортує |

Із цього переліку два ключі відповідають на різні питання й тому не заміняють одне одного. `--show-depends` показує **кінцевий намір**: які саме файли, в якому порядку й з яким рядком параметрів пішли б у ядро — тобто вже після злиття конфігурації. `-n -v` показує **весь шлях думки**, разом із директивами `install`, які до системного виклику взагалі не доходять; на модулі з `install` перший ключ мовчить, бо завантаження як такого не планується.

Пара `--force-*` не «примушує ядро»: вона підробляє образ до подачі, щоб перевірка не мала на що спрацювати. Ядро при цьому позначає себе як забруднене (`F` у `/proc/sys/kernel/tainted`), а модуль, зібраний проти іншого дерева, після такого завантаження поводиться непередбачувано.

### Решта

```
insmod <файл.ko> [<параметр>=<значення> …]     # ключів практично не має
rmmod  [-f] [-s] [-v] <модуль> …
lsmod                                          # ключів немає
modinfo [-F <поле>] [-0] [-k <версія>] [-b <корінь>] <модуль|файл>
depmod [-a] [-A] [-n] [-e] [-F System.map] [-E Module.symvers] [-b <корінь>] [-w] [<версія>]
```

| ключ | команда | дія |
|---|---|---|
| `-f`, `--force` | `rmmod` | зняти попри лічильник; діє лише в ядрі з `CONFIG_MODULE_FORCE_UNLOAD` |
| `-s`, `--syslog` | `rmmod` | помилки в системний журнал, а не на `stderr` |
| `-F <поле>` | `modinfo` | лише одне поле: `filename`, `license`, `depends`, `alias`, `vermagic`, `srcversion`, `parm`, `parmtype`, `signer`, `sig_key`, `intree` |
| `-p`, `-a`, `-d`, `-l`, `-n` | `modinfo` | скорочення для `parm`, `author`, `description`, `license`, `filename` |
| `-0` | `modinfo` | розділяти поля нулем — для машинного розбору |
| `-a` | `depmod` | обійти всі модулі (домовчазно, коли не названо файлів) |
| `-A` | `depmod` | перебудувати, лише якщо якийсь модуль новіший за `modules.dep` |
| `-n` | `depmod` | вивести результат у `stdout`, нічого не записуючи |
| `-e` + `-F System.map` | `depmod` | назвати символи, яких не постачає ні ядро, ні інший модуль |
| `-E Module.symvers` | `depmod` | назвати розбіжності хешів версій символів (несумісне з `-F`) |
| `-b <корінь>` | `depmod` | будувати покажчики для дерева під іншим коренем — так пакують образи |
| `-w` | `depmod` | попереджати про дублікати залежностей, аліасів і версій символів |

Окремо варто знати поля `modinfo`, які стосуються підпису: `sig_id` (формат, звично `PKCS#7`), `signer` (чиїм ключем), `sig_key` (відбиток сертифіката), `sig_hashalgo` (алгоритм гешування). Вони читаються з файла й не вимагають ані привілеїв, ані завантаження — тобто на питання «цей модуль узагалі підписаний і ким?» відповідають до того, як ядро відмовить:

```
$ modinfo xfs | grep '^sig'
sig_id:         PKCS#7
signer:         Build time autogenerated kernel key
sig_key:        3A:9C:…:F1
sig_hashalgo:   sha512
```

Жодного поля `sig*` у виводі — модуль непідписаний; чи це завадить, залежить лише від того, чи ввімкнено на машині вимогу підпису.

## `/etc/modprobe.d/*.conf`

Читаються `/etc/modprobe.d/`, `/run/modprobe.d/`, `/usr/lib/modprobe.d/` (і `/lib/modprobe.d/`); файл з тим самим іменем в `/etc` перекриває однойменний нижче, а серед решти порядок — лексичний за іменем. Розширення мусить бути `.conf`. Один запис — один рядок; продовження — зворотною похилою в кінці; коментар — `#`.

```
alias     <шаблон-із-джокерами> <модуль>
blacklist <модуль>
options   <модуль> <параметр>=<значення> […]
install   <модуль> <команда оболонки>
remove    <модуль> <команда оболонки>
softdep   <модуль> pre: <модулі…> post: <модулі…>
weakdep   <модуль> <модулі…>
```

| директива | що саме робить | межа |
|---|---|---|
| `alias` | додає до покажчика ще одне ім'я; джокери — як в оболонці (`*`, `?`, `[…]`) | аліас на аліас не працює; аліас на модуль — так |
| `blacklist` | **вимикає внутрішні аліаси модуля**, тобто добір за пристроєм | явне `modprobe <модуль>` спрацює як і раніше |
| `options` | додає параметри до кожного завантаження цього модуля | зливається з параметрами аліаса й командного рядка, а не заміняє їх |
| `install` | замість завантаження виконує команду оболонки | команда, що кличе `modprobe` на той самий модуль, зациклиться без `--ignore-install` |
| `remove` | те саме для `modprobe -r` | |
| `softdep` | залежність, якої немає в ELF-таблицях: `pre:` — до, `post:` — після | перекриває `install`/`remove` для того самого модуля |
| `weakdep` | те саме, але ініціює його ядро під час прив'язки до пристрою, а не `modprobe` наперед | новіший набуток `kmod` |

`install` бачить змінну `$CMDLINE_OPTS` — рядок параметрів, які прийшли з командного рядка. Оскільки команда всередині кличе `modprobe` знову, її неодмінно треба захистити від самозаклику:

```
install nvidia /sbin/modprobe --ignore-install nvidia $CMDLINE_OPTS && /sbin/modprobe nvidia-drm
```

Без `--ignore-install` цей рядок покличе сам себе, і `modprobe` закрутиться.

Аліас із власними параметрами — типова форма, коли для однієї моделі пристрою треба своє налаштування:

```
alias   pci:v00008086d00002723sv*sd*bc*sc*i*  iwlwifi
options iwlwifi                               power_save=0 11n_disable=1
```

Параметри з різних джерел не сперечаються, а **склеюються в один рядок** — спершу з файлів конфігурації, потім із аліаса, яким модуль знайшли, і наприкінці ті, що набрали в командному рядку. Далі цей рядок розбирає ядро зліва направо, привласнюючи значення по черзі, тож для звичайного скалярного параметра переможе останнє входження — те, що з командного рядка. Наслідок практичний: `modprobe iwlwifi power_save=1` перебиває `options` у файлі, а от параметр-масив зайвим входженням не «доповнюється», а переписується цілком.

## `/etc/modules-load.d/*.conf`

Найпростіший синтаксис у всій темі: одна назва модуля на рядок. Порожні рядки й ті, що починаються з `#` або `;`, пропускаються. Ті самі три теки (`/etc`, `/run`, `/usr/lib`) з тим самим порядком перекриття; читає це `systemd-modules-load.service` під час старту — тобто механізм належить [systemd](book:unix-linux/systemd-model), а не `kmod`.

```
# /etc/modules-load.d/50-netfilter.conf
nf_conntrack
br_netfilter
```

## Командний рядок ядра

```
<модуль>.<параметр>=<значення>            # vfio_pci.ids=10de:1b80
<модуль>.<параметр>=<a>,<b>,<c>           # масив: значення через кому, без пробілів
<модуль>.<параметр>="значення з пробілом" # лапки лишаються цілими
```

Крапка тут — не роздільник шляху, а межа між іменем модуля й іменем параметра, тож дефіси в назві модуля зазвичай пишуть як підкреслення (`vfio_pci`, не `vfio-pci`): ядро й `modprobe` зводять обидва написання до одного.

Для коду, [вкомпільованого в образ](book:unix-linux/kernel-config-and-build), це єдина дорога: ядро розбирає свій [командний рядок](book:unix-linux/bootloader-and-cmdline) на старті. Для завантажуваного модуля механізм інший і його варто знати точно: ядро таких аргументів нікуди не відкладає — **`modprobe` сам читає `/proc/cmdline` і збирає звідти параметри щоразу, коли вантажить модуль**. Тому форма з крапкою працює в обох випадках, але через двох різних виконавців.

| форма | хто виконує | дія |
|---|---|---|
| `module_blacklist=mod1,mod2` | ядро | відмовляти в завантаженні названих модулів на рівні системного виклику |
| `modprobe.blacklist=mod1,mod2` | `modprobe` | те саме, що директива `blacklist`, але без правки файлів |
| `module.sig_enforce=1` | ядро | вимагати чинний підпис; видно в `/sys/module/module/parameters/sig_enforce` |
| `initcall_blacklist=fn1,fn2` | ядро | не виконувати названих початкових викликів — інструмент налагодження вбудованого коду |

## Покажчики в `/lib/modules/<версія>/`

| файл | хто пише | що всередині |
|---|---|---|
| `modules.dep` | `depmod` | `<шлях модуля>: <шлях> <шлях>…` — увесь **транзитивний** список залежностей; шляхи відносні до цієї теки |
| `modules.dep.bin` | `depmod` | те саме у вигляді покажчика; **саме його читає `kmod`** — текстовий тримають для очей людини |
| `modules.alias`, `.bin` | `depmod` | рядки `alias <зразок> <модуль>`, зібрані із секцій `.modinfo` |
| `modules.symbols`, `.bin` | `depmod` | рядки `alias symbol:<ім'я> <модуль>` — за ними ядро просить модуль, що постачає конкретний символ |
| `modules.devname` | `depmod` | модулі, які просять створити вузол наперед; `kmod static-nodes` перетворює це на файли в `/dev` |
| `modules.builtin` | збірка ядра | перелік вкомпільованого коду; `modprobe` мовчки погоджується на такі назви замість помилки |
| `modules.builtin.modinfo` | збірка ядра | секції `.modinfo` вбудованого коду, злиті в один файл |
| `modules.builtin.bin`, `modules.builtin.alias.bin` | `depmod` | двійкові покажчики над попередніми двома |
| `modules.order` | збірка ядра | порядок, у якому модулі складалися; `depmod` бере його як старшинство при однакових аліасах |

```
$ head -2 /lib/modules/$(uname -r)/modules.dep
kernel/net/mac80211/mac80211.ko.zst: kernel/net/wireless/cfg80211.ko.zst
kernel/drivers/net/wireless/intel/iwlwifi/mvm/iwlmvm.ko.zst: kernel/drivers/net/wireless/intel/iwlwifi/iwlwifi.ko.zst kernel/net/mac80211/mac80211.ko.zst kernel/net/wireless/cfg80211.ko.zst

$ grep '^alias symbol:ieee80211_rx ' /lib/modules/$(uname -r)/modules.symbols
alias symbol:ieee80211_rx mac80211
```

## Вікна в `/sys` і `/proc`

`/sys/module/<назва>/` — те, що ядро показує про код, який зараз у ньому живе; це звичайні [псевдофайли](book:unix-linux/pseudo-filesystems), не диск.

| шлях | вміст |
|---|---|
| `parameters/<параметр>` | сама змінна; права — з третього аргументу `module_param()`, нуль означає «файла не робити» |
| `holders/` | символьні посилання на модулі, які тримають цей |
| `refcnt` | значення лічильника посилань |
| `initstate` | `coming` (ініціалізується), `live` (працює), `going` (вивантажується) |
| `taint` | літери забруднення саме цим модулем: `P` невільна ліцензія, `O` поза деревом, `F` завантажено силою, `E` без підпису, `C` staging |
| `srcversion` | хеш сирців — те саме поле, що показує `modinfo -F srcversion`; збіг доводить, що на диску й у ядрі один код |
| `coresize`, `initsize` | розмір постійної й початкової частин у байтах |
| `sections/`, `notes/` | адреси секцій і ELF-нотатки; читаються лише привілейованим — на цьому тримається адресна таємниця ядра |
| `version` | рядок із `MODULE_VERSION()`, якщо він є |

Вкомпільований код теж має тут теку — але тільки з `parameters/`. Ні `refcnt`, ні `initstate`, ні `holders/` у ній немає, і це найдешевша перевірка «модуль чи вбудоване» без жодних покажчиків:

```
$ ls /sys/module/printk/        # вкомпільоване
parameters
$ ls /sys/module/xfs/           # модуль
coresize  holders  initsize  initstate  notes  parameters  refcnt  sections  srcversion  taint
```

`/proc/modules` — шість полів через пробіл, іноді сьоме:

```
iwlmvm 602112 0 - Live 0xffffffffc0a91000
mac80211 1355776 1 iwlmvm Live 0xffffffffc0b40000
zfs 4763648 6 - Live 0xffffffffc1200000 (PO)
```

| поле | значення |
|---|---|
| 1 | назва модуля |
| 2 | розмір у байтах |
| 3 | лічильник посилань |
| 4 | тримачі через кому, або `-` |
| 5 | стан: `Live`, `Loading`, `Unloading` |
| 6 | адреса в пам'яті ядра — нулі для непривілейованого читача |
| 7 | літери забруднення в дужках, якщо є |

Сусідні важелі лежать серед [настройок ядра](book:unix-linux/sysctl-tunables): `/proc/sys/kernel/modprobe` — шлях до програми, яку ядро запускає для `request_module`; `/proc/sys/kernel/modules_disabled` — вимикач в один бік: записали `1`, і жодного модуля до перезавантаження більше не завантажити й не вивантажити.

## Три системні виклики

Обгорток у glibc немає в жодного з трьох — лише через `syscall(2)`.

```c
#include <linux/module.h>          /* лише заради прапорців */
#include <sys/syscall.h>
#include <unistd.h>

int syscall(SYS_init_module,   void *image, unsigned long size, const char *params);
int syscall(SYS_finit_module,  int fd, const char *params, int flags);
int syscall(SYS_delete_module, const char *name, unsigned int flags);
```

`params` — один рядок у тій самій формі, що в командному рядку: `"power_save=0 11n_disable=1"`. Порожній рядок означає «без параметрів»; `NULL` не приймається.

| прапорець `finit_module` | значення | дія |
|---|---|---|
| `MODULE_INIT_IGNORE_MODVERSIONS` | `1` | не звіряти хеші версій символів |
| `MODULE_INIT_IGNORE_VERMAGIC` | `2` | не звіряти рядок сумісності |
| `MODULE_INIT_COMPRESSED_FILE` | `4` | файл стиснено — розпакувати в ядрі (з Linux 5.17) |

| прапорець `delete_module` | дія |
|---|---|
| нічого | позначити модуль і **чекати в неперервному сні**, доки лічильник не впаде до нуля |
| `O_NONBLOCK` | повернутися негайно з помилкою, якщо лічильник ненульовий — саме так завжди робить `rmmod` |
| `O_NONBLOCK` разом із `O_TRUNC` | зняти попри лічильник; забруднює ядро (`TAINT_FORCED_RMMOD`) і мовчки не діє без `CONFIG_MODULE_FORCE_UNLOAD` |
| сам `O_TRUNC` | дозволяє зняти модуль, що має вхід, але не має виходу |

Коди помилок варто читати разом із текстом, який пише інструмент — бо в кількох випадках `strerror` каже зовсім не те, що сталося.

| що видно | `errno` | причина |
|---|---|---|
| `Invalid module format` | `ENOEXEC` | не ELF, не та архітектура або не збігся `vermagic` |
| `Unknown symbol in module` | `ENOENT` | нерозв'язаний символ — не «файла немає»; імена символів ядро пише в журнал |
| `Key was rejected by service` | `EKEYREJECTED` | увімкнено вимогу підпису, а модуль непідписаний або підпис не перевіряється |
| `Required key not available` | `ENOKEY` | підпис є, але потрібного [ключа](book:unix-linux/kernel-keyrings) в кільці ядра немає |
| `Bad message` | `EBADMSG` | підпис формально зіпсовано |
| `File exists` | `EEXIST` | модуль із такою назвою вже в ядрі |
| `Operation not permitted` | `EPERM` | немає [можливості](book:unix-linux/capabilities) `CAP_SYS_MODULE` або `kernel.modules_disabled=1` |
| `Device or resource busy` | `EBUSY` (завантаження) | вичерпано час на розв'язання символу |
| `Resource temporarily unavailable` | `EWOULDBLOCK` | вивантаження: ненульовий лічильник або є тримачі |
| `Device or resource busy` | `EBUSY` (вивантаження) | модуль ще не «живий» або має вхід без виходу — той самий `[permanent]` |
| `No such file or directory` | `ENOENT` (вивантаження) | модуля з такою назвою в ядрі немає |

Розбіжність `ENOENT` на двох боках — не збіг, а джерело найпоширенішої хибної діагностики: при завантаженні цей код означає «бракує символу», при вивантаженні — «бракує модуля». Подробиць у ньому немає жодних, тому [журнал ядра](book:unix-linux/journald-logging) читають не як пораду, а як обов'язковий другий крок.

## Мінімальний робочий виклик

```c
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/syscall.h>

#ifndef MODULE_INIT_COMPRESSED_FILE
#define MODULE_INIT_COMPRESSED_FILE 4
#endif

static int finit_module(int fd, const char *params, int flags)
{
    return syscall(SYS_finit_module, fd, params, flags);
}

static int delete_module(const char *name, unsigned int flags)
{
    return syscall(SYS_delete_module, name, flags);
}

/* стиснений .ko розпакує саме ядро — інакше довелося б робити це тут */
static int compressed(const char *path)
{
    const char *dot = strrchr(path, '.');
    return dot && (strcmp(dot, ".zst") == 0 ||
                   strcmp(dot, ".xz")  == 0 ||
                   strcmp(dot, ".gz")  == 0);
}

int main(int argc, char **argv)
{
    if (argc < 3) {
        fprintf(stderr, "вжиток: %s load ФАЙЛ.ko [\"параметри\"] | %s unload НАЗВА\n",
                argv[0], argv[0]);
        return 2;
    }

    if (strcmp(argv[1], "load") == 0) {
        int fd = open(argv[2], O_RDONLY | O_CLOEXEC);
        if (fd < 0) { perror("open"); return 1; }

        int flags = compressed(argv[2]) ? MODULE_INIT_COMPRESSED_FILE : 0;

        if (finit_module(fd, argc > 3 ? argv[3] : "", flags) != 0) {
            fprintf(stderr, "finit_module: %s (errno %d) — подробиці в dmesg\n",
                    strerror(errno), errno);
            close(fd);
            return 1;
        }
        close(fd);            /* образ уже в ядрі, дескриптор більше ні до чого */
        puts("завантажено");
        return 0;
    }

    if (delete_module(argv[2], O_NONBLOCK) != 0) {
        fprintf(stderr, "delete_module: %s (errno %d)\n", strerror(errno), errno);
        return 1;
    }
    puts("вивантажено");
    return 0;
}
```

Збирається як `cc -O2 -o modctl modctl.c` і працює лише з `CAP_SYS_MODULE`. Розпакування в ядрі вимагає Linux 5.17 із `CONFIG_MODULE_DECOMPRESS`; без нього прапорець повертає `EOPNOTSUPP`, і стиснений файл доводиться розпаковувати самому й подавати старим `init_module`.

Сорок рядків — і це весь контракт із ядром: ні залежностей, ні аліасів, ні конфігурації тут немає й бути не може. Усе, чим `modprobe` відрізняється від цієї програми, він робить до першого системного виклику — звичайним читанням файлів.
