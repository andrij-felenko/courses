# Символьні та блочні пристрої

В операційних системах Unix і Linux апаратне забезпечення абстрагується у вигляді спеціальних файлів пристроїв (device nodes). Ці файли є мостом між простором користувача та ядром: програми читають і пишуть у них, як у звичайні файли, а ядро перенаправляє ці операції до відповідного драйвера. Залежно від природи пристрою та способу обміну даними, пристрої поділяються на два фундаментальні класи: **символьні (character, cdev)** та **блочні (block, bdev)**.

Цей поділ зумовлений фізичними властивостями апаратури та тим, як ефективно передавати інформацію: побайтово (як потік) чи великими шматками (як масив даних із довільним доступом).

## Символьні пристрої (cdev)

Символьний пристрій — це потік даних. Читання або запис відбувається байт за байтом (або символами), строго послідовно. Дані, які витягуються із символьного пристрою, зазвичай не можна прочитати повторно — вони споживаються в момент читання.

Символьні пристрої не мають фіксованого розміру і не підтримують довільний доступ (`lseek` зазвичай повертає помилку).

### Приклади
- **Термінали та консолі** (`/dev/tty`, `/dev/console`): введення з клавіатури, виведення на екран.
- **Послідовні порти** (`/dev/ttyS0`): обмін даними через UART.
- **Псевдопристрої** (`/dev/null`, `/dev/random`, `/dev/zero`): програмні абстракції, що генерують або поглинають потік байтів.

### Архітектура та `file_operations`
Коли програма відкриває символьний файл пристрою, VFS створює структуру файлу. Для символьних пристроїв драйвер реєструє структуру `file_operations`, яка містить вказівники на функції обробки стандартних системних викликів.

:::tabs
== C (Linux Kernel API)
```c
struct file_operations my_cdev_fops = {
    .owner   = THIS_MODULE,
    .read    = my_cdev_read,
    .write   = my_cdev_write,
    .open    = my_cdev_open,
    .release = my_cdev_release,
    .unlocked_ioctl = my_cdev_ioctl,
};
```
== Rust (kernel crate)
```rust
struct MyDevice;

#[vtable]
impl file_operations::FileOperations for MyDevice {
    fn read(
        _file: &file::File,
        _data: &mut impl io::Read,
    ) -> Result<usize> {
        // Логіка послідовного читання
        Ok(0)
    }
}
```
:::

Драйвер реєструє символьний пристрій за допомогою функції `cdev_add()`, пов'язуючи мажорний і мінорний номери із цією таблицею `file_operations`. Коли програма викликає `read()`, ядро просто переходить за вказівником `.read` у таблиці драйвера.

## Блочні пристрої (bdev)

Блочний пристрій — це масив даних, до якого можливий довільний доступ. Обмін даними відбувається не побайтово, а фіксованими блоками (зазвичай 512 байт, 4 КБ тощо). Оскільки такі пристрої містять файлові системи і потребують високої пропускної здатності, пряма взаємодія з драйвером неефективна.

### Приклади
- **Жорсткі диски та SSD** (`/dev/sda`, `/dev/nvme0n1`).
- **USB-накопичувачі** (`/dev/sdb`).
- **SD-картки** (`/dev/mmcblk0`).
- **RAM-диски** (`/dev/ram0`).

### Кешування та `request_queue`
Головна відмінність блочних пристроїв — наявність проміжного шару буферизації. Коли користувач запитує дані, ядро спершу шукає їх у **сторінковому кеші (page cache)**. Якщо даних немає, запит на читання формується і додається до черги запитів — **`request_queue`**.

Черга запитів дозволяє ядру оптимізувати доступ:
1. **Злиття (Merging):** Суміжні запити об'єднуються в один великий.
2. **Сортування (Sorting):** Запити перевпорядковуються для зменшення рухів магнітної головки (актуально для HDD) або оптимізації доступу до флеш-пам'яті (через I/O планувальники, як-от `mq-deadline`, `bfq`).

### Архітектура та `block_device_operations`
Драйвери блочних пристроїв не обробляють `read` і `write` безпосередньо. Вони реєструють структуру `block_device_operations`, яка описує низькорівневе керування пристроєм (наприклад, монтування або специфічні ioctl), а безпосередня передача даних керується через `request_queue` та функцію обробки запитів (сучасний інтерфейс `blk-mq` — multi-queue block IO).

```c
static const struct block_device_operations my_bdev_ops = {
    .owner  = THIS_MODULE,
    .open   = my_bdev_open,
    .release= my_bdev_release,
    .ioctl  = my_bdev_ioctl,
    // read/write тут немає! Вони керуються через request_queue
};
```

Коли VFS виконує читання з блочного пристрою, вона взаємодіє з підсистемою блочного вводу-виводу (Block I/O Layer), яка вже формує об'єкти `struct bio` та передає їх до черги драйвера.

## Ідентифікація: Major та Minor номери

Щоб ядро знало, який драйвер відповідає за певний файл пристрою, кожен пристрій має два числа:
- **Major (старший номер):** Ідентифікує драйвер. Наприклад, драйвер SCSI дисків зазвичай має major 8.
- **Minor (молодший номер):** Ідентифікує конкретний екземпляр пристрою або розділ, який обслуговує цей драйвер (наприклад, `/dev/sda1` має minor 1, `/dev/sda2` — minor 2).

### Створення файлів пристроїв (`mknod`)
Утиліта `mknod` створює файл пристрою у файловій системі, вказуючи тип (символьний `c` або блочний `b`) та його номери.

```bash
# Створити символьний пристрій (c), major 1, minor 3 (/dev/null)
sudo mknod /dev/mynull c 1 3

# Створити блочний пристрій (b), major 8, minor 1 (/dev/sda1)
sudo mknod /dev/myhdd1 b 8 1
```

Сьогодні ручне створення через `mknod` використовується рідко. Підсистема `udev` (або `devtmpfs` у ядрі) автоматично створює відповідні вузли у `/dev/` під час виявлення пристрою, запитуючи драйвери про їхні major/minor номери через `sysfs`.

## Підсумок різниці

| Характеристика | Символьний (Character) | Блочний (Block) |
| :--- | :--- | :--- |
| **Одиниця даних** | Байт (потік символів) | Блок (фіксований розмір, 512B/4KB) |
| **Доступ** | Послідовний (як правило) | Довільний (random access) |
| **Кешування** | Не кешується (прямий доступ) | Сторінковий кеш (Page Cache) |
| **Черга запитів** | Відсутня (одразу в драйвер) | `request_queue` (злиття та сортування) |
| **Ядерний інтерфейс** | `struct file_operations` | `struct block_device_operations` + `blk-mq` |
| **Типове використання** | Клавіатури, миші, UART, `/dev/urandom` | Жорсткі диски, SSD, флеш-накопичувачі |

Цей розподіл дозволяє ядру застосовувати складні алгоритми оптимізації лише там, де це має сенс (для блочних накопичувачів), залишаючи доступ до потокових пристроїв максимально прямим і швидким.
