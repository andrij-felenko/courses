# 📋 Контракт профілю цілісності: sysfs, `blk_integrity`, `sg3_utils`, `nvme-cli`, io_uring

Профіль цілісності описаний у ядрі однією структурою, показаний назовні шістьма файлами sysfs і задається на носії низькорівневим форматуванням — тут зібрано весь цей контракт: імена файлів і полів, повний перелік значень, розміри кортежів і команди, якими стан читають і міняють.

## Шість файлів у `/sys/block/<dev>/integrity/`

Тека — звичайна група атрибутів блокового пристрою ([модель sysfs](book:unix-linux/sysfs-device-model): ядро показує свої об'єкти каталогами, а поля — текстовими файлами, які читає `cat` і пише `echo`).

| Файл | Запис | Значення |
|---|---|---|
| `format` | — | рядок імені профілю; `none`, коли службових байтів на блок немає взагалі |
| `protection_interval_bytes` | — | скільки байтів даних накриває один кортеж: `1 << interval_exp` |
| `tag_size` | — | байтів прикладного тега, вільних для власника вище: `2`, `6` або `0` |
| `device_is_integrity_capable` | — | `1`, коли ці байти справді зберігає сам носій, а не шар вище |
| `read_verify` | **так** | `1` — блоковий шар звіряє теги на завершенні читання |
| `write_generate` | **так** | `1` — блоковий шар сам рахує теги перед записом |

Одну звичку варто зламати одразу: сама наявність теки нічого не доводить. У ядрі, зібраному з `CONFIG_BLK_DEV_INTEGRITY`, група додається до кожного диска беззастережно — питати треба `format`, і `none` там означає рівно те, що написано.

Запис у два останні файли міняє прапорці навпаки: `echo 0 > read_verify` **ставить** внутрішній `BLK_INTEGRITY_NOVERIFY`, `echo 1` — знімає. Те саме з `write_generate` і `BLK_INTEGRITY_NOGENERATE`.

## Повний перелік рядків `format`

Ім'я не зберігається ніде: воно щоразу складається з двох речей — типу контрольної суми й того, чи є в профілі посилальний тег.

| Рядок | Сума | Посилальний тег | Типовий носій |
|---|---|---|---|
| `none` | — | — | службових байтів на блок немає |
| `nop` | немає | немає | службові байти є, захисної інформації в них немає |
| `T10-DIF-TYPE1-CRC` | CRC-16 (0x8BB7) | є | SCSI тип 1 або 2; NVMe тип 1 або 2 |
| `T10-DIF-TYPE3-CRC` | CRC-16 (0x8BB7) | немає | SCSI тип 3, NVMe тип 3 |
| `T10-DIF-TYPE1-IP` | сума доповнень | є | адаптер рахує суму дешевше, а CRC доробляє сам |
| `T10-DIF-TYPE3-IP` | сума доповнень | немає | те саме для типу 3 |
| `EXT-DIF-TYPE1-CRC64` | CRC-64 | є | NVMe 2.0 з широким вартовим |
| `EXT-DIF-TYPE3-CRC64` | CRC-64 | немає | те саме без посилального тега |

Звідси два висновки, на яких легко спіткнутися. **Тип 2 у цьому рядку не видно**: посилальний тег у нього є, тож він показується як `TYPE1`. І **`nop` — не те саме, що `none`**: службові байти на блок носій відводить, але захисної інформації в них немає (типовий випадок — простір імен NVMe, відформатований з `ms:8` і вимкненим захистом).

Варіант `-IP` — це [інтернетна контрольна сума](book:communications/internet-checksum), сума доповнень із заголовків IP: слабша за [CRC](book:communications/crc), зате рахується кількома додаваннями. Хост кладе в кортеж її, адаптер перед відправкою на шину перераховує на справжній CRC.

## Структура в `queue_limits`

Драйвер не реєструє профіль окремим викликом — він заповнює поля всередині обмежень черги, і ядро перевіряє їх разом з усім іншим.

```c
struct blk_integrity {
	unsigned char			flags;
	enum blk_integrity_checksum	csum_type;
	unsigned char			metadata_size;   /* усіх службових байтів на інтервал */
	unsigned char			pi_offset;       /* зсув кортежу всередині них */
	unsigned char			interval_exp;    /* log₂ інтервалу даних */
	unsigned char			tag_size;        /* вільних байтів для власника вище */
	unsigned char			pi_tuple_size;   /* 8 або 16 */
};

enum blk_integrity_checksum {
	BLK_INTEGRITY_CSUM_NONE  = 0,
	BLK_INTEGRITY_CSUM_IP    = 1,
	BLK_INTEGRITY_CSUM_CRC   = 2,
	BLK_INTEGRITY_CSUM_CRC64 = 3,
};

enum blk_integrity_flags {
	BLK_INTEGRITY_NOVERIFY       = 1 << 0,  /* ← read_verify = 0 */
	BLK_INTEGRITY_NOGENERATE     = 1 << 1,  /* ← write_generate = 0 */
	BLK_INTEGRITY_DEVICE_CAPABLE = 1 << 2,  /* → device_is_integrity_capable */
	BLK_INTEGRITY_REF_TAG        = 1 << 3,  /* → TYPE1 у рядку format */
	BLK_INTEGRITY_STACKED        = 1 << 4,  /* профіль зібрано з нижніх шарів */
	BLK_SPLIT_INTERVAL_CAPABLE   = 1 << 5,  /* інтервал можна різати між сторінками */
};
```

Назовні видно чотири поля з семи: `csum_type` разом із прапорцем посилального тега — в `format`, `interval_exp` — у `protection_interval_bytes`, `tag_size` — сам собою. `metadata_size`, `pi_offset` і `pi_tuple_size` в sysfs не показані взагалі; саме `metadata_size` вирішує, чи є профіль (нуль — немає).

Перевірки, які ядро робить над цими полями, і є формальним контрактом:

- `pi_tuple_size` мусить дорівнювати 8 для `CSUM_CRC` і `CSUM_IP` та 16 для `CSUM_CRC64`;
- посилальний тег без контрольної суми заборонений;
- `interval_exp`, якщо драйвер його не задав, ядро підставляє як `log₂` логічного розміру блока; заданий — мусить бути в межах від 9 до цього ж `log₂`;
- `metadata_size` нуль — профілю немає, і ядро одразу ставить `NOGENERATE | NOVERIFY`.

При складанні пристрою з нижніх шарів ([device mapper](book:unix-linux/device-mapper), програмний RAID) звіряються **шість** значень: `metadata_size`, `interval_exp`, `tag_size`, `csum_type`, `pi_tuple_size` і наявність посилального тега. Розійшлося хоч одне — профіль зверху обнуляється цілком.

## Кортежі

```c
struct t10_pi_tuple {          /* 8 байтів: SCSI DIF, NVMe з 16-бітовим вартовим */
	__be16 guard_tag;      /* CRC-16 від байтів інтервалу */
	__be16 app_tag;        /* власникові вище; носій не чіпає */
	__be32 ref_tag;        /* молодші 32 біти адреси (тип 1) */
};

struct crc64_pi_tuple {        /* 16 байтів: NVMe 2.0 */
	__be64 guard_tag;
	__be16 app_tag;
	__u8   ref_tag[6];     /* 48 бітів адреси і мітки зберігання */
};

#define T10_PI_APP_ESCAPE  0xffff      /* блок не перевіряти взагалі */
#define T10_PI_REF_ESCAPE  0xffffffff  /* посилальний тег не перевіряти */
```

Значення-втечі — не заглушки, а частина протоколу: `app_tag` = `0xffff` каже носієві пропустити перевірку цього блока (так позначають ніколи не записані блоки), `ref_tag` = `0xffffffff` вимикає звірку адреси на одному конкретному блоці.

## Носій SCSI з командного рядка

Обидва знаряддя з набору `sg3_utils` розмовляють з носієм командами протоколу через [наскрізний доступ SCSI](book:unix-linux/scsi-generic-passthrough) — драйвер бере вже готову команду й повертає сирі сенс-дані, тому питати можна і те, чого блоковий шар назовні не показує.

```
$ sudo sg_readcap -l /dev/sg2
Read Capacity results:
   Protection: prot_en=1, p_type=0, p_i_exponent=0 [type 1 protection]
   Last LBA=1953525167 (0x74706db7), Number of logical blocks=1953525168
   Logical block length=512 bytes
```

`p_type` — це **номер типу мінус один**: `0` означає тип 1, `1` — тип 2, `2` — тип 3. `prot_en=0` — носій відформатований без захисту. `p_i_exponent` — двійковий логарифм кількості кортежів на логічний блок: `0` — один кортеж, `3` — вісім. Друге трапляється саме на чотирикілобайтових носіях, де інтервал лишили в 512 байтів: на носії тоді 4096 + 8·8 = 4160 байтів на блок.

Перевести носій в інший формат можна лише повним переформатуванням — з утратою всього, що на ньому є. Тип задають двома ключами:

| Тип | Ключі `sg_format` |
|---|---|
| 0 (без захисту) | `--fmtpinfo=0 --pfu=0` |
| 1 | `--fmtpinfo=2 --pfu=0` |
| 2 | `--fmtpinfo=3 --pfu=0` |
| 3 | `--fmtpinfo=3 --pfu=1` |

```sh
# захист типу 1 — усе на носії буде втрачено
$ sudo sg_format --format --fmtpinfo=2 --pfu=0 /dev/sg2
```

Ключ `--size=` тут не потрібен і шкідливий: він задає кількість байтів **даних** у блоці (512 або 4096), а службові байти в неї не входять і додаються самим форматуванням. Тому `READ CAPACITY` на захищеному носії й далі показує 512 чи 4096, хоча на пластині або в комірках лежить більше.

Що з цього побачило ядро, драйвер каже двома рядками в журналі: `Enabling DIF Type 1 protection` — це про сам носій, і `Enabling DIX T10-DIF-TYPE1-CRC, application tag size 2 bytes` — це вже про пару «адаптер плюс ядро».

## Носій NVMe

Тут те саме зашито у формат простору імен ([NVMe в Linux](book:unix-linux/nvme-in-linux): носій розбитий на простори імен, і кожен має свій розмір блока й свій розмір службових даних).

```
$ sudo nvme id-ns /dev/nvme0n1
flbas   : 0x3
mc      : 0x3
dpc     : 0x1f
dps     : 0x1
lbaf  0 : ms:0   lbads:9  rp:0x2
lbaf  1 : ms:8   lbads:9  rp:0x2
lbaf  2 : ms:0   lbads:12 rp:0
lbaf  3 : ms:8   lbads:12 rp:0 (in use)
```

| Поле | Біти | Що каже |
|---|---|---|
| `lbaf N: lbads` | — | `log₂` розміру блока: `9` → 512, `12` → 4096 |
| `lbaf N: ms` | — | скільки службових байтів іде на кожен блок у цьому форматі |
| `flbas` | 3:0 і 6:5 | номер чинного формату з переліку `lbaf` |
| `flbas` | 4 | `1` — службові байти йдуть суцільно за даними (розширений блок); `0` — окремим буфером |
| `mc` | 0, 1 | пристрій уміє розширений блок / окремий буфер |
| `dpc` | 0, 1, 2 | пристрій **уміє** тип 1 / 2 / 3 |
| `dpc` | 3, 4 | уміє тримати захисну інформацію в перших / останніх байтах службових |
| `dps` | 2:0 | **увімкнений** тип: `0` — жодного, далі 1, 2, 3 |
| `dps` | 3 | `1` — захисна інформація в перших байтах службових, `0` — в останніх |

У прикладі вище чинний формат — четвертий: блок 4096 байтів плюс 8 службових, захист типу 1 в останніх байтах, службові байти окремим буфером. Саме це ядро й покаже як `T10-DIF-TYPE1-CRC` з інтервалом 4096.

| Ключ `nvme format` | Значення |
|---|---|
| `-n, --namespace-id` | номер простору імен; `0xffffffff` — усі |
| `-l, --lbaf` | номер формату LBA з переліку `lbaf` |
| `-i, --pi` | `0` — без захисту, `1`/`2`/`3` — тип |
| `-p, --pil` | `1` — захисна інформація в перших байтах службових, `0` — в останніх |
| `-m, --ms` | `0` — службові байти окремим буфером, `1` — розширений блок |
| `-s, --ses` | `0` — без стирання, `1` — звичайне, `2` — криптографічне |

```sh
# формат 3 (4096+8), захист типу 1, службові байти окремо — усе на носії буде втрачено
$ sudo nvme format /dev/nvme0n1 --lbaf=3 --pi=1 --pil=0 --ms=0
```

## PRACT і PRCHK у командах читання й запису

Чотири біти в команді керують тим, хто саме працює з тегами. У Linux вони живуть у полі `control`, у самому протоколі — у старших бітах слова DW12.

| Прапорець | Біт у `control` | Біт DW12 | Дія |
|---|---|---|---|
| PRACT | 13 | 29 | контролер сам вставляє теги при записі й знімає їх при читанні — хост тегів не бачить |
| PRCHK guard | 12 | 28 | звіряти вартового |
| PRCHK apptag | 11 | 27 | звіряти прикладний тег |
| PRCHK reftag | 10 | 26 | звіряти посилальний тег |

Різниця між ними принципова. `PRACT` вимкнений — теги їдуть у пам'ять хоста і з неї, конверт наскрізний. `PRACT` увімкнений — теги народжуються й помирають у контролері, а хост про них не знає; захищено лише відтинок від контролера до комірок. У `nvme-cli` це поле подають ключем `--prinfo` командам `read` і `write`, а очікувані значення тегів — ключами `--ref-tag`, `--app-tag` і `--app-tag-mask`.

## Власні теги з io_uring

З ядра 6.14 застосунок може подати свої теги разом із самою операцією — через [io_uring](book:unix-linux/io-uring), інтерфейс, у якому запити кладуть у кільце в пам'яті, а не передають окремим системним викликом.

```c
/* include/uapi/linux/io_uring.h */
#define IORING_RW_ATTR_FLAG_PI	(1U << 0)

struct io_uring_attr_pi {
	__u16	flags;    /* IO_INTEGRITY_CHK_* — які саме перевірки вимагати */
	__u16	app_tag;  /* прикладний тег */
	__u32	len;      /* довжина буфера з тегами, байтів */
	__u64	addr;     /* сам буфер з тегами */
	__u64	seed;     /* посилальний тег першого блока запиту */
	__u64	rsvd;     /* мусить бути 0 */
};

/* include/uapi/linux/fs.h */
#define IO_INTEGRITY_CHK_GUARD	(1U << 0)
#define IO_INTEGRITY_CHK_REFTAG	(1U << 1)
#define IO_INTEGRITY_CHK_APPTAG	(1U << 2)
```

Мінімальний виклик — читання чотирьох кілобайтів разом із їхніми тегами:

```c
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, data, 4096, offset);   /* fd відкрито з O_DIRECT */

struct io_uring_attr_pi pi = {
	.flags   = IO_INTEGRITY_CHK_GUARD | IO_INTEGRITY_CHK_REFTAG,
	.app_tag = 0,
	.addr    = (__u64)(uintptr_t)meta,   /* nblocks × metadata_size байтів */
	.len     = nblocks * 8,
	.seed    = lba,                      /* очікуваний посилальний тег першого блока */
	.rsvd    = 0,
};
sqe->attr_ptr       = (__u64)(uintptr_t)&pi;
sqe->attr_type_mask = IORING_RW_ATTR_FLAG_PI;
```

Правила, за якими це або працює, або повертає помилку:

- дескриптор мусить бути відкритий з `O_DIRECT` — інакше `-EOPNOTSUPP`; через сторінковий кеш теги не проходять, бо [прямий ввід-вивід](book:unix-linux/buffered-and-direct-io) і є єдиним шляхом, де буфер застосунку доїжджає до контролера незміненим;
- `rsvd` не нуль або біт поза `IO_INTEGRITY_CHK_*` — `-EINVAL`;
- `len` мусить точно покривати запит: стільки інтервалів, скільки в ньому блоків, помножити на `metadata_size` пристрою;
- `seed` ядро само збільшує на одиницю на кожен інтервал, ідучи по запиту, і відновлює початкове значення, якщо операцію треба повторити;
- жоден із трьох прапорців не поставлено — теги все одно поїдуть на носій, але звіряти їх ніхто не проситиме.
