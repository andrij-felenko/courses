# 📜 Від монолітного контейнера VFIO Type1 до об'єктної моделі IOMMUFD

У 2012 році поява фреймворку VFIO (Virtual Function I/O) у ядрі Linux 3.6 стала вирішальним кроком уперед для безпечної прямої парапрохідності периферійних пристроїв PCIe у віртуальні машини KVM. Попередній механізм прямого призначення `pci-assign` (`kvm-kmod`) не враховував топологію шини й відкривав критичні дірки в ізоляції через неконтрольований транзитний обмін даними між пристроями (Peer-to-Peer DMA повз Root Complex). Автор архітектури VFIO Алекс Вільямсон (Alex Williamson, Red Hat) запропонував сувору концепцію апаратної ізоляції: найменшою неподільною одиницею став не окремий фізичний пристрій, а IOMMU-група (IOMMU Group), яка об'єднувала всі пристрої, здатні взаємодіяти в обхід IOMMU.

Для керування трансляцією адрес у пам'яті VFIO запровадив драйвер `vfio_iommu_type1`. Його архітектура спиралася на концепцію монолітного контейнера (`/dev/vfio/vfio`), який водночас виступав і точкою монтування апаратного IOMMU-домену, і картою сторінок вводу-виводу (IOVA), і контекстом жорсткого закріплення фізичної пам'яті (`pin_user_pages()`). Десять років ця модель бездоганно виконувала своє призначення для простих конфігурацій віртуалізації, де на кожну віртуальну машину виділявся один мережевий адаптер або одна відеокарта.

## Архітектурний глухий кут VFIO Type1

З вибуховим розвитком хмарних сховищ, високопродуктивних розподілених обчислень (HPC), технологій штучного інтелекту та масового розгортання сотень віртуальних черг NVMe через SPDK і 100/400 GbE драйверів DPDK монолітна архітектура VFIO Type1 вперше вперлася в фундаментальні обмеження.

### 1. Катастрофічне дублювання закріплення пам'яті (Pinning Explosion)

У моделі VFIO Type1 кожен контейнер створює власний незалежний IOMMU-домен. Якщо процес простору користувача (наприклад, гіпервізор QEMU або рушій обробки пакетів DPDK) відкриває кілька контейнерів для ізольованих пристроїв, що обслуговують спільний пул оперативної пам'яті (Guest RAM або DPDK Memory Pool), ядро Linux змушене для кожного контейнера окремо викликати системну функцію `pin_user_pages()`.

```
[ Хост RAM: 64 GB буфер ]
   │
   ├──(pin_user_pages)──> VFIO Container 1 (GPU)  ──> Ліміт locked_vm: +64 GB
   │
   └──(pin_user_pages)──> VFIO Container 2 (NIC)  ──> Ліміт locked_vm: +64 GB (РАЗОМ: 128 GB!)
```

Якщо один 64-гігабайтний пул оперативної пам'яті відображається у два різні контейнери, ядро закріплює кожну фізичну сторінку двічі, подвоюючи лічильник `locked_vm` процесу та витрачаючи сотні мегабайтів пам'яті ядра на відстеження дубльованих структур `struct page`. Для серверів із терабайтами RAM та десятками прокинутих прискорювачів це призводило до вичерпання лімітів безпеки `RLIMIT_MEMLOCK` та багатосекундних затримок під час запуску віртуальних машин.

### 2. Жорстке зв'язування адресного простору з фізичним обладнанням

У VFIO Type1 неможливо виділити та попередньо наповнити таблицю сторінок IOMMU (IOVA) без фізично підключеного пристрою. Адресний простір створювався лише в момент додавання першої IOMMU-групи до контейнера (`VFIO_SET_IOMMU`). 

Це створювало непереборні складнощі для гарячого підключення пристроїв (PCIe Hotplug) та динамічної міграції:
* Не можна було підготувати карту пам'яті заздалегідь до появи пристрою в системі.
* Від'єднання останнього пристрою з групи автоматично руйнувало весь адресний простір і скидало налаштовані мапінги сторінок.
* Додавання нового пристрою до вже працюючої конфігурації вимагало тривалого заморожування I/O та синхронної повторної побудови всіх трансляцій.

### 3. Неможливість роботи з вкладеними таблицями (Nested Paging) та PASID

Сучасні апаратні архітектури IOMMU (Intel VT-d 3.0+ Scalable Mode, ARM SMMUv3, AMD-Vi) отримали підтримку двостадійної трансляції адрес (Two-Stage Translation) та ідентифікаторів адресного простору процесу PASID (Process Address Space ID). Це дозволяє гостьовій віртуальній машині напряму заповнювати власні таблиці сторінок Стадії 1 (Stage 1), передаючи їх апаратному IOMMU без програмної емуляції в гіпервізорі.

Спроби додати підтримку вкладеної трансляції та черг сторінкових помилок (Page Request Interface) до монолітного контейнера VFIO Type1 перетворили кодову базу ядра на заплутане нашарування пропрієтарних викликів `ioctl`. Кожен виробник апаратного забезпечення (Intel, ARM, AMD) намагався проштовхнути власні специфічні структури даних для роботи з регістрами vIOMMU, оскільки у Type1 була відсутня уніфікована абстракція апаратної таблиці сторінок (Hardware Page Table).

## Народження IOMMUFD: архітектурна революція 2021–2023 років

У 2021 році інженери Джейсон Ганторп (Jason Gunthorpe, NVIDIA), Ї Лю (Yi Liu, Intel), Алекс Вільямсон (Alex Williamson, Red Hat), Ніколін Чен (Nicolin Chen, NVIDIA) та Кевін Тіань (Kevin Tian, Intel) ініціювали глобальну ревізію підсистеми взаємодії простору користувача з IOMMU.

Замість чергового латання застарілого драйвера Type1 було ухвалено рішення відокремити керування таблицями сторінок IOMMU від логіки прокидання шини PCIe, винісши IOMMU в самостійну підсистему ядра першого класу — **IOMMUFD** (`/dev/iommufd`).

Ключові архітектурні принципи нового дизайну:
1. **Декомпозиція сутностей:** Повний розрив моноліту на незалежні об'єкти з власними дескрипторами uAPI — логічний адресний простір `IOAS`, апаратні сторінкові домени `HWPT` та прив'язані фізичні пристрої `DevID`.
2. **Єдине закріплення пам'яті (Single Pinning):** Фізичні сторінки пам'яті хоста закріплюються рівно один раз у межах об'єкта `IOAS` (через внутрішнє дерево `IOPT`), незалежно від того, скільки фізичних пристроїв чи апаратних таблиць HWPT підключено до цього простору.
3. **Першокласна підтримка двостадійної віртуалізації:** Нативна абстракція вкладених таблиць `HWPT` з уніфікованим інтерфейсом інвалідації апаратних кешів `IOMMU_HWPT_INVALIDATE` для всіх архітектур процесорів.
4. **Зворотна сумісність:** Створення шару емуляції контейнерів (`CONFIG_IOMMUFD_VFIO_CONTAINER`), що дозволило існуючим бібліотекам DPDK та гіпервізорам QEMU безперешкодно перейти на нову підсистему ядра.

У лютому 2023 року підсистему IOMMUFD було офіційно включено до основного дерева ядра Linux у релізі **Linux 6.2**. Подальші версії ядра (Linux 6.7–6.11) розширили підсистему нативною підтримкою черг сторінкових помилок (Fault Queues), віртуальних IOMMU (`VIOMMU`) та повноцінною інтеграцією зі спільним віртуальним адресним простором SVA.
