# 📋 Важелі прив'язки: файли sysfs, параметри ядра й точки спостереження

Прив'язка драйвера до пристрою — стан, а не подія, тож ядро дає повний набір ручок, якими цей стан читають і міняють ззовні. Нижче зібрано їх усі за ядром Linux 6.x: точний шлях, хто цей файл має, що саме в нього пишуть, що стається одразу після запису й на якій помилці спотикаються найчастіше.

## Три власники, а не один каталог

Ручки розкидані по трьох різних об'єктах, і плутанина між ними — найчастіша причина відповіді «немає такого файла». Шина відповідає за політику загалом, драйвер — за свій бік пари, пристрій — за свій:

```
/sys/bus/<шина>/
├── drivers_autoprobe                шина,    0644  ← 0|1
├── drivers_probe                    шина,    0200  ← <пристрій>
├── drivers/<драйвер>/
│   ├── bind                         драйвер, 0200  ← <пристрій>
│   ├── unbind                       драйвер, 0200  ← <пристрій>
│   ├── new_id                       драйвер, 0200  ← ознаки, 16-кові
│   └── remove_id                    драйвер, 0200  ← ознаки, 16-кові
└── devices/<пристрій> → /sys/devices/…/<пристрій>/
    ├── driver → …/drivers/<драйвер>  посилання; є ⟺ прив'язано
    ├── modalias                     пристрій, 0444 (лише читання)
    ├── uevent                       пристрій, 0644 ← дія
    └── driver_override              пристрій, 0644 ← ім'я драйвера
```

Каталог `devices/` під шиною складається з символьних посилань; самі каталоги пристроїв живуть у [дереві sysfs](book:unix-linux/sysfs-device-model) за фізичною топологією, і писати можна хоч туди, хоч через посилання.

Ім'я пристрою в усіх цих файлах — рівно назва каталогу в `devices/`: `0000:03:00.0` на PCI, `1-1:1.0` для інтерфейсу USB, `1-0076` на I²C, `fe801000.i2c` на платформенній шині. Ніяких скорочень і ніяких шляхів — тільки ім'я.

## bind і unbind — переставити одну пару

**Шлях:** `/sys/bus/<шина>/drivers/<драйвер>/bind`, `…/unbind`. Приймають ім'я пристрою; кінцевий символ нового рядка ядро відкидає саме, тож звичайного `echo` досить.

```
# echo 0000:03:00.0 > /sys/bus/pci/drivers/nvme/unbind
# echo 0000:03:00.0 > /sys/bus/pci/drivers/vfio-pci/bind
```

`unbind` вимагає, щоб пристрій був прив'язаний саме до цього драйвера, і виконує повноцінний `remove()` негайно, ні в кого не питаючи. `bind` — навпаки: він **не** обходить таблицю ознак. Усередині стоїть той самий виклик збігу, що й при автоматичній прив'язці, тож нав'язати драйверові чуже залізо через `bind` не вийде — для цього є `new_id` і `driver_override`.

Типові невдачі:

- `No such device` (`-ENODEV`) — імені немає на цій шині або пристрій прив'язаний до когось іншого (`unbind`), чи ознаки не збіглися (`bind`);
- `No such file or directory` — файлів просто немає: драйвер оголосив `suppress_bind_attrs`, і ядро не створило йому `bind`/`unbind`. Так роблять там, де відв'язка на ходу нічим добрим не закінчиться;
- будь-який інший код — прийшов із самого `probe`: `bind` повертає його дослівно, тому `Invalid argument` тут означає скаргу драйвера, а не помилку в команді.

## new_id і remove_id — дописати ознаку в таблицю

**Шлях:** `/sys/bus/<шина>/drivers/<драйвер>/new_id`. Файл існує лише на шинах із динамічними ознаками — PCI, USB, HID, SDIO; на платформенній шині його немає взагалі.

Усі числа шістнадцяткові, розділені пропусками, порядок полів фіксований.

| Шина | Формат запису | Обов'язкові |
| --- | --- | --- |
| PCI, `new_id` | `VVVV DDDD SVVV SDDD CCCC MMMM PPPP` | перші два |
| PCI, `remove_id` | `VVVV DDDD SVVV SDDD CCCC MMMM` | перші два |
| USB, `new_id` | `idVendor idProduct bInterfaceClass RefIdVendor RefIdProduct` | перші два |
| USB, `remove_id` | `idVendor idProduct` | обидва |

Для PCI це виробник, пристрій, підсистемний виробник, підсистемний пристрій, клас, маска класу й число, яке драйвер отримає як власні дані. Пара `Ref*` на USB каже: візьми для нового пристрою ті самі внутрішні дані, що й для вже відомого.

```
# echo "8086 10f5" > /sys/bus/pci/drivers/e1000e/new_id
```

Запис не просто розширює таблицю — одразу після нього шина проходить свої неприв'язані пристрої й пробує прив'язати ті, що підійшли. Тому `new_id` часто виявляється єдиною потрібною дією.

Типові невдачі: менше двох чисел — `Invalid argument`; десяткове число замість шістнадцяткового мовчки дасть не ту ознаку. І окремо варто знати, що `remove_id` прибирає ознаку зі списку, але **не** відв'язує те, що вже прив'язалося, а спроба прибрати ознаку зі статичної таблиці драйвера дає `-ENODEV`: динамічно можна зняти тільки динамічно додане.

## drivers_probe і drivers_autoprobe — вимкнути самодіяльність шини

**Шлях:** `/sys/bus/<шина>/drivers_autoprobe` (читається й пишеться, `0` або `1`) і `/sys/bus/<шина>/drivers_probe` (лише запис, ім'я пристрою).

Одиниця — звична поведінка: кожна реєстрація з будь-якого боку запускає пошук пари. Нуль лишає реєстрацію, але вимикає спробу: пристрої з'являються в `/sys`, драйвери стають до списку, а `probe` не кличуть, доки не попросять. Це єдиний спосіб перехопити пристрій **до** того, як його візьме штатний драйвер:

```
# echo 0 > /sys/bus/pci/drivers_autoprobe
   … під'єднати пристрій, виставити йому driver_override …
# echo 0000:03:00.0 > /sys/bus/pci/drivers_probe
# echo 1 > /sys/bus/pci/drivers_autoprobe
```

Невідоме ім'я в `drivers_probe` дає `-ENODEV`, а `-EINVAL` означає, що пристрій знайшовся, але прив'язати його не вдалося.

## driver, modalias, uevent, driver_override — з боку пристрою

**`driver`** — символьне посилання на каталог драйвера. Його наявність і є визначенням прив'язки: `readlink` дає ім'я, відсутність файла означає «господаря немає».

**`modalias`** — рядок ознак цього пристрою тим самим словником, яким драйвери оголошують свої таблиці. Звідси береться звична дія «знайти драйвер за пристроєм»: `modprobe $(cat modalias)` шукає серед [аліасів модулів](book:unix-linux/kernel-modules) той, чия таблиця покриває цей рядок. Файл лише читається.

**`uevent`** при читанні віддає змінні майбутньої події, по одній на рядок. При записі приймає назву дії — `add`, `remove`, `change`, `move`, `online`, `offline`, `bind`, `unbind` — і випускає подію повторно, ніби пристрій щойно з'явився. Саме це робить `udevadm trigger`, і саме так змушують [правила іменування](book:unix-linux/udev-rules) відпрацювати ще раз. Невідомий рядок дає `-EINVAL` і запис у журналі ядра: `uevent: failed to send synthetic uevent: -22`.

Дві дії з цього переліку ядро випускає й само: `bind` — щойно `probe` повернув нуль, `unbind` — коли пристрій відпускають. Програма, що чекає на готовий пристрій, має слухати саме `bind`, а не `add`: `add` приходить тоді, коли пристрій лише зареєстровано, і драйвера в нього може ще довго не бути.

**`driver_override`** — ім'я єдиного драйвера, якому дозволено взяти цей пристрій. Заповнений файл замінює порівняння ознак порівнянням імен: таблиця драйвера більше не важить, а всі інші драйвери відпадають незалежно від того, хто встиг першим. Очищають порожнім записом — `echo > driver_override` кладе туди один символ нового рядка, а ядро зводить його до порожнього значення.

Головна пастка: запис у `driver_override` **нічого не запускає сам по собі**. Пристрій, уже прив'язаний до старого драйвера, там і лишиться. Повна послідовність — три записи:

```
# echo vfio-pci > /sys/bus/pci/devices/0000:03:00.0/driver_override
# echo 0000:03:00.0 > /sys/bus/pci/drivers/nvme/unbind
# echo 0000:03:00.0 > /sys/bus/pci/drivers_probe
```

## Куди дивитися, коли прив'язки немає

**`/sys/kernel/debug/devices_deferred`** показує чергу відкладених спроб. Файл живе в [debugfs](book:unix-linux/pseudo-filesystems), тож потребує змонтованої `/sys/kernel/debug` і прав адміністратора. Рядок — ім'я пристрою, знак табуляції й **причина**, а не ім'я драйвера:

```
$ cat /sys/kernel/debug/devices_deferred
1-0076	supplier regulator@1 not ready
2-0068
```

Другий стовпчик заповнює `dev_err_probe()`: драйвер, який відмовляється через нього, лишає по собі пояснення. Драйвер, який просто повернув `-EPROBE_DEFER`, лишає порожньо — як `2-0068` вище. Порожній стовпчик означає не «причини немає», а «драйвер її не назвав».

**`initcall_debug`** у [командному рядку ядра](book:unix-linux/bootloader-and-cmdline) додає до кожного `probe` вимірювання й рядок у журналі:

```
probe of 0000:03:00.0 returned 0 after 148213 usecs
```

Виводить його звичайний `printk` рівня `KERN_DEBUG`, а не динамічне налагодження — у ядрі коло цього рядка навіть стоїть окремий коментар, щоб ніхто не «полагодив»: параметр командного рядка має працювати сам, без додаткових умов збирання. Звідси прямий спосіб знайти, хто з'їв секунди старту:

```
$ dmesg -t | grep 'probe of' | sort -k7 -n | tail
```

## Параметри, що міняють правила гри

**`deferred_probe_timeout=<секунди>`** — командний рядок ядра. Скільки чекати, доки з'явиться постачальник, перш ніж вважати, що його не буде:

| Значення | Поведінка |
| --- | --- |
| `0` | здатися наприкінці [initcall](book:unix-linux/kernel-initcalls) |
| `> 0` | чекати стільки секунд після initcall |
| `< 0` | нескінченність: не здаватися ніколи |

Типове значення задають при збиранні ядра: нуль, якщо підтримки модулів немає, і десять, якщо є. Логіка проста — там, де модулів немає, новому драйверові після initcall уже нізвідки взятися.

Таймер не абсолютний: кожна реєстрація нового драйвера перезапускає відлік із повного значення. Система, у яку модулі приїжджають один за одним, дочекається останнього.

Вичерпаний таймер не викидає чергу. Він міняє відповідь помічників, через які підсистеми питають «чи є вже мій постачальник»: замість `-EPROBE_DEFER` ті починають повертати `-ETIMEDOUT`, і споживач відмовляється остаточно, замість висіти в черзі вічно. Стосується це лише залежностей, які на таку поведінку підписалися, — насамперед [зв'язків між пристроями](book:unix-linux/device-links).

**`driver_async_probe=<імена>`** — командний рядок ядра, список імен драйверів через кому, чий `probe` виконувати в окремому потоці. Зірочка `*` означає «всі»; якщо вона є, решта імен читається навпаки — як перелік винятків:

```
driver_async_probe=mmcblk,sdhci        лише ці двоє — асинхронно
driver_async_probe=*,nvme              усі, крім nvme
```

**`async_probe`** — параметр не драйвера, а завантажувача модулів, тож приймає його **будь-який** модуль:

```
# modprobe usb-storage async_probe        асинхронно
# modprobe usb-storage async_probe=0      примусово синхронно
```

Значення розбирають як булеве, і саме тому параметр без значення означає «так»: розібрати нічого, отже вмикаємо. Дія обмежена драйверами, які зареєструє цей модуль під час своєї ініціалізації.

Драйвер може попросити асинхронність і сам — полем `probe_type` у своїй структурі. Значень три: `PROBE_FORCE_SYNCHRONOUS` тримає синхронність, і ззовні її не перебити; `PROBE_PREFER_ASYNCHRONOUS` вмикає окремий потік завжди; типове значення віддає рішення назовні — спершу дивиться на командний рядок, далі на параметр модуля.

## Коди помилок одним списком

| Код | Що сталося |
| --- | --- |
| `ENOENT` | файла немає: шина не має цього важеля, драйвер зі `suppress_bind_attrs`, debugfs не змонтовано |
| `ENODEV` | ім'я пристрою не знайдене; невідповідні ознаки в `bind`; зняття ознаки, якої не додавали |
| `EINVAL` | менше двох чисел у `new_id`; невідома дія в `uevent`; завелике значення `driver_override` |
| `EACCES` | не адміністратор або спроба прочитати файл, який лише пишеться |
| решта | код, що його повернув `probe` самого драйвера |
