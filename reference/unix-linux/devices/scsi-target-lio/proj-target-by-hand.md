# ⚙️ Ціль руками: як звичайний файл стає диском `/dev/sdb`

За десять хвилин і без жодного заліза перетворимо файл на диск SCSI: піднімемо сховище, зберемо ціль самими лише каталогами, увійдемо в неї ініціатором тієї самої машини — і подивимось, чим вона відрізняється від справжнього диска (нічим, що видно хостові). Вправа варта не «налаштованого iSCSI», а того, що по дорозі стає видно: які саме відповіді роблять пристрій пристроєм і в які моменти їх ще можна змінити.

Усе виконуємо від root. З пакетів потрібні `open-iscsi` (звідти `iscsiadm`), `sg3-utils` і `lsscsi`; ядро годиться будь-яке дистрибутивне.

## Сховище

```bash
truncate -s 1G /srv/disk1.img
modprobe target_core_mod; modprobe target_core_file; modprobe iscsi_target_mod
mountpoint -q /sys/kernel/config || mount -t configfs none /sys/kernel/config

CFG=/sys/kernel/config/target
mkdir -p $CFG/core/fileio_0/disk1
echo "fd_dev_name=/srv/disk1.img,fd_dev_size=1073741824" > $CFG/core/fileio_0/disk1/control
echo 1 > $CFG/core/fileio_0/disk1/enable
cat $CFG/core/fileio_0/disk1/info
```

`truncate` робить розріджений файл: у каталозі гігабайт, на диску нуль байтів, місце витрачається в міру запису. Ім'я теки `fileio_0` не довільне — до підкреслення стоїть назва backstore, після нього номер віртуальної шини. Тека `disk1` під нею вже є пристроєм, тільки порожнім, поки в `control` не запишеш ім'я файлу й розмір; [у configfs](book:unix-linux/configfs) `mkdir` не показує наявне, а створює в ядрі новий об'єкт, і `enable` — той момент, коли об'єкт із опису стає робочим.

Серед виводу `info` є рядок, який варто прочитати уважно:

```
        File: /srv/disk1.img  Size: 1073741824  Mode: O_DSYNC Async: 0
```

`Mode: O_DSYNC` — це вся модель довговічності fileio одним словом. Файл відкрито так, що кожен запис повертається аж тоді, коли дані дійшли до носія. Саме тому ціль має право чесно сказати ініціаторові «кешу запису в мене немає». Протилежний режим вмикають параметром `fd_buffered_io=1` у тому ж `control`, і тоді ядро саме, без прохання, виставляє `emulate_write_cache=1`: записи осідатимуть [у сторінковому кеші](book:unix-linux/page-cache-durability) цілі, і мовчати про це було б обманом.

## Розмір блоку: вікно завширшки у дві команди

```bash
echo 4096 > $CFG/core/fileio_0/disk1/attrib/block_size
```

Тут перша пастка, і вона не там, де її чекають. Записати цей атрибут **до** `enable` можна, і це не дасть нічого: при вмиканні ядро виконує `block_size = hw_block_size`, а для звичайного файлу апаратний розмір жорстко дорівнює 512. Записати його **після** того, як пристрій уже виставлено як LUN, теж не вийде: лічильник експорту не нульовий, оболонка відповість `write error: Invalid argument`, а `dmesg` пояснить — `Unable to change SE Device block_size while export_count is 1`. Вікно рівно одне: між `enable` і символьним посиланням у LUN.

![Три атрибути й моменти, коли ядро ще приймає їхню зміну.](/reference/unix-linux/devices/scsi-target-lio/img/attr-windows.svg)

*Одні атрибути завмирають при вмиканні пристрою, інші — щойно його комусь віддали. Сірий відтинок означає не заборону, а марність: запис пройде, і його затре.*

Ємність рахується з того самого розміру блоку, тож `READ CAPACITY` після цієї команди відповість інакше:

```
блоків  = (1073741824 − 4096) ÷ 4096 = 262143   ← номер останнього блоку
ємність = (262143 + 1) · 4096 = 1073741824 байтів = 1 ГіБ
```

## Ціль, портал, LUN і дозвіл

```bash
IQN=iqn.2026-08.org.example:store
mkdir -p $CFG/iscsi/$IQN/tpgt_1/np/0.0.0.0:3260
cd $CFG/iscsi/$IQN/tpgt_1

mkdir lun/lun_0
ln -s $CFG/core/fileio_0/disk1 lun/lun_0/store

INIT=$(sed -n 's/^InitiatorName=//p' /etc/iscsi/initiatorname.iscsi)
mkdir -p acls/$INIT/lun_0
ln -s $CFG/iscsi/$IQN/tpgt_1/lun/lun_0 acls/$INIT/lun_0/mapped

echo 0 > attrib/authentication
echo 1 > enable
```

Номер LUN тут заводиться двічі, і це не надмірність. `lun/lun_0` — порт пристрою на цій цілі: посилання всередині нього прив'язує номер до backstore. А `acls/<ініціатор>/lun_0` — номер, під яким цей конкретний ініціатор побачить той самий порт; для іншого ініціатора той самий диск може бути `lun_3`. Обидва рази значення несе тека, а не ім'я посилання всередині неї: `store` і `mapped` вигадані, ядро дивиться лише на те, куди посилання веде. Перше має вести на пристрій у `core/`, друге — на LUN саме цієї групи портів; інакше ядро відмовить.

Рядок `attrib/authentication` вимикає вимогу CHAP — для лабораторії на петлі це доречно, для будь-чого іншого ні.

## Вхід

```bash
iscsiadm -m discovery -t sendtargets -p 127.0.0.1:3260
iscsiadm -m node -T $IQN -p 127.0.0.1:3260 --login
lsblk -S
dmesg | tail -4
```

Дві команди тут не дублюють одна одну. `discovery` питає портал «які цілі ти взагалі обслуговуєш» і записує відповідь на диск, у теку `/etc/iscsi/nodes/`; `--login` уже піднімає сеанс до конкретної цілі з цього списку. Побічний наслідок помітний не одразу: запис переживає перезавантаження, і після досліду ініціатор старанно шукатиме зниклу ціль, поки запис не прибрати командою `iscsiadm -m node -T $IQN -p 127.0.0.1:3260 -o delete`.

У `dmesg` з'являється звичайнісіньке знайомство драйвера `sd` з диском — рядок про `262144 4096-byte logical blocks` і окремо `Write cache: disabled, read cache: enabled`. Другий рядок і є та сама відповідь про кеш, яку ціль дала чесно, бо файл відкрито з `O_DSYNC`. Далі підставляйте свій вузол замість `/dev/sdb`.

Одне застереження про саму петлю: для досліду вона ідеальна, для роботи — ні. Щоб виштовхнути брудну сторінку, ядро мусить надіслати пакет, а щоб надіслати пакет, йому потрібна пам'ять — і під тиском пам'яті локальний [iSCSI](book:unix-linux/iscsi-in-linux) із файловою системою зверху вміє замкнутися сам на себе. Для серйозного навантаження беруть другу машину або обходяться без мережі зовсім (нижче).

## Ким він назвався

```bash
sg_inq --page=0x83 /dev/sdb
cat $CFG/core/fileio_0/disk1/wwn/vpd_unit_serial
```

`sg_inq` не питає драйвер `sd`, а шле власну команду [наскрізним каналом](book:unix-linux/scsi-generic-passthrough), тож бачить рівно те, що відповіла ціль. На сторінці 0x83 буде кілька дескрипторів, і серед них той, що містить серійний номер із `vpd_unit_serial`. Це не декорація: [multipath](book:unix-linux/dm-multipath) вважає два вузли одним диском саме тоді, коли ці дескриптори збігаються. Змінити серійник ядро дозволить лише поки лічильник експорту нульовий — та сама межа, що й для розміру блоку, і з тієї самої причини: під працюючим ініціатором ідентичність пристрою мінятися не має права.

## Той самий диск без жодного дроту

```bash
modprobe tcm_loop
WWN=naa.5001405d1e2f3a4b
mkdir -p $CFG/loopback/$WWN/tpgt_0/lun/lun_0
ln -s $CFG/core/fileio_0/disk1 $CFG/loopback/$WWN/tpgt_0/lun/lun_0/store
echo $WWN > $CFG/loopback/$WWN/tpgt_0/nexus
lsscsi -t
```

Запис у `nexus` — це і є «під'єднання»: ядро створює пару ініціатор-ціль усередині машини й одразу гукає сканування, після чого в системі з'являється ще один вузол `/dev/sd*`. Мережі не задіяно жодної, а `sg_inq --page=0x83` на новому вузлі поверне ті самі дескриптори, що й на старому: ідентичність живе в backstore, транспорт до неї не причетний. `lsscsi -t` покаже різницю чесно — навпроти одного вузла стоятиме `iqn.…`, навпроти другого `naa.…`.

Тепер хост має два шляхи до одного LUN і має повне право звести їх в один пристрій `dm-`. **Але не монтуйте обидва вузли окремо** — це два незалежні входи в одну й ту саму ділянку файлу, і файлова система, яка не знає про сусіда, зіпсує себе за секунди.

## Біт кешу, який змінює поведінку `fsync`

```bash
echo 1 > $CFG/core/fileio_0/disk1/attrib/emulate_write_cache
echo 1 > /sys/block/sdb/device/rescan
cat /sys/block/sdb/queue/write_cache      # було write through, стало write back
```

Перечитування потрібне тому, що драйвер `sd` питає про кеш один раз, при знайомстві. Тепер порахуймо скидання: у `/sys/block/sdb/stat` шістнадцяте поле — це кількість запитів `flush`, які блоковий рівень справді відправив пристроєві.

```bash
mkfs.ext4 -q /dev/sdb && mkdir -p /mnt/t && mount /dev/sdb /mnt/t
b=$(awk '{print $16}' /sys/block/sdb/stat)
for i in $(seq 200); do dd if=/dev/zero of=/mnt/t/f bs=4k count=1 conv=fsync status=none; done
echo "скидань: $(( $(awk '{print $16}' /sys/block/sdb/stat) - b ))"
```

При `write back` лічильник виростає на сотні: кожен `fsync()` перетворюється на `SYNCHRONIZE CACHE`, який їде до цілі. Поверніть `emulate_write_cache` у нуль, перечитайте, повторіть — і різниця стане нульовою: блоковий рівень просто не породжує flush для пристрою, який заявив, що кешу не має.

> 🔧 **Навіщо це.** Обидва напрямки цієї ручки коштують по-різному. З `O_DSYNC`-fileio ввімкнений кеш обходиться дешево — дані вже на носії, скидання майже холосте, ви лише платите за зайві команди. А от `fd_buffered_io=1` разом із `emulate_write_cache=0` ядро дозволить без єдиного слова, і це вже прямий обман: ініціатор перестане просити скидання, а підтверджені записи лежатимуть у чужій оперативці. На backstore `iblock` такої свободи немає — там `echo 1` поверне `emulate_write_cache not supported for this device`, бо біт кешу береться з реального пристрою, а не вигадується.

## Чого цей стенд не міряє

Спокуса поміряти тут швидкість велика, і майже кожне число вийде неправдивим. Дані двічі проходять крізь ту саму оперативку й той самий процесор, петльовий інтерфейс не має ні затримки, ні втрат, ні обмеження на розмір кадру, а fileio з `O_DSYNC` над розрідженим файлом упирається то у виділення блоків файловою системою, то в чесне очікування на кожному записі. Порівнювати варто лише те, що від дроту не залежить: скільки команд породжує та чи та операція, як їхня кількість змінюється від розміру блоку, скільки коштує сама емуляція. Для останнього і є backstore `rd_mcp`, який тримає блоки просто в пам'яті: він прибирає сховище з рівняння й лишає в замірі саму ціль. А справжні цифри iSCSI показують дві машини й мережа між ними.

## Розібрати назад

```bash
umount /mnt/t
iscsiadm -m node -T $IQN -p 127.0.0.1:3260 --logout
iscsiadm -m node -T $IQN -p 127.0.0.1:3260 -o delete
echo NULL > $CFG/loopback/$WWN/tpgt_0/nexus
rm $CFG/loopback/$WWN/tpgt_0/lun/lun_0/store
rmdir $CFG/loopback/$WWN/tpgt_0/lun/lun_0 $CFG/loopback/$WWN/tpgt_0 $CFG/loopback/$WWN

cd $CFG/iscsi/$IQN/tpgt_1 && echo 0 > enable
rm acls/$INIT/lun_0/mapped lun/lun_0/store
rmdir acls/$INIT/lun_0 acls/$INIT lun/lun_0 np/0.0.0.0:3260
cd $CFG && rmdir iscsi/$IQN/tpgt_1 iscsi/$IQN core/fileio_0/disk1 core/fileio_0
```

Порядок тут не з ввічливості. Спробуйте почати з кінця — і `rmdir core/fileio_0/disk1` відповість `Device or resource busy`, поки на цю теку веде бодай одне посилання з якогось LUN. Це той самий лічильник експорту, що не давав змінити розмір блоку, тільки цього разу він проступає звичайною помилкою файлової системи: об'єкт живий, доки на нього хтось посилається. Сам файл `/srv/disk1.img` жодна з цих команд не чіпає — його видаляють руками, і в ньому лишається все, що ви туди записали.

## Пастки, на які натикаються всі

**Вхід відхилено з «authorization failure» (код 24).** Для рядка, яким назвався ініціатор, немає теки в `acls/`. Найчастіше річ не у відсутності запису, а в тому, що його зробили не з того рядка: звіряти треба точно з вмістом `/etc/iscsi/initiatorname.iscsi`, до літери й двокрапки.

**Вхід пройшов, сеанс є, диска немає.** Тека ACL створена, а мапованого LUN у ній — ні. Ініціатор запитав `REPORT LUNS`, отримав порожній список і чесно нічого не показав; `iscsiadm -m session -P 3` покаже сеанс без жодного пристрою.

**`write error: Invalid argument` на `block_size`.** Пристрій уже комусь відданий. Правило просте: усе, що стосується ідентичності й геометрії, виставляють одразу після `enable`, до першого посилання з LUN.

**Однаковий серійник на двох машинах.** Береться він майже завжди з одного місця — `/etc/target/saveconfig.json`, який скопіювали разом із конфігурацією. Хост побачить два різні сховища як два шляхи до одного, зіллє їх і почне розкладати записи навпіл. Конфігурацію цілей не клонують; якщо вже скопіювали, серійник міняють до того, як пристрій хоч раз кудись експортовано.
