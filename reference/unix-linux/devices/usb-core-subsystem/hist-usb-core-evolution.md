# 📜 Еволюція підсистеми USB у ядрі Linux

Обмеження пропускної здатності перших специфікацій USB 1.0/1.1 на рівні 12 Мбіт/с (Full Speed) у поєднанні з синхронним опитуванням пристроїв створювали суттєві затримки та простій шини при інтенсивному введенні-виведенні. Для подолання цієї фізичної перепони архітектура ядра Linux пройшла шлях від фрагментованих драйверів серії 2.2 до запровадження неблокувальних асинхронних запитів USB Request Block (URB) і створення уніфікованого шару-посередника `usbcore` у випуску 2.4, з подальшою інтеграцією у модель пристроїв Linux 2.6 та адаптацією до протоколів USB 3.x і USB4.

## Перші кроки: перехід від послідовних портів до USB (1996–1998)

До появи Універсальної Послідовної Шини (Universal Serial Bus, USB) підключення периферійних пристроїв до ПК було серйозним випробуванням для користувачів та розробників операційних систем. Кожен тип пристрою вимагав власного фізичного порту та власної архітектури контролера:
- Миші та клавіатури підключалися через роз'єми PS/2 або послідовні порти RS-232.
- Принтери та сканери вимагали громіздких паралельних портів LPT (IEEE 1284).
- Зовнішні накопичувачі покладалися на дорогі контролери SCSI або на повільні адаптери паралельного порту.

Поява специфікації USB 1.0 у 1996 році та USB 1.1 у 1998 році мала розв'язати проблему хаосу портів за допомогою єдиного 4-провідного кабелю з підтримкою гарячого підключення (Hotplugging) та швидкостями 1.5 Мбіт/с (Low Speed) та 12 Мбіт/с (Full Speed). Однак апаратна реалізація хост-контролерів з самого початку виявилася розколотою між двома непримиренними таборами вендорів:
1. **UHCI (Universal Host Controller Interface)** від компанії Intel — спрощений апаратний контролер, який перекладав більшість обчислень із розкладу передач на процесор.
2. **OHCI (Open Host Controller Interface)** від консорціуму Compaq, Microsoft та National Semiconductor — складний апаратний контролер, який вимагав меншого втручання процесора, але мав складну логіку станів.

## Криза Linux 2.2: фрагментація та відсутність загальної моделі

Підтримка USB уперше з'явилася в ядрі Linux серії 2.2, завдяки зусиллям Лінуса Торвальдса (Linus Torvalds), Йоханнеса Ердфельта (Johannes Erdfelt), Грега Кроа-Хартмана (Greg Kroah-Hartman) та Ренді Данлапа (Randy Dunlap).

Однак перша реалізація підсистеми виявилася надзвичайно крихкою. У ядрі 2.2 не існувало централізованої абстракції шини. Кожен розробник драйвера конкретного пристрою (наприклад, сканера чи модема) змушений був самостійно враховувати, до якого саме хост-контролера — UHCI чи OHCI — підключено пристрій.

Це призводило до хронічних архітектурних проблем:
- **Дублювання коду**: Кожен драйвер периферії вручну формував списки кадрів (Frame Lists) та списки опису передач у форматі конкретного специфічного контролера.
- **Відсутність єдиної нумерації**: Процес розпізнавання нового пристрою (Enumeration) виконувався драйвером контролера локально. Якщо користувач підключав два однакові пристрої до різних портів, у ядрі виникали стани ґонки за унікальні адреси шини.
- **Відсутність абстракції скасування запитів**: Якщо пристрій відключали під час обміну даними, система нерідко занурювалася у зависання, оскільки драйвер чекав відповіді від пристрою, якого більше фізично не існувало на шині.

## Великий рефакторинг Linux 2.4: створення підсистеми `usbcore`

Під час підготовки випуску Linux 2.4 у 1999–2000 роках стало зрозуміло, що попередній підхід зайшов у глухий кут. Йоханнес Ердфельт запропонував повністю переписати апаратний стек USB, впровадивши трирівневу модель з центральним шаром-посередником — **USB Core (`usbcore`)**.

Головним розробницьким проривом стала відмова від прямого керування апаратурою з боку драйверів пристроїв і впровадження трьох фундаментальних концепцій:

1. **Host Controller Driver (HCD)**: Апаратний драйвер контролера (UHCI або OHCI) більше не контактував з драйверами пристроїв. Він реєстрував у підсистемі `usbcore` вектор операцій `struct hc_driver` і перетворював уніфіковані ядерні запити на апаратні команди.
2. **USB Request Block (URB)**: Всі операції обміну даними стали описуватися єдиним асинхронним об'єктом `struct urb`. Драйвер пристрою створював URB, заповнював його буфером та функцією зворотного виклику (`complete`) і відправляв у `usbcore`.
3. **Централізована нумерація (`khubd`)**: Процес розпізнавання пристроїв, електричного скидання портів та призначення адрес (1–127) перейшов під одноосібний контроль ядра `usbcore` та фонового потоку `khubd`.

Завдяки цьому рефакторингу розробник нового USB-пристрою отримав можливість писати драйвер, який взагалі нічого не знає про апаратну реалізацію хост-контролера материнської плати.

## Епоха EHCI, High Speed та інтеграція з Linux Device Model у 2.6

27 квітня 2000 року вийшла специфікація USB 2.0 High Speed, яка підняла швидкість передачі з 12 Мбіт/с до 480 Мбіт/с. Для підтримки нових контролерів EHCI (Enhanced Host Controller Interface) ядру знадобилося навчитися керувати мікрокадрами тривалістю 125 мікросекунд та складною системою split-транзакцій для підтримки старих USB 1.1 пристроїв через нові хаби.

Одночасно у ядрі Linux 2.6 Патрік Мошель (Patrick Mochel) впровадив уніфіковану модель пристроїв (**Linux Device Model**). Підсистему `usbcore` було глибоко інтегровано з новою ієрархією `kobject` та псевдофайловою системою `sysfs`:
- Об'єкти `struct usb_device` та `struct usb_interface` отримали власні строго структуровані каталоги у `/sys/bus/usb/devices/`.
- Запровадження автоматичної системи гарячого підключення через події `uevent` дозволило демону `udev` автоматично завантажувати необхідні модулі ядра при фізичному підключенні пристрою.
- З'явилася псевдофайлова система `usbfs` (перпочатково `usbdevfs`), яка розкрила можливість написання драйверів у просторі користувача без збірки модулів ядра.

## Перехід до SuperSpeed та розширення xHCI (Linux 2.6.31+)

У 2008 році консорціум USB IF представив специфікацію USB 3.0 SuperSpeed зі швидкістю 5 Гбіт/с, а згодом USB 3.1 (10 Гбіт/с) та USB4 (40 Гбіт/с). Для підтримки нових швидкостей знадобився новий стандарт хост-контролерів — **xHCI (eXtensible Host Controller Interface)**.

На відміну від EHCI, контролер xHCI взяв на себе більшість функцій керування кінцевими точками, адресацією та розкладом передач на апаратному рівні. У 2009 році розробниця **Сара Шарп (Sarah Sharp)** з компанії Intel додала до ядра Linux 2.6.31 драйвер `xhci-hcd` та внесла масштабні зміни до `usbcore`:
- **Підтримка Bulk Streams**: Для забезпечення паралельного читання та запису на високошвидкісні SSD (протокол UASP) підсистему `usbcore` навчили підтримувати багатопотокові кінцеві точки.
- **Кільця TRB (Transfer Request Blocks)**: Передача даних між `usbcore` та xHCI була переведена на прямі кільцеві буфери DMA без використання проміжних списків.
- **Розширене керування живленням (LPM)**: Підсистема отримала підтримку апаратних станів сну лінії U1, U2 та U3, що дозволило суттєво зменшити споживання енергії у мобільних пристроях.

Завдяки грамотно спроектованій концепції URB та трирівневій абстракції `usbcore`, розробникам ядра вдалося пройти шлях еволюції швидкостей від 1.5 Мбіт/с у 1996 році до 40 Гбіт/с у сучасних системах USB4, зберігши повну сумісність з тисячами існуючих драйверів пристроїв.
