# 🧾 Контракт loop-пристрою: `losetup`, `ioctl`, `sysfs`

Керують loop-пристроєм трьома способами, і всі три говорять з тим самим драйвером: `losetup` із командного рядка, `ioctl` на файлі пристрою з програми та кілька файлів у `sysfs`, з яких стан лише читають. Тут зібрано контракт цілком — які ключі має `losetup` і в який виклик кожен перетворюється, який `ioctl` з'явився в якому ядрі й що бере третім аргументом, що лежить у полях `loop_info64` та `loop_config`, які прапорці ще можна поміняти після прив'язки, а які — лише під час неї, і що насправді означає кожен код помилки.

## `losetup`: ключі й куди вони ведуть

| ключ | що робить | що це в ядрі |
|---|---|---|
| `-f`, `--find` | знайти вільний номер (і зайняти, якщо названо файл) | `LOOP_CTL_GET_FREE` |
| `--show` | надрукувати ім'я щойно зайнятого пристрою | — |
| `-o`, `--offset N` | початок даних зсунуто на `N` байтів углиб файлу | `lo_offset` |
| `--sizelimit N` | від початку даних видно не більше за `N` байтів | `lo_sizelimit` |
| `-r`, `--read-only` | відкрити файл-носій лише для читання | `LO_FLAGS_READ_ONLY` |
| `-P`, `--partscan` | прочитати таблицю розділів → `/dev/loopNp1`, `p2`… | `LO_FLAGS_PARTSCAN` |
| `-b`, `--sector-size N` | логічний розмір сектора пристрою | `loop_config.block_size` |
| `--direct-io[=on\|off]` | читати й писати файл повз кеш господаря | `LOOP_SET_DIRECT_IO` |
| `-c`, `--set-capacity` | перечитати розмір файлу, що виріс | `LOOP_SET_CAPACITY` |
| `-d`, `--detach` | відчепити названі пристрої | `LOOP_CLR_FD` |
| `-D`, `--detach-all` | відчепити всі | той самий у циклі |
| `-l`, `--list` | таблиця стану | `LOOP_GET_STATUS64` + `sysfs` |
| `-a`, `--all` | те саме про всі наявні пристрої | — |
| `-j`, `--associated FILE` | які пристрої тримають саме цей файл | — |
| `-L`, `--nooverlap` | не заводити другий пристрій на ту саму ділянку файлу | перевірка в `losetup` |
| `-J`, `--json`, `-O`, `--output`, `--raw` | формат виводу | — |

Ключі `--offset`, `--sizelimit`, `--sector-size`, `--read-only`, `--partscan` дійсні лише в тому виклику, який створює прив'язку: потім їх не міняють, бо міняти нема через що — пристрій уже видали ядру як готовий.

```sh
losetup --find --show --offset 1048576 --sector-size 4096 --partscan disk.img
# /dev/loop7
losetup --list --output NAME,BACK-FILE,OFFSET,SIZELIMIT,DIO,LOG-SEC
losetup --detach /dev/loop7
```

Стовпчики `--list` за замовчуванням — `NAME`, `SIZELIMIT`, `OFFSET`, `AUTOCLEAR`, `RO`, `BACK-FILE`, `DIO`, `LOG-SEC`; повний перелік доступних дає `losetup --help`. Більшість із цього `losetup` бере не з `ioctl`, а із `sysfs`, тому таблиця стану читається й без прав на самі файли пристроїв.

## `ioctl` на `/dev/loopN`

| команда | число | третій аргумент | з ядра | що робить |
|---|---|---|---|---|
| `LOOP_SET_FD` | `0x4C00` | `int` — дескриптор | здавна | прив'язати відкритий файл |
| `LOOP_CLR_FD` | `0x4C01` | — | здавна | відчепити (або поставити автоочищення, якщо зайнято) |
| `LOOP_SET_STATUS` | `0x4C02` | `struct loop_info *` | здавна | застаріла 32-бітна версія |
| `LOOP_GET_STATUS` | `0x4C03` | `struct loop_info *` | здавна | те саме на читання |
| `LOOP_SET_STATUS64` | `0x4C04` | `struct loop_info64 *` | 2.6 | доналаштувати вже прив'язаний пристрій |
| `LOOP_GET_STATUS64` | `0x4C05` | `struct loop_info64 *` | 2.6 | прочитати весь стан |
| `LOOP_CHANGE_FD` | `0x4C06` | `int` — дескриптор | 2.6.5 | підмінити файл-носій на льоту |
| `LOOP_SET_CAPACITY` | `0x4C07` | — | 2.6.30 | перечитати розмір файлу |
| `LOOP_SET_DIRECT_IO` | `0x4C08` | `unsigned long`, 0 або не 0 | 4.10 | увімкнути прямий ввід-вивід |
| `LOOP_SET_BLOCK_SIZE` | `0x4C09` | `unsigned long` | 4.14 | змінити логічний сектор |
| `LOOP_CONFIGURE` | `0x4C0A` | `struct loop_config *` | 5.8 | прив'язати й налаштувати одним викликом |

Числа тут — голі константи, а не вирази з макросів `_IOW`/`_IOR`, тому [в номері не закодовано ні напрям, ні розмір аргументу](book:unix-linux/ioctl-interface): `strace` показує їх як є, а розкладку структури ядро зіставити не може й покладається на те, що обидва боки зібрані з того самого заголовка.

Дві пари `SET/GET_STATUS` існують через ширину полів. Стара `struct loop_info` тримає зсув у `int`, тобто образ, більший за 2 ГіБ, у ній уже не адресується; `losetup` користується виключно 64-бітними варіантами, а старі лишилися заради програм, зібраних до 2.6. Обидві версії `LOOP_SET_STATUS` вимагають, щоб пристрій було відкрито на запис або щоб викликач мав [можливість `CAP_SYS_ADMIN`](book:unix-linux/capabilities) — інакше `EPERM`.

`LOOP_CHANGE_FD` — найвужчий із усіх: він працює лише тоді, коли пристрій прив'язано лише для читання, а новий файл того самого розміру й того самого типу. Такі обмеження не примха: заміна відбувається під живою файловою системою, яка нічого про неї не дізнається, тож усе, що могло б змінити геометрію чи дозволити запис, заборонено наперед.

## Керуючий пристрій `/dev/loop-control`

Три команди, усі з ядра 3.1; сам пристрій має старший номер 10, молодший 237.

| команда | число | аргумент | повертає |
|---|---|---|---|
| `LOOP_CTL_ADD` | `0x4C80` | `long` — бажаний номер | номер створеного пристрою |
| `LOOP_CTL_REMOVE` | `0x4C81` | `long` — номер | успіх або код помилки |
| `LOOP_CTL_GET_FREE` | `0x4C82` | — | номер вільного, створивши його за потреби |

`LOOP_CTL_GET_FREE` існує саме для того, щоб пошук вільного номера був атомарним: без нього два процеси, які перебирають `/dev/loop*`, знаходять той самий вільний пристрій.

## Структури

```c
struct loop_info64 {
        __u64 lo_device;                    /* лише читання: пристрій, де лежить файл */
        __u64 lo_inode;                     /* лише читання: номер inode файлу */
        __u64 lo_rdevice;                   /* лише читання: якщо носій сам є пристроєм */
        __u64 lo_offset;                    /* зсув початку даних у файлі, байти */
        __u64 lo_sizelimit;                 /* скільки байтів видно; 0 — до кінця файлу */
        __u32 lo_number;                    /* лише читання: N у /dev/loopN */
        __u32 lo_encrypt_type;              /* мусить бути LO_CRYPT_NONE (0) */
        __u32 lo_encrypt_key_size;          /* мусить бути ≤ LO_KEY_SIZE (32) */
        __u32 lo_flags;                     /* LO_FLAGS_* */
        __u8  lo_file_name[LO_NAME_SIZE];   /* 64 байти: те, що видно в backing_file */
        __u8  lo_crypt_name[LO_NAME_SIZE];
        __u8  lo_encrypt_key[LO_KEY_SIZE];
        __u64 lo_init[2];
};
```

Ім'я файлу тут — не адреса, а напис. Ядро копіює рядок як є й ніколи більше на нього не дивиться; пристрій тримає **дескриптор**, тож `lo_file_name` лишається просто поміткою про походження. `losetup` кладе туди шлях, який набрали ви, і саме він потім з'являється в `sysfs`.

```c
struct loop_config {
        __u32              fd;              /* дескриптор файлу-носія */
        __u32              block_size;      /* логічний сектор; 0 — вибрати самому */
        struct loop_info64 info;            /* offset, sizelimit, flags, ім'я */
        __u64              __reserved[8];   /* запас на майбутнє: нулі */
};
```

`block_size` мусить бути ступенем двійки в межах від 512 до розміру сторінки; інше значення — `EINVAL`. Поля `__reserved` сьогоднішнє ядро не звіряє, але це запас на розширення, і єдиний правильний спосіб заповнити структуру — обнулити її цілком, а потім проставити потрібне.

> 🔧 **Навіщо це.** `LOOP_CONFIGURE` з'явився не заради стислості. Поки прив'язку робили в два кроки — `LOOP_SET_FD`, потім `LOOP_SET_STATUS64`, — між ними існував пристрій із нульовим зсувом і чужими прапорцями, і саме його встигали побачити [правила `udev`](book:unix-linux/udev-rules): вони бралися сканувати розділи не там, де треба. Один виклик закриває це вікно, бо назовні пристрій з'являється вже налаштованим.

## Мінімальний виклик

```c
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/ioctl.h>
#include <linux/loop.h>

int main(void)
{
        int  ctl = open("/dev/loop-control", O_RDWR);
        int  n   = ioctl(ctl, LOOP_CTL_GET_FREE);   /* номер вільного пристрою */
        char path[32];
        snprintf(path, sizeof path, "/dev/loop%d", n);

        int img = open("disk.img", O_RDWR);
        int dev = open(path, O_RDWR);

        struct loop_config cfg;
        memset(&cfg, 0, sizeof cfg);                /* __reserved і решта — нулі */
        cfg.fd             = img;
        cfg.block_size     = 4096;
        cfg.info.lo_offset = 1048576;               /* початок першого розділу */
        cfg.info.lo_flags  = LO_FLAGS_AUTOCLEAR | LO_FLAGS_PARTSCAN;

        if (ioctl(dev, LOOP_CONFIGURE, &cfg) < 0)
                perror("LOOP_CONFIGURE");

        close(img);                                 /* ядро тримає власне посилання */
        /* … робота з /dev/loopN … */

        ioctl(dev, LOOP_CLR_FD, 0);
        close(dev);
        close(ctl);
        return 0;
}
```

## Прапорці `lo_flags`

| прапорець | значення | що означає | коли ставиться |
|---|---|---|---|
| `LO_FLAGS_READ_ONLY` | `0x01` | пристрій захищений від запису | лише на прив'язці |
| `LO_FLAGS_AUTOCLEAR` | `0x04` | відчепитися на останньому закритті | на прив'язці й після; єдиний, який можна **зняти** |
| `LO_FLAGS_PARTSCAN` | `0x08` | сканувати таблицю розділів | на прив'язці й після; зняти не можна |
| `LO_FLAGS_DIRECT_IO` | `0x10` | [прямий ввід-вивід](book:unix-linux/buffered-and-direct-io) до файлу | на прив'язці або окремим `LOOP_SET_DIRECT_IO` |

Правило, за яким це розділено, записано в заголовку двома константами: `LOOP_SET_STATUS_SETTABLE_FLAGS` — це `AUTOCLEAR | PARTSCAN`, а `LOOP_SET_STATUS_CLEARABLE_FLAGS` — самий `AUTOCLEAR`. Усе інше `LOOP_SET_STATUS64` мовчки ігнорує: помилки він не поверне, просто нічого не станеться. `LOOP_CONFIGURE` натомість приймає всі чотири, а на незнайомий біт відповідає `EINVAL` — і різниця тут не косметична: програма, яка попросила можливості, якої в цьому ядрі ще немає, дізнається про це одразу, замість мовчки дістати пристрій із не тими налаштуваннями.

## Шифрування, якого вже немає

`lo_encrypt_type` приймає лише `LO_CRYPT_NONE`. `LO_CRYPT_XOR` і `LO_CRYPT_CRYPTOAPI` дають `-EINVAL` і рядок у журналі ядра, який прямо радить [`dm-crypt`](book:unix-linux/dm-crypt). Самі ж константи (`LO_CRYPT_DES`, `LO_CRYPT_BLOW`, `LO_CRYPT_IDEA` й решта з переліку до 20) досі стоять у заголовку разом із полями `lo_encrypt_key` та `lo_crypt_name` — не тому, що щось із цього працює, а тому, що [розкладка структури заморожена назавжди](book:unix-linux/userspace-abi-stability): прибрати поле означає змінити `sizeof` і зламати кожну зібрану програму.

## Що видно в `sysfs`

Усі атрибути в `/sys/block/loopN/loop/` доступні [лише на читання](book:unix-linux/sysfs-device-model) — керують пристроєм не звідси.

| файл | що показує |
|---|---|
| `backing_file` | шлях, з якого прив'язали; у видаленого файлу з позначкою `(deleted)` |
| `offset` | `lo_offset` у байтах |
| `sizelimit` | `lo_sizelimit`; `0` — до кінця файлу |
| `autoclear` | `1`, якщо стоїть `LO_FLAGS_AUTOCLEAR` |
| `partscan` | `1`, якщо стоїть `LO_FLAGS_PARTSCAN` |
| `dio` | `1`, якщо ввімкнено прямий ввід-вивід |

Поруч, у звичайній групі блокової черги, лежить `/sys/block/loopN/queue/discard_max_bytes`. Нуль там означає, що [discard на цьому пристрої вимкнено](book:unix-linux/discard-and-trim) — файлова система господаря не вміє вибивати діри, тож звільнене всередині образу місце назовні не повернеться. Перевіряти це варто одразу після прив'язки, а не після першого `fstrim`.

## Параметр модуля `max_loop`

[Параметр модуля](book:unix-linux/kernel-modules) `max_loop` задають як `modprobe loop max_loop=64` або `loop.max_loop=64` у рядку завантаження; типове значення бере `CONFIG_BLK_DEV_LOOP_MIN_COUNT` і зазвичай дорівнює восьми. Сенс у нього залежить від збірки ядра: там, де ввімкнено старе самозавантаження модуля за звертанням до `/dev/loopN`, це **стеля** кількості пристроїв, а в сучасній збірці без нього — лише **скільки створити на старті**, бо далі `LOOP_CTL_GET_FREE` додає їх на вимогу. Стеля в обох випадках одна: `max_loop` не може перевищити ємність простору молодших номерів, поділену на кількість місць під розділи.

## Коди помилок

| код | звідки | що насправді сталося |
|---|---|---|
| `EBUSY` | `LOOP_CONFIGURE`, `LOOP_SET_FD` | пристрій уже прив'язаний до іншого файлу |
| `EBUSY` | `LOOP_CTL_REMOVE` | пристрій прив'язаний або хтось тримає його відкритим |
| `EEXIST` | `LOOP_CTL_ADD` | пристрій із таким номером уже є |
| `ENXIO` | `LOOP_CLR_FD`, `LOOP_CHANGE_FD` | пристрій вільний — відчіплювати чи міняти нема чого |
| `ENODEV` | `LOOP_CTL_REMOVE` | пристрою з таким номером не існує |
| `EINVAL` | `LOOP_CONFIGURE` | негодящий `block_size`, невідомий біт у `lo_flags`, ненульовий `lo_encrypt_type`, переповнення на `lo_offset + lo_sizelimit` |
| `EINVAL` | `LOOP_CHANGE_FD` | новий файл іншого розміру або іншого типу |
| `EBADF` | `LOOP_CONFIGURE`, `LOOP_SET_FD`, `LOOP_CHANGE_FD` | переданого дескриптора немає |
| `EPERM` | `LOOP_SET_STATUS(64)` | пристрій відкрито лише на читання, а `CAP_SYS_ADMIN` немає |
| `ENOMEM` | `LOOP_CONFIGURE`, `LOOP_CTL_ADD` | не вийшло виділити чергу або сам пристрій |

Найчастіша плутанина тут між `EBUSY` і `EEXIST`. Перший каже про **прив'язку**: пристрій існує, але вже зайнятий іншим файлом або кимось відкритий. Другий — про **сам пристрій**: створити `/dev/loop3` не вийшло, бо він уже створений, хай навіть і вільний. Звідси різні ліки: `EBUSY` від `LOOP_CTL_REMOVE` знімається розмонтуванням і закриттям дескрипторів, а `EEXIST` від `LOOP_CTL_ADD` не знімається нічим — номер треба брати інший або взагалі не вибирати його самому, а спитати `LOOP_CTL_GET_FREE`.
