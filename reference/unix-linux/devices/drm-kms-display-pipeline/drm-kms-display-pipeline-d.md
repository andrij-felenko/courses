Коли графічний композитор оновлює зображення робочого столу на частоті 60 Гц, а користувач одночасно пересуває курсор миші з оновленням 1000 Гц, монітор зчитує пікселі з відеопам'яті кожні 16.6 мілісекунди електронним променем або послідовністю пакетів DisplayPort. Якщо оновлення координати курсора та перемикання основного буфера відбуваються через окремі незахищені виклики до пристрою прямо в середині кадрової розгортки, верхня половина екрана відображає старий кадр, а нижня — новий. На екрані виникає горизонтальний розрив зображення (tearing), а курсор візуально «відривається» від рамки вікна. Підсистема ядра DRM/KMS вирішує цю проблему шляхом транзакційного об'єднання всіх змін конфігурації дисплея в єдину атомарну операцію, яка застосовується апаратно під це у вузькому вікні кадрового гасіння VBlank.

## 1. Архітектура підсистеми Direct Rendering Manager (DRM)

Підсистема DRM (Direct Rendering Manager) — це фундаментальний шар ядра Linux, який арбітрує доступ процесів простору користувача до графічного прискорювача (GPU), керує відеопам'яттю та контролює вивід зображення на фізичні монітори.

Фізично підсистема експортує у простір користувача файлові пристрої в каталозі `/dev/dri/`:

- `/dev/dri/cardX` — первинний вузол пристрою (Primary Node), який надає повний доступ до контролера дисплея (KMS) та підсистеми управління пам'яттю;
- `/dev/dri/renderD128` — вузол рендерингу (Render Node), призначений виключно для некопичувальних 3D-обчислень та GPGPU (Vulkan, OpenGL, OpenCL, VA-API) без прав керування моніторами.

```
+-----------------------------------------------------------------------+
|                         ПРОСТІР КОРИСТУВАЧА                           |
|  [ Wayland Compositor / X11 ]          [ 3D App / Vulkan Client ]     |
+------------------------------+----------------------------------------+
                               | (DRM_IOCTL_MODE_ATOMIC)
                               v
+-----------------------------------------------------------------------+
|                              ЯДРО LINUX                               |
|                         [ /dev/dri/card0 ]                            |
|                                                                       |
|   +---------------------------------------------------------------+   |
|   |                       DRM Core (Ядро DRM)                     |   |
|   |   - Обробка ioctl         - Арбітраж файлових дескрипторів    |   |
|   |   - Менеджер GEM / TTM    - Управління об'єктами KMS          |   |
|   +-------------------------------+-------------------------------+   |
|                                   |                                   |
|   +-------------------------------+-------------------------------+   |
|   |             Апаратні драйвери DRM (Hardware Drivers)           |   |
|   |    [ i915 / xe ]          [ amdgpu ]          [ nouveau ]     |   |
|   +-------------------------------+-------------------------------+   |
+-----------------------------------|-----------------------------------+
                                    v
+-----------------------------------------------------------------------+
|                         АПАРАТНЕ ЗАБЕЗПЕЧЕННЯ                         |
|   [ GPU Memory (VRAM) ] ---> [ Display Engine (CRTC) ] ---> [ Panel ] |
+-----------------------------------------------------------------------+
```

Архітектурно DRM розділено на загальне ядро DRM Core та специфічні драйвери виробників (`amdgpu`, `i915`, `xe`, `nouveau`, `msm`). Загальне ядро забезпечує уніфікований POSIX-інтерфейс викликів `ioctl`, а драйвери перекладають ці запити у команди конкретних регістрів графічного процесора.

### 1.1. Підсистеми управління пам'яттю: GEM та TTM

Для рендерингу та відображення кадрів GPU потребує доступу до буферів у пам'яті. Управління цими буферами здійснюється через дві підсистеми ядра:

First, **GEM (Graphics Execution Manager)**. Створений початково компанією Intel, GEM надає простий інтерфейс для створення, мапування та знищення буферів пам'яті (GEM Buffers). Кожен буфер у просторі користувача опредметнюється у вигляді цілочисельного селектора — `GEM Handle`. GEM ідеально підходить для архітектур зі спільною пам'яттю (Unified Memory Architecture, UMA), де CPU та GPU ділять один обсяг RAM.

Second, **TTM (Translation Table Maps)**. Більш потужний менеджер пам'яті, розроблений для дискретних відеокарт з власною локальною відеопам'яттю (VRAM). TTM керує трирівневими просторами пам'яті (VRAM, GTT/GART-системна пам'ять, доступна через DMA, та звичайна RAM) і автоматично витісняє неактивні буфери з VRAM у системну оперативну пам'ять під час дефіциту ресурсів.

Сучасні драйвери дискретних карт використовують GEM як зовнішній API для простору користувача, але всередині ядра транслюють операції на інфраструктуру TTM.

Для створення найпростішого буфера відображення (без використання 3D-прискорювача) DRM надає інтерфейс `Dumb Buffers` через виклики `DRM_IOCTL_MODE_CREATE_DUMB` та `DRM_IOCTL_MODE_MAP_DUMB`. Вони дозволяють простору користувача отримати лінійний масив пікселів у пам'яті, записати туди кадри процесором та вивести їх безпосередньо на монітор.

### 1.2. Формати пікселів та модифікатори розміщення (FourCC & Layout Modifiers)

Для опису вмісту кадрового буфера використовується стандарт FourCC (Four-Character Code), прийнятий у підсистемі DRM (заголовний файл `<drm_fourcc.h>`). Наприклад:

- `DRM_FORMAT_XRGB8888`: 32-бітний упакований формат RGB, де старші 8 біт ігноруються;
- `DRM_FORMAT_ARGB8888`: 32-бітний формат з альфа-каналом прозорості;
- `DRM_FORMAT_NV12`: 12-бітний напівпланарний YUV 4:2:0 формат для декодування відео;
- `DRM_FORMAT_P010`: 16-бітний контейнерний YUV 4:2:0 формат для 10-бітного HDR відео.

Окрім колірного формату, сучасні GPU вимагають знання геометричної упаковки пікселів у пам'яті — **Format Modifiers** (Модифікатори). Замість лінійного розташування (Linear Layout) відеокарти зберігають пікселі тайлами (Tile4, TileY, AFBC — Arm Frame Buffer Compression), що прискорює кешування GPU при 3D-рендерингу. Модифікатор передається через структуру `drmModeAddFB2WithModifiers` і властивість `IN_FORMATS`.

Про те, як графічна підсистема пройшла шлях від небезпечного прямого запису в регістри з боку X11 до монопольного контролю ядра, розказано в [історії еволюції від UMS до Atomic KMS](book:unix-linux/drm-kms-display-pipeline/hist-x11-to-atomic-kms.md).

## 2. Апаратний конвеєр Kernel Mode Setting (KMS)

Kernel Mode Setting (KMS) — це підсистема в рамках DRM, яка повністю абстрагує апаратний конвеєр виводу зображення (Display Pipeline). Завдання KMS — зчитати пікселі з кадрових буферів у пам'яті, виконати їх змішування, сформувати сигнали хронометражу та передати підготовлений потік на фізичний роз'єм екрана.

![Дисплейний конвеєр KMS](/reference/unix-linux/devices/drm-kms-display-pipeline/img/kms-pipeline.svg)
*Топологія конвеєра KMS: зв'язок між кадровими буферами в пам'яті, площинами сканування (Planes), контролером розгортки (CRTC), передавачем (Encoder) та роз'ємом (Connector).*

Конвеєр KMS описується чотирма основними абстракціями ядра:

### 2.1. Planes (Площини сканування)

Площина (Plane) — це апаратне джерело піксельних даних. Вона вказує на конкретний фреймбуфер у пам'яті (`drmModeFB2`), який має визначену роздільну здатність, колірний формат та координати вибірки.

Площини діляться на три типи:

- **Primary Plane (Основна площина):** Повноекранне полотно робочого столу. Кожен CRTC повинен мати принаймні одну активну основну площину.
- **Cursor Plane (Площина курсора):** Спеціалізована легковагова площина малого розміру (зазвичай 64×64 або 128×128 пікселів). Апаратний курсор пересувається по екрану зміною координат у регістрах GPU без перемальовування основного кадру.
- **Overlay/Sprite Plane (Оверлейна площина):** Додаткові апаратні шари, які накладаються поверх основної площини. Вони підтримують апаратне масштабування та колірне перетворення (YUV у RGB), що дозволяє виводити відеопотік з апаратного декодера безпосередньо на екран (Direct Scanout) минаючи композитор.

### 2.2. CRTC (Cathode Ray Tube Controller)

Абстракція CRTC представляє апаратний блок дисплейного контролера у GPU (Display Engine). Незважаючи на застарілу назву від ЕПТ-моніторів, сучасний CRTC виконує три критичні функції:

1. **Сканування та змішування (Scanout & Blending):** Читає пікселі з усіх активних площин (Planes), підпорядкованих цьому CRTC, вибудовує їх за Z-індексом та змішує з урахуванням альфа-каналу.
2. **Колірна обробка (Color Pipeline):** Застосовує таблиці корекції гами (Degamma / Gamma LUT) та колірну матрицю трансформації (CTM).
3. **Генерація кадрового хронометражу (Timings):** Синхронізується з внутрішнім генератором частоти (PLL) та формує сигнали кадрової (`VSYNC`) і рядкової (`HSYNC`) розгортки для обраного відеорежиму (наприклад, 3840×2160 при 60 Гц).

Кількість доступних CRTC на відеокарті визначає максимальну кількість незалежних моніторів, на які GPU може одночасно виводити різні зображення.

### 2.3. Encoders (Енкодери)

Енкодер (Encoder) перетворює цифровий потік пікселів і сигналів синхронізації, згенерований CRTC, у специфічний електронний протокол передачі (наприклад, TMDS для HDMI, main-link для DisplayPort, LVDS для матриць ноутбуків). Енкодер абстрагує внутрішній передавач GPU (PHY).

### 2.4. Connectors (Конектори)

Конектор (Connector) представляє фізичний роз'єм на задній панелі відеокарти або платі (HDMI-A, DisplayPort, eDP, VGA). Конектор відповідає за:

- Моніторинг гарячого підключення (Hotplug Detection, HPD);
- Зчитування структури EDID/DisplayID з EEPROM монітора по шині I2C/DDC для визначення списку підтримуваних відеорежимів;
- Налаштування параметрів каналу зв'язку (сигнали DPCD, керування яскравістю підсвітки).

Повний потік даних у KMS описується направленим графом:
`Plane` → `CRTC` → `Encoder` → `Connector` → `Display`.

## 3. Механізм Atomic KMS: транзакційне перемикання режимів

До появи Atomic KMS оновлення екрана виконувалося через незахищені імперативні виклики `ioctl`. Atomic KMS змінює цю парадигму: усі об'єкти конвеєра перетворюються на носії властивостей (Properties), а зміна стану стає повністю транзакційною.

### 3.1. Двофазна модель Atomic Commit (Two-Phase Commit)

Процес оновлення конфігурації дисплея в Atomic KMS розбитий на два чіткі етапи:

![Двофазний транзакційний процес Atomic Commit](/reference/unix-linux/devices/drm-kms-display-pipeline/img/atomic-commit-flow.svg)
*Двофазний транзакційний процес Atomic Commit: підготовка об'єктів у просторі користувача, перевірка драйвером у режимі TEST_ONLY та атомарне перемикання на VBlank.*

First, **фаза перевірки (Validation Phase):**
Композитор формує контейнер запиту `drmModeAtomicReqPtr`, додає туди нові значення властивостей для необхідних площин, CRTC та конекторів, і викликає `drmModeAtomicCommit` з прапорцем `DRM_MODE_ATOMIC_TEST_ONLY`.

Драйвер ядра виконує внутрішню функцію `atomic_check()`. Вона моделює стан GPU і перевіряє:
- Чи вистачає пропускної здатності шини пам'яті для читання зазначених площин;
- Чи підтримує апаратний колірний блок обрані колірні формати;
- Чи здатні генератори частоти PLL видати потрібну частоту пікселів.

Якщо конфігурація недопустима, ядро негайно повертає помилку `-EINVAL` або `-EBUSY`. Жоден апаратний регістр при цьому не змінюється. Це дозволяє композитору безпечно повернутися до програмного змішування кадрів (software composition fallback).

Second, **фаза коміту (Commit Phase):**
Якщо перевірка успішна, композитор повторює виклик з прапорцями `DRM_MODE_ATOMIC_NONBLOCK | DRM_MODE_PAGE_FLIP_EVENT`. Драйвер ядра приймає запит і під час наступного імпульсу кадрового гасіння VBlank атомарно перезаписує всі відповідні регістри GPU. 

Виклик `drmModeAtomicCommit` не блокує потік виконання композитора. Після того, як апаратне забезпечення перемикає буфери на VBlank, ядро надсилає у файловий дескриптор `/dev/dri/card0` подію `DRM_EVENT_FLIP_COMPLETE`. Композитор зчитує її через `poll()` і починає рендерити наступний кадр.

## 4. Явна синхронізація (Explicit Synchronization) та DRM Sync Objects

У високонавантажених графічних системах (Vulkan, Wayland) рендеринг кадру на GPU та його відображення через KMS відбуваються асинхронно у паралельних чергах команд. Для того, щоб дисплейний контролер не почав сканування буфера до того, як 3D-шейдери завершать запис у пікселі, використовується механізм **Явної синхронізації (Explicit Sync)** на базі DRM Sync Objects (`drm_syncobj`).

```
+-------------------------------------------------------------------+
|                     ПОТІК СИНХРОНІЗАЦІЇ (EXPLICIT SYNC)           |
|                                                                   |
|  [ 3D Render Queue (Vulkan) ] --(signals)--> [ Sync Object Fence ] |
|                                                       |           |
|                                                    (awaits)       |
|                                                       v           |
|  [ Atomic KMS Scanout ] <---(IN_FENCE_FD)-------------+           |
+-------------------------------------------------------------------+
```

1. Композитор або гра надсилає команди рендерингу у 3D-чергу Vulkan і прив'язує до вихідного буфера фенс `IN_FENCE_FD`.
2. При складанні атомарного запиту `drmModeAtomicReq` композитор передає файловий дескриптор цього фенсу у властивість `IN_FENCE_FD` відповідної площини (Plane).
3. Драйвер ядра KMS призупиняє запис у регістри GPU до моменту, поки hardware-сигнал фенсу від 3D-командного движка не стане активним.
4. Після настання VBlank та успішного перемикання кадру ядро сигналізує вихідний фенс `OUT_FENCE_PTR` об'єкта CRTC, інформуючи простір користувача про звільнення попереднього буфера.

## 5. PRIME та dma-buf: Безкопіювальний обмін між багаторазовими GPU

У сучасних комп'ютерах та ноутбуках із гібридною графікою (наприклад, Intel iGPU + NVIDIA dGPU) вивід зображення на монітор фізично підключений до енергоефективного інтегрованого графічного ядра (iGPU), тоді як рендеринг важкої 3D-ігри здійснюється на потужному дискретному прискорювачі (dGPU).

Для передачі відрендерених кадрів від dGPU до iGPU без залучення центрального процесора (Zero-Copy) підсистема DRM використовує інфраструктуру **PRIME**, побудовану на базі ядерного фреймворку **dma-buf**.

![Передача буферів PRIME dma-buf між GPU](/reference/unix-linux/devices/drm-kms-display-pipeline/img/prime-dmabuf-offload.svg)
*Архітектура PRIME dma-buf: безкопіювальний обмін буферами між дискретним GPU (рендеринг) та інтегрованим GPU (сканування на вихід).*

Процес передачі кадрів через PRIME dma-buf функціонує за такою послідовністю:

1. **Рендеринг:** Застосунок (гра) рендерить 3D-сцену у буфер відеопам'яті dGPU за допомогою Vulkan або OpenGL.
2. **Експорт (PRIME Export):** Композитор або драйвер dGPU викликає `ioctl(DRM_IOCTL_PRIME_HANDLE_TO_FD)`. Драйвер dGPU створює в ядрі анонімний об'єкт `dma-buf` і повертає простору користувача звичайний POSIX файловий дескриптор (`dma_buf_fd`).
3. **Передача:** Файловий дескриптор `dma_buf_fd` передається композитору через UNIX-сокет.
4. **Імпорт (PRIME Import):** Драйвер iGPU приймає `dma_buf_fd` через виклик `ioctl(DRM_IOCTL_PRIME_FD_TO_HANDLE)`. Ядро налаштовує таблиці сторінок IOMMU для iGPU так, щоб він міг напряму зчитувати дані з пам'яті dGPU (або через копіювання контролером DMA ядра).
5. **Scanout:** Отриманий `GEM Handle` імпортованого буфера зв'язується з `FB_ID` і передається в Atomic KMS на iGPU для безпосереднього сканування на монітор.

## 6. Діагностика та інспекція стану KMS через debugfs

Для моніторингу поточного стану об'єктів Atomic KMS ядро Linux експортує розширене вікно відлагодження у псевдофайловій системі `debugfs` за шляхом `/sys/kernel/debug/dri/`:

```bash
# Перегляд повного графа об'єктів Atomic KMS та їхніх властивостей
cat /sys/kernel/debug/dri/0/state

# Перегляд стану зареєстрованих кадрових буферів (Framebuffers)
cat /sys/kernel/debug/dri/0/framebuffer

# Перегляд статусу гарячого підключення конекторів
cat /sys/class/drm/card0-HDMI-A-1/status
```

Файл `/sys/kernel/debug/dri/0/state` містить миттєвий злімок усіх активних CRTC, площин та конекторів із зазначенням прив'язаних `FB_ID`, координат `CRTC_X/Y`, таймінгів `MODE_ID` та статусів індикації фенсів, що робить його головним інструментом при пошуку проблем із графічним виводом у ядрі.

Детальний перелік усіх властивостей об'єктів DRM та сигнатури методів `libdrm` наведено в [інтерфейсі властивостей та структурі викликів libdrm](book:unix-linux/drm-kms-display-pipeline/api-drm-kms-properties.md).

Як розрахувати обсяг читання пам'яті та перевірити, чи не перевищить конфігурація площин межу шини пам'яті, описано в [математичному розрахунку хронометражу та пропускної здатності шини](book:unix-linux/drm-kms-display-pipeline/math-display-bandwidth-calc.md).

Для ознайомлення з робочим кодом побудови подвійного буферизатора скористайтеся [повним проєктом двобуферного атомарного перемикання кадрів на C та C++](book:unix-linux/drm-kms-display-pipeline/proj-atomic-kms-flip.md).

> 🔧 **Навіщо це.**
> Архітектура Atomic KMS та dma-buf є основою для побудови сучасних графічних композиторів (Mutter у GNOME, KWin у KDE, `wlroots` у Sway/Hyprland). Вона дозволяє реалізувати технології змінного екрана VRR (FreeSync / G-Sync), розширеного динамічного діапазону HDR, а також гарантує відсутність затримок введення (Input Lag) та розривів зображення без необхідності виконання важких операцій копіювання пам'яті через CPU.

## 7. Підсумковий синтез

Розділення графічної підсистеми Linux на ізольовані шари — арбітраж пам'яті GEM/TTM, об'єктний конвеєр KMS, транзакційний двохфазний Atomic Commit та безкопіювальний обмін буферами dma-buf — створило масштабовану архітектуру. Вона гарантує повну безпеку ядра від збоїв у просторі користувача та забезпечує максимально можливу продуктивність графічного виводу як у крихітних вбудованих системах, так і у потужних багатопроцесорних графічних станціях.
