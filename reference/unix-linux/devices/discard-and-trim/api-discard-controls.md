# 📋 Важелі discard: сисфс, `ioctl`, монтування, утиліти

Повний перелік місць, де discard вмикають, обмежують, викликають рукою й перевіряють — від чисел, які пристрій виставляє в сисфс, до прапорців `fstrim`, `blkdiscard`, `cryptsetup` і `swapon`. Для кожного важеля тут стоїть одиниця виміру, напрямок (лише читати чи можна писати) і те, що станеться, коли шар під ним цієї операції не вміє.

## Чотири поверхи керування

| Поверх | Що вирішує | Де крутиться |
|---|---|---|
| пристрій і черга | чи вміє, якою одиницею, скільки за раз | `/sys/block/<dev>/queue/` |
| блоковий шар напряму | одноразовий запит на конкретний діапазон | `ioctl`: `BLKDISCARD`, `BLKSECDISCARD`, `BLKZEROOUT` |
| проміжні шари | пропускати запит далі чи з'їсти | `lvm.conf`, `cryptsetup`, таблиця dm, loop |
| файлова система | чи віддавати звільнене й коли саме | параметри монтування, `ioctl FITRIM` |

Поверхи складаються послідовно, і запит помирає на найнижчому з тих, що його не пропустили — мовчки, з кодом успіху. Тому шукати обрив треба знизу вгору: спершу переконатися, що discard узагалі доходить до заліза, і лише потім розбиратися з параметрами монтування.

## Що пристрій каже про себе

Файли в `/sys/block/<dev>/queue/` — звичайні текстові, по одному числу в кожному ([модель sysfs](topic:unix-linux/sysfs-device-model): ядро показує свої об'єкти каталогами, а їхні поля — файлами, які читає `cat` і пише `echo … >` від root). Одиниця скрізь байт.

| Файл | Запис | Що означає |
|---|---|---|
| `discard_granularity` | — | розмір внутрішньої одиниці розподілу, якщо пристрій її повідомив; запит підрізається до кратности цьому числу |
| `discard_max_hw_bytes` | — | стеля заліза на один запит |
| `discard_max_bytes` | **так** | програмна стеля в межах апаратної. **Нуль тут — головна ознака: звідси й нижче discard не проходить** |
| `write_zeroes_max_bytes` | — | скільки байтів пристрій занулює однією операцією, не переганяючи нулі через шину |
| `discard_zeroes_data` | — | залишок минулого: від випуску 4.12 **завжди читається нулем**, і покладатися на нього не можна взагалі |
| `<dev>/discard_alignment` | — | лежить поверхом вище, поруч із пристроєм: зсув початку пристрою або розділу від межі внутрішньої одиниці |

Записане в `discard_max_bytes` живе до зникнення пристрою; постійности досягають правилом udev. Опускають цю стелю тоді, коли великий discard займає носій на секунди й псує затримку всьому іншому. Решту чисел черги зібрано в [властивостях черги](topic:unix-linux/block-device-model/api-queue-attributes.md) — там і розміри блоків, і межі запиту, і планувальник.

Ту саму четвірку людською таблицею дає `lsblk -D` (колонки `DISC-ALN`, `DISC-GRAN`, `DISC-MAX`, `DISC-ZERO`), і саме нею зручно дивитися весь стос згори вниз.

## Запити `ioctl` на блоковому пристрої

Три запити, і аргумент у всіх трьох однаковий — масив із двох 64-бітних чисел: зсув і довжина **в байтах**, не в секторах ([керуючий канал `ioctl`](topic:unix-linux/ioctl-interface): третій аргумент — просто вказівник, і його вміст описує кожен запит по-своєму).

```c
#include <linux/fs.h>     /* BLKDISCARD, BLKSECDISCARD, BLKZEROOUT */
#include <sys/ioctl.h>
#include <fcntl.h>
#include <stdint.h>

int fd = open("/dev/nvme0n1", O_WRONLY);        /* саме на запис */
uint64_t range[2] = { 1ULL << 30, 256ULL << 20 };   /* зсув 1 ГіБ, довжина 256 МіБ */

if (ioctl(fd, BLKDISCARD, range) < 0)
        perror("BLKDISCARD");
```

| Запит | Код | Вирівнювання зсуву й довжини | Чого просить |
|---|---|---|---|
| `BLKDISCARD` | `_IO(0x12, 119)` | логічний блок пристрою | «діапазон більше не потрібен» |
| `BLKSECDISCARD` | `_IO(0x12, 125)` | 512 байтів | те саме плюс вимога знищити й внутрішні копії |
| `BLKZEROOUT` | `_IO(0x12, 127)` | 512 байтів | «звідси читатимуться нулі» — і це вже гарантія |
| `BLKDISCARDZEROES` | `_IO(0x12, 124)` | — | залишок минулого: завжди віддає 0 |

Різниця між першим і третім принципова. `BLKDISCARD` не обіцяє нічого спостережного, зате `BLKZEROOUT` не має права збрехати: якщо пристрій не вміє занулення однією командою, ядро просто перепише діапазон нулями через шину. Тому `BLKZEROOUT` не повертає `EOPNOTSUPP` — він або швидкий, або повільний, але завжди справджується. `BLKSECDISCARD` же не має нічого спільного з `SANITIZE`: це запит до контролера, який мало хто з пристроїв заявляє, і для гарантованого знищення потрібні [інші команди](topic:unix-linux/secure-erase-and-sanitize).

| Код помилки | Коли |
|---|---|
| `EBADF` | дескриптор відкрито без права запису. Не «поганий дескриптор», а «не той режим» |
| `EPERM` | пристрій переведено в режим лише читання (`blockdev --setro`) |
| `EOPNOTSUPP` | шар не вміє: для `BLKDISCARD` це `discard_max_bytes` = 0, для `BLKSECDISCARD` — незаявлене захищене відкидання |
| `EINVAL` | зсув чи довжина не вирівняні, довжина нульова або діапазон вилазить за край пристрою |
| `EFAULT` | масив `range` не читається за поданою адресою |
| `EBUSY` | пристрій уже комусь належить — майже завжди змонтований |
| `ENOTTY` | дескриптор указує не на блоковий пристрій |

## `FITRIM`: те саме через файлову систему

`FITRIM` подають не на пристрій, а на **будь-який файл або каталог усередині змонтованої файлової системи** — зазвичай на точку монтування. Реалізує його кожна файлова система сама (ext4, XFS, btrfs, F2FS), тому й поводиться він трохи по-різному.

```c
#include <linux/fs.h>     /* FITRIM; struct fstrim_range оголошено тут:
                             __u64 start   — звідки шукати вільні блоки, байти
                             __u64 len     — скільки байтів переглянути
                             __u64 minlen  — найкоротша суцільна смуга, варта запиту */

struct fstrim_range r = { .start = 0, .len = UINT64_MAX, .minlen = 0 };
int fd = open("/", O_RDONLY);

if (ioctl(fd, FITRIM, &r) == 0)
        printf("віддано вниз %llu байтів\n", (unsigned long long)r.len);
```

Три поля роблять три різні речі. `start` і `len` обмежують **ділянку файлової системи**, яку варто обійти, — так великий обхід ріжуть на частини, щоб не займати систему надовго. `minlen` же відсіює дрібне: смуги вільного місця, коротші за це число, у запит не потрапляють. Нуль означає «віддавати все підряд», але ядро однаково підніме `minlen` щонайменше до `discard_granularity` пристрою, бо дрібніший запит усе одно перетвориться на порожній.

Після успішного повернення `len` **перезаписано**: там уже не «скільки переглянути», а скільки байтів файлова система віддала вниз. Саме це число друкує `fstrim -v`.

| Код помилки | Коли |
|---|---|
| `EPERM` | у процесу немає `CAP_SYS_ADMIN` ([можливості](topic:unix-linux/capabilities): права root розібрано на окремі дозволи, і цей запит вимагає саме адміністративного) |
| `EOPNOTSUPP` | файлова система не реалізує `FITRIM` або пристрій під нею не вміє discard |
| `EINVAL` | `start` за межами файлової системи, `len` менша за блок, `minlen` більша за групу блоків |
| `EROFS` | ext4: журнал ще не програно |
| `EFAULT` | структура не читається або не записується |

## Утиліти

`fstrim` — це `FITRIM` із розбором точок монтування; `blkdiscard` — це три `BLK*`-запити напряму, повз файлову систему.

| `fstrim` | Що робить |
|---|---|
| `-a, --all` | обійти всі змонтовані ФС, які вміють discard, решту мовчки пропустити |
| `-A, --fstab` | обійти лише те, що згадано в `/etc/fstab` |
| `--listed-in <список>` | джерела списку через двокрапку, напр. `/etc/fstab:/proc/self/mountinfo` |
| `-o, --offset` | звідки починати пошук вільних блоків (`start`) |
| `-l, --length` | скільки байтів переглянути (`len`) |
| `-m, --minimum` | `minlen`; округлюється вгору до блока ФС. Типово 0 |
| `-n, --dry-run` | пройти все, крім самого `ioctl` |
| `-v, --verbose` | надрукувати, скільки байтів віддано вниз |
| `--quiet-unsupported` | не лаятися на ФС без підтримки |

Коди виходу окремі: `0` — все вдалося, `1` — загальна помилка, `32` — не вдалося ніде, `64` — десь вдалося, десь ні.

Типовий дистрибутив нічого з цього не запускає рукою: у util-linux є пара юнітів ([systemd](topic:unix-linux/systemd-model): таймер — це юніт, який будить свій однойменний сервіс за розкладом), і працює вона так:

```ini
# fstrim.timer
OnCalendar=weekly
AccuracySec=1h
Persistent=true
RandomizedDelaySec=100min

# fstrim.service
ExecStart=/usr/sbin/fstrim --listed-in /etc/fstab:/proc/self/mountinfo --verbose --quiet-unsupported
```

`Persistent=true` доганяє пропущений запуск після ввімкнення машини, а стохвилинна затримка розводить у часі гостей, які прокидаються разом на одному хості.

| `blkdiscard` | Що робить |
|---|---|
| `-o, --offset` | зсув у байтах |
| `-l, --length` | довжина в байтах; без неї — до кінця пристрою |
| `-p, --step` | різати роботу на порції такого розміру замість одного велетенського запиту |
| `-s, --secure` | `BLKSECDISCARD` замість `BLKDISCARD` |
| `-z, --zeroout` | `BLKZEROOUT`: не відкидати, а занулити |
| `-f, --force` | не відкривати пристрій виключно — саме цим і знімають `EBUSY`, і саме тому це найнебезпечніший ключ утиліти |
| `-v` / `-q` | показувати вирівняні межі й поступ / мовчати |

Без `-o` й `-l` `blkdiscard` віддає **весь пристрій** — це не помилка проєктування, а основний його вжиток: так робить `mkfs` перед створенням файлової системи.

## Параметри монтування

| ФС | Параметр | Типово | Коли віддається вниз |
|---|---|---|---|
| ext4 | `discard` / `nodiscard` | `nodiscard` | у фіксації транзакції, яка звільнила блоки |
| XFS | `discard` / `nodiscard` | `nodiscard` | коли звільнений екстент стає придатним для повторного виділення |
| btrfs | `discard`, воно ж `discard=sync` | — | синхронно, у момент звільнення екстента |
| btrfs | `discard=async` | увімкнено само від 6.2 на носіях, що вміють (з'явився в 5.6) | фоновим потоком, після злиття діапазонів і з обмеженням швидкости |
| btrfs | `nodiscard` | — | ніколи |
| F2FS | `discard` / `nodiscard` | `discard` — **увімкнено** | коли сегмент прибрано збирачем |
| F2FS | `discard_unit=block\|segment\|section` | `block`; на зонних носіях — `section` | задає вирівнювання запиту |

Асинхронний режим btrfs — єдиний, у якого є власні регулятори швидкости, і живуть вони в `/sys/fs/btrfs/<UUID>/discard/`:

| Файл | Од. | Типово | Що обмежує |
|---|---|---|---|
| `iops_limit` | запити/с | 1000 (до 6.3 — 100) | як часто фоновий потік подає запити |
| `kbps_limit` | КіБ/с | 0 — без обмеження | сумарну швидкість відкидання |
| `max_discard_size` | Б | 64 МіБ | найбільший діапазон в одному запиті |

Поруч у тому ж каталозі лежать лічильники лише на читання — скільки зараз стоїть у черзі на відкидання й скільки роботи вже зекономлено.

## Діра у файлі

Для звичайного файлу роль discard відіграє пробивання діри: ділянку списують, файл стає [розрідженим](topic:unix-linux/sparse-files) (у ньому просто немає блоків під цим зсувом, і читання з такого місця віддає нулі, не займаючи носія), а звільнені блоки повертаються у файлову систему — яка вже сама вирішує, чи віддавати їх нижче.

```c
#define _GNU_SOURCE
#include <fcntl.h>

/* PUNCH_HOLE обов'язково разом із KEEP_SIZE — розмір файлу не міняється */
fallocate(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, offset, len);
```

`FALLOC_FL_PUNCH_HOLE` з'явився в 2.6.38; підтримують XFS (2.6.38), tmpfs (3.5), ext4 (3.0), btrfs (3.7), gfs2 (4.16). Відсутність підтримки видно одразу — `EOPNOTSUPP`; інші помилки: `EINVAL` (від'ємний зсув або недодатна довжина), `EPERM` (файл незмінний чи запечатаний), `ETXTBSY` (файл зараз виконується). Сусідній прапорець `FALLOC_FL_ZERO_RANGE` (з 3.15) робить те, що обіцяє `BLKZEROOUT`: гарантує нулі, місце ж може лишити за файлом.

Те саме з командного рядка: `fallocate -p -o <зсув> -l <довжина> <файл>` пробиває вказану діру, а `fallocate -d <файл>` обходить файл і викидає ті ділянки, де вже й так суцільні нулі.

## Розділ підкачки

Простір підкачки нікому не потрібен між перезавантаженнями цілком, тому в нього своя пара політик ([свопінг](topic:unix-linux/swap-and-reclaim): ядро виносить сторінки в цей простір і повертає назад, а звільнені слоти перевикористовує).

| Ключ `swapon` / поле в `/etc/fstab` | Що робить |
|---|---|
| `-d`, `--discard`, або `discard` | обидві політики разом |
| `--discard=once`, `discard=once` | один великий discard на всю ділянку в мить підключення |
| `--discard=pages`, `discard=pages` | відкидати звільнені сторінки далі, у міру роботи |

Політика `once` майже безкоштовна й майже завжди виправдана; `pages` — це той самий гарячий шлях, що й `-o discard` у файловій системі, з тією ж ціною.

## Шари між файловою системою й носієм

Кожен шар [device mapper](topic:unix-linux/device-mapper) вирішує долю discard окремо, і типові налаштування в них різні.

| Шар | Важіль | Типово | Що саме вмикає |
|---|---|---|---|
| [LVM](topic:unix-linux/lvm-and-snapshots) | `issue_discards` у `lvm.conf` | `0` | чи видає **сама LVM** discard на фізичний том, звільняючи екстенти в `lvremove` і `lvreduce`. Наскрізного discard від файлової системи через лінійний том це не стосується — він іде незалежно |
| [тонкий пул](topic:unix-linux/dm-thin-provisioning) | `thin_pool_discards` у `lvm.conf` | `passdown` | `passdown` — повернути шматки в пул і передати запит нижче; `nopassdown` — повернути, але вниз не передавати; `ignore` — не приймати взагалі |
| [dm-crypt](topic:unix-linux/dm-crypt) | `--allow-discards` у `cryptsetup open`; `discard` у `/etc/crypttab` | заборонено | пропускати discard крізь шифрування. `--persistent` записує прапорець у метадані LUKS2, щоб не повторювати його щоразу |
| [loop](topic:unix-linux/loop-device) | окремого ключа немає | само | loop оголошує підтримку discard тоді й лише тоді, коли файл-підкладка лежить на ФС із пробиванням дір; `REQ_OP_DISCARD` перетворюється на `FALLOC_FL_PUNCH_HOLE \| FALLOC_FL_KEEP_SIZE` |

Заборона в dm-crypt — не обережність упорядників, а прямо описаний у документації обмін: наскрізний discard показує стороннім, скільки на зашифрованому томі даних і як вони розкладені, бо карта відкинутих ділянок повторює карту зайнятости.

## Де обривається ланцюг

```sh
$ lsblk -D
NAME          DISC-ALN DISC-GRAN DISC-MAX DISC-ZERO
nvme0n1              0      512B       2T         0
└─nvme0n1p2          0      512B       2T         0
  └─luks-root        0        0B       0B         0   ← далі не йде
```

Нулі в `DISC-GRAN` і `DISC-MAX` на верхньому шарі при живих числах під ним читаються однозначно: обрив саме тут, і шукати треба параметр цього шару, а не модель диска. Далі — параметри монтування (`findmnt -no OPTIONS /`) і холостий прогін `fstrim -nv /`, який пройде весь шлях і не подасть самого запиту.
