# 📜 Історія стандартизації SPDM та трансформації безпеки PCIe

Стандартизація протоколу Security Protocol and Data Model (SPDM) стала відповіддю на фундаментальну кризу довіри до периферійного апаратного забезпечення, що розгорталася протягом двох десятиліть розвитку високошвидкісних шин системного вводу-виводу.

## Ера монолітної довіри та перші апаратні атестації

На початку 2000-х років концепція криптографічної перевірки цілісності платформи базувалася на модульній технології Trusted Platform Module (TPM), розробленій консорціумом Trusted Computing Group (TCG). ТКМ виступав у ролі пасивного криптографічного якоря довіри (Root of Trust, RoT) на материнській платі. Його завданням було вимірювання завантажувача (Bootloader), ядра операційної системи та основних конфігурацій шляхом послідовного хешування і збереження результатів у реєстрах конфігурації платформи (Platform Configuration Registers, PCR).

Проте TPM оперував виключно центральним процесором та системною платою. Периферійні пристрої на шинах PCI та PCI-X вважалися апріорі довіреними компонентами, закритими внутрішнім периметром корпусу сервера. Стрімкий перехід на PCI Express (PCIe) у 2003 році та впровадження високошвидкісного прямого доступу до пам'яті (Direct Memory Access, DMA) кардинально змінили ландшафт загроз. Мережеві контролери, адаптери Fibre Channel та графічні прискорювачі отримали можливість читати та модифікувати будь-яку ділянку RAM зі швидкістю кількох гігабайтів на секунду.

## Розквіт DMA-атак та обмеженість IOMMU

З появою доступних контролерів на базі FPGA та спеціалізованих плат для аналізу шини (наприклад, інструментів PCILeech, розроблених дослідником Ульфом Фріском у 2016 році) DMA-атаки перетворилися з теоретичної загрози на масовий інструмент компрометації. Зловмисник, що мав фізичний доступ до PCIe-слота або інтерфейсу Thunderbolt, міг підключити плату-емулятор, яка підробляла ідентифікаційні дані Vendor ID / Device ID і зчитувала з пам'яті ядра криптографічні ключі SSH, шифрування дисків LUKS або таблиці сторінок пам'яті.

Апаратна відповідь індустрії — блок трансляції та ізоляції адрес IOMMU (Intel VT-d, AMD-Vi) — частково обмежила регіони пам'яті, доступні конкретним пристроям. Однак IOMMU мав дві критичні слабкості:
1. **Відсутність автентифікації прошивки**: Якщо зловмисник перепрошивав оригінальну мережеву карту модифікованим мікрокодом (Option ROM / Firmware), пристрій отримував легітимні права IOMMU від ядра, але таємно виконував несанкціоноване читання сусідніх buffers.
2. **Атаки на етапі ініціалізації**: Під час завантаження системи (Early Boot) до ввімкнення таблиць IOMMU периферійний пристрій міг повністю перехопити контроль над процесом завантаження.

Виробники обладнання намагалися вирішувати проблему власницькими (proprietary) методами. Компанії Intel, Nvidia, Broadcom та Mellanox створювали закриті протоколи перевірки підписів прошивок через виклики Vendor Specific Extended Capabilities (VSEC) або інтерфейси SMBus/I2C. Наприклад, мережеві карти Intel використовували закриті ключі в інкапсульованих контролерах Management Engine, а графічні процесори Nvidia використовували технологію Falcon / GSP для перевірки цифрових підписів Option ROM. Це призвело до фрагментації: операційна система Linux повинна була мати десятки унікальних проприєтарних драйверів для перевірки цілісності периферії кожного окремого вендора.

## Народження SPDM у надрах DMTF

У 2019 році організація Distributed Management Task Force (DMTF) за участі провідних технологічних гігантів (Intel, AMD, Nvidia, ARM, Broadcom, Microsoft, Western Digital) випустила першу специфікацію стандарту SPDM 1.0. Метою проєкту було створення єдиного відкритого криптографічного протоколу, незалежного від фізичного транспорту, який дозволяє будь-якому елементу обчислювальної системи перевірити автентичність та цілісність іншого елемента.

Архітектура SPDM запозичила фундаментальні концепції з публічних протоколів TLS 1.3 та X.509, але була жорстко оптимізована для обмежених обчислювальних ресурсів периферійних мікроконтролерів (Security Controllers / Embedded EC):
- **SPDM 1.0 (2019)**: Визначив базову структуру повідомлень, узгодження криптографічних алгоритмів, завантаження ланцюжка сертифікатів (Certificate Chain) та виконання процедури Challenge-Response для підтвердження володіння приватним ключем пристрою.
- **SPDM 1.1 (2020)**: Додав підтримку вимірювань цілісності (Measurements) — аналогів PCR у TPM, що дозволило хосту зчитувати хеші всіх модулів прошивки та таблиць конфігурації Responder.
- **SPDM 1.2 (2021)**: Запровадив механізм встановлення захищеної сесії (Session Key Exchange) на основі алгоритму Diffie-Hellman на еліптичних кривих (ECDHE) або PSK. Це створило фундамент для канального шифрування.
- **SPDM 1.3 (2023)**: Додав підтримку постквантової криптографії (PQC), оптимізовані вимірювання за запитом та розширені сертифікати ідентичності пристроїв (Device Identity Certificates).

Для забезпечення відкритості та сумісності між різними ОС у 2020 році консорціум UEFI Forum та DMTF запустили проєкт `libspdm` (початково названий `OpenSPDM`). Ця реалізація мовою C з відкритим вихідним кодом була спроєктована таким чином, щоб працювати в умовах суворих обмежень: без динамічного виділення пам'яті (no heap allocation), без плаваючої коми та з можливістю компіляції як у призначеному для користувача просторі, так і в режимі ядра чи мікроконтролера.

## Інтеграція PCI-SIG: DOE, CMA та PCIe IDE

Стандарт SPDM залишався б абстрактним специфікованим протоколом, якби консорціум PCI-SIG не інтегрував його безпосередньо у специфікацію PCI Express 5.0 та 6.0.

Для цього PCI-SIG створив два ключові апаратні механізми:
1. **Data Object Exchange (DOE)**: Нова розширена можливість PCIe (Extended Capability з ID `0x002E`), яка надає стандартний поштовий ящик (Mailbox) у конфігураційному просторі пристрою. Через цей поштовий ящик хост і пристрій можуть обмінюватись довільними бінарними пакетами даних без залучення драйверів пристрою та без прямого доступу до RAM.
2. **Component Measurement and Authentication (CMA)**: Стандартизований профіль інкапсуляції SPDM-повідомлень у пакети DOE. CMA чітко регламентує, які саме команди SPDM є обов'язковими для автентифікації PCIe-пристрою.

Паралельно з цим було розроблено технологію **PCIe Integrity and Data Encryption (IDE)**. Вона вирішила проблему фізичного перехоплення пакетів TLP (Transaction Layer Packets) між процесором та пристроєм на лінії PCIe. Завдяки SPDM 1.2 хост і пристрій виконують взаємну атестацію, генерують симетричні ключі AES-256-GCM і завантажують їх у свої апаратні IDE-контролери, забезпечуючи наскрізне шифрування шини з нульовою затримкою.

## Сучасний стан, стандарти PCIe 6.0/7.0 та екосистема CXL

З появою специфікацій PCIe 6.0 (2022) та PCIe 7.0 (2025), а також архітектури Compute Express Link (CXL 2.0 / 3.0), яка дозволяє об'єднувати оперативну пам'ять процесора та зовнішніх прискорювачів у спільний когерентний простір, SPDM перетворився на обов'язковий стандарт сертифікації обладнання. У когерентній системі неавтентифікований пристрій може отруїти кеш процесора або прочитати пам'ять сусідньої віртуальної машини в середовищах Confidential Computing (Intel TDX, AMD SEV-SNP, ARM CCA).

У ядрі Linux підтримка SPDM розвивалася завдяки співпраці інженерів Intel, Western Digital, Red Hat, Google та AMD. Створення нативної ядерної бібліотеки `libspdm` та її інтеграція у підсистему PCI ядра Linux (починаючи з версії 6.5+) перетворила атестацію PCIe-пристроїв із проприєтарного лабораторного експерименту на стандартний етап ініціалізації апаратного забезпечення операційної системи. Специфікація SPDM стала невід'ємною частиною архітектури Zero Trust Hardware у сучасних дата-центрах.
