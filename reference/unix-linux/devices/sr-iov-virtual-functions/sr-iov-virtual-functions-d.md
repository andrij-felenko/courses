# Апаратне розділення пристроїв (SR-IOV)

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У сучасних центрах обробки даних (ЦОД) та середовищах хмарних обчислень продуктивність мережі та підсистем зберігання даних відіграє критичну роль. Традиційні методи віртуалізації вводу-виводу (I/O), такі як програмні комутатори (vSwitch) або пара-віртуалізовані драйвери (virtio), забезпечують гнучкість, але вносять помітні накладні витрати на обробку кожного пакета чи запиту центральним процесором (CPU). Щоб вирішити цю проблему, консорціум PCI-SIG розробив специфікацію **Single Root I/O Virtualization (SR-IOV)**.

SR-IOV — це розширення стандарту PCI Express (PCIe), яке дозволяє одному фізичному пристрою (наприклад, мережевому адаптеру або NVMe-накопичувачу) представляти себе як кілька окремих, незалежних пристроїв на шині PCIe. Це дає змогу віртуальним машинам (ВМ) отримувати прямий доступ до апаратних ресурсів без участі гіпервізора в процесі передачі даних (data path), забезпечуючи продуктивність на рівні bare-metal (безпосереднього доступу до «заліза»).

У цій статті ми детально розглянемо архітектуру SR-IOV, концепції Physical Functions (PF) та Virtual Functions (VF), процес їх налаштування в Linux через `/sys/bus/pci/devices/.../sriov_numvfs`, а також внутрішні механізми роботи апаратних черг.

---

## 1. Архітектура та принципи роботи SR-IOV

Специфікація SR-IOV вводить два ключових поняття для PCIe-пристроїв:

1. **Physical Function (PF):**
   PF — це повнофункціональний пристрій PCIe. Він має повний доступ до всіх конфігураційних регістрів пристрою та відповідає за глобальне керування ним. PF використовується для налаштування самого пристрою, а також для створення та управління віртуальними функціями. Операційна система хоста (або гіпервізор) бачить PF як звичайний PCI-пристрій, до якого застосовуються стандартні драйвери.
   
2. **Virtual Function (VF):**
   VF — це «полегшена» версія PCIe-пристрою (lightweight PCIe function). Вона містить лише ресурси, необхідні для переміщення даних (I/O) та обмежений набір конфігураційних регістрів. VF не можуть самостійно змінювати глобальний стан пристрою (наприклад, змінювати швидкість лінка чи виконувати повне скидання пристрою). Їхня єдина мета — приймати та надсилати дані. Кожна VF має власне конфігураційне простір PCIe (включаючи ідентифікатори Vendor ID / Device ID) і виглядає для операційної системи гостя як незалежний апаратний пристрій.

### Переваги такого підходу:
- **Прямий доступ до пам'яті (Direct Memory Access, DMA):** VF можуть виконувати DMA безпосередньо в пам'ять віртуальної машини (завдяки IOMMU/VT-d/AMD-Vi, що здійснюють трансляцію адрес).
- **Зниження навантаження на CPU:** Оскільки гіпервізор виключений зі шляху передачі даних, CPU не витрачає цикли на копіювання пакетів між віртуальними інтерфейсами та фізичним обладнанням.
- **Мінімальна затримка (Latency):** Мережеві пакети потрапляють безпосередньо в пам'ять гостьової ОС, що радикально знижує затримки та джитер, що критично для NFV (Network Functions Virtualization), HFT (High-Frequency Trading) та телекомунікацій.

## 2. Роль IOMMU у SR-IOV

Для безпечного та коректного прокидання (passthrough) VF у віртуальну машину необхідна підтримка на рівні платформи, а саме — **IOMMU** (Input/Output Memory Management Unit). У процесорах Intel ця технологія називається **VT-d** (Virtualization Technology for Directed I/O), у AMD — **AMD-Vi**.

IOMMU виконує дві критично важливі функції:
1. **Трансляція адрес DMA:** Коли VF намагається виконати DMA-запис у пам'ять, вона використовує адресу пам'яті гостьової ОС (Guest Physical Address, GPA). IOMMU перехоплює цей запит і транслює GPA у реальну фізичну адресу хоста (Host Physical Address, HPA) за допомогою таблиць сторінок (IOMMU page tables), що підтримуються гіпервізором.
2. **Ізоляція та безпека (Interrupt/DMA Remapping):** IOMMU гарантує, що конкретна VF може читати чи писати лише в ті сторінки пам'яті, які належать її віртуальній машині. Це запобігає атакам типу DMA-spoofing або випадковому пошкодженню пам'яті інших ВМ чи самого гіпервізора.

Без увімкненого IOMMU використання SR-IOV для віртуальних машин неможливе. В ОС Linux це зазвичай досягається додаванням параметрів ядра при завантаженні (у GRUB):
```bash
# Для процесорів Intel:
intel_iommu=on iommu=pt

# Для процесорів AMD:
amd_iommu=on iommu=pt
```
Параметр `iommu=pt` (passthrough) оптимізує продуктивність для пристроїв, які залишаються у використанні самого хоста, дозволяючи їм обходити складну трансляцію.

## 3. Налаштування SR-IOV у Linux (`sriov_numvfs`)

Сучасне ядро Linux (починаючи з версій 3.8+) пропонує стандартизований інтерфейс (sysfs) для керування SR-IOV, абстрагуючи відмінності між різними виробниками обладнання. 

Раніше створення VF виконувалося через передачу параметрів модулю ядра (наприклад, `modprobe ixgbe max_vfs=7`). Цей метод нині вважається застарілим і часто не підтримується новими драйверами. Замість цього використовується файл `sriov_numvfs` у sysfs.

### 3.1. Перевірка підтримки SR-IOV

Спочатку необхідно переконатися, що пристрій та його драйвер підтримують SR-IOV. Знайдемо наш мережевий адаптер за допомогою `lspci`:

```bash
$ lspci | grep Ethernet
03:00.0 Ethernet controller: Intel Corporation Ethernet Controller X710 for 10GbE SFP+ (rev 02)
03:00.1 Ethernet controller: Intel Corporation Ethernet Controller X710 for 10GbE SFP+ (rev 02)
```

Перевіримо наявність файлу `sriov_numvfs` та `sriov_totalvfs` у директорії пристрою:

```bash
$ cd /sys/bus/pci/devices/0000:03:00.0/
$ cat sriov_totalvfs
64
$ cat sriov_numvfs
0
```
- `sriov_totalvfs` — максимальна апаратна кількість VF, яку може створити цей PF (у цьому випадку 64).
- `sriov_numvfs` — поточна кількість активних VF.

### 3.2. Створення віртуальних функцій (VF)

Щоб створити віртуальні функції, необхідно записати бажану кількість у файл `sriov_numvfs`. Важливо: якщо VF вже існують (значення > 0), спочатку потрібно записати 0, щоб видалити їх, а потім задати нове значення.

Створимо 4 VF для порту `0000:03:00.0`:

```bash
$ echo 4 | sudo tee /sys/bus/pci/devices/0000:03:00.0/sriov_numvfs
```

Перевіряємо результат:

```bash
$ lspci | grep -i "Virtual Function"
03:02.0 Ethernet controller: Intel Corporation Ethernet Virtual Function 700 Series (rev 02)
03:02.1 Ethernet controller: Intel Corporation Ethernet Virtual Function 700 Series (rev 02)
03:02.2 Ethernet controller: Intel Corporation Ethernet Virtual Function 700 Series (rev 02)
03:02.3 Ethernet controller: Intel Corporation Ethernet Virtual Function 700 Series (rev 02)
```

Тепер на шині PCI з'явилися 4 нові пристрої. Гіпервізор хоста (наприклад, драйвер `iavf` для адаптерів Intel) може відразу прив'язатися до них і створити для них звичайні мережеві інтерфейси (наприклад, `eth1`, `eth2`), але зазвичай їх відв'язують (unbind) від хостового драйвера і передають драйверу `vfio-pci` для подальшого прокидання у ВМ.

### 3.3. Керування MAC-адресами та VLAN на рівні PF

Оскільки VF розділяють один фізичний порт (і один провід/оптичний кабель), PF містить вбудований апаратний комутатор (Embedded eSwitch), який сортує вхідні пакети та спрямовує їх до відповідної VF.

Для забезпечення безпеки та коректної маршрутизації адміністратор хоста повинен призначити MAC-адреси та, за потреби, теги VLAN для кожної VF через утиліту `ip link`. Якщо цього не зробити, гостьова ОС може генерувати випадкові MAC-адреси, але хост може заблокувати такий трафік (anti-spoofing).

Приклад налаштування MAC-адреси та ізоляції у VLAN 100 для першої VF (vf 0) фізичного інтерфейсу `enp3s0f0`:

```bash
$ ip link set dev enp3s0f0 vf 0 mac 52:54:00:11:22:33 vlan 100 spoofchk on
```
- `mac 52:54...` — жорстко задає MAC для гостя.
- `vlan 100` — апаратний eSwitch буде додавати тег VLAN 100 до вихідних пакетів цієї VF і знімати тег при надходженні пакетів з мережі до VF. Гостьова ОС не бачить тегів і вважає, що працює у нетегованій мережі.
- `spoofchk on` — апаратне блокування пакетів, якщо гість спробує надіслати пакет із підробленим вихідним MAC-адресом.

## 4. Апаратні черги: Ніша продуктивності

Однією з найважливіших складових сучасних NIC (і NVMe) є наявність багатьох апаратних черг (Hardware Queues) для передачі (Tx) та прийому (Rx). У традиційному сценарії ці черги розділяються між ядрами процесора хоста (за допомогою технології RSS - Receive Side Scaling).

При використанні SR-IOV апаратні ресурси пристрою, включно з чергами, жорстко діляться між PF і VF. Коли ви створюєте VF, прошивка мережевої карти виділяє кожній VF свій власний незалежний пул апаратних черг (Tx/Rx queues) та переривань (MSI-X).

Коли пакет приходить з мережі, вбудований у NIC комутатор (L2-сортувальник або eSwitch) перевіряє MAC-адресу призначення та/або VLAN тег. На основі цих даних він миттєво приймає рішення, до пулу черг якої VF належить пакет, і кладе його туди. Після цього ініціюється апаратне переривання (MSI-X), яке прокидається через гіпервізор (KVM) безпосередньо у віртуальну машину.

Гостьова ОС обробляє це переривання своїм власним драйвером (наприклад, `iavf` або `mlx5_core`) та читає дані безпосередньо з фізичної пам'яті (завдяки DMA через IOMMU).

### 4.1. SR-IOV у Storage (NVMe)

Хоча SR-IOV найчастіше асоціюється з мережевими інтерфейсами, ця технологія також широко застосовується для NVMe-накопичувачів.
NVMe-пристрій з підтримкою SR-IOV може створити кілька VF, кожна з яких представлятиме віртуальний контролер. Кожній такій VF виділяється окремий простір імен (Namespace) або його частина, а також окремі черги Submission та Completion (SQ/CQ).
Віртуальна машина отримує прямий доступ до NVMe VF. Запити I/O не проходять через віртуальні контролери типу `virtio-blk` або `virtio-scsi`, що дозволяє досягти затримок на рівні мікросекунд та мільйонів IOPS прямо всередині ВМ.

## 5. Персистентність налаштувань

Зміни, внесені через `/sys/.../sriov_numvfs`, є тимчасовими і скидаються під час перезавантаження сервера. У Linux немає єдиного стандартизованого конфігураційного файлу для sysfs-параметрів пристроїв, оскільки шина PCI ініціалізується динамічно.

Щоб зберігати кількість VF після ребуту, зазвичай використовують правила `udev` або сервіси `systemd`.

**Приклад правила udev (розміщується у `/etc/udev/rules.d/99-sriov.rules`):**
```udev
# Встановлення 4 VF для пристрою з Vendor ID 8086 та Device ID 1572
ACTION=="add", SUBSYSTEM=="pci", ATTR{vendor}=="0x8086", ATTR{device}=="0x1572", ATTR{sriov_numvfs}="4"
```

Або специфічно за PCI-адресою:
```udev
ACTION=="add", SUBSYSTEM=="pci", KERNEL=="0000:03:00.0", ATTR{sriov_numvfs}="4"
```

Після створення або зміни правил слід виконати:
```bash
$ sudo udevadm control --reload-rules
$ sudo udevadm trigger
```

## 6. Виклики та обмеження SR-IOV

Незважаючи на високу продуктивність, SR-IOV має низку недоліків:

1. **Втрата Live Migration:**
   Оскільки ВМ має прямий доступ до апаратних регістрів та фізичних адрес пам'яті (через IOMMU), класична «жива» міграція (Live Migration) між фізичними серверами стає надзвичайно складною або неможливою. Щоб перенести ВМ, гіпервізор повинен зберегти стан апаратного пристрою та відновити його на іншому сервері. Хоча існують технології міграції з SR-IOV (через bonding з virtio-net або специфічні розширення вендорів), це значно ускладнює архітектуру.
2. **Апаратна залежність гостьової ОС:**
   Гостьова ОС повинна мати драйвер (VF driver), специфічний для фізичного обладнання (наприклад, драйвер Intel, Mellanox або Broadcom). Це порушує парадигму віртуалізації, де гість бачить лише універсальні віртуальні пристрої (virtio/e1000).
3. **Обмежена гнучкість:**
   Налаштування складних мережевих політик (Firewall, QoS, Open vSwitch) на рівні гіпервізора для трафіку SR-IOV складніше, оскільки трафік проходить повз програмні комутатори ядра (bypass). Для вирішення цієї проблеми виробники випускають карти з технологією **SmartNIC / DPU** та апаратним offload-ом OVS (Hardware-offloaded OVS), що поєднує переваги SR-IOV зі гнучкістю програмних мереж.

## Висновок

SR-IOV — це потужна технологія, що дозволяє максимально утилізувати сучасне високошвидкісне обладнання (10/25/100 Гбіт/с NIC, NVMe) у віртуалізованих середовищах. Шляхом поділу пристрою на Physical Function та Virtual Functions, з безпосереднім доступом (passthrough) останніх до ВМ, досягається продуктивність рівня bare-metal. Водночас системний адміністратор повинен розуміти тонкощі налаштування (через `sriov_numvfs`), керування ресурсами IOMMU та вплив на гнучкість інфраструктури (міграції).
