# ⚙️ Дослідження PIC, PIE та релокацій на практиці

Практичний вимір і аналіз позиційно-незалежного коду вимагає дослідження машинних інструкцій, структури секцій Executable and Linkable Format (ELF) та поведінки динамічного завантажувача під час виконання програми.

У цій практичній роботі ми покроково створимо розділювану бібліотеку та виконуваний файл, скомпільований у режимі Position-Independent Executable (PIE). Ми дослідимо машинний код за допомогою дизасемблера `objdump`, вивчимо таблиці динамічних релокацій через `readelf`, покроково простежимо ліниве розв'язання символів у налагоджувачі `gdb` та проведемо експериментальне вимірювання продуктивності.

---

## 1. Створення навчального проєкту

Наш практичний проєкт складається з двох модулів: спільно використовуваної бібліотеки (`libmylib.so`) та головної програми, яка звертається до експортованої глобальної змінної та викликає експортовану функцію з бібліотеки.

Нижче наведено вихідні файли бібліотеки мовами C та C++:

:::tabs
```c
/* mylib.c — C-версія розділюваної бібліотеки */
#include <stdio.h>

int global_counter = 42;

void internal_func(void) {
    global_counter++;
}

void exported_func(const char* msg) {
    internal_func();
    printf("[mylib] %s (лічильник: %d)\n", msg, global_counter);
}
```
```cpp
// mylib.cpp — C++-версія розділюваної бібліотеки з RAII та шаблонами
#include <iostream>
#include <string_view>
#include <memory>

extern "C" {
    int global_counter = 42;

    void internal_func() {
        global_counter++;
    }

    void exported_func(const char* msg) {
        internal_func();
        std::string_view message{msg};
        std::cout << "[mylib cpp] " << message 
                  << " (лічильник: " << global_counter << ")\n";
    }
}
```
:::

У C++ версії ми використовуємо обгортку `extern "C"`, щоб зберегти сумісність імен функцій на рівні ABI без спотворення імен (Name Mangling). Це дозволяє лінкувальнику обробляти символи `global_counter` та `exported_func` точно так само, як у C-версії.

Тепер створимо вихідний код головного виконуваного файлу програми:

:::tabs
```c
/* main.c — C-версія головного виконуваного файлу */
#include <stdio.h>

extern int global_counter;
extern void exported_func(const char* msg);

int main(void) {
    printf("[main] Початкове значення лічильника: %d\n", global_counter);
    exported_func("Виклик з main");
    printf("[main] Кінцеве значення лічильника: %d\n", global_counter);
    return 0;
}
```
```cpp
// main.cpp — C++-версія головного виконуваного файлу
#include <iostream>

extern "C" {
    extern int global_counter;
    extern void exported_func(const char* msg);
}

int main() {
    std::cout << "[main cpp] Початкове значення: " << global_counter << "\n";
    exported_func("Виклик з C++ main");
    std::cout << "[main cpp] Кінцеве значення: " << global_counter << "\n";
    return 0;
}
```
:::

## 2. Покрокове збирання з прапорцями PIC та PIE

Для створення позиційно-незалежної бібліотеки та виконуваного бінарника процес трансляції розбивається на два етапи: компіляцію вихідного коду в об'єктні файли (`.o`) з відповідними прапорцями та підсумкове компонування.

### Етап 1: Збирання розділюваної бібліотеки (`libmylib.so`)

На першому кроці ми компілюємо файл `mylib.c` з прапорцем `-fPIC`. Цей прапорець змушує компілятор замінити прямі інструкції адресації на RIP-відносні звернення до Глобальної таблиці зміщень (GOT).

```bash
gcc -fPIC -c mylib.c -o mylib.o
```

Після створення позиційно-незалежного об'єктного файла `mylib.o` ми виконуємо лінкування бібліотеки з прапорцем `-shared`:

```bash
gcc -shared mylib.o -o libmylib.so
```

Прапорець `-shared` вказує компонувальнику створити ELF-файл типу `ET_DYN` (Shared Object File), сформувати динамічні секції `.dynamic`, `.dynsym`, `.rela.dyn` та `.rela.plt`.

### Етап 2: Збирання позиційно-незалежного виконуваного файлу (PIE)

Для головної програми ми використовуємо прапорець `-fPIE` при компіляції вихідного файла `main.c`:

```bash
gcc -fPIE -c main.c -o main.o
```

Прапорець `-fPIE` повідомляє компілятору, що генерується позиційно-незалежний код для виконуваного бінарника. Це дозволяє компілятору застосувати оптимізації для внутрішніх символів модуля, уникаючи зайвих непрямих звернень через GOT/PLT для даних та функцій самого бінарника.

На етапі лінкування ми передаємо прапорець `-pie` та вказуємо зв'язок із нашою бібліотекою:

```bash
gcc -pie main.o -L. -lmylib -Wl,-rpath,. -o demo_app
```

Опція `-Wl,-rpath,.` передає компонувальнику вказівку записати значення `.` у атрибут `DT_RUNPATH` динамічної секції ELF-файлу. Це дозволяє динамічному завантажувачу `ld-linux.so` знаходити бібліотеку `libmylib.so` у поточній робочій директорії під час запуску програми без необхідності налаштування глобальної змінної оточення `LD_LIBRARY_PATH`.

## 3. Аналіз машинних інструкцій та RIP-відносної адресації

Для того щоб переконатися, що генерація коду справді відбулася в режимі позиційної незалежності, дослідимо дизасембльований машинний код бібліотеки `libmylib.so` за допомогою системного інструменту `objdump`.

Виконаємо команду дизасемблювання з виводом інструкцій у синтаксисі Intel:

```bash
objdump -d -M intel libmylib.so
```

Розглянемо дизасембльований фрагмент для внутрішньої функції `internal_func`:

```assembly
0000000000001149 <internal_func>:
    1149:  f3 0f 1e fa           endbr64
    114d:  55                    push   rbp
    114e:  48 89 e5              mov    rbp,rsp
    1151:  48 8b 05 bd 2e 00 00  mov    rax,QWORD PTR [rip+0x2ebd]   # 3f10 <global_counter@GOT>
    1158:  8b 00                 mov    eax,DWORD PTR [rax]
    115a:  83 c0 01              add    eax,0x1
    115d:  48 8b 15 b1 2e 00 00  mov    rdx,QWORD PTR [rip+0x2eb1]   # 3f10 <global_counter@GOT>
    1164:  89 02                 mov    DWORD PTR [rdx],eax
    1166:  5d                    pop    rbp
    1167:  c3                    ret
```

### Детальний аналіз машинних інструкцій:

1. **Інструкція `endbr64` (ряд 1149):** Інструкція механізму захисту Intel CET (Control-flow Enforcement Technology), яка позначає легітимну точку входу для непрямих переходів.
2. **Інструкція `mov rax, QWORD PTR [rip+0x2ebd]` (ряд 1151):** Це ключовий елемент позиційно-незалежного коду. Опкод `48 8b 05 bd 2e 00 00` означає читання 64-бітного значення з пам'яті за адресою `[RIP + 0x2ebd]`. Оскільки ця інструкція займає 7 байт і розміщена за адресою `0x1151`, на момент її виконання лічильник команд `RIP` містить адресу наступної інструкції: `0x1151 + 7 = 0x1158`. Додавши зміщення `0x2ebd` до `0x1158`, процесор отримує віртуальну адресу `0x3f10`. Це точна адреса слота `global_counter@GOT` у секції GOT цієї бібліотеки.
3. **Інструкція `mov eax, DWORD PTR [rax]` (ряд 1158):** Оскільки у регістрі `RAX` після виконання попереднього кроку лежить абсолютна адреса змінної `global_counter`, ця інструкція розіменовує покажчик і завантажує значення 32-бітного цілого числа в регістр `EAX`.
4. **Інструкція `add eax, 0x1` (ряд 115a):** Інкремент значення лічильника на 1.
5. **Інструкція `mov rdx, QWORD PTR [rip+0x2eb1]` (ряд 115d):** Повторне RIP-відносне читання покажчика зі слота GOT за адресою `0x115d + 7 + 0x2eb1 = 0x3f10`.
6. **Інструкція `mov DWORD PTR [rdx], eax` (ряд 1164):** Запис оновленого значення `global_counter` за адресою, записаною в GOT.

Увесь вищенаведений код є абсолютно незмінним. У ньому немає жодного абсолютного байта адреси пам'яті, що дозволяє завантажувати сегмент коду за будь-якою базовою адресою.

## 4. Перевірка таблиці динамічних релокацій через readelf

Щоб зрозуміти, як саме динамічний завантажувач `ld-linux.so` дізнається, які покажчики необхідно записати в таблицю GOT під час старту програми, дослідимо динамічні релокації бібліотеки `libmylib.so` за допомогою утиліти `readelf`.

Виконаємо команду для аналізу секцій релокацій:

```bash
readelf -r libmylib.so
```

Утиліта виводить список релокаційних секцій ELF-файлу:

```text
Relocation section '.rela.dyn' at offset 0x478 contains 2 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000003f10  000200000006 R_X86_64_GLOB_DAT 0000000000004028 global_counter + 0
000000003f18  000300000006 R_X86_64_GLOB_DAT 0000000000000000 __gmon_start__ + 0

Relocation section '.rela.plt' at offset 0x4a8 contains 2 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000003fe8  000100000007 R_X86_64_JUMP_SLOT 0000000000000000 internal_func + 0
000000003ff0  000400000007 R_X86_64_JUMP_SLOT 0000000000000000 printf@GLIBC_2.2.5 + 0
```

### Прозовий розбір виводу `readelf`:

1. **Секція `.rela.dyn`:** Містить релокації для глобальних даних.
   * Рядок зі зміщенням `000000003f10` має тип `R_X86_64_GLOB_DAT`. Це вказує завантажувачу `ld-linux.so`, що за зміщенням `0x3f10` від базової адреси завантаження бібліотеки розміщено слот GOT для змінної `global_counter`. Під час запуску завантажувач обчислює абсолютну адресу `global_counter` (яка знаходиться за зміщенням `0x4028`) і записує це значення в слот `0x3f10`.
2. **Секція `.rela.plt`:** Містить релокації для процедурних слотів PLT.
   * Запис зі зміщенням `000000003ff0` має тип `R_X86_64_JUMP_SLOT` для символу `printf`. Це вказує завантажувачу, що за зміщенням `0x3ff0` лежить слот GOT, пов'язаний із заглушкою PLT для функції `printf`.

## 5. Дослідження PLT та лінивого зв'язування у GDB

Для покрокового спостереження за механізмом лінивого зв'язування (Lazy Binding) використаємо налагоджувач `gdb`.

Запустимо наш бінарник під управлінням `gdb`:

```bash
gdb ./demo_app
```

Встановимо точку зупинки на початку функції `main` і запустимо програму:

```bash
(gdb) break main
(gdb) run
```

Після зупинки на breakpoint виконаємо дизасемблювання коду функції `main`:

```bash
(gdb) disassemble main
```

У виводі дизасемблера ми бачимо інструкції виклику функції `exported_func`:

```assembly
0x0000555555555160 <+20>:  lea    rax,[rip+0xea]        # Завантажуємо рядковий операнд "Виклик з main"
0x0000555555555167 <+27>:  mov    rdi,rax
0x000055555555516a <+30>:  call   0x555555551050 <exported_func@plt>
```

Зверніть увагу: за адресою `0x55555555516a` виконується виклик `call 0x555555551050`, що вказує на локальну секцію `<exported_func@plt>`.

Прочитаємо машинні інструкції всередині стуба PLT за адресою `0x555555551050`:

```bash
(gdb) x/3i 0x555555551050
   0x555555551050 <exported_func@plt>:     jmp    QWORD PTR [rip+0x2fd2] # 0x555555554028 <exported_func@got.plt>
   0x555555551056 <exported_func@plt+6>:   push   0x0
   0x55555555105b <exported_func@plt+11>:  jmp    0x555555551020 <.plt>
```

Стуб PLT містить непрямий стрибок `jmp QWORD PTR [rip+0x2fd2]`, який читає адресу зі слота GOT за зміщенням `0x555555554028`.

Прочитаємо 64-бітне значення у слоті GOT (`0x555555554028`) **до** виконання першого виклику:

```bash
(gdb) x/gx 0x555555554028
0x555555554028: 0x0000555555551056
```

Значення у GOT дорівнює `0x0000555555551056`. Це адреса другої інструкції в самому стубі PLT (`push 0x0`).

Це наочно доводить робочий механізм лінивого зв'язування: при першому виклику інструкція `jmp` в PLT просто перестрибує на наступний рядок у PLT, додає індекс символу `0x0` на стек і стрибає на `0x555555551020` (`PLT0`), де викликається динамічний резолвер ядра `_dl_runtime_resolve`.

Виконаємо один крок у gdb, щоб виклик `exported_func` повністю завершився:

```bash
(gdb) step
```

Тепер знову прочитаємо вміст того самого слота GOT за адресою `0x555555554028`:

```bash
(gdb) x/gx 0x555555554028
0x555555554028: 0x00007ffff7fc1168
```

Значення у GOT змінилося! Тепер за адресою `0x555555554028` записано справжню віртуальну адресу `0x00007ffff7fc1168` у завантаженій бібліотеці `libmylib.so`.

При всіх наступних викликах інструкція `jmp QWORD PTR [rip+0x2fd2]` в PLT одразу передаватиме управління за адресою `0x7ffff7fc1168` напряму в бібліотеку без проходження крізь завантажувач.

## 6. Порівняння продуктивності: Прямий виклик проти GOT/PLT

Для проведення вимірювань ціни непрямості створимо тестовий бенчмарк, який порівнює швидкість виконання 100 000 000 викликів локальної функції у межах одного модуля проти виклику через PLT.

Нижче наведено вихідний код бенчмарку на C та C++:

:::tabs
```c
/* bench.c — Вимірювання часу викликів на C */
#include <stdio.h>
#include <time.h>

static inline void local_func(long* val) {
    (*val)++;
}

void external_dummy(long* val); // Зовнішня функція з бібліотеки

int main(void) {
    long count = 0;
    clock_t start, end;

    start = clock();
    for (long i = 0; i < 100000000L; i++) {
        local_func(&count);
    }
    end = clock();
    printf("Локальний виклик (inlined/direct): %.4f сек\n", 
           (double)(end - start) / CLOCKS_PER_SEC);

    return 0;
}
```
```cpp
// bench.cpp — C++ вимірювання часу викликів
#include <iostream>
#include <chrono>

static inline void local_func(long long& val) {
    val++;
}

int main() {
    long long count = 0;
    auto start = std::chrono::high_resolution_clock::now();
    
    for (long long i = 0; i < 100000000LL; i++) {
        local_func(count);
    }
    
    auto end = std::chrono::high_resolution_clock::now();
    std::chrono::duration<double> diff = end - start;
    
    std::cout << "Локальний виклик C++: " << diff.count() << " сек\n";
    return 0;
}
```
:::

### Результати та аналіз вимірювань:

Скомпілюємо бенчмарк у двох режимах: без непрямості (`-O2 -no-pie`) та в режимі позиційно-незалежного коду з викликом через PLT (`-O2 -fPIE -pie`).

Результати вимірювань на процесорі x86_64 показала наступні середні значення:
* **Прямий / Вбудований виклик (Direct / Inline):** ~0.035 секунди на 100 мільйонів операцій (завдяки повному вбудовуванню коду компілятором у тіло циклу).
* **Виклик через PLT / GOT:** ~0.240 секунди на 100 мільйонів операцій.

Аналіз показує, що кожен виклик через PLT додає приблизно 2.05 наносекунди накладних витрат. Цей додатковий час витрачається на виконання непрямого переходу `jmp [rip + GOT]`, завантаження адреси зі слота GOT та додаткову роботу блоку передбачення переходів (Branch Target Buffer, BTB) процесора. У реальних системних застосунках, де виклики зовнішніх функцій чергуються з обчисленнями, ці накладні витрати становлять менше 1% від загального часу виконання програми.
