# 📋 Інтерфейс компілятора, лінкувальника та типи релокацій ELF

Цей довідник містить повну специфікацію опцій компіляції GCC та Clang, прапорців компонувальника `ld`, а також системну таблицю та розширений опис типів релокацій Executable and Linkable Format (ELF) для архітектури x86_64. 

Компілятори та динамічні завантажувачі покладаються на чітко визначений інтерфейс взаємодії. Опції компілятора керують генерацією машинних інструкцій на рівні окремих файлів вихідного коду, прапорці компонувальника визначають результуючу структуру сегментів ELF-файлу, а типи релокацій описують точні математичні операції, які динамічний завантажувач `ld-linux.so` має виконати в пам'яті під час запуску програми.

## 1. Прапорці компілятора (GCC / Clang)

Опції компілятора керують тим, чи генерує компілятор прямі інструкції адресації, чи використовує непрямі звернення через таблицю GOT та трампліни PLT.

| Прапорець | Призначення | Область застосування | Вплив на генерацію коду |
| :--- | :--- | :--- | :--- |
| `-fPIC` | Генерація позиційно-незалежного коду великого розміру. | Розділювані бібліотеки (`.so`). | Підтримує неограничений розмір таблиці GOT (використовує 32-бітні зміщення в x86_64). |
| `-fpic` | Генерація позиційно-незалежного коду з малим розміром GOT. | Розділювані бібліотеки (`.so`). | Використовує коротші інструкції на архітектурах із обмеженим розміром таблиці GOT. |
| `-fPIE` | Позиційно-незалежний код для виконуваного бінарника. | Головні бінарники (Executables). | Дозволяє оптимізувати локальні звернення, уникаючи GOT/PLT для внутрішніх символів. |
| `-fpie` | Оптимізована версія `-fPIE` для малих таблиць GOT. | Головні бінарники (Executables). | Використовує малі зміщення GOT на сумісних архітектурах. |
| `-no-pie` | Вимкнення генерації позиційно-незалежного коду. | Системні бінарники, bootloaders. | Генерує фіксовані абсолютні адреси для коду та даних. |
| `-fno-plt` | Прямий виклик функцій через GOT без використання PLT. | Бінарники та бібліотеки. | Замінює `call func@PLT` на `call [rip + func@GOTPCREL]`, прибираючи трамплін PLT. |
| `-fno-semantic-interposition` | Заборона перевизначення внутрішніх символів. | Розділювані бібліотеки (`.so`). | Дозволяє компілятору оптимізувати виклики всередині модуля так само, як у PIE. |
| `-fvisibility=hidden` | Приховування символів за замовчуванням. | Спільні бібліотеки (`.so`). | Дозволяє прямі RIP-відносні виклики всередині модуля, минаючи PLT. |
| `-fvisibility=default` | Експорт усіх публічних символів. | Спільні бібліотеки (`.so`). | Усі символи додаються до `.dynsym` і можуть бути перевизначені (Symbol Interposition). |

### Детальний прозовий опис прапорців компіляції

#### Прапорці `-fPIC` та `-fpic`
Прапорець `-fPIC` (Position-Independent Code) наказує компілятору генерувати машинний код, який не містить жодних абсолютних адрес коду чи даних. Усі звернення до глобальних змінних та функцій транслюються в RIP-відносне читання покажчиків із Глобальної таблиці зміщень (Global Offset Table, GOT). 

Відмінність між `-fpic` (нижній регістр) та `-fPIC` (верхній регістр) є історичною й залежить від цільової архітектури процесора. На таких архітектурах, як SPARC, MIPS або IBM System/390, інструкції адресації з коротким операндом обмежені розміром таблиці GOT (наприклад, не більше 8192 слотів або 16 КБ для SPARC). Прапорець `-fpic` генерує коротші й швидші інструкції, але якщо бібліотека перевищує ліміт слотів GOT, компонувальник видає помилку. Прапорець `-fPIC` використовує розширені інструкції адресації, що дозволяє мати таблицю GOT необмеженого розміру. На сучасній 64-бітній архітектурі x86_64 обидва прапорці `-fpic` та `-fPIC` обробляються компілятором GCC однаково й генерують 32-бітні відносні зміщення `[rip + offset]`.

#### Прапорці `-fPIE` та `-fpie`
Прапорці `-fPIE` (Position-Independent Executable) використовуються при компіляції вихідних файлів, призначених для збирання головного виконуваного бінарника програми, а не розділюваної бібліотеки. 

Головна відмінність коду, згенерованого з `-fPIE`, від коду з `-fPIC` полягає у відсутності **перевизначення символів (Symbol Interposition)**. Компілятор знає, що головний виконуваний модуль є вершиною ієрархії виконання процесу. Жодна інша бібліотека не може перевизначити глобальну змінну чи функцію, оголошену в самому головному бінарнику (якщо тільки не використано спеціальні прапорці лінкувальника). Тому при компіляції з `-fPIE` компілятор застосовує суттєві оптимізації для внутрішніх глобальних даних бінарника: замість читання покажчика з GOT він генерує безпосередню RIP-відносну інструкцію `mov rax, [rip + offset]` напряму до секції даних `.data` або `.bss`.

#### Прапорець `-fno-plt`
Прапорець `-fno-plt` скасовує використання трамплінів PLT для викликів зовнішніх функцій. Замість генерування відносного виклику `call func@PLT`, який потім перестрибує через інструкцію `jmp [rip + GOT]`, компілятор згенерує один прямий непрямий виклик через покажчик у GOT: `call QWORD PTR [rip + func@GOTPCREL]`. Це зменшує розмір коду та прискорює виконання за рахунок видалення проміжного стрибка, однак вимагає, щоб усі адреси функцій у GOT були розв'язані на етапі старту програми (тобто вимикає ліниве зв'язування).

#### Прапорець `-fno-semantic-interposition`
За замовчуванням у C/C++ при збиранні динамічної бібліотеки з `-fPIC` компілятор припускає, що будь-яка глобальна функція може бути перевизначена головним виконуваним файлом чи іншою бібліотекою через `LD_PRELOAD`. Це заважає компілятору виконувати інлайнінг (inlining) та міжпроцедурну оптимізацію всередині бібліотеки. Прапорець `-fno-semantic-interposition` дозволяє компілятору припустити, що внутрішні виклики функцій у межах цієї самої бібліотеки завжди звертатимуться до її власних реалізацій, що дозволяє виконувати інлайнінг та прямі виклики.

#### Прапорець `-no-pie`
Прапорець `-no-pie` інструктує компілятор та лінкувальник згенерувати звичайний позиційно-залежний виконуваний файл (тип ELF `ET_EXEC`). У такому бінарнику всі інструкції виклику функцій та звернення до даних закодовані у вигляді фіксованих 32-бітних абсолютних адрес у віртуальному просторі (за замовчуванням починаючи з `0x00400000` на x86_64). Застосування `-no-pie` унеможливлює використання повного механізму ASLR для сегмента коду програми.

#### Прапорці керування видимістю символів (`-fvisibility`)
Прапорець `-fvisibility=hidden` змінює видимість усіх функцій та змінних у вихідному коді з публічної (`default`) на приховуну (`hidden`). У розділюваних бібліотеках це дозволяє компілятору припустити, що приховані символи не будуть доступні ззовні `.so` файлу. Завдяки цьому компілятор повністю оминає використання PLT та GOT для внутрішніх викликів між функціями бібліотеки, генеруючи прямі відносні інструкції `call`, що відчутно зменшує розмір бінарника та підвищує продуктивність.

## 2. Опції компонувальника (Linker Flags)

Компонувальник `ld` приймає прапорці для формування підсумкових секцій та сегментів ELF-файлу. При виклику через запускний інтерфейс `gcc` або `clang` прапорці лінкувальника передаються за допомогою ключа `-Wl,`.

| Прапорець лінкувальника | Внутрішній прапорець `ld` | Системний опис і дія на бінарник |
| :--- | :--- | :--- |
| `-pie` | `-z pie` | Створення позиційно-незалежного бінарника ELF (тип `ET_DYN`). |
| `-no-pie` | `-no-pie` | Створення традиційного абсолютного бінарника ELF (тип `ET_EXEC`). |
| `-Wl,-z,now` | `-z now` | Вмикає негайне розв'язання символів (Immediate Binding) при старті процесу. |
| `-Wl,-z,lazy` | `-z lazy` | Відновлює ліниве зв'язування викликів функцій через PLT при старті. |
| `-Wl,-z,relro` | `-z relro` | Позначення внутрішніх таблиць лінкувальника як Read-Only після завантаження. |
| `-Wl,-z,relro,-z,now` | Full RELRO | Повний захист GOT: розв'язання всіх функцій при старті й блокування запису в GOT. |
| `-Wl,-Bsymbolic` | `-Bsymbolic` | Прив'язка викликів глобальних функцій усередині бібліотеки до власних визначень. |
| `-Wl,-Bsymbolic-functions` | `-Bsymbolic-functions` | Прив'язка викликів функцій усередині бібліотеки, залишаючи змінні відкритими. |
| `-Wl,--no-undefined` | `--no-undefined` | Заборона наявности нерозв'язаних символів під час створення бібліотеки `.so`. |

### Повний аналіз режимів захисту RELRO

Механізм **RELRO (ReLocation Read-Only)** розроблений для захисту структури таблиці GOT від хакерських атак типу "перезапис GOT" (GOT overwrite vulnerability). Існує два режими RELRO:

1. **Partial RELRO (`-Wl,-z,relro`):**
   Під час лінкування компонувальник групує секції ELF-модуля так, що таблиці `.dynamic`, `.got` та інші службові дані розташовуються безпосередньо перед секцією даних `.data`. Під час запуску програми динамічний завантажувач розв'язує символи для даних і викликає системний виклик `mprotect(PROT_READ)`, роблячи секцію `.got` доступною лише для читання. Однак секція `.got.plt` (яка містить покажчики для лінивого зв'язування функцій) залишається доступною для запису протягом усього часу життя процесу.

2. **Full RELRO (`-Wl,-z,relro,-z,now`):**
   Вимагає прапорця `-z now`, який примушує динамічний завантажувач розв'язати абсолютно всі покажчики функцій у таблиці GOT під час ініціалізації процесу до передачі управління функції `main()`. Після завершення розв'язання динамічний завантажувач позначає **всю таблицю GOT** (`.got` та `.got.plt`) як Read-Only через `mprotect(..., PROT_READ)`. Жодна інструкція програми під час виконання більше не має права записувати в GOT, що повністю блокує можливі спроби перезапису покажчиків функцій.

## 3. Специфікація типів релокацій ELF для x86_64

Під час збирання об'єктних файлів (`.o`) компілятор залишає записи релокацій у секціях `.rela.text`, `.rela.data`, `.rela.dyn` та `.rela.plt`. Динамічний завантажувач `ld-linux.so` обробляє ці записи при виконанні програми.

У 64-бітній системі System V AMD64 ABI кожен запис релокації описується структурою `Elf64_Rela`:

:::tabs
```c
/* Elf64_Rela з системного заголовка <elf.h> */
typedef struct {
    Elf64_Addr   r_offset; /* Віртуальна адреса або зміщення для запису */
    Elf64_Xword  r_info;   /* Індекс символу в таблиці та тип релокації */
    Elf64_Sxword r_addend; /* Явне додаткове зміщення (addend) */
} Elf64_Rela;
```
```cpp
// Ідіоматичне вираження Elf64_Rela у C++20 із системними типами <cstdint>
#include <cstdint>

struct Elf64_Rela {
    std::uint64_t r_offset; // Віртуальна адреса або зміщення для запису
    std::uint64_t r_info;   // Індекс символу в таблиці та тип релокації
    std::int64_t  r_addend; // Явне додаткове зміщення (addend)
};
```
:::

Для маніпуляцій з полем `r_info` використовуються макроси `ELF64_R_SYM(info)` (отримання індексу символу в таблиці `.dynsym`) та `ELF64_R_TYPE(info)` (отримання типу релокацій).

### Позначення у формулах обчислення:
* **`A` (Addend):** Значення поля `r_addend` з відповідної структури `Elf64_Rela`.
* **`B` (Base):** Фізична базова адреса у віртуальній пам'яті, за якою динамічний завантажувач відобразив ELF-модуль.
* **`G` (GOT offset):** Зміщення від початку таблиці GOT до слота даного символу.
* **`GOT`:** Віртуальна адреса початку Глобальної таблиці зміщень (GOT).
* **`P` (Place):** Віртуальна адреса місця у пам'яті, що підлягає модифікації (обчислюється як `B + r_offset`).
* **`S` (Symbol):** Фактична віртуальна адреса розв'язаного символу у пам'яті процесу.

### Системна таблиця типів релокацій x86_64

| Назва релокації | Код (Hex) | Формула обчислення | Опис механізму дії динамічного завантажувача |
| :--- | :--- | :--- | :--- |
| `R_X86_64_RELATIVE` | `0x08` | `B + A` | **Базова внутрішня релокація:** Динамічний завантажувач додає базову адресу завантаження модуля `B` до зміщення `A` і записує результат за адресою `P`. Застосовується для внутрішніх покажчиків у PIE та `.so`. |
| `R_X86_64_GLOB_DAT` | `0x06` | `S` | **Слот даних GOT:** Динамічний завантажувач знаходить адресу глобального символу `S` і записує її у відповідний слот GOT. |
| `R_X86_64_JUMP_SLOT` | `0x07` | `S` | **Слот функцій GOT/PLT:** Динамічний завантажувач записує адресу функції `S` у слот GOT. Використовується для лінивого зв'язування викликів PLT. |
| `R_X86_64_PC32` | `0x02` | `S + A - P` | **32-бітна відносна адресація:** Обчислює 32-бітну відносну відстань від адреси інструкції `P` до символу `S`. Використовується для викликів `call` у межах модуля. |
| `R_X86_64_GOTPCREL` | `0x09` | `G + GOT + A - P` | **Відносна адреса слота GOT:** Обчислює відносну відстань від поточної інструкції `P` до слота в GOT для даного символу. База інструкції `mov rax, [rip + offset]`. |
| `R_X86_64_GOTPCRELX` | `0x29` | `G + GOT + A - P` | **Релаксована адреса GOT:** Розширена версія `R_X86_64_GOTPCREL`, яка дозволяє компонувальнику оптимізувати інструкцію `mov rax, [rip + GOT]` у `lea rax, [rip + symbol]`, якщо символ виявився локальним. |
| `R_X86_64_REX_GOTPCRELX`| `0x2a` | `G + GOT + A - P` | Аналогічно `R_X86_64_GOTPCRELX` для інструкцій з REX-префіксом. |
| `R_X86_64_64` | `0x01` | `S + A` | **Абсолютна 64-бітна адреса:** Записує пряму 64-бітну адресу символу `S`. Не є позиційно-незалежною (викликає TEXTREL при використанні у коді!). |
| `R_X86_64_32` | `0x0a` | `S + A` | **Абсолютна 32-бітна адреса:** Пряма 32-бітна адреса з беззнаковим розширенням. Призводить до помилки компонувальника при збиранні PIE чи `.so`. |
| `R_X86_64_32S` | `0x0b` | `S + A` | **Абсолютна 32-бітна адреса зі знаком:** Пряма 32-бітна адреса зі знаковим розширенням. |

### Детальний опис ключових релокацій

#### `R_X86_64_RELATIVE`
Цей тип релокації є найпоширенішим у позиційно-незалежних виконуваних файлах (PIE) та розділюваних бібліотеках. Він використовується для налаштування покажчиків, які вказують на дані або функції всередині того самого модуля. Оскільки модуль завантажується за довільною базовою адресою `B`, динамічному завантажувачу не потрібно шукати символ у таблиці `.dynsym`. Він просто бере записане у файлі зміщення `A` (Addend) і додає до нього базову адресу завантаження `B`.

#### `R_X86_64_GLOB_DAT`
Використовується для ініціалізації слотів у таблиці GOT, які відповідають глобальним змінним. Під час завантаження модуля `ld-linux.so` бере ім'я символу з таблиці `.dynsym`, шукає його віртуальну адресу `S` у всіх завантажених об'єктах процесу й записує `S` у слот GOT.

#### `R_X86_64_JUMP_SLOT`
Використовується для ініціалізації слотів у таблиці GOT, пов'язаних із функціями в PLT. У режимі лінивого зв'язування (Lazy Binding) завантажувач залишає в цьому слоті початковий покажчик на реструктуризаційний стуб у PLT, і лише при першому виклику функції замінює його на абсолютну адресу `S`. У режимі Full RELRO або при виклику з `BIND_NOW` всі релокації `R_X86_64_JUMP_SLOT` виконуються одразу під час старту програми.

#### `R_X86_64_GOTPCREL` та `R_X86_64_GOTPCRELX`
Ці типи релокацій створюються компілятором під час обробки вихідного коду в об'єктні файли `.o`. Вони вказують статичному компонувальнику `ld` обчислити відносну відстань між машинною інструкцією в `.text` та відповідним слотом у таблиці GOT. Сучасні компонувальники використовують варіанти `GOTPCRELX` для проведення оптимізацій (Linker Relaxation): якщо лінкувальник бачить, що символ є внутрішнім для бінарника і не вимагає GOT, він "на льоту" трансформує непряму інструкцію читання з пам'яті `mov rax, QWORD PTR [rip + GOT]` у пряму обчислювальний інструкцію `lea rax, [rip + symbol]`.
