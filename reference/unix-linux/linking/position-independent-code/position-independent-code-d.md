# Позиційно-незалежний код: PIC, PIE й ціна непрямості

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Коли ми розробляємо програми мовами C або C++, одним із найскладніших етапів створення виконуваного файлу є процес лінкування (компонування). У ранніх операційних системах пам'ять для застосунків виділялася в жорстко заданих регіонах, і код містив абсолютні адреси для викликів функцій та звернень до глобальних змінних. Однак з розвитком багатозадачності, спільно використовуваних бібліотек і вимог до кібербезпеки виникла потреба в коді, який можна завантажувати й виконувати з будь-якої адреси в пам'яті. 

Ця концепція отримала назву **Позиційно-незалежний код (Position-Independent Code, PIC)**. Похідна від неї технологія для виконуваних файлів називається **Позиційно-незалежний виконуваний файл (Position-Independent Executable, PIE)**.

У цій статті ми детально розберемо, як саме працюють PIC та PIE, яку роль відіграє RIP-відносна адресація в архітектурі x86_64, як працюють таблиці GOT і PLT, як ця технологія пов'язана з ASLR та якою є ціна цієї непрямості з погляду продуктивності.

---

## 1. Вступ. Чому абсолютні адреси стали проблемою

У традиційних операційних системах, що не використовували віртуальну пам'ять, або в ранніх реалізаціях застосунків під x86, компонувальник (linker) під час створення програми фіксував адреси всіх функцій і змінних. Коли процесор виконував інструкцію виклику функції (наприклад, `call 0x401000`), він очікував, що код цієї функції завжди буде знаходитися саме за адресою `0x401000`.

Цей підхід мав кілька суттєвих недоліків:

1. **Спільно використовувані бібліотеки (Shared Libraries):** Коли кілька програм використовують одну й ту саму бібліотеку (наприклад, `libc`), операційна система намагається завантажити цю бібліотеку в пам'ять лише один раз, а потім відобразити (map) її у віртуальний адресний простір кожного процесу. Якщо код бібліотеки містить абсолютні адреси, ОС довелося б завантажувати бібліотеку за однією і тією ж адресою для всіх процесів, що призводить до конфліктів адресного простору, або ж модифікувати код (relocate) під час завантаження для кожного процесу окремо, що зводить нанівець перевагу спільного використання пам'яті (пам'ять стає унікальною для кожного процесу і не може бути розшарена).
2. **Безпека:** Якщо адреси всіх функцій і даних відомі заздалегідь, зловмисникам набагато легше писати експлойти (наприклад, атаки типу Return-Oriented Programming, ROP). Вони можуть жорстко закодувати адреси функцій (як-от `system()`) у своїх шкідливих сценаріях.

Щоб розв'язати ці проблеми, було винайдено механізми, які дозволяють виконувати той самий машинний код незалежно від того, за якою базовою адресою він завантажений у віртуальну пам'ять.

## 2. Розділення понять: PIC, PIE та їх роль у сучасних ОС

Терміни PIC і PIE часто плутають або використовують як синоніми, але між ними є важлива різниця в контексті компіляції та лінкування.

### Position-Independent Code (PIC)
**PIC (Позиційно-незалежний код)** — це загальний термін для машинного коду, який виконується коректно незалежно від того, де він розміщений у пам'яті. У світі Unix і Linux прапорець компілятора `-fPIC` використовується насамперед для створення **спільно використовуваних об'єктів (shared objects, `.so`)**, тобто динамічних бібліотек.

Код, скомпільований з `-fPIC`, уникає абсолютних посилань не лише на глобальні змінні, але й на функції. Усі звернення до даних та виклики зовнішніх функцій здійснюються через спеціальні таблиці непрямості.

### Position-Independent Executable (PIE)
**PIE (Позиційно-незалежний виконуваний файл)** — це застосунок (головний виконуваний файл програми, а не бібліотека), який скомпільовано повністю з позиційно-незалежного коду. Прапорець `-fPIE` вказує компілятору, що генерується код не для динамічної бібліотеки, а для головного модуля програми. 

Різниця між `-fPIC` і `-fPIE` полягає в оптимізаціях. Коли компілятор генерує PIE, він знає, що певні глобальні символи (наприклад, статичні змінні або функції самого застосунку) ніколи не будуть "перекриті" (overridden) іншими бібліотеками, тому звернення до них можна оптимізувати, обійшовши таблиці непрямості. Для `.so` бібліотек компілятор такої гарантії не має (ситуація відома як symbol interposition).

## 3. Базовий принцип позиційної незалежності

Як можна звернутися до змінної чи функції, якщо ми не знаємо її адреси? Відповідь полягає у **відносній адресації**.

Замість того, щоб вказувати: "Змінна X лежить за адресою 0x8048000", компілятор генерує інструкції, що означають: "Змінна X знаходиться на відстані 0x1200 байт вперед від поточної інструкції".

Оскільки код і дані в одному модулі (виконуваному файлі або бібліотеці) компілюються і лінкуються як єдине ціле, відстань (зміщення) між будь-якою інструкцією та будь-якою локальною змінною чи функцією всередині цього модуля завжди є константою, незалежно від того, за якою адресою цей модуль завантажено.

В архітектурі x86 (32-біт) це було досить складно реалізувати, оскільки процесор не мав вбудованої підтримки адресації відносно лічильника команд (Instruction Pointer, EIP) для даних. Компіляторам доводилося використовувати трюки, наприклад, виклик спеціальної функції-трампліна для отримання поточного EIP в регістр.

## 4. RIP-відносна адресація в архітектурі x86_64

З переходом на 64-бітну архітектуру (x86_64 / AMD64) розробники процесорів врахували потребу в PIC і додали безпосередню апаратну підтримку — **RIP-відносну адресацію (RIP-relative addressing)**.

Регістр `RIP` (Instruction Pointer) містить адресу наступної інструкції, яка має бути виконана. У x86_64 процесор може завантажувати дані з пам'яті, використовуючи адресу, обчислену як `RIP + зміщення (офсет)`. Зміщення кодується в самій інструкції і може бути 32-бітним числом зі знаком (від -2 ГБ до +2 ГБ).

Приклад машинної інструкції:
```assembly
mov eax, DWORD PTR [rip+0x2000]
```
Якщо ця інструкція знаходиться за адресою `0x401000` і має довжину 6 байт, то `RIP` у момент її виконання дорівнює `0x401006`. Процесор додасть `0x2000` до `0x401006`, отримає `0x403006` і прочитає дані з цієї адреси. Якщо всю програму перемістити на іншу базову адресу, значення `RIP` зміниться відповідно, але зміщення залишиться незмінним, і дані будуть знайдені коректно.

Це робить локальні виклики та звернення до локальних статичних даних вкрай швидкими і природно позиційно-незалежними. Але що робити зі зверненнями до функцій або змінних, що знаходяться в *інших* динамічних бібліотеках? Їхня відстань від нашого коду невідома під час компіляції. Тут на допомогу приходять GOT та PLT.

## 5. Глобальна таблиця зміщень (GOT)

**Global Offset Table (GOT)** — це структура даних, що створюється компонувальником і розташовується в сегменті даних (який є доступним для запису) кожного модуля.

Замість того, щоб вшивати абсолютні адреси зовнішніх змінних чи функцій у сегмент коду (який у пам'яті має права тільки на читання й виконання і шариться між процесами), код використовує RIP-відносну адресацію для звернення до певного слоту (елемента) всередині GOT.

Коли програма завантажується в пам'ять, динамічний лінкувальник (dynamic linker/loader, наприклад `ld-linux.so`) знаходить усі необхідні бібліотеки, обчислює їхні фактичні адреси в пам'яті й записує ці правильні абсолютні адреси у відповідні слоти GOT.

**Як це виглядає на практиці:**
1. Код програми містить інструкцію: `mov rax, [rip+offset_to_got_entry_for_X]`
2. З цього слоту GOT процесор завантажує фактичну адресу змінної `X`.
3. Потім він звертається до змінної `X` за цією адресою: `mov eax, [rax]`.

Таким чином, сам сегмент коду залишається незмінним, що дозволяє різним процесам спільно використовувати його в пам'яті. Усі "коригування" адрес робляться виключно в GOT, яка є частиною сегмента даних і є унікальною для кожного процесу.

## 6. Таблиця зв'язування процедур (PLT) і ліниве зв'язування

Для функцій використовується додатковий рівень непрямості — **Procedure Linkage Table (PLT)**.

Якби динамічний лінкувальник шукав адреси абсолютно всіх зовнішніх функцій (наприклад, усіх функцій з `libc`) під час запуску програми і заповнював їх у GOT, запуск програм був би дуже повільним. Натомість використовується механізм **лінивого зв'язування (lazy binding)**.

![Таблиці GOT і PLT](/reference/unix-linux/linking/position-independent-code/img/got-plt.svg)

Коли ви викликаєте зовнішню функцію, наприклад `printf()`, компілятор не генерує прямий виклик. Замість цього він генерує виклик локального "трампліна" в PLT:
```assembly
call printf@PLT
```

Кожен запис у PLT є невеликим шматочком коду:
```assembly
printf@PLT:
    jmp [printf@GOT]      ; Перехід за адресою, записаною в GOT
    push id               ; Якщо адреса в GOT вказує сюди, готуємо ідентифікатор функції
    jmp PLT0              ; Перехід до коду резолвінгу динамічного лінкувальника
```

**Що відбувається при першому виклику?**
1. При запуску програми запис `printf@GOT` вказує на наступну інструкцію всередині самої `printf@PLT` (на `push id`).
2. Коли ми викликаємо `call printf@PLT`, програма перестрибує через `jmp` на `push id`, а потім до `PLT0`.
3. `PLT0` містить код, що викликає динамічний лінкувальник.
4. Лінкувальник знаходить `printf` у завантаженій бібліотеці `libc`, записує правильну адресу функції у `printf@GOT` і передає управління власне `printf`.

**Що відбувається при наступних викликах?**
Наступного разу `call printf@PLT` виконає `jmp [printf@GOT]`, але цього разу в GOT вже лежить реальна адреса `printf`! Програма перестрибне прямо до бібліотеки, минаючи етап резолвінгу. Це робить наступні виклики швидкими, хоч і дещо повільнішими за прямий виклик.

*Примітка: У сучасних системах для посилення безпеки (Full RELRO) ліниве зв'язування іноді вимикають, резолвлячи всі адреси на старті й роблячи GOT доступною тільки для читання, щоб захистити її від перезапису експлойтами.*

## 7. Вартість непрямості: Продуктивність і накладні витрати

Позиційна незалежність, попри всі свої переваги в гнучкості та безпеці, має ціну.

1. **Зайві інструкції та звернення до пам'яті:**
   Для доступу до зовнішньої глобальної змінної процесору замість одного звернення до пам'яті потрібно зробити два: спочатку прочитати покажчик з GOT, а потім звернутися за цією адресою.

2. **Зайві переходи (Jumps):**
   Виклик функції через PLT додає додаткову інструкцію непрямого переходу (indirect jump). Сучасні процесори з їхніми розширеними механізмами передбачення переходів (Branch Predictor, BTB) зазвичай дуже добре кешують такі переходи, але це все одно вимагає певних ресурсів.

3. **Тиск на регістри (на x86 32-bit):**
   У старих 32-бітних системах x86 компіляторам доводилося резервувати один із нечисленних регістрів загального призначення (часто `EBX`) для зберігання базової адреси GOT. Це викликало сильне падіння продуктивності (до 10-20% у деяких задачах). У x86_64, завдяки RIP-відносній адресації та збільшенню кількості регістрів, це падіння майже повністю нівелювалося (зазвичай воно становить менш як 1-3%).

## 8. Address Space Layout Randomization (ASLR) та безпека

Основна причина, чому сучасні дистрибутиви Linux (починаючи десь з 2017 року, як-от Ubuntu 16.10+) роблять PIE типовим для всіх застосунків, — це **безпека**.

**ASLR (Рандомізація компонування адресного простору)** — це механізм операційної системи, який щоразу при запуску програми випадковим чином обирає базові адреси для її сегментів: стека, купи (heap), бібліотек та самого коду програми.

![ASLR та PIE](/reference/unix-linux/linking/position-independent-code/img/aslr-pie.svg)

Якщо програма скомпільована без `-fPIE` (як традиційний виконуваний файл), операційна система не може застосувати ASLR до її сегмента коду та даних — вони мають завантажуватись за фіксованою адресою, інакше програма крашнеться (через використання абсолютних адрес). Зловмисник може використовувати ці фіксовані адреси для ROP-ланцюжків, стрибаючи на існуючі шматки коду в програмі, щоб виконати свої завдання (наприклад, відкрити shell).

Коли програма скомпільована як PIE, вона є на 100% позиційно-незалежною. Ядро Linux може розмістити *весь* виконуваний файл (і його код, і дані) за випадковою адресою при кожному новому запуску. У поєднанні з ASLR це означає, що жодна адреса в пам'яті (ні стек, ні купа, ні бібліотеки, ні код самої програми) не є відомою заздалегідь. Навіть якщо зловмисник знайде вразливість переповнення буфера, йому вкрай важко скористатися нею, оскільки він не знає, куди саме потрібно передати управління.

## 9. Практичне використання: прапорці компілятора (-fPIC, -fPIE)

У комерційній та open-source розробці сьогодні правила досить чіткі:

*   **Для створення розділюваної бібліотеки (`.so`):** Завжди використовуйте `-fPIC` під час компіляції вихідних файлів у об'єктні (`.o`), а потім лінкуйте з прапорцем `-shared`.
    ```bash
    gcc -fPIC -c mylib.c -o mylib.o
    gcc -shared mylib.o -o libmylib.so
    ```

*   **Для створення головного виконуваного файлу:** Використовуйте `-fPIE` для компіляції та `-pie` для лінкування. Сьогодні більшість компіляторів (`gcc`, `clang`) на сучасних дистрибутивах Linux мають PIE увімкненим за замовчуванням, тому вам навіть не потрібно вказувати це вручну. Якщо ви захочете вимкнути PIE (що не рекомендується з міркувань безпеки, хіба що для специфічних випадків відлагодження чи вбудованих систем), використовуйте прапорець `-no-pie`.
    ```bash
    gcc -fPIE -c main.c -o main.o
    gcc -pie main.o -o program
    ```

## 10. Підсумки

*   **Позиційно-незалежний код (PIC)** є основою системи динамічних бібліотек у Unix-системах. Він дозволяє різним процесам використовувати один і той самий екземпляр машинного коду бібліотеки в пам'яті, незважаючи на те, що ця бібліотека завантажується за різними віртуальними адресами в різних процесах.
*   **GOT та PLT** відіграють роль прошарків непрямості. GOT зберігає адреси даних та функцій, а PLT слугує трамплінами для лінивого зв'язування викликів функцій.
*   Завдяки **RIP-відносній адресації** в x86_64, звернення до локального коду й даних всередині одного PIC-модуля є дуже ефективними і не використовують додаткових регістрів.
*   **PIE** дозволяє застосувати переваги позиційно-незалежного коду до самого застосунку. Хоча це і додає мізерні накладні витрати на продуктивність, це дозволяє ядру застосовувати **ASLR** до коду програми, що радикально підвищує стійкість системи до кібератак. Сьогодні PIE є стандартом де-факто для всіх сучасних ОС, включаючи Linux, macOS та Android.

З розумінням цих механізмів ви не лише краще розумітимете повідомлення про помилки лінкувальника (наприклад, сумнозвісне "relocation R_X86_64_32 against symbol can not be used when making a PIE object"), але й зможете писати безпечніший та оптимізованіший системний код.
