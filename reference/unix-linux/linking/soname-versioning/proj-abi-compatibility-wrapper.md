# ⚙️ Практична реалізація зворотної сумісності ABI у C та C++

Цей практичний проект показує покроковий процес розробки, збирання, інспектування та тестування спільної бібліотеки `libcalc`, яка зберігає 100% зворотну бінарну сумісність при зміні бінарного інтерфейсу (ABI). Ми розберемо реальний виробничий сценарій, коли у новій версії бібліотеки змінюється сигнатура та порядок аргументів ключової функції обчислень `calc_metric`.

У першій версії бібліотеки `LIBCALC_1.0` функція `calc_metric` приймала один цілочисельний параметр `int items`. У другій версії `LIBCALC_2.0` розробники розширили алгоритм і додали другий параметр — коефіцієнт масштабування `double scale`. У звичайних умовах така зміна зламала б усі вже скомпільовані бінарні файли. Проте використання механізму GNU Symbol Versioning дозволяє новій версії бібліотеки одночасно обслуговувати як старі бінарники (викликаючи версію 1.0), так і нові додатки (спрямовуючи виклики у версію 2.0).

## 1. Архітектура та вихідний код бібліотеки libcalc

Для розмежування двох реалізацій однієї і тієї ж функції у вихідному коді C або C++ створюються дві окремі внутрішні функції з різними іменами: `calc_metric_v1` та `calc_metric_v2`. За допомогою асемблерних директив `.symver` обидві внутрішні функції зв'язуються з єдиним публічним ім'ям `calc_metric`, але з різними суфіксами версійних вузлів.

Розглянемо вихідний код бібліотеки для мов C та C++:

:::tabs
```c
// calc_v1_v2.c — Вихідний код бібліотеки libcalc з підтримкою двох ABI у C
#include <stdio.h>

// 1. Історична реалізація для ABI v1.0
// Ця функція обробляє виклики від бінарних файлів, скомпільованих під LIBCALC_1.0
int calc_metric_v1(int items) {
    printf("[libcalc v1.0] Запущено історичний ABI: items = %d (дефолтний scale = 1.0)\n", items);
    return items * 100;
}
// Прив'язуємо внутрішнє ім'я calc_metric_v1 до символу calc_metric@LIBCALC_1.0 (один собачка)
__asm__(".symver calc_metric_v1, calc_metric@LIBCALC_1.0");

// 2. Сучасна реалізація для ABI v2.0
// Ця функція приймає додатковий параметр з плаваючою крапкою
int calc_metric_v2(int items, double scale) {
    printf("[libcalc v2.0] Запущено новий ABI: items = %d, scale = %.2f\n", items, scale);
    return (int)(items * 100 * scale);
}
// Прив'язуємо внутрішнє ім'я calc_metric_v2 до дефолтного символу calc_metric@@LIBCALC_2.0 (два собачки)
__asm__(".symver calc_metric_v2, calc_metric@@LIBCALC_2.0");
```
```cpp
// calc_v1_v2.cpp — Вихідний код бібліотеки libcalc з підтримкою двох ABI у C++
#include <iostream>
#include <iomanip>

extern "C" {

// 1. Історична реалізація для ABI v1.0
int calc_metric_v1(int items) {
    std::cout << "[libcalc v1.0] Запущено історичний ABI: items = " << items 
              << " (дефолтний scale = 1.0)\n";
    return items * 100;
}
__asm__(".symver calc_metric_v1, calc_metric@LIBCALC_1.0");

// 2. Сучасна реалізація для ABI v2.0
int calc_metric_v2(int items, double scale) {
    std::cout << "[libcalc v2.0] Запущено новий ABI: items = " << items 
              << ", scale = " << std::fixed << std::setprecision(2) << scale << "\n";
    return static_cast<int>(items * 100 * scale);
}
__asm__(".symver calc_metric_v2, calc_metric@@LIBCALC_2.0");

}
```
:::

У коді вище директива `__asm__(".symver calc_metric_v1, calc_metric@LIBCALC_1.0")` інструктує компілятор записати у таблицю динамічних символів `.dynsym` запис про функцію `calc_metric` із версійною позначкою `LIBCALC_1.0`. Один собачка `@` означає, що символ є прихованим і не буде використовуватися новими етапами компонування. Подвійний собачка `@@` у директиві `calc_metric@@LIBCALC_2.0` робить цей символ дефолтним для усіх нових компіляцій.

## 2. Скрипт версіонування компонувальника (libcalc.map)

Для коректного збирання бібліотеки створюється скрипт версій `libcalc.map`. Він будує структуру секції `.gnu.version_d` у ELF-файлі та керує видимістю символів:

```text
LIBCALC_1.0 {
    global:
        calc_metric;
    local:
        *;  /* Приховує всі службові та внутрішні функції */
};

LIBCALC_2.0 {
    global:
        calc_metric;
} LIBCALC_1.0; /* Спадкує граф версії 1.0 */
```

Скрипт явно оголошує символ `calc_metric` у глобальній секції обох версійних вузлів `LIBCALC_1.0` та `LIBCALC_2.0`. Вказівка `local: *;` гарантує, що допоміжні символи компілятора та внутрішні процедури не потраплять у динамічну таблицю експорту.

## 3. Покроковий процес збирання та еволюції бібліотеки

Простежимо весь життєвий цикл збирання бібліотеки та двох версій клієнтських додатків у терміналі Linux.

### Крок 1: Збирання першої версії бібліотеки (v1.0.0)

На першому етапі розробники випускають початкову версію бібліотеки `libcalc.so.1.0.0`, яка містить тільки один ABI `LIBCALC_1.0`.

```bash
# Компіляція спільної бібліотеки версії 1.0.0 з вказанням DT_SONAME
gcc -fPIC -shared -Wl,-soname,libcalc.so.1 -o libcalc.so.1.0.0 calc_v1.c -Wl,--version-script=libcalc_v1.map

# Створення необхідних символічних посилань у каталозі збірки
ln -sf libcalc.so.1.0.0 libcalc.so.1
ln -sf libcalc.so.1 libcalc.so
```

### Крок 2: Збирання застарілого клієнтського додатка (app_legacy)

Тепер скомпілюємо клієнтську програму `client_v1.c`, яка використовує першу версію API:

:::tabs
```c
// client_v1.c — Застарілий клієнт C (ABI v1.0)
#include <stdio.h>

// Оголошення першої сигнатури функції
extern int calc_metric(int items);

int main(void) {
    printf("[app_legacy] Викликаємо calc_metric(5)...\n");
    int result = calc_metric(5);
    printf("[app_legacy] Отримано результат: %d\n", result);
    return 0;
}
```
```cpp
// client_v1.cpp — Застарілий клієнт C++ (ABI v1.0)
#include <iostream>

extern "C" int calc_metric(int items);

int main() {
    std::cout << "[app_legacy] Викликаємо calc_metric(5)...\n";
    int result = calc_metric(5);
    std::cout << "[app_legacy] Отримано результат: " << result << "\n";
    return 0;
}
```
:::

Компілюємо додаток і перевіряємо записані у нього версійні вимоги:

```bash
# Компіляція застарілого додатка
gcc client_v1.c -L. -lcalc -o app_legacy

# Інспектування версійних вимог бінарника через readelf
$ readelf -V app_legacy | grep -A 5 "Version Needs section"
Version Needs section '.gnu.version_r' contains 1 entry:
  Addr: 0x0000000000000420  Offset: 0x000420  Link: 5 (.dynstr)
  0x0000: Version: 1  File: libcalc.so.1  Cnt: 1
  0x0010: Name: LIBCALC_1.0  Flags: none  Version: 2
```

Як видно з виводу `readelf -V`, статичний компонувальник `ld` прочитав `DT_SONAME` бібліотеки (`libcalc.so.1`) і надійно закарбовав у секції `.gnu.version_r` бінарника `app_legacy` вимогу: «Для роботи потрібна версія `LIBCALC_1.0` з бібліотеки `libcalc.so.1`».

### Крок 3: Оновлення бібліотеки до версії v2.0 (libcalc.so.1.2.0)

Розробники бібліотеки випускають оновлену версію `libcalc.so.1.2.0`, яка підтримує новий ABI v2.0 і одночасно зберігає сумісність із v1.0.

```bash
# Збирання оновленої бібліотеки з двома реалізаціями функцій
gcc -fPIC -shared -Wl,-soname,libcalc.so.1 -o libcalc.so.1.2.0 calc_v1_v2.c -Wl,--version-script=libcalc.map

# Оновлення символічного посилання SONAME
ln -sf libcalc.so.1.2.0 libcalc.so.1
```

Перевіримо експортовані символи у новій бібліотеці за допомогою `objdump -T`:

```bash
$ objdump -T libcalc.so.1.2.0 | grep calc_metric
0000000000001140 g    DF .text  0000000000000022  LIBCALC_1.0  calc_metric
0000000000001170 g    DF .text  0000000000000035 (LIBCALC_2.0) calc_metric
```

У динамічній таблиці символів наявні обидві версії: `calc_metric@LIBCALC_1.0` для старих програм та дефолтна `calc_metric@@LIBCALC_2.0` (у круглих дужках) для нових збірок.

### Крок 4: Збирання сучасного клієнтського додатка (app_modern)

Скомпілюємо новий клієнтський додаток `client_v2.c`, який розрахований на новий API v2.0:

:::tabs
```c
// client_v2.c — Сучасний клієнт C (ABI v2.0)
#include <stdio.h>

// Оголошення оновленої сигнатури функції
extern int calc_metric(int items, double scale);

int main(void) {
    printf("[app_modern] Викликаємо calc_metric(5, 1.5)...\n");
    int result = calc_metric(5, 1.5);
    printf("[app_modern] Отримано результат: %d\n", result);
    return 0;
}
```
```cpp
// client_v2.cpp — Сучасний клієнт C++ (ABI v2.0)
#include <iostream>

extern "C" int calc_metric(int items, double scale);

int main() {
    std::cout << "[app_modern] Викликаємо calc_metric(5, 1.5)...\n";
    int result = calc_metric(5, 1.5);
    std::cout << "[app_modern] Отримано результат: " << result << "\n";
    return 0;
}
```
:::

```bash
# Компіляція сучасного додатка проти оновленої бібліотеки
gcc client_v2.c -L. -lcalc -o app_modern
```

## 4. Перевірка виконання завантажувачем ld.so

Тепер виконаємо обидва бінарні файли (`app_legacy` та `app_modern`) в одному й тому самому середовищі проти єдиного оновленого файлу бібліотеки `libcalc.so.1.2.0`:

```bash
$ LD_LIBRARY_PATH=. ./app_legacy
[app_legacy] Викликаємо calc_metric(5)...
[libcalc v1.0] Запущено історичний ABI: items = 5 (дефолтний scale = 1.0)
[app_legacy] Отримано результат: 500

$ LD_LIBRARY_PATH=. ./app_modern
[app_modern] Викликаємо calc_metric(5, 1.5)...
[libcalc v2.0] Запущено новий ABI: items = 5, scale = 1.50
[app_modern] Отримано результат: 750
```

### Аналіз механізму завантаження під час виконання:

1. **При запуску `app_legacy`:** Динамічний завантажувач `ld.so` відкриває `libcalc.so.1`, читає вимогу бінарника `LIBCALC_1.0` із секції `.gnu.version_r` і знаходить у динамічній таблиці `.dynsym` символ `calc_metric@LIBCALC_1.0`. Завантажувач зв'язує виклик у таблиці PLT з адресою внутрішньої функції `calc_metric_v1`. Завдяки цьому програма передає один аргумент у регістр `rdi`, функція приймає цей аргумент і повертає `500`. Відсутність другого аргументу не призводить до збою, оскільки функція `calc_metric_v1` знає про старий макет стека.
2. **При запуску `app_modern`:** Завантажувач `ld.so` бачить вимогу `LIBCALC_2.0` і спрямовує виклик на дефолтний символ `calc_metric@@LIBCALC_2.0` (внутрішня функція `calc_metric_v2`). Функція зчитує перший аргумент із регістра `rdi`, а другий (тип `double`) — із регістра `xmm0` згідно з угод про виклики System V ABI, обчислює результат і повертає `750`.

## 5. Пастки та межі застосування версіонування у C та C++

Хоча GNU Symbol Versioning є потужним механізмом збереження ABI, розробники мусять пам'ятати про його фундаментальні обмеження:

### 1. Версіонування не захищає від змін у заголовочних файлах `.h`
Якщо у заголовочному файлі `libcalc.h` оголошено підстановчу функцію `inline` або макрос препроцесора `#define`, який розгортається безпосередньо у коді додатків, зміна цього макросу у новій версії заголовочного файла не може бути зафіксована завантажувачем `ld.so`. Скомпільовані бінарні файли залишаться зі старим розгорнутим кодом макросу.

### 2. Зміни внутрішнього розміру структур даних у C++
Якщо бібліотека передає за посиланням або покажчиком структуру `struct MetricConfig`, у якій між версіями v1.0 та v2.0 додалися нові поля, стара програма виділятиме на стеку менше пам'яті, ніж очікує нова функція `calc_metric_v2`. Версіонування символу захищає точки входу у функції, але не може розширити вже виділені кадри стека або масиви у старому додатку. Для вирішення цієї проблеми розробники використовують нерозкриті покажчики (Opaque Pointers) або явне версіонування самих структур через назви типів (`MetricConfigV1`, `MetricConfigV2`).

### 3. Особливості декорування імен у C++ (Name Mangling)
У мові C++ компілятор модифікує імена функцій, додаючи інформацію про типи параметрів (наприклад, `_Z11calc_metrici` для `int` та `_Z11calc_metricid` для `int, double`). Оскільки перевантажені функції у C++ вже мають різні декоровані імена, вони можуть потрапити у різні версійні вузли скрипту `libcalc.map` без використання `.symver`. Проте використання `extern "C"` та явних `.symver` залишається необхідним для забезпечення сумісності із мовою C та запобігання зламу ABI при зміні внутрішніх реалізацій.

Автоматизована перевірка бінарної сумісності у CI/CD пайплайнах виконується за допомогою утиліт `abi-compliance-checker` та `abipkgdiff`, які порівнюють дамп дампа таблиць `.dynsym` та секцій версіонування між двома випусками бібліотеки.
