# SONAME і версіонування спільних бібліотек

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Спільні бібліотеки (shared libraries) є фундаментом сучасних операційних систем сімейства Unix та Linux. Вони дозволяють багатьом програмам використовувати спільний виконуваний код, що значно економить оперативну пам'ять та дисковий простір. Проте, з часом код бібліотек еволюціонує: виправляються помилки, додаються нові функції, а іноді змінюється інтерфейс або структура даних. Це неминуче призводить до проблеми сумісності: як оновити бібліотеку так, щоб старі програми, які від неї залежать, не зламалися?

У світі Windows ця проблема відома як "DLL Hell". В Unix/Linux її вирішують за допомогою комплексної системи версіонування, яка включає концепцію `SONAME` (Shared Object Name), використання символічних посилань та GNU Symbol Versioning. Цей розділ докладно розглядає всі аспекти цієї системи.

## 1. Основи версіонування файлів: major.minor.patch

Традиційно, спільні бібліотеки в Linux мають розширення `.so` (Shared Object). Для управління версіями розробники дотримуються певної конвенції іменування файлів, яка зазвичай базується на семантичному версіонуванні (Semantic Versioning), хоча і в дещо спрощеному вигляді. 

Повне ім'я файлу спільної бібліотеки зазвичай виглядає так: `libfoo.so.1.2.3`, де:
*   `lib` — стандартний префікс для всіх системних бібліотек.
*   `foo` — власне назва бібліотеки.
*   `.so` — розширення, що вказує на shared object.
*   `1` (major version) — мажорна версія. Змінюється лише тоді, коли відбуваються несумісні зміни в ABI (Application Binary Interface). Якщо програма була зібрана з версією 1, вона, швидше за все, впаде або працюватиме некоректно з версією 2.
*   `2` (minor version) — мінорна версія. Вказує на додавання нового функціоналу (наприклад, нових функцій), але зберігає зворотну сумісність. Програма, зібрана з версією 1.1, буде без проблем працювати з 1.2.
*   `3` (patch або release) — версія патчу. Вказує на виправлення помилок, внутрішні оптимізації без зміни ABI.

### Проблема прямого зв'язування
Уявіть, що під час компіляції вашої програми лінкер вписав би безпосередньо рядок `libfoo.so.1.2.3` у ваш виконуваний файл як залежність. У такому разі, навіть просте оновлення бібліотеки до `libfoo.so.1.2.4` (виправлення критичної вразливості) вимагало б перекомпіляції вашої програми, адже динамічний завантажувач шукав би саме `1.2.3`. Щоб розв'язати цю проблему, впровадили механізм `SONAME`.

## 2. Механізм DT_SONAME

`SONAME` — це спеціальне поле у форматі ELF (Executable and Linkable Format), яке зберігається всередині самої спільної бібліотеки. 

Коли ви створюєте спільну бібліотеку, ви можете передати лінкеру (зазвичай через gcc/clang) опцію `-Wl,-soname,libfoo.so.1`. Це запише рядок `libfoo.so.1` у секцію `.dynamic` файлу під тегом `DT_SONAME`.

```bash
# Компіляція об'єктного файлу
gcc -fPIC -c foo.c -o foo.o

# Створення спільної бібліотеки з визначенням SONAME
gcc -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3 foo.o
```

Перевірити наявність SONAME можна за допомогою утиліти `readelf` або `objdump`:

```bash
$ readelf -d libfoo.so.1.2.3 | grep SONAME
 0x000000000000000e (SONAME)             Library soname: [libfoo.so.1]
```

### Як це працює на етапі лінкування
Коли ви компілюєте свою програму (наприклад, `main.c`), і лінкуєте її з `libfoo`:

```bash
gcc main.c -o myapp -L. -lfoo
```

Лінкер (`ld`) знаходить бібліотеку на диску. Він читає її заголовки, бачить запис `DT_SONAME` зі значенням `libfoo.so.1` і записує **саме це значення**, а не ім'я файлу на диску, у виконуваний файл `myapp` як обов'язкову залежність (`DT_NEEDED`).

```bash
$ readelf -d myapp | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libfoo.so.1]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
```

Завдяки цьому, `myapp` не прив'язана до мінорної версії чи патчу. Їй потрібна будь-яка бібліотека, яка забезпечує ABI версії 1.

## 3. Танець символічних посилань (Symlinks)

Щоб описана вище система працювала, файлова система повинна містити правильний набір символічних посилань. Класична схема виглядає так:

![Архітектура симлінків](/reference/unix-linux/linking/soname-versioning/img/soname-symlinks.svg)
*Рис. 1. Ієрархія символічних посилань для спільної бібліотеки.*

У системному каталозі (наприклад, `/usr/lib`) розміщуються три файли (один реальний і два симлінки):

1.  **Реальний файл:** `libfoo.so.1.2.3` — містить безпосередньо скомпільований код.
2.  **SONAME симлінк:** `libfoo.so.1` -> `libfoo.so.1.2.3`. Цей лінк потрібен **динамічному лінкеру** (`ld.so` / `ld-linux.so.2`) під час запуску програми. Оскільки `myapp` просить `libfoo.so.1`, система шукає саме цей файл і через симлінк потрапляє на реальний код версії 1.2.3.
3.  **Linker Name симлінк:** `libfoo.so` -> `libfoo.so.1`. Цей лінк потрібен **компілятору/лінкеру** під час збирання (`gcc ... -lfoo`). Прапорець `-lfoo` змушує лінкер шукати файл `libfoo.so` або `libfoo.a`.

### Роль `ldconfig`
Керувати всіма цими симлінками вручну було б жахіттям для системних адміністраторів. В Linux цю роботу виконує утиліта `ldconfig`.

Коли в систему встановлюється нова бібліотека (наприклад, `libfoo.so.1.2.4`), пакетний менеджер кладе її в `/usr/lib` і запускає `ldconfig`.

Що робить `ldconfig`?
1. Сканує каталоги бібліотек (задані в `/etc/ld.so.conf`).
2. Читає `DT_SONAME` кожного `.so` файлу.
3. Автоматично створює або оновлює SONAME симлінки (`libfoo.so.1` тепер вказуватиме на `libfoo.so.1.2.4`). Стара версія `1.2.3` може залишитися на диску, але за замовчуванням використовуватиметься `1.2.4`.
4. Оновлює бінарний кеш `/etc/ld.so.cache`, щоб динамічний завантажувач знаходив бібліотеки миттєво, не скануючи каталоги при кожному запуску програми.

*Примітка:* `ldconfig` зазвичай не створює "Linker Name" симлінк (`libfoo.so`). Цей симлінк зазвичай постачається в `-dev` або `-devel` пакетах дистрибутиву, оскільки він потрібен лише для компіляції.

## 4. GNU Symbol Versioning (Версіонування символів)

Механізм SONAME чудово вирішує проблему мажорних оновлень. Але що, коли розробники хочуть змінити сигнатуру однієї функції, не збільшуючи мажорну версію бібліотеки (щоб не ламати решту програм)? Або що, якщо програма лінкується з двома різними бібліотеками, які, в свою чергу, залежать від двох різних мажорних версій `libfoo`?

Щоб надати ще більш гранульований контроль, розробники glibc та GNU binutils створили **GNU Symbol Versioning**. Це дозволяє присвоювати версію кожній окремій функції (символу) всередині бібліотеки. Більше того, одна бібліотека може містити **дві реалізації однієї функції** з різними версіями!

### Як виглядають версіоновані символи
Якщо ви подивитеся на таблицю символів стандартної бібліотеки C (`glibc`), ви побачите щось подібне:

```bash
$ objdump -T /lib/x86_64-linux-gnu/libc.so.6 | grep " malloc"
00000000000a6e10 g    DF .text  0000000000000288  GLIBC_2.2.5 malloc
```

Символ `malloc` має мітку `GLIBC_2.2.5`. 

При використанні Symbol Versioning кожен символ може мати суфікс:
*   `func@VERSION` — стара (сумісна) версія символу. Вона існує лише для старих програм, які були з нею скомпільовані. Нові програми не можуть з нею злінкуватися.
*   `func@@VERSION` (подвійна `@`) — версія за замовчуванням. Всі нові компіляції будуть лінкуватися саме з цією версією.

![Версіонування символів](/reference/unix-linux/linking/soname-versioning/img/symbol-versioning.svg)
*Рис. 2. Резолвінг функцій при використанні GNU Symbol Versioning.*

### Створення версіонованої бібліотеки
Щоб створити бібліотеку з версіонованими символами, розробнику потрібен **map-файл** (script).

Припустимо, ми маємо функцію `int do_work(int)`. Вона була у версії `LIBFOO_1.0`. 
Згодом ми зрозуміли, що вона має приймати рядок: `int do_work(const char*)`. Ми створюємо нову версію, але залишаємо стару для зворотної сумісності.

У коді C це реалізується за допомогою спеціальних асемблерних директив (або атрибутів компілятора):

```c
// foo.c
#include <stdio.h>

// Стара реалізація
int do_work_old(int x) {
    printf("Old work: %d\n", x);
    return x * 2;
}
// Вказуємо, що do_work_old - це do_work версії LIBFOO_1.0
__asm__(".symver do_work_old,do_work@LIBFOO_1.0");

// Нова реалізація
int do_work_new(const char* s) {
    printf("New work: %s\n", s);
    return 0;
}
// Вказуємо, що do_work_new - це do_work за замовчуванням (@@) у версії LIBFOO_2.0
__asm__(".symver do_work_new,do_work@@LIBFOO_2.0");
```

Далі ми пишемо файл `versions.map`:

```text
LIBFOO_1.0 {
    global:
        do_work;
    local:
        *;
};

LIBFOO_2.0 {
    global:
        do_work;
} LIBFOO_1.0; /* Спадкуємо від 1.0 */
```

Під час лінкування ми передаємо цей файл:

```bash
gcc -shared -fPIC -Wl,--version-script=versions.map -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.0 foo.c
```

Тепер, якщо стара програма була зібрана проти `do_work@LIBFOO_1.0`, динамічний завантажувач зв'яже її зі старою реалізацією `do_work_old`. Якщо ви скомпілюєте нову програму зараз, лінкер побачить символ за замовчуванням `do_work@@LIBFOO_2.0` і зв'яже вашу програму з `do_work_new`. 

Це дозволяє уникнути "DLL Hell" і забезпечити десятиліття зворотної сумісності (як це робить glibc, де можна запустити бінарний файл 20-річної давнини на сучасній системі).

## Висновки

Система управління спільними бібліотеками в Linux є багатошаровою та надзвичайно надійною.
1. **SONAME** відв'язує виконувані файли від конкретних мінорних версій бібліотек, покладаючись на фіксований ABI (мажорна версія).
2. **Символічні посилання** (`.so` -> `.so.1` -> `.so.1.x.y`) забезпечують гнучкість для `ldconfig` щодо оновлень "на льоту" без перезавантаження чи перекомпіляції.
3. **GNU Symbol Versioning** йде на крок далі, дозволяючи багатьом версіям одного інтерфейсу співіснувати в одному файлі бібліотеки, гарантуючи 100% зворотну сумісність на бінарному рівні.
