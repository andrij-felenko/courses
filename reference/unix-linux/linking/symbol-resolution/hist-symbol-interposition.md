# 📜 Історія розв'язання символів та виникнення ELF interposition

Еволюція механізму розв'язання символів пройшла шлях від статичного зв'язування викликів у ранніх Unix-системах до появи перекриття символів (symbol interposition) у специфікаціях System V Release 4 (SVR4) та ELF, що надало можливість прозоро перехоплювати виклики функцій без модифікації та перекомпіляції виконуваних програм.

## 1. Епоха а.out та статичного лінкування

У ранніх версіях Unix (1970–1980-ті роки) виконуваний формат `a.out` (англ. *assembler output*) розраховувався на просту модель пам'яті. Кожен виконуваний файл містив увесь системний код, необхідний для роботи. Якщо програма використовувала функції C-бібліотеки `printf` чи `open`, статичний компонувальник `ld` знаходив їхні байтові образи в архіві `libc.a` та копіював у підсумковий бінарний файл.

Розв'язання символів на цьому етапі було одноразовим і безповоротно закривалося в момент збірки:
- Компонувач формував єдиний лінійний простір адресації.
- Символи розділялися на два класи: глобальні (доступні між об'єктними `.o` файлами) та локальні (обмежені ключовим словом `static`).
- Жодного розв'язання під час запуску (load-time) не існувало — адреса кожної функції записувалася безпосередньо у машинні інструкції `call`.

Зі зростанням кількості програм у системі цей підхід призвів до двох системних проблем: марнотратного витрачання дискового простору та оперативної пам'яті (кожен процес тримав власну дубльовану копію `libc`), а також неможливості оновити системну бібліотеку без перекомпіляції геть усіх бінарників у системі. Якщо в утиліті `malloc` виявляли помилку витоку пам'яті, системному адміністраторові доводилося перекомпілювати сотні системних утиліт від `ls` до `vi`.

## 2. SunOS 4.0 та поява перших спільних бібліотек

Першу практичну спробу впровадити динамічні (спільні) бібліотеки здійснила компанія Sun Microsystems у системі SunOS 4.0 у 1988 році під керівництвом інженерів команд розробки операційних систем, а трохи згодом аналоги з'явилися у System V Release 3.2 від AT&T.

Початкова схема використовувала так звані **статичні спільні бібліотеки** (англ. *static shared libraries*). Операційна система виділяла фіксовані віртуальні адреси пам'яті для кожного системного модуля (наприклад, `libc` завжди завантажувалася за адресою `0x60000000`). Компонувач фіксував адреси викликів під час компіляції.

Такий підхід розв'язав проблему дублювання оперативної пам'яті на дисках і у RAM, але створив нові технологічні труднощі:
1. **Конфлікти адресних просторів:** Якщо дві незалежні бібліотеки обирали однакові віртуальні адреси, вони не могли працювати в одному процесі.
2. **Жорсткість розмірів:** Якщо нова версія `libc` ставала більшою за виділене їй адресне вікно, старі програми ламалися або перекривали пам'ять сусідніх модулів.
3. **Неможливість підміни:** Оскільки адреси були зафіксовані під час збірки, підставити власну версію функції `malloc` без перезбірки програми було неможливо.

## 3. Революція SVR4, ELF та народження Dynamic Linker

У 1989–1990 роках консорціум Unix System Laboratories (USL) разом із Sun Microsystems розробив специфікацію **SVR4 ABI**, у якій представив формат **ELF** (англ. *Executable and Linkable Format*) та механізм позиційно-незалежного коду (англ. *Position-Independent Code*, PIC).

Для підтримки справді динамічного розв'язання символів було створено три ключові концепції:
- **Таблиця індирекції GOT** (англ. *Global Offset Table*): таблиця абсолютних адрес змінних та функцій, яка заповнюється під час завантаження.
- **Таблиця залучення PLT** (англ. *Procedure Linkage Table*): кодові трампліни, які реалізують ліниве розв'язання (lazy binding) викликів.
- **Динамічний компонувальник `ld.so`** (англ. *dynamic linker/loader*): спеціальний інтерпретатор простору користувача, якому ядро передає керування після виклику `execve`.

Саме `ld.so` брав на себе задачу обходу таблиць символів усіх завантажених об'єктів `.so` та зв'язування неконкретизованих символів з їхніми реальними адресами у пам'яті. Це створило гнучке середовище, у якому кожна бібліотека могла завантажуватися за довільною віртуальною адресою, підлаштовуючи свої таблиці GOT під підсумкову розкладку пам'яті процесу.

## 4. Створення LD_PRELOAD та виникнення Symbol Interposition

Під час розробки SunOS 5.0 (Solaris 2.0) інженерам Sun Microsystems (зокрема Роду Евансу та його колегам) знадобився зручний інструмент для налагодження трасування пам'яті, моніторингу системних викликів та тестування профільних бібліотек без модифікації вихідного коду базових утиліт. Вони запропонували алгоритм пошуку символів **First-Match Wins** (виграє той, хто знайдений першим).

Згідно з цим алгоритмом, `ld.so` перевіряє таблиці символів динамічних об'єктів у суворо визначеному порядку:
1. Бібліотеки, явно вказані у змінній середовища `LD_PRELOAD`.
2. Головний виконуваний файл.
3. Залежності, перелічені в секції `DT_NEEDED` у порядку їх згадування.

Впровадження `LD_PRELOAD` створило поняття **Symbol Interposition** (перекриття символів): якщо бібліотека з `LD_PRELOAD` містить символ `malloc`, динамічний лінкер зв'язує **усі** виклики `malloc` у системі з цією новою функцією, ігноруючи однойменний символ у системній `libc.so`.

## 5. Додавання dlsym та RTLD_NEXT

Перекриття символів породило нову проблему: як користувацькій бібліотеці-перехоплювачу викликати справжню системну функцію? Якщо `malloc` всередині перехоплювача просто виконував `call malloc`, це призводило до нескінченної рекурсії та переповнення стека.

У рамках стандарту POSIX.1-2001 та реалізації у GNU C Library (glibc) під керівництвом Ульріха Дреппера було розширено API динамічного зчитування `dlfcn.h`. Зокрема, додано псевдо-дескриптор `RTLD_NEXT` для функції `dlsym`:

:::tabs
```c
void *real_malloc = dlsym(RTLD_NEXT, "malloc");
```
```cpp
auto real_malloc = reinterpret_cast<void*(*)(std::size_t)>(dlsym(RTLD_NEXT, "malloc"));
```
:::

Значення `RTLD_NEXT` вказує лінкеру шукати символ `malloc`, починаючи з бібліотеки, що іде **після** тієї, яка здійснює запит. Це дозволило будувати прозорі ланцюжки перехоплення (hooking chains), де власна реалізація виконує облікові чи захисні дії та проксирує виклик далі до системної `libc`.

Завдяки цьому відкриттю сучасні Unix-подібні системи отримали універсальний інструмент для трасування, налагодження та профілювання. Спадщина SVR4 ELF та `LD_PRELOAD` сьогодні використовується у санітайзерах пам'яті (AddressSanitizer), інструментах перехоплення графічних викликів (RenderDoc, MangoHud), системних моніторах продуктивності та профілювальниках бездротових і високонавантажених мережевих застосунків.
