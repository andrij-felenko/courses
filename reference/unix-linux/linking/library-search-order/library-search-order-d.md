# Порядок пошуку бібліотек: rpath, LD_LIBRARY_PATH, кеш

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У середовищі Unix та Linux переважна більшість програм покладається на динамічне зв'язування (dynamic linking). Коли програма компілюється, її виконуваний файл не містить усього необхідного коду. Натомість, він містить лише посилання на зовнішні розділювані бібліотеки (shared libraries, файли з розширенням `.so`), які мають бути знайдені та завантажені в оперативну пам'ять під час запуску програми. Цей процес виконує динамічний завантажувач (dynamic linker), зазвичай відомий як `ld.so` або `ld-linux.so`. 

Критично важливим аспектом роботи динамічного завантажувача є алгоритм пошуку цих бібліотек. Якщо бібліотека не знайдена, програма просто не запуститься, видавши помилку на зразок "cannot open shared object file: No such file or directory". Якщо ж завантажувач знайде неправильну версію бібліотеки, програма може поводитися непередбачувано або завершитися аварійно з помилкою сегментації. Саме тому детальне розуміння порядку пошуку бібліотек, механізмів `DT_RPATH`, `DT_RUNPATH`, `LD_LIBRARY_PATH`, а також використання `$ORIGIN` є абсолютно необхідним для розробників, системних адміністраторів та інженерів з розгортання програмного забезпечення.

Ця стаття детально досліджує кожен етап пошуку розділюваних бібліотек, історичний контекст появи різних механізмів (таких як перехід від `DT_RPATH` до `DT_RUNPATH`), а також міркування безпеки, пов'язані з `LD_LIBRARY_PATH` у контексті SUID/SGID програм.

## 1. Роль динамічного лінкера/завантажувача

Коли ви запускаєте динамічно скомпільовану програму (ELF файл - Executable and Linkable Format), операційна система (ядро Linux) завантажує її в пам'ять. Проте, перш ніж передати управління самій програмі, ядро завантажує та запускає динамічний завантажувач. Його шлях зазвичай зашитий в ELF-заголовку програми в секції `.interp` (інтерпретатор). Ви можете перевірити це за допомогою інструменту `readelf`:

```bash
$ readelf -l /bin/ls | grep "Requesting program interpreter"
      [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
```

Завдання `ld.so` полягає в тому, щоб:
1. Проаналізувати секцію `DT_NEEDED` у `DYNAMIC` сегменті виконуваного файлу, щоб скласти список усіх бібліотек, від яких залежить ця програма.
2. Знайти ці бібліотеки у файловій системі за чітко визначеним порядком.
3. Завантажити їх у пам'ять, якщо вони ще не були завантажені іншими процесами.
4. Розв'язати (resolve) символи — функції та глобальні змінні, на які посилається програма, прив'язавши їх до реальних адрес у завантажених бібліотеках.

Якщо бібліотеку вказано за абсолютним шляхом (наприклад, `/opt/mylib/libfoo.so`), завантажувач просто намагається відкрити цей файл. Однак, зазвичай бібліотеки вказуються лише за іменем (наприклад, `libc.so.6`), і саме тоді активується алгоритм пошуку.

## 2. Повний алгоритм пошуку: крок за кроком

Динамічний завантажувач у GNU/Linux дотримується чітко визначеної послідовності при пошуку кожної бібліотеки. Ця послідовність еволюціонувала з часом, щоб краще відповідати вимогам гнучкості та безпеки. Сучасний стандартний порядок виглядає наступним чином:

1. **DT_RPATH** (старий шлях пошуку). Використовується лише в тому випадку, якщо у файлі **ВІДСУТНІЙ** атрибут `DT_RUNPATH`.
2. **Змінна середовища LD_LIBRARY_PATH**. Дозволяє користувачеві тимчасово перевизначити шляхи пошуку. Ігнорується для програм з встановленими бітами SUID/SGID з міркувань безпеки.
3. **DT_RUNPATH** (новий шлях пошуку). Альтернатива RPATH, яка має менший пріоритет, ніж `LD_LIBRARY_PATH`, що дозволяє легко тестувати нові версії бібліотек.
4. **Кеш лінкера (/etc/ld.so.cache)**. Двійковий файл, який містить попередньо скомпільовану хеш-таблицю всіх відомих системних бібліотек.
5. **Стандартні системні каталоги**. Fallback-варіанти, зазвичай `/lib` та `/usr/lib` (або їх 64-бітні еквіваленти `/lib64`, `/usr/lib64`).

Кожен з цих механізмів має своє призначення, переваги, недоліки та типові сценарії використання (use cases). Розглянемо їх детальніше.

## 3. DT_RPATH: Старий, але потужний механізм

`RPATH` (Run-time search PATH) — це рядок, який записується безпосередньо у виконуваний файл (або спільну бібліотеку) під час компіляції (лінкування). Він зберігається в DYNAMIC-секції ELF-файлу під тегом `DT_RPATH`. 

Мета `RPATH` — вказати завантажувачу жорстко закодовані шляхи, де слід шукати бібліотеки. Це вкрай корисно для комерційного програмного забезпечення або програм, встановлених у нестандартні директорії (наприклад, в `/opt/myapp/lib`), коли ви не хочете покладатися на загальносистемні налаштування або вимагати від користувачів змінювати `LD_LIBRARY_PATH`.

### Як встановити RPATH

Встановити `RPATH` можна під час лінкування, передавши відповідні аргументи лінкеру (зазвичай через компілятор `gcc` або `clang` за допомогою прапорця `-Wl`):

```bash
gcc -o myapp main.c -L/opt/mylib -lmylib -Wl,-rpath=/opt/mylib
```

У цьому прикладі `/opt/mylib` буде записано в `DT_RPATH` програми `myapp`.

### Проблеми з DT_RPATH

Основна проблема `DT_RPATH` полягає у його надто високому пріоритеті. Оскільки він перевіряється *до* `LD_LIBRARY_PATH`, розробникам або користувачам дуже важко примусово змусити програму використовувати іншу версію бібліотеки для налагодження або тестування. 

Наприклад, якщо програма скомпільована з `RPATH=/opt/prod/lib`, і ви хочете протестувати виправлення помилки у бібліотеці, яка знаходиться у `/home/user/test/lib`, встановлення `LD_LIBRARY_PATH=/home/user/test/lib` не матиме бажаного ефекту, оскільки завантажувач спочатку перевірить `/opt/prod/lib`, знайде бібліотеку там і зупинить пошук.

Щоб вирішити цю проблему надмірної жорсткості, розробники специфікацій ELF ввели новий атрибут — `DT_RUNPATH`.

## 4. Змінна середовища LD_LIBRARY_PATH

`LD_LIBRARY_PATH` — це, мабуть, найвідоміший механізм керування пошуком бібліотек серед користувачів Linux. Вона містить список каталогів, розділених двокрапкою (`:`), аналогічно до змінної `PATH`.

```bash
export LD_LIBRARY_PATH=/home/user/mylibs:/tmp/testlibs
./myapp
```

### Коли використовувати LD_LIBRARY_PATH

1. **Розробка та тестування**: Це ідеальний інструмент для швидкої перевірки нової версії бібліотеки без необхідності перекомпільовувати програму або втручатися в систему.
2. **Запуск програм з нестандартними вимогами**: Якщо користувач не має прав root для встановлення бібліотек у `/usr/lib`, він може покласти їх у свою домашню директорію і використовувати `LD_LIBRARY_PATH`.
3. **Обгортки (Wrapper scripts)**: Багато складних програм постачаються зі скриптом-запускачем, який встановлює `LD_LIBRARY_PATH` перед тим, як викликати реальний бінарник. 

### Чому LD_LIBRARY_PATH є злом для Production

Незважаючи на свою зручність, використання `LD_LIBRARY_PATH` вважається антипатерном (bad practice) у production-середовищах і для загальносистемних конфігурацій. 

1. **Глобальний вплив**: Якщо ви встановите `LD_LIBRARY_PATH` у `.bashrc` або `/etc/environment`, це вплине на *всі* програми, які ви запускаєте. Це може призвести до "DLL Hell", коли системні утиліти раптом починають завантажувати несумісні бібліотеки з вашої власної директорії замість системних, що може повністю зламати систему.
2. **Продуктивність**: Додавання багатьох шляхів до `LD_LIBRARY_PATH` змушує завантажувач перевіряти кожен з цих каталогів для *кожної* бібліотеки, яку завантажує *кожна* програма. Це створює величезну кількість зайвих системних викликів `stat` і `open`, сповільнюючи запуск програм.
3. **Безпека**: Оскільки ця змінна дозволяє легко підмінити бібліотеку, вона ігнорується для програм з підвищеними привілеями (про це нижче).

Сучасні практики розгортання віддають перевагу використанню `RUNPATH` (з `$ORIGIN`) або правильному налаштуванню `/etc/ld.so.conf` замість глобального використання `LD_LIBRARY_PATH`.

## 5. DT_RUNPATH: Новий стандарт

`DT_RUNPATH` було створено як заміну `DT_RPATH`. Він працює майже так само, за однією критичною відмінністю: **він обробляється ПІСЛЯ `LD_LIBRARY_PATH`**.

Це означає, що програма зберігає знання про те, де знаходяться її бібліотеки за замовчуванням (через `RUNPATH`), але розробник або адміністратор може легко перевизначити це за допомогою `LD_LIBRARY_PATH` для цілей тестування чи налагодження.

### Як сучасні лінкери обробляють RPATH і RUNPATH

Важливо розуміти поведінку сучасного лінкера GNU (`ld`). Історично він створював лише `DT_RPATH`. Якщо ви сьогодні використовуєте прапорець `--enable-new-dtags` (який є типовим у більшості сучасних дистрибутивів Linux), лінкер створить **ОБИДВА** атрибути у виконуваному файлі: `DT_RPATH` і `DT_RUNPATH`. 

Однак, згідно зі специфікацією динамічного завантажувача (glibc):
> Якщо у файлі присутній `DT_RUNPATH`, то атрибут `DT_RPATH` повністю **ІГНОРУЄТЬСЯ**.

Таким чином, наявність `DT_RUNPATH` автоматично знижує пріоритет зашитих шляхів і ставить їх після `LD_LIBRARY_PATH`.

Щоб перевірити, які теги встановлені, використовуйте `readelf`:

```bash
$ readelf -d ./myapp | grep PATH
 0x000000000000000f (RPATH)              Library rpath: [/opt/mylib]
 0x000000000000001d (RUNPATH)            Library runpath: [/opt/mylib]
```
У цьому випадку завантажувач ігноруватиме `RPATH` і використовуватиме лише `RUNPATH`.

## 6. Магія $ORIGIN, $LIB, $PLATFORM

Найбільшим недоліком жестко закодованих шляхів в RPATH/RUNPATH є те, що програму неможливо перемістити. Якщо ви скомпілювали програму з `RUNPATH=/opt/myapp/lib`, ви повинні розгорнути її саме в `/opt/myapp`. Якщо користувач розпакує ваш архів у `/home/user/myapp`, програма не знайде своїх бібліотек.

Для вирішення проблеми створення "переміщуваних" (relocatable) пакетів був введений спеціальний токен розширення: `$ORIGIN`.

### $ORIGIN

Коли динамічний завантажувач бачить рядок `$ORIGIN` (або `${ORIGIN}`) всередині RPATH/RUNPATH, він автоматично замінює його на абсолютний шлях до каталогу, в якому лежить сам виконуваний файл.

Це дозволяє створювати портативні програми, які містять власні бібліотеки відносно свого розташування:

```
myapp/
├── bin/
│   └── myapp.exe
└── lib/
    └── libhelper.so
```

Щоб `myapp.exe` завжди знаходив `libhelper.so` незалежно від того, куди розпаковано теку `myapp`, ми компілюємо його з:

```bash
gcc -o myapp/bin/myapp.exe main.c -Lmyapp/lib -lhelper -Wl,-rpath='$ORIGIN/../lib'
```
*(Примітка: ми використовуємо одинарні лапки `'$ORIGIN'`, щоб запобігти інтерпретації змінної оболонкою (shell) до того, як вона потрапить до лінкера).*

Тепер, коли програма запускається, `$ORIGIN` замінюється на `/path/to/myapp/bin`, і завантажувач шукає бібліотеки у `/path/to/myapp/bin/../lib`, тобто в `myapp/lib`.

### Інші корисні токени

- `$LIB`: Замінюється на `lib` для 32-бітної архітектури та на `lib64` (або щось подібне) для 64-бітної архітектури. Дозволяє створювати мультиархітектурні бінарники з єдиним RUNPATH, наприклад, `$ORIGIN/../$LIB`.
- `$PLATFORM`: Замінюється на назву платформи/архітектури (наприклад, `x86_64`, `haswell`). Дозволяє мати оптимізовані версії бібліотек для різних поколінь процесорів.

## 7. Кеш лінкера (/etc/ld.so.cache)

Якщо бібліотека не знайдена за допомогою RPATH, RUNPATH або `LD_LIBRARY_PATH`, завантажувач міг би теоретично почати шукати її, перевіряючи всі системні каталоги `/usr/lib`, `/lib` тощо. Однак такий підхід був би надзвичайно повільним. Програмі часто потрібні десятки бібліотек, а файлова система може бути повільною.

Щоб оптимізувати процес, Linux використовує файл кешу — `/etc/ld.so.cache`. Це двійковий файл (бінарний формат), який містить зіставлення між іменами бібліотек (наприклад, `libm.so.6`) та їхніми повними абсолютними шляхами (наприклад, `/lib/x86_64-linux-gnu/libm.so.6`).

Цей кеш генерується утилітою **`ldconfig`**. Коли ви встановлюєте нові бібліотеки в систему, ви зазвичай повинні запустити `ldconfig` (або пакетний менеджер робить це за вас).

### Як працює ldconfig

Утиліта `ldconfig` читає файл конфігурації `/etc/ld.so.conf` (який зазвичай включає всі файли з `/etc/ld.so.conf.d/`). Ці файли містять списки додаткових каталогів, у яких лежать системні розділювані бібліотеки.

`ldconfig` сканує ці каталоги, а також стандартні довірені шляхи (`/lib`, `/usr/lib`, `/lib64`, `/usr/lib64`), знаходить усі розділювані бібліотеки, створює необхідні символічні посилання (від імені-сонейму (soname) до реального файлу версії) і записує результати у швидкий для читання двійковий кеш `/etc/ld.so.cache`.

Ви можете переглянути поточний вміст кешу за допомогою команди:

```bash
$ ldconfig -p
2397 libs found in cache `/etc/ld.so.cache'
        libzstd.so.1 (libc6,x86-64) => /usr/lib/x86_64-linux-gnu/libzstd.so.1
        libz.so.1 (libc6,x86-64) => /lib/x86_64-linux-gnu/libz.so.1
        ...
```

Динамічний завантажувач просто зчитує цей кеш, і за долі секунди знаходить шлях до системних бібліотек.

## 8. Стандартні системні каталоги

Якщо бібліотеки немає в RPATH, LD_LIBRARY_PATH, RUNPATH, і навіть у кеші `ld.so.cache` (наприклад, якщо хтось скопіював бібліотеку в `/lib64`, але забув запустити `ldconfig`), завантажувач робить останню відчайдушну спробу. Він перевіряє так звані "довірені" (trusted) каталоги системи за замовчуванням.

Для більшості Linux-систем це:
- `/lib`
- `/usr/lib`
Для 64-бітних архітектур на багатьох дистрибутивах (наприклад, RHEL/CentOS/Fedora) також жорстко закодовані:
- `/lib64`
- `/usr/lib64`
На дистрибутивах, що базуються на Debian/Ubuntu, використовується мультиархітектурна структура (Multi-Arch), тому стандартні шляхи виглядають як `/lib/x86_64-linux-gnu` або `/usr/lib/aarch64-linux-gnu`.

Якщо після перевірки всіх цих шляхів бібліотеку не знайдено, `ld.so` припиняє виконання з фатальною помилкою.

## 9. Безпека: SUID і SGID бінарники

Налаштування шляхів пошуку бібліотек є класичним вектором для атак на підвищення привілеїв (Privilege Escalation).

### Загроза
Уявіть програму `/usr/bin/passwd`, яка має встановлений біт SUID і належить користувачеві `root`. Вона виконується з правами `root`, незалежно від того, який користувач її запустив. Ця програма завантажує `libc.so.6`.
Якщо зловмисник (звичайний користувач) створить свою власну шкідливу версію `libc.so.6` і встановить змінну середовища:
`LD_LIBRARY_PATH=/tmp/evil /usr/bin/passwd`

То програма `passwd`, маючи права root, завантажила б шкідливу бібліотеку з `/tmp/evil`, а її код виконав би функції (наприклад, запуск шелу), віддавши зловмиснику права суперкористувача.

### Захист у ld.so
Щоб запобігти цьому, динамічний завантажувач перевіряє, чи має виконуваний файл встановлені біти SUID або SGID. Більш технічно, в Linux ядро передає завантажувачу спеціальний допоміжний вектор `AT_SECURE`. Якщо `AT_SECURE` дорівнює 1 (режим "безпечного виконання"), завантажувач вживає суворих заходів:

1. **Повне ігнорування `LD_LIBRARY_PATH`**. Навіть якщо користувач встановив цю змінну, для SUID-програм вона просто відкидається. Завантажувач також ігнорує інші "небезпечні" змінні, такі як `LD_PRELOAD`.
2. **Обмеження на $ORIGIN**. Використання `$ORIGIN` у `RPATH` або `RUNPATH` суворо обмежується. Завантажувач може відмовитися розгортати `$ORIGIN` для SUID-програм, якщо шлях призначення сам не знаходиться у захищеній, довіреній директорії, оскільки зловмисник міг би скопіювати SUID-файл у свою директорію і змусити `$ORIGIN` вказувати на шкідливу бібліотеку поруч із копією. 

Через ці обмеження безпеки, SUID-програми майже виключно покладаються на системний кеш `/etc/ld.so.cache` та стандартні системні шляхи `/lib64`, `/usr/lib64`. Якщо вам необхідно, щоб SUID-програма використовувала нестандартну бібліотеку, вам доведеться додати шлях до неї в `/etc/ld.so.conf` (що вимагає прав root).

## 10. Інструменти для діагностики та Troubleshooting

Працюючи з динамічним лінкуванням, розробники часто стикаються з проблемами. На щастя, існують потужні інструменти для діагностики.

### ldd
`ldd` — найперший інструмент для перевірки залежностей. Він імітує завантаження програми і показує, як завантажувач розв'язав шляхи до всіх необхідних бібліотек.

```bash
$ ldd /bin/bash
        linux-vdso.so.1 (0x00007ffd2cf7c000)
        libtinfo.so.6 => /lib/x86_64-linux-gnu/libtinfo.so.6 (0x00007f3c4c952000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f3c4c760000)
        /lib64/ld-linux-x86-64.so.2 (0x00007f3c4caaa000)
```
Якщо бібліотека не знайдена, ви побачите повідомлення "not found". *Застереження: Ніколи не запускайте `ldd` на виконуваних файлах з невідомих або сумнівних джерел, оскільки в деяких старих реалізаціях це могло призвести до виконання їхнього коду.*

### objdump та readelf
Ці утиліти дозволяють зазирнути безпосередньо в заголовки ELF-файлу та побачити `DT_NEEDED`, `DT_RPATH` та `DT_RUNPATH` без спроб завантаження.

```bash
$ readelf -d myapp | grep -E "NEEDED|RPATH|RUNPATH"
```

### LD_DEBUG
Це "секретна" зброя розробників. Динамічний завантажувач має вбудовану систему детального логування, яка активується змінною середовища `LD_DEBUG`.

Якщо ви не можете зрозуміти, *чому* завантажувач бере не ту бібліотеку, або *де саме* він її шукає, запустіть програму так:

```bash
$ LD_DEBUG=libs ./myapp
```
Ви отримаєте детальний вивід на консоль (stderr) кожного кроку: у яких каталогах завантажувач шукав бібліотеки, де знайшов, які змінні та кеші використовував. Інші корисні значення: `LD_DEBUG=files` (детальніше про файли), `LD_DEBUG=symbols` (допомагає вирішувати помилки undefined symbol), `LD_DEBUG=help` (виводить довідку).

### strace
Якщо `LD_DEBUG` чомусь недоступний або не працює як очікується, `strace` дозволяє відстежити системні виклики. Ви можете побачити реальні спроби відкрити файли:

```bash
$ strace -e open,openat ./myapp
```
Ви побачите послідовність викликів `openat`, які повертають `ENOENT` (No such file or directory), поки завантажувач перебирає всі шляхи RPATH, LD_LIBRARY_PATH, і нарешті знаходить потрібний файл (або зазнає невдачі).

## 11. Висновок

Розуміння порядку пошуку бібліотек є критичним для забезпечення стабільності, безпеки та портативності програмного забезпечення в екосистемі Unix/Linux. 

Перехід від `DT_RPATH` до комбінації `DT_RUNPATH` та `LD_LIBRARY_PATH` забезпечив кращий баланс між жорстким контролем розробників над залежностями та гнучкістю, необхідною системним адміністраторам для тестування і відлагодження. Водночас використання `$ORIGIN` значно спростило розповсюдження автономних (standalone) програм.

Пам'ятайте базове правило:
1. Використовуйте кеш та `/etc/ld.so.conf` для загальносистемних бібліотек.
2. Використовуйте `RUNPATH` (з `$ORIGIN`) для бібліотек, які розповсюджуються разом з вашим застосунком.
3. Уникайте `LD_LIBRARY_PATH` у production; зберігайте цей інструмент для тимчасових завдань та тестування.
4. Завжди враховуйте обмеження безпеки при роботі зі SUID/SGID програмами.

Озброївшись розумінням цих механізмів та інструментами на зразок `readelf`, `ldd` і `LD_DEBUG`, ви зможете швидко та ефективно розв'язувати будь-які проблеми з динамічним лінкуванням (популярні помилки "DLL Hell"), що виникають у вашій практиці.
