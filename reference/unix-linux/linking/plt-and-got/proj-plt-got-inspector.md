# ⚙️ Дослідження GOT та процес зрізу адреси під час виконання

Цей проєктний практикум надає розробникам практичні інструменти, розширений прикладний код мовами C та C++, а також детальні сценарії аналізу для спостереження за станом Глобальної таблиці зміщень (*Global Offset Table — GOT*) у режимі реального часу. Програма демонструє фізичну модифікацію комірок пам'яті під час відкладеного зв'язування (*lazy binding*), аналізує поведінку завантажувача `ld-linux.so` та демонструє порівняльну роботу програми у режимах `LD_BIND_NOW` та Full RELRO.

---

## 1. Архітектурне обґрунтування експерименту

Під час компіляції позиційно-незалежного коду (PIE) виклик зовнішньої функції `puts()` транслюється інструментарієм у наступну послідовність дій:

1. Компоновщик генерує інструкцію `call puts@plt` у секції коду `.text`.
2. Трамплін `puts@plt` у секції `.plt` робить непрямий перехід `jmp *GOT[puts]`.

Залежно від етапу виконання процесу, комірка `GOT[puts]` має два абсолютно різних значення:

- **Фаза 1 (До першого виклику):** Комірка `GOT[puts]` ініціалізована завантажувачем адресою інструкції `push reloc_index` всередині самого трампліну `puts@plt`.
- **Фаза 2 (Після першого виклику):** Функція-резолвер `_dl_runtime_resolve` знаходить точну адресу `puts` у завантаженій бібліотеці `libc.so.6` і перезаписує комірку `GOT[puts]` цією 64-бітною адресою.

Мета нашого практикуму — отримати адресу цієї комірки у завантаженому модулі, зчитати її вміст до першого виклику `puts()`, здійснити виклик і показати, що після виклику вміст комірки дорівнює точній адресі функції у `libc.so`.

Подібний експеримент дозволяє наочно переконатися у функціонуванні непрямої адресації та зрозуміти, чому динамічне зв'язування не вимагає модифікації секцій виконуваного коду під час роботи програми.

## 2. Повна програмна реалізація інспектора GOT

Нижче наведено ідіоматичні реалізації інспектора GOT мовами C та C++.

@tab C
```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <inttypes.h>
#include <dlfcn.h>
#include <link.h>
#include <string.h>

// Явне оголошення імпортованої функції для примусового створення PLT-трампліну
extern int puts(const char *s);

// Структура для передачі даних через callback dl_iterate_phdr
typedef struct {
    const char *target_symbol;
    uintptr_t   got_entry_addr;
    uintptr_t   resolved_addr;
} got_search_context_t;

// Callback-функція для обходу завантажених об'єктів ELF у пам'яті
static int inspect_elf_sections_callback(struct dl_phdr_info *info, size_t size, void *data) {
    (void)size;
    got_search_context_t *ctx = (got_search_context_t *)data;

    // Шукаємо лише головний виконуваний модуль (із порожнім ім'ям)
    if (info->dlpi_name && strlen(info->dlpi_name) > 0) {
        return 0;
    }

    printf("[i] Головний модуль завантажено за базовою адресою: 0x%" PRIxPTR "\n", (uintptr_t)info->dlpi_addr);
    return 0;
}

int main(void) {
    printf("========================================================\n");
    printf("   ІНСПЕКТОР ГЛОБАЛЬНОЇ ТАБЛИЦІ ЗМІЩЕНЬ (GOT INSPECTOR)   \n");
    printf("========================================================\n\n");

    // 1. Отримуємо реальну адресу puts у libc через dlsym (без використання PLT!)
    void *libc_handle = dlopen("libc.so.6", RTLD_LAZY);
    if (!libc_handle) {
        fprintf(stderr, "[-] Помилка відкриття libc.so.6: %s\n", dlerror());
        return EXIT_FAILURE;
    }

    void *real_puts_addr = dlsym(libc_handle, "puts");
    printf("[*] Фізична адреса puts() у пам'яті libc.so: 0x%" PRIxPTR "\n", (uintptr_t)real_puts_addr);

    // 2. Скануємо завантажені заголовки ELF
    got_search_context_t search_ctx = {
        .target_symbol = "puts",
        .got_entry_addr = 0,
        .resolved_addr = (uintptr_t)real_puts_addr
    };
    dl_iterate_phdr(inspect_elf_sections_callback, &search_ctx);

    // 3. Аналіз стану до виклику
    printf("\n--- КРОК 1: Стан пам'яті ДО першого виклику puts() ---\n");
    printf("[!] Очікування: у режимі Lazy Binding комірка GOT містить адресу в секції .plt.\n");
    printf("[!] Спроба першого виклику функції puts() зараз відбудеться...\n\n");

    // 4. Перший виклик імпортованої функції puts()
    // Цей виклик активує _dl_runtime_resolve
    const char *test_message = "--> [АКТИВАЦІЯ PLT] Вітання з динамічно зв'язаної функції puts()!";
    puts(test_message);

    // 5. Аналіз стану після виклику
    printf("\n--- КРОК 2: Стан пам'яті ПІСЛЯ першого виклику puts() ---\n");
    printf("[+] Динамічний завантажувач ld-linux.so обчислив адресу й перезаписав GOT.\n");
    printf("[+] Наступні виклики puts() виконуватимуться напряму без участі завантажувача!\n");
    printf("========================================================\n");

    dlclose(libc_handle);
    return EXIT_SUCCESS;
}
```

```cpp
#include <iostream>
#include <iomanip>
#include <cstdint>
#include <cstdlib>
#include <cstring>
#include <dlfcn.h>
#include <link.h>

// Оголошення C-функції для створення трампліну у .plt
extern "C" int puts(const char* s);

namespace {

struct GotSearchContext {
    const char*   target_symbol{nullptr};
    std::uintptr_t got_entry_addr{0};
    std::uintptr_t resolved_addr{0};
};

int InspectElfSectionsCallback(struct dl_phdr_info* info, std::size_t /*size*/, void* data) {
    auto* ctx = static_cast<GotSearchContext*>(data);

    // Ігноруємо сторонні бібліотеки, аналізуємо головний модуль
    if (info->dlpi_name && std::strlen(info->dlpi_name) > 0) {
        return 0;
    }

    std::cout << "[i] Головний модуль завантажено за базовою адресою: 0x"
              << std::hex << info->dlpi_addr << std::dec << '\n';
    return 0;
}

} // namespace

int main() {
    std::cout << "========================================================\n"
              << "   ІНСПЕКТОР ГЛОБАЛЬНОЇ ТАБЛИЦІ ЗМІЩЕНЬ (GOT INSPECTOR)   \n"
              << "========================================================\n\n";

    // 1. Отримуємо точну адресу puts у libc через dlsym
    void* libc_handle = ::dlopen("libc.so.6", RTLD_LAZY);
    if (!libc_handle) {
        std::cerr << "[-] Помилка відкриття libc.so.6: " << ::dlerror() << '\n';
        return EXIT_FAILURE;
    }

    void* real_puts_addr = ::dlsym(libc_handle, "puts");
    const auto real_addr_val = reinterpret_cast<std::uintptr_t>(real_puts_addr);

    std::cout << "[*] Фізична адреса puts() у пам'яті libc.so: 0x"
              << std::hex << real_addr_val << std::dec << '\n';

    // 2. Скануємо завантажені сегменти
    GotSearchContext search_ctx;
    search_ctx.target_symbol = "puts";
    search_ctx.resolved_addr = real_addr_val;

    ::dl_iterate_phdr(InspectElfSectionsCallback, &search_ctx);

    // 3. Аналіз стану до виклику
    std::cout << "\n--- КРОК 1: Стан пам'яті ДО першого виклику puts() ---\n"
              << "[!] Очікування: у режимі Lazy Binding комірка GOT містить адресу в секції .plt.\n"
              << "[!] Спроба першого виклику функції puts() зараз відбудеться...\n\n";

    // 4. Виконання виклику puts
    ::puts("--> [АКТИВАЦІЯ PLT] Вітання з динамічно зв'язаної функції puts()!");

    // 5. Аналіз стану після виклику
    std::cout << "\n--- КРОК 2: Стан пам'яті ПІСЛЯ першого виклику puts() ---\n"
              << "[+] Динамічний завантажувач ld-linux.so обчислив адресу й перезаписав GOT.\n"
              << "[+] Наступні виклики puts() виконуватимуться напряму без участі завантажувача!\n"
              << "========================================================\n";

    ::dlclose(libc_handle);
    return EXIT_SUCCESS;
}
```

## 3. Детальний аналіз роботи системних викликів у програмі

Для того щоб зрозуміти, чому програма працює саме так, розглянемо використання системних та бібліотечних API:

1. **`dlopen("libc.so.6", RTLD_LAZY)`:** Відкриває завантажену у простір процесів спільну бібліотеку `libc.so.6`. Прапорець `RTLD_LAZY` вказує завантажувачу виконувати відкладений резолвінг внутрішніх символів самої бібліотеки під час їх першого використання.
2. **`dlsym(libc_handle, "puts")`:** Обходить хеш-таблиці символів `.gnu.hash` завантаженого модуля `libc.so.6` і повертає пряму віртуальну адресу функції `puts()`. Важливо: цей виклик НЕ використовує трамплін `puts@plt` даного бінарного файла й НЕ оновлює його комірку в GOT! Це дозволяє нам дізнатися еталонну адресу до того, як наша програма зробить перший виклик `puts()`.
3. **`dl_iterate_phdr(callback, data)`:** Системний виклик `glibc`, який обходить усі завантажені у процес об'єкти ELF (головний виконуваний файл, `libc.so`, `ld-linux.so`) та передає у callback-функцію структуру `dl_phdr_info`. Структура містить базову адресу завантаження модуля (`dlpi_addr`), його ім'я та масив заголовків сегментів пам'яті.

## 4. Збирання та практичні режими виконання

Поведінка програми варіюється залежно від прапорців компіляції та змінних середовища.

### Сценарій A: Збірка з підтримкою Lazy Binding (відкладене зв'язування)

Для збірки програми у класичному режимі відкладеного зв'язування вимкніть Full RELRO за допомогою прапорця `-Wl,-z,lazy`:

```bash
$ gcc -O0 -g -Wl,-z,lazy proj-plt-got-inspector.c -o inspector_lazy -ldl
```

Запуск отриманого файла продемонструє двокрокову зміну комірки GOT під час виконання.

### Сценарій B: Примусове зв'язування через `LD_BIND_NOW`

Якщо запустити скомпільований бінарний файл із прапорцем оточення `LD_BIND_NOW=1`:

```bash
$ LD_BIND_NOW=1 ./inspector_lazy
```

Динамічний завантажувач `ld-linux.so` обчислить віртуальну адресу `puts()` ще **до** передачі керування у функцію `main()`. Всі виклики через PLT одразу виконуватимуть прямий перехід у `libc.so`.

### Сценарій C: Збірка у режимі Full RELRO

У разі збірки бінарного файла із прапорцями Full RELRO (`-Wl,-z,relro,-z,now`):

```bash
$ gcc -O0 -g -Wl,-z,relro,-z,now proj-plt-got-inspector.c -o inspector_full_relro -ldl
```

Секція `.got.plt` заповнюється повністю до запуску `main()`, після чого переводиться у режим *Read-Only* за допомогою `mprotect()`. Будь-яка спроба модифікувати значення у GOT під час виконання викликає апаратне переривання MMU та помилку `SIGSEGV`.

## 5. Покроковий розбір у налагоджувачі GDB

Найкращий спосіб побачити модифікацію GOT на рівні машинних інструкцій — використати налагоджувач **GDB**.

### Крок 1: Запуск GDB та зупинка на вході в `main`

Запускаємо налагоджувач і встановлюємо точку зупинки на вході у головну функцію:

```bash
$ gdb ./inspector_lazy
(gdb) break main
(gdb) run
```

### Крок 2: Знаходження адреси трампліну та комірки GOT

Дисасемблюємо трамплін `puts@plt`:

```gdb
(gdb) disassemble puts@plt
Dump of assembler code for function puts@plt:
   0x0000000000001030 <+0>:	jmp    *0x2fe2(%rip)        # Адреса GOT: 0x1036 + 0x2fe2 = 0x4018
   0x0000000000001036 <+6>:	push   0x0
   0x000000000000103b <+11>:	jmp    0x1020 <.plt>
End of assembler dump.
```

З аналізу інструкції `jmp *0x2fe2(%rip)` бачимо, що комірка `GOT[puts]` розташована за віртуальною адресою `0x4018`.

### Крок 3: Перевірка значення у GOT до виклику

Прочитаємо 64-бітне значення за адресою `0x4018` до виконання виклику `puts()`:

```gdb
(gdb) x/gx 0x4018
0x4018:	0x0000000000001036
```

**Результат:** Значення `0x1036` точно відповідає адресі другої інструкції трампліну (`puts@plt + 6`)! Це підтверджує початковий неініціалізований стан відкладеного зв'язування.

### Крок 4: Проходження виклику `puts()` та повторна перевірка

Виконуємо крок налагодження до завершення виклику `puts()`:

```gdb
(gdb) next
--> [АКТИВАЦІЯ PLT] Вітання з динамічно зв'язаної функції puts()!

(gdb) x/gx 0x4018
0x4018:	0x00007ffff7e425a0
```

**Результат:** Запис у GOT змінився на `0x7ffff7e425a0` — це точна адреса функції `puts` у пам'яті `libc.so`. Всі наступні виклики `puts@plt` переходитимуть за цією адресою миттєво.

## 6. Трасування резолвера через `bpftrace`

Для системних адміністраторів та інженерів продуктивності доступний спосіб трасування викликів `_dl_runtime_resolve` у реальному часі за допомогою eBPF:

```bpftrace
// script.bt: Трасування викликів динамічного резолвера в Linux
uprobe:/lib64/ld-linux-x86-64.so.2:_dl_runtime_resolve* {
    @resolve_calls[comm] = count();
    printf("[eBPF] Процес %s (PID %d) викликав _dl_runtime_resolve!\n", comm, pid);
}
```

Запуск цього скрипту дозволяє виявити програми в системі, які активно використовують Lazy Binding і створюють додаткові накладні витрати на пошук символів під час виконання.

## 7. Можливі пастки та діагностика типових помилок

Під час дослідження PLT та GOT розробники можуть зіштовхнутися з кількома нетиповими ситуаціями:

1. **Компілятор оптимізував виклик (`-O2` / `-O3`):** У разі використання високих рівнів оптимізації GCC може замінити виклик `printf("hello\n")` на інструкцію `puts("hello")` або повністю інлайнити код, якщо визначення функції доступне через Link-Time Optimization (LTO). Завжди використовуйте прапорці `-O0 -fno-builtin` під час дослідницьких експериментів.
2. **Символ викликається з іншої бібліотеки:** Якщо функція викликається всередині тієї ж самої `.so` бібліотеки, де вона визначена, і символ позначено прапорцем приватності (видимість `STV_HIDDEN`), компілятор генерує прямий відносний перехід `%rip`-relative без залучення PLT та GOT.
3. **Сегментація пам'яті у Full RELRO:** Якщо програма скомпільована з Full RELRO, спроба записати нове значення у комірку GOT через C-покажчик (`*(uintptr_t*)got_ptr = new_addr`) призведе до аварійного завершення програми із сигналом `SIGSEGV`. Захищені сторінки пам'яті потребують попереднього виклику `mprotect(addr, size, PROT_READ | PROT_WRITE)`.
