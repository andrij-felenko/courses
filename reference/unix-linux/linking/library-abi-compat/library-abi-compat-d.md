# Сумісність ABI бібліотеки й що її ламає

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

У світі розробки програмного забезпечення на C та C++, особливо в середовищах Unix та Linux, поняття сумісності відіграє ключову роль у забезпеченні стабільності систем. Коли ви постачаєте динамічну бібліотеку (shared library, `.so`), програми, які з нею скомпільовані, очікують певної поведінки не лише на рівні викликів функцій, але й на бінарному рівні. Саме тут виникає поняття **ABI** (Application Binary Interface).

Ця стаття детально розглядає, що таке ABI, чим він відрізняється від API, як працює вирівнювання даних у пам'яті, як C++ таблиці віртуальних функцій впливають на бінарну сумісність, та як використовувати сучасні інструменти, такі як `libabigail` (зокрема `abidiff`), для перевірки зворотної сумісності ваших бібліотек.

---

## 1. Різниця між API та ABI

Перш ніж заглиблюватися в технічні деталі, варто чітко розмежувати API та ABI.

**API (Application Programming Interface)** — це інтерфейс на рівні вихідного коду. Він визначає, які функції, класи, типи даних та макроси доступні розробнику. Якщо ви змінили API (наприклад, видалили функцію або змінили типи аргументів), програма користувача **не скомпілюється**. 
Поломка API виявляється на етапі компіляції.

**ABI (Application Binary Interface)** — це інтерфейс на бінарному рівні, на рівні машинного коду та оперативної пам'яті. ABI визначає:
- Як аргументи передаються у функції (через регістри чи через стек).
- Який розмір мають базові типи даних (`int`, `long`, `size_t`).
- Як структури (structs) та класи розташовуються в пам'яті (memory layout, вирівнювання).
- Як декоруються імена функцій у C++ (name mangling).
- Де і як розташовані таблиці віртуальних функцій (vtable) і віртуальні вказівники (vptr) в C++ об'єктах.

Якщо ви ламаєте ABI, програма клієнта, яка була скомпільована зі старою версією вашої бібліотеки, може успішно завантажити нову версію бібліотеки під час виконання, але **зазнає краху (segfault) або почне працювати некоректно** (memory corruption). Це найгірший вид помилок, оскільки вони не виявляються компілятором.

## 2. Сумісність ABI на рівні C

Мова C має відносно простий і стабільний ABI, який залежить від апаратної архітектури (наприклад, x86_64, ARM64) та операційної системи. В Unix/Linux для x86_64 використовується стандарт System V AMD64 ABI.

### 2.1. Розміри типів та Вирівнювання (Alignment / Padding)

Структури в C не просто розташовують свої поля одне за одним. Процесори працюють значно швидше, коли дані вирівняні в пам'яті за адресами, кратними їхньому розміру. 

Розглянемо структуру:
```c
struct MyStruct {
    char a;  // 1 байт
    int b;   // 4 байти
};
```
Наївне припущення: розмір `MyStruct` становить 5 байт (1 + 4).
Реальність: розмір становить 8 байт. Чому?
Оскільки тип `int` має бути вирівняний по межі 4 байт, компілятор вставляє 3 байти відступу (padding) після поля `char a`.

![Вирівнювання в структурі](/reference/unix-linux/linking/library-abi-compat/img/struct-layout.svg)

### 2.2. Що ламає C ABI?

Будь-яка зміна, що впливає на розмір структури або зсув (offset) її полів, є порушенням ABI (ABI break).

1. **Зміна розміру базового типу.** Наприклад, зміна поля з `int` на `long`.
2. **Додавання поля в середину структури.** Якщо ви додаєте нове поле між `a` та `b`, зсув `b` зміниться. Старий клієнтський код буде звертатися до старої адреси, де тепер лежить ваше нове поле, що призведе до катастрофи.
3. **Видалення поля.** Знову ж таки, це зсуває всі наступні поля.
4. **Додавання поля в кінець структури.** Чи це безпечно? **Ні**, якщо клієнтська програма самостійно виділяє пам'ять під структуру (наприклад, на стеку як локальну змінну або масив `struct MyStruct arr[10];`). Якщо нова бібліотека очікує структуру більшого розміру (бо ви додали туди поле), вона прочитає або запише дані поза межами виділеної пам'яті клієнта (buffer overflow).
5. **Зміна сигнатури функції.** Зміна типу параметрів або значення, що повертається. Навіть якщо типи мають однаковий розмір (наприклад, `int` і `float`), вони передаються через різні регістри процесора згідно зі стандартом виклику (calling convention).

#### Як додавати нові дані безпечно (Pimpl & Opaque Pointers)?
Щоб мати змогу безпечно розширювати бібліотеку на C, структури повинні бути «непрозорими» (Opaque Pointers). Клієнтський код має знати лише про те, що структура існує, але не її вміст:

```c
// header.h (API)
typedef struct MyContext MyContext;
MyContext* my_context_create(void);
void my_context_do_work(MyContext* ctx);
void my_context_destroy(MyContext* ctx);
```
Клієнт ніколи не виділяє `MyContext` на стеку і не звертається до його полів напряму. Розробник бібліотеки може вільно додавати та видаляти поля у визначенні `struct MyContext` всередині своїх `.c` файлів, і це ніколи не зламає ABI, оскільки вказівник `MyContext*` завжди має стабільний розмір (8 байт на 64-бітних системах).

## 3. Сумісність ABI на рівні C++

C++ ABI є набагато складнішим, ніж C ABI. Окрім вирівнювання структур, тут грають роль декорування імен, віртуальні функції, таблиці `vtable`, розміри порожніх класів, винятки та RTTI. Найвідомішим стандартом є Itanium C++ ABI, що використовується у GCC та Clang на Linux.

### 3.1. Name Mangling (Декорування імен)
Оскільки C++ підтримує перевантаження функцій (однакове ім'я, різні аргументи), компілятор генерує унікальні імена для кожної функції. Наприклад, `void foo(int)` може перетворитися на `_Z3fooi`, а `void foo(double)` на `_Z3food`.
Зміна параметрів функції або її константності (`const`) змінить декороване ім'я, і динамічний лінкувальник просто не знайде символ під час запуску (Unresolved symbol error). Це порушення ABI.

### 3.2. Таблиці віртуальних функцій (vtable) та vptr
Коли клас має принаймні одну віртуальну функцію, компілятор додає до пам'яті об'єкта невидимий вказівник (`vptr`), який вказує на масив вказівників на функції — таблицю `vtable`.

Розглянемо базовий клас:
```cpp
class Base {
public:
    virtual void doA();
    virtual void doB();
private:
    int x;
};
```
Таблиця `vtable` матиме такий вигляд:
`vtable[0]` -> `Base::doA()`
`vtable[1]` -> `Base::doB()`

Якщо у новій версії бібліотеки ви додасте нову віртуальну функцію **перед** існуючими:
```cpp
class Base {
public:
    virtual void doNewThing(); // НОВЕ!
    virtual void doA();
    virtual void doB();
private:
    int x;
};
```
Тепер `vtable` має такий вигляд:
`vtable[0]` -> `Base::doNewThing()`
`vtable[1]` -> `Base::doA()`
`vtable[2]` -> `Base::doB()`

Стара клієнтська програма, скомпільована проти старого заголовка, при виклику `obj->doA()` спробує викликати функцію за індексом `0`. Але в новій бібліотеці за індексом `0` знаходиться `doNewThing()`. Викличеться неправильна функція!
**Правило:** Ніколи не додавайте нові віртуальні функції в середину класу і не змінюйте їхній порядок. (Додавання в кінець `vtable` часто є безпечнішим, але також може мати нюанси з множинним спадкуванням).

### 3.3. Empty Base Class Optimization (EBCO)
У C++ порожній клас (без даних-членів) має розмір 1 байт. Проте, якщо він є базовим класом для іншого класу, компілятор зазвичай оптимізує його, щоб він займав 0 байт. Зміна класу з порожнього на непорожній (додавання хоча б одного `char`) зламає оптимізацію EBCO, що різко збільшить розмір усіх дочірніх класів, ламаючи їхній memory layout.

### 3.4. Зміни в C++ Standard Library
C++ ABI також залежить від стандартної бібліотеки. Найвідоміший припадок — це перехід GCC на новий C++11 ABI. Реалізація `std::string` змінилася: раніше вона використовувала Copy-On-Write (COW), що було заборонено новим стандартом. Змінився розмір і структура `std::string`. Функції, які приймали `std::string`, отримали нові декоровані імена (через `abi:cxx11` тег). Бібліотеки, зібрані старим компілятором, були несумісні з новим клієнтським кодом без перекомпіляції.

## 4. Версіонування символів (Symbol Versioning)

Щоб полегшити біль ABI-несумісності в Linux (формат ELF), використовується **Symbol Versioning**. Цей механізм дозволяє мати в одній `.so` бібліотеці кілька версій однієї функції.

Якщо ви виявили, що вам **треба** змінити ABI функції, ви можете залишити стару реалізацію зі старим тегом версії (наприклад `MYLIB_1.0`), і додати нову реалізацію з новим тегом (`MYLIB_2.0`).

Старі програми, які вже були злінковані з вашою бібліотекою, будуть прив'язані до тегу `MYLIB_1.0` і продовжать викликати стару функцію. Нові програми під час компіляції лінкуватимуться до нової, `MYLIB_2.0` за замовчуванням. Це дозволяє розвивати бібліотеку, не ламаючи бінарну сумісність для існуючих користувачів (саме так розвивається `glibc`).

## 5. Інструменти для перевірки ABI: abidiff (libabigail)

Відслідковувати кожну зміну очима в складному проєкті неможливо. Для автоматизації цього процесу Red Hat розробили набір інструментів **libabigail**, одним з яких є утиліта **`abidiff`**.

`abidiff` аналізує DWARF-інформацію (дебажні символи) двох `.so` файлів і знаходить розбіжності в ABI (зміни розміру структур, зсувів, видалення функцій).

### 5.1. Використання abidiff

Щоб інструмент міг працювати, бібліотеки треба зібрати з відлагоджувальною інформацією (`-g`):

```bash
# Збираємо стару і нову версію бібліотеки
gcc -g -shared -fPIC old.c -o libmylib.so.1
gcc -g -shared -fPIC new.c -o libmylib.so.2

# Порівнюємо їх
abidiff libmylib.so.1 libmylib.so.2
```

Якщо зміни відсутні, команда нічого не виведе і поверне код 0. Якщо ви, наприклад, змінили тип поля структури, `abidiff` видасть детальний звіт:

```text
Functions changes summary: 0 Removed, 0 Changed, 0 Added function
Variables changes summary: 0 Removed, 0 Changed, 0 Added variable
Type changes summary: 1 type changed

1 type with local changes:

  [C] 'struct MyStruct' changed:
    type size changed from 64 to 128 (in bits)
    1 data member insertion:
      'double new_field', at offset 64 (in bits)
```
Це явний сигнал розробнику, що нова бібліотека ламає ABI і вимагає збільшення мажорної версії (soname bump). Інтеграція `abidiff` у пайплайни CI/CD є золотим стандартом розробки системних бібліотек під Linux.

## 6. Висновки та правила безпечного ABI

Збереження ABI є одним із найскладніших завдань при розвитку бібліотек. Щоб уникнути проблем:

1. **Ховайте деталі реалізації:** Використовуйте Pimpl у C++ або непрозорі вказівники у C. Клієнти не повинні знати розмір або внутрішню структуру ваших даних.
2. **Ніколи не додавайте і не видаляйте віртуальні функції** у відкритих класах C++.
3. **Використовуйте резервні поля (padding/reserved fields):**
   ```c
   struct Config {
       int version;
       int param1;
       void* reserved[4]; // Резерв для майбутніх розширень
   };
   ```
4. **Використовуйте Symbol Versioning**, якщо неминуче доведеться зламати ABI функції в ELF-бібліотеці.
5. **Автоматизуйте:** Використовуйте `abidiff` (libabigail) або `abi-compliance-checker` в CI для раннього виявлення випадкових поломок ABI.

Розуміння та повага до ABI робить вашу бібліотеку надійною платформою, на якій розробники можуть без страху будувати свої застосунки.
