</preknowlist>

Запуск оновленої динамічної бібліотеки у системі Linux часто завершується раптовим аварійним виходом програми з помилкою `SIGSEGV` (Segmentation Fault) або непомітним псуванням даних у пам'яті. При цьому вихідний код програми може успішно компілюватися з новими заголовковими файлами без жодного попередження компілятора. Джерелом цієї проблеми є аварія на бінарному рівні виконання — порушення сумісності ABI (Application Binary Interface).

Коли виконуваний файл лінкується з динамічною бібліотекою (`.so`), динамічний завантажувач (`ld.so`) зв'язує точки виклику функцій та зсуви даних безпосередньо в оперативній пам'яті. Якщо внутрішня структура даних або порядок виклику у бінарному файлі бібліотеки змінилися, машинний код клієнтської програми продовжує звертатися до старих адресових зсувів, що призводить до катастрофічних наслідків під час виконання.

## Межа між кодом та бінарником: API проти ABI

Розмежування програмного інтерфейсу (API) та бінарного інтерфейсу (ABI) виникає на межі між етапом компіляції сирцевого коду та етапом виконання машинного коду процесором.

**API (Application Programming Interface)** є угодою на рівні мови програмування (C або C++). Він визначає назви функцій, типи аргументів, макроси, оголошення структур та класів, які доступні програмісту через заголовкові файли (`.h` / `.hpp`). Зміна API (наприклад, зміна імені функції або видалення параметра) виявляється компілятором під час збирання: компіляція завершується помилкою, і бінарний файл взагалі не створюється.

**ABI (Application Binary Interface)** є угодою на рівні машинного коду, оперативної пам'яті та архітектури процесора. ABI визначає низку низькорівневих параметрів:
- Фізичний розмір базових типів даних (`sizeof(int)`, `sizeof(long)`, `sizeof(void*)`).
- Правила вирівнювання (alignment) та відступів (padding) у структурах.
- Угоду про виклики функцій (calling convention): які регістри процесора використовуються для передачі аргументів, хто очищає стек та як повертаються значення.
- Схему декорування імен функцій (name mangling) у C++.
- Точне розташування вказівника на таблицю віртуальних функцій (`vptr`) та порядок елементів у самій таблиці `vtable`.
- Формат представлення винятків та таблиць розгортання стеку (`.eh_frame`).

```
Джерело змін       | Вплив на API | Вплив на ABI | Результат для користувача
-------------------|--------------|--------------|-----------------------------------------
Зміна імені полів  | Ламає        | Сумісний*    | Код не компілюється; бінарник працює ok
Зміна порядку полів| Сумісний     | Ламає        | Код компілюється ok; аварія у runtime!
Додавання полів    | Сумісний     | Ламає        | Непередбачуване руйнування пам'яті
```
*\* За умови збереження вирівнювання, розміру та публічних заголовків.*

Якщо розробник бібліотеки змінює ABI, зберігаючи API недоторканим, старий виконуваний файл під час запуску із новою версією бібліотеки `.so` потрапляє у пастку: машинний код клієнта розраховує на одну бінарну структуру, а бібліотека надає зовсім іншу.

## Угоди викликів та бінарні стандарти системних архітектур

На найнижчому рівні ABI визначається стандартом конкретної апаратної архітектури та операційної системи. В операційних системах Unix та Linux для 64-бітних процесорів x86_64 застосовується стандарт **System V AMD64 ABI**, а для архітектури ARM64 — стандарт **AAPCS64 (Procedure Call Standard for the Arm 64-bit Architecture)**.

### Розподіл регістрів та передача аргументів

Угода про виклики (calling convention) регулює, які регістри процесора використовуються для передачі аргументів у функцію, а які — для повернення результатів:

- **System V AMD64 ABI (x86_64):** Перші 6 цілочисельних аргументів або вказівників передаються через регістри `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`. Дійсні числа передаються через регістри `xmm0`–`xmm7`. Решта аргументів записуються у стек у зворотному порядку. Значення повертається через `rax` (або `rax:rdx` для 128-бітних структур).
- **AAPCS64 (ARM64):** Перші 8 аргументів передаються через загальні регістри `x0`–`x7`, а дійсні числа — через `v0`–`v7`.

Крім того, регістри поділяються на дві категорії відносно збереження стану при виклику:
1. **Caller-saved (volatile):** Регістри, вміст яких функція має право довільно змінювати (`rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11` на x86_64). Якщо викликаюча програма потребує збереження значень цих регістрів, вона зобов'язана зберегти їх у своєму стековому кадрі перед викликом `call`.
2. **Callee-saved (non-volatile):** Регістри, стан яких викликана функція зобов'язана відновити перед поверненням `ret` (`rbx`, `rsp`, `rbp`, `r12`–`r15` на x86_64).

### Вирівнювання стека

Стандарт System V AMD64 ABI вимагає, щоб перед виконанням інструкції `call` стек був вирівняний по межі **16 байтів** (`%rsp + 8` має бути кратним 16 у точці входу у функцію). Сучасні векторизовані інструкції (AVX, AVX-512) генерують невідворотний збій `SIGSEGV`, якщо намагаються виконати векторний запис `movaps` за невирівняною адресою стека. При невідповідності прапорців компілятора між бібліотекою та клієнтом це вирівнювання ламається.

## Анатомія пам'яті C: Вирівнювання, padding та зсуви полів

На рівні мови C сумісність ABI базується на фізичному розташуванні даних у пам'яті. Сучасні процесори вимагають, щоб змінні базових типів розташовувалися за адресами пам'яті, які є кратними їхньому розміру. Це явище називається вирівнюванням даних (data alignment).

### Правила розрахунку відступів у структурах

Для забезпечення вирівнювання компілятор вставляє між полями структури порожні невидимі байти — відступи (padding). Правила вирівнювання за стандартом System V AMD64 ABI є наступними:

1. Кожне поле структури вирівнюється за адресою, кратною `alignof(T)` (для `int32_t` це 4 байти, для `uint64_t` або вказівника — 8 байтів).
2. Загальний розмір всієї структури `sizeof(Struct)` має бути кратним вирівнюванню її найширшого поля. Для цього компілятор додає відступи у кінець структури (tail padding).

Розглянемо структуру даних у заголовку бібліотеки версії 1:

:::tabs
```c
// Структура на C
struct Data {
    char a;    // 1 байт (offset 0x00)
               // 3 байти padding (offset 0x01..0x03)
    int b;     // 4 байти (offset 0x04..0x07)
};
```
```cpp
// Аналогічна структура на C++ (з тими ж правилами System V ABI)
struct Data {
    char a;    // 1 байт (offset 0x00)
               // 3 байти padding
    int b;     // 4 байти (offset 0x04..0x07)
};
```
:::

Хоча сума розмірів полів становить 5 байтів (1 + 4), фізичний розмір `sizeof(struct Data)` у пам'яті дорівнює 8 байтам через 3 байти відступу після `char a`.

![Розташування полів у пам'яті та зсуви](/reference/unix-linux/linking/library-abi-compat/img/struct-layout.svg)
*Поняття вирівнювання полів у структурах мови C. Вставка поля short c у версії 2 змінює зсуви наступних елементів, що ламає ABI для раніше скомпільованого коду.*

### Що саме ламає C ABI у структурах

Будь-яка зміна у заголовковому файлі бібліотеки, яка змінює під час компіляції зсув (offset) хоча б одного поля або загальний розмір структури `sizeof`, є незворотним зламом ABI.

1. **Зміна порядку полів:** Перестановка полів місцями змінює їхні зсуви. Старий бінарний файл, звертаючись за зсувом `0x04`, очікує прочитати `int b`, але прочитає інший тип даних.
2. **Вставка нового поля в середину структури:** Вставка зміщує всі наступні поля на величину розміру нового поля та його відступів.
3. **Видалення поля:** Видалення поля згортає зсуви наступних елементів назад, викликаючи плутанину в адресації.
4. **Зміна типу існуючого поля:** Зміна `int` на `long` (з 4 на 8 байтів на 64-бітній платформі) змінює як розмір самого поля, так і зсуви всіх елементів після нього.
5. **Додавання поля в кінець структури:** На перший погляд здається безпечним, але це **також ламає ABI**, якщо клієнтський код виділяє структуру на власному стеку або у вигляді масиву (`struct Data arr[10];`). Старий клієнт виділяє на стеку 8 байтів на об'єкт, тоді як новий код бібліотеки очікує 16 байтів. Під час запису у нове поле бібліотека перезапише чужі змінні на стеку клієнтської програми.

:::tabs
```c
// ВЕРСІЯ 1 та ВЕРСІЯ 2 на C (демонстрація зламу ABI через вставку поля)
typedef struct {
    int id;
    int flags; // НОВЕ ПОЛЕ у версії 2! Зсув name змістився з 4 на 8 байтів!
    char name[32];
} UserRecord;
```
```cpp
// У C++ клас без Pimpl зазнає точного такого ж зміщення полів у пам'яті
struct UserRecord {
    int id;
    int flags; // Вставка поля змінює memory layout для всіх методів
    char name[32];
};
```
:::

Для порівняння, аналогічний код на мові C++ з використанням ідіоматичних контейнерів виглядає так:

:::tabs
```c
// C-версія: зміна структури ламає зсуви у бінарнику
#include <stdint.h>

typedef struct {
    uint32_t id;
    uint32_t flags; // Вставка зміщує name з offset 4 на offset 8
    char name[64];
} UserRecord;

void process_user(const UserRecord* user);
```
```cpp
// C++ версія: ідіоматичний підхід з прихованням даних за допомогою Pimpl
#include <string_view>
#include <cstdint>
#include <memory>

class UserRecord {
public:
    UserRecord(uint32_t id, std::string_view name);
    ~UserRecord();

    [[nodiscard]] uint32_t id() const noexcept;
    [[nodiscard]] std::string_view name() const noexcept;

private:
    struct Impl;
    std::unique_ptr<Impl> impl_; // Фіксований розмір 8 B — ABI повністю захищено
};
```
:::

### Пастки з упаковкою структур та бітовими полями (Bitfields)

Використання директив упаковки структур `#pragma pack(n)` або специфікаторів `__attribute__((packed))` створює додаткові пастки ABI:

- Упакована структура видаляє всі відступи padding, що робить її розмір меншим, але звернення до полів стає невирівняним. Якщо клієнтська програма компілюється без атрибута `packed`, а бібліотека зібрана з ним, розходження в зсувах полів виникає миттєво.
- **Бітові поля (Bitfields):** Порядок розміщення бітових полів усередині цілочисельного контейнера є специфічним для реалізації компілятора (implementation-defined). GCC та MSVC можуть розміщувати біти у зворотній послідовності. Зміна типу контейнера бітового поля з `unsigned int` на `uint64_t` змінює бінарну упаковку всього об'єкта.

## Складність C++ ABI: Манґлінг, vtable та структура об'єктів

Бінарний інтерфейс C++ є значно складнішим і крихкішим за C ABI. Специфікація Itanium C++ ABI, яка є стандартом для компіляторів GCC та Clang на Linux, визначає низькорівневу поведінку всіх конструктів мови: від декорування імен до таблиць віртуальних методів.

### Декорування імен (Name Mangling)

Оскільки C++ підтримує перевантаження функцій, простори імен та шаблони, компілятор повинен створити унікальне ім'я символу для кожної функції у таблиці символів ELF.

Наприклад, функція `int Account::deposit(double amount)` перетворюється компілятором у декорований символ `_ZN7Account7depositEd`.

Будь-яка зміна сигнатури функції (додавання параметра з значенням за замовчуванням, зміна `const`-кваліфікатора, зміна типу аргументу) створює **новий декорований символ**.

Коли клієнтська програма, скомпільована зі старим заголовком, намагається завантажити нову бібліотеку, динамічний лінкер `ld.so` видає помилку: `undefined symbol: _ZN7Account7depositEd` і негайно зупиняє виконання.

### Таблиці віртуальних функцій (vtable) та вказівники vptr

Кожен клас, який містить бодай одну віртуальну функцію, дістає від компілятора приховане поле-вказівник — `vptr` (virtual table pointer). Зазвичай воно розміщується на початку об'єкта (зсув `0x00`).

Вказівник `vptr` вказує на масив вказівників на функції — таблицю `vtable`. Під час виклику віртуального методу (`obj->draw()`) компілятор генерує машинний код, який звертається до `vtable` за фіксованим індексом:

```
Машинна інструкція виклику virtual метода (індекс N):
1. Read vptr = *(obj + 0)
2. Read func_ptr = *(vptr + N * sizeof(void*))
3. Call func_ptr(obj)
```

![Зсув індексів у vtable при зміні віртуальних методів](/reference/unix-linux/linking/library-abi-compat/img/vtable-layout.svg)
*Схема розташування vptr та vtable об'єкта C++. Вставка нової віртуальної функції перед існуючими змінює індекси у таблиці, призводячи до виклику чужого методу при виконанні старого клієнтського коду.*

Якщо у новій версії бібліотеки розробник додає нову віртуальну функцію на початок або в середину класу, індекси всіх наступних функцій у `vtable` зміщуються:

- Старий клієнт розраховує, що `draw()` знаходиться за індексом `0`.
- У новій бібліотеці за індексом `0` опинилася нова функція `audit()`, а `draw()` змістилася на індекс `1`.
- При виклику `obj->draw()` програма виконає код `audit()`, що призведе до виконання невірного коду та аварії.

```cpp
// ==================== Ламання vtable у C++ ====================
// ВЕРСІЯ 1
class Widget {
public:
    virtual void draw();   // vtable[0]
    virtual void resize(); // vtable[1]
};

// ВЕРСІЯ 2 (ЗЛАМАНО ABI!)
class Widget {
public:
    virtual void audit();  // vtable[0] — НОВИЙ МЕТОД ЗМІСТИВ ІНДЕКСИ!
    virtual void draw();   // vtable[1] (старий код викликає тут audit!)
    virtual void resize(); // vtable[2]
};
```

### Множинне спадкування, EBCO та таблиці винятків (.eh_frame)

У складніших ієрархіях C++ ABI ламається через наступні механізми:

1. **Зміна порядку базових класів:** При множинному спадкуванні (`class C : public A, public B`) компілятор розташовує поля `A`, а потім поля `B`. Зміна порядку базових класів змінює зсуви полів та вимоги корекції вказівника `this` (this-adjustment offset у vtable).
2. **Порушення оптимізації порожнього базового класу (EBCO):** У C++ порожній клас без даних-членів має розмір 1 байт. Проте коли він використовується як базовий клас, компілятор оптимізує його розмір до 0 байтів. Якщо у новій версії бібліотеки до базового класу додають хоча б один `char`, EBCO вимикається, і розмір усіх похідних класів раптово зростає на величину вирівнювання (зазвичай на 4 або 8 байтів).
3. **Обробка винятків та таблиці DWARF unwind (`.eh_frame`):** Передавання винятків (exceptions) через межі динамічних бібліотек вимагає строгої відповідності структур RTTI (`std::type_info`) та таблиць розгортання стеку `.eh_frame`. Якщо класи винятків змінюють свою структуру або базові класи, механізм `catch` не зможе порівняти типи, і програма аварійно завершиться через виклик `std::terminate()`.
4. **Зміни у стандартній бібліотеці (STL):** Зміна внутрішньої структури стандартних класів створює системні зсуви ABI. Детальний опис цього прецеденту наведено у матеріалі [Історія зміщення C++11 ABI](book:unix-linux/library-abi-compat/hist-cxx11-abi.md).

## Вплив прапорців компілятора на сумісність ABI

Навіть якщо вихідний код бібліотеки не змінювався ні на одну лінійку, зміна прапорців компіляції під час збирання бінарного файлу `.so` може радикально зламати ABI.

### Критичні прапорці компілятора

- `-D_FILE_OFFSET_BITS=64`: На 32-бітних архітектурах Linux цей прапорець змінює системний тип `off_t` з 32-бітного цілого на 64-бітне ціле (`off64_t`). Якщо бібліотеку зібрано з `-D_FILE_OFFSET_BITS=64`, а клієнтський код — без нього, розміри всіх системних структур, які містять розміри файлів (`struct stat`), розійдуться у 2 рази.
- `-fshort-enums`: Примушує компілятор обирати мінімально можливий цілочисельний тип для `enum` (наприклад, `uint8_t` замість `int32_t`). Це змінює розмір полів-перелічень у структурах з 4 байтів до 1 байта.
- `-fno-exceptions` та `-fno-rtti`: Вимикають генерацію таблиць розгортання стеку та інформації про типи під час виконання. Бінарні файли, зібрані з підтримкою винятків, не можуть безпечно викликати функції з бібліотеки, зібраної з `-fno-exceptions`.
- `-mabi=sysv` проти `-mabi=ms`: Визначають угоду про виклики функцій на рівні процесора.

```bash
# Небезпечна збірка: зміна розміру enum ламає ABI для існуючих клієнтів!
gcc -shared -fPIC -fshort-enums -o libdata.so data.c
```

## Вбудовані функції (Inline) та шаблони як пастка ABI

Функції, позначені ключовим словом `inline` у заголовкових файлах C/C++, а також шаблони C++ (templates) мають унікальну особливість з точки зору ABI: **їхній машинний код компілюється безпосередньо всередину виконуваного файлу клієнта**.

Якщо розробник бібліотеки змінює внутрішню реалізацію `inline`-функції або методу шаблону у новій версії заголовкових файлів:

1. Старий клієнтський бінарний файл містить вбудовану старову версію інструкцій машинного коду.
2. Під час виконання старий вбудований код звертається до нових полів динамічної бібліотеки `.so`, використовуючи застарілу логіку.
3. Процес розсинхронізації між вбудованим кодом клієнта та кодом динамічної бібліотеки неможливо виправити підключенням нової `.so` бібліотеки — вимагається повна перекомпіляція клієнта.

**Правило:** Публічні заголовки динамічної бібліотеки не повинні містити складної логіки у `inline`-функціях. Логіка має бути винесена у `.c` / `.cpp` файли реалізації.

## Архітектурні паттерни для збереження ABI

Для збереження стабільності бінарного інтерфейсу у системному програмуванні застосовують спеціальні архітектурні підходи.

### Паттерн Pimpl (Pointer to Implementation) та Opaque Pointers

Найбільш надійним способом захисту ABI є повне приховання полів структури або класу за вказівником на приватну реалізацію.

У публічному заголовку оголошується лише вказівник на структуру, повне визначення якої знаходиться у вихідному файлі бібліотеки. Завдяки цьому зовнішній розмір об'єкта завжди дорівнює розміру одного вказівника (8 байтів), незалежно від того, скільки полів буде додано чи видалено всередині бібліотеки.

Детальний практичний розбір реалізації цього паттерна мовами C та C++ з використанням `std::unique_ptr` наведено у статті [Практична реалізація ABI-безпечного Pimpl](book:unix-linux/library-abi-compat/proj-abi-safe-pimpl.md).

### Резервні поля (Reserved Padding)

Якщо використання Pimpl є недопустимим через накладні витрати на динамічну пам'ять, у структурах передбачають резервні поля:

:::tabs
```c
// Резервні байти у C-структурі для збереження фіксованого розміру
struct HardwareConfig {
    uint32_t baud_rate;
    uint8_t parity;
    uint8_t stop_bits;
    uint8_t reserved[10]; // Резервні байти для майбутніх полів
};
```
```cpp
// C++ альтернатива: резервний масив з фіксованим розміром
#include <cstdint>
#include <array>

struct HardwareConfig {
    uint32_t baud_rate;
    uint8_t parity;
    uint8_t stop_bits;
    std::array<uint8_t, 10> reserved{}; // Захист загального розміру
};
```
:::

Коли у версії 2 виникає потреба додати нове поле `uint8_t flow_control`, його розміщують за рахунок зменшення масиву `reserved` до `9` байтів. Загальний розмір `sizeof(struct HardwareConfig)` та зсуви решти полів залишаються незмінними.

### Абстрактні інтерфейсні класи (Pure Virtual Interfaces)

У C++ створюють класи, які містять **виключно** чисті віртуальні функції та не мають жодних даних-членів:

```cpp
class IStreamReader {
public:
    virtual ~IStreamReader() = default;
    virtual size_t read(std::span<std::byte> buffer) = 0;
    virtual void close() = 0;
    // Нові віртуальні методи додаються ЕКСКЛЮЗИВНО в кінець класу!
};
```

Оскільки клас не має полів даних, його розмір дорівнює лише розміру `vptr` (8 байтів). Додавання нових методів у кінець класу додає записи в кінець `vtable`, не ламаючи індекси існуючих методів.

### Фабричні функції замість виділення пам'яті клієнтом

Слід заборонити клієнтському коду самостійно виділяти пам'ять під структури бібліотеки (на стеку чи через `malloc(sizeof(T))`). Створення та видалення об'єктів має відбуватися виключно через фабричні функції бібліотеки:

:::tabs
```c
// C-підхід: виділення пам'яті виконує бібліотека
MyContext* my_context_create(void);
void my_context_destroy(MyContext* ctx);
```
```cpp
// C++ підхід: фабричний метод повертає розумний вказівник
#include <memory>

class MyContext;
[[nodiscard]] std::unique_ptr<MyContext> create_context();
```
:::

Завдяки цьому зміна розміру об'єкта всередині бібліотеки не призводить до виділення недостатньої кількості пам'яті на боці клієнта.

## Версіонування символів у форматі ELF

Операційна система Linux надає потужний системний механізм вирішення конфліктів ABI у форматі ELF — **GNU Symbol Versioning**. Цей механізм дозволяє зберігати усередині однієї динамічної бібліотеки `.so` **декілька реалізацій однієї і тієї ж функції** для різних версій ABI.

Зв'язування здійснюється за допомогою скрипта версій лінкера (version script):

```text
# mylib.map
MYLIB_1.0 {
    global:
        data_process;
    local: *;
};

MYLIB_2.0 {
    global:
        data_process;
} MYLIB_1.0;
```

У сирцевому коді бібліотеки розробник прив'язує реалізації функцій до відповідних версій символів за допомогою директив препроцесора:

:::tabs
```c
// Реалізація для старих бінарників версії 1.0 (C)
int data_process_v1(int id) {
    return id * 10;
}
__asm__(".symver data_process_v1, data_process@MYLIB_1.0");

// Реалізація для нових бінарників версії 2.0 (C)
int data_process_v2(int id, int flags) {
    return (id + flags) * 10;
}
__asm__(".symver data_process_v2, data_process@@MYLIB_2.0");
```
```cpp
// C++ реалізація з символами різної версії у GNU C++
extern "C" {
    int data_process_v1(int id) {
        return id * 10;
    }
    __asm__(".symver data_process_v1, data_process@MYLIB_1.0");

    int data_process_v2(int id, int flags) {
        return (id + flags) * 10;
    }
    __asm__(".symver data_process_v2, data_process@@MYLIB_2.0");
}
```
:::

Символ з двома собачками `@@MYLIB_2.0` є версією за замовчуванням: з нею лінкуються всі нові програми під час компіляції. Старі вже скомпільовані програми під час запуску продовжують звертатися до `@MYLIB_1.0`.

Завдяки версіонуванню символів системна бібліотека `glibc` у Linux зберігає бінарну сумісність з програмами, скомпільованими понад 20 років тому.

## Автоматизована перевірка та аудит ABI в CI/CD

Відстежувати зміни ABI вручну у великому проекті неможливо. Сучасний процес розробки вимагає автоматизованого аудиту бінарного інтерфейсу на кожному етапі CI/CD.

Найбільш досконалим інструментом аудиту є бінарний аналізатор **libabigail** від компанії Red Hat. Інструмент `abidiff` порівнює відлагоджувальну інформацію DWARF у двох `.so` файлах і генерує звіт про всі зміни у зсувах полів, розмірах типів та віртуальних таблицях.

Детальні інструкції щодо використання утиліт `abidiff`, `abidw` та створення конфігурацій пригнічення наведено у матеріалі [Довідник інструментарію libabigail](book:unix-linux/library-abi-compat/api-libabigail.md).

Інтеграція перевірок `abidiff` у пайплайни CI дозволяє автоматично блокувати пулл-реквести, які випадково ламають бінарну сумісність бібліотеки, і сигналізувати про необхідність підняття мажорної версії `SONAME`.
