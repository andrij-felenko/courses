# 📜 Еволюція виконуваних форматів Unix: від a.out до ELF

Історія стандартів виконуваних файлів в операційних системах Unix — це еволюція від найпростіших лінійних дампів пам'яті до складної, двокомпонентної метаструктури, здатної адаптуватися до віртуальної пам'яті, динамічного зв'язування та жорстких вимог безпеки. 

Коли Кен Томпсон та Денніс Рітчі розробляли перші версії Unix на PDP-7 та PDP-11 на початку 1970-х років, комп'ютери мали лічені кілобайти оперативної пам'яті, а концепція розділюваних об'єктних бібліотек ще не існувала. Створений тоді формат отримав назву **`a.out`** (скорочення від *assembler output*).

## Архітектура a.out та її технологічні межі

Формат `a.out` був надзвичайно простим. Файл починався з фіксованого 32-байтного заголовка (`struct exec`), за яким послідовно розташовувалися лише три блоки даних:
1. **`.text`** — бінарний код інструкцій процесора.
2. **`.data`** — ініціалізовані глобальні змінні.
3. **Таблиця символів** та інформація про релокацію.

Параметри незаініціалізованих змінних (**`.bss`**) визначалися єдиним числом у заголовку, що вказувало, скільки додаткової пам'яті ядро має виділити й обнулити одразу після блоку `.data`.

```
+-------------------+
|  exec header      |  (32 байти)
+-------------------+
|  .text section    |  (Код)
+-------------------+
|  .data section    |  (Ініціалізовані дані)
+-------------------+
|  Symbol table     |  (Символи компонування)
+-------------------+
|  Relocation info  |  (Адресні поправки)
+-------------------+
```

Ця схема бездоганно працювала в раніх версіях Unix, поки програма завантажувалася в єдиний неперервний фізичний або віртуальний адресний простір. Однак у 1980-х роках із поширенням мережевих систем, графічних оболонок (X Window System) та ростом обсягів ПЗ проявилися принципові недоліки `a.out`:

- **Жорстке фіксування адрес спільних бібліотек:** Для реалізації розділювальних бібліотек (shared libraries) у середовищах з `a.out` розробники операційних систем були змушені централізовано виділяти кожній бібліотеці (наприклад, `libc.so`) унікальний діапазон віртуальних адрес в усій системі. Якщо дві бібліотеки претендували на одну й ту саму адресу пам'яті, процес завантаження руйнувався.
- **Відсутність віртуальної структури секцій:** Формат `a.out` не підтримував довільну кількість секцій. Додати метадані для налагодження, таблиці винятків (exception frames) чи специфічні дані потоків (TLS) без зламу сумісності із заголовком було неможливо.
- **Конфлікт зі сторінковою організацією пам'яті (Paging):** Апаратне забезпечення віртуальної пам'яті оперує сторінками (розміром 4 КиБ або 64 КиБ). Формат `a.out` не гарантував вирівнювання зсувів у файлі відносно розміру сторінки пам'яті, через що ядро Linux або BSD не могло ефективно виконувати відображення файлів у пам'ять за допомогою системного виклику `mmap()`.

## Спроба реформи: Поява COFF

З виходом System V Release 3 (SVR3) у середині 1980-х років компанія AT&T зробила спробу подолати обмеження `a.out`, запровадивши **COFF** (*Common Object File Format*). 

COFF увів концепцію таблиці заголовків секцій. Компонувальник міг створювати довільну кількість секцій із власними іменами та прапорами. Проте COFF мав власні важкі недоліки:
- Обмежена довжина імен секцій та символів (максимум 8 символів у базі, решта виносилася у таблиці рядків через ускладнену систему зсувів).
- Складна й повільна обробка таблиць релокації.
- Слабка підтримка динамічного зв'язування, яке саме ставало стандартом індустрії.

Хоча розширена версія COFF (PE/COFF) пізніше стала основою для виконуваних файлів Microsoft Windows (`.exe` та `.dll`), у світі Unix цей формат розцінили як тимчасовий і недосконалий компроміс.

## Стандартизація ELF у System V Release 4

Наприкінці 1980-х років консорціум Unix System Laboratories (USL) та група стандартизації TIG (*Tool Interface Standards*) розробили формат **ELF** (*Executable and Linkable Format*), який дебютував у **System V Release 4 (SVR4)** у 1989 році.

Творці ELF заклали у фундамент формату фундаментальне архітектурне рішення: **двоїсте бачення (Dual View)**.

1. **Компонувальний погляд (Linking View):** Файл описується таблицею секцій (*Section Header Table*). Компонувальник бачить гранулярні блоки (`.text`, `.data`, `.rodata`, `.bss`, `.comment`, `.debug`), що дозволяє гнучко збирати об'єктні файли.
2. **Виконуваний погляд (Execution View):** Файл описується таблицею заголовків програм (*Program Header Table*). Завантажувач операційної системи взагалі не читає секції — він бачить лише кілька сегментів `PT_LOAD`, які групують секції за правами доступу до пам'яті (Read-Only, Read-Execute, Read-Write) і сторінковим вирівнюванням.

```
       [ Файл ELF ]
       /          \
      /            \
Linking View     Execution View
 (Секції)          (Сегменти)
    |                  |
    v                  v
Компонувальник     Завантажувач
    (ld)             (Kernel/ld-linux)
```

Такий поділ дозволив операційній системі завантажувати гігабайтні двійкові файли за одиниці мікросекунд через простий цикл системних викликів `mmap()`, абсолютно не витрачаючи час на розбір дрібних секцій коду чи символів.

## Перехід Linux на ELF та світове визнання

Світ Linux тривалий час використовував модифікований `a.out` (QMAGIC / ZMAGIC). Однак у 1995 році розробники ядра та стандартної бібліотеки C здійснили масштабний перехід на ELF (починаючи з ядра Linux 1.1.95 та бібліотеки `libc 5`). Основною причиною була необхідність повноцінної підтримки shared libraries без фіксованих адрес пам'яті за допомогою позиційно-незалежного коду (**PIC** — *Position Independent Code*) та таблиць **GOT/PLT**.

Переваги ELF виявилися настільки переконливими, що формат став загальноприйнятим стандартом для:
- Усіх дистрибутивів Linux (x86, ARM, MIPS, RISC-V).
- Операційних систем родини BSD (FreeBSD, OpenBSD, NetBSD).
- Операційної системи Oracle Solaris.
- Ігрових консолей Sony PlayStation (PlayStation 2, 3, 4, 5 використовують модифікації ELF) та Nintendo Switch.
- Вбудованих систем реального часу (RTOS), де ELF є основним форматом прошивок для програмування мікроконтролерів через JTAG/SWD.

Розширюваність ELF дозволила спільноті Linux додавати нові сегменти й секції для захисту від експлойтів (невиконуваний стек `PT_GNU_STACK`, релокація в режимі "тільки для читання" `PT_GNU_RELRO`), виключно швидкого хешування символів (`.gnu.hash`) та відображення системних викликів у користувачеві (`vdso`) без порушення базової специфікації 1989 року.
