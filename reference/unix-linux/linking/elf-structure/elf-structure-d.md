## Вступ до формату ELF

Формат ELF (Executable and Linkable Format) є стандартним форматом двійкових файлів для виконуваних файлів, об'єктного коду, спільних бібліотек (shared libraries) і дампів пам'яті (core dumps) в Unix-подібних операційних системах, таких як Linux, FreeBSD та Solaris. Запроваджений у System V Release 4 (SVR4), він швидко витіснив старіші формати, такі як a.out та COFF, завдяки своїй гнучкості, розширюваності та підтримці динамічного зв'язування і крос-компіляції.

Особливість ELF полягає в тому, що він надає подвійне бачення структури файлу:
1. **З точки зору компонувальника (Linker View):** файл розглядається як набір **секцій** (sections). Це бачення використовується під час статичного зв'язування об'єктних файлів (`.o`). Секції містять код, дані, таблиці символів, інформацію для релокації тощо.
2. **З точки зору завантажувача (Execution View):** файл розглядається як набір **сегментів** (segments). Це бачення використовується операційною системою під час завантаження програми в пам'ять. Сегменти вказують системі, як саме відобразити файл у віртуальний адресний простір процесу.

## Структура файлу ELF

Будь-який ELF-файл починається з **ELF Header** (заголовка ELF). За ним слідують:
- Таблиця заголовків програм (Program Header Table), обов'язкова для виконуваних файлів (вказує на сегменти).
- Різноманітні дані, які становлять вміст сегментів та секцій.
- Таблиця заголовків секцій (Section Header Table), яка використовується під час компонування.

### Заголовок ELF (ELF Header)

Заголовок ELF завжди розташований на початку файлу. Його розмір фіксований (наприклад, 64 байти для 64-бітних систем). Він містить основну інформацію про файл, необхідну системі для його правильної інтерпретації.

Ключові поля заголовка (структура `Elf64_Ehdr` з `<elf.h>`):
- **`e_ident` (Magic bytes):** Перші 16 байт. Завжди починаються з магічного числа `0x7F 'E' 'L' 'F'`. Вони також вказують клас (32- або 64-бітний), порядок байтів (Little або Big Endian) та версію формату.
- **`e_type`:** Тип файлу: `ET_REL` (переміщуваний об'єктний файл, `.o`), `ET_EXEC` (виконуваний файл), `ET_DYN` (спільний об'єкт, `.so`, або виконуваний файл PIE - Position Independent Executable), `ET_CORE` (дамп ядра).
- **`e_machine`:** Архітектура (наприклад, `EM_X86_64` для x86-64, `EM_AARCH64` для ARM64).
- **`e_entry`:** Віртуальна адреса точки входу (Entry Point). Саме з цієї адреси процесор почне виконання інструкцій після завантаження програми. У файлах типу `ET_REL` це поле зазвичай дорівнює нулю.
- **`e_phoff` (Program Header Offset):** Зміщення у байтах від початку файлу до таблиці заголовків програм.
- **`e_shoff` (Section Header Offset):** Зміщення у байтах від початку файлу до таблиці заголовків секцій.

Використовуючи утиліту `readelf`, ми можемо переглянути заголовок ELF:

### Секції та Таблиця заголовків секцій (Section Headers)

Секції — це логічні блоки, на які компілятор і асемблер розбивають код та дані. Вони необхідні компонувальнику (linker) для об'єднання кількох об'єктних файлів у один виконуваний. Кожна секція описується записом у **Section Header Table**.

Найважливіші стандартні секції:
- **`.text`:** Містить скомпільовані машинні інструкції (виконуваний код). Ця секція зазвичай має права доступу "читання" (R) та "виконання" (X), але не "запис" (W).
- **`.data`:** Містить глобальні та статичні змінні, які були явно ініціалізовані ненульовими значеннями. Наприклад, `int my_var = 42;`. Має права "читання" і "запис" (RW).
- **`.bss` (Block Started by Symbol):** Містить глобальні та статичні змінні, які не ініціалізовані або ініціалізовані нулем. В ELF-файлі ця секція займає *нуль байтів*. Натомість, у заголовку секції просто вказується необхідний розмір. Під час завантаження система виділяє пам'ять цього розміру і заповнює її нулями.
- **`.rodata` (Read-Only Data):** Константні дані, такі як рядкові літерали (`"Hello, world!"`) або змінні зі специфікатором `const`.
- **`.symtab` та `.strtab`:** Таблиця символів (імена функцій, змінних) та таблиця рядків (імена секцій та символів).
- **`.rel.text` або `.rela.text`:** Інформація для релокації коду (якщо файл ще не скомпонований остаточно).

Для перегляду секцій використовують команду `readelf -S`:
```bash
$ readelf -S my_program
Section Headers:
  [Nr] Name              Type             Address           Offset
       Size              EntSize          Flags  Link  Info  Align
...
  [14] .text             PROGBITS         0000000000001040  00001040
       00000000000001a1  0000000000000000  AX       0     0     16
  [15] .rodata           PROGBITS         0000000000002000  00002000
       000000000000000c  0000000000000000   A       0     0     4
  [24] .data             PROGBITS         0000000000004000  00003000
       0000000000000010  0000000000000000  WA       0     0     8
  [25] .bss              NOBITS           0000000000004010  00003010
       0000000000000008  0000000000000000  WA       0     0     4
```
Зверніть увагу на прапорці (Flags): `AX` (Alloc, Execute) для `.text`, `WA` (Write, Alloc) для `.data` та `.bss`.

### Сегменти та Таблиця заголовків програм (Program Headers)

У той час як секції існують для компонувальника, **сегменти** існують для операційної системи (завантажувача). Завантажувачу байдуже на поділ між `.text` і `.rodata` — йому лише потрібно знати, що певний шматок файлу має бути завантажений у пам'ять з правами "тільки для читання" і "виконання" (R-E). 

Тому компонувальник групує секції з однаковими правами доступу у великі **сегменти**. Наприклад, секції `.text` і `.rodata` часто об'єднуються в один сегмент типу `PT_LOAD`.

Кожен сегмент описується в **Program Header Table**. Основні типи сегментів:
- **`PT_LOAD`:** Сегмент, який потрібно безпосередньо відобразити (mapped) з файлу в оперативну пам'ять (за допомогою `mmap`). Зазвичай програма має щонайменше два сегменти `PT_LOAD`: один для коду/констант (R-E), інший для даних (RW-).
- **`PT_DYNAMIC`:** Містить інформацію, необхідну для динамічного зв'язування (шляхи до `.so` файлів, таблиці динамічних символів, GOT/PLT тощо). Цей сегмент використовується динамічним компонувальником (`ld-linux.so`).
- **`PT_INTERP`:** Вказує шлях до інтерпретатора програми (зазвичай це динамічний компонувальник, наприклад `/lib64/ld-linux-x86-64.so.2`).
- **`PT_GNU_STACK`:** Спеціальний сегмент, який вказує ядру, чи повинен стек програми бути виконуваним. З міркувань безпеки зазвичай стек не виконуваний (RW-).

Використовуючи `readelf -l`, можна побачити як сегменти, так і те, які секції до них належать (mapping):

## Точка входу (Entry Point) та `_start`

Коли ядро Linux закінчує завантаження ELF у пам'ять (і налаштовує стек, аргументи `argc`/`argv` та змінні оточення), воно передає керування на адресу, вказану в полі `e_entry` ELF-заголовка.

Для програм на C/C++ точка входу — це зазвичай **не** функція `main()`. Точкою входу є символ з назвою `_start` (або `__start`), який надається стандартною бібліотекою С (C Runtime, CRT).

Функція `_start` написана на асемблері. Її головні завдання:
1. Отримати `argc`, `argv` та масив змінних оточення `envp` зі стеку (куди їх поклало ядро).
2. Викликати ініціалізатори (конструктори глобальних об'єктів у C++, функції з атрибутом `__attribute__((constructor))`). Це робиться через виклик функції `__libc_csu_init` або подібної.
3. Викликати користувацьку функцію `main(argc, argv, envp)`.
4. Отримати код повернення, який повернула `main`, і передати його у системний виклик `exit()` (або `_exit()`), щоб коректно завершити процес і викликати деструктори.

Використовуючи `objdump -d`, ми можемо подивитися на код `_start`:
```bash
$ objdump -d -j .text my_program | grep -A 15 "<_start>:"
0000000000001040 <_start>:
    1040:       f3 0f 1e fa             endbr64 
    1044:       31 ed                   xor    %ebp,%ebp
    1046:       49 89 d1                mov    %rdx,%r9
    1049:       5e                      pop    %rsi
    104a:       48 89 e2                mov    %rsp,%rdx
    104d:       48 83 e4 f0             and    $0xfffffffffffffff0,%rsp
    1051:       50                      push   %rax
    1052:       54                      push   %rsp
    1053:       4c 8d 05 56 01 00 00    lea    0x156(%rip),%r8        # 11b0 <__libc_csu_fini>
    105a:       48 8d 0d df 00 00 00    lea    0xdf(%rip),%rcx        # 1140 <__libc_csu_init>
    1061:       48 8d 3d d1 00 00 00    lea    0xd1(%rip),%rdi        # 1139 <main>
    1068:       ff 15 72 2f 00 00       callq  *0x2f72(%rip)        # 3fe0 <__libc_start_main@GLIBC_2.2.5>
    106e:       f4                      hlt    
```
Тут ми бачимо підготовку аргументів для виклику `__libc_start_main`, куди як один із параметрів передається адреса `main` (через регістр `%rdi`).

## Інструменти для аналізу ELF

- **`readelf`**: Універсальна утиліта з пакету `binutils` для читання ELF. Не залежить від бібліотеки BFD, тому часто надійніша.
- **`objdump`**: Зручний для дизасемблювання (`-d`) та перегляду вмісту специфічних секцій (`-s -j .data`).
- **`nm`**: Виводить таблицю символів (список функцій та глобальних змінних) з ELF файлу.
- **`size`**: Швидко показує розміри секцій `.text`, `.data` та `.bss`.
- **`strace` / `ltrace`**: Інструменти для відстеження системних викликів та викликів бібліотечних функцій під час виконання програми, що дозволяє спостерігати за процесом завантаження динамічним компонувальником.

Розуміння структури ELF є критично важливим для системних програмістів, спеціалістів з кібербезпеки (наприклад, для аналізу шкідливого ПЗ або розробки експлойтів, таких як ROP), та розробників компіляторів. Поділ на секції та сегменти демонструє елегантний баланс між зручністю побудови програми та ефективністю її виконання операційною системою.
