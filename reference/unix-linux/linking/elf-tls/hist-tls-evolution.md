# 📜 Історія еволюції локальної пам’яті потоків

Історія механізмів локальної пам'яті потоків (Thread-Local Storage) відображає фундаментальну трансформацію операційних систем Unix від однопотокових монолітних архитектур 1970-х років до високопродуктивних багатопотокових систем із підтримкою симетричного мультипроцесингу (SMP) та мільйонів паралельних потоків у сучасних серверах.

## Епоха однопотокового Unix та системна глобальна змінна errno

У перші два десятиліття розвитку Unix (від перших версій AT&T PDP-11 Unix у 1971 році до масових систем System V Release 4 та BSD 4.3 у наприкінці 1980-х) концепція виконання була строго однопотоковою. Процес розглядався як єдина віртуальна машина з єдиним лічильником інструкцій (Program Counter) та єдиним стеком викликів.

Вся мова C і стандартна бібліотека POSIX проєктувалися виходячи з припущення, що глобальний стан програми є єдиним і недеструктивним. Найбільш показовим прикладом цього підходу була змінна обробки помилок системних викликів `errno`. У системних заголовках Вона оголошувалася просто як глобальний цілочисельний атрибут у секції `.bss`:

```c
extern int errno;
```

Ця модель була елегантною і працювала ідеально у разі виконання одного потоку: коли системний виклик (наприклад, `read()`, `write()` або `open()`) повертав помилковий код `-1`, ядро записувало точний код помилки у цю єдину глобальну комірку пам'яті. Потік негайно зчитував `errno` після повернення з ядра.

Проте з появою комерційних багатопроцесорних систем (Sun Enterprise, SGI Origin, DEC Alpha) та впровадженням багатопотоковості на початку 1990-х років ця схема катастрофічно зламалася. Якщо Потік A виконував системний виклик `read()`, який завершувався з помилкою `EAGAIN` (немає даних для читання), а в цей же мікросекундний проміжок часу Потік B виконував успішний виклик `write()`, який записував у `errno` значення `0`, стан помилки Потоку A виявлявся назавжди втраченим або спотвореним. 

Виникнув класичний стан гонитви (race condition), який унеможливлював створення надійних системних серверів (веб-серверів, баз даних) у багатопотоковому середовищі.

Аналогічна фундаментальна проблема торкнулася великої кількості стандартних функцій C-бібліотеки, які використовували всередині статичні буфери для повернення результатів:
- `strtok()` зберігала вказівник на поточну позицію розбору рядка у статичній змінній.
- `gethostbyname()` повертала вказівник на єдину статичну структуру `struct hostent`.
- `ctime()` та `localtime()` повертали адреси статичних буферів форматованого часу.

## Перша адаптація: Перевхідні функції та POSIX Thread-Specific Data (TSD)

Для розв'язання проблеми системного `errno` розробники стандартних бібліотек Unix вдалися до макросного перенаправлення. Змінну `errno` перетворили з прямого атрибута пам'яті на виклик функції, що повертала вказівник на комірку пам'яті унікальну для кожного потоку:

```c
/* У системних заголовках під час компіляції з прапорцями -D_REENTRANT або -D_THREAD_SAFE */
extern int *__errno_location(void);
#define errno (*__errno_location())
```

Завдяки цьому макросу кожен синтаксичний доступ `if (errno == EAGAIN)` прозоро розвертався у розіменування вказівника `(*__errno_location())`. Всередині реалізація `__errno_location()` зверталася до управляючих структур підсистеми потоків.

Паралельно з цим стандарт POSIX 1003.1c-1995 запропонував інтерфейс **Thread-Specific Data (TSD)** для програмного забезпечення користувача. Модель TSD базувалася на системі динамічних ключів:

```c
int pthread_key_create(pthread_key_t *key, void (*destructor)(void*));
int pthread_setspecific(pthread_key_t key, const void *value);
void *pthread_getspecific(pthread_key_t key);
int pthread_key_delete(pthread_key_t key);
```

### Механізм роботи POSIX TSD у перших бібліотеках (LinuxThreads)

Під час виклику `pthread_key_create()` POSIX-бібліотека виділяла глобальний індекс у загальносистемному масиві ключів процесу (зазвичай до 1024 або 4096 ключів).

Кожен потік мав у своїй керуючій структурі масив вказівників. Виклик `pthread_setspecific(key, ptr)` записував значення `ptr` у слот масиву поточного потоку за індексом `key`. Виклик `pthread_getspecific(key)` зчитував це значення.

### Критичні недоліки моделі POSIX TSD

Незважаючи на те що POSIX TSD розв'язав проблему ізоляції даних, він мав три фатальні недоліки для високопродуктивних систем:

1. **Високі накладні витрати на виконання (Function Call Overhead)**: кожного разу, коли програма запитувала локальну змінну потоку, виконувався повноцінний виклик функції `pthread_getspecific()`. Це спричиняло збереження й відновлення регістрів на стек, створення нового кадру функції, індиректне зчитування з масиву та перевірку меж індексу. У гарячих обчислювальних циклах продуктивність програм падала на 20–40%.
2. **Складність синтаксису та втрата типобезпеки**: замість природного зчитування чи присвоєння `counter++` розробники були змушені алокувати пам'ять у купі через `malloc()`, кастувати вказівники до `void*`, передавати їх у `pthread_setspecific()` та вручну контролювати витоки пам'яті.
3. **Неможливість оптимізацій компілятора**: компілятори (GCC, Sun Studio) розглядали виклики `pthread_getspecific()` як зовніший системний бар'єр з невідомими побічними ефектами. Це блокувало оптимізації винесення виразів за межі циклів (loop-invariant code motion) та реєстровий розподіл.

## Нативна специфікація ELF TLS (2002)

На межі 2000-х років стався кризовий перелом: швидкий розвиток багатоядерних архітектур і вимоги корпоративних систем баз даних (Oracle, MySQL) зробили накладні витрати POSIX TSD неприйнятними.

У 2002 році Ульріх Дреппер (Ulrich Drepper) з Red Hat у тісній співпраці з інженерами Sun Microsystems опублікував фундаментальну специфікацію **"ELF Handling For Thread-Local Storage"**.

Метою специфікації було перенесення відповідальності за локальні дані потоку з рівня користувацьких функцій API на рівень **компілятора, ABI, лінкера та динамічного завантажувача**.

### Ключові інновації специфікації Дреппера:

- **Спеціалізовані ELF-секції**: введення секцій `.tdata` (ініціалізований TLS) та `.tbss` (неініціалізований TLS), які описуються у виконуваному файлі шаблоном `PT_TLS`.
- **Архітектурні топології Variant I та Variant II**: оптимізація розміщення даних у пам'яті з урахуванням регістрової адресації конкретних процесорів (`FS`/`GS` в x86_64, `TPIDR_EL0` в ARM).
- **Чотири класичні моделі доступу (GD, LD, IE, LE)**: надання компілятору можливості згенерувати код прямого читання пам'яті за 1 інструкцію для внутрішніх змінних бінарника, зберігаючи універсальні виклики через `__tls_get_addr` лише для динамічних плагінів.
- **TLS Linker Relaxations**: автоматична перебудова та переписування інструкцій асемблера статичним компонувальником `ld` під час підсумкового збирання бінарника.

## Революція NPTL у Linux та стандартизація в мовах

Впровадження специфікації ELF TLS стало каталізатором для створення нової підсистеми потоків у Linux — **NPTL (Native POSIX Thread Library)**, розробленої Ульріхом Дреппером та Інго Молнаром (Ingo Molnar) у 2002–2003 роках. 

Стара бібліотека LinuxThreads мала модель 1:1 з важким керуючим потоком (manager thread) і не мав апаратної підтримки TLS. NPTL, спираючись на системні виклики `futex`, `clone(CLONE_SETTLS)` та нові специфікатори ELF TLS, дозволила Linux обробляти десятки тисяч потоків із мінімальними накладними витратами, випередивши багатьох комерційних конкурентів.

Успіх специфікації ELF TLS забезпечив її швидку стандартизацію у мовах програмування:

- **GCC extension (2002)**: додавання ключового слова `__thread int x;`.
- **C11 (ISO/IEC 9899:2011)**: впровадження специфікатора зберігання `_Thread_local` та заголовочного файлу `<threads.h>`.
- **C++11 (ISO/IEC 14882:2011)**: введення ключового слова `thread_local`, яке поширило поняття локальності потоку не лише на фундаментальні типи даних, а й на об'єкти з динамічними конструкторами та деструкторами.

Завдяки реалізації ELF TLS сучасні багатопотокові програми звертаються до `thread_local` змінних з тією ж апаратною швидкістю, що й до локальних змінних на стеку, зберігаючи зручність і прозорість глобальної області видимості.
