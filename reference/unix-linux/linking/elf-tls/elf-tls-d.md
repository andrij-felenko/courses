# TLS в ELF: як потік дістає власні глобальні змінні

<preknowlist>
- [Концепції ядра Linux](book:unix-linux/kernel-and-userspace) — базові поняття системних викликів та VFS.
</preknowlist>

Коли ми пишемо багатопотокові програми на C або C++, часто виникає потреба у змінних, які є глобальними з точки зору доступу, але мають унікальний екземпляр для кожного потоку. В C і C++ це реалізується за допомогою ключових слів `__thread` (у GNU C) або `thread_local` (починаючи з C++11). Механізм, що лежить в основі цього, називається **Thread Local Storage (TLS)**. У світі Unix і Linux, де використовується формат виконуваних файлів ELF, реалізація TLS є елегантним, хоча і досить складним поєднанням роботи компілятора, компонувальника (лінкера) та динамічного завантажувача (ld.so).

У цій статті ми детально розберемо, як саме працює TLS у форматі ELF, які існують моделі доступу до TLS (General Dynamic, Local Dynamic, Initial Exec, Local Exec), як задіяні сегментні регістри FS/GS на архітектурі x86_64 та яку роль відіграє функція `__tls_get_addr`.

## Що таке Thread Local Storage?

У класичній моделі пам'яті процесу є глобальні змінні, які розташовуються у секціях `.data` (ініціалізовані) або `.bss` (неініціалізовані). Усі потоки процесу спільно використовують цей адресний простір. Якщо один потік змінює глобальну змінну, інші потоки бачать цю зміну.

Однак часто нам потрібна глобальна змінна, яка є унікальною для кожного потоку. Наприклад, класична змінна `errno`. В епоху однопотокових програм `errno` була просто глобальною змінною. З появою багатопотоковості стало очевидно, що якщо один потік отримає помилку, а інший потік тим часом виконає успішну операцію, `errno` може бути перезаписано, що призведе до гострої проблеми (race condition). Щоб уникнути цього, `errno` стала потоко-локальною (thread-local).

У сучасних стандартах C/C++ ми можемо оголосити таку змінну:

```c
__thread int my_tls_var = 42;
thread_local int cpp_tls_var = 100;
```

Для кожної такої змінної компілятор та лінкер повинні забезпечити механізм, який гарантує, що при зверненні до неї з потоку A, буде прочитано/записано екземпляр для потоку A, а при зверненні з потоку B — екземпляр для потоку B.

## Організація TLS у форматі ELF

Для підтримки TLS у стандарті ELF були введені спеціальні секції:
- `.tdata` — для ініціалізованих TLS-змінних.
- `.tbss` — для неініціалізованих TLS-змінних.

Коли лінкер створює виконуваний файл або спільну бібліотеку, він об'єднує всі `.tdata` та `.tbss` з різних об'єктних файлів у єдиний **TLS-шаблон** (TLS Initialization Image). Цей шаблон описується в ELF-заголовку програмою (Program Header) типу `PT_TLS`.

Важливо розуміти: дані в `PT_TLS` — це лише шаблон. Коли процес стартує або коли створюється новий потік (наприклад, через `pthread_create`), операційна система (або бібліотека pthreads/glibc) виділяє новий блок пам'яті для цього потоку і копіює туди вміст секції `.tdata`, а частину для `.tbss` заповнює нулями. 

Таким чином, кожен потік отримує власну копію TLS-змінних. Але як код дізнається, за якою адресою знаходиться копія саме для поточного потоку?

## Сегментні регістри FS та GS (x86_64)

В архітектурі x86_64 для швидкого доступу до локальних даних потоку традиційно використовуються сегментні регістри, які залишилися у спадок від старих 16- та 32-бітних режимів.

У 32-бітному x86 для цього зазвичай використовувався регістр `GS`. В архітектурі x86_64 для доступу до локальних даних потоку (Thread Control Block, TCB) у просторі користувача (userspace) Linux використовується регістр **`FS`**. (Регістр `GS` використовується ядром для доступу до структур даних конкретного процесора — per-CPU data).

Регістр `FS` вказує на початок Thread Control Block. Коли потік створюється, ядро налаштовує базу регістра `FS` на адресу TCB за допомогою системного виклику `arch_prctl(ARCH_SET_FS, addr)` або через `clone`.

У моделі TLS для x86_64 змінні розташовуються зі зміщенням відносно регістра `FS`. Якщо ми хочемо прочитати TLS-змінну, ми не використовуємо абсолютну адресу, а використовуємо відносну:

```assembly
mov rax, QWORD PTR fs:[offset]
```

Значення `offset` обчислюється на етапі компіляції та лінкування (залежно від моделі доступу). У різних архітектурах використовуються різні регістри (наприклад, `TP` (Thread Pointer) в ARM або RISC-V).

## Динамічні бібліотеки (DSO) та __tls_get_addr

Проблема стає значно складнішою, коли ми використовуємо спільні динамічні бібліотеки (Shared Libraries, `.so`). 
Виконуваний файл має фіксований шаблон TLS, і його зміщення відомі на момент завантаження. Однак програма може завантажувати бібліотеки за допомогою `dlopen()` під час виконання. Кожна така бібліотека може мати свій власний блок `.tdata`/`.tbss`.

Оскільки кількість бібліотек та їх розмір TLS невідомі заздалегідь, неможливо виділити один неперервний блок для всіх TLS змінних під час старту потоку. Глібс (glibc) використовує динамічну структуру для керування цим. 

Для кожної динамічної бібліотеки (і для самого виконуваного файлу) створюється свій модуль (Module ID). Основний виконуваний файл зазвичай має Module ID = 1.
Потік має структуру, яка називається **DTV** (Dynamic Thread Vector). DTV — це масив вказівників, де кожен елемент вказує на блок TLS-даних для певного модуля (бібліотеки).

Для доступу до змінної, що знаходиться у спільній бібліотеці, компілятор генерує виклик спеціальної функції **`__tls_get_addr`**.
Ця функція приймає структуру з двома полями:
1. `ti_module` — ідентифікатор модуля (бібліотеки).
2. `ti_offset` — зміщення змінної всередині TLS-блоку цього модуля.

Функція `__tls_get_addr` знаходить DTV для поточного потоку, перевіряє, чи виділено пам'ять для блоку `ti_module`, якщо ні — виділяє її (лінива алокація), і повертає кінцеву абсолютну адресу змінної (`DTV[ti_module] + ti_offset`).

Виклик цієї функції є досить дорогим (порівняно з одним `mov fs:[...]`), тому розробники ELF та компіляторів розробили кілька різних оптимізованих моделей доступу до TLS.

## Моделі доступу до TLS в ELF

Існує чотири основні моделі (TLS Access Models) для архітектури ELF (на прикладі x86_64). Вони оптимізують доступ до TLS залежно від того, чи відомо, де буде знаходитись змінна (в основному виконуваному файлі чи в динамічній бібліотеці), і чи може цей код бути завантаженим через `dlopen`.

Компілятор GCC/Clang дозволяє вибрати модель за допомогою прапорця `-ftls-model=...` (за замовчуванням компілятор намагається вибрати найзагальнішу, але якщо ми компілюємо виконуваний файл, лінкер може оптимізувати модель).

### 1. General Dynamic (GD)

Це найповільніша, але найбільш універсальна модель. Її можна використовувати будь-де: в основній програмі або в бібліотеці, яка може бути завантажена через `dlopen()`.

У цій моделі код не знає ні ідентифікатора модуля, ні точного зміщення. Тому компілятор генерує код, який отримує ці дані з Global Offset Table (GOT) і викликає `__tls_get_addr`.

Асемблерний код виглядає приблизно так:
```assembly
# Отримуємо адресу структури (module_id, offset) з GOT
lea rdi, [rip + x@tlsgd]
# Викликаємо функцію з libc
call __tls_get_addr@PLT
```

**Переваги:** працює завжди і всюди.
**Недоліки:** виклик функції `__tls_get_addr` при кожному зверненні, додаткові звернення до пам'яті (GOT).

### 2. Local Dynamic (LD)

Якщо ми звертаємось до кількох TLS-змінних, які гарантовано знаходяться в одному модулі (тій самій бібліотеці, що й поточний код), ми можемо оптимізувати General Dynamic.

Замість того, щоб викликати `__tls_get_addr` для кожної змінної, ми можемо викликати `__tls_get_addr` один раз, щоб отримати базову адресу TLS-блоку для нашого модуля (передаючи offset = 0), а потім просто додавати зміщення конкретних змінних (які відомі на етапі лінкування бібліотеки).

```assembly
# Отримуємо базову адресу нашого модуля
lea rdi, [rip + @tlsld]
call __tls_get_addr@PLT
# Тепер в rax знаходиться база
# Для кожної змінної ми просто додаємо зміщення
lea r8, [rax + var1@dtpoff]
lea r9, [rax + var2@dtpoff]
```

**Переваги:** лише один виклик `__tls_get_addr` для багатьох змінних у тій самій бібліотеці.
**Недоліки:** все ще потребує виклику функції при першому доступі.

### 3. Initial Exec (IE)

Ця модель використовується, якщо змінна знаходиться у бібліотеці, яка завантажується *при старті програми* (а не через `dlopen`).

Оскільки бібліотека завантажується одразу, динамічний лінкер (ld.so) може одразу виділити місце для її TLS-даних і обчислити точне зміщення цієї змінної відносно регістра `FS` (відносно Thread Pointer). Це зміщення записується в спеціальний запис у GOT (Global Offset Table).

Тому при доступі до змінної код просто читає це від'ємне або додатне зміщення з GOT, і додає його до `FS`. Виклику `__tls_get_addr` немає!

```assembly
# Читаємо зміщення змінної з GOT
mov rax, QWORD PTR [rip + x@gottpoff]
# Доступ до змінної через FS
mov ecx, DWORD PTR fs:[rax]
```

**Переваги:** дуже швидко (одне читання пам'яті з GOT, потім прямий доступ через FS), немає виклику функції.
**Недоліки:** не може бути використана для бібліотек, що завантажуються динамічно через `dlopen`, оскільки для них зміщення від `FS` не може бути зафіксоване на старті (сталий блок TLS вже виділено). (Щоправда, сучасний glibc має певний резервний простір "surplus TLS", який дозволяє деяким dlopen-бібліотекам використовувати модель IE, але він обмежений).

### 4. Local Exec (LE)

Це найшвидша модель, яка використовується, коли ми точно знаємо, що код буде працювати *лише в основному виконуваному файлі* (або змінна є прихованою і не експортується).

Оскільки основний виконуваний файл завжди є першим у черзі завантаження, зміщення його TLS-змінних відносно `FS` відоме ще на етапі статичного лінкування (link-time) і ніколи не зміниться! 
Тому лінкер може вписати точне число (константу) зміщення прямо в машинний код. Ні GOT, ні `__tls_get_addr` не потрібні.

```assembly
# Прямий доступ до змінної зі сталим зміщенням (наприклад, -4)
mov eax, DWORD PTR fs:[-4]
```

**Переваги:** максимально швидко, як звичайна локальна або глобальна змінна.
**Недоліки:** не працює у спільних бібліотеках (`.so`).

## Оптимізації лінкера (TLS Transitions)

Часто компілятор не знає, де зрештою буде використано код. Наприклад, якщо ви компілюєте файл з `fPIC` (Position Independent Code), компілятор за замовчуванням обере модель General Dynamic.

Однак, коли компонувальник (linker, наприклад `ld` або `lld`) створює фінальний виконуваний файл (а не `.so`), він бачить всю картину. Якщо він помічає код GD, який звертається до змінної, що знаходиться у цьому ж виконуваному файлі, лінкер може переписати (патчити) машинні інструкції GD (перетворити виклик `__tls_get_addr` на `mov fs:[...]`). Це називається **TLS Transitions**.

Саме тому інструкції для доступу до TLS мають специфічну форму (наприклад, `lea rdi, ...`, потім обов'язково `call ...`). Вони спроектовані так, щоб їхній розмір у байтах дозволяв лінкеру перезаписати їх більш ефективними інструкціями моделі LE або IE без зміни загальної довжини коду (щоб не зсувати інші інструкції). Зайві байти просто заповнюються NOP-ами.

## Висновки

Thread Local Storage в ELF і Linux — це результат складної еволюції. Він гарантує високу продуктивність за рахунок апаратної підтримки (сегментний регістр FS у x86_64) та багатошарової архітектури (GD, LD, IE, LE).

Розуміння того, як працює TLS, критично важливе для розробників системного програмного забезпечення, при написанні власних алокаторів пам'яті, або при зневадженні складних проблем із `dlopen` (коли раптово закінчується пам'ять для статичного TLS через модель IE в динамічній бібліотеці).

Завдяки оптимізаціям сучасних компіляторів та лінкерів, у більшості випадків доступ до `__thread` / `thread_local` змінної в основній програмі займає всього одну машинну інструкцію `mov fs:offset, ...`, що робить TLS майже таким же швидким, як використання локальних змінних на стеку.
