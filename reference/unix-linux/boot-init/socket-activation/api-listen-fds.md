# 📋 Контракт передавання дескрипторів: LISTEN_FDS, sd_listen_fds і сховок

Усе, що менеджер служб обіцяє процесові, якому передає готові сокети, вміщається в чотири змінні оточення, одну константу й дві функції — нижче їхній точний опис разом із директивами юніта, які на ці значення впливають. Довідка потрібна тому, що інтерфейс мовчазний і без зворотного зв'язку: служба, яка перевірила не те або взяла не той номер, не дістане ані помилки, ані попередження — вона просто працюватиме не з тим дескриптором.

Усе нижче звірено з чинними сторінками довідника: `sd_listen_fds(3)`, `sd_is_socket(3)`, `sd_notify(3)`, `systemd.socket(5)`.

---

## 1. Змінні оточення

| Змінна | Що в ній | Хто ставить |
| --- | --- | --- |
| `LISTEN_FDS` | кількість переданих дескрипторів, десяткове число | менеджер, перед `exec` |
| `LISTEN_PID` | десятковий номер процесу, якому призначено передавання | менеджер, перед `exec` |
| `LISTEN_FDNAMES` | імена дескрипторів через двокрапку, стільки ж, скільки й дескрипторів | менеджер, перед `exec` |
| `LISTEN_PIDFDID` | номер (inode) pidfd процесу-адресата; з'явилася у версії 259 | менеджер, перед `exec` |

Звірка `LISTEN_PID` із власним `getpid()` — не порада, а частина контракту. Оточення успадковує все піддерево процесів, тож помічник, якого служба запустить із себе, побачить ті самі змінні, хоча дескрипторів йому ніхто не передавав; без звірки він візьме за сокет випадковий відкритий файл під номером 3.

`LISTEN_PIDFDID` затуляє вужчу шпарину. Номери процесів у системі повторно вживані: якщо адресат помер, а номер дістався комусь іншому, самої лише звірки `LISTEN_PID` мало. Тому з версії 259 бібліотека додатково порівнює це значення з [дескриптором процесу](book:unix-linux/pidfd) — сталим посиланням на конкретний процес, яке не переїжджає на іншого разом із номером.

Імена в `LISTEN_FDNAMES` беруться з `FileDescriptorName=` в юніті сокета. Якщо директиви немає, ім'ям стає назва юніта **разом із суфіксом** `.socket` при `Accept=no` і рядок `connection` при `Accept=yes`.

## 2. Нумерація: чому саме 3

```c
#define SD_LISTEN_FDS_START 3
```

Числа 0, 1 і 2 за давньою угодою зайняті стандартними потоками, тож перший вільний номер — 3. Дескриптори лежать поспіль без дірок: від `SD_LISTEN_FDS_START` до `SD_LISTEN_FDS_START + LISTEN_FDS − 1`.

Порядок усередині одного юніта — це порядок рядків `Listen*` у ньому. Між різними юнітами сокетів, які активують ту саму службу, порядок **не визначено** — покладатися можна лише на імена.

![Ліворуч рядки юніта web.socket, праворуч масив дескрипторів 3, 4, 5 з описом кожного; знизу — значення трьох змінних оточення](/reference/unix-linux/boot-init/socket-activation/img/fd-array-map.svg)

*Три рядки `ListenStream=` дають три сусідні числа, а `FileDescriptorName=` дає одне ім'я на всі три: імена в цьому протоколі не унікальні.*

## 3. Функції читання

```c
#include <systemd/sd-daemon.h>   /* pkg-config libsystemd, лінкувати -lsystemd */

int sd_listen_fds(int unset_environment);
int sd_listen_fds_with_names(int unset_environment, char ***names);
```

| | |
| --- | --- |
| **Повертає** | кількість переданих дескрипторів; `0` — не передавали нічого (зокрема й тоді, коли `LISTEN_PID` не збігся з власним номером); від'ємне — код помилки зі знаком мінус |
| **`unset_environment ≠ 0`** | прибирає з оточення `LISTEN_FDS`, `LISTEN_PID`, `LISTEN_PIDFDID` і `LISTEN_FDNAMES` — щоб змінні не поїхали далі в нащадків |
| **`names`** | масив рядків, що закінчується `NULL`, довжиною в кількість дескрипторів; звільняти треба **і кожен рядок, і сам масив** через `free()` |
| **Побічна дія** | обидві функції ставлять `FD_CLOEXEC` на всі передані дескриптори, тож заміну образу в нащадках вони вже не переживуть |

`sd_listen_fds_with_names()` додано у версії 227; до неї імен не було взагалі, і дескриптор шукали лише за номером та за перевіркою типу.

Бібліотека тут не обов'язкова — увесь протокол читається двома `getenv()`. Її користь у дрібній бухгалтерії, яку легко забути зробити руками: звірка номера процесу, `FD_CLOEXEC` на кожному дескрипторі й прибирання змінних.

## 4. Перевірка того, що приїхало

```c
int sd_is_fifo(int fd, const char *path);
int sd_is_socket(int fd, int family, int type, int listening);
int sd_is_socket_inet(int fd, int family, int type, int listening, uint16_t port);
int sd_is_socket_unix(int fd, int type, int listening,
                      const char *path, size_t length);
int sd_is_socket_sockaddr(int fd, int type, const struct sockaddr *addr,
                          unsigned addr_len, int listening);
int sd_is_mq(int fd, const char *path);
int sd_is_special(int fd, const char *path);
```

Усі повертають додатне число, коли дескриптор відповідає описові, `0` — коли не відповідає, і від'ємний код помилки при невдачі. Кожен параметр має «нейтральне» значення, яке вимикає саме цю перевірку:

| Параметр | Нейтральне значення | Що означає |
| --- | --- | --- |
| `family` | `AF_UNSPEC` | родину не перевіряти |
| `type` | `0` | тип сокета не перевіряти |
| `listening` | від'ємне | стан не перевіряти; `0` — вимагати, щоб сокет **не** слухав; додатне — вимагати, щоб слухав |
| `port` | `0` | порт не перевіряти |
| `path` | `NULL` | адресу не перевіряти |
| `length` (у `sd_is_socket_unix`) | `0` | звичайний сокет у файловій системі, а не в абстрактному просторі імен |

`sd_is_socket_sockaddr()` додано у версії 233.

## 5. Мінімальний робочий виклик

Типове завдання — знайти серед переданого сокет із потрібним іменем і переконатися, що це справді слухач.

```c
#include <systemd/sd-daemon.h>
#include <sys/socket.h>
#include <stdlib.h>
#include <string.h>

/* Повертає номер переданого сокета з іменем name або -1. */
int listen_fd_by_name(const char *name)
{
    char **names = NULL;
    int fd = -1;
    int n = sd_listen_fds_with_names(1, &names);   /* 1 — прибрати змінні з оточення */

    if (n <= 0)
        return -1;                                 /* нам нічого не передавали */

    for (int i = 0; i < n; i++) {
        if (fd < 0 && strcmp(names[i], name) == 0)
            fd = SD_LISTEN_FDS_START + i;          /* перше влучання, імена не унікальні */
        free(names[i]);
    }
    free(names);

    /* Потоковий IP-сокет, що вже слухає; порт не перевіряємо. */
    if (fd >= 0 && sd_is_socket_inet(fd, AF_UNSPEC, SOCK_STREAM, 1, 0) <= 0)
        return -1;

    return fd;
}
```

Викликати `bind()` чи `listen()` на такому дескрипторі не треба й не можна: він приходить уже прив'язаним і в стані слухання, а повторний `bind()` поверне «адреса вже зайнята».

## 6. Директиви юніта сокета

| Директива | Значення | Типово |
| --- | --- | --- |
| `ListenStream=` | `SOCK_STREAM`: TCP для IP-адрес, потоковий сокет для шляху | — |
| `ListenDatagram=` | `SOCK_DGRAM`: UDP для IP-адрес, дейтаграмний — для шляху | — |
| `ListenSequentialPacket=` | `SOCK_SEQPACKET`, **лише** для `AF_UNIX` | — |
| `Accept=` | `no` — службі віддають сокет, що слухає; `yes` — менеджер приймає сам і запускає примірник на кожне з'єднання | `no` |
| `Service=` | який юніт служби піднімати; дозволено лише при `Accept=no` | однойменний юніт із суфіксом `.service` |
| `Backlog=` | глибина черги готових з'єднань, беззнакове 32-бітне | `4294967295` |
| `FileDescriptorName=` | ім'я на **всі** дескриптори цього юніта | назва юніта з `.socket` при `Accept=no`, `connection` при `Accept=yes` |
| `MaxConnections=` | скільки примірників одночасно (лише при `Accept=yes`) | `64` |
| `MaxConnectionsPerSource=` | те саме в розрізі однієї адреси-джерела | `0` — вимкнено |
| `TriggerLimitIntervalSec=` / `TriggerLimitBurst=` | запобіжник від каруселі активацій | `2s`; `200` при `Accept=yes`, інакше `20` |

Форми адреси в усіх трьох `Listen*` однакові: саме число — це порт IPv6 (а доступність через IPv4 залежить від `BindIPv6Only=`, який типово успадковує загальносистемне `net.ipv6.bindv6only`); `1.2.3.4:80` — IPv4; `[::1]:80` — IPv6; шлях від кореня — сокет у файловій системі; `@ім'я` — абстрактний простір імен (символ `@` перед прив'язкою замінюють на нульовий байт); `vsock:CID:порт` — `AF_VSOCK`. Порожнє значення будь-якої з `Listen*` скидає **весь** список адрес, набраний доти.

Значення `Backlog=` варте окремого слова, бо його типова величина оманлива. Максимум для 32-бітного числа означає «стільки, скільки дасть система», а дасть система рівно `net.core.somaxconn` — [загальносистемний важіль ядра](book:unix-linux/sysctl-tunables), що зазвичай стоїть на 4096. Обрізання відбувається мовчки: ані юніт, ані журнал про нього не скажуть.

Юніт сокета сам, без жодного рядка від автора, дістає `Before=` на службу, яку активує, і на ціль `sockets.target`; `After=` й `Requires=` на `sysinit.target`; `Before=` й `Conflicts=` на `shutdown.target`. Саме залежність від `sockets.target` і робить так, що всі оголошені сокети існують ще до того, як менеджер візьметься запускати служби.

При `Accept=yes` кожен примірник дістає в оточенні дані про того, хто прийшов: `REMOTE_ADDR` — адресу клієнта (для `AF_UNIX` це шлях або абстрактне ім'я), `REMOTE_PORT` — порт для IPv4 та IPv6, `SO_COOKIE` — cookie сокета в ядрі десятковим числом. Останнє зручне тим, що воно єдине на все життя цього з'єднання, тож за ним зшивають записи журналу з різних місць.

## 7. Сховок дескрипторів

Той самий канал доставки вживають і для дескрипторів, які служба поклала на зберігання сама. Кладуть їх не через оточення, а повідомленням у [протоколі сповіщення менеджера](book:unix-linux/service-notify-protocol): служба пише рядки в сокет, чия адреса лежить у `NOTIFY_SOCKET`, і разом із рядками надсилає самі дескриптори допоміжним повідомленням `SCM_RIGHTS` — [штатним способом передавати відкритий ресурс через сокет у межах машини](book:unix-linux/unix-domain-sockets).

```c
int sd_pid_notify_with_fds(pid_t pid, int unset_environment,
                           const char *state, const int *fds, unsigned n_fds);
```

| Поле повідомлення | Дія |
| --- | --- |
| `FDSTORE=1` | взяти долучені до повідомлення дескриптори на зберігання |
| `FDNAME=…` | ім'я для них; довільні знаки ASCII, крім керівних і `:`, не довше 255 знаків; типово `stored` |
| `FDPOLL=0` | не викидати дескриптор автоматично, коли на ньому з'явиться `POLLHUP` або `POLLERR` (з версії 246) |
| `FDSTOREREMOVE=1` | забрати зі сховку; вживають разом із `FDNAME=` |

Одне повідомлення дає одне ім'я на всі долучені до нього дескриптори — щоб імена були різні, надсилайте окремі повідомлення.

Менеджер приймає `FDSTORE=1`, лише якщо в юніті служби задано ненульовий `FileDescriptorStoreMax=` (типово він **нульовий**, тобто сховок вимкнений); службам із увімкненим сховком менеджер ставить у оточенні `FDSTORE`. Назад дескриптори приїжджають звичайним шляхом — тими самими номерами від 3 і тими самими змінними, тож `sd_listen_fds_with_names()` бачить їх упереміш із сокетами юніта й розрізняє лише за іменами.

Межа тут одна, і про неї легко забути: сховок переживає **перезапуск**, але не зупинку. Коли службу спиняють по-справжньому, сховок викидають і всі дескриптори в ньому закривають — якщо цього не змінено директивою `FileDescriptorStorePreserve=`.
