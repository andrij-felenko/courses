# 📜 Еволюція генераторів initramfs: від mkinitrd до dracut та mkinitcpio

Історія генераторів initramfs у світі Linux відображає фундаментальну трансформацію ядра та простору користувача — від простих shell-скриптів виклику `mke2fs` та `cpio` до складних подійно-орієнтованих інструментаріїв, здатних динамічно аналізувати апаратне забезпечення та будувати граф залежностей служб systemd.

Осмислення цієї еволюції дозволяє зрозуміти, чому різні дистрибутиви прийшли до принципово відмінних рішень і чому уніфікація раннього простору користувача залишається однією з найскладніших системних задач.

---

## Ера блокового mkinitrd та його обмеження (1995–2005)

У появі раннього простору користувача в серії ядер Linux 1.3 ключову роль відігравав механізм **initrd** (англ. *initial RAM disk*). Оскільки initrd вимагав створення віртуального блокового пристрою `/dev/ram0` з повноцінною файловою системою (найчастіше ext2 або minix), перші інструменти генерації образів мали назву `mkinitrd`.

Перша реалізація `mkinitrd` у дистрибутивах Red Hat Linux, Slackware та Debian представляла собою монолітний shell-скрипт. Процес створення образу складався з таких кроків:

1. Створення порожнього файлу фіксованого розміру через `dd` (наприклад, 4096 кілобайтів).
2. Форматування цього файлу у файлову систему ext2 за допомогою `mke2fs`.
3. Монтування створеного образу через пристрій петлі (*loop device*) у тимчасову директорію.
4. Копіювання мінімального набору файлів (інтерпретатора `nash` або `ash`, бінарників `insmod`, модулів ядра та вузлів пристроїв у `/dev`).
5. Демонтування образу та його стиснення алгоритмом `gzip`.

Цей підхід мав фатальні архітектурні вади. Головною з них була **фіксована ємність**. Якщо адмін додавав у конфігурацію додатковий модуль для Fibre Channel контролера або підтримку шифрування, вміст переставав влазити в розрахований обсяг 4 МБ. Спроба збільшити зарезервований розмір призводила до того, що система назавжди втрачала оперативну пам'ять під розмір рамдиска, навіть після переходу в справжній корінь.

Крім того, скрипт ініціалізації всередині образу (часто це був спеціалізований мінімалістичний інтерпретатор Red Hat `nash`) працював імперативно. Він послідовно виконував команды `echo`, `modprobe` та `mount`. Якщо дисковий накопичувач ініціалізувався на 100 мілісекунд пізніше за виклики `modprobe`, завантаження зупинялося з помилкою *Unable to mount root fs*.

```
+-----------------------------------------------------------------------+
|  Старий mkinitrd (блоковий ext2):                                     |
|  dd (4МБ) -> mke2fs -> mount -o loop -> cp modules -> gzip            |
|  Недоліки: фіксована пам'ять, дублювання в кеші, імперативний boot     |
+-----------------------------------------------------------------------+
|  Сучасний dracut / mkinitcpio (потоковий cpio):                        |
|  Аналіз ldd/modinfo -> dracut.conf/HOOKS -> cpio -H newc -> zstd      |
|  Переваги: динамічний розмір, udev/systemd події, host-only відбір    |
+-----------------------------------------------------------------------+
```

## Розділення шляхів: Debian initramfs-tools проти Red Hat dracut

З появою в ядрі Linux 2.6 механізму **initramfs** (розпакування cpio-архіву безпосередньо у `rootfs` на базі ramfs/tmpfs) потреба у блокових пристроях зникла. Проте дистрибутиви по-різному підійшли до створення нових інструментаріїв.

Спільнота Debian створила інструмент **initramfs-tools** (у співіснуванні з альтернативою `yaird`). Головною ідеєю Debian була максимальна легковажність та мінімалізм. Замість важких залежностей initramfs-tools спирався на легкий shell-інтерпретатор `dash` та набір статичних або динамічних утиліт `busybox` / `klibc`. Скрипти розділили на чіткі директорії-фази (`init-top`, `local-top`, `local-premount`), де кожен пакунок (наприклад, `lvm2` або `cryptsetup`) міг покласти свій shell-скрипт.

Натомість компанія Red Hat стикнулася з кризою складності у корпоративному сегменті. У 2008–2009 роках для Red Hat Enterprise Linux 6 старий `mkinitrd` став непосильним баластом. Корпоративні сервери вимагали завантаження з складних каскадних конфігурацій: iSCSI поверх VLAN, FCoE з ротацією шляхів Multipath, LUKS-шифрування поверх LVM2 з RAID6-масивами. Намагання описати всі можливі комбінації імперативними shell-скриптами призводило до «комбінаторного вибуху» у коді.

Розробник Гаральд Гойєр (Harald Hoyer) у 2009 році запропонував радикальне рішення — проєкт **dracut**.

Головна ідея dracut полягала у перенесенні подійного підходу `udev` та `systemd` безпосередньо всередину initramfs. Замість того щоб угадувати порядок підключення пристроїв, dracut запускає демони `udevd` та `systemd` у ранньому просторі користувача. Коли демон udev виявляє блоковий пристрій, спрацьовує відповідне правило, яке сповіщає systemd про готовність юніта. Завантаження здійснюється не за жорстким сценарієм, а за графом залежностей подій.

## Шлях Arch Linux: декларативний та швидкий mkinitcpio

Поки Red Hat будувала універсальний dracut для серверних центрів обробки даних, спільнота Arch Linux розвивала власний генератор — **mkinitcpio** (створений Джуддом Вінетом та розширений розробниками Arch).

Філософія Arch Linux (KISS — *Keep It Simple, Stupid*) вимагала інструменту, який би поєднував максимальну швидкість збирання, прозорість конфігурації та контроль користувача. `mkinitcpio` відмовився від концепції автоматичного припущення конфігурації за замовчуванням.

Замість цього було введено декларативний масив `HOOKS=(...)` у конфігурації `/etc/mkinitcpio.conf`. Кожен хук складається з двох роздільних частин:
1. **Інсталяційний скрипт** (`/usr/lib/initcpio/install/name`), який виконується під час збирання образу на працюючій системі та визначає, які бінарні файли та модулі копіювати.
2. **Скрипт виконання** (`/usr/lib/initcpio/hooks/name`), який потрапляє всередину cpio-архіву та виконується під час завантаження системи.

Величезним проривом у mkinitcpio стала поява хука `autodetect`. При його використанні генератор зчитує з `/sys` список усіх активних PCI/USB пристроїв та системних модулів і залишає в cpio-архіві лише ті драйвери, які реально потрібні даній конкретній машині. Це дозволило зменшити розмір initramfs з 30–50 МБ до 8–12 МБ і прискорити розпакування ядром у кілька разів.

Таблиця нижче підсумовує еволюційні етапи та технічні рішення інструментів генерації:

| Ера / Інструмент | Формат образу | Модель виконання в initramfs | Стратегія відбору файлів | Залежність від systemd |
| :--- | :--- | :--- | :--- | :--- |
| **mkinitrd** (1995) | ext2 image (loop device) | Монолітний імперативний shell-скрипт (`nash`) | Фіксований список файлів та драйверів | Відсутня (пре-systemd ера) |
| **initramfs-tools** (2005) | cpio newc archive | Фазові директорії shell-скриптів (`dash` / `busybox`) | Параметри `most` або `dep` | Опціональна (за замовчуванням POSIX shell) |
| **dracut** (2009) | cpio newc archive | Подійна модель systemd та udev правила | Модульна структура (`modules.d`), `host-only` | Глибока інтеграція systemd |
| **mkinitcpio** (2006) | cpio newc archive | Декларативні хуки (`busybox` або `systemd`) | Декларативний список `HOOKS` + `autodetect` | Опціональна (підтримує обидва двигуни) |

## Сучасний етап: Ера Unified Kernel Images (UKI)

З появою специфікації **Unified Kernel Image (UKI)** у 2020-х роках генератори initramfs увійшли в новий етап свого розвитку.

Раніше генератор створював окремий файл `initramfs.img`, який завантажувач (GRUB чи systemd-boot) передавав ядру через додаткову область пам'яті. Це створювало уразливість у системах із підтвердженим завантаженням (Secure Boot): зловмисник із правами root міг замінити файл `initramfs.img` на модифікований із шкідливим `/init`, і Secure Boot цього б не виявив, оскільки завантажувач перевіряв лише цифровий підпис самого бінарного файлу ядра `vmlinuz`.

Сучасні версії `dracut` (через прапорець `--uefi`) та `mkinitcpio` (через прапорець `-U` або використання `systemd-ukify`) більше не зупиняються на створенні cpio-архіву. Вони викликають компілятор або інструменти ELF/PE для збирання єдиного виконного файлу `.efi`.

Усередині цього виконного файлу розміщуються:
- Завантажувальна заглушка EFI (`systemd-stub`).
- Параметри командного рядка ядра (`.cmdline`).
- Оновлення мікрокоду процесора (`.ucode`).
- Основне ядро Linux (`.linux`).
- Згенерований cpio-архів initramfs (`.initrd`).

Отриманий бінарний файл підписується єдиним приватним ключем Secure Boot (Machine Owner Key, MOK). Це гарантує, що жоден компонент раннього простору користувача не може бути підроблений без порушення цифрового підпису, перетворюючи генератори initramfs з простих пакувальників на криптографічні збирачі цілісних образів завантаження.
